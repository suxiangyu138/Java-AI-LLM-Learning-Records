# 面向对象设计原则（SOLID + 补充原则）

> **文档定位**：Java 后端企业级技术文档 | 面向对象设计原则  
> **核心定位**：设计模式的"内功心法"，所有设计模式遵循的底层规范

---

## 一、核心概念

### 1.1 设计原则与设计模式的关系

```
面向对象设计原则（SOLID + 补充）→ 设计模式（23种）→ 框架底层设计
     ↑ 内功心法              ↑ 具体招式           ↑ 实践应用
```

### 1.2 核心目标

降低耦合度 → 提高复用性 → 增强扩展性与可维护性 → 减少需求迭代改造成本

## 二、底层原理

### 2.1 SOLID 五大核心原则

#### S - 单一职责原则（Single Responsibility Principle）

**一个类只做一件事。** 职责分离、粒度细化，避免"万能类"。

```
❌ 反例：一个类同时负责用户管理、登录鉴权、消息推送
✅ 正例：UserInfoManager + UserLoginService + UserPushService 三个独立类
```

#### O - 开放封闭原则（Open Closed Principle）

**对扩展开放，对修改关闭。** 新增功能通过扩展实现，不修改已有代码。

```
❌ 反例：消息处理类中用 if-else 判断消息类型
✅ 正例：定义 MessageHandler 接口 → Text/Image/VoiceHandler 分别实现
```

#### L - 里氏替换原则（Liskov Substitution Principle）

**子类可替换父类，不破坏原有逻辑。** 子类可扩展，不重写父类核心方法。

```
❌ 反例：鸵鸟继承 Bird，重写 fly() 抛异常
✅ 正例：Flyable 接口独立，鸵鸟不实现 Flyable
```

#### I - 接口隔离原则（Interface Segregation Principle）

**不依赖不需要的接口。** 大接口拆分为多个专用小接口。

```
❌ 反例：单一 UserService 接口包含用户+订单+支付等所有方法
✅ 正例：UserInfoService + OrderService + PaymentService 独立接口
```

#### D - 依赖倒置原则（Dependency Inversion Principle）

**依赖抽象而非具体实现。** 面向接口编程。

```
❌ 反例：业务层直接依赖 RedisUtil 具体实现类
✅ 正例：业务层依赖 CacheService 接口 → RedisCacheImpl / RedissonCacheImpl
```

### 2.2 两大补充原则

| 原则 | 定义 |
|------|------|
| **迪米特法则**（最少知道） | 只与直接朋友通信，减少类间交互 |
| **合成复用原则** | 优先组合/聚合，而非继承 |

## 三、代码实现

### 3.1 依赖倒置示例

```java
// ✅ 依赖抽象接口
public interface CacheService {
    String get(String key);
    void set(String key, String value);
}

@Service
public class UserService {
    private final CacheService cacheService;  // 依赖接口，不依赖具体实现

    public UserService(CacheService cacheService) {
        this.cacheService = cacheService;
    }
}

// 切换缓存实现 → 只需新增实现类，UserService 无需修改
@Service
public class RedisCacheServiceImpl implements CacheService { ... }
```

### 3.2 开放封闭示例

```java
// ✅ 通过扩展处理新消息类型
public interface MessageHandler {
    void handle(Message msg);
}

@Component
public class TextMessageHandler implements MessageHandler { ... }

// 新增图片消息 → 新增类即可，不改原有代码
@Component
public class ImageMessageHandler implements MessageHandler { ... }
```

## 四、实战要点

| 原则 | 落地技巧 |
|------|----------|
| **SRP** | 类名能准确描述其职责，方法不超过 50 行 |
| **OCP** | 用策略模式/模板方法替代 if-else |
| **LSP** | 子类只扩展不修改，继承前先问"is-a"是否成立 |
| **ISP** | 接口方法数控制在 5 个以内 |
| **DIP** | 成员变量声明为接口类型，构造函数注入 |

---

## 五、避坑总结

| 坑点 | 说明 |
|------|------|
| **继承滥用** | 优先用组合而非继承，避免继承层级过深 |
| **接口过胖** | 一个接口包含 10+ 个方法 → 该拆分了 |
| **违反 OCP** | 每新增功能都修改核心类 → 重构为扩展模式 |

---

## 六、企业级最佳实践

- Spring IOC 天然实现 DIP（依赖倒置）
- Netty ChannelHandler 完美体现 SRP + OCP
- 代码审查时用 SOLID 作为检查标准
