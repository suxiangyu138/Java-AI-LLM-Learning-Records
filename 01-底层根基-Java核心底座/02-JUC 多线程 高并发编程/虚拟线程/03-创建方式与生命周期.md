## 1. 创建方式的四种姿势

### 1.1 方式一：`Thread.ofVirtual()` 工厂（JDK 21 新增）

```java
// 最推荐的创建方式：Builder 模式
Thread vt = Thread.ofVirtual()          // 返回 Thread.Builder
    .name("worker-1")                    // 可选：命名（虚拟线程转储友好）
    .unstarted(() -> System.out.println("hello virtual thread"));
vt.start();

// 或直接一步到位
Thread vt2 = Thread.ofVirtual()
    .name("worker-2")
    .start(() -> System.out.println("started directly"));
```

Builder 上的主要方法：

| 方法 | 作用 |
|------|------|
| `name(String)` / `name(String, long)` | 命名；`name("worker-", 0L)` 自动生成 `worker-0, worker-1, ...` |
| `allowSetThreadLocals(boolean)` | 是否允许 ThreadLocal 写入（JDK 21 新增） |
| `inheritInheritableThreadLocals(boolean)` | 是否继承父线程的 inheritable ThreadLocal（默认继承，但 JEP 444 建议设为 false） |
| `unstarted(Runnable)` / `start(Runnable)` | 创建未启动/直接启动 |
| `scheduler(Executor)` | 自定义调度器（特殊场景） |
| `uncaughtExceptionHandler(handler)` | 未捕获异常处理器 |

### 1.2 方式二：`Thread.startVirtualThread()` 便捷方法

```java
// 无命名需求的极简写法
Thread vt = Thread.startVirtualThread(() -> doWork());
```

### 1.3 方式三：`Executors.newVirtualThreadPerTaskExecutor()`（生产首选）

```java
// 每一个任务 → 一个新的虚拟线程；任务结束 → 线程即销毁（不池化！）
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> handleRequest(req));
    executor.submit(() -> handleRequest(req2));
}
// try-with-resources 关闭时：等待已提交任务完成（shutdown + awaitTermination）
```

对应平台线程时代的 `Executors.newFixedThreadPool(n)`——语义差异对比（详见 05 章）：

| 维度 | `newFixedThreadPool(n)` | `newVirtualThreadPerTaskExecutor()` |
|------|:---:|:---:|
| 线程数 | 固定 n | 无上限（每个任务一个虚拟线程） |
| 排队 | 有界/无界队列 | 无队列（直接创建） |
| 池化 | 复用 | **不池化** |
| 适用 | 需要限制并发数的场景 | I/O 密集的"任务即线程"场景 |

### 1.4 方式四：传统 `new Thread()` 兼容（不推荐）

```java
// 技术上兼容但不推荐——虚拟线程专有工厂更清晰
// new Thread() 永远创建平台线程
```

> 🎯 **核心要点**：四种方式本质只有两条路径——**直接 `Thread` 工厂**（细粒度控制）与**执行器**（批量任务）。生产代码优先 `newVirtualThreadPerTaskExecutor()`，与现有 `ExecutorService` 接口无缝替换。

## 2. 命名、特性与 daemon 语义

### 2.1 命名

```java
Thread vt = Thread.ofVirtual().name("req-", 0L).start(task);
// 生成名称：req-0, req-1, req-2...
// 线程转储（jcmd Thread.dump_to_file）中可直接按名称检索
```

### 2.2 `Thread.characteristics()`（JDK 21 新增）

```java
int c = Thread.currentThread().characteristics();
if ((c & Thread.THREAD_CHARACTERISTICS_VIRTUAL) != 0) {
    // 当前在虚拟线程上
}
boolean isVt = Thread.currentThread().isVirtual();   // 更常用
```

> 💡 **第三方库检测**：`isVirtual()` 让库作者可以判断环境——例如连接池可以拒绝虚拟线程（因为池化虚拟线程无意义），框架可以决定默认线程策略。

### 2.3 daemon 语义

```java
Thread vt = Thread.ofVirtual().start(task);
System.out.println(vt.isDaemon());   // true —— 虚拟线程始终是 daemon
```

- 虚拟线程**永远是 daemon**，无法设为非 daemon；
- **JVM 不会等待虚拟线程完成就退出**——主线程结束后，未完成的虚拟线程直接终止；
- 后果：在 `main` 里启动虚拟线程后，主线程不能立刻结束，否则任务可能没跑完。正确做法：显式 `join()` / 使用执行器（关闭执行器时等待任务完成）。

```java
// 错误示范：主线程退出，任务可能被中断
Thread.ofVirtual().start(() -> expensiveWork());
// main 结束 → JVM 退出 → 虚拟线程被强杀

// 正确示范：等待完成
Thread vt = Thread.ofVirtual().start(() -> expensiveWork());
vt.join();                              // 或者
```

## 3. 生命周期与状态机

### 3.1 状态流转

```text
NEW → RUNNABLE → WAITING/TIMED_WAITING（阻塞时）→ RUNNABLE → TERMINATED
       │
       └─（无法出现 BLOCKED 状态的正常运行路径；JDK 24 后 synchronized 阻塞也走卸载）
```

| 状态 | 虚拟线程下的含义 | 说明 |
|------|----------------|------|
| `NEW` | 已创建未 start | 与平台线程一致 |
| `RUNNABLE` | 正在载入线程上执行**或**已入队等待调度 | **注意**：与平台线程不同，`RUNNABLE` 不保证正在运行！ |
| `WAITING` / `TIMED_WAITING` | park 挂起（sleep、锁、I/O） | 已卸载，不占载入线程 |
| `BLOCKED` | 阻塞在监视器上 | JDK 21：synchronized 竞争时出现；JDK 24（JEP 491）后：竞争阻塞同样卸载，**理论上看不到 BLOCKED**（JDK 26 曾修复一个虚拟线程卡在 BLOCKED 状态的 bug，见 08 章） |
| `TERMINATED` | 已结束 | 对象可被 GC |

> ⚠️ **易错点**：`Thread.getState() == RUNNABLE` 在虚拟线程上**不代表正在运行**——可能只是排队等载入线程。线上诊断"卡死"问题时不要只看线程状态，要结合转储中的 `park` 信息与 JFR 事件。

### 3.2 `join()` / `Thread.sleep()` 等基础 API

| API | 虚拟线程行为 |
|------|------------|
| `join()` | 内部 park，可中断；跨虚拟线程等待语义与平台线程一致 |
| `Thread.sleep(millis)` | 定时 park，**不阻塞载入线程**（JDK 21 起） |
| `Thread.yield()` | 仅让出当前载入线程（建议用 `sleep(0)` 或 parkNanos 替代，避免自旋语义差异） |
| `interrupt()` | 唤醒 park，抛出 `InterruptedException`（与平台线程一致） |
| `Thread.onSpinWait()` | 照常可用（CPU 等待提示） |

## 4. 异常处理与中断

### 4.1 未捕获异常

```java
// 虚拟线程内的未捕获异常默认终止该线程，但不影响其他线程与 JVM
Thread vt = Thread.ofVirtual()
    .uncaughtExceptionHandler((t, e) -> {
        System.out.println(t.getName() + " failed: " + e.getMessage());
        // 记录日志、上报指标
    })
    .start(() -> { throw new RuntimeException("boom"); });

// 在 ExecutorService 中：submit 的 Future 会捕获异常，get() 时抛出
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<?> f = executor.submit(() -> { throw new IllegalStateException("x"); });
    f.get();   // 抛 ExecutionException
}
```

### 4.2 中断语义（与平台线程完全一致）

```java
Thread vt = Thread.ofVirtual().start(() -> {
    try {
        Thread.sleep(10_000);          // 可中断的阻塞点
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();   // 恢复中断标志（标准惯例）
        return;
    }
});
Thread.sleep(100);
vt.interrupt();                        // 中断生效：sleep 立即抛 InterruptedException
```

| 中断场景 | 行为 |
|---------|------|
| 虚拟线程在 `sleep`/`park`/`lock` 阻塞中 | 立即唤醒并抛 `InterruptedException` |
| 虚拟线程在运行中 | 仅设置中断标志，业务代码用 `isInterrupted()` 感知 |
| 虚拟线程被 `join` 等待 | 等待方（平台/虚拟均可）抛 `InterruptedException` |

> 💡 虚拟线程使"线程中断"变得更加可用：之前池化线程被中断会污染池状态（中断标志残留），虚拟线程每任务独立、用完即弃，中断成为干净的任务取消手段。配合结构化并发的取消机制（06 章）更佳。

## 5. ThreadLocal：虚拟线程时代的取舍

### 5.1 问题：百万线程 × 每个线程的 ThreadLocal

```java
// 每个虚拟线程默认允许使用 ThreadLocal
ThreadLocal<String> traceId = new ThreadLocal<>();
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // 100 万任务 → 100 万虚拟线程
    // 若每个任务都 set 了 1KB 的 ThreadLocal → 峰值额外 ~1GB 堆内存
}
```

平台线程时代 ThreadLocal 的问题被虚拟线程**放大**：

1. **内存放大**：线程数从几十变成百万级，ThreadLocal 值随线程数线性增长；
2. **泄漏风险**：线程池复用使未清理的 ThreadLocal 长期存活；虚拟线程用完即弃虽不会"长存"，但**高峰并发 × 大对象 = 瞬时堆压力 + GC 压力**；
3. **继承语义模糊**：虚拟线程不继承普通 ThreadLocal（只有 `InheritableThreadLocal` 可继承，且官方建议关闭）。

### 5.2 官方建议与三条出路

| 方案 | 适用场景 | 说明 |
|------|---------|------|
| **ScopedValue**（推荐） | 只读上下文（traceId、用户身份、租户） | JDK 25 转正（JEP 506），见 07 章——不可变、自动清理、可继承到子任务 |
| 方法参数显式传递 | 少量参数 | 最清晰，无隐藏状态 |
| ThreadLocal（谨慎） | 必须写可变的线程局部状态 | 控制 value 大小、及时 remove |

```java
// 创建虚拟线程时明确关闭 ThreadLocal 支持（JDK 21 支持）
Thread.ofVirtual()
    .allowSetThreadLocals(false)
    .inheritInheritableThreadLocals(false)
    .start(task);
```

> 🎯 **核心要点**：虚拟线程时代的原则是——**能不用 ThreadLocal 就不用**；确实需要"线程局部上下文"，用 ScopedValue；JDK 自身也遵循此原则，在 JDK 25/26 中移除了若干假设线程池复用的 ThreadLocal 缓存（见 08 章）。

## 6. 经典 Demo：百万虚拟线程

```java
import java.util.concurrent.CountDownLatch;

public class MillionVirtualThreads {
    public static void main(String[] args) throws Exception {
        // 平台线程对比：小堆下 ~1600 个即 OOM
        // for (int i = 0; i < 1_000_000; i++) new Thread(() -> sleepQuietly()).start();

        CountDownLatch latch = new CountDownLatch(1_000_000);
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 1_000_000; i++) {
                executor.submit(() -> {
                    try { Thread.sleep(1_000); }     // 1M 个同时睡 1 秒
                    catch (InterruptedException ignored) {}
                    latch.countDown();
                });
            }
            latch.await();
        }
        System.out.println("1,000,000 virtual threads completed");
    }
}
```

```bash
# 运行（JDK 21+，无需任何 flag）
java MillionVirtualThreads.java
# 输出：1,000,000 virtual threads completed
# 内存实测：约 400MB 堆 + 极小原生内存（对比：平台线程版本 ~1600 个就 OOM）
```

> ⚠️ **正确理解这个 Demo**：它展示的是"可创建性"，不是"应创建性"。生产环境仍要考虑峰值内存与任务真实价值（08 章），并通常配合限流（Semaphore，05 章）防止失控。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 四种创建方式，生产首选 `Executors.newVirtualThreadPerTaskExecutor()`，语义是"每任务一线程、不池化、用完即弃"；
> 2. 虚拟线程永远 daemon、`RUNNABLE` 不等于正在运行、中断/异常语义与平台线程一致；
> 3. ThreadLocal 在百万级线程下是内存放大与 GC 压力来源，官方出路是 ScopedValue（07 章）。

**思考题**：

1. 主线程结束时虚拟线程还在跑，会发生什么？（→ 2.3）
2. `Thread.getState()` 显示 `RUNNABLE` 的虚拟线程一定在运行吗？（→ 3.1）
3. 为什么"线程池 + ThreadLocal"的泄漏问题在虚拟线程下变成了"高峰内存压力"？（→ 5.1）
4. `newVirtualThreadPerTaskExecutor()` 的 `close()` 行为是什么？（→ 1.3，05 章展开）
