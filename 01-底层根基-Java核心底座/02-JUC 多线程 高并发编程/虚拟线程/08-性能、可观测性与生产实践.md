## 1. 性能画像：内存与切换成本

### 1.1 内存对比（核心数字）

| 项目 | 平台线程 | 虚拟线程 |
|------|:---:|:---:|
| 每线程元数据 | ~1MB 原生栈（默认 `-Xss1m`，预留） | **200-300 字节**（对象本身）+ 堆上分块栈 |
| 栈 | 原生内存，固定，不可伸缩 | 堆上 chunk，按需增长（实际使用量计） |
| 1 万线程 | ~10GB 虚拟内存（原生区） | ~几十 MB 堆（浅栈场景） |
| 100 万线程 | **必然 OOM**（实测小堆下 ~1600 个即挂） | 实测 ~**401MB 堆**（100 万 sleep 任务） |

```text
为什么平台线程栈不能省：
- 内核线程栈无法在运行中伸缩 → 必须按最坏情况预留 ~1MB
- 且预留的是地址空间 + 部分物理内存，直接进"Native 内存"（非堆）

为什么虚拟线程栈能省：
- 栈是堆上的 StackChunk 链，浅栈线程只用几百字节
- 深度递归时自动分块增长（初始大小可用 `-XX:VirtualThreadStackSize` 调节，默认过小会提前 `StackOverflowError`），用完随对象被 GC
```

### 1.2 切换成本对比

| 切换类型 | 成本量级 | 说明 |
|---------|:---:|------|
| OS 线程上下文切换 | ~微秒级 | 内核态：寄存器/MMU/TSS/缓存失效 |
| 虚拟线程 mount/unmount | ~纳秒~百纳秒级 | 用户态：Continuation 状态保存/恢复 |
| 极端场景 | OS 切换可吃 **~80% CPU** | 大量平台线程疯狂切换时 |

> 💡 **直觉换算**：一次 OS 切换 ≈ 几百次虚拟线程切换。虚拟线程"阻塞即换人"之所以可行，正是因为切换成本低到可以频繁发生。

## 2. 实测基准数字

### 2.1 可复现基准一：百万线程睡眠

```java
// 平台线程版：jmap 显示堆 1.85MB 时即 OOM（原生栈吃光地址空间）
// for (int i = 0; i < 1_000_000; i++) new Thread(() -> sleepQuietly()).start();
//
// 虚拟线程版（JDK 21+，4GB 堆内）：1,000,000 个全部完成
// 堆中约 999,999 个 VirtualThread 实例 ≈ 401MB，其余是栈 chunk
```

| 版本 | 1M 线程睡眠 1h 结果 |
|:---:|:---:|
| 平台线程（小堆） | ~1600 个 OOM |
| 平台线程（大堆实测报告） | ~25,000 个 OOM |
| 虚拟线程 | ✅ 完成，~401MB 堆 |

> ⚠️ **数字的正确读法**：401MB/百万 ≈ **每虚拟线程约 400B-1KB 有效成本**（对象+空栈），但这是"全阻塞"理想场景。若任务带大局部变量、深栈或 ThreadLocal，单线程成本会显著上升。

### 2.2 可复现基准二：synchronized 内阻塞（JEP 491 官方）

> 5,000 虚拟线程 × 各自锁的 synchronized 块内 CPU 工作 + sleep 5ms，调度器并行度=1：

| 版本 | 耗时 | 结论 |
|:---:|:---:|------|
| JDK 21 | ~31.8s | 每次 pin 串行 5ms |
| JDK 24 | ~0.454s | 阻塞即卸载，约 70 倍提升 |

### 2.3 基准三：I/O 密集吞吐（量级参考）

```text
8 核、每任务 80ms 阻塞 + 20ms CPU、目标 10,000 QPS：

固定池 40 线程          → 上限 ~400 QPS（线程数是天花板）
虚拟线程（8 载入线程）  → CPU 段 20ms × 10k QPS = 200s/s 超过 8 核 → 上限 ~400 QPS
                          但若 I/O 段占比 95%（20ms I/O + 1ms CPU）
                          虚拟线程上限 → 8 核可支撑 ~8000 QPS（CPU 是天花板）
```

> 🎯 **核心要点**：虚拟线程不产生 CPU，它只把"等 I/O 的时间"还给其他任务。**CPU 占比越高，虚拟线程收益越小**——这是所有性能决策的总纲。

## 3. CPU 密集陷阱：载入线程饥饿

### 3.1 机制：协作式调度的代价

虚拟线程是**协作式**调度（blocking 才让出），没有时间片抢占：

```java
// 危险：一个 CPU 密集虚拟线程霸占一个载入线程
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> jwtDecodeLoop());   // 持续算 5 分钟，绝不阻塞
    executor.submit(() -> dbQuery());          // 被饿死！等不到载入线程
}
// 8 核机器：8 个 CPU 密集任务 = 8 个载入线程全部被占 → 所有 I/O 任务排队
```

- **JWT 校验、JSON 解析、加解密、图像处理**是典型"伪装成 I/O 的 CPU 密集"代码；
- 平台线程时代有 OS 抢占（时间片轮转），虚拟线程时代**没有**；
- 结果：I/O 任务的延迟从毫秒级劣化到秒级，且**无任何异常/告警**——静默退化。

### 3.2 解决方案：CPU 密集任务走独立平台线程池

```java
// 1. 预留 CPU 密集任务的专用平台线程池
ExecutorService cpuPool = Executors.newFixedThreadPool(4, Thread.ofPlatform().name("cpu-").factory());

// 2. 虚拟线程侧遇到 CPU 密集段，桥接到平台池
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> {
        String token = request.getToken();
        Claims claims = cpuPool.submit(() -> jwtParser.parse(token)).get();  // 桥接
        return handle(claims);
    });
}
```

| 方案 | 适用 | 说明 |
|------|------|------|
| 独立平台线程池桥接 | 混布场景（最常见） | `CompletableFuture.supplyAsync(heavy, cpuPool)` 也可 |
| 全部 CPU 密集 | 直接不要用虚拟线程 | 固定池才是正确工具（05 章决策树） |
| 调大 parallelism | 兜底，不推荐 | 载入线程数 = CPU 数，调大反而抢 CPU |

> ⚠️ **识别信号**：`jdk.VirtualThreadSubmitFailed` 事件频繁、载入线程长时间 RUNNABLE 不 park、CPU 密集段吞吐骤降——优先排查"是否 CPU 密集任务进了虚拟线程池"。

## 4. JDK 25/26 稳定性与性能修复回顾

虚拟线程调度器不完美——2025-2026 年修复过的重要问题：

| 问题 | 现象 | 修复版本 |
|------|------|:---:|
| JDK-8370887 | **`Thread.sleep` 密集场景性能回退**：JDK 25 比 JDK 21 更慢 | JDK 25.0.3（2026 年补丁）+ JDK 26 |
| JDK-8373120 | **虚拟线程卡在 BLOCKED 状态**（监视器竞争路径） | JDK 26u（2026-03） |
| JDK-8375130 | 空任务提交的可扩展性优化（JDK-8360046）引入 SPECjbb2015 回退 → **JDK 26 RC 前回退**（保留 setParallelism 与 submit 一致性修正） | JDK 26（回退） |

> 💡 **工程启示**：
> 1. 虚拟线程性能是**版本敏感**的——基准结论要标注 JDK 版本，生产升级 21→25/26 建议跑一遍自己的压测；
> 2. 头部版本（LTS）的 x.0.x 补丁值得跟进（25.0.3 的 sleep 修复就是例子）；
> 3. 官方在功能激进与稳定之间选择**回退**（8375130）——生产环境优先求稳。

## 5. 可观测性工具箱

### 5.1 jcmd 线程转储（虚拟线程专用）

```bash
# 传统文本转储：虚拟线程聚合展示，标记平台/虚拟
jcmd <pid> Thread.dump_to_file -format=text vt-dump.txt

# JSON 转储（推荐）：结构化信息，便于脚本分析
jcmd <pid> Thread.dump_to_file -format=json vt-dump.json
```

```json
// JSON 转储片段（关键字段）
{
  "platformThreads": { "threads": [ ... ] },          // 载入线程（含 ForkJoinPool-1-worker-*）
  "virtualThreads": { "threads": [ ... ] },           // 虚拟线程单独分组
  "threadContainers": [ ... ]                         // 含调度器信息
}
```

| 排查问题 | 看哪里 |
|---------|--------|
| 虚拟线程卡住 | virtualThreads 分组的栈 + `park` 状态 |
| pinning | 载入线程栈中嵌套 `Continuation.run()` + 业务帧 |
| 载入线程数量异常 | platformThreads 中 ForkJoinPool-1-worker-* 数量（应 ≈ parallelism） |
| 阻塞在什么锁上 | 栈帧中的 monitor / LockSupport.park |

### 5.2 JFR 事件（生产级采样）

```bash
java -XX:StartFlightRecording=filename=app.jfr,settings=profile app.jar
jfr print --events 'jdk.VirtualThread*' app.jfr    # 正则匹配全部虚拟线程事件
```

| 事件 | 告警价值 |
|------|---------|
| `jdk.VirtualThreadStart/End` | 吞吐与创建速率（突发创建 → 告警） |
| `jdk.VirtualThreadPinned` | **必须告警**（默认 >20ms 才记录） |
| `jdk.VirtualThreadSubmitFailed` | 调度器过载（队列/池异常） |
| `jdk.ThreadDump` | 定时转储采样 |

### 5.3 生产指标建议

```text
应用层指标（Micrometer/Prometheus 自定义）：
- virtual_threads.peak                   峰值存活虚拟线程数（对比堆内存容量）
- virtual_threads.created_total          创建速率（突发告警）
- carrier_threads.active                 载入线程利用率（高 = CPU 密集风险）
- task_io_wait_p95                      业务 I/O 时延（验证收益）
```

## 6. 生产检查清单

```text
□ 1. 压测前置
       - 压测客户端也要支持高并发（压测机线程/连接数 > 目标并发，否则测的是压测机）
       - 对比基线：固定池 vs 虚拟线程，同 JDK 版本、同配置
       - 记录峰值堆内存：虚拟线程无上限，堆容量就是软上限
□ 2. CPU 密集排查
       - 扫描代码：JWT/JSON/加密等 CPU 密集段是否混入虚拟线程（→ 3.2 桥接）
□ 3. 限流落地
       - Semaphore 保护下游（DB 连接池、外部 API 配额）——05 章
□ 4. 上下文方案
       - ThreadLocal 盘点 → 换 ScopedValue（07 章）
□ 5. 监控告警
       - jdk.VirtualThreadPinned / SubmitFailed 告警
       - 载入线程数、虚拟线程峰值指标
□ 6. 版本核对
       - JDK 21/24/25/26 行为差异（pinning、sleep 性能、调度器修复）→ 本文 4 节
       - 升级后回归压测
□ 7. 转储演练
       - 故障时能 30 秒内拿到 json 转储并定位"哪个虚拟线程在等什么"
```

> 🎯 **核心要点**：虚拟线程上线不是"改一行配置"，而是**限流 + CPU 密集隔离 + 可观测性**三个工程动作的组合。收益可量化（内存 3 个数量级、吞吐 10-50 倍），风险也可量化（无背压、无抢占、版本敏感）。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 内存：平台线程 ~1MB 原生栈 vs 虚拟线程 200-300B 元数据 + 堆上栈（百万线程 ~401MB 堆实测可行）；切换成本差 2-3 个数量级；
> 2. 最大陷阱是 CPU 密集任务——协作式调度下会饿死其他虚拟线程，必须桥接到独立平台线程池；
> 3. 生产三件套：Semaphore 限流（无背压）、JFR/jcmd 可观测（VirtualThreadPinned 必须告警）、版本回归压测（25/26 修过 sleep 性能回退与调度器 bug）。

**思考题**：

1. 为什么 100 万虚拟线程只需 ~400MB 堆？（→ 1.1）
2. 一个 2 核 Docker 容器跑虚拟线程，最多几个任务同时在 CPU 上？（→ 02 章 + 本节 1.2）
3. 线上怎么发现"CPU 密集任务混进了虚拟线程池"？（→ 3.2 识别信号 + 5.2）
4. JDK 25 升级到 25.0.3 的意义？（→ 4 节）
