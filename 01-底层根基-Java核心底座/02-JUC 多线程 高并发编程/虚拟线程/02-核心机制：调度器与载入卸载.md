## 1. 一次完整的执行旅程

以一个虚拟线程执行 `socket.read()`（阻塞 200ms）为例，看它的一生：

```text
时间轴
────────────────────────────────────────────────────────────────
创建        Thread.ofVirtual().start()        堆上分配 VirtualThread 对象（~几百字节）
              │
入队        submit(ForkJoinTask)              → 加入调度器工作队列
              │
mount      ForkJoinPool 线程（载入线程）      → 从队列取出，执行 Continuation
              │                                   ┌─────────────────────┐
执行       socket.read()                      → │ 阻塞点拦截             │
              │                                   │ park() → 保存寄存器/栈 │
unmount    Continuation 挂起                  → │ 释放载入线程           │
              │                                   └─────────────────────┘
等待       Poller 线程监听 fd                  → 载入线程立刻执行下一个虚拟线程
              │                                    （其他虚拟线程可能正在跑）
唤醒       200ms 后数据到达                   → poller 回调 → unpark(vt)
              │
重新入队    虚拟线程再次 submit                → 加入工作队列（可能换一个载入线程）
              │
remount    恢复 Continuation 状态             → 从上次挂起点继续执行
              │
结束        run() 返回 → 对象被 GC            → jdk.VirtualThreadEnd 事件
────────────────────────────────────────────────────────────────
```

> 🎯 **核心要点**：整个旅程中，**OS 只看到 N 个载入线程**在永不停歇地切换执行对象；虚拟线程的挂起/恢复全部在 JVM 用户态完成，没有一次内核上下文切换。

## 2. 调度器：ForkJoinPool 载入线程池

### 2.1 默认调度器

每个虚拟线程创建时绑定一个**调度器（scheduler）**——一个 `Executor`，默认是 JVM 私有的 **ForkJoinPool**：

```java
// jdk.internal.misc / java.lang.VirtualThread 内部逻辑（简化）
private static ForkJoinPool createDefaultScheduler() {
    ForkJoinPool.ForkJoinWorkerThreadFactory factory = ...;
    PrivilegedAction<ForkJoinPool> pa =
        () -> new ForkJoinPool(parallelism, factory, null, true);   // asyncMode = true
    return AccessController.doPrivileged(pa);
}
```

关键点：

- **parallelism（并行度）默认 = CPU 核数**（`Runtime.availableProcessors()`，容器环境由 JEP 418 感知 cgroup 配额）；
- **maxPoolSize 默认 = 256**：极端情况下（虚拟线程执行 CPU 密集任务不卸载）载入线程会增至 256 个，防止所有虚拟线程饿死在队列里；
- `asyncMode = true`：工作队列采用 FIFO（而非 LIFO 分治模式），因为虚拟线程任务是独立任务而非 fork/join 子任务；
- 调度器线程是 **daemon 线程**，不阻止 JVM 退出。

### 2.2 载入线程（Carrier Thread）是什么

载入线程就是调度器的 ForkJoinPool 工作线程（`ForkJoinWorkerThread`），它承担三重职责：

1. 从工作队列取出虚拟线程任务；
2. 执行虚拟线程的 Continuation（此时它被"载入"，成为该虚拟线程的 carrier）；
3. 虚拟线程挂起后，继续取下一个任务执行——**一个载入线程在生命周期内会依次服务成千上万个虚拟线程**。

```java
// 在虚拟线程内观察：currentThread() 返回的是虚拟线程对象
Thread me = Thread.currentThread();          // 虚拟线程
System.out.println(me.isVirtual());          // true
// 但底层"真正在跑的" OS 线程无法从标准 API 直接看到
// 只能通过 jcmd Thread.dump_to_file -format=json 的 carrierThreadId 字段观察
```

> 💡 **理解关键**：载入线程 = 跑道，虚拟线程 = 运动员。跑道只有 CPU 核数那么多，运动员可以有几百万——因为运动员跑累了（阻塞）就让出跑道，JVM 负责在跑道间调度运动员。

### 2.3 为什么不用普通线程池做调度器

ForkJoinPool 被选中而非 `ThreadPoolExecutor`，因为虚拟线程调度需要：

| 需求 | ThreadPoolExecutor | ForkJoinPool |
|------|:---:|:---:|
| 工作窃取（work-stealing），避免队头阻塞 | ❌ | ✅ |
| 载入线程与任务解耦，任务可任意切换 | 一般 | ✅（任务本质是可挂起单元） |
| 高吞吐的短任务切换 | 一般 | ✅（FIFO + 窃取） |
| 与 Continuation 机制深度集成 | ❌ | ✅ |

## 3. mount 与 unmount：上载与卸载

### 3.1 两个核心操作

| 操作 | 英文 | 发生时 | 做了什么 |
|------|------|--------|---------|
| 上载 | mount | 载入线程开始执行虚拟线程 | 把虚拟线程的 Continuation 状态"接管"到载入线程上运行 |
| 卸载 | unmount | 虚拟线程在阻塞点挂起 | 保存执行现场到堆上分块栈，载入线程立即回到调度循环 |

### 3.2 卸载成本为什么低

- **没有系统调用**：不涉及内核，只是一次 JVM 内部的状态保存；
- **栈帧拷贝有优化**：深层栈帧保存在堆上的 StackChunk 中，只有最浅的若干帧留在载入线程栈上（由 JVM 生成代码直接操作），多数情况下**不需要逐帧拷贝**；
- **恢复是对称操作**：remount 时把 chunk 栈帧恢复到（可能是另一个）载入线程。

```text
unmount 时载入线程栈的布局（示意）
┌────────────────────────────────┐
│ 载入线程栈                      │
│  ┌──────────────────────────┐  │
│  │ Continuation.run() 帧    │  │  ← 这里以下的帧会被拷贝/标记保存
│  │ 业务方法帧（浅层）        │  │
│  │ 阻塞点帧                  │  │  ← park() 触发点
│  └──────────────────────────┘  │
│  ↓ 阻塞点：剩余深层帧保存到堆上 StackChunk │
└────────────────────────────────┘
```

### 3.3 park/unpark：虚拟线程的挂起原语

虚拟线程的阻塞全部收敛到 `LockSupport.park()`/`unpark()` 这对原语：

```java
// java.lang.VirtualThread 内部（关键源码路径）
final class VirtualThread extends BaseVirtualThread {
    // park 内部：先尝试立即获得许可，否则卸载
    void park() {
        // 1. 尝试获取许可（unpark 竞争窗口）
        // 2. 调用 Continuation.yield() —— 挂起点
        // 3. 若 yield 返回 true，说明被唤醒重新上载，循环检查
    }
    void unpark() {
        // 1. 设置许可
        // 2. 若虚拟线程已卸载，重新提交到调度器（submitRunContinuation）
    }
}
```

**阻塞 = park + 卸载；解除阻塞 = unpark + 重新入队**——所有高级 API（sleep、锁、队列、I/O）最终都走到这里。这也是 `ForkJoinPool` 的 `common` 池与 `jdk.VirtualThreadScheduler` 线程必须使用 `DefaultForkJoinWorkerThreadFactory` 的原因：载入线程必须注册为虚拟线程的载体，`Thread.currentThread()` 才能正确返回虚拟线程对象。

> ⚠️ **边界**：载入线程在以下两种"异常"场景不会立即回到调度循环：
> 1. **pinning**：虚拟线程持有监视器（synchronized）或执行原生回调时无法卸载（JDK 24 后仅剩原生场景，见 04 章）；
> 2. **CPU 密集任务**：虚拟线程持续计算不阻塞，载入线程自然被它独占（协作式调度的固有特性，见 08 章）。

## 4. Continuation 与堆上分块栈

### 4.1 Continuation：可挂起/恢复的执行状态

`jdk.internal.vm.Continuation` 是 Loom 的底层基石（`VirtualThread` 继承关系：`Thread` → `BaseVirtualThread` → `VirtualThread`，内部持有一个 Continuation）：

```java
// jdk.internal.vm.Continuation（JDK 内部类，非公开 API）
public class Continuation {
    private Object[] stackChunks;   // 堆上分块栈的引用链
    // 关键方法
    static Object enter(Continuation cont);    // 开始执行（native）
    boolean yield();                            // 挂起，返回 true 表示被唤醒
    void run();                                 // 运行/继续执行
}
```

**Continuation 的能力**：任意深度的调用栈可以被整体挂起、保存、之后在任意线程上恢复。这正是"阻塞点拦截"的底层支撑——`yield()` 时整个栈被冻结，恢复时从冻结点继续。

### 4.2 分块栈（Chunked Stack）：堆上、按需、可回收

平台线程的栈是 OS 分配的原生内存，**虚拟线程的栈是堆上的对象**：

| 属性 | 平台线程栈 | 虚拟线程栈（StackChunk） |
|------|-----------|------------------------|
| 存放位置 | 原生内存 | **JVM 堆** |
| 大小 | 固定 ~1MB（预留） | 分块（chunk）按需增长/收缩 |
| 生命周期 | 线程创建到销毁 | 随 Continuation 状态，**可被 GC 回收** |
| 深度限制 | `StackOverflowError` 由 OS 决定 | JVM 决定（初始大小可用 `-XX:VirtualThreadStackSize` 调节，偏小会提前 SOE） |
| 阻塞时的保存 | 无需保存（OS 处理） | 拷贝/冻结到 chunk 链 |

**分块机制的意义**：

- 浅栈虚拟线程（常见：一个 handler + 一次 I/O）只占几百字节堆；
- 深栈递归代码在虚拟线程上依然工作，栈按需长到最多约 128KB 的连续 chunk 链；
- 虚拟线程结束后，整个 chunk 链随对象一起被 GC——**不需要归还机制，这正是"不要池化虚拟线程"的根源**（池化保存的栈反而阻碍回收，见 05 章）。

### 4.3 与栈帧相关的限制

```text
注意：虚拟线程栈不是普通 Java 对象可访问的
- 栈帧中的对象引用不参与常规堆遍历（JIT 编译后栈帧布局特殊）
- 因此：深度递归 + 大局部变量在虚拟线程上可能比平台线程更快触发 StackOverflowError
- JVM 对虚拟线程栈深度的限制与栈上替换（OSR）行为与平台线程有差异
```

## 5. 阻塞点全集与恢复路径

### 5.1 JVM 拦截的阻塞点（会卸载）

| 类别 | 具体 API | 卸载后的等待机制 |
|------|---------|-----------------|
| 时间等待 | `Thread.sleep()`、`LockSupport.parkNanos()` | 调度器定时唤醒 |
| 锁 | `ReentrantLock.lock()`、`Condition.await()`（JUC） | 持锁线程 unlock 时 unpark |
| 监视器 | `synchronized`、`Object.wait()` | JDK 24+（JEP 491）支持卸载，见 04 章 |
| 队列 | `BlockingQueue.take()` / `put()` | 元素进出时 unpark |
| 网络/文件 I/O | `Socket`、`InputStream`、`HttpClient` | **JDK 内部 Poller 监听 fd，就绪时 unpark** |
| 异步等待 | `Future.get()`、`CompletableFuture.join()` | 完成时 unpark |

### 5.2 I/O 恢复路径：Poller 机制（JDK 内部）

阻塞式 socket 读写如何唤醒虚拟线程？JDK 内部（`jdk.internal.net` 的 Poller / NIO Selector）维护少量平台线程做事件轮询：

```text
虚拟线程 A（socket.read 阻塞）
    │ park + 卸载
    ▼
JDK Poller 线程（epoll/kqueue，平台线程，数量少而固定）
    │ 注册 fd；数据到达 → 事件触发
    ▼
unpark(A) → A 重新入队调度器 → 恢复执行
```

- Poller 线程数量与 fd 无关（一个 epoll 实例可监听海量 fd），所以**百万虚拟线程阻塞 I/O 只需极少量轮询线程**；
- 这也是"虚拟线程 + 阻塞式 I/O = 高吞吐"的物理基础：阻塞等待的"钱"由 OS 的 epoll 机制付，业务代码完全同步。

### 5.3 不拦截的调用（不卸载）

```java
// 这些不会触发卸载，虚拟线程会一直占着载入线程：
// 1. 纯 CPU 计算：循环、加密、JSON 解析
// 2. JNI 调用：原生库中的阻塞（无法在 JVM 层挂起）
// 3. synchronized（JDK 21 及以前，见 04 章）
// 4. 类初始化 / 符号解析过程中的阻塞
```

## 6. 并发度配置

### 6.1 系统属性

| 属性 | 默认值 | 作用 |
|------|:---:|------|
| `jdk.virtualThreadScheduler.parallelism` | CPU 核数 | 载入线程池的并行度（工作线程基数） |
| `jdk.virtualThreadScheduler.maxPoolSize` | 256 | 载入线程池最大线程数（CPU 密集兜底） |
| `jdk.tracePinnedThreads` | - | **JDK 24 已移除**（JEP 491 后 pin 场景大幅收窄） |

```bash
# 示例：Docker 容器分配了 4 核但物理机 32 核时，强制 4 个载入线程
java -Djdk.virtualThreadScheduler.parallelism=4 -Djdk.virtualThreadScheduler.maxPoolSize=64 app.jar
```

> ⚠️ **配置注意事项**：
> 1. 默认并行度依赖 `Runtime.availableProcessors()`，Docker 下由 JEP 418（容器感知）自动取 cgroup 配额；**不要盲目调大 parallelism**，它等于同时执行 CPU 任务的载入线程数；
> 2. `maxPoolSize=256` 是"防止饿死"的兜底：当虚拟线程都在跑 CPU 密集任务（无法卸载）时池子才会增长到 256；正常 I/O 密集场景永远只有 parallelism 个载入线程在工作；
> 3. 自定义调度器（`Thread.ofVirtual().scheduler(executor)`）仅在特殊场景使用，生产环境默认即可。

### 6.2 相关 JFR 事件与诊断钩子

| 事件/钩子 | 触发时机 | 用途 |
|-----------|---------|------|
| `jdk.VirtualThreadStart` | 虚拟线程开始执行 | 统计线程生命周期 |
| `jdk.VirtualThreadEnd` | 虚拟线程结束 | 统计线程生命周期 |
| `jdk.VirtualThreadPinned` | 虚拟线程发生 pinning | **定位 pin 问题（详见 04/08 章）** |
| `jdk.VirtualThreadSubmitFailed` | 虚拟线程提交调度失败 | 监控调度器过载 |
| `jdk.ThreadDump` | jcmd 触发转储 | 虚拟线程转储（`-format=json`） |

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 默认调度器是 ForkJoinPool（parallelism=CPU 核数，maxPoolSize=256），载入线程是它的工作线程；
> 2. 虚拟线程阻塞 = `park()` + Continuation 挂起 + 卸载载入线程，解除 = `unpark()` + 重新入队，全程用户态零系统调用；
> 3. 虚拟线程栈是堆上分块栈（StackChunk），按需伸缩、可被 GC——这是"不池化"原则的底层依据。

**思考题**：

1. 为什么调度器用 ForkJoinPool 而不是 ThreadPoolExecutor？（→ 2.3）
2. 一个 32 核机器上同时有 100 万个阻塞的虚拟线程，此时 OS 线程有多少个在干活？（→ 2.2 + 5.2）
3. JDK 21 中 `synchronized` 内阻塞会怎样？JDK 24 之后呢？（→ 04 章）
4. CPU 密集的虚拟线程会怎样影响其他虚拟线程？（→ 08 章）
