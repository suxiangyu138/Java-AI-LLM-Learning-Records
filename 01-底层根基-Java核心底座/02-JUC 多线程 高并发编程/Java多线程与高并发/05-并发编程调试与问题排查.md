## 1. 死锁排查全流程 {#1}

### 1.1 快速诊断

```bash
# ── 第一步：找到 Java 进程 PID ──
jps -l                    # 列出所有 Java 进程
# 或
ps aux | grep java

# ── 第二步：获取线程 Dump ──
jstack <PID> > thread_dump.txt

# jstack 会自动检测死锁！
# 输出末尾会包含：
# Found one Java-level deadlock:
# =============================
# "Thread-1":
#   waiting to lock monitor 0x00007f (object 0x000000076abc)
#   which is held by "Thread-0"
# "Thread-0":
#   waiting to lock monitor 0x00007f (object 0x000000076def)
#   which is held by "Thread-1"

# ── 第三步：连续 dump 3 次（间隔 3 秒），观察变化 ──
jstack <PID> > dump1.txt
sleep 3
jstack <PID> > dump2.txt
sleep 3
jstack <PID> > dump3.txt
```

### 1.2 线程 Dump 解读

```text
"http-nio-8080-exec-5" #42 daemon prio=5 os_prio=0 tid=0x00007f8b nid=0x1a2b
                        │     │    │    │         │
                        │     │    │    │         └─ OS 线程 ID (十六进制)
                        │     │    │    └─ Java 线程 ID
                        │     │    └─ 优先级
                        │     └─ 守护线程标记
                        └─ 线程名称

常见线程状态：
  RUNNABLE          — 运行中（可能在 CPU 上，也可能在等待 CPU）
  BLOCKED           — 等待获取锁（synchronized）→ 重点关注！
  WAITING           — 无限等待 (Object.wait / LockSupport.park)
  TIMED_WAITING     — 限时等待 (Thread.sleep / Lock.tryLock)
```

```text
# 关键：查看 BLOCKED 线程的堆栈

"Thread-1" #21 prio=5 tid=0x... nid=0x1a2c BLOCKED
   java.lang.Thread.State: BLOCKED (on object monitor)
        at com.example.Service.methodB(Service.java:30)
        - waiting to lock <0x000000076abc>      ← 想获取这个锁
        - locked <0x000000076def>               ← 自己持有这个锁
        ..."

"Thread-0" #20 prio=5 tid=0x... nid=0x1a2b BLOCKED
   java.lang.Thread.State: BLOCKED (on object monitor)
        at com.example.Service.methodA(Service.java:20)
        - waiting to lock <0x000000076def>      ← 想获取这个锁
        - locked <0x000000076abc>               ← 自己持有这个锁
        ..."

→ 经典死锁！Thread-1 等 abc（被 Thread-0 持有），Thread-0 等 def（被 Thread-1 持有）
```

### 1.3 死锁预防模式

```java
// ── 模式1: 锁排序（Lock Ordering）──
// 所有线程按相同顺序获取锁，打破循环等待
public void transfer(Account from, Account to, BigDecimal amount) {
    // 按 id 排序，确保锁获取顺序一致
    Account first = from.getId() < to.getId() ? from : to;
    Account second = from.getId() < to.getId() ? to : from;

    synchronized (first) {
        synchronized (second) {
            // 转账逻辑
        }
    }
}

// ── 模式2: tryLock 超时 ──
public boolean transferWithTimeout(Account from, Account to,
        BigDecimal amount) {
    while (true) {
        if (from.lock.tryLock(100, TimeUnit.MILLISECONDS)) {
            try {
                if (to.lock.tryLock(100, TimeUnit.MILLISECONDS)) {
                    try {
                        // 转账逻辑
                        return true;
                    } finally { to.lock.unlock(); }
                }
            } finally { from.lock.unlock(); }
        }
        // 获取锁失败 → 短暂休眠后重试
        Thread.sleep(ThreadLocalRandom.current().nextInt(50));
    }
}

// ── 模式3: 死锁自动检测（监控用）──
@Scheduled(fixedRate = 10000)
public void detectDeadlocks() {
    ThreadMXBean bean = ManagementFactory.getThreadMXBean();
    long[] deadlockedThreads = bean.findDeadlockedThreads();

    if (deadlockedThreads != null) {
        log.error("🚨 检测到死锁！线程: {}",
            Arrays.toString(deadlockedThreads));
        // 发送告警
        Alert.send("死锁告警", deadlockedThreads);
    }
}
```

### 1.4 分布式死锁

```text
分布式死锁：多个服务间的锁相互等待

场景：
  ServiceA: [获取 Redis 锁 L1] → 调用 ServiceB → [等待 Redis 锁 L2]
  ServiceB: [获取 Redis 锁 L2] → 调用 ServiceA → [等待 Redis 锁 L1]

解决：
  1. 统一锁顺序（全局锁命名规范）
  2. 锁超时（Redisson 看门狗 + 最大持有时间）
  3. 避免跨服务的锁嵌套
```

## 2. 线程安全问题定位 {#2}

### 2.1 常见并发 Bug 速查

| 症状 | 可能原因 | 排查方向 |
|------|---------|---------|
| 数据偶尔不一致 | 无同步的共享变量 | 检查变量是否有 volatile/synchronized |
| 列表大小不对 | ArrayList 并发 add | 换成 CopyOnWriteArrayList 或加锁 |
| HashMap CPU 100% | 并发 resize 死循环 | 换成 ConcurrentHashMap |
| 计数器偏小 | count++ 非原子 | 用 AtomicInteger / LongAdder |
| null 指针 | 指令重排序（部分构造） | 检查 final 字段 / 安全发布 |
| ThreadLocal 值错乱 | 线程复用（线程池） | try-finally 中 remove() |
| SimpleDateFormat 串号 | 非线程安全 + 多线程 | 用 ThreadLocal 或 DateTimeFormatter |

### 2.2 竞态条件复现技巧

```java
/**
 * 让竞态条件更容易复现的技巧：
 *
 * 1. 在临界区前后加 Thread.yield() / sleep(随机)
 * 2. 增大并发数（线程数 >> CPU 核数）
 * 3. 使用 ThreadSanitizer 类的工具
 * 4. 压力测试 + 断言检查
 *
 * 示例：复现 count++ 的竞态
 */
@Test
void reproduceRaceCondition() throws Exception {
    final int THREADS = 100;
    final int ITERATIONS = 10_000;
    CountDownLatch latch = new CountDownLatch(THREADS);

    // ❌ 有竞态的计数器
    Counter unsafe = new UnsafeCounter();

    ExecutorService executor = Executors.newFixedThreadPool(THREADS);
    for (int i = 0; i < THREADS; i++) {
        executor.submit(() -> {
            for (int j = 0; j < ITERATIONS; j++) {
                unsafe.increment();

                // 🔑 增加上下文切换概率
                if (j % 100 == 0) Thread.yield();
            }
            latch.countDown();
        });
    }

    latch.await();
    // 预期: THREADS × ITERATIONS = 1,000,000
    // 实际: < 1,000,000 (竞态导致计数丢失)
    assertEquals(THREADS * ITERATIONS, unsafe.get());
    // ❌ 断言失败！竞态已复现
}
```

## 4. 线程池故障诊断 {#4}

### 4.1 诊断流程图

```text
接口响应慢 / 请求被拒绝
│
├── 1. 检查线程池指标
│   ├── activeCount ≈ maxPoolSize ？→ 线程池打满
│   ├── queueSize ≈ queueCapacity ？→ 队列积压
│   └── rejectedCount > 0 ？→ 拒绝策略触发
│
├── 2. 检查线程状态
│   ├── BLOCKED 数量多？→ 锁竞争严重
│   ├── WAITING 数量多？→ 等待外部资源（DB/Redis/HTTP）
│   └── RUNNABLE 且 CPU 高？→ CPU 密集任务过多
│
├── 3. 检查下游资源
│   ├── DB 连接池 → 是否打满
│   ├── Redis 连接池 → 是否泄漏
│   └── HTTP 连接池 → 是否 TIME_WAIT 过多
│
└── 4. 检查 GC
    ├── Full GC 频繁？→ 内存不足
    └── GC 暂停时间长？→ 线程池表现变差
```

### 4.2 线程泄漏排查

```java
/**
 * 线程泄漏的典型症状：
 * - 线程数持续增长，从不下降
 * - JVM 最终因无法创建新线程而 OOM
 *
 * 排查方法：
 */

// ── 方法1: jstack 对比 ──
// 间隔 10 分钟做两次 jstack，对比线程名/数量
// jstack <PID> > dump1.txt
// sleep 600
// jstack <PID> > dump2.txt
// diff <(grep "^\"" dump1.txt | sort) <(grep "^\"" dump2.txt | sort)

// ── 方法2: 监控线程池生命周期 ──
@Scheduled(fixedRate = 30000)
public void monitorThreadPools() {
    for (var entry : pools.entrySet()) {
        ThreadPoolExecutor pool = entry.getValue();
        log.info("Pool[{}]: active={}, pool={}, largest={}, queue={}, completed={}, rejected={}",
            entry.getKey(),
            pool.getActiveCount(),
            pool.getPoolSize(),
            pool.getLargestPoolSize(),
            pool.getQueue().size(),
            pool.getCompletedTaskCount(),
            rejectedCount.get(entry.getKey())
        );

        // 告警规则
        if (pool.getActiveCount() >= pool.getMaximumPoolSize()) {
            Alert.warn("线程池[{}]已打满", entry.getKey());
        }
    }
}
```

### 4.3 任务堆积处理

```java
/**
 * 处理任务堆积的策略：
 *
 * 1. 快速失败 (Reject + 告警)
 * 2. 动态扩容 (setMaximumPoolSize)
 * 3. 任务丢弃 (DiscardOldestPolicy + 监控)
 * 4. 调用者执行 (CallerRunsPolicy — 自然限流)
 */
public class OverloadHandler {

    // 过载自动降级
    public void handleWhenOverloaded(ThreadPoolExecutor pool) {
        // 队列使用率 > 80%
        double queueUsage = (double) pool.getQueue().size()
            / (pool.getQueue().size() + pool.getQueue().remainingCapacity());

        if (queueUsage > 0.8) {
            log.warn("线程池过载: queueUsage={:.2f}", queueUsage);

            // 方案A: 动态扩容
            int newMax = pool.getMaximumPoolSize() * 2;
            pool.setMaximumPoolSize(newMax);

            // 方案B: 开启降级开关
            degradeService.setDegraded(true);
        }
    }
}
```

## 5. 线上应急手册 {#5}

### 5.1 CPU 飙高

```bash
# Step 1: 找到 CPU 最高的进程
top -c

# Step 2: 找到该进程中 CPU 最高的线程
top -H -p <PID>
# 记录线程 ID (十进制)

# Step 3: 十进制 → 十六进制
printf "%x\n" <DECIMAL_TID>
# 例: 12345 → 0x3039

# Step 4: 在线程 dump 中查找
jstack <PID> | grep -A 20 "0x3039"

# Step 5: 快速定位 (Arthas)
thread -n 5   # 直接显示 CPU 最高的 5 个线程堆栈
```

```text
常见 CPU 飙高场景：
├── 死循环 (while true / for 无退出条件)
├── 正则表达式灾难性回溯 (Catastrophic Backtracking)
├── HashMap 并发死循环 (JDK 7)
├── GC 频繁 (Young GC 过于频繁)
└── JSON 大对象序列化/反序列化
```

### 5.2 内存泄漏

```bash
# Step 1: 查看内存使用
jmap -heap <PID>

# Step 2: 导出堆 dump
jmap -dump:format=b,file=heap.hprof <PID>

# Step 3: 用 MAT (Memory Analyzer Tool) 分析
# 打开 heap.hprof → Leak Suspects Report
# 重点看: 大对象 / 集合大量元素 / ThreadLocal 残留

# Arthas 快捷方式
memory                           # 查看内存使用
heapdump /tmp/heap.hprof         # 导出 dump
vmtool --action getInstances     # 查看某个类的所有实例
```

```java
// ── 常见内存泄漏模式 ──
// 1. ThreadLocal 未清理
public class ThreadLocalLeak {
    private static final ThreadLocal<byte[]> BUFFER =
        ThreadLocal.withInitial(() -> new byte[1024 * 1024]); // 1MB

    // ❌ 线程池 + ThreadLocal → 内存泄漏
    // 线程不销毁 → ThreadLocal 不回收 → 泄漏
    // ✅ 修复: try-finally 中 remove()
    public void process() {
        try {
            byte[] buf = BUFFER.get();
            // ...
        } finally {
            BUFFER.remove();  // 必须！
        }
    }
}

// 2. 集合持续增长无上限
// ❌ ConcurrentHashMap 不断 put 从不 remove
// ✅ 加 LRU 淘汰 / 定时清理
```

### 5.4 应急检查清单

```text
🌀 线上事故应急检查清单

□ 1. 查看监控大盘
   □ QPS 是否异常（突增/突降）
   □ 错误率是否飙升
   □ RT 是否变长
   □ CPU / 内存 / 磁盘 IO 是否异常

□ 2. 快速诊断
   □ jstack: 线程状态（死锁/BLOCKED）
   □ jmap -histo: 内存占用 Top 类
   □ top -H: CPU 最高线程
   □ Arthas dashboard: 整体概况

□ 3. 止血
   □ 重启 (保留现场 → dump 后重启)
   □ 限流 (降低入口流量)
   □ 降级 (关闭非核心功能)
   □ 回滚 (如果是新版本引入)

□ 4. 复盘
   □ 根因分析 (5 Whys)
   □ 修复方案 + 测试
   □ 监控补充 (下次能更早发现)
   □ 预案更新 (下次能更快止血)
```

> 🎯 **核心要点**：排查并发问题的铁三角——**jstack（看状态）+ Async Profiler（看性能）+ Arthas（看运行时）**。熟练使用这三把刀，90% 的并发问题都能快速定位。
