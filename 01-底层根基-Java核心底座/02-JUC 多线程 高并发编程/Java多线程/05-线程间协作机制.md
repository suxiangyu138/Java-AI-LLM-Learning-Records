## 1. 协作 vs 互斥：两类同步的本质

**并发编程的两种同步**（区分它们是理解本节的前提）：

| 维度 | 互斥（Mutual Exclusion） | 协作（Coordination） |
|------|------------------------|---------------------|
| 解决的问题 | "别同时进临界区" | "等别人做完/做某事" |
| 机制 | synchronized / Lock / CAS | **wait/notify、join、park/unpark**、CountDownLatch |
| 类比 | 厕所门锁 | 等电梯、等外卖 |

```java
// 互斥：同一时刻一个线程改余额
synchronized (account) { balance += amt; }

// 协作：消费者等生产者"生产完再消费"
synchronized (buffer) {
    while (buffer.isEmpty()) buffer.wait();   // 等待：释放锁，进入 WaitSet
    buffer.take();                            // 被唤醒后继续
}
```

**关键区分**：互斥的锁**不解决"顺序"**——两个线程都拿到过锁，谁先谁后不可控；协作才解决"**等待某个条件成立**"。真实系统两者叠加：**在互斥（锁）内做协作（wait/notify）**。

> 🎯 **核心要点**：**"锁"管互斥，"条件"管协作**——`wait/notify` 必须与锁配合（条件与互斥绑定，防止条件判断与修改之间的竞态）。JUC 的 `Condition` 是"更精细的 wait/notify"（见第 4 节与 `02-JUC高并发编程/04`）。

## 2. wait / notify / notifyAll 语义精讲

**三方法只能在 synchronized 块/方法内调用**（持有 Monitor 才能操作 WaitSet）：

| 方法 | 行为 | 细节 |
|------|------|------|
| `wait()` | 释放锁 + 进入 **WaitSet** 等待 | **先释放锁再等**（这是它区别于 sleep 的关键） |
| `wait(ms)` | 限时等待 | 超时自动唤醒（TIMED_WAITING） |
| `notify()` | 唤醒 WaitSet 中**一个**线程 | 谁被唤醒不确定（非公平） |
| `notifyAll()` | 唤醒 **所有** 等待线程 | 都去 EntryList 重新抢锁 |

```java
// wait 的完整时序（面试画图题）：
// 线程 A：synchronized(lock) { lock.wait(); }
//   ① A 持有 lock 的 Monitor → ② wait 把 A 放入 WaitSet → ③ A 释放锁 → ④ A 状态 WAITING
// 线程 B：synchronized(lock) { lock.notifyAll(); }
//   ① B 拿到锁（A 释放后）→ ② notifyAll 把 WaitSet 的 A 移到 EntryList → ③ B 出锁
//   ④ A 在 EntryList 抢到锁 → ⑤ wait 返回，继续执行
```

**notify vs notifyAll 的选择**（经典面试题）：

| 场景 | 选择 | 原因 |
|------|------|------|
| 只有一个等待者 | notify | 够用且开销小 |
| 多个等待者，条件不同 | **notifyAll** | notify 可能唤醒"条件不满足的线程"，它只能再 wait（浪费 + 可能饿死） |
| 不确定有几个 | notifyAll | 保守正确 |

> 🎯 **核心要点**：wait 的语义 = "**释放锁 + 挂起 + 等待通知**"——释放锁是它和 sleep 的本质区别（sleep 抱着锁睡）。notifyAll 是默认安全选择：唤醒全部让它们自己判断条件。

## 3. 虚假唤醒与 while 循环范式

**虚假唤醒（Spurious Wakeup）**：等待线程**在没有收到 notify 的情况下被唤醒**——OS 层面允许的行为（POSIX 规范明确说明）：

> "A thread that has been waiting... may be woken up spuriously."

```java
// ❌ 错误范式：if 判断条件 —— 虚假唤醒或 notify 后条件又被别人改掉时，直接越界/错误
synchronized (buffer) {
    if (buffer.isEmpty()) buffer.wait();   // 被虚假唤醒 → 不检查条件 → 空取 → 异常！
    return buffer.take();
}

// ✅ 正确范式：while 循环 —— 唤醒后重新检查条件，不满足继续等
synchronized (buffer) {
    while (buffer.isEmpty()) buffer.wait();   // 唤醒后回到这里重新判断
    return buffer.take();
}
```

**为什么 while 是标准答案**（三层理由）：

1. **虚假唤醒**：被无故唤醒 → 重新判断条件 → 不满足继续 wait；
2. **notify 唤醒"错的人"**：多个等待者条件不同，被唤醒的未必条件满足；
3. **条件在竞争中被改**：唤醒后到取数据之间，其他线程可能又清空了缓冲区。

**JUC 世界的同款要求**：`Condition.await()` 同样必须在循环中使用（`while (!condition) condition.await()`）——这是 Java 并发编程的通用范式。

> 🎯 **核心要点**：**"wait 必须配 while"是硬规则**（Java 官方文档明确要求）——面试答"wait 的正确写法"时，`while` 循环 + 条件判断 + `notifyAll` 三件套缺一不可。

## 4. sleep / wait / yield / park 对比矩阵

| 维度 | sleep | wait | yield | park |
|------|:-----:|:----:|:-----:|:----:|
| 释放锁 | **不释放**（抱着锁睡） | **释放**（进 WaitSet） | 不释放 | 不释放（语义上） |
| 唤醒方式 | 超时自动 | notify/超时 | 自动（让出后继续） | unpark/超时 |
| 状态 | TIMED_WAITING | WAITING/TIMED_WAITING | RUNNABLE | WAITING |
| 必须持锁 | 否 | **必须（synchronized 内）** | 否 | 否 |
| 异常 | InterruptedException | InterruptedException | 无 | 无 |
| 用途 | 定时暂停 | 条件等待 | 提示让出 CPU | **LockSupport 核心** |

```java
// park/unpark：LockSupport —— 不用持锁的挂起/唤醒（JUC 锁的底层基石）
LockSupport.park();              // 挂起当前线程（WAITING）
LockSupport.unpark(thread);      // 唤醒指定线程（可由任意线程调用）

// 与 wait/notify 的区别：
// ① 不需要 synchronized —— 无锁可协作（语义更自由）
// ② unpark 可指定线程 —— notify 做不到"精确唤醒"
// ③ 许可机制：先 unpark 后 park 不会丢（"发个许可，之后用"）
// AQS 的阻塞/唤醒就是 park/unpark 实现的（JUC/04 源码）
```

**面试必背对比题**："sleep 和 wait 的区别"标准答案 = **① 锁：sleep 不释放、wait 释放；② 场景：sleep 定时暂停、wait 条件协作；③ 位置：wait 必须在 synchronized 里、sleep 不需要；④ 唤醒：sleep 靠超时、wait 靠 notify/超时**。

> 🎯 **核心要点**：协作工具演进 = **wait/notify（锁内协作）→ Condition（锁内多条件）→ park/unpark（无锁精确协作，AQS 基石）**——现代并发组件几乎都用 park/unpark，但 wait/notify 的语义是理解一切的基础。

## 5. 生产者-消费者经典模型

**经典范式**（wait/notifyAll + while + 有界缓冲区）：

```java
public class BoundedBuffer<T> {
    private final Object[] items;
    private int head, tail, count;

    public BoundedBuffer(int capacity) { items = new Object[capacity]; }

    public synchronized void put(T item) throws InterruptedException {
        while (count == items.length) wait();      // 满则等（生产者等待）
        items[tail] = item;
        tail = (tail + 1) % items.length;          // 循环数组
        count++;
        notifyAll();                               // 唤醒可能等"取"的消费者
    }

    @SuppressWarnings("unchecked")
    public synchronized T take() throws InterruptedException {
        while (count == 0) wait();                 // 空则等（消费者等待）
        T item = (T) items[head];
        head = (head + 1) % items.length;
        count--;
        notifyAll();                               // 唤醒可能等"放"的生产者
        return item;
    }
}
```

**为什么这个模型"教科书"**：

1. **两个 while**：满/空条件的虚假唤醒防护（第 3 节范式）；
2. **notifyAll**：生产者和消费者共享同一把锁、两个不同条件——notify 可能唤醒"错误的一方"；
3. **循环数组**：无动态扩容，容量边界明确。

**现代替代**（生产环境几乎不用手写）：`ArrayBlockingQueue`/`LinkedBlockingQueue` 内建阻塞语义（`put/take`），线程池内部就是它们（见 `Java集合框架/04` 与 `02-JUC高并发编程/06`）——**手写模型是理解题，用 BlockingQueue 是工程题**。

> 🎯 **核心要点**：生产者-消费者是"协作 + 互斥 + 边界 + 唤醒策略"的综合体操——面试手写时展示 while+notifyAll+循环数组三个决策，再补充"生产环境用 BlockingQueue"的工程认知，就是满分。

## 6. join 的实现原理

**join 的语义**：当前线程等待目标线程终止——**底层就是 wait/notify 机制**：

```java
// Thread.join() 的核心实现（JDK 源码视角，简化）：
public final synchronized void join(long millis) throws InterruptedException {
    long base = System.currentTimeMillis();
    long now = 0;
    if (millis < 0) throw new IllegalArgumentException("timeout value is negative");
    if (millis == 0) {                          // 无限等待
        while (isAlive()) wait(0);              // ← wait 循环：线程活着就一直等
    } else {                                    // 限时等待
        while (isAlive()) {                     // ← 同一个"while isAlive"范式！
            long delay = millis - now;
            if (delay <= 0) break;
            wait(delay);
            now = System.currentTimeMillis() - base;
        }
    }
}
```

**两个关键认知**：

1. **join 是 wait 的封装**：`while (isAlive()) wait(0)` —— JVM 在线程终止时会执行 `notifyAll()`（native 层），唤醒等待 join 的线程；
2. **join 可被中断**：声明 `throws InterruptedException`——等待期间可被 interrupt（处理规范见 02 模块第 3 节）。

**join 与 CountDownLatch 的对比**（面试延伸）：

| 维度 | join | CountDownLatch |
|------|:----:|:--------------:|
| 等待对象 | 特定线程终止 | 任意"计数归零"事件 |
| 灵活性 | 只能等线程 | 可等任意任务完成（非线程） |
| 现代实践 | 少用 | 常用（JUC 工具，见 JUC/07） |

> 🎯 **核心要点**：join = **"wait 循环 + 线程终止时 notifyAll"** 的语法糖——理解了这一点，就能解释"为什么 join 需要处理 InterruptedException"以及"为什么是 synchronized 方法"（要操作自己的 Monitor）。
