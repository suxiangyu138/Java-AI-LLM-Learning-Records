## 1. 线程安全三要素：原子性 / 可见性 / 有序性

**并发 bug 的三个维度**——每个都必须被保障：

| 要素 | 定义 | 被破坏的例子 | 保障手段 |
|------|------|------------|---------|
| **原子性** | 操作不可分割 | `count++`（读-加-写三步被穿插） | synchronized / Lock / CAS |
| **可见性** | 一个线程的修改其他线程可见 | 线程 A 改了 flag，线程 B 死循环看不到 | volatile / synchronized / Lock |
| **有序性** | 指令执行顺序不被重排破坏 | 双检锁中"半初始化对象"被发布 | volatile（禁重排）/ 锁 |

```java
// 原子性破坏：两步操作被穿插
static int count = 0;
// count++ 编译为三条指令：getstatic → iadd → putstatic
// 线程 A 执行 getstatic 后，线程 B 插进来完成整个 ++ —— A 写回时覆盖 B 的结果

// 可见性破坏：flag 变化看不到
static boolean flag = false;                  // 非 volatile
// 线程 A：flag = true
// 线程 B：while (!flag) { }   —— 可能永远循环（flag 读的是缓存/寄存器中的旧值）

// 有序性破坏：重排序 + 半初始化
// new 对象三步：① 分配内存 ② 初始化字段 ③ 赋值引用 —— ②③ 可能重排！
// 双检锁单例必须 volatile 防止"引用先发布、字段还没初始化"的洞
```

> 🎯 **核心要点**：**三要素必须同时满足**——volatile 修可见性但不修原子性（`volatile int i; i++` 依然不安全）；synchronized 三者都修（锁 + 内存屏障）。面试答"volatile 能保证线程安全吗"——只能保证可见性与有序性，原子性要 CAS 或锁。

## 2. 临界区与竞态条件

**临界区（Critical Section）**：访问共享可变资源的代码段——同一时刻只允许一个线程进入。

**竞态条件（Race Condition）**：程序结果**依赖于线程执行时序**——不同时序产生不同结果：

```java
// 竞态条件三形态（面试三个经典例子）：

// ① Check-then-Act（先检查后行动）——最经典
if (!map.containsKey(key)) {        // 检查
    map.put(key, value);            // 行动 —— 两个线程可同时通过检查 → 覆盖
}

// ② Read-Modify-Write（读改写）
balance = balance - amount;         // 读-算-写三步 —— 丢失更新

// ③ 复合操作
list.size() + list.get(i)           // 两步之间集合被修改 → 越界/错位
```

**竞态与"临界区未加锁"的关系**：

```text
竞态发生 = 共享 + 可变 + 非原子（未保护临界区）
修复 = 给临界区加锁（synchronized）或让操作原子化（CAS）或消灭共享（不可变）
```

> ⚠️ **最难排查的竞态**：时序依赖越窄越难复现——单测跑一万次不出错、线上偶发数据错乱。**推演 > 试错**：先画出"两个线程的指令穿插序列"，再找哪一步能被穿插。

## 3. 线程安全等级分类

**《Java 并发编程实战》的四级分类**（面试答"什么是线程安全"的完整框架）：

| 等级 | 定义 | 例子 | 说明 |
|------|------|------|------|
| **不可变**（最强） | 对象创建后状态不可变 | String、Integer、record | 天然安全，无锁 |
| **绝对线程安全** | 所有操作都同步，无需调用方额外同步 | ConcurrentHashMap | 内部已保证 |
| **相对线程安全** | 单操作安全，复合操作需调用方加锁 | **Vector、Hashtable、Collections.synchronizedList** | 单方法同步 ≠ 复合操作安全 |
| **线程不安全** | 所有操作都需调用方保护 | ArrayList、HashMap | 并发使用必须外部同步 |

```java
// "相对线程安全"的经典坑：Vector 单方法安全，复合操作不安全
Vector<String> v = new Vector<>();
// 两个线程同时执行"判断后删除"：
if (!v.isEmpty()) {          // 单方法安全 ✅
    v.remove(0);             // 但两个线程可能同时通过判断 → 一个 remove 抛异常
}
// 必须外部加锁：synchronized (v) { if (!v.isEmpty()) v.remove(0); }
```

**判断标准**："单方法加了 synchronized" 只算相对安全——**"复合操作（check-then-act / 读改写）"是否安全，才是真正的问题**。

> 🎯 **核心要点**：线程安全等级 = 调用方需要付出多少努力——不可变零努力、绝对安全零努力、相对安全需要"调用方自己锁复合操作"、不安全全程自己锁。**设计目标是前两级**（不可变或绝对安全），别设计成"第三个"。

## 4. 不可变优先：消灭共享状态

**并发编程的第一原则（2025 行业共识再确认）**：**"消除可变状态"优于"保护可变状态"**——不可变对象没有竞态（没有状态可以竞）。

```java
// 不可变对象的五要素（见 Java面向对象/02-封装）
public final class Money {           // ① final 类
    private final int amount;        // ② final 字段
    private final String currency;
    public Money(int amount, String currency) { this.amount = amount; this.currency = currency; }
    // ③ 无 setter；④ 构造器全赋值；⑤ 可变字段防御性拷贝
    public Money add(Money other) { return new Money(amount + other.amount, currency); }  // 返回新对象
}

// Java 16+：record 一行获得不可变
public record Money(int amount, String currency) { }
```

**不可变带来的收益**（线程安全视角）：

1. **无竞态**：没有可修改的状态，任意线程任意时刻读到的都是一致快照；
2. **免锁共享**：可安全发布到所有线程（final 字段的可见性由 JVM 保证）；
3. **可安全缓存**：同一实例无限复用（`Integer.valueOf` 缓存、常量池）。

**不可变的边界**：**引用不可变 ≠ 对象不可变**——`final List<String>` 里的 List 还是可变的；不可变集合（`List.of`）才能彻底（见 `Java集合框架/08`）。

> 🎯 **核心要点**：设计线程安全的第一问 = "**这个状态能变成不可变吗**"——能用 record/final/不可变集合消灭的，就不要加锁保护。锁是最后手段，不是第一选择。

## 5. 如何设计一个线程安全的类

**线程安全类的设计流程**（面试设计题的标准框架）：

```text
① 找状态：这个类有哪些字段？哪些是共享可变的？
② 定策略：不可变？加锁？CAS？线程封闭（ThreadLocal）？
③ 保原子：复合操作怎么办（方法级锁/原子类/同步块）？
④ 管发布：对象如何安全发布给其他线程（安全发布四方式）？
```

```java
// 设计案例：一个线程安全的计数器（三种方案按场景选）
// 方案 A：synchronized 方法（简单，竞争激烈时性能一般）
public class Counter {
    private long count;
    public synchronized void inc() { count++; }
    public synchronized long get() { return count; }
}

// 方案 B：原子类（无锁，低竞争最优）
public class Counter {
    private final AtomicLong count = new AtomicLong();
    public void inc() { count.incrementAndGet(); }
    public long get() { return count.get(); }
}

// 方案 C：LongAdder（高并发写多场景最优，如统计）—— 分段累加，读时汇总
public class Counter {
    private final LongAdder count = new LongAdder();
    public void inc() { count.increment(); }
    public long get() { return count.sum(); }   // 近似值（分段的语义）
}
```

**安全发布（Safe Publication）四种方式**：

| 方式 | 机制 |
|------|------|
| 静态初始化 | `static final X x = new X()`（类初始化有锁） |
| volatile 引用 | 发布后立即可见 |
| 不可变对象 | final 字段 + 正确构造 |
| 锁/并发容器 | 放入 ConcurrentHashMap 等 |

> 🎯 **核心要点**：线程安全设计 = **状态识别 → 策略选择（不可变 > CAS > 锁）→ 复合操作原子化 → 安全发布**。策略选择的经验：读多写少 CopyOnWrite/ReadWriteLock、写多 LongAdder、普通竞争 synchronized/原子类、强一致锁。

## 6. 可见性与 happens-before 规则

**happens-before（先行发生）**：JMM 定义的**可见性契约**——若操作 A happens-before 操作 B，则 A 的效果对 B 可见（且 A 不重排到 B 之后）。

**六条核心规则**（面试必背）：

| 规则 | 含义 | 例子 |
|------|------|------|
| 程序顺序 | 同一线程按代码顺序 | 线程内天然可见 |
| **监视器锁** | 解锁 happens-before 后续加锁 | synchronized 块内修改，块外其他线程拿到锁后可见 |
| **volatile** | 写 happens-before 后续读 | volatile 字段的写立即对读可见 |
| 线程启动 | start() happens-before 线程内所有操作 | 启动前设置的字段，线程内可见 |
| 线程终止 | 线程内操作 happens-before join() 返回 | join 后主线程可见其修改 |
| **传递性** | A→B 且 B→C 则 A→C | 链式推导 |

```java
// 利用 happens-before 的正确发布：
class Singleton {                     // 双检锁（DCL）—— volatile 的经典场景
    private static volatile Singleton instance;   // volatile：防止"半初始化发布"（有序性）
    public static Singleton get() {
        if (instance == null) {                    // 快路径（无锁）
            synchronized (Singleton.class) {
                if (instance == null) {            // 慢路径（加锁）
                    instance = new Singleton();    // 三步可能重排 → volatile 禁止
                }
            }
        }
        return instance;
    }
}
```

> ⚠️ **为什么 DCL 必须 volatile**：`new Singleton()` 的三步（分配/初始化/赋值）可能重排为"先赋值后初始化"——线程 B 在快路径读到**非 null 但未初始化**的实例，直接返回使用 → 半初始化对象。volatile 禁止该重排，保证"看到引用即看到完整初始化"。

> 🎯 **核心要点**：happens-before 是"推理可见性"的语法——**synchronized 的可见性由"锁规则"保证（解锁→加锁），volatile 由"volatile 规则"保证（写→读）**。判断"这段代码安全吗"的终极工具就是这套规则（JMM 深挖见 `02-JUC高并发编程/02-Java内存模型JMM.md`）。
