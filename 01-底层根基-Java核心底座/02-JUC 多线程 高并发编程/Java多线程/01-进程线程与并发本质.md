## 1. 进程与线程：资源 vs 执行单元

| 维度 | 进程（Process） | 线程（Thread） |
|------|:--------------:|:--------------:|
| 本质 | **资源容器**（内存空间/文件/信号） | **执行单元**（指令流/栈/寄存器） |
| 内存 | 独立地址空间 | **共享进程地址空间** |
| 通信 | IPC（管道/消息/共享内存） | 直接共享变量 |
| 创建开销 | 大（复制地址空间） | 小（分配栈 + 线程控制块） |
| 切换成本 | 高（TLB 失效） | 较低 |
| 故障隔离 | 进程间隔离 | **同进程线程互相影响** |

```java
// Java 视角：main 方法在 main 线程执行，JVM 本身是多线程进程
// JVM 进程内的重要线程：main、GC 线程、Finalizer、编译器（C1/C2）...
// 验证：jcmd <pid> Thread.print 或 JConsole 看线程列表
```

**两个直觉**：

1. **线程之间共享堆内存**——Java 对象的"共享"由此而来：所有线程都能访问同一个对象（`static` 字段更是全局共享）；
2. **每个线程独立栈**——局部变量是线程私有的（这就是"局部变量天然线程安全"的原因）。

> 🎯 **核心要点**：进程管资源、线程管执行——**共享内存是线程高效的原因，也是并发 bug 的根源**。Java 多线程的一切问题都从"共享"二字开始。

## 2. 线程模型：内核线程与 1:1 映射

**OS 线程模型的三代演进**（Java 的历史包袱由此而来）：

| 模型 | 时期 | 特点 | 问题 |
|------|------|------|------|
| **用户线程（1:N）** | 早期 | 线程在用户态调度，内核只认识进程 | 一个线程阻塞，**整个进程卡死** |
| 内核线程（1:1） | 现代主流 | **每个 Java 线程映射一个内核线程** | 创建/切换成本高（万级就极限） |
| 混合（M:N） | 折中 | 用户线程映射少量内核线程 | 实现复杂，调度不可控 |

**Java 的现状**：

```text
Java 平台线程（1:1）：
Java 线程 ──→ 内核线程（Linux: clone() 创建，每线程独立栈 ~1MB 虚拟内存）
特点：真并行（多核利用）、成本高（创建 ~几十微秒、1MB 栈、切换进内核态）

Java 虚拟线程（M:N，JDK 21+）：
虚拟线程 ──→ 载体线程池（ForkJoinPool，~CPU 核数）──→ 内核线程
特点：用户态调度、阻塞自动卸载（unmount）、创建成本 ~微秒级、百万级可用
```

**为什么"平台线程贵"**（面试必答）：

1. 每线程 **1MB+ 虚拟内存**栈（1 万线程 = 10GB 虚拟地址空间）；
2. 创建/切换需要**内核态系统调用**；
3. 线程切换触发 **TLB/缓存失效**（上下文切换成本，见第 3 节）。

> 🎯 **核心要点**：Java 平台线程 = 内核线程（1:1）——"贵"是内核线程的本性；虚拟线程 = 用户态调度（M:N）——把线程从"OS 资源"变成"JVM 廉价对象"。这是 JDK 21 最大变革的本质。

## 3. 上下文切换：隐藏的成本

**上下文切换（Context Switch）**：CPU 从线程 A 切到线程 B 时，保存 A 的现场（寄存器/PC/栈指针）、恢复 B 的现场——**一切切换都有开销**：

```text
上下文切换成本构成：
① 寄存器保存/恢复（CPU 周期）
② 内核态进出（用户态 → 内核态 → 用户态）
③ TLB 失效：新线程的地址空间不同 → 缓存映射作废 → 后续访问重新加载
④ 缓存冷启动：数据/指令缓存不命中
实测量级：一次切换 ~微秒级（比一条指令慢几百倍）；频繁切换可吃掉 10-30% CPU
```

**线程数与上下文切换的关系**（经典的 U 型曲线）：

```text
线程数太少 → CPU 利用率不足（等待 IO 时空闲）
线程数合适 → 充分利用 CPU
线程数过多 → 上下文切换开销吞噬收益，性能反而下降（拐点后下跌）
经验值：CPU 密集 = 核数 + 1；IO 密集 = 核数 × (1 + IO等待/CPU计算) —— 或直接用虚拟线程
```

**如何度量**：

```bash
# Linux 查看上下文切换统计
vmstat 1          # cs 列 = context switch 次数/秒
# Java 侧：JFR / JMC 有 Thread Context Switch 事件
```

> 🎯 **核心要点**：线程不是越多越好——**切换有成本，超卖必反噬**。这也是线程池存在的原因之一（限制并发数、减少切换），以及"虚拟线程不池化"的底气（用户态切换便宜得多）。

## 4. 并发 vs 并行：单核也能并发

| 维度 | 并发（Concurrency） | 并行（Parallelism） |
|------|:------------------:|:-------------------:|
| 定义 | 多个任务**交替执行**（宏观同时） | 多个任务**同时执行**（微观同时） |
| 硬件 | 单核即可 | 必须多核/多 CPU |
| 关注点 | **任务结构**（怎么组织） | **执行效率**（怎么加速） |
| 类比 | 一个人交替做三件事 | 三个人各做一件事 |

```text
并发（单核）：  [A][B][A][C][B][A]  ← 时间片轮转，宏观"同时"
并行（双核）：  [A][B][C]          ← 同一时刻真并行
              [D][E][F]
```

**Java 里的对应**：

- **并发**：多线程 + 时间片轮转——单核上 `new Thread()` 一样"看起来同时"；
- **并行**：多核上的真并行——`parallelStream()`、ForkJoinPool 利用多核；
- **注意**：`Runtime.getRuntime().availableProcessors()` 才是并行上限，**线程数 ≠ 并行度**。

> 🎯 **核心要点**：并发是"结构"（交替执行），并行是"效率"（同时执行）——**并发解决"不阻塞"（IO 等待时干别的），并行解决"快"（多核分摊）**。虚拟线程解决的是并发问题，不是并行问题。

## 5. 虚拟线程：线程模型的演进

**虚拟线程（JDK 21 转正，JEP 444）**对"线程"概念的重塑：

```text
平台线程（OS 线程）：阻塞 = 占着内核线程闲着 → 需要线程池复用
虚拟线程（JVM 线程）：阻塞 = 从载体线程卸载（unmount），载体线程去干别的
```

| 维度 | 平台线程 | 虚拟线程 |
|------|:--------:|:--------:|
| 创建成本 | ~几十微秒，1MB 栈 | ~微秒级，几百字节起 |
| 数量上限 | 千~万级 | **百万级** |
| 调度 | 内核调度 | JVM 用户态调度 |
| 阻塞处理 | 占着线程 | **自动卸载（挂起）** |
| 适合 | CPU 密集 / 原生调用 | **IO 密集**（阻塞多） |
| 池化 | 需要（线程池） | **不需要**（每任务一个） |

```java
// 虚拟线程的正确用法：每任务一个，不池化
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Result>> futures = requests.stream()
            .map(r -> executor.submit(() -> fetch(r)))
            .toList();
}
```

**虚拟线程时代的"多线程基础"没变**：共享可变状态仍要同步、死锁仍会发生、原子性可见性仍成立——**变的是线程的成本，不变的是并发的规则**（synchronized 与虚拟线程的交互见 04 模块第 5 节）。

> 🎯 **核心要点**：虚拟线程 = "**IO 密集场景的默认线程策略**"（2025 最佳实践）——平台线程留给 CPU 密集与原生代码，虚拟线程接管"每请求一线程"的阻塞式编程，让同步代码获得异步的性能（详见 `02-JUC高并发编程/12-虚拟线程与结构化并发.md`）。

## 6. 多线程为什么难：共享可变状态

**多线程 bug 的根源是"共享可变状态"**——三个词缺一个都不难：

```text
共享（Shared）+ 可变（Mutable）+ 多线程（Multi-thread）
        ↓
竞态条件（Race Condition）：结果取决于线程执行时序

// 经典演示：100 个线程各做 10 万次 i++
static int count = 0;                       // 共享 + 可变
for (int i = 0; i < 100_000; i++) count++;  // 非原子：读-加-写三步
// 实际结果 < 10_000_000 —— 丢失更新（Lost Update）
```

**竞态的三步推演**（面试标准演示）：

```text
count++ 实际是三步：① 读 count ② count+1 ③ 写回 count
线程 A 读到 100 → 线程 B 也读到 100（还没写回）→ A 写 101 → B 写 101
→ 两次自增只加了一次 —— 丢更新
```

**应对方向**（对应 03 模块）：

| 方向 | 手段 | 适用 |
|------|------|------|
| **消除共享** | 局部变量、ThreadLocal、不可变对象 | 最优先（无共享则无竞争） |
| **消除可变** | final/record/不可变集合 | 次优先 |
| **同步访问** | synchronized/Lock/CAS | 兜底（有共享且可变时） |

> 🎯 **核心要点**：并发 bug 的推演公式 = **共享 × 可变 × 非原子操作 = 竞态**——排查并发问题先问三个问题：共享吗？可变吗？操作原子吗？缺一问号，答案就在下一个。
