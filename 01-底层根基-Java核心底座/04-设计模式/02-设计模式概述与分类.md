## 1. 什么是设计模式

设计模式（Design Pattern）是前辈们经过反复验证、总结出的在特定场景下解决常见问题的**可复用方案**。它不是代码框架，而是一套**经验范式**——就像建筑行业的蓝图，告诉我们"当遇到这类问题时，这样组织代码最稳妥"。

1995年，GoF（Gang of Four，四位作者Erich Gamma、Richard Helm、Ralph Johnson、John Vlissides）出版了《Design Patterns: Elements of Reusable Object-Oriented Software》，正式确立了23种经典设计模式的分类体系。

### 学习设计模式的意义

不在于记住23个名词，而在于掌握**面向对象设计的核心思想**：

| 核心思想 | 说明 |
|----------|------|
| **封装变化** | 将可能变化的部分隔离封装，不变的部分保持稳定 |
| **面向接口编程** | 依赖抽象而非具体实现，降低耦合 |
| **组合优于继承** | 组合更灵活、更动态，不破坏封装 |
| **高内聚低耦合** | 模块内部高度相关，模块之间尽量少依赖 |

## 2. GoF 23种设计模式分类

GoF将23种设计模式按用途分为三大类：

| 分类 | 数量 | 模式名称 | 核心关注 |
|------|------|----------|----------|
| **创建型** | 5 | 单例、工厂方法、抽象工厂、建造者、原型 | 对象创建与初始化 |
| **结构型** | 7 | 适配器、装饰器、代理、外观、桥接、组合、享元 | 类与对象的组合结构 |
| **行为型** | 11 | 策略、模板方法、观察者、迭代器、责任链、命令、备忘录、状态、访问者、中介者、解释器 | 对象间通信与职责分配 |

## 3. 创建型模式概述

**核心目标**：关注对象的创建过程，隐藏创建细节，降低对象创建与使用的耦合。

| 模式 | 核心思想 | 适用场景 |
|------|----------|----------|
| **单例模式** | 确保一个类只有一个实例，提供全局访问点 | 全局配置、工具类、线程池、连接池 |
| **工厂方法** | 定义创建对象的接口，由子类决定实例化哪个类 | 产品种类多、创建逻辑复杂 |
| **抽象工厂** | 提供一个接口创建一系列相关对象（产品族） | UI组件库、多数据库适配 |
| **建造者模式** | 分步构建复杂对象，构建过程与表示分离 | 属性多的复杂对象、不可变对象 |
| **原型模式** | 通过克隆已有对象创建新对象，避免重复初始化 | 创建成本高、需批量创建的场景 |

> 创建型模式的核心思想是：**将"创建"与"使用"分离**，让系统不依赖于具体类的实例化方式。

## 4. 结构型模式概述

**核心目标**：关注类与对象的组合方式，通过合理的组合优化类的结构，实现功能复用、降低耦合。

| 模式 | 核心思想 | 适用场景 |
|------|----------|----------|
| **适配器模式** | 将一个类的接口转换成客户端期望的另一个接口 | 第三方SDK对接、老系统兼容 |
| **桥接模式** | 将抽象部分与实现部分分离，使二者可独立变化 | 多维度独立变化的场景 |
| **组合模式** | 将对象组合成树形结构，表示"部分-整体"层次 | 文件系统、菜单、组织架构 |
| **装饰器模式** | 动态地给对象添加额外职责，不改变原对象结构 | IO流、日志增强、权限控制 |
| **外观模式** | 为子系统提供统一入口，隐藏子系统复杂性 | 复杂业务流程封装 |
| **享元模式** | 运用共享技术减少大量相似对象的创建开销 | String常量池、连接池、缓存 |
| **代理模式** | 为其他对象提供代理，以控制对这个对象的访问 | AOP、权限控制、延迟加载 |

## 5. 行为型模式概述

**核心目标**：关注对象之间的通信方式和职责分配，规范对象的行为交互。

| 模式 | 核心思想 | 适用场景 |
|------|----------|----------|
| **模板方法** | 定义算法骨架，将部分步骤延迟到子类实现 | 流程标准化、框架扩展点 |
| **策略模式** | 定义一系列算法，封装并使它们可相互替换 | 支付方式、排序算法、促销活动 |
| **观察者模式** | 定义一对多依赖，状态变化时通知所有观察者 | Spring Event、消息订阅 |
| **责任链模式** | 多个处理者连成链，请求沿链传递直到被处理 | 审批流、过滤器、拦截器 |
| **命令模式** | 将请求封装为对象，支持排队、撤销、重做 | 操作撤销、任务队列、事务 |
| **状态模式** | 状态改变时行为自动改变，消除大量if-else | 订单状态机、工作流 |
| **迭代器模式** | 提供统一方式遍历集合元素，不暴露内部结构 | Java集合框架遍历 |
| **访问者模式** | 将数据结构与数据操作分离，新增操作无需修改元素 | 数据统计、报表生成 |
| **中介者模式** | 引入中介者协调多对象交互，降低耦合 | 聊天室、UI组件交互 |
| **解释器模式** | 定义语言文法，提供解释器解释该语言的句子 | 规则引擎、表达式解析 |
| **备忘录模式** | 在不破坏封装前提下，捕获并保存对象内部状态 | 撤销恢复、游戏存档 |

## 7. 设计模式选择指南

### 问题驱动法

设计模式的选用应该**根据实际场景反推**，推荐的决策流程：

1. **识别变化点**：找到代码中"可能发生变化"的部分
2. **封装变化**：将变化的部分封装起来，不让变化扩散到整个系统
3. **模式匹配**：看看经典模式是否正好解决了这个场景的问题

### 问题对照表

| 你的问题 | 对应的模式 |
|----------|-----------|
| 需要全局唯一实例 | 单例模式 |
| 需要一套可互相替换的算法 | 策略模式 |
| 需要为对象动态增加功能 | 装饰器模式 |
| 需要控制对象访问 | 代理模式 |
| 需要统一处理一系列相关对象的创建 | 工厂方法或抽象工厂 |
| 需要在不修改代码的情况下新增功能 | 策略/模板方法/装饰器 |
| 需要在多个对象间传递请求直到有人处理 | 责任链模式 |
| 需要一个对象状态变化时通知其他对象 | 观察者模式 |
| 对象创建过程很复杂，构造器参数太多 | 建造者模式 |

> 核心原则：**先有设计问题，后有设计模式。不要为了用设计模式而写代码。**

## 8. 实战要点与避坑

### 实战要点

| 要点 | 说明 |
|------|------|
| **切勿死记硬背** | 重在理解场景——"为什么用、什么时候用、怎么用" |
| **拒绝盲目滥用** | 简单场景无需强行套用模式，避免过度设计 |
| **遵循原则优先** | 先掌握SOLID，再灵活选用模式 |
| **结合框架源码** | 读Spring/Netty/MyBatis源码理解模式落地 |

### 避坑总结

| 坑点 | 正确做法 |
|------|----------|
| **盲目套用模式** | 简单业务无需工厂/建造者等复杂模式 |
| **过度设计** | 3个if-else不需要策略模式，KISS原则优先 |
| **模式本身成为负担** | 新增成员不熟悉模式反而降低效率 |
| **先设计后问题** | 不要为了用设计模式而写代码，先有设计问题，后有设计模式 |

### 过度设计警示

```java
// 错误：只有两种支付方式，却硬套策略模式+工厂模式+单例+反射注册
// 正确：先用简单的if-else，当支付方式增长到4-5个以上时再重构为策略模式

// 错误：只有一种实现，却创建了接口→抽象类→工厂接口→具体工厂四层结构
// 正确：当某个接口只有1-2个实现且不会增加时，不需要抽象工厂模式
```

### 实用建议

1. 先写出能工作的简单代码
2. 当发现修改代码变得困难、同一个地方频繁修改时重构
3. 重构时引入设计模式，而不是从一开始就预测未来需求

## 9. 设计模式关系图谱

### 9.1 模式间的协作关系

| 核心模式 | 常协作的模式 | 协作说明 |
|----------|-------------|----------|
| **工厂方法** | 单例模式 | 工厂内部使用单例管理工厂实例 |
| **抽象工厂** | 工厂方法 | 抽象工厂的每个创建方法通常用工厂方法实现 |
| **建造者** | 策略模式 | 不同建造者可以使用不同策略组装产品 |
| **组合模式** | 迭代器+访问者 | 用迭代器遍历树形结构，用访问者执行操作 |
| **装饰器** | 工厂模式 | 用工厂生产被装饰对象，再按需装饰 |
| **代理模式** | 工厂方法 | Spring通过工厂方法创建代理对象 |
| **策略模式** | 工厂模式 | 用工厂选择具体策略，客户端无感策略创建 |
| **模板方法** | 工厂方法 | 模板方法中的抽象步骤可通过工厂创建对象 |
| **观察者** | 中介者 | 观察者模式的一对多可演化为中介者的多对多 |
| **命令模式** | 备忘录 | 命令的执行历史可用备忘录保存状态以支持撤销 |
| **状态模式** | 享元模式 | 状态对象通常无状态，可用享元模式共享复用 |
| **职责链** | 组合模式 | 可将职责链节点用组合模式组织成树形结构 |

### 9.2 易混淆模式对比矩阵

#### 工厂方法 vs 抽象工厂

| 维度 | 工厂方法 | 抽象工厂 |
|------|---------|---------|
| 创建对象 | 一种产品 | 一整套产品族 |
| 扩展方向 | 新增产品（符合OCP） | 新增产品族（符合OCP），新增产品等级（违反OCP） |
| 层次 | 一个方法 | 多个方法（每个产品一个） |
| 典型场景 | 单一对象有多种实现 | 成套组件需要配套使用 |

#### 装饰器 vs 代理

| 维度 | 装饰器 | 代理 |
|------|--------|------|
| 目的 | 增强功能 | 控制访问 |
| 创建方式 | 客户端手动嵌套 | 框架/工厂自动生成 |
| 对象关系 | 可多层嵌套 | 通常一对一 |
| 接口一致性 | 保持原接口 | 保持原接口 |
| 典型场景 | IO流、日志增强 | AOP、远程调用、延迟加载 |

#### 策略 vs 状态

| 维度 | 策略模式 | 状态模式 |
|------|---------|---------|
| 切换方式 | 客户端主动选择 | 内部状态自动流转 |
| 对象关系 | 策略间独立 | 状态间有关联（流转规则） |
| 目的 | 解决"怎么做" | 解决"何时做、做什么" |
| 客户端参与 | 需要选择策略 | 不参与状态切换 |

#### 适配器 vs 桥接

| 维度 | 适配器 | 桥接 |
|------|--------|------|
| 设计阶段 | 后期兼容 | 前期设计 |
| 目的 | 接口转换 | 分离抽象与实现 |
| 变化方向 | 适配者不变，目标变 | 抽象和实现各自独立变化 |
| 典型场景 | 第三方SDK对接 | JDBC驱动、消息通知 |

#### 模板方法 vs 策略

| 维度 | 模板方法 | 策略模式 |
|------|---------|---------|
| 粒度 | 控制算法骨架（多步骤） | 封装整个算法（单步骤） |
| 复用方式 | 继承（父类定义骨架） | 组合（上下文持有策略） |
| 变更点 | 子类重写抽象步骤 | 替换整个策略对象 |
| 典型场景 | JdbcTemplate | 支付方式切换 |

## 10. 设计模式与六大设计原则的对应关系

| 设计原则 | 遵循该原则的模式 | 说明 |
|----------|-----------------|------|
| **单一职责** | 所有模式 | 每个模式都让每个类只承担一种角色 |
| **开闭原则** | 策略、模板方法、装饰器、代理、观察者等 | 新增功能通过扩展实现，不修改原有代码 |
| **里氏替换** | 模板方法、策略 | 子类替换父类不影响程序行为 |
| **接口隔离** | 适配器、外观 | 提供客户端需要的专用接口 |
| **依赖倒置** | 工厂方法、抽象工厂、策略 | 依赖抽象接口，不依赖具体实现 |
| **合成复用** | 装饰器、桥接、策略、适配器（对象） | 优先组合而非继承 |
| **迪米特法则** | 外观、中介者、代理 | 只与直接朋友通信，减少类间耦合 |

## 12. 设计模式相关名词解释

| 术语 | 解释 |
|------|------|
| **GoF** | Gang of Four（四人组），指《设计模式》一书的四位作者 |
| **OCP** | 开闭原则，对扩展开放、对修改关闭 |
| **DIP** | 依赖倒置原则，依赖抽象而非具体实现 |
| **LSP** | 里氏替换原则，子类可替换父类 |
| **ISP** | 接口隔离原则，不依赖不需要的接口 |
| **SRP** | 单一职责原则，一个类只做一件事 |
| **LoD** | 迪米特法则/最少知道原则 |
| **组合优于继承** | 优先使用组合而非继承来达到代码复用 |
| **封装变化** | 将可能变化的逻辑封装起来，不让变化扩散 |
| **面向接口编程** | 声明变量时使用接口类型，而非实现类类型 |
| **泛型** | Java中的`<>`语法，99%用于指定容器类型，编译期类型检查 |
| **双分派** | 访问者模式的核心机制，动态绑定两次来决定执行哪个方法 |

> 补充说明：泛型（`<>`语法）不是设计模式，但设计模式代码中大量使用（如`List<T>`、`Map<K,V>`），理解泛型有助于阅读模式源码。
