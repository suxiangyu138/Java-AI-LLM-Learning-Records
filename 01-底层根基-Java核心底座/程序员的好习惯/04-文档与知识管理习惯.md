## 1. 文档不是负担是设计工具

> 🎯 **核心认知**：文档不是写代码后的「收尾工作」，而是写代码前的「设计工具」——**好的文档习惯让代码更好，而不是更多工作**。

```text
文档价值的重新定义
├── ❌ 旧认知：代码写完了补文档（为了交差）
├── ✅ 新认知：写码前写文档（为了设计）：
│   ├── 暴露设计缺陷（写清楚时发现漏洞）
│   ├── 让接口设计更简洁（想清楚再写）
│   └── 减少方向不明确的内耗（写完就知道要做什么）
└── 结论：文档先行 = 低成本试错 + 高质量设计
```

| 文档类型 | 时机 | 价值 |
|---------|------|------|
| 设计文档 | **写码前** | 暴露缺陷、对齐方案 |
| 接口文档 | 写码前/中 | 协作契约、调用方先行 |
| 使用说明 | 交付时 | 减少重复答疑 |
| 复盘文档 | 完成后 | 经验沉淀 |

## 2. 文档先行：先写文档再写代码

### 2.1 文档先行的写法

> 🎯 **文档先行**：写代码之前先用大白话回答五个问题——「这个功能解决什么痛点」「接口怎么调用」「传入什么数据、吐出什么结果」「边缘情况如何表现」：

```text
功能设计文档（写码前 30 分钟）
┌────────────────────────────────┐
│ 功能：订单导出                    │
│ 1. 解决什么痛点：运营手动导出 1000+ 订单到 Excel 耗时 2 小时   │
│ 2. 接口怎么调用：GET /api/orders/export?status=PAYING         │
│ 3. 传入什么：status 筛选 + dateRange 时间范围                 │
│ 4. 吐出什么：Excel 文件（列：订单号/金额/状态/时间/用户）       │
│ 5. 边缘情况：空数据返回空表头 Excel / 超大数据量走异步任务      │
│    / 并发导出限制 5 次/分钟                                    │
└────────────────────────────────┘
→ 写完这 5 个问题，代码结构已经清晰（甚至发现 2 个设计漏洞）
```

### 2.2 文档先行的收益

| 收益 | 说明 |
|------|------|
| **暴露缺陷** | 写清楚时发现边界/异常遗漏 |
| **接口更简洁** | 想清楚再写，少返工 |
| **减少内耗** | 方向明确，不用边写边猜 |
| **评审前置** | 设计文档先行评审，避免代码白写 |

> 💡 **实战经验**：写代码前花 30 分钟写设计文档，通常能省下 3 小时返工——「慢就是快」的典型场景。

## 3. 边做边记：让记录成为习惯

### 3.1 记录是周报与复盘的原料

> ⚠️ **周报写得费劲不是写作能力问题，而是工作过程没有被好好记录**——没有记录，周报只能靠回忆（回忆 ≈ 编造 + 遗漏）。

### 3.2 记录习惯三要点

```text
边做边记三要点
├── ① 随手记：任务/待办/跟进议题记在随时能看到的地方
│   ├── 不记脑子里（会忘）
│   └── 不记微信聊天里（会淹没）
├── ② 看板化：任务卡片带四要素
│   ├── 创建时间 / 负责人 / 截止日期 / 状态标签
│   └── 工具：看板（板栗/Trello/Notion）或轻量清单
└── ③ 周五即周报：看板拉出来就是周报草稿（零成本）
```

### 3.3 记录的最小闭环

```text
每日记录最小闭环（3 分钟）
├── 开工：今日 3 件事（优先级 TOP3）
├── 进行中：完成的打勾 + 卡住的标注原因
├── 收工：明日 3 件事预告 + 遗留问题
└── 周末：看板 = 周报 + 周复盘原料
→ 成本 3 分钟/天，收益：周报 10 分钟 + 复盘有据 + 进度可视化
```

## 4. 单人晨会日志

### 4.1 什么是单人晨会

> 🎯 **单人晨会**：每天开工前花五分钟写下三行——**昨天彻底干完了什么、今天盯死哪几个核心产出、眼前有什么潜在隐患**。

```text
单人晨会日志模板（3 行）
┌────────────────────────────────────┐
│ 2026-08-04 晨会                     │
│ 1. 昨天干完：订单导出 API + 单元测试（8 个用例全绿）│
│ 2. 今天盯死：退款幂等改造（下午 4 点前完成并提评审）  │
│ 3. 潜在隐患：支付网关联调还没确认环境，今天上午要催  │
└────────────────────────────────────┘
```

### 4.2 单人晨会的价值

| 价值 | 说明 |
|------|------|
| **夺回主动权** | 思维在失控前被拉回主线 |
| **聚焦核心产出** | 「盯死」= 明确今天唯一的攻坚目标 |
| **风险前置** | 隐患写下来 = 不会忘 = 提前处理 |
| **复盘依据** | 晨会日志 = 周复盘/总结的客观数据源 |

> 💡 **与时间管理的关系**：晨会日志的「今天盯死哪 2-3 件事」就是第 02 篇 TOP 3 原则的落地载体——两个习惯合体使用。

## 5. 周报自动化

### 5.1 周报的正确姿势

```text
周报 = 记录的自然产物（不是写作任务）
├── ❌ 错误姿势：周五下午憋 2 小时回忆这周干了什么
├── ✅ 正确姿势：每天 3 分钟记录 → 周五拉取看板
│    → 补充价值说明 → 10 分钟完成
└── 周报结构：
    ├── 本周完成（从看板勾选完成项）
    ├── 下周计划（从待办池挑 TOP3）
    ├── 风险与阻塞（晨会日志里的隐患汇总）
    └── 需要支持（向协作方要资源的清单）
```

### 5.2 周报的定位

> 🎯 **周报不是写给领导的流水账，是写给自己的进度仪表盘**——它同时服务：领导知情（信任）、自己复盘（调整）、团队同步（协作）。

```text
周报质量对照
├── ❌「本周写了订单模块、修复了 3 个 bug、开了几个会」
├── ✅「本周完成订单导出功能（已上线，运营导出耗时从 2h → 10s）；
│       修复 3 个线上 bug（均为边界条件，已补测试）；
│       下周：退款幂等改造 + 支付网关联调；
│       风险：联调环境未就绪，需要运维本周内提供」
```

## 6. 个人知识管理系统

### 6.1 知识管理的目标

> 🎯 **知识管理目标**：让「踩过的坑」变成「可复用的资产」——不让经验随人走、不让教训重复踩。

### 6.2 知识系统五要素

```text
个人知识管理系统
├── ① 统一工具：一个主力笔记工具（Notion/Obsidian/语雀）
├── ② 清晰分类：按领域/项目/时间三维标签
├── ③ 可搜索结构：标题规范（[BUG] / [方案] / [学习] 前缀）
├── ④ 三类必记内容：
│   ├── Bug 复现步骤 + 根因 + 修复方案
│   ├── 技术决策的原因（为什么选 A 不选 B）
│   └── 审查中获得的最佳反馈
└── ⑤ 定期整理：每周整理一次「本周收获」归档
```

### 6.3 知识管理习惯闭环

```text
知识管理闭环
├── 输入：工作中踩坑/决策/新知识（随时记）
├── 处理：每周整理归档（标签/分类/去重）
├── 输出：周复盘引用 / 技术分享 / 团队知识库
└── 复利：知识库越用越值钱——「人肉问答」变「知识库问答」
```

> 💡 **知识的复利效应**：同样的坑，记下来 = 只踩一次；不记 = 每次踩。三年后的差别是「老手」与「三年经验重复了三次的新人」。

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 文档先行：写码前用 5 问（痛点/调用/输入输出/边缘）写设计文档——低成本试错 + 高质量设计
> 2. 边做边记：任务看板化（时间/负责人/截止/状态），周五拉取即周报
> 3. 单人晨会 3 行日志（昨天干完/今天盯死/潜在隐患）——夺回主动权 + 复盘数据源
> 4. 知识管理闭环（输入→整理→输出→复利）：Bug 复现/决策原因/审查反馈三类必记
