## 1. 字符串拼接 "+"

### 1.1 最熟悉的语法糖

Java 中最常用的语法糖，没有之一。

```java
// 源代码——语法糖写法
String s = "Hello, " + name + "!";
```

### 1.2 编译前后对比

**Java 5~8 解糖（javac 编译后等价代码）：**

```java
// 等价于——编译器翻译结果
String s = new StringBuilder()
    .append("Hello, ")
    .append(name)
    .append("!")
    .toString();
```

**字节码验证（使用 javap -c 反编译）：**

```text
 0: new           #2    // class java/lang/StringBuilder
 3: dup
 4: invokespecial #3    // Method StringBuilder."<init>":()V
 7: ldc           #4    // String "Hello, "
 9: invokevirtual #5    // Method StringBuilder.append:(String)
12: aload_1             // ← name 变量
13: invokevirtual #5    // Method StringBuilder.append:(String)
16: ldc           #6    // String "!"
18: invokevirtual #5    // Method StringBuilder.append:(String)
21: invokevirtual #7    // Method StringBuilder.toString:()String
```

> 可以看到：`new StringBuilder` → 三次 `append()` → 一次 `toString()`。

### 1.3 性能陷阱：循环内拼接

```java
// ❌ 反例：循环内拼接字符串
String s = "";
for (int i = 0; i < 1000; i++) {
    s += i;  // 每次循环 new 一个 StringBuilder！
}
```

**等价代码：**

```java
// 编译器生成的等价代码
String s = "";
for (int i = 0; i < 1000; i++) {
    s = new StringBuilder()
        .append(s)    // ← 每次都要拷贝已有内容！
        .append(i)
        .toString();
}
```

> 循环 1000 次 → 创建 1000 个 StringBuilder 对象 → O(n^2) 复杂度。

**正确做法：**

```java
// ✅ 正例：显式使用 StringBuilder
StringBuilder sb = new StringBuilder(1024); // 预估容量
for (int i = 0; i < 1000; i++) {
    sb.append(i);
}
String s = sb.toString();
```

### 1.4 Java 9 的优化：invokedynamic

Java 9 开始，`javac` 不再生成 `StringBuilder` 调用，而是生成 `invokedynamic + StringConcatFactory`：

```text
; Java 9+ 字节码
 0: aload_1             ; name
 1: invokedynamic #2    ; makeConcatWithConstants
```

```java
// Java 9+ 等价行为（运行期决定实现策略）
// 可能使用 StringBuilder、StringBuffer、或直接计算长度后 new String
```

> 💡 **面试追问**：Java 9 为什么换成 `invokedynamic`？
>
> 答：将拼接策略从**编译期决定**改为**运行期决定**。JVM 可以在运行期根据字符串长度、上下文选择最优策略（如直接预分配数组），未来还可优化而无需重新编译源码。

### 1.5 常量折叠（Constant Folding）

```java
// 编译期优化：常量拼接在编译期直接完成
String s = "Hello, " + "World!"; // 直接编译为 "Hello, World!"
```

字节码：

```text
 0: ldc           #6    // String "Hello, World!"
```

> 只有**字面量常量**才会折叠。变量参与拼接 → StringBuilder。

### 1.6 `+` 与 `concat()` 的区别

| 对比维度 | `+` | `String.concat()` | `StringBuilder` |
|---------|:---:|:----------------:|:---------------:|
| 语法糖 | 是 | 否 | 否 |
| 编译策略 | Java 8: StringBuilder / Java 9+: indy | 普通方法调用 | 普通方法调用 |
| null 处理 | 拼接 "null" 字符串 | NullPointerException | 拼接 "null" |
| 多段性能 | 优（单次 StringBuilder） | 差（多次 new String） | 优 |

> 🎯 **核心要点**：
> 1. 单行拼接 `"a" + b + "c"` → 编译为单个 `StringBuilder` 链式调用，性能可接受
> 2. 循环内拼接 → 每次 new StringBuilder，**必须改成显式 StringBuilder**（O(n^2) → O(n)）
> 3. Java 9+ 使用 `invokedynamic`，运行期决定拼接策略
> 4. 常量拼接在编译期直接折叠成结果字符串

## 2. 自动装箱与拆箱

### 2.1 自动装箱（Autoboxing）

```java
// 源代码——自动装箱
Integer n = 42;
```

**等价代码：**

```java
Integer n = Integer.valueOf(42);
```

**字节码验证：**

```text
 0: bipush        42
 2: invokestatic  #2  // Method Integer.valueOf:(I)Integer
 5: astore_1
```

### 2.2 自动拆箱（Unboxing）

```java
// 源代码——自动拆箱
Integer n = Integer.valueOf(42);
int m = n;
```

**等价代码：**

```java
int m = n.intValue();  // 编译器插入 intValue() 调用
```

### 2.3 Integer 缓存机制（关键陷阱根源）

```java
// 陷阱代码——你以为的 == 和实际的 !=
Integer a = 127;
Integer b = 127;
System.out.println(a == b); // true

Integer c = 200;
Integer d = 200;
System.out.println(c == d); // false !!!
```

**原因：** `Integer.valueOf()` 缓存了 -128~127 之间的值。

```java
// Integer.valueOf 源码（示意）
public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];
    return new Integer(i);
}
```

> 默认缓存范围 -128~127，可通过 JVM 参数 `-XX:AutoBoxCacheMax=10000` 调整上限。

**其他包装类型的缓存：**

| 包装类型 | 缓存范围 | 说明 |
|---------|:--------:|------|
| `Boolean` | true / false | 只有两个值，必然缓存 |
| `Byte` | -128~127 | 所有值（byte 范围） |
| `Short` | -128~127 | 仅部分 |
| `Integer` | -128~127 | 默认，可配置 |
| `Long` | -128~127 | 不可配置 |
| `Float` | 无 | 不缓存 |
| `Double` | 无 | 不缓存 |
| `Character` | 0~127 | 仅 ASCII |

### 2.4 null 拆箱 → 空指针异常

```java
// ⚠️ 经典 NPE 陷阱
public static Integer getNull() { return null; }

public static void main(String[] args) {
    int i = getNull(); // ❌ NullPointerException!
    // 编译为：getNull().intValue() → null.intValue() → NPE
}
```

**更隐蔽的形式——三元运算符类型推断造成的 NPE：**

```java
// ⚠️ 三元运算符类型推断陷阱
Map<String, Boolean> map = new HashMap<>();
map.put("key", null);

Boolean b = map.containsKey("key") ? map.get("key") : false;
// ❌ 仍然 NPE！因为三元运算符两侧类型推断为 boolean（自动拆箱）
// 等价于：Boolean.valueOf(map.containsKey("key") ? map.get("key").booleanValue() : false)
```

> 原因：三元运算符 `? :` 要求两侧表达式类型一致。`false` 是 `boolean`，编译器会尝试将 `map.get("key")`（`Boolean`）拆箱为 `boolean` → null 拆箱 → NPE。

### 2.5 频繁装箱造成的 GC 压力

```java
// ❌ 反例：大量自动装箱
Integer sum = 0;  // 运行时：Integer.valueOf(0)
for (int i = 0; i < 1000000; i++) {
    sum += i;     // 每次：拆箱 + 运算 + new Integer() → 100 万次对象创建！
}
```

等价于：

```java
Integer sum = Integer.valueOf(0);
for (int i = 0; i < 1000000; i++) {
    sum = Integer.valueOf(sum.intValue() + i); // 每次创建新对象
}
```

> 会导致大量短期对象的创建，增加 Young GC 频率。

**正确做法：**

```java
// ✅ 正例：使用原始类型
int sum = 0;
for (int i = 0; i < 1000000; i++) {
    sum += i;  // 原始类型运算，无对象创建
}
```

### 2.6 `==` 与 `equals()` 的选择

```java
Integer a = new Integer(100); // 显式 new，不走缓存
Integer b = 100;              // 走 Integer.valueOf(100) → 缓存
System.out.println(a == b);   // false（不同对象引用）
System.out.println(a.equals(b)); // true（值相等）

Integer c = 100;
System.out.println(b == c);   // true（来自同一缓存对象）
System.out.println(b.equals(c)); // true
```

> 黄金规则：**包装类型比较永远用 `equals()`，不要用 `==`**。即使 -128~127 之间偶然正确，也不该依赖这个实现细节。

### 面试追问合集

| 追问 | 解答 |
|------|------|
| `Integer a = 200; Integer b = 200; a == b` 为什么 false？ | `valueOf()` 超出缓存范围 → new 新对象 |
| 缓存范围能否修改？ | `-XX:AutoBoxCacheMax=10000` 可调整 Integer 上限 |
| `Boolean` 的 `==` 安全吗？ | 安全，只有两个常量 `TRUE` / `FALSE`，`==` 恒等于 `equals()` |
| 拆箱 NPE 怎么排查？ | 看字节码中是否有 `intValue()` / `doubleValue()` 等方法调用 |
| `long a = 0L; Long b = null; a = b;` 会怎样？ | NPE，拆箱 `b.longValue()` |
| `Integer` 和 `int` 做 `==` 比较？ | Integer 自动拆箱为 int 后比较值（不会 NPE 除非 null） |

> 🎯 **核心要点**：
> 1. 装箱调用 `valueOf()`（有缓存），拆箱调用 `xxxValue()`
> 2. Integer 缓存范围 -128~127，`==` 比较在此范围内为 true，超出为 false
> 3. null 拆箱必然 NPE——三元运算符类型推断是隐藏 NPE 来源
> 4. 大量装箱导致 GC 压力，**数值计算用原始类型**
> 5. **包装类型永远用 `equals()` 比较值**

## 3. 增强 for 循环

### 3.1 两种底层实现

增强 for 循环（for-each）的底层实现取决于遍历的目标类型。

#### 情况一：遍历数组

```java
// 源代码
int[] arr = {1, 2, 3};
for (int x : arr) {
    System.out.println(x);
}
```

**解糖后：**

```java
// 等价于普通 for 循环
int[] arr = {1, 2, 3};
for (int i = 0; i < arr.length; i++) {
    int x = arr[i];
    System.out.println(x);
}
```

#### 情况二：遍历 Iterable（如 List、Set）

```java
// 源代码
List<String> list = Arrays.asList("A", "B", "C");
for (String s : list) {
    System.out.println(s);
}
```

**解糖后：**

```java
// 等价于 Iterator 循环
List<String> list = Arrays.asList("A", "B", "C");
for (Iterator<String> it = list.iterator(); it.hasNext(); ) {
    String s = it.next();
    System.out.println(s);
}
```

### 3.2 字节码验证

```text
; 遍历 List 的字节码
 0: aload_1                ; list
 1: invokeinterface #2     ; List.iterator():Iterator
 6: astore_3               ; 保存 Iterator 到局部变量
 7: aload_3
 8: invokeinterface #3     ; Iterator.hasNext():boolean
13: ifeq          38       ; 没有下一个则跳转
16: aload_3
17: invokeinterface #4     ; Iterator.next():Object
22: checkcast     #5       ; 强制转型为 String
25: astore_2               ; 保存到 s
26: getstatic     #6       ; System.out
29: aload_2
30: invokevirtual #7       ; PrintStream.println(String)
33: aload_3
34: goto          7        ; 继续循环
37: return
```

> 字节码确认：生成了 `Iterator` 对象 + `hasNext()` + `next()` 调用 + `checkcast` 转型。

### 3.3 ConcurrentModificationException 根因

```java
// ❌ 经典错误：增强 for 循环中删除元素
List<String> list = new ArrayList<>(Arrays.asList("A", "B", "C", "D"));
for (String s : list) {
    if (s.equals("B")) {
        list.remove(s); // ❌ 抛 ConcurrentModificationException!
    }
}
```

**根本原因：**

```java
// 增强 for 解糖后的代码——等价于：
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    String s = it.next();  // ← 这里检查 modCount
    if (s.equals("B")) {
        list.remove(s);    // ← 直接调用 List.remove() 修改 modCount
    }
}
```

`ArrayList` 内部维护了一个 `modCount`（修改次数）。`Iterator` 内部有 `expectedModCount`（期望的修改次数）。`it.next()` 时会检查 `modCount != expectedModCount` → 不一致 → 抛出 `ConcurrentModificationException`。

```java
// ArrayList.Itr.next() 源码示意
public E next() {
    checkForComodification(); // ← 检查点
    // ...
}

final void checkForComodification() {
    if (modCount != expectedModCount) // modCount 被 list.remove 修改过
        throw new ConcurrentModificationException();
}
```

**正确做法：**

```java
// ✅ 方法一：使用 Iterator.remove()
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    String s = it.next();
    if (s.equals("B")) {
        it.remove(); // Iterator.remove() 会同步 expectedModCount
    }
}

// ✅ 方法二：使用 Collection.removeIf()（Java 8+）
list.removeIf(s -> s.equals("B"));
// 等价于内部使用 Iterator.remove() + 遍历

// ✅ 方法三：收集后再删除
List<String> toRemove = list.stream()
    .filter(s -> s.equals("B"))
    .collect(Collectors.toList());
list.removeAll(toRemove);
```

### 3.4 fail-fast 机制

```java
// ⚠️ fail-fast 不保证一定触发
List<String> list = new ArrayList<>(Arrays.asList("A", "B", "C"));

// 单元素删除：运气好不抛异常？
list.remove("A"); // 直接 List.remove(Object)
for (String s : list) {
    System.out.println(s); // 正常输出 "B" "C"
}
// 原因：remove 在迭代开始前调用，不会触发检查
```

> `ConcurrentModificationException` 只是**错误检测机制**，不是**并发安全保证**。它基于 `modCount` 检查，但**不保证一定会抛出**。

```java
// ⚠️ 更隐蔽——只删除倒数第二个元素可能不抛异常
List<String> list = new ArrayList<>(Arrays.asList("A", "B", "C"));
for (String s : list) {
    if (s.equals("B")) {
        list.remove(s); // 不抛异常？！
        // 原因："B" 是倒数第二个，删除后 size--
        // it.hasNext() 检查 hasNext 时恰好相等
    }
}
```

解释：删除 "B" 后 size 从 3 变为 2，此时 `cursor == size`，`it.hasNext()` 返回 false → 循环结束，没有触发下一次 `next()` 的 `checkForComodification()`。

> ⚠️ **不要依赖这类行为**——这属于具体实现细节，不同 JDK 版本可能不同。

### 3.5 增强 for 的局限性

| 场景 | 增强 for | 普通 for | Iterator |
|:---:|:--------:|:--------:|:--------:|
| 遍历时删除元素 | ❌ 不可 | ❌ 不可（index 偏移） | ✅ `it.remove()` |
| 遍历时修改元素 | ❌ 不可 | ✅ `arr[i]=x` | ❌ 不可 |
| 反向遍历 | ❌ 不可 | ✅ `i--` | ❌ 不可 |
| 步长控制 | ❌ 不可 | ✅ `i+=2` | ❌ 不可 |
| 获取当前索引 | ❌ 不可 | ✅ `i` | ❌ 不可 |

> 🎯 **核心要点**：
> 1. 数组类型 → 编译为普通 for 循环（下标访问）
> 2. Iterable 类型 → 编译为 Iterator 循环（`iterator()` + `hasNext()` + `next()`）
> 3. 增强 for **遍历过程中不能修改集合结构**（add / remove），否则抛 `ConcurrentModificationException`（fail-fast）
> 4. 正确删除方式：`Iterator.remove()` 或 `Collection.removeIf()`
> 5. fail-fast 不保证一定触发，不要依赖它做并发控制

## 4. 可变参数 varargs

### 4.1 基本用法

```java
// 源代码
public static void printAll(String... args) {
    for (String arg : args) {
        System.out.println(arg);
    }
}

printAll("A", "B", "C");
printAll(); // 可不传参数 → 空数组
```

### 4.2 编译原理

```java
// 解糖后：可变参数编译为数组参数
public static void printAll(String[] args) {
    for (String arg : args) {
        System.out.println(arg);
    }
}
```

**调用处的编译行为：**

```java
// printAll("A", "B", "C"); → 编译器生成数组创建
printAll(new String[]{"A", "B", "C"});

// printAll(); → 空数组
printAll(new String[0]);
```

**字节码：**

```text
; 调用 printAll("A", "B", "C")
 0: iconst_3              ; 数组长度 3
 1: anewarray #2          ; 创建 String[] 数组
 4: dup
 5: iconst_0
 6: ldc           #3      ; String "A"
 8: aastore               ; 存入数组[0]
 9: dup
10: iconst_1
11: ldc           #4      ; String "B"
13: aastore               ; 存入数组[1]
14: dup
15: iconst_2
16: ldc           #5      ; String "C"
18: aastore               ; 存入数组[2]
19: invokestatic  #6      ; printAll([String)
```

### 4.3 重载歧义

```java
// ❌ 歧义问题
public static void method(int... nums) {}
public static void method(int[] nums) {} // ⚠️ 编译错误：与 varargs 方法冲突

// 方法签名相同：method([I)V
```

> 可变参数在字节码层面就是数组参数，所以**不能同时定义参数类型相同的可变参数版本和数组版本**。

### 4.4 重载选择规则

```java
public class VarargsOverload {
    public static void foo(int i) { System.out.println("exact match"); }
    public static void foo(int... i) { System.out.println("varargs"); }

    public static void main(String[] args) {
        foo(42);    // 输出 "exact match"——精确匹配优先于可变参数
        foo(1, 2);  // 输出 "varargs"——必须可变参数
        foo();      // 输出 "varargs"——空参数调用可变参数
    }
}
```

> **选择规则**：固定参数 > 自动装箱 > 可变参数。Java 编译器在重载解析时，可变参数的优先级是最低的。

### 4.5 堆污染（Heap Pollution）与 @SafeVarargs

```java
// ⚠️ 堆污染
@SuppressWarnings("unchecked")
public static <T> void addToList(List<T>... lists) {
    // 编译后：List<T>... → List[]（数组协变 + 泛型擦除）

    Object[] objArray = lists;        // 数组是协变的
    objArray[0] = Arrays.asList(1, 2); // 存 List<Integer> → 合法（类型擦除）

    String s = (String) lists[0].get(0); // ❌ 运行期 ClassCastException
    // 编译期无法检测到类型错误
}
```

**@SafeVarargs 注解：**

```java
// ✅ 安全可变参数——使用 @SafeVarargs 抑制警告
@SafeVarargs
public static <T> List<T> merge(List<T>... lists) {
    // 前提：方法内部不修改 lists 数组内容
    List<T> result = new ArrayList<>();
    for (List<T> list : lists) {
        result.addAll(list);
    }
    return result;
}
```

> `@SafeVarargs` 可应用在：final 方法、static 方法、private 方法（Java 9+ 允许 private）。

### 4.6 面试追问

| 追问 | 解答 |
|------|------|
| 可变参数能不能为 null？ | 可以，传入 `obj.method(null)` → 传入参数即 null，不是空数组 |
| 可变参数和数组重载的区别？ | 字节码层面没区别，但源码层面不能同时存在同类型重载 |
| 可变参数方法调用时一定创建数组吗？ | 不一定，0 参数时创建空数组（`new Object[0]`）；单参数也可能复用空数组常量 |
| `void foo(T... args)` 在运行时 T 是什么？ | 擦除为 `Object[]` |

> 🎯 **核心要点**：
> 1. 可变参数编译为数组参数——调用处自动创建数组
> 2. **不能**与同类型数组参数方法重载
> 3. 重载选择：固定参数 > 装箱 > 可变参数（可变参数优先级最低）
> 4. 泛型可变参数存在堆污染风险，方法内部不修改数组时用 `@SafeVarargs`

## 5. 枚举 enum

### 5.1 枚举的本质

```java
// 源代码——枚举定义
public enum Color {
    RED, GREEN, BLUE;
}
```

**解糖后等价于：**

```java
// 编译器自动生成的 final class（不能手动编写）
public final class Color extends java.lang.Enum<Color> {
    // 枚举常量 → 静态 final 实例
    public static final Color RED = new Color("RED", 0);
    public static final Color GREEN = new Color("GREEN", 1);
    public static final Color BLUE = new Color("BLUE", 2);

    // 私有构造器
    private Color(String name, int ordinal) {
        super(name, ordinal);
    }

    // 编译器自动生成——静态字段存放所有枚举值
    private static final Color[] $VALUES = {RED, GREEN, BLUE};

    // 编译器自动生成——values() 方法
    public static Color[] values() {
        return $VALUES.clone(); // 返回克隆数组，避免外部修改
    }

    // 编译器自动生成——valueOf() 方法
    public static Color valueOf(String name) {
        return Enum.valueOf(Color.class, name);
    }
}
```

**字节码验证：**

```text
 0: class                #2   // class Color
 3: extends              #37  // java.lang.Enum
 6: final                // ← final class

; 静态块初始化枚举常量
 0: new             #2   // class Color
 3: dup
 4: ldc             #3   // String "RED"
 6: iconst_0             // ordinal 0
 7: invokespecial   #4   // Color."<init>":(String;I)V
10: putstatic       #5   // RED

; values() 方法
 0: getstatic       #7   // $VALUES
 3: invokevirtual   #8   // [Color.clone():Object
 6: checkcast       #9   // 转型 Color[]
 9: areturn
```

### 5.2 enum 单例模式——绝对防反射

```java
// 最佳单例实现——枚举单例
public enum Singleton {
    INSTANCE; // 唯一的实例

    public void doSomething() {
        // 业务逻辑
    }
}

// 使用
Singleton.INSTANCE.doSomething();
```

**为什么枚举单例是完美的？**

| 攻击方式 | 枚举防护机制 |
|---------|------------|
| 反射 `newInstance()` | `Constructor.newInstance()` 禁止对枚举类调用（源码层面抛出 `IllegalArgumentException`） |
| 序列化/反序列化 | 枚举的序列化由 JVM 保证，反序列化返回同一实例（不是通过反射创建） |
| 克隆 | `Enum` 的 `clone()` 是 final 的，抛出 `CloneNotSupportedException` |
| 多线程 | JVM 保证枚举常量的初始化是线程安全的 |

```java
// 验证反射无法创建枚举实例
Constructor<Color> constructor = Color.class.getDeclaredConstructor(String.class, int.class);
constructor.setAccessible(true);
Color color = constructor.newInstance("YELLOW", 3);
// ❌ 抛出：java.lang.IllegalArgumentException: Cannot reflectively create enum objects
```

### 5.3 为枚举添加字段和方法

```java
public enum Operation {
    PLUS("+") {
        @Override
        public double apply(double x, double y) { return x + y; }
    },
    MINUS("-") {
        @Override
        public double apply(double x, double y) { return x - y; }
    },
    TIMES("*") {
        @Override
        public double apply(double x, double y) { return x * y; }
    },
    DIVIDE("/") {
        @Override
        public double apply(double x, double y) { return x / y; }
    };

    private final String symbol; // 字段

    Operation(String symbol) {   // 构造器
        this.symbol = symbol;
    }

    public String getSymbol() { return symbol; }

    public abstract double apply(double x, double y); // 抽象方法
}

// 使用
double result = Operation.PLUS.apply(3, 4); // 7.0
```

### 5.4 EnumSet 和 EnumMap——极致性能

```java
// EnumSet——基于位向量的高性能 Set
public enum Weekday { MON, TUE, WED, THU, FRI, SAT, SUN }

EnumSet<Weekday> workdays = EnumSet.range(Weekday.MON, Weekday.FRI);
EnumSet<Weekday> weekend = EnumSet.of(Weekday.SAT, Weekday.SUN);

// 内部实现：RegularEnumSet 使用 long 类型位向量
// 每个枚举常量对应一个 bit 位（最大 64 个枚举值）
// 操作都是位运算，比 HashSet 快得多
```

```java
// EnumMap——基于数组的高性能 Map
EnumMap<Weekday, String> schedule = new EnumMap<>(Weekday.class);
schedule.put(Weekday.MON, "开会");
schedule.put(Weekday.FRI, "复盘");

// 内部实现：Object[] 数组，索引 = ordinal()
// 不需要 hashCode，直接数组访问 O(1)
```

**性能对比：**

| 实现 | 内部结构 | contains 复杂度 | 内存占用 |
|:---:|:--------:|:--------------:|:--------:|
| `EnumSet` | long 位向量 | O(1) 位运算 | ~8 bytes |
| `HashSet<Enum>` | 哈希表 | O(1) 平均 | 数百 bytes |
| `EnumMap` | Object[] | O(1) 数组访问 | ~枚举数 × 引用 |
| `HashMap<Enum,V>` | 哈希表 | O(1) 平均 | 更大 |

> 💡 **枚举常量 ≤ 64 个时，EnumSet 使用 RegularEnumSet（long 位向量）；超过 64 个使用 JumboEnumSet（long[]）**。

### 5.5 values() 和 valueOf() 的编译器生成

```java
// values() 返回的是克隆数组
Color[] colors = Color.values();
colors[0] = null; // 不会影响 Color.RED

// valueOf() 如果找不到则抛 IllegalArgumentException
Color c = Color.valueOf("YELLOW"); // ❌ IllegalArgumentException
// 而不是返回 null！
```

```java
// 安全获取枚举常量
public static Color safeValueOf(String name) {
    try {
        return Color.valueOf(name);
    } catch (IllegalArgumentException e) {
        return null; // 或默认值
    }
}
```

### 面试追问合集

| 追问 | 解答 |
|------|------|
| 枚举的构造器一定是 private 吗？ | 是，JVM 强制私有。不能显式创建 enum 实例 |
| 枚举可以继承其他类吗？ | 不能，因为隐式继承了 `java.lang.Enum`（Java 单继承）|
| 枚举可以实现接口吗？ | 可以，enum 可以实现一个或多个接口 |
| `values()` 方法定义在哪？ | 编译器在生成的 enum 类中自动添加的静态方法，不在 `Enum` 基类中 |
| 枚举的 `ordinal()` 能用于版本兼容吗？ | ❌ 不能！如果枚举常量顺序改变，ordinal 值也会变。应用自定义字段替代 |
| 枚举可以用 `==` 比较吗？ | ✅ 可以，因为每个枚举常量是单例对象，`==` 和 `equals()` 结果相同 |

> 🎯 **核心要点**：
> 1. 枚举本质是 `final class extends Enum`——编译器自动生成 `values()` / `valueOf()`
> 2. 枚举单例是**最安全的单例实现**——反射、序列化、克隆都无法破坏
> 3. `EnumSet` 基于位向量（long），`EnumMap` 基于数组——性能远超普通 Set/Map
> 4. 不要依赖 `ordinal()`——用自定义字段替代

## 6. try-with-resources

### 6.1 基本用法

```java
// 源代码——try-with-resources
try (BufferedReader br = new BufferedReader(new FileReader("test.txt"))) {
    return br.readLine();
}
```

### 6.2 编译解糖原理

**解糖后等价于：**

```java
// 解糖后的代码
BufferedReader br = new BufferedReader(new FileReader("test.txt"));
Throwable primaryException = null;
try {
    return br.readLine();
} catch (Throwable e) {
    primaryException = e;
    throw e;
} finally {
    if (br != null) {
        if (primaryException != null) {
            try {
                br.close();
            } catch (Throwable suppressed) {
                primaryException.addSuppressed(suppressed); // 抑制异常
            }
        } else {
            br.close();
        }
    }
}
```

**多资源时（释放顺序 LIFO——后进先出）：**

```java
// 源代码
try (FileInputStream fis = new FileInputStream("in.txt");
     FileOutputStream fos = new FileOutputStream("out.txt")) {
    // 使用 fis 和 fos
}

// 解糖后——fos 先 close，fis 后 close（后声明先释放）
// 因为 close 在 finally 中按声明反向顺序调用
```

### 6.3 Suppressed Exception 机制

在普通 try-finally 中，如果 try 块抛异常的同时 finally 也抛异常，**finally 的异常会覆盖 try 块的原始异常**——这是常见的异常丢失问题。

```java
// ❌ 普通 try-finally 的异常丢失问题
public static String oldWay() throws Exception {
    BufferedReader br = new BufferedReader(new FileReader("test.txt"));
    try {
        throw new RuntimeException("业务异常"); // 原始异常
    } finally {
        br.close(); // 这里如果抛异常，会覆盖上面的！
        // 调用者只看到 "Stream closed" 等，看不到 "业务异常"
    }
}
```

**try-with-resources 通过 Suppressed Exception 解决：**

```java
// try-with-resources 会自动保存所有异常
try (BufferedReader br = new BufferedReader(new FileReader("test.txt"))) {
    throw new RuntimeException("业务异常");
}

// 调用者捕获时：
try {
    oldWay();
} catch (Exception e) {
    System.out.println(e.getMessage());       // "业务异常"——主异常
    Throwable[] suppressed = e.getSuppressed();
    for (Throwable se : suppressed) {
        System.out.println(se.getMessage());  // "Stream closed"——被抑制的异常
    }
}
```

### 6.4 AutoCloseable 与 Closeable

```java
// AutoCloseable（Java 7 引入）——最顶层接口
public interface AutoCloseable {
    void close() throws Exception; // 可抛任何异常
}

// Closeable——继承 AutoCloseable，用于 IO 资源
public interface Closeable extends AutoCloseable {
    void close() throws IOException; // 更具体的异常类型
}
```

| 接口 | 版本 | close() 异常 | 幂等性 | 适用场景 |
|:----:|:----:|:----------:|:-----:|:--------:|
| `AutoCloseable` | Java 7 | `throws Exception` | 未要求 | 所有可关闭资源 |
| `Closeable` | Java 5 | `throws IOException` | 要求幂等（多次调用无害） | IO 流、网络连接 |

```java
// 自定义资源：实现 AutoCloseable
public class MyResource implements AutoCloseable {
    private final String name;
    private boolean closed = false;

    public MyResource(String name) { this.name = name; }

    public void doWork() {
        if (closed) throw new IllegalStateException("已关闭");
        System.out.println(name + " 正在工作");
    }

    @Override
    public void close() throws Exception {
        if (!closed) {
            closed = true;
            System.out.println(name + " 已关闭");
        }
    }
}

// 使用
try (MyResource r1 = new MyResource("资源1");
     MyResource r2 = new MyResource("资源2")) {
    r1.doWork();
    r2.doWork();
}
// 输出：
// 资源1 正在工作
// 资源2 正在工作
// 资源2 已关闭    ← LIFO 释放顺序
// 资源1 已关闭
```

### 6.5 Java 9 的增强：已有效 final 变量

```java
// Java 7~8：资源必须在 try() 中声明
try (BufferedReader br = new BufferedReader(...)) { ... }

// Java 9+：可以使用已有效 final 的变量
BufferedReader br = new BufferedReader(...);
// ... 其他代码（不能修改 br 引用）
try (br) { // ✅ 直接使用已声明的变量
    return br.readLine();
}
// br 在 try 之后仍然有效，但 try 块结束时会自动关闭
```

> 原理：Java 9 编译器识别出在 try() 中使用的变量，在 finally 块中添加 close() 调用。

### 面试追问合集

| 追问 | 解答 |
|------|------|
| try 和 finally 都抛异常怎么办？ | 普通 try-finally 会丢失 try 的异常；try-with-resources 用 Suppressed Exception 保存所有异常 |
| 如何获取被抑制的异常？ | `Throwable.getSuppressed()` |
| 多个资源的关闭顺序？ | LIFO（后声明的先关闭） |
| try-with-resources 可以 catch 吗？ | 可以，`try (...) { } catch (XxxException e) { }` |
| AutoCloseable 和 Closeable 选哪个？ | IO 资源用 Closeable（throws IOException），自定义资源用 AutoCloseable |

> 🎯 **核心要点**：
> 1. try-with-resources 解糖为 try-finally + close() + Suppressed Exception 机制
> 2. **解决了普通 try-finally 的异常丢失问题**——所有异常都被记录
> 3. 多资源释放顺序：**LIFO**（后声明先释放）
> 4. Java 9+ 支持已有效 final 变量放入 try() 中

## 7. 钻石操作符 <>

### 7.1 基本用法

```java
// 源代码——省略泛型参数
List<String> list = new ArrayList<>(); // 编译器推断为 ArrayList<String>
```

**解糖后：**

```java
List<String> list = new ArrayList<String>();
```

### 7.2 类型推断原理

```java
// 钻石操作符的推断规则
Map<String, List<Integer>> map = new HashMap<>();
// 编译器根据左侧变量声明类型推断右侧类型参数
// 等价于：new HashMap<String, List<Integer>>()
```

```java
// 方法调用时也可以推断
public static <T> List<T> emptyList() {
    return new ArrayList<>(); // 编译器根据返回类型 T 推断
}

List<String> list = emptyList(); // T = String
```

### 7.3 匿名内部类的限制

```java
// ✅ 普通类——可以使用 <>
List<String> list1 = new ArrayList<>();

// ❌ 匿名内部类——Java 7~8 中不能使用 <>
List<String> list2 = new ArrayList<>() {
    // 匿名内部类
    // ❌ 编译错误：Cannot use "<>" with anonymous inner classes
};

// ✅ Java 9+ 匿名内部类支持 <>
List<String> list3 = new ArrayList<>() {
    // 匿名内部类——Java 9+ 允许
    @Override
    public String toString() {
        return "custom list: " + super.toString();
    }
};
```

> 原因：Java 7 引入钻石操作符时，匿名内部类的类型推断存在技术困难。Java 9 通过改进类型推断算法解决了这个问题。

### 7.4 与原始类型（Raw Type）的区别

```java
// ⚠️ 原始类型——不使用泛型
List list1 = new ArrayList();    // Raw Type——编译器警告
list1.add("hello");
list1.add(123);                  // 可添加任意类型——不安全

// ✅ 钻石操作符——完整类型安全
List<String> list2 = new ArrayList<>();
list2.add("hello");
list2.add(123);                  // ❌ 编译错误——类型安全
```

### 面试追问合集

| 追问 | 解答 |
|------|------|
| `new ArrayList<>()` 和 `new ArrayList()` 的区别？ | 前者类型安全（类型推断），后者是 raw type（编译器警告） |
| 匿名内部类 Java 9 才支持 <>？ | 是的，Java 9 开始改了类型推断规则 |
| 钻石操作符是否在运行期执行？ | 不，纯编译期语法糖 |

> 🎯 **核心要点**：
> 1. 钻石操作符是编译期类型推断，解糖后替换为完整泛型参数
> 2. 匿名内部类 Java 7~8 不支持 `<>`，Java 9+ 支持
> 3. 永远用 `new ArrayList<>()` 而不是 raw type `new ArrayList()`

## 8. switch 支持 String

### 8.1 基本用法

```java
// 源代码
public static String getType(String fruit) {
    switch (fruit) {
        case "apple":  return "水果";
        case "carrot": return "蔬菜";
        default:       return "未知";
    }
}
```

### 8.2 编译原理：hashCode + equals

Java 7 之前，switch 只支持 `int`（包括 byte/short/char/enum）。switch String 是编译器实现的语法糖。

**解糖后等价于：**

```java
// Java 7~16 的等价实现
public static String getType(String fruit) {
    String s = fruit;
    int code;

    if (s == null) {
        throw new NullPointerException(); // ← switch String 不能为 null！
    }

    // 第一层：switch hashCode
    switch (s.hashCode()) {
        case 93029264: // "apple".hashCode()
            if (s.equals("apple")) return "水果"; // 二次校验
            break;
        case -331436490: // "carrot".hashCode()
            if (s.equals("carrot")) return "蔬菜";
            break;
    }
    return "未知";
}
```

**关键点：双层校验**

1. 先计算 `hashCode()`，用 switch-int 快速定位
2. 再用 `equals()` 确认——因为不同字符串可能有相同 hashCode（哈希碰撞）

```java
// ⚠️ 哈希碰撞示例——不同字符串相同 hashCode
String s1 = "Aa";  // hashCode = 2112
String s2 = "BB";  // hashCode = 2112
System.out.println(s1.hashCode() == s2.hashCode()); // true — 哈希碰撞
```

> 编译器之所以要两层校验（hashCode + equals），就是为了处理哈希碰撞。只靠 hashCode 无法唯一确定字符串。

### 8.3 switch String 的 null 问题

```java
// ⚠️ 经典 NPE 陷阱
String s = null;
switch (s) {
    case "A":
        System.out.println("A");
        break;
}
// ❌ NullPointerException！因为会调用 s.hashCode()
```

**为什么会抛 NPE？** 从解糖后的代码可以看到，`s.hashCode()` 在 switch 开始时就被调用，null 调用 hashCode() → NPE。

**Java 17+ 的改进：** 从 Java 17 开始，switch 语句的预览特性（JEP 406）开始支持 null 分支：

```java
// Java 17+ 预览特性（Java 21 正式）——switch 可以匹配 null
String s = null;
switch (s) {
    case null -> System.out.println("null 值");
    case "A"  -> System.out.println("A");
    default   -> System.out.println("其他");
}
// 输出：null 值
```

### 8.4 switch String 的性能分析

```java
// 少量 case → 编译为 lookupswitch（顺序查找）
public static void few(String s) {
    switch (s) {
        case "A": break;
        case "B": break;
        default: break;
    }
}
```

```text
; 少量 case → lookupswitch
 0: aload_0
 1: invokevirtual #2  // String.hashCode()
 4: lookupswitch      // 顺序查找
     65: 36   // "A".hashCode()
     66: 50   // "B".hashCode()
```

```java
// 大量 case → 编译为 tableswitch（跳转表）
public static void many(String s) {
    switch (s) {
        case "A": case "B": case "C": case "D":
        case "E": case "F": case "G": // ...
            break;
    }
}
```

```text
; 大量 case（密集） → tableswitch
 0: aload_0
 1: invokevirtual #2  // String.hashCode()
 4: tableswitch       // 跳转表 O(1) 访问
```

| switch 类型 | 复杂度 | 适用场景 |
|:----------:|:-----:|:--------:|
| `tableswitch` | O(1) | case 值密集连续 |
| `lookupswitch` | O(log n) | case 值稀疏不连续 |

> 注：String 的 case 经过 hashCode 映射后，不一定能形成密集的 tableswitch，实际编译器策略取决于具体值。

### 8.5 switch String vs switch enum

```java
// 🔸 switch String
String fruit = "apple";
switch (fruit) {
    case "apple": ...
    case "carrot": ...
}

// 🔸 switch enum——更好的选择
enum Fruit { APPLE, CARROT }
Fruit fruit = Fruit.APPLE;
switch (fruit) {
    case APPLE: ...
    case CARROT: ...
}
```

| 对比维度 | switch String | switch enum |
|:--------:|:------------:|:-----------:|
| 编译后指令 | hashCode + equals + tableswitch/lookupswitch | tableswitch（直接使用 ordinal） |
| 性能 | 间接（hash + equals） | 直接（ordinal 值） |
| null 安全 | NPE（除非 Java 17+ null case） | NPE |
| 类型安全 | ❌ 拼写无检查 | ✅ 编译器保证 |
| 扩展性 | 增加 case 无约束 | 增加枚举值可穷举检查 |

> 当 case 值有明确枚举含义时，**优先使用 enum 而非 String**。

### 面试追问合集

| 追问 | 解答 |
|------|------|
| switch String 一定比 switch int 慢吗？ | 不一定。JVM 做两层 switch（hashCode 外层 + equals 内层），有额外开销 |
| switch String 和 if-else 链哪个快？ | 大量 case 时 switch 快（跳转表）；少量 case 时差异不大 |
| switch String 会调用 equals 多少次？ | 每个候选 case 最多一次 equals（hashCode 定位到候选后再 equals 确认） |
| switch(String) 的 case 能不能有重复？ | 不能，检查点在不同 hashCode 或相同 hashCode + equals |

> 🎯 **核心要点**：
> 1. switch String 解糖为：`hashCode()` → `tableswitch`/`lookupswitch` → `equals()` 二次校验（处理哈希碰撞）
> 2. switch String 传入 null → 抛 **NullPointerException**（因为调用 hashCode()）
> 3. Java 17+ 支持 `case null`（Java 21 正式）
> 4. 有枚举含义的场景，**用 enum 代替 String** 做 switch 更高效安全
