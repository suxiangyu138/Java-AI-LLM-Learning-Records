## 2. 系统性调试：50% 时间的胜负手

### 2.1 为什么调试是核心技能

> 📊 程序员约一半时间在调试——**调试效率直接决定开发效率**。普通程序员「乱试」，顶级工程师「系统定位」。

### 2.2 调试三大黄金习惯

| # | 习惯 | 说明 |
|---|------|------|
| 1 | **记录复现步骤** | 复现不了 = 修不了 = 验证不了 |
| 2 | **假设-验证-结论** | 每个动作都基于假设（不是瞎试） |
| 3 | **一次只改一个变量** | 多变量同改 = 无法归因 |

### 2.3 二分法定位

```text
二分法调试（1000 行代码 5 次内定位）
├── ① 确定问题范围（错误在哪一段/哪一层）
├── ② 二分：中间加日志/断点 → 问题在前半段还是后半段？
├── ③ 递归缩小（每次砍一半）
├── ④ 5 次内定位到行级
└── 对比：顺序排查 1000 行 vs 二分 10 次左右
```

### 2.4 调试流程化

```text
精英调试流程
├── ① 复现：稳定复现 + 记录输入/环境/操作序列
├── ② 假设：列出所有可能原因（排序）
├── ③ 验证：一次验证一个假设（最小实验）
├── ④ 定位：二分法收敛到根因
├── ⑤ 修复：最小改动 + 补测试
└── ⑥ 复盘：为什么没被测试发现 → 补盲区
→ 金句：调试不是找 bug，是验证假设的科学实验
```

## 3. 读码能力：考古的艺术

### 3.1 为什么读码是硬技能

> 💡 **代码写出来只用一次，但会被阅读一百次**——精英工程师的读码速度，就是团队的认知速度。

### 3.2 读码三件套

```text
读码考古三件套
├── ① git blame：看每一行的作者 + 提交信息
│   └── 提交信息 = 当时的「为什么」（团队知识资产）
├── ② 调用链追踪：从入口 → 出口（IDE 跳转 + 断点）
│   └── 理解数据流向，而非孤立看函数
└── ③ 单测双重验证：跑测试理解行为契约
    └── 测试 = 代码行为的可执行文档
```

### 3.3 读码的顺序

```text
读一段陌生代码的顺序（精英习惯）
├── ① 先读测试：它承诺了什么行为？（最快理解）
├── ② 再读接口：入参/出参/异常（契约）
├── ③ 后读实现：数据流向 + 关键分支
├── ④ 最后考古：git blame 看演进历史
└── ⑤ 记录：发现的设计决策记入笔记（知识沉淀）
→ 顺序决定效率：从「行为的承诺」到「行为的实现」
```

## 4. 安全重构：小步与验证

### 4.1 三阶段法

> 🎯 **安全重构三阶段**：识别坏味道 → 小步前进 → 验证安全——追求「人类能理解的代码」。

```text
安全重构流程
├── ① 识别坏味道：重复/长函数/魔法数字/散弹式修改
├── ② 小步前进：一次一个重构（提取/改名/拆分）
├── ③ 验证安全：每步后跑测试（全绿才下一步）
└── 铁律：重构不改变行为——测试全绿 = 重构成功的证据
```

### 4.2 重构的优先级

```text
重构优先级（ROI 排序）
├── P0：删除注释掉的代码 / 魔法数字 → 常量（零风险）
├── P1：提取重复逻辑（三处以上）
├── P2：长函数拆分（有测试保护）
└── P3：架构级重构（需专项排期）
→ 金句：最好的代码是你从不必写的代码——重构是让代码「少」的艺术
```

## 5. 技术翻译：商业语言

### 5.1 翻译公式

> 🎯 **技术翻译公式**：把技术语言翻译成商业语言——**「工期 + 影响」**（详见《程序员的好习惯》03 篇，此处聚焦博弈价值）：

```text
翻译的价值（博弈视角）
├── ❌ 技术语言：「要改 3 层架构，涉及 20 个服务……」
│   → 商业方：听不懂 = 不信任 = 无法决策
├── ✅ 商业语言：「需要两周，上线后搜索速度提升 3 倍」
│   → 商业方：听得懂 = 能决策 = 认可价值
└── 本质：技术翻译 = 把「技术成本」翻译成「业务收益」——
    让决策者能用商业逻辑支持你的技术方案
```

### 5.2 翻译能力进阶

```text
翻译能力三级
├── L1 说结论：工期 + 影响（最基本）
├── L2 说取舍：方案 A/B 的代价与收益（决策支持）
└── L3 说价值：技术投入 → 业务指标（算账思维，见 01 篇）
→ 精英的标志：业务方愿意找你讨论技术方案的商业影响
```

## 6. 诚实估算：信任的基石

### 6.1 估算的博弈本质

> 🎯 估算是程序员最被低估的能力——**诚实估算 = 信任的基石**：估不准会透支信任，报虚高会失去机会。

### 6.2 估算工具箱

| 工具 | 说明 | 适用 |
|------|------|------|
| **估算锥** | 项目越早期估算误差越大（早期 ±4 倍，后期 ±0.25） | 认知校准 |
| **T 恤尺码法** | S/M/L/XL 相对范围（不承诺绝对天数） | 早期粗估 |
| **三点估算** | (乐观 + 4×最可能 + 悲观) / 6 | 中期细估 |
| **拆解估算** | 拆到任务级逐个估（误差相互抵消） | 交付前 |

### 6.3 诚实估算的话术

```text
诚实估算公式 = 数值 + 依据 + 波动范围
├── ❌ 「两周吧」（随口 → 超期 → 信任受损）
├── ✅ 「两周（拆解：API 3 天 + 状态 3 天 + 失败 2 天 + 测试 2 天
│    + 文档 1 天 + 缓冲 3 天），这是最可能值，
│    上下可能有 50% 波动，主要风险是联调环境」
└── 效果：即使超期，对方有预期 → 信任不崩
→ 金句：诚实是最好的策略——估算的波动不可消除，但可被预知
```

## 7. 优雅拒绝：边界的力量

### 7.1 拒绝的博弈价值

> 🎯 **一个清晰的「不」，比一个模糊的「可能吧」更有价值**——模糊承诺 = 双方都以为对方负责 = 双输；清晰拒绝 = 重新对齐 = 双赢。

### 7.2 拒绝公式

```text
拒绝公式 = 先说结论 + 诚实原因 + 替代方案 + 约定时间
├── ① 结论：「这个需求这周排不了」
├── ② 原因：「手上有两个已承诺上线任务」
├── ③ 替代：「可放下周；或需要这周则须暂停其一」
└── ④ 约定：「你确认优先级后我马上调整」
→ 效果：诚实 + 建设性 + 把决策权交还对方（详见《好习惯》03 篇）
```

### 7.3 拒绝的进阶：拒绝「坏工程」而非「任务」

```text
精英的拒绝对象（比拒绝任务更高一层）
├── 拒绝无测试的合并（质量底线）
├── 拒绝不合理的工期承诺（诚信底线）
├── 拒绝破坏架构的临时方案（工程底线）
└── 拒绝方式：不是「不行」，是「可以，但需要 xx 前提」
→ 精英的拒绝 = 对质量负责，而非对人不配合
```

## 8. 建设性评审：从批评者到导师

### 8.1 Google 评审法则

> 🎯 建设性评审：从「批评者」升级为「导师」——**评审的目的不是证明代码有错，而是帮助代码变得更好**。

### 8.2 评审三原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **对事不对人** | 批评代码不批评作者（「这段逻辑的风险是…」非「你写得…」） |
| 2 | **一次 ≤3 条核心建议** | 建议太多 = 没重点 = 都没被采纳 |
| 3 | **「我建议」而非「你必须」** | 语气决定接受度（建议式 > 命令式） |

### 8.3 评审的导师心态

```text
评审作为导师的三层
├── L1 指出问题：这里有空指针风险（发现错误）
├── L2 解释原因：为什么是风险 + 什么场景触发（传授知识）
└── L3 引导思考：这个风险你觉得怎么处理最好？
    → 让被审者自己得出结论（培养能力）
→ 精英评审的效果：被审者不仅改了代码，还学会了判断
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 七项核心软技能覆盖程序员 90% 的非编码时间：调试（50%）+ 读码（40%）是主战场
> 2. 系统性调试三黄金习惯（复现/假设验证/一次一变量）+ 二分法——调试是科学实验
> 3. 读码三件套（git blame/调用链/单测验证）——先读测试后读实现
> 4. 诚实估算（数值+依据+波动）+ 优雅拒绝（结论+原因+替代+约定）+ 建设性评审（导师式）——三项都是信任资产
