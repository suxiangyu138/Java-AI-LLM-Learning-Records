# 05 - Maven 与 Gradle 选型对比

> **核心摘要**：2026 的 Java 构建选型不再「Maven 老 / Gradle 新」二元对立——Maven 4 重构后差距收窄，Gradle 9 性能依旧领先。真正的决策变量是：**团队熟悉度、构建规模、可编程性需求、生态依赖**。本文给出完整对比框架 + 决策流程 + 迁移策略。

## 1. 2026 选型格局

> **背景**：过去十年「Gradle 取代 Maven」的叙事正在被 Maven 4 改写——2025.10 起的重构让 Maven 重新进入竞争。
> **目的**：建立客观的选型决策框架，不跟风、不守旧。
> **适用范围**：技术负责人/架构师做构建工具选型时。

```text
2026 三方格局
├── Maven 3（存量主力）
│   ├── 仍在维护（至 2026.12 后进入过渡）
│   └── 大量存量项目：等 Maven 4 GA 后升级
├── Maven 4（rc-5 阶段）
│   ├── 重构完成度已高：Consumer POM / 并发构建 / POM 4.1.0
│   └── 生产采纳度：等 GA + 生态插件适配
├── Gradle 9.3（2026.06）
│   ├── 性能与工程化成熟
│   └── Android/Spring 新项目主流
└── 金句：没有「最优」，只有「最适合」——三个变量：团队/规模/生态
```

## 2. 全维度对比表

| 维度 | Maven 4 | Gradle 9 | 胜负手 |
|------|---------|----------|--------|
| **核心模型** | 声明式（POM 数据） | 编程式（Task 图代码） | 看团队习惯 |
| **学习曲线** | 低（XML 声明即可） | 中高（DSL + 两阶段心智） | Maven 胜 |
| **多模块构建** | 树形 + `-b concurrent` | 并行（Task 级粒度） | Gradle 略胜 |
| **增量构建** | ⚠️ 起步 | ✅ 成熟（UP-TO-DATE） | Gradle 胜 |
| **构建缓存** | ⚠️ 起步 | ✅ 本地+远程成熟 | Gradle 胜 |
| **配置语法** | XML（IDE 补全好） | Kotlin/Groovy DSL | 平手 |
| **类型安全** | XML 无编译期检查 | Kotlin DSL 编译期检查 | Gradle 胜 |
| **可编程性** | 插件开发（重） | 脚本即代码（轻） | Gradle 胜 |
| **依赖管理** | 就近裁决 + BOM | 最高版本 + Catalog | 平手 |
| **生态兼容** | ✅ Consumer POM 更兼容 | ✅ Maven 依赖直接拉 | 平手 |
| **中央仓库集成** | ✅ 原生 | ✅ 原生 | 平手 |
| **版本现状** | rc-5（未 GA） | 9.3 GA（稳定） | Gradle 胜 |
| **IDE 支持** | IDEA 2026.1 完善 | IDEA 2026.1 全面 | 平手 |
| **Android 支持** | ❌ | ✅ 官方唯一 | Gradle 胜 |
| **Spring 官方** | ✅ 全支持 | ✅ 全支持 | 平手 |

**一句话总结**：

```text
Gradle 赢在：性能（增量/缓存）+ 可编程性 + Android
Maven 赢在：简单（声明式）+ 生态存量 + 上手成本
平手：依赖管理能力、仓库生态、IDE 支持
```

## 3. 性能对比实测

> 🎯 **性能差距的核心来源**：增量粒度 + 缓存能力，而非「谁更快启动」：

```text
性能分层（多模块大项目）
├── 冷构建（无缓存首次）：
│   ├── Gradle：并行 + 缓存预热 → 通常快 2-4 倍
│   └── Maven 4：树形并发（-b concurrent）→ 差距收窄
├── 增量构建（改一行代码）：
│   ├── Gradle：UP-TO-DATE 跳过 → 秒级
│   └── Maven 4：树形避免冗余 → 仍有明显差距
├── 跨机器复用：
│   ├── Gradle：远程缓存 → CI 与本地共享产物
│   └── Maven 4：起步阶段（Consumer POM 加速解析，但无产物缓存）
└── 结论：构建越频繁、模块越多 → Gradle 优势越大

真实世界参考（社区反馈汇总）
├── 10+ 模块中型项目：Gradle 增量构建 3-10s vs Maven 全量 30-60s
├── CI 大项目：Gradle 远程缓存可省 50-80% 构建时间
└── 注意：Gradle 配置阶段（Kotlin DSL 编译）有固定开销——
    小项目（1-3 模块）两者差距可忽略
```

> 💡 **性能决策原则**：构建频率 × 构建时长 = 时间成本。每天构建 50 次 × 省 30s = 每天省 25 分钟——大团队收益可观，小项目无所谓。

## 4. 生态与团队因素

> 🎯 **技术选型 60% 是团队问题，不是技术问题**：

```text
团队因素（最重要的决策变量）
├── 团队熟悉度
│   ├── 全组 Maven 熟练 → 迁移成本 = 培训 + 踩坑期（数周）
│   ├── 全组 Gradle 熟练 → 直接用 Gradle
│   └── 新团队 → 无历史包袱，看项目形态
├── 招聘市场：Gradle 经验者更多（Android 生态溢出）
├── 存量资产：现有 CI 脚本/私有插件/文档 → 迁移成本高
└── 维护意愿：谁维护构建脚本？Maven 门槛低，Gradle 需要进阶成员

生态因素
├── Android → 只能 Gradle（唯一选择）
├── Spring Boot → 两者皆可（官方全支持）
├── 老 Spring Cloud 全家桶 → Maven 存量多，但 Gradle 无缝
├── 微服务 Java 17+ 新项目 → 两者皆可
└── 构建插件生态：Gradle 插件市场活跃；Maven 插件老而全
```

## 5. 决策流程图

```text
开始：构建工具选型
│
├─ 做 Android？ → Gradle（唯一选择）
│
├─ 已有成熟 Maven 存量项目？
│   ├─ 团队满意 + 构建速度可接受？
│   │   └─ YES → 留 Maven，等 Maven 4 GA 升级
│   └─ 构建慢/想优化？
│       ├─ 模块 < 5 → 留 Maven（优化收益有限）
│       └─ 模块 ≥ 5 + CI 常跑 → 评估迁移 Gradle
│
├─ 新项目（无历史包袱）？
│   ├─ 团队全 Gradle 经验 → Gradle
│   ├─ 团队全 Maven 经验 → Maven 4（等 GA）或 Maven 3 起步
│   ├─ 性能敏感 + 构建频繁 → Gradle
│   └─ 想要简单 + 易维护 → Maven（声明式胜出）
│
└─ 特殊诉求
    ├─ 复杂自定义构建逻辑 → Gradle（可编程性）
    ├─ 强类型构建配置 → Gradle Kotlin DSL
    └─ 团队新人多/轮换快 → Maven（门槛低）
```

**决策金句**：

```text
├── 「性能差距大」：项目大 + 构建频繁 → Gradle
├── 「成本敏感」：团队熟 Maven → 留 Maven，别为性能折腾
├── 「新项目无约束」：默认 Gradle（生态/性能/未来），Maven 4 是备选
├── 「存量 Maven」：等 Maven 4 GA，升级收益 = 并发 + Consumer POM
└── 最终标准：选「团队用起来最舒服」的——构建工具不是业务竞争力
```

## 6. 混合使用：Maven 项目引入 Gradle

> 🎯 **不需要二选一**——Gradle 可以直接消费 Maven 仓库的依赖；Maven 多模块也可以让 Gradle 构建（Gradle 支持读取 Maven 本地仓库）：

```text
场景 1：Gradle 项目用 Maven 私有仓库依赖
├── Gradle 原生支持（repositories.maven { url = nexus }）
└── 存量公司 jar → Gradle 新项目直接拉

场景 2：Maven 项目逐步引入 Gradle
├── 新建 Gradle 构建脚本（保留 pom.xml 作对照）
├── 关键验证：产物一致（jar 结构/依赖树）
├── 双构建并行跑 CI 一段时间
└── 稳定后删 pom.xml

场景 3：依赖 Maven 本地仓库
├── Gradle 可配置 mavenLocal()（读 ~/.m2）
└── 注意：mavenLocal 不推荐用于团队共享（机器不一致）

迁移注意事项
├── 依赖版本：Gradle 默认最高版本 → 与 Maven 就近裁决结果可能不同！
├── 插件版本：迁移后显式锁定（Maven 插件不兼容 Gradle）
├── 资源处理/打包差异：核对产物内容
└── 金句：迁移 = 验证产物一致性，不是换个语法
```

## 7. 常见场景建议

| 场景 | 推荐 | 理由 |
|------|------|------|
| Android App | Gradle | 官方唯一支持 |
| 大型微服务（10+ 模块） | Gradle | 增量/缓存收益最大 |
| 中小 Web 服务（1-5 模块） | 均可 | 差距可忽略，看团队 |
| 老 Spring Boot 项目维护 | 留 Maven | 迁移成本 > 收益 |
| 全 Maven 团队的 2026 新项目 | Maven 4（GA 后） | 升级收益大 + 团队零培训 |
| 需要复杂自定义构建（代码生成/多平台） | Gradle | 可编程性 |
| 严格依赖审计企业 | 均可 | 配合 Nexus + 扫描工具 |
| 个人学习/教学 | Maven 先学 | 声明式简单，原理清晰 |

**2026-2027 预测视角**：

```text
├── Maven 4 GA 后：存量 Maven 团队升级（Consumer POM + 并发构建）
├── Gradle：继续主导新项目（尤其 Android/多模块）
├── 两者共存是常态——不是替代关系
└── 对个人：两个都要会（简历/面试两个都考，见 [[08-其他生态与生产实践]] 面试部分）
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. **格局**：Maven 4 重构收窄差距，但 Gradle 性能/可编程性仍领先
> 2. **Gradle 赢**：增量构建 + 远程缓存 + Kotlin DSL 类型安全 + Android
> 3. **Maven 赢**：声明式简单 + 上手成本低 + 生态存量 + 4.x 兼容
> 4. **决策变量**：团队熟悉度 > 构建规模 > 生态需求（不是性能第一）
> 5. **新项目**：默认 Gradle，全 Maven 团队可选 Maven 4
> 6. **存量 Maven**：等 Maven 4 GA 升级，别盲目迁移 Gradle
> 7. **混合可行**：Gradle 直接消费 Maven 仓库，迁移重点是产物一致性验证
> 8. **个人建议**：两个都会——Maven 理解原理，Gradle 掌握性能工程
