## 1. Go modules

> 🎯 **Go 的包管理是「官方内置 + 极简」**——没有第三方工具战争（对比 npm/pip 生态的碎片化）：

```bash
go mod init github.com/user/my-module   # 初始化
go get github.com/gin-gonic/gin@v1.10.0 # 加依赖
go mod tidy                             # 整理（加缺/去余）
go mod download                         # 预下载
go list -m all                          # 依赖列表
go mod graph                            # 依赖图
```

**Go modules 的核心机制**：

```text
① 模块 = 版本化的包集合
├── go.mod 声明：module 名 + go 版本 + 直接依赖
├── go.sum：依赖校验和（防篡改，必提交 git）
└── 模块版本语义：v1.10.0（SemVer 严格）

② MVS（最小版本选择）
├── 每个包只保留一个版本（所有约束的最大需求）
├── 新增依赖不升级已有包 → 构建高度可复现
├── 无冲突求解（不需要降级）→ 解析极快
└── 真正冲突（互斥要求）→ 直接报错，人肉解决

③ 代理与私有化
├── GOPROXY：proxy.golang.org（国内 goproxy.cn）
├── 私有模块：GOPRIVATE + 内部代理（不再污染公共模块缓存）
└── 校验和：GONOSUMCHECK 别关（安全底线）

④ 版本兼容（Go 1.21+ 的 toolchain 机制）
├── go.mod 声明最低 Go 版本
├── 工具链自动下载所需 Go 版本
└── 项目级隔离（对比 SDKMAN 手动管）
```

> 💡 **Go 的哲学**：官方把「版本解析、校验和、缓存」做进核心——开发者没有选择权，也就没有碎片化；**「少选择 = 少痛苦」**是 Go 给包管理界的启示。

## 2. Rust cargo

> 🎯 **cargo 被誉为「包管理器的教科书级实现」**——官方内置 + 语义化 + 极好用的 CLI：

```bash
cargo new my-project           # 创建（自带 git + 目录结构）
cargo add serde --features derive   # 加依赖（自动写 Cargo.toml）
cargo build / cargo run / cargo test  # 构建/运行/测试
cargo update                   # 按约束升级
cargo tree                     # 依赖树
cargo audit                    # 安全审计（社区标准）
cargo fmt / clippy             # 格式化/静态检查
```

**cargo 的设计亮点**：

```text
├── Cargo.toml（清单）+ Cargo.lock（锁文件，二进制项目必提交）
├── 语义化版本约束：serde = "1.0"（兼容 1.x 全部）
├── crates.io 中央仓库 + 校验和 + 版本不可变
├── 特性（features）系统：条件编译依赖（精细控制依赖树）
├── 工作空间（workspace）：monorepo 原生支持
└── 构建缓存：target/ 增量 + sccache 分布式缓存

Cargo.toml 示例
[package]
name = "my-tool"
version = "0.1.0"
edition = "2021"

[dependencies]
serde = { version = "1.0", features = ["derive"] }
tokio = { version = "1.40", features = ["full"] }

[dev-dependencies]
criterion = "0.5"
```

> 💡 **对比结论**：Rust 生态把「包管理」做成了语言的一部分（无第三方工具）；Go 的 MVS 与 cargo 的严格求解是两种哲学——前者重可复现、后者重精确控制。

## 3. 其他语言包管理器速览

> 🎯 **主流语言生态全景**——原理同 [[01-核心概念与原理]]（坐标/仓库/锁文件），只需记住各自特性：

| 生态 | 工具 | 仓库 | 锁文件 | 特性 |
|------|------|------|--------|------|
| Ruby | gem + Bundler | rubygems.org | Gemfile.lock | `gem install` 装全局；Bundler 管项目依赖 |
| PHP | Composer | packagist.org | composer.lock | 依赖隔离（vendor/）+ autoload 自动加载 |
| .NET | NuGet | nuget.org | packages.lock.json | 官方内置 `dotnet add package` |
| Swift | SPM（Swift Package Manager） | GitHub（git 即仓库） | Package.resolved | 无中央仓库，包即 git 仓库 |
| Dart/Flutter | pub | pub.dev | pubspec.lock | 官方内置（`dart pub`/`flutter pub`） |
| Scala | sbt / Mill / coursier | Maven Central 同源 | build.sbt 依赖 | JVM 生态，直接用 Maven 坐标 |
| C/C++ | **vcpkg**（微软）/ Conan | 各自 registry | vcpkg.json / conan.lock | 二进制库分发（源码+预编译） |
| R | CRAN + renv | CRAN | renv.lock | 数据科学/统计专用 |
| Julia | Pkg | General registry | Project.toml + Manifest.toml | 科学计算/AI |
| PowerShell | PSGallery | powershellgallery.com | psd1 模块清单 | 官方 `Install-Module` |

```bash
# Ruby：gem（包）+ Bundler（项目）
gem install rails                 # 全局安装
bundle init && bundle add rails   # 项目依赖管理（Gemfile + Gemfile.lock）
bundle install --deployment       # CI 严格模式

# PHP：Composer
composer require laravel/framework:^11.0   # 加依赖（composer.lock）
composer install --no-dev                  # CI 安装
composer update --lock                     # 只更新锁文件

# .NET：NuGet（官方内置）
dotnet add package Newtonsoft.Json --version 13.0.3
dotnet restore                            # 按项目文件还原
dotnet list package --outdated            # 过期检查

# Swift：SPM（git 即仓库）
# Package.swift 里声明 .package(url: "https://github.com/...", from: "1.2.0")
swift package resolve                     # 生成 Package.resolved 锁文件

# Dart/Flutter：pub（官方内置）
dart pub add http                         # 加依赖（pubspec.lock）
flutter pub get                           # Flutter 项目安装
flutter pub outdated                      # 过期检查

# C/C++：vcpkg（微软官方，与 winget 同厂商）
vcpkg install fmt                         # 安装库（源码编译/预编译二进制）
vcpkg.json 声明 + CMake 集成（toolchain 自动链接）

# R：CRAN + renv（项目级环境隔离）
install.packages("ggplot2")               # 装包
renv::init() / renv::snapshot()           # 项目环境 + renv.lock

# Julia：Pkg（官方内置）
julia> using Pkg; Pkg.add("Flux")
# Project.toml（清单）+ Manifest.toml（锁文件）
```

**长尾生态速查**（遇见了知道是谁就行）：

| 生态 | 工具 | 一句话定位 |
|------|------|-----------|
| Haskell | cabal / stack | 老牌函数式生态 |
| Elixir | mix / hex | Erlang VM 生态（Phoenix Web） |
| Erlang | rebar3 | OTP 项目标准 |
| Lua | luarocks | 游戏/嵌入式脚本 |
| Kotlin Multiplatform | Gradle（无独立工具） | 共享代码走 Gradle 依赖 |
| 基础设施 | Terraform Registry / Helm Charts | IaC/K8s 的「配置包」分发 |
| 模型（AI） | Hugging Face Hub / Ollama | 模型即依赖（2026 AI 工程新形态） |

> 💡 **共性总结**：`Gemfile.lock`、`composer.lock`、`packages.lock.json`、`Package.resolved`、`pubspec.lock`、`renv.lock`、`Manifest.toml`——**全部遵循「清单 + 锁文件」模型**（见 [[01-第7节 锁文件]]）；只是仓库形态不同（中央仓库 vs git 即仓库 vs 二进制 registry）。

> 💡 **工具分发（CLI 工具也是「包」）**：`pipx`（Python 隔离装 CLI 工具）、`npx`（临时执行 npm 包）、`cargo install`（Rust 工具）、`go install`（Go 工具）、`brew`（macOS 软件）——语言包管理器也承担「全局工具安装器」角色，别漏了这一面。

## 4. 系统包管理器：Windows / Linux / macOS

> 🎯 **系统包管理器管的是「软件本身」**（JDK/MySQL/编辑器），与语言包管理器（管库）分工不同。2026 全景：**Windows 三雄（winget/choco/scoop）、Linux 家族（apt/dnf/pacman/apk）、macOS（Homebrew）**、跨平台（snap/flatpak/容器）。

### 4.1 Windows：winget（官方内置，首选）

> 🎯 **winget（Windows Package Manager）是微软官方包管理器，Windows 11 默认内置**——2026 已迭代到 v1.29.x（1.29.250 正式版 / 1.29.280 RC），还支持 MCP（AI 代理可直接操作安装升级）。

```bash
# 常用命令
winget search vscode              # 搜索软件
winget install Microsoft.VisualStudioCode   # 按包 ID 安装
winget install --id=Oracle.JDK.21 --source winget   # 指定源
winget list                       # 已安装列表（支持 --sort 排序）
winget upgrade --all              # 全部升级
winget uninstall <id>             # 卸载
winget export settings.json       # 导出清单（装机迁移！）
winget import settings.json       # 新机器一键还原
winget show <id>                  # 查看详情（版本/来源/许可证）

# 自动化场景
winget install <id> --silent --accept-package-agreements --accept-source-agreements
winget install <id> --no-progress     # 无进度输出（CI 友好）
```

**winget 核心机制与 v1.29 新特性（2026）**：

```text
工作机制
├── 仓库：Windows 包清单（manifest）托管在 GitHub（microsoft/winget-pkgs）
├── 包 ID：厂商命名（Microsoft.VisualStudioCode / Oracle.JDK.21）
├── 安装器选择层级（1.29）：MSIX > MSI > NSIS/Inno > portable
├── 兼容：Windows 10/11 + Server，x86/x64/ARM64
└── 生态：winget 也支持第三方源（配置 source edit 优先级）

v1.29 新特性速览
├── 源优先级（Source Priority）：多源场景下结果排序/单一匹配直接装
├── 可排序 list：winget list --sort name --ascending
├── export/import 保留安装参数（--override/--custom 随配置迁移）
├── --no-progress：CI 管道友好输出
├── MCP 升级支持：AI 代理调 winget 查可升级/只升级已装包
├── PowerShell 模块 GitHub API 认证（读 GH_TOKEN 提速）
└── DSC v3 支持（配置即代码，见下）
```

**winget vs choco vs scoop（Windows 三雄）**：

| 维度 | winget（推荐） | Chocolatey | Scoop |
|------|:---:|:---:|:---:|
| 官方 | ✅ 微软 | ❌ 社区 | ❌ 社区 |
| Windows 11 | 内置 | 需安装 | 需安装 |
| 安装器类型 | MSIX/MSI/EXE 全支持 | 主要 EXE/MSI | **绿色便携**（无安装器） |
| 权限 | 部分需 UAC | **管理员模式** | 用户级（无 UAC） |
| 自动化 | ✅ 成熟（export/import + DSC） | ✅ 老牌（脚本多） | ✅ 简洁 |
| 包数量 | 大规模增长中 | 多 | 少（精） |
| 适合 | 个人/企业默认 | 企业批量部署（老牌） | 便携工具/开发 CLI |

> 💡 **Windows 装机推荐流程**：`winget export` 导出清单 → 新机器 `winget import` 一键还原；配合 **winget DSC 配置**（`winget configure` + DSC 文件）实现 Windows 配置即代码——2026 企业 Windows 标准化的官方路线。

### 4.2 Linux：apt / dnf / pacman / apk 家族

```bash
# Debian/Ubuntu 系：apt（依赖解析成熟，最常用）
sudo apt update && sudo apt install nginx
# RHEL/CentOS/Fedora 系：dnf（yum 的现代化继任者）
sudo dnf install nginx
# Arch 系：pacman（滚动更新，包最新）
sudo pacman -S nginx
# Alpine（容器基础镜像）：apk（极小极快）
apk add nginx

# 通用补充
snap install code        # Canonical 跨发行版（沙箱容器化）
flatpak install flathub org.videolan.VLC   # 桌面应用跨发行版
```

```text
Linux 家族关系
├── 包格式：deb（apt） vs rpm（dnf/yum）——格式决定发行版阵营
├── pacman：Arch 极简哲学（无版本锁定概念，滚动更新）
├── apk：Alpine 容器镜像标配（体积小，无 glibc 依赖负担）
├── snap/flatpak：跨发行版沙箱（解决「每个发行版装一遍」）
└── 2026 趋势：容器镜像（FROM ubuntu/debian/alpine）成为
    「基础设施软件」的事实标准——apt 只管镜像构建时
```

### 4.3 macOS：Homebrew（及 MacPorts）

```bash
brew install git node jq        # 常用软件
brew install --cask vscode      # GUI 应用（cask）
brew upgrade                    # 全部升级
brew bundle dump                # 导出 Brewfile（装机迁移）
brew bundle install             # 新机器还原

# 对比
# MacPorts：老牌（/opt/local，需 sudo，编译安装多）
# Homebrew：默认选择（/opt/homebrew 用户级，预编译 bottle）
# 2026 状态：Homebrew 事实标准；Apple Silicon 下 /opt/homebrew
```

### 4.4 选型与分工

```text
系统包管理器选型
├── Windows → winget（官方内置首选）；choco（企业脚本存量）；scoop（便携 CLI）
├── Linux → apt/dnf（发行版默认）+ Docker（环境隔离）
├── macOS → Homebrew（唯一主流答案）
└── 跨平台桌面 → snap/flatpak（沙箱）、Docker（开发环境）

2026 趋势
├── 语言运行时（JDK/Node/Python）→ 不用系统包管理器！
│   └── 用 SDKMAN/mise（版本切换灵活，见下节）
├── 基础设施软件（MySQL/Redis/Nginx）→ 系统包或 Docker
├── Windows 配置即代码：winget DSC + export/import 成为官方标准化路线
└── 金句：系统包管理器管「稳定」，版本管理器管「灵活」
```

> ⚠️ **不要用 apt/brew 装 JDK**：apt 的 OpenJDK 版本陈旧且无法多版本切换；brew 的 openjdk 是当前版单版本——Java 开发用 SDKMAN/mise（见下节），系统包管理器只装 docker/git 等基础工具。

## 5. 统一版本管理：SDKMAN / mise

> 🎯 **版本管理器 = 管「运行时」的包管理器**（JDK 8/17/21 多版本共存切换）——这是 2026 多语言开发者的标准姿势：

```bash
# SDKMAN（JVM 生态专用，Java 人首选）
curl -s "https://get.sdkman.io" | bash
sdk list java                     # 所有 JDK 版本
sdk install java 21.0.5-temurin   # 装 Temurin JDK 21
sdk use java 17.0.12-temurin      # 当前 shell 临时切换
sdk default java 21.0.5-temurin   # 设为默认
sdk install maven 4.0.0-rc-5      # 也能管构建工具
sdk install gradle 9.3            # Gradle 版本
```

```bash
# mise（多语言统一，2026 快速崛起）
mise install node@22              # Node
mise install python@3.12          # Python
mise install java@21              # JDK
mise use node@22                  # 项目级锁定（写 .mise.toml）
# 项目目录内有 .mise.toml → cd 进入自动切换（类似 asdf 但更快）
```

**版本管理器对比**：

| 工具 | 覆盖 | 特点 | 2026 状态 |
|------|------|------|-----------|
| SDKMAN | JVM 生态（JDK/Maven/Gradle/Kotlin） | 最全的 JDK 发行版列表 | Java 人标准 |
| nvm | Node | 老牌，shell 钩子切换 | 前端标准 |
| pyenv | Python | 编译源码装版本（慢） | 被 uv 内置替代 |
| asdf | 全语言 | 插件化，配置复杂 | 存量 |
| **mise** | 全语言 | Rust 快 + .mise.toml 项目级 | ⭐ 新趋势 |
| **uv** | Python | 内置 python 版本管理 | Python 标准 |

> 💡 **2026 推荐组合**：Java 开发 = SDKMAN；多语言混栈 = mise；纯 Python = uv 内置即可——**项目级版本锁定文件（.mise.toml）进 git**，团队环境自动一致。

## 6. 多语言工程实践

> 🎯 **一个真实服务端项目往往横跨 4-5 个生态**——统一工程纪律才是关键：

```text
典型 Java 后端 + AI 项目的包管理全景
├── Java 服务：Maven 4 / Gradle 9（JDK 17/21 经 SDKMAN/mise）
├── Python AI 服务：uv（Python 3.12 经 uv 内置）
├── 前端：pnpm（Node 经 mise/nvm）
├── 基础设施：Docker 镜像（构建阶段装工具链）
└── 金句：每个生态用「该生态的标准工具」，跨生态用「mise 统一版本」

工程纪律十条
├── ① 锁文件全部进 git（pom 依赖树/package-lock/uv.lock/go.sum）
├── ② CI 强制一致性（--frozen-lockfile / -Dmaven.resolver.transport）
├── ③ 依赖升级走专门命令 + review（不手动改版本号）
├── ④ 私有仓库统一收口（Nexus 管 Java/npm，PyPI 私有源管 Python）
├── ⑤ 版本管理文件进 git（.mise.toml / .nvmrc / .tool-versions）
├── ⑥ 构建脚本可复现（Docker 里固化工具链版本）
├── ⑦ 依赖审计接入 CI（npm audit / uv audit / OWASP DC）
├── ⑧ 生成 SBOM（cyclonedx/syft）满足合规
├── ⑨ 主依赖升级设「更新窗口」（如每季度统一评估）
└── ⑩ 新依赖入库门槛：维护活跃度 + 下载量 + 许可证检查
```

## 7. 供应链安全企业实践

> 🎯 **2026 供应链安全已是企业级硬指标**（log4j 之后无人再敢忽视）：

```text
企业依赖治理架构
├── 唯一入口：私有制品仓库（Nexus/Artifactory）
│   ├── 代理公共源（开发者不直连中央仓库）
│   ├── 白名单：仅允许已审核的包版本
│   └── 缓存不可变：防删除/篡改
├── 扫描流水线
│   ├── CI 构建时：依赖漏洞扫描（阻断高危）
│   ├── 周期扫描：全量项目清单（发现存量漏洞）
│   └── 工具：OWASP Dependency-Check / Snyk / Trivy / 各生态 audit
├── 签名与校验
│   ├── Maven：GPG 签名验证（中央仓库强制）
│   ├── Go：go.sum 校验
│   └── npm：integrity 字段
└── SBOM 与合规
    ├── SBOM（软件物料清单）：cyclonedx-maven-plugin / syft 生成
    ├── 许可证合规：license 扫描（GPL 传染性检查）
    └── 出口合规：受管制组件清单
```

**常见攻击与防御对照**：

| 攻击 | 手段 | 防御 |
|------|------|------|
| 仿冒包 | 近拼写包名窃密钥 | 私有源白名单 + 安装核对 |
| 依赖混淆 | 私有包名在公共源注册同名 | 私有源优先 + 唯一源策略 |
| 投毒更新 | 维护者账号被攻破 | 版本锁定 + 发布后审计窗口 |
| 传递投毒 | 底层小包被污染 | 锁文件 + 依赖最小化 |
| 仓库篡改 | 攻击制品服务器 | 校验和 + 签名 + 只读制品 |

## 8. CI 中的包管理器

```yaml
# 示例：GitHub Actions + pnpm + uv（2026 典型流水线）
steps:
  - uses: actions/setup-node@v4
    with: { node-version: 22, cache: "pnpm" }
  - uses: astral-sh/setup-uv@v6      # uv 官方 action
  - run: uv python install 3.12 && uv sync --frozen --no-group dev
  - run: pnpm install --frozen-lockfile
  - run: pnpm build
  - run: uv run pytest
```

**CI 缓存策略（速度关键）**：

```text
├── Maven：缓存 ~/.m2（cache key 按 pom 哈希）
├── Gradle：远程构建缓存（HttpBuildCache 企业自建）
├── pnpm：缓存内容寻址存储 + --frozen-lockfile
├── uv：缓存 ~/.cache/uv（actions 自带 cache）
└── Go：缓存 module cache（GOCACHE 远程可选）

CI 一致性三件套
├── 锁文件强制：--frozen-lockfile / npm ci / go mod tidy 校验
├── 版本锁定：构建工具版本固定（sdkman-java 文件/gradle wrapper）
└── 审计阻断：高危漏洞 → 构建失败（fail-on-severity 思想）
```

> 💡 **gradle wrapper 是 Java 侧一致性典范**：`gradlew` + `gradle-wrapper.properties` 固定 Gradle 版本——团队/CI 永远用同一版本构建。

## 9. 面试高频题

**Q1：Maven 和 Gradle 怎么选？**

```text
答：看团队和场景。性能敏感/新项目/Android → Gradle（增量+缓存+DSL）；
存量 Maven 团队/追求简单 → Maven 4（声明式+并发构建）。
没有绝对优劣——团队熟悉度是第一决策变量。
```

**Q2：Maven 依赖冲突怎么解决？**

```text
答：Maven 就近原则（离根近的版本胜出）→ mvn dependency:tree 定位
→ 用 exclusions 排除或 dependencyManagement 统一版本
→ enforcer 插件 dependencyConvergence 强制收敛防复发。
```

**Q3：虚拟环境是干什么的？**

```text
答：Python 包隔离。PEP 405 机制：独立 site-packages + PATH 切换。
解决「两个项目要不同版本的同一个包」的问题。
2026 由 uv/poetry 自动管理，不必手动 activate。
```

**Q4：pnpm 为什么比 npm 快？**

```text
答：内容寻址存储 + 硬链接——所有项目共享一份物理包文件，
不重复复制；同时符号链接做严格隔离，杜绝幽灵依赖。
```

**Q5：锁文件有什么用？**

```text
答：固定全量依赖精确版本（含传递依赖）→ 可复现构建。
本地、CI、同事机器装出完全一致的环境；
升级走专门命令 + review，锁文件提交 git。
```

**Q6：uv 的版本约束有什么坑？（2026 新题）**

```text
答：uv add 默认写入无上界约束（pydantic>=2.13.4），
批量升级可能跨主版本引入破坏性变更。
应用项目要配 [tool.uv] add-bounds="major" 或精确固定版本。
```

**Q7：Windows 上装软件用什么？winget 和 Chocolatey 区别？**

```text
答：首选 winget——微软官方、Windows 11 内置（无需安装）、
支持 MSIX/MSI/EXE 全类型，export/import + DSC 支持配置即代码；
choco 是老牌社区方案（管理员模式、脚本生态多），
scoop 是便携式（无安装器、用户级无 UAC）。
现代 Windows 环境默认 winget，choco 留给企业存量脚本。
```

**Q8：Ruby/PHP/.NET/Swift 的包管理器分别是什么？**

```text
答：Ruby gem+Bundler、PHP Composer、.NET NuGet（官方内置）、
Swift SPM（git 仓库即分发）。共同点：清单 + 锁文件模型
（Gemfile.lock / composer.lock / packages.lock.json / Package.resolved）。
```

## 10. 核心要点

> 🎯 **核心要点**：
> 1. **Go MVS**：最小版本选择，构建高度可复现——少选择少痛苦
> 2. **Rust cargo**：包管理教科书——官方内置 + 锁文件 + audit
> 3. **Ruby/PHP/.NET/Swift**：gem+Bundler / Composer / NuGet / SPM——同一套「清单+锁文件」模型
> 4. **Windows 包管理首选 winget**：官方内置 + v1.29（MCP/DSC/源优先级）+ export/import 装机迁移；choco 留存量、scoop 管便携
> 5. **Linux 家族**：apt（Debian）/ dnf（RHEL）/ pacman（Arch）/ apk（Alpine）——格式决定阵营，容器是事实标准
> 6. **系统包管理器管软件**、版本管理器管运行时（SDKMAN/mise 管 JDK/Node/Python）
> 7. **mise 是 2026 多语言统一版本管理的新趋势**（.mise.toml 项目级锁定）
> 8. **多语言纪律**：锁文件进 git + CI frozen + 私有仓库收口 + 审计
> 9. **供应链五防**：仿冒/混淆/投毒/传递/篡改——私有源 + 校验 + SBOM
> 10. **面试主线**：选型（Maven/Gradle）、冲突、虚拟环境、锁文件、uv 约束、winget 生态
> 11. **体系回顾**：原理（[[01]]）→ Java（[[02]]~[[05]]）→ 前端（[[06]]）→ Python（[[07]]）——生产实践即本模块
