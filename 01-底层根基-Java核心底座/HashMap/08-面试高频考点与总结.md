## 1. 面试高频题与答题框架

### 1.1 数据结构类

**Q1：HashMap 的底层数据结构？**

```text
① JDK 7：数组 + 链表
② JDK 8+：数组 + 链表 + 红黑树
③ 数组（桶）：哈希定位 O(1) 入口
④ 链表：冲突处理（短链）
⑤ 红黑树：防退化（长冲突 O(log n)）
⑥ 金句：数组管定位、链表管冲突、红黑树管极端
```

**Q2：默认参数有哪些？为什么负载因子是 0.75？**

```text
① 参数：初始容量 16、负载因子 0.75、阈值 12、树化 8、退化 6、最小树化容量 64
② 0.75 = 时间与空间的折中：
   ├── 太高：空间利用好但冲突多（查询慢）
   ├── 太低：冲突少但空间浪费（扩容频繁）
   └── 0.75：泊松分布下冲突概率低
③ 金句：0.75 = 「空间不浪费 + 查询不慢」的工程平衡
```

### 1.2 Hash 与定位类

**Q3：扰动函数是什么？为什么需要？**

```text
① 定义：hash = hashCode() ^ (hashCode() >>> 16)
② 目的：高 16 位与低 16 位异或——高位信息参与定位
③ 问题背景：容量小（16）只用低 4 位——低位相同则全冲突
④ JDK 7：9 次位运算；JDK 8：2 次（树化兜底简化）
⑤ 金句：扰动 = 「让高位参与低位」——小容量下分布均匀
```

**Q4：为什么容量必须是 2 的幂？**

```text
① 位运算代替取模：(n-1) & hash（快）
② 分布均匀：2 的幂低 k 位全覆盖
③ 扩容友好：容量翻倍 = 多一位参与（高低位拆分）
④ tableSizeFor：任意容量 → 最近 2 的幂
⑤ 金句：2 的幂 = 性能 + 均匀 + 扩容三合一
```

### 1.3 树化类

**Q5：什么条件下链表转红黑树？（陷阱题）**

```text
① 双条件：链表长度 ≥ 8 且 容量 ≥ 64
② 容量 < 64：先扩容（不是树化！）
③ 为什么：小容量下扩容收益 > 树化收益
④ 为什么 8：泊松分布（0.75 下概率千万分之六）
⑤ 为什么退化 6：与 8 形成缓冲（防震荡）
⑥ 金句：只说「≥8 转树」是错的——漏了容量条件
```

**Q6：为什么用红黑树不用 AVL？**

```text
① 场景：读写混合（put/get 都有）
② 红黑树：插入/删除快（旋转少）
③ AVL：查询略快但插入删除频繁旋转
④ HashMap 桶操作读写混合 → 红黑树更平衡
⑤ 金句：红黑树 = 「查询够快 + 写入不慢」的工程平衡
```

### 1.4 扩容类

**Q7：扩容机制是什么？高低位拆分是什么？**

```text
① 触发：size > 阈值（容量 × 0.75）
② 新容量：×2（2 的幂保持）
③ 高低位拆分：扩容后多一位参与——(hash & oldCap) == 0
   ├── 0：留原索引
   └── 非 0：移「原索引 + oldCap」
④ 效果：免重算 hash + 一次遍历
⑤ 金句：JDK 8 扩容 = 位运算拆分（不是重算）
```

**Q8：JDK 7 并发扩容为什么死循环？**

```text
① 头插法：迁移时链表反转
② 并发：线程 A 迁移一半挂起 → 线程 B 完成（反转）
③ A 恢复 → 基于旧引用迁移 → 环形链表
④ 结果：get 死循环 CPU 100%
⑤ JDK 8 修复：尾插法保序 + 高低位拆分
⑥ 注意：JDK 8 修死循环但仍非线程安全
```

### 1.5 并发类

**Q9：HashMap 为什么线程不安全？**

```text
① 无锁：put 多步非原子
② 数据覆盖：并发 put 同一桶互相覆盖
③ 数据丢失：并发扩容迁移丢失
④ size 不准：size++ 非原子
⑤ JDK 8 修死循环但没修安全
⑥ 金句：并发场景第一反应 = ConcurrentHashMap
```

**Q10：ConcurrentHashMap 怎么保证线程安全？（JDK 8）**

```text
① 空桶：CAS 无锁插入（高并发最优路径）
② 非空桶：synchronized 锁头节点（桶级锁）
③ 读：完全无锁（volatile 可见性）
④ 扩容：多线程协作（ForwardingNode 标记）
⑤ 不允许 null key/value
⑥ 金句：CAS 无锁 + 桶级锁 + 无锁读 = 并发度最大化
```

**Q11：computeIfAbsent 在 HashMap 和 ConcurrentHashMap 的区别？**

```text
① HashMap：非原子——并发 mappingFunction 可能执行多次
② CHM：原子——只执行一次（锁保证）
③ 风险：非幂等函数（扣款/发短信）重复执行 → 业务错误
④ 场景：缓存加载/初始化用 CHM
⑤ 金句：并发初始化 = computeIfAbsent（CHM）
```

### 1.6 JDK 21 与生产类

**Q12：JDK 21 对 HashMap 的优化？（2026 新考点）**

```text
① 增量扩容：扩容分批 + 读写顺带迁移（防 CPU 峰值）
② 哈希优化：随机扰动因子（防特殊 key 冲突）
③ 内存优化：移除冗余 hash 字段
④ CHM 优化：细粒度锁 + 新工厂方法
⑤ 金句：JDK 21 = 大规模 Map 的生产级优化
```

**Q13：生产怎么预估 HashMap 容量？**

```text
① 公式：initialCapacity = expectedSize / 0.75 + 1
② 效果：已知数据量 → 零扩容
③ 场景：批量导入/缓存预加载
④ 反例：默认 16 存 1000 → 7 次扩容
⑤ 金句：预估 = 多花初始内存、省多次 O(n) 迁移
```

**Q14：自定义 key 有什么要求？**

```text
① 不可变（final）——修改后 hash 变 get 不到
② equals + hashCode 一起重写（一致）
③ equals 相等 → hashCode 必须相等
④ 推荐：record（自动生成）
⑤ 金句：可变 key 是生产事故（永久丢失）
```

**Q15：遍历中删除元素会怎样？**

```text
① 直接 remove：ConcurrentModificationException（fail-fast）
② 正确：Iterator.remove / removeIf
③ 原因：modCount 修改计数检测
④ 金句：fail-fast 是设计不是防护——用迭代器删除
```

**Q16：HashMap 和 Hashtable 的区别？**

```text
① 线程安全：HashMap 否 / Hashtable 全方法 synchronized
② null：HashMap 允许 / Hashtable 不允许
③ 初始容量：16 vs 11；扩容 ×2 vs ×2+1
④ 性能：HashMap 高 / Hashtable 全局锁
⑤ 结论：并发用 ConcurrentHashMap（不是 Hashtable）
```

**Q17：所有 key 哈希相同会怎样？**

```text
① 全部落入同一桶（冲突）
② JDK 7：链表 O(n)（退化）
③ JDK 8：≥8 且容量 ≥64 → 红黑树 O(log n)
④ key 实现 Comparable：树化按 compareTo 排序
⑤ 恶意场景：哈希碰撞攻击（DoS）
⑥ 金句：HashMap 的 O(1) 前提 = hash 分布均匀
```

**Q18：HashMap 和 LinkedHashMap/TreeMap 的区别？**

```text
① HashMap：无序（哈希）
② LinkedHashMap：插入/访问顺序（LRU 缓存可继承）
③ TreeMap：key 排序（红黑树——O(log n)）
④ 选择：需要顺序 → LinkedHashMap/TreeMap
⑤ 金句：HashMap 默认；顺序需求换 Map 实现
```

## 2. 代码题实战

**题 1：输出什么？**

```java
Map<String, Integer> map = new HashMap<>();
map.put(null, 1);
map.put("a", 2);
map.put(null, 3);          // 覆盖 null key
System.out.println(map.size());        // ? 2（null key 只 1 个）
System.out.println(map.get(null));     // ? 3（后放覆盖）
```

**题 2：下面代码有什么问题？**

```java
// ① 并发累加（丢更新）
Map<String, Integer> map = new HashMap<>();
map.merge("count", 1, Integer::sum);   // ❌ 并发丢累加
// ✅ map = new ConcurrentHashMap<>()

// ② 遍历删除
for (String k : map.keySet()) map.remove(k);   // ❌ ConcurrentModificationException
// ✅ map.keySet().removeIf(k -> true)

// ③ 可变 key
class Key { String id; }               // ❌ 可变 + 无 hashCode
// ✅ record Key(String id) { }
```

**题 3：手写 put 的关键逻辑**

```java
// 简述 HashMap.put 流程（面试口述）：
// ① 扰动 hash
// ② 懒初始化（resize）
// ③ 定位 (n-1) & hash
// ④ 桶空直插；非空遍历（hash+equals 判定）
// ⑤ 相同 key 覆盖；不同追加（尾插）
// ⑥ ≥8 且容量 ≥64 树化
// ⑦ size > 阈值扩容
```

**题 4：实现 LRU 缓存（LinkedHashMap）**

```java
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    public LRUCache(int capacity) {
        super(capacity, 0.75f, true);   // accessOrder=true（LRU）
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;       // 超容量移除最久未用
    }
}
```

**题 5：找出 Top K 出现次数（HashMap + 排序）**

```java
public List<String> topK(List<String> words, int k) {
    return words.stream()
        .collect(Collectors.groupingBy(w -> w, Collectors.counting()))
        .entrySet().stream()
        .sorted(Map.Entry.<String, Long>comparingByValue().reversed())
        .limit(k)
        .map(Map.Entry::getKey)
        .toList();
}
```

## 3. 速查表

```text
结构：数组 + 链表 + 红黑树（JDK 8+）
参数：容量 16 / 负载因子 0.75 / 阈值 12 / 树化 8 / 退化 6 / 最小树化容量 64
哈希：扰动 (h ^ (h>>>16)) + 定位 ((n-1) & hash)——容量必须 2 的幂
put：懒初始化 → 定位 → 空桶直插/冲突遍历 → 覆盖/追加 → 树化 → 扩容
扩容：size > 阈值 → ×2 → 高低位拆分（(hash & oldCap) == 0 判定）
树化：≥8 且容量 ≥64（容量 <64 先扩容）；退化 ≤6（6-8 缓冲）
并发：JDK 7 死循环（头插）；JDK 8 尾插修复但仍非安全
替代：ConcurrentHashMap（CAS + 锁头 + 无锁读）
JDK 21：增量扩容 / 随机扰动 / 内存优化
生产：容量预估（/0.75+1）、自定义 key（record）、removeIf 删除
```

## 4. 五大常见误区

| # | 误区 | 真相 |
|---|------|------|
| 1 | 「HashMap 线程安全（JDK 8 修了）」 | 修的是死循环——数据覆盖/丢失仍在 |
| 2 | 「链表 ≥8 就转树」 | 双条件：≥8 且容量 ≥64（否则先扩容） |
| 3 | 「初始容量直接用传入值」 | tableSizeFor 转成最近 2 的幂 |
| 4 | 「自定义 key 只需 equals」 | equals + hashCode 必须一起且一致 |
| 5 | 「并发场景加锁的 HashMap 够用」 | 首选 ConcurrentHashMap（原子方法/高并发） |
