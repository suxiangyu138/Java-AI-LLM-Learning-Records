## 1. JDK 21 新优化总览

> **背景**：JDK 21（LTS，2023.09）对 HashMap 的优化——解决大规模 Map 的痛点（扩容卡顿、特殊 key 冲突、内存占用）。
> **目的**：掌握 2026 面试新考点（JDK 21 优化点）。
> **适用范围**：JDK 21+ 的 HashMap/ConcurrentHashMap。

```text
JDK 21 四大优化
├── ① 增量扩容：扩容分批次（防 CPU 峰值卡顿）
├── ② 哈希算法优化：随机扰动因子（降低特殊 key 冲突）
├── ③ 内存优化：移除冗余 hash 字段（减少占用）
├── ④ ConcurrentHashMap：细粒度节点锁 + CAS + 新工厂方法
└── ⑤ 金句：JDK 21 = 「大规模 Map 的生产级优化」
```

## 2. 增量扩容

### 2.1 传统扩容的问题

```text
传统扩容（一次性迁移）的问题
├── ① 大 Map 扩容：千万级元素全部迁移
├── ② CPU 峰值：迁移瞬间 CPU 飙升
├── ③ 卡顿：业务请求被扩容阻塞
└── ④ 场景：缓存/索引等大 Map 的扩容痛点
```

### 2.2 增量扩容机制

```text
JDK 21 增量扩容
├── ① 扩容任务拆分为多批次
├── ② 后续 put/get 时顺带迁移部分元素
│   ├── 读路径：遇到未迁移桶 → 协助迁移
│   ├── 写路径：写入时顺带迁移
│   └── 分摊：把一次大迁移摊到多次操作
├── ③ 效果：
│   ├── 无 CPU 峰值（平滑扩容）
│   ├── 无长时间卡顿（业务无感知）
│   └── 吞吐稳定
└── ④ 对比 ConcurrentHashMap 已有多线程协作扩容
    └── JDK 21 的优化面向 HashMap 串行场景
```

```text
面试答法（JDK 21 增量扩容）
├── ① 问题：一次性扩容在大 Map 上有 CPU 峰值
├── ② 方案：扩容分批 + 读写路径顺带迁移
├── ③ 效果：平滑扩容（无卡顿）
└── ④ 注意：这是 JDK 21 新特性（2026 面试加分点）
```

## 3. 哈希算法优化

### 3.1 问题：特殊 key 的冲突

```text
传统扰动函数的问题
├── ① 扰动固定：(h) ^ (h >>> 16)
├── ② 特殊 key（连续整数等）：
│   ├── 某些 hashCode 模式低位相似
│   └── 冲突集中在少数桶（链表退化）
└── ③ 攻击：恶意 key 构造同 hash → 冲突攻击
```

### 3.2 随机扰动因子

```text
JDK 21 哈希优化
├── ① 新增随机扰动因子（多轮异或）
│   ├── 哈希计算引入随机性
│   ├── 降低特殊 key 的冲突概率
│   └── 每次 JVM 启动随机（同 key 不同 JVM 分布不同）
├── ② 效果：
│   ├── 连续整数等特殊 key 分布更均匀
│   ├── 抗冲突攻击增强（攻击者无法预测分布）
└── ③ 注意：
    ├── 分布有随机性（不保证最优）
    └── 面向「特殊 key」的鲁棒性提升
```

## 4. 内存优化

```text
JDK 21 内存优化
├── ① 移除 Node 节点的冗余 hash 字段
│   ├── 传统：Node 存 hash（缓存——免重算）
│   ├── 优化：部分场景不再缓存（计算更便宜时）
│   └── 效果：减少每节点内存
├── ② 大 Map 的收益：
│   ├── 百万级节点：内存节省明显
│   └── 与增量扩容协同（内存 + 性能双优）
└── ③ 权衡：
    ├── 传统存 hash：查询免重算（快但占内存）
    └── 优化移除：省内存（hash 计算开销增加）
    → JDK 21 在「hash 计算便宜」的场景移除
```

## 5. 生产实践：容量预估

> 🎯 **预估容量避免多次扩容**（最有效的生产优化）：

```java
// ❌ 不预估：已知 1000 个 → 7 次扩容（16→...→2048）
Map<String, Order> map = new HashMap<>();
for (int i = 0; i < 1000; i++) map.put("k" + i, order);

// ✅ 预估：initialCapacity = 预期 / 0.75 + 1
Map<String, Order> map = new HashMap<>((int) (1000 / 0.75f) + 1);

// 通用工具（生产建议）
public static <K, V> HashMap<K, V> newHashMap(int expectedSize) {
    return new HashMap<>((int) (expectedSize / 0.75f) + 1);
}

// 或 Java 19+：ConcurrentHashMap.newKeySet 类似的工厂
// HashMap 无官方工厂——自定义工具类即可

// ⚠️ 注意：
// ① 过度预估 → 内存浪费（数组按容量分配）
// ② 批量导入/缓存预加载场景必预估
// ③ 预估误差 50% 内影响可控（多一次扩容可接受）
```

## 6. 生产实践：自定义 key

### 6.1 三条铁律

```text
自定义 key 铁律（生产）
├── ① 不可变：final 字段（修改后 hash 变 → get 不到）
├── ② equals + hashCode 一起重写（不一致 = 定位失败）
├── ③ 与 equals 一致：equals 相等 → hashCode 必须相等
└── ④ 2026 推荐：record（自动生成 equals/hashCode + 不可变）
```

### 6.2 示例

```java
// ✅ 推荐：record（不可变 + equals/hashCode 自动）
record OrderKey(String orderId, Long userId) { }

// ✅ 手动重写（正确姿势）
class UserKey {
    private final String id;      // 不可变
    private final int type;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof UserKey)) return false;
        UserKey k = (UserKey) o;
        return type == k.type && id.equals(k.id);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id, type);   // 与 equals 字段一致！
    }
}

// ❌ 常见错误
// ① 只重写 equals 不重写 hashCode → 永远定位失败
// ② 可变字段参与 hash → 修改后 get 不到
// ③ 用默认 hashCode（引用）→ new 的 key 永远 get 不到

// 生产场景
Map<UserKey, User> userCache = new HashMap<>();
userCache.put(new UserKey("U-1", 1), user);
userCache.get(new UserKey("U-1", 1));   // ✅ 找到（equals/hashCode 一致）
```

## 7. 生产实践：遍历与删除

```java
// ① 遍历删除（fail-fast 陷阱）
// ❌ 直接 remove → ConcurrentModificationException
for (String key : map.keySet()) {
    if (key.startsWith("x")) map.remove(key);   // ❌
}
// ✅ Iterator.remove
Iterator<String> it = map.keySet().iterator();
while (it.hasNext()) {
    if (it.next().startsWith("x")) it.remove();
}
// ✅ removeIf（简洁）
map.keySet().removeIf(k -> k.startsWith("x"));

// ② 安全取值（null 歧义）
// get 返回 null 无法区分「不存在」与「值为 null」
String v = map.getOrDefault("k", "default");
if (map.containsKey("k")) { ... }   // 需要区分时

// ③ 迭代性能（大 Map）
// entrySet 遍历（避免 keySet + get 二次哈希）
for (Map.Entry<String, Order> e : map.entrySet()) { ... }

// ④ 清空与复用（内存）
map.clear();              // 清空（保留容量——可复用）
// ⚠️ 大 Map 用完置 null（帮助 GC）：
// map = null（引用置空——大对象尽快回收）
```

## 8. 性能排查与调优

### 8.1 排查手段

```text
HashMap 性能排查
├── ① 冲突检测：debug 看链表长度/树化情况
│   ├── 断点：putVal 中 binCount ≥ 8（树化触发）
│   └── 或监控：大量树化 = 冲突异常
├── ② 容量/扩容监控：
│   ├── 日志：扩容次数（自定义包装）
│   └── 或预估验证（容量是否够）
├── ③ 内存排查：
│   ├── jmap 堆转储 → 看 Map 占用
│   └── 大 Map 识别（对象大小分析）
└── ④ 热点定位：火焰图（get/put 占比）
```

### 8.2 调优清单

```text
HashMap 调优清单（生产）
├── ① 容量预估：/0.75+1（已知数据量必做）
├── ② 负载因子：默认 0.75（除非特殊）
│   ├── 高内存敏感：0.8-1.0（冲突增多）
│   └── 高查询敏感：0.5-0.6（空间换时间）
├── ③ key 质量：hashCode 分布均匀（自定义 key）
├── ④ 大 Map 替代：考虑 Redis/外部缓存（本地内存有限）
├── ⑤ 只读场景：Map.copyOf（不可变——省检查）
└── ⑥ 并发场景：ConcurrentHashMap（绝不用 HashMap）
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. JDK 21 四大优化：增量扩容（防 CPU 峰值）/随机扰动（防特殊 key 冲突）/内存优化（移冗余字段）/CHM 新方案——2026 面试新考点
> 2. 容量预估是最高性价比优化：initialCapacity = 预期/0.75 + 1（零扩容）
> 3. 自定义 key 三铁律：不可变 + equals/hashCode 一起 + 一致——record 最安全
> 4. 遍历删除：Iterator.remove/removeIf（fail-fast 禁止直接 remove）
> 5. get 返回 null 有歧义——getOrDefault/containsKey 区分
> 6. 调优清单：预估/负载因子/key 质量/大 Map 替代/只读 copyOf/并发 CHM
