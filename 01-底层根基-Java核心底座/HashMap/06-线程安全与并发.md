## 1. HashMap 的非线程安全问题

> **背景**：HashMap 的所有操作都没有同步保护——多线程并发读写会导致数据错误。
> **目的**：理解问题的表现与根源。
> **适用范围**：任何多线程场景使用 Map 时。

```text
并发问题的三类表现
├── ① 数据覆盖：两个线程同时 put 同一桶 → 后写覆盖
├── ② 数据丢失：扩容迁移时元素丢失（并发 resize）
├── ③ 死循环（JDK 7）：环形链表 → get 卡死 CPU 100%
└── ④ 结构破坏：size 不准/链表断裂

根源
├── ① 无锁：所有操作非原子（put 多步）
├── ② 共享可变状态：table/size 无 volatile 保护
├── ③ 并发扩容：迁移过程无同步
└── ④ 结论：并发场景严禁直接使用 HashMap
```

## 2. JDK 7 死循环详解

> ⚠️ **JDK 7 并发扩容死循环**——经典生产事故（CPU 100%）：

```text
死循环成因（三步）
├── ① JDK 7 头插法：
│   ├── 迁移时新节点插链表头部
│   └── 迁移后链表顺序反转
├── ② 并发扩容（两个线程）：
│   ├── 线程 A：遍历旧链表迁移（到一半被挂起）
│   ├── 线程 B：完成迁移（链表已反转）
│   └── 线程 A 恢复：基于「已变化的引用」继续迁移
├── ③ 结果：形成环形链表
│   ├── A → B → A（循环引用）
│   └── get 遍历 → 死循环 → CPU 100%
└── ④ 修复（JDK 8）：尾插法 + 高低位拆分（保序——不反转）

⚠️ 面试要点
├── ① JDK 7：死循环（头插法 + 并发反转）
├── ② JDK 8：修复死循环（尾插法保序）
├── ③ 但 JDK 8 仍有：数据覆盖/丢失/size 不准
└── ④ 结论：并发场景永远用 ConcurrentHashMap
```

## 3. JDK 8 的剩余问题

```text
JDK 8 HashMap 的并发问题（修了死循环但没修安全）
├── ① 数据覆盖：
│   ├── 线程 A/B 同时 put 同一空桶
│   ├── 都判断桶空 → 都直接插入
│   └── 一个覆盖另一个（丢数据）
├── ② 扩容竞态：
│   ├── 并发 resize → 元素可能丢失
│   ├── 迁移中读 → 读到 null/旧值
├── ③ size 不准：
│   ├── size++ 非原子（多个线程同时加）
│   └── 计数偏差
└── ④ modCount 竞态：
    ├── 迭代中并发修改 → ConcurrentModificationException
    └── （fail-fast 是设计不是防护）

结论
├── JDK 8 的 HashMap「不会卡死」≠「线程安全」
└── 生产铁律：多线程共用的 Map → ConcurrentHashMap
```

## 4. 线程安全替代方案

| 方案 | 锁粒度 | 性能 | 2026 推荐 |
|------|:---:|:---:|:---:|
| **ConcurrentHashMap** | 桶级（CAS+synchronized） | 高 | ✅ **首选** |
| Collections.synchronizedMap | 全局锁 | 低 | 少量读场景 |
| Hashtable | 全局 synchronized | 最低 | ❌ 过时 |
| 业务加锁 | 按业务 | 视场景 | 特殊需求 |

```java
// ① ConcurrentHashMap（首选）
Map<String, Order> map = new ConcurrentHashMap<>();
map.put("ORD-1", order);
map.get("ORD-1");

// ② synchronizedMap（简单但慢）
Map<String, Order> map = Collections.synchronizedMap(new HashMap<>());
// ⚠️ 遍历仍需手动同步：
synchronized (map) {
    for (var e : map.entrySet()) { ... }
}

// ③ 业务锁（读多写少的特殊场景）
private final Map<String, Order> cache = new HashMap<>();
synchronized (cache) { cache.put(...); }   // 手动控制

// ④ 不可变 Map（只读场景——最优）
Map<String, Order> immutable = Map.copyOf(orders);   // 不可变
```

## 5. ConcurrentHashMap 原理

> **背景**：ConcurrentHashMap 是并发 Map 的标准答案——JDK 8 重构为「CAS + synchronized 锁头节点」。
> **目的**：理解并发安全与高并发的来源。
> **适用范围**：所有并发 Map 场景。

### 5.1 JDK 7 vs JDK 8

| 维度 | JDK 7（Segment） | JDK 8+（CAS + 锁头） |
|------|:---:|:---:|
| 结构 | Segment 数组 + HashEntry | **与 HashMap 一致（数组+链表+红黑树）** |
| 锁粒度 | 分段锁（默认 16 段） | **桶级（单链表头）** |
| 插入空桶 | 锁（Segment） | **CAS 无锁** |
| 插入非空桶 | 锁（Segment） | **synchronized 锁头节点** |
| 读 | 无锁（volatile） | **无锁（volatile）** |
| 并发度 | 16 | **桶数（更高）** |

### 5.2 JDK 8 核心机制

```text
ConcurrentHashMap 三机制
├── ① 空桶插入：CAS（无锁——最优路径）
│   ├── compareAndSet 尝试插入
│   ├── 失败说明有竞争 → 走锁路径
│   └── 高并发大部分插入走 CAS（性能核心）
├── ② 非空桶：synchronized 锁头节点
│   ├── 只锁单个桶（不是全表）
│   ├── 不同桶可并发（桶级并发）
│   └── 锁头节点而非整个链表（粗中有细）
├── ③ 读：完全无锁
│   ├── Node 的 value/next 用 volatile
│   └── 读可见性由 volatile 保证
└── ④ 扩容：多线程协作
    ├── ForwardingNode 标记已迁移桶
    ├── 读遇 ForwardingNode → 去新数组
    └── 写协助扩容（多线程共同迁移）

关键设计
├── 不允许 null key/value（get 返回 null 无法区分）
├── size()：CounterCell + baseCount（高并发近似值）
└── 金句：CAS 无锁 + 桶级锁 + 无锁读 = 并发度最大化
```

## 6. 并发场景的写操作

```java
// ConcurrentHashMap 的原子方法（并发写推荐）
Map<String, Integer> map = new ConcurrentHashMap<>();

// ① putIfAbsent：不存在才放（原子！）
map.putIfAbsent("count", 1);

// ② compute：计算后放入（原子——函数内可读旧值）
map.compute("count", (k, v) -> (v == null) ? 1 : v + 1);

// ③ merge：合并（原子——累加场景）
map.merge("count", 1, Integer::sum);   // 经典累加

// ④ computeIfAbsent：不存在才计算（原子——缓存模式）
map.computeIfAbsent("ORD-1", k -> loadOrder(k));

// ⑤ computeIfPresent：存在才更新
map.computeIfPresent("count", (k, v) -> v - 1);

// ⚠️ 对比 HashMap：
// 非原子方法在多线程下丢更新：
Map<String, Integer> bad = new HashMap<>();
bad.merge("count", 1, Integer::sum);   // ❌ 非原子——丢累加！
```

> 🎯 **并发累加的正确姿势**：`merge(k, 1, Integer::sum)` 或 `computeIfAbsent`——原子性由 ConcurrentHashMap 保证。

## 7. computeIfAbsent 的并发差异

> ⚠️ **computeIfAbsent 的原子性差异（业务陷阱）**：

```text
HashMap vs ConcurrentHashMap 的 computeIfAbsent
├── ① HashMap（非线程安全）：
│   ├── 多线程同时 computeIfAbsent
│   ├── mappingFunction 可能执行多次！
│   └── 非幂等函数（扣款/发短信）→ 严重业务错误
├── ② ConcurrentHashMap（原子）：
│   ├── mappingFunction 只执行一次（锁保证）
│   └── 适合：缓存加载/初始化
└── ③ 场景（危险示例）：
    // ❌ HashMap 并发 computeIfAbsent（函数执行多次）
    Map<String, Integer> map = new HashMap<>();
    map.computeIfAbsent("k", k -> expensiveInit());   // 可能多次执行！
    // ✅ ConcurrentHashMap 只执行一次
    Map<String, Integer> map = new ConcurrentHashMap<>();
    map.computeIfAbsent("k", k -> expensiveInit());   // 一次

⚠️ 其他注意
├── ① 函数内不应修改该 Map（递归/死锁风险）
├── ② 函数耗时：持有锁期间阻塞其他（避免重逻辑）
└── ③ 生产：缓存初始化场景首选 computeIfAbsent
```

## 8. 并发使用决策

```text
并发 Map 决策树
开始
 ├─ 多线程共享写？
 │   ├─ 是 → ConcurrentHashMap（首选）
 │   └─ 否 → 下一步
 ├─ 只读（初始化后不写）？
 │   ├─ 是 → Map.copyOf（不可变——最优）
 │   └─ 否 → 下一步
 ├─ 读多写极少？
 │   ├─ 用 ConcurrentHashMap（简单安全）
 │   └─ 或 synchronizedMap（简单但慢）
 ├─ 需要顺序（如 LRU）？
 │   └─ ConcurrentHashMap 无顺序 → 业务锁 LinkedHashMap
 └─ 金句：并发场景第一反应 = ConcurrentHashMap（不是「加个锁的 HashMap」）

生产清单
[ ] 共享 Map 用 ConcurrentHashMap？
[ ] 累加用 merge（原子）？
[ ] 缓存加载用 computeIfAbsent？
[ ] 无 null key/value 依赖？（CHM 不允许）
[ ] 迭代安全？（CHM 弱一致性——迭代不抛 ConcurrentModificationException）
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. HashMap 非线程安全：数据覆盖/丢失/size 不准（JDK 8 修死循环但没修安全）
> 2. JDK 7 死循环：头插法 + 并发反转 → 环形链表 → CPU 100%（历史面试题）
> 3. **并发首选 ConcurrentHashMap**（JDK 8）：CAS 空桶无锁 + synchronized 锁头节点 + 无锁读
> 4. 原子方法：putIfAbsent/compute/merge/computeIfAbsent——累加用 merge
> 5. computeIfAbsent：CHM 只执行一次（HashMap 并发可能多次——非幂等函数危险）
> 6. 决策：并发写 CHM、只读 Map.copyOf、需要顺序业务锁
