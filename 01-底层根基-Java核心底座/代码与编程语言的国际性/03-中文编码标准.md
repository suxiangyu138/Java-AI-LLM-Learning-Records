## 1. 中文编码演进全景

> **背景**：中文有数万汉字——ASCII 无法表示，需要专门编码方案。中国经历了三代国家标准。
> **目的**：理解三代标准的演进逻辑与兼容关系。
> **适用范围**：中文系统的编码处理；遗留系统迁移。
> **前提假设**：2026 新系统默认 UTF-8——GB 系列主要用于遗留数据与兼容。

```text
中文编码三代
┌─────────────────────────────────────────────┐
│ GB2312（1980）                               │
│ ├── 6763 个汉字（常用字）                     │
│ ├── 双字节编码，兼容 ASCII                    │
│ └── 简体中文为主                            │
├─────────────────────────────────────────────┤
│ GBK（1993）                                  │
│ ├── 21886 个汉字（含繁体/生僻字）             │
│ ├── 向下兼容 GB2312                          │
│ └── Windows 中文系统默认                      │
├─────────────────────────────────────────────┤
│ GB18030（2000/2022）                         │
│ ├── 全 Unicode 覆盖（含少数民族文字/Emoji）   │
│ ├── 1/2/4 字节变长编码                        │
│ ├── 中国强制标准（新系统必须支持）             │
│ └── 完全兼容 GB2312/GBK                      │
└─────────────────────────────────────────────┘
```

## 2. GB2312：第一代国家标准

### 2.1 基本设计

> **背景**：1980 年发布（GB 2312-80）——中国第一个汉字编码国家标准。
> **目的**：为简体中文建立标准编码。
> **适用范围**：常用汉字与符号（6763 字）。
> **局限**：不含繁体/生僻字/少数民族文字。

```text
GB2312 结构
├── 编码：双字节（每个字节 0xA1-0xFE）
├── 汉字：6763 个
│   ├── 一级汉字：3755 个（按拼音排序）
│   └── 二级汉字：3008 个（按部首排序）
├── 符号：682 个（标点/数字/字母）
├── 分区（94 区 × 94 位）
│   ├── 01-09 区：符号
│   ├── 16-55 区：一级汉字
│   └── 56-87 区：二级汉字
└── 兼容：ASCII（0x00-0x7F 不变）

示例
├── "中" = 区位 54-48 → GB2312 字节 D6 D0
├── "文" = 区位 46-36 → GB2312 字节 CE C4
└── 特点：双字节高位均 ≥ 0xA1（与 ASCII 区分）
```

## 3. GBK：汉字扩充

### 3.1 设计背景

> **背景**：1993 年发布——为覆盖更多汉字（繁体/生僻字/扩展区）。
> **目的**：扩充 GB2312 的汉字覆盖。
> **适用范围**：Windows 中文系统默认编码（GBK ≈ CP936）。
> **不适用场景**：新系统（GB18030/UTF-8 更完整）。

```text
GBK 的扩充
├── 汉字：21886 个（+15123 个）
│   ├── 繁体字（Big5 兼容区）
│   ├── 生僻字/异体字
│   └── 扩展 A 区部分
├── 符号：扩充（含部分日文假名）
├── 兼容：GB2312 全部保留（向后兼容）
└── 特点：
    ├── 首字节：0x81-0xFE
    ├── 次字节：0x40-0xFE（注意含 ASCII 范围！）
    └── ⚠️ 与 UTF-8 无法相互识别（需转换）

GBK 的历史地位
├── 2000s 中文 Windows 默认（记事本/文件系统）
├── 大量遗留数据/文件是 GBK
├── 2026 现状：新系统 UTF-8，旧数据仍需 GBK 转换
└── 金句：GBK 是「必须能读」的编码（遗留数据）
```

## 4. GB18030：强制国家标准

### 4.1 设计

> **背景**：2000 年发布（最新版 2022）——中国强制国家标准（新系统必须支持）。
> **目的**：覆盖全部 Unicode 字符（含少数民族文字/Emoji）。
> **适用范围**：中国境内销售/使用的信息系统（强制）。
> **特点**：变长编码（1/2/4 字节）——与 UTF-8 对应但字节不同。

```text
GB18030 的四字节体系
├── 1 字节：0x00-0x7F（兼容 ASCII）
├── 2 字节：0x81-0xFE + 0x40-0xFE（兼容 GBK）
├── 4 字节：0x81-0xFE × 2（Unicode 补充平面）
│   └── 覆盖：BMP 外字符（Emoji/生僻字/CJK 扩展）
└── 特点：
    ├── 与 Unicode 一一对应（可双向转换）
    ├── 与 UTF-8 不同字节（GB18030 的 "中" 仍是 D6 D0）
    └── ⚠️ 不是 UTF-8 的别名——是独立的编码！

强制要求（2022 版）
├── 中国境内销售的信息系统必须支持
├── 政府/公共服务系统强制
└── 但实际使用：互联网生态仍以 UTF-8 为主
```

## 5. 汉字编码原理：区位码

### 5.1 区位码是什么

> **背景**：GB2312 用「区 + 位」定位汉字——每个汉字有唯一的区位号。
> **目的**：理解汉字在 GB 编码中的组织方式。
> **适用范围**：汉字编码的底层原理理解。

```text
区位码结构
├── 区（01-94）：行
├── 位（01-94）：列
├── 汉字 = 区号 + 位号（如 中 = 54区 48位）
├── 字节计算：
│   ├── 区号 + 0xA0 = 首字节（54 + 0xA0 = 0xD6）
│   └── 位号 + 0xA0 = 次字节（48 + 0xA0 = 0xD0）
└── 所以 "中" = D6 D0（区位码 + 0xA0 偏移）

编程意义
├── 拼音排序依据：一级汉字按拼音排序（区位序 = 拼音序）
├── 汉字转区位：查表/计算（现代编程用 Unicode 即可）
└── ⚠️ 现代开发不需要手算区位——理解即可（Unicode 统一处理）
```

## 6. GBK vs UTF-8 工程选择

### 6.1 对比

| 维度 | GBK | UTF-8 |
|------|:---:|:---:|
| 汉字字节 | 2 字节（固定） | 3 字节 |
| 英文字节 | 1 字节 | 1 字节 |
| 覆盖 | 2 万+ 汉字 | 全 Unicode |
| 国际化 | 仅中文 | **全球** |
| 2026 定位 | 遗留兼容 | **事实标准** |
| 数据库 | 已淘汰 | **默认（utf8mb4）** |

### 6.2 工程决策

```text
什么时候用 GBK（2026）
├── ① 读取遗留数据（老系统导出的文件/数据库）
├── ② 与遗留系统对接（接口仍是 GBK）
├── ③ 老 Windows 文件（记事本 GBK 保存的历史文件）
└── ④ 特殊硬件/设备（打印/扫描等仍用 GBK）

新系统决策（2026）
├── 一律 UTF-8（代码/文件/数据库/接口）
├── 边界转换：读 GBK 数据 → 转 UTF-8 存储
├── 数据库：utf8mb4（MySQL）/ UTF8（PostgreSQL）
├── HTTP：Content-Type: text/html; charset=utf-8
└── Java 源码：UTF-8（编译器默认）

转换命令
# 文件编码转换（iconv 通用）
iconv -f GBK -t UTF-8 old.txt -o new.txt
# 批量转换目录（find + iconv 脚本）
```

## 7. 中文乱码的根源与修复

### 7.1 乱码的四种形态

```text
中文乱码的典型形态（识别根因）
├── ① 锟斤拷：UTF-8 字节被按 GBK 解码（或反之）
│   ├── 特征：大量替换字符（U+FFFD 的 GBK 表示）
│   └── 根源：编码转换错误
├── ② 鈥斺€：UTF-8 按 GBK 读的经典形态
├── ③ ？？？：编码信息丢失（已替换为 ?）
│   └── 根源：数据已损坏（不可恢复！）
├── ④ 乱码但可读：双字节错位（如 中文变 中文乱）
└── ⑤ 正常显示但程序报错：BOM 问题（EF BB BF）

识别方法
├── ① 看特征（锟斤拷 = UTF-8→GBK 错误）
├── ② 用工具检测：file 命令 / enca / Python chardet
├── ③ 十六进制查看：hexdump -C（看实际字节）
└── ④ 尝试解码：先确定「源编码」再转换
```

### 7.2 修复流程

```bash
# 修复中文乱码的标准流程
# ① 确定源编码（file 命令提示）
file old.txt
# old.txt: ISO-8859 text, with CRLF line terminators（提示非 UTF-8）

# ② 尝试 GBK 解码
iconv -f GBK -t UTF-8 old.txt -o fixed.txt

# ③ 验证结果
file fixed.txt        # 应为 UTF-8 Unicode text
head -5 fixed.txt     # 人工确认无乱码

# Python 检测（不确定编码时）
python3 -c "
import chardet
print(chardet.detect(open('old.txt','rb').read()))"

# Java 读取 GBK 文件（正确处理）
try (BufferedReader reader = Files.newBufferedReader(
        Paths.get("old.txt"), Charset.forName("GBK"))) {
    // 读取后内容已是 Unicode（String）
}
```

> ⚠️ **关键认知**：**乱码一旦经过「？替换」或多次错误转换，原始信息不可恢复**——预防（明确编码）远胜修复（猜编码）。数据库/文件读写必须显式指定编码。

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 中文编码三代：GB2312（6763 字）→ GBK（21886 字）→ GB18030（全 Unicode，强制标准）——逐代兼容
> 2. 区位码原理：汉字 = 区号+位号（+0xA0 得字节）——理解即可，现代用 Unicode
> 3. GB18030 是独立的 1/2/4 字节编码（不是 UTF-8 别名）——"中" 仍是 D6 D0
> 4. **2026 决策：新系统一律 UTF-8，GBK 只用于遗留数据读取**（iconv 转换）
> 5. 乱码识别：锟斤拷 = UTF-8→GBK 错误；？= 数据已损坏不可恢复
> 6. 预防远胜修复：文件/数据库读写**显式指定编码**（Java Charset/iconv/chardet）
