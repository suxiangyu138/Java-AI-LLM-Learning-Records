## 1. 编码的本质

> **背景**：计算机只懂二进制——字符必须编码为字节序列才能存储与传输。
> **目的**：理解「字符 → 字节」的映射机制，这是所有乱码问题的根源。
> **适用范围**：所有文本处理场景。
> **前提假设**：编码是「约定」——收发双方用同一编码才不会乱码。

```text
编码的本质
├── 字符（人类可读）→ 码点（编号）→ 字节序列（存储/传输）
├── "A" → 65 → 0x41（1 字节）
├── "中" → 20013 → UTF-8: E4 B8 AD（3 字节）/ GBK: D6 D0（2 字节）
├── ⚠️ 同一个字符在不同编码下字节不同！
└── ⚠️ 解码用错编码 = 乱码（编码是约定，双方一致才行）
```

| 关键认知 | 说明 |
|---------|------|
| **字符 vs 字节** | 字符是语义，字节是存储——之间隔着编码 |
| **编码一致性** | 写入用 A 编码、读取用 B 编码 = 乱码 |
| **无自描述** | 文件本身不声明编码（需外部约定/嗅探） |

## 2. ASCII：英文字符集始祖

### 2.1 基本设计

> **背景**：ASCII（American Standard Code for Information Interchange）1963 年发布——计算机字符编码的始祖。
> **目的**：为英文字符建立标准编码。
> **适用范围**：英文字母、数字、基本符号。
> **局限**：只有 128 个字符（7 位）——装不下其他语言。

```text
ASCII 结构（7 位 128 个）
├── 0-31：控制字符（换行 10/回车 13/Tab 9）
├── 32：空格
├── 33-47：标点（! " # $ % & ' ( ) * + , - . /）
├── 48-57：数字 0-9
├── 58-64：标点（: ; < = > ? @）
├── 65-90：大写 A-Z
├── 91-96：标点（[ \ ] ^ _ `）
├── 97-122：小写 a-z
└── 123-126：标点（{ | } ~）

关键值（面试必背）
├── 'A' = 65 = 0x41
├── 'a' = 97 = 0x61（差 32）
├── '0' = 48 = 0x30
├── '\n' = 10 / '\r' = 13 / Tab = 9
└── 空格 = 32
```

### 2.2 ASCII 的遗产

```text
ASCII 的深远影响（2026 依然存在）
├── ① 编程语言关键字全部 ASCII（if/for/class）
├── ② 协议头 ASCII（HTTP 方法/头字段）
├── ③ UTF-8 完全兼容 ASCII（前 128 个不变）
├── ④ 大小写转换靠 ±32（'a'-'A' = 32）
├── ⑤ 判断数字：'0' <= c <= '9'
└── ⑥ 2026 新进展：C++ P3688R6 提案标准化 ASCII 工具函数
    （ascii_is_digit/ascii_to_lower 等——明确 ASCII 范围 c<=0x7F）
```

## 3. 各国扩展编码：混乱时代

### 3.1 为什么需要扩展

> ⚠️ **ASCII 的局限**：128 个字符只够英文——非英语国家必须扩展编码，于是出现了「各搞一套」的混乱时代。

```text
各国扩展编码（1980s）
├── 中国：GB2312（1980）/ GBK（1993）
├── 日本：JIS X 0208（Shift-JIS）
├── 韩国：EUC-KR
├── 俄罗斯：KOI-8
├── 欧洲：Latin-1（ISO-8859-1）/ Latin-2
└── 台湾：Big5（繁体）

混乱的后果
├── ① 同一字节在不同编码中含义不同
├── ② 跨平台/跨语言文档必乱码
├── ③ 编码检测靠猜（启发式嗅探）
└── ④ 「乱码」成为 1990s-2000s 的日常
```

### 3.2 扩展编码的两种思路

```text
两种扩展方案
├── 方案 1：高位扩展（单字节 → 双字节）
│   ├── 保留 ASCII（0-127 不变）
│   ├── 128-255 用于本国字符
│   └── 代表：GB2312/Latin-1（1 字节）/GBK（2 字节）
├── 方案 2：全量重编（不兼容 ASCII）
│   └── 代表：EBCDIC（IBM 大型机）
└── 主流：方案 1（兼容 ASCII 是生存基础）

扩展编码的致命问题
├── ⚠️ 互不兼容：GBK 的字节在 JIS 里是另一个字符
├── ⚠️ 编码检测难：同样的字节流有多种可能
└── ⚠️ 无法容纳所有语言：GBK 装不下日文
```

## 4. Unicode 革命

### 4.1 Unicode 的设计

> **背景**：1991 年 Unicode 联盟成立——目标：**每个字符一个唯一码点，终结编码混乱**。
> **目的**：全球所有书写系统的统一编码。
> **适用范围**：所有现代系统（操作系统/编程语言/Web）。
> **前提假设**：Unicode 是「字符集」（编号方案），不是「编码」（字节方案）——字节方案是 UTF。

```text
Unicode 的核心设计
├── ① 码点（Code Point）：每个字符一个唯一编号
│   ├── "A" → U+0041
│   ├── "中" → U+4E2D
│   └── "😊" → U+1F60A
├── ② 覆盖：14 万+ 字符（世界上几乎所有书写系统）
├── ③ 17 个平面：每平面 65536 个码点
│   ├── 平面 0（BMP）：基本多文种平面——常见字符
│   └── 平面 1+：补充平面（Emoji 等）
├── ④ 与 ISO/IEC 10646 国际标准对应
└── ⑤ 2026 仍在扩充（新字符随版本增加）

Unicode 的两层概念（关键区分）
├── 字符集（Unicode）：字符 → 码点的映射
└── 编码（UTF）：码点 → 字节的映射
→ 金句：Unicode 定义「是什么」，UTF 定义「怎么存」
```

### 4.2 Unicode 的意义

```text
Unicode 革命的三重价值
├── ① 统一：一个码点体系容纳全球文字
├── ② 唯一：同一个字符在任何系统都是同一个码点
├── ③ 可扩展：新字符追加新码点（不破坏已有）
└── 影响：现代操作系统/编程语言/Web 全部 Unicode 化
```

## 5. UTF 家族：Unicode 的传输格式

### 5.1 三种 UTF 对比

| 编码 | 字节数 | 特点 | 适用 |
|------|:---:|------|------|
| **UTF-8** | 1-4 变长 | 兼容 ASCII、自同步 | **互联网标准（Web >98%）** |
| **UTF-16** | 2 或 4 | 定长为主 + 代理对 | Java char/Windows 内部 |
| **UTF-32** | 4 定长 | 简单但浪费 | 罕见（内部处理） |

### 5.2 UTF-8 为什么成为标准（2026）

```text
UTF-8 的四大优势
├── ① 兼容 ASCII：前 128 个码点 1 字节——英文文本零开销
├── ② 自同步：从任意字节开始可正确解析（损坏不扩散）
├── ③ 无字节序问题：单字节流（无 BOM 歧义）
├── ④ 变长高效：英文 1 字节/中文 3 字节/Emoji 4 字节

UTF-8 字节模式
├── 0xxxxxxx                  （1 字节，ASCII）
├── 110xxxxx 10xxxxxx         （2 字节，欧洲字符）
├── 1110xxxx 10xxxxxx 10xxxxxx （3 字节，中文等 BMP）
└── 11110xxx 10xxxxxx ...     （4 字节，Emoji 等补充平面）

UTF-16 的特点（Java 相关）
├── BMP 内字符：2 字节定长
├── BMP 外（Emoji）：代理对（2 × 2 字节）
├── Java char = 16 位（一个 UTF-16 单元）
└── ⚠️ Java 处理 Emoji 需用 code point 方法（不是 char）
```

## 6. 2026 现状：UTF-8 一统天下

### 6.1 当前格局

```text
2026 编码格局
├── Web：UTF-8 占比 >98%（HTML 默认 charset）
├── 文件：现代工具默认 UTF-8（无 BOM）
├── 数据库：MySQL utf8mb4 / PostgreSQL UTF8
├── 编程语言：源码默认 UTF-8（Java 18+ 默认）
├── 遗留：GBK（中文老系统）/Latin-1（欧洲老数据）
└── 特殊：Windows 内部 UTF-16（API 层）

趋势
├── ① UTF-8 成为「唯一事实标准」（含邮箱/JSON/XML）
├── ② 新标准强制 UTF-8（ECMA-402 等规范明确）
├── ③ 遗留编码只在数据迁移场景出现
└── ④ 2026 新规范：JSON 规范强制 UTF-8（不允许其他编码）
```

### 6.2 工程基线（2026 推荐）

```text
编码工程基线
├── ① 应用内部：统一 UTF-8（代码/文件/字符串）
├── ② 边界转换：文件/数据库/网络入口出口做转换
├── ③ 显式声明：HTTP Content-Type charset=utf-8
├── ④ 数据库：MySQL 用 utf8mb4（不是 utf8！）
├── ⑤ Java 启动：-Dfile.encoding=UTF-8（Java 18+ 默认）
├── ⑥ 文件保存：UTF-8 无 BOM（见 06 篇）
└── ⑦ 用户输入：校验 + 规范化（防编码攻击）
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 编码 = 字符 ↔ 字节的约定——**收发双方不一致 = 乱码**
> 2. ASCII 关键值：'A'=65/'a'=97/'0'=48/差 32——编程基础
> 3. 各国扩展编码互不兼容是乱码时代的根源（GB2312/JIS/KOI-8 各搞一套）
> 4. Unicode 是字符集（码点）、UTF 是编码（字节）——**两者区分是面试点**
> 5. UTF-8 四大优势（兼容 ASCII/自同步/无字节序/高效）——2026 互联网标准
> 6. 工程基线：内部 UTF-8 + 边界转换 + utf8mb4 + 显式 charset
