## 1. 编码陷阱全景

> **背景**：编码问题横跨「显示乱码」与「安全漏洞」两层——前者烦人，后者致命。
> **目的**：系统识别编码陷阱，区分「麻烦」与「危险」。
> **适用范围**：所有文本处理系统。
> **前提假设**：**编码是安全边界的一部分**——不可信输入必须校验编码。

```text
编码陷阱分类
├── 显示层（乱码）：
│   ├── BOM 头（EF BB BF 多 3 字节）
│   ├── 编解码不匹配（GBK vs UTF-8）
│   └── MySQL utf8 阉割（Emoji 报错）
├── 传输层（Web）：
│   ├── Content-Type 未指定 charset
│   ├── URL 编码错误
│   └── 表单编码不一致
└── 安全层（漏洞）：
    ├── 宽字节注入（addslashes 绕过）
    ├── 非法 UTF-8 利用（编码规范化绕过）
    └── 孤立代理攻击
```

## 2. BOM 陷阱

### 2.1 什么是 BOM

> **背景**：BOM（Byte Order Mark）是文件开头的字节序标记——UTF-8 的 BOM 是 EF BB BF。
> **目的**：理解 BOM 的来源与危害。
> **适用范围**：文件读写/解析场景。
> **前提假设**：现代标准（UTF-8 无 BOM）vs 微软传统（UTF-8 带 BOM）。

```text
BOM 的本质
├── UTF-8 BOM：EF BB BF（3 字节，Unicode 字符 U+FEFF）
├── 目的（历史）：标记字节序/编码（UTF-16 需要）
├── 现代问题：UTF-8 无需 BOM（单字节流无字节序问题！）
├── ⚠️ 但 Windows 记事本默认保存带 BOM
└── ⚠️ BOM 在程序里是「看不见的 3 个字符」——解析异常！

BOM 引发的事故
├── ① JSON 解析失败：第一个 key 前有隐藏字符
├── ② Java 读取：字符串首字符异常（﻿）
├── ③ Shell 脚本：#!/bin/bash 前有 BOM → command not found
├── ④ CSV 首列名带 BOM（Excel 导出常见）
├── ⑤ 数据库首行异常（导入文件带 BOM）
└── ⑥ HTTP 响应开头带 BOM（渲染空白/JSON 失败）
```

### 2.2 BOM 的检测与处理

```bash
# 检测 BOM
hexdump -C file.txt | head -1
# 00000000  ef bb bf 48 65 6c ...（EF BB BF = BOM！）
# 或 file 命令：file file.txt（显示 "with BOM"）

# 去除 BOM
sed -i '1s/^\xEF\xBB\xBF//' file.txt    # Linux
dos2unix file.txt                        # 一并转换行符

# Java 处理（读取时剥离）
public static String readUtf8(Path path) throws IOException {
    String content = Files.readString(path, StandardCharsets.UTF_8);
    if (content.startsWith("﻿")) {
        content = content.substring(1);   // 剥离 BOM
    }
    return content;
}

# 编辑器设置（预防）
# VS Code：右下角 UTF-8 → 保存为 UTF-8（无 BOM）
# IDEA：Settings → File Encodings → UTF-8（无 BOM）
```

## 3. MySQL 的 utf8 陷阱

### 3.1 utf8 vs utf8mb4

> ⚠️ **MySQL 经典陷阱**：`utf8` 是「阉割版 UTF-8」——只支持 3 字节（BMP 内字符），**Emoji 直接报错**：

```text
MySQL 字符集真相
├── utf8（utf8mb3）：最多 3 字节
│   ├── 中文/英文/日文（BMP 内）→ OK
│   └── Emoji/生僻字（补充平面）→ ❌ 报错/变 ??
├── utf8mb4：完整 4 字节（真正的 UTF-8）
│   ├── Emoji/补充平面 → OK
│   └── 2026 标准选择
└── ⚠️ 历史原因：MySQL 早期实现限 3 字节——utf8mb4 是后补

Emoji 写入 utf8 列的后果
├── ① 报错：Incorrect string value: '\xF0\x9F...'
├── ② 静默变 ?（取决于模式）
├── ③ 数据损坏（不可恢复！）
└── ④ 2000s 的经典事故：「Emoji 存不进数据库」
```

### 3.2 完整配置

```sql
-- 数据库/表/列三级配置
CREATE DATABASE app_db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
ALTER TABLE orders CONVERT TO CHARACTER SET utf8mb4;
-- 连接字符集
SET NAMES utf8mb4;
```

```yaml
# Spring Boot 数据源配置
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/app_db
         ?useUnicode=true&characterEncoding=utf8&serverTimezone=UTC
    # ⚠️ characterEncoding=utf8 在连接层面 = utf8mb4（JDBC 约定）
    # 但显式用 utf8mb4 更清晰（部分驱动版本）
```

```text
迁移检查（老库 utf8 → utf8mb4）
├── ① 索引长度：utf8mb4 每字符 4 字节——索引超长需改（767 字节限制）
├── ② 连接参数：JDBC/PHP 连接字符集同步
├── ③ 排序规则：utf8mb4_unicode_ci vs _general_ci（unicode 更准）
├── ④ 备份先行：字符集迁移有风险
└── ⑤ 验证：写入 Emoji 测试
```

## 4. HTTP 与 Web 编码

### 4.1 Content-Type 的 charset

```text
HTTP 编码三要素（缺一乱码）
├── ① 响应：Content-Type: text/html; charset=utf-8
├── ② 请求：表单提交编码（application/x-www-form-urlencoded 默认 UTF-8）
├── ③ 存储/处理：服务端内部编码一致
└── ⚠️ 浏览器默认按 Content-Type 解析——不指定可能乱猜

服务端设置
├── Spring：HttpMessageConverter 默认 UTF-8（JSON）
├── 响应头：produces = "application/json;charset=UTF-8"
├── 容器：Tomcat URIEncoding=UTF-8（URL 参数！）
└── ⚠️ Tomcat 8+ 默认 UTF-8（老版本默认 ISO-8859-1）
```

### 4.2 URL 编码

```text
URL 编码（percent-encoding）
├── 中文/特殊字符在 URL 中必须编码
├── 编码规则：UTF-8 字节 → %XX
├── Java：URLEncoder.encode(s, "UTF-8")
├── JS：encodeURIComponent(s)
├── ⚠️ 编码错误导致：
│   ├── 中文参数乱码（服务端拿不到正确值）
│   ├── 特殊字符截断（# & 等被解析）
│   └── 注入（路径穿越等）
└── 解码统一：服务端按 UTF-8 解码（Tomcat URIEncoding）

# 错误示例（中文直接拼 URL）
# http://api.com/search?kw=中文  ← 浏览器会自动编码
# ⚠️ 代码里必须显式编码：URLEncoder.encode("中文", "UTF-8")
```

## 5. 宽字节注入

### 5.1 攻击原理

> ⚠️ **宽字节注入（Wide Byte Injection）**：多字节编码下，转义函数被「吃掉转义符」绕过——经典 PHP 漏洞（也是所有多字节系统的警示）：

```text
攻击链路（经典 PHP + GBK 场景）
├── ① 开发者用 addslashes() 转义输入（防 SQL 注入）
│   → 单引号 ' 变成 \'
├── ② 攻击者输入：%bf%27（GBK 中 0xbf5c 是一个汉字）
│   → %bf + \（0x5c）组合成 GBK 汉字「縗」
│   → 单引号 ' 逃出转义！
├── ③ 结果：转义被绕过 → SQL 注入成功
└── ④ 本质：**字节级转义 vs 字符级解析的错位**

其他场景
├── ① PHP + GBK：addslashes 绕过
├── ② MySQL + 连接字符集：SET NAMES GBK 时危险
├── ③ 任何「字节转义 + 多字节解析」的组合
└── ④ 现代防护：参数化查询（根本解法）
```

### 5.2 防护

```text
宽字节注入防护
├── ① 根本解法：参数化查询（PreparedStatement）
│   → 数据与 SQL 分离，转义问题消失
├── ② 连接字符集：显式 utf8mb4（避免 GBK 歧义）
├── ③ 输入校验：白名单 + 编码校验
├── ④ 不使用字节级转义函数（addslashes 类）
└── ⑤ 现代框架：ORM 默认参数化（MyBatis #{} 而非 ${}）

MyBatis 注意
├── #{} 参数化（安全）
├── ${} 字符串拼接（⚠️ 注入风险——禁止用户输入用）
└── 动态表名/列名场景：白名单校验后拼接
```

## 6. 非法 UTF-8 与攻击面

### 6.1 非法 UTF-8 的风险

```text
非法 UTF-8 的三种危险形态
├── ① 过长的编码（Overlong Encoding）：
│   ├── "/" 正常是 0x2F
│   ├── 恶意：C0 AF（2 字节表示 ASCII 字符）
│   └── 风险：绕过路径/过滤器（WAF 绕过）
├── ② 孤立代理（Lone Surrogate）：
│   ├── 单独的 D800-DFFF（无配对）
│   └── 风险：解析器差异（有的接受有的拒绝）
├── ③ 非法字节序列：
│   ├── 无效续字节/超范围
│   └── 风险：解析器行为不一致 → 绕过
└── 本质：**不同解析器对非法 UTF-8 的处理不同 → 校验绕过**

典型攻击
├── ① WAF 绕过：恶意编码让 WAF 看不到危险模式
├── ② 路径规范化绕过：%c0%ae%c0%ae/（过长编码的 ..）
├── ③ 编码混淆注入：混合编码绕过过滤器
└── ④ 存储型 XSS：非法编码存入 → 前端解析异常
```

### 6.2 防护实践

```java
// Java 严格校验 UTF-8（安全要点）
public static boolean isValidUtf8(byte[] bytes) {
    try {
        StandardCharsets.UTF_8.newDecoder()
            .onMalformedInput(CodingErrorAction.REPORT)
            .onUnmappableCharacter(CodingErrorAction.REPORT)
            .decode(ByteBuffer.wrap(bytes));
        return true;
    } catch (CharacterCodingException e) {
        return false;   // 非法 UTF-8 → 拒绝
    }
}

// 或者使用 CharsetDecoder 持续解码（流式）
// ⚠️ 原则：
// ① 用户输入入口统一校验编码
// ② 拒绝非法输入（或替换为 U+FFFD——明确策略）
// ③ 不信任「看起来正常」的字节流
// ④ 所有解析器统一严格模式
```

```text
编码安全基线（2026）
├── ① 入口校验：所有外部输入先验证 UTF-8 合法性
├── ② 规范化：NFC 规范化（防视觉混淆/等价绕过）
├── ③ 白名单优先：文件名/路径等用白名单字符
├── ④ 参数化查询：SQL 注入根本防护
├── ⑤ WAF 编码检查：不要只匹配字面模式
├── ⑥ 存储统一：数据库 utf8mb4 + 应用内 UTF-8
└── ⑦ 输出编码：响应 Content-Type 显式 charset
```

## 7. 编码安全防护清单

```text
编码安全总检查（上线前过一遍）
[ ] 数据库：utf8mb4（非 utf8！）+ 连接字符集一致
[ ] HTTP：所有响应 Content-Type 带 charset=utf-8
[ ] URL 参数：显式编码（URLEncoder/encodeURIComponent）
[ ] SQL：全部参数化（MyBatis #{}，无 ${} 用户输入）
[ ] 输入校验：入口统一 UTF-8 合法性校验
[ ] 规范化：NFC 规范化（比较/存储前）
[ ] 文件读取：显式指定编码（Charset 参数）
[ ] BOM 处理：解析前剥离（或保存无 BOM）
[ ] 日志脱敏：中文正常记录（编码一致）
[ ] 遗留 GBK 数据：边界转换 + 验证
[ ] 无字节级转义函数（addslashes 类）
[ ] 测试：Emoji/生僻字/非法 UTF-8 全链路
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 编码陷阱三层：显示（乱码）/传输（Web）/安全（漏洞）——**安全层最致命**
> 2. BOM：EF BB BF 是「看不见的 3 个字符」——JSON/脚本/CSV 解析异常；保存无 BOM
> 3. **MySQL utf8 是阉割版（3 字节）**——Emoji 报错/变 ?；必须 utf8mb4（数据库/表/连接三级）
> 4. 宽字节注入：字节级转义 vs 字符级解析的错位——**根本防护是参数化查询**
> 5. 非法 UTF-8 三种形态（过长编码/孤立代理/非法序列）——解析器差异 = 校验绕过；入口统一校验
> 6. 编码安全基线：入口校验 + NFC 规范化 + 参数化 + utf8mb4 + 显式 charset
