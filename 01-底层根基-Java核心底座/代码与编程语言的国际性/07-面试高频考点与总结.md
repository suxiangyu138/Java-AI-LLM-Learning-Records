## 1. 面试高频题与答题框架

### 1.1 编码基础类

**Q1：ASCII、Unicode、UTF-8 的关系？**

```text
① ASCII：7 位 128 字符（1963）——只装得下英文
② Unicode：字符集——每个字符唯一码点（"中"=U+4E2D）
③ UTF-8：编码方案——码点转字节（变长 1-4 字节）
④ 关系：Unicode 定义「是什么」、UTF-8 定义「怎么存」
⑤ UTF-8 兼容 ASCII（前 128 个 1 字节）→ 互联网标准
⑥ 加分：GBK 也是编码（"中" 是 2 字节）——与 UTF-8 不同
```

**Q2：UTF-8 和 UTF-16 的区别？**

```text
① UTF-8：变长 1-4 字节、兼容 ASCII、自同步、Web 标准
② UTF-16：2 字节为主 + 代理对（Emoji 4 字节）
③ Java char = 16 位（UTF-16 单元）
④ 中文：UTF-8 3 字节 / UTF-16 2 字节
⑤ 英文：UTF-8 1 字节 / UTF-16 2 字节（浪费）
⑥ 结论：存储/传输用 UTF-8；Java 内部 char 是 UTF-16
```

**Q3：什么是代理对？Emoji 为什么特殊？**

```text
① BMP（前 65536 码点）内：UTF-16 单单元表示
② BMP 外（Emoji U+1F600+）：需两个 16 位单元 = 代理对
③ 高位代理 D800-DBFF + 低位代理 DC00-DFFF
④ Java 中 "😊" = 2 个 char（length() = 2！）
⑤ 处理：codePoint API（codePointCount/codePoints）
⑥ 金句：Java char ≠ 一个字符——char 是 UTF-16 单元
```

**Q4：GB2312、GBK、GB18030 的区别？**

```text
① GB2312（1980）：6763 汉字（常用简体）
② GBK（1993）：21886 汉字（含繁体/生僻）——Windows 默认
③ GB18030（2000/2022）：全 Unicode（1/2/4 字节）——强制标准
④ 逐代兼容（GBK 兼容 GB2312、GB18030 兼容 GBK）
⑤ 中文编码：双字节为主（"中" = D6 D0）
⑥ 2026 决策：新系统 UTF-8；GBK 读遗留数据
```

**Q5：什么是 BOM？有什么坑？**

```text
① BOM：EF BB BF（UTF-8 的字节序标记）
② 来源：Windows 记事本默认保存带 BOM
③ 坑：JSON 解析失败/脚本 command not found/CSV 首列异常
④ 处理：保存无 BOM；读取时剥离（startsWith("﻿")）
⑤ 金句：UTF-8 无需 BOM（单字节流无字节序问题）——纯历史包袱
```

### 1.2 Java 实践类

**Q6：Java 中怎么正确处理 Emoji？**

```text
① 认识：Emoji 是代理对（2 个 char）
② length() 返回 2——用 codePointCount() 得真字符数
③ substring 会切坏——用 codePoints() 遍历
④ Character.toChars(cp) 码点转字符
⑤ 判断：Character.isEmoji(cp)（Java 21+）
⑥ 正则：\p{IsEmoji}
```

**Q7：Java 字符串默认编码是什么？**

```text
① char 内部：UTF-16（String 存储）
② 字节转换：Java 18+ 默认 UTF-8（JEP 400）
③ Java 1-17：平台默认（Windows GBK/Linux UTF-8——坑！）
④ 遗留：-Dfile.encoding=UTF-8 显式指定
⑤ 最佳实践：getBytes 显式传 Charset（不依赖默认）
⑥ 金句：显式指定编码是 Java 编码处理的铁律
```

**Q8：怎么把 GBK 文件转成 UTF-8？**

```text
① Java：new String(bytes, GBK).getBytes(UTF_8)
② 或 Files.readString(path, Charset.forName("GBK"))
③ 命令行：iconv -f GBK -t UTF-8 old.txt -o new.txt
④ 检测编码：file 命令 / Python chardet
⑤ ⚠️ 先确定源编码再转换（猜错 = 二次损坏）
⑥ 金句：乱码经过 ? 替换后不可恢复——预防远胜修复
```

**Q9：MySQL 的 utf8 和 utf8mb4 有什么区别？**

```text
① utf8（utf8mb3）：3 字节——Emoji 报错/变 ?
② utf8mb4：4 字节——完整 UTF-8（Emoji/生僻字 OK）
③ 历史：MySQL 早期实现限 3 字节
④ 配置：数据库/表/连接三级统一 utf8mb4
⑤ 迁移注意：索引长度（767 字节限制）+ 排序规则
⑥ 金句：新系统一律 utf8mb4——「utf8 是阉割版」
```

### 1.3 国际化类

**Q10：什么是 Locale？为什么不能依赖默认？**

```text
① Locale = 语言 + 地区（zh_CN/en_US）——决定格式化
② 格式化差异：数字/日期/货币/排序随 Locale 变
③ 不能依赖默认：服务器 Locale 变化 = 输出变化（事故源）
④ 显式指定：所有格式化 API 传 Locale（Locale.ROOT 兜底）
⑤ 用户 Locale：Accept-Language 头贯穿请求
⑥ 金句：Locale 是贯穿请求的上下文，不是启动时定死的全局
```

**Q11：时区处理的最佳实践？**

```text
① 存储统一 UTC（ISO 8601）——数据库/接口
② 展示按用户时区转换（ZoneId）
③ 绝不存本地时间（无时区信息 = 歧义）
④ 夏令时：ZoneId 自动处理（别手写偏移）
⑤ 数据库：TIMESTAMP WITH TIME ZONE
⑥ 金句：存储 UTC、展示转换——两端分离
```

**Q12：国际化项目中文案怎么管理？**

```text
① 不硬编码：所有用户可见文本走资源文件
② 资源命名：messages_zh_CN.properties（语言_地区）
③ 占位符：{0}/{1}（翻译顺序可能变！）
④ 逐级回退：zh_CN → zh → 默认
⑤ 翻译完整性：key 数量 CI 检查
⑥ 文化差异：长度膨胀/图标/占位符顺序
```

### 1.4 安全类

**Q13：什么是宽字节注入？怎么防护？**

```text
① 原理：字节级转义被多字节编码「吃掉转义符」
② 经典：PHP addslashes + GBK（%bf%27 绕过）
③ 本质：转义函数与编码解析的错位
④ 根本防护：参数化查询（PreparedStatement/#{}）
⑤ 其他：连接字符集 utf8mb4 + 输入校验
⑥ 金句：数据与 SQL 分离——转义问题自然消失
```

**Q14：非法 UTF-8 有什么安全风险？**

```text
① 过长编码（C0 AF 表示 /）——绕过 WAF/过滤器
② 孤立代理（单独 D800-DFFF）——解析器差异
③ 非法序列——不同解析器行为不一致
④ 风险：校验绕过/路径穿越/存储型 XSS
⑤ 防护：入口统一严格校验（REPORT 模式）
⑥ 规范化：NFC（防视觉混淆）
```

## 2. 代码题实战

**题 1：输出什么？**

```java
String s = "你好😊";
System.out.println(s.length());          // ? 5（2+2+1——😊 是代理对）
System.out.println(s.codePointCount(0, s.length()));  // ? 3（真字符数）
// 解析：length 是 UTF-16 单元数；codePointCount 是字符数
```

**题 2：找出问题并修复**

```java
// 问题代码（Emoji 截断）
String text = "订单😊完成";
String sub = text.substring(0, 3);   // ❌ 可能切到代理对！

// 修复（按码点截取）
int[] cps = text.codePoints().limit(3).toArray();
String safe = new String(cps, 0, cps.length);   // "订单😊"
```

**题 3：编码转换**

```java
// GBK 字节 → UTF-8 字符串（正确处理）
byte[] gbkBytes = { (byte)0xD6, (byte)0xD0 };   // GBK 的 "中"
String text = new String(gbkBytes, Charset.forName("GBK"));  // "中"
byte[] utf8 = text.getBytes(StandardCharsets.UTF_8);         // E4 B8 AD
```

**题 4：判断字符类型**

```java
// 判断是否中文（Unicode 属性——比范围判断更全）
boolean isHan = Character.UnicodeScript.of(cp) == Character.UnicodeScript.HAN;
// 或正则：\p{IsHan}
```

**题 5：国际化格式化**

```java
// 数字/货币按 Locale 格式化
NumberFormat nf = NumberFormat.getCurrencyInstance(Locale.US);
nf.format(1234.5);   // $1,234.50
NumberFormat nfCN = NumberFormat.getCurrencyInstance(Locale.CHINA);
nfCN.format(1234.5); // ¥1,234.50
```

## 4. 五大常见误区

| # | 误区 | 真相 |
|---|------|------|
| 1 | 「UTF-8 和 GBK 差不多」 | 字节完全不同（"中"：3 字节 vs 2 字节）——混用必乱码 |
| 2 | 「char 就是一个字符」 | char 是 UTF-16 单元——Emoji 是 2 个 char |
| 3 | 「MySQL utf8 够了」 | 阉割版（3 字节）——Emoji 报错，必须 utf8mb4 |
| 4 | 「编码只是显示问题」 | 宽字节注入/非法 UTF-8 绕过是安全漏洞 |
| 5 | 「依赖默认编码没问题」 | 服务器/平台差异 = 输出变化——显式指定是铁律 |

## 5. 一句话总结全系列

```text
01 演进：ASCII → 各国扩展（乱码时代）→ Unicode 统一 → UTF-8 一统
02 Unicode：码点/17 平面/代理对/UTF-8 字节模式——char ≠ 字符
03 中文：GB2312 → GBK → GB18030——2026 新系统 UTF-8、GBK 读遗留
04 语言：Java 原生最强/C++ 需 ICU/PHP 靠 mbstring/JS 有 ECMA-402
05 工程：Locale 显式 + 资源文件 + UTC 存储 + 错误码返前端
06 安全：BOM/utf8mb4/宽字节注入/非法 UTF-8——编码是安全边界
07 面试：14 题框架 + 5 道代码题 + 终极速查表
```

> 🎯 **系列总结**：代码国际性 = **编码（字符如何表示）× 语言（各语言支持）× 工程（i18n 实践）× 安全（编码陷阱）** 四维能力。2026 年标准答案：**内部统一 UTF-8 + 边界显式转换 + Locale 显式指定 + 参数化查询 + utf8mb4**——掌握这套体系，乱码不是玄学、国际化不是翻译、编码安全不是选修。
