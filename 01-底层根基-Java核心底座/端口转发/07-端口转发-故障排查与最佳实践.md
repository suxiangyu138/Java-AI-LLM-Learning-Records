## 1. 故障全景：为什么「规则生效但流量不通」

> **背景**：端口转发排障的核心难点是「链路长」——客户端 → 防火墙 → NAT → 服务，任何一环断都表现为「不通」。
> **目的**：建立分层排查思维，把「猜哪里断了」变成「逐层验证」。
> **适用范围**：所有端口转发故障。
> **前提假设**：故障大概率出在「你没想到的那一层」——所以逐层验证，不凭感觉。

```text
转发完整链路（每一层都可能断）
┌────────┐  ①  ┌────────┐  ②  ┌────────┐  ③  ┌────────┐
│ 客户端   │ →  │ 防火墙   │ →  │ NAT 转发 │ →  │ 目标服务 │
│        │    │ (ufw/  │    │ (DNAT)  │    │ (监听？)│
│        │    │ 安全组) │    │ (FORWARD)│   │        │
└────────┘    └────────┘    └────────┘    └────────┘
① 防火墙放行了吗？（云安全组 + 本机防火墙）
② NAT 规则对吗？（DNAT/FORWARD/SNAT 三要素）
③ 服务在监听吗？（端口监听 + 绑定地址）

经典故障：「规则配了、端口通了、curl 却超时」
→ 大概率是 ② 的 FORWARD 或回程（SNAT）问题
```

## 2. 分层验证法（排查方法论）

### 2.1 三层验证（从外到内）

```bash
# 第 1 层：网络可达性（防火墙是否放行）
# 在客户端执行（或外部机器）
telnet <转发IP> <端口>          # TCP 连通测试
nc -vz <转发IP> <端口>          # 更清晰的测试
# 结果：通 → 防火墙 OK；不通 → 防火墙/安全组问题（先查这层）

# 第 2 层：本机/转发点验证（NAT 是否生效）
# 在转发机器上执行
ss -tlnp | grep <端口>          # 确认端口在监听（NAT 监听的是目标端口映射）
# iptables 规则确认
sudo iptables -t nat -L PREROUTING -n -v   # DNAT 规则
sudo iptables -L FORWARD -n -v             # FORWARD 放行
cat /proc/sys/net/ipv4/ip_forward          # 内核转发开关（1 = 开）

# 第 3 层：目标服务验证（服务是否在跑）
# 在目标机器上执行
ss -tlnp | grep <目标端口>      # 服务监听确认
curl http://127.0.0.1:<目标端口>  # 本地访问服务（排除服务本身问题）
```

### 2.2 回程路径验证（最容易忽略）

```text
转发是「双向的」——去程 OK 不代表回程 OK
├── 去程：客户端 → DNAT → 目标（PREROUTING）
├── 回程：目标响应 → SNAT/MASQUERADE → 客户端（POSTROUTING）
├── ⚠️ 只配 DNAT 不配 SNAT → 目标服务看到的是「原始客户端 IP」
│   → 响应直接发给客户端（不走转发机器）→ 客户端连接被重置
├── 症状特征：TCP 三次握手成功（telnet 通）但数据收不到
└── 验证：conntrack -L 看连接跟踪条目是否完整
```

## 3. 经典故障定位表

| # | 症状 | 根因 | 排查命令 | 解法 |
|---|------|------|---------|------|
| 1 | **外部不通本地通** | 防火墙/安全组未放行 | 外部 telnet + 防火墙状态 | 放行端口（三层链路都查） |
| 2 | **telnet 通但数据不通** | 回程 SNAT 缺失 | conntrack -L | 补 SNAT/MASQUERADE |
| 3 | **ip_forward 未开启** | 内核转发关闭 | `cat /proc/sys/net/ipv4/ip_forward` | `sysctl -w ...=1` + 持久化 |
| 4 | **FORWARD 默认拒绝** | 规则只配了 NAT 没配 FORWARD | `iptables -L FORWARD -n` | 显式 ACCEPT |
| 5 | **服务没监听** | 服务未启动/绑定 127.0.0.1 | `ss -tlnp` | 启动/改绑定 0.0.0.0 |
| 6 | **绑定 127.0.0.1 导致外部不通** | 服务只听本机 | `ss -tlnp` 看绑定地址 | 绑定 0.0.0.0 或走本机转发 |
| 7 | **重启后规则丢失** | 未持久化 | 重启后 `iptables -L` | iptables-persistent/save |
| 8 | **Docker 映射失败** | 端口冲突/网络模式 | docker ps + ss | 换端口/host 模式注意 |
| 9 | **转发到别的机器超时** | 目标机器防火墙拦截 | 目标机器上 tcpdump | 目标防火墙放行 |
| 10 | **UDP 转发失效** | 只配了 TCP 规则 | iptables -p udp 检查 | 补 udp 规则 |
| 11 | **客户端 IP 全是一个** | NAT 后看不到真实 IP | - | Proxy Protocol/TOA/X-Real-IP |
| 12 | **conntrack 满** | 连接跟踪表溢出 | `conntrack -S` | 调大 nf_conntrack_max |

## 4. 抓包与连接跟踪

### 4.1 tcpdump：看流量到底走到哪

```bash
# 转发机器上抓包（看流量是否到达转发点）
sudo tcpdump -i eth0 port 8080 -n        # 抓转发端口流量
# 看：客户端 SYN 是否到达？是否回 SYN-ACK？

# 目标机器上抓包（看流量是否到达目标）
sudo tcpdump -i eth0 port 80 -n          # 目标服务端口
# 对比两个抓包：能定位「流量断在哪一跳」

# 常用过滤
sudo tcpdump -i eth0 host 203.0.113.10   # 按主机
sudo tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0'  # 只看 SYN
```

### 4.2 conntrack：查看连接跟踪

```bash
# 查看连接跟踪（转发是否建立双向条目）
sudo conntrack -L | grep 8080
# 期望看到：
# tcp 6 431999 ESTABLISHED src=客户端IP dst=转发IP sport=xxx dport=8080
#   src=内网IP dst=转发IP sport=80 dport=xxx [ASSURED]

# 统计（检查表容量）
sudo conntrack -S
# entries / max 比例高 → 需要调大 nf_conntrack_max

# 动态调整
sysctl -w net.netfilter.nf_conntrack_max=1000000
```

### 4.3 排查流程图

```text
「不通」排查流程图
客户端 telnet 转发端口
├── 不通 → 防火墙/安全组（①层）
│   └── 放行后重测
├── 通 → 转发点验证（②层）
│   ├── ip_forward=1？ → 否 → 开启
│   ├── DNAT 规则在？ → 否 → 补规则
│   ├── FORWARD 放行？ → 否 → 补放行
│   └── 目标可达？ → 否 → 目标防火墙/网络
└── 通 → 目标服务验证（③层）
    ├── 服务监听？ → 否 → 启动
    ├── 绑定地址？ → 127.0.0.1 → 改绑定
    └── 本地访问 OK？ → 否 → 服务自身问题
最后：数据不通但握手通 → 回程 SNAT 检查
```

## 5. 测试工具链

### 5.1 工具清单

| 工具 | 用途 | 示例 |
|------|------|------|
| **nc (netcat)** | TCP/UDP 连通测试 | `nc -vz host 8080` |
| **telnet** | TCP 连通测试 | `telnet host 8080` |
| **curl** | HTTP 验证 | `curl -v http://host:8080` |
| **ss** | 端口监听查看 | `ss -tlnp` |
| **tcpdump** | 抓包分析 | `tcpdump -i eth0 port 8080` |
| **conntrack** | 连接跟踪 | `conntrack -L` |
| **nmap** | 端口扫描（安全视角） | `nmap -p 8080 host` |
| **iperf** | 带宽测试（性能验证） | `iperf3 -c host -p 8080` |

### 5.2 验证顺序

```bash
# 转发验证五步（从快到慢）
nc -vz 127.0.0.1 8080        # ① 本地端口监听（秒级）
nc -vz <转发IP> 8080          # ② 外部连通（防火墙层）
curl -v http://<转发IP>:8080  # ③ 应用层验证（HTTP）
tcpdump 双向抓包             # ④ 流量路径确认（疑难）
iperf3 带宽测试              # ⑤ 性能验证（生产转发）
```

## 6. 生产最佳实践

### 6.1 设计层面

```text
生产转发设计最佳实践
├── ① 转发层与业务分离：NAT/反代独立于业务机器
├── ② 高可用：转发点多活（Keepalived VIP / 云 LB）
├── ③ 性能预留：conntrack 容量按峰值 ×2 配置
├── ④ 链路可视化：监控转发链路的连通性（探活）
├── ⑤ 降级预案：转发点故障时如何切换（VIP 漂移/备节点）
└── ⑥ 规则即代码：Ansible/Terraform 管理（可审计可回滚）
```

### 6.2 运维层面

```text
生产运维最佳实践
├── ① 变更走流程：转发规则变更记录（谁/何时/为什么/到期）
├── ② 定期巡检：季度暴露面扫描 + 僵尸规则清理
├── ③ 监控告警：转发链路探活（每分钟探测，故障即告警）
├── ④ 容量监控：conntrack 使用率、转发流量、连接数
├── ⑤ 文档化：每台机器的转发规则清单（运维交接的命脉）
└── ⑥ 测试先行：生产规则先在测试环境验证（避免「规则生效流量不通」）
```

### 6.3 常见事故复盘模板

```text
转发事故复盘五问
├── ① 事故现象：什么服务不通？影响谁？
├── ② 根因：哪一层断了？（防火墙/NAT/回程/服务）
├── ③ 为什么没早发现：链路探活缺失？
├── ④ 改进：加探活？规则审计？变更流程？
└── ⑤ 沉淀：故障定位表 + 排查清单更新
→ 金句：每次转发事故都是排查方法论的一次升级
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 转发链路三层（防火墙 → NAT → 服务监听）——逐层验证，不凭感觉猜
> 2. 「握手通但数据不通」= 回程问题（SNAT/MASQUERADE 缺失）——最容易忽略的环节
> 3. 排查三板斧：telnet/nc（连通）+ tcpdump（流量路径）+ conntrack（连接跟踪）
> 4. 12 个经典故障定位表：ip_forward 未开/FORWARD 默认拒绝/绑定 127.0.0.1/重启丢规则是 TOP5
> 5. 生产实践：链路探活 + 规则清单 + 变更留痕 + 季度巡检——**规则生效流量不通的经典故障，靠测试环境先行验证根治**
