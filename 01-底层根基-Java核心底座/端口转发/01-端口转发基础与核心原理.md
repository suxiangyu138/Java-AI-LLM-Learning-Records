## 1. 端口转发的本质

> **背景**：网络服务默认只在本机端口监听——要让「别处的流量」到达它，需要转发；要让「本机的服务」被别处访问，也需要转发。
> **目的**：在不改服务代码的前提下，改变流量的到达路径。
> **适用范围**：临时调试、环境打通、服务暴露、内网访问、架构解耦。
> **不适用场景**：高频大流量生产转发（优先架构层解决）；需要应用层逻辑的转发（用反向代理）。

```text
端口转发 = 流量改道（不改变服务本身）
┌──────────┐    ┌──────────────┐    ┌──────────┐
│  客户端    │ → │  转发点       │ → │  目标服务  │
│ 访问 A 端口│   │ A → B 规则    │   │ 监听 B 端口│
└──────────┘    └──────────────┘    └──────────┘
转发点做的事：
├── ① 监听 A 端口（接收流量）
├── ② 改写目的地（发往 B 端口）
└── ③ 回传响应（对客户端透明）

本质：客户端以为在访问 A，实际服务在 B——转发层做「流量搬运」
```

| 关键认知 | 说明 |
|---------|------|
| **透明性** | 客户端无感知（以为直接访问目标） |
| **不改服务** | 服务代码零改动（转发是网络层方案） |
| **方向性** | 本地↔远程的双向搬运 |
| **协议敏感** | TCP/UDP 转发方式不同（见下节） |

## 2. TCP vs UDP：转发的差异

### 2.1 两者的本质区别

| 维度 | TCP | UDP |
|------|:---:|:---:|
| 连接 | 有连接（三次握手） | 无连接（发就完） |
| 可靠性 | 可靠（重传/有序） | 不可靠（丢包不管） |
| 状态 | 有状态（连接跟踪） | 无状态 |
| 转发实现 | 简单（连接映射） | **需显式指定（无连接概念）** |
| 典型服务 | HTTP/SSH/MySQL | DNS/游戏/视频流 |

### 2.2 转发时的差异（关键）

```text
TCP 转发：天然支持（连接级映射）
├── iptables DNAT + conntrack 自动处理
├── SSH 隧道：仅 TCP（不支持 UDP！）⚠️
├── socat：TCP/UDP 都支持
└── Nginx stream：TCP/UDP 都支持

UDP 转发：需要显式处理
├── iptables：需加 -p udp 规则
├── socat：UDP4-LISTEN:53,fork UDP4:8.8.8.8:53
├── Nginx stream：listen 53 udp
└── ⚠️ 常见遗漏：只配 TCP 不配 UDP → DNS 转发失效
```

> 🎯 **关键提示**：**SSH 隧道不支持 UDP**（如远程 DNS/视频流）——UDP 场景改用 socat/iptables/Nginx stream。

## 3. 三种转发方向

### 3.1 方向分类（理解一切转发工具的总纲）

```text
三种转发方向
┌─────────────────────────────────────────────┐
│ ① 本地转发（Local Forwarding）               │
│    把「远程的服务」映射到「本地端口」           │
│    场景：本地连远程数据库/远程 Web             │
│    代表：ssh -L、kubectl port-forward         │
├─────────────────────────────────────────────┤
│ ② 远程转发（Remote Forwarding）              │
│    把「本地的服务」暴露到「远程端口」           │
│    场景：远程调试本地服务/本地 Web 给远程看     │
│    代表：ssh -R、frp（反向穿透）               │
├─────────────────────────────────────────────┤
│ ③ 双向/网关转发（Gateway Forwarding）         │
│    公网端口 → 内网服务（流量穿越边界）          │
│    场景：路由器端口映射、云服务器转内网         │
│    代表：iptables DNAT、firewalld、Docker -p  │
└─────────────────────────────────────────────┘
```

### 3.2 方向选择决策

```text
选方向的三问
├── ① 谁需要访问谁？
│   ├── 我需要访问远程 → 本地转发（-L）
│   ├── 远程需要访问我 → 远程转发（-R）
│   └── 公网用户访问内网 → 网关转发（DNAT/frp）
├── ② 有没有跳板机？（中转节点）
│   ├── 有 → 转发可以多级串联（跳板链）
│   └── 无 → 需公网可达节点（frp 服务器）
└── ③ 长期还是临时？
    ├── 临时 → SSH 隧道（起停方便）
    └── 长期 → 系统级/工具级（systemd 托管）
```

## 4. 五种实现层级

### 4.1 层级全景

```text
端口转发五层级
┌─────────────────────────────────────────────┐
│ ⑤ 应用层：Nginx/HAProxy（HTTP 感知）          │
│    → 可做 SSL 卸载/负载均衡/路径路由           │
├─────────────────────────────────────────────┤
│ ④ 用户态工具：socat/rinetd（通用中继）        │
│    → 灵活但性能低于内核                       │
├─────────────────────────────────────────────┤
│ ③ 传输层加密：SSH 隧道（-L/-R/-D）            │
│    → 加密 + 认证 + 穿透防火墙                 │
├─────────────────────────────────────────────┤
│ ② 内核级 NAT：iptables/nftables/firewalld    │
│    → 高性能（内核态）、路由器/网关标准         │
├─────────────────────────────────────────────┤
│ ① 容器/云网络：Docker -p / K8s / 安全组       │
│    → 平台内建的端口暴露机制                   │
└─────────────────────────────────────────────┘
```

### 4.2 层级选型对比（权衡）

| 层级 | 性能 | 灵活性 | 安全性 | 适用 |
|------|:---:|:---:|:---:|------|
| 内核 NAT（iptables） | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐⭐⭐ | 网关/高性能 |
| SSH 隧道 | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 临时/加密 |
| socat/rinetd | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | 复杂协议/UDP |
| Nginx/HAProxy | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | HTTP/负载均衡 |
| Docker/K8s | 平台决定 | ⭐⭐⭐ | 平台决定 | 容器生态 |

> 🎯 **选型原则**：**高性能走内核（iptables）、加密临时走 SSH、灵活走 socat、应用逻辑走 Nginx、容器走平台内建**——按需求层级选工具，不迷信单一方案。

## 5. NAT 原理：内核级转发的根基

### 5.1 NAT 的三种类型

> **背景**：NAT（Network Address Translation，网络地址转换）是内核级端口转发的底层机制——改包头的地址/端口。
> **目的**：让内网/本机流量在穿越边界时被「重写目的地」。
> **适用范围**：iptables/nftables/firewalld 的转发实现；路由器端口映射。
> **前提假设**：需要内核开启 IP 转发（ip_forward=1）——**不开启则转发静默失败**。

```text
NAT 三种类型（iptables -t nat 链）
├── DNAT（目的地址转换）
│   链：PREROUTING（流量进来时改目的）
│   用途：公网端口 → 内网服务（端口转发核心）
│   示例：--dport 8080 → --to-destination 192.168.1.100:80
├── SNAT（源地址转换）
│   链：POSTROUTING（流量出去时改来源）
│   用途：内网出网（固定公网 IP 时）
├── MASQUERADE（动态源地址转换）
│   链：POSTROUTING
│   用途：动态公网 IP（宽带拨号）——自动取当前出口 IP
└── REDIRECT（本机重定向）
    链：PREROUTING/OUTPUT
    用途：本机端口重定向（80 → 8080，不跨机器）
```

### 5.2 内核转发的完整链路（跨机器）

```text
公网用户 → 网关 → 内网服务（完整链路）
① 公网用户访问 203.0.113.10:8080
② 网关 PREROUTING：DNAT 规则 → 目的改为 192.168.1.100:80
③ 网关 FORWARD 链：默认拒绝转发！需显式允许 ⚠️
④ 内网服务响应 192.168.1.100:80 → 回程流量
⑤ 网关 POSTROUTING：SNAT/MASQUERADE → 源改为网关 IP
⑥ 公网用户收到响应（以为是网关直接响应）

三个必配要素（缺一流量不通）：
├── ① ip_forward=1（内核转发开关）
├── ② DNAT 规则（PREROUTING 改目的）
└── ③ FORWARD 放行 + SNAT（回程路径）
→ 经典故障：配了 DNAT 忘了 FORWARD 放行 → 流量有去无回
```

### 5.3 conntrack：连接跟踪

```text
conntrack（连接跟踪）的作用
├── ① 记住已转发的连接（回程流量自动匹配）
├── ② DNAT + conntrack = TCP 转发自动双向
├── ③ 查看：conntrack -L / /proc/net/nf_conntrack
├── ④ 性能：nf_conntrack_max 限制（默认几万——高并发调大）
│   示例：sysctl -w net.netfilter.nf_conntrack_max=1000000
└── ⑤ 案例：iptables 转发调优后 QPS 12k → 35k（延迟 -60%）
```

## 6. 核心决策框架

### 6.1 场景 → 方案速查

```text
场景决策表
├── 临时访问远程数据库 → SSH -L
├── 远程调试本地服务 → SSH -R
├── 科学上网/全局代理 → SSH -D（SOCKS5）
├── 低端口（80/443）转发到高端口 → firewalld/iptables
├── 高性能生产转发 → iptables/nftables（内核态）
├── UDP 转发（DNS 等） → socat/Nginx stream（SSH 不行！）
├── Docker 服务暴露 → docker -p（平台内建）
├── K8s Pod 调试 → kubectl port-forward
├── 内网服务暴露公网（长期） → frp/ngrok
├── HTTP 负载均衡/SSL → Nginx/HAProxy
└── 穿透防火墙的加密通道 → SSH 隧道（443 伪装）
```

### 6.2 决策四问

```text
转发方案决策四问
├── ① 临时还是长期？（SSH 临时 / systemd 托管长期）
├── ② TCP 还是 UDP？（SSH 仅 TCP！）
├── ③ 要不要加密？（内网明文可 / 公网必加密）
├── ④ 性能要求？（内核级 vs 用户态 vs 应用层）
└── ⑤ 有没有公网节点？（有 → SSH/frp；无 → P2P 类工具）
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 端口转发 = 流量改道：不改服务代码，改变流量到达路径（客户端无感知）
> 2. **SSH 隧道不支持 UDP**——UDP 转发用 socat/iptables/Nginx stream
> 3. 三种方向：本地转发（访问远程）/远程转发（暴露本地）/网关转发（公网→内网）
> 4. 内核 NAT 三要素：**ip_forward=1 + DNAT + FORWARD 放行/SNAT**——缺一流量不通（经典故障）
> 5. 五层级选型：性能走内核、加密临时走 SSH、灵活走 socat、应用逻辑走 Nginx、容器走平台内建
