# 06 - 端口转发：安全与攻击面治理

## 1. 端口转发的安全风险模型

> **背景**：端口转发 = 把「原本不可达的服务」变为「可达」——每一条规则都是攻击面的一次扩大。
> **目的**：理解转发引入的风险，用工程手段把暴露面压到最小。
> **适用范围**：所有端口转发场景（系统级/容器/穿透）。
> **前提假设**：公网扫描是常态——**规则存在一天，就被扫描一天**。

```text
端口转发的风险模型
├── ① 暴露面扩大：内网/本机服务被公网可达
│   → 原本只有本机能访问的 Redis，转发后公网可扫到
├── ② 认证缺失放大：无认证服务（Redis/ES/MongoDB 默认）暴露即沦陷
├── ③ 链式攻击：转发入口被攻破 → 内网横向移动
├── ④ 规则遗忘：为调试加的转发，生产后忘记删除 → 长期暴露
└── ⑤ 扫描常态：公网端口扫描（Shodan 等）持续收集暴露服务

风险公式：暴露风险 = 服务敏感度 × 暴露时长 × 认证强度
→ 治理思路：降低每一项（敏感服务不暴露 / 临时转发即删 / 强认证）
```

| 服务类型 | 默认暴露风险 | 治理策略 |
|---------|:---:|---------|
| Web（有认证） | 🟡 | 限源 + HTTPS + 加固 |
| 数据库（MySQL/PG） | 🔴 | **禁止公网暴露**（走 VPN/SSH 隧道） |
| Redis/MongoDB（无默认认证） | 🔴🔴 | **绝不允许**（历史事故重灾区） |
| SSH（22） | 🟠 | 密钥认证 + 高位端口 + 限源 |
| 调试端口（5005/JMX） | 🔴 | 用完即关 + 仅本机绑定 |

## 2. 最小暴露原则

### 2.1 原则

> 🎯 **最小暴露**：只暴露「必须暴露的端口 × 给必须访问的人 × 在必须的时间」——三个维度都最小化：

```text
最小暴露三维度
├── ① 端口维度：只转发必要端口（不批量开）
├── ② 来源维度：限定源 IP（iptables -s / 安全组来源）
└── ③ 时间维度：临时规则用后即删（不留僵尸规则）
```

### 2.2 来源限制实战

```bash
# iptables 限定来源（只允许公司 IP 访问转发的 8080）
sudo iptables -t nat -A PREROUTING -s 203.0.113.0/24 \
    -p tcp --dport 8080 -j DNAT --to-destination 192.168.1.100:80

# firewalld 限定来源（富规则）
sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" \
    source address="203.0.113.0/24" \
    forward-port port="8080" protocol="tcp" to-port="80" to-addr="192.168.1.100"'

# 云安全组限定来源（控制台）
# 入方向：8080/tcp 来源 203.0.113.0/24（而非 0.0.0.0/0）

# Docker 仅本机绑定（调试端口场景）
docker run -p 127.0.0.1:5005:5005 myapp   # 不暴露公网
```

### 2.3 临时规则管理

```bash
# 临时规则必须「记得删」——用脚本 + 定时检查
# ① 加规则时记录
sudo iptables -t nat -A PREROUTING ... && echo "$(date) 添加 8080→100:80" >> /var/log/forward-changes.log

# ② 定期检查僵尸规则（cron 周检）
# 列出所有转发规则，人工确认是否仍需要
sudo iptables -t nat -L PREROUTING -n --line-numbers
# firewalld
sudo firewall-cmd --list-forward-ports

# ③ 删除
sudo iptables -t nat -D PREROUTING <行号>
```

## 3. 高危端口治理

### 3.1 高危端口清单

| 端口 | 服务 | 风险 | 治理 |
|:---:|------|:---:|------|
| **22** | SSH | 暴力破解重灾区 | 密钥认证 + 高位端口 + fail2ban |
| **3306** | MySQL | 拖库 | 禁止公网（走 SSH 隧道） |
| **6379** | Redis | 无认证即沦陷 | **绝对禁止公网** |
| **27017** | MongoDB | 无认证即沦陷 | 绝对禁止公网 |
| **9200** | Elasticsearch | 数据泄露 | 禁止公网 + 认证 |
| **3389** | RDP | 爆破 | 改端口 + 限源 + 2FA |
| **5005** | Java 调试 | RCE 风险 | 用完即关 + 仅本机 |
| **8080/9090** | 管理控制台 | 弱口令 | 强认证 + 限源 |

### 3.2 高危端口治理实战

```bash
# ① 扫描自己的暴露面（主动发现——比攻击者先）
sudo ss -tlnp | grep -E ':(22|3306|6379|27017|9200)\s'   # 本机监听
# 云环境：用云安全组检查入方向规则（0.0.0.0/0 的高危端口）
# 外部视角：nmap -p 22,3306,6379,27017,9200 <公网IP>

# ② SSH 加固（最常见的高危端口）
# /etc/ssh/sshd_config
PasswordAuthentication no          # 禁用密码（只密钥）
Port 2222                          # 改高位端口（降低扫描命中）
AllowUsers deploy                  # 限制用户

# ③ fail2ban（自动封禁爆破 IP）
sudo apt install fail2ban
# /etc/fail2ban/jail.local
[sshd]
enabled = true
maxretry = 5
bantime = 3600

# ④ Redis 加固（若必须暴露）
# 绑定内网 + requirepass 强密码 + rename-command 禁用危险命令
```

> 🎯 **金句**：**数据库类服务（MySQL/Redis/ES）的默认策略是「不暴露」**——远程访问走 SSH 隧道/VPN，而不是开公网端口。转发是最后手段，不是第一选择。

## 4. 认证与加密

### 4.1 转发层认证（穿透场景）

```text
frp 穿透的认证三件套（见 05 篇）
├── ① auth.token：强随机令牌（必配）
├── ② TLS 加密：transport.tls.enable = true
└── ③ 端口白名单：allowPorts 限制客户端可开端口
```

### 4.2 服务层认证（转发背后的服务也要锁）

```text
转发 ≠ 安全——背后的服务必须自带认证
├── Web 服务：HTTPS + 登录认证（Basic/OAuth）
├── SSH：密钥认证（PasswordAuthentication no）
├── 数据库：强密码 + 账号最小权限
├── 管理控制台：强口令 + 2FA + 限源
└── 金句：转发解决「可达性」，认证解决「谁能用」——两者缺一不可
```

### 4.3 加密传输

```text
公网转发的加密要求
├── ① SSH 隧道：天然加密（最省心）
├── ② frp + TLS：transport.tls.enable
├── ③ Nginx stream + SSL：四层 TLS 透传
├── ④ 明文协议（HTTP/MySQL）公网传输 = 可嗅探
└── 结论：公网转发必加密——明文协议走公网等于裸奔
```

## 5. 限流与防护

### 5.1 网络层限流

```bash
# iptables 速率限制（防端口转发被滥用）
# 每 IP 每秒最多 50 个新连接
sudo iptables -A FORWARD -p tcp -m limit --limit 50/s \
    -j ACCEPT

# 对转发到内网服务的连接做连接数限制
sudo iptables -A FORWARD -p tcp -d 192.168.1.100 --dport 80 \
    -m connlimit --connlimit-above 100 -j REJECT
```

### 5.2 应用层防护

```text
转发 + WAF/反代的组合
├── ① HTTP 转发：Nginx 前置（限流/防注入/WAF 规则）
├── ② 非 HTTP：fail2ban + 连接数限制
├── ③ 云 WAF：云厂商托管防护（有预算时）
└── ④ 监控告警：异常流量/连接数激增告警
```

## 6. 监控与审计

### 6.1 监控项

```text
转发监控四件套
├── ① 连接监控：conntrack -L / ss 查看活跃转发连接
├── ② 流量监控：接口流量异常（vnstat/nload）
├── ③ 端口监控：被转发端口的连接来源分布
├── ④ 规则审计：转发规则变更记录（谁加了/何时删）
└── 告警阈值：
    ├── 连接数激增（可能是攻击/扫描）
    ├── 来源地域异常（非业务地域）
    └── 规则变更无记录（未授权变更）
```

### 6.2 审计日志

```bash
# iptables 转发日志（记录被转发流量）
sudo iptables -A FORWARD -p tcp -d 192.168.1.100 --dport 80 \
    -j LOG --log-prefix "FW-FORWARD: " --log-level warning
# 查看：tail -f /var/log/syslog | grep FW-FORWARD

# frp 审计：frps 日志记录所有代理连接
tail -f /var/log/frps.log    # 谁连接了哪个代理、来源 IP

# SSH 隧道审计：auth.log 记录连接
tail -f /var/log/auth.log | grep -i ssh
```

### 6.3 定期安全巡检

```text
转发规则季度巡检清单
[ ] 列出所有转发规则（iptables/firewalld/Docker -p/安全组）
[ ] 逐条确认：还在用吗？来源限制了吗？认证配置了吗？
[ ] 扫描公网暴露面（nmap 高危端口）
[ ] 高危端口检查：22/3306/6379/27017/9200 是否暴露
[ ] 僵尸规则清理（调试遗留的转发）
[ ] 变更记录核对（谁加的规则与记录一致）
```

## 7. 转发规则的生命周期管理

### 7.1 生命周期五阶段

```text
转发规则生命周期
├── ① 申请：明确「为什么转发 + 暴露给谁 + 用多久」
├── ② 审批：高危端口/公网暴露需审批
├── ③ 创建：最小暴露（限源 + 认证 + 加密）
├── ④ 使用：监控 + 日志
└── ⑤ 回收：到期自动提醒 + 定期清理
→ 企业实践：规则清单 + 到期时间（如 7 天临时规则自动告警）
```

### 7.2 规则即代码（IaC）

```yaml
# 转发规则声明式管理（Ansible/Terraform 示例思路）
# 优点：可审计、可回滚、变更走评审
- name: 端口转发 8080 → 内网 80
  iptables:
    table: nat
    chain: PREROUTING
    destination_port: 8080
    jump: DNAT
    to_destination: 192.168.1.100:80
    comment: "临时转发-工单#1234-到期2026-08-15"
  when: forward_rule_enabled
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 风险模型：暴露风险 = 服务敏感度 × 暴露时长 × 认证强度——三维度都压到最小
> 2. 最小暴露三维：端口最小 × 来源最小（限 IP）× 时间最小（用后即删）
> 3. **数据库类服务默认不暴露**（MySQL/Redis/ES 走 SSH 隧道/VPN）；Redis/MongoDB 无认证公网暴露 = 历史事故重灾区
> 4. 转发解决可达性、认证解决谁能用——两层都要；公网转发必加密（明文=裸奔）
> 5. 生命周期管理：申请→审批→创建（最小暴露）→监控→回收；规则清单 + 季度巡检防僵尸规则
