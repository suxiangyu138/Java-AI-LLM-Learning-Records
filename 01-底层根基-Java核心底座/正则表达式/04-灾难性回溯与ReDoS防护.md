# 04 - 灾难性回溯与 ReDoS 防护

## 1. ReDoS 是什么

> **背景**：正则引擎的灾难性回溯是已知数十年的问题——攻击者不需要漏洞利用技巧，只需要一条「精心构造的输入」。
> **目的**：让受害者的正则匹配「永远跑不完」——CPU 100%、线程耗尽、服务不可用。
> **适用场景**：任何处理不可信输入的 Java 服务（Web 参数校验、日志解析、WAF 规则）。
> **前提假设**：**不可信输入 + 未防护的正则 = 可被攻击**。

```text
ReDoS 攻击链
├── ① 服务有一个「易回溯」的正则（如 (a+)+ 校验输入）
├── ② 攻击者构造输入：正常字符 + 不匹配结尾
│   （如 "aaaa...aX"——30 个 a 就够触发 2^30 次尝试）
├── ③ 请求处理线程卡死在正则匹配
├── ④ 并发攻击 → 线程池耗尽 → 服务拒绝服务
└── ⑤ 本质：一个「合法请求」就能打垮服务（无入侵痕迹）
```

| 特征 | 说明 |
|------|------|
| 攻击成本 | 极低（一条 HTTP 请求） |
| 检测难度 | 高（请求看起来完全合法） |
| 影响 | CPU 100% / 线程耗尽 / 服务宕机 |
| 修复成本 | 高（需要扫描 + 改写全部正则） |

## 2. 攻击机制拆解

### 2.1 触发条件（三要素）

```text
ReDoS 触发三要素（缺一不可）
├── ① 存在灾难性回溯模式：
│   嵌套量词 (a+)+ / 重叠交替 (a|a)+ / 共享字符类 (\w+\s?)+
├── ② 输入进入「失败路径」：
│   目标字符 + 一个不匹配的结尾字符（如 "aaaaX"）
├── ③ 输入长度足够（指数爆炸在 20-30 字符就开始明显）
└── 防御：破坏任一要素即可（改写模式/限长/超时/换引擎）
```

### 2.2 攻击输入构造方法

```text
构造攻击输入的思路
├── ① 识别服务使用的正则（错误信息/公开代码/黑盒测试）
├── ② 找出量词嵌套的分组（(x+)+ 结构）
├── ③ 构造：重复 x 的字符 + 一个不匹配字符
│   └── (a+)+  → "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaX"
│   └── (\w+\s?)+ → "word word word ... X"（空格模式）
├── ④ 逐步加长输入（20 → 30 → 40 字符）观察响应时间
└── ⑤ 找到「响应时间指数增长」的输入长度 → 攻击载荷
```

### 2.3 响应时间测试（判断是否易受攻击）

```text
复杂度探测（安全测试必做）
├── 输入 10 字符：耗时 1ms
├── 输入 20 字符：耗时 4ms
├── 输入 30 字符：耗时 16ms
├── 输入 40 字符：耗时 256ms     ← 指数增长！
└── 输入 50 字符：耗时 16s+      ← 灾难确认

规则：输入翻倍耗时翻倍 = 线性（安全）；
      输入 +10 耗时 ×4 = 指数（高危！）
```

## 3. 真实案例与影响

### 3.1 标志性事件

| 事件 | 详情 | 教训 |
|------|------|------|
| **Cloudflare 2019** | WAF 规则含易回溯正则 → 全球 CPU 飙至 100% → **宕机 27 分钟** | 生产 WAF 规则也要正则审查 |
| **ua-parser-js CVE-2022-25927** | `\s\s*$` 尾部空白模式 ReDoS | 看似无害的简单模式也危险 |
| **各种 npm 包 ReDoS 漏洞** | 大量流行库中招 | 依赖也要正则审计 |
| **JDK 自身** | 官方承认 O(2^N) 与 StackOverflowError 风险（JEP 8260688） | 引擎层无法根治，工程层必须防护 |

### 3.2 影响面评估

```text
受影响场景（按风险排序）
├── 🔴 Web 输入校验（手机号/邮箱/URL 校验正则——最暴露）
├── 🔴 日志解析（解析不可信日志行）
├── 🔴 WAF/防火墙规则（Cloudflare 案例）
├── 🟠 数据清洗（处理外部数据）
├── 🟡 内部工具（仅可信输入）
└── 🟢 纯内部固定文本（低风险）

→ 风险判断公式：正则复杂度 × 输入可信度 × 暴露面
```

## 4. 四层防护体系

> 🎯 **纵深防御**：单层防护不够——四层叠加才是生产级方案：

```
ReDoS 四层防护
┌──────────────────────────────────────────────┐
│ 第 1 层：模式层——写安全的正则（消除歧义）       │ ← 治本
│ 第 2 层：输入层——限制长度 + 前置校验            │ ← 拦截载荷
│ 第 3 层：运行层——执行超时（自定义引擎/线程）    │ ← 兜底
│ 第 4 层：引擎层——RE2J 线性引擎（不可信输入）    │ ← 免疫
└──────────────────────────────────────────────┘
```

| 层 | 手段 | 强度 | 说明 |
|:--:|------|:---:|------|
| 1 | 模式改写（消除嵌套量词/原子化） | ⭐⭐⭐⭐⭐ | 治本（03 篇七原则） |
| 2 | 输入长度限制 + 格式前置校验 | ⭐⭐⭐⭐ | 拦截攻击载荷 |
| 3 | 正则执行超时 | ⭐⭐⭐ | Java 无内置超时，需工程实现 |
| 4 | RE2J 引擎替换 | ⭐⭐⭐⭐⭐ | 构造保证线性 |

## 5. 输入限制与超时

### 5.1 输入长度限制（最有效的拦截）

```java
// 正则处理前校验长度（第一道拦截）
public boolean isValidEmail(String email) {
    if (email == null || email.length() > 64) {   // 长度短路
        return false;                              // 邮箱合法上限 64
    }
    return EMAIL_PATTERN.matcher(email).matches();
}

// 通用长度策略
if (input.length() > MAX_LENGTH) {
    log.warn("输入超长，拒绝处理: {} bytes", input.length());
    return REJECT;
}
```

> 🎯 **长度限制的效果**：灾难性回溯在 30-50 字符开始指数爆炸——**限制到 64-256 字符能拦截绝大多数攻击载荷**（合法输入极少超长）。

### 5.2 执行超时（Java 的实现方式）

> ⚠️ **Java 正则没有内置超时**（.NET 有 matchTimeout）——需要工程手段：

```java
// 方案 1：Future + 超时（线程池）
public boolean matchWithTimeout(Pattern p, String input, long timeoutMs) {
    ExecutorService pool = Executors.newSingleThreadExecutor();
    try {
        Future<Boolean> future = pool.submit(() -> p.matcher(input).matches());
        return future.get(timeoutMs, TimeUnit.MILLISECONDS);
    } catch (TimeoutException e) {
        log.error("正则匹配超时（疑似 ReDoS）: pattern={}, inputLen={}", p, input.length());
        return false;                     // 超时即拒绝
    } finally {
        pool.shutdownNow();               // 中断线程（重要！）
    }
}
// ⚠️ 代价：每次匹配一个线程——只用于不可信输入的高危路径

// 方案 2：RE2J 自带超时（见第 7 节）
```

### 5.3 限流与降级

```text
ReDoS 场景的限流
├── ① 接口级：含正则校验的接口限流（每 IP/每秒）
├── ② 长度级：请求体大小限制（防超大输入）
├── ③ 超时降级：匹配超时 → 返回校验失败（服务不卡）
└── ④ 熔断：异常匹配次数触发熔断（告警 + 人工）
```

## 7. RE2J：线性时间引擎

### 7.1 什么是 RE2J

> 🎯 **RE2J**：Google RE2 的 Java 移植版——DFA 引擎，**从构造上保证 O(N) 线性匹配时间**，彻底免疫 ReDoS。代价：**不支持反向引用**等特性。

```xml
<!-- 依赖 -->
<dependency>
    <groupId>com.google.re2j</groupId>
    <artifactId>re2j</artifactId>
    <version>1.8</version>
</dependency>
```

```java
// RE2J 使用（API 与 java.util.regex 类似）
import com.google.re2j.Pattern;
import com.google.re2j.Matcher;

Pattern p = Pattern.compile("(a+)+b");        // 危险模式也不怕！
Matcher m = p.matcher("aaaa...aX".repeat(100000));
m.matches();    // 线性时间完成（Java 原生会卡死！）

// RE2J 支持超时
Pattern p2 = Pattern.compile("a+", Pattern.RE2J_FLAG_NONE);
p2.matcher(input).matches();    // 超时可选
```

### 7.2 RE2J 的取舍

| 维度 | java.util.regex | RE2J |
|------|:---:|:---:|
| 时间保证 | 无（可能指数） | **O(N) 线性保证** |
| 反向引用 | ✅ | ❌ |
| 后顾断言 | ✅ | ❌（仅定长前瞻） |
| 命名组 | ✅ | ✅ |
| 性能（正常输入） | 快 | 稍慢（DFA 构建开销） |
| 适用 | 业务文本（可信） | **不可信输入** |

> 🎯 **工程结论**：**不可信输入的校验正则用 RE2J（免疫 ReDoS）；业务可信文本用 java.util.regex（功能全）**——按输入可信度选引擎。

## 8. 用户输入正则的沙箱化

### 8.1 风险：让用户提供正则

```text
接受用户正则的风险（搜索/过滤功能）
├── ① 用户故意写 (a+)+ → 攻击其他用户
├── ② 用户无意写坏正则 → 服务性能下降
└── ③ 正则内联标志滥用（(?s) 等改变语义）
```

### 8.2 沙箱方案

```text
用户正则沙箱化四方案
├── ① 白名单引擎：只允许 RE2J（线性保证 + 不支持反向引用）
├── ② 模式预检：编译前静态分析危险模式（拒绝/简化）
├── ③ 长度限制：正则字符串长度限制 + 输入长度限制
├── ④ 权限隔离：用户正则仅在独立低优先级线程执行 + 超时
└── ⑤ 推荐组合：RE2J + 长度限制 + 超时（三层都上）
```

```java
// 用户正则的沙箱执行（组合方案）
public boolean safeUserRegex(String userPattern, String input) {
    if (userPattern.length() > 200) return false;          // ① 模式限长
    if (input.length() > 1000) return false;               // ② 输入限长
    com.google.re2j.Pattern p =                           // ③ RE2J 引擎
        com.google.re2j.Pattern.compile(userPattern);
    return p.matcher(input).find();                        // 线性时间
}
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. ReDoS = 灾难性回溯 × 不可信输入——一条合法请求打垮服务（Cloudflare 宕机 27 分钟的教训）
> 2. 触发三要素：危险模式 + 失败路径输入 + 足够长度——破坏任一要素即防御
> 3. 四层防护：模式改写（治本）→ 长度限制（拦截）→ 执行超时（兜底）→ RE2J（免疫）
> 4. Java 无内置正则超时——Future + 超时线程池实现；复杂度测试写进 CI
> 5. RE2J 是处理不可信输入的标准答案（线性保证，但无反向引用）；用户提供的正则必须沙箱化
