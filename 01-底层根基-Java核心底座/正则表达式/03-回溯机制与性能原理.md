## 1. 两类正则引擎

> **背景**：正则引擎分两大流派——回溯型（NFA）与线性型（DFA）。Java/Python/JS 用的是 NFA，RE2/RE2J 用 DFA。
> **目的**：理解引擎类型 = 理解「为什么同样模式在不同语言表现不同」。
> **适用范围**：任何需要评估正则性能风险的场景。

| 维度 | NFA（回溯型） | DFA（线性型） |
|------|:---:|:---:|
| 代表 | Java/Python/JS/PCRE | RE2/RE2J（Google） |
| 匹配速度 | 通常快（优化路径） | **稳定 O(N) 线性** |
| 最坏情况 | **指数级（灾难性回溯）** | 线性（构造保证） |
| 支持特性 | 全（反向引用/断言/命名组） | 有限（**无反向引用**） |
| ReDoS 免疫 | ❌ 需人工防护 | ✅ 天然免疫 |
| 适用 | 通用文本处理 | 处理不可信输入 |

> 🎯 **结论**：NFA 功能强但需性能纪律；DFA 性能稳但功能受限——**处理不可信输入用 RE2J，处理业务文本用 Java 正则 + 防护**。

## 2. 回溯的逐步图解

### 2.1 一个简单回溯（O(N) 级别）

```text
模式: a+b    输入: "aaab"

匹配过程（贪婪）：
① a+ 贪婪吃掉全部 "aaa"（当前位置到末尾）
② 尝试 b → 失败（输入到头了）
③ 回溯：a+ 少匹配一个 → "aa" + 剩 "ab"
④ 尝试 b → 成功 ✅

回溯次数：1 次（O(N) 级，无性能问题）
```

### 2.2 一个平方级回溯（O(N²)）

```text
模式: a.*b    输入: "aaaa...a"（100 个 a，无 b）

① .* 贪婪吃掉全部 100 个 a
② 尝试 b → 失败
③ 回溯 .* 到 99 → 尝试 b → 失败
④ 回溯到 98 → 尝试 b → 失败
...（回溯 100 次）
总尝试：约 100 次（O(N)，可接受）

但若模式是 a.*b.*c 且缺 c：
每次 .* 组合都要试 → O(N²) ≈ 5000 次（开始变慢）
```

### 2.3 一个指数级回溯（O(2^N)——灾难）

```text
模式: (a+)+b    输入: "aaaa" + "c"（4 个 a 加不匹配字符）

(a+)+ 的两种解释方式：
① 外层一次吃 4 个： (aaaa)
② 外层分两次：    (aa)(aa)、 (aaa)(a)、 (a)(aaa)、 (a)(aa)(a)...
→ 4 个 a 有 2^4 = 16 种分组方式，全都要试完才宣告失败！

30 个 a → 2^30 ≈ 10 亿次尝试 → 匹配卡死（ReDoS！）

为什么外层 + 是多余的？
├── (a+)+ 匹配的能力 = a+（外层 + 不增加能匹配的文本）
├── 但引擎不知道这一点——它会尝试所有分组
└── 正确写法：直接 a+b（消除歧义而非智斗回溯）
```

## 3. 复杂度模型：为什么正则可能很慢

### 3.1 复杂度三档

| 复杂度 | 触发模式 | 表现 | 危险度 |
|:---:|---------|------|:---:|
| **O(N) 线性** | 无歧义模式 | 毫秒级 | 🟢 |
| **O(N²) 平方** | 多个 `.*` 组合、重复扫描 | 秒级（长输入） | 🟡 |
| **O(2^N) 指数** | 嵌套量词/重叠交替 | 卡死（ReDoS） | 🔴 |

### 3.2 高危模式四类（背下来）

```text
四类高危模式（灾难性回溯触发点）
├── ① 嵌套量词：(a+)+、(a*)*
├── ② 重叠交替：(a|a)+（分支共享相同字符）
├── ③ 共享字符类的连续量词：(\w+\s?)+
├── ④ 仅一端锚定的无界重复：^\s*(\S+\s*)*$（trim 类）
└── 危险组合特征：量词嵌套 + 可重复的模糊匹配 + 失败才暴露

真实案例：
├── Cloudflare 2019：WAF 规则含 (a|a)* 类模式 → 全球 CPU 100% 宕机 27 分钟
├── ua-parser-js：\s\s*$ 尾部空白模式 → CVE-2022-25927
└── 教训：一条坏正则 = 一次服务级事故
```

### 3.3 复杂度检测（快速自查）

```bash
# 用「长输入 + 失败场景」实测（最直接）
# 输入构造：目标字符 + 一个不匹配结尾字符
# 如 (a+)+ 测试输入：aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaX（30 个 a + X）
# 观察耗时：毫秒级正常；秒级以上 = 灾难性回溯

# 工具：safe-regex（Node）/ Semgrep 正则规则 / regex 静态分析
```

## 4. 贪婪 vs 勉强 vs 占有：性能对比

### 4.1 三种量词的回溯行为

| 模式 | 匹配方向 | 回溯行为 | 最坏复杂度 |
|------|:---:|---------|:---:|
| `.*`（贪婪） | 先多吃再回吐 | 逐步减少重试 | 可能 O(N²)/指数 |
| `.*?`（勉强） | 先少吃再增加 | 逐步增加重试 | **同样可能灾难** |
| `.*+`（占有） | 一次吃完提交 | **永不回溯** | **O(N) 线性** |

### 4.2 关键认知：勉强 ≠ 安全

> ⚠️ **常见误解**：「用勉强量词就安全了」——**错误**！勉强量词只是「改变回溯方向」，回溯次数可能一样多：

```text
模式: (a*?)+b    输入: "aaaa" + "X"

勉强版 (a*?)+ 会怎么试？
① a*? 先匹配 0 个 → 外层 + 再试 → 0+0+... 尝试组合
② 同样有 2^N 种分组方式 → 同样灾难！
→ 结论：嵌套量词无论贪婪还是勉强都危险
→ 解法：原子化/占有化/消除嵌套
```

### 4.3 性能对比实测（设计基准）

```text
同一任务三种写法的性能对比（输入 1000 个 a + X）

写法 A（危险）：(a+)+b        → 指数级 → 卡死 ❌
写法 B（勉强）：(a*?)+b       → 指数级 → 卡死 ❌（误解破除！）
写法 C（正确）：a+b           → 线性 → 毫秒级 ✅
写法 D（原子）：(?>(a+))+b    → 线性 → 毫秒级 ✅

→ 结论：消除歧义（C）> 原子化（D）> 依赖量词模式
```

## 5. 回溯优化的边界（JDK 已知问题）

### 5.1 JDK 的缓解机制与局限

> ⚠️ **JDK 官方承认**（JEP 8260688 草案）：当前实现「缓解但未消除 O(2^N) 性能问题，且存在 StackOverflowError 风险」：

```text
JDK 回溯优化的已知边界
├── ① 记忆化优化（JDK-6328855）：缓解大部分指数级问题
│   └── 但存在反向引用时优化被关闭！
├── ② 深嵌套模式 → StackOverflowError（不是超时，是崩溃）
├── ③ Matcher.find() 隐式 O(N) 循环 → 整体可能 O(N²)
│   └── 单纯用占有量词不足以解决（JEP 8260688 指出）
└── ④ 用户得不到任何性能保证（无超时机制）
```

### 5.2 JEP 8260688（2026 趋势）

```text
JEP 8260688：Predictable regex performance（草案中）
├── 目标：可请求 O(N) 性能的 API（Pattern.compile 加标志）
├── 思路：保留兼容性的同时提供线性时间保证
├── 允许：替换 Pattern 的实现（可插拔引擎）
└── 2026 现状：草案阶段——生产防护仍靠工程手段（见 04 篇）
```

## 6. 性能安全的模式写作原则

### 6.1 七原则

```text
性能安全正则七原则
├── ① 消除嵌套量词：(a+)+ → a+（外层冗余量词直接删）
├── ② 用精确字符类：[A-Z]{2} 优于 [A-Z]+（收窄匹配空间）
├── ③ 锚定先行：^xxx$ 让引擎快速失败（不全文扫描）
├── ④ 用「预期失败」测试：目标字符 + 不匹配尾巴（验证最坏情况）
├── ⑤ 反向引用谨慎：会关闭回溯优化——不可信输入禁用
├── ⑥ 原子组/占有量词：确认语义无损后用（防回溯跨段）
└── ⑦ 先过滤再正则：输入长度限制 + 前置校验（最后防线）
```

### 6.2 改写对照表

| 危险写法 | 安全改写 | 说明 |
|---------|---------|------|
| `(a+)+` | `a+` | 删除冗余外层量词 |
| `(\w+\s?)+` | `\w+(\s\w+)*` | 明确结构（首项无尾随空白） |
| `(a\|a)+` | `a+` | 消除重叠分支 |
| `^\s*(\S+\s*)*$` | `^\S+(\s\S+)*$` 或 `\S+(?:\s+\S+)*` | 消除共享字符重叠 |
| `(.*a){10}` | 拆分或原子化 `(?>.*a){10}` | 每段原子化 |
| `.*` 解析嵌套 | `.*?` + 明确定界符或字符类 `[^>]*` | 用排除类收窄 |

> 🎯 **金句**：**消除歧义而非「智斗」回溯**——引擎不知道你的意图，只按模式机械尝试；把模式写得「无歧义」才是性能与安全的根本。

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 两类引擎：NFA（回溯型，功能全）vs DFA（线性，免疫 ReDoS）——不可信输入用 RE2J
> 2. 回溯三档复杂度：线性（无歧义）→ 平方（多个 .*）→ 指数（嵌套量词）
> 3. 四类高危模式：嵌套量词 `(a+)+`/重叠交替 `(a|a)+`/共享字符连续量词/无界重复 trim 模式
> 4. **勉强量词 ≠ 安全**（`(a*?)+` 同样灾难）——消除歧义 > 原子化 > 换量词模式
> 5. JDK 优化有边界：反向引用关闭优化、深嵌套 StackOverflow、find() 可能 O(N²)——JEP 8260688 仍在草案
