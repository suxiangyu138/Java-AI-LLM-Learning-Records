### <a id="q1"></a>1. Java泛型是真正的泛型吗？和C++模板有什么区别？

**面试官意图**：考察对泛型本质的理解深度，是否知道"类型擦除"这个核心概念。

#### 表面回答

Java 泛型是"伪泛型"，C++ 模板是"真泛型"。Java 通过类型擦除实现，C++ 通过模板实例化（代码膨胀）实现。

#### 原理级回答

| 对比维度 | Java 泛型 | C++ 模板 |
|---------|-----------|----------|
| 实现机制 | 类型擦除（Type Erasure） | 模板实例化（Template Instantiation） |
| 编译后 | 统一替换为 Object / 上界 | 每种类型参数独立生成一份代码 |
| 代码膨胀 | 无（复用同一份字节码） | 有（int、long、double各生成一份） |
| 运行时信息 | 擦除，不可知实际类型参数 | 保留，模板参数在运行时可见 |
| 性能 | 无编译期优化空间 | 可为每种类型特化优化 |
| 限制 | 不能 `new T()`、不能 `new T[]` | 无限制 |

```java
// Java 泛型 —— 编译后实际等价于下面这样
// 源码：
List<String> strings = new ArrayList<>();
List<Integer> integers = new ArrayList<>();
System.out.println(strings.getClass() == integers.getClass()); // true!
// 两者运行时都是 ArrayList.class

// 更直接的证据：
// 以下代码无法编译
// 因为 T 在运行时不存在
public <T> T createInstance() {
    return new T(); // 编译错误: Type parameter 'T' cannot be instantiated directly
}
```

```cpp
// C++ 模板 —— 编译器各自生成代码
// template<typename T> T add(T a, T b) { return a + b; }
// add<int>(1, 2)    → 生成 int 版本
// add<double>(1,2)  → 生成 double 版本
// add<string>()     → ❌ 编译错误，string 没有 operator+
// 每种类型互不干扰！
```

#### 源码级回答

```java
// 验证类型擦除 —— 反编译看字节码
// javap -c -p GenericClass.class

public class GenericClass<T> {
    public T value;

    // 编译后实际生成 (Signature 属性保留擦除前信息)
    // public Object value;

    public static void main(String[] args) throws Exception {
        GenericClass<String> g = new GenericClass<>();
        // 编译后：
        // GenericClass g = new GenericClass();
        // g.value = "hello";       → 自动插入 checkcast
        // String s = (String) g.value; → 自动插入强转
    }
}
```

#### 加分项

- Java 泛型擦除后，仍然通过 **Signature 属性** 在字节码中保留泛型签名信息，反射可以读取
- 数组和泛型不能混用（`new ArrayList<String>[10]` 非法），因为数组在运行时需要知道具体类型
- Java 泛型的 `? extends` / `? super` 通配符实现了 **协变** 和 **逆变**，C++ 通过模板特化实现不同行为
- Kotlin 的 `inline` + `reified` 关键字可以绕过类型擦除

#### 追问

**Q**: 既然擦除了，为什么 `List<String>` 的 `get()` 返回 `String` 而非 `Object`？

**A**: 编译期自动插入了强转 (`checkcast` 字节码指令)。源码中的 `List<String>` 让编译器知道在何处插入正确的类型转换——因此类型安全由编译器保障，而非运行时。

> 🎯 **核心要点**：Java 泛型 = **编译期类型检查** + **类型擦除** + **自动插入强转** + **Signature属性保留元信息**。本质是语法糖，编译器替你写好了强转。

### <a id="q2"></a>2. 什么是PECS原则？举例说明

**面试官意图**：考察对泛型通配符 `? extends` / `? super` 的理解，以及是否能在实际场景中正确使用。

#### 表面回答

PECS = **P**roducer **E**xtends, **C**onsumer **S**uper。生产者用 `extends`，消费者用 `super`。

#### 原理级回答

```java
// ==================== 生产者用 extends ====================
// 从一个集合中读取元素 —— 它是生产者（提供数据）
public void processNumbers(Collection<? extends Number> nums) {
    // ✅ 可以读取 —— 编译器知道里面至少是 Number
    for (Number n : nums) {
        System.out.println(n.doubleValue());
    }

    // ❌ 不能添加 —— 编译器不知道具体类型是什么
    // nums.add(42);     // 编译错误!
    // nums.add(3.14);   // 编译错误!
}

// ==================== 消费者用 super ====================
// 向集合中添加元素 —— 它是消费者（接收数据）
public void addNumbers(Collection<? super Integer> sink) {
    // ✅ 可以添加 Integer —— 编译器知道至少能装 Integer
    sink.add(42);
    sink.add(100);

    // ❌ 读取只能读到 Object —— 因为可能是 List<Object>
    // Integer i = sink.iterator().next(); // 编译错误!
    Object o = sink.iterator().next();     // ✅ 只能读到 Object
}

// ==================== 经典应用：Collections.copy ====================
// JDK 源码 —— PECS 的完美实践
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    // dest 是消费者（接收 T）→ ? super T
    // src  是生产者（提供 T）→ ? extends T
    for (int i = 0; i < src.size(); i++) {
        dest.set(i, src.get(i));
    }
}
```

#### 源码级回答

```java
// Stream.collect(Collectors.toList()) 的签名
// <R, A> R collect(Collector<? super T, A, R> collector);
//                                    ↑ Collector 消费 T，所以是 ? super T

// Collections.sort 的签名
// public static <T> void sort(List<T> list, Comparator<? super T> c)
//                                                   ↑ Comparator 消费 T
```

#### 记忆技巧

```text
PECS 助记：
- 你从箱子里「取」(Get/Produce) 东西 → 箱子用 extends
- 你往箱子里「放」(Put/Consume) 东西 → 箱子用 super

Joshua Bloch 在 Effective Java 中的口诀：
「Producer Extends, Consumer Super」
```

#### 加分项

- **不可变性 (Invariance)**: `List<String>` 既不是 `List<Object>` 的子类型也不是父类型，PECS 提供了安全的替代方案
- Kotlin 使用了不同的关键词：`out` ≈ `extends`（协变），`in` ≈ `super`（逆变）
- Java 数组是**协变**的：`String[]` 是 `Object[]` 的子类型——这导致了数组的运行时类型检查

#### 追问

**Q**: 为什么数组是协变的而泛型是不可变的？

**A**: 这是历史原因。数组协变是 Java 1.0 的设计，若泛型也协变则会破坏类型安全。例如：`List<String>` 若赋值给 `List<Object>`，就可以往里放 `Integer`，取出来时认为它是 `String` 就会 ClassCastException。数组在运行时检查：`Object[] arr = new String[1]; arr[0] = 42;` 会在运行时抛 `ArrayStoreException`。

> 🎯 **核心要点**：PECS 是泛型通配符使用的黄金法则。`? extends T` 保证**安全读取**（不可写），`? super T` 保证**安全写入**（不可准确读取）。一句话：**取用 extends，存入 super**。

### <a id="q3"></a>3. 泛型擦除后为什么还能通过反射获取泛型类型？

**面试官意图**：考察是否知道 Signature 属性，以及 Gson 的 TypeToken 原理。

#### 表面回答

虽然运行时类型参数被擦除了，但字节码中保留了 Signature 属性，反射可以通过 `getGenericSuperclass()`、`getGenericReturnType()` 等方法获取。

#### 原理级回答

```java
// ==================== 证据：字节码中的 Signature ====================
// 写一个带泛型的类：
public class Box<T> {
    public T value;
    public List<String> names;
}

// 编译后用 javap -verbose 查看：
// public class Box<T extends java.lang.Object> {
//   Signature: #12 <T:Ljava/lang/Object;>Ljava/lang/Object;
//   ↑ 泛型签名保存在 Signature 属性中，擦除的是方法体中的类型信息
//
//   public T value;
//     descriptor: Ljava/lang/Object;   ← 擦除后是 Object
//     Signature: #13 TT;               ← 但 Signature 保留了 T!
//
//   public java.util.List<java.lang.String> names;
//     descriptor: Ljava/util/List;     ← 擦除后是 List
//     Signature: #14 Ljava/util/List<Ljava/lang/String;>;
//     ↑ Signature 保留了完整的 List<String>!
// }

// ==================== 反射读取泛型信息 ====================
public class GenericReflectionDemo {
    public List<String> stringList;
    public Map<String, Integer> map;

    public static void main(String[] args) throws Exception {
        // 1. 读取字段的泛型类型
        Field field = GenericReflectionDemo.class
                .getDeclaredField("stringList");
        Type type = field.getGenericType(); // → List<String>

        if (type instanceof ParameterizedType) {
            ParameterizedType pt = (ParameterizedType) type;
            System.out.println("原类型: " + pt.getRawType());       // interface java.util.List
            System.out.println("实际类型参数: "
                    + Arrays.toString(pt.getActualTypeArguments()));
            // → [class java.lang.String]
        }

        // 2. 读取方法的泛型返回类型
        Method method = GenericReflectionDemo.class.getMethod("getList");
        Type returnType = method.getGenericReturnType();
        System.out.println("方法返回类型: " + returnType);
        // → java.util.List<java.lang.String>
    }

    public List<String> getList() { return null; }
}
```

#### 源码级回答 — Gson 的 TypeToken 原理

```java
// ==================== Gson 的 TypeToken 如何工作？ ====================
// 这是 Gson 中最精巧的泛型用法
// 使用方式：
List<User> users = gson.fromJson(json, new TypeToken<List<User>>(){}.getType());

// ==================== TypeToken 核心原理 ====================
// Gson 源码简化版：
public class TypeToken<T> {
    final Class<? super T> rawType;
    final Type type;

    @SuppressWarnings("unchecked")
    protected TypeToken() {
        // 关键：获取子类的父类泛型信息
        // TypeToken<List<User>>(){} 创建了一个匿名内部类
        // 匿名类的父类是 TypeToken<List<User>>
        // 所以 getGenericSuperclass() 返回的就是 TypeToken<List<User>>
        Type superclass = getClass().getGenericSuperclass();

        if (superclass instanceof ParameterizedType) {
            // 取出 List<User>
            this.type = ((ParameterizedType) superclass)
                    .getActualTypeArguments()[0];
        } else {
            throw new RuntimeException("Invalid TypeToken");
        }
    }

    public Type getType() { return type; }
}

// ==================== 使用原理展示 ====================
public class TypeTokenDemo {
    public static void main(String[] args) {
        // 创建一个匿名内部类继承 TypeToken<List<String>>
        // 相当于 class $1 extends TypeToken<List<String>> {}
        TypeToken<List<String>> token = new TypeToken<List<String>>() {};
        //                                     ↑ 这个 {} 创建了匿名子类

        Type type = token.getType();
        System.out.println(type); // java.util.List<java.lang.String>

        // 对比——没有 {} 会怎样？
        // TypeToken<List<String>> token2 = new TypeToken<List<String>>();
        // 编译错误！TypeToken 的构造器是 protected
        // 而且即使能编译，getGenericSuperclass() 返回的是 TypeToken<Object>
        // 因为 TypeToken<T> 的 T 被擦除了！
        // 所以 {} 匿名内部类是必不可少的！
    }
}
```

#### 加分项

- 字段、方法参数、方法返回值的泛型信息通过 Signature 属性完整保留
- 局部变量的泛型信息被完全擦除（没有对应的字节码属性）
- Spring 的 `GenericTypeResolver` / `ResolvableType` 封装了这些复杂的泛型反射操作

#### 追问

**Q**: 为什么 `new ArrayList<String>().getClass()` 无法获取 `String`？

**A**: 因为 `ArrayList<String>` 不是匿名子类，它本身就是 `ArrayList`，`getGenericSuperclass()` 拿到的父类是 `AbstractList<E>`，E 还在"未绑定"状态。必须要有一个 **具体的子类或匿名内部类** 去"固定"泛型参数，反射才能获取到。

> 🎯 **核心要点**：泛型信息擦除的是**方法体内**的类型参数，但**类签名**（Signature属性）中保留了完整信息。通过**匿名内部类**继承泛型父类可以"固定"类型参数，供反射读取。这就是 Gson/Jackson 反序列化泛型的底层原理。

### <a id="q4"></a>4. 桥方法是什么？为什么需要桥方法？

**面试官意图**：考察对泛型擦除和多态交互的理解深度。

#### 表面回答

桥方法是编译器自动生成的合成方法，用于解决泛型擦除后的多态冲突问题。名称通常为 `bridge`，在字节码中标记 `ACC_BRIDGE` 和 `ACC_SYNTHETIC`。

#### 原理级回答

```java
// ==================== 场景 ====================
// 我们有一个泛型父类和一个具体子类
class Parent<T> {
    public T getValue() {
        return null;
    }
}

class Child extends Parent<String> {
    @Override
    public String getValue() {
        return "hello";
    }
}

// ==================== 擦除后的问题 ====================
// 类型擦除后，Parent 变成：
class Parent {  // <T> 被擦掉
    public Object getValue() {  // T → Object
        return null;
    }
}

// Child 本意是：
class Child extends Parent {
    // 程序员想重写的是：
    @Override
    public String getValue() {  // String 不是 Object 的重写！
        return "hello";
    }
}

// 但实际上：String getValue() 和 Object getValue() 是两个不同的方法！
// String 不是 Object 的子类？当然是，但在 JVM 方法分派中
// 方法签名包含 方法名 + 参数类型 + 返回类型
// 返回类型不同不构成重写！
```

#### 源码级回答

```java
// ==================== 编译后的字节码 ====================
// javap -c -p Child.class
//
// public class Child extends Parent {
//
//   // 程序员写的"重写"方法
//   public java.lang.String getValue();
//     Code:...
//
//   // 编译器自动生成的桥方法 —— 这才是真正的重写！
//   public java.lang.Object getValue();
//     flags: ACC_BRIDGE, ACC_SYNTHETIC  ← 标记
//     Code:
//        0: aload_0
//        1: invokevirtual #getValue       // 调用 String 版本
//        4: areturn
//
//   桥方法的逻辑很简单：调用 String 版本的方法
//   本质是：Object getValue() { return ((Child)this).getValue(); }
// }

// ==================== 为什么需要桥方法？ ====================
// 如果没有桥方法，多态就失效了：
public class BridgeDemo {
    public static void main(String[] args) {
        Parent<String> parent = new Child();

        // 多态调用 —— 应该调用子类的 getValue()
        // 如果不生成桥方法：
        //   parent 的静态类型是 Parent
        //   Parent.getValue() 返回 Object
        //   → 调用的是 Parent 的 Object getValue()，不会调用子类的
        //   → 多态失效！

        // 生成了桥方法：
        //   Child 中有 Object getValue()（桥方法）
        //   桥方法内部调用 String getValue()
        //   → 多态正确！
        String value = parent.getValue();
        System.out.println(value); // "hello"
    }
}
```

#### 加分项

- `getDeclaredMethods()` 会返回桥方法，需要注意过滤：`method.isBridge()`
- 除了泛型返回类型，泛型参数也会生成桥方法（如 `Comparable<T>.compareTo(T)` 的子类）
- `ACC_SYNTHETIC` 标记可用于识别编译器生成的方法
- JVM 方法分派依据是**描述符**（descriptor），包含参数类型和返回类型——这是桥方法存在的根本原因

#### 追问

**Q**: 如何判断一个方法是桥方法？

**A**: `Method.isBridge()` 返回 `true`，或者检查字节码 flags。典型场景：`Method[] methods = clazz.getDeclaredMethods(); for(Method m : methods) if(m.isBridge()) ...`

> 🎯 **核心要点**：桥方法是编译器在泛型擦除后维持多态的"补丁"。`String getValue()` 和 `Object getValue()` 在 JVM 规则下是两个方法，桥方法负责将泛型擦除后的调用路由到真实的类型化方法。

### <a id="q5"></a>5. List\<String\>能否赋值给List\<Object\>？为什么？

**面试官意图**：考察对泛型不变性 (Invariance) 的理解。

#### 表面回答

不能。编译错误。因为 Java 泛型是**不可变**的（Invariant），`List<String>` 不是 `List<Object>` 的子类型。

#### 原理级回答

```java
public class InvarianceDemo {
    public static void main(String[] args) {
        List<String> strings = new ArrayList<>();
        strings.add("hello");

        // ❌ 编译错误：不兼容的类型
        // List<Object> objects = strings;

        // 假设能通过编译，会出什么问题？
        // List<Object> objects = strings; // 假设可以
        // objects.add(42);                 // 放进一个 Integer!
        // String s = strings.get(0);       // ❌ ClassCastException!
        // String value 期望拿到 String，但实际拿到的是 Integer

        // ==================== 通配符的正确姿势 ====================
        // 只读 —— 可以用 ? extends
        List<? extends Object> readOnly = strings; // ✅

        // 只写 —— 可以用 ? super
        List<? super String> writeOnly = new ArrayList<>();
        writeOnly.add("hello");  // ✅

        // ==================== 数组的协变对比 ====================
        // 数组是协变的：
        String[] strArray = new String[1];
        Object[] objArray = strArray;       // ✅ 编译通过
        objArray[0] = 42;                   // ❌ 运行时 ArrayStoreException
        // 数组在运行时知道自己的实际元素类型
        // 而泛型 List 在运行时不知道（擦除了）
    }
}
```

#### 源码级回答

```java
// JDK 中 Collections.unmodifiableList 的巧妙设计
public static <T> List<T> unmodifiableList(List<? extends T> list) {
    // 参数用 ? extends T 接受协变，返回值用 T 保证类型安全
    return new UnmodifiableList<>(list);
}

// 使用：
List<String> strings = new ArrayList<>();
// unmodifiableList 接受 ? extends T，T 被推断为 String
List<String> safe = Collections.unmodifiableList(strings); // ✅
```

#### 加分项

- 这是 Java 泛型设计的安全决策，牺牲灵活性换取类型安全
- Kotlin 通过 `out`/`in` 声明点变位，比 Java 的使用点变位更简洁
- 数组协变是 Java 最早的"错误"设计之一，泛型刻意修复了这个问题

> 🎯 **核心要点**：泛型不可变性确保了类型安全。需要协变用 `? extends T`，需要逆变用 `? super T`。编译器用 **编译器检查** 替代了数组的 **运行时检查**。

### <a id="q6"></a>6. 如何获取泛型父类的实际类型参数？

**面试官意图**：考察 `ParameterizedType` 和 `Type` 体系的掌握程度。

#### 表面回答

使用 `(Class) ((ParameterizedType) getClass().getGenericSuperclass()).getActualTypeArguments()[0]`。

#### 原理级回答

```java
public class TypeResolver<T> {
    private final Class<T> type;

    @SuppressWarnings("unchecked")
    public TypeResolver() {
        // 核心一行：
        Type genericSuperclass = getClass().getGenericSuperclass();

        if (genericSuperclass instanceof ParameterizedType) {
            ParameterizedType pt = (ParameterizedType) genericSuperclass;
            this.type = (Class<T>) pt.getActualTypeArguments()[0];
        } else {
            // 若父类未被参数化（即直接继承 TypeResolver 而非 TypeResolver<String>）
            // 抛出异常或回退
            throw new RuntimeException("Type parameter not found");
        }
    }

    public Class<T> getType() { return type; }

    public static void main(String[] args) {
        // ✅ 正确用法：
        TypeResolver<String> resolver = new TypeResolver<String>() {};
        //                                     ↑ 必须加 {} 创建匿名子类
        System.out.println(resolver.getType()); // class java.lang.String

        // ❌ 错误用法：
        // TypeResolver<String> resolver2 = new TypeResolver<>();
        // 直接 new → 没有匿名子类 → getGenericSuperclass() 返回 TypeResolver<T>
        // → T 还未绑定 → 抛异常

        // ==================== Spring 的 ResolvableType ====================
        // Spring 封装了更完善的泛型解析 API：
        // ResolvableType resolvableType = ResolvableType.forClass(MyClass.class);
        // Class<?> generic = resolvableType.getSuperType().getGeneric(0).resolve();
    }
}

// ==================== Type 体系总览 ====================
// Type (接口)
// ├── Class                  — 原始类型: String.class, List.class
// ├── ParameterizedType      — 参数化类型: List<String>, Map<String,Integer>
// │   ├── getRawType()       — 原始类型: List
// │   └── getActualTypeArguments() — [String], [String, Integer]
// ├── TypeVariable           — 类型变量: T, E, K, V
// │   └── getBounds()        — 上界: T extends Number -> Number
// ├── WildcardType           — 通配符: ? extends Number, ? super String
// │   ├── getUpperBounds()   — 上界
// │   └── getLowerBounds()   — 下界
// └── GenericArrayType       — 泛型数组: T[], List<String>[]
//     └── getGenericComponentType()
```

#### 加分项

```java
// ==================== 多层泛型解析 ====================
// 不是简单的 Class<T>，而是嵌套泛型
class Holder<T> {}
class StringListHolder extends Holder<List<String>> {}

// 获取 List<String>
ParameterizedType pt = (ParameterizedType)
        StringListHolder.class.getGenericSuperclass();

// actualArg 是 ParameterizedType: List<String>
```

### <a id="q7"></a>7. 反射有几种获取Class对象的方式？各有什么特点？

**面试官意图**：考察反射基础，以及是否了解类加载的时机差异。

#### 表面回答

三种方式：`类名.class`、`对象.getClass()`、`Class.forName()`。

#### 原理级回答

```java
public class GetClassDemo {
    public static void main(String[] args) throws Exception {
        // ==================== 方式1：类名.class ====================
        Class<String> clazz1 = String.class;

        // 特点：
        // - 编译期类型安全（泛型参数可用）
        // - 不触发静态初始化块（类初始化延迟到首次主动使用）
        // - 最安全、最快（无方法调用开销）

        // ==================== 方式2：对象.getClass() ====================
        String str = "hello";
        Class<? extends String> clazz2 = str.getClass();

        // 特点：
        // - 需要对象实例
        // - 返回类型是 ? extends T（通配符）
        // - 已触发类加载（对象都创建了）

        // ==================== 方式3：Class.forName() ====================
        Class<?> clazz3 = Class.forName("java.lang.String");

        // 特点：
        // - 全限定名（字符串）—— 编译期未知时唯一选择
        // - 默认初始化类（触发静态块）← 这是重要的副作用！
        // - 会抛 ClassNotFoundException（受检异常）

        // ==================== 额外方式：类加载器 ====================
        Class<?> clazz4 = GetClassDemo.class.getClassLoader()
                .loadClass("java.lang.String");
        // 特点：
        // - 不触发类初始化（与 class 语法类似）
        // - 需要 ClassLoader 实例
    }
}

// ==================== forName 的初始化对比 ====================
class InitDemo {
    static {
        System.out.println("静态块执行！");
    }
}

// Class.forName("InitDemo");       → 输出 "静态块执行！"
// InitDemo.class;                   → 不输出
// getClassLoader().loadClass(...);  → 不输出

// Class.forName 可控制初始化：
// Class.forName("com.example.Driver", false, classLoader);
// 第二个参数 false 表示不初始化
```

#### 各方式对比

| 方式 | 需要对象 | 编译期类型安全 | 触发初始化 | 异常 | 使用场景 |
|------|---------|:-----------:|:---------:|:---:|---------|
| `类名.class` | 否 | 是 | 否 | 无 | 已知类型，获取 Class |
| `对象.getClass()` | 是 | 通配符 | 已初始化 | 无 | 已有对象实例 |
| `Class.forName()` | 否 | 否 | 是 | ClassNotFoundException | JDBC驱动加载、动态类加载 |
| `loader.loadClass()` | 否 | 否 | 否 | ClassNotFoundException | 延迟初始化、OSGi/模块化 |

#### 加分项

- `boolean.class` 和 `Boolean.TYPE` 是等价的（表示基本类型的 Class）
- `void.class` 表示 `void` 返回类型
- Java 9+ `Module` API 影响了 `Class.forName` 的行为（模块化系统）

> 🎯 **核心要点**：三种获取方式的核心差异在 **编译期安全性**、**是否触发类初始化**、**适用场景**。`Class.forName` 会触发静态块，在 JDBC 时代用于加载驱动，现在仍是动态加载的主要方式。

### <a id="q8"></a>8. 反射的性能为什么慢？如何优化？

**面试官意图**：考察是否真的用过反射做性能敏感的开发，以及是否了解 JVM 内部的运行时优化机制。

#### 表面回答

反射慢因为：动态类型检查、方法查找开销、无法内联、JIT 无法优化。

#### 原理级回答

```java
public class ReflectionPerformance {
    // ==================== 四种调用方式性能对比 ====================
    public static void main(String[] args) throws Exception {
        int iterations = 10_000_000;
        String target = "hello";
        Method method = String.class.getMethod("length");

        // 1. 直接调用 (基准)
        long t1 = System.nanoTime();
        for (int i = 0; i < iterations; i++) {
            int len = target.length();
        }
        long t2 = System.nanoTime();

        // 2. 反射调用 (无优化)
        long t3 = System.nanoTime();
        for (int i = 0; i < iterations; i++) {
            int len = (int) method.invoke(target);
        }
        long t4 = System.nanoTime();

        // 3. 反射调用 (setAccessible)
        method.setAccessible(true);
        long t5 = System.nanoTime();
        for (int i = 0; i < iterations; i++) {
            int len = (int) method.invoke(target);
        }
        long t6 = System.nanoTime();

        // 4. MethodHandle (Java 7+)
        MethodHandles.Lookup lookup = MethodHandles.lookup();
        MethodHandle mh = lookup.findVirtual(
                String.class, "length", MethodType.methodType(int.class));
        mh = mh.asType(mh.type().wrap()); // 适配参数类型
        long t7 = System.nanoTime();
        for (int i = 0; i < iterations; i++) {
            int len = (int) mh.invokeExact(target);
        }
        long t8 = System.nanoTime();

        System.out.println("直接调用:      " + (t2 - t1) / 1_000_000 + "ms");
        System.out.println("反射(无优化):   " + (t4 - t3) / 1_000_000 + "ms");
        System.out.println("反射(setAccess):" + (t6 - t5) / 1_000_000 + "ms");
        System.out.println("MethodHandle:  " + (t8 - t7) / 1_000_000 + "ms");

        // 大致结果 (JIT 预热后):
        // 直接调用:      ~30ms
        // 反射(无优化):   ~200ms  (6-7x)
        // 反射(setAccess):~120ms  (4x, 少了访问检查)
        // MethodHandle:  ~40ms   (接近直接调用)
    }
}
```

#### 反射慢的三大原因

```java
// 1. 每次 invoke 都会进行访问检查 (AccessibleObject 权限验证)
//    → setAccessible(true) 可以跳过访问检查
//    → Java 9+ 模块化系统限制 setAccessible

// 2. 参数自动装箱 (Object[] args / invoke(Object, Object...))
//    → 每次调用都需要把参数变成 Object[]
//    → 基本类型需要自动装箱
//    → 方法返回值需要强转

// 3. JIT 无法内联
//    → 直接调用可以被 JIT 内联（消除方法调用开销）
//    → 反射调用经过 invoke 分发，调用图对 JIT 不透明
//    → JIT 无法确定实际调用目标，无法内联
```

#### 优化方案

```java
// ==================== 方案1：setAccessible(true) ====================
method.setAccessible(true);
// 跳过 Java 语言访问检查，可提升 ~30-50% 性能

// ==================== 方案2：MethodHandle (Java 7+) ====================
// 比反射快 2-3 倍，接近直接调用
MethodHandle mh = MethodHandles.lookup()
    .findVirtual(String.class, "length",
            MethodType.methodType(int.class));

// ==================== 方案3：LambdaMetafactory (Java 8+) ====================
// 极致优化——将反射调用转换为函数式接口
@FunctionalInterface
interface StringLength {
    int length(String s);
}

// 运行时将 Method → LambdaMetafactory → 生成直接调用的字节码
MethodHandles.Lookup lookup = MethodHandles.lookup();
MethodType funcType = MethodType.methodType(int.class, String.class);
MethodType methType = MethodType.methodType(int.class);
MethodHandle target = lookup.findVirtual(String.class, "length", methType);

CallSite site = LambdaMetafactory.metafactory(
    lookup,
    "length",
    MethodType.methodType(StringLength.class),
    funcType,
    target,
    methType
);
StringLength lambda = (StringLength) site.getTarget().invokeExact();
lambda.length("hello"); // 接近直接调用性能！

// ==================== 方案4：缓存反射对象 ====================
// 避免重复 Class.forName()、getMethod() 等查找开销
// 使用 ConcurrentHashMap 缓存 Method/Field/Constructor
```

#### 加分项

- Spring 5 开始大量使用 `MethodHandle` 替代 `Method.invoke()`，提升了框架启动和运行时性能
- Java 17+ 的 `Reflection.filterFields()` 提供了更精细的反射过滤控制
- `VarHandle` (Java 9+) 替代 `Field.set/get`，提供了更好的字段访问性能
- JIT 在检测到 MethodHandle 是"常量化"（constant）时，可以完全去虚拟化和内联

#### 追问

**Q**: `MethodHandle` 和 `Method.invoke` 有什么区别？

**A**: `MethodHandle` 是"可执行的符号引用"，它像方法指针一样可以直接调用，近似于 C 的函数指针。JIT 可以将其内联（因为调用图中对 JIT 更透明）。而 `Method.invoke` 需要经过反射框架的分发逻辑，调用链路更长。

> 🎯 **核心要点**：反射慢的根本原因是 **JIT 无法内联**。优化三件套：`setAccessible(true)`跳过访问检查 → `MethodHandle` 提速 2x+ → `LambdaMetafactory` 生成直接调用代码极致优化。

### <a id="q9"></a>9. JDK动态代理和CGLIB有什么区别？如何选择？

**面试官意图**：考察 AOP 底层原理，是否了解 Spring AOP 的代理策略。

#### 表面回答

JDK 动态代理基于接口，CGLIB 基于继承（子类化）。Spring 默认：有接口时用 JDK 代理，无接口时用 CGLIB。

#### 原理级回答

| 对比维度 | JDK 动态代理 | CGLIB |
|---------|-------------|-------|
| 原理 | `Proxy.newProxyInstance()` 生成接口实现类 | ASM 字节码生成目标类的子类 |
| 要求 | 目标必须有接口 | 目标类不能是 final |
| 生成时机 | 运行时 `Proxy.getProxyClass()` | 运行时字节码生成 |
| 生成速度 | 快（结构简单） | 慢（需操作字节码） |
| 调用性能 | 较低（反射调用） | 较高（可直接调用、无需反射） |
| 代理方法 | `InvocationHandler.invoke()` | `MethodInterceptor.intercept()` |
| 限制 | 只能代理接口方法 | `final` 方法无法重写 |
| 版本 | JDK 原生，无需额外依赖 | 需导入 cglib 或 spring-core |

```java
// ==================== JDK 动态代理 ====================
// 运行时生成的代理类等价于：
public final class $Proxy0 extends Proxy implements UserService {
    private InvocationHandler h;

    @Override
    public void createUser(String name) {
        // 所有调用转发给 InvocationHandler
        h.invoke(this, createUserMethod, new Object[]{name});
    }
}

// 使用 Proxy.getProxyClass() 生成代理类字节码
// 代理类继承 Proxy，实现目标接口
// 所有接口方法调用 → InvocationHandler.invoke()

// ==================== CGLIB 代理 ====================
// 运行时生成的代理类等价于：
public class UserServiceImpl$$EnhancerByCGLIB extends UserServiceImpl {
    private MethodInterceptor interceptor;

    @Override
    public void createUser(String name) {
        // 调用转发给 MethodInterceptor
        interceptor.intercept(this, createUserMethod,
                new Object[]{name}, createUserMethodProxy);
    }
}

// CGLIB 生成目标类的子类
// 重写所有非 final 方法
// 使用 FastClass 机制提升调用性能（索引方式而非反射）
```

#### 源码级回答

```java
// Spring 的代理选择逻辑
public class DefaultAopProxyFactory implements AopProxyFactory {
    @Override
    public AopProxy createAopProxy(AdvisedSupport config) {
        if (config.isOptimize() || config.isProxyTargetClass()
                || hasNoUserSuppliedProxyInterfaces(config)) {
            // 条件满足 → 使用 CGLIB
            Class<?> targetClass = config.getTargetClass();
            if (targetClass.isInterface()) {
                return new JdkDynamicAopProxy(config);
            }
            return new ObjenesisCglibAopProxy(config);
        } else {
            // 有接口 → 用 JDK 代理
            return new JdkDynamicAopProxy(config);
        }
    }
}

// Spring Boot 2.x+ 默认使用 CGLIB (spring.aop.proxy-target-class=true)
// 因为现代应用大多不需要依赖接口编程
```

#### 如何选择

```text
选 JDK 代理：
- 目标对象有完善的接口抽象
- 需要代理的只是接口中声明的方法
- 对生成速度有要求（CGLIB 生成略慢）
- 团队遵循"面向接口编程"风格

选 CGLIB：
- 目标对象没有接口（或不想设计接口）
- 需要代理非接口方法
- Spring Boot 默认配置（简单省事）
- 对调用性能有更高要求
```

#### 加分项

- CGLIB 的 `FastClass` 机制通过索引直接调用方法，避免了反射，调用性能更好
- Objenesis 库绕过构造器创建 CGLIB 代理对象（无需无参构造器）
- Java 16+ 限制了 `setAccessible` 对 `--add-opens` 未开放的模块的访问，CGLIB 在模块化环境下需要额外配置
- 两种代理都无法代理 `final` 类和 `final` 方法（CGLIB 也无法重写 `final` 方法）

#### 追问

**Q**: Spring Boot 为什么默认改成 CGLIB？

**A**: 简化配置，避免接口的强制要求；CGLIB 的调用性能更好；现代应用中大部分 Bean 不需要被其他非代理类引用（接口的主要价值在于解耦，但在小型应用中不必要）。

> 🎯 **核心要点**：JDK代理 = **接口 + 反射**，CGLIB = **继承 + 字节码增强**。选择取决于目标对象是否有接口、是否需要代理非接口方法、以及性能要求。Spring 6 / Boot 3 开始内置 CGLIB，不再需要额外依赖。

### <a id="q10"></a>10. setAccessible(true)做了什么？有什么风险？

**面试官意图**：考察反射安全机制的理解，以及是否了解 Java 模块化系统带来的影响。

#### 表面回答

`setAccessible(true)` 取消 Java 语言访问检查，让反射可以访问 private 字段和方法。有安全风险，Java 9+ 模块化限制了其使用。

#### 原理级回答

```java
public class AccessibleDemo {
    private String secret = "这是私密数据";

    public static void main(String[] args) throws Exception {
        AccessibleDemo demo = new AccessibleDemo();

        Field field = AccessibleDemo.class.getDeclaredField("secret");

        // 没有 setAccessible 时：
        // field.get(demo); // ❌ IllegalAccessException

        // setAccessible(true) 做了什么？
        field.setAccessible(true);

        // 现在可以访问了
        System.out.println(field.get(demo)); // "这是私密数据"

        // 甚至能修改
        field.set(demo, "数据被篡改！");
    }
}

// ==================== setAccessible 做了什么？ ====================
// 1. 设置 AccessibleObject 的 override 标志位为 true
// 2. 反射调用时检查 override 标志：若为 true → 跳过 access check
// 3. 在 Java 9+ 模块系统中，还需检查模块是否 export/open
//
// 源码路径: java.base/java.lang.reflect.AccessibleObject
// public void setAccessible(boolean flag) {
//     if (flag) {
//         setAccessible0(this, flag);
//     } else {
//         setAccessible0(this, flag);
//     }
// }
//
// private static void setAccessible0(AccessibleObject ao, boolean flag) {
//     if (flag && !override && !Reflection.areAccessChecked()) {
//         // Java 9+ 增加模块化检查
//         Module callerModule = Reflection.getCallerClass().getModule();
//         // 检查模块是否 open 给调用者
//         ...
//     }
//     ao.override = flag; // ← 核心就是设一个 boolean
// }
```

#### 风险分析

| 风险类型 | 说明 | 示例 |
|---------|------|------|
| 封装破坏 | 绕过 private/protected 访问控制 | 修改 `String` 内部 `byte[] value` |
| 线程安全破坏 | 修改 `final` 字段可能导致的不可预测行为 | 修改 `Integer` 缓存池 |
| 安全漏洞 | 绕过安全检查机制 | 修改 `SecurityManager` 字段 |
| 模块化限制 | Java 9+ 模块系统限制反射访问 | `--add-opens java.base/java.lang=ALL-UNNAMED` |

```java
// ==================== Java 9+ 模块化限制 ====================
// 在模块化系统中，即使 setAccessible(true) 也不够
// 还需目标模块 open 或 exports 包给调用者

// JDK 内部模块（如 java.base/java.lang）默认不 open
// 访问 String 的私有字段会抛 InaccessibleObjectException

// 启动参数开放：
// --add-opens java.base/java.lang=ALL-UNNAMED
// 或在模块描述文件 module-info.java 中 open

// Java 17 进一步加强：通过 JEP 403 强封装 JDK 内部 API
// --illegal-access=deny (Java 16+ 默认)
```

#### 加分项

- Java 9 引入模块化时提出了 `org.openjdk.jmh` 基准测试框架来解决 setAccessible 的问题
- Spring / Hibernate 等框架在 Java 9+ 需要 `--add-opens` 启动参数
- `--add-opens` 只影响指定模块，比 `setAccessible` 范围更精确
- Java 22+ 的 `Implicitly Declared Classes` 和 `Unnamed Variables` 进一步收紧了反射限制

> 🎯 **核心要点**：`setAccessible(true)` 本质是设置一个 `override` 标志位跳过访问检查。Java 9+ 模块化系统在此基础上增加了模块级的安全控制。在框架中它不可或缺，但在业务代码中应尽量避免。

### <a id="q11"></a>11. 如何用反射修改String的内容？

**面试官意图**：考察反射的实际运用能力，以及是否了解 String 的不可变性设计。

#### 表面回答

通过反射获取 `String` 内部的 `value` 字段（`byte[]` 或 `char[]`），然后修改数组内容。

#### 原理级回答

```java
import java.lang.reflect.Field;
import java.util.Arrays;

public class ModifyStringDemo {

    public static void main(String[] args) throws Exception {
        // ==================== 危险示例：修改 String ====================
        String str = "Hello, World!";
        System.out.println("修改前: " + str); // Hello, World!

        // 使用反射修改 String 内部
        modifyString(str, "已篡改!");

        System.out.println("修改后: " + str); // 已篡改!
        // 注意：str 是同一个引用，但内容变了！
        // 神奇的是，常量池中的字符串也可能受影响！

        // 更危险的操作：
        modifyString("Hello", "XXXXX");
        // 常量池中所有 "Hello" 都被改了！
        System.out.println("Hello"); // XXXXX
    }

    @SuppressWarnings("deprecation")
    public static void modifyString(String target, String replacement)
            throws Exception {
        // ==================== 获取 String 内部的 value 字段 ====================

        // Java 8 及以前：char[] value
        // Java 9+：byte[] value (Compact Strings 优化)
        Field valueField;

        try {
            // Java 9+: String 内部使用 byte[]
            valueField = String.class.getDeclaredField("value");
        } catch (NoSuchFieldException e) {
            // Java 8: String 内部使用 char[]
            valueField = String.class.getDeclaredField("value");
        }

        valueField.setAccessible(true);

        // 获取 value 数组
        Object value = valueField.get(target);

        // 将替换字符串的字符/字节写入
        if (value instanceof char[]) {
            // Java 8: char[] 类型
            char[] original = (char[]) value;
            char[] replacementChars = replacement.toCharArray();
            System.arraycopy(replacementChars, 0, original, 0,
                    Math.min(original.length, replacementChars.length));
        } else if (value instanceof byte[]) {
            // Java 9+: byte[] 类型 (ISO-8859-1 编码)
            byte[] original = (byte[]) value;
            byte[] replacementBytes = replacement.getBytes("ISO-8859-1");
            System.arraycopy(replacementBytes, 0, original, 0,
                    Math.min(original.length, replacementBytes.length));
        }
    }
}
```

#### Java 版本差异

| 版本 | 内部字段 | 编码方式 | 原因 |
|------|---------|---------|------|
| Java 6 | `char[] value` | UTF-16 | 每个 char 2字节 |
| Java 7/8 | `char[] value` | UTF-16 | 同上 |
| Java 9+ | `byte[] value` + `byte coder` | LATIN1 或 UTF-16 | Compact Strings 优化（大多数 Latin-1 字符节省 50% 内存） |

#### 为什么这是一个危险操作？

```java
public class DangerDemo {
    public static void main(String[] args) throws Exception {
        // ==================== 破坏安全隐患 ====================
        // String 常用于安全相关的判断，修改后会被绕过
        String password = "secret123";
        modifyString(password, "任意密码"); // 假设这里被攻击者利用

        if ("secret123".equals(password)) {
            // 这个判断仍然通过！因为常量池中的 "secret123" 也被改了
            // 或者 password 指向的内容被改了
        }

        // ==================== 破坏 HashMap 不可变性 ====================
        // String 作为 HashMap 的 key 依赖于不可变性
        // 修改后会导致 hash 值变化但 HashMap 中的 bucket 未更新
    }
}
```

> ⚠️ **危险操作！** 这是纯技术演示，**绝对不要在业务代码中使用**。String 被设计为不可变是有充分理由的：线程安全、常量池共享、HashMap key 的哈希值稳定等。

> 🎯 **核心要点**：通过反射获取 `String.value` 数组并修改内容可以"篡改"不可变对象。Java 9+ 使用 `byte[]` 和 `coder` 字段实现 Compact Strings 优化。此操作违反语言契约，仅用于理解反射的能力边界。

### <a id="q12"></a>12. @Retention三种策略有什么区别？什么时候用哪个？

**面试官意图**：考察注解的生命周期理解，以及是否知道 APT、运行时反射等机制的区别。

#### 表面回答

`SOURCE`：源码级，编译后丢弃；`CLASS`：编译到字节码，运行时不保留；`RUNTIME`：运行时保留，可通过反射读取。

#### 原理级回答

```java
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;

// ==================== SOURCE ====================
@Retention(RetentionPolicy.SOURCE)
@interface Getter {
    // 仅在源码中存在
    // 编译后 class 文件中没有该注解
}

// 使用场景：
// 1. Lombok 的 @Data, @Getter, @Setter — 编译期生成代码后，注解不再需要
// 2. @Override, @SuppressWarnings — 编译器指令
// 3. @NonNull (某些版本) — 源码级检查

// ==================== CLASS ====================
@Retention(RetentionPolicy.CLASS)
@interface ClassLevelAnnotation {
    // 编译到字节码中，但 JVM 不保留
    // 反射无法读取
}

// 使用场景：
// 1. 字节码分析工具（如 ASM、ByteBuddy）
// 2. 编译时注解处理器（APT）
// 3. Android 的注解（部分）
// 默认值！如果没有显式指定 @Retention，默认就是 CLASS

// ==================== RUNTIME ====================
@Retention(RetentionPolicy.RUNTIME)
@interface RuntimeAnnotation {
    // 源码 + 字节码 + 运行时全保留
    // 反射可以读取：method.getAnnotation(RuntimeAnnotation.class)
}

// 使用场景：
// 1. Spring 的 @Component, @Autowired, @Transactional
// 2. MyBatis 的 @Select, @Insert
// 3. JUnit 的 @Test
// 4. Jackson 的 @JsonProperty
// 5. 自定义运行时注解
```

#### 三种策略的完整生命周期对比

```
SOURCE:      源代码 → (编译器) → 丢弃
                         ↓
CLASS:       源代码 → 字节码 → (JVM) → 丢弃
                         ↓
RUNTIME:     源代码 → 字节码 → JVM → 运行时保留
```

| 策略 | 保留到 | 反射读取 | 典型应用 |
|------|-------|:-------:|---------|
| `SOURCE` | .java 文件 | 否 | Lombok、Override、SuppressWarnings |
| `CLASS` | .class 文件 | 否 | APT、字节码工具、默认策略 |
| `RUNTIME` | 运行时 | 是 | Spring、MyBatis、JUnit、Jackson |

#### 源码级回答

```java
// ==================== 字节码验证 ====================
// 分别用三种 Retention 注解一个类，然后 javap 查看

// @Retention(SOURCE)  → javap 中看不到注解
// @Retention(CLASS)   → javap 显示 RuntimeInvisibleAnnotations (运行时不可见)
// @Retention(RUNTIME) → javap 显示 RuntimeVisibleAnnotations (运行时可见)

// javap -verbose AnnotatedClass.class 输出：
// RuntimeVisibleAnnotations:
//   0: #12()  → RUNTIME 注解
// RuntimeInvisibleAnnotations:
//   0: #15()  → CLASS 注解
// SOURCE 注解 → 完全不在字节码中

// ==================== 注解属性的默认值 ====================
// @Retention 的默认值是 RetentionPolicy.CLASS
// 所以如果你写：
public @interface MyAnno {} // 没有 @Retention
// 等价于：
@Retention(RetentionPolicy.CLASS)
public @interface MyAnno {}
// 这是很多人忘记指定 RUNTIME 然后反射找不到的原因！
```

#### 加分项

- `@Inherited` 元注解可让子类继承父类的注解（仅对 RUNTIME 注解有效）
- Java 8 `@Repeatable` 允许同一位置重复使用相同注解
- Java 9 引入 `@Deprecated(forRemoval=true)` 等增强
- Kotlin 的注解定位点 (`@get:`, `@field:`, `@param:`) 提供了更精细的控制

> 🎯 **核心要点**：`SOURCE` 面向编译器/代码生成器，`CLASS` 面向字节码工具/APT，`RUNTIME` 面向框架/运行时处理。**框架开发几乎只用 RUNTIME**，因为需要反射读取。Lombok 用 SOURCE 是因为它在编译期已完成代码生成，运行时不需注解。

### <a id="q13"></a>13. Lombok的@Data是怎么工作的？它和APT有什么区别？

**面试官意图**：考察对编译期注解处理和代码生成的理解深度。

#### 表面回答

Lombok 在编译期修改 AST（抽象语法树），自动生成 getter/setter/toString/equals/hashCode 等方法。APT（Annotation Processing Tool）只能生成新的文件，不能修改现有文件。

#### 原理级回答

```java
// ==================== 使用对比 ====================
// Lombok 方式 (修改 AST)：
@Data // ← 编译时自动插入了 getter/setter/toString/equals/hashCode
public class User {
    private Long id;
    private String name;
}

// 反编译后看到的是 (Lombok 修改 AST 后)：
public class User {
    private Long id;
    private String name;

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    // ... toString, equals, hashCode ... 
}

// ==================== APT 方式 (生成新文件) ====================
// 注解：
@AutoValue
public abstract class User {
    public abstract Long id();
    public abstract String name();

    public static User create(Long id, String name) {
        return new AutoValue_User(id, name); // 生成 AutoValue_User.java
    }
}

// APT 生成 AutoValue_User.java (新文件)：
final class AutoValue_User extends User {
    private final Long id;
    private final String name;
    // ... 构造器、equals、hashCode、toString ...
}
```

#### 核心区别

| 对比维度 | Lombok | APT (Annotation Processing) |
|---------|--------|-----------------------------|
| 工作时机 | 解析阶段后，编译阶段前 | 编译阶段中的 Annotation Processing |
| 操作对象 | 内存中的 AST（语法树） | 生成新的 .java 源文件 |
| 能否修改现有类 | ✅ 可以 | ❌ 不能，只能生成新文件 |
| 实现方式 | JSR 269 未公开 API + 内部 hack | JSR 269 标准 API |
| 依赖 | 需 Lombok 插件（IDE 支持） | 纯编译期依赖 |
| 可调试性 | 较难（非标准 API） | 较好（标准 API） |
| 代表 | Lombok | AutoValue、Dagger、MapStruct |

#### Lombok 原理细节

```java
// Lombok 的核心工作流程：
// 1. 自定义 AnnotationProcessor 注册
//    在 META-INF/services/javax.annotation.processing.Processor 中声明
//    lombok.launch.AnnotationProcessorHider$AnnotationProcessor

// 2. 在 process() 中拦截所有注解
//    不限于 Lombok 自身的注解！它会拦截所有注解

// 3. 对于每个标有 @Data 等的类：
//    使用 javac 内部 API (com.sun.tools.javac.tree.JCTree)
//    修改内存中的 AST 语法树
//    在树中插入 getter/setter 等方法节点

// 4. 关键在于：
//    javac 的 com.sun.tools.javac.processing.JavacProcessingEnvironment
//    Lombok 使用了 javac 的未公开 API (内部 API)
//    因此需要 IDE 插件配合（在 Eclipse/JDT 中也需要对应实现）

// 简化的 AST 操作代码 (伪码)：
// public void process(JCClassDecl classNode) {
//     // 遍历字段
//     for (JCVariableDecl field : classNode.getFields()) {
//         // 生成 getter 方法 AST 节点
//         JCMethodDecl getter = makeGetterMethod(field);
//         // 插入到类中
//         classNode.defs = classNode.defs.append(getter);
//     }
// }
```

#### 为什么需要使用 IDE 插件？

```
普通编译：javac → APT → Lombok 修改 AST → 编译 → .class (包含生成的方法)
IDE 中：  IDE 用自身编译器（而非 javac）→ 无法触发 Lombok
         → 看到的源码中缺少 getter/setter → 编译错误
         → 需要 Lombok 插件让 IDE 编译器也执行同样的 AST 修改
```

#### 加分项

- Lombok 是"hack"了 javac 的未公开 API，因此版本兼容性是最大痛点
- MapStruct、Immutables、Record Builder 等通过标准 APT 生成新源码，兼容性更好
- Java 16 的 `record` 解决了 Lombok 的很多痛点（自动生成构造器、equals、hashCode、toString）
- Kotlin 的 `data class` 从语言层面解决了这个问题

> 🎯 **核心要点**：Lombok = **JSR 269 拦截注解处理** + **javac AST 操作（非标准API）**。它能在现有类中"注入"方法。APT 遵循标准 API，只能生成新文件。Lombok 是"侵入式"代码生成，APT 是"非侵入式"代码生成。Java 16+ 的 `record` 正逐步替代 Lombok 的核心功能。

### <a id="q14"></a>14. 如何实现一个自定义注解实现字段校验？

**面试官意图**：考察自定义注解 + 反射的实际编码能力。

#### 表面回答

定义注解 → 标记 `@Retention(RUNTIME)` 和 `@Target(FIELD)` → 实现一个校验器，通过反射读取字段和注解 → 执行校验逻辑。

#### 完整实现

```java
// ==================== 1. 定义校验注解 ====================

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.Field;
import java.util.*;

// === @NotBlank: 字符串不能为空 ===
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface NotBlank {
    String message() default "字段不能为空";
}

// === @Min / @Max: 数值范围 ===
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface Min {
    long value();
    String message() default "值太小";
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface Max {
    long value();
    String message() default "值太大";
}

// === @Length: 字符串长度 ===
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface Length {
    int min() default 0;
    int max() default Integer.MAX_VALUE;
    String message() default "长度不符合要求";
}

// === @EnumValue: 枚举值校验 (自定义) ===
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface EnumValue {
    // 限定的枚举类
    Class<? extends Enum<?>> value();
    String message() default "值不在允许的枚举范围内";
}

// ==================== 2. 用户实体 ====================
class User {
    @NotBlank(message = "用户名不能为空")
    private String userName;

    @Min(value = 1, message = "年龄必须大于0")
    @Max(value = 150, message = "年龄不能超过150")
    private Integer age;

    @Length(min = 6, max = 20, message = "密码长度6-20位")
    private String password;

    @EnumValue(value = UserStatus.class, message = "无效的用户状态")
    private String status;

    // 构造器和 setter
    public User(String userName, Integer age, String password, String status) {
        this.userName = userName;
        this.age = age;
        this.password = password;
        this.status = status;
    }
}

enum UserStatus {
    ACTIVE, INACTIVE, BANNED
}

// ==================== 3. 校验器 ====================
class ValidationResult {
    private final boolean valid;
    private final Map<String, String> errors = new LinkedHashMap<>();

    private ValidationResult(boolean valid) {
        this.valid = valid;
    }

    public static ValidationResult success() {
        return new ValidationResult(true);
    }

    public static ValidationResult failure() {
        return new ValidationResult(false);
    }

    public boolean isValid() { return valid; }

    public Map<String, String> getErrors() { return errors; }

    public void addError(String field, String message) {
        errors.put(field, message);
    }

    @Override
    public String toString() {
        return valid ? "校验通过" : "校验失败: " + errors;
    }
}

class Validator {
    public static ValidationResult validate(Object obj) {
        ValidationResult result = ValidationResult.success();
        Class<?> clazz = obj.getClass();

        // 遍历所有字段
        for (Field field : clazz.getDeclaredFields()) {
            field.setAccessible(true);
            Object value;
            try {
                value = field.get(obj);
            } catch (IllegalAccessException e) {
                continue;
            }
            String fieldName = field.getName();

            // === @NotBlank 校验 ===
            NotBlank notBlank = field.getAnnotation(NotBlank.class);
            if (notBlank != null) {
                if (value == null || value.toString().trim().isEmpty()) {
                    result = ValidationResult.failure();
                    result.addError(fieldName, notBlank.message());
                }
            }

            // === @Min / @Max 校验 ===
            if (value instanceof Number) {
                long num = ((Number) value).longValue();

                Min min = field.getAnnotation(Min.class);
                if (min != null && num < min.value()) {
                    result = ValidationResult.failure();
                    result.addError(fieldName, min.message());
                }

                Max max = field.getAnnotation(Max.class);
                if (max != null && num > max.value()) {
                    result = ValidationResult.failure();
                    result.addError(fieldName, max.message());
                }
            }

            // === @Length 校验 ===
            Length length = field.getAnnotation(Length.class);
            if (length != null && value instanceof String) {
                int len = ((String) value).length();
                if (len < length.min() || len > length.max()) {
                    result = ValidationResult.failure();
                    result.addError(fieldName, length.message());
                }
            }

            // === @EnumValue 校验 ===
            EnumValue enumValue = field.getAnnotation(EnumValue.class);
            if (enumValue != null && value instanceof String) {
                Class<? extends Enum<?>> enumClass = enumValue.value();
                boolean matched = false;
                for (Enum<?> e : enumClass.getEnumConstants()) {
                    if (e.name().equals(value)) {
                        matched = true;
                        break;
                    }
                }
                if (!matched) {
                    result = ValidationResult.failure();
                    result.addError(fieldName, enumValue.message());
                }
            }
        }

        return result;
    }
}

// ==================== 使用示例 ====================
public class ValidationDemo {
    public static void main(String[] args) {
        // 测试1: 合法数据
        User user1 = new User("张三", 25, "password123", "ACTIVE");
        System.out.println("user1: " + Validator.validate(user1));
        // 输出: user1: 校验通过

        // 测试2: 用户名为空
        User user2 = new User("", 25, "password123", "ACTIVE");
        System.out.println("user2: " + Validator.validate(user2));
        // 输出: user2: 校验失败: {userName=用户名不能为空}

        // 测试3: 年龄超出范围
        User user3 = new User("张三", 200, "password123", "ACTIVE");
        System.out.println("user3: " + Validator.validate(user3));
        // 输出: user3: 校验失败: {age=年龄不能超过150}

        // 测试4: 密码太短
        User user4 = new User("张三", 25, "abc", "ACTIVE");
        System.out.println("user4: " + Validator.validate(user4));
        // 输出: user4: 校验失败: {password=密码长度6-20位}

        // 测试5: 无效状态
        User user5 = new User("张三", 25, "password123", "UNKNOWN");
        System.out.println("user5: " + Validator.validate(user5));
        // 输出: user5: 校验失败: {status=无效的用户状态}
    }
}
```

#### 设计要点

| 设计决策 | 原理 | 说明 |
|---------|------|------|
| `@Retention(RUNTIME)` | 注解保留到运行时 | 反射才能读取 |
| `@Target(FIELD)` | 限制应用目标 | 避免误用在类或方法上 |
| `field.setAccessible(true)` | 反射访问私有字段 | 跳过访问检查 |
| `field.get(obj)` | 反射获取字段值 | 获取校验目标值 |
| `String message() default "..."` | 注解属性默认值 | 提供默认错误信息 |

#### 加分项

- 可以扩展 `@Pattern` (正则校验)、`@Email`、`@Future` 等复杂校验
- 真正的 Bean Validation (JSR 380) 支持级联校验：`@Valid` 注解嵌套对象
- 更优雅的设计：将校验逻辑抽象为 `ConstraintValidator` 接口，每种注解对应一个实现类（策略模式）

> 🎯 **核心要点**：自定义注解校验 = **RUNTIME注解定义规则** + **反射遍历字段获取值** + **策略模式执行校验逻辑**。核心在于用 `field.getAnnotation()` 判断字段是否需要校验，用 `field.get()` 获取值进行比较。这就是 Hibernate Validator / Spring Validation 的底层原理。

### <a id="q15"></a>15. Spring的@Autowired是怎么实现自动注入的？

**面试官意图**：考察对 IoC 容器的理解深度，是否看过 Spring 源码。

#### 表面回答

`@Autowired` 注解标记依赖，Spring 容器在创建 Bean 后，通过反射遍历字段，找到有 `@Autowired` 的字段并注入依赖。

#### 原理级回答

```java
// ==================== Spring @Autowired 完整工作流程 ====================

// 1. 容器启动阶段：
//    ClassPathBeanDefinitionScanner 扫描 @Component/@Service/@Repository
//    → 创建 BeanDefinition 注册到 BeanFactory

// 2. Bean 创建阶段（核心）：
//    AbstractAutowireCapableBeanFactory.doCreateBean()
//    ├── createBeanInstance()      → 反射创建对象 (Constructor)
//    ├── populateBean()            → 填充属性 (核心！)
//    └── initializeBean()          → 执行 Aware / BeanPostProcessor

// 3. populateBean() 中对 @Autowired 的处理：
//    调用 AutowiredAnnotationBeanPostProcessor
//    → 遍历所有 Field
//    → 找 @Autowired / @Value / @Inject
//    → 获取 field.getType() 作为依赖类型
//    → 调用 BeanFactory.getBean(Class) 查找依赖
//    → field.setAccessible(true)
//    → field.set(bean, dependency)  ← 反射注入！
```

#### Spring 源码简化

```java
// ==================== AutowiredAnnotationBeanPostProcessor (简化) ====================
public class AutowiredAnnotationBeanPostProcessor
        implements InstantiationAwareBeanPostProcessor {

    // 缓存每个类需要注入的元信息（避免重复反射）
    private final Map<Class<?>, InjectionMetadata> injectionMetadataCache
            = new ConcurrentHashMap<>(256);

    @Override
    public PropertyValues postProcessProperties(PropertyValues pvs,
            Object bean, String beanName) {

        // 1. 查找需要注入的字段/方法
        InjectionMetadata metadata = findAutowiringMetadata(beanName,
                bean.getClass(), pvs);

        // 2. 执行注入
        metadata.inject(bean, beanName, pvs);

        return pvs;
    }

    private InjectionMetadata findAutowiringMetadata(String beanName,
            Class<?> clazz, PropertyValues pvs) {

        // 缓存查找
        return injectionMetadataCache.computeIfAbsent(clazz, type -> {
            List<InjectionMetadata.InjectedElement> elements = new ArrayList<>();

            // 遍历所有字段
            for (Field field : type.getDeclaredFields()) {
                Autowired ann = field.getAnnotation(Autowired.class);
                if (ann != null) {
                    // 构建注入元信息
                    elements.add(new AutowiredFieldElement(field, ann.required()));
                }
            }

            // 遍历所有方法 (setter 注入)
            for (Method method : type.getDeclaredMethods()) {
                Autowired ann = method.getAnnotation(Autowired.class);
                if (ann != null) {
                    elements.add(new AutowiredMethodElement(method, ann.required()));
                }
            }

            return new InjectionMetadata(type, elements);
        });
    }

    // 字段注入执行
    private static class AutowiredFieldElement extends InjectionMetadata.InjectedElement {
        private final Field field;
        private final boolean required;

        @Override
        protected void inject(Object bean, String beanName, PropertyValues pvs) {
            // 核心注入逻辑
```

### <a id="q16"></a>16. Spring如何通过@Component注解创建Bean？

**面试官意图**：综合考察泛型+反射+注解在 Spring IoC 中的协同运用。

#### 表面回答

`@Component` 标记类 → Spring 扫描到 → 反射创建实例 → 放入容器。

#### 完整流程

```java
// ==================== 全流程串联 ====================  
// 
// 阶段1: 注解标记 (@Component)
// ┌─────────────────────────────────────────────────┐
// │ @Component                                      │
// │ public class UserService { ... }                │
// └─────────────────────────────────────────────────┘
//          ↓
// 阶段2: 反射扫描 (ClassPathScanningCandidateComponentProvider)
// ┌─────────────────────────────────────────────────┐
// │ 扫描 classpath 下所有 .class                   │
// │ → 读取字节码的注解元数据 (ASM)                 │
// │ → 不加载类！仅有 @Component 的才 Class.forName │
// └─────────────────────────────────────────────────┘
//          ↓
// 阶段3: 泛型约束 (BeanFactory<T>)
// ┌─────────────────────────────────────────────────┐
// │ BeanFactory 使用泛型保证类型安全：              │
// │ <T> T getBean(Class<T> requiredType)            │
// │ 使用方无需强转                                   │
// └─────────────────────────────────────────────────┘
//          ↓
// 阶段4: 反射创建 (Constructor.newInstance())
// ┌─────────────────────────────────────────────────┐
// │ clazz.getDeclaredConstructor().newInstance()    │
// │ → 创建 Bean 实例                                 │
// │ → 放入 singletonObjects 缓存                    │
// └─────────────────────────────────────────────────┘
//          ↓
// 阶段5: 依赖注入 (populateBean + @Autowired)
// ┌─────────────────────────────────────────────────┐
// │ 遍历所有 Field → @Autowired → 递归 getBean()   │
// → field.setAccessible(true) → Field.set(依赖)     │
// └─────────────────────────────────────────────────┘

// ==================== ClassPathScanningCandidateComponentProvider ====================
// Spring 的扫描不是用 ClassPathScanner 那么简单
// 它使用 ASM 字节码框架读取 .class 文件的注解
// 这样做的原因：避免加载大量不包含 @Component 的类

// 核心代码路径：
// ClassPathBeanDefinitionScanner.doScan()
// → ClassPathScanningCandidateComponentProvider.findCandidateComponents()
// → PathMatchingResourcePatternResolver.getResources("classpath*:**/*.class")
// → MetadataReader 使用 ASM 读取字节码 → 检查是否有 @Component
// → 有 → 注册 BeanDefinition → 后续由 BeanFactory 创建
```

#### 加分项

- Spring 使用 ASM 而非反射来扫描注解，因为性能更好（不需要加载类）
- `@Component` 的衍生注解：`@Service`, `@Repository`, `@Controller` 都被 `@Component` 元注解标记
- `@ComponentScan` 启动扫描，`@Filter` 控制扫描范围
- Spring 5 的构造函数注入是推荐方式，不需要 `@Autowired`

> 🎯 **核心要点**：Spring Bean创建 = **@Component注解(元数据)** + **ASM/反射扫描(发现)** + **泛型BeanFactory(约束)** + **反射创建和注入(执行)**。三者在整个过程中缺一不可。

### <a id="q17"></a>17. MyBatis的Mapper接口为什么能直接调用SQL？

**面试官意图**：综合运用动态代理+注解+泛型+反射来解释 MyBatis 的核心原理。

#### 表面回答

MyBatis 在启动时为 Mapper 接口创建 JDK 动态代理对象，代理拦截方法调用，解析注解或 XML 中的 SQL，执行并返回结果。

#### 完整流程

```java
// ==================== 核心四步 ====================
//
// 步骤1: 解析元数据
// ┌────────────────────────────────────────────────────────┐
// │ 扫描 Mapper 接口 → 解析 @Select/@Insert/@Update/@Delete│
// │ 或解析 XML 中的 <select>/<insert> 标签               │
// │ → 建立 MappedStatement: {sql, resultType, ...}       │
// └────────────────────────────────────────────────────────┘
//          ↓
// 步骤2: 创建代理
// ┌────────────────────────────────────────────────────────┐
// │ MapperProxyFactory.newInstance()                      │
// │ → Proxy.newProxyInstance(mapperInterface, handler)    │
// │ → 创建 MapperProxy (InvocationHandler)                │
// └────────────────────────────────────────────────────────┘
//          ↓
// 步骤3: 拦截调用
// ┌────────────────────────────────────────────────────────┐
// │ MapperProxy.invoke(proxy, method, args)               │
// │ → 1. 根据 method 查找 MappedStatement                 │
// │ → 2. 解析 args 绑定 SQL 参数 (#{id} → args[0])        │
// │ → 3. 执行 JDBC                                       │
// └────────────────────────────────────────────────────────┘
//          ↓
// 步骤4: 处理结果
// ┌────────────────────────────────────────────────────────┐
// │ 泛型 + 反射:                                          │
// │ → 通过 method.getGenericReturnType() 获取返回类型      │
// │ → 如果是 List<User>，解析出 User                      │
// │ → 反射创建 User 实例，设置字段值                       │
// │ → 返回结果                                            │
// └────────────────────────────────────────────────────────┘
```

#### MyBatis 源码关键点

```java
// ==================== MapperProxy (MyBatis 核心代理) ====================
public class MapperProxy<T> implements InvocationHandler, Serializable {

    // 缓存已解析的方法 → MappedStatement 映射
    private final Map<Method, MapperMethodInvoker> methodCache;

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        try {
            // Object 类方法直接放行
            if (Object.class.equals(method.getDeclaringClass())) {
                return method.invoke(this, args);
            }

            // 核心：从缓存获取 MapperMethodInvoker 并执行
            return cachedInvoker(method).invoke(proxy, method, args, sqlSession);

        } catch (Throwable t) {
            throw ExceptionUtil.unwrapThrowable(t);
        }
    }

    private MapperMethodInvoker cachedInvoker(Method method) throws Throwable {
        return methodCache.computeIfAbsent(method, m -> {
            // 解析方法 → 获取对应的 SQL 信息
            return new PlainMethodInvoker(
                    new MapperMethod(mapperInterface, method, config));
        });
    }
}

// ==================== 泛型返回类型处理 ====================
public class MapperMethod {
    // 方法签名——包含泛型处理
    public static class MethodSignature {
        private final Class<?> returnType;        // 原始返回类型
        private final Type genericReturnType;     // 泛型返回类型
        private final Class<?> resultType;        // 实际结果类型

        public MethodSignature(Configuration config, Class<?> mapperInterface,
                Method method) {
            this.returnType = method.getReturnType();
            this.genericReturnType = method.getGenericReturnType();

            // 核心：处理泛型返回类型
            if (this.returnType.isAssignableFrom(List.class)) {
                // 返回值是 List<T> → 获取 T
                Type actualType = ((ParameterizedType) genericReturnType)
                        .getActualTypeArguments()[0];
                this.resultType = (Class<?>) actualType;
            } else if (this.returnType.isArray()) {
                // 返回值是 T[] → 获取数组元素类型
                this.resultType = returnType.getComponentType();
            } else {
                // 简单类型 → 直接使用
                this.resultType = returnType;
            }
        }
    }
}
```

#### 加分项

- MyBatis 的 `@Param` 注解用来自定义参数名（解决 Java 8 之前无法获取参数名称的问题）
- MyBatis 3.5+ 支持 `Optional<T>` 返回类型
- 如果 Mapper 接口标注了 `@Mapper` 但没有被扫描，Spring Boot 会通过 `@MapperScan` 或 `@MapperScannerConfigurer` 注册

> 🎯 **核心要点**：MyBatis Mapper = **JDK动态代理**（魔法入口）+ **注解/XML SQL 解析**（配置读取）+ **泛型返回类型推导**（类型安全）+ **反射创建结果对象**。四步串联实现"接口即DAO"。

### <a id="q18"></a>18. 设计一个类似Retrofit的接口式HTTP客户端

**面试官意图**：最高难度——考察是否能在新场景中灵活运用三剑合璧。

#### 表面回答

类似 MyBatis 的 Mapper 原理：定义 HTTP 方法的注解（`@GET`, `@POST`），通过动态代理拦截接口调用，解析注解中的 URL 和参数，执行 HTTP 请求并反序列化响应。

#### 完整实现

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.*;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;

// ==================== HTTP 方法注解 ====================
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface GET {
    String value(); // URL 路径
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
@interface POST {
    String value();
}

// 请求参数注解
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.PARAMETER)
@interface Query {
    String value(); // 参数名
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.PARAMETER)
@interface Body {
}

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.PARAMETER)
@interface Path {
    String value(); // 路径变量名
}

// ==================== 响应封装 ====================
class Response<T> {
    private final int statusCode;
    private final T body;
    private final Map<String, String> headers;

    public Response(int statusCode, T body, Map<String, String> headers) {
        this.statusCode = statusCode;
        this.body = body;
        this.headers = headers;
    }

    public int code() { return statusCode; }
    public T body() { return body; }
    public boolean isSuccessful() { return statusCode >= 200 && statusCode < 300; }
}

// ==================== HTTP 客户端接口 ====================
// 用户定义的 API 接口
interface GitHubApi {
    @GET("/users/{username}")
    Response<User> getUser(@Path("username") String username);

    @GET("/users/{username}/repos")
    Response<List<Repo>> listRepos(@Path("username") String username);

    @POST("/repos/{owner}/{repo}/issues")
    Response<Issue> createIssue(
            @Path("owner") String owner,
            @Path("repo") String repo,
            @Body CreateIssueRequest request
    );
}

    // getter/setter 省略
}

// ==================== Mini Retrofit ====================
class MiniRetrofit {
    private final String baseUrl;
    private final Map<Class<?>, Object> apiCache = new ConcurrentHashMap<>();

    public MiniRetrofit(String baseUrl) {
        this.baseUrl = baseUrl.endsWith("/") ? baseUrl.substring(0, baseUrl.length() - 1) : baseUrl;
    }

    @SuppressWarnings("unchecked")
    public <T> T create(Class<T> apiClass) {
        // 泛型：返回类型 T 由调用方指定
        if (!apiClass.isInterface()) {
            throw new IllegalArgumentException("API must be an interface");
        }

        return (T) apiCache.computeIfAbsent(apiClass, clazz ->
                Proxy.newProxyInstance(
                        apiClass.getClassLoader(),
                        new Class[]{apiClass},
                        new RetrofitInvocationHandler<>(apiClass, baseUrl)
                )
        );
    }

    // ==================== 代理核心 ====================
    private static class RetrofitInvocationHandler<T> implements InvocationHandler {
        private final Class<T> apiClass;
        private final String baseUrl;

        RetrofitInvocationHandler(Class<T> apiClass, String baseUrl) {
            this.apiClass = apiClass;
            this.baseUrl = baseUrl;
        }

        @Override
        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            // Object 方法直接放行
            if (method.getDeclaringClass() == Object.class) {
                return method.invoke(this, args);
            }

            // 1. 解析 HTTP 方法和路径
            GET get = method.getAnnotation(GET.class);
            POST post = method.getAnnotation(POST.class);

            String httpMethod;
            String path;

            if (get != null) {
                httpMethod = "GET";
                path = get.value();
            } else if (post != null) {
                httpMethod = "POST";
                path = post.value();
            } else {
                throw new UnsupportedOperationException(
                        "No HTTP method annotation on " + method.getName());
            }

            // 2. 解析参数
            //    → @Path: URL 路径变量替换
            //    → @Query: 查询参数
            //    → @Body: 请求体
            Map<String, String> pathParams = new HashMap<>();
            Map<String, String> queryParams = new LinkedHashMap<>();
            Object body = null;

            Annotation[][] paramAnnotations = method.getParameterAnnotations();
            for (int i = 0; i < paramAnnotations.length; i++) {
                for (Annotation ann : paramAnnotations[i]) {
                    if (ann instanceof Path) {
                        pathParams.put(((Path) ann).value(), args[i].toString());
                    } else if (ann instanceof Query) {
                        queryParams.put(((Query) ann).value(),
                                args[i] != null ? args[i].toString() : null);
                    } else if (ann instanceof Body) {
                        body = args[i];
                    }
                }
            }

            // 3. 组装 URL: 替换 @Path 变量
            String url = baseUrl + path;
            for (Map.Entry<String, String> entry : pathParams.entrySet()) {
                url = url.replace("{" + entry.getKey() + "}", entry.getValue());
            }

            // 添加 @Query 参数
            if (!queryParams.isEmpty()) {
                StringBuilder queryString = new StringBuilder("?");
                for (Map.Entry<String, String> entry : queryParams.entrySet()) {
                    if (queryString.length() > 1) queryString.append("&");
                    queryString.append(entry.getKey()).append("=").append(entry.getValue());
                }
                url += queryString.toString();
            }

            // 4. 模拟 HTTP 请求 (实际应使用 HttpClient/OkHttp)
            System.out.println("[请求] " + httpMethod + " " + url);
            if (body != null) {
                System.out.println("[请求体] " + body);
            }

            // 5. 泛型 + 反射解析返回类型
            Type returnType = method.getGenericReturnType();
            Class<?> resultType = extractResultType(returnType);
            System.out.println("[返回类型] " + resultType.getName());

            // 6. 模拟 HTTP 响应
            //    实际应执行 HTTP 请求 → 获取 JSON → JSON 反序列化
            System.out.println("[模拟] HTTP 200 OK");
            System.out.println("=====================================");

            // 返回空结果 (实际应反序列化 JSON)
            return null;
        }

        // 关键：泛型返回类型解析
        private Class<?> extractResultType(Type returnType) {
            // 处理 Response<T> 泛型
            if (returnType instanceof ParameterizedType) {
                ParameterizedType pt = (ParameterizedType) returnType;
                Type rawType = pt.getRawType();
                if (rawType == Response.class) {
                    // 取出 T: Response<User> → User
                    Type actualType = pt.getActualTypeArguments()[0];
                    if (actualType instanceof Class) {
                        return (Class<?>) actualType;
                    } else if (actualType instanceof ParameterizedType) {
                        // Response<List<User>> → List
                        return (Class<?>) ((ParameterizedType) actualType).getRawType();
                    }
                }
            }
            return (Class<?>) returnType;
        }
    }
}
```

```java
// ==================== 核心区别 ====================
public class MethodHandleVsReflection {
    public static void main(String[] args) throws Throwable {
        String str = "hello";

        // Reflection: 经过层层包装
        Method method = String.class.getMethod("length");
        int len1 = (int) method.invoke(str);
        // 调用链路:
        //   Method.invoke()
        //   → MethodAccessor.invoke() (委派)
        //     → NativeMethodAccessorImpl.invoke() (首次)
        //       → 或 GeneratedMethodAccessor.invoke() (多次调用后 JIT 生成)
        //     每层都有参数检查、装箱、拆箱

        // MethodHandle: "函数指针"式调用
        MethodHandle mh = MethodHandles.lookup()
                .findVirtual(String.class, "length",
                        MethodType.methodType(int.class));
        int len2 = (int) mh.invokeExact(str);
        // 调用链路:
        //   MethodHandle.invokeExact()
        //   → LambdaForm 编译 (JIT 友好的调用路径)
        //     更少的类型检查、更少的包装
    }
}
```

| 对比维度 | Method.invoke | MethodHandle |
|---------|--------------|--------------|
| 本质 | 反射 API，面向方法对象 | 可执行符号引用，近似函数指针 |
| 调用方式 | 通过委派访问器 | 通过 LambdaForm |
| JIT 内联 | 困难（调用图不透明） | 容易（常量化后可完全内联） |
| 类型检查 | 运行时检查参数类型 | 链接时检查（invokeExact 严格匹配） |
| 性能 | 较慢（4-5x 直接调用） | 接近直接调用（1.1-1.5x）|
| 安全性 | 需 setAccessible | 受 lookup 模式控制 |

```java
// ==================== LambdaMetafactory 终极优化 ====================
// 原理：运行时生成一个实现了函数式接口的类

import java.lang.invoke.*;

@FunctionalInterface
interface StringProcessor {

public class LambdaMetaFactoryDemo {

    public static void main(String[] args) throws Throwable {
        String target = "Hello, World!";

        // ==================== 方式1: 直接调用 (基准) ====================
        long t1 = System.nanoTime();
        int r1 = 0;
        for (int i = 0; i < 10_000_000; i++) {
            r1 += target.length();
        }
        long t2 = System.nanoTime();

        // ==================== 方式2: 反射 ====================
        Method method = String.class.getMethod("length");
        long t3 = System.nanoTime();
        int r2 = 0;
        for (int i = 0; i < 10_000_000; i++) {
            r2 += (int) method.invoke(target);
        }
        long t4 = System.nanoTime();

        // ==================== 方式3: LambdaMetafactory ====================
        MethodHandles.Lookup lookup = MethodHandles.lookup();
        MethodHandle targetMethod = lookup.findVirtual(
                String.class, "length",
                MethodType.methodType(int.class));

        // 使用 LambdaMetafactory 生成 StringProcessor 实现
        CallSite site = LambdaMetafactory.metafactory(
                lookup,
                "process",                             // 函数式接口方法名
                MethodType.methodType(StringProcessor.class), // 工厂方法类型
                MethodType.methodType(int.class, Object.class), // 泛化签名 (擦除)
                targetMethod,                          // 实际调用的方法句柄
                MethodType.methodType(int.class, String.class)  // 具体签名
        );

        StringProcessor processor = (StringProcessor) site.getTarget().invokeExact();

        long t5 = System.nanoTime();
        int r3 = 0;
        for (int i = 0; i < 10_000_000; i++) {
            r3 += processor.process(target);
        }
        long t6 = System.nanoTime();

        System.out.println("直接调用:       " + (t2 - t1) / 1_000_000 + "ms");
        System.out.println("反射:           " + (t4 - t3) / 1_000_000 + "ms");
        System.out.println("LambdaMeta工厂: " + (t6 - t5) / 1_000_000 + "ms");
        // 结果: LambdaMetafactory 最接近直接调用性能！
        // 因为它生成的字节码相当于：
        // class $Generated implements StringProcessor {
        //     int process(String s) {
        //         return s.length();  // 直接调用，无反射！
        //     }
        // }
    }
}
```

#### 追问链的本质意义

```
这条追问链考察的是对「框架底层 → JVM 底层」的深度：

@Autowired                                        → IoC容器原理
  ↓ (反射 getDeclaredFields)                     → Class 元数据模型
    ↓ (setAccessible)                            → JVM 访问控制
      ↓ (反射性能)                               → JIT 优化认知
        ↓ (MethodHandle)                         → invokedynamic 指令
          ↓ (LambdaMetafactory)                  → 运行时字节码生成
                                                   → 终极性能优化
```

> 🎯 **核心要点**：这条连招链从最上层的框架注解使用，一路深挖到 JVM 字节码生成。每一层都在考察对"三剑合璧"的掌握深度。回答的关键不是记住每层的细节，而是展示你理解 **抽象层次** 的推进——从 API 使用到 JVM 内部机制，每一层都有明确的映射关系。
