## 1. 高并发核心指标体系 {#1}

### 1.1 四个核心指标

| 指标 | 定义 | 计算方式 | 典型目标 |
|------|------|---------|:---:|
| **QPS** | 每秒查询数 | 总请求数 / 秒 | API 网关: 10万+ |
| **TPS** | 每秒事务数 | 完成事务数 / 秒 | 订单: 1万+ |
| **RT** | 响应时间 | 请求发出→收到响应 | P99 < 200ms |
| **并发数** | 同时处理的请求数 | 系统同时承载的请求 | 受线程池/连接数限制 |

### 1.2 关键公式与小定律

```text
1. QPS 与并发数的关系
   QPS = 并发数 / 平均响应时间（秒）
   例：并发 100，RT=50ms → QPS = 100/0.05 = 2000

2. 利特尔法则 (Little's Law)
   L = λ × W
   L: 系统中平均请求数（并发数）
   λ: 请求到达率（QPS）
   W: 请求在系统中的平均停留时间（RT）

3. 阿姆达尔定律 (Amdahl's Law)
   加速比 = 1 / [(1-P) + P/N]
   P: 可并行化比例 → 串行部分决定加速上限

4. 二八原则
   80% 的请求消耗 20% 的资源（热点）
   优化应聚焦在那 20%
```

### 1.3 响应时间分位数

```text
不要只看平均 RT！平均值掩盖了长尾问题：

请求:  [10ms, 10ms, 10ms, 10ms, 2000ms]
平均 RT = 408ms   ← 看起来还行
P99    = 2000ms   ← 真实情况：1% 的用户等了 2 秒！
P50    = 10ms     ← 一半的用户很快

生产环境关注: P50 / P95 / P99 / P999
```

```java
// Micrometer 中配置分位数
@Bean
public TimedAspect timedAspect(MeterRegistry registry) {
    return new TimedAspect(registry);
}

// 或手动记录
Timer timer = Timer.builder("api.latency")
    .publishPercentiles(0.5, 0.95, 0.99)
    .register(meterRegistry);
timer.record(() -> doSomething());
```

## 2. 分层流量治理架构 {#2}

### 2.1 漏斗模型

```
          ┌─────────────────────────────┐
  客户端  │  CDN + 按钮防重 + 验证码      │  过滤 80%+
          └─────────────┬───────────────┘
                        │ 20%
          ┌─────────────▼───────────────┐
  网关层  │  Nginx 限流 + WAF + IP 黑名单  │  过滤 10%+
          └─────────────┬───────────────┘
                        │ 10%
          ┌─────────────▼───────────────┐
  服务层  │  Sentinel 限流 + 熔断 + 队列   │  过滤 8%+
          └─────────────┬───────────────┘
                        │ 2%
          ┌─────────────▼───────────────┐
  数据层  │  缓存命中 ≈90% → DB仅承受 0.2% │  过滤 1.8%+
          └─────────────┬───────────────┘
                        │ 0.2%
          ┌─────────────▼───────────────┐
  数据库  │  连接池 + 读写分离 + 分库分表   │  最终承载
          └─────────────────────────────┘
```

### 2.2 各层策略总览

| 层级 | 核心策略 | 技术实现 |
|------|---------|---------|
| **客户端** | 防重提交、CDN 缓存、验证码 | 按钮置灰、滑块验证 |
| **网关层** | IP 限流、黑名单、请求校验 | Nginx `limit_req_zone`、Kong/APISIX |
| **服务层** | 分布式限流、熔断降级、异步化 | Sentinel / Resilience4j |
| **缓存层** | 多级缓存、热点探测、预热 | Caffeine + Redis Cluster |
| **数据层** | 读写分离、分库分表、连接池 | ShardingSphere、HikariCP |
| **消息层** | 异步削峰、解耦 | RocketMQ / Kafka |

## 3. 限流算法全解 {#3}

### 3.1 四种核心算法对比

| 算法 | 原理 | 突发流量 | 平滑度 | 实现难度 |
|------|------|:---:|:---:|:---:|
| **固定窗口** | 计数周期内请求数 | ❌ 临界问题 | ⭐⭐ | 极低 |
| **滑动窗口** | 细分窗口平滑过渡 | ⚠️ 一般 | ⭐⭐⭐ | 中 |
| **漏桶** | 固定速率流出 | ❌ 丢弃 | ⭐⭐⭐⭐⭐ | 中 |
| **令牌桶** | 固定速率放令牌，有则通过 | ✅ 允许 | ⭐⭐⭐⭐ | 中 |

### 3.2 限流实现代码

```java
// ── 1. Guava RateLimiter（单机令牌桶）──
import com.google.common.util.concurrent.RateLimiter;

RateLimiter limiter = RateLimiter.create(1000.0);  // 1000 QPS

public void handleRequest() {
    if (limiter.tryAcquire(100, TimeUnit.MILLISECONDS)) {
        // 获取到令牌，处理请求
        process();
    } else {
        // 限流，快速失败
        throw new RateLimitException("系统繁忙，请稍后重试");
    }
}

// 带预热期的令牌桶（防止冷启动压垮系统）
RateLimiter warmup = RateLimiter.create(1000,  // 稳定速率
    3, TimeUnit.SECONDS);  // 预热时间
```

### 3.3 分布式限流 —— Redis + Lua

```java
/**
 * Redis Lua 令牌桶 —— 分布式限流
 * 支持动态调整速率，多服务实例共享
 */
public class RedisRateLimiter {

    private final StringRedisTemplate redis;

    /**
     * 尝试获取令牌
     * @param key 限流 key
     * @param maxTokens 桶容量（允许突发）
     * @param rate 令牌生成速率（个/秒）
     * @param requested 请求令牌数
     * @return true-通过，false-限流
     */
    public boolean tryAcquire(String key, long maxTokens,
                               long rate, int requested) {
        String lua = """
            local key = KEYS[1]
            local maxTokens = tonumber(ARGV[1])
            local rate = tonumber(ARGV[2])
            local requested = tonumber(ARGV[3])
            local now = tonumber(ARGV[4])

            -- 获取当前状态
            local bucket = redis.call('HMGET', key, 'tokens', 'lastRefill')
            local tokens = tonumber(bucket[1]) or maxTokens
            local lastRefill = tonumber(bucket[2]) or now

            -- 补充令牌
            local elapsed = math.max(0, now - lastRefill)
            local refill = math.floor(elapsed * rate / 1000)
            tokens = math.min(maxTokens, tokens + refill)

            -- 判断并扣减
            if tokens >= requested then
                tokens = tokens - requested
                redis.call('HMSET', key, 'tokens', tokens, 'lastRefill', now)
                redis.call('EXPIRE', key, 60)
                return 1
            end
            return 0
            """;

        Long result = redis.execute(
            (RedisCallback<Long>) conn -> conn.eval(
                lua.getBytes(),
                ReturnType.INTEGER,
                1,
                key.getBytes(),
                String.valueOf(maxTokens).getBytes(),
                String.valueOf(rate).getBytes(),
                String.valueOf(requested).getBytes(),
                String.valueOf(System.currentTimeMillis()).getBytes()
            )
        );
        return result != null && result == 1;
    }
}
```

### 3.4 Sentinel 集成

```java
// ── Sentinel 限流 + 熔断注解 ──
@RestController
public class OrderController {

    @GetMapping("/order/create")
    @SentinelResource(
        value = "createOrder",
        blockHandler = "createOrderBlocked",   // 限流/熔断回调
        fallback = "createOrderFallback"       // 异常回调
    )
    public ApiResponse<Order> createOrder(@RequestParam Long goodsId) {
        return ApiResponse.success(orderService.create(goodsId));
    }

    // 限流处理
    public ApiResponse<Order> createOrderBlocked(Long goodsId,
            BlockException ex) {
        return ApiResponse.error(429, "系统繁忙，请稍后重试");
    }

    // 异常兜底
    public ApiResponse<Order> createOrderFallback(Long goodsId,
            Throwable ex) {
        log.error("创建订单失败", ex);
        return ApiResponse.error(500, "服务异常");
    }
}
```

## 4. 熔断降级与服务韧性 {#4}

### 4.1 熔断器三态转换

```
         ┌──────────┐
         │  CLOSED  │  ← 正常状态，请求通过
         │ (正常)    │
         └─────┬────┘
               │ 错误率 > 阈值
               ▼
         ┌──────────┐
         │   OPEN   │  ← 熔断打开，快速失败
         │ (熔断)    │
         └─────┬────┘
               │ 冷却时间到
               ▼
         ┌──────────┐
         │ HALF_OPEN│  ← 半开状态，试探性放行
         │ (试探)    │
         └────┬─────┘
              │
     成功 ↙       ↘ 失败
  CLOSED           OPEN（重新熔断）
```

### 4.2 Resilience4j 配置

```yaml
resilience4j:
  circuitbreaker:
    configs:
      default:
        sliding-window-type: COUNT_BASED    # 基于请求计数
        sliding-window-size: 100            # 窗口大小
        failure-rate-threshold: 50          # 失败率 > 50% 触发熔断
        wait-duration-in-open-state: 10s    # 熔断保持 10 秒
        permitted-number-of-calls-in-half-open-state: 5  # 半开试探 5 次
        automatic-transition-from-open-to-half-open-enabled: true
    instances:
      orderService:
        base-config: default

  retry:
    configs:
      default:
        max-attempts: 3
        wait-duration: 500ms
        exponential-backoff-multiplier: 2    # 指数退避
```

```java
@Service
public class OrderService {

    @CircuitBreaker(name = "orderService", fallbackMethod = "fallback")
    public Order createOrder(Long goodsId) {
        // 业务逻辑
    }

    // 降级方法
    public Order fallback(Long goodsId, Exception ex) {
        log.warn("订单服务熔断降级: {}", ex.getMessage());
        return Order.createPending(goodsId);  // 返回待处理状态
    }
}
```

### 4.4 降级策略总结

| 策略 | 实现 | 适用场景 |
|------|------|---------|
| **静态兜底** | 返回默认值 | 推荐列表、广告位 |
| **缓存兜底** | 返回上一次成功数据 | 商品详情、用户信息 |
| **降级开关** | 关闭非核心功能 | 双11关闭退货、取消订单 |
| **队列缓冲** | 写入队列异步处理 | 下单、支付回调 |
| **优雅降级** | 简化计算逻辑 | 精准推荐→热门推荐 |

## 5. CAP 理论与 BASE 最终一致性 {#5}

### 5.1 CAP 定理

```text
              ┌───────┐
              │   C   │  一致性 (Consistency)
              │ 一致性  │  所有节点同时看到相同数据
              └───┬───┘
                  │
      ┌───────────┼───────────┐
      │           │           │
┌─────▼─────┐    │    ┌──────▼──────┐
│     A     │    │    │      P      │
│   可用性   │    │    │  分区容错     │
│           │    │    │             │
│ 每个请求   │    │    │ 网络分区时  │
│ 都有响应   │    │    │ 系统继续工作 │
└───────────┘    │    └─────────────┘
                  │
        高并发系统 → 选择 AP（牺牲强一致）
        金融系统   → 选择 CP（牺牲可用性）
```

### 5.2 BASE 理论 ⭐

```text
BASE = Basically Available + Soft State + Eventually Consistent

核心思想：
  CAP 说三者不可兼得 → BASE 说可以"柔性"折中

Basically Available（基本可用）
  系统出现故障时，允许损失部分可用性
  例：双 11 时关闭退货功能，保证下单可用

Soft State（软状态）
  允许系统中的数据存在中间状态
  例：订单"支付中"状态，不用立即确定成功或失败

Eventually Consistent（最终一致性）
  不要求数据实时一致，但保证最终一致
  例：支付成功后，订单状态在 3 秒内变为"已支付"
```

## 6. 高并发架构演进路径 {#6}

```text
阶段1: 单体架构
├── QPS: < 100
├── 所有逻辑一个 WAR/JAR
└── 瓶颈: 数据库连接数

阶段2: 读写分离 + 缓存
├── QPS: 100 - 1000
├── 主库写 + 从库读
├── Redis 引入缓存
└── 瓶颈: 单库写压力

阶段3: 垂直拆分 (微服务)
├── QPS: 1000 - 5000
├── 按业务拆服务 (用户/订单/商品)
├── RPC 通信 (Dubbo/gRPC)
└── 瓶颈: 热点服务、分布式事务

阶段4: 水平扩展 + 消息队列
├── QPS: 5000 - 50000
├── 同服务多实例 + 负载均衡
├── MQ 削峰解耦
└── 瓶颈: 数据库成为单点

阶段5: 分库分表 + 读写分离集群
├── QPS: 50000+
├── ShardingSphere 分片
├── 多级缓存 (L1+L2)
└── 瓶颈: 跨分片查询、分布式事务

阶段6: 云原生弹性架构
├── QPS: 弹性伸缩
├── K8s HPA 自动扩缩
├── Service Mesh (Istio)
├── Serverless 冷启动
└── 趋势: 从"扛得住"到"自适应"
```

> 🎯 **核心要点**：高并发设计是一个**分层过滤**的过程——不是在某一层硬扛，而是让每一层拦住自己能处理的流量，最终到达数据库的请求极少。
