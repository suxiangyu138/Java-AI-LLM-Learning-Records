## 1. 锁优化策略 {#1}

### 1.1 锁升级路径与选型决策

```
Java 锁升级路径（synchronized 自动完成）：

偏向锁 → 轻量级锁 (CAS) → 重量级锁 (OS Mutex)

决策树：
│
├── 竞争极低（通常单线程访问）
│   └── synchronized (偏向锁，几乎零开销)
│
├── 读多写少（缓存、配置）
│   └── ReentrantReadWriteLock 或 StampedLock
│
├── 写操作多但极短
│   └── synchronized (轻量级锁 CAS 自旋)
│
├── 需要超时/tryLock/公平锁/多条件
│   └── ReentrantLock
│
├── 极高并发 + 极短临界区
│   └── 无锁编程 (Atomic / LongAdder)
│
└── synchronized 块内有 IO 操作（虚拟线程）
    └── 换成 ReentrantLock（避免 Pinning）
```

### 1.2 StampedLock —— 读写锁的升级版

```java
public class StampedLockCache {
    private final StampedLock lock = new StampedLock();
    private final Map<String, Object> cache = new HashMap<>();

    // ── 乐观读（无锁，适用于读多写极少）──
    public Object readOptimistic(String key) {
        long stamp = lock.tryOptimisticRead();  // 获取乐观读戳记，无锁！
        Object value = cache.get(key);

        if (!lock.validate(stamp)) {            // 戳记失效 → 说明有写操作
            stamp = lock.readLock();            // 降级为悲观读锁
            try {
                value = cache.get(key);
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return value;
    }

    // ── 写操作 ──
    public void write(String key, Object value) {
        long stamp = lock.writeLock();
        try {
            cache.put(key, value);
        } finally {
            lock.unlockWrite(stamp);
        }
    }
}
```

| 锁类型 | 读并发 | 写并发 | 使用场景 |
|------|:---:|:---:|------|
| synchronized | ⭐⭐ | ⭐⭐ | 通用，简单可靠 |
| ReentrantLock | ⭐⭐ | ⭐⭐ | 需要 tryLock/超时/Condition |
| ReadWriteLock | ⭐⭐⭐⭐ | ⭐ | 读多写少（配置、字典） |
| StampedLock | ⭐⭐⭐⭐⭐ | ⭐ | 读极多写极少（缓存） |
| Atomic/LongAdder | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | 计数器、统计 |

### 1.3 锁优化技巧

```java
// ── 1. 减小锁粒度 ──
// ❌ 粗粒度：整个方法加锁
public synchronized void updateUser(Long id, String name) { ... }

// ✅ 细粒度：只锁关键资源
private final ConcurrentHashMap<Long, Object> locks = new ConcurrentHashMap<>();
public void updateUser(Long id, String name) {
    Object lock = locks.computeIfAbsent(id, k -> new Object());
    synchronized (lock) {
        // 只有同一用户的请求才互斥
    }
}

// ── 2. 锁粗化 ──
// ❌ 循环内反复加锁
for (int i = 0; i < 1000; i++) {
    synchronized (this) { count++; }
}
// ✅ 循环外加一次锁
synchronized (this) {
    for (int i = 0; i < 1000; i++) { count++; }
}

// ── 3. 读写分离 ──
// ❌ 读写都用同一把锁
// ✅ 读用 ConcurrentHashMap (无锁读)，写用锁保护

// ── 4. 伪共享避免 ──
// ❌ 相邻字段被不同线程频繁修改 → 缓存行颠簸
class Counter {
    volatile long count1;  // 同一缓存行
    volatile long count2;
}
// ✅ 填充缓存行（64 字节）
@Contended  // JDK 9+
class Counter {
    volatile long count1;
    volatile long count2;
}
```

## 2. 线程池深度调优 {#2}

> 📖 线程池 API 详见 [JUC-06-线程池与Executor框架](../02-JUC高并发编程/06-线程池与Executor框架.md)

### 2.1 参数计算公式

```java
/**
 * 线程池参数计算公式
 *
 * CPU 密集型 (计算为主，几乎无 IO)：
 *   核心线程数 = CPU 核数 + 1
 *   最大线程数 = CPU 核数 × 2
 *
 * IO 密集型 (网络/磁盘 IO 为主)：
 *   核心线程数 = CPU 核数 × 2
 *   最大线程数 = CPU 核数 / (1 - 阻塞系数)
 *
 *   阻塞系数 = IO 耗时 / (CPU 耗时 + IO 耗时)
 *   典型 Web 应用阻塞系数 ≈ 0.8 ~ 0.9
 *   例: 8 核 × 2 = 16 核心线程，最大 = 8/(1-0.9) = 80
 */

int cpuCores = Runtime.getRuntime().availableProcessors();

// IO 密集型配置
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    cpuCores * 2,        // corePoolSize: 核心线程
    cpuCores * 10,       // maxPoolSize:  最大线程
    60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(2000),   // 有界队列！
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略
);
```

### 2.2 队列选型

| 队列 | 特点 | 适用场景 |
|------|------|---------|
| `SynchronousQueue` | 无容量，来一个必须处理一个 | 瞬时高并发，需要快速伸缩 |
| `LinkedBlockingQueue` | 无界（不指定容量）| ❌ 不用——OOM 风险 |
| `LinkedBlockingQueue(N)` | 有界，FIFO | **推荐**，配合 CallerRunsPolicy |
| `ArrayBlockingQueue` | 有界，预分配内存 | 固定大小场景 |

### 2.3 拒绝策略实战

```java
// ── 策略对比 ──
// AbortPolicy:        抛异常（默认）
// CallerRunsPolicy:   提交者自己执行 ← 推荐：自然限流
// DiscardPolicy:      静默丢弃 ← 危险！
// DiscardOldestPolicy: 丢弃最旧 ← 可能丢弃重要请求

// ── 自定义拒绝策略：告警 + 记录 ──
public class AlertingRejectedPolicy implements RejectedExecutionHandler {
    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        // 1. 记录指标
        Metrics.counter("thread.pool.rejected").increment();

        // 2. 告警
        if (executor.getQueue().size() > executor.getQueue().remainingCapacity() * 0.9) {
            Alert.send("线程池队列使用率 > 90%");
        }

        // 3. 兜底：尝试放入队列（阻塞等待）
        try {
            executor.getQueue().offer(r, 500, TimeUnit.MILLISECONDS);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RejectedExecutionException("任务被拒绝", e);
        }
    }
}
```

### 2.4 动态线程池

```java
/**
 * 动态线程池 —— 接入配置中心，运行时调整参数
 * 核心：监听配置变更 → setCorePoolSize / setMaximumPoolSize
 */
@Component
public class DynamicThreadPoolManager {

    private final Map<String, ThreadPoolExecutor> pools = new ConcurrentHashMap<>();

    public ThreadPoolExecutor getOrCreate(String poolName) {
        return pools.computeIfAbsent(poolName, name -> {
            ThreadPoolConfig config = configCenter.get(name);
            ThreadPoolExecutor executor = new ThreadPoolExecutor(
                config.getCoreSize(), config.getMaxSize(),
                60, TimeUnit.SECONDS,
                new LinkedBlockingQueue<>(config.getQueueSize()),
                new ThreadPoolExecutor.CallerRunsPolicy()
            );

            // 注册指标
            registerMetrics(name, executor);
            return executor;
        });
    }

    // 监听配置变更 → 动态调整
    @EventListener
    public void onConfigChange(ThreadPoolConfigChangeEvent event) {
        ThreadPoolExecutor executor = pools.get(event.getPoolName());
        executor.setCorePoolSize(event.getNewCoreSize());
        executor.setMaximumPoolSize(event.getNewMaxSize());
        log.info("线程池 {} 参数更新: core={}, max={}",
            event.getPoolName(), event.getNewCoreSize(), event.getNewMaxSize());
    }
}

// 配合 Nacos/Apollo 配置中心实现：
// nacos 配置: threadpool.order.core=20
// 配置变更 → 发布 ConfigChangeEvent → 动态调整线程池
```

## 3. 缓存策略与多级缓存 {#3}

### 3.1 多级缓存架构

```
请求 → L1 本地缓存 (Caffeine) → L2 分布式缓存 (Redis) → L3 数据库
        命中率 ~70%              命中率 ~25%              命中率 ~5%

每层缓存意义：
  L1: 微秒级访问，无网络开销，JVM 堆内
  L2: 毫秒级访问，跨实例共享，高可用
  L3: 持久化保证，数据最终一致
```

```java
// ── L1 本地缓存 (Caffeine) ──
Cache<Long, Product> localCache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(60, TimeUnit.SECONDS)
    .recordStats()        // 开启统计（命中率监控）
    .build();

// ── 多级缓存查询 ──
public Product getProduct(Long id) {
    // L1: 本地缓存
    Product product = localCache.getIfPresent(id);
    if (product != null) return product;

    // L2: Redis
    String json = redis.opsForValue().get("product:" + id);
    if (json != null) {
        product = JSON.parseObject(json, Product.class);
        localCache.put(id, product);   // 回填 L1
        return product;
    }

    // L3: 数据库
    product = productMapper.selectById(id);
    if (product != null) {
        redis.opsForValue().set("product:" + id,
            JSON.toJSONString(product), 300, TimeUnit.SECONDS);
        localCache.put(id, product);
    }
    return product;
}
```

### 3.2 缓存三大问题及对策

```
┌─────────────────────────────────────────────────────────┐
│ 问题         │ 原因              │ 解决方案               │
├──────────────┼──────────────────┼───────────────────────┤
│ 缓存穿透      │ 查不存在的数据     │ 布隆过滤器 + 空值缓存   │
│              │ 每次都穿透到 DB   │                       │
├──────────────┼──────────────────┼───────────────────────┤
│ 缓存击穿      │ 热点 Key 过期瞬间  │ 互斥锁 (单线程回源)    │
│              │ 大量请求打到 DB   │ 逻辑过期 + 异步刷新     │
├──────────────┼──────────────────┼───────────────────────┤
│ 缓存雪崩      │ 大量 Key 同时过期 │ TTL 加随机值 (60-90s)  │
│              │ 或 Redis 宕机     │ Redis Cluster 高可用  │
└─────────────────────────────────────────────────────────┘
```

```java
// ── 缓存击穿：互斥锁方案 ──
public Product getProductWithLock(Long id) {
    Product product = getFromCache(id);
    if (product != null) return product;

    // 单线程回源加载
    String lockKey = "lock:product:" + id;
    try {
        if (redis.setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS)) {
            product = productMapper.selectById(id);
            setCache(id, product, 60 + ThreadLocalRandom.current().nextInt(30));
        } else {
            Thread.sleep(50);  // 等待其他线程加载
            product = getFromCache(id);  // 重试读缓存
        }
    } finally {
        redis.delete(lockKey);
    }
    return product;
}

// ── 缓存雪崩：TTL 随机化 ──
int ttl = 300 + ThreadLocalRandom.current().nextInt(60);  // 5-6 分钟随机
redis.opsForValue().set(key, value, ttl, TimeUnit.SECONDS);
```

## 4. 批量处理与异步化 {#4}

### 4.1 请求合并

```java
/**
 * 请求合并 —— 将短时间内多个相同查询合并为一次批量查询
 * 思想：Hystrix Request Collapsing 的简化实现
 */
public class RequestCollapser {
    private final LinkedBlockingQueue<Request> queue = new LinkedBlockingQueue<>();
    private final ScheduledExecutorService scheduler =
        Executors.newSingleThreadScheduledExecutor();

    public RequestCollapser() {
        // 定时批量处理（每 50ms 或攒够 100 个）
        scheduler.scheduleWithFixedDelay(this::batchProcess,
            50, 50, TimeUnit.MILLISECONDS);
    }

    public CompletableFuture<Product> getProduct(Long id) {
        CompletableFuture<Product> future = new CompletableFuture<>();
        queue.offer(new Request(id, future));
        return future;
    }

    private void batchProcess() {
        List<Request> batch = new ArrayList<>();
        queue.drainTo(batch, 100);  // 最多取 100 个

        if (batch.isEmpty()) return;

        // 批量查询
        List<Long> ids = batch.stream().map(r -> r.id).toList();
        Map<Long, Product> result = productService.batchGet(ids);

        // 分发结果
        for (Request req : batch) {
            req.future.complete(result.get(req.id));
        }
    }
}
```

### 4.2 异步削峰 —— MQ + 线程池组合

```java
// ── 生产者：快速接收请求，写入 MQ ──
@PostMapping("/order")
public ApiResponse<String> createOrder(@RequestBody OrderRequest req) {
    String orderId = UUID.randomUUID().toString();
    // 1. Redis 预扣库存（快速校验）
    if (!redisLua.deductStock(req.getGoodsId(), req.getUserId())) {
        return ApiResponse.error(400, "库存不足");
    }
    // 2. 发送 MQ，立即返回
    rocketMQ.send("ORDER_TOPIC", new OrderMessage(orderId, req));
    return ApiResponse.success(orderId + " 排队中");
}

// ── 消费者：异步消费，从容处理 ──
@RocketMQMessageListener(topic = "ORDER_TOPIC", consumerGroup = "order-group")
public class OrderConsumer implements RocketMQListener<OrderMessage> {

    // 限流消费：最多 500 TPS
    private final RateLimiter limiter = RateLimiter.create(500);

    @Override
    public void onMessage(OrderMessage msg) {
        limiter.acquire();  // 匀速消费

        // 幂等性校验
        if (orderMapper.exists(msg.getOrderId())) {
            return;  // 已处理，跳过
        }

        // 事务：减库存 + 创建订单
        orderService.createOrderInTx(msg);
    }
}
```

## 5. JVM 高并发调优 {#5}

### 5.1 GC 选型

| GC | 特点 | 高并发适用性 | JDK 版本 |
|----|------|:---:|:---:|
| **G1** | 低延迟，可预测暂停 | ⭐⭐⭐⭐ 通用 | JDK 9+ 默认 |
| **ZGC** | 亚毫秒级暂停 (<1ms) | ⭐⭐⭐⭐⭐ 极致低延迟 | JDK 15+ |
| **Shenandoah** | 并发回收，低暂停 | ⭐⭐⭐⭐ | JDK 15+ |
| Parallel | 高吞吐 | ⭐⭐⭐ 离线计算 | 所有版本 |
| Serial | 单线程 | ❌ 不适合 | 客户端小应用 |

```bash
# G1 GC 高并发配置
-XX:+UseG1GC
-XX:MaxGCPauseMillis=100          # 期望最大暂停
-XX:G1HeapRegionSize=16m          # Region 大小
-XX:G1ReservePercent=10            # 预留空间
-XX:InitiatingHeapOccupancyPercent=45  # 并发标记阈值
-XX:ConcGCThreads=4                # 并发 GC 线程
-XX:ParallelGCThreads=8            # 并行 GC 线程

# ZGC（JDK 21+ 分代 ZGC）
-XX:+UseZGC
-XX:+ZGenerational                 # 分代 ZGC
-Xms16g -Xmx16g
```

### 5.2 对象复用 —— 减少 GC 压力

```java
// ── 场景：高并发下频繁创建短生命周期对象 ──

// ❌ 频繁 new —— GC 压力大
for (Request req : requests) {
    StringBuilder sb = new StringBuilder();      // 每次 new
    sb.append(req.getId()).append(":").append(req.getData());
    process(sb.toString());
}

// ✅ ThreadLocal 复用 StringBuilder
private static final ThreadLocal<StringBuilder> SB_POOL =
    ThreadLocal.withInitial(() -> new StringBuilder(256));

for (Request req : requests) {
    StringBuilder sb = SB_POOL.get();
    sb.setLength(0);                              // 清空复用
    sb.append(req.getId()).append(":").append(req.getData());
    process(sb.toString());
}

// ✅ 对象池（适合重量级对象）
GenericObjectPool<HeavyObject> pool = new GenericObjectPool<>(
    new HeavyObjectFactory());
pool.setMaxTotal(50);    // 池大小

HeavyObject obj = pool.borrowObject();
try { obj.doWork(); }
finally { pool.returnObject(obj); }
```

### 5.3 伪共享 —— @Contended

```java
/**
 * 伪共享场景：两个 volatile long 紧挨着，在同一缓存行（64字节）
 * 线程 A 修改 count1 → 整个缓存行失效 → 线程 B 需要重新从内存加载 count2
 * 解决方案：填充使两个字段分布在不同缓存行
 */

// JDK 8: 手动填充
public class PaddedCounter {
    public volatile long value = 0;
    private long p1, p2, p3, p4, p5, p6, p7;  // 56 字节填充
}
// value(8) + padding(56) = 64 字节 = 一个缓存行

// JDK 9+: @Contended 注解（需 JVM 参数 -XX:-RestrictContended）
@Contended
public class ModernCounter {
    public volatile long value = 0;
}
```

> 🎯 **核心要点**：高并发性能优化的三个最高杠杆点——**锁选型**（减少竞争）、**缓存设计**（减少 IO）、**线程池调优**（减少等待）。GC 调优是兜底手段，先优化代码再调 JVM。
