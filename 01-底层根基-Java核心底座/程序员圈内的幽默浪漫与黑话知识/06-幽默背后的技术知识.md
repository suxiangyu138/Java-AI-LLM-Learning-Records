## 2. 「深陷」梗：递归与栈溢出

### 2.1 梗的原文

```text
「我写了个递归函数。然后调用了它。
然后栈溢出了。然后我明白了，
有些爱，越深陷越无法自拔。」
```

### 2.2 背后的技术

```text
递归（Recursion）——函数调用自身
├── ① 定义：函数直接或间接调用自己
├── ② 必要要素：
│   ├── 终止条件（Base Case）：没有则无限递归
│   └── 递归步骤：向终止条件推进
├── ③ 调用栈（Call Stack）：
│   ├── 每次调用压入栈帧（参数/局部变量/返回地址）
│   ├── 栈深度有限（默认约 1MB）
│   └── 无限递归 → 栈溢出（StackOverflowError）
├── ④ 经典示例：
│   // 正确递归（阶乘）
│   long factorial(int n) {
│       return n <= 1 ? 1 : n * factorial(n - 1);
│   }
│   // 无限递归（栈溢出）
│   long bad(int n) {
│       return n * bad(n);   // 无终止条件！
│   }
└── ⑤ 工程实践：
    ├── 深度受限（递归层数大用迭代）
    ├── 尾递归优化（部分语言支持）
    └── 日志排查：栈溢出看调用链（谁在递归）
→ 详见：本仓库「数据结构与算法」系列
```

## 3. 「放不下」梗：内存泄漏

### 3.1 梗的原文

```text
「爱上一个人，就是内存泄露——
你永远释放不了。」
```

### 3.2 背后的技术

```text
内存泄漏（Memory Leak）——对象无法回收
├── ① 定义：不再使用的对象被「引用着」——GC 无法回收
├── ② Java 中的常见泄漏：
│   ├── 静态集合持有对象（static List 只增不减）
│   ├── 未关闭的资源（Connection/Stream/Reader）
│   ├── 监听器未注销（addListener 不 remove）
│   ├── 缓存无淘汰（Map 无限增长）
│   └── ThreadLocal 未清理（线程池场景）
├── ③ 后果：
│   ├── 内存持续增长（OOM 前兆）
│   ├── GC 频繁（Full GC 卡顿）
│   └── 最终 OutOfMemoryError
├── ④ 排查：
│   ├── jmap 堆转储 + MAT 分析
│   ├── 观察内存曲线（持续上升 = 泄漏）
│   └── 常见：集合类持有对象（Dominator Tree 找根）
└── ⑤ 预防：
    ├── 集合考虑弱引用（WeakHashMap）
    ├── 资源 try-with-resources
    ├── 缓存加淘汰策略
    └── 监听器随生命周期注销
→ 详见：本仓库「JVM 完整底层」系列
```

## 4. 「别乱动」梗：指针与引用

### 4.1 梗的原文

```text
「情人就是指针，用的时候一定要注意，
要不然就带来巨大的灾难。」
```

### 4.2 背后的技术

```text
指针/引用的风险（C/C++ 经典问题）
├── ① 野指针（Dangling Pointer）：
│   ├── 指向已释放内存的指针
│   ├── 后果：未定义行为（崩溃/数据损坏/安全漏洞）
│   └── 预防：释放后置 NULL
├── ② 空指针（Null Pointer）：
│   ├── 解引用 NULL → 崩溃（Java NPE）
│   └── Java 预防：Optional/判空（见「写代码的好习惯」）
├── ③ 悬垂引用（Java 场景）：
│   ├── 弱引用对象被回收后引用失效
│   └── 处理：判空 + 重新获取
├── ④ 共享引用（并发场景）：
│   ├── 多线程共享可变对象 → 数据竞争
│   └── 预防：不可变对象/同步/ThreadLocal
└── ⑤ Java 的引用体系（4 种）：
    ├── 强引用：默认（不回收）
    ├── 软引用：内存不足时回收（缓存）
    ├── 弱引用：GC 即回收（WeakHashMap）
    └── 虚引用：回收通知（清理外部资源）
```

## 5. 「在我电脑上正常」梗：环境一致性

### 5.1 梗的场景

```text
「在我电脑上是正常的啊。」
——程序员最著名的「辩护词」
```

### 5.2 背后的技术（真实存在！）

```text
环境差异的真实来源（这个梗有技术依据）
├── ① 依赖版本差异：本机 jar 版本 vs 服务器
├── ② JDK 版本差异：本机 17 vs 服务器 8（行为不同！）
├── ③ 操作系统差异：Windows vs Linux（路径/换行符/编码）
├── ④ 数据库差异：本地 H2 vs 生产 MySQL
├── ⑤ 配置差异：本机 yml vs 生产环境变量
├── ⑥ 时区/语言环境：默认 Locale 差异（格式化输出不同）
├── ⑦ 并发差异：本机单线程 vs 生产并发（竞态条件）

工程解法（让「本机能跑」变成「生产能跑」）
├── ① 容器化：Docker 统一环境（本机 = 生产）
├── ② 依赖锁定：lock 文件（见 Python 虚拟环境系列）
├── ③ 配置外部化：环境变量注入（见配置文件系列）
├── ④ 双环境 CI：Windows + Linux 矩阵测试
├── ⑤ 生产日志：日志带环境信息（快速对比）
└── ⑥ 金句：梗好笑是因为「真实」——环境一致性是真实工程问题
```

## 6. 「能跑就别动」梗：重构与回归

### 6.1 梗的场景

```text
「代码莫名其妙运行起来，就不要再动了。」
「// 这段代码别动，我也不知道为什么能跑」
```

### 6.2 背后的技术

```text
「能跑就别动」的合理与不合理
├── 合理的部分（真实风险）：
│   ├── 无测试保护的重构 = 高风险（改坏不知道）
│   ├── 玄学依赖：看似无关的代码实际有依赖
│   └── 回归风险：改了 A 坏了 B（无回归测试）
├── 不合理的部分（技术债）：
│   ├── 不重构 = 债越积越多（维护成本上升）
│   └── 不敢动 = 系统僵化（无法演进）

正确姿势（「写代码的好习惯」系列）
├── ① 测试先行：重构前建立测试（安全网）
├── ② 小步重构：一次一个改动（行为不变验证）
├── ③ 预备性重构：先让改变变容易（Kent Beck）
├── ④ 重构与功能分提交：可独立回滚
└── ⑤ 金句：不是「别动」而是「有把握地动」——
    测试是重构的底气（见测试驱动系列）
```

## 7. 「玄学问题」梗：非确定性

### 7.1 梗的场景

```text
「为什么刚刚能运行，现在就不行？
为什么他的可以跑，我的不能跑？
为什么加了日志就正常，去掉就报错？」
——终极哲学拷问
```

### 7.2 背后的技术

```text
「玄学问题」的非确定性根因（其实是科学！）
├── ① 竞态条件（Race Condition）：
│   ├── 多线程访问共享资源的时序问题
│   ├── 特征：有时对有时错（看时序）
│   └── 修复：同步/原子操作/不可变
├── ② 未初始化数据：
│   ├── 变量初始值依赖运行时状态
│   └── 修复：显式初始化
├── ③ 哈希相关：
│   ├── HashMap 扩容后顺序变化
│   └── 依赖迭代顺序的逻辑不稳定
├── ④ 浮点精度：
│   ├── 不同环境计算顺序 → 微小差异
│   └── 比较用阈值而非 ==
├── ⑤ 缓存一致性：
│   ├── 缓存未失效 → 旧数据
│   └── 修复：缓存策略 + 清理
├── ⑥ 时间相关：
│   ├── 依赖系统时间/时区 → 环境差异
│   └── 修复：统一 UTC
└── ⑦ 排查思路（对应「写代码的好习惯」调试篇）：
    ├── 复现 → 假设 → 验证（一次一个变量）
    └── 金句：没有玄学，只有「还没找到的确定性」
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 梗 = 概念的记忆钩子：先记住梗、再展开知识（深陷 = 递归）
> 2. 「放不下」= 内存泄漏：静态集合/未关资源/监听器未注销——jmap/MAT 排查
> 3. 「别乱动」= 指针风险：野指针/空指针/悬垂引用——Java 四种引用体系
> 4. 「本机正常」= 环境一致性：版本/OS/配置/并发差异——容器化 + 双环境 CI 是解法
> 5. 「能跑别动」= 重构风险：测试先行 + 小步重构——不是别动而是有把握地动
> 6. 「玄学问题」= 非确定性：竞态/未初始化/缓存/时间——没有玄学只有未找到的确定性
> 7. AI 梗背后是真实的 AI 工程问题——顺着梗的疑问走进知识体系
