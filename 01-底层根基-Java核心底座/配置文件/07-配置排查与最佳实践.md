## 1. 配置问题类型全景

> **背景**：配置问题占生产事故排查的相当比例——「配置没生效」「值不对」「环境不对」是高频排查诉求。
> **目的**：建立系统化的配置排查方法论，把「猜」变成「查」。
> **适用范围**：所有 Spring Boot 服务。
> **前提假设**：Spring Boot 提供了完整的配置可观测手段，问题 90% 可定位。

```text
配置问题四大类
├── ① 加载问题：配置文件没加载（命名/位置/编码）
├── ② 覆盖问题：值不是预期的（多来源优先级）
├── ③ 绑定问题：注入失败/类型错误（@Value/@ConfigurationProperties）
└── ④ 刷新问题：动态刷新不生效（@RefreshScope）

排查原则：先确认「哪个来源的哪个 key」——配置问题本质是来源定位问题
```

## 2. 排查三板斧

### 2.1 第一斧：启动加 --debug

```bash
# 启动时打印全部 PropertySource 加载顺序（最直观）
java -jar app.jar --debug

# 输出片段（关键信息）
# ============================
# The following 1 profile is active: "prod"
# ============================
# Property sources loaded:
#  1. configurationProperties
#  2. nacos: order-service-prod.yaml (NacosConfigData)
#  3. nacos: order-service.yaml
#  4. application.yml (classpath:/application.yml)
#  5. systemEnvironment
#  6. systemProperties
# ============================

→ 看什么：
├── ① 激活了哪个 profile（"The following 1 profile is active"）
├── ② 哪些配置源加载了、顺序如何（越靠上优先级越高）
└── ③ Nacos 配置源是否存在（没有 = Data ID 有问题）
```

### 2.2 第二斧：/actuator/env 端点

```bash
# 需要依赖：spring-boot-starter-actuator
# 查看全部配置源与值
curl localhost:8080/actuator/env

# 精准查询单个 key（最重要！）
curl "localhost:8080/actuator/env/myapp.timeout-ms"
# 返回：
{
  "propertySources": [
    {
      "name": "nacos:order-service.yaml",
      "property": {"value": 5000}          # ← 最终生效值 + 来源
    },
    {
      "name": "application.yml",
      "property": {"value": 3000}          # ← 被覆盖的低优先级源
    }
  ]
}

→ 价值：精准回答「这个 key 的最终值从哪来」——覆盖问题的标准解法
```

### 2.3 第三斧：Environment 编程式排查

```java
// 代码里遍历配置源（调试专用）
@Component
public class ConfigDebug {
    @Autowired
    private Environment env;

    public void dumpSources() {
        if (env instanceof ConfigurableEnvironment ce) {
            for (PropertySource<?> ps : ce.getPropertySources()) {
                log.info("配置源: {} (优先级位置: {})", ps.getName(), 
                         ce.getPropertySources().precedenceOf(ps));
            }
        }
    }

    // 查看某个 key 在所有源的值
```

## 3. actuator/env 深度使用

### 3.1 端点配置

```yaml
# application.yml（排查环境开启；生产按需）
management:
  endpoints:
    web:
      exposure:
        include: env,health,info    # 只暴露需要的
  endpoint:
    env:
      show-values: WHEN_AUTHORIZED  # 敏感值展示控制
```

### 3.2 常用查询

```bash
# 全部配置源总览
curl localhost:8080/actuator/env

# 单个 key 溯源（覆盖问题定位）
curl "localhost:8080/actuator/env/server.port"

# 特定来源的值
curl "localhost:8080/actuator/env/nacos:order-service.yaml"

# 前缀查询
curl "localhost:8080/actuator/env/myapp"
```

### 3.3 安全注意

```text
actuator/env 的安全边界
├── ⚠️ 该端点暴露全部配置（含敏感值！）
├── ⚠️ 生产环境必须：
│   ├── show-values: NEVER 或 WHEN_AUTHORIZED
│   ├── 端点只在内网/经网关暴露
│   └── Spring Security 保护（角色限制）
└── 排查完成后关闭（生产默认关闭 env 端点）
```

## 4. 常见配置问题定位表

| 症状 | 可能原因 | 定位方法 | 解法 |
|------|---------|---------|------|
| **属性为 null** | 文件没加载/拼写不符 | --debug 看配置源 | 查文件名/位置/拼写 |
| **值不是预期的** | 多来源覆盖 | /actuator/env/{key} | 按优先级调整来源 |
| **yml 不生效** | properties 与 yml 并存 | --debug 看顺序 | 统一只留一种 |
| **Nacos 没加载** | Data ID 不匹配 | --debug 找 Nacos 源 | 检查 app-name/profile/ext |
| **@Value 启动失败** | key 缺失 | 启动报错信息 | 加默认值或补配置 |
| **绑定失败** | 类型不匹配 | BindException 信息 | 校验配置值 |
| **动态刷新不生效** | 缺 @RefreshScope | 刷新日志 | 加 @RefreshScope |
| **中文乱码** | 文件编码 | 打开文件看 | UTF-8 无 BOM |
| **profile 不对** | 激活错误 | --debug 首行 | 检查 active 设置 |
| **配置中心失效** | Nacos 不可达 | HealthIndicator | 本地快照/兜底 |

## 5. 配置即代码：工程化实践

### 5.1 配置的版本管理

> 🎯 **配置即代码**：配置与代码同仓库、同评审、同版本——变更可追溯、可回滚：

```text
配置版本管理规范
├── ① 包内配置：Git 管理（application.yml 及模板）
├── ② 模板文件：application.example.yml（可提交，无真实值）
├── ③ 真实配置：不入库（.gitignore + 外部注入）
├── ④ 配置中心：Nacos 自带版本历史（变更可回滚）
└── ⑤ 变更流程：改配置 = 提 PR（评审后合入/发布）
```

### 5.2 配置校验自动化

```text
配置质量自动化三道闸
├── ① 语法校验：yamllint（格式/缩进/重复键）
├── ② 模板校验：配置模板与代码字段一致性（配置类测试）
├── ③ 集成校验：测试环境启动验证（配置可加载）
└── ④ 安全扫描：gitleaks（敏感信息检测）

CI 示例（GitHub Actions）：
  - name: 校验配置
    run: |
      yamllint src/main/resources/*.yml
      python validate_config.py src/main/resources/
```

## 6. 团队配置规范

### 6.1 命名与结构规范

```text
团队配置规范（Code Review 检查项）
├── ① 自定义配置统一前缀（myapp.*/app.*）——不裸奔
├── ② 敏感配置只留占位符（${DB_PASSWORD} 无默认值）
├── ③ 业务配置一律 @ConfigurationProperties（禁止散落 @Value）
├── ④ 配置文件统一 YAML（删 properties 防优先级冲突）
├── ⑤ 默认值写 Java 字段，不写配置文件
├── ⑥ 配置分组：server/spring/myapp/logging 分域
└── ⑦ 配置变更与代码同 PR（评审可见）
```

### 6.2 配置评审清单

```text
配置 PR 评审六查
[ ] 敏感信息？（密码/密钥/token → 占位符或拒绝合并）
[ ] 默认值合理？（不会静默用错环境）
[ ] 与环境相关？（应外部注入而非硬编码）
[ ] 命名统一？（前缀/命名风格）
[ ] 与代码绑定一致？（@ConfigurationProperties 字段匹配）
[ ] 是否需要配置中心？（动态性判断）
```

### 6.3 配置文档化

```text
配置文档化实践
├── ① README 配置说明：每个配置项的用途/范围/默认值
├── ② application.example.yml：带注释的模板（新成员参考）
├── ③ 配置变更记录：CHANGELOG 或 Nacos 变更历史
└── ④ 环境差异表：dev/test/prod 差异清单（部署参考）
→ 金句：配置没有文档 = 别人不敢改你的配置
```

## 7. 配置评审与审计

### 7.1 定期配置审计

```text
配置季度审计清单
├── ① 无用配置清理（grep 未引用的 key）
├── ② 敏感值检查（明文密码扫描）
├── ③ 默认值合理性（是否过度暴露）
├── ④ 环境一致性（prod 配置是否混入 dev 地址）
└── ⑤ 权限审计（配置中心/Secret 访问权限）
```

### 7.2 配置漂移检测

```text
配置漂移（配置与预期不符）检测
├── ① 基线比对：环境间配置 diff（dev vs prod 差异清单）
├── ② 运行态检查：/actuator/env 定期快照对比
├── ③ 告警：敏感配置值异常变化（密码变更未走流程）
└── ④ Nacos 审计：配置变更事件监控（谁改了什么）
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 配置问题 = 来源定位问题：三板斧（--debug 看源、/actuator/env 溯源、Environment 遍历）
> 2. actuator/env 是覆盖问题定位的标准工具——但要保护（生产禁开/脱敏）
> 3. 配置即代码：模板入库 + 真实配置外部注入 + 变更走 PR + Nacos 版本回滚
> 4. 配置质量自动化：yamllint + 配置绑定测试 + gitleaks 三道闸
> 5. 团队规范：统一前缀/占位符/@ConfigurationProperties/删 properties 防冲突——评审六查 + 季度审计防漂移
