## 1. 生产资源规划

SonarQube 是「重平台」——资源规划按扫描规模（项目数 × 分析频率 × 代码量）估算：

**最低配置**（小团队、每日扫描）：4 核 / 8GB 内存 / 50GB 磁盘——服务器本体 2GB 起步 + Elasticsearch 索引 1-2GB + 分析任务并发余量；**中规模**（50+ 项目、多语言）：8 核 / 16GB；**大规模**（百级项目、频繁分析）：16 核 / 32GB+（或集群化——Enterprise 版才支持多节点，Community 单节点上限）。**磁盘是增长项**：每次分析累积历史数据（问题、度量、快照）——按「每月 GB 级」规划，监控磁盘水位（下节）。

**数据库**：PostgreSQL（Community 主流）——版本配套（SonarQube 26.x 支持的 PG 版本看官方兼容矩阵）；**数据库是容量瓶颈**（分析历史全在库里）——与服务器同机或同内网低延迟。**「先算规模再买机器」**——按「未来一年的扫描量」规划，别按「今天的数据量」。

## 2. 生产部署形态

**Docker Compose**（单机生产，02 篇的完整形态）：官方镜像锁月版 tag + PostgreSQL + 数据卷 + 健康检查——**小团队标准答案**；**Kubernetes**（Helm 图表——官方 chart）：`sonarqube` Helm release——**多环境、自动扩缩、滚动升级**；**裸机/VM**：官方 zip + JDK21 + systemd——遗留环境。**部署选型**：有 K8s → Helm（升级是 `helm upgrade`——配合 04 篇升级流程）；无 K8s → Compose 足够（单机承载中规模无压力）。

**生产环境的四个必配**：**数据卷**（data/extensions 持久化——升级不丢）；**反向代理/TLS**（Nginx 终止 TLS——分析数据含源码信息，传输加密是底线；[[../../11-云原生/Docker/00-Docker总览|Docker 体系]] 与 [[../运维/Nginx%20基础|Nginx 体系]] 的配套姿势）；**健康检查**（`/api/system/status`——K8s 探针/Compose healthcheck）；**日志治理**（SonarQube 日志落盘 + 轮转——`logs/` 挂卷——排障与审计）。

## 3. 备份与恢复

**备份是运维底线**——SonarQube 的状态 = 数据库 + 配置 + 插件：**数据库**（PG `pg_dump`——分析结果、问题、门禁配置全在库里——**备份的核心**）；**配置**（`conf/sonar.properties` 等——升级前快照）；**插件**（`extensions/` 目录——第三方插件单独备份）。

**备份策略**：**每日数据库备份**（`pg_dump` 定时任务 + 保留 N 天）；**升级前手动快照**（库 + 配置 + 插件三件套）；**恢复演练**（每季度恢复一次到测试环境验证——「备份没验证过 = 没有备份」）。**恢复流程**：新机器 → 装同版本 → 恢复数据库 → 恢复配置/插件 → 启动验证。

## 4. 升级：月度节奏

**Community Build 的现实**：无 LTA——**bug 与安全修复只在下个月度版**——「升级是运维常态」而非「年度事件」。**升级节奏的权衡**：每月追新（安全修复及时、但要频繁验证）vs 隔月/季度追（省事、安全窗口扩大）——**推荐节奏：跟随月版 + 至少每季度一次**（安全修复窗口 ≤3 个月）。

**升级流程五步**（每步都有验证）：**备份**（库 + 配置 + 插件三件套）；**读 Release Notes**（破坏性变更、数据库迁移要求——**升级前必读**）；**检查插件兼容**（第三方插件对新版本兼容性——不兼容先卸）；**升级 + 验证**（新镜像起服务 → 健康检查 → 跑一次真实扫描对比结果）；**规则评审**（新规则是否纳入 Profile——07 篇——「升级不评规则 = 标准悄悄变」）。**跨大版本**（如跨多个 26.x 月版）——按官方升级路径逐步（中间版本要求见文档）。

## 5. 权限与安全模型

SonarQube 的权限模型：**全局权限**（Global Permissions——admin 管理平台、scan 执行分析、provision 创建项目）；**项目权限**（Project Permissions——browse 查看、administer 管理、issue 处理）；**用户与组**（组是权限管理单位——「按组授权、按人分配」）；**Token**（个人访问令牌——分析认证首选，02/05 篇）。

**安全基线**：**管理员账号最小化**（admin 只做平台治理——日常用普通账号）；**Token 权限最小化**（每个集成场景独立 Token——CI 的 Token 只给 scan 权限；吊销按场景不影响其他）；**HTTPS 全覆盖**（TLS 终止在反向代理——分析数据与 Token 不过明文）；**定期清理**（离职账号、过期 Token、僵尸项目——审计与治理）；**审计**（管理员操作日志——谁改了门禁、谁删了项目——平台治理的可追溯性）。

## 6. 性能与容量治理

**性能瓶颈的三大块**：**分析任务（Compute Engine）**——并发分析任务的吞吐（`sonar.ce.javaOpts` 调内存、`sonar.ce.workerCount` 调并发——服务器资源与队列的平衡）；**Elasticsearch 索引**——问题搜索与 Dashboard 的响应速度（索引内存分配、磁盘 IO）；**数据库**——历史数据查询（快照与度量的查询——索引维护）。

**容量治理**：**磁盘水位监控**（历史数据累积——`sonar.log.level` 与审计策略控制日志量、旧快照清理策略）；**扫描频率治理**（每日全量 + PR 增量——分析任务量是资源消耗的主因）；**性能观察指标**（分析任务队列长度、单次分析耗时、Dashboard 响应）——「平台慢了」先看这三项；**扩容路径**（单机升配 → 数据库分离 → 商业版集群——Community 单节点上限是架构边界，规模到了要算商业化的账）。

## 7. 常见坑

**坑一：备份只备数据库**。配置与插件丢失——升级回退不了——三件套。

**坑二：升级前不读 Release Notes**。数据库迁移要求没满足——升级失败——必读。

**坑三：插件不兼容硬升**。插件坏了平台挂——升级前检查插件兼容。

**坑四：升级后不评规则**。标准悄悄变——规则评审是升级流程一部分。

**坑五：Token 一个用到底**。泄漏无法单独吊销——按场景独立 Token。

**坑六：磁盘不监控**。历史数据撑爆磁盘——水位监控 + 清理策略。

**坑七：无恢复演练**。备份没验证过等于没有——季度演练。
