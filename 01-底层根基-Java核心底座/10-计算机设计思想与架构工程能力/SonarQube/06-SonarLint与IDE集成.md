## 1. SonarLint 是什么

SonarLint 是 SonarQube 的 IDE 插件（IntelliJ/VSCode/Eclipse 全支持）——**写代码时的实时静态分析**：敲完一行，潜在问题立刻以编辑器内高亮 + 修复建议的形式出现。它的价值在「成本位置」：**问题在诞生处修复成本最低**（写的时候改一行；合入后发现要翻代码、开工单、排期修——成本差一个数量级），SonarLint 把「发现问题的位置」从「CI 流水线」提前到「编辑器」。

**SonarLint 与 SonarQube 的关系**：SonarLint 是「IDE 触角」，SonarQube 是「平台大脑」——**单独用 SonarLint（未连接）**：内置规则独立工作（开箱即用，无需服务器）；**connected mode（连接）**：与 SonarQube 共享规则配置（07 篇 Quality Profile）与项目绑定——**「团队规则」在 IDE 里生效**（下节）。

## 2. 安装与实时分析

**安装**：IntelliJ IDEA → Settings → Plugins → 搜「SonarLint」安装；VSCode → Extensions → 搜 SonarLint。装完**对打开的项目自动分析**——默认开启。

**使用姿势**：**实时高亮**——代码里黄色/红色波浪线（按 severity）；**问题面板**——右侧 SonarLint 面板列出当前文件的问题（规则名、severity、说明、修复建议）；**快速修复**——部分规则提供自动修复（Alt+Enter 应用）；**文件级分析**——`Analyze → Analyze with SonarLint` 手动触发（大文件或关闭实时时）；**分析范围**——默认分析「修改的文件」（增量），可切换全项目分析（Analyze → Analyze all files）。

**体验设置**：**只分析变更文件**（大项目全量分析卡顿——SonarLint 默认增量设计）；**忽略规则**（项目内个别规则太吵——在项目级配置关闭，07 篇规则治理的 IDE 侧）。

## 3. 规则来源与配置

未连接模式下，SonarLint 的规则来自**内置规则集**（SonarSource 官方规则的 IDE 版——与 SonarQube 平台规则同源，但独立于服务器配置）。**配置入口**：Settings → Tools → SonarLint → Rules——按规则/语言/severity 启停。

**规则配置的三层来源**（从具体到全局）：**项目级 .sonarlint 配置**（随仓库共享——团队规则一致）；**IDE 用户级配置**（个人偏好——标记误报等）；**内置默认**（开箱即用）。**「规则在 IDE 里关掉 ≠ 平台不查」**——未连接模式下 IDE 配置与平台无关——**「IDE 不报但 CI 挂了」的割裂**就是未连接模式的典型痛点（connected mode 解决）。

## 4. connected mode

connected mode（连接模式）——SonarLint 与 SonarQube 建立连接，**平台配置下沉到 IDE**：

**配置步骤**（IntelliJ 示例）：Settings → SonarLint → SonarQube Connections → 添加服务器（URL + Token——02 篇的 Token 同样适用）→ 绑定项目（选择 SonarQube 里的 projectKey）。

**连接后的能力**：**规则同步**——IDE 用平台的 Quality Profile（团队在平台裁好的规则集——07 篇）——「IDE 与门禁同一套标准」；**项目绑定**——打开项目自动关联对应 projectKey；**问题与平台一致**——本地标 False Positive 的行为与平台联动（可选）；**「开发时就知道 CI 会说什么」**——门禁条件（覆盖率、新代码）在 IDE 有提示——**割裂消失**。

**connected mode 的前提**：需要能访问 SonarQube 服务器（内网可达）；个人 Token（权限最小化——09 篇权限模型）；**离线/隔离开发环境**：未连接模式兜底（内置规则仍工作）。

## 5. IDE 与平台的协作分工

「质量防线」的三层协作，SonarLint 是第一层：

**第一层（写代码时）：SonarLint**——实时消灭「明显问题」（格式、命名、常见 bug 模式）——**目标：提交前问题≈0**；**第二层（合入前）：CI 门禁**（05 篇）——新代码质量达标才合入——**目标：合入前卡住回归**；**第三层（合入后）：平台治理**——存量债、趋势、专项治理（07/09 篇）——**目标：债有清单、趋势向好**。

**三层分工的配合**：第一层做「日常」（每个开发者每行代码）、第二层做「关卡」（每个 PR）、第三层做「治理」（每个迭代）——**SonarLint 用得好，CI 门禁很少红**——门禁红说明「IDE 层漏了」（规则没同步/开发者没看）——三层互相校验，形成闭环。

**SonarLint 的推广与团队落地**：工具的威力取决于「用不用」——推广三件套：**写进团队规范**（「提交前 SonarLint 零 Blocker/Critical」是代码提交的隐形门槛——IDE 层的纪律，不依赖服务器）；**connected mode 一次配好**（团队文档给三步配置截图——连接服务器、绑定项目、规则同步——新人 5 分钟搞定）；**IDE 问题与平台问题对账**（团队例会抽查「IDE 报了但 CI 没报」的差异——规则同步问题的发现渠道）。**「SonarLint 是质量文化的日常载体」**——门禁是月末考试的关卡，SonarLint 是每天的作业本——日常用好了，关卡很少红。

## 6. 常见坑

**坑一：未连接模式当连接用**。IDE 规则与平台不一致——「IDE 没报 CI 挂了」——connected mode。

**坑二：大项目实时分析卡顿**。全量分析开启——只分析变更文件。

**坑三：IDE 关规则平台还查**。个人关掉 ≠ 团队不查——规则治理在平台 Profile（07 篇），IDE 只做显示。

**坑四：Token 用管理员账号**。个人 Token 权限最小化——按需分配项目权限。

**坑五：依赖 IDE 不依赖门禁**。「我 IDE 看了就行」——三层防线各有职责，门禁是机器执行的标准。

**坑六：SonarLint 不更新**。规则库随版本更新——IDE 插件定期更新（与平台版本配套意识）。

**坑七：误把 SonarLint 当平台**。「IDE 显示通过」不等于「门禁通过」——IDE 是增量局部、门禁是全量新代码 + 覆盖率——**两者范围不同，IDE 绿了 CI 红了是正常现象**（IDE 看代码，门禁看新代码 + 指标）。

**坑八：不配 connected mode 的团队割裂**。每人 IDE 各查各的——「为什么你 IDE 不报我 IDE 报」——connected mode 让规则统一，是团队标配不是可选。

**坑九：安全热点在 IDE 里被忽略**。热点标记为「安全」时没做人工审查——IDE 的一键标记要有审查动作（看规则说明、确认上下文）——「标记安全」是审查结论不是跳过按钮。

**坑十：IDE 分析结果不进团队统计**。SonarLint 本地修复的问题平台不知道——「IDE 修了 100 个，平台看不到」——平台度量的是「合入时」的质量，IDE 修得好会让门禁更顺——**IDE 的价值体现在「门禁通过率」的趋势里**，不需要单独统计。
