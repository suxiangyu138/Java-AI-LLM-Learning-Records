## 1. 语言支持全景

Community Build 的语言覆盖（2026 基线）：**16-20+ 种**——Java、JavaScript/TypeScript、Python、C#、PHP、Go、Kotlin、Ruby、Scala、HTML、CSS、XML、Terraform、CloudFormation 等；**商业版 35+ 种**（追加 C/C++/Objective-C/Swift/PL-SQL/ABAP/COBOL 等企业语言）。**语言支持的含义**：每种语言有独立的规则集（Quality Profile）、分析器与覆盖率集成方式。

**「一个平台管全部语言」的价值**：前端（JS/TS）+ 后端（Java/Python/Go）在同一平台、同一门禁体系、同一 Dashboard——**跨语言的质量标准统一**（后端要求新代码无 bug，前端同样）；跨语言的技术栈项目（全栈应用）一次扫描全分析（下节）。

## 2. 多模块项目配置

**单项目多模块**（Maven 多模块：`parent` + `module1` + `module2`）——**SonarQube 按「一个 projectKey 一个分析单元」**，三种姿势：

**姿势一：聚合分析（推荐）**——整个 Maven/Gradle 项目一个 projectKey，`mvn sonar:sonar` 自动聚合所有模块——**一个 Dashboard 看全貌**；**姿势二：分模块独立项目**——每个模块独立 projectKey（`-Dsonar.projectKey=parent:module1`）——模块各自门禁（适合模块独立发布）；**姿势三：混合**——聚合分析 + 模块级过滤（Dashboard 按模块切片看）。**选型**：模块共享发布节奏 → 聚合；模块独立演进 → 分项目。

**微服务仓库的姿势**：**monorepo**——多服务在一个仓库 → 每服务独立 projectKey（CI 里按目录分别扫描——`sonar.sources=services/order-service/src`）——服务级门禁；**多仓库**——每仓库一项目（默认姿势）。**「一个仓库一个 projectKey」是常见错误**——全仓扫成一个项目，门禁无法按服务卡（order 的红被 payment 的绿掩盖）。

## 3. 覆盖率集成

覆盖率（Coverage）是门禁的核心条件之一（04 篇），**SonarQube 不自己跑测试——它消费测试覆盖率报告**：

**Java + JaCoCo**（Maven 标准姿势）：

```xml
<!-- pom.xml：JaCoCo 生成覆盖率报告 -->
<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.12</version>
  <executions>
    <execution><goals><goal>prepare-agent</goal></goals></execution>
    <execution><id>report</id><phase>verify</phase><goals><goal>report</goal></goals></execution>
  </executions>
</plugin>
```

```bash
mvn clean verify sonar:sonar     # verify 阶段生成 jacoco.xml → sonar:sonar 自动读取
```

**其他语言的报告**：JS/TS（`sonar.javascript.lcov.reportPaths`——lcov 格式）；Python（`sonar.python.coverage.reportPaths`——coverage.py 的 XML）；Go（`sonar.go.coverage.reportPaths`——go test -coverprofile）。**要点**：**报告路径配置**（Scanner 不知道报告在哪——`sonar.<lang>.coverage.reportPaths`）；**报告生成与分析同一次构建**（`mvn verify sonar:sonar` 顺序执行）；**覆盖率指标按新旧两维**（`Coverage` 全量 + `Coverage on New Code` 门禁主力）。

## 4. 排除与边界配置

**排除（Exclusions）是分析配置的必做项**——不排除，报告会被噪音淹没（07 篇误报治理）：

```properties
# 生成代码与构建产物（最大噪音源）
sonar.exclusions=**/generated/**,**/target/**,**/build/**,**/dist/**
# 特定文件（历史遗留、第三方包装）
sonar.exclusions+=**/LegacyParser.java
# 测试代码独立管理（默认测试与主代码分开分析）
sonar.tests=src/test/java
# 覆盖率排除（生成的 DTO 等——测了没意义）
sonar.coverage.exclusions=**/dto/**,**/*Config.java
```

**边界配置的决策**：**生成代码必排**（Lombok 生成的、代码生成器产物——分析它们全是噪音）；**测试代码纳入分析**（`sonar.tests`——测试代码也有质量，但规则与门禁分开——`sonar.test.exclusions` 排除个别）；**覆盖率排除**（DTO/Config 类——「测了没价值」的类从覆盖率剔除——否则覆盖率虚低逼人写垃圾测试）。

## 5. Java 项目完整配置

Java/Spring 项目的完整配置模板（生产可直接抄）：

```properties
sonar.projectKey=my-backend
sonar.projectName=My Backend
sonar.sources=src/main/java
sonar.tests=src/test/java
sonar.java.binaries=target/classes
sonar.java.test.binaries=target/test-classes
sonar.sourceEncoding=UTF-8
sonar.java.coveragePlugin=jacoco
sonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml
sonar.exclusions=**/generated/**,**/dto/**
sonar.coverage.exclusions=**/dto/**,**/*Config.java,**/*Application.java
```

**要点**：**`sonar.java.binaries` 双件套**（主代码 + 测试代码编译产物——漏了测试二进制则测试代码分析不全）；**Spring 项目的典型排除**（启动类 `*Application.java` 覆盖率剔除——一行 main 方法）；**Maven 场景**——pom 里配好 JaCoCo 后，上述配置大半自动（`mvn sonar:sonar` 自动识别 sources/binaries）——**CLI 场景才需要全量手写**。

## 6. 前端与 Python 项目

**前端项目**（JS/TS/React/Vue）：**无编译产物需求**（解释型——直接扫源码）；**lcov 覆盖率**——Vitest/Jest 的 `lcov` 报告（`sonar.javascript.lcov.reportPaths=coverage/lcov.info`）；**node_modules 必须排除**（依赖目录——默认可能不排，显式配）；**TS 的 `tsconfig` 认知**（`sonar.typescript.tsconfigPaths`——多 tsconfig 项目配置）。

**Python 项目**：**直接扫源码**（无编译）；**覆盖率**——pytest + coverage.py 生成 XML（`sonar.python.coverage.reportPaths`）；**虚拟环境目录排除**（`.venv/`——同 node_modules 的噪音源）；**Python 规则集**（PEP8 风格 + 安全规则 + 复杂度）。

**多语言仓库**（全栈应用）：**一个 projectKey 多语言共扫**——`sonar.sources` 列全部源码目录（`src/main/java,src/main/js`）——每语言自动匹配规则与 Profile（按文件扩展名路由）；**每语言覆盖率分别配**（Java 的 jacoco.xml + JS 的 lcov.info 同一次扫描上报）。

**配置的工程化管理**：**`sonar-project.properties` 进仓库**（项目级配置随代码版本化——新开发者克隆即扫）；**公共配置进 CI 模板**（服务器地址、Token 引用、公共排除项——放流水线模板，不放每个项目手写）；**配置评审**（排除项、覆盖率路径的改动进 PR 评审——「排除太宽 = 漏检」是配置事故的一种）；**配置漂移检测**（CI 里定期对比「实际分析配置 vs 期望配置」——排除项被悄悄改宽时及时发现）。**「配置即代码」的纪律**：分析配置与业务代码同等级管理——改配置走评审、进历史、可回滚——「配置文件在某人电脑里」是团队事故的温床。

## 7. 常见坑

**坑一：monorepo 一个 projectKey**。服务级门禁失效——每服务独立键。

**坑二：node_modules/.venv 不排除**。依赖代码全是噪音——显式排除。

**坑三：覆盖率报告路径不配**。`Coverage` 指标为 0——`sonar.<lang>.coverage.reportPaths`。

**坑四：测试二进制漏配**。Java 测试代码分析不全——`sonar.java.test.binaries`。

**坑五：生成代码不排除**。最大误报源——`sonar.exclusions`。

**坑六：覆盖率排除不做**。DTO 拖低覆盖率逼垃圾测试——`sonar.coverage.exclusions`。

**坑七：报告生成与分析分离**。CI 里先跑测试后跑 sonar 但报告路径过期——同一构建内 verify + sonar 顺序执行。

**坑八：全栈项目只配一种语言**。前后端同仓库只配了 Java——前端代码完全漏检——`sonar.sources` 列出全部语言目录，覆盖率分别配（Java 的 jacoco + JS 的 lcov）。

**坑九：测试代码完全排除**。`sonar.tests` 不配——测试代码质量无人看管（测试烂了测试就没意义）——测试代码纳入分析，DTO 类单独剔除。

**坑十：覆盖率报告过大/缺失**。JaCoCo XML 几百 MB 或 CI 缓存问题——报告路径精确到文件（`target/site/jacoco/jacoco.xml` 而非目录），CI 清理机制保证每次构建重新生成——「覆盖率偶发为 0」先查报告文件存在性与时间戳。
