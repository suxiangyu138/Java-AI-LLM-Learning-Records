## 1. 平台定位

SonarQube 不是「一个检查工具」，而是「一个质量平台」：**服务器端承载分析引擎、规则库、项目数据与质量门禁；Scanner 在构建环境采集分析结果；SonarLint 在 IDE 给实时反馈**——三层构成从「写代码」到「合代码」的全链路质量闭环。平台的意义在于「积累」：问题不是查完就没了，而是入库跟踪（谁、何时、是否修复）、跨版本对比（技术债趋势）、门禁自动拦截（新问题不让进）。

2026 年的地位：**6500-7000 条确定性规则、700 万开发者用它构建流水线**——代码质量工具的行业标准（`SonarQube` 几乎是「静态分析」的同义词）；GitHub 上 6500+ stars、活跃维护。它的核心哲学是「Clean as You Code」——**关注新代码的质量，而不是一次修完历史债**（03 篇详解）。

## 2. 2026 版本格局

2026 年 SonarQube 的产品线分为两条，版本规则完全不同：

| 维度 | Community Build（免费） | SonarQube Server（商业） |
|------|------------------------|-------------------------|
| 定位 | 开源免费，无限用户/项目/扫描 | 企业版（Developer/Enterprise/Data Center） |
| 版本格式 | 日历版本 `YY.M.0.Build`（26.7.0.124771） | 年度版本（2026.1.4 / 2026.4.0） |
| 发布节奏 | 每月一发 | 季度级 + LTA（Long-Term Active） |
| 长期支持 | **无 LTA**（修复只在下个月度版） | 有 LTA 稳定线 |
| 运行时 | 需完整 JDK（JRE 不够），Java 21 | 同 |
| 语言支持 | 16-20+ 种 | 35+ 种（含 C/C++/Swift 等） |
| 分支/PR | **无分支分析、无 PR 装饰** | 有（PR 级反馈） |
| 安全分析 | 模式匹配（无数据流污点） | 数据流污点 + secrets 检测 |

**2026-08 基线**：Community Build 最新 **26.7.0.124771（2026-07-08）**——「26」周期自 2026-01-06 开始，逐月更新，**生产部署要跟上月度节奏或接受「上月的修复没有」**；商业线最新 2026.4.0。运行时要求：完整 JDK 21（不再是 JRE）、支持 ARM 架构与 IPv6。

## 3. 改名史与版本规则

理解版本乱象要先懂改名史：**Community Edition →（2024 年底）→ Community Build**——改名同时切断了与商业线的版本号关联。以前「10.x」是全家族统一版本，现在：**免费线用日历版本（26.7 = 2026 年 7 月）**，商业线用年度版本（2026.1 = 2026 年第一季度）——**看到「SonarQube 10.x」的老教程要意识到那是 2024 年前的版本**；看到「26.x」是免费线；看到「2026.x」是商业线。**部署选型**：免费够用（自托管、无限扫描）选 Community Build 锁月版；要 PR 级反馈、分支分析、数据流安全分析选 Developer 起——**「免费版缺什么」比「免费版有什么」更值得先了解**（第 6 节）。

## 4. 与静态分析工具族的关系

SonarQube 是「平台级」，工具族是「单点级」——同级 [[../代码质量/00-代码质量管理体系总览|代码质量体系]] 的完整全景：

| 工具 | 定位 | 与 SonarQube 关系 |
|------|------|------------------|
| SonarQube | 平台：全语言、门禁、度量 | 主角 |
| SpotBugs | Java 字节码级缺陷分析 | 同类能力（SonarQube Java 规则部分同源思路） |
| PMD | Java 源码级缺陷与坏味道 | 同类能力 |
| Checkstyle | Java 代码风格检查 | SonarQube 风格规则可替代 |
| SonarLint | IDE 实时反馈 | SonarQube 的 IDE 触角 |
| 代码审查 | 人工审查 | 与自动分析互补（机器查不了语义与设计） |

**分工逻辑**：单语言小项目可用 SpotBugs/PMD/Checkstyle 组合（轻量无服务器）；**多语言、要门禁、要历史趋势 → SonarQube 平台**（一站式、CI 集成、度量积累）。SonarQube 内置了工具族的绝大多数能力（Java 规则覆盖 SpotBugs/PMD 的常见项），不必叠装。

## 5. 解决什么问题

**「代码烂了才发现」**——上线后出 bug 才发现问题代码进了 main——质量门禁在合入前拦截（04 篇）；**「问题无人跟踪」**——review 说了不改——SonarQube 入库跟踪（谁、何时、修没修）；**「质量不可度量」**——「代码还行」没有数字——技术债、覆盖率、问题密度是量化指标（04 篇）；**「标准无法执行」**——规范写在 wiki 没人看——规则集 + 门禁让标准自动执行（07 篇）；**「安全漏洞后知后觉」**——安全热点与漏洞规则提前发现（03 篇）。**一句话**：SonarQube 把「质量」从「靠自觉」变成「靠机制」。**平台的三层闭环**——Scanner 分析（发现问题）→ 门禁判定（拦截问题）→ Dashboard 度量（跟踪问题）——每层都有自动化支撑，团队只需处理「被拦住的真问题」与「被误报的假问题」——这就是「平台」与「工具」的本质区别：工具给你报告，平台给你机制。

## 6. Community Build 的局限

选型前先看清免费版的三个硬边界：**无分支分析与 PR 装饰**——只分析 main 分支，问题在合入后才发现（PR 阶段没有自动反馈——CI 补偿姿势见 05 篇）；**安全分析是模式匹配**——无数据流污点分析（跨方法/跨类的注入类漏洞查不到）、secrets 检测缺失（商业版有）；**无企业治理**——无 portfolio 管理、无治理报表、无权限的细粒度（Data Center 才有）。**判断标准**：团队规模小、单 main 分支流、常规质量需求 → Community Build 足够；要 PR 级质量反馈、安全深度分析 → 预算内直接 Developer。**「免费版够用」的落地前提**：用 CI 脚本补偿 PR 反馈（05 篇），别假装局限不存在。

## 7. 五条边界

**不替代代码审查**——机器查不了设计、语义与业务正确性——自动分析 + 人工 review 互补（[[../代码质量/06-代码审查最佳实践|代码审查体系]]）。

**不替代测试**——覆盖率只测「测了多少」，测不到「测得对不对」——静态分析 + 单测 + 集成测试三层。

**不保证安全**——静态分析是安全左移的一环，不是全部——配合依赖扫描、渗透测试。

**不解决架构**——代码坏味道能提示，架构腐化要靠设计与治理。

**不豁免业务债**——技术债是代码层面的度量，「业务该不该做」是产品决策。
