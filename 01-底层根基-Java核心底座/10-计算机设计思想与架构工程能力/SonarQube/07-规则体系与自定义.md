# 07-规则体系与自定义
> 定位：规则集是「质量标准的表达」——Quality Profile 按语言裁剪规则、severity 定优先级、误报治理保可信度；规则治理的核心是「少而准」，不是「越多越好」。

## 1. Quality Profile 是什么

Quality Profile（质量配置档案）= **某种语言的规则集合**：哪些规则启用、每条规则的严重级（severity）——**「团队的质量标准」以 Profile 的形式存在平台上**。每个项目绑定一个 Profile（按语言分别绑定——Java 项目绑 Java Profile、JS 项目绑 JS Profile）；**每次分析时，项目按绑定的 Profile 跑规则**。

**Profile 的价值**：**标准可配置**（团队规范从 wiki 变成可执行配置）；**标准可演进**（改 Profile 一次生效——不用改任何代码）；**标准可复用**（新项目绑定同一 Profile）；**IDE 同步**（connected mode 把 Profile 下沉到 SonarLint——06 篇）。**「Profile 是规则的容器」**——规则库 6500+ 条是「原料」，Profile 是「选了哪些、定了几级」的成品。

## 2. severity 与规则激活

**severity 五档**（问题严重级，决定门禁与处理顺序）：**Blocker**（阻断级——必须修：崩溃、漏洞、资源泄漏）；**Critical**（严重——极可能出错：空指针、并发隐患）；**Major**（主要——大概率是 bug 或明显坏味道）；**Minor**（次要——可维护性问题）；**Info**（信息——提示性）。

**severity 的使用**：**门禁条件按 severity 卡**（`New Bugs` 实质是 Blocker+Critical 的新问题）；**处理顺序按 severity**（先 Blocker/Critical 再往下）；**同一规则可调 severity**（团队觉得某规则在自己场景更重/更轻——Profile 里调整）；**severity 与规则类型独立**（坏味道可以是 Critical——如「循环复杂度爆炸」；bug 也可以只是 Minor——如「日志参数顺序」）。

**规则激活的决策**：**默认 Profile 激活「高质量、低误报」规则**（Sonar way——社区共识）；团队按场景增删——**增规则问「这规则在团队场景误报率高吗」、删规则问「这条真不需要吗」**。

## 3. 内置 Profile 与新建

**内置 Profile（Sonar way）**：每语言一个默认 Profile——社区维护、随版本更新——**90% 团队直接用默认即可**。**新建 Profile 的动机**：团队要「自己的标准」（自定义规则、调整 severity、删掉噪音规则）。

**新建流程**：Quality Profiles → Create（选语言）→ **复制（Copy）默认 Profile 再改**（别从零建——6500 条规则手动选不现实）→ 调整（激活/停用规则、改 severity）→ 设置默认（新项目自动绑）→ 旧项目逐个换绑。**Profile 的维护**：规则库随版本更新——**Profile 要做「规则更新评审」**（升级后新规则是否纳入——09 篇升级流程的一部分）；**Profile 数量克制**（一个语言一个团队 Profile——多 Profile 并存是标准混乱的前兆）。

## 4. 误报治理

**误报是规则治理的核心战场**——误报率高了团队不信报告、门禁被架空；治理的目标是「**报告里出现的问题基本是真的**」：

**误报来源**：规则语义与场景不符（框架惯例被当问题——如 Lombok 生成代码、Spring 代理模式）；生成代码混入（不排除 `generated`——05 篇）；规则过期（旧规则与新版语言特性冲突）；上下文特殊（业务上「明知故犯」且合理）。**治理三件套**：**排除生成代码**（`sonar.exclusions`——最大误报源，一次配好）；**标记机制**（问题详情 → 标记 False Positive / Won't Fix——平台记录原因、审计留痕）；**规则裁剪**（误报率高的规则在 Profile 停用或降 severity——**「标记」是单点处理，「裁剪」是系统处理**）。

**治理节奏**：每周花 30 分钟过「本周误报标记」——分类（真误报 → 裁剪规则；合理豁免 → 留标记）；**误报率指标**：标记数/问题总数——高说明规则集该修了。

## 5. 规则豁免与存量治理

**豁免（Won't Fix）的正确姿势**：**豁免必须留因**（平台标记处写原因——「框架约定」「业务故意」「第三方代码」——可审计）；**豁免要有时限意识**（「暂时豁免」要有 revisit 机制——季度回顾豁免清单）；**豁免 ≠ 规则裁剪**（单点豁免 vs 全局裁剪的区分——单点豁免保留规则，裁剪放弃规则）。

**存量治理与规则的关系**（03 篇 Clean as You Code 的展开）：**存量问题不在门禁范围**（门禁卡新代码）——但存量债要有治理：**按规则分组**（同一规则的问题批量修——「统一改法」效率最高）；**按模块分批**（核心模块优先）；**新代码零容忍 + 存量排期**——「新债不欠、旧债有账」。

## 6. 自定义规则

规则库覆盖不到团队规范时，自定义规则（**需要自研插件**——SonarQube 的规则插件架构）：

**能自定义什么**：代码风格规范（团队命名约定、禁用的 API/模式）；**技术栈规则**（框架特有规范——如「所有 Controller 必须返回统一响应」）；**安全规范**（禁用危险 API 清单）。

**实现方式**：Java 插件（`sonar-plugin-api`，规则用 AST 访问器或符号分析实现）——**复杂度较高**（理解解析器 API、处理语法版本差异）；**替代方案**（先问「真要写插件吗」）：**现有规则组合**（多数规范能用现成规则拼出来）；**XPath 规则**（XML/部分场景）；**外部工具集成**（Checkstyle/PMD 规则导入 SonarQube——团队已有规则集复用）。**写插件的前提**：团队规范无法用现成规则表达 + 有维护意愿（规则随语言演进要更新）——**先穷尽现成方案再动手**。

## 7. 常见坑

**坑一：规则全开**。误报淹死团队、门禁不可信——Sonar way 起步，少而准。

**坑二：误报不标记**。团队不信报告——标记 + 裁剪双管齐下。

**坑三：生成代码不排除**。误报最大来源——`sonar.exclusions` 一次配好。

**坑四：Profile 从零建**。手动选 6500 条——复制默认再改。

**坑五：豁免不留因**。无法审计的豁免——留原因、有时限。

**坑六：随便写自定义插件**。维护成本高——先穷尽现成规则与导入方案。

**坑七：升级不评审规则**。新规则进 Profile 与否没决策——升级流程带规则评审（09 篇）。
