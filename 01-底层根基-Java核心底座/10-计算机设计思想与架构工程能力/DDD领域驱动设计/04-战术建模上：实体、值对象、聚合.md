# 04-战术建模上：实体、值对象、聚合

> 定位：进入限界上下文内部，三个建模原语决定领域模型的骨架——实体管身份、值对象管属性、聚合管一致性。建模顺序与优先级判断比具体语法更重要。

## 实体：有身份、有生命周期的对象

**实体（Entity）**的本质是"身份连续性"：无论字段怎么变，同一个 ID 代表的还是同一个对象。订单从"待支付"变到"已支付"再变到"已发货"，身份始终是 Order-20260812-001——这就是它需要唯一标识的原因。设计实体的三条铁律：**标识策略要有意选择**（自然键如订单号 vs 代理键如 UUID，代理键抗业务变化但不可读，自然键可读但会随业务规则漂移，混合策略先想清楚）；**行为要封装在实体内部**——"订单能否取消"的判断逻辑属于 Order 自身，而不是 Service 层的 if 判断（贫血模型反模式）；**实体之间通过身份而非对象引用协作**。

## 值对象：默认首选，没有身份的世界

**值对象（Value Object）**没有唯一标识，两个值对象相等 = 属性全部相等。建模时应**默认用值对象**，只有当"需要追踪一个对象随时间的变化"时才升级为实体。这个默认方向极其重要：绝大多数领域对象（金额、地址、电话、时间段、坐标、颜色）都是值对象。值对象的三个特性：**不可变**（所有 setter 返回新对象而非修改自身）、**可自我验证**（构造时校验，非法状态无法存在）、**可组合**（Money + Currency 组成 Price）。值对象是 DDD 的隐藏宝藏——它能吸收大量领域规则（金额的精度规则、地址的格式规则、时间段的重叠规则都写在 VO 里），让实体保持轻盈。Java 中实现值对象 = final class + record 或不可变类。

## 聚合：一致性边界的定义者

**聚合（Aggregate）**解决"哪些对象必须保持一致"。订单 + 订单项 + 配送地址构成一个聚合：订单项不能脱离订单存在，订单的总额必须等于所有订单项之和——这个"总和不变式"必须在一个事务里保证，而保证的载体就是聚合。聚合的设计规则：

- **唯一聚合根**：外部只能通过聚合根（Order）访问聚合内对象，禁止直接引用订单项（OrderItem）；
- **一致性边界**：聚合内部强一致，聚合之间最终一致——跨聚合事务是分布式事务陷阱的源头；
- **小聚合优先**：聚合越小，锁冲突越少、并发越高，但规则完整性越难保证——最小聚合原则（能一个根就一个根）；
- **通过 ID 引用其他聚合**：聚合之间不持有对象引用，只持有 ID（Order 持有 CustomerId 而非 Customer 对象），这是聚合可独立持久化、可分布式部署的前提。

## 三大原语的建模决策序列

遇到一个领域概念，按固定顺序决策：**1. 需要追踪身份吗？** 是 → 实体；否 → 值对象。**2. 它属于哪个聚合？** 找它的一致性伙伴——和谁一起变化、一起约束就进同一个聚合。**3. 谁当聚合根？** 找访问入口与事务锚点（订单是根，订单项不是）。这套序列解决 90% 的建模分歧。举例：地址在城市模型里是"顾客的地址"→ 值对象；在物流模型里是"配送地址快照"→ 仍是值对象（不可变快照）；但在"地址簿"上下文里是"可修改的联系方式"→ 实体。**同一个概念在不同上下文里类型不同**，这是限界上下文思想在战术层的自然延伸。

## 值对象的实战案例集

值对象最容易"看着简单、建模时犹豫"，三个高频案例演示决策过程：**金额（Money）**——币种 + 数值是经典值对象：封装精度规则（分单位存储）、运算规则（同币种才能相加，跨币种先换算）、比较规则（数值与币种同判）。把金额建模成 double 裸字段是财务系统的头号事故源（浮点误差、币种混加），金额值对象让这些规则只写一次、处处生效。**时间段（TimeRange）**——开始 + 结束封装"重叠判断""包含判断""时长计算"，促销活动的有效时段、优惠券的可用窗口都是它；注意它不可变——"延长有效期"返回新对象而非修改原对象。**地址（Address）**——按用途分两种建模：订单上下文中它是"下单瞬间的配送信息快照"（值对象，收货后变更不影响已下订单）；地址簿上下文中它是"可增删改的联系方式"（实体，需要追踪身份）。同一个 Address 在不同上下文类型不同，正是限界上下文思想的直接体现。**三维坐标/尺寸/颜色**——物理属性类全用值对象。判断口诀："相等就相等、变了就换新"，满足就是值对象。

## 聚合的拆分案例：订单的历史教训

经典的订单聚合拆分过程演示"最小聚合原则"的完整推理：初版模型把订单、订单项、支付记录、发货信息全放一个聚合——好处是"全强一致"，代价是每次并发更新（支付回调、物流回执、用户改地址）都锁整个订单，高并发下订单行成了全局瓶颈，且支付失败重试的频繁更新会阻塞订单状态流转。拆分决策按不变式排查：**订单项**不能脱离订单存在（总额不变式依赖它）→ 保留在聚合内；**支付记录**与订单的强制约束只有"退款累计 ≤ 支付金额"，且支付有独立生命周期（失败重试、部分退款）→ 拆为独立聚合，通过 PaymentOrderId 引用；**发货信息**与订单无强一致需求（发货后订单状态只是"已发货"的终态通知）→ 拆出或事件化。拆分后：订单聚合只锁订单状态机，支付聚合只锁支付记录，并发冲突面大幅收窄。拆分的验收标准：拆出的聚合能否说出自己的不变量清单（支付聚合能说出"退款累计 ≤ 支付金额"）——说不出的拆分是逃避一致性责任，说不出的合并是制造全局锁。

## 聚合内的并发与事务语义

聚合建模直接决定并发行为：两个请求同时改同一聚合，需要锁；改不同聚合，天然可并行。聚合根提供方法入口（`order.cancel(reason)`），所有状态变更经由根的方法走——这就是"行为驱动"的模型（方法表达业务意图）与"数据驱动"的模型（getter/setter 暴露裸数据）的分水岭。持久化层面：聚合整体加载、整体保存（JPA 中以根为单位做级联持久化），聚合边界外的数据不因聚合操作而变更。判断聚合设计是否合格的标准：**能否在纸面上说出每个聚合的不变量（invariant）清单**——说不出的聚合就是退化成了"对象容器"。

> 🎯 **核心要点**：三个原语的优先级是"值对象 > 实体 > 聚合"——能建模为值对象的别建实体，能小聚合的别大聚合，身份与一致性是稀缺资源，只在必要处使用。聚合的边界决定事务的边界，事务的边界决定并发与性能的上限——这是战术建模最具杠杆的决策。
