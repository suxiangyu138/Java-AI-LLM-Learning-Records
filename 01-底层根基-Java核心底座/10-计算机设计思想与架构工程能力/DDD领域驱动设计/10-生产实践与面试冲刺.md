# 10-生产实践与面试冲刺

> 定位：把前九篇收束为可执行的生产清单、可复用的迁移路线、可背诵的面试弹药。DDD 的面试考察核心是"概念区分是否精确 + 建模判断是否成熟"。

## 生产落地清单（12 项）

1. **识别真实复杂度**：系统存在多视角术语冲突、复杂业务规则、跨团队协作 → 适合 DDD；纯 CRUD 管理系统硬套 DDD 是过度设计。
2. **工作坊启动**：事件风暴（Big Picture 半天 + 核心上下文 Process 半天），产出事件清单、规则表、上下文候选。
3. **上下文划分**：按子领域分类定投资策略；上下文边界按"一套模型 + 一套语言 + 独立演化"三标准验证。
4. **上下文映射登记**：所有协作线标注模式（六主三辅），防共享数据库与隐式依赖；地图进架构评审。
5. **聚合建模**：每个聚合写出不变量清单；默认值对象；聚合间只通过 ID 引用。
6. **分层落地**：领域层纯 POJO、应用层管事务、基础设施层实现仓储；依赖方向单向。
7. **统一语言渗透**：类名/方法名/API 端点/测试名全用领域术语；ADR 存档语言决策。
8. **事件契约管理**：命名过去时、schema 版本化、幂等键 + 去重窗口、Outbox 保证发布一致性。
9. **部署形态决策**：20 人以下模块化单体起步；按部署/扩展/技术独立压力决定拆服务；禁共享数据库。
10. **质量门禁**：契约测试（Pact）+ 依赖扫描（零越界）+ 边界一致性检查进 CI。
11. **遥测验证**：跨服务调用延迟/失败率、变更耦合统计，验证边界假设；错误边界触发重新建模。
12. **边界演化**：合并/拆分/职责转移是常态；上下文地图保持与代码一致，不搞"装饰性架构图"。

## 故障模式排查表

| 症状 | 根因 | 对策 |
|---|---|---|
| 领域层不断"膨胀"出跨聚合逻辑 | 聚合边界画大 | 回到不变量清单重划聚合 |
| Service 层全是业务 if | 贫血模型 | 把规则下沉到实体/值对象方法 |
| 改一个模块必改另一个 | 边界错误/隐式共享 | 依赖扫描定位，合并或建防腐层 |
| 服务"独立部署"了但总协调上线 | 分布式单体 | 查共享数据库与同步深链，改事件驱动 |
| 事件丢了/重复消费 | 无 Outbox/无幂等 | Outbox + 幂等键 + 去重窗口 |
| 模型改了数据库跟着改 | JPA 对象导航残留 | @ManyToOne 改 ID 引用，聚合内级联 |
| 上下文地图与代码不符 | 地图沦为装饰 | 依赖扫描自动化校验 |

## 面试 12 题（含答题范式）

1. **DDD 是什么？解决了什么问题** → 建模方法论，解决"复杂业务系统的模型混乱"；战略层切块、战术层建模。
2. **限界上下文是什么？为什么不能全局建模** → 模型有效性边界；"用户"在不同上下文语义不同，全局模型必然概念冲突。
3. **子领域三类与投资策略** → 核心（重投）/支撑（适度）/通用（采购）；分类决定建模精力分配。
4. **上下文映射六模式对比** → 共享内核/客户-供应商/遵奉者/防腐层/开放主机/发布订阅；耦合度与选择场景。
5. **防腐层 vs 适配器** → 适配器解接口差异，防腐层解模型语义差异；翻译"概念"而非"签名"。
6. **实体 vs 值对象的决策** → 是否追踪身份；默认值对象；地址、金额、时间段都是 VO。
7. **聚合的设计规则** → 唯一根、一致性边界、小聚合、ID 引用；不变量清单是验收标准。
8. **跨聚合事务怎么办** → 不硬跨；领域事件 + 最终一致性；Outbox 保证发布原子性。
9. **DDD 与微服务的关系** → 上下文是候选服务；"不小于聚合、不大于上下文"；模块化单体是多数团队起点。
10. **贫血模型为什么是反模式** → 业务规则泄漏到 Service，模型退化数据容器；领域知识散落。
11. **DDD 与 AI 生成代码的关系** → 模型是生成约束；无约束生成是 Vibe Coding，有约束是 Architecture Coding。
12. **什么时候不该用 DDD** → 简单 CRUD、无领域规则、无多视角冲突；DDD 的协作与建模成本需要复杂度来摊销。

## 高频题的完整答题模板

**模板一：限界上下文（2 分钟版）**——先给定义（模型有效性边界：一套模型 + 一套语言 + 独立演化），再给反例（"用户"在商品/运营/客服三个上下文语义不同，全局建模必然概念冲突），最后给实践（识别信号：组织/语言/数据/系统四类；上下文地图登记协作）。三步走的结构让面试官看到"概念 + 例证 + 落地"三层能力。

**模板二：聚合与一致性（2 分钟版）**——定义（一致性边界 + 唯一根 + 事务不变量），设计规则（小聚合、ID 引用、行为封装），反模式（跨聚合事务、对象导航、贫血模型），判断方法（不变量清单说不清 = 聚合不合格）。补一句"聚合边界决定事务边界，事务边界决定并发上限"的杠杆性结论收尾，这是区分背概念与真理解的关键句。

**模板三：DDD 与微服务（2 分钟版）**——先纠正前提（DDD 不是微服务方法论，边界是模型边界），再给映射规则（不小于聚合、不大于上下文），再给 2026 的理性修正（分布式单体三探针、模块化单体推荐、按遥测数据决定拆分），最后落到数据所有权（服务独占数据、事件维护视图）。这套回答同时覆盖概念、反模式、趋势，是架构师级答案。

**模板四：AI 时代的 DDD（1 分钟版）**——领域模型是 LLM 生成代码的契约与约束；无约束生成是 Vibe Coding、有约束生成是 Architecture Coding；神经符号双核（LLM 意图 + 引擎确定性）是 2026 主流路径；建模裁决权始终在人（ICSA 实验：LLM 会系统性遗漏关键元素）。

## 加分深度题

**Q：一个聚合多大合适？** 用不变量与并发判断——聚合内对象必须满足"同事务强一致"且"变更频率相近"；能独立变更的拆出去。最小聚合原则，但别拆到不变量断裂。

**Q：事件风暴为什么用事件开场？** 事件是业务人员最自然的表达；时间线暴露顺序、并发与异常分支；命令/规则是事件的补充而非替代。

**Q：模块化单体如何保留微服务演进空间？** 模块边界 = 限界上下文 + 显式接口 + 事件契约 + 独立数据 schema（同库多 schema 或逻辑隔离）；抽取服务时迁移数据所有权与事件订阅，其余零改动。

**Q：如何向管理层证明 DDD 价值？** 用质量场景（可修改性/可分析性/可替换性）做架构护栏，把边界决策翻译成可度量指标（2026 案例研究路径）；变更耦合率、独立部署次数、缺陷定位时间都是可量化证据。

## 面试速记

1. DDD = 战略层（边界与协作）+ 战术层（聚合与对象）；核心产出是限界上下文与统一语言。
2. 建模默认值对象，身份与一致性是稀缺资源；聚合不变量清单是模型质量的验收标准。
3. 上下文映射六模式，防腐层保护模型纯度，发布订阅换取演化自由。
4. 分布式单体三探针：共享数据库/协调部署/同步深链；模块化单体是 2026 推荐起点。
5. AI 时代：领域模型是 LLM 生成代码的契约；神经符号双核让 AI 产出可控。

> 🎯 **核心要点**：DDD 的生产价值 = 复杂度的可管理性（边界让复杂度局部化）+ 业务知识的持久化（模型承载领域规则）+ 演化的安全性（契约与地图让变更可评估）。面试与生产的共同核心是"概念区分精确、边界判断有据"——把本体系的决策序列（分类→划界→映射→聚合→分层→门禁）讲成自己的方法论，比背诵术语更打动人。
