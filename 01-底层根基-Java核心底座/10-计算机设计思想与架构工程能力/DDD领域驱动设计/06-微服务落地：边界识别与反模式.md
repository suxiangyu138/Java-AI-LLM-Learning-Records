# 06-微服务落地：边界识别与反模式

> 定位：限界上下文是服务边界的候选，但"上下文 → 微服务"不是自动映射。2026 年的实践共识是：先防分布式单体，再谈服务化——以及"模块化单体 + 右规模服务"的理性回归。

## 分布式单体：微服务最大的反模式

微服务迁移的第一大失败模式不是技术，而是**沿技术层切分**（认证服务、日志服务、邮件服务）或沿数据表机械切分——产物是"分布式单体"：服务各自部署，但共享数据库、依赖同步调用链、任何变更仍需多方协调上线。2025-2026 年的行业报告反复确认：大量号称微服务的系统实际就是这个形态。分布式单体比单体更糟——它同时具备单体的耦合与分布式的复杂度。

判断分布式单体的三个探针：**共享数据库**（多个服务读写同一 schema——最硬的信号）；**部署需协调**（一次发布要排期多个服务同时上线）；**同步调用链深**（一个请求串起 5+ 服务同步等待）。对应三条硬纪律：服务拥有自己的数据（其他服务的数据通过事件/API 获取自己的视图）；独立部署无协调（契约测试保证）；异步优先（同步调用是例外而非默认）。

## 从限界上下文到服务边界的映射规则

服务边界 ≠ 上下文边界，二者之间有判断阶梯：

1. **上下文是候选服务**，但先验证：该上下文能否独立部署、独立演化、独立失败（独立性不足的上下文合并）；
2. **聚合是服务下限**：服务不小于聚合（不能把聚合拆散到多个服务），不大于限界上下文（不能把多上下文并进一个服务除非演化压力小）——"不小于聚合、不大于上下文"是 2026 年 Azure 指南的原文；
3. **反切分规则**：两个聚合若频繁同步通信且无法容忍延迟，不要拆到不同服务——跨服务同步调用每加一层，故障域与延迟都线性恶化；
4. **数据所有权是硬约束**：服务必须独占数据，无共享数据库——"数据所有权是迁移中最难的部分"（2026 行业共识），服务内建自己数据的视图，经事件更新。

## 模块化单体：2026 的理性回归

2026 年最值得注意的转向：**模块化单体（Modular Monolith）**重新成为推荐起点。20 人以下团队被明确建议"先做边界清晰的模块化单体，而非分布式系统"——单体内部按限界上下文切模块（模块间通过显式接口通信，禁止跨模块对象引用），获得 DDD 的建模收益而不付分布式成本。何时升级为微服务：模块化单体出现"独立部署压力"（发布频率差异大）、"独立扩展压力"（某模块流量激增）、"独立技术栈需求"时，再把对应模块抽取为服务。**右规模服务（Right-sized）**是 2026 的关键词：不要"能拆多细拆多细"，而是"按生产遥测数据决定拆分"——让数据（延迟、变更频率、团队认知负荷）而非架构偏好做决策。

## 单体到微服务的迁移路线

对已有单体系统，2026 年的标准迁移路径是**绞杀者模式（Strangler Fig）**：网关按流量比例逐步把请求路由到新抽取的领域服务，老单体逐步瘦身，最后被整体替换——每步可回滚、每次发布独立。具体步骤：**1. 边界分析**——用依赖扫描 + 变更耦合统计识别候选限界上下文（改 A 必改 B 的模块对就是候选聚合）；**2. 抽取顺序**——按风险从低到高：先抽无共享数据的独立上下文（最容易，建立信任），再处理依赖复杂者；**3. 数据迁移**——最难的一步：新服务建自己的 schema，通过双写或事件同步从老库搬数据，老库的对应表改由新服务写入（数据所有权转移要显式立项，禁止"两边都写"）；**4. 契约建立**——新服务用开放主机服务暴露 API + 契约测试，老单体经防腐层调用新服务（反向亦然）；**5. 流量切换**——网关灰度切流，按错误率自动回滚；**6. 清理**——老服务代码与数据删除前保留双写窗口（通常 1-3 个月）。整条路线的纪律：**一次只抽一个上下文**、每步都可回滚、数据库变更与代码变更解耦（数据库重构先行：先加列后换写入方）。

## 服务粒度决策的问题清单

拆分前用十问自检，答不出就暂缓：**1. 独立部署**——该服务能否不与任何其他服务协调就上线？**2. 独立失败**——它挂了，其他服务的核心流程是否不受影响？**3. 数据独占**——它的数据是否只有它写？**4. 团队匹配**——是否有一个团队对它有完整认知负荷？**5. 延迟容忍**——它与协作方的通信是异步可容忍的吗？**6. 发布频率**——它的变更频率是否显著不同于相邻上下文？**7. 扩展需求**——它是否有独立的水平扩展需求？**8. 事务边界**——它的聚合是否需要跨服务强一致（需要 = 拆分失败）？**9. 契约稳定**——它的对外 API 是否已经稳定到可契约化？**10. 成本核算**——新增的部署/监控/运维成本是否低于单体内的协作成本？十问中任何一条不满足，都先留在模块化单体里并记录待观察项——"右规模服务"的决策依据是数据与清单，不是架构洁癖。

## 领域事件与跨服务数据一致性

服务间数据同步的 2026 标准答案是**事件驱动**：上游服务在自己的事务内更新数据并发布事件（Outbox 保证原子性），下游服务订阅事件、更新自己的数据视图。这套模式的三个工程支柱：**Outbox 模式**（业务写与事件写同事务，relay 异步发布，杜绝"数据变了事件没发"）；**幂等消费**（下游按事件幂等键去重，重放安全）；**事件契约管理**（schema 版本化 + 兼容性策略，见 05 篇）。替代同步调用的价值：上游变更不再阻塞下游、下游故障不拖垮上游、新消费者加入无需改上游——这是"服务独立演化"的技术基础。

## 边界的验证与演化

边界不是一次画对的（2026 案例研究反复出现"初始边界错误 → 团队重组"的教训），验证手段：**依赖分析**（定期扫描跨上下文依赖，出现越界依赖即报警）；**变更耦合统计**（两个模块频繁同次变更 = 边界可能画错）；**契约测试**（服务间接口用 Pact 类工具自动验证，独立部署才安全）；**生产遥测**（跨服务调用的延迟与失败率暴露隐式依赖）。边界演化是常态：限界上下文合并（模型概念统一时）、拆分（一个上下文膨胀时）、职责转移（子领域地位变化时）都是正常操作，关键是有**显式的地图与登记机制**（见 02 篇），让演化可见、可评审、可回滚。

> 🎯 **核心要点**：2026 年的边界共识一句话——"先用限界上下文划清楚，再按部署压力决定是否拆微服务"。分布式单体是头号反模式（探针：共享数据库/协调部署/同步深链）；模块化单体是多数团队的理性起点；事件驱动 + 数据所有权是服务化后的运行纪律。边界是演化的判断而非一次性的交付。
