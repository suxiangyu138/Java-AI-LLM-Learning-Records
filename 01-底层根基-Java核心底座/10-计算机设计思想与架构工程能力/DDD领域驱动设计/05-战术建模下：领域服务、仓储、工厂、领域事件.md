# 05-战术建模下：领域服务、仓储、工厂、领域事件

> 定位：实体/值对象/聚合定义了"数据 + 行为"的骨架，四个辅助构建块解决"跨聚合逻辑放哪、对象从哪来、持久化怎么解耦、变化如何传播"——它们共同完成战术层的完整拼图。

## 领域服务：不属于任何聚合的业务逻辑

聚合封装自身的规则，但有些业务逻辑天然跨越多个聚合：电商的"下单"涉及订单聚合（创建）、库存聚合（扣减）、优惠券聚合（核销）——把这段逻辑塞进任何一个聚合都不合适（会引入对别的聚合的依赖），塞进应用服务又会把业务规则混入技术编排。**领域服务（Domain Service）**正是这个位置的载体：无状态（不持有数据，只持有行为）、表达领域动词（PlaceOrder 而不是 OrderService.xxx）、操作多个聚合并通过各自的方法完成协作。

领域服务与**应用服务（Application Service）**的职责边界是战术层最常见的混淆点：应用服务负责编排与事务（调用仓储、提交事务、处理幂等），领域服务负责业务规则（跨聚合的规则判断与执行）——应用服务薄而技术化，领域服务厚而业务化。判断规则：逻辑"必须跨聚合"才进领域服务；"纯编排 + 事务 + 权限"留在应用服务。2026 年 Agent 实践中的对应物是确定性协调器——跨限界上下文的流程编排（见 09 篇），两者是同构思想在不同层的体现。

## 仓储：持久化的语义契约

**仓储（Repository）**是聚合与持久化之间的抽象：为每个聚合定义"加载、保存、按 ID 查询"的契约接口，实现在基础设施层。核心纪律：**接口用领域语言，不含任何持久化细节**——方法名是 findByOrderId 而非 findBySql；参数是领域对象而非 SQL 片段；返回聚合而非裸数据行。仓储让领域层对数据库技术完全无感（MySQL、MongoDB、Redis 缓存都是实现选择），也让领域模型可单元测试（内存假仓储替换真实实现）。

仓储实现的两个务实建议：**按聚合根设计仓储**（不是每张表一个仓储，订单项没有自己的仓储——它随订单整体加载）；**查询分离**（聚合加载走仓储，列表/报表查询走独立的只读查询通道——CQRS 思想的轻量版），避免"复杂查询把聚合加载搞得千疮百孔"。一个常见误区：仓储不等于 DAO——DAO 是表驱动的数据访问，仓储是聚合驱动的语义契约，同一个仓储接口下可以映射多张表。

## 工厂：复杂创建的封装

当聚合创建逻辑复杂（多个构造步骤、依赖校验、初始状态计算），把创建逻辑放在客户端代码会造成重复与散落。**工厂（Factory）**封装创建：静态工厂方法（`Order.place(customerId, items)`）适合简单场景；独立工厂类（`OrderFactory`）适合跨聚合组装。工厂与聚合构造函数的分工：构造函数保证"合法状态可构造"（不变量建立），工厂负责"业务场景化创建"（从命令/DTO 推导聚合初始状态、触发创建事件）。**反模式提醒**：聚合根方法内部的"工厂"不是工厂（那是领域逻辑），工厂只出现在聚合根外部创建聚合的场景。

## 领域事件：事实的广播与订阅

**领域事件（Domain Event）**记录领域中已发生的事实，过去时命名（OrderPaid 而非 PayOrder）、业务可读（付款金额、订单号是事件字段，不是内部对象）。领域事件的三个层次用途：**上下文内**——聚合间解耦（订单确认后触发库存聚合的动作，通过事件而非直接调用）；**跨上下文**——集成事件驱动微服务协作（订单上下文发布 OrderPaid，物流上下文订阅），事件在此成为跨上下文契约（见 02 篇）；**审计与溯源**——事件流成为业务可读的操作日志甚至事件溯源（ES）的数据源。

工程纪律（2026 实践清单）：区分**领域事件**（上下文内）与**集成事件**（跨上下文），命名与规范各自独立；关键事件定义**幂等键**与去重窗口（订阅方消费失败重放时不重复处理）；事件发布与业务状态变更的一致性用 **Outbox 模式**保证（同事务写业务表 + outbox 表，relay 异步发布——见 10 篇）；事件 schema 版本化，兼容性策略写进契约（新增字段向后兼容、删除字段走新版本）。领域事件的过度使用同样危险：为每个状态变化都发事件会让系统变成噪音广播——只对"业务上有意义的事实"发事件（价格调整是事件，日志记录不是）。

## 事件发布的实现要点

领域事件从"聚合内记录"到"订阅方消费"的完整链路有四个易错点：**聚合内收集**——业务方法只把事件放进聚合的事件列表（不直接发消息），保证"状态变更"与"事件产生"在模型层面同生共死；**事务边界内收集、提交后发布**——应用服务在事务提交成功后统一发布事件（Spring 用 @TransactionalEventListener(phase=AFTER_COMMIT)），避免事务回滚后事件已发出的脏事件；**Outbox 兜底**——生产级必须同事务写 outbox 表 + 异步 relay 发布，覆盖"事务提交后进程崩溃"的窗口（见 10 篇清单第 8 条）；**幂等与重放**——订阅方按事件 ID 去重，消费失败退避重试，事件流支持重新回放（测试与数据修复都依赖重放能力）。这条链路的本质是把"状态变更"与"通知"的一致性从"碰运气"变成"有保障"，是事件驱动架构能否上生产的分水岭。

## 领域服务与贫血服务的边界

领域服务设计最常见的退化是"领域服务变成大杂烩 Service 类"——判断领域服务是否合格的三问：**它是否只做业务规则？**（出现事务、权限、参数校验、日志 = 越界，那是应用服务的职责）；**它是否无状态？**（持有字段的服务是伪装成服务的对象，状态应放回聚合）；**它是否表达领域动词？**（类名与方法名用领域语言：OrderPlacementService.place，而不是 OrderBizService.doStuff）。另一个边界：领域服务**可以调用多个仓储吗**——可以（跨聚合读数据是常态），但写操作必须经过聚合方法（领域服务不直接改聚合内部状态，只能调用聚合根的公开业务方法）——这是"聚合封装"的最后防线。当发现领域服务里出现大量 if-else 分支判断聚合状态时，先怀疑聚合内缺少状态机方法，而不是领域服务逻辑复杂。

## 战术构建块决策速查

| 场景 | 选择 | 反例 |
|---|---|---|
| 单一聚合内规则 | 实体/值对象方法 | 塞进 Service 的 if |
| 跨聚合业务逻辑 | 领域服务 | 任意聚合根里直接调别的聚合 |
| 聚合持久化 | 按根设计仓储 | 每表一个 DAO 暴露给领域层 |
| 复杂创建 | 工厂 | 客户端散落创建逻辑 |
| 状态变化通知 | 领域事件 | 同步调用别的聚合 |
| 事务编排/幂等 | 应用服务 | 领域服务里管事务 |

> 🎯 **核心要点**：五个构建块的共同纪律是"职责归属"——业务规则进领域层（实体/领域服务），技术细节进基础设施层（仓储实现/消息客户端），领域层通过接口依赖抽象。2026 年的 DDD Agent 实践（DDD-Enforcer 的约束检查清单）正是把这些归属规则变成可自动校验的约束：事件命名过去时、仓储接口不含 SQL、复杂创建必须有工厂。
