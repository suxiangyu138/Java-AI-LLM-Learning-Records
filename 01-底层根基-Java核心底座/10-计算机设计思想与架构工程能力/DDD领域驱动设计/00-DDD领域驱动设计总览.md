## 3. 学习路线推荐

**路线 A（入门认知，2 天）**：01 核心概念 → 04 战术建模上 → 05 战术建模下。先建立"限界上下文 + 聚合"的完整心智，配合同级《软件架构能力体系培养》理解 DDD 在架构全景中的位置。

**路线 B（架构落地，3-5 天）**：02 战略设计 → 03 事件风暴 → 06 微服务落地 → 07 Java 实现 → 08 实战案例。适合要带队做系统拆分或微服务改造的工程师，重点在"边界怎么划、划完怎么实现"。

**路线 C（前沿研究，进阶）**：09 DDD×AI → 10 生产实践 → 反向补 03 事件风暴。适合关注"LLM 辅助建模、AI 时代的领域模型"话题，以及准备大厂架构面试的读者。

## 4. 核心概念速查

| 概念 | 一句话本质 |
|---|---|
| 领域（Domain） | 业务问题空间的总称，系统要解决的问题本身 |
| 子领域（Subdomain） | 领域按业务能力拆分，分核心/支撑/通用三类 |
| 限界上下文（BC） | 模型有效性的边界：一套统一语言 + 一套模型的物理边界 |
| 统一语言（UL） | 领域专家与开发共享的术语表，消除技术黑话 |
| 上下文映射 | 两个 BC 之间协作关系的九种模式（六主三辅） |
| 防腐层（ACL） | 保护本上下文模型不被外部模型污染的翻译层 |
| 实体（Entity） | 有唯一标识、随时间变化、需追踪身份的对象 |
| 值对象（VO） | 无标识、不可变、由属性集合定义的对象（默认首选） |
| 聚合（Aggregate） | 一致性边界：一组对象 + 唯一聚合根 + 事务不变量 |
| 领域服务 | 不属于任何单一聚合的跨聚合业务逻辑 |
| 领域事件 | 领域中已发生事实的过去时记录，驱动最终一致性 |
| 事件风暴 | 用领域事件铺时间线的协作建模工作坊 |

> 🎯 **核心要点**：DDD 的完整逻辑链是"领域问题 → 子领域分类 → 限界上下文切块 → 上下文映射定协作 → 聚合定一致性边界 → 战术对象实现"。2026 年的三个新坐标：模块化单体回潮让"切块"不再等于"拆微服务"；AI 辅助建模要求人类先有清晰的领域模型；约束验证工具（Round-trip 工程）正在把战术建模从专家手艺变成可校验工程。

## 4.5 术语对照速查

面试与阅读原文时的中英对照（部分术语常见误译需注意）：

| 英文 | 中文 | 说明 |
|---|---|---|
| Domain / Subdomain | 领域 / 子领域 | 问题空间的分析产物 |
| Bounded Context | 限界上下文 | 模型有效性边界；常被误译成"边界上下文" |
| Ubiquitous Language | 统一语言 | 术语必须渗透到代码 |
| Context Map | 上下文地图 | 战略设计全景图 |
| Anti-Corruption Layer | 防腐层 | 模型翻译层，防污染 |
| Open Host Service | 开放主机服务 | 发布稳定协议的上游 |
| Aggregate / Aggregate Root | 聚合 / 聚合根 | 一致性边界与入口 |
| Value Object | 值对象 | 无身份、不可变 |
| Entity | 实体 | 有身份、可跟踪 |
| Domain Service | 领域服务 | 跨聚合业务逻辑 |
| Application Service | 应用服务 | 编排与事务 |
| Repository | 仓储 | 聚合的持久化契约 |
| Domain Event | 领域事件 | 已发生事实的广播 |
| Event Storming | 事件风暴 | 协作建模工作坊 |
| Anemic Model | 贫血模型 | 反模式：实体只剩 getter/setter |
| Strategic / Tactical Design | 战略 / 战术设计 | 边界层与模型层 |

对照表的使用场景：读英文原文（Evans 原书、Khononov 新书、2026 论文）时按此表对应；写代码与文档时保持术语一致——统一语言本身就是 DDD 的实践对象。

## 5. 常见误区速查

- **误区一："DDD 就是微服务拆分"**。DDD 先于微服务存在 15 年，限界上下文是模型边界而非部署边界；小团队更适合"模块化单体 + 限界上下文模块"，拆微服务只是其中一种部署选择。
- **误区二："实体就该只有 getter/setter"**。这是贫血模型反模式——实体必须封装业务规则与状态转换，否则领域逻辑全部泄漏到 Service 层。
- **误区三："值对象没必要"**。值对象是建模默认选项：不可变、可复用、自带行为，绝大多数"小对象"都应建模为 VO，只有需要追踪身份才升级为实体。
- **误区四："跨聚合强一致是常态"**。跨聚合事务是陷阱——用领域事件 + 最终一致性替代，聚合只保证自身内部不变量。
- **误区五："统一语言只是词汇表"**。它必须渗透到代码类名、方法名、API 端点、测试用例名；术语只在限界上下文内有效，跨上下文同名不同义是常态。
- **误区六："上下文边界一次划对"**。边界是持续演化的判断（2026 案例研究反复出现"初始边界错误导致团队重组"的教训），用生产遥测数据验证边界比拍脑袋更可靠。
- **误区七："DDD 适合所有系统"**。纯 CRUD、无业务规则、无多视角冲突的系统用 DDD 是过度设计——建模与协作的成本需要真实复杂度来摊销，判断标准是"术语是否冲突、规则是否复杂、团队是否多视角"。
