# 09-DDD × AI/LLM（2026 前沿）

> 定位：2026 年 DDD 最活跃的议题——LLM/Agent 进入建模工作坊与代码生成后，领域模型从"软件设计产物"变成"人机协作的锚点"。核心结论：AI 是建模助手，领域纪律是 AI 时代的稀缺品。

## AI 辅助事件风暴：能力边界的实验证据

ICSA 2026 控制实验（240 名研究生、60 个团队，三组对照：人工 ES、LLM 基础提示词、LLM 优化提示词）给出了迄今最可信的边界刻画：**LLM 生成的事件/模型元素总体可靠（术语与结构正确），但会系统性地遗漏关键元素**——复杂业务逻辑下，优化提示词可以恢复部分遗漏，但单一提示词无法持续输出高质量模型。DDD Europe 2026 的工作坊姿态与此一致：LLM 作为"协作伙伴"增强事件风暴——生成事件草稿、检查统一语言一致性、为限界上下文划分提供多样化候选，人工负责裁决。工程含义：把 LLM 当"无限耐心的草稿机"，不当"建模裁判"；工作坊产出的验收标准不变（业务专家能复述流程）。

## AI 辅助代码生成：从 Vibe Coding 到 Architecture Coding

QCon 北京 2026 的 Toco AI 实践提出"建模驱动开发（MDD）+ LLM"范式，针对 Vibe Coding 在复杂系统中的三大痛点（结构不可控、上下文幻觉、资产难维护——代码采用率不足 10%）。方案是**神经符号双核架构**：LLM/Agent 负责意图理解与胶水代码（概率性，右脑），确定性引擎负责架构约束与业务规则（确定性，左脑）。DDD 在此扮演"确定性锚点"角色：用克制的 DSL 定义实体、聚合、读写契约（不侵入 if/else，避免重蹈 UML 覆辙），LLM 只生成 DSL 描述范围内的代码，引擎自动渲染约 80% 的 DDD/CQRS 结构化代码。这回答了"DDD 与 AI 生成代码的关系"：**领域模型是 LLM 生成代码的契约与约束——没有模型约束的生成是 Vibe Coding，有模型约束的生成是 Architecture Coding**。

## 多智能体强制 DDD：DDD-Enforcer

IISEC 2026 的 DDD-Enforcer 展示了另一种结合形态：四阶段多智能体 + AST 静态分析，在 VS Code 中实时检测领域模型退化（贫血模型、聚合边界泄漏、跨上下文依赖），并集成 RAG 管道做需求可追溯。实测：15 个违规用例 100% 检出、平均延迟 4.49 秒、RAG Top-1 准确率 76.8%。它的意义不在检出率本身，而在于验证了**"LLM 判读 + 静态分析兜底"的混合路径**可以落地——LLM 负责需要语义理解的判读（这是不是贫血模型），静态分析负责可穷举的约束（跨包依赖、命名规则），两者互补。工程启示：团队可以把 DDD 约束清单（事件命名过去时、仓储接口无 SQL、聚合无外部引用）改写成"静态扫描 + LLM 审查"的自动化流水线，作为 10 篇质量门禁的前置环节。

## 用 DDD 组织 Agent 系统：限界上下文是 Agent 的自然边界

2026 年的 Agent 工程实践给出一个对称的洞察：**限界上下文是组织 Agent 职责的自然边界**。invoice-booking-agent（SAP 发票入账 Agent）围绕 4 个限界上下文组织（intake/verification/approval/booking），上下文间无直接依赖，由确定性协调器编排——与 DDD 的上下文映射如出一辙。它的安全设计**约束层级**（Constraint Hierarchy）同样值得注意：提示词规则 → 纯 Python 校验 → 工具移除 → 参数移除（审批人字段对 LLM 不可见，由协调器注入），实现"LLM 想犯错都犯不了"——这正是"确定性引擎 + LLM 意图理解"双核思想在安全维度的展开。customer-support-ai-ddd-refactor 则用 4 个限界上下文（分类/检索/生成/质量保障）重构 RAG 客服管线，AI 客户端经 Protocol 依赖注入可一行切换供应商，提示词作为版本化 PromptTemplate 管理。

## LLM 辅助建模的提示词工程要点

从 ICSA 实验与 DDD Europe 工作坊提炼的实战提示词纪律：**先给领域事实再提问**——"这是电商系统，包含订单/库存/支付/营销/物流模块，用户下单后流程是……请列出所有可能发生的领域事件"优于空泛的"帮我想电商领域事件"（有上下文锚点的生成遗漏更少）；**要求穷举而非择优**——显式指令"覆盖异常分支：超时、失败、取消、补偿"能部分弥补 LLM 系统性遗漏关键元素的缺陷；**多轮校验循环**——第一轮生成后，第二轮要求"为每个事件补充触发命令与前置条件"，第三轮要求"检查遗漏：有没有涉及金额变化的场景"——实验证据表明优化提示词有效但单轮不够，轮次化的"查漏"流程比追求一次性完美更实际；**人工裁决不变**——LLM 输出进工作坊作为"草稿墙"，领域专家在便签墙上增删改，裁决权在人的立场不变。**术语一致性检查**是 LLM 的另一个可靠用途：把统一语言术语表给 LLM，让它扫描代码/文档标注术语偏离，这种"确定性可验证"的任务正是 LLM 擅长区间。

## 给工程团队的三条落地建议

- **建一条"AI 建模校验流水线"**：把本体系的约束清单（事件命名过去时、聚合无跨引用、仓储接口无 SQL、上下文零越界依赖）写成"静态扫描（可穷举项）+ LLM 审查（语义判断项）"两步流水线，进 CI——DDD-Enforcer 证明这条路可行，成本是一次性的规则编写。
- **Agent 系统从第一天用限界上下文组织**：Agent 的工具划分、提示词边界、状态存储都按上下文隔离；跨上下文由确定性协调器编排（invoice-booking-agent 的约束层级是安全模板：提示词规则 → 纯校验 → 工具移除 → 参数移除）。用 DDD 组织 Agent，比事后补救提示词注入安全得多。
- **AI 生成代码必须配模型约束**：接入 Architecture Coding 范式时，先用 DSL/契约定义实体与聚合（克制、无 if/else 侵入），LLM 只在其范围内生成；没有模型约束的 AI 生成，在复杂系统上的代码采用率不足 10%（Toco 数据）——约束不是限制，是让 AI 产出可用的前提。

## 战略设计提速与"DDD 第三次复兴"

"AI 是 DDD 的第三次复兴"（Dear Architects 播客 2026）的论证值得展开：第一、二次复兴分别对应微服务与云原生，第三次对应 **AI 生成代码时代——当自然语言 prompt 直接生成代码时，模糊的领域模型会被静默烧进代码**，建模纪律成为与 AI 协作的前提而非可选项。DDD Europe 2026 的"Accelerate your Strategic Design with LLMs"工作坊实践了这一命题：LLM 辅助子领域分类、统一语言提炼、上下文边界候选生成，人工做取舍——战略设计从"数周的专家工作坊"提速为"几天的人机协同"。同时研究警示保持清醒：自动化 DDD 提示词框架（arXiv:2603.26244）的评估显示 LLM 在聚合设计与技术架构映射上仍然脆弱、可能过度细划限界上下文，且自动化削弱了 DDD 强调的干系人协作价值——**协作是 DDD 的隐含收益，不能被工具化掉**。

> 🎯 **核心要点**：DDD × AI 的 2026 全景一句话——AI 在四个环节增强 DDD（事件风暴草稿、代码生成约束、约束检查、战略设计提速），但"模型裁决权"始终在人。领域模型成为 AI 时代的稀缺品：prompt 驱动的开发把建模责任前置到每个人，而限界上下文与聚合纪律正是让 AI 产出可控的确定性锚点。神经符号双核（LLM 意图 + 引擎约束）与 DDD-Enforcer 的混合校验，是 2026 年最可复制的两条工程路径。给团队的落地方案：提示词纪律（给事实再提问、要求穷举、多轮查漏）+ 约束流水线（静态扫描 + LLM 审查）+ Agent 上下文隔离，三者叠加即可在不依赖工具成熟度的前提下吃到 AI 红利。
