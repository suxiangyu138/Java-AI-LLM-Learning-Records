# 08-实战案例：电商订单端到端

> 定位：把前七篇串成一个完整案例——从事件风暴识别领域，到限界上下文划分，到订单聚合的战术建模，再到微服务落地决策。这是本体系的方法论"总装车间"。

## 第一步：事件风暴识别领域

电商系统的工作坊（Big Picture 风格）产出的事件主线：用户下单 → 订单已创建 → 支付已完成 → 支付已退款 → 库存已扣减 → 库存已释放 → 商品已发货 → 订单已签收 → 订单已取消 → 优惠券已核销 → 发票已开具。事件流暴露三组隐藏规则：**超时分支**（支付超时自动取消——只有事件时间线才能逼出"超时也是事件"）；**并发冲突**（支付与取消同时发生——"订单已取消"与"支付已完成"谁先谁后，业务规则需要明确）；**补偿逻辑**（取消订单要释放库存、退回优惠券——"事件链"让补偿关系显形）。

按子领域分类（01 篇的表格）：订单履约是核心子领域（差异化竞争点，投入最重）；库存与优惠券是支撑子领域；支付通道与通知是通用子领域（接现成方案）。聚类便签得到候选限界上下文：订单上下文、库存上下文、支付上下文、营销（优惠券）上下文、物流上下文、用户上下文。

## 第二步：上下文映射定协作

用 02 篇的决策序列为每个协作定模式：订单与支付之间——订单发布"订单已创建"，支付订阅并驱动收银台（**发布-订阅**，异步）；支付完成回传订单——支付发布"支付已完成"，订单订阅（**发布-订阅**）；订单与库存——订单要求"扣减库存"，库存上下文暴露**开放主机服务**（REST + 幂等键），订单经**防腐层**适配（库存的"预占/确认/释放"三态模型翻译成订单视角的"扣减请求"）；与用户上下文——**客户-供应商**（下游用户资料服务保证契约）；与遗留 ERP——**防腐层**（30 字段的 ERP 客户翻译成 5 字段的用户快照）。

两个刻意决策：支付上下文用共享内核吗？不用——支付字段语义与订单差异大，选择发布-订阅 + 事件契约管理（事件 schema 版本化、幂等键）。物流上下文直接依赖订单上下文吗？不依赖——物流订阅事件 + 自己的数据视图（配送地址快照），反向需要回执时发布"已发货"事件。全部协作线登记进上下文地图，纳入架构评审。

## 第三步：订单上下文的战术建模

订单上下文的聚合识别：**Order 聚合**（订单 + 订单项 + 金额，不变式"总额 = 各项小计之和"、"已发货不可取消"）；**购物车聚合**（Cart + CartItem，"同商品合并行"不变式）；**支付记录聚合**（PaymentRecord，独立于 Order——支付可能失败重试，生命周期与订单不同步）。建模决策记录：金额与地址是**值对象**（Money 封装币种与精度，Address 不可变快照——物流上下文收到的是快照而非实时引用）；"订单项"不是独立聚合（不能脱离订单存在，随订单整体加载）；订单通过 CustomerId、PaymentId 引用其他上下文（不持有对象）。

领域服务：**OrderPlacementService**（跨 Order/Cart/库存防腐层的下单编排，属于订单上下文内的跨聚合逻辑）；**订单超时取消调度**（扫描超时订单触发取消——时间事件是领域事件，不是技术定时任务）。领域事件：OrderPlaced（下单）、OrderPaid（支付完成，携带支付单号）、OrderCancelled（取消，携带原因）、OrderShipped（发货）。应用服务 OrderApplicationService 负责事务边界与幂等（重复提交订单请求用幂等键拦截）。

## 第四步：微服务落地决策

按 06 篇的阶梯：团队 15 人、发布频率差异明显、流量峰值集中在订单与支付——决策：**订单、支付、库存拆为三个微服务**（独立部署压力真实存在）；营销与物流暂留在**模块化单体**内（模块边界清晰，无独立扩展压力，避免过度拆分）；用户上下文继续用现成服务（客户-供应商）。数据所有权：订单服务独占订单库；库存服务通过开放主机服务暴露接口、通过事件维护自己的数据视图；**禁止共享数据库**（团队间共享 schema 是分布式单体的第一条红线）。跨服务一致性：支付完成 → 订单更新的路径用 Outbox + 事件（订单服务订阅"支付已完成"，幂等消费，重放安全）；订单取消 → 库存释放走同一套机制。

## 其他上下文的建模速览

订单之外四个上下文的建模决策（对照前文决策序列快速过一遍）：**库存上下文**——聚合：库存预占聚合（Reservation，不变式"预占总量 ≤ 可用库存"）、库存台账聚合（StockLedger，按 SKU 记录增减）；事件：库存已预占/已确认/已释放；对外：开放主机服务（预占/确认/释放三操作 + 幂等键），订单经防腐层适配。**支付上下文**——聚合：支付单聚合（PaymentOrder，独立于订单生命周期——可失败重试、可部分退款），不变式"退款累计 ≤ 支付金额"；事件：支付已完成/已退款；与支付通道（通用子领域）对接走现成 SDK + 防腐层。**营销上下文**——聚合：优惠券聚合（Coupon，状态机 未使用→已核销→已过期，不变式"核销订单数 ≤ 发行量"）；事件：优惠券已核销；与订单通过事件解耦（订单发"已下单"，营销核销，不反向阻塞下单）。**物流上下文**——聚合：运单聚合（Shipment，不变式"一个订单只有一个激活运单"）；数据策略：配送地址是订单事件携带的快照值对象，不实时回查订单——"下游维护自己的数据视图"原则的现场演示。四个上下文的共同模式：独立聚合 + 事件协作 + 幂等消费，再次验证"边界、契约、数据所有权"三件套。

## 第五步：落地验收与持续演化

验收清单：上下文地图与代码一致（依赖扫描零越界）；每个聚合能说出不变量清单；订单取消、支付超时、库存释放三条关键链路端到端事件流可追踪（tracing 带事件 ID）；契约测试覆盖订单-支付、订单-库存两条对外契约；发布流程独立（任何服务可独自上线）。演化预案：优惠券上下文膨胀出"营销引擎"时，从模块化单体抽取为服务（有事件契约兜底，抽取是平滑的）；订单上下文出现第二个业务团队视角（批发 vs 零售）时，评估拆分为两个上下文——边界演化是常态，地图保持更新即可。整套案例的复盘主线：没有一次建模决策是"技术最优"，每个决策都是业务语义（不变量）、团队结构（认知负荷）、部署现实（发布频率）三方权衡的结果——这正是 DDD 区别于"数据库设计 + CRUD"方法论的地方。

> 🎯 **核心要点**：案例的完整链条证明 DDD 的价值排序——**先建模（事件风暴发现规则）→ 再划界（上下文映射定契约）→ 后实现（聚合纪律 + 分层）→ 最后部署（按压力决定服务化）**。每一步的错误都会在后续放大：事件风暴漏掉的超时规则会让聚合不变量残缺，上下文映射选错的同步调用会让微服务变成分布式单体。建模在前，架构在后，是案例的总纲。
