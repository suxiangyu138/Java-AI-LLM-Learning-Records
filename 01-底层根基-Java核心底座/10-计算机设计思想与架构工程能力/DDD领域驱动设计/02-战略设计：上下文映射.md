# 02-战略设计：上下文映射

> 定位：限界上下文切完之后，上下文之间的协作关系决定系统是"清晰的拼图"还是"缠在一起的毛线球"。上下文映射就是协作关系的九种模式，其中防腐层是保护模型纯度的第一道防线。

## 为什么协作关系需要显式建模

上下文之间必然协作（订单上下文要通知物流上下文"已支付"），但协作方式不同，双方模型的耦合程度天差地别。不显式定义协作关系，团队就会默认采用"直接调对方接口 + 共享对方对象"——这是最紧的耦合，任何一方的模型调整都会破坏对方。上下文映射的价值：把协作模式**写进文档和代码边界**，让"我们之间的耦合程度"成为有意识的设计决策而非默认值。

## 六种主要映射模式

| 模式 | 方向/依赖 | 耦合度 | 一句话本质 |
|---|---|---|---|
| 共享内核 | 双方共享一小块模型 | 高（共享代码） | 极小共享 + 全员评审，仅限少量核心概念 |
| 客户-供应商 | 下游依赖上游接口 | 中 | 上游开发计划优先保证下游契约，类似 SLA |
| 遵奉者 | 下游完全采用上游模型 | 中 | 下游放弃自己的模型，直接翻译上游（别用，会污染） |
| 防腐层 | 下游自己建模，翻译上游 | 低 | 下游模型保持纯净，ACL 做双向翻译 |
| 开放主机服务 | 上游发布稳定协议 | 低 | 用 REST/事件/契约测试发布公开 API |
| 发布-订阅 | 无直接依赖 | 最低 | 事件广播，双方通过消息总线解耦 |

两个被低估的补充模式：**分离方式（Separate Ways）**——两个上下文完全无协作，各自实现（识别后直接删掉集成代码）；**大泥球（Big Ball of Mud）**——没有模式、共享模型、耦合混乱的反模式，是重构的起点而非终点。2026 年的实践共识：能选松耦合就不选紧耦合，但**刻意保留少量紧耦合（共享内核）胜过伪装成松耦合的隐式依赖**——诚实标注比美观更重要。

## 防腐层：最常被低估的模式

防腐层（Anti-Corruption Layer，ACL）解决"外部系统模型 vs 本上下文模型"的翻译问题。经典场景：遗留 ERP 的"客户"有 30 个字段 8 种状态，而订单上下文只需要其中 5 个字段和 3 种状态——直接复用 ERP 对象，订单模型的纯度立刻被污染；正确做法是在订单上下文边界内建 ACL：对外调用 ERP 适配器，对内暴露订单自己的领域模型，翻译逻辑全部收在 ACL 里。

ACL 的实现形态：门面（统一入口）+ 适配器（协议翻译）+ 转换器（模型映射）+ 集成测试（契约验证）。判断 ACL 是否必要：外部模型的术语/结构/语义与本上下文差异越大越需要；同构系统（同一团队维护的兄弟上下文）直接走客户-供应商或发布订阅即可，没必要 ACL。防腐层与"适配器模式"的区别：适配器解决接口差异，ACL 解决**模型语义**差异——它翻译的是"概念"不是"方法签名"。

## 上下文映射与事件驱动

2026 年微服务实践强烈倾向异步协作：上游上下文发布领域事件（"OrderPaid"），下游上下文订阅并按需取数，双方无同步依赖。事件驱动下的上下文映射退化得非常简单——上游发布-订阅，下游自己建模 + 可选防腐层。但代价转嫁到事件契约本身：**事件的语义（字段含义、幂等键、版本）成为跨上下文契约**，需要事件规范管理（命名过去时、schema 版本化、兼容性策略），这是"上下文映射从代码层上升到消息层"的迁移。

## 上下文映射的七个常见错误

2026 年企业实践的教训清单，每条都对应一个真实事故：**1. 隐藏的共享数据库**——地图上画着"发布-订阅"，实际两个服务读写同一张表（最普遍，先查 DBA 权限矩阵）；**2. 同步调用伪装成事件**——消息总线只是"异步的 RPC"（下游收到消息立刻回查上游 API，等于同步依赖 + 额外一跳）；**3. 防腐层只翻译字段不翻译语义**——把 ERP 的"状态码 3"机械映射为本地"已发货"，却丢失了 ERP 中"状态码 3 表示已发货但可能被回滚"的语义（防腐层要翻译概念，不是搬运字段）；**4. 遵奉者被默认为低成本**——直接采用上游模型确实省了翻译，但上游每次模型变更都会穿透进来，长期成本最高；**5. 共享内核悄悄扩大**——从"两个类"扩成"半个库"，评审纪律失守；**6. 开放主机服务只有接口没有契约**——没有契约测试的 API 不是"开放主机服务"，是"没有文档的依赖"；**7. 上下文地图不更新**——地图与代码脱节后，新人按旧地图集成，错误边界被固化。自查方法：每个协作线问三个问题——"依赖方向对吗？共享了什么？变更谁受影响？"

## 模式选择的决策树

把六种模式变成可执行的决策树，避免"凭感觉选"：**两个上下文是否必须协作？** 否 → 分离方式（并检查是不是该合并——不协作却共享数据的上下文是隐式依赖，先解决共享）。**是否共享少量核心概念且双方都会修改？** 是 → 共享内核（极小范围 + 全员评审纪律）。**一方是遗留系统/外部系统？** 是 → 防腐层（本上下文建模自由，翻译成本收在 ACL）。**双方同团队同节奏演化？** 是 → 客户-供应商（下游依赖上游接口，契约测试锁定）；或遵奉者（下游模型简单、愿意完全跟随上游——想清楚污染代价再用）。**上游能发布稳定协议？** 是 → 开放主机服务（REST + 契约测试）。**能容忍异步？** 是 → 发布-订阅（事件驱动，耦合最低）。决策树的末端提示：能异步就异步（发布-订阅）、能独立就独立（防腐层）、能契约就契约（开放主机）——三个"能"依次检查后，剩下的场景才轮到共享内核与遵奉者这类紧耦合选择，并且紧耦合选择必须写成 ADR 说明理由。

## 上下文地图的绘制与维护

上下文映射的产物是**上下文地图（Context Map）**：一张标注所有上下文与协作关系的图，是战略设计的"架构图"。绘制要点：每个上下文标注其子领域类型与归属团队；每条协作线标注模式；地图纳入架构评审（新增集成必须在地图上登记）。2026 年的实践教训：**上下文地图必须与真实代码一致**——大量团队的 Context Map 画得漂亮但代码里全是隐藏的共享数据库和同步调用，地图沦为装饰。一致性验证手段：依赖分析工具扫描跨上下文依赖、数据库 schema 权限审计、契约测试注册表。地图是活文档，随边界演化持续更新，而不是交付物。

> 🎯 **核心要点**：上下文映射的决策序列是"先定协作模式（六选一）→ 再定技术形态（同步/异步/事件）→ 最后落实契约管理"。防腐层保护的是模型纯度，开放主机服务输出的是稳定契约，发布订阅换取的是演化自由度——三者的共同前提是：耦合必须显式、可审计、可变更，反对一切隐式共享。
