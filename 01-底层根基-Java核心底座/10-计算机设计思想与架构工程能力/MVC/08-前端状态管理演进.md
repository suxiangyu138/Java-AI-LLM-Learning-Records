# 08-前端状态管理演进

> 定位：MVC 双向绑定的最大缺陷是"状态变更不可追溯"，Flux 用它最鲜明的纪律回应——单向数据流。2026 年的状态管理已从"Redux 大一统"走向"按状态来源分类管理"：跨组件状态用 Store、细粒度状态用原子化库、服务端状态用专用库。

## Flux：单向数据流的起源

Flux（2014，Facebook）针对 MVC 双向绑定的调试噩梦提出四条纪律：**状态集中**（Store 是唯一状态持有者）；**变更只能经 Action**（显式意图，禁止组件直接改 Store）；**单向流动**（Action → Dispatcher → Store → View）；**View 只读**（组件通过订阅读取状态，通过派发 Action 变更）。核心价值是**可追溯性**：任何状态变化都能沿 Action 链回放，DevTools 时间旅行调试成为可能。代价是样板代码（Action 类型、Action Creator、Reducer、Store 四件套）——这是后续一切"减少样板"改革的起点。

## Redux 与三大原则

Redux 把 Flux 精炼为**三大原则**：单一数据源（整个应用一个 Store 树）、状态只读（变更只能 dispatch action）、纯函数变更（Reducer 必须纯函数——同输入同输出、无副作用）。纯函数 Reducer 的意义：可预测（测试极简）、可回放（时间旅行）、可序列化（服务端渲染状态复用）。2026 年的 Redux 已是 Redux Toolkit 形态：createSlice 自动生成 action/reducer（样板大减）、RTK Query 内置服务端状态缓存——Redux 从"纯 Flux 实现"演进为"综合状态方案"。Vue 生态的 Pinia 同理：显式 store + 显式 action，单向语义（组件不能直接改 state，必须经 action）——**"Vue 响应式做局部、Pinia 单向流做全局"是 2026 年的标准组合**。

## 原子化状态：细粒度的逆袭

Redux 大一统时代的问题：全局单一 Store 导致**无关组件共享状态树、更新时全部重渲染**（性能）与**样板代码与状态复杂度成正比**（心智负担）。2026 年的答案之一：**原子化状态库**（Zustand、Jotai、Recoil）——状态按原子（atom）拆分，每个原子自带订阅者集合，依赖追踪精确到原子级：只有订阅了该原子的组件重渲染。

```js
// Zustand：微型 Store，状态 + 命令 + 选择器订阅
const useCart = create((set) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
  total: (s) => s.items.reduce((sum, i) => sum + i.price, 0),
}))
// 组件只订阅自己需要的切片：
const items = useCart((s) => s.items)
```

Zustand 与 Redux 的本质区别：**不强制全局单一 Store**（可以多个独立 Store）、**不强制单向约束**（命令直接改状态，靠纪律而非框架）、**选择器订阅**（细粒度重渲染）。选择标准（2026）：状态数量 <20 且交互简单 → 组件局部状态；状态跨组件共享但规模可控 → Zustand/Jotai 原子化；状态复杂且需要时间旅行/严格单向 → Redux Toolkit；同时用 Redux 的团队常配"先上 Zustand，出现可追溯性需求再上 Redux"的渐进路径。

## 服务端状态：数据获取与缓存的专项化

2026 年最务实的分类是**把状态分为客户端状态与服务端状态**：服务端状态（从 API 获取的数据）不是"前端状态管理"该管的——它有自己的生命周期（加载/成功/失败/失效）、缓存策略（TTL、重新验证）、并发语义（重复请求合并）。React Query/SWR 类库（Vue 生态为 TanStack Query 同源）专项解决：**缓存**（同一 key 的请求自动合并去重）、**失效与重新验证**（mutation 后自动刷新相关查询）、**乐观更新**（UI 先行、失败回滚）、**无限滚动/分页查询**。其核心抽象是"查询键 + 查询函数"：`useQuery({ queryKey: ['products', page], queryFn: fetchProducts })`——**把"数据获取"从组件/Store 中彻底抽出**，组件只声明"我需要这个数据"，库管生命周期。2026 年共识：**服务端状态永远优先用 React Query 类库，而不是塞进 Redux**——Redux 管跨组件客户端状态，React Query 管服务端数据，职责分离。

## 服务端状态库的缓存失效机制

React Query 类库的核心难点是"缓存何时失效"，掌握失效机制才算会用：**失效的三种触发**——mutation 成功后按 queryKey 前缀失效相关查询（invalidateQueries）、定时重新验证（refetchInterval，轮询场景）、窗口聚焦时静默重验证（refetchOnWindowFocus，保证数据新鲜度）；**缓存的新鲜度模型**——staleTime（数据在多久内视为新鲜，期间不重新请求）与 gcTime（缓存保留时长，超出后清理）两个时间维度分开管理；**乐观更新的正确姿势**——先本地更新 UI（onMutate 写入临时值）、失败时回滚（onError 恢复原值）、成功时失效查询拉真实数据（settled 后 invalidate）——"UI 先行、真实数据兜底"避免闪烁。服务端状态库与 Store 的分工再强调：**查询数据（从 API 来）归查询库，写操作结果与 UI 状态归 Store**——把查询结果塞进 Redux 是 2026 年仍在发生的高频错误。

## 状态分类管理框架（2026 共识）

| 状态类型 | 例子 | 推荐方案 |
|---|---|---|
| 局部 UI 状态 | 弹窗开关、表单输入 | 组件本地 state（Vue ref / React useState） |
| 派生状态 | 过滤后的列表、合计 | 计算属性 / useMemo（不存储，只推导） |
| 跨组件共享 | 用户信息、主题、购物车 | Store：Zustand/Jotai（轻）或 Pinia/Redux Toolkit（重） |
| 服务端状态 | API 数据、缓存 | React Query/SWR/TanStack Query |
| URL 状态 | 路由参数、筛选条件 | 路由库（URL 即状态源，刷新可恢复） |

框架的总体纪律：**状态就近声明（局部优先）、跨层才提升（共享进 Store）、服务端不过手（查询库直管）**——按来源分类而不是按模式统一，是 2026 年状态管理对 Flux 时代的最大修正。五类划分还有一条隐藏收益：团队新成员只需按类型对号入座，无需理解全局状态模型——分类降低认知负荷，与 2026 年"架构为团队认知服务"的共识一致。

## 从 Flux 到原子化的具体教训

Redux 大一统时代留下的工程教训值得单独记录：**教训一：Store 里放一切是反模式**——把 UI 状态（弹窗开关）、服务端数据（用户列表）、派生状态（过滤结果）全塞进全局 Store，导致 Store 膨胀、action 噪音化、组件全部订阅无关状态；2026 年修复：按 08 篇的分类表各归其位。**教训二：样板代码不是框架问题，是抽象层级问题**——Redux 四件套的样板本质是"把隐式状态变更显式化"的代价；RTK 的 createSlice 通过"约定优于配置"消掉样板，说明样板可压缩但显式化的思想不可丢弃。**教训三：时间旅行调试的实用价值有限**——DevTools 的时间旅行在真实项目中的使用频率远低于宣传，但"状态可回放"的思想催生了更有价值的产物：state 序列化（SSR 状态复用）、状态快照（bug 报告携带现场）。教训的总结论：**单一 Store 与单向流的纪律，在"复杂共享状态"场景依然正确；把它推广到一切状态，才是 2026 年反思的对象**。

## 演进逻辑总结

状态管理的演进与 MVC 的演进同构：MVC 双向绑定 → 状态路径不可追溯（问题）→ Flux 单向流（可追溯）→ Redux 简化（可预测）→ 样板与粒度问题 → 原子化与分类管理（2026）。每一步都是"上一个方案的代价成为下一个方案的起点"——与 01 篇的"三次危机与回应"同构。给学习者的心智模型：**追溯性（Flux 的遗产）、细粒度（原子的创新）、分类化（2026 的共识）**三条主线串起全部历史。

> 🎯 **核心要点**：2026 年状态管理的总纲一句话——"不选一个模式，分类用对四个方案"：局部状态用框架原生、派生状态用计算、共享状态用轻 Store（需要可追溯再上 Redux 系）、服务端数据用查询库。Flux 的单向流纪律没有过时，它只是从"唯一方案"降级为"复杂共享状态的方案之一"。Redux 时代的三个教训（Store 不放一切、样板可压缩但显式化不可丢、可回放思想的价值大于时间旅行工具）是理解 2026 修正线的钥匙；服务端状态库的失效机制（invalidate/新鲜度/乐观更新）则是查询库选型的实操纵深。
