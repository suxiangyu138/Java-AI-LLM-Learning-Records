# 09-并发与规模：分治、推拉、悲观乐观

> 定位：三条"系统怎么变大"的思想——分治管"拆"、推拉管"数据怎么流动"、悲观乐观管"并发怎么处理"。共同主题：规模增长时系统如何保持正确与可控。

## 分治思想

**定义**：大问题拆成多个小问题，分别解决再合并。**工程体现**：**分库分表**（数据按维度分片——订单按用户 ID 哈希/按时间范围分表）；**分片**（Kafka 分区 = 并行度上限；ES 分片）；**分布式任务**（大任务拆子任务并行执行——MapReduce 的思想：map 并行处理、reduce 汇总）；**模块化与微服务**（系统按业务拆模块/服务——DDD 的限界上下文就是分治的业务化）。**规模化的第一性原则**：**单个节点有物理上限**（CPU/内存/磁盘/连接数），分治是绕过单点上限的通用手段。

**分治的代价**：**一致性成本**（跨分片事务——分布式事务的复杂度）；**运维成本**（多节点管理）；**查询复杂度**（跨分片 JOIN 不可用，数据按维度冗余）。**设计决策**：**先问"真的需要拆吗"**——单库能扛（读多写少、数据量可控）不拆；**分片键设计决定一切**——按"最高频查询维度"分片（订单按 user_id 分片让"我的订单"查询走单片；按 order_id 分片则"用户维度查询"变跨片扫描）；**分片与扩容**——一致性哈希解决"加节点要迁移多少数据"（迁移面最小），range 分片支持顺序扫描但热点集中。

## 推拉思想

**定义**：**推（Push）**——服务主动推送数据给消费者（变更发生时立刻送达）；**拉（Pull）**——消费者主动轮询拉取数据（按自己的节奏取）。**核心决策**：数据"什么时候流动、由谁发起"按场景选择。

**工程体现**：**消息队列偏推**——生产者发布、消费者订阅，变更即时送达（Kafka/RabbitMQ 的消费模型）；**定时任务大多是拉**——批处理按周期拉取待处理数据（每小时拉一次未支付订单）；**WebSocket/SSE 是推**（实时通知）；**HTTP 轮询是拉**（客户端定时请求）。**选型依据**：**实时性需求**——推的延迟低（毫秒级），拉的延迟 = 轮询周期（分钟级）；**消费者节奏自主权**——拉允许消费者按自身负载取数据（背压天然），推需要消费者处理不过来（限流/积压）；**连接成本**——推需要长连接（连接数与连接维护成本），拉用普通请求（无状态）。

**2026 实践**：**推拉结合**——变更事件推送到消息队列（实时性）+ 消费者按需拉取全量快照（补偿一致性）；**Webhook 是推的 HTTP 形态**（服务端回调，注意幂等与重试——回调场景必须配合幂等设计，见 05 篇）；**消费者滞后（Lag）监控**——拉模型下消费进度可视化（Kafka consumer lag 是核心指标）。**面试常问**："消息队列是推还是拉？"——Kafka 是"拉为主"（消费者主动拉取，broker 不推），RabbitMQ 是"推为主"（broker 推送）；理解这个差异就理解了两种队列的消费模型与背压机制。

## 悲观与乐观并发控制

**定义**：**悲观**——认为并发冲突一定会发生，提前上锁（数据库行锁、分布式锁）；**乐观**——认为冲突很少发生，不上锁，冲突发生再重试（版本号/CAS）。**核心决策**：锁的代价（阻塞、死锁风险、性能）vs 重试的代价（冲突时重试成本）按冲突概率选择。

**工程体现**：**悲观锁**——SELECT ... FOR UPDATE（长事务、复杂逻辑、冲突率高场景——订单金额计算、库存扣减）；分布式锁（Redisson/Redis SETNX——跨服务互斥）；**乐观锁**——version 字段/CAS 更新（冲突率低、短操作场景——状态迁移（06 篇）、点赞计数）；**补偿**——乐观冲突时返回"冲突"错误，客户端重试或提示用户。**选择矩阵**：冲突率高 + 逻辑复杂 → 悲观；冲突率低 + 操作简短 → 乐观；读多写少 → 两者都少用（读写分离 + 快照读）。

**2026 实践**：**CAS 在状态机中的主流化**（06 篇的 `UPDATE ... WHERE status=?` 条件更新）；**锁的粒度意识**（行锁 vs 表锁、分布式锁的粒度与持有时间——锁粒度越细并发越高，但死锁面越复杂）；**锁超时与可重入**（分布式锁必须有超时防死锁，Redisson 看门狗续期）；**乐观重试的幂等配套**（重试 = 重复执行，必须幂等——乐观并发与幂等设计天然配对）。**面试对比答法**：悲观"宁可错杀不可放过"、乐观"信任至上冲突再战"；判据"冲突频率 × 冲突代价 vs 锁代价 × 死锁风险"。

## 实战案例：库存系统的并发与规模设计

一个电商库存系统的设计演示三条思想的完整运用：**规模问题**——单库单表扛不住秒杀流量，库存表成为热点行；**分治方案**——库存按 SKU 维度分片（每个 SKU 独立表/独立 Redis key，热 SKU 与冷 SKU 互不干扰）；**并发方案选型**——扣减是高频短操作，用乐观锁（`UPDATE stock SET qty=qty-? , version=version+1 WHERE sku_id=? AND version=? AND qty>=?`——数量校验与版本校验一次原子完成），冲突率高时再考虑悲观锁或 Redis 预扣减（Lua 原子减 + 异步落库）；**推拉结合**——库存变更事件推送到 MQ（下游订单/搜索订阅，实时性），对账任务拉取快照（每日核对，兜底一致）。设计决策的推理链：**先分治（拆维度）→ 再选并发（乐观优先）→ 最后定通信（推拉结合）**——与 09 篇路线图完全一致。这个案例的面试价值：完整演示"思想 → 决策 → 实现"的推理过程，比背概念更能展示架构能力。

## 悲观乐观与数据库隔离级别

悲观乐观的选择与数据库事务隔离级别存在联动，面试常把两者一起考：**悲观锁与隔离级别**——SELECT ... FOR UPDATE 在 READ COMMITTED 下即可工作（加锁读与隔离级别无关，锁本身提供互斥）；但"先查后改"的检查-执行序列必须用 FOR UPDATE 或升隔离级别（否则读到旧值后覆盖写，丢失更新）；**乐观锁与隔离级别**——version 条件更新（UPDATE ... WHERE version=?）在任何隔离级别下都正确（原子条件更新不依赖隔离级别），这是乐观锁的工程优势——无需调整隔离级别、无锁等待、无死锁。**选择联动结论**：悲观方案要评估锁等待与死锁（长事务锁持有越久风险越高，配套锁超时与重试）；乐观方案要评估冲突率与重试成本（冲突率高时重试风暴——退避 + 上限）。**2026 实践**：默认乐观（条件更新），确需悲观时用短事务 + FOR UPDATE + 锁超时，并优先考虑"减少临界区"（把长流程拆短事务）而非堆锁。面试答法："乐观默认、悲观例外、临界区尽量短"三句话收尾。

## 三条思想的组合：规模化路线图

规模增长的三步走：**第一步：垂直优化**（缓存 + 索引 + 读写分离——不拆就能扛则不拆，08 篇缓存思想的用武之地）；**第二步：分治**（分库分表/分片/分布式任务——单点上限到了才拆，按最高频查询维度选分片键）；**第三步：异步化**（推拉结合——实时链路用消息推送，批处理用拉取，流量削峰）。并发控制贯穿全程：**冲突率低用乐观、高用悲观、跨服务用分布式锁**。路线图的总体纪律（与 YAGNI 呼应）：**先不拆、能缓则缓、到点才拆**——规模化的正确姿势是"被数据驱动的必要性推动"，不是"架构洁癖驱动的提前拆分"。

> 🎯 **核心要点**：三条规模化思想一句话——分治"大拆小"、推拉"按需流动"、悲观乐观"按冲突率选锁"。记忆话术：分治拆维度、推拉看实时性、并发看冲突率。面试答法：每条"定义 + 工程体现 + 选型依据 + 组合路线图"——能讲出"先垂直后水平、推拉结合、乐观优先"的完整决策链，就是架构师级答案。
