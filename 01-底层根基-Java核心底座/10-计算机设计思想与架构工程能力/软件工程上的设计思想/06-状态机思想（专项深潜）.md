# 06-状态机思想（专项深潜）

> 定位：复杂流程业务（订单、审批、支付）的骨架思想——对象状态有限、流转严格定义、禁止随意改状态。本篇覆盖 FSM 契约、并发安全（CAS/版本号）、泛型触发器、事件溯源与幂等的结合。

## 状态机思想的核心

**定义**：对象状态有限，状态流转严格定义——每个状态 + 每个事件 → 唯一合法目标状态（或拒绝），禁止随意修改 status 字段。**为什么需要**：订单的 status 字段若可被各处直接 set，就会出现"已发货回退到待支付"、"已取消再次支付"等业务不可能状态；状态机的价值是**把"合法的变化路径"变成显式契约**（状态迁移表），非法迁移在代码层面被拦截而非运行期靠运气。

**核心三要素**：**状态集合**（有限枚举，如 PLACED/PAID/SHIPPED/CANCELLED）；**事件集合**（触发流转的输入，如 PayEvent/CancelEvent）；**迁移函数**（(state, event) → state，未定义的组合即非法）。2026 年实践强调：**每个状态作为不可变值对象**，事件处理器返回"新状态实例"而非修改状态字段——天然并发安全与逻辑隔离。

## 实现形态一：状态模式与迁移表

**状态模式**（State Pattern）——每个状态一个类，状态类自己处理事件并返回下一状态：订单状态类簇（PlacedState.handle(PayEvent) → PaidState）。**迁移表驱动**——`Map<(State, Event), 处理器>` 查表驱动：触发前查表，查不到即抛 IllegalStateException（非法迁移显式报错）；查得到执行处理器并切换状态。**2026 泛型状态机触发器**（金融订单场景）：`StateTrigger<S, E, C>` 泛型解耦状态类型、事件类型、业务上下文，以迁移映射驱动合法转换，不写死 if-else——动作处理器封装完整业务单元：内部 @Transactional 完成本地更新；对外部系统调用失败返回 RETRYING/FAILED 中间态；提供 rollback(C) 默认方法支持补偿；所有动作默认具备幂等键（`ctx.orderId + ":" + event.name()`）。

**对比 if-else 硬编码**：散落的 `if (status == PAID && event == CANCEL)` 分支——无法穷举所有组合、无全局视图、测试覆盖靠运气；迁移表 + 处理器让"全部合法路径"一目了然、可测试（每路径一用例）、可审计（每次迁移记录 from→to + 事件 + 触发者）。

## 并发安全：CAS 与版本号

**问题**：两个请求同时触发状态迁移（支付成功 + 用户取消）——都读到 PLACED，都执行各自的迁移，最后落库互相覆盖。**方案一：CAS 原子更新**——`UPDATE orders SET status='PAID', version=version+1 WHERE id=? AND status='PLACED'`（受影响行数 = 1 才成功，0 说明状态已变，返回冲突让调用方处理）——无锁实现原子状态迁移，适合冲突率低、短临界区；**方案二：行锁/悲观锁**——SELECT FOR UPDATE，适合复杂逻辑长临界区（2026 实践建议：能 CAS 尽量 CAS，锁的代价与死锁风险更高）。**方案三：数据库约束兜底**——CHECK 约束或触发器（状态合法迁移的数据库级最后防线，防代码漏网）。

## 与事件驱动的结合

**状态机 + 事件发布**：状态迁移成功后发布领域事件（StateChangeEvent 携带 from/to/event/时间/操作者）供审计、通知、异步补偿订阅——状态机是"状态变更的裁决者"，事件是"变更的广播者"，两者解耦（状态机不关心谁订阅事件）。**与事件溯源（Event Sourcing）**：传统 CRUD 覆写记录丢失"怎么变成这样"的上下文；事件溯源只追加不可变事件流，状态由重放事件派生——状态机的迁移函数成为重放的核心逻辑，审计天然完整。**与 Outbox**：状态变更与事件发布的一致性用 Outbox 模式保证（同事务写状态 + outbox 表）。

**2026 状态机设计的最新实践**：**领域事件严格区分"业务意图"与"可靠传输"**——把领域事件直接投递到 Kafka 并携带序列化与重试逻辑，会导致重复消费和状态机错乱（2026 DDD 落地陷阱研究）；正确做法是领域事件承载业务意图、传输层负责可靠投递，两层职责分离；**状态迁移契约不可变化**——定义不可变的 StateTransitionContract 契约接口，声明"谁、何时、从哪到哪"，状态机仅负责流转，事件发布由独立监听器完成，为事件溯源和审计提供结构化元数据；**运行时动态重入（forceTransition）**——绕过前置状态校验的强制迁移（运维修复场景），配合数据库 last_event 和 version 字段确保重入不覆盖更高版本的状态变更——强制迁移必须留痕（谁、何时、为什么）。

## 与幂等设计的结合（2026 关键）

**状态机是幂等的天然载体**：重复事件到达时——`PaidState.handle(PayEvent)` 收到重复支付事件，直接返回自身（不新建状态），记录日志"忽略重复支付事件"——**幂等处理内置于状态处理器**。**组合约束**：`(order_id, expected_version)` 或 `status IN ('pending','failed')` 条件更新——把"状态校验"与"更新"原子化（见 05 篇的操作版本号机制）。**补偿事务的幂等**：Saga 补偿重复执行不改变最终状态，手段包括唯一业务 ID + 状态机校验、INSERT ... ON CONFLICT DO NOTHING、SET key value NX EX ttl。**2026 总结论**：**状态机是骨架、幂等是底线、事件是神经**——三者组合是支付/下单/库存核心链路的标配。**状态机的完整测试策略**：mock 数据优于 mock 方法——直接构造真实状态实例 + 真实事件断言返回值；每条合法迁移一用例、每条非法组合一用例（断言抛错）、重复事件一用例（断言返回自身）——路径即用例的可测试性，正是状态机优于散落 if-else 的关键工程收益。

## 完整代码形态：订单状态机的 Java 实现

一个最小完整示例串联本篇全部要点（枚举状态、迁移表、处理器、CAS、幂等）：

```java
enum OrderState { PLACED, PAID, SHIPPED, CANCELLED }
enum OrderEvent { PAY, CANCEL, SHIP }

final class Order {                                  // 状态作为不可变值对象
    private final OrderState state;                  // final：状态不可原地修改
    private final long version;                      // 版本号：CAS 依据

    private Order(OrderState state, long version) { this.state = state; this.version = version; }

    Order on(OrderEvent e) {                         // 幂等内置：重复事件返回自身
        if (e == PAY && state == PAID) { log("忽略重复支付"); return this; }
        OrderState next = TRANSITIONS.get(Map.entry(state, e));   // 迁移表查表
        if (next == null) throw new IllegalStateException(state + " 不能接受 " + e);
        return new Order(next, version + 1);
    }
    static final Map<Map.Entry<OrderState, OrderEvent>, OrderState> TRANSITIONS = Map.of(
        Map.entry(PLACED, PAY), PAID,
        Map.entry(PLACED, CANCEL), CANCELLED,
        Map.entry(PAID, SHIP), SHIPPED);
}
// 持久化：UPDATE orders SET state=?, version=version+1 WHERE id=? AND version=? AND state=?
// 受影响行数 0 → 并发冲突，返回重试错误
```

代码要点回读：迁移表是唯一的事实源（合法路径一眼可见）；非法迁移抛 IllegalStateException（Fail-Fast）；version 递增支撑 CAS 并发；重复事件幂等返回自身；测试按迁移表逐条断言（含非法组合断言抛错）。这份代码可以直接作为订单类业务的脚手架。

## 工程落地清单

1. **状态与事件全部枚举化**（Enum 而非字符串散落）；
2. **迁移表集中定义**（一文件可读全部合法路径）；
3. **非法迁移显式抛错**（ErrInvalidTransition 类错误，用 errors.Is 判断而非字符串比较）；
4. **状态不可变**（处理器返回新状态，不修改旧实例）；
5. **并发更新用 CAS**（版本号或条件更新，冲突返回可重试错误）；
6. **每次迁移发布事件**（审计与通知）；
7. **幂等内置于处理器**（重复事件返回自身）；
8. **测试按迁移路径写**（每 (state, event) 组合一用例，含非法路径）。

> 🎯 **核心要点**：状态机思想一句话——"状态流转是显式契约，不是散落的分支"。面试答法：定义（有限状态 + 合法迁移）→ 三要素（状态/事件/迁移函数）→ 实现（迁移表/状态模式/CAS）→ 结合（幂等内置 + 事件发布 + 事件溯源）→ 反例（到处 setStatus 的订单服务）。2026 升级：泛型触发器与操作版本号机制是状态机 × 幂等的生产级答案。
