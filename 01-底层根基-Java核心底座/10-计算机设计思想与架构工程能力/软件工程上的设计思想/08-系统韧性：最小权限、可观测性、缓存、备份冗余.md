# 08-系统韧性：最小权限、可观测性、缓存、备份冗余

> 定位：四条"生产安全"思想——最小权限管"权限面"、可观测性管"故障发现"、缓存管"性能"、备份冗余管"数据安全"。共同主题：系统在真实环境里活得久。

## 最小权限原则

**定义**：组件、接口、账号只分配完成任务必须的权限——不多给一分。**工程体现**：服务之间调用只开放必要字段与端点（接口最小面）；数据库账号按职责分权（应用账号只给 SELECT/INSERT/UPDATE 所需表，不给 drop/truncate，甚至不给全库）；云资源按角色授权（IAM 最小权限策略）；容器非 root 运行；密钥与权限分离（凭据独立管理，轮换自动化）。

**为什么重要**：权限是"爆炸半径"的边界——账号权限越大，被攻破/误操作时的破坏面越大（删库事故大多源于"一个账号什么都能干"）；**纵深防御**：即使一层被突破（应用被注入），最小权限让下一层（数据库）的破坏受限。**2026 实践**：多云/微服务环境下权限审计常态化（定期扫描"谁有什么权限"）；权限变更走审批流（权限即负债，新增权限要理由）；服务间调用用 mTLS + 按服务分权而非共享凭据。

**反例**：所有服务共用一个数据库超管账号；管理后台账号权限不分角色；接口返回多余字段（数据泄漏面扩大——最小权限同样适用于"数据暴露面"：接口只返回调用方需要的字段）。

## 可观测性设计

**定义**：系统设计时就要考虑：日志、指标、链路追踪——出问题能定位，而不是写完代码再补埋点。**三支柱**：**日志**（结构化、带上下文：traceId/业务 ID/耗时）；**指标**（QPS、延迟分布、错误率、资源水位——Prometheus 系）；**链路追踪**（跨服务调用链——OpenTelemetry 标准，2026 年已是非协商性基础设施）。

**设计要点**：**埋点在设计期规划**（每个外部调用、每个状态迁移、每个异常分支都要能回答"发生了什么"）；**指标先行于告警**（先有指标再定阈值再告警——没有指标的告警是拍脑袋）；**日志即证据**（故障复盘依赖日志完整，日志级别设计（debug/info/warn/error 各管什么）与脱敏（敏感字段不落日志）同属设计内容）；**健康检查**（存活/就绪探针——部署编排的依据）。

**反例**：上线后才发现"系统为什么慢"无从查起（无链路追踪）；告警风暴（阈值拍脑袋，每 5 分钟一条无意义告警）；日志打满敏感信息（用户身份证号进日志，审计违规）。**与容错的关系**：降级/熔断/重试必须埋点（04 篇）——"系统为什么降级了"是运维第一问，无埋点的降级等于无降级。

## 缓存思想

**定义**：用空间换时间——把高频访问的计算结果缓存，减少重复计算与存储访问。**核心价值**：性能数量级提升（内存读 vs 磁盘/网络读）；保护下游（数据库不被重复打爆）。

**设计要点（面试必考）**：**失效策略**（TTL/主动失效/版本化——缓存与数据一致性的平衡）；**四大问题**：**击穿**（热点 key 过期瞬间高并发打到 DB——互斥锁/逻辑过期）、**穿透**（查询不存在的数据，缓存与 DB 都打——布隆过滤器/空值缓存）、**雪崩**（大量 key 同时过期导致 DB 被打爆——过期时间加随机抖动/多级缓存）、**一致性**（先更新 DB 还是先删缓存——Cache Aside/双删/延迟双删，2026 共识是 Cache Aside + 消息异步失效）。**缓存分层**（本地缓存 Caffeine + 分布式缓存 Redis + CDN——按数据规模与一致性要求分层）。

**反例**：只加缓存不设计失效（缓存永不更新，数据永久陈旧）；热点 key 不加保护（双 11 秒杀 key 过期即 DB 击穿）；缓存与 DB 一致性不做设计（先写缓存后写 DB，失败后两处不一致）。**与仓库的 Redis 体系的关系**：本思想是"为什么用缓存"的判断层，Redis 体系的缓存一致性（语义缓存）、Lua 原子操作（防击穿锁）、哨兵/集群（可用性）是实现层——思想指导实现选型。

## 备份与冗余

**定义**：不要单点——重要数据多副本，故障可以切换副本。**核心价值**：**数据安全**（误删/损坏可恢复）与**可用性**（节点故障不中断服务）。

**工程体现**：**数据备份三层**（本地备份 + 异地备份 + 冷备归档——3-2-1 原则：3 份副本、2 种介质、1 份异地）；**备份验证**（定期恢复演练——没有恢复演练的备份等于没有备份）；**冗余部署**（多副本/多机房/多可用区——无单点）；**故障切换**（主备切换、负载均衡摘除故障节点）；**容灾等级**（RPO 可容忍丢失多久、RTO 多久恢复——备份策略的量化目标）。

**反例**：数据库只跑一份实例（主机宕机即全站不可用）；备份从不做恢复演练（真出事发现备份损坏）；主备切换靠人工（故障 2 小时没人操作）。**补充决策要点**：RPO 与 RTO 的量化——RPO 决定备份频率（每 5 分钟增量备份 → RPO 5 分钟），RTO 决定恢复手段（全量恢复慢 → 主备切换/日志重放快）；两者与成本权衡（备份频率越高存储成本越高）——"可容忍丢失 10 分钟数据、可接受 30 分钟恢复"这类量化目标应写进系统设计文档，作为备份与冗余方案的验收标准。**2026 实践**：备份自动化与验证自动化（定期自动恢复演练 + 报告）；云上多 AZ 部署成为默认；关键数据快照 + 增量备份组合（恢复时间与丢失窗口的平衡）。

## 可观测性三支柱的落地配置

把三支柱落到工程的最小配置：**日志**——统一日志框架（SLF4J + Logback）+ 结构化格式（JSON，字段含 traceId/业务ID/耗时/级别）+ MDC 传递上下文；日志级别语义化（info 记业务流转、warn 记可恢复异常、error 记需要人处理的事件——error 数量即告警信号）。**指标**——Micrometer + Prometheus：必配四类指标（QPS、P99/P95 延迟、错误率、资源水位），业务指标按需（订单量、支付成功率）；指标命名规范（命名空间 + 指标名 + 标签，标签基数控制）。**链路追踪**——OpenTelemetry：SDK 自动埋点（HTTP 客户端/数据库调用/消息消费）+ traceId 跨服务传递（HTTP 头注入）+ 采样策略（全量保留错误 trace、采样正常 trace）。**告警设计**——先指标后阈值（告警必须有指标依据）、分级（P1 页面故障/ P2 功能降级/ P3 潜在风险）、抑制与去重（告警风暴治理）。落地顺序：日志先行为最快、指标次之（自动采集）、链路最后（侵入最小但要治理采样）——三支柱齐备后，"系统为什么慢"才能按 trace 定位到具体调用。

## 四条思想的组合：生产安全的四道防线

**权限管"进得来吗"**（最小权限：攻破一层破坏受限）；**观测管"出问题知道吗"**（可观测：故障可发现可定位）；**缓存管"扛得住吗"**（性能：高负载不被打垮）；**备份管"丢得起吗"**（冗余：数据可恢复服务可切换）。四道防线缺一不可：无权限防线——安全事故扩大；无观测防线——故障后知后觉；无缓存防线——流量高峰打垮 DB；无备份防线——数据丢失无法恢复。面试答法：每条"定义 + 工程体现 + 反例 + 量化指标（权限审计频率/告警准确率/缓存命中率/RPO-RTO）"。

> 🎯 **核心要点**：四条生产安全思想一句话——最小权限"权限最小面"、可观测性"故障可定位"、缓存"空间换时间"、备份冗余"数据可恢复"。记忆话术：权限管爆炸半径、观测管发现速度、缓存管扛压能力、备份管恢复底线。共同验收标准：任何单一故障（权限泄漏/性能尖峰/节点宕机/数据损坏），系统都有对应的防线。
