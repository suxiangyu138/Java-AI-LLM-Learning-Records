# 04-健壮性设计：防御式、Fail-Fast、容错

> 定位：系统"不出错"的三道防线——防御式编程防输入错误、Fail-Fast 让错误尽早暴露、容错设计让部分故障不拖垮整体。三者的关系：防御与快速失败是"个体正确"，容错是"群体韧性"。

## 防御式编程

**定义**：不信任外部输入，提前校验参数；边界判断；异常捕获；失败提前返回。**核心澄清（2026 高频误读）**：防御式编程不是疯狂加 try-catch 吞异常，而是**提前拦截非法输入**——"接收方永不假设输入合法"是它的精神；吞异常把错误藏起来恰恰是它的反面。

**工程体现**：入参校验（DTO 层 @Valid + 服务层业务校验双层）；外部系统返回值判空与格式校验；配置项启动时校验（非法配置启动即失败而非运行中爆雷）；时间与数值边界判断（金额非负、日期不晚于今天）。**分层校验的职责划分**：接口层校验"格式合法性"（字段必填、长度、格式），业务层校验"语义合法性"（余额是否足够、状态是否可转换）——两层各管一段，不在 Controller 里写业务校验、也不在 Service 里写格式校验。**防御式编程的边界**：对内部可信代码（自己的工具方法）过度防御会污染代码可读性——防御的强度应随"数据来源可信度"递减：外部输入最强、跨服务次之、同进程内部最弱。

## 失败优先 / 快速失败（Fail-Fast）

**定义**：错误尽早暴露，不要把错误藏到后面流程——校验不通过直接抛异常返回，不带着错误数据继续往下跑。**核心逻辑**：错误越早发现，定位成本越低——在入口发现错误的成本是"一次日志"；在数据写库后发现错误的成本是"数据修复 + 全链路排查"。

**工程体现**：参数校验失败立即 400 返回（不继续执行后续逻辑）；启动时校验配置与依赖（连接池连不上、配置缺失 → 启动失败而非运行期半死）；循环中发现非法数据立即中断（而不是攒到最后一起报）；**断言**（assert）用于"绝不该发生"的内部不变量检查。**反例**：把异常收集进 list 继续跑完再一次性返回（吞掉中间错误的上下文）；数据校验不过还继续写入"待修复"状态表（脏数据扩散）。**与防御式编程的关系**：防御式决定"校验什么"（不信任输入），Fail-Fast 决定"校验不过怎么办"（立即失败）——两者是同一姿态的两个阶段。

## 容错设计

**定义**：部分组件故障时，整体系统还能可用。**手段五件套**：**降级**（核心链路保留、非核心功能关闭——推荐页挂了返回默认推荐）；**熔断**（下游故障时快速失败而非等待超时——Sentinel/Resilience4j 的熔断状态机）；**限流**（保护系统不被打垮——令牌桶/滑动窗口）；**重试**（瞬时故障的自动恢复——指数退避 + 重试上限）；**隔离**（故障不扩散——线程池隔离、舱壁模式、多机房）。

**容错设计的核心思想**：**系统性的"部分可用"优于"全部不可用"**——把"一个组件挂了"从"系统事故"降级为"局部降级"。工程体现：降级开关（配置驱动的功能开关）；熔断与重试的分工（熔断管"别再打了"，重试管"再试几次"，二者叠加有顺序问题——先重试后熔断，熔断开启时禁止重试）；兜底数据（缓存/静态数据在数据源故障时返回）。

**反例**：无降级无熔断的调用链——核心支付组件故障拖垮整个下单链路；无限重试（下游已死还狂打，把自己打挂）。**容错与幂等/状态机的关系**：容错的重试必须有幂等兜底（重试 = 重复执行，见 05 篇）；降级后的状态流转必须经状态机校验（见 06 篇）——三者的组合是 2026 年分布式健壮性的标准配方。

## 三道防线的组合使用

**输入链路**：防御式校验（入口拦截）→ Fail-Fast 抛错（立即失败）→ 统一错误处理（ProblemDetail 返回）；**调用链路**：重试（瞬时故障）→ 熔断（持续故障）→ 降级（功能降级）→ 兜底（缓存/默认值）；**恢复链路**：补偿（Saga/事务消息）→ 人工介入（告警 + 降级开关）→ 复盘（故障根因分析）。三层的验收标准：**任何单一组件故障，系统都不应出现"全链路不可用"**——这是容错设计的终极目标。2026 年实践把这三道防线与可观测性（08 篇）绑定：降级/熔断/重试事件必须埋点，否则"系统为什么慢"无据可查。

## 容错设计的量化与验收

容错不是"加了熔断就行"，需要量化目标：**降级覆盖率**——核心链路（支付/下单/登录）是否有降级方案（无降级方案的核心链路是上线事故的定时炸弹）；**熔断参数**——错误率阈值（如 50%）、熔断持续时间、半开探测间隔（Sentinel/Resilience4j 的可调参数要按业务定，抄默认值是失职）；**重试纪律**——重试上限（3 次内）、退避策略（指数 + 抖动）、仅限幂等操作；**隔离度**——线程池隔离时线程池耗尽的影响面（一个下游的线程池爆满不能拖垮其他下游）。**验收方式**：故障注入演练（Chaos Engineering——随机杀节点/延迟注入/超时注入，验证降级路径真实生效）；压测验证限流阈值。**2026 共识**：容错设计是"设计出来的"不是"运维补出来的"——评审清单里"这个服务挂了会发生什么"是架构评审的第一问；答不出降级路径的架构，默认不合格。

## 防御式与 Fail-Fast 的分层实施

两道防线在分层架构中的落点：**接口层（格式校验）**——@Valid 校验字段格式与必填，失败立即 400（Fail-Fast 第一站）；**应用层（语义校验）**——业务前置条件（余额、状态、权限）校验，失败抛业务异常（Fail-Fast 第二站）；**领域层（不变量校验）**——聚合内规则（金额非负、状态机合法迁移）在模型方法内校验，失败抛领域异常（Fail-Fast 第三站）；**基础设施层（资源校验）**——连接、配置、外部响应在入口校验（外部数据判空、格式校验），失败快速失败而非带脏数据继续。分层校验的验收标准：**每层只校验自己该管的**——Controller 校验"格式"、Service 校验"语义"、领域校验"不变量"，越界校验（Controller 里写业务校验）与漏校验（Service 信任入参）同为缺陷。**错误响应的统一**：各层抛出的异常经全局异常处理器统一转换为错误响应（ProblemDetail），错误码语义分层（参数错 400xx / 业务错 4xxxx / 依赖错 5xxxx）——防御的"拦截"与 Fail-Fast 的"暴露"在统一错误契约处汇合。

## 面试高频问答

**Q：try-catch 吞异常为什么是反模式？** 吞异常 = 违反 Fail-Fast：错误信息丢失、调用方误以为成功、问题延迟爆发且无从定位。正确姿势：捕获后要么重新抛出（带上下文）、要么记录完整错误后降级返回，绝不"捕获后无事发生"。

**Q：熔断与限流的区别？** 限流保护"自己"（控制入口流量），熔断保护"下游"（停止对故障下游的调用）；限流是预防性（流量超限拦截），熔断是反应性（故障触发开启）。

**Q：重试的设计要点？** 只对"幂等操作"重试（写操作必须先幂等化）；指数退避 + 抖动（避免重试风暴）；上限次数与超时（防止无限重试）；熔断开启时停止重试。

> 🎯 **核心要点**：健壮性三道防线一句话——防御式"不信输入"、Fail-Fast"错要早爆"、容错"局部坏整体好"。记忆话术：防输入、快失败、可降级、有熔断、能重试、可隔离。面试答法：先分个体正确（防御+快速失败）与群体韧性（容错五件套），再讲组合顺序（重试→熔断→降级→兜底）。
