# 07-配置与演进：配置驱动、分层、约定大于配置、向后兼容

> 定位：四条"系统怎么变化"的思想——配置驱动管"规则怎么改"、分层管"代码怎么组织"、约定大于配置管"配置怎么省"、向后兼容管"接口怎么升"。共同主题：让系统演化更便宜。

## 数据驱动 / 配置驱动

**定义**：把规则、策略放到配置/数据库，而不是硬编码 if-else——改动规则不用改代码发版本。**核心价值**：**运行时可变更**——营销活动规则（满减门槛、折扣力度）进配置中心（Nacos/Apollo），运营改配置秒级生效，不用走发版流程。

**工程体现**：**规则配置化**（折扣、限流阈值、功能开关）；**策略表驱动**（数据库存策略组合，代码解释执行——替代 if-else 链）；**功能开关**（Feature Flag：灰度发布、降级开关——容错设计的配置化实现）；**配置分级**（本地配置 < 环境配置 < 配置中心 < 数据库——按变更频率与生效时延分级）。**边界与陷阱**：配置化不是万能——**配置过多 = 隐性编程语言**（业务逻辑全部搬进配置，配置本身变成不可测试的代码）；判断标准：**配置管"参数值"，代码管"逻辑流"**——折扣力度是参数（可配置），折扣规则（满减还是阶梯）是逻辑（应写代码+测试）。2026 年 AI 辅助开发时代配置驱动的形态：LLM 生成代码 + 配置中心管理运行时参数，逻辑与参数分离的重要性进一步上升。

## 分层思想

**定义**：职责纵向切分——Controller → Service → Manager → DAO，每层只和上下层交互，跨层禁止直接调用。**核心价值**：**依赖单向**（上层依赖下层接口，下层不反向依赖）——层与层独立演化、可替换（换存储不动业务层）。

**工程体现**：经典四层（接口层/应用层/领域层/基础设施层——DDD 的分层）；依赖注入（Spring 的 @Service/@Repository 分层装配）；跨层禁止（Controller 不直接调 DAO、Service 不操作 HttpServletRequest）；层间 DTO 转换（相邻层用 DTO 传递，避免层间对象耦合）。**分层的代价**：层间转换代码（DTO map）与跳层调试成本——**分层不是越厚越好**（纯 CRUD 套五层是过度设计，见 03 篇 KISS）；判断标准：层是否真的在"独立演化"——十年不改的层可以合并。**与 SoC 的关系**：SoC 是"按问题切分"的总原则，分层是它的"纵向"制度化（按职责深度切）；与 02 篇正交是"维度"制度化（按变化维度切）——三者在不同轴。

## 约定大于配置

**定义**：统一默认约定，减少大量配置项——Spring Boot 大量自动配置就是这个思想（约定类名/目录/注解扫描，省掉 XML 配置）。**核心价值**：**新手友好**（约定即文档：项目结构一看就懂）；**配置面收缩**（只写"偏离约定"的配置）；**一致性**（同项目同结构，降低切换成本）。

**工程体现**：Spring Boot 自动配置（starter 按约定装配）；项目结构约定（controller/service/repository 目录规范）；命名约定（实体表名映射、DTO 命名）；框架默认值（端口、日志格式）。**边界**：约定是"团队的共同默认"——**团队内部约定必须文档化**（ADR/规范文档），否则约定变成"隐式魔法"（新人不知道自动配置做了什么，排查困难）；偏离约定的配置必须显式写注释说明理由。**与配置驱动的关系**：配置驱动管"规则数据"、约定大于配置管"默认行为"——约定是"无需配置的默认值"，配置是"偏离默认的显式声明"，两者互补。

## 向后兼容

**定义**：接口升级尽量兼容旧版本，不强制上游立刻改造——字段新增不删除、旧字段保留、版本控制。**核心价值**：**上游零成本迁移窗口**——客户端可以按自己的节奏升级，系统演化不依赖"一次性全量改造"。

**工程体现**：**新增不删减**（只加字段不加删除、旧字段保留语义不变）；**兼容性规则**（字段新增向后兼容、字段删除/语义变更走新版本——Spring 7 的语义版本解析）；**版本化策略**（请求头/路径段版本化，见 MVC 体系 06 篇）；**弃用周期**（deprecation 标注 + sunset 日期 + 迁移文档——给客户端明确升级窗口）；**契约测试**（Pact 锁定响应 schema，防"悄悄破坏契约"——向后兼容的自动化保障）；**兼容性测试矩阵**（旧版本客户端的代表性请求在升级后全量通过——回归的兼容性维度）。**边界的辩证**：向后兼容不是无条件——**兼容的代价是包袱**（旧字段永存、老行为永留），需要版本治理（Spring 7 @ApiVersion 的"固定版本 + 基线版本"机制：契约不变不新增 handler，契约真变才开新版本）；版本化的收益与成本核算：**版本数即 API 稳定性指标**——能靠兼容性策略（字段新增向后兼容）解决的问题不开新版本，每开一个新版本都要评估"能否兼容替代"，版本膨胀本身是设计信号；**破坏性变更的纪律**：必须破坏时（安全修复、语义纠错），提前公告 + 双版本并行 + 迁移工具。

## 工程落地清单（四条思想各三问）

**配置驱动三问**：规则与参数是否分离（参数进配置、逻辑留代码）？配置中心是否支持分级与审计（本地/环境/生产隔离，变更留痕）？功能开关是否覆盖降级与灰度场景？**分层三问**：依赖是否单向（上层依赖下层接口）？跨层调用是否被拦截（评审与 ArchUnit）？层是否真的在独立演化（十年不动的层考虑合并）？**约定大于配置三问**：团队约定是否文档化（ADR/规范）？偏离约定是否显式注释理由？新成员能否按约定上手（约定即入门文档）？**向后兼容三问**：变更是否遵守"新增不删减"？版本化策略是否全站一致？弃用周期与迁移文档是否发布？四组三问作为评审模板直接贴在代码评审模板里，每次变更过一遍。

## 四条思想的组合与面试

**组合关系**：配置驱动让"规则"可运行时变更（不改代码）、分层让"变更"局部化（改一层不动全局）、约定大于配置让"新代码"默认正确（少配置少出错）、向后兼容让"接口变更"不破坏生态——四条思想共同回答"如何让系统持续演化而不碎裂"。**面试高频**：**"改一个规则要发版吗？"**——答配置驱动（规则参数化 + 配置中心 + 功能开关）；**"接口升级怎么不破坏老客户端？"**——答向后兼容三件套（新增不删减、版本化、弃用周期 + 契约测试）；**"分层与性能的冲突？"**——答"分层管代码组织、性能优化走缓存与查询优化（08 篇），用分层换可维护性、用缓存换性能，二者不冲突"。**"约定太多变成魔法？"**——答"约定必须文档化 + 偏离必须显式"，约定是团队资产不是黑盒。

> 🎯 **核心要点**：四条演进思想一句话——配置驱动"规则可热改"、分层"改动局部化"、约定大于配置"默认就正确"、向后兼容"升级不伤客"。记忆话术：规则进配置、依赖不跨层、默认成约定、接口不破坏。面试答法：每条"定义 + 工程体现 + 边界（配置别变逻辑、分层别过度、约定要文档化、兼容有成本）"。
