# 05-幂等设计（专项深潜）

> 定位：面试与生产双重最高频的思想——"同一个请求多次执行，结果与执行一次完全一样"。覆盖四大场景、三种实现方案、2026 年的边界陷阱与生产级框架设计。

## 幂等的本质与四大场景

**本质**：幂等 = 重复执行不产生额外副作用。注意区分"天然幂等"与"设计幂等"：GET 天然幂等（读不改变状态）、PUT 语义上幂等（全量替换）、DELETE 幂等（删不存在的返回成功即可）；POST 天然不幂等（每次创建一条）——需要设计。**四大触发场景**：**用户重复提交**（网络抖动双发、双击按钮）；**MQ 重复消费**（消费成功后 ack 丢失，重投递）；**接口重试**（Feign/客户端超时重试）；**分布式事务回滚重试**（Saga 补偿执行多次）。

## 方案一：Token 模式

**流程**：前端先调"获取 Token"接口拿到一次性令牌 → 提交业务请求时携带 → 服务端校验 Token 存在且未被使用 → 处理后删除 Token。**特点**：Token 用后即焚（"用后即焚"是 2026 阿里云实践的推荐措辞）——天然防"同一笔操作提交两次"；适合**用户主动发起的操作**（下单、支付）。**实现**：Redis SETNX + TTL；Token 与业务参数绑定（Token 只对一次提交有效，参数变化视为新提交）。**局限**：需要额外的取 Token 请求；适用于"防重"而非"重试恢复"（重试场景中 Token 已焚，无法重放）。

## 方案二：业务 Key 模式（幂等表）

**流程**：用业务自然键作为幂等标识（`order:create:{userId}:{productId}:{timestamp}`）→ 首次执行插入幂等记录（状态=处理中）→ 后续请求命中记录直接返回首次结果。**特点**：适合 **MQ 消费与系统重试**（消费端没有前端配合取 Token）；**零侵入性扩展**——MongoDB 用唯一索引（unique + upsert）、MySQL 用唯一键 + INSERT IGNORE/ON DUPLICATE KEY、Redis 用 SETNX。

**关键工程点（2026 实践）**：**幂等记录三态化**——0=处理中、1=成功、2=失败。单纯 SETNX 无法解决状态流转：处理中崩溃后记录永远卡在"处理中"，需要状态机化（超时重置）；**Lua 脚本保证原子性**——"判断 Key 是否存在 + 记录状态"必须原子执行，否则并发双请求都通过判断（竞态）。**返回首次结果**：重复请求返回第一次的执行结果（缓存结果或状态查询），而非直接成功——保证客户端拿到的结果一致。

## 方案三：版本号 / 乐观锁模式

**适用**：**更新类操作**（扣减库存、改订单状态），Token 与业务 Key 管"提交去重"，版本号管"并发更新不覆盖"。**实现**：数据表带 version 字段；更新语句 `UPDATE t SET amount=amount-?, version=version+1 WHERE id=? AND version=?`；版本不匹配返回冲突，客户端重试或报错。**与 CAS 的关系**：数据库的 version 校验就是 CAS（Compare-And-Swap）思想的关系型实现；Redis 的 WATCH/MULTI 或 Lua 中的比较-更新也是 CAS。

## 2026 边界陷阱：状态机回滚 vs 幂等

华为云 2026 的经典教训：传统"请求 ID 去重"在**状态机回滚场景**下失效——订单从"支付中"回滚到"待支付"后，幂等缓存未清理，新请求带新 ID 触发资金二次划扣；而旧重试请求因缓存已清可能再次执行。**核心洞见**：**幂等性设计必须把"业务状态"和"操作状态"看作一个原子对**，而非孤立记录"请求是否被处理"。**解决方案：操作版本号机制**——为订单维护递增 version，幂等记录以 `(order_id, expected_version)` 为组合约束，请求必须携带 expected_version，仅当当前 version 等于期望值才处理；回滚后 version 不回到旧值，旧重试请求携带过期版本号被直接拒绝（实测将并发状态冲突率从千分级降至十万分级）。

## 生产级框架设计（Redis + Lua）

2026 阿里云生产级幂等框架的完整形态：**注解驱动**——@Idempotent(keyPrefix=..., keySpEL=..., expire=...) AOP 切面；**Lua 原子脚本**——`SET key value NX EX ttl` 原子完成"判断+记录+过期"；**三态记录**——处理中/成功/失败，配合超时重置与结果缓存；**组合约束**——`(order_id, expected_version)` 或 `(biz_key, status)` 条件更新。**选择矩阵**：用户主动操作 → Token 模式；MQ 消费/重试 → 业务 Key + 唯一索引；并发更新 → 版本号乐观锁；回滚场景 → 操作版本号组合约束。

## 幂等键设计的最佳实践

幂等键是方案落地的最小单元，设计规范直接决定正确性：**幂等键必须可复现**——同一业务操作在任何重试中都生成相同的键（键里带时间戳/随机数 = 每次不同 = 幂等失效）；**键的构成 = 业务域 + 业务标识**——`order:pay:{orderId}` 优于裸 `{orderId}`（不同域不互相污染）；**键的语义要唯一对应"一次操作"**——一次支付操作（而非一个订单）对应一个键：同一订单的"发起支付"与"支付回调"是两个操作，键要区分；**键的存储与过期**——Redis 键设 TTL（超过业务处理窗口的旧键自动清理）、键值存操作结果（重复请求直接返回）；**键的版本化**——操作版本号机制（05 篇边界陷阱）下，键演进为 `(order_id, expected_version)` 组合——键的设计随一致性模型演进，不是一次定死。**反面案例**：用"订单号"做支付幂等键——同一订单两笔不同支付被去重；用"时间戳"做键——重试生成新键绕过去重。面试加分：能讲出"幂等键 = 操作级唯一标识 + 可复现 + 带域前缀 + 版本化演进"四要素，即展示真实落地经验。

## 幂等与分布式事务的协同

幂等是分布式事务（Saga/TCC/事务消息）的底层支撑，两者的协同关系是面试加分点：**Saga 补偿的幂等性**——每个补偿步骤必须幂等（重复补偿不改变最终状态），否则补偿重试会二次破坏数据；手段：唯一业务 ID + 状态机校验（`status IN ('pending','failed')` 条件更新）+ 幂等记录。**TCC 的幂等**——Try/Confirm/Cancel 三阶段各自幂等：Confirm 重复执行返回成功（不重复扣款）、Cancel 重复执行幂等（不重复回补）；幂等键通常是 `(事务ID + 阶段)`。**事务消息的幂等**——本地消息表 + 消息投递重试，消费端必须幂等（MQ 至少一次语义，重复消费靠消费端去重）。**最终一致性**：分布式事务无法保证强一致，只能保证"最终一致"——最终一致的前提就是每个环节幂等 + 可重放：**幂等是把"不可控的重试"变成"可安全重复的操作"的唯一手段**。面试答法：先讲幂等四场景，再讲"幂等 × 分布式事务"的协同（Saga/TCC/事务消息各自怎么用幂等兜底）——这个组合答法是分布式面试的满分答案。

## 幂等设计的验收清单

1. **四场景覆盖**：重复提交、MQ 重放、接口重试、回滚重试各有一案；
2. **原子性验证**：去重判断与状态记录必须原子（Lua/唯一索引）；
3. **结果一致性**：重复请求返回与首次一致的结果（缓存或查询）；
4. **过期与重置**：幂等记录有 TTL；"处理中"状态超时可重置（防永久卡死）；
5. **回滚联动**：状态回滚时幂等记录的处理策略明确（操作版本号方案）；
6. **并发验证**：双请求并发测试通过（压测脚本覆盖）；
7. **幂等键设计**：业务键可复现（同一操作多次生成相同键）——键里带随机数就是设计错误。

> 🎯 **核心要点**：幂等三方案一句话——Token 防"用户重复提交"、业务 Key 防"系统重复执行"、版本号防"并发覆盖更新"；2026 的升级——幂等必须与业务状态绑定（操作版本号组合约束），否则状态机回滚会击穿"一次且仅一次"的假设。面试答法：先讲本质（重复执行无副作用）→ 四大场景 → 三方案选型 → 边界陷阱（回滚 vs 幂等）。
