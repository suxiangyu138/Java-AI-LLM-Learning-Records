# 02-类与模块设计：迪米特、高内聚低耦合、正交

> 定位：SOLID 管"类内部怎么设计"，本篇三条思想管"类与类、模块与模块之间怎么相处"——迪米特管调用距离、高内聚低耦合管组织原则、正交设计管维度独立。

## 迪米特法则（最少知道原则）

**定义**：一个对象对其他对象知道得越少越好——只和"直接朋友"交互，不打听朋友的朋友。**核心信号：禁止链式调用** `a.getB().getC().doSomething()`——a 知道 b、b 知道 c、a 间接依赖了 c 的内部结构，任何一层的结构变化都会传导。**工程体现**：把逻辑封装在对象内部（b 提供 doSomething 的语义接口，a 只调 b 的方法）；分层架构中"只和相邻层交互"就是迪米特的制度化（Controller 不直接调 DAO）。

**反例与危害**：链式调用让"变更爆炸半径"扩大——c 改结构，a、b、测试全部跟着改；且链式调用无法 mock（测试 a 需要真实构建 b 和 c 的对象树）。**面试话术**：迪米特的核心不是"少写代码"，而是"缩小依赖面"——一个类的依赖数量（耦合数）直接决定它的测试成本与变更成本。例外说明：构建者模式（Builder）与流式 API 的链式是"同一对象的连续方法调用"，不违反迪米特（朋友始终是同一个）。

## 高内聚、低耦合

**定义**：**高内聚**——相关强的逻辑放在一起，模块内部功能紧密（一个模块服务于一个明确目的）；**低耦合**——模块之间依赖少，改动一个模块尽量不影响其他模块。这几乎是所有工程设计的总目标，SOLID、迪米特、正交都是它的具体化手段。

**工程体现**（2026 实践路径）：**充血模型承载核心业务**——把强状态性、多规则校验、频繁状态流转的逻辑封装进领域对象内部（`wallet.deposit(amount)` 内部自动完成幂等校验、余额非负检查、流水事件生成），逻辑不散落 Service 层——对象内聚、服务瘦身；**防腐层与事件解耦**——跨模块直接调用（订单直接调客户服务的 CreditService）引发紧耦合，用防腐层或领域事件替代实时调用；**接口契约**——模块间通过稳定接口交互，内部实现自由演化。

**度量与验证**：耦合可用依赖图 + 变更耦合统计（两个模块频繁同次变更 = 耦合过高）验证；内聚可用 LCOM 度量。**反例**：一个"工具类"什么都放（Util 类收集所有无归属方法）是低内聚的典型；模块 A 改动导致模块 B、C、D 连锁修复是高耦合的典型。

## 正交设计

**定义**：两个维度互相独立——修改 A 不影响 B，组合 A 与 B 可以产生新能力。**数学类比**：笛卡尔坐标系中 x 与 y 正交，改 x 不扰动 y。**典型例子**：业务逻辑与日志打印正交（日志是横切面，不侵入业务代码——AOP 的存在意义）；业务与监控埋点正交；数据存储与业务计算正交（换数据库不影响业务逻辑）。

**工程收益**：**独立迭代**——每个维度可以单独演进（日志系统升级不动业务代码）；**组合能力**——正交维度自由组合出多种形态（同业务逻辑 × 不同存储 = 多存储支持；同业务 × 不同渠道 = 多渠道接入）。**与关注点分离（SoC）的关系**：SoC 是"按问题分模块"（纵向切割），正交是"按变化维度分模块"（维度独立）——SoC 是正交的粗粒度形态，AOP（切面编程）是正交思想在横切面的制度化。

**反例**：业务代码里到处是 System.out.println（日志与业务耦合，日志升级要改全部业务代码）；支付金额计算与汇率换算写死在同一个方法（改汇率逻辑必须动支付代码）。**面试话术**：正交设计判断问题——"改动需求 A 时，改动面是否只覆盖 A 的模块？"是则正交，波及 B/C 则非正交。注意正交不是绝对：完全正交的维度在业务上常有隐式依赖（日志要能关联业务上下文——traceId 传递是"必要的最小耦合"），设计目标是"让非必要耦合归零"。

## 实战案例：订单模块的模块化重构

一个具体的重构案例演示三条思想的运用：初版订单模块中，OrderService 直接持有 OrderMapper（MyBatis）、CouponClient（远程优惠券）、SmsClient（短信），并在下单方法里链式调用 `order.getItems().get(0).getProduct().getStock()` 查询库存——问题清单：**迪米特违规**（链式穿越 Order→Items→Product→Stock 四层结构，任何一层字段变更都传导）；**高耦合**（Service 直连三个外部依赖的具体实现，mock 测试要构建三套桩）；**低内聚**（下单、优惠、通知三类逻辑挤在一个方法）。重构步骤：**第一步（迪米特）**——把"查询商品库存"封装为 OrderItem 的方法（`item.availableStock()`），链式消失，对象自己回答自己的问题；**第二步（耦合）**——CouponClient/SmsClient 抽象为接口 + Spring 注入（依赖倒置），测试替换为 mock 实现；**第三步（内聚）**——下单流程拆为 OrderPlacementService（业务）、CouponService（优惠）、NotificationService（通知），OrderService 只做编排。重构后：每个类的依赖数从 3+ 降到 1-2、变更影响面从"改一处试三处"降到"改一处测一处"、测试从"构建三套桩"降到"注入一个 mock"。这个案例的通用流程（查链式 → 抽接口 → 拆职责）可以直接套用到任何模块。

## 与 SOLID 的分工与衔接

三条思想与 SOLID 的关系是"模块级 vs 类级"的分工：SOLID 管"类内部怎么设计"（职责、接口、依赖方向），本篇管"类之间怎么组织"（调用距离、模块边界、维度独立）。衔接点：**DIP 与低耦合**——DIP 给"低耦合"提供了具体手段（依赖抽象），低耦合是 DIP 的目标；**SRP 与高内聚**——SRP 是"类级内聚"，高内聚是"模块级内聚"，同一思想的两个粒度；**迪米特与 ISP**——迪米特限制"对象知道谁"，ISP 限制"接口暴露什么"，都是"信息暴露面最小化"。面试被问"SOLID 之外还有哪些设计思想"时，用这层衔接回答：SOLID 管类、迪米特管调用、内聚耦合管模块、正交管维度——四层构成"从类到系统"的完整思想栈，比零散背名词更有体系感。

## 三条思想的关系与使用序列

设计一个模块时的使用序列：**先问内聚**（这些逻辑是否服务于同一目的？不是 → 拆）→ **再问耦合**（它与谁交互？能否只依赖接口？→ 加接口）→ **最后问正交**（它包含几个变化维度？维度能否分离？→ 拆维度）。三条思想共同服务于"模块的可独立演化性"：内聚保证模块内自洽、耦合保证模块间独立、正交保证维度间独立——三者的验收标准一致：**改一处，只影响该处**。2026 年的 DDD 实践把这条序列升级为边界纪律（限界上下文 = 内聚的边界、防腐层 = 耦合的控制点、领域事件 = 正交的通信机制），设计思想与架构方法在这里合流。

> 🎯 **核心要点**：三条思想一条主线——"把变化隔离到最小范围"：迪米特隔离调用链、高内聚低耦合隔离模块、正交隔离维度。记忆话术：迪米特"只交直接朋友"、内聚耦合"相关内聚无关解耦"、正交"改 A 不动 B"。面试答法：定义 + 反例 + 度量（依赖数/变更耦合/LCOM）+ 与 SoC/DDD 的关系。
