## 1. 韧性工程的范式转变

2026 韧性工程的核心理念转变：

**旧范式：追求"绝对稳定"**

- 目标：五个九（99.999%），系统尽量不挂
- 思路：防故障（冗余/监控/人工值守）
- 现实：故障必然发生（硬件/代码/依赖/人为），防不胜防

**新范式：韧性（Resilience）**

- 目标：挂了快速恢复 + 降级时业务可接受
- 思路：假设故障会发生，设计故障后的行为
- 关键：MTTR（恢复时间）比 MTTF（故障间隔）更重要

韧性的三个层次：

- **预防**：减少故障发生（代码质量/容量/监控）
- **吸收**：故障发生时系统内部消化（熔断/降级/重试）
- **恢复**：故障后快速恢复（自动化/预案/演练）

**韧性设计的出发点**：**问"挂了怎么办"而不是"怎么不挂"**——每个关键路径回答：环节挂了系统表现如何？降级到什么程度？多久恢复？这个追问会暴露绝大多数高可用设计的空白。

## 2. 高可用的量化框架：SLA/RTO/RPO

高可用设计从量化开始（02 篇 NFR 的落地）：

三个核心指标：

- **SLA**：可用性百分比（99.9% = 年停机 ≤ 8.76 小时；99.99% ≤ 52.6 分钟）
- **RTO（恢复时间目标）**：故障到恢复的时长（RTO ≤ 5 分钟是常见基线）
- **RPO（恢复点目标）**：可容忍的数据丢失（RPO = 0 不丢数据；RPO 5 分钟 = 丢 5 分钟数据）

指标的组合设计：

- RTO 决定恢复手段（分钟级恢复 → 双活/自动切换；小时级 → 备份恢复）
- RPO 决定复制模式（RPO=0 → 同步复制；RPO 分钟级 → 异步复制）
- 指标按业务分级（交易核心 RTO 5 分钟；报表系统 RTO 2 小时）
- 指标要有验证（故障演练实测 RTO，不是纸面承诺）

指标的工程落地：

- 每个关键系统有 SLA/RTO/RPO 表（设计文档必含）
- 监控覆盖指标（可用性/恢复时长可度量）
- 演练验证指标（混沌工程实测）

**指标的代价意识**：RTO 从小时级到分钟级的成本差一个数量级（备份 → 双活）；RPO=0 的同步复制有性能代价——**指标是业务决策**（02 篇 SLA 设计），架构师提供成本选项。

## 3. 故障模式与防御

高可用设计先列故障模式（FMEA 思路）：

故障模式清单（按来源）：

- **依赖故障**：下游服务/数据库/第三方（最常见——防御：超时/熔断/降级）
- **流量故障**：突发流量/热点（防御：限流/削峰/缓存）
- **资源故障**：CPU/内存/磁盘/连接池（防御：监控/配额/自动扩容）
- **数据故障**：数据损坏/误删（防御：备份/审计/权限）
- **代码故障**：bug/内存泄漏（防御：质量体系/灰度/回滚）
- **环境故障**：机房/云厂商/网络（防御：多可用区/容灾）
- **人为故障**：误操作/配置错误（防御：变更流程/权限/审计）

防御的层次：

- 预防：质量/监控/流程（减少发生）
- 检测：告警/指标（快速发现）
- 响应：预案/自动化（快速处理）
- 恢复：备份/切换（快速恢复）

**故障模式表的使用**：架构评审时过一遍故障清单（每个关键路径问"哪种故障最可能、最致命"）——评审四问的"最大风险"在这里有系统化清单支撑。

## 4. 韧性三件套：熔断/隔离/降级

韧性设计的核心机制三件套（L2/L3 提及，L4 讲全局策略）：

- **熔断（Circuit Breaker）**：失败率超阈值 → 熔断（快速失败）；状态：关闭 → 打开 → 半开（试探恢复）。全局策略：哪些链路要熔断、阈值、恢复策略。反模式：全链路无熔断 → 级联故障（A→B→C 全挂）
- **隔离（Bulkhead）**：资源按依赖分舱（线程池/信号量隔离）。关键依赖独立线程池（不共享耗尽）。场景：慢依赖不拖垮快依赖（慢 SQL 不占完连接池）
- **降级（Degradation）**：故障时提供降级方案（缓存兜底/默认值/部分功能）。全局策略：每个关键功能的降级方案（挂了给什么）；降级开关：配置中心（人工/自动触发）

三件套配合：**熔断保下游、隔离保自己、降级保业务**。

**韧性的全局视角**：L2/L3 的熔断是"一个接口"，L4 是**全链路策略体系**——哪些链路保护、优先级、降级矩阵（功能 × 故障 → 降级方案）。

## 5. 容灾架构：同城双活/异地多活

容灾是故障模式的极端场景（机房/区域级故障）：

容灾级别：

- **备份恢复**：定期备份，故障后恢复（RTO 小时级，成本最低）
- **同城双活**：同城两机房同时服务（RTO 分钟级，成本中）
- **异地多活**：异地多机房（RTO 秒级/分钟级，成本高，复杂度高）
- 级别选择：业务价值 × 成本（02 篇的 SLA 决策）

同城双活的要点：

- 两机房同时承担流量（不是主备，是双活）
- 数据同步：同城专线同步复制（RPO ≈ 0）
- 自动切换：故障检测 + 流量切换（分钟级）
- 验证：切换演练常态化（不演练的容灾是摆设）

异地多活的难点：

- 数据一致性：异地同步延迟不可避免 → 分片设计（按地域分数据）
- 流量调度：按地域路由（用户就近）
- 复杂度代价：多活架构的运维与调试成本显著

**容灾的工程纪律**：**容灾能力 = 演练频率**——不演练的容灾方案（文档写的双活）在真实故障时大概率失效；演练从"季度桌面演练"到"季度真实切换"。容灾设计的起点是 RTO/RPO 指标（第 2 节），终点是演练验证。

## 6. 混沌工程：故障的常态化演练

混沌工程（Chaos Engineering）是韧性验证的 2026 标配：

混沌工程的原则：

- 在生产/准生产环境注入故障（小范围可控）
- 验证假设：系统在故障下的行为是否符合设计
- 自动化：故障注入脚本化（不是手动搞破坏）
- 最小爆炸半径：先小范围（1 个实例 → 1 个服务 → 1 个链路）

常见故障注入：

- 实例级：杀进程/断网络（验证重启恢复）
- 依赖级：下游延迟/错误注入（验证熔断/降级）
- 资源级：CPU/内存/磁盘压力（验证资源防御）
- 数据级：主库故障/复制延迟（验证切换）
- 区域级：可用区故障（验证容灾）

混沌工程的收益：

- 验证韧性设计（不是"应该能扛"，是"实测能扛"）
- 暴露盲区（监控缺失/预案错误/依赖脆弱）
- 培养故障文化（团队不惧故障，善处理故障）

**混沌工程的落地节奏**：从"季度故障演练"开始（人工 + 简单注入），逐步自动化（Chaos Mesh/Litmus 等工具）——**演练的频率与业务价值成正比**（交易系统月演练、报表系统季度演练）。

## 7. 故障复盘与改进闭环

故障处理与复盘是韧性的最后一环：

故障处理流程：

- 发现（监控告警）→ 止血（降级/切换/扩容）
- 定位（链路追踪/日志）→ 修复（回滚/补丁）
- 恢复（验证/解除降级）→ 复盘（事后分析）

复盘的纪律（避免甩锅式复盘）：

- 还原时间线（什么时间发生了什么，谁做了什么）
- 找根因（5 Why 追问，找到系统层面原因）
- 找系统改进（不是找个人责任——"防再犯"而非"责人"）
- 改进项闭环（改进清单 + 负责人 + 验证——不复盘的故障白发生）

改进闭环的输出：

- 监控补盲（故障时没告警的指标补上）
- 预案补齐（没有预案的故障场景补预案）
- 架构改进（暴露的设计缺陷进架构改进计划）
- 演练计划（新增场景进混沌工程清单）

**复盘的产出不是报告是改进**：一份漂亮的复盘报告没有改进闭环 = 白复盘。**故障是架构改进的最大信息来源**——每次故障都是系统的"体检报告"，善用故障的组织架构越挫越强。

## 8. 练习

1. 为你的核心系统写 SLA/RTO/RPO 表（含分级）
2. 列一份故障模式清单（按来源，标出最可能的三个）
3. 为你的三条关键链路设计熔断/隔离/降级策略
4. 评估你系统的容灾级别与演练频率
5. 设计一次混沌工程演练（注入内容/验证假设/最小半径）
