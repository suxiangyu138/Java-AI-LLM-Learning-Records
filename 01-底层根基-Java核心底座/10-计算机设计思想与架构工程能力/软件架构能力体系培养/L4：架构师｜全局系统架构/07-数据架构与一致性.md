## 1. 数据架构的三个基础决策

数据架构的起点是三个决策：

**决策一：数据所有权**

- 每份数据谁写（唯一写者）
- 谁读（读写分离的消费方）
- 数据属主模块（L3 05 篇的延伸——全局视角）

**决策二：存储选型**

- 数据特征 → 存储类型（关系/文档/缓存/搜索/向量）
- 每类数据用最合适的存储（不是一种数据库打天下）
- 选型依据：读模式/写模式/一致性/规模（03 篇方法论）

**决策三：一致性策略**

- 数据间的依赖关系（哪些数据要一致）
- 一致性级别（强/最终——04 篇 CAP）
- 不一致时的处理（补偿/对账/修复）

**三个决策的顺序**：所有权 → 存储 → 一致性（先定谁负责，再定放哪，后定怎么同步）——顺序颠倒会导致"多模块写同一份数据"的混乱。

## 2. 数据所有权：谁写谁读

数据所有权是数据架构的第一原则（L3 05 篇的全局版）：

所有权规则：

- 每份数据有一个"属主"（唯一写者）
- 其他模块读：通过属主的 API/事件（不直接写）
- 跨模块共享：属主提供读接口/发布事件（L2 06 篇）
- 禁止：多模块直接写同一张表（数据边界 = 模块边界）

所有权违法的信号：

- 多模块写同一张表（改表结构互相影响）
- 跨模块直接查对方库（绕过 API，耦合数据模型）
- 数据逻辑分散（同一字段的规则散在多个服务）
- 删除/迁移数据要协调多个团队（属主不明）

所有权的好处：

- 变更可控（改表结构只影响属主与显式消费者）
- 数据质量责任明确（数据坏了找属主）
- 演进自由（属主可以重构内部存储，API 不变）
- 治理简单（权限/审计/合规按属主落实）

数据所有权与共享核心：

- 纯共享数据（字典/配置）→ 独立属主服务或共享只读
- 业务数据 → 严格属主
- 判断：谁能回答"这份数据的规则是什么"——他就是属主

**数据所有权的全局视角**：L4 数据架构文档必含**数据所有权矩阵**（数据 × 属主 × 消费者 × 获取方式）——数据混乱的根源 80% 是所有权不清。

## 3. 存储选型矩阵

存储选型按数据特征匹配（不是"用什么数据库"是"每类数据用什么"）：

| 数据特征 | 存储 | 典型场景 |
|----------|------|----------|
| 强一致/事务/关系 | 关系型（MySQL/PG） | 订单/账户/主数据 |
| 高吞吐 KV | Redis | 缓存/会话/计数 |
| 文档结构 | MongoDB | 灵活 schema 业务数据 |
| 搜索/聚合 | Elasticsearch | 全文搜索/日志分析 |
| 时序 | TSDB（InfluxDB） | 监控/物联网指标 |
| 向量 | 向量库（Milvus/ES 向量） | RAG/AI 检索（09 篇） |
| 大文件 | 对象存储（MinIO/S3） | 图片/附件/音视频 |

选型判断（按场景）：读模式（点查/搜索/聚合决定形态）、写模式（事务/追加决定一致性成本）、规模（决定是否分片）、一致性（强一致→关系型；最终可接受→分布式存储）、成本（TCO——08 篇）。

选型的常见错误：

- 一种数据库打天下（MySQL 存 JSON/搜索/时序——性能灾难）
- 为"时髦"引入存储（数据量没到就用 ES/向量库）
- 忽略迁移成本（换存储是重构级）

**存储选型的全局视角**：**每类数据一个最合适的存储**（多存储是常态），选型由数据特征与容量/成本数字决定——不是"喜欢哪个"。

## 4. 分布式一致性落地

分布式一致性从 CAP 决策到落地（04 篇的工程化）：

一致性策略的落地路径：

- 能收进单库/单事务的尽量收（模块化单体优势）
- 跨服务强一致 TCC/2PC（极少用）
- 跨服务最终一致 SAGA/可靠事件（主流）
- 读一致性（缓存/副本策略）
- 对账机制（异步链路最终核对——最后防线）

最终一致的工程要点：

- 事件表/事务消息（可靠投递）
- 消费幂等（L2 铁律）
- 补偿/重试（失败路径完备）
- 对账任务（定时核对两端）
- 可观测（一致性延迟监控）

一致性问题的典型场景：下单扣库存（原子操作/乐观锁）、支付回调与订单状态（幂等 + 对账）、缓存与数据库（缓存一致性）、多副本（主从延迟——读己之写）。

**一致性的工程判断**：**能用单库事务解决就不上分布式事务**；必须分布式的，**选最终一致 + 对账兜底**为主流；**对账是分布式一致性的"体检"**——没有对账是盲目信任。

## 5. 数据规模化：分库分表与读写分离

数据规模增长的路径（30% 预留之后的规模化）：

规模化路径（按顺序）：

- **读写分离（主写从读）**：读多写少场景，从库扩读容量，处理主从延迟
- **分库分表（水平拆分）**：单库容量/写入成瓶颈时
  - 分片键按查询模式设计（大部分查询路由到单分片）
  - 分片策略：范围/哈希；全局唯一 ID（雪花/UUID）
  - 代价：跨分片查询/事务复杂化（能避免则避免）
- **分布式数据库/NewSQL（TiDB/OceanBase 等）**：分库分表复杂度不可承受时——权衡：成熟度 vs 运维成本

**规模化的判断**：**先看能不能不拆**——缓存（热点）、归档（冷数据）、读写分离（读多）能解决的，不拆库；拆库是容量与写入瓶颈的"最后手段"（为"万一"提前分库分表是过度设计典型）。

## 6. 缓存体系设计

缓存是数据架构的性能层（04 篇多级分流的服务端部分）：

缓存的三层体系：本地缓存（进程内，最快）/分布式缓存（Redis，共享）/数据层缓存（最稳）。

缓存设计要点：

- 缓存什么：热点/读多写少/计算昂贵的数据（不是所有数据）
- 缓存多久：TTL 策略（业务容忍度决定）
- 缓存一致性：写后失效/双删/版本号（一致性 vs 性能）
- 三防：穿透（布隆过滤器/空值缓存）、击穿（互斥重建）、雪崩（过期打散）
- 监控：命中率/延迟/容量（命中率下降 = 告警信号）

缓存与一致性权衡：强一致不走缓存或写后失效（性能代价）；最终一致 TTL 容忍——判断业务能容忍多少毫秒的旧数据。

**缓存设计顺序**：先定"哪些数据该缓存"（命中率收益）→ 再定一致性策略（容忍度）→ 最后防三类问题——**收益算不清的缓存是负债**。

## 7. 数据合规与治理

数据合规是数据架构的硬约束（02 篇合规清单的数据部分）：

数据合规要点：

- 分类分级（个人信息/敏感/一般）+ 最小化收集
- 留存期限（到期删除/归档）+ 出境评估（数据本地化）
- 加密（传输 TLS + 存储静态加密）+ 脱敏（测试/展示）
- 审计留痕（谁读了什么）

数据治理：

- 数据字典（定义/属主/口径）+ 质量监控（坏数据是架构问题）
- 数据血缘（流转追踪）+ 主数据管理（单一事实来源）

**合规的架构影响**：加密影响存储选型与性能、留痕影响日志架构、分类分级影响存储隔离——**合规前置**（02 篇），后补合规是重构级。

## 8. 数据架构评审要点

数据架构评审清单：所有权矩阵（数据 × 属主 × 消费者 × 获取方式）/存储选型依据/一致性策略（CAP 依据 + 对账机制）/容量与增长/缓存体系/合规清单/演进路径。

常见发现：多模块写同一张表（所有权违反）、一种存储打天下、无对账（最终一致裸奔）、分库分表过早（过度设计）、合规缺失。

**数据架构评审的价值**：数据问题是"慢性病"——当前不炸，规模大/迁移时集中爆发。**评审抓住数据架构，就抓住了长期稳定地基**。

## 9. 练习

1. 画你系统的数据所有权矩阵（找出无属主/多属主的数据）
2. 用存储选型矩阵评估你系统每类数据的存储匹配度
3. 设计一条跨服务链路的最终一致方案（含对账）
4. 评估你系统是否到了分库分表阶段（先检查缓存/归档/读写分离）
5. 用评审清单过一遍你系统的数据架构

---

> 🎯 **核心要点**：数据架构三决策（所有权→存储→一致性）。所有权：每份数据唯一属主，跨模块走 API/事件，所有权矩阵是评审第一看。存储选型：数据特征决定（关系/文档/缓存/搜索/向量各司其职）。一致性：能单库解决不分布，分布式主流是最终一致 + 对账兜底。规模化：缓存/归档/读写分离先于分库分表（最后手段）。合规前置：加密/留存/出境是硬约束。
