# 07-架构评审与ATAM
> 定位：评审是架构质量的「关卡」——ATAM 是结构化评审方法（质量属性场景驱动），评审文化是「赋能而非挑刺」；评审要有产出（问题清单 + 责任 + 期限），走过场的评审是仪式不是流程。

## 1. 评审的目标与形态

**架构评审的目标不是「挑错」而是「降低风险」**——在架构决策固化前发现「没考虑到的质量属性、被忽略的权衡、潜在的反模式」——**评审的时机越早越便宜**（设计期发现问题改文档，上线后发现问题改系统——成本差一个数量级）。

评审的三种形态：**设计评审（Design Review）**——新系统/新架构方案上线前的评审（最常用——方案评审会）；**持续评审（Continuous Review）**——演进中的定期架构检查（季度架构巡检——NFR 是否仍达标、文档是否过期——[[../L4：架构师｜全局系统架构|L4 体系]] 的持续视角）；**事故后评审（Post-Incident Review）**——故障后的架构复盘（「这个事故暴露了哪个架构缺陷」——反模式识别的实战场景）。**评审与代码评审的区别**：代码评审查「实现对不对」，架构评审查「设计对不对」——**「评审的层级与决策的层级匹配」**。

## 2. ATAM 方法

ATAM（Architecture Tradeoff Analysis Method）——卡内基梅隆 SEI 提出的结构化评审方法——**「质量属性场景驱动的评审」**：

**核心概念：质量属性场景（Quality Attribute Scenario）**——「刺激 → 环境 → 响应 → 响应度量」四要素的测试用例式描述：「当订单查询 QPS 达到 2000（刺激），在正常运行环境（环境），系统应在 200ms 内返回（响应），P95 度量（度量）」——**场景把 NFR（05 篇）变成可评审的测试用例**。

**ATAM 的流程要点**：**收集质量属性场景**（相关方列出关键场景——「系统最重要的非功能需求是什么」）；**分析架构对场景的支持**（架构方案逐场景过——「这个方案能达成这个场景吗」）；**识别权衡点与敏感点**（架构中的关键决策与风险——「缓存解决了性能场景，但引入了一致性风险」——**权衡点是架构的核心资产**（02 篇的显式化）；**输出风险清单**（风险/非风险/权衡点三类——评审产出）。**ATAM 的价值**：**评审从「观点争论」变成「场景对照」**——「我觉得不行」→「场景 X 这个架构达不成」——**「有场景的评审是可验证的评审」**。

## 3. 评审流程

标准评审的五步流程：**第一步，准备**——架构师提交方案（C4 图 04 篇 + ADR 03 篇 + NFR 清单 05 篇——**评审的输入是文档不是 PPT**）；**第二步，简介**——架构师 15 分钟讲方案（评审人先读文档再听——「会上从头讲」是准备不足）；**第三步，场景收集**——评审人基于 NFR 提出关键场景（ATAM）；**第四步，逐场景对照**——方案过场景（「这个架构能否达成场景 X」）+ 反模式检查（06 篇清单）；**第五步，产出**——问题清单（按严重级）+ 决策记录更新（ADR——评审结论进 ADR 状态）。

**评审的时间纪律**：**评审会是「决策会」不是「讨论会」**——预读文档 + 限时（1-2 小时）+ 结论明确（通过/有条件通过/打回）——「评审开了三小时没有结论」是评审失败的标志。

## 4. 评审检查单

架构评审的检查单（按评审对象裁剪）：**需求对齐**——方案覆盖所有功能与非功能需求？（NFR 清单逐条过）；**权衡显式**——关键权衡是否写明（02/03 篇——ADR 的 Consequences）；**模式合理**——结构/领域/数据模式选型是否符合场景（06 篇）；**反模式**——是否踩了反模式清单（分布式单体/共享库/大爆炸设计）；**质量属性**——性能/可用性/安全/可观测性是否有明确方案与验收（05 篇）；**故障路径**——故障场景是否设计（熔断/重试/降级——韧性模式）；**演进性**——方案能否演进（拆分/扩展路径）；**文档配套**——C4 图与 ADR 是否随方案更新（04 篇活的文档）。

**「检查单是评审的骨架」**——逐项过检查单保证评审覆盖面——「评审漏项」是评审失败的另一半原因（与「走过场」并列）。

## 5. 评审产出与跟进

**「没有产出的评审 = 没有评审」**——评审的产出与跟进纪律：**问题清单**——按严重级分类（必须修复/建议改进/记录在案）+ 责任人与期限（「评审问题无人认领 = 评审白开」）；**评审结论**——通过 / 有条件通过（列出条件）/ 打回重设计；**ADR 更新**——评审通过 → ADR 状态 Accepted；评审发现决策问题 → ADR 状态调整（03 篇生命周期）；**跟进机制**——评审问题进项目跟踪（问题列表/看板——「评审问题的跟踪与代码 bug 同级」）；**复盘**——「上次评审的问题这次还在吗」——**「评审问题的闭环率」是评审体系健康度的指标**。

## 6. 评审文化

**评审文化的核心：「赋能改变而非阻止改变」**（01 篇治理姿态）——评审是「帮方案更好」不是「证明方案不行」——文化的五个表现：**评审是邀请不是审查**（架构师主动请评审——「越早邀请越便宜」）；**对事不对人**（问题指向方案不指向人——「这个设计有风险」不是「你不行」）；**安全氛围**（评审现场允许说「我不确定」——被嘲笑一次就不说了——评审的信息价值就没了）；**评审是学习**（评审是横向能力成长的最大课堂——「看别人评审 = 学别人权衡」）；**评审常态化**（不是「大项目才评审」——模块级设计也评审（L2/L3 视角）——**「评审习惯比评审规格更重要」**。

## 7. 常见坑

**坑一：评审走过场**。会开了、问题没跟——产出 + 跟进。

**坑二：评审无场景**。观点争论——ATAM 场景对照。

**坑三：评审输入是 PPT**。文档没预读——评审的输入是 C4 + ADR + NFR 文档。

**坑四：评审会无结论**。讨论三小时没结论——限时 + 结论明确。

**坑五：问题无责任人**。评审问题无人认领——责任 + 期限 + 跟踪。

**坑六：评审变审判**。挑刺文化——赋能文化。

**坑七：只评大架构**。模块级设计不评——评审习惯常态化。
