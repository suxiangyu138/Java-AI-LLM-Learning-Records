## 1. 架构表达的问题

架构表达是横向能力中最「隐形」却最常出问题的一环：**「一张图讲全部」**——系统级架构图塞满类名与数据库字段，谁也看不清；**「图与代码脱节」**——图是三个月前画的，代码已经改了——图成了「历史文物」；**「没有图」**——「架构在大家的脑子里」——新人入职考古三个月。**C4 模型解决的是「分层」与「工具化」两个问题**——每层图只讲一个粒度的抽象，图的生成尽量自动化（代码即图）——**「表达能力的核心不是画图技巧，是抽象层级的分寸感」**。

## 2. C4 四层模型

C4 = Context（上下文）/ Container（容器）/ Component（组件）/ Code（代码）——四层逐步放大，各讲各的粒度：

**Level 1：Context（系统上下文）**——系统在生态中的位置：用户、外部系统、本系统——**一张图讲「系统与谁交互」**——给非技术人员看（老板、产品、新人）；**Level 2：Container（容器）**——系统的运行单元：Web 应用、微服务、数据库、消息队列——**一张图讲「系统由哪些运行单元组成 + 单元间怎么通信」**——给开发团队看（部署与架构的桥梁）；**Level 3：Component（组件）**——容器内部的模块：Controller/Service/Repository——**一张图讲「一个容器内部的结构」**——给模块开发者看；**Level 4：Code（代码）**——类与代码结构（UML 类图级别）——**实践中基本不画**（代码即真相，IDE 里看）。

**核心纪律**：**每层只画该层的抽象**（L2 不画类名、L3 不画部署细节）；**按需深入**——L3 只对最复杂的容器画（不是每个容器都画到 L3——「全画 = 全没人看」）；**图的数量克制**——「一个系统 5-10 张图」是健康范围（L1 一张 + L2 一张 + L3 若干）——**「图的粒度与数量」就是架构表达的分寸感**。

## 3. 画图工具链

C4 的工具链 2026 年已成熟——核心原则是「**代码即图**」（图从文本/代码生成，可版本化、可 diff）：

**Structurizr**——C4 原生工具（DSL 描述架构 → 生成图）：`structurizr` DSL 文件进仓库，图是生成物——「架构描述即代码」的 C4 实现（配合 ADR 的文档即代码）；**Mermaid**——Markdown 原生图表语法（`flowchart`/`sequenceDiagram`）——GitHub 直接渲染——**最轻量的 C4 表达**（README 里直接画）；**PlantUML**——类似 Mermaid 的老牌文本图工具（C4 插件）；**Excalidraw**——白板风格手绘图（设计讨论阶段，非正式文档）。

**工具选型**：正式架构文档 → Structurizr/Mermaid（可版本化）；讨论草稿 → Excalidraw；**「图必须是文本/代码产物」是 2026 的纪律**——Visio/手画的图无法 diff、无法评审、无法随代码演进——**「图即代码」是「活的文档」的前提**。

## 4. 与其他图的关系

C4 不是取代所有图，而是「架构全景的分层框架」——其他图在 C4 里的位置：

**部署图**——L2 的部署视角（容器落在哪些节点）——K8s 架构图/网络拓扑属于 L2 的部署维度；**时序图**——L3/L4 的行为视图（组件间交互的时序）——「结构看 C4、行为看时序」；**ER 图**——数据模型（独立于 C4 的数据视角——C4 不画数据，ER 补）；**UML 类图**——L4 的形态（实践中 IDE 替代）；**C4 与 [[../../../04-设计模式/01-面向对象设计原则与UML|UML]] 的关系**：C4 管「系统结构的宏观分层」，UML 管「微观的类级表达」——**「宏观用 C4、微观用 UML」是分层协作**——架构文档以 C4 为骨架，需要细节处嵌入对应图。

## 5. 活的文档实践

**「活的文档（Living Documentation）」**——架构文档像代码一样演进：**图即代码**（第 3 节——文本图进仓库、进评审、可 diff）；**文档与代码同仓**（`docs/architecture/` 与代码同 PR——架构变更伴随文档变更——「改架构不改文档 = 改动不完整」）；**C4 与 ADR 配合**（03 篇）——**「图表达现状、ADR 表达决策历史」**——新成员读文档 = 图（现状）+ ADR 序列（为什么变成这样）；**定期校准**——架构评审（07 篇）带「文档与代码一致性检查」——「图过期了」是评审的必查项。

**「文档与代码同 PR」是活的文档的落地关键**——架构图不在代码 PR 里 = 必然过期——「架构文档的保鲜期 = 上次更新的时间」。

## 6. 常见坑

**坑一：一张图讲全部**。类名、服务器、外部系统塞一张——没人看得清——C4 分层。

**坑二：L3 全画**。每个容器都画组件图——图多没人看——只画最复杂的。

**坑三：手画图不进仓库**。Visio 画完放共享盘——无法 diff、无法评审——文本图进仓库。

**坑四：图与代码脱节**。改架构不改图——图成历史文物——同 PR 更新。

**坑五：C4 当 UML 用**。在 L2 图画类——抽象层级混乱——每层只讲该层粒度。

**坑六：只画不写**。图没有文字说明——图 + 简短说明（图里讲不清的用文字）——「图是摘要、文字是细节」。

**坑七：文档与决策分离**。图更新了但 ADR 没有——决策历史断了——C4 + ADR 配套。

**C4 图的内容规范**（让图「画得对」）：**每个元素有名称与一句话职责**（「订单服务：处理订单生命周期」——无说明的元素是装饰）；**箭头标注通信方式与协议**（「HTTPS/REST」「Kafka 事件」——通信语义是架构的关键信息）；**技术栈标注**（容器级标注运行技术——「Spring Boot 3」「PostgreSQL 16」——「图是技术决策的可视化」）；**边界线表达组织边界**（系统边界、团队边界——「边界是架构的核心信息」）。**「图的内容规范 = 架构信息的最小完备集」**——一张 C4 图要能回答「系统有哪些部分、怎么通信、用什么技术、边界在哪」四个问题。
