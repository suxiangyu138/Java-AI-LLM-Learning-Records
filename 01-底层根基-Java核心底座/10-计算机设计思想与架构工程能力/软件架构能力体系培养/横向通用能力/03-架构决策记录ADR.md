## 1. ADR 是什么

**ADR（架构决策记录）= 一条决策的持久化文档**——记录「我们决定做什么、为什么做、放弃了什么、后果是什么」——核心是 **「why」而非「what」**：三个月后翻文档，「what」（用了 Redis）代码里看得见，「why」（为什么不用 Memcached/本地缓存）只有 ADR 里才有。

**ADR 的价值**：**可追溯**（新成员问「为什么这样设计」——看 ADR，不用考古）；**可复核**（决策的前提变了——「当初选 X 因为 Y，现在 Y 不成立了」——ADR 是推翻决策的依据）；**可审计**（评审与治理的输入——「架构是怎么演进的」看 ADR 序列）；**组织记忆**（人员流动不带走决策上下文）。**「讨论完就定了」的代价**：决策上下文随讨论消散——ADR 是「让讨论的成果不蒸发」的容器。

## 2. Nygard 模板

ADR 的经典模板（Michael Nygard 提出——四段式）：

```markdown
# ADR-012：订单查询引入 Redis 缓存

## Status
Accepted          <!-- Proposed / Accepted / Deprecated / Superseded -->

## Context
订单详情查询 QPS 峰值 2000，P95 延迟 800ms 超过 SLA（200ms）。
数据库（MySQL）读放大明显，压测显示连接池成为瓶颈。
已评估：订单数据变更频率低（状态变更才有写），缓存一致性窗口可接受（≤5s）。

## Decision
引入 Redis 缓存（key: order:{id}，TTL 5 分钟，失效策略：更新时主动删缓存）。
查询路径：Redis → 未命中 → MySQL → 回填缓存。

## Consequences
正面：P95 延迟降到 50ms 以下，数据库读压力下降 90%。
负面：引入缓存一致性维护成本（更新订单要同步删缓存）；
     缓存击穿/雪崩需要兜底（空值缓存、热点 key 预热）；
     新增 Redis 运维依赖（高可用、监控）。
```

**四段式的语义**：**Context 是「决策的问题与约束」**（背景数据、限制条件——「为什么此刻要决策」）；**Decision 是「决定」**（具体可执行、不含糊）；**Consequences 是「正反两面后果」**——**「只写正面不写负面 = 没写完」**——负面后果是「接受的权衡」（02 篇权衡显式化的载体）。

## 3. MADR 与格式演进

MADR（Markdown Any Decision Records）是 2026 年的轻量标准——在 Nygard 基础上加了结构化小节：

```markdown
# 决策标题
## 状态：已接受
## 背景与驱动因素       <!-- 为什么现在要决策 -->
## 决策                <!-- 我们决定做什么 -->
## 备选方案            <!-- 评估过什么（含被否决的） -->
## 后果                <!-- 正面 + 负面 -->
## 遵循本决策的指导     <!-- 实施时注意什么 -->
```

**MADR 的关键演进是「备选方案」小节**——「评估过什么、为什么否决」显式化——**「被否决的方案」与「被选中的方案」同等重要**：它记录「为什么不是它」——防止三个月后有人重新提「为什么不用 X」（答案已在 ADR 里）；**其他格式变体**——Y-Statement（「在……背景下，我们决定……，以达成……，接受……）」单句式，适合极简团队——**格式选择的原则：团队统一、写得出、读得懂——「模板是脚手架不是教条」**。

## 4. 生命周期

ADR 的状态流转（与代码评审/迭代节奏配合）：

```text
Proposed（提议）→ Accepted（已接受）→ [Deprecated（已弃用）/ Superseded（已被替代）]
                        ↑                        ↓
              （评审通过后）              （新 ADR 引用旧 ADR 标记）
```

**状态语义**：**Proposed**——决策待评审（讨论中——PR 评审就是 ADR 评审）；**Accepted**——评审通过、决策生效（实施中）；**Deprecated**——不再推荐（但未替代——历史遗留的「已接受但别再用」）；**Superseded**——被新 ADR 替代（新 ADR 中写明「替代 ADR-012」——**决策链可追溯**：ADR-012 → ADR-018 的演进路径一目了然）。

**生命周期与代码的配合**：**「实施完成」不是终结**——决策实施后要「验证」：3 个月后检查决策的假设是否成立（02 篇第六步复盘）——**ADR 可以「Superseded 于验证失败」**——「决策会错，记录让错可纠正」。

## 5. 质量门槛

一条合格的 ADR 的五个检查点：**Context 有数据**（不是「性能不好」而是「P95 800ms > SLA 200ms」——证据驱动，02 篇）；**Decision 可执行**（「引入 Redis」vs「优化性能」——决策要具体到能落地）；**备选有记录**（至少 2 个被否决方案 + 否决理由）；**Consequences 双侧**（正面 + 负面——负面是接受的权衡）；**无术语黑话**（新成员能读懂——ADR 是给「未来的团队」看的，不是给「今天参会的人」看的）。

**「质量门槛是评审的检查单」**——ADR 的 PR 评审按五条过——「ADR 不合格就合入」等于「决策没有记录」。

## 6. ADR 库的工程化

ADR 的工程化落地（让它成为团队习惯而非文档负担）：**目录结构**——`docs/adr/` 下按序号命名（`001-引入redis缓存.md`、`012-...`——序号递增、文件名即索引）；**模板与工具**——adr-tools CLI（`adr new` 建模板、`adr link` 维护关联）、Log4brains（ADR 库的搜索与浏览站点）；**流程嵌入**——「架构决策必须 ADR」进 PR 规范（评审时检查「这个改动有没有决策需要记录」）；**ADR 的数量纪律**——**「值得记录的决策」是单向门级**（数据库/架构风格/重大选型——「日志库用 slf4j」这种双向门不必 ADR，全记 = 噪音淹没信号）；**ADR 与 C4 图（04 篇）配合**——「图表达现状、ADR 表达决策历史」——活的文档体系。

## 7. 常见坑

**坑一：ADR 写「what」不写「why」**。「我们用了 Redis」——代码里看得见——Context 与备选才是价值。

**坑二：只写正面后果**。接受的权衡不记录——决策不可复核——双侧都写。

**坑三：被否决方案不记录**。「为什么不用 X」三个月后被重新问——备选小节。

**坑四：什么决策都记**。日志库也 ADR——噪音淹没信号——单向门级才记。

**坑五：ADR 与代码脱节**。决策改了 ADR 没更新——实施完成后检查 ADR 状态（Superseded 维护）。

**坑六：ADR 不进评审**。写完就合——评审是 ADR 质量的关卡——PR 评审含 ADR 检查。

**坑七：ADR 是中文还是英文不统一**。团队语言统一（国内团队中文优先）——「记录的语言要让未来的团队读得懂」。
