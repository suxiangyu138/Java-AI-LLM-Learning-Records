## 1. 包结构：架构的物理形态

**包结构（Package Structure）是架构在代码仓库里的物理形态**——**03 篇的架构模式最终都落实为包怎么分**。**读包结构的两个视角**：**按层分包**（controller/service/mapper 各自成包——**分层架构的形态**）；**按业务分包**（order/controller、order/service……——**模块化单体的形态**）。**包结构的三个功能**：**导航**（找代码靠包名——"**包名即地图坐标**"）；**边界**（包内高内聚、跨包访问靠约定/权限——**包是模块的最小边界**）；**约束**（**依赖规则通过包结构执行**——第 4 节）。**L1 的第一纪律**：**新代码写进"它该在的包"**——**Controller 代码进 controller 包、Mapper 进 mapper 包**——"**代码放错包 = 架构被破坏的第一现场**"。

## 2. 经典分层包结构

**Java Web 项目最经典的分层包结构**（按层分包）：

```text
com.company.project
├── controller/        # 表现层：接收请求、参数校验、返回响应
│   └── OrderController.java
├── service/           # 业务层：业务逻辑、事务边界
│   ├── OrderService.java          # 接口
│   └── impl/OrderServiceImpl.java # 实现
├── mapper/            # 数据访问层：数据库操作
│   └── OrderMapper.java
├── entity/            # 实体：与表结构对应
│   └── Order.java
├── dto/               # 传输对象：接口出入参
│   ├── OrderCreateReq.java
│   └── OrderResp.java
├── config/            # 配置类
├── common/            # 公共能力：统一返回/异常/工具
│   ├── Result.java
│   └── GlobalExceptionHandler.java
└── enums/             # 枚举
```

**每个包的职责一句话**：**controller 只管"接与回"**（不写业务）、**service 只管"业务"**（不写 SQL）、**mapper 只管"数据"**（不写业务）、**entity 对表、dto 对接口**——"**包名即职责声明：代码在哪包，就该只干哪包的活**"——**Service 里拼 SQL、Controller 里写业务 = 分层被破坏的信号**（第 4 节）。

## 3. 按业务分包：模块化单体的形态

**模块化单体（03 篇）的包形态：先按业务分模块，模块内再分层**：

```text
com.company.project
├── order/                    # 订单模块
│   ├── controller/OrderController.java
│   ├── service/OrderService.java
│   ├── mapper/OrderMapper.java
│   └── entity/Order.java
├── payment/                  # 支付模块
│   ├── controller/PaymentController.java
│   ├── service/PaymentService.java
│   └── ...
└── user/                     # 用户模块
    └── ...
```

**两种形态的对比**：**按层分包**——**找"订单的所有代码"要跨三个包**；**按业务分包**——**订单模块自成一体（未来拆微服务就是现成候选）**。**2026 主流**：**模块化单体（按业务分包）**——"**先按业务切模块，模块内再分层——'业务优先、技术其次'的包组织**"。**模块间的协作**：**模块间不直接访问对方 mapper/entity**——通过**模块提供的接口（Service）**协作——"**模块边界 = 接口边界：跨模块只能走 Service，不能摸对方的表**"（依赖规则在模块层同样生效）。

## 4. 依赖规则：只能往下

**分层架构的第一铁律：依赖只能往下，不能往上，不能跨层**：

```text
controller → service → mapper → 数据库
    ↑ 不能：controller 直接调 mapper（跳过业务层）
    ↑ 不能：mapper 调 controller（下层不知道上层存在）
    ↑ 不能：service 依赖另一个 service 的 controller（跨层绕路）
```

**违反依赖规则的后果**：**controller 直接调 mapper**——**业务校验/事务被跳过**（逻辑分散、事务失效）；**跨层调用**——**架构腐化开始**（01 篇"守护者"的现实版）；**循环依赖**——**两个 service 互相调用**（Spring 启动报错/设计缺陷信号）。**L1 的判断标准**：**写代码前问一句"这行代码该在哪个层"**——**Controller 只调 Service、Service 只调 Mapper/其他 Service、Mapper 只碰数据库**——"**依赖规则是架构的交通规则：人人都遵守，路上才不堵**"。

## 5. Maven 多模块

**Maven 多模块（Multi-Module）是工程级的模块化**——**一个父工程下多个子模块**：

```text
project-parent (pom)          # 父工程：统一依赖版本
├── common                    # 公共模块：工具/统一返回/异常
├── order-service             # 订单模块（可独立打包）
├── payment-service           # 支付模块
└── gateway                   # 网关模块（如微服务）
```

**多模块的三个价值**：**依赖版本统一**（父 pom 的 dependencyManagement 管版本——**一处升级全局生效**）；**模块独立打包**（order-service 可单独打 jar——**为将来拆服务留路**）；**编译隔离**（模块间依赖显式声明——**依赖关系可审计**）。**L1 在多模块里的注意**：**依赖方向与第 4 节同规则**——**业务模块依赖 common（向下），不能反向**；**common 里别放业务代码**（公共模块只放"公共"的）——"**多模块是'包结构'的工程放大版：规则一模一样，规模更大**"。

## 6. 命名规范

**包与类的命名规范**（Java 系，写代码的好习惯体系交叉：`../写代码的好习惯/00-写代码的好习惯知识体系总览.md`）：**包名全小写**（`com.company.order`）；**类名大驼峰**（`OrderController`）；**方法名小驼峰**（`createOrder`）；**后缀表职责**（Controller/Service/ServiceImpl/Mapper/Entity/Req/Resp——**后缀即角色声明**）。**命名与架构的关系**：**包名承载"业务归属"**（order 包 = 订单相关）、**类名承载"职责归属"**（XxxController = 表现层）——"**好命名让架构'看一眼就懂'，坏命名让架构'查半天才懂'**"——**新模块的命名先看既有风格**（对齐比创新重要，08 篇落地纪律）；**Maven 坐标与包名一致**（groupId:artifactId 与包名同源——"坐标即身份"）。

## 7. 五个常见坑

- **坑一**：代码放错包——**架构第一现场被破坏；新代码问一句"该在哪个包"**（第 1 节）；
- **坑二**：Controller 里写业务逻辑——**分层被破坏；Controller 只接回，业务进 Service**（第 2 节）；
- **坑三**：Service 里拼 SQL——**数据访问职责越界；SQL 进 Mapper**（第 2 节）；
- **坑四**：跨模块直接访问对方 mapper——**模块边界失效；走对方 Service**（第 3 节）；
- **坑五**：common 里塞业务代码——**公共模块被污染；common 只放真公共的**（第 5 节）。
