## 1. 接口 = 契约：模块的脸

接口（Interface）是模块对外的**契约**：它声明"模块能做什么、调用方要提供什么、会得到什么"，不承诺"怎么做"。

```text
接口契约的四要素：
├── 语义：方法做什么（一句话，无歧义）
├── 输入：参数及其约束（类型/必填/取值范围）
├── 输出：返回值及其含义（成功/失败/异常）
└── 副作用：调用会改变什么（写库/发消息/有状态）
```

接口设计差的两个典型后果：**语义模糊**（调用方猜用法，误解产生 bug）；**契约不稳定**（接口常变，所有调用方跟着改）。接口设计的原则一句话：**"别人无需看实现就能正确使用"**——调用方只读接口签名与文档即可写代码，这是接口质量的验收标准。

## 2. Port 接口：依赖倒置的落地

Port（端口）是依赖倒置（02 篇 D 原则）在接口层面的落地：**接口定义在"使用方"所在层，而非"实现方"所在层**。

```text
经典示例（用例层定义 Port）：
├── usecases/UserUseCases 层定义：
│   ├── Input Port：CreateUserUseCase（用例接口）
│   └── Output Port：UserRepository（持久化接口）
├── adapters/ 层实现：
│   ├── UserController implements CreateUserUseCase（入站适配）
│   └── JpaUserRepository implements UserRepository（出站适配）

依赖方向：usecases 不依赖 adapters
Controller 依赖 CreateUserUseCase 接口而非 Service 实现类
Service 依赖 UserRepository 接口而非 JPA 实现
```

Port 的工程价值：**并行开发**（接口先行，双方按契约实现）、**可测试**（mock Port 实现）、**可替换**（换实现不换契约）、**依赖方向正确**（核心不依赖外围）。判断标准：**依赖箭头指向接口所在层**——接口在用例层、实现在适配层，方向就对了。

## 3. 接口设计的四个原则

**原则一：单一语义**——一个接口一个用途。

```text
❌ UserService { createUser, deleteUser, getUser, listUsers, sendWelcomeEmail, checkPermission }
✅ CreateUserUseCase / GetUserUseCase / NotificationPort
（按使用场景拆，而非按实体聚合）
```

**原则二：小而聚焦**（接口隔离 I）——接口方法数克制（3-5 个是舒适区，超过 8 个要审视）。

**原则三：语义稳定**——接口一旦发布，禁止破坏性修改（改名/改参数/改返回类型），只做加法（加方法/加可选参数）。

**原则四：自解释**——接口名 + 参数名 + 文档让调用方无歧义：

```text
❌ process(data, flag)
✅ submitOrder(OrderRequest request)   // 语义自明
```

## 4. 参数设计：最小化与语义化

参数设计决定接口的易用性与耦合度：

```text
参数最小化：
├── 只传方法真正需要的参数
├── 不传"整个对象"只用其中一个字段（传字段或专门 DTO）
├── 不传"为了将来"的参数（预留参数是负债）
└── 相关参数聚合成 DTO（3+ 个散参数 → 请求对象）

参数语义化：
├── 布尔参数用动词开头：isActive / shouldNotify（而非 flag）
├── 枚举代替魔法字符串：OrderStatus.PAID 而非 "paid"
├── 时间参数明确时区：Instant/OffsetDateTime（而非裸 Date）
└── 数量参数明确单位：timeoutMs 而非 timeout

参数约束文档化：
├── 必填/可选（null 语义）
├── 取值范围（0 < pageSize ≤ 100）
└── 变更影响（新增必填参数 = 破坏性变更，需版本化）
```

**参数即契约的一部分**——调用方按参数签名写代码，参数的语义错误比实现 bug 更难排查（调用方以为传对了、实际语义不同）。

## 5. 返回设计：结果与错误

返回设计常见三错：**返回 null**（调用方不知道"没结果"还是"出错"）；**返回魔法值**（返回 -1 表示失败）；**吞异常**（接口内部 catch 掉，调用方无感知失败）。

```text
返回设计的推荐形态：
├── 成功：返回领域对象/DTO（语义明确）
├── 无结果：Optional<T> 或空集合（不返回 null）
├── 业务失败：领域异常（调用方可捕获分类处理）
├── 系统失败：技术异常（调用方兜底/告警）
└── 批量场景：结果对象（成功列表 + 失败列表 + 原因）

错误码 vs 异常：
├── 模块内（同进程）：异常更自然（类型安全、可分类 catch）
├── 跨模块（进程边界）：错误码/DTO 更稳（REST 状态码 + 错误体）
└── 原则：错误信息要有可操作性（"订单号不存在"优于"处理失败"）
```

**返回契约文档化**：接口文档写清成功/失败/异常三类返回，调用方按契约处理——这是接口文档（Knife4j 体系）里 @ApiResponse 覆盖 400/404/500 的架构原因。

## 6. 接口版本化与演进

接口发布后的演进纪律：

```text
兼容演进（推荐）：
├── 加方法（新增能力，不破坏现有）
├── 加可选参数（有默认值，不破坏）
├── 扩展返回对象（加字段，不破坏现有字段语义）
└── 放宽输入约束（原来是必填，改为可选）

破坏性变更（需要版本化）：
├── 改方法名/参数顺序/类型
├── 删除方法/字段
├── 收紧约束（可选改必填）
└── 改返回语义（返回结构大变）

版本化策略：
├── 同模块内：接口名带版本（V2 接口）或版本参数
├── 跨模块（REST）：URL 版本 /v1//v2/ 或 header 版本
└── 过渡期：双版本并存 + 弃用标记 + 迁移窗口（deprecated 标注）
```

**版本化成本最小化**：接口设计时想清楚"这接口真的稳定吗"——内部模块接口可以快速演进（影响面可控），对外接口（第三方消费）必须严格版本化。**接口是负债**：每多一个版本，维护成本多一份——所以接口要少而稳。

## 7. 接口的可测试性

接口设计的可测试性检验：**不依赖具体实现也能测试调用逻辑**。

```text
可测试的接口形态：
├── 依赖注入而非内部 new（构造注入/方法注入）
├── 副作用可观察（写库 → 可通过 Port mock 断言）
├── 无隐藏全局状态（时间/随机数要可注入）
└── 接口粒度为"行为"而非"细节"（测行为不测步骤）

测试形态：
├── 单元测试：mock Port，测用例层逻辑
├── 契约测试：接口实现方与调用方共测契约（输入输出一致）
└── 集成测试：真实实现 + 测试容器（DB/消息）
```

**接口可测试性 = 模块可测试性**：接口设计决定测试的难度——接口注入点清晰，测试就简单；接口内部 new 依赖，测试就要 mock 框架硬凑。设计时问一句"这个接口怎么测"，能暴露一半的设计问题。

## 8. 接口评审清单

| # | 检查项 | 标准 |
|---|--------|------|
| 1 | 语义单一 | 一句话能说清接口用途 |
| 2 | 方法数克制 | ≤5 个方法（超过审视） |
| 3 | 参数最小 | 无冗余参数/预留参数 |
| 4 | 参数语义化 | 动词开头、枚举、单位明确 |
| 5 | 返回无 null | Optional/异常/结果对象 |
| 6 | 错误可操作 | 错误信息有可操作性 |
| 7 | 依赖方向 | 接口在用例层、实现在适配层 |
| 8 | 可测试 | 注入点清晰，可 mock 测试 |
| 9 | 版本策略 | 对外接口有版本化计划 |
| 10 | 文档完整 | 语义/输入/输出/副作用四要素齐全 |

**评审的本质**：接口是契约，契约质量决定协作质量——接口评审是模块评审的核心环节（09 篇），不是可选项。
