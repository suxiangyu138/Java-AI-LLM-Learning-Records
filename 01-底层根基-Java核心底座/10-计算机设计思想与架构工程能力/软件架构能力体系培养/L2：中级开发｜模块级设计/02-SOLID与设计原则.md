## 1. SOLID 全景：五个原则一句话

| 原则 | 一句话 | 收益 |
|------|--------|------|
| S 单一职责 | 一个类/模块只有一个变更理由 | 可维护性，限制变更爆炸半径 |
| O 开闭原则 | 对扩展开放、对修改关闭 | 新增功能不修改已测试代码 |
| L 里氏替换 | 子类可无缝替换父类 | 继承层次可靠，促进复用 |
| I 接口隔离 | 小而聚焦的接口而非胖接口 | 降低耦合，避免无关依赖 |
| D 依赖倒置 | 高层不依赖低层，都依赖抽象 | 解耦、可测试、抗变更 |

SOLID 不是五个独立技巧，而是一个整体：**S 定职责粒度，O 定扩展方式，L 保继承正确，I 定接口形态，D 定依赖方向**——五者共同服务于模块的解耦（01 篇的第一性原理）。Apache Fineract 的 FSIP-8 案例（2026）展示了典型场景：跨域服务直接引用、违反分层（业务服务直接用别的域的 Repository）——SOLID 逐一修正。

## 2. S 单一职责：变更理由唯一

S（Single Responsibility）的核心不是"一个类只做一件事"（太模糊），而是**"一个类只有一个变更理由"**。

```text
违反 S 的信号：
├── 类名带"And"（OrderAndPaymentService）
├── 方法超过 2 个明显职责域（CRUD + 权限 + 通知）
├── 一个方法 30 行以上且有多段"段落注释"（每段一个职责）
├── 改动一个功能需要牵动类的多个方法

应用边界（避免机械拆分）：
├── 不是"一个方法一个类"——那是拆碎
├── 不是"一个类只能有一个方法"——S 管职责域不管方法数
└── 判断标准：类是否因多种不相关原因变化
```

S 的实践价值：**变更定位成本**——"改订单状态规则去哪？"答案唯一；**测试范围**——单职责类的测试集中，改动验证成本低。这是模块内最基本的可维护性保障。

## 3. O 开闭原则：扩展不修改

O（Open-Closed）：**对扩展开放，对修改关闭**——新增功能通过扩展实现，不修改已测试的代码。

```text
O 的实现手段（按优先顺序）：
├── 策略模式：行为变化 → 策略接口 + 新实现
├── 模板方法：流程固定、步骤可变 → 骨架方法 + 步骤钩子
├── 装饰器：功能叠加 → 包装原实现
├── 事件/观察者：副作用扩展 → 发布事件、监听者扩展
└── 配置驱动：数值变化 → 配置项而非改代码

O 的边界（避免过度设计）：
├── 不是"所有地方都要能扩展"——预测的扩展才值得做
├── 不是"新增即新类"——简单 if-else 分支有时更清晰
└── 判断标准：这个点真的会变吗？变了几次？
```

O 的本质是**把变化点隔离**：预测变化的位置 → 在变化点设计抽象 → 变化通过新增实现吸收。过度应用 O 的代价是"到处都是接口和策略类"，比不用更糟——2026 实践共识：**为已验证的变化设计扩展点，不为想象的变化预留**。

## 4. L 里氏替换：继承的可靠性

L（Liskov Substitution）：**子类必须能无缝替换父类**——调用方不需要知道具体子类。

```text
违反 L 的经典案例：
├── Square extends Rectangle：宽高不同语义
│   → setWidth 对 Square 的行为与 Rectangle 不同（改 width 会动 height）
├── 子类抛出父类未声明的异常
├── 子类方法签名收窄/放宽参数
├── 子类覆盖方法后"悄悄"改变前置条件

L 的替代方案（2026 实践）：
├── 优先组合而非继承（接口 + 委托）
├── 接口约束行为契约，实现各自正确
└── 用不变式（invariant）描述契约，子类保持
```

L 的工程意义：**依赖抽象时行为的一致性**——如果子类替换会破坏行为，继承层次就不可靠，"依赖抽象"（D）建立在 L 之上。实际项目里 L 的违反常表现为"继承复用但覆盖了关键行为"，用组合替代继承是最干净的解法。

## 5. I 接口隔离：小而聚焦

I（Interface Segregation）：**客户端不应依赖它不用的接口方法**——胖接口迫使实现方实现无关方法、调用方依赖无关契约。

```text
胖接口的问题：
├── Connector 接口 10 个方法：只做同步连接的实现被迫实现事件方法
├── 调用方依赖大接口：编译期强耦合（改无关方法也波及）

拆分的实践（iPaaS 案例）：
├── Connector（同步连接）
├── EventDrivenConnector（事件驱动）
└── BatchConnector（批量处理）
—— 按"使用场景"拆，而非按方法数拆

I 与 S 的关系：
├── S 管"实现类的职责"（一个变更理由）
└── I 管"接口的形态"（小而聚焦）
```

I 的收益：**接口是契约，小契约易维护、易实现、易替换**。判断信号：接口有超过 5 个方法且实现类有"不支持"的方法（抛 UnsupportedOperationException）——这就是胖接口的味道。

## 6. D 依赖倒置：高层不依赖低层

D（Dependency Inversion）：**高层模块不依赖低层模块，两者都依赖抽象**——这是模块解耦的最关键原则。

```text
违反 D：高层直接依赖低层实现
├── OrderService 直接 new JdbcOrderRepository
├── Controller 直接依赖 UserService 实现类
└── 业务逻辑依赖具体数据库/具体第三方库

遵守 D：都依赖接口（Port）
├── OrderService 依赖 OrderRepository（接口）
├── Controller 依赖 UserServicePort（接口）
└── 数据库/第三方通过实现 Port 接入（依赖注入）

D 与 DI 的区别：
├── 依赖倒置 = 方向原则（高层不依赖低层实现）
└── 依赖注入 = 组装手段（把实现注入到需要处）
—— DI 是落地 D 的常用工具，但 D 是原则
```

D 的收益：**模块可独立测试**（接口 + mock 实现）、**可替换**（换数据库只换实现）、**可并行开发**（接口先行，双方按契约开发）。这是模块级设计里"接口先行"的底层原理——05 篇的 Port 设计。

## 7. SOLID/DRY/KISS 的协同

2026 的共识：三者不是并列原则，而是**分层关系**——KISS 是顶层指导思想，SOLID 与 DRY 是落实 KISS 的手段。

```text
KISS（Keep It Simple）：系统的总目标——简单可维护
  ├── SOLID：通过清晰职责拆分让逻辑边界清晰 → 降低长期复杂度 → 服务 KISS
  └── DRY：写新代码前搜相似逻辑，2+ 处复用的进共享 Core → 减少重复 → 服务 KISS
```

```text
DRY 的实践边界：
├── 2 处相似：先不抽象（过早抽象是负债）
├── 3 处以上相似：抽共享（DRY 原则触发）
├── "相似"的边界：语义相同才 DRY，形似神异不要强行合并
└── 共享放哪：模块内共享 Core 优先于全局 Common（08 篇）
```

协同的判断：**一切原则最终服务"简单可维护"**——某个原则的应用让系统更复杂，就该质疑应用方式。原则是工具，KISS 是目的。

## 8. 机械套用的陷阱

| 陷阱 | 表现 | 正确姿势 |
|------|------|----------|
| S 拆碎 | 每个方法一个类 | S 管职责域，判断变更理由 |
| O 过度预留 | 每个类都留扩展点 | 为已验证的变化设计扩展 |
| L 滥用继承 | 为复用继承、覆盖关键行为 | 组合优先，接口约束契约 |
| I 过度拆分 | 一个方法一个接口 | 按使用场景拆，小而聚焦非碎 |
| D 全面抽象 | 所有类都配接口 | 变化点才需要抽象（稳定性依赖） |

**判断标准**：原则应用后，系统是更简单还是更复杂？变更是更局部还是更扩散？测试是更容易还是更难？三个问题都是负面答案——停止套用，回到 KISS。原则是"思考工具"不是"评分标准"。

## 9. 练习

1. 用五个原则各找一个你代码中的违反案例
2. 画一个"O 开闭"的改造：把 if-else 分支改成策略
3. 找出一个胖接口并设计拆分方案
4. 用 D 原则重构：高层直接依赖具体实现 → Port 接口
5. 判断三个原则应用案例是否过度设计（用"三个问题"检验）

---

> 🎯 **核心要点**：SOLID 五原则 = S 变更理由唯一 + O 扩展不修改 + L 子类可替换 + I 小而聚焦 + D 依赖抽象。协同：KISS 是目的，SOLID/DRY 是手段。陷阱：机械套用与不套用同样有害——用"三个问题"（更简单？更局部？更容易测？）检验每次套用。D 是模块解耦的关键：高层不依赖低层，接口先行。
