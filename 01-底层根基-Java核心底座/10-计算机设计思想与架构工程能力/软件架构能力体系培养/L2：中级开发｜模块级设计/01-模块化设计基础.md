# 01 - 模块化设计基础

> 🎯 模块化设计的第一性原理只有一句话：**高内聚、低耦合**。任何违反它的设计都是结构性缺陷。本章讲清模块的定义、内聚与耦合的判断标准、职责一句话原则与命名——这是 L2 全部内容的基石

## 1. 模块是什么：职责边界而非代码组织

模块（Module）是**职责的边界**，不是代码的组织形式——包、类、文件只是实现手段。判断"什么是模块"的标准是职责：**一组只因为同一个原因而变化的代码**。

```text
模块的四个要素：
├── 职责：它负责什么（一句话能说清）
├── 边界：它包含什么、不包含什么
├── 接口：对外暴露的契约（别人怎么用它）
└── 依赖：它依赖谁（依赖方向）
```

一个常见的认知错误：把"包结构"当"模块设计"——`controller/service/repository` 平铺包不是模块化（04 篇展开），按业务域组织才是。模块设计在包结构之前：先划职责边界，再用代码组织落地边界。L1 的"模块与包结构"篇讲的是读懂别人的组织方式，本 L2 讲的是**设计自己的边界**。

## 2. 高内聚：一种原因而变

高内聚的定义：**模块只因一种原因（一个变更动机）而改变**。判断方法：问"这个模块会因为什么而变化"，如果答案有两个以上不相关的理由，内聚度就低。

```text
低内聚的例子：
├── UserService 既管用户 CRUD、又管权限校验、还发欢迎邮件
│   → 三个变更理由：用户规则变、权限规则变、邮件内容变
├── 万能模块 Utils/Common 什么都放
│   → 无职责可言，所有人都在往里加东西
├── 一个方法干了"查询 + 校验 + 转换 + 落库"四件事
│   → 单一变更会牵连其他逻辑

高内聚的例子：
├── OrderModule：订单状态流转（唯一理由：订单规则变化）
├── PaymentModule：支付与退款（唯一理由：支付规则变化）
└── NotificationModule：所有通知发送（唯一理由：通知渠道变化）
```

内聚的收益：**变更爆炸半径最小**——改订单规则不影响支付，测试范围可控，新人看代码有明确的"这个改动去哪改"的答案。

## 3. 低耦合：通过接口交互

低耦合的定义：**模块间通过接口或抽象交互，不依赖对方的实现细节**。耦合的判断标准：

```text
耦合信号：
├── 业务代码直接 new 具体实现类（而非接口）
├── 跨模块访问对方的内部数据/内部类
├── 上层依赖下层的实现细节（而非抽象）
├── 一个模块的改动迫使其他模块跟着改
├── 循环依赖（A 依赖 B、B 依赖 A）

解耦手段：
├── 依赖倒置：都依赖抽象接口（02/05 篇）
├── 参数最小化：接口只传必要参数
├── 防腐层：语言不同的模块间加翻译层（03 篇）
└── 事件：跨模块副作用用事件而非直接调用（06 篇）
```

耦合的代价：**改动传导**——一个模块的内部实现变化，所有直接依赖它的模块都要跟着验证；耦合越高，"改一处"越接近"改全部"。低耦合的工程本质是**让模块可以独立变化、独立测试、独立替换**。

## 4. 职责一句话原则

"职责一句话原则"是高内聚的实践检验：**每个模块的职责必须能用一句话准确描述**。写不出来 = 边界不清。

```text
合格的一句话：
├── "订单模块：管理订单从创建到完成的全部状态流转"
├── "支付模块：处理支付与退款，不关心订单业务"
└── "通知模块：把消息投递到各渠道（短信/邮件/推送）"

不合格的表达：
├── "用户模块：用户相关的东西"（相关=边界不清）
├── "工具模块：放各种工具方法"（万能=无职责）
└── "管理模块：订单和用户和配置的管理"（多职责）
```

一句话原则的用法：**写代码前先写这句话**，写不出来或要写两句，说明模块还没想清楚；评审时先看模块的一句话描述，与代码行为对比——对不上就是职责漂移。

## 5. 模块命名：语义即边界

命名是模块设计的"合同"——名字决定边界预期：

- **业务语义优先**：OrderModule、PaymentModule（业务词）优于 TechnicalModule、CoreModule（技术词）
- **动词 + 对象**：订单管理、支付处理（表明行为）
- **避免万能词**：Utils、Common、Helper、Manager 是边界模糊的信号——出现"杂项包"说明有东西没找到归属
- **命名稳定**：模块名一旦发布就是团队语言的一部分，改名成本高（文档、包名、讨论习惯）

命名的工程意义：**名字是协作的最小契约**——"去订单模块看看"和"去那堆类里看看"是两种开发体验。命名体现的是设计者对边界的理解深度。

## 6. 内聚与耦合的量化判断

直觉之外，内聚耦合可以量化（07 篇的 ArchUnit 落地）：

```text
Cohesion Ratio（内聚比）= 模块内部调用边数 / 模块内节点数
  理想值 ≥ 0.8：模块内节点高度关联
  低于 0.5：模块内部像"陌生人聚会"，边界可疑

Cross-Module Call Density（跨模块调用密度）= 跨模块调用边数 / 总调用边数
  越高耦合越强；设阈值进 CI 门禁
```

量化的价值：**把"感觉"变成"门禁"**——架构评审说"耦合太高"是讨论，CI 红灯说"跨模块调用超标"是事实。模块设计要有"度量"意识，但不要被指标绑架：指标是边界设计的辅助验证，不是设计的出发点。

## 7. 练习

1. 用四要素描述你当前项目的一个模块（职责/边界/接口/依赖）
2. 找出你代码里两个低内聚的例子并重构描述
3. 找出三个耦合信号的实际案例并给出解耦手段
4. 用一句话原则检验三个模块，不合格的改边界
5. 用 CR/CMCD 公式手算一个小模块的内聚比

> 🎯 **核心要点**：模块化第一性原理 = 高内聚（一种原因而变）+ 低耦合（接口交互、独立变化）。四要素：职责/边界/接口/依赖。三件工具：职责一句话原则（写不出=边界不清）、业务语义命名（名字是协作契约）、量化指标（CR≥0.8、CMCD 进 CI）。模块设计在包结构之前——先划边界，再用代码组织落地。
