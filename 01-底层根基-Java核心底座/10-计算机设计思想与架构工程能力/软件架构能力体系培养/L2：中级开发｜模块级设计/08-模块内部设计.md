## 1. 模块内部的三层结构

模块内部遵循 04 篇的分层规则（依赖方向），典型的三层：

```text
模块内部（以订单模块为例）：
├── api/（对外契约层）
│   ├── OrderServicePort（对外接口）
│   └── dto/（对外传输对象）
├── application/（用例/应用层）
│   ├── OrderApplicationService（用例编排）
│   └── OrderStateMachine（状态流转）
├── domain/（领域层）
│   ├── Order（领域模型）
│   └── OrderStatus（枚举/规则）
└── infrastructure/（基础设施层）
    ├── JpaOrderRepository（数据访问实现）
    └── OrderEventPublisher（事件发布实现）

依赖方向：api ← application ← domain（向内）
         infrastructure 实现 domain 定义的接口（依赖倒置）
```

内部三层的价值：**契约（api）稳定、用例（application）清晰、领域（domain）纯粹、基础设施可换**。规模小的模块可以压缩为两层（api + 实现），规模大再展开——**内部结构跟复杂度走，不跟模板走**。

## 2. 设计模式：应用时机与克制

设计模式（GoF 等）是模块内部设计的弹药库，但用错的代价很高：

```text
模式应用的判断标准：
├── 用：变化点已验证（O 开闭的实践）
├── 用：复杂度确实需要（策略/状态机解决真实分支爆炸）
├── 不用：为"优雅"而用（模式是手段，KISS 是目的）
└── 不用：为"简历"而用（面试写工厂，代码里 if 更清晰）

模块内部高频模式（按实用排序）：
├── 策略：行为变体（支付方式/通知渠道）
├── 状态机：状态流转（订单/审批流）
├── 模板方法：流程骨架固定、步骤可变
├── 仓储模式：数据访问抽象（domain 定义、infra 实现）
└── 事件/观察者：副作用解耦（06 篇）

模式使用的纪律：
├── 一个模式解决一个问题，不要"模式套模式"
├── 模式命名进类名（xxxStrategy/xxxStateMachine）——读者一看就懂
└── 模式引入时写注释说明"为什么用这个模式"
```

**模式的本质**：它是"经过验证的变化隔离方案"——用模式=预判变化点并隔离。没有变化点的模式应用是过度设计（02 篇 O 的边界）。

## 3. DRY 与共享核心

模块内与模块间的代码复用策略：

```text
DRY 的层级（按优先级）：
├── 模块内复用：同模块 2+ 处 → 模块内公共类（最优先）
├── 模块间纯逻辑共享 → shared/ 共享核心（无业务语义）
├── 模块间业务共享 → 通过模块 API（不直接依赖内部）
└── 全局 Common 包 → 慎用（"什么都放"是腐化信号）

共享核心（Shared Core）的边界：
├── 放什么：无业务语义的纯逻辑（时间/金额计算/校验工具）
├── 不放什么：业务对象（Order/User 属于模块）、半业务半通用
├── 判定标准：shared 的类能否被"业务无关"地描述
└── 规模克制：shared 膨胀 = 隐藏的万能模块（01 篇）

反模式：Copy-Paste 复用 vs 强行合并
├── 2 处相似：先不抽象（合并过早，语义可能分叉）
├── 3 处以上：抽共享（DRY 触发）
└── "形似神异"：不合并（语义不同，合并是负债）
```

**共享的代价意识**：共享代码是"隐式依赖"——shared 改了，所有依赖它的模块都要验证。所以共享只放"不会因为业务变化而变"的纯逻辑，业务相关的共享一律走模块 API。

## 4. 依赖注入：构造注入优先

模块内部的依赖组装方式直接决定可测试性：

```text
依赖注入的方式（按推荐排序）：
├── 构造注入：构造器传依赖（推荐——依赖显式、不可变、测试易 mock）
├── 方法注入：方法参数传依赖（临时依赖）
├── 字段注入：@Autowired 字段（不推荐——隐藏依赖、测试难）
└── Service Locator：从注册表取依赖（反模式——隐藏依赖图）

构造注入的实践：
├── 构造器参数 = 依赖清单（一眼看出类依赖什么）
├── 配合 DI 容器（Spring）：Bean 定义即组装
├── 禁止业务代码手写 Service Locator（静态 getBean()）
└── 循环依赖：构造注入会暴露（Spring 构造循环直接启动失败——好事，逼你重构）

模块内部的 DI 纪律：
├── 依赖通过构造注入，不通过内部 new（new 具体实现 = 硬编码依赖）
├── 模块边界处用 DI 容器组装（api 接口 ↔ infrastructure 实现）
└── 测试里用 mock 注入（构造注入天然支持）
```

**DI 的本质**：依赖注入是"组装"的手段，配合依赖倒置（02 篇 D）让"实现可换"。Service Locator 的问题：依赖是隐藏的（类内部查注册表），测试要 mock 全局注册表——构造注入让依赖显式可见。

## 5. 包内组织与类命名

模块内部的类组织规范（工程落地细节）：

```text
类的文件组织：
├── 类文件职责单一（一个类一个文件，无多顶级类）
├── 按行为组织（OrderService/OrderRepository/OrderValidator）
├── 避免"上帝类"（OrderManager 管所有订单逻辑——S 违反）
└── 类名动词短语（XxxService/XxxHandler/XxxStrategy）

类规模的经验红线（2026 实践）：
├── Controller 类 < 50 行（薄适配层）
├── Service 类 < 100 行（用例编排，超过拆）
├── Repository 接口方法 < 10 个（超过审视）
└── 类方法 < 15 个、行数 < 300（经验值，非硬规则）

包内依赖规则：
├── 包内类可互相引用（模块内正常）
├── 跨包引用走公共接口
└── 包循环依赖 = 模块内结构失败（抽公共包）
```

**规模红线是"信号"不是"法律"**：超过红线触发审视（是否职责混杂），而不是机械拆分。S 原则（02 篇）是判断依据，行数只是提醒。

## 6. 模块内部的可测试结构

内部结构直接影响测试成本（05 篇接口可测试性的延伸）：

```text
可测试的内部结构：
├── 逻辑纯化：业务规则尽量放在无 IO 的纯方法（domain 层）
│   → 单测不需要 mock 任何东西
├── 副作用隔离：IO/时间/随机数通过接口注入
│   → 测试注入固定实现（固定时间/固定随机数）
├── 状态可观察：状态变化通过返回值/事件暴露
│   → 测试断言结果而非窥探内部
├── 例外：static 方法慎用（不可 mock、隐藏依赖）

测试分层（模块内部）：
├── 单元测试：domain 纯逻辑（最快、最多）
├── 组件测试：application 层 + mock infrastructure
└── 集成测试：真实 infrastructure（测试容器）——最少
—— 测试金字塔在模块内部同样成立
```

**内部可测试的收益**：模块的单元测试成本低 → 变更回归快 → 重构敢做 → 模块不腐化。**不可测试的模块**（大量 static、隐藏依赖、逻辑与 IO 纠缠）是技术债的重灾区——测试写不动，变更不敢做，代码烂掉。

## 7. 内部腐化信号

| 信号 | 问题 | 修复 |
|------|------|------|
| 类超过 300 行 | 职责混杂 | 按职责拆类（S） |
| 大量 static 方法 | 隐藏依赖、不可测试 | 改为实例 + 注入 |
| 字段注入泛滥 | 依赖隐藏 | 构造注入 |
| Service 类代码膨胀 | 用例层臃肿 | 下沉领域逻辑/拆用例类 |
| shared 包膨胀 | 万能模块 | 业务共享回模块 API |
| 复制粘贴 3 处+ | DRY 违反 | 抽共享（按 3 处规则） |
| 类名带 Manager/Util 泛滥 | 无职责表述 | 重命名 + 重新归位 |

**内部腐化与外部腐化的区别**：外部腐化（跨模块违规）靠 ArchUnit 拦截；内部腐化（类级问题）靠代码评审 + 测试覆盖率 + 规范。内部腐化不立即炸（能跑），但累积成"改不动"的模块——**内部健康是长期可维护性的地基**。

## 8. 练习

1. 画出你模块内部的三层结构与依赖方向
2. 找 3 个过度使用/该用未用设计模式的实际案例
3. 按 DRY 规则审视你的 shared/Common 包（该留/该拆/该移）
4. 把 3 个字段注入/Service Locator 改成构造注入
5. 用"规模红线"审视你的 Service 类并给出拆分方案

---

> 🎯 **核心要点**：模块内部 = 三层结构（api/application/domain/infrastructure，依赖向内）+ 模式克制（变化点才用）+ DRY 分层（模块内 > shared 纯逻辑 > 模块 API）+ 构造注入（依赖显式可测）。可测试结构：逻辑纯化 + 副作用注入 + 状态可观察。内部腐化是长期可维护性的地基——测试写不动 = 代码开始烂。
