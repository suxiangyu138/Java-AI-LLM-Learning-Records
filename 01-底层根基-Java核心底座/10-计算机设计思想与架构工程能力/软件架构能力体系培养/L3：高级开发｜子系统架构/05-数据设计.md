## 1. 数据所有权

**数据所有权（02 篇边界的展开）——每个数据项有且只有一个拥有者**：**拥有者的职责**——数据的写入与变更（CRUD 的唯一入口）、数据质量与治理（完整性约束、校验）、数据的对外暴露（通过契约——04 篇）；**消费者的约束**——通过拥有者的接口读写（不能直连拥有者的数据库）、消费的数据不反写（「读到的数据是快照，不是可写资源」）。

**数据所有权的落地**：**数据边界图**——子系统 × 数据表/数据域的归属矩阵（「订单表 → 订单子系统」——评审检查「有没有共享表」）；**共享数据的处理**——真正需要共享的数据用「数据复制 + 事件同步」或「独立聚合视图」（读模型——CQRS 的思想——[[../横向通用能力/06-架构模式知识地图|模式地图]]）；**「共享数据库是边界失效的信号」**（02 篇反模式）。

## 2. 数据模型设计

子系统内的数据模型设计（领域模型 vs 数据模型的桥接）：**领域建模**——从业务出发建模型（实体、聚合、值对象——[[../横向通用能力/06-架构模式知识地图|DDD 战术]]——「领域模型讲业务语言」）；**持久化模型**——表结构设计（范式与反范式、索引设计——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MySQL|MySQL 体系]] 的表设计）；**两者的映射**——ORM 桥接（JPA/MyBatis——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/06-Spring全家桶/Spring%20Data%20JPA|Spring Data JPA]] 的实体设计）。

**模型设计的核心决策**：**模型边界**（哪些数据属于哪个聚合——聚合根是一致性边界）；**表结构**（规范化程度——过度范式化查询难、过度反范式化一致难——**「范式与查询的权衡」**）；**索引设计**（查询模式 → 索引——「先有查询模式，再有索引设计」——不是先建表再补索引）；**历史数据**（是否保留、怎么保留——审计与演进）。

## 3. 存储选型

存储选型是 L3 的高频决策（[[../横向通用能力/02-架构权衡与决策|权衡决策]] 的场景）：**关系型（MySQL/PostgreSQL）**——结构化数据、事务、复杂查询——**默认选择**；**文档型（MongoDB）**——半结构化、schema 灵活、水平扩展——文档型业务数据；**键值（Redis）**——缓存、会话、计数器——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/02-非关系型数据库/Redis|Redis 体系]]；**搜索引擎（ES）**——全文检索、聚合分析；**时序/列式**——监控指标、分析负载；**对象存储**——文件、图片（MinIO/OSS）。

**选型方法**（options matrix 的应用）：**数据特征**（结构化程度、读写比、数据量级）；**访问模式**（查询复杂度、实时性）；**一致性要求**（强一致/最终一致）；**运维成本**（自建 vs 托管）——**「选型的产出是决策记录（ADR）——为什么是它、为什么不是别的」**。

## 4. 缓存设计

缓存是性能设计的头号手段（06 篇的性能手段之一），L3 的缓存设计要点：**缓存位置**——本地缓存（Caffeine——进程内、最快、多实例不一致）、分布式缓存（Redis——共享、跨实例一致——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/02-非关系型数据库/Redis/缓存设计|缓存体系]]）——**「本地 + 分布式两级缓存的组合」是高性能场景的标配**；**缓存策略**——读策略（Cache-Aside——先读缓存未命中读库回填）、写策略（Write-Through/Write-Behind——直写/异步写）、失效策略（TTL、主动删除——更新时删缓存）；**缓存问题**——**穿透**（查不存在的数据——空值缓存/布隆过滤器）、**击穿**（热点 key 过期——互斥锁/逻辑过期）、**雪崩**（大量 key 同时过期——过期时间加随机、多级缓存）——**「缓存三问（穿透/击穿/雪崩）是 L3 面试必问，也是设计必答」**。

**缓存设计的决策**：**缓存什么**（热点数据、读多写少——「缓存是给读服务的」）；**一致性窗口**（能容忍多旧——决定策略——[[../横向通用能力/02-架构权衡与决策|权衡]]：一致性与性能）。

## 5. 数据一致性

子系统内的一致性设计（强一致场景）与跨子系统的一致性（最终一致场景——[[../横向通用能力/06-架构模式知识地图|分布式数据模式]]）：**事务设计**——本地事务（ACID——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MySQL|MySQL 事务]]）、事务边界（「一个用例一个事务」vs「长事务」的权衡——事务边界 = 一致性边界）；**并发控制**——乐观锁（版本号——冲突少场景）、悲观锁（行锁——冲突多场景）、唯一约束（幂等防重——[[../横向通用能力/06-架构模式知识地图|幂等设计]]）；**跨子系统一致性**——最终一致 + 补偿（Saga）、事件同步（Outbox——「业务变更 + 发事件」原子化）。

**一致性的设计纪律**：**「一致性需求要显式声明」**——「这个数据要多强的一致」（强一致/秒级最终一致/分钟级）——声明写进设计文档（NFR 的一部分——[[../横向通用能力/05-质量属性与NFR|横向 NFR]]）；**「默认强一致、按需放松」**——能强一致就强一致（简单），必要时才最终一致（性能/分布式妥协）。

## 6. 数据生命周期

数据设计的完整视角——生命周期管理：**数据保留策略**——「数据留多久」（业务需要 + 合规要求——[[../横向通用能力/05-质量属性与NFR|合规 NFR]]）——删除策略（物理删除/软删除/归档）；**数据归档**——历史数据归档（冷热分离——热数据性能、冷数据成本——「归档是容量治理的常态动作」）；**备份恢复**——RPO/RTO 设计（备份频率、恢复演练——[[../横向通用能力/05-质量属性与NFR|可靠性 NFR]] 的数据面）；**数据迁移**——schema 演进（兼容迁移——加字段向后兼容）、数据迁移方案（双写/影子表）。

## 7. 常见坑

**坑一：共享表**。多子系统直连一张表——边界失效——数据所有权。

**坑二：先建表后补索引**。查询模式没分析——索引设计随查询模式。

**坑三：缓存不防三问**。穿透/击穿/雪崩裸奔——三个问题都设计。

**坑四：一致性不声明**。「数据应该一致」——没说多强——显式声明。

**坑五：存储选型不记录**。「用 MongoDB 因为流行」——options matrix + ADR。

**坑六：数据只进不出**。无保留策略、无归档——容量爆炸——生命周期设计。

**坑七：备份不演练**。RPO/RTO 写在文档里没验证——恢复演练。

## 8. 练习

1. 数据所有权的「拥有者职责」与「消费者约束」？
2. 领域模型与持久化模型的桥接？
3. 存储选型的方法（数据特征/访问模式/一致性/成本）？
4. 缓存三问（穿透/击穿/雪崩）与对策？
5. 数据生命周期的四件事？

> 🎯 **核心要点**：数据所有权 = 边界物理表达（共享表是边界失效信号）；模型设计（领域 ↔ 持久化桥接、索引随查询模式）；存储选型走 options matrix + ADR；缓存三问必答（穿透/击穿/雪崩）、一致性窗口是权衡；一致性需求显式声明、默认强一致按需放松；生命周期（保留/归档/备份演练/迁移）是设计一部分。
