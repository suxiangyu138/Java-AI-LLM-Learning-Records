# 07-可靠性与韧性设计
> 定位：可靠性是设计出来的——故障模式分析、幂等、重试/熔断/降级、备份恢复；「系统一定会出错，设计要让它出错了也可用」——韧性设计是 L3 与 L2 的分界之一。

## 1. 可靠性目标

**可靠性目标 = 可验收的 NFR**（[[../横向通用能力/05-质量属性与NFR|横向 NFR]] 的可靠族）：**可用性**（SLA——99.9% 意味着月故障 ≤ 43 分钟）；**RTO**（恢复时间目标——故障后多久恢复服务）；**RPO**（恢复点目标——故障时最多丢多少数据）；**数据可靠性**（不丢不坏——存储与备份）。**「没有目标的可靠性是口号」**——「系统要稳定」vs「99.9% 可用 + RTO 30 分钟 + RPO 5 分钟」——**「目标决定设计投入」**（99.9% 与 99.99% 的设计复杂度差一个量级）。

**可靠性设计的姿态**：**「系统一定会出错」**——网络会断、依赖会挂、数据会坏——**设计的目标不是「不出错」而是「出错了也可用、可恢复」**——「假设失败（Assume Failure）的设计」是韧性设计的起点。

## 2. 故障模式分析

**故障模式分析（Failure Mode Analysis）——枚举故障 + 设计对应韧性机制**：**第一步，枚举故障**——按故障面系统过一遍：**依赖故障**（下游服务挂了、超时）、**资源故障**（数据库连接池耗尽、磁盘满）、**数据故障**（数据损坏、主从延迟）、**流量故障**（突发流量、慢请求堆积）、**代码故障**（bug 引发的异常链）；**第二步，分析影响**——每个故障的影响面（谁受影响、影响多久）；**第三步，设计对策**——每个故障的韧性机制（超时、重试、熔断、降级、限流、备份——本文各节）。

**故障模式分析的产出**：**故障清单 + 对策表**（设计文档的一部分）——「这个子系统怕什么、出事了怎么办」——**「故障模式分析是可靠性设计的骨架」**——评审检查「故障清单是否覆盖」（[[../横向通用能力/07-架构评审与ATAM|评审]] 的可靠性维度）。

## 3. 幂等设计

**幂等——「重复执行结果一致」——可靠性的地基**：**为什么必须幂等**——网络重试（客户端超时重发）、消息重复消费（at-least-once——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/03-消息队列/消息队列理论与实战/00-消息队列理论与实战总览|消息队列]] 语义）、人工重放——**「不可幂等的接口在重试下必然出事故」**（重复下单、重复扣款）。

**幂等的实现姿势**：**幂等键**（请求方生成唯一键——服务端按键去重——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 幂等键]]）；**业务唯一约束**（数据库唯一索引——「支付单号唯一」——数据层兜底）；**状态机幂等**（「已支付状态再收支付回调 → 直接返回成功」——状态转移的幂等）；**「接口层幂等键 + 数据层唯一约束」双保险**（[[../横向通用能力/06-架构模式知识地图|模式地图]] 的幂等模式）。

## 4. 重试与退避

**重试——瞬时故障的恢复手段**：**重试什么**——瞬时故障（网络超时、5xx）可重试；**永久故障不重试**（4xx——重试无意义）；**重试的姿势**——**指数退避 + 抖动**（1s/2s/4s + 随机——防同步风暴）、重试次数封顶（3-5 次）、全局限流在重试之上（防重试风暴——**「重试是最容易引发雪崩的机制」**——[[../横向通用能力/06-架构模式知识地图|韧性模式]] 的重试纪律）；**超时设计**——「没有超时的调用是故障放大器」（一个慢依赖拖垮全部——超时链：连接/读/总时长——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/网络问题排查|网络排查体系]] 的超时设计）。

**重试与幂等的配合**：**「重试的前提是幂等」**——不可幂等的操作重试前要有幂等键（03 节）——「重试与幂等是可靠性的双轮」。

## 5. 熔断与降级

**熔断（Circuit Breaker）——依赖故障的隔离机制**：**原理**——调用失败率达到阈值 → 熔断器打开（快速失败，不再调用下游）→ 冷却期后半开（试探恢复）→ 恢复/继续熔断——**「熔断把故障隔离在依赖侧，不让它拖垮自己」**——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/08-分布式系统与架构/Java分布式框架/00-Java分布式框架总览|分布式框架体系]] 的熔断实现（Sentinel/Resilience4j）。

**降级（Degradation）——核心功能优先的取舍**：**降级策略**——「依赖挂了，提供降级响应」（返回缓存数据/默认值/提示稍后）；**降级分类**——功能降级（次要功能关停——推荐位改静态）、数据降级（实时数据改缓存数据）、容量降级（限流保护核心）；**「降级是提前设计的取舍」**——「哪个功能可以牺牲、牺牲时返回什么」在故障前定好（[[../横向通用能力/02-架构权衡与决策|权衡]] 的可靠性场景）——**「降级不是故障时的慌乱决策，是设计时的预案」**。

## 6. 备份与恢复

**备份恢复——数据可靠性的最后防线**：**备份策略**——全量 + 增量（频率按 RPO——RPO 5 分钟 → 增量 5 分钟）；**恢复流程**——恢复演练（RTO 验证——「备份没演练过 = 没有备份」——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/MySQL%20Redis%20MQ%20运维相关故障现象|运维体系]] 的备份纪律）；**多级备份**——本地备份 + 异地备份（机房故障的防线）；**「备份恢复是可靠性设计的最底一层」**——前面所有机制失效后的兜底——**「兜底也要演练」**。

## 7. 故障演练

**故障演练（Chaos 实验的工程化）——「可靠性是练出来的」**：**演练内容**——故障模式分析的对策逐项演练（下游挂掉 → 熔断生效？数据库主从切换 → 恢复时间？）；**演练方法**——混沌工程（Chaos Monkey 类工具——随机故障注入）、定期演练日（季度故障演练——设计对策的实战验证）；**演练的产出**——对策有效性验证（「熔断真的在 10 秒内生效」）、预案修正（演练发现预案失效 → 修正）、团队肌肉记忆（故障处置的熟练度）——**「故障演练让可靠性设计从纸面变成事实」**。

## 8. 常见坑

**坑一：无故障模式分析**。对策临场发挥——故障清单 + 对策表。

**坑二：不可幂等硬重试**。重复执行出事故——重试前提是幂等。

**坑三：重试无退避**。同步风暴——指数退避 + 抖动 + 封顶。

**坑四：无超时**。慢依赖拖垮全部——超时链设计。

**坑五：降级无预案**。故障时慌——降级提前设计。

**坑六：备份不演练**。RPO/RTO 纸面值——恢复演练。

**坑七：可靠性无目标**。「要稳定」——SLA/RTO/RPO 可验收。
