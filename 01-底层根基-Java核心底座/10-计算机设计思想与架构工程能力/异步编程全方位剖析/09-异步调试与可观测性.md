## 1. 栈丢失：异步排障的第一困境

同步代码的调试靠完整调用栈；异步代码的栈**在挂起点断裂**：

```text
同步：A → B → C → 异常（栈完整：A→B→C 全在）
异步：A → 发起异步 → 返回（A 的栈已消失）
     → B 挂起 → 事件恢复（栈只有 B 的局部）
异常发生时：只能看到"当前恢复点"，看不到"谁发起的这条链"
```

三处具体丢失：

1. **发起者丢失**：异常栈里看不到"谁启动了这条异步链"——线上日志里 `Exception in task` 没有调用方上下文
2. **等待链不可见**：futurelock（05 章）中"A 等 B、B 等 A"的环在传统 `jstack` 里看不到——每个线程各自"看起来正常"
3. **协程栈压缩**：Python 协程的 `traceback` 只显示当前 await 之后的帧；Java 虚拟线程的栈（JDK 21+）虽有改善（完整显示挂起链），但跨事件循环的链依然断裂

**对策**：不要指望栈，建立"**异步上下文**"——traceId + 阶段日志（第 3 节），让"链条"存在于日志里而非栈里。**异步排障的第一原则：栈不可用时，日志必须可拼链**。

## 2. 异步 profiler：async-profiler 与 py-spy

性能与卡顿排障的工具对比：

| 工具 | 平台 | 能力 | 异步适配 |
|------|------|------|---------|
| async-profiler | JVM | 采样火焰图、分配、锁 | **Java 21+ 虚拟线程/CompletableFuture 栈可采样** |
| jstack/jcmd | JVM | 线程转储 | 只能看平台线程；虚拟线程需转储增强（JDK 21+） |
| py-spy | Python | 采样调用栈（免插桩） | **可采样挂起中的协程恢复点** |
| cProfile | Python | 函数级计时 | 只统计实际执行，等待不计入 |

```bash
# 生产安全采样（无需重启、低开销）
# JVM：CPU 火焰图（含虚拟线程与异步链）
async-profiler -d 60 -e cpu -o flamegraph.html <pid>
# Python：采样定位"协程卡在哪"
py-spy top --pid <pid> --subprocesses
```

**2026 的关键改善**：Java 21+ 的虚拟线程让"每任务一行栈"成为可能——**异步任务第一次有了"自己的完整栈"**（挂起时栈帧保存在堆上，可被转储读取），这是虚拟线程相对协程/回调在可观测性上的决定性优势；Python 侧 py-spy 对 asyncio 协程的采样已成熟（能显示"哪个协程在等待哪个 Future"）。**选型"可观测性"维度时，虚拟线程/goroutine 明显优于裸协程**——09 章第 6 节的清单会再强调。

## 3. traceId 贯穿：上下文传播的工业方案

异步系统的可观测性靠"**日志拼链**"：每个请求生成 traceId，随异步调用传播到所有环节：

```text
入口：生成 traceId=abc123
  → HTTP 调用：Header 传递（W3C traceparent）
  → 消息队列：消息头传递
  → 异步任务：线程/协程上下文传递（MDC/ScopedValue/contextvars）
每个环节日志都带 traceId —— 按 traceId 聚合即完整链路
```

三语言/三框架的上下文传播机制：

| 环境 | 传播载体 | 注意 |
|------|---------|------|
| Java 线程池 | MDC（ThreadLocal） | **线程池复用线程 → 必须手动传递 MDC**（TaskDecorator） |
| Java 虚拟线程 | MDC + ScopedValue（JEP 506） | 虚拟线程新建栈 → ThreadLocal 不继承，用 ScopedValue 显式作用域 |
| Python asyncio | `contextvars`（async 原生支持） | **协程自动继承**——Python 的上下文传播是语言级内建 |
| JS | AsyncLocalStorage | 语言级内建 |

**常见事故**：Java 线程池丢 traceId（线程复用但 MDC 没传）——日志里同请求的链路断裂；Python 的 `contextvars` 只在 `asyncio.create_task` 时正确继承，`asyncio.to_thread` 的线程任务要手动传。**"traceId 断链"与"栈丢失"叠加 = 异步排障的至暗时刻**——两套机制都要在框架层统一解决（Spring 的 TaskDecorator、FastAPI 中间件 + contextvars）。

## 4. 超时与取消：异步系统的两大纪律

异步系统的"无等待上限"是资源泄漏与故障扩散的温床，两条纪律必须制度化：

- **超时纪律：每个异步调用必须有超时**——`orTimeout`（CompletableFuture）、`asyncio.wait_for`、`http.ClientTimeout`；超时是 futurelock 的头号解药（05 章），也是"下游故障不扩散"的护栏

```python
# 每个 await 都要有超时上限（生产铁律）
async def fetch_order(order_id: str) -> Order:
    try:
        return await asyncio.wait_for(order_api.get(order_id), timeout=3.0)
    except asyncio.TimeoutError:
        raise BizException("order service timeout")
```

- **取消纪律：发起方放弃时，异步链要能终止**——`CancellationToken`/`AbortController`/结构化并发的自动取消；**取消不是"不管了"，而是"显式终止资源占用"**（不取消 = 泄漏：连接、线程、内存持续被"僵尸任务"占用）

```kotlin
// Kotlin 结构化并发的取消传播：父取消 → 子全部取消
suspend fun runAll() = coroutineScope {
    async { fetchA() }   // 父 scope 取消时自动取消
    async { fetchB() }
}
```

2026 的格局：**结构化并发（JEP 525/Kotlin coroutineScope）把"取消传播"变成语言级语义**——手动取消令牌的时代正在结束；Java 侧 JEP 525 转正后，"超时 + 取消"两大纪律将首次获得标准 API 支撑。

## 5. futurelock 诊断实例

一个完整的 futurelock 排障案例（复现 05 章第 5 节的形态）：

```text
现象：服务偶发"请求全部卡住"数秒，之后自愈；无异常日志；CPU 正常
线索：P99 突刺与某下游服务发布重合；卡住时连接数激增
假设：事件循环/线程池被等待环占满

诊断路径：
  1. jstack/py-spy 采样 → 发现大量线程处于 "park"（等待 Future）
  2. 线程转储增强（JDK 21+）：看到每个等待点的"发起链"——两条任务互相等待
  3. 确认环：任务 A 的完成依赖任务 B，任务 B 在 A 的线程池里排队等线程
  4. 根因：A/B 用了同一线程池（线程池饥饿）+ 循环等待
  5. 修复：拆线程池（A/B 不同池）+ 全部调用加 orTimeout（超时即断环）
```

教训提炼：**futurelock 的三大促成因素**——线程池共享（饥饿互锁）、无超时（环永不破）、栈不可见（发现滞后）。**预防组合拳 = 隔离池 + 全链路超时 + 异步转储采样**——三条都做到，futurelock 几乎不可能发生。

## 6. 异步可观测性清单

生产可观测性的落地清单（10 章自测也可用）：

1. **traceId 贯穿**：入口生成、跨进程传播（HTTP 头/消息头）、上下文正确传递（线程池 MDC/协程 contextvars）
2. **阶段日志**：异步链每环节打"开始/结束/耗时"（traceId 相同）——拼链材料
3. **队列指标**：等待队列长度、积压量、处理延迟——背压是否生效的第一信号（08 章）
4. **超时指标**：超时次数与分布——下游健康度仪表盘
5. **线程/协程转储能力**：生产可采样的 profiler 预案（async-profiler/py-spy 提前验证权限）
6. **取消/泄漏指标**：僵尸任务数、未完成 Future 数——取消纪律是否执行的证据
7. **异常集中收集**：静默失败（05 章）的兜底——未处理拒绝的告警通道

> 🎯 **核心要点**：异步排障 = 承认"栈断了"，用"traceId + 阶段日志"重建链路；async-profiler（虚拟线程可采样）与 py-spy（协程恢复点可采样）是两类 profiler 的标配；超时 + 取消是两大制度化纪律（结构化并发将之语言级化）；futurelock 的三剂解药是隔离池、全链路超时、异步转储。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 栈在挂起点断裂 → 可观测性靠 traceId + 阶段日志拼链，不靠栈；
> 2. 虚拟线程的"每任务完整栈"是异步可观测性的决定性优势；py-spy 让 Python 协程卡点可见；
> 3. 两大纪律（超时/取消）+ 三剂解药（隔离池/超时断环/异步转储）= futurelock 预防组合拳。

**思考题**：

1. 为什么说"栈不可用时日志必须可拼链"？（→ 1 节）
2. 虚拟线程相对协程在可观测性上强在哪？（→ 2 节）
3. Java 线程池丢 traceId 的根因与解法？（→ 3 节）
4. 取消为什么是"显式终止资源占用"而非"不管了"？（→ 4 节）
