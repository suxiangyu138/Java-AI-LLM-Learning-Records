## 1. 异步模型选型决策树

按"语言 → 场景 → 团队"三层决策：

```text
语言层（硬约束）：
  Java 21+      → 默认虚拟线程；CompletableFuture 只做并行扇出
  Go            → 默认 goroutine + channel（无需选型）
  JS/浏览器      → 事件循环 + Promise/async-await（唯一模型）
  Python        → asyncio + FastAPI（AI/IO）；多进程（CPU 并行）
  Kotlin        → 协程 + Dispatchers（或虚拟线程基座）

场景层（需求驱动）：
  IO 密集 + 高并发连接   → 轻量线程（虚拟线程/goroutine）或事件循环
  实时流式/WebSocket     → 事件循环 + 协程（asyncio/Netty）
  并行扇出/聚合          → CompletableFuture/结构化并发/goroutine+channel
  CPU 密集并行           → 线程/进程池（异步模型无效，别硬用）
  长事务/强一致          → 同步代码 + 轻量线程（异步编排是负资产）

团队层（现实约束）：
  全员同步经验           → 虚拟线程/goroutine（零学习成本）
  已深谙异步             → 显式协程（控制力 + 内存省）
  生态同步主导           → 轻量线程（避免着色分裂）
```

**2026 默认答案**：Java 新项目虚拟线程、Python AI 服务 asyncio、Go 一切 goroutine、JS 别无选择——**"默认值"之外的选型必须回答"为什么打破默认"**。

## 2. 12 项落地清单

1. **Java 新服务启用虚拟线程**：Spring Boot `spring.threads.virtual.enabled=true`；自定义 ExecutorService 改用虚拟线程
2. **顺序编排用同步代码**：虚拟线程下"每请求一线程"回归；CompletableFuture 只留并行扇出场景
3. **事件循环线程纪律**：Python/JS 的循环线程里只有 await 与 CPU 快操作——阻塞任务一律 `to_thread`/线程池
4. **全链路超时**：每个异步调用 `orTimeout`/`wait_for`/`ClientTimeout`——futurelock 头号解药
5. **取消传播显式化**：结构化并发（coroutineScope）或取消令牌；发起方放弃即终止资源
6. **traceId 贯穿**：线程池 MDC 手动传递（TaskDecorator）、协程 contextvars、ScopedValue（虚拟线程）
7. **阶段日志**：异步链每环节打点（traceId 相同）——栈断了靠日志拼链
8. **背压显式设计**：队列有界 + 丢弃策略按业务语义（订单阻塞/指标丢弃）
9. **隔离线程池**：相互依赖的任务分池，避免"线程池饥饿互锁"（futurelock 温床）
10. **异步转储预案**：async-profiler/py-spy 生产权限与命令提前验证
11. **静默失败兜底**：每个 Future/Promise 有终止分支；未处理拒绝告警通道
12. **版本与内核基线**：JDK 21+（虚拟线程）、Linux 6.1+（io_uring 全特性）、Python 3.13+（性能）——新特性依赖新基线

## 3. 10 大避坑

1. **事件循环里写阻塞调用**（`time.sleep`/`requests`）——全服务停摆（07 章灾难模型）
2. **线程池里共享 MDC 不传 traceId**——链路断裂，排障瞎猜
3. **无超时的异步调用**——下游故障永久挂起，futurelock 温床
4. **CompletableFuture 嵌套不拍平**（`thenApply` 返回 Future）——类型地狱
5. **未处理拒绝静默**——任务"没执行"的诡异现象（05 章）
6. **给虚拟线程/goroutine 写池**——过度工程（03 章反模式）
7. **无界队列 + 无背压**——内存 OOM（08 章灾难）
8. **异步代码里用 `synchronized`/全局锁**——虚拟线程 pinning；协程锁语义混乱（用 Mutex）
9. **`asyncio` 里混用同步 ORM**——事件循环被数据库查询卡死
10. **按"异步更高级"选型**——CPU 密集/长事务场景异步是负资产（决策树团队层）

## 4. 高频面试题 12 问

### Q1：同步、异步、阻塞、非阻塞的区别？

> 答：两组正交维度——同步/异步看"调用方是否等待结果"，阻塞/非阻塞看"等待时线程状态"。异步非阻塞是正统异步（事件循环/协程），异步阻塞是虚拟线程挂起形态。经典四象限图是回答骨架。（→ 01）

### Q2：事件循环为什么能单线程高并发？

> 答：非阻塞 IO + 多路复用（epoll）——一个线程监听海量 fd，就绪才处理；挂起任务只占等待注册表的条目，不占线程。代价是回调不能阻塞，否则全循环停摆。（→ 04/07）

### Q3：epoll 和 io_uring 的区别？2026 年怎么选？

> 答：epoll 是就绪通知（Reactor，应用自己 read），io_uring 是完成通知（Proactor，内核代读+复制）。io_uring 吞吐高约 60%、p99 低约 25%，但低并发不划算、多租户容器默认禁用。主流服务继续 epoll，追求极致吞吐换 io_uring。（→ 02）

### Q4：虚拟线程、goroutine、协程的本质区别？

> 答：调度主体不同——虚拟线程 JVM 挂载体线程、goroutine Go 运行时 M:N、协程语言级状态机（无栈）。透明性：虚拟线程/goroutine 完全（同步代码兼容），协程显式（必须 await）。内存：协程最省（256B-几 KB）。50K 连接实测：协程 1.2GB < 虚拟线程 2.5GB << 平台线程 50GB。（→ 03/06）

### Q5：async/await 的原理？

> 答：CPS 变换——编译器把协程改写成状态机；await 是挂起点：保存状态机局部状态 → 让出控制权给事件循环 → 完成后恢复继续。协程无栈，内存极省，但挂起必须显式标注。（→ 06）

### Q6：函数着色问题是什么？怎么解决？

> 答：同步/异步函数不可互调，异步传染导致生态分裂（requests vs httpx）。解法：透明轻量线程（虚拟线程/goroutine 绕过着色）或生态全员异步（JS）。（→ 05/06）

### Q7：futurelock 是什么？怎么预防？

> 答：异步等待链成环且栈不可见——比传统死锁难诊断。预防三件套：隔离线程池（避免饥饿互锁）、全链路超时（断环）、异步转储采样（发现）。诊断用线程转储增强 + profiler。（→ 05/09）

### Q8：虚拟线程的 pinning 是什么？

> 答：虚拟线程执行 `synchronized` 阻塞时会钉住载体线程，失去卸载能力（JEP 491 已大幅改善但重锁仍可能）。对策：锁竞争激烈处用 ReentrantLock。（→ 03；细节见「虚拟线程」体系）

### Q9：背压是什么？request(n) 为什么是消费者驱动？

> 答：生产快于消费时防止缓冲无限膨胀的速率契约。只有消费者知道自己的消化能力，所以"速率决策权"在消费方——request(n) 让生产严格按需发放。实现三板斧：有界队列阻塞/拒绝策略/信号量。（→ 08）

### Q10：异步代码为什么难调试？怎么解决？

> 答：栈在挂起点断裂、异常丢失发起者、等待链不可见。解决：traceId + 阶段日志拼链（不靠栈）、async-profiler/py-spy 采样、虚拟线程的完整栈转储（JDK 21+）。（→ 09）

### Q11：2026 年 Java 新项目怎么写异步？

> 答：默认虚拟线程 + 同步代码（Spring Boot 一行启用）；并行扇出用 CompletableFuture/结构化并发（JEP 525 预览中）；IO 基座虚拟线程、上层编排结构化并发——与 Kotlin 协程组合模式同构。（→ 03/06/10）

### Q12：Python asyncio 和 Java 虚拟线程怎么选？

> 答：看生态与场景——Python 的 AI/流式场景 asyncio 是事实标准（FastAPI 生态），且 Python 无透明线程；Java 生态同步主导，虚拟线程零学习成本消灭着色问题。共同点：都在 IO 密集场景吃"等待复用"红利。（→ 06/10）
