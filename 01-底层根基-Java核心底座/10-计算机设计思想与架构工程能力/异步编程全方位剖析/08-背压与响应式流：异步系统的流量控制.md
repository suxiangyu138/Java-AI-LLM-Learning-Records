# 背压与响应式流：异步系统的流量控制

> 异步系统把"等待"藏了起来，但把"生产速度失控"暴露了出来：生产者比消费者快时，缓冲无限膨胀 → 内存耗尽。**背压（backpressure）**是速率契约——消费者通过 request(n) 告诉生产者"我还能吃多少"。本章讲透背压机制、JDK Flow API、以及它与削峰/限流/熔断的分工

## 1. 背压问题：缓冲失控的灾难

背压问题的发生链条：

```text
生产者（快）：每秒产生 10,000 个事件
消费者（慢）：每秒处理 1,000 个事件
无背压：  队列无限膨胀 → 内存 OOM / 延迟爆炸 / 数据积压后集中处理
有背压：  消费者说"慢点" → 生产者降速或丢弃 → 系统稳定
```

三种"无背压"的现场（生产事故常客）：

- **无界队列**：`LinkedBlockingQueue()` 无容量上限——生产者平均速度快于消费者时，内存线性增长直到 OOM
- **无限重试**：消费者失败 → 立即重试 → 重试风暴加剧积压（Kafka 消费端经典事故）
- **事件循环堆积**：回调/协程生产事件快于消费——就绪队列膨胀，延迟雪崩（07 章的长任务叠加）

**核心认知**：异步系统里"看不见的缓冲"到处都是（事件队列、任务队列、消息积压）——**背压不是优化，是防止"缓冲无限膨胀"的结构性护栏**。同步世界有自然的背压（线程阻塞 = 生产者自动减速），异步世界把等待藏起来后，速率控制必须显式设计。

## 2. request(n)：消费者驱动的速率契约

响应式流的背压协议是**消费者驱动**：订阅者主动声明"给我 N 个"，生产者按量发放：

```java
// Reactive Streams 四接口的最小语义
interface Subscriber<T> {
    void onSubscribe(Subscription s);   // 订阅建立：拿到"需求控制器"
    void onNext(T item);                // 收到一个元素
    void onError(Throwable t);
    void onComplete();
}
interface Subscription {
    void request(long n);   // 消费者：再给我 n 个
    void cancel();          // 消费者：我不要了
}
```

```java
// 消费者驱动的典型流程：request(1) 处理一个再要一个（严格背压）
public void onSubscribe(Subscription s) {
    subscription = s;
    s.request(1);                    // 先要 1 个
}
public void onNext(Item item) {
    process(item);                   // 处理
    subscription.request(1);         // 处理完再要下一个——生产永远不超消费
}
```

**为什么必须 request(n) 而非生产者自由推送**：只有消费者知道自己当前的消化能力（CPU 占用、下游积压）；"推"模型里生产者永远猜不准，只能靠无限缓冲兜底。**request(n) 把"速率决策权"从生产方移交到消费方**——这是响应式流设计的核心哲学。

## 3. JDK Flow API 与 Reactive Streams

JDK 9 的 `java.util.concurrent.Flow` 是响应式流的 Java 标准（四接口：Publisher/Subscriber/Subscription/Processor），Reactive Streams 规范是它的工业版本（Reactor/RxJava 实现）：

```java
// Flow API：Publisher 的生产由 Subscriber 的需求驱动
SubmissionPublisher<String> publisher = new SubmissionPublisher<>();  // 背压内置
publisher.subscribe(new Flow.Subscriber<>() { ... });

publisher.submit("event-1");   // 若订阅者未 request，submit 阻塞（有界缓冲）→ 背压生效
```

Flow API 的工程形态：**JDK 内置的 `SubmissionPublisher` 自带有界缓冲 + 背压**——订阅者处理慢时，submit 阻塞或拒绝（按溢出策略）。2026 年的定位（与「Java Python对比」体系 09 章呼应）：**Flow 主要是协议层与标准层**——多数团队经 Reactor/RxJava 或消息中间件（Kafka 的消费者组就是"消费者驱动"的工业实现）使用背压思想；虚拟线程普及后，REST 场景大量回归同步写法，**背压的主角转移到"消息队列与流式管道"而非应用内事件流**。

## 4. 有界队列与丢弃策略

背压的工程实现三板斧（按"保真度"降序）：

1. **有界队列 + 阻塞**：容量固定（如 10,000），满时生产者阻塞等待——最"真"的背压（`SubmissionPublisher`、`ArrayBlockingQueue` 默认）
2. **有界队列 + 拒绝策略**：满时按策略丢弃——`CallerRuns`（生产者自己执行）、`Abort`（抛异常）、`DiscardOldest`（丢最旧，**适合"只关心最新状态"的场景**，如监控指标）
3. **计数信号量限流**：消费者处理完一个释放一个许可——生产者 acquire 前先拿许可，等价于分布式 request(n)

```java
// 有界队列 + 丢弃最旧：监控/推送场景的正确选择
BlockingQueue<Event> q = new ArrayBlockingQueue<>(10_000);
// 满时 offer 失败 → 丢弃最旧或新事件（按业务语义选）
if (!q.offer(event)) { metrics.drop(event); }   // 显式丢弃 + 计数
```

**丢弃不是失败，是策略**：背压体系的完整设计必须回答"满了怎么办"——业务语义决定策略：**订单不能丢**（阻塞/拒绝+告警）、**日志指标可以丢**（丢弃最旧）、**重放任务可以重试**（持久化 + 补偿）。**没有丢弃策略的背压是不完整的背压**——10 章避坑清单的常客。

## 5. 背压 vs 削峰 vs 限流 vs 熔断

四个"流量控制"概念经常混用，分工如下：

| 概念 | 作用对象 | 机制 | 典型工具 |
|------|---------|------|---------|
| 背压 | 生产者→消费者 | 消费者反推速率，系统内闭环 | Flow API、Kafka 消费者组 |
| 削峰 | 流量曲线 | 缓冲 + 平滑（队列存峰、匀速消费） | 消息队列、线程池队列 |
| 限流 | 入口流量 | 拒绝超量请求（固定/滑动窗口、令牌桶） | Sentinel、Guava RateLimiter |
| 熔断 | 下游依赖 | 失败率超阈值→快速失败/降级 | Sentinel、Resilience4j |

```text
入口限流（挡超量）→ 系统内背压（速率闭环）→ 依赖熔断（防雪崩）
     限流               削峰+背压              熔断
```

**分工记忆**：背压管"系统内部的生产消费速率"，限流管"外部进来的量"，削峰管"波峰波谷的缓冲"，熔断管"下游坏了怎么办"——四者是不同防线，不是同义词。2026 年的微服务实践：网关限流（入口）+ 消息队列削峰（中段）+ 消费者背压（内部）+ 熔断降级（出口）构成完整防线（与「软件工程上的设计思想」体系"容错五件套"呼应）。

## 6. 2026 的背压实践

- **应用内事件流**：Flow API/Reactor 的背压用于"数据管道"（Kafka Streams 处理器、ETL 管道）——**消费速率由下游能力决定**，管道设计时就要按"最慢环节"配背压
- **消息队列是"分布式背压"**：Kafka 消费者组的手动提交 + `max.poll.records` 控制 = request(n) 的工业版——**处理速度跟不上就减少拉取量，而不是无限积压**（「消息队列理论与实战」体系详述）
- **虚拟线程改变了讨论重心**：同步代码阻塞 = 天然背压（线程数就是上限），应用内背压问题简化；**背压的主战场回到"跨系统管道"**（消息、流式、AI 推理批处理）
- **AI 场景新形态**：LLM 流式输出的"每 token 消费速率"、推理服务的 batch 队列——背压协议（慢速消费者 → 降级流式）正在成为 AI 网关的设计要素（本仓库「LiteLLM/模型推理与部署」体系有对应实践）

> 🎯 **核心要点**：背压 = 消费者驱动的速率契约（request(n)），把"速率决策权"从生产方移交消费方；实现三板斧（有界阻塞/拒绝策略/信号量）+ 丢弃策略必须显式设计；与限流（入口）、削峰（波峰）、熔断（下游）是四条防线；2026 年应用内背压因虚拟线程简化，主战场转向跨系统管道与 AI 流式。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 无背压 = 缓冲无限膨胀（无界队列/重试风暴/事件堆积三现场）；背压是异步的结构性护栏；
> 2. request(n) 是消费者驱动的速率契约；JDK Flow API（SubmissionPublisher）内置背压；
> 3. 背压（内部闭环）/限流（入口）/削峰（缓冲）/熔断（下游）四条防线分工明确，丢弃策略必须按业务语义设计。
