## 1. OS 线程：成本结构决定天花板

OS 线程（平台线程）是"1:1 模型"——一个 Java 线程 = 一个内核线程。成本结构决定了它的天花板：

- **创建成本**：约 1MB 栈（Java 默认）→ 创建与销毁都是重量级操作
- **切换成本**：内核态上下文切换（寄存器/缓存/TLB 冲刷）约 1-10 微秒，切换频繁时打散 CPU 缓存命中率
- **数量上限**：1 万线程 ≈ 10GB 虚拟内存 + 调度器压力——**"每请求一线程"在万级并发前崩盘**

```text
内存账本：1000 并发连接
  1:1 平台线程：1000 × 1MB = 1GB（OS 线程）
  虚拟线程：    ~1-2KB/个，按需增长 ≈ 几 MB（JVM 堆管理）
  goroutine：   初始 2KB，动态增长 ≈ 几 MB（Go 运行时管理）
  协程：        ~256B-几 KB（纯堆对象，无栈帧）
```

**2026 的启示**：平台线程的"贵"不是缺陷而是设计——内核线程保证优先级与实时性，代价是重量。轻量线程的出现不是淘汰内核线程，而是**"把调度权从内核拿回用户态"**：让"任务的并发形态"由运行时决定，而非内核。

## 2. 线程池：1:1 模型的现实妥协

在轻量线程之前，线程池是唯一解药：**限制线程总数，用队列排队任务**。

```java
// 线程池：用队列换线程数——任务等待而非线程膨胀
ExecutorService pool = Executors.newFixedThreadPool(200);   // 上限 200 线程
pool.submit(() -> handleRequest(request));                  // 超出的任务排队
```

线程池的功劳与代价：

- **功劳**：线程数有界（100-500），内存可控；任务排队削峰；线程复用省创建成本
- **代价**：**队列积压 = 延迟上升**（任务在队列里等）；**池大小调参是玄学**（IO 密集 vs CPU 密集差一个数量级）；**池耗尽 = 雪崩**（请求全排队，下游超时，连锁失败）；**线程池语义与调用方割裂**（谁提交的？排队多久？无处得知）

2026 年的定位：线程池仍是"有界资源"的通用工具（CPU 密集任务、数据库连接池配套），但作为"并发模型"已被虚拟线程取代——**"为 IO 任务调线程池参数"的时代正在结束**（03 章第 7 节与 10 章详述）。

## 3. 虚拟线程：JVM 管理的轻量线程

**虚拟线程**（JDK 21 定稿，JEP 444）：`java.lang.Thread` 的 JVM 实现——**任务还是"线程"，调度权在 JVM**：

- **机制**：虚拟线程挂在少量载体线程（carrier，平台线程）上运行；阻塞操作时 JVM 保存栈帧（堆中的 continuation）并卸载，载体线程转跑其他虚拟线程
- **透明性（杀手锏）**：`Thread`/`ExecutorService`/`synchronized`/ThreadLocal 全兼容——**现有同步代码不改一行获得异步容量**；调试器、profiler 原生可看（栈在堆上可读）
- **成本**：每线程约 1-2KB 可增长栈；创建百万级可行
- **边界**：`synchronized` 阻塞会 pinning（钉住载体线程，JEP 491 已大幅改善但重锁仍可能）；ThreadLocal 大量使用时注意堆压力

```java
// 虚拟线程：每请求一线程的朴素写法，容量百万级
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> handleRequest(request));   // 同步代码，阻塞不占载体线程
}
```

**2026 的现实**：Spring Boot 3.2+ 一行配置启用（`spring.threads.virtual.enabled=true`），新 Java 项目默认虚拟线程已是社区共识——**"每请求一线程"以最低学习成本回归**（细节见「虚拟线程」体系）。

虚拟线程的**适配面**也要讲清：**线程池迁移**——`Executors.newFixedThreadPool` 换成 `newVirtualThreadPerTaskExecutor`，任务提交代码不变、容量从百级到百万级；**ThreadLocal 的堆压力**——虚拟线程数量大时 ThreadLocal 变成"百万个对象"，用 ScopedValue（JEP 506 定稿）替代；**synchronized pinning**——重锁竞争场景仍会钉住载体线程（JEP 491 改善后多数场景已解除）。**"启用虚拟线程"不是开关，是迁移工程**——但迁移成本远低于当年"线程池 → 响应式"的改造，这正是它成为默认的原因。

## 4. goroutine：Go 运行时调度

**goroutine**（Go 诞生即有）：Go 运行时实现 M:N 调度——N 个 goroutine 映射到 M 个 OS 线程：

- **机制**：两级调度（本地队列 + 全局队列）+ 工作窃取（work-stealing）——空闲的 P 偷别的 P 队列的任务；栈从 2KB 动态增长
- **透明性**：与虚拟线程同级别的"隐形并发"——`go func()` 即并发，阻塞自动让出（Go 的 runtime 处理系统调用阻塞）
- **文化差异**：goroutine 创建极便宜，**Go 社区反对线程池**——"给运行时已优化的事写池是过度工程"；通信靠 channel 而非共享内存

```go
// goroutine：并发是一等公民
go handleRequest(req)     // 启动一个 goroutine，成本≈微秒级
// 通信：channel 而非锁
resp := <-ch
```

**2026 的地位**：goroutine 是"轻量线程"的参考模型——虚拟线程的设计理念与之一致（透明 + 用户态调度），差异在"语言内置（Go）vs 库层/JVM 层（Java）"。Go 的教训对 Java 的启示：**池化轻量线程是反模式**（03 章第 7 节）。

## 5. 协程：语言级状态机

**协程（coroutine）**是第三条路线——不模拟线程，而是**把函数变成可挂起的状态机**：

- **机制**：`async def`/`suspend` 函数经编译器 CPS 变换为状态机对象；挂起点（await）保存的是"状态机的局部状态"而非栈帧——**协程没有栈，只有堆上的状态对象（约 256B-几 KB）**
- **显式性**：挂起必须显式标注（`await`）——代码"看起来同步"，但调用方知道"这里是异步边界"；调度靠事件循环或 Dispatchers（协程自己选"跑在哪个线程池"）
- **代表**：Python asyncio、JS async/await（浏览器硬约束）、Kotlin coroutine（结构化并发 coroutineScope 稳定）、C++20 coroutine（需自建调度器）、PHP Swoole
- **与轻量线程的本质差异**：协程是"函数级并发"（挂起的是调用链），轻量线程是"任务级并发"（挂起的是整条执行链）——**协程无法透明替换同步代码，必须"着色"**（05/06 章）

```kotlin
// Kotlin 协程：显式挂起 + 结构化并发
suspend fun fetchOrder(id: String): Order = withContext(Dispatchers.IO) {
    orderDao.findById(id)          // 阻塞调用显式包进 IO 调度器
}
```

## 6. 三模型对照与 2026 实测

| 维度 | 虚拟线程 | goroutine | 协程 |
|------|:---:|:---:|:---:|
| 调度主体 | JVM（挂载体线程） | Go 运行时（M:N） | 语言/事件循环（无栈） |
| 每任务内存 | 1-2KB 可增长栈 | 2KB 动态栈 | 256B-几 KB 状态对象 |
| 透明性 | 完全（同步代码兼容） | 完全（idiomatic Go） | 显式（必须 await/suspend） |
| 结构化并发 | 预览中（JEP 525） | 无内建（靠 context） | Kotlin 稳定 / asyncio 手动 |
| 适用 | Java 服务端 IO | 网络服务/CLI | 前端/脚本/AI 服务 |

**2026 实测基准（Ktor 4 核 VPS，50K 并发连接）**：

| 指标 | 协程（Dispatchers.IO） | 虚拟线程 | 平台线程 |
|------|:---:|:---:|:---:|
| 内存（RSS） | ~1.2GB | ~2.5GB | ~50GB（不可行） |
| 每任务开销 | 256B-几 KB | 1-2KB 栈 | 1MB 栈 |
| GC 压力 | 低 | 较高（栈帧在堆） | — |

结论：**协程内存最省、虚拟线程透明性最强、goroutine 语言最省心**。2026 年的工程共识（多家来源）：三者互补而非竞争——**虚拟线程做 IO 基座，协程做上层结构化并发抽象**（Kotlin 社区已验证 `withContext(虚拟线程调度器)` 组合），Go 继续当"默认并发"的参考系。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 平台线程 1MB 栈 + 内核切换 = 万级天花板；线程池是妥协（有界但有积压/雪崩/调参三坑）；
> 2. 三轻量线程：虚拟线程（JVM 调度、透明）、goroutine（运行时调度、语言内置）、协程（状态机、显式着色）；50K 实测协程 1.2GB < 虚拟线程 2.5GB << 平台线程 50GB；
> 3. 2026 共识：虚拟线程做 IO 基座、协程做上层抽象、Go 当参考模型——"池化轻量线程"是反模式。
