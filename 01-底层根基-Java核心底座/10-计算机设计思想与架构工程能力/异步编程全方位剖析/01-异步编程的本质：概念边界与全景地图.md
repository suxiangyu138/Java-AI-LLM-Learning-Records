## 1. 四个概念的十字坐标系

异步编程讨论的混乱，根源是四组概念经常被混用。先钉死定义：

| 概念 | 定义 | 判定问题 |
|------|------|---------|
| 同步 | 调用方发起操作后**等待结果**才继续 | 调用返回时，结果是否已就绪？ |
| 异步 | 调用方发起后**不等待**，结果稍后到达 | 调用返回的是"操作本身"还是"结果"？ |
| 阻塞 | 调用让出 CPU（线程挂起等待） | 等待期间线程是否可执行其他任务？ |
| 非阻塞 | 调用立即返回（忙等或返回未就绪） | 失败返回时是否立刻拿到控制权？ |

```java
// 同步阻塞：最常见的形态（调用即等待，等待即让出）
byte[] data = socket.read();          // 读不到数据就挂起线程

// 异步非阻塞：发起后返回，数据到了回调/挂起点恢复
socket.readAsync(buffer, callback);   // 立即返回，数据到了执行 callback
```

**十字坐标系**：同步/异步 × 阻塞/非阻塞 = 四种组合。异步非阻塞是"正统异步"；异步阻塞（发起后线程挂起等通知）是虚拟线程/协程挂起时的真实形态；同步非阻塞（忙轮询）只在极少数场景存在。**讨论异步时默认指"异步非阻塞"，但要知道还有另外三种形态**——这四象限是后面所有章节的地图。

## 2. 阻塞 vs 非阻塞：与同步异步正交

阻塞与非阻塞描述的是**调用期间的线程状态**，与"是否等待结果"正交：

- 阻塞调用：线程挂起，把 CPU 让给其他线程——**代价是上下文切换**（约 1-10 微秒，且打散 CPU 缓存）
- 非阻塞调用：立即返回（可能带"未就绪"状态），线程继续跑——**代价是调用方要管理"未就绪怎么办"**

```python
# 非阻塞读：立即返回，未就绪则抛/返回空
data = sock.recv(1024)          # BlockingIOError 或 b""——调用方自己决定下一步

# 阻塞读：线程挂起直到数据到达
data = sock.recv(1024)          # 同上代码，语义不同——取决于 socket 配置
```

**工程直觉**：阻塞调用是"省心的挂起"（OS 帮你调度），非阻塞是"费心的轮询"（应用自己管理状态）。事件循环的核心技巧正是"用非阻塞 + 多路复用替代阻塞 + 线程"——**把"每个连接一个线程"变成"一个线程管所有连接"**（02 章详述）。而虚拟线程/协程的挂起则实现了"阻塞写法的非阻塞效果"（06 章）。

## 3. 并发 vs 并行：吞吐 vs 速度

- **并发（concurrency）**：多个任务**交错推进**——单核即可实现，关注"同时处理多少任务"（吞吐）
- **并行（parallelism）**：多个任务**同时执行**——必须多核，关注"单个任务多快完成"（速度）

```text
并发：任务A →→ 任务B →→ 任务A →→   （单核交错，吞吐高）
并行：任务A ────────────            （多核同时，延迟低）
      任务B ────────────
```

经典误解：**"异步 = 并行"是错的**——事件循环是单线程并发（无并行）；"异步 = 快"也不对——异步不减少总工作量，只改变"等待的利用方式"。异步解决的从来不是"算得快"，而是"**等得起**"：把等待 IO 的线程时间让给别的任务，让同等的硬件承载更多请求。2026 年一篇广为传播的异步批判文章（"What Async Promised and What it Delivered"）的核心论点就是：**每一代异步模型都在优化"等待"，却把复杂性留给了开发者的心智**——先理解这个本质，再谈具体模型。

## 4. 为什么需要异步：资源利用率的账本

异步存在的唯一理由：**IO 等待占用了线程，而线程是稀缺资源**。算一笔账：

- 一个请求的典型生命周期：CPU 处理 1-5ms + IO 等待 10-50ms（数据库/下游/网络）
- 同步模型：一个请求 = 一个线程全程占用，线程 80-95% 时间在等待
- 异步模型：等待期间线程被复用，**同等的线程数承载 10-50 倍请求**

```text
同步（每请求一线程）：   1000 请求 = 1000 线程 × 1MB 栈 = 1GB 内存，OS 切换负担重
异步（事件循环/轻量线程）：1000 请求 = 1 个事件循环（或少量虚拟线程），栈按需
```

量级对比（2026 实测）：平台线程承载 50K 连接需约 **50GB 内存（不可行）**；虚拟线程约 2.5GB；协程约 1.2GB（Ktor 基准，03 章详述）。**"异步 = 省内存 + 提高单机吞吐"是它的全部经济账**——而账的另一边（复杂度）在 5-10 节展开。

## 5. 异步的代价：三本明账

异步不是免费午餐，三本账必须提前算清：

1. **调试账**：异步代码的调用栈会在挂起点断开——异常栈丢失上下文，死锁（futurelock）难定位，排查成本是同步代码的 3-10 倍（09 章详述）
2. **心智账**：回调时代是"金字塔代码"，Promise 时代是"组合子学习曲线"，协程时代是"async 传染"——**每一代模型都要求开发者重新学习一套心智模型**，团队培训与招聘成本真实存在
3. **生态账**：**函数着色问题**（05 章）——同步库与异步库不能互调，生态被迫分裂（Python 的 requests vs httpx、Java 的同步 JDBC vs 异步驱动）；异步化的库维护成本转嫁给整个生态

**2026 年的趋势判断**：虚拟线程与 goroutine 这类"透明轻量线程"正是冲着第 3 本账去的——**让同步代码获得异步容量，生态不用分裂**（06 章详述）。但事件循环与显式协程（asyncio/Node）因其控制力与生态惯性，短期内不会消失——**"透明线程"与"显式协程"将在 2026-2030 长期共存**，各自占据 IO 密集与实时/流式场景。

## 6. 2026 的格局：异步成为默认

2026 年的异步编程格局一句话：**"异步"不再是可选项，而是高并发系统的默认设定**——

- Java 侧：JDK 21 虚拟线程定稿后，"同步代码 + 百万线程"成为新默认；CompletableFuture 退居"并行扇出"专项；结构化并发（JEP 525）即将转正
- Python 侧：asyncio 生态（FastAPI/uvloop）统治 AI 模型服务；free-threading 3.15 统一 ABI 之后，协程与多线程将各归其位
- JS 侧：事件循环 + Promise 依然是唯一模型（浏览器与 Node 的硬约束）
- Go 侧：goroutine + channel 一直是"最便宜的并发"，2026 年依然是参考模型

**选型心法**：先看语言（Java 默认虚拟线程、Go 默认 goroutine、JS 必须事件循环），再看场景（IO 密集选轻量线程/协程、实时流式选事件循环、CPU 密集回到线程/进程），最后看团队（透明模型上手快，显式协程控制强）。细节在 10 章给完整决策树。

> 🎯 **核心要点**：同步/异步讲"是否等待结果"，阻塞/非阻塞讲"等待时线程状态"，并发/并行讲"交错还是同时"——四概念正交，地图从此展开。异步的账本：省线程换吞吐，代价是调试、心智、生态三本账；2026 年"透明轻量线程"正在偿还生态账，但四代模型将长期共存。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 同步/异步（等待与否）× 阻塞/非阻塞（线程状态）四象限是全部讨论的地图；
> 2. 异步的经济账 = IO 等待期复用线程，50K 连接实测 50GB vs 2.5GB vs 1.2GB；
> 3. 三本代价（调试/心智/生态）中，生态账（函数着色）正被虚拟线程/goroutine 偿还。
