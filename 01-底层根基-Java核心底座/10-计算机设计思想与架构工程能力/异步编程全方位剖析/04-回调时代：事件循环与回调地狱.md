## 1. 事件循环：单线程高并发的秘密

**事件循环（event loop）**：一个线程循环执行"取事件 → 分发处理"——用非阻塞 IO + 多路复用（02 章的 epoll）监听海量 fd，谁就绪处理谁：

```python
# 事件循环的最小形态（伪代码）
while True:
    ready = epoll.poll(timeout)        # 阻塞等就绪事件（唯一"阻塞点"）
    for fd, event in ready:
        handler = handlers[fd]         # 事件 → 回调
        handler(event)                 # 执行回调
```

三个关键性质：

1. **单线程**：所有回调串行执行——**无竞态、无锁**，这是事件循环最大的心智红利
2. **回调不阻塞**：回调里若出现阻塞调用（`time.sleep`、同步 `requests.get`），**整个循环停摆**——所有连接一起卡死，这是事件循环的"阿喀琉斯之踵"
3. **就绪即触发**：IO 就绪事件驱动回调执行——代码顺序与执行顺序由"事件到达时间"决定，而非书写顺序

事件循环不是某语言的专利：**Node.js（libuv）、Python asyncio、Netty 的 EventLoop、Redis 单线程模型**共享同一骨架——差异只在"谁提供循环"（C 库 vs 语言内置）与"回调之外还能用什么"（Promise/协程包装）。

## 2. 宏任务与微任务：两个队列的秩序

JS 事件循环的"两个队列"是理解"执行顺序反直觉"的关键（Python asyncio 的 task/ready 队列同理）：

- **宏任务（macrotask）**：setTimeout、IO 回调、事件处理器——每轮循环取一个执行
- **微任务（microtask）**：Promise 的 then、async/await 的恢复、queueMicrotask——**当前宏任务结束后、下一个宏任务前，全部执行完**

```javascript
console.log("1");                     // 同步：直接执行
setTimeout(() => console.log("2"));   // 宏任务：本轮之后
Promise.resolve().then(() => console.log("3"));  // 微任务：本轮内插队
// 输出顺序：1 → 3 → 2（微任务优先于下一个宏任务）
```

工程含义：**"Promise 比 setTimeout 先执行"不是巧合而是协议**——微任务队列保证了"同一批异步操作按提交顺序执行"（FIFO），这是 Promise 链"看起来同步"的底层保障。面试常考的"输出顺序题"背后就是这两个队列的秩序；理解它，异步代码的执行顺序就不再是玄学。

## 3. 回调地狱三宗罪

**回调地狱（callback hell / 金字塔之灾）**：异步操作 A 完成后才能做 B，B 完成后做 C——嵌套回调形成金字塔：

```javascript
// 回调地狱：三层嵌套已是灾难，六层是常态
getUser(id, (user) => {
    getOrders(user.id, (orders) => {
        getTotal(orders, (total) => {
            renderTotal(total, (view) => {
                // ……深不见底
            });
        });
    });
});
```

三宗罪，每一宗都真实地伤害工程：

1. **顺序不可读**：执行顺序 = 嵌套深度，代码阅读从"从上到下"变成"跳进跳出"——review 与维护的认知负担爆炸
2. **错误处理碎片化**：每层回调都要单独处理错误，漏一层就静默吞掉——"错在哪一层"成为悬案
3. **不可组合**：回调无法作为值传递、无法取消、无法并行编排——"先 A 后 B 再并行 C"这种组合需求在回调世界要手工造轮子

**2026 的视角**：回调地狱没有消失，它只是被 Promise/协程"包"住了——Netty 的 ChannelHandler、Redis 的 Lua 回调、以及所有"框架回调 API"依然是回调形态。**回调本身不坏（它是事件驱动的自然语言），坏的是"用回调表达控制流"**——进化的方向（05/06 章）不是消灭回调，而是用"可组合的抽象"包裹回调。

## 4. 可取消性与错误处理的缺失

回调模型的两个结构性缺失，是它被取代的直接原因：

- **可取消性缺失**：发起异步操作后，"我不想等了"怎么办？回调模型没有语言级答案——要么忽略结果（资源泄漏），要么引入"取消令牌"（手工传播，极易遗漏）。相比之下，协程的 `cancel()`、Promise 的 `AbortController` 都是语言级方案
- **错误处理缺失**：回调签名通常没有"错误参数"（`callback(data)` vs `callback(err, data)` 两派打架），未捕获的回调异常直接崩进程或静默丢失——**"错误去哪了"成为回调代码的第一谜题**

这两项缺失在 2026 年依然存在于"裸回调 API"中（Netty 的 promise 回调用 exception 分支、Node 的 callback 风格已弃用但存量仍在）。**判断一个异步 API 是否"现代"的标准：能否取消、错误是否结构化**——两条都不满足的 API 在使用时就要自己补包装。

## 5. Netty / Node.js：回调时代的工业形态

- **Netty**（Java 事件驱动网络框架）：EventLoop 线程模型 + ChannelHandler 回调链——Reactor 模型的工业巅峰；RPC 框架（Dubbo/gRPC-Java）的底层底座。它的回调形态（Handler 链）由框架定义、顺序由框架保证，比"裸回调"体面得多，但"链路里的状态传递"（ChannelHandlerContext）依然需要经验
- **Node.js**：libuv 事件循环 + 回调 API（fs.readFile(cb) 等）——早期 Node 是回调地狱的代名词；随后 ES6 Promise/async-await 语法层拯救了生态，但"事件循环 + 回调"的内核从未改变

**2026 的遗产视角**：回调时代的架构遗产（事件循环、多路复用、Handler 链）全部保留在现代栈里——**Netty 的 EventLoop 与 asyncio 的事件循环是同一件事，只是包装层不同**。学习回调时代不是考古，而是理解"事件驱动"这个不变内核，以及"可组合抽象"为何成为下一代模型的主线。

## 6. 从回调到 Promise：进化的动机

进化的动机可以压缩成一句话：**"把异步操作变成可组合的值"**——回调是"过程"（执行到某处触发），Promise 是"值"（一个代表未来结果的容器），值可以传递、组合、编排：

```text
回调：  doA(a => doB(b => doC(c => ...)))     —— 过程嵌套，顺序=嵌套深度
Promise：doA().then(doB).then(doC)             —— 值链式，顺序=链式书写
协程：  c = await doC(await doB(await doA()))  —— 同步外观，状态机执行
```

**Promise 的价值不是消灭回调，而是"把回调收敛到一个可组合的容器里"**——错误处理集中（catch）、组合子齐全（all/race/any）、执行顺序可读（链式）。它的局限（一次性、着色问题、futurelock）推动第三代模型（协程/虚拟线程）登场——这正是 05 章的主题。**五代模型（回调→Promise→协程→轻量线程→结构化并发）不是否定前代，而是每代解决前代的结构性缺陷**——这条主线贯穿本体系全部章节。

> 🎯 **核心要点**：事件循环（单线程 + 多路复用 + 就绪回调）是异步的地基，所有现代模型都是它的包装；宏/微任务双队列解释了"执行顺序反直觉"；回调地狱三宗罪（顺序不可读/错误碎片化/不可组合）+ 可取消性缺失驱动了 Promise 进化——"把异步变成可组合的值"是此后一切模型的主线。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 事件循环 = 单线程串行回调 + epoll 就绪监听，回调不阻塞是它的铁律；
> 2. 回调地狱三宗罪 + 可取消/错误处理缺失 = 结构缺陷，非风格问题；
> 3. 进化主线：回调（过程）→ Promise（值）→ 协程（同步外观），每代修补前代的结构缺陷。
