## 1. 四种 IO 模型：从阻塞到异步

Unix 网络编程把 IO 分为四种模型，它们是 01 章"四象限"的操作系统版：

| 模型 | 线程状态 | 数据到达时 | 代表 |
|------|---------|-----------|------|
| 阻塞 IO | 挂起等待 | 内核复制完返回 | 传统 socket |
| 非阻塞 IO | 忙轮询（返回未就绪） | 应用反复试探 | 早期游戏服务器 |
| 多路复用 | 单线程监听批 fd | 就绪事件通知 | epoll/Netty/Redis |
| 异步 IO | 发起即返回 | 内核完成并复制好数据，完成事件通知 | io_uring |

```text
阻塞：  read() ── 挂起 ── 数据到 ── 返回
非阻塞： read() ── 未就绪立即返回 ── 忙轮询……
多路复用：epoll_wait() ── 就绪列表 ── 逐个处理
异步：  io_uring_submit() ── 干别的 ── 完成队列通知
```

关键区分：**多路复用仍是"就绪通知"**——内核告诉你"可以读了"，应用自己执行 read 并复制数据；**异步 IO 是"完成通知"**——内核读好并把数据放进应用缓冲区，再通知完成。就绪通知省了"线程等待"，完成通知连"应用发起 read"都省了——这是 io_uring 高效的结构性原因。

## 2. 多路复用三兄弟：select / poll / epoll

三代多路复用接口，解决同一问题（监听大量 fd 的就绪状态），复杂度递增：

| 维度 | select | poll | epoll |
|------|--------|------|-------|
| fd 上限 | 1024（FD_SETSIZE） | 无硬限 | 无硬限 |
| 每次调用 | 全量拷贝 fd 集合到内核 | 同左 | 注册一次，内核维护红黑树 |
| 就绪返回 | 全量扫描 O(n) | 同左 | 就绪链表直接返回 O(就绪数) |
| 触发模式 | 水平 | 水平 | 水平 + 边缘 |
| 时代 | 1990s | 1990s | Linux 2.6（2003 起主流） |

**epoll 的核心突破**：把"每次调用都全量拷贝 + 扫描"变成"注册一次 + 事件回调"——fd 集合由内核长期维护（红黑树），就绪的 fd 挂上就绪链表，`epoll_wait` 只拿结果。配合**边缘触发（ET）**模式（只在状态变化时通知一次），配合非阻塞读写，是 Nginx/Redis/Netty 高吞吐的根基。2026 年的 epoll 依然是这些主流服务器的事实底座——它没有消失，只是"不够新"。

## 3. Reactor vs Proactor：就绪 vs 完成

两种事件处理架构，是理解 epoll 与 io_uring 差异的钥匙：

- **Reactor（就绪通知，epoll 阵营）**：事件循环监听到"可读/可写"→ 应用自己 read/write → 处理完再注册下一轮。**读操作由应用完成**，数据在应用调用 read 时复制
- **Proactor（完成通知，io_uring 阵营）**：应用提交"读请求 + 目标缓冲区"→ 内核完成读取并复制 → 完成事件带数据通知。**读操作由内核完成**

```text
Reactor：epoll 通知"可读" → 应用 read() → 复制数据 → 处理
Proactor：提交读请求 → 内核 read() + 复制 → 完成事件 → 处理
```

工程含义：Reactor 的实现（Netty 的 EventLoop、Redis 的事件模型、Node 的 libuv）成熟且可控——应用掌握读取时机，缓冲管理直观；Proactor 的 io_uring 则把"读"也卸载给内核，**系统调用次数与上下文切换大幅减少**，代价是缓冲区的生命周期要提前设计（内核要往你给的内存写）。2026 年的实践共识：**主流服务继续 Reactor（epoll），追求极致吞吐与尾部延迟的服务升级 Proactor（io_uring）**。

## 4. C10K 问题：历史与启示

C10K（一万并发连接）是 1999 年 Dan Kegel 提出的经典问题：单机如何同时服务一万连接？当时的答案演进史，就是异步编程的史前史：

1. **每连接一线程**：1 万连接 = 1 万线程——内存（1MB 栈 × 1 万 = 10GB）与调度直接崩盘
2. **每连接一进程 + 非阻塞轮询**：省内存但 CPU 空转
3. **事件驱动 + 多路复用**：select 受 1024 限制，poll 受 O(n) 扫描限制，最终 epoll 给出 O(1) 级答案——**单线程事件循环 + epoll = 万级连接**，Nginx/Redis 因此诞生

2026 年的启示有两层：**C10K 早已被 epoll 解决（现在谈 C100K/C1M）**，且被虚拟线程重新定义——"每连接一协程"让"每连接一线程"的朴素写法重新可行（03 章）；**但多路复用的思想没有过时**——事件循环的"一个线程管所有连接"依然是 JS/Python 生态的硬约束。**学历史的价值：知道"线程不够用"与"事件循环太复杂"两难是 20 年不变的基本矛盾**，所有异步模型都是在这对矛盾上打补丁。

补充一个面试常用视角：**C10K 的"K"为什么是一万**——1999 年硬件下单线程处理一万连接的瓶颈不在 CPU 而在"每连接的开销"（fd 数、内存、上下文切换），今天的 C100K/C1M 讨论同一问题、量级提升三个数量级，靠的是**事件驱动 + 用户态调度 + 轻量内存**三件套的叠加。**"问题没变，成本被技术摊薄"是网络编程演进史的主线**——从"线程太贵"到"连接太贵"到"内存太贵"，每一轮摊薄都带来一轮架构革命。

## 5. io_uring：2026 的异步 IO 新标准

**io_uring**（Linux 5.1，2019 引入，Jens Axboe 设计）通过**共享内存环形队列**提交与收割 IO，2026 年已确立为 Linux 高性能异步 IO 的新标准：

- **机制**：应用往 Submission Queue 写请求（写文件、读 socket 等），内核执行后往 Completion Queue 写结果——**无系统调用循环、支持批量、支持真正的异步文件 IO**（epoll 做不到文件异步）
- **2026 基准**：纯 socket 吞吐比 epoll 快约 60%，加 SQPOLL（内核态轮询提交队列）再快约 40%；高并发下 p99 低约 25%、p99.9 低约 30%；Red Hat 示例 5000 个 socket 操作仅 23 次系统调用
- **multishot 革命（5.19+）**：内核自动重新武装接受/接收事件，应用只消费完成队列——2025 年"杀事件循环"论战的核心；事件循环不会消失，但简化到"消费完成 + 批量提交"
- **生产采纳**：PostgreSQL/MySQL/RocksDB/ScyllaDB（磁盘 IO）、HAProxy 2.6、NGINX io_uring 模块、MinIO；语言侧 uvloop（Python，2024 起可选）、Go 部分后端、Node libuv 实验支持、.NET 2026 接入（15-40% CPU 下降）
- **安全与边界**：2021-2023 的 CVE 历史（Google 报告 2022 年内核漏洞赏金 60% 瞄准 io_uring）已随加固收敛；**多租户容器默认禁用、可信服务器进程可用**；低并发/小消息场景 epoll 反而略优，io_uring 不是万能替代

> ⚠️ **内核要求**：基础功能 5.1+，multishot 5.19+，零拷贝 6.0+，全特性建议 6.1+。

## 6. 零拷贝：sendfile 与绕过用户态

异步 IO 的另一半是"少复制"——**零拷贝（zero-copy）**：避免数据在"磁盘→内核缓冲→用户缓冲→内核 socket 缓冲→网卡"间的多次复制：

- `sendfile()`：文件 → socket 直接在内核空间传递（文件服务器/静态资源分发的事实标准）
- `MSG_ZEROCOPY`（io_uring/内核 6.0+）：网络发送路径零拷贝
- 意义：大文件传输场景 CPU 占用与内存带宽下降显著，与异步 IO 叠加（io_uring 的注册缓冲区）是 2026 年"极致 IO 吞吐"的完整拼图

```c
// 经典四拷贝 → sendfile 零拷贝
read(fd, buf, n);  write(sock, buf, n);   // 4 次复制（内核↔用户往返）
sendfile(sock, fd, &off, n);              // 0 次用户态复制
```

> 🎯 **核心要点**：四种 IO 模型的分水岭是"就绪通知 vs 完成通知"——epoll（Reactor）通知"可以读"，io_uring（Proactor）连"读+复制"都完成；epoll 是 2026 主流底座，io_uring 是高性能新标准（吞吐 +60%、p99 低 25%），但低并发场景不划算、容器默认禁用；C10K 的历史启示：线程与事件循环的两难是异步编程 20 年不变的基本矛盾。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 四模型从"阻塞等待"到"完成通知"，io_uring 的 Proactor 是"内核代读"的极致；
> 2. epoll（Reactor）仍是 Nginx/Redis/Netty 的底座，io_uring（Proactor）在高吞吐/尾部延迟场景胜出（+60% 吞吐、p99 低 25%）；
> 3. 零拷贝（sendfile/io_uring）与异步叠加构成 2026 极致 IO 拼图；io_uring 非万能：低并发不划算、多租户默认禁用。
