## 1. 什么是软件过程模型

### 1.1 为什么需要过程模型

软件开发天然具有**不可见性**（代码是逻辑产物而非物理产品）和**复杂性**（需求变化、技术选型、团队协作）。没有结构化的过程，项目会陷入：

| 问题 | 表现 | 后果 |
|------|------|------|
| 需求蔓延 | 用户不断"加一个功能" | 项目无限延期、预算超支 |
| 集成地狱 | 各模块各自开发，最后才发现不兼容 | 大量返工、进度崩溃 |
| 质量不可控 | 没有阶段评审，缺陷堆积到测试阶段 | 上线后发现严重Bug |
| 沟通断层 | 需求→设计→编码之间信息失真 | 做出来的不是用户想要的 |

**软件过程模型**就是为解决这些问题而生——它规定了开发活动的**阶段划分、产出物、评审节点和角色职责**。

### 1.2 过程模型的三要素

```
过程模型 = 生命周期阶段 + 活动与产出物 + 里程碑评审
               │                  │                  │
           做什么            怎么做            什么时候检查
```

> 💡 **核心认知**：没有完美的过程模型，只有最适合当前项目上下文的模型。不同模型适合不同场景，关键在于理解每种模型的**适用条件**和**权衡取舍**。

## 2. 瀑布模型

### 2.1 定义与核心思想

瀑布模型（Waterfall Model）由 Winston Royce 于 1970 年提出，是**最经典**的软件过程模型。它强调**阶段顺序性**——每个阶段必须完成后才能进入下一阶段，如同瀑布流水自上而下。

### 2.2 六个阶段

```
┌──────────────────┐
│  需求分析阶段    │  → 产出：SRS需求规格说明书
└────────┬─────────┘
         ↓
┌──────────────────┐
│  系统设计阶段    │  → 产出：架构设计文档、详细设计文档
└────────┬─────────┘
         ↓
┌──────────────────┐
│  实现（编码）阶段 │  → 产出：代码、单元测试报告
└────────┬─────────┘
         ↓
┌──────────────────┐
│  测试阶段        │  → 产出：测试报告、缺陷记录
└────────┬─────────┘
         ↓
┌──────────────────┐
│  部署阶段        │  → 产出：部署手册、上线报告
└────────┬─────────┘
         ↓
┌──────────────────┐
│  维护阶段        │  → 产出：变更记录、问题报告
└──────────────────┘
```

| 阶段 | 核心活动 | 关键产出物 |
|------|----------|-----------|
| 需求分析 | 用户访谈、需求调研、原型验证 | SRS（Software Requirements Specification） |
| 系统设计 | 架构设计、模块划分、接口定义、数据库设计 | SDD（Software Design Document）、ER图 |
| 实现 | 编码、单元测试、代码审查 | 源码、单元测试用例 |
| 测试 | 集成测试、系统测试、验收测试 | 测试报告、Bug清单 |
| 部署 | 环境准备、发布、用户培训 | 部署手册、发布说明 |
| 维护 | Bug修复、功能增强、性能优化 | 变更请求、维护日志 |

### 2.3 优点与缺点

| 优势 | 劣势 |
|------|------|
| 阶段划分清晰，管理简单 | **变更成本极高**——后期改需求需要回退多个阶段 |
| 每个阶段有明确产出物 | 用户直到后期才能看到可运行产品 |
| 里程碑明确，易于进度跟踪 | 依赖需求完全明确——但现实中几乎不可能 |
| 文档完备，人员交接成本低 | 客户签完SRS后无法看到进展，易产生焦虑 |
| 适合大型复杂系统的高层规划设计 | 测试介入太晚，缺陷发现延迟 |

### 2.4 何时使用瀑布模型

| 适用场景 | 不适用场景 |
|----------|-----------|
| 需求极其稳定且可提前完全确定 | 需求模糊或频繁变化 |
| 项目规模大但技术成熟（如航天、银行核心） | 创新性、探索性项目 |
| 开发团队经验不足，需要严格流程约束 | 需要快速交付原型验证市场 |
| 合同制项目，需要每个阶段验收付款 | 需要持续交付的互联网产品 |

> ⚠️ **警告**：在现代互联网开发中，纯瀑布模型已经很少使用。它的主要价值在于为理解其他过程模型提供了**基准参照系**。

## 3. V模型

### 3.1 定义与核心思想

V模型（V-Model）是瀑布模型的变体，强调**测试与开发的对应关系**——每个开发阶段都有对应的测试阶段，形成"V"字形结构。

```
需求分析 ─────────────────► 验收测试
    │                          │
    │   概要设计 ──────────► 系统测试   │
    │       │                    │     │
    │       │   详细设计 ────► 集成测试 │   │
    │       │       │              │   │   │
    │       │       │   编码 ──► 单元测试 │   │
    │       │       │     │        │   │   │
    ◄───────┴───────┴─────┴────────┘   │   │
        开发阶段（左）            测试阶段（右）
```

### 3.2 验证与确认的配对

| 左侧（开发） | 验证方式 | 右侧（测试） |
|-------------|----------|-------------|
| 需求分析 | 需求是否实现？ | 验收测试（UAT） |
| 概要设计 | 架构是否合理？ | 系统测试 |
| 详细设计 | 接口是否正确？ | 集成测试 |
| 编码 | 代码是否正确？ | 单元测试 |

> 💡 **V模型的核心贡献**：它是最早明确强调"测试不是编码后的单独活动，而是贯穿整个开发过程"的模型。这种"测试左移"的思想一直延续到现代敏捷和DevOps实践。

### 3.3 适用场景

- **安全关键系统**：如医疗设备、航空航天、汽车电子，需要每个阶段的严格验证
- **合规性要求高的项目**：如金融系统审计需要每个阶段的签审记录
- **外包/合同开发**：每个阶段有明确的验收标准

## 4. 增量模型与迭代模型

### 4.1 增量模型（Incremental Model）

**核心思想**：将系统拆分为多个**增量**（Increment），每个增量交付一部分功能，逐步构建完整系统。

```
第一次发布：┌─核心登录─┐  （增量1：MVP最小可行产品）
第二次发布：┌─核心登录─┬─订单管理─┐  （增量2）
第三次发布：┌─核心登录─┬─订单管理─┬─支付系统─┐  （增量3）
第四次发布：┌─核心登录─┬─订单管理─┬─支付系统─┬─报表分析─┐  （最终系统）
```

| 特点 | 说明 |
|------|------|
| **早期价值** | 用户可以尽早使用部分功能，不必等全部完成 |
| **风险分散** | 关键功能优先交付，即使项目中止也有可用产出 |
| **反馈驱动** | 每个增量都收集用户反馈，后续增量据此调整 |
| **规模递增** | 团队可以随着增量逐步扩充 |

### 4.2 迭代模型（Iterative Model）

**核心思想**：每次迭代都对整个系统进行一轮完整的"需求-设计-编码-测试"循环，每次都比上一次更完善。

```
迭代1: ┌───────────┐  20%功能，100%完成度（粗糙但可用）
迭代2: ┌───────────────┐  50%功能，100%完成度
迭代3: ┌───────────────────┐  80%功能，100%完成度
迭代4: ┌───────────────────────┐  100%功能，100%完成度
```

### 4.3 增量 vs 迭代对比

| 维度 | 增量模型 | 迭代模型 |
|------|----------|----------|
| 每次交付 | 部分功能（子系统） | 完整功能的更优版本 |
| 关注点 | **广度**——先覆盖部分功能再到全部 | **深度**——先粗糙实现再逐步精化 |
| 用户反馈 | 新增功能的取舍 | 已有功能的改进方向 |
| 典型场景 | 按模块分批上线 | 原型逐步演进到最终产品 |

> 💡 **现代实践**：大多数成功的项目**同时采用增量与迭代**——每次迭代都交付一个增量，既增加新功能又完善已有功能。Scrum的Sprint就是这种结合的最佳实践。

## 5. 螺旋模型

### 5.1 定义与核心理念

螺旋模型（Spiral Model）由 Barry Boehm 于 1988 年提出，是**风险驱动**（Risk-Driven）的过程模型。它结合了迭代与瀑布思想，将开发过程表示为沿螺旋线前进的循环，每个循环包含四个象限。

### 5.2 四个象限

```
                       ┌───────────┐
                       │  象限1     │
                       │ 确定目标   │
                       │ 制定方案   │
                       │ 识别约束   │
                       └─────┬─────┘
                             │
         ┌───────────────────┼───────────────────┐
         │                   │                    │
         ▼                   ▼                    ▼
   ┌──────────┐                              ┌──────────┐
   │  象限4    │                              │  象限2    │
   │ 评审成果  │    螺旋前进方向               │ 风险分析  │
   │ 计划下一轮│ ──────────────────►          │ 原型验证  │
   │ 承诺继续  │                              │ 制定对策  │
   └──────────┘                              └──────────┘
         ▲                   ▲                    ▲
         │                   │                    │
         └───────────────────┼───────────────────┘
                             │
                       ┌─────┴─────┐
                       │  象限3     │
                       │ 开发验证   │
                       │ 编码测试   │
                       │ 准备交付   │
                       └───────────┘
```

| 象限 | 活动 | 关键问题 |
|------|------|----------|
| 1. 确定目标 | 明确本轮目标、备选方案、约束条件 | "我们要达成什么？有哪些方案？" |
| 2. 风险分析 | 识别风险、构建原型、评估可行性 | "最大的风险是什么？如何规避？" |
| 3. 开发验证 | 设计、编码、测试、评审 | "如何确保交付物正确？" |
| 4. 评审与规划 | 评审成果、计划下一轮、决定是否继续 | "继续投入还是终止？下一步做什么？" |

### 5.3 螺旋模型的特点

| 优势 | 劣势 |
|------|------|
| 风险管理是显式的核心活动 | 风险管理需要专业技能，对团队要求高 |
| 灵活适应变化，每轮循环可调整方向 | 没有明确的阶段终点，管理层难以跟踪进度 |
| 原型验证降低不确定性 | 合同制项目难以按螺旋模型签订 |
| 大规模、高风险项目特别适用 | 小项目过重——螺旋模型的仪式感太强 |

> 🎯 **总结**：螺旋模型最适合**高风险、高价值、探索性**的项目（如航天系统、新平台研发）。对于大多数业务应用来说，敏捷方法已经覆盖了其核心价值（迭代+风险反馈），且仪式感更轻。

## 6. 敏捷开发

### 6.1 敏捷宣言（Agile Manifesto）

2001 年，17 位轻量级方法论的倡导者在 Utah 的 Snowbird 滑雪胜地聚会，共同发布了**敏捷软件开发宣言**：

**四个核心价值观**：

| 序号 | 价值声明 | 反面（传统做法的过度） |
|------|---------|---------------------|
| 1 | **个体和互动** 高于 流程和工具 | 过度迷恋流程和工具会扼杀人的创造力 |
| 2 | **可工作的软件** 高于 详尽的文档 | 文档很重要，但最终目的是交付可用的软件 |
| 3 | **客户合作** 高于 合同谈判 | 合同无法覆盖所有变化，持续合作才能成功 |
| 4 | **响应变化** 高于 遵循计划 | 计划必须灵活，变化是竞争优势的源泉 |

> 💡 **关键理解**：敏捷宣言不是说"不要流程、不要文档"，而是说有价值的流程和文档应该**服务于**人、软件、合作和响应变化——而不是反过来。

### 6.2 敏捷的 12 条原则

| 编号 | 原则 | 核心理念 |
|------|------|---------|
| 1 | 最高优先级是**通过尽早和持续交付有价值的软件**来满足客户 | 价值优先于任务完成 |
| 2 | 欢迎需求变化，即使是开发后期——敏捷利用变化**为客户创造竞争优势** | 变化是机会而非威胁 |
| 3 | **频繁交付可工作的软件**，交付周期从几周到几个月，越短越好 | 短周期、快反馈 |
| 4 | 业务人员和开发者**每天都在项目中一起工作** | 打破业务与技术壁垒 |
| 5 | 围绕**有自驱力的个体**构建项目，给他们环境和支持，信任他们能完成工作 | 赋能而非控制 |
| 6 | 面对面的交谈是传递信息**最有效**的方式 | 文档不如对话 |
| 7 | **可工作的软件**是衡量进度的**首要**标准 | 代码为王，而非PPT |
| 8 | 敏捷过程倡导**可持续的开发**——赞助方、开发者和用户应该能长期保持恒定的节奏 | 防止团队 burnout |
| 9 | 对**技术卓越和良好设计**的持续关注增强敏捷性 | 好代码是敏捷的基础 |
| 10 | **简单**——最大化不做的工作的艺术——是根本 | 少即是多 |
| 11 | 最好的架构、需求和设计来自**自组织团队** | 自上而下不如自驱动 |
| 12 | 团队定期反省如何提升效率，并**调整行为** | 持续改进文化 |

### 6.3 敏捷 vs 瀑布：核心差异

| 维度 | 瀑布模型 | 敏捷开发 |
|------|---------|---------|
| **需求** | 提前完全确定 | 持续涌现和迭代细化 |
| **交付** | 一次交付完整产品 | 多次交付增量功能 |
| **变更态度** | 变更=风险，需严格控制 | 变更=机会，主动拥抱 |
| **团队结构** | 角色划分明确（分析师→设计师→开发→测试） | 跨职能自组织团队 |
| **客户参与** | 只在需求阶段和验收阶段 | 全程持续参与 |
| **文档** | 大量文档，每个阶段有正式产出物 | "刚好够用"的文档 |
| **成功标准** | 按计划、按预算、按规格 | 交付用户价值、快速响应变化 |
| **管理风格** | 命令-控制（Command & Control） | 服务型领导（Servant Leadership） |

> ⚠️ **实践中的敏捷误区**：
> - 敏捷 != 没有计划——敏捷有计划，只是计划是持续调整的
> - 敏捷 != 没有文档——敏捷写"刚好够用"的文档
> - 敏捷 != 没有架构——敏捷强调技术卓越和良好设计
> - 敏捷 != 可以随便延期——Sprint时间盒是刚性的

## 7. Scrum框架

> 💡 本节提供 Scrum 的核心概念速览。详细的 Scrum 实战内容请参考 **`../工程与项目能力/04-敏捷开发与Scrum实战.md`**。

### 7.1 Scrum三角色

| 角色 | 职责 | 核心能力 |
|------|------|---------|
| **Product Owner（PO）** | 定义产品Backlog、排优先级、最大化产品价值 | 业务洞察力、决策力 |
| **Scrum Master（SM）** | 确保Scrum流程正确执行、消除障碍、教练团队 | 引导力、服务型领导 |
| **开发团队（Dev Team）** | 自组织完成Sprint Backlog、交付潜在可交付增量 | 技术能力、自管理能力 |

### 7.2 Scrum五事件

```
Sprint（时间盒：1-4周，通常2周）
├── Sprint Planning     ← 确定"做什么"和"怎么做"
├── Daily Scrum         ← 每日15分钟站会：昨天做了什么/今天做什么/有什么阻碍
├── Sprint Review       ← 向干系人演示成果，收集反馈
└── Sprint Retrospective ← 团队内部回顾：哪些做得好/哪些可以改进/下个Sprint做什么
```

### 7.3 Scrum三工件

| 工件 | 描述 | 谁负责 |
|------|------|--------|
| **Product Backlog** | 产品需求的优先级列表，持续演化的待办清单 | PO负责排序 |
| **Sprint Backlog** | 当前Sprint要完成的任务列表，由PB拆分而来 | 开发团队自管理 |
| **Increment** | 每个Sprint结束时交付的"潜在可发布功能增量" | 团队共同负责 |

> 💡 Scrum本质上是一个**经验主义过程控制**框架——通过透明度（Transparency）、检查（Inspection）、适应（Adaptation）三个支柱来管理不确定性。

## 8. Kanban方法

### 8.1 核心思想

Kanban（看板）源自丰田生产系统（TPS），由 David Anderson 引入软件开发。与Scrum不同，Kanban不规定固定的时间盒（Sprint），而是**基于流程的持续交付**。

### 8.2 核心实践

| 实践 | 说明 | 效果 |
|------|------|------|
| **可视化工作流** | 用看板墙展示所有工作项及其状态 | 让瓶颈一目了然 |
| **限制在制品（WIP）** | 每个列设置最大数量的工作项上限 | 防止多任务切换带来的效率损失 |
| **管理流动** | 关注工作项从"待办"到"完成"的流动速度 | 持续优化交付周期 |
| **显式化流程规则** | 明确每个列的准入/准出标准 | 减少团队沟通成本 |
| **协作改进** | 基于数据（如累积流图）持续优化流程 | 形成度量驱动的改进文化 |

### 8.3 典型看板墙示例

```
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│  待办     │  分析中   │  开发中   │  测试中   │  已完成   │
│ (Backlog) │ (WIP:3)  │ (WIP:3)  │ (WIP:2)  │  (Done)   │
├──────────┼──────────┼──────────┼──────────┼──────────┤
│  US-005   │  US-003  │  US-002  │  US-001  │  US-000   │
│  US-006   │          │  Bug-012 │          │           │
│  US-007   │          │          │          │           │
└──────────┴──────────┴──────────┴──────────┴──────────┘
      ↑              ↑                    ↑
   优先级队列      WIP达到上限        瓶颈（拥堵）
                   不能再拉入        测试拖累整个流水线
```

### 8.4 Scrum vs Kanban 对比

| 维度 | Scrum | Kanban |
|------|-------|--------|
| **节奏** | 固定时间盒（Sprint） | 持续流动，无固定迭代 |
| **角色** | PO + SM + Dev Team（三角色） | 不规定角色，保留现有角色 |
| **变更策略** | Sprint内不引入新需求 | 随时可拉入新工作项（前提是未超WIP） |
| **度量指标** | 速率（Velocity）、燃尽图 | 前置时间（Lead Time）、吞吐量（Throughput） |
| **适合团队** | 需要结构化的团队 | 运维/支持类团队、成熟的自组织团队 |

## 9. DevOps

### 9.1 定义与核心思想

DevOps 不是工具也不是职位，而是一种**文化、原则与实践的结合体**，旨在打破开发（Dev）和运维（Ops）之间的壁垒，实现快速、可靠的软件交付。

> 💡 **DevOps不是开发人员的Ops化**——而是开发与运维通过共同目标（快速安全交付）和共享工具（CI/CD、监控、IaC）达成协作。

### 9.2 CI/CD 流水线

完整的 DevOps 流水线如下：

```
编码 ──► 构建 ──► 测试 ──► 打包 ──► 部署到Staging ──► 自动化测试 ──► 部署到生产
 │        │        │         │          │                  │              │
 │    CI（持续集成）           │    CD（持续交付/部署）                 │
 │                           │                                       │
 └── 开发者Push代码 ─────────┘        └── 经过审批后自动部署到生产 ──┘
     自动触发构建和测试                     （持续部署）或手动触发（持续交付）
```

| 阶段 | 工具示例 | 活动 |
|------|---------|------|
| 编码 | IDE + Git | 特性分支开发，代码审查 |
| 构建 | Maven/Gradle | 编译、依赖解析、静态代码分析 |
| 测试 | JUnit + Mockito + Selenium | 单元测试、集成测试、UI测试 |
| 打包 | Docker + Jib | 镜像构建、版本标记 |
| 部署 | Jenkins + Kubernetes + ArgoCD | 自动部署到目标环境 |
| 运维 | Prometheus + Grafana + ELK | 监控、日志、告警、可观测性 |

### 9.3 CALMS 框架

CALMS 是评估 DevOps 成熟度的经典框架：

| 维度 | 含义 | 实践体现 |
|------|------|---------|
| **C**ulture | 文化：协作而非对立 | 共享责任目标，消除指责文化（Blame-Free） |
| **A**utomation | 自动化：减少人工操作 | CI/CD、基础设施即代码（IaC）、自动化测试 |
| **L**ean | 精益：消除浪费，优化流动 | 限制WIP、小批量交付、价值流映射 |
| **M**easurement | 度量：用数据驱动改进 | DORA指标（部署频率、变更前置时间、变更失败率、MTTR） |
| **S**haring | 共享：知识经验跨团队流动 | 共享代码所有权、运维轮值、事故复盘共享 |

### 9.4 DORA 核心指标

| 指标 | 精英级 | 高绩效级 | 中绩效级 | 低绩效级 |
|------|--------|---------|---------|---------|
| **部署频率** | 按需（每日多次） | 每周一次到每月一次 | 每月一次到每季度一次 | 每季度一次以上 |
| **变更前置时间** | 小于1小时 | 1天到1周 | 1周到1个月 | 大于1个月 |
| **变更失败率** | 0%-5% | 5%-10% | 10%-20% | 20%以上 |
| **故障恢复时间（MTTR）** | 小于1小时 | 小于1天 | 小于1周 | 大于1周 |

> 🎯 **DevOps的终极目标**：在保障质量和安全的前提下，实现**快速流动**（Fast Flow of Changes Through the System）。

## 10. CMMI成熟度模型

### 10.1 定义

CMMI（Capability Maturity Model Integration，能力成熟度模型集成）由美国卡内基梅隆大学软件工程研究所（SEI）开发，是评估和改进组织软件开发过程能力的框架。

### 10.2 五个成熟度级别

```
Level 5: 优化级（Optimizing）
    └── 持续改进，量化反馈驱动过程优化
         ↑
Level 4: 量化管理级（Quantitatively Managed）
    └── 用统计和质量控制方法管理过程
         ↑
Level 3: 已定义级（Defined）
    └── 组织级标准过程已建立，项目可裁剪使用
         ↑
Level 2: 已管理级（Managed）
    └── 项目级过程有规划、有监控、有评审
         ↑
Level 1: 初始级（Initial）
    └── 过程不可预测，依赖个人英雄主义，混乱无序
```

| 级别 | 名称 | 核心特征 | 关键实践 |
|------|------|---------|---------|
| **1** | 初始级（Initial） | 过程不可预测，成功依赖个人能力 | 无—仅需识别差距 |
| **2** | 已管理级（Managed） | 项目级过程制度化，有基础管理 | 需求管理、项目计划、配置管理、度量分析 |
| **3** | 已定义级（Defined） | 组织级标准过程，可裁剪应用 | 组织过程定义、组织培训、集成项目管理 |
| **4** | 量化管理级（Quantitatively Managed） | 用统计过程控制管理质量和性能 | 组织过程绩效、量化项目管理 |
| **5** | 优化级（Optimizing） | 持续改进，因果分析驱动过程优化 | 组织创新与部署、因果分析与解决 |

### 10.3 CMMI 实践领域（Process Areas）

CMMI 将过程域分为四类：

| 类别 | 示例过程域 |
|------|-----------|
| **过程管理** | 组织过程定义、组织培训、组织过程绩效 |
| **项目管理** | 项目计划、项目监控、风险管理、集成项目管理 |
| **工程** | 需求开发、技术解决方案、产品集成、验证、确认 |
| **支持** | 配置管理、度量与分析、决策分析与解决、原因分析与解决 |

### 10.4 对 CMMI 的辩证看待

| 肯定 | 批评 |
|------|------|
| 为组织过程改进提供了系统化的路线图 | 认证导向容易导致"为过级而过级"，形式大于实质 |
| 大型招标中（如政府、军工）CMMI级别是硬性门槛 | 过度文档化，仪式感重，不适用于创业团队 |
| 量化管理思想有借鉴价值 | 与敏捷/精益思想在某些地方存在张力 |

> 💡 **现代实践**：越来越多的组织将 CMMI 的思想融入敏捷/DevOps 实践中——比如用 CMMI 的度量思想来驱动 DevOps 的 DORA 指标改进，而不是追求认证本身。

## 11. 模型对比总表

### 11.1 基础信息对比

| 维度 | 瀑布 | V模型 | 增量/迭代 | 螺旋 | 敏捷/Scrum | Kanban | DevOps |
|------|------|-------|----------|------|-----------|--------|--------|
| **提出年份** | 1970 | 1980s | 1970s | 1988 | 2001 | 2007（引入IT） | 2009 |
| **核心驱动力** | 计划驱动 | 验证驱动 | 功能/反馈驱动 | **风险驱动** | 价值驱动 | 流动驱动 | 自动化驱动 |
| **变更适应性** | 极低 | 低 | 中 | 高 | 高 | 高 | 高 |
| **用户参与度** | 低 | 低 | 中 | 中 | **持续参与** | 持续参与 | 持续 |
| **文档完备度** | 极高 | 高 | 中 | 中 | **刚好够用** | 轻量 | 轻量+自动化 |
| **风险处理** | 隐式（靠评审） | 隐式（靠验证） | 中（早期交付） | **显式核心** | 隐式（迭代降低） | 显式（瓶颈可见） | 显式（自动化降低） |

### 11.2 适用场景对比

| 模型 | 适合项目特点 | 典型领域 |
|------|-------------|---------|
| **瀑布** | 需求稳定、规模大、技术成熟、合同制 | 政府系统、航天国防、银行核心 |
| **V模型** | 安全关键、合规要求高、需要严格验证 | 医疗器械、汽车电子、嵌入式 |
| **增量模型** | 需要早期部分上线、模块间耦合低 | 电商平台、SaaS（分模块上线） |
| **螺旋模型** | 高风险、探索性、需要原型验证 | 新平台研发、航天系统 |
| **Scrum** | 需求不确定、需要快速迭代反馈 | 互联网产品、企业业务系统 |
| **Kanban** | 运维类、支持类、事件驱动的工作 | IT运维、服务台、持续交付团队 |
| **DevOps** | 需要高频交付、自动化程度高 | SaaS/云原生、微服务架构 |

### 11.3 团队规模与沟通需求

| 模型 | 推荐团队规模 | 沟通频率 | 管理开销 |
|------|-------------|---------|---------|
| 瀑布 | 大型团队（20+） | 阶段节点评审 | 高 |
| V模型 | 中大型团队 | 阶段节点+测试配对 | 高 |
| 增量/迭代 | 中型团队 | 每轮增量/迭代 | 中 |
| 螺旋 | 中型团队 | 每轮循环评审 | 高 |
| Scrum | 5-9人/小队 | **每日站会** | 中 |
| Kanban | 不限 | 持续（无固定频率） | 低 |
| DevOps | 不限（跨团队文化） | 持续（自动化驱动） | 中 |

## 12. 如何选择过程模型

### 12.1 决策矩阵

选择过程模型时，需从以下五个维度评估：

| 决策因素 | 倾向传统模型（瀑布/V/螺旋） | 倾向敏捷模型（Scrum/Kanban/DevOps） |
|----------|---------------------------|-----------------------------------|
| **需求稳定性** | 需求完全明确，几乎不变 | 需求不明确，预期频繁变化 |
| **项目规模** | 超大规模（100+人，2+年） | 中小规模（<50人，<1年） |
| **团队分布** | 团队分散在不同地点 | 团队集中办公（Co-located） |
| **风险容忍度** | 低风险容忍度，追求确定性 | 中高风险容忍度，拥抱变化 |
| **客户参与度** | 客户无法频繁参与 | 客户愿意并与团队紧密协作 |
| **交付频率要求** | 低频（季度/半年一次） | 高频（周/双周一次） |
| **合规/审计要求** | 需要大量文档证据 | 轻量级合规 |

### 12.2 混合模型

在实践中，大多数项目使用的是**混合模型**（Hybrid Model）：

```
敏捷的高层 + 瀑布的底层
│
├── 需求层面：用Scrum的Product Backlog管理（敏捷）
├── 架构层面：前期进行充分的架构设计（趋向瀑布）
├── 开发层面：Sprint迭代交付（敏捷）
├── 合规层面：关键节点有正式评审（趋向瀑布）
└── 部署层面：CI/CD自动化流水线（DevOps）
```

### 12.3 常见行业选择建议

| 行业 | 推荐模型 | 原因 |
|------|---------|------|
| 互联网/电商 | Scrum + DevOps | 快速迭代、高频发布、A/B测试 |
| 金融核心系统 | 瀑布为主 + 敏捷外围 | 核心稳定 + 外围快速迭代 |
| 医疗设备/嵌入式 | V模型（或含螺旋） | 安全性验证是关键 |
| 政府/大型企业 | CMMI + 裁剪敏捷 | 合规性 + 一定灵活性 |
| 创业公司（早期） | Lean Startup + Scrum | 快速验证产品市场匹配（PMF） |
| 云原生/SaaS平台 | DevOps + Kanban | 持续交付、基础设施即代码 |

> 🎯 **最终建议**：不要教条地选择模型——理解每个模型的**核心思想**（螺旋的风险管理、Scrum的自组织、Kanban的流动、DevOps的自动化），将它们作为工具箱中的工具，根据项目上下文**裁剪组合**出最适合的过程。

### 12.4 过程评估与改进循环

无论选择何种模型，都应建立持续改进机制：

```
┌──────────────┐
│  评估现状     │ ← DORA指标、团队健康度、交付满意度
└──────┬───────┘
       ↓
┌──────────────┐
│  识别瓶颈     │ ← 价值流映射（Value Stream Mapping）
└──────┬───────┘
       ↓
┌──────────────┐
│  设计改进     │ ← 小步实验（Kaizen改善）
└──────┬───────┘
       ↓
┌──────────────┐
│  实施度量     │ ← 用数据验证改进效果
└──────┬───────┘
       ↓
      (循环)
```

> 🎯 **本章核心**：软件过程模型是管理软件开发复杂性的工具，不是束缚团队的锁链。理解每种模型的**适用条件和核心思想**，根据项目上下文灵活裁剪，才是真正的工程能力。
