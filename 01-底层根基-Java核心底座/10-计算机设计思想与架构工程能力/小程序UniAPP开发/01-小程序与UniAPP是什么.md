## 1. 小程序生态

小程序是「移动端轻应用」——**免安装、扫即用、平台托管**的移动应用形态：微信小程序（用户量最大）、支付宝小程序（交易场景）、抖音小程序（内容电商）、百度/快手/京东/小红书等——**「小程序是国内移动流量的重要入口」**——对后端开发者而言，小程序是「后端 API 的高频消费端」：登录、商品、订单、支付——**「小程序 + 后端」是国内业务系统的经典组合**。

**小程序的运行模型**（与网页的本质差异）：**双线程模型**——逻辑层（JSCore——跑 JS）与视图层（WebView——渲染 UI）分离，通过 **setData** 通信——**「没有 DOM、不能直接操作视图、setData 有性能代价」**——这是小程序开发的底层约束（08 篇性能）；**平台托管**——代码在平台审核后托管运行（发布流程——09 篇）；**平台限制**——包体积（微信主包 2MB）、API 权限（平台 API 需申请）——**「小程序是在平台规则内开发」**。

## 2. UniAPP 的定位

UniAPP（DCloud 出品）是**跨端开发框架**——**「一套 Vue 代码，编译到多端」**：10+ 小程序平台（微信/支付宝/抖音/百度/快手/QQ/京东/小红书）+ H5 + App（iOS/Android）+ 鸿蒙——**核心价值：多端覆盖的成本摊薄**——「一次开发多端上架」vs「每端原生开发」——**「跨端框架的本质是编译器的差异」**——同一套代码按目标平台编译成对应形态（小程序编译成小程序代码、H5 编译成网页、App 编译成原生壳）。

**UniAPP 的技术栈**（2026）：**Vue 3 语法**（组合式 API——[[../../10-前端知识拓展/Vue/00-Vue总览与核心概念|Vue 体系]] 的语法基础）+ **uni API**（平台差异封装的统一 API——`uni.request` 等）+ **Vite 构建**——**「会 Vue 就会 uni-app」**是它的学习优势（前端人才池大）。

## 3. 2026 基线

**uni-app 4.x**（4.35/4.87 线）+ **Vue 3.4** + **Vite**——**官方推荐技术栈：uni-app 4.x + Vue3 Setup + Vite + Pinia + SCSS + uni-ui**；HBuilderX 迭代到 5.x（2026-03 版本 5.06）。

**Vue2 淘汰**：2026 下半年 Vue2 停止新功能迭代；微信小程序收紧 Webpack 老旧基座审核；**Vue2 新项目被禁止启动**——存量 Vue2 项目尽快迁移 Vue3——**「2026 新项目写 Vue2 是错误」**（与 [[../../10-前端知识拓展/Vue/00-Vue总览与核心概念|Vue 体系]] 的版本线一致）。**鸿蒙适配**：uni-app 官方支持编译 HarmonyOS NEXT（ArkTS）——多端版图新增鸿蒙端。

## 4. uni-app x：下一代引擎

**uni-app x** 是架构级的新引擎（HBuilderX 3.9+ 支持，2026 已正式版）：**核心是抛弃 WebView 渲染**——**uts 语言**（跨平台强类型语言——编译到 JS/Web 与小程序、Kotlin/Android、Swift/iOS、ArkTS/鸿蒙）；**uvue 渲染引擎**（兼容 Vue 语法的原生渲染——**蒸汽模式 Vapor 2026 起逐步替代 VDOM 模式**——免 vnode 创建，渲染性能比原生快 2-3 倍——实测 4050 个节点：鸿蒙原生 798ms vs 蒸汽 280ms）；**性能优势**——启动快 40%+、零跨层通信损耗、复杂动画 60fps——**「性能接近 Flutter」**。

**选型建议（2026）**：**新建商用 App 项目 → uni-app x**（原生渲染性能）；**小程序/H5 为主 → 传统 uni-app（Vue3）**（生态成熟、小程序端支持完善——x 的小程序端刚上线）；**存量 Vue 项目 → 增量迁移**（语法改动率 ≤18%）；**重度 3D/音视频编辑 → 不建议**（x 生态尚在完善）——**「按场景选引擎，不按流行选」**。

## 5. 与替代方案的对比

| 框架 | 定位 | 对比 UniAPP |
|------|------|------------|
| 原生小程序 | 单平台开发 | 性能最好、生态最全，但每端一套代码 |
| Taro | React 语法跨端 | 技术栈不同（React vs Vue）——Vue 团队选 uni-app |
| Flutter | 原生渲染跨端 | 性能最强，但 Dart 语言成本高、小程序支持弱 |
| RN | 原生渲染跨端 | 同 Flutter 定位，小程序支持弱 |
| uni-app x | 原生渲染 + 多端 | DCloud 的下一代——小程序 + App 兼顾 |

**选型判断**：**国内多端覆盖（小程序为主）→ uni-app（Vue3）**；**App 性能优先 + 也要小程序 → uni-app x**；**React 技术栈 → Taro**；**只做 App 且追求极致性能 → Flutter**——**「uni-app 的独特价值是『小程序多端 + H5 + App』的覆盖广度」**。

**生态与社区现实**（选型与学习的参考）：**DCloud 生态**——HBuilderX/uni-app/uni-app x 一体（官方工具链）、插件市场（uni_modules——组件/模板/插件丰富）；**社区规模**——国内跨端框架的第一梯队（教程/问答/招聘需求量大——「会 uni-app 是国内前端岗位的常见要求」）；**学习路径**——Vue 基础（[[../../10-前端知识拓展/Vue/00-Vue总览与核心概念|Vue 体系]]）→ uni-app 语法与 API（本体系）→ 实战项目（10 篇）——**「生态成熟度是选型的重要维度」**——「选框架不只看技术，看生态能给你什么」。

**小程序与后端开发者的关系**（本体系的服务对象视角）：**小程序是后端 API 的高频消费端**——登录（微信 code → 后端 openid）、业务数据（RESTful 接口）、支付（后端下单签名）——**「后端开发者写小程序 = 把自己设计的 API 用一遍」**——这个视角的学习价值：**API 设计好不好，小程序端最敏感**（字段命名、错误码、分页契约——「写一遍消费端就懂 API 设计」）；**小程序是后端的「验收客户端」**（接口联调、问题复现、性能感知）——**「后端会小程序开发 = 能端到端验证自己的设计」**——本体系以「后端视角的前端拓展」定位（01 篇的读者视角）。

## 6. 五条边界

**不是原生开发**——App 端是壳 + 原生渲染（x）/WebView（传统）——重度原生能力（复杂硬件交互）要原生插件。

**不替代后端**——小程序是消费端——业务逻辑与数据在后端（本体系的另一半是后端 API）。

**不保证零适配**——跨端要条件编译处理平台差异（08 篇）——「零适配」是宣传语。

**不受平台之外控制**——审核、API 权限、平台规则说了算——「平台是裁判」。

**不解决重度场景**——3D 渲染、音视频编辑、游戏——选原生或专用引擎。
