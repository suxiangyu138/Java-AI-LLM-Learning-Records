## 1. 网络请求基础

`uni.request` 是小程序的 HTTP 客户端（axios 的小程序版——[[../../10-前端知识拓展/Axios%20异步请求、Promise%20基础/01-Axios核心用法与后端对标|Axios 体系]] 的 uni 形态）：

```js
uni.request({
  url: 'https://api.example.com/api/orders',
  method: 'GET',
  header: { 'Authorization': 'Bearer xxx' },
  success: (res) => { console.log(res.data) },
  fail: (err) => { console.error(err) }
})
```

**基础要点**：**success/fail 回调**（非 Promise——封装时转 Promise）；**`res.data` 是响应体**（后端返回的 JSON）；**header 传凭证**（Token 体系——[[../../10-前端知识拓展/Token/00-Token总览|Token 鉴权]] 的 Bearer 头）；**域名限制**——**小程序请求域名必须在小程序后台配置**（`request 合法域名`——**「开发环境可关校验，正式环境必须配置」**——09 篇上线配置）。

## 2. 统一封装

**「裸调 uni.request 是工程底线问题」**——统一封装（类似 axios 封装——[[../../10-前端知识拓展/Axios%20异步请求、Promise%20基础/03-前端请求实战模式|请求实战]]）的四个职责：

```js
// api/request.js —— 统一请求封装
const BASE_URL = 'https://api.example.com/api'

export function request(options) {
  return new Promise((resolve, reject) => {
    uni.request({
      url: BASE_URL + options.url,
      method: options.method || 'GET',
      data: options.data,
      header: {
        'Authorization': getToken() ? `Bearer ${getToken()}` : '',
        ...options.header
      },
      success: (res) => {
        if (res.statusCode >= 200 && res.statusCode < 300) {
          resolve(res.data)          // 成功：返回数据
        } else {
          handleError(res)           // 业务/状态码错误统一处理
          reject(res)
        }
      },
      fail: (err) => { handleNetworkError(err); reject(err) }
    })
  })
}
// 业务调用
const orders = await request({ url: '/orders', method: 'GET' })
```

**封装的四个职责**：**baseURL 统一**（环境切换只改一处——dev/test/prod）；**Token 统一注入**（每次请求自动带——登录态）；**成功/失败统一判定**（状态码语义——[[../../09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 状态码]]）；**错误统一处理**（401 跳登录、网络错误提示——下节）。

## 3. 登录与 Token 流程

小程序登录的 Token 流程（微信小程序标准姿势——与 [[../../10-前端知识拓展/Token/00-Token总览|Token 体系]] 配合）：

```text
小程序                      后端
  │  wx.login() 拿 code       │
  ├──POST /auth/login {code}──→│  code 换 openid → 签发 JWT
  ←──{accessToken, refreshToken}──│
  │  存储 Token（storage）     │
  │  请求带 Bearer Token ─────→│  验签 → 业务数据
  │  401 → 刷新 Token ───────→│  refresh 轮换
```

**微信登录的要点**：**`uni.login()` 拿临时 code**（几分钟有效）→ 后端拿 code 换 `openid`（用户唯一标识——后端调微信接口——**code 换 openid 必须后端做**——appid/secret 不能暴露在小程序）；**后端签发 JWT**（双 Token——access 短 TTL + refresh 轮换——[[../../10-前端知识拓展/Token/05-双Token模式|双 Token 模式]]）；**前端存储 Token**（`uni.setStorageSync`——**access 短存、refresh 的安全考量**——敏感场景用「内存 + 静默刷新」或安全存储）；**401 统一处理**——刷新 Token 重试原请求（封装层——[[../../10-前端知识拓展/Token/03-登录认证流程|登录认证流程]] 的拦截器模式）。

## 4. 与后端契约对接

小程序与后端的对接纪律（后端视角的配合）：**契约一致**——接口文档（OpenAPI/Swagger——[[../../../01-底层根基-Java核心底座/09-计算机工具与常识补全/Swagger/00-Swagger总览|Swagger 体系]]）是双方依据——「字段名、错误码、状态码以契约为准」；**统一返回格式**——小程序解析 `res.data` 的结构（成功包 data、错误包错误码——[[../../10-前端知识拓展/RESTful%20接口设计、统一返回格式/00-RESTful接口设计知识体系总览|统一返回格式]]）；**错误码映射**——后端的业务错误码 → 小程序的提示文案（「订单不存在」→ toast——错误码字典集中管理）。

**对接的排障**：**Network 面板看请求**（微信工具——请求发了没、状态码、响应体）；**与后端联调的常见问题**——跨域（H5 端——[[../../09-Web开发全流程/Web%20高阶知识/04-跨域与浏览器安全机制|CORS]]）、域名未配置（小程序——第 1 节）、参数格式（JSON 序列化差异）。

## 5. 错误处理

错误处理的完整姿势（封装层统一）：**网络错误**（fail 回调——超时/断网）——提示「网络异常，请重试」；**HTTP 错误**（状态码非 2xx）——按状态码处理：**401**（Token 失效——刷新重试/跳登录）、**403**（无权限——提示）、**404/500**（服务端问题——通用提示）；**业务错误**（2xx 但业务失败——错误码）——按错误码提示——**「错误处理的层级：网络 → HTTP → 业务」三层都要有**（[[../../10-前端知识拓展/Token/09-安全红线与攻防|Token 安全]] 的 401 处理纪律）。

## 6. 安全注意

小程序端的安全注意（前端侧能做的）：**HTTPS 必须**（请求域名必须 HTTPS——小程序强制）；**Token 不落日志**（console.log 不打凭证）；**敏感信息不存明文**（storage 的敏感数据考量——Token 短存）；**防越权靠后端**（对象级授权——[[../../10-前端知识拓展/Token/09-安全红线与攻防|BOLA 防线]]——前端不做安全决策）；**appid/secret 不进前端**（code 换 openid 在后端——第 3 节）。

**联调与排障的完整流程**（后端开发者的联调习惯迁移）：**第一查 Network**——请求发了没（URL/域名对没对）、状态码（4xx/5xx——[[../../09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|状态码语义]]）、响应体（后端返回什么——字段名对没对）；**第二查参数**——请求参数与契约是否一致（字段名/类型/格式——「参数错了后端 400 常见」）；**第三查后端日志**——请求到没到后端（后端日志看请求——「前端发了后端没收到 = 网络/网关层问题」）；**第四查环境**——域名配置（正式环境）、HTTPS（证书）、跨域（H5 端）——**「联调排障四查：Network → 参数 → 后端日志 → 环境」**——与后端联调的问题 80% 在前两步。

## 7. 常见坑

**坑一：裸调 uni.request**。每处重复 baseURL/Token/错误处理——统一封装。

**坑二：域名没配**。正式环境请求失败——小程序后台配置 request 合法域名。

**坑三：code 换 openid 放前端**。secret 暴露——必须后端。

**坑四：401 不统一处理**。每个请求自己写刷新——封装层统一。

**坑五：Token 存明文 storage**。XSS/逆向风险——Token 存储策略（敏感场景内存）。

**坑六：错误只提示不分类**。网络/HTTP/业务三层不区分——统一错误处理。

**坑七：对接不按契约**。字段名猜、错误码猜——OpenAPI 契约。

**坑八：并发请求的竞态**。「快速点击/重复触发」多个请求乱序返回——列表页「先发的后到」覆盖新数据——请求竞态处理（请求序号/取消旧请求——「竞态是列表页高频 bug」）。

**坑九：loading 状态不管理**。每页自己写 loading 布尔——请求封装层统一 loading（showLoading 配对——「loading 的集中管理」）。
