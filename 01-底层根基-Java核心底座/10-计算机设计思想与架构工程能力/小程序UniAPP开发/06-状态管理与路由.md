## 1. 为什么需要状态管理

**跨页面共享状态是页面开发的常态**——用户信息（多个页面要显示）、登录态（所有请求要用）、购物车（多页面操作同一份数据）——**「每个页面自己存一份」的问题**：数据不同步（A 页改了 B 页不知道）、重复请求（每页都拉一遍）、状态分散（找不到「用户信息在哪」）。**状态管理（Pinia）解决「跨页面的单一数据源」**——一份状态、各页面读写同一份——**「状态管理是『多个页面操作同一份数据』的工程方案」**（[[../../10-前端知识拓展/Vue/00-Vue总览与核心概念|Vue 体系]] 的响应式状态）。

## 2. Pinia 基础

Pinia（Vue3 官方推荐状态管理——替代 Vuex）三件套：

```js
// stores/user.js —— 用户状态
import { defineStore } from 'pinia'

export const useUserStore = defineStore('user', {
  state: () => ({ token: '', userInfo: null }),
  getters: { isLogin: (s) => !!s.token },
  actions: {
    setLogin(token, userInfo) { this.token = token; this.userInfo = userInfo },
    logout() { this.token = ''; this.userInfo = null }
  }
})
```

```vue
<!-- 页面中使用 -->
<script setup>
import { useUserStore } from '@/stores/user'
const userStore = useUserStore()
console.log(userStore.userInfo)        // 读状态
userStore.setLogin(token, user)        // 改状态（action）
</script>
```

**三件套语义**：**state**（数据）、**getters**（派生——`isLogin`）、**actions**（操作——登录/登出）——**「页面通过 store 读写，不直接碰 localStorage」**——状态与存储分离（持久化——第 6 节）。

## 3. 用户状态与登录态

用户状态的设计（登录态的核心状态）：**user store 的职责**——token、userInfo、登录/登出动作——**「登录态的单一数据源」**：登录成功 → `setLogin`（写 store + 存 storage）；请求 401 → 刷新（05 篇）；登出 → `logout`（清 store + 清 storage + 跳登录页）。**「状态与存储的分工」**——store 是「运行时的单一数据源」、storage 是「持久化」——**「启动时从 storage 恢复 store」**（App.vue 的 onLaunch 或 store 初始化——「页面刷新/重启后登录态还在」靠持久化恢复）。

## 4. 路由与传参

路由的完整姿势（04 篇导航 API 的展开）：**页面间传参三姿势**——**url 参数**（小数据：id、type——`uni.navigateTo({ url: '/pages/detail/detail?id=123' })`——onLoad options 接收——**「url 传参是默认姿势」**）；**全局状态**（大数据/对象——详情数据放 store——避免 url 超长与序列化问题）；**storage**（跨页面的大数据——草稿、表单——「场景数据暂存」）。**路由的组合**——列表 → 详情（navigateTo）、登录 → 首页（redirectTo——不留登录页在栈里）、tab 切换（switchTab）。

**路由的工程注意**：**参数编码**（中文/特殊字符 encodeURIComponent——url 传参的乱码坑）；**参数长度**（url 长度限制——大数据走状态）；**返回传值**（详情页修改后返回列表要刷新——`uni.$emit`/`getOpenerEventChannel` 或 onShow 刷新（03 篇）——**「返回刷新用 onShow」是简单方案**。

## 5. 登录态守卫

**登录态守卫——「未登录不能访问的页面」**：**实现姿势**——页面 onShow 检查 `isLogin`（简单场景——每个受保护页面检查）；**统一拦截**（封装层——请求 401 统一跳登录——05 篇——**「请求层守卫是底线」**）；**路由层守卫**（H5 端可配 Vue Router 守卫；小程序端没有统一路由守卫——页面级检查或封装跳转函数——**「小程序的路由守卫 = 请求 401 拦截 + 页面级检查」**）。

**登录后回跳**——「从详情页被踢到登录，登录后回到详情页」——登录页记住来源（`uni.$emit` 或 storage 存 redirect 目标——登录成功 `navigateBack` 或跳回目标页）——**「登录回跳是体验的细节」**（Token 体系的登录流程——[[../../10-前端知识拓展/Token/03-登录认证流程|登录认证流程]]）。

## 6. 状态持久化

**状态持久化——「重启后状态还在」**：**持久化的对象**——token、用户信息（登录态）；**不持久化的对象**——临时数据（购物车草稿看场景）；**实现**——手动持久化（action 里 setLogin 时同时写 storage——**显式可控**）或 Pinia 持久化插件（`pinia-plugin-persistedstate`——自动同步 storage）；**安全考量**——**token 的持久化策略**（05 篇——敏感场景「内存 + 静默刷新」不落 storage——持久化与安全的权衡——[[../../10-前端知识拓展/Token/04-Token的存储与传输|Token 存储]] 的小程序版）。

**多 store 的组织**（项目规模增长后的状态治理）：**按模块分 store**——`user`（用户/登录态）、`cart`（购物车）、`order`（订单状态）——「一个 store 一个业务域」（与后端 Service 划分同构）；**store 间的协作**——store 可以引用其他 store（`useUserStore()` 在另一个 store 里调用——「跨 store 读状态」）；**store 的边界**——「页面级临时状态不进 store」（表单草稿、列表筛选条件——组件内 ref 就够——**「store 只放跨页面共享的状态」**——「状态放错层级 = 状态管理混乱的开始」）；**store 的持久化配合**——需要持久化的 store 显式声明（第 6 节）——**「store 的组织：按业务域分、只放共享状态、持久化显式声明」**。

## 7. 常见坑

**坑一：页面自己存用户信息**。每页一份不同步——user store 单一数据源。

**坑二：状态与存储不分**。页面直接读写 localStorage——store 是运行时、storage 是持久化。

**坑三：url 传大对象**。url 超长/序列化错——大数据走状态。

**坑四：返回不刷新**。详情改完返回列表数据旧——onShow 刷新。

**坑五：未登录硬访问**。受保护页面无检查——页面级检查 + 请求 401 拦截。

**坑六：登录回跳不做**。登录后回首页丢上下文——记住来源回跳。

**坑七：token 持久化一刀切**。敏感场景全落 storage——安全考量。

**坑八：路由跳转堆栈无限**。navigateTo 连环跳（列表→详情→详情…）页面栈爆——需要时 redirectTo 替换（「页面栈深度是路由设计的一部分」）。

**坑九：tab 页刷新不彻底**。「切 tab 回来数据没更新」——tab 页 onShow 刷新（03 篇生命周期）。

**坑十：store 与页面状态混淆**。临时状态（输入框内容）也进 store——store 只放跨页共享——「状态分层：组件 ref → 页面 ref → store」。

**坑十一：登录态检查只在前端**。页面守卫过了但后端不验 Token——前端守卫是体验、后端鉴权是安全（[[../../10-前端知识拓展/Token/09-安全红线与攻防|Token 安全]]——「前端不信任后端不设防」）。

**坑十二：退出登录不完整**。只清 store 不清 storage/跳转——登出三件事（清 store + 清 storage + 跳登录——06 篇登出纪律）。
