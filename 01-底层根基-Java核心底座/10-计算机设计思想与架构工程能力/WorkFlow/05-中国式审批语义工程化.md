# 05-中国式审批语义工程化：会签、加签、退回、撤回

> 定位：会签/加签/任意节点驳回/撤回是中国 OA 语境的业务能力，**BPMN 2.0 标准里根本没有这些完整产品**——引擎只提供多实例、Token、状态变更等积木，语义规则必须由平台层补齐。本篇给出三层架构原则与每个操作的真实实现路径。

## 1. 三层架构原则（先立框架）

1. **BPMN 引擎层**：只负责标准语义——多实例、Execution、Task、网关，不写任何中国式业务规则。
2. **流程服务层**（核心工程量所在）：封装会签策略、加签/减签、回退/跳转、撤销/委派、抄送台账等审批操作，编排引擎 API。
3. **低代码应用层**：表单、待办列表、审批按钮、流程设计器。

> 💡 分层理由：引擎 API 每次升级都变（Flowable 6→8 变了大量 API），业务语义与引擎内部实现解耦后，升级只改流程服务层一处。三层之间用业务语义接口通信，不直接散落调引擎。

## 2. 会签 / 或签 / 顺序会签

引擎层基础是**多实例（multi-instance）**：顺序或并行循环执行同一节点，配合完成条件表达式：

```xml
<userTask id="countersign" name="会签" flowable:assignee="${assigneeList}">
  <multiInstanceLoopCharacteristics isSequential="false"
      flowable:collection="${assigneeList}" flowable:elementVariable="assignee">
    <completionCondition>${nrOfCompletedInstances >= nrOfInstances * 0.6}</completionCondition>
  </multiInstanceLoopCharacteristics>
</userTask>
```

平台层必须补齐的规则（引擎不负责的部分）：

- **会签**：全部同意才通过（完成条件 = 实例总数）；**或签**：任一通过即过；**顺序会签**：逐人轮转。
- **人员集合来源**：会签人员集合（assigneeList）在任务创建前由流程服务层解析——按角色查人、按部门查人、按"发起人 + 上级链"推人，解析结果以变量注入多实例集合。人员集合的生成时机与变更处理要设计清楚：任务创建后部门调整，是维持原集合还是重算，业务规则要显式化（默认维持原集合，避免审批中途换人引发争议）。
- **完成条件表达式速查**：`nrOfInstances`（实例总数）、`nrOfCompletedInstances`（已完成数）、`nrOfActiveInstances`（活动数）、`loopCounter`（当前序号）——"≥60% 通过"写作 `${nrOfCompletedInstances >= nrOfInstances * 0.6}`；一票否决在或签上叠加"拒绝即终止"用事件子流程或完成条件配合实现。
- **一票否决**、按权重计票、重复人员去重、人员中途变更等——全部在流程服务层实现，通过条件表达式注入。
- 会签任务在库里体现为**多实例 Execution**，这也是"只有会签任务才能加减签"的原因。

## 3. 加签与减签

- **向后加签（AFTER）**：当前人继续批，子任务先设 owner、状态 WAIT，父任务通过后才激活后签人。
- **向前加签（BEFORE）**：当前人变 owner、assignee 清空、任务置 WAIT，先建子任务（直接设 assignee 立刻可办），子任务完成后 resolve 回自己再批。
- **硬性校验**：同一父任务上 BEFORE 与 AFTER 互斥，否则"谁先谁后"无法解释；减签只能删未完成子任务，禁止删已审批人、校验最低人数、处理并发冲突并保留意见。
- 实现底座：Flowable 8 的 `RuntimeService` 提供多实例 Execution 动态增删 API，配合 `addMultiInstanceExecution` 创建子任务。

## 4. 退回（任意节点驳回）——最复杂的一块

核心 API 是**流程实例修改**：`runtimeService.createChangeActivityStateBuilder().moveActivityIdsToSingleActivityId(executionIds, targetActivityId).changeState()`。难点在**可退回节点计算**：

- 通过 `ACT_RU_ACTINST`（运行时活动实例）、`ACT_RU_EXECUTION`（执行流）、`ACT_HI_ACTINST`/`ACT_HI_TASKINST`（历史）计算候选退回节点。
- 只有已执行完毕（`END_TIME_` 不为空）的节点才可退回；目标节点必须在当前或父级执行流的路径上，**不能跳到并行网关未涉足的分支**。
- 串行与并行场景不同：退到并行网关之前要停掉所有并行分支活动，撤销中间已执行活动实例，并**回滚工作流与业务操作（同一事务）**。
- 工程封装：`TaskService` 扩展 `getRollBackList(taskId)`（可退回节点清单）与 `executRollBack(taskId, targetId, comment)`（执行退回 + 追加退回意见 + 更新历史任务）。

```java
// 退回实现核心（概念代码，Flowable 8 基线）
List<String> executionIds = runtimeService.createExecutionQuery()
    .processInstanceId(piId)
    .activityId(currentTaskDefKey)   // 当前活动
    .list().stream().map(Execution::getId).toList();

runtimeService.createChangeActivityStateBuilder()
    .moveActivityIdsToSingleActivityId(executionIds, targetActivityId)
    .processInstanceId(piId)
    .changeState();

// 退回后业务回滚与意见必须与 changeState 同一事务（@Transactional 方法级）
// 回退记录落业务表：回退人、目标节点、原因、时间
```

**退回的三个设计决策**：其一，回退后是否生成新任务还是复用历史任务（推荐生成新任务，意见与时间线清晰）；其二，并行网关前的回退要同时停掉所有并行分支的执行（`deleteProcessInstance` 删除多余分支，否则僵尸分支继续推进）；其三，回退目标节点的执行人按当前规则重算（历史执行人不一定还在岗）。

### 4.1 审批意见与附件管理

- **意见**：`addComment` 落 ACT_HI_COMMENT，与任务/实例关联——审批记录页直接查历史表，不用自建表；意见类型（同意/驳回/退回）用 `type` 字段区分，展示层按类型渲染。
- **附件**：附件落文件服务（MinIO/OSS），引擎里只存附件 URL 与元数据（参考同级《MinIO》体系的元数据分离原则）——附件塞进流程变量是变量表膨胀的元凶。
- **意见必填策略**：驳回/退回场景强制意见，通过场景可省略——用任务监听器在 complete 前校验，或在业务层判断审批结论后校验。

## 5. 自由跳转

- 引擎 API：`ChangeActivityStateBuilder` 支持单 Execution 移动、多 Execution 汇聚/拆分、按当前活动 ID 跳转——普通节点跳转与会签节点跳转要分开实现。
- 平台层必须加**目标节点白名单**（不能跳到无意义节点）、执行人重算、事件与定时器清理。
- 自由跳转是"特事特办"能力，审计日志必须记录跳转人、跳转目标与理由，否则合规上无法交代。

## 6. 转办 vs 委派（高频面试辨析）

- **转办**：`setAssignee(新处理人)` 直接换人，彻底交出处理权，原人不再担责。
- **委派**：`delegateTask(新处理人)` 保留 owner，`DelegationState.PENDING`，委派人办完 resolve 回原人——**责任仍在原人**。
- 二者业务语义截然不同：转办是"换人办"，委派是"代我办"。面试答出 DelegationState 三态（PENDING→RESOLVED）即加分。

## 7. 撤回三态（审批"反悔"）

三条完全不同的状态路径，别混成一条：

- **发起人撤回（withdraw-to-start）**：流程未进入第一审批人/已拒绝时，发起人撤回——复用退回逻辑退到开始事件。
- **已办取回（withdrawTask）**：下一节点还没处理时，上一节点取回待办重新审批——需要"任务是否已被处理"的竞态判断。
- **驳回后重提（resubmit）**：驳回后修改内容重新提交，通常走"原路重走"或"指定节点重走"。

## 8. 抄送与按钮体系

- **抄送**：写抄送台账（流程实例 ID + 被抄送人 + 意见），**不创建 UserTask**——否则待办列表被抄送人污染，且抄送任务无法 complete。
- **按钮体系三层契约**：设计时开关（buttonsSetting，流程定义时可配按钮）+ 运行时语义（审批操作服务）+ 端上组件，按"通过/拒绝、转办/委派、加签/减签、退回、抄送"七类管理，禁止前端写死按钮列表。
- **操作按钮与节点能力绑定**：同一操作在不同节点语义不同——"退回"在主管节点可退到发起人，在财务节点只能退到主管；"加签"只在会签节点开放。运行时语义层要做"节点 × 操作 × 条件"的能力矩阵校验，设计时开关管"哪些按钮显示"，运行时校验管"这个节点能不能这么操作"，两层都过才放行，缺一层都会出现"按钮能点、点了报错"的体验事故。

## 9. 国产轻量替代

Dromara 社区的 **Warm-Flow** 仅 7 张表，原生支持通过、退回、撤销、拿回、任意跳转、终止、转办、票签、委派、加减签等全部中国式操作，支持经典与仿钉钉双模式，适合不想啃 Flowable 复杂 API 的中小项目（详见 09 篇选型）。

> 🎯 核心要点：中国式审批的工程本质是"**引擎给积木，平台定语义**"。会签靠多实例+条件，加签靠多实例动态增删，退回靠流程实例修改+节点可达性计算，撤回三态是三条独立路径——把这些讲清楚，工作流面试直接封顶。
