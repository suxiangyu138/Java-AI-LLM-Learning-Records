# 08-生产运维与性能调优：历史治理、异步执行器与排障

> 定位：工作流系统上线三个月后，头号问题不是功能而是**数据与运行治理**——历史表膨胀、定时器不触发、流程莫名卡死、并发上去性能塌方。本篇给出嵌入式引擎（以 Flowable 为基线）的生产运维手册。

## 1. 历史数据治理（运维头号问题）

历史表（ACT_HI_*）只增不减，高并发审批三个月可达千万行，直接拖垮历史查询与统计报表。

- **归档策略**：已完成实例的历史按"实例维度"批量迁入归档表/冷库（按 `PROC_INST_ID_` 整实例搬，保持关联完整性），生产只留 3-6 个月热数据；归档表只读，查询走归档库或数仓。
- **清理任务**：Flowable 提供 `ProcessInstanceQuery` + `HistoryService` 的清理 API（按时间/已结束实例删历史），配定时任务低频执行；删除前先备份，删除后验证历史查询报表不破。
- **数据量估算**：一次典型审批（5 节点）约产生 20-40 行历史（实例+活动+任务+变量），用"日实例数 × 行数 × 保留天数"规划容量。
- **变量表瘦身**：只存流程控制所需 key，审批明细落业务表——变量表（ACT_HI_VARINST）是膨胀最快的表。

```java
// 归档骨架：按"已结束 + 结束时间早于保留期"批量迁历史，逐批提交
List<HistoricProcessInstance> done = historyService.createHistoricProcessInstanceQuery()
    .finished().finishedBefore(DateUtils.parse("2026-05-01"))
    .listPage(0, 1000);
for (HistoricProcessInstance pi : done) {
    archiveService.archive(pi.getId());          // 整实例搬入归档库（含子表）
    historyService.deleteHistoricProcessInstance(pi.getId());  // 生产库删除
}
```

- **删除顺序纪律**：先归档后删除；删除走引擎 API（级联清理 ACT_HI_ 全子表），禁止手写 SQL 删关联表——外键与清理逻辑在引擎内部。
- **容量规划公式**：日历史行数 = 日启动实例数 × 单实例平均历史行数（典型审批 20-40 行）；生产库容量 = 日行数 × 保留天数 × 单行平均字节（约 300-500B）；按这个公式在立项时就算出归档任务频率与冷库容量，别等告警。

### 1.1 真实故障案例

**案例一（定时器集体静默）**：某系统上线半年后"审批超时自动通过"全部失效，排查发现测试环境 `flowable.async-executor-activate=true` 写进了文档但生产配置漏配——引擎从未扫描过定时器，Job 一直沉睡在表里。教训：上线检查单第一条就是验证异步执行器激活状态（查 ACT_RU_JOB 有无 JOB_TYPE=timer 的作业在正常移动）。

**案例二（历史表撑爆磁盘）**：日审批 2 万单的项目未配清理，三个月 ACT_HI_ACTINST 超 8000 万行，单表 40GB 逼近磁盘上限，所有历史查询秒级变分钟级，最终引发数据库只读保护。教训：历史治理是立项期任务不是运维期救火——容量公式要在上线前算好。

## 2. 异步执行器（定时器/异步继续的生命线）

- JobExecutor 默认未激活，`flowable.async-executor-activate=true` 必须在生产打开，否则定时器、异步继续、事件子流程全部静默失效。
- 核心参数：`async-executor-core-pool-size`（Job 执行线程，默认 8，按实例吞吐调）、`async-executor-max-pool-size`、`default-job-owner`（多节点部署时避免 Job 抢锁冲突）。
- **Job 重试与死信**：Job 失败按 `default-retries`（默认 3）重试，重试耗尽变死信 Job（`ACT_RU_DEADLETTER_JOB`）——告警必须盯死信表，那里是"流程静默断掉"的源头。
- 定时器精度是分钟级轮询，不是毫秒级调度——业务对"准时"有强诉求时用消息驱动而非定时器。

**执行器调优思路**：先量后调——用监控数据回答"Job 队列积压多少、单 Job 执行耗时多少、线程利用率多少"，再决定调线程池还是改业务（Job 本身太慢往往比线程不够更值得查）。线程池不是越大越好：Job 与数据库事务绑定时，池过大只会放大数据库压力；常见的健康基线是"池大小 × 单 Job 耗时 × 每秒 Job 数"三者的配平。另一个常被忽略的点是定时器 Job 的阻塞现象——某个 Job 里调了慢外部服务，会占住线程拖慢同一池内的其他定时任务，慢 Job 与快 Job 按类型分池是进阶做法。

## 3. 性能与并发

- **命令拦截器优化**：自定义 `CommandInterceptor` 做统一日志/限流/多租户注入，比业务代码里散着处理干净，也是性能剖析的挂点。
- **锁与死锁**：引擎用悲观锁保证同一实例串行推进；高并发下"多实例会签 + 并发 complete"易死锁——锁等待超时参数（`flowable.transaction-lock-owner` 等）与数据库 innodb_lock_wait_timeout 协同调优，事务内尽量少跨服务调用。
- **200+ 并发稳定性**：Flowable 社区公开认知的短板区间——集群多节点 + 读写分离（历史表查询走从库）+ 批量操作 API（`BatchService`）是常规解法；真到千级并发且要分布式弹性，换 Camunda 8 路线（见 07 篇）。
- **查询优化**：待办查询高频，`ACT_RU_TASK` 的 `ASSIGNEE_` 索引必须确认存在；待办列表分页 + 缓存，禁止全表扫。
- **读写分离实践**：历史查询（报表、审批记录页）对实时性要求低但频率高，是拖累引擎写路径的常见元凶——把历史查询路由到只读从库，运行时表（ACT_RU_）与业务写保持同库，从架构上隔离"写路径的短事务"与"读路径的大查询"两类负载；只读副本延迟在秒级对历史查询可接受，监控从库延迟即可。

## 4. 监控与告警

- **指标五件套**：活跃实例数、待办积压数（按处理人分组）、Job 死信数、节点滞留时长（SLA 对比）、历史表容量增速。
- **告警规则**：死信 Job > 0 告警；节点滞留超 SLA 告警（对应自动催办）；历史表容量超阈值告警；引擎异常日志（`ActivitiException` 频率）告警。
- 与日志体系打通：流程实例 ID / businessKey 进日志上下文，排障时日志链可追溯（参考《日志监控指标》体系）。

**告警治理的实践经验**：指标五件套全部接上后，真正的难点是"告警疲劳"——节点滞留告警在人手不足时必然常态化，团队会习惯性忽略。对策是按影响分级：死信 Job 与容量超限属于 P1（立刻处理），节点滞留按 SLA 阈值分级（超 1 倍提醒、超 2 倍告警、超 3 倍升级），把告警做成"能区分偶发与系统性故障"的漏斗，而不是一视同仁的噪声。季度复盘时对比"告警数 vs 真实故障数"，持续收敛误报，告警体系才有公信力。

## 5. 故障排查速查表

| 现象 | 第一排查点 | 常见根因与处理 |
|---|---|---|
| 流程卡死不动 | 查 ACT_RU_EXECUTION 令牌停在哪 | 停在 UserTask=等人批；停在 ServiceTask/Job=Job 失败重试中，看死信表 |
| 定时器不触发 | `flowable.async-executor-activate` 是否开启 | 未开启 = 静默失效；Job 被锁（owner 冲突） |
| 待办丢失 | 事务边界 | complete 后同事务查下一任务查不到（未提交）；监听器异常吞掉 |
| 并发 complete 报死锁 | 锁等待日志 | 多实例并发 + 长事务；拆短事务、减少事务内外部调用 |
| 启动流程超时 | 数据库锁/表膨胀 | 定义表被大事务锁；历史表过大拖慢查询 |
| 升级后变量读不出来 | Jackson 序列化 | 6/7→8 的 Jackson 3 变量兼容层未做 |

## 6. 升级迁移清单（6/7 → 8）

- Spring Boot 自动配置与事务边界回归：starter 行为变化、`flowable.*` 配置项改名。
- **Jackson 2→3**：JSON 类型流程变量的读写兼容层（历史表存量数据）。
- 脚本/表达式里的 JsonNode API 变化（Jackson 3 的 API 变更）。
- 历史表数据量与清理策略：升级前先归档压缩，升级后启用新清理机制。
- 自定义 SQL 与国产数据库兼容层：直接查 ACT_* 表的自定义 DAO 要重新验证（达梦/人大金仓等）。
- 回归清单：部署、启动、审批全链路、定时器、会签/加签/退回五个专项各跑一轮端到端用例。

> 🎯 核心要点：工作流运维 = 管历史（归档）、管 Job（死信）、管锁（并发）、管升级（兼容）。"流程卡死"先看令牌停哪，定时器不触发先查异步执行器——80% 故障在这两条线上。
