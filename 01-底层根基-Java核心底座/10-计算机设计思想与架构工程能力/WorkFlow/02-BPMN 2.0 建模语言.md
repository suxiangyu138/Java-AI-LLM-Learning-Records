# 02-BPMN 2.0 建模语言：流程建模的事实标准

> 定位：BPMN（Business Process Model and Notation）是工作流建模的语言——业务用图说话，引擎按 XML 执行。掌握五类元素、核心符号语义和建模纪律，才能画出"能跑、好改、可审计"的流程，而不是画图自嗨。

## 1. 标准化历程

- **2004**：BPMI 组织发布 BPMN 1.0，统一流程图符号。
- **2011**：OMG 发布 BPMN 2.0，最大变化是**定义了执行语义和 XML 序列化**——同一张图既能给人看，也能给引擎跑，这是它战胜 XPDL/EPC 成为事实标准的根本原因。
- **2013**：成为 ISO 19510 国际标准，与 UML、CMMN（案例管理）、DMN（决策建模）构成 OMG 流程三件套。

> 💡 理解要点：BPMN 2.0 的本质是"图元 ↔ XML 的双向映射"。画图工具导出的 `.bpmn20.xml` 就是引擎部署的模型文件，人看的图只是 XML 的可视化。

**BPMN 2.0 战胜 XPDL/EPC 的四个原因**：其一，执行语义标准化——同一种图元在任意合规引擎上行为一致，而 XPDL 只是格式标准不约束行为；其二，XML 序列化与图元一一对应，工具、引擎、仓库三方直接交换文件；其三，表达力覆盖人工流程与系统流程（用户任务与服务任务同图共存），EPC 侧重管理视角缺乏执行视角；其四，OMG 与 ISO 双重背书带来生态效应——建模工具、引擎、培训材料全部向标准对齐。这也是为什么 2010 年代百花齐放的流程语言最终收敛到 BPMN 一个。

## 2. 五类元素全景

- **流对象（Flow Objects）**：事件（Event）、活动（Activity）、网关（Gateway）——流程的"名词与动词"。
- **连接对象（Connecting Objects）**：顺序流（Sequence Flow，实线箭头）、消息流（Message Flow，虚线箭头，跨泳池）、关联（Association，点线）。
- **泳道（Swimlanes）**：泳池（Pool，参与者/系统边界）与泳道（Lane，池内角色分组）。
- **工件（Artifacts）**：数据对象（Data Object）、组（Group）、文本注释（Text Annotation）——不参与执行，只做语义补充。
- **数据（Data）**：数据输入/输出、数据存储（Data Store），描述流程读写的数据。

## 3. 核心元素语义（必须吃透）

**事件（Event）**：用圆圈表示，按位置分开始、中间、结束三种；按触发分消息、定时、错误、补偿、信号、终止等。关键组合是**边界事件**——挂在活动边界的中间事件，活动运行时被触发则打断流程，如"审批超时 72 小时走自动通过"。

```xml
<!-- 边界定时事件：审批任务挂 72 小时超时兜底 -->
<userTask id="approve" name="领导审批" />
<boundaryEvent id="timeout" attachedToRef="approve">
  <timerEventDefinition>
    <timeDuration>PT72H</timeDuration>
  </timerEventDefinition>
</boundaryEvent>
```

**活动（Activity）**：圆角矩形。任务（Task）是原子活动：**用户任务（UserTask）**要人等，**服务任务（ServiceTask）**由系统自动执行（调用 Java 服务/HTTP/外部 Worker），脚本任务、接收任务、发送任务补充场景。子流程（SubProcess）是复合活动——内部再嵌一套 BPMN 元素，可折叠、可事务、可事件触发（Event SubProcess，用于"审批作废"这类全局兜底）。

**网关（Gateway）**：菱形，控制流的岔路口：

- **排他网关（XOR）**：多条件取一，条件从上到下求值，全部不满足走默认流——**必须配 default 流，否则运行时抛错**。
- **并行网关（AND）**：分叉全部激活、汇聚等齐所有分支才继续。
- **包容网关（OR）**：条件为真的分支全走，汇聚时"只要激活过的分支都到达"即可继续。
- **事件网关**：先触发的事件决定走向，适合"审批 vs 超时竞速"。

**连线**：顺序流可带条件表达式（引擎内用 UEL 表达式，如 `${amount > 10000}`）和默认流标记。

### 3.1 事件分类深潜

事件的正确分类是建模的第一道基本功，按两个维度交叉理解：

- **按位置**：开始事件（流程入口）、中间事件（流程过程中触发/等待）、结束事件（流程/分支出口）。
- **按类型**：消息（Message，接收/发送，跨泳池通信）、定时（Timer，时间驱动）、错误（Error，异常抛出/捕获）、补偿（Compensation，回滚已成功步骤）、信号（Signal，广播式，一对多）、终止（Terminate，立即结束整个实例）、条件（Condition）、链接（Link，跨页连接）。

**三个最常用的实战组合**：

- 定时中间事件 + 用户任务 = 审批超时自动处理（SLA 兜底）。
- 错误边界事件 + 服务任务 = 服务调用失败走补偿/人工处理路径。
- 信号事件 = 跨流程实例广播（"年度冻结"通知所有在途审批终止）。

命名纪律：消息/信号名全项目唯一且语义化（如 `msg.leave.recalled`），否则跨流程连线接错是静默事故。

### 3.2 子流程三兄弟

- **嵌入式子流程（Embedded）**：图内嵌，共享父流程变量与令牌，可折叠，适合"同一段逻辑多流程复用"。
- **调用子流程（Call Activity）**：引用独立的流程定义，解耦部署、独立版本管理，适合跨系统/跨团队复用；代价是变量传递要靠映射。
- **事件子流程（Event Subprocess）**：不被正常流触发，由事件（错误/定时/消息）在**任意时刻**打断父流程执行——"审批作废""强制撤回"这类全局兜底语义的首选，也是中国式"作废重提"的建模基础。

三者选择口诀：同图复用选嵌入式，跨定义复用选调用，全局兜底选事件。

### 3.3 建模工具与 XML 结构

- **建模工具**：Flowable Modeler（官方 web 设计器）、Camunda Modeler（桌面端，导出 BPMN 文件通用）、bpmn.io（网页端轻量）、IDEA 插件（代码评审流程文件）。工具只负责画图与导出，**引擎认的是 XML 不认图**。
- **XML 结构**：`definitions`（命名空间 + targetNamespace）→ `process`（id、name、isExecutable）→ 流对象与连线。`isExecutable="true"` 是引擎执行的必要条件，从 Camunda Modeler 导出的文件常常漏掉它，部署报"无执行流程"错——这是新手头号部署坑。
- **命名规范**：元素 id 用英文驼峰且稳定（`leaveApprove`），name 用中文展示名——id 是引擎索引与跳转目标，改名等于重写流程引用。

## 4. 建模纪律（工程红线）

- **一个节点只干一件事**：把"审批 + 写库 + 发通知"拆成用户任务 + 两个服务任务，否则退回、重试、审计全部变脏。
- **每条并行分支要有汇聚点**：漏掉汇聚会导致流程"永远走不完"，是建模头号事故。
- **网关条件必须完备**：排他网关补 default，条件表达式不能引用不存在的变量（变量缺失时表达式求值为 false，流程静默走错分支）。
- **超时与异常必须建模**：边界事件兜底超时，错误边界事件接服务失败，不要指望"引擎不会出错"。
- **区分流程内循环与驳回**：循环是建模期的正常回路；"驳回"是中国式审批的动态语义，靠引擎的流程实例修改 API 实现（见 05 篇），不要为了驳回把图画成一团循环。

## 5. BPMN vs 状态图

| 维度 | BPMN | UML 状态图 |
|---|---|---|
| 视角 | 多参与者过程协作（谁在做什么） | 单对象状态流转（对象处于什么状态） |
| 一等公民 | 任务、网关、泳道 | 状态、事件、转移 |
| 执行载体 | 引擎按 XML 驱动 | 状态机框架（Spring StateMachine 等） |
| 适用 | 审批流、跨部门流程 | 订单状态、任务生命周期 |
| 中国式审批 | 原生不覆盖，需引擎修改 API | 天然支持驳回（状态回退） |

> 🎯 核心要点：BPMN 是"图即代码"。建模纪律比符号记忆重要——网关缺 default、并行漏汇聚、条件引用未定义变量，是生产环境三个最常见的事故源头。

**符号记忆的最小集**：新手不必背全部事件类型，先吃透十个高频符号——开始/结束事件、用户/服务任务、排他/并行网关、顺序流、边界定时事件、错误边界事件、多实例标记（底部三条竖线）、子流程标记（底部加号）。其余符号（补偿、信号、事务子流程等）遇到再查，用过的自然记住；画图时若发现自己在用冷门符号解决常见问题，通常是建模思路出了问题，先怀疑模型再怀疑符号库。
