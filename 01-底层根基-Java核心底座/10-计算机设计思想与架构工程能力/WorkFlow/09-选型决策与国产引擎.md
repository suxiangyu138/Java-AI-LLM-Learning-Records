# 09-选型决策与国产引擎：先分类，再比较，后算账

> 定位：工作流选型 90% 的错误源于"把不同类别的产品放进同一张排行榜"。本篇先把产品分成四类，再给三剑客与国产引擎的对比结论，最后算许可与 TCO 的账——选型是商业决策，不只是技术对比。

## 1. 先分类，再比较（四类产品）

| 类别 | 代表 | 解决什么 | 不解决什么 |
|---|---|---|---|
| BPMN 人工审批引擎 | Flowable、Activiti、jBPM、Operaton | OA 审批、订单履约、跨部门流程 | 组织权限、表单门户、分析看板 |
| 完整 BPM/DPA 平台 | Camunda 商业平台、Bonita | 建模+表单+任务门户一体化 | 同样不覆盖全部业务 |
| 分布式耐久执行编排 | Camunda 8、Temporal、Conductor | 微服务编排、Saga、跨语言 Worker | 会签/退回等人工审批语义 |
| 应用内逻辑编排 | LiteFlow | 规则链、营销计算、风控 | 人工任务、审计流程 |

> ⚠️ 常见错误：拿 Camunda 8 做 OA 审批（无中国式语义）、拿 Flowable 做千级并发微服务编排（嵌入式扩展有限）——类别不匹配，功能再强也是错配。

为什么类别先于版本：同一类别内的产品（如 Flowable 与 Activiti）核心能力同构，差异主要在版本节奏、许可与社区；跨类别的产品（如 Flowable 与 Camunda 8）连"问题定义"都不同——前者的问题是"怎么把审批流跑稳"，后者的问题是"怎么把跨服务编排跑弹"。把不同类别放同一张表比功能，等于拿轿车和卡车比百公里油耗，结论必然失真。2026 年选型报告里"权重法"（社区活跃 15%、架构先进性 15%、功能完备 15%、标准符合 12%、二次开发 12%、许可 11%、本土化 10%、学习成本 10%）能跑通的前提，也是先完成类别筛选再逐项打分。

## 2. 三剑客对比（2026-08 基线）

| 维度 | Activiti | Flowable | Camunda 8 |
|---|---|---|---|
| 版本 | 9.0.0（Java 25 基线） | 8.0.0（Boot 4/Jackson 3） | 8.9.13（分布式） |
| 架构 | 嵌入式 | 嵌入式（多引擎 BPMN/CMMN/DMN） | Zeebe 分布式 |
| 中国式审批 | 弱 | **最强**（状态变更 API 丰富） | 弱 |
| 社区活跃度 | 低（Alfresco 商业化） | 高（国内资料最多） | 中（国内社区弱） |
| 部署形态 | 单体/模块化 | 单体/模块化 | K8s 集群 + 许可 |
| 2026 定位 | 存量加固/渐进迁移 | 中国式 OA 与低代码平台底座 | 金融电信大型编排 |

**结论**：新建 OA/低代码审批平台 → Flowable（优先 PoC）；存量 Activiti 资产 → 评估加固 vs 渐进迁移，不因版本号更高而选 Activiti 9（Java 25 对政企内网不现实）；跨语言高吞吐编排 → Camunda 8 或 Temporal。

## 3. 国产引擎与信创

- **Warm-Flow（Dromara）**：仅 7 张表，原生支持通过、退回、撤销、拿回、任意跳转、终止、转办、票签、委派、加减签，经典与仿钉钉双模式，可 jar 引入设计器——解决 Flowable 复杂、学习成本高的痛点，中小项目落地最快。技术画像：内嵌式、无 BPMN XML 依赖（以流程设计 JSON 为模型）、学习曲线陡降；代价是生态与资料规模远小于 Flowable，复杂边界场景（跨系统调用、历史分析报表）需要自研补齐。判断标准：流程简单、团队小、要快——Warm-Flow 是优选；流程复杂、要 BPMN 标准与生态兜底——仍选 Flowable。
- **JFlow/CCFlow（驰骋）**：开箱即用中国式审批（任意节点退回、前后加签、会签并行），自带表单引擎，支持达梦、人大金仓、GaussDB 等国产数据库与信创环境——国产化/政务场景的第一候选。双引擎结构（C# 版 CCFlow 与 Java 版 JFlow）在政企有十余年存量，运维资料以中文为主；注意其许可模式与 Flowable 的 Apache 2.0 不同，商用前需商务确认。
- 选国产引擎的边界：社区规模与问题可查性不如 Flowable；但"信创合规 + 中国式审批开箱即用"这两条硬指标下，JFlow 类产品不可替代。折中路径也常见：引擎用 Flowable 保证生态，信创兼容层（国产数据库方言适配）自研或采购——成本介于两者之间，适合"既要生态又要合规"的大型集团。

## 4. TCO 与许可算账

- **开源 ≠ 可自由商用**：Camunda 8 自 8.6 起 Self-Managed 生产需要生产许可证；Flowable 引擎 Apache 2.0 可商用，但"商业低代码产品"（设计协作、统一任务中心、细粒度权限、分析看板）不在开源引擎开箱范围内——这些体验要自建。
- **成本项清单**：引擎许可费（如有）+ 集群资源（Camunda 8 常驻三组件）+ 运维人力 + 二次开发量（中国式语义平台层）。
- **免费引擎的隐性成本**：Apache 2.0 的 Flowable 引擎本体免费，但"免费"只覆盖引擎 jar——流程设计器、任务门户、权限体系、历史分析报表这些平台能力都需要自建，每一块都是人月；把隐性成本（自建功能 × 平均工时）算进 TCO 后，很多"免费方案"五年成本并不比商业平台低。选型汇报时的正确姿势是同时展示开源路线的"隐性工作量清单"与商业路线的"显性许可费"，让决策者看全图而不是只看报价单。
- **决策模板**：列 5 年成本（许可 + 人力 + 基础设施）× 两个候选 × 三个场景（当前、翻倍增长、信创替换），再谈技术对比。

**场景推演（中小审批平台，5 年）**：

- Flowable 路线：许可 0 元 + 二次开发（中国式语义 2-3 人月）+ 单机/双机部署（2 台 4C8G）；总成本主要落在人力，可控。
- Camunda 8 路线：生产许可按节点年费计 + 集群常驻 3 组件（至少 3-6 节点）+ 运维人力；规模不到金融电信级时，成本是 Flowable 路线的 5-10 倍。
- JFlow 路线（信创场景）：许可按项目计 + 国产数据库兼容天然无适配成本；非信创场景则无优势。

推演的结论很直白：**预算与规模决定路线**——小额预算的审批平台选嵌入式开源，重合规重弹性的场景才轮到分布式商业路线。

### 4.1 PoC 验收标准（八项全过才算数）

1. 部署-启动-审批-退回全链路跑通，含并行分支与多实例。
2. 中国式语义清单逐项验收：会签比例、前后加签、任意节点退回、撤回三态。
3. 压力测试：目标并发的 2 倍下，任务 complete 的 P95 延迟达标。
4. 历史数据增长实测：按容量公式核对归档方案可行。
5. 升级路径验证：从候选版本到最新 LTS 的迁移文档齐全且可执行。
6. 监控与排障：死信、滞留、容量三类告警能收到且定位准确。
7. 团队可维护性：核心成员能独立完成一次流程定制开发。
8. 许可与合规：法务确认商用边界与信创要求满足。

## 5. 选型决策树（一图走完）

```text
需要工作流？
├── 信创/政务强制国产化 → JFlow/CCFlow
├── 中小项目要快、要中国式审批开箱即用 → Warm-Flow
├── 企业 OA/低代码审批平台 → Flowable 8（优先 PoC；排 Activiti 9 的 Java 25 与低活跃社区）
├── 微服务跨语言高吞吐编排 → Camunda 8（算许可账）/ Temporal（纯代码编排）
├── 已有 Activiti 存量资产 → 评估加固或迁移 Operaton/CIB seven
└── 应用内规则链/风控 → LiteFlow，别上引擎
```

**落地清单八项**：① 类别匹配确认 ② 版本与许可核对 ③ PoC 跑通"部署-启动-审批-退回"全链路 ④ 中国式语义二次开发量估算 ⑤ 历史数据量规划与清理方案 ⑥ 集群/单机资源预算 ⑦ 升级路径（含 Jackson/Boot 兼容）⑧ 五年 TCO 对比结论。

**决策树使用注意**：决策树给出的是"默认最优解"而非"唯一解"——同一条路径下还有组合空间（引擎可分层：审批用 Flowable、跨系统编排用 Camunda 8，两者通过消息衔接，大型集团实际就是这种混合拓扑）；决策的关键不是选对某一个，而是**明确每个引擎的职责边界与衔接协议**，避免"两个引擎都碰审批"的职责重叠。混合拓扑的额外成本是运维复杂度翻倍，只有规模真正撑得起时才值得。

> 🎯 核心要点：选型四步——分类（先定类别）、对比（同类别内比）、算账（许可+人力+二次开发）、PoC（真实场景验证）。2026 年选型权重里"社区活跃与长期维护、许可成本与商业风险"已超过纯技术维度。
