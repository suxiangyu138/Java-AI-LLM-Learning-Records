# 06-建模方法论与状态机选型：流程怎么画、引擎要不要上

> 定位：工作流选型失败的第一原因不是引擎选错，而是"这个问题根本不该用工作流"。本篇给出建模方法论（粒度/兜底/版本/可观测）与**状态机 vs 工作流引擎的决策树**，并讲清 DMN 规则分离。

## 1. 流程建模方法论

**粒度原则**：流程是"业务过程的骨架"，粒度控制在"部门级协作"——跨角色、跨状态分支、需要审计的过程适合建模；单对象的一步判断、简单状态翻转不要建模（那是状态机的活）。

**六个建模习惯**：

- **节点单一职责**：审批、写库、发通知拆开，否则退回/重试/审计全部变脏（详见 02 篇纪律）。
- **显式建模兜底**：每个用户任务挂超时边界事件，每个服务任务挂错误边界事件或重试策略——"流程停摆"事故九成来自没建模的等待。
- **条件完备**：排他网关补 default，表达式引用的变量在流程启动时初始化。
- **版本管理**：流程定义不可变，改流程 = 部署新版本 + 新旧实例并行跑完（老实例跑老版本是引擎默认语义，业务上注意"新单走新流程、老单走老流程"）。版本差异评估要显式化：新增节点属兼容变更（新老实例都能跑），删节点/改网关条件属破坏性变更——破坏性变更必须评估"老实例推进到被删节点时怎么办"，预案通常是维护兼容映射或在流程服务层做兜底跳转，而不是指望引擎处理。
- **挂起而非删除**：废弃流程定义用 suspend，实例未结束的定义不能删。
- **测试即流程**：每条网关分支、每个边界事件都要有测试用例，用流程引擎的测试框架（Flowable 的 Spring 测试支持）跑端到端流程断言——流程是代码，不是画。

## 2. 状态机 vs 工作流引擎：决策树

先回答三个问题，全否才考虑工作流引擎：

1. **是否多参与者协作？** 单人单系统的内部状态变化（订单状态、任务状态）→ 状态机。
2. **是否需要回退/驳回/会签？** 中国式审批天然需要"退回任意节点"——状态机做任意回退要维护历史栈，复杂度爆表 → 工作流引擎。
3. **是否需要流程可视化与审计？** 合规要求"流程可看图、可审计"（金融/政务）→ 工作流引擎；否则状态机 + 事件日志足够。

```text
业务过程
├── 单对象生命周期（订单/任务/工单）→ 状态机（Spring StateMachine/自研 FSM）
│   └── 需要审计/可视化？→ 叠加事件溯源或审计日志即可
├── 多角色审批流转 → 工作流引擎（Flowable/Activiti/国产）
├── 微服务跨系统编排 → Camunda 8 / Temporal / Conductor
└── 应用内规则链（营销计算/风控）→ LiteFlow 等轻量编排
```

**可叠加，非互斥**：订单用状态机管"生命周期正确性"，审批过程用工作流管"任务流转"，两套并行——状态机在业务层，引擎在流程层，中间用领域事件衔接。

**叠加案例（订单审批）**：订单实体状态机管理"待提交 → 审批中 → 已通过/已驳回 → 已发货"五个业务状态；审批过程由工作流引擎管理"谁审批、超时怎么办、能否退回"。订单状态机收到"流程通过"领域事件才跃迁到"已通过"——**业务状态的正确性由状态机保证，流程的推进与回退由引擎保证**，任何一层出问题都能在另一层兜住（引擎卡死时订单状态仍在"审批中"，不会漂移到非法状态）。这个"状态机守边界、引擎管流转"的叠加模式，是生产级审批系统的标准答案。

> 💡 记忆点：状态机管"对象现在是什么状态"，工作流管"下一步谁来做"。复杂度临界线是**是否需要多参与者的任意回退**——出现这个需求，就值得上引擎。

**决策树的补充判断（四个易错场景）**：其一，流程短且参与者固定（如"提交→审核"两步），上引擎反而增加表与运维成本，状态机 + 简单队列即可；其二，流程将来大概率演化出退回/会签，宁可提前上引擎，二次迁移比提前设计贵得多；其三，已有状态机代码且流程复杂度中等，评估"状态机 + 历史栈"能否覆盖退回需求（可覆盖则不必引入引擎）；其四，多人协作但无审批语义（如并行任务分派），那是任务编排不是审批流，别硬套工作流引擎。四问走完，选型不再凭感觉。

## 3. DMN：把规则从流程中剥离

流程里 `if-else` 条件写多了，图就变成规则代码。DMN（决策模型与符号，OMG 标准）把"决策"抽成独立模型，用决策表表达：

- **Flowable 原生支持 DMN**：`flowable-dmn-engine` 部署 `.dmn` 文件，`DmnRuleService` 执行决策表，流程里用表达式引用决策结果。
- 适用信号：条件表达式超过 3 个分支、规则经常变更（改规则不用重新发流程版本）、多流程复用同一套规则（如额度判定、风控评分）。
- 边界：DMN 解决"条件判断"，不解决"过程编排"——别用 DMN 画流程，别用 BPMN 写规则。

```xml
<!-- 额度决策表：审批流程只写 "额度判定" 服务任务，规则改这里，流程版本不动 -->
<decision id="limitDecision" name="额度判定">
  <decisionTable hitPolicy="FIRST">
    <input id="amount" label="金额" typeRef="number" />
    <output id="level" label="审批级别" typeRef="string" />
    <rule><inputEntry><text>&lt; 5000</text></inputEntry>
          <outputEntry><text>"主管"</text></outputEntry></rule>
    <rule><inputEntry><text>[5000..20000)</text></inputEntry>
          <outputEntry><text>"总监"</text></outputEntry></rule>
    <rule><inputEntry><text>&gt;= 20000</text></inputEntry>
          <outputEntry><text>"总经理"</text></outputEntry></rule>
  </decisionTable>
</decision>
```

规则从流程里剥出来的收益：改审批级别不用重新部署流程（运行中实例立即生效新规则）、规则可被多个流程复用、规则变更可单独走评审与测试。

## 4. 可观测性埋点

- **全局事件监听器**统一挂审计与指标：TASK_CREATED/TASK_COMPLETED/PROCESS_COMPLETED 五类事件，落"流程-节点-人-耗时"明细表。
- **指标三件套**：流程平均耗时（P50/P95）、各节点滞留时间（卡点在哪个节点）、驳回率（驳回率飙升 = 业务规则或表单出问题）。
- **预警**：节点滞留超过 SLA 触发告警 + 自动催办（定时器边界事件本身就是催办的一种实现）。
- 与日志体系打通：流程实例 ID 进日志上下文，`businessKey` 关联业务单号（参考同级《日志监控指标》体系）。

## 5. 五个建模反模式

1. **上帝流程**：一张图画完公司所有流程，改一处全图重构——按业务域拆成多个小流程 + 消息衔接。
2. **if-else 成瘾**：条件判断写成网关链，实际是规则——抽 DMN 或规则引擎。典型症状：同一个"金额分段"判断在五个流程里各画一遍网关，改一次规则改五张图；判别标准是"这条判断是否会被多个流程复用、是否频繁变更"，命中任一就应抽成 DMN 决策表（见第 3 节），流程图里只留一个服务任务引用决策结果。
3. **永不结束的流程**：并行分支漏汇聚、等待节点无超时——流程实例泄漏，历史表膨胀。
4. **流程即数据库**：把审批意见、单据明细全塞流程变量——变量表爆炸，应只存流程控制所需的 key。
5. **拒绝升级**：业务已演化到多角色回退，还用 if-else 状态枚举硬撑——该上引擎就上，硬撑的维护成本远超迁移成本。

> 🎯 核心要点：选型先问"这是不是多参与者流程"，建模先立"兜底与版本"，实现上"规则用 DMN、状态用状态机、流转用引擎"。工程上不追求技术炫技，追求每层工具解决对的问题。
