# 03-引擎全景与内核原理：三剑客与执行内核

> 定位：把开源工作流引擎当"黑盒"用是入门，理解内核才是进阶——同宗同源的三剑客为何分道扬镳、嵌入式与分布式两套架构怎么选、流程 XML 如何变成数据库里奔跑的 Token。本篇是 04-08 篇的地基。

## 1. 三剑客同宗同源史

- **2010**：Alfresco 团队基于 jBPM4 重写发布 **Activiti**，成为 Java 工作流开源霸主。
- **2013**：Activiti 创始团队部分成员分叉出 **Camunda**（6），走 BPM 平台化路线。
- **2016**：Activiti 内部理念分歧（商业化 vs 社区化），原核心团队分叉出 **Flowable**（6），Activiti 转入 Alfresco 商业化路线。

十年分叉后，"同源"只是历史线索，不再是替换承诺——**数据库结构、包名、执行语义、扩展 API 均已各自独立修改**。

## 2. 2026 版本格局

| 引擎 | 当前版本 | 运行模型 | 关键信号 |
|---|---|---|---|
| Activiti | 9.0.0（8.8.1 维护线） | Java 嵌入式，关系型数据库 | Java 25 基线较激进，存量资产价值 |
| Flowable | 8.0.0（2026-02） | BPMN+CMMN+DMN 多引擎，关系型数据库 | 升级 Spring 7/Boot 4/Jackson 3，移除 JUnit 3/4 |
| Camunda 8 | 8.9.13（2026-07） | Zeebe 分布式，Raft+分区日志 | Self-Managed 生产许可，8.9 起 RDBMS 二级存储 |
| Camunda 7 | 7.24 终版（已归档） | 嵌入式 | **CE 已于 2025-10 EOL**，存量可迁移 Operaton 2.1.3 / CIB seven |

> ⚠️ 三个版本坑：Activiti 9 的 Java 25 基线对政企内网（主流 Java 17/21）不现实；Flowable 8 是跨代升级（Boot 4/Jackson 3）；Camunda 8 不是 Camunda 7 的 Maven 升级，迁移要重设计。

**"同源不等于可替换"的具体含义**：分叉十年后，三家的数据库结构各自演化（表名、列、索引不同），包名与 API 全部独立（Flowable 是 `org.flowable`、Camunda 7 是 `org.camunda`、Activiti 是 `org.activiti`），执行语义存在微妙差异（多实例完成条件的解析、历史记录的删除策略、事件触发顺序）。这意味着：其一，流程定义文件（BPMN XML）本身基本可互导（标准红利），但绑定引擎扩展属性（监听器类名、表达式写法）的流程文件不能直接搬家；其二，换引擎等于重写集成代码与运维脚本，成本接近自研；其三，招聘与社区资产按引擎品牌独立积累——选型时"换得起"比"现在够用"更重要。

## 3. 两种架构路线

**嵌入式引擎（Activiti/Flowable/Camunda 7）**：引擎作为库与业务应用同 JVM，共享数据源与事务——一次方法调用内流程推进与业务写库要么全成要么全滚，实现简单、事务一致性强；代价是引擎与业务耦合，弹性只能靠应用水平扩展。适合单体、模块化系统与内网 OA。

**分布式引擎（Camunda 8/Zeebe）**：流程状态存于 Broker 的分区日志（Raft 复制），业务逻辑由引擎外部的 Job Worker 长轮询执行——跨语言（任何 HTTP/gRPC 客户端都可当 Worker）、水平扩展、故障恢复强；代价是引入独立集群，且需要外部编排器（Camunda 8 自带 Orchestration Cluster）承载查询/运维视图。

> 💡 选型分水岭：单体/模块化 + 强事务一致性 → 嵌入式；微服务 + 跨语言 + 高吞吐 + 独立运维团队 → 分布式。详见 09 篇决策树。

## 4. 内核执行原理（嵌入式引擎视角）

1. **部署与解析**：`deployment` 把 BPMN XML 解析为内存模型（流程图、元素映射、表达式编译），写入定义表；解析失败（语法错、表达式编译错）部署即拒绝。
2. **启动实例**：`startProcessInstanceByKey` 按最新定义创建实例，令牌（Token）在开始事件生成，沿顺序流推进。
3. **令牌推进**：每个活动对应运行时 Execution（子流程/多实例产生子 Execution 树）；UserTask 生成任务待办等待 complete，ServiceTask 同步/异步执行委托逻辑，网关按条件路由令牌。**Token 模型是引擎核心抽象**：一个流程实例 = 一棵 Execution 树 + 一串任务。
4. **持久化**：每一步推进都写库——引擎的数据全部落关系型数据库（见下表），重启不丢状态；"流程卡死"多数时候不是引擎坏了，而是令牌停在一个等人工/等消息/等定时器的活动上。
5. **命令模式**：所有 API 调用封装为命令对象，经命令上下文执行，统一实现事务边界、拦截器钩子（日志、权限、多租户注入点）与异步执行（JobExecutor 扫描定时器/异步继续）。

```java
// 一次 complete 的真实链路（概念示意）
TaskService.complete(taskId, vars)
  → CommandContext 开启事务 → 查任务 → 执行变量更新
  → 令牌推进到下一活动（可能触发网关/服务任务/多实例）
  → 生成下一任务/触发 Job → 事务提交 → 异步执行器处理 Job
```

### 4.1 变量作用域与版本语义

- **变量五作用域**：全局（流程实例级，随处可读）、本地（任务/Execution 级，仅所在分支可见）、定义级（流程定义参数，所有实例共享只读）、多实例集合（会签集合变量，仅多实例内部可见）、历史变量（已结束实例的审计快照）。作用域搞错是"条件分支走错"的第二大根因（第一是变量名拼错）——排障时先查 ACT_RU_VARIABLE 确认变量落在哪个作用域。
- **版本语义**：每次部署同名流程定义，版本号 +1，`startProcessInstanceByKey` 默认启动最新版本；**已启动实例永远跑启动时的版本**——这是引擎的正确默认行为，但业务要意识到"老单走老流程、新单走新流程"可能造成两套逻辑并存，需要版本差异评估（改网关条件、删节点属于破坏性变更）。

### 4.2 历史等级（审计粒度）

- **none**：不记录历史，性能最好但不可审计——生产禁止。
- **activity**：记录实例与活动，不记变量——升级前的历史不可追踪业务数据。
- **audit**（默认）：追加任务与变量记录，满足一般审计。
- **full**：追加变量变化明细，可回答"谁在什么时候把字段改成什么"——合规强要求场景（金融/政务）使用，代价是历史表膨胀加速。

**部署语义补充**：部署接口支持增量校验（`duplicateFiltering`），同内容重复部署可跳过；`suspend` 挂起的定义不可启动新实例，存量实例不受影响——这是"废弃流程"的标准操作而非删除（删除会连带破坏历史表外键）。

**核心服务 API（嵌入式引擎五虎）**：

- **RepositoryService**：部署/查询流程定义，管理版本与挂起。
- **RuntimeService**：启动实例、信号/消息触发、流程实例修改（中国式审批的跳转/驳回就靠它的状态变更 API）。
- **TaskService**：任务查询、认领、完成、转办/委派、评论与附件。
- **HistoryService**：查询历史实例/活动/任务/变量，审计与统计的数据源。
- **IdentityService/ManagementService**：用户组管理、引擎运维（Job 重试、表查询）。

## 5. 表结构设计（ACT_* 表族）

| 表族 | 前缀 | 内容 | 量级特征 |
|---|---|---|---|
| 定义 | ACT_RE_ | 流程定义、模型、部署 | 少量，随版本发布增长 |
| 运行 | ACT_RU_ | 执行、任务、变量、Job | 中等，随并发实例波动，流程结束后清理 |
| 历史 | ACT_HI_ | 实例/活动/任务/变量审计 | **无限增长，运维头号治理对象** |
| 通用 | ACT_GE_ | 字节数组、属性 | 少量 |

> 🎯 核心要点：理解引擎 = 理解"XML 定义 → Token 推进 → 表持久化"三件事。面试问"流程卡死怎么办"的标准答案链条是：看 ACT_RU_EXECUTION 令牌停在哪 → 对应活动类型判断在等谁（人工/消息/定时器/Job 失败）→ 对症处理。

**命令模式的价值再强调**：命令模式看似只是"API 调用的包装"，实际是嵌入式引擎的架构灵魂——统一事务边界（每个命令一个事务）、统一异常处理（失败回滚 + Job 重试语义）、统一扩展点（拦截器可插入日志、权限、多租户、性能埋点）。理解这一点后，两个生产问题迎刃而解：其一，自定义拦截器是"全局切面"的正确位置，比散落业务代码里的 try-catch 干净得多；其二，命令内做外部调用（HTTP/RPC）会拉长引擎事务，是性能与死锁的常见来源——"引擎事务内只做本地工作，外部调用放事务外"应成为纪律。
