# 01-核心概念与演进史：工作流到底是什么

> 定位：把"工作流"从直觉概念还原成可工程化的定义——核心要素、工作流模式、与状态机/规则引擎/编排/AI Agent 的边界，以及从纸质表单到 Agentic Workflow 的六阶段演进。看懂这篇，后面所有引擎话题都有锚点。

## 1. 定义与核心要素

**工作流（Workflow）**：WfMC（工作流管理联盟）的经典定义——业务流程中可由计算机自动执行的、可部分或整体在参与者之间传递文档、信息或任务的过程。落到工程上，一句话：**把"业务过程"从代码里抽出来，变成数据（流程定义），再让引擎按数据驱动执行（流程实例）**。

一个工作流系统由六个要素构成：

- **流程定义（Process Definition）**：描述过程"长什么样"的模型——节点、连线、路由条件，即 BPMN XML 或 JSON 模型文件。
- **流程实例（Process Instance）**：一次具体的执行，携带自己的变量集（业务数据），同一定义可并发跑成千上万个实例。
- **活动（Activity）**：过程中的一个步骤，分用户任务（人等审批）、服务任务（系统自动执行）、网关（路由判断）。
- **任务（Task）**：用户活动的待办载体，有 assignee（处理人）、owner（责任归属）、到期时间、优先级。
- **路由（Routing）**：顺序、排他、并行、包容、循环五种流转逻辑，决定实例下一步去哪。
- **流转记录（Audit Trail）**：每一步谁在何时做了什么，历史表是合规审计的基础，也是"退回能退到哪"的计算依据。

> 💡 记忆锚点：流程定义 ≈ 类，流程实例 ≈ 对象，任务 ≈ 待办，路由 ≈ 控制流。引擎的本质是"解释流程定义的虚拟机"。

## 2. 工作流模式（Workflow Patterns）

工作流模式是范德阿尔斯特（van der Aalst）等学者从 200+ 真实业务流程中归纳出的 43 种控制流模式，是评估引擎能力的中立标尺。高频 8 种：

- **顺序（Sequence）**：A 完成后 B 开始，最基础。
- **并行分支（Parallel Split）**：一个节点分出多条互不依赖的分支，全部走。
- **同步汇聚（Synchronization）**：多条分支全部到达才继续（并行网关）。
- **排他选择（Exclusive Choice）**：多条件只走一条（排他网关）。
- **简单汇聚（Simple Merge）**：多条路径汇合，先到先走，无需等齐。
- **多实例（Multi-Instance）**：同一节点按集合批量执行，如会签/或签。
- **循环（Loop）**：重复执行直到条件满足（会签完成比例、驳回重提）。
- **取消（Cancel）**：终止实例或子流程，如发起人撤回、超时作废。

> 🎯 核心要点：判断一个引擎"行不行"，别数功能按钮，对着模式清单逐条验证——中国式审批的"退回任意节点"就是"取消 + 重新定位"模式的组合，大多数引擎默认不做，需要二次开发。

### 2.1 WfMC 参考模型五接口

WfMC 1995 年提出的参考模型定义了工作流管理系统与周边环境的五个标准接口，至今仍是理解工作流系统边界的框架：

- **接口 1（过程定义导入导出）**：流程定义的可互操作格式——XPDL 时代的标准，BPMN 2.0 出现后被替代。
- **接口 2（客户端应用）**：待办列表、任务处理等客户端接口——今天的待办中心、审批 App。
- **接口 3（调用应用）**：引擎调用外部应用的接口——今天的服务任务/Job Worker。
- **接口 4（工作流互操作）**：不同厂商引擎之间的流程互操作——实践中极少落地。
- **接口 5（管理与监控）**：审计、监控、管理接口——今天的 Operate、历史表、指标监控。

这五接口的价值在于提醒架构师：工作流系统的工程量不只在引擎，任务客户端、外部应用调用、监控管理三块占比更高——这正是"引擎给积木、平台定语义"的历史渊源。

### 2.2 用模式评估引擎

选型或自研前，把需求翻译成模式清单逐条打勾，比看功能列表可靠：

- 先列业务模式（如：会签=多实例+同步汇聚、退回=取消+重新定位、超时=竞争事件）。
- 再对着引擎文档查每个模式的实现路径（原生支持/API 可拼/需要二次开发）。
- 最后统计"需要二次开发"的模式数量，就是平台的真实工作量。

**三条模式教训**：其一，模式是中立标尺，厂商宣传的功能名靠不住，代码里见真章；其二，中国式审批模式组合（加签+退回+撤回）在多数引擎中无原生实现，这是平台层存在的理由；其三，模式清单会随业务演化，评估要留扩展空间，别为当下需求把架构焊死。

## 3. 与相邻概念的边界

- **状态机**：描述**一个对象**的状态流转（待审核→审核中→通过/驳回），关注对象生命周期；工作流描述**多参与者的过程协作**，关注任务流转。同一系统可叠加：订单用状态机管状态，审批过程用工作流管流转（详见 06 篇选型决策树）。
- **规则引擎**：解决"下一步条件怎么判断"（决策），工作流解决"下一步去哪"（路由）。流程复杂时用 DMN 把规则从流程中剥离（详见 06 篇）。
- **业务流程编排（Orchestration）**：跨服务、跨系统的工作流，工作流引擎（Camunda 8）就是编排器的一种实现；与之相对的是无中心控制者的编排合唱（Choreography）。
- **AI Agent**：Agent 自主规划"怎么做"，工作流确定性规定"何时何地做"——2026 年二者融合为 Agentic Workflow（详见 10 篇），不是替代关系。
- **定时任务调度**：Quartz 等调度器解决"按时间周期执行"（触发），工作流解决"按业务条件流转"（编排）——审批超时"自动通过"看似定时任务，实际必须由工作流的定时边界事件实现，因为只有流程上下文知道"这条审批该不该超时、超时后往哪走"。

## 4. 六阶段演进史

1. **纸质时代**：单据 + 签批流转，无系统、无审计、靠人盯。
2. **OA 电子流（1990s）**：办公自动化把签批搬进电脑，流程写死在代码里，改流程要改代码发版。
3. **工作流管理系统（WfMS，1990s-2000s）**：流程与业务解耦，WfMC 提出参考模型（过程定义互换 XPDL），"改流程不再改代码"成为卖点，但标准不统一、厂商各说各话。
4. **BPMN 标准化（2004-2013）**：BPMI 2004 发布 BPMN 1.0，OMG 2011 发布 BPMN 2.0（2013 年成为 ISO 19510），建模语言大一统；同期 jBPM → Activiti → Flowable/Camunda 分叉，开源引擎进入主舞台。
5. **云原生与分布式（2016-2025）**：Camunda 8 以 Zeebe 重写为分布式引擎；嵌入式引擎（Flowable/Activiti）向 Spring Boot 化、低代码平台化演进；2025 年 Camunda 7 CE 停止维护（详见 03/07 篇）。
6. **AI 融合（2025-）**：Agent 作为引擎的"服务任务"被编排，引擎提供确定性、审计与兜底，智能体工作流成为企业落地 AI 的主流形态（详见 10 篇）。

## 5. 2026 现状一句话

工作流引擎没有死，也没有被 Agent 取代——**确定性流程 + 自主智能体的混合编排**是企业级 AI 落地的共识形态；而传统引擎选型的核心矛盾从"功能够不够"转移到"许可与维护风险"（Camunda 8 生产许可、Activiti 9 Java 25 基线、Flowable 8 跨代升级）。

值得注意的另一条主线是**低代码平台的吞噬效应**：钉钉/飞书等平台把常见审批做成 SaaS 能力，传统 OA 自研工作流的需求在萎缩，但企业级复杂流程（跨系统、强合规、高定制）依然落在自建引擎上——2026 年的格局是"标准审批上平台，复杂流程留自建"，工作流工程师的价值更多体现在中国式语义、性能治理与 AI 编排三项硬功夫上。

> 🎯 核心要点：工作流的本质是"把过程变成数据、把执行交给引擎"。理解模式与边界，比记住某个引擎的 API 更值钱——因为 API 每代在变，模式二十年不变。
