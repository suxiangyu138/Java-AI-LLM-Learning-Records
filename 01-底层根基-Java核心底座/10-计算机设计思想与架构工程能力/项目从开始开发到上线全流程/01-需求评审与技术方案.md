## 1. 需求评审

### 1.1 评审前准备清单

```text
评审前必读 PRD（产品需求文档），带着问题去：

  □ 需求目标是什么？（解决什么问题？）
  □ 核心用户场景有哪些？（User Story）
  □ 关键业务流程是怎样的？
  □ 有哪些边界条件和异常情况？
  □ 依赖哪些外部系统/接口？
  □ 非功能性需求：并发量、数据量、响应时间？

必须向产品确认的三件事：
  1. 这个功能解决了谁的什么问题？← 确认价值
  2. 优先级排序：如果只能做 50%，保留哪些？← 砍需求准备
  3. 异常场景怎么处理？（空数据/超时/并发冲突）← 产品最容易漏
```

### 1.2 需求评审三大原则

| 原则 | 说明 |
|------|------|
| **闭环思维** | 每个需求必须有始有终：触发→处理→结果→异常 |
| **数据优先** | 先定义数据结构（表结构/接口字段），再讨论逻辑 |
| **砍需求勇气** | 宁少勿多；MVP 原则：最小可行产品 |

## 2. 技术方案设计模板

### 2.1 方案结构

```markdown
# [功能名称] 技术方案

## 1. 背景与目标
简单描述为什么做、解决什么问题、预期效果。

## 2. 核心流程
用流程图描述核心业务流程（主要路径 + 异常路径）。

## 3. 数据库设计
### 3.1 新增表
CREATE TABLE xxx (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    ...
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_user_id (user_id)
);

### 3.2 现有表变更
ALTER TABLE xxx ADD COLUMN ...;

## 4. 接口设计
### 4.1 POST /api/v1/xxx
请求参数 / 响应格式 / 错误码

## 5. 核心逻辑说明
关键业务逻辑的文字说明 + 伪代码

## 6. 缓存策略
哪些数据需要缓存？TTL？更新策略？

## 7. 异常处理
| 异常场景 | 处理方式 | 用户提示 |
| 并发冲突 | 乐观锁重试 | "操作繁忙，请重试" |

## 8. 影响范围与风险
- 影响哪些现有功能？是否需要数据迁移？

## 9. 测试建议
需要重点测试的场景

## 10. 工时估算
| 任务 | 工时 | 负责人 |
```

### 2.2 方案评审 CHECKLIST

```text
技术方案评审必须覆盖：

  □ 数据库索引是否合理？（覆盖查询场景）
  □ 接口是否幂等？（POST 尤其注意）
  □ 并发场景是否考虑？（锁、队列、幂等）
  □ 大促/峰值流量是否能扛？
  □ 异常是否有兜底？（超时降级、熔断）
  □ 是否需要数据迁移？（迁移方案+回滚方案）
  □ 是否影响现有功能？
  □ 是否需要配置开关？（灰度/紧急关闭）
```

| 工具 | 适用 | 特点 |

### 3.2 时序图示例（PlantUML）

```text
用户 → 前端：提交订单
前端 → Gateway：POST /orders
Gateway → 订单服务：创建订单
订单服务 → 库存服务：锁定库存
库存服务 → MySQL：UPDATE inventory
库存服务 → 订单服务：锁定成功
订单服务 → MQ：发送订单创建事件
订单服务 → Gateway：201 Created
Gateway → 前端：创建成功
前端 → 用户：显示订单详情
```

## 4. 接口定义规范

### 4.1 RESTful 设计原则

```text
URL 设计：
  GET    /api/v1/users          → 列表
  GET    /api/v1/users/{id}     → 详情
  POST   /api/v1/users          → 创建
  PUT    /api/v1/users/{id}     → 全量更新
  PATCH  /api/v1/users/{id}     → 部分更新
  DELETE /api/v1/users/{id}     → 删除

  ❌ POST /api/v1/deleteUser?id=123    -- 动词！应 DELETE + URL
  ❌ GET  /api/v1/getUserList           -- 动词！
```

### 4.2 统一响应格式

```json
// 成功
{
  "code": 200,
  "data": { "id": 1, "name": "Alice" },
  "message": "success",
  "timestamp": 1750000000000,
  "requestId": "uuid-xxx"
}

// 分页
{
  "code": 200,
  "data": {
    "list": [...], "total": 95, "page": 1, "size": 20
  }
}

// 错误
{
  "code": 40001,
  "data": null,
  "message": "用户名已存在",
  "timestamp": 1750000000000,
  "requestId": "uuid-xxx"
}
```

## 5. 工时估算

### 5.1 三点估算法

```text
工时 = (乐观 + 4×最可能 + 悲观) / 6

示例：用户注册功能
  乐观：2天（接口+数据库+简单校验）
  最可能：4天（含验证码、密码加密、事务处理）
  悲观：7天（含第三方短信接入、各种异常处理）
  估算 = (2 + 4×4 + 7) / 6 = 4.2天 → 报 5 天

常见遗漏项：
  ⚠️ 数据库迁移脚本 + 回滚脚本（至少半天）
  ⚠️ 单元测试（至少 30% 开发时间）
  ⚠️ 联调 + 自测（至少 1 天）
  ⚠️ Code Review 修复（预留 20% 缓冲）
```

### 5.2 工时模板

| 任务 | 工时 | 负责人 | 依赖 |
|------|:--:|:----:|------|
| 数据库设计 + 迁移脚本 | 0.5d | - | - |
| 接口开发 | 2d | - | 数据库 |
| 单元测试 | 1d | - | 接口 |
| 联调 + 自测 | 1d | - | 前端 |
| Code Review + 修复 | 0.5d | - | - |
| **合计** | **5d** | | |

---

> 🎯 **核心要点**：好方案 = **闭环的产品逻辑** + **合理的数据库设计** + **清晰的接口定义** + **充分的异常考虑**。方案阶段多花 1 天，开发阶段少返工 5 天。
