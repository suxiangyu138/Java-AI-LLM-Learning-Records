## 2. 发布 SOP

### 2.1 标准发布流程

```text
发布窗口：建议避开周五下午和节假日前后
推荐时间：周二到周四 14:00-17:00

标准 SOP：

  T-30min  发布通告（企业微信/钉钉/Slack）
  T-15min  部署到 Staging → 冒烟测试
  T+0min   开始生产部署
  T+5min   部署完成 → 冒烟测试（核心接口 + 健康检查）
  T+10min  观察监控（错误率、P99、CPU、GC）
  T+30min  灰度 5% → 观察 → 灰度 20% → 全量
  T+60min  确认发布成功 → 发布通告

关键原则：
  ✅ 每次发布必须有回滚方案
  ✅ 必须有值班人
  ✅ 任何阶段发现异常立即回滚
  ❌ 不要"修一下很快"→ 正式回滚，修复后重新走发布流程
```

### 2.2 冒烟测试

```bash
#!/bin/bash
# smoke-test.sh —— 发布后立即执行

BASE_URL="https://api.example.com"

# 健康检查
curl -fsS "$BASE_URL/actuator/health" || exit 1

# 核心接口（无鉴权）
curl -fsS "$BASE_URL/api/v1/public/status" || exit 1

# 核心接口（有鉴权）
TOKEN=$(curl -sS -X POST "$BASE_URL/api/v1/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"username":"monitor","password":"***"}' | jq -r '.data.token')

curl -fsS -H "Authorization: Bearer $TOKEN" "$BASE_URL/api/v1/users?size=1" || exit 1

echo "✅ 冒烟测试通过"
```

## 3. 回滚方案

### 3.1 回滚决策

```text
触发立即回滚的条件：
  🚨 错误率 > 1%（持续 2 分钟以上）
  🚨 核心流程不可用（登录、支付、下单）
  🚨 P99 延迟 > 正常值的 3 倍
  🚨 数据异常（多扣款、重复订单）
  🚨 安全漏洞暴露

不回滚的情况：
  → 非核心功能 Bug（可修复后灰度上线）
  → 可以热修复的配置错误
```

### 3.2 回滚操作

```bash
# K8s 回滚（最常用）
kubectl rollout undo deployment/user-service      # 回滚到上一个版本
kubectl rollout undo deployment/user-service --to-revision=3  # 回滚到指定版本
kubectl rollout status deployment/user-service    # 查看回滚状态

# 代码回滚（数据库已变更时）
# 1. 代码回滚到旧版本（kubectl rollout undo）
# 2. 执行数据库回滚脚本（flyway undo / 手动执行回滚 SQL）
# 3. 清理缓存（Redis 中与新版相关的 key）
# 4. 冒烟测试确认
```

### 3.3 数据库回滚

```sql
-- 正向迁移（V1.3__add_status_column.sql）
ALTER TABLE orders ADD COLUMN status VARCHAR(20) DEFAULT 'PENDING';
CREATE INDEX idx_status ON orders(status);

-- 回滚迁移（V1.3__rollback.sql）
DROP INDEX idx_status ON orders;
ALTER TABLE orders DROP COLUMN status;

-- ⚠️ 有数据的列回滚前务必确认不会丢失已有数据！
```

## 4. 监控与告警

### 4.1 黄金监控指标

```text
RED 方法（Google 推荐）：

  Rate      → 每秒请求数（QPS）
  Errors    → 错误率（5xx / 超时）
  Duration  → 响应时间（P50/P90/P99）

告警阈值配置（示例）：
  ┌──────────┬───────┬──────────────┐
  │ 指标     │ 警告  │ 严重         │
  ├──────────┼───────┼──────────────┤
  │ 错误率   │ >0.5% │ >1%          │
  │ P99延迟  │ >500ms│ >1000ms      │
  │ CPU      │ >80%  │ >95% (5min)  │
  │ 内存     │ >85%  │ >95% (5min)  │
  │ GC频率   │ >5/min│ >20/min      │
  │ DB慢查询 │ >10/s │ >50/s        │
  └──────────┴───────┴──────────────┘
```

### 4.2 告警通知分级

| 级别 | 通知方式 | 响应时间 |
|:--:|------|:-----:|
| **P0 严重** | 电话 + 短信 + 群通知 | 5 分钟内 |
| **P1 警告** | 群通知 + 邮件 | 30 分钟内 |
| **P2 提醒** | 邮件 | 工作时间 |

## 5. 应急响应

### 5.1 应急处理流程

```text
线上故障处理五步法：

  1. 止损（1-5 分钟）—— 最优先！
     □ 回滚？切流？扩容？限流？
     → 目标：先恢复服务，再找原因

  2. 定位（5-30 分钟）
     □ 看监控：错误率、P99、CPU 尖峰
     □ 看日志：ELK 搜 ERROR
     □ 看链路：SkyWalking/Zipkin 找最慢的 Span

  3. 修复（30 分钟 - ?）
     □ 热修复 or 回滚后逐步修复

  4. 验证
     □ 冒烟测试 + 监控恢复

  5. 复盘
     □ 故障报告：时间线、根因、改进措施
```

### 5.2 常见故障速查

| 症状 | 先看什么 | 常见原因 |
|------|---------|------|
| CPU 飙升 | top -Hp → jstack | 死循环/频繁GC/序列化 |
| 内存飙升 | jmap -histo | 内存泄漏/大对象 |
| 响应变慢 | SkyWalking Span | 慢SQL/远程调用超时 |
| 错误率突增 | 日志 + 监控 | 发布变更/第三方故障/流量突增 |
| 端口无响应 | ss -tlnp | 进程挂了/端口冲突 |
