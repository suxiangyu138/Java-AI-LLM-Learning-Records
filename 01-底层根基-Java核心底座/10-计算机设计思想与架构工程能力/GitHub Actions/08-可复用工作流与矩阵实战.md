# 08-可复用工作流与矩阵实战：收敛重复、放大验证

> 定位：团队 CI 烂掉的两种姿势——"每个仓库一份复制粘贴的工作流"（改一处改十处）与"矩阵无限膨胀"（烧钱）。本篇讲透 reusable workflows、复合 Action 与矩阵策略的正确用法，并给出 Java 项目标准流水线模板。

## 1. 可复用工作流（Reusable Workflows）

`workflow_call` 事件让一个工作流可以被其它仓库/工作流调用，是"一套 CI 逻辑，N 个仓库复用"的标准机制：

```yaml
# 被调用方 .github/workflows/java-ci.yml
name: Java CI（可复用）
on:
  workflow_call:
    inputs:                        # 输入契约（调用方 with 传入）
      java-version:
        type: string
        default: '21'
      run-tests:
        type: boolean
        default: true
    secrets:                       # 显式声明需要哪些 secrets
      DOCKER_TOKEN:
        required: false

# 调用方
jobs:
  ci:
    uses: org/java-ci/.github/workflows/java-ci.yml@v1
    with:
      java-version: '17'
    secrets: inherit               # 继承调用方全部 secrets（慎用）或逐项传入
```

**关键限制与纪律**：① 被调工作流有自己的 `permissions`，不会继承调用方——安全上反而更干净；② `secrets: inherit` 会把调用方全部 secrets 暴露给被调工作流（多仓库复用时等于把密钥面放大），**优先显式声明 + 逐项传**；③ 被调方 `on` 只能有 `workflow_call`（可混 `workflow_dispatch` 便于手动测）；④ 版本管理用 tag/分支引用（`@v1`），升级走 Dependabot 或显式 bump；⑤ 跨仓库调用仅限公开仓库或同 org 私有仓库。

**复合 Action vs 可复用工作流**：复合 Action 打包的是"步骤组"（在单个 job 内展开）；可复用工作流打包的是"整条流水线"（独立 job、独立 Runner、可配矩阵）。选型：只复用步骤 → composite；复用完整 job 链 → reusable；两者可嵌套（工作流里调复合 Action）。

**可复用工作流的限制与设计权衡**：其一，被调工作流的 job 不能挂 `environment` 之外的运行时依赖（如不能声明 runner group 之外的自托管标签限制），复杂的环境映射要在调用方做；其二，矩阵不能跨工作流传递（被调工作流内部可以有自己的矩阵，但调用方无法动态改它的矩阵结构）——"动态矩阵"需求要在调用方层解决（本节后面的路径过滤方案）；其三，**调试复杂度上升**：可复用工作流的日志散在调用方运行详情里，出问题时定位链变长，设计时要在被调方留足诊断输出（step 摘要、关键变量回显）；其四，版本管理是成败关键——`@v1` tag 语义要团队约定（滚动 minor 还是只动 major），否则"悄悄改了被调方，调用方全挂"是常态事故。

## 2. 矩阵策略：放大与收敛

矩阵（matrix）把 job 复制为"多版本 × 多平台"组合，是验证矩阵（兼容性测试）的标配：

```yaml
strategy:
  fail-fast: false            # 生产建议 false：多平台失败各自呈现，不互相取消
  matrix:
    os: [ubuntu-latest, windows-latest]
    java: ['17', '21']
```

**矩阵纪律五条**：① 组合数是笛卡尔积——`3 × 3` 就是 9 个 job、9 份 Runner 计费，**区分"验证矩阵"（全组合，发版前跑）与"常规矩阵"（代表组合，日常跑）**；② `include` 注入附加维度（`profile`、`dist`），`exclude` 剔除无意义组合（Windows × Java 21 无兼容诉求就排除）；③ `fail-fast: false` 让多平台各自报告，避免一个失败取消全部浪费其它平台结果；④ **动态矩阵**：`fromJSON` 从文件/API 读取组合列表——"改矩阵不用改工作流"的配置化方案（测试用例分片、镜像清单驱动）；⑤ 矩阵上限 256 组合，超大验证分多个工作流跑。

**矩阵 + 路径过滤的组合**：变更只影响服务 A → 只跑 A 的矩阵成员。实现：前置 job 输出变更列表（`gh api` 对比或 `dorny/paths-filter`），下游 `needs.changes.outputs.*` 动态过滤矩阵——这是"大仓库按服务收敛 CI"的标准姿势。

**动态矩阵的工程细节**：`dorny/paths-filter` 是事实标准——声明"服务 A → src/a/**"，输出 `changes.a = 'true'`；下游 job 的矩阵从 `fromJSON` 拼装：`matrix: ${{ fromJSON(needs.changes.outputs.matrix) }}`（前置 job 把"哪些服务被变更"序列化为 JSON 数组输出）。三个注意点：其一，前置 job 本身要极快（路径检测无构建），否则矩阵等待时间反超收益；其二，矩阵为空数组时工作流直接失败——前置 job 输出兜底组合（如"全部未命中时跑 lint 代表组合"）；其三，变更检测基于 git diff 对比，依赖 `fetch-depth: 0`（checkout 全量历史），浅克隆会导致检测失效。

### 3.1 门禁常见错误清单

1. **分支保护勾错对象**：分支保护里勾的是 **job 名**（如 `test`、`lint`），不是 workflow 文件名——勾错后"任意一个 job 跑过"就算通过，门禁形同虚设。
2. **参考检查当必查**：把覆盖率报告、性能基准这类"会波动、低频有意义"的检查挂进必查，团队被迫频繁重跑，最终关掉门禁——参考类用 `continue-on-error`（08 篇模板）。
3. **needs 环与无谓串行**：`a needs b` 且 `b needs a` 直接报错；更重要的是"无依赖却用 needs"——两个独立 job 加 needs 后丧失并行，CI 时间翻倍却无收益。
4. **环境审批与并发组冲突**：部署 job 挂了环境审批 + `concurrency` 组，审批通过后并发组可能已取消该运行——部署被静默取消是重试场景的高频事故，设计时把"审批通过后的重跑路径"想清楚。
5. **fail-fast 与矩阵的交互**：矩阵 + `fail-fast: true` 时，一个成员失败会取消全部成员——多平台测试要 `fail-fast: false`，否则 Windows 失败会把 Linux 结果一起扔了。

## 3. 门禁实践：needs 链与质量门禁

- **needs 链**：`build → test → deploy` 串行依赖用 `needs` 表达；同层并行（`lint`/`test`/`scan` 互不依赖）自动并行。**门禁即合并检查**：分支保护勾选关键 job，形成"未过测试不能合并"的硬约束。
- **质量门禁**（与《CI/CD 与灰度发布》门禁四层呼应）：SonarQube 类工具在 CI 里 `waitForQualityGate`——覆盖率/违规数不达标即失败；这类 job 用 `continue-on-error: false` 挂进必查，覆盖率**报告**类用 `continue-on-error: true` 挂参考。
- **环境审批门禁**：部署 job 挂 `environment: production` + required reviewers——"代码自动过、部署人审批"（06 篇安全拓扑的第二层）。
- **并发门禁**：`concurrency` 防重复部署（02 篇）；tag 发布用 `if: startsWith(github.ref, 'refs/tags/')` 防误触发。

## 4. Java 项目标准流水线模板（生产可抄）

```yaml
name: CI
on:
  push:
    branches: [main]
    paths: ['src/**', 'pom.xml', '.github/workflows/*.yml']
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read
  checks: write

jobs:
  lint:                       # 快速反馈层（2 核足够）
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '21', cache: maven }
      - run: mvn -B verify -DskipTests
        env: { MAVEN_OPTS: '-Dstyle.color=never' }
  test:                       # 验证矩阵层（arm64 省钱）
    needs: lint
    runs-on: ubuntu-24.04-arm
    strategy:
      fail-fast: false
      matrix: { java: ['17', '21'] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: ${{ matrix.java }}, cache: maven }
      - run: mvn -B test
      - uses: actions/upload-artifact@v4
        if: always()          # 失败也上传报告
        with: { name: test-reports-${{ matrix.java }}, path: '**/target/surefire-reports/*.xml' }
```

模板设计要点：lint 先行快速失败、矩阵管版本兼容、`if: always()` 保报告、arm64 降本、权限最小化、路径过滤防空跑——五条齐了才是生产级（完整门禁/部署链参考 09 篇规范与《CI/CD 与灰度发布》）。

### 4.1 模板的版本化与演进

模板仓库本身也要版本管理：主分支是"当前标准"，打 tag 发布稳定版（`template@v1`）；存量仓库按需升级（改模板 → 发 tag → 各仓库跟进），避免"模板一改，全公司 CI 一夜之间全变"的失控。演进节奏建议：新语法（如并行步骤）先在模板里试用验证，稳定后再推广到存量仓库——模板是"最佳实践的承载体"，它落后了，团队的 CI 水平就落后了。推广的阻力通常不是技术而是习惯：配合 09 篇的"模板 → 门禁 → 复盘"三步走，模板的价值才能真正释放——**一套好模板省的不是一次开发，而是 N 个仓库 × 每次维护**。

**可复用体系与矩阵的治理节奏（把本篇串成闭环）**：可复用工作流与矩阵不是"建完就完"的静态资产，而是随团队演化的活系统——季度审视四个指标：① 复用率（多少仓库在调模板，低于 70% 说明模板脱离实际）；② 矩阵平均成员数（长期膨胀说明没做收敛）；③ 模板变更频率（频繁小改说明设计不稳，考虑拆细粒度可复用件）；④ 空跑率（路径过滤失效的信号）。把治理节奏写进团队例会的固定议程，可复用体系才不会沦为"另一个没人维护的仓库"——这与《软件工程上的设计思想》里"配置与演进"的思想同源：任何工程资产都需要显式的演进管理。

> 🎯 核心要点：可复用是"团队级工程"，矩阵是"成本级工程"——复用收敛的是维护成本，矩阵收敛的是运行成本。一套好的 CI 模板 = 复用骨架 + 动态矩阵 + 分层门禁，让"新仓库加 CI"从半天变成十分钟。
