# 01-核心概念与事件模型：Actions 是什么、被什么触发

> 定位：GitHub Actions 的本质是"事件驱动的 YAML 流水线声明"——把 CI/CD 逻辑写成数据（workflow 文件），GitHub 平台负责触发、调度与执行。本篇讲清组件层次与触发事件全解，是所有后续篇章的地基。

## 1. 核心组件层次

一个 workflow 由五层嵌套组件构成，理解层次是阅读任何工作流文件的第一步：

- **Workflow**：一个 `.yml` 文件（位于 `.github/workflows/`），声明"何时运行、跑什么"的完整流水线，一个仓库可放多个工作流，互不感知。
- **Job**：工作流内的一个执行单元，默认与其它 job **并行**运行；通过 `needs` 声明依赖后串行。job 拥有独立的运行环境与工作目录。
- **Step**：job 内的一个步骤，**顺序**执行，共享同一个 shell 与工作目录；前一步失败默认中断后续步骤（除非 `continue-on-error`）。
- **Action**：可复用的最小执行单元，是"市场里的零件"——`uses:` 引入官方或第三方 Action，或在步骤内直接 `run:` shell 命令。
- **Runner**：执行 job 的物理环境，GitHub 托管的免费/付费虚拟机，或自托管机器（详见 04 篇）。

层级口诀：**工作流（文件）→ 作业（并行单元）→ 步骤（顺序单元）→ 动作（复用零件）→ Runner（执行环境）**。

```yaml
name: Java CI            # Workflow
on: [push]               # 事件
jobs:                    # Jobs（可并行）
  build:                 # Job 1
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4      # Action（复用零件）
      - uses: actions/setup-java@v4    # Action
        with:
          distribution: temurin
          java-version: '21'
      - run: mvn -B test               # Step（shell 命令）
```

## 2. 触发事件全解

事件是工作流的"开关"，按使用频率分四主类：

**push 与 pull_request（代码事件，最高频）**：

- `on: push`：推送到分支/标签触发，可用 `branches`、`tags`、`paths`、`paths-ignore` 过滤——`paths` 过滤（如 `paths: ['src/**', 'pom.xml']`)是减少无效运行的第一成本杠杆（详见 09 篇）。
- `on: pull_request`：PR 打开/同步/关闭时触发，`types: [opened, synchronize, reopened, ready_for_review]` 控制触发时点；`pull_request_target` 是特殊变体——在**目标分支**上下文中运行，可访问目标分支的 secrets，用于"机器人评论"类场景，但它是安全重灾区（恶意 PR 可篡改代码被执行），必须慎用（详见 06 篇）。

**schedule（定时事件）**：cron 表达式触发，2026-03 起支持 `timezone` 字段（IANA 时区），不再被 UTC 束缚：

```yaml
on:
  schedule:
    - cron: '0 2 * * 1'          # 每周一 02:00
      timezone: 'Asia/Shanghai'  # 2026 新增：显式时区
```

注意定时任务不保证精确到秒，最小粒度分钟；cron 表达式只能 5 段（分 时 日 月 周）。

**workflow_dispatch（手动事件，运维最常用）**：Web 界面/API 手动触发，可定义输入参数（`inputs`），2025 起输入数量上限从 10 提升到 **25**：

```yaml
on:
  workflow_dispatch:
    inputs:
      environment:
        description: '部署环境'
        required: true
        default: 'staging'
        type: choice
        options: [staging, production]
```

**repository_dispatch（外部系统事件）**：通过 GitHub API 的 `POST /repos/{owner}/{repo}/dispatches` 触发，`client_payload` 携带自定义数据——"外部系统完成后再触发流水线"的解耦通道，比轮询干净。

**其它常用事件**：`release`（发版）、`issues`/`issue_comment`、`workflow_run`（另一个工作流完成——工作流间串联的标准方式）、`merge_group`（合并队列）、`deployment` 等。

### 2.1 过滤条件的细节与陷阱

`branches`/`tags`/`paths` 过滤有三个高频翻车点，逐个讲清：

- **通配符语义**：分支匹配用 glob——`branches: ['release/**']` 匹配 `release/1.0` 但不匹配 `release` 本身（`**` 需要斜杠上下文）；`paths: ['**/*.md']` 的 `**` 可跨目录。写过滤条件先想清楚"我要匹配的字符串长什么样"，再用表达式测试页验证。
- **paths 的目录陷阱**：`paths: ['docs/**']` 表示**只**在 docs 变更时触发（而非"docs 变更时也触发"）——想"代码或文档变更都触发"要写完整列表；更常见的坑是**用 paths 过滤 push 事件后，PR 事件未同步配置 paths，导致 PR 空跑**——push 与 pull_request 是两套过滤，必须各自配置。
- **paths 与 merge 的交互**：分支合并产生的 push 事件同样受 paths 过滤；若 A 分支改了 docs 而 B 分支改了代码，合并时"代码变更"会被计入，A 的 CI 可能空跑——这是 paths 过滤的固有语义，接受它（省分钟）还是换"变更检测 job"（08 篇动态矩阵），按团队对"空跑容忍度"选。

## 3. 事件与分支保护的联动

PR 事件的价值不止"跑测试"，更在于与**分支保护规则**结合成门禁：

- 分支保护里配置"Required status checks"勾选工作流 job（如 `build`、`test`），该 job 失败则 PR 无法合并——这是"CI 是合并门禁"的机制基础。
- 2023 起 GitHub 默认配置 "Require branches to be up to date" 与 checks 的配合；合并队列（merge queue）则要求 `merge_group` 事件的工作流——启用合并队列的仓库必须为事件注册工作流，否则队列永远卡住。
- 门禁设计要区分"必查"与"参考"：lint、单元测试、安全扫描设必查；性能基准、覆盖率报告设参考（`continue-on-error`），避免低频噪声阻塞合并（参考《CI/CD 与灰度发布》门禁四层）。

**分支保护的三个实践细节**：其一，勾选的是 job 名不是 workflow 名——分支保护页面列出的是每个工作流里的 job（如 `test`、`lint`），勾错对象会导致门禁形同虚设（08 篇有完整清单）；其二，PR 的"改动后重新检查"——合并前最后一次 push 必须重新跑完必查 job，否则"我改完没跑测试就合了"；其三，合并队列（merge queue）与 `merge_group` 事件——启用合并队列的仓库必须给该事件配工作流（哪怕是快速空跑确认），否则队列永远阻塞；合并队列的价值是"CI 结果有效时快速合入"，团队用不用它按吞吐需求决定，别为了用而用。

**门禁与 fork 的联动**：外部贡献者（fork）的 PR 默认**不访问 secrets、不改写仓库**——这是平台安全边界；需要"fork PR 跑完整测试"时用 `pull_request`（只读上下文跑公开内容）或人工确认后重跑，**绝不**用 `pull_request_target` 直接信任 PR 内容（06 篇安全章节详述攻击链）。团队规范里要写清"fork PR 的 CI 策略"，这是开源协作仓库的必修课（呼应《Git 知识体系》Fork 工作流）。

### 3.1 事件选择的决策准则

事件多，别乱用——每个事件对应一类场景，选错事件的代价是"空跑"或"漏跑"：

- **代码质量验证** → `push`（主干直推）与 `pull_request`（合入前验证）双配：push 管"主干不破"，PR 管"合入前把关"，两条线缺一不可。
- **定期任务**（依赖更新、报表生成、缓存预热）→ `schedule`：优先合并低频任务（一天一次全量，不要每仓库各跑一遍），配合时区字段把执行时间对齐业务时段。
- **人工触发**（部署、回滚、临时验证）→ `workflow_dispatch`：所有"按需操作"都应该有手动入口——把部署类操作做成手动触发 + 环境审批，比"推 tag 自动发版"更可控。
- **外部系统联动**（消息队列回调、CRM 事件）→ `repository_dispatch`：用 client_payload 传业务数据，注意 payload 大小限制与幂等（外部重发时工作流要能容忍重复触发）。
- **工作流串联** → `workflow_run`：A 完成后再跑 B，替代"B 轮询 A 状态"的笨办法；用 `workflow_run.workflows` 指定上游，配合 `concurrency` 防重。

决策口诀：**代码变 → push/PR；时间到 → schedule；人按 → dispatch；外部来 → repository_dispatch；上游完 → workflow_run**。

选事件时顺带做"防重复"设计：push 与 PR 可能对同一变更双触发（PR 合入的 merge commit 触发 push）——需要"只跑一次"的场景（发版、部署）用事件级 `concurrency` 或 tag 过滤收敛；CI 的"重复跑一遍"可接受（幂等），部署类必须防重。**触发设计 = 事件选择 + 过滤条件 + 防重复**三件套，缺一件都是生产事故的伏笔。

## 4. 运行时上下文与事件载荷

工作流启动后，平台注入两类数据：

- **GITHUB_ 环境变量**：`GITHUB_REF`（当前 ref）、`GITHUB_SHA`（提交）、`GITHUB_EVENT_NAME`（触发事件名）、`GITHUB_WORKSPACE`（工作目录）、`GITHUB_RUN_ID`（本次运行 ID，日志关联与制品命名的黄金字段）等 20+ 个。
- **事件载荷文件**：`GITHUB_EVENT_PATH` 指向的事件 JSON 文件，含事件全部细节（PR 标题、issue 评论、commits 列表）——取事件细节用 `jq -r '.pull_request.title' $GITHUB_EVENT_PATH`。

上下文对象的完整用法在 03 篇展开，这里记住一个原则：**事件信息优先从上下文/载荷取，不要解析 git 命令输出**——平台注入的数据更可靠，且不依赖 shell 环境。

## 5. 2026 事件侧变化速览

- schedule 支持 `timezone` 字段（2026-03-19，晚于 GitHub Actions Late March 2026 updates）。
- workflow_dispatch 输入上限 25（2025 起）。
- `actions/setup-java` 等官方 Action 持续更新，多版本矩阵配 `distribution` 选项已成标准写法。
- 新仓库默认 `permissions: read-all`（2023-02 起），旧仓库需显式收紧（06 篇）。

> 🎯 核心要点：Actions 的"触发"是数据驱动的——事件决定何时跑，过滤条件决定哪些变更跑，分支保护决定跑了有没有用。写工作流前先问三个问题：哪个事件触发？要不要路径过滤？这个 job 是不是合并门禁？
