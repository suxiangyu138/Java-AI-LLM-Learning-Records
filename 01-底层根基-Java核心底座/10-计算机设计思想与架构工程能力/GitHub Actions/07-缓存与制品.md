# 07-缓存与制品：依赖复用、跨 Job 传递与存储成本

> 定位：缓存与制品是 CI 提速与产物留存的左右手——缓存让依赖"装一次用十次"，制品让构建结果"跨 job、跨运行"传递。本篇讲透缓存 key 设计（含 2026 新限流）、制品生命周期与存储计费，以及"缓存 vs 制品"的分工边界。

## 1. 依赖缓存：原理与 key 设计

`actions/cache` 是键值存储：运行结束时把指定路径存进缓存（post 步骤自动执行），下次运行按 key 命中则直接恢复，跳过安装：

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.m2/repository      # Maven 本地仓库
    key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}
    restore-keys: |
      ${{ runner.os }}-maven-   # 未精确命中时回退匹配
```

**key 设计的三个原则**：

- **内容哈希优先**：`hashFiles('**/pom.xml')` 是依赖缓存的标准 key——依赖声明变 → key 变 → 自然重建；比"按分支/按日期"精确得多。
- **restore-keys 是"降级命中"**：精确 key 未命中时按前缀回退最近缓存（如 pom 改动后仍复用旧依赖缓存跑一次，本轮存新 key）——回退命中能省"全量重装"的首次开销，但要注意旧缓存可能与新依赖不匹配（Maven 会补下载缺失项，通常安全）。
- **维度合并**：key 里带上 `runner.os` 与工具链版本（JDK 大版本），避免跨平台/跨版本串缓存——串用是缓存污染的经典来源。

**缓存与 setup 工具的联动（Java 工程的标准姿势）**：`actions/setup-java@v4` 内置 `cache: maven`（以及 gradle、sbt 等）——它自动完成"找 Maven 本地仓库路径 + 用 hashFiles 算 key + 上传/恢复"三件事，与手写 `actions/cache` 的效果一致但少三行配置、少一处出错机会。它的 key 内部结构是"工具版本 + hashFiles 依赖文件"，升级 JDK 或改 pom 都会自然失效重建。**什么时候才需要手写 cache**：缓存内容不是依赖目录（如工具链二进制、预构建镜像层）时——手写场景记住"路径必须精确到可复用目录，别把临时目录当缓存"。推荐顺序：setup 工具内置缓存优先 → 官方 cache Action → 自研；官方能做的别自己发明。

**多仓库共享缓存的现实**：缓存的隔离粒度是仓库——org 内多仓库无法直接共享缓存（自托管 Runner 挂同一台机器时，`~/.m2` 落在 Runner 持久盘可"物理共享"，但这是隐式依赖，Runner 换机即失效，且违反"环境干净"原则，不建议当方案）。跨仓库依赖复用靠私有制品库（Nexus/Artifactory 镜像 Maven 中央仓库），不是缓存——**缓存是运行间的短期复用，制品库是依赖的长期共享**，两者职责不同（呼应 08 篇的依赖管理视角）。

**2026 限流变化（2026-01-16 起）**：缓存**上传**限 200 条/分钟/仓库（下载不限）——"缓存抖动"（cache thrash，key 每次变导致每次重存）会撞限流，表现为缓存上传静默失败。对策：合并缓存 key（如 Maven 与 Gradle 分仓合并为单一 key 族）、矩阵 job 错峰完成、减少无谓的 key 变化（hashFiles 的 glob 别写太宽）。

**配额与费用**：缓存每仓库免费 **10GB**，超出按 LRU 驱逐（旧缓存先被清）；2025 末起可付费扩容（超量约 $0.07/GB/月）。容量治理：只缓存依赖目录，不缓存工作区、日志与制品（那是制品/临时文件的职责）。

**缓存命中与排障**：仓库 Settings → Actions → Caches 页面可看缓存清单与命中情况（命中率 = 命中次数 / 总请求数）。命中率长期低于 60% 说明 key 设计有问题——按顺序排查：key 里是否含"每次变的值"（时间戳、run-id 是典型误用，应只放内容哈希与版本维度）；restore-keys 是否缺失（只有精确 key 没有回退，第一次改动就全量重装）；缓存是否被矩阵维度污染（os 混用、JDK 版本混用导致反复失效）。命中率是缓存治理的核心 KPI，纳入 09 篇的成本报表。

**restore-keys 的命中语义（容易被误解）**：精确 key 未命中时，GitHub 按 restore-keys 列表**前缀最长匹配**最近的缓存，并把命中的 key 记为 `CACHE_KEY`；运行结束写缓存时用精确 key 保存——即"本次用旧缓存跑，跑完存新 key"，下次起用新 key。注意 restore 命中的缓存是"读"，不会因读取而更新它的有效期——长时间未更新的缓存仍可能被 LRU 驱逐，关键依赖缓存要关注陈旧度。

## 2. 制品（Artifacts）：跨 Job 与跨运行传递

`upload-artifact` 把文件/目录上传为运行级制品，`download-artifact` 在其它 job 拉取：

```yaml
# 构建 job：上传制品
- uses: actions/upload-artifact@v4
  with:
    name: jar-artifacts
    path: target/*.jar
    if-no-files-found: error    # 产物缺失直接失败（防静默空传）
# 部署 job：下载制品
- uses: actions/download-artifact@v4
  with:
    name: jar-artifacts
    path: release/
```

**制品与缓存的分工（高频面试辨析）**：缓存是"装过的东西再复用"（依赖、工具链，自动清理、不计审计）；制品是"构建出来的东西要留证"（jar、镜像清单、测试报告、SBOM，有保留期、可下载、可审计）。同一次运行内 job 间传数据，轻量值用 `GITHUB_OUTPUT`（秒级、无存储），文件级用制品。

**制品生命周期**：默认保留 **90 天**（可配 1-400 天）；保留期内可下载、可被复用（如手动触发部署拉取上次构建产物）；过期自动删除。发布类制品（如 release 附件）用 `gh release` 单独留存，不受 90 天限制。

**存储计费**：制品与 GitHub Packages **共享存储池**——Free 500MB、Pro 1GB、Team 2GB、Enterprise 50GB，超量约 $0.25/GB/月。成本治理：上传前裁剪（只传 jar 不传 classes/、只传报告摘要）、设置保留期上限（流水线制品 7-30 天足够）、定期清理（API 或 Actions 定时任务删除陈旧制品）。

### 2.1 制品实践细节与安全

- **上传裁剪**：`path` 支持 glob 与多路径（`path: |` 多行列举）；`if-no-files-found: error` 防止"产物没生成还上传成功"的静默事故（07 篇模板已示范）。裁剪原则：只传"消费方需要的最小集合"——测试报告传 XML 摘要不传 HTML 全量、jar 传目标产物不传 classes 目录。
- **下载与重命名**：download 时可用 `merge-multiple: true` 合并同名单制品（矩阵各成员上传同名制品后合并下载）；重命名在下载后做，别在 upload 阶段做（同 key 覆盖是事故源）。
- **制品与运行保留的关系**：制品保留期独立于运行记录保留期——运行记录删了制品还在；清理任务（API 删旧制品）与"运行保留 90 天"是两套旋钮，治理时别只调一个。
- **制品的审计价值**：制品是"这个构建到底产出了什么"的唯一证据——发版链路里 release 附件、SBOM、签名哈希都从制品导出，制品管理的秩序直接决定供应链审计的质量（衔接 06 篇）。

**制品命名的规范（可追溯性的根基）**：制品名是"构建 → 提交 → 产物"三角关联的索引——命名规则建议"产物名-平台-版本"（如 `app-linux-amd64-1.4.2.jar`），版本来源用 `GITHUB_SHA` 短哈希或语义版本；矩阵成员上传同名制品时用 `merge-multiple` 或按矩阵维度命名区分；下载侧的路径规划（`path: release/`）保持稳定，部署脚本引用的路径不随版本变——**路径稳定 + 名称带版本**，是制品链路可追溯与可回滚的两个支柱。缓存放量、制品收敛，存储账单才能稳定在免费线内。

## 3. 输出传递的完整方案

step → step：`GITHUB_OUTPUT`（`echo "key=value" >> $GITHUB_OUTPUT`，下游 `steps.id.outputs.key` 读）；step 状态跨 step：`GITHUB_STATE`。job → job：job `outputs` + `needs`（02/03 篇）。运行 → 运行：制品（留证）或缓存（复用）。选型一句话：**值小且即时 → OUTPUT；文件且要留证 → 制品；依赖且要提速 → 缓存**。

## 4. 安全衔接：制品与供应链审计

- 制品里附 **SBOM**（依赖清单，Maven 的 `cyclonedx-maven-plugin` 生成）与**签名/校验和**——"产物 + 清单 + 签名"三件套是供应链审计（06 篇）的交付物。
- 制品名与 `GITHUB_RUN_ID` 关联命名（`app-${{ github.run_id }}.jar`），实现"哪个构建、哪个提交、哪个产物"可追溯闭环。
- 下载制品到部署 job 时校验哈希（upload 时输出哈希、download 后比对），防传输/存储层篡改。

> 🎯 核心要点：缓存与制品各司其职——**缓存求快、制品求证**。key 设计三原则（内容哈希、回退前缀、维度合并）与 2026 上传限流的配合，是缓存治理的全部；制品三件事（裁剪上传、保留期、SBOM 附签）是存储成本与审计合规的全部。
