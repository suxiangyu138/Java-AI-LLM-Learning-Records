# 03-表达式与上下文：`${{ }}` 的语法、函数与陷阱

> 定位：表达式是 Actions 的条件逻辑核心——"这个 job 跑不跑、这个步骤传什么参数、矩阵怎么拼"全靠它。本篇讲透表达式语法、函数集与九大上下文，并给出 if 条件的全部陷阱与 2026 改进。

## 1. 表达式语法与求值时机

表达式用 `${{ }}` 包裹，在**工作流运行前**由平台求值（不是 shell 求值），支持以下位置：`if`、`with` 输入、`env`、矩阵字段、job 名称、`run-name`、并发分组等。

两个关键认知：

- **求值时机**：`${{ }}` 在 job 启动前替换完成——所以它无法读取"步骤运行中才产生"的值（那要用 `GITHUB_OUTPUT` 传递后由下游步骤的表达式读取）。
- **`if:` 的隐式求值**：`if:` 条件里写 `if: github.event_name == 'push'` 时不加 `${{ }}` 也会被求值；但加了更清晰，且 2026-01 起编辑器会校验 `${{ }}` 外的游离文本。

**字面量**：`true`/`false`、`null`、数字、字符串（单引号包裹，`''` 转义单引号）。**真值规则**：`if:` 结果类型转换——布尔直接用；字符串空串为假、非空为真；数字 0 为假；`null` 为假。所以 `if: github.ref` 的写法（ref 存在才跑）依赖"空串为假"的规则。

**表达式能用在哪（求值边界）**：表达式可以出现在 `if`、`with` 输入、`env` 值、矩阵字段、job 名称、`run-name`、concurrency 分组等**元数据位置**；但**不能**出现在 `uses` 的 Action 引用部分（`uses: actions/${{ inputs.action }}@v4` 是合法的拼装用法，但引用路径本体必须静态可解析——GitHub 官方文档明确 `uses` 的动态路径有限支持，靠它做"按参数选 Action"有版本解析风险，能用 `if` 分步就别拼路径）；也不能在 `run:` 命令的"语法位置"（`${{ }}` 会先于 shell 展开，无法给 shell 结构补全）。理解求值边界，才能判断"这个动态需求该用表达式还是该拆 job"——凡是"运行中才知道的值"，一律走输出文件 + 下游步骤读取，不在表达式里赌时机。

**字符串与数字的类型陷阱**：`'21'`（字符串）与 `21`（数字）在 `==` 下相等，但 `'21' > 3` 这类混合比较行为与直觉不符（字符串与数字比较按字符串规则还是数字规则取决于具体实现）——安全写法是**同类型比较**：数值一律 `fromJSON('21')` 后比较，或统一转字符串后 `==`。矩阵里的 `java-version: '21'` 常以字符串存在，比较前先确认两端类型，是"条件不生效"类问题的第二大来源（第一是游离文本）。

## 2. 运算符与宽松比较

- **比较**：`==`、`!=` 是**宽松比较**——数字与字符串可互比（`'21' == 21` 为真），这带来 `if: inputs.java-version == 21` 这类写法可行；`<`、`>`、`<=`、`>=` 只对数字语义生效。
- **逻辑**：`&&`、`||`、`!`；**没有三元运算符**，条件赋值用 `case` 或 `format` 拼。
- **2026 case 函数**：SQL 风格多分支，替代长串 `&&`/`||`：

```yaml
if: ${{ case(fromJSON('["prod", "staging", "dev"]').contains(inputs.env),
             when: '${{ inputs.env == "prod" }}', then: 'release',
             when: '${{ inputs.env == "staging" }}', then: 'test',
             else: 'dev') }}
```

（写法示意）case 的实义是：把"环境 → 分支/参数"的映射写成可读分支，比链式短路表达式可维护得多，特别适合部署映射场景。

## 3. 核心函数集

按用途分组记忆：

- **判断类**：`contains(s, sub)`（字符串/数组包含）、`startsWith`、`endsWith`。
- **数据处理**：`fromJSON`（字符串转对象——读取矩阵注入的 JSON 字段的必经之路）、`toJSON`、`join`、`format('{0} {1}', a, b)`。
- **文件类**：`hashFiles('**/pom.xml')`——**缓存 key 的黄金函数**：内容变 → hash 变 → 缓存失效重建（见 07 篇）。
- **状态类**：`success()`、`failure()`、`always()`、`cancelled()`——step 状态判断，`if: always()` 用于"无论如何都要执行的清理步骤"。
- **对象属性**：`github.event.xxx` 链式取事件载荷字段，`fromJSON` 搭配矩阵上下文取值。

## 4. 九大上下文对象

| 上下文 | 内容 | 高频用法 |
|---|---|---|
| `github` | 事件、仓库、ref 等 | `github.ref`、`github.event_name`、`github.event.pull_request` |
| `needs` | 前置 job 的输出与结果 | `needs.build.outputs.artifact`、`needs.build.result` |
| `jobs` | 当前工作流所有 job 结果 | 门禁判断（少用，需求不满足时为空） |
| `steps` | 步骤输出与结果 | `steps.deploy.outputs.url` |
| `runner` | Runner 信息 | `runner.os`、`runner.arch`、`runner.temp` |
| `env` | 环境变量 | 与 `vars` 配合读配置 |
| `vars` | 仓库/组织级配置变量（非密） | 版本号、构建参数 |
| `secrets` | 加密密钥 | `secrets.DOCKER_TOKEN`（日志中不可见） |
| `inputs` | workflow_dispatch 输入 | `inputs.environment` |
| `matrix` / `strategy` | 矩阵上下文 | `matrix.java`、`strategy.job-index` |

**vars 与 secrets 的区别要讲清**：`vars` 是明文配置变量（构建号、默认分支），`secrets` 是加密密钥（token、密码）——明文配置走 vars 便于审计，密钥永远走 secrets。

### 4.1 读取链与优先级

上下文的值在运行时是"只读快照"，但读取路径有优先级与覆盖语义，搞混会导致"配置不生效"类问题：

- **env 的三级覆盖链**：工作流级 `env`（最宽）→ job 级 `env` → step 级 `env`（最窄），同键名由窄覆盖宽；step 级 env 只在当前步骤可见，job 级 env 在该 job 所有步骤可见——设计配置时把"全局稳定配置放工作流级、环境差异放 job 级、步骤私有放 step 级"，覆盖语义自然清晰。
- **vars 与 env 的关系**：`vars` 是配置变量（仓库/环境级设置），`env` 是运行环境变量——vars 要在表达式里 `${{ vars.X }}` 读取后显式注入 env 才能在 shell 里用；GitHub 也支持在 env 块里直接写 `env: { V: ${{ vars.V }}}` 完成"配置 → 环境"的显式注入，这条链路比"每个 job 手写一遍"干净得多。
- **secrets 只进环境不进表达式**：secrets 只能在 `${{ secrets.X }}` 处引用，且引用结果注入 env 后 shell 才可见——表达式里直接拼 secrets 值到命令（如 `run: curl -H "token: ${{ secrets.T }}"`）虽可用但不推荐，统一走 env 中转更利于审计与脱敏。

## 5. if 条件陷阱清单

1. **表达式外游离文本**：`if: ${{ github.event_name }} == 'push'`——`${{ }}` 外残留文本会让整个条件变成字符串，恒为真。2026-01 起编辑器报错 + 运行时 annotation 提示，但仍要养成"整个 if 要么全表达式要么纯文本"的书写习惯。
2. **宽松比较的意外**：`'21' != 21` 为假（相等），需要严格区分类型时用 `fromJSON` 转换后再比。
3. **空值链式崩溃**：`github.event.pull_request.title` 在 push 事件下不存在——先判 `github.event_name == 'pull_request'` 再取字段，或 `${{ github.event.pull_request && github.event.pull_request.title }}` 短路。
4. **矩阵空组合**：matrix 全被 exclude 后 job 数组为空，工作流直接失败——用 `strategy.matrix` 的 include 保证至少一组，或 if 里判 `matrix != null`。
5. **always() 与 continue-on-error 混用**：`continue-on-error: true` 的步骤失败后 `success()` 仍为真，`always()` 才保证执行——清理步骤必须 `always()`，否则失败路径不清理。
6. **跳过 job 的日志**：2026-01 起，被 if 跳过的 job 日志会显示"原始表达式 + 展开后的运行时值"——排查"为什么没跑"直接看运行详情，不用再手动模拟。

**条件逻辑的建模建议（上升到设计层）**：if 条件写多了，工作流会变成"表达式迷宫"。三个降复杂度的手段：其一，**条件收敛到 job 级**——能在 job 级 `if` 过滤的，别在 step 级到处写（job 级一处、step 级 N 处）；其二，**矩阵替代重复条件**——"三平台各跑一次"用矩阵表达，比三个 if 分支清晰；其三，**输入驱动替代事件判断**——手动触发场景把"跑什么"做成 workflow_dispatch 的 inputs 选择项，比在表达式里猜事件更可读。条件逻辑的可维护性 = 团队 CI 可维护性的一半，值得用设计视角对待。表达式与上下文是工作流的"编程语言"——它没有变量声明、没有函数定义，只有只读快照与内联求值，理解这个约束（而非对抗它），条件逻辑自然收敛到"简单、可读、可测"的形态——表达式不是程序语言，它是工作流里"小而明确"的判断语言。

## 6. 表达式实战组合

**常用模式库（照抄级）**：

- 状态组合：`if: success()`（默认语义，显式写更清晰）、`if: always()`（清理）、`if: failure()`（失败补救，如失败通知）、组合 `if: success() && !cancelled()`。
- 事件分支：`if: github.event_name == 'pull_request'`（PR 专属）、`if: startsWith(github.ref, 'refs/tags/')`（发版专属）、`if: github.event.pull_request.draft == false`（草稿 PR 不跑）。
- 输入门控：`if: inputs.environment == 'production'`（手动触发时按参数分流）、`if: contains(inputs.targets, 'backend')`（多目标选择）。
- 矩阵判断：`if: matrix.os == 'windows-latest'`（平台专属步骤）、`if: fromJSON(matrix.extra).enabled`（include 注入的开关字段）。

**表达式调试三板斧**：其一，`run: echo '${{ toJSON(github) }}'` 打印上下文全貌（注意秘密字段会脱敏）；其二，2026-01 起跳过的 job 日志自动显示"原始表达式 + 展开值"，if 不生效先看运行详情；其三，`ACTIONS_STEP_DEBUG=true` 输出每个表达式的求值过程——从"结果不对"到"哪一步求值错"一目了然。

```yaml
- name: 条件编译上传
  if: ${{ startsWith(github.ref, 'refs/tags/') && !contains(github.ref, '-SNAPSHOT') }}
  run: |
    echo "release=release" >> $GITHUB_OUTPUT

- name: 读取矩阵 JSON 字段
  run: echo "profile=${{ fromJSON(matrix.extra).profile }}"
```

> 🎯 核心要点：表达式层一句话——**能读的只有上下文，能传的只有输出文件，能比的只有宽松类型**。if 条件写完用"三问自查"：游离文本？空值字段？类型假设？（真值规则与宽松比较）
