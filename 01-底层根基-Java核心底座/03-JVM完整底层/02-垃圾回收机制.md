## 1. 为什么需要 GC

### 1.1 手动 vs 自动

```c
// C 语言：手动内存管理
void* ptr = malloc(1024);
// 使用 ptr...
free(ptr);  // 必须手动释放，否则内存泄漏
```

```java
// Java：自动内存管理
void method() {
    byte[] data = new byte[1024];
    // 使用 data...
    // 不需要手动释放，JVM 自动回收
}
```

### 1.2 不 GC 的后果

| 问题 | 描述 | 后果 |
|------|------|------|
| 内存泄漏 (Memory Leak) | 对象不再使用但未被回收 | 可用内存持续减少 → OOM |
| 悬垂指针 (Dangling Pointer) | 释放后仍被引用 | C/C++ 未定义行为 |
| 双重释放 (Double Free) | 同一块内存释放两次 | C/C++ 程序崩溃 |
| 内存碎片化 | 分配和释放导致不连续 | 无法分配大对象 |

> GC 把开发者从内存管理中解放出来，但代价是引入了停顿时间和 CPU 开销。理解 GC 才能在**吞吐量**和**延迟**之间做出合理 trade-off。

## 2. 垃圾识别算法

### 2.1 Reference Counting (引用计数)

```
原理：每个对象维护一个引用计数器
  ╔══════════╗     +1    ╔══════════╗
  ║ 对象 A   ║◀─────────║ 引用者 1 ║
  ║ refCount ║     +1    ║          ║
  ║ = 2      ║◀─────────║ 引用者 2 ║
  ╚══════════╝          ╚══════════╝
  销毁时：遍历引用者，各 -1
  refCount = 0 时回收
```

| 优点 | 缺点 |
|------|------|
| 实现简单 | **循环引用无法回收** |
| 实时性高（引用为 0 即回收） | 每次引用修改都有额外开销 |
| 停顿时间短 | 多线程环境下计数器同步成本高 |

```java
// 循环引用陷阱（引用计数无法处理）
public class CircularRef {
    public Object ref;

    public static void main(String[] args) {
        CircularRef a = new CircularRef();
        CircularRef b = new CircularRef();
        a.ref = b;
        b.ref = a;
        a = null;
        b = null;
        // 引用计数：a 和 b 的计数器仍为 1
        // 永远不会被回收！
    }
}
```
> PyPy、CPython 使用引用计数，但配合了 GC 处理循环引用。**Java 使用可达性分析，避免了这个问题。**

### 2.2 Reachability Analysis (可达性分析) — HotSpot 采用

```
GC Roots 集合
  ┌─────────┐
  │ Root 1  │───▶ 对象 A ──▶ 对象 B
  ├─────────┤              │
  │ Root 2  │───▶ 对象 C    └──▶ 对象 D (可达)
  ├─────────┤
  │ Root 3  │───▶ 对象 E
  └─────────┘
               对象 F (不可达，被回收)
               对象 G ──▶ 对象 H (循环引用，但不可达—同时回收)
```

**可达 = 从 GC Roots 出发能找到的路径**。不可达的对象就是"垃圾"。

**解决了循环引用问题**：即使 A 和 B 互相引用，只要它们到 GC Roots 不可达，就判定为垃圾。

## 3. GC Roots 详解

### 3.1 哪些对象可以作为 GC Roots？

```java
public class GCRootsDemo {
    // 1. 静态变量引用的对象（在方法区中）
    private static SomeObject staticObj = new SomeObject();

    public void method() {
        // 2. JVM Stack 中的引用（局部变量）
        SomeObject localObj = new SomeObject();

        // 3. JNI 本地方法栈中的引用（全局引用）
        //    （通过 JNI 创建的全局引用）
    }

    // 4. 活跃线程（Thread 对象本身就是 GC Root）
    // 5. 同步锁持有的对象（synchronized 的对象）
    // 6. JVM 内部引用（ClassLoader, System Class, etc.）
    // 7. 所有被 GC 管理的对象（JNI Monitor 等）
}
```

### 3.2 直观理解 GC Roots

```java
/**
 * GC Roots 可视化演示
 */
public class GCRootsVisualization {
    // 静态引用 → GC Root
    private static List<byte[]> STATIC_CACHE = new ArrayList<>();

    public static void main(String[] args) throws Exception {
        // 1. Stack 引用 → GC Root
        byte[] stackRef = new byte[1024 * 1024];  // 1MB

        // 2. 将引用置为 null，对象变成不可达
        stackRef = null;  // 该 1MB 对象可被回收

        // 3. 静态引用持有的对象不会被回收
        STATIC_CACHE.add(new byte[1024 * 1024]);

        System.gc();
        System.out.println("GC 完成。");
        // 此时：stackRef 指向的对象已被回收
        //       STATIC_CACHE 中的 1MB 仍然存活

        Thread.sleep(10000);
    }
}
```

## 4. 引用类型深入

### 4.1 引用类型对比

| 引用类型 | 回收时机 | 用途 | 实现类 |
|----------|---------|------|--------|
| **Strong** | 永不回收（可达时） | 普通对象引用 | 默认 |
| **Soft** | 内存不足时回收（OOM 前） | 缓存 | `SoftReference` |
| **Weak** | 下一次 GC 立即回收 | WeakHashMap, 框架 | `WeakReference` |
| **Phantom** | 任何时候，但 get() 永远返回 null | 资源清理、对象销毁跟踪 | `PhantomReference` |

**回收强度：Strong < Soft < Weak < Phantom**

```
GC 时的引用链判定：
  ┌──────────────────┐
  │  GC Roots        │
  └───────┬──────────┘
          │
  ┌───────▼──────────┐
  │  强引用对象       │ ← 不可回收
  └───────┬──────────┘
          │
  ┌───────▼──────────┐
  │  软引用对象       │ ← 内存不足时回收
  └───────┬──────────┘
          │
  ┌───────▼──────────┐
  │  弱引用对象       │ ← 下一次 GC 必回收
  └───────┬──────────┘
          │
  ┌───────▼──────────┐
  │  虚引用对象       │ ← get() 永远 null，通知队列
  └──────────────────┘
```

### 4.2 Soft Reference — 内存敏感缓存

```java
/**
 * 软引用：适合做缓存，内存不足时自动释放
 * JVM: -Xmx10m 观察效果
 */
public class SoftReferenceDemo {
    public static void main(String[] args) {
        // 创建一个强引用对象
        Object strongRef = new Object();

        // 创建一个软引用指向它
        SoftReference<Object> softRef = new SoftReference<>(strongRef);

        // 清除强引用
        strongRef = null;

        System.out.println("GC 前: " + softRef.get());  // 非 null

        // 尝试触发 GC（但软引用不一定释放，除非内存不足）
        System.gc();

        System.out.println("GC 后: " + softRef.get());
        // 输出：非 null（内存充足时不会被回收）
    }
}
```

```java
/**
 * 软引用缓存实战
 */
public class SoftCache<K, V> {
    private final Map<K, SoftReference<V>> cache = new HashMap<>();

    public V get(K key) {
        SoftReference<V> ref = cache.get(key);
        if (ref == null) return null;
        return ref.get();  // 如果已被 GC 回收，返回 null
    }

    public void put(K key, V value) {
        cache.put(key, new SoftReference<>(value));
    }

    public void evict(K key) {
        cache.remove(key);
    }
}
```

### 4.3 Weak Reference — 框架级使用

```java
/**
 * WeakReference：WeakHashMap 的核心
 */
public class WeakReferenceDemo {
    public static void main(String[] args) {
        Object key = new Object();
        Object value = new Object();

        // WeakHashMap 的 Entry 继承 WeakReference
        Map<Object, Object> weakMap = new WeakHashMap<>();
        weakMap.put(key, value);

        System.out.println("Map size before GC: " + weakMap.size()); // 1

        // 清除强引用
        key = null;

        System.gc();  // 弱引用对象会被回收

        System.out.println("Map size after GC: " + weakMap.size());  // 0
    }
}
```

**WeakReference 在框架中的使用场景**：
- `ThreadLocal` 的 `ThreadLocalMap.Entry` 继承 `WeakReference<ThreadLocal<?>>`
- `WeakHashMap` — 缓存 key 可被自动回收
- Wicket、Guice 等框架中的对象作用域管理
- `java.util.ServiceLoader` 中的 provider 缓存

### 4.4 Phantom Reference — 终极清理

```java
/**
 * PhantomReference：在对象被回收后得到通知
 *
 * 特点：
 * 1. get() 永远返回 null
 * 2. 对象被回收后，PhantomReference 被放入 ReferenceQueue
 * 3. 用于对象销毁后的资源清理（比 finalize 更安全）
 */
public class PhantomReferenceDemo {
    public static void main(String[] args) throws Exception {
        Object obj = new Object();
        ReferenceQueue<Object> queue = new ReferenceQueue<>();

        PhantomReference<Object> phantomRef = new PhantomReference<>(obj, queue);

        System.out.println("get(): " + phantomRef.get());  // null（永远）

        // 清除强引用
        obj = null;

        System.gc();

        // PhantomReference 在对象回收后会被放入 queue
        Reference<?> refFromQueue = queue.remove(1000);
        if (refFromQueue != null) {
            System.out.println("对象已被回收！收到通知。");
            // 可以在这里执行清理操作（如关闭文件、释放资源）
        }
    }
}
```

## 5. finalize() 与 Cleaner

### 5.1 finalize() — 不推荐使用

```java
/**
 * finalize() 的问题
 * JDK 9: @Deprecated(forRemoval=true)
 * JDK 18: 正式移除
 */
public class FinalizeDemo {

    private Resource resource;

    public FinalizeDemo() {
        resource = new Resource();
    }

    @Override
    @SuppressWarnings("deprecation")
    protected void finalize() throws Throwable {
        try {
            if (resource != null) {
                resource.release();
            }
        } finally {
            super.finalize();
        }
    }
}
```

**finalize() 的问题**：
1. **执行时间不确定** — JVM 不保证何时调用
2. **性能差** — 需要额外的 GC 周期（第一周期标记可执行 finalize，第二周期才回收）
3. **可能导致对象复活** — finalize 中可以将 `this` 赋值给静态变量
4. **异常被吞** — 抛出的异常不会被传播

```java
/**
 * 对象复活演示（仅供理解，不要在实际代码中使用）
 */
public class ResurrectionDemo {
    private static ResurrectionDemo SAVED;

    @Override
    @SuppressWarnings("deprecation")
    protected void finalize() throws Throwable {
        System.out.println("finalize() called");
        // 对象"复活"
        SAVED = this;
    }

    public static void main(String[] args) throws Exception {
        ResurrectionDemo obj = new ResurrectionDemo();
        obj = null;  // 对象变为不可达

        System.gc();
        Thread.sleep(100);

        System.out.println("SAVED: " + (SAVED != null ? "复活了" : "已回收"));
        // 输出: 复活了

        // 第二次释放，finalize() 不会被再次调用
        SAVED = null;
        System.gc();
        Thread.sleep(100);

        System.out.println("第二次: " + (SAVED != null ? "复活" : "已回收"));
        // 输出: 已回收（finalize 只执行一次）
    }
}
```

### 5.2 Cleaner (JDK 9+) — 现代替代方案

```java
import java.lang.ref.Cleaner;

/**
 * Cleaner：JDK 9+ 正式提供的替代 finalize 的方案
 * 类似 PhantomReference，但更方便使用
 */
public class CleanerDemo {

    // 1. 创建全局 Cleaner
    private static final Cleaner CLEANER = Cleaner.create();

    // 2. 清理任务（必须是 Runnable，不能引用要清理的对象）
    private static class ResourceCleanup implements Runnable {
        private final int resourceId;

        ResourceCleanup(int resourceId) {
            this.resourceId = resourceId;
        }

        @Override
        public void run() {
            // 执行清理操作
            System.out.println("Cleanup: 释放资源 " + resourceId);
        }
    }

    // 3. 被管理资源的对象
    private final Cleaner.Cleanable cleanable;

    public CleanerDemo(int id) {
        // 注册清理任务
        this.cleanable = CLEANER.register(this, new ResourceCleanup(id));
    }

    public static void main(String[] args) throws Exception {
        CleanerDemo obj = new CleanerDemo(1);
        obj = null;  // 清除强引用

        System.gc();
        Thread.sleep(100);

        // 输出: Cleanup: 释放资源 1
        System.out.println("Done");
    }
}
```

## 6. GC 算法详解

### 6.1 Mark-Sweep (标记-清除)

```
初始状态：                   标记后（灰色=存活，白色=垃圾）
┌────┬────┬────┬────┐      ┌────┬────┬────┬────┐
│ A  │ B  │ C  │ D  │      │ ▓A▓ │ B  │ ▓C▓ │ D  │
└────┴────┴────┴────┘      └────┴────┴────┴────┘
                            A 和 C 存活

清除后（产生碎片）：
┌────┬────┬────┬────┐
│ ▓▓ │ 空 │ ▓▓ │ 空 │
└────┴────┴────┴────┘
碎片空间
```

| 优点 | 缺点 |
|------|------|
| 算法简单 | **内存碎片化** — 无法分配大对象 |
| 实现成本低 | **分配效率下降** — 空闲链表查找耗时 |

### 6.2 Mark-Sweep-Compact (标记-清除-整理)

```
标记存活对象：               整理后：
┌────┬────┬────┬────┐      ┌────┬────┬────┬────┐
│ A  │ B  │ C  │ D  │      │ A  │ C  │    │    │
└────┴────┴────┴────┘      └────┴────┴────┴────┘
标记: A,C 存活              紧凑排列，无碎片

B, D 被清除
```

**特点**：解决了碎片化问题，但多了整理阶段，停顿时间更长。

### 6.3 Mark-Copy (标记-复制)

```
┌────┬────┬────┬────┐   ┌────┬────┬────┬────┐
│Eden│ S0 │ S1 │Old │   │Eden│ S0 │ S1 │Old │
│░░░░│ ▓▓ │    │    │   │    │    │ ▓▓ │    │
│░░░░│A, C│    │    │   │    │    │A, C│    │
│░░░░│    │    │    │   │    │    │    │    │
└────┴────┴────┴────┘   └────┴────┴────┴────┘
 填充满                   复制存活: A,C → S1
                          Eden,S0 清空
```

| 优点 | 缺点 |
|------|------|
| **无碎片** — 连续排列 | **内存浪费** — 一半空间空闲 |
| 分配效率高（bump-the-pointer） | 存活率高时复制成本大 |

> **Young Gen 的默认方案**：Eden 存活对象复制到 Survivor。因为 Young Gen 存活率低（约 98% 对象很快死亡），标记-复制效率最高。

### 6.4 算法对比总结

| 算法 | 碎片 | 内存利用率 | 吞吐量 | 停顿 | 适用场景 |
|------|------|-----------|-------|------|---------|
| Mark-Sweep | 严重 | 高 | 中 | 中 | Old Gen (CMS) |
| Mark-Compact | 无 | 高 | 低 | 长 | Old Gen (Parallel Old) |
| Mark-Copy | 无 | 低（浪费一半） | 高 | 短 | Young Gen |

## 7. 分代收集理论

### 7.1 理论基础

**两个经验法则 (Weak Generational Hypothesis)**：
1. **绝大多数对象"朝生夕死"**（98%+ 的对象很快死亡）
2. **熬过多次 GC 的对象难以回收**（存活对象稳定）

### 7.2 分代结构

```
对象年龄演进：
  Eden (age=0)
    │ 第一次 Minor GC 后存活
    ▼
  S0 (age=1)
    │ 第二次 Minor GC 后存活，交换到 S1
    ▼
  S1 (age=2)
    │ 第三次 Minor GC 后存活，交换回 S0
    ▼
  ...
    │ age ≥ 阈值 (-XX:MaxTenuringThreshold, 默认 15)
    ▼
  Old Gen（晋升）
```

### 7.3 GC 类型

| 类型 | 区域 | 触发条件 |
|------|------|---------|
| Minor GC / Young GC | Young Gen | Eden 区满 |
| Major GC / Old GC | Old Gen | Old Gen 满或 CMS 并发失败 |
| Full GC | 整个堆 + 方法区 | Old Gen 满 / System.gc() / Promotion Failed |
| Mixed GC | Young + 部分 Old | G1 特有 |

## 8. HotSpot GC 收集器

### 8.1 收集器总览（JDK 8）

```
Serial ────┐  (Young)      Serial Old ────┐  (Old)
           │                              │
ParNew ────┤              Parallel Old ───┤
           │                              │
Parallel  ─┘              CMS ────────────┘
  Scavenge                              

G1: 独立于以上层次，全堆管理

连线表示可搭配使用：
  Serial + Serial Old
  ParNew + CMS
  Parallel Scavenge + Parallel Old
  G1（独立）
```

### 8.2 Serial / Serial Old

```bash
# 启用
-XX:+UseSerialGC       # Serial (Young) + Serial Old (Old)
```

| 特性 | 描述 |
|------|------|
| 线程数 | **单线程** |
| 暂停 | Stop-The-World（所有用户线程停止） |
| 算法 | Young: Mark-Copy; Old: Mark-Compact |
| 适用 | 客户端模式、单核 CPU、桌面应用 |
| 特点 | 简单高效，没有线程交互开销 |

### 8.3 ParNew — 多线程 Young GC

```bash
-XX:+UseParNewGC                           # JDK 9 前可用
-XX:ParallelGCThreads=N                    # 并行线程数（默认 CPU 核数）
```

| 特性 | 描述 |
|------|------|
| 本质 | Serial 的多线程版本 |
| 算法 | Mark-Copy（并行） |
| 搭配 | 只能与 CMS 搭配 |
| 适用 | Server 模式，**与 CMS 配合使用** |

### 8.4 Parallel Scavenge / Parallel Old — JDK 8 默认

```bash
# JDK 8 默认
-XX:+UseParallelGC      # Parallel Scavenge (Young)
-XX:+UseParallelOldGC   # Parallel Old (Old, JDK 6u23+ 默认关联)
-XX:ParallelGCThreads=N # GC 线程数

# 控制目标
-XX:MaxGCPauseMillis=N  # 最大停顿时间（毫秒）
-XX:GCTimeRatio=N       # 吞吐量目标（默认 99, 即 1% 时间 GC）
-XX:+UseAdaptiveSizePolicy  # 自适应调整（GC Ergonomics）
```

| 特性 | 描述 |
|------|------|
| 目标 | **高吞吐量**（关注 CPU 用于业务的时间占比） |
| 算法 | Young: Mark-Copy; Old: Mark-Compact |
| 自适应 | 自动调整 Eden/Survivor 比例 |
| 适用 | 后台计算、批量处理、对停顿不敏感的场景 |

```java
/**
 * 查看当前 GC 收集器（JDK 8+）
 */
public class GCDetector {
    public static void main(String[] args) {
        List<GarbageCollectorMXBean> beans =
                ManagementFactory.getGarbageCollectorMXBeans();
        for (GarbageCollectorMXBean bean : beans) {
            System.out.println(bean.getName());
        }
        // Parallel: PS Scavenge (Young), PS MarkSweep (Old)
        // G1: G1 Young Generation, G1 Old Generation
        // ZGC: ZGC
    }
}
```

### 8.5 CMS — Concurrent Mark-Sweep

```bash
# JDK 8 使用（JDK 9+ deprecated，JDK 14 移除）
-XX:+UseConcMarkSweepGC
-XX:+UseParNewGC            # ParNew + CMS
-XX:CMSInitiatingOccupancyFraction=70  # 触发 CMS 的 Old Gen 比例
-XX:+UseCMSInitiatingOccupancyOnly
-XX:+CMSScavengeBeforeRemark # Remark 前触发一次 Young GC
-XX:CMSFullGCsBeforeCompaction=0  # Full GC 后整理
```

**CMS 执行阶段**：

```
时间线 ─────────────────────────────────────────►

1. Initial Mark (STW)
   └─ 标记 GC Roots 直接关联的对象（快）

2. Concurrent Mark
   └─ 从 GC Roots 开始遍历整个对象图（最耗时）
   └─ 与用户线程并发执行

3. Concurrent Preclean
   └─ 处理 Concurrent Mark 阶段发生变化的对象

4. Remark (STW)
   └─ 修正并发阶段漏标/错标的对象
   └─ 使用增量更新 (Incremental Update)

5. Concurrent Sweep
   └─ 清除不可达对象，与用户线程并发
   └─ 使用 Mark-Sweep（无整理，产生碎片）
```

**CMS 的问题**：

| 问题 | 描述 | 解决/影响 |
|------|------|----------|
| **Concurrent Mode Failure** | 并发标记时 Old Gen 被填满 | 退化为 Serial Old Full GC，停顿极长 |
| **碎片化** | Mark-Sweep 导致内存碎片 | 触发 Full GC 进行整理 |
| **CPU 敏感** | 与用户线程争抢 CPU | 降低应用吞吐量 |
| **浮动垃圾** | 并发清除阶段产生的垃圾 | 需要预留空间，提前触发 GC |

### 8.6 G1 — Garbage-First (JDK 9+ 默认)

```bash
-XX:+UseG1GC                       # JDK 9+ 默认
-XX:G1HeapRegionSize=4m            # Region 大小 (1-32MB)
-XX:MaxGCPauseMillis=200           # 目标停顿时间 (默认 200ms)
-XX:ParallelGCThreads=N            # 并行线程数
-XX:ConcGCThreads=N                # 并发线程数
-XX:InitiatingHeapOccupancyPercent=45  # 启动并发标记的堆占用率
-XX:G1ReservePercent=10            # 预留空间
-XX:+UnlockExperimentalVMOptions -XX:G1MixedGCLiveThresholdPercent=85
```

#### G1 的核心设计

```
Region 布局（2MB 示例，共 16 个 Region）：
┌────┬────┬────┬────┐
│ E  │ E  │ E  │ O  │
├────┼────┼────┼────┤
│ O  │ O  │ E  │ S  │
├────┼────┼────┼────┤
│ H  │ H  │ O  │ O  │
├────┼────┼────┼────┤
│ O  │ O  │ E  │ E  │
└────┴────┴────┴────┘
E = Eden (黄色)   O = Old (蓝色)
S = Survivor      H = Humongous (红色)
                  大对象 > 50% Region size
```

**G1 关键数据结构**：

| 结构 | 作用 | 实现要点 |
|------|------|---------|
| Remembered Set (RSet) | 记录其他 Region 对本 Region 的引用 | 空间换时间，Card Table 实现 |
| Collection Set (CSet) | 本次 GC 要回收的 Region 集合 | 优先处理垃圾最多的 Region |
| SATB (Snapshot At The Beginning) | 并发标记的快照 | 确保并发标记的正确性 |

#### G1 GC 周期

```
              ┌──────────────────────┐
              │  Young GC (Normal)    │ ← 持续执行
              │  - Eden → Survivor    │
              │  - 调优停顿时间       │
              └──────────┬───────────┘
                         │ IHOP 达到
                         ▼
              ┌──────────────────────┐
              │  Concurrent Marking   │ ← 并发周期
              │  1. Initial Mark      │
              │  2. Root Region Scan  │
              │  3. Concurrent Mark   │
              │  4. Remark            │
              │  5. Cleanup           │
              └──────────┬───────────┘
                         ▼
              ┌──────────────────────┐
              │  Mixed GC            │ ← 同时回收 Young + 部分 Old
              │  (多次, 直到暂停达标)│
              └──────────────────────┘
                         │
                         ▼ 暂停超时 → Full GC
              ┌──────────────────────┐
              │  Full GC (Serial)    │ ← G1 退化为单线程 Full GC
              └──────────────────────┘
```

```java
/**
 * G1 的 Humongous 对象分配
 * 大对象（> 50% Region Size）直接分配到 H Region
 */
public class G1HumongousDemo {
    public static void main(String[] args) {
        // 默认 Region 大小，对象 > 512KB 即为 Humongous
        byte[] hugeObject = new byte[1024 * 1024];    // 1MB → Humongous
        byte[] normalObject = new byte[256 * 1024];   // 256KB → 普通对象
    }
}
```

### 8.7 ZGC — Ultra-Low-Latency

```bash
# JDK 11-14: 实验性
-XX:+UnlockExperimentalVMOptions -XX:+UseZGC

# JDK 15+: 生产就绪
-XX:+UseZGC

# JDK 21+: 分代 ZGC
-XX:+UseZGC -XX:+ZGenerational

# 参数
-XX:ConcGCThreads=N       # 并发线程
-XX:ZAllocationSpikeTolerance=2.0  # 分配抖动容忍
```

| 特性 | ZGC | G1 |
|------|-----|-----|
| 最大停顿 | < 1ms（与堆大小无关） | ~200ms |
| 算法 | 并发 Mark-Copy（Region） | 并发 Mark-Sweep-Compact |
| 指针 | **着色指针 (Colored Pointers)** | 普通指针 |
| 屏障 | 读屏障 (Load Barrier) | 写屏障 (SATB) |
| 堆大小 | 支持 TB 级 | TB 级 |
| JDK 版本 | 15+ 生产 | 9+ 默认 |

**ZGC 的着色指针技术**：

```
64 位虚拟地址空间（ZGC 使用 4TB 地址空间）：
┌──┬──┬──┬────────────────────────────────────────┐
│M0│M1│R │         有效地址 (42 bits)             │
└──┴──┴──┴────────────────────────────────────────┘
48  47 46 45-0

M0 = Mark Bit 0 (标记位 0)
M1 = Mark Bit 1 (标记位 1)
R  = Remapped (重映射位)
```

**ZGC 执行阶段**：

```
1. Pause Mark Start (STW, 极短)
   └─ 标记 GC Roots, 更新时间戳

2. Concurrent Mark (并发)
   └─ 使用读屏障 + 着色指针标记对象

3. Pause Mark End (STW, 极短)
   └─ 处理软引用、弱引用等

4. Concurrent Process Non-Strong References

5. Relocate (并发重定位)
   └─ 使用重映射位跟踪
   └─ 后台线程逐步移动对象
```

### 8.8 Shenandoah — Red Hat 的低延迟 GC

```bash
# JDK 12+ (JDK 15 移出实验)
-XX:+UseShenandoahGC

```

| 特性 | Shenandoah vs ZGC |
|------|-------------------|

### 8.9 Epsilon — 无操作 GC


### 8.10 收集器对比总结

| 收集器 | 适用 JDK | 线程 | 算法 | 目标 | 停顿 | 适用场景 |
|--------|---------|------|------|------|------|---------|

| Epsilon | 11+ | - | 无 | 测试 | 无 | 测试场景 |

## 9. GC 调优实战

### 9.1 调优流程

```
1. 明确目标
   ├─ 吞吐量优先 (Parallel)
   ├─ 延迟优先 (G1/ZGC)
   └─ 内存占用优先

2. 收集 Baseline
   ├─ 当前 GC 频率、停顿时间
   ├─ 内存占用、对象分布
   └─ CPU 使用率

3. 设置关键参数
   ├─ -Xms, -Xmx (堆大小)
   ├─ 收集器选择
   └─ 目标停顿/吞吐量

4. 分析 GC 日志
   ├─ 确认 GC 频率是否合理
   ├─ 确认停顿时间是否达标
   └─ 确认是否有异常模式

5. 调优迭代
   └─ 调整一个参数 → 观察效果 → 继续调整
```

### 9.2 场景 1: 高吞吐批处理

## 11. 内存泄漏检测

### 11.1 常见内存泄漏模式

```java
/**
 * 泄漏模式 1: 静态集合
 */
public class StaticCollectionLeak {
    // 静态集合永远不会被 GC 回收
    private static final List<byte[]> CACHE = new ArrayList<>();

    public void leak() {
        // 只增不减
        CACHE.add(new byte[1024 * 1024]);
    }
}

/**
 * 泄漏模式 2: 未关闭的资源
 */
public class ResourceLeak {
    public void leak() throws Exception {
        // 文件流未关闭
        FileInputStream fis = new FileInputStream("/tmp/test.txt");
        // ... 使用但不关闭
        // fis.close(); // 忘记关闭
    }
}

/**
 * 泄漏模式 3: 内部类持有外部类引用
 */
public class InnerClassLeak {
    private byte[] bigData = new byte[1024 * 1024 * 10];

    // 非静态内部类持有外部类引用
    class Listener {
        public void handle() {
            System.out.println("handle");
        }
    }

    public Listener getListener() {
        return new Listener(); // 持有整个 InnerClassLeak 的引用
    }
}

/**
 * 泄漏模式 4: ThreadLocal 内存泄漏
 */
public class ThreadLocalLeak {
    // ThreadLocalMap 的 Entry 继承 WeakReference
    // 但 value 是强引用！如果不 remove()，值永远不会被回收
    private static final ThreadLocal<byte[]> TL = new ThreadLocal<>();

    public void process() {
        TL.set(new byte[1024 * 1024]); // 设置大对象
        // ... 使用后没有调用 TL.remove()
    }
}

/**
 * 泄漏模式 5: 缓存没有过期策略
 */
public class CacheLeak {
    private static final Map<String, Session> SESSION_CACHE = new HashMap<>();

    public void addSession(String token, Session session) {
        SESSION_CACHE.put(token, session); // 永远不删除
    }
}
```

## 13. 面试经典问题

### 基础问题

**Q1: 如何判断一个对象是否可回收？**
- 可达性分析：从 GC Roots 出发不可达的对象
- GC Roots：栈引用、静态引用、JNI引用、活跃线程、同步锁等

**Q2: 强引用、软引用、弱引用、虚引用的区别和使用场景？**
- 强：永不回收（普通 new）
- 软：内存不足时回收（缓存）
- 弱：下次 GC 就回收（WeakHashMap）
- 虚：get() 返回 null 用于跟踪回收（资源清理）

**Q3: CMS 收集器的执行过程？有什么缺点？**
- Initial Mark → Concurrent Mark → Remark → Concurrent Sweep
- 缺点：Concurrent Mode Failure、CPU 敏感、碎片化

### 进阶问题

**Q4: G1 相比 CMS 有什么优势？**
- Region 化——不要求物理连续
- RSet 减少了 Full GC 范围
- 可预测停顿时间
- 自动整理减少碎片

**Q5: ZGC 的"着色指针"是什么？**
- 利用 64 位地址空间的 4 位元数据
- M0, M1 标记位 + Remap 位
- 通过读屏障 + 着色指针实现并发复制

**Q6: 什么情况下会触发 Full GC？**
- Old Gen 满
- Metaspace 满
- System.gc() / GC 调优工具调用
- G1 并发标记失败 / Promotion Failed

**Q7: 如何查看当前 JVM 的 GC 收集器？**
- `jinfo -flag UseG1GC <pid>`
- `jcmd <pid> VM.flags`
- `ManagementFactory.getGarbageCollectorMXBeans()`

### 深度问题

**Q8: 三色标记法是什么？CMS 和 G1 分别如何处理漏标？**
- 白色：未扫描；灰色：自身已扫但引用未扫；黑色：全扫完
- CMS：增量更新（Incremental Update）——黑色对象新指向白色时记录
- G1：SATB（Snapshot At The Beginning）——开始时快照，灰色->白色断开时记录
- 两者区别：增量更新更精确，SATB 更简单但可能有浮动垃圾

**Q9: 解释一下 GC 停顿（Stop-The-World）是什么？为什么无法完全消除？**
- STW 时所有用户线程暂停
- 原因是：如果不暂停，对象引用关系持续变化，无法准确标记
- ZGC/Shenandoah 通过读屏障/写屏障和并发标记接近消除 STW

**Q10: 如果 JVM 频繁 Full GC，你会如何排查？**
1. `jstat -gcutil` 看各代使用率
2. `jmap -histo:live` 看存活对象
3. 分析 GC 日志（GCeasy）
4. heap dump 分析（MAT）
5. 检查业务代码：静态集合、ThreadLocal、循环引用、大对象
