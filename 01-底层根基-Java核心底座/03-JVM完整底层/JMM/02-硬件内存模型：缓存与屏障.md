## 1. CPU 缓存与可见性问题

### 1.1 缓存层次回顾

```text
每个核有私有 L1/L2，共享 L3：
  CPU 0 写变量 x → 写入自己的 L1
  CPU 1 读变量 x → 读自己的 L1（可能还是旧值！）

跨核一致性问题由缓存一致性协议（MESI 等）解决
  —— 但"一致性协议"只保证单个地址最终一致
  —— 不保证"何时可见"（异步传播）
```

> 💡 硬件基础详见 `计算机组成原理/缓存与Cache/05-缓存一致性协议`——MESI 状态机、伪共享等。本章聚焦"一致性协议管不了什么"。

### 1.2 一致性协议管不了的两件事

| 问题 | 说明 | 例子 |
|------|------|------|
| 写缓冲（store buffer） | 写操作先入队列，延迟刷出 | 一个核写后立即读另一核的值 |
| 读乱序（load reordering） | 读操作可提前执行 | 先读新值再读旧值 |

```text
经典反直觉场景（store buffer 引起）：
  CPU0：x = 1（入 store buffer）→ 读 y（仍可能是旧值 0）
  CPU1：y = 1（入 store buffer）→ 读 x（仍可能是旧值 0）
  结果：两个核都读到 0 —— 两个写"互相看不见"

这就是"写后读可见性"需要显式屏障的原因
```

## 2. store buffer 与失效队列

### 2.1 为什么要有 store buffer

```text
写操作太慢：写 L1 后还要等缓存一致性消息（数百周期）
优化：写先入 store buffer（异步刷出）→ CPU 不等

代价：本核读自己刚写的值时，需先查 store buffer
   （store-to-load forwarding）→ 单核内仍然一致
   其他核看不到 store buffer 里的写 → 跨核不一致窗口
```

### 2.2 失效队列（Invalidation Queue）

```text
读操作：收到"该行失效"消息后，无需等确认即可继续读
  → 失效消息在队列中排队，读可能读到"已失效但未处理"的行

两层延迟：写侧（store buffer）+ 读侧（失效队列）
  → 跨核可见性 = 两个异步机制，需要屏障显式同步
```

### 2.3 一致性协议 vs 内存模型

| 层面 | 保证 | 不管 |
|------|------|------|
| 缓存一致性协议 | 单地址：所有核看到同一写序 | 多地址间的顺序 |
| 内存模型 | 多地址：读写操作的整体顺序 | — |

```text
推论：MESI 保证"x 的值最终一致"
      内存模型保证"x=1 与 y=1 的观察顺序"
  —— 内存屏障就是在 MESI 之上补充"顺序"语义
```

## 3. 内存屏障指令

### 3.1 屏障家族（以 x86/ARM 为例）

| 屏障 | 作用 | x86 | ARM |
|------|------|-----|-----|
| 读屏障 | 之后的读不越过屏障（等待失效队列） | 无（TSO 下天然） | ldar（读获取） |
| 写屏障 | 之前的写全部刷出（等待 store buffer） | 无（TSO 下天然） | stlr（写释放） |
| 全屏障 | 读写都不越过 | mfence / lock 前缀 | dmb sy |
| 获取/释放 | 分别对应读屏障/写屏障 | xchg/lock | ldar/stlr |

```text
x86 的"天然强模型"：
  TSO（总存储序）下，普通读不会被普通写重排
  → 多数场景只需在"原子/锁指令"处加 lock 前缀（自带全屏障）
  → x86 上 volatile 的屏障成本 ≈ 0（硬件已保证）

ARM 的"弱模型"：
  普通读写可任意重排 → volatile/锁必须显式插屏障
  → ARM 上 volatile 有真实成本（ldar/stlr 指令）
```

### 3.2 屏障的组合语义

```text
四种组合（volatile 的读写）：
  写 volatile：LoadStore + StoreStore 屏障（之前的读写先完成）
  读 volatile：LoadLoad + LoadStore 屏障（之后的读写不提前）

具体到 HotSpot x86：
  volatile 写 → lock 前缀（或 xchg）→ 全屏障效果
  volatile 读 → 普通读（x86 硬件已保证）

具体到 HotSpot ARM：
  volatile 写 → stlr（写释放）
  volatile 读 → ldar（读获取）
```

## 4. x86 TSO vs ARM 弱模型

### 4.1 两大硬件内存模型

| 维度 | x86（TSO） | ARM/Power（弱模型） |
|------|-----------|-------------------|
| 写序 | 总序（所有写全局可见序一致） | 无全局写序 |
| 读写重排 | 读可越过旧写（仅此一种） | 任意重排 |
| 屏障需求 | 少（原子指令自带） | 多（显式获取/释放） |
| 移动端存在感 | 桌面/服务器 | 手机/嵌入式（JDK 需适配） |

```text
TSO 允许的唯一重排（store-load）：
  store x; load y → load y 可先于 store x 完成
  → 这正是 store buffer 的硬件表达

弱模型允许全部四种重排：
  load-load / load-store / store-load / store-store
  → 需要完整的屏障体系
```

### 4.2 一个"只有弱模型会错"的例子

```text
经典验证（Litmus Test，SB 场景）：
  线程 1：x = 1; r1 = y;
  线程 2：y = 1; r2 = x;
  允许结果 r1 = r2 = 0 吗？

  x86（TSO）：允许（store-load 重排）✓
  ARM（弱）：也允许（更自由）
  但有些更复杂的场景：x86 不允许的，ARM 允许

推论：x86 上"碰巧正确"的并发代码，ARM 上可能错
  → JMM 契约让 Java 程序员无需关心平台差异
  → 但 JVM 内部（HotSpot）必须为每个平台正确插屏障
```

## 5. JVM 到硬件的映射

### 5.1 HotSpot 的屏障模板

```text
JVM 编译 volatile/锁 时插入屏障，平台相关：
  OrderAccess::loadload/loadstore/storeload/storestore（抽象）
  → x86 实现：多为空操作（TSO 已保证）或 lock 前缀
  → ARM 实现：ldar/stlr/dmb

内存屏障在 JVM 中的角色（对应 03 模块的重排序）：
  编译期屏障（C2 编译器插入）
  运行期屏障（JIT 生成的指令序列中）
  → 保证"语义正确"且"优化空间最大"
```

### 5.2 代价的真相

| 平台 | volatile 读写成本 | 原因 |
|------|:---:|------|
| x86 | 读≈0、写≈lock 指令 | TSO 硬件强模型 |
| ARM | 读写各一条 ldar/stlr | 弱模型需显式屏障 |
| 服务器（大部分生产） | 低 | 部署在 x86 为主 |

```text
工程结论：
  ① volatile/锁在 x86 上"便宜"（对比直觉）
  ② 真正的成本是"优化限制"（编译器不能重排/缓存）而非指令
  ③ 移动端（ARM）上的并发成本真实存在 → 设计时考虑
```

## 6. 为什么要懂硬件层

### 6.1 三层收益

| 收益 | 说明 |
|------|------|
| 面试深度 | "volatile 为什么在 x86 便宜"——硬件层答案 |
| 性能判断 | 理解屏障成本 → 正确评估同步开销 |
| 底层排查 | 性能异常/并发异常时能定位到平台因素 |

### 6.2 边界：程序员该懂多少

```text
必须懂（正确性）：
  happens-before 规则（04 模块）——与硬件无关的契约

建议懂（性能）：
  屏障的成本量级、x86 vs ARM 差异

不必懂（除非做 JVM）：
  具体指令选择、缓存一致性协议细节
  —— HotSpot 已经替你处理了

铁律：永远不要"绕过 JMM 直接依赖硬件行为"
  （如用 Unsafe 猜测屏障——那是 JVM 内部的事）
```

> 🎯 **核心要点**：硬件层解释了"JMM 为什么存在"——CPU 的 store buffer/失效队列让跨核可见性天然延迟，x86 与 ARM 的强弱差异让"平台相关"成为必然。JMM 的贡献正是把这一切统一成一份平台无关的契约，让 Java 程序员只写一次、处处正确。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 可见性延迟哪来的？ | store buffer（写侧）+ 失效队列（读侧） |
| 一致性协议管什么？ | 单地址一致；不管多地址顺序 |
| 屏障家族？ | 读/写/全屏障，x86 多用 lock，ARM 用 ldar/stlr |
| x86 vs ARM？ | TSO 强模型（仅 store-load 重排）vs 弱模型（全重排） |
| volatile 在 x86 贵吗？ | 读≈0、写≈lock 指令——比直觉便宜 |
| 程序员该懂多少？ | 规则必懂；屏障细节交给 JVM |
