## 1. 并发为什么难

### 1.1 三个层次的"乱"

```text
并发问题的三个来源：
  ① 线程调度：执行顺序不确定（何时切换、在哪切换）
  ② 内存可见性：线程间的读写可能"互相看不见"
  ③ 指令重排序：编译器/CPU 可能改变操作顺序

单线程时①②③都无感（as-if-serial 保证）
多线程时三者叠加 → 程序行为"看起来违反直觉"
```

### 1.2 反直觉的根源

```java
// 经典示例：两个线程共享标志位
static boolean stop = false;

// 线程 A（写入）
stop = true;

// 线程 B（读取）
while (!stop) { /* 可能永远循环！ */ }
```

```text
为什么 B 可能看不到 A 的写入：
  ① 可见性：A 写的是"自己的缓存副本"，尚未同步到 B
  ② 重排序：A 的写入可能被推迟到后面才"生效"
  ③ 无同步：两个线程间没有任何 happens-before 边

这不是 JVM bug——是 JMM 允许的行为（无同步的并发无保证）
```

> 🎯 核心认知：**并发 bug 不是"编译器坏了"，而是程序违反了内存模型契约**。理解 JMM，就是理解"什么样的并发代码有保证、什么样的没有"。

## 2. 三大保证：可见性、有序性、原子性

### 2.1 三保证总览

| 保证 | 含义 | 违反的后果 | 工具 |
|------|------|-----------|------|
| 可见性 | 线程 A 的写，线程 B 能否看到 | 读到过期值 | volatile、锁 |
| 有序性 | 操作执行顺序是否可重排 | 观察顺序异常 | volatile、锁 |
| 原子性 | 操作是否不可分割 | 半完成状态 | 原子类、锁 |

### 2.2 三保证的层级关系

```text
原子性 ⊂ 可见性 ⊂ 有序性（重要性递增，实现成本递增）

  原子性：单条读写不被撕开（引用/int 天然满足）
  可见性：写之后，读能看到最新值
  有序性：读写顺序符合程序语义（最难，涉及全链重排序）

volatile 提供：可见性 + 有序性（不提供原子性！）
synchronized 提供：三者全部（互斥保证原子性）
```

> ⚠️ 常见误区："volatile 是原子的"。volatile 只保证单个读写的可见性与有序性；`volatile int i; i++` 仍是读-改-写三步，非原子——必须用 AtomicInteger 或锁。

## 3. 数据竞争与竞态条件

### 3.1 两个易混概念

| 概念 | 定义 | 例子 |
|------|------|------|
| 数据竞争（Data Race） | 两个线程**无同步**访问同一变量，至少一个写 | 上面 stop 示例 |
| 竞态条件（Race Condition） | 结果依赖执行时序的逻辑错误 | 检查-再执行（check-then-act） |

```text
关系：数据竞争是"内存层"问题（JMM 管）
      竞态条件是"逻辑层"问题（JMM 不管，靠设计避免）

数据竞争 → 行为未定义（可能读到任意值、可能死循环）
竞态条件 → 即使无数据竞争也可能错（如 if(!map.containsKey(k)) put）
```

### 3.2 数据竞争为什么是"未定义"

```text
JMM 对数据竞争的处理：
  ① 不保证可见性（可能读到旧值）
  ② 不保证有序性（可能观察到乱序）
  ③ 极端情况：读到"撕裂值"（long/double 高低位来自不同写）

对比 C/C++：数据竞争是 UB（未定义行为，可能崩溃）
      Java：无同步读写至少是"确定的值"（不崩溃，但可能过期）
  —— Java 的"弱保证"让多线程编程"能写但可能错"
```

## 4. 为什么需要内存模型

### 4.1 没有 JMM 的世界

```text
每个 JVM 实现各自为政：
  ① 相同代码在不同平台行为不同（x86 强 vs ARM 弱）
  ② 编译器优化程度不同 → 语义漂移
  ③ 程序员无法写出"可移植的并发代码"

1995-2004 的 Java 1.0-1.4 正是如此（JMM 缺失期）
  → volatile 语义含糊、final 无保证 → 大量平台相关 bug
```

### 4.2 JMM 的三重价值

| 价值 | 说明 |
|------|------|
| 可移植性 | 同一并发程序在所有 JVM/平台行为一致 |
| 优化空间 | 只要不违反契约，编译器/CPU 可自由优化 |
| 程序正确性 | 程序员只需满足"规则"即可获得保证 |

```text
JMM 的平衡艺术：
  给编译器/CPU 最大的优化自由（性能）
  给程序员最少但够用的保证（正确性）
  —— 这就是"契约式"设计的本质
```

## 5. JMM 的定位：契约而非实现

### 5.1 三个层次

```text
第 1 层 规范（JLS 第 17 章）：定义 happens-before、同步语义
  → 回答"什么样的程序是正确同步的"

第 2 层 JVM 实现（HotSpot）：把规范翻译为屏障指令
  → 回答"如何在 x86/ARM 上满足规范"

第 3 层 硬件（CPU 手册）：提供屏障/原子指令
  → 回答"硬件提供了什么原语"

程序员只关心第 1 层；第 2、3 层是 JVM/CPU 的事
```

### 5.2 关键推论

```text
推论 1：不要依赖"具体 JVM 的行为"写代码
  例："我这台机器上不用 volatile 也对" → 换平台/JVM 版本就错

推论 2：满足 happens-before 的代码，任何实现下都正确
  例：正确的同步代码在 x86/ARM/任何 JVM 都正确

推论 3：JMM 是"最弱保证"——实际 JVM 通常更强
  例：x86 上 volatile 语义天然被硬件覆盖（TSO），
      但 ARM 上必须显式插屏障——规范统一了两者
```

> 🎯 一句话：**JMM = "写并发 Java 的最低合法底线"**。满足它 → 所有平台正确；不满足 → 任何平台都可能错。理解这一点，就理解了为什么"本地跑通"不能证明并发正确。

## 6. 一个贯穿全书的例子

```java
public class VisibilityDemo {
    private static int data = 0;
    private static volatile boolean ready = false;

    public static void main(String[] args) throws InterruptedException {
        Thread writer = new Thread(() -> {
            data = 42;          // ① 普通写
            ready = true;       // ② volatile 写
        });
        Thread reader = new Thread(() -> {
            while (!ready) Thread.onSpinWait();  // ③ volatile 读
            System.out.println(data);            // ④ 普通读
        });
        reader.start(); writer.start();
        reader.join();
    }
}
```

```text
为什么这个程序一定输出 42（正确同步）：
  HB 链：① →(程序顺序) ② →(volatile 写 HB volatile 读) ③ →(程序顺序) ④
  传递性：① HB ④ → data 的写入对 reader 可见 ✓

对比：去掉 volatile → ②③ 间无 HB 边 → data 可能读到 0

这个例子串联了 04（HB 规则）、05（volatile 语义）模块的核心
```

> 🎯 **核心要点**：JMM 解决"并发正确性的可移植性"——用一份契约统一所有平台。三大保证中，可见性与有序性靠 happens-before 规则（04 模块），原子性靠锁与原子类（06 模块）。从本章起，所有"为什么这样写才对"的问题都有规范答案。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 并发难在哪？ | 调度不确定 + 可见性 + 重排序三层叠加 |
| 三大保证？ | 可见性、有序性、原子性（volatile 管前两个） |
| 数据竞争 vs 竞态？ | 内存层未定义行为 vs 逻辑层顺序依赖 |
| 为什么需要 JMM？ | 可移植性 + 优化空间 + 正确性基准 |
| JMM 是什么？ | 契约（JLS 第 17 章），不是实现 |
| 铁律？ | 满足 HB 全平台正确；不满足本地跑通也无效 |
