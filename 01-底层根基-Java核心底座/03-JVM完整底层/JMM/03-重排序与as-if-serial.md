## 1. 重排序是什么

### 1.1 定义

**重排序**：实际执行顺序与源代码顺序不一致的现象——编译器、处理器、内存系统都可能调整指令顺序。

```text
源代码：        a = 1;  b = 2;
可能的执行序：  b = 2;  a = 1;    ← 交换（若无依赖）

为什么允许：优化性能（流水线、寄存器分配、缓存局部性）
为什么安全：单线程下结果不变（as-if-serial）
为什么不安全：多线程下观察顺序可能"异常"
```

### 1.2 重排序的观察视角

```text
重排序的"受害者"是观察者：
  单线程观察自己：永远看不到（as-if-serial）
  其他线程观察：可能看到乱序

JMM 的工作：定义"哪些重排序在多线程下被禁止"
  —— 通过 happens-before（04 模块）划定边界
```

## 2. 三类重排序来源

### 2.1 编译器重排序

```text
JIT（C2/C1）优化引起的顺序调整：
  ① 公共子表达式消除（提前计算）
  ② 循环优化（展开/向量化）
  ③ 寄存器分配（改变内存访问顺序）

例：int x = a + b; int y = a + b;
  → 编译器可能只算一次（等价但改变"何时读 a"）

现代 JIT 会在"无同步区域"自由优化——这正是 JMM 允许的
```

### 2.2 处理器指令重排序

```text
CPU 乱序执行（OoO，见 计算机组成原理/CPU/03）：
  执行单元按依赖就绪度调度，而非按程序顺序
  结果：指令完成顺序 ≠ 发射顺序

硬件层面：x86 只允许 store-load 重排（TSO）
          ARM 允许全部四种（弱模型）
```

### 2.3 内存系统重排序

```text
缓存与内存系统的"实际生效顺序"：
  写进 store buffer → 实际刷出顺序可能与程序顺序不同
  读命中不同缓存行 → 观察到的时间顺序不同

例：两行不同地址（不同缓存行）的写
  → 刷出顺序取决于缓存一致性消息的时序（不保证程序顺序）
```

| 来源 | 可控制性 | 说明 |
|------|:---:|------|
| 编译器 | JIT 决定 | 优化自由度最大 |
| 处理器 | CPU 决定 | OoO 调度 |
| 内存系统 | 硬件决定 | store buffer/缓存时序 |

## 3. 数据依赖的硬约束

### 3.1 三类数据依赖

| 依赖 | 形式 | 重排后果 |
|------|------|---------|
| 写后读（RAW） | a=1; b=a; | b 读到旧值 ✗ |
| 读后写（WAR） | b=a; a=1; | a 的新值覆盖旧读 ✗ |
| 写后写（WAW） | a=1; a=2; | 最终值可能变 1 ✗ |

```text
核心规则：有数据依赖的操作，编译器/处理器均不得重排
  —— 这是所有优化（JIT、OoO）必须遵守的底线

例外：寄存器层面可以（如写后写在寄存器中合并）
  —— 依赖约束针对"可观察的存储访问"
```

### 3.2 依赖与屏障的分工

```text
数据依赖：CPU 硬件自动尊重（OoO 调度器检查依赖）
  例：load x; add x, 1; store x —— 必然按序

无依赖的操作：可自由重排
  例：load x; load y —— 可能先读 y（若 y 缓存命中）

→ 重排序只发生在"无依赖"的操作之间
→ 屏障/volatile 的作用：给"无依赖但有语义要求"的操作强制顺序
```

## 4. as-if-serial：单线程的底线

### 4.1 定义

**as-if-serial**：无论怎么重排序，单线程程序的执行结果必须与"按源码顺序执行"一致。

```text
含义：
  ① 单线程永远看不到重排序（结果层面）
  ② 编译器/CPU 在"结果不变"前提下自由优化
  ③ 这就是"并发 bug 只在多线程出现"的原因

注意：as-if-serial 只保证"结果"，不保证"时机"
  例：读外部状态（时间、IO）的顺序可能变化
```

### 4.2 与 JMM 的关系

```text
JMM 扩展了 as-if-serial：
  单线程：as-if-serial（无同步时也成立）
  多线程：happens-before 链内的操作也"像按序执行"

统一表述：
  JMM = as-if-serial（单线程底线）
      + happens-before（多线程扩展）
      + 数据竞争未定义（无保证区域）
```

### 4.3 常见误解澄清

| 误解 | 真相 |
|------|------|
| "volatile 保证不重排序" | 只保证 HB 边界两侧不跨越；HB 链内的无关操作仍可重排 |
| "final 字段写后一定立即可见" | final 有特殊保证（见 05 模块），但非"立即" |
| "同步块内不会重排序" | 块内仍可重排（块边界才受约束） |

> 🎯 关键认知：**重排序的边界是"同步点"而非"同步区域"**——synchronized 块/volatile 读写之间（HB 边）保证顺序，块内/边内的无关操作照样优化。

## 5. 重排序的经典例子

### 5.1 双重检查锁（DCL）的历史教训

```java
// 错误版本（Java 5 之前）：重排序导致半初始化对象泄漏
class Singleton {
    private static Singleton instance;          // 需 volatile
    private final int value;

    static Singleton getInstance() {
        if (instance == null) {                  // ① 检查
            synchronized (Singleton.class) {
                if (instance == null) {          // ② 双检
                    instance = new Singleton(42); // ③ 创建
                }
            }
        }
        return instance;
    }
}

// ③ 的三步（可重排）：
//   memory = allocate()       分配
//   instance = memory         引用赋值（可提前！）
//   value = 42                初始化（可能被推迟）
// → 另一线程在 ① 读到非 null 但 value 未初始化的对象

// 修复：instance 声明为 volatile → ③ 的写被全屏障保护
```

### 5.2 单例模式的血泪史

```text
DCL 的完整演进：
  ① 朴素 DCL（Java 1.4）：有 bug（重排序）
  ② 加 volatile（Java 5 起）：正确（JMM 修订后的标准）
  ③ 静态内部类（Bill Pugh）：无锁且正确（类加载时机保证）

教训：重排序 bug 极难复现（需要特定调度）
  → 规范上"可能错"就是错，不要赌运气
```

## 6. 重排序与 JMM 的关系

### 6.1 全链路总结

```text
重排序的完整链路（03 模块 + 02 模块）：
  源代码 → 编译器（JIT）→ 处理器（OoO）→ 内存系统（store buffer）
              ↓ 三类来源都可能调整顺序

JMM 的约束机制：
  ① 数据依赖：硬件/编译器自动遵守（硬约束）
  ② as-if-serial：单线程底线
  ③ happens-before：多线程可见性契约（04 模块）
  ④ volatile/锁：屏障强制边界（05 模块）
```

### 6.2 排序保证速查

| 场景 | 保证 |
|------|------|
| 单线程内 | as-if-serial（结果一致） |
| HB 边两侧 | 顺序保证（可见性） |
| 无 HB 边 | 无任何保证（数据竞争） |
| 数据依赖操作 | 永不重排 |

> 🎯 **核心要点**：重排序是性能的引擎、并发 bug 的温床——它无处不在（三类来源），但有明确边界（数据依赖 + as-if-serial + HB）。理解"什么情况下排序有保证"，就掌握了 JMM 有序性的全部；而 DCL 的历史教训提醒我们：规范层面的"可能错"在实践中一定会遇到。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 三类重排序？ | 编译器（JIT）、处理器（OoO）、内存系统（缓存） |
| 什么永不重排？ | 有数据依赖的操作（RAW/WAR/WAW） |
| as-if-serial？ | 单线程结果不变的底线 |
| 重排序边界在哪？ | 同步点（HB 边），不是同步区域 |
| DCL 教训？ | 重排序 bug 规范上可能错就是错，volatile 修复 |
| JMM 怎么管？ | 数据依赖 + as-if-serial + HB 三层约束 |
