## 1. JEP 491：虚拟线程不再 pinning

### 1.1 问题回顾（JDK 21-23）

```text
虚拟线程（JEP 444，JDK 21）：
  轻量线程，阻塞时卸载载体（平台线程）→ 高并发可扩展

历史问题（pinning）：
  虚拟线程在 synchronized 块内阻塞时，
  监视器归属"载体线程"→ 虚拟线程无法卸载 → 载体被占死
  → synchronized + 阻塞 I/O 的组合摧毁虚拟线程优势

规避方案（JDK 21-23 时代）：
  用 ReentrantLock 替代 synchronized（等待路径走 Java 锁机制）
  —— 官方文档曾如此建议
```

### 1.2 JEP 491 的修复（JDK 24，2025-03）

```text
核心变化：监视器所有权从"载体线程"改为"虚拟线程自身"

实现细节（OpenJDK 实现）：
  ① 轻量级锁：载体 LockStack 中的 oops 在冻结时
     复制到 stackChunk（清除 LockStack），解冻时复制回来
  ② 重量级锁：ObjectMonitor._owner 从 JavaThread* 改为
     java.lang.Thread.tid（虚拟线程可独立持有）
  ③ 覆盖四个移植端口（x64/aarch64/riscv/ppc）
  ④ 默认 LM_LIGHTWEIGHT 模式生效（LM_LEGACY 仍会 pinning）

效果：
  synchronized 内阻塞（I/O、sleep、wait）→ 虚拟线程可卸载
  → JDK 24+ 的 synchronized 重新成为虚拟线程安全的选择
```

### 1.3 实践建议（版本敏感）

| JDK 版本 | synchronized + 虚拟线程 | 建议 |
|:---:|:---:|------|
| 21-23 | 可能 pinning | 阻塞路径用 ReentrantLock 或避免 |
| 24+ | 已修复（JEP 491） | synchronized 可用；仍建议测试 |
| 24+ LM_LEGACY | 仍 pinning | 使用默认锁定模式 |

```text
验证方法（官方推荐）：
  启用 JFR 事件 jdk.VirtualThreadPinned
  → 检测生产环境是否还有 pinning 事件
  → 有 → 定位并改造；无 → 放心使用

来源：[JEP 491 官方页面](https://openjdk.org/jeps/491)（2025-11 更新）
```

> 🎯 与 JMM 的关系：JEP 491 不修改 JMM 规则（happens-before 不变）——它修改的是"锁的实现归属"；但工程影响巨大：synchronized 重新成为虚拟线程场景的推荐原语，锁的内存语义（unlock HB lock）完全不变。

## 2. JMM 的稳定与演进

### 2.1 为什么 JMM 20 年没变

```text
JMM（JLS 第 17 章）自 2004（Java 5）修订后保持稳定：
  ① 契约稳定 → 编译器/CPU 优化空间稳定
  ② 实现成熟 → HotSpot 的屏障模板已验证 20 年
  ③ 改动的风险极高 → 任何语义变化都会破坏存量程序

2025-2026 检索结论：无 JMM 规范修订计划
  （JEP 491 等是"实现层"变化，不是"规范层"变化）
```

### 2.2 相关演进（非规范层）

| 演进 | 层面 | 对 JMM 的影响 |
|------|------|-------------|
| JEP 491（JDK 24） | 锁实现 | 无（规则不变） |
| 偏向锁移除（JDK 18） | 锁实现 | 无（语义不变） |
| ScopedValue（JEP 506） | 数据传递 | 无（新增 API） |
| Valhalla（JEP 401） | 值类型 | 未来可能涉及 |
| Project Loom 结构化并发（JEP 525） | API | 无 |

```text
结论：JMM 规则 = 稳定公约
  变化的是"实现效率"与"使用方式"
  → 学习 JMM 的投入长期有效
```

## 3. 性能陷阱与权衡

### 3.1 同步的成本量级（x86，量级数据）

| 操作 | 相对成本 |
|------|:---:|
| 普通读写 | 1× |
| volatile 读 | ≈1×（TSO 免费） |
| volatile 写 | 2-10×（lock 前缀） |
| CAS | 5-20× |
| 无竞争 synchronized | ≈CAS |
| 竞争锁（阻塞） | 100-10000×（上下文切换） |

```text
工程推论：
  ① 无竞争同步很便宜（别过度优化）
  ② 竞争是万恶之源（阻塞/切换）
  ③ 真正的成本：优化受限 + 竞争等待
```

### 3.2 典型陷阱

| 陷阱 | 表现 | 对策 |
|------|------|------|
| 细粒度锁过度 | 锁对象多但竞争转移 | 权衡粒度 |
| volatile 循环读 | 每轮全屏障 | 本地缓存 + 定期检查 |
| 伪共享（false sharing） | 多线程同缓存行互踢 | 填充/分离（见缓存目录） |
| LongAdder 用错场景 | 需要精确值 | 精确场景用 AtomicLong |
| 锁顺序不一致 | 死锁 | 全局锁序 |
| 大临界区 | 串行化严重 | 缩小临界区 |

### 3.3 锁竞争优化路线

```text
① 缩小临界区（只锁必要部分）
② 读写分离（ReadWriteLock / StampedLock）
③ 无锁化（原子类 / LongAdder）
④ 分片（分段锁 / ConcurrentHashMap 思想）
⑤ 避免同步（不可变对象 / ThreadLocal / 事件驱动）

评估工具：JFR（锁竞争事件）、jstack 线程转储、jmc 分析
```

## 4. 正确性验证方法

### 4.1 静态验证：人工 HB 分析

```text
流程（04 模块三步法）：
  ① 列出所有共享变量读写
  ② 找同步边（锁/volatile/线程生命周期）
  ③ 逐条验证 HB 链

适合：核心共享数据的设计评审
局限：大型系统人工分析不可行 → 靠工具 + 规范
```

### 4.2 动态验证工具

| 工具 | 检测内容 | 适用 |
|------|---------|------|
| JFR | 锁竞争、pinning、暂停 | 生产观测 |
| ThreadSanitizer（JVM 实验） | 数据竞争检测 | 测试阶段 |
| jcstress | 内存模型压力测试框架 | **JMM 验证标准** |
| 压力测试 + 断言 | 行为正确性 | 常规 |
| jmh | 性能基准（非正确性） | 性能验证 |

```text
jcstress 的价值：
  官方并发测试框架（OpenJDK 出品）
  自动生成多种线程调度 → 暴露数据竞争
  例：验证自定义并发原语的 HB 语义

局限：动态验证不能证明"正确"（只能证明"未发现错误"）
  → 正确性最终靠规范分析（HB 链）
```

### 4.3 验证流程建议

```text
新并发代码的验证闭环：
  Step 1  规范分析：画 HB 链（设计期）
  Step 2  jcstress 压力测试（开发期）
  Step 3  生产 JFR 观测（运行期）
  Step 4  代码评审（同行验证 HB 分析）

注意：本地"跑对了"无意义（调度偶然性）
  → 必须规范正确 + 工具验证双保险
```

## 5. 常见并发错误清单

| # | 错误 | JMM 层面 | 修复 |
|---|------|---------|------|
| 1 | 裸共享变量 | 无 HB 边 | volatile/锁/并发容器 |
| 2 | volatile 计数器 | 非原子读-改-写 | AtomicLong |
| 3 | 读方不加锁 | 无同步边 | 读写同锁 |
| 4 | 双重检查无 volatile | 重排序半初始化 | volatile 或静态内部类 |
| 5 | HashMap 并发写 | 数据结构破坏 | ConcurrentHashMap |
| 6 | 依赖 sleep 同步 | sleep 无 HB | 显式同步 |
| 7 | 先检查后执行无锁 | 竞态条件 | 原子/锁 |
| 8 | 发布未同步 | 半初始化可见 | 安全发布模式 |
| 9 | 忽略中断/等待 | 逻辑错误 | 处理中断 |
| 10 | 锁顺序不一致 | 死锁 | 全局锁序 |

> 🎯 核心要点：并发错误的 90% 可归为两类——**无 HB 边（可见性）与复合操作无原子性**。修复路径无非三条：加同步点（volatile/锁）、用并发容器、用原子类。JEP 491 之后 synchronized 在虚拟线程场景重新可用——但"版本敏感"（21-23 仍需 ReentrantLock 替代）值得每个团队写进规范。

## 6. 学习路径建议

```text
① 掌握规则（04 模块）→ 判断正确性的唯一依据
② 理解硬件（02 模块）→ 理解成本与平台差异
③ 会用工具（07 模块）→ 把规则封装成 API 使用
④ 学会验证（本章）→ jcstress + JFR + HB 分析
⑤ 跟踪演进 → JEP 491（JDK 24）、ScopedValue（JEP 506）

配套阅读：
  JUC/虚拟线程目录（JEP 444/491/525 的线程层全景）
  Java多线程目录（API 层）
  计算机组成原理/缓存与Cache/05（缓存一致性硬件层）
```

> 🎯 **核心要点**：JMM 是"稳定公约 + 实现演进"的组合——规则 20 年不变（值得深学），实现持续演进（JEP 491 让 synchronized 回归虚拟线程场景）。工程上：**正确性靠规范（HB 链），验证靠工具（jcstress/JFR），性能靠理解成本（无竞争同步很便宜）**。

## 7. 小结

| 问题 | 答案 |
|------|------|
| JEP 491 改了什么？ | 监视器归属虚拟线程自身 → synchronized 不再 pinning |
| JMM 规范变了吗？ | 没变（JLS 第 17 章稳定；变化在实现层） |
| 无竞争同步贵吗？ | 不贵（volatile 读≈0、synchronized≈CAS） |
| 怎么验证正确性？ | HB 分析（规范）+ jcstress（压力）+ JFR（生产） |
| 最典型的错误？ | 无 HB 边 + 复合操作无原子性 |
| JDK 21-23 注意什么？ | synchronized+阻塞 I/O 会 pinning（用 ReentrantLock） |
