## 1. 后端视角的核心认知

### 1.1 内存模型（调优核心靶点）

| 区域 | 存储内容 | 后端风险 |
|------|----------|----------|
| **堆（Heap）** | 对象实例、数组 | GC 主战场，OOM 主要发生地 |
| 新生代 | Eden（80%）+ Survivor 0/1（各 10%） | Minor GC 频繁 → 接口响应延迟 |
| 老年代 | 多次 GC 存活对象 | Full GC → 服务卡顿、STW |
| **元空间（Metaspace）** | 类元数据、常量池、静态变量 | 大量动态代理/反射 → OOM |
| **虚拟机栈** | 方法栈帧 | 递归过深 → StackOverflowError |

### 1.2 垃圾回收器速选

| 回收器 | 目标 | 适用场景 | JDK 版本 |
|--------|------|----------|----------|
| **G1 GC** | 平衡吞吐量+延迟 | ✅ 后端 Web/微服务首选（4GB+ 堆） | JDK 9+ 默认 |
| **Parallel GC** | 吞吐量优先 | 批处理、数据计算 | JDK 8 默认 |
| **ZGC** | 超低延迟（毫秒级） | 金融交易、高频接口 | JDK 11+ |
| CMS GC | 低延迟 | ⚠️ 已废弃（JDK 9+），内存碎片 | 老项目兼容 |

### 1.3 类加载机制

> 核心遵循**双亲委派模型**。Spring AOP、动态代理、反射频繁触发类加载，处理不当 → 元空间溢出、类加载冲突。

## 2. 案例一：微服务接口频繁卡顿

### 问题现象

| 指标 | 正常 | 异常 |
|------|------|------|
| 接口响应 | 200ms | **8s** |
| Young GC | 2 分钟/次 | **30 秒/次** |
| Full GC 持续 | 200ms | **5 秒** |
| 老年代使用率 | — | **98%** |

> 电商订单服务，8 核 16GB，JDK 11 + G1 GC。

### 排查三步走

```text
① jinfo -flags <pid>     → 发现 -Xms4g -Xmx8g（不相等，堆频繁扩容）
② jstat -gcutil <pid> 1s → 老年代持续增长，Full GC 回收量极少
③ jmap -dump → MAT 分析  → 发现百万级 Order 对象驻留（批量查询缓存未关闭）
```

### 调优方案

**紧急修复**：

- 关闭批量查询结果集缓存 + 增加 10 分钟过期策略
- `jmap -histo:live <pid>` 触发 Full GC 临时释放

**长期 JVM 参数**（16GB 服务器）：

```text
-Xms10g -Xmx10g                           # 初始=最大，避免堆震荡（60% 内存）
-XX:+UseG1GC                              # 显式启用 G1
-XX:MaxGCPauseMillis=200                  # 期望最大停顿
-XX:G1HeapRegionSize=8m                   # 适配大堆
-XX:InitiatingHeapOccupancyPercent=45     # 提前触发并发 GC
-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m
-XX:+PrintGCDetails -XX:+PrintGCDateStamps
-Xloggc:/var/log/jvm/gc.log
-XX:+UseStringDeduplication
```

### 验证效果

| 指标 | 调优前 | 调优后 |
|------|--------|--------|
| Young GC | 30 秒/次，停顿长 | 1-2 分钟/次，≤50ms |
| Full GC | 频繁，5 秒/次 | 0-1 次/天，≤300ms |
| 接口响应 | 8s | 200-300ms |
| 老年代 | 98% | <60% |

## 3. 案例二：批处理任务 OOM

### 问题现象

> 数据同步批处理服务，JDK 8，运行 3-4 天后 `java.lang.OutOfMemoryError: Metaspace`，服务崩溃。

### 排查三步走

```text
① 日志明确 "Metaspace" 溢出 → 问题在元空间
② jstat -class <pid> → 类加载数量持续增加，卸载极少
③ 代码排查 → 大量反射+Spring 动态代理生成数据转换类，未做资源释放
```

### 调优方案

**代码优化（核心）**：

| 措施 | 效果 |
|------|------|
| 缓存动态代理类 | 避免每次批处理重新生成 |
| 释放反射资源 | `Method`/`Field` 对象及时解除引用 |
| 静态工具类替代部分动态生成 | 减少不必要的反射/代理 |

**JVM 参数**：

```text
-XX:MetaspaceSize=512m -XX:MaxMetaspaceSize=1024m
-XX:+CMSClassUnloadingEnabled    # JDK 8 默认关闭，需显式开启
```

### 验证效果

> 稳定运行 7 天+，元空间使用率稳定 40%，类加载数趋于稳定，GC 正常卸载无用类。

## 4. 案例三：高并发接口 CPU 飙升

### 问题现象

> 支付接口，QPS 5000+，JDK 17 + ZGC，16 核 32GB。CPU 飙至 90%+，响应 50ms-1s 波动，无 Full GC。

### 排查三步走

```text
① top -H -p <pid> → 找 CPU 最高线程 → jstack 查状态 → 均处于"JIT 编译"
② jinfo 查 JIT 参数 → CompileThreshold=10000（默认，过高）
③ Arthas trace → 支付校验方法（QPS 5000+）未被 JIT 编译，每次解释执行
```

### 调优方案

**JIT 参数**：

```text
-XX:+AggressiveOpts
-XX:+UseFastAccessorMethods
-XX:CompileThreshold=5000          # 降低阈值，更快触发 JIT
-XX:CICompilerCount=8              # 编译线程 = CPU 核数/2
-XX:+PrintCompilation              # 跟踪编译情况
```

**代码优化**：热点方法拆分简化 + 避免频繁创建临时对象 + 全局变量改局部变量。

### 验证效果

| 指标 | 调优前 | 调优后 |
|------|--------|--------|
| CPU | 90%+ | 40-60% |
| 接口响应 | 50ms-1s | 50-80ms 稳定 |
| 热点方法 | 解释执行 | JIT 编译，效率 +60% |

## 5. 调优原则与避坑指南

### 核心原则

```text
① 先调代码，再调参数 —— 代码内存泄漏，参数再好也无效
② 参数适配场景 —— 微服务（低延迟 G1/ZGC）vs 批处理（高吞吐 Parallel）
③ 监控先行 —— 基于 GC 日志 + 内存快照 + CPU 数据，拒绝盲调
④ 循序渐进 —— 每次只调 1-2 个参数，验证效果后再继续
```

### 高频避坑

| 避坑 | 说明 |
|------|------|
| `-Xms` ≠ `-Xmx` | 堆频繁扩容/缩容 → 性能损耗 |
| 堆内存盲目过大 | 10GB → 32GB，Full GC 停顿 300ms → 1s+ |
| 忽略元空间 | JDK 8+ 动态类过多仍会 OOM |
| 过度依赖 JIT | 热点代码太复杂 → JIT 编译失败 → CPU 更高 |
| 关闭 `UseCompressedOops` | 32GB+ 内存关闭 → 浪费内存 |

## 6. 必备工具

| 类别 | 工具 | 用途 |
|------|------|------|
| **JDK 自带** | `jps` / `jstat` / `jmap` / `jstack` / `jinfo` | 快速排查（全覆盖） |
| **可视化** | MAT | 堆快照分析，定位内存泄漏 |
| **在线诊断** | **Arthas** | 无需重启，在线排查热点/线程 |
| **监控平台** | Prometheus + Grafana | 生产持续监控 |
| **GC 日志** | GCEasy | 在线分析 GC 日志，生成可视化报告 |
