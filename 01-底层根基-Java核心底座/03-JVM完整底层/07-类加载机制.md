## 1. 类加载的生命周期

### 1.1 整体流程

```
┌──────────┐    ┌───────────────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ Loading  │───▶│     Linking       │───▶│Initial-  │───▶│  Using   │───▶│Unloading │
│ (加载)    │    │     (连接)        │    │ization   │    │ (使用)   │    │ (卸载)   │
└──────────┘    └───────────────────┘    └──────────┘    └──────────┘    └──────────┘
                      │
         ┌────────────┼────────────┐
         ▼            ▼            ▼
    Verification  Preparation   Resolution
    (验证)        (准备)        (解析)
```

> 💡 **解析阶段的灵活性**：JVM 规范允许在初始化之后才执行解析（Resolution），这是**动态绑定** / **晚期解析**的底层基础，也是多态得以实现的根本原因。

### 1.2 各阶段核心职责

| 阶段 | 核心职责 | 是否执行 Java 代码 | 典型异常 |
|------|---------|-------------------|---------|
| 加载 | 获取 .class 二进制字节流，堆中生成 Class 对象 | 否 | `ClassNotFoundException` |
| 验证 | 校验字节码合法性，防止恶意字节码 | 否 | `VerifyError` |
| 准备 | 为静态变量分配元空间内存，设置默认零值 | 否 | — |
| 解析 | 常量池符号引用替换为直接引用（内存地址） | 否 | `NoSuchMethodError` |
| 初始化 | 执行 `<clinit>`（静态变量赋值 + 静态代码块） | **是（唯一）** | `ExceptionInInitializerError` |

> 🎯 **记忆口诀**："加载验证准备解析初始化"——前四个阶段是 JVM 内部行为，只有初始化阶段才会执行开发者编写的 Java 代码。

## 2. 加载（Loading）

### 2.1 三个核心动作

1. 通过类的全限定名获取**二进制字节流**
2. 将字节流转化为**方法区**的运行时数据结构
3. 在堆中生成 **`java.lang.Class` 对象**，作为方法区数据的访问入口

### 2.2 二进制字节流的来源

| 来源 | 典型场景 |
|------|---------|
| 本地文件系统 | 标准 classpath 加载 |
| JAR 包 | 第三方 Maven 依赖 |
| 网络 | 远程加载（Applet） |
| 动态代理生成 | Spring AOP `Proxy.newProxyInstance()`、MyBatis Mapper |
| JSP 编译 | Tomcat JasperLoader 访问 JSP 时动态生成 |
| 数据库 / 加密文件 | 自定义 ClassLoader 读取加密字节码 |

### 2.3 加载 API 对比

```java
// Class.forName() —— 默认执行初始化阶段（JDBC 驱动专用）
Class<?> c1 = Class.forName("com.mysql.cj.jdbc.Driver");

// ClassLoader.loadClass() —— 仅加载 + 链接，不执行初始化
Class<?> c2 = MyClass.class.getClassLoader().loadClass("com.example.MyClass");

// Class.forName() —— 可控制是否执行初始化
Class<?> c3 = Class.forName("com.example.MyClass", false, tccl);

// .class 字面量 —— 不触发初始化（编译期常量）
Class<?> c4 = MyClass.class;
```

> ⚠️ `Class.forName()` 会执行静态代码块；`ClassLoader.loadClass()` 不会。JDBC 4.0 之前驱动注册正是利用 `forName()` 触发 `Driver` 的静态注册代码。

## 3. 验证（Verification）

### 3.1 四个校验关卡

| 验证阶段 | 检查内容 | 失败异常 |
|---------|---------|---------|
| **文件格式** | 魔数 `0xCAFEBABE`、JDK 版本号、常量池结构 | `ClassFormatError` |
| **元数据** | 父类是否存在、是否继承 final 类、抽象方法是否实现 | `NoClassDefFoundError` |
| **字节码** | 操作数栈类型匹配、跳转指令合法性、类型转换安全（最复杂） | `VerifyError` |
| **符号引用** | 常量池中引用的类/方法/字段是否存在且可访问 | `NoSuchMethodError`、`IllegalAccessError` |

## 4. 准备（Preparation）

### 4.1 核心规则

- 为 **静态变量** 在元空间中分配内存，设置**默认零值**
- `static final` 常量在准备阶段直接赋值为 `ConstantValue`
- 实例变量在对象实例化时在堆中分配，与此阶段无关

| 代码声明 | 准备阶段值 | 初始化阶段值 |
|---------|-----------|------------|
| `static int value = 123` | 0 | 123 |
| `static Object obj = new Object()` | null | 堆中对象引用 |
| `static final int CONST = 456` | **456**（直接赋值） | 不变 |
| `static final String S = "hi"` | **"hi"**（常量池） | 不变 |

```java
public class OrderTrap {
    // ❌ 静态代码块中使用未显式赋值的静态变量——只能看到准备阶段的零值
    // static { System.out.println(count); } // 输出 0，而非 10
    // public static int count = 10;

    // ✅ 变量定义在静态代码块之前
    public static int count = 10;
    static { System.out.println(count); } // 输出 10
}
```

## 5. 解析（Resolution）

### 5.1 概念对比

| 类型 | 定义 | 示例 |
|------|------|------|
| **符号引用** | 以一组符号描述目标，无歧义定位 | `java/lang/String.equals(Ljava/lang/Object;)Z` |
| **直接引用** | 指向目标的指针或偏移量 | 内存地址 `0x7c3627f8` |

### 5.2 解析的七种目标类型

| 类型 | 常量池入口 | 对应指令 |
|------|-----------|---------|
| 类/接口 | `CONSTANT_Class_info` | `anewarray`、`checkcast`、`instanceof` |
| 字段 | `CONSTANT_Fieldref_info` | `getfield`、`putfield`、`getstatic`、`putstatic` |
| 方法 | `CONSTANT_Methodref_info` | `invokevirtual`、`invokespecial`、`invokestatic` |
| 接口方法 | `CONSTANT_InterfaceMethodref_info` | `invokeinterface` |
| 方法类型 | `CONSTANT_MethodType_info` | `invokedynamic`（JDK 7+） |
| 方法句柄 | `CONSTANT_MethodHandle_info` | `invokedynamic` |
| 调用点限定符 | `CONSTANT_Dynamic_info` | `invokedynamic`（JDK 11+） |

## 6. 初始化（Initialization）

### 6.1 `<clinit>()` 方法

编译器自动收集 **静态变量赋值** + **静态代码块** 合并而成的类构造器。

```java
public class ClinitDemo {
    // 编译后的 <clinit>() 等价于（按源文件顺序合并）：
    // static void <clinit>() {
    //     x = 10;
    //     System.out.println("static block 1: x = " + x);
    //     x = 20;
    //     y = x * 2;
    //     System.out.println("static block 2: x = " + x + ", y = " + y);
    // }
    static int x = 10;
    static { System.out.println("static block 1: x = " + x); x = 20; }
    static int y = x * 2;
    static { System.out.println("static block 2: x = " + x + ", y = " + y); }
}
```

### 6.2 `<clinit>()` 五大特性

| 特性 | 说明 |
|------|------|
| **线程安全** | JVM 加锁同步执行，同一时间只有一个线程能执行 |
| **父类优先** | 父类的 `<clinit>()` 先于子类执行 |
| **按序合并** | 静态变量赋值和静态代码块按出现顺序合并 |
| **可不生成** | 无静态变量赋值且无静态代码块则不生成 |
| **接口特殊** | 接口 `<clinit>()` 不需要先于实现类执行 |

### 6.3 完整初始化顺序

```
① 父类静态变量显式赋值 ── 按顺序 ── 父类静态代码块
                          │
                          ▼
② 子类静态变量显式赋值 ── 按顺序 ── 子类静态代码块
                          │
                          ▼
③ 父类实例变量 ── 父类构造代码块 ── 父类构造器
                          │
                          ▼
④ 子类实例变量 ── 子类构造代码块 ── 子类构造器
```

## 7. 类加载器分类

### 7.1 JDK 8 类加载器层次

```
┌──────────────────────────────────────────────────────┐
│          Bootstrap ClassLoader (C++, null)           │
│  加载 <JAVA_HOME>/lib/rt.jar → java.lang.* 等核心库   │
└──────────────────────┬───────────────────────────────┘
                       │ parent
┌──────────────────────▼───────────────────────────────┐
│       Extension ClassLoader (sun.misc.Launcher$Ext)  │
│  加载 <JAVA_HOME>/lib/ext/*.jar                       │
└──────────────────────┬───────────────────────────────┘
                       │ parent
┌──────────────────────▼───────────────────────────────┐
│    Application ClassLoader (sun.misc.Launcher$App)   │
│  加载 classpath → 项目代码、第三方 Maven 依赖          │
└──────────────────────┬───────────────────────────────┘
                       │ parent
┌──────────────────────▼───────────────────────────────┐
│          Custom ClassLoader                           │
│  热部署、字节码加密、Tomcat 容器隔离等                 │
└──────────────────────────────────────────────────────┘
```

### 7.2 JDK 9+ 模块化变化

| 对比项 | JDK 8 | JDK 9+ |
|-------|-------|--------|
| 顶层 | Bootstrap (null) | Bootstrap (null) |
| 第二层 | Extension ClassLoader | **Platform ClassLoader** |
| 第三层 | Application ClassLoader | Application ClassLoader |
| 核心 API | `rt.jar`、`tools.jar` | 模块化 `java.base`、`java.sql` 等 |
| 加载方式 | 从 JAR 文件 | 从模块（`jimage` 格式） |

### 7.3 验证代码

```java
public class ClassLoaderHierarchy {
    public static void main(String[] args) {
        ClassLoader app = ClassLoaderHierarchy.class.getClassLoader();
        System.out.println("Application: " + app);

        ClassLoader platform = app.getParent();
        System.out.println("Platform: " + platform);

        ClassLoader bootstrap = platform.getParent();
        System.out.println("Bootstrap: " + bootstrap); // null

        System.out.println("String loader: " + String.class.getClassLoader()); // null
    }
}
```

## 8. 双亲委派模型源码分析

### 8.1 核心源码逐行解析

```java
// java.lang.ClassLoader.loadClass() —— 双亲委派核心实现
protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {   // ① 加锁，线程安全
        // 第一步：检查类是否已被加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                // 第二步：委派给父加载器
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    // 第三步：无父加载器，由 Bootstrap 尝试
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器找不到，忽略异常
            }
            if (c == null) {
                // 第四步：父加载器找不到，自己尝试加载
                c = findClass(name);
            }
        }
        if (resolve) resolveClass(c); // 需要解析则执行
        return c;
    }
}
```

### 8.2 执行流程图

```
loadClass("com.example.MyService")
    │
    ▼
┌─────────────────────────────┐
│ findLoadedClass 已加载？     │
│ └── 是 → 直接返回           │
└─────────────────────────────┘
    │ 未加载
    ▼
┌─────────────────────────────┐
│ parent != null ?             │
│ ├── 是 → parent.loadClass() │  ← 向上委托
│ └── 否 → Bootstrap 尝试     │
└─────────────────────────────┘
    │ 父加载器找不到
    ▼
┌─────────────────────────────┐
│ findClass(name) 自己加载     │  ← defineClass() 生成 Class
└─────────────────────────────┘
```

### 8.3 双亲委派的两大价值

| 价值 | 说明 | 示例 |
|------|------|------|
| **安全性** | 防止核心 API 被篡改 | 自定义 `java.lang.String` 永远无法加载，Bootstrap 优先加载 rt.jar 的标准 String |
| **避免重复加载** | 同一全限定名类只加载一次 | 不同类加载器加载的同一类在 JVM 中视为**不同类**，`instanceof` 会返回 false |

### 8.4 类的唯一性规则

> ⚠️ **关键点**：类的唯一性由 **"加载它的类加载器"** + **"类的全限定名"** 共同决定。同一全限定名的类由两个不同加载器加载，在 JVM 中是两个完全独立的 Class 对象，互相强转抛出 `ClassCastException`。这是 DevTools 热部署类型转换异常的根源。

## 9. 破坏双亲委派的三种场景

### 9.1 Tomcat WebAppClassLoader

**需求**：同一 Tomcat 部署多个 Web 应用，各应用可能依赖不同版本的 Spring、MyBatis。

**方案**：为每个 WebApp 创建独立 ClassLoader，**优先加载自身 `WEB-INF/lib` 和 `WEB-INF/classes` 中的类**。

```
Tomcat 类加载器体系：
  Bootstrap
    └── System (Application)
          └── Common (Tomcat 自身 + 共享类)
                ├── Catalina
                │     └── Shared
                │           ├── Webapp1CL (WEB-INF/lib 优先)
                │           └── Webapp2CL (WEB-INF/lib 优先)
                └── JasperLoader (JSP 热加载)
```

### 9.2 SPI 机制（JDBC 驱动）

**核心矛盾**：
- SPI 接口 `java.sql.Driver` 由 **Bootstrap ClassLoader** 加载
- 实现类 `com.mysql.cj.jdbc.Driver` 在 classpath，由 **Application ClassLoader** 加载
- 双亲委派中父加载器看不到子加载器的类

**解决方案**：线程上下文类加载器（TCCL）—— 详见第 10 节。

### 9.3 OSGi / 自定义热部署

```java
/**
 * 破坏双亲委派的自定义加载器。
 * 核心逻辑：核心类由 Bootstrap 加载，非核心类优先自己加载。
 */
public class BreakDelegationClassLoader extends ClassLoader {
    private final String classPath;

    public BreakDelegationClassLoader(String classPath) {
        this.classPath = classPath;
    }

    @Override
    public Class<?> loadClass(String name) throws ClassNotFoundException {
        if (name.startsWith("java.") || name.startsWith("javax.")) {
            return super.loadClass(name); // 核心类必须由 Bootstrap 加载
        }
        try {
            return findClass(name);       // 优先自己加载（打破委派）
        } catch (ClassNotFoundException e) {
            return super.loadClass(name); // 找不到再委托父加载器
        }
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        try {
            String fileName = classPath + "/" + name.replace('.', '/') + ".class";
            byte[] bytes = Files.readAllBytes(Paths.get(fileName));
            return defineClass(name, bytes, 0, bytes.length);
        } catch (IOException e) {
            throw new ClassNotFoundException(name);
        }
    }
}
```

> 💡 **热部署原理**：每次修改代码后创建新的 ClassLoader 重新加载类。由于类加载器不同，新旧 Class 对象完全隔离，实现不重启 JVM 更新代码。Spring DevTools `RestartClassLoader` 和 JRebel 均基于此原理。

### 9.4 总结

| 场景 | 代表技术 | 打破方式 | 目的 |
|------|---------|---------|------|
| Web 容器 | Tomcat `WebAppClassLoader` | 优先加载自身 WEB-INF 类 | 多应用依赖隔离 |
| SPI | JDBC `DriverManager` | 线程上下文类加载器逆向委派 | 父加载器调用子加载器加载的类 |
| 模块化 | OSGi `BundleClassLoader` | 网络状加载器关系 | 模块间依赖管理 |
| 热部署 | Spring DevTools | 新建 ClassLoader 重新加载 | 免重启更新代码 |
| 字节码框架 | CGLIB、ASM | 自定义加载器直接加载动态生成类 | 运行时代理类 |

## 10. 线程上下文类加载器

### 10.1 SPI 的核心矛盾

```
Bootstrap ClassLoader                    Application ClassLoader
┌─────────────────────────┐              ┌──────────────────────┐
│  java.sql.DriverManager │  ──(要加载)──▶│ com.mysql.jdbc.Driver│
│  java.sql.Driver (接口)  │  ✗ 不可见   │ (在 classpath 中)    │
│  ServiceLoader          │              └──────────────────────┘
└─────────────────────────┘
```

**问题本质**：子加载器可委托父加载器，但**父加载器无法回调子加载器**。`DriverManager`（Bootstrap 加载）需要加载 MySQL 驱动类（Application 加载），双亲委派模型中行不通。

### 10.2 TCCL 的工作原理

```java
// 线程上下文类加载器的设置与获取
ClassLoader contextCL = Thread.currentThread().getContextClassLoader();
System.out.println("Default TCCL: " + contextCL); // 默认 Application

// 可手动设置（框架常用）
Thread.currentThread().setContextClassLoader(new CustomClassLoader("/tmp/classes"));

// ServiceLoader 内部实现（核心逻辑）：
// ClassLoader cl = Thread.currentThread().getContextClassLoader();
// if (cl == null) cl = ClassLoader.getSystemClassLoader();
// return new ServiceLoader<>(service, cl);
ServiceLoader<Driver> drivers = ServiceLoader.load(Driver.class);
```

### 10.3 Spring 中的应用

```java
// Spring 通过 TCCL 加载用户自定义 Bean
public abstract class SpringContextUtil {
    public static <T> T loadBean(Class<T> beanType) {
        ClassLoader cl = Thread.currentThread().getContextClassLoader();
        if (cl == null) cl = ClassLoader.getSystemClassLoader();
        try {
            Class<?> beanClass = cl.loadClass(beanType.getName());
            return beanType.cast(beanClass.getDeclaredConstructor().newInstance());
        } catch (Exception e) {
            throw new RuntimeException("Failed to load bean", e);
        }
    }
}
```

> 🎯 **TCCL 本质**：破坏双亲委派的**逆向委派机制**——让父加载器通过线程上下文反向获取子加载器的能力，加载原本不可见的类。是 SPI 机制的基石，也是 Spring、MyBatis、JDBC 等框架能够工作的关键。

## 11. 类的主动使用与被动引用

### 11.1 六种主动引用（触发初始化）

```java
public class ActiveRef {
    public static void main(String[] args) throws Exception {
        // 1. new 关键字
        Parent p = new Parent();
        // 2. 访问静态字段（非 final）
        System.out.println(Parent.value);
        // 3. 调用静态方法
        Parent.staticMethod();
        // 4. 反射调用
        Class.forName("com.example.Parent");
        // 5. 初始化子类，先触发父类初始化
        Child child = new Child();
        // 6. 启动类（main 所在类）
    }
}
```

### 11.2 三种被动引用（不触发初始化）

```java
public class PassiveRef {
    public static void main(String[] args) {
        // 1. 通过子类引用父类静态字段 → 只触发父类初始化
        System.out.println(Child.value); // Parent init, 不输出 Child init

        // 2. 数组定义引用类 → 触发 [LParent; 而非 Parent
        Parent[] arr = new Parent[10];   // 不触发任何 static 块

        // 3. 访问编译期常量（static final）→ 常量折叠优化
        System.out.println(Child.CONST); // 不触发任何初始化
    }
}

class Parent {
    static int value = 42;
    static final String CONST = "const";
    static { System.out.println("Parent init"); }
}
class Child extends Parent {
    static { System.out.println("Child init"); }
}
```

> 💡 **常量折叠**：`static final String CONST = "const"` 在编译期被替换为字面量注入引用类的常量池，对 `CONST` 的访问实际是访问当前类的常量池，与被引用类无关。

## 12. 面试高频考点

### 12.1 概念问答

| 问题 | 答案 |
|------|------|
| 类加载五阶段？ | 加载 → 验证 → 准备 → 解析 → 初始化 |
| 哪个阶段执行 Java 代码？ | 初始化阶段执行 `<clinit>()` |
| 双亲委派是什么？ | 子加载器先委托父加载器，父找不到再由自己加载 |
| 双亲委派两大价值？ | ① 安全性（防篡改核心 API）② 避免重复加载 |
| 如何打破双亲委派？ | ① 重写 `loadClass()` ② TCCL ③ OSGi 网络状加载器 |

### 12.2 异常对比

| 对比项 | `ClassNotFoundException` | `NoClassDefFoundError` |
|-------|------------------------|------------------------|
| 类型 | **Exception**（受检） | **Error** |
| 阶段 | 加载阶段 | 初始化阶段 |
| 原因 | `.class` 文件不存在 | 字节码存在但初始化失败（静态块异常等） |
| 排查 | 检查依赖、classpath | 排查 static 块异常栈 `Caused by` |

### 12.3 API 对比

| 对比项 | `Class.forName()` | `ClassLoader.loadClass()` |
|-------|------------------|--------------------------|
| 执行初始化 | **是** | **否** |
| 适用场景 | JDBC 驱动注册 | 延迟加载、仅需 Class 对象 |
| 调用方式 | 静态方法 | 实例方法 |

### 12.4 源码考核要点

```
loadClass() 核心流程四步走：
① synchronized 加锁
② findLoadedClass() 检查是否已加载
③ parent.loadClass() 或 findBootstrapClassOrNull() 向上委托
④ findClass() 自己加载
```

### 12.5 场景设计题

| 问题 | 核心要点 |
|------|---------|
| Tomcat 为何能部署不同版本的 Spring？ | 每个 WebApp 独立 `WebAppClassLoader`，优先加载自身 `WEB-INF/lib` |
| 为什么 JDBC 4.0 不需要 `Class.forName()`？ | SPI + TCCL，ServiceLoader 读取 `META-INF/services/` 配置 |
| 自定义 `java.lang.String` 能成功吗？ | 不能，双亲委派下 Bootstrap 优先加载标准 String |
| Metaspace OOM 的典型原因？ | 大量 CGLIB 动态代理、JSP 频繁编译、自定义加载器不卸载 |
| DevTools 热部署类型转换异常原因？ | 同一类被不同 ClassLoader 加载，JVM 中视为不同类型 |

### 12.6 相关 JVM 参数

```bash
-XX:+TraceClassLoading          # 追踪类加载
-XX:+TraceClassUnloading        # 追踪类卸载
-verbose:class                  # 类加载详细日志
-XX:MetaspaceSize=256m          # 元空间初始大小
-XX:MaxMetaspaceSize=512m       # 元空间最大值（防止 Metaspace OOM）
```

---

> 🎯 **核心要点总结**
>
> 1. **五阶段生命周期**：加载（获取二进制流）→ 验证（安全校验）→ 准备（静态变量零值）→ 解析（符号引用转直接引用）→ 初始化（执行 `<clinit>`）
> 2. **双亲委派模型**：`loadClass()` 源码四步走——`findLoadedClass` → `parent.loadClass` / `findBootstrapClassOrNull` → `findClass`
> 3. **破坏双亲委派三驾马车**：Tomcat WebAppClassLoader（应用隔离）、SPI/TCCL（逆向委派）、OSGi/热部署（网络状加载器）
> 4. **两大异常区分**：`ClassNotFoundException`（加载阶段）vs `NoClassDefFoundError`（初始化阶段）
> 5. **类的唯一性**：全限定名 + 类加载器共同决定，不同加载器加载的同一类在 JVM 中视为不同类型
