## 1. HotSpot 收集器全景与组合关系

### 1.1 六大经典收集器总览

HotSpot 虚拟机在 JDK 7/8 时代提供了六款经典垃圾收集器，按代际划分为新生代收集器和老年代收集器，彼此通过接口组合使用：

```ascii
                    新生代 (Young)                   老年代 (Old)

               ┌──────────────────┐          ┌──────────────────┐
   Serial ────→│    Serial        │───connect─→│   Serial Old     │
               │  (单线程, Copy)  │          │  (单线程, Compact)│
               └──────────────────┘          └──────────────────┘

               ┌──────────────────┐          ┌──────────────────┐
   ParNew ────→│    ParNew        │───only───→│      CMS          │
               │  (多线程, Copy)  │          │  (并发, Sweep)    │
               └──────────────────┘          └──────────────────┘

               ┌──────────────────┐          ┌──────────────────┐
  Throughput → │ Parallel Scavenge│───connect─→│  Parallel Old     │
               │  (多线程, Copy)  │          │  (多线程, Compact)│
               └──────────────────┘          └──────────────────┘
```

**连线规则（可搭配使用的组合）：**

| 新生代收集器 | 老年代收集器 | 启动参数 | JDK 默认 |
|-------------|-------------|---------|---------|
| Serial | Serial Old | `-XX:+UseSerialGC` | JDK 7 客户端模式 |
| ParNew | CMS | `-XX:+UseConcMarkSweepGC` | 需显式指定 |
| Parallel Scavenge | Parallel Old | `-XX:+UseParallelGC` | **JDK 8 服务端默认** |
| G1（独立，不受上述限制） | | `-XX:+UseG1GC` | **JDK 9+ 默认** |

> 💡 G1 已超越经典收集器的范畴，不在此章讨论。本章聚焦 JDK 8 及之前的主流收集器。

### 1.2 JDK 版本的默认收集器演变

| JDK 版本 | 默认收集器组合 | 关键变化 |
|---------|--------------|---------|
| JDK 7 | Parallel Scavenge + Parallel Old | CMS 可用但非默认 |
| **JDK 8** | **Parallel Scavenge + Parallel Old** | CMS 可用，企业广泛使用 |
| JDK 9 | **G1** | CMS **标记为 deprecated** |
| JDK 11 | G1 | ZGC 实验性引入 |
| JDK 14 | G1 | **CMS 正式移除** |
| JDK 15+ | G1 | ZGC 转正，Shenandoah 可用 |

> 🎯 尽管 JDK 9+ 已默认 G1，但大量存量系统仍运行在 JDK 8 上，理解经典收集器是排查线上 GC 问题和面试的必备技能。

### 1.3 并行 vs 并发的概念区分

| 概念 | 说明 | 特点 |
|------|------|------|
| **并行 (Parallel)** | 多条 GC 线程协作，用户线程处于等待状态 | 提高 GC 效率，但 STW 时间更长 |
| **并发 (Concurrent)** | GC 线程与用户线程同时执行 | 降低停顿，但增加实现复杂度和 CPU 争抢 |
| **串行 (Serial)** | 单线程执行 GC，用户线程等待 | 简单高效，无线程交互开销 |

## 2. Serial 收集器：单线程新生代

### 2.1 基本信息

```bash
-XX:+UseSerialGC    # Serial (Young) + Serial Old (Old)
```

| 特性 | 描述 |
|------|------|
| 线程数 | **单线程** |
| 暂停模式 | Stop-The-World（所有用户线程停止） |
| GC 算法 | **标记-复制 (Mark-Copy)** |
| 适用场景 | 客户端模式、单核 CPU、桌面应用、< 100MB 堆 |
| 优点 | 简单高效，无线程交互开销，单核下表现最优 |
| 缺点 | STW 时间长，多核 CPU 无法利用多核优势 |

### 2.2 工作流程

```ascii
时间线 ───────────────────────────────────────────────────►

  用户线程 ┌─────────────┐          ┌─────────────┐
  正常运行 │   业务逻辑   │   STW    │   业务逻辑   │
           └──────┬──────┘          └─────────────┘
                  │ GC 触发                 时间
                  ▼
          ┌───────────────┐
          │ Serial 单线程  │
          │ 标记-复制      │
          │ 全程 STW      │
          └───────────────┘
```

```java
// 验证当前使用的 GC 收集器
public class GCDetector {
    public static void main(String[] args) {
        List<GarbageCollectorMXBean> beans =
                ManagementFactory.getGarbageCollectorMXBeans();
        for (GarbageCollectorMXBean bean : beans) {
            System.out.println(bean.getName());
        }
        // Serial 输出: Copy (Young), MarkSweepCompact (Old)
    }
}
```

> ⚠️ Serial 收集器在 JDK 8 服务端模式下已不再是默认选项，但在**单核 CPU 环境**或**微容器（内存极小）场景**中，因省去线程调度开销，性能反而优于并行收集器。

## 3. ParNew 收集器：多线程新生代

### 3.1 基本信息

```bash
-XX:+UseParNewGC               # JDK 9 前可用
-XX:ParallelGCThreads=N        # 并行线程数（默认 = CPU 核数）
```

| 特性 | 描述 |
|------|------|
| 本质 | **Serial 的多线程版本** |
| GC 算法 | **标记-复制 (Mark-Copy)**，多线程并行 |
| 线程数 | 默认 = CPU 核数 |
| 搭配限制 | **只能与 CMS 搭配使用** |
| 适用场景 | Server 模式，与 CMS 配合的低延迟场景 |

### 3.2 ParNew + CMS 是 JDK 8 低延迟时代的标配

```ascii
ParNew (Young, 多线程 Mark-Copy, STW)  ← 新生代 Minor GC
    │
    │ 存活对象晋升
    ▼
CMS (Old, 并发 Mark-Sweep, 少量 STW)     ← 老年代 GC
```

> 💡 ParNew 与 Serial 的核心区别仅在于**多线程并行**进行标记-复制。由于 ParNew 是唯一能与 CMS 搭配的新生代收集器，在 JDK 8 的低延迟方案中不可或缺。

### 3.3 并行线程数控制

```bash
# 控制 ParNew 的并行线程数（一般无需修改）
-XX:ParallelGCThreads=4

# CPU 核数 < 8 时：ParallelGCThreads = CPU 核数
# CPU 核数 > 8 时：ParallelGCThreads = 3 + (5 * CPU / 8)
```

> ⚠️ ParNew 在 JDK 9 已被标记为废弃（deprecated），JDK 14 随 CMS 一同移除。JDK 9+ 应使用 G1 替代。

## 4. Parallel Scavenge 收集器：吞吐量优先新生代

### 4.1 基本信息

```bash
# JDK 8 默认启用（-XX:+UseParallelGC 等效）
-XX:+UseParallelGC              # 新生代 Parallel Scavenge
-XX:+UseParallelOldGC           # 老年代 Parallel Old（JDK 6u23+ 默认关联）
-XX:ParallelGCThreads=N         # GC 线程数
```

| 特性 | 描述 |
|------|------|
| 设计目标 | **高吞吐量**（关注 CPU 用于业务的时间占比） |
| GC 算法 | **标记-复制 (Mark-Copy)**，多线程并行 |
| 与 ParNew 的区别 | **更关注吞吐量控制，支持自适应调节** |
| 适用场景 | 后台计算、批量处理、ETL、对停顿不敏感的场景 |

### 4.2 吞吐量优先的三大控制参数

```
吞吐量 = 用户代码运行时间 / (用户代码运行时间 + GC 时间)
```

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `-XX:MaxGCPauseMillis` | 期望最大停顿时间（毫秒） | 无默认，值越小则 GC 频率越高 |
| `-XX:GCTimeRatio` | 吞吐量目标：GC 时间占比 = 1 / (1 + N) | **99**（允许 1% 时间用于 GC） |
| `-XX:+UseAdaptiveSizePolicy` | 开启**GC 自适应调节（GC Ergonomics）** | 关闭 |

### 4.3 自适应调节机制 (GC Ergonomics)

```bash
# 只需设定目标，JVM 自动调优
java -XX:+UseParallelGC \
     -XX:MaxGCPauseMillis=100 \
     -XX:GCTimeRatio=99 \
     -XX:+UseAdaptiveSizePolicy \
     -jar app.jar
```

开启自适应后，JVM 会根据实际运行情况自动调整：
- Eden / Survivor 比例
- 晋升老年代的年龄阈值
- 新生代 / 老年代大小

> 🎯 Parallel Scavenge 的这一特性使其成为"吞吐量优先"场景的首选——开发者只需声明目标（停顿时间 / 吞吐量），JVM 自主完成代际调优。

### 4.4 三种新生代收集器对比

| 收集器 | 线程模式 | 算法 | STW | 核心关注点 | 最佳场景 |
|--------|---------|------|-----|-----------|---------|
| **Serial** | 单线程 | 标记-复制 | 全程 STW | 简单无开销 | 客户端 / 单核 / < 100MB 堆 |
| **ParNew** | 多线程并行 | 标记-复制 | 全程 STW | 与 CMS 配合 | 服务端 + CMS 低延迟方案 |
| **Parallel Scavenge** | 多线程并行 | 标记-复制 | 全程 STW | **吞吐量优先** | 后台批处理 / 离线计算 |

> ⚠️ CRITICAL：三者的新生代 GC 算法都是**标记-复制（Mark-Copy）**，区别仅在线程模型和关注目标。

## 5. Serial Old 收集器：单线程老年代

### 5.1 基本信息

```bash
# 启用 Serial + Serial Old
-XX:+UseSerialGC
```

| 特性 | 描述 |
|------|------|
| 线程数 | **单线程** |
| 暂停模式 | Stop-The-World |
| GC 算法 | **标记-整理 (Mark-Compact)** |
| 用途 | **CMS 失败的后备方案**，客户端模式老年代收集 |

### 5.2 标记-整理算法流程

```ascii
标记前:
┌─────┬─────┬─────┬─────┬─────┬─────┐
│  A  │  B  │  C  │  D  │  E  │  F  │    (A、C、E 存活)
└─────┴─────┴─────┴─────┴─────┴─────┘
              ↓ 标记存活对象 + 向一端移动
标记-整理后:
┌─────┬─────┬─────┬──────────────────┐
│  A  │  C  │  E  │     空闲         │    无碎片
└─────┴─────┴─────┴──────────────────┘
```

**标记-整理 vs 标记-清除：**

| 对比项 | 标记-整理 (Mark-Compact) | 标记-清除 (Mark-Sweep) |
|--------|------------------------|----------------------|
| 碎片 | **无碎片**（存活对象连续排列） | 严重碎片化 |
| 分配效率 | 指针碰撞，高效 | 空闲链表，低效 |
| 停顿时间 | 较长（需要移动对象） | 较短 |
| 典型应用 | Serial Old、Parallel Old | CMS |

### 5.3 Serial Old 的三个使用场景

1. **JDK 8 客户端模式**：与 Serial 搭配作为完整 GC 方案。
2. **CMS 的后备方案**：CMS 发生 Concurrent Mode Failure 时，退化为 Serial Old 执行 Full GC（此时 STW 时间急剧增加）。
3. **与 Parallel Scavenge 搭配（JDK 5 及之前）**：在 Parallel Old 出现前，Parallel Scavenge 只能与 Serial Old 搭配。

> ⚠️ 线上 CMS 场景若出现"Concurrent Mode Failure - Use Serial Old"，说明 CMS 已无法维持，系统将经历长时间的 Full GC STW——这是**最需要警惕的异常模式**。

## 6. Parallel Old 收集器：多线程老年代

### 6.1 基本信息

```bash
-XX:+UseParallelOldGC    # JDK 6u23+ 默认与 UseParallelGC 关联
```

| 特性 | 描述 |
|------|------|
| 线程数 | **多线程** |
| 暂停模式 | Stop-The-World |
| GC 算法 | **标记-整理 (Mark-Compact)**，多线程并行 |
| 设计目标 | **高吞吐量** |
| 出现背景 | JDK 6 之前 Parallel Scavenge 无老年代伙伴，只能配 Serial Old |

### 6.2 Parallel Scavenge + Parallel Old 组合

```bash
# JDK 8 服务端默认的吞吐量优先方案
java -Xms4g -Xmx4g \
     -XX:+UseParallelGC \
     -XX:+UseParallelOldGC \
     -XX:ParallelGCThreads=8 \
     -XX:MaxGCPauseMillis=500 \
     -XX:GCTimeRatio=19 \          # 5% 时间用于 GC (1/(1+19))
     -XX:+UseAdaptiveSizePolicy \
     -jar batch-processor.jar
```

```ascii
Parallel GC 完整周期：

  ┌─────────────────────────┐      ┌─────────────────────────┐
  │  Parallel Scavenge      │      │  Parallel Old            │
  │  (Young Gen)            │─────→│  (Old Gen)               │
  │                         │ 晋升 │                          │
  │  Mark-Copy (多线程并行)  │      │  Mark-Compact (多线程并行) │
  │  STW                    │      │  STW                     │
  └─────────────────────────┘      └─────────────────────────┘
         ↓ 频繁但快                      ↓ 低频但慢
    Minor GC 通常 < 50ms           Full GC 可能 > 1s
```

> 💡 Parallel Old 的出现使 Parallel Scavenge 形成了完整的"吞吐量优先"组合，这是 JDK 8 服务端默认方案的背后逻辑——追求单位时间内完成最多的业务任务。

### 6.3 六大收集器核心参数速查

```bash
# 常用收集器切换参数
-XX:+UseSerialGC                 # Serial + Serial Old
-XX:+UseParNewGC                 # ParNew（JDK 9 废弃）
-XX:+UseConcMarkSweepGC          # ParNew + CMS
-XX:+UseParallelGC               # Parallel Scavenge + Parallel Old
-XX:+UseParallelOldGC            # Parallel Old（JDK 6u23+ 被 UseParallelGC 隐含启用）
```

## 7. CMS 收集器：低延迟老年代（并发标记-清除）

### 7.1 基本信息

```bash
# JDK 8 低延迟方案（JDK 9+ deprecated，JDK 14 移除）
-XX:+UseConcMarkSweepGC            # 启用 CMS（自动关联 ParNew）
-XX:CMSInitiatingOccupancyFraction=70  # CMS 触发阈值（老年代 70%）
-XX:+UseCMSInitiatingOccupancyOnly      # 仅使用设定的阈值
-XX:+CMSScavengeBeforeRemark            # Remark 前触发一次 Young GC
-XX:CMSFullGCsBeforeCompaction=0        # Full GC 后整理
```

| 特性 | 描述 |
|------|------|
| 设计目标 | **最短回收停顿时间**（响应时间优先） |
| 搭配的新生代 | **只能使用 ParNew** |
| GC 算法 | **标记-清除 (Mark-Sweep)**（老年代） |
| 适用场景 | B/S 架构服务端、高并发 Web 接口、对响应时间敏感的系统 |
| 历史地位 | JDK 9 前最主流的低延迟收集器，G1 出现前的首选 |

### 7.2 为什么 CMS 需要与 ParNew 搭配

CMS 的老年代回收是并发的（与用户线程同时运行），但**新生代回收必须是 STW 的**。ParNew 的多线程并行能力能缩短新生代 STW 时间，配合 CMS 实现整体低延迟。

```ascii
CMS 整体结构：

  ParNew (Young GC)
  ┌───────────────────────────────────┐
  │  多线程标记-复制（STW）            │
  │  Eden 满时触发 Minor GC            │
  │  存活对象 → Survivor / 老年代      │
  └───────────────┬───────────────────┘
                  │ 晋升
                  ▼
  CMS (Old GC)
  ┌───────────────────────────────────┐
  │  并发标记-清除（大部分并发）         │
  │  老年代占用率触发                    │
  │  Initial Mark(STW) → Concurrent    │
  │  Mark → Remark(STW) → Concurrent   │
  │  Sweep                             │
  └───────────────────────────────────┘
```

## 8. CMS 的四个阶段与三色标记

### 8.1 CMS 四阶段流程图

```ascii
时间线 ──────────────────────────────────────────────────────►

 Phase 1        Phase 2          Phase 3         Phase 4
┌────────┐  ┌──────────────┐  ┌────────┐  ┌──────────────┐
│Initial  │  │  Concurrent  │  │ Remark │  │ Concurrent   │
│ Mark    │  │  Mark        │  │(STW)   │  │ Sweep       │
│(STW)    │  │(用户线程并发)  │  │        │  │(用户线程并发)  │
└────┬───┘  └──────┬───────┘  └────┬───┘  └──────┬───────┘
     │             │               │             │
     ▼             ▼               ▼             ▼
  标记 GC     遍历对象图       修正并发标记    回收不可达
  Roots 直达   (最耗时)       期间变化的       对象
  的对象                       引用             (无整理)
                                   
停顿时间:       无停顿             停顿时间:       无停顿
  很短                            比初标略长
                                   
                                  增量更新
                                  (Incremental
                                   Update)
```

### 8.2 各阶段详解

| 阶段 | 是否 STW | 耗时 | 工作内容 |
|------|---------|------|---------|
| 1. 初始标记 (Initial Mark) | **是** | **很短**（一次 Minor GC 的时间） | 标记 GC Roots 直接关联的对象 + 年轻代指向老年代的引用 |
| 2. 并发标记 (Concurrent Mark) | **否** | **最长**（整个遍历过程） | 从 GC Roots 出发遍历整个对象图，标记所有可达对象 |
| 3. 重新标记 (Remark) | **是** | **比初标略长** | 修正并发标记期间因用户程序运行而变化的引用（增量更新） |
| 4. 并发清除 (Concurrent Sweep) | **否** | 中等 | 清除已标记为死亡的对象，回收内存 |

### 8.3 三色标记算法详解

CMS 和 G1 等并发收集器使用**三色标记法**进行并发可达性分析：

| 颜色 | 含义 | 处理方式 |
|------|------|---------|
| **白色** | 尚未被访问 | 标记结束时仍为白色 → 不可达 → 回收 |
| **灰色** | 自身已被标记，但其引用的对象尚未完全标记 | **中间状态** → 需要继续扫描 |
| **黑色** | 自身和所有引用都已完成标记 | 存活对象，不再扫描 |

```ascii
三色标记过程示例：

初始状态:
  [GC Roots] ──→ [A(灰)] ──→ [B(白)]
                                 │
                                 └──→ [C(白)]

并发标记进行中:
  [GC Roots] ──→ [A(黑)] ──→ [B(灰)] ──→ [D(白)]
                                 │
                                 └──→ [C(白)]

并发标记完成:
  [GC Roots] ──→ [A(黑)] ──→ [B(黑)] ──→ [D(黑)]
                                 │
                                 └──→ [C(白)] ← 不可达，回收
```

### 8.4 并发标记的核心问题：对象消失

```ascii
问题场景（并发标记过程中）：

  初始:  A(黑) ──→ B(白)         C(灰) ──→ B(白)  (B 被两个对象引用)
  后发:  A(黑) ──→ B(白) ──→ X   C(灰)          (C → B 的引用被删除!)
  
  结果:  B 虽然是可达的（A → B 可达），但 A 已经是黑色（不会再扫描）
        C 是灰色，但已不再引用 B
        B 被错误标记为白色 → 回收 → **程序崩溃！**
```

**两种解决方案：**

| 方案 | 采用者 | 原理 |
|------|-------|------|
| **增量更新 (Incremental Update)** | **CMS** | 当黑色对象**新增**指向白色对象的引用时，将黑色对象重新变为灰色，Remark 阶段重新扫描 |
| **SATB (Snapshot At The Beginning)** | **G1** | 记录并发标记开始时所有存活对象的快照。并发期间被删除的引用通过写屏障记录，确保那些对象不会被错误回收 |

```java
/**
 * CMS 增量更新示意：当黑色对象新增指向白色对象的引用时，
 * 将该黑色对象重新标记为灰色，保证 Remark 阶段不遗漏
 */
// 假设对象 A(黑) 新增指向对象 B(白) 的引用
// CMS 通过写屏障拦截，将 A 重新置为灰色
// Remark 阶段重新扫描 A 的所有引用，发现 B 是可达的
```

> 💡 CMS 的增量更新更精确（只记录新增引用），但 Remark 阶段需要重新扫描被修改的对象；G1 的 SATB 更保守（记录快照），可能产生更多浮动垃圾但 Remark 更简单。

## 9. CMS 的三大问题：CPU 敏感 / 浮动垃圾 / 内存碎片

### 9.1 问题一：CPU 资源敏感

CMS 的所有并发阶段（并发标记、并发清除）会与用户线程争抢 CPU 资源。

```bash
# 默认并发线程数 = (CPU 核心数 + 3) / 4
# 4 核服务器 → 约 1 个并发 GC 线程
# 2 核服务器 → 严重影响应用性能
```

| CPU 核心数 | 并发 GC 线程数 | 影响程度 |
|-----------|--------------|---------|
| 2 核 | 1 | **严重受影响**（GC 占用 50% CPU） |
| 4 核 | 1 | 中等（GC 占用 25%） |
| 8 核 | 2 | 可接受（GC 占用 25%） |
| 16 核 | 4 | 影响较小 |

```bash
# 调低并发线程数以减少对应用的影响
-XX:ConcGCThreads=N
```

> ⚠️ 2 核 CPU 的服务器应**避免**使用 CMS 收集器，并发阶段会严重拖慢应用响应。

### 9.2 问题二：浮动垃圾 (Floating Garbage)

CMS 的并发标记和并发清除阶段，用户线程仍在运行，持续产生新对象：

```ascii
时间线 ───────────────────────────────────────────────────►

        并发标记阶段              并发清除阶段
   ┌─────────────────┐    ┌─────────────────┐
   │ 用户线程持续运行   │    │ 用户线程持续运行   │
   │ 产生新对象         │    │ 产生新对象         │
   │ → 这些对象本次     │    │ → 这些对象本次     │
   │   CMS 不标记      │    │   CMS 不清除      │
   └─────────────────┘    └─────────────────┘
        ↓                       ↓
   浮动垃圾 (本次未回收)     浮动垃圾 (本次未回收)
                             积累到下一次 GC
```

**后果**：CMS 必须预留空间容纳浮动垃圾，否则会触发 Concurrent Mode Failure。

```bash
# 解决方案1：提前触发 CMS（降低触发阈值）
-XX:CMSInitiatingOccupancyFraction=70   # 默认 92%，降低到 70%
-XX:+UseCMSInitiatingOccupancyOnly      # 仅使用设定的阈值

# 解决方案2：增大老年代空间，提供更多缓冲
-Xmx8g                # 增大堆大小
-XX:NewRatio=3        # 降低新生代比例 → 增大老年代
```

### 9.3 问题三：内存碎片化 (Fragmentation)

CMS 使用**标记-清除**算法，因此**不会自动整理内存**，长期运行后会产生大量内存碎片。

```ascii
CMS 长期运行后的老年代：

 初始状态（连续）:
  ┌──────────────────────────────────────────┐
  │  存活对象 │ 存活对象 │ 存活对象 │ 存活对象 │
  └──────────────────────────────────────────┘

 多次 CMS GC 后（碎片化）:
  ┌─────┬───┬─────┬───┬─────┬───┬─────┬───┐
  │ 存活 │ 空 │ 存活 │ 空 │ 存活 │ 空 │ 存活 │ 空 │
  └─────┴───┴─────┴───┴─────┴───┴─────┴───┘
  ↑   碎片     碎片    碎片     碎片    碎片

 分配大对象时失败:
  需要 5 块连续空闲 → 无法满足 → Promotion Failed → Full GC
```

**碎片化导致的连锁反应：**

```
碎片化严重
    ↓
分配大对象时找不到连续空间
    ↓
Promotion Failed / Concurrent Mode Failure
    ↓
触发 Full GC（退化为 Serial Old）
    ↓
长时间 STW（可能数秒到数十秒）
    ↓
服务超时、雪崩
```

```bash
# 缓解方案：定期整理
-XX:+UseCMSCompactAtFullCollection     # Full GC 时整理（默认开启）
-XX:CMSFullGCsBeforeCompaction=5       # 5 次 Full GC 后进行一次整理

# 根本方案：升级到 G1（无碎片问题）
-XX:+UseG1GC
```

### 9.4 CMS 三大问题总结

| 问题 | 原因 | 影响 | 缓解措施 |
|------|------|------|---------|
| **CPU 敏感** | 并发阶段抢占 CPU | 应用吞吐量下降 | 控制并发线程数；2 核以下避免使用 CMS |
| **浮动垃圾** | 并发阶段用户线程仍在运行 | 提前触发 GC；Concurrent Mode Failure | 降低触发阈值（70%）；增大堆空间 |
| **内存碎片** | 标记-清除算法不整理 | 大对象分配失败；退化为 Full GC | 定期整理；根本方案：换 G1 |

> 🎯 CMS 的退出并非因为它是失败的收集器，而是因为 G1 在保持低延迟的同时解决了 CMS 的碎片化痛点，且在停顿可预测性上更优秀。JDK 14 正式移除 CMS 标志着**经典收集器时代的终结**。

## 10. 收集器组合选择指南

### 10.1 选型决策树

```ascii
服务类型？
├── 客户端 / 单核 CPU / < 100MB 堆
│   └── Serial + Serial Old (-XX:+UseSerialGC)
│
├── 批量处理 / 后台计算 / 离线 ETL
│   └── Parallel Scavenge + Parallel Old (-XX:+UseParallelGC)
│       → 目标：高吞吐量
│
├── 高并发接口 / Web 服务 (JDK 8)
│   ├── 对停顿敏感 → ParNew + CMS (-XX:+UseConcMarkSweepGC)
│   └── 可升级 JDK → G1
│
└── JDK 9+ 服务端 (推荐)
    └── G1 (-XX:+UseG1GC)
        → 默认首选，平衡吞吐量和延迟
```

### 10.2 六大收集器全维度对比

| 收集器 | 所属代 | 线程模型 | GC 算法 | 是否 STW | 设计目标 | 启用参数 | JDK 状态 |
|--------|-------|---------|---------|---------|---------|---------|---------|
| **Serial** | Young | 单线程 | 标记-复制 | 全程 STW | 简单高效 | `-XX:+UseSerialGC` | 可用 |
| **ParNew** | Young | 多线程并行 | 标记-复制 | 全程 STW | 与 CMS 配合 | `-XX:+UseParNewGC` | **JDK 9 废弃** |
| **Parallel Scavenge** | Young | 多线程并行 | 标记-复制 | 全程 STW | **吞吐量优先** | `-XX:+UseParallelGC` | JDK 8 默认 |
| **Serial Old** | Old | 单线程 | **标记-整理** | 全程 STW | CMS 后备方案 | `-XX:+UseSerialGC` | 可用 |
| **Parallel Old** | Old | 多线程并行 | **标记-整理** | 全程 STW | **吞吐量优先** | `-XX:+UseParallelOldGC` | JDK 8 默认 |
| **CMS** | Old | **并发** | **标记-清除** | **少量 STW** | **低延迟** | `-XX:+UseConcMarkSweepGC` | **JDK 14 移除** |

### 10.3 组合选型速查

| 组合 | 核心优势 | 核心劣势 | 最佳场景 | JDK 版本 |
|------|---------|---------|---------|---------|
| Serial + Serial Old | 简单、无线程开销 | 单线程 STW 长 | 客户端 / 单核 / 微容器 | 全版本 |
| ParNew + CMS | 低延迟、并发清除 | CPU 敏感、碎片化 | JDK 8 高并发接口 | JDK 7~13 |
| **Parallel + Parallel Old** | **高吞吐量** | STW 时间长 | **JDK 8 默认、批处理** | JDK 7~21 |
| G1（独立） | 平衡、可预测停顿 | 小堆性能略差 | JDK 9+ 默认、微服务 | JDK 7+ |
| ZGC（独立） | < 1ms 超低延迟 | 实现复杂 | 大堆（> 16GB）、高频交易 | JDK 15+ |

### 10.4 生产环境推荐配置模板

```bash
# 方案 A: JDK 8 高并发接口（低延迟）
java -Xms4g -Xmx4g \
     -XX:+UseConcMarkSweepGC \
     -XX:CMSInitiatingOccupancyFraction=70 \
     -XX:+UseCMSInitiatingOccupancyOnly \
     -XX:+CMSScavengeBeforeRemark \
     -XX:+UseCMSCompactAtFullCollection \
     -XX:CMSFullGCsBeforeCompaction=5 \
     -XX:+PrintGCDetails \
     -XX:+PrintGCDateStamps \
     -Xloggc:/var/log/app/gc.log \
     -jar web-api.jar

# 方案 B: JDK 8 批量处理（吞吐量优先）
java -Xms8g -Xmx8g \
     -XX:+UseParallelGC \
     -XX:+UseParallelOldGC \
     -XX:ParallelGCThreads=8 \
     -XX:MaxGCPauseMillis=500 \
     -XX:GCTimeRatio=19 \
     -XX:+UseAdaptiveSizePolicy \
     -jar batch-processor.jar

# 方案 C: JDK 9+ 微服务（G1 推荐）
java -Xms4g -Xmx4g \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=100 \
     -XX:MetaspaceSize=256m \
     -XX:MaxMetaspaceSize=512m \
     -jar microservice.jar
```

> 💡 如果项目运行在 JDK 8 且短期内无法升级，ParNew + CMS 仍是高并发 Web 服务的最佳选择。但需要做好 CMS 的监控和参数调优，特别是设定合理的 CMSInitiatingOccupancyFraction 并开启碎片整理选项。

## 11. 面试高频考点

### 11.1 基础问答

**Q1：JDK 8 默认的垃圾收集器是什么？它的设计目标是什么？**

JDK 8 服务端默认是 **Parallel Scavenge + Parallel Old** 组合，设计目标是**高吞吐量**（最大化 CPU 用于业务代码的时间占比）。通过 `-XX:+UseParallelGC` 和 `-XX:GCTimeRatio` 等参数控制 GC 时间占比。

**Q2：CMS 收集器的四个阶段是什么？哪些阶段会 Stop The World？**

四个阶段：**初始标记**(STW) → **并发标记**(无 STW) → **重新标记**(STW) → **并发清除**(无 STW)。其中初始标记和重新标记两个阶段会 STW，初始标记很快（只标记 GC Roots 直达对象），重新标记修正并发期间变化的引用。

**Q3：ParNew 和 Parallel Scavenge 有什么区别？**

| 对比维度 | ParNew | Parallel Scavenge |
|---------|--------|-----------------|
| 核心目标 | 配合 CMS 实现低延迟 | 高吞吐量优先 |
| GC 算法 | 标记-复制 | 标记-复制 |
| 线程模型 | 多线程并行 | 多线程并行 |
| 自适应调节 | 不支持 | **支持**（UseAdaptiveSizePolicy） |
| 搭配限制 | **只能与 CMS 搭配** | 与 Parallel Old 搭配 |

**Q4：什么是 Concurrent Mode Failure？如何应对？**

CMS 在并发标记过程中，老年代被浮动垃圾填满，无法分配对象时触发。CMS 会退化为 **Serial Old** 进行 Full GC（单线程标记-整理，STW 时间极长）。

应对措施：
- 降低 `-XX:CMSInitiatingOccupancyFraction`（如 70%），提前触发 CMS
- 增大堆大小，提供更多缓冲空间
- 长期方案：升级到 G1 收集器

### 11.2 进阶问答

**Q5：解释三色标记法。CMS 和 G1 分别如何处理并发标记时的对象漏标问题？**

三色标记法将对象分为白色（未访问）、灰色（自身已标记，引用未标记完）、黑色（全部标记完成）。

| 收集器 | 避免漏标的方案 | 原理 |
|-------|-------------|------|
| **CMS** | **增量更新 (Incremental Update)** | 黑色对象新增指向白色对象的引用时，将黑色变回灰色，Remark 重新扫描 |
| **G1** | **SATB (Snapshot At The Beginning)** | 记录初始标记时的对象快照，并发期间删除的引用通过写屏障记录，确保不会误回收 |

**Q6：Serial Old 收集器除了与 Serial 搭配，还有什么重要作用？**

**CMS 的后备方案**。当 CMS 发生 Concurrent Mode Failure 时，JVM 会自动退化为 Serial Old 执行 Full GC。这是 CMS 生产环境中 STW 时间陡增的主要原因。

**Q7：Parallel Old 为什么出现？它解决了什么问题？**

在 JDK 6 之前，Parallel Scavenge 只能与 Serial Old 搭配（因为 CMS 的并发设计不适合与吞吐量优先的 Parallel Scavenge 配合）。Parallel Old 的出现使 Parallel Scavenge 拥有了完整的多线程老年代伙伴，形成了完整的**吞吐量优先组合**，并在 JDK 8 成为了默认方案。

### 11.3 深度问题

**Q8：如何查看当前 JVM 使用的垃圾收集器？**

```bash
# 命令行方式
jinfo -flag UseG1GC <pid>
jcmd <pid> VM.flags | findstr GC

# Java 代码方式
ManagementFactory.getGarbageCollectorMXBeans()
    .forEach(bean -> System.out.println(bean.getName()));
// Parallel 输出: PS Scavenge, PS MarkSweep
// G1 输出: G1 Young Generation, G1 Old Generation
```

**Q9：什么是吞吐量（Throughput）？如何通过参数控制？**

```
吞吐量 = 用户代码运行时间 / (用户代码运行时间 + GC 总时间)
```

控制参数：`-XX:GCTimeRatio=N`，默认 N=99，即允许 1/(1+99) = **1%** 的时间用于 GC。N=19 时允许 5% 的 GC 时间。

**Q10：从 Serial 到 CMS，收集器的演进脉络是什么？**

```
Serial (单线程) 
    → Parallel (多线程并行，追求吞吐量) 
    → CMS (并发，追求低延迟) 
    → G1 (Region 化，平衡吞吐量和延迟) 
    → ZGC / Shenandoah (染色指针，< 1ms 停顿)
```

这条演进脉络的核心矛盾始终是**吞吐量 vs 延迟**的权衡。经典收集器时代的集大成者是 CMS，而 CMS 的三个痛点（CPU 敏感、浮动垃圾、内存碎片）正是 G1 设计的出发点。

---

> 🎯 **核心要点总结**
>
> 1. **三对组合**掌握连线规则：Serial + Serial Old（客户端）、ParNew + CMS（低延迟）、Parallel Scavenge + Parallel Old（高吞吐）
> 2. **Parallel Scavenge** 是 JDK 8 服务端默认，核心特性是吞吐量优先 + 自适应调节（GC Ergonomics）
> 3. **CMS** 的核心价值是**并发降低 STW**，但引入三大问题：CPU 争抢、浮动垃圾、内存碎片
> 4. **三色标记 + 增量更新**是 CMS 并发标记的精髓，面试高频考点
> 5. **Concurrent Mode Failure** 退化为 Serial Old 是 CMS 最严重的异常场景
> 6. CMS 在 JDK 14 被移除，G1 是它的自然继任者——理解 CMS 的痛点就是理解 G1 设计的起点
