## 1. OOM 四类：从异常名定位

**OOM 的异常名直接告诉你是哪个区域**：

| OOM 类型 | 异常信息 | 区域 | 排查方向 |
|---------|---------|------|---------|
| 堆溢出 | `Java heap space` | 堆 | 泄漏 vs 容量（见第 3 节） |
| 元空间溢出 | `Metaspace` | 元空间 | 动态类/类加载器泄漏 |
| 线程溢出 | `unable to create native thread` | 栈/线程 | 线程数/栈大小/系统限制 |
| 直接内存 | `Direct buffer memory` | 直接内存 | NIO/Netty 泄漏 |

```bash
# 堆溢出排查起点
jcmd <pid> GC.heap_info         # 堆配置与使用
jcmd <pid> GC.class_histogram   # 对象嫌疑
# 元空间排查
jcmd <pid> GC.class_histogram | grep -i classloader   # 类加载器统计
# 线程 OOM
jstack <pid> | grep -c "java.lang.Thread"             # 线程数
```

**OOM 处理的总原则**：

```text
① 先留现场：OOM 前转储（-XX:+HeapDumpOnOutOfMemoryError）
   → 参数：-XX:HeapDumpPath=/data/dump/
② 分析根因（泄漏？容量？代码？）而非直接加大堆
③ 修复代码 > 调大内存（调大只是拖延）
④ 容器环境：+ExitOnOutOfMemoryError 快速重启（僵尸 Pod 处理）
```

> 🎯 **核心要点**：OOM 排查 = "**异常名定位区域 → 留现场（HeapDumpOnOOM）→ 根因分析**"——**"先留现场再处理"**是黄金法则（转储参数提前配好）；调大内存是临时止血不是修复。

## 2. GC 频繁与停顿排查

**"GC 频繁"的排查路径**（与 03 模块决策链联动）：

```text
现象：日志大量 GC、接口变慢、CPU 高
① 确认频率与类型：jstat -gcutil（YGC/FGC 次数）
② 分类型定位：
   Minor GC 频繁 → 分配速率高（JFR 分配事件）→ 优化对象创建
   Full GC 频繁 → IHOP/存活集 → 降 IHOP 或查泄漏
   停顿超目标 → P99 分布（JFR）→ 参数调优或换收集器
③ 单参数实验 → 对比基线
④ 代码侧：大对象（Humongous）、缓存清理、集合泄漏
```

```bash
# 快速判断"分配太快 vs 容量不足"
jstat -gcutil <pid> 1000 10
# 现象 A：E 很快满、O 平稳 → 分配速率问题（代码）
# 现象 B：O 持续高位、FGC 多 → 老年代压力（容量/IHOP/泄漏）
```

**停顿排查的三个工具组合**：

```text
① jstat：频率与类型（第一眼）
② JFR GC 事件：P95/P99 停顿分布（量化）
③ GC 日志：-Xlog:gc*（详细事件，含 ergonomics 决策）
→ 三层叠加定位"停在哪、为什么停"
```

> 🎯 **核心要点**：GC 频繁排查 = "**分类型（Minor vs Full）→ 分归因（分配 vs 容量）→ 对症**"——**"E 快满 O 平稳 = 分配问题；O 高位 FGC 多 = 老年代问题"**是最重要的二分判断。

## 3. 内存泄漏定位五步

**泄漏定位的标准流程**（面试必背，与 02 模块联动）：

```text
① 确认泄漏：堆/RSS 持续增长不回落
   → jstat -gcutil 多次采样看趋势
② 抓堆转储：jcmd <pid> GC.heap_dump heap.hprof
   → 建议连抓两次（间隔数分钟，对比增量）
③ 分析转储：MAT 打开
   → Histogram（对象分布）→ Dominator Tree（支配树）
   → Leak Suspects（泄漏嫌疑报告）
④ 定位引用链：GC Roots → 嫌疑对象的路径
   → "谁持有它"：static Map / ThreadLocal / 缓存未清理
⑤ 修复验证：修代码 → 同负载复测 → 趋势确认回落
```

**四种经典泄漏模式**：

| 模式 | 场景 | 定位线索 |
|------|------|---------|
| 静态集合 | `static Map` 只加不删 | Dominator 根在 static |
| ThreadLocal | 线程池中未 remove | ThreadLocalMap 持有 |
| 监听器/回调 | 注册未注销 | 集合持有业务对象 |
| 类加载器 | 热部署/动态类 | Metaspace 增长 + classloader 引用 |

```java
// 泄漏示例（静态集合 + 大对象）
public class CacheManager {
    private static final Map<String, byte[]> CACHE = new HashMap<>();
    public static void put(String k, byte[] v) { CACHE.put(k, v); }
    // 只加不删 → 大 byte[] 永不回收 → 堆持续增长
}
```

> 🎯 **核心要点**：泄漏五步 = "**确认趋势 → 双转储 → MAT 分析 → 引用链 → 修复验证**"——**"连抓两次对比增量"**是定位"哪些对象在增长"的关键技巧；四种经典模式覆盖 80% 泄漏。

## 4. 死锁与线程阻塞

**死锁排查**（jstack 自动检测）：

```bash
jstack <pid> | grep -A 10 "deadlock"
# Found one Java-level deadlock → 直接给出线程对与锁链
```

**阻塞排查路径**：

```text
① jstack 找大量 BLOCKED/WAITING 线程
② BLOCKED：等 synchronized 锁 → 找锁持有者（同栈中 held by）
③ WAITING：池耗尽/join/等待 → 上下文判断
④ 多次抓取对比：线程一直不动 = 真卡住（vs 瞬态等待）
```

**常见阻塞场景**：

| 场景 | 特征 | 解法 |
|------|------|------|
| 死锁 | 互相等待 + 循环 | 锁顺序/超时（见多线程 06） |
| 线程池耗尽 | 大量 WAITING（队列等待） | 外部依赖超时/有界队列 |
| 数据库连接池耗尽 | 等待获取连接 | 连接池参数/慢 SQL |
| 锁竞争激烈 | 大量 BLOCKED | 锁粒度/无锁化 |

> 🎯 **核心要点**：线程问题 = "**jstack 三看（死锁自动检测/阻塞找持有者/多次对比确认）**"——**"WAITING 大量先查池、BLOCKED 大量先找锁"**；与 `Java多线程/06`、`Java异常体系/07` 联动。

## 5. CPU 飙高排查

**CPU 100% 的排查路径**（线上最高频问题）：

```bash
# ① 找 CPU 最高的进程/线程
top -Hp <pid>            # 进程内线程 CPU 排序（记下最忙线程 ID）
# ② 线程 ID 转十六进制
printf '%x\n' <tid>      # 十进制 → 十六进制（jstack 中 nid）
# ③ jstack 定位线程栈
jstack <pid> | grep -A 20 "nid=0x<hex>"

# 或 Arthas 一步到位
thread -n 3              # 最忙的 3 个线程（自动定位）
```

**CPU 高的三类根因**：

| 根因 | 特征 | 解法 |
|------|------|------|
| 业务死循环/热点 | 业务代码栈反复出现 | 修代码（缓存/算法） |
| GC 频繁 | GC 线程 CPU 高 | 见第 2 节 |
| 锁自旋 | synchronized 竞争 | 锁优化（见 06 模块） |

```text
判断"是 GC 还是业务"：
  top 看进程 CPU → 若 GC 线程占比高 → GC 问题
  业务线程高 → 热点代码（Arthas thread -n + trace）
```

> 🎯 **核心要点**：CPU 排查 = "**top -Hp 找线程 → 十六进制转 nid → jstack 定位栈**"三连（或 Arthas `thread -n` 一步到位）——**"GC 线程高 = GC 问题、业务线程高 = 热点代码"**二分判断。

## 6. 排查流程总图

**线上 JVM 问题的总排查流程**（面试画图题）：

```text
现象（慢/卡/OOM/CPU 高）
  │
  ├─ ① 快速健康检查：jstat（GC）+ top（CPU）
  ├─ ② 分方向：
  │    ├─ GC 问题 → GC 日志 + JFR → 类型定位 → 调参/代码
  │    ├─ 内存问题 → 转储 + MAT → 泄漏定位五步
  │    ├─ 线程问题 → jstack → 死锁/阻塞/热点
  │    └─ CPU 高 → top -Hp → jstack/Arthas → 热点/GC
  ├─ ③ 根因 → 修复（代码优先 > 参数 > 升级）
  └─ ④ 预防：监控接入（GC 指标）+ 转储参数预配 + 压测
```

**预防三件套**（事故前就配好）：

```text
① -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...   # OOM 留现场
② JFR 常开（-XX:StartFlightRecording）                    # 黑匣子
③ GC 日志（-Xlog:gc*）→ 监控接入                            # 趋势可查
```

> 🎯 **核心要点**：排查总图 = "**快速检查 → 四方向（GC/内存/线程/CPU）→ 根因修复 → 预防**"——**"预防三件套（转储/JFR/GC 日志）提前配好**"让事故从"无痕"变"可查"；面试画这张图 = 排查题满分。
