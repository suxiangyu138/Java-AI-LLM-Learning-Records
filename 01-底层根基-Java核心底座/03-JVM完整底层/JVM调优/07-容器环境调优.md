## 1. 容器 JVM 的两大陷阱

**陷阱一：内存限制 <1792MB 回退 SerialGC**：

```text
JVM 的"服务器级"判定：cgroup 内存限制 < 1792MB
  → 判定为非服务器 → 回退单线程 SerialGC
  → 并发服务表现：长 STW + 频繁 Minor GC

解法：显式指定收集器（-XX:+UseG1GC）
  → 不管容器多小，强制 G1（小容器 G1 也是最佳）
```

**陷阱二：默认堆只有容器的 25%**：

```text
JVM 容器感知（UseContainerSupport 默认开）：
  堆上限 = 容器内存限制 × 25%（默认 MaxRAMPercentage=25）
  → 容器限 4GB → 堆只有 1GB → 频繁 GC/OOM

解法：MaxRAMPercentage=50~75（见第 2 节）
```

```text
2026 实测案例：JDK 25 + 容器默认配置
  → SerialGC + 25% 堆（双重坑）
  → 修复：-XX:+UseG1GC -XX:MaxRAMPercentage=50 → 恢复正常
```

> 🎯 **核心要点**：容器两大陷阱 = "**<1792MB 回退 SerialGC + 默认堆 25%**"——**`-XX:+UseG1GC + MaxRAMPercentage`**是必配组合；小容器也必须显式指定收集器（别依赖默认）。

## 2. MaxRAMPercentage：替代静态 -Xmx

**为什么不用 -Xmx**（容器环境）：

```text
-Xmx4g：写死绝对大小 → 容器扩缩容时不匹配
  → 容器 8G 时浪费、容器 2G 时 OOM
MaxRAMPercentage：按容器限制百分比 → 自适应

推荐值：
  50%：为 off-heap（Metaspace/线程栈/直接内存）留一半
       → 有 agent（OTel）+ 并发服务时的稳妥值
  60%：通用容器建议（InitialRAMPercentage 同设）
  75%：简单服务/内存占用低（ECS/EKS 常见）
  100%：❌ 绝对不要（无 off-heap 空间 → 容器 OOM）

验证：JFR/jcmd VM.flags 看 MaxHeapSize 实际值
```

```bash
# 推荐组合（2026 生产验证）：
-XX:+UseG1GC \
-XX:MaxRAMPercentage=50.0 \
-XX:+UseStringDeduplication \
-XX:+ExitOnOutOfMemoryError
# 注入方式：JDK_JAVA_OPTIONS（注意不与 JAVA_TOOL_OPTIONS 冲突）
```

**off-heap 预算**（为什么不能 100%）：

```text
JVM 内存 = 堆 + 元空间 + 线程栈 + 直接内存 + JIT/GC 结构
off-heap 无上限管控 → 堆占满 100% → 其余无空间 → 容器 OOM Kill
→ MaxRAMPercentage 75% 已是激进值，50-60% 更稳
```

> 🎯 **核心要点**：MaxRAMPercentage = "**容器内存的自适应堆配置**"——**50-75% 区间（别 100%）**；`JDK_JAVA_OPTIONS` 注入 + `UseG1GC + ExitOnOOM` 是 2026 生产标配组合。

## 3. 完整容器参数模板

**K8s 部署 JVM 的完整参数模板**（2026 推荐）：

```yaml
# K8s Deployment 片段
spec:
  containers:
    - name: app
      image: app:latest
      resources:
        limits:
          memory: 2Gi        # 容器内存限制
          cpu: "1"           # CPU 限制（ActiveProcessorCount 用）
      env:
        - name: CPU_LIMIT
          valueFrom:
            resourceFieldRef: { resource: limits.cpu }
        - name: JDK_JAVA_OPTIONS
          value: >-
            -XX:+UseG1GC
            -XX:MaxRAMPercentage=60.0
            -XX:InitialRAMPercentage=60.0
            -XX:ActiveProcessorCount=$(CPU_LIMIT)
            -XX:+ExitOnOutOfMemoryError
            -XX:+HeapDumpOnOutOfMemoryError
            -XX:HeapDumpPath=/tmp/dumps
            -Xlog:gc*:file=/tmp/gc.log
```

**模板设计要点**：

| 参数 | 作用 |
|------|------|
| UseG1GC | 防 SerialGC 回退（<1792MB 陷阱） |
| MaxRAMPercentage=60 | 堆自适应（容器限制的 60%） |
| ActiveProcessorCount | CPU 配额（GC 线程数正确） |
| ExitOnOutOfMemoryError | OOM 快速退出（K8s 重启僵尸 Pod） |
| HeapDumpOnOOM | OOM 留现场（分析素材） |
| Xlog:gc* | GC 日志（监控接入） |

> 🎯 **核心要点**：容器模板 = "**六参数一套**"——**G1 + MaxRAM% + ActiveProcessor + ExitOnOOM + 转储 + GC 日志**覆盖"选型/内存/CPU/恢复/现场/监控"六件事；复制模板改百分比即可上线。

## 4. 启动加速：AppCDS（JDK 25 GA）

**启动慢的容器痛点与解法**（2026）：

```text
问题：Java 启动秒级-10 秒级（类加载 + JIT 预热）
  → K8s 滚动更新/弹性扩容时感知明显

方案对比：
  ① AppCDS（应用类数据共享）—— JDK 25 AOT 缓存 GA
     → 类元数据归档 → 启动加速 30-50%
     → 零侵入（-javaagent 兼容）、无需专用 JDK
  ② CRaC（检查点恢复）—— 需专用 JDK
  ③ GraalVM Native —— 无法运行 -javaagent（运维受限）
  → 2026 推荐：AppCDS（性价比最高）
```

```bash
# AppCDS 三步（2026 实践）：
# ① 生成归档（首次运行）
java -XX:ArchiveClassesAtExit=app.jsa -jar app.jar
# ② 后续启动使用
java -XX:SharedArchiveFile=app.jsa -jar app.jar
# ③ 与 OTel agent 兼容（零冲突）
```

**AppCDS 的适用判断**：

```text
适合：微服务/弹性扩容频繁（启动加速直接收益）
注意：依赖变更（框架升级）后需重新生成归档
收益量级：启动 30-50% 加速（类加载阶段为主）
```

> 🎯 **核心要点**：启动加速 = "**AppCDS（JDK 25 GA，零侵入 + 30-50%）> CRaC > GraalVM**"——**"与 -javaagent 兼容"让 AppCDS 成为运维最友好的方案**；面试谈容器启动优化先答 AppCDS = 时效性加分。

## 5. 容器环境排障速查

**容器 JVM 问题速查**：

| 症状 | 根因 | 解法 |
|------|------|------|
| 频繁 GC/OOM | 堆只有 25%（MaxRAM 未配） | MaxRAMPercentage=50-75 |
| 启动后立刻 SerialGC | <1792MB 回退 | 显式 UseG1GC |
| 容器内 GC 慢 | GC 线程按宿主机核数 | ActiveProcessorCount |
| 容器 OOM Kill | 堆 100% + off-heap 无空间 | MaxRAM < 75% |
| 启动慢 | 类加载 + JIT | AppCDS |
| OOM 无现场 | 未配转储 | HeapDumpOnOOM |
| 僵尸 Pod | OOM 不退出 | ExitOnOOM |

**容器 vs 物理机参数差异总结**：

```text
物理机：-Xmx4g + 按物理核数（默认即可）
容器：MaxRAMPercentage + ActiveProcessorCount + 显式收集器
→ "容器参数是另一套配置"——别把物理机参数照搬进容器
```

> 🎯 **核心要点**：容器排障 = "**七症状速查表**"——**"堆 25% + SerialGC 回退 + CPU 不感知"三大陷阱**是容器 JVM 问题的 80%；"容器参数是另一套"是 2026 部署的基本认知。

## 6. 容器调优速查卡

**容器 JVM 参数速查**（复制即用）：

```bash
# 标准容器参数（K8s 注入 JDK_JAVA_OPTIONS）
-XX:+UseG1GC
-XX:MaxRAMPercentage=60.0
-XX:InitialRAMPercentage=60.0
-XX:ActiveProcessorCount=$(CPU_LIMIT)   # downwardAPI 注入
-XX:+ExitOnOutOfMemoryError
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/tmp/dumps
-Xlog:gc*:file=/tmp/gc.log
```

**容器 vs 物理机对照**：

| 维度 | 物理机 | 容器 |
|------|:------:|:----:|
| 堆配置 | -Xmx | MaxRAMPercentage |
| CPU | 默认感知 | ActiveProcessorCount |
| 收集器 | 默认 G1 | **显式 G1**（防 Serial 回退） |
| OOM 处理 | 手动 | ExitOnOOM（自动重启） |
| 启动优化 | 可选 | AppCDS（弹性场景必选） |

**面试一句话**：

```text
"容器化时代 JVM 参数必须重写：
 1792MB 以下会回退 SerialGC（要显式 G1），
 默认堆只有容器的 25%（要 MaxRAMPercentage 50-75%），
 GC 线程按宿主机核数（要 ActiveProcessorCount），
 加 ExitOnOOM 让 K8s 快速重启僵尸 Pod。"
```

> 🎯 **核心要点**：容器速查 = "**标准参数模板 + 物理机对照 + 面试一句话**"——**"容器是另一套配置"**是本模块的灵魂；模板六参数覆盖选型/内存/CPU/恢复/现场/日志。
