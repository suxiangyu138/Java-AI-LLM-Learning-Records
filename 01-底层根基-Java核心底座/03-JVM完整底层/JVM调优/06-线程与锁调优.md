## 1. 线程数：多少合适

**线程数的经验公式**（与 `Java多线程/07` 联动）：

```text
CPU 密集：线程数 = CPU 核数 + 1
IO 密集：线程数 = 核数 × (1 + IO等待/CPU计算)
虚拟线程时代：IO 密集不猜线程数（每任务一个虚拟线程）

JVM 侧的影响：
  线程数 × 栈大小（-Xss）= 线程内存
  1000 线程 × 1MB = 1GB 虚拟内存
  线程过多 → 上下文切换开销（见第 3 节）
```

**JVM 相关线程的观察**：

```bash
jstack <pid> | grep "java.lang.Thread.State" | sort | uniq -c
# 统计线程状态分布（RUNNABLE/BLOCKED/WAITING 数量）
# 大量 WAITING → 线程池/连接池耗尽
# 大量 BLOCKED → 锁竞争
```

> 🎯 **核心要点**：线程数 = "**按类型定（CPU 密集核数+1 / IO 密集公式 / 虚拟线程不猜）**"——**线程栈内存与切换开销**是 JVM 侧的两个约束；虚拟线程（JDK 21+）大幅放松这两个约束。

## 2. GC 并发线程与 CPU 感知

**GC 并发线程数**（与 CPU 核数相关）：

```bash
-XX:ConcGCThreads=N       # 并发标记线程数（G1/ZGC）
-XX:ParallelGCThreads=N   # 并行 GC 线程数
# 默认：按 CPU 核数计算（ParallelGCThreads ≈ 核数 × 5/8）
```

**容器 CPU 感知问题（2026 关键）**：

```text
问题：JVM 默认按【宿主机】核数计算 GC 并发线程
  → 容器限 2 核，宿主机 64 核 → GC 开 40 个线程 → 线程争抢 + STW 拉长

解法：显式指定容器实际核数
  -XX:ActiveProcessorCount=2     # 容器配额（K8s limits.cpu）
  -XX:+UseContainerSupport       # 容器感知（默认开，确认即可）
  K8s 注入：downwardAPI 读 limits.cpu → JAVA_OPTS

验证：JFR 中 GC 线程数 / jcmd VM.flags 看 ActiveProcessorCount
```

```yaml
# K8s 注入 CPU 配额的示例（downwardAPI）
env:
  - name: CPU_LIMIT
    valueFrom:
      resourceFieldRef:
        resource: limits.cpu
  - name: JAVA_OPTS
    value: "-XX:ActiveProcessorCount=$(CPU_LIMIT)"
```

> 🎯 **核心要点**：CPU 感知 = "**容器里必须显式 ActiveProcessorCount**"——**默认按宿主机核数算 GC 线程是容器时代的经典坑**（STW 拉长、线程争抢）；K8s 用 downwardAPI 注入配额。

## 3. 锁竞争与上下文切换

**锁竞争对 JVM 的影响**：

```text
锁竞争 → BLOCKED 线程挂起 → 唤醒（两次上下文切换）
→ 频繁切换 → CPU 浪费（可达 10-30%）
→ 与 GC 停顿叠加 → 延迟恶化

观察：
  jstack 大量 BLOCKED → 锁竞争
  JFR 锁事件（Monitor）→ 锁热点定位（哪个锁最忙）
  vmstat：cs（context switch）列飙高 → 切换过多
```

**锁优化手段**（与 `Java多线程/07` 联动）：

| 手段 | 说明 |
|------|------|
| 缩小临界区 | 只锁共享操作 |
| 锁粒度细化 | 分段（ConcurrentHashMap 思路） |
| 读写分离 | ReadWriteLock/StampedLock |
| 无锁化 | CAS/原子类（冲突少时） |
| 减少共享 | 不可变/ThreadLocal |

```bash
# 切换观测
vmstat 1        # cs 列 = 每秒上下文切换
# 正常 < 数万；异常飙高 → 锁/线程数问题
```

> 🎯 **核心要点**：锁调优 = "**先观察（BLOCKED/锁事件/切换数）→ 再优化（粒度/分离/无锁）**"——**"上下文切换是锁竞争的隐藏成本"**（与 GC 停顿叠加放大延迟）；JFR 锁事件定位热点锁。

## 4. 线程池参数与 JVM 联动

**线程池与 JVM 的联动点**（调优时一起看）：

```text
① 线程池大小 → 线程栈内存（-Xss × 线程数）
② 队列积压 → 内存占用（无界队列 = OOM 风险）
③ 任务异常 → 线程泄漏（见 Java异常体系/07）
④ 拒绝策略 → 调用方阻塞（背压）

排查联动：
  接口变慢 + 大量 WAITING → 线程池队列积压
    → 外部依赖慢（超时）？池太小？任务阻塞？
  内存增长 + 任务堆积 → 无界队列 → 必须有界 + 拒绝策略
```

**线程池调优速查**：

| 参数 | 规范 |
|------|------|
| 核心/最大 | IO 密集可大、CPU 密集 = 核数+1（虚拟线程另说） |
| 队列 | **有界**（ArrayBlockingQueue）+ 明确拒绝策略 |
| 超时 | 任务内外部调用必须设超时（池耗尽头号元凶） |
| 监控 | 活跃线程/队列深度/拒绝次数（接入监控） |
| 关闭 | 优雅关闭（shutdown + awaitTermination） |

> 🎯 **核心要点**：线程池联动 = "**栈内存（-Xss）+ 队列内存（有界）+ 超时（防耗尽）**"——**"池耗尽 + 队列积压 = 外部依赖慢的放大器"**是线上最经典的事故链（详见 `Java异常体系/07` 与 `Java多线程/02`）。

## 5. 线程调优速查

**线程相关参数全表**：

| 参数 | 默认 | 作用 | 建议 |
|------|:----:|------|------|
| -Xss | 1MB | 线程栈 | 按线程数（512k-1m） |
| -XX:ActiveProcessorCount | 宿主机核数 | 容器 CPU 感知 | **容器必设** |
| -XX:ConcGCThreads | 按核数 | GC 并发线程 | 一般不动 |
| -XX:ParallelGCThreads | 核数×5/8 | GC 并行线程 | 一般不动 |
| -XX:+UseContainerSupport | on | 容器感知 | 确认开启 |

**线程问题排查速查**：

| 症状 | 工具 | 解法 |
|------|------|------|
| CPU 高 | top -Hp + jstack / Arthas thread -n | 热点/GC |
| BLOCKED 多 | jstack | 锁竞争（粒度/无锁） |
| WAITING 多 | jstack | 池耗尽（超时/队列） |
| 线程数暴涨 | jstack 计数 | 线程泄漏（任务不结束） |
| 切换飙高 | vmstat cs | 锁/线程数 |
| 容器内 GC 慢 | JFR GC 线程数 | ActiveProcessorCount |

> 🎯 **核心要点**：线程调优 = "**三参数（-Xss/ActiveProcessorCount/GC 线程）+ 六症状速查**"——**"容器 CPU 感知"是 2026 最高频考点**；线程问题与 GC 问题常交织（切换 × 停顿叠加），排查时一起看。

## 6. 线程调优速查卡

**线程数决策速查**：

```text
CPU 密集：核数 + 1（容器用 ActiveProcessorCount）
IO 密集：核数 × (1 + 等待/计算)（或虚拟线程）
虚拟线程（JDK 21+）：IO 密集每任务一个（不猜）

线程栈内存：-Xss × 线程数（1000 线程 × 1MB = 1GB 虚拟内存）
GC 线程：容器里按 ActiveProcessorCount（默认宿主机核数——坑）
```

**锁优化速查**（与 Java多线程/07 联动）：

```text
观察 → jstack BLOCKED 数量 / JFR 锁事件 / vmstat cs
优化 → 缩小临界区 → 锁粒度 → 读写分离 → 无锁（CAS）
红线 → 锁内不调外部代码（超时/死锁源）
```

**面试一句话**：

```text
"线程调优的关键是容器 CPU 感知——
 JVM 默认按宿主机核数算 GC 并发线程，
 容器里必须用 ActiveProcessorCount 修正；
 线程数按任务类型定，锁竞争用 JFR 定位热点再优化。"
```

> 🎯 **核心要点**：线程速查 = "**线程数（类型定）+ 栈内存（-Xss）+ 容器感知（ActiveProcessorCount）+ 锁优化链**"——**"容器 CPU 感知"是最高频考点**；一句话话术覆盖要点。
