## 1. 目标驱动：延迟 / 吞吐 / 内存三角

**调优前先回答"优化哪个目标"**——三个目标不可兼得：

| 目标 | 核心指标 | 手段 | 代价 |
|------|---------|------|------|
| **延迟** | P95/P99 停顿、GC 次数 | ZGC、小堆、低停顿配置 | -10-15% 吞吐 |
| **吞吐** | 每秒事务数、GC 总耗时占比 | Parallel、大堆、少 GC | 停顿更长 |
| **内存** | 堆使用率、OOM 次数 | 堆大小、压缩指针、对象优化 | 与吞吐/延迟权衡 |

```text
三角权衡示例：
  追求低延迟（P99 < 50ms）→ 分代 ZGC（停顿 <1ms，吞吐 -10-15%）
  追求吞吐（批处理）→ ParallelGC + 大堆（停顿秒级可接受）
  默认均衡 → G1（200ms 停顿目标，吞吐/延迟兼顾）

判断公式（面试必答）：
  "我们的 SLA 是 X ms 的 P99" → 有明确低延迟要求 → ZGC
  "我们是批处理/离线任务" → 吞吐优先 → Parallel
  "我们是 Web/微服务，无极端要求" → G1（默认即可）
```

> 🎯 **核心要点**：调优第一问 = "**目标是什么**"——没有目标就调优 = 无的放矢；**"先选对收集器（目标），再谈参数"**是 2026 共识（不要跨收集器复制参数）。

## 2. 调优五步流程

```text
① 建基线：先开 GC 日志 + JFR，运行代表性负载 30 分钟+
   → 记录：GC 次数/停顿/分配速率/晋升速率/live-set/GC CPU
② 定位瓶颈：数据 → 是停顿多？分配快？还是 Full GC？
   → 用数据定位"问题在哪"，不靠猜
③ 提出假设：瓶颈 → 假设（如"IHOP 太低导致提前并发标记"）
④ 实验验证：一次只改一个参数 → 同负载重测 → 对比基线
⑤ 决策：指标改善？→ 保留；无改善 → 回滚换假设

铁律：一次只改一个参数（多参数同时改 = 无法归因）
```

```bash
# ① 建基线的标准命令（2026 推荐）：
java -Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags \
     -XX:StartFlightRecording=filename=app.jfr,duration=30m \
     -jar app.jar
# 产出：gc.log（GC 事件）+ app.jfr（JFR 飞行记录）
```

**调优的"非目标"**（重要认知）：

```text
不为调优而调优：指标可接受（P95 < 100ms、无 OOM）→ 停止
调优有边际：多数系统默认 G1 已经够好，参数是锦上添花
升级优先：JDK 21+ 的 GC 改进常让"历史参数问题"自然消失
```

> 🎯 **核心要点**：调优流程 = "**基线 → 定位 → 假设 → 实验 → 决策**"五步——**"一次只改一个参数"是归因的前提**；"指标可接受就停"防止过度调优。

## 3. 基线：先测量再优化

**基线是调优的地基**——没有基线的调优是玄学：

| 基线指标 | 来源 | 含义 |
|---------|------|------|
| GC 次数与耗时 | gc.log | 停顿频率与总量 |
| P95/P99 暂停 | gc.log/JFR | 延迟体验 |
| 分配速率（MB/s） | JFR | 对象创建速度 |
| 晋升速率 | JFR | 进入老年代的速度 |
| live-set（存活集） | jmap -histo:live | 老年代真实需求 |
| GC CPU 占比 | JFR | 吞吐损耗 |

```text
基线的使用：
  分配速率高 → 优化对象创建（不是调 GC）
  晋升速率高 → 调整新生代大小/IHOP
  Full GC 频繁 → IHOP 或存活集问题
  P99 停顿高 → 收集器选型（ZGC）
→ 每个指标对应一类解法，基线数据直接指导参数选择
```

**错误示范**（面试反例）：

```text
❌ "我看网上说 -Xmx4g -XX:MaxGCPauseMillis=50 就配上了"
   （没建基线、参数照抄、目标未定义）
✅ "GC 日志显示 Full GC 每 5 分钟一次，IHOP 45% 提前触发
   并发标记 → 先降到 35% 观察"
   （数据 → 假设 → 实验）
```

> 🎯 **核心要点**：基线 = "**GC 日志 + JFR 的量化快照**"——**"每个指标对应一类解法"**是基线指导调优的关键；面试答"怎么调优"先说基线 = 方法论分。

## 4. "升级 JDK 优于堆参数"（2026 认知）

**2026 年最重要的调优认知：新版本 JVM 的算法改进 > 参数堆砌**：

| 版本 | GC/启动改进 | 调优意义 |
|:----:|------------|---------|
| JDK 21 | **分代 ZGC（ZGenerational）成熟** | 低延迟场景吞吐大幅提升 |
| JDK 24+ | G1 并发年轻代回收、NUMA 增强 | 大堆/多路服务器吞吐↑ |
| **JDK 25** | **AppCDS/AOT 缓存 GA（启动加速 30-50%）** | 零侵入启动优化 |
| JDK 26 | G1/ZGC 深度重构（增量重新标记等） | 尾延迟降 70%+（量级参考） |

```text
实践含义：
  ① 老项目在旧 JDK 上调一堆参数 → 先评估升级 JDK（收益常更大）
  ② 容器 + 新 JDK → 参数更简单（新 GC 默认已好）
  ③ 启动慢 → JDK 25 AppCDS（不换 GraalVM/CRaC 也能加速）
  ④ 升级路径：17 → 21（分代 ZGC）→ 25（AOT/新 GC）

注意：升级是"决策"不是"万能"——需兼容性评估（框架/依赖）
```

> 🎯 **核心要点**：**"升级优先"是 2026 调优的第一策略**——分代 ZGC（21）、AppCDS（25）、GC 重构（26）让"调参收益"小于"版本收益"；面试谈调优时先提升级 = 时效性加分。

## 5. 调优红线与反模式

| # | 反模式 | 表现 | 正确做法 |
|:-:|--------|------|---------|
| 1 | **无基线调参** | 照抄网上参数 | 先 GC 日志 + JFR |
| 2 | **多参数同时改** | 无法归因 | 一次一个 |
| 3 | **跨收集器复制参数** | G1 参数给 ZGC | 按收集器文档 |
| 4 | **追求零 GC** | 把堆调巨大 | GC 是正常的，优化频率而非消除 |
| 5 | **盲目最大堆** | -Xmx 设满机器内存 | 容器/off-heap 留余量（MaxRAMPercentage） |
| 6 | **调优无停止条件** | 无限调参 | 指标达标即停 |
| 7 | **忽略升级** | 旧 JDK 堆参数 | 先评估升级 |
| 8 | **只看平均** | 忽略 P99 | 长尾才是体验 |
| 9 | **生产直接改** | 无压测验证 | staging 同规格验证 |
| 10 | **改完不监控** | 无回归观察 | GC 指标持续监控 |

**调优红线总结**：

```text
① 没有基线不动手（数据驱动）
② 一次只改一个参数（可归因）
③ 目标达标即停（不过度）
④ 优先升级 JDK（版本收益）
⑤ 容器参数用百分比（MaxRAMPercentage）
```

> 🎯 **核心要点**：反模式总纲 = "**无数据、不归因、无停止、忘升级**"四类——十条清单与五条红线是调优纪律；**"先建基线"是第一纪律**（贯穿本体系）。

## 6. 方法论速查卡

**调优决策速查**（一张卡走天下）：

```text
问题 → 先建基线（GC 日志 + JFR 30 分钟）
→ 看指标：GC 频率/停顿分布/分配速率/晋升速率/live-set
→ 定位：停顿类型（Minor/Mixed/Full）→ 归因
→ 假设 → 单参数实验 → 对比基线 → 达标即停
→ 持续监控（回归观察）

红线五条：
  ① 没有基线不动手
  ② 一次只改一个参数
  ③ 目标达标即停
  ④ 优先升级 JDK
  ⑤ 容器参数用百分比
```

**"面试一句话方法论"**：

```text
"JVM 调优我遵循数据驱动流程：先开 GC 日志和 JFR 建基线，
 用数据定位瓶颈（停顿类型/分配速率），
 一次只改一个参数验证，指标达标即停；
 2026 年的经验是升级 JDK（分代 ZGC/AppCDS）往往比堆参数更有效。"
```

> 🎯 **核心要点**：方法论速查 = "**决策链（基线→定位→实验→停止）+ 红线五条 + 面试一句话**"——**能背一句话方法论** = 面试调优题的开场白；本卡是 01 模块的浓缩版（配合其他模块使用）。
