## 3. 为什么必须学透 JVM 调优

1. **生产事故第一现场**：OOM、GC 频繁、停顿、内存泄漏——JVM 调优是线上排障的必修技能，**"先开 GC 日志建基线"是任何调优的起点**。
2. **2026 容器环境的新陷阱**：cgroup 限制 <1792MB 时 JVM 回退 SerialGC、默认堆只有容器的 25%——**容器化时代 JVM 参数必须重写**（MaxRAMPercentage 替代 -Xmx）。
3. **面试高频且区分度明显**：GC 选型矩阵、G1 参数、OOM 排查流程、容器内存感知——"背参数"与"懂流程"一眼可见。
4. **升级红利大于调参**：JDK 21 分代 ZGC、JDK 25 AppCDS/AOT 缓存、JDK 26 GC 重构——**"升级 JDK 往往比堆参数更有效"**是 2026 的关键认知。
5. **与并发/容器/监控体系的交汇点**：线程调优、K8s 部署、监控告警——JVM 调优是知识体系的"汇聚点"。

## 4. 核心概念速查

### 4.1 调优三角

| 目标 | 指标 | 手段 |
|------|------|------|
| 延迟 | P95/P99 停顿、GC 次数 | ZGC/低停顿配置 |
| 吞吐 | 每秒事务数 | ParallelGC/大堆 |
| 内存 | 堆使用、OOM 次数 | 堆大小/压缩指针 |

**三者不可兼得**：低延迟（ZGC）≈ -10-15% 吞吐；大堆（吞吐）≈ 停顿更长。

### 4.2 2026 收集器速查

| 收集器 | 定位 | 停顿 | 适用 |
|--------|------|:----:|------|
| **G1** | **默认均衡** | ~200ms 目标 | 大多数 Web/微服务 |
| 分代 ZGC | 低延迟王者（JDK 21+） | <1ms | P99 <50ms 金融/交易 |
| Shenandoah | 低延迟备选 | <10ms | 中等堆（<32GB） |
| Parallel | 吞吐优先 | 长 | 批处理 |

### 4.3 容器关键参数（2026 必配）

```text
-XX:+UseContainerSupport          # 容器感知（默认开）
-XX:MaxRAMPercentage=50~75        # 替代静态 -Xmx（50 给 off-heap 留空间）
-XX:ActiveProcessorCount=N        # 修正 CPU 感知（容器配额）
-XX:+ExitOnOutOfMemoryError       # OOM 即退出（K8s 快速重启）
-XX:+AlwaysPreTouch               # 延迟敏感时预热内存
```

## 6. 学习路线推荐

**路线一：方法论与内存（1-2 天，模块 01-02）**
调优流程（基线→实验→验证）→ 内存参数——先建立"数据驱动"的调优观。

**路线二：GC 与工具（1 周，模块 03-04）**
选型矩阵 → G1/ZGC 参数 → 诊断工具实战（重点 jstat/jcmd/JFR）——**动手跑工具是核心**。

**路线三：排查与生产（模块 05-08）**
典型问题（OOM/GC 频繁）→ 线程 → 容器（MaxRAMPercentage）→ 面试冲刺。

## 7. 常见误区

| 误区 | 真相 |
|------|------|
| "调优就是堆参数" | **先建基线（GC 日志 + JFR）再动手**——数据驱动 |
| "-Xmx 越大越好" | 大堆 → 停顿长 + 压缩指针失效（>32GB）；按负载定 |
| "容器参数照搬物理机" | 容器是另一套：**MaxRAMPercentage + ActiveProcessorCount + 显式收集器** |
| "MaxRAMPercentage=100" | off-heap 无空间 → 容器 OOM——50-75% |
| "CMS 还能调" | CMS 已移除（JDK 14）——G1/ZGC 时代 |
| "追求零 GC" | GC 是正常的——优化频率而非消除 |
| "调参比升级有效" | **升级优先**（21 分代 ZGC/25 AppCDS/26 GC 重构） |
| "jmap -histo:live 随时用" | 触发 Full GC——生产慎用（用 jcmd） |
