## 1. 收集器选型矩阵（2026）

**2026 收集器格局**（G1 默认、CMS 已移除、分代 ZGC 成熟）：

| 收集器 | 停顿 | 吞吐 | 适用 | 版本状态 |
|--------|:----:|:----:|------|:-------:|
| **G1** | ~200ms 目标 | 均衡 | **大多数 Web/微服务（默认）** | ✅ 稳定 |
| **分代 ZGC** | **<1ms** | -10-15% | P99 <50ms 金融/交易/实时 | ✅ JDK 21+ 成熟 |
| Shenandoah | <10ms | 略低 | 中等堆（<32GB）低延迟 | ✅ |
| Parallel | 秒级 | **最高** | 批处理/离线 | ✅ |

**选型公式（面试必答）**：

```text
P99 延迟 SLA < 50ms 且堆 > 32GB → 分代 ZGC
中等堆（<32GB）+ 低延迟 → Shenandoah（或 ZGC）
吞吐优先（批处理）→ ParallelGC
默认（无极端要求）→ G1（不要动）

2026 共识：绝大多数项目 G1 默认即可；
"调参收益 < 升级收益"——JDK 21+ 的 GC 改进常让历史问题消失
```

> 🎯 **核心要点**：选型 = "**目标定收集器**"——**低延迟用 ZGC、吞吐用 Parallel、默认 G1**；CMS 已成历史（JDK 9 废弃/14 移除），面试别再提 CMS 调优。

## 2. G1 关键参数详解

**G1 的核心参数族**（2026 实践）：

| 参数 | 默认 | 作用 | 调优建议 |
|------|:----:|------|---------|
| -XX:MaxGCPauseMillis | 200 | 停顿目标 | 100-200ms 起步，**别设太低**（设低 → GC 更频繁） |
| -XX:InitiatingHeapOccupancyPercent | 45 | 并发标记触发阈值 | **Full GC 频繁 → 降到 30-35** |
| -XX:G1HeapRegionSize | 堆/2048 | Region 大小 | 仅 Humongous 问题时调 8m/16m |
| -XX:G1ReservePercent | 10 | 预留空间（防晋升失败） | 晋升失败 → 提到 15-25 |
| -XX:G1MixedGCCountTarget | 8 | 混合 GC 轮数 | 保持默认 |
| -XX:G1NewSizePercent | 5 | 新生代下限 | 默认即可 |

**G1 调优心法**：

```text
Full GC 频繁（最常见问题）→ 查 IHOP：
  IHOP 45% 提前触发并发标记 → 标记跟不上分配 → Full GC
  → 降 IHOP（30-35）让标记更早开始（给并发留时间）
  → 或降低晋升速率（调新生代）

停顿超目标 → 先确认是 Minor 还是 Mixed/Full：
  Minor 停顿高 → 新生代太大（G1NewSizePercent）
  Mixed 停顿高 → MixedGCCountTarget 或 Region 大小
  Full 停顿高 → 存活集大（live-set）→ 大对象/泄漏

Humongous（巨型对象）→ 见第 3 节（G1 头号坑）
```

> 🎯 **核心要点**：G1 参数记忆 = "**停顿目标（MaxPause）+ 标记阈值（IHOP）+ 预留（Reserve）**"三核心——**"Full GC 频繁先看 IHOP"**是最常见问题的第一反应。

## 3. Humongous 分配风暴：G1 的大坑

**Humongous（巨型对象）**：对象大小 > Region 一半（默认 Region ≈ 堆/2048，约 512KB-1MB）→ **直接进老年代且不压缩**：

```text
问题链：
  ① 大数组/大 List/大缓存 > Region 一半 → Humongous 区
  ② Humongous 区不参与混合回收（大对象整区分配）
  ③ 频繁分配大对象 → 老年代碎片 + 秒级 Full GC
  → "分配风暴"：停顿飙升、吞吐暴跌

触发示例：
  byte[] buf = new byte[10 * 1024 * 1024];   // 10MB 大数组（典型）
  频繁创建大 JSON/大缓存/大位图 → 风暴

解法：
  ① 控制大对象：对象池化复用（避免频繁创建）
  ② 调大 Region：G1HeapRegionSize=16m（让对象 < 一半 Region）
  ③ 代码层面：大缓存用堆外/磁盘/池化
  ④ 观察：GC 日志中 "Humongous" 标记出现频率
```

```bash
# 观察 Humongous（GC 日志）：
-Xlog:gc+region+humongous=debug
# 日志出现大量 humongous allocation → 确认问题
```

> 🎯 **核心要点**：Humongous = "**G1 的头号大坑**"——**大对象直接进老年代 + 不压缩 + 碎片化**；解法优先级 = **代码（池化）> Region（调大）**；面试答"G1 有哪些坑"先答 Humongous。

## 4. 分代 ZGC 与低延迟场景

**分代 ZGC（JDK 21+，-XX:+ZGenerational）**：低延迟场景的成熟方案：

```bash
# 启用（JDK 21+）
-XX:+UseZGC -XX:+ZGenerational     # 分代 ZGC（21 起默认分代）

# 关键参数
-XX:SoftMaxHeapSize=8g   # 软上限（容器环境极实用，降平均占用）
-XX:ConcGCThreads=N       # 并发线程数
-XX:ZUncommitDelay=300    # 内存归还延迟
```

**ZGC 的代价与预算**（面试必答）：

```text
收益：停顿 <1ms（与堆大小几乎无关）、P99 稳定
代价：
  ① 吞吐 -10-15%（并发收集的开销）
  ② 原生内存 +25%（着色指针/多映射）→ 容器内存预算 heap×1.25！
  ③ 压缩指针不可用（ZGC 用 4TB 地址空间）→ 引用 8 字节

适用判断（三条件）：
  ① P99 延迟 SLA < 50ms
  ② 堆 > 32GB（小堆 ZGC 收益不明显）
  ③ 能接受吞吐 -10-15% 与内存 +25%
```

**ZGC vs G1 的 2026 定位**：

| 维度 | G1 | 分代 ZGC |
|------|:--:|:--------:|
| 停顿 | ~200ms 目标 | <1ms |
| 吞吐 | 基准 | -10-15% |
| 内存 | 基准 | +25% |
| 适用 | 默认/均衡 | 严格低延迟 |
| 调优复杂度 | 中 | 低（参数少） |

> 🎯 **核心要点**：分代 ZGC = "**低延迟王者（JDK 21+ 成熟）**"——**"停顿 <1ms + 吞吐 -10-15% + 内存 +25%"**三个数字是面试必背；容器用 ZGC 必须按 heap×1.25 预算内存。

## 5. GC 日志与指标解读

**GC 日志是调优的"仪表盘"**（2026 标准命令）：

```bash
# 统一日志（JDK 9+）
-Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags
# 关键标签：gc / gc+heap / gc+ergo / gc+region+humongous

# JFR（现代首选——低开销、丰富事件）
-XX:StartFlightRecording=filename=app.jfr,duration=30m
# JFR 事件：GC 暂停、分配速率、晋升速率、live-set、GC CPU
```

**GC 日志解读要点**：

```text
从日志提取的核心指标：
  ① GC 频率（每 N 秒一次？）
  ② 停顿时长（P50/P95/P99）
  ③ 停顿类型分布（Minor/Mixed/Full）
  ④ 堆使用趋势（平稳/增长=泄漏）
  ⑤ 分配与晋升速率（JFR）

判读示例：
  "Full GC 每 5 分钟一次，堆 4g 只用到 60%" 
  → 标记跟不上（IHOP 提前）→ 降 IHOP 或调新生代
  "Mixed GC 停顿 500ms" 
  → 存活集大/Humongous → 查 live-set 与大对象
```

> 🎯 **核心要点**：GC 日志 = "**调优的数据源**"——**`-Xlog:gc*` + JFR 双采集**是 2026 基线标配；解读五指标（频率/停顿/类型/趋势/速率）覆盖 90% 的 GC 问题定位。

## 6. GC 调优决策链

**GC 问题 → 决策的完整链路**（面试/生产通用）：

```text
① 建基线：GC 日志 + JFR（30 分钟）
② 看停顿类型分布：
   Full GC 多 → IHOP 调低 / 检查泄漏（live-set 增长）
   Minor GC 多 → 新生代调大 / 优化分配速率
   Mixed GC 停顿高 → 存活集大 / Humongous
   P99 停顿仍高（参数调尽）→ 换收集器（ZGC）
③ 单参数实验 → 对比基线 → 达标即停
④ 持续监控：GC 指标接入 Prometheus（部署工具 09 联动）

红线提醒：
  调参不能掩盖代码问题（泄漏/大对象/分配风暴）
  升级 JDK 优先于堆参数（01 模块方法论）
```

**常见问题速查**：

| 症状 | 第一反应 |
|------|---------|
| Full GC 频繁 | IHOP 降到 30-35 / 查泄漏 |
| Minor GC 频繁 | 新生代调大 / 优化对象创建 |
| 停顿超目标 | 先分类型（Minor/Mixed/Full）再调 |
| Humongous 日志多 | 大对象池化 / Region 调大 |
| 堆涨不回落 | 泄漏（转储分析，见 02 模块） |
| 参数调尽仍慢 | 换 ZGC / 升级 JDK |

> 🎯 **核心要点**：GC 调优决策链 = "**基线 → 类型分布 → 对症参数 → 验证 → 监控**"——**"先分停顿类型再调参"**避免乱调；红线 = 参数不能掩盖代码问题、升级优先于堆参数。
