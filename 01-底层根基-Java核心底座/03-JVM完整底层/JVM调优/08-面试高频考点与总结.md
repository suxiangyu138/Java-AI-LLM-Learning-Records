## 1. 必背考点：十二问

### 1.1 调优的第一步是什么？

**答题链**：**建基线（GC 日志 + JFR）** → 定位瓶颈（数据说话）→ 假设 → 实验（**一次只改一个参数**）→ 决策 → **"没有基线不动手"是第一纪律**（01 模块方法论）。

### 1.2 GC 收集器怎么选？

**答题链**：目标定收集器——**P99 <50ms 低延迟 → 分代 ZGC（JDK 21+）**、吞吐优先 → Parallel、默认 → G1 → 2026 认知：**"调参收益 < 升级收益"**（21 分代 ZGC/25 AppCDS/26 GC 重构）。

### 1.3 G1 的关键参数？

**答题链**：**MaxGCPauseMillis（停顿目标 100-200ms，别设太低）+ IHOP（45%，Full GC 频繁降到 30-35）+ G1ReservePercent（10→15-25 防晋升失败）** → 调优心法："Full GC 频繁先看 IHOP"。

### 1.4 Humongous 是什么？

**答题链**：**对象 > Region 一半 → 直接进老年代且不压缩** → 碎片化 + 秒级 Full GC（分配风暴）→ 解法：**代码（池化）> Region 调大** → G1 头号大坑。

### 1.5 分代 ZGC 的三个数字？

**答题链**：**停顿 <1ms（与堆大小无关）+ 吞吐 -10-15% + 原生内存 +25%** → JDK 21 成熟（ZGenerational）→ 容器预算 heap×1.25 → 适用：P99 <50ms + 堆 >32GB。

### 1.6 容器 JVM 的两大陷阱？

**答题链**：**<1792MB 回退 SerialGC（显式 UseG1GC）+ 默认堆 25%（MaxRAMPercentage）** → CPU 感知（ActiveProcessorCount）→ 完整模板六参数（07 模块）。

### 1.7 MaxRAMPercentage 为什么不用 -Xmx？

**答题链**：容器自适应（按限制百分比）vs 写死 → **50-75%（别 100%，off-heap 需空间）** → 注入 JDK_JAVA_OPTIONS。

### 1.8 OOM 四类？

**答题链**：**heap space（堆）/ Metaspace（元空间）/ unable to create native thread（栈线程）/ Direct buffer memory（直接内存）** → 异常名直接定位区域 → 先留现场（HeapDumpOnOOM）再分析。

### 1.9 内存泄漏五步？

**答题链**：**确认趋势（持续增长=泄漏）→ 双转储 → MAT 分析（Histogram/Dominator）→ 引用链（谁持有）→ 修复验证** → 四经典模式（静态集合/ThreadLocal/监听器/类加载器）。

### 1.10 jstat 怎么用？

**答题链**：`jstat -gcutil`（S/E/O/M + YGC/FGC）→ 判读："E 快满 O 平稳 = 分配问题；O 高位 FGC 多 = 老年代问题"。

### 1.11 JFR 是什么？

**答题链**：**飞行记录（黑匣子，<2% 开销）** → 常开（事故后分析）→ 事件：GC 暂停/分配速率/晋升/live-set/锁竞争 → 现代诊断首选。

### 1.12 AppCDS 是什么？

**答题链**：**类数据共享归档 → 启动加速 30-50%（JDK 25 GA）** → 零侵入（-javaagent 兼容）→ 三步生成（ArchiveClassesAtExit → SharedArchiveFile）→ 优于 CRaC/GraalVM（运维友好）。

## 2. 高频陷阱题 12 连问

1. **对错**：容器限制 <1792MB 时 JVM 用 G1。（❌ 回退 SerialGC——需显式 UseG1GC）
2. **对错**：MaxRAMPercentage=100 充分利用容器内存。（❌ off-heap 无空间 → 容器 OOM）
3. **结果**：`-Xmx4g` 在容器扩缩容时的表现？（不匹配——写死 vs 容器限制变化）
4. **对错**：G1 的 MaxGCPauseMillis 设 20ms 更好。（❌ 设太低 → GC 更频繁，100-200ms 起步）
5. **结果**：Full GC 频繁的第一反应？（查 IHOP（45% 是否提前触发）→ 降 30-35）
6. **对错**：Humongous 对象参与混合回收。（❌ 不压缩不参与——整区分配）
7. **结果**：ZGC 的容器内存预算？（heap×1.25——原生 +25%）
8. **对错**：jmap -histo:live 生产随时可用。（⚠️ 触发 Full GC——慎用）
9. **结果**：OOM 前没配转储参数？（无现场——HeapDumpOnOOM 必须提前配）
10. **对错**：jstack 能自动检测死锁。（✅ "Found one Java-level deadlock"）
11. **结果**：泄漏和容量不足怎么区分？（持续增长=泄漏；平稳峰值=容量）
12. **对错**：JDK 25 启动加速必须用 GraalVM。（❌ AppCDS GA——零侵入 30-50%）

## 3. 高频追问速答

| 追问 | 速答 |
|------|------|
| 调优为什么一次只改一个参数？ | 可归因（多参数同时改无法定位哪个生效） |
| 升级 JDK 和调参哪个优先？ | **升级优先**（21 分代 ZGC/25 AppCDS/26 GC 重构收益常大于参数） |
| 大堆（>32GB）注意什么？ | 压缩指针失效（引用 8 字节）+ 停顿变长 → 考虑 ZGC |
| 分配速率高怎么办？ | 优化对象创建（复用/去重）——分配是因、堆大小是果 |
| 元空间溢出常见原因？ | 动态类（CGLIB/热部署）+ 类加载器泄漏 |
| thread -b 是什么？ | Arthas 找阻塞线程（死锁） |
| 上下文切换怎么观察？ | vmstat cs 列（异常飙高 → 锁/线程数问题） |
| 容器 CPU 感知？ | ActiveProcessorCount（默认按宿主机核数——坑） |
| JFR 开销多大？ | <2%——常开无压力（黑匣子） |
| 老年代高位平稳正常吗？ | 正常（容量充足）；高位 + FGC 频繁 = 问题 |

## 4. 场景题：OOM 排查流程

**题目**：线上服务频繁 OOM（Java heap space），怎么排查？

**答题框架**（按评分点展开）：

```text
① 留现场（如果已发生）：
   - 检查 HeapDumpOnOOM 是否配置（没有 → 这次只能靠日志推断，并立即补配）
② 确认是泄漏还是容量：
   - jstat -gcutil 观察趋势：持续增长 = 泄漏；平稳峰值 = 容量
   - JFR 分配/晋升事件（若常开）
③ 抓转储（泄漏方向）：
   - jcmd <pid> GC.heap_dump heap.hprof（生产安全）
   - 建议连抓两次（间隔几分钟）→ 对比增量对象
④ MAT 分析：
   - Histogram → 找增长对象（byte[]/集合/业务对象）
   - Dominator Tree → 谁占内存
   - Leak Suspects → 泄漏嫌疑报告
⑤ 引用链定位：
   - GC Roots → 嫌疑对象路径 → "谁持有"（static Map/ThreadLocal/缓存）
⑥ 修复与验证：
   - 修代码（清理/复用）→ 同负载复测 → 趋势回落确认
⑦ 加分点：
   - 谈"调大堆只是拖延"（泄漏必须修根因）
   - 谈容量场景的调堆规范（Xms=Xmx + 容器 MaxRAMPercentage）
   - 谈预防三件套（转储/JFR/GC 日志提前配好）
```

## 6. 记忆口诀

```text
调优五步：基线、定位、假设、实验、决策——一次只改一个。
收集器三选：G1 默认、ZGC 低延迟（<1ms）、Parallel 吞吐。
G1 三参数：Pause 目标、IHOP 标记、Reserve 预留。
Humongous 大坑：大对象进老年代不压缩——池化优先。
容器两陷阱：1792 回退 Serial、堆只 25%——G1 + MaxRAM。
MaxRAM 三值：50 稳妥、60 通用、75 激进——别 100。
OOM 四类：堆、元空间、线程、直接内存——异常名定位。
泄漏五步：趋势、转储、MAT、引用链、修复。
工具六把：jstat 快看、jcmd 综合、JFR 黑匣、Arthas 线上。
升级优先：21 分代 ZGC、25 AppCDS——版本收益 > 参数。
```
