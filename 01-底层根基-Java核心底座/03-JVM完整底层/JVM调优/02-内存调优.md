## 1. 内存全景：四个区域

**JVM 内存的四大去向**（调优先分清）：

| 区域 | 默认 | 主要参数 | 溢出表现 |
|------|:----:|---------|---------|
| **堆** | 物理内存 25% | -Xms/-Xmx | `OutOfMemoryError: Java heap space` |
| **元空间** | 无上限（本机内存） | -XX:MaxMetaspaceSize | `Metaspace` |
| **线程栈** | 1MB/线程 | -Xss | `unable to create native thread` |
| **直接内存** | 与堆相近 | -XX:MaxDirectMemorySize | `Direct buffer memory` |

```text
调优思维：先回答"内存被谁占了"再调——
  jmap -heap（堆）/ jcmd VM.native_memory（原生内存）
  → 数据决定调哪个区域
```

> 🎯 **核心要点**：内存调优的起点 = "**四个区域分清**"——**OOM 的异常名直接告诉你哪个区域**（heap space / Metaspace / native thread / Direct buffer memory）。

## 2. 堆参数详解

```bash
# 堆参数族
-Xms512m        # 初始堆（启动即分配）
-Xmx4g          # 最大堆
-Xmn1g          # 新生代大小（G1 用 NewSize/MaxNewSize）
-XX:NewRatio=2  # 老年代:新生代 = 2:1（默认）
-XX:SurvivorRatio=8  # Eden:Survivor = 8:1
-XX:MaxTenuringThreshold=15  # 晋升年龄阈值
```

**核心实践**：

```text
① -Xms = -Xmx（生产规范）：
   → 避免动态扩容/缩容抖动（扩容是 STW 操作）
   → 启动即到位，吞吐稳定
② 新生代大小（-Xmn）：
   → 太小：对象频繁晋升老年代 → Full GC 多
   → 太大：老年代变小 → 老年代 GC 频繁
   → 经验：新生代 = 堆的 1/3 ~ 1/4 起步，按晋升速率调整
③ 大堆注意：
   → 堆 > 32GB：压缩指针失效（对象引用 8 字节）→ 内存膨胀
   → 堆 > 32GB 且低延迟 → 考虑 ZGC（不是加大堆）
```

**对象创建的调优视角**（分配速率优先于堆大小）：

```text
分配速率高（MB/s 大）→ 即使堆大也会频繁 Minor GC
  → 优化代码：对象复用、String 去重、避免装箱
  → -XX:+UseStringDeduplication（字符串去重，2026 推荐）
分配是"因"，堆大小是"果"——先看分配速率再调堆
```

> 🎯 **核心要点**：堆调优 = "**Xms=Xmx（规范）+ 新生代按晋升速率调 + 大堆注意压缩指针**"——**"分配速率是因、堆大小是果"**：对象创建太快，堆再大也白搭。

## 3. 元空间与类加载

**元空间（Metaspace）**：类元数据（JDK 8 起取代永久代）——**默认无上限**（用本机内存）：

```text
元空间调优：
  -XX:MaxMetaspaceSize=512m   # 设上限（防失控）
  -XX:MetaspaceSize=256m      # 初始水位（触发扩容阈值）
  -XX:+PrintGCDetails（旧）/ -Xlog:gc+metaspace

元空间溢出的常见原因：
  ① 动态生成类（CGLIB 代理/反射/热部署）失控
  ② 类加载器泄漏（每次部署新 classloader 不回收）
  ③ Groovy/脚本引擎频繁编译

排查：jcmd <pid> GC.class_histogram → 看类加载器统计
```

**类加载器泄漏的经典场景**（与 Spring 热部署/插件系统相关）：

```text
症状：Metaspace OOM + 重启后恢复
根因：自定义 ClassLoader 被引用（如 ThreadLocal 持有）
→ 老类加载器无法 GC → 元空间持续增长
解法：找到持 ClassLoader 的引用（jmap + MAT 分析）
```

> 🎯 **核心要点**：元空间 = "**类元数据 + 默认无上限**"——**必须设 MaxMetaspaceSize 防失控**；溢出排查方向 = 动态生成类 / 类加载器泄漏（热部署重灾区）。

## 4. 线程栈与直接内存

**线程栈（-Xss，默认 1MB）**：

```text
-Xss512k    # 栈大小（默认 1MB）
栈溢出：StackOverflowError（递归无出口）/ unable to create native thread

线程数 × 栈大小 = 线程内存总量：
  1000 线程 × 1MB = 1GB 虚拟内存（栈是虚拟内存，实际按使用）
  调小 -Xss 可支撑更多线程（虚拟线程时代此约束减弱）

"unable to create native thread" 的排查：
  ① 线程数超限（ulimit -u / 容器限制）
  ② 栈内存耗尽（-Xss 过大 × 线程过多）
  ③ 进程数/内存限制（容器 cgroup）
```

**直接内存（Direct Memory）**——NIO/Netty 的堆外缓冲区：

```text
-XX:MaxDirectMemorySize=1g   # 直接内存上限（默认约等于堆大小）
堆外内存特征：堆不大但 RSS 持续增长

排查：jcmd <pid> VM.native_memory → 看 arena/code/thread 分布
经典场景：Netty 缓冲区泄漏（ByteBuf 未释放）
```

> 🎯 **核心要点**：栈与直接内存 = "**易被忽略的两个区域**"——**"unable to create native thread"是栈/线程数问题**、**堆外内存增长是直接内存问题**；`jcmd VM.native_memory` 是原生内存排查的利器。

## 5. 内存泄漏定位思路

**内存泄漏（Memory Leak）的五步定位法**（面试标准流程）：

```text
① 确认泄漏：RSS/堆持续增长不回落（多次采样对比）
   → jstat -gcutil（堆使用趋势）
② 抓堆转储：jmap -dump:format=b,file=heap.hprof <pid>
   → 生产用 jcmd GC.heap_dump（JDK 8+，同能力）
③ 分析转储：MAT / JProfiler / Eclipse Memory Analyzer
   → 找大对象、Dominator Tree（支配树）、泄漏嫌疑
④ 定位引用链：GC Roots 到嫌疑对象的路径
   → 谁持有它不让回收（如 static Map / ThreadLocal）
⑤ 修复与验证：修代码 → 同负载复测 → 确认趋势回落
```

```bash
# 关键命令
jstat -gcutil <pid> 1000 20      # 堆使用趋势（确认增长）
jcmd <pid> GC.heap_dump heap.hprof   # 堆转储（生产安全）
jmap -histo:live <pid> | head     # 存活对象统计（快速嫌疑）
```

**泄漏 vs 内存不足**（重要区分）：

```text
内存不足（容量）：负载高 + 堆小 → 调大堆即可
内存泄漏（代码）：对象不可达但被引用 → 调大堆只是拖延
判断：堆持续增长不回落 = 泄漏；平稳但峰值高 = 容量
```

> 🎯 **核心要点**：泄漏定位五步 = "**确认（趋势）→ 转储 → 分析（MAT）→ 引用链 → 修复验证**"——**"持续增长 = 泄漏、平稳峰值 = 容量"**是第一步判断；生产转储用 jcmd（比 jmap 更安全）。

## 6. 参数速查表

**内存相关参数全表**（调优/面试速查）：

| 参数 | 默认 | 作用 | 生产建议 |
|------|:----:|------|---------|
| -Xms | 物理 1/64 | 初始堆 | **= -Xmx** |
| -Xmx | 物理 1/4 | 最大堆 | 按负载/容器 |
| -Xmn | — | 新生代 | 堆的 1/3~1/4 |
| -XX:SurvivorRatio | 8 | Eden:Survivor | 保持默认起步 |
| -XX:MaxMetaspaceSize | 无上限 | 元空间上限 | **必设**（如 512m） |
| -Xss | 1MB | 线程栈 | 512k-1m（按线程数） |
| -XX:MaxDirectMemorySize | 堆大小 | 直接内存 | 按 NIO 使用 |
| -XX:+UseStringDeduplication | off | 字符串去重 | 2026 推荐开 |
| -XX:+AlwaysPreTouch | off | 启动预占物理内存 | 延迟敏感时 |
| -XX:+ExitOnOutOfMemoryError | off | OOM 即退出 | 容器环境推荐 |

**内存调优决策链**：

```text
OOM？→ 看异常名定位区域 → 堆问题看分配速率 vs 容量
  → 泄漏（趋势增长）→ 转储分析
  → 容量（平稳峰值）→ 调堆（Xms=Xmx）
堆外问题 → VM.native_memory → 直接内存/类加载器
```

> 🎯 **核心要点**：参数速查 = "**十参数一表 + 决策链**"——**Xms=Xmx、MaxMetaspaceSize 必设、ExitOnOOM 容器推荐**三条是最常用的生产规范；决策链让排查有路径可循。
