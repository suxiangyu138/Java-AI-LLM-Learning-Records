## 1. 编译模式：解释执行 + JIT编译 + AOT编译

### 1.1 三种编译模式总览

JVM采用**混合执行架构**，根据阶段与场景选择不同的编译策略：

```text
Java源码 (.java) ──javac──→ .class字节码（平台无关）
                                  │
                    ┌─────────────┼─────────────┐
                    ▼             ▼             ▼
              解释执行         JIT编译        AOT编译
          逐条翻译字节码    热点代码触发    打包阶段预编译
          启动快/性能低    动态优化/高性   零编译CPU损耗
                              能           极速冷启动
                    │             │             │
                    └─────────────┼─────────────┘
                                  ▼
                          本地机器码执行
```

| 编译模式 | 时机 | 优点 | 缺点 | 适用场景 |
|----------|------|------|------|----------|
| **解释执行** | 运行时逐条翻译 | 启动快，不占内存 | 运行性能低（约原生1/10） | 启动阶段、低频方法 |
| **JIT即时编译** | 运行时触发编译 | 运行性能高，动态优化 | 冷启动有编译开销，编译卡顿 | 长驻后端服务、高并发接口 |
| **AOT提前编译** | 打包阶段预编译 | 极速冷启动，零编译CPU损耗 | 打包慢，绑定CPU架构 | Serverless、网关、边缘计算 |

> 💡 **JDK11+支持JIT+AOT混合模式**：轻量逻辑用AOT预编译，高频热点交由JIT持续优化，兼顾冷启动与稳态性能。

### 1.2 JIT完整工作流程

```text
┌──────────────────────────────────────────────────────────────┐
│                     JIT 编译流程                              │
│                                                              │
│  .class字节码                                                │
│      │                                                       │
│      ▼                                                       │
│  ┌──────────┐    ┌──────────────┐    ┌──────────────────┐   │
│  │ 热点探测  │───→│ 编译器决策   │───→│ 机器码 → CodeCache│   │
│  │ 计数器统计 │    │ C1/C2/Graal │    │ 缓存复用         │   │
│  └──────────┘    └──────────────┘    └──────────────────┘   │
│       │                                                       │
│       ▼                                                       │
│  [触发条件]                           [优化技术]              │
│  方法调用计数器 > CompileThreshold    ├── 方法内联（最高优先级）│
│  或回边计数器 > OSR阈值              ├── 逃逸分析 + 标量替换  │
│                                       ├── 循环展开 / 向量化   │
│                                       ├── 去虚拟化 / 类型预测 │
│                                       └── 锁消除 / 锁粗化     │
└──────────────────────────────────────────────────────────────┘
```

> ⚠️ **关键风险点**：
> - 探测过早：大量低频无效代码触发编译，浪费CPU；
> - 探测过晚：核心接口长期解释执行，QPS升高后延迟飙升；
> - CodeCache占满：缓存被GC清空，已编译代码需重新编译，CPU持续拉高。

## 2. 热点探测：方法调用计数器 + 回边计数器

HotSpot通过两种计数器识别热点代码，决定是否触发JIT编译：

```text
方法调用计数器                   回边计数器（OSR编译）
┌──────────────────┐          ┌──────────────────────┐
│ 记录方法被调用次数 │          │ 记录循环体执行次数    │
│ 阈值：CompileThreshold │      │ 触发栈上替换（OSR） │
│ 默认10000          │          │ 允许循环体执行中     │
│ 半衰期衰减        │          │ 直接替换为机器码     │
└──────────────────┘          └──────────────────────┘

执行流程：
方法被调用 → 计数器+1
    ├── > CompileThreshold → 提交编译请求（标准编译）
    └── 否则 → 继续解释执行

循环迭代 → 回边计数器+1
    ├── > OSR阈值 → 触发OSR编译
    └── 否则 → 继续解释执行

热度衰减（超时不编译） → 计数器减半
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `-XX:CompileThreshold` | 10000 | 方法调用计数器阈值 |
| `-XX:OnStackReplacePercentage` | 140（C2） | OSR触发比率 |
| `-XX:CounterHalfLifeTime` | 自动 | 计数器半衰期时间 |
| `-XX:-UseCounterDecay` | 开启 | 关闭热度衰减（性能测试时使用） |

> 🎯 **调优建议**：流量稳定的核心服务可适当降低CompileThreshold，让热点代码更快被编译为机器码；但阈值过低会导致大量非热点方法也触发编译，浪费CPU。

## 3. 分层编译：C1（Client）→ C2（Server）→ Graal

### 3.1 分层编译机制

JDK6起引入分层编译（Tiered Compilation），将编译过程分为5个层级：

| 层级 | 编译级别 | 说明 |
|:----:|----------|------|
| 0 | 解释执行 | 启动阶段，无编译开销 |
| 1 | C1简单编译 | 基础优化（内联、常量传播），无profiling |
| 2 | C1有限profiling | 收集部分运行时信息 |
| 3 | C1完整profiling | 收集全部运行时信息，用于C2/Graal决策 |
| 4 | C2/Graal终极编译 | 基于profiling数据做激进优化 |

```text
启动（Level 0）
    │
    ▼
C1简单编译（Level 1）←──────────────┐
    │                                 │
    ▼                                 │
C1完整profiling（Level 3）            │
    │                                 │
    ▼                                 │
C2/Graal编译（Level 4）── 达到阈值 ──┘
         │
         └── 若优化失败，回退到Level 1/3
```

### 3.2 C1 vs C2 vs Graal 对比

| 维度 | C1（Client Compiler） | C2（Server Compiler） | Graal Compiler |
|------|----------------------|----------------------|----------------|
| **目标** | 快速编译，启动快 | 极致优化，稳态性能高 | 兼具编译速度与优化质量 |
| **编译速度** | 快（秒级） | 慢（分钟级） | 中等（比C2快30%） |
| **优化激进程度** | 低（基础内联、常量折叠） | 高（逃逸分析、向量化、循环变换） | 高（增强逃逸分析、部分Escape） |
| **Profiling依赖** | 低 / 无 | 强依赖完整profiling | 依赖profiling，支持推测优化 |
| **默认使用** | JDK6-8客户端模式 | JDK6-8服务端模式 | JDK17+替代C2作为服务编译器 |
| **适用场景** | 桌面应用、短任务 | 长驻服务端应用 | 微服务、低延迟业务、云原生 |
| **内存消耗** | 低 | 高 | 中等 |
| **支持AOT** | 否 | 否 | 是（GraalVM Native Image） |

### 3.3 各JDK版本编译器演进

| JDK版本 | 默认编译器 | 核心变化 |
|---------|-----------|----------|
| JDK6 | C1（-client）/ C2（-server） | 引入分层编译（实验） |
| JDK8 | C1 + C2（分层编译默认开启） | 无原生AOT |
| JDK11 | C1 + C2，Graal实验特性 | jaotc AOT工具、字符串去重 |
| JDK17（LTS） | Graal替代C2作为服务编译器 | 编译速度提升30%，稳定AOT |
| JDK21+ | Graal + Project Leyden | 虚拟线程协同编译、分代ZGC、强化AOT |

> 💡 **升级建议**：新项目优先使用JDK17/21，默认Graal编译器性能显著优于老旧C2；老项目从JDK8升级到JDK11过渡时需测试编译器行为变化。

## 4. 方法内联（Method Inlining）

### 4.1 内联原理

方法内联是JIT **优先级最高**的优化技术，将高频小方法的调用指令替换为方法体本身，消除栈帧创建/销毁开销。

```text
调用前：                         调用后（内联后）：
caller() {                       caller() {
  int a = 1;                       int a = 1;
  int b = add(a);  ──→ add()      int b = a + 2;   ← 内联展开
}                                }
```

### 4.2 内联判定条件

| 判定因素 | 条件 | 说明 |
|----------|------|------|
| **方法大小** | `-XX:MaxInlineSize` 默认35字节 | 超过此限制不内联 |
| **调用频率** | `-XX:InlineFrequency` | 高频调用优先内联 |
| **方法热度** | 编译层级≥3 | 低热方法不触发内联 |
| **分支复杂度** | 过多条件分支 | 分支复杂拒绝内联 |
| **接口调用** | 单实现类 → 去虚拟化内联 | 多态调用需类型预测 |

| 参数 | 默认值 | 作用 |
|------|--------|------|
| `-XX:MaxInlineSize` | 35 | 内联方法最大字节码大小 |
| `-XX:InlineSmallCode` | 1000 | C2内联阈值（编译后机器码大小） |
| `-XX:FreqInlineSize` | 325 | 热点方法内联大小上限 |
| `-XX:+PrintInlining` | 关闭 | 打印内联决策详情 |

> 💡 **编写规范**：
> - 核心接口逻辑拆分为**100行内的小方法**（getter/setter天然适合内联）；
> - 避免上千行的巨型业务方法，分支过多会拒绝内联；
> - 频繁调用的`private`方法比`public`方法更容易内联（不受多态影响）。

## 5. 逃逸分析与标量替换

### 5.1 逃逸分析原理

逃逸分析判断对象的作用域是否逃出当前方法/线程：

| 逃逸状态 | 说明 | JIT优化 |
|----------|------|---------|
| **不逃逸** | 对象仅在方法内使用，未赋值给全局变量或返回 | 栈上分配 + 标量替换 |
| **方法逃逸** | 对象作为方法返回值或参数传递到外部 | 锁消除（若未发生线程竞争） |
| **线程逃逸** | 对象被赋值给全局变量或跨线程访问 | 无优化（必须堆分配） |

### 5.2 代码演示：逃逸分析触发标量替换

```java
/**
 * 逃逸分析 + 标量替换演示
 * 参数：-XX:+DoEscapeAnalysis -XX:+EliminateAllocations
 */
public class EscapeAnalysisDemo {

    // ❌ 对象返回调用方 → 方法逃逸，堆分配
    public Point createPoint(int x, int y) {
        return new Point(x, y);
    }

    // ✅ 对象仅在循环内使用 → 不逃逸，触发标量替换
    public long sum(int iterations) {
        long total = 0L;
        for (int i = 0; i < iterations; i++) {
            Point p = new Point(i, i + 1);
            total += p.getX() + p.getY();
        }
        return total;
    }

    // ⚠️ 对象存入外部数组 → 逃逸
    public void fillArray(Point[] arr) {
        for (int i = 0; i < arr.length; i++) {
            arr[i] = new Point(i, i);
        }
    }
}

class Point {
    private int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    int getX() { return x; }
    int getY() { return y; }
}
```

### 5.3 标量替换原理

逃逸分析后，JIT将不逃逸对象的字段拆解为独立标量变量：

```text
【原始代码】                         【标量替换后等价】
Point p = new Point(3, 5);          int x = 3;       // 栈上局部变量
int sum = p.x + p.y;                int y = 5;       // 栈上局部变量
                                    int sum = x + y; // 无对象创建，无GC
```

| 优化收益 | 说明 |
|----------|------|
| **减少堆分配** | 对象避免在堆上创建，降低GC频率 |
| **缓存友好** | 栈上数据局部性更好，CPU缓存命中率提升 |
| **零GC停顿** | 栈上分配的对象随栈帧销毁自动回收 |

| 参数 | 默认值 | 作用 |
|------|--------|------|
| `-XX:+DoEscapeAnalysis` | 开启 | 开启逃逸分析 |
| `-XX:+EliminateAllocations` | 开启 | 开启标量替换（基于逃逸分析） |
| `-XX:+EliminateLocks` | 开启 | 开启锁消除（基于逃逸分析） |
| `-XX:MaxEscapeAnalysisRecursionDepth` | 6 | 逃逸分析最大递归深度 |

> ⚠️ **逃逸分析避坑**：
> - 循环内创建对象并返回 → **破坏逃逸分析**，对象必须在堆分配；
> - 跨方法传递实体类 → 方法逃逸，标量替换失效；
> - 反射/动态代理创建的对象 → 逃逸分析无法判断，回退到堆分配。

## 6. 锁消除与锁粗化

### 6.1 锁消除（Lock Elimination）

JVM通过逃逸分析检测到锁对象**仅在当前线程内使用**时，自动消除锁操作。例如局部变量的`synchronized(lock)`会被JVM消除，因为lock不逃逸、无多线程竞争；实例字段的`lock`则无法消除。

### 6.2 锁粗化（Lock Coarsening）

JVM检测到**连续的锁操作**（如循环中反复加解锁），自动合并为单个锁，减少获取/释放次数。建议手动粗化以降低编译器负担。

### 6.3 锁优化总结

| 优化技术 | 触发条件 | JVM参数 | 开发影响 |
|----------|----------|---------|----------|
| **锁消除** | 锁对象不逃逸，无竞争 | `-XX:+EliminateLocks` | 局部变量加锁会被消除 |
| **锁粗化** | 连续加解锁操作 | 自动 | 循环内小操作建议手动粗化 |
| **偏向锁** | 单线程反复获取同一锁 | `-XX:+UseBiasedLocking` | 无竞争场景性能最优 |
| **轻量级锁** | 多线程交替获取锁 | CAS自旋 | 避免线程阻塞 |
| **重量级锁** | 多线程同时竞争 | Monitor | 高竞争场景兜底 |

> 🎯 **最佳实践**：
> - 非共享资源不要加锁，给JVM锁消除创造条件；
> - 循环内需要同步时，将整个循环体加锁（手动粗化），而不是在循环内反复加解锁；
> - 简单同步场景优先使用`synchronized`，JVM自动做锁升级优化。

## 7. AOT编译：jaotc与GraalVM Native Image

### 7.1 AOT vs JIT 对比

| 维度 | JIT即时编译 | AOT提前编译 |
|------|------------|------------|
| **编译时机** | 运行期动态编译 | 构建期预编译 |
| **跨平台性** | 字节码跨平台 | 机器码绑定CPU架构 |
| **冷启动速度** | 慢（需预热） | 快（直接执行机器码） |
| **稳态性能** | 高（动态优化） | 中（无运行时profiling） |
| **镜像体积** | 小（JRE+字节码） | 大（包含运行时） |
| **反射/动态代理** | 支持 | 受限（需配置反射） |
| **适用场景** | 常驻后端服务 | Serverless、CLI工具、边缘计算 |

### 7.2 jaotc（JDK9+，JDK17不推荐）

```bash
jaotc --output libjava.base.so --module java.base
java -XX:AOTLibrary=./libjava.base.so -jar myapp.jar
```

> ⚠️ jaotc在JDK17中已不再推荐使用，GraalVM Native Image是替代方案。

### 7.3 GraalVM Native Image

```bash
# GraalVM原生编译
native-image -jar myapp.jar --no-fallback myapp
./myapp -Xmx64m -Xms64m   # 直接运行，无JVM
```

**Spring Boot 3 + GraalVM：**

```xml
<plugin>
    <groupId>org.graalvm.buildtools</groupId>
    <artifactId>native-maven-plugin</artifactId>
</plugin>
```

```bash
mvn -Pnative native:compile
./target/myapp
```

| 指标 | 传统JVM | Native Image |
|------|---------|-------------|
| 启动时间 | ~5s（含JIT预热） | <0.1s |
| 内存占用 | ~200MB | ~30MB |
| 镜像大小 | JDK+JAR约200MB | 单文件约50MB |
| 稳态吞吐 | 高（JIT持续优化） | 中（无动态优化） |

> 💡 **AOT适用判断**：
> - 强适合：Serverless函数、CLI工具、网格网关、轻量定时任务；
> - 不适合：运行时大量反射/CGLIB代理、热部署需求、多态热点接口；
> - 折中：JDK11+ JIT+AOT混合模式，静态逻辑AOT + 高频热点JIT。

## 8. CodeCache管理与CodeCache满问题排查

### 8.1 CodeCache结构

CodeCache是JVM用于存储JIT编译后**本地机器码**的内存区域，位于堆外元空间管理：

```text
JVM内存
┌─────────────────────────────────────────────┐
│  堆（Heap）：Eden | Survivor | Old Gen      │
├─────────────────────────────────────────────┤
│  元空间（Metaspace）：类元数据 | 常量池       │
│    └── CodeCache：JIT编译后的机器码          │
└─────────────────────────────────────────────┘
```

### 8.2 症状与排查

**典型症状：**
- CPU飙高，日志大量输出`Compilation`和`CodeCache`相关记录；
- JIT编译器日志：`CodeCache is full. Compiler has been disabled.`；
- 服务越跑越慢（已编译机器码被回收，热点代码反复重编译）；
- GC日志频繁打印`Metadata GC Threshold`。

**排查命令：**

```bash
jcmd <PID> Compiler.codecache      # 查看CodeCache使用量
jstat -compiler <PID> 1000 5       # 监控编译状态
-XX:+PrintCompilation -XX:+PrintCodeCache  # 开启编译日志
```

### 8.3 优化方案

| 优化类型 | 具体措施 | JVM参数 |
|----------|----------|---------|
| **扩容CodeCache** | 增大预留空间 | `-XX:ReservedCodeCacheSize=512m` |
| **控制编译数量** | 降低编译线程数 | `-XX:CICompilerCount=4` |
| **启用缓存刷新** | 允许回收旧机器码 | `-XX:+UseCodeCacheFlushing` |
| **提高编译阈值** | 减少非热点代码编译 | `-XX:CompileThreshold=15000` |
| **代码优化** | 缓存动态代理类，减少反射 | — |

> ⚠️ **典型故障场景**：大量Spring AOP动态生成代理类 → 元空间上涨 → GC清空CodeCache → 热点代码反复重编译（批处理从2h延长到5h）。解决：**全局缓存AOP代理类** + 扩容元空间和CodeCache。

## 9. JIT编译日志分析与-XX:+PrintCompilation

### 9.1 开启编译日志

```bash
-XX:+PrintCompilation                    # 打印每次编译事件
-XX:+PrintInlining                       # 打印内联决策
-XX:+PrintCodeCache                      # 打印CodeCache状态
-XX:+PrintCompilationFailureReason       # 打印编译失败原因（JDK11+）
```

### 9.2 日志格式解读

```text
 65150  306       3       com.example.service.OrderService::createOrder (45 bytes)
 ①      ②       ③       ④                              ⑤

① 65150     ── 时间戳（ms from JVM start）
② 306       ── 编译ID（递增）
③ 3         ── 编译层级（0=解释, 1=C1, 2=C1有限profiling, 3=C1完整profiling, 4=C2/Graal）
④ 全限定名   ── 编译的方法全限定名
⑤ (45 bytes)─ 方法字节码大小

标记：! = 编译异常  s = 同步方法  % = OSR编译
```

### 9.3 常见编译日志指标

| 日志模式 | 含义 | 处理建议 |
|----------|------|----------|
| 大量`made not entrant` | 方法被废弃（被更优编译替换） | 正常，关注频率 |
| 大量`made zombie` | 方法被回收（CodeCache空间释放） | 若频繁出现说明CodeCache不足 |
| 连续相同方法重复编译 | 编译后又被回收，再编译 | CodeCache不足，需扩容 |
| `compilation failed: method too large` | 方法体过大无法编译 | 拆分巨型方法 |
| `compilation failed: inline limit` | 内联达到上限 | 减小方法体或调整内联阈值 |

### 9.4 Arthas编译诊断

```bash
dashboard                          # 查看JIT编译器信息
jvm                                # 查看JIT编译统计
trace *Service *Method -n 5        # 追踪方法调用，定位热点
jad com.example.service.OrderService  # 反汇编查看编译后字节码
```

> 🎯 **线上排查黄金流程**：发现CPU打满 → 开启`-XX:+PrintCompilation -XX:+PrintCompilationFailureReason` → 分析编译失败原因 → 定位巨型方法/代码缓存满 → 针对性优化代码或调整JVM参数。

## 10. 前端编译（javac）：语法糖解糖

### 10.1 javac编译流程

```text
.java源码 → 词法分析（Token序列）→ 语法分析（AST树）→ 语义分析（类型检查+常量折叠）→ 字节码生成
```

### 10.2 前端静态优化

| 优化项 | 说明 |
|--------|------|
| **常量折叠** | `int a = 1+2+3` → `int a=6` |
| **常量传播** | `final`变量值替换到使用处 |
| **无用代码消除** | `if(false){...}` 直接删除 |
| **语法糖解糖** | 泛型擦除、自动装箱转换、lambda转invokedynamic |
| **字符串常量池复用** | 相同字符串字面量共用 |

### 10.3 前端编译 vs 后端JIT协作

```text
前端编译（javac）                      后端JIT编译
    ├── 常量折叠 / 传播                ├── 循环展开 / 向量化
    ├── 无用代码消除                    ├── 逃逸分析 + 标量替换
    └── 语法糖解糖                     ├── 深度方法内联
                                       ├── 锁消除 / 锁粗化
                                       └── 去虚拟化 / 类型预测
              ↓                                  ↓
          高效字节码 ───────────────────→ 热点代码 → 本地机器码
          （减少JIT工作量）              （极致性能）
```

> 💡 **协作策略**：生产环境开启`-O`（基础优化）；使用`final`修饰常量触发常量折叠；构建简洁方法（≤10行），同时便于前端内联和后端JIT内联。

## 11. 面试高频考点

### 11.1 基础概念类

| 问题 | 核心回答 |
|------|----------|
| **JVM为什么采用解释+编译混合执行？** | 兼顾启动速度（解释执行）与稳态性能（JIT编译） |
| **分层编译的5个层级？** | 0解释 → 1 C1无profiling → 2 C1有限profiling → 3 C1完整profiling → 4 C2/Graal |
| **两种计数器的作用？** | 方法调用计数器（调用次数）+ 回边计数器（循环次数），超阈值触发编译/OSR |
| **C1、C2、Graal的区别？** | C1快但优化弱，C2慢但优化极致，Graal兼具两者优势，JDK17+默认Graal |

### 11.2 优化技术类

| 问题 | 核心回答 |
|------|----------|
| **方法内联的条件？** | 默认≤35字节；高频、小方法、单实现类接口更易内联；分支复杂拒绝内联 |
| **逃逸分析能带来哪些优化？** | 标量替换（栈上分配）、锁消除、减少GC压力三种优化 |
| **锁消除与锁粗化的区别？** | 锁消除：无竞争锁直接去掉；锁粗化：连续加解锁合并为一次 |
| **为什么方法内联是JIT最重要的优化？** | 内联是其他优化的基础——内联后逃逸分析、循环优化才有更大的分析范围 |

### 11.3 故障排查类

| 问题 | 核心回答 |
|------|----------|
| **服务越跑越慢，CPU波动大？** | CodeCache满 → 机器码被回收 → 反复重编译 → CPU持续升高 |
| **巨型方法的影响？** | 超过编译阈值 → 编译失败 → 长期解释执行 → CPU飙升、RT抖动 |
| **如何排查JIT编译问题？** | 开启`-XX:+PrintCompilation -XX:+PrintCompilationFailureReason`，分析编译失败原因 |

### 11.4 AOT & 趋势

| 问题 | 核心回答 |
|------|----------|
| **AOT vs JIT适用场景？** | AOT：Serverless/CLI；JIT：长驻后端服务 |
| **GraalVM Native Image优劣势？** | 优：极速启动、低内存；劣：反射/动态代理受限 |
| **JDK17+编译器相对JDK8的改进？** | Graal替代C2（速度+30%）、增强逃逸分析、稳定AOT |

> 🎯 **大厂面试重点**：方法内联 + 逃逸分析 + 标量替换是**必考三件套**；线上JIT故障排查是**高频场景题**（CPU打满 → 编译日志定位 → 拆分方法/扩容参数）；Graal替代C2和AOT编译是JDK17+新热点。

## 12. 常用JVM编译参数速查

```bash
# 编译模式
-Xint                        # 纯解释执行（禁用JIT，调试用）
-Xcomp                       # 纯编译模式（所有方法编译，启动慢）
-XX:+TieredCompilation       # 开启分层编译（JDK8默认开启）

# 编译器选择
-XX:+UseGraal                # 使用Graal编译器（JDK17+默认）

# 热点探测
-XX:CompileThreshold=10000   # 方法调用计数器阈值
-XX:-UseCounterDecay         # 关闭热度衰减（性能测试时）

# 方法内联
-XX:MaxInlineSize=35         # 内联最大字节码大小
-XX:FreqInlineSize=325       # 热点方法内联上限
-XX:+PrintInlining           # 打印内联决策

# 逃逸分析
-XX:+DoEscapeAnalysis        # 开启逃逸分析
-XX:+EliminateAllocations    # 开启标量替换
-XX:+EliminateLocks          # 开启锁消除

# CodeCache
-XX:ReservedCodeCacheSize=512m   # CodeCache预留大小
-XX:CICompilerCount=8            # 编译线程数
-XX:+UseCodeCacheFlushing        # 允许刷新CodeCache
-XX:+PrintCodeCache              # 打印CodeCache状态

# AOT
-XX:+UseAOT                  # 开启AOT
-XX:AOTLibrary=./aot.so      # 指定AOT库路径

# 编译日志
-XX:+PrintCompilation                # 打印编译事件
-XX:+PrintCompilationFailureReason   # 打印编译失败原因
-XX:+LogCompilation                  # 输出编译日志到文件
```
