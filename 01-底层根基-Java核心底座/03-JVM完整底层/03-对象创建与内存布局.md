## 1. 对象创建的五步流程

在 Java 中创建一个对象，只需短短一行 `new` 关键字，但在 JVM 底层却经历了一个完整的五步链路。

```java
// 以这行代码为入口，跟踪整个创建流程
Student s = new Student("Alice", 20);
```

### 1.1 完整流程图

```
┌─────────────────────────────────────────────────────────────────┐
│                对象创建完整链路（Five-Step Flow）                    │
│                                                                   │
│  字节码指令: new → dup → ldc → invokespecial <init>               │
│                                                                   │
│  ┌─────────────────────────────────────────────────────────────┐  │
│  │ Step 1: 类加载检查                                           │  │
│  │   new 指令 → 常量池中定位类的符号引用                           │  │
│  │   ├── 类已加载 → 跳过                                        │  │
│  │   └── 类未加载 → 执行类加载（加载→验证→准备→解析→初始化）        │  │
│  └───────────────────┬─────────────────────────────────────────┘  │
│                      ▼                                             │
│  ┌─────────────────────────────────────────────────────────────┐  │
│  │ Step 2: 分配内存                                             │  │
│  │   确定对象大小 → 从堆中分配连续内存                             │  │
│  │   ├── 指针碰撞（Bump-the-Pointer）：GC 规整时使用              │  │
│  │   └── 空闲列表（Free List）：不规整时使用（如 CMS）              │  │
│  │   线程安全：TLAB 优先 / CAS + 失败重试                         │  │
│  └───────────────────┬─────────────────────────────────────────┘  │
│                      ▼                                             │
│  ┌─────────────────────────────────────────────────────────────┐  │
│  │ Step 3: 初始化零值                                           │  │
│  │   所有实例字段设为零值（0 / 0L / 0.0f / false / null）         │  │
│  │   目的：保证字段在未显式赋值前可直接使用（不会出现随机值）         │  │
│  └───────────────────┬─────────────────────────────────────────┘  │
│                      ▼                                             │
│  ┌─────────────────────────────────────────────────────────────┐  │
│  │ Step 4: 设置对象头                                           │  │
│  │   ├── Mark Word：哈希码、GC 分代年龄、锁标志位                 │  │
│  │   └── Klass Pointer：指向方法区中该类的元数据                   │  │
│  └───────────────────┬─────────────────────────────────────────┘  │
│                      ▼                                             │
│  ┌─────────────────────────────────────────────────────────────┐  │
│  │ Step 5: 执行 <init> 方法                                     │  │
│  │   执行顺序：父类构造器 → 实例变量初始化 → 构造代码块 → 构造器     │  │
│  │   <init> 由 invokespecial 指令触发                           │  │
│  └─────────────────────────────────────────────────────────────┘  │
│                                                                   │
│  ⚠️ new + dup + invokespecial 这条字节码序列不可分割：              │
│  前两步（new + dup）分配裸对象，最后一步（invokespecial）才          │
│  调用构造器完成初始化。中间出现的异常会导致对象变成"半初始化"状态。    │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 对应字节码分析

```java
public class ObjectCreationBytecode {
    public static void main(String[] args) {
        Student s = new Student("Alice", 20);
    }
}
```

反编译后对应的字节码指令序列：

```text
 0: new             #7    // class Student        ← 分配裸对象（步骤 1-4）
 3: dup                   // 复制引用，留给 invokespecial 消耗
 4: ldc             #9    // String "Alice"        ← 加载常量
 6: bipush         20     // int 20
 8: invokespecial   #12   // Method Student."<init>":(Ljava/lang/String;I)V  ← 调用构造器
11: astore_1              // 将引用存入局部变量表
12: return
```

> 💡 **关键认知**：`new` 指令只完成"创建裸对象"（分配内存 + 设置对象头），此时对象还处于"零值状态"。真正的初始化由后续的 `invokespecial <init>` 完成。这意味着两条指令之间如果有异常，堆中会存在一个"半初始化"对象——这也是为什么 `new` 和 `invokespecial` 在字节码层面必须成对出现。

### 1.3 `<init>` 方法的执行顺序

```java
public class InitOrder {
    private int x = getX();            // ③ 实例变量初始化（按声明顺序）
    private int y;                     // ③ y = 0（零值已被步骤 3 覆盖）

    {                                  // ④ 构造代码块
        System.out.println("instance block");
        y = 10;
    }

    public InitOrder() {               // ⑤ 构造器方法体
        super();                        // ① 隐式调用父类 <init>
        // ② 父类构造器返回后，才执行本类的实例变量 + 构造代码块
        System.out.println("constructor body: x=" + x + ", y=" + y);
    }

    private int getX() {
        return 42;
    }

    public static void main(String[] args) {
        new InitOrder();
    }
}
```

**实际执行顺序（编译后 <init> 中的代码排列）：**

| 执行次序 | 内容 | 说明 |
|---------|------|------|
| 1 | `super()`（父类 `<init>`） | 必须位于最前 |
| 2 | 实例变量初始化 | 按声明顺序（`x = getX()` → 42） |
| 3 | 构造代码块 `{ ... }` | 按声明顺序（`y = 10`） |
| 4 | 构造器方法体剩余代码 | `println` |

> ⚠️ 如果父类的 `<init>` 中调用了被子类重写的方法（且该方法访问了子类实例变量），则会访问到尚未初始化的变量（零值）。这是多态性在构造器中的经典陷阱。

## 2. 内存分配方式：指针碰撞 vs 空闲列表

JVM 从堆中为对象分配内存时，有两种基本策略，具体选择取决于**堆内存是否规整**。

### 2.1 两种分配方式对比

```
规整内存（标记-整理 / 复制算法 GC 后）:
┌──────────────────────────────────────────────────────┐
│  已分配对象               │       剩余空闲空间          │
│  [obj1][obj2][obj3]      │      (连续的一块)          │
└──────────────────────────┴───────────────────────────┘
                            ↑
                     指针（指针碰撞，只需移动指针）

不规整内存（标记-清除 GC 后）:
┌──────────────────────────────────────────────────────┐
│  已分配   │ 空闲 │  已分配  │ 空闲  │ 已分配  │ 空闲   │
│  [obj1]  │     │  [obj2]│      │ [obj3] │       │
└──────────┴─────┴────────┴──────┴────────┴───────┘
                          ↑
            需要遍历空闲列表找到足够大的一块（空闲列表）
```

| 分配方式 | 适用条件 | 对应垃圾收集器 | 描述 |
|---------|---------|---------------|------|
| **指针碰撞**（Bump-the-Pointer） | 堆内存规整（无碎片） | Serial、ParNew、Parallel Scavenge、G1（Young GC） | 维护一个指针指向已分配区域边界，分配时指针前移对象大小 |
| **空闲列表**（Free List） | 堆内存不规整（有碎片） | CMS（Concurrent Mark-Sweep） | 维护一个空闲块列表，分配时查找足够大的块 |

```java
/**
 * 指针碰撞 vs 空闲列表的选择在 JVM 中由 GC 收集器决定
 * 配置不同的 GC 即选择了不同的分配策略
 */
public class AllocationStrategyDemo {
    public static void main(String[] args) {
        // -XX:+UseSerialGC       → 新生代复制算法 → 指针碰撞
        // -XX:+UseParallelGC     → 新生代复制算法 → 指针碰撞
        // -XX:+UseConcMarkSweepGC → 老年代标记-清除 → 空闲列表
        // -XX:+UseG1GC           → Region 级别指针碰撞

        byte[] obj = new byte[1024]; // 底层分配策略由 GC 决定
    }
}
```

### 2.2 线程安全问题与解决方案

多线程并发分配对象时，存在线程安全问题：多个线程同时修改同一个指针。

| 解决方案 | 描述 | 开启方式 |
|---------|------|---------|
| **TLAB**（优先） | 每个线程在 Eden 区有一块私有的分配缓冲区，小对象在 TLAB 内分配，无需同步 | `-XX:+UseTLAB`（默认开启） |
| **CAS + 失败重试** | TLAB 空间不足或大对象分配时，使用 CAS 乐观锁更新分配指针 | 自动降级 |

> 💡 TLAB 是典型的"空间换时间"策略——用少量内存浪费换取分配时无锁化。绝大多数小对象分配在 TLAB 中就完成了，只有 TLAB 用尽或分配大对象时才走 CAS 路径。

## 3. TLAB（Thread Local Allocation Buffer）

### 3.1 设计原理

TLAB 是 Eden 区中为每个线程划分出的一块私有内存区域，用于**无锁分配小对象**。

```
Eden 区内的 TLAB 分布（逻辑视角）：

┌──────────────────────────────────────────────────────────────┐
│                          Eden                                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────────┐ │
│  │ TLAB     │  │ TLAB     │  │ TLAB     │  │ 共享区域      │ │
│  │ (线程1)  │  │ (线程2)  │  │ (线程3)  │  │ (大对象/      │ │
│  │          │  │          │  │          │  │  TLAB溢出)   │ │
│  └──────────┘  └──────────┘  └──────────┘  └──────────────┘ │
│         │              │             │                         │
│         ▼              ▼             ▼                         │
│     线程1 new        线程2 new     线程3 new                   │
│     无锁分配         无锁分配       无锁分配                    │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 TLAB 分配流程

```
线程请求分配对象:
    │
    ├── 对象大小 > TLAB 剩余空间?
    │       │
    │       ├── 否 → 在 TLAB 内分配（无锁，极快）
    │       │
    │       └── 是 → 剩余空间 < TLABRefillWasteLimit（浪费阈值）?
    │               │
    │               ├── 是 → 当前 TLAB 废弃（归还 Eden），
    │               │        重新申请新 TLAB 并分配
    │               │
    │               └── 否 → 对象在 TLAB 外分配
    │                         （CAS + 指针碰撞 / 空闲列表）
    ▼
分配完成
```

### 3.3 相关参数

| JVM 参数 | 默认值 | 说明 |
|---------|--------|------|
| `-XX:+UseTLAB` | true | 启用 TLAB（JDK 8+ 默认开启） |
| `-XX:TLABSize` | 动态调整 | 每个 TLAB 的初始大小 |
| `-XX:TLABRefillWasteFraction` | 64 | TLAB 允许浪费的比例，值越大浪费越少 |
| `-XX:+PrintTLAB` | - | 打印 TLAB 使用情况（诊断用） |
| `-XX:ResizeTLAB` | true | 允许 JVM 动态调整 TLAB 大小 |

```java
/**
 * TLAB 使用效果演示
 * 运行参数：-XX:+UseTLAB -XX:+PrintTLAB -XX:-DoEscapeAnalysis
 */
public class TLABDemo {
    private static final int THREAD_COUNT = 4;
    private static final int ALLOC_SIZE = 1024;     // 1KB 小对象
    private static final int ALLOC_COUNT = 100000;

    public static void main(String[] args) throws Exception {
        Thread[] threads = new Thread[THREAD_COUNT];
        for (int i = 0; i < THREAD_COUNT; i++) {
            threads[i] = new Thread(() -> {
                // 每个线程在自己的 TLAB 中无锁分配大量小对象
                for (int j = 0; j < ALLOC_COUNT; j++) {
                    byte[] b = new byte[ALLOC_SIZE]; // TLAB 分配
                }
            });
            threads[i].start();
        }
        for (Thread t : threads) {
            t.join();
        }
        System.out.println("分配完成，4 个线程共分配 " +
                (THREAD_COUNT * ALLOC_COUNT * ALLOC_SIZE / 1024 / 1024) + " MB");
    }
}
```

### 3.4 TLAB 的局限

| 场景 | 说明 |
|------|------|
| **大对象** | 超过 `-XX:PretenureSizeThreshold` 的对象直接进入老年代，不走 TLAB |
| **TLAB 外分配** | TLAB 剩余空间不足且浪费率超过阈值时，对象在 Eden 共享区通过 CAS 分配 |
| **逃逸分析 + 栈上分配** | JIT 检测到对象不逃逸时，直接在栈上分配，连 TLAB 都不经过 |

> 🎯 **核心要点**：TLAB 是小对象分配的主力通道，它使得绝大多数 `new` 操作在用户态即可完成，无需内核同步。一个 Java 应用每秒可能分配数十万对象，TLAB 是支撑这个吞吐量的关键基础设施。

## 4. 对象内存布局（Mark Word + Klass Pointer + 实例数据 + 对齐填充）

对象在堆中并非"裸数据"的简单堆放，而是按照固定格式组织的。HotSpot 虚拟机中，一个 Java 对象在内存中划分为四个区域。

### 4.1 整体布局图

```
64 位 HotSpot JVM 对象布局（默认开启指针压缩）

┌──────────────────────────────────────────────────────────────┐
│ ① Mark Word（标记字）               8 bytes                    │
│  ├── 哈希码（无锁时生成，25/31 bits）                           │
│  ├── GC 分代年龄（4 bits，最大 15）                             │
│  ├── 偏向锁线程 ID（54 bits，偏向锁时）                          │
│  ├── 锁标志位（2 bits）                                        │
│  └── 是否偏向锁（1 bit）                                        │
├──────────────────────────────────────────────────────────────┤
│ ② Klass Pointer（类指针）           4 bytes（压缩） / 8 bytes（非压缩） │
│  └── 指向方法区中该对象的 Class 元数据                            │
│      （JVM 通过此指针知道对象是哪个类的实例）                       │
├──────────────────────────────────────────────────────────────┤
│ ③ 实例数据（Instance Data）          取决于字段类型和数量            │
│  ├── 父类声明的字段（按继承顺序排列）                              │
│  ├── 子类声明的字段（按声明顺序排列）                              │
│  └── 排列顺序：double/long > int/float > char/short > byte/boolean > oop │
├──────────────────────────────────────────────────────────────┤
│ ④ 对齐填充（Padding）               对齐到 8 字节的整数倍           │
│  └── 对象总大小必须是 8 的倍数（HotSpot 对象对齐要求）              │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 使用 JOL 工具观察对象布局

JOL（Java Object Layout）是 OpenJDK 提供的工具，可以精确查看对象的内存布局。

```xml
<!-- Maven 依赖 -->
<dependency>
    <groupId>org.openjdk.jol</groupId>
    <artifactId>jol-core</artifactId>
    <version>0.17</version>
</dependency>
```

```java
import org.openjdk.jol.info.ClassLayout;
import org.openjdk.jol.info.GraphLayout;
import org.openjdk.jol.vm.VM;

public class JOLSample {

    public static void main(String[] args) {
        // 查看 JVM 信息（指针压缩状态、对齐等）
        System.out.println(VM.current().details());

        SimpleObject obj = new SimpleObject();
        // 打印对象内部布局
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());

        // 打印对象总大小（含引用的子对象）
        System.out.println("Total size: " +
                GraphLayout.parseInstance(obj).totalSize() + " bytes");
    }

    static class SimpleObject {
        int id;              // 4 bytes
        long timestamp;      // 8 bytes
        String name;         // 4 bytes（压缩 OOP）
        boolean active;      // 1 byte
        byte flag;           // 1 byte
    }
}
```

**预期输出（64-bit, compressed OOPs）：**

```
# WARNING: Unable to attach Serviceability Agent...
java.lang.Object object internals:
OFF  SZ   TYPE DESCRIPTION               VALUE
  0   8        (object header: mark)     0x0000000000000001 (non-biasable)
  8   4        (object header: class)    0x00012345
 12   4    int SimpleObject.id           0
 16   8   long SimpleObject.timestamp    0
 24   4   String SimpleObject.name       null
 28   1 boolean SimpleObject.active      false
 29   1    byte SimpleObject.flag        0
 30   6        (loss due to padding)     ← 填充至 8 的倍数
Instance size: 36 bytes (aligned to 40 bytes)
```

> 💡 **注意对齐规则**：HotSpot 要求对象起始地址必须是 8 的倍数。即便 `SimpleObject` 的字段总大小为 `8+4+4+8+4+1+1 = 30` 字节，经对齐填充后，实际占用的空间是 `40` 字节。这 10 字节的差异就是对齐填充。

### 4.3 实例数据的排列顺序为什么这样设计？

JVM 对实例字段的排列遵循局部性原理和内存对齐优化，并非简单的"代码声明顺序"。

```java
/**
 * 字段重排优化
 * 错误的声明方式（浪费空间）：
 */
class BadOrder {
    boolean a;     // 1 byte
    long b;        // 8 bytes（需要对齐到 8 的偏移量）
    int c;         // 4 bytes
    // 布局：a(1) + padding(7) + b(8) + c(4) + padding(4) = 24 bytes
}

/**
 * 优化后的声明方式（节省空间）：
 */
class GoodOrder {
    long b;        // 8 bytes
    int c;         // 4 bytes
    boolean a;     // 1 byte
    // 布局：b(8) + c(4) + a(1) + padding(3) = 16 bytes
}
```

| 声明顺序（优化后） | 偏移量 | 大小 | 说明 |
|-----------------|--------|------|------|
| long/double | 0 | 8 | 8 字节对齐，放最前面 |
| int/float | 8 | 4 | 4 字节对齐 |
| char/short | 12 | 2 | 2 字节对齐 |
| byte/boolean | 14 | 1 | 1 字节对齐 |
| reference (OOP) | 15 | 4/8 | 压缩指针 4 字节，非压缩 8 字节 |

> 💡 **实战建议**：将大的字段（long、double）放在类的前面声明，小的字段（byte、boolean）放在后面，可以最大化利用对齐空间，减少填充损耗。这个技巧在创建大量对象的场景下效果显著。

## 5. Mark Word 详解（32位/64位，压缩指针）

Mark Word 是对象头的核心组成部分，存储了对象的运行时元数据。它的数据结构非常"弹性"——同一块内存区域在不同状态下存储不同含义的数据。

### 5.1 32 位 Mark Word 结构

```
32 位 JVM Mark Word:

无锁状态:
┌────────────────────┬───────────────────────┬──────┬──────┐
│    25 bits         │    31 bits             │ 1bit │ 2bit │
│    unused          │    identity_hashcode   │ age  │ 01   │
└────────────────────┴───────────────────────┴──────┴──────┘
                                                     lock=01(无锁)

偏向锁状态:
┌──────────────────────────┬──────────┬──────┬──────┬──────┐
│    23 bits                │ 2bits    │ 1bit │ 4bit │ 01   │
│    threadID               │ epoch    │ 1    │ age  │ 01   │
└──────────────────────────┴──────────┴──────┴──────┴──────┘
                                          biased=1(偏向锁)

轻量级锁:
┌──────────────────────────────────────────────────────┬──────┐
│                    30 bits                            │ 00   │
│                指向 Lock Record 的指针                  │ 轻量 │
```

### 5.3 锁标志位速查

| 锁标志位（2 bits） | 是否偏向锁（1 bit） | 状态 | 说明 |
|------------------|-----------------|------|------|
| 01 | 0 | **无锁**（Non-biasable） | 对象刚创建或偏向锁被撤销后的状态 |
| 01 | 1 | **偏向锁**（Biased Locking） | 只有一个线程访问同步块 |
| 00 | - | **轻量级锁**（Lightweight Locked） | 多线程交替执行，未竞争 |
| 10 | - | **重量级锁**（Heavyweight Locked） | 多线程竞争激烈，进入 OS 管程 |
| 11 | - | **GC 标记**（GC Marking） | GC 标记阶段使用 |

### 5.4 指针压缩（Compressed OOPs）

```bash
# 默认开启（堆 < 32GB）
-XX:+UseCompressedOops
# 手动关闭
-XX:-UseCompressedOops
```

| 特性 | 未压缩（-UseCompressedOops） | 压缩（+UseCompressedOops） |
|------|----------------------------|---------------------------|
| 对象引用大小 | 8 bytes | 4 bytes |
| Klass Pointer 大小 | 8 bytes | 4 bytes |
| 对象头总大小 | 16 bytes（Mark 8 + Klass 8） | 12 bytes（Mark 8 + Klass 4） |
| 最大堆限制 | 几乎无限制 | 约 32GB（2^32 × 8 字节对齐） |
| 内存占用 | 大 | 小（减少约 30%-40% 引用空间） |
| 缓存命中率 | 低 | 高（更紧凑，CPU 缓存更有效） |

**压缩指针的原理：**

对象地址仍然是 64 位的，但由于对象总是 8 字节对齐，JVM 将地址右移 3 位后再存储（压缩 8 倍），使用时左移 3 位还原。这样 32 位最大可表示 `2^32 × 8 = 32GB` 的地址空间。

> ⚠️ 当堆大小超过 32GB 时，指针压缩自动失效，每个对象引用从 4 字节膨胀回 8 字节。此时即便你多分配了内存，可用容量反而可能因为引用膨胀而减少。这是 JDK 官方测试中多次验证的现象——**堆跨过 32GB 阈值后，有效容量有时反而下降**。

```java
/**
 * 验证指针压缩影响
 * 运行参数：-XX:+UseCompressedOops（默认）
 * 或者：-XX:-UseCompressedOops
 */
public class CompressedOopsDemo {
    public static void main(String[] args) {
        // 创建一个包含大量引用的对象，对比不同参数下的内存占用
        Node head = new Node();
        Node current = head;
        for (int i = 0; i < 1_000_000; i++) {
            current.next = new Node();
            current = current.next;
        }
        System.out.println("链表创建完成。引用数量: 1,000,000");
        // 开启压缩时：每个 Node ≈ 24 bytes（12 header + 12 字段）
        // 关闭压缩时：每个 Node ≈ 32 bytes（16 header + 16 字段）
        // 节省超过 33% 的内存！
    }

    static class Node {
        Node next;     // 压缩时 4B，非压缩时 8B
        Node prev;     // 压缩时 4B，非压缩时 8B
        long value;    // 8B（不变）
        // 压缩总计：12(header) + 4+4+8 = 28 → 对齐 32B
        // 未压缩：16(header) + 8+8+8 = 40 → 对齐 40B
    }
}
```

## 6. 对象访问定位：句柄访问 vs 直接指针

Java 程序通过栈上的局部变量引用来操作堆中的对象。这个引用如何定位到实际对象？有两种主流实现方式。

### 6.1 两种方式对比图解

```
句柄访问（Handle Access）:
                                                                 方法区
  Java 栈（局部变量表）              Java 堆                    ┌──────────┐
  ┌──────────────┐            ┌─────────────────┐            │ Klass    │
  │  reference   │───────────▶│  Handle Pool     │           │Metadata │
  │              │            │ ┌─────────────┐ │ ────────▶│          │
  │              │            │ │ 对象实例指针  │ │ ──▶     │类型信息、│
  │              │            │ │ 类型数据指针  │ │ ────────│ 接口、   │
  └──────────────┘            │ └─────────────┘ │          │ 方法表等 │
                              │                 │          └──────────┘
                              │ ┌─────────────┐ │
                              │ │  object1     │ │  ← 句柄池中的指针指向实际对象
                              │ └─────────────┘ │
                              └─────────────────┘

直接指针访问（Direct Pointer，HotSpot 方案）:
                                                                 方法区
  Java 栈（局部变量表）               Java 堆                    ┌──────────┐
  ┌──────────────┐            ┌─────────────────┐              │ Klass    │
  │  reference   │───────────▶│ 对象头 (Header)  │             │Metadata │
  │              │            │ ┌─────────────┐ │ ──────────▶│          │
  │              │            │ │  Mark Word  │ │             │类型信息、│
  │              │            │ ├─────────────┤ │             │ 接口、   │
  │              │            │ │Klass Pointer│─┼───────────▶│ 方法表等 │
  │              │            │ └─────────────┘ │             └──────────┘
  └──────────────┘            │ │ Instance Data│ │
                              │ └─────────────┘ │
                              └─────────────────┘
```

### 6.2 详细对比

| 特性 | 句柄访问 | 直接指针（HotSpot 使用） |
|------|---------|------------------------|
| **访问速度** | 慢：两次指针访问（句柄池 → 对象 → 类型数据） | 快：一次指针访问直接找到对象 |
| **GC 影响** | GC 移动对象时只需更新句柄池中的指针，栈上的引用不变 | GC 移动对象时必须遍历所有线程栈更新引用 |
| **实现复杂度** | 简单（句柄池统一管理） | 复杂（需要遍历查重引用） |
| **代表实现** | IBM J9 / 早期 JVM | **HotSpot**（Oracle JDK / OpenJDK） |
| **内存开销** | 额外维护句柄池 | 更紧凑 |

```java
/**
 * 访问效率差异演示（概念层面）
 * HotSpot 使用直接指针访问，所以以下代码中
 * obj.method() 的底层只需要一次指针解引用
 */
public class AccessDemo {
    public static void main(String[] args) {
        MyClass obj = new MyClass();

        // HotSpot 直接指针访问路径：
        // reference → obj 对象（通过 Klass Pointer 找到方法表）
        obj.sayHello();

        // 句柄访问路径（如果是 IBM J9）：
        // reference → 句柄池 → obj 对象（再通过类型指针找到方法表）
        // 多了一次内存访问
    }
}

class MyClass {
    private int value;

    public void sayHello() {
        System.out.println("Hello, value=" + value);
    }
}
```

> 🎯 **HotSpot 选择直接指针的原因**：对象访问是 Java 程序最频繁的操作之一。一次额外的指针访问看似微不足道，但在数亿次调用下就会成为显著的性能瓶颈。HotSpot 选择"性能优先"的策略，将 GC 移动对象的额外复杂度体现在 GC 实现中（通过 OopMap 数据结构高效管理引用）。

### 6.3 OopMap 与 GC 时的引用更新

HotSpot 使用直接指针，GC 移动对象后需要更新所有引用。这是通过 **OopMap**（普通对象指针映射表）来实现的：

```
OopMap 工作流程：

1. 编译阶段（JIT）：
   方法编译时，记录哪些栈位置和寄存器存有对象引用
   → 生成 OopMap 数据结构

2. 安全点（Safepoint）：
   所有线程运行到安全点后暂停，此时引用状态一致

3. GC 移动对象后：
   JVM 通过 OopMap 知道所有引用位置，一次性更新
   → 比遍历整个栈高效得多
```

| 机制 | 描述 |
|------|------|
| **OopMap** | JIT 编译时记录的总引用位置表 |
| **Safepoint** | 线程可安全暂停的执行点（方法调用、循环回边、异常抛出等） |
| **GC Roots 枚举** | 在安全点借助 OopMap 快速找到所有 GC Roots |

## 8. 基本类型包装类的缓存对象

Java 对部分基本类型的包装类实现了缓存机制（Flyweight 模式），在特定范围内的对象不会重复创建。

### 8.1 各包装类的缓存范围

| 包装类 | 缓存范围 | 实现机制 |
|--------|---------|---------|
| `Boolean` | `true` / `false` | 两个静态 final 实例 |
| `Byte` | -128 ~ 127 | 静态内部类数组，类加载时预创建 |
| `Short` | -128 ~ 127 | 静态内部类数组，类加载时预创建 |
| `Integer` | -128 ~ 127（默认，上限可通过 JVM 参数调整） | 静态内部类 `IntegerCache` |
| `Long` | -128 ~ 127 | 静态内部类数组 |
| `Character` | 0 ~ 127（' ' ~ ''） | 静态内部类数组 |
| `Float` | **无缓存** | 浮点数数量太多 |
| `Double` | **无缓存** | 浮点数数量太多 |

```java
/**
 * 包装类缓存验证
 */
public class WrapperCacheDemo {

    public static void main(String[] args) {
        // Integer 缓存（-128 ~ 127）
        Integer a = 127;
        Integer b = 127;
        System.out.println("Integer 127 == 127: " + (a == b));     // true

        Integer c = 128;
        Integer d = 128;
        System.out.println("Integer 128 == 128: " + (c == d));     // false（超出缓存范围）

        // Boolean 缓存
        Boolean t1 = true;
        Boolean t2 = true;
        System.out.println("Boolean true: " + (t1 == t2));          // true

        // Long 缓存（-128 ~ 127）
        Long l1 = 100L;
        Long l2 = 100L;
        System.out.println("Long 100 == 100: " + (l1 == l2));       // true

        Long l3 = 200L;
        Long l4 = 200L;
        System.out.println("Long 200 == 200: " + (l3 == l4));       // false

        // Float 无缓存
        Float f1 = 1.0f;
        Float f2 = 1.0f;
        System.out.println("Float 1.0 == 1.0: " + (f1 == f2));      // false

        // new 关键字强制创建新对象（不走缓存）
        Integer n1 = new Integer(100);
        Integer n2 = new Integer(100);
        System.out.println("new Integer(100) == new Integer(100): "
                + (n1 == n2));                                      // false
    }
}
```

### 8.3 缓存对象的内部实现（Integer 源码分析）

```java
// Integer 内部类（JDK 8+ 源码简化版）
public final class Integer extends Number implements Comparable<Integer> {

    // 缓存数组位于静态内部类中，类加载时初始化
    private static class IntegerCache {
        static final int low = -128;
        static final int high;         // 默认 127，可通过 AutoBoxCacheMax 调整
        static final Integer cache[];

        static {
            // 解析 -XX:AutoBoxCacheMax 参数
            int h = 127;
            String integerCacheHighPropValue =
                sun.misc.VM.getSavedProperty(
                    "java.lang.Integer.IntegerCache.high");
            if (integerCacheHighPropValue != null) {
                h = Math.max(Integer.parseInt(integerCacheHighPropValue), 127);
            }
            high = h;
            cache = new Integer[(high - low) + 1];
            int j = low;
            for (int k = 0; k < cache.length; k++) {
                cache[k] = new Integer(j++); // 预创建所有缓存对象
            }
        }
    }

    // valueOf 方法使用缓存
    public static Integer valueOf(int i) {
        if (i >= IntegerCache.low && i <= IntegerCache.high) {
            return IntegerCache.cache[i + (-IntegerCache.low)];
        }
        return new Integer(i);
    }
}
```

> ⚠️ **开发陷阱**：始终使用 `valueOf()` 或自动装箱（编译器会调用 `valueOf()`）而非 `new Integer()` 获取包装类实例。`new Integer()` 每次都创建新对象，违背了缓存设计的初衷。在循环中大量使用 `new Integer()` 会造成不必要的 GC 压力。

## 9. 面试高频考点

### 9.1 基础问题

**Q1：一个 `Object` 对象在 64 位 JVM 中占多少内存？**

| 场景 | Mark Word | Klass Pointer | 实例数据 | 对齐填充 | 总大小 |
|------|-----------|---------------|---------|---------|--------|
| 压缩指针开启（默认） | 8 bytes | 4 bytes | 0 | 4 bytes | **16 bytes** |
| 压缩指针关闭 | 8 bytes | 8 bytes | 0 | 0 | **16 bytes** |

巧合的是两种场景下都是 16 字节，但结构不同。答案通常为 **16 bytes**（64 位 JVM 默认）。

**Q2：对象创建过程中，哪个步骤保证线程安全？**

TLAB 机制优先，TLAB 空间不足时通过 CAS + 失败重试保证分配线程安全。

**Q3：实例变量在什么时候会被赋予初始值（0, null, false）？**

在**初始化零值**步骤（对象创建流程 Step 3），此时实例字段被设为零值，随后 `<init>` 方法中才会被赋予代码中指定的初始值。

### 9.2 进阶问题

**Q4：指针压缩的原理是什么？为什么堆超过 32GB 时自动关闭？**

对象地址始终 8 字节对齐，JVM 存储引用时右移 3 位（除以 8），使用时左移 3 位（乘以 8）。32 位无符号整数左移 3 位后最大表示 `2^32 × 8 = 32GB`，超过此范围地址无法用 32 位表示。

**Q5：JDK 8 中 `Integer a = 100` 和 `Integer b = 100` 是否相等？`Integer c = 200` 和 `Integer d = 200` 呢？**

`a == b` 为 true（缓存 -128~127），`c == d` 为 false（超出缓存范围）。但使用 `equals()` 比较值则始终相等。

**Q6：数组 `new boolean[0]` 占用多少内存？**

16 bytes（12 bytes 对象头 + 4 bytes 数组长度，即使长度为 0 也需要这 4 bytes 存储 `length` 字段）。

### 9.3 深度问题

**Q7：聊一聊 JVM 的锁升级过程？Mark Word 在其中如何变化？**

```
无锁(01) → 偏向锁(01 + 偏向位=1) → 轻量级锁(00) → 重量级锁(10)
                                          ↓
                                    (不可逆，锁只能升级不能降级)
```

Mark Word 在不同阶段存储不同内容：偏向锁存线程 ID，轻量级锁存 Lock Record 指针，重量级锁存 Monitor 指针。

**Q8：为什么 HotSpot 选择直接指针访问而非句柄访问？**

直接指针性能更好（一次内存寻址到位），这是 Java 高频操作（字段访问、方法调用）的核心优化路径。句柄访问虽在 GC 移动对象时更灵活，但多一次内存访问的成本在数亿次调用下不可忽视。HotSpot 通过 OopMap + Safepoint 机制高效管理 GC 后的引用更新。

**Q9：对象的分配是否一定在堆上？**

不一定。JIT 编译器通过**逃逸分析**（Escape Analysis）判定对象是否逃逸出方法作用域。如果对象不逃逸，可以进行：
- **栈上分配**：对象直接在栈帧上分配，方法结束后自动销毁
- **标量替换**：将对象拆解为基本类型字段，直接在栈上分配

```java
/**
 * 逃逸分析 + 栈上分配
 * 运行参数：-XX:+DoEscapeAnalysis（JDK 8+ 默认开启）
 * 验证：-XX:+PrintEliminateAllocations
 */
public class EscapeAnalysisDemo {

    public static void main(String[] args) {
        long start = System.currentTimeMillis();
        for (int i = 0; i < 10_000_000; i++) {
            createPoint(); // 方法内部创建，不逃逸
        }
        long end = System.currentTimeMillis();
        System.out.println("耗时: " + (end - start) + " ms");
    }

    // point 对象没有逃逸出 createPoint 方法
    // JIT 编译器可能将其进行标量替换：
    // 相当于直接在栈上分配 x 和 y 两个局部变量
    private static int createPoint() {
        Point point = new Point(1, 2); // 可能被优化为栈上分配
        return point.x + point.y;
    }

    static class Point {
        int x;
        int y;
        Point(int x, int y) {
            this.x = x;
            this.y = y;
        }
    }
}
```

> 🎯 **总结**：对象创建和内存布局是 JVM 的"基础架构"——理解了这个链路，才能深入理解 GC 策略、锁优化、内存占用分析等高阶话题。几个关键认知：TLAB 是小对象无锁分配的主力；Mark Word 是元数据弹性利用的典范；指针压缩是用空间换性能的经典权衡；直接指针是 HotSpot 性能至上的体现。
