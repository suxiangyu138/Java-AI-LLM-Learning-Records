## 1. 现代收集器概览：从CMS到低延迟

### 1.1 为什么CMS被淘汰

| 问题 | 描述 | 后果 |
|------|------|------|
| Concurrent Mode Failure | 并发标记期间老年代被填满 | 退化为Serial Old Full GC，停顿秒级 |
| 内存碎片化 | Mark-Sweep不整理 | 大对象分配失败 -> 提前Full GC |
| CPU敏感 | 与用户线程争抢CPU | 吞吐量下降10-20% |
| 浮动垃圾 | 并发清除阶段产生的新垃圾 | 需预留空间，提前触发GC |

> 💡 CMS的根本问题：**标记-清除的碎片化 + 无法控制并发标记期间的内存分配**。G1/ZGC/Shenandoah从不同角度解决了这些缺陷。

### 1.2 JDK版本演进

| 版本 | 默认收集器 | 关键变化 |
|------|-----------|---------|
| JDK 7 | Parallel Scavenge + Parallel Old | G1引入（实验性） |
| JDK 8 | Parallel Scavenge + Parallel Old | G1趋于成熟 |
| JDK 9 | **G1** | CMS标记为deprecated |
| JDK 11 | G1 | ZGC实验性引入 |
| JDK 14 | G1 | **CMS正式移除** |
| JDK 15 | G1 | ZGC转生产 |
| JDK 17 | G1 | ZGC生产就绪 |
| JDK 21 | G1 | 分代ZGC可用 |

### 1.3 现代收集器定位

```
延迟优先（ZGC/Shenandoah）       吞吐优先（Parallel）
         │                              │
         │    平衡型（G1）               │
         ▼         ▼                    ▼
    <1ms         ~200ms             容忍秒级
    金融交易     Web服务/微服务       批处理/数仓
```

| 收集器 | 目标停顿 | 核心创新 | 适用JDK |
|--------|---------|---------|---------|
| G1 | ~200ms | Region分区 + RSet + 停顿预测模型 | 9+（默认） |
| ZGC | <1ms | 染色指针 + 读屏障 + 并发重定位 | 15+（生产） |
| Shenandoah | <10ms | Brooks转发指针 + 并发整理 | 15+（OpenJDK） |
| Epsilon | 无GC | 零开销内存分配 | 11+（实验） |

> 🎯 **核心理念**：现代GC将**尽可能多的工作从STW移到并发阶段**，让停顿时间与堆大小解耦。

## 2. G1收集器：Region分区与RSet

### 2.1 Region布局

传统收集器是**物理连续**的分代堆。G1将堆划分为**大小相等的Region**（默认2048个），每个Region独立扮演Eden/Survivor/Old/Humongous角色：

```ascii
G1 Region布局（16个Region示例）：
┌─────┬─────┬─────┬─────┐
│  E  │  E  │  E  │  O  │    E = Eden  O = Old
├─────┼─────┼─────┼─────┤    S = Survivor  H = Humongous
│  O  │  O  │  E  │  S  │
├─────┼─────┼─────┼─────┤
│  H  │  H  │  O  │  O  │
├─────┼─────┼─────┼─────┤
│  O  │  O  │  E  │  E  │
└─────┴─────┴─────┴─────┘
```

**Region大小自动推导**：堆<4GB=1MB，4-8GB=2MB，8-16GB=4MB，依此类推至32MB上限。

> ⚠️ **Humongous对象**：大小 > Region的50%时直接分配到H区。频繁的巨型对象分配会触发提前GC，是G1的常见瓶颈。

### 2.2 RSet（Remembered Set）

每个Region维护一个RSet，记录**哪些外部Region引用了本Region中的对象**：

```ascii
Region O1                       Region E1
┌─────────────┐               ┌─────────────┐
│ Object A    │───引用─────→  │ Object B    │
└──────┬──────┘               └──────┬──────┘
       │              RSet of E1:   │
       └───→ Region O1引用了B       │
             Region O2引用了C        │
```

| 场景 | 无RSet | 有RSet |
|------|--------|--------|
| Young GC扫描跨区引用 | 扫描整个老年代 | 只扫描RSet中记录的Card |
| Mixed GC选择Region | 全量遍历 | 通过RSet快速计算引用关系 |

**实现层次**：Card Table（512字节粒度）-> Per Region RSet（哈希表，key=源Region，value=Card集合）。

> 💡 RSet是**空间换时间**：约占堆内存的5-20%，大堆上开销不可忽略。

## 3. G1的Young GC与Mixed GC流程

### 3.1 G1完整GC周期

```ascii
               ┌──────────────────────┐
               │    Young GC (常规)     │  ← Eden满触发
               │  - 并行复制存活对象     │
               └──────────┬───────────┘
                          │ IHOP阈值达到
                          ▼
               ┌──────────────────────┐
               │   并发标记周期         │
               │  1. Initial Mark(STW) │
               │  2. Concurrent Mark   │
               │  3. Remark(STW)       │
               │  4. Cleanup(STW)      │
               └──────────┬───────────┘
                          ▼
               ┌──────────────────────┐
               │    Mixed GC（多次）    │  ← 回收Young + 部分Old
               │  每次选垃圾最多的Region │
               └──────────┬───────────┘
                          ▼  停顿超限或分配失败
               ┌──────────────────────┐
               │    Full GC (串行)     │  ← G1退化，应极力避免
               └──────────────────────┘
```

### 3.2 Young GC vs Mixed GC

| 对比项 | Young GC | Mixed GC |
|--------|---------|---------|
| 回收范围 | Eden + Survivor | Eden + Survivor + **部分Old** |
| 触发条件 | Eden满 | 并发标记完成 + IHOP达标 |
| Region选择 | 所有Eden/Survivor | 所有Young + 垃圾最多的Old |
| 执行次数 | 每次Eden满 | 多次，直到垃圾回收完 |

**GC日志对比**：

```log
# Young GC（老年代不变）
[0.234s][info][gc] Pause Young (Normal)  Eden:128->0  Old:32->32  0.002s
# Mixed GC（老年代也减少）
[0.567s][info][gc] Pause Mixed           Eden:64->0   Old:20->12  0.003s
```

### 3.3 停顿预测模型

G1使用**衰减加权平均（EWMA）**预测停顿：

```java
class PausePredictionModel {
    static final double ALPHA = 0.5;
    double predictedMs = 0;

    void recordPause(long actualPauseMs) {
        predictedMs = ALPHA * actualPauseMs + (1 - ALPHA) * predictedMs;
    }
}
```

> ⚠️ 预测基于历史统计。负载剧烈变化（如突增流量）会导致预测失准，停顿超目标。

## 4. G1的SATB并发标记与三色标记

### 4.1 三色标记算法

并发标记的核心挑战：**用户线程不断修改引用关系时，如何保证标记准确？**

| 颜色 | 含义 | 结局 |
|------|------|------|
| 白色 | 尚未被GC访问 | 标记结束仍是白色 -> 垃圾 |
| 灰色 | 自身已访问，引用字段未扫完 | 中间状态，需继续遍历 |
| 黑色 | 自身和引用均扫描完成 | 存活 |

```
初始：  [Roots] -> [A(灰)] -> [B(白)]
                              [C(白)]
扫描A：[Roots] -> [A(黑)] -> [B(灰)] -> [D(白)]
                              [C(白)]
完成：  [Roots] -> [A(黑)] -> [B(黑)] -> [D(黑)]
                              [C(白)] <- 不可达
```

### 4.2 对象消失问题

并发标记期间，如果灰色A删除指向白色B的引用、同时黑色C新增指向B的引用，B会被漏标（实际存活却被回收）。两个条件缺一不可。

### 4.3 CMS解法：增量更新

**记录黑色对象新增的引用**，Remark阶段重新扫描，STW较长但精确。

### 4.4 G1解法：SATB

**记录灰色对象删除的引用**（写屏障记录到SATB缓冲区），Remark只处理缓冲区：

```java
void satbWriteBarrier(Object oldValue) {
    if (isConcurrentMarking() && isWhite(oldValue)) {
        currentThread().satbBuffer.add(oldValue);
    }
}
```

| 对比项 | CMS增量更新 | G1 SATB |
|--------|------------|---------|
| 记录时机 | 黑色->白色新增引用 | 灰色->白色删除引用 |
| 精度 | 高，不漏标 | 有浮动垃圾 |
| Remark停顿 | 较长 | 较短 |
| 本质 | 及时修正 | 允许误差，下周期纠正 |

> 💡 G1选择SATB是因为它在保证正确性的前提下，减少了Remark的STW时间，有利于停顿预测。

## 5. G1调优参数与最佳实践

### 5.1 核心参数

```bash
-XX:+UseG1GC                              # JDK 9+默认
-Xms8g -Xmx8g                             # 初始=最大，避免堆震荡
-XX:MaxGCPauseMillis=200                   # 目标停顿（默认200ms）
-XX:InitiatingHeapOccupancyPercent=45      # 触发并发标记的堆占用率
-XX:ConcGCThreads=N                        # 并发线程数（默认CPU/4）
-XX:ParallelGCThreads=N                    # STW并行线程数（默认CPU数）
-XX:G1ReservePercent=10                    # 预留空间
-XX:+ParallelRefProcEnabled                # 并行处理引用
-XX:+AlwaysPreTouch                        # 启动时预申请物理内存
-XX:G1HeapRegionSize=4m                    # Manual Region大小
```

### 5.2 调优三步走

```text
第一步：设定 MaxGCPauseMillis=100~300（太激进=频繁Young GC，降低吞吐）
第二步：观察指标——Young GC频率、Mixed GC频率、Full GC次数（目标0/天）
第三步：针对性调整
  Young GC太频繁（<10s/次） -> 增大堆或 G1MaxNewSizePercent
  Mixed GC不收敛           -> 降低IHOP提前触发
  出现 Full GC            -> 检查Humongous，增大ReservePercent或降低IHOP
```

### 5.3 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| Full GC频繁 | Humongous对象过多 | 增大Region Size或优化大对象 |
| Mixed GC不足 | IHOP设太高 | 降低至35-45% |
| Young GC过长 | 存活对象复制量大 | 检查过早晋升，调TenuringThreshold |

> ⚠️ G1 Full GC是退化串行GC，停顿极长。生产环境出现说明配置或代码存在严重问题。

### 5.4 实战配置

```bash
# 8C16G微服务模板
java -Xms8g -Xmx8g \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -XX:InitiatingHeapOccupancyPercent=45 \
     -XX:ConcGCThreads=4 -XX:ParallelGCThreads=8 \
     -XX:G1ReservePercent=10 -XX:+ParallelRefProcEnabled -XX:+AlwaysPreTouch \
     -XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/app/heapdump.hprof \
     -Xlog:gc*:file=/var/log/app/gc.log:tags,time,uptime:filecount=10,filesize=50m \
     -jar app.jar
```

## 6. ZGC收集器：染色指针技术

### 6.1 设计目标

- **STW < 1ms**（与堆大小无关）
- **最大堆4TB**（染色指针限制）
- **全部阶段并发**：标记、重定位、引用处理

### 6.2 染色指针（Colored Pointer）

这是ZGC最核心的创新。传统GC在**对象头**标记状态；ZGC将GC状态编码在**指针**中：

```ascii
64位染色指针布局（AMD64）：
┌────┬────┬────┬────┬──────────────────────────────────┐
│ M0 │ M1 │ R  │ 0  │         有效地址位 (42bit)        │
│ 45 │ 44 │ 43 │ 42 │       42-0 -> 4TB地址空间          │
└────┴────┴────┴────┴──────────────────────────────────┘

M0 = Mark Bit 0   第一次标记
M1 = Mark Bit 1   第二次标记
R  = Remapped     对象是否已被移动
0  = 保留位       指针压缩适配
```

**状态转换**：

```
分配:  Remapped=0  ->  并发标记: M0=1, Remapped=0  ->  重定位: M0=0, Remapped=1
   用户线程通过读屏障自动修正指针
```

### 6.3 为什么需要染色指针

| 问题 | 传统GC | ZGC解法 |
|------|--------|---------|
| 并发访问冲突 | 需修改对象头 | 不修改对象，只改指针元数据 |
| 对象移动后更新引用 | 遍历全堆修正 | 读屏障自动修正（自愈） |
| 元数据膨胀 | 对象头加字段 | 元数据在指针上，零空间开销 |

> 💡 **染色指针的本质**：**将GC元数据从对象内部移到外部（指针上）**，使GC和用户线程可并发操作同一对象而互不干扰。

## 7. ZGC的并发重定位与Load Barrier

### 7.1 工作流程

```ascii
                     STW                  并发                          STW
时间线 ───────────────┬─────────────────────┬───────────────────────────┬───►
                      │                     │
Pause Mark Start      │◀───并发标记─────→   │Pause Mark End
(标记GC Roots)        │                     │(处理弱/虚引用)
                      │                     │
Pause Relocate Start  │◀───并发重定位────→   │
(STW, 重置重定位集)    │ 后台线程逐步复制对象  │
                      │ 用户线程读屏障自愈    │
```

### 7.2 读屏障（Load Barrier）

ZGC是**读屏障**（读取引用时触发），而非G1/CMS的写屏障：

```java
Object zgcLoadBarrier(Object ref) {
    if (ref == null) return null;
    long ptr = (long) ref;

    if (isRemapped(ptr)) return ref;     // 已是最新位置
    if (isMarked(ptr)) { fixPointer(ref); return ref; }  // 自愈

    Object newRef = forwardingTable.get(ref);
    fixPointer(ref, newRef);             // 自愈：下次不再走屏障
    return newRef;
}
```

**自愈（Self-Healing）**：第一次访问触发屏障 -> 修正指针 -> 后续直接访问。访问压力越大，修正越快。

### 7.3 G1写屏障 vs ZGC读屏障

| 对比 | G1写屏障 | ZGC读屏障 |
|------|---------|-----------|
| 触发时机 | 引用**赋值**时 | 引用**读取**时 |
| 频率 | 读写比~1:10，数量少 | 频率高~10倍 |
| 优化 | 批量SATB缓冲区 | 自愈 + 快速路径（fast path） |

> ⚠️ ZGC读屏障由JIT内联为几条机器指令。快速路径在90%+情况下仅检查指针位，成本极低。

### 7.4 ZGC参数

```bash
java -XX:+UseZGC -Xms16g -Xmx16g \
     -XX:ConcGCThreads=4                          # 并发线程（默认CPU/2）
     -XX:ZAllocationSpikeTolerance=2.0            # 分配波动容忍度
     -XX:ZCollectionInterval=300                   # 最大GC间隔（秒）
     -XX:ZFragmentationLimit=25                    # 最大碎片率%
```

| 参数 | 默认 | 说明 |
|------|------|------|
| `ConcGCThreads` | CPU/2 | 越小CPU占用越低但GC变慢 |
| `ZAllocationSpikeTolerance` | 2.0 | 越大预留空间越多，减少GC |
| `ZFragmentationLimit` | 25 | 碎片率超此值触发重定位 |

## 8. ZGC分代模式（JDK 21+）

### 8.1 为什么需要分代

ZGC停顿极短但**吞吐量损失10-20%**（整个堆全量标记）。分代ZGC解决了这一问题：

| 对比 | 单代ZGC | 分代ZGC |
|------|---------|---------|
| 标记范围 | 整个堆 | 主要是新生代 |
| 停顿 | <1ms | <1ms（不变） |
| 吞吐量 | 损失10-20% | 接近G1 |
| 启用 | `-XX:+UseZGC` | `+ -XX:+ZGenerational` |

### 8.2 工作流程

```
新生代GC：Pause Mark Start(STW) -> Concurrent Mark(仅Young) -> Pause Mark End(STW) -> Concurrent Relocate
老年代GC：同上，但标记Old Region，频率更低
```

> 🎯 **分代ZGC的意义**：使ZGC从"极致低延迟但高代价"变为"极致低延迟且高吞吐"。

## 9. Shenandoah收集器：Brooks指针

### 9.1 技术路线对比

| 对比项 | Shenandoah | ZGC |
|--------|-----------|-----|
| 指针技术 | 普通64位指针 | 染色指针（依赖虚拟地址） |
| 屏障 | 写屏障（Brooks Pointer） | 读屏障 |
| 对象转发 | 对象头的Brooks指针 | 染色指针Remap位 |
| 硬件依赖 | 无 | 多级页表 |
| 堆上限 | ~512GB | 4TB |

### 9.2 Brooks转发指针

Shenandoah在**对象头部**增加一个转发指针：

```ascii
[ Mark Word(64bit) | Klass Ptr(32bit) | Brooks Ptr | ...数据 ]
                                           │
                                 正常 -> 指向自身
                                 移动 -> 指向新位置

对比：ZGC = [64位指针: M0|M1|R|0|地址]
     Shenandoah = [对象头: Mark|Klass|BrooksPtr]
```

### 9.3 工作流程（9个阶段，每个STW极短）

```
Init Mark(STW) -> Concurrent Mark -> Final Mark(STW) -> Concurrent Cleanup
-> Concurrent Evacuation(核心创新：并发复制) -> Init Update Refs(STW)
-> Concurrent Update Refs -> Final Update Refs(STW) -> Concurrent Cleanup
```

**与G1的核心差异**：G1的整理阶段是STW的，而Shenandoah**完全并发**。

### 9.4 写屏障

```java
void shenandoahWriteBarrier(Object obj) {
    Object actualObj = obj.brooksPointer();
    if (actualObj == obj) return;  // 未移动，正常写入
    fixReference(obj, actualObj);  // 自愈：修正引用后写入新位置
}
```

### 9.5 参数

```bash
java -XX:+UseShenandoahGC \
     -XX:ShenandoahGCMode=iu              # iu=增量更新，默认SATB
     -XX:ShenandoahGarbageThreshold=15     # Region垃圾占比阈值
     -XX:ConcGCThreads=4
```

## 10. Epsilon收集器：无操作GC

Epsilon（JDK 11+实验性）**不执行任何回收**，堆满即OOM：

```bash
-XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC
```

| 特性 | 说明 |
|------|------|
| 回收 | **永不回收** |
| GC线程 | 0（无STW） |
| 内存开销 | 极低 |

**适用场景**：性能测试（排除GC干扰）、内存压力测试、极短生命周期任务。

> ⚠️ 绝对不能用于生产。它只回答"如果GC不存在，程序能跑多快"。

## 11. 收集器选型决策树

### 11.1 选型流程

```ascii
                    你的应用需要什么？
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
     ┌──────────┐    ┌──────────┐    ┌──────────┐
```

### 11.2 选型速查

| 场景 | 堆大小 | 推荐 | 理由 |
|------|--------|------|------|
| Web微服务 | 4-16GB | **G1**（默认） | 平衡吞吐和延迟 |
| 高性能交易 | 16-512GB | **ZGC** | <1ms停顿，TB级堆 |
| OpenJDK低延迟 | 4-64GB | **Shenandoah** | 无硬件依赖 |
| 离线批处理 | 16-128GB | **Parallel GC** | 吞吐优先 |
| 云原生容器 | 256MB-4GB | **G1**或Serial | 小堆G1即可 |
| 性能测试 | 按需 | **Epsilon** | 消除GC噪声 |

> 🎯 **选型铁律**：80%的应用用G1默认参数就够了。只有延迟极致要求（<10ms）才考虑ZGC/Shenandoah。每次切换需全面性能验证。

## 12. 面试高频考点

### 12.1 G1核心

**Q1: G1如何实现可预测的停顿时间？**

基于EWMA衰减加权平均的**停顿预测模型**，优先选择垃圾最多的Region加入CSet，使总停顿逼近`MaxGCPauseMillis`。

**Q2: RSet解决了什么问题？**

**跨Region引用扫描效率**。无RSet时Young GC需扫描整个老年代；有RSet只需扫描记录的Card，复杂度从O(OldGen)降到O(CrossRef)。

**Q3: SATB vs 增量更新？**

| 对比 | 增量更新（CMS） | SATB（G1） |
|------|---------------|-----------|
| 记录 | 黑色->白色新增引用 | 灰色->白色删除引用 |
| 精度 | 高，不漏标 | 有浮动垃圾 |
| Remark STW | 较长 | 较短 |
| 本质 | 及时修正 | 允许误差，下周期纠正 |

### 12.2 ZGC核心

**Q4: 染色指针怎么工作？**

利用64位指针高4位（M0/M1/R/0）编码GC元数据。M0/M1标记存活，R标识移动状态。用户线程通过读屏障读取指针位判断对象状态，无需访问对象头。

**Q5: 读屏障自愈是什么？**

第一次访问已移动对象时触发屏障，自动将引用修正为新地址。后续访问直接命中，不再走屏障。**访问压力越大，修正越快**。

**Q6: ZGC为何能做到<1ms停顿？**

设计哲学：**除GC Roots标记和弱引用处理外，全部并发**。染色指针使GC和用户线程无需互斥；读屏障自愈让引用修正也无需STW。

### 12.3 Shenandoah核心

**Q7: Brooks指针 vs 染色指针？**

| 对比 | Brooks指针 | 染色指针 |
|------|-----------|---------|
| 位置 | 对象头部 | 64位指针本身 |
| 硬件依赖 | 无 | 需多级页表 |
| 堆上限 | ~512GB | 4TB |

**Q8: Shenandoah和G1的核心差异？**

G1的**整理阶段是STW的**，Shenandoah的**整理阶段完全并发**（Concurrent Evacuation），这是其停顿更短的根本原因。

### 12.4 选型与调优

**Q9: 8C16G Web服务选什么收集器？**

首选**G1**：`-Xms8g -Xmx8g -XX:MaxGCPauseMillis=200`。极致延迟要求（如支付）切ZGC。

**Q10: G1出现Full GC怎么办？**

1. Humongous对象：增大`G1HeapRegionSize`或优化业务
2. 并发标记来不及：降低`IHOP`至35%
3. 存活对象太多：调大`G1MixedGCLiveThresholdPercent`
4. 预留不足：增大`G1ReservePercent`至15%

**Q11: ZGC vs 分代ZGC？**

| 场景 | 推荐 |
|------|------|
| JDK 17以下，极致低延迟 | ZGC（单代） |
| JDK 21+，低延迟+高吞吐 | **分代ZGC**（`-XX:+ZGenerational`） |
| 堆>4TB | 无法ZGC，考虑G1或Shenandoah |

> 🎯 **面试加分点**：能说出"G1停顿模型基于EWMA"、"ZGC读屏障自愈使压力分散"、"分代ZGC解决吞吐量痛点"——体现对设计哲学的深度理解。
