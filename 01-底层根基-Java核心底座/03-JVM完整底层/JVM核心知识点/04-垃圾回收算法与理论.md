## 1. 垃圾回收概述：手动 vs 自动

### 1.1 手动内存管理的痛点

```c
// C语言：开发者必须手动管理内存
void* ptr = malloc(1024);
// 使用 ptr ...
free(ptr);              // 必须手动释放，否则内存泄漏
ptr->data = 42;         // free后继续使用 → 悬垂指针，未定义行为
```

| 手动管理问题 | 后果 |
|-------------|------|
| 内存泄漏 (Memory Leak) | 忘记释放 → OOM |
| 悬垂指针 (Dangling Pointer) | 释放后继续使用 → 程序崩溃 |
| 双重释放 (Double Free) | 同一内存释放两次 → 堆结构损坏 |
| 内存碎片化 | 频繁分配释放 → 大对象分配失败 |

### 1.2 Java 自动内存管理

```java
// Java：自动内存管理，开发者无需关心释放
void method() {
    byte[] data = new byte[1024];
    // 使用 data ...
    // 方法结束后，data 对象不再可达，JVM 自动回收
}
```

> 💡 GC 把开发者从内存管理中解放出来，但代价是引入了**停顿时间**和**CPU开销**。理解 GC 才能在**吞吐量**和**延迟**之间做出合理 trade-off。

## 2. 判断对象存活的两种方法

### 2.1 Reference Counting（引用计数法）

**原理**：每个对象维护引用计数器，被引用 +1，失效 -1，为 0 时回收。

```
  ╔══════════╗     +1    ╔══════════╗
  ║ 对象 A   ║◀─────────║ 引用者 1 ║
  ║ refCount ║          ║          ║
  ║ = 2      ║     +1    ║          ║
  ║          ║◀─────────║ 引用者 2 ║
  ╚══════════╝          ╚══════════╝
```

| 优点 | 缺点 |
|------|------|
| 实现简单，实时性高 | **循环引用无法回收** |
| 停顿时间短 | 每次引用修改有额外开销，多线程同步成本高 |

```java
// 循环引用陷阱：a.ref = b, b.ref = a → 计数器永不为 0，无法回收
```

> ⚠️ **Java HotSpot 没有采用引用计数法**，而是使用可达性分析，从根源上避免了循环引用问题。

### 2.2 Reachability Analysis（可达性分析法）— HotSpot 采用

**原理**：以一系列称为 **GC Roots** 的根对象为起点，向下搜索引用链，不可达的对象即为垃圾。

```
GC Roots 集合
  ┌─────────┐
  │ Root 1  │───▶ 对象 A ──▶ 对象 B
  ├─────────┤              │
  │ Root 2  │───▶ 对象 C    └──▶ 对象 D (可达)
  └─────────┘
               对象 F (不可达，被回收)
               对象 G ──▶ 对象 H (循环引用，皆不可达 → 同时回收)
```

> 🎯 **判定公式**：存活 = 从 GC Roots 出发能到达该对象。死亡 = 从 GC Roots 出发无法到达。

## 3. GC Roots详解与枚举

### 3.1 GC Roots 的 7 大类来源

```
┌──────────────────────────────────────────────────┐
│                    GC Roots                       │
├──────────────────────────────────────────────────┤
│ ① 虚拟机栈引用：栈帧中局部变量表引用的对象          │
│ ② 静态引用：方法区中类的静态属性引用的对象          │
│ ③ JNI 引用：本地方法栈中 JNI 引用的对象            │
│ ④ 活跃线程：所有尚未终止的 Thread 对象              │
│ ⑤ 同步锁：被 synchronized 持有的对象                │
│ ⑥ JVM 内部引用：系统类加载器、常驻异常对象等          │
│ ⑦ 被 GC 管理的 JNI Monitor 等                      │
└──────────────────────────────────────────────────┘
```

```java
public class GCRootsDemo {
    private static SomeObject staticObj = new SomeObject();  // ① 静态引用

    public void method() {
        SomeObject localObj = new SomeObject();              // ② 栈引用
    }

    public static void main(String[] args) {
        Thread t = new Thread(() -> {
            synchronized (GCRootsDemo.class) {                // ③ 同步锁
            }
        });
        t.start();                                            // ④ 活跃线程
    }
}
```

### 3.2 GC Roots 枚举与 OopMap

> 💡 **枚举** GC Roots 是 GC 的起点，必须**暂停所有用户线程（STW）**，因为引用关系在枚举过程中不能变化。

**优化手段 — OopMap**：HotSpot 使用 OopMap（对象引用映射表）避免逐个扫描栈帧判断每个位置是否引用。OopMap 在 **JIT 编译时** 生成，记录栈中哪些位置是对象引用。GC 时直接查询 OopMap，实现**准确式 GC（Exact GC）**。

```
GC Roots 枚举流程：
  SafePoint → STW → 查 OopMap → 枚举 Roots → 遍历对象图 → 标记存活对象
```

**SafePoint（安全点）**：线程只有在到达 SafePoint 时才能暂停执行进行 GC。选择原则：既不能太少（GC 等待长），也不能太多（运行时开销大）。通常设在循环结束、方法调用、异常跳转处。

## 4. 四种引用类型：强/软/弱/虚引用

### 4.1 引用类型总览

| 引用类型 | 实现类 | 回收时机 | 典型用途 |
|----------|--------|---------|----------|
| **强引用** | 默认引用 | 永不回收（只要可达） | 普通 `new` 对象 |
| **软引用** | `SoftReference` | OOM 前回收 | 内存敏感缓存 |
| **弱引用** | `WeakReference` | 下一次 GC 立即回收 | `WeakHashMap`、`ThreadLocal` |
| **虚引用** | `PhantomReference` | 随时可能，`get()`永远 null | 资源清理追踪、堆外内存 |

**回收强度**：`强引用 < 软引用 < 弱引用 < 虚引用`

```
GC 时的引用链判定：
  GC Roots → 强引用对象(不可回收) → 软引用对象(OOM前回收) → 弱引用对象(下次GC必回收) → 虚引用对象(get()永远null, queue通知)
```

### 4.2 强引用

```java
Object obj = new Object();  // 永不回收（除非 obj = null 解除引用）
```

### 4.3 软引用

```java
// 软引用：内存充足时不回收，OOM 前回收
Object strongRef = new Object();
SoftReference<Object> softRef = new SoftReference<>(strongRef);
strongRef = null;
System.gc();
System.out.println(softRef.get());  // 内存充足时仍非 null
```

```java
// 软引用实现内存敏感缓存
public class SoftCache<K, V> {
    private final Map<K, SoftReference<V>> cache = new HashMap<>();

    public V get(K key) {
        SoftReference<V> ref = cache.get(key);
        return ref != null ? ref.get() : null;  // 若被回收则返回 null
    }

    public void put(K key, V value) {
        cache.put(key, new SoftReference<>(value));
    }
}
```

> 💡 **软引用适合做缓存**：内存充足时正常使用，即将 OOM 时自动释放，避免应用崩溃。

### 4.4 弱引用

```java
// 弱引用：下一次 GC 必回收
Object key = new Object();
WeakHashMap<Object, String> map = new WeakHashMap<>();
map.put(key, "value");
key = null;
System.gc();
System.out.println(map.size());  // 0，Entry 被自动清理
```

**经典应用场景**：`WeakHashMap`、`ThreadLocalMap.Entry`（key 为弱引用）、`ServiceLoader` provider 缓存。

> ⚠️ **ThreadLocal 内存泄漏**：Entry 的 key 是弱引用，但 **value 是强引用**。`threadLocal = null` 后 key 被回收，但 value 仍被 Entry 强引用无法释放。**使用后务必 `remove()`**。

```java
ThreadLocal<String> tl = new ThreadLocal<>();
try {
    tl.set("value");
    // 使用 ...
} finally {
    tl.remove();  // 防止内存泄漏
}
```

### 4.5 虚引用

```java
// 虚引用：get() 永远返回 null，对象回收后放入 ReferenceQueue
Object obj = new Object();
ReferenceQueue<Object> queue = new ReferenceQueue<>();
PhantomReference<Object> phantomRef = new PhantomReference<>(obj, queue);
obj = null;
System.gc();
Reference<?> ref = queue.remove(1000);  // 对象回收后收到通知
```

> 🎯 **虚引用核心应用**：NIO 的 `DirectByteBuffer` 通过虚引用管理堆外内存释放，`Cleaner` 线程在虚引用入队后执行对应清理操作。

## 5. finalize()的自我救赎（已废弃）

### 5.1 对象的"两次标记"过程

```
第一次标记 → 可达性分析发现对象不可达
    │
    ├── 未覆盖 finalize() 或已被调用过 → 直接回收
    │
    └── 覆盖 finalize() 且未被调用 → 放入 F-Queue 低优先级队列
                                      │
第二次标记 → F-Queue 中的 finalize() 被执行
    │
    ├── finalize() 中 this 重新被引用 → 对象"复活"，移出回收集合
    │
    └── 仍未复活 → 回收
```

### 5.2 对象"复活"演示

```java
public class ResurrectionDemo {
    private static ResurrectionDemo SAVED;

    @Override
    protected void finalize() throws Throwable {
        SAVED = this;  // 对象"复活"
    }

    public static void main(String[] args) throws Exception {
        ResurrectionDemo obj = new ResurrectionDemo();
        obj = null;
        System.gc();
        Thread.sleep(100);
        System.out.println(SAVED != null ? "复活了" : "已回收");  // 复活了

        // 第二次释放：finalize() 只执行一次，无法再次复活
        SAVED = null;
        System.gc();
        Thread.sleep(100);
        System.out.println(SAVED != null ? "复活" : "已回收");    // 已回收
    }
}
```

### 5.3 finalize() 的缺陷与替代方案

| 问题 | 说明 |
|------|------|
| 执行时机不确定 | JVM 不保证何时调用，甚至可能不调用 |
| 性能差 | 需额外 GC 周期 |
| 对象复活 | 将 this 赋给静态变量导致逃逸 |
| 只执行一次 | 二次回收时不再执行 |
| 异常被吞 | 抛出异常不传播 |

> ⚠️ **finalize() 已在 JDK 9 标记废弃，JDK 18 正式移除**。资源清理应使用 `try-with-resources`（`AutoCloseable`）或 `Cleaner`（JDK 9+）。

## 6. 标记-清除算法

### 6.1 算法描述

**Mark-Sweep** 是最基础的 GC 算法，分两个阶段：

1. **标记（Mark）**：从 GC Roots 出发，标记所有可达对象
2. **清除（Sweep）**：遍历整个堆，回收所有未被标记的对象

```
初始状态（A、C 存活）：   标记后：                清除后（碎片）：
┌────┬────┬────┬────┐  ┌────┬────┬────┬────┐  ┌────┬────┬────┬────┐
│ A  │ B  │ C  │ D  │  │ ▓A▓│ B  │ ▓C▓│ D  │  │ ▓▓ │空闲│ ▓▓ │空闲│
└────┴────┴────┴────┘  └────┴────┴────┴────┘  └────┴────┴────┴────┘
                                                  ↑     ↑
                                               内存碎片
```

### 6.2 分析

| 优点 | 缺点 |
|------|------|
| 算法简单，实现成本低 | **内存碎片化严重** — 无法分配大对象 |
| 不需要移动对象 | **分配效率低** — 需空闲链表，无法指针碰撞 |
| 存活对象少时效率尚可 | 标记/清除效率随对象数量增加而降低 |

> ⚠️ 碎片化可能导致紧接着分配大对象时找不到连续空间而**提前触发另一次 GC**。

**使用场景**：CMS 收集器的并发清除阶段。

## 7. 标记-复制算法

### 7.1 算法描述

**Mark-Copy**：将可用内存分为两块，每次只用一块。用完时将存活对象复制到另一块，再清理已用空间。

**HotSpot 优化**：新生代划分 `Eden : S0 : S1 = 8 : 1 : 1`，每次使用 Eden + 一块 Survivor（From），另一块 Survivor（To）空闲。

```
GC 前（Eden 满）：           Minor GC 后：
┌──────┬────┬────┐          ┌──────┬────┬────┐
│Eden满 │S0  │S1空│          │空闲  │S0空│S1  │
│A,B,CD │  F │    │          │      │    │A,F │
└──────┴────┴────┘          └──────┴────┴────┘
       存活: A,F → S1           交换 S0/S1 角色
```

**分配担保（Handle Promotion）**：Survivor 空间不足时，溢出对象直接晋升到老年代。

### 7.2 分析

| 优点 | 缺点 |
|------|------|
| **无内存碎片** — 连续排列 | **内存浪费** — 始终部分空间空闲（优化后仅 10%） |
| **分配效率高** — 指针碰撞 | **存活率高时效率骤降**（>50% 不适用） |

> 💡 **新生代为什么用复制算法**：98%+ 对象很快死亡，只有少量存活，复制成本极低。存活率高时复制算法性价比差，不适合老年代。

**使用场景**：所有新生代收集器（Serial、ParNew、Parallel Scavenge）的 Young GC，G1 的 Young/Mixed GC。

## 8. 标记-整理算法

### 8.1 算法描述

**Mark-Compact** 在标记-清除基础上增加**整理**阶段：将所有存活对象向内存一端移动，再清理边界以外的内存。

```
标记存活对象（A、C 存活）：   整理后（紧凑排列）：
┌────┬────┬────┬────┐       ┌────┬────┬────┬────┐
│ A  │ B  │ C  │ D  │       │ A  │ C  │空闲│空闲│
└────┴────┴────┴────┘       └────┴────┴────┴────┘
                                    ↑ 指针碰撞
```

### 8.2 分析

| 优点 | 缺点 |
|------|------|
| **无内存碎片** | **停顿时间长** — 移动对象 + 更新引用需 STW |
| **内存利用率高** — 无需预留空间 | 实现复杂 |
| **指针碰撞分配** | 吞吐量可能低于复制算法 |

> 🎯 标记-整理是 **"用停顿时间换空间"** 的代表。

**使用场景**：Serial Old、Parallel Old 老年代收集，CMS 退化时退化为 Serial Old Full GC。

## 9. 三种GC算法对比总结

### 9.1 核心维度对比

| 维度 | 标记-清除 | 标记-复制 | 标记-整理 |
|------|-----------|-----------|-----------|
| **内存碎片** | 严重 | 无 | 无 |
| **内存利用率** | 高 | 低（浪费部分空间） | 高 |
| **分配方式** | 空闲链表 | 指针碰撞 | 指针碰撞 |
| **吞吐量** | 中 | 高 | 低 |
| **STW 停顿** | 中 | 短 | 长 |
| **移动对象** | 不移动 | 移动 | 移动 |
| **存活率影响** | 无关 | 存活越多越慢 | 存活越多越慢 |
| **实现复杂度** | 低 | 中 | 高 |

### 9.2 算法选择决策

```
对象存活率
 ├── 低（< 50%，如新生代）→ 标记-复制 ✅
 └── 高（> 50%，如老年代）
     ├── 可接受长停顿 → 标记-整理 ✅
     └── 追求低延迟 → 标记-清除 ✅（需处理碎片）
```

> ⚠️ **没有完美算法**：清除了碎片必然增加停顿，要低延迟就得忍受碎片。现代收集器结合多种算法，在不同阶段使用不同策略取得平衡。

## 10. 分代收集理论

### 10.1 三个核心假说

| 假说 | 内容 | 含义 |
|------|------|------|
| **弱分代假说** | 绝大多数对象"朝生夕死" | 98%+ 对象很快死亡，不值得频繁扫描 |
| **强分代假说** | 熬过越多次 GC 的对象越难回收 | 存活越久越稳定，降低扫描频率 |
| **跨代引用假说** | 跨代引用相对同代引用极少 | 无需扫描整个老年代来标记新生代引用 |

### 10.2 分代结构

```
                     Java Heap
├──────────────────────┬──────────────────────────┤
│      新生代 (Young)   │      老年代 (Old)         │
├────────┬──────┬──────┤                          │
│  Eden  │ S0  │ S1  │                            │
│ (80%)  │(10%) │(10%)│                            │
└────────┴──────┴──────┴──────────────────────────┘

Eden : S0 : S1 = 8 : 1 : 1  (-XX:SurvivorRatio)
新生代 : 老年代 = 1 : 2      (-XX:NewRatio=2)
```

**对象年龄演进**：Eden(age=0) -> Minor GC -> S0(age=1) -> Minor GC -> S1(age=2) -> ... -> age >= MaxTenuringThreshold(默认15) -> Old Gen

| 代 | 回收频率 | 算法 | 原因 |
|----|---------|------|------|
| 新生代 | 频繁（Minor GC） | 标记-复制 | 存活率低，复制成本小 |
| 老年代 | 低频（Major/Full GC） | 标记-清除 或 标记-整理 | 存活率高，需高空间利用率 |

### 10.3 跨代引用问题

**问题**：老年代->新生代的引用在 Young GC 时若被忽略，会导致存活对象被误判为垃圾。

**解决方法**：使用**记忆集（Remembered Set）**记录老年代指向新生代的引用。Young GC 只需扫描 GC Roots + 记忆集，无需全量扫描老年代。

## 11. 记忆集（Remembered Set）与卡表（Card Table）

### 11.1 记忆集的作用

记录**从非收集区域指向收集区域的指针**，避免全量扫描老年代。

```
无记忆集：   GC Roots → 老年代（全量扫描所有对象找跨代引用）→ 新生代
有记忆集：   GC Roots → RSet（精确知道哪些卡片有跨代引用）→ 新生代
```

### 11.2 卡表（Card Table）— HotSpot 实现

**卡表**是记忆集的一种具体实现：堆划分为 512 字节的**卡页（Card Page）**，卡表是一个字节数组，每个元素对应一个卡页，标记该页是否有跨代引用。

```
堆内存（按卡页划分）：
┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│  Card 0  │  Card 1  │  Card 2  │  Card 3  │  Card 4  │  Card 5  │  ...
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘

卡表（byte数组）：
┌──────┬──────┬──────┬──────┬──────┬──────┐
│  0   │  1   │  0   │  0   │  1   │  0   │  ...
└──────┴──────┴──────┴──────┴──────┴──────┘
        ↑                    ↑
      脏页(有跨代引用)      脏页
```

**写屏障**：对象引用修改时自动将对应卡页标记为脏，无需每次 GC 时全量扫描。

### 11.3 G1 的 RSet

G1 的 RSet 更精细——记录**其他 Region 中每个 Card** 对本 Region 的引用：

```
Region A 的 RSet：
  From Region B: Card 10, Card 15
  From Region C: Card 3, Card 7
```

> 💡 **空间换时间**：RSet/Card Table 使用额外内存（约堆的 1-5%）记录引用信息，避免扫描整个老年代，大幅减少 STW 时间。

| 屏障类型 | 用途 | 收集器 |
|----------|------|--------|
| **写屏障** | 引用赋值时触发，维护 RSet/Card Table | CMS、G1（SATB）、Parallel |
| **读屏障** | 读取引用时触发，处理并发重定位 | ZGC（着色指针）、Shenandoah |

## 12. Minor GC / Major GC / Full GC 对比

### 12.1 GC 类型

| GC 类型 | 区域 | 触发条件 | 特征 |
|---------|------|---------|------|
| **Minor / Young GC** | 新生代 | Eden 满 | 最频繁，停顿最短（ms级），复制算法 |
| **Major / Old GC** | 老年代 | 老年代空间不足 | 较慢，CMS 并发模式可能触发 |
| **Full GC** | 整个堆 + 元空间 | 多种条件 | 最慢（百 ms ~ 几秒），需尽量避免 |
| **Mixed GC** | Young + 部分 Old | 达 IHOP 阈值 | G1 特有 |

### 12.2 Full GC 触发因素

```
Full GC 触发因素：
  Old Gen 空间不足           ← 最常见
  Metaspace 空间不足         ← 动态生成类过多
  System.gc() / Runtime.gc() ← 建议 -XX:+DisableExplicitGC
  CMS Concurrent Mode Failure ← CMS 并发标记时老年代被填满
  G1 Promotion Failed        ← 晋升时无足够空间
  分配担保失败                ← 新生代晋升时老年代不够
```

### 12.3 执行过程对比

```
Minor GC：Eden满 → 标记存活对象(GC Roots + RSet) → 复制到 To(或晋升) → 清空 Eden+From → 交换 From/To

Full GC：STW → 标记整个堆+元空间 → 整理/复制存活对象 → 更新引用 → 恢复线程
```

> ⚠️ **生产环境 Full GC 标准**：每天不超过 1 次，单次 < 1 秒。频繁 Full GC 往往是内存泄漏或参数配置不当。

## 13. 面试高频考点

### 13.1 基础问题

**Q1：如何判断一个对象是否可回收？**

可达性分析：从 **GC Roots**（栈引用/静态引用/JNI引用/活跃线程/同步锁等）出发搜索引用链，不可达即为垃圾。

**Q2：四种引用类型的区别？**

| 类型 | 回收时机 | `get()` | 应用 |
|------|---------|---------|------|
| 强 | 永不 | 对象 | `new` |
| 软 | OOM 前 | 对象（内存充足时） | 缓存 |
| 弱 | 下次 GC | 对象（GC 前） | WeakHashMap、ThreadLocal |
| 虚 | 随时 | 永远 null | 资源清理追踪 |

**Q3：三种基础 GC 算法的核心区别？**

- **标记-清除**：产生碎片，不移动对象
- **标记-复制**：无碎片但浪费空间，适合存活率低的场景
- **标记-整理**：无碎片但停顿最长，适合老年代

### 13.2 进阶问题

**Q4：跨代引用如何解决？**

使用**记忆集**（HotSpot 通过**卡表**实现）。写屏障在引用修改时记录脏页，GC 时只扫描脏页区域，避免全量扫描老年代。

**Q5：Minor GC vs Full GC？**

- Minor GC：新生代，Eden 满触发，复制算法，频繁但停顿短
- Full GC：整个堆+元空间，多种原因触发，不频繁但停顿极长

**Q6：对象何时晋升到老年代？**

| 条件 | 说明 |
|------|------|
| 年龄阈值 | `-XX:MaxTenuringThreshold`，默认 15 |
| 动态年龄判定 | 同龄总和 > Survivor 50%，>= 该年龄晋升 |
| 分配担保 | Survivor 空间不足时溢出晋升 |
| 大对象 | `-XX:PretenureSizeThreshold` 超阈值直接老年代分配 |

**Q7：什么是 SafePoint？**

安全点是线程可暂停执行进行 GC 的位置。所有线程须到达 SafePoint 才能 STW。选在循环结束、方法调用、异常跳转等处。

### 13.3 深度问题

**Q8：三色标记法是什么？CMS 和 G1 如何处理对象消失问题？**

| 颜色 | 含义 |
|------|------|
| 白色 | 未被 GC 访问（最终仍白色 = 可回收） |
| 灰色 | 自身已扫，引用未扫完 |
| 黑色 | 自身+引用都扫完 |

**对象消失问题**：并发标记期间灰色->白色被删，黑色新增->白色，导致该白色被误回收。

| 收集器 | 方案 | 原理 |
|--------|------|------|
| CMS | 增量更新 | 黑色新增指向白色时，将其变回灰色重新扫 |
| G1 | SATB | 记录开始时快照，并发期删除的引用被记录，确保不漏标 |

**Q9：记忆集和卡表是同一个东西吗？**

不是。**记忆集**是抽象概念（记录跨代指针），**卡表**是具体实现（字节数组）。G1 的 RSet 是更精细的记忆集实现。

**Q10：频繁 Full GC 如何排查？**

1. `jstat -gcutil <pid> 1000` 看各代使用率
2. `jmap -histo:live <pid>` 看存活对象
3. 分析 GC 日志（GCeasy）
4. `-XX:+HeapDumpOnOutOfMemoryError` + MAT 分析
5. 检查业务代码：静态集合、ThreadLocal 未 remove、未关闭资源、缓存无限增长
