## 1. 真实案例复盘：反向海淘黑五大促

2025 黑五，某反向海淘系统踩了教科书式的坑：**1688 API 因请求量过大间歇性超时，超时率 15%**。此时系统没有熔断保护——超时请求不释放 Tomcat 线程，线程池逐渐占满，正常请求排队，RT 恶性上升，部分服务不可用，险些整体雪崩（[雪崩链条](01-分布式高并发全景与雪崩链条.md)的完整重演）。

修复动作正是本专题的四道防线：**QPS 限流**（网关层挡总量）+ **熔断降级**（慢调用比例熔断，自动转队列兜底）+ **系统负载保护**（CPU/负载自适应限流）。结果：**API 超时率从 15% 压到 2%，P99 220ms，可用性 99.95%+**。注意一个细节：15%→2% 不是"把故障修好了"，而是"把故障关在笼子里"——下游 API 该抖动还是抖，只是抖动不再放大成雪崩。这就是防护体系与修复的区别：**防护永远比修复快**。

## 2. 大促全链路防护方案

把四道防线铺到请求全链路，一个可复制的部署模板：

1. **客户端层**：按钮防重复提交（前端限流），降低无谓流量。
2. **接入层**：Nginx IP 限流（漏桶/计数），挡 DDoS 与单 IP 刷量；大促前 10 分钟开 WarmUp 预热（[02 篇](02-扩展模式与容量边界.md)）。
3. **网关层**：Sentinel gw-flow 或 Redis Lua 全局限流（接口维度，阈值 = 压测拐点 × 0.7-0.8）。
4. **应用层**：Sentinel/Resilience4j 注解——方法级限流 + 热点参数限流（防单商品打满）+ 熔断（慢调用/异常比例）+ 信号量隔离。
5. **数据层**：连接池保护（Hikari 上限）、慢 SQL 兜底降级（读降级到缓存）、MQ 削峰写链路。
6. **预案层**：L1/L2/L3 降级预案演练（[07 篇](07-降级与兜底预案：分级设计.md)）、监控大盘 + 告警（限流命中率、熔断状态、降级次数、P99 劣化）。

配套的**演练节奏**决定方案能否在故障时真的生效：T-30 完成全链路压测并锁定各层阈值；T-14 做一轮故障演练（人为注入下游故障，验证熔断→降级→恢复全链路自动流转，顺带检验告警是否真的有人响应）；T-7 复查规则配置与 Nacos 持久化（配置漂移是临战前最常见的坑）；T-1 开启预热限流并核对监控大盘。演练的原则是**每次故障注入都要求"不改代码只改开关"就能止血**——如果演练中发现需要发版才能修复，说明预案没设计到位。

## 3. 配置基线清单

| 项目 | 基线值 | 依据 |
|---|---|---|
| 限流阈值 | 压测拐点 × 0.7-0.8 | [02 篇](02-扩展模式与容量边界.md) |
| 熔断错误率阈值 | 50% + 最小调用数 10-20 | [06 篇](06-熔断机制：状态机与参数设计.md) |
| 慢调用阈值 | P99 × 2-3 | 监控数据推导 |
| 熔断等待期 | 5-10 秒 | 下游恢复窗口 |
| 半开探测数 | 5-10 | 样本量与压力权衡 |
| 超时金字塔 | DNS 500ms → 建连 500ms → 读写 1-1.5s，总超时 < 链路预算 | [08 篇](08-隔离与舱壁：线程池与信号量.md) |
| 降级触发 | L1 >5% / L2 >15% / L3 >30% 延迟劣化 | 分级预案 |
| 重试 | 幂等 + 指数退避，上限 3 次，CLOSED 态才允许 | [06 篇](06-熔断机制：状态机与参数设计.md) |
| 限流故障语义 | 核心链路 fail-closed | [05 篇](05-分布式限流：Redis与多级限流.md) |

## 4. 故障速查表

| 现象 | 第一怀疑 | 处置 |
|---|---|---|
| 限流该挡没挡住 | key 维度错误/时间偏差/fail-open | 查 key 拼接与 TIME 来源，改 fail-closed |
| 熔断频繁误触 | 慢调用阈值拍脑袋/minimumNumberOfCalls 太小 | 用真实 P99×2-3 重设，加最小调用数 |
| 线程池打满 | 慢调用无超时/无隔离 | 先补超时金字塔，再加舱壁隔离 |
| 雪崩征兆（RT 恶性上升） | 无熔断或熔断参数失效 | 立即主动降级 L2/L3，确认熔断生效 |
| 降级了但用户仍报错 | fallback 本身挂了（单点） | fallback 改链式多级，加监控告警 |
| 限流后体验暴差 | 直接拒绝无兜底 | 限流拒绝返回 429 + Retry-After，配排队模式 |

## 5. 毕业检查单

- 能画出自己系统的雪崩传播路径与四道防线落点
- 限流阈值来自压测数据（0.7-0.8），不是拍脑袋
- 限流实现无竞态（Lua/框架），时间基准统一，故障语义明确
- 熔断参数由真实 P99 推导，最小调用数防误触，上线前演练过
- 降级预案 L1/L2/L3 有量化触发信号与完整兜底链，开关可动态下发
- 核心依赖有隔离（线程池或信号量），超时金字塔完整
- 限流/熔断/降级全部接入监控告警，大促后复盘预案
