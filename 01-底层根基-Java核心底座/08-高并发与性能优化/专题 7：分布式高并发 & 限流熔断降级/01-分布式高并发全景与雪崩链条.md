## 1. 单机并发的天花板

单机性能由三个硬资源决定：**CPU 核数**（并发计算上限）、**内存带宽**（缓存与对象分配）、**网络与连接**（线程与 socket）。即便垂直扩展堆到 128 核、数百 GB 内存，仍有三个不可逾越的墙：

- **连接墙**：Tomcat 线程池默认 200 线程，每个请求阻塞一个线程，超时请求不释放，线程池满则排队，排队即雪崩起点（[专题 2](../专题%202：Java%20单机并发编程/00-总览.md) 讲线程模型）。
- **数据库墙**：单库连接数、行锁与索引竞争决定写入上限，QPS 数千即到瓶颈，而大促秒杀接口可达日常 50 倍流量（[专题 4](../专题%204：数据库性能优化/00-总览.md)）。
- **单点墙**：一台机器宕机就是整体不可用，可用性上不去——2026 年大促系统的目标可用性普遍是 99.95%+，单机架构在数学上就不可能达成。

垂直扩展（加配置）与水平扩展（加机器）的分水岭在于**无状态化**：只有把 Session、本地缓存、临时文件外置到 Redis/DB/对象存储，实例才能随意增删（[02 篇](02-扩展模式与容量边界.md)展开）。水平扩展解决容量，却引入了本讲的核心主题——分布式的新挑战。

## 2. 分布式引入的新挑战

分布式系统与单机最大的区别是**故障成为常态**，具体拆成四类：

- **部分失败**：调用下游，结果可能是成功、超时、未知三种。超时最危险——发起方不知道请求是否已执行，重试可能重复扣款，不重试可能丢单（幂等设计见[名词通俗解释体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/后端%20分布式常用名词通俗解释/04-重复请求治理：幂等与防抖.md)）。
- **网络分区与抖动**：机器间通信不可靠，跨机房专线抖动、单条链路 TCP 重传都会放大延迟；故障的传播速度远快于人的发现速度。
- **时钟与状态共享**：多实例各自维护内存状态会分叉——3 个实例各限 100 QPS，全局瞬间可到 300 QPS；分布式限流必须把计数器收敛到共享存储（[05 篇](05-分布式限流：Redis与多级限流.md)）。
- **配置与版本漂移**：规则只在一台机器改、阈值各实例不一致，防护体系形同虚设；规则必须集中下发（[09 篇](09-防护框架选型：Sentinel vs Resilience4j.md)）。

这四类挑战背后是分布式系统的**三个公理**：网络不可靠、时钟不可信、故障必然发生。设计防护体系的前提是承认它们——"假设网络一定可靠"的代码在故障时就是雪崩的引线。这也是为什么 2026 年的高可用实践把"故障演练"当作常态化动作：故障不是会不会发生的问题，而是何时发生、能否在 5 分钟内止血的问题。

## 3. 雪崩链条：故障如何被放大

雪崩不是"下游挂了所以挂"，而是一条可复现的放大链条，2026 年的大促事故复盘几乎都指向同一路径：

**下游超时 → 上游请求堆积 → 线程池打满 → 连接池打满 → 同机其他服务被拖死 → 级联扩散**。

一个典型的午夜事故：秒杀接口 QPS 飙到日常 50 倍，订单服务调用库存接口超时，超时请求不释放 Tomcat 线程，线程池打满后新请求排队，排队导致 RT 进一步上升；订单服务占满数据库连接，同机部署的营销服务拿不到连接也被拖垮——"一个模块崩溃，全家升天"。反向海淘系统 2025 黑五的真实数据：1688 API 间歇性超时率 15%，无熔断保护时超时请求持续占用线程池，正常请求被阻塞，险些触发整体雪崩。

链条上有三个放大器：**线程池**（阻塞不释放）、**连接池**（被慢请求占满）、**重试**（失败重试再放大流量）。防护的核心就是给这条链条装刹车——让超时的请求快速失败而非排队等待。

## 4. 四道防线：限流熔断降级隔离

针对雪崩链条，业界沉淀出四道防线，层层递进：

- **限流（第一道闸门）**：控制进入系统的流量总量，超过阈值快速失败（fast fail）返回 429。解决"流量超容量"——超出的部分根本不让进（[03/05 篇](03-限流算法四选一.md)）。
- **熔断（第二道保险）**：下游故障率达到阈值时切断调用链路，让故障请求快速失败而不是无限等待，给下游恢复时间（[06 篇](06-熔断机制：状态机与参数设计.md)）。反向海淘案例引入熔断后超时率从 15% 压到 2%，P99 220ms，可用性 99.95%+。
- **降级（最后兜底）**：资源不足时保核心、牺牲非核心——读降级返回缓存兜底，写降级转异步，功能降级直接关闭（[07 篇](07-降级与兜底预案：分级设计.md)）。
- **隔离（舱壁）**：从物理上阻断故障传播——线程池隔离、信号量隔离、集群隔离，让"一个舱进水不沉全船"（[08 篇](08-隔离与舱壁：线程池与信号量.md)）。

请求进入系统的时序是：**限流校验 → 熔断状态检查 → 正常转发 → 失败进入降级兜底**。三道闸门缺一不可：只有限流，下游故障时请求照样进来排队；只有熔断，流量洪峰照样打穿容量；没有降级，被拦下的请求体验是"系统错误"而不是"排队稍后"。后续各篇按此顺序逐层展开。

> 🎯 **核心要点**：分布式高可用的敌人不是并发本身，而是"部分失败"的放大链条——超时→排队→线程池打满→级联雪崩；四道防线（限流挡流量、熔断切断传播、降级兜底体验、隔离阻断物理传播）分别作用于链条的不同环节，缺一层在极端场景都会暴露脆弱面；2026 大促的可用性目标 99.95%+ 靠的是整条防线而不是单个组件。
