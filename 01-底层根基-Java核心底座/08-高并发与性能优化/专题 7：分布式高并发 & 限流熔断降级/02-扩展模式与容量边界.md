## 1. 垂直扩展与水平扩展

扩展只有两种方向，各有边界：

- **垂直扩展**：加 CPU、加内存、换更强的机器。优点是零改造，缺点是线性成本高、有物理上限（单机天花板见 [01 篇](01-分布式高并发全景与雪崩链条.md)），且无法消除单点。
- **水平扩展**：增加实例数。容量理论上无限，代价是引入分布式问题——状态共享、负载均衡、故障处理。无状态化不到位时，水平扩展的收益会被一致性成本吃掉。

读多写少是绝大多数业务的常态，所以扩展的第一步永远是**拆读**：CDN 挡静态、Nginx 挡层、Redis 挡热点（[专题 5](../专题%205：缓存体系专题/00-总览.md) 的分层缓存），最后才轮到应用与数据库。写扩展更重：分库分表解决单库写入上限，消息队列把同步写拆成异步链路（削峰见下节），两者的复杂度都不低，务必在压测证明"确实不够了"之后再上。

## 2. 无状态化：水平扩展的前提

水平扩展的前提是实例可任意增删而不丢上下文，三件事必须外置：

- **会话状态**：Session 移到 Redis（Spring Session），实例重启不掉登录态。
- **本地缓存**：Caffeine 等本地缓存扩容后命中率不变（每台都是全量副本），但一致性弱；一致性敏感的数据放 Redis 集中管理。
- **定时任务与幂等记录**：分布式锁与幂等表防止多实例重复执行（参考[雪花算法与分布式锁体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/08-分布式系统与架构/Java分布式框架/04-分布式锁：Redisson与多方案对比.md)）。

判断标准很简单：**杀掉任意一台实例，系统功能与容量是否完整**。满足才算无状态，才有资格谈水平扩展与后续的容量评估。

## 3. 削峰三件套：缓存、异步、批处理

流量峰值是容量的敌人——按峰值设计容量，平日资源浪费 90%；按均值设计，峰值直接击穿。削峰就是把尖峰抹平：

- **缓存挡读**：热点数据提前预热进缓存，把峰值 QPS 从数据库前挡住（大促前对秒杀商品做 Redis 预热是标准动作）。
- **MQ 削峰**：写请求先进队列、后端按自身处理能力消费——订单创建、扣库存这类允许延迟的链路同步转异步，吞吐由消费端决定而不是由峰值决定（与[消息队列理论与实战](../../../02-后端核心技术%20微服务%20分布式%20云原生/03-消息队列/消息队列理论与实战/00-消息队列知识体系总览.md)的削峰章节互读）。
- **批处理**：同类小请求合并成大请求（批量写库、批量通知），减少往返次数，吞吐翻倍。

削峰的本质是"把瞬时压力转化为持续压力"，它改变流量形态，但不消灭流量总量——总量超过系统容量时，限流才是最后的闸门。

## 4. 容量评估与限流红线

限流阈值必须来自容量评估，流程闭环四步：

1. **压测找上限**：用梯度加压找到系统吞吐拐点（[专题 1](../专题%201：性能理论基础/07-容量规划与水位线.md) 的方法论），记录该配置下的最大 QPS 与 P99。
2. **定红线**：限流阈值取最大 QPS 的 **0.7-0.8 倍**——预留 20-30% 缓冲吸收波动，否则限流阈值贴着容量上限，一次 GC 停顿、一次网络抖动就把系统推入超时区。
3. **分链路定**：下单链路（写）与商品详情（读）容量完全不同，逐接口评估，不能只给网关一个全局限流值。
4. **压测验证**：用全链路压测验证限流触发后下游峰值确实被压住（全链路压测方法见同级专题 8，本专题只讲边界设定）。

被限流的请求必须**快速失败**返回 429（带 Retry-After），而不是排队——排队会重演[雪崩链条](01-分布式高并发全景与雪崩链条.md)的线程堆积。

容量评估还有两个实践纪律：**逐接口而非只压网关**——网关入口的容量不等于每个下游接口的容量，写接口（下单）与读接口（详情）的拐点相差一个数量级，只设一个全局阈值等于没设；**压测环境要贴近生产**——测试库数据量小一个量级时，SQL 执行计划不同，压出的拐点虚高 3-5 倍是常态（压测方法见[专题 1](../专题%201：性能理论基础/04-性能测试方法论.md)）。

## 5. WarmUp 预热与冷启动保护

两个容易被忽略的边界：**冷启动**与**扩容后**。

冷启动时 JIT 未完成编译、缓存未预热、连接池未填满，系统真实容量只有稳态的几分之一——此时按稳态阈值放行等于自杀。Sentinel 的 WarmUp 预热限流让允许 QPS 从低值（如 200）在预热期（如 10 分钟）内平滑爬升到目标值（如 2000），对应 Guava 的 SmoothWarmingUp 冷启动模式（[04 篇](04-单机限流：Guava与手写实现.md) 讲实现）。大促前 10 分钟开启预热，是防"开闸即雪崩"的标准动作。

扩容场景同样要预热：新实例刚加入负载均衡，流量立刻切过去，冷实例被瞬间打满。解法是**慢启动**（权重从 0 逐渐爬升）或预热限流，让新实例先攒缓存再扛流量。

> 🎯 **核心要点**：扩展先拆读再拆写，水平扩展的前提是无状态化；削峰（缓存/MQ/批处理）改变流量形态但不消灭总量；限流阈值 = 压测拐点 × 0.7-0.8，必须分链路设定；冷启动与扩容后的预热限流是防"开闸即雪崩"的关键细节。
