## 1. 为什么必须用 Lua：原子性与单次往返

分布式限流最隐蔽的坑是竞态：两个请求同时读到计数器=99，都判断"未超 100"，都放行——超发。用 INCR 单命令能解决计数原子性，但"先判断后扣减"的完整决策仍然是读改写，需要原子性。Redis 单线程执行 Lua 脚本，**脚本运行期间无任何命令插入**，天然消灭竞态；同时"读取→计算→判断→扣减"在一次网络往返内完成，实测单次调用 0.5-1ms。两个诉求（原子 + 低延迟）一次解决，这就是"分布式限流必须 Lua"的原因。Lua 脚本机制本身（KEYS/ARGV、call 与 pcall、EVALSHA 缓存）见 [Redis Lua 脚本体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/02-非关系型数据库/Redis/Lua脚本/00-Lua脚本总览.md)，本讲只写限流脚本。

## 2. 三种算法的 Lua 实现

**固定窗口**：INCR + EXPIRE，两行命令但非原子（INCR 后崩溃会遗留无 TTL 的 key），用 Lua 打包：

```lua
local c = redis.call('INCR', KEYS[1])
if c == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
if c > tonumber(ARGV[2]) then return 0 else return 1 end
```

**滑动窗口日志**（ZSET 精确版）：先清窗口外旧时间戳再计数，窗口自动滑动：

```lua
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, tonumber(ARGV[1]))
if redis.call('ZCARD', KEYS[1]) < tonumber(ARGV[2]) then
    redis.call('ZADD', KEYS[1], ARGV[1], ARGV[1] .. ':' .. ARGV[3])
    redis.call('EXPIRE', KEYS[1], ARGV[1])
    return 1 else return 0 end
```

**令牌桶**（Hash 存储 tokens + last_refill_time，惰性补充）：按时间差计算应补令牌，上限为桶容量，不足则拒绝——与 [04 篇](04-单机限流：Guava与手写实现.md) 的手写版同一模型，只是状态搬到 Redis。推荐用 **Redis Function（EVAL 的 7.0+ 官方进化版）** 管理这些脚本：注册一次、版本化热更新，脚本内 `redis.call('TIME')` 直接取服务器时间（Redis 8.x 基准下 Function 为官方推荐，详见 Lua 脚本体系 05 篇）。

## 3. 时间同步与 key 设计

两个决定限流准确性的细节：

**时间从哪来**：各实例系统时钟有偏差（NTP 同步误差毫秒级），用客户端时间补令牌会造成实例间速率不一致。生产级方案是用 `redis.call('TIME')` 取 **Redis 服务器时间**——所有实例对同一 Redis 计数，时间基准天然统一，2026 年的工业级实现已明确采用此方案。

**key 怎么设计**：硬编码一个全局 key 会退化为全局限流。正确姿势是动态拼接维度：按用户 `user:{id}:api:/order/create`、按 IP+接口、按租户 `tenant:{id}:qps:50`。关键纪律：**userID 必须来自可信头**（内部鉴权后注入），不能直接取客户端参数，否则可被伪造绕过；身份识别优先用已认证主体而非 IP——IP 池攻击会绕过 IP 维度限流。

## 4. 故障语义：fail-closed 与 fail-open

限流依赖 Redis，Redis 挂了限流器怎么办，两种选择：

- **fail-open（放行）**：Redis 不可用时全部放行。系统可用性不下降，但**限流失效**——如果同时下游在故障，等于把雪崩重新打开。
- **fail-closed（拒绝）**：Redis 不可用时全部拒绝（返回 503/429）。严格防护，但 Redis 抖动会误杀正常流量。

2026 年的生产共识：**核心交易链路必须 fail-closed**（宁可短暂拒绝，不可击穿防线），辅以"限流器本身降级到本地单机限流"的中间态（第二层单机兜底），并让各策略自行计算 Retry-After 头告知客户端退避。Redis 恢复后自动切回。这是[四道防线](01-分布式高并发全景与雪崩链条.md)里最容易忽视的边界——限流器自身的故障也要有预案。

## 5. 扩展：Redis Cell、分片与双层限流

单 Redis 节点是性能与可用性双瓶颈，三个演进方向：

- **Redis Cell 模块**：`CL.THROTTLE key capacity interval` 命令把令牌桶下沉到 Redis 服务端，返回值带 `retry_after_ms` 字段，客户端据此做指数退避——零 Lua 代码即可用，是 2026 年轻量场景的推荐路径。
- **一致性哈希分片**：按 key 分片到多个 Redis 节点，突破单节点吞吐（有实现以分片达到 18,769 req/s、p95 16ms），代价是"每节点独立计数"的语义回到分布式——分片限流适合按用户/租户天然分维度的场景，不适合全局总量控制。
- **双层限流架构**：网关层（Nginx/Spring Cloud Gateway）做 IP/全局限流，应用层做业务维度精确限流。单层限流挡不住热点（一个热点用户打满全局配额）与业务维度攻击，双层各司其职——这也是 Sentinel 与网关集成（gw-flow 规则）的标准形态。
- **Sentinel 集群流控**：独立 Token Server 承担统一计数，应用实例以 client 身份接入——它是"真正的分布式限流"（总量可控），与 Redis Lua 方案的取舍在：Token Server 多一个部署组件但规则/管控更完善，Redis 复用现有基础设施但总量与分片语义要自行设计（Token Server 模式细节见 [Sentinel 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/06-Spring全家桶/Spring组件汇总/Spring%20Cloud%20微服务全家桶（分布式）/Spring%20Cloud%20Alibaba（阿里实现，属于%20Spring%20Cloud%20生态实现）/Sentinel：流量控制熔断降级/00-Sentinel知识体系总览.md)）。

限流器自身也要可观测：**限流命中次数、各维度 key 的分布、限流器延迟**必须进监控大盘——"限流了但没人知道"和"限流器慢了拖垮业务"都是常见事故。2026 年的工业级实现标准做法是 Prometheus 指标：`rate_limited_requests_total`（命中计数，rate() 聚合看趋势）与限流器调用耗时直方图，配合告警规则（命中率突增 = 流量异常或阈值退化）。

## 6. 热点参数限流

普通限流按接口/QPS 维度，一个热门商品（如某款 iPhone 秒杀）可以占满整个接口配额，普通用户全被误杀。**热点参数限流**对参数值单独计数：`@SentinelResource` + 热点规则按"参数值维度"限流（如按商品 ID 限 500 QPS），非热点参数不受影响。实现上同样依赖滑动窗口采样，只是维度从资源变成参数值。秒杀、抢购类场景的标配，与[专题 5](../专题%205：缓存体系专题/00-总览.md) 的热点 Key 治理（多副本、本地缓存兜底）是一对组合拳。

> 🎯 **核心要点**：分布式限流 = Lua 原子脚本（一次往返消灭竞态）+ Redis 服务器时间（消灭实例时钟偏差）+ 维度化 key 设计（可信头注入防伪造）+ fail-closed 故障语义（核心链路防击穿）；扩展路径是 Redis Cell 下沉、一致性哈希分片、网关+应用双层限流；热点参数限流解决"一个热点打满全局配额"。
