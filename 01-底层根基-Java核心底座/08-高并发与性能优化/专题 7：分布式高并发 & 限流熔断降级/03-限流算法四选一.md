# 03 限流算法四选一

## 1. 固定窗口：实现最简单，边界有突刺

固定窗口把时间切成固定长度（如 1 秒）的窗口，每个窗口一个计数器，窗口内计数超过阈值即拒绝，窗口切换清零。实现就是一个 INCR + 过期——两行代码的事，也是它最大的诱惑。

致命缺陷在**窗口边界**：假设阈值 100 QPS，窗口 [0,1s] 的 0.9-1.0s 内放行 100 个请求，[1s,2s] 的 1.0-1.1s 内又放行 100 个——0.2 秒内实际通过了 200 个请求，即 2 倍阈值的瞬时突刺。秒杀场景下，这个突刺恰好打在系统最脆弱的时刻（压测拐点附近），会直接击穿容量。**任何限流阈值接近容量的场景，固定窗口都不合格**。它的适用面只有"高吞吐的粗略计数"——比如防刷日志、粗略的采集频率控制。

## 2. 滑动窗口日志：最精确，内存最贵

滑动窗口日志用 ZSET 记录每个请求的时间戳（score=时间戳，member=唯一标识），每次请求先删除窗口外的旧时间戳（`ZREMRANGEBYSCORE key 0 now-window`），再 `ZCARD` 计数，小于阈值才 `ZADD` 放行。窗口是真正逐请求滑动的，**没有任何边界突刺，精度 100%**。

代价是内存：每个请求占一个 ZSET 成员，10 万 QPS 下每秒产生 10 万条记录、1 秒窗口常驻 10 万成员——高流量下内存与 GC 压力可观。它的定位是**计费敏感、SLA 绑定**的接口：宁可花钱买精度，不允许边界多放一个请求。实现细节（TTL 自动清理、member 唯一性）见 [05 篇](05-分布式限流：Redis与多级限流.md) 的 Lua 版本。

## 3. 滑动窗口计数：精度与内存的平衡点

滑动窗口计数（Sentinel 采用）是工程上的最优解：把窗口切成 N 个小格（如 1 秒切 2 格，或 1 分钟切 60 格），维护每格计数，滑动时按公式加权估算：

```
count ≈ prev_count × (1 - elapsed/window) + curr_count
```

其中 `elapsed` 是当前格已走过的时间。它的聪明之处在于**用上一个完整窗口的计数按比例折算**——内存 O(1)（只存 N 个格子的计数器），误差 <1%（格数越多越准），无边界突刺。这是"精度与内存"的甜点，也是 Sentinel 单机限流的默认实现（[04 篇](04-单机限流：Guava与手写实现.md) 讲时间窗采样原理）。大多数生产限流场景，选它就够了。

## 4. 漏桶与令牌桶：平滑与突发的对立

两个最经典的"流控"算法，哲学完全相反：

**漏桶**：请求任意速率进桶，桶以恒定速率"漏水"（处理），桶满则丢弃。输出速率绝对平滑、**不允许任何突发**——即使桶是空的，请求也得等下一个滴水周期。适合防 DDoS、下游对流量抖动极度敏感的弱一致性系统（如短信网关）。

**令牌桶**：令牌以恒定速率补充进桶（容量上限），请求取到令牌才放行，取不到直接拒绝。关键特性是**允许突发**：桶里最多攒 capacity 个令牌，闲时攒令牌、瞬间洪峰可一次全部取出（最多 2 倍均速的突发）。这就是 API 网关、电商大促等绝大多数场景选择它的原因——业务天然有"偶发尖峰"，完全平滑的限流会把正常波动误杀。

| 维度 | 固定窗口 | 滑动窗口日志 | 滑动窗口计数 | 漏桶 | 令牌桶 |
|---|---|---|---|---|---|
| 边界突刺 | 有（2 倍） | 无 | 无 | 无 | 无（上限=桶容量） |
| 突发容忍 | 无 | 无 | 无 | 无 | 有（攒桶） |
| 内存 | O(1) | O(请求数) | O(格数) | O(1) | O(1) |
| 实现复杂度 | 最低 | 高 | 中 | 中 | 中 |
| 典型场景 | 粗略防刷 | 计费 SLA | 默认选择 | 防 DDoS | API 网关/大促 |

## 5. 限流的拒绝语义与优先级

算法决定"放不放行"，拒绝之后的行为同样决定成败。2026 年的生产共识是**拒绝语义三段式**：

- **明确告知**：返回 429 Too Many Requests，带 `Retry-After` 头告诉客户端何时重试——客户端据此退避，而不是盲目重试放大流量。
- **快速失败**：拒绝必须毫秒级返回，禁止让被拒请求排队等线程——排队把"拒绝"变成"积压"，重演雪崩链条。
- **降级兜底**：被拒的请求进入降级路径（[07 篇](07-降级与兜底预案：分级设计.md)）——秒杀场景"已参与排队"比"请求失败"体验好一个量级。

在此基础上可以叠加**优先级限流**：VIP 用户与普通用户不同配额，流量超限时优先拒绝低优先级——本质是"限流按业务价值分配容量"，与降级预案的分级思想同源。Sentinel 的匀速排队模式（rate limiter 控制放行间隔）则是"拒绝"之外的另一条路：把超限请求按固定速率排队放行，用于削峰填谷，代价是排队延迟（适用于可容忍延迟的异步链路）。

## 6. 选型决策与自适应限流

选型遵循一个决策链：**是否容忍突发 → 容忍就令牌桶；不能容忍 → 是否要求绝对平滑 → 平滑选漏桶；只要求无突刺 → 精度敏感选滑动窗口日志，否则滑动窗口计数**。固定窗口仅在极简防刷场景兜底。

2026 年出现的新趋势是**自适应限流**：阈值不再写死，而是根据 CPU 负载、内存使用率、下游延迟动态调整（如 CPU 超过 80% 时阈值自动下探），配合滑动窗口平滑过渡。其动机是"静态阈值配置僵化"——流量画像变了、机器配置变了，手改阈值永远慢一拍。但自适应要建立在可观测数据完整的前提上（[10 篇](10-生产实战与自测.md) 的监控闭环），没有指标埋点的自适应就是盲人摸象。Sentinel 的系统自适应保护（BBR 思想）是这一方向的工业实现——它不设固定 QPS 阈值，而是根据系统负载实时推导安全阈值，对流量画像剧变的场景（大促、突发热点）尤其有效。

> 🎯 **核心要点**：五种算法是"突发容忍 × 精度 × 内存"的三角权衡——固定窗口有 2 倍边界突刺仅适合粗略防刷；滑动窗口日志最精确但内存 O(请求数) 适合计费 SLA；滑动窗口计数 O(1) 内存误差 <1% 是默认选择；漏桶绝对平滑适合防 DDoS，令牌桶容忍突发是 API 网关与大促的标准答案；2026 年阈值动态化的自适应限流正在成为生产标配。
