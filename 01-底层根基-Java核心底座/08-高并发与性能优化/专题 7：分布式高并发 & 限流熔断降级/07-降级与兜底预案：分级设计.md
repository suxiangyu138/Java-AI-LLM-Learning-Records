## 1. 降级的本质：保核心弃非核心

限流挡流量、熔断切断故障，但如果被拦下来的请求直接抛"系统错误"，用户流失、订单丢失。**降级是用户体验的兜底**：资源不足时，核心功能继续可用（哪怕降质量），非核心功能主动让路。一个类比：停电时保障医疗用电，关闭景观灯——不是"没有电"，而是"决定电给谁"。

降级的设计前提是**业务分级**：哪些链路绝不能挂（下单、支付、登录）、哪些可以降质量（商品详情、推荐、评论）、哪些可以直接关闭（积分、签到、个性化）。分级不清晰，故障时所有团队都抢资源，系统在混乱中崩溃——预案必须提前写清楚，而不是故障现场讨论。

## 2. 三类降级：读、写、功能

降级按操作类型分三类，实现手段完全不同：

- **读降级**：返回兜底数据而非实时数据。商品详情链路典型兜底链：**本地缓存 → Redis → 数据库 → fallback**（静态页/占位数据）。最常用也最安全，因为读天然可重试、可缓存。
- **写降级**：同步转异步。订单创建后扣库存从同步 RPC 改为发 MQ 异步执行——用户先看到"下单成功"，库存一致性由异步任务保证（用[幂等](../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/后端%20分布式常用名词通俗解释/04-重复请求治理：幂等与防抖.md)与对账补偿兜底）。
- **功能降级**：直接关闭非核心功能。大促时关闭评论、推荐、积分展示——这些功能消失不影响交易主链路，但显著降低资源占用。

三类降级可以叠加：写降级 + 功能降级在大促中是标准组合拳，读降级则是日常故障的第一响应。

## 3. 主动降级与被动降级

按触发方式分两种：

- **被动降级**：熔断触发、超时异常、限流拒绝时自动执行 fallback（[06 篇](06-熔断机制：状态机与参数设计.md) 的 OPEN 态就是被动降级的触发器）。系统自动完成，无需人工介入。
- **主动降级**：运营/运维预判资源紧张（大促流量预测超容量、下游供应商故障）时，提前手动打开降级开关。主动降级是**预防性**的——等到熔断被动触发，往往已经造成了部分故障。

工程实现上两者统一为"开关 + 兜底链"：开关控制是否走降级路径，兜底链定义降级后的行为。被动降级是开关自动打开，主动降级是开关手动打开，机制同一套。

## 4. L1/L2/L3 分级预案设计

分级预案把"业务分级"翻译成可执行的三级预案（参考 2026 年书城大促项目的生产实践）：

| 级别 | 内容 | 触发信号 | 兜底链 |
|---|---|---|---|
| L1 | 商品详情降级：简化富文本渲染 | 延迟劣化 >5% | CDN 缓存 → 只读库 → 空白占位 |
| L2 | 购物车降级：本地存储 + 异步持久化 | 延迟劣化 >15% | 本地 Map → Redis → 返回当前列表 |
| L3 | 订单提交降级：同步转异步 | 延迟劣化 >30% | MQ 异步 → 通知"排队中" → 页面轮询 |

设计要点：**每个级别有明确的触发信号（量化指标）**、**有完整的兜底链（不只第一步）**、**降级是渐进的**（先降最外层，L1 不够再进 L2）。核心原则是保障"可浏览 → 可加购 → 可下单"的链路连续性——最坏情况下用户下不了单但能看到"排队中"，而不是页面 500。触发阈值必须来自压测数据（[02 篇](02-扩展模式与容量边界.md) 的容量红线），与监控告警联动。

## 5. fallback 链与动态开关

**fallback 链**是"逐级退让"的调用序列：优先调用备用服务 → 失败取缓存 → 再失败取静态数据 → 最终返回友好提示。2026 年实践明确 fallback 设计为**链**而非单点——只配一个 fallback，它自己挂掉时兜底就消失了。Sentinel 的 `@SentinelResource` 区分两种兜底方法：`fallback`（业务异常/熔断时执行）与 `blockHandler`（限流被拒时执行），两者语义不同不能混用。

**动态开关**是降级的工程底座：降级开关、阈值、兜底链内容都放 Nacos 配置中心，配置变更实时下发、**不重启生效**（大促调参 10 秒级生效，规则持久化与下发机制见 [Sentinel 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/06-Spring全家桶/Spring组件汇总/Spring%20Cloud%20微服务全家桶（分布式）/Spring%20Cloud%20Alibaba（阿里实现，属于%20Spring%20Cloud%20生态实现）/Sentinel：流量控制熔断降级/00-Sentinel知识体系总览.md)）。

降级有两个必须提前想清楚的边界。**一致性风险**：读降级返回的缓存数据是旧数据——商品降价了、库存变了，降级期间的订单可能按旧价成交，所以降级数据要标注"降级标识"与数据时间戳，交易类降级必须联动风控校验；**演练纪律**：降级预案不演练等于没有——故障时没人能在压力下临时设计 fallback 链，正确做法是压测时顺带触发各降级开关验证兜底链路可用（混沌工程的"预演故障"思想），大促前 T-7 必须完成一轮全量演练。

降级必须有**可观测性**：降级命中次数、兜底命中率、各级降级开关状态必须进监控大盘并配告警——"降级了没人知道"等于"故障了没人知道"，大促结束后还要复盘降级命中是否合理、预案是否需要调整。

> 🎯 **核心要点**：降级 = 保核心弃非核心，分读/写/功能三类实现（缓存兜底/转异步/关功能）；主动降级预防性手动开、被动降级熔断自动触，机制统一为"开关+兜底链"；L1/L2/L3 分级预案要有量化触发信号与完整兜底链，保障"可浏览→可加购→可下单"链路连续性；fallback 要设计成链，开关走 Nacos 动态下发，降级全程可观测。
