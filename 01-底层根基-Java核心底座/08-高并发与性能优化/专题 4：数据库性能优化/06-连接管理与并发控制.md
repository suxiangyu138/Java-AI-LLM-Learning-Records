## 1. 连接数模型：Little's Law 的应用

一次查询的完整链路过五层：业务线程 → 连接池 → 服务端连接 → SQL 执行 → 释放。连接数 = QPS × RT（Little's Law，推导见[专题 1 03 篇](../专题%201：性能理论基础/03-三大理论定律.md)）——**RT 翻倍，需要的连接数就翻倍**。这是理解连接事故的总纲：

- RT 正常（50ms）时 1000 QPS 只需 50 个连接；RT 劣化到 5s 时同样 QPS 需要 10000 个——数据库不可能有这么多连接，于是全部请求在连接池排队，连接池耗尽 → 应用线程池被占满 → 雪崩。
- 所以"连接打满"通常**不是连接参数问题，是 RT 问题的投影**：修好慢 SQL 与锁等待（[05 篇](05-事务MVCC与锁竞争调优.md)），连接自然回落。调大参数只是把雪崩延后几分钟。
- 每个连接至少 256KB 内存（加线程栈与缓冲），连接数上限由内存反推：8GB 实例留 4GB 给 buffer pool 后，理论上限在几千以内——连接数从来不是"越大越好"。

用数字走一遍雪崩演算：连接池 50、单条 SQL 正常 50ms → 支撑 1000 QPS。某天统计信息过期，一条高频查询从走索引变成全表扫，RT 变成 5s——同样的 1000 QPS 需要 5000 个连接，池子 50 个连接每秒只能服务 10 个请求，剩下 990 个在池前排队，connectionTimeout 30s 内全部超时，应用线程池再被占满，服务雪崩。全链路每层数字都算得出来，这就是为什么"先修 RT"是连接治理的第一原则。

## 2. 服务端连接参数

| 参数 | 建议 | 理由 |
|---|---|---|
| max_connections | 128-4096 按内存与业务 | 每连接 ≥256KB，5000+ 是 OOM 前奏 |
| back_log | 500 | 握手等待队列，过低直接拒连 |
| wait_timeout / interactive_timeout | 600-1800（10-30 分钟） | 两者必须一致，且高于应用端 idleTimeout |
| skip_name_resolve | ON | 避免 DNS 反查拖慢建连（云环境尤其） |

MySQL 服务端不做连接复用，复用靠应用侧连接池；服务端参数的价值是**给连接设上限与老化策略**，与连接池参数对齐（见下节）。连接建立本身有成本（TCP + 握手 + 鉴权），`skip_name_resolve` 关闭反查、连接池保活，是降低建连成本的两件套。

## 3. 连接池决策：HikariCP 高并发配置

连接池是应用与数据库之间的缓冲层，HikariCP 的高并发配置决策（参数语义全解见[数据库连接池 02 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/数据库连接池/02-HikariCP深度.md)）：

- **maximumPoolSize**：≤ max_connections × 60-80%（给 DBA 与监控留余量）；多实例场景 = max_connections × 0.6 ÷ 实例数。起步值 `2 × CPU 核数 + 1`，压测中看 Threads_running 与 RT 校准——OLTP 多数场景超过 30 后性能不升反降（锁竞争与上下文切换）。反例：max_connections 只有 150 却把池设 200，5k QPS 压测错误率 63.8%、平均 RT 从 87ms 飙到 4.2s。
- **connectionTimeout**：默认 30000ms 是雪崩放大器——慢查询一来，请求在池前排队 30 秒才报错，线程池被占满。线上压到 **1000-3000ms**，快速失败交给上游重试/降级；频繁超时是排查信号，不是调大参数的借口。
- **minimumIdle = maximumPoolSize**：固定大小池，启动即预热，防止流量突增时"连接风暴"（建连握手把 DB 打满）。
- **maxLifetime**：30 分钟，必须短于 MySQL wait_timeout，防连接被服务端静默断开。
- **leakDetectionThreshold**：60 秒必开——连接借出超时未归还打印堆栈定位泄漏代码；关掉的压测错误率案例高达 92.1%。
- **keepaliveTime** 5 分钟心跳保活，防 LB/NAT 中间件断连；**validationTimeout < connectionTimeout** 铁律。

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50        # ≤ max_connections × 60-80%，压测校准
      minimum-idle: 50             # 固定池，防连接风暴
      connection-timeout: 3000     # 快速失败，拒绝 30s 排队
      max-lifetime: 1800000        # 30 分钟 < wait_timeout
      leak-detection-threshold: 60000
      keepalive-time: 300000
```

还有一个容易被忽略的坑：`spring.datasource.hikari.` 前缀写错或属性名拼错，参数会**静默回退默认值**——连接池问题的第一排查动作永远是"确认启动日志里 HikariPool 实际生效的池大小"，配置不生效比配置错误更隐蔽。改连接池参数后要重启验证（Spring Boot 的配置绑定不支持运行时热更新）。

## 4. 连接泄漏诊断

症状：`Too many connections`（错误 1040）或 `HikariPool-1 - Connection is not available, request timed out after 30000ms`。诊断三步：

1. **数据库侧**：`SHOW GLOBAL STATUS LIKE 'Threads_connected'` 与 `Threads_running` 对比——连接多但干活的少，就是泄漏；`PROCESSLIST` 里 `COMMAND='Sleep' AND TIME>60` 的会话是嫌疑人。
2. **应用侧**：Actuator 的 `hikaricp.connections.active` 长时间等于 maximum 且 pending > 0 → 连接借出未归还；jstack 抓卡在 `HikariPool.getConnection()` 的线程，看调用栈定位未关闭的代码路径。
3. **根因分类**：事务没提交/回滚、ResultSet 未关闭、异常吞掉后没走 finally、线程池线程死掉前没归还——修复代码而不是调参数。

## 5. 服务端线程模型与 Threads_running

服务端每个连接一个线程（一连接一线程模型），`Threads_running` 是**真正在执行的线程数**——这是比连接数更可靠的负载信号：

- Threads_running 长期 > 50：SQL 或锁有问题，先查慢日志与 `sys.innodb_lock_waits`（[07 篇](07-慢查询诊断与性能分析.md)）。
- 高连接低执行（connected 高、running 低）：应用侧排队，连接在池里空等，看 [01 篇](01-数据库性能全景与调优方法论.md) 的泄漏与 RT 排查。
- 连接数极高但多数在 Sleep：连接池 idleTimeout 与 wait_timeout 配置错位，或连接风暴后遗症。
- 极端场景（几千连接、几十万 QPS）：MySQL 企业版/Percona 的 **Thread Pool**（thread_pool_size）用固定线程池 + 队列替代一连接一线程，降低上下文切换；开源社区版无此功能，靠连接池上限控制连接数。

Threads_running 与 Threads_connected 的差值本身就是信号：两者接近说明连接都在干活（负载真实）；差值巨大说明大量连接空闲挂池——要么池配大了（成本浪费）、要么流量波谷（正常）、要么空闲连接在等待什么资源（可疑）。给差值和比值都建一条历史曲线，比固定阈值告警更能识别趋势性恶化。

> 🎯 **核心要点**：连接数 = QPS × RT（Little's Law），连接打满是 RT 问题的投影，修根因而非调参数；服务端 max_connections/back_log/wait_timeout/skip_name_resolve 四参数与连接池对齐；HikariCP 五决策——池大小 ≤60-80%、connectionTimeout 压到 1-3s、固定池防风暴、leakDetection 必开、maxLifetime < wait_timeout；泄漏诊断三步（Threads_connected vs running、hikaricp.active、jstack）；Threads_running 是比连接数更可靠的负载信号，长期 >50 查 SQL 与锁。
