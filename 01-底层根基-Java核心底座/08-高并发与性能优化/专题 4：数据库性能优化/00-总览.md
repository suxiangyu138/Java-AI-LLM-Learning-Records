# 数据库性能优化 · 知识体系总览

> 高并发服务里，数据库是最容易"雪崩式变慢"的一层——一条慢 SQL、一批连接泄漏、一次锁等待，就能把整个系统的 P99 拖垮。本专题站在"高并发系统"视角：先建性能模型，再逐层定位，最后用压测验证；2026 年的共识是升级到 MySQL 8.4 LTS 并吃透并行查询与连接治理

## 6. 十大常见误区

1. **慢查询=没索引**：锁等待、连接耗尽、引擎刷盘瓶颈同样表现为"慢"，先看等待再看计划。
2. **max_connections 越大越好**：每连接至少 256KB 内存，过大直接 OOM；连接是并发度不是容量。
3. **连接池越大越好**：超过数据库承载反而锁竞争加剧，`2×CPU+1` 起步、压测校准。
4. **调大 connectionTimeout**：默认 30s 是雪崩放大器——慢查询一来，请求排队 30 秒占满线程池；应快速失败加排查根因。
5. **Buffer Pool 越大越好**：专用机 70-80% 封顶，留给 OS 的没有了会 swap，更糟。
6. **只看平均 RT**：高并发下一条慢 SQL 把 P99 拉爆而平均无感，延迟分布才是真相。
7. **升级后不查默认值**：8.4 的 `innodb_change_buffering=none`、redo 参数合并都是静默行为变化，升级即回归风险。
8. **统计信息不维护**：计划漂移（好索引不走）是生产事故常见根源，ANALYZE 与直方图要制度化。
9. **128 线程压测够了**：Percona 2026 实测饱和点要 1024+ 线程才看得到，线程太少结论失真。
10. **分库分表万能**：多数系统死在"不需要分却分了"，正确顺序是缓存 → 读写分离 → 才到分库分表。

## 7. 一周学习计划

- **Day 1**：00 总览 + 01 方法论，给线上库开慢日志与 PFS，记录 QPS/TPS/连接数基线。
- **Day 2**：02 索引设计 + 03 优化器，用 EXPLAIN ANALYZE 实测两条慢 SQL。
- **Day 3**：04 InnoDB 参数，核对 Buffer Pool 与 io_capacity 与存储类型是否匹配。
- **Day 4**：05 锁与事务 + 06 连接管理，检查 HikariCP 参数与 max_connections 的配比。
- **Day 5**：07 慢查询诊断，用 performance_schema 定位一条真实慢 SQL 的等待类型。
- **Day 6**：08 压测，用 sysbench 跑出吞吐拐点，算 70% 水线。
- **Day 7**：09 扩展决策 + 10 案例与自测，判断自己的库该不该分，完成 20 题自测。

## 8. 快速自测 10 题

1. 数据库性能四层模型是什么？慢查询日志里没有记录但接口变慢，该查哪层？
2. 索引为什么是读性能与写放大的权衡？8.4 的 change_buffering 默认值改了什么？
3. EXPLAIN 与 EXPLAIN ANALYZE 的本质区别是什么？为什么说"用 ANALYZE 告别估算"？
4. MySQL 9.7 的 Hypergraph Optimizer 为什么默认关闭？什么场景值得逐语句开启？
5. Buffer Pool 命中率低于 95% 说明什么？预热参数三件套是什么？
6. innodb_io_capacity 按存储类型如何取值？innodb_flush_sync=ON 时它会失效吗？
7. 一条更新频繁的热点行，如何用乐观锁替代行锁排队？副作用是什么？
8. HikariCP 的 maximumPoolSize、connectionTimeout、leakDetectionThreshold 各自怎么定？
9. sysbench 压测为什么要预热、为什么线程要梯度加压？饱和点怎么找？
10. 读写分离的正确性前提是什么？分库分表前先做哪两步？
