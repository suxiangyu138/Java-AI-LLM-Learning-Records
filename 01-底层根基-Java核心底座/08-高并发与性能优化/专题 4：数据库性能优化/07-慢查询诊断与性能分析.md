## 1. 慢日志配置

慢日志是慢查询治理的入口，生产配置基线：

```ini
slow_query_log = ON
long_query_time = 1          # 超过 1s 记录；高并发库可压到 0.5
log_queries_not_using_indexes = ON   # 没走索引的也记（注意会很多，观察期后按需关）
log_slow_admin_statements = ON       # DDL 也记录
log_output = FILE           # 文件便于 pt-query-digest；也可 TABLE 便于 SQL 查询
```

要点：`long_query_time` 是**纯执行时间**，不含排队与网络——应用侧 RT 高但慢日志干净的，问题在锁等待或连接排队（[06 篇](06-连接管理与并发控制.md)），不在 SQL 本身；慢 SQL 量巨大的生产库可考虑采样策略——Percona 分支的 `log_slow_rate_limit` 类参数按"每类 digest 只记一条 + 计数"降量，8.4 的 `long_query_time` 支持微秒精度；全量日志在磁盘打满时本身会成为故障源，日志轮转与容量监控要配套；按 digest 聚合统计（`pt-query-digest /var/log/mysql/slow.log`）输出"Top 10 慢查询 + 频率 + 总耗时占比"，先处理**总耗时占比高**的（频率 × 单次耗时），而不是单次最慢的——高并发下跑 200ms 但每秒 1000 次的 SQL，危害远大于一条 10s 的离线任务。

按 digest 聚合的意义在于**把同一条 SQL 的不同参数看成一类**：查询条件不同但执行路径相同，聚合后频率与总耗时才有统计意义。直接看原始慢日志会被"一条 10 秒的罕见查询"带偏，而真正吃吞吐的是每秒几百次的半慢查询——后者在 digest 排行里以"总耗时"排序才浮出水面。慢日志输出到文件还是表各有场景：文件（`log_output=FILE`）配合 pt-query-digest 做离线聚合最顺手，日志量大时文件更省内存；表（TABLE）写入 `mysql.slow_log` 可直接 SQL 查询，适合中小库与临时排查。生产标准是文件 + 定时出周报；用表时注意定期清理历史防膨胀。

## 2. performance_schema 诊断方法论

官方推荐的 PFS 诊断流程是**四步迭代法**（[MySQL 8.4 官方文档](https://docs.oracle.com/cd/E17952_01/mysql-8.4-en/performance-schema-examples.html)）：

1. **启用全部 instrumentation**（不做预过滤），避免漏掉真凶；
2. 复现/运行问题负载，基于事件表**事后过滤**分析根因；
3. 对排除掉的区域**关闭对应 instrument**，并 `TRUNCATE` 历史表清除噪声；
4. 重复迭代，每次提高信噪比，直到锁定瓶颈，然后修复并验证。

高频分析表：`events_statements_summary_by_digest`（按 SQL 指纹聚合的耗时/次数，先看这里找 Top SQL）、`events_waits_current`（线程当前等待什么）、`events_waits_history_long`（等待历史）、`mutex_instances.LOCKED_BY_THREAD_ID` / `rwlock_instances.WRITE_LOCKED_BY_THREAD_ID`（谁持锁）。注意 PFS 的虚拟索引只支持 `=` 等值比较且无序，排序要显式 `ORDER BY`，查询别漏 WHERE 否则慢在 PFS 自己身上。`performance_schema=ON` 有约 10-20% 级开销但 8.0+ 已可控，生产按需开、开完关。

启停 instrumentation 的正确姿势是"只开需要的消费者，其他保持关"——生产上通常只开语句事件与等待事件两类消费者（`setup_consumers` 里 NAME 含 events_statements 与 events_waits 的条目），并把 `events_waits_history_long` 这类历史表按窗口 TRUNCATE，防止事件堆积把性能采样变成性能负担。全开只在复现问题的短窗口内做，问题定位完立刻收。

## 3. sys schema 与 pt-query-digest

sys schema 是 PFS 之上的"傻瓜视图"，先查它再手写 SQL：

- `sys.statement_analysis`：按 digest 的耗时排行，一页看全 Top SQL。
- `sys.schema_unused_indexes`：从未使用的索引清单，直接喂给[索引治理](02-索引与查询性能设计.md)。
- `sys.innodb_lock_waits`：锁等待的等待者/持有者/锁对象三件套（[05 篇](05-事务MVCC与锁竞争调优.md) 第三节）。
- `sys.processlist`：比 `SHOW PROCESSLIST` 多出锁等待与进度信息。

pt-query-digest 处理慢日志文件（上文）；Percona Toolkit 全家桶（pt-index-usage、pt-duplicate-key-checker、pt-online-schema-change）与[MySQL 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MySQL/00-MySQL总览与技术术语.md)的排查章节配合使用。

sys schema 视图本质是 PFS 之上的"傻瓜封装"：它把 join 与统计逻辑写好了，查询性能比手写 PFS SQL 更好，因为只取需要的列。生产排查顺序建议固定为"先 sys 后 PFS"——sys 答不出的问题（如等待深度、mutex 持有者）再进 PFS 深挖，避免一上来就钻事件表。注意 `sys.statement_analysis` 默认按总执行时间排序，与慢日志口径一致；配合 `sys.statement_performance_analyzer` 做两时间点对比分析，"上周 vs 本周"的 digest 差异能一眼看清回归。

## 4. 定位四步与治理闭环

一条"接口变慢"的完整归因路径：

1. **确认在 DB 侧**：应用 RT 高 → 慢日志有无新条目、Threads_running 是否飙升（没有 → 去查连接与锁，[06 篇](06-连接管理与并发控制.md)）。
2. **EXPLAIN 看索引**：type/key/Extra 三字段——ALL 或 key 为 NULL 是索引问题；`Using temporary`/`Using filesort` 是排序聚合问题（字段语义见 [SQL调优 02 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/SQL调优/02-执行计划EXPLAIN深度.md)）。
3. **EXPLAIN ANALYZE 看真实瓶颈**：实际行数 vs 预估行数（差 10 倍 → 统计信息过期，`ANALYZE TABLE`）；时间集中在哪个算子（join 顺序、全扫、排序）。
4. **兜底看等待**：`sys.innodb_lock_waits` 有锁等待、`events_waits_current` 卡在 IO/mutex——按 [05 篇](05-事务MVCC与锁竞争调优.md) 与 [04 篇](04-InnoDB引擎性能调优.md) 处置。

治理闭环：找到 → 修（SQL 改写/索引/参数三选一）→ **回归验证**（同负载对比前后 RT 分布）→ **沉淀台账**（digest 维度周报，Top 10 慢查询上榜/下榜跟踪）。闭环的关键在"验证"与"台账"——不回归等于没修，不台账等于下次重新排查。台账的形态不需要复杂：一张表记录"digest 前缀、首次上榜时间、优化动作、优化前后 P99、当前状态"，每周把慢日志 Top 10 与台账对账——新上榜的三天内要有响应，老榜单每月清理。把治理从"救火"变成"管线"，靠的就是这个简单的闭环表。慢查询治理的系统化流程另见 [SQL调优 04 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/SQL调优/04-慢查询定位与治理.md)，本篇补充的是工具链深度。

> 🎯 **核心要点**：慢日志按"总耗时占比"而非单次最慢排序治理；PFS 四步迭代法（全开→事后过滤→关无关→迭代）是官方推荐的信噪比提升路径，高频表 digest/waits_current/lock 三件；sys schema 先查视图再手写 SQL；定位四步"确认在库→EXPLAIN→ANALYZE→看等待"闭环兜底；治理闭环必须带回归验证与 digest 台账，否则等于没修。
