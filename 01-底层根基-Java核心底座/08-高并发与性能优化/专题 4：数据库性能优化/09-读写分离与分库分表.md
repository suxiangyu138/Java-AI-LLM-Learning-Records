## 1. 扩展决策框架

扩展的顺序有严格逻辑，跳级是大多数失败架构的根源：

1. **先缓存**：热点读用 Redis 挡掉（[Redis 主体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/02-非关系型数据库/Redis/01-Redis入门与安装配置.md)），数据库只接"必须落库"的流量——大部分系统在这一步就解决 80% 压力。
2. **再读写分离**：读多写少的业务，把读流量卸给从库，水平加只读实例。
3. **才到分库分表**：单库内存/IO 顶不住或写入量超单机，才按业务切分。

何时"该分了"的三个信号：**内存**（热点数据超过 Buffer Pool 承载，命中率长期 <95% 且扩容无济于事）、**IO**（写 IOPS 接近存储额定 ×70%）、**连接**（max_connections 顶满且 RT 劣化）。方案细节（MyCat/ShardingSphere、双写迁移、扩容流程）见 [MySQL 08 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MySQL/08-分库分表与高可用.md)，本篇只讲性能账。

## 2. 读写分离：复制延迟是正确性前提

读写分离把读压力摊到从库，但正确性被**复制延迟**锁死：主库写、从库读，延迟窗口内读到旧数据。治理维度：

- **量化延迟**：`SHOW SLAVE STATUS` 的 `Seconds_Behind_Source` 与 9.7 新增的 replication applier metrics（按 worker 的延迟与吞吐，从库回放瓶颈可定位到具体 worker）；延迟波动时先查主库大事务与 DDL（[05 篇](05-事务MVCC与锁竞争调优.md) 的长事务部分）。
- **流量策略**：读最新数据（订单状态、余额）强制走主；可容忍秒级延迟（列表、统计、配置）走从；`max_execution_time` 之类的保护要在从库上更严格——从库承载大查询最合适，但大查询也最容易拖垮从库延迟。
- **架构纪律**：半同步复制（semi-sync）在主写关键路径上保底，避免"主挂了从也缺数据"的降级雪上加霜；只读实例用于备份与报表查询，与业务流量隔离。从库的另一个性能纪律是**禁止在主库执行大查询与备份**——备份与统计查询全部走从库（或专门的备份实例），这是 MySQL 官方优化建议里成本最低的一条。从库挂掉只是读降级，主库被大查询拖垮则是全站事故，两者的止损成本差一个数量级。

## 3. 分库分表：分片键与跨片代价

分库分表是最高杠杆也最高税率的扩展。两个决策决定成败：

- **分片键**：必须同时满足"均匀"（数据与流量分布均衡）与"业务相关"（同用户的记录落在同一片，本地查询免跨片）——订单按 user_id 分片，用户维度查询全本地；按 order_id 分片则"查某用户的订单"必然跨片。选错分片键是分片方案的第一死因。
- **跨片代价**：跨片 join 与聚合要在应用层或代理层合并（内存里 join N 片结果）、跨片事务退化成分布式事务（性能与复杂度双杀）、深分页跨片要重排——这些代价要在分片前就设计进业务查询形态，而不是分完再补救。

辅助决策：范围分片天然支持扩容（按时间加片）但热点集中在最新片；一致性哈希均匀但迁移复杂。9.6 的 GTID 结构升级提升了复制集的处理效率，多源/级联复制在分片场景更实用，但迁移与校验工具链要提前备好。

## 4. 扩展后的性能陷阱

扩展方案落地后，性能问题从"单机调优"变成"分布式新税"，高频陷阱清单：

- **数据倾斜**：分片均匀只是起点——大客户、大卖家的数据量天然倾斜，热点片提前扩容或二次拆分。
- **跨片分页**：`LIMIT 100000, 20` 在分片后变成每片取 100020 条再合并——用游标/时间戳分页替代深分页（[SQL调优 05 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/SQL调优/05-JOIN与分页排序优化.md) 的深分页方案）。
- **分布式事务**：跨片事务要么拆解为本地事务 + 最终一致（MQ 对账），要么引入 Seata（见 [Seata 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/06-Spring全家桶/Spring组件汇总/Spring%20Cloud%20微服务全家桶（分布式）/Spring%20Cloud%20Alibaba（阿里实现，属于%20Spring%20Cloud%20生态实现）/Seata：分布式事务/00-Seata知识体系总览.md)），无论如何都不该在事务里跨片 join。
- **从库放大**：分片 × 读写分离 = 片数 × 副本数，从库数量爆炸，回放压力与运维成本按乘法增长——从库只加"必要的最少副本"，备份与统计共用。

**收益递减的清醒**：每一次扩展（分片、加副本）都同时增加延迟一跳与运维复杂度；压测里经常出现"分完更慢"——本地查询要跨两跳网络，跨片查询要合并。扩展决策的终极判据不是"架构听起来高级"，而是容量四维（[08 篇](08-数据库压测与容量规划.md) 第五节）确实逼近拐点。

分片后的扩容也比想象中贵：加一片要迁移既有数据（数据重分布）、校验一致性、切换路由——线上做一次是小时级工程。所以分片数的规划要按"两年后的数据量"定，而不是按当下够用定；宁一开始分 32 片，不要 4 片起步年年扩——迁移成本远超闲置片的内存成本。

> 🎯 **核心要点**：扩展顺序不可跳级——缓存 → 读写分离 → 分库分表，用内存/IO/连接三信号判断时机；读写分离被复制延迟锁死正确性，读最新走主、可容忍走从、半同步保底；分片键必须均匀+业务相关，跨片 join/事务/分页是分片前就要设计掉的代价；扩展后防数据倾斜、深分页、分布式事务、从库爆炸四陷阱；扩展是收益递减的投资，判据是容量逼近拐点而非架构猎奇。
