## 1. 成本模型与优化器开关

MySQL 优化器为候选执行计划估算成本（IO 成本 + CPU 成本），选成本最低者执行。成本估算依赖三样东西：统计信息（行数）、表大小、`optimizer_switch` 中的策略开关。高并发运维只需盯住几个关键开关，其余保持默认：

- `semijoin`、`materialization`：IN/EXISTS 子查询的两大加速策略，默认开，是多数子查询优化的来源，别关。
- `hash_join`：默认开；小表 join 在内存压力大时，BNL（块嵌套循环）可能更稳，出问题再评估。
- `condition_fanout_filter`：多条件过滤的行数修正，偶发误判嵌套子查询，用 `EXPLAIN FORMAT=TREE` 验证。

**统计信息是整个成本模型的地基**：8.4 要求 `innodb_stats_persistent=ON` 且升级后跑过 `ANALYZE TABLE`，否则 EXPLAIN 的 rows 估算可偏差 10 倍以上——这直接导致计划漂移（[02 篇](02-索引与查询性能设计.md) 第三节）。判断"该不该信这个计划"，永远回到"rows 估得准不准"。

快速检查优化器"看不看得清"：把 `EXPLAIN` 的 rows 与 `EXPLAIN ANALYZE` 的实际行数对比，偏差超一个数量级就说明统计信息与真实分布脱节——这在数据分布倾斜的表上尤其常见（如订单状态字段 99% 是已完结）。此时先修统计信息与直方图，而不是急着加 hint。

## 2. EXPLAIN ANALYZE：告别估算

普通 `EXPLAIN` 输出的是**估算**值（rows、cost）；MySQL 8.0.18 起的 `EXPLAIN ANALYZE` 会**真实执行**并输出每步的实际行数与实际耗时：

```sql
EXPLAIN ANALYZE SELECT o.order_id, u.name
FROM orders o JOIN users u ON o.user_id = u.id
WHERE o.status = 'PAID' AND o.created_at > '2026-01-01';
```

输出会显示每个算子：实际行数、实际时间占比（`actual time=...`）、是否 filesort/临时表。它的价值在于**把"优化器以为"变成"实际是"**：预估行数与实际行数差 10 倍 → 统计信息过期；时间集中在 join 算子 → 驱动表选错；出现 `Using temporary` → 聚合或去重设计问题。配合 8.4 并行查询，`Extra` 里的 `Using parallel scan (N workers)` 同时验证了并行是否生效。

定位四步口诀（完整流程见 [07 篇](07-慢查询诊断与性能分析.md)）：慢日志找到 SQL → `EXPLAIN` 看索引使用（type/key/Extra 三字段）→ `EXPLAIN ANALYZE` 看真实瓶颈算子 → 回到表结构与统计信息求证。

EXPLAIN ANALYZE 有两个注意事项：它会**真实执行**语句——生产库对写语句或大查询要先评估影响再跑，或抓只读实例分析；输出按算子树逐层缩进展示，读的顺序是从里到外，每层"实际行数 × 执行次数"相乘才是该算子的总工作量——只看单层耗时会被"执行次数很多但单次很快"的算子误导。

## 3. 优化器的常见陷阱

高并发下反复踩的几类坑，每类都有明确的验证方法：

- **隐式转换**：字段是字符串却传数字，索引直接失效——`EXPLAIN` 的 type 从 ref 掉到 ALL 立刻暴露。
- **函数包裹列**：`WHERE DATE(created_at) = ...` 让索引失效，改写为范围条件。
- **大 IN 列表**：几百上千个值的 IN 会退化为全扫，拆批或改 join 临时表。
- **排序与分组**：`ORDER BY` 无法走索引时 `Using filesort`，`GROUP BY` 出现 `Using temporary`——覆盖索引或索引列顺序调整可消解（[SQL调优 05 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/SQL调优/05-JOIN与分页排序优化.md) 详述）。
- **计划漂移**：同样的 SQL 今天走索引明天不走，几乎都是统计信息变化，不是"优化器发疯"。
- **join 顺序错位**：多表 join 的原则是小表驱动大表——驱动表行数少，循环次数少。EXPLAIN ANALYZE 的时间占比能直接看出顺序是否合理：若大表成了驱动表，先查统计信息（多半是估算失真），再考虑 `STRAIGHT_JOIN` 或改写。驱动表判定与优化细节见 [SQL调优 05 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/SQL调优/05-JOIN与分页排序优化.md)，本篇只强调它对高并发延迟的决定性——join 顺序错一次，RT 放大一个数量级。

判断原则：**先怀疑统计信息，再怀疑 SQL 写法，最后才怀疑优化器本身**——多数"优化器 bug"是统计信息的锅。

## 4. 2026 新基线：Hypergraph Optimizer

MySQL 9.7 LTS（2026-04 发布）把此前仅企业版的 **Hypergraph Optimizer** 带进了社区版——这是自 5.7 以来优化器的最大重构：基于 DPhyp 算法（SIGMOD 2008 的经典研究），能枚举 bushy plan（总线型计划）、按代价逐 join 选择 hash join 还是嵌套循环、传播 interesting order。Oracle 公布的 TPC-DS 实测：**近半查询提升 ≥25%，19 条提升 ≥50%，但 14 条回退 ≥50%**——收益与风险同样真实。

落地要点：

- **实验性、默认关闭**；OLTP 快路径上经典优化器仍然更优，简单查询的规划成本更高。
- 推荐用法是**逐语句 opt-in**：`SELECT /*+ SET_VAR(optimizer_switch='hypergraph_optimizer=on') */ ...`，而不是全局开启。
- 它对统计信息质量**敏感得多**——启用前必须 ANALYZE TABLE 并刷新直方图，否则回退会被放大。
- 深连接、星型、分析类查询最受益；用它时保留经典计划做 A/B 对比。

9.7 之外，9.6 创新版还有两处性能相关变更值得知道：GTID 结构升级（复制集处理更高效）与 `container_aware` 容器感知启动参数（按容器限额自适应内存配置，云原生部署更稳）。这些不直接影响优化器，但升级选型时要纳入评估——8.4 LTS 与 9.7 LTS 的定位差异（前者稳、后者新）决定生产怎么选。

## 5. Hint 的使用纪律

Hint（`FORCE INDEX`、`USE INDEX`、`SET_VAR`、`STRAIGHT_JOIN`）是绕过优化器决策的最后手段，高并发生产里必须守纪律：

- **先证明后使用**：EXPLAIN ANALYZE 确认当前计划确实差，新计划确实好，再上 hint。
- **hint 是债务**：数据分布一变 hint 就失效，所以每条 hint 必须带注释记录"为什么、什么时候加、失效条件是什么"，并排期回访验证。
- **优先修根因**：hint 掩盖统计信息问题或数据分布变化，修好统计信息后 hint 往往可以删除。

> 🎯 **核心要点**：优化器是"统计信息 + 成本模型"的决策器，rows 估算准不准决定计划好坏的八成；EXPLAIN ANALYZE 用真实执行数据取代估算，是慢 SQL 定位的第一工具；隐式转换/函数包裹/计划漂移是高并发下三大陷阱，先怀疑统计信息再怀疑写法；9.7 Hypergraph Optimizer 对深连接查询收益显著但默认关闭、逐语句启用、对统计信息极敏感；hint 是最后手段，必须带注释与回访。
