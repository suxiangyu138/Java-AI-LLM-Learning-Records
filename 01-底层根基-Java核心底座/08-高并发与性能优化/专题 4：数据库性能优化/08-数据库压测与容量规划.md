## 1. sysbench 实战

sysbench 是 MySQL 压测的事实标准（Percona、阿里云官方测试均采用）。三阶段模型：`prepare`（灌数据）→ `run`（跑负载）→ `cleanup`（清理）。OLTP 类 Lua 脚本族覆盖三类负载：`oltp_read_write`（读写混合，约 18 条 SQL/事务，含二级索引维护）、`oltp_read_only`（14 条：主键点查 + 范围查）、`oltp_write_only`（4 条：2 UPDATE + 1 DELETE + 1 INSERT）——这是阿里云 RDS 测试指南的口径，点查与写占比不同的脚本测的是不同能力。

```bash
sysbench oltp_read_write --mysql-host=... --db-driver=mysql \
  --table_size=250000 --tables=16 --time=300 --threads=64 \
  --percentile=95 --rand-type=uniform --report-interval=10 run
```

sysbench 的安装有个常见坑：发行版包管理器的二进制可能链接旧版客户端库，连 8.x 的 `caching_sha2_password` 鉴权会报错——从源码编译（1.0.18+）或使用官方二进制最稳；`prepare` 阶段的大批量插入要临时调大 `max_allowed_packet`，否则灌数据就失败，这属于"压测环境准备"而非测试本身，但一半的压测事故死在这里。

关键参数决策：`--table_size` 要够大（10 万+ 行/表），太小则全表进 Buffer Pool，测的是内存不是 IO；`--tables` 取 2-4 × CPU 核数，防锁竞争集中在少数表；`--time` 不低于 300s；`--rand-type` 决定随机数分布——uniform 均匀随机访问，zetta 偏斜访问。默认场景用 uniform 模拟真实点查；如果业务有明显的"热 key"（如头部商品占 80% 查询），用 zetta 模拟偏斜更贴近——压测模型要与业务流量模型对齐，否则测出的拐点没有代表性（流量模型方法论见[专题 1 04 篇](../专题%201：性能理论基础/04-性能测试方法论.md)）；`--report-interval` 实时观察吞吐曲线。

## 2. Percona 2026 基线方法

[Percona 2026 基准报告](https://www.percona.com/blog/2026-mysql-ecosystem-performance-benchmark-report/) 是当前最严谨的方法参照：

- **Schema**：20 表 × 500 万行（共 100M 行、约 24GB），保证数据量远超内存、IO 真实参与。
- **共享基础配置**：`innodb_buffer_pool_size` 按档位（2G/12G/32G）、`max_connections=4096`、`innodb_io_capacity=2500 / max=5000`、`innodb_flush_log_at_trx_commit=1`（全 ACID）、`innodb_flush_method=O_DIRECT`、`sync_binlog=1`、`binlog_format=ROW`、redo 容量 4G。
- **预热协议**：Warmup A 只读 180s 填热 Buffer Pool → Warmup B 读写 600s 让脏页与 redo 进入稳态 → **测量 900s**，1 秒粒度记录，TPS 为主指标，同时采集 iostat/vmstat。
- **并发梯度**：从 512 线程起压到 2000+，**只有 1024+ 线程才能看到饱和点**——128 线程以内的结论会高估吞吐（线程太少时延迟还没放大）。

这套方法学对自有环境同样适用：数据量 > 内存、双阶段预热、15 分钟测量、多并发档位，缺任何一环结论都会失真。

Percona 报告里还有一个要点：**稳态判定**——只读负载要确认预热后 InnoDB/OS 的读指标归零（内存全命中），读写负载要等到吞吐与延迟曲线稳定 5 分钟以上再开始记数。没到稳态就开测，前几分钟的数据既不能算进结果，还会污染后面窗口的统计。

## 3. 压测纪律：预热、梯度与拐点

压测不是"跑一条命令看个数字"，纪律清单：

- **预热**：只读预热填 Buffer Pool，读写预热进稳态；冷库第一分钟的数据不可用。
- **梯度加压**：4 → 8 → 16 → 32 → 64 → 128 → 256 → 512 → 1024 → 2048，每档 2-3 分钟；记录每档 TPS 与 P95——**TPS 增速放缓的点就是拐点**，拐点之后 RT 开始线性恶化。
- **水线**：承诺水位 = 拐点 TPS × 70%（理论依据见[专题 1 07 篇](../专题%201：性能理论基础/07-容量规划与水位线.md)的排队论分析——利用率过 70% 等待时间开始指数增长）。
- **拐点判定**：看两个信号——TPS 增速减半（从每档 +40% 变成 +10% 以内）或 P95 开始脱离线性（从缓慢爬升转为陡增）。两个信号出现任何一个，拐点就在前一档。实际操作中把每档的 TPS 与 P95 画成两条曲线贴进报告，比任何文字描述都有说服力。
- **同环境对比**：压测机与生产机规格一致、`innodb_flush_method` 一致、MySQL 版本一致，否则数字不可比。
- **观测配套**：压测期间同时采 Threads_running、Buffer Pool 命中率、脏页比例、iostat——拐点出现在哪一层，答案直接指向瓶颈（[01 篇](01-数据库性能全景与调优方法论.md) 四层模型）。
- **错误率必须为 0**：出现 reconnects 先查 max_connections 与连接池，别把失败当吞吐。

## 4. TPC-C 与业务回放

sysbench 的读点查为主，与真实 OLTP（订单、支付）仍有距离；更接近真实的是 TPC-C：50/50 读写比、多表事务、外键约束与仓库-订单-明细的真实数据依赖。工具用 `tpcc-mysql`（Percona 维护）或 HammerDB，方法上同样套用"预热 + 梯度 + 稳态"。

终极验证是**业务流量回放**：把线上抓取的 SQL（general log 或 PFS digest 抽样）按时间戳回放，全链路压测的数据库环节就是它（[专题 1 04 篇](../专题%201：性能理论基础/04-性能测试方法论.md) 的流量模型）。回放能暴露 sysbench 测不出的问题——某条低频 SQL 的数据分布、特殊参数绑定、会话级状态依赖。

## 5. 容量规划：内存、IOPS 与连接数

压测数据反推容量需求，四个维度取**最低维**为瓶颈（四维建模方法论见[专题 1 07 篇](../专题%201：性能理论基础/07-容量规划与水位线.md)）：

- **内存**：目标数据量 × 热点比例 ≤ Buffer Pool × 命中率红线——命中率掉破 95% 说明内存不够，先于磁盘处理。
- **IOPS**：业务写模型（点写 vs 批量 vs 大事务）× 放大系数（二级索引数、redo/doublewrite 双写），对照存储额定随机写 IOPS × 70% 水线。
- **连接数**：峰值 QPS × 目标 P99 RT = 所需连接数，对照 max_connections × 70%。
- **CPU**：8.4 并行查询与高 QPS 场景 CPU 先行——压测中 CPU 先到 80% 而 IO 空闲，瓶颈在计算。

输出物：每维度"当前水位 / 拐点 / 建议上限"一张表，加"到达 80% 水位的时间预测"——容量规划不是算一次，是**随业务增速滚动复核**的例行动作。报告建议六段式：业务量预测 → 每维当前水位 → 拐点与建议上限 → 到达 80% 水位的预计时间 → 扩展方案候选（加内存/加副本/读写分离/分片）→ 复核周期。模板比拍脑袋的数字更值钱的是"预测有假设、假设可更新"——每次压测与每次大促都是更新假设的机会。

> 🎯 **核心要点**：sysbench 三阶段 + 三类负载，表数据量必须大于内存、tables 取 2-4×核数；Percona 2026 基线——预热 180s+600s、测量 900s、1024+ 线程才见饱和点、TPS 为主指标；压测纪律：预热→梯度加压→拐点→×70% 水线，错误率必须为 0；TPC-C 与业务回放补真实负载；容量四维（内存/IOPS/连接/CPU）取最低维，滚动复核而非一次性计算。
