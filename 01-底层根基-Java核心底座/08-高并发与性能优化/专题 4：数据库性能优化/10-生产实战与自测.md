## 1. 生产实战：三个案例

**案例 A：连接打满雪崩**。现象：大促当天订单接口 P99 从 80ms 飙到 30s，日志刷 `Too many connections` 与 Hikari 超时。排查：Threads_connected 顶满 max_connections 但 Threads_running 只有 30——连接被借走不干活；jstack 发现大量线程卡在 `HikariPool.getConnection()`，再追栈发现某个 DAO 在事务里做了远程调用，连接被长事务占住；慢日志同时出现一条新上线的全表扫描 SQL 把 RT 拉高，连接需求翻倍。根因是**慢 SQL（放大） + 事务内远程调用（泄漏）**双因叠加。处置：先 `kill` 长事务止损、关掉问题 SQL 的流量，改代码后压测验证。沉淀：连接池参数评审纳入发布流程。

**案例 B：热点行锁等待风暴**。现象：秒杀开始时接口大量报 1205（lock wait timeout），RT 全线恶化。排查：`sys.innodb_lock_waits` 显示几百个等待者都卡在同一行库存记录，持有者是每秒 500 次的扣库存 UPDATE 长事务。根因是**热点行行锁串行化**。处置：改为 `UPDATE ... SET stock=stock-1 WHERE id=? AND stock>0` 条件更新 + 失败走重试，锁窗口从"排队等事务"缩到"单条瞬时"；再压测验证 P99 回落。沉淀：热点行清单纳入压测场景（[05 篇](05-事务MVCC与锁竞争调优.md)）。

**案例 C：命中率骤降引发的整体变慢**。现象：无发布、无流量变化的凌晨，全库 RT 缓慢抬升。排查：命中率从 99% 掉到 88%，`Innodb_buffer_pool_pages_dirty` 持续 >20%，`Innodb_log_waits` 非零——脏页刷不动。根因：新加的批量任务把 `innodb_io_capacity` 设值的云盘（额定 3000 IOPS）写爆，后台刷盘与业务抢 IO。处置：按云盘额定随机写 IOPS×70% 校准 io_capacity、`io_capacity_max` 设 2 倍，批量任务错峰。沉淀：io_capacity 与存储规格对照表入基线（[04 篇](04-InnoDB引擎性能调优.md)）。

三个案例共同点：**现象都在连接/延迟，根因都在 SQL 与引擎层**——先建基线、分层定位、一次一变量，然后监控固化，就是 [01 篇](01-数据库性能全景与调优方法论.md) 的闭环在实战里的样子。

## 2. 生产纪律清单

1. 慢日志长期开启（`long_query_time=1`），digest 周报跟踪 Top 10。
2. Buffer Pool 命中率、脏页比例、Threads_running、锁等待四类指标接入告警。
3. HikariCP 参数（池大小/超时/leakDetection）纳入发布评审。
4. 发版与导数据后跑 `ANALYZE TABLE`，关键过滤列建直方图。
5. 生产参数一次一变量、`SET PERSIST` 热生效、留回滚快照。
6. 升级 MySQL 前核对默认值变更（8.4：change_buffering、redo 参数）。
7. 长事务（>60s）与锁等待告警，事务内禁止远程调用。
8. 上线前 sysbench 压测出拐点，承诺水位 = 拐点 ×70%。
9. 批量任务拆小事务、错峰执行，写密集任务避开高峰。
10. 压测环境与生产规格一致（版本、flush_method、数据量级）。

## 3. 报错速查表

| 错误 | 含义 | 快速处置 |
|---|---|---|
| 1040 Too many connections | 连接打满 | 先看 Threads_running：低=泄漏，高=慢 SQL；kill 长事务止损 |
| 1205 Lock wait timeout | 锁等待超时 | `sys.innodb_lock_waits` 找持有者，查热点行与长事务 |
| 1213 Deadlock | 死锁（自动回滚一方） | 收集死锁日志，改锁顺序/拆事务，重试被回滚方 |
| 2006 Server has gone away | 连接被断开 | 查 wait_timeout 与 max_allowed_packet 匹配 |
| 1042/2003 连接失败 | 网络/握手问题 | 查 skip_name_resolve、防火墙、back_log |
| 1114 Table is full | 表空间满 | 扩容/清理，查磁盘与临时表空间 |

## 4. 面试三范式与简历写法

- **价值式**（简历/开场）："将核心订单库 P99 从 5s 降至 120ms——定位到计划漂移与锁放大，重建统计信息并引入条件更新，压测验证后固化告警"。公式：量化 + 方法 + 闭环。
- **技术式**（追问六段）：现象（RT/连接数）→ 定位（四层排除、EXPLAIN ANALYZE）→ 根因（统计信息过期/锁等待/刷盘）→ 方案（索引/参数/代码三选一）→ 验证（压测前后对比）→ 沉淀（监控/台账/规范）。
- **架构式**：从容量四维（内存/IOPS/连接/CPU）判断该调优还是该扩展，讲清缓存 → 读写分离 → 分库分表的决策链与各自代价。
- **追问四连**：连接池 30s 默认值为什么是坑？锁等待怎么取证？8.4 并行查询参数与甜点？分库分表后深分页怎么做？——对应本专题 06/05/04/09 篇。

4. 知道 8.4 的 change_buffering/redo 参数变更与并行查询参数。

7. 能给出 HikariCP 五参数决策并解释雪崩链路。
