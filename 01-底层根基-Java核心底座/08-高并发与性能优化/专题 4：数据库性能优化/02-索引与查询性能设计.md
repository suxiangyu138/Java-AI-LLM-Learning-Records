## 1. 索引决策：读与写的权衡

索引让查询走 B+ 树而非全表扫描，代价是每次 INSERT/UPDATE/DELETE 都要维护索引——写一条记录，N 个二级索引就要写 N 个位置，随机写放大直接反映在 IO 与延迟上。高并发下的决策框架是：

- **读多写少**（报表、详情页）：索引大胆加，覆盖高频查询，用空间换延迟。
- **写多读少**（日志、埋点）：索引严格收敛，只保留等值条件必需的，宁可用联合索引一箭多雕。
- **读写均衡**（订单、交易）：按"高频 SQL 清单"逐条反推索引，不为低频查询买单——查询一年跑不了几次，别让它拖累每次写入。

MySQL 8.4 有一个直接影响写路径的静默变更：`innodb_change_buffering` 默认从 `all` 变为 `none`——过去对非唯一二级索引的 INSERT/DELETE 会先缓冲到内存异步合并落盘，现在改为直接写入。SSD 上通常无感，但**高频率批量写 + 多二级索引**的表升级后可能 QPS 微降，不要误判成硬件问题去调 `innodb_io_capacity`（详见 [04 篇](04-InnoDB引擎性能调优.md)）。

## 2. 覆盖索引与回表成本

二级索引只存索引列 + 主键，查询字段不在其中就得回表按主键再查聚簇索引——一次随机 IO，高并发下是延迟的主要构成。让查询字段全部落在索引里（`Extra: Using index`）就是覆盖索引：省掉回表，还能借索引有序性免掉排序。对高频查询，这是**优先级最高的优化**——常常比"加个索引"再进一步。

对应的治理动作是**冗余索引清理**：联合索引 (a,b) 建立后，单独的 (a) 就冗余了；用 `pt-duplicate-key-checker` 或 sys schema 的 `schema_unused_indexes` 定期找出从未被使用的索引。每个冗余索引都在给每次写入交税，删掉它就是白捡的写性能。给每张表的每个索引做"四问评审"：这个索引服务哪条高频 SQL？能不能被现有联合索引覆盖？写入放大值不值？删掉它压测回不退？四问答完，冗余索引自然浮出——评审比事后清理更省事，因为索引是"加的容易删的难"。索引设计原则（最左前缀、等值在前范围在后）与失效场景在 [SQL调优 03 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/SQL调优/03-索引优化实战.md) 有完整展开，这里只强调高并发视角的取舍。

与覆盖索引经常并列出现的是**索引下推（ICP）**：`WHERE` 里无法完全走索引的过滤条件，交给索引层先滤一遍再回表，减少回表行数——MySQL 默认开启，`Extra` 出现 `Using index condition` 即生效。它不消灭回表，只是让回表次数更少；对"联合索引 + 范围条件 + 高频查询"的组合，ICP 与覆盖索引可以叠加使用，两者是"覆盖索引优先、ICP 兜底"的关系。

## 3. 统计信息与直方图：计划的稳定性

比"索引缺失"更隐蔽的生产事故是**计划漂移**：索引都在，但优化器选了错的执行计划，RT 一夜之间从 50ms 涨到 5s。根因几乎都是统计信息失真：

- `innodb_stats_persistent=ON`（默认）保证统计信息持久化，重启不丢失，务必确认开启。
- `innodb_stats_auto_recalc`：写占比 >10% 的表开启自动重算；只读报表库关闭省开销。
- **直方图不会自动生成**：对分布不均的过滤列（如状态字段），`ANALYZE TABLE t UPDATE HISTOGRAM ON col` 手动生成；且 `histogram_generation_max_mem_size` 默认仅 64KB，大表的关键列会被跳过，生产建议提到 256KB 左右。直方图生成会取表级读锁，避开高峰执行。

纪律：**上线发版后、批量导数据后必须 ANALYZE TABLE**；把直方图纳入发布清单。ANALYZE 的时机不是随缘：新索引建成后、大批量导数后、报表日切前后各跑一次；直方图则跟着"过滤列的选择性变化"走——状态字段分布一旦偏斜（如某状态占比从 1% 变成 90%），立即刷新。把这两条写进发布 check-list，比任何"调一次优化器参数"都更治本，因为成本模型只信它手里的统计信息。8.4 的并行查询（见下节）对统计信息同样敏感——行数估算错 10 倍，并行度决策与 join 顺序决策全错。

## 4. 并行查询：不替代索引的补充

MySQL 8.4 的 InnoDB 并行查询（8.0.30 实验 → 8.4 稳定默认开）解决了"单条扫描查询只用一个线程"的老问题：大表 COUNT、全表聚合、DDL 扫描这类**注定要全扫**的场景，可以拆成多线程并行。实测数据（[腾讯云 8.4 运维实录](https://cloud.tencent.com/developer/article/2624399)）：42M 行 COUNT(*) 从 18.2s 降到 2.3s（16 线程）、100M 行订单表 18.72s → 1.43s（约 13 倍）。关键参数与纪律：

- `parallel_query` 默认 ON；`parallel_threads_limit` 默认 4，生产实测 **16 线程是多数场景甜点**，32 线程可能因上下文切换反而回退。
- `innodb_parallel_read_threads` 为全局并行扫描线程池，默认自适应（核数/8，最小 4）。
- 用 `EXPLAIN ANALYZE` 验证是否生效——`Extra` 出现 `Using parallel scan (N workers)` 即为并行。
- **不要追 100% CPU**：给业务线程留余量，重扫描场景压到 25-30% CPU 是常见安全线。

要清醒：并行查询**不替代索引**——它能加速"必须全扫"的查询，但一条本该走索引的查询被改成全扫并行，IO 与 CPU 一样爆炸。并行是"全扫不可避免时"的加速器，索引才是"避免全扫"的根本。

> 🎯 **核心要点**：索引决策本质是读性能与写放大的交易，按读写比分类制定策略；覆盖索引是高频查询的最高优先级优化，冗余索引是白交的写税；计划漂移比缺索引更隐蔽，统计信息与直方图必须制度化维护；8.4 并行查询解决"注定全扫"场景的吃多核问题（16 线程甜点），但绝不替代索引。
