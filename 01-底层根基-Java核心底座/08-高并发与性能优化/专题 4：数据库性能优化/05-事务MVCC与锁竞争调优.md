# 05 事务 MVCC 与锁竞争调优

> 写场景的性能事故几乎都绕着锁——锁等待把单条慢事务放大成整体雪崩，热点行让并发写入串行化；调优的目标不是消灭锁，是让锁等待可观测、可控、不放大

## 1. 隔离级别与性能代价

MySQL 默认 RR（可重复读），它比 RC（读已提交）多付出的性能代价常被忽略：

- **间隙锁**：RR 下等值/范围扫描会锁住记录间的"间隙"防幻读，高并发插入同一范围时互相阻塞；RC 只锁记录本身，写并发明显更好。
- **undolog 保留时长**：RR 下事务要能看到自己快照时刻的数据，长事务导致旧版本链不清除，间接推高 undolog 与磁盘 IO（见第五节）。
- 8.0 已移除 semi-consistent read，更新路径的优化窗口进一步收窄，隔离级别的影响更直接。

取舍结论：**读多写少或对一致性有强要求用 RR（默认不动）；高并发写密集且业务可接受读已提交语义，评估切换到 RC**——这是大厂订单类系统的常见选择。隔离级别原理见 [MySQL 03 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MySQL/03-事务与锁机制.md)，这里只讲性能账。

## 2. 锁等待的放大效应

一条 UPDATE 持锁事务慢（长事务、死循环、网络超时），后面所有触碰同范围的行都在排队——**单个事务的 RT 被放大成 N 个连接的空等**，连接池随之打满，最终整库不可用。放大链条：慢事务 → 锁等待堆积 → 连接耗尽 → 应用超时 → 重试风暴 → 流量翻倍。理解这条链，就明白为什么"先砍锁等待源头"是写场景的第一动作。

超时参数是止损阀：`innodb_lock_wait_timeout`（默认 50s）太长，生产通常压到 3-5s 让失败快速返回，由应用层重试或降级；`lock_wait_timeout`（元数据锁）同理。死锁（错误 1213）与锁等待超时（错误 1205）的处置在 [SQL调优 06 篇](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/SQL调优/06-锁与事务调优.md) 有完整案例，本篇只强调：**死锁本身不可怕（InnoDB 自动回滚牺牲者），可怕的是等待超时没被发现、业务线程干等**。

## 3. 锁竞争的取证：data_locks 家族

8.0 起锁现状迁入 performance_schema，`INNODB_LOCKS` 已移除，取证用这套表：

```sql
-- 谁在持有锁、谁在等待（事务 ID 维度）
SELECT * FROM performance_schema.data_lock_waits;
SELECT * FROM performance_schema.data_locks WHERE NOT IS_FREE;
-- 该事务正在执行的语句
SELECT * FROM sys.innodb_lock_waits;
```

定位锁等待的完整姿势：`sys.innodb_lock_waits` 直接给出"等待者事务 → 持有者事务 → 锁住的表与行"三件套；配合 `events_waits_current` 看线程卡在哪个等待；持有者与等待者都拿到后，回 [06 篇](06-连接管理与并发控制.md) 的连接清单（`PROCESSLIST`）查每个事务跑了多久、执行什么 SQL。**锁竞争是"受害者与肇事者分离"的排查**：等待的事务是无辜的，持有锁卡住的那个才是问题。

锁竞争的监控要"少而准"：对 `sys.innodb_lock_waits` 做两条告警——等待时长超过 5s 且持续 1 分钟、同一行被等待次数超过阈值。前者抓"单个慢事务放大"，后者抓"热点行串行化"。告警频率控制在每周个位数，否则就是噪声；配合应用侧的 1205/1213 错误率双向印证，比单侧告警可靠得多。

## 4. 热点行治理

秒杀扣库存是热点行的教科书：所有并发 UPDATE 同一行，行锁让并发归零，RT 变成"排队时间 + 执行时间"。三级治理阶梯：

- **第一级：乐观锁**——`UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0` 用条件原子性替代行锁排队；受影响行数为 0 就说明超卖或失败，应用层重试。副作用：`stock > 0` 条件本身仍会短暂持有行锁（写还是要落锁），但等待窗口从"排队等别人事务"缩到"单条语句瞬时"，P99 改善显著。
- **第二级：版本号/状态机**——订单类更新用 `version` 字段 CAS 防并发覆盖，把冲突判断前移到业务层。
- **第三级：流量前置**——把热点写改成异步队列（削峰）或 Redis 原子减后再异步落库，数据库只承接"最终一致"的写（Redis 侧见 [Redis 主体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/02-非关系型数据库/Redis/01-Redis入门与安装配置.md)）。

判断原则：**锁等待告警先看是不是热点行**——`sys.innodb_lock_waits` 里反复出现的同一主键就是信号；热点行治理优先级高于任何参数调优，因为参数无法让串行变并行。

热点行的另一种形态是**写放大热点**：不是同一行被并发写，而是同一索引范围被并发插入（如订单号前缀相同的批量插入），间隙锁把它们串行化。形态不同、治理不同——行热点用条件更新，范围热点要先看隔离级别（RR 的间隙锁是否必要），再考虑调整插入批次大小与随机化。

## 5. 长事务与 undolog 膨胀

长事务（几分钟不提交）对性能的三重打击：

- **undolog 无法 purge**：旧版本链必须保留到所有活动事务结束，长事务期间 undolog 只增不减，磁盘与 IO 被无效数据吃满。
- **查询变慢**：其他查询读到长版本链，要顺着版本链找可见版本，行越多越慢。
- **binlog/复制放大**：大事务在主库执行久，从库回放同样久，复制延迟被拉高（[09 篇](09-读写分离与分库分表.md)）。

治理：`information_schema.innodb_trx` 找出 `trx_started` 超过阈值（如 60s）的事务告警；批量作业拆小事务提交；应用侧事务内禁止远程调用与等待（事务里做 HTTP/RPC 是长事务头号来源）。

MVCC 的另一面：读不阻塞写、写不阻塞读，靠的是版本链（undolog 里每个事务的旧版本快照），查询要沿着版本链找"自己快照时刻可见的版本"——链越长，定位越慢。所以长事务不仅拖累自己，还让**所有走这条链的查询变慢**：这也是为什么"长事务监控"是所有高并发团队的标配告警，而不是可选项。

> 🎯 **核心要点**：RR 比 RC 多付出间隙锁与版本链代价，写密集场景评估切 RC；锁等待会把单条慢事务放大成整库雪崩，innodb_lock_wait_timeout 压到 3-5s 做止损阀；取证用 performance_schema 的 data_locks/data_lock_waits 与 sys.innodb_lock_waits，受害者与肇事者分离排查；热点行用条件更新/版本号/流量前置三级治理，参数无法让串行变并行；长事务三重打击（undolog 膨胀/查询变慢/复制延迟），事务内禁止远程调用。
