# 01 数据库性能全景与调优方法论

> 数据库调优的第一性问题是"瓶颈在哪一层"——连接、SQL、引擎、IO 四层表现相似但处置完全不同，先建模型再动手，避免把锁等待误诊成慢查询、把连接泄漏误诊成参数问题

## 1. 性能指标与模型

数据库的性能指标必须分**业务侧**与**服务侧**两组看，单一数字永远是片面的：

- **业务侧**：QPS（每秒查询数）、TPS（每秒事务数）、RT 分布（P50/P95/P99）、错误率。高并发下 P99 才是核心——一条慢 SQL 能把 P99 从 50ms 拉到 5s 而平均无感（口径细节见[专题 1 01 篇](../专题%201：性能理论基础/01-性能指标体系.md)）。
- **服务侧**：Threads_running（真正干活的连接数）、Threads_connected（含空闲）、Buffer Pool 命中率、脏页比例、IOPS 与磁盘延迟、锁等待次数。

两组指标通过 **Little's Law** 连接：并发度 = QPS × RT。数据库的"并发度"就是连接数——QPS 不变而 RT 翻倍，需要的连接数就翻倍，这正是慢查询引发连接打满的数学解释（[专题 1 03 篇](../专题%201：性能理论基础/03-三大理论定律.md)）。因此调优的本质是**压缩 RT**：RT 降下来，连接需求、锁竞争、资源占用全线回落。

## 2. 性能问题的四层解剖

从应用视角到磁盘视角，一次查询穿越四层，每层有各自的"最可疑指标"，这是定位的第一依据：

| 层 | 代表指标 | 典型症状 | 高并发下的典型根因 |
|---|---|---|---|
| 连接层 | Threads_connected、池活跃数 | 接口超时、报 1040 | 连接泄漏、慢查询放大 |
| SQL 层 | 慢日志占比、锁等待次数 | 特定接口变慢 | 索引缺失、计划漂移 |
| 引擎层 | 命中率、脏页、redo 等待 | 整体 RT 波动 | Buffer Pool 过小、刷盘瓶颈 |
| IO 层 | await、IOPS 利用率 | 磁盘响应随负载恶化 | 存储规格不足、随机写放大 |

层与层会**互相伪装**：连接层打满可能是 SQL 层慢查询放大出来的；SQL 层变慢可能是引擎层刷盘抢 IO 引起的；引擎层压力可能是 IO 层规格不够。所以定位必须自顶向下分层排除——先确认连接层健康（有无排队），再看 SQL 层（慢日志有没有新增），再看引擎与 IO（状态变量与系统监控）。每排除一层就记录依据，避免在错误层反复折腾。

层间伪装的典型剧本值得提前熟悉：深夜批量任务占满磁盘 IO → 引擎层刷盘抢不到带宽 → 所有查询 RT 抬升 → 应用侧连接需求翻倍 → 连接池排队报警——表面是连接问题，根因在 IO 层。反过来，一条全表扫描把 CPU 打满，表现却是"慢日志暴涨 + Threads_running 高"，三层信号同时亮。定位的价值就在于把信号按层归类，再按"成本最低的证据"逐层求证，而不是看到连接报警就去调连接参数。

## 3. 数据驱动的调优闭环

调优是实验科学，标准流程五步，每一步都以数据为准：

1. **建基线**：开慢日志（`long_query_time=1`）、按需开 performance_schema、接入 Prometheus 的 QPS/RT/连接数/命中率指标，采集一周期数据。
2. **定位**：用 RED 视角（Rate 错误率、Errors、Duration 延迟）先定性，再用四层模型逐层排除定量——"哪个接口、哪类 SQL、什么等待"。
3. **提出假设**：如"P99 上涨集中在订单接口，慢日志出现全表扫描，索引缺失导致 RT 放大"——假设必须可验证。
4. **实验验证**：一次只改一个变量（一个索引、一个参数），用 `SET PERSIST` 热生效便于回滚，压测或灰度验证前后基线对比。多变量同改无法归因，是新手最常见错误。
5. **固化**：把有效的优化沉淀为规范（索引评审、参数基线、告警），让回归在变更时立刻暴露，而不是下次事故再排查一遍。

配套两条纪律：**先代码后参数**——SQL 与索引是最高杠杆，参数是最后手段，参数见效快但掩盖根因；**监控常态化**——没有监控的调优是碰运气，告警要"少而准"（详见[专题 1 01 篇](../专题%201：性能理论基础/01-性能指标体系.md)的告警设计）。

基线采集不必一步到位，按"先指标后明细"的顺序渐进：第一天只接四类服务侧指标（QPS/TPS/Threads_running/Buffer Pool 命中率），第三天补慢日志与锁等待计数，一周内补全 EXPLAIN 采样与错误率——基线越早越粗地建立，越早能回答"这是回归还是常态"。注意基线要带**流量上下文**：记录当时 QPS 量级与时间窗口（白天高峰 vs 凌晨），没有上下文的数据无法对比，口径要求与采样纪律见[专题 1 01 篇](../专题%201：性能理论基础/01-性能指标体系.md)。

## 4. 调优的边界

数据库调优解决不了的问题必须认得出来，否则在错误层浪费大量时间：

- **应用侧问题伪装成数据库问题**：连接池耗尽但数据库 Threads_running 很低、QPS 不高——是应用把连接借走不还，属 [06 篇](06-连接管理与并发控制.md) 的连接治理范畴，调数据库参数无用。
- **本应被缓存挡掉的读流量**：热点读全部打库，Buffer Pool 命中率再高也扛不住——先上缓存层（Redis 体系见 [02-.../02-非关系型数据库/Redis](../../../02-后端核心技术%20微服务%20分布式%20云原生/02-非关系型数据库/Redis/)），数据库只该承担"必须落库"的读写。
- **上游与网络延迟**：客户端到 DB 之间的 RT 大头在网络或中间件，jstack 与抓包定位，不是库内问题。
- **业务规模本身超载**：QPS 需求超过单机上限，调优只是延后，正确动作是[扩展决策](09-读写分离与分库分表.md)（读写分离、分片）或异步削峰。

判断框架：**先看连接数与 Threads_running**——连接打满但 Threads_running 低，是泄漏；连接没满但 Threads_running 高且慢日志暴涨，是 SQL 层；连接与慢日志都正常而整体 RT 高，才轮到引擎与 IO 层。顺序永远自顶向下，证据优先于直觉。

> 🎯 **核心要点**：数据库性能由连接/SQL/引擎/IO 四层共同决定，层间互相伪装，定位必须自顶向下分层排除；Little's Law 揭示了"RT 压缩带动全局"的杠杆；调优是"基线→定位→假设→实验→固化"的实验流程，一次一变量、先代码后参数、监控常态化；先确认瓶颈在数据库层再动手，连接泄漏、缓存缺失、网络延迟不是数据库的职责。
