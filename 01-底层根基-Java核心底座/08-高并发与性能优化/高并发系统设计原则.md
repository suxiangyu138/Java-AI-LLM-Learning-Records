## 1. 核心指标

| 指标 | 含义 | 典型值 |
|------|------|:------:|
| **QPS** | 每秒请求数 | 10000 |
| **RT** | 响应时间 | P99 < 100ms |
| **并发数** | 同时处理的请求数 | 1000 |
| **可用性** | 正常运行时间比例 | 99.99%（全年宕机 < 53 分钟） |

## 2. 五大设计原则

### 2.1 缓存先行

```text
浏览器缓存 → CDN → Nginx 缓存 → Redis → 本地缓存(Caffeine)
```

| 层级 | 方案 |
|------|------|
| 静态资源 | CDN |
| 热点数据 | Redis |
| 极热点数据 | Caffeine 本地缓存（微秒级） |

### 2.2 池化复用

| 池类型 | 说明 |
|--------|------|
| **连接池** | 数据库、Redis、HTTP 客户端都要用连接池 |
| **线程池** | 异步任务用线程池，不要 `new Thread()` |
| **对象池** | 大开销对象复用（如 Protobuf Builder） |

### 2.3 异步解耦

| 策略 | 做法 |
|------|------|
| 非核心逻辑异步化 | 注册后发短信 → MQ 异步处理 |
| 响应式编程 | IO 密集型用 WebFlux 提升吞吐 |
| 批量合并 | 多条 SQL 合并、多次 Redis 调用合并为 Pipeline |

### 2.4 削峰填谷

| 手段 | 工具 |
|------|------|
| 消息队列 | 突发请求先进队列 |
| **限流** | Sentinel / RateLimiter |
| **降级** | 高峰期关闭非核心功能 |
| **熔断** | 下游不可用时快速失败 |

### 2.5 读写分离 + 分库分表

| 策略 | 做法 |
|------|------|
| 一主多从 | 写走主库，读走从库 |
| 分库分表 | ShardingSphere |
| 冷热分离 | 热数据 Redis/SSD，历史数据归档 |

## 3. 常见方案速查

| 问题 | 方案 | 工具 |
|------|------|------|
| 热点数据 | 多级缓存 | Caffeine + Redis |
| 大量请求 | 限流 | Sentinel / Guava RateLimiter |
| 秒杀超卖 | 分布式锁 + Lua | Redisson + Redis |
| 接口响应慢 | 异步 + 缓存预热 | RocketMQ + 定时任务 |
| DB 扛不住 | 读写分离 / 分表 | ShardingSphere |
| 服务雪崩 | 熔断 + 降级 | Sentinel / Resilience4j |
| 重复下单 | 幂等设计 | MySQL 唯一索引 + Redis |
| 数据一致性 | 最终一致 + 补偿 + 对账 | MQ + 定时任务 |

## 5. 面试高频题

### Q: 如何设计一个秒杀系统？

**九层保护**：

```text
① 前端：按钮置灰 + 防重复点击
② CDN：静态资源走 CDN
③ 网关：IP 限流
④ Nginx：并发连接数限制
⑤ 服务层：Sentinel 接口限流
⑥ Redis：预减库存（Lua 原子操作）
⑦ MQ：下单请求入队消峰
⑧ DB：扣减最终库存
⑨ 对账：发现超卖回补
```

### Q: 缓存和数据库一致性怎么保证？

> **Cache Aside**：更新数据库后删除缓存。复杂场景用 **Canal 监听 binlog** 异步更新缓存。

### Q: 亿级流量下怎么扩容？

```text
横向扩展（加机器）→ 无状态服务随意扩 → 数据库读写分离 → 分库分表 → 多级缓存 → CDN
```

---

> 🎯 **核心总结**：高并发 = 缓存（空间换时间）+ 异步（削峰填谷）+ 拆分（分而治之）。所有的优化都是这三者的组合。
