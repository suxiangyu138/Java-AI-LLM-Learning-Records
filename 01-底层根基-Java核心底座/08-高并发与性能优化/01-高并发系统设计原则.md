## 1. 核心性能指标

高并发系统的性能必须用量化指标来衡量与监控，不能凭感觉优化。

### 1.1 关键指标速查

| 指标 | 全称 | 含义 | 典型目标值 |
|------|------|------|:----------:|
| **QPS** | Queries Per Second | 每秒查询数，衡量读请求处理能力 | 10000+ |
| **TPS** | Transactions Per Second | 每秒事务数，衡量完整事务处理能力 | 1000+ |
| **RT** | Response Time | 响应时间，从请求发出到收到完整响应 | P99 < 200ms |
| **并发用户数** | Concurrent Users | 系统同时承载的活跃用户数 | 因场景而异 |
| **可用性** | Availability | 正常运行时间占总时间的比例 | 99.99%+ |

> 💡 **P99 比平均值更重要**：平均值容易被少数极快请求拉低，P99（99%请求的响应时间）更能反映真实用户体验。例如平均 RT 50ms 但 P99 可能高达 500ms，意味着 1% 的用户体验极差。

### 1.2 可用性等级（几个9）

| 可用性 | 年宕机时间 | 典型场景 |
|--------|-----------|----------|
| 99%（两个9） | 87.6 小时 | 内部系统、开发环境 |
| 99.9%（三个9） | 8.76 小时 | 多数互联网业务可接受 |
| 99.99%（四个9） | 52.56 分钟 | 关键业务系统、支付系统 |
| 99.999%（五个9） | 5.26 分钟 | 电信级、金融核心系统 |

> ⚠️ 达到四个9意味着全年宕机不能超过 53 分钟，需要完善的故障检测、自动切换和容错机制。

## 2. 三高设计目标

高并发系统设计的核心目标可以归纳为三个维度：**高性能、高可用、高可扩展**，简称"三高"。

### 2.1 高性能 (High Performance)

| 维度 | 说明 | 度量方式 |
|------|------|----------|
| **低延迟** | 单个请求处理速度快 | RT（平均/P99/P999） |
| **高吞吐** | 单位时间内处理请求数量多 | QPS / TPS |

互联网场景下用户期望页面加载在 **200ms 以内**，金融交易场景要求在几十毫秒内完成。

### 2.2 高可用 (High Availability)

系统在面对各种故障时仍能持续提供服务的能力。高可用不是"不宕机"，而是"宕机后能快速恢复"——**MTBF（平均无故障时间）** 和 **MTTR（平均恢复时间）** 是核心衡量指标。

**实现手段**：
- 冗余部署：消除单点故障
- 故障自动转移：Keepalived、Sentinel
- 多活架构：同城双活、两地三中心
- 灰度发布：新功能小范围上线验证

### 2.3 高可扩展 (High Scalability)

系统通过增加资源（硬件）来提升处理能力的能力。

| 扩展方式 | 做法 | 成本 | 灵活性 |
|----------|------|:----:|:------:|
| **水平扩展** | 增加更多服务器节点 | 低 | 高 |
| **垂直扩展** | 升级单机硬件（CPU/内存/磁盘） | 高 | 低 |

理想系统应具备**水平扩展**能力——通过增加节点线性提升处理能力，不需修改代码架构。

## 3. 三大核心思想

高并发系统设计背后可归纳为六个字：**缓存、异步、拆分**。

### 3.1 缓存（空间换时间）

将计算结果或数据副本存储在更快的存储介质中。据统计，引入合适的缓存策略可将系统响应时间降低一个数量级甚至更多。

**缓存层级**：
```
浏览器缓存 → CDN → Nginx本地缓存 → 本地缓存(Caffeine) → 分布式缓存(Redis) → 数据库
```

### 3.2 异步（削峰填谷）

将同步阻塞操作转化为非阻塞操作，提高系统吞吐能力。核心场景是"削峰填谷"——流量高峰时将请求先放入消息队列暂存，后端服务按自身处理能力消费。

### 3.3 拆分（分而治之）

| 拆分层面 | 具体做法 |
|----------|----------|
| 业务拆分 | 微服务化 |
| 数据拆分 | 分库分表 |
| 功能拆分 | 读写分离 |

通过将大系统拆解为多个小系统，独立部署、独立扩缩容，降低系统复杂度，提升可用性和可维护性。

## 4. CAP 定理与 BASE 理论

### 4.1 CAP 定理

分布式系统无法同时满足以下三个特性，最多只能同时满足两个：

| 特性 | 全称 | 含义 |
|------|------|------|
| **C** | Consistency（一致性） | 所有节点在同一时刻看到相同的数据 |
| **A** | Availability（可用性） | 每个请求都能获得一个（非错误的）响应 |
| **P** | Partition Tolerance（分区容忍性） | 系统在网络分区时仍能正常运行 |

**CAP 组合选择**：

| 选择 | 特点 | 典型系统 |
|------|------|----------|
| **CP** | 放弃可用性，保证一致性和分区容忍性 | Zookeeper、Etcd、HBase |
| **AP** | 放弃强一致性，保证可用性和分区容忍性 | Eureka、Cassandra、DynamoDB |
| **CA** | 放弃分区容忍性（实际不存在，网络分区必然发生） | 单机数据库 |

> 💡 在实际分布式系统中，**网络分区是必然会发生**的，所以 P 是必须选择的。真正的权衡在 C 和 A 之间：是选择强一致性（CP）还是高可用（AP）。

### 4.2 BASE 理论

BASE 是对 CAP 中 AP 方案的延伸，核心思想是**即使无法做到强一致性，也可以采用适当的方式达到最终一致性**。

| 要素 | 全称 | 含义 |
|------|------|------|
| **BA** | Basically Available | 基本可用——系统出现故障时允许损失部分可用性 |
| **S** | Soft State | 软状态——允许系统存在中间状态 |
| **E** | Eventually Consistent | 最终一致性——经过一段时间后数据最终达到一致 |

> 🎯 BASE 理论的核心：**可用性优先，允许短暂不一致，但保证最终一致**。这是绝大多数互联网业务系统的设计哲学。

## 5. 限流算法

限流是保护系统不被流量冲垮的第一道防线。常见的限流算法有四种。

### 5.1 算法对比

| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **固定窗口** | 固定时间窗口内计数达到阈值则拒绝 | 实现简单 | 存在边界突刺问题 | 粗略限流 |
| **滑动窗口** | 将窗口划分为小格子，滑动统计 | 限流平滑，无边界问题 | 内存占用随精度增加 | 通用限流 |
| **漏桶** | 恒定速率处理，桶满丢弃 | 输出流量绝对平滑 | 无法应对突发流量 | 保护下游系统 |
| **令牌桶** | 恒定速率生成令牌，消耗令牌通过 | 允许一定突发流量 | 桶大小需合理设置 | 通用限流，最常用 |

### 5.2 固定窗口的问题

```
时间窗口: 1秒  阈值: 100

第一个窗口最后100ms:  100个请求（计数100，达到阈值）
第二个窗口最初100ms:  100个请求（计数重置后再次达到阈值）

结果：200ms内承受200个请求冲击，远超阈值
```

> ⚠️ **边界突刺问题**：固定窗口在窗口切换边界可能出现流量翻倍的情况。滑动窗口通过细化粒度解决此问题。

### 5.3 令牌桶实现（Guava RateLimiter）

```java
// 创建令牌桶，每秒生成100个令牌
RateLimiter limiter = RateLimiter.create(100);

public void handleRequest() {
    // 获取令牌，阻塞直到获取成功（或超时）
    boolean acquired = limiter.tryAcquire(500, TimeUnit.MILLISECONDS);
    if (!acquired) {
        // 返回限流提示
        return "系统繁忙，请稍后再试";
    }
    // 处理业务逻辑
}
```

### 5.4 Sentinel 实现

```java
@SentinelResource(value = "getOrder", blockHandler = "handleBlock")
public Order getOrder(Long orderId) {
    // 业务逻辑
    return orderService.getOrder(orderId);
}

public Order handleBlock(Long orderId, BlockException e) {
    // 限流后的兜底处理
    return new Order();
}
```

### 5.5 限流维度

| 维度 | 说明 | 典型阈值 |
|------|------|:--------:|
| **接口维度** | 不同 API 设置不同阈值 | 查询 1000 QPS，下单 100 QPS |
| **IP 维度** | 限制单个 IP 的访问频率 | 10~100 QPS |
| **用户维度** | 不同用户等级不同权限 | 普通 10 QPS，VIP 100 QPS |
| **全局 + 单机** | 集群总限流 + 单机补充 | Redis+Lua 全局，本地限流兜底 |

**Sentinel 集群限流配置**：

```yaml
flow:
  - resource: "getOrder"
    clusterMode: true     # 开启集群限流
    count: 1000            # 集群总 QPS
    grade: 1               # 1=QPS, 0=线程数
    controlBehavior: 0     # 0=快速失败, 1=Warm Up, 2=排队等待
```

## 6. 熔断机制

熔断借鉴了电路断路器的概念。当系统检测到某个依赖服务的错误率达到阈值时，断路器打开，后续请求直接返回错误（快速失败），给下游服务恢复的时间。

### 6.1 断路器三态模型

```
Closed（关闭）
    └── 错误率达到阈值 → Open（打开）
Open（打开）
    └── 超时时间到达 → Half-Open（半开）
Half-Open（半开）
    ├── 探测请求成功 → Closed（关闭）
    └── 探测请求失败 → Open（打开）
```

| 状态 | 含义 | 行为 |
|------|------|------|
| **Closed** | 关闭（正常） | 请求正常通过，统计错误率 |
| **Open** | 打开（熔断） | 请求直接返回错误，不调用下游 |
| **Half-Open** | 半开（探测） | 放行少量请求，检查下游是否恢复 |

### 6.2 Sentinel 熔断配置

```yaml
degrade:
  - resource: "paymentService"
    grade: 0           # 0=RT, 1=异常比例, 2=异常数
    count: 200          # RT超过200ms触发
    timeWindow: 10      # 熔断时长（秒）
    minRequestAmount: 5 # 触发熔断的最小请求数
    statIntervalMs: 1000
```

### 6.3 Resilience4j 熔断配置

```java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)                          // 失败率阈值 50%
    .waitDurationInOpenState(Duration.ofSeconds(10))   // 熔断持续时间
    .slidingWindowSize(100)                            // 滑动窗口大小
    .minimumNumberOfCalls(10)                          // 最小调用数
    .build();

CircuitBreaker breaker = CircuitBreaker.of("paymentService", config);
Supplier<Result> supplier = CircuitBreaker.decorateSupplier(breaker, () -> paymentService.call());
```

## 7. 降级策略

降级是系统在压力过大时，主动牺牲非核心功能，保证核心功能的可用性，属于"有损服务"思想。

### 7.1 降级策略速查

| 策略 | 说明 | 示例 |
|------|------|------|
| **非核心功能关闭** | 停用非关键业务 | 大促关闭"商品推荐"、"历史浏览" |
| **返回兜底数据** | 用默认值替代真实数据 | 推荐不可用时返回热门商品列表 |
| **返回静态页面** | 动态降级为静态缓存 | 详情页降级为 CDN 静态缓存 |
| **简化业务流程** | 省略非关键步骤 | "先下单后支付"延迟扣款 |

### 7.2 降级触发方式

| 方式 | 优点 | 缺点 |
|------|------|------|
| **手动降级** | 可控性强，人为判断准确 | 响应慢，需要运维介入 |
| **自动降级** | 响应快，秒级触发 | 可能误判，需合理配置阈值 |

## 8. 容量规划与水位线

### 8.1 资源水位线建议

超过水位线后，系统响应时间会急剧上升，进入"过载"状态。

| 资源 | 建议水位线 | 原因 |
|------|:----------:|------|
| **CPU** | < 70% | 预留 30% 应对突发流量 |
| **内存** | < 80% | 避免 GC 压力过大和 OOM |
| **磁盘 IO** | < 70% | IO 饱和导致请求排队 |
| **网络带宽** | < 70% | 预留流量裕度 |

### 8.2 容量评估方法

```
预期 QPS × 单请求资源消耗 × 冗余系数 = 所需资源
```

例如：预期 10000 QPS，单请求消耗 10ms CPU，冗余系数 1.5：
```
所需 CPU 核心数 = 10000 × 0.01 × 1.5 = 150 核
```

## 9. 缓存设计原则

### 9.1 缓存更新策略对比

| 策略 | 读操作 | 写操作 | 一致性 | 复杂度 |
|------|--------|--------|:------:|:------:|
| **Cache Aside（旁路缓存）** | 读缓存→未命中读DB→回填缓存 | 更新DB→删除缓存 | 最终一致 | 低 |
| **Read/Write Through（读写穿透）** | 缓存代理层统一处理 | 缓存代理层统一处理 | 强 | 高 |
| **Write Behind（异步写回）** | 读缓存 | 写缓存后异步批量写DB | 弱 | 中 |

### 9.2 为什么先更新 DB 后删缓存？

**错误做法（先删缓存后更新DB）**：
```
1. 线程A 删除缓存
2. 线程B 读请求→缓存为空→读DB得到旧值→旧值写入缓存
3. 线程A 更新DB为新值
4. 结果：缓存中一直是旧值，数据永久不一致 ❌
```

**正确做法（先更新DB后删缓存）**：
```
1. 线程A 更新DB
2. 线程B 读请求→命中缓存（旧值）直接返回（短暂不一致）
3. 线程A 删除缓存
4. 后续请求读DB并将新值写入缓存 ✓
```

> ⚠️ "先更新DB后删缓存"仍存在短暂的不一致窗口（约几毫秒），但概率极低，可通过设置缓存过期时间来保证最终一致性。

### 9.3 Java Cache Aside 示例

```java
public class CacheAsideService {
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private JdbcTemplate jdbcTemplate;

    public Object getData(String key) {
        // 先读缓存
        Object value = redisTemplate.opsForValue().get(key);
        if (value != null) {
            return value;
        }
        // 缓存未命中，读数据库
        value = jdbcTemplate.queryForObject(
            "SELECT data FROM table WHERE key=?", Object.class, key);
        if (value != null) {
            // 写入缓存，设置过期时间
            redisTemplate.opsForValue().set(key, value, 30, TimeUnit.MINUTES);
        }
        return value;
    }

    public void updateData(String key, Object newValue) {
        // 先更新数据库
        jdbcTemplate.update("UPDATE table SET data=? WHERE key=?", newValue, key);
        // 后删除缓存
        redisTemplate.delete(key);
    }
}
```

## 10. 最终一致性与幂等设计

### 10.1 最终一致性方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **本地消息表** | 业务操作与消息写入同本地事务，定时任务发送 | 实现简单，不依赖外部中间件 | 业务代码侵入，需轮询数据库 |
| **事务消息（RocketMQ）** | 半消息对消费者不可见，本地事务成功后再 Commit | 解耦彻底，消息不丢失 | 依赖 RocketMQ 特性 |
| **对账系统** | 定期比对多方数据，不一致则修复 | 兜底方案，最终防线 | 事后修复，有延迟 |

### 10.2 本地消息表流程

```
业务操作（如创建订单）
    ↓ (同一本地事务)
写入业务表 + 写入本地消息表（状态=待发送）
    ↓
定时任务扫描本地消息表，发送到 MQ
    ↓ (发送成功)
更新本地消息表状态（状态=已发送）
    ↓ (发送失败)
定时任务重试，直到成功
```

### 10.3 事务消息（RocketMQ）

```java
public class OrderService {
    @Autowired
    private TransactionMQProducer producer;

    public void createOrder(Order order) {
        // 发送事务消息
        Message msg = new Message("order-topic", JSON.toJSONBytes(order));
        TransactionSendResult result = producer.sendMessageInTransaction(msg, order);
        if (result.getLocalTransactionState() == LocalTransactionState.COMMIT_MESSAGE) {
            // 事务提交成功
        }
    }

    @Transactional
    public void executeLocalTransaction(Order order) {
        // 执行本地事务：扣减库存、生成订单
        orderMapper.insert(order);
        stockMapper.deduct(order.getProductId(), order.getQuantity());
    }
}
```

### 10.4 幂等设计

幂等是指同一个操作无论执行多少次，结果与执行一次相同。在高并发系统中，重复请求是常态（网络重试、MQ 重复消费），幂等是保证数据一致性的基石。

| 实现方式 | 说明 | 适用场景 |
|----------|------|----------|
| **唯一索引** | 数据库唯一约束防止重复插入 | 订单号、流水号唯一 |
| **Redis 分布式锁** | 处理前加锁，处理完释放 | 扣减库存、领取优惠券 |
| **状态机** | 业务状态有向流转，不可逆 | 订单状态（待支付→已支付→已发货） |
| **去重表** | 用独立去重表记录已处理的请求 ID | 消息消费去重 |
| **Token 机制** | 前端请求先获取 Token，提交时携带 | 表单重复提交 |

- [ ] 缓存更新策略是否选择了 Cache Aside（更新DB后删缓存）？
- [ ] 是否设计了缓存过期时间保证最终一致性？
- [ ] 是否存在数据不一致场景需要最终一致性方案？
- [ ] 关键接口是否实现了幂等（唯一索引 / 去重表 / Token）？
- [ ] 是否制定了资源水位线和容量规划？

---

> 🎯 **核心总结**：高并发系统设计的本质 = **缓存（空间换时间）** + **异步（削峰填谷）** + **拆分（分而治之）**。原则层面核心是 **CAP/BASE 指导一致性选型**，**限流/熔断/降级构成系统自我保护的三重防线**。所有的优化手段都是这三者与三者的组合。
