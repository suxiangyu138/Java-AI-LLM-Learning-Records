## 4. 核心性能指标速查

### 4.1 基础指标

| 指标 | 全称 | 定义 | 度量方式 | 典型目标 |
|:----:|------|------|:--------:|:--------:|
| **QPS** | Queries Per Second | 每秒查询次数 | 总查询数 / 时间窗口 | 10000+ |
| **TPS** | Transactions Per Second | 每秒事务数 | 总事务数 / 时间窗口 | 1000+ |
| **RT** | Response Time | 响应时间 | 请求发出到收到响应的时间 | P99 < 200ms |
| **吞吐量** | Throughput | 单位时间处理的数据量 | QPS × 单请求平均数据量 | 因场景而异 |
| **并发数** | Concurrency | 系统同时处理的请求数 | 活跃连接数 | 与QPS/RT相关 |

> 💡 **Little 定律**：`并发数 = QPS × RT`。当 RT 从 50ms 增加到 200ms，在相同并发数下 QPS 下降 75%。

### 4.2 延迟分位数

| 分位 | 含义 | 说明 | 业务建议 |
|:----:|------|------|----------|
| **P50** | 中位数 | 50% 的请求快于此值 | 反映典型体验 |
| **P90** | 90 分位 | 90% 的请求快于此值 | 反映大多数用户体验 |
| **P99** | 99 分位 | 99% 的请求快于此值 | 核心监控指标 |
| **P999** | 99.9 分位 | 99.9% 的请求快于此值 | 反映长尾延迟 |
| **MAX** | 最大值 | 最慢请求的耗时 | 关注异常值 |

> ⚠️ **P99 陷阱**：在分布式系统中，请求经过 N 个服务，整体 P99 = 1 - (1 - 单服务 P99) ^ N。例如单服务 P99 = 99%，经过 10 个服务后整体 P99 = 1 - 0.99^10 ≈ 9.6%（即 90.4% 的请求在 P99 以内）。这就是为什么微服务架构下延迟控制更难。

### 4.3 可用性等级

| 等级 | 年宕机时间 | 月宕机时间 | 典型场景 |
|:----:|:----------:|:----------:|----------|
| 90%（1个9） | 876 小时 | 72 小时 | 个人项目 |
| 99%（2个9） | 87.6 小时 | 7.2 小时 | 内部管理系统 |
| 99.9%（3个9） | 8.76 小时 | 43.2 分钟 | 普通互联网业务 |
| **99.99%（4个9）** | **52.56 分钟** | **4.32 分钟** | **关键业务系统** |
| 99.999%（5个9） | 5.26 分钟 | 25.9 秒 | 金融核心、电信级 |

### 4.4 指标间的关系

```
        吞吐量（QPS）
            ↑
     ┌──────┴──────┐
     │             │
   并发数        处理速度（1/RT）
     │             │
     └─────────────┘
     Little定律：并发数 = QPS × RT

例：目标 QPS = 10000，平均 RT = 100ms
    需要并发数 = 10000 × 0.1 = 1000
```

> 🎯 性能优化的本质就是降低 RT 或提升并发处理能力。降低 RT 更有效——RT 减半意味着相同并发数下 QPS 翻倍。

## 5. 三高目标关系图

高性能、高可用、高可扩展是高并发系统的三大目标，三者相互制约、相互促进。

### 5.1 三高关系三角

```
                    高性能
                 (低延迟 + 高吞吐)
                    /    \
                   /      \
                  /        \
                 /          \
                /            \
        高可用 ─────────────── 高可扩展
    (故障自愈 + 持续可用)     (水平拓展 + 弹性伸缩)
```

### 5.2 三高权衡速查

| 目标 | 定义 | 核心指标 | 实现手段 | 常见技术 |
|:----:|------|:--------:|----------|----------|
| **高性能** | 低延迟 + 高吞吐 | RT / QPS / TPS | 缓存 / 异步 / 并行 / 缩短链路 | Redis / Caffeine / CompletableFuture / CDN |
| **高可用** | 故障时持续可用 | 可用性（几个9） | 冗余 / 故障转移 / 读写分离 | 主从复制 / Sentinel / Keepalived / 多活 |
| **高可扩展** | 增加资源提升性能 | 加速比（Speedup） | 无状态设计 / 水平分片 / 微服务化 | Kubernetes / ShardingSphere / Consistent Hashing |

### 5.3 三高冲突与平衡

```
高性能 ← → 高可用:
  缓存提升性能，但引入一致性问题（C 与 A 的权衡）
  主从复制提升可用性，但引入主从延迟（影响读取性能）

高性能 ← → 高可扩展:
  无状态设计利于扩展，但需要外部存储（增加 RT）
  分库分表可扩展，但跨分片查询性能下降

高可用 ← → 高可扩展:
  多副本提升可用性，但扩展时需要同步数据
  分布式共识（Raft/Paxos）保证可用，但扩展节点时变复杂
```

> 💡 实际工作中不需要一次性追求"三高极致"。根据业务阶段选择合适的平衡点——**初创期优先可用性，增长期重视可扩展，成熟期追求高性能**。

### 7.7 开放性问题（🔥🔥🔥）

| 问题类型 | 典型问题 | 考察点 |
|----------|----------|--------|
| 场景题 | "假设数据库抗不住 10 万 QPS，你怎么办？" | 逐层分析（缓存 → 限流 → 拆分） |
| 权衡题 | "一致性要求极高但又要高可用，怎么设计？" | Paxos/Raft + 妥协方案 |
| 故障题 | "突然出现大量超时，如何排查？" | 问题排查链路 |
| 优化题 | "接口 RT 从 200ms 降到 50ms 有什么思路？" | 逐层优化方法论 |

> 💡 面试时遇到开放性问题，建议采用**分层思考法**：接入层 → 服务层 → 缓存层 → 数据层，逐层分析瓶颈与解决方案。先定位瓶颈再给出方案比直接抛方案更有结构感。
