## 1. 指标族全景

性能指标分两类：**业务侧指标**描述系统对外表现（吞吐、延迟、正确性），**资源侧指标**描述内部消耗（CPU、内存、IO、网络）。两者必须成对看：QPS 很高但 CPU 已 95%，说明系统在红线边缘跳舞，任何突发流量都会击穿；反之资源空闲但 RT 很高，说明瓶颈在锁、等待或架构层。

| 指标 | 含义 | 关键点 |
|---|---|---|
| QPS | 每秒查询数 | 单条请求即计数，不论成败，偏入口/网关口径 |
| TPS | 每秒事务数 | 完整业务事务（下单=查库存+扣库存+生成订单），只统计成功，后端核心达标指标 |
| RT | 响应时间 | 单次请求总耗时；平均 RT 掩盖长尾，价值有限 |
| 并发数 | 同时在途请求 | 活跃请求数 ≠ 在线人数，由 QPS 与 RT 决定 |
| 错误率 | 失败请求占比 | 4xx/5xx/超时/连接拒绝，目标 <0.1% |
| 资源利用率 | CPU/内存/IO 占用 | CPU<70%、内存<80%、连接池<80% 为常见水位线 |

## 2. 指标间关系

并发数、QPS、RT 三者被 Little's Law 绑定：**并发数 = QPS × RT**（推导见 03 篇）。这条公式有三个工程用途：

- **推算容量**：目标 QPS=1000、RT=200ms，则系统需维持 200 个在途并发；压测机线程数就按此设置，而不是拍脑袋的 5000。
- **排查异常**：并发数突然飙高，要么 QPS 涨了，要么 RT 涨了——后者往往是慢 SQL、GC 停顿、第三方超时的信号，是定位问题的第一入口。
- **反向验证**：压测结果中并发数、QPS、RT 三者必须满足公式，若偏离说明压测工具口径有问题（比如把已完成的请求仍计入并发）。

## 3. 口径陷阱

- **QPS ≠ TPS**：网关层 QPS 高不代表业务成功率高，一次下单请求可能连带 5 次内部调用；对外宣称"10 万 QPS"前先确认口径，面试被追问时口径一致是加分项。
- **平均 RT 是谎言**：100 个请求 90 个 100ms、10 个 5s，平均 590ms"看着还行"，实际 10% 用户在骂娘。必须看分布（02 篇）。
- **错误口径要提前定义**：超时后重试成功，算失败还是成功？压测工具统计的"请求失败"与业务口径的"事务失败"不同，评审时先对齐。
- **环境不可比**：本机、测试、生产环境的 RT 不能互相引用——配置、数据量级、网络拓扑都不同，对比必须同口径同时期。
- **口径要写进文档**：团队内明确一份指标口径说明（QPS 统计窗口、错误率分母、百分位分桶），评审与对账都以此为准——口头对齐的口径，三个月后必然各说各话。

## 4. 达标标准参考

| 指标 | 参考标准 | 说明 |
|---|---|---|
| P99 响应时间 | 读接口 <500ms，写接口 <1s | 核心考核指标 |
| 平均 RT | <200ms | 仅作辅助参考 |
| 错误率 | <0.1% | 含超时与 5xx |
| CPU 利用率 | <70% | 高吞吐业务水位线 |
| 内存利用率 | <80% | 预留 GC 与突发 |
| 数据库/Redis 连接池 | <80% | 超过易触发排队 |
| 磁盘 IO 等待 | await<10ms，>50ms 即高负载 | iostat 口径 |

标准随业务形态变化：ToB 系统看 P95 即可，ToC 秒杀系统必须盯 P999；交互型接口优先延迟，批处理任务优先吞吐。标准的作用是让"优化有没有效果"有判据——没有基线的优化报告等于自嗨。

## 5. 指标选型决策

- 用户可感知的接口（列表、下单、详情）：**P99 延迟优先**，QPS 是容量约束而非体验指标。
- 后台批处理/异步消费：**吞吐与积压优先**——QPS、消费速率、队列 Lag。
- 网关/入口层：**QPS、错误率、限流触发次数**，是流量压力的第一观测点。
- 中间件（DB/Redis/MQ）：**连接数、命中率、慢查询数、堆积量**——它们往往是应用延迟的传导源，中间件指标先于应用指标恶化。
- 基础设施：**CPU/内存/网络/磁盘**四件套 + 上下文切换、Swap，用于区分"资源不够"与"代码低效"。

指标最终要落到 **SLO（服务级别目标）**：一个接口的完整 SLO 形如"P99 ≤ 300ms 且错误率 ≤ 0.1%，按 30 天滚动评估"——同时约束延迟与错误，配评估周期。SLO 的价值是让"快还是慢"有客观判据：SLO 达标与否直接决定优化优先级与告警分级，性能工作从"感觉慢"升级为"偏离目标"。SLO 定太紧（P99 50ms）会制造大量无效优化，定太松（P99 5s）等于没有——从用户可感知阈值反推，是主流定法。

## 6. 指标传导链：谁先恶化，定位谁

指标不是孤立的，它们沿调用链传导：**资源指标（CPU/连接）→ 中间件指标（连接池排队、慢查询）→ 业务指标（P99/错误率）**。业务指标恶化时，链路下游的中间件指标一定更早出现异常——连接池排队计数上升先于接口 P99 上升，慢查询数增长先于下单超时出现。排查时沿传导链倒查：看业务指标 → 找中间件指标最早恶化的那层 → 用资源指标取证。掌握传导链，比背任何告警阈值都重要：阈值会随业务变，传导顺序不会。

## 7. 指标采集与告警实践

采集层面：接口 RT 用 **Histogram 埋点**而非平均值——Prometheus histogram（分桶）或 Micrometer 的 PercentileHistogram，按 1 分钟窗口聚合百分位；百分位必须在服务端聚合，客户端算好上报会丢失分布信息。日志埋点输出结构化字段（method、status、latency_ms、trace_id），供离线做慢请求采样分析。

统计细节：P99 在窗口内请求量太小时无意义（几百条起才有统计价值）；线上 P99 与压测 P99 对比时，两边的直方图分桶必须一致，否则数字不可比——这是压测报告对不上线上数据的常见原因。

从指标到行动：把指标映射为动作清单——P99 上升但 QPS 平稳 → 查慢依赖、GC、锁；QPS 上升且 P99 平稳 → 容量正常，继续观察水位；错误率上升 → 先分 4xx/5xx 与超时占比，判断业务错误还是系统故障。告警遵循"少而准"：只告警需要人介入的（P99 超 SLO 连续 5 分钟、错误率 >0.1%、连接池 >80%），指标抖动交给仪表盘，告警刷屏等于没有告警。

> 🎯 **核心要点**：先统一口径（QPS 还是 TPS、平均还是 P99、错误怎么算），再谈优化；任何优化结论必须挂在指标前后对比上，否则不可信。
