## 1. Amdahl 定律：并行加速的天花板

任务总耗时 = 串行部分 + 可并行部分。加速比公式：

```
Speedup = 1 / (串行比例 + (1 - 串行比例) / N)   # N = 处理器/线程数
```

示例：串行比例 10% 时，16 核加速上限 = 1 / (0.1 + 0.9/16) ≈ 6.4 倍；核数翻到 32，也只到 7.8 倍——收益趋缓的曲线一目了然。串行比例的实测方法：单线程压测占总耗时比（对比 1 线程与 N 线程的耗时差），或火焰图里看锁等待与单点段的占比。

两个推论价值远超公式本身：

- **优化非瓶颈 = 零收益**：若串行比例占 20%，即使并行部分无限优化，加速上限也只有 5 倍。这直接导出"木桶效应"——先找瓶颈再优化（05 篇）。
- **递减回报**：N 从 4 加到 8，加速比提升远小于 N 翻倍；当 N→∞，加速比趋近 1/串行比例。加机器解决不了串行瓶颈，只会浪费钱。

工程场景：多线程改造时先量化串行比例（锁临界区、单点资源、启动初始化），若串行占 30%，8 线程理论加速仅 2.4 倍，就值得先考虑别的手段（异步、缓存）。2026 年的扩展研究甚至证明：AI Agent 流水线中并行 Agent 数超过临界值后，合并评审、集成测试等系统级串行环节会让整体**变慢**——串行瓶颈在并行系统里是硬天花板。

与 Amdahl 相对的 **Gustafson 定律**给出乐观视角：实际问题规模随机器增加而扩大，加速比 ≈ N + (1 - N) × 串行比例，N 足够大时接近线性。工程含义：Amdahl 限制的是"单任务内并行"的天花板，Gustafson 说明"任务规模可扩展"（批处理拆分、数据分片）时并行依然划算——所以优先做**可拆分的工作**（分片、分区），再谈单任务内并行。

## 2. Little's Law：容量计算的基石

稳定系统中：**系统中请求数 L = 到达率 λ × 平均停留时间 W**，即：

```
并发数 = QPS × 平均RT
```

三个用途（01 篇已述其检查作用，这里给出推导直觉）：系统处于稳态时，请求"进去多少、停留多久、占着多少坑"三者必然守恒。用它计算：

- **线程池大小**：目标 QPS=2000、RT=100ms → 需要 200 并发 → 线程池按 CPU 密集/IO 密集折算（IO 密集可 2-4 倍线程）。
- **队列容量与积压**：MQ 消费端 RT=50ms、消费速率 1000/s → 在途 50 条；突发 5 倍流量时积压以 λ×W 增长，据此设计队列长度与报警阈值。
- **线程池计算实例**：IO 密集接口（数据库耗时 80ms、业务计算 20ms）目标 500 QPS：单线程吞吐 = 1000/100 ≈ 10 QPS，理论需 50 并发；考虑锁与 GC 损耗，按 Little 反推取 60-70 线程即可——**线程数不是越大越好**，超配的线程只是排队等 IO，徒增上下文切换（这就是"线程数 10 倍于核数反而更慢"的数学解释）。
- **压测验证**：压测结果若不满足"并发=QPS×RT"，先怀疑工具（协调遗漏）。

注意适用前提：系统必须**稳态**（到达率与处理能力不变）。容量规划、扩容判断本质是"预估 λ 与 W，反推 L 是否超限"。

## 3. 排队论：利用率与等待时间的 J 曲线

把系统看作单服务台队列（M/M/1 模型）：请求到达率 λ、服务速率 μ，**利用率 ρ = λ/μ**。平均等待时间：

```
W = 服务时间 × ρ / (1 - ρ)
```

数字直观化：服务时间 10ms、利用率 50% 时平均等待 10ms，80% 时 40ms，90% 时 90ms，95% 时 190ms——延迟从线性爬升转入指数陡升的区间，就是系统设计上的红线。

关键性质：ρ→1 时，分母趋近 0，等待时间**非线性爆炸**。具体数字：利用率 50% 时等待=服务时间，80% 时等待=4 倍服务时间，95% 时等待=19 倍服务时间——**从 80% 到 95%，等待时间涨近 5 倍**。这就是所有资源水位线（CPU<70%、连接池<80%）的理论来源：在 70% 处停止加压，给突发流量留出缓冲，让延迟保持可预测。

M/M/c（多服务台）与 M/M/1 结论同构：**多线程、多副本只是把爆炸点右移，不能消灭爆炸**。扩容/加线程解决不了"利用率过高"的本质，只是推迟拐点——这就是为什么压测要找拐点、容量规划要留余量（07 篇）。服务台越多拐点越靠后，但利用率逼近 100% 时同样爆炸；而真实系统的到达率往往非泊松（突发流量、重试风暴让到达更聚集），爆炸会**提前**发生——所以水位线还要再保守一点。

反例提醒：压测中若 QPS 不随并发线性增长，说明系统未达稳态（排队在堆积），Little 公式此时失效——并发数虚高是排队延迟的假象，不是容量。先压稳，再套公式。

现实中的 M/M/1 无处不在：线程池（任务排队等线程）、数据库连接池（请求等连接）、CPU 调度（线程等时间片）、MQ 消费（消息等消费者）。判断"哪个池先满"就是判断"哪条排队曲线先进入陡升区"——所以排查瓶颈时按"队列长度"而不是按"资源利用率"来找最早饱和者：利用率可能都不到 50%，但某个队列已经排了上千任务，它才是第一瓶颈。

## 4. 三定律分工：先分类再动手

| 现象 | 对应定律 | 判断动作 |
|---|---|---|
| 加线程/加机器后吞吐不涨 | Amdahl | 找串行瓶颈（锁、单点、共享资源） |
| 想知道该设多少并发/队列 | Little | 由 QPS×RT 推算，再验证稳态 |
| 利用率高、延迟剧增 | 排队论 | 控水位、扩容量、削峰 |
| 延迟分布拖尾严重 | 排队论+尾延迟 | 看排队与等待，而非平均 |

适用边界：三定律都是理想化模型——Little 要求稳态，M/M/1 假设泊松到达与指数服务，真实系统有突发与重试，数值会偏移。但定律的价值在于**方向与量级判断**：定律给出直觉，压测给出真相，两者互相验证——数字对不上时，先怀疑测量而不是先怀疑定律。

> 🎯 **核心要点**：三定律是面试与架构决策的元工具——先判断问题是"串行限制"（Amdahl）、"容量不足"（Little）还是"排队爆炸"（排队论），再选优化手段，方向错了手段全错。
