## 4. 核心概念速查

| 概念 | 一句话 |
|---|---|
| QPS/TPS | 每秒查询数/每秒完整事务数，口径必须确认 |
| RT 与 P99 | 响应时间看分布不看平均，P99 是大厂核心考核指标 |
| 并发数 | 同时在途请求数 = QPS × RT（Little's Law） |
| 错误率 | 目标 <0.1%；压测与业务口径需统一 |
| Amdahl 定律 | 并行加速受串行比例上限约束，优化非瓶颈收益为零 |
| Little's Law | L = λ × W，并发 = 吞吐 × 延迟，容量计算基石 |
| 排队论 M/M/1 | 利用率超 70% 后等待时间非线性爆炸，水位线由来 |
| 协调遗漏 | 同步压测工具低估尾延迟可达 3.5 万倍，用 wrk2/HdrHistogram |
| 尾延迟放大 | 100 路扇出下叶子 P99=10ms 变根 P99≈140ms，63% 请求命中 |
| 梯度加压 | 压测从低到高逐步加压，观察吞吐拐点而非一次压死 |
| USE/RED | 资源视角（利用率/饱和度/错误）/服务视角（速率/错误/延迟） |
| 水位线 | CPU<70%、内存<80% 等资源红线，预留突发缓冲 |
| JMH DCE | 微基准最大陷阱：结果未被消费，JIT 直接消除负载 |
| 架构层优化 | 收益 10-100 倍，优先级最高；硬件层收益有物理上限 |

## 5. 十大误区

- 平均 RT 达标就以为系统快，均值掩盖 90% 的差评来源
- QPS 高 = 用户快，吞吐与延迟是两回事
- 压测线程数拍脑袋定，不按"目标 QPS × RT"推算
- 压测用均匀流量模型，掩盖真实业务突发（峰值可达平时 5-8 倍）
- 只看 TPS 不看资源水位，TPS 8000 达标、实际 3500 就超时
- 一上来就优化，不先测量——无法度量就无法优化
- 优化命中已快的组件，木桶效应下整体收益为零
- 把微基准当绝对真理，不设 warmup、结果被 DCE/常量折叠污染
- 容量规划靠拍脑袋，不做历史外推与业务预期建模
- 把压测当一次性动作，不做基线入库与性能回归门禁
- 把"压测通过"当"上线安全"，不验证流量模型是否贴近真实业务
- 只看业务指标不看资源指标，优化做完都不知道瓶颈在哪一层
