## 1. 综合实战：秒杀接口 P99 优化全程

场景：商品秒杀接口大促峰值 QPS 从 500 飙到 5000，压测发现 P99=3s、错误率 2%，CPU 尚未打满（60%）——排除资源瓶颈，判定为链路问题。

**第一步 基线**：wrk2 固定到达率压测（防协调遗漏），记录 QPS=5000 时 P99=3s、各资源水位。

**第二步 定位**：链路追踪显示 3s 中 2.4s 为数据库查询（深分页 + 无索引过滤）与第三方库存接口同步等待；RED 看 Duration 集中在数据库调用，USE 看连接池利用率 95%（排队）。

**第三步 分层优化**：

- 架构层：库存预减到 Redis（本地缓存 + Lua 原子扣减），数据库读流量降 90%；第三方调用改异步 + 对冲请求。
- 应用层：列表接口改索引覆盖查询、深分页改游标；JSON 序列化改 Protobuf。
- 配置层：连接池按 CPU 核数重算，线程池收敛（之前 1000 线程导致切换风暴）。

**第四步 验证**：同环境同口径复测，P99=200ms、错误率 <0.1%，每步收益可归因。

**第五步 固化**：压测基线入 CI 门禁（JMeter 脚本转 k6 进流水线），监控加 P99 告警 + 连接池水位告警。

## 2. 生产纪律清单 10 项

1. 任何优化先记基线（指标 + 环境 + 口径三要素）
2. 一次只改一个变量，改完立刻复测归因
3. 压测环境配置与生产一致，数据量级贴近生产
4. 用 wrk2/固定到达率防协调遗漏，报告带百分位分布
5. 容量承诺 = 压测拐点 × 70%，不报拐点值
6. 资源水位告警先行：CPU>85% 持续 5 分钟、连接池>80%、磁盘 await>50ms
7. 线上改动必须可回滚，配置外置 + 灰度发布
8. 新功能评审带性能影响评估，不发无基线功能
9. 优化收益写入发布说明，供复盘追溯
10. 性能回归进 CI：微基准 + 接口级基线双门禁

## 3. 报错速查十条

- 压测 P99 虚低：怀疑协调遗漏 → 换 wrk2/HdrHistogram
- QPS 上不去但 CPU 空：锁竞争或等待 → jstack 抓等待点
- CPU 高 QPS 低：计算热点 → 火焰图找宽顶函数
- 并发涨 RT 陡升：排队爆炸 → 查连接池/线程池水位，控流
- 全链路压测污染生产：数据隔离标识未生效 → 先验证影子表再放大
- GC 频繁停顿长：堆配置或泄漏 → JFR 看分配与对象龄期
- CLOSE_WAIT 堆积：连接未关闭 → 查响应流是否完整消费
- 扩实例吞吐不涨：共享瓶颈 → 找单点（共享库、分布式锁、热点数据）
- 微基准快得不合理：DCE → perfasm 读汇编验证
- 压测通过上线炸：流量模型失真 → 按真实比例复刻场景，加突发

## 4. 面试三范式与追问

**价值式**（自我介绍）：「我的性能工作围绕指标闭环展开——先建基线，再定位瓶颈，优化结果用 P99 前后对比说话，最后把基线固化进 CI 防止回归。」

**技术式**（讲案例）：按"背景 → 基线 → 定位 → 分层优化 → 验证 → 固化"六段讲，每段带量化数据；重点是讲清楚**为什么先做架构层**（收益量级）与**怎么证明瓶颈**（RED 定位服务、USE 定位资源）。

**架构式**（被追问时）：容量规划用 Little's Law 推算并发，排队论解释水位线 70% 的由来，Amdahl 解释为什么先解串行瓶颈；被问"压测数字可信吗"时主动讲协调遗漏与拐点 × 70% 的承诺逻辑。

**追问四连**：平均 RT 和 P99 的区别？扇出 100 的尾延迟算术？JMH 为什么不可信？扩容为什么可能无效？

## 5. 简历呈现写法

「负责秒杀链路性能优化：建立压测基线体系，通过缓存预减、异步化与连接池调优，将 P99 从 3s 降至 200ms（降幅 93%），错误率降至 0.1% 以下；搭建 CI 性能门禁与水位告警，保障大促 5000 QPS 平稳。」——量化 + 方法 + 固化闭环，三条都占。

## 9. 复盘模板（事故/优化后必用）

复盘五段式：**现象与影响**（时间线、指标损失）→ **根因**（一句话，不含"运气不好"）→ **为什么前期没发现**（流程漏洞，这才是重点）→ **修复与验证**（量化前后对比）→ **沉淀**（告警、门禁、文档、checklist 更新）。复盘的产出不是报告，是把个案变成系统防护——每一条沉淀必须落到"下次不会发生"的机制上，否则复盘白做。
