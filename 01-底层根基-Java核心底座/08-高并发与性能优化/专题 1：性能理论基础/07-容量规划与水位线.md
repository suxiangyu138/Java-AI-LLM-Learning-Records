## 1. 容量规划三问

- 系统能承受的**预期峰值流量**是多少？（需求预测）
- 单实例在该流量下的**资源消耗**是多少？（资源建模）
- 扩容后能否**线性扩展**、拐点在哪？（压测验证）

三者缺一，容量规划就是拍脑袋。大促翻车案例几乎都是同一个原因：峰值流量超过设计上限——不是没优化，是根本没算过上限。

## 2. 需求预测：两个来源

- **历史趋势外推**：基于监控数据的日/周/月趋势建模（线性、指数、对数）。注意外推的失效边界：业务大变化（新功能、新市场、活动）会让历史曲线失真，外推只适用于平稳期。
- **业务预期对齐**：与业务团队确认用户数目标、活动排期、新市场，再转化为技术指标：DAU → 人均请求数 → 日均请求量 → 峰值 QPS。转化公式：

```
峰值QPS = DAU × 人均请求数 × 峰均比 / 86400
```

## 3. 峰均比：容量必须按峰值设计

| 业务类型 | 峰均比参考 |
|---|---|
| 企业 SaaS | 2-3x |
| 社交媒体 | 3-5x |
| 电商日常 | 3-5x |
| 电商大促 | 10-50x |
| 游戏 | 5-10x |

按平均值规划容量是经典错误：平均 1000 QPS 的系统，峰值可能 5000——按平均值买机器，峰值必炸；按峰值 × 安全系数（1.2-1.5）买，才能接住。

## 4. 四维资源建模

| 维度 | 模型 | 单位估算参考 |
|---|---|---|
| CPU | 单请求 CPU 耗时 × QPS | 压测实测单核处理能力 |
| 内存 | 基础内存 + 每并发 × 上下文 | Java 单实例 6-10GB 常见 |
| 磁盘 IOPS | 每请求 IO 数 × QPS | HDD 100-200、SSD 1万-10万 |
| 网络带宽 | 每请求流量 × QPS | 出入方向分别算 |

瓶颈 = **四维中最早到上限的那个**（木桶效应）：带宽够但 CPU 先满，扩容就应加 CPU 核而不是加带宽。据此反推所需实例数 = 峰值需求 / 单实例在该维度上的容量 × 安全系数。

## 5. 水位线：为什么是 70%

排队论（03 篇）给出答案：利用率从 80% 到 95%，等待时间涨近 5 倍。水位线的本质是**给突发留缓冲**（预留 20-30% 的突发吸收能力）——压测拐点（04 篇）测出最大能力后，容量承诺取拐点 × 70% 左右：

- CPU：高吞吐业务 <70%，告警阈值 >85% 持续 5 分钟。
- 内存：<80%，容器环境 Pod 资源请求/限制配比 1:1.5。
- 连接池：<80%，超过则新请求开始排队。
- 磁盘 IO：await <10ms 正常，>50ms 高负载。
- 网络：千兆网卡 80% 利用率时只剩 800Mbps 可用，接近上限就该升级。

水位线不是拍出来的，是由"利用率-延迟"曲线标定的：压测中记录各利用率档位的 RT，找到延迟陡升点（通常 70-80%），水位设在陡升点之前。

## 6. 扩容判断与线性验证

- **扩容有效的前提**：瓶颈维度可水平扩展（无状态应用、可路由的分片数据）；瓶颈是单点（数据库主库、有状态会话）时，加实例无效——先解单点再谈扩容。
- **线性验证**：压测中从 1 实例加到 4 实例，吞吐应近似 4 倍（线性度 = 实际增速 / 实例增速，如 4 倍实例只带来 2.8 倍吞吐则线性度 70%）；线性度 <70% 时，说明存在共享瓶颈（分布式锁、共享连接池、热点数据），扩容只是浪费钱。
- **扩容触发机制**：基于水位线自动/人工扩缩（K8s HPA 按 CPU/自定义指标），缩容时同样看水位并加冷却窗口，防止抖动（频繁扩缩比容量不足更伤，每轮扩缩都有启动与调度开销）。

## 7. 容量规划闭环

1. 需求预测（外推 + 业务对齐）→ 2. 峰值估算（峰均比）→ 3. 四维建模（找瓶颈维）→ 4. 压测标定（拐点 + 水位线）→ 5. 容量承诺（拐点 × 70%）→ 6. 监控验证（水位告警 + 大促复盘）。

## 8. 弹性伸缩与规划误区

容量规划不是一次性买断：K8s HPA 按 CPU/自定义指标自动扩缩是 2026 年标配，扩缩依据就是水位线——扩容阈值设在陡升点前（如 CPU 75%），缩容阈值加**冷却窗口**（如持续 15 分钟低于 40% 才缩），防止流量抖动引起频繁扩缩，频繁扩缩比容量不足更伤（每轮扩缩都有启动与调度开销）。云上容量还要算成本：预留实例 + 按需突发实例组合，比全量预留省 30-50% 成本。

规划误区：① 预测误差是常态，方案要留调整空间（系数可修订），而不是追求"精确预测"；② 过度规划同样有害——按 50 倍峰均比买机器，平峰期 98% 资源闲置，成本浪费；③ 只算实例数不算依赖容量——MQ、数据库、带宽都是容量的一环，应用层扩了 8 台，数据库还是 1 台主库，拐点没动；④ 大促后不复盘——预测 vs 实际对照是修正系数的唯一来源，不复盘等于下一年重新拍脑袋。

## 9. 实例演示与输出模板

实例：电商 DAU=100 万、人均日请求 20 次 → 日均 2000 万请求；峰均比 5 → 峰值 QPS = 2000 万 / 86400 × 5 ≈ 1157；安全系数 1.3 → 设计目标 1500 QPS。单实例压测拐点 300 QPS（P99 达标）→ 承诺值 = 300 × 70% = 210 QPS → 需实例数 = 1500 / 210 ≈ 8 台。内存维校验：单实例堆 4GB + 非堆 1GB，峰值 1500 并发 × 20KB 上下文增量 30MB，内存不构成瓶颈。带宽维校验：单请求响应 50KB × 1500 QPS ≈ 600Mbps，千兆网卡 80% 水位 800Mbps——**带宽贴近红线**，需要万兆或 CDN 分流。结论：瓶颈维是带宽，方案 = 8 台实例 + 网络升级。这个 walkthrough 展示四维建模的完整走法：每维都算，结论取最低维。

**输出模板**：① 目标与口径（SLO、峰均比依据、安全系数）② 需求预测（数据来源与假设，注明外推失效条件）③ 四维测算表（每维的模型与结论）④ 压测验证记录（拐点、水位标定）⑤ 容量承诺与扩容预案（触发条件、加多少、验证方式）⑥ 大促后复盘对照（预测 vs 实际，修正系数）。模板的价值：下次预测有据可依，系数越调越准。

> 🎯 **核心要点**：容量 = 预测需求 × 峰值系数 ÷ 单实例容量 × 安全系数；瓶颈取四维最低者；承诺值取压测拐点 70%；扩容前先验证瓶颈可水平扩展。
