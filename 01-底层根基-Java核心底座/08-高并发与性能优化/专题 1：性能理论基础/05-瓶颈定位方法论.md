## 1. 木桶效应：性能由最短板决定

系统整体性能由最慢的环节决定（Amdahl 定律的直接推论，见 03 篇）：数据库慢，加再多应用服务器也没用；GC 停顿长，改接口代码是隔靴搔痒。定位的第一原则：**先找最短的板**。判断标准是量化对比——各环节耗时占比、资源利用率对比、压测拐点前的最后饱和者。80% 的性能问题集中在 20% 的瓶颈点，别平均用力。

## 2. 两套方法论：USE 与 RED

| 方法论 | 视角 | 看什么 | 适用对象 |
|---|---|---|---|
| USE | 资源视角 | Utilization（利用率）、Saturation（饱和度，排队任务数）、Errors（错误） | CPU、磁盘、网络、连接池等资源 |
| RED | 服务视角 | Rate（请求速率）、Errors（错误率）、Duration（延迟分布 p50/p99/p999） | 每个服务/接口 |

USE 回答"资源是不是瓶颈"：CPU 利用率 95% 但无排队，说明是计算瓶颈；利用率 60% 但运行队列长，说明调度/锁竞争。RED 回答"服务表现如何"：接口 P99 恶化时，逐层看 Rate 是否跌、Errors 是否涨，快速判断"流量问题"还是"代码问题"。两套配合：RED 定位到具体服务，USE 定位到具体资源。

## 3. 排查方向：自上而下 vs 自底向上

- **自上而下**（推荐首轮）：用户端 → 网关 → 应用 → 中间件 → 数据库 → 基础设施，每层用监控数据快速排除，逐层缩小范围。优点快，缺点是可能漏掉底层资源问题。
- **自底向上**：基础设施 → 系统 → 中间件 → 应用，先确认资源是否够。适合"资源侧已有报警"的场景（CPU 飙高、IO 打满）。
- 实际做法是两者结合：先看监控大盘的异常层（自上而下快速收敛），再对可疑层深入排查（自底向上取证）。

自上而下的提速技巧：**分层并行排查**——多人分工，一人看一层（网络、系统、应用、数据库），5 分钟同步一次结论；每层用"最可疑的 3 个指标"快速排除，而不是穷举。逐层排除要记录排除依据（该层指标截图 + 一句话结论），防止查完一轮忘了查过什么、或者在同一层反复打转——排查记录本身也是复盘素材。

## 4. 瓶颈类型识别

- **CPU 密集**：CPU>80% 且 QPS 上不去。查热点函数（火焰图，06 篇），典型如 JSON 序列化、正则、循环内低效算法；案例：某电商 CPU 95% 消耗在 JSON 序列化，改 Protobuf 后 QPS 提升 3 倍。
- **IO 密集**：磁盘 await>50ms、网络重传高。查慢查询、大对象序列化传输、日志刷盘、未分页查询。
- **锁竞争**：jstack 大量 WAITING/BLOCKED。查线程堆栈热点锁，用读写锁、CAS、分段锁、无锁结构替换。
- **排队/连接耗尽**：线程池活跃数接近上限、连接池等待计数上升。查慢依赖、收紧超时、扩容量。
- **内存/GC**：堆占用持续上升、GC 频繁。jstat 看 GC 频率与停顿，区分泄漏与容量不足（专题 3 深讲）。

瓶颈很少孤立出现，更多是**传导链**：慢 SQL 拖住数据库连接 → 连接池打满 → 应用线程池排队 → 请求超时重试 → 重试加重数据库压力，形成正反馈直到雪崩。排查时先打断链：定位第一个恶化的队列（按 03 篇的"队列长度优先"原则），把它列为根因级瓶颈，其余都是它的症状。修复也按链序：先解第一瓶颈（索引、超时、限流），链路下游的异常往往自动消失——一次只改一个，改完看传导链是否整体恢复。

## 5. 五步闭环（优化必须可验证）

1. **建立基线**：优化前先测量，记录当前 QPS/RT/资源数据。
2. **定位瓶颈**：按上述方法论收敛到单一瓶颈点——一次只处理一个瓶颈。
3. **方案设计与实施**：遵循"最小改动、最大收益"，一次只改一个变量（改两个变量无法归因）。
4. **验证与回归**：同环境同口径复测，对比基线；性能损耗系数 =（实际 RT - 理论最优 RT）/ 理论最优 RT，系数 >0.5 说明仍有显著瓶颈。
5. **监控固化**：把关键指标接入告警与基线库，防止回归——优化是一次性的，水位是持续的。

## 6. 定位实例：一次完整的五分钟排查

场景：大促压测时下单接口 P99 从 200ms 恶化到 2s。第一步用 RED 定性：Rate 平稳但 Duration 暴涨 → 服务本身问题而非流量问题。第二步自上而下分层排除：网关正常（其他接口 P99 正常）→ 下单服务 CPU 40%（排除计算瓶颈）→ 数据库慢查询日志命中一条未走索引的状态过滤 + 深分页 → USE 看连接池利用率 95% 排队。结论：SQL 全表扫描 + 连接池排队双重叠加。修复索引、改游标分页后复测 P99=220ms。整个排查中 RED 缩小范围、USE 取证、分层 checklist 排除，三个工具各司其职，谁先谁后都有章法。

**性能损耗系数**用于判断"还有没有必要继续调"：损耗系数 =（实际 RT - 理论最优 RT）/ 理论最优 RT。理论最优 RT 取纯业务计算（无等待）的实测值；系数 >0.5 说明存在显著瓶颈值得深挖，系数 <0.2 说明已接近最优，继续优化边际收益低——防止在 20% 的残量上花 80% 的时间。

## 7. 分层排查 checklist

- 网络层：超时三兄弟（连接/读取/写入超时）、重传率、DNS 解析耗时
- 系统层：CPU user/sys 占比、上下文切换（>5000 次/秒异常）、Swap（>10% 预警）
- 中间件层：连接数、慢查询、命中率、Lag、阻塞等待——细分到具体中间件：Redis 看大 key 与命中率（命中率骤降=缓存失效风暴）、MQ 看消费 Lag 分类（是积压还是单条卡死）、数据库看慢查询 TOP N 与锁等待
- 应用层：GC 频率与停顿、线程池活跃度（活跃/排队/拒绝三计数）、锁竞争、序列化耗时——线程池拒绝计数>0 是最直观的容量不足信号，比看延迟更早

> 🎯 **核心要点**：先定位后优化、一次只改一个变量、结论必须量化对比；USE 管资源、RED 管服务、木桶管方向，三者合起来就是完整的瓶颈定位体系。
