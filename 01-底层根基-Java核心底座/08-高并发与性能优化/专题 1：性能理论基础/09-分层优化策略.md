# 09 分层优化策略：从架构到配置

> 优化优先级与收益成反比：架构层改动大但收益 10-100 倍，配置层改动小但收益有物理上限——先做对的层，再做快的层。

## 1. 优化优先级排序

| 层级 | 典型手段 | 收益量级 | 复杂度 |
|---|---|---|---|
| 架构层 | 缓存、异步削峰、读写分离、分库分表、无状态化 | 10-100 倍 | 高，改动大 |
| 应用层 | 算法、锁优化、池化、序列化、批量 | 2-10 倍 | 中 |
| 配置层 | JVM 参数、连接池、线程池、内核参数 | 1.2-2 倍 | 低 |
| 硬件层 | 升 CPU、换 SSD、加带宽 | 固定倍率 | 低，有物理上限 |

核心认知：**先用架构手段把量级降下来（缓存命中、异步化），再谈细节调优**。数据库慢查询再优化，也不如把 90% 的读打到缓存；GC 参数再调，也不如减少对象分配。反过来，架构层动不了时，配置层 20% 的收益也值得拿。

方案选型用四维评估，而不是只看收益：**收益量级**（10 倍还是 1.2 倍）、**改动风险**（缓存加一层有数据一致性风险，改序列化要全链路兼容测试）、**开发成本**（人天）、**维护成本**（缓存一致性、分库分表带来的长期复杂度）。典型权衡：读写分离收益 3-5 倍但引入主从延迟一致性窗口；异步化收益大但把同步问题变成一致性难题——高收益方案的隐藏成本往往在一致性上，评估表里必须列这一列。

执行口诀：**收益/复杂度比最高的方案先做**。同样是 P99 从 2s 到 200ms，先加缓存（收益 10 倍、成本 2 人天）还是先改 GC 参数（收益 1.2 倍、成本 0.5 人天）？先做前者——但前提是两者都做不了冲突：缓存方案动了架构，参数方案只动配置，评估时要算清"一次架构调整的窗口成本"，架构方案集中做、配置方案顺手做。

## 2. 各层优化要点

**架构层**（收益最大，改动最重）：

- 缓存：多级缓存（Caffeine → Redis → DB），消灭重复计算与重复查询；缓存三问必须过关——穿透（查不到的数据用布隆过滤器拦截）、击穿（热点 key 过期用互斥重建）、雪崩（批量过期加随机过期时间），三问不答，缓存体系就是纸糊的（专题 5 深讲）。
- 异步削峰：非核心链路走 MQ，把同步等待变异步解耦，削平流量尖峰。
- 读写分离与分库分表：读多写少拆读流量，数据量大拆库拆表；注意一致性窗口与分布式事务成本。
- 无状态化：会话与本地状态外置，应用层可水平无限扩展——这是扩容的前提（07 篇）。

**应用层**（日常主战场）：

- 算法与复杂度：循环内低效实现、正则回溯、深拷贝滥用。
- 锁优化：缩小临界区、读写锁、CAS、分段锁；能无锁则无锁（线程局部、不可变对象）。
- 序列化：JSON → Protobuf/二进制，案例：某电商 CPU 95% 耗在 JSON 序列化，改 Protobuf 后 QPS 提升 3 倍（05 篇已提，这里落到选型）。
- 池化与批量：连接池、线程池、对象池复用；数据库批量插入替代单条。

**配置层**（快而准）：

- JVM：堆大小、GC 选型（G1/ZGC）、线程栈；专题 3 深讲。
- 连接池：HikariCP 常用 maximumPoolSize = CPU 核数 × 2 + 存储设备数；过大反而有害。
- 线程池：max-threads 不宜过大（常见 200-500），超配导致上下文切换风暴。
- 内核：somaxconn、tcp_tw_reuse、文件描述符上限；网络瓶颈时才有意义。

**硬件层**（最后手段）：升 CPU 核数、换 NVMe SSD、加带宽——收益确定但线性，且成本高；用于"已经验证是资源瓶颈"的场景。

架构层两个高频权衡需要明确决策：**读写分离的一致性窗口**——主从延迟秒级，刚写入的数据立即读可能读不到，读接口要么接受最终一致，要么强制读主（代价是分流失效），业务对账、资金类场景必须读主；**无状态化与 session 外置**——会话存 Redis 后应用可随意扩缩容，代价是每次请求多一跳网络，权衡点在"是否需要水平扩展"，不需要扩展的内部系统保留本地 session 更省。

配置层 JVM 判断框架（细节见专题 3）：堆大小按活跃数据量定——压测观测老年代稳定占用 × 1.5-2；GC 选型看停顿目标——<10ms 用 ZGC、<100ms 用 G1、无严格要求用默认；`-Xlog:gc*` 开 GC 日志做基线。判断顺序永远是"先看分配热点（06 篇分配火焰图），再调堆，最后选 GC"——顺序反了就是在没确诊的情况下开药。

## 3. 优化黄金法则

- **先测量，后优化**：没有基线对比的优化是玄学（05 篇五步闭环）。
- **避免过早优化**：未验证的热点不优化——按二八原则，80% 收益来自 20% 热点。
- **一次只改一个变量**：同时改 JVM 参数和代码，无法归因收益。
- **不脱离业务谈优化**：ToB 报表接口的 1s 与秒杀接口的 200ms 不是一回事；优化目标写在 SLO 里。
- **兼顾性能与可用性**：限流、熔断、降级、过载保护是性能体系的一部分——性能再好，雪崩时等于零（专题 7 深讲）。

## 4. 典型优化案例：读接口 P99 从 2s 到 200ms

1. 测量基线：P99=2s，CPU 40%（说明不是资源瓶颈，是链路问题）。
2. 定位：链路追踪发现 1.6s 消耗在数据库慢查询 + 第三方调用串行等待。
3. 架构层：加 Redis 缓存命中 90% 读流量，P99 降到 600ms。
4. 应用层：第三方调用改并行 + 超时收紧，消除尾部等待，P99 降到 300ms。
5. 配置层：连接池扩容 + 慢查询索引优化，P99 稳定 200ms。
6. 固化：基线入 CI，接口监控 + 告警水位。

每一步都能归因到量化收益——这是优化报告的唯一可信格式。

## 5. 优化与回归的平衡

- 优化后必须跑基准回归（04 篇），防"修好 A 弄坏 B"。
- 技术债显式记录：跳过的优化（如分库分表）写进架构决策记录，标注触发条件（数据量到达 X 时执行）。
- 性能是持续工程：新功能评审时带上性能影响评估，而不是上线后救火。

> 🎯 **核心要点**：先架构后细节、先测量后动手、一次一变量、结论挂指标；优先级排序 = 收益/复杂度，架构层永远排第一，硬件层是最后兜底。
