# 04 性能测试方法论：五类压测与执行流程

## 1. 五类压测类型

| 类型 | 目的 | 施压方式 | 产出 |
|---|---|---|---|
| 基准测试 | 单接口基线 | 单/少量用户，低负载 | 基准报告，后续回归对照 |
| 负载测试 | 找最大处理能力 | 梯度加压至峰值 | 吞吐拐点、最佳水位 |
| 压力测试 | 找极限与失败表现 | 持续超载 | 崩溃行为、恢复能力 |
| 稳定性测试 | 验证长期可靠 | 80% 容量或日峰值持续数小时 | 泄漏检测、抖动观察 |
| 全链路压测 | 端到端真实场景 | 全链路按真实流量比例施压 | 系统级容量与瓶颈清单 |

五种类型不是可选项，是标准执行序列：**基准 → 负载 → 稳定性 → 压力**。跳级直接压上限，测不出"哪个环节先到瓶颈"。

## 2. 压测四要素：环境、数据、场景、监控

- **环境**：压测环境配置与生产一致（同等 CPU 核数、JVM 参数、连接池大小、网络拓扑），否则结论不可迁移。
- **数据**：数据量级与分布贴近生产（用生产脱敏数据同步），1 万条与 1 亿条数据的索引命中、缓存命中完全不同。
- **场景**：按生产日志分析真实流量比例设计——浏览 60%、下单 10%、搜索 30%，而不是单接口孤立压测；要含突发（整点、抢券可达平时 5-8 倍）。
- **监控**：压测同时采集业务指标（QPS/RT/错误率）与资源指标（CPU/内存/GC/IO/线程），压测结束才看数字等于盲测——拐点出现时资源侧会先报警。

## 3. 梯度加压与拐点判断

一次压满（5000 并发直接上）是新手常见错误：系统可能在 3000 并发时就到瓶颈，高压下只会得到一堆超时与假崩溃。正确做法是**梯度加压**：从 50 并发起步，按 50→100→200→400→800 翻倍爬升，每档稳定 1-2 分钟，记录该档的 QPS、RT、错误率。

- 吞吐拐点：QPS 随并发增长到某一档后不再增长甚至下降——拐点即系统最大处理能力。
- RT 拐点：RT 从平缓进入陡升（排队论 J 曲线），对应资源利用率通常 70-80%。
- 拐点后的数据是"崩溃区间"，用于定位瓶颈与设计限流阈值，不用于容量承诺。
- 用**拐点吞吐 × 合理水位**（如 70%）作为容量承诺值，而不是拐点本身（07 篇）。

## 4. 工具选型

| 工具 | 优势 | 短板 | 适用 |
|---|---|---|---|
| JMeter | 协议全、插件丰富、门槛低 | 分布式协调成本高、UI 大脚本卡 | 复杂场景编排、传统企业 |
| Gatling | Scala 异步非阻塞、单机并发高、报告好 | 学习曲线陡 | 代码化团队、高并发单机 |
| k6 | Go 编写、CLI+JS、云原生、可嵌 CI | 生态较新 | DevOps 持续性能测试 |
| Locust | Python、分布式简单 | GIL 限制压测端性能 | Python 团队 |
| wrk/wrk2 | 轻量、单机高并发、wrk2 防协调遗漏 | 脚本能力弱 | 单接口快速压测 |

选型决策口诀：**要编排选 JMeter，要持续集成选 k6，要单机极致并发选 Gatling/wrk2，云上大促演练选云压测**（阿里云 PTS 等，免运维、可模拟全球流量）。切换工具的成本远低于压测结论不可信的成本——工具只是手段，场景真实与口径正确才是目的。性能基线一旦选定工具，团队内就不要随意更换，否则历史基线全部失去可比性。

## 5. 全链路压测要点

全链路压测是 2026 年大促系统标配，核心是"模拟真实、数据隔离"：

- **流量模型**：按日志比例复刻接口调用链，含依赖调用（下游也要压到），单点压测测不出级联瓶颈。
- **数据隔离**：压测数据加专属标识（如 userId 前缀），服务端与影子表过滤，防止污染生产；或影子库/影子 MQ Topic 方案。
- **流量标记透传**：压测流量通过请求头标记贯穿全链路，监控系统据此区分压测与真实数据。
- **执行纪律**：压测窗口避开业务高峰，先小流量试跑验证隔离生效，再梯度放大；压测前备份配置，结束后检查脏数据。
- **回归闭环**：每次大版本发布前跑基准回归，对比基线（可用 JMeter/Gatling 出报告，或 k6 直接进 CI 门禁），吞吐下降超阈值即阻断发布。

## 6. 脚本设计细节与常见错误

- **think time（思考时间）**：用户不会无间隔刷接口，脚本要按真实间隔分布模拟；纯无间隔压测得到的是系统上限，不是业务容量。
- **参数化**：所有请求用同一商品 ID 会把单 key 热点打满（缓存命中率虚高或单分片打满），掩盖真实容量——参数必须按生产分布随机化。
- **施压端自身**：压测机 CPU 打满时压的是压测机而不是被测系统，先看施压端负载再信结果。
- **JVM 预热**：被测服务前几分钟处于 JIT 预热期，数字偏高/偏低都失真——预热后再采集有效数据（与 08 篇微基准同源）。
- **结果分区统计**：每档并发的数据单独统计，全程混在一起平均会掩盖拐点；每档记录 QPS、RT 分布、错误率、资源水位四件套。

**报告规范**：环境信息（机器配置、数据量级、JVM 参数）→ 场景设计（接口比例、并发梯度、think time）→ 分档结果表 → 拐点与瓶颈定位 → 容量结论（拐点 × 水位）→ 风险与建议。报告缺环境信息的，等于不可复现的实验——评审第一眼看的就是这个。

**执行纪律**：压测窗口避开业务高峰；大流量压测前先小流量试跑（验证隔离、监控、回滚链路都通）；压测中同步盯监控大盘，异常立即停——压测的目的是找问题，不是把系统压到出事；压测前后各做一次基准对比，压测本身不能悄悄改掉环境状态。

> 🎯 **核心要点**：压测 = 环境 + 数据 + 场景 + 监控四要素齐全 + 梯度加压找拐点 + 全链路模拟真实；结论只取拐点以下的水位值，且必须防协调遗漏（02 篇）。
