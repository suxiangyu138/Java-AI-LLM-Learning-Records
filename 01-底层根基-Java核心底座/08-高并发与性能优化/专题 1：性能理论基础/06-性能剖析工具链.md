## 1. CPU 类工具

| 工具 | 用途 | 关键命令 |
|---|---|---|
| top/htop | 第一眼全局：CPU 占比、负载、进程 | `top` 按 P 排序 |
| vmstat | CPU 用户态/内核态、上下文切换、运行队列 | `vmstat 1` |
| perf | 系统级采样，含内核态热点 | `perf top` |
| async-profiler | Java 进程采样，直接出火焰图 | `profiler.sh -d 60 -f flame.html <pid>` |
| Arthas profiler | 已挂载场景下现场采样 | `profiler start` / `stop` |

CPU 瓶颈取证三步：top 确认 CPU 高 → vmstat 看 us/sy 占比（sy 高说明系统调用/上下文切换异常）→ async-profiler 采样 60 秒出火焰图找热点函数。注意采样时长要覆盖业务高峰窗口，采样期间保持真实流量，否则采样的是空转代码。热点判定阈值：**单函数采样占比 >20% 才值得优化**——占比 3% 的"热点"是分布噪音，优化它等于平均用力。

## 2. 火焰图解读

火焰图横轴是采样占比（宽 = 耗时多），纵轴是调用栈（下层是调用者、上层是被调者），**顶部越宽的函数越可疑**。三看：看顶部（热点函数是谁）、看宽度分布（是否集中在少数函数）、看平台段（平顶说明在等 IO/锁，不是 CPU 计算）。CPU 火焰图宽顶是计算热点；等待类问题要用 **off-CPU 火焰图**（async-profiler `-e cpu` 与 `-e itimer` 之外，采集阻塞采样）区分"在干活"与"在等待"。锁竞争会表现为栈顶停在 `monitor enter` / `park`；等待类问题的火焰图顶部呈扁平宽台——函数在等而非在算，这是 CPU 火焰图与 off-CPU 火焰图联合解读的关键。

## 3. 内存与 GC 类工具

- **jstat**：GC 频率、单次停顿、各代容量与占用。`jstat -gcutil <pid> 1000`，关注 FGCT（Full GC 累计时间）与 YGC 频率；GC 高频且老年代持续增长，再上 jmap。
- **jmap -dump**：堆转储，配合 MAT 分析泄漏三步：直方图看对象数量异常（某业务对象百万级）、支配树找大对象、GC Roots 引用链找持有者。生产环境慎用（会 STW），优先用 **JFR** 的 GC 事件与 `jcmd GC.heap_dump`（对正在运行的进程更温和）。
- **JFR（JDK Flight Recorder）**：JDK 自带、开销 <2%，录制 GC、分配、锁、IO 全量事件，`jfr print` 按类型过滤；录制的 jfr 文件用 JDK Mission Control（jmc）可视化分析，火焰图、事件时间线、对象统计开箱即用。2026 年 JFR 已是 Java 调优第一工具，Arthas 与 async-profiler 都能触发 JFR 录制。
- **Arthas**：在线诊断瑞士军刀——`dashboard` 看全局、`memory` 看分区、`heapdump` 转储、`watch` 观测方法入参出参耗时。适合生产现场不停机排查。

## 4. IO 与网络类工具

- **iostat**：磁盘利用率与 await、svctm——await>50ms 即磁盘瓶颈；注意区分"磁盘慢"与"应用刷盘频繁"。
- **ss/netstat**：连接数、TIME_WAIT/CLOSE_WAIT 堆积（CLOSE_WAIT 泄漏=代码未关闭连接）、重传率——`ss -i` 看单连接 retrans 计数，`netstat -s` 看全局重传统计，重传率持续 >1% 基本可断定网络链路有丢包（云厂商实例间偶发，需抓包定位）。
- **iftop/nethogs**：实时流量与进程流量排行，判断带宽是否打满。
- **tcpdump**：抓包定论，网络问题排查的最终手段（详见 07-工程运维基础/网络问题排查体系）。

## 5. Java 线程与锁工具

- **jstack**：线程快照。看大量线程 WAITING 在 `AbstractQueuedSynchronizer$ConditionObject`（池满排队）、BLOCKED（锁竞争）、`Object.wait`（等待业务条件）。多抓几份间隔 3-5 秒的堆栈，对比等待点是否一致——一致的等待点是真瓶颈。
- **async-profiler 锁分析**：`-e lock` 采样锁事件直接出锁竞争火焰图——比翻 jstack 快得多，锁竞争集中在哪个类哪把锁一目了然；配合 `-e wall`（墙上时钟采样）区分 CPU 时间与等待时间，锁问题与 IO 等待问题一次分清。
- **Arthas thread**：`thread -n 3` 找最忙线程、`thread --state WAITING` 分类统计；`thread -b` 直接定位死锁。
- 上下文切换飙高（vmstat cs > 5000/秒）时，先看线程数是否过多——**线程数 > 10×CPU 核数是常见自伤**，排查线程池滥用。

## 6. 可观测性延伸

单机工具只能看一台，分布式系统要结合**三支柱**（日志、指标、链路追踪，OTel 体系）跨节点关联：traceId 贯穿调用链找慢环节、按服务聚合 P99、链路视图看跨节点等待。单机工具定位"是什么"，可观测性定位"在哪一环"——两者衔接是完整排查闭环。

## 7. 系统级观测三件套与采集纪律

单机 Linux 侧先看三件套：**mpstat**（每核 CPU 明细，识别单核打满的多线程假象）、**pidstat**（进程级 CPU/内存/IO 细分，识别是哪个进程在抢资源）、**sar**（历史数据回看——问题发生时没盯现场，sar 是事后取证的主渠道，建议常驻采集）。三者与 Java 工具配合：pidstat 定位到进程 → jstack/async-profiler 定位到线程 → 火焰图定位到方法，层层下钻。

采集纪律三条：**采样必须覆盖业务高峰窗口**（低谷采样的火焰图没有任何参考价值）；**多份采样交叉验证**（单次采样可能撞上 GC 或调度噪音，间隔 5 秒采 3 份对比，热点一致才可信）；**记录采样时的流量上下文**（QPS、并发、压测状态），否则复现不了当时的结论。

三套 Java 工具的定位分工：**JFR 是常态侦察**（开销低、事件全，适合常开录制与事后分析）；**async-profiler 是定点打击**（火焰图直观、按事件类型采样，适合现场定位热点）；**Arthas 是贴身手术**（在线改查、无需重启，适合已挂载的生产进程应急）。选型不纠结工具本身，按场景走：事发时用 Arthas 快速看，高峰时用 async-profiler 采样，平时用 JFR 留底。

## 8. 常用命令速查

```bash
# iostat（磁盘视角）
iostat -x 1                      # await 与 util%，util 高=磁盘忙，await 高=排队慢
iostat -x 1 | grep -E 'nvme|sda' # 只看物理盘，过滤虚拟分区噪音

# async-profiler（Linux 需 CAP_PERFMON 权限，Java 8-21 全支持）
./profiler.sh -d 60 -e cpu -f cpu.html <pid>      # CPU 采样火焰图
./profiler.sh -d 60 -e alloc -f alloc.html <pid>  # 分配火焰图：找 GC 压力来源

# JFR（JDK 自带，录制开销 <2%）
jcmd <pid> JFR.start duration=120s filename=app.jfr
jfr print --events jdk.GCPause app.jfr          # GC 停顿事件明细
jfr print --events jdk.ObjectAllocationSample app.jfr  # 分配热点

# Arthas 高频三件
dashboard                 # 全局线程/内存/GC 一览
trace com.x.OrderService query   # 方法内各段耗时分解
watch com.x.OrderService query '{params, returnObj}' -x 3  # 观测调用
```

命令背熟不如理解选型逻辑：**先看分配热点（alloc 火焰图），再调 GC 参数**——顺序反了是 GC 调优最常见错误；堆参数改十轮，不如把每秒千万次的对象分配消掉。JFR 是 2026 年 Java 调优的第一工具：一次录制同时覆盖 GC、锁、IO、分配四类事件，先 `jfr print` 全量扫一遍分类统计，再按类别深入，比逐个工具轮询快一个数量级。

> 🎯 **核心要点**：CPU 问题上火焰图、内存问题看 JFR/jstat、IO 问题看 iostat、锁问题看 jstack/Arthas——工具按瓶颈类型选用，采样必须在真实流量窗口，结论用多次采样交叉验证。
