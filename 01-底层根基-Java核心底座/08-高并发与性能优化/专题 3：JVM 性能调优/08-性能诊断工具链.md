## 1. 趋势与快照：jstat / jmap / jstack

- **jstat（趋势）**：`jstat -gcutil <pid> 1000` 每 1 秒输出一次 GC 汇总。关键字段：E（Eden 占用）、O（老年代占用）、YGC/YGCT、FGC/FGCT。**看趋势不看单点**——老年代 GC 后是否回落、FGC 频率是否爬升，是泄漏与容量问题的第一现场。

  | 字段 | 含义 | 健康信号 |
  |---|---|---|
  | E / O | Eden 与老年代当前占用 | O 在 GC 后明显回落 |
  | YGC / YGCT | Young GC 次数与累计耗时 | 单次 YGCT 增量 < 100ms |
  | FGC / FGCT | Full GC 次数与累计耗时 | 长期为 0，出现即重视 |
  | S0U / S1U | 两个 Survivor 使用率 | 一高一低正常，两者都高警惕晋升 |

  jstat 的正确姿势是**定时采集落库**（每 5-10 秒一次，脚本或监控代理），事后画曲线——单次快照没有趋势，趋势才有诊断价值。
- **jmap（快照）**：`jmap -histo <pid> | head -20` 看对象分布（哪个类实例最多）；`jcmd <pid> GC.heap_dump` 生成 dump（比 jmap -dump 安全，不强制 FGC）。**生产优先 jcmd**，配合 MAT 分析（Leak Suspects / Dominator Tree，见 [09 篇](09-高并发场景调优实战.md) 泄漏案例）。histo 的读法有讲究：byte[] 与 String 多通常是序列化/缓冲膨胀；业务类实例数异常高才是泄漏嫌疑——先按 retained size 排，再沿引用链找持有者，两步把"哪个对象"收敛成"谁拿着不放"。
- **jstack（线程快照）**：`jstack -l <pid>` 带锁信息。死锁直接输出 `Found one Java-level deadlock`；线程状态分布（WAITING/BLOCKED/RUNNABLE 计数）一眼看出锁竞争 vs IO 等待。**连续抓 3-5 次（间隔 5 秒）对比**——"卡住不动"与"短暂等待"在多次快照里现形。找高 CPU 线程：`top -H -p <pid>` 取线程号转 16 进制后 `jstack` grep。状态分布解读：大量 `WAITING (parking)` 是线程池空闲，正常；`BLOCKED` 集中且持续，是锁竞争（配合 JFR 锁事件定位）；`RUNNABLE` 占比高但 CPU 低，是网络/IO 等待伪装成运行态——注意 RUNNABLE 不能直接读作"在算"。

## 2. 全能指挥：jcmd

jcmd 是现代 JDK 的诊断总入口（jmap/jstack 的多数能力它都有），生产安全的动态操作基本都走它：

```bash
jcmd <pid> help                          # 列出全部可用命令
jcmd <pid> VM.flags                      # 生效参数（含默认值，验证配置是否生效）
jcmd <pid> VM.native_memory summary      # NMT：堆外内存分布（需启动加 -XX:NativeMemoryTracking=summary）
jcmd <pid> GC.heap_info                  # 堆分区使用概况
jcmd <pid> GC.heap_dump heap.hprof       # 生成堆转储（不强制 FGC，生产首选）
jcmd <pid> Compiler.codecache            # Code Cache 使用率（检查是否将满）
jcmd <pid> Thread.print                  # 等价 jstack
```

NMT 的用法是**对比两次快照**（`summary.diff`）：启动后采样一次，运行一段时间再采样，差值揭示哪块堆外内存在涨——堆外泄漏的定位主工具（[02 篇](02-内存性能调优.md)）。

## 3. JFR：现代首选

JFR（JDK Flight Recorder）是 JDK 内置的事件记录器，**生产可常开**（JDK 11+ 免费，开销约 1-2%）。它把"事后猜现场"变成"事前录证据"：

- **录制**：`jcmd <pid> JFR.start name=profile duration=60s filename=rec.jfr settings=profile`（profile 档含分配采样、锁事件、安全点）；启动参数加 `-XX:StartFlightRecording` 可开机即录。JMC（JDK Mission Control）打开 .jfr 查看。
- **三种取档姿势**：临时录制（上述命令，抓取毛刺窗口）；常开循环录制（`settings=profile` 配 `disk=true`，保留最近 1-2 小时环形缓冲，事故后 `jcmd <pid> JFR.dump` 落盘取证据）；容器环境注意把 .jfr 输出到持久卷，Pod 重建不丢记录。
- **性能调优最常用的四类事件**：分配采样（allocation profiling，热点分配栈）、Java Monitor Blocked / Lock Held（锁竞争量化）、Safepoint（非 GC 停顿来源）、GC pause 各阶段耗时。
- **对比思路**：录制"正常时段"与"毛刺时段"两份记录，差异即线索——这是 JFR 相对日志的最大优势，事件级别的时间线让"先发生什么"一目了然。

## 4. Arthas：在线诊断

Arthas（Alibaba）解决"生产不重启地看代码与状态"：

- `dashboard`：线程/GC/堆/CPU 实时面板。
- `thread -n 3`：CPU 最高的线程；`thread -b`：找死锁阻塞线程。
- `trace` / `watch`：方法级耗时与入参/返回值——定位"哪个方法慢"的直通车。
- `jvm` / `memory`：JVM 参数与内存分布速览。
- `ognl`：在线调用 Spring Bean 观察内部状态（只读诊断，注意权限与审计）。

分工：**Arthas 适合"现场交互式排查"，JFR 适合"长期录证据"**——毛刺是偶发的，先 JFR 常开留底，毛刺再现时 Arthas 进场深挖。两者的差异要记牢：JFR 事件是**时间线全局回放**，能看到毛刺发生前后 5 秒内所有 GC/锁/分配事件的前后关系；Arthas 只能看到**当下**的状态，但它能动态反编译（jad）、改观测点（watch/trace）而无需重启。排查姿势组合拳：毛刺发生时先 `thread -n 3` 抓现场，再用 JFR 回放确认根因链，最后用 watch 验证修复效果。

## 5. GC 日志规范与生产安全

GC 日志是调优的**基线数据源**，生产必须常开并轮转：

```yaml
-Xlog:gc*:file=/logs/gc.log:time,pid,tags:filecount=10,filesize=100m
-Xlog:safepoint*:file=/logs/safepoint.log
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/logs/
-XX:NativeMemoryTracking=summary
```

- **GC 日志读什么**：停顿原因（Allocation Failure / to-space exhausted）、老年代 GC 后占用是否回落、Mixed GC 频率、安全点耗时。GC 日志分析工具（GCeasy 等）可出趋势报告，但结论要靠人核对根因。
- **生产安全纪律**：动态 dump/诊断操作按权限审批并记录；`jmap -dump:live` 会触发 FGC——生产禁用，用 jcmd；Arthas 需白名单与审计；诊断命令全部只读优先，写操作（如 JFR.stop 前）确认不影响采集。
- **与压测配合**：压测（[专题 1](../专题%201：性能理论基础/04-性能测试方法论.md)）是唯一安全的"主动制造问题"窗口——JVM 参数验证、GC 行为观测、dump 练习都在压测环境完成，线上只做被动观测。

> 🎯 **核心要点**：工具链分工——jstat 看趋势、jstack 抓线程现场（连续多次）、jcmd 是生产安全的全能入口（NMT 对比找堆外泄漏）、JFR 常开录证据（分配/锁/安全点四类事件）、Arthas 现场交互；GC 日志常开轮转是调优基线；生产纪律：jcmd 优先于 jmap、dump 只在压测与 OOM 自动触发、诊断操作留审计。
