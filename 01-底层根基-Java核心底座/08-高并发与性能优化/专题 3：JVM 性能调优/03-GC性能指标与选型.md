## 1. GC 性能指标体系

调 GC 先要会读指标。五个核心指标各有语义，混为一谈是选型错误的根源：

- **吞吐（throughput）**：应用线程工作时间占总时间比。`应用时间 / (应用时间 + GC 时间)`，90% 意味着 GC 吃掉 10% 的 CPU。批处理场景关心它，在线服务次要。
- **停顿（pause / STW）**：应用线程冻结时长。平均停顿意义有限，**P99/P999 与最大值**才决定业务毛刺。停顿目标是 SLA 反推的，不是拍脑袋定的（见第 4 节）。
- **分配速率（allocation rate）**：每秒分配字节数，决定 GC 频率。它受业务代码支配，调参只能影响后果不能影响源头（[01 篇](01-JVM性能全景与调优方法论.md)）。
- **存活集（live set）**：GC 后存活对象总量，决定单次回收成本。存活集大 = 每次 GC 都贵，需要更聪明的回收策略。
- **GC 频率与原因**：Young GC 每秒几次、Mixed/Full GC 多久一次、FGC 的触发原因（Allocation Failure / Metadata GC Threshold / Ergonomics），日志里每一条原因都是一条线索。

判断健康度的一句话：**Young GC 高频但停顿短是常态（分配多），Full GC 出现且频繁是事故（回收跟不上分配）**。

指标从哪里来，三路数据交叉验证：GC 日志（`-Xlog:gc*`）给出每条停顿的准确时长、原因与前后堆占用——**最权威**，是调优基线；JFR 的 GC 事件给出同一时间线的分配采样与锁竞争——**归因必需**，回答"为什么此刻停顿"；Micrometer 的 `jvm.gc.pause` / `jvm.memory.used` 指标进 Prometheus——**趋势必需**，回答"回归从什么时候开始"。三路缺一不可：只有监控没有日志，无法定位停顿原因；只有日志没有监控，无法感知长期趋势。

## 2. 四个收集器的性能特征

2026 年四个主流收集器的取舍，可用 120GB 堆实测数据（JDK 21，Java Code Geeks 2026 报告）直观对比：

| 收集器 | 典型停顿 | 120GB 堆实测 | 吞吐 | 内存开销 | 定位 |
|---|---|---|---|---|---|
| Parallel | 秒级（FGC） | 未测（吞吐向） | 最高 | 基准 | 吞吐优先、批处理 |
| G1 | 20-200ms，大堆峰值可达秒级 | avg 150ms / max 10.5s | 高（JDK 26 提升 5-15%） | 基准 | 通用默认 |
| 分代 ZGC | 亚毫秒 | avg 0.8ms / max 1.2ms | 中高（约 G1 的 96%） | 比 G1 高 15-30% | 低延迟王者 |
| Shenandoah | 1-5ms | avg 1.2ms / max 2.5ms | 中（约 G1 的 94%） | 比 G1 高 10-20% | 内存受限的低延迟 |

机制差异决定性格：ZGC 用**着色指针 + 读屏障**做完全并发回收，停顿与堆大小无关，但指针需要额外映射空间，且**不支持压缩指针**——这是它内存开销高的根源；Shenandoah 用 **Brooks 转发指针 + 读写屏障**，支持压缩指针，停顿略高于 ZGC 但内存友好。G1 在 JDK 26 通过 JEP 522（双卡表 + 写屏障从 50 条降到 12 条指令）显著缩小了与 Parallel 的吞吐差距。

## 3. 2026 选型决策树

选型不是"哪个好"，而是**约束条件的交**：

1. **吞吐优先**（批处理、离线计算、日志分析，停顿秒级可接受）→ Parallel GC。吞吐最高、实现最简，这类场景的延迟指标没人看。
2. **通用在线服务**（停顿目标 20ms 以上、堆 32GB 以内）→ G1（默认）。零配置起步，先调 `MaxGCPauseMillis` 与 IHOP（[04 篇](04-G1性能调优深潜.md)）。
3. **尾延迟敏感**（P99 < 10ms、交易/支付/实时推荐，堆可大至 TB 级）→ 分代 ZGC。接受 CPU 5-10% 与内存 15-30% 的代价，换停顿恒定亚毫秒。
4. **内存受限但需要低延迟**（K8s 小内存 Pod、Cassandra 节点、内存型缓存服务）→ Shenandoah。它支持压缩指针，同样的 Pod 配额比 ZGC 更能扛住，且在 OpenJDK/Adoptium/Corretto 发行版可用（Oracle JDK 不包含）。

一个必须避开的误区：**不要因为"网上说 ZGC 好"就换**。内存开销 15-30% 在内存紧张的容器里是致命的，吞吐折损在 CPU 打满的服务里同样致命。换收集器前先回答：停顿目标是多少？当前哪个指标不达标？换完如何验证？（决策树与业务 SLA 的对应见第 4 节）

还有一个反向误区同样常见：**默认 G1 就绝不换**。当业务明确进入低延迟赛道（P99 必须 <10ms）、或堆涨到 100GB 以上时，硬守 G1 意味着承受每秒级的停顿峰值——这时候换 ZGC 不是跟风，是对 SLA 负责。选型没有"永远正确"的答案，只有"在约束下最优"的方案：吞吐约束、内存约束、延迟约束三者的排序由业务定，收集器由排序推出来。

## 4. 停顿目标如何反推

停顿目标来自业务，不是来自 GC 参数。反推链条：

1. **SLA 拆解**：接口 P99 延迟目标（如 200ms）减去网络、中间件、业务计算预算后，留给 GC 的**停顿预算**通常只有 20-50ms 且要求"不频繁"——GC 停顿是串行叠加的，一次 100ms 停顿可能吃掉一半预算。
2. **换算成收集器约束**：停顿预算 50ms+ → G1 即可（MaxGCPauseMillis=50）；预算 10-20ms → 认真考虑 ZGC/Shenandoah；预算 <10ms → 只有 ZGC。
3. **换算成堆约束**：堆需求由活跃数据决定（[02 篇](02-内存性能调优.md)），堆 >32GB 且要低停顿 → ZGC 几乎是唯一解；堆 <32GB 且内存紧 → Shenandoah 值得测。
4. **验证闭环**：选型后压测确认 P99 停顿与吞吐达标，不达标就换下一档，而不是硬调参数硬撑。

> 🎯 **核心要点**：五个指标中吞吐与停顿是业务目标，分配速率与存活集是根因，GC 频率与原因是线索；四个收集器在"停顿-吞吐-内存"三维上各有取舍，120GB 实测数据是选型的事实基础；选型由停顿预算与内存预算反推，G1 默认、ZGC 极低延迟、Shenandoah 内存受限、Parallel 吞吐——换收集器前先定义目标，换后必须压测验证。
