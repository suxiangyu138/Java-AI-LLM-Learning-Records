## 1. 调优全流程模板

一次规范的 JVM 调优，产出物是"数据 + 报告"，不是"参数 + 感觉"：

1. **开基线**：GC 日志（`-Xlog:gc*`）、JFR 常开、Micrometer JVM 指标接入监控；压测或观察 1 个周期，记录吞吐、P99、FGC 次数、老年代曲线。
2. **确诊**：按"分配热点 → 泄漏 → 堆 → GC → 线程/安全点"顺序定位根因（[01 篇](01-JVM性能全景与调优方法论.md)五源头）。
3. **假设**：写下一句话假设（如"IHOP 45% 太晚导致 Mixed 来不及"），预测会看到什么变化。
4. **实验**：一次只改一个参数，压测环境验证；参数快照留档（`jcmd <pid> VM.flags` 对比）。
5. **验证**：对比基线指标；确认改进且无副作用（吞吐/内存/停顿三项都不恶化）。
6. **灰度上线**：先一台实例验证真实流量，再滚动全量；参数与验证报告入配置管理（Nacos/Apollo 统一管理 JVM 参数时留回滚通道）。
7. **复盘**：把根因、参数、效果写入团队知识库——**调优报告写"为什么"比写"改了什么"值钱**。

## 2. 参数基线模板

**G1 通用（在线服务，堆 ≤32GB）**：

```yaml
-Xms4g -Xmx4g -XX:+UseG1GC
-XX:MaxGCPauseMillis=100
-XX:InitiatingHeapOccupancyPercent=30   # 高分配场景；平稳场景可回 45%
-XX:G1ReservePercent=15
-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m
-XX:+DisableExplicitGC
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/logs/
-Xlog:gc*:file=/logs/gc.log:time,pid,tags:filecount=10,filesize=100m
```

**分代 ZGC（P99 <10ms 场景）**：

```yaml
-Xms16g -Xmx16g -XX:+UseZGC
-XX:ConcGCThreads=4
-XX:ZAllocationSpikeTolerance=3.0      # 分配突发明显时
-XX:MaxDirectMemorySize=2g             # 堆外显式设限
-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/logs/
```

**容器环境（无论哪个收集器）**：去掉写死 `-Xmx`，用 `-XX:MaxRAMPercentage=75 -XX:InitialRAMPercentage=75`；`-XX:MaxDirectMemorySize` 显式设限；K8s request = limit。

## 3. 生产纪律清单

- [ ] 所有服务：GC 日志常开轮转、OOM 自动 dump、JFR 常开、JVM 指标进监控
- [ ] 告警：FGC 即告警；YGC 单次 >500ms 告警；老年代 GC 后不回落连续 3 次告警
- [ ] 容器：MaxRAMPercentage 而非 -Xmx；堆 + 非堆 ≤ 容器限制（[09 篇](09-高并发场景调优实战.md)案例五）
- [ ] 变更纪律：参数变更走配置中心、留快照、灰度验证、可回滚
- [ ] 压测必做：每次大版本/大促前全链路压测，确认 JVM 参数在峰值流量下的表现
- [ ] 发布流程：就绪探针前预热（CDS/AOT + 核心接口预热请求）
- [ ] 安全：诊断命令只读优先、jcmd 优先于 jmap、Arthas 白名单审计、生产禁用 `jmap -dump:live`
- [ ] 复盘：每次 GC 事故后写根因报告，沉淀为团队排查手册

## 4. 报错速查十条

| 现象/报错 | 根因方向 | 排查入口 |
|---|---|---|
| `OutOfMemoryError: Java heap space` | 堆满：泄漏或堆小 | jstat 趋势 + dump/MAT |
| `OutOfMemoryError: Metaspace` | 动态类加载泄漏 | MetaspaceSize 设置 + 类加载器审查 |
| `OutOfMemoryError: Direct buffer memory` | 堆外泄漏 | NMT 对比快照 |
| `StackOverflowError` | 递归过深或 -Xss 过小 | jstack 看栈深度 |
| 容器 OOMKilled | 堆+非堆超容器限制 | MaxRAMPercentage 改造 |
| FGC 频繁且停顿长 | 回收跟不上分配 | 分配热点 → 泄漏 → IHOP/扩堆 |
| to-space exhausted | 晋升失败 | Humongous + G1ReservePercent |
| 运行后吞吐下降 CPU 升 | Code Cache 满退化解释执行 | `jcmd Compiler.codecache` |
| 启动慢 + 启动后毛刺 | C2 热身期 | CDS/AOT + 预热 |
| GC 正常但 RT 抖动 | 安全点/锁竞争/网络 | safepoint 日志 + JFR 锁事件 |

## 5. 面试三范式

- **价值范式**（为什么做）：先给业务收益——"GC 停顿 P99 从 300ms 压到 50ms，大促不再丢单"。调优必须绑定业务指标，否则是自嗨。
- **技术范式**（怎么做）：讲方法论而非参数表——"先 jstat/JFR 确诊根因，当时是分配速率超标，IHOP 提前 + 扩堆，一次一参数压测验证"。展示**数据→假设→验证**的闭环。
- **生产范式**（扛得住）：讲灰度与回滚——"参数走配置中心灰度，快照留档，压测先验证，线上可秒回滚"。再补一句升级 JDK 白拿收益（JEP 522 5-15%），体现 2026 视野。

**追问四连预案**：为什么 ZGC 内存开销大（着色指针不支持压缩 oops）；安全点与 GC 停顿如何区分（safepoint 日志）；容器环境堆怎么配（MaxRAMPercentage 而非 -Xmx）；CDS 与 JEP 483 区别（类加载 vs 类链接，JEP 516 才覆盖 ZGC）。
