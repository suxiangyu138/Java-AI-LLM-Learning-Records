## 5. 核心概念速查

| 概念 | 一句话本质 | 所在篇 |
|---|---|---|
| 分配速率 | 每秒新生对象字节数，GC 压力的根源 | 02/03 |
| 存活集 | GC 后仍存活的对象量，决定回收成本 | 03 |
| 停顿（pause） | STW 时间，业务可感知的毛刺来源 | 03 |
| G1 | 默认收集器，Region 化 + 并发标记 | 04 |
| IHOP | 老年代占用阈值，触发并发标记的开关 | 04 |
| 分代 ZGC | 亚毫秒停顿的低延迟王，JDK 22 起默认模式 | 05 |
| Allocation Stall | ZGC 分配停顿，低延迟场景的头号指标 | 05 |
| 逃逸分析 | 对象不逃逸则标量替换/锁消除/栈上分配 | 06 |
| CDS/AOT | 启动期缓存类加载与链接结果（JEP 483/516） | 06 |
| 安全点 | 线程统一到达的停顿点，GC 与偏执检查依赖它 | 07 |
| JFR | 内置飞行记录器，低开销性能事件采集 | 08 |
| MaxRAMPercentage | 容器环境堆大小百分比参数 | 09 |

## 6. 十大常见误区

1. **调参优先于测量**：没有 GC 日志与基线的调优是玄学；先 jstat/JFR 拿到数据再动手。
2. **堆越大越好**：堆超过活跃数据 3 倍后，GC 停顿与堆成正比，大堆需要 ZGC 才压得住。
3. **FGC 就是调参问题**：FGC 多是分配速率 > 回收速率，先查对象泄漏与分配热点，参数是最后手段。
4. **ZGC 万能**：低延迟用吞吐换，内存开销比 G1 高 15-30%，吞吐优先场景仍是 Parallel/G1。
5. **追求"最优参数"**：G1 默认值（200ms 目标）适合绝大多数服务，改参数前先问业务停顿目标。
6. **调 JVM 前先看代码**（反了）：大量"GC 频繁"是代码问题（大对象、泄漏、过度分配）伪装成 JVM 问题。
7. **忽略 JDK 升级**：JEP 522 白拿 5-15% 吞吐、分代 ZGC 白拿亚毫秒停顿——升级 JDK 是最划算的调优。
8. **Shenandoah = ZGC**：机制不同（Brooks 指针 vs 着色指针），Shenandoah 支持压缩指针，内存受限场景反而更合适。
9. **只调 GC 不调线程**：安全点停顿、栈内存、锁竞争与 GC 交织，07 篇的维度常被遗漏。
10. **容器里写死 -Xmx**：容器内存受限必须用 MaxRAMPercentage，写死 -Xmx 是 OOMKilled 的头号原因。

## 7. 一周学习计划

- **Day 1**：00 总览 + 01 方法论，给当前项目开 GC 日志与 JFR 基线。
- **Day 2**：02 内存调优，用 jstat 观测分配速率与晋升，判断堆是否合理。
- **Day 3**：03 选型 + 04 G1 深潜，画出 G1 并发标记周期，读一条真实 GC 日志。
- **Day 4**：05 分代 ZGC，对比 G1 与 ZGC 在延迟/内存/吞吐的取舍，做选型练习。
- **Day 5**：06 JIT，验证逃逸分析（-XX:+PrintEliminateAllocations）并做一次启动预热。
- **Day 6**：07 线程安全点 + 08 工具链，用 jcmd 抓安全点耗时，用 JFR 看锁竞争。
- **Day 7**：09 案例 + 10 自测，模拟一次 OOM 做完整排查闭环，完成 20 题自测。
