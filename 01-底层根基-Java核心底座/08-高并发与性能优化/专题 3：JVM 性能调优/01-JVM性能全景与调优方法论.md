## 1. JVM 性能四维

JVM 的性能表现由四个维度共同决定，任何单一维度的调优都无法解决整体问题：

- **内存**：堆大小、新生代比例、TLAB、Metaspace、堆外内存。决定对象分配路径的快慢与 GC 的工作量——这是**地基**，其他维度的问题往往表现为内存压力。
- **GC**：收集器选型与参数。决定停顿（STW）时长与频率，是业务可感知毛刺的最主要来源（[03 篇](03-GC性能指标与选型.md)详述）。
- **JIT**：分层编译、逃逸分析、内联、Code Cache。决定热点代码的机器码质量与启动速度（[06 篇](06-JIT编译性能调优.md)详述）。
- **线程**：线程数、安全点、锁竞争。决定并发吞吐的上限与调度开销（[07 篇](07-线程与锁性能调优.md)详述）。

四维之间强耦合：分配速率过高 → GC 压力大 → 停顿变长 → 线程阻塞 → 请求堆积 → 分配更多对象，形成恶性循环。因此调优必须**从数据出发定位源头维度**，而不是按维度轮流试。

## 2. 性能问题的来源

JVM 层面的性能问题可以归结为五个源头，理解它们才能把现象翻译成根因：

- **分配速率（allocation rate）**：每秒新生对象的字节数。它是 GC 压力的源头——回收多少垃圾取决于分配多少垃圾。高分配速率直接推高 Young GC 频率与停顿。
- **存活集（live set）**：GC 后仍存活的对象量。它决定回收成本：Young GC 要复制存活对象，Mixed/Full GC 要扫描与标记。存活集大而稳定，说明业务缓存大或代码把数据留在了堆里。
- **停顿（pause）**：STW 期间所有应用线程冻结。停顿的来源不只是 GC——还有安全点协调、代码缓存刷新（CodeCache）、JIT 编译线程的偏执检查（`-XX:+SafepointTimeout` 可观测）。
- **编译与反优化**：C2 编译是异步的（编译线程跑在后台），但反优化（deoptimization）会在线程上同步执行，热点路径失速瞬间明显。
- **锁与调度**：锁竞争让线程阻塞在 Monitor 上（JFR 的 Java Monitor Blocked 事件可直接量化），线程过多则上下文切换吃掉 CPU。

> 💡 五个源头中，**分配速率**是最容易被业务代码放大的：序列化、字符串拼接、装箱、日志参数拼接，都是隐形分配器。用 JFR 的分配采样（allocation profiling）看热点分配栈，往往比调 GC 参数更有效。

## 3. 数据驱动的调优方法论

调优不是调参，是**实验科学**。标准流程四步，每一步都以数据为准：

1. **建立基线**：开启 GC 日志（`-Xlog:gc*`）与 JFR 录制，压测或线上采集一周期数据，记录吞吐、P99 延迟、GC 频率与停顿、内存曲线。
2. **提出假设**：从数据定位瓶颈维度（如"FGC 每 3 分钟一次，老年代 GC 后不回落"→ 假设泄漏或堆过小），假设必须能用下一步验证。
3. **设计实验**：一次只改一个参数，小流量/压测验证。多个参数同改无法归因，这是新手最常见的错误。
4. **验证与回滚**：对比实验前后基线指标，确认改进（或确认无恶化）；保留参数快照，任何参数都要有回滚方案。

配套三条纪律：

- **先代码后参数**：排查顺序永远是"看分配热点 → 查泄漏 → 调堆 → 选 GC"。参数调整放在代码问题排除之后，因为参数是最后的杠杆，见效快但掩盖根因。
- **升级 JDK 优先**：2026 年最划算的调优是升级——JDK 26 的 JEP 522 给 G1 带来 5-15% 吞吐提升且零配置，分代 ZGC 在 JDK 21+ 逐步成熟（[04 篇](04-G1性能调优深潜.md)、[05 篇](05-分代ZGC与低延迟调优.md)）。老 JDK 上堆参数的收益往往不如一次升级。
- **监控常态化**：调优不是一次性动作。GC 日志、JFR、Prometheus JVM 指标（Micrometer 的 jvm.gc.* / jvm.memory.*）应长期运行，让回归在参数变更或代码变更时立刻暴露。

## 4. 调优的边界

JVM 调优解决不了的问题必须认得出来，否则会在错误层浪费大量时间：

- **SQL 慢查询与无索引**：数据库层的延迟，调 JVM 无济于事（属 [专题 4：数据库性能优化](../专题%204：数据库性能优化/) 范畴）。
- **上游服务 RT 高**：依赖的延迟问题，应做超时、降级、熔断而非调堆。
- **网络与带宽**：RPC 传输层瓶颈，jstack 能看到大量 RUNNABLE 但 CPU 不高——线程在等 IO。
- **业务逻辑复杂**：算法复杂度、循环内做 IO、重复计算，属于代码层优化。
- **中间件本身**：Redis/MQ 的自身性能，JVM 只是客户端的载体。

判断框架：**先看 CPU 与内存曲线**——CPU 正常而 RT 高，大概率不是 JVM 问题；CPU 高再细分是 GC 线程、JIT 编译线程还是业务线程，用 `top -H` 加 jstack 定位。全链路压测（[专题 1 04 篇](../专题%201：性能理论基础/04-性能测试方法论.md)）的意义就在这里：压测分层放大，逐层剥离，JVM 只是其中一层。

> 🎯 **核心要点**：JVM 性能四维（内存/GC/JIT/线程）强耦合，从分配速率与存活集这两个源头追根因；调优是"基线→假设→实验→验证"的实验流程，一次一参数、先代码后参数、升级 JDK 优先；先确认瓶颈在 JVM 层再动手，SQL、网络、上游延迟不是 JVM 的职责。
