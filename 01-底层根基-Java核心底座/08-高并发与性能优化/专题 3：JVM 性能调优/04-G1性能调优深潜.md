## 1. G1 的工作模式

G1 把堆划分为 1-32MB 的 Region（默认堆/2048），逻辑上仍分新生代与老年代，但物理上 Region 动态归属。性能特征由三件机制决定：

- **并发标记周期（concurrent cycle）**：老年代占用达到 IHOP 阈值时，G1 启动并发标记（标记阶段在 GC 线程上跑，应用线程不冻结），标记完成后回收**回收价值最高**的 Region。这个周期的启动时机直接决定老年代压力能否被及时释放。
- **Young GC 与 Mixed GC**：Young GC 只回收新生代 Region（停顿 20-100ms 量级）；Mixed GC 在标记周期后混合回收新生代 + 部分老年代 Region，是老年代空间释放的主要手段。
- **停顿模型**：G1 以 `MaxGCPauseMillis` 为软目标（默认 200ms），通过调整回收集大小控制停顿——**目标越小，每次回收越少，GC 越频繁**，二者必须权衡。

调优的第一课：**G1 的参数调整本质上是在调整这三个机制的节奏**。节奏对了，默认值就够用；节奏错了，任何参数都救不回来。

节奏是否健康，看三个信号：**Young GC 停顿是否逼近目标**（逼近说明回收集过大，目标或堆要调整）；**并发标记周期能否在老年代耗空前完成**（不能 → IHOP 太高或并发线程不足）；**Mixed GC 是否真正释放了老年代空间**（只回收不释放 → 回收价值判断失效，多半是存活对象太多）。把这三个信号写进监控与例行巡检，G1 的问题会在恶化前被看见——这是"调优是常态化监控"纪律在 G1 上的具体形态（[01 篇](01-JVM性能全景与调优方法论.md)）。

## 2. 关键参数与默认值

| 参数 | 默认值 | 控制什么 | 调优方向 |
|---|---|---|---|
| `MaxGCPauseMillis` | 200ms | 停顿软目标 | 在线服务 50-100ms；过小则 GC 过频 |
| `InitiatingHeapOccupancyPercent`（IHOP） | 45% | 老年代占用触发并发标记的阈值 | 高分配场景降到 30-35%，让标记更早启动 |
| `G1HeapRegionSize` | 堆/2048 | Region 大小 | 大对象多可调大；一般不动 |
| `G1ReservePercent` | 10% | 预留空间防晋升失败 | FGC 频繁时可到 15-20% |
| `G1NewSizePercent`/`G1MaxNewSizePercent` | 5%/60% | 新生代上下限 | 高分配场景适当抬高下限 |
| `ConcGCThreads` | ParallelGCThreads 的 1/4 | 并发标记线程数 | 标记跟不上分配时加大 |

IHOP 是最值得调的参数：它决定了并发标记**是否来得及**在老年代耗尽前完成。判断标准看 GC 日志——如果 Mixed GC 频繁出现且老年代占用已接近 100% 才触发标记，说明 IHOP 太高；如果频繁触发周期但老年代占用低，说明 IHOP 太低，标记工作浪费。G1 也提供自适应 IHOP（`-XX:+G1UseAdaptiveIHOP`，JDK 11+ 默认开启），它会按历史分配速率动态推算阈值；显式设置只在自适应表现差（标记经常赶不上）时才介入——多数场景"先观察自适应、再决定是否覆盖"比上来就写死更稳。

## 3. Humongous 与晋升失败

G1 的两个隐藏陷阱都与"大对象"相关：

- **Humongous 对象**：超过 Region 一半的对象直接分配在连续 Humongous Region（老年代）。它不参与 young GC 复制、回收依赖并发标记周期、且立即抬高老年代占用——**大对象多 = IHOP 频繁触发 = 标记周期繁忙**。业务侧对策：拆分大对象（大数组分批、大字符串分块、批量结果集分批处理），这比任何参数都有效。
- **晋升失败（to-space exhausted）**：Young/Mixed GC 时新生代存活对象放不进 Survivor/老年代预留空间，GC 中断并退化为 Full GC——这是 G1 最严重的停顿事故（可达数秒）。对策按序：查 Humongous 对象、调大 `G1ReservePercent`、提前 IHOP、必要时扩堆。

## 4. JEP 522：JDK 26 的吞吐改善

JDK 26 的 JEP 522（G1 GC: Improve Throughput by Reducing Synchronization）是 G1 近年最大的性能变革，升级即可获得：

- **双卡表（dual card table）**：应用线程更新活跃卡表无同步，GC 优化线程在另一张表工作，切换时通过线程局部握手（thread-local handshake）对齐可见性，不再需要全局安全点。
- **流线化写屏障**：x86-64 上写屏障指令从约 50 条降到 12 条——每个引用字段写入都省下的指令数，在重写入负载下累计为 **5-15% 吞吐提升**。
- **调优含义**：GC 停顿时间可能略降，native 内存可能更低；**无需任何参数变更**。这是"升级 JDK 优于堆参数"论点的最新证据（[01 篇](01-JVM性能全景与调优方法论.md)纪律之一）。

## 5. 大促案例：从 FGC 到零 FGC

**背景**：某电商订单服务大促流量翻 10 倍，FGC 每 3 分钟一次、单次停顿 3-5 秒，P99 RT 3200ms。

**初始配置**：`-Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200`

**日志诊断**：`[GC pause (G1 Evacuation Pause) (young) ... to-space exhausted]` → 老年代 98% 触发 Full GC。根因是流量放大后分配速率远超回收速率：堆过小、IHOP 45% 触发太晚、大促订单对象量大。

**调整方案**（一次一组，每组压测验证）：

```yaml
-Xms8g -Xmx8g                        # 堆翻倍匹配峰值分配
-XX:MaxGCPauseMillis=100             # 停顿目标收紧
-XX:InitiatingHeapOccupancyPercent=30 # 老年代 30% 即启动并发标记
-XX:G1ReservePercent=15              # 预留空间防晋升失败
```

**结果**：FGC 清零，Mixed GC 平均停顿 85ms，P99 RT 180ms。

**复盘**：真正起作用的顺序是扩堆 → 提前标记 → 预留空间；三个参数都服务于同一个诊断结论"回收跟不上分配"。调优报告必须写明每个参数与根因的对应关系，否则无法沉淀为方法论。

> 🎯 **核心要点**：G1 调优是调"并发标记 + Mixed GC"的节奏——IHOP 决定标记是否来得及，MaxGCPauseMillis 决定停顿与频率的平衡，ReservePercent 是晋升失败的缓冲；Humongous 与晋升失败两大陷阱靠拆分大对象与预留空间解决；JDK 26 的 JEP 522 双卡表 + 12 条写屏障让 G1 白拿 5-15% 吞吐，升级优先于调参。
