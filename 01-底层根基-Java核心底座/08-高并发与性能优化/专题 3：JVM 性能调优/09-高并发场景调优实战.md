## 1. 案例一：大促 GC 停顿

**症状**：双十一订单服务流量翻 10 倍后，P99 RT 从 80ms 飙到 3200ms，告警连续轰炸，`Full GC` 每 3 分钟一次、单次 3-5 秒。

**数据**：GC 日志显示 `to-space exhausted` → Full GC；老年代 GC 后占用 98% 不回落；`jstat` 看 Eden 每秒分配量是平日的 8 倍。

**根因**：分配速率 > 回收速率——4GB 堆容不下峰值分配，IHOP 45% 触发并发标记太晚，标记周期未完成老年代已耗尽，晋升失败退化为 Full GC。

**对策**（见 [04 篇](04-G1性能调优深潜.md) 完整参数）：扩堆 8GB、IHOP 降到 30%、`G1ReservePercent` 提到 15%、停顿目标 100ms。逐项压测验证后 FGC 清零，P99 180ms。

**复盘**：三个参数对应同一个根因"回收跟不上分配"；如果只调 `MaxGCPauseMillis` 而不扩堆，等于让 G1 用更小的工作集反复救火——调参必须服务根因，这是本案例的通用教训。

## 2. 案例二：堆内存泄漏

**症状**：后台服务运行两周后 FGC 从每天 2 次爬升到每 10 分钟 1 次，停顿从 300ms 涨到 2 秒，CPU 持续高位。

**数据**：jstat 老年代 GC 后占用逐日抬高（从 20% 到 85%）；OOM 自动 dump（`-XX:+HeapDumpOnOutOfMemoryError` 提前配好）。

**分析**：MAT Leak Suspects 报告指向 `HashMap` 实例 300 万个、retained 1.2GB，引用链是"用户上下文缓存"——每次请求把用户对象放入一个**静态缓存 Map** 且只增不减（value 按 key 未命中才 put，但业务新增了"永不重复的 key"：时间戳拼接）。

**对策**：缓存加 TTL（过期清理）+ 容量上限 + 监控 `Map.size()`；启动加日志确认清理生效。

**复盘**：泄漏的经典形态是"缓存"——无界 Map 加永不复用的 key。排查顺序是 jstat 趋势 → dump → MAT 引用链 → 代码修复，**先确诊后动手**，参数调整在这里毫无意义。

## 3. 案例三：堆外内存泄漏

**症状**：容器频繁 OOMKilled（重启后撑几天再死），但**堆内存曲线完全正常**（jstat 老年代平稳），GC 日志无异常。

**数据**：`free` 看物理内存持续上涨；NMT 两次快照对比，`Internal` 与 `Direct buffer` 段差值持续增长；代码审查发现 Netty 的 `ByteBuf` 在异常路径未 release。

**根因**：`DirectByteBuffer`（堆外）只增不减——异常路径跳过 `release()`，最终触达 `MaxDirectMemorySize`（或容器内存上限）。

**对策**：try-finally 保证 release（`ReferenceCountUtil.release`）；`-XX:MaxDirectMemorySize` 设上限让问题显性化（报错而非沉默）；NMT 常开监控。

**复盘**：**"堆正常但 RSS 涨"是堆外问题的标志性特征**（[02 篇](02-内存性能调优.md)），NMT 对比快照是定位主工具。这类问题与 GC 调优无关，靠的是资源生命周期纪律。

## 4. 案例四：启动毛刺与预热

**症状**：服务发布后前 3-5 分钟 RT 波动大（偶发 500ms+），随后自动恢复；每次发布都被"有没有新问题"的误报警吓一跳。

**数据**：JFR 显示前几分钟大量解释执行与 C2 编译事件；安全点日志显示编译完成前有反优化。

**根因**：新实例上线即接流量，热点方法还在解释执行/浅编译阶段；容器化发布滚动替换放大了"每台机器都要热身"的窗口。

**对策**：就绪探针（readiness）前增加预热请求（`@PostConstruct` 循环调用核心接口，或压测请求打一轮）；Spring Boot 3.5 自动 CDS 归档 + JDK 26 AOT 缓存缩短启动（[06 篇](06-JIT编译性能调优.md)，实测启动 3s→0.8s）；发布节奏"先一台验证再滚动"。

**复盘**：启动毛刺是 JVM 热身期的必然（C2 编译需要调用次数），解决方式不是调参而是**预热与探针设计**——让服务"准备好了再收流量"，并把预热纳入发布流程。

## 5. 案例五：容器 OOMKilled

**症状**：K8s Pod 限 4GB 内存，高峰期随机 OOMKilled，重启自愈但造成毛刺；排查发现 `-Xmx4g` 写死在启动参数里。

**数据**：`kubectl describe pod` 显示 OOMKilled；`jstat` 堆从未超过 3GB；但堆外（Metaspace + 线程栈 + Code Cache + DirectBuffer）吃掉 1GB+——堆 + 堆外 = 5GB > 4GB 限制。

**根因**：**-Xmx 写死等于容器限制，没有给非堆留余量**（[02 篇](02-内存性能调优.md) 内存账）。

**对策**：改用百分比参数——`-XX:MaxRAMPercentage=75 -XX:InitialRAMPercentage=75`（4GB 容器得 3GB 堆，1GB 留给非堆）；K8s resource request = limit（避免 CPU 压缩影响 GC 性能）；监控改为按容器内存利用率告警；`-XX:MaxDirectMemorySize` 显式设限，把"堆外预算"变成可审计的数字。

**复盘**：容器化环境"写死 -Xmx"是 2026 年最常见的 JVM 事故，升级到容器感知参数（JDK 10+ 默认 `UseContainerSupport`）是标准解法；发布前检查清单必须含"堆 + 非堆 ≤ 容器限制"（[10 篇](10-生产实战与自测.md)）。追问一步：为什么不用 `-Xmx` 直接留余量？因为容器规格会变（4GB → 8GB 扩容时 -Xmx 写死要改代码，百分比参数自动跟随），百分比参数把"内存预算"声明为容器规格的比例，扩缩容免维护。

> 🎯 **核心要点**：五个案例对应五类高频事故——大促 FGC（回收跟不上分配，调参服务根因）、堆泄漏（缓存无界 Map，MAT 引用链确诊）、堆外泄漏（堆正常 RSS 涨，NMT 对比定位，释放纪律兜底）、启动毛刺（C2 热身期，预热与探针解决）、容器 OOMKilled（-Xmx 写死，MaxRAMPercentage 标准解）。共同教训：**先数据确诊、后对症下药，参数是最后手段**。
