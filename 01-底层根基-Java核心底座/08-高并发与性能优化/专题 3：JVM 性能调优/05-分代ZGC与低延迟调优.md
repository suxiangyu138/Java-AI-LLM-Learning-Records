## 1. ZGC 的性能原理

ZGC 的性能特征由三件机制决定，理解它们才能理解"为什么停顿与堆大小无关"：

- **着色指针（colored pointers）**：对象地址的 64 位中借用高位记录对象状态（Marked/Finalizable/Remapped），GC 状态变化只改指针不碰对象——这使回收的绝大多数阶段无需移动对象的互斥保护。
- **读屏障（load barrier）**：应用线程读取对象引用时，若指针状态过期则在线程上"自愈"式修正。回收与分配因此完全并发，STW 只剩根扫描、栈扫描等极小部分——这正是停顿恒定的来源。
- **分代化后的双代模型**：年轻代对象大部分朝生夕死，分代让 Young 回收与并发标记的工作量大幅下降，吞吐比单代时代明显提升，这也是它从"实验品"走向"默认低延迟之选"的关键。

代价必须说清：着色指针需要地址映射空间，**ZGC 不支持压缩指针**，堆内存开销比 G1 高 15-30%；读屏障在每个引用读取上都有开销，CPU 比 G1 多消耗约 5-10%。ZGC 的本质是**用内存与 CPU 预算买停顿预算**。

由此推出一组"不适用"场景，判断时先排除：**内存受限的容器**（Pod 配额紧，多出的 15-30% 可能直接触发 OOMKilled——这类场景优先考虑 Shenandoah，它支持压缩指针且停顿也在毫秒级）；**CPU 打满的吞吐型服务**（读屏障与并发回收的 CPU 预算无处可挤）；**堆很小且延迟要求不苛刻**（<4GB 堆上 G1 的停顿本就有限，ZGC 的优势没有发挥空间）。先排除了再谈"要不要 ZGC"，选型才有依据。

## 2. 演进：从单代到分代的三个里程碑

- **JEP 439（JDK 21）**：分代 ZGC 预览，首次引入分代模型。
- **JEP 474（JDK 22）**：**分代模式成为默认**（`-XX:+UseZGC` 即分代），单代模式标记废弃；`-XX:+ZGenerational` 选项开始告警。
- **JEP 490（JDK 24）**：**移除单代模式**，分代成为唯一模式；到 JDK 26，过期的 `ZGenerational`/`ZMarkStackSpaceLimit` 标志正式清除（指定即报错）。

演进结论：2026 年的 ZGC 就是分代 ZGC，任何教程里"单代 vs 分代对比"的写法都已过时（[00 总览](00-总览.md)误区 8 同源）。选型时只需回答"要不要低延迟"，不必再选模式。

## 3. JDK 26 的性能改进

JDK 26 的分代 ZGC 又上一层，让"低延迟"与"大堆"的边界进一步扩大：

- **完全并发年轻代收集**：年轻代回收不再有 STW，停顿来源进一步收窄。
- **并发栈扫描**：最大停顿从 JDK 21 的约 1.5ms 降到约 0.3ms——降幅 80%，高频请求场景的毛刺窗口再缩小。
- **NUMA 感知增强**：内存分配、GC 线程绑定、对象迁移按 NUMA 节点优化，双路服务器实测吞吐提升 15-20%。
- **压缩类指针支持**：对象头从 16 字节降到 12 字节，内存占用降低 10-15%——部分抵消了不支持压缩 oops 的代价。
- **JEP 516（AOT 对象缓存支持 ZGC）**：启动优化（CDS/AOT）首次覆盖 ZGC 场景，训练与部署可用不同收集器（[06 篇](06-JIT编译性能调优.md)）。

这些改进全部"升级即得"，再次印证"升级 JDK 优先"的纪律。

## 4. 参数与关键指标

ZGC 需要人工干预的参数极少，默认值几乎就是最优，**过度调参是 ZGC 调优的第一误区**：

| 参数 | 默认 | 何时调整 |
|---|---|---|
| `ConcGCThreads` | 自适应 | 分配尖峰频繁、Allocation Stall 增多时加大 |
| `ZAllocationSpikeTolerance` | 2.0 | 分配突发明显时调大到 3-4，预留更多回收空间 |
| `-Xmx` | — | 给 ZGC 的内存预算 = 活跃数据 × 3（因并发回收需余量） |
| `MaxDirectMemorySize` | 默认堆上限 | 堆外场景显式设限 |

关键指标是 **Allocation Stall**——应用线程因分配不到内存而阻塞的累计时长。它是 ZGC 世界里"分配速率 > 回收速率"的告警灯：stall 频繁 = 堆偏小或 ConcGCThreads 不足，先扩堆（或调大 ZAllocationSpikeTolerance），再考虑并发线程数。GC 日志里 `Allocation Stall (Thread=..., N requesters, Xms)` 即为该事件。另一个值得看的指标是 GC 周期触发原因（Allocation Rate / Proactive / Warmup）——原因分布揭示老年代压力来源。

## 5. 低延迟场景落地

低延迟不是"选了 ZGC 就完事"，而是**链路级的停顿治理**：

1. **确认停顿预算**：P99 <10ms 才值得上 ZGC；预算 10-50ms 先用 G1 的 50ms 目标试试，多数服务够用且成本低（[03 篇](03-GC性能指标与选型.md)反推法）。
2. **给足内存预算**：活跃数据 × 3 起步，必要时用 `MaxRAMPercentage` 在容器内给堆留足余量——**ZGC 死于内存不足的概率远高于死于停顿**。
3. **排查非 GC 停顿**：切换 ZGC 后若毛刺仍在，转向安全点（`-Xlog:safepoint*`）、JIT 编译、锁竞争——GC 只是停顿的一个来源（[07 篇](07-线程与锁性能调优.md)）。
4. **压测验证**：用 [专题 1](../专题%201：性能理论基础/05-瓶颈定位方法论.md) 的分层压测方法，对比 G1 与 ZGC 在 P99 停顿、吞吐、RSS 三个维度上的实测，数据说话再上线。
5. **接受代价**：吞吐降 5-10%、内存升 15-30% 是购买低延迟的价格。若业务实际不敏感，切回去是理性的，不是失败。

> 🎯 **核心要点**：ZGC 用着色指针 + 读屏障把回收完全并发化，停顿恒定亚毫秒且与堆大小无关，代价是内存 +15-30%、CPU +5-10%；分代是唯一模式（JEP 474 默认、JEP 490 移除单代）；JDK 26 并发栈扫描 0.3ms、NUMA 提升、AOT 缓存支持让它更进一步；调参极少，盯 Allocation Stall 与触发原因即可；低延迟落地是停顿链路治理——确认预算、给足内存、排查非 GC 停顿、压测对比、接受代价。
