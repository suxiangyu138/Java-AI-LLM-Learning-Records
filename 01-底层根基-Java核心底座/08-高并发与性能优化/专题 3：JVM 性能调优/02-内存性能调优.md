## 1. 堆大小策略

堆大小不是越大越好，而是**匹配活跃数据量**：

- **经验公式**：压测观测老年代稳定占用（GC 后不降的水平线），堆总大小设为活跃数据 × 1.5-2。堆过小 → FGC 频繁；堆过大 → 单次 GC 扫描范围大、停顿长（G1 按 Region 回收有所缓解，但仍要付出标记成本）。
- **-Xms = -Xmx**：初始堆与最大堆一致，避免运行时动态扩容带来的两次停顿与性能抖动。容器环境则用 `MaxRAMPercentage` 代替写死（[09 篇](09-高并发场景调优实战.md)容器案例）。
- **堆的物理内存账**：堆外还有 Metaspace、线程栈、JIT Code Cache、DirectBuffer、GC 内部结构。物理机/容器内存 = 堆 + 约 25% 的非堆余量，写死 `-Xmx` 等于容器总内存是最经典的 OOMKilled 事故。
- **超大堆的边界**：堆超过 32GB 时压缩指针（compressed oops）失效，对象引用从 4 字节变 8 字节，同样数据量的内存开销上升约 10%。要么控制在 32GB 以内，要么接受代价并用 ZGC（[05 篇](05-分代ZGC与低延迟调优.md)）。

## 2. 新生代与对象晋升

新生代大小的本质是**在 Young GC 频率与晋升风险之间取舍**：

- 新生代大 → Young GC 频率低，但单次停顿变长（复制更多存活对象），且老年代空间被挤压。
- 新生代小 → Young GC 频繁，临时对象在 Eden 就能回收，但短命对象晋升到老年代的风险上升，老年代碎片化后触发 Mixed/Full GC。
- **经验起点**：堆的 1/3 左右（G1 由 `G1NewSizePercent`/`G1MaxNewSizePercent` 自动调节，默认 5%/60%）。高分配速率场景（RPC 序列化、日志、DTO 转换）可适度调大，让大部分临时对象死在新生代。

**晋升（promotion）是监控重点**：用 jstat 观察老年代增长速率。老年代平稳缓慢增长是正常业务留存；GC 后老年代不回落、或 FGC 时老年代占用居高不下，是泄漏或晋升过快的信号（[08 篇](08-性能诊断工具链.md) jstat 指标解读）。G1 的晋升失败（to-space exhausted）会直接退化为 Full GC，这是大促场景最典型的停顿事故（[04 篇](04-G1性能调优深潜.md)案例）。

## 3. TLAB 与分配路径

对象分配的默认路径是 TLAB（Thread-Local Allocation Buffer）——每个线程在 Eden 里划一段私有空间，分配对象只做指针 bump，无锁无竞争。理解 TLAB 对性能的意义：

- **TLAB 之外的分配是慢路径**：对象超过 TLAB 剩余空间、或对象是巨型对象（G1 中超过 Region 一半的 Humongous），会走共享空间分配或直接进老年代，触发同步。高频大数组、大字符串是慢路径分配的常见来源。
- **Humongous 对象是 G1 的隐藏坑**：大对象直接分配在连续 Humongous Region，不参与 young GC 的复制，回收靠并发标记周期，且会立即占用老年代空间。业务侧对策是**拆分大对象**（大 List 分批、大字符串分块），而不是调参。
- **TLAB 参数一般不动**：`-XX:TLABSize`、`-XX:ResizeTLAB` 默认已自适应，手工调整收益极低。真正有效的是**减少对象总量**——避免循环内装箱、避免无谓的中间字符串（`StringBuilder` 优于拼接）、复用缓冲（`ThreadLocal` 池化 byte[]）。
- **分配热点怎么找**：JFR 分配采样（allocation profile）直接给出"哪个调用栈分配了多少字节"，这是内存调优的第一工具，比猜代码高效得多。

## 4. Metaspace 与堆外内存

- **Metaspace**：类元数据的本地内存。**必须显式设置上限**（`-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m`）——默认无上限，动态类加载（CGLib 代理、反射生成类、脚本引擎）泄漏时会被打爆。Metaspace 频繁触发 FGC 是类加载器泄漏的典型信号。
- **堆外内存（DirectBuffer）**：`ByteBuffer.allocateDirect()`、Netty 的 `Unpooled.directBuffer()`、MappedByteBuffer 都分配在堆外。特征是**堆正常但 RSS 持续上涨**，最终触发容器 OOMKilled 或 `OutOfMemoryError: Direct buffer memory`。排查工具是 NMT：启动加 `-XX:NativeMemoryTracking=summary`，用 `jcmd <pid> VM.native_memory summary` 对比两次快照看哪块在涨（[08 篇](08-性能诊断工具链.md)完整命令）。
- **堆外泄漏三守则**：DirectBuffer 使用 try-finally 释放（Netty 的 `ReferenceCountUtil.release`）；`-XX:MaxDirectMemorySize` 设上限做兜底；NMT 在生产低开（summary 开销约 1-2%）常态化监控。

## 5. 内存泄漏如何拖垮性能

泄漏对性能的破坏不是"内存不够"那么直接，而是**渐进式恶化**：

1. 老年代被泄漏对象占据 → 可用空间减少 → FGC 提前且频繁。
2. 每次 GC 都要扫描/标记海量已死对象 → 停顿逐步拉长（从百毫秒级滑向秒级）。
3. 分配失败频率上升 → 应用进入"GC 循环"状态，吞吐断崖式下跌。
4. 最差情况 OOM 或容器被杀 → 毛刺升级为宕机。

所以**内存调优的第一优先级是确认没有泄漏**，其次才是调大小。识别信号：jstat 看老年代 GC 后占用是否回落、GC 日志看 FGC 频率趋势、监控看 RSS 是否持续上升。定位手段是 heap dump（`-XX:+HeapDumpOnOutOfMemoryError` 自动触发，或 `jcmd <pid> GC.heap_dump` 手动抓）加 MAT 的 Leak Suspects——生产环境优先用 jcmd 而非 jmap（jmap -dump:live 会触发一次 FGC 且停顿应用）。

> 🎯 **核心要点**：堆大小匹配活跃数据 ×1.5-2 并 -Xms=-Xmx，容器用 MaxRAMPercentage；新生代取舍在 GC 频率与晋升风险之间，晋升速率是监控重点；TLAB 是默认快路径，Humongous 与慢路径分配靠拆分对象而非调参解决；Metaspace 显式设限、堆外用 NMT 盯防；先确认无泄漏再谈调大小，泄漏是性能渐进恶化的根因。
