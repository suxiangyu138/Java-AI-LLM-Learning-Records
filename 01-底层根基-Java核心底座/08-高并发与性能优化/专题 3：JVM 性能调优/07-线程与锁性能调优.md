## 1. 线程的开销

每个平台线程两笔固定开销，线程数失控时双双放大：

- **栈内存**：默认 1MB/线程（`-Xss`），1000 个线程 = 1GB 堆外内存。线程数多但堆正常时 RSS 飙升，多半是它。调小 `-Xss`（如 512KB）可缓解，但递归深的代码会栈溢出——先量化最大递归深度再调。
- **上下文切换**：线程切换涉及寄存器保存/恢复、缓存失效、调度队列操作。症状是 **CPU 高但业务吞吐低**——CPU 在"切换"而非"干活"。用 JFR 的线程上下文切换事件（OS thread context switches）量化。

2026 年的解法是**虚拟线程**（JEP 491 已解决大部分 pinning）：栈不在内存中、切换是轻量挂起，百万级并发不再靠调平台线程数（[专题 2](../专题%202：Java%20单机并发编程/08-异步编程：Future到虚拟线程.md)）。JVM 调优视角的结论：**平台线程池按 IO 模型精算参数，虚拟线程按结构化并发设计，不要混用两种心智**。

## 2. 安全点：被忽略的停顿

安全点（safepoint）是所有应用线程必须到达的统一停顿点——GC 需要、偏向锁偏置需要、类重定义需要。它是**非 GC 停顿的头号来源**，但常被误诊为"GC 问题"：

- **观测**：`-Xlog:safepoint*` 记录每次安全点停顿的耗时与到达原因；JFR 的 Safepoint 事件直接给出"哪个线程最慢到达"（阻塞在什么代码里）。
- **慢安全点根因**：某个线程长时间不进入安全点检查点——典型的元凶是**密集循环**（尤其无方法调用的纯计算循环、`System.currentTimeMillis()` 高频率调用）、**大对象拷贝**、`Thread.sleep` 与 IO 是安全的（会主动检查），而 `while(true){...}` 数学计算是"流氓"。
- **对策**：热点循环内插入安全点检查点（JDK 9+ 默认按需插入，多数已缓解）；升级 JDK——JDK 17+ 的偏执检查与安全点机制持续简化；确认"GC 停顿"前先看安全点日志，**不要把安全点问题当成 GC 问题调**。

## 3. 锁竞争调优

锁竞争让并发退化为串行——持锁阻塞直接拖慢整个服务。调优顺序与 JUC 体系一致（[专题 2](../专题%202：Java%20单机并发编程/09-并发性能调优与故障排查.md)），JVM 侧补充三点：

- **量化竞争**：JFR 的 `Java Monitor Blocked` / `Lock Held` 事件给出"哪个锁、竞争多激烈、持有多久"——这是锁调优的数据依据，比猜代码高效。`thread -n 3`（Arthas）看最忙线程在等什么。
- **锁粒度**：锁内只留原子操作，IO/序列化/远程调用移出锁外；写多读少用无锁（CAS/原子类），读多写少用读写锁（StampedLock 乐观读）。
- **锁升级路径（JDK 现代状态）**：无竞争时轻量级锁开销极低（CAS 一次），竞争升级为重量级 Monitor。**偏向锁已在 JDK 15 废弃、JDK 18 移除**——任何"偏向锁优化"的面试答案与教程都是旧基线（JMM 体系已同步更新）。JDK 26 的虚拟线程 pinning 修复（JEP 491）让 synchronized 不再坑虚拟线程，但重量级 Monitor 竞争仍是热点，锁粒度优化永不过时。

## 4. 伪共享与缓存行

伪共享（False Sharing）：两个线程各自修改不同变量，但两变量落在同一 64 字节缓存行——每次写入都使对方的缓存行失效，被迫反复重载，性能可退化一个数量级。JUC 源码的 `@Contended` 与 padding 是现成教材（LongAdder 的 Cell）。

业务侧认知：**把多个高频热变量放进同一个类/相邻数组是伪共享的温床**。诊断难（火焰图显示缓存未命中但代码无锁），对策简单——热变量间留 padding 或拆对象；JDK 允许 `-XX:-RestrictContended` 启用注解 padding，但多数场景直接改代码更干净。

## 5. 虚拟线程对调优的影响

虚拟线程（JEP 444 正式化，JDK 21）改变了线程维度调优的玩法：

- **平台线程数不再等于并发度**：百万级虚拟线程的栈在堆外按需增长（KB 级），`-Xss` 调优与"线程数超限"类问题基本消失，线程池"按核数×倍数"的公式不再适用（[专题 2](../专题%202：Java%20单机并发编程/07-线程池.md) 的虚拟线程选型）。
- **新增两个观测点**：`jfr jdk.VirtualThreadStart/End` 看虚拟线程生命周期；`jdk.JavaMonitorEnter` 看锁竞争（虚拟线程阻塞在 Monitor 时仍是真阻塞）。
- **pinning 残余**：JEP 491 修复了大部分 synchronized pinning，但同步块内做阻塞 IO 仍可能 pin 住平台线程——GC 停顿表现相同，但根因在锁设计（[专题 2](../专题%202：Java%20单机并发编程/02-synchronized与volatile深潜.md)）。
- **调优纪律不变**：安全点与 GC 停顿照样发生，虚拟线程不消除它们——只消除了"线程数量"这一维度的瓶颈。

> 🎯 **核心要点**：平台线程栈内存与上下文切换是线程失控的两种症状，虚拟线程是 2026 的正解；安全点是常被误诊为 GC 的停顿来源，慢到达根因是密集循环，先看 safepoint 日志再调 GC；锁竞争用 JFR 锁事件量化，粒度优化永远有效，偏向锁已废弃别再用旧答案；伪共享藏在缓存行里；虚拟线程改变了线程维度玩法，但安全点与 GC 依旧——调优纪律不变。
