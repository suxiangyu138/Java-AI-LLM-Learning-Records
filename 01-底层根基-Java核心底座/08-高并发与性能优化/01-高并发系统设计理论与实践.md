# 高并发系统设计理论与实践

## 一、高并发系统设计概述

高并发（High Concurrency）是互联网分布式系统设计中最为核心的挑战之一。它指的是系统能够同时处理大量请求的能力。在当今互联网时代，从电商秒杀、社交媒体热点事件到金融交易系统，高并发场景无处不在。设计一个能够稳定支撑高并发流量的系统，是每一位后端工程师必须掌握的核心技能。

### 1.1 高并发系统的三大目标

高并发系统设计的核心目标可以归纳为三个关键维度：高性能（High Performance）、高可用（High Availability）和高可扩展（High Scalability），通常称为"三高"。

**高性能（High Performance）**

高性能体现在两个核心指标上：低延迟（Low Latency）和高吞吐（High Throughput）。延迟是指系统处理一个请求所花费的时间，通常以毫秒（ms）为单位。吞吐量是指单位时间内系统能够处理的请求数量，通常用QPS（Queries Per Second）或TPS（Transactions Per Second）来衡量。在互联网场景下，用户期望的页面加载时间通常在200ms以内，而金融交易场景的要求更为严苛，往往要求在几十毫秒内完成。

**高可用（High Availability）**

高可用是指系统在面对各种故障时仍能持续提供服务的能力。可用性通常用"几个9"来衡量：

| 可用性 | 年宕机时间 | 描述 |
|--------|-----------|------|
| 99%（两个9） | 87.6小时 | 基本可用，会有明显的不可用时段 |
| 99.9%（三个9） | 8.76小时 | 较高可用，多数业务可接受 |
| 99.99%（四个9） | 52.56分钟 | 高可用，关键业务系统要求 |
| 99.999%（五个9） | 5.26分钟 | 极高可用，电信级系统要求 |

达成四个9的可用性意味着全年宕机时间不能超过53分钟，这需要系统具备完善的故障检测、自动切换和容错机制。

**高可扩展（High Scalability）**

可扩展性是指系统通过增加资源（硬件）来提升处理能力的能力。理想的系统应该具备**水平扩展**能力——即通过增加更多的服务器节点来线性提升系统处理能力，而不需要修改代码架构。水平扩展与垂直扩展（升级单机硬件）相比，成本更低、灵活性更高，是现代分布式系统的主流选择。

### 1.2 三大核心思想

高并发系统设计并非无章可循，其背后的核心思想可以概括为六个字：**缓存、异步、拆分**。

**缓存（空间换时间）**

缓存是最常见也是最高效的性能优化手段。其核心思想是用存储空间来换取处理速度——将计算结果或数据副本存储在更快的存储介质中，以便后续请求能够快速获取。从CPU的多级缓存到浏览器的HTTP缓存，从Redis到CDN，缓存贯穿了整个计算机系统的每一层。据统计，引入合适的缓存策略可以将系统响应时间降低一个数量级甚至更多。

**异步（削峰填谷）**

异步处理的核心在于将同步阻塞的操作转化为非阻塞操作，从而提高系统的吞吐能力和响应速度。异步最典型的场景是"削峰填谷"——在流量高峰时期，将请求先放入消息队列暂存，后端服务按照自身处理能力从队列中消费请求，从而平滑流量波峰，保护下游系统不被冲垮。

**拆分（分而治之）**

拆分是解决复杂系统问题的通用方法论。在高并发场景下，拆分体现在多个层面：业务拆分（微服务化）、数据拆分（分库分表）、功能拆分（读写分离）。通过将大系统拆解为多个小系统，每个小系统独立部署、独立扩缩容，可以大幅降低系统复杂度，提升整体可用性和可维护性。

### 1.3 关键性能指标

设计高并发系统之前，必须先建立量化指标来衡量和监控系统性能。

**QPS（Queries Per Second）**：每秒查询数，衡量系统处理读请求的能力。在Web系统中，一次页面加载可能产生多个QPS（包含CSS、JS、图片等静态资源的请求）。

**TPS（Transactions Per Second）**：每秒事务数，衡量系统处理完整事务的能力。一个事务通常包含多个操作步骤，例如下单事务包含扣库存、生成订单、扣减余额等多个子操作。

**RT（Response Time）**：响应时间，指从客户端发起请求到收到完整响应所经过的时间。RT通常关注平均值、P99（99%请求的响应时间）、P999（99.9%请求的响应时间）等分位值。P99比平均值更能反映系统的真实体验，因为平均值容易被少数极快请求拉低。

**并发用户数**：系统同时承载的活跃用户数量。需要注意，高并发用户数不一定意味着高QPS——如果用户操作间隔较长，即使同时在线用户数很高，系统压力也可能不大。

**水位线**：系统资源使用率的安全警戒线。通常建议CPU使用率控制在70%以下（预留30%应对突发流量），内存使用率控制在80%以下，磁盘IO和网络带宽使用率控制在70%以下。超过这些水位线，系统响应时间会急剧上升，进入"过载"状态。

## 二、负载均衡

负载均衡是高并发系统的入口层，也是第一道防线。它的核心任务是将用户请求分发到多台后端服务器上，避免单点过载，同时提供高可用保障。

### 2.1 负载均衡的分层架构

负载均衡可以在网络协议的不同层次实现，从DNS层到应用层，每一层都有各自的特点和适用场景。

#### DNS层负载均衡

DNS负载均衡是最简单也最基础的负载均衡方式。其原理是：在DNS服务器中，将一个域名解析为多个IP地址，DNS服务器根据策略返回其中一个IP给客户端。

**优点**：
- 实现简单，无需额外硬件或软件
- 成本低，直接利用DNS基础设施
- 可以将流量分发到不同地理位置的机房（基于地理位置的DNS解析）

**缺点**：
- DNS缓存导致生效延迟——修改DNS记录后，由于各级DNS缓存，需要数小时甚至更长时间才能完全生效
- 无法感知后端服务器的健康状态——即使某个IP对应的服务器已经宕机，DNS仍可能将流量分发过去
- 控制粒度粗糙——只能基于IP轮询或地理位置分配，无法做精细化的流量控制

DNS负载均衡通常作为全局负载均衡的第一层，与其他负载均衡方式配合使用。

#### 硬件负载均衡（F5）

F5 BIG-IP是业界最知名的硬件负载均衡设备。它作为专用硬件设备部署在网络入口处，具有强大的处理能力和丰富的功能。

**优点**：
- 性能强大：单台设备可以处理数百万并发连接
- 功能丰富：支持四层到七层的全面负载均衡，内置SSL卸载、会话保持、健康检查等功能
- 稳定性高：专用硬件和操作系统，经过严格测试

**缺点**：
- 成本高昂：一台F5设备动辄数十万甚至上百万人民币
- 扩展性受限：硬件设备的处理能力有上限，超过上限需要更换更高级的设备
- 灵活性不足：配置变更需要专业技术人员操作，无法像软件方案那样快速迭代

硬件负载均衡适合银行、证券等对性能和稳定性要求极高且预算充足的大型企业。

#### 软件负载均衡（Nginx / LVS / HAProxy）

软件负载均衡是当前互联网企业的主流选择，以其低成本、高灵活性和丰富的功能生态受到广泛青睐。

**Nginx**：基于七层（应用层）的负载均衡，支持HTTP/HTTPS协议。Nginx以其卓越的并发处理能力（单机可支撑数万并发连接）、强大的反向代理功能和灵活的配置而闻名。它不仅可以做负载均衡，还集成了限流、缓存、SSL终止、动静分离等功能。

**LVS（Linux Virtual Server）**：基于四层（传输层）的负载均衡，工作在内核空间。LVS的转发性能极高，通常作为大型系统的入口层，将流量分发到后端的Nginx集群。LVS支持三种工作模式：NAT模式（网络地址转换）、DR模式（直接路由，性能最高）、TUN模式（IP隧道）。

**HAProxy**：同时支持四层和七层的负载均衡软件，以高性能和丰富的负载均衡算法著称。HAProxy在TCP/HTTP代理场景下表现优异，常用于MySQL、Redis等数据库层的负载均衡。

这三者经常组合使用形成经典的"LVS四层入口 + Nginx七层代理"架构，既能享受LVS高性能的四层转发能力，又能利用Nginx丰富的七层路由和过滤功能。

### 2.2 负载均衡算法

负载均衡算法决定了请求如何分配给后端服务器，不同的算法适用于不同的场景。

**轮询（Round Robin）**

轮询是最简单的算法，按照请求顺序依次将请求分发到各台服务器。假设有三台服务器A、B、C，第一个请求给A，第二个给B，第三个给C，第四个又给A，以此类推。

**适用场景**：所有服务器配置相同、处理能力相等的场景。

**优点**：实现简单，无状态，请求平均分配。

**缺点**：不考虑服务器的实际负载情况，如果某台服务器性能较差或当前负载较高，仍会被分配同等数量的请求。

**加权轮询（Weighted Round Robin）**

加权轮询是轮询算法的增强版——给每台服务器设置一个权重（Weight），权重越高分配的请求越多。例如服务器A权重为5，服务器B权重为3，服务器C权重为2，则在10个请求中，A会分到5个，B分到3个，C分到2个。

**适用场景**：服务器配置不均衡的场景（例如新老机器混用），或者需要将更多流量引导到某台特定服务器时。

**Nginx加权轮询配置示例**：

```nginx
upstream backend {
    server 192.168.1.1 weight=5;
    server 192.168.1.2 weight=3;
    server 192.168.1.3 weight=2;
}
```

**最少连接（Least Connections）**

最少连接算法将请求分发给当前活跃连接数最少的服务器。与轮询不同，最少连接算法动态感知服务器的实时负载。

**适用场景**：请求处理时间差异较大的场景（例如某些请求是简单的静态页面响应，某些请求是耗时的计算任务）。

**Nginx最少连接配置**：

```nginx
upstream backend {
    least_conn;
    server 192.168.1.1;
    server 192.168.1.2;
}
```

**源地址哈希（IP Hash）**

源地址哈希算法根据客户端的IP地址计算哈希值，然后根据哈希值将请求映射到某台服务器。同一个IP的请求始终会被发往同一台服务器。

**适用场景**：需要会话保持的场景（Session Sticky），即某个用户的请求必须由同一台服务器处理。但需要注意，IP Hash在客户端使用代理或NAT时可能失效（多个用户共享同一个出口IP）。

**Nginx IP Hash配置**：

```nginx
upstream backend {
    ip_hash;
    server 192.168.1.1;
    server 192.168.1.2;
}
```

**一致性哈希（Consistent Hashing）**

一致性哈希算法将服务器节点映射到一个虚拟的哈希环上，请求的哈希值在环上顺时针查找最近的服务器节点。

**核心优势**：当增加或减少服务器节点时，只有哈希环上相邻节点的映射关系发生变化，大部分请求的映射关系保持不变。这大幅降低了节点变动对缓存和会话数据的影响。

**适用场景**：分布式缓存（如Redis集群）、分布式数据库的分片路由。

**与普通哈希的区别**：
- 普通哈希取模：`serverIndex = hash(key) % N`，当N变化时（节点增减），几乎所有key的映射关系都会改变
- 一致性哈希：节点增减只会影响哈希环上相邻节点的少量key

### 2.3 Nginx实战配置

Nginx是Java后端开发中最常用的反向代理和负载均衡工具，以下是几个关键的生产级配置场景。

**反向代理与负载均衡**：

```nginx
upstream backend_cluster {
    # 加权轮询
    server 10.0.0.1:8080 weight=5 max_fails=3 fail_timeout=30s;
    server 10.0.0.2:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.0.3:8080 backup;  # 备用服务器
}

server {
    listen 80;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://backend_cluster;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # 超时配置
        proxy_connect_timeout 5s;
        proxy_read_timeout 10s;
        proxy_send_timeout 10s;
    }
}
```

**限流配置**：

```nginx
# 定义限流区域：每个IP最大速率10r/s，突发20个请求
limit_req_zone $binary_remote_addr zone=mylimit:10m rate=10r/s;

server {
    location /api/ {
        limit_req zone=mylimit burst=20 nodelay;
        proxy_pass http://backend_cluster;
    }
}
```

其中 `rate=10r/s` 表示每秒最多处理10个请求，`burst=20` 表示允许瞬间超过速率限制的请求数量（最多20个排队等待），`nodelay` 表示在burst范围内的请求不延迟处理。

**动静分离**：

将静态资源（JS、CSS、图片等）和动态请求分离处理，静态资源由Nginx直接返回（或从CDN加载），动态请求转发到后端应用服务器：

```nginx
server {
    listen 80;
    server_name www.example.com;

    # 静态资源直接由Nginx处理
    location ~* \.(jpg|jpeg|png|gif|ico|css|js|woff|woff2|ttf|svg)$ {
        root /var/www/static;
        expires 30d;  # 浏览器缓存30天
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # 动态请求转发到后端
    location / {
        proxy_pass http://backend_cluster;
    }
}
```

### 2.4 客户端负载均衡

传统的负载均衡器（如Nginx）是服务端负载均衡——由负载均衡器统一分发请求。但在微服务架构中，还有一种客户端负载均衡方式，典型代表是Spring Cloud中的Ribbon和Spring Cloud LoadBalancer。

**工作原理**：

1. 服务提供者启动时，将自己的IP地址和端口注册到注册中心（如Nacos、Eureka、Consul）
2. 服务消费者从注册中心获取目标服务的完整实例列表
3. 消费者使用负载均衡算法（如轮询、加权）从列表中选择一个实例发起调用

**与服务端负载均衡的区别**：

| 特性 | 服务端负载均衡 | 客户端负载均衡 |
|------|---------------|---------------|
| 部署位置 | 独立部署的中间件（Nginx/LVS） | 嵌入在服务消费者进程中 |
| 服务发现 | 手动配置或通过DNS | 自动从注册中心获取 |
| 网络跳数 | 多一次网络跳转 | 直连服务提供者 |
| 故障处理 | 负载均衡器自动剔除故障节点 | 客户端感知并切换 |
| 代表产品 | Nginx, F5, LVS | Ribbon, Spring Cloud LoadBalancer |

**Spring Cloud LoadBalancer配置示例**：

```yaml
spring:
  cloud:
    loadbalancer:
      # 开启重试
      retry:
        enabled: true
      # 负载均衡策略
      ribbon:
        NFLoadBalancerRuleClassName: com.netflix.loadbalancer.WeightedResponseTimeRule
```

## 三、缓存策略

缓存是提升系统性能最立竿见影的手段。一个精心设计的缓存体系可以让系统响应时间从几十毫秒降低到几微秒。

### 3.1 多级缓存体系

现代高并发系统的缓存是分层的，从客户端到数据库之间有多层缓存，每一层的访问速度和命中率各有不同。

**浏览器缓存**：浏览器会将静态资源（JS、CSS、图片）缓存到本地。通过HTTP响应头 `Cache-Control` 和 `Expires` 控制缓存策略。浏览器缓存的优势是零网络开销，速度最快。

**CDN缓存**：内容分发网络（Content Delivery Network）将静态资源部署到全球各地的边缘节点，用户可以从最近的节点获取资源。主流CDN服务商包括阿里云CDN、腾讯云CDN、Cloudflare等。

**Nginx本地缓存**：Nginx可以将后端返回的响应缓存到本地磁盘，后续相同的请求直接返回缓存结果，避免穿透到后端应用服务器。使用 `proxy_cache` 指令配置。

**分布式缓存（Redis）**：Redis是当前最主流的分布式缓存中间件，支持丰富的数据结构（String、Hash、List、Set、Sorted Set、HyperLogLog、BitMap等），提供毫秒级的数据访问速度。Redis常用于缓存热点数据、会话数据、计数器等。

**本地缓存（Caffeine）**：Caffeine是Java领域性能最高的本地缓存库（微秒级访问速度），使用Window-TinyLFU淘汰算法，在命中率和内存效率上优于Guava Cache。本地缓存的优势是速度快（无网络开销），缺点是容量有限（受限于JVM堆内存），且多节点之间数据不一致。

**多层缓存的访问流程**：

```
用户请求
    ↓
浏览器缓存 → 有则直接返回（浏览器级别，零网络成本）
    ↓ (未命中)
CDN → 有则直接返回（边缘节点，就近访问）
    ↓ (未命中)
Nginx本地缓存 → 有则直接返回（Nginx级别，避免请求到应用服务器）
    ↓ (未命中)
本地缓存Caffeine → 有则直接返回（微秒级）
    ↓ (未命中)
分布式缓存Redis → 有则返回并回填本地缓存（毫秒级）
    ↓ (未命中)
数据库 → 读取并逐级回填缓存
```

### 3.2 缓存更新策略

读多写少的场景最适合使用缓存，但缓存和数据库之间的数据一致性是必须面对的难题。以下是几种主流的缓存更新策略。

**Cache Aside 模式（旁路缓存）**

这是最常用的缓存更新模式，核心逻辑是：

- **读操作**：先读缓存，命中则直接返回；未命中则读数据库，将结果写入缓存，再返回
- **写操作**：先更新数据库，再删除缓存（而不是更新缓存）

为什么是"先更新DB后删缓存"而不是"先删缓存后更新DB"？因为前者在并发场景下出现数据不一致的概率更低。考虑以下场景：

如果采用"先删缓存后更新DB"：
1. 线程A删除缓存
2. 线程B读请求，发现缓存为空，读取数据库得到旧值，将旧值写入缓存
3. 线程A更新数据库为新值
4. 结果：缓存中一直是旧值，数据永久不一致

而"先更新DB后删缓存"：
1. 线程A更新数据库
2. 线程B读请求，命中缓存（旧值）直接返回（短暂的不一致）
3. 线程A删除缓存
4. 后续请求读DB并将新值写入缓存

"先更新DB后删缓存"仍然存在短暂的不一致窗口，但概率极低（只有在缓存刚好在更新DB和删除缓存之间失效时才会出现），且可以通过设置缓存过期时间来保证最终一致性。

```java
public class CacheAsideService {
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private JdbcTemplate jdbcTemplate;

    public Object getData(String key) {
        // 先读缓存
        Object value = redisTemplate.opsForValue().get(key);
        if (value != null) {
            return value;
        }
        // 缓存未命中，读数据库
        value = jdbcTemplate.queryForObject("SELECT data FROM table WHERE key=?", Object.class, key);
        if (value != null) {
            // 写入缓存，设置过期时间
            redisTemplate.opsForValue().set(key, value, 30, TimeUnit.MINUTES);
        }
        return value;
    }

    public void updateData(String key, Object newValue) {
        // 先更新数据库
        jdbcTemplate.update("UPDATE table SET data=? WHERE key=?", newValue, key);
        // 后删除缓存
        redisTemplate.delete(key);
    }
}
```

**Read/Write Through 模式（读写穿透）**

缓存层作为数据读写的主要入口，应用程序只与缓存层交互，由缓存层负责与数据库同步数据。这种模式对应用层屏蔽了数据库的细节，但实现复杂度较高。

**Write Behind 模式（异步写入/写回）**

应用程序只更新缓存，不直接更新数据库。缓存会异步地将一批写操作批量提交到数据库。这种模式写入性能最高（因为写操作先落缓存，立即返回），但存在数据丢失的风险（如果缓存宕机，未持久化的数据会丢失）。适合写频率高但对一致性要求较低的场景（如记录访问日志、点赞计数等）。

### 3.3 热点数据处理

热点数据是指被大量请求同时访问的少量数据（例如电商秒杀的商品详情、微博热搜事件）。热点数据如果没有特殊处理，可能会导致缓存层瞬间被击穿，甚至压垮数据库。

**热点数据识别**：可以通过实时监控QPS、访问频次来识别热点。Redis 4.0提供了 `hotkeys` 命令，可以扫描出热键。

**热点数据处理策略**：

1. **提前预热**：对于可预知的热点（如秒杀商品、大促活动），在活动开始前将数据预先加载到缓存中，避免瞬间涌入的请求穿透到数据库。

2. **本地缓存兜底**：在Redis之上再加一层Caffeine本地缓存。即使Redis出现瓶颈，本地缓存仍然能以微秒级速度响应。即使本地缓存未命中，也能分散对Redis的压力。

3. **多副本分摊**：对于单个热点key，在Redis集群中创建多个副本（如 `hotkey_1`、`hotkey_2`、`hotkey_3`），将请求分散到不同的Redis节点。

4. **限流保护**：在缓存层之前加限流，超出阈值的请求直接返回兜底数据。

## 四、读写分离与分库分表

随着业务的发展和数据的增长，单一的数据库实例逐渐成为瓶颈。读写分离解决"读压力大"的问题，分库分表解决"数据量大"和"写入压力大"的问题。

### 4.1 读写分离

读写分离的基本架构是一主多从——主机（Master）处理写操作（INSERT、UPDATE、DELETE），从机（Slave）处理读操作（SELECT）。主库将变更通过binlog同步到从库。

**配置示例（MySQL主从复制）**：

```sql
-- 在主库上创建复制账号
CREATE USER 'repl'@'%' IDENTIFIED BY 'password';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

-- 在从库上配置主库信息
CHANGE MASTER TO
    MASTER_HOST='master_host',
    MASTER_PORT=3306,
    MASTER_USER='repl',
    MASTER_PASSWORD='password',
    MASTER_LOG_FILE='mysql-bin.000001',
    MASTER_LOG_POS=0;
START SLAVE;
```

**主从延迟问题**：主从复制本质上是异步的，从库的数据总会比主库落后一段时间（通常几毫秒到几秒不等）。在读写分离架构下，可能出现"刚写入的数据读不到"的问题。

**解决方案**：
- **强制读主**：对数据一致性要求高的业务（如支付结果、订单状态），配置强制从主库读取
- **延迟读**：写入后一定时间内（如1秒）的读请求也走主库
- **缓存标记**：写入时将key写入Redis缓存，读请求先检查缓存，如果key存在则读主库

**ShardingSphere-JDBC读写分离配置**：

```yaml
spring:
  shardingsphere:
    datasource:
      names: master,slave0,slave1
      master:
        url: jdbc:mysql://master_host:3306/db
        username: root
        password:
      slave0:
        url: jdbc:mysql://slave0_host:3306/db
        username: root
        password:
      slave1:
        url: jdbc:mysql://slave1_host:3306/db
        username: root
        password:
    rules:
      readwrite-splitting:
        data-sources:
          primary_ds:
            write-data-source-name: master
            read-data-source-names: slave0,slave1
            load-balancer-name: round_robin
        load-balancers:
          round_robin:
            type: ROUND_ROBIN
```

### 4.2 垂直分库

垂直分库是按照业务模块将数据库拆分为多个独立的数据库，每个数据库对应一个业务域。

**拆分示例**：
- 用户库（user_db）：存放用户信息、登录记录
- 订单库（order_db）：存放订单数据、订单详情
- 商品库（product_db）：存放商品信息、库存数据
- 支付库（payment_db）：存放支付流水、账单数据

**优势**：
- 业务解耦：每个团队可以独立维护自己的数据库
- 独立扩容：用户库压力大时可以单独为用户库增加资源
- 故障隔离：一个数据库宕机不会影响其他业务

**挑战**：
- 跨库查询困难：无法跨库JOIN查询，需要应用层组装数据
- 分布式事务：跨库操作需要引入分布式事务方案（如Seata、RocketMQ事务消息）
- 数据一致性：不同业务域之间的数据同步需要额外的机制

### 4.3 水平分表

水平分表（Sharding）是将同一张表中的数据按照某种规则拆分到多个物理表中。通常当单表数据量超过500万行或表容量超过10GB时，就需要考虑水平分表。

**分片键选择**：分片键的选择是分表的灵魂。理想的分片键应该满足以下条件：
- 大部分查询都携带该字段（这样才能将查询路由到正确的分片）
- 分布均匀，避免数据倾斜（不能出现某些分片数据量特别大）
- 不可变或极少变化（分片键变更意味着数据迁移）

常见的分片键：用户ID（适合用户维度的查询）、订单ID（适合订单维度的查询）、时间字段（适合按时间范围查询）。

**分片算法**：

**取模分片**：`tableIndex = shardingKey % tableCount`

```
用户ID=1001 → 1001 % 4 = 1 → 分到user_1表
用户ID=1002 → 1002 % 4 = 2 → 分到user_2表
用户ID=1003 → 1003 % 4 = 3 → 分到user_3表
用户ID=1004 → 1004 % 4 = 0 → 分到user_0表
```

优点：实现简单，数据分布均匀。
缺点：扩容时几乎全部数据需要迁移（例如从4张表扩展到5张表，取模基数变化导致几乎所有数据都需要重新分片）。

**范围分片**：按照某个字段的范围将数据分配到不同的分片。

```
user_0：用户ID 1~1000000
user_1：用户ID 1000001~2000000
user_2：用户ID 2000001~3000000
```

优点：扩容方便（直接增加新的范围分片即可），无需迁移历史数据。
缺点：容易出现热点问题（新注册用户集中在ID较大的分片上）。

**一致性哈希分片**：如前文所述，在哈希环上进行路由。

优点：扩容时影响范围小（只影响相邻节点）。
缺点：实现相对复杂，需要处理虚拟节点问题。

**雪花算法（Snowflake）分布式ID**：

水平分表后，数据库自增ID不再适用（多个分片可能生成重复ID），需要全局唯一的分布式ID。

雪花算法生成的ID是一个64位的Long型整数，结构如下：

```
0 - 0000000000 0000000000 0000000000 0000000000 0 - 00000 - 00000 - 000000000000
|   \--- 时间戳（41位，精确到毫秒，可用69年） ---/ |   |   |   |   |
|                          |                       |   |   |   |   |
|                  1位符号位（始终为0）               |   |   |   |   |
|                                                    |   |   |   |   |
1位符号位（固定0）               数据中心ID（5位）  |   |   |   |   |
                                                         |   |   |   |
                                                   机器ID（5位） |   |   |
                                                                 |   |   |
                                                          序列号（12位，同一毫秒内自增）
```

```java
public class SnowflakeIdGenerator {
    private final long datacenterId;
    private final long machineId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨异常");
        }
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & 0xFFF; // 12位序列号
            if (sequence == 0) {
                timestamp = waitUntilNextMillis(timestamp);
            }
        } else {
            sequence = 0L;
        }
        lastTimestamp = timestamp;
        return ((timestamp - 1288834974657L) << 22)
             | (datacenterId << 17)
             | (machineId << 12)
             | sequence;
    }
}
```

### 4.4 ShardingSphere-JDBC实战

Apache ShardingSphere是目前Java生态中最成熟的分库分表中间件。ShardingSphere-JDBC以JAR包形式嵌入应用，作为JDBC驱动的增强层，对应用代码侵入性极小。

**核心配置（YAML）**：

```yaml
spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
      ds0:
        url: jdbc:mysql://localhost:3306/db0
        username: root
        password:
      ds1:
        url: jdbc:mysql://localhost:3306/db1
        username: root
        password:
    rules:
      sharding:
        tables:
          t_order:
            # 实际表分布
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..3}
            # 分库策略
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: db_inline
            # 分表策略
            table-strategy:
              standard:
                sharding-column: order_id
                sharding-algorithm-name: table_inline
        sharding-algorithms:
          db_inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{user_id % 2}
          table_inline:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 4}
        # 分布式主键
        key-generators:
          snowflake:
            type: SNOWFLAKE
            props:
              worker-id: 1
```

**绑定表配置**：

关联查询是分库分表后的一大难题。如果 `t_order` 和 `t_order_item` 都按照 `order_id` 分片，两者可以配置为绑定表，ShardingSphere会将它们的路由保持一致，避免跨库JOIN：

```yaml
rules:
  sharding:
    binding-tables:
      - t_order,t_order_item
```

## 五、限流降级熔断

在没有流量控制的高并发系统中，流量暴雨瞬间到来时，系统往往会从"缓慢"迅速演变为"完全不可用"。限流、降级和熔断是保护系统不被流量冲垮的三种核心手段。

### 5.1 限流算法

**计数器算法（固定窗口）**

最简单的限流方式：在固定时间窗口（如1秒）内维护一个计数器，每次请求计数器加1，达到阈值后拒绝后续请求，到下一个时间窗口计数器重置。

```
时间窗口: 1秒
阈值: 100

请求到达时间: 0ms(计数=1), 10ms(计数=2), ..., 500ms(计数=100), 510ms(拒绝)
下一个窗口: 1000ms后重置计数
```

**问题**：存在"边界临界"问题——如果用户在第一个窗口最后100ms发了100个请求，在第二个窗口最初100ms又发了100个请求，实际上在200ms内系统承受了200个请求的冲击，远超阈值。

**滑动窗口算法**：将时间窗口划分为更小的格子，滑动窗口按时间粒度移动。滑动窗口越精细，限流越精确，但内存占用也越高。

**漏桶算法（Leaky Bucket）**

漏桶算法将请求看作水滴，桶有一个固定的出水速率。无论进水速率多大，出水速率始终恒定。当桶满时，新请求被丢弃。

```
请求 → [ 漏桶 ] → 恒定速率处理
         ↑
    桶已满则丢弃
```

**优点**：输出流量绝对平滑，不会对下游造成突发压力。
**缺点**：无法应对突发流量——即使下游有能力处理，漏桶也会强制限流。

**适用场景**：保护下游系统（如数据库），需要平滑流量的场景。

**令牌桶算法（Token Bucket）**

令牌桶以恒定速率向桶中放入令牌，请求到达时需要获取一个令牌才能被处理。与漏桶不同，令牌桶允许一定程度的突发——桶中积累的令牌可以被快速消耗。

```
令牌以固定速率放入桶中 → [ 令牌桶 ] ← 请求消耗令牌后通过
                            ↑
                     桶满则丢弃新令牌
```

**优点**：允许突发流量（只要桶中有足够的令牌），同时平均速率受控。
**缺点**：突发程度受桶大小限制，需要合理设置桶容量。

**Guava RateLimiter 实现**：

```java
// 创建令牌桶，每秒生成100个令牌
RateLimiter limiter = RateLimiter.create(100);

public void handleRequest() {
    // 获取令牌，阻塞直到获取成功（或超时）
    boolean acquired = limiter.tryAcquire(500, TimeUnit.MILLISECONDS);
    if (!acquired) {
        // 返回限流提示
        return "系统繁忙，请稍后再试";
    }
    // 处理业务逻辑
}
```

**Sentinel 实现**：

```java
@SentinelResource(value = "getOrder", blockHandler = "handleBlock")
public Order getOrder(Long orderId) {
    // 业务逻辑
    return orderService.getOrder(orderId);
}

public Order handleBlock(Long orderId, BlockException e) {
    // 限流后的兜底处理
    return new Order();
}
```

### 5.2 限流维度

限流不能"一刀切"，需要根据不同的维度制定不同的限流策略。

**接口维度**：对不同的API接口设置不同的限流阈值。例如，查询接口QPS限制为1000，下单接口QPS限制为100。

**IP维度**：限制单个IP的访问频率，防止恶意爬虫或攻击。通常单个IP的QPS限制为10~100。

**用户维度**：限制单个用户的访问频率。普通用户QPS限制为10，VIP用户QPS限制为100。

**全局限流 + 单机限流**：

在分布式系统中，限流需要在两个层面同时实施：
- **全局限流**：控制整个集群的总入口流量，通常使用Redis + Lua脚本实现（原子操作）
- **单机限流**：每台机器独立限流，作为全局限流的补充，防止全局限流失效时单机被打垮

**Sentinel集群限流配置**：

```yaml
flow:
  - resource: "getOrder"
    clusterMode: true  # 开启集群限流
    count: 1000         # 集群总QPS
    grade: 1            # 1=QPS, 0=线程数
    controlBehavior: 0  # 0=快速失败, 1=Warm Up, 2=排队等待
```

### 5.3 降级

降级是指系统在压力过大时，主动牺牲非核心功能，保证核心功能的可用性。降级是"有损服务"思想的体现。

**降级策略**：
- **非核心功能关闭**：大促期间关闭"商品推荐"、"历史浏览"等非核心功能
- **返回兜底数据**：当推荐系统不可用时，返回默认的热门商品列表
- **返回静态页面**：动态页面降级为静态缓存页面
- **简化业务流程**：完整的支付流程降级为"先下单，后支付"（延迟扣款）

**降级方式**：
- **手动降级**：运维人员通过配置中心（如Nacos、Apollo）手动触发降级开关
- **自动降级**：系统根据监控指标（如RT超过阈值、错误率达到阈值）自动触发降级

### 5.4 熔断

熔断机制借鉴了电路断路器的概念。当系统检测到某个依赖服务的错误率达到阈值时，断路器打开，后续请求直接返回错误（快速失败），不再调用下游服务，给下游服务恢复的时间。

**断路器三态模型**：

```
Closed（关闭）
    └── 错误率达到阈值 → Open（打开）
Open（打开）
    └── 超时时间到达 → Half-Open（半开）
Half-Open（半开）
    ├── 探测请求成功 → Closed（关闭）
    └── 探测请求失败 → Open（打开）
```

**Sentinel熔断配置**：

```yaml
degrade:
  - resource: "paymentService"
    grade: 0           # 0=RT, 1=异常比例, 2=异常数
    count: 200          # RT超过200ms
    timeWindow: 10      # 熔断时长（秒）
    minRequestAmount: 5 # 触发熔断的最小请求数
    statIntervalMs: 1000 # 统计窗口
```

**Resilience4j熔断配置**：

```java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)           // 失败率阈值 50%
    .waitDurationInOpenState(Duration.ofSeconds(10))  // 熔断持续时间
    .slidingWindowSize(100)             // 滑动窗口大小
    .minimumNumberOfCalls(10)           // 最小调用数
    .build();

CircuitBreaker breaker = CircuitBreaker.of("paymentService", config);
// 通过断路器执行方法
Supplier<Result> supplier = CircuitBreaker.decorateSupplier(breaker, () -> paymentService.call());
```

## 六、异步与消息队列

同步调用在微服务架构中会形成调用链的串行依赖——一个请求需要依次等待多个服务返回结果，响应时间等于所有服务响应时间之和。异步化是打破这种串行依赖、提升系统吞吐量的关键手段。

### 6.1 异步典型场景

**短信/邮件通知**：用户注册后发送欢迎短信和邮件。这个过程不应该阻塞用户注册的响应，应异步处理。

**日志收集**：应用日志通过MQ发送到日志中心（如ELK），避免日志写入影响业务逻辑的性能。

**数据同步**：订单系统产生订单后，通过MQ通知库存系统扣减库存、通知财务系统生成账单。

**事件驱动**：用户下单后触发一系列事件（发送短信、更新积分、推送消息），这些事件通过MQ异步执行。

### 6.2 削峰填谷

消息队列最核心的价值在于"削峰填谷"——将突发的流量高峰削平，让后端系统以稳定的速率处理请求。

**秒杀场景**：

```
秒杀开始瞬间：100万用户同时请求
    ↓
Nginx网关（限流：只放行10万请求）
    ↓
MQ队列（10万请求排队，每秒消费1000单）
    ↓
订单服务（按自身处理能力稳定处理）
```

通过MQ缓冲，后端订单服务不会感受到"流量洪峰"，始终以恒定的速率处理订单。用户端则显示"排队中，请稍候"。

**RocketMQ事务消息**：

RocketMQ支持事务消息，可以解决分布式场景下的最终一致性问题。典型流程如下：

1. 生产者发送半消息（Half Message）到MQ
2. 生产者执行本地事务（如创建订单、扣减库存）
3. 生产者根据本地事务结果向MQ发送Commit或Rollback
4. 如果MQ长时间未收到Commit/Rollback，会回查生产者询问事务状态

```java
public class OrderService {
    @Autowired
    private TransactionMQProducer producer;

    public void createOrder(Order order) {
        // 发送事务消息
        Message msg = new Message("order-topic", JSON.toJSONBytes(order));
        TransactionSendResult result = producer.sendMessageInTransaction(msg, order);
        if (result.getLocalTransactionState() == LocalTransactionState.COMMIT_MESSAGE) {
            // 事务提交成功
        }
    }

    @Transactional
    public void executeLocalTransaction(Order order) {
        // 执行本地事务：扣减库存、生成订单
        orderMapper.insert(order);
        stockMapper.deduct(order.getProductId(), order.getQuantity());
    }
}
```

### 6.3 CompletableFuture 异步编排

Java 8引入的 `CompletableFuture` 是Java异步编程的核心工具，它支持异步任务的编排组合，非常适合微服务中多个远程调用的并行执行。

**多个远程调用并行执行**：

```java
public OrderDetail getOrderDetail(Long orderId) {
    CompletableFuture<Order> orderFuture = CompletableFuture
        .supplyAsync(() -> orderService.getOrder(orderId), executor);

    CompletableFuture<List<OrderItem>> itemsFuture = CompletableFuture
        .supplyAsync(() -> orderItemService.getItems(orderId), executor);

    CompletableFuture<User> userFuture = orderFuture
        .thenCompose(order -> CompletableFuture
            .supplyAsync(() -> userService.getUser(order.getUserId()), executor));

    CompletableFuture<List<Payment>> paymentFuture = CompletableFuture
        .supplyAsync(() -> paymentService.getPayments(orderId), executor);

    // 等待所有任务完成并组装结果
    return CompletableFuture
        .allOf(orderFuture, itemsFuture, userFuture, paymentFuture)
        .thenApply(v -> {
            OrderDetail detail = new OrderDetail();
            detail.setOrder(orderFuture.join());
            detail.setItems(itemsFuture.join());
            detail.setUser(userFuture.join());
            detail.setPayments(paymentFuture.join());
            return detail;
        })
        .orTimeout(3000, TimeUnit.MILLISECONDS)  // 超时控制
        .exceptionally(e -> {
            log.error("获取订单详情失败", e);
            return getDefaultOrderDetail();  // 异常时的兜底数据
        })
        .join();
}
```

上述代码中，订单信息、订单项、用户信息、支付信息的查询被并行执行，总响应时间等于最慢的那个调用耗时，而不是串行执行时四个调用耗时的总和。

### 6.4 异步中的注意事项

**线程池隔离**：不同业务使用不同的线程池，避免一个业务的异步任务阻塞另一个业务。可以使用 `ThreadPoolExecutor` 配合 `ThreadPoolTaskExecutor` 进行管理。

**上下文传递**：异步调用中需要传递TraceID、用户认证信息等上下文数据，可以使用 `ThreadLocal` + 任务装饰器（`TaskDecorator`）实现。

**异常处理**：异步任务的异常需要在回调中妥善处理，避免异常被吞没导致问题难以排查。

## 七、数据库性能优化

在高并发系统中，数据库往往是最容易成为瓶颈的环节。合理优化数据库性能可以在不增加硬件成本的前提下显著提升系统吞吐量。

### 7.1 SQL优化

**避免 `SELECT *`**：只查询需要的字段，减少网络传输和内存占用。

```sql
-- 不推荐
SELECT * FROM order WHERE user_id = 1001;

-- 推荐
SELECT id, order_no, amount, status FROM order WHERE user_id = 1001;
```

**避免索引失效**：索引是数据库性能的基石。常见的索引失效场景包括：
- 对索引列进行函数操作：`WHERE DATE(create_time) = '2024-01-01'`（应改为范围查询）
- 类型隐式转换：`WHERE user_id = '1001'`（user_id是int类型，字符串比较会导致索引失效）
- 使用 `LIKE '%keyword'` 前缀模糊查询
- OR条件中只要有一个条件没有索引，整个查询索引失效

**大分页优化**：传统大分页 `LIMIT 1000000, 20` 会扫描1000020条记录然后丢弃前1000000条，性能极差。

```sql
-- 传统方式（性能差）
SELECT * FROM order ORDER BY id LIMIT 1000000, 20;

-- 优化方式一：子查询（利用覆盖索引）
SELECT * FROM order
WHERE id >= (SELECT id FROM order ORDER BY id LIMIT 1000000, 1)
LIMIT 20;

-- 优化方式二：游标分页（需要前端传入上一页最后一个ID）
SELECT * FROM order WHERE id > :lastId ORDER BY id LIMIT 20;
```

**批量操作**：避免在循环中逐条执行SQL，使用批量操作大幅减少数据库交互次数。

```java
// 不推荐
for (Order order : orders) {
    orderMapper.insert(order); // 循环中逐条插入，N次数据库交互
}

// 推荐
orderMapper.batchInsert(orders); // 一次批量插入，1次数据库交互
```

### 7.2 连接池

数据库连接池是连接复用的核心组件，避免了每次数据库操作都创建和销毁连接的开销。

**HikariCP** 是Spring Boot 2.x及以上版本的默认连接池，以其极致的高性能著称。其核心优势包括：

1. **字节码精简**：HikariCP的JAR包仅有几百KB，代码量极少，减少了加载和执行的开销
2. **无锁并发**：使用 `ConcurrentBag` 替代传统的 `BlockingQueue`，减少了锁竞争
3. **FastList**：自定义的 `List` 实现替代 `ArrayList`，移除了 `ArrayList` 中不必要的边界检查
4. **高效的连接校验**：使用 `jdbc4.isValid()` 代替传统的 `SELECT 1` 校验，避免网络开销

**连接池配置**：

```yaml
spring:
  datasource:
    hikari:
      # 核心配置
      minimum-idle: 10           # 最小空闲连接数
      maximum-pool-size: 50      # 最大连接数
      idle-timeout: 600000       # 空闲超时（毫秒）
      max-lifetime: 1800000      # 连接最大存活时间（毫秒）
      connection-timeout: 30000  # 获取连接超时时间（毫秒）
      # 性能优化
      pool-name: HikariOrderPool
      connection-test-query: SELECT 1
      validation-timeout: 5000
```

连接池大小的设置原则：对于CPU密集型的应用（业务逻辑复杂、计算量大），连接池不宜过大（通常10~20个即可），过多的连接会导致CPU上下文切换开销增加。对于IO密集型应用（简单查询、高延迟场景），连接池可以设置得更大一些。

### 7.3 批处理与FetchSize

在Hibernate/JPA和MyBatis中，可以通过批处理和FetchSize优化来减少数据库交互次数。

**Hibernate @BatchSize**：

```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    @BatchSize(size = 20)  // 批量加载：一次加载20个order的items
    private List<OrderItem> items;
}
```

**JDBC Batch**：

```java
// 启用批处理
connection.setAutoCommit(false);
PreparedStatement ps = connection.prepareStatement(
    "INSERT INTO order (user_id, amount) VALUES (?, ?)");

for (Order order : orders) {
    ps.setLong(1, order.getUserId());
    ps.setBigDecimal(2, order.getAmount());
    ps.addBatch();        // 添加到批处理
}
ps.executeBatch();        // 一次批量执行
connection.commit();
```

## 八、高可用架构

高可用是系统设计的生命线。没有任何系统能够保证永不宕机，但通过合理的架构设计，可以将宕机的影响降到最低。

### 8.1 部署架构模式

**同城双活**：在同一个城市部署两个数据中心，两个中心同时承载业务流量。当一个数据中心故障时，另一个数据中心接管全部流量。

**两地三中心**：在同城双活的基础上，在异地再部署一个灾备中心。同城双活中心处理日常流量，异地灾备中心作为"数据备份"，仅在极端灾难（如地震导致同城双活同时不可用）时启用。

**多活架构**：在多个地理位置（通常三个以上）部署数据中心，所有数据中心同时承载流量，任意一个数据中心故障不影响整体服务。

```
用户 → 全局负载均衡（DNS/GSLB）
    ├── 数据中心A（北京主中心）
    ├── 数据中心B（北京灾备中心）
    └── 数据中心C（上海灾备中心，两地三中心场景）
```

### 8.2 故障转移

**Keepalived + VIP漂移**：

Keepalived通过VRRP协议实现虚拟IP（VIP）的漂移。正常情况下VIP绑定在主服务器上；当主服务器宕机时，Keepalived将VIP漂移到备服务器，应用通过VIP访问服务，对客户端完全透明。

```
正常状态：
  主服务器(192.168.1.10) ← 绑定VIP 192.168.1.100
  备服务器(192.168.1.11) ← 监控主服务器状态

主服务器宕机：
  主服务器(192.168.1.10) ✗ 宕机
  备服务器(192.168.1.11) ← 接管VIP 192.168.1.100（毫秒级切换）
```

**Redis哨兵模式**：

Redis Sentinel（哨兵）是Redis的高可用解决方案。哨兵集群监控Redis主节点的状态，当主节点宕机时，自动从从节点中选举一个提升为新的主节点。

```
Sentinel集群（3个哨兵节点，形成共识）
    │ 监控
    ├── Redis主节点（Master）
    ├── Redis从节点（Slave 1）
    └── Redis从节点（Slave 2）

当Master宕机：
    Sentinels选举 → Slave 1提升为新的Master
    应用端 → 通过Sentinel获取新的Master地址
```

### 8.3 混沌工程

混沌工程（Chaos Engineering）是一种通过主动注入故障来验证系统韧性的实践。Netflix的Chaos Monkey是最早的混沌工程工具，它会随机终止生产环境中的服务实例，验证系统是否能够自动恢复。

**混沌工程实验流程**：

1. 定义稳态：确定系统正常运行时的基准指标（如RT、错误率、吞吐量）
2. 假设系统在故障注入后仍能保持稳态
3. 注入故障：如杀死进程、网络延迟、磁盘故障、CPU过载
4. 验证假设：检查系统在故障下的表现是否符合预期

### 8.4 最终一致性方案

在分布式系统中，强一致性（强同步）往往意味着低性能和高延迟。大多数业务场景下，最终一致性是一个更务实的选择——允许数据短暂不一致，但保证最终一致。

**本地消息表**：

```
业务操作（如创建订单）
    ↓ (同一本地事务)
写入业务表 + 写入本地消息表（状态=待发送）
    ↓
定时任务扫描本地消息表，发送到MQ
    ↓ (发送成功)
更新本地消息表状态（状态=已发送）
    ↓ (发送失败)
定时任务重试，直到成功
```

**事务消息（RocketMQ）**：

RocketMQ事务消息从根本上解决了消息发送与本地事务的一致性问题：
- 半消息对消费者不可见
- 本地事务执行成功后再Commit消息，消费者才能看到
- 事务超时后MQ会回查生产者

**对账机制**：

对账是保证最终一致性的最后一道防线。通过对账系统定期比对不同系统的数据，发现不一致后自动或人工修复。

```
每日凌晨：
  订单系统账单 → 对账任务 → 支付系统流水
              ↓ 比对
        不一致的记录 → 自动修复 / 人工介入
```

## 九、总结与最佳实践

高并发系统设计没有银弹，每一个系统都需要根据自身的业务特点、技术栈和团队能力来选择合适的架构方案。以下是一份总结性的最佳实践清单：

### 设计原则

- **架构先行**：在写第一行代码之前，先确定系统的总体架构和核心设计
- **渐进演进**：不要过度设计，根据业务增长逐步演进系统架构
- **数据驱动**：通过监控和数据分析来指导优化决策，避免"拍脑袋"式优化

### 核心要点

- **缓存是王道**：优先考虑缓存，其次才是扩容
- **异步解耦**：能用异步就不要同步，消息队列是最好的解耦工具
- **做好限流**：永远不要假设流量是可控的，限流是系统的最后一道防线
- **冗余部署**：所有关键组件至少部署两个实例，消除单点故障
- **灰度发布**：新功能先在小范围上线，验证稳定后再全量发布
- **持续压测**：定期进行压力测试，发现系统的真实瓶颈

### 性能调优路线图

```
识别瓶颈（监控告警） → 制定优化方案 → 实施优化 → 验证效果 → 持续监控
                                      ↑
                              （如果效果不达标，继续下一轮）
```

### 总结检查清单

- [ ] 是否明确了QPS、TPS、RT等性能目标？
- [ ] 是否在DNS/硬件/软件层配置了负载均衡？
- [ ] 是否实施了多级缓存（浏览器/CDN/Nginx/Redis/本地）？
- [ ] 是否配置了合理的缓存过期时间和更新策略？
- [ ] 是否实施了读写分离？是否解决了主从延迟问题？
- [ ] 单表数据量是否超过500万？是否需要分库分表？
- [ ] 分片键的选择是否合理？大部分查询是否携带分片键？
- [ ] 是否在关键接口上配置了限流（接口/IP/用户维度）？
- [ ] 是否为核心依赖服务配置了熔断降级规则？
- [ ] 是否使用消息队列实现了异步削峰？
- [ ] SQL查询是否经过Review？是否避免了索引失效？
- [ ] 是否配置了合理的数据库连接池参数？
- [ ] 是否实现了关键业务的高可用部署（双活/多活）？
- [ ] 是否配置了自动化故障转移机制？
- [ ] 是否建立了混沌工程或定期容灾演练机制？
- [ ] 是否设计了最终一致性保证方案（本地消息表/事务消息/对账）？

以上清单可以作为高并发系统设计时的自检参考，每一条背后都有无数线上故障的血泪教训。高并发系统设计是一个系统工程，不仅需要深入理解每项技术本身，更需要将它们有机组合，形成一个能够自我保护和自我修复的有机整体。
