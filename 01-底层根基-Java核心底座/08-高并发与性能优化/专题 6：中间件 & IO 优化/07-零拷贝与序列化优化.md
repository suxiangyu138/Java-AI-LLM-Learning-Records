# 07 零拷贝与序列化优化

> 数据在系统里每多复制一次，CPU 与内存带宽就多付一份账——零拷贝把"文件到网卡"从四次拷贝减到一次 DMA；序列化把"对象到字节"从 300 字节减到 60 字节；这两件事是高吞吐链路成本的大头

## 1. 传统 IO 的四次拷贝与四次切换

一次"读文件 → 发网络"的传统路径（`read()` + `write()`）分四步：

1. 磁盘 DMA 拷贝到内核页缓存（第 1 次，DMA，不耗 CPU）；
2. `read()` 从内核拷贝到用户态缓冲（第 2 次，CPU 拷贝）；
3. `write()` 从用户态拷回内核 Socket 缓冲（第 3 次，CPU 拷贝）；
4. 网卡 DMA 从 Socket 缓冲读走（第 4 次，DMA）。

同时伴随 4 次用户态/内核态上下文切换。**第 2、3 次 CPU 拷贝是性能杀手**——大文件场景它们吃掉内存带宽与 CPU 时间，这就是传统 MQ/Web 服务器大文件传输 CPU 高的根源。

零拷贝的目标就是消灭第 2、3 次 CPU 拷贝与对应的切换。两条主流路线各有适用场景，别混用。

## 2. mmap 与 sendfile：两条零拷贝路线

- **mmap（内存映射）**：把文件映射进进程地址空间，读写直接操作内核页缓存，省掉第 2 次拷贝（用户态直读页缓存）。RocketMQ 的 CommitLog、Elasticsearch 的段文件、数据库预读都用它。代价：**虚拟内存黑洞**——映射总量不能超堆外内存预算（建议 ≤ 物理内存 × 40%），且随机写场景页缓存回收成本高。
- **内核差异**：sendfile 在 Linux 上是最成熟的零拷贝路径；macOS/Windows 有各自实现（kqueue 的 `sendfile`、Windows 的 TransmitFile）。Java 的 `transferTo()` 在不同平台映射到不同内核调用，**跨平台性能对标要以压测为准**——这也是很多公司把静态文件服务固定部署在 Linux 的原因。
- **sendfile（零拷贝发送）**：数据从页缓存直接 DMA 到网卡（部分内核还支持网卡级合并），完全不过用户态，剩 1-2 次拷贝、2 次切换。Kafka 消费、Nginx 静态文件、Netty FileRegion 都是它。Java 侧是 `FileChannel.transferTo()`，**只能用于"文件 → 网络"的直传**，不能改写数据。

选型一句话：**源是文件、目标是网络、不改内容 → sendfile；需要读写同一份数据（消息存储、索引）→ mmap**。Kafka 是两者都用：写路径 mmap 风格（页缓存），读路径 sendfile。io_uring 进一步把这两条路都异步化（[05 篇](05-JavaIO模型演进与多路复用.md)）。

## 3. Protobuf 与 JSON：体积与速度的账

序列化对比（2026 实测基线，见[00 篇](00-总览.md)参考来源）：

- **体积**：同一个温湿度传感器消息，JSON 约 110-120 字节（含空白与引号），Protobuf 约 20-25 字节——**小 80%**；混合负载实测 3.82MB → 1.18MB（-69%）。体积直接决定带宽、磁盘与下游处理成本。
- **速度**：Protobuf 的 TLV（Tag-Length-Value）结构 + 编译期生成代码，解码像内存寻址；JSON 要词法解析 + 反射 + 中间对象。**反序列化 Protobuf 显著快于 Jackson**。
- **内存**：Protobuf 反序列化近乎零中间对象（实测约 104 字节驻留）；JSON 解析产生大量临时对象，高 QPS 下 GC 压力大。
- **代价**：需要 .proto schema 与代码生成，调试要转 hex；跨团队协作有版本演进纪律（向后兼容字段编号不可复用）。

结论：**内部高吞吐链路（MQ 消息体、RPC 负载）默认 Protobuf**；JSON 留给对外 API 与排障。Java 内部可评估 Kryo（更小但需注册类、跨语言差）；追求极致体积与零拷贝看第 5 节。

选型决策树一句话版本：**跨语言或流式 → Protobuf；纯 Java 内部且追求最小体积 → Kryo；对外接口/调试 → JSON；字段极多且读多写少 → 考虑 FlatBuffers**。别因为"团队成员都会 JSON"就把内部链路留在 JSON——体积差 4-5 倍意味着同带宽下吞吐差 4-5 倍，这个账在高 QPS 链路是决定性的。

一个真实的组合收益实例：物联网消息用 Protobuf 序列化（体积 110 字节 → 25 字节）后进 Kafka（[02 篇](02-消息队列性能模型：Kafka深潜.md)）加 lz4 压缩，单节点实测百万 QPS 且端到端毫秒级延迟——**序列化省体积、压缩省流量、Kafka 省 IO，三个优化叠加而不是只做一项**。

## 4. 压缩选型：zstd / lz4 / gzip

压缩与序列化是叠加关系：序列化解决结构体积，压缩解决内容冗余（日志、JSON 文本压缩率惊人）。三种主流算法：

- **gzip**：压缩率最高但 CPU 最贵（解压是压缩的 3-5 倍便宜），适合"压缩一次、解压多次"的静态资源与归档。
- **lz4**：极速（压缩/解压吞吐 GB/s 级），压缩率中等，适合实时链路——Kafka 消息、网络帧压缩首选。
- **zstd**：压缩率逼近 gzip、速度远快于 gzip（解压尤其快），2026 年数据管道的默认选择；Kafka/RocketMQ 均原生支持。CPU 充裕选 zstd，CPU 紧张选 lz4。

压缩位置原则：**尽早压缩、尽量晚解压**——Kafka 生产端压缩后，broker 不拆包直存，消费端解压，压缩数据全程只解一次。别在链路上反复压缩解压。另一个实践细节是压缩等级：zstd/lz4 都有 1-22 的等级旋钮，**等级 1-3 与等级 19 的压缩率差距不到 10%，CPU 却差数倍**——实时链路用低等级，归档场景才开高等级。

## 5. 零拷贝序列化：FlatBuffers / Cap'n Proto

Protobuf 优化的是带宽，编解码 CPU 成本仍在（O(n)）。**零拷贝序列化**（FlatBuffers / Cap'n Proto）更进一步：线格式与内存结构位级一致，读取时直接指向缓冲内部，不解析（O(1)）。

- **FlatBuffers**：实测反序列化约 0.01ms、驻留 312 字节，游戏/高频读场景用；代价是自底向上序列化很慢（约 1 秒级），写入路径差。
- **Cap'n Proto**：64 位对齐 + 相对指针，消息可 mmap 映射后惰性加载（页故障按需读），能解析大于内存的数据集；代价是格式脆弱、生态小。

2026 的工程现实：**Protobuf 仍是内部链路事实标准**，零拷贝序列化用于读多写少、极致延迟的专项场景（高频行情、游戏状态同步）。别为"看起来先进"引入生态风险。

> 🎯 **核心要点**：传统"文件→网络"四次拷贝两次 CPU 拷贝是性能杀手；mmap 省一次 CPU 拷贝（存储类组件用），sendfile 直达网卡（传输类组件用），io_uring 把两者异步化；Protobuf 比 JSON 小 60-80%、反序列化更快、内存近零，内部链路默认选它；zstd/lz4/gzip 按 CPU 与压缩率权衡，尽早压缩、尽量晚解压；FlatBuffers/Cap'n Proto 是读多写少场景的零拷贝序列化，Protobuf 仍是主流。
