## 1. RocketMQ：日志结构 + mmap + 刷盘策略

RocketMQ（2026 基线 5.3.x）走的是"日志文件 + 索引文件"的存储路线，与 Kafka 同源但工程细节不同：

- **CommitLog + ConsumeQueue + IndexFile 三段式**：所有 Topic 的消息顺序追加到统一的 CommitLog（单文件固定 1G，文件名即起始偏移量）；ConsumeQueue 是消费逻辑队列，存消息在 CommitLog 中的偏移量、大小与 Tag 哈希；IndexFile 支持按 Key/时间戳查询。三段的代价是消费多一跳索引查找，收益是**单机多 Topic 无文件放大**——这点与 Kafka 每个分区独立文件不同。
- **mmap 零拷贝**：`FileChannel.map()` 把 CommitLog 映射到堆外内存，读写少一次用户态拷贝；CommitLog 固定 1G 正是为了适配 mmap 的 2G 地址空间限制。消费路径用 `transferTo()`（sendfile）直接把页缓存数据送进 Socket。
- **刷盘策略是性能与安全的分水岭**：异步刷盘（默认，约每 500ms force 一次）实测单 broker 写 12.3 万 TPS、消费 18.6 万 TPS、延迟 <1ms；同步刷盘每条都 force，**吞吐直降 50% 以上**，但宕机窗口不丢数据。金融/交易场景必须同步，日志类用异步。
- **transientStorePoolEnable**：高吞吐场景（峰值 10 万 TPS+）建议开启，消息先写堆外内存再异步刷盘，减少 JVM GC 影响；池大小取物理内存的 1/8~1/4。
- **mmap 的坑**：映射总大小不能超堆外内存预算，建议映射总量 ≤ 物理内存 × 0.4；大促扩容前先算映射预算，否则 OOM 的是虚拟内存。
- **消费模型**：RocketMQ 默认 push 模式（broker 主动推送 + 本地拉取循环），`consumeThreadMin/Max` 与 `pullBatchSize` 决定消费并发与批量；消息堆积、消费 TPS 低时先调这三项，再查下游（DB 慢查询、外部调用）——与 Kafka 消费排查同构（[02 篇](02-消息队列性能模型：Kafka深潜.md)的消费侧纪律）。
- **主从读与重平衡**：读写分离部署下消费可以走从节点（slaveReadEnable），分担主节点压力；消费者组扩容时重平衡有短暂停止，大促前要演练"滚动扩容不惊扰在线消费"。

## 2. Pulsar：存算分离的架构红利与代价

Pulsar（2026 基线 4.0.9）的核心是**存储与计算分离**：broker 只做路由与缓存，数据落在 BookKeeper 分片日志里。这带来三个 Kafka 难有的能力：

- **无级扩容**：存储节点（bookie）与计算节点（broker）独立扩容，扩容不搬数据——Kafka 加 broker 要重新平衡分区，Pulsar 加 bookie 只影响新写入。
- **多租户隔离**：命名空间级配额与隔离，大促时一个租户的流量不会挤爆另一个租户——这是云原生 MQ 服务的架构基础。
- **分层存储**：数据可自动归档到对象存储，老数据几乎零成本保留（Kafka 4.x 也通过 KIP-405 追平了这一能力）。

代价同样明显：组件数翻倍（broker + bookie + 元数据），运维复杂度显著高于 Kafka；吞吐经过调优可逼近 Kafka 单节点，但延迟通常略高。**流式 + 队列混合场景（既要 streaming 又要 queue 语义）是 Pulsar 的甜区**。

调优要点有两个内存参数：**broker 写缓存**（write cache，暂存写入再批量落 bookie）与**读缓存**（read cache，热数据命中免落盘）——两者默认值按内存预算配比，写缓存过小吞吐掉、读缓存过小热读延迟升；与 Kafka 的页缓存思路不同，Pulsar 的缓存是显式可调的，参数语义更接近[专题 5 的缓存治理](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%205：缓存体系专题/00-总览.md)而非内核黑盒。

## 3. RabbitMQ：灵活路由与仲裁队列

RabbitMQ（4.x 基线）的定位从来不是吞吐：单节点约 4 万级 TPS，靠加节点水平扩展而非单节点性能。它不可替代的是**灵活性与易用性**：

- **复杂路由**：exchange/queue 的多层绑定、topic/headers 匹配，是"消息要按业务规则分发"场景的最优解——Kafka 的 topic 模型做不到按内容路由。
- **请求/响应模式**：RPC over MQ、任务队列（工作队列模式）是它的经典场景。
- **仲裁队列（Quorum Queue）**：4.x 默认队列类型，Raft 复制多副本，替代旧镜像队列，数据不丢且故障切换无需人工干预；吞吐比单副本低，但换来可靠性。

调优重点在确认机制（publisher confirms）与预取（prefetch）——`prefetch=1` 保证公平分发但吞吐受限，处理快的消费者可以放宽到几十。

## 4. 选型决策：吞吐 / 事务 / 路由 / 流式

选型收敛成四个问题（完整对比见 [消息队列理论与实战](../../../02-后端核心技术%20微服务%20分布式%20云原生/03-消息队列/消息队列理论与实战/00-消息队列知识体系总览.md) 的选型篇）：

- **要吞吐还是要灵活？** 百万级吞吐/事件流 → Kafka（或 Pulsar）；复杂路由/任务队列/RPC → RabbitMQ。
- **要事务与可靠吗？** RocketMQ 的事务消息（半消息+回查）与同步刷盘是交易场景首选，吞吐在百万 TPS 以下都够用。
- **要存算分离与多租户吗？** 云原生多租户、无级扩容 → Pulsar；但团队要能承受 BookKeeper 运维成本。
- **要流式 + 队列混合吗？** 既要有序流式处理又要消息竞争消费 → Pulsar（Share 订阅）；Kafka 4.2 的 Share Groups 是另一个解。

**不要一个 MQ 打天下**：成熟架构普遍"Kafka 管事件流 + RocketMQ 管交易 + RabbitMQ 管路由"多 broker 并存，按工作负载选型而非统一收敛（2026 基线见[00 篇](00-总览.md)）。各中间件的完整机制（部署、高可用、API）见 [RocketMQ 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/03-消息队列/RocketMQ/00-RocketMQ知识体系总览.md) 与 [Pulsar 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/03-消息队列/Pulsar/00-Pulsar知识体系总览.md)。

> 🎯 **核心要点**：RocketMQ 用"CommitLog + mmap + 双刷盘策略"平衡吞吐与可靠，异步刷盘 12 万+ TPS、同步刷盘降 50%+，交易场景用同步；Pulsar 存算分离带来无级扩容与多租户，代价是组件翻倍；RabbitMQ 吞吐 4 万级但路由与 RPC 模式无可替代；选型四问（吞吐/事务/路由/混合），成熟架构多 broker 并存。
