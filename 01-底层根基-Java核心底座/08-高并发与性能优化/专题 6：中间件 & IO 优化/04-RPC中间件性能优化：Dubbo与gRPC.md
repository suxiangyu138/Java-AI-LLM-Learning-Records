## 1. RPC 性能四因子

一次 RPC 调用的总延迟由四段叠加，优化顺序应遵循"先大头后小头"：

- **序列化**：对象 ⇄ 字节流的耗时与体积。占单次调用延迟的 5-15%，但体积直接决定带宽与 GC（[07 篇](07-零拷贝与序列化优化.md)）。
- **传输**：网络往返（RTT）、协议效率（HTTP/1.1 头开销 vs HTTP/2 二进制帧）、连接复用与否。**连接复用是最大的延迟因子**——每次新建连接多一次 TCP 握手 + 可能的 TLS 握手（1-3 个 RTT）。
- **线程模型**：IO 线程与业务线程是否分离、是否阻塞（[05 篇](05-JavaIO模型演进与多路复用.md)）。IO 线程被业务代码占住是常见事故。
- **连接管理**：连接池大小、超时链、健康检查。连接数=并发度上限，池太小排队、池太大资源浪费（[08 篇](08-网络层与连接治理.md)）。

排查 RPC 慢的标准顺序：**先看网络（RTT、重传）→ 再看连接（复用率、池满排队）→ 再看线程（IO 线程占用）→ 最后看序列化与业务代码**。90% 的"RPC 慢"不是序列化慢。

## 2. Dubbo 3.3：triple 协议与协议选型

Dubbo 3.3 的协议格局是 2026 基线：**triple 与 dubbo 双协议并存，官方推荐 triple**。

- **triple 协议**：基于 HTTP/1、HTTP/2，100% 兼容 gRPC，支持 Unary/流式/双向流，还能以 REST 风格发布标准 HTTP 服务（3.3 起框架不再有独立 rest 协议扩展）。序列化用 Protobuf Binary / Protobuf-json。多语言覆盖 Java/Go/Node.js/Rust。
- **dubbo 协议**：私有 TCP 二进制协议，性能最高的私有实现，支持 Hessian/Fastjson2/Kryo/Avro 等序列化；但网关不友好、流式不支持、跨语言弱。
- 官方建议：新项目明确配置 triple，老项目平滑迁移；默认协议出于兼容仍是 dubbo，**"默认"不等于"最优"**。

选型一句话：**纯 Java 内部高吞吐且无跨语言诉求 → dubbo 协议；要网关直连、多语言、流式、gRPC 互通 → triple**。

## 3. gRPC：HTTP/2 多路复用与流式

gRPC 的性能核心在 HTTP/2：

- **多路复用**：一个 TCP 连接上并发承载成百上千个流，消灭"连接风暴"。HTTP/1.1 的 1000 QPS 需要上百连接，HTTP/2 一条连接即可，连接数下降直接减少服务器 FD 与内存开销。
- **二进制帧 + 头压缩（HPACK）**：帧头只有 9 字节，头部压缩消除重复头开销，小请求延迟优势明显。
- **流式语义**：服务端流/客户端流/双向流，支撑流式处理与双向通信（AI 推理流式输出、实时数据推送）。
- 短板：HTTP/2 的队头阻塞（TCP 层丢包影响所有流）、Protobuf 的 schema 演进成本。

gRPC 与 triple 同源（triple 兼容 gRPC 协议），选型差别在于框架生态——Dubbo 侧重 Java 微服务体系与注册中心集成，gRPC 侧重跨语言与云原生（Envoy/Istio 原生支持）。

## 4. 连接管理与线程模型

连接与线程是 RPC 高并发下的两个隐性瓶颈：

- **连接复用优先**：长连接 + 多路复用（HTTP/2）是 2026 标准姿势。短连接每请求一次握手，在 TLS 场景下延迟翻倍；连接池要"复用 + 超时释放 + 健康检查"三件套，池大小按 `并发目标 QPS × P99 延迟` 用 Little's Law 估算（[专题 1](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%201：性能理论基础/03-三大理论定律.md)），并留 20-30% 余量。
- **IO/业务线程分离**：IO 线程只做收发，业务逻辑交给业务线程池——IO 线程被同步业务阻塞是 RPC 框架最经典的错误用法；虚拟线程（JDK 21+）让"每请求一线程"的阻塞式写法也能达到高并发（[专题 2 的异步编程篇](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%202：Java%20单机并发编程/08-异步编程：Future到虚拟线程.md)）。
- **超时链设计**：连接超时 < 读超时 < 总超时；重试只对幂等调用开启，且要配退避，否则"超时→重试→风暴"的雪崩链路会放大故障（[08 篇](08-网络层与连接治理.md)）。
- **服务端资源上限**：连接数是双向约束——服务端每连接一个 FD 与内核缓冲，`ulimit -n` 默认 1024 时客户端 1000 并发就把服务端打满。生产环境服务端 FD 上限提到 65535+，配合 HTTP/2 多路复用把"连接数"降为"流数"。
- **注册中心与负载均衡对性能的影响**：服务发现延迟决定"扩容多久生效"——注册中心推送慢时，新节点上线后流量仍在旧节点排队；负载均衡策略（随机/加权/一致性哈希）影响热点分布。2026 基线是注册中心推送毫秒级 + 客户端本地缓存兜底（注册中心抖动不影响调用），这些是 RPC 性能的"看不见的维度"（专题 7 分布式高并发与限流熔断降级将展开）。
- **优雅上下线**：发布时"先摘流量再停服务、先起服务再挂流量"，否则发布窗口的调用失败会触发重试，重试又放大发布瞬间的负载——发布即性能事故的根因常在这里。

## 5. 序列化与压缩：延迟的最后一公里

序列化调优的收益排序：**体积 > 速度 > 内存**。Protobuf 的 TLV 紧凑编码比 JSON 小 60-80%，反序列化更快（编译期生成代码 vs 反射+词法解析），内存占用近乎为零（JSON 解析产生大量中间对象，GC 压力大）——高吞吐内部链路的默认选择。选型参考[07 篇](07-零拷贝与序列化优化.md)的决策树：跨语言/流式用 Protobuf，Java 内部可权衡 Kryo（体积更小但需注册类），JSON 只用于对外接口与排障。

生产调优建议先做一次"四因子体检"：压测基线 → 看连接复用率与池排队 → 看 IO 线程占用 → 最后换序列化，每次只动一个变量（[01 篇](01-中间件性能全景与调优方法论.md)闭环）。Dubbo 完整功能面（SPI、注册中心集成、容错策略）见 [Dubbo 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/Dubbo/00-Dubbo知识体系总览.md)。

> 🎯 **核心要点**：RPC 性能 = 序列化 × 传输 × 线程模型 × 连接管理，90% 的慢先查网络与连接复用，序列化排最后；Dubbo 3.3 官方推荐 triple（HTTP/2+Protobuf、兼容 gRPC），纯 Java 高吞吐才用私有 dubbo 协议；HTTP/2 多路复用消灭连接风暴；IO/业务线程分离 + 长连接池 + 超时链设计是生产基线。
