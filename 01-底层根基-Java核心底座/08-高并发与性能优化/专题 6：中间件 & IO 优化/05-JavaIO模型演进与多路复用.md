## 1. BIO：一连接一线程的代价

BIO（阻塞 IO）的模型最简单：每个连接分配一个线程，线程在 read 上阻塞等待数据。连接数少时这是最直观的写法——`server.accept()` 后 `new Thread` 处理即可。

代价随连接数指数级上升：

- **线程 = 内存**：每个平台线程默认栈 1MB（可调但换汤不换药），1 万连接 ≈ 1.2GB 内存只养线程。
- **线程 = 调度成本**：上万线程的上下文切换（一次约微秒级）吃掉 CPU，大量线程阻塞在等待上，调度器忙得不可开交。
- **阻塞 = 资源闲置**：99% 的连接 99% 的时间没有数据，线程却全程占用。

1 万连接是 BIO 的实用天花板——不是连不上，是"连上了跑不动"。这正是高并发必须换模型的物理原因。

这套演进的引擎是 2000 年代的 **C10K 问题**（1 万并发连接挑战）：当时的主流服务器一连接一线程，在万级连接处集体崩溃，逼出了事件驱动（select/epoll）、异步 IO 与后来的框架化（Netty、Nginx 都是 C10K 时代的产物）。今天的"百万并发"不过是 C10K 的延续——模型对了，连接数只是资源问题。

## 2. NIO 与多路复用：select / poll / epoll

NIO 的思路是把"线程等数据"改成"内核帮线程盯数据，有事件再通知"。核心是一次 `select/epoll_wait` 系统调用监听海量连接：

- **select/poll**：把关心的 FD 集合传给内核，内核遍历返回就绪集。**O(n) 遍历**——FD 上万时每次调用的遍历成本很高，且有 FD 数量上限（select 默认 1024）。
- **epoll**（Linux 专用）：内核维护红黑树登记监听 FD，就绪的 FD 挂进就绪链表，应用只取就绪集。**事件通知 O(1)**，无上限。是 Linux 高并发服务器的绝对主力。
- **kqueue**（BSD/macOS）与 io_uring 是同族更优解，Windows 用 IOCP。

Java 侧对应 `java.nio` 三件套：**Channel**（连接通道）、**Buffer**（数据容器）、**Selector**（多路复用器，封装 epoll/kqueue/IOCP）。理解 NIO 的钥匙是"**就绪通知 + 非阻塞读写**"：应用线程在 `select()` 上阻塞，被唤醒后只处理就绪连接，绝不阻塞等待某个连接的 IO 完成。

Buffer 有一个容易踩的性能点：**堆内 Buffer 与直接 Buffer（DirectBuffer）**。直接内存省去"堆 → 内核"之间的一次拷贝（写 Socket 时），是网络 IO 的推荐形态，但不归 JVM 堆管、要手动释放（Netty 的 PooledDirectByteBuf 解决了分配与释放，[06 篇](06-Netty线程模型与内存优化.md)）；堆内 Buffer 有 GC 管理，但每次 IO 多一次拷贝。**高吞吐链路用直接内存，业务小包场景用堆内缓冲更省心**——按场景选，别默认。

## 3. Reactor 模型：事件循环的经典形态

多路复用之上长出了 Reactor 模型，Netty 是它的教科书实现（[06 篇](06-Netty线程模型与内存优化.md)）：

- **单 Reactor 单线程**：一个事件循环线程负责 accept + read + 业务处理。吞吐依赖单核，业务稍慢就阻塞所有连接——只适合教学。
- **主从 Reactor 多线程**：**boss 线程**只 accept，把连接注册给**worker 线程池**；每个 worker 是独立事件循环，绑定一批连接，串行处理其事件。连接与线程绑定后无锁竞争，这是 Netty 的默认形态，也是几乎所有现代网络中间件（Redis 单线程模型的扩展版、Nginx、Kafka 网络层）的架构底色。
- 变体：worker 内再分 IO 与业务线程，或配虚拟线程承载阻塞业务（[专题 2](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%202：Java%20单机并发编程/00-总览.md) 的线程模型篇）。

**一个事件循环线程不能跑阻塞操作**——睡 100ms 就是全连接 100ms 停顿，这是 Reactor 体系最常被违反的铁律。

## 4. io_uring：异步 IO 的新内核

epoll 仍是"就绪通知 + 自己读写"，读写的系统调用依然同步。io_uring（Linux 5.1+）把 IO 彻底异步化：应用把读写请求提交进内核环形队列（SQ），内核完成后写回完成队列（CQ），全程无阻塞等待——一次提交可以批量携带成百上千请求，天然是零拷贝的载体。

- **收益**：高吞吐场景（存储、网关、大数据）比 epoll 吞吐提升显著，Netty 4.2 已正式支持 io_uring 传输（[06 篇](06-Netty线程模型与内存优化.md)）；RocketMQ 等存储型中间件也在评估落地。
- **边界**：需要内核 5.19+（功能完整）、部分文件系统特性受限；延迟敏感的小请求场景收益不如大吞吐场景。**先压测再迁移，别迷信"新=快"**。

## 5. 虚拟线程：阻塞式代码的回归

2026 年的 Java 视角有个反转：JDK 21 GA、JDK 26 基线的**虚拟线程**让"阻塞式代码"重新成为高并发主流写法。

- 虚拟线程由 JVM 调度到少量平台线程（载体）上，阻塞时被移出载体，让出执行权——**1 万虚拟线程只需 8MB 内存、12ms 启动**，而 1 万平台线程要 1.2GB、1850ms（[专题 2 的异步编程篇](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%202：Java%20单机并发编程/08-异步编程：Future到虚拟线程.md) 实测）。
- 业务代码可以写"每请求一个线程 + 阻塞式 JDBC/HTTP 调用"，并发度由虚拟线程数保证——对大多数业务开发，这比 NIO 的异步回调心智负担低一个量级。
- 但它**不取代 NIO**：虚拟线程解决"线程数"，不解决"系统调用次数与内核拷贝"；Netty/io_uring 解决的是后者。网关、中间件这类吞吐型组件仍用事件循环，业务服务用虚拟线程，各司其职。

**选型坐标**：连接少、代码简单 → BIO/虚拟线程阻塞式；连接海量、吞吐型 → NIO + 多路复用（epoll/io_uring）；Java 组件开发 → Netty。IO 模型的完整代码形态与 API 见 [Netty 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/Netty/00-Netty知识体系总览.md) 与[专题 2](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%202：Java%20单机并发编程/00-总览.md) 的虚拟线程篇。

> 🎯 **核心要点**：BIO 一连接一线程在 1 万连接处撞墙（1.2GB 内存只养线程）；epoll 用内核事件通知做到 O(1)，是 Linux 高并发主力；Reactor 主从多线程（boss accept + worker 事件循环）是所有现代网络中间件的底色，事件循环内禁止阻塞；io_uring 把 IO 彻底异步化，Netty 4.2 已支持；虚拟线程解决线程数、NIO 解决系统调用，两者互补不互斥。
