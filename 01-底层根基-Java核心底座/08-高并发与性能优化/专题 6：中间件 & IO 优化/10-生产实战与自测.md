## 1. 实战一：订单系统 MQ 吞吐上不去

**症状**：大促下单消息生产端 QPS 卡在 2 万，目标 8 万；broker 负载不高，生产端 CPU 高。

**定位三步**：① 看生产端指标——`record-send-total` 平稳但 CPU 高，说明瓶颈不在 broker 在本地；② 看参数——`linger.ms=0`、`batch.size=16KB`（默认未动）；③ 看单条大小——订单消息带全量详情约 8KB。

**根因**：linger=0 导致每次发送都是单条小批次，批量机制失效，压缩率也上不去（小包压缩收益低），CPU 全耗在"建批次 + 压缩 + 序列化"上。

**对策**：① `linger.ms=10`、`batch.size=64KB`，批量摊薄成本；② `compression.type=lz4`；③ 消息体瘦身——详情字段拆出去按需拉取（序列化体积 8KB → 1.2KB，[07 篇](07-零拷贝与序列化优化.md)）；④ 分区数 16 → 48，生产并发写路径翻三倍。

**复盘**：压测后生产端 QPS 2 万 → 9.6 万，broker 仍未饱和。教训：**吞吐瓶颈先查"批量是否生效"，再查分区与下游**——顺序不能反（[02 篇](02-消息队列性能模型：Kafka深潜.md)）。

## 2. 实战二：RPC P99 从 80ms 涨到 500ms

**症状**：大促前压测发现订单服务调库存服务的 P99 从 80ms 涨到 500ms，P50 只从 40ms 涨到 60ms——**典型的排队型长尾**（[专题 1 的尾延迟篇](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%201：性能理论基础/02-延迟分布与长尾效应.md)）。

**定位**：① 网络层排除——RTT 稳定 0.5ms 无重传；② 连接层——连接池 20 连接已打满，`acquireTimeout` 排队；③ 线程层——IO 线程正常，业务线程池队列堆积。

**根因**：连接池 20 = 并发度上限 20，QPS 2 万 × P99 80ms 需要约 1600 并发，**池小了 80 倍**（Little's Law，[08 篇](08-网络层与连接治理.md)）。

**对策**：① 连接池 20 → 100（含 25% 余量）；② 升级 triple/HTTP/2 多路复用，单连接承载并发流，连接数与 FD 双降（[04 篇](04-RPC中间件性能优化：Dubbo与gRPC.md)）；③ 给下游设独立超时（P99×2）防止慢实例拖全池；④ 压测验证后固化为容量基线。

**复盘**：P99 回到 65ms。教训：**P99 恶化先怀疑连接与线程的排队，不要先怀疑网络与代码**。

## 3. 实战三：大文件下载 CPU 打满

**症状**：文件下载接口（走应用层读文件 → 写响应流）CPU 100%，QPS 只 200；IO 利用率却不高。

**根因**：应用层每次下载走"文件 → 用户态缓冲 → Socket"两次 CPU 拷贝（[07 篇](07-零拷贝与序列化优化.md)的四次拷贝路径），8 核 CPU 全部耗在拷贝上。

**对策**：① 静态文件交给 Nginx 直出——`sendfile on`，内核零拷贝直达网卡（[08 篇](08-网络层与连接治理.md)）；② 必须走应用的场景用 Netty `FileRegion`（sendfile）替代 read+write（[06 篇](06-Netty线程模型与内存优化.md)）；③ 动态生成的下载包（如导出的 Excel）先落临时文件再 FileRegion 发送。

**复盘**：QPS 200 → 5000，CPU 降至 15%。教训：**能交给内核的拷贝不要自己做**——零拷贝是成本最低的 IO 优化。

## 4. 生产纪律清单

1. **先压测基线，后调参数**——没有基线数字的调优是玄学（[01 篇](01-中间件性能全景与调优方法论.md)闭环）。
2. **一次一变量**——同批改多个参数无法归因，回滚也说不清。
3. **参数变更走评审并记录**——参数漂移比代码退化更隐蔽。
4. **配置基线文档化**——版本、环境、压测数据、变更历史四栏齐全。
5. **EventLoop/IO 线程内禁止阻塞**——睡眠、锁等待、同步 IO 都是事故。
6. **连接池/线程池按 QPS×P99 计算并留 20-30% 余量**——不拍脑袋。
7. **超时链单调递增、重试只对幂等**——防重试风暴（[08 篇](08-网络层与连接治理.md)）。
8. **刷盘策略按数据价值定**——日志异步、交易同步/组提交（[09 篇](09-文件与磁盘IO优化.md)）。
9. **中间件版本跟进安全线**——Netty 4.2.15 这类安全版本必须升级。
10. **监控固化**——吞吐/延迟/连接数/lag/端口状态建看板，报警先于事故。

## 5. 报错速查十条

| 现象 | 大概率原因 | 处理 |
|---|---|---|
| 生产端 QPS 上不去、CPU 高 | linger/batch 未生效 | 调批量与压缩（实战一） |
| P99 涨、P50 平 | 连接/线程排队 | 查池大小与队列（实战二） |
| CLOSE_WAIT 堆积 | 应用未 close | jstack 找泄漏线程 |
| TIME_WAIT 巨量 | 短连接高频 | 连接复用，一般正常 |
| connect 超时 | backlog 满或服务不可达 | 查 somaxconn 与服务健康 |
| RPC 偶发超时 | 慢实例拖全池 | 独立超时 + 熔断剔除 |
| MQ lag 持续增长 | 分区数不足或消费慢 | 先扩分区再扩消费者 |
| 大文件下载 CPU 高 | 应用层拷贝 | sendfile/FileRegion |
| 异步刷盘丢消息 | 刷盘窗口宕机 | 改同步/组提交 |
| 直接内存 OOM | ByteBuf 泄漏 | 查引用计数释放 |

## 6. 面试三范式

- **价值式**："Kafka 为什么快？" → 四支柱（顺序写/页缓存/零拷贝/批量压缩）→ 每个支柱给出数量级（HDD 顺序 vs 随机差 100 倍）→ 落到"摊薄单次 IO 成本"的抽象。
- **技术式六段**（RPC 调优题）：指标定义 → 分层定位（网络/连接/线程/序列化）→ 根因假设 → 验证手段（压测/监控）→ 对策与权衡 → 结果复盘。
- **生产式**："线上 MQ 积压怎么办？" → 先止血（扩分区扩消费）→ 定位（lag 曲线 + 消费线程）→ 根治（批量/瘦身/下游提速）→ 复盘固化。
