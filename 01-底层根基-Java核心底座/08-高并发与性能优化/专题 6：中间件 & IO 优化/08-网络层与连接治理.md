## 1. TCP 参数：Nagle / backlog / keepalive

三个高频 TCP 参数，各自管一件事：

- **TCP_NODELAY（禁用 Nagle）**：Nagle 算法把小包合并后再发，避免"小包洪泛"，但对交互式请求会引入高达 40ms 的确认延迟。Java 服务端（Tomcat/Netty/连接池）默认开启 `TCP_NODELAY=true`；**只开这个参数不够**——延迟还受对端处理与重传影响，别指望一个参数包治百病。
- **backlog（监听队列长度）**：内核为监听 Socket 维护 accept 队列，队列满后新连接被丢弃（客户端表现为 connect 超时/拒绝）。高并发入口（网关、Redis、DB）backlog 要放大到 1024-4096，并同步调整 `somaxconn`。**连接数接近上限时先看这里**，不要误判为应用故障。
- **keepalive（探活）**：默认 2 小时太晚发现死连接，生产建议调小（如 60s 探测）；但探活只保"连接存活"，业务级健康检查（应用层心跳）才能发现"半死"服务。代理层与连接池各有自己的 idle 超时，链路不匹配会导致"服务端先断、客户端还以为是好连接"。

## 2. 连接治理：复用、池化与健康检查

**连接数 = 并发度上限**（Little's Law 的物理面，[专题 1](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%201：性能理论基础/03-三大理论定律.md)）：每个连接占用 FD、内核缓冲与接收队列，连接打满 = 请求排队。

- **复用优先**：HTTP/1.1 的 keep-alive、HTTP/2 多路复用、RPC 长连接池——每次新建连接多 1-3 个 RTT（TLS 更多），大流量下新建连接本身就成为瓶颈（[04 篇](04-RPC中间件性能优化：Dubbo与gRPC.md)）。
- **池大小计算**：`池大小 = 目标 QPS × P99 延迟`，留 20-30% 余量；连接池不是越大越好——HikariCP 的教训是"池大 10 倍，慢 10 倍"（排队都堆在数据库侧）。配置要分场景：网关连接上游的池、应用连 Redis/MQ/DB 的池，各自独立评估。
- **健康检查三件套**：连接空闲回收、探测失败自动剔除、恢复后自动回池——缺一个，故障节点就会持续吃流量。
- **FD 与端口是物理上限**：每个连接消耗一个文件描述符，服务端 `ulimit -n` 默认 1024——客户端连接数一到 1024 就被拒。生产基线：服务端 FD 65535+，客户端出站端口受 `net.ipv4.ip_local_port_range` 限制（默认约 2.8 万个端口），短连接高频时端口耗尽表现为"connect 失败"——用连接复用消灭新建，比调端口范围更治本。
- **DNS 缓存是隐藏的延迟炸弹**：JVM 默认 `networkaddress.cache.ttl=30` 秒（安全目录）或永久缓存（Java 17+ 默认 -1 缓存成功解析），DNS 切换后老 IP 还会被调用数分钟；生产应显式设 `-Dnetworkaddress.cache.ttl=10` 左右，兼顾切换速度与 DNS 压力。

## 3. TIME_WAIT 与 CLOSE_WAIT：端口状态学

`ss -s` 或 `netstat` 看到大量状态时，要能读懂它们的含义：

- **TIME_WAIT 多**：主动关闭方在等待 2MSL（约 60s）后回收端口。**短连接高频场景大量 TIME_WAIT 是正常现象**，不是故障——只有端口耗尽（六万多）或出现在长连接服务上才要处理。缓解：连接复用、调整 `net.ipv4.tcp_tw_reuse`（出站复用）。
- **CLOSE_WAIT 多 = 应用 bug**：对端关闭了连接，应用却没调用 close——典型原因是"读超时/异常没走到 finally 释放连接"。**CLOSE_WAIT 堆积几乎必然指向应用层泄漏**，是排查重点（配合 jstack 找持有连接的线程）。
- 排查顺序：`ss -s` 看总量 → `ss -tanp` 看具体连接与进程 → 结合应用日志与 jstack 定位。细节见仓库的[网络问题排查体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/网络问题排查/00-网络问题排查总览.md)。

## 4. 超时链与重试风暴

超时是分布式系统最锋利的双刃剑：设太长，故障被拖成雪崩；设太短，正常慢请求被误杀。设计原则：

- **超时链单调递增**：连接超时 < 读超时 < 总超时。例如网关对上游：connect 500ms < read 3s < 总 5s；逐层向内收缩，保证"上层先放弃，下层早失败"。
- **重试只对幂等操作**：读请求可重试，写请求必须有幂等键；重试加指数退避 + 抖动，否则超时瞬间全网重试 = 重试风暴（缓存重建风暴的兄弟，见[专题 5](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%205：缓存体系专题/08-缓存并发控制与降级.md)）。
- **超时值 = P99 × 2 经验法**：以基线 P99 为锚定，兼顾正常慢请求与故障探测；每个依赖单独设，别用全局统一值。
- **延迟分段再动手**：一次调用慢，先拆网络往返（RTT）与应用处理（服务端耗时）——用 `curl -w` 的 time_namelookup/time_connect/time_starttransfer 或链路追踪分四段：DNS → TCP → 首字节 → 传输。**不分段就调参数，等于蒙着眼开枪**（分层排查方法论见[专题 1](../../../01-底层根基-Java核心底座/08-高并发与性能优化/专题%201：性能理论基础/05-瓶颈定位方法论.md)）。

## 5. 网关层：Nginx 性能参数

Nginx 是接入层的默认选择，2026 性能基线：

- **worker_processes = CPU 核数**：每个 worker 是独立事件循环，进程数超过核数只增加切换；worker 连接数上限 `worker_connections` 按 `QPS × P99` 估算。
- **upstream 连接池**：`keepalive` 参数复用与后端的连接（默认 0 = 每请求新建，**必须显式配置**）；后端 HTTP/2 或长连接配合（[04 篇](04-RPC中间件性能优化：Dubbo与gRPC.md)）。
- **sendfile + tcp_nopush**：静态文件走零拷贝直发，大文件 CPU 占用下降一个量级（[07 篇](07-零拷贝与序列化优化.md)）。
- **gzip/zstd + 缓存头**：静态资源压缩与长缓存；限流（limit_req 漏桶）与安全头是接入层标配。完整参数面见 [Nginx 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/Nginx/00-Nginx知识体系总览.md)。

> 🎯 **核心要点**：网络调优 80% 是连接治理——复用与池化是并发度的物理保障，池大小按 QPS×P99 计算并留余量；TIME_WAIT 多大多正常，CLOSE_WAIT 多必查应用泄漏；超时链"连接<读<总"单调递增、重试只对幂等并退避，防重试风暴；TCP_NODELAY/backlog/keepalive 三个参数按场景配置，backlog 是连接打满的第一嫌疑。
