## 1. 慢 SQL 三型：行锁、DDL、深分页

2025-2026 年数据库故障复盘里，慢 SQL 几乎都是这三副面孔之一：

- **行锁争抢**：多个大用户高并发更新同一条 count/quota 数据（如每日限额、库存余量），行锁排队导致单次更新耗时 5-6 秒。实测对比：压测 1200 并发热点更新，**开事务需 1 分钟，不开事务仅 3 秒**——事务内热点行更新是最贵的操作。治理：热点行拆分（多行分片计数）、事务最小化、乐观锁（版本号/CAS）替代行锁。
- **DDL 锁表**：大表加字段未走 Online DDL，Metadata Lock（MDL）导致大量 SQL 锁等待，应用线程池被快速打满。治理：Online DDL（pt-online-schema-change/gh-ost）、DDL 窗口期（低峰执行）、DDL 审批。
- **深分页**：数据量大的账号分页查询（`limit 100000, 20`）触发慢 SQL——即使 where 字段有索引，深分页也要扫描并丢弃前 10 万行，数据库 CPU 直接 100%。治理：游标分页（`where id > last_id limit 20`）、NextToken 方案、限制最大分页深度。

共同特征：**不是 SQL 写错了，而是量变引发质变**——上线时数据量小没问题，数据增长后索引退化/锁冲突爆发，这类故障最需要"容量视角"（[专题 8](../专题%208：架构层面优化%20+%20全链路压测/06-全链路压测方法论.md) 的压测才能提前暴露）。

## 2. 经典传导链：连接池→线程池→雪崩

慢 SQL 的杀伤力不在 SQL 本身，而在传导链（与[专题 7 的雪崩链条](../专题%207：分布式高并发%20&%20限流熔断降级/01-分布式高并发全景与雪崩链条.md)同构）：

**慢 SQL → 数据库连接被占满 → 业务线程阻塞等连接 → 业务线程池（Dubbo/HTTP）耗尽 → 新请求排队超时 → 上游等待 → 级联雪崩**。

每一步的放大机制：慢 SQL 占连接不释放（一条 5 秒的 SQL 占着连接，其他请求全部等待）；业务线程池的线程数远大于连接池数（200 线程 vs 50 连接），等待连接的线程堆积成山；恢复后积压请求集中重试，二次冲击（[06 篇](06-真实案例：线程池与分布式锁.md) 的重试风暴）。

防护要点（[专题 7](../专题%207：分布式高并发%20&%20限流熔断降级/00-总览.md) 的防线在数据库场景的落地）：连接获取超时（200ms 拿不到连接快速失败，禁止无限等待）；慢 SQL 监控告警（`long_query_time` 阈值 + 实时 processlist 采样）；数据库侧限流/熔断（Sentinel 对 DB 调用的降级）。

## 3. 主从延迟与锁等待

两类高频但不是慢 SQL 的数据库故障：

- **主从延迟**：大事务（批量更新、DDL）导致从库延迟秒级到分钟级，读从库的业务读到旧数据，引发"数据丢失"误报（[专题 8 的读写分离](../专题%208：架构层面优化%20+%20全链路压测/03-数据架构优化：读写分离与分库分表.md) 治理：大事务拆分、并行复制、延迟告警后读切主库）。
- **锁等待与死锁**：两个事务互相持锁等待 → 死锁（InnoDB 自动回滚一个事务）；锁等待（非死锁）更隐蔽——大量线程在等一把锁，处理不过来。取证用 `SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK 与 TRANSACTIONS 段（[中间件运维故障排查体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/MySQL%20Redis%20MQ%20运维相关故障现象/00-中间件运维故障排查总览.md) 有完整速查）。

## 4. 定位手法：processlist 与 explain

数据库故障定位的标准动作（[03 篇](03-故障定位工具链.md) 的数据库工具展开）：

1. **`SHOW PROCESSLIST` 多抓几次**：找长时间 Running 的 SQL——抓一次不够（可能错过），间隔几秒连续抓，对比状态变化；重点看 `Time`（跑了多久）与 `State`（Sending data = 正在扫数据）。
2. **`EXPLAIN` 看执行计划**：确认是否走索引——`type=ALL`（全表扫描）或 `rows` 巨大就是问题 SQL；`EXPLAIN ANALYZE`（8.0+）能看真实执行耗时。
3. **慢查询日志**：`long_query_time=1` 开启，复盘时扫日志找"异常时段新增的慢 SQL"——发布后新增的慢 SQL 九成是索引退化或数据分布变化。

定位的纪律：**找到 SQL 后先看它是不是变更引入的**（新 SQL/新索引/新数据量），再判断是 SQL 问题还是容量问题——这决定修复方向（改 SQL vs 加资源）。

实际排障中还有一个高频混淆：**慢 SQL 与锁等待互相伪装**——processlist 里大量 `Waiting for table metadata lock` 是 DDL 锁表（不是 SQL 慢），大量 `Lock wait timeout` 是行锁争抢（不是查询慢）；先分清"等锁"与"执行慢"再动手，方向错了等于白查。判断技巧：看 `State` 字段——`Sending data`/`Sorting result` 是执行慢，`Waiting for ... lock` 是等锁。

## 5. 治理：从 SQL 到架构

数据库慢 SQL 治理按收益排序的完整链条：

1. **SQL 层**：索引优化（复合索引覆盖查询）、避免深分页（游标）、事务最小化（不开长事务）、避免热点行更新（分片计数）；
2. **监控层**：慢 SQL 实时告警、processlist 采样、连接池水位监控——**在故障发生前 30 分钟发现，比故障后复盘强 100 倍**；
3. **防护层**：连接获取超时 + fast-fail、数据库调用限流熔断、连接池隔离（[专题 7](../专题%207：分布式高并发%20&%20限流熔断降级/08-隔离与舱壁：线程池与信号量.md) 的舱壁）；
4. **架构层**：读写分离（读压分离）、缓存前置（热点读不再打库）、分库分表（单库容量上限，[专题 8](../专题%208：架构层面优化%20+%20全链路压测/03-数据架构优化：读写分离与分库分表.md)）；
5. **变更管控**：DDL 审批与窗口期、索引变更走灰度（先在从库验证执行计划）。

> 🎯 **核心要点**：慢 SQL 三型（行锁争抢开事务慢 20 倍、DDL 锁表、深分页 CPU 100%）的共同特征是"量变引发质变"，需要容量视角提前暴露；传导链"慢 SQL→连接池满→线程池满→雪崩"与专题 7 的雪崩链条同构，防护靠连接超时+限流熔断+隔离；定位靠 processlist 多抓+EXPLAIN+慢查询日志，先查变更再定方案；治理链条从 SQL 优化到监控到防护到架构到变更管控，越靠前成本越低。
