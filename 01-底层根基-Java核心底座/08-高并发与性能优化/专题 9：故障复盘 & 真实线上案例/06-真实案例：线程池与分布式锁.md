## 1. 案例一：CaribouCommons 重试风暴

2026 年 3 月的一起全网级事故，根因是公共库的一行代码：某公共组件把分布式锁的重试间隔从 100ms 改成 10ms。高并发下 Redis 请求量激增 → Redis 过载 → 服务线程池耗尽 → 数据库连接池耗尽 → 连锁故障，**订单失败率从 0.1% 飙升至 35%**，最终全量回滚。

复盘的关键洞察有三个：

- **公共组件的微变更影响半径是全局的**——一行代码改动影响所有接入方，远超普通业务代码的爆炸半径；
- **重试是流量放大器**——重试间隔缩短 10 倍，Redis 请求量放大 10 倍，放大的流量又触发更多失败，形成正反馈；
- **回滚是唯一解**——发现根因后全量回滚（[02 篇](02-故障分级与响应机制.md) 的止血第一手段）。

教训沉淀为变更管控铁律：公共库变更必须评估上下游影响、灰度发布、压测验证（[08 篇](08-发布变更事故与变更管控.md) 展开）。

## 2. 案例二：map 遍历删除引发的雪崩

某大厂事故：服务在遍历 map 的同时删除元素，并发场景下引发异常与数据错乱，进一步触发重试放大，最终雪崩。技术细节（[专题 2 的并发容器](../专题%202：Java%20单机并发编程/00-总览.md)）：HashMap 遍历中删除会抛 ConcurrentModificationException；高并发下的错误处理（捕获异常后重试）把单点问题放大成雪崩。

这个案例的启示不在 map 本身，而在**错误处理链路**：单点代码缺陷 + 不合理的重试 + 无熔断保护 = 雪崩。三个环节任何一环有防护（熔断、限流、合理的重试上限），事故都不会扩散——防护体系（[专题 7](../专题%207：分布式高并发%20&%20限流熔断降级/00-总览.md)）是"单点 bug 不放大"的保险丝。

## 3. 线程池耗尽：结果而非根因

线程池打满是线上最常见的表象，但**它永远是结果**。按根因分类的四种典型成因链：

1. **下游变慢**：依赖服务变慢/超时 → 调用方线程全部阻塞等待 → 线程池耗尽（无超时或超时过长是帮凶）；
2. **数据库连接不足**：慢 SQL 占满连接池 → 业务线程等待连接（[05 篇](05-真实案例：数据库与慢SQL.md)）；
3. **重试放大**：失败重试把压力放大 N 倍（案例一）；
4. **任务积压**：MQ 消费积压或批量任务突增，处理速度跟不上入队速度。

定位手法：jstack 抓线程快照（[03 篇](03-故障定位工具链.md)），看线程**阻塞在什么资源上**——阻塞在数据库连接（SQL 问题）、阻塞在下游 RPC（超时/熔断问题）、阻塞在锁（锁竞争问题）。线程状态分布直接指向根因层，这是"线程池问题"定位的核心动作。

另一个容易误判的细节：**线程池的队列长度与拒绝策略**——核心线程占满后任务进队列（LinkedBlockingQueue 默认无界），队列积压到一定量时 RT 已劣化但线程池指标看似正常（活跃线程未满、拒绝次数为零）；此时真正的问题是"队列深度在涨"。监控必须同时看活跃线程数与队列深度两个指标，只看线程数会漏判积压型故障。

## 4. 恢复后的重试风暴

一个反直觉但高频的事故模式：**故障恢复时刻比故障时刻更危险**。故障期间积压的请求（重试队列、MQ 堆积、客户端退避后集中重试）在恢复瞬间全部涌入——单机瞬间收到 10 倍流量，刚刚恢复的系统再次被打满，雪崩重启。

防护手段：**恢复限流**（恢复后前几分钟限流放量，逐渐放开）；**退避抖动**（客户端重试加随机退避，避免同时重试的同步脉冲）；**积压分批消化**（MQ 消费按速率恢复，禁止一次性拉满）。2026 年事故复盘显示"恢复后二次雪崩"的占比不低——恢复预案要和故障预案一样写进 runbook。

## 5. 三条防护铁律

综合案例，线程池/锁/重试类事故的三条铁律：

- **重试必须限流且退避**：重试次数上限（2-3 次）、指数退避 + 随机抖动、重试只限幂等操作（[专题 7](../专题%207：分布式高并发%20&%20限流熔断降级/06-熔断机制：状态机与参数设计.md) 的重试纪律）；公共库的重试参数变更要按案例一的标准走变更管控。
- **超时必须显式**：任何网络调用都有超时（[专题 7 的超时金字塔](../专题%207：分布式高并发%20&%20限流熔断降级/08-隔离与舱壁：线程池与信号量.md)），无超时 = 允许线程无限阻塞 = 允许雪崩。
- **隔离与熔断兜底**：线程池隔离（[专题 7](../专题%207：分布式高并发%20&%20限流熔断降级/08-隔离与舱壁：线程池与信号量.md)）保证一个依赖拖不死全部；熔断让故障快速失败而不是排队堆积——两个案例如果当时有熔断，事故影响半径都会小一个数量级。

> 🎯 **核心要点**：两个真实案例（重试间隔 100ms→10ms 导致失败率 0.1%→35%、map 并发缺陷经重试放大成雪崩）说明"单点缺陷 + 重试放大 + 无防护 = 雪崩"的通用公式；线程池耗尽永远是结果，jstack 看线程阻塞在什么资源上来定位根因层；恢复后重试风暴是反直觉的高频事故，需要恢复限流与退避抖动；三条铁律——重试限流退避、超时显式、隔离熔断兜底。
