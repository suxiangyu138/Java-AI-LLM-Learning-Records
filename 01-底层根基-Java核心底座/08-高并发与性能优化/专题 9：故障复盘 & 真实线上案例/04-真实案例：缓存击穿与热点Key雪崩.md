## 1. 案例一：1.5MB 大 Key 击穿双十一

某电商活动上线的瞬间，一个 **1.5MB 的 Redis Key** 被数万 QPS 同时访问——本地 JVM 缓存冷启动为空，所有请求穿透到同一个 Key。双重暴击：

- **缓存击穿**：热点数据失效瞬间，高并发同时回源；
- **带宽瓶颈**：Redis 单分片约 25MB/s（200Mbps 限流），除以 1.5MB 意味着每秒最多 16-17 次有效吞吐——数万 QPS 全部排队，Redis 成为死锁瓶颈。

修复三板斧：JSON 改 Protostuff 序列化（1.5MB → 500KB）；Gzip 压缩（→ 17KB，**负载下降 98%**）；Guava Cache `get(key, callable)` 回源加锁杜绝并发穿透。复盘教训：**禁止缓存整表/复杂聚合对象**；涉及缓存结构的变更必须做"大 Key + 高并发"压测（[专题 8](../专题%208：架构层面优化%20+%20全链路压测/06-全链路压测方法论.md) 的场景设计）；上线流程对缓存变更要有管控。

## 2. 案例二：热点 Key 打满 Redis CPU

会员积分系统 `user:score:{userId}` 类 Key 被高频访问——**一分钟 23 万次**，Redis 集群 CPU 100%，服务整体劣化。排查链路值得背下来：先排除慢 SQL（日志为空）→ 排除线程池满（监控未饱和）→ 排除网络 → 用 `redis-cli --hotkeys` 定位到热点 Key（[03 篇](03-故障定位工具链.md) 的排查顺序实战版）。

演进方案分三阶段：**紧急止血**（本地缓存互斥锁 + 调大连接池 + Sentinel 限流）→ **热点探测与隔离**（`INFO commandstats` + 云厂商热点检测，软过期 + 异步刷新）→ **三级缓存架构**（L1 Caffeine 本地缓存、L2 Redis 集群、L3 MySQL + MQ 异步补偿）。教训：热点 Key 治理不是一次性的，而是"探测 → 隔离 → 架构演进"的持续工程（与[专题 5](../专题%205：缓存体系专题/00-总览.md) 的热点治理互读）。

一个值得强调的细节是**热点 Key 的识别信号**：`INFO commandstats` 里单命令调用占比异常高（某条命令占 90%+ 的调用量）、Redis CPU 持续高位但 QPS 平稳、单分片延迟显著高于其他分片（集群模式）——三条信号任一命中，优先跑 `--hotkeys` 确认。识别之后的标准动作是**热点 Key 本地缓存 + 多副本**（副本 key 加随机后缀，各副本独立过期，配合[05 篇](05-真实案例：数据库与慢SQL.md) 的随机 TTL 思路防集中失效）。

## 3. 案例三："善意降级"引发的雪崩

订单履约系统最隐蔽的案例：MySQL QPS 从 800 飙升至 12000，Redis 分片内存 30 秒内从 45% 暴涨到 98%，触发 **OOM 强制淘汰**，缓存命中率从 99.6% 骤降到 18%。

根因令人警醒——**不是 TTL 到期，而是降级策略反成帮凶**：原设计"Redis 响应超过 50ms 自动切换本地 Caffeine 缓存"，但本地缓存未设合理过期时间，且**各实例独立加载同一热点数据**，形成惊群效应集体穿透数据库。结论一句话：**"逻辑失效"比物理失效更隐蔽**——错误的降级逻辑比不降级更危险（[专题 7](../专题%207：分布式高并发%20&%20限流熔断降级/07-降级与兜底预案：分级设计.md) 的降级边界章节）。

修复方向：放弃"Redis 超时即降级"；本地缓存短 TTL（100ms）仅抗瞬时高峰；Redis 作为主缓存加**随机 TTL 抖动**（防集中失效）；数据库兜底；`hotkeys` 命令 + Grafana 追踪 Top 10 热点。

## 4. 共性根因：穿透、击穿、雪崩三兄弟

三个案例反复出现的三个概念，必须分清：

- **穿透**：查询不存在的数据——缓存与数据库都没有，每次请求直达 DB（攻击手段）；治理：空值缓存、布隆过滤器。
- **击穿**：热点数据失效瞬间高并发回源（案例一）；治理：互斥回源（单线程加载）、逻辑过期。
- **雪崩**：大量 key 同时失效或缓存层整体故障，流量洪峰直达 DB（案例三）；治理：随机 TTL、多级缓存、降级兜底。

三兄弟的共同点：**都是"缓存保护失效 → 数据库被击穿"的路径**——缓存的价值是挡流量，挡不住时的保护（限流、互斥、多级）比缓存本身更重要。

## 5. 治理工具箱

综合三个案例，缓存故障治理的完整工具箱：

- **互斥回源**：缓存失效时单线程加载（Guava `get(key, callable)` / 分布式锁），杜绝惊群；
- **多级缓存**：L1 本地（短 TTL 抗瞬时）+ L2 Redis（主缓存）+ L3 DB（兜底），[专题 5](../专题%205：缓存体系专题/00-总览.md) 的分层架构；
- **热点探测与隔离**：`--hotkeys` + 热点 key 多副本（副本带随机后缀防集中失效）、本地缓存优先；
- **大 Key 治理**：序列化瘦身（Protostuff/Gzip）、分片存储（hash 拆分）、禁止整表缓存；
- **随机 TTL**：`TTL + random(0, 300s)` 防集中失效；
- **容量验证**：缓存结构变更必须大 Key + 高并发压测（[专题 8](../专题%208：架构层面优化%20+%20全链路压测/10-生产实战与自测.md) 的场景清单）；
- **降级边界**：降级策略要防反噬——本地缓存兜底必须短 TTL、可熔断；
- **监控先行**：命中率、大 Key 数量、热点 Top N、Redis 内存水位（预留 20-30% 余量）进监控大盘，命中率骤降即告警——案例三的命中率从 99.6% 掉到 18%，如果当时有命中率告警，30 秒内就能发现而不是等 DB 被打穿。

> 🎯 **核心要点**：三个真实案例覆盖缓存三大死法——大 Key 击穿（1.5MB→17KB 负载降 98%）、热点打满 CPU（23 万次/分钟）、善意降级反噬（命中率 99.6%→18%）；穿透/击穿/雪崩的共同路径是"缓存保护失效→DB 被击穿"；治理工具箱七件套（互斥回源/多级缓存/热点隔离/大 Key 瘦身/随机 TTL/容量验证/降级边界），其中"错误的降级逻辑比不降级更危险"是最深的一课。
