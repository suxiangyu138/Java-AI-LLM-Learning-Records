## 1. 四层排查法：症状、资源、变更、依赖

线上故障定位的第一原则是**先拉时间线缩小故障域，再逐层排查**，四层排查法按顺序走：

- **症状层**：先确认"哪里坏了"——错误码分布、成功率、P99、哪个接口/页面。症状描述要具体（"下单接口成功率 60%，P99 2.3s，从 14:02 开始"），模糊的症状（"系统好像有点卡"）无法定位。
- **资源层**：CPU/内存/IO/线程池/连接池/GC——资源打满是故障的常见表象，`top -H`、jstack、监控大盘先看一圈（资源层往往是"结果"而非"根因"，但能缩小范围）。
- **变更层**：**故障前 30 分钟内的变更是最优先怀疑对象**——发布、配置、DB 变更、流量调整。变更排查必须快（看发布记录/配置 diff），因为发布类故障占线上事故的 50%+（[08 篇](08-发布变更事故与变更管控.md)）。
- **依赖层**：下游服务、Redis/MQ/DB 等依赖是否异常——从调用链路的被依赖方反向排查。

排查顺序不是死板的，但**变更层要第一时间看**——很多团队在症状和资源层绕两小时，才发现 10 分钟前刚发过版。

## 2. JVM 定位工具：jstack 到 Arthas

JVM 问题定位的经典工具组合（详细用法见[专题 1 的剖析工具链](../专题%201：性能理论基础/06-性能剖析工具链.md)与 JVM 体系，本讲给故障场景速查）：

- **jstack**：线程快照——定位死锁（BLOCKED 环）、线程池打满（大量 WAITING/RUNNABLE 堆积）、GC 线程异常。命令 `jstack <pid>` 多看几次对比（每次 1-2 秒间隔），线程状态变化比单次快照更有信息量。
- **jmap -dump**：堆转储——OOM 后必做，用 MAT/VisualVM 分析大对象与泄漏链。
- **jstat**：GC 频率与停顿——`jstat -gcutil <pid> 1000` 观察 FGCT 曲线，Full GC 频繁是 OOM 前兆。
- **JFR**：飞行记录器——低开销录制，事后回放定位慢调用与锁竞争（生产故障后恢复期最实用，无需复现）。
- **Arthas**：线上诊断神器——`thread -n 3`（最忙线程）、`watch`（方法入参返回值）、`trace`（方法耗时拆解），无需重启、无需改动代码。

实战要点：**先拿证据再动手**——jstack 一次不一定抓到问题瞬间，多抓几次对比；线上先保全现场（dump/日志）再重启，重启会毁掉唯一的取证机会。

一个典型的 jstack 判读案例：抓到的线程快照里 80% 线程处于 `WAITING (on object monitor)` 且栈顶是 `HikariCP getConnection`——结论不是"线程池坏了"，而是"数据库连接被占满"（[05 篇](05-真实案例：数据库与慢SQL.md) 的传导链）；如果栈顶是 Dubbo 的 `SocketTimeoutException` 等待，则是下游超时问题。**线程状态 + 栈顶资源 = 根因层**，这是线程快照的核心判读逻辑。

## 3. Redis 定位工具：bigkeys 与 hotkeys

Redis 故障（大 Key、热点 Key）是 2026 年最高频的故障类型（[04 篇](04-真实案例：缓存击穿与热点Key雪崩.md) 全是案例），三个核心命令：

- **`redis-cli --bigkeys`**：大 Key 首轮筛查——扫描各类型最大 key 与数量分布；1.5MB 的双十一事故就是它发现的。
- **`redis-cli --hotkeys`**：热点 Key 定位（需要开启 `maxmemory-policy` 统计或 4.0+ 的 LFU 策略）——会员积分案例靠它找到 23 万次/分钟的热点 key。
- **`INFO commandstats`**：命令调用统计——找出高频/高耗时命令（如 `keys *`、`hgetall` 大 hash）。

配套排查：`top -H -p <redis_pid>` 看单线程 CPU（Redis 单线程，一个慢命令卡住全部）；`INFO persistence`/`INFO memory` 看持久化与内存（大 key 与持久化窗口叠加是经典事故组合）。阻塞命令（keys/慢 Lua）在生产必须禁用——排查时发现 `keys *` 在跑，根因基本就找到了。

## 4. 数据库与链路追踪

- **数据库**：`SHOW PROCESSLIST`（当前会话快照，找长时间 Running 的 SQL）、`EXPLAIN`（执行计划，索引失效/全表扫一眼确认）、`SHOW ENGINE INNODB STATUS`（锁等待与死锁取证）、慢查询日志（`long_query_time` 配置）。数据库故障定位的重点是**找出那条"拖垮一切的 SQL"**——processlist 快照多抓几次，全表扫描的 SQL 特征很明显（Rows_examined 巨大）。
- **链路追踪**（SkyWalking/Zipkin）：跨服务故障归因的第一工具——traceId 串联整条调用链，故障请求的每一跳耗时一目了然（哪个服务慢、哪个依赖超时）；没有链路追踪时，跨服务排障只能靠猜，这是 2026 年监控体系的最低配置。

## 5. 时间线拉齐：定位的第一步

所有定位动作之前，先做**时间线拉齐**——把监控指标、告警、发布记录、值班操作放到同一条时间轴上：

- 告警时间 vs 用户反馈时间 vs 发布时间的先后关系，直接决定怀疑方向（发布在前 → 变更类；告警在前 → 容量/依赖类）。
- 时间线来自监控系统的统一时间源（NTP），否则各系统时间偏差会误导判断。
- 时间线也是复盘的骨架（[01 篇](01-故障复盘方法论：无指责与四步法.md) 的报告模板核心章节）——定位时顺手记录"什么时间做了什么"，复盘时就不用靠回忆。

时间线拉齐还有一个反直觉的用法：**先看"什么没有变"**——如果故障前 30 分钟没有任何发布/配置/流量变更，变更类怀疑直接排除，把精力集中到容量与依赖层；反之命中变更，立即拉变更责任人共同定位。时间线的价值在于快速缩小怀疑域，让四层排查走得更快（本讲的排查顺序即按此组织）。

> 🎯 **核心要点**：四层排查（症状/资源/变更/依赖）中变更层最先看（发布类事故占 50%+）；JVM 工具按场景组合——jstack 抓线程、jmap 保堆现场、jstat 看 GC、Arthas 线上手术，先保全现场再重启；Redis 三命令（--bigkeys/--hotkeys/INFO commandstats）直击大 Key 与热点，禁用阻塞命令；链路追踪是跨服务归因第一工具；一切定位前先拉齐时间线——发布在前怀疑变更，告警在前怀疑容量。
