## 1. MQ 堆积：消费端瓶颈还是生产端洪峰

MQ 故障的经典表象是**消息堆积**，但堆积的根因在两端都有可能，排查第一步是分清方向：

- **生产端洪峰**：瞬时流量超过消费能力（[专题 7 的削峰](../专题%207：分布式高并发%20&%20限流熔断降级/02-扩展模式与容量边界.md) 失效或未设计）——堆积消息是新产生的，消费速率其实正常。处置：扩容消费者、开启削峰限流、评估峰值是否符合预期。
- **消费端瓶颈**：消费逻辑变慢（慢 SQL、下游依赖、死循环）、消费者宕机/缩容、消费异常重试风暴——堆积是"消化不了"。处置：看消费者实例数与消费耗时，查消费逻辑变更（发布类占多数）。
- **特殊形态：积压 + 延迟**——消费失败重试堆积（重试风暴的 MQ 形态，[06 篇](06-真实案例：线程池与分布式锁.md) 的恢复后风暴）。

识别指标：积压量（lag）、消费耗时、消费失败率。处置纪律：**先止血（扩容消费者/暂停生产端/丢非核心消息）再查根因**——堆积不是等来的，分分钟影响下游依赖。

判断生产端还是消费端有一个快速经验：**看堆积的增长斜率与消费耗时曲线**——lag 直线上升而消费耗时正常 = 生产端洪峰（扩容消费者无效，要限流削峰）；lag 上升且消费耗时同时劣化 = 消费端变慢（查消费逻辑与下游依赖）；lag 缓慢上升且消费失败率同步上涨 = 消费重试循环（查异常与死信配置）。三类形态的处置完全不同，先定性再动手是 MQ 排障的第一纪律。

## 2. Redis 阻塞：大 Key、慢命令与持久化

Redis 单线程模型决定"一个慢操作卡住全部请求"（[专题 5](../专题%205：缓存体系专题/00-总览.md) 的 Redis 模型），三类阻塞源：

- **大 Key 操作**：`hgetall`/`lrange` 大 key、大 value 序列化传输——[04 篇](04-真实案例：缓存击穿与热点Key雪崩.md) 的 1.5MB 案例；排查用 `--bigkeys`。
- **慢命令**：`keys *`、`smembers` 大集合、慢 Lua 脚本——阻塞期间所有命令排队；排查用 `INFO commandstats` 与 slowlog。
- **持久化/Fork 阻塞**：`BGSAVE`/`BGREWRITEAOF` 的 fork 在内存大时阻塞主线程（毫秒到秒级）；内存 45%→98% 的案例里 OOM 淘汰与持久化叠加是经典组合（[04 篇](04-真实案例：缓存击穿与热点Key雪崩.md) 案例三）。

识别特征：Redis 延迟突增但 QPS 没变、`INFO` 的 `latest_fork_usec` 巨大、客户端连接堆积。处置：拆分大 key、禁用阻塞命令（生产红线）、持久化窗口错峰、内存治理（预留 20-30% 余量防 OOM 淘汰）。

## 3. 网络抖动与超时链

网络故障的隐蔽性在于：**应用层看到的是超时与重试，网络层才是真相**。三类高频：

- **跨机房/跨云专线抖动**：丢包率上升、RTT 翻倍——链路监控（丢包/延迟）是前置检测手段；
- **连接耗尽**：TIME_WAIT 堆积（短连接风暴）或 CLOSE_WAIT 泄漏（对端关闭未释放）——`ss -s` 一眼定位；
- **TCP 重传风暴**：配置错误（MTU 不一致）、网卡故障——抓包（tcpdump）定论。

处置与防护：**超时链设计**（连接/读/写逐层超时，[专题 7 的超时金字塔](../专题%207：分布式高并发%20&%20限流熔断降级/08-隔离与舱壁：线程池与信号量.md)）；连接池治理（keepalive 复用、连接数监控）；**熔断兜底**（网络抖动时熔断比重试有效——重试放大抖动，熔断快速失败让流量退避）。完整排查方法论见[网络问题排查体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/网络问题排查/00-网络问题排查总览.md)。

## 4. DNS 与证书：看不见的定时炸弹

两类"平时无感、爆炸时全局"的故障：

- **DNS 故障**：解析失败/解析变慢——服务间域名解析全部受影响，表象是"连接超时"且难以定位。典型坑：DNS 缓存 TTL 过长（故障切换不生效）、JVM 的 DNS 缓存（`networkaddress.cache.ttl` 默认缓存成功解析，失败不缓存——故障期间雪上加霜）、容器 DNS 配置错误。
- **证书过期**：HTTPS 证书未续期——用户侧看到"连接不安全"，内部调用（HTTPS 内网）直接失败。典型坑：只监控了域名证书，忘了内网证书、CDN 证书、过期前 30 天无告警。

治理：证书到期监控（30 天/7 天/1 天三级告警，自动续期脚本）；DNS 缓存策略统一（JVM 参数 + 容器配置）；DNS 故障预案（IP 直连/备用域名）。

## 5. 中间件故障排查要点

中间件故障排查的共性方法论三条：

- **症状、资源、变更、依赖四层排查**（[03 篇](03-故障定位工具链.md)）：中间件故障常被误判为应用问题——先确认"中间件自身指标"（延迟/QPS/连接数/内存）再下结论；
- **先拉时间线**：中间件故障与变更（配置/版本/容量）的时序关系是定位钥匙；
- **速查表优先**：[中间件运维故障排查体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/MySQL%20Redis%20MQ%20运维相关故障现象/00-中间件运维故障排查总览.md) 按"现象→排查路径"组织，先查速查表再动手，比现场试错快一个数量级。

> 🎯 **核心要点**：MQ 堆积先分生产/消费端再处置，先止血再查因；Redis 阻塞三大源（大 Key/慢命令/持久化 fork）源于单线程模型，生产禁用阻塞命令；网络故障的表象是超时重试、真相在链路层，熔断比重试更能抗抖动；DNS 与证书是定时炸弹（JVM 缓存坑、证书三级告警）；中间件排查统一走"四层排查 + 时间线 + 速查表"，避免误判为应用问题。
