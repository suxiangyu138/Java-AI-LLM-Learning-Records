## 4. 学习路线推荐

- **入门速成（2-3 天）**：00 → 01 → 02 → 03 → 10。掌握复盘方法、分级响应与定位工具，完成自测。
- **案例深潜（5-7 天）**：入门路线 → 04 → 05 → 06 → 07 → 08。逐案例读"根因→传导→治理"，对照自己系统排查同类隐患。
- **演练专项（1 周+）**：全篇 → 09 混沌工程。建设团队的故障演练体系与演练平台。

## 6. 十大常见误区

1. **复盘就是追责**：指责文化让问题被掩盖，根因永远挖不出来。
2. **复盘文档写完就结束**：行动项完成率低于 50% 的复盘是"复盘表演"，同类事故换个名字再来。
3. **P 级全看业务影响**：数据丢失、监控失效、需要人工干预的险情同样要复盘。
4. **一上来就查根因**：先止血（回滚/限流/扩容）再定位，止血慢了查清根因也没意义。
5. **线程池打满就是根因**：线程池满只是结果，根因在慢 SQL/无超时/重试风暴。
6. **大 Key 是小问题**：一个 1.5MB Key 能击穿双十一，缓存变更必须压测。
7. **降级策略写了就安全**：错误的降级（"Redis 超时就切本地缓存"）会制造惊群反噬。
8. **公共库改一行没事**：影响半径是全局的，必须灰度+压测+可回滚。
9. **混沌工程就是随机破坏**：没有稳态假设与爆炸半径的破坏只是破坏。
10. **故障处理完就完事**：不复盘、不演练，同类事故 12 个月复发率就是你的答案。

## 7. 一周学习计划

- **Day 1**：00 总览 + 01 复盘方法论，重写一次自己经历过的故障复盘。
- **Day 2**：02 分级响应 + 03 工具链，检查自己团队的告警分级与值班手册。
- **Day 3**：04 缓存案例，用 --bigkeys/--hotkeys 检查自己系统的 Redis。
- **Day 4**：05 数据库案例，排查慢 SQL 与连接池传导链。
- **Day 5**：06 线程池案例 + 07 中间件案例，核对重试与超时配置。
- **Day 6**：08 变更管控，梳理发布流程的可回滚性。
- **Day 7**：09 混沌工程 + 10 自测，做一次 GameDay 演练。
