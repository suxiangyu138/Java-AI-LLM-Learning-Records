## 1. ThreadPoolExecutor：七参数与状态机

线程池的价值：**复用线程**（省创建销毁）、**限流**（并发度封顶）、**管理生命周期**（优雅关闭）。七个构造参数缺一不可，逐个说明：

- **corePoolSize**：常驻线程数。低于它时新任务直接建线程（即使有空闲），预热期尤其注意。
- **maximumPoolSize**：线程数上限，超过它任务才进队列（顺序见下节——与直觉相反）。
- **keepAliveTime + unit**：非核心线程空闲回收时间；`allowCoreThreadTimeOut(true)` 可让核心线程也回收。
- **workQueue**：任务缓冲队列。**有界队列是生产底线**（[05 篇](05-JUC同步工具与阻塞队列.md) 选型），无界队列 + 突发流量 = OOM。
- **threadFactory**：必须自定义——命名（`pool-order-1`）+ 非守护 + 异常处理，否则 jstack 里全是一串数字，排查无从下手。
- **handler**：队列满 + 线程数达上限后的拒绝策略。

线程池的运行状态是 5 态状态机（RUNNING/SHUTDOWN/STOP/TIDYING/TERMINATED），`ctl` 用一个 int 的高 3 位存状态、低 29 位存 workerCount——一个 int 原子地装下"状态 + 线程数"，这是并发设计的教科书级技巧。

## 2. execute 源码流程

`execute(Runnable)` 的三步决策顺序（面试必考，顺序反了就是错的）：

```java
public void execute(Runnable command) {
    int c = ctl.get();
    // ① 工作线程数 < corePoolSize → 新建核心线程执行
    if (workerCountOf(c) < corePoolSize)
        addWorker(command, true);
    // ② 否则尝试入队；入队成功且无双关检查问题 → 返回
    else if (isRunning(c) && workQueue.offer(command))
        ... // 二次检查：池关了要移除任务并拒绝；线程数为 0 要补建
    // ③ 入队失败（队列满）→ 尝试建非核心线程；建不了 → 拒绝
    else if (!addWorker(command, false))
        reject(command);
}
```

关键点：**先建线程后入队**（core 满 → 直接建 max 线程？不，顺序是 core 满 → 入队 → 队列满 → 建到 max → 拒绝）。所以"maximumPoolSize 只在队列满时才生效"，合理配置是 core 小 + 有界队列中等 + max 兜底——core 负责常态负载，队列吸收瞬时尖峰，max 是最后防线，拒绝是极限保护。Worker 是线程池的最小执行单元：继承 AQS 实现不可重入锁，循环从队列取任务执行，取不到且超 keepAlive 就退出；任务抛异常时 Worker 会捕获记录后继续取下一个任务——所以"任务异常会杀掉线程池"是误解，真正的问题在异常被吞掉后无感知。

## 3. 拒绝策略

四种内置策略 + 实务选择：

- **AbortPolicy**（默认）：直接抛 `RejectedExecutionException`。生产必配兜底（try-catch 或自定义），裸奔会静默丢任务。
- **CallerRunsPolicy**：由提交线程自己执行任务。**最推荐的兜底**——不会丢任务，同时天然限流（提交线程被任务占用，提交速度自然下降）；副作用是提交线程阻塞，要接受这一点。
- **DiscardPolicy / DiscardOldestPolicy**：静默丢弃，仅适合日志、统计等可丢任务。

生产标准姿势：默认 AbortPolicy 太粗暴，CallerRunsPolicy 会拖慢调用方——实务是自定义策略：**写监控日志 + 报警 + 落盘补偿**（任务入持久化队列，事后重放）。任何策略都要配线程池监控（见下节），拒绝事件必须可观测。

## 4. 参数计算与监控

经验公式（只能做起点，最终靠压测校准）：

- **CPU 密集**：`core = CPU 核数 + 1`（预留系统线程余量）。任务不阻塞，超配只会增加切换。
- **IO 密集**：`core = CPU 核数 × (1 + 等待时间/计算时间)`，或简化为 `核数 × 2` 起步；2026 更优解见下节（虚拟线程）。
- **队列容量**：`max 并发 × 单任务延迟容忍`——比如限流 100 并发、容忍 1 秒延迟、任务 100ms：队列 ≈ 1000。
- **拒绝策略与 max**：max = 峰值并发上限（结合下游能力，如数据库连接池大小）。

监控三件套：线程数（active/poolSize/maxPoolSize）、队列积压（queue.size、queue.remainingCapacity）、拒绝次数。用 Micrometer 指标 + 告警，积压曲线是容量规划的输入。核心池预热用 `prestartAllCoreThreads()`；优雅关闭是三段式：

```java
executor.shutdown();                                // ① 拒绝新任务，存量跑完
if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
    executor.shutdownNow();                         // ② 超时未清空则中断强停
}
```

`shutdownNow` 返回未执行任务列表，配合持久化可做补偿重放——任务"提交后可能没跑"必须可感知。常见坑清单：`shutdown` 后继续 submit 抛 RejectedExecutionException（调用方要有降级）；任务里吞了 InterruptedException 会无视 shutdownNow；线程池对象不 shutdown 导致 JVM 无法退出（线程非守护）。

## 5. ForkJoinPool 工作窃取

ForkJoinPool 是"分治并行"的专用线程池（JDK 7+，Stream.parallel 与 CompletableFuture 默认池）：任务分解为子任务（fork），结果合并（join）；每个工作线程一条**双端任务队列**，自己从头部取，空闲时从**别的线程队列尾部窃取**——这就是工作窃取（work-stealing），天然负载均衡，且窃取失败的概率低（尾部竞争少）。

适用：可递归分解的计算密集任务（大数组排序/聚合、树遍历）。不适合：阻塞 IO 型任务（窃取队列里堆满阻塞任务，线程数小会卡死）。线程数默认 CPU 核数减 1，是"CPU 密集专用"的默认前提。

## 6. 虚拟线程时代：线程池还要吗

2026 的并发版图因为虚拟线程发生了结构性变化：

- **IO 密集任务的线程池被虚拟线程替代**：`Executors.newVirtualThreadPerTaskExecutor()`——每个任务一个虚拟线程，无池化必要（创建近乎免费），`executor.close()`（try-with-resources）等待全部完成。Spring Boot 3.2+ `spring.threads.virtual.enabled=true` 后 Tomcat 即以虚拟线程承载请求（实测 TPS 提升 2-4 倍是常态，见 [08 篇](08-异步编程：Future到虚拟线程.md)）。
- **虚拟线程替代不了线程池的两类场景**：CPU 密集任务（虚拟线程不带来并行度，线程数仍按核数）；需要"限流到固定并发度"的场景（信号量或定长池仍是约束工具）。
- **固定线程池仍存在的理由**：存量代码、显式并发度控制、与现有 Executor 接口的兼容。

结论：**新代码的"线程池"默认是 newVirtualThreadPerTaskExecutor，不是 FixedThreadPool**；传统 Executors 工厂四大坑（FixedThreadPool 无界队列、CachedThreadPool 线程无上限、ScheduledThreadPool 线程数=1 的坑、SingleThread 里藏匿异常）在虚拟线程时代逐一失去存在意义，面试答"选型逻辑"比背参数重要。

> 🎯 **核心要点**：execute 的顺序是"先核后队再扩再拒"；拒绝策略配监控是生产底线；参数公式只是起点，压测校准才可靠；虚拟线程已接管 IO 型并发，线程池退守 CPU 密集与显式限流两大场景。
