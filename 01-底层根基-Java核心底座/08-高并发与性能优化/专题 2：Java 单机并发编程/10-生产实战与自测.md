## 1. 实战一：高并发计数器

需求：接口统计每日调用量，QPS 峰值 2 万，只要求最终值准确。直接 `AtomicLong` 在高竞争下会撞缓存行（[04 篇](04-CAS与原子类.md)），正确答案是 LongAdder：

```java
public class TrafficCounter {
    private final LongAdder count = new LongAdder();
    public void hit()  { count.increment(); }     // 每次请求调用，无锁
    public long total() { return count.sum(); }   // 定时任务落库/上报用
}
```

延伸两个变体：需要"每秒独立计数"用 `ConcurrentHashMap<String, LongAdder>`（key 为时间分片）；需要原子读改写（如发号器）则必须退回 AtomicLong 或数据库序列。

## 2. 实战二：缓存防击穿与防重

需求：热点 key 过期瞬间，1000 个请求同时回源数据库。**单机内防击穿 = 每个 key 一把锁**，用 `computeIfAbsent` 原子完成：

```java
private final ConcurrentHashMap<String, Object> lockMap = new ConcurrentHashMap<>();

public V get(String key) {
    V v = cache.get(key);
    if (v != null) return v;
    // 每个 key 独立锁对象，只阻塞同 key 的请求，互不干扰
    synchronized (lockMap.computeIfAbsent(key, k -> new Object())) {
        v = cache.get(key);              // 双检：第一个线程已回源填充
        if (v == null) { v = loadFromDb(key); cache.put(key, v); }
        lockMap.remove(key);             // 清理锁对象，防 map 无限增长
        return v;
    }
}
```

三个要点：锁对象按 key 分片（粒度正确）；双检防止重复回源（正确性）；用后移除（内存治理）。对"写不常发生"的防重场景（幂等创建），`ConcurrentHashMap.putIfAbsent` 或 `computeIfAbsent` 同样是标准姿势，见 [06 篇](06-并发容器.md) 复合操作节。

## 3. 实战三：批量任务异步编排

需求：根据 1000 个用户 ID 拉取订单并聚合，单次拉取 10ms，串行要 10 秒，要求 2 秒内完成。2026 标准答案是虚拟线程 + 结构化并发（JDK 26 前用 CompletableFuture 过渡，语义等价）：

```java
// 虚拟线程版：每个 ID 一个虚拟线程，语义与同步代码一致
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<List<Order>>> futures = ids.stream()
        .map(id -> executor.submit(() -> orderApi.list(id)))
        .toList();
    for (var f : futures) results.addAll(f.get(3, TimeUnit.SECONDS)); // 带超时
}

// JDK 26 结构化并发版：失败即取消、自动清理
try (var scope = StructuredTaskScope.open()) {
    List<Future<List<Order>>> futures = ids.stream()
        .map(scope::fork).toList();
    scope.join().allSuccessfulOrThrow();
    return futures.stream().map(Future::resultNow).flatMap(List::stream).toList();
}
```

对比 [08 篇](08-异步编程：Future到虚拟线程.md)：虚拟线程版本地复用了同步代码的全部思维——try-with-resources 保证线程资源释放（不再有 ExecutorService 泄漏），超时通过 `get(timeout)` 补上。**不要**用 `Executors.newFixedThreadPool(100)` 硬扛这类任务——并发度、队列、拒绝策略三件事全要自己调，虚拟线程一把梭。

## 4. 工程规范纪律清单

1. **锁纪律**：Lock 一律 try-finally 释放；`tryLock` 失败分支不 unlock；锁内禁止 IO/远程调用；多锁全局统一获取顺序。
2. **线程池纪律**：ThreadFactory 必带业务命名前缀；workQueue 有界；拒绝策略可观测（监控 + 日志）；`Executors` 工厂方法只作了解不作生产；shutdown → awaitTermination → shutdownNow 三段式关闭。
3. **共享状态纪律**：能 final 就 final；需要共享的集合用并发容器而非 `Collections.synchronizedList`（锁粒度粗一个量级）；volatile 只用于标志位。
4. **异步纪律**：CompletableFuture 链尾必有 exceptionally/handle；显式传 Executor；异步任务异常统一记日志（线程内异常默认吞掉）。
5. **上下文纪律**：线程池/虚拟线程内使用 ThreadLocal 必须 remove（或用 [ScopedValue 替代](../../02-JUC%20多线程%20高并发编程/虚拟线程/07-ScopedValue作用域值.md)）；traceId/用户身份传播用显式参数或作用域值。
6. **监控纪律**：线程池指标（active/queue/拒绝数）、LongAdder 计数定时落库、死锁告警（JMX ThreadMXBean 定期检测）。
7. **评审纪律**：并发代码必须过评审，评审重点不是 API 用没用对，而是三问——这个状态能不能不共享？锁内代码能不能再短？等待有没有超时上限？三问都答不出理由的写法一律打回。并发代码是"写出来容易、证对很难"，评审是唯一低成本的验证手段。

## 5. 虚拟线程落地检查单

- [ ] 长阻塞路径无 synchronized（已换 ReentrantLock 或确认 JEP 491 覆盖）；
- [ ] JDBC 驱动版本支持虚拟线程（JDBC 5.0+ / R2DBC），连接池参数按并发数复核；
- [ ] ThreadLocal 审计：清除或迁移 ScopedValue；
- [ ] 阻塞式第三方库（锁/信号量）检查，避免虚拟线程内长时间持锁；
- [ ] 线程池迁移：`newVirtualThreadPerTaskExecutor()` + try-with-resources；
- [ ] 监控补齐：Micrometer 虚拟线程指标（active/yield count）+ JFR 事件；
- [ ] 压测验证：对比迁移前后 TPS/P99/GC，不达预期回滚；
- [ ] 容量复核：虚拟线程数上不封顶，但下游（DB 连接池、外部服务）并发上限仍在——并发度迁移到虚拟线程后，限流手段要跟上（信号量/有界连接池）。

面试呈现三范式：**价值式**——"单机并发是分布式一切问题的缩影，我在单机层面解决过缓存击穿与线程池过载，这些经验直接迁移到微服务限流与降级"；**技术式**——讲 AQS 讲"state + 队列 + park"三件套、讲 CHM 讲"CAS 占位 + 锁桶 + 无锁读"，用骨架不用背源码；**生产式**——讲"线上死锁 jstack 定位 → 锁顺序治理 + 超时兜底 → JMX 探针告警"的完整闭环。简历呈现：项目里写"通过 LongAdder 与分片锁将热点计数吞吐提升 X 倍""迁移虚拟线程后 TPS 提升 2-3 倍、P99 下降 60%"——**量化 + 对比**比罗列 API 有说服力得多。

> 🎯 **核心要点**：本体系的落地标准——计数器用 LongAdder、防击穿按 key 分片锁、异步编排用虚拟线程 + 结构化并发；六条纪律（锁/池/状态/异步/上下文/监控）是生产代码的及格线；20 题全过即毕业。
