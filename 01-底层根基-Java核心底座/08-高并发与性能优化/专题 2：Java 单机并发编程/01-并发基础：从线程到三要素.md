## 1. 线程模型：从平台线程到虚拟线程

进程是资源分配的最小单位，线程是 CPU 调度的最小单位。同一个进程内的线程共享堆内存，各自持有栈、程序计数器与线程局部存储——共享内存正是并发问题的来源，也是解决手段（锁、volatile 都建立在共享内存之上）。

**平台线程**（platform thread）由操作系统调度，每个线程对应一个内核线程，创建成本约 1-2MB 栈空间加内核态分配。一台 8 核服务器线程数开到上千，调度开销与上下文切换就会显著拖慢吞吐，因此历史上"线程池 + 队列"成为标配——线程是昂贵资源，必须复用。

**虚拟线程**（virtual thread）自 JDK 21 转正，是运行在 JVM 内部的轻量线程：没有自己的内核栈，阻塞时自动释放载入线程（carrier），挂起再恢复的成本远低于上下文切换。实测 1 万个平台线程启动约 1850ms、占用约 1.2GB 内存，而 1 万虚拟线程约 12ms、8MB（2026 基准）。虚拟线程不改变编程模型——代码还是顺序阻塞风格，只是"一个任务一个线程"从奢侈变成了常态。它的机制细节见[虚拟线程体系](../../02-JUC%20多线程%20高并发编程/虚拟线程/00-虚拟线程知识体系总览.md)。

## 2. 线程生命周期与关键 API

线程生命周期六态：NEW → RUNNABLE（含 OS 运行/就绪）→ BLOCKED / WAITING / TIMED_WAITING → TERMINATED。日常开发中真正容易踩坑的只有四个 API：

- **interrupt 三件套**：`interrupt()` 只是置中断标志，不会暴力杀线程；`isInterrupted()` 查询标志；`interrupted()` 查询并清除。阻塞中的线程（sleep/wait/join/park）收到中断会抛 `InterruptedException` 并**清除标志**——所以捕获后必须 `Thread.currentThread().interrupt()` 恢复标志，否则调用方无法感知中断。正确的取消协议是：任务循环内检查中断标志，自行退出。
- **join**：等待某线程结束，底层是 wait 机制，可带超时 `join(1000)`。注意 join 只保证"执行完"，不保证结果正确（需配合 volatile 或锁做内存可见性）。
- **daemon**：守护线程随最后一个非守护线程退出而终止，JVM 不会等它。线程池的线程是**非守护**的，这就是为什么 ExecutorService 不 shutdown 时 JVM 无法退出。
- **UncaughtExceptionHandler**：线程内异常不会冒泡到主线程，必须用全局或每线程 handler 记录日志，否则异常被吞掉极难排查。

创建线程的演进：`new Thread`（原始）→ `ThreadFactory` 统一命名 → `Executors.newVirtualThreadPerTaskExecutor()`（虚拟线程工厂，2026 生产标配）。直接 new Thread 的三个问题——无复用、无上限、无命名规范——是线程池与线程工厂存在的全部理由。

## 3. 上下文切换与并发指标

上下文切换 = 保存当前线程寄存器/程序计数器/栈指针，加载下一个线程的现场，再经历 TLB 失效、缓存冷启动。一次切换耗时约微秒级，看似小，但每秒切换上万次就是秒级 CPU 浪费。**锁竞争导致的阻塞切换比 CPU 时间片切换更昂贵**，因为伴随了互斥等待与线程唤醒（park/unpark 内核交互）。

衡量并发质量的三个指标：

- **吞吐量**（throughput）：单位时间完成任务数。提升手段：减少临界区、提升并发度。
- **延迟**（latency）：单任务完成时间。二者常此消彼长（批处理提高吞吐但增加单任务等待）。
- **可伸缩性**（scalability）：加资源后吞吐提升的比率。Amdahl 定律给出上限：加速比 = 1/(串行比例 + 并行比例/核数)——**串行部分就是不可逾越的天花板**，锁和共享状态都属于串行部分，所以"消灭锁"比"优化锁"高一个维度。

## 4. 并发三要素：原子性、可见性、有序性

并发正确的全部问题收敛为三个字：**原子、可见、有序**。

- **原子性**：一个操作不可被线程调度打断。`i++` 在字节码层是读-改-写三步，任何一步都可能被其他线程插足，这就是竞态条件。保障手段：synchronized/Lock 互斥，或 CAS 无锁更新。
- **可见性**：线程 A 修改了共享变量，线程 B 不一定立刻看到。原因有两层：CPU 多级缓存（L1/L2/L3，写后可能暂存在核心私有缓存）；编译/CPU 重排序（store 缓冲）。`volatile` 与锁都能建立可见性——写入后强制刷新到内存并失效其他核心缓存行。
- **有序性**：为了流水线优化，指令可能重排，只要不违反单线程 as-if-serial 语义。但跨线程时重排会破坏直觉：经典的单例双重检查锁若不加 volatile，可能出现"引用非空但构造未完成"（先赋引用后执行构造）。

三要素不是三个孤立问题：**锁同时解决三要素**（互斥 + 释放锁时刷新内存 + 临界区不重排出界），**volatile 只解决可见性与有序性，不解决原子性**——这就是 `volatile int count` 执行 `count++` 依然丢更新的原因。JMM 用 happens-before 规则把"哪些顺序可见"变成可判断的契约，完整推导见 [JMM 体系](../../03-JVM完整底层/JMM/00-JMM知识体系总览.md)。

## 5. 为什么并发编程难

并发 bug 难在三个特征：**偶发**（依赖时序，压测才现形）、**无上下文**（崩溃时现场已被其他线程改写）、**不可复现**（换个 CPU 核心数就消失）。其根源只有一个：**共享可变状态**。因此并发编程的第一原则不是"学会加锁"，而是"消灭共享"：

1. **不可变优先**：能用 `final` 就不留 setter，不可变对象天然线程安全；
2. **线程封闭**：ThreadLocal 或方法局部变量，把状态关在单线程内；
3. **共享则同步**：确需共享的，用并发容器/锁/原子类，并明确同步契约。

> 🎯 **核心要点**：单机并发的地基是三句话——线程是廉价化资源（虚拟线程时代）但并发问题一点没变少；三要素（原子/可见/有序）是所有并发 bug 的分类框架；消灭共享状态优于任何加锁技巧。
