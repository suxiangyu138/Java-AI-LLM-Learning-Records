## 1. ConcurrentHashMap：CAS + 细粒度同步

ConcurrentHashMap 是并发容器的核心，演进脉络就是 JUC 设计思想的缩影：

- **JDK 7**：Segment 分段锁——把整个表切成 16 段，每段一把 ReentrantLock，写操作只锁所在段，锁竞争被摊薄 16 倍；但段内仍是链表 + 锁，二次哈希与段粒度的取舍复杂。
- **JDK 8 重构**：弃 Segment，改为 **CAS + synchronized 锁桶**——空桶初始化用 CAS 占位，非空桶用 synchronized 锁该桶的头节点，锁粒度从段降到"单桶"；链表长度 ≥ 8 且表长 ≥ 64 时转红黑树，查询从 O(n) 降到 O(logn)。读操作无锁（volatile 读 + 树/链表的读写分离），所以读并发极高。

源码里值得记住的三个设计：

```java
// 1. 空桶 CAS 占位：并发 put 到同一空桶只有一个成功
casTabAt(tab, i, null, new Node<>(hash, key, value));

// 2. 哈希分散：高 16 位参与扰动，避免低 bit 冲突集中
(h ^ (h >>> 16)) & HASH_BITS

// 3. 计数：baseCount + CounterCell[]，高竞争下按 LongAdder 方式分段
addCount(x, 1);
```

完整 put 流程值得跟一遍源码（这是面试讲 CHM 的标准素材）：① 算哈希（扰动函数）；② 空表先 `initTable` 扩容初始化（CAS 竞争 `sizeCtl`，只有一个线程胜出）；③ 目标桶为空 → CAS 直接占位成功即返回；④ 桶非空 → 锁头节点，检查是否 ForwardingNode（在扩容中则帮助迁移）、树或链表分别处理（链表遍历到 key 相同则覆盖，否则尾插）；⑤ 链表长度 ≥ 8 且表长 ≥ 64 → `treeifyBin` 树化；⑥ `addCount` 计数。读路径全无锁——`get` 通过 volatile 读桶引用，树/链表节点在写时以新节点替换，读到的总是某个一致快照。

size 统计是 LongAdder 思路（[04 篇](04-CAS与原子类.md)）：baseCount 加上 CounterCell 分段，`mappingCount()` 才是长整型正确入口（`size()` 有溢出截断历史）。扩容是并发协作的：多个线程发现需要扩容时各自领取一段旧桶迁移（transfer），迁移完的桶用 ForwardingNode 标记——这是"并发系统设计"的绝佳素材。

## 2. CopyOnWrite 系列

CopyOnWriteArrayList/Set 的核心策略：**读不加锁，写时复制**——add/remove 时对整个底层数组做一次快照拷贝，在新数组上修改后原子替换引用（volatile array），读直接读旧数组，永不阻塞、永不读到中间态。

适合"读极多、写极少"的场景：监听器列表、黑白名单、缓存配置项。代价是写 O(n) 拷贝——写频繁时复制开销 + 内存翻倍 + 触发 GC，所以"写占比超过 5%"就该换普通集合加锁。另一个隐性成本：**迭代器是快照**，迭代过程中看不到并发写入，业务若期望"实时看到"会踩坑；且每次写都产生新数组，长期持有的旧引用会拖住大数组无法回收（内存滞留），持有快照引用的代码要尽快释放。

## 3. 无锁队列与跳表

- **ConcurrentLinkedQueue**：完全无锁的 FIFO 队列（CAS 移动 head/tail），吞吐高但**不支持阻塞、size() 是 O(n) 且不精确**。适用"无界、无阻塞、容忍弱一致"的流式场景——比如日志/事件收集，生产端不可阻塞，消费端尽力消费即可。需要阻塞语义（空则等、满则拒）时换阻塞队列（[05 篇](05-JUC同步工具与阻塞队列.md)），两类队列语义不同，混用是 bug 源。
- **ConcurrentLinkedDeque**：双端版本，工作窃取算法的载体（见 [07 篇](07-线程池.md) ForkJoinPool）。
- **ConcurrentSkipListMap/Set**：跳表实现的**有序**并发 Map，支持范围查询（subMap）、按 key 序迭代，写入 O(logn) 无锁化；是"并发下的 TreeMap"唯一选择，也是 ZooKeeper/Kafka 元数据管理背后的结构。跳表用多级索引换查询速度，层数随机生成，平均 O(logn)——比树少一档实现复杂度，且天然适合无锁化（节点插入只 CAS 局部指针）。

弱一致性是它们的共同属性：迭代、size、contains 都可能反映"过去某个时刻"的状态——这不是 bug，是设计取舍，使用时必须有这个预期。作为对比，**普通 HashMap 在并发下连"弱一致"都谈不上**：JDK 7 的 put 扩容头插法并发下会形成环，get 直接死循环拖垮 CPU（JDK 8 改为尾插修复了环，但丢失更新、size 错乱依旧）——"并发下用 HashMap"是没有任何正当理由的反模式。

生产里另一个常见的错误替代品是 `Collections.synchronizedMap(new HashMap())`：它把**所有方法**串行化，读也要全表锁——并发读场景下吞吐比 ConcurrentHashMap 低一个量级，且复合操作（如 get 后 putIfAbsent）依然不原子。结论：Java 生态里并发 KV 只有一个正确选项（ConcurrentHashMap），synchronizedMap 只适合"低并发、小数据、图省事"的存量代码，新代码不要写。

## 4. 容器选型决策

| 场景 | 选择 | 关键理由 |
|---|---|---|
| KV 缓存/映射 | ConcurrentHashMap | 读无锁、写锁桶，通用最优 |
| 读多写极少列表 | CopyOnWriteArrayList | 读零成本，写快照 |
| FIFO 队列（无界无阻塞） | ConcurrentLinkedQueue | 无锁高吞吐 |
| 有界阻塞队列 | ArrayBlockingQueue | 配合线程池有界+拒绝 |
| 有序并发集合 | ConcurrentSkipListMap | 唯一并发有序选择 |
| 计数器/统计 | LongAdder | 高竞争分段 |
| 旧集合（Hashtable/Vector） | 一律不选 | 全表锁，性能差一个量级 |

## 5. "安全容器"的操作边界

并发容器只保证**单方法原子**，不保证**复合操作原子**——这是生产 bug 第一来源：

```java
// 错误：检查-修改两步，中间被其他线程插足
if (!map.containsKey(key)) { map.put(key, value); }

// 正确：容器提供的原子复合方法
map.computeIfAbsent(key, k -> value);   // 原子，且锁桶粒度

// 错误：先 get 再 remove 的"取走"语义
if (map.size() > 0) { Item it = map.remove(firstKey()); }

// 正确：队列的原子取出
BlockingQueue<Item> q = ...; Item it = q.poll(1, SECONDS);
```

实务清单：需要"若不存在则写入"用 `computeIfAbsent`（高并发缓存标准姿势）；需要"取出并删除"用队列的 poll 或 `remove(key, expectedValue)` 条件删除；遍历期间做结构性修改用迭代器提供的 `forEach`/`replaceAll` 原子遍历，或 CopyOnWrite 的快照迭代。"遍历中删除满足条件的元素"有三种姿势：收集待删 key 后统一 remove（两阶段，简单正确）；`entrySet().removeIf(...)`（CHM 提供原子遍历删除）；或 CopyOnWrite 快照迭代。**凡是"先读后写、中间跨多个方法"的逻辑，必须自己上锁**——容器的安全边界到此为止，这正是"线程安全"与"逻辑安全"的分界线。

> 🎯 **核心要点**：ConcurrentHashMap 是"CAS 占位 + 锁桶 + 无锁读 + LongAdder 计数"的集大成者；CopyOnWrite 用空间换读不阻塞；并发容器保证单方法原子，复合操作要靠 computeIfAbsent 这类原子 API 或自行加锁。
