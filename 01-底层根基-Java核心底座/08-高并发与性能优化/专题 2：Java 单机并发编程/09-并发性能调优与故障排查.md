## 1. 并发性能优化的四条路径

并发性能问题本质是**同步开销**与**资源争用**问题，优化路径按性价比排序：

1. **消灭共享**：不可变对象、线程封闭（ThreadLocal）、无状态服务——没有共享就没有同步，这是第一优先且零副作用。
2. **减少临界区**：锁内只留必须原子保护的代码，IO、序列化、远程调用一律挪出锁外——持锁时间决定竞争概率。
3. **降低争用粒度**：读写锁分离、分段/分桶（LongAdder、ConcurrentHashMap 的思路）、无锁化（CAS）。
4. **提升并发度**：线程池参数、虚拟线程、并行分片——但受 Amdahl 定律约束，串行部分不减少，加资源没用。

调优铁律：**先测量后动手**。用压测拿到基线（吞吐/P99），定位热点（火焰图/JFR），针对热点做一处优化，再压测对比。没有基线的"优化"是玄学，并发领域尤其如此——JIT 与锁升级的存在让直觉完全不可靠（见 [02 篇](02-synchronized与volatile深潜.md) 锁消除）。

## 2. 锁粒度优化与无锁化

- **锁分段**：把一个大锁拆成 N 个小锁（分片 key 哈希取模），争用从集中变摊薄。ConcurrentHashMap 锁桶、LongAdder 分段 Cell 都是此思想的量产实现，业务上"按业务 ID 分片加锁"（如订单号取模 64 把锁）是最实用的一招。
- **读写分离**：读多写少场景用 ReadWriteLock/StampedLock（[03 篇](03-显式锁与AQS源码.md)），但写者饥饿要防。
- **无锁化**：单变量用原子类（[04 篇](04-CAS与原子类.md)）；复合状态难无锁，别硬来。
- **避免嵌套锁**：多把锁的获取顺序必须全局一致，否则死锁（银行转账经典案例：先锁 id 小的一方）。

一个判断标准：**锁内代码能不能删成"三条以内的变量操作"？** 能，说明粒度合理；不能，就继续拆。锁内做远程调用是生产事故的头号形态——锁让并发退化为串行，持锁阻塞直接拖垮整个服务。排查这类问题的信号：压测吞吐随线程数增加反而下降、锁的持有时间（JFR Lock Held 事件）远大于临界区代码应有耗时——数据先行，不用靠猜。

## 3. 伪共享与缓存行

伪共享（False Sharing）是隐蔽的性能杀手：CPU 缓存以 64 字节缓存行为单位加载，两个线程各自修改**不同变量**，但两个变量恰好落在同一缓存行——每次写入都互相使对方的缓存行失效，被迫反复重新加载，性能可退化一个数量级。

JUC 源码里到处是应对痕迹：`LongAdder` 的 Cell 标注 `@Contended` 并填充到缓存行边界（JDK 8 起内部 `@jdk.internal.vm.annotation.Contended`）；旧版 ConcurrentHashMap 的 CounterCell 同样 padding。业务侧的两条认知：

- **检测**：jstack 看不出，用 perf/火焰图观察"大量缓存未命中但代码没有锁"；
- **应对**：一般业务无需手工 padding（JVM 参数 `-XX:-RestrictContended` 配合注解），但"把多个高频热变量放进同一个类/数组相邻位置"要警惕——拆开或留 padding。

## 4. 常见并发 bug 模式

- **竞态条件**（read-modify-write 不原子）：计数器、累加、懒加载检查。修复：原子类或锁。
- **可见性丢失**：共享标志位没加 volatile，另一个线程死循环看不到退出信号。修复：volatile + happens-before，或直接交给锁/原子类。
- **逸出发布**（unsafe publication）：对象在构造完成前被其他线程看到（DCL 单例忘加 volatile、构造器里注册监听器）。修复：安全发布手段（volatile/锁/并发容器/静态初始化）。
- **死锁**：互斥 + 占有并等待 + 不可剥夺 + 循环等待。修复：锁顺序一致、tryLock 超时、锁超时后回滚重试。
- **线程泄漏**：线程池不 shutdown、CountDownLatch 计数错、异步任务异常吞掉。修复：生命周期管理 + 异常兜底 + 线程数监控。
- **过载堆积**：无界队列吞掉限流语义，OOM 前先看到的是"队列积压曲线陡增"。修复：有界 + 拒绝策略 + 告警。

## 5. 故障排查工具链

排查三板斧按"从现象到根因"排序：

- **jstack**（首选）：`jstack <pid>` 打线程快照。死锁直接输出 Found one Java-level deadlock；线程卡住看 WAITING/BLOCKED 栈与持锁栈帧；配合 `top -H` 找高 CPU 线程号转 16 进制后 grep。连打三次（间隔几秒）对比，能区分"死循环"（同一栈持续高 CPU）与"阻塞等待"（状态固定 WAITING）。
- **JMX 主动检测**：`ThreadMXBean.findDeadlockedThreads()` 定期扫描并告警——死锁的"事后人工发现"不如"机器自动检测"，监控配置里应常驻这个探针。
- **Arthas**（线上利器）：`thread -n 3` 找最忙线程、`thread --state WAITING` 按状态过滤、`watch` 动态观察方法入参返回值、`jad` 反编译确认线上代码——不重启改参数、在线定位死锁与热点。经典三板斧：先用 `thread -n` 抓 CPU 热点栈，再用 `watch` 盯可疑方法的入参（找"同一个参数反复触发"的竞态），最后 `jad` 核对线上字节码与预期实现是否一致（避免"以为修了其实没发布"）。
- **JFR**（JDK 自带飞行记录器）：`jcmd <pid> JFR.start` 录制后，火焰图看 CPU 热点、锁竞争事件（Java Monitor Blocked / Lock Held）直接给出"哪个锁竞争最激烈"——这是锁优化的数据依据。
- **压测工具**：JMeter/wrk 打基线，配合监控（Micrometer/Prometheus）看线程池指标与 GC——并发性能问题常与 GC 交织（锁竞争 → 对象分配 → GC 压力 → 更慢），定位时要一起看。

排查纪律：**先看监控曲线再抓现场**（积压、线程数、GC 突变是线索）；一次只改一处并保留基线；线上抓 jstack 用 `jstack -l` 带锁信息；Arthas 生产使用注意权限与审计。最后一条心法：并发问题的根因往往不在"出事的线程"而在"别的线程"——看到的是受害者（阻塞/超时），肇事者（持锁不放、状态写错）在另一个栈里，多打几份快照找"谁一直持有锁"比盯着出栈的线程更有效。

> 🎯 **核心要点**：优化四路径按"消灭共享 → 缩小临界区 → 降粒度 → 提并发度"推进，先测量后动手；伪共享藏在缓存行里，JUC 源码的 padding 是现成教材；排查靠 jstack 抓现场、Arthas 在线定位、JFR 给锁竞争数据，缺一不可。
