## 1. 性能测试金字塔

性能测试不是简单的"用 JMeter 怼一下接口看 TPS"，而是一个分层次、分阶段、持续进行的体系化工作。

**性能测试金字塔**：

```
             ┌──────────────┐
             │  生产环境压测  │  ← 最高成本，最接近真实
             │  (Production) │
            ┌┴──────────────┴┐
            │  全链路压测     │  ← 端到端，多系统联动
            │  (E2E)         │
           ┌┴───────────────┴┐
           │  接口压测        │  ← 单服务/单接口，找性能拐点
           │  (API Test)     │
          ┌┴────────────────┴┐
          │ 单元性能测试       │  ← 方法级，代码热点
          │ (Unit/Profiling) │
         ┌┴─────────────────┴┐
         │  代码级 Profiling   │  ← Arthas/JProfiler/async-profiler
         │  (CPU/Memory)     │
         └───────────────────┘
```

| 层次 | 目标 | 工具 | 执行频率 | 成本 |
|:----|------|------|:--------:|:----:|
| **单元性能测试** | 发现方法级性能问题 | JMH、单元测试 | 每次提交 | 低 |
| **接口压测** | 单接口/单服务吞吐极限 | JMeter、wrk、ab | 每次版本迭代 | 中 |
| **全链路压测** | 端到端瓶颈、依赖影响 | JMeter、GoReplay | 大版本发布前 | 高 |
| **生产压测** | 真实流量下的容量评估 | 全链路压测平台 | 大促前 | 最高 |

> 💡 **最佳实践**：从底层向上逐层推进。先通过 JMH 确保热点方法性能达标，再通过 JMeter 找出接口拐点，最后通过全链路压测验证整体容量。跳过层级直接上全链路压测，定位问题会非常困难。

### 1.1 JMH 微基准测试

```java
// JMH (Java Microbenchmark Harness) — JDK 自带的微基准测试工具
@BenchmarkMode(Mode.Throughput)      // 吞吐量模式
@OutputTimeUnit(TimeUnit.SECONDS)    // 每秒
@State(Scope.Thread)
public class StringConcatBenchmark {

    private String a = "Hello";
    private String b = "World";
    private int count = 100;

    @Benchmark
    public String plus() {
        String s = "";
        for (int i = 0; i < count; i++) {
            s += a + b;
        }
        return s;
    }

    @Benchmark
    public String builder() {
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < count; i++) {
            sb.append(a).append(b);
        }
        return sb.toString();
    }

    @Benchmark
    public String buffer() {
        StringBuffer sb = new StringBuffer();
        for (int i = 0; i < count; i++) {
            sb.append(a).append(b);
        }
        return sb.toString();
    }
}
// 运行：java -jar benchmarks.jar
// 结论：StringBuilder > StringBuffer >>> 字符串拼接(+)
```

## 2. JMeter实战

JMeter 是 Apache 开源的性能测试工具，也是目前国内互联网企业使用最广泛的压测工具。

### 2.1 线程组配置

线程组（Thread Group）是 JMeter 中所有请求的载体，核心配置参数如下。

| 参数 | 含义 | 推荐设置 |
|------|------|----------|
| **线程数** | 并发用户数 | 从 50 开始逐步增加 |
| **Ramp-Up 时间** | 线程启动时长(秒) | 线程数 / 10 ~ 线程数 / 5 |
| **循环次数** | 每个线程执行的次数 | 永远 → 在调度器中设置时长 |
| **持续时间** | 测试运行时长(秒) | 至少在 300 秒(5分钟)以上 |

**关于 Ramp-Up 时间的说明**：

```
Ramp-Up = 60 秒，线程数 = 600
→ 每分钟启动 600 个线程
→ 每 100ms 启动 1 个线程
→ 60 秒后全部 600 个线程同时运行

Ramp-Up 太短：启动瞬间流量冲击过大，TPS 看起来低（实际是预热期）
Ramp-Up 太长：先启动的线程执行了很多轮，后启动的才刚开始
推荐值：Ramp-Up = 线程数 / 10
         即 600 线程 = 60 秒启动完成
```

**图形界面配置线程组**：

```xml
<!-- JMeter .jmx 文件中线程组的 XML 配置 -->
<ThreadGroup guiclass="ThreadGroupGui" testclass="ThreadGroup" testname="压测场景-订单查询">
  <stringProp name="ThreadGroup.on_sample_error">continue</stringProp>  <!-- 错误时继续 -->
  <elementProp name="ThreadGroup.main_controller" elementType="LoopController" guiclass="">
    <boolProp name="LoopController.continue_forever">true</boolProp>     <!-- 永远循环 -->
    <stringProp name="LoopController.loops">-1</stringProp>
  </elementProp>
  <stringProp name="ThreadGroup.num_threads">200</stringProp>            <!-- 200 线程 -->
  <stringProp name="ThreadGroup.ramp_time">20</stringProp>               <!-- 20 秒启动 -->
  <longProp name="ThreadGroup.start_time">1730000000000</longProp>
  <longProp name="ThreadGroup.end_time">1730000000000</longProp>
  <boolProp name="ThreadGroup.scheduler">true</boolProp>                 <!-- 开启调度器 -->
  <stringProp name="ThreadGroup.duration">600</stringProp>               <!-- 持续 600 秒 -->
  <stringProp name="ThreadGroup.delay">5</stringProp>                    <!-- 延迟 5 秒启动 -->
</ThreadGroup>
```

### 2.2 HTTP 请求配置

```xml
<!-- GET 请求 -->
<HTTPSamplerProxy guiclass="HttpTestSampleGui" testclass="HTTPSamplerProxy">
  <stringProp name="HTTPSampler.domain">api.example.com</stringProp>
  <stringProp name="HTTPSampler.port">443</stringProp>
  <stringProp name="HTTPSampler.protocol">https</stringProp>
  <stringProp name="HTTPSampler.path">/api/v1/orders/${orderId}</stringProp>
  <stringProp name="HTTPSampler.method">GET</stringProp>
  <boolProp name="HTTPSampler.use_keepalive">true</boolProp>
</HTTPSamplerProxy>

<!-- POST 请求 -->
<HTTPSamplerProxy guiclass="HttpTestSampleGui" testclass="HTTPSamplerProxy">
  <stringProp name="HTTPSampler.domain">api.example.com</stringProp>
  <stringProp name="HTTPSampler.path">/api/v1/orders/create</stringProp>
  <stringProp name="HTTPSampler.method">POST</stringProp>
  <boolProp name="HTTPSampler.postBodyRaw">true</boolProp>
  <elementProp name="HTTPsampler.Arguments" elementType="Arguments">
    <collectionProp name="Arguments.arguments">
      <elementProp name="" elementType="HTTPArgument">
        <stringProp name="Argument.value">
          {"userId": 1001, "productId": 2001, "quantity": 1}
        </stringProp>
      </elementProp>
    </collectionProp>
  </elementProp>
</HTTPSamplerProxy>
```

**HTTP 请求配置要点**：

```text
1. KeepAlive: 必须开启（模拟真实浏览器行为）
2. Timeout: 连接超时 3000ms，响应超时 60000ms
3. 自动重定向: 一般关闭，除非测试重定向场景
4. 同请求一起发送参数: 参数化时使用 CSV 或 __V 函数
5. 文件上传: 使用"文件上传"页签，指定 MIME 类型
6. Header: 必须携带 Content-Type、Authorization、TraceId 等
```

**常见 HTTP Header 配置**：

```text
Content-Type: application/json
Authorization: Bearer ${token}
X-Trace-Id: ${__UUID}
X-Source: jmeter-test             # 压测标记，用于全链路识别
```

### 2.3 常用监听器

| 监听器 | 作用 | 什么时候用 |
|--------|------|----------|
| **聚合报告** | 展示 TPS、平均RT、中位数RT、P90/P95/P99、错误率 | 每次压测必备 |
| **汇总图** | 可视化展示 TPS、RT 随时间变化趋势 | 观察性能拐点 |
| **TPS 图(Transactions per Second)** | 每秒事务数曲线 | 分析吞吐量稳定性 |
| **响应时间图(Response Times Over Time)** | RT 随时间变化曲线 | 发现 RT 毛刺 |
| **断言结果** | 断言成功/失败详情 | 调试断言规则 |

**聚合报告关键指标解读**：

```
Label               #Samples   Avg    Min    Max    StdDev   Error%   Throughput   Received   Sent
订单查询            50000       156    12     3200   45       0.00%    1250.5/sec    125.4     15.3
└── #Samples：总请求数
└── Avg：平均响应时间（ms）
└── Min/Max：最小/最大响应时间（ms）
└── StdDev：标准差（越小表示波动越小）
└── Error%：错误率（必须为 0%，否则查原因）
└── Throughput：吞吐量（TPS）（核心指标）
```

> ⚠️ **不要只关注平均值**：平均 RT 156ms，但 Max 3200ms，说明存在严重的 RT 毛刺。压测报告必须包含 **P99/P999** 数据。JMeter 聚合报告默认没有百分比数据，需要使用"聚合报告"监听器的"保存表头数据"功能，或在报告中手动计算。

**响应时间百分位分析**：

```text
1000ms 以上：体验极差，用户会流失
500~1000ms：体验较差，需要优化
200~500ms： 可接受
100~200ms： 良好
< 100ms：   优秀

P99 = 500ms 意味着 99% 的请求在 500ms 内完成，1% 的用户体验较差
P999 = 2000ms 意味着 0.1% 的请求可能超时
```

### 2.5 断言

**响应断言（Response Assertion）**：

```xml
<ResponseAssertion guiclass="AssertionGui" testclass="ResponseAssertion">
  <collectionProp name="Asserion.test_strings">
    <stringProp name="-1246">"code":200</stringProp>     <!-- 断言响应包含 "code":200 -->
    <stringProp name="-1246">"success":true</stringProp>  <!-- 断言响应包含 "success":true -->
  </collectionProp>
  <stringProp name="Assertion.test_field">ASSERTION_TEXT_RESPONSE</stringProp>
  <boolProp name="Assertion.assume_success">true</boolProp>
  <intProp name="Assertion.test_type">2</intProp>         <!-- 2=包含, 16=正则匹配, 8=等于 -->
</ResponseAssertion>
```

**JSON 断言（JSON Assertion）**：

```xml
<JSONPathAssertion guiclass="JSONPathAssertionGui" testclass="JSONPathAssertion">
  <stringProp name="JSON_PATH">$.code</stringProp>         <!-- JSONPath 表达式 -->
  <stringProp name="EXPECTED_VALUE">200</stringProp>       <!-- 期望值 -->
  <boolProp name="JSONVALIDATION">true</boolProp>          <!-- 开启 JSON 验证 -->
  <boolProp name="EXPECT_NULL">false</boolProp>            <!-- 不允许为 null -->
  <boolProp name="INVERT">false</boolProp>                 <!-- 不取反 -->
</JSONPathAssertion>
```

> 💡 **断言的最佳实践**：
> 1. 先做 HTTP 状态码断言（期望 200）
> 2. 再做 JSON 断言验证业务正确性
> 3. 不要断言过多字段（只断言关键返回值）
> 4. 断言失败的请求计入错误率

### 2.6 JMeter 命令行执行

> ⚠️ **重要**：压测必须使用 CLI（命令行）模式运行！GUI 模式本身会消耗大量资源，压测数据不准确。

```bash
# CLI 模式执行压测
jmeter -n -t test-plan.jmx -l result.jtl -e -o report/

# 参数说明：
#   -n     非 GUI 模式
#   -t     测试计划文件
#   -l     结果文件（.jtl 格式）
#   -e     生成 HTML 报告
#   -o     报告输出目录

# 分布式压测（Master-Slave 模式）
# Slave 节点启动代理
jmeter-server -Dserver.rmi.localport=1099

# Master 节点执行
jmeter -n -t test-plan.jmx -R slave1_ip,slave2_ip -l result.jtl

# 远程执行：指定 IP
jmeter -n -t test-plan.jmx -r -l result.jtl
```

## 3. JMeter压测场景

### 3.1 场景1：单接口 TPS 测试（梯度加压找拐点）

**目标**：找出单接口的吞吐量上限（最高 TPS）和性能拐点。

**方法**：逐步增加并发线程数，观察 TPS 和 RT 的变化。

```text
线程数: 50 → 100 → 200 → 300 → 500 → 800 → 1000
Ramp-Up: 5秒 → 10秒 → 20秒 → 30秒 → 50秒 → 80秒 → 100秒
Duration: 每个梯度运行 5 分钟

预期结果走势：
┌────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│ 50     │ 100    │ 200    │ 300    │ 500    │ 800    │ 1000   │  线程数
│ 980    │ 1950   │ 3800   │ 5200   │ 6500   │ 6800   │ 6700   │  TPS
│ 51     │ 51     │ 52     │ 57     │ 76     │ 117    │ 149    │  RT(ms)
└────────┴────────┴────────┴────────┴────────┴────────┴────────┘
结论：最佳并发数 ≈ 500（TPS 最高且 RT 较低）
     拐点 ≈ 500 线程（超过后 TPS 不再增长，RT 急剧上升）
```

**拐点判断标准**：

| 现象 | 含义 |
|------|------|
| TPS 不再增长（达到天花板） | 系统已达吞吐量上限 |
| RT 急剧上升（超过拐点前的 2~3 倍） | 系统进入过载状态 |
| CPU 保持在 95%+ | CPU 是瓶颈 |
| 错误率 > 0% | 系统已被压垮 |

> 💡 **为什么要梯度加压**：一次性加到 1000 线程可能导致系统瞬间过载崩溃，梯度加压可以找到"恰好让系统跑满"的最优并发度。

### 3.2 场景2：混合场景（模拟真实流量比例）

**目标**：模拟生产环境的真实流量分布，验证系统在真实比例下的表现。

**方法**：根据业务埋点数据或线上监控统计各接口占比，按比例分配线程。

```text
订单查询:  50%    (500 线程)
下单:      10%    (100 线程)
支付:      10%    (100 线程)
商品详情:  20%    (200 线程)
用户登录:  10%    (100 线程)
─────────────────────────────────
总线程数:  100%   (1000 线程)
```

**JMeter 实现——使用 Throughput Controller 控制比例**：

```xml
<!-- 通过 Throughtput Controller 控制流量比例 -->
<ThroughputController guiclass="ThroughputControllerGui" testclass="ThroughputController">
  <stringProp name="ThroughputController.style">0</stringProp>  <!-- 0=百分比, 1=总执行次数 -->
  <stringProp name="ThroughputController.percent">50</stringProp> <!-- 50% 的线程执行此分支 -->
  <stringProp name="ThroughputController.maxThroughput">0</stringProp>
</ThroughputController>
```

### 3.3 场景3：稳定性压测（7x24 小时长时间运行）

**目标**：验证系统长时间运行的稳定性，发现内存泄漏、连接泄露、Full GC 频繁等"慢病"。

**配置**：

```text
线程数: 200（最佳 TPS 的 60~80%）
持续时间: ≥ 24 小时（最好 7 天）
Ramp-Up: 30 秒
```

**监控关键指标变化趋势**：

| 指标 | 正常趋势 | 异常趋势 | 问题 |
|------|----------|----------|------|
| TPS | 平稳（±5% 波动） | 持续下降 | 存在内存泄漏或资源泄露 |
| RT | 平稳 | 逐渐升高 | GC 频繁 / 连接池耗尽 |
| Full GC 频率 | 低（数小时一次） | 持续上升 | 堆内存出现泄漏 |
| 线程数 | 稳定 | 持续增长 | 线程泄漏 |
| 连接池 | 稳定 | 连接数持续增长 | 连接未释放 |

```bash
# 稳定性压测期间定期采集 JVM 数据
while true; do
  # JVM 堆内存
  jmap -heap <pid> >> jvm_$(date +%Y%m%d_%H%M).log

  # Full GC 情况
  jstat -gcutil <pid> 5000 1 >> gc_$(date +%Y%m%d).log

  # 线程转储
  jstack -l <pid> >> thread_$(date +%Y%m%d_%H%M).log

  sleep 300  # 每 5 分钟采集一次
done
```

> ⚠️ **稳定性压测的常见发现**：
> 1. Redis 连接池未释放 → 连接耗尽
> 2. HTTP 连接池未关闭 → TIME_WAIT 堆积
> 3. ThreadLocal 未 remove → 内存泄漏
> 4. 日志框架异步队列积压 → OOM
> 5. SQL 慢查询逐渐增多 → 数据库连接被占满

### 3.4 场景4：秒杀场景（突发流量冲击）

**目标**：模拟瞬间流量洪峰，观察系统的限流、削峰、熔断机制是否正常工作。

**配置**：

```text
线程数: 2000
Ramp-Up: 0 秒          ← 瞬间全部启动！
持续时间: 120 秒
循环次数: 1            ← 每个线程只请求一次（模拟真实秒杀）
```

**验证点**：

```text
1. 限流是否生效 → 预期大多数请求返回"系统繁忙"
2. MQ 削峰是否生效 → 下游以恒定 TPS 处理
3. Redis 预扣库存是否准确 → 最终库存 = 初始库存 - 成功订单数
4. 系统是否被压垮 → 压测结束后恢复能力
```

**观察重点**：

| 观察项 | 预期行为 | 异常行为 |
|--------|----------|----------|
| 网关限流 | 返回 429（Too Many Requests） | 请求穿透到下游 |
| Redis 库存 | 原子扣减，精确无误 | 超卖（库存减为负数） |
| MQ 队列 | 先陡增后平稳消费 | MQ 消息膨胀导致 OOM |
| DB 压力 | 稳定在 100% TPS 以内 | QPS 飙升拖垮 DB |

### 3.5 报告解读

压测完成后，最核心的工作是**解读报告数据**。

**关键指标速查**：

| 指标 | 优秀 | 良好 | 需关注 | 危险 |
|:----|:---:|:----:|:------:|:----:|
| **TPS（吞吐量）** | 符合预期 | 接近预期 | 低于预期50% | 极低或无 |
| **平均 RT** | < 100ms | < 200ms | < 500ms | > 1000ms |
| **P99 RT** | < 200ms | < 500ms | < 1000ms | > 3000ms |
| **错误率** | 0% | < 0.1% | < 1% | > 1% |
| **CPU** | < 50% | < 70% | < 90% | > 90% |
| **内存** | 稳定 | 略微增长 | 持续增长 | 内存泄漏 |

**异常曲线识别**：

```
TPS 抖动曲线（锯齿状）：GC 频繁或任务定时触发
    ┌──┐    ┌──┐    ┌──┐
 ───┘  └────┘  └────┘  └───

RT 毛刺曲线：Full GC 或外部依赖超时
    ──┐─────┐─────┐──
   ──┘     ┘     └─────

TPS 持续下降曲线：内存泄漏或连接池耗尽
    ┌───
   ┌┘
  ┌┘
 ┌┘
─┘
```

## 4. 压测环境搭建

### 4.1 压测环境 vs 生产环境

| 对比项 | 压测环境 | 生产环境 | 差异影响 |
|:-------|:--------:|:--------:|:---------|
| **服务器配置** | 通常低于生产 | 正式配置 | 压测 TPS 不能直接推生产（需换算） |
| **数据量** | 少量 | 海量 | 索引效果、查询性能差异大 |
| **数据分布** | 均匀 | 倾斜 | 热点数据测试不准 |
| **网络带宽** | 受限 | 充足 | 可能测出网络瓶颈而非服务瓶颈 |
| **依赖服务** | Mock 或精简 | 完整 | 忽略下游瓶颈可能漏测 |

> 💡 **压测环境要求**：最理想是与生产环境配置 1:1（全镜像）。如果成本受限，至少要保证**数据量级一致**，且**无外部依赖的 Mock 行为**。

### 4.2 压测数据准备

**数据规模要求**：

```text
数据量 = 线上核心表行数 × (80%~100%)

必须保证：
1. 索引区分度与线上一致（数据量级要接近）
2. 热点数据分布与线上一致（比如头部 20% 的商品占据 80% 的流量）
3. 避免"新表无数据，查询全部走全表扫描"的问题
```

**准备压测数据**：

```sql
-- 生成 100 万条测试订单数据
INSERT INTO t_order (id, user_id, order_no, amount, status, create_time)
SELECT
    generate_series(1, 1000000),
    round(random() * 100000)::int,
    'ORD' || LPAD(generate_series(1, 1000000)::text, 12, '0'),
    (random() * 1000)::decimal(10,2),
    CASE WHEN random() > 0.9 THEN 'PAID' ELSE 'CREATED' END,
    now() - (random() * interval '365 days')
FROM generate_series(1, 1000000);

-- 创建测试数据脚本
-- 使用存储过程或数据生成工具（DataFactory / 自研脚本）
```

### 4.3 数据隔离方案

压测流量产生的数据必须与生产数据严格隔离。常用方案有三种。

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|:----|------|------|------|----------|
| **影子表** | 同一库中创建同名+前缀的表（`t_order_test`） | 不需额外数据库，清理方便 | 影响主库性能 | 大部分业务适用 |
| **影子库** | 独立数据库，表结构与生产一致 | 完全隔离，不影响生产 | 成本高 | 金融、交易核心 |
| **逻辑隔离** | 在现有字段加 `test_flag` 标记 | 不需要新表 | 业务入侵，清理易遗漏 | 辅助验证 |

**影子表方案实现**：

```text
压测请求 → Header(X-Source: jmeter-test)
    ↓
网关识别压测标签 → 传递到下游
    ↓
ORM 拦截器根据标签改写 SQL
    ┌─ 正常请求: INSERT INTO t_order VALUES (...)
    └─ 压测请求: INSERT INTO t_order_test VALUES (...)
    ↓
压测结束后: DROP TABLE t_order_test;  -- 一键清理
```

### 4.4 压测流量标记

为了保证压测数据不污染生产环境，需要在压测流量的入口处打上标记，并让标记穿透整个链路。

**JMeter 端添加压测标识**：

```xml
<HeaderManager guiclass="HeaderPanel" testclass="HeaderManager">
  <collectionProp name="HeaderManager.headers">
    <elementProp name="" elementType="Header">
      <stringProp name="Header.name">X-Source</stringProp>
      <stringProp name="Header.value">jmeter-test</stringProp>
    </elementProp>
    <elementProp name="" elementType="Header">
      <stringProp name="Header.name">X-Trace-Id</stringProp>
      <stringProp name="Header.value">TEST_${__UUID}</stringProp>
    </elementProp>
  </collectionProp>
</HeaderManager>
```

**服务端识别**：

```java
// 方案1：过滤器识别压测标记
@Component
public class TestFlagFilter implements Filter {

    private static final String TEST_HEADER = "X-Source";
    private static final String TEST_VALUE = "jmeter-test";

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
        HttpServletRequest req = (HttpServletRequest) request;
        String source = req.getHeader(TEST_HEADER);
        if (TEST_VALUE.equals(source)) {
            TestFlagHolder.set(true);  // 标记当前请求为压测流量
        }
        try {
            chain.doFilter(request, response);
        } finally {
            TestFlagHolder.clear();
        }
    }
}

// ThreadLocal 传递压测标识
public class TestFlagHolder {
    private static final ThreadLocal<Boolean> HOLDER = new ThreadLocal<>();

    public static boolean isTest() {
        return Boolean.TRUE.equals(HOLDER.get());
    }

    public static void set(boolean flag) {
        HOLDER.set(flag);
    }

    public static void clear() {
        HOLDER.remove();
    }
}
```

**MyBatis 拦截器自动路由影子表**：

```java
@Component
@Intercepts({
    @Signature(type = Executor.class, method = "update", args = {MappedStatement.class, Object.class})
})
public class ShadowTableInterceptor implements Interceptor {

    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        if (!TestFlagHolder.isTest()) {
            return invocation.proceed();
        }

        MappedStatement ms = (MappedStatement) invocation.getArgs()[0];
        String sql = ms.getBoundSql(invocation.getArgs()[1]).getSql();
        String newSql = sql.replace("t_order", "t_order_test");  // 替换为影子表

        // 创建新的 MappedStatement
        // ... 省略复杂实现

        return invocation.proceed();
    }
}

```

> 💡 **数据隔离最佳实践**：使用 MyBatis-Plus 或 ShardingSphere 的数据脱敏/影子库功能，可以更优雅地实现压测数据隔离。

## 5. 全链路压测

### 5.1 流量录制（GoReplay / TCPCopy）

全链路压测的第一步是获取"真实流量"。通过流量录制工具捕获生产环境的请求，回放到压测环境。

| 工具 | 原理 | 优点 | 缺点 |
|:----|------|------|------|
| **GoReplay** | 代理 HTTP 流量，复制到压测环境 | 简单，支持 HTTP 协议 | 不支持 RPC 协议（Dubbo/gRPC） |
| **TCPCopy** | 复制 TCP 请求到压测服务器 | 底层协议，支持多协议 | 配置复杂，需关注 iptables |

**GoReplay 流量录制与回放**：

```bash
# 1. 在生产环境录制流量（不阻塞正常请求）
# 监听 80 端口，将请求复制到压测环境
gor --input-raw :80 --output-http "http://staging-api:8080|80%"

# 2. 录制到文件保存
gor --input-raw :80 --output-file requests.gor

# 3. 从文件回放
gor --input-file requests.gor --output-http "http://staging-api:8080"

# 4. 回放时添加压测标记 Header
gor --input-file requests.gor \
    --output-http "http://staging-api:8080" \
    --http-set-header "X-Source: jmeter-test"
```

> ⚠️ **重要**：流量回放时要**过滤写请求**（POST/PUT/DELETE），或在回放时自动路由到影子表/影子库，避免压测数据污染生产。

### 5.2 全链路压测架构

```
┌─────────────────────────────────────────────────────────────────────┐
│                          全链路压测平台                               │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────────┐  │
│  │ 压测发起  │ →  │ 流量控制  │ →  │ 数据收集  │ →  │ 报告生成     │  │
│  │ JMeter   │    │ 熔断/限流 │    │ 全链路监控 │    │ 自动化分析   │  │
│  └──────────┘    └──────────┘    └──────────┘    └──────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
         │                  │                    │
         ↓                  ↓                    ↓
    ┌─────────┐      ┌─────────┐          ┌─────────┐
    │ API网关  │      │ 业务服务  │          │ 基础组件  │
    │ Nginx   │      │ 服务A~Z  │          │ MySQL   │
    │ Spring GW│     │         │          │ Redis   │
    │         │      │         │          │ MQ      │
    │         │      │         │          │ ES      │
    └─────────┘      └─────────┘          └─────────┘
         │                                         │
         └─────────────────────────────────────────┘

```

**全链路压测数据流**：

```text
压测平台发起请求
    ↓ (携带 X-Source: jmeter-test)
API 网关识别压测流量
    ↓
网关将压测标记写入 Header 传递到下游
    ↓
服务 A 识别标记 → DB 操作走影子表
    ↓ (RPC 调用传递标记)
服务 B 识别标记 → MQ 消息投递到影子 Topic
    ↓
MQ Consumer 识别标记 → 处理结果写入影子库
```

### 5.3 压测风险控制

全链路压测风险极高——压测流量一旦失控可能直接打垮生产环境。

**风险控制三板斧**：

**第一板斧：熔断兜底**

```java
// 压测流量专用熔断
public class StressTestCircuitBreaker {
    // 如果压测导致系统指标超过阈值，自动熔断压测流量
    private static final double CPU_THRESHOLD = 0.85;   // CPU > 85%
    private static final double MEMORY_THRESHOLD = 0.90; // 内存 > 90%
    private static volatile boolean circuitOpen = false;

    public static boolean isCircuitOpen() {
        if (circuitOpen) return true;  // 已经熔断

        OperatingSystemMXBean osBean = ManagementFactory.getPlatformMXBean(
            OperatingSystemMXBean.class);
        double cpu = osBean.getSystemLoadAverage() / osBean.getAvailableProcessors();
        double memory = (Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory())
            / (double) Runtime.getRuntime().maxMemory();

        if (cpu > CPU_THRESHOLD || memory > MEMORY_THRESHOLD) {
            circuitOpen = true;
            log.warn("[压测熔断] 系统指标超标! CPU={}, Memory={}", cpu, memory);
            return true;
        }
        return false;
    }
}

// 在拦截器中使用
if (TestFlagHolder.isTest() && StressTestCircuitBreaker.isCircuitOpen()) {
    response.setStatus(503);
    response.getWriter().write("{\"code\":503,\"msg\":\"压测熔断，请降低压力\"}");
    return;
}
```

**第二板斧：流量逐级放大**

```text
阶段1: 5% 流量（验证链路可用性）
    → 检查：影子表写入正常、监控数据正常、错误率为 0%
阶段2: 30% 流量（验证中等压力）
    → 检查：各服务 CPU < 70%、RT < 300ms、无 Full GC
阶段3: 70% 流量（接近生产极限）
    → 检查：发现瓶颈、记录 TPS 上限
阶段4: 100%+ 流量（突破系统极限）
    → 检查：限流/熔断机制是否正常触发
```

**第三板斧：一键降级**

```text
压测过程中如出现异常（如监控大盘显示异常），立即执行：
1. 网关层：Nginx 拒绝 X-Source: jmeter-test 请求
2. 服务层：标记位全局关闭压测模式
3. 数据层：回滚影子表/影子库
4. 恢复：降低并发后重新压测
```

## 6. 性能瓶颈定位流程

压测发现了问题（RT 高、TPS 低、错误率上升），下一步就是找到根因。这里有一套标准的定位流程。

```
压测发现 RT 毛刺 / TPS 不达标
    ↓
1. Arthas trace 定位慢方法    ← 找到耗时最长的代码
    ↓
2. jstack 看线程状态         ← 看线程在等待什么
    ↓
3. top 看 CPU / 内存         ← 资源层面确认瓶颈
    ↓
4. 监控看 DB / Redis         ← 看中间件是否有延迟或慢查询
    ↓
5. 逐步优化                  ← 对症下药
    ↓
6. 重新压测验证              ← 是否改善
```

### 6.1 Arthas trace 定位慢方法

Arthas 是阿里开源的 Java 诊断工具，`trace` 命令可以追踪方法的调用链和耗时。

```bash
# 启动 Arthas
java -jar arthas-boot.jar <pid>

# 1. trace 一个接口，看哪些子调用耗时最长
trace com.example.service.OrderService getOrderDetail

# 输出示例：
# `---[52.36% 180.1234ms ] com.example.service.OrderService:getOrderDetail()
#     +---[0.12% 0.2157ms ] com.example.service.OrderService:validate()
#     +---[85.36% 153.7211ms] com.example.service.OrderService:queryUser()
#     |   `---[100% 153.7211ms] com.example.service.UserService:getById()
#     |       `---[98% 150.6458ms] com.example.dao.UserMapper:selectByPrimaryKey()
#     |           `---[96% 144.62ms] 慢查询SQL（数据库耗时）
#     +---[8.12% 14.6231ms] com.example.service.OrderService:queryItems()
#     +---[6.40% 11.5222ms] com.example.service.OrderService:assemble()
#
# 结论：UserService.getById() 的 DB 查询占用了 153ms（85%），是最慢的环节

# 2. 查看方法的调用次数和耗时分布
monitor com.example.service.UserService getById -c 5

# 3. 查看方法的入参和返回值
watch com.example.service.UserService getById "{params,returnObj}" -x 2
```

### 6.2 jstack 看线程状态

```bash
# 1. 查看 Java 进程
jps -l

# 2. 导出线程堆栈
jstack -l <pid> > thread_dump.txt

# 3. 查看线程状态分布
grep "java.lang.Thread.State" thread_dump.txt | sort | uniq -c

# 输出示例：
#    23 java.lang.Thread.State: BLOCKED        ← 阻塞等待锁
#    42 java.lang.Thread.State: RUNNABLE       ← 正常执行
#    15 java.lang.Thread.State: TIMED_WAITING  ← 定时等待（正常）
#     8 java.lang.Thread.State: WAITING        ← 永久等待

# 4. 查看 BLOCKED 线程正在等待什么锁
grep -A 10 "BLOCKED" thread_dump.txt

# 5. 找到 CPU 消耗最高的线程
top -H -p <pid>        # 查看哪个线程 CPU 最高
printf "%x\n" <tid>    # 转成十六进制
jstack <pid> | grep -A 30 "<十六进制tid>"  # 查看该线程的堆栈
```

**线程状态快速诊断**：

| 状态 | 可能原因 | 排查方向 |
|------|----------|----------|
| **大量 BLOCKED** | 锁竞争激烈 | 查看锁对象，优化锁粒度 |
| **大量 WAITING** | 线程池耗尽或死锁 | 检查线程池配置，排查死锁 |
| **大量 RUNNABLE** | CPU 密集型或 GC 频繁 | 查看 CPU 占用和 GC 日志 |
| **TIMED_WAITING** | 大部分正常（sleep/wait/timeout） | 检查超时时间是否合理 |

### 6.3 top 看 CPU / 内存

```bash
# 1. 查看系统整体负载

# 输出解读：

# 2. 按 CPU 排序查看进程

### 6.5 性能瓶颈定位速查表

| 现象 | 常见原因 | 排查工具 | 解决方案 |
|:----|:---------|:---------|:---------|
| **CPU 高，TPS 低** | 死循环、频繁 GC、序列化开销大 | `top`、`jstack`、async-profiler | 优化热点代码、减少对象创建 |
| **RT 毛刺** | Full GC、网络抖动、依赖超时 | GC 日志、Arthas trace | 调优 GC 参数、加超时重试 |
| **TPS 上不去** | 锁竞争、线程数太少、DB 连接不够 | jstack（BLOCKED）、连接池监控 | 优化锁、调整线程池/连接池 |
| **错误率上升** | 超时、限流、依赖服务故障 | 错误日志、监控大盘 | 超时重试、熔断降级、扩容 |
| **内存持续增长** | 内存泄漏（ThreadLocal、缓存无上限） | `jmap -histo`、Heap dump 分析 | 修复泄漏点、限制缓存大小 |
| **IO 等待高** | 磁盘读写慢、DB 慢查询 | `iostat`、慢查询日志 | 索引优化、SSD 升级、批量读写 |

## 7. 性能优化验证闭环

性能优化不是"改完就算完"，必须形成**验证闭环**——优化前有基线，优化后有对比，收益要量化。

### 7.1 优化闭环流程

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 建立基线   │ →  │ 定位瓶颈   │ →  │ 实施优化   │ →  │ 再次压测   │ →  │ 收益记录   │
│ (压测)    │    │ (分析)    │    │ (修改)    │    │ (验证)    │    │ (文档)    │
└──────────┘    └──────────┘    └──────────┘    └──────────┘    └──────────┘
                                                                       │
                                                           ┌───────────┘
                                                           ↓
                                                  是否达到目标？
                                                  ├── 是 → 闭环完成，记录文档
                                                  └── 否 → 返回第二步继续优化
```

  P99 RT:      210ms        ↓ 45%
  P999 RT:     450ms        ↓ 51%
  Error%:      0.00%       ↓ 0.02%
  CPU 平均:    45%          ↓ 27%
  内存:        52%          ↓ 13%
  Full GC:     0次/小时     ↓ 2次
  DB CPU:      18%          ↓ 17%
  Redis CPU:   8%           ↓ 4%

收益量化:
  - TPS 提升 81%，可支撑更大业务量
  - RT 降低 45%，用户体验显著改善
  - CPU 降低 27%，可节省服务器成本约 1/3
  - 无 Full GC，系统稳定性大幅提升
```

### 7.4 持续优化原则

| 原则 | 说明 |
|:-----|------|
| **一次只改一个变量** | 每次优化只做一个修改，分别验证效果后再进行下一个 |
| **保持压测条件一致** | 环境、数据量、并发模型、持续时间必须与基线一致 |
| **收益小于 5% 不值得** | 微优化投入产出比低，集中精力解决主要矛盾 |
| **记录全量配置** | 每次压测的 JVM 参数、线程池大小、连接池参数都记录 |
| **沉淀为技术文档** | 优化经验文档化，团队共享，避免重复踩坑 |

### 8.3 压测报告检查清单

提交报告前对照以下清单逐项确认：

- [ ] 是否明确了测试目标（可量化的指标）

- [ ] 是否描述了测试场景和数据准备方式
- [ ] 是否提供了 TPS / RT / 错误率的原始数据和趋势图
- [ ] 是否分析并标出了性能拐点
