## 1. 线程池深度配置

线程池是Java并发编程中最基础也最容易被滥用的工具。绝大多数性能问题和线上故障都源于线程池配置不当。

### 1.1 ThreadPoolExecutor 核心参数详解

```java
public ThreadPoolExecutor(
    int corePoolSize,      // 核心线程数
    int maximumPoolSize,   // 最大线程数
    long keepAliveTime,    // 非核心线程空闲存活时间
    TimeUnit unit,         // 存活时间单位
    BlockingQueue<Runnable> workQueue, // 任务队列
    ThreadFactory threadFactory,       // 线程工厂
    RejectedExecutionHandler handler   // 拒绝策略
)
```

| 参数 | 含义 | 说明 |
|------|------|------|
| **corePoolSize** | 核心线程数 | 即使空闲也不会被回收的线程数量 |
| **maximumPoolSize** | 最大线程数 | 线程池能容纳的最大线程数量 |
| **keepAliveTime** | 空闲存活时间 | 超出 corePoolSize 的线程空闲多久后被回收 |
| **workQueue** | 任务队列 | 线程数超过 corePoolSize 时，新任务放入队列等待 |
| **threadFactory** | 线程工厂 | 创建线程的工厂，建议自定义以便区分线程来源 |
| **handler** | 拒绝策略 | 队列和线程池都满了时的处理策略 |

**线程池执行流程**：

```
提交任务
    ↓
核心线程 < corePoolSize？ → 是 → 创建新线程执行
    ↓ 否
任务队列未满？ → 是 → 入队等待
    ↓ 否
当前线程数 < maximumPoolSize？ → 是 → 创建新线程执行
    ↓ 否
执行拒绝策略
```

> ⚠️ **常见误区**：很多人以为"先创建核心线程 → 核心线程满了直接创建非核心线程 → 满了才入队"。实际上流程是"核心线程 → 入队 → 非核心线程 → 拒绝"。队列是**在核心线程满后、非核心线程创建之前**用来缓冲的。

### 1.2 四种拒绝策略对比

| 策略 | 类名 | 行为 | 适用场景 |
|------|------|------|----------|
| **抛异常** | `AbortPolicy` | 直接抛出 `RejectedExecutionException` | 默认策略，业务要求必须处理 |
| **调用者执行** | `CallerRunsPolicy` | 由提交任务的线程自己执行 | 降低任务提交速度，天然的负反馈调节 |
| **丢弃最老** | `DiscardOldestPolicy` | 丢弃队列中最老的任务，然后重试提交 | 允许丢弃非关键任务 |
| **静默丢弃** | `DiscardPolicy` | 直接丢弃任务，不抛异常 | 不重要、可丢失的任务 |

```java
// 自定义拒绝策略：告警 + 落盘
RejectedExecutionHandler alertHandler = (r, executor) -> {
    log.error("线程池已满！活跃: {}, 队列: {}, 拒绝任务: {}",
        executor.getActiveCount(), executor.getQueue().size(), r.toString());
    // 将任务写入磁盘，后续补偿处理
    saveToDisk(r);
};

ThreadPoolExecutor executor = new ThreadPoolExecutor(
    10, 20, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(1000),
    new ThreadFactoryBuilder().setNameFormat("biz-pool-%d").build(),
    alertHandler
);
```

> 💡 **CallerRunsPolicy 的负反馈机制**：当线程池满时，任务由提交线程（通常是 Tomcat 线程）执行，Tomcat 线程被占用无法处理新请求，从而自然降低上游请求速度——这是一种优雅的自保护。

### 1.3 线程池参数公式

#### CPU 密集型

**特征**：计算为主，CPU 利用率高，几乎没有等待（如图像处理、加密解密）。

```java
// 公式：Ncpu + 1
int cpuCores = Runtime.getRuntime().availableProcessors(); // 8
executor = new ThreadPoolExecutor(
    cpuCores + 1, cpuCores + 1,  // 8 + 1 = 9
    0L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(100)
);
```

#### IO 密集型

**特征**：存在大量阻塞等待（如数据库查询、远程RPC调用、文件读写），CPU 利用率低。

```java
// 公式：2 * Ncpu
// 或更精确的：Ncpu * (1 + 等待时间/计算时间)
executor = new ThreadPoolExecutor(
    2 * cpuCores, 2 * cpuCores,  // 16
    60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(500)
);
```

#### 混合型

同时包含 CPU 计算和 IO 等待的任务，最佳线程数需要根据**等待时间与计算时间的比率**动态调整。

```java
// 精确公式：Nthreads = Ncpu * Ucpu * (1 + W/C)
// Ncpu = CPU核心数, Ucpu = 目标CPU利用率, W = 等待时间, C = 计算时间
// 例如：8核, 目标80%, 等待时间100ms, 计算时间20ms
// Nthreads = 8 * 0.8 * (1 + 100/20) = 8 * 0.8 * 6 = 38.4 ≈ 40
int optimalThreadCount = (int) (cpuCores * 0.8 * (1 + waitTime / computeTime));
```

| 类型 | 参考公式 | 队列建议 | 典型示例 |
|------|----------|----------|----------|
| **CPU 密集型** | `Ncpu + 1` | `SynchronousQueue` 或小队列 | 数据加密、视频编码 |
| **IO 密集型** | `2 * Ncpu` | `LinkedBlockingQueue` 大队列 | 数据库操作、HTTP 调用 |
| **混合型** | `Ncpu * Ucpu * (1 + W/C)` | 根据场景调整 | 业务流程编排 |

### 1.4 动态线程池（美团 DynamicTP 思路）

美团开源的 DynamicTP 实现了线程池参数的**动态调整**和**实时监控**，解决了传统线程池配置固定、调优困难的问题。

**核心能力**：

```
配置中心(Nacos/Apollo)
    ↓ 动态推送
动态线程池（实时调整 corePoolSize、maximumPoolSize、queueCapacity、keepAliveTime）
    ↓
监控平台（实时展示活跃线程数、队列积压、拒绝次数）
```

**自定义动态线程池示例**：

```java
@Data
public class DynamicThreadPool {
    private String poolName;
    private ThreadPoolExecutor executor;

    public DynamicThreadPool(String poolName, int core, int max, int queueSize) {
        this.poolName = poolName;
        this.executor = new ThreadPoolExecutor(
            core, max, 60L, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(queueSize),
            new ThreadFactoryBuilder().setNameFormat(poolName + "-%d").build()
        );
    }

    // 动态调整核心线程数
    public void updateCorePoolSize(int newCore) {
        executor.setCorePoolSize(newCore);
        log.info("[动态线程池] {} corePoolSize: {} → {}", poolName, executor.getCorePoolSize(), newCore);
    }

    // 动态调整最大线程数
    public void updateMaximumPoolSize(int newMax) {
        executor.setMaximumPoolSize(newMax);
        log.info("[动态线程池] {} maximumPoolSize: {} → {}", poolName, executor.getMaximumPoolSize(), newMax);
    }

    // 动态调整队列容量（通过重写 offer 实现）
    public void updateQueueCapacity(int newCapacity) {
        // 需要自定义 BlockingQueue 支持动态调整
        log.info("[动态线程池] {} queueCapacity: {}", poolName, newCapacity);
    }
}
```

### 1.5 线程池监控

没有监控的线程池就是黑盒。当线上出现接口超时、CPU 飙升时，线程池的实时数据是最关键的定位线索。

```java
public class ThreadPoolMonitor {
    private final ThreadPoolExecutor executor;
    private final String poolName;

    public ThreadPoolMonitor(String poolName, ThreadPoolExecutor executor) {
        this.poolName = poolName;
        this.executor = executor;
        // 启动监控定时任务
        ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);
        scheduler.scheduleAtFixedRate(this::printMetrics, 0, 5, TimeUnit.SECONDS);
    }

    public void printMetrics() {
        log.info("""
            线程池[{}] 监控数据:
              活跃线程数: {}
              核心线程数: {}
              最大线程数: {}
              队列当前大小: {}
              队列剩余容量: {}
              已完成任务数: {}
              总任务数: {}
              活跃线程占比: {}%
            """,
            poolName,
            executor.getActiveCount(),
            executor.getPoolSize(),
            executor.getLargestPoolSize(),
            executor.getQueue().size(),
            executor.getQueue().remainingCapacity(),
            executor.getCompletedTaskCount(),
            executor.getTaskCount(),
            String.format("%.1f", executor.getActiveCount() * 100.0 / executor.getMaximumPoolSize())
        );
    }
}
```

| 监控指标 | 获取方法 | 告警阈值 | 异常含义 |
|----------|----------|:--------:|----------|
| **活跃线程数** | `getActiveCount()` | > maximumPoolSize * 90% | 线程池即将耗尽 |
| **当前线程数** | `getPoolSize()` | 接近 maximumPoolSize | 创建了大量线程 |
| **队列积压** | `getQueue().size()` | > 队列容量 * 80% | 消费速度跟不上生产速度 |
| **已完成任务** | `getCompletedTaskCount()` | 长时间不增长 | 任务可能卡住了 |
| **拒绝次数** | 自定义计数器 > 0 | > 0 | 系统过载，任务被丢弃 |

> ⚠️ **线上事故案例**：某公司将 `newFixedThreadPool(10)` 配合无界队列 `LinkedBlockingQueue<>()` 用于文件上传。高并发时队列堆积数百万个任务，导致内存 OOM，服务宕机半小时。**永远不要用无界队列，永远要设置拒绝策略+监控告警**。

## 2. CompletableFuture异步编程

CompletableFuture 是 Java 8 引入的异步编程利器，解决了 Future 不支持回调、无法编排的痛点。Java 9 后又增加了超时控制等能力。

### 2.1 核心 API 全景图

```
CompletableFuture 核心方法分类：

├── 创建异步任务
│   ├── supplyAsync(Supplier)       → 有返回值
│   ├── runAsync(Runnable)          → 无返回值
│   └── completedFuture(value)      → 创建已完成的Future
│
├── 任务转换（同步转换，同线程执行）
│   ├── thenApply(Function)         → 转换结果（类比 Stream.map）
│   ├── thenAccept(Consumer)        → 消费结果，无返回值
│   └── thenRun(Runnable)           → 任务完成后执行，不需要结果
│
├── 任务组合（异步编排，可换线程）
│   ├── thenCompose(Function)       → 扁平化组合（类比 flatMap）
│   ├── thenCombine(CompletableFuture, BiFunction) → 合并两个独立任务结果
│   ├── allOf(CompletableFuture...)  → 所有任务都完成
│   └── anyOf(CompletableFuture...)  → 任意一个任务完成
│
├── 结果处理
│   ├── exceptionally(Function)     → 异常时返回默认值
│   ├── handle(BiFunction)          → 无论成功与否都处理（可恢复）
│   └── whenComplete(BiConsumer)    → 无论成功与否都处理（不可恢复）
│
└── 超时控制（Java 9+）
    ├── orTimeout(timeout, unit)    → 超时则抛出 TimeoutException
    └── completeOnTimeout(value, timeout, unit) → 超时则返回默认值
```

### 2.2 thenApply vs thenCompose 区别

```java
// thenApply: 返回 U（结果转换）
CompletableFuture<String> future = CompletableFuture
    .supplyAsync(() -> "hello")
    .thenApply(s -> s + " world");         // 返回 CompletableFuture<String>

// thenCompose: 返回 CompletableFuture<U>（扁平化）
CompletableFuture<String> future = CompletableFuture
    .supplyAsync(() -> "hello")
    .thenCompose(s -> CompletableFuture
        .supplyAsync(() -> s + " world"));  // 返回 CompletableFuture<String>
// ⚠️ 如果 Function 内部又返回一个 CompletableFuture，必须用 thenCompose 避免嵌套
```

| 方法 | 返回类型 | 函数内异步 | 类比 Stream |
|------|----------|:----------:|:-----------:|
| `thenApply` | `CompletableFuture<U>` | 否 | `map` |
| `thenCompose` | `CompletableFuture<U>` | 是 | `flatMap` |
| `thenCombine` | `CompletableFuture<V>` | 是（两个并行） | — |
| `allOf` | `CompletableFuture<Void>` | 是（多个并行） | — |

### 2.3 线程池隔离

> ⚠️ **重要**：`supplyAsync()` / `runAsync()` 如果不指定 Executor，默认使用 `ForkJoinPool.commonPool()`。如果所有业务共用一个线程池，一个接口慢会导致所有接口都受影响。

```java
// 不同业务使用独立线程池实现隔离
@Configuration
public class ThreadPoolConfig {

    @Bean("orderExecutor")
    public ThreadPoolExecutor orderExecutor() {
        return new ThreadPoolExecutor(
            10, 20, 60L, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(500),
            new ThreadFactoryBuilder().setNameFormat("order-pool-%d").build(),
            new ThreadPoolExecutor.CallerRunsPolicy()
        );
    }

    @Bean("userExecutor")
    public ThreadPoolExecutor userExecutor() {
        return new ThreadPoolExecutor(
            5, 10, 60L, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>(200),
            new ThreadFactoryBuilder().setNameFormat("user-pool-%d").build(),
            new ThreadPoolExecutor.AbortPolicy()
        );
    }
}
```

```java
@Service
public class OrderDetailService {
    @Autowired @Qualifier("orderExecutor") private ThreadPoolExecutor orderExecutor;
    @Autowired @Qualifier("userExecutor") private ThreadPoolExecutor userExecutor;

    public OrderDetail getOrderDetail(Long orderId) {
        // 订单查询线程组 — 使用 orderExecutor
        CompletableFuture<Order> orderFuture = CompletableFuture
            .supplyAsync(() -> orderService.getOrder(orderId), orderExecutor);
        CompletableFuture<List<OrderItem>> itemsFuture = CompletableFuture
            .supplyAsync(() -> itemService.getItems(orderId), orderExecutor);

        // 用户查询线程组 — 使用 userExecutor（与订单线程池隔离）
        CompletableFuture<User> userFuture = orderFuture
            .thenComposeAsync(order ->
                CompletableFuture.supplyAsync(
                    () -> userService.getUser(order.getUserId()), userExecutor
                ), orderExecutor
            );

        // 支付查询线程组 — 使用 orderExecutor
        CompletableFuture<Payment> paymentFuture = CompletableFuture
            .supplyAsync(() -> paymentService.getPayment(orderId), orderExecutor);

        return CompletableFuture
            .allOf(orderFuture, itemsFuture, userFuture, paymentFuture)
            .thenApply(v -> assemble(
                orderFuture.join(), itemsFuture.join(),
                userFuture.join(), paymentFuture.join()))
            .join();
    }
}
```

> 💡 **线程池隔离原则**：按业务领域划分线程池（订单池、用户池、库存池），不同领域的异步任务互不影响。一个池子慢了，其他池子的任务仍然正常执行。

### 2.4 异常处理

CompletableFuture 的异常处理有三种方式，它们的行为和适用场景不同。

| 方法 | 异常时是否可恢复 | 正常时是否触发 | 是否可改变结果类型 |
|------|:----------------:|:--------------:|:------------------:|
| `exceptionally` | 是（返回默认值） | 否 | 是 |
| `handle` | 是（可恢复） | 是 | 是 |
| `whenComplete` | 否（无法恢复） | 是 | 否 |

```java
// exceptionally：异常时提供默认值
CompletableFuture<Integer> future = CompletableFuture
    .supplyAsync(() -> 1 / 0)  // 抛出 ArithmeticException
    .exceptionally(e -> {
        log.error("计算异常", e);
        return 0;               // 返回默认值
    });
// 结果: 0

// handle：无论正常异常都处理，可恢复
CompletableFuture<Integer> future = CompletableFuture
    .supplyAsync(() -> {
        if (Math.random() > 0.5) throw new RuntimeException("随机失败");
        return 100;
    })
    .handle((result, ex) -> {
        if (ex != null) {
            log.error("执行失败", ex);
            return -1;           // 异常时返回默认值
        }
        return result * 2;       // 正常时转换结果
    });

// whenComplete：主要用于副作用（日志、监控），不能改变结果
CompletableFuture<Integer> future = CompletableFuture
    .supplyAsync(() -> 100)
    .whenComplete((result, ex) -> {
        if (ex != null) {
            log.error("异步任务异常", ex);  // 只能记录，不能恢复
        } else {
            log.info("异步任务成功: {}", result);
            monitor.recordSuccess();
        }
    });
// whenComplete 的返回值与上游相同，异常会继续传播
```

### 2.5 超时控制（Java 9+）

```java
// orTimeout：超时抛出 TimeoutException
CompletableFuture<Order> future = CompletableFuture
    .supplyAsync(() -> orderService.getOrder(orderId), executor)
    .orTimeout(3, TimeUnit.SECONDS);
// 3秒内未完成 → TimeoutException

// completeOnTimeout：超时返回默认值
CompletableFuture<Order> future = CompletableFuture
    .supplyAsync(() -> orderService.getOrder(orderId), executor)
    .completeOnTimeout(defaultOrder, 3, TimeUnit.SECONDS);
// 3秒内未完成 → 返回 defaultOrder（不抛异常）
```

> ⚠️ **Java 8 兼容方案**：如果项目使用 Java 8，可以通过 `get(timeout, unit)` 实现超时，但会阻塞调用线程。

```java
// Java 8 超时方案
CompletableFuture<Order> future = CompletableFuture
    .supplyAsync(() -> orderService.getOrder(orderId), executor);
try {
    Order order = future.get(3, TimeUnit.SECONDS); // 阻塞等待，最多3秒
} catch (TimeoutException e) {
    future.cancel(true); // 超时后取消任务
    order = defaultOrder; // 返回兜底数据
}
```

### 2.6 实战：并发调用3个微服务聚合结果

这是一个典型的微服务编排场景：用户请求一个页面，需并发调用3个下游服务，将结果聚合后返回。

```java
@Service
public class ProductDetailService {

    @Autowired @Qualifier("bizExecutor") private ThreadPoolExecutor executor;

    public ProductDetailVO getProductDetail(Long productId) {
        long start = System.currentTimeMillis();

        // Step 1: 并发调用3个微服务
        CompletableFuture<ProductInfo> infoFuture = CompletableFuture
            .supplyAsync(() -> productClient.getInfo(productId), executor);

        CompletableFuture<List<Review>> reviewFuture = CompletableFuture
            .supplyAsync(() -> reviewClient.getReviews(productId), executor);

        CompletableFuture<Inventory> inventoryFuture = CompletableFuture
            .supplyAsync(() -> inventoryClient.getStock(productId), executor);

        // Step 2: 聚合结果，最多等待 2 秒
        ProductDetailVO result = CompletableFuture
            .allOf(infoFuture, reviewFuture, inventoryFuture)
            .thenApplyAsync(v -> {
                ProductDetailVO vo = new ProductDetailVO();
                vo.setInfo(infoFuture.join());
                vo.setReviews(reviewFuture.join());
                vo.setInventory(inventoryFuture.join());
                return vo;
            }, executor)
            .completeOnTimeout(buildPartialResult(infoFuture.join()), 2, TimeUnit.SECONDS)
            .exceptionally(e -> {
                log.error("获取商品详情异常, productId={}", productId, e);
                return buildFallback(productId);
            })
            .join();

        log.info("商品详情聚合完成, productId={}, 耗时={}ms",
            productId, System.currentTimeMillis() - start);
        return result;
    }

    // 超时时返回部分结果（已有数据不浪费）
    private ProductDetailVO buildPartialResult(ProductInfo info) {
        ProductDetailVO vo = new ProductDetailVO();
        vo.setInfo(info);
        vo.setReviews(Collections.emptyList());
        vo.setInventory(new Inventory(0, "未知"));
        return vo;
    }

    // 完全失败时返回兜底数据
    private ProductDetailVO buildFallback(Long productId) {
        ProductDetailVO vo = new ProductDetailVO();
        vo.setInfo(new ProductInfo(productId, "商品信息获取失败"));
        vo.setReviews(Collections.emptyList());
        vo.setInventory(new Inventory(0, "未知"));
        return vo;
    }
}
```

> 🎯 **核心要点**：CompletableFuture 的威力在于编排——`allOf` 并行执行、`thenApply` 聚合结果、`completeOnTimeout` 优雅超时、`exceptionally` 兜底容错。配合独立线程池，可以构建高性能、高可用的异步服务。

## 3. ForkJoinPool与并行流

### 3.1 ForkJoinPool 原理

ForkJoinPool 是 Java 7 引入的**分治并行框架**，核心思想是将大任务递归拆分成小任务（Fork），子任务完成后合并结果（Join）。

**工作窃取（Work-Stealing）算法**：

```
┌───────────────────────────────────────────────────────────┐
│  线程1 队列: [任务A1] [任务A2] [任务A3]                     │
│  线程2 队列: [任务B1]                                      │  ← 线程2空闲，从线程1队尾窃取任务
│  线程3 队列: (空闲)                                        │  ← 从线程2或线程1队尾窃取任务
└───────────────────────────────────────────────────────────┘
```

| 特性 | 说明 |
|------|------|
| **分治模型** | 大任务递归拆解为子任务，并行执行后合并 |
| **工作窃取** | 空闲线程从其他线程的任务队列尾部"窃取"任务执行 |
| **双端队列** | 每个工作线程拥有一个双端队列（Deque），头部为自有任务，尾部可被窃取 |
| **适用场景** | 计算密集型、可拆分的任务（排序、矩阵运算、树遍历） |

### 3.2 自定义 ForkJoinTask

```java
// 使用 ForkJoinPool 计算 1 到 1_000_000 的和
public class SumTask extends RecursiveTask<Long> {
    private static final long THRESHOLD = 10_000;  // 拆分阈值
    private final long[] numbers;
    private final int start;
    private final int end;

    public SumTask(long[] numbers, int start, int end) {
        this.numbers = numbers;
        this.start = start;
        this.end = end;
    }

    @Override
    protected Long compute() {
        int length = end - start;
        if (length <= THRESHOLD) {
            // 小任务：直接计算
            long sum = 0;
            for (int i = start; i < end; i++) {
                sum += numbers[i];
            }
            return sum;
        }
        // 大任务：拆分为两个子任务
        int mid = start + length / 2;
        SumTask leftTask = new SumTask(numbers, start, mid);
        SumTask rightTask = new SumTask(numbers, mid, end);

        leftTask.fork();          // 异步执行左子任务
        long rightResult = rightTask.compute();  // 当前线程执行右子任务
        long leftResult = leftTask.join();        // 等待左子任务结果

        return leftResult + rightResult;
    }

    public static void main(String[] args) {
        long[] numbers = new long[1_000_000];
        Arrays.fill(numbers, 1);

        ForkJoinPool pool = new ForkJoinPool();  // 默认并行度 = CPU核心数
        long result = pool.invoke(new SumTask(numbers, 0, numbers.length));
        System.out.println("Sum: " + result);  // 1000000
    }
}
```

### 3.3 parallelStream 的坑

`Collection.parallelStream()` 默认使用 `ForkJoinPool.commonPool()`，其并行度 = `Runtime.getRuntime().availableProcessors() - 1`。

**问题一：共用线程池导致互相干扰**

```java
// 两个不同的并行流共用同一个线程池
List<Integer> list1 = Arrays.asList(1, 2, 3, 4, 5, 6, 7, 8);
List<Integer> list2 = Arrays.asList(10, 20, 30, 40, 50, 60, 70, 80);

// 任务A：使用 commonPool
CompletableFuture.runAsync(() -> {
    list1.parallelStream()
        .forEach(i -> {
            sleep(1000);  //模拟耗时操作
            System.out.println("Task A: " + i);
        });
});

// 任务B：也使用 commonPool，会与任务A争抢线程
list2.parallelStream()
    .forEach(i -> {
        sleep(1000);
        System.out.println("Task B: " + i);
    });
// 结果：两个任务相互阻塞，总耗时比预期长得多
```

**问题二：Blocking 操作导致线程池耗尽**

```java
// 如果 parallelStream 内部包含阻塞操作（如 RPC 调用）
IntStream.range(0, 100)
    .parallel()
    .forEach(i -> {
        Order order = orderService.getOrder(i);  // 阻塞等待
        // ... 如果 commonPool 只有 7 个线程，所有线程都阻塞时，系统会卡死
    });
```

> ⚠️ **commonPool 的致命问题**：如果并行流内的任务包含阻塞操作（网络 IO、DB 查询），所有工作线程都阻塞时，系统会陷入"貌似卡死"的状态——因为没有人能帮他们窃取任务。**不要在 parallelStream 中使用阻塞操作**。

### 3.4 自定义 ForkJoinPool 隔离

```java
// 创建自定义 ForkJoinPool，避免干扰 commonPool
ForkJoinPool customPool = new ForkJoinPool(
    16,                         // 并行度
    ForkJoinPool.defaultForkJoinWorkerThreadFactory,
    null,                       // 异常处理器
    false                       // 非异步模式
);

// 在自定义池中执行并行流
try {
    customPool.submit(() ->
        list.parallelStream()
            .filter(item -> expensiveFilter(item))
            .collect(Collectors.toList())
    ).get();
} finally {
    customPool.shutdown();
}
```

> 💡 **最佳实践**：对于 IO 密集型的并行流操作，始终使用自定义 ForkJoinPool，并行度设置为 `2 * Ncpu`。对于 CPU 密集型任务，使用默认的 commonPool 即可。

## 4. 锁优化实战

### 4.1 synchronized 升级路径

Java 6 对 synchronized 进行了重大优化，引入了**偏向锁→轻量级锁→重量级锁**的升级路径，使其性能在低并发场景下甚至优于 ReentrantLock。

```
无锁
  ↓ 线程第一次获取锁
偏向锁（Biased Locking）— 锁对象头 Mark Word 记录线程ID
  ↓ 有其他线程竞争
轻量级锁（Lightweight Locking）— CAS 自旋获取锁
  ↓ 自旋超过阈值 或 线程数超过CPU核心数/2
重量级锁（Heavyweight Locking）— 操作系统 Mutex，线程阻塞
```

| 锁状态 | 开销 | 适用场景 | 何时升级 |
|--------|:----:|----------|:--------:|
| **偏向锁** | 极低（仅一次 CAS） | 单线程重复获取同一锁 | 另一线程竞争时 |
| **轻量级锁** | 低（CAS 自旋） | 多线程交替执行，无竞争 | 自旋超过阈值 |
| **重量级锁** | 高（线程阻塞+唤醒） | 多线程激烈竞争 | 自旋失败 |

```java
// 查看锁升级过程（JVM 参数）
// -XX:+PrintBiasedLockingStatistics
// -XX:BiasedLockingStartupDelay=0  // 关闭偏向锁延迟（默认4秒后开启）

// 关闭偏向锁优化（高并发场景下推荐）
// -XX:-UseBiasedLocking
```

> 💡 **Java 15+** 默认禁用了偏向锁（因为偏向锁的撤销成本在某些场景下较高）。如果你的 JDK 版本 >= 15，不需要再考虑偏向锁的优化问题。

### 4.2 Lock / ReadWriteLock / StampedLock 选择

```java
// ReentrantLock：独占锁，功能最全
Lock lock = new ReentrantLock(true); // true = 公平锁
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock();
}

// ReadWriteLock：读写分离，读读不互斥
ReadWriteLock rwLock = new ReentrantReadWriteLock();
rwLock.readLock().lock();   // 读锁：多个线程可同时读
try {
    // 读操作
} finally {
    rwLock.readLock().unlock();
}

rwLock.writeLock().lock();  // 写锁：独占
try {
    // 写操作
} finally {
    rwLock.writeLock().unlock();
}

// StampedLock：Java 8引入，支持乐观读
StampedLock stampedLock = new StampedLock();
long stamp = stampedLock.tryOptimisticRead(); // 乐观读（无锁）
int data = this.data;  // 读取数据
if (!stampedLock.validate(stamp)) {   // 检查期间是否有写操作
    stamp = stampedLock.readLock();    // 升级为悲观读锁
    try {
        data = this.data;
    } finally {
        stampedLock.unlockRead(stamp);
    }
}
```

| 锁 | 读读互斥 | 写写互斥 | 读写互斥 | 乐观读 | 可重入 | 适用场景 |
|:---|:--------:|:--------:|:--------:|:------:|:------:|----------|
| **synchronized** | 是 | 是 | 是 | 否 | 是 | 简单同步需求 |
| **ReentrantLock** | 是 | 是 | 是 | 否 | 是 | 需要超时/中断/公平锁 |
| **ReadWriteLock** | 否 | 是 | 是 | 否 | 是 | 读多写少 |
| **StampedLock** | 否 | 是 | 是 | 是 | 否 | 读极多写极少，高性能 |

```java
// StampedLock 乐观读 — 性能最高的读操作（无锁无阻塞）
public class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    // 写操作 — 使用悲观写锁
    void move(double deltaX, double deltaY) {
        long stamp = sl.writeLock();
        try {
            x += deltaX;
            y += deltaY;
        } finally {
            sl.unlockWrite(stamp);
        }
    }

    // 读操作 — 乐观读（完全无锁）
    double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();
        double currentX = x, currentY = y;
        if (!sl.validate(stamp)) {        // 有写操作干扰
            stamp = sl.readLock();         // 降级为悲观读锁
            try {
                currentX = x;
                currentY = y;
            } finally {
                sl.unlockRead(stamp);
            }
        }
        return Math.sqrt(currentX * currentX + currentY * currentY);
    }
}
```

> 💡 **StampedLock 特别适合**：读操作远多于写操作的场景（如缓存），且读操作能容忍短暂的脏读。它的乐观读完全不阻塞写线程，吞吐量极高。

### 4.3 锁粗化 / 锁消除 / 锁分段

#### 锁粗化（Lock Coarsening）

JVM 将多个连续的加锁-解锁操作合并为一次，减少锁的获取/释放开销。

```java
// JVM 会自动优化为：
// synchronized (lock) {
//     sb.append("a");
//     sb.append("b");
//     sb.append("c");
// }
StringBuffer sb = new StringBuffer(); // StringBuffer的方法都是synchronized的
sb.append("a");
sb.append("b");
sb.append("c");
```

#### 锁消除（Lock Elimination）

JVM 通过逃逸分析发现锁对象不会逃逸出线程，直接消除锁。

```java
public void concat(String a, String b) {
    // JVM 分析发现 sb 只在这个方法内部使用，不会逃逸
    // 消除 StringBuffer 内部的锁
    StringBuffer sb = new StringBuffer();
    sb.append(a).append(b);
}
```

#### 锁分段（Lock Striping）

将一个大锁拆分成多个小锁，每个锁保护一段数据，降低锁竞争。典型代表是 ConcurrentHashMap 的实现方式。

```java
// 分段锁示例：实现一个高并发的计数器
public class StripedCounter {
    private final int stripes = 16;
    private final AtomicLong[] counters = new AtomicLong[stripes];

    public StripedCounter() {
        for (int i = 0; i < stripes; i++) {
            counters[i] = new AtomicLong(0);
        }
    }

    // 根据 key 的哈希值决定使用哪个计数器
    public void increment(String key) {
        int stripe = Math.abs(key.hashCode() % stripes);
        counters[stripe].incrementAndGet();
    }

    public long total() {
        long sum = 0;
        for (AtomicLong counter : counters) {
            sum += counter.get();
        }
        return sum;
    }
}
```

| 优化手段 | 谁负责 | 原理 | 效果 |
|----------|:------:||------|:----:|
| **锁粗化** | JIT 编译器 | 合并相邻的同步块 | 减少锁获取次数 |
| **锁消除** | JIT 编译器+逃逸分析 | 检测不会逃逸的锁 | 完全消除同步开销 |
| **锁分段** | 开发者 | 一个大锁拆多个小锁 | 降低锁竞争粒度 |

### 4.4 死锁排查

死锁是并发编程中最严重的故障之一，一旦发生，相关线程永久阻塞，服务不可用。

**死锁产生的四个必要条件**：

```
1. 互斥：资源一次只能被一个线程占用
2. 持有并等待：线程持有资源，同时等待其他资源
3. 不可剥夺：资源只能由持有者主动释放
4. 循环等待：多个线程形成环形等待链
```

**典型死锁场景**：

```java
public class DeadLockExample {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        // 线程1：先拿 lockA，再拿 lockB
        new Thread(() -> {
            synchronized (lockA) {
                sleep(100); // 确保线程2拿到 lockB
                synchronized (lockB) {
                    System.out.println("Thread 1 got both locks");
                }
            }
        }).start();

        // 线程2：先拿 lockB，再拿 lockA（注意顺序与线程1相反！）
        new Thread(() -> {
            synchronized (lockB) {
                sleep(100);
                synchronized (lockA) {
                    System.out.println("Thread 2 got both locks");
                }
            }
        }).start();
    }
}
```

**排查步骤**：

第一步，使用 `jps` 找到 Java 进程 ID：

```bash
jps -l
# 输出: 12345 com.example.DeadLockExample
```

第二步，使用 `jstack` 查看线程堆栈：

```bash
jstack -l 12345
```

第三步，在输出中搜索 `deadlock`：

```
Found 1 deadlock.

"Thread-1":
  waiting to lock monitor 0x00007f... (object at 0x000000076...)
  which is held by "Thread-0"

"Thread-0":
  waiting to lock monitor 0x00007f... (object at 0x000000076...)
  which is held by "Thread-1"

Found 1 deadlock.
```

jstack 会直接输出 `Found 1 deadlock.` 以及参与死锁的线程和锁的信息。

**预防死锁的最佳实践**：

| 措施 | 做法 |
|------|------|
| **固定锁顺序** | 所有线程按相同顺序获取锁（最有效） |
| **使用超时锁** | `tryLock(timeout)` 获取不到则释放已有锁重试 |
| **缩小锁范围** | 持有的锁尽快释放，减少并发持有多个锁的窗口 |
| **使用更高级的工具** | 用 `ReentrantLock` 替代 `synchronized`，利用 `tryLock` |

```java
// 使用 tryLock 避免死锁
ReentrantLock lockA = new ReentrantLock();
ReentrantLock lockB = new ReentrantLock();

public boolean transfer() {
    while (true) {
        if (lockA.tryLock()) {
            try {
                if (lockB.tryLock(1, TimeUnit.SECONDS)) {
                    try {
                        // 成功获取两个锁
                        return true;
                    } finally {
                        lockB.unlock();
                    }
                }
            } finally {
                lockA.unlock();
            }
        }
        // 获取失败，等待后重试
        sleep(ThreadLocalRandom.current().nextInt(10, 50));
    }
}

```

> 🎯 **核心要点**：synchronized 已经做了大量优化（偏向锁→轻量锁→重量锁），在低竞争场景下性能极好。高并发读多写少场景优先考虑 `ReadWriteLock` 或 `StampedLock` 的乐观读。**锁的顺序一致性**是预防死锁最重要且最有效的手段。

## 5. 并发容器选型

### 5.1 ConcurrentHashMap

ConcurrentHashMap 是 HashMap 的线程安全版本，从 Java 7 到 Java 8 经历了重大升级。

**Java 7：分段锁（Segment）**

```java
// Java 7 实现
// 结构：Segment[] → HashEntry[]
// 定位：两次 hash，先定位 Segment，再定位 HashEntry
// 锁：继承 ReentrantLock，每个 Segment 一把锁
// 并发度：默认 16（最多16个线程同时写）

ConcurrentHashMap<K, V> map = new ConcurrentHashMap<>(16, 0.75f, 16);
// initialCapacity=16, loadFactor=0.75, concurrencyLevel=16
// → 16个Segment，每个Segment保护1个HashEntry[]
```

**Java 8+：CAS + synchronized**

```java
// Java 8+ 实现
// 结构：Node[] + TreeNode[]（红黑树）
// 定位：一次 hash，直接定位 Node
// 锁：数组元素 Node 上的 synchronized
// 并发度：数组长度（理论无上限）

ConcurrentHashMap<String, String> map = new ConcurrentHashMap<>();
// 写操作核心逻辑：
// 1. hash 定位 Node[] 中的槽位
// 2. 槽位为空：CAS 原子写入
// 3. 槽位非空：synchronized(槽位Node) 后进行链表/红黑树操作
// 4. 链表长度 >= 8 且数组长度 < 64：先扩容
// 5. 链表长度 >= 8 且数组长度 >= 64：链表转红黑树
```

| 对比项 | Java 7 (Segment) | Java 8+ (CAS+synchronized) |
|--------|:----------------:|:--------------------------:|
| **数据结构** | Segment[] + HashEntry[] | Node[] + TreeNode[] |
| **锁粒度** | 一个 Segment（多 HashEntry） | 一个 Node 槽位 |
| **并发度** | 固定 16 | 随数组长度增长 |
| **查找效率** | 两次 hash | 一次 hash |
| **内存占用** | 较高（Segment 对象额外开销） | 更低 |
| **锁实现** | ReentrantLock | synchronized（JVM 优化后性能更好） |

**常用 API 注意事项**：

```java
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

// ❌ 非原子操作：存在并发问题
if (!map.containsKey("key")) {
    map.put("key", 1);
}

// ✅ 原子操作：使用 computeIfAbsent
map.computeIfAbsent("key", k -> 1);

// ✅ 原子增减
map.merge("key", 1, Integer::sum);

// ✅ 遍历是线程安全的，但不保证实时一致性
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    // 遍历过程中其他线程的修改不会影响当前迭代
}

// ❌ size() 和 isEmpty() 是近似值，不是精确值
int size = map.size();    // 可能不准确
boolean empty = map.isEmpty();
```

> ⚠️ **非原子组合操作**：`containsKey` 后跟 `put` 是典型的竞态条件，必须使用 `computeIfAbsent`、`merge` 等原子方法替代。

### 5.2 CopyOnWriteArrayList

**原理**：所有修改操作（add/set/remove）都通过**复制底层数组**来实现，读操作不加锁。

```java
public class CopyOnWriteArrayList<E> {
    private volatile transient Object[] array; // volatile保证可见性

    // 写操作：加锁 + 复制数组
    public boolean add(E e) {
        synchronized (lock) {
            Object[] oldArray = getArray();
            int len = oldArray.length;
            Object[] newArray = Arrays.copyOf(oldArray, len + 1); // 复制
            newArray[len] = e;
            setArray(newArray); // 替换数组引用
            return true;
        }
    }

    // 读操作：无锁，直接读取
    public E get(int index) {
        return getArray()[index];
    }
}
```

| 特性 | 说明 |
|------|------|
| **适用场景** | 读多写少（读 >> 写），如白名单、配置、路由表 |
| **读性能** | 极快（无锁、无 CAS、无阻塞） |
| **写性能** | 差（每次写都复制整个数组，O(n) 时间+O(n) 内存） |
| **内存开销** | 高（写时复制两份数组） |
| **数据一致性** | 最终一致（迭代器读取的是"快照"） |

```java
// 典型应用：白名单
public class WhiteListService {
    private final CopyOnWriteArrayList<String> whiteList = new CopyOnWriteArrayList<>();

    public WhiteListService() {
        whiteList.addAll(loadFromDB());
    }

    // 读操作：极高并发，无锁
    public boolean isAllowed(String ip) {
        return whiteList.contains(ip); // 无锁遍历
    }

    // 写操作：低频，每次复制数组
    public void addIp(String ip) {
        whiteList.add(ip);        // 添加时复制数组
    }

    public void refresh() {      // 定时刷新，通常每分钟或每小时一次
        whiteList.clear();
        whiteList.addAll(loadFromDB());
    }
}
```

### 5.3 ConcurrentLinkedQueue vs LinkedBlockingQueue

| 对比项 | ConcurrentLinkedQueue | LinkedBlockingQueue |
|--------|:--------------------:|:------------------:|
| **类型** | 非阻塞队列 | 阻塞队列 |
| **算法** | CAS（无锁） | 锁（ReentrantLock） |
| **容量** | 无界 | 有界（必须指定容量） |
| **队列空时** | poll() 返回 null | take() 阻塞等待 |
| **队列满时** | offer() 返回 false | put() 阻塞等待 |
| **适用场景** | 纯消费者-生产者，允许丢弃 | 必须处理每个任务，削峰填谷 |

```java
// ConcurrentLinkedQueue：CAS 无锁实现，高吞吐但无阻塞能力
ConcurrentLinkedQueue<Task> queue = new ConcurrentLinkedQueue<>();

// 生产者
queue.offer(task);

// 消费者
Task task = queue.poll();
if (task == null) {
    // 队列为空，做其他事情或等待
}

// LinkedBlockingQueue：有界阻塞队列，支持阻塞等待
LinkedBlockingQueue<Task> queue = new LinkedBlockingQueue<>(1000);

// 生产者 — 队满时阻塞
queue.put(task); // 会阻塞直到有空间

// 消费者 — 队空时阻塞
Task task = queue.take(); // 会阻塞直到有元素
```

| 选择策略 | 推荐队列 |
|----------|----------|
| 需要无界、高吞吐、可丢弃 | ConcurrentLinkedQueue |
| 需要阻塞、有界、背压控制 | LinkedBlockingQueue |
| 需要延迟执行 | DelayQueue |
| 需要优先级调度 | PriorityBlockingQueue |
| 需要传递（零容量） | SynchronousQueue |

## 6. ThreadLocal与内存泄漏

### 6.1 ThreadLocalMap 的 Entry 弱引用

ThreadLocal 的原理是每个 Thread 维护一个 ThreadLocalMap，其 Entry 的 Key 是弱引用。

```java
// 简化后的 ThreadLocalMap 结构
static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;          // 值（强引用）
        Entry(ThreadLocal<?> k, Object v) {
            super(k);          // Key 是弱引用
            value = v;
        }
    }
    private Entry[] table;
}
```

**内存泄漏路径**：

```
Thread 对象
    ↓ (强引用)
ThreadLocalMap
    ↓ (强引用)
Entry[] 数组
    ↓
├── Entry.key  →  WeakReference(ThreadLocal对象)  ← 外部强引用 ThreadLocal 被置 null 后，可被 GC
└── Entry.value → 强引用                            ← ThreadLocalMap 不清理就永远无法被 GC！
```

> ⚠️ **内存泄漏的本质**：当 `ThreadLocal` 对象被 GC 回收后（因为外部没有强引用），Entry 的 key 变为 `null`，但 value 仍然被 Entry 强引用。如果线程存活时间较长（如线程池中的线程），这些 value 永远不会被回收，导致内存泄漏。

### 6.2 remove() 的必要性

```java
private static final ThreadLocal<UserContext> USER_CONTEXT = new ThreadLocal<>();

public void handleRequest(User user) {
    try {
        // 设置上下文
        USER_CONTEXT.set(new UserContext(user));

        // ... 业务逻辑，可能在代码深处调用 USER_CONTEXT.get() ...

        // 如果这里忘记 remove()
        // 线程池中的线程处理完一个请求后不会被销毁
        // 下一个请求复用该线程时，get() 会拿到上一个用户的上下文！
    } finally {
        // 必须在 finally 块中清理！
        USER_CONTEXT.remove();
    }
}
```

**漏斗形流程**：

```java
// ❌ 错误做法：不清理
public void badPractice() {
    USER_CONTEXT.set(new UserContext(user));
    doBusiness();    // 如果这里抛出异常，remove 永远不会执行
    USER_CONTEXT.remove();  // 异常时不会执行到这里！
}

// ✅ 正确做法：finally 中清理
public void goodPractice() {
    try {
        USER_CONTEXT.set(new UserContext(user));
        doBusiness();
    } finally {
        USER_CONTEXT.remove();  // 无论是否异常都会执行
    }
}
```

### 6.3 线程池中使用 ThreadLocal 的坑

```java
// 模拟线程池中 ThreadLocal 的问题
ExecutorService executor = Executors.newFixedThreadPool(2);

// 请求1：设置上下文
executor.execute(() -> {
    USER_CONTEXT.set(new UserContext("用户A"));
    service.process();          // 处理过程中使用了 USER_CONTEXT
    // 忘记 remove()
});

// 请求2：复用线程，没有设置上下文
executor.execute(() -> {
    // ❌ 这里 get() 到的是"用户A"！
    // 因为线程池复用了线程，而 ThreadLocal 还未清理
    UserContext ctx = USER_CONTEXT.get();  // 用户A的数据泄露到用户B！
});
```

| 问题 | 后果 | 解决方案 |
|------|------|----------|
| **数据泄露** | 请求B读到请求A的数据 | finally 中必须 remove() |
| **内存泄漏** | 长时间运行的线程持有大对象 | finally 中必须 remove() |
| **跨线程传递** | 子线程拿不到主线程的 ThreadLocal | TransmittableThreadLocal |

### 6.4 TransmittableThreadLocal 解决跨线程传递

阿里开源的 `TransmittableThreadLocal`（TTL）解决了线程池中 ThreadLocal 值无法跨线程传递的问题。

```java
// 引入依赖
// <dependency>
//     <groupId>com.alibaba</groupId>
//     <artifactId>transmittable-thread-local</artifactId>
//     <version>2.14.5</version>
// </dependency>
```

```java
// 使用 TTL 替代 ThreadLocal
private static final TransmittableThreadLocal<UserContext> USER_CONTEXT =
    new TransmittableThreadLocal<>();

// 方式1：使用 TTL 包装线程池
ExecutorService executor = TtlExecutors.getTtlExecutorService(
    Executors.newFixedThreadPool(10)
);

// 方式2：使用 TTL Runnable 包装
Runnable task = TtlRunnable.get(() -> {
    UserContext ctx = USER_CONTEXT.get(); // 可以拿到父线程的值
    System.out.println("当前用户: " + ctx.getUserName());
});

executor.submit(task);

// 方式3：Java Agent（无侵入，自动增强）
// -javaagent:transmittable-thread-local-2.14.5.jar
```

**底层原理**：

```
父线程设置 TTL 值
    ↓
提交任务到线程池时，TtlRunnable 快照当前 TTL 的值
    ↓
子线程执行时，从快照中恢复 TTL 的值（在 run 方法开始时）
    ↓
子线程执行完毕后，清理 TTL 的值（在 run 方法结束时）
```

| 方案 | 侵入性 | 说明 |
|------|:------:|------|
| **TtlExecutors** | 中 | 包装已有线程池，自动处理所有任务 |
| **TtlRunnable/TtlCallable** | 低 | 只包装特定需要传递上下文的任务 |
| **Java Agent** | 无 | 启动参数注入，自动增强，推荐生产使用 |

```java
// 生产级最佳实践：TTL + MDC + TraceId
public class TraceContext {

    private static final TransmittableThreadLocal<String> TRACE_ID =
        new TransmittableThreadLocal<>();

    public static void setTraceId(String traceId) {
        TRACE_ID.set(traceId);
        MDC.put("traceId", traceId);  // 日志框架
    }

    public static String getTraceId() {
        return TRACE_ID.get();
    }

    public static void clear() {
        TRACE_ID.remove();
        MDC.clear();
    }
}

// 过滤器中使用
public class TraceFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
        try {
            TraceContext.setTraceId(UUID.randomUUID().toString().replace("-", ""));
            chain.doFilter(request, response);
        } finally {
            TraceContext.clear(); // 必须清理
        }
    }
}
```

> 🎯 **核心要点**：ThreadLocal 用完后务必在 finally 中 `remove()`。在线程池环境中使用 ThreadLocal 要格外小心——线程复用会带来数据泄露问题。跨线程传递上下文（TraceId、用户信息）使用 TransmittableThreadLocal。

## 7. 虚拟线程实战

### 7.1 虚拟线程是什么

虚拟线程（Virtual Threads）是 Java 21 正式发布的轻量级线程（Preview 在 Java 19/20）。它不是"取代线程池"，而是改变了我们处理并发的方式。

| 对比项 | 平台线程（Platform Thread） | 虚拟线程（Virtual Thread） |
|--------|:--------------------------:|:-------------------------:|
| **底层实现** | 操作系统线程（内核线程 1:1） | JVM 管理的纤程（M:N） |
| **创建成本** | 高（约 1MB 栈空间） | 极低（约 1KB 栈空间） |
| **最大数量** | 数千（取决于内存） | 数百万 |
| **上下文切换** | 系统调用（昂贵） | JVM 内部（轻量） |
| **阻塞时** | 线程阻塞，系统线程被占用 | 挂起虚拟线程，释放平台线程 |

### 7.2 虚拟线程 vs 传统线程池性能对比

```java
// 传统线程池：100个平台线程的线程池
ExecutorService platformPool = Executors.newFixedThreadPool(100);

// 虚拟线程：无限制，每个任务一个虚拟线程
ExecutorService virtualPool = Executors.newVirtualThreadPerTaskExecutor();
```

**线程池模型的问题**：

```java
// 场景：同时发起 10000 个 HTTP 请求
// 传统方式：每个请求占用一个线程，线程池满了就排队
ExecutorService pool = Executors.newFixedThreadPool(200);
List<CompletableFuture<Response>> futures = new ArrayList<>();
for (int i = 0; i < 10000; i++) {
    int id = i;
    futures.add(CompletableFuture.supplyAsync(
        () -> httpClient.send(request(id)), pool));
}
// 问题：只有 200 个请求在并发，其余 9800 个在排队
```

```java
// 虚拟线程：每个请求一个虚拟线程，同时并发
ExecutorService vtExecutor = Executors.newVirtualThreadPerTaskExecutor();
// 或
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Response>> futures = new ArrayList<>();
    for (int i = 0; i < 10000; i++) {
        int id = i;
        futures.add(executor.submit(() -> httpClient.send(request(id))));
    }
    // 10000 个请求同时发出！
    for (var future : futures) {
        Response resp = future.get();
        // 处理响应
    }
}
```

| 对比维度 | 传统线程池 | 虚拟线程 |
|----------|:----------:|:--------:|
| **最大并发数** | 线程数（200~5000） | 数百万 |
| **阻塞时行为** | 线程阻塞，浪费系统资源 | 挂起释放平台线程，资源零浪费 |
| **IO 密集型** | 需要调优线程池参数 | 天然适配，无需调优 |
| **CPU 密集型** | 合适 | 不合适（线程数量优势体现不出） |
| **编码模型** | 复杂（CompletableFuture 回调节点） | 简单（传统的同步代码风格） |

### 7.3 为什么虚拟线程让"一线程一任务"成为可能

虚拟线程的核心优势在于**阻塞操作的代价极低**。

```java
// 传统平台线程：阻塞 = 昂贵的系统线程被浪费
public Order getOrder(Long id) {
    Order order = orderRepository.findById(id).get();  // 线程阻塞等待DB
    User user = userService.getUser(order.getUserId()); // 线程阻塞等待RPC
    // 一个请求处理过程中，线程大部分时间在等待
    return order;
}

// 虚拟线程：阻塞 = 挂起虚拟线程，平台线程去执行其他虚拟线程
public Order getOrder(Long id) {
    Order order = orderRepository.findById(id).get();  // 虚拟线程挂起
    User user = userService.getUser(order.getUserId()); // 虚拟线程挂起
    // 平台线程一直在工作，不会被浪费
    return order;
}
```

**传统模型 vs 虚拟线程模型**：

```
传统线程池模型 (平台线程 = 系统线程，珍贵资源)：
┌────────────────────────────────────────┐
│ 平台线程1: 等待DB → 等待RPC → 返回结果   │  线程一直占有，即使空闲等待
│ 平台线程2: 等待DB → 等待RPC → 返回结果   │
│ 平台线程3: 等待DB → 等待RPC → 返回结果   │
│ ...                                     │
│ 只有 N 个线程在同时工作                     │
└────────────────────────────────────────┘

虚拟线程模型 (平台线程 = 运载车辆，虚拟线程 = 乘客)：
┌────────────────────────────────────────┐
│ 平台线程1: VT1(忙) → VT2(忙) → VT3(忙)   │  阻塞时换另一个VT继续执行
│ 平台线程2: VT4(忙) → VT5(忙) → VT6(忙)   │
│ ...                                     │
│ 数千个VT排队，平台线程永远不空闲              │
└────────────────────────────────────────┘
```

### 7.4 结构化并发（StructuredTaskScope）

Java 21 引入了**结构化并发**（JEP 453），将并发任务的生命周期与代码块绑定。

```java
// 非结构化方式：任务生命周期不明确
CompletableFuture<Order> future1 = CompletableFuture.supplyAsync(() -> orderService.getOrder(id));
CompletableFuture<User> future2 = CompletableFuture.supplyAsync(() -> userService.getUser(id));
// 如果这里抛出异常，future1 和 future2 不会被取消，成为"孤儿"任务

// 结构化并发：作用域结束前，所有子任务必须完成或被取消
public Response handle() throws ExecutionException, InterruptedException {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        // 在作用域内提交子任务
        Subtask<Order> orderTask = scope.fork(() -> orderService.getOrder(id));
        Subtask<User> userTask = scope.fork(() -> userService.getUser(id));

        // 等待所有子任务完成（或任一失败）
        scope.join();
        scope.throwIfFailed(); // 如果有子任务失败，抛出异常

        // 所有子任务成功完成，获取结果
        return new Response(orderTask.get(), userTask.get());
    } // 作用域结束，自动取消未完成的任务
}
```

| 特性 | CompletableFuture | StructuredTaskScope |
|------|:-----------------:|:------------------:|
| **生命周期管理** | 手动 | 自动（try-with-resources） |
| **异常传播** | 需要手动处理 | 自动传播（throwIfFailed） |
| **取消传播** | 需手动 cancel | 作用域退出自动取消 |
| **超时控制** | orTimeout/completeOnTimeout | 结合虚拟线程更简洁 |

**虚拟线程 + 结构化并发的最佳实践**：

```java
// 高并发场景下的推荐模式
public ProductDetail getProductDetail(Long productId) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        // 并发获取三个服务的数据
        var product = scope.fork(() -> productService.getProduct(productId));
        var reviews = scope.fork(() -> reviewService.getReviews(productId));
        var inventory = scope.fork(() -> inventoryService.getStock(productId));

        // 等待全部完成，最多 2 秒
        scope.joinUntil(Instant.now().plusMillis(2000));
        scope.throwIfFailed();

        // 聚合结果
        return new ProductDetail(
            product.get(),   // 永远不会阻塞，因为已经完成
            reviews.get(),
            inventory.get()
        );
    }
    // 超时或异常时，scope 自动取消所有还在运行的任务
}
```

> ⚠️ **虚拟线程限制**：
> 1. **不适合 CPU 密集型**：虚拟线程的优势在于阻塞操作场景，CPU 计算型任务使用平台线程更合适
> 2. **synchronized 锁**：虚拟线程在 synchronized 中不会释放平台线程（导致平台线程被钉死），尽量使用 `ReentrantLock` 替代
> 3. **池化虚拟线程**：不要池化虚拟线程，创建成本极低，每个需要的地方 new 一个即可
> 4. **JVM 版本**：需要 JDK 21+。Java 21 是 LTS 版本，建议逐步迁移

**虚拟线程适用场景速查**：

| 场景 | 适合虚拟线程 | 原因 |
|------|:----------:|------|
| HTTP/RPC 调用 | 是 | 大量 IO 等待 |
| 数据库查询 | 是 | 大量 DB 阻塞 |
| 文件读写 | 是 | IO 密集型 |
| 数据加密/解密 | 否 | CPU 密集型 |
| 图像处理 | 否 | CPU 密集型 |
| 大量小任务并行 | 是 | 创建成本低 |

```bash
# JVM 参数启用虚拟线程（JDK 21+ 默认开启）
--enable-preview  # Java 19/20 需要，Java 21 不需要

# 查看虚拟线程状态
# JDK 21 的 jcmd 工具
jcmd <pid> Thread.dump_to_file -format=json <file>
```

> 🎯 **核心要点**：虚拟线程改变了 Java 并发的编程模型——"一线程一任务"成为现实。IO 密集型场景下，虚拟线程可以大幅简化代码（不需要 CompletableFuture 的回调编排），同时提供更高的吞吐量。但 CPU 密集型场景和 synchronized 锁的使用仍需注意。
