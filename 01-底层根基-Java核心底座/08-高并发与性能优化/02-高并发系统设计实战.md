## 1. 多级缓存体系

### 1.1 缓存层级总览

| 层级 | 存储位置 | 访问速度 | 容量 | 典型实现 |
|------|----------|:--------:|:----:|----------|
| **浏览器缓存** | 用户本地 | 零网络开销 | 取决于浏览器 | `Cache-Control` / `Expires` |
| **CDN 缓存** | 边缘节点 | 就近访问 | 大 | 阿里云 CDN / Cloudflare |
| **Nginx 本地缓存** | Nginx 服务器 | 毫秒级 | 磁盘容量 | `proxy_cache` |
| **本地缓存** | JVM 堆内存 | 微秒级 | 小（GB 级） | Caffeine / Guava Cache |
| **分布式缓存** | 独立缓存集群 | 毫秒级 | 大（TB 级） | Redis / Memcached |

### 1.2 多层缓存访问流程

```
用户请求
    ↓
浏览器缓存 → 有则直接返回（零网络成本）
    ↓ (未命中)
CDN → 有则直接返回（边缘节点就近访问）
    ↓ (未命中)
Nginx 本地缓存 → 有则直接返回（避免请求到应用服务器）
    ↓ (未命中)
本地缓存 Caffeine → 有则直接返回（微秒级）
    ↓ (未命中)
分布式缓存 Redis → 有则返回并回填本地缓存（毫秒级）
    ↓ (未命中)
数据库 → 读取并逐级回填缓存
```

### 1.3 本地缓存选型：Caffeine vs Guava Cache

| 特性 | Caffeine | Guava Cache |
|------|:--------:|:-----------:|
| 淘汰算法 | Window-TinyLFU | LRU |
| 命中率 | 更高（接近最优） | 一般 |
| 并发性能 | 优秀（分段锁） | 良好 |
| 内存效率 | 高 | 中 |

```java
Cache<String, Object> cache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(5, TimeUnit.MINUTES)
    .recordStats()
    .build();
```

## 2. 热点数据处理

| 策略 | 做法 | 适用场景 |
|------|------|----------|
| **提前预热** | 活动前将数据预先加载到缓存 | 可预知热点（秒杀、大促） |
| **本地缓存兜底** | 在 Redis 之上加 Caffeine | Redis 瓶颈时仍可响应 |
| **多副本分摊** | 热点 key 创建多个副本分散请求 | 单个 key 压力过大 |
| **限流保护** | 缓存层之前加限流，超出返回兜底数据 | 保护后端系统 |

## 3. 负载均衡

### 3.1 方案对比

| 类型 | 代表产品 | 层次 | 性能 | 成本 | 适用场景 |
|------|----------|:----:|:----:|:----:|----------|
| **DNS 负载均衡** | DNS 服务器 | 应用层 | 中 | 低 | 全局流量调度 |
| **硬件负载均衡** | F5 BIG-IP | 4~7层 | 极高 | 极高 | 金融、电信核心系统 |
| **软件负载均衡** | Nginx / LVS / HAProxy | 4~7层 | 高 | 低 | 互联网企业主流 |
| **客户端负载均衡** | Ribbon / Spring Cloud LB | 应用层 | — | 低 | 微服务内部调用 |

### 3.2 LVS + Nginx 经典架构

```
用户请求 → DNS（全局负载均衡）
    ↓
LVS（四层负载均衡，工作在内核空间）
    ↓
Nginx 集群（七层反向代理：路由/限流/缓存）
    ↓
应用服务器集群 → 数据库 / Redis
```

### 3.3 负载均衡算法

| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **轮询** | 按顺序依次分发 | 实现简单 | 不考虑实际负载 | 服务器配置一致 |
| **加权轮询** | 按权重比例分配 | 支持异构服务器 | 权重需手动调整 | 新旧机器混用 |
| **最少连接** | 分配给活跃连接最少的服务器 | 动态感知负载 | 有状态开销 | 请求处理时间差异大 |
| **IP Hash** | 根据客户端 IP 哈希映射 | 会话保持 | 代理/NAT 失效 | 需要 Session Sticky |
| **一致性哈希** | 哈希环上顺时针路由 | 节点增减影响小 | 实现复杂 | 分布式缓存路由 |

### 3.4 Nginx 配置示例

```nginx
upstream backend {
    server 192.168.1.1 weight=5 max_fails=3 fail_timeout=30s;
    server 192.168.1.2 weight=3 max_fails=3 fail_timeout=30s;
    server 192.168.1.3 backup;
}
```

## 4. 读写分离

### 4.1 一主多从架构

```
应用层 → 读写分离中间件（ShardingSphere / 自研）
    ├── 写请求 → 主库（Master）
    └── 读请求 → 从库集群（Slave1, Slave2, ...）
                        ↑
          主库 binlog → 异步复制到从库
```

### 4.2 主从延迟与解决方案

> ⚠️ 主从复制是异步的，从库数据总会比主库落后（几毫秒到几秒），可能出现"刚写入的数据读不到"的问题。

| 方案 | 做法 | 复杂度 |
|------|------|:------:|
| **强制读主** | 一致性要求高的业务配置强制读主库 | 低 |
| **延迟读** | 写入后一段时间内的读请求也走主库 | 低 |
| **缓存标记** | 写入时将 key 写入 Redis，读请求先检查缓存 | 中 |

### 4.3 MySQL 主从复制

```sql
-- 主库创建复制账号
CREATE USER 'repl'@'%' IDENTIFIED BY 'password';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

-- 从库配置
CHANGE MASTER TO MASTER_HOST='master_host', MASTER_PORT=3306,
    MASTER_USER='repl', MASTER_PASSWORD='password',
    MASTER_LOG_FILE='mysql-bin.000001', MASTER_LOG_POS=0;
START SLAVE;
```

### 4.4 ShardingSphere 读写分离配置

```yaml
spring:
  shardingsphere:
    datasource:
      names: master,slave0,slave1
      master:   url: jdbc:mysql://master_host:3306/db
      slave0:   url: jdbc:mysql://slave0_host:3306/db
      slave1:   url: jdbc:mysql://slave1_host:3306/db
    rules:
      readwrite-splitting:
        data-sources:
          primary_ds:
            write-data-source-name: master
            read-data-source-names: slave0,slave1
            load-balancer-name: round_robin
```

## 5. 分库分表

当单表数据量超过 **500 万行**或表容量超过 **10GB** 时需要考虑水平分表。

### 5.1 垂直分库 vs 水平分表

| 维度 | 垂直分库 | 水平分表 |
|------|----------|----------|
| **拆分方式** | 按业务模块拆为独立数据库 | 按规则将数据拆分到多张表 |
| **示例** | 用户库、订单库、商品库 | `t_order_0` ~ `t_order_127` |
| **解决问题** | 业务耦合、独立扩容、故障隔离 | 单表数据量过大、写入瓶颈 |
| **新问题** | 跨库查询、分布式事务 | 跨分片查询、分页排序、分布式 ID |

### 5.2 分片键选择与算法

**分片键三原则**：大部分查询携带该字段 / 分布均匀 / 不可变。

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **取模分片** | `index = key % N` | 简单，分布均匀 | 扩容时几乎全部数据需迁移 |
| **范围分片** | 按 ID 范围分配 | 扩容方便，无需迁移历史数据 | 热点问题（新数据集中在高分片） |
| **一致性哈希** | 哈希环路由 | 扩容影响范围小 | 实现复杂 |

### 5.3 雪花算法（Snowflake）分布式 ID

```
0 - 0000000000 0000000000 0000000000 0000000000 0 - 00000 - 00000 - 000000000000
|   \--- 时间戳（41位，精确到毫秒，可用69年） ---/ |   |   |   |   |
|                                                   数据中心ID 机器ID  序列号
1位符号位（固定0）                                   (5位)   (5位)  (12位)
```

```java
public synchronized long nextId() {
    long timestamp = System.currentTimeMillis();
    if (timestamp < lastTimestamp) {
        throw new RuntimeException("时钟回拨异常");
    }
    if (timestamp == lastTimestamp) {
        sequence = (sequence + 1) & 0xFFF;
        if (sequence == 0) timestamp = waitUntilNextMillis(timestamp);
    } else {
        sequence = 0L;
    }
    lastTimestamp = timestamp;
    return ((timestamp - 1288834974657L) << 22)
         | (datacenterId << 17) | (machineId << 12) | sequence;
}
```

### 5.4 ShardingSphere-JDBC 实战配置

```yaml
spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
      ds0:  url: jdbc:mysql://localhost:3306/db0
      ds1:  url: jdbc:mysql://localhost:3306/db1
    rules:
      sharding:
        tables:
          t_order:
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..3}
            database-strategy:
              standard:  sharding-column: user_id   sharding-algorithm-name: db_inline
            table-strategy:
              standard:  sharding-column: order_id  sharding-algorithm-name: table_inline
        sharding-algorithms:
          db_inline:     type: INLINE  props: algorithm-expression: ds$->{user_id % 2}
          table_inline:  type: INLINE  props: algorithm-expression: t_order_$->{order_id % 4}
        binding-tables: [t_order, t_order_item]
```

> 💡 绑定表 `t_order` / `t_order_item` 按同一字段分片，ShardingSphere 保持路由一致避免跨库 JOIN。

## 6. 异步与消息队列

### 6.1 典型异步场景

| 场景 | 做法 | 效果 |
|------|------|------|
| 短信/邮件通知 | 注册后放入 MQ | 不阻塞用户响应 |
| 日志收集 | 通过 MQ 发送到 ELK | 不影响业务性能 |
| 数据同步 | 订单产生后通知库存/财务 | 服务解耦 |
| 事件驱动 | 下单触发发短信、更新积分 | 并行执行 |

### 6.2 削峰填谷（秒杀场景）

```
100万用户同时请求 → Nginx限流(放行10万) → MQ队列(排队) → 订单服务(恒定1000 TPS)
```

> 🎯 通过 MQ 缓冲，后端系统感受不到"流量洪峰"，始终以恒定速率处理。

### 6.3 CompletableFuture 异步编排

```java
public OrderDetail getOrderDetail(Long orderId) {
    var orderFuture = CompletableFuture.supplyAsync(() -> orderService.getOrder(orderId), executor);
    var itemsFuture = CompletableFuture.supplyAsync(() -> orderItemService.getItems(orderId), executor);
    var userFuture = orderFuture.thenCompose(order ->
        CompletableFuture.supplyAsync(() -> userService.getUser(order.getUserId()), executor));
    var paymentFuture = CompletableFuture.supplyAsync(() -> paymentService.getPayments(orderId), executor);

    return CompletableFuture.allOf(orderFuture, itemsFuture, userFuture, paymentFuture)
        .thenApply(v -> assemble(orderFuture.join(), itemsFuture.join(), userFuture.join(), paymentFuture.join()))
        .orTimeout(3000, TimeUnit.MILLISECONDS)
        .exceptionally(e -> { log.error("获取失败", e); return new OrderDetail(); })
        .join();
}
```

### 6.4 异步注意事项

| 要点 | 做法 |
|------|------|
| **线程池隔离** | 不同业务使用独立线程池 |
| **上下文传递** | `ThreadLocal` + `TaskDecorator` 传递 TraceID |
| **异常处理** | `exceptionally()` / `handle()` 回调处理 |

## 7. 数据库性能优化

### 7.1 SQL 优化

**避免 `SELECT *`，只查需要的字段**：

```sql
-- 推荐
SELECT id, order_no, amount, status FROM order WHERE user_id = 1001;
```

**避免索引失效**：

| 失效场景 | 错误写法 | 正确写法 |
|----------|----------|----------|
| 函数操作 | `WHERE DATE(create_time) = '2024-01-01'` | 改为范围查询 |
| 类型隐式转换 | `WHERE user_id = '1001'`（int 字段） | 保持类型一致 |
| 前缀模糊查询 | `WHERE name LIKE '%keyword'` | 搜索引擎或前缀匹配 |
| OR 条件无索引 | `WHERE status=1 OR remark='xxx'` | UNION 拆分 |

**大分页优化**：

```sql
-- 传统方式（性能差）：扫描 1000020 条再丢弃
SELECT * FROM order ORDER BY id LIMIT 1000000, 20;

-- 子查询优化（利用覆盖索引）
SELECT * FROM order
WHERE id >= (SELECT id FROM order ORDER BY id LIMIT 1000000, 1) LIMIT 20;

-- 游标分页（传入上一页最后一个 ID）
SELECT * FROM order WHERE id > :lastId ORDER BY id LIMIT 20;
```

**批量操作**：避免循环中逐条执行 SQL。

```java
// 推荐：一次批量插入
orderMapper.batchInsert(orders);
```

### 7.2 HikariCP 连接池配置

```yaml
spring:
  datasource:
    hikari:
      minimum-idle: 10
      maximum-pool-size: 50
      idle-timeout: 600000
      max-lifetime: 1800000
      connection-timeout: 30000
```

> 💡 **CPU 密集型**应用连接池 10~20 个即可；**IO 密集型**可设置更大。

## 8. 高可用部署架构

### 8.1 部署模式

| 模式 | 描述 | 切换时间 | 成本 |
|------|------|:--------:|:----:|
| **同城双活** | 同城两个数据中心同时承载流量 | 秒级 | 中 |
| **两地三中心** | 同城双活 + 异地灾备 | 分钟级 | 高 |
| **多活架构** | 三个以上数据中心同时承载流量 | 秒级 | 极高 |

### 8.2 Keepalived + VIP 漂移

```
正常：主(192.168.1.10) ← VIP 192.168.1.100  备(192.168.1.11) 监控
故障：主宕机 → 备接管 VIP 192.168.1.100（毫秒级切换）
```

### 8.3 Redis 哨兵模式

```
Sentinel 集群（3 节点）监控 Master/Slave
Master 宕机 → Sentinel 选举 → Slave 提升为新 Master
```

### 8.4 混沌工程

主动注入故障验证系统韧性：定义稳态 → 假设 → 注入故障（杀死进程/网络延迟/磁盘故障）→ 验证。

## 9. 微服务治理

### 9.1 问题速查

| 问题 | 方案 | 工具 |
|------|------|------|
| 大量请求冲击 | 限流 | Sentinel / Guava RateLimiter |
| 服务雪崩 | 熔断 + 降级 | Sentinel / Resilience4j |
| 重复下单 | 幂等设计 | 唯一索引 + Redis 锁 |
| 数据一致性 | 最终一致 + 对账 | MQ + 定时任务 |

### 9.2 Sentinel 配置

```yaml
flow:
  - resource: "getOrder"
    clusterMode: true
    count: 1000
    grade: 1           # QPS
    controlBehavior: 0 # 快速失败

degrade:
  - resource: "paymentService"
    grade: 0           # RT
    count: 200         # RT 超过 200ms 触发
    timeWindow: 10     # 熔断时长（秒）
```

### 9.3 Resilience4j 配置

```java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)
    .waitDurationInOpenState(Duration.ofSeconds(10))
    .slidingWindowSize(100)
    .minimumNumberOfCalls(10)
    .build();
CircuitBreaker breaker = CircuitBreaker.of("paymentService", config);
```

## 10. 秒杀系统架构设计

### 10.1 九层防护体系

```text
① 前端：按钮置灰 + 防重复点击
② CDN：静态资源走 CDN
③ 网关：IP 限流
④ Nginx：并发连接数限制
⑤ 服务层：Sentinel 接口限流
⑥ Redis：预减库存（Lua 原子操作）
⑦ MQ：下单请求入队削峰
⑧ DB：扣减最终库存
⑨ 对账：发现超卖回补
```

### 10.2 Redis Lua 预减库存

```lua
local key = KEYS[1]
local stock = redis.call('GET', key)
if not stock or tonumber(stock) <= 0 then
    return 0  -- 库存不足
end
redis.call('DECR', key)
return 1  -- 扣减成功
```

### 10.3 核心要点

| 层面 | 措施 | 目的 |
|------|------|------|
| **前端** | 按钮置灰、限制频率 | 减少无效请求 |
| **网关** | IP 限流、单机限流 | 拦截恶意流量 |
| **缓存** | Redis 预扣库存（Lua 原子） | 减少 DB 写入压力 |
| **消息** | MQ 异步削峰 | 平滑流量 |
| **数据库** | 最终扣减 + 唯一索引幂等 | 防止超卖 |
| **对账** | 事后对账回补 | 最终防线 |

## 11. 最佳实践与性能调优路线图

### 11.1 核心要点

| 原则 | 说明 |
|------|------|
| **缓存是王道** | 优先考虑缓存，其次才是扩容 |
| **异步解耦** | 能用异步就不要同步 |
| **做好限流** | 永远不要假设流量是可控的 |
| **冗余部署** | 所有关键组件至少部署两个实例 |
| **灰度发布** | 新功能先小范围上线验证 |
| **持续压测** | 定期压力测试发现真实瓶颈 |

### 11.2 性能调优路线图

```
识别瓶颈(监控告警) → 制定方案 → 实施 → 验证 → 持续监控(效果不达标继续下一轮)
```

### 11.3 技能进阶

**初级阶段**：会用 Redis 做缓存 / 会用 MQ 异步处理 / 理解布隆过滤器 / 能写分布式锁 / 理解幂等。

**进阶阶段**：设计秒杀系统 / 缓存一致性方案选型 / 多级缓存架构 / ShardingSphere 分库分表落地。

**扩展方向**：
```
加机器 → 无状态服务扩缩容 → 读写分离 → 分库分表 → 多级缓存 → CDN
```

> 🎯 **最终总结**：高并发系统设计没有银弹。从最小化可行架构开始，通过监控数据驱动渐进式演进——**先做好缓存和异步，再考虑分库分表**。系统的韧性不在于单体有多强，而在于架构有多冗余、防护有多层、恢复有多快。
