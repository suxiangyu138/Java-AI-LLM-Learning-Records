## 1. 负载均衡全栈：从 DNS 到注册中心

一个请求的负载均衡发生在五个层级，层层递进，各司其职：

- **DNS 层**：域名解析到多 IP，做地域级调度（就近接入、容灾切换）。粒度最粗，生效时间由 TTL 决定（分钟级），适合机房级调度。
- **LVS/四层**：内核态转发，按 IP+端口分发，抗压最强（百万级并发），无应用层认知——只能按连接分发。
- **Nginx/七层**：按 HTTP 语义分发（路径、Header、Cookie），能做灰度比例、健康检查、限流（[Nginx 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/Nginx/00-Nginx知识体系总览.md) 全套）。
- **网关层**：微服务网关（Spring Cloud Gateway）做路由、鉴权、全局限流，与注册中心联动动态路由。
- **注册中心**：服务间调用（RPC）的负载均衡——Dubbo/Feign 从注册中心拉实例列表，客户端负载均衡（随机/轮询/一致性哈希），服务上下线秒级感知（[Nacos 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/06-Spring全家桶/Spring组件汇总/Spring%20Cloud%20微服务全家桶（分布式）/Spring%20Cloud%20Alibaba（阿里实现，属于%20Spring%20Cloud%20生态实现）/Nacos：注册中心%20+%20配置中心/00-Nacos知识体系总览.md)）。

每层的均衡粒度不同：DNS 管机房、四层管连接、七层管请求、注册中心管 RPC——**流量治理要明确在哪一层做**：全局限流在网关、地域调度在 DNS、服务熔断在 RPC 层。

## 2. 均衡策略与连接治理

均衡策略的选择直接影响吞吐与延迟：

- **轮询/加权轮询**：默认选择，适合处理时间相近的请求；加权应对异构机器。
- **最小连接**：请求发给当前连接数最少的实例，适合长连接与处理时间差异大的场景（网关、WebSocket）。
- **一致性哈希**：同一用户/IP 固定到同一实例，配合本地缓存命中率提升；代价是扩缩容引发重分布（[Redis 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/02-非关系型数据库/Redis/01-Redis入门与安装配置.md) 的哈希环变体同样适用）。
- **自适应**：根据实例实时负载（CPU/RT）动态调整权重——2026 年云原生网关的默认演进方向。

连接治理是流量层最容易翻车的细节：**keepalive 超时链**（客户端→网关→上游逐层递减）、连接池上限（打满即排队）、被动健康检查（连续失败摘除）与主动健康检查（探针）配合。一个常见事故：Nginx 上游 60 秒 keepalive，业务服务 30 秒就断开空闲连接，网关还往死连接上转发——超时链设计见[专题 7 的超时金字塔](../专题%207：分布式高并发%20&%20限流熔断降级/08-隔离与舱壁：线程池与信号量.md)。

## 3. 灰度发布：蓝绿、金丝雀与流量比例

发布是变更风险最高的时刻，灰度把"一次全量"拆成"渐进放量"，三种模式：

- **蓝绿发布**：新旧两套环境并存，流量一次性切换（蓝→绿）。切换瞬间无灰度期，回滚是切回旧环境——快但浪费资源（双套环境），适合基础设施类变更。
- **金丝雀发布**：新版本先放 5%-10% 流量，观察监控指标正常后逐步放大到 100%。风险最小，周期最长，适合业务服务（[CI/CD 体系的灰度发布](../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/CI%20CD灰度发布/00-CI-CD与灰度发布总览.md) 有 Argo Rollouts/Istio 权重路由的完整实现）。
- **流量比例（A/B）**：按用户特征（地域、会员等级、随机哈希）切流，用于功能对比与定向放量，与发布解耦。

2026 年实践的关键词是**渐进与自动化**：金丝雀的放量节奏由监控指标自动驱动（错误率、P99、资源利用率达标才放大），而不是人工盯盘——人工盯盘的灰度在第 3 次放大后必然出错。

## 4. 灰度三件套：会话保持、监控与回滚

灰度发布最容易失败的三个点，必须提前设计：

- **会话保持**：用户首次请求进了新版本，刷新跳回旧版本，体验割裂——按用户维度（Cookie/Header 的 user_id 哈希）粘滞路由，灰度期间同一用户固定版本。
- **监控对比**：新旧版本实例的指标并排看（错误率、P99、CPU、下游调用量），灰度是否继续由对比数据决定——没有对比面板的灰度是赌博。压测时同样要带版本对比（[08 篇](08-压测工具与平台全景.md)）。
- **回滚预案**：灰度前写好回滚步骤（流量切回、版本回退、数据补偿），并演练过——2026 年发布的"可回滚性"是发布门禁的第一项检查，回滚不是"发布失败后想的事"，而是"发布前必须证明可行的事"。

## 5. 流量调度与防护联动

流量调度与[专题 7](../专题%207：分布式高并发%20&%20限流熔断降级/00-总览.md) 的防护体系必须联动，两个典型场景：

- **扩容与限流联动**：灰度放量前先扩容 + 预热（冷实例扛不住全量流量），限流阈值按新容量重算（[专题 7 的容量红线](../专题%207：分布式高并发%20&%20限流熔断降级/02-扩展模式与容量边界.md)）。
- **故障转移与熔断联动**：机房故障时 DNS/网关切流，RPC 层熔断兜底——切流不是瞬间完成（DNS TTL、连接池回收都有延迟），熔断保证切流期间不雪崩；容灾切换的具体演练见[05 篇](05-高可用部署架构：双活与两地三中心.md)。

> 🎯 **核心要点**：负载均衡五层全栈（DNS 管机房/四层管连接/七层管请求/网关管路由/注册中心管 RPC），流量治理要明确在哪一层做；均衡策略按请求特征选（轮询/最小连接/一致性哈希）；灰度发布金丝雀为主，放量节奏由监控自动驱动；灰度三件套（会话保持/监控对比/可回滚性）缺一不可；扩容预热、故障切流都要与限流熔断联动。
