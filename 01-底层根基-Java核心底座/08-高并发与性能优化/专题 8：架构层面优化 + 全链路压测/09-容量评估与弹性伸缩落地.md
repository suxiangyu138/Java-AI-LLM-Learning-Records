## 1. 容量评估公式与水位线

容量评估是弹性伸缩的目标输入，公式化的流程四步：

1. **单机容量**：压测确定单实例容量拐点（[06 篇](06-全链路压测方法论.md) 的 Little's Law 拐点），记录拐点吞吐与 P99。
2. **实例数需求**：`实例数 = 峰值 QPS / (单实例拐点 QPS × 0.7)`——0.7 的安全系数预留突发与故障冗余（与[专题 7 的限流红线](../专题%207：分布式高并发%20&%20限流熔断降级/02-扩展模式与容量边界.md)同源）。
3. **水位线设计**：高水位（扩容阈值）70%、低水位（缩容阈值）40%——留 30% 缓冲避免扩容风暴，缩容低于 40% 才触发避免抖动。
4. **峰值核算**：大促峰值 = 业务目标反推（GMV 目标 ÷ 客单价 ÷ 转化率 → 下单 QPS → 全链路各环节 QPS），与历史峰值交叉验证。

容量评估的前提是[专题 1 的容量规划方法论](../专题%201：性能理论基础/07-容量规划与水位线.md)——本讲只做伸缩落地，指标口径与压测方法见专题 1。

三个常见评估错误要避免：**按均值算容量**（流量有尖峰，均值容量在峰值瞬间被打穿——必须按 P99 曲线或峰值窗口算）；**忽略故障冗余**（单实例宕机要能扛住，容量 = 峰值 ÷ (实例数 - 1) × 安全系数，而不是 ÷ 实例数）；**只算应用不算依赖**（下游数据库、MQ 的容量同样要评估——应用扩到 100 实例而数据库连接池只有 200，扩容等于空转）。容量评估的产出是"每层容量表"，而不只是"应用要多少实例"。

## 2. HPA：指标驱动的基础设施

HPA（Horizontal Pod Autoscaler）是 K8s 内置的水平伸缩：`desiredReplicas = ceil(currentReplicas × currentMetric / desiredMetric)`，带 0.1 容差与稳定窗口（stabilization window）防止抖动。2026 年生产实践四个关键点：

- **必须用 `autoscaling/v2` API**：v1 只支持单 CPU 指标且无稳定窗口。
- **必须设置 `resources.requests`**：HPA 按"实际用量/请求量"计算利用率，requests 不设显示 `<unknown>` 且**静默不伸缩**——这是最常见的 HPA 假死。
- **稳定窗口调优**：默认缩容窗口 300 秒建议调到 600 秒（防波动缩容），扩容窗口默认 0 秒建议 60 秒（防叠加扩容）。
- **maxReplicas 来自压测**：上限按实测峰值设定，而不是保守拍脑袋——上限太低，峰值直接打满集群。

HPA 的本质是**反应式**：指标延迟 + 冷启动延迟意味着扩容永远慢于流量变化——大促这类可预见的流量不能只靠它（下节预测式伸缩）。

## 3. VPA 与 KEDA：垂直与事件驱动

- **VPA（垂直伸缩）**：调整 Pod 的 CPU/内存 requests。四种模式（Off 仅推荐/Initial 新 Pod 生效/Recreate 驱逐重建/Auto 就地更新）。**与 HPA 冲突警告**：同一资源指标上 VPA 与 HPA 不能同时用（互相干扰、伸缩行为不可预测）；安全组合是"HPA 管自定义指标（QPS/队列深度）+ VPA 管 CPU/内存"，或 VPA 用 Off 模式做离线 right-sizing 推荐。
- **KEDA（事件驱动伸缩）**：CNCF 毕业项目，把 HPA 从"指标驱动"扩展为"事件驱动"——60+ scaler（Kafka、RabbitMQ、Redis、PostgreSQL、Prometheus、Cron），支持**缩容到零**（HPA 最小 1）。适合队列消费、流处理等"CPU 低但消息堆积"的场景——HPA 会因 CPU 低而误判平静，KEDA 按队列深度伸缩（如每副本 20 条消息，队列 200 条 → 10 副本）。

选型口诀：**无状态在线服务用 HPA，事件驱动负载用 KEDA，资源规格不合理用 VPA**。

## 4. 预测式伸缩：消除反应滞后

反应式伸缩永远追着流量跑（指标延迟 + 冷启动延迟），2026 年的重点是预测式伸缩——**提前于需求扩容**，三条实现路径：

- **CronHPA / 定时预伸缩**：按时间表提前扩容（工作日早高峰、大促整点），适合规律性流量；局限是处理不了不定期营销事件。
- **AHPA（自适应预测伸缩）**：阿里云开源组件，分析历史负载指标预测未来需求提前扩容，适合直播、电商等周期性波动负载；约束是**至少需要 7 天历史数据**生成预测。
- **ML 预测伸缩**：时间序列模型（LSTM/Transformer）在 CPU 达阈值前数分钟提前扩容——需要三件套：高分辨率指标管道（30 秒-1 分钟粒度）、能处理季节性与部署阶跃的模型、预测-实际差值反馈的定期重训闭环。研究趋势（2026）：多智能体强化学习、GPU 感知伸缩。

预测式伸缩的黄金组合是**与 HPA 并存**：CronHPA/AHPA 提前扩容兜住可预见的峰，HPA 处理不可预见的突发——"定时 + 反应"双保险。

## 5. 伸缩协同与成本治理

弹性伸缩落地一半靠工具，一半靠协同，三个高频问题：

- **HPA 与节点伸缩器打架**：HPA 要扩容但节点不够（Cluster Autoscaler 加节点有延迟）——`--scale-down-delay-after-add` 应 ≥ HPA 的缩容稳定窗口，Karpenter 的 `consolidateAfter` 建议 10 分钟，避免"HPA 还没确认缩容、节点已被回收"的抖动。
- **requests 规格是伸缩的地基**：2026 年行业数据——生产集群平均 CPU 利用率仅 8%，69% 的已请求 CPU 完全未用；requests 设大（请求 2000m 实际用 500m）导致 HPA 认为余量充足不缩容，资源浪费在 Pod 内部。**先做 right-sizing（VPA 推荐 + 压测数据校准规格），再上 HPA**，否则伸缩建立在错误的地基上。
- **伸缩与防护联动**：扩容要配合新实例预热（冷启动限流，[专题 7](../专题%207：分布式高并发%20&%20限流熔断降级/02-扩展模式与容量边界.md)）、限流阈值按新容量重算、缩容要等流量平稳（缩容过早=刚扛完峰值就砍掉一半容量）。

> 🎯 **核心要点**：容量评估"实例数 = 峰值 QPS/(单机拐点 × 0.7)"，水位线高 70%/低 40%；HPA 三件坑（v2 API/必须设 requests/稳定窗口调优），本质是反应式；KEDA 事件驱动补 HPA 盲区（队列深度/缩容到零），VPA 与 HPA 避免同指标冲突；预测式伸缩（CronHPA/AHPA 需 7 天历史/ML）提前扩容与 HPA 双保险；伸缩协同注意节点伸缩器节奏、先 right-sizing 再上 HPA（CPU 利用率仅 8% 的行业数据）、扩容配预热限流。
