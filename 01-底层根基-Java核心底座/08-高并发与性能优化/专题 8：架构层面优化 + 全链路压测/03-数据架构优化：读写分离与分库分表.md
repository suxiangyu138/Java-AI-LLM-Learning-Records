## 1. 演进顺序：缓存 → 读写分离 → 分库分表

数据架构优化有严格的演进阶梯，**跳过前级直接上后级是事故源头**：

1. **缓存前置**：读多写少场景先用缓存挡住 90%+ 读流量（[专题 5](../专题%205：缓存体系专题/00-总览.md)），此时数据库压力已大幅下降——绝大多数系统到此为止。
2. **读写分离**：缓存命中率到顶后读流量仍超单库读能力（或需要读扩展），主从复制 + 读走从库，读容量翻倍。
3. **分库分表**：写流量超单库写入上限，或单表数据量过大（>千万级）导致索引性能劣化，才动分库分表。

判断"是否该拆"的唯一依据是压测数据（[专题 1](../专题%201：性能理论基础/07-容量规划与水位线.md) 的拐点方法），而不是"表大了就该拆"。分库分表是**最后手段**：查询复杂度、跨库事务、运维成本都在这里爆发，且几乎不可回退——上线前必须有完整的压测验证与回滚预案。

## 2. 读写分离：主从复制与延迟治理

读写分离基于 MySQL 主从异步复制：主库独占写（Insert/Update/Delete），从库承载读（Select），读请求按策略（轮询/权重/随机）路由到从库。收益是读容量线性扩展，代价是**复制延迟**——主库写入后从库毫秒到秒级滞后，读到旧数据。

延迟治理的四个标准动作：

- **事务内读强制走主库**：同一事务里先写后读，读必须命中主库，否则读到旧值（ShardingSphere 的 `transactionalReadQueryStrategy` 参数即为此设计）。
- **关键读强制主库**：支付结果、库存余量等"读后即决策"的接口用 Hint 强制主库（`setWriteRouteOnly()`），容忍延迟的读（列表、详情）走从库。
- **延迟敏感业务降级方案**：写后立即跳转的页面（下单成功页）直接读主库或从缓存读自己刚写的数据。
- **从库延迟监控**：`Seconds_Behind_Master` 超阈值告警，延迟大时读流量降级到主库。

读写分离的正确姿势是"**大多数读从库、敏感读主库**"，一刀切全走从库会在高延迟场景翻车。

## 3. 分库分表：拆分维度与分片键

分库分表解决两个不同的问题，常被混为一谈：

- **分库（垂直/水平）**：垂直分库按业务域拆库（订单库、用户库），解决单库连接数瓶颈；水平分库按分片键把数据分散到多库，解决单库容量与写入上限。
- **分表（水平为主）**：单表数据量大时按分片键拆多表（如 order_id 取模 64 表），解决单表索引退化。

**分片键选型是分库分表的灵魂**，三个约束：

1. **覆盖高频查询**：不带分片键的查询 = 全库全表扫描（ShardingSphere 会对无分片键 SQL 做全路由，性能灾难）——分片键必须是你业务最高频的查询条件（订单表用 user_id 或 order_id，用户表用 user_id）。
2. **数据分布均匀**：取模/哈希保证数据均匀，否则热点分片把容量吃掉。
3. **支持范围查询**：分片键若支持范围（如按时间），要设计好"时间 + 取模"组合，否则范围查询跨全部分片。

**广播表**是配套设计：字典、配置等小表（<万级）不分片，全量同步到每个库，与分片表 JOIN 时避免跨库。

## 4. ShardingSphere 5.5.x 落地

Apache ShardingSphere 是 Java 生态事实标准，2026 年版本线 5.5.x（5.5.3 于 2026 年发布），技术栈基准 JDK 17 + Spring Boot 3.3.x + MySQL 8.x。5.5.3 的关键演进是**可插拔 BOM 微内核架构**：数据分片、读写分离、数据加密、脱敏全部剥离为独立插件，按需引入——依赖不再臃肿，且 SQL 兼容度覆盖 MySQL/PostgreSQL/Oracle/Doris/Hive。集成方式：JDBC 模式（应用内路由，推荐轻量场景，5.3.x+ 用 Driver 模式）与 Proxy 模式（独立代理，多语言接入）。

两个高频实战点：**Hint 强制路由**（`HintManager.setWriteRouteOnly()`）解决延迟敏感读；**分布式 ID** 内建雪花算法自动回填分片键，避免拆表后 ID 冲突（雪花算法原理与时钟回拨见[雪花算法体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/08-分布式系统与架构/雪花算法/00-雪花算法知识体系总览.md)）。仓库内 [MySQL 体系的分库分表章节](../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MySQL/08-分库分表与高可用.md) 有更细的 SQL 兼容性与路由规则，本讲聚焦架构决策。

## 5. 拆分后的分布式事务

拆分后单库事务变成跨库操作，一致性方案二选一：

- **XA 强一致（2PC）**：适合短事务、强一致要求（支付），代价是性能与锁时间（ShardingSphere 支持 XA）。
- **Seata AT 柔性事务（BASE）**：生产推荐——业务无侵入（注解 + 全局事务），AT 模式用 undo_log 补偿，性能远好于 2PC；TCC 模式适合复杂场景（[Seata 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/06-Spring全家桶/Spring组件汇总/Spring%20Cloud%20微服务全家桶（分布式）/Spring%20Cloud%20Alibaba（阿里实现，属于%20Spring%20Cloud%20生态实现）/Seata：分布式事务/00-Seata知识体系总览.md) 全套）。

架构层的铁律：**能不用分布式事务就不用**——用"本地事务 + 消息 + 幂等 + 对账"的最终一致方案替代跨库事务，是 2026 年拆分实践的第一选择；分布式事务是兜底，不是默认。

> 🎯 **核心要点**：数据架构演进严格按"缓存→读写分离→分库分表"，跳过前级直接拆是事故源头；读写分离必须处理复制延迟（事务内读主库/关键读 Hint 强制主库/延迟监控）；分片键选型三约束（覆盖高频查询/分布均匀/支持范围），广播表配套；ShardingSphere 5.5.3 BOM 插件化按需引入；跨库事务优先"本地事务+消息+幂等"替代，分布式事务是兜底。
