## 1. 大促压测全流程：三张清单

2026 年 618 复盘的共识：**压测别急着跑，先把三张清单过一遍**。

1. **链路清单**：全链路依赖拓扑完整——从网关到数据库的每个服务、中间件、外部依赖都在压测范围内且有监控（漏掉一个依赖，压出的容量就虚高一段）。
2. **场景清单**：覆盖全部高压场景——秒杀脉冲、优惠券领取、直播陡增（[06 篇](06-全链路压测方法论.md) 的场景设计），每个场景有验证目标与通过标准。
3. **数据清单**：影子库/缓存/队列就绪，造数贴近生产分布（热点、大 key 都要有），压完一键清理（[07 篇](07-流量染色与影子链路.md)）。

三张清单之后是节奏：**T-30 全链路压测锁定容量基线 → T-14 故障注入演练（验证[专题 7](../专题%207：分布式高并发%20&%20限流熔断降级/00-总览.md) 的限流熔断降级在压力下生效）→ T-7 复核规则配置 → T-1 预热与监控核对**——压测不是一次事件，而是大促前持续收紧的闭环。

## 2. 压测执行的五步闭环

每次压测执行按五步闭环，缺一步结果不可信：

1. **定目标**：本次压测验证什么（容量拐点/限流触发/降级预案），目标值量化（"秒杀场景 P99<300ms 且零超卖"）。
2. **造环境**：影子链路就绪、施压机就位（数量=目标 QPS/单机施压能力）、监控模型打开（含压测流量过滤视图）。
3. **压与看**：按业务模型曲线加压（爬坡→平台→退坡），实时盯监控（吞吐、P99、资源利用率、错误率），**发现异常立即停止**而不是压完再说。
4. **归因**：Little's Law 找拐点、按链路追踪归因到具体服务/中间件（ForceBot 式端到端绑定），产出"瓶颈在哪一层"的明确结论。
5. **改进与回归**：按归因优化（缓存/异步/拆分，[01 篇](01-架构优化全景与分层地图.md) 的收益排序），复压验证收益，更新容量基线与限流阈值（[专题 7 的 0.7-0.8 红线](../专题%207：分布式高并发%20&%20限流熔断降级/02-扩展模式与容量边界.md)）。

压测报告的归档格式是闭环的最后一环，建议固定四段式：**结论**（本次压测通过/未通过、关键数字）、**瓶颈归因**（瓶颈层 + 证据指标）、**优化建议**（按收益排序的 action 列表 + 责任团队）、**基线更新**（新拐点吞吐/P99、限流阈值、扩容水位线）。报告的价值在历史对比——大促前把历次报告摊开看容量趋势，比任何人的记忆都可靠；没有归档的压测等于没压。

## 3. 故障速查表

| 现象 | 第一怀疑 | 处置 |
|---|---|---|
| 压测 P99 劣化但吞吐没涨 | 慢调用在瓶颈层堆积 | 链路追踪定位瓶颈服务，查线程池/连接池 |
| 目标 10 万 QPS 压不满 | 施压机不够或单机准确性不足 | 加施压机，逐机验证实际 RPS |
| 压测数据污染线上 | 染色标记透传断层 | 查网关→RPC→MQ 标记链路，影子资源隔离 |
| 压测结果与单接口差 5 倍 | 依赖链路瓶颈（同步 RPC/DB） | 归因到具体依赖，做异步化或缓存 |
| 扩容后容量没涨 | 冷启动（JIT/缓存未预热） | 新实例预热限流 + 慢启动权重 |
| HPA 不伸缩 | requests 未设置（静默失效） | 检查 resources.requests 与 v2 API |
| 缩容把容量砍没了 | 稳定窗口/节点回收节奏不匹配 | 缩容窗口 600s，协调 Cluster Autoscaler |

## 4. 毕业检查单

- 能画出自己系统六层架构地图，并指出当前瓶颈层
- 能说出无状态化判断标准与三层业务拆解方法
- 理解读写分离延迟治理与分片键三约束，能判断是否该分库分表
- 能用 RPO/RTO 推导容灾方案并说明同城双活/两地三中心的成本差异
- 掌握全链路压测五类模型与三张清单，能设计自己的压测场景
- 理解流量染色与影子资源原理，能排查标记透传问题
- 知道 HPA/VPA/KEDA/预测式伸缩的选型与坑，能完成容量评估计算
- 能执行"压测→归因→优化→回归"闭环并更新限流阈值
