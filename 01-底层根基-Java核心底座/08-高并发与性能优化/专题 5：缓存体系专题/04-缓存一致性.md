## 1. 四种双写策略对比

数据库与缓存的更新顺序之争，业界实践沉淀出四种策略：

| 策略 | 时序 | 不一致窗口 | 结论 |
|---|---|---|---|
| 先更 DB → 再更缓存 | 写路径两次写 | 可能永久不一致 | ❌ 不用 |
| 先更 DB → 再删缓存 | 写删 + 懒加载回填 | 1-5ms | ✅ 主流首选 |
| 先删缓存 → 再更 DB | 删后读请求回填旧值 | 可能永久脏数据 | ❌ 不用 |
| 监听 binlog 异步删 | 中间件解耦删除 | <100ms | ✅ 核心数据 |

**先更 DB 再更缓存**被淘汰的原因：高并发下两个写请求并发时，后提交的 DB 更新反而先完成缓存更新，新数据被旧数据覆盖，形成永久不一致。**先删缓存再更 DB**被淘汰的原因：删除缓存与更新 DB 之间有空窗，读请求会读 DB 旧值并回填缓存，同样产生永久脏数据。两条死路都是"缓存里存了旧值且没人再删它"，而**删除缓存 + 懒加载**让缓存永远是"查了才回填"，天然规避了互相覆盖。

## 2. Cache Aside：为什么先更新 DB

Cache Aside 是缓存读写的标准模式，读路径"先查缓存，未命中查 DB 后回填"，写路径"先更新 DB，再删除缓存"。删除而非更新，是因为：

- **删除成本低**：删掉后下次读自动回填最新值，不需要知道新值长什么样（更新则需要先查出新值，多一次查询）。
- **避免覆盖竞态**：写并发下"更新缓存"存在覆盖旧值问题，删除则不存在——缓存里永远只有"读请求主动回填"的数据。
- **失败可重试**：删除失败时，读请求最终也会回填新值；而更新失败则缓存永远留着旧值。

先更 DB 后删缓存的极端并发下仍存在 1-5ms 脏读窗口：更新 DB 与删除缓存之间，读请求读到 DB 旧值并回填。绝大多数业务（商品信息、内容、配置）可以容忍；容忍不了的上延迟双删或 Canal。

## 3. 延迟双删：流程与局限

延迟双删在 Cache Aside 基础上加一道兜底：**删除缓存 → 更新 DB → 延迟 N ms → 再次删除缓存**。第二次删除用于清除"更新期间并发读请求回填的旧缓存"。

延迟时间 N 的确定是核心：必须大于"读请求查 DB + 写回缓存"的完整耗时，行业经验为 200-500ms（读请求总耗时约 20-100ms），并叠加数据库主从同步延迟（读从库时新数据可能未同步）。严谨口径：`N = 平均读耗时 × 1.5 + 主从同步最大延迟`。

局限也必须认清：

- 阻塞式 sleep 会拖慢写路径，生产上用 MQ 延迟消息替代（RocketMQ 延迟消息/Redis ZSET 定时扫描）。
- 第二次删除失败没有保障，需要重试机制（MQ 重试 + 死信告警）。
- 高并发下仍可能"第二次删除前已被再次回填"。
- 分布式多实例部署时，各实例的读回填窗口不同步，双删无法完全覆盖。

所以**延迟双删是兜底不是保证**——它把窗口从毫秒级压到接近零，但删除动作本身需要可靠投递。

## 4. Canal 订阅 binlog：<100ms 窗口

核心数据（库存、价格、余额）用 Canal 方案实现解耦与近实时一致：

```text
业务更新 DB → MySQL binlog(row 格式) → Canal 伪装从库拉取
→ 解析出表名 + 主键 + 变更数据 → 投递 MQ → 消费服务删除/重建缓存
```

**优势**：业务代码零侵入（完全不管缓存）；异步执行不阻塞主链路；MQ 投递 + 重试保证删除最终到达，即使消费方宕机或 Redis 瞬时不可用也能最终完成失效；支持多表多实例扩展。**代价**：引入 Canal + MQ 两个组件，运维复杂度上升；存在 <100ms 的延迟窗口；本质仍是最终一致而非强一致。

阿里、美团等一线电商的实践组合：**核心数据用 Canal 监听 binlog 异步删缓存，非核心数据用 Cache Aside 容忍短暂不一致，强一致要求的数据（支付对账）干脆不用缓存直读 DB**。2026 年的行业共识是"Cache Aside 为基础 + 延迟双删兜底 + Canal 做防火墙级保障"，把不一致窗口控制在百毫秒内。

Canal 落地的四个工程前提：binlog 必须开 **row 格式**（statement 格式只能拿到 SQL 语句，无法知道具体改了哪行）；Canal 实例要**高可用部署**（主备 + 位点持久化，故障切换后从上次位点续传，避免丢事件）；消费侧按表名做**幂等去重**（binlog 事件可能重复投递，删除缓存天然幂等，重建缓存需判版本）；主从复制延迟会拉大窗口——读从库 + 缓存失效的场景要评估延迟叠加。Redis 侧兜底：Canal 消费时带上消息唯一 ID 做防重，MQ 消费失败进死信队列人工介入。

另一种轻量思路是**版本号方案**：缓存 value 携带版本号（或 DB 行版本），读请求发现版本落后于 DB 时主动重建。适合"读侧有能力校验"的场景，但每次读都要多查一次版本，成本高于删除方案，生产上少见，了解即可。

## 5. 一致性分级选型

| 业务类型 | 方案 | 不一致窗口 | 实现成本 |
|---|---|---|---|
| 非核心读多数据（内容/配置） | Cache Aside | 1-5ms | 低 |
| 核心数据中并发（商品/订单详情） | 延迟双删（MQ 异步） | ~500ms → 近零 | 中 |
| 核心数据高并发（库存/价格） | Canal + MQ | <100ms | 高 |
| 零容错（支付/余额对账） | 不用缓存直读 DB | 0 | — |

选型的判断顺序：**数据改错了会怎样？** 会扣钱、算错账 → 直读 DB；会显示旧价、旧库存 → 看写频度，高写用 Canal，低写用双删；无感（昵称、头像、文章内容）→ Cache Aside 即可。另外注意多级缓存的一致性：本地缓存与 Redis 之间同样需要失效传播——更新 DB 后通过 MQ/Redis Pub/Sub 广播失效事件，各实例监听后执行本地驱逐（[05 篇](05-本地缓存：Caffeine与Spring%20Cache.md)）。

> 🎯 **核心要点**：四种双写策略只有"先更 DB 再删缓存"是活路，因为删除 + 懒加载天然规避覆盖竞态；延迟双删是兜底不是保证，延迟 N 必须覆盖读回填全耗时且删除要可靠重试；核心数据用 Canal 订阅 binlog 异步失效，零容错数据直读 DB 不用缓存；一致性的本质是用可度量的窗口换性能，选型先问"改错了会怎样"。
