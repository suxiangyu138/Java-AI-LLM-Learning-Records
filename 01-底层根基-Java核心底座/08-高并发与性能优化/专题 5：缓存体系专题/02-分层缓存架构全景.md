# 02 分层缓存架构全景

## 1. 六层缓存链路

一条完整的高并发读链路从上到下依次是：

```text
浏览器缓存（Cache-Control / ETag）
    ↓ 未命中
CDN 边缘节点（静态资源就近分发）
    ↓ 未命中
Nginx 缓存（proxy_cache 页面/接口快照）
    ↓ 未命中
本地缓存（Caffeine，进程内 L1）
    ↓ 未命中
分布式缓存（Redis，集群共享 L2）
    ↓ 未命中
数据库（InnoDB Buffer Pool 已是最后一层缓存）
```

每层解决一类问题：浏览器层省网络请求，CDN 层把静态内容推到用户身边，Nginx 层扛住页面级重复请求，本地缓存用微秒级延迟挡住单机热点，Redis 层让所有实例共享命中，数据库层只承担真正的冷数据回源。**设计原则是"每层只缓存自己的职责"**——浏览器不缓存用户私有数据，CDN 不缓存动态接口，本地缓存不缓存全量数据，避免跨层越权导致的缓存污染与失效混乱。

## 2. 浏览器缓存与 CDN

浏览器缓存是成本最低的一层——命中后**连请求都不发**。通过响应头控制：`Cache-Control: max-age` 定有效期，`ETag`/`Last-Modified` 做协商缓存。静态资源用文件名哈希 + 超长 max-age（如 1 年 + `immutable`），更新即换文件名，永不失效问题。

CDN 层把静态内容缓存到边缘节点，衡量指标要拆两个口径：**请求命中率**（关联加载延迟）与**字节命中率**（关联回源带宽与流量费用）。大文件频繁回源时会出现"请求命中率 95% 但字节命中率只有 60%"的流量漏洞，两个指标必须同时看。2026 年的 CDN 实践共识：

- **动静分离**：`/api/` 动态请求走动态加速（不缓存或短 TTL 5 分钟以内），图片/CSS/JS 走静态缓存（长 TTL）。
- **TTL 分层**：不变资源 1 年，常规静态资源 7-30 天，新闻活动页 12-24 小时，HTML 几分钟到 1 小时。
- **预热与刷新**：大促前主动预热热点内容（[09 篇](09-缓存监控与容量规划.md)详述），更新时用 URL/目录/正则三种刷新方式，优先版本化文件名避免清缓存。
- **回源合并**：多个边缘节点对同一资源回源时汇聚为一个请求，峰值回源可降 80%。

静态资源请求命中率稳定在 95% 以上才健康，低于 90% 说明缓存规则有漏洞。

## 3. Nginx 与本地缓存

Nginx 在接入层用 `proxy_cache` 缓存页面快照与接口响应，命中时完全不进应用。适合登录无关的页面、秒杀静态页、公告类接口。配置三件套：`proxy_cache_path` 定义缓存目录与大小，`proxy_cache_key` 定义缓存键（默认含 Query String，需归一化），`proxy_cache_valid` 按状态码分档缓存时间（如 200 缓存 60s、404 缓存 10s——**404 也缓存能防穿透打到应用**）。两个进阶参数：`proxy_cache_lock` 开启缓存锁，同一资源并发回源时只放一个请求进应用（Nginx 层的单飞）；`proxy_cache_use_stale` 允许上游故障时返回过期缓存（Nginx 层的降级兜底）——这两个参数把 [08 篇](08-缓存并发控制与降级.md) 的击穿防护与故障降级下沉到了接入层。

需要绕过 Nginx 缓存的请求用 `proxy_cache_bypass` 按 Cookie/Header 判定（登录用户、AB 实验流量必须穿透），否则会串数据。

**本地缓存**（Caffeine）是链路中延迟最低的一层（微秒级），也是单机 QPS 上万时最容易忽视的一层。它缓存两类数据：**单机热点**（同一实例反复读的 key）与**不可变配置**（字典、白名单）。但本地缓存各实例独立、重启即失、占用堆内存，容量与一致性需要专门治理（[05 篇](05-本地缓存：Caffeine与Spring%20Cache.md)）。典型收益：接口 RT 从 Redis 的 1-3ms 降到本地命中的 50-200μs，单机 QPS 翻数倍。

## 4. 分布式缓存与数据库缓冲池

Redis 作为 L2 承担集群级共享缓存：多实例一致命中、容量可规划、支持 TTL 与淘汰策略，是缓存链路的枢纽（[06 篇](06-分布式缓存：Redis与Memcached.md)）。它缓存各实例都能命中的热点数据，如商品详情、用户资料、聚合统计。

数据库自己还有最后一层——**InnoDB Buffer Pool**。即使前五层全部失效，热数据页仍在内存中，DB 仍能扛住相当压力。因此缓存优化要把 Buffer Pool 命中率（目标 99%+）纳入视角：内存远大于热数据时，Buffer Pool 本身就是最大的缓存。这也是为什么"缓存全部失效时 DB 还能撑几分钟"经常成立——但这几分钟是救命的降级窗口，不是常态（[08 篇](08-缓存并发控制与降级.md)）。

## 5. 动静分离与缓存键设计

缓存键设计决定命中率的上下限，核心原则是**"同一资源对应唯一缓存键"**：

- **忽略无关参数**：`?t=123456`、`?from=xxx` 等无效参数必须从缓存键剥离（实测可把命中率从 70% 提到 92% 以上）。
- **路径归一化**：小写化、去除末尾斜杠、统一协议（HTTP/HTTPS 同键）。
- **版本化更新**：文件名带哈希或版本号，更新即新 URL，天然免疫旧缓存。
- **缓存键分类前缀**：`user:1001`、`goods:88` 这类键名是治理与批量操作的基础（[07 篇](07-热点Key与BigKey治理.md)的批量识别依赖它）。

各层缓存的数据特征与失效方式差异很大，设计时按下表对号入座：

| 层 | 缓存什么 | 典型 TTL | 失效方式 |
|---|---|---|---|
| 浏览器 | 静态资源、页面快照 | 1 年（哈希文件名）/ 数分钟 | 换文件名、Cache-Control |
| CDN | 图片/CSS/JS、活动页 | 7-30 天 / 12-24 小时 | 预热、URL 刷新 |
| Nginx | 页面快照、接口响应 | 秒级-分钟级 | proxy_cache_purge、TTL |
| 本地缓存 | 单机热点、不可变配置 | 5-10 分钟 | 失效广播、刷新 |
| Redis | 集群共享热点（详情/资料/统计） | 30 秒-1 小时按变更频率 | 删除、TTL、Canal |
| DB Buffer Pool | 热数据页 | 无（内存页管理） | LRU 页淘汰 |

规律：**越靠上层 TTL 越长、数据越静态；越靠下层 TTL 越短、数据越动态**——上层的长 TTL 靠"版本化更新"免疫，下层的短 TTL 靠"主动失效"控制。TTL 倒挂（上层短、下层长）是最常见的配置错误，会让上层缓存永远打不中。

> 🎯 **核心要点**：缓存是浏览器 → CDN → Nginx → 本地 → Redis → DB 六层链路，每层只缓存自己的职责数据，逐层卸压；CDN 要同时盯请求命中率与字节命中率，动静分离 + TTL 分层 + 预热刷新是 2026 年标配；缓存键设计（忽略参数、归一化、版本化）决定命中率上下限；Buffer Pool 是最末端的缓存，缓存全失效时它是最后的降级窗口。
