## 1. 原子抢写：SETNX + EX

缓存击穿（[03 篇](03-缓存三大问题：穿透击穿雪崩.md)）的互斥锁解法，核心是一条 Redis 原子命令：

```java
// 抢锁：仅当锁不存在时设置，EX 保证锁自动过期
Boolean ok = redis.set("lock:goods:88", "req-abc123", "NX", "EX", 5);
if (ok) {
    try {
        Goods goods = queryDb(88);          // 只有抢到锁的请求回源
        redis.set("goods:88", goods, 300);  // 回填缓存
    } finally {
        // 释放锁：用 Lua 比较锁值再删，防止误删他人锁
        redis.eval("if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end", ...);
    }
} else {
    // 未抢到锁：等待后重读缓存（自旋，带超时上限）
    Thread.sleep(50);
    return readCache(88);
}
```

四个关键点：**锁值必须唯一**（如 `req-` + UUID），释放时用 Lua 比较后删除——否则锁过期后其他请求持锁，本请求误删；**锁过期时间 > 回源耗时**（DB 查询 + 回填，建议 ≥5 秒）；**抢锁失败走等待重试而非直接打 DB**，否则锁白抢；**绝不可先 GET 再 SETNX**——两条命令之间是竞态窗口，高并发下照样打穿。

## 2. 请求合并：singleflight

singleflight（Java 可用 ConcurrentHashMap + CompletableFuture 或第三方库实现）保证：**同一 key 在同一时刻只有一个回源在飞**，其他并发请求挂起等待并共享该次结果——1000 个并发查同一 key，DB 只被查 1 次。正确使用姿势：

- **完整闭环缺一不可**：先查缓存 → 命中直接返回 → 未命中进单飞回源 → 成功后写缓存 → 返回。漏掉任何一环等于白加。
- **单飞对象全局复用**：必须声明为单例，绝不能每次请求 new——否则每次都是新实例，合并失效。
- **只包最重的操作**：单飞只包 DB 查询/RPC 那一步，别包整个业务逻辑。
- **key 稳定**：用缓存 key 或业务 ID 做单飞键，不能带时间戳/随机数，否则永远合并不上还撑爆内存。
- **回调内处理超时与错误**：回源失败不写缓存，避免脏数据；单飞本身无超时，必须在回调内设 deadline。

单飞与 SETNX 的关系：**SETNX 拦写冲突（跨实例），单飞合并读重放（进程内）**。Java 的进程内单飞可用 `ConcurrentHashMap<String, CompletableFuture<?>>` 实现：

```java
ConcurrentHashMap<String, CompletableFuture<Goods>> inflight = new ConcurrentHashMap<>();

public Goods get(Long id) {
    Goods g = readCache(id);
    if (g != null) return g;                        // ① 先查缓存
    CompletableFuture<Goods> future = inflight.computeIfAbsent("g:" + id, k ->
        CompletableFuture.supplyAsync(() -> {       // ② 只有第一个请求创建任务
            Goods db = queryDb(id);
            writeCache(id, db);                     // ③ 回填缓存
            return db;
        }));
    try {
        return future.get(2, TimeUnit.SECONDS);     // ④ 其余请求共享结果，带超时
    } catch (Exception e) {
        inflight.remove("g:" + id);                 // 失败要移除，否则后续请求永远卡住
        throw new RuntimeException(e);
    } finally {
        inflight.remove("g:" + id);                 // 成功也移除（可配合 TTL 防过期残留）
    }
}
```

实现要点：`computeIfAbsent` 保证并发下只创建一次任务；`remove` 在 finally 执行避免"永久卡死"（对应"单飞无 TTL、旧 key 不清理"的坑）；`future.get` 必须带超时，超时走降级。单飞只解决进程内并发，多实例部署时各实例分别合并，仍会各自回源一次——此时叠加 SETNX 或本地缓存（[05 篇](05-本地缓存：Caffeine与Spring%20Cache.md)）才能全局收敛。`@Cacheable(sync=true)` 就是 Spring 对进程内单飞的内置封装。

## 3. 逻辑过期与异步重建

逻辑过期方案：value 里内嵌逻辑过期时间，物理上永不过期：

```java
record CacheValue(Object data, long expireAt) {}

// 读路径：命中后先看逻辑时间
CacheValue v = read("goods:88");
if (v == null) return queryAndFill(88);
if (v.expireAt > now) return v.data;        // 未过期，直接返回
// 已逻辑过期：返回旧值 + 尝试异步重建（只允许一个线程重建）
tryReconstruct("goods:88", () -> { Goods g = queryDb(88); write("goods:88", g); });
return v.data;                               // 读路径零阻塞
```

优势：**读路径永远不会阻塞**——即使过期也先返回旧值，重建在后台进行；重建用 SETNX 或单飞保证只有一个线程执行。代价：数据在"重建完成前"短暂过期可见。适合读多写少、可容忍秒级陈旧的热点数据（商品详情、榜单、配置聚合）。与永不过期 + 后台刷新（[07 篇](07-热点Key与BigKey治理.md)）的区别：后者是主动定时刷新，前者是被读到过期才触发重建——逻辑过期对"未被读的 key"零开销。

## 4. 缓存故障降级

Redis 故障（宕机、超时、OOM 逐出）时，没有预案的业务直接雪崩。降级预案按梯度设计：

- **L1 兜底**：本地缓存继续服务热点数据，命中率越高，Redis 故障的影响越小（[05 篇](05-本地缓存：Caffeine与Spring%20Cache.md)）——这是"多级缓存"在故障场景的隐藏价值。
- **直连 DB + 限流**：Redis 不可用时读路径直接查 DB，同时用 Sentinel/网关对回源请求限流（QPS 降到 DB 可承受水位），超出部分降级返回默认值/空数据。**限流必须提前设好，不能故障现场拍脑袋**。
- **降级开关**：通过配置中心（Nacos/Spring Cloud Config）预设"缓存熔断开关"，故障时一键打开：跳过缓存读、关闭缓存写、停止预热任务，避免"缓存半死 + 重建风暴"互相踩踏。
- **写路径保护**：缓存写失败不能影响主流程——写缓存放在 try-catch 或异步链路里，Redis 抖动只是丢缓存不丢业务。

降级预案必须**演练**：定期做"杀 Redis 一半节点""主从切换"演练，验证限流阈值、降级开关、告警链路全通（[09 篇](09-缓存监控与容量规划.md)的演练与监控配合）。标准演练五步：① 通知——提前通告演练时间与影响面；② 注入故障——停掉一个 Redis 分片或模拟超时（慢命令注入）；③ 观测——验证降级开关自动/手动生效、限流水位正确、本地缓存仍在服务热点；④ 恢复——故障解除后验证缓存重建（预热/懒加载回填）不产生重建风暴；⑤ 复盘——记录"从故障到降级生效"的时长，超时即预案失败。2026 年生产实践：缓存故障演练纳入发布流程的回归项，和 [专题 9：故障复盘](../专题%209：故障复盘%20&%20真实线上案例/) 的机制对齐。

## 5. 兜底纪律

- **区分"查无"与"错误"**：`redis.Nil`（key 不存在）是预期行为，走缓存回填；连接超时/网络错误才走降级。混为一谈会把"查无"误判为故障，触发无谓降级。
- **缓存读写全链路超时**：客户端设 connect/read 超时（如 100ms），Redis 慢不拖业务——超时即降级，别让"等 Redis"变成"等死"。
- **失败不写缓存**：回源异常时不回填空缓存，避免把瞬时错误固化。
- **重建风暴防护**：缓存批量失效时，重建请求要节流（单飞 + 限流），防止"缓存恢复了，DB 却被重建压垮"。

> 🎯 **核心要点**：SETNX+EX 原子抢写拦跨实例写冲突（锁值唯一、过期 > 回源耗时、失败等待重试）；singleflight 合并进程内读重放（全局复用、只包重操作、回源失败不写缓存）；逻辑过期让读路径零阻塞、旧值秒级可见；Redis 故障靠"本地缓存兜底 + 直连 DB 限流 + 配置中心降级开关"三梯度预案，且必须演练；查无与错误分开、读写全链路超时、失败不写缓存是三条兜底纪律。
