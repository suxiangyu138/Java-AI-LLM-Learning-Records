## 1. 局部性：缓存成立的依据

缓存不是工程发明的技巧，而是计算机系统的基本规律——**局部性原理**（[CPU 缓存体系](../../05-计算机基础/计算机组成原理/缓存与Cache/00-缓存与Cache知识体系总览.md)同源）：

- **时间局部性**：刚访问过的数据很快还会被访问。用户浏览商品后返回、刷新，聚合统计被反复查询，都是时间局部性。
- **空间局部性**：访问某数据后，附近的数据也大概率被访问。程序顺序读数组、列表页拉取相邻分页，都是空间局部性。
- **二八定律**：20% 的热点数据承载 80% 的访问量。这是所有缓存策略成立的统计前提——只缓存少部分数据就能覆盖大部分请求。

判断一个场景适不适合缓存，先问两个问题：**数据是否被重复访问？重复访问是否集中在少数条目上？** 两个都答"是"，缓存就有价值；否则缓存只是在增加复杂度。

## 2. 收益模型：命中率决定价值

缓存的平均访问延迟由命中率决定。设缓存读取延迟为 L，未命中后回源总延迟为 M（含缓存读取），则：

```text
平均延迟 = 命中率 × L + (1 - 命中率) × M
```

以 Redis（约 0.5ms）+ MySQL（约 10ms）为例：命中率 90% 时平均延迟约 1.45ms；命中率 99% 时约 0.6ms；命中率 0 时 10ms。**命中率从 90% 提到 99%，延迟降低近 60%**——这就是为什么大厂把命中率当作核心 KPI（[09 篇](09-缓存监控与容量规划.md)的告警阈值由此而来）。

收益还有一个易被忽略的维度：**DB 侧 QPS 的放大倍数**。设业务读 QPS 为 10 万，命中率 95% 时 DB 只承受 5000；命中率降到 80% 时 DB 要扛 2 万——4 倍压力。命中率不是"体验优化"，是数据库容量的生命线。

**收益曲线是递减的**：命中率从 0 提到 80% 很容易（缓存 Top 热点即可），从 80% 提到 95% 需要更精细的键设计与容量投入，从 95% 提到 99% 则要处理长尾数据——每提升 1 个百分点的边际成本都在上升。因此实践上先做"够用"的缓存（覆盖二八中的八），再按监控数据决定是否投入长尾（[09 篇](09-缓存监控与容量规划.md)的命中率看板就是决策依据）。

**缓存粒度是命中率之外的第二个杠杆**：细粒度（按字段缓存）命中率高但回填复杂、聚合成本高；粗粒度（按页面/对象缓存）实现简单但变更时整块失效。商品价格频繁变、描述很少变——如果按整对象缓存，价格一变描述也失效；按字段拆分后，价格字段失效只波及价格。粒度选择的原则是"**按变更频率切分，高频变更的字段独立成更细的缓存**"，与一致性成本直接挂钩（[04 篇](04-缓存一致性.md)）。

## 3. 缓存的三大价值

缓存的收益可以量化到三个层面，任何一个都足以支撑引入决策。

- **降延迟**：把数据从毫秒级（DB）或亚毫秒级（Redis）挪到微秒级（本地内存）甚至纳秒级（CPU）。用户体感上 P99 的改善往往最先来自缓存。
- **削峰**：缓存把访问压力挡在数据库之前。大促流量放大数倍时，DB 连接池是最脆弱的资源，缓存是第一道也是性价比最高的防线（[02 篇](02-分层缓存架构全景.md)的六层链路逐层卸压）。
- **降本**：命中率提升直接换算成实例数。CDN 命中率从 80% 提到 99%，回源成本下降约 95%；Redis 缓存挡住 DB 扩容，一台 DB 的单价远超一台缓存。

## 4. 什么场景不该用缓存

- **写多读少**：写入后几乎不被读，缓存命中率极低，每次写入还要付出失效/更新成本，纯亏。
- **强一致要求**：交易、支付、库存扣减等对一致性零容错的场景，缓存的不一致窗口不可接受。这类数据应直读 DB，用索引与连接池优化代替缓存（[04 篇](04-缓存一致性.md)的选型表明确此边界）。
- **一次性数据**：验证码、一次性令牌，用完即弃，缓存无意义。
- **体量极小**：全表就几百行且查询已命中索引，缓存收益小于维护成本。
- **数据高度个性化**：每个用户的缓存键几乎都不重复，命中率天然低下，缓存变成分布式存储，失去意义。

## 5. 引入缓存的隐性成本

缓存从来不是"加了就完事"，它同时引入了四类成本，后续各篇逐一展开：

- **一致性问题**：缓存与数据库两份数据，更新时序处理不当就是脏数据——需要一致性方案兜底（[04 篇](04-缓存一致性.md)）。
- **失效风暴风险**：穿透、击穿、雪崩三个经典故障全部因缓存而生（[03 篇](03-缓存三大问题：穿透击穿雪崩.md)）。
- **内存与容量成本**：缓存数据占内存，本地缓存占应用堆，需要容量规划与淘汰策略（[06 篇](06-分布式缓存：Redis与Memcached.md)、[09 篇](09-缓存监控与容量规划.md)）。
- **故障域扩展**：缓存实例故障时业务要能降级存活，否则缓存从"加速器"变成"单点"（[08 篇](08-缓存并发控制与降级.md)）。

引入缓存的决策可以收敛成一个三问模型：**数据会被重复读吗？重复读集中在少数 key 上吗？读到的数据允许短暂陈旧吗？** 三个都答"是"，缓存带来的延迟/削峰/降本收益大概率超过一致性与运维成本；任何一个答"否"，就需要重新考虑缓存粒度、TTL 策略甚至是否引入——比如"重复读集中"不成立时，命中率天花板就在 50% 以下，缓存退化为分布式存储，不如直读 DB 加索引。判断在动手之前完成，可以省掉后面所有治理成本。

> 🎯 **核心要点**：局部性原理（时间/空间/二八）是缓存成立的物理依据；平均延迟与 DB 压力都由命中率决定，命中率是缓存价值的生死线；缓存只适用于"重复访问 + 热点集中"的数据，强一致、写多读少、一次性数据不该用缓存；一致性、失效风暴、容量、故障域四类成本必须在引入缓存前想清楚。
