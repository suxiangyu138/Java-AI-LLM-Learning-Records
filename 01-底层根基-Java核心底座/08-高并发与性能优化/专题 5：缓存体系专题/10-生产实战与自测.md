## 1. 实战：秒杀详情页多级缓存

**场景**：秒杀活动商品详情页，目标 P99 < 200ms，峰值读 QPS 5 万，商品信息变更不频繁、价格变更分钟级可容忍。

**基线**：Redis 单层缓存，命中率 85%，P99 420ms——DB 慢查询在缓存 Miss 时被打穿。

**改造五步**（每步可归因）：

1. **预热**：活动前 15 分钟按商品清单灌入 Redis + Caffeine，首请求命中率从 0 提到 95%（[09 篇](09-缓存监控与容量规划.md)）。
2. **加 L1 本地缓存**：Caffeine `refreshAfterWrite(5m) + expireAfterWrite(10m)`，详情页热点商品命中 L1，单机 QPS 从 200 提到 2000+，P99 降到 80ms（[05 篇](05-本地缓存：Caffeine与Spring%20Cache.md)）。
3. **防击穿**：`@Cacheable(sync=true)` 进程内单飞 + 回源路径 SETNX 互斥，模拟"缓存全失效"压测：DB 只承受 1/N 回源（[08 篇](08-缓存并发控制与降级.md)）。
4. **过期随机化**：TTL 基础 300s + 随机 0-60s，防整点雪崩（[03 篇](03-缓存三大问题：穿透击穿雪崩.md)）。
5. **监控与预案**：命中率看板（Redis/Caffeine 双指标）+ "缓存熔断开关"（Redis 故障一键直连 DB + 限流）；演练"杀一个 Redis 分片"，验证降级链路（[09 篇](09-缓存监控与容量规划.md)、[08 篇](08-缓存并发控制与降级.md)）。

**结果**：命中率 85% → 97%（Redis）+ 65%（L1 命中率，含回源），P99 420ms → 60ms，DB 读 QPS 从 7500 降到 1500。

**过程中的三个坑**（都是前九篇讲过的知识在真实环境的具体形态）：① 首轮只加 Redis 空值缓存没做参数校验，压测脚本用随机 ID 打流量，空值 key 占满内存——空值缓存必须限 TTL 30-60 秒并配合布隆过滤（[03 篇](03-缓存三大问题：穿透击穿雪崩.md)）；② Caffeine 首版 `expireAfterWrite` 单独使用，热点商品整点集体失效造成本地缓存雪崩——换成 `refreshAfterWrite + expireAfterWrite` 双配置后消失（[05 篇](05-本地缓存：Caffeine与Spring%20Cache.md)）；③ 大促压测发现 Redis 单分片 CPU 打满，`HOTKEYS` 一查是某爆款商品 key 占了 40% 流量——多副本扩散后单分片压力降 60%（[07 篇](07-热点Key与BigKey治理.md)）。

## 2. 生产纪律清单

1. maxmemory 显式设置，淘汰策略显式选择（缓存场景绝不用 noeviction）。
2. 所有缓存 key 有统一前缀规范，key 设计可治理（批量操作/识别的前提）。
3. 缓存读写全链路超时（connect/read 各 ≤100ms），超时即降级不阻塞。
4. 空值缓存 + 过期随机化 + 防穿透三件套进代码模板。
5. 热点 key 有识别机制与治理方案，大促清单提前圈定。
6. 缓存写失败不影响主流程（try-catch 或异步）。
7. 配置中心管理 TTL/容量/开关，变更可灰度可回滚。
8. 命中率监控上墙，突降告警联动发布记录。
9. 降级预案成文并演练，Redis 故障演练进发布回归。
10. 代码评审必问三件事：缓存 key 是否规范、value 是否超红线、有没有防击穿。

## 3. 报错速查十条

| 报错/现象 | 原因 | 处理 |
|---|---|---|
| OOM command not allowed | maxmemory 满 + noeviction | 改淘汰策略或扩容 |
| Redis connection refused | 实例宕机/网络不通 | 查 Sentinel/Cluster 状态，走降级 |
| Read timeout | 客户端超时设置过短或大 key | 调超时、查 big key（[07 篇](07-热点Key与BigKey治理.md)） |
| 命中率突降 >10% | 发布变更/TTL 异常/热点漂移 | 联动发布记录查代码，查过期分布 |
| evicted_keys 持续增长 | 容量不足 | 扩容或优化 value 体积 |
| DEL 卡住 Redis 数秒 | 大集合阻塞删除 | 改用 UNLINK |
| 分片内存水位不均 | 热点 key / big key 集中 | 多副本扩散 / 拆分 |
| Cluster 槽位迁移报错 | 扩容中访问 | 客户端需支持集群重定向 |
| 本地缓存 OOM | 未设 maximumSize | 设容量上限 + 监控驱逐 |
| 双删后仍读到旧值 | 删除失败无重试 | 上 MQ 可靠删除 / Canal 兜底（[04 篇](04-缓存一致性.md)） |

## 4. 面试三范式

- **价值式**（"你做过缓存吗"）：命中率从 85% 提到 97%，DB 读 QPS 7500→1500，P99 420ms→60ms——先给量化收益再讲方法。
- **技术式**（"缓存一致性怎么保证"）：六段式——先更 DB 后删缓存（Cache Aside）→ 极端并发 1-5ms 窗口 → 延迟双删兜底（延迟 = 读耗时 ×1.5 + 主从延迟）→ 核心数据 Canal 订阅 binlog <100ms → 零容错直读 DB → 选型按"改错了会怎样"分级（[04 篇](04-缓存一致性.md)）。
- **架构式**（"详情页 10 万 QPS 怎么扛"）：六层链路逐层卸压 → 本地缓存扛单机热点 → Redis 扛集群共享 → 热点多副本扩散 + 单飞防击穿 → 预热 + 降级预案 → 命中率看板闭环（[02 篇](02-分层缓存架构全景.md)）。
- **追问四连**：穿透/击穿/雪崩区别？热点怎么识别？双删延迟怎么定？缓存挂了怎么办？
