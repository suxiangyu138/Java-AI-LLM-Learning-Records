# 07 热点 Key 与 Big Key 治理

> 热点 key 是"单点放大"——一个 key 的流量能打垮整条链路；big key 是"慢性毒药"——平时无感，网络、内存、集群稳定性全面侵蚀。治理它们的前提是先能识别它们

## 1. 热点 Key 识别

热点 key 的识别有四个手段，按成本从低到高：

- **访问日志分析**：从网关/应用日志按 key 聚合统计访问频次，离线分析热点分布。成本最低，用于日常巡检。
- **埋点计数（滑动窗口）**：JVM 内用分段计数数组（Segment Array）对 key 做窗口计数，写入为纳秒级自增、零网络开销，窗口轮转天然实现热度衰减——热点"上得快，冷下来也快"。比 Redis Sorted Set 统计（每次记录一次网络 IO）更适合请求级高频统计。热度映射为分级阈值（HIGH/MEDIUM/LOW），驱动差异化 TTL 与防护策略。
- **Redis 8.6 HOTKEYS**：一条命令实时返回热 key，作为 Redis 侧的权威探测手段（[06 篇](06-分布式缓存：Redis与Memcached.md)）。
- **大促提前圈定**：秒杀商品、活动页在活动开始前由业务方圈定并预热（[09 篇](09-缓存监控与容量规划.md)）。这是唯一能"预知"热点的途径——其余手段都是事后识别。

滑动窗口计数的落地要点：窗口切 6-12 段（太细求和开销大、太粗识别迟钝），每个 key 的计数是 `int[]` 数组自增（纳秒级、无 GC 压力）；热度映射为分级阈值（如 QPS 阈值 HIGH/MEDIUM/LOW/NONE 四级），**不同等级驱动不同防护策略**——HIGH 级 key 进入本地缓存 + 多副本扩散，MEDIUM 级只延长 TTL，LOW 级维持常态。分级的意义是"防护成本按热度分配"，避免给所有 key 都上重防护把性能吃掉。识别结果要**推送给治理端**（配置中心/治理平台），而不是散落在各实例内存里——否则实例重启后热点认知清零。

## 2. 热点 Key 治理方案

识别出热点后，按热度分级治理，核心思路是**把压力从单点分散掉**：

- **多副本扩散（热 key 打散）**：把 `goods:88` 拆成 `goods:88#0`、`goods:88#1`…`goods:88#N` 多个副本 key，读请求按 `hash(userId) % N` 随机读一个副本。原理：热点压力被 N 个 key 均摊，且 Cluster 下天然分散到不同分片，解决"热点全打一个分片"的负载不均（[06 篇](06-分布式缓存：Redis与Memcached.md)）。代价：写路径要更新 N 个副本，写放大 N 倍，只适合"读极热写极冷"的数据。
- **本地缓存兜底**：热点 key 进入 Caffeine L1，单机命中后根本不出进程（微秒级），Redis 和 DB 压力同时归零（[05 篇](05-本地缓存：Caffeine与Spring%20Cache.md)）。热点场景下这是性价比最高的方案。
- **永不过期 + 后台刷新**：热点 key 设超长 TTL，后台定时任务按业务周期刷新。配合刷新失败告警，避免缓存僵死。
- **预热**：大促前把预测热点提前灌入缓存，让第一个请求也命中（[09 篇](09-缓存监控与容量规划.md)）。

与 [03 篇](03-缓存三大问题：穿透击穿雪崩.md) 的击穿防护组合：多副本扩散解决"单 key 流量过大"，互斥锁/单飞解决"单 key 过期瞬间打穿"，本地缓存解决"Redis 带宽与延迟"——热点治理是这套组合拳的编排者。多副本扩散还有一个隐藏收益：**副本 key 天然分散到不同 Cluster 分片**，顺带缓解"热点 key 所在分片 CPU 打满、其他分片空闲"的负载不均问题。

## 3. Big Key 的危害与识别

**定义**：value 很大的 key——String 超过 100KB、集合类元素超过万级都算 big key。危害是慢性且全面的：

- **网络阻塞**：一次 GET 拉取 MB 级数据，单请求带宽占用巨大，Redis 单线程模型下拖慢其他请求（8.x 引入多线程 IO 只缓解部分）。
- **内存不均**：集群下大 key 所在分片内存水位远高于其他分片，触发淘汰时整个分片的 key 遭殃。
- **删除阻塞**：`DEL` 大集合是 O(N) 阻塞操作，删除一个百万元素 key 会卡住 Redis 数秒——用 `UNLINK`（惰性删除，后台线程回收）替代。
- **序列化放大**：应用侧序列化/反序列化大 value 消耗 CPU 与堆内存。

**识别手段**：`redis-cli --bigkeys` 扫描大 key 分布；`MEMORY USAGE key` 看单 key 精确内存；8.6 新增的键内存直方图（key-memory-histograms）从实例视角看分布；应用侧埋点统计 value 大小分位数。生产上建议巡检脚本定期扫描，纳入告警（[09 篇](09-缓存监控与容量规划.md)）。

big key 的**逐出放大效应**值得一提：Redis 淘汰策略按 key 粒度淘汰，一个 10MB 的大 key 被逐出时释放的内存 = 一万个 1KB 小 key——大 key 占比越高，淘汰粒度越粗，内存水位波动越剧烈，甚至出现"逐出后马上又写满"的震荡。这也是为什么大 key 治理要放在容量规划（[09 篇](09-缓存监控与容量规划.md)）之前：**先瘦身再扩容**。

## 4. Big Key 的处理

- **拆分为小 key**：大 Hash 按业务维度拆分（如 `user:1001:base`、`user:1001:ext`）；大 String 拆成多个分片 key 或多级结构。拆分后单 key 内存与网络占用同时下降。示例：一个 10MB 的 JSON 字符串拆成"元信息（小 value，实时性高）+ 详情体（大 value，变更频率低）"两个 key，热点读路径只拉元信息，详情体走对象存储直链——Redis 里永远不放大块数据。集合类大 key（百万元素 ZSet/List）按业务分桶（按时间、按类型拆多个 key），读写都限定在桶内。
- **压缩序列化**：value 用 Protobuf/压缩 JSON 替代纯文本，体积可降 60-80%；注意压缩在应用侧做，Redis 不感知。
- **惰性删除**：必须删时用 `UNLINK` 替代 `DEL`，避免阻塞；批量删除用 `SCAN` + `UNLINK`，禁止 `KEYS`。
- **写入侧治理**：设计阶段就定 value 大小红线（如 String ≤ 10KB、集合 ≤ 万级元素），review 时拦截；大字段（商品富文本、用户行为流）直接进对象存储/DB 大字段，不进 Redis——红线写进代码评审检查单，比事后治理便宜一个量级。

> 🎯 **核心要点**：热点识别四手段（日志分析/滑动窗口埋点/Redis 8.6 HOTKEYS/大促圈定），治理核心是"多副本扩散 + 本地缓存兜底 + 永不过期 + 预热"组合拳，把单点压力分散掉；big key 是慢性毒药，网络、内存、删除阻塞三面侵蚀，用 --bigkeys/MEMORY USAGE 识别、拆分 + 压缩 + UNLINK 处理，设计阶段定 value 大小红线从源头拦截。
