# 03 缓存三大问题：穿透击穿雪崩

## 1. 缓存穿透：查不存在的数据

**现象**：请求查询的数据在缓存与数据库中都不存在。缓存未命中 → 查 DB 也不存在 → 不写缓存 → 下次同样的请求再次穿透。恶意攻击者用大量不存在的 ID（负数、超长、随机值）可直接把请求全部打到数据库。

**核心解法（三件套叠加）**：

- **缓存空值**：查询结果不存在时，向缓存写入空值占位（如 `"null"` 字符串），TTL 设短（30-60 秒），并加随机抖动。成本最低、立竿见影，注意空值键不能永久有效否则数据补录后读不到。
- **布隆过滤器**：启动时把合法 ID 全量灌入布隆过滤器，请求先过过滤器，未命中直接返回。优点是拦截精准、内存极小（千万级 ID 仅几十 MB）；缺点是误判率与重建成本——新增数据要同步更新，且"误判存在"只是让请求退回缓存空值方案兜底。
- **参数校验与限流**：前置校验 ID 格式与范围（负 ID、超长 ID 直接拒绝），配合接口级限流。这是第一道闸门，成本最低。

三者关系：**参数校验挡非法、布隆过滤挡不存在、空值缓存挡漏网之鱼**，层层递减兜底，单用任何一个都有漏洞。

布隆过滤器落地时的两个参数要讲清楚：位数组大小 m 与哈希函数数 k，由预期元素数 n 与可接受误判率 p 决定（`m ≈ -n·ln(p) / (ln2)²`，`k ≈ (m/n)·ln2`）。目标误判率 1% 时，千万级 ID 约需 12MB 位数组 + 7 个哈希函数——内存代价极小，但**误判 = 放行一次 DB 查询**，所以误判的兜底恰恰是空值缓存。另一个易错点：布隆过滤器不支持删除元素，数据下线后位会被"污染"，长期运行需重建或改用 Cuckoo Filter。热点 key 的动态识别（哪些 ID 合法、哪些 key 正在热）见 [07 篇](07-热点Key与BigKey治理.md)。

## 2. 缓存击穿：热点 key 瞬时失效

**现象**：单个热点 key（如秒杀商品详情）在**高并发访问瞬间过期**，大量请求同时发现未命中并同时回源 DB，DB 连接池瞬间打满。与穿透的区别：数据**存在**，只是缓存恰好失效；与雪崩的区别：只有一个 key 出事。

**核心解法（四选一或组合）**：

- **互斥锁（SETNX+EX）**：第一个未命中的请求用 `SET key_lock 1 EX 5 NX` 抢锁回源，其余请求等待锁释放后重读缓存（自旋重试）。注意锁值要唯一（防误删他人锁）、锁过期要大于回源耗时、抢锁失败走"等待重试"而非"直接打 DB"（[08 篇](08-缓存并发控制与降级.md)有完整姿势）。
- **逻辑过期**：value 内嵌逻辑过期时间，物理上永不过期。读到过期数据时返回旧值，同时触发异步重建（只允许一个线程重建，其余直接拿旧值）。优点是**读路径零阻塞**，缺点是数据短暂过期可见。
- **永不过期 + 后台刷新**：热点 key 设超长 TTL，后台定时任务提前刷新。适合可预测的强热点，注意刷新失败要有告警与兜底。
- **请求合并（singleflight）**：进程内同一 key 的并发回源合并为一次，1000 个并发请求只回源 1 次（[08 篇](08-缓存并发控制与降级.md)详述）。

2026 年 Redis 8.6 新增 `HOTKEYS` 命令可实时探测热点 key，让"哪个 key 需要重点保护"从拍脑袋变成数据驱动（[07 篇](07-热点Key与BigKey治理.md)）。

互斥锁方案最容易被忽略的是**锁失效的处理**：回源请求查 DB 耗时超过锁过期时间时，锁已被 Redis 自动释放，其他请求会再次抢锁回源——解决方式是锁过期时间设得比回源耗时长（建议 ≥5 秒，不超过 30 秒）并监控回源耗时；而**抢锁失败的自旋**必须有上限（如最多重试 5 次、总等待 2 秒），超限后直接降级返回默认值，否则"等待锁"会变成"请求堆积"（[08 篇](08-缓存并发控制与降级.md)有完整代码）。

## 3. 缓存雪崩：批量失效与实例宕机

**现象**：两种情况——大量 key **同时过期**（统一 TTL、程序 bug 批量设零），或缓存**实例宕机**（主节点故障、机房故障）。整个缓存在瞬间失效，全部请求直接压到 DB，DB 崩溃后业务雪崩。雪崩是三大问题里破坏力最大的。

**核心解法（四道防线）**：

- **过期时间随机化**：TTL 统一时加随机抖动（如 `base + random(0, 300)`），让失效时间点散开。这是成本最低的第一道防线，配置层面即可完成。
- **多级缓存**：Redis 之上加本地缓存（Caffeine），Redis 失效时本地缓存仍能扛住一部分热点（[05 篇](05-本地缓存：Caffeine与Spring%20Cache.md)）。多级缓存的本质是把"单一失效点"变成"逐层失效"。
- **缓存高可用**：Redis 主从 + Sentinel/Cluster，实例故障自动切换，让"缓存不可用"尽量不发生（[06 篇](06-分布式缓存：Redis与Memcached.md)）。
- **限流熔断降级**：缓存失效已成事实时，对回源请求限流保护 DB，超出部分直接降级返回默认值/空数据，等缓存重建后再恢复（[08 篇](08-缓存并发控制与降级.md)的降级预案）。

## 4. 三问题对比与治理顺序

| 维度 | 穿透 | 击穿 | 雪崩 |
|---|---|---|---|
| 数据状态 | 不存在 | 存在，缓存恰失效 | 存在，批量失效/实例挂 |
| 范围 | 特定非法 key | 单个热点 key | 大量 key 或全实例 |
| 危害 | 恶意流量打满 DB | 热点瞬时打穿 DB | DB 崩溃业务雪崩 |
| 第一解法 | 空值缓存 + 布隆过滤 | 互斥锁 / 单飞 | TTL 随机化 |
| 兜底解法 | 参数校验 + 限流 | 逻辑过期 + 后台刷新 | 多级缓存 + 降级 |

治理顺序遵循"先识别再防御"：**穿透靠前置拦截，击穿靠并发控制，雪崩靠架构分散**。三者还会叠加出现——穿透攻击集中在热点 key 上就会演变成击穿；缓存服务降级时又放大雪崩风险。生产上的完整姿势是三层同防：空值缓存 + 布隆过滤防穿透，单飞/互斥防击穿，TTL 随机化 + 多级 + 降级防雪崩。

> 🎯 **核心要点**：穿透（不存在）用空值缓存 + 布隆过滤 + 参数校验三件套；击穿（热点瞬时失效）用互斥锁/逻辑过期/单飞四选一；雪崩（批量失效/宕机）用 TTL 随机化 + 多级缓存 + 高可用 + 限流降级四道防线；三者触发条件与解法完全不同，但生产中会叠加，必须三层同防。
