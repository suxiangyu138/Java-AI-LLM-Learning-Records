## 1. 命中率指标体系

命中率公式：`命中率 = 命中次数 / (命中次数 + 未命中次数)`。按层级拆出完整的指标体系：

- **Redis 侧**：`keyspace_hits / (keyspace_hits + keyspace_misses)`，`INFO stats` 直接可读；配套驱逐率 `evicted_keys`（逐出说明容量不足）、`expired_keys`（过期速率）、命令级延迟与慢查询。
- **本地缓存侧**：Caffeine `recordStats()` 上报 hitRate/missCount/evictionCount（[05 篇](05-本地缓存：Caffeine与Spring%20Cache.md)）。
- **CDN 侧**：拆请求命中率（关联加载延迟）与字节命中率（关联回源带宽与费用）两个口径——大文件场景必须两个都看（[02 篇](02-分层缓存架构全景.md)）。
- **DB 侧**：InnoDB Buffer Pool 命中率（目标 99%+），缓存层的失效最终都会反映在 DB 读压力上。

指标要看趋势不看瞬时：**命中率突降是最高价值的告警**——它意味着缓存策略、数据热度或代码逻辑发生了变化，往往先于业务投诉暴露问题。2026 年的实践是引入**动态基线**：对命中率做 EWMA（指数加权移动平均）建模，告警不是"低于固定阈值"而是"偏离基线超过 N%"，这样能自动适应业务周期（大促前命中率自然波动、活动后回落），减少误报——固定阈值在高峰期容易误报、在低谷期容易漏报。突降告警务必**联动发布记录与变更记录**：命中率突降 90% 的案例中，最常见根因是发布引入了新的缓存键、修改了 TTL、或热数据迁移，排查第一步是看最近 30 分钟有没有变更，而不是一头扎进监控里找原因。

## 2. 告警阈值

2026 年实践基线：

| 指标 | 健康线 | 告警线 | 危险线 |
|---|---|---|---|
| Redis 命中率 | ≥95%（高峰） | <90% | <85% |
| 本地缓存命中率 | ≥95% | <90% | <85% |
| 命中率突降 | — | 5 分钟下降 >10% | 持续下降 |
| CDN 请求命中率 | ≥95% | <90% | — |
| evicted_keys | 低 | 持续增长 | 峰值时段大量逐出 |
| 缓存延迟 | P99 <5ms | P99 >10ms | 超时率上升 |

告警分级：命中率低于阈值触发"策略级告警"（分析 Miss 原因——是数据热度变化、TTL 过短还是缓存键设计问题）；命中率突降触发"变更级告警"（联动发布记录，查代码变更）；evicted_keys 增长触发"容量级告警"（联动容量规划）。大促期间命中率下降超 20% 即视为缓存架构需优化信号——某电商大促案例中，热点商品 TTL 过短导致命中率从 98% 骤降至 85%，DB 连接数突破 80% 才被发现，代价是提前压测中的连环告警。

## 3. 容量规划：与命中率联动

缓存容量规划公式：`maxmemory ≈ key 数量 × 平均 value 大小 × 1.3-1.5 冗余`，并预留 20-30% 给内存碎片与主从复制缓冲。但容量规划真正的核心是与**命中率联动**：

- **命中率 <80% 时容量是无效的**：假设业务读 QPS 1 万、命中率 70%，DB 实际承受 3000；命中率提到 95% 后 DB 只承受 500——**命中率每提升 5 个百分点，DB 压力可能减半**。容量规划先回答"这个缓存装不装得下热点数据"，再回答"装多少"。
- **从业务推演**：峰值读 QPS = DAU × 人均请求 × 峰均比（参考 [专题 1](../专题%201：性能理论基础/07-容量规划与水位线.md) 的方法论）；结合 key 数量与 value 大小算出内存需求，反推实例规格与分片数。
- **大促专项**：按历史大促峰值 × 1.5-2 预留；预热（下节）直接影响命中率，必须纳入容量推演——不预热的缓存实例容量规划在第一天就失真。
- **逐出作为信号**：`evicted_keys` 增长说明容量见顶，而不是"Redis 自动管理得很好"——逐出即命中率下降的起点。

一个完整的计算示例：电商商品详情，预估峰值读 QPS 5 万、有效 key 数 3000 万（商品 + 变体）、平均 value 1KB，则 `maxmemory = 3000 万 × 1KB × 1.4 ≈ 42GB`，加 25% 缓冲（碎片 + 复制）≈ 52GB——Cluster 三主三从（每主 18GB）可承载；若命中率按 90% 算，Redis 层挡住 4.5 万 QPS，DB 承受 5000——若命中率只能做到 80%，DB 承受 1 万，DB 规格要翻倍。**容量报告必须同时写"内存需求"与"命中率假设下的 DB 压力"两栏**，只写内存不写命中率的容量规划是不完整的。

## 4. 预热策略

预热是用**主动推送的成本**换**被动回源的延迟与带宽**，大促前的标准动作。三种策略对比：

| 策略 | 命中率 | 成本 | 适用 |
|---|---|---|---|
| 全量无差别预热 | <20% | 高（带宽浪费严重） | 小体量目录 |
| 灰度/按需预热（历史日志/画像） | 60-80% | 中 | 日常大促标配 |
| 自适应预热（AI 按热度动态调） | 70%+ | 高（技术门槛） | 大平台 |

电商大促推荐**全量 + 增量组合**：提前 2 小时全量预热静态资源（图片/CSS），活动开始前 15 分钟按业务圈定的商品清单精准预热动态详情页；预热效果盯"完成时间"与"命中率"两个变量（推上去的内容有没有被访问）。某电商教训：热门商品 key 未预热，首请求穿透 DB，回源率飙升 50%；另一视频平台全量预热直播回放，用户只看了前 3 分钟，90% 预热内容浪费——**预热前先问"推什么给谁"**。

## 5. 缓存治理平台

缓存治理在 2026 年已平台化，核心能力四件套：

- **热 key / big key 平台**：接入 Redis 8.6 HOTKEYS 与 --bigkeys 扫描结果，可视化分布、自动告警、一键治理动作（副本扩散、拆分建议）（[07 篇](07-热点Key与BigKey治理.md)）。
- **配置中心化**：TTL、淘汰策略、容量上限、降级开关全部走配置中心，变更可灰度、可回滚，禁止改代码发布才能调缓存（[08 篇](08-缓存并发控制与降级.md)）。
- **命中率看板**：全链路命中率一屏总览（CDN/本地/Redis/DB），联动发布记录与告警。
- **巡检与演练**：定期巡检 big key、过期时间分布、内存水位；缓存故障演练纳入发布回归（[08 篇](08-缓存并发控制与降级.md)）。

> 🎯 **核心要点**：命中率是缓存价值的生死线——Redis ≥95%/本地 ≥95%/突降 10% 告警是 2026 基线；容量规划 = key 数 × 平均大小 × 冗余 + 与命中率联动（命中率 <80% 时容量无效，每提升 5 个百分点 DB 压力可能减半）；预热三策略中灰度按需 60-80% 命中是日常标配、电商大促用全量 + 增量组合；治理平台把热 key、配置、命中率、演练四件事收敛成常态化机制。
