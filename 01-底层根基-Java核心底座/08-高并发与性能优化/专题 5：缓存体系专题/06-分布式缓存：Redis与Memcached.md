## 1. 缓存场景的内存管理

缓存场景下 Redis 的定位是"高速内存存储 + 集群共享"，与数据库场景（持久化、复杂查询）的用法截然不同。内存管理是第一个决策点：

- **maxmemory 必须显式设置**：不设置则数据无上限增长，内存耗尽触发系统 OOM，Redis 进程被杀。
- **缓存 vs 持久化分离**：纯缓存数据可关 RDB/AOF（或 AOF 用 no），重启后由缓存重建；混用（缓存 + 持久数据）时按 key 前缀分实例，避免持久化压力污染缓存延迟。
- **内存模型**：`info memory` 关注 used_memory、mem_fragmentation_ratio（>1.5 需处理碎片）、maxmemory 水位。键内存直方图（key-memory-histograms，8.6 新增）可看大 key 分布（[07 篇](07-热点Key与BigKey治理.md)联动）。

容量规划公式在 [09 篇](09-缓存监控与容量规划.md)：`maxmemory ≈ key 数量 × 平均 value 大小 × 冗余系数(1.3-1.5)`，并留 20-30% 给碎片与主从复制缓冲。配置与观测三板斧：

```bash
# redis.conf 或 CONFIG SET 动态调整
maxmemory 8gb
maxmemory-policy allkeys-lru          # 缓存实例：淘汰策略必须显式设置
maxmemory-samples 5                   # LRU 采样数：越大越准，CPU 越高
config set activedefrag yes           # 碎片自动整理，碎片率 >1.5 时启用
info memory                           # 观测 used_memory / 碎片率 / 逐出计数
```

另一个常被忽略的点：**主从复制与持久化占用**——`RDB 子进程 fork 时写时复制`、AOF 缓冲都会在 maxmemory 之上再占内存，Redis 6.0+ 对复制缓冲单独计内存（`repl-backlog-size` 等），maxmemory 要给这些"隐性内存"留出空间，否则 fork 时 OOM 是缓存实例最典型的"意外死亡"。

## 2. 淘汰策略：LRU/LFU 与 8.6 的 LRM

maxmemory 写满后的行为由淘汰策略决定，缓存场景必须从默认的 `noeviction`（写满直接报错）改为淘汰策略：

- **allkeys-lru**：全键按最近使用淘汰，最通用，适合"热点数据驱动"的绝大多数缓存。
- **allkeys-lfu**：按访问频率淘汰，适合访问分布极不均匀、频率特征明显的场景（如商品详情），比 LRU 更能保护高频 key，代价是额外计数开销。
- **volatile-xxx 系列**：只淘汰带 TTL 的 key，适合"部分数据可淘汰、部分必须常驻"的混用场景。
- **noeviction**：默认值，缓存场景下是事故开关——写满后 SET 直接报 `OOM command not allowed when used memory`。

**2026 年新成员**：Redis 8.6 新增基于"最近修改时间"的淘汰策略 `volatile-lrm` 与 `allkeys-lrm`。与 LRU 的关键区别：**LRU 读操作也会刷新淘汰优先级，LRM 只有写操作刷新**。适用场景非常精准——**"写入后不再变化、被频繁读取、期望生产方停止更新后自动消失"的缓存数据**（如聚合结果、语义缓存）：LRU 会因频繁读而永不淘汰，LRM 会按最后修改时间自然过期。长短 TTL 混合场景下，LRM 还能确保优先淘汰"长期未修改的长周期 key"，不受读模式影响。

选型决策：**LRU 是默认选择**（实现简单、无额外内存）；**LFU 适合访问分布极不均**（如 20% key 占 90% 访问）的场景，能保护高频 key 不被低频大流量挤出，代价是 16bit 频率计数器（每个 key 约 2 字节额外开销，实际只在内存写满触发淘汰时才体现）；**LRM 适合"数据由生产者周期刷新、读流量大"**的场景——语义缓存、聚合报表、配置快照。三者可以在同一实例按 key 前缀混用（不同 maxmemory 策略不支持按 key 细分，需要拆实例或使用 7.0+ 的 `maxmemory-policy` 全局设置 + 业务侧控制 TTL）。

## 3. 缓存场景的部署形态

- **单机 + 主从 + Sentinel**：中小规模（几 GB 内），Sentinel 保证主节点故障自动切换，缓存不可用时间压到秒级。缓存数据可接受丢失，不需要复杂集群。
- **Cluster 集群**：数据量大（几十 GB+）或写并发高时启用，16384 个槽位分片，客户端按 CRC16 路由。缓存场景特别注意：**热点 key 全部落在同一分片**时，分片间负载不均，需要热 key 分散（[07 篇](07-热点Key与BigKey治理.md)的多副本扩散）。
- **多级缓存兜底**：无论哪种形态，Redis 故障时本地缓存与直连 DB 降级预案必须存在（[08 篇](08-缓存并发控制与降级.md)）——缓存的高可用不解决"缓存挂了业务怎么办"，降级预案才解决。

## 4. Redis 8.6 的缓存新能力

Redis 8.6（2026-02-10 GA）对缓存场景有三个直接收益：

- **HOTKEYS 命令**：实时探测高频访问的 key，让热 key 识别从"埋点统计 + 人工圈定"升级为"一条命令"（[07 篇](07-热点Key与BigKey治理.md)详述识别机制）。
- **内存占用下降**：hashtable 与 skiplist 编码结构优化，字段/分值与值合并到单一结构体，减少指针开销——同样数据量占用更低，直接提升缓存容量经济性。
- **吞吐与延迟改善**：命令执行与系统调用优化，缓存读取延迟更低，命中路径的 P99 改善。

生产升级建议：缓存实例的升级收益（内存下降 + 延迟改善）几乎是零成本白拿，但要先在测试环境跑通客户端兼容性（主要涉及新客户端命令与 `XADD` 等非缓存场景特性）。

## 5. vs Memcached 选型

| 维度 | Redis | Memcached |
|---|---|---|
| 数据类型 | 丰富（String/Hash/List/Set/ZSet） | 仅键值 |
| 缓存辅助能力 | TTL、淘汰、锁、Pub/Sub、8.6 HOTKEYS | TTL、淘汰 |
| 内存分配 | jemalloc（可压缩） | slab 分块（固定块内存浪费） |
| 持久化 | 支持（缓存场景可关） | 不支持 |
| 单线程 vs 多线程 | 单线程（8.x 引入多线程 IO） | 多线程 |
| 定位 | **缓存 + 通用数据结构的事实标准** | 极简键值缓存，存量系统 |

选型结论一句话：**新系统一律 Redis**——Memcached 只剩"极简 + 纯 KV + 存量迁移成本高"的角落场景。Redis 主体系的完整机制（持久化、高可用、Lua、数据结构）见 [Redis 缓存实战](../../../02-后端核心技术%20微服务%20分布式%20云原生/02-非关系型数据库/Redis/06-Redis缓存实战与常见问题.md)，Memcached 的 slab 与一致性哈希见 [Memcached 体系](../../../02-后端核心技术%20微服务%20分布式%20云原生/02-非关系型数据库/Memcached/00-Memcached知识体系总览.md)，本专题只做缓存视角的选型。

> 🎯 **核心要点**：缓存场景下 Redis 的核心是内存管理——maxmemory 显式设置、淘汰策略从 noeviction 改为 allkeys-lru/lfu；Redis 8.6 的 LRM 策略解决"频繁读导致永不淘汰"的问题，HOTKEYS 让热 key 探测一条命令完成；部署形态按数据量选 Sentinel 或 Cluster，热点 key 分片不均要靠多副本扩散；新系统选型一律 Redis，Memcached 仅剩存量角落。
