## 1. 配置文件格式

### 1.1 格式对比总表

| 后缀 | 格式 | 支持层级 | 注释 | Java 生态使用 |
|:----:|------|:------:|:--:|------|
| **.yml / .yaml** | YAML | ✅ 多级 | ✅ `#` | Spring Boot, Docker Compose, K8s |
| **.properties** | key=value | ❌ 扁平 | ✅ `#` | Spring Boot, Java 传统配置 |
| **.toml** | TOML | ✅ 多级 | ✅ `#` | Rust Cargo, Python 项目 |
| **.ini** | INI | ✅ Section | ✅ `;` 或 `#` | Windows, PHP |
| **.env** | key=value | ❌ 扁平 | ✅ `#` | Docker, Node.js, 环境变量 |
| **.xml** | XML | ✅ 多级 | ✅ `<!-- -->` | Maven pom.xml, Spring 旧配置 |
| **.json** | JSON | ✅ 多级 | ❌ 不支持！ | 现代配置趋势 |
| **.conf** | 多种 | 视情况 | 视情况 | Nginx, Apache, Logstash |

### 1.2 同配置三种写法对比

```yaml
# application.yml（Spring Boot）—— 层级清晰
server:
  port: 8080
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb
    username: root
    password: ${DB_PASSWORD}        # 环境变量引用
  redis:
    host: localhost
    port: 6379
```

```properties
# application.properties —— 扁平、冗长
server.port=8080
spring.datasource.url=jdbc:mysql://localhost:3306/mydb
spring.datasource.username=root
spring.datasource.password=${DB_PASSWORD}
spring.redis.host=localhost
spring.redis.port=6379
```

```toml
# config.toml —— 表格分节
[server]
port = 8080

[spring.datasource]
url = "jdbc:mysql://localhost:3306/mydb"
username = "root"
password = "${DB_PASSWORD}"

[spring.redis]
host = "localhost"
port = 6379
```

```ini
# config.ini —— 传统 Section 风格
[database]
host=localhost
port=3306
name=mydb
```

## 2. 配置格式选型决策

| 维度 | YAML | TOML | properties | INI | JSON |
|------|:---:|:---:|:---:|:---:|:---:|
| 层级 | ✅ 缩进 | ✅ 表格 | ❌ 点路径 | ✅ Section | ✅ 嵌套 |
| 类型 | 弱（字符串陷阱） | **完善** | 全字符串 | 全字符串 | 基础 |
| 注释 | ✅ | ✅ | ✅ | ✅ | ❌ |
| 大配置可读性 | ⭐ 最佳 | 好 | 差 | 中 | 中 |
| 陷阱 | 缩进错误静默失败 | 少 | 转义/编码 | 少 | 无注释/尾逗号 |
| 代表场景 | K8s/Compose/Spring | Cargo/pyproject | Java 传统 | Windows | 工具配置 |

> 🎯 **2026 选型口诀**：
> - 服务/基础设施配置 → **YAML**（K8s/Docker Compose/Spring Boot）
> - 项目构建配置 → **TOML**（Cargo/pyproject.toml）
> - Java 遗留系统 → **properties**（保持兼容）
> - 环境变量注入 → **.env**（不上 Git）
> - 程序化配置（需要逻辑）→ **JSON**（能被程序安全解析）

### 2.1 YAML 的四大陷阱

```yaml
# ⚠️ 陷阱 1：缩进错误（Tab 或空格混用）→ 解析失败或静默错层
server:
    port: 8080        # 4 空格
  port: 8081          # 2 空格 → 报错！

# ⚠️ 陷阱 2：字符串被解析成其他类型
version: 1.0          # 被解析为浮点数！应为 version: "1.0"
port: 0808            # 八进制？应为 port: "0808"
no: false             # 字符串 no 被解析为布尔 false！

# ⚠️ 陷阱 3：多文档分隔符 ---
# ⚠️ 陷阱 4：锚点/别名（&anchor *alias）——读不懂的写法
```

```bash
# YAML 校验工具（CI 中必用）
python -c "import yaml,sys; yaml.safe_load(open('app.yml'))"  # 校验
yamllint app.yml          # lint（缩进/规范）
```

## 3. .env 环境变量规范

### 3.1 规范要点

```env
# .env 文件（十二要素应用规范）
# ⚠️ 铁律：永不提交 Git（进 .gitignore）！

# 基础格式：KEY=VALUE（无引号或双引号）
DB_HOST=localhost
DB_PORT=3306

# 含特殊字符用引号
DB_PASSWORD="p@ss w0rd!"
APP_NAME="My Service"

# 注释用 #
# 下一行配置超时
TIMEOUT_MS=30000

# 引用其他变量（部分工具支持）
API_URL=http://${DB_HOST}:8080
```

### 3.2 .env 的使用场景

```text
.env 的三大使用场景
├── ① Docker Compose：env_file 指令加载
├── ② Node.js：dotenv 库（process.env）
├── ③ 本地开发：多环境切换（.env.dev / .env.prod）
└── 安全替代方案：生产用密钥管理服务（Vault/云 KMS）
    → .env 只适合本地/开发，生产密钥走 KMS + 环境变量注入
```

> ⚠️ **.env 泄露事故**：`.env` 文件泄露 API Key 是 GitHub 最高频的密钥泄露原因（机器人扫描公开仓库）——`.gitignore` 必须包含 `.env*`，并定期用 gitleaks 扫描历史。

### 4.2 SQL 脚本与备份

|:----:|------|------|

```bash
gunzip -c mydb_20260804.sql.gz | mysql -u root -p mydb
```

## 5. SQLite 文件结构深入

### 5.1 魔数与结构

> 🎯 **SQLite 是单文件数据库的典范**——魔数文本是 `SQLite format 3`：

```text
SQLite .db 文件结构
├── 文件头（100 字节）：
│   ├── "SQLite format 3\0"    ← 魔数（16 字节）
│   ├── 页面大小（2 字节）
│   ├── 文件格式版本
│   └── 编码/表头信息
├── 页面（Page）：默认 4096 字节
│   ├── B-tree 页（表/索引）
│   └── 溢出页（大字段）
└── 日志文件（.db-wal / .db-journal）：
    ├── -wal：WAL 模式预写日志
    └── -journal：回滚日志

验证：
$ file my.db
my.db: SQLite 3.x database, user_version 1
$ sqlite3 my.db ".tables"       # 查看表
```

### 5.2 SQLite 的三个伴随文件

| 文件 | 作用 | 何时出现 |
|------|------|---------|
| **.db-wal** | 预写日志（WAL 模式） | 写入时出现，checkpoint 后消失 |
| **.db-shm** | 共享内存索引 | WAL 模式的并发协调 |
| **.db-journal** | 回滚日志（默认模式） | 事务进行中出现 |

> 💡 **认知**：看到 `.db-wal` 不要惊讶——它是 SQLite 的正常组成部分，备份时需用 `sqlite3 my.db ".backup"`（在线安全备份），不能直接拷文件（WAL 数据可能未合并）。

## 6. 大数据文件格式

### 6.1 列式存储格式（2026 大数据主流）

| 后缀 | 格式 | 特点 | 适用 |
|:----:|------|------|------|
| **.parquet** | Apache Parquet | 列式存储、压缩率高、谓词下推 | **大数据分析首选**（Spark/Hive/DuckDB） |
| **.orc** | Optimized Row Columnar | Hive 优化列式 | Hive 生态 |
| **.avro** | Apache Avro | 行式、带 Schema | Kafka/流式序列化 |
| **.arrow** | Apache Arrow | 内存列式格式 | 分析加速 |

```text
为什么 Parquet 是大数据首选？
├── 列式存储：只需读查询涉及的列（跳过无关列）
├── 高压缩：同列数据相似度高 → 压缩率比行式高 3-10 倍
├── 谓词下推：在文件层过滤（min/max 统计）
└── Schema 内嵌：自带字段类型与嵌套结构
→ 对比 CSV：100GB CSV → 约 15-30GB Parquet，查询快 10-100 倍
```

### 6.2 交换与流式格式

| 后缀 | 说明 | 场景 |
|:----:|------|------|
| **.jsonl / .ndjson** | JSON Lines（每行一个对象） | 日志流/大数据逐行处理 |
| **.gz / .gzip** | GZIP 单文件压缩 | 日志归档 |
| **.snappy** | Snappy 快速压缩 | 流式压缩（Parquet 默认） |
| **.lz4** | LZ4 极速压缩 | 实时场景 |

## 7. 压缩与归档格式

### 7.1 格式总览

| 后缀 | 类型 | 压缩率 | 速度 | 特点 |
|:----:|------|:---:|:---:|------|
| **.zip** | 归档+压缩 | 中 | 快 | 最通用、自带目录结构 |
| **.tar** | 仅归档（不压缩） | 无 | 快 | 保留权限/符号链接 |
| **.tar.gz / .tgz** | tar + gzip | 中高 | 快 | **Linux 事实标准** |
| **.gz** | gzip 单文件 | 中 | 快 | 单文件压缩 |
| **.bz2** | bzip2 | 高 | 慢 | 高压缩（文本） |
| **.xz** | xz | 很高 | 慢 | **高压缩率（Linux 内核/发行版）** |
| **.7z** | 7-Zip | 最高 | 中 | 压缩率之王 |
| **.rar** | RAR | 高 | 中 | 专有格式 |
| **.zst** | Zstandard | 高 | 极快 | **2026 新宠（Docker/备份）** |

### 7.2 关键认知：归档 vs 压缩

> 🎯 **tar 管归档（把文件装一起），gzip 管压缩（把字节压小）**——`.tar.gz` = 先打包再压缩。

```text
为什么 Linux 用 .tar.gz 而不是 .zip？
├── tar 保留：文件权限（rwx）、符号链接、所有者、时间戳
├── zip 丢失：权限位（跨平台混乱的根源）
├── 管道的哲学：tar -cf - . | gzip > backup.tar.gz
└── 结论：系统级备份/分发用 tar；办公文件交换用 zip
```

### 7.3 压缩命令速查

```bash
# tar + gzip（Linux 标准）
tar -czvf backup.tar.gz ./data          # 打包压缩（c 创建 z gzip v 显示 f 文件）
tar -xzvf backup.tar.gz                 # 解压
tar -tzf backup.tar.gz                  # 查看内容（不解压）

# zip
zip -r archive.zip ./dir                # 递归压缩
unzip archive.zip                       # 解压
unzip -l archive.zip                    # 查看

# 7z
7z a archive.7z ./dir                   # 压缩
7z x archive.7z                         # 解压

# 单文件
gzip file.txt        # → file.txt.gz（原文件被替换）
zcat file.txt.gz     # 不解压查看
```

## 8. ZIP 结构深入：魔数与原理

### 8.1 ZIP 的魔数

> 🎯 **ZIP 魔数：`50 4B 03 04`（即 ASCII "PK"，致敬 Phil Katz）**——一半以上的「高级格式」都是 ZIP 外壳：

```text
ZIP 魔数 PK 的家族成员
├── .zip          ← 原始 ZIP
├── .jar / .war   ← Java 归档
├── .docx / .xlsx / .pptx  ← Office 文档（OOXML）
├── .apk          ← Android 安装包
├── .ipa          ← iOS 安装包
├── .epub         ← 电子书
├── .nupkg        ← NuGet 包
└── .whl          ← Python wheel 包

验证：
$ head -c 4 file.apk
PK\x03\x04
$ file file.apk
Android package (APK), ... (Zip archive)
```

### 8.2 ZIP 的内部结构

```text
ZIP 文件结构（三段式）
├── 文件头区：每个条目有 Local File Header
│   ├── 魔数 PK\x03\x04
│   ├── 压缩方法（0=存储 / 8=Deflate）
│   ├── CRC-32 校验
│   └── 压缩后/前大小
├── 中央目录：Central Directory（所有条目的索引表）
└── 结束记录：End of Central Directory（中央目录位置）

→ 为什么 ZIP 能「不解压查看」？
  → 先读尾部结束记录 → 定位中央目录 → 读索引表 → 按偏移提取单文件
```

### 8.3 压缩算法对比

| 算法 | 类型 | 速度 | 压缩率 | 使用场景 |
|------|:---:|:---:|:---:|---------|
| **Deflate** | ZIP 默认 | 快 | 中 | 通用（zip/gzip） |
| **LZMA** | 7z/xz | 慢 | 高 | 高压缩归档 |
| **Zstandard (zstd)** | 新锐 | 极快 | 高 | Docker 层、日志、备份 |
| **Brotli** | Web 专用 | 快 | 高 | HTTP 内容压缩 |
| **LZ4** | 极速 | 最快 | 低 | 实时流 |

> 💡 **2026 趋势**：Zstandard（zstd）正在取代 gzip——Docker 镜像、数据库备份、日志轮转都能用 `zstd` 达到「更快 + 更小」的双赢（`tar --zstd`）。

## 9. tar vs zip vs 7z：怎么选

| 场景 | 首选 | 理由 |
|------|------|------|
| Linux 系统备份/分发 | **tar.gz / tar.zst** | 保留权限/链接 |
| 跨平台文件交换 | **zip** | 全平台原生支持 |
| 最高压缩率归档 | **7z** | 压缩率之王 |
| 日志归档 | **gz / zst** | 快 + 小 |
| Docker 镜像层 | zstd（新）/ gzip | 构建缓存效率 |
| Windows 安装包 | exe/msi（自解压） | 用户无工具 |

> ⚠️ **踩坑提示**：`tar.gz` 解压到 Windows 前检查是否含符号链接/权限文件；`zip` 在 Linux 解压可能丢失可执行权限（`unzip -X` 保留属性不可靠——用 tar 传输可执行文件）。

## 10. 序列化与缓存文件

### 10.1 序列化格式

| 后缀 | 格式 | 特点 | 适用 |
|:----:|------|------|------|
| **.serialized** | Java 原生序列化 | 简单但脆弱（类变更即失效） | 遗留系统 |
| **.pkl / .pickle** | Python pickle | Python 原生 | Python 缓存模型 |
| **.msgpack** | MessagePack | 二进制 JSON 替代 | 高性能 RPC |
| **.pb / .bin** | Protobuf | 高效、需 .proto 定义 | gRPC/微服务 |
| **.avro** | Avro | 带 Schema 演进 | Kafka 消息 |
| **.cbor** | CBOR | 二进制 JSON 兼容 | IoT/移动端 |

### 10.2 序列化选型

```text
序列化选型决策
├── 跨语言微服务 → Protobuf（.proto 编译，效率最高）
├── 纯 Java 内部 → 谨慎用原生序列化（安全漏洞 CVE 频发）
├── Python 模型缓存 → pickle（同版本安全）
├── 可读性优先 → JSON（牺牲体积换调试便利）
└── 安全警告：永远不要反序列化不可信输入
    （Java 原生序列化是 RCE 高危漏洞源，生产禁用！）
```

### 10.3 缓存文件

| 后缀 | 说明 |
|:----:|------|
| **.cache** | 通用缓存（Redis dump、工具缓存） |
| **.pyc** | Python 字节码缓存（__pycache__） |
| **.ttf 缓存** | 字体/图标缓存 |
| **.index** | 搜索引擎索引文件 |
| **.log.1 / .log.2** | 日志轮转（logrotate） |

## 11. 核心要点

> 🎯 **核心要点**：
> 1. 配置选型：服务配置 YAML、项目构建 TOML、Java 遗留 properties、环境变量 .env（永不提交 Git！）
> 2. YAML 四大陷阱（缩进/类型推断/多文档/锚点）——CI 中必加 yamllint 校验
> 3. ZIP 魔数 PK 统治半个文件世界（jar/war/docx/apk/ipa/epub）——理解 ZIP 三段结构 = 理解全部
> 4. tar 管归档 zip 管交换 7z 管压缩率 zstd 是 2026 新宠——按场景选格式
> 5. 安全底线：.env/.pem 永不进 Git；永不反序列化不可信输入（Java 原生序列化是 RCE 源头）
