## 1. 并发设计模式全景

> 并发设计模式是解决多线程协作中典型问题的"最佳实践模板"，来源于 Doug Lea 的《Java Concurrency in Practice》与《Pattern-Oriented Software Architecture》等经典著作。

| 分类 | 模式 | 核心思想 | 典型应用 |
|------|------|---------|---------|
| 结构性 | Immutable 不可变模式 | 对象创建后不可修改，天然线程安全 | String、BigDecimal、值对象 |
| 结构性 | Thread Confinement 线程封闭 | 将数据限制在单个线程内访问 | ThreadLocal、栈封闭 |
| 创建性 | Future 模式 | 异步提交任务，通过凭证获取结果 | Callable + Future、CompletableFuture |
| 协作性 | Producer-Consumer 生产者-消费者 | 通过缓冲区解耦生产与消费 | BlockingQueue |
| 协作性 | Guarded Suspension 保护性暂停 | 条件不满足时等待，满足时唤醒 | wait/notify、Condition |
| 协作性 | Two-Phase Termination 两阶段终止 | 优雅终止线程，先通知再清理 | 线程池 shutdown、interrupt |
| 协作性 | Balking 模式 | 条件不满足时直接返回，避免等待 | 单例双检锁 |
| 协作性 | Copy-on-Write 写时复制 | 读不阻塞，写时复制新容器 | CopyOnWriteArrayList |
| 协作性 | Worker-Thread 工作线程 | 线程池复用线程处理任务 | ThreadPoolExecutor |

> 选择并发模式的核心原则：能不可变就不要可变，能封闭就不要共享，能用工具类就不要手写锁。

## 2. 不可变模式（Immutable）

对象一旦创建，其内部状态就永远不会改变。不可变对象天然线程安全，无需任何同步措施即可安全地在多线程间共享。

```java
public final class ImmutablePoint {
    private final int x;
    private final int y;
    private final List<Integer> list;

    public ImmutablePoint(int x, int y, List<Integer> list) {
        this.x = x;
        this.y = y;
        this.list = list == null ? Collections.emptyList() : List.copyOf(list);
    }

    public int getX() { return x; }
    public int getY() { return y; }
    public List<Integer> getList() { return list; }

    public ImmutablePoint withX(int newX) {
        return new ImmutablePoint(newX, this.y, this.list);
    }
}
```

| 规则 | 说明 | 违反后果 |
|------|------|---------|
| 类用 `final` 修饰 | 防止子类破坏不可变性 | 子类可添加可变字段 |
| 所有字段用 `final` 修饰 | 确保字段在构造完成后不可修改 | 可被反射修改 |
| 不提供 setter 方法 | 防止外部修改状态 | 调用方能随意更改字段值 |
| 引用类型防御性拷贝 | 防止外部修改传入的可变对象引用 | 外部引用可修改内部数据 |
| 禁止 `this` 逸出 | 构造期间不发布 this 引用 | 其他线程看到不完整对象 |

JDK 不可变类：`String`（substring 在 JDK 7+ 复制新数组）、`Integer/Long`（缓存池 -128~127）、`BigDecimal`、`List.of()`（JDK 9+ 真正不可变）。

> 不可变模式是"无锁编程"的基石，在多线程环境中优先考虑使用不可变对象。

## 3. Future模式

Future 模式的核心是"异步执行，凭票取结果"：提交任务时立即返回凭证（Future），主线程继续执行其他工作，需要结果时再通过凭证获取。

```java
public class FuturePatternDemo {
    public static void main(String[] args) throws Exception {
        // 1. 基础 Future（JDK 5）
        ExecutorService executor = Executors.newFixedThreadPool(2);
        Future<String> future = executor.submit(() -> {
            Thread.sleep(1000);
            return "Task result";
        });
        String result = future.get(3, TimeUnit.SECONDS); // 带超时获取

        // 2. CompletableFuture（JDK 8）：声明式异步
        CompletableFuture.supplyAsync(() -> fetchUser())
                .thenCombine(
                    CompletableFuture.supplyAsync(() -> fetchOrder()),
                    (u, o) -> u + " - " + o
                )
                .thenAccept(System.out::println)
                .exceptionally(ex -> { System.err.println(ex); return null; });

        CompletableFuture.allOf(                  // 等待所有完成
            CompletableFuture.supplyAsync(() -> "A"),
            CompletableFuture.supplyAsync(() -> "B")
        ).join();

        executor.shutdown();
    }
    static String fetchUser() { return "Alice"; }
    static String fetchOrder() { return "Order#10086"; }
}
```

| CompletableFuture API | 作用 |
|----------------------|------|
| `thenApply(fn)` | 转换结果（有返回值） |
| `thenAccept(consumer)` | 消费结果（无返回值） |
| `thenCombine(other, fn)` | 合并两个 CompletableFuture |
| `thenCompose(fn)` | 异步 flatMap（展平嵌套 Future） |
| `exceptionally(fn)` | 异常时返回默认值 |
| `handle((r, ex) -> ...)` | 无论是否异常都处理 |

> CompletableFuture 实现了"异步回调 + 事件驱动"，适合编排复杂的异步业务流程。

## 4. 生产者-消费者模式

通过共享缓冲区解耦生产者和消费者。生产环境直接使用 `BlockingQueue`，其 `put()` 在满时阻塞，`take()` 在空时阻塞。

```
  生产者 --> BlockingQueue --> 消费者
```

```java
public class ProducerConsumerPattern {
    private static final BlockingQueue<Integer> QUEUE = new ArrayBlockingQueue<>(10);

    static class Producer implements Runnable {
        public void run() {
            int i = 0;
            try {
                while (!Thread.currentThread().isInterrupted()) {
                    QUEUE.put(i++);
                    Thread.sleep(200);
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }
    }

    static class Consumer implements Runnable {
        public void run() {
            try {
                while (true) {
                    Integer item = QUEUE.take();
                    System.out.println("Consumed: " + item);
                    Thread.sleep(500);
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }
    }

    public static void main(String[] args) {
        new Thread(new Producer()).start();
        new Thread(new Consumer()).start();
    }
}
```

> 底层原理：手写版本使用 `synchronized + wait/notify` 实现，必须用 `while` 而非 `if` 检查条件防止虚假唤醒（spurious wakeup）。`BlockingQueue` 封装了所有等待/通知逻辑，生产环境直接使用。

## 5. 两阶段终止模式（Two-Phase Termination）

优雅终止线程的两个阶段：
- **通知阶段**：发送终止信号（`interrupt()` 或标志位）
- **清理阶段**：目标线程收到信号后执行资源清理并终止

```java
public class TwoPhaseTerminationPattern {
    private final Thread monitorThread;

    public TwoPhaseTerminationPattern() {
        this.monitorThread = new Thread(() -> {
            Thread current = Thread.currentThread();
            while (true) {
                if (current.isInterrupted()) {   // 阶段一：检查信号
                    cleanup();                    // 阶段二：清理资源
                    break;
                }
                try {
                    Thread.sleep(1000);
                    doWork();
                } catch (InterruptedException e) {
                    current.interrupt();          // 重新设置中断标志
                }
            }
        });
    }

    public void start() { monitorThread.start(); }
    public void stop()  { monitorThread.interrupt(); }
    private void cleanup() { /* 释放资源：关闭连接、释放文件句柄 */ }
    private void doWork()  { /* 监控任务 */ }
}
```

| 方式 | 安全性 | 资源清理 | 推荐 |
|------|--------|---------|------|
| `stop()`（已废弃） | 极不安全，释放所有锁 | 不执行 finally | 禁止使用 |
| `interrupt()` | 安全 | 可在 finally 中清理 | 推荐 |
| `volatile boolean` 标志位 | 安全 | 无法中断阻塞方法 | 可配合 interrupt |

> 强行终止会释放所有锁，可能导致共享数据处于不一致状态。永远不要使用 `Thread.stop()`。

## 6. 保护性暂停模式（Guarded Suspension）

条件不满足时线程主动挂起等待，条件满足后被唤醒。本质是"等待-通知"机制的标准化。

```java
public class GuardedSuspensionPattern {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition condition = lock.newCondition();
    private volatile boolean ready = false;

    public void guardedMethod(long timeout, TimeUnit unit)
            throws InterruptedException, TimeoutException {
        lock.lock();
        try {
            long nanos = unit.toNanos(timeout);
            while (!ready) {                       // 必须用 while 防虚假唤醒
                if (nanos <= 0) throw new TimeoutException();
                nanos = condition.awaitNanos(nanos);
            }
        } finally { lock.unlock(); }
    }

    public void changeCondition() {
        lock.lock();
        try { ready = true; condition.signalAll(); } finally { lock.unlock(); }
    }
}
```

| 经典应用 | 等待条件 | 条件改变者 |
|---------|---------|-----------|
| `Future.get()` | 任务是否完成 | 执行任务线程 |
| `BlockingQueue.take()` | 队列非空 | `put()` 方法 |
| `CountDownLatch.await()` | 计数是否为 0 | `countDown()` |

> 关键规则：永远在 while 循环中检查条件，而不是 if——防止虚假唤醒。

## 7. 线程封闭模式（Thread Confinement）

| 方式 | 描述 | 实现 |
|------|------|------|
| 栈封闭 | 局部变量，线程独享 | 方法内局部变量 |
| ThreadLocal 封闭 | 每个线程持有变量副本 | `ThreadLocal` 类 |
| 全局变量封闭 | 避免共享可写全局变量 | 无状态对象 |

```java
public class ThreadConfinementPattern {
    // 栈封闭：局部变量天然线程安全
    public int stackConfinement() {
        int localVar = 42;
        return localVar;
    }

    // ThreadLocal 封闭
    private static final ThreadLocal<SimpleDateFormat> DATE_FORMAT =
            ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

    public String formatDate(Date date) {
        return DATE_FORMAT.get().format(date);
    }

    // 必须 remove() 防止内存泄漏
    public void processWithCleanup() {
        try { /* 使用 ThreadLocal */ } finally { DATE_FORMAT.remove(); }
    }
}
```

**ThreadLocal 内存泄漏原理**：ThreadLocalMap 的 Entry 中 key 为弱引用（GC 后 key=null），value 为强引用。线程池中线程长期存活导致"脏 Entry"累积。预防：每次使用后调用 `remove()`。

## 8. 死锁的4个必要条件

死锁是指两个或多个线程因争夺资源而造成互相等待的状态，若无外力干涉将无法继续执行。

### 8.1 四个必要条件（Coffman 条件，必须同时满足）

| 条件 | 描述 | 形象类比 |
|------|------|---------|
| **互斥**（Mutual Exclusion） | 资源只能被一个线程独占使用 | 一个房间只有一个钥匙 |
| **持有并等待**（Hold and Wait） | 线程在持有资源的同时等待其他资源 | 拿着A钥匙等着B钥匙 |
| **不可剥夺**（No Preemption） | 已分配给线程的资源不能被强行剥夺 | 别人手里的钥匙不能抢 |
| **循环等待**（Circular Wait） | 线程之间形成循环等待链 | A等B，B等C，C等A |

### 8.2 哲学家就餐问题（死锁经典模型）

```
  哲学家1 (叉子1, 叉子2)
  哲学家2 (叉子2, 叉子3)
  哲学家3 (叉子3, 叉子4)
  哲学家4 (叉子4, 叉子5)
  哲学家5 (叉子5, 叉子1)
  所有人同时拿起左叉等待右叉 --> 循环等待 --> 死锁
```

**解决方案**：
- 最多允许4位哲学家同时拿叉子（信号量限流，破坏"持有并等待"）
- 拿起两把叉子的操作原子化（破坏"持有并等待"）
- 奇数/偶数哲学家不同拿叉顺序（破坏"循环等待"）

## 9. 死锁代码演示与jstack排查实战

### 9.1 完整死锁演示代码

```java
import java.util.concurrent.TimeUnit;

/**
 * 死锁代码演示
 * 线程1：持有 A，等待 B
 * 线程2：持有 B，等待 A
 * 两个线程反向嵌套加锁形成循环等待
 */
public class DeadlockDemo {

    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        new Thread(() -> {
            synchronized (LOCK_A) {
                System.out.println(Thread.currentThread().getName() + " 持有 A，等待 B...");
                try { TimeUnit.MILLISECONDS.sleep(100); } catch (InterruptedException e) { }
                synchronized (LOCK_B) {
                    System.out.println(Thread.currentThread().getName() + " 持有 B");
                }
            }
        }, "Deadlock-Thread-1").start();

        new Thread(() -> {
            synchronized (LOCK_B) {
                System.out.println(Thread.currentThread().getName() + " 持有 B，等待 A...");
                try { TimeUnit.MILLISECONDS.sleep(100); } catch (InterruptedException e) { }
                synchronized (LOCK_A) {
                    System.out.println(Thread.currentThread().getName() + " 持有 A");
                }
            }
        }, "Deadlock-Thread-2").start();

        // 程序卡死，不会输出"Done"（主线程最终也会受影响）
        System.out.println("Done");
    }
}
```

## 10. 死锁预防与避免策略（破坏4条件）

### 10.1 策略总览

| 死锁条件 | 破坏策略 | 实现方式 |
|---------|---------|---------|
| 互斥 | 使用无锁编程 | CAS、原子类、不可变对象 |
| 持有并等待 | 一次性申请所有资源 | 全有或全无 |
| 不可剥夺 | 使用可超时锁 | `ReentrantLock.tryLock(timeout)` |
| 循环等待 | 固定锁获取顺序 | 按全局排序加锁（锁排序） |

### 10.2 破坏循环等待：固定锁顺序（最实用）

```java
public class DeadlockPreventionOrdered {
    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();
    private static final int ORDER_A = 1, ORDER_B = 2;

    private static void lockInOrder(Object lock1, int order1,
                                    Object lock2, int order2) {
        if (order1 < order2) {
            synchronized (lock1) { synchronized (lock2) { /* 临界区 */ } }
        } else {
            synchronized (lock2) { synchronized (lock1) { /* 临界区 */ } }
        }
    }

    public static void main(String[] args) {
        new Thread(() -> lockInOrder(LOCK_A, ORDER_A, LOCK_B, ORDER_B)).start();
        new Thread(() -> lockInOrder(LOCK_A, ORDER_A, LOCK_B, ORDER_B)).start();
    }
}
```

### 10.3 破坏不可剥夺：tryLock 超时

```java
public class DeadlockPreventionTryLock {
    private static final Lock LOCK_A = new ReentrantLock();
    private static final Lock LOCK_B = new ReentrantLock();

    public static void main(String[] args) {
        Runnable task = () -> {
            try {
                if (LOCK_A.tryLock(100, TimeUnit.MILLISECONDS)) {
                    try {
                        if (LOCK_B.tryLock(100, TimeUnit.MILLISECONDS)) {
                            try { /* 临界区 */ }
                            finally { LOCK_B.unlock(); }
                        }
                    } finally { LOCK_A.unlock(); }    // 获取B失败时释放A
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        };
        new Thread(task).start();
        new Thread(task).start();
    }
}
```

### 10.4 策略选择指南

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 固定锁顺序 | 零开销，实现简单 | 需全局约定 | 少量锁（2-3个） |
| tryLock 超时 | 灵活，自动回滚 | 需处理重试逻辑 | 高并发系统 |
| 全有或全无 | 语义清晰 | 锁粒度变大 | 低频临界区 |
| 无锁编程（CAS） | 无死锁风险 | ABA 问题 | 原子类/并发容器 |

> 最实用方案：在项目中约定"统一锁顺序"（如按对象 hashCode 排序或按业务ID排序），简单高效，零额外开销。

## 11. 并发性能优化思路

### 11.1 优化方向金字塔

```
优先度        手段                      示例
 高    无锁编程              CAS、不可变对象、线程封闭
       减少锁粒度            ConcurrentHashMap 桶锁
       减少锁持有时间        锁内只操作共享变量
       降低锁竞争频率        LongAdder 分段计数
       优化锁实现            ReentrantLock vs synchronized
 低    合理线程池大小        CPU密集型 N+1，IO密集型 N*(1+wait/compute)
```

### 11.2 减少锁持有时间示例

```java
public class LockOptimizationDemo {
    private final Map<String, Integer> cache = new HashMap<>();
    private final ReentrantLock lock = new ReentrantLock();

    public Integer goodGet(String key) {
        Integer val = cache.get(key);          // 1. 无锁检查
        if (val != null) return val;

        lock.lock();
        try {
            val = cache.get(key);              // 2. 双重检查
            if (val == null) {
                val = fetchFromRemote(key);    // 锁内执行
                cache.put(key, val);
            }
            return val;
        } finally { lock.unlock(); }
    }

    private Integer fetchFromRemote(String key) {
        try { Thread.sleep(100); } catch (InterruptedException e) { }
        return key.length();
    }
}
```

### 11.3 优化手段速查

| 手段 | 说明 | 示例 |
|------|------|------|
| 锁消除 | JIT 检测无竞争时移除锁 | 逃逸分析优化 |
| 锁粗化 | 多次加锁合并为一次 | for 循环加锁提到循环外 |
| 读写分离 | 读锁/写锁分离 | `ReentrantReadWriteLock` |
| 乐观读 | 读不阻塞写 | `StampedLock.tryOptimisticRead()` |
| 分段思想 | 数据分片减少竞争 | `ConcurrentHashMap`、`LongAdder` |
| 虚拟线程 | 轻量级线程减少上下文切换 | JDK 21 Virtual Threads |

## 12. 面试高频考点

### 12.1 设计模式类

**Q1: 不可变模式如何保证线程安全？** final 类 + final 字段 + 无 setter + 防御性拷贝。应用：String、Integer、BigDecimal。加分点：`List.of()` 与 `Collections.unmodifiableList()` 的区别。

**Q2: 生产者-消费者实现方式？** (1) `BlockingQueue`（最推荐）, (2) wait/notify 手写（while 防虚假唤醒）, (3) `Condition + ReentrantLock`, (4) Semaphore 双信号量。

**Q3: 两阶段终止模式核心？** 不暴力停止，通过 interrupt 发送信号，目标线程在安全点响应并执行清理。`stop()` 废弃原因：释放所有锁导致数据不一致。

### 12.2 死锁类

**Q4: 死锁四个条件及破坏方法？**

| 条件 | 破坏方法 | 面试关键词 |
|------|---------|-----------|
| 互斥 | 无锁编程 | "CAS + 不可变" |
| 持有并等待 | 一次性申请全部资源 | "全有或全无" |
| 不可剥夺 | `tryLock(timeout)` | "超时放弃" |
| 循环等待 | 固定锁顺序 | "锁排序（Lock Ordering）" |

**Q5: 线上排查死锁步骤？** `jps -l` 找 PID -> `jstack <pid>` 取栈 -> 搜索 `Found one Java-level deadlock`。

**Q6: 哲学家就餐问题解决方案？** 限流4人同时拿叉子（信号量）、原子化拿两把叉子、奇偶哲学家不同拿叉顺序。

### 12.3 并发优化类

**Q7: LongAdder vs AtomicLong？** AtomicLong 所有线程 CAS 同一变量，高竞争失败率高；LongAdder 分段 Cell 数组，每个线程更新自己的 Cell，最终求和汇总，空间换时间。

**Q8: ThreadLocal 内存泄漏原因及预防？** Entry 的 key 为弱引用（GC 后 null），value 为强引用（不回收）。每次使用后调用 `remove()`。

**Q9: synchronized vs ReentrantLock？** synchronized 隐式自动释放，不可中断；ReentrantLock 显式手动释放，支持可中断、可超时、公平锁、多 Condition。
