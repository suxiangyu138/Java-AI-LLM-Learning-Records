## 1. 虚拟线程原理与最佳实践 {#1}

> 📖 原理深度讲解详见 [JUC-12-虚拟线程与结构化并发](../02-JUC高并发编程/12-虚拟线程与结构化并发.md)

### 1.1 一句话原理

```text
虚拟线程 = 由 JVM 调度的轻量级线程，不绑定 OS 线程

平台线程:  1 个 Java 线程 = 1 个 OS 线程（~1MB 栈空间）
虚拟线程:  N 个虚拟线程 → M 个载体线程 (OS 线程)
           阻塞时自动 "卸载" (unmount)
           恢复时重新 "挂载" (mount)

结果：可以创建数百万个虚拟线程，内存开销极低
```

### 1.2 创建与使用

```java
// ── 方式1: 直接创建 ──
Thread vt = Thread.ofVirtual()
    .name("my-virtual-thread")
    .start(() -> {
        System.out.println("Running on: " + Thread.currentThread());
    });

// ── 方式2: Virtual Thread Executor（最常用）──
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    // 提交 10 万个任务，每个任务一个虚拟线程
    for (int i = 0; i < 100_000; i++) {
        int taskId = i;
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1));  // IO 模拟
            return "task-" + taskId + " done";
        });
    }
}  // try-with-resources 自动等待所有任务完成并关闭

// ── 方式3: Thread.Builder ──
Thread.Builder builder = Thread.ofVirtual()
    .name("worker-", 1)         // 前缀 + 编号
    .inheritInheritableThreadLocals(false);
```

### 1.3 适用与不适用场景

| 场景 | 虚拟线程 | 平台线程 |
|------|:---:|:---:|
| **HTTP 请求处理** | ✅ 最佳 | ⚠️ 需线程池 |
| **数据库查询** | ✅ 天然适配 | ⚠️ 连接池瓶颈 |
| **文件 IO** | ✅ | ⚠️ |
| **消息消费** | ✅ | ⚠️ |
| **CPU 密集计算** | ❌ 无优势 | ✅ 核数匹配 |
| **需要线程本地状态** | ⚠️ 不推荐 | ✅ |
| **synchronized 内有阻塞 IO** | ❌ Pinning！ | ✅ |

### 1.4 Pinning 问题 —— 最重要的一条规则

```java
// ⚠️ Pinning 发生条件：虚拟线程在 synchronized 块内执行阻塞操作，
// 载体线程被 "钉住"，无法卸载去服务其他虚拟线程

// ❌ 问题代码 —— 导致 Pinning
synchronized (lock) {
    String data = httpClient.send(request);  // 阻塞 IO 在 synchronized 内！
    process(data);
}

// ✅ 修复：替换为 ReentrantLock
lock.lock();
try {
    String data = httpClient.send(request);  // 阻塞时虚拟线程正常卸载
    process(data);
} finally {
    lock.unlock();
}

// ── 调试 Pinning ──
// JVM 参数：-Djdk.tracePinnedThreads=full
// 输出：
//  Thread[#123,virtual] pinned due to synchronized block
//      at com.example.Service.process(Service.java:42)
```

```java
// ── Pinning 检测工具 ──
public class PinningDetector {
    /**
     * 定期检测是否有虚拟线程被 pin
     * 配合 JFR 事件 jdk.VirtualThreadPinned
     */
    public static void monitor() {
        ScheduledExecutorService monitor =
            Executors.newSingleThreadScheduledExecutor();

        monitor.scheduleAtFixedRate(() -> {
            ThreadMXBean bean = ManagementFactory.getThreadMXBean();
            long pinnedCount = bean.getTotalStartedThreadCount();
            // 上报到监控系统
            Metrics.gauge("jvm.virtual.threads.pinned", pinnedCount);
        }, 1, 10, TimeUnit.SECONDS);
    }
}
```

### 1.5 性能对比

```java
/**
 * 对比：平台线程池 vs 虚拟线程
 * 场景：10000 个并发的 HTTP 调用（每个耗时 100ms）
 */
public class VirtualThreadBenchmark {

    // 平台线程池 —— 需要 10000 个 OS 线程（不可能）
    // 实际最多 ~2000 线程，其余排队 → QPS 受限

    // 虚拟线程 —— 10000 个虚拟线程映射到 ~10 个载体线程
    @Test
    void virtualThreads() throws Exception {
        long start = System.currentTimeMillis();

        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            List<Future<String>> futures = new ArrayList<>();
            for (int i = 0; i < 10_000; i++) {
                futures.add(executor.submit(() -> {
                    Thread.sleep(Duration.ofMillis(100));  // 模拟 IO
                    return "ok";
                }));
            }
            futures.forEach(f -> { try { f.get(); } catch (Exception e) {} });
        }

        long elapsed = System.currentTimeMillis() - start;
        System.out.println("10000 tasks completed in " + elapsed + "ms");
        // 预期 ~100ms（所有任务并发执行）
        // 平台线程池 ~5-10 秒（排队等待）
    }
}
```

## 2. Structured Concurrency —— 结构化并发 {#2}

### 2.1 核心思想

```text
"当控制流分裂为多个并发任务时，它们必须重新汇合"

传统问题 (CompletableFuture):
  ┌── 任务A ──┐
  主线程 ─── 任务B ─── ???  (B 可能还在运行，或已泄漏)
  └── 任务C ──┘
  → 主线程 return 了，子任务还在跑 → 线程泄漏！

结构化并发 (StructuredTaskScope):
  ┌── 任务A ──┐
  主线程 ─── 任务B ─── scope.join() → 确保全部完成
  └── 任务C ──┘
  → try-with-resources 确保 scope 关闭时取消所有未完成子任务
```

### 2.2 三大核心模式

```java
// ── 模式1: ShutdownOnFailure（全成功/全失败）──
// 用途：需要所有子任务都成功 (如：聚合多个数据源)
String fetchUserAndOrders(Long userId) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        // 并发提交两个子任务
        Subtask<User> userTask = scope.fork(() -> fetchUser(userId));
        Subtask<List<Order>> ordersTask = scope.fork(() -> fetchOrders(userId));

        scope.join();               // 等待全部完成
        scope.throwIfFailed();      // 任一失败 → 抛异常，其余被取消

        return buildResponse(userTask.get(), ordersTask.get());
    }
    // scope 关闭 → 保证所有子任务已终止
}

// ── 模式2: ShutdownOnSuccess（竞速模式）──
// 用途：多个数据源返回最快的结果 (如：缓存/主库/备库)
String queryFastest(String key) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
        scope.fork(() -> queryCache(key));       // 缓存 ~1ms
        scope.fork(() -> queryMainDB(key));       // 主库 ~10ms
        scope.fork(() -> queryBackupDB(key));     // 备库 ~50ms

        return scope.join().result();   // 返回最先成功的结果
    }
    // 其余子任务自动取消
}

// ── 模式3: 自定义 Scope（部分成功）──
// 用途：等前 N 个成功就返回
class AnySuccessScope<T> extends StructuredTaskScope<T> {
    private final int minSuccess;
    private final List<T> results = Collections.synchronizedList(new ArrayList<>());
    private final CountDownLatch latch;

    public AnySuccessScope(int minSuccess) {
        this.minSuccess = minSuccess;
        this.latch = new CountDownLatch(minSuccess);
    }

    @Override
    protected void handleComplete(Subtask<? extends T> subtask) {
        if (subtask.state() == Subtask.State.SUCCESS) {
            results.add(subtask.get());
            latch.countDown();
        }
    }

    public List<T> results() throws InterruptedException {
        latch.await(5, TimeUnit.SECONDS);
        return new ArrayList<>(results);
    }
}
```

### 2.3 超时控制

```java
// ── StructuredTaskScope 的超时机制 ──
String fetchWithTimeout(Long userId) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        Subtask<User> userTask = scope.fork(() -> fetchUser(userId));
        Subtask<List<Order>> orderTask = scope.fork(() -> fetchOrders(userId));

        // 整体超时：1 秒内全部完成
        scope.joinUntil(Instant.now().plusSeconds(1));

        // 部分完成？让 scope 自行处理
        scope.throwIfFailed();
        return buildResponse(userTask.get(), orderTask.get());
    }
}

// ── 单任务超时 ──
String fetchWithPerTaskTimeout() throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        scope.fork(() -> {
            try {
                return CompletableFuture.supplyAsync(() -> fetchUser(1L))
                    .get(500, TimeUnit.MILLISECONDS);
            } catch (TimeoutException e) {
                return User.FALLBACK;  // 单个任务兜底
            }
        });
        // ...
    }
}
```

### 2.4 Structured Concurrency vs CompletableFuture

| 维度 | StructuredTaskScope | CompletableFuture |
|------|:---:|:---:|
| **线程安全** | ✅ try-with-resources 保证 | ❌ 可能泄漏 |
| **异常传播** | ✅ 聚合异常自动传播 | ⚠️ 需手动 exceptionally |
| **取消传播** | ✅ scope 关闭即取消全部 | ❌ 需手动 cancel |
| **调试体验** | ✅ 完整因果链堆栈 | ❌ 回调地狱堆栈 |
| **学习成本** | ⭐⭐ 低 | ⭐⭐⭐⭐ 高 |
| **API 要求** | JDK 21+ Preview | JDK 8+ |

## 3. Scoped Values —— 跨线程上下文传递 {#3}

### 3.1 ThreadLocal 在虚拟线程中的问题

```java
// ── ThreadLocal 的问题 ──
// 1. 虚拟线程数量巨大 → ThreadLocal 内存开销大
// 2. 虚拟线程会复用载体线程 → ThreadLocal 可能污染
// 3. 子线程继承需 InheritableThreadLocal → 更深的问题

// ❌ 虚拟线程 + ThreadLocal → 反模式
private static final ThreadLocal<String> USER_CONTEXT = new ThreadLocal<>();

// ✅ 用 Scoped Values 替代
private static final ScopedValue<String> USER_CONTEXT = ScopedValue.newInstance();
```

### 3.2 Scoped Values 基本用法

```java
// ── 创建 ScopedValue ──
private static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();
private static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

// ── 绑定值 + 执行 ──
void handleRequest(User user, String requestId) {
    ScopedValue.where(CURRENT_USER, user)
               .where(REQUEST_ID, requestId)
               .run(() -> {
                   // 整个调用栈中均可访问
                   serviceA.process();
                   serviceB.process();
               });
    // 离开 run() → 绑定自动解除，不可变保证
}

// ── 在深层调用中获取 ──
class SomeDeepService {
    void process() {
        User user = CURRENT_USER.get();     // 获取上下文
        String rid = REQUEST_ID.get();
        log.info("User={}, RequestId={}", user.getId(), rid);
    }
}

// ── 带返回值 ──
String result = ScopedValue.where(CURRENT_USER, user)
    .call(() -> processAndReturn());
```

### 3.3 Scoped Values vs ThreadLocal

| 维度 | ThreadLocal | Scoped Values |
|------|:---:|:---:|
| **可变性** | ✅ 可变（set） | ❌ 不可变（仅 bind 时） |
| **继承方式** | InheritableThreadLocal（深拷贝） | 自动继承（零拷贝） |
| **虚拟线程友好** | ❌ 内存开销大 | ✅ 轻量，自动清理 |
| **子线程可见** | ⚠️ 需显式继承 | ✅ 自动继承 |
| **生命周期** | 手动 remove（易泄漏） | 自动（离开 run()） |
| **JDK 版本** | 1.2+ | 21+ (Preview) / 23+ |

## 4. 从 Reactive 迁移到 Virtual Threads {#4}

### 4.1 迁移决策

```text
什么情况下值得从 WebFlux/Reactor 迁移？

✅ 迁移：
  - 团队不熟悉 Reactive，维护成本高
  - 代码调试困难（堆栈可读性差）
  - 没有背压需求（大部分 CRUD 场景）
  - 性能瓶颈不是 CPU 而是 IO 等待

❌ 保留 Reactive：
  - 有流式处理/背压需求（WebSocket 推送）
  - 事件驱动架构（高频事件处理）
  - 已有大量 Reactive 基建投入
```

### 4.2 迁移步骤

```java
// ── 步骤1: Controller 从 Mono/Flux 改为同步 ──
// ❌ WebFlux
@GetMapping("/users/{id}")
public Mono<User> getUser(@PathVariable Long id) {
    return userService.findById(id);  // 返回 Mono<User>
}

// ✅ WebMVC + Virtual Threads
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    return userService.findById(id);  // 直接返回 User
}

// ── 步骤2: Service 层改为同步阻塞 ──
// ❌ 响应式链式调用
public Mono<Order> createOrder(OrderRequest req) {
    return userService.getUser(req.getUserId())
        .zipWhen(user -> productService.getProduct(req.getProductId()))
        .flatMap(tuple -> orderRepository.save(...));
}

// ✅ 同步阻塞 + 虚拟线程（代码清晰十倍）
public Order createOrder(OrderRequest req) {
    User user = userService.getUser(req.getUserId());       // 同步阻塞
    Product product = productService.getProduct(req.getProductId());
    return orderRepository.save(new Order(user, product));
}

// ── 步骤3: 保留 Reactive 的场景用桥接 ──
// 需要背压的流式场景 → 保留 Reactor
// 内部阻塞逻辑 → 卸载到虚拟线程
public Mono<DataChunk> streamProcess() {
    return Mono.fromCallable(() ->
        Executors.newVirtualThreadPerTaskExecutor().submit(() -> {
            // 阻塞式处理
            return heavyProcess();
        }).get()
    ).subscribeOn(Schedulers.boundedElastic());
}
```

### 4.3 迁移优先级

```text
优先级1: 纯 CRUD 服务 → 直接替换，收益最大
优先级2: 简单聚合服务 → 引入 StructuredTaskScope 替代 zip/flatMap
优先级3: 有流式场景 → 混合模式 (Reactive 边界 + VT 内部)
优先级4: 事件驱动系统 → 暂不迁移，保留 Reactive
```

## 5. Spring Boot 3.2+ 集成 {#5}

### 5.1 一行配置开启

```yaml
# application.yml
spring:
  threads:
    virtual:
      enabled: true    # 🎉 所有 HTTP 请求都运行在虚拟线程上了
```

```java
// 效果：
// Tomcat/Jetty 的每个请求分配一个虚拟线程
// @Async 标注的方法运行在虚拟线程上
// 不再需要配置 server.tomcat.threads.max
```

### 5.2 自定义配置

```java
@Configuration
public class VirtualThreadConfig {

    // ── 替换整个应用的线程池为虚拟线程 ──
    @Bean
    public ExecutorService applicationTaskExecutor() {
        return Executors.newVirtualThreadPerTaskExecutor();
    }

    // ── Spring @Async 使用虚拟线程 ──
    @Bean
    public Executor asyncTaskExecutor() {
        return Executors.newVirtualThreadPerTaskExecutor();
    }

    // ── 数据库连接池调整（线程数不再是瓶颈）──
    // application.yml:
    // spring.datasource.hikari.maximum-pool-size: 50  (之前可能只有 20)
    // 现在可以用更多连接，因为虚拟线程量大，需要更多 DB 连接

    // ── JDBC 客户端配置 ──
    @Bean
    public RestClient restClient() {
        return RestClient.builder()
            .requestFactory(new JdkClientHttpRequestFactory())  // 使用 Java HttpClient
            .build();
    }
}
```

### 5.3 监控指标

```java
@Configuration
public class VirtualThreadMetrics {

    @Bean
    public MeterBinder virtualThreadMetrics() {
        return registry -> {
            // 虚拟线程总数
            Gauge.builder("jvm.virtual.threads.count",
                    () -> ManagementFactory.getThreadMXBean().getThreadCount())
                .register(registry);

            // 需要 JMX 开启虚拟线程统计
            // -Djdk.trackAllVirtualThreads=true
        };
    }
}
```

> 🎯 **核心要点**：虚拟线程不是"更快的线程"——它是让你能用**更简单的代码**达到**更高的并发度**。迁移的核心收益是**代码可维护性**，性能提升是副产品。
