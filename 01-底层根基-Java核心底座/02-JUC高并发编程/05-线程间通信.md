## 1. 线程间通信概述与原理

### 1.1 为什么需要线程间通信

多线程环境中，不同线程通常承担不同的业务任务（生产者生产数据、消费者处理数据、协作线程按步骤执行）。若无通信机制，线程只能通过"无限循环 + 休眠"的轮询方式感知状态变化，导致三大问题：

| 问题 | 说明 |
|------|------|
| **CPU 资源浪费** | 空轮询持续占用处理器，即使线程无实际任务也会频繁检查状态 |
| **响应延迟** | 休眠时间难以精准控制 —— 过久则响应滞后，过短则加剧 CPU 消耗 |
| **数据不一致** | 缺少同步协同，并发访问共享资源会导致读取错误、修改覆盖 |

> **核心目标**：让线程在条件不满足时主动等待，条件满足时被精准唤醒，实现高效协作并保证线程安全。

### 1.2 通信的两个核心前提

| 前提 | 说明 |
|------|------|
| **共享载体** | 多个线程必须基于同一个共享对象/资源进行通信（如共享队列、共享变量、锁对象） |
| **线程安全** | 对共享资源的操作必须保证原子性、可见性和有序性，通常通过 `synchronized` 或 `Lock` 实现 |

> **共享资源选择建议**：优先使用不可变对象作为通信载体；若使用可变对象，需确保所有修改操作被同步控制，避免线程读取到中间态数据。

### 1.3 线程状态与通信的关系

```
                        ┌───────────────┐
                        │     NEW       │
                        │ (new Thread())│
                        └───────┬───────┘
                                │ start()
                                ▼
                        ┌───────────────┐
                  ┌────▶│  RUNNABLE     │◀────┐
                  │     │ (就绪/运行)    │     │
                  │     └───────┬───────┘     │
  ┌───────────────┐            │              │
  │   BLOCKED     │◀── 未获得 ─┤              │
  │ (等待锁)      │   sync锁   │              │
```

## 2. wait/notify/notifyAll 核心方法

### 2.1 方法对比

三个方法均为 `Object` 类的 `native` 方法，**必须在同步代码块/同步方法中调用（持有对象锁时）**，否则抛出 `IllegalMonitorStateException`。

| 方法 | 核心作用 | 是否释放锁 | 调用条件 | 关键细节 |
|------|----------|-----------|----------|---------|
| `wait()` | 当前线程进入无限期等待，直到被唤醒或中断 | **是**（立即释放持有的锁） | 必须在 `synchronized` 块/方法中；必须持有当前对象的锁 | 被唤醒后不会立即执行，需重新竞争锁；支持 `wait(long timeout)` 超时自动唤醒 |
| `wait(long timeout)` | 带超时的等待，超时后自动唤醒 | **是** | 同上 | `timeout` 为 0 时等同于 `wait()`；超时后线程进入就绪状态参与锁竞争 |
| `notify()` | 随机唤醒一个在当前对象上等待的线程（无法指定目标） | **否**（唤醒后仍持有锁） | 同上 | 唤醒的线程是随机的；若没有线程在等待，调用无效果 |
| `notifyAll()` | 唤醒所有在当前对象上等待的线程 | **否** | 同上 | 实际开发中更常用；所有线程竞争同一把锁，只有一个能执行，其余继续等待 |

### 2.2 关键行为细节

- **`wait()` 释放锁，`notify()`/`notifyAll()` 不释放锁**：调用 `wait()` 后线程立即释放锁并进入等待队列；`notify()` 后线程仍持有锁，需执行完同步代码块才释放，被唤醒线程需等待锁释放后才能竞争。
- **锁对象一致性**：`wait()`、`notify()`、`notifyAll()` 必须调用**同一个对象**的方法，否则无法实现通信。
- **线程中断**：`wait()` 会响应中断，抛出 `InterruptedException`，中断标志被清除。

> 💡 **设计思路**：`wait/notify` 机制本质上是**基于共享对象监视器（Monitor）的协作**，JVM 为每个对象维护一个等待集（Wait Set），调用 `wait()` 的线程进入该等待集，`notify()` 从等待集中随机移出一个线程。

## 3. 虚假唤醒与 while 循环范式

### 3.1 什么是虚假唤醒

线程可能被 JVM 意外唤醒（如系统中断、JVM 内部调度），此时等待条件并未真正满足。若用 `if` 判断条件，会导致线程在条件不满足时错误执行后续逻辑。

```java
// 错误写法：if 判断 — 虚假唤醒会导致逻辑错误
synchronized (lock) {
    if (count == 0) {   // ❌ 必须用 while
        wait();
    }
    // 线程被虚假唤醒后直接执行到这里，但 count 可能仍为 0
    consume();
}
```

### 3.2 正确范式：while 循环检查

```java
synchronized (lock) {
    // 必须用 while 循环检查等待条件
    while (condition == false) {
        wait(); // 条件不满足，等待
    }
    // 条件满足，继续执行（无论被何种方式唤醒，都会重新检查条件）
    doSomething();
}
```

> ⚠️ **JDK 官方规范**：`wait()` 应始终放在 `while` 循环中调用。这是 Java 线程通信的**第一铁律**，适用于所有等待-唤醒机制（包括 `Condition.await()`）。

### 3.3 虚假唤醒的根源

| 原因 | 说明 |
|------|------|
| JVM 实现层面 | 某些 JVM 实现中，等待线程可能因平台底层原因被意外唤醒 |
| 多条件共享等待队列 | 使用 `notifyAll()` 时，所有等待线程被唤醒，但只有部分线程的条件满足 |
| 系统中断信号 | 操作系统层面的信号传递可能导致线程提前退出等待状态 |

## 4. 生产者-消费者模型（wait/notify 实现）

```java
import java.util.LinkedList;
import java.util.Queue;

// 共享资源：固定容量的消息队列（通信载体）
class MessageQueue {
    private final Queue<String> queue = new LinkedList<>();
    private final int CAPACITY = 5;

    // 生产者方法：同步方法保证线程安全
    public synchronized void produce(String message) throws InterruptedException {
        // while 循环检查条件，防止虚假唤醒
        while (queue.size() == CAPACITY) {
            System.out.println("队列已满，生产者 " + Thread.currentThread().getName() + " 等待...");
            wait(); // 队列满，释放锁，进入等待
        }
        queue.add(message);
        System.out.println("生产者 " + Thread.currentThread().getName()
                + " 生产：" + message + "，当前大小：" + queue.size());
        // 唤醒消费者：有消息可消费
        notifyAll();
    }

    // 消费者方法：同步方法保证线程安全
    public synchronized String consume() throws InterruptedException {
        while (queue.isEmpty()) {
            System.out.println("队列空，消费者 " + Thread.currentThread().getName() + " 等待...");
            wait(); // 队列空，释放锁，进入等待
        }
        String message = queue.poll();
        System.out.println("消费者 " + Thread.currentThread().getName()
                + " 消费：" + message + "，当前大小：" + queue.size());
        // 唤醒生产者：有空间可生产
        notifyAll();
        return message;
    }
}

// 测试类：多生产者 + 多消费者
public class WaitNotifyProducerConsumer {
    public static void main(String[] args) {
        MessageQueue queue = new MessageQueue();

        // 启动 3 个生产者
        for (int i = 0; i < 3; i++) {
            int id = i + 1;
            new Thread(() -> {
                try {
                    for (int j = 0; j < 4; j++) {
                        queue.produce("消息-" + id + "-" + (j + 1));
                        Thread.sleep(500); // 模拟生产耗时
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }, "P" + id).start();
        }

        // 启动 2 个消费者
        for (int i = 0; i < 2; i++) {
            int id = i + 1;
            new Thread(() -> {
                try {
                    while (true) {
                        queue.consume();
                        Thread.sleep(800); // 模拟消费耗时
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }, "C" + id).start();
        }
    }
}
```

### 核心设计要点

| 要点 | 说明 |
|------|------|
| **共享对象** | `MessageQueue` 实例被所有生产者/消费者共享，作为通信载体 |
| **同步控制** | `produce()` 和 `consume()` 均为 `synchronized` 方法，保证线程安全 |
| **while 循环** | 条件检查使用 `while`而非 `if`，防止虚假唤醒 |
| **notifyAll() 而非 notify()** | 避免仅唤醒同类线程导致"信号丢失"（所有生产者等待，却只唤醒了另一个生产者） |
| **中断处理** | 捕获 `InterruptedException` 后调用 `Thread.currentThread().interrupt()` 恢复中断标志 |

> 🎯 **小结**：wait/notify 机制适用于简单等待-唤醒场景，代码简洁、原生支持，但存在**无法精准唤醒**、**单个等待队列**等局限，复杂场景需升级为 Lock + Condition。

## 5. Thread.join() 详解

### 5.1 核心作用

`join()` 让当前线程等待目标线程终止后再继续执行，实现线程间的**顺序化执行**。

```java
public class JoinDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(() -> {
            System.out.println("T1 开始执行");
            try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            System.out.println("T1 执行完毕");
        });

        Thread t2 = new Thread(() -> {
            System.out.println("T2 开始执行");
            try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            System.out.println("T2 执行完毕");
        });

        t1.start();
        t2.start();

        t1.join(); // 主线程等待 t1 结束
        t2.join(); // 主线程等待 t2 结束

        System.out.println("所有线程执行完毕，主线程继续");
    }
}
```

### 5.2 重载方法

| 方法 | 说明 |
|------|------|
| `join()` | 无限等待目标线程终止 |
| `join(long millis)` | 最多等待 `millis` 毫秒，超时后当前线程继续执行 |
| `join(long millis, int nanos)` | 最多等待 `millis` 毫秒 + `nanos` 纳秒 |

### 5.3 底层原理

`join()` 的底层实现本质上是**基于 `wait/notify` 的封装**：

```java
// Thread.join() 简化源码逻辑
public final synchronized void join(long millis) throws InterruptedException {
    if (millis == 0) {
        while (isAlive()) {
            wait(0); // 当前线程等待，直到目标线程终止时调用 notifyAll()
        }
    } else {
        // 带超时的等待逻辑
    }
}
```

> 💡 **关键理解**：`join()` 调用 `wait(0)` 让当前线程进入等待状态；目标线程终止时，JVM 会调用该线程对象的 `notifyAll()`，唤醒所有通过 `join()` 等待的线程。

### 5.4 join() vs 其他通信方式

| 方式 | 适用场景 | 特点 |
|------|---------|------|
| `join()` | 一个线程等待另一个线程结束 | 简单直接，只能等待线程终止 |
| `CountDownLatch` | 等待多个线程完成任务（不一定是终止） | 更灵活，计数归零即可 |
| `CyclicBarrier` | 多个线程互相等待到达屏障点 | 可循环使用 |

## 6. LockSupport.park/unpark

### 6.1 核心概念

`LockSupport` 是 JUC 提供的线程阻塞/唤醒原语工具类，基于 **Unsafe 类** 实现，核心机制是**许可证（Permit）** 模型：

- `park()`：等待获取许可证，若许可证可用则消耗许可证并返回，否则阻塞
- `unpark(Thread t)`：为指定线程发放许可证（许可证累计上限为 1）

### 6.2 API 说明

| 方法 | 说明 |
|------|------|
| `park()` | 阻塞当前线程，直到获得许可或被中断 |
| `park(Object blocker)` | 带阻塞对象的 `park()`，便于线程 dump 定位 |
| `parkNanos(long nanos)` | 超时阻塞，纳秒级 |
| `parkUntil(long deadline)` | 阻塞到指定绝对时间（`System.currentTimeMillis()`） |
| `unpark(Thread thread)` | 唤醒指定线程，发放许可证 |

### 6.3 核心特性

- **不需要在同步代码块中调用**：与 `wait/notify` 不同，`park/unpark` 不依赖 `synchronized` 或锁
- **许可证机制**：`unpark` 相当于发放一个许可证，`park` 相当于消费一个许可证；若先调用 `unpark` 再调用 `park`，线程不会阻塞
- **响应中断**：`park()` 会响应中断，抛出 `InterruptedException` 后返回

```java
import java.util.concurrent.locks.LockSupport;

public class LockSupportDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> {
            System.out.println("线程开始运行");
            // 阻塞当前线程，等待许可证
            LockSupport.park();
            System.out.println("线程被唤醒，继续执行");
            // 验证：响应中断
            System.out.println("中断状态：" + Thread.currentThread().isInterrupted());
        });
        t.start();

        Thread.sleep(1000);
        System.out.println("主线程准备唤醒子线程");
        // 为指定线程发放许可证
        LockSupport.unpark(t);
    }
}
```

> 💡 **park/unpark vs wait/notify**：`park/unpark` 的许可证模型使得**调用顺序可以颠倒**（先 `unpark` 再 `park` 不会阻塞），而 `wait/notify` 必须严格按照"先 wait 后 notify"的顺序，否则会丢失信号。

### 6.4 对比总结

| 特性 | wait/notify | LockSupport.park/unpark |
|------|-------------|------------------------|
| 依赖条件 | 必须在 `synchronized` 块内 | 无要求 |
| 唤醒精度 | `notify()` 随机唤醒，`notifyAll()` 唤醒全部 | 精准唤醒指定线程 |
| 顺序要求 | 必须先 wait 再 notify，否则信号丢失 | 可先 unpark 再 park，不会丢失 |
| 中断响应 | 抛出 `InterruptedException` | 正常返回，可通过中断状态判断 |
| 超时支持 | `wait(long timeout)` | `parkNanos()`、`parkUntil()` |

## 7. Condition 实现精准唤醒

### 7.1 Condition 的概念

`Condition` 是 JUC 提供的替代 `wait/notify` 的接口，与 `Lock` 配合使用，核心优势在于**支持多个独立的等待队列**，实现精准唤醒。

| Condition 方法 | 对应 Object 方法 | 说明 |
|----------------|-----------------|------|
| `await()` | `wait()` | 进入等待，释放锁，响应中断 |
| `awaitUninterruptibly()` | — | 不响应中断的等待 |
| `await(long time, TimeUnit unit)` | `wait(long timeout)` | 超时等待，返回 `boolean` 表示是否被唤醒 |
| `signal()` | `notify()` | 唤醒当前 Condition 上的一个等待线程 |
| `signalAll()` | `notifyAll()` | 唤醒当前 Condition 上的所有等待线程 |

### 7.2 多 Condition 精准唤醒设计

传统 `synchronized + wait/notify` 只有一个等待队列，调用 `notifyAll()` 会唤醒**所有**等待线程，包括不必要的线程竞争。而 `Lock + Condition` 可以为每个条件分配独立的等待队列：

```java
Lock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();  // 生产者等待队列：队列未满
Condition notEmpty = lock.newCondition();  // 消费者等待队列：队列非空
```

> 🎯 **精准唤醒的优势**：生产者生产后只唤醒消费者（`notEmpty.signal()`），消费者消费后只唤醒生产者（`notFull.signal()`），避免无效线程竞争，减少上下文切换。

### 7.3 Condition 使用范式

```java
lock.lock();
try {
    while (条件不满足) {
        condition.await(); // 线程等待并释放锁
    }
    // 执行临界区操作
    otherCondition.signal(); // 精准唤醒相关线程
} finally {
    lock.unlock(); // 必须放在 finally 中
}
```

## 8. 生产者-消费者模型（Lock+Condition 实现）

```java
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

// 高级阻塞队列：精准唤醒，支持公平锁
class AdvancedBlockingQueue<T> {
    private final Lock lock = new ReentrantLock(true); // 公平锁
    // 两个独立 Condition，实现精准唤醒
    private final Condition notFull  = lock.newCondition();  // 生产者等待：队列未满
    private final Condition notEmpty = lock.newCondition();  // 消费者等待：队列非空

    private final T[] items;
    private int count;
    private int putIndex;
    private int takeIndex;

    @SuppressWarnings("unchecked")
    public AdvancedBlockingQueue(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("容量必须大于 0");
        }
        this.items = (T[]) new Object[capacity];
    }

    // 生产者入队
    public void put(T item) throws InterruptedException {
        lock.lockInterruptibly(); // 可中断获取锁
        try {
            while (count == items.length) {
                notFull.await(); // 在 notFull 队列等待
            }
            items[putIndex] = item;
            putIndex = (putIndex + 1) % items.length;
            count++;
            // 精准唤醒消费者：只有消费者在等待 notEmpty
            notEmpty.signal();
        } finally {
            lock.unlock(); // 必须释放锁
        }
    }

    // 消费者出队
    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) {
                notEmpty.await(); // 在 notEmpty 队列等待
            }
            T x = items[takeIndex];
            items[takeIndex] = null; // 帮助 GC
            takeIndex = (takeIndex + 1) % items.length;
            count--;
            // 精准唤醒生产者：只有生产者等待 notFull
            notFull.signal();
            return x;
        } finally {
            lock.unlock();
        }
    }
}

// 测试类
public class LockConditionProducerConsumer {
    public static void main(String[] args) {
        AdvancedBlockingQueue<String> queue = new AdvancedBlockingQueue<>(5);

        // 启动 2 个生产者
        for (int i = 0; i < 2; i++) {
            int id = i + 1;
            new Thread(() -> {
                try {
                    for (int j = 0; j < 5; j++) {
                        queue.put("数据-" + id + "-" + (j + 1));
                        Thread.sleep(600);
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }, "P" + id).start();
        }

        // 启动 3 个消费者
        for (int i = 0; i < 3; i++) {
            int id = i + 1;
            new Thread(() -> {
                try {
                    while (true) {
                        queue.take();
                        Thread.sleep(1000);
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }, "C" + id).start();
        }
    }
}
```

### Lock+Condition 实现 vs wait/notify 实现

| 对比维度 | wait/notify 实现 | Lock+Condition 实现 |
|---------|-----------------|-------------------|
| 等待队列 | 单个等待队列 | 多个独立 Condition 队列 |
| 唤醒粒度 | `notifyAll()` 唤醒所有 | `signal()` 只唤醒对应条件的线程 |
| 锁机制 | `synchronized` 自动管理 | `ReentrantLock` 手动管理 |
| 可中断 | 支持 | 支持 `lockInterruptibly()` |
| 超时等待 | `wait(long timeout)` | `await(long, TimeUnit)` 返回唤醒状态 |
| 锁释放保障 | 自动释放 | 必须在 `finally` 中 `unlock()` |

> ⚠️ **Lock 使用警告**：`lock()` 后必须在 `finally` 块中调用 `unlock()`，否则异常会导致锁永久泄漏。`synchronized` 由 JVM 自动管理释放，不存在此问题。

## 9. 各种通信方式对比与选型

### 9.1 总体对比

| 通信方式 | 核心机制 | 等待队列 | 唤醒精度 | 依赖条件 | 适用场景 |
|---------|---------|---------|---------|---------|---------|
| `wait/notify` | Object Monitor | 单个 | 低（随机/全部） | `synchronized` 块内 | 简单等待-唤醒 |
| `Lock + Condition` | AQS ConditionObject | 多个 | 高（精准唤醒） | `Lock` 显式锁 | 复杂多条件控制 |
| `join()` | 基于 `wait()` | — | — | 目标线程终止 | 等待线程结束 |
| `LockSupport.park/unpark` | Unsafe 许可证 | — | 最高（指定线程） | 无 | 灵活阻塞/唤醒 |
| `CountDownLatch` | AQS 共享模式 | — | — | 计数归零 | 等待多任务完成 |
| `CyclicBarrier` | ReentrantLock + Condition | — | — | 全部到达屏障 | 多线程互相等待 |
| `Semaphore` | AQS 共享模式 | — | — | 许可获取 | 限流、资源池 |
| `Exchanger` | CAS + 自旋 | — | — | 双方到达 | 两线程数据交换 |
| `CompletableFuture` | Callback + ForkJoinPool | — | — | 异步回调 | 异步编排 |

### 9.2 场景选型指南

| 业务场景 | 推荐方案 | 原因 |
|---------|---------|------|
| 基础生产者-消费者 | `wait/notify` 或 `BlockingQueue` | 原生支持、代码简洁 |
| 多条件精准控制（多生产者/多消费者） | `Lock + Condition` | 多等待队列、精准唤醒 |
| 主线程等待多个子线程完成 | `CountDownLatch` | 封装完善、使用简单 |
| 多线程分批计算、循环复用 | `CyclicBarrier` | 可循环使用、支持屏障任务 |
| 并发限流、连接池管理 | `Semaphore` | 精准控制并发数 |
| 两线程数据交换 | `Exchanger` | 专门用于双线程数据配对 |
| 异步任务编排、链式调用 | `CompletableFuture` | 声明式编程、丰富组合能力 |
| 灵活阻塞/唤醒单个线程 | `LockSupport.park/unpark` | 不依赖锁、许可证模型 |

> 🎯 **选型原则**：简单场景用基础方案，复杂场景用高级工具，避免过度设计。优先使用 `BlockingQueue` 等封装好的工具类，减少手动实现等待-唤醒逻辑。

## 10. 面试高频考点

### Q1：wait() 和 sleep() 的区别？

| 对比维度 | wait() | sleep() |
|---------|-------|--------|
| 所属类 | `Object` | `Thread` |
| 是否释放锁 | **是**（释放锁并进入等待队列） | **否**（不释放锁，持有锁休眠） |
| 调用条件 | 必须在 `synchronized` 块内 | 任意位置 |
| 唤醒方式 | `notify()`/`notifyAll()`/超时/中断 | 时间到/中断 |
| 方法性质 | 实例方法 | 静态方法 |

### Q2：为什么 wait() 必须在 synchronized 块中调用？

这是**语义和实现双重**要求：
- **语义上**：`wait()` 的目的是在持有锁的前提下释放锁并等待，必须在同步环境中保证操作的原子性
- **实现上**：`wait()` 需要操作对象的 Monitor 等待集，而等待集的管理依赖锁的持有状态；若不在同步块中调用，无法确定在哪个对象上等待，且存在竞态条件（检查条件 → 等待之间被其他线程修改）

### Q3：notify() 和 notifyAll() 怎么选？

- **优先使用 `notifyAll()`**：虽然开销略大，但更安全，不会因唤醒同类线程导致"信号丢失"
- 使用 `notify()` 的场景：所有等待线程执行同一逻辑（如同一种条件的消费者），且能确保不会丢失信号
- **Condition 的 `signal()` 则相对安全**：因为每个 Condition 队列中只有同类线程

### Q4：虚假唤醒产生的原因及解决办法？

**原因**：JVM 平台底层实现、`notifyAll()` 唤醒全部线程导致部分线程条件不满足、操作系统信号传递。

**解决**：**始终使用 `while` 循环检查等待条件**，这是 JDK 官方规范的强制要求：

```java
// 正确 ✅
synchronized (lock) {
    while (!condition) { wait(); }
    // 业务逻辑
}

// 错误 ❌
synchronized (lock) {
    if (!condition) { wait(); }
    // 虚假唤醒后条件可能不满足
}
```

### Q5：LockSupport.park/unpark 的优势是什么？

1. **不需要同步代码块**：不依赖 `synchronized` 或锁
2. **许可证模型**：先 `unpark` 再 `park` 不会阻塞，不会丢失信号
3. **精准唤醒**：直接唤醒指定线程，比 `notify()` 和 `notifyAll()` 更精确
4. **响应中断**：`park()` 响应中断但不抛异常，通过中断状态判断

### Q6：Lock + Condition 相比 synchronized + wait/notify 的优势？

| 优势 | 说明 |
|------|------|
| 多等待队列 | 每个 Condition 独立等待队列，精准唤醒相关线程 |
| 可中断锁 | `lockInterruptibly()` 支持中断等待 |
| 超时获取锁 | `tryLock(long, TimeUnit)` 避免永久阻塞 |
| 公平性选择 | 支持公平/非公平锁 |

### Q7：join() 的底层原理是什么？

`join()` 底层调用 `wait(0)` 让当前线程在目标线程对象上等待；目标线程终止时，JVM 在 `exit()` 方法中调用 `notifyAll()` 唤醒等待线程。本质上是 `wait/notify` 机制的应用。

### Q8：如何实现精准唤醒？

使用 `Lock + 多个 Condition`：为每个需要独立唤醒的条件创建一个 `Condition` 对象，调用对应 `Condition` 的 `signal()` 只唤醒该条件队列中的线程：

```java
Lock lock = new ReentrantLock();
Condition producerCond = lock.newCondition(); // 生产者条件
Condition consumerCond = lock.newCondition(); // 消费者条件

// 消费者消费后：只唤醒生产者
producerCond.signal();
// 生产者生产后：只唤醒消费者
consumerCond.signal();
```

> 💡 **Condition.signal() 的安全使用**：Condition 的等待队列是隔离的，`signal()` 只会唤醒同类线程，不会像 `notify()` 那样唤醒所有线程，因此使用 `signal()` 比 `notify()` 安全得多。
