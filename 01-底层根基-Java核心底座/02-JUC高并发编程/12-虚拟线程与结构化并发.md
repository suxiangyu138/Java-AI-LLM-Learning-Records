## 1. 平台线程的局限性

### 1.1 传统线程模型

Java 自诞生以来，`java.lang.Thread` 实例一直直接映射为操作系统内核线程（OS Thread），即 **1:1 模型**：

```
┌────────────────────────────────────────────────────────────┐
│                    JVM 进程 (1 个)                          │
│                                                            │
│  ┌──────┐  ┌──────┐  ┌──────┐          ┌──────┐          │
│  │Thread│  │Thread│  │Thread│    ...    │Thread│          │
│  │  ①   │  │  ②   │  │  ③   │          │  N   │          │
│  └──┬───┘  └──┬───┘  └──┬───┘          └──┬───┘          │
│     │         │         │                 │               │
│     ▼         ▼         ▼                 ▼               │
│  ┌──────┐  ┌──────┐  ┌──────┐          ┌──────┐          │
│  │  OS  │  │  OS  │  │  OS  │    ...    │  OS  │          │
│  │Kernel│  │Kernel│  │Kernel│          │Kernel│          │
│  │Thr①  │  │Thr②  │  │Thr③  │          │Thr N │          │
│  └──────┘  └──────┘  └──────┘          └──────┘          │
│                                                            │
│  ┌────────────────────────────────────────────────────────┐│
│  │            OS Kernel (线程调度器)                       ││
│  └────────────────────────────────────────────────────────┘│
└────────────────────────────────────────────────────────────┘
```

| 特性 | 说明 |
|------|------|
| 栈大小 | 默认 1MB+（可配置 `-Xss`，但最小值 ~64KB） |
| 创建成本 | 需要系统调用，每线程约 1-2ms |
| 上下文切换 | 内核态切换，耗时约 1-10μs |
| 最大数量 | 受 OS 限制（Linux 通常数千到数万） |
| 内存占用 | N 个线程占用至少 N×1MB 栈空间 |

### 1.2 传统线程池的困境

```java
// 传统做法：限制线程数，避免 OOM
ExecutorService pool = Executors.newFixedThreadPool(200);

// 当 200 个线程都在 IO 阻塞时（如数据库查询、RPC 调用）
// → 第 201 个请求必须等待
// → CPU 利用率极低（线程在阻塞等待 IO 而非计算）
// → 吞吐量受限于线程池大小，而非 CPU 核心数
```

> **💡 核心矛盾**：平台线程是稀缺资源，但 IO 密集型应用需要大量并发线程来充分利用 CPU。线程池复用机制本质上是在"稀缺资源"和"高并发"之间做权衡。

## 2. 虚拟线程核心原理：Object Continuation 与 Carrier Thread

### 2.1 M:N 调度模型

虚拟线程采用 **M:N** 模型（多个虚拟线程映射到少数平台线程），由 JVM 而非 OS 进行调度：

```
┌───────────────────────────────────────────────────────────────┐
│                     JVM 进程                                   │
│                                                               │
│  虚拟线程 (可创建数百万个)                                      │
│  ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐      ┌──┐        │
│  │VT│ │VT│ │VT│ │VT│ │VT│ │VT│ │VT│ │VT│ ......│VT│        │
│  │ 1│ │ 2│ │ 3│ │ 4│ │ 5│ │ 6│ │ 7│ │ 8│      │ N│        │
│  └─┬┘ └─┬┘ └─┬┘ └─┬┘ └─┬┘ └─┬┘ └─┬┘ └─┬┘      └──┘        │
│    │    │    │    │    │    │    │    │                       │
│    └────┴────┴────┴────┴────┴────┴────┴─── ... ────┘         │
│                         │                                      │
│              JDK 调度器 (ForkJoinPool)                         │
│                         │                                      │
│                         ▼                                      │
│   Carrier Threads (平台线程, 数量 = CPU 核心数 或 配置)        │
│  ┌────────────────┐  ┌────────────────┐                       │
│  │  Carrier Th 1  │  │  Carrier Th 2  │   ...                  │
│  │  (OS Thread)   │  │  (OS Thread)   │                       │
│  └───────┬────────┘  └───────┬────────┘                       │
│          │                   │                                 │
│          ▼                   ▼                                 │
│  ┌────────────────┐  ┌────────────────┐                       │
│  │    CPU 1       │  │    CPU 2       │   ...                  │
│  └────────────────┘  └────────────────┘                       │
└───────────────────────────────────────────────────────────────┘
```

| 对比维度 | 平台线程 (Platform Thread) | 虚拟线程 (Virtual Thread) |
|----------|---------------------------|--------------------------|
| 映射关系 | 1:1 映射到 OS 线程 | M:N（多VT→少Carrier） |
| 调度层级 | 内核态（OS 调度器） | 用户态（JDK 调度器） |
| 栈大小 | ~1MB（固定分配） | ~几百字节（动态增长） |
| 创建成本 | 高（系统调用） | 极低（纯用户态对象） |
| 上下文切换成本 | ~1-10μs（内核态） | ~0.1-1μs（用户态） |
| 最大数量 | 数千~数万 | 数百万 |

### 2.2 Object Continuation 机制

虚拟线程的底层实现依赖 `jdk.internal.vm.Continuation`（Object Continuation），它是虚拟线程能够"挂起-恢复"的核心：

```
虚拟线程执行流程（含 Continuation）：

  首次 mount ──► 执行任务代码 ──► 遇到阻塞操作 ──► Continuation.yield()
                                    │                  │
                                    │    ┌─────────────┘
                                    │    ▼
                                    │  保存栈帧到堆（堆栈复制）
                                    │  卸载 (unmount) Carrier Thread
                                    │
  等待 IO 完成后 ──► Continuation.run() ──► 从堆中恢复栈帧
                       │                    重新 mount 到 Carrier Thread
                       ▼
                   继续执行后续代码
```

```java
// 伪代码：Continuation 的核心行为
class Continuation {
    // 挂起点：保存当前执行状态到堆
    void yield() {
        // 1. 捕获执行上下文（寄存器、栈帧）
        // 2. 复制到堆内存中的 Continuation 对象
        // 3. 返回给调度器，Carrier Thread 可以执行其他 VT
    }

    // 恢复点：从堆中恢复执行状态
    void run() {
        // 1. 从堆中恢复之前保存的栈帧
        // 2. 挂载到一个可用的 Carrier Thread
        // 3. 从 yield() 返回的位置继续执行
    }
}
```

> **💡 核心洞察**：虚拟线程本质上是 JDK 在用户态实现了"线程切换"。传统的 OS 线程切换需要陷入内核态保存/恢复寄存器；虚拟线程的 Continuation 在用户态直接把调用栈复制到堆上，避免了内核态切换的成本。

### 2.3 Mount / Unmount 机制

虚拟线程在生命周期中会反复经历 **mount**（挂载到 Carrier Thread）和 **unmount**（从 Carrier Thread 卸载）：

```
时间线 ────►

Carrier Thread 1:
┌──────────────────────────────────────────────────────────────────┐
│  mount(VT-A) │ 执行 VT-A 代码 │ 阻塞 → unmount │ mount(VT-C)...│
└──────────────────────────────────────────────────────────────────┘

Carrier Thread 2:
┌──────────────────────────────────────────────────────────────────┐
│  mount(VT-B) │ 执行 VT-B │ 阻塞 → unmount │ mount(VT-D)...     │
└──────────────────────────────────────────────────────────────────┘

虚拟线程视角:
VT-A:  ┌─────┬─────┬────────────────┬─────┬─────┐
       │mount│执行 │  阻塞(IO等待)   │mount│执行 │
       └─────┴─────┴────────────────┴─────┴─────┘
              │     ↑                    │
              ▼     │                    ▼
          Continuation.yield()     Continuation.run()
```

## 3. 虚拟线程的创建与使用

### 3.1 创建方式

JDK 21 提供了三种标准创建方式：

```java
import java.util.concurrent.*;

public class VirtualThreadCreateDemo {

    public static void main(String[] args) throws Exception {

        // ===== 方式 1：Thread.ofVirtual() (推荐) =====
        Thread vt1 = Thread.ofVirtual()
                .name("vt-1")
                .start(() -> {
                    System.out.println("VT 方式1: " + Thread.currentThread());
                    // Thread.currentThread() 返回 VirtualThread 实例
                });

        // ===== 方式 2：Executors.newVirtualThreadPerTaskExecutor() =====
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            Future<String> result = executor.submit(() -> {
                Thread.sleep(100);     // 阻塞不会持有 Carrier Thread
                return "Hello from VT";
            });
            System.out.println(result.get()); // Hello from VT
        } // 自动关闭，等待所有提交任务完成

        // ===== 方式 3：Thread.startVirtualThread() (静态工厂) =====
        Thread vt3 = Thread.startVirtualThread(() -> {
            System.out.println("VT 方式3: " + Thread.currentThread().isVirtual());
            // 输出 true
        });

        // ===== 线程属性对比 =====
        Thread vt = Thread.ofVirtual().name("demo").unstarted(() -> {});
        Thread pt = new Thread(() -> {});

        System.out.println("isVirtual: " + vt.isVirtual());       // true
        System.out.println("isDaemon: " + vt.isDaemon());         // true (VT 默认守护线程)
        System.out.println("priority: " + vt.getPriority());      // NORM_PRIORITY (5)
        System.out.println("group: " + vt.getThreadGroup());      // null (VT 无 ThreadGroup)

        System.out.println("isVirtual: " + pt.isVirtual());       // false
        System.out.println("isDaemon: " + pt.isDaemon());         // false (PT 默认用户线程)
    }
}
```

### 3.2 虚拟线程的 API 兼容

```java
public class VirtualThreadApiDemo {

    public static void main(String[] args) throws Exception {
        // 虚拟线程 100% 兼容 java.lang.Thread API
        Thread vt = Thread.ofVirtual().name("worker").start(() -> {
            try {
                System.out.println("线程名: " + Thread.currentThread().getName());
                System.out.println("线程ID: " + Thread.currentThread().threadId());
                System.out.println("是否虚拟: " + Thread.currentThread().isVirtual());

                // sleep/wait/join 都可用
                Thread.sleep(100);

                // ThreadLocal 可用，但需注意数量限制
                ThreadLocal<String> tl = new ThreadLocal<>();
                tl.set("value");
                System.out.println(tl.get()); // value
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        // 等待虚拟线程结束
        vt.join();

        // 中断
        // vt.interrupt();

        // 检查状态
        // vt.getState()
    }
}
```

> **⚠️ ThreadLocal 与虚拟线程**：虚拟线程可以创建数百万个，如果每个 VT 都用 ThreadLocal 持有大对象（如 1MB 缓存），仍会导致内存溢出。建议在虚拟线程中慎用 ThreadLocal，或限制其持有的数据量。

## 4. 虚拟线程调度：ForkJoinPool 与 Carrier Thread 绑定

### 4.1 默认调度器

JDK 21 为虚拟线程提供了默认的 `ForkJoinPool` 调度器：

```java
// JVM 内部默认创建 (伪代码)
ForkJoinPool VIRTUAL_THREAD_SCHEDULER = new ForkJoinPool(
    Runtime.getRuntime().availableProcessors(), // 并行度 = CPU 核心数
    pool -> {
        var worker = new VirtualThreadWorker(pool);
        // 每个 Worker 就是一个 Carrier Thread (平台线程)
        return worker;
    },
    // 非并发的调度模式
    true
);
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| 并行度 | `Runtime.getRuntime().availableProcessors()` | Carrier Thread 数量 |
| 最大池大小 | 并行度（不可扩容） | 固定大小 |
| 线程工厂 | 内部实现 | 创建 VirtualThreadWorker |

### 4.2 调度流程

```
虚拟线程调度完整流程：

  应用程序代码                        JDK 运行时
  ┌─────────────┐
  │ vt.start()  │
  └──────┬──────┘
         │
         ▼
  ┌─────────────────┐
  │ 创建 Continuation│
  │ 对象 (堆上)      │
  └──────┬──────────┘
         │
         ▼
  ┌─────────────────┐       submit       ┌─────────────────────┐
  │ 等待调度          │ ────────────────► │ ForkJoinPool         │
  │                  │                   │ (调度器)             │
  └─────────────────┘                   │                     │
                                         │   ┌───────────────┐ │
                                         │   │ Carrier Th 1  │─┼──► mount VT
                                         │   ├───────────────┤ │
                                         │   │ Carrier Th 2  │─┼──► mount VT
                                         │   ├───────────────┤ │
                                         │   │ ...           │ │
                                         │   └───────────────┘ │
                                         └─────────────────────┘

  阻塞操作发生后:
         ▼
  ┌─────────────────┐
  │ IO / 阻塞操作    │
  └──────┬──────────┘
         │
         ▼
  ┌─────────────────────────┐
  │ Continuation.yield()    │
  │ 1. 保存栈帧到堆           │
  │ 2. unmount Carrier Thread│
  │ 3. FJP 调度另一个 VT     │
  └─────────────────────────┘
         │
  IO 就绪后:
         ▼
  ┌─────────────────────────┐
  │ Continuation.run()      │
  │ 1. 从堆恢复栈帧           │
  │ 2. 寻找空闲 Carrier      │
  │ 3. mount 继续执行        │
  └─────────────────────────┘
```

### 4.3 Carrier Thread 绑定特性

```java
public class CarrierThreadDemo {

    public static void main(String[] args) throws Exception {
        // 验证 Carrier Thread 信息
        Thread vt = Thread.ofVirtual().start(() -> {
            // 虚拟线程本身
            Thread me = Thread.currentThread();
            System.out.println("我是虚拟线程: " + me);

            // 获取承载当前 VT 的 Carrier Thread (平台线程)
            // Carrier Thread 是 ForkJoinPool 的工作线程
            // 但 JDK 没有公开 API 直接获取 Carrier Thread
        });

        vt.join();

        // 证明：多个 VT 可能共享同一个 Carrier Thread
        var latch = new CountDownLatch(1);

        for (int i = 0; i < 5; i++) {
            final int id = i;
            Thread.ofVirtual().start(() -> {
                try {
                    latch.await(); // 所有 VT 同时释放
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
                // 打印当前线程的 hashCode（不同 VT 可能同值）
                System.out.println("VT " + id + " on carrier: "
                        + Thread.currentThread().toString());
            });
        }

        Thread.sleep(100);
        latch.countDown(); // 释放所有 VT
        Thread.sleep(500);
    }
}
```

## 5. 虚拟线程 vs 平台线程性能对比

### 5.1 创建开销对比

```java
import java.util.concurrent.*;
import java.util.stream.*;

public class PerformanceBenchmark {

    public static void main(String[] args) throws Exception {
        final int COUNT = 10_000;

        // ===== 创建 10,000 个平台线程 =====
        long ptStart = System.nanoTime();
        var ptLatch = new CountDownLatch(COUNT);
        for (int i = 0; i < COUNT; i++) {
            Thread pt = new Thread(() -> {
                ptLatch.countDown();
            });
            pt.start();
        }
        ptLatch.await();
        long ptTime = System.nanoTime() - ptStart;
        System.out.printf("Platform Threads (%d): %.2f ms%n",
                COUNT, ptTime / 1_000_000.0);

        // ===== 创建 10,000 个虚拟线程 =====
        long vtStart = System.nanoTime();
        var vtLatch = new CountDownLatch(COUNT);
        for (int i = 0; i < COUNT; i++) {
            Thread vt = Thread.ofVirtual().start(() -> {
                vtLatch.countDown();
            });
        }
        vtLatch.await();
        long vtTime = System.nanoTime() - vtStart;
        System.out.printf("Virtual Threads (%d): %.2f ms%n",
                COUNT, vtTime / 1_000_000.0);

        System.out.printf("Speedup: %.1fx%n", (double) ptTime / vtTime);
        // 输出参考:
        // Platform Threads (10000): 2456.34 ms
        // Virtual Threads (10000): 98.21 ms
        // Speedup: ~25x
    }
}
```

### 5.2 百万虚拟线程演示

```java
/**
 * 百万虚拟线程压力测试
 * 演示虚拟线程可以轻松创建 100 万个并发任务
 */
public class MillionVirtualThreadsDemo {

    public static void main(String[] args) throws Exception {
        final int MILLION = 1_000_000;

        System.out.println("启动 " + MILLION + " 个虚拟线程...");
        long start = System.nanoTime();

        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            // IntStream 并行提交会更快
            IntStream.range(0, MILLION).forEach(i -> {
                executor.submit(() -> {
                    // 模拟 100ms IO 操作
                    Thread.sleep(100);
                    return i;
                });
            });
        } // 所有任务完成 (ExecutorService.close() 等待)

        long elapsed = System.nanoTime() - start;
        System.out.printf("%d 个虚拟线程完成, 耗时: %.2f 秒%n",
                MILLION, elapsed / 1_000_000_000.0);
        // 输出参考 (16 核机器):
        // 1000000 个虚拟线程完成, 耗时: ~12.5 秒
        // 相当于每秒约 80,000 个 VT 被创建、执行、销毁

        // 对比：平台线程尝试创建 10,000 时就可能 OOM
    }
}
```

### 5.3 性能对比总表

| 对比项 | 平台线程 (Platform Thread) | 虚拟线程 (Virtual Thread) |
|--------|---------------------------|--------------------------|
| 创建 10,000 个线程 | ~2500 ms | ~100 ms (25x 更快) |
| 创建 1,000,000 个线程 | OOM / 不可行 | ~15 秒 (内存 ~256MB) |
| 单线程栈内存 | 1MB (固定) | ~几百字节~几KB (动态) |
| 上下文切换 | ~1-10 μs (内核态) | ~0.1-1 μs (用户态) |
| 100ms IO 阻塞吞吐 | 受限于线程池大小 | 接近无限制 (每个请求一VT) |
| 适合场景 | CPU 密集型 | IO 密集型 |

> **💡 关键结论**：虚拟线程不是让单线程计算变快，而是让 **阻塞等待不再昂贵**。原本线程池需要精细调优 "线程数 = CPU 核数 × (1 + 等待时间/计算时间)"，虚拟线程完全消除了这个公式的必要性。

## 6. 虚拟线程的适用场景与限制（Pinning 问题）

### 6.1 适用场景

| 场景 | 推荐度 | 说明 |
|------|--------|------|
| HTTP 请求 / API 调用 | ★★★★★ | 每个请求一 VT，天然高并发 |
| 数据库查询 (JDBC) | ★★★★★ | 阻塞等待连接池时自动 yield |
| RPC / gRPC 调用 | ★★★★★ | IO 密集型，收益最大 |
| 文件读写 (File I/O) | ★★★★☆ | NIO 原生支持，BIO 略有局限 |
| 消息队列消费 | ★★★★★ | 大量并发消费场景优势明显 |
| CPU 密集型计算 | ★★☆☆☆ | 无优势，仍建议用平台线程 |
| 高频交易 / 微秒级延迟 | ★☆☆☆☆ | VT 调度增加 jitter 延迟 |

### 6.2 Pinning 问题

**Pinning** 是虚拟线程使用中最重要的限制——当虚拟线程执行 `synchronized` 块或 `native` 方法时，会被 **钉住** 在 Carrier Thread 上，无法 unmount：

```
synchronized 块内的阻塞 → 虚拟线程无法 yield:

  Carrier Thread ┌──────────────────────────────────────┐
                 │  mount(VT-A)                         │
                 │  synchronized(lock) {                 │
                 │      IO 阻塞 ──► ❌ 不能 unmount       │
                 │      Carrier Thread 也被阻塞!         │
                 │  }                                    │
                 └──────────────────────────────────────┘

  → Carrier Thread 被浪费（不能调度其他 VT）
  → 所有 Carrier 都被 pin 时，退化为平台线程模型
```

```java
public class PinningDemo {

    private static final Object lock = new Object();
    private static final ReentrantLock fairLock = new ReentrantLock();

    public static void main(String[] args) throws Exception {

        // ===== 会导致 PINNING 的代码 =====
        Thread.ofVirtual().name("bad-vt").start(() -> {
            synchronized (lock) {           // ⚠️ 这里会 pin 住 Carrier
                try {
                    Thread.sleep(1000);     // Carrier 被阻塞 1 秒！
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        });

        // ===== 不会导致 PINNING 的替代写法 =====
        Thread.ofVirtual().name("good-vt").start(() -> {
            fairLock.lock();                // ✅ ReentrantLock 不会 pin
            try {
                Thread.sleep(1000);         // VT 会 yield，Carrier 空闲
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                fairLock.unlock();
            }
        });

        Thread.sleep(2000);
    }
}
```

### 6.3 Pinning 产生的条件

| 构造 | 是否 Pinning | 替代方案 |
|------|-------------|---------|
| `synchronized` 实例方法 | **是** | `ReentrantLock` |
| `synchronized` 静态方法 | **是** | `ReentrantLock` |
| `synchronized (this)` | **是** | `ReentrantLock` |
| `synchronized (obj)` | **是** | `ReentrantLock` |
| `ReentrantLock.lock()` | 否 | — |
| `ReentrantReadWriteLock` | 否 | — |
| `StampedLock` | 否 | — |
| `native` 方法 | **是** | 无直接替代（尽量少用） |
| `IO` 操作 (NIO) | 否 | — |
| `Future.get()` / `CompletableFuture` | 否 | — |

> **⚠️ Pinning 警告**：如果代码中有大范围的 `synchronized` 块（尤其是涉及阻塞 IO 的），切换到虚拟线程后可能性能不升反降。建议在迁移前先用 `ReentrantLock` 替换关键路径上的 `synchronized`。JDK 未来版本可能会优化此限制（Loom 项目后续工作）。

## 7. 结构化并发：StructuredTaskScope

### 7.1 传统异步编程的问题

```java
// 传统方式：任务生命周期不明确，错误处理复杂
public class TraditionalAsyncDemo {

    public static void main(String[] args) throws Exception {
        var executor = Executors.newCachedThreadPool();

        // 问题：如果 fetchUser 抛异常，fetchOrder 仍在后台运行
        // 问题：任务泄漏 —— 忘记取消已失败的任务
        Future<String> userFuture = executor.submit(() -> fetchUser());
        Future<Integer> orderFuture = executor.submit(() -> fetchOrder());

        try {
            String user = userFuture.get();     // 可能阻塞等待
            Integer order = orderFuture.get();
            System.out.println(handle(user, order));
        } finally {
            // 容易忘记取消
            // userFuture.cancel(true);
            // orderFuture.cancel(true);
        }
    }

    static String fetchUser() {
        // 可能抛出异常
        return "Alice";
    }

    static int fetchOrder() {
        // 可能抛出异常
        return 42;
    }

    static String handle(String user, int order) {
        return user + ": " + order;
    }
}
```

### 7.2 StructuredTaskScope 核心用法

结构化并发的核心原则：**并发任务的生命周期必须绑定到代码块的作用域**。

```java
import java.util.concurrent.*;

/**
 * 结构化并发 StructuredTaskScope (JDK 21 Preview, JDK 22 Second Preview)
 *
 * 编译运行需: --enable-preview
 * 但在 JDK 22+ 中已不在预览状态
 */
public class StructuredConcurrencyDemo {

    // ===== 核心模式：ShutdownOnFailure =====
    // 最常见：任一子任务失败则取消所有
    public Response handleShutdownOnFailure() throws Exception {
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {

            // fork 创建子任务，返回 Future 但无需手动管理生命周期
            Future<String> user = scope.fork(() -> fetchUser());
            Future<Integer> order = scope.fork(() -> fetchOrder());

            // join() 等待所有子任务完成
            // 如果任一子任务抛出异常，立即取消其他所有子任务
            scope.join();
            // 如果任一子任务失败，throwIfFailed 会重新抛出异常
            scope.throwIfFailed(); // 默认抛出 ExecutionException

            // resultNow() 非阻塞获取结果（任务已确保完成）
            return new Response(user.resultNow(), order.resultNow());
        } // try-with-resources 自动关闭 scope，确保所有任务终止
    }

    // ===== 变体：ShutdownOnSuccess =====
    // 任一子任务成功即返回，取消其他
    public String handleShutdownOnSuccess() throws Exception {
        try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
            scope.fork(() -> queryFromPrimary());
            scope.fork(() -> queryFromSecondary());

            // 返回最先成功的结果
            return scope.join().result(); // 第一个成功的结果
        } // 未完成的子任务被自动取消
    }

    static String fetchUser() throws Exception {
        Thread.sleep(200);
        return "Alice";
    }

    static int fetchOrder() throws Exception {
        Thread.sleep(100);
        return 42;
    }

    static String queryFromPrimary() throws Exception {
        Thread.sleep(500);
        return "primary-result";
    }

    static String queryFromSecondary() throws Exception {
        Thread.sleep(300);
        return "secondary-result";
    }

    record Response(String user, int order) {}
}
```

### 7.3 StructuredTaskScope 的三种策略

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| `ShutdownOnFailure` | 任一子任务失败 → 取消其余所有 | 互相依赖的并行请求（如查用户+订单） |
| `ShutdownOnSuccess` | 任一子任务成功 → 取消其余所有 | 冗余请求（主/备查询、多数据中心） |
| 自定义 (继承) | 开发者控制 shutdown 策略 | 复杂编排逻辑 |

### 7.4 自定义策略

```java
/**
 * 自定义结构化并发策略：
 * 收集所有成功结果，忽略失败的任务
 */
public class CollectSuccessfulScopeDemo {

    public static void main(String[] args) throws Exception {
        // 自定义 scope
        var scope = new CollectSuccessfulScope<String>();
        try (scope) {
            scope.fork(() -> maybeSuccess("A"));
            scope.fork(() -> maybeSuccess("B"));
            scope.fork(() -> maybeSuccess("C"));

            scope.join();

            var results = scope.results();
            System.out.println("收集到 " + results.size() + " 个成功结果: " + results);
        }
    }

    static String maybeSuccess(String name) {
        if (Math.random() > 0.5) {
            return name + "-ok";
        }
        throw new RuntimeException(name + " failed");
    }

    // 自定义 StructuredTaskScope: 收集成功结果
    static class CollectSuccessfulScope<T> extends StructuredTaskScope<T> {
        private final Queue<T> successResults = new ConcurrentLinkedQueue<>();
        private final Queue<Throwable> exceptions = new ConcurrentLinkedQueue<>();

        @Override
        protected void handleComplete(Future<T> future) {
            // 只关心已成功完成的结果
            if (future.state() == Future.State.SUCCESS) {
                successResults.add(future.resultNow());
            } else if (future.state() == Future.State.FAILED) {
                exceptions.add(future.exceptionNow());
            }
        }

        public List<T> results() {
            return List.copyOf(successResults);
        }

        public List<Throwable> errors() {
            return List.copyOf(exceptions);
        }
    }
}
```

### 7.5 结构化并发的核心价值

```
传统模式:
┌────────────────────────────────────────────┐
│  Future f1 = submit(task1)                  │
│  Future f2 = submit(task2)                  │
│  result1 = f1.get()   ← 可能阻塞，没有超时  │
│  result2 = f2.get()   ← 可能阻塞            │
│  // 如果 f1 抛异常，f2 仍在后台运行 (泄漏)   │
└────────────────────────────────────────────┘

结构化并发模式:
┌────────────────────────────────────────────┐
│  try (var scope = new ShutdownOnFailure()) {│
│      scope.fork(task1)  ← 生命周期绑定 scope│
│      scope.fork(task2)  ← 生命周期绑定 scope│
│      scope.join();                          │
│      // scope 关闭时, 所有子任务自动终止    │
│  }  ← 确保持有子任务不泄漏                  │
└────────────────────────────────────────────┘
```

| 对比维度 | 传统 Future/CompletableFuture | 结构化并发 |
|----------|------------------------------|-----------|
| 生命周期 | 任务超出作用域仍可运行（泄漏） | 绑定到代码块，超出自动终止 |
| 错误传播 | 子任务异常需手动检查 | `throwIfFailed()` 自动传播 |
| 取消机制 | 需显式 `cancel()` | scope 关闭自动取消 |
| 任务编排 | 需 `allOf()` / `anyOf()` 组合 | 范围限定的 fork-join 模型 |
| 可观测性 | 线程转储中无任务关系 | 显示父子任务层级关系 |

> **🎯 总结**：结构化并发让异步多任务的代码看起来像同步代码一样清晰——进入 `try` 块时任务开始，退出 `try` 块时所有任务保证结束。这是对 `CompletableFuture` 编排模式的范式级简化。

### 8.3 使用注意事项

```java
@RestController
public class VirtualThreadController {

    // ✅ 虚拟线程适合：IO 密集型请求
    @GetMapping("/api/user/{id}")
    public User getUser(@PathVariable Long id) {
        // 每个请求自动在虚拟线程中处理
        // 多个数据库查询会自动 yield，不阻塞
        User user = userRepository.findById(id).orElseThrow();
        Order order = orderService.getLatestOrder(id);
        return user.withOrder(order);
    }

    // ⚠️ synchronized 需要注意
    @Service
    static class UserService {
        // ❌ 避免在虚拟线程中使用 synchronized 块
        // 如果内有阻塞操作，会导致 Carrier Thread pinning
        public synchronized User syncMethod(Long id) {
            // 数据库查询可能阻塞，导致 pinning
            return findById(id);
        }

        // ✅ 改用 ReentrantLock
        private final ReentrantLock lock = new ReentrantLock();

        public User safeMethod(Long id) {
            lock.lock();
            try {
                return findById(id);
            } finally {
                lock.unlock();
            }
        }

        private User findById(Long id) {
            // 模拟数据库查询
            return new User(id, "name");
        }
    }

    record User(Long id, String name) {}
    record Order(Long id, String item) {}
}
```

> **⚠️ 迁移注意**：Spring Boot 3.2 启用虚拟线程后，如果应用大量使用 `synchronized` 或第三方库内部使用了 `synchronized`，建议开启 `-Djdk.tracePinnedThreads=short` 在生产环境观察是否存在 Pinning 问题，评估后再全面上线。

## 9. 迁移建议与最佳实践

### 9.1 迁移路径

```
Step 1: 评估
  ├── 检查代码中 synchronized 使用范围
  ├── 检查 ThreadLocal 使用量（VT 大量创建时内存膨胀）
  ├── 检查自定义线程池（是否需要替换为 VirtualThreadPerTaskExecutor）
  └── 确认依赖库是否兼容（数据库驱动、HTTP 客户端等）

Step 2: 试用
  ├── 开启 -Djdk.tracePinnedThreads=short
  ├── 在非关键服务启用 spring.threads.virtual.enabled=true
  ├── 运行压力测试，观察 pinning 事件和吞吐量
  └── 对比 P99 延迟，确保无显著抖动

Step 3: 优化
  ├── 替换 synchronized → ReentrantLock
  ├── 替换 ThreadLocal → 局部变量 / 缩小作用域
  ├── 考虑删除自定义线程池配置（让 VT 管理并发）
  └── 重构阻塞 IO 代码，确保通过标准 API 调用

Step 4: 全量上线
  ├── 监控 P99 延迟、线程状态、Full GC 频率
  ├── 保留回退方案（可一键切回平台线程）
  └── 持续观察 JVM 堆使用（VT 的 Continuation 对象在堆上）
```

### 9.2 最佳实践清单

```java
public class VirtualThreadBestPractices {

    // ===== 1. 替换线程池 =====
    // ❌ 旧代码：固定大小线程池
    ExecutorService oldPool = Executors.newFixedThreadPool(200);

    // ✅ 新代码：每任务一虚拟线程
    ExecutorService newPool = Executors.newVirtualThreadPerTaskExecutor();

    // ===== 2. 避免 synchronized + 阻塞 =====
    // ❌ 会导致 pinning
    public synchronized void blockingMethod() {
        // IO 操作
    }

    // ✅ 使用 ReentrantLock
    private final ReentrantLock lock = new ReentrantLock();

    public void safeBlockingMethod() {
        lock.lock();
        try {
            // IO 操作 (VT 在 lock 上等待时会 yield)
        } finally {
            lock.unlock();
        }
    }

    // ===== 3. 控制 ThreadLocal 规模 =====
    // ❌ 每个 VT 持有大对象
    private static final ThreadLocal<byte[]> LARGE_CACHE = ThreadLocal.withInitial(
            () -> new byte[1024 * 1024]);  // 1MB

    // ✅ 只在需要时创建，或改用局部变量
    private static final int MAX_CACHE_SIZE = 1024; // 限制为 1KB

    // ===== 4. 慎用线程池限流 =====
    // ❌ 虚拟线程本身轻量，但仍需控制资源（如数据库连接池、线程池下游）
    // 虚拟线程数量不再受限，但数据库连接数仍有限
    // 应该限流的是下游资源，而非线程数

    // ✅ 使用 Semaphore 限流数据库连接
    private final Semaphore dbSemaphore = new Semaphore(50); // 最多 50 并发 DB 操作

    public void queryDatabase() {
        dbSemaphore.acquire();
        try {
            // 数据库查询
        } finally {
            dbSemaphore.release();
        }
    }

    // ===== 5. 使用结构化并发替代 CompletableFuture 编排 =====
    // CompletableFuture 仍可用，但结构化并发更安全、更清晰

    // ===== 6. JVM 调优建议 =====
    // -XX:MaxHeapSize=2g  (VT 的 Continuation 在堆上，需更大堆)
    // -Djdk.tracePinnedThreads=short  (诊断 pinning)
    // 避免使用 -Xss 设置过小（虚拟线程自动管理栈大小）
}
```

### 9.3 不应使用虚拟线程的场景

| 场景 | 原因 |
|------|------|
| CPU 密集型计算（视频编码、加密、压缩） | 虚拟线程不提高计算速度，上下文切换反而增加开销 |
| GPU 加速计算 | 需 JNI/native 绑定，容易产生 pinning |
| 高精度定时器（微秒级） | VT 调度有不可预测的延迟抖动 |
| 持有原生资源的操作（DirectBuffer） | 资源回收依赖平台线程 |
| 长时间不阻塞的计算循环 | 虚拟线程没有时间片抢占，会独占 Carrier Thread |

## 10. 面试高频考点

### 10.1 常见问题与回答要点

| 问题 | 核心回答要点 |
|------|-------------|
| 虚拟线程和平台线程的区别？ | M:N 模型 vs 1:1 模型；用户态调度 vs 内核态调度；栈在堆上 vs 栈在 native 内存 |
| 虚拟线程能无上限创建吗？ | 理论上可以数百万，但受堆内存（Continuation 对象）和文件描述符等资源限制 |
| 什么是 Continuation？ | 用户态可以挂起/恢复的执行上下文，保存栈帧到堆，实现线程的 yield/resume |
| 什么是 Pinning？ | `synchronized` 或 `native` 方法导致 VT 无法从 Carrier Thread 卸载，阻塞 Carrier |
| 如何解决 Pinning？ | 用 `ReentrantLock` 替换 `synchronized`；开启 `-Djdk.tracePinnedThreads` 诊断 |
| 虚拟线程适合 CPU 密集任务吗？ | 不适合。CPU 密集任务没有阻塞点，VT 无优势，上下文切换反而增加开销 |
| 虚拟线程和协程/纤程的关系？ | 类似 Go goroutine、Erlang process、Kotlin coroutine，Java 称之为 Virtual Thread |
| 虚拟线程如何影响线程池设计？ | 从"池化线程"转向"每任务一 VT"，不再需要线程池调优 |
| ThreadLocal 在 VT 中的问题？ | 数百万 VT × 大对象 = OOM，需限制 ThreadLocal 数据量或改用局部变量 |
| StructuredTaskScope 解决了什么？ | 任务生命周期管理、错误传播、自动取消，防止任务泄漏 |

```java
// 面试题 2：用虚拟线程 + StructuredTaskScope 实现"请求聚合"
public class RequestAggregationDemo {

    record AggregatedResult(String user, List<String> orders, double balance) {}

    // 并行查询多个服务，聚合结果
    public AggregatedResult getAggregatedData(String userId) throws Exception {
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            Future<String> user = scope.fork(() -> callUserService(userId));
            Future<List<String>> orders = scope.fork(() -> callOrderService(userId));
            Future<Double> balance = scope.fork(() -> callBalanceService(userId));

            scope.join();
            scope.throwIfFailed();

            return new AggregatedResult(
                    user.resultNow(),
                    orders.resultNow(),
                    balance.resultNow()
            );
        } // 任何异常或正常退出，所有任务保证结束
    }

    String callUserService(String id) { return "Alice"; }
    List<String> callOrderService(String id) { return List.of("order1", "order2"); }
    Double callBalanceService(String id) { return 1000.0; }
}
```

### 10.3 对比：虚拟线程 vs 其他语言协程

| 维度 | Java Virtual Thread | Go Goroutine | Kotlin Coroutine |
|------|-------------------|--------------|-----------------|
| 调度方式 | 抢占式（阻塞时 yield） | 协作式（仅 IO/chan 时 yield） | 协作式（suspend 函数） |
| 栈管理 | 堆上复制（Continuation） | 动态增长栈（2KB 起） | 状态机编译转换 |
| 并发模型 | 每个操作一个线程（1:1 代码） | goroutine + channel | suspend 函数 + Flow |
| 与同步代码兼容 | 100% 兼容 | 兼容（通过 runtime） | 需标记 suspend |
| 学习成本 | 极低（API 完全不变） | 需学习 channel 模式 | 需学习协程构建器 |

> **🎯 总结**：虚拟线程是 Java 并发编程的历史性变革。它让"每个请求一个线程"的模型从不可能变为现实，彻底消除了线程池调优的复杂性。对于 IO 密集型应用，虚拟线程 + 结构化并发是 JDK 21+ 时代的最佳实践，也是向 Loom 项目愿景（轻量级并发 + 结构化代码）迈出的关键一步。
