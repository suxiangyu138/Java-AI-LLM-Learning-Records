## 1. 平台线程：1:1 内核线程模型的代价

### 1.1 传统模型回顾

从 JDK 1.0 到 JDK 20，`java.lang.Thread` 始终是**平台线程（platform thread）**：一个 `Thread` 对象背后是一个操作系统线程（内核线程），JVM 与内核以 **1:1** 方式映射。

```text
Java 线程对象 ──→ JVM 内 JavaThread ──→ 内核线程（kthread）──→ CPU 调度
      1                 1                    1
```

这种模型的优点：简单、语义清晰、线程数即并发能力，Java 并发模型与操作系统完全对齐。

### 1.2 三个致命成本

| 成本项 | 具体表现 | 数据参考 |
|-------|---------|---------|
| **内存** | 每个线程预留 ~1MB 原生栈（Linux/macOS 默认 `-Xss1m`），内核线程栈不可伸缩，只能按最坏情况预留 | 1M 个平台线程需要 ~1TB 地址空间，实测小堆下 **~1600 个线程即 OOM** |
| **上下文切换** | 内核态切换：保存/恢复寄存器、TSS、TLB 刷新；实测极端场景线程切换可吃掉 **~80% CPU** | 切换成本约微秒级（相对 JVM 用户态纳秒级） |
| **稀缺性思维** | 线程数是稀缺资源 → 必须用线程池复用 → 池化、排队、拒绝策略、线程饥饿 | 这是所有 Java 并发复杂性的根源之一 |

### 1.3 线程池是"妥协"而非"设计"

因为平台线程昂贵，业界发明了线程池：

- 固定大小线程池（`Executors.newFixedThreadPool(n)`）→ 池满时任务排队 → 吞吐受限；
- 需要**根据 I/O 延迟估算线程数**（经验公式：`线程数 = 核数 × (1 + 等待时间/计算时间)`）→ 估算错就性能差；
- 每个线程被"一个连接占用一个线程"（thread-per-connection）模式绑死 → 大量线程在阻塞等 I/O，CPU 却闲着。

> 🎯 **核心要点**：线程池是"用复杂的管理逻辑，为昂贵的资源做复用"——它治标不治本。如果线程本身足够便宜，池化就是多余的复杂度。

## 2. 从 1:1 到 M:N：两种并发模型

| 维度 | 1:1 模型（平台线程） | M:N 模型（虚拟线程） |
|------|---------------------|---------------------|
| 线程与内核线程映射 | 1 : 1 | M : N（M 个虚拟线程，N 个内核线程） |
| 调度者 | 操作系统内核 | JVM（用户态调度） |
| 上下文切换 | 内核态，昂贵 | 用户态，几乎免费 |
| 栈 | 原生栈 ~1MB，不可伸缩 | 堆上栈，按需增长，可被 GC |
| 阻塞语义 | 阻塞内核线程 | 阻塞只挂起虚拟线程，释放内核线程 |
| 线程数上限 | 数千（受内存/内核限制） | 数百万（受堆内存限制） |

虚拟线程的底层思想并不新：**用户态线程**（user-level threads）在操作系统教材里存在了半个世纪，Go 的 Goroutine（GMP 模型）、Erlang 的 Process、Lua 的协程都是同族。Java 的独特之处在于：

- **完整保留 `Thread` 编程模型**——不引入新概念、新语法、新框架，所有现有并发代码（`synchronized`、锁、阻塞 I/O）对开发者透明；
- **集成到 JVM 与 JDK**——调度器、阻塞点拦截、线程转储、调试器、JFR 全部原生支持；
- **Java 虚拟机规范层面统一**——而不是像 Kotlin 协程那样需要编译器变换与运行时库配合。

> 💡 **理解视角**：虚拟线程不是"新线程"，而是"线程的用户态实现"。对应用开发者，它看起来、用起来和 `Thread` 一模一样；对 JVM，它只是堆上的一个对象加上一段可挂起的执行状态。

## 3. 虚拟线程的本质定义

引用 JEP 444 的权威定义，虚拟线程有三个核心特征：

### 3.1 它是 `java.lang.Thread` 的子类

```java
public class Thread implements Runnable {
    // ...
    static Thread newVirtualThread(Executor scheduler, String name,
                                   int characteristics, Runnable task);
}
```

- `Thread.ofVirtual()` 返回的虚拟线程与 `Thread.ofPlatform()` 返回的平台线程**同一个类层级**；
- 现有 API（`Thread.currentThread()`、`Thread.sleep()`、`join()`、`interrupt()`、`UncaughtExceptionHandler`）**全部无需修改**。

### 3.2 由 JVM 调度，而非 OS 调度

- 虚拟线程被提交到**调度器（scheduler）**，默认是 `ForkJoinPool`（详见 02 章）；
- 真正运行虚拟线程代码的 OS 线程称为**载入线程（carrier thread）**；
- 虚拟线程阻塞时**自动卸载（unmount）**，把载入线程让给其他虚拟线程。

### 3.3 阻塞点被 JVM 拦截

虚拟线程只有在"阻塞点"（blocking operation）才会真正挂起。JVM 拦截的阻塞点包括：

```java
// 这些调用会触发虚拟线程卸载，而不是阻塞载入线程
Thread.sleep()                          // 睡眠
Socket.read() / Socket.write()          // 网络 I/O
InputStream.read()                      // 文件/流 I/O
HttpClient.send() / sendAsync()         // HTTP 客户端
LockSupport.park()                      // JUC 锁底层
Object.wait()                           // 监视器等待（JDK 24+ 不再 pin）
BlockingQueue.take()                    // 阻塞队列
FutureTask.get() / CompletableFuture.join()
```

> ⚠️ **边界**：JVM 只拦截它**认识**的阻塞点。非阻塞回调式 API（如 Netty 的 `channel.read()` 回调）、CPU 密集计算、原生代码（JNI）中的阻塞，都不在拦截范围内——前者照常工作，后者可能造成 pinning（见 04 章）。

## 4. JEP 演进史：从预览到转正

虚拟线程是 Project Loom（2007 年立项，早期代号 "Fibers"）的旗舰特性，历时 5 个 JDK 版本才转正：

| JEP | 版本 | 内容 | 阶段 |
|-----|:---:|------|:---:|
| JEP 425 | JDK 19 | Virtual Threads 首次预览 | 预览 |
| JEP 436 | JDK 20 | 第二次预览（栈检查、类初始化期间固定等细节调整） | 预览 |
| JEP 437 | JDK 21 | 第三次预览（JEP 444 发布前最后的调整） | 预览 |
| **JEP 444** | **JDK 21 LTS** | **Virtual Threads 正式转正** | ✅ 最终版 |

JEP 444 转正时的关键决策：

- **synchronized 内阻塞 → pinning**：作为已知限制保留（JVM 无法安全地让持锁虚拟线程卸载），官方建议改用 `ReentrantLock`；
- **`jdk.tracePinnedThreads` 系统属性**：用于打印 pin 线程的栈，辅助诊断；
- **调度器可替换**：`jdk.virtualThreadScheduler` 系统属性可自定义调度器。

这个"带病转正"的决策在 2024-2025 年被验证是正确的：

- 2025-03 JDK 24 通过 **JEP 491** 彻底修复 synchronized pinning（详见 04 章）；
- JDK 21 至今是虚拟线程生产部署最广的 LTS 版本，Spring Boot 3.2+ 可一行配置启用。

> 🎯 **演进节奏启示**：Loom 团队坚持"先转正核心、再补痛点"的节奏——虚拟线程先以完整 API 面世，pinning 修复作为独立 JEP（491）在 3 个版本后交付，避免再一次推迟虚拟线程本身。

## 5. 虚拟线程 vs 平台线程 vs 协程/Goroutine

### 5.1 与平台线程的对比（同线程模型内）

| 维度 | 平台线程 | 虚拟线程 |
|------|---------|---------|
| 每线程元数据 | ~1MB 栈 + 内核资源 | ~200-300 字节 + 堆上栈（按需增长） |
| 创建成本 | 微秒~毫秒级（系统调用） | 纳秒~微秒级（堆分配） |
| 数量上限 | 数千（OOM 前） | 数百万（堆允许） |
| 切换成本 | 内核上下文切换 | JVM 内 Continuation 切换 |
| 是否可池化 | 必须池化 | **禁止池化**（池化反噬内存） |
| 适用任务 | 长期驻留、CPU 密集 | 大量短任务、I/O 密集 |

### 5.2 与 Goroutine 的对比（跨语言）

| 维度 | Java 虚拟线程 | Go Goroutine |
|------|--------------|--------------|
| 模型 | M:N（ForkJoinPool 调度） | M:N（GMP 调度器） |
| 栈 | 堆上分块栈（chunk 链表） | 堆上可增长栈（早期是分段栈，现为复制栈） |
| 阻塞拦截 | JVM 拦截已知阻塞点 | 运行时钩子拦截（netpoll 等） |
| 阻塞式系统调用 | 会 pin（JNI 场景） | 会阻塞线程（特殊处理网络 I/O） |
| 生态适配 | 大量旧库按平台线程假设实现 | 语言层面统一设计 |
| 并发原语 | synchronized/ReentrantLock/信号量 | channel/mutex/waitgroup |

> 💡 **本质差异**：两者内核思想相同，但 Go 从第一天就为 M:N 设计了语言与运行时；Java 是在 25 年历史的线程模型上**叠加**了用户态线程——这决定了 Java 虚拟线程的"兼容优先"路线，也决定了 pinning 这类历史包袱必须逐个用新 JEP 偿还。

## 6. 为什么说虚拟线程是"更简单的异步"

### 6.1 异步编程的复杂度黑洞

传统异步方案（CompletableFuture、响应式流）的核心问题是**代码形态被调度撕裂**：

```java
// 传统响应式：一个业务操作被拆成 5 段回调，错误处理、线程上下文四处散落
fetchUser(userId)
    .thenCompose(user -> fetchOrders(user))
    .thenCompose(orders -> fetchDiscounts(orders))
    .exceptionally(e -> ...);
```

- 调试困难：线程切换后栈信息丢失，异常栈只显示最后一段；
- 心智负担：`thenCompose`/`exceptionally`/`completeOnTimeout` 的组合规则远超同步代码；
- 上下文传播困难：ThreadLocal 在异步链中失效（`thenApplyAsync` 换了线程）。

### 6.2 虚拟线程把"异步"还原为"同步"

```java
// 虚拟线程：1000 个请求 = 1000 个虚拟线程，代码与同步版本完全一致
public OrderData getOrderData(long userId) throws Exception {
    var user = fetchUser(userId);      // 阻塞？不，虚拟线程卸载，载入线程继续服务别人
    var orders = fetchOrders(user);
    var discounts = fetchDiscounts(orders);
    return new OrderData(user, orders, discounts);  // 顺序、直观、可调试
}
```

**虚拟线程的价值不是"快"而是"简"**：

| 传统同步 + 线程池 | 异步编程 | 虚拟线程 |
|------------------|---------|---------|
| 代码简单，但受线程数限制 | 无线程数限制，但代码复杂 | **两者兼得** |
| 吞吐受池大小上限 | 吞吐高，复杂度爆炸 | 吞吐高 + 代码同步化 |

> 🎯 **核心要点**：虚拟线程的核心主张是——阻塞 I/O 的代价不应成为并发模型的负担。把"每个任务一个线程"的简单模型扩展到百万级，就是 Loom 的全部野心。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 平台线程 1:1 内核线程，~1MB 栈 + 内核切换昂贵，线程池是资源稀缺下的妥协产物；
> 2. 虚拟线程是 JVM 调度的用户态线程（M:N），本质是"廉价化后的 `Thread`"，API 完全兼容；
> 3. 它的目标不是替代异步编程的性能，而是用"简单"替代"复杂"，让同步代码获得异步规模。

**思考题**：

1. 虚拟线程的调度器在哪个池子里？载入线程的数量由什么决定？（→ 02）
2. 为什么虚拟线程**不能**被池化？这与平台线程的池化逻辑有什么冲突？（→ 05）
3. 如果一段代码 CPU 密集且从不阻塞，虚拟线程相比平台线程还有优势吗？（→ 08）
