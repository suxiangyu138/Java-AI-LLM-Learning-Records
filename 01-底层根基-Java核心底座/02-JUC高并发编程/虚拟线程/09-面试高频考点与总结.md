## 1. 高频面试题 14 问

### Q1：虚拟线程是什么？解决什么问题？

> 答：虚拟线程是 JVM 调度的轻量级线程（JDK 21 JEP 444 转正），与 OS 线程无 1:1 映射（M:N 模型）。解决平台线程"贵"的问题：~1MB 原生栈 + 内核态切换，导致线程数稀缺、必须池化。虚拟线程栈在堆上（200-300B 元数据 + 分块栈），阻塞自动卸载载入线程，让"一个请求一个线程"模型扩展到百万级。
> 参考：01、02 章

### Q2：虚拟线程和平台线程有什么区别？

> 关键点：① 调度者不同（JVM vs OS）；② 栈不同（堆上分块栈 vs 1MB 原生栈）；③ 切换成本（纳秒级 vs 微秒级）；④ 数量级（百万 vs 数千）；⑤ 可池化（禁止 vs 必须）；⑥ daemon（永远 daemon vs 可设置）；⑦ 优先级（不支持 vs 支持）；⑧ 转储分组（jcmd JSON 分区展示）。
> 参考：01 章 5.1、03 章

### Q3：虚拟线程是怎么调度的？什么是载入线程？

> 答：默认调度器是 ForkJoinPool（parallelism = CPU 核数，maxPoolSize = 256），其工作线程即"载入线程（carrier）"。虚拟线程 mount 到载入线程上执行，阻塞时 unmount 释放载入线程，恢复时重新入队（可能换载入线程）。一个载入线程生命周期内服务成千上万虚拟线程。相关属性：`jdk.virtualThreadScheduler.parallelism/maxPoolSize`。
> 参考：02 章 2/3 节

### Q4：虚拟线程阻塞时发生了什么？为什么切换便宜？

> 答：阻塞点（sleep、锁、队列、I/O）被 JVM 拦截，收敛到 `LockSupport.park()` → Continuation 挂起 → 保存执行状态到堆上 StackChunk → 卸载载入线程；解除时 `unpark()` → 重新提交调度器。全程无系统调用、无内核态切换，因此成本约几百纳秒。I/O 恢复依赖 JDK 内部 Poller（epoll/kqueue）监听到期/就绪后 unpark。
> 参考：02 章 3/5 节

### Q5：什么是 pinning？JDK 24 怎么解决的？

> 答：pinning = 虚拟线程阻塞时无法卸载、钉死载入线程。JDK 21 中 synchronized 内阻塞（sleep/I/O/锁竞争/Object.wait）会 pin，因为监视器所有权记录在物理线程上（LockStack / ObjectMonitor._owner=JavaThread*）。JDK 24（JEP 491）三招解决：① 轻量锁的 LockStack 随 Continuation 迁移到下一个载入线程；② 膨胀锁 _owner 改记虚拟线程 tid；③ 监视器阻塞与 Object.wait 支持卸载。官方基准：并行度 1 的 5000 任务场景从 31.8s → 0.454s。剩余 pin：原生回调、类初始化、符号解析。
> 参考：04 章

### Q6：synchronized 和 ReentrantLock 在虚拟线程时代怎么选？

> 答：JDK 24+ 两者都不 pin，选型回归功能需求：默认 synchronized（简洁、生态兼容）；需要 tryLock/超时/公平/多条件时用 ReentrantLock。JDK 21 环境仍需避免 synchronized 内长阻塞（或升级）。
> 参考：04 章 7 节

### Q7：虚拟线程能替代线程池吗？什么场景不该用？

> 答：能替代"I/O 密集任务的执行器"（`newVirtualThreadPerTaskExecutor()`），不能替代全部线程池。不适用：① CPU 密集任务（无收益 + 载入线程饥饿）；② 依赖池大小限流的场景（需换 Semaphore）；③ 长期驻留/原生资源绑定场景。原则：task-per-thread、禁止池化虚拟线程。
> 参考：05 章

### Q8：为什么不能池化虚拟线程？

> 答：虚拟线程的优势正是"创建便宜 + 用完即弃"：栈在堆上可 GC 回收，池化反而保留大量栈 chunk 与对象、放大内存，还引入排队/复用复杂度。OpenJDK 明确反模式化（JDK 自身移除 ThreadLocal 缓存）。限流用 Semaphore 而非池化。
> 参考：05 章 1/5 节

### Q9：虚拟线程池没有队列，突发流量怎么办？

> 答：`newVirtualThreadPerTaskExecutor()` 无队列无拒绝策略，突发任务会瞬间创建海量虚拟线程 → 堆峰值 + 下游被打爆。方案：Semaphore 限流（acquire 阻塞/ tryAcquire 快速失败），按下游依赖分别限流更精细。
> 参考：05 章 5 节

### Q10：什么是结构化并发？解决什么问题？

> 答：`StructuredTaskScope`（JEP 525，JDK 26 六览预览）把一组子任务纳入父作用域：fork 子任务默认虚拟线程执行；join 返回时所有子任务必已结束；任一失败自动取消其余（fail-fast）；try-with-resources 兜底取消——从结构上消灭线程泄漏、统一错误处理与取消。与 CompletableFuture 选型：同请求内相关子任务用前者，跨模块异步流水线用后者。
> 参考：06 章

### Q11：ScopedValue 和 ThreadLocal 的区别？为什么虚拟线程时代需要它？

> 答：三大区别：① 不可变（绑定一次）vs 可变（任意 set）；② 有界生命周期（run 内自动清理）vs 手动 remove；③ 单副本近局部变量读取速度 vs 每线程 Map。虚拟线程时代 ThreadLocal 内存随线程数线性放大且异步断链，ScopedValue 是官方替代（JEP 506，JDK 25 转正），结构化并发子任务自动继承。
> 参考：07 章

### Q12：虚拟线程与 Go 的 Goroutine 有什么区别？

> 答：同：都是 M:N 用户态线程、堆上栈、运行时调度。异：① Java 是在 25 年 Thread 模型上叠加（API 兼容优先，历史包袱逐个用 JEP 偿还如 JEP 491）；Go 语言层面统一设计；② 阻塞点拦截：Java 拦截已知阻塞点（JNI/native 回调可能 pin），Go 通过运行时钩子（netpoll）；③ Java 的生态适配靠库作者升级，Go 生态从零就是 M:N 设计。
> 参考：01 章 5.2

### Q13：虚拟线程的性能坑有哪些？怎么监控？

> 答：三大坑：① CPU 密集任务饥饿（协作式调度无抢占）→ 桥接独立平台线程池；② 无背压 → Semaphore 限流；③ 版本敏感（JDK 25.0.3 修 sleep 回退、JDK 26 回退可扩展性优化）→ 升级回归压测。监控：JFR 的 jdk.VirtualThreadPinned（>20ms 记录，必须告警）、SubmitFailed、Start/End；jcmd JSON 转储；载入线程数与虚拟线程峰值指标。
> 参考：08 章

### Q14：JDK 21 迁移到虚拟线程，完整步骤？

> 答：① 盘点执行器与任务类型 → 决策树（I/O 迁/CPU 不迁）；② `Executors.newVirtualThreadPerTaskExecutor()` 替换工厂（ExecutorService 接口零改动）；③ Semaphore 补限流；④ ThreadLocal 换 ScopedValue；⑤ 清理池化代码（有界队列/拒绝策略）；⑥ 压测 + JFR 验证 + pin 告警。注意 JDK 21 的 synchronized pinning 限制（升级 JDK 24+ 或改 ReentrantLock）。
> 参考：05 章 7 节

### Q15（追问）：可以自定义虚拟线程的调度器吗？

> 答：可以。`Thread.ofVirtual().scheduler(Executor)` 可指定任意 `Executor` 作为调度器（如固定线程池、自己的 FJP），默认才是 JDK 的 ForkJoinPool。生产场景**很少需要**：自定义调度器要自行处理载入线程注册（ForkJoinWorkerThread 需满足 JVM 对 carrier 的隐式要求），且失去官方对 mount/unmount 的调优。典型动机是隔离业务（不同优先级任务走不同调度器），但更简单的做法是 CPU 密集桥接平台池（08 章 3.2）。
> 参考：02 章 2 节、03 章 1.1

### Q16（追问）：虚拟线程与 WebFlux/响应式编程怎么选？

> 答：两者都解决"高并发 I/O"，路线相反：WebFlux 通过非阻塞 API 减少线程占用（复杂度转移到回调/操作符），虚拟线程让阻塞式同步代码获得同等吞吐（复杂度转移给 JVM）。虚拟线程转正后，**新项目优先考虑同步栈 + 虚拟线程**（Spring Boot 3.2+ 一行配置）；响应式适合已有响应式基建或超大流量网关等场景。迁移成本与团队熟悉度是主要决策变量。
> 参考：01 章 6 节

### Q17（追问）：虚拟线程下日志 MDC（ThreadLocal）怎么传 traceId？

> 答：两代方案：① 现状——入口处把 MDC 值拷贝到 ScopedValue，业务代码统一从 ScopedValue 读取，异步子任务在 fork 后重新写入 MDC（需手动桥接，因为日志框架仍读 ThreadLocal）；② 未来——SLF4J 2.x 已推进 ScopedValue 适配（MDC 支持"作用域值"模式），届时无需桥接。迁移期统一封装"上下文工具类"（get/set/clear）避免散落直接调用。
> 参考：07 章 7.2

### Q18（追问）：虚拟线程适合做消息队列消费者吗？

> 答：适合且是典型场景。消费逻辑 = 阻塞 I/O（拉取、处理、写回），每消息一个虚拟线程，吞吐瓶颈转移到下游与 CPU。注意三点：① 消费速率限流——Semaphore 控制 in-flight 消息数，避免下游过载与堆压力；② 幂等与重试——虚拟线程无状态，消息处理必须是幂等任务；③ 线程数失控风险——队列突发时虚拟线程数暴涨，务必先限流再消费。
> 参考：05 章 5 节

### 追问：虚拟线程下线程池还有用吗？（工程向）

> 答：有，但角色变了——CPU 密集任务仍用固定平台线程池（虚拟线程无收益且有饥饿风险，08 章 3 节）；虚拟线程执行器只负责 I/O 密集的"任务即线程"场景。关键区分：**虚拟线程替代的是"线程复用"思维，不替代"并发控制"**——限流用 Semaphore、CPU 密集隔离用独立池。加分项：给出"虚拟线程池 + CPU 桥接平台池"的混合架构。
> 参考：05 章、08 章 3 节

### 追问：百万虚拟线程的峰值内存怎么估算？（性能向）

> 答：三部分——① 线程对象元数据（~200-300B × 100 万 ≈ 300MB）；② 栈 chunk（浅栈场景几十 KB × 并发活跃数，不是总数！——阻塞的虚拟线程栈很小）；③ ThreadLocal（若用则每线程放大，07 章）。实测参考：100 万 sleep 场景 ≈ 401MB 堆。工程结论：**预算按"并发峰值 × 每线程成本"而非"创建总数"**，并配 Semaphore 限流。
> 参考：08 章 1 节、05 章 5 节

### 追问：JDK 26 的虚拟线程有什么新变化？（时效向）

> 答：无新特性，主要是稳定性修复——JDK-8375130（可扩展性优化因 SPECjbb2015 回退被撤销）、JDK-8373120（虚拟线程卡 BLOCKED 状态，26u 修复）、JDK-8370887（sleep 密集场景性能回退，25.0.3 修复）。同版本还有 JEP 525（结构化并发六览）的 onTimeout 等新 API（06 章）。面试加分：展示"关注版本动态"的习惯——虚拟线程性能是版本敏感的。
> 参考：08 章 4 节、00 章时间线

## 2. 易错点清单

| # | 易错点 | 正确认知 |
|---|--------|---------|
| 1 | "虚拟线程 = 更快" | 虚拟线程不产生 CPU，只消除 I/O 等待浪费；CPU 密集无收益 |
| 2 | "RUNNABLE = 正在运行" | 虚拟线程 RUNNABLE 可能只是排队等载入线程 |
| 3 | "虚拟线程是 daemon 会等 JVM 退出" | 恰恰相反：daemon = JVM 不等它，主线程结束任务可能被强杀 |
| 4 | "池化虚拟线程提高复用" | 反模式：栈在堆上可 GC，池化放大内存 |
| 5 | "JDK 21 的 pinning 问题现在还有" | JDK 24（JEP 491）已修复，只剩 native 回调/类初始化/符号解析 |
| 6 | "换锁解决 pin" | JDK 24+ 不需要为 pin 换锁；需要 tryLock 等功能时才换 |
| 7 | "结构化并发已经转正" | JEP 525 在 JDK 26 仍是第六次预览，需 `--enable-preview` |
| 8 | "ScopedValue 还需要 remove" | 不需要：run 结束自动销毁；orElse(null) 在 JDK 25+ 编译报错 |
| 9 | "maxPoolSize=256 是常驻线程" | 仅 CPU 密集兜底时才会增至 256；正常场景只有 parallelism 个载入线程 |
| 10 | "虚拟线程不用管并发限制" | 恰恰最需要：无队列无背压，Semaphore 是标配 |

## 4. 快速自测（含答案）

1. **虚拟线程的栈存在哪？** 堆上（StackChunk 分块栈），可被 GC 回收。
2. **载入线程数量默认多少？由什么决定？** CPU 核数（`availableProcessors`），可用 `jdk.virtualThreadScheduler.parallelism` 覆盖。
3. **阻塞的虚拟线程怎么被唤醒？** 时间到/事件就绪 → `unpark()` → 重新入队调度器。
4. **JDK 24 后 pin 的剩余场景？** 原生代码回调 Java、类初始化、符号引用解析。
5. **虚拟线程限流用什么？** Semaphore（池大小/有界队列已不存在）。
6. **JDK 26 结构化并发的新 API？** `Joiner.onTimeout()`、`allSuccessfulOrThrow()` 返回 `List<T>`、`anySuccessfulOrThrow()` 改名。
7. **ScopedValue 未绑定时的行为？** `get()` 抛 NoSuchElementException；`orElse`/`orElseThrow` 处理。
8. **百万虚拟线程实测堆内存？** 约 401MB（sleep 场景）。
9. **虚拟线程支持线程优先级吗？** 不支持（`setPriority` 无效）。
10. **synchronized 内 sleep 在 JDK 21 会发生什么？** pin 载入线程（JDK 24+ 已修复）。
11. **结构化并发子任务默认在什么线程上跑？** 虚拟线程。
12. **如何查看虚拟线程转储？** `jcmd <pid> Thread.dump_to_file -format=json`，虚拟线程单独分组展示。
