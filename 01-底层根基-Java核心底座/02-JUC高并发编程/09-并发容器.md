## 1. 并发容器全景图

JDK 5 通过 JSR-166 引入 `java.util.concurrent` 包，其中的并发容器彻底替代了 `Vector`、`Hashtable`、`Collections.synchronizedXxx()` 等低效同步容器，成为高并发场景下的唯一选择。

```
JUC 并发容器家族
┌──────────────────────────────────────────────────────────────┐
│                    Concurrent Map                            │
│  ConcurrentHashMap          —— 线程安全 HashMap（核心）        │
│  ConcurrentSkipListMap     —— 线程安全 TreeMap（跳表）        │
├──────────────────────────────────────────────────────────────┤
│                    Concurrent List / Set                      │
│  CopyOnWriteArrayList      —— 写时复制 List（读多写少）       │
│  CopyOnWriteArraySet       —— 写时复制 Set                    │
│  ConcurrentSkipListSet     —— 线程安全 TreeSet                │
├──────────────────────────────────────────────────────────────┤
│                    Non-blocking Queue                         │
│  ConcurrentLinkedQueue     —— 无锁无界队列（CAS）             │
│  ConcurrentLinkedDeque     —— 无锁双端队列                    │
├──────────────────────────────────────────────────────────────┤
│                    Blocking Queue                             │
│  ArrayBlockingQueue        —— 有界数组阻塞队列                 │
│  LinkedBlockingQueue       —— 可选有界链表阻塞队列             │
│  PriorityBlockingQueue     —— 无界优先级阻塞队列               │
│  DelayQueue                —— 延迟队列                        │
│  SynchronousQueue          —— 零容量直接交付                   │
│  LinkedTransferQueue       —— 传递队列（JDK 7）               │
│  LinkedBlockingDeque       —— 双端阻塞队列                     │
└──────────────────────────────────────────────────────────────┘
```

> 💡 并发容器的核心设计理念是"**无锁读 + 细粒度锁写**"，读操作尽量不加锁（volatile + CAS），写操作使用分段/桶级锁，最大化并发度。

| 容器 | 线程安全机制 | 数据结构 | 适用场景 |
|------|-------------|---------|---------|
| ConcurrentHashMap | CAS + synchronized（桶锁） | 数组 + 链表 + 红黑树 | 高并发 KV 存储 |
| CopyOnWriteArrayList | ReentrantLock + 数组复制 | 数组 | 读多写极少 |
| ConcurrentLinkedQueue | CAS（Michael-Scott 算法） | 单向链表 | 高并发无锁队列 |
| ArrayBlockingQueue | ReentrantLock + Condition | 数组 | 有界缓冲（生产者-消费者） |
| LinkedBlockingQueue | ReentrantLock + Condition | 链表 | 无界/有界缓冲 |
| SynchronousQueue | CAS / TransferStack/Queue | 零容量 | 直接交付（线程池） |
| DelayQueue | PriorityQueue + ReentrantLock | 堆 | 延迟任务调度 |
| LinkedTransferQueue | CAS + 松弛式哨兵 | 链表 | 高并发传递 |

## 2. ConcurrentHashMap 演进：JDK 7 分段锁 → JDK 8 CAS+synchronized

### 2.1 JDK 7 实现：分段锁（Segment）

```
JDK 7 ConcurrentHashMap 结构

          ┌─────────────────────────────────────┐
          │        ConcurrentHashMap             │
          │  segments[] (默认 16 个 Segment)     │
          │  ┌──────┐┌──────┐┌──────┐┌──────┐   │
          │  │Seg 0 ││Seg 1 ││ ... ││Seg15 │   │
          │  └──┬───┘└──┬───┘└──┬───┘└──┬───┘   │
          │     │        │        │        │      │
          │  ┌──▼──┐ ┌──▼──┐  ┌──▼──┐ ┌──▼──┐   │
          │  │HT[] │ │HT[] │  │HT[] │ │HT[] │    │
          │  │E→E→E│ │E→E  │  │E    │ │E→E→E│   │
          │  └─────┘ └─────┘  └─────┘ └─────┘   │
          └─────────────────────────────────────┘

Segment 继承 ReentrantLock，每个 Segment 管理一段 HashEntry[]
并发度 = segments.length（默认 16），即最多 16 个线程同时写
```

**JDK 7 ConcurrentHashMap 核心特性：**

| 特性 | 说明 |
|------|------|
| 数据结构 | Segment[] + HashEntry[] + 链表 |
| 锁机制 | Segment 继承 ReentrantLock（分段锁） |
| 并发度 | 默认 16（segments 数组长度，构造后不可变） |
| 读操作 | 读不加锁（volatile 读取 HashEntry.value） |
| 扩容 | 每个 Segment 独立扩容（rehash） |
| put 流程 | hash → 定位 Segment → tryLock 自旋 → 插入链表 |
| size() | 先乐观不加锁统计，不一致时加锁重试 |

```java
// JDK 7 ConcurrentHashMap put 示意（简化）
static class Segment<K,V> extends ReentrantLock {
    transient volatile HashEntry<K,V>[] table;

    final V put(K key, int hash, V value, boolean onlyIfAbsent) {
        // tryLock 非阻塞尝试，失败则 scanAndLockForPut 自旋等待
        HashEntry<K,V> node = tryLock() ? null : scanAndLockForPut(key, hash, value);
        try {
            // 定位到具体桶，遍历链表插入或替换
            // ...
        } finally {
            unlock();
        }
    }
}
```

### 2.2 JDK 8 实现：CAS + synchronized 桶锁

```
JDK 8 ConcurrentHashMap 结构

          ┌────────────────────────────────────────┐
          │      ConcurrentHashMap                  │
          │  Node<K,V>[] table                     │
          │  ┌─────┬─────┬─────┬─────┬─────┬─────┐ │
          │  │     │  N  │     │  N  │     │  N  │ │
          │  │     │ K→V→│     │ K→V │     │ K→V │ │
          │  │     │  ▓  │     │  ▓  │     │     │ │ ← 红黑树 (>=8)
          │  │     │  ▓  │     │  ▓  │     │     │ │
          │  └─────┴─────┴─────┴─────┴─────┴─────┘ │
          └────────────────────────────────────────┘

关键字段:
  sizeCtl       — -1(初始化中), -N(N-1个线程在扩容), >0(阈值=capacity*0.75)
  transferIndex — 扩容迁移索引（从后往前分配）
  counterCells  — 高并发分段计数器（类似 LongAdder）
```

| 特性 | JDK 7（Segment） | JDK 8（CAS+synchronized） |
|------|------------------|--------------------------|
| 数据结构 | Segment[] + HashEntry[] + 链表 | Node[] + 链表 + 红黑树 |
| 锁粒度 | Segment 级（默认 16 个） | 桶级（单个链表/树） |
| 锁实现 | ReentrantLock（继承） | synchronized + CAS |
| 读操作 | 不加锁（volatile 读） | 不加锁（volatile + CAS） |
| 并发度 | 固定 16 | 随桶数量扩展（桶数 = 容量） |
| 长链表优化 | 无 | 链表 ≥ 8 转红黑树（容量 ≥ 64） |
| 扩容 | 单 Segment 内 rehash | 多线程协同扩容（transfer） |
| 计数 | 分段锁累加 | CounterCell 分段计数 + CAS |
| key/value null | 不允许 | 不允许 |

> 🎯 **面试核心**：JDK 7 → JDK 8 的最大变化是"锁粒度从 Segment 级降为桶级 + 引入 CAS 无锁操作"，并发度从固定 16 变为随容量动态扩展，同时红黑树解决了长链表查询 O(n) 的问题。

## 3. ConcurrentHashMap 核心源码分析（JDK 8）

### 3.1 初始化：initTable()

```java
// 延迟初始化：首次 put 时才创建 table
private final Node<K,V>[] initTable() {
    Node<K,V>[] tab; int sc;
    while ((tab = table) == null || tab.length == 0) {
        if ((sc = sizeCtl) < 0)
            Thread.yield(); // 其他线程正在初始化，让出 CPU
        else if (U.compareAndSetInt(this, SIZECTL, sc, -1)) {
            // CAS 将 sizeCtl 设为 -1（标记初始化中）
            try {
                if ((tab = table) == null || tab.length == 0) {
                    int n = (sc > 0) ? sc : DEFAULT_CAPACITY; // 默认 16
                    @SuppressWarnings("unchecked")
                    Node<K,V>[] nt = (Node<K,V>[])new Node<?,?>[n];
                    table = tab = nt;
                    sc = n - (n >>> 2); // sc = n * 0.75（阈值）
                }
            } finally {
                sizeCtl = sc;
            }
            break;
        }
    }
    return tab;
}
```

### 3.2 put 流程：putVal()

```java
// JDK 8 ConcurrentHashMap.putVal()（简化核心逻辑）
final V putVal(K key, V value, boolean onlyIfAbsent) {
    if (key == null || value == null) throw new NullPointerException();
    int hash = spread(key.hashCode()); // (h ^ (h >>> 16)) & HASH_BITS

    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        // 1️⃣ 延迟初始化
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();

        // 2️⃣ 桶为空 → CAS 无锁插入
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)))
                break; // CAS 成功，插入完成
        }

        // 3️⃣ 正在扩容 → 帮忙迁移（ForwardingNode）
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);

        // 4️⃣ 桶非空 → synchronized 锁住桶头节点
        else {
            V oldVal = null;
            synchronized (f) { // 细粒度桶锁
                if (tabAt(tab, i) == f) { // 双重检查
                    if (fh >= 0) { // 链表
                        for (Node<K,V> e = f;; ++binCount) {
                            if (e.hash == hash &&
                                ((ek = e.key) == key || (ek != null && key.equals(ek)))) {
                                oldVal = e.val; // 找到，替换
                                break;
                            }
                            Node<K,V> pred = e;
                            if ((e = e.next) == null) {
                                pred.next = new Node<>(hash, key, value, null); // 尾插
                                break;
                            }
                        }
                    } else if (f instanceof TreeBin) { // 红黑树
                        // 树节点插入
                    }
                }
            }
            if (binCount != 0) {
                if (binCount >= TREEIFY_THRESHOLD) // 链表长度 ≥ 8
                    treeifyBin(tab, i); // 转红黑树（需 table.length ≥ 64）
                break;
            }
        }
    }
    // 5️⃣ 计数（分段计数器，类似 LongAdder）
    addCount(1L, binCount);
    return null;
}
```

### 3.3 get 流程：get()

```java
// get() 完全无锁！仅靠 volatile 可见性保证
public V get(Object key) {
    Node<K,V>[] tab; Node<K,V> e, p; int n, eh; K ek;
    int h = spread(key.hashCode());
    if ((tab = table) != null && (n = tab.length) > 0 &&
        (e = tabAt(tab, (n - 1) & h)) != null) {
        if ((eh = e.hash) == h) {
            if ((ek = e.key) == key || (ek != null && key.equals(ek)))
                return e.val; // 桶首节点命中
        }
        else if (eh < 0)
            return (p = e.find(h, key)) != null ? p.val : null;
        // eh < 0: ForwardingNode(扩容) / TreeBin(红黑树) / ReservationNode
        while ((e = e.next) != null) {
            if (e.hash == h && ((ek = e.key) == key || key.equals(ek)))
                return e.val; // 链表遍历
        }
    }
    return null;
}
```

### 3.4 扩容原理：多线程协同

```
扩容触发条件: put 后元素数量 > sizeCtl (容量 × 0.75)

多线程协同迁移:
  ┌─────────────────────────────────────┐
  │  table (旧)       nextTable (新)    │
  │  ┌──┬──┬──┬──┬──┐   ┌──┬──┬──┬──┐ │
  │  │0 │1 │2 │3 │4 │   │  │  │  │  │ │
  │  ├──┼──┼──┼──┼──┤   ├──┼──┼──┼──┤ │
  │  │  │FN│  │  │FN│   │  │  │  │  │ │ ← FN = ForwardingNode
  │  └──┴──┴──┴──┴──┘   └──┴──┴──┴──┘ │
  │       ↑                    ↑         │
  │   线程A迁移完成        线程B迁移完成   │
  │  transferIndex 从后往前分配批次        │
  └─────────────────────────────────────┘

每个线程领取一个 stride（步长）的桶区间
迁移完成后旧桶置为 ForwardingNode（hash=MOVED）
put 发现 MOVED → helpTransfer() 加入扩容
```

> ⚠️ **关键注意**：扩容时 `get()` 仍然可以无锁读取——如果遇到 ForwardingNode，会转发到 `nextTable` 继续查找。正是这种设计保证了扩容不阻塞读操作。

## 4. CopyOnWriteArrayList / CopyOnWriteArraySet

### 4.1 写时复制思想

```
写时复制 (Copy-On-Write, COW)

读操作: 不加锁，直接读取当前数组引用（volatile 可见性）
写操作: 
  1. 加锁 (ReentrantLock)
  2. 复制整个数组 (Arrays.copyOf)
  3. 在新数组上修改
  4. 用新数组替换旧数组引用 (volatile 写)
  5. 释放锁

读 → 读    : 完全不阻塞（无锁）
读 → 写    : 不阻塞（写时复制，读线程仍在读旧数组）
写 → 写    : 互斥（ReentrantLock）
写 → 读    : 不阻塞（读线程读到旧数组，写完成后后续读拿到新数组）
```

### 4.2 CopyOnWriteArrayList 源码核心

```java
public class CopyOnWriteArrayList<E> {
    // volatile 保证数组修改对所有线程可见
    private transient volatile Object[] array;

    /** get() — 无锁！直接读 volatile 数组 */
    public E get(int index) {
        return elementAt(getArray(), index);
    }

    /** add() — 加锁 + 复制数组 */
    public boolean add(E e) {
        final ReentrantLock lock = this.lock;
        lock.lock(); // 写写互斥
        try {
            Object[] elements = getArray();
            int len = elements.length;
            // 复制新数组（长度 + 1）
            Object[] newElements = Arrays.copyOf(elements, len + 1);
            newElements[len] = e;
            setArray(newElements); // volatile 写，让读线程可见
            return true;
        } finally {
            lock.unlock();
        }
    }

    /** addIfAbsent() — 遍历 + 去重 */
    public boolean addIfAbsent(E e) {
        Object[] snapshot = getArray();
        // 先无锁遍历，如果存在直接返回
        return indexOf(e, snapshot, 0, snapshot.length) >= 0 ? false
            : addIfAbsent(e, snapshot); // 不存在 → 加锁再检查（双重检查）
    }
}
```

### 4.3 CopyOnWriteArraySet 实现

```java
// CopyOnWriteArraySet 内部委托给 CopyOnWriteArrayList
// 使用 addIfAbsent() 保证元素不重复
public class CopyOnWriteArraySet<E> extends AbstractSet<E> {
    private final CopyOnWriteArrayList<E> al;

    public boolean add(E e) {

    }
}
```

### 4.4 使用场景与性能特点

| 特性 | 说明 |
|------|------|
| 适用场景 | **读多写极少**的事件监听器列表、黑白名单、配置缓存 |
| 不适用 | 写频繁的场景（每次写都复制全数组，O(n) 开销） |
| 迭代器 | 弱一致性（snapshot 迭代器，不抛 ConcurrentModificationException） |
| 内存占用 | 写时同时存在两个数组（旧 + 新），可能触发频繁 GC |
| 数据实时性 | 读可能读到旧数据（写未完成时），非强一致性 |

> ⚠️ **避坑**：如果写操作频繁（写次数 > 读次数的 1/10），不要使用 CopyOnWriteArrayList。每次写都复制全数组，频繁 Full GC 会导致严重的性能问题。此时应考虑 `ConcurrentLinkedDeque` 或其他方案。

## 5. ConcurrentLinkedQueue / ConcurrentLinkedDeque

### 5.1 无锁队列：Michael-Scott 算法

```java
/**
 * ConcurrentLinkedQueue：基于 CAS 的无界无锁队列
 *
 * 核心算法：Michael & Scott 无锁队列算法（M&S 算法）
 * - head 指向哨兵节点（dummy node），tail 不一定指向尾节点
 * - 使用 CAS 原子更新 next 指针和 head/tail
 * - 允许 tail 落后于实际尾节点（减少 CAS 更新 tail 的次数）
 */
public class ConcurrentLinkedQueue<E> {
    // head 和 tail 都是 volatile
    private transient volatile Node<E> head;
    private transient volatile Node<E> tail;

    public ConcurrentLinkedQueue() {
        head = tail = new Node<>(null); // 哨兵节点
    }

    public boolean offer(E e) {
        Node<E> newNode = new Node<>(Objects.requireNonNull(e));
        for (Node<E> t = tail, p = t;;) {
            Node<E> q = p.next;
            if (q == null) {
                // CAS 将 p.next 从 null 更新为新节点
                if (NEXT.compareAndSet(p, null, newNode)) {
                    // CAS tail（允许失败，不强制每次更新）
                    if (p != t)
                        TAIL.weakCompareAndSet(this, t, newNode);
                    return true;
                }
            } else if (p == q) // 哨兵回退（poll 操作导致的）
                p = (t != (t = tail)) ? t : head;
            else
                p = (p != t && t != (t = tail)) ? t : q;
        }
    }

    public E poll() {
        for (Node<E> h = head, p = h;;) {
            Node<E> q = p.next;
            E item = p.item;
            if (item != null && ITEM.compareAndSet(p, item, null)) {
                // CAS 将头节点的 item 置为 null（出队）
                if (p != h)
                    updateHead(h, (q != null) ? q : p);
                return item;
            }
            else if (q == null) { // 队列空
                updateHead(h, p);
                return null;
            }
            else
                p = q;
        }
    }
}
```

### 5.2 与阻塞队列的区别

| 对比维度 | ConcurrentLinkedQueue | LinkedBlockingQueue |
|---------|----------------------|-------------------|
| 线程安全机制 | CAS 无锁 | ReentrantLock + Condition |
| 阻塞特性 | 非阻塞（立即返回或失败） | 阻塞（put/take 可阻塞） |
| 有界性 | 无界 | 可选有界 |
| 适用场景 | 高并发、低延迟、不要求阻塞等待 | 生产者-消费者模型、线程池 |
| 内存占用 | CAS 自旋可能消耗 CPU | 锁阻塞会释放 CPU |
| size() | O(n) 遍历（无原子计数） | O(1) 原子计数 |

> 💡 ConcurrentLinkedQueue 的 `size()` 是 O(n) 的，因为它是无锁队列，没有维护原子计数器。如果需要频繁获取大小，考虑 `LinkedBlockingQueue` 或维护独立的 `AtomicInteger`。

### 5.3 ConcurrentLinkedDeque

```java
/**
 * ConcurrentLinkedDeque：双端无锁队列
 * 支持头尾两端的高效插入和移除
 * 使用"松弛式"引用（relaxed pointers）减少 CAS 竞争
 */
ConcurrentLinkedDeque<String> deque = new ConcurrentLinkedDeque<>();

deque.addFirst("head");  // 头插
deque.addLast("tail");   // 尾插
String first = deque.pollFirst(); // 弹出头元素
String last = deque.pollLast();   // 弹出尾元素

// 适用场景：工作窃取（Work-Stealing）
// 线程从自己的双端队列头部取任务，空闲时从其他线程队列尾部偷取
```

## 6. BlockingQueue 体系：ArrayBlockingQueue / LinkedBlockingQueue

### 6.1 阻塞队列 API 分组

BlockingQueue 提供四组操作，行为不同：

| 操作 | 抛异常 | 返回特殊值 | 阻塞等待 | 超时退出 |
|------|--------|-----------|---------|---------|
| 插入 | `add(e)` | `offer(e)` | `put(e)` | `offer(e, time, unit)` |
| 移除 | `remove()` | `poll()` | `take()` | `poll(time, unit)` |
| 检查 | `element()` | `peek()` | — | — |

> 💡 生产首选 `offer(e, time, unit)` / `poll(time, unit)` 超时版本，既能阻塞等待，又不会永久阻塞，兼顾功能与安全性。

### 6.2 ArrayBlockingQueue：有界数组阻塞队列

```java
/**
 * ArrayBlockingQueue：基于数组的有界阻塞队列
 *
 * 特性：
 * - 容量固定（构造时指定，不可变）
 * - 同一把 ReentrantLock + 两个 Condition（notFull, notEmpty）
 * - 支持公平/非公平模式（默认非公平）
 * - put/take 阻塞，offer/poll 非阻塞
 */
public class ArrayBlockingQueue<E> {
    final Object[] items;   // 环形数组
    int takeIndex;          // 下次 take 位置
    int putIndex;           // 下次 put 位置
    int count;              // 元素数量

    final ReentrantLock lock;                  // 同一把锁！
    private final Condition notEmpty;           // 等待非空
    private final Condition notFull;            // 等待非满

    public ArrayBlockingQueue(int capacity, boolean fair) {
        if (capacity <= 0) throw new IllegalArgumentException();
        this.items = new Object[capacity];
        this.lock = new ReentrantLock(fair);
        this.notEmpty = lock.newCondition();
        this.notFull = lock.newCondition();
    }

    /** put() — 队列满时阻塞等待 */
    public void put(E e) throws InterruptedException {
        Objects.requireNonNull(e);
        final ReentrantLock lock = this.lock;
        lock.lockInterruptibly(); // 可中断加锁
        try {
            while (count == items.length)
                notFull.await();          // 队列满 → 等待
            enqueue(e);
        } finally {
            lock.unlock();
        }
    }

    /** take() — 队列空时阻塞等待 */
    public E take() throws InterruptedException {
        final ReentrantLock lock = this.lock;
        lock.lockInterruptibly();
        try {
            while (count == 0)
                notEmpty.await();         // 队列空 → 等待
            return dequeue();
        } finally {
            lock.unlock();
        }
    }

    private void enqueue(E e) {
        items[putIndex] = e;
        if (++putIndex == items.length) putIndex = 0; // 环形
        count++;
        notEmpty.signal(); // 唤醒等待 take 的线程
    }

    private E dequeue() {
        E e = (E) items[takeIndex];
        items[takeIndex] = null;
        if (++takeIndex == items.length) takeIndex = 0;
        count--;
        notFull.signal(); // 唤醒等待 put 的线程
        return e;
    }
}
```

### 6.3 LinkedBlockingQueue：链表阻塞队列

```java
/**
 * LinkedBlockingQueue：基于链表的阻塞队列
 *
 * 特性：
 * - 默认无界（Integer.MAX_VALUE），可指定容量
 * - 两把锁 + 两个 Condition（takeLock + putLock 分离）
 * - 吞吐量通常高于 ArrayBlockingQueue
 * - 链表节点动态创建
 */
public class LinkedBlockingQueue<E> {
    // 两把锁分离：提高并发度
    private final ReentrantLock takeLock = new ReentrantLock();
    private final Condition notEmpty = takeLock.newCondition();

    private final ReentrantLock putLock = new ReentrantLock();
    private final Condition notFull = putLock.newCondition();

    // 原子计数器（AtomicInteger）
    private final AtomicInteger count = new AtomicInteger();

    static class Node<E> {
        E item;
        Node<E> next;
        Node(E x) { item = x; }
    }

    private transient Node<E> head; // 哨兵
    private transient Node<E> last; // 尾指针

    public LinkedBlockingQueue() {
        this(Integer.MAX_VALUE); // 默认无界！
    }
}
```

### 6.4 ArrayBlockingQueue vs LinkedBlockingQueue

| 对比维度 | ArrayBlockingQueue | LinkedBlockingQueue |
|---------|-------------------|-------------------|
| 数据结构 | 数组（固定容量） | 链表（动态节点） |
| 有界性 | 必须指定容量 | 可选有界，默认无界 Integer.MAX_VALUE |
| 锁设计 | 同一把锁（lock） | 两把锁分离（takeLock + putLock） |
| 吞吐量 | 低（单锁竞争） | 高（读写锁分离） |
| 内存分配 | 预先分配，无 GC 压力 | 动态创建节点，GC 压力大 |
| 公平策略 | 支持公平/非公平 | 不支持公平（链表先天公平） |
| 性能特点 | 稳定、可预测 | 高吞吐、有波动 |

> 🎯 **选型建议**：需要严格有界 + 公平策略选 `ArrayBlockingQueue`；追求吞吐量 + 允许一定内存波动选 `LinkedBlockingQueue`；默认无界是坑——生产环境务必指定容量，防止 OOM！

## 7. PriorityBlockingQueue 与 DelayQueue

### 7.1 PriorityBlockingQueue：无界优先级阻塞队列

```java
/**
 * PriorityBlockingQueue：支持优先级的无界阻塞队列
 *
 * 特性：
 * - 内部使用二叉堆（小顶堆/大顶堆）
 * - 元素必须实现 Comparable 或提供 Comparator
 * - 无界（可动态扩容），不会阻塞 put
 * - take 时队列空则阻塞
 * - 迭代器不保证顺序
 */
public class PriorityBlockingQueue<E> {
    // 二叉堆数组
    private transient Object[] queue;
    private transient int size;
    private transient Comparator<? super E> comparator;

    // 同一把锁 + 一个 Condition
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();

    // 自旋 + CAS 用于扩容（避免扩容时阻塞读）
    private transient volatile int allocationSpinLock;

    public void put(E e) {
        offer(e); // 无界队列，put 不阻塞，直接调用 offer
    }

    public boolean offer(E e) {
        final ReentrantLock lock = this.lock;
        lock.lock();
        try {
            // 扩容检查与 CAS 自旋扩容
            // 插入元素到堆尾，执行 siftUp 上浮调整
            return true;
        } finally {
            lock.unlock();
        }
    }

    public E take() throws InterruptedException {
        final ReentrantLock lock = this.lock;
        lock.lockInterruptibly();
        try {
            while (size == 0)
                notEmpty.await(); // 队列空则阻塞
            // 弹出堆顶元素，执行 siftDown 下沉调整
```

### 7.2 DelayQueue：延迟队列

```java
/**
 * DelayQueue：支持延迟获取元素的阻塞队列
 *
 * 特性：
 * - 元素必须实现 Delayed 接口（getDelay + compareTo）
 * - take() 只有在元素延迟时间到期后才能取出
 * - 内部使用 PriorityQueue 存储，按到期时间排序
 * - 无界队列
 *
 * 典型场景：
 * - 定时任务调度
 * - 订单超时取消
 * - 缓存过期清理
 * - 连接池空闲连接回收
 */

public class DelayQueue<E extends Delayed> {
    private final transient ReentrantLock lock = new ReentrantLock();
    private final PriorityQueue<E> q = new PriorityQueue<E>(); // 内部堆
    private final Condition available = lock.newCondition();
    private Thread leader = null; // 领导者（Leader-Follower 模式）

    public E take() throws InterruptedException {
        final ReentrantLock lock = this.lock;
        lock.lockInterruptibly();
        try {
            for (;;) {
                E first = q.peek();
                if (first == null)
                    available.await(); // 队列空，等待
                else {
                    long delay = first.getDelay(NANOSECONDS);
                    if (delay <= 0)
                        return q.poll(); // 到期 → 取出

                    // 未到期，等待 delay 时间
                    first = null;
                    if (leader != null)
                        available.await(); // 有其他 leader 线程在等
                    else {
                        Thread thisThread = Thread.currentThread();
                        leader = thisThread;
                        try {
                            available.awaitNanos(delay); // 精确等待
                        } finally {
                            if (leader == thisThread)
                                leader = null; // 释放 leader
                        }
                    }
                }
            }
        } finally {
            // 唤醒其他等待线程
            if (leader == null && q.peek() != null)
                available.signal();
            lock.unlock();
        }
    }
}

// 元素必须实现 Delayed 接口
class DelayedTask implements Delayed {
    private final long executeTime;
    private final String name;

    public DelayedTask(String name, long delay, TimeUnit unit) {
        this.name = name;
        this.executeTime = System.currentTimeMillis()
                         + TimeUnit.MILLISECONDS.convert(delay, unit);
    }

    @Override
    public long getDelay(TimeUnit unit) {
        return unit.convert(executeTime - System.currentTimeMillis(),
                TimeUnit.MILLISECONDS);
    }

    @Override
    public int compareTo(Delayed o) {
        return Long.compare(this.executeTime,
                ((DelayedTask) o).executeTime);
    }
}
```

### 7.3 Leader-Follower 模式

```
DelayQueue 的 Leader-Follower 模式：

   leader = ThreadA
   ┌──────────┐    ┌──────────┐    ┌──────────┐
   │ ThreadA  │    │ ThreadB  │    │ ThreadC  │
   │ (Leader) │    │(Follower)│    │(Follower)│
   │ awaitNanos│   │  await() │    │  await() │
   │ 精确等待  │    │  无限等待  │    │  无限等待  │
   └──────────┘    └──────────┘    └──────────┘
         │
   delay 到期
         │
         ▼
   ThreadA 取出元素
   → signal 唤醒一个 Follower
   → Follower 成为新 Leader

优点：精确等待 + 减少不必要的唤醒竞争
```

## 8. SynchronousQueue 与 TransferQueue

### 8.1 SynchronousQueue：零容量直接交付

```java
/**
 * SynchronousQueue：容量为 0 的阻塞队列
 *
 * 核心特性：
 * - 内部不存储任何元素
 * - put() 必须等待一个 take()，take() 必须等待一个 put()
 * - 每个插入操作必须等待一个移除操作，反之亦然
 * - 只是"传递"，不"缓存"
 *
 * 两种实现模式：
 * - 公平模式：TransferQueue（FIFO 队列）
 * - 非公平模式：TransferStack（LIFO 栈，默认）
 */
public class SynchronousQueue<E> {
    // 默认 TransferStack（非公平，吞吐量更高）
    public SynchronousQueue() {
        this(false);
    }

    public SynchronousQueue(boolean fair) {
        transferer = fair ? new TransferQueue<E>() : new TransferStack<E>();
    }

    // put() 阻塞直到有消费者取走
    public void put(E e) throws InterruptedException {
        if (e == null) throw new NullPointerException();
        if (transferer.transfer(e, false, 0) == null) { // e != null == producer
            Thread.interrupted();
            throw new InterruptedException();
        }
    }

    // take() 阻塞直到有生产者放入
    public E take() throws InterruptedException {
        Object e = transferer.transfer(null, false, 0); // null == consumer
        if (e != null)
            return (E) e;
        Thread.interrupted();
        throw new InterruptedException();
    }
}

// 典型应用场景：CachedThreadPool 的任务队列
// new CachedThreadPool() 内部使用 SynchronousQueue
// 任务到达时，有空闲线程直接取走执行，无空闲则创建新线程
```

### 8.2 LinkedTransferQueue：传递队列（JDK 7）

```java
/**
 * LinkedTransferQueue：JDK 7 引入的传递队列
 *
 * 继承接口 TransferQueue（BlockingQueue 的增强版）
 *
 * 核心方法：
 * - transfer(E e)：直接传递，如有消费者则立即交付，否则阻塞
 * - tryTransfer(E e)：尝试传递，如无消费者则立即返回 false
 * - tryTransfer(E e, long timeout, TimeUnit unit)：带超时的尝试传递
 * - hasWaitingConsumer()：是否有消费者在等待
 * - getWaitingConsumerCount()：等待消费者的数量
 */
public class LinkedTransferQueue<E> {
    // 使用松弛式哨兵（slotted waiters）和 CAS
    // 比 SynchronousQueue 更灵活：没有消费者时也能入队（有缓冲能力）

    public void transfer(E e) throws InterruptedException {
        // 先尝试直接交给消费者
        if (!tryTransfer(e, 0, false)) {
            // 无消费者 → 入队等待，直到被消费者取走
        }
    }

    public boolean tryTransfer(E e) {
        // 尝试直接交给消费者，无消费者则立即返回 false
        return false; // 实际逻辑略
    }
}

// 使用场景：需要"有则消费，无则排队"的灵活传递语义
// 比 SynchronousQueue 更灵活：作为有界缓冲 + 直接传递的混合体
```

### 8.3 三种"传递型"队列对比

| 特性 | SynchronousQueue | LinkedTransferQueue | LinkedBlockingQueue |
|------|-----------------|-------------------|-------------------|
| 容量 | 0（零存储） | 无界（可存储） | 可选有界 |
| 直接传递 | ✅ transfer() | ✅ transfer() | ❌ 只能存 |
| 缓冲能力 | 无 | 有 | 有 |
| 公平模式 | 支持（队列/栈） | 近似公平 | 先天公平 |
| 典型应用 | CachedThreadPool | 高并发消息传递 | 线程池通用队列 |
| 吞吐量 | 极高（零拷贝） | 高 | 中高 |

> ⚠️ SynchronousQueue 的 `offer()` 行为特殊：如果无消费者等待，`offer()` 立即返回 `false`，不会阻塞。`put()` 则会阻塞等待消费者。

### 9.1 场景速查

### 9.3 避坑指南

| 易错点 | 问题 | 正确做法 |
|--------|------|---------|
| ConcurrentHashMap 用错 key | 空指针异常 | key/value 都不能为 null（区别于 HashMap） |
| ConcurrentHashMap 复合操作 | 线程不安全 | `putIfAbsent`、`compute`、`merge` 原子方法替代 |
| CopyOnWriteArrayList 写频繁 | Full GC | 写次数 > 读次数的 1/10 时换用其他方案 |
| LinkedBlockingQueue 默认无界 | OOM | 构造时务必指定容量 |
| ConcurrentLinkedQueue size() | O(n) 遍历 | 改用 `LinkedBlockingQueue` 或维护独立计数器 |
| SynchronousQueue offer() | 数据丢失 | 确认无消费者时 offer 立即返回 false |
| DelayQueue 元素未实现 Delayed | ClassCastException | 元素必须实现 `getDelay()` + `compareTo()` |

> 🎯 **核心原则**：高并发场景优先选 `ConcurrentHashMap`（Map）、`CopyOnWriteArrayList`（读多写少 List）、`LinkedBlockingQueue`（有界阻塞队列）。按"有界、阻塞、CAS"三层递进思路选择合适容器。

## 10. 面试高频考点

### 10.1 基础问答

**Q1: ConcurrentHashMap JDK 7 和 JDK 8 的区别？**

| 对比项 | JDK 7 | JDK 8 |
|-------|-------|-------|
| 数据结构 | Segment[] + HashEntry[] + 链表 | Node[] + 链表 + 红黑树 |
| 锁粒度 | Segment 级（默认 16 个） | 桶级（单个链表头节点） |
| 锁实现 | ReentrantLock（Segment 继承） | synchronized + CAS |
| 并发度 | 固定 16 | 随桶数量扩展 |
| 长链表优化 | 无 | ≥ 8 转红黑树（容量 ≥ 64） |
| 扩容 | 单 Segment rehash | 多线程协同迁移 |
| 计数 | 分段锁累加 | CounterCell 分段 CAS |

**Q2: ConcurrentHashMap 的 get() 为什么不需要加锁？**

- Node 的 `val` 和 `next` 字段使用 `volatile` 修饰，保证可见性
- 插入时使用 CAS 或 synchronized 保证原子性，插入完成前读线程不会看到
- 扩容时通过 ForwardingNode 转发，保证读操作能访问到最新数据

**Q3: CopyOnWriteArrayList 的读写分离机制？**

读不加锁，直接读 volatile 数组引用；写加锁后复制新数组修改，再用新数组替换旧数组引用。读线程可能读到旧数据（写未完成时），但永远不会读到不一致的数据。

### 10.2 进阶问答

**Q4: ConcurrentHashMap 的 size() 方法如何实现高并发？**

JDK 8 使用 CounterCell 分段计数（类似 LongAdder）。先尝试 CAS 更新 baseCount，失败则随机选择一个 CounterCell 累加。`size()` 时累加 `baseCount + ΣCell.value`，不需要加锁。

```java
public int size() {
    long s = sumCount(); // baseCount + ΣcounterCells
    return (s < 0L) ? 0 : (s > (long) Integer.MAX_VALUE) ? Integer.MAX_VALUE : (int) s;
}
```

**Q5: BlockingQueue 的 put() 和 take() 底层如何实现阻塞和唤醒？**

使用 ReentrantLock + Condition：
- `put()` 时队列满 → `notFull.await()` 阻塞
- `take()` 取出元素后 → `notFull.signal()` 唤醒
- `take()` 时队列空 → `notEmpty.await()` 阻塞
- `put()` 放入元素后 → `notEmpty.signal()` 唤醒

**Q6: 如何用 DelayQueue 实现订单超时取消？**

```java
// 1. 订单创建时加入 DelayQueue
class OrderDelayed implements Delayed {
    long expireTime; // 订单超时时间戳
    String orderId;
    // 实现 getDelay() 和 compareTo()
}

// 2. 后台线程不断 take()
// 3. take() 返回 → 订单已超时 → 执行取消逻辑
```

**Q7: ConcurrentLinkedQueue 的 tail 为什么不总是指向尾节点？**

为了减少 CAS 更新 tail 的次数。尾节点 CAS 插入成功后，不立即 CAS 更新 tail，而是等到一定次数后再更新。这是"松弛式"更新策略——用一定的"不精确性"换取更高的 CAS 成功率。

### 10.3 深度问答

**Q8: ConcurrentHashMap 的多线程扩容原理？**

1. 当元素数量超过 `sizeCtl`（容量 × 0.75）时触发扩容
2. 创建新的 nextTable（容量翻倍）
3. 将 table 从后往前分成连续的 stride（步长），每个线程领取一个 stride
4. 迁移完的桶置为 ForwardingNode（hash=MOVED）
5. put 发现 MOVED 会调用 `helpTransfer()` 加入扩容
6. 所有桶迁移完成 → nextTable 替换旧 table，sizeCtl 为新阈值

**Q9: 生产环境如何选择有界队列？**

```text
ArrayBlockingQueue:
  优点：容量固定、预分配数组无 GC 压力、支持公平策略
  缺点：单锁竞争、吞吐量较低
  适合：需要严格限制容量、需要公平保证、对延迟敏感的场景

LinkedBlockingQueue:
  优点：两把锁分离、吞吐量高
  缺点：动态创建节点 GC 压力大、不支持公平
  适合：强调吞吐量、允许一定 GC 开销的场景
```

**Q10: 手写一个简单的生产者-消费者模型？**

```java
public class ProducerConsumerDemo {
    private static final BlockingQueue<Integer> QUEUE
            = new ArrayBlockingQueue<>(10);

    static class Producer implements Runnable {
        @Override
        public void run() {
            for (int i = 0; i < 50; i++) {
                try {
                    QUEUE.put(i);
                    System.out.println("[P] 生产: " + i);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }
    }

    static class Consumer implements Runnable {
        @Override
        public void run() {
            while (!Thread.currentThread().isInterrupted()) {
                try {
                    Integer item = QUEUE.take();
                    System.out.println("[C] 消费: " + item);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }
    }

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(3);
        pool.submit(new Producer());
        pool.submit(new Consumer());
        pool.submit(new Consumer());
        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
}
```
