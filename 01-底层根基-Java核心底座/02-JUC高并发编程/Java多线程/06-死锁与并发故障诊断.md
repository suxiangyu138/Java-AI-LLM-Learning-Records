## 1. 死锁四条件与经典案例

**死锁（Deadlock）**：两个以上线程**互相持有对方需要的锁，且互不相让**——所有线程永久阻塞。

**死锁四条件（缺一不可，打破任一即解）**：

| 条件 | 含义 | 打破手段 |
|------|------|---------|
| 互斥 | 资源同一时刻只能一个线程用 | 难以打破（锁的本质） |
| **持有并等待** | 拿着 A 锁去等 B 锁 | **一次性申请全部资源** |
| **不可剥夺** | 拿到的锁不能强制抢走 | 超时释放（tryLock） |
| **循环等待** | A 等 B 持的，B 等 A 持的 | **全局锁顺序** |

```java
// 经典死锁：账户转账（锁顺序不一致）
public void transfer(Account from, Account to, double amt) {
    synchronized (from) {              // 线程 1：锁 A
        synchronized (to) {            // 同时等锁 B —— 线程 2 反向操作时互相等待
            from.debit(amt);
            to.credit(amt);
        }
    }
}
// 线程 1：transfer(A, B)  持有 A 等 B
// 线程 2：transfer(B, A)  持有 B 等 A
// → 循环等待形成 → 死锁
```

**死锁的典型场景**：

- 多把锁的**获取顺序不一致**（最经典：转账、资源池双重获取）；
- 在持锁时调用**外部/未知代码**（回调、远程调用——对方可能反向拿你的锁）；
- **嵌套锁** + 不同路径反向加锁。

> 🎯 **核心要点**：死锁排查的四条件清单 = 诊断工具——**jstack 看到"互相等待"的线程对后，用四条件逐项核对，找到哪条可打破**（通常是"循环等待"最容易从设计上消灭）。

## 2. jstack / jcmd 排查实战

**工具**：`jstack <pid>`（或 `jcmd <pid> Thread.print`）——打印所有线程的堆栈与锁状态。

```bash
# 排查流程
jps                          # 找 Java 进程 PID
jstack <pid> > dump.txt      # 抓线程堆栈（死锁现场）
# 或：jcmd <pid> Thread.print > dump.txt
```

**死锁在 jstack 中的特征**（JVM 自带死锁检测！）：

```text
Found one Java-level deadlock:
=============================
"Thread-2":                      ← 死锁线程 1
  waiting to lock monitor 0x... (object 0x..., a java.lang.Object),   ← 想拿的锁
  which is held by "Thread-1"    ← 被谁持有
"Thread-1":                      ← 死锁线程 2
  waiting to lock monitor 0x... (object 0x...),
  which is held by "Thread-2"    ← 互相等待 → JVM 自动识别并打印 "Found one Java-level deadlock"
```

**诊断步骤**（非死锁场景也适用）：

```text
① 抓堆栈：jstack 拿快照
② 找状态异常线程：大量 BLOCKED/WAITING 的线程是嫌疑
③ 看锁链：waiting to lock ... held by ... 串成环 = 死锁实锤
④ 看业务特征：全部线程堆栈是否集中在一个方法（锁粒度问题？）
⑤ 多次抓取对比：如果线程一直不前进（时间戳/次数），确认卡死
```

**其他工具**：`jconsole`（图形化线程图，可看死锁）、JFR 的 `jdk.JavaMonitorEnter` 事件（锁竞争热力）。

> 🎯 **核心要点**：**jstack 能自动检测死锁**（"Found one Java-level deadlock"）——线上排障第一动作就是抓堆栈；即使不是死锁，**"线程都停在哪"**也直接暴露问题（等锁、等 IO、死循环）。

## 3. 死锁预防：顺序 / 超时 / 检测

**预防三策略**（按推荐度）：

### 策略 1：全局锁顺序（治本，最推荐）

```java
// 所有多锁获取按固定顺序：先比较身份，永远小→大
public void transfer(Account a, Account b, double amt) {
    Account first = a.id() < b.id() ? a : b;    // 按 id 排序
    Account second = a.id() < b.id() ? b : a;
    synchronized (first) {
        synchronized (second) { ... }           // 所有线程同一顺序 → 循环等待不可能
    }
}
```

### 策略 2：超时获取（兜底，ReentrantLock 的 tryLock）

```java
if (lockA.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lockB.tryLock(1, TimeUnit.SECONDS)) {   // 拿不到 B → 放弃 A → 不形成循环等待
            try { ... } finally { lockB.unlock(); }
        } else { log.warn("拿不到 B，放弃本次"); }
    } finally { lockA.unlock(); }
}
```

### 策略 3：死锁检测（事后，JVM 已内置）

JVM 在 `ThreadMXBean.findDeadlockedThreads()` 提供检测 API——监控系统定期调用，发现死锁即告警/重启：

```java
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] deadlocked = bean.findDeadlockedThreads();   // 返回死锁线程，null = 无
if (deadlocked != null) { alertAndRestart(); }
```

**防死锁的总原则**：**少持锁、短持锁、不乱序、不在锁内调外部代码**。

> 🎯 **核心要点**：死锁预防 = **设计上（锁顺序）消灭循环等待 + 机制上（tryLock 超时）兜底 + 监控上（findDeadlockedThreads）报警**——三层齐备，死锁基本免疫。

## 4. 活锁与饥饿

**与死锁并列的两个"伪死锁"**：

| 形态 | 表现 | 与死锁的区别 | 典型场景 |
|------|------|------------|---------|
| **活锁（Livelock）** | 线程**都在动**，但一直无法推进 | 状态在变（RUNNABLE）而非永久阻塞 | 两个线程互相"谦让"：A 让 B，B 让 A，死循环 |
| **饥饿（Starvation）** | 线程**一直得不到**资源 | 没有循环等待，是被长期排挤 | 非公平锁下低优先级线程长期拿不到锁 |

```java
// 活锁示例：两个线程反复让出（每次都是"你先"）
while (true) {
    if (lockA.tryLock()) {
        if (lockB.tryLock()) { /* 成功 */ }
        else { lockA.unlock(); Thread.yield(); }   // 让出后立刻重试 → 可能两个线程互相让，永不成功
    }
}

// 饥饿示例：非公平锁 + 高竞争 —— 新来的线程插队，等待久的线程饿死
new ReentrantLock();          // 非公平：释放锁瞬间新线程可能插队成功
new ReentrantLock(true);      // 公平锁：FIFO，等待最久的先拿 → 防饥饿
```

**活锁 vs 死锁的识别**：死锁 = "线程都不动"（BLOCKED/WAITING 固定）；活锁 = "线程都在跑但没进展"（CPU 高、堆栈反复相同）。

> 🎯 **核心要点**：三种"锁故障"的对比记忆 = **死锁：都不动（互相等）、活锁：都在动（互相让）、饥饿：总轮不到（被插队）**——排查时先看 CPU（高=活锁/忙等，低=死锁/等待）。

## 5. 线程泄漏与线程池耗尽

**线程泄漏（Thread Leak）**：线程创建后无法回收——**线程对象本身是 GC 根（强引用）**，泄漏线程永远占着内存与资源：

```java
// 线程泄漏的经典成因：
// ① 每次任务 new Thread 且不 join/不管理 —— 任务结束不了，线程变僵尸
// ② 线程池未关闭且任务阻塞 —— shutdown 不被调用，池线程永远存活
// ③ 阻塞任务永不结束 —— 线程卡在 IO/等待，池被占满

// 线程池耗尽的表现（生产高频事故）：
// 所有线程阻塞在某处（如第三方接口不返回）→ 新任务全部排队 → 队列满 → 拒绝策略触发
// 症状：请求大量失败（RejectedExecutionException）/ 假死
```

**排查线程泄漏/池耗尽**：

| 步骤 | 手段 | 看什么 |
|------|------|--------|
| 线程数趋势 | `jstack` 多次抓取统计线程数 | 线程数只增不减 = 泄漏 |
| 线程状态分布 | jstack 统计 BLOCKED/WAITING 数量 | 大量阻塞 = 池耗尽 |
| 池配置审计 | 检查线程池参数 | 无界队列 + 无拒绝策略 = OOM 风险 |
| 监控指标 | JFR/线程池自定义指标 | 池大小、队列深度、拒绝次数 |

**防御清单**：

1. **有界线程池 + 有界队列 + 明确拒绝策略**（见 `02-JUC高并发编程/06`）；
2. **任务必须设超时**（第三方调用不返回是池耗尽头号元凶）；
3. **优雅关闭**：`shutdown()` + `awaitTermination()`；
4. **监控池状态**：队列深度/活跃线程数接入告警。

> 🎯 **核心要点**：线程池耗尽的本质 = **"任务出不去"**（外部依赖挂起）而不是池配置错——排查先找"哪些任务在阻塞"，再谈调参数（详见 `Java异常体系/07` 的线程异常与 `02-JUC高并发编程/06` 的线程池）。

## 6. 生产事故复盘模板

**并发故障复盘五段式**（面试/文档都适用）：

```text
① 现象：什么症状？（请求超时/数据错乱/服务假死）
② 复现条件：什么触发？（流量峰值/特定接口/特定数据）
③ 定位过程：怎么查的？（jstack 快照 → 线程状态 → 锁链 → 根因）
④ 根因分析：为什么？（四条件核对 / 竞态推演 / 池耗尽链条）
⑤ 修复与预防：
   - 立即止血（重启/回滚/限流）
   - 根治修复（锁顺序/tryLock/有界池/超时）
   - 预防机制（监控指标/压测/代码评审清单）
```

**评审清单**（把并发 bug 挡在线上之前）：

| 检查项 | 问题 |
|--------|------|
| 共享状态 | 静态字段/单例里有可变状态吗？ |
| 复合操作 | check-then-act / 读改写有同步吗？ |
| 锁使用 | 多锁顺序一致吗？锁内调用外部代码了吗？ |
| 线程生命周期 | 线程池有界吗？关闭了吗？ |
| 可见性 | 跨线程的标志/状态有 volatile/锁吗？ |
| 阻塞风险 | 所有 IO/远程调用有超时吗？ |

> 🎯 **核心要点**：并发故障的排查 = **工具（jstack/JFR）+ 原理（四条件/三要素）+ 纪律（评审清单）**——工具能告诉你"停在哪"，原理能告诉你"为什么"，纪律能让它不再发生。
