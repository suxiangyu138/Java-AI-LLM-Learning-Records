## 1. 并发性能的度量与瓶颈

**并发优化的目标不是"用更多线程"，而是"提高吞吐、降低延迟"**——先度量，再优化：

| 指标 | 含义 | 工具 |
|------|------|------|
| 吞吐量（TPS） | 单位时间完成任务数 | 压测（JMeter/JFR） |
| 延迟（P99） | 99% 请求在多少毫秒内完成 | APM/JFR |
| 线程利用率 | 线程忙等 vs 阻塞占比 | JFR 的 `jdk.ThreadParked` |
| 锁竞争率 | 锁被争抢的程度 | `jdk.JavaMonitorEnter` 事件 |

**并发瓶颈的四个层次**（从大到小）：

```text
① 架构层：串行依赖、锁的粒度（业务设计）
② 调度层：线程数不匹配（过多切换/过少闲置）
③ 同步层：锁竞争、原子操作冲突
④ 硬件层：缓存一致性（伪共享）、内存带宽
```

> 🎯 **核心要点**：**"先度量后优化"是并发性能的铁律**——盲目调线程数/换锁类型前，先用 JFR 看瓶颈在哪一层。**最常见的真相：瓶颈在 IO 等待（浪费线程）或锁竞争（浪费等待），而不是代码不够快**。

## 2. 上下文切换的隐藏成本

**切换成本回顾**（见 01 模块第 3 节）：寄存器保存/恢复 + 内核进出 + TLB/缓存失效——一次切换微秒级，但**频繁切换可吃掉 10-30% CPU**。

**Java 侧的切换来源**：

| 来源 | 说明 | 优化 |
|------|------|------|
| 线程数 > 核数 | 时间片轮转必然切换 | 线程数与核数匹配 |
| **锁竞争** | 等锁线程被挂起 → 锁释放再唤醒（两次切换） | 减少锁竞争（第 3 节） |
| 阻塞 IO | 线程挂起等待 IO → 切换走 | 异步 IO / 虚拟线程 |
| 频繁 sleep/唤醒 | 定时任务粒度过细 | 合理节流 |

```text
一个"锁竞争 + 唤醒"的完整代价：
线程 A 释放锁 → 唤醒 B（一次切换）→ B 抢锁执行 → B 又阻塞（第二次切换）
→ 一次简单的临界区交换 = 2-4 次上下文切换 + 缓存冷启动
→ 这就是"高竞争锁"场景性能暴跌的底层原因
```

**线程数与吞吐的 U 型曲线**（面试必画）：

```text
吞吐
  ▲          ╱╲
  │        ╱   ╲
  │      ╱      ╲        ← 超卖区：切换开销反超收益
  │    ╱
  │  ╱
  └─┴──────────────▶ 线程数
    核数      过度线程
```

> 🎯 **核心要点**：切换成本是"隐藏的税"——**线程池的意义之一就是把线程数限制在收益区间**；虚拟线程把"每任务线程"的切换成本降到用户态（但竞争/同步的切换仍在）。优化线程数前先算：任务是 CPU 密集还是 IO 密集（IO 密集可以更多线程/虚拟线程）。

## 3. 锁粒度与锁分离

**锁粒度**：临界区的大小——**越小竞争越少，但同步代码越碎**。核心手段：

```java
// ① 缩小临界区：只锁真正共享的操作
// ❌ 锁住整个方法（无共享计算也被锁）
public synchronized void process(Order o) {
    validate(o);                 // 无共享 —— 不需要锁
    buildReport(o);              // 无共享 —— 不需要锁
    cache.put(o.id(), o);        // 只有这里碰共享缓存
}
// ✅ 只锁共享操作（方法级 → 代码块级）
public void process(Order o) {
    validate(o);
    buildReport(o);
    synchronized (cache) { cache.put(o.id(), o); }   // 临界区缩到最小
}

// ② 锁分离：读锁/写锁分离（读多写少）
ReadWriteLock rw = new ReentrantReadWriteLock();
rw.readLock().lock();    // 多个读线程可同时持有读锁
// 写时独占：rw.writeLock().lock();

// ③ 分段/分桶：不同数据不同锁（ConcurrentHashMap 的设计思路）
// ④ 无共享数据：每线程独立（ThreadLocal 计数）
```

**锁分离的经典实现**（理解 JDK 容器的钥匙）：

| 容器 | 锁策略 |
|------|--------|
| ConcurrentHashMap | 锁桶头节点（JDK 8+），不同桶并行 |
| LongAdder | **分段累加**（多个 Cell，写线程分散），读时汇总 |
| CopyOnWriteArrayList | 写复制 + volatile 发布（读写完全分离） |
| StampedLock | 乐观读（无锁读 + 校验版本） |

> 🎯 **核心要点**：锁优化的主旋律 = **"让不同线程的锁互不相干"**——缩小临界区（减少无关线程等锁）、读写分离（读不互斥）、分段（不同数据不同锁）。JDK 并发容器是这三招的工业级示范（见 `Java集合框架/06`）。

## 4. 伪共享：缓存行与 @Contended

**缓存行（Cache Line）**：CPU 缓存以 64 字节为单位加载——**两个线程操作同一缓存行上的不同变量，会互相拖慢**：

```text
缓存行（64B）：[ varA | varB | padding... ]
线程 1 频繁写 varA → 该缓存行在 CPU1 标记"脏"
线程 2 频繁写 varB → 需要从 CPU1 同步该行（缓存一致性协议 MESI）
→ 两个线程互相触发"缓存行同步" —— 明明没有共享变量，性能却互相拖累
→ 这就是"伪共享"（False Sharing）：不共享数据，但共享了缓存行
```

```java
// 伪共享的典型场景：并发统计多指标
class Stats {
    volatile long hits;      // 线程 A 只写 hits
    volatile long misses;    // 线程 B 只写 misses —— 在同一缓存行 → 互相拖累
}
// 修复：填充 padding 让它们落在不同缓存行
class PaddedStats {
    volatile long hits;
    long p1, p2, p3, p4, p5, p6, p7;    // 填充到 64 字节边界（旧手法）
    volatile long misses;
}
// 现代 JDK：@Contended 注解（jdk.internal.vm.annotation，需 -XX:-RestrictContended）
```

**JDK 内部的伪共享防护实例**：`LongAdder` 的 `Cell[]` 用 `@Contended` 注解隔离——**每个累加单元独占缓存行**，这是 LongAdder 高并发写性能的关键。

> 🎯 **核心要点**：伪共享的识别 = **"两个变量各自独立被不同线程写，性能却线性下降"**；修复 = 缓存行隔离（padding/@Contended）或重构数据结构。它是"硬件层的并发优化"，面试能答出 MESI/64 字节/@Contended 三层即满分。

## 5. 无锁思维：CAS 与原子类

**锁 vs 无锁**（CAS）：

| 维度 | 锁（悲观） | CAS（乐观） |
|------|:----------:|:-----------:|
| 假设 | 冲突必然发生 → 先锁后做 | 冲突很少 → 先做后验 |
| 机制 | 挂起/唤醒（切换成本） | **自旋重试**（不挂起） |
| 竞争小时 | 有锁开销 | **最快** |
| 竞争激烈 | 排队公平 | 自旋浪费 CPU（ABA 等） |
| 适用 | 写多/长临界区 | **读多写少/短临界区** |

```java
// CAS 的本质：比较并交换（compare-and-swap）—— 一条硬件原子指令
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();
// 内部：do { old = get(); } while (!compareAndSet(old, old + 1));   // 自旋重试

// CAS 的三大问题（面试必背）：
// ① ABA：A → B → A，CAS 看不出中间变过 → AtomicStampedReference（带版本号）
// ② 自旋开销：竞争激烈时大量空转 → 用 LongAdder（分段）或回退锁
// ③ 只能保护单变量：复合状态用锁或 AtomicReference 包装对象
```

**原子类选择**（性能场景）：

| 场景 | 选择 |
|------|------|
| 一般计数 | AtomicInteger/AtomicLong |
| **高并发写**（统计） | **LongAdder**（分段，读近似） |
| 引用更新 | AtomicReference（CAS 整个对象） |
| 带版本防 ABA | AtomicStampedReference / AtomicMarkableReference |

> 🎯 **核心要点**：无锁思维 = **"用硬件指令（CAS）替代操作系统锁"**——低竞争时性能碾压、无死锁；高竞争时自旋反而更差（用 LongAdder 分段或锁）。"锁 vs CAS"的选择本质是**冲突概率的假设**（细节见 `02-JUC高并发编程/08-CAS与原子类.md`）。

## 6. 虚拟线程时代的性能观

**2025 并发性能实践的重大转变**（时效性）：

```text
传统性能观：线程贵 → 池化复用 → 调线程池参数 → 锁竞争优化
虚拟线程观：线程便宜 → 每任务一个 → 不用调池 → 瓶颈转移到"共享资源"

核心转变：
① 线程不是稀缺资源了 —— IO 密集场景不再"猜线程数"，每任务一个虚拟线程
② 稀缺的是真实资源 —— 数据库连接、外部 API 额度：用 Semaphore 限流（不是限线程！）
③ 池化虚拟线程是反模式 —— 增加开销无收益（JDK 官方指导）
④ synchronized 在 Java 24+ 恢复正常（JEP 491）—— 21-23 的 ReentrantLock workaround 可移除
```

```java
// 虚拟线程时代的正确姿势（IO 密集 + 共享资源限流）
var semaphore = new Semaphore(100);              // 限制数据库连接数（真稀缺资源）
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    requests.forEach(r -> executor.submit(() -> {
        semaphore.acquire();                     // 限流：不限制虚拟线程，限制底层资源
        try { db.query(r); } finally { semaphore.release(); }
    }));
}
```

**什么场景仍用平台线程/锁优化**：

| 场景 | 策略 |
|------|------|
| IO 密集（HTTP/DB 调用多） | **虚拟线程每任务一个**（默认） |
| CPU 密集 | 平台线程（核数 + 1）或并行流 |
| 混合 | 虚拟线程为主 + 关键计算并行流 |
| 持锁长操作/原生代码 | 注意（锁内阻塞问题在 24+ 已修复） |

> 🎯 **核心要点**：虚拟线程时代的性能观 = **"线程无限，资源有限"**——优化对象从"线程数"变成"共享资源（连接池/Semaphore）"；锁优化原则（粒度/分离/无锁）依然有效，因为同步问题与线程成本无关（详见 `02-JUC高并发编程/12-虚拟线程与结构化并发.md`）。
