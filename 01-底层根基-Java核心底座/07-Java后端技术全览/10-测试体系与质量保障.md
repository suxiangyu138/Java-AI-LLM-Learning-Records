## 1. 测试金字塔与策略

### 1.1 测试金字塔

```
              ┌──────────┐
              │  E2E 测试  │  少量（5-10%）
              │  (端到端)   │  最慢、最易碎、最接近真实场景
              ├──────────┤
              │  集成测试  │  适量（20-30%）
              │ (多个组件) │  中等速度、验证组件间交互
              ├──────────┤
              │  单元测试  │  大量（60-70%）
              │ (单个类/方法)│  最快、最稳定、反馈最快
              └──────────┘

正确的测试比例（金字塔）：
  大量单元测试 + 适量集成测试 + 少量 E2E 测试

错误的比例（倒金字塔/甜筒）：
  大量 E2E 测试 → 运行慢、维护成本高、反馈慢
```

### 1.2 测试 F.I.R.S.T 原则

```
Fast（快速）：
  单元测试应该在毫秒级完成
  任何需要秒级的测试都是不合格的单元测试

Independent（独立）：
  每个测试独立运行，不依赖其他测试
  测试顺序不应该影响结果

Repeatable（可重复）：
  任何环境、任何时间运行，结果都应该相同
  不能依赖外部资源（时间、网络、数据库）

Self-Validating（自校验）：
  测试应该自己判断成功/失败
  不需要人工检查输出

Timely（及时）：
  测试应该在产品代码编写之前或同步编写
  不要等产品代码写完了再补测试（TDD 更佳）
```

## 2. JUnit 5 完全指南

### 2.1 JUnit 5 架构

```
JUnit 5 = JUnit Platform + JUnit Jupiter + JUnit Vintage

JUnit Platform → 测试运行平台（IDE、Maven/Gradle 集成）
JUnit Jupiter  → 新的编程模型和扩展模型
JUnit Vintage  → 兼容 JUnit 3/4 的测试

核心注解：
  @Test          标记测试方法
  @BeforeEach    每个测试前执行（旧的 @Before）
  @AfterEach     每个测试后执行（旧的 @After）
  @BeforeAll     所有测试前执行一次，须 static（旧的 @BeforeClass）
  @AfterAll      所有测试后执行一次，须 static（旧的 @AfterClass）
  @DisplayName   测试描述名
  @Disabled      禁用测试（旧的 @Ignore）
  @Nested        嵌套测试类
  @Tag("unit")   标签（分类）
  @Timeout(1)    超时
  @RepeatedTest  重复测试
  @ParameterizedTest 参数化测试
  @TempDir       临时目录
```

### 2.2 断言

```java
// JUnit 5 断言
assertEquals(expected, actual);
assertNotEquals(unexpected, actual);
assertTrue(condition);
assertFalse(condition);
assertNull(object);
assertNotNull(object);
assertSame(expected, actual);  // 同一个对象引用
assertThrows(IllegalArgumentException.class, () -> {
    service.doSomething(null); // 期望抛异常
});
assertDoesNotThrow(() -> service.doSomething("ok"));
assertTimeout(Duration.ofSeconds(1), () -> {
    service.slowOperation();  // 期望 1s 内完成
});

// assertAll（软断言，所有断言都执行，会报告所有失败）
assertAll("user",
    () -> assertEquals("张三", user.getName()),
    () -> assertTrue(user.getAge() > 0),
    () -> assertNotNull(user.getEmail())
);

// AssertJ（流式断言库，更直观，推荐）
assertThat(user.getName()).isEqualTo("张三");
assertThat(user.getAge()).isGreaterThan(18).isLessThan(60);
assertThat(userList)
    .hasSize(3)
    .extracting(User::getName)
    .contains("张三", "李四");
```

### 2.3 参数化测试

```java
// @ParameterizedTest 通过不同的参数运行同一个测试
class ParameterizedTests {

    // ValueSource：简单值
    @ParameterizedTest
    @ValueSource(strings = {"admin", "user", "guest"})
    void testRoleNameNotEmpty(String roleName) {
        assertFalse(roleName.isEmpty());
    }

    // CsvSource：CSV 格式
    @ParameterizedTest
    @CsvSource({
        "0, 0, 0",
        "1, 2, 3",
        "100, 200, 300"
    })
    void testAdd(int a, int b, int expected) {
        assertEquals(expected, calculator.add(a, b));
    }

    // MethodSource：方法提供参数
    @ParameterizedTest
    @MethodSource("provideUsers")
    void testUserValidation(User user, boolean valid) {
        assertEquals(valid, userService.validate(user));
    }

    static Stream<Arguments> provideUsers() {
        return Stream.of(
            Arguments.of(new User("张三", 25), true),
            Arguments.of(new User("", 25), false),     // 空名称
            Arguments.of(new User("李四", -1), false)  // 负年龄
        );
    }
}
```

## 3. Mockito 深度实践

### 3.1 核心概念

```
Mock vs Stub vs Spy：

Stub：返回预设值的简单替代品
  when(userMapper.findById(1L)).thenReturn(mockUser);

Mock：不仅可以预设返回值，还可以验证交互行为
  verify(userMapper, times(1)).findById(1L);
  // 除了返回值，还要验证方法是否按预期被调用

Spy：真实对象的包装，只 Mock 部分方法
  UserService spyService = spy(realService);
  doReturn(mockResult).when(spyService).externalCall();  // 只 Mock 外部调用
  spyService.internalMethod();  // 走真实逻辑
```

### 3.2 Mockito 实用技巧

```java
@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @Mock          // 创建 Mock 对象
    private UserMapper userMapper;

    @Mock
    private CacheService cacheService;

    @InjectMocks   // 将 Mock 注入到被测试对象
    private UserServiceImpl userService;

    @Captor        // 参数捕获器
    private ArgumentCaptor<User> userCaptor;

    // === Mock 返回值 ===

    @Test
    void testGetUser() {
        // 基本 Mock
        User mockUser = new User(1L, "张三");
        when(userMapper.findById(1L)).thenReturn(mockUser);

        // 根据参数动态返回
        when(userMapper.findById(anyLong())).thenAnswer(invocation -> {
            Long id = invocation.getArgument(0);
            return new User(id, "User-" + id);
        });

        // 多次调用返回不同值
        when(cacheService.getCount())
            .thenReturn(0, 1, 2);  // 第 1 次返回 0，第 2 次返回 1，第 3 次返回 2

        // Mock 异常
        when(userMapper.findById(-1L)).thenThrow(new IllegalArgumentException());

        // Mock void 方法
        doNothing().when(cacheService).clear();
        doThrow(new RuntimeException()).when(cacheService).clear();
    }

    // === 验证交互 ===

    @Test
    void testInteraction() {
        userService.updateUser(new User(1L, "张三"));

        // 验证调用次数
        verify(userMapper, times(1)).update(any(User.class));
        verify(cacheService, atLeastOnce()).clear();

        // 验证从未调用
        verify(userMapper, never()).deleteById(anyLong());

        // 捕获实际参数
        verify(userMapper).update(userCaptor.capture());
        User captured = userCaptor.getValue();
        assertEquals("张三", captured.getName());
    }

    // === ArgumentMatcher ===

    @Test
    void testArgumentMatcher() {
        // 自定义参数匹配器
        when(userMapper.insert(argThat(user ->
            user.getName() != null && user.getAge() > 0))).thenReturn(1);

        // 常用匹配器
        any(User.class)     任何 User 对象
        anyLong()           任何 long 值
        eq("value")         精确匹配
        contains("keyword") 包含字符串
        isNull() / isNotNull()
        same(expected)      同一个引用
    }

    // === BDD 风格（given-when-then） ===

    @Test
    void testBddStyle() {
        // given（给定条件）
        User mockUser = new User(1L, "张三");
        given(userMapper.findById(1L)).willReturn(mockUser);

        // when（执行操作）
        User result = userService.getUser(1L);

        // then（验证结果）
        assertThat(result.getName()).isEqualTo("张三");
        then(userMapper).should(times(1)).findById(1L);
    }
}
```

### 3.3 Mockito 注意事项

```java
// ❌ 错误：不能 Mock final 类/方法（需要额外配置）
// Mockito 2.1+ 开始支持，需要创建文件：
// src/test/resources/mockito-extensions/org.mockito.plugins.MockMaker
// 内容：mock-maker-inline

// ❌ 错误：不能 Mock static 方法（需要 Mockito 3.4+ 的 mockStatic）
try (MockedStatic<StaticUtils> mocked = mockStatic(StaticUtils.class)) {
    mocked.when(StaticUtils::getNow).thenReturn("mocked");
}

// ❌ 反模式：Mock 被测试的类本身
@Test
void testService() {
    UserService spy = spy(UserService.class);
    // 不应该这样！应该 Mock 依赖，不 Mock 被测试对象
}

// ✅ 正确：只 Mock 间接依赖
@Test
void testServiceWithMockedDependencies() {
    // Mock 依赖（Mapper、远程服务等）
    // 不 Mock 被测试的 Service 本身
}
```

```java
// @SpringBootTest 加载完整 Spring 上下文（最慢）
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureMockMvc
@ActiveProfiles("test")  // 使用 test profile
class UserIntegrationTest {

    @Autowired private MockMvc mockMvc;
    @Autowired private UserService userService;

    @Test
    @Transactional  // 测试后自动回滚
    void testCreateUser() throws Exception {
        String requestBody = """
            {
                "userName": "张三",
                "age": 25,
                "email": "zhangsan@example.com"
            }
            """;

        mockMvc.perform(post("/api/users")
                .contentType(MediaType.APPLICATION_JSON)
                .content(requestBody))
               .andExpect(status().isCreated())
               .andExpect(jsonPath("$.data.userName").value("张三"))
               .andExpect(jsonPath("$.data.id").isNumber());

        // 验证数据库
        User user = userService.getUserByUserName("张三");
        assertThat(user).isNotNull();
        assertThat(user.getEmail()).isEqualTo("zhangsan@example.com");
    }

### 6.1 JaCoCo 配置

                            </limit>
                        </limits>
                    </rule>
                </rules>
            </configuration>

    </executions>

```

### 6.2 覆盖率指标解读

```
覆盖率类型：

行覆盖率（Line Coverage）：最常用，执行的代码行比例
分支覆盖率（Branch Coverage）：if/switch 各分支的执行比例
方法覆盖率（Method Coverage）：方法被调用比例
类覆盖率（Class Coverage）：类被测试比例

建议指标：
  核心业务代码：> 80% 行覆盖率
  工具类/工具方法：> 90%
  Controller/普通 CRUD：60-70%
  配置类/常量类：不需要追求覆盖率

不要迷信 100%：
  100% 覆盖率 ≠ 没有 Bug
  覆盖率只能发现"没测到的代码"，不能发现"写错的逻辑"
  追求有意义的测试，而非追求数字
```

## 7. 性能测试

### 7.1 JMH（Java 微基准测试）

```java
@BenchmarkMode(Mode.Throughput)     // 吞吐量
@OutputTimeUnit(TimeUnit.SECONDS)   // 每秒
@State(Scope.Thread)                // 状态共享范围
@Warmup(iterations = 3, time = 1)   // 预热 3 次，每次 1s
@Measurement(iterations = 5, time = 2)  // 测量 5 次，每次 2s
@Fork(1)
public class StringConcatenationBenchmark {

    @Benchmark
    public String stringBuilder() {
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < 100; i++) {
            sb.append("hello").append(i);
        }
        return sb.toString();
    }

    @Benchmark
    public String stringPlus() {
        String result = "";
        for (int i = 0; i < 100; i++) {
            result += "hello" + i;
        }
        return result;
    }
}
```

### 7.2 压力测试工具

```
压测流程：
  1. 确定压测目标（QPS、P99 延迟）
  2. 准备压测脚本
  3. 预热
  4. 阶梯加压（100 → 500 → 1000 → 2000 QPS）
  5. 观察指标（QPS、延迟、错误率、CPU、内存、GC）
  6. 找到瓶颈和拐点

工具：
  JMeter（GUI + 命令行，功能全面）
  wrk/wrk2（命令行，轻量高效）
  Gatling（Scala DSL，可编程）
  K6（JS 脚本，云原生友好）
  Arthas（阿里，在线诊断而不是压测）

关键指标：
  QPS（每秒请求数）
  RT（响应时间，P50/P90/P99/P999）
  Error Rate（错误率）
  CPU / Memory / GC / IO
```

## 8. 契约测试

### 8.1 Spring Cloud Contract

```
契约测试（Consumer-Driven Contract）：
  消费者（调用方）定义期望的 API 行为
  提供者（被调用方）验证是否满足期望
  确保 API 变更不会破坏消费者

Spring Cloud Contract：
  契约定义（Groovy DSL 或 YAML）：
    Contract.make {
        request {
            method 'GET'
            url '/api/users/1'
        }
        response {
            status 200
            headers {
                contentType applicationJson()
            }
            body([
                id: 1,
                name: "张三"
            ])
        }
    }

  提供者端：
    根据契约生成测试 → 验证 Controller 返回是否符合契约

  消费者端：
    根据契约生成 Stub → 本地测试时用 Stub 替代真实提供者

  好处：
    提前发现 API 不兼容变更
    消费者可以独立测试
    契约即文档
```

## 9. 测试中常见的反模式

```java
// ❌ 反模式 1：测试依赖执行顺序
// 测试 A 创建用户 → 测试 B 使用该用户
// 解决：每个测试独立创建数据

// ❌ 反模式 2：测试太复杂（有 if/for/异常处理）
@Test
void testSomething() {
    if (someCondition) {
        doThis();
    } else {
        doThat();
    }
}
// 解决：拆成两个测试，分别覆盖两个分支

// ❌ 反模式 3：Mystery Guest（神秘的测试数据）
User user = new User("test", 123, new Date(), "x", true);
// 解决：数据意图清晰
User user = UserFixture.activeUser();

// ❌ 反模式 4：测试方法名不达意
@Test void test1() { }  // 不知道测什么
@Test void shouldThrowExceptionWhenUserNameIsNull() { }  // 一目了然

// ❌ 反模式 5：没有断言（或断言值为 null 也算通过）
// 测试方法体为空或没有 assert 语句

// ❌ 反模式 6：测试依赖外部资源
// 依赖当前时间 → 用 Clock + Clock.fixed()
// 依赖远程 API → 用 WireMock
// 依赖数据库 → 用 Testcontainers

// ❌ 反模式 7：Sleep 替代等待
Thread.sleep(5000);  // 不可靠且慢
// 解决：用 Awaitility
await().atMost(5, SECONDS).until(() -> order.getStatus() == COMPLETED);
```
