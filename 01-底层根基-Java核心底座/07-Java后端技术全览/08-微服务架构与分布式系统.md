## 1. 分布式理论基础

### 1.1 CAP 定理

```
CAP 定理（2000 年由 Eric Brewer 提出）：

C（Consistency）一致性：
  所有节点在同一时间看到相同的数据
  读请求可能被阻塞，直到数据在所有节点上一致
  例子：转账后马上查余额，必须看到最新余额

A（Availability）可用性：
  每个请求都能获得非错误的响应
  但不保证返回的是最新数据
  例子：即使部分节点故障，服务仍然可用

P（Partition Tolerance）分区容错：
  系统即使出现网络分区（丢包、断网），仍能正常工作
  网络分区是不可避免的（交换机故障、网线断、GC STW）

三者只有同时满足两个：
  CP 系统（牺牲 A）：ZooKeeper、Consul（CP 模式）
    → 网络分区时，少数派节点拒绝服务
  AP 系统（牺牲 C）：Eureka、Nacos（AP 模式）
    → 网络分区时，各分区独立服务（短暂不一致）
  CA 系统（不存在！网络分区无法避免）

实际选择：
  分布式系统中 P 必须满足（网络不可靠）
  在 C 和 A 之间权衡：
    金融支付 → CP 核心（宁愿不可用也不能出错）
    社交/电商 → AP 核心（可以暂时不一致但不能不可用）
```

### 1.2 BASE 理论

```
BASE = Basically Available + Soft State + Eventually Consistent
是 CAP 中 AP 的延伸和妥协：

Basically Available（基本可用）：
  系统在故障时允许损失部分可用性
  例子：响应时间变长（从 50ms → 500ms）、功能降级（关闭部分非核心功能）

Soft State（软状态）：
  允许系统中的数据存在中间状态
  例子：订单"已创建"，支付结果"处理中"（不是非黑即白）

Eventually Consistent（最终一致性）：
  不要求数据实时一致，但最终会达到一致
  例子：下单后库存扣减、支付状态同步 → 经过一段延迟最终一致
  实现方式：消息队列、补偿机制、定时对账
```

### 1.3 一致性协议

```
强一致性协议：
  2PC（两阶段提交）：
    Phase 1: 准备 → 所有参与者锁定资源，回复"准备好"
    Phase 2: 提交 → 所有参与者执行提交
    问题：同步阻塞、协调者单点故障、数据不一致风险

  3PC（三阶段提交）：
    增加预提交阶段 + 超时机制
    解决 2PC 的部分问题，但仍不完善

最终一致性协议：
  Saga：
    长事务拆分为一系列本地短事务
    每个短事务有对应的补偿事务
    协调 Saga / 编排 Saga

  TCC（Try-Confirm-Cancel）：
    Try: 预留资源（检查 + 冻结）
    Confirm: 确认执行（使用预留资源）
    Cancel: 取消执行（释放预留资源）
    牺牲实现复杂度换取强一致性

  AT 模式（Seata，自动补偿）：
    全局锁 + undo log
    第一阶段提交 + 第二阶段统一回滚或异步删除 undo log
    对业务代码侵入最小
```

## 2. 注册中心与配置中心

### 2.1 注册中心核心能力

```
服务注册：
  服务启动时，向注册中心注册自己的地址（IP:Port）+ 元数据

服务发现：
  调用方从注册中心获取所有可用服务实例列表

健康检查：
  定期检测服务实例是否存活，剔除不健康的实例

配置推送：
  服务实例变更时，实时推送给调用方
```

### 2.2 主流注册中心对比

| 维度 | Nacos | Consul | Eureka | ZooKeeper |
|------|-------|--------|--------|-----------|
| **CAP** | AP/CP 可切换 | CP（默认） | AP | CP |
| **一致性协议** | Raft（CP 模式）/Distro（AP 模式） | Raft | Peer to Peer | ZAB |
| **健康检查** | TCP/HTTP/MySQL/自定义 | TCP/HTTP/Script | HTTP 心跳 | Keep Alive |
| **配置中心** | ✅（内置） | ✅（KV Store） | ❌ | ✅（需配合） |
| **多数据中心** | ✅ | ✅ | ✅ | ❌ |
| **访问协议** | HTTP/DNS/gRPC | HTTP/DNS/gRPC | HTTP | TCP |
| **雪崩保护** | ✅ | ✅ | ✅ | ❌（CP 本身保护） |
| **控制台** | ✅（功能丰富） | ✅ | ✅（简单） | ❌ |
| **Spring Cloud 集成** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ |
| **单独使用复杂度** | 低 | 中 | 低 | 高 |

### 2.3 Nacos 架构与配置

```
Nacos 架构：
┌─────────────────────────────────────────────┐
│                Nacos Server 集群              │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐     │
│  │ Node 1  │  │ Node 2  │  │ Node 3  │     │
│  └────┬────┘  └────┬────┘  └────┬────┘     │
│       └────────────┼────────────┘           │
│                    │                        │
│         MySQL 集群（数据持久化）               │
└─────────────────────────────────────────────┘
          ↑ 注册/订阅          ↑ 注册/订阅
   ┌──────────┐        ┌──────────┐
   │ 服务 A   │  ←调用→ │ 服务 B   │
   └──────────┘        └──────────┘

AP 模式 vs CP 模式：
  AP 模式（默认）：
    - 临时实例（ephemeral=true）
    - 心跳检测，自动剔除不健康实例
    - 适合：常规微服务

  CP 模式：
    - 持久化实例（ephemeral=false）
    - 不自动剔除，需手动注销
    - 适合：DNS、CoreDNS 场景
```

### 3.1 调用方式演进

```
RestTemplate（HTTP 同步调用，低版本）
  ↓
Ribbon（客户端负载均衡，已停更）
  ↓
Spring Cloud LoadBalancer（官方替代 Ribbon）

选择导向：
  通用微服务 → OpenFeign + LoadBalancer
  Java 生态 + 高性能 + 服务治理 → Dubbo
  多语言异构系统 → gRPC
```

```java
// 自定义负载均衡策略
@Bean
public ReactorLoadBalancer<ServiceInstance> customLoadBalancer(
    Environment environment, LoadBalancerClientFactory factory) {
    String name = environment.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
    // 返回基于权重的负载均衡器（或自定义）
    return new RandomLoadBalancer(
        factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
}

// 常见负载均衡算法：
// - 轮询（Round Robin）：依次分配
// - 权重（Weighted）：按权重分配（适合异构机器）
// - 最少连接（Least Connections）：选活跃连接数最少的
// - 一致性 Hash（Consistent Hash）：同一个请求发到同一个实例
// - 随机（Random）：随机选一个
```

### 3.4 Dubbo 核心概念

```java
// Dubbo 3.x 核心能力
// 1. 服务提供者
@DubboService(version = "1.0.0", group = "user", timeout = 3000)
public class UserServiceImpl implements UserService { ... }

// 2. 服务消费者
@DubboReference(version = "1.0.0", group = "user",
    timeout = 3000, retries = 0,  // 注意：幂等服务才设 retries>0
    loadbalance = "leastactive",  // 负载均衡策略
    cluster = "failfast")         // 集群容错策略
private UserService userService;

// 负载均衡策略（loadbalance）：
//   random      → 随机（默认）
//   roundrobin  → 轮询
//   leastactive → 最少活跃调用数
//   consistenthash → 一致性 Hash

// 集群容错策略（cluster）：
//   failover    → 失败自动切换重试（默认，重试其他机器）
//   failfast    → 快速失败，立即报错
//   failsafe    → 失败安全，忽略异常
//   failback    → 失败自动恢复，后台记录
//   forking     → 并行调用，只要一个成功
//   broadcast   → 广播调用所有提供者

// 线程模型：
//   - 业务线程池（默认固定 200 线程）
//   - IO 线程（Netty EventLoop）
//   - 线程派发策略：all / direct / message / execution / connection
```

## 4. 服务网关

### 4.1 Spring Cloud Gateway

```yaml
# Gateway 配置
spring:
  cloud:
    gateway:
      routes:
        # 用户服务路由
        - id: user-service
          uri: lb://user-service       # lb:// 表示负载均衡
          predicates:                   # 断言（匹配条件）
            - Path=/api/users/**
          filters:                      # 过滤器
            - StripPrefix=0
            - AddRequestHeader=X-Gateway, gateway
            - name: RequestRateLimiter  # 限流
              args:
                redis-rate-limiter:
                  replenishRate: 10     # 每秒生成令牌数
                  burstCapacity: 20     # 最大突发容量
                  requestedTokens: 1    # 每次请求消耗令牌数

        # 订单服务路由
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=0

      # 全局过滤器
      default-filters:
        - DedupeResponseHeader=Access-Control-Allow-Origin

      # 跨域配置
      globalcors:
        cors-configurations:
          '[/**]':
            allowedOrigins: "https://example.com"
            allowedMethods: GET, POST, PUT, DELETE
            allowedHeaders: "*"
            allowCredentials: true
```

### 4.2 Gateway 核心概念

```
Route（路由）：网关的基本构建块
  = Predicate + Filter + URI
  一个请求匹配到 Route → 经过 Filter → 转发到目标 URI

Predicate（断言）：
  匹配请求的特征（路径、方法、Header 等）
  - Path=/api/users/**
  - Method=GET,POST
  - Header=Auth-Token
  - Query=version,v2
  - Host=**.example.com
  - Cookie=sessionId,.*

Filter（过滤器）：
  对请求/响应进行处理
  - 全局过滤器（GlobalFilter）：对所有路由生效
  - 路由过滤器（GatewayFilter）：对特定路由生效
  - 内置过滤器：AddRequestHeader、RemoveResponseHeader、RequestRateLimiter、Retry...
  - 自定义过滤器

请求处理流程：
  Client → Gateway
    → Route Predicate（匹配到哪个路由）
    → Pre Filters（转发前：鉴权、限流、日志、修改请求头）
    → 代理到微服务
    → Post Filters（返回前：修改响应头、脱敏、日志）
    → Client
```

### 4.3 自定义网关过滤器

```java
// 全局认证过滤器
@Component
public class AuthGlobalFilter implements GlobalFilter, Ordered {

    // 白名单路径（不需要认证）
    private static final List<String> WHITE_LIST = List.of(
        "/api/auth/login", "/api/auth/register", "/api/public/**"
    );

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();

        // 白名单放行
        if (isWhiteListed(path)) {
            return chain.filter(exchange);
        }

        // 获取 Token
        String token = exchange.getRequest().getHeaders()
            .getFirst("Authorization");
        if (token == null || !token.startsWith("Bearer ")) {
            return unauthorized(exchange, "未登录");
        }

        // 验证 Token
        try {
            Claims claims = jwtService.parseToken(token.substring(7));
            // 将用户信息放入请求头传给下游
            exchange = exchange.mutate()
                .request(exchange.getRequest().mutate()
                    .header("X-User-Id", claims.getSubject())
                    .header("X-User-Name", claims.get("name", String.class))
                    .build())
                .build();
        } catch (Exception e) {
            return unauthorized(exchange, "Token 无效或已过期");
        }

        return chain.filter(exchange);
    }

    @Override
    public int getOrder() {
        return -100;  // 优先级最高
    }
}
```

## 5. 服务保护：熔断、限流、降级

### 5.1 Sentinel 核心概念

```
资源（Resource）：
  需要保护的代码（接口、方法、代码块）

规则（Rule）：
  定义资源的保护策略

熔断（Circuit Breaker）：
  当资源不稳定时（慢调用比例/异常比例达到阈值），熔断该资源
  熔断期间所有请求快速失败
  一段时间后半开状态：放少量请求探测，成功则关闭熔断器关闭，失败则继续熔断

限流（Rate Limiting）：
  控制单位时间内的请求数量
  - QPS 限流：每秒通过 N 个请求
  - 线程数限流：同时处理的不超过 N 个线程
  - 流控效果：快速失败 / Warm Up / 排队等待
  - 流控模式：直接 / 关联 / 链路

降级（Fallback）：
  资源被限流/熔断 → 执行 fallback 逻辑
```

### 5.2 Sentinel 实战

```java
// 1. 注解方式
@RestController
public class OrderController {

    @GetMapping("/order/{id}")
    @SentinelResource(
        value = "getOrder",                        // 资源名
        blockHandler = "getOrderBlockHandler",      // 限流/熔断处理
        fallback = "getOrderFallback"               // 异常降级处理
    )
    public Result<Order> getOrder(@PathVariable Long id) {
        return Result.success(orderService.getOrder(id));
    }

    // 限流/熔断时的处理（参数需与原始方法一致 + BlockException）
    public Result<Order> getOrderBlockHandler(Long id, BlockException e) {
        log.warn("getOrder 被限流/熔断: id={}", id);
        return Result.error(429, "请求太频繁，请稍后再试");
    }

    // 业务异常降级处理
    public Result<Order> getOrderFallback(Long id, Throwable e) {
        log.error("getOrder 异常降级: id={}", id, e);
        return Result.error(500, "获取订单失败，请稍后再试");
    }
}

// 2. 代码方式定义规则
public class SentinelRules {
    public static void initRules() {
        List<FlowRule> rules = new ArrayList<>();

        // QPS 限流规则
        FlowRule rule = new FlowRule();
        rule.setResource("getOrder");
        rule.setGrade(RuleConstant.FLOW_GRADE_QPS);  // QPS 限流
        rule.setCount(10);  // 每秒最多 10 个
        rule.setLimitApp("default");
        rule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_DEFAULT);
        // CONTROL_BEHAVIOR_DEFAULT → 快速失败
        // CONTROL_BEHAVIOR_WARM_UP → 预热（逐步提升到阈值）
        // CONTROL_BEHAVIOR_RATE_LIMITER → 排队等待
        rules.add(rule);

        // 线程数限流规则
        FlowRule threadRule = new FlowRule();
        threadRule.setResource("createOrder");
        threadRule.setGrade(RuleConstant.FLOW_GRADE_THREAD);  // 线程数限流
        threadRule.setCount(5);  // 最多 5 个线程同时处理
        rules.add(threadRule);

        FlowRuleManager.loadRules(rules);

        // 熔断降级规则
        List<DegradeRule> degradeRules = new ArrayList<>();
        DegradeRule degradeRule = new DegradeRule();
        degradeRule.setResource("getOrder");
        degradeRule.setGrade(RuleConstant.DEGRADE_GRADE_RT);  // 慢调用比例
        degradeRule.setCount(500);    // 响应时间 > 500ms 算慢调用
        degradeRule.setTimeWindow(10);  // 熔断持续 10s
        degradeRule.setMinRequestAmount(10);  // 10 个请求内统计
        degradeRule.setSlowRatioThreshold(0.5);  // 慢调用比例 > 50% 触发熔断
        degradeRules.add(degradeRule);

        DegradeRuleManager.loadRules(degradeRules);
    }
}
```

### 5.3 流控效果详解

```
快速失败（Default）：
  超过阈值立即抛 BlockException
  适用：保护系统不被打垮

Warm Up（预热）：
  初始阈值 = count / coldFactor（默认 3）
  在 warmUpPeriodSec 秒内逐步提高到 count
  适用：秒杀开始前的预热（防止冷系统被瞬间打垮）

排队等待（Rate Limiter）：
  请求排队，匀速通过
  排队超时 timeoutInMs 后放弃
  适用：处理突发流量（脉冲流量平滑化）
```

## 6. 分布式事务

### 6.1 解决方案总览

```
┌─────────────┬────────────┬──────────┬──────────────┐
│ 方案 │ 一致性 │ 性能 │ 实现复杂度 │
├─────────────┼────────────┼──────────┼──────────────┤
│ 2PC │ 强一致 │ 低 │ 中 │
│ TCC │ 强一致 │ 中 │ 高 │
│ Saga │ 最终一致 │ 高 │ 中 │
│ AT (Seata) │ 最终一致 │ 中 │ 低 │
│ 本地消息表 │ 最终一致 │ 高 │ 中 │
│ MQ 事务消息│ 最终一致 │ 高 │ 低 │
│ 最大努力通知│ 最终一致 │ 高 │ 低 │
└─────────────┴────────────┴──────────┴──────────────┘
```

### 6.2 Seata AT 模式原理

```
Seata AT 模式（Auto Transaction）：

角色：
  TC（Transaction Coordinator）- 事务协调器，Seata Server
  TM（Transaction Manager）- 事务管理器，@GlobalTransactional 所在的服务
  RM（Resource Manager）- 资源管理器，每个参与事务的数据库

执行流程（两个阶段）：

阶段一：执行 + 注册 + 提交
  1. TM 向 TC 申请开启全局事务 → 获得 XID
  2. 每个 RM（微服务）的本地事务都提交
     - 业务 SQL 执行
     - 记录 undo log（before-image + after-image）
     - 提交本地事务（是的，第一阶段就提交了！）
     - 向 TC 注册分支事务

阶段二：全局提交或全局回滚
  全部成功：
    TC 通知各 RM → 异步删除 undo log
  有失败：
    TC 通知各 RM → 根据 undo log 回滚（before-image 还原）
    - 如果数据被其他事务修改 → 人工处理

优点：对业务无侵入（跟本地事务一模一样）
缺点：依赖 undo log + 全局锁（性能不如最终一致性方案）
```

### 6.3 Seata TCC 模式

```java
// TCC 模式：业务需要实现 Try、Confirm、Cancel 三个方法
// 优点：强一致性，不依赖 undo log
// 缺点：代码侵入大

public interface AccountTccAction {

    // Try：冻结余额
    @TwoPhaseBusinessAction(name = "debit", commitMethod = "commit", rollbackMethod = "rollback")
    boolean prepareDebit(
        @BusinessActionContextParameter(paramName = "userId") Long userId,
        @BusinessActionContextParameter(paramName = "amount") BigDecimal amount);

    // Confirm：解冻并扣除
    boolean commit(BusinessActionContext context);

    // Cancel：解冻退还
    boolean rollback(BusinessActionContext context);
}

// 注意：
// 1. 需要维护冻结金额字段（freeze_amount）
// 2. Try 阶段做检查和资源预留
// 3. Confirm 简单执行
// 4. Cancel 释放预留资源
// 5. 所有操作需要幂等（Confirm/Cancel 可能被多次调用）
```

### 6.4 MQ 事务消息（RocketMQ）

```
事务消息 = 两阶段提交 + 事务状态回查

适用场景：确保本地事务执行和消息发送同时成功

流程：
  1. 发送 Half 消息（消费者不可见）
  2. 执行本地事务
  3. 本地事务成功 → Commit Half 消息 → 消费者可见
     本地事务失败 → Rollback Half 消息 → 消费者永远看不到
  4. 如果本地事务执行超时（Broker 没收到 Commit/Rollback）
     → Broker 定时回查 Producer 的 checkLocalTransaction()
     → Producer 检查本地事务状态并回复
```

## 7. 分布式链路追踪

### 7.1 核心概念

```
TraceId（Trace ID）：
  全局唯一的请求链路标识
  一个请求从网关到各个微服务，都有同一个 TraceId

SpanId（Span ID）：
  链路中每个操作的标识
  多个 Span 通过 Parent Span ID 形成调用链

Span：
  基本工作单元，包含：
  - 服务名、方法名
  - 开始时间 + 耗时
  - 标签（状态码、URL、SQL）
  - 事件（日志、异常）

上下文传递：
  微服务间通过 HTTP Header 传递 TraceId + SpanId
  常见 Header：
    X-B3-TraceId / X-B3-SpanId / X-B3-Sampled (Zipkin)
    traceparent / tracestate (W3C Trace Context 标准)
    sw8 / sw8-x (SkyWalking)
```

### 7.2 SkyWalking 架构

```
SkyWalking 组件：
  Agent（探针）：
    Java Agent 方式（字节码增强，无侵入）
    自动拦截 HTTP/RPC/DB/Cache 调用
    生成 Trace 数据

  OAP（Observability Analysis Platform）：
    收集 + 分析 + 聚合 Agent 上报的数据
    接收端 + 分析引擎（聚合指标） + 存储接口

  UI（可视化界面）：
    调用链拓扑图
    服务地图
    慢端点/慢 SQL 统计
    告警

SkyWalking 优势：
  1. Java Agent → 零代码侵入
  2. 支持多种语言（Java, .NET, Node.js, Go, Python...）
  3. 支持多种存储（Elasticsearch, H2, MySQL, TiDB）
  4. Apache 顶级项目
```

## 8. 服务网格 (Service Mesh)

### 8.1 概念

```
Service Mesh = Sidecar 模式 + 微服务治理下沉

传统微服务：
  每个微服务自己实现：服务发现、负载均衡、熔断限流、链路追踪...
  → 框架绑定（Spring Cloud vs Dubbo）
  → 代码侵入（引入各种依赖）
  → 多语言难统一

Service Mesh：
  将微服务治理能力下沉到 Sidecar 代理（如 Envoy）
  应用代码只关注业务，不管治理
  ┌──────────┐          ┌──────────┐
  │ 服务 A   │ ←→ Envoy │ 服务 B   │
  │ (业务代码)│   Proxy  │ (业务代码)│
  └──────────┘          └──────────┘
  Envoy 代理处理：负载均衡、服务发现、熔断、限流、追踪、指标

主流的 Service Mesh 实现：
  Istio = Envoy + Pilot + Citadel + Galley + Mixer
  当前非超大集群不推荐自建 Service Mesh（复杂度极高）
```

## 11. 常见面试题深度解析

### Q1: 分布式系统 CAP 定理，实际如何权衡？

```
CAP 只能三选二是个简化的说法，实际上：
  P（分区容错）必须选（网络分区无法避免）
  在 C 和 A 之间做取舍

实际系统：
  注册中心：
    Nacos AP 模式（默认）：允许短暂不一致，保证可用
    Nacos CP 模式：保证一致性，可能短暂不可用

  分布式事务：
    金融：牺牲 A → CP（宁可不服务也不能错账）
    电商：牺牲 C → AP（可以暂时显示库存不准但不能不能下单）

  柔性策略：
    分区期间 → 先保证可用（AP）
    分区恢复 → 异步修复一致性
```

### Q2: Seata AT 模式和 TCC 模式怎么选？

```
AT 模式：
  - 优点：对业务无侵入（跟普通 @Transactional 一样用）
  - 缺点：需要 undo log 表、有全局锁（性能略低）、只支持关系型数据库
  - 适用：关系型数据库、对性能要求不太极致的场景

TCC 模式：
  - 优点：强一致性、不依赖数据库 undo log、可操作非数据库资源
  - 缺点：代码侵入大（需要实现 Try/Confirm/Cancel）、需处理幂等和空回滚
  - 适用：一致性要求高的金融场景、需要操作非数据库资源

Saga 模式：
  - 优点：长事务支持好、无全局锁
  - 缺点：只有最终一致性、补偿回滚需要业务实现
  - 适用：业务流程长（跨多个系统）、老系统改造
```

### Q3: 服务雪崩如何防止？

```
服务雪崩：一个服务故障 → 调用它的服务也故障 → 连累更多服务

三层防护（由外到内）：

1. 限流（入口）
   控制进入系统的流量
   例：Sentinel QPS 限流，超过阈值直接拒绝

2. 熔断（调用链）
   下游故障时快速失败，不继续调
   例：错误率 > 50% 时熔断，后续请求直接走 fallback

3. 降级（保底）
   故障时返回兜底数据或简化逻辑
   例：商品详情页 → 价格服务挂了 → 返回缓存的价格

三板斧：
  限流（自己不被冲垮）+ 熔断（不被下游拖死）+ 降级（故障时有兜底）
```
