## 1. JDBC 底层原理

### 1.1 JDBC 核心组件

```
JDBC (Java Database Connectivity) 是 Java 访问数据库的标准 API

核心接口（java.sql 包）：
┌─────────────────────┬──────────────────────────────────────────┐
│ DriverManager       │ 驱动管理器，注册和获取数据库连接           │
│ Connection          │ 数据库连接（TCP 连接 + 会话）             │
│ Statement           │ SQL 语句对象                              │
│ PreparedStatement   │ 预编译 SQL 语句（防注入 + 性能优化）       │
│ CallableStatement   │ 调用存储过程                              │
│ ResultSet           │ 查询结果集（游标）                         │
│ ResultSetMetaData   │ 结果集元数据（列名/类型等）               │
│ DatabaseMetaData    │ 数据库元数据（表/列/索引等）              │
└─────────────────────┴──────────────────────────────────────────┘
```

### 1.2 JDBC 连接流程（含 SPI 机制）

```java
// JDBC 4.0+（JDK 6+）：不需要 Class.forName() 显式加载驱动
// 原理：DriverManager 通过 SPI（Service Provider Interface）
// 自动加载 META-INF/services/java.sql.Driver 中声明的驱动

// MySQL 8.0 JDBC URL 参数详解
String url = "jdbc:mysql://localhost:3306/mydb"
    + "?useUnicode=true"               // 使用 Unicode 编码
    + "&characterEncoding=utf8mb4"     // 字符编码（支持 emoji）
    + "&useSSL=true"                   // 使用 SSL 连接
    + "&serverTimezone=Asia/Shanghai"  // 时区
    + "&allowPublicKeyRetrieval=true"  // 允许获取公钥
    + "&rewriteBatchedStatements=true" // 批量改写（提高批量插入性能）
    + "&useServerPrepStmts=true"       // 使用服务端预编译
    + "&cachePrepStmts=true"           // 缓存预编译语句
    + "&cacheCallableStmts=true";      // 缓存 CallableStatement
```

### 1.3 PreparedStatement vs Statement

```java
// Statement：简单 SQL 拼接 → 每次都要编译 + 有 SQL 注入风险
Statement stmt = conn.createStatement();
String sql = "SELECT * FROM users WHERE name = '" + inputName + "'";
// 如果 inputName = "'; DROP TABLE users; --"
// 实际执行的 SQL：SELECT * FROM users WHERE name = ''; DROP TABLE users; --'
ResultSet rs = stmt.executeQuery(sql);

// PreparedStatement：预编译 + 参数化查询
// 优势 1：SQL 注入防护（参数值不会作为 SQL 的一部分执行）
// 优势 2：预编译，同一条 SQL 多次执行，数据库不用每次都解析编译
// 优势 3：二进制协议传输参数（比文本协议快）
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE name = ?");
ps.setString(1, inputName);  // 参数转义，安全
ResultSet rs = ps.executeQuery();
```

## 2. 数据库连接池

### 2.1 为什么需要连接池？

```
数据库连接的代价很大：
1. TCP 三次握手（网络开销）
2. 数据库验证（用户名/密码校验）
3. 创建会话（分配内存、设置参数）

连接池 = 预先创建一批连接，用的时候取，用完还回去

解决的核心问题：
- 连接复用：避免创建/销毁的耗时
- 连接数控制：防止连接数过多拖垮数据库
- 泄漏保护：超时未归还自动回收
- 健康检查：剔除不可用的连接
```

### 2.2 主流连接池对比

| 连接池 | 性能 | 功能 | 监控 | Spring Boot 默认 |
|--------|------|------|------|-----------------|
| **HikariCP** | ⭐⭐⭐⭐⭐ | 基础 | 基础 | ✅ (2.x+) |
| **Druid** | ⭐⭐⭐⭐ | 丰富 | ⭐⭐⭐⭐⭐ | ❌ (需手动配置) |
| **Tomcat CP** | ⭐⭐⭐ | 基础 | 无 | 1.x 默认 |
| **DBCP2** | ⭐⭐⭐ | 中等 | 基础 | ❌ |
| **C3P0** | ⭐⭐ | 中等 | 基础 | ❌ (已不活跃) |

### 2.3 HikariCP 配置详解

```yaml
# HikariCP 为什么快？
# 1. 字节码级优化（生成字节码替代反射调用，如 ProxyConnection）
# 2. 使用 ConcurrentBag（自定义无锁并发集合）替代 LinkedBlockingQueue
# 3. 使用 FastList 替代 ArrayList（更少的 rangeCheck）

spring:
  datasource:
    hikari:
      pool-name: MyPool               # 连接池名字（便于 JMX 监控区分）
      minimum-idle: 10                # 最小空闲连接数（默认 = maximum-pool-size）
      maximum-pool-size: 20           # 最大连接数（包含 idle + active）
      idle-timeout: 600000            # 空闲连接超时（10min，超过最小闲置则回收）
      max-lifetime: 1800000           # 连接最大存活时间（30min，应 < 数据库 wait_timeout）
      connection-timeout: 30000       # 获取连接等待超时（30s 后抛 SQLException）
      connection-test-query: SELECT 1 # 连接有效性验证 SQL
      validation-timeout: 5000        # 验证超时（JDBC 4.0 驱动可用 isValid 替代）
      leak-detection-threshold: 60000 # 泄漏检测阈值（60s，开发时可开）
      keepalive-time: 0               # 保活时间（0=不保活，建议 30000~60000）

# 最大连接数怎么设置？
# 公式：connections = ((core_count * 2) + effective_spindle_count)
# 但更实用的方法：
# 1. 数据库端：SHOW VARIABLES LIKE 'max_connections'; → 确保连接池数 < 数据库最大连接数
# 2. 假设部署 N 个服务实例，则 pool_size <= db_max_connections / N - 预留
# 3. 压测找到最优值（TPS 不再增长时为拐点）
```

### 2.4 Druid 配置详解

```yaml
# Druid（阿里巴巴开源）
# 优势：内置 SQL 监控、Web 控制台、防火墙、慢 SQL 记录

spring:
  datasource:
    druid:
      # 基础配置（同 HikariCP）
      initial-size: 5
      min-idle: 5
      max-active: 20
      max-wait: 60000
      # 检测
      test-while-idle: true
      test-on-borrow: false
      test-on-return: false
      validation-query: SELECT 1
      # 回收
      time-between-eviction-runs-millis: 60000  # 检测间隔
      min-evictable-idle-time-millis: 300000    # 最小空闲存活时间
      # 过滤器
      filters: stat,wall,slf4j   # stat=监控统计, wall=SQL防火墙, slf4j=日志
      # Web 监控（StatViewServlet）
      stat-view-servlet:
        enabled: true
        url-pattern: /druid/*
        login-username: admin
        login-password: admin
      # Web 过滤器（WebStatFilter）
      web-stat-filter:
        enabled: true
        url-pattern: /*
        exclusions: "*.js,*.gif,*.jpg,*.png,*.css,*.ico,/druid/*"

# Druid vs HikariCP 选型建议：
# - 默认用 HikariCP（Spring Boot 官方推荐，性能最优）
# - 需要 SQL 监控、慢 SQL 分析 → 用 Druid
# - 银行/金融等对 SQL 安全要求严格的 → 用 Druid（内置 SQL 防火墙）
# - 可以两者都引入依赖，Druid 作为数据源，HikariCP 部分场景使用
```

## 3. MyBatis 深度剖析

### 3.1 工作原理

```
MyBatis 执行流程（从调用到返回）：

Java 代码调用 Mapper 接口方法
    ↓
1. MapperProxy（JDK 动态代理）
   → 拦截接口方法调用，转交给 SqlSession
    ↓
2. SqlSession
   → 获取 MappedStatement（XML 中 <select>/<insert> 等的解析结果）
   → 具体执行委托给 Executor
    ↓
3. Executor
   → SimpleExecutor / ReuseExecutor / BatchExecutor
   → 一级缓存判断（默认开启）
   → 调用 StatementHandler
    ↓
4. StatementHandler
   → 调用 ParameterHandler 设置参数（#{} 占位符赋值）
   → 调用 JDBC PreparedStatement
   → 数据库执行 SQL → 返回 ResultSet
    ↓
5. ResultSetHandler
   → 将 JDBC ResultSet 映射为 Java 对象
   → ResultMap / 自动映射（下划线转驼峰等）
    ↓
6. 返回给调用者
   → 一级缓存存储结果
   → 返回映射后的 Java 对象
```

### 3.2 核心配置详解

```xml
<!-- MyBatis 全局配置 mybatis-config.xml（或通过 Spring Boot 配置） -->
<configuration>
    <!-- 属性：加载外部配置 -->
    <properties resource="db.properties"/>

    <!-- 设置 -->
    <settings>
        <!-- 下划线自动转驼峰：user_name → userName -->
        <setting name="mapUnderscoreToCamelCase" value="true"/>
        <!-- 懒加载（按需加载关联对象，默认 false） -->
        <setting name="lazyLoadingEnabled" value="true"/>
        <setting name="aggressiveLazyLoading" value="false"/>
        <!-- 日志实现：SLF4J | LOG4J | STDOUT_LOGGING -->
        <setting name="logImpl" value="SLF4J"/>
        <!-- 启用二级缓存（默认 true，但 Mapper XML 中还要配 <cache/>） -->
        <setting name="cacheEnabled" value="true"/>
        <!-- 允许在 SQL 中使用 "user" 等保留字作为参数名 -->
        <setting name="useActualParamName" value="true"/>
    </settings>

    <!-- 类型别名（包扫描，类名首字母小写作为别名） -->
    <typeAliases>

    </typeAliases>

    <!-- 插件（拦截器） -->
    <plugins>
        <plugin interceptor="com.github.pagehelper.PageInterceptor">
            <property name="helperDialect" value="mysql"/>
        </plugin>
    </plugins>

    <!-- 环境（数据库连接） -->
    <environments default="dev">
        <environment id="dev">
            <transactionManager type="JDBC"/>
            <dataSource type="POOLED">
                <property name="driver" value="com.mysql.cj.jdbc.Driver"/>
                <property name="url" value="jdbc:mysql://localhost:3306/mydb"/>
                <property name="username" value="root"/>
                <property name="password" value="123456"/>
            </dataSource>
        </environment>
    </environments>

    <!-- SQL 映射文件 -->
    <mappers>
        <package name="com.example.mapper"/>
    </mappers>
</configuration>
```

### 3.3 缓存机制

```
MyBatis 两级缓存：

一级缓存（默认开启，SqlSession 级别）：
  - 同一个 SqlSession 内，相同的查询只执行一次 SQL
  - 作用域：SqlSession（通常对应一次数据库事务）
  - 何时清空？commit、close、执行 update/delete/insert
  - 可以通过 clearCache() 手动清空
  - 无法跨 SqlSession 共享
  - 注意：Spring 整合后每次查询都新建 SqlSession，
    因此一级缓存在 Spring 中基本不生效！

二级缓存（需要配置，Mapper 级别）：
  - 不同 SqlSession 之间共享（同一个 namespace）
  - 配置方式：
    1. mybatis-config.xml：<setting name="cacheEnabled" value="true"/>
    2. Mapper XML 中加 <cache/> 或 <cache-ref namespace="..."/>
    3. 实体类实现 Serializable
  - 何时清空？同一个 namespace 下有任何写操作时清空
  - 问题：
    - 分布式部署时，多个实例的 MyBatis 二级缓存无法互通 → 数据不一致
    - 跨 namespace 的关联查询（一个 Mapper 查另一个 Mapper 的表）无法感知
  - 建议：生产环境禁用 MyBatis 二级缓存！
    用 Redis 等分布式缓存替代
```

### 3.4 插件机制（四大拦截器）

```java
// MyBatis 插件基于责任链模式 + 动态代理
// 可以拦截四大核心对象的方法：

// 1. Executor（拦截 SQL 执行）
@Intercepts(@Signature(type = Executor.class, method = "update",
    args = {MappedStatement.class, Object.class}))
public class SqlCostInterceptor implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return invocation.proceed();
        } finally {
            long cost = System.currentTimeMillis() - start;
            if (cost > 1000) {
                MappedStatement ms = (MappedStatement) invocation.getArgs()[0];
                log.warn("慢SQL: {} 耗时: {}ms", ms.getId(), cost);
            }
        }
    }
}

// 2. ParameterHandler（拦截参数设置）
// 3. ResultSetHandler（拦截结果集处理）
// 4. StatementHandler（拦截 SQL 语句构建 - 最常用）
//    可以修改 SQL（如分页插件 PageHelper 就在这层改写 SQL）
```

```xml

            <foreach collection="deptIds" item="deptId" open="(" close=")" separator=",">

        </if>
        <if test="endTime != null">

        </if>
    </where>
    <choose>
        <when test="orderBy == 'name'">ORDER BY user_name</when>
        <when test="orderBy == 'time'">ORDER BY create_time DESC</when>
        <otherwise>ORDER BY id DESC</otherwise>
    </choose>
</select>
```

## 4. MyBatis-Plus 企业实践

### 4.1 MyBatis-Plus 架构优势

```
MyBatis-Plus 不是 MyBatis 的替代品，而是增强工具

核心能力：
1. 通用 CRUD：BaseMapper 提供 17 个常用方法，不用写 SQL
2. 条件构造器：LambdaQueryWrapper / LambdaUpdateWrapper，类型安全
3. 分页插件：物理分页，简单配置即可使用
4. 逻辑删除：@TableLogic 注解，删除变更新
5. 自动填充：@TableField(fill = ...) 自动填充创建时间/更新时间
6. 乐观锁插件：@Version 注解，更新时自动做版本号校验
7. 主键策略：雪花算法主键（默认）、自增、UUID
8. 代码生成器：根据数据库表自动生成 Entity/Mapper/Service/Controller
```

### 4.2 条件构造器详解

```java
// LambdaQueryWrapper — 类型安全（用的 Lambda 表达式，字段名写错编译报错）
List<User> users = userMapper.selectList(
    new LambdaQueryWrapper<User>()
        .eq(User::getStatus, 1)                             // = 
        .ne(User::getType, 3)                               // !=
        .gt(User::getAge, 18)                               // > 
        .ge(User::getScore, 60)                             // >=
        .lt(User::getAge, 60)                               // <
        .le(User::getScore, 100)                            // <=
        .like(User::getName, "张")                          // LIKE '%张%'
        .likeLeft(User::getName, "张")                      // LIKE '%张'
        .likeRight(User::getName, "张")                     // LIKE '张%'
        .in(User::getDeptId, Arrays.asList(1, 2, 3))
        .between(User::getCreateTime, start, end)
        .isNull(User::getAvatar)                            // IS NULL
        .isNotNull(User::getEmail)                           // IS NOT NULL
        .orderByDesc(User::getCreateTime)
        .last("LIMIT 100")                                  // 最后拼接（慎用）
);

// LambdaQueryWrapper 执行 OR 条件
new LambdaQueryWrapper<User>()
    .eq(User::getStatus, 1)
    .and(w -> w.eq(User::getName, "张三").or().eq(User::getName, "李四"));
// WHERE status = 1 AND (name = '张三' OR name = '李四')

// LambdaUpdateWrapper — 条件更新
userMapper.update(null, new LambdaUpdateWrapper<User>()
    .set(User::getStatus, 2)
    .eq(User::getId, 1));

// 选择只查部分字段
userMapper.selectList(new LambdaQueryWrapper<User>()
    .select(User::getId, User::getName)  // SELECT id, name FROM user
    .eq(User::getStatus, 1));
```

### 4.3 分页插件

```java
// 2. 使用分页
```

### 4.4 常用注解

```java
@Data
@TableName("t_user")  // 指定表名（默认驼峰转下划线）
public class User {
    @TableId(type = IdType.ASSIGN_ID)  // 主键策略：雪花算法（默认）
    private Long id;

    @TableField("user_name")  // 指定数据库字段名（默认驼峰转下划线）
    private String userName;

    @TableField(select = false)  // 查询时排除此字段（如大字段 text）
    private String bio;

    @TableField(exist = false)  // 不是数据库字段（Java 辅助字段）
    private String deptName;

    @TableLogic  // 逻辑删除（0=未删除，1=已删除）
    private Integer deleted;

    @Version  // 乐观锁版本号
    private Integer version;

    @TableField(fill = FieldFill.INSERT)  // 插入时自动填充
    private LocalDateTime createTime;

    @TableField(fill = FieldFill.INSERT_UPDATE)  // 插入和更新时自动填充
    private LocalDateTime updateTime;
}
```

## 5. JPA / Hibernate / Spring Data JPA

### 5.1 三者的关系

```
JPA (Java Persistence API)：
  → 一套 ORM 规范/标准（Jakarta Persistence），只定义接口和注解
  → 不包含具体实现

Hibernate：
  → JPA 规范最主流的实现
  → 也是最早的 ORM 框架（先有 Hibernate，后有 JPA）
  → 提供 JPA 标准之外的功能（如 HQL、Criteria、缓存策略）

Spring Data JPA：
  → Spring 对 JPA 的进一步封装
  → 提供声明式查询（方法名即查询）
  → 提供 JpaRepository 等通用接口
  → 底层仍然使用 Hibernate（或其他 JPA 实现）
```

### 5.2 实体状态与生命周期

```
JPA Entity 的四种状态：

transient（瞬时态）
  new User() — 刚 new 出来的对象，跟数据库无关
     ↓ persist() / merge()
managed（持久态/托管态）
  被 EntityManager 管理，任何修改会被自动同步到数据库（脏检查）
     ↓ EntityManager.close() / clear() / detach()
detached（游离态）
  曾经是持久态，但 EntityManager 已关闭
     ↓ merge()  — 重新绑定到当前 EntityManager
  managed
     ↓ remove()
removed（删除态）
  标记为删除，事务提交时执行 DELETE
     ↓ 事务提交
  回到 transient（数据库中不存在了）
```

### 5.3 核心注解

```java
@Entity
@Table(name = "t_user",
       indexes = {@Index(name = "idx_name", columnList = "name")})  // 创建索引
@Data
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // 主键自增
    private Long id;

    // 字段映射

    private String userName;

    @Enumerated(EnumType.STRING)  // 枚举类型，STRING=存名字, ORDINAL=存序号(不推荐)
    private UserStatus status;

    @Lob  // 大对象（对应数据库 BLOB/TEXT）
    private byte[] avatar;

    @Transient  // 非数据库字段
    private String tempData;

    // 关联关系
    @ManyToOne(fetch = FetchType.LAZY)  // 多对一（默认 EAGER → 性能隐患！）
    @JoinColumn(name = "dept_id", foreignKey = @ForeignKey(ConstraintMode.NO_CONSTRAINT))
    private Dept dept;

    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Order> orders;

    @ManyToMany
    @JoinTable(name = "user_role",
        joinColumns = @JoinColumn(name = "user_id"),
        inverseJoinColumns = @JoinColumn(name = "role_id"))
    private Set<Role> roles;

    // 审计字段
    @CreatedDate
    private LocalDateTime createTime;

    @LastModifiedDate
    private LocalDateTime updateTime;

    // 乐观锁
    @Version
    private Integer version;
}

// FetchType（抓取策略）
// EAGER：立即加载（默认，JOIN 查询）
//   → 问题：查询 User 时自动 JOIN Dept 和 Orders，结果集爆炸（笛卡尔积）

//   → 需要在事务内使用，否则抛 LazyInitializationException
```

### 5.5 N+1 问题与解决方案

```
什么是 N+1 问题？
  查询出 N 个 User（1 次查询）
  → 遍历 User 获取 Dept（每个 User 触发 1 次 SQL → N 次）
  → 总共 N+1 次 SQL

解决方案：

方案 1：JOIN FETCH
  @Query("SELECT u FROM User u JOIN FETCH u.dept WHERE u.status = :status")
  一次 SQL JOIN 全部查出，但注意：
  - 同时 FETCH 多个 @OneToMany 会产生笛卡尔积
  - 分页 + FETCH 需要在内存中分页（先查所有），性能差

方案 2：@EntityGraph
  @EntityGraph(attributePaths = {"dept", "roles"})
  @Query("SELECT u FROM User u WHERE u.status = :status")
  List<User> findByStatus(@Param("status") int status);

方案 3：批量抓取（batch fetch）
  spring.jpa.properties.hibernate.default_batch_fetch_size=100
  用户查询 → N 个 User → 一次查所有 Dept（WHERE id IN (...全部 dept_ids...)）
  将 N+1 降为 1+1

方案 4：DTO 投影（推荐，性能最好）
  @Query("SELECT new com.example.dto.UserWithDeptDTO(u.id, u.name, d.name) " +
         "FROM User u LEFT JOIN u.dept d")
  直接用 DTO 承载结果，不涉及懒加载
```

## 7. MySQL 核心原理

### 7.1 架构层次

```
┌─────────────────────────────────────────────────────────┐
│                    客户端/连接层                          │
│   连接处理 → 身份验证 → 线程处理                          │
├─────────────────────────────────────────────────────────┤
│                     服务层                               │
│   查询缓存(8.0已废弃) → 解析器 → 预处理器 → 优化器        │
│   内置函数（日期/数学/加密/聚合...）                      │
├─────────────────────────────────────────────────────────┤
│                     引擎层（可插拔）                      │
│   InnoDB | MyISAM | Memory | Archive | ...              │
├─────────────────────────────────────────────────────────┤
│                     存储层                               │
│   文件系统（数据文件、日志文件）                           │
└─────────────────────────────────────────────────────────┘

查询执行流程：
SQL 文本 → 连接器 → 分析器(词法/语法) → 优化器(执行计划)
→ 执行器 → 存储引擎 → 返回结果

注意：MySQL 8.0 移除了查询缓存功能
原因：查询缓存失效太频繁（表有更新就清空），在并发场景成为瓶颈
```

### 7.2 InnoDB 存储引擎核心

```
为什么 InnoDB 是 MySQL 5.5.5+ 的默认引擎？

1. 支持事务（ACID）
2. 行级锁 + MVCC → 高并发
3. 聚集索引（数据按主键顺序存储）→ 主键查询快
4. 支持外键
5. 崩溃恢复（Redo Log + Undo Log）
6. 缓冲池（Buffer Pool）→ 数据缓存在内存

MyISAM 对比（仅用于了解，生产不推荐）：
- 不支持事务
- 表级锁 → 并发写性能差
- 不支持外键
- 崩溃后恢复困难
- 曾经优势：全文索引、压缩表（InnoDB 现已支持）
```

### 7.3 索引

#### B+Tree 为什么适合数据库索引？

```
B+Tree vs B-Tree vs 二叉树 vs Hash：

二叉树：
  - 2 叉 → 树太高 → 磁盘 IO 次数多
  - 极端情况退化为链表（需要旋转平衡 → 红黑树/AVL）

B-Tree：
  - 多叉 → 矮胖 → 减少磁盘 IO
  - 非叶子节点也存数据 → 相同高度下存的键更少

B+Tree（InnoDB 的选择）：
  1. 非叶子节点只存键（不存数据），一个节点能存更多键 → 更矮
  2. 叶子节点通过双向链表连接 → 范围查询直接遍历链表，不用回溯
  3. 每次查询的 IO 次数 ≈ 树的高度（通常 3~4 层就能索引 千万级数据）
  4. 叶子节点存完整数据（聚簇索引）或主键值（二级索引）

Hash 索引（Memory 引擎 / InnoDB 自适应 Hash）：
  - 等值查询 O(1)，极快
  - 不支持范围查询 / 排序 / 最左前缀
  - 冲突多时退化为 O(n)
  - InnoDB 自适应 Hash 索引：由 InnoDB 自动创建，用户不可控
```

#### 聚簇索引 vs 二级索引

```
聚簇索引（Clustered Index = 主键索引）：
  B+Tree 叶子节点 = 完整的数据行
  一个表只有一个（数据只能按一种顺序存放）
  - 有主键 → 主键是聚簇索引
  - 无主键 → 找第一个唯一非空索引
  - 都没有 → 自动生成隐藏的 row_id（6 字节）

二级索引（Secondary Index = 非聚簇索引/辅助索引）：
  B+Tree 叶子节点 = 主键值（不是完整数据）
  查找流程：在二级索引找到主键 → 再到聚簇索引查完整数据 = 回表

回表优化 — 覆盖索引（Covering Index）：
  如果查询的列都在索引中 → 不需要回表
  SELECT id, name FROM user WHERE name = '张三';
  索引：idx_name (name) → name 的叶子存了主键 id → 不需要回表！
  EXPLAIN Extra 列：Using index（覆盖索引）
```

### 7.4 事务与 MVCC

```sql
-- 事务隔离级别
-- 查看当前隔离级别
SELECT @@transaction_isolation;  -- 8.0 (旧版用 @@tx_isolation)

-- 设置隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 各隔离级别的实现原理：

-- READ UNCOMMITTED（几乎不用）
--   不加锁，读最新数据（不管是否已提交）
--   脏读：读到其他事务未提交的数据

-- READ COMMITTED（Oracle 默认）
--   每次 SELECT 创建新的 ReadView → 读到其他事务已提交的数据
--   解决脏读
--   不可重复读：同一事务两次 SELECT 读到不同数据（因为 ReadView 会更新）
--   实现：普通 SELECT 是快照读（MVCC 无锁）；SELECT ... FOR UPDATE 是当前读

-- REPEATABLE READ（MySQL 默认）
--   事务开始时创建 ReadView，整个事务复用同一个
--   解决脏读 + 不可重复读
--   普通 SELECT 始终看到事务开始时的数据 → 可重复读
--   幻读：第一次 SELECT 没有某数据，INSERT 时报重复（理论上存在）
--   但 InnoDB 用 Next-Key Lock 在大部分场景避免了幻读

-- SERIALIZABLE（最高隔离级别，几乎不用）
--   读加共享锁，写加排他锁 → 串行执行
--   解决所有问题，但并发性能极差
```

#### MVCC（Multi-Version Concurrency Control）原理

```
InnoDB 每行数据有两个隐藏列：
  DB_TRX_ID（6字节）：最近修改（insert/update）这行的事务 ID
  DB_ROLL_PTR（7字节）：回滚指针，指向 undo log 中的上一版本
  如果有主键 → 还隐式包含 DB_ROW_ID（6字节）

undo log（回滚日志）：
  记录了数据修改前的旧版本
  不同的 undo log 通过 DB_ROLL_PTR 形成版本链
  MVCC 通过版本链在不同时间点看到不同的数据

ReadView（读视图）：
  包含当前活跃事务 ID 列表 + 最小活跃事务 ID + 下一个待分配事务 ID

  可见性规则：对于某行数据（DB_TRX_ID = trx_id）
  1. trx_id == 当前事务 ID → 可见（自己修改的）
  2. trx_id < min_up_limit_id → 可见（事务在当前 ReadView 创建前就提交了）
  3. trx_id >= max_low_limit_id → 不可见（事务在当前 ReadView 创建后才开始）
  4. trx_id 在活跃列表中 → 不可见（事务未提交）
  5. 否则 → 可见

这就是为什么：
  - REPEATABLE READ 能避免不可重复读
    → 整个事务在第一次 SELECT 时创建一个 ReadView，后续都用它
  - READ COMMITTED 不能避免
    → 每次 SELECT 都创建新 ReadView，能看到其他事务提交的修改
```

### 7.5 锁机制

```
InnoDB 锁分类：

按锁的颗粒度：
  表锁：LOCK TABLE ... READ/WRITE
  行锁：InnoDB 默认，通过索引实现（锁的是索引记录，不是行！）
    如果没走索引 → 退化为表锁！

按锁的模式：
  共享锁（S 锁，读锁）：允许其他事务读，不允许写
    SELECT ... LOCK IN SHARE MODE（8.0 改为 SELECT ... FOR SHARE）
  排他锁（X 锁，写锁）：不允许其他事务读写
    SELECT ... FOR UPDATE
    INSERT / UPDATE / DELETE 自动加 X 锁

按锁的算法（行锁的三种实现）：
  Record Lock：锁定单个索引记录
    SELECT * FROM user WHERE id = 1 FOR UPDATE
    锁住 id=1 这条记录

  Gap Lock：锁定索引记录之间的间隙（开区间）
    SELECT * FROM user WHERE id > 5 AND id < 10 FOR UPDATE
    锁住 (5, 10) 之间的间隙，不允许插入 id 在其中的记录
    只在 REPEATABLE READ 级别下生效

  Next-Key Lock：Record Lock + Gap Lock（左开右闭）
    SELECT * FROM user WHERE id = 8 FOR UPDATE
    锁住 (5, 8] + (8, 10) = (5, 10)
    解决幻读的主要手段

死锁检测：
  InnoDB 自动检测死锁（等待图），选择回滚代价最小的事务
  或通过 innodb_lock_wait_timeout（默认 50s）超时回滚

  避免死锁的建议：
  1. 保持事务短小
  2. 固定加锁顺序（先锁 A 再锁 B，不要反过来）
  3. 尽量用索引（避免行锁变表锁）
  4. 大事务拆分
```

## 8. SQL 优化实战

### 8.1 EXPLAIN 详解

```sql
EXPLAIN SELECT * FROM user WHERE name = '张三' AND age > 20;

-- 核心列解读（按重要性排序）：

-- type（访问类型，越靠前越好）：
--   system  → 表只有一行（系统表）
--   const   → 主键/唯一索引等值查询，最多返回一行
--   eq_ref  → JOIN 时被驱动表走主键/唯一索引
--   ref     → 非唯一索引等值查询
--   range   → 索引范围扫描（<, >, BETWEEN, IN）
--   index   → 全索引扫描（比 ALL 快，因为索引文件小）
--   ALL     → 全表扫描（必须优化！）

-- key（实际使用的索引）
--   NULL → 没走索引

-- rows（估计要扫描的行数）
--   越少越好

-- Extra（额外信息，重要！）：
--   Using index  → 覆盖索引（不回表，最优！）
--   Using where  → 使用了 WHERE 过滤
--   Using index condition → 索引下推（ICP: Index Condition Pushdown）
--       存储引擎层先按索引条件过滤，减少回表 → 比传统方式快
--   Using filesort → 文件排序（需要优化！说明 ORDER BY 没用到索引）
--   Using temporary → 使用临时表（需要优化！说明 GROUP BY 没用到索引）
--   Using join buffer → JOIN 条件没走索引（需要优化！）
```

### 8.2 索引失效场景汇总

```sql
-- 索引失效的 11 种常见情况：

-- 1. LIKE 前置模糊
    WHERE name LIKE '%三'     -- 索引失效
    WHERE name LIKE '张%'     -- 走索引

-- 2. 索引列上使用函数
    WHERE DATE(create_time) = '2024-01-01'  -- 索引失效
    WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'  -- 走索引

-- 3. 索引列上做运算
    WHERE age + 10 = 30       -- 索引失效
    WHERE age = 20            -- 走索引

-- 4. 隐式类型转换
    -- phone 是 varchar 类型
    WHERE phone = 13800138000   -- 索引失效（字符串和数字比较，MySQL 会把字符串转数字）
    WHERE phone = '13800138000' -- 走索引

-- 5. OR 条件两边都有索引才生效
    -- name 有索引，age 无索引
    WHERE name = '张三' OR age = 20  -- 索引可能失效
    -- 解决：UNION ALL 拆分
    SELECT * FROM user WHERE name = '张三'
    UNION ALL
    SELECT * FROM user WHERE age = 20 AND name != '张三'

-- 6. IS NULL / IS NOT NULL（看情况）
    -- 索引列允许 NULL 时，IS NULL 可能走索引，IS NOT NULL 可能不走

-- 7. NOT IN / NOT EXISTS
    WHERE id NOT IN (SELECT user_id FROM blacklist)  -- 大概率不走

-- 8. ORDER BY 不满足最左前缀或混用 ASC/DESC
    -- 联合索引 (a, b)
    ORDER BY b       -- 不走
    ORDER BY a, b    -- 走
    ORDER BY a ASC, b DESC  -- 8.0+ 支持降序索引，之前不走

-- 9. 联合索引范围查询右边失效
    -- 联合索引 (a, b, c)
    WHERE a = 1 AND b > 5 AND c = 3
    -- c 走不到索引（范围查询 b > 5 后，c 无序）

-- 10. 区分度太低
    WHERE gender = 'M'   -- 只有男女两个值，MySQL 优化器可能放弃索引选全表扫描

-- 11. JOIN 关联字段字符集/排序规则不一致
    -- 不同编码的表 JOIN，索引失效
```

### 8.3 慢查询优化流程

```
1. 开启慢查询日志
   SET GLOBAL slow_query_log = ON;
   SET GLOBAL long_query_time = 1;  -- 超过 1 秒记录
   SET GLOBAL log_queries_not_using_indexes = ON;  -- 记录未走索引的查询

2. 使用 mysqldumpslow 分析慢查询日志
   mysqldumpslow -s c -t 10 /var/log/mysql-slow.log
   # -s c: 按次数排序，-t 10: Top 10

3. 对慢查询 SQL 执行 EXPLAIN

4. 根据 EXPLAIN 结果优化：
   a. type = ALL → 加索引
   b. Extra = Using filesort → 优化 ORDER BY
   c. Extra = Using temporary → 优化 GROUP BY / DISTINCT
   d. rows 太大 → 加更精准的索引
   e. 大量 JOIN → 考虑冗余字段或 ES

5. 使用 profiling 查看各阶段耗时
   SET profiling = ON;
   SHOW PROFILES;
   SHOW PROFILE FOR QUERY 1;
```

### 8.4 企业级 SQL 优化案例

```sql
-- 案例 1：分页优化（深分页）
-- 慢：OFFSET 大时，MySQL 需要扫描前 100010 条数据并丢弃前 100000 条
SELECT * FROM orders ORDER BY id LIMIT 100000, 10;
-- 优化（游标分页）：
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 10;
-- 或子查询优化：
SELECT * FROM orders WHERE id >= (SELECT id FROM orders ORDER BY id LIMIT 100000, 1)
ORDER BY id LIMIT 10;

-- 案例 2：COUNT 优化
-- 慢：COUNT(*) 走全表扫描
SELECT COUNT(*) FROM orders WHERE status = 1;
-- 优化 1：覆盖索引
ALTER TABLE orders ADD INDEX idx_status (status);
-- 优化 2：汇总表（维护一张统计表）
CREATE TABLE order_stats (status INT PRIMARY KEY, cnt INT);
-- 定时刷新或用触发器更新

-- 案例 3：批量插入优化
-- 慢：逐条 INSERT（每条一次网络往返 + 事务提交）
INSERT INTO user (name) VALUES ('张三');
INSERT INTO user (name) VALUES ('李四');
-- 优化：批量 INSERT
INSERT INTO user (name) VALUES ('张三'), ('李四'), ('王五');
-- 或 JDBC URL 加 rewriteBatchedStatements=true，用 addBatch() + executeBatch()

-- 案例 4：大表 DDL 优化
-- 慢：直接 ALTER TABLE 锁表
ALTER TABLE big_table ADD COLUMN new_col VARCHAR(100);
-- 优化：使用 pt-online-schema-change（Percona Toolkit）
-- 原理：创建新表 → 触发器同步增量 → 分批拷贝数据 → 原子切换
```

## 9. 分库分表方案设计

### 9.1 拆分策略

```
垂直拆分（Vertical Split）：
  垂直分库：按业务模块拆到不同的库
    user_db（用户服务）→ t_user, t_user_profile, t_user_address
    order_db（订单服务）→ t_order, t_order_item, t_order_log
    优点：业务清晰、独立扩展、故障隔离
    缺点：跨库 JOIN 不可能（需要服务层拼接）

  垂直分表：同一库中把宽表拆成多张
    t_user_base（id, name, age）  ← 常用字段
    t_user_detail（id, bio, avatar, setting_json） ← 大字段/不常用字段
    优点：减少单行数据大小，提高缓存命中率
    ID 使用相同的，不需要分片键

水平拆分（Horizontal Split）：
  水平分表：按行拆分到同一个库的不同表
    t_order_0, t_order_1, t_order_2, ..., t_order_15（共 16 张表）
  
  水平分库分表：按行拆分到不同库的不同表
    库 0 → t_order_0 ... t_order_15
    库 1 → t_order_0 ... t_order_15
    （共 2 库 × 16 表 = 32 张表）
```

### 9.2 分片算法

```java
// 分片键（Sharding Key）选择原则：
// 1. 查询最频繁的字段（用户 ID、订单 ID）
// 2. 数据分布均匀（避免热点）
// 3. 大部分查询能带上分片键（否则需要全库全表扫描）

// 分片算法：

// 1. 取模（最常用）
// 分片 = id % N
// 优点：数据均匀、实现简单
// 缺点：扩容难（N 变了，需要迁移数据）

// 2. 范围分片
// 分片 = id / 1000000（按 100 万为一段）
// 优点：扩容方便（新范围自动到新分片）
// 缺点：可能热点（最新数据集中在一个分片）

// 3. 一致性 Hash
// 优点：扩容时只需迁移小部分数据
// 缺点：实现复杂度高

// 4. 复合分片
// 先按时间分库（如按年），再按 user_id 取模分表
// 适合有时间属性的数据（如订单、日志）

// 5. 基因法（解决"用 user_id 查订单"但分片键是 order_id）
// user_id 最后 N 位拼接到 order_id 中，这样 order_id 包含了 user_id 的信息
```

### 9.3 ShardingSphere 实战

```yaml
# ShardingSphere-JDBC 配置（Spring Boot）
spring:
  shardingsphere:
    datasource:
      names: ds0, ds1    # 两个数据源
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/db0
        username: root
        password: root
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/db1
        username: root
        password: root

    rules:
      sharding:
        # 分片规则
        tables:
          t_order:
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..15}  # 2库×16表=32张表
            # 分库策略
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: database-inline
            # 分表策略
            table-strategy:
              standard:
                sharding-column: order_id
                sharding-algorithm-name: table-inline
            # 分布式主键
            key-generate-strategy:
              column: id
              key-generator-name: snowflake

        # 分片算法
        sharding-algorithms:
          database-inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{user_id % 2}
          table-inline:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 16}

        # 绑定表（关联表使用相同的分片规则，避免跨库 JOIN）
        binding-tables:
          - t_order, t_order_item

        # 广播表（每个库都有的全量表，如字典表）
        broadcast-tables:
          - t_config

    props:
      sql-show: true  # 打印分片后的 SQL
```

### 9.4 分库分表面临的问题

```
1. 分布式 ID
   → 雪花算法 / Leaf / 数据库号段

2. 跨库 JOIN
   → 应用层拼接 / 冗余存储 / 全局表（广播表）

3. 跨库事务
   → Seata AT 模式 / 最终一致性 / 避免跨分片事务

4. 排序分页
   → 每个分片查询 N+offset 条，内存归并排序
   → 深分页性能差（几乎不可行），推荐游标分页

5. COUNT 聚合
   → 汇总表（定时统计） / 异步更新 / 估算（HyperLogLog）

6. 扩容迁移
   → 停机迁移（最简单）
   → 双写方案（逐步切换）
   → 使用一致性 Hash 减少迁移量
```

## 10. 分布式 ID 生成方案

### 10.1 方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **UUID** | 随机 128 位 | 简单、无中心 | 无序→索引分裂；占空间大 | 非主键的场景 |
| **自增 ID** | 数据库自增 | 简单、递增 | 单点、不适合分布式 | 单库系统 |
| **雪花算法** | 时间戳+机器+序号 | 递增、高性能 | 依赖时钟 | 主流方案 |
| **号段模式** | 批量取号 | 无时钟依赖 | 需额外服务 | Leaf-segment |
| **Redis INCR** | Redis 原子自增 | 简单快速 | 需持久化保证 | 中等规模 |

### 10.2 雪花算法详解

```
Snowflake（Twitter 开源）ID 结构（64 bits）：

┌─┬──────────────────────────────────────────┬───────────┬────────────┐
│0│        41 bits 时间戳（毫秒）             │10 bits 机器│12 bits 序列 │
│ │         可用 69 年                       │  支持 1024  │ 每 ms 4096  │
│ │                                         │  台机器    │  个 ID      │
└─┴──────────────────────────────────────────┴───────────┴────────────┘

优点：
  - 趋势递增（时间戳在高位）
  - 本地生成，无网络开销
  - 每秒理论生成 409.6 万 个 ID

问题：时钟回拨
  - NTP 时钟同步导致时间倒退
  - 解决：回拨时 ①等待时钟追上 ②使用备用 workerId ③抛异常

美团的 Leaf 方案：
  Leaf-segment：号段模式，数据库维护 (biz_tag, max_id, step)，批量取号
  Leaf-snowflake：用 ZooKeeper 持久顺序节点注册 workerId，解决时钟回拨
```

## 13. 常见面试题深度解析

### Q1: MyBatis 中 #{} 和 ${} 的区别及场景？

```
#{}：
  - 预编译占位符，替换为 ?
  - 参数值经过 JDBC PreparedStatement 安全处理（防 SQL 注入）
  - 自动加引号（如字符串 'value'）
  - 适用于所有参数化的值

${}：
  - 字符串直接拼接
  - 有 SQL 注入风险
  - 不会加引号
  - 仅适用于：动态表名/列名、ORDER BY 字段名、LIMIT 数值
  - 使用时必须白名单校验！

// 安全使用 ${} 的示例：
private static final Set<String> ALLOWED_COLUMNS = Set.of("id", "username", "create_time");
public List<User> findByOrder(String orderBy) {
    if (!ALLOWED_COLUMNS.contains(orderBy)) {
        throw new IllegalArgumentException("Invalid column: " + orderBy);
    }
    return mapper.findByOrder(orderBy);  // Mapper XML 中用 ${orderBy}
}
```

### Q2: MyBatis 一级缓存失效的场景？

```
当 Spring 整合 MyBatis 时，一级缓存（SqlSession 级别）几乎不生效！

原因：Spring 事务管理的 SqlSession 生命周期
  - 同一事务内 → 复用 SqlSession → 一级缓存有效
  - 没有事务时 → 每次查询 new SqlSession → 一级缓存无效

这也是为什么 MyBatis 一级缓存在 Spring 中是"透明"的：
  @Transactional
  public void test() {
      userMapper.findById(1L);  // SqlSession A，查询数据库
      userMapper.findById(1L);  // 同一 SqlSession A，命中一级缓存
  }

  public void test2() {
      userMapper.findById(1L);  // SqlSession A，查询数据库
      userMapper.findById(1L);  // SqlSession B（新的！），查询数据库
  }

结论：不要在业务中依赖 MyBatis 一级缓存！把它当安全的性能红利即可
```

### Q3: MySQL 中 DELETE、TRUNCATE、DROP 的区别？

```
DELETE：
  - DML 语句
  - 删除部分或全部行（可用 WHERE 过滤）
  - 逐行删除，记录日志 → 可回滚
  - 触发器会触发
  - 不释放表空间（碎片还在）
  - 自增 ID 继续递增

TRUNCATE：
  - DDL 语句（本质是 DROP + CREATE）
  - 删除全部行，不可 WHERE
  - 直接释放数据页 → 无法回滚
  - 不触发触发器
  - 释放表空间
  - 自增 ID 重置

DROP：
  - DDL 语句
  - 删除整个表（结构和数据都没了）
  - 释放表空间
  - 无法回滚
```
