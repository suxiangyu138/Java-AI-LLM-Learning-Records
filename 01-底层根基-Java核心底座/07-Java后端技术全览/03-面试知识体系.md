```
回答框架：
  1. 整体结构：数组 + 链表 + 红黑树
  2. put 流程
  3. get 流程
```

```java
public class HashMapPrinciple {

    /**
     * 核心参数
     */
    static final int DEFAULT_INITIAL_CAPACITY = 1 << 4;  // 16
    static final float DEFAULT_LOAD_FACTOR = 0.75f;
    static final int TREEIFY_THRESHOLD = 8;
    static final int UNTREEIFY_THRESHOLD = 6;
    static final int MIN_TREEIFY_CAPACITY = 64;

    /**
     * put 流程（JDK 1.8）：
     * 1. 计算 key 的 hash：key.hashCode() XOR (h >>> 16)
     * 2. 计算桶位置：hash & (table.length - 1)
     * 3. 如果桶为空 → 直接放入
     * 4. 如果桶不为空 → 遍历链表/红黑树
     *    a. 找到了相同的 key → 覆盖 value
     *    b. 没找到 → 插入尾部（尾插法）
     *    c. 链表长度 >= 8 且数组长度 >= 64 → 转为红黑树
     * 5. 检查是否需要扩容 (size > threshold)
     *
     * 扩容机制：
     * 1. 新容量 = 旧容量 * 2
     * 2. 创建新数组
     * 3. rehash（重新计算位置）
     *    - 元素在新数组的位置：原位置 或 原位置 + 旧容量
     *    - 根据 hash & oldCap 是否为 0 判断
     * 4. 转移完成，替换引用
     */
    public void explainPut() {}

    /**
     * get 流程：
     * 1. 计算 key 的 hash
     * 2. 定位到桶位置
     * 3. 如果第一个节点就是 → 直接返回
     * 4. 如果是红黑树 → 树查找
     * 5. 如果是链表 → 遍历查找
     * 6. 没找到 → 返回 null
     */
    public void explainGet() {}

    /**
     * JDK 1.7 vs 1.8 对比
     *
     * | 特性       | JDK 1.7               | JDK 1.8               |
     * |-----------|----------------------|----------------------|
     * | 数据结构   | 数组 + 链表            | 数组 + 链表 + 红黑树   |
     * | 插入方式   | 头插法                 | 尾插法                |
     * | hash 计算 | 多次扰动               | 一次扰动              |
     * | 扩容后   | 全部 rehash            | 按位判断              |
     * | 并发问题  | 扩容死循环             | 数据丢失              |
     */
    public void compareVersion() {}
}
```

**扩展回答**：

```
为什么负载因子是 0.75？
  - 泊松分布原理，在时间和空间成本之间的权衡
  - 太高：空间利用率高，但冲突增加，查询变慢
  - 太低：空间浪费

为什么链表转红黑树的阈值是 8？
  - 泊松分布：链表长度 8 的概率已经极低（0.00000006）
  - 红黑树节点占用空间是链表的 2 倍
  - 所以只在冲突严重时才使用红黑树

为什么容量是 2 的幂次？
  - 计算位置时：hash & (table.length - 1) 等价于取模
  - 前提是 length 是 2 的幂次
  - 位运算比取模运算快得多
```

#### Q2: ConcurrentHashMap 原理

```
回答框架：
  1. JDK 1.7：分段锁 (Segment)
  2. JDK 1.8：CAS + synchronized
  3. put 流程
  4. 扩容机制
  5. size 计算
```

```java
public class ConcurrentHashMapPrinciple {

    /**
     * JDK 1.8 实现原理：
     *
     * 1. 数据结构：数组 + 链表 + 红黑树（同 HashMap）
     *
     * 2. 并发控制：
     *    - 初始化：CAS (sizeCtl)
     *    - 插入/更新：synchronized (桶的头节点)
     *    - 扩容：多线程协助
     *    - 计数：CAS + CounterCell
     *
     * 3. put 流程：
     *    a. 计算 hash
     *    b. while(true) {
     *         if (table 未初始化) → 初始化 (CAS 竞争)
     *         else if (桶为空) → CAS 直接插入
     *         else if (正在扩容) → 协助扩容
     *         else → synchronized(头节点) { 插入链表或红黑树 }
     *       }
     *
     * 4. 为什么用 synchronized 而不是 ReentrantLock？
     *    - JDK 1.6 后 synchronized 性能已经很好
     *    - synchronized 不需要手动释放锁
     *    - JVM 级别优化（偏向锁、轻量级锁）
     *    - 代码更简洁
     *
     * 5. 弱一致性：
     *    - get 操作不加锁
     *    - size() 不是精确值
     *    - 迭代器不抛 ConcurrentModificationException
     */
    public void explainCHM() {}
}
```

#### Q3: ArrayList vs LinkedList

| 维度 | ArrayList | LinkedList |
|------|-----------|------------|
| 底层结构 | 动态数组 | 双向链表 |
| 随机访问 | O(1) | O(n) |
| 头部插入 | O(n) | O(1) |
| 尾部插入 | O(1) 均摊 | O(1) |
| 内存占用 | 更少（只存数据） | 更多（需要前后指针） |
| 扩容 | 1.5 倍扩容 | 无 |
| 适用场景 | 频繁随机访问 | 频繁增删 |

**面试话术**：

```
"ArrayList 和 LinkedList 的选择取决于使用场景。
ArrayList 基于动态数组，随机访问是 O(1)，适合需要频繁 get 的场景。
LinkedList 基于双向链表，头部插入是 O(1)，适合需要频繁在头部操作的场景。

但实际开发中，
ArrayList 的使用频率远高于 LinkedList，
因为大多数场景都是尾部插入 + 随机访问。
LinkedList 的节点内存开销更大（每个节点存储前驱和后继指针），
所以除非确认需要频繁头部插入，否则推荐 ArrayList。"
```

#### Q4: fail-fast vs fail-safe

```
fail-fast（快速失败）：
  - 遍历时检测到结构修改 → 立即抛 ConcurrentModificationException
  - 实现方式：modCount 计数器
  - 代表：ArrayList, HashMap（非并发集合）

fail-safe（安全失败）：
  - 遍历的是原集合的副本
  - 修改原集合不会影响遍历
  - 缺点：内存开销，数据可能不是最新的
  - 代表：CopyOnWriteArrayList, ConcurrentHashMap

扩展回答 - CopyOnWriteArrayList 原理：
  - 写操作时复制底层数组
  - 读写分离，读无锁
  - 适合读多写少的场景
  - 数据最终一致性
```

### 2.2 JVM

#### Q5: JVM 内存区域

```
┌─────────────────────────────────────────────────────────────┐
│                     JVM 内存结构                              │
│                                                             │
│  ┌───────────────────────────────────────────────────┐     │
│  │                堆 (Heap)                          │     │
│  │  ┌──────────────────┐  ┌──────────────────┐     │     │
│  │  │  年轻代           │  │  老年代           │     │     │
│  │  │ ┌──┐ ┌──┐ ┌──┐ │  │                  │     │     │
│  │  │ │E │ │S1│ │S2│ │  │                  │     │     │
│  │  │ └──┘ └──┘ └──┘ │  │                  │     │     │
│  │  └──────────────────┘  └──────────────────┘     │     │
│  │                       │                          │     │
│  │                       │ 元空间 (元数据)           │     │
│  │                       │ (本地内存)               │     │
│  └───────────────────────────────────────────────────┘     │
│                                                             │
│  ┌──────────────────┐  ┌─────────────────────────────┐     │
│  │ 虚拟机栈          │  │ 本地方法栈                   │     │
│  │ (线程私有)        │  │ (native 方法)               │     │
│  │ 每个方法一个栈帧   │  │                             │     │
│  └──────────────────┘  └─────────────────────────────┘     │
│                                                             │
│  ┌──────────────────┐  ┌─────────────────────────────┐     │
│  │ 程序计数器        │  │ 直接内存 (Direct Buffer)     │     │
│  │ (线程私有)        │  │ (NIO 使用)                  │     │
│  └──────────────────┘  └─────────────────────────────┘     │
└─────────────────────────────────────────────────────────────┘
```

```
各区域作用：

堆 (Heap) - 所有线程共享
  - 对象实例和数组
  - GC 管理的主要区域
  - 可以细分为：年轻代 (Eden, S0, S1) + 老年代
  - 参数：-Xms, -Xmx

方法区 (元空间) - JDK 8+
  - 类的元数据、常量池、静态变量
  - 原先是永久代 (PermGen)，JDK 8 改为元空间 (Metaspace)
  - 元空间使用本地内存，不再 OOM (默认无上限)
  - 参数：-XX:MaxMetaspaceSize

虚拟机栈 - 线程私有
  - 每个方法对应一个栈帧
  - 栈帧包含：局部变量表、操作数栈、动态链接、返回地址
  - StackOverflowError：栈深度超过限制
  - OutOfMemoryError：无法申请足够内存

本地方法栈 - 线程私有
  - 执行 native 方法
  - 类似的也有 StackOverflowError 和 OOM

程序计数器 - 线程私有
  - 记录当前线程执行的字节码指令地址
  - 线程切换后能恢复到正确位置
```

#### Q6: GC 算法对比

| 算法 | 原理 | 优点 | 缺点 | 适用区域 |
|------|------|------|------|---------|
| **标记-清除** | 标记存活对象，清除未标记的 | 简单 | 内存碎片 | 老年代 (CMS) |
| **标记-复制** | 分成两半，存活对象复制到另一半 | 无碎片，简单高效 | 浪费一半空间 | 年轻代 |
| **标记-整理** | 标记存活对象，整理到一端 | 无碎片 | 需要移动对象 | 老年代 |
| **分代收集** | 不同代使用不同算法 | 效率高 | 跨代引用处理复杂 | 整堆 |

```
对象分配与晋升流程：

1. 新对象 → Eden 区
2. Minor GC → 存活对象从 Eden → S0 或 S1
3. 每次 Minor GC → 存活对象 age + 1
4. age >= 15 (默认) → 晋升到老年代
5. 大对象直接进入老年代（-XX:PretenureSizeThreshold）
6. 老年代满 → Major GC / Full GC
```

#### Q7: GC 收集器对比

| 收集器 | 处理区域 | 算法 | 特点 | 暂停时间 |
|--------|---------|------|------|---------|
| **Serial** | 年轻代 | 复制 | 单线程，暂停应用 | 长 |
| **ParNew** | 年轻代 | 复制 | Serial 的多线程版 | 较短 |
| **Parallel Scavenge** | 年轻代 | 复制 | 追求吞吐量 | 较短 |
| **Serial Old** | 老年代 | 标记-整理 | Serial 的老年代版 | 长 |
| **Parallel Old** | 老年代 | 标记-整理 | 吞吐量优先 | 较长 |
| **CMS** | 老年代 | 标记-清除 | 并发收集，低延迟 | 短 |
| **G1** | 整堆 | 分区 + 复制 | 可预测停顿 | 可控 |
| **ZGC** | 整堆 | 染色指针 | 超低延迟 (< 10ms) | 极短 |

**G1 工作原理**：

```
G1 将堆划分为 2048 个 Region（1MB-32MB）
每个 Region 可以扮演 Eden、Survivor、Old 或 Humongous

G1 GC 阶段：
1. 年轻代 GC (STW)
   - 复制 Eden+Survivor 到空闲 Region
   - 达到阈值晋升到老年代

2. 并发标记 (Concurrent)
   - 初始标记 (STW, 短暂)
   - 并发标记
   - 重新标记 (STW)
   - 清理 (STW, 部分)

3. 混合收集 (Mixed GC, STW)
   - 选择回收收益最大的 Region（根据停顿预测模型）
   - 复制存活对象到空闲 Region

关键参数：
  -XX:+UseG1GC
  -XX:MaxGCPauseMillis=200  (目标停顿时间)
  -XX:G1HeapRegionSize=4M   (Region 大小)
```

#### Q8: OOM 排查场景

```
场景 1: Java heap space
  表现：不断 Full GC，对象无法回收
  排查：
    1. jmap -heap <pid> 查看堆使用
    2. jmap -dump:live,format=b,file=heap.hprof <pid> (导出堆快照)
    3. 用 MAT 或 VisualVM 分析：
       - 查看大对象 (Biggest Objects)
       - 查看 GC Roots 引用链
       - 分析可疑对象 (Leak Suspects)
  常见原因：
    - 内存泄漏 (未关闭资源、ThreadLocal 不 remove)
    - 大对象 (一次加载过多数据)
    - 对象引用链过长

场景 2: Metaspace
  表现：元空间 OOM
  排查：
    - 查看类加载日志：-XX:+TraceClassLoading
    - 检查是否有动态生成类的代码（CGLIB, ASM）
    - 检查 ClassLoader 泄漏
  常见原因：
    - 热部署导致 ClassLoader 泄漏
    - 动态代理类过多

场景 3: Direct buffer memory
  表现：Direct Buffer OOM
  排查：
    - 检查 NIO 使用 (ByteBuffer.allocateDirect)
    - Netty 的内存泄漏检测
  常见原因：
    - NIO 操作后未释放 DirectBuffer

场景 4: unable to create new native thread
  表现：无法创建新线程
  排查：
    - ulimit -u 查看进程限制
    - /proc/sys/kernel/threads-max 查看系统限制
    - jstack 查看线程数量
  常见原因：
    - 线程池参数不合理
    - 无限制创建线程
```

### 2.3 并发编程

#### Q9: synchronized vs Lock

| 维度 | synchronized | Lock (ReentrantLock) |
|------|-------------|---------------------|
| 实现方式 | JVM 层面 (Monitor) | JDK 层面 (AQS) |
| 锁释放 | 自动 | 手动 unlock() |
| 公平性 | 非公平 | 可设置公平/非公平 |
| 可中断 | 否 | lockInterruptibly() |
| 超时 | 否 | tryLock(timeout) |
| 条件变量 | wait/notify | Condition.await/signal |
| 多个条件 | 否 | 多个 Condition 对象 |
| 性能 | 优化后相近 | 原有较高 |

```
synchronized 优化（JDK 1.6+）：
  偏向锁 → 轻量级锁 → 重量级锁（锁升级，不可逆）

锁升级流程：
  1. 无锁：对象刚创建
  2. 偏向锁：第一个线程获取，Mark Word 记录线程 ID
  3. 轻量级锁：有竞争，CAS 尝试获取
  4. 重量级锁：CAS 失败，线程阻塞等待

选择建议：
  简单场景：使用 synchronized（代码简洁，不会忘记释放）
  复杂场景：使用 Lock（可中断、超时、多条件）
  读多写少：使用 ReadWriteLock / StampedLock
```

#### Q10: volatile 语义

```
volatile 保证两个特性：
  1. 可见性：一个线程修改 volatile 变量 → 其他线程立即看到
  2. 有序性：禁止指令重排序

不保证：原子性

实现原理：
  - 可见性：在变量修改后插入内存屏障
    StoreStoreBarrier → volatile 写 → StoreLoadBarrier
  - 有序性：禁止重排序

内存屏障类型：
  LoadLoad: Load1 → Load2, 保证 Load1 在 Load2 之前加载
  StoreStore: Store1 → Store2, 保证 Store1 在 Store2 之前刷新
  LoadStore: Load1 → Store2
  StoreLoad: Store1 → Load2（最严格）
```

```java
// volatile 典型使用场景
public class VolatileDemo {

    // 1. 状态标志
    private volatile boolean running = true;

    public void stop() {
        running = false;
    }

    public void run() {
        while (running) {
            // do work
        }
    }

    // 2. DCL (Double-Checked Locking) 单例
    public class Singleton {
        private static volatile Singleton instance;

        public static Singleton getInstance() {
            if (instance == null) {  // 第一次检查
                synchronized (Singleton.class) {
                    if (instance == null) {  // 第二次检查
                        instance = new Singleton();
                        // 需要 volatile 防止指令重排序
                        // new 操作：1.分配内存 2.初始化对象 3.赋值给引用
                        // 如果不加 volatile，可能 1→3→2
                    }
                }
            }
            return instance;
        }
    }
}
```

**线程池大小的计算公式**：

```
CPU 密集型：Ncpu + 1
IO 密集型：2 * Ncpu

更精确的公式：
线程数 = Ncpu * Ucpu * (1 + W/C)
  Ncpu: CPU 核心数
  Ucpu: 目标 CPU 利用率 (0-1)
  W/C: 等待时间 / 计算时间

示例：4 核 CPU，等待时间 100ms，计算时间 10ms
  线程数 = 4 * 0.9 * (1 + 100/10) = 4 * 0.9 * 11 = 39.6 ≈ 40
```

```java

 * Spring 如何解决循环依赖？
 *
 * 核心：三级缓存 + 提前暴露

    /**
     * 三级缓存：
     *
     * 第一级: singletonObjects
     *   完整的单例 Bean
     *
     * 第二级: earlySingletonObjects
     *   提前暴露的 Bean（未完全初始化，但已经实例化）

     *   ObjectFactory，用于生成代理对象

     *
     * 1. A 开始创建
     *    - 实例化 A
     *    - 将 A 的 ObjectFactory 放入三级缓存
     *    - 填充属性：发现需要 B
     *
     * 2. B 开始创建
     *    - 实例化 B
     *    - 将 B 的 ObjectFactory 放入三级缓存
     *    - 填充属性：发现需要 A
     *    - 从三级缓存获取 A 的 ObjectFactory

     *    - 将 A 放入二级缓存

     *
     * 3. B 完成初始化
     *    - B 所有属性填充完成
     *    - B 初始化完成
     *    - B 放入一级缓存
     *    - B 从二三级缓存移除
     *
     * 4. A 继续初始化
     *    - 从一级缓存获取 B
     *    - A 属性填充完成
     *    - A 初始化完成
     *    - A 放入一级缓存
     *    - A 从二三级缓存移除
     *
     * 限制：只能解决 setter 注入的循环依赖
     * 不能解决：构造器注入的循环依赖
     */
    public void explainCircularDependency() {}
```

### 4.1 MySQL

#### Q21: B+Tree 索引

```
B+Tree 的特点：
  1. 所有数据存储在叶子节点
  2. 叶子节点形成有序链表（范围查询高效）
  3. 非叶子节点只存储索引键（可存储更多键值）
  4. 树的高度通常 2-4 层（查询稳定）

InnoDB B+Tree 结构：
  Root Node (Page)
    ├── 索引键: [1, 50, 100]
    ├── 指针指向中间节点
    │
    ├── Internal Node (Page)
    │   ├── 索引键: [1, 10, 20, ...]
    │   └── 指针指向叶子节点
    │
    └── Leaf Node (Page)
        ├── 索引键 + 主键值 (二级索引)
        └── 索引键 + 整行数据 (聚簇索引)

聚簇索引 vs 二级索引：
  聚簇索引：InnoDB 主键索引，叶子节点存整行数据
  二级索引：非主键索引，叶子节点存主键值
  回表：通过二级索引查到主键，再回聚簇索引查完整行

最左匹配原则：
  联合索引 (a, b, c)：
    能用到索引的查询：
      WHERE a = 1
      WHERE a = 1 AND b = 2
      WHERE a = 1 AND b = 2 AND c = 3
      WHERE a = 1 ORDER BY b
    不能用到索引的查询：
      WHERE b = 2           (跳过 a)
      WHERE a = 1 AND c = 3 (跳过 b)
      WHERE b = 2 AND c = 3 (跳过 a)
```

#### Q22: 事务隔离级别

```
读未提交 (READ UNCOMMITTED)
  - 能读到其他事务未提交的数据
  - 问题：脏读

读已提交 (READ COMMITTED) - PostgreSQL 默认
  - 只能读到其他事务已提交的数据
  - 问题：不可重复读
  - 实现：每次读都生成新的 ReadView（MVCC）

可重复读 (REPEATABLE READ) - MySQL/InnoDB 默认
  - 同一事务内的相同查询结果一致
  - 问题：幻读
  - 实现：事务开始时生成 ReadView，后续复用
  - InnoDB 通过间隙锁解决幻读

串行化 (SERIALIZABLE)
  - 事务串行执行
  - 性能最差

MySQL InnoDB 默认 RR 的原因：
  1. MySQL 的 Binlog 只支持 STATEMENT 格式时，
     如果使用 RC 会导致主从不一致
  2. 现在使用 ROW 格式 Binlog，RC 也是安全的
```

#### Q23: MVCC 原理

```
MVCC = Multi-Version Concurrency Control

核心概念：
  - 每行记录有多个版本（undo log 保存）
  - 每个事务有唯一的事务 ID (trx_id)
  - 读操作不阻塞写，写操作不阻塞读

关键字段（行记录隐藏列）：
  DB_TRX_ID：最近修改该行的事务 ID
  DB_ROLL_PTR：回滚指针，指向上一个版本
  DB_ROW_ID：隐含的自增 ID（没有主键时使用）

ReadView 结构：
  m_ids：活跃事务 ID 列表
  min_trx_id：最小活跃事务 ID
  max_trx_id：最大事务 ID + 1
  creator_trx_id：创建该 ReadView 的事务 ID

可见性判断规则：
  1. 如果 DB_TRX_ID < min_trx_id → 可见（已提交）
  2. 如果 DB_TRX_ID >= max_trx_id → 不可见（未来事务）
  3. 如果 min_trx_id <= DB_TRX_ID < max_trx_id
     且 DB_TRX_ID 在 m_ids 中 → 不可见（未提交）
     且 DB_TRX_ID 不在 m_ids 中 → 可见（已提交）
```

#### Q24: 行锁与间隙锁

```
InnoDB 行锁类型：
  记录锁 (Record Lock)：锁定单行
  间隙锁 (Gap Lock)：锁定一个区间（防止幻读）
  临键锁 (Next-Key Lock)：记录锁 + 间隙锁

锁的退化：
  - 唯一索引等值查询 → Record Lock
  - 普通索引等值查询 → Next-Key Lock → Gap Lock
  - 范围查询 → Next-Key Lock

死锁排查：
  SHOW ENGINE INNODB STATUS \G

  查看 LATEST DETECTED DEADLOCK 部分
  - 涉及的事务
  - 等待的资源
  - 回滚的事务

解决方案：
  - 调整事务顺序
  - 减少事务持有锁的时间
  - 使用索引减少锁范围
  - 设置 lock_wait_timeout
```

| **Hash** | 压缩列表 / 哈希表 | 对象缓存 | `HMSET user:1 name "a" age 18` |
| **List** | 压缩列表 / 双向链表 | 消息队列、最新列表 | `LPUSH queue task` |
| **Set** | 整数集合 / 哈希表 | 去重、共同好友 | `SADD tag:java article1` |
| **ZSet** | 压缩列表 / 跳表 | 排行榜、延迟队列 | `ZADD rank 100 user1` |
| **BitMap** | 位数组 | 签到、布隆过滤器 | `SETBIT sign:202401 0 1` |
| **HyperLogLog** | 基数估算 | UV 统计 | `PFADD uv:202401 user1` |
| **GEO** | ZSet 封装 | 地理位置 | `GEOADD city 116 40 beijing` |

#### Q26: 缓存三大问题

```
缓存穿透：
  问题：查询一个不存在的数据，缓存没有，每次都打到 DB
  危害：DB 压力大，可能被打垮
  解决方案：
    1. 布隆过滤器（一定不存在的数据直接返回）
    2. 空值缓存（短 TTL）
    3. 参数校验

缓存雪崩：
  问题：大量缓存同时过期，或 Redis 宕机
  危害：请求全部打到 DB
  解决方案：
    1. 过期时间加随机值
    2. 多级缓存（本地 + Redis）
    3. 缓存集群高可用
    4. 限流降级

缓存击穿：
  问题：热点 key 过期，高并发访问该 key
  危害：DB 瞬间高负载
  解决方案：
    1. 互斥锁（只让一个线程查 DB）
    2. 逻辑过期（后台异步刷新）
    3. 热点数据永不过期
```

```java
// 互斥锁解决缓存击穿
public String getData(String key) {
    // 1. 从缓存获取
    String data = redisTemplate.opsForValue().get(key);
    if (data != null) {
        return data;
    }

    // 2. 缓存穿透，尝试获取互斥锁
    String lockKey = "lock:" + key;
    if (redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS)) {
        try {
            // 3. 查数据库
            data = queryFromDB(key);
            // 4. 回填缓存
            redisTemplate.opsForValue().set(key, data, 30, TimeUnit.MINUTES);
            return data;
        } finally {
            // 5. 释放锁
            redisTemplate.delete(lockKey);
        }
    } else {
        // 6. 没获取到锁，等待后重试
        Thread.sleep(100);
        return getData(key);  // 递归重试
    }
}
```

#### Q28: 消息可靠性

```
消息可靠性 = 生产可靠 + 存储可靠 + 消费可靠

生产可靠：
  1. 同步确认
     Producer → Broker: 确认收到 (ack)
     Producer → Broker: 确认持久化 (sync flush)
  2. 事务消息（RocketMQ 特有）
     - 半消息 → 执行本地事务 → 确认/回滚
  3. 失败重试

存储可靠：
  1. 持久化到磁盘
  2. 主从复制
  3. 刷盘策略：同步刷盘（最安全）、异步刷盘（高效）

消费可靠：
  1. ACK 机制：消费成功后再确认
  2. 重试机制：失败后自动重试
  3. 死信队列：多次重试失败的消息
```

## 五、分布式系统面试题

### 5.1 CAP 定理

```
CAP 定理：
  C (Consistency)：一致性，所有节点看到相同数据
  A (Availability)：可用性，每个请求都能获得响应
  P (Partition Tolerance)：分区容错性，网络分区时仍能工作

CAP 只能三选二（实际是 P 必选，在 C 和 A 之间权衡）

CP 系统：ZooKeeper, etcd
  - 分区时优先保证一致性
  - 可能拒绝请求（牺牲可用性）

AP 系统：Eureka, Cassandra
  - 分区时优先保证可用性
  - 数据可能不一致（牺牲一致性）

BASE 理论：
  BA (Basically Available)：基本可用
  S (Soft State)：软状态
  E (Eventually Consistent)：最终一致性
```

### 5.2 分布式事务方案

```
1. 二阶段提交 (2PC)
   流程：准备阶段 + 提交阶段
   优点：强一致性
   缺点：同步阻塞、单点故障、协调者挂了就卡住

2. TCC (Try-Confirm-Cancel)
   流程：Try 尝试 → Confirm 确认 → Cancel 取消
   优点：不阻塞、性能好
   缺点：业务侵入性强（需要实现 Try/Confirm/Cancel 三个方法）

3. 本地消息表
   流程：业务操作 + 消息表在一个本地事务中 → 异步发送
   优点：简单、可靠
   缺点：消息表耦合业务

4. 消息事务 (RocketMQ)
   流程：半消息 → 执行本地事务 → 确认/回滚
   优点：基于 MQ，解耦好

5. Seata AT 模式
   流程：自动生成反向 SQL → 提交时一阶段提交
        → 二阶段自动回滚
   优点：业务无侵入
   缺点：性能有损耗
```

### 5.3 分布式锁

```
实现方式对比：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 数据库唯一索引 | 简单 | 性能差，单点 |
| Redis SETNX | 性能好 | 需要看门狗，可能不一致 |
| Redisson | 功能完善 | 依赖 Redis |
| ZooKeeper | 可靠，一致性 | 性能不如 Redis |

Redis 分布式锁最佳实践（Redisson）：
  1. 互斥：SET key value NX PX 30000
  2. 防死锁：设置过期时间
  3. 防误删：value 是唯一 ID（锁的持有者标识）
  4. 自动续期：看门狗 (Watch Dog)
  5. 可重入：同一线程可重入
  6. Redlock：多节点容错
```

### 6.2 技术问题回答框架

```
"你能讲讲 ConcurrentHashMap 的原理吗？"

回答框架：
1. 概述（一句话）
   "ConcurrentHashMap 是线程安全的 HashMap，
    JDK 1.8 使用 CAS + synchronized 实现。"

2. 核心原理（2-3 句话）
   "底层结构和 HashMap 一样，数组+链表+红黑树。
    并发控制采用 CAS 控制初始化，
    synchronized 锁住桶的头节点保证线程安全。"

3. 关键细节（选择性深入）
   "put 流程是：先 CAS 初始化，再判断桶位置，
    空桶用 CAS 插入，非空桶用 synchronized 锁住头节点后操作。
    get 不需要加锁，靠 volatile 保证可见性。"

4. 对比
   "和 HashTable 比，性能更好，因为锁粒度更细。
    和 Collections.synchronizedMap 比，
    ConcurrentHashMap 在迭代时不会抛
    ConcurrentModificationException。"

5. 总结
   "所以 ConcurrentHashMap 的核心设计思想是
    通过缩小锁粒度 + CAS 无锁操作来实现高并发。"

6. 准备追问
   (准备好回答：扩容机制、size 计算、红黑树转换条件)
```
