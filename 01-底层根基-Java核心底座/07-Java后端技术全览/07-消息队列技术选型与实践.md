## 1. 消息队列基础概念

### 1.1 为什么需要消息队列？

```
场景 1：异步处理
  同步：用户注册 → 写DB(50ms) + 发邮件(500ms) + 发短信(300ms) = 850ms
  异步：用户注册 → 写DB(50ms) + 发MQ消息(1ms) = 51ms → 立即返回
        消费者异步发邮件、短信

场景 2：削峰填谷
  秒杀：10000 QPS 瞬时流量 → MQ 缓冲 → 后台按 1000/s 处理
  数据库不会被瞬时打垮

场景 3：解耦
  订单服务：直接调库存 + 优惠券 + 积分 + 物流 = 强耦合
  改为：发"订单创建"消息，各服务自行订阅 → 解耦
  新增服务只需订阅消息，不需要改订单代码

场景 4：数据分发
  商品变更 → 发消息 → 搜索服务更新索引 + 推荐服务更新模型 + 缓存服务刷新
```

### 1.2 核心概念

```
Producer（生产者）：发送消息的一方
Consumer（消费者）：接收并处理消息的一方
Broker（消息代理）：消息队列服务端，类似邮局
Topic（主题）：消息的逻辑分类，生产者向 Topic 发，消费者从 Topic 收
Partition / Queue（分区 / 队列）：Topic 的物理分片，提高并行度
Consumer Group（消费者组）：组内分工，组间广播
Offset（偏移量）：消息在分区/队列中的位置
Message（消息）：实际传递的数据（Header + Body）
```

### 1.3 两种消息模型

```
点对点（Point-to-Point / Queue 模式）：
  生产者 → Queue → 消费者（只有一个消费者收到）
  一条消息只被消费一次
  RabbitMQ 的默认模式、RocketMQ 的集群消费

发布-订阅（Pub/Sub / Topic 模式）：
  生产者 → Topic → 多个消费者组
  每个消费者组都收到完整消息副本
  组内竞争消费（一条消息被一个组员处理）
  组间广播消费（每条消息被所有组都处理）
```

## 2. RocketMQ 详解

### 2.1 架构设计

```
NameServer（命名服务器）：
  - 充当注册中心（无状态，彼此不通信）
  - 路由信息：哪些 Topic 在哪些 Broker 上
  - Producer/Consumer 从 NameServer 获取路由

Broker（消息代理）：
  - 存储消息、转发消息
  - 主从架构（Master-Slave）
  - 同步刷盘 / 异步刷盘

Producer 发送流程：
  1. 从 NameServer 获取 Topic 路由
  2. 根据路由选择 MessageQueue（轮询或按 key hash）
  3. 直接连接 Broker 发送消息

Consumer 消费流程：
  1. 从 NameServer 获取路由
  2. 负载均衡分配 MessageQueue
  3. 从 Broker 拉取消息（长轮询）
```

### 2.2 消息模型

```
RocketMQ 消息模型：
  Topic
    ├── MessageQueue-0（物理队列）
    ├── MessageQueue-1
    ├── MessageQueue-2
    └── MessageQueue-3

  Consumer Group
    ├── Consumer-1 → 负责 MQ-0, MQ-1
    ├── Consumer-2 → 负责 MQ-2, MQ-3
    └── (组内竞争，一个 Queue 只被一个 Consumer 消费)

  Rebalance 触发时机：
  - Consumer 数量变化
  - Broker 数量变化
  - 定时触发（20s）

两种消费模式：
  集群消费（CLUSTERING，默认）：一条消息只被组内一个消费者消费
  广播消费（BROADCASTING）：一条消息被组内所有消费者都消费
```

### 2.3 消息类型

```java
// 1. 普通消息（同步/异步/单向）
// 同步
SendResult result = producer.send(message);
// 异步
producer.send(message, new SendCallback() {
    @Override
    public void onSuccess(SendResult result) { }
    @Override
    public void onException(Throwable e) { }
});
// 单向（不关心结果，如日志）
producer.sendOneway(message);

// 2. 顺序消息
// 同一个 MessageQueue 内的消息严格有序
// 需要将同一业务 ID 的消息发送到同一 Queue
SendResult result = producer.send(message,
    new MessageQueueSelector() {
        @Override
        public MessageQueue select(List<MessageQueue> queues, Message msg, Object arg) {
            Long orderId = (Long) arg;
            int index = (int) (orderId % queues.size());
            return queues.get(index);
        }
    }, orderId);

// 消费时注意：顺序消费需要加锁
consumer.registerMessageListener(new MessageListenerOrderly() {
    @Override
    public ConsumeOrderlyStatus consumeMessage(List<MessageExt> msgs, ConsumeOrderlyContext ctx) {
        // 处理顺序消息，同一 Queue 的消息串行消费
        ctx.setAutoCommit(true);
        return ConsumeOrderlyStatus.SUCCESS;
    }
});

// 3. 事务消息（RocketMQ 核心优势！）
TransactionMQProducer producer = new TransactionMQProducer("group");
producer.setTransactionListener(new TransactionListener() {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        // 执行本地事务
        try {
            orderService.createOrder((OrderDTO) arg);  // 本地事务
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 事务状态回查（本地事务执行超时时触发）
        // 检查本地事务是否成功完成
        String orderId = msg.getKeys();
        Order order = orderService.getOrder(orderId);
        return order != null ? LocalTransactionState.COMMIT_MESSAGE
                             : LocalTransactionState.ROLLBACK_MESSAGE;
    }
});

// 4. 延迟消息
// 支持 18 个延迟级别：1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
message.setDelayTimeLevel(3);  // 10s

// 5. 批量消息
List<Message> messages = new ArrayList<>();
messages.add(new Message("topic", "tag", "msg1".getBytes()));
messages.add(new Message("topic", "tag", "msg2".getBytes()));
producer.send(messages);
```

### 2.4 存储设计

```
CommitLog：
  所有消息顺序写入一个文件（或少量几个大文件）
  顺序写，性能极高（磁盘顺序写接近内存随机写）

ConsumeQueue：
  按 Topic+QueueId 组织的索引
  指向 CommitLog 中的消息位置
  消费时先查 ConsumeQueue，再根据 offset 去 CommitLog 读

刷盘机制：
  同步刷盘：消息写入磁盘后才返回成功（数据安全，性能低）
    flushDiskType = SYNC_FLUSH
  异步刷盘：消息写入 Page Cache 即返回成功（性能高，断电可能丢）
    flushDiskType = ASYNC_FLUSH（默认）

主从同步：
  同步复制：Master+Slave 都写成功才返回（推荐金融场景）
    brokerRole = SYNC_MASTER
  异步复制：Master 写成功即返回（性能高）
    brokerRole = ASYNC_MASTER（默认）
```

## 3. Kafka 详解

### 3.1 架构设计

```
Kafka 核心组件：

Broker：
  - Kafka 服务节点
  - 管理 Partition 的读写

Topic：
  - 消息的逻辑分类
  - 可以有多个 Partition

Partition：
  - Topic 的物理分片
  - 一个 Partition 是一个有序的、不可变的消息序列
  - 每个 Partition 对应一个文件夹

Replica：
  - 每个 Partition 可以有多个副本
  - Leader：处理所有读写请求
  - Follower：从 Leader 同步数据（被动备份）
  - ISR（In-Sync Replicas）：与 Leader 保持同步的副本集合

Consumer Group：
  - 组内：一个 Partition 只被组内一个 Consumer 消费
  - 组间：Topic 消息被每个组都消费
  - Rebalance：Consumer 变化时重新分配 Partition

Offset：
  - 每条消息在其 Partition 中的位置（递增 Long 值）
  - Consumer 维护自己消费到的 Offset
  - __consumer_offsets（内部 Topic）存储消费者 Offset

ZooKeeper / KRaft：
  - ZK（旧）：管理集群元数据、Controller 选举、Consumer Group
  - KRaft（3.3+）：移除 ZK 依赖，Kafka 自身管理元数据
```

### 3.2 生产者详解

```java
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");

// 关键配置
props.put("acks", "all");              // 确认机制
props.put("retries", 3);              // 重试次数
props.put("batch.size", 16384);       // 批量发送大小
props.put("linger.ms", 10);           // 发送前等待时间（攒批量）
props.put("buffer.memory", 33554432); // 缓冲区大小
props.put("compression.type", "snappy");  // 压缩算法
props.put("max.in.flight.requests.per.connection", 5);  // 最大未确认请求数
// 如果需要严格顺序：max.in.flight.requests = 1
props.put("enable.idempotence", true);  // 幂等性（5.0+）

KafkaProducer<String, String> producer = new KafkaProducer<>(props);

// 发送方式
// 异步（推荐）
producer.send(record, (metadata, exception) -> {
    if (exception == null) {
        log.info("发送成功: topic={} partition={} offset={}",
            metadata.topic(), metadata.partition(), metadata.offset());
    }
});

// 同步（等确认）
Future<RecordMetadata> future = producer.send(record);
RecordMetadata metadata = future.get();  // 阻塞等待
```

#### acks 参数详解

```
acks = 0
  生产者不等待任何确认
  最快，但可能丢消息

acks = 1
  等待 Leader 确认（写入 Leader 的 Page Cache 即返回）
  性能和安全折中
  Leader 宕机且 Follower 还没同步 → 消息可能丢失

acks = all（或 -1）
  等待所有 ISR 中的副本确认
  最安全，最慢
  配合 min.insync.replicas >= 2 防止单点故障
  → 推荐生产环境配置
```

### 3.3 消费者详解

```java
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id", "order-consumer-group");
props.put("key.deserializer", "StringDeserializer");
props.put("value.deserializer", "StringDeserializer");
props.put("enable.auto.commit", "false");  // 关闭自动提交（推荐）
props.put("auto.offset.reset", "earliest");  // 没有 offset 时从哪开始
// earliest → 从最早开始；latest → 从最新开始
props.put("max.poll.records", 500);  // 一次拉取最多条数
props.put("max.poll.interval.ms", 300000);  // 两次 poll 最大间隔
props.put("session.timeout.ms", 10000);     // 心跳超时
props.put("heartbeat.interval.ms", 3000);   // 心跳间隔

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(Collections.singletonList("order-topic"));

try {
    while (true) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
        for (ConsumerRecord<String, String> record : records) {
            try {
                processMessage(record);  // 处理消息
            } catch (Exception e) {
                log.error("处理消息失败: offset={}", record.offset(), e);
                // TODO: 写入死信队列或本地重试队列
            }
        }
        // 业务处理完再提交 offset（至少一次语义）
        consumer.commitSync();  // 同步提交（阻塞）
        // consumer.commitAsync();  // 异步提交（更快）
    }
} finally {
    consumer.close();
}

// Rebalance 监听器
consumer.subscribe(topics, new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        // 分区被剥夺前 → 提交 offset
        consumer.commitSync();
    }
    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        // 新分区分配后 → 重置状态、从特定 offset 开始消费等
    }
});
```

### 3.4 存储与高吞吐原理

```
Kafka 高吞吐的 6 个原因：

1. 顺序写入磁盘
   消息追加到 Partition 文件末尾 → 顺序写
   顺序写磁盘比随机写内存还快（HDD ~150MB/s，SSD ~500MB/s）

2. 零拷贝（Zero Copy）
   传统：磁盘 → 内核缓冲区 → 用户缓冲区 → Socket 缓冲区 → 网卡
   零拷贝：磁盘 → 内核缓冲区 → 网卡（sendfile 系统调用）
   减少 2 次上下文切换 + 2 次拷贝

3. Page Cache
   消息先写入 OS Page Cache（内核缓冲区）
   读的时候也从 Page Cache 读
   避免直接磁盘 IO

4. 批量处理
   生产者：批量发送（batch.size + linger.ms）
   消费者：批量拉取（一次 poll 拿多条）
   磁盘：顺序写自动批量刷盘

5. 分区并行
   不同 Partition 分散在不同 Broker → 并行读写
   一个 Topic 的吞吐 = N × 单 Partition 吞吐

6. 压缩
   支持 gzip / snappy / lz4 / zstd
   压缩率：zstd > lz4 > gzip > snappy
   吞吐率：lz4 > snappy > gzip > zstd
   折中推荐：lz4
```

### 3.5 Rebalance 详解

```
Rebalance 触发条件：
  1. Consumer 组成员数量变化（新增/移除消费者）
  2. 订阅的 Topic 的 Partition 数量变化
  3. 订阅的 Topic 数量变化
  期间整个 Consumer Group 暂停消费（Stop-The-World）！

Rebalance 策略（partition.assignment.strategy）：
  RangeAssignor（默认）：
    按 Topic 各自分配 Partition 范围
    可能不均衡（前 N 个 Consumer 分得更多）
  RoundRobinAssignor：
    把所有 Partition 轮询分配给 Consumer
    更均衡
  StickyAssignor（推荐）：
    尽量保持原有分配，减少浪费
    Rebalance 时迁移最少
  CooperativeStickyAssignor（2.4+）：
    增量 Rebalance，不 Stop-The-World！
    使用它需要 session.timeout.ms 配置合理

避免频繁 Rebalance：
  max.poll.interval.ms 不宜太小（默认 5min）
  不要在 poll 循环中做长时间处理
  长时间处理 → 异步 + 暂停分区 + 恢复分区
```

## 4. RabbitMQ 详解

### 4.1 架构模型

```
RabbitMQ 核心概念：

Connection：TCP 连接（重量级）
Channel：虚拟连接（轻量级，复用 TCP 连接）
  一个 Connection 可以有多个 Channel
  每个 Channel 独立传输消息

Exchange（交换机）：
  接收生产者消息，根据 Binding 规则路由到 Queue
  类型：
    Direct    → 精确匹配 routing key
    Topic     → 通配符匹配（* 一个词, # 零或多个词）
    Fanout    → 广播到所有绑定的队列
    Headers   → 按消息头匹配（一般不用）

Queue（队列）：
  消息的实际存储
  消费者从 Queue 消费

Binding（绑定）：
  Exchange 和 Queue 之间的关系
  绑定时指定 routing key

Virtual Host（vHost）：
  逻辑隔离单元（多租户）
  每个 vHost 有独立的 Exchange / Queue / Binding
```

### 4.2 消息确认机制

```
生产者确认（Publisher Confirm）：
  1. 生产者 Channel 开启 confirm 模式
  2. 发消息后 → Broker 返回 ack/nack
  3. 可用异步回调处理

消费者确认（Consumer ACK）：
  1. autoAck = true（自动确认）
     消费者收到消息就自动确认 → 丢失风险高
     消息发给消费者就删除了

  2. autoAck = false（手动确认，推荐）
     channel.basicAck(deliveryTag, false)      → 确认
     channel.basicNack(deliveryTag, false, true)  → 拒绝 + 重试
     channel.basicReject(deliveryTag, true)    → 拒绝单条
```

### 4.3 死信队列 (DLX)

```
死信队列（Dead Letter Queue）：
  当消息变成"死信"时，自动转发到死信交换机

消息变成死信的三种情况：
  1. 消息被消费者拒绝（basicNack/basicReject 且 requeue=false）
  2. 消息 TTL 过期
  3. 队列达到最大长度

配置方法：
  在源 Queue 上声明：
    x-dead-letter-exchange: "dlx.exchange"
    x-dead-letter-routing-key: "dlx.routing.key"

用途：
  - 重试 N 次后进入死信 → 人工处理/告警
  - 延迟队列：消息 TTL + 死信队列 组合
    消息发到 TTL 队列 → TTL 过期 → 自动进死信队列
    → 消费者监听死信队列 → 实现延迟消费

延迟队列插件（rabbitmq-delayed-message-exchange）更优：
  直接指定延迟时间，不需要额外的 DLX 队列
```

### 4.4 消息持久化

```
消息不丢失的三层保证：

1. Exchange 持久化
   channel.exchangeDeclare(exchangeName, "topic", true);
   // durable = true

2. Queue 持久化
   channel.queueDeclare(queueName, true, false, false, null);
   // durable = true

3. Message 持久化
   channel.basicPublish(exchange, routingKey,
       MessageProperties.PERSISTENT_TEXT_PLAIN, body);
   // deliveryMode = 2

三样都配齐 → 消息持久化到磁盘，Broker 重启不丢失
注意：持久化消息的刷盘是异步的（有短时间窗口可能丢失）
```

## 5. 主流 MQ 全面对比

### 5.1 综合对比

| 维度 | RocketMQ | Kafka | RabbitMQ | Pulsar |
|------|----------|-------|----------|--------|
| **语言** | Java | Java/Scala | Erlang | Java |
| **吞吐量** | 十万级 | **百万级** | 万级 | 百万级 |
| **延迟** | 毫秒级 | 毫秒级 | **微秒级** | 毫秒级 |
| **消息模式** | 丰富 | 基础 | 丰富 | 丰富 |
| **事务消息** | ✅ | ❌ | ❌ | ❌ |
| **延迟消息** | ✅(18级别) | ❌ | 插件 | ✅ |
| **顺序消息** | ✅ | ✅(分区内) | ✅(单队列单消费者) | ✅ |
| **消息回溯** | ✅(按时间) | ✅(按 offset) | ❌ | ✅ |
| **消息重试** | ✅(内置) | ❌(手动) | ✅ | ✅ |
| **消息过滤** | ✅(Tag + SQL) | ❌ | ❌(Header) | ✅ |
| **集群管理** | NameServer | ZK / KRaft | Erlang 内置 | ZooKeeper |
| **社区活跃** | 中(阿里主导) | **高** | 高 | 增长中 |
| **运维难度** | 中 | 高 | 低 | 高 |
| **适用场景** | 电商、金融、事务 | 大数据、日志、流计算 | 业务解耦、中小规模 | 云原生、多租户 |

### 5.2 选型决策树

```
业务场景分析：

需要事务消息？
  YES → RocketMQ

  YES → RabbitMQ

需要低运维成本 + 快速上手？
  YES → RabbitMQ

大规模电商/金融（事务+延迟+高可用）？
  YES → RocketMQ

数据流/Event Sourcing/多系统数据同步？
  YES → Kafka

云原生/K8s/多租户？

阿⾥巴巴/金融/政府（国产化要求）？
  YES → RocketMQ
```

## 6. 消息可靠性保障

### 6.1 消息丢失的 3 个环节

```
环节一：生产者 → Broker
  丢失原因：网络问题 / Producer 宕机 / 异步发送不确认
  解决方案：
    - 同步发送 / 异步回调确认
    - 发送重试（RocketMQ retryTimesWhenSendFailed=3）
    - Kafka acks=all + min.insync.replicas=2

环节二：Broker 存储
  丢失原因：Broker 宕机 / 未刷盘
  解决方案：
    - 同步刷盘（牺牲性能换安全）
    - 多副本（RocketMQ SYNC_MASTER / Kafka acks=all）
    - 监控 ISR 列表，小于 min.insync 时告警

环节三：Broker → 消费者
  丢失原因：消费者拉取后宕机 / 自动确认 / 未处理完就确认
  解决方案：
    - 手动确认（处理成功后才确认）
    - 消费重试 + 死信队列兜底
```

### 6.2 可靠性全景

```
RocketMQ 消息不丢失配置：
  生产者：
    - 同步发送 + 重试 3 次
    - 记录发送日志用于对账
  Broker：
    - 同步刷盘（flushDiskType=SYNC_FLUSH）
    - 同步主从（brokerRole=SYNC_MASTER）
    - 主节点至少有一个从节点同步
  消费者：
    - 手动确认（CONSUME_FROM_LAST_OFFSET）
    - 重试 16 次后进死信队列
    - 消费幂等处理

Kafka 消息不丢失配置：
  生产者：
    - acks=all
    - retries=Integer.MAX_VALUE
    - enable.idempotence=true
    - min.insync.replicas=2
  消费者：
    - enable.auto.commit=false
    - 业务处理完 commitSync()
```

## 7. 消息幂等性方案

### 7.1 为什么需要幂等性？

```
消息重复的常见场景：
  1. 生产者重试 → Broker 收到两条相同消息
  2. 消费者处理成功但确认超时 → Broker 重新投递
  3. Rebalance 后 Offset 提交失败 → 重复消费

幂等性的含义：
  同一条消息被处理 1 次和 N 次的最终结果相同
```

### 7.2 实现方案

```java
// 方案 1：数据库唯一索引（最常用）
// 在订单表中 order_id 建唯一索引
CREATE UNIQUE INDEX uk_business_id ON orders(business_id);

// 消费端
@Transactional
public void handleMessage(OrderMessage msg) {
    // INSERT 如果成功 → 第一次处理 / 失败(DuplicateKeyException) → 重复消息
    try {
        orderMapper.insert(new Order(msg.getOrderId(), msg.getAmount()));
        // 后续业务逻辑...
    } catch (DuplicateKeyException e) {
        log.info("重复消息，已忽略: {}", msg.getOrderId());
        // 确认消费成功（不报错，不重试）
    }
}

// 方案 2：Redis + SETNX（应对非数据库操作的幂等）
String key = "msg:consumed:" + msgId;
Boolean success = redisTemplate.opsForValue()
    .setIfAbsent(key, "1", 24, TimeUnit.HOURS);
if (Boolean.TRUE.equals(success)) {
    // 第一次处理
    doBusiness(msg);
} else {
    log.info("重复消息，已忽略: {}", msgId);
}

// 方案 3：数据库消费记录表
// 业务操作 + 消费记录 在同一事务中
@Transactional
public void handleMessage(OrderMessage msg) {
    // 检查消费记录
    int count = consumeLogMapper.countByMsgId(msg.getMsgId());
    if (count > 0) {
        log.info("重复消息，已忽略: {}", msg.getMsgId());
        return;
    }
    // 业务操作
    doBusiness(msg);
    // 记录消费
    consumeLogMapper.insert(new ConsumeLog(msg.getMsgId(), LocalDateTime.now()));
}
```

## 8. 消息积压与处理

### 8.1 原因分析

```
消息积压的常见原因：
  1. 消费速度 < 生产速度（最根本原因）
  2. 消费者处理逻辑慢（网络 IO、数据库慢查询）
  3. 消费者数量不足（某个 Partition/Queue 只有一个 Consumer）
  4. 消费者故障（消费线程 hung 住、频繁 rebalance）
  5. 消息量激增（大促、秒杀）
```

### 8.2 处理方案

```java
// 短期应急：紧急扩容消费能力
// 1. 增加消费者实例（水平扩容）
//    注意：不能超过 Partition/Queue 数量！
//    如果 8 个 Partition，最多 8 个消费者
// 2. 增加 Partition/Queue 数量（需要提前规划）

// 3. 降级处理
//    - 跳过非关键消息
//    - 减少日志打印
//    - 关闭不必要的检查

// 4. 批量消费优化
@KafkaListener(topics = "order-topic", groupId = "batch-group",
    containerFactory = "batchFactory")
public void onBatchMessages(List<OrderEvent> events, Acknowledgment ack) {
    // 批量插入，减少 DB 交互次数
    orderService.batchInsert(events);
    ack.acknowledge();
}

// 长期方案：
// 1. 消费者处理逻辑优化（减少 IO、加缓存、优化 SQL）
// 2. 转存到新 Topic（增加 Partition），用更多消费者消费
// 3. 监控告警：积压量 > 阈值 → 自动扩容
```

## 9. 顺序消息与延迟消息

### 9.1 顺序消息

```java
// Kafka 顺序消息：同一个 key 的消息发到同一 Partition
// Producer
producer.send(new ProducerRecord<>("topic", orderId.toString(), message));

// RocketMQ 顺序消息：自定义 MessageQueueSelector
producer.send(message, (queues, msg, arg) -> {
    Long orderId = (Long) arg;
    return queues.get((int) (orderId % queues.size()));
}, orderId);

// 消费端（RocketMQ）：
// MessageListenerOrderly 保证同一 Queue 消息串行消费
// 问题：消费失败会无限重试到成功，可能阻塞后续消息
// 解决：设置重试次数限制 + 失败转移

// 消费端（Kafka）：
// 同一 Partition 的消息天然有序
// 但 Rebalance 可能导致 Partition 重分配
```

### 9.2 延迟消息

```
延迟消息的实现方案：

方案 1：RocketMQ 延迟级别（18 个级别）
  限制：只支持 18 个预设级别
  适用：大部分场景

方案 2：时间轮算法（Netty HashedWheelTimer）
  优点：灵活（任意延迟时间），高效
  RocketMQ 内部也用时间轮实现定时消息

方案 3：Redis ZSet + 定时扫描
  ZADD delay_queue <执行时间戳> <taskId>
  定时任务：ZRANGEBYSCORE delay_queue 0 <now> LIMIT 0 100
  取出任务执行 → ZREM

方案 4：RabbitMQ 死信队列
  TTL 队列 → 消息过期 → 死信交换 → 延迟消费队列

选型建议：
  - 简单场景 → RocketMQ 18 级延迟
  - 灵活延迟 → Redis ZSet 或 时间轮
  - 复杂调度 → 专业任务调度框架（XXL-JOB）
```

## 10. 企业实践与案例

### 10.1 可靠事件模式（最终一致性）

```java
// 本地事件表 + RocketMQ 实现分布式事务最终一致性
@Service
public class OrderService {

    @Transactional
    public void createOrder(OrderDTO dto) {
        // 1. 本地事务：创建订单 + 写入事件表
        Order order = orderMapper.insert(dto);
        Event event = new Event("order.created", order.getId());
        eventMapper.insert(event);

        // 2. 事务提交后 → 异步发送 MQ
        TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    sendEventToMQ(event);
                }
            });
    }

    private void sendEventToMQ(Event event) {
        try {
            rocketMQTemplate.syncSend(event.getTopic(), event);
            eventMapper.markAsSent(event.getId());  // 标记已发送
        } catch (Exception e) {
            // 定时任务会扫描未发送的事件，重新发送
            log.error("发送事件失败: {}", event.getId(), e);
        }
    }
}

// 定时任务：补偿发送
@Scheduled(fixedDelay = 60000)
public void resendFailedEvents() {
    List<Event> unsent = eventMapper.findUnsent();
    unsent.forEach(this::sendEventToMQ);
}
```

## 11. 常见面试题深度解析

### Q1: 消息队列怎么保证消息不丢？

```
三段式防护：生产者 → Broker → 消费者

生产者端：
  - 使用同步发送 / 异步回调确认
  - 配置重试（RocketMQ 默认 2 次，Kafka 配置 retries）
  - 本地消息表兜底（事务发消息后记表，定时扫描补发）

Broker 端：
  - 多副本（主从同步）
  - 同步刷盘（可选，性能换安全）
  - 配置最小 ISR 数量（Kafka min.insync.replicas >= 2）
  - 集群监控（ISR 数量下降告警）

消费者端：
  - 手动确认（业务处理成功后才确认）
  - 消费重试机制
  - 死信队列兜底
```

### Q2: 如何解决消息重复消费？

```
重复消费无法 100% 避免，必须从业务上实现幂等：

方案：每条消息带唯一业务 ID
  1. DB 唯一约束（最可靠）
  2. Redis SETNX
  3. 消费记录表 + 本地事务

关键原则：
  不要靠 MQ 保证不重复 → MQ 只保证 at-least-once
  业务端自己保证幂等性
```

### Q3: Kafka 为什么比 RabbitMQ 吞吐高？

```
1. 存储模型不同
   Kafka：顺序写磁盘（append-only log）→ 磁盘顺序写极快
   RabbitMQ：消息驱动，需要索引和元数据管理 → 元数据开销大

2. 批量处理
   Kafka：天然批量（生产者批量发送 + 消费者批量拉取）
   RabbitMQ：偏重单条消息处理

3. 零拷贝
   Kafka：sendfile 零拷贝
   RabbitMQ：过去需要经过用户态（现在也有改进）

4. 内存使用
   Kafka：主要依赖 Page Cache（OS 管理，可以很大）
   RabbitMQ：消息在 Erlang 进程中管理，内存和 GC 有开销

5. 设计理念
   Kafka 为流/吞吐设计（顺序 append、批处理）
   RabbitMQ 为路由/可靠设计（复杂 Exchange、灵活 ACK）
```
