## 1. 设计模式概述

### 1.1 六大设计原则（SOLID + 1）

```
S - 单一职责原则（Single Responsibility Principle）
  一个类只负责一件事
  → UserService 只管用户业务，不要管日志和权限

O - 开闭原则（Open-Closed Principle）
  对扩展开放，对修改关闭
  → 加新功能用新类实现接口，而不是改老类

L - 里氏替换原则（Liskov Substitution Principle）
  子类可以完全替换父类
  → 正方形不是矩形的子类（宽度 != 高度 时行为不同）

I - 接口隔离原则（Interface Segregation Principle）
  接口应该小而精，不要强迫实现不需要的方法
  → 不要把读和写放在同一个接口

D - 依赖倒置原则（Dependency Inversion Principle）
  依赖抽象，不依赖具体
  → UserService 依赖 UserRepository 接口，不依赖 JdbcUserRepository 具体类

+ 迪米特法则（Law of Demeter = 最少知识原则）
  一个类应该尽可能少地了解其它类
  → a.getB().getC().doSomething() → 违背！
  → a.doSomething() → 只跟直接朋友交流
```

## 2. 创建型模式 (5 种)

### 单例模式 (Singleton)

```java
// 1. 饿汉式（类加载时创建，线程安全，但启动慢）
public class EagerSingleton {
    private static final EagerSingleton INSTANCE = new EagerSingleton();
    private EagerSingleton() {}
    public static EagerSingleton getInstance() {
        return INSTANCE;
    }
}

// 2. 双重检查锁（DCL，推荐！volatile + synchronized）
public class DoubleCheckSingleton {
    // volatile 防止指令重排序（分配内存 + 初始化 + 赋引用）
    private static volatile DoubleCheckSingleton instance;
    private DoubleCheckSingleton() {}

    public static DoubleCheckSingleton getInstance() {
        if (instance == null) {                    // 第一次检查
            synchronized (DoubleCheckSingleton.class) {
                if (instance == null) {            // 第二次检查
                    instance = new DoubleCheckSingleton();
                }
            }
        }
        return instance;
    }
}

// 3. 枚举（最安全，防反射、防序列化）
public enum EnumSingleton {
    INSTANCE;
    public void doSomething() { }
}
```

### 工厂模式 (Factory Method / Abstract Factory)

```java
// 简单工厂（不是 GoF 23，但常用）
public class BeanFactory {

        return context.getBean(type);

}

// 工厂方法（一个工厂接口，子工厂各创建一种产品）
// Spring 的 FactoryBean<T> 就是工厂方法！

// 抽象工厂（一个工厂可以创建一族产品）
```

### 建造者模式 (Builder)

```java
// Lombok @Builder 生成的建造者模式
User user = User.builder()
    .name("张三")
    .age(25)
    .email("zhangsan@example.com")
    .build();

// 手动实现
public class User {
    private String name;
    private int age;
    // 私有构造器
    private User(Builder builder) {
        this.name = builder.name;
        this.age = builder.age;
    }
    public static class Builder {
        private String name;
        private int age;
        public Builder name(String name) { this.name = name; return this; }
        public Builder age(int age) { this.age = age; return this; }
        public User build() { return new User(this); }
    }
}
```

### 原型模式 (Prototype)

```java
// 原型模式 = 克隆对象
// Java 中实现 Cloneable 接口
public class User implements Cloneable {
    private String name;
    @Override
    public User clone() {
        try { return (User) super.clone(); }  // 浅拷贝
        catch (CloneNotSupportedException e) { return null; }
    }
}
// Spring Bean Scope: prototype → 每次获取都返回新 Bean
```

## 3. 结构型模式 (7 种)

### 代理模式 (Proxy)

```java
// Spring AOP 的核心！
// JDK 动态代理（基于接口）
public class JdkProxy implements InvocationHandler {
    private final Object target;
    public JdkProxy(Object target) { this.target = target; }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        System.out.println("before");
        Object result = method.invoke(target, args);
        System.out.println("after");
        return result;
    }
}

// CGLIB 动态代理（基于继承）
public class CglibProxy implements MethodInterceptor {
    @Override
    public Object intercept(Object obj, Method method, Object[] args, MethodProxy proxy)
        throws Throwable {
        System.out.println("before");
        Object result = proxy.invokeSuper(obj, args);
        System.out.println("after");
        return result;
    }
}
```

### 适配器模式 (Adapter)

```java
// Spring MVC 的 HandlerAdapter 就是适配器模式
// 不同 Controller 适配到统一接口

// 例子：把旧接口适配到新接口
interface NewApi { void newMethod(); }
class OldApi { void oldMethod() { } }

class Adapter implements NewApi {
    private OldApi oldApi;
    @Override
    public void newMethod() {
        oldApi.oldMethod();  // 适配
    }
}
```

### 装饰器模式 (Decorator)

```java
// 不改变原对象，动态添加功能
// Java IO 流：new BufferedReader(new FileReader("file.txt"))
// Spring 的 TransactionalAopProxy（事务代理包装了原始 Bean）

// 例子：给 Service 加缓存装饰
class CachedUserService implements UserService {
    private UserService delegate;  // 被装饰对象
    private Cache cache;

    @Override
    public User getUser(Long id) {
        User cached = cache.get(id);
        if (cached != null) return cached;
        User user = delegate.getUser(id);
        cache.put(id, user);
        return user;
    }
}
```

```java
// 提供统一的简单接口，隐藏内部复杂性
// Spring 的 JdbcTemplate 就是外观模式
// Controller → Service（Facade） → 多个底层 Service
```

### 享元模式 (Flyweight)

```java

// Integer 的 -128~127 缓存池就是享元模式
```

## 4. 行为型模式 (11 种)

### 策略模式 (Strategy)

```java
// 定义一组算法，运行时动态选择
@Service
public class PaymentService {
    private final Map<String, PaymentStrategy> strategies;

    // Spring 自动将所有的 PaymentStrategy Bean 注入到这个 Map
    public PaymentService(Map<String, PaymentStrategy> strategies) {
        this.strategies = strategies;
    }

    public void pay(String channel, BigDecimal amount) {
        PaymentStrategy strategy = strategies.get(channel);
        if (strategy == null) throw new IllegalArgumentException("不支持的支付方式: " + channel);
        strategy.pay(amount);
    }
}

public interface PaymentStrategy {
    void pay(BigDecimal amount);
}

@Component("alipay")
public class AlipayStrategy implements PaymentStrategy { ... }

@Component("wechat")
public class WechatPayStrategy implements PaymentStrategy { ... }
```

```java
// Spring Event 机制就是观察者模式

// Spring Boot 启动事件就是观察者模式：
```

### 模板方法模式 (Template Method)

```java
// 父类定义算法骨架，子类实现具体步骤
// JdbcTemplate、RestTemplate 都是模板方法模式！

public abstract class AbstractFileProcessor {
    // 模板方法（final，防止子类篡改流程）
    public final void process(String filePath) {
        openFile(filePath);         // 1. 打开（固定）
        String content = read();    // 2. 读取（固定）
        String processed = doProcess(content);  // 3. 处理（子类实现）
        save(processed);            // 4. 保存（固定）
        close();                    // 5. 关闭（固定）
    }
    // 钩子方法，子类选择性覆盖
    protected void afterProcess() { }
    // 抽象方法，子类必须实现
    protected abstract String doProcess(String content);
}
```

### 责任链模式 (Chain of Responsibility)

```java
// Servlet Filter Chain → 责任链模式
// Spring Security Filter Chain → 责任链模式
// Spring Interceptor 链 → 责任链模式

// 自己实现：
@Component
public class ValidateHandler extends AbstractHandler {

        if (request.getData() == null) {
            throw new BusinessException("数据为空");
        }
        if (next != null) next.handle(request);  // 交给下一个
    }
}
```

## 6. 架构模式与演进

### 6.1 系统架构演进

```
单体架构（Monolith）：
  一个 JAR/WAR 包包含所有功能
  优点：开发简单、部署简单、事务一致性好
  缺点：耦合重、难以扩展、启动慢、协作困难

SOA（Service-Oriented Architecture）：
  按业务拆分为多个服务，通过 ESB（企业服务总线）通信
  优点：服务化、可重用
  缺点：ESB 重、通信协议复杂、中心化

微服务（Microservices）：
  每个服务独立部署、独立数据库
  轻量级通信（HTTP/RPC）
  优点：独立扩展、技术异构、松耦合
  缺点：分布式复杂度（CAP、事务、运维）

服务网格（Service Mesh）：
  将服务治理下沉到 Sidecar 代理
  Istio = Envoy + Pilot
  当前主流微服务的下一阶段（但复杂度仍高）

Serverless：
  函数即服务（FaaS）
  不需要管理服务器
  适合：事件驱动、弹性伸缩场景
```

### 6.2 常见的架构模式

```
分层架构（Layered Architecture）：
  Controller → Service → Repository(Mapper) → DB
  最基础最常见

六边形架构（Hexagonal Architecture / 端口和适配器）：
  业务核心通过 Port（端口）对外交互
  Adapter（适配器）实现 Port
  解耦业务逻辑和外部依赖

整洁架构（Clean Architecture）：
  内层不依赖外层
  业务实体在内，UI/DB 在外

CQRS（Command Query Responsibility Segregation）：
  读和写分离
  写：走领域模型
  读：直接读优化过的查询模型（甚至不同数据库）

事件驱动架构（Event-Driven Architecture）：
  通过事件进行服务间通信
  松耦合、最终一致性

微内核架构（Microkernel）：
  核心系统 + 插件
  适合 IDE、规则引擎
```

## 7. DDD 领域驱动设计

### 7.1 核心概念

```
战略设计（Strategic Design）：
  限界上下文（Bounded Context）：
    一个领域模型的边界
    在边界内，术语有明确的含义
    通常一个微服务对应一个限界上下文

  上下文映射（Context Map）：
    多个限界上下文之间的关系
    如：共享内核、客户-供应商、防腐层、开放主机服务

  通用语言（Ubiquitous Language）：
    开发人员和领域专家共同使用的统一术语
    代码中的类名、方法名应该使用通用语言

战术设计（Tactical Design）：
  实体（Entity）：
    有唯一标识，可变
    如：User（ID = 123）

  值对象（Value Object）：
    无唯一标识，不可变
    如：Address（省+市+区+街道）、Money（金额+币种）

  聚合（Aggregate）：
    一组相关对象的集合
    通过聚合根（Aggregate Root）访问
    保证业务不变量
    如：Order（聚合根）→ OrderItem（聚合内实体）

  领域服务（Domain Service）：
    不属于任何实体或值对象的领域概念
    无状态的操作
    如：PricingService（计算价格）、TransferService（转账）

  领域事件（Domain Event）：
    领域中发生的有意义的事件
    如：OrderPlaced、UserRegistered

  仓储（Repository）：
    聚合的持久化接口
    保存和获取聚合
    如：OrderRepository

  工厂（Factory）：
    复杂对象的创建逻辑
    如：OrderFactory.createOrder()

  防腐层（Anti-Corruption Layer, ACL）：
    在上下文之间做转换
    防止外部模型污染内部领域模型
```

### 7.3 贫血模型 vs 充血模型

```
贫血模型（Anemic Domain Model）：
  Entity 只有属性 + getter/setter（纯数据载体）
  业务逻辑全在 Service 中
  优点：简单、上手快
  缺点：业务逻辑散落、违反封装
  现状：大多数项目都是贫血模型

充血模型（Rich Domain Model）：
  Entity 包含数据 + 行为
  业务逻辑在领域对象中
  Service 变薄，只做编排
  优点：封装好、可维护、符合 DDD
  缺点：对团队要求高、复杂

实际选择：
  简单 CRUD → 贫血模型（够用）
  复杂业务（电商、金融）→ 重点领域用充血模型（如订单、支付）
```

## 8. 实战：策略模式 + 工厂 + 注解

```java
// 一个完整的企业级策略模式示例：支付方式路由

// 1. 策略接口
public interface PayStrategy {
    PayType getType();       // 策略类型
    PayResult pay(PayRequest request);
}

// 2. 策略类型枚举
public enum PayType {
    ALIPAY, WECHAT_PAY, UNION_PAY, CREDIT_CARD
}

// 3. 具体策略实现
@Component
public class AlipayStrategy implements PayStrategy {
    @Override public PayType getType() { return PayType.ALIPAY; }
    @Override
    public PayResult pay(PayRequest request) {
        // 调用支付宝 SDK
        return new PayResult(true, "支付成功");
    }
}

@Component
public class WechatPayStrategy implements PayStrategy {
    @Override public PayType getType() { return PayType.WECHAT_PAY; }
    @Override
    public PayResult pay(PayRequest request) { ... }
}

// 4. 策略工厂（利用 Spring 容器注入）
@Component
public class PayStrategyFactory {
    // Spring 注入所有 PayStrategy Bean 到 Map<PayType, PayStrategy>
    private final Map<PayType, PayStrategy> strategyMap;

    public PayStrategyFactory(List<PayStrategy> strategies) {
        this.strategyMap = strategies.stream()
            .collect(Collectors.toMap(PayStrategy::getType, Function.identity()));
    }

    public PayStrategy getStrategy(PayType type) {
        PayStrategy strategy = strategyMap.get(type);
        if (strategy == null) throw new IllegalArgumentException("不支持的支付方式: " + type);
        return strategy;
    }
}

// 5. 使用
@Service
public class PayService {
    private final PayStrategyFactory factory;
    public PayResult pay(PayType type, PayRequest request) {
        return factory.getStrategy(type).pay(request);
    }
}
```

## 9. 常见面试题

### Q1: 你在项目中用过哪些设计模式？

```
示例回答（结合 Spring 生态）：

1. 单例模式：Spring Bean 默认就是单例
   控制反转和依赖注入就是基于单例模式

2. 代理模式：Spring AOP 中使用 JDK 动态代理 / CGLIB
   实现了事务、日志拦截等功能

3. 模板方法模式：使用了 JdbcTemplate、RestTemplate
   父类定义流程骨架，子类（回调）实现具体逻辑

4. 责任链模式：Spring Security 的 Filter Chain
   一个请求经过多个过滤器

5. 策略模式：项目中实现了支付方式路由
   根据支付类型选择不同的支付策略

6. 工厂模式：通过各种 FactoryBean 创建复杂 Bean
   如 SqlSessionFactoryBean、KafkaListenerContainerFactory

7. 建造者模式：构造复杂 DTO
   使用 Lombok @Builder
```

### Q2: DDD 的核心概念是什么？值得用吗？

```
核心概念：
  限界上下文：划分微服务边界的依据
  聚合：数据一致性边界
  领域事件：服务间解耦

值得用的场景：
  - 业务复杂（支付、风控、保险、供应链）
  - 代码迭代频繁，逻辑越来越乱
  - 团队对 DDD 有基本了解

不值得用的场景：
  - 简单 CRUD（管理后台等）
  - 团队不熟悉，学习成本高
  - 交付压力大

折中：
  战术设计慢慢引入（聚合、领域事件、防腐层）
  不一定要全盘引用 DDD
  核心业务领域充血的模型，非核心继续贫血
```
