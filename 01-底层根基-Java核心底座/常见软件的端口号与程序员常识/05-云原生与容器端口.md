## 1. Docker 端口映射

> **背景**：容器有独立网络命名空间——容器内端口宿主不可达，需要 `-p` 映射。
> **目的**：掌握 Docker 端口映射语法与常见问题。
> **适用范围**：Docker 部署的容器服务。
> **前提假设**：映射是「宿主端口 ↔ 容器端口」的桥（底层 iptables DNAT）。

```bash
# 端口映射语法：-p [宿主IP:]宿主端口:容器端口[/协议]

# 最简（随机宿主端口）
docker run -p 8080 myapp            # 宿主随机端口 → 容器 8080
docker port <容器>                  # 查看实际映射

# 标准映射（指定端口）
docker run -p 8080:8080 myapp

# 指定协议
docker run -p 8080:8080/tcp -p 53:53/udp myapp

# 仅本机（安全——调试端口）
docker run -p 127.0.0.1:5005:5005 myapp

# 多端口
docker run -p 8080:8080 -p 9090:9090 myapp

# docker-compose
services:
  app:
    ports:
      - "8080:8080"
      - "127.0.0.1:5005:5005"
```

```text
Docker 端口映射要点
├── ① 宿主端口冲突 → 启动失败（bind 错误）
├── ② host 网络模式：无映射（直接用宿主端口）——-p 无效！
├── ③ 容器间通信：同网络用容器名直连（不需要 -p）
├── ④ 映射查看：docker ps（PORTS 列）/ docker port
└── ⑤ 底层机制：iptables DNAT（见端口转发系列）
```

## 2. Docker 网络模式与端口

### 2.1 网络模式对比

| 模式 | 端口行为 | 适用 |
|------|---------|------|
| **bridge（默认）** | -p 映射（iptables DNAT） | 单机标准 |
| **host** | 直接用宿主端口（-p 无效！） | 高性能/UDP |
| **none** | 无网络 | 隔离场景 |
| **overlay** | Swarm 跨主机 | 集群 |

```bash
# host 模式（端口直接暴露在宿主）
docker run --network host myapp
# ⚠️ 容器监听的端口 = 宿主端口（无需 -p 也无法 -p）
# ⚠️ 端口冲突：容器端口与宿主已有服务冲突即失败
```

### 2.2 容器间通信（不走 -p）

```text
容器间通信的正确方式
├── ① 同 bridge 网络：容器名直连
│   docker run --network mynet --name app1 ...
│   docker run --network mynet --name app2 ...
│   app2 访问 app1：http://app1:8080（容器名解析）
├── ② ⚠️ 常见错误：容器间用宿主 IP + 映射端口（绕远且脆弱）
└── ③ 金句：-p 是「宿主↔容器」的桥，不是「容器↔容器」的桥
```

## 3. K8s 端口暴露体系

### 3.1 四层暴露方式

| 方式 | 层级 | 场景 | 端口说明 |
|------|:---:|------|---------|
| **ClusterIP** | 集群内 | 服务间调用 | 任意端口（集群内） |
| **NodePort** | 节点端口 | 集群外简单访问 | 30000-32767 |
| **LoadBalancer** | 云 LB | 云环境公网 | 云分配 |
| **Ingress** | 七层 | HTTP 生产标准 | 80/443 入口 |

### 3.2 NodePort 示例

```yaml
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  type: NodePort
  selector:
    app: order
  ports:
    - port: 8080              # 集群内访问端口
      targetPort: 8080        # Pod 容器端口
      nodePort: 30080         # 节点暴露端口（30000-32767）
# 访问：http://任意节点IP:30080
```

### 3.3 Ingress（生产标准）

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: order-ingress
spec:
  rules:
    - host: order.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: order-service
                port:
                  number: 8080
# 链路：443（Ingress Controller）→ 8080（Service）→ Pod 端口
```

```text
K8s 端口体系要点
├── ① Pod 内端口：应用自己监听（可任意）
├── ② Service 端口：集群内访问（port → targetPort）
├── ③ NodePort：节点暴露（30000-32767 范围）
├── ④ Ingress：80/443 统一入口（生产标准）
└── ⑤ 金句：K8s 端口是「多层映射」——Ingress → Service → Pod
```

## 4. K8s 组件端口

| 端口 | 组件 | 说明 |
|:---:|------|------|
| **6443** | API Server | K8s 管理入口（HTTPS） |
| **2379/2380** | etcd | 配置存储 / 集群通信 |
| **10250** | Kubelet | 节点代理（metrics/exec） |
| **10255** | Kubelet | 只读端口（旧） |
| **10256** | Kube-Proxy | 健康检查 |
| **30000-32767** | NodePort | 服务暴露范围 |

```text
K8s 组件端口要点
├── ① API Server(6443)：所有管理操作入口
│   ├── kubectl 连接该端口
│   └── 公网暴露需鉴权（kubeconfig 证书）
├── ② etcd(2379)：集群状态存储（K8s 的「大脑」）
│   ├── ⚠️ 公网暴露 etcd = 集群被接管（经典攻击）
│   └── 内网 + TLS + 防火墙
├── ③ Kubelet(10250)：节点管理
│   └── 公网暴露 = 节点被控制（高危）
└── ④ 2026 安全实践：
    ├── 控制平面组件内网隔离
    ├── 防火墙限源（管理网段）
    └── RBAC + TLS 认证
```

## 5. 容器端口常见问题

| # | 问题 | 根因 | 解法 |
|---|------|------|------|
| 1 | **-p 后启动失败** | 宿主端口被占 | 换端口/杀占用 |
| 2 | **host 模式 -p 无效** | host 无网络隔离 | 不写 -p |
| 3 | **容器间连不上** | 用宿主 IP + 映射（绕远） | 同网络容器名直连 |
| 4 | **外部访问不通** | 防火墙/安全组未放行宿主端口 | 三层链路放行 |
| 5 | **容器重启端口丢** | 无 -p 声明 | compose/编排文件声明 |
| 6 | **NodePort 超范围** | 非 30000-32767 | 用范围内端口 |
| 7 | **端口映射后还是不通** | 应用绑定 127.0.0.1（容器内） | 应用绑定 0.0.0.0 |
| 8 | **curl 本机容器端口通、外部不通** | 防火墙层 | 云安全组 + 本机防火墙 |

```text
容器端口排查三板斧
├── ① 容器内验证：docker exec <容器> curl localhost:端口
│   ├── 通 → 容器内 OK（查映射/防火墙）
│   └── 不通 → 应用问题（绑定地址/未启动）
├── ② 宿主验证：curl localhost:宿主端口
│   ├── 通 → 容器 OK（查外部防火墙）
│   └── 不通 → 映射问题（docker ps 看映射）
├── ③ 外部验证：nc -vz 宿主IP 端口
│   └── 不通 → 防火墙/安全组
→ 金句：容器端口问题按「容器内 → 宿主 → 外部」三层排查
```

## 6. 云环境端口（安全组）

### 6.1 三层链路

> ⚠️ **云环境端口暴露 = 三层都要放行**：

```text
云环境端口链路（三层缺一不通）
① 云安全组（控制台）
   └── 入方向规则（端口 + 来源 IP）
② 宿主防火墙（ufw/firewalld/iptables）
   └── 放行端口
③ 容器映射 / 应用监听
   └── -p 映射 + 应用绑定 0.0.0.0

经典故障：安全组放了、应用绑了，但宿主 ufw 没放 → 不通
```

### 6.2 云端口安全实践

```text
云端口安全基线（2026）
├── ① 最小化：只开必要端口（80/443 + 管理端口限源）
├── ② 来源限制：管理端口只允许办公 IP
├── ③ 高危端口：22/3389 改端口 + 限源
├── ④ 数据库：私有子网（无公网路由）
├── ⑤ 安全组 vs 防火墙：两层都配（纵深防御）
├── ⑥ 国内合规：Web 服务需 ICP 备案（80/443）
└── ⑦ 定期审计：安全组规则巡检（多余规则清理）
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. Docker -p 是「宿主↔容器」的桥（底层 iptables DNAT）——host 模式 -p 无效
> 2. 容器间通信用网络名直连（不走 -p 映射）——绕远是常见错误
> 3. K8s 四层暴露：ClusterIP（集群内）/NodePort（30000-32767）/LoadBalancer（云）/Ingress（生产标准）
> 4. K8s 组件端口：API Server 6443 + etcd 2379 + Kubelet 10250——**公网暴露 = 集群被接管**
> 5. 容器端口排查三层：容器内（docker exec）→ 宿主（curl）→ 外部（nc）
> 6. 云环境三层链路：安全组 → 宿主防火墙 → 容器映射——**任一层拦截都不通**
