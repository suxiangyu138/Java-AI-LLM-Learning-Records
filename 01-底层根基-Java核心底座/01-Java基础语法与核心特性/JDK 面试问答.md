# JDK 面试问答

### Q1. JDK、JRE、JVM 有什么区别？

**口述答案**

JVM 是执行字节码的虚拟机，负责类加载、内存管理、即时编译，它是规范，HotSpot 是具体实现。JRE 是运行环境，等于 JVM 加核心类库，只能跑不能编译。JDK 是开发工具包，等于 JRE 加 javac、javap、jstack 这些工具。

JDK 9 之后安装目录里不再单独提供 JRE，需要的话用 jlink 自己裁一个运行时镜像，所以现在部署其实未必要装完整 JDK。面试常追问这一点，答案是模块化之后运行时可以按需组装，不再需要一个大而全的 JRE。这一点在容器化部署里尤其明显，基础镜像能小一半。

---

### Q2. 新项目你会选哪个 JDK 版本？为什么？

**口述答案**

新项目直接上最新的 LTS，现在就是 JDK 25，下一个 LTS 是 29。理由有三点：

- LTS 有长期补丁，生态支持最完整
- 虚拟线程、record、模式匹配这些在 21 之后都稳定了
- Spring Boot 3.x 起最低要求 17，4.x 基线更高，跟着框架走不会踩坑

老项目升级主要看依赖，Spring Boot 2.x 最多到 17，Jakarta 包名迁移是升级路上最大的坑。选型不是越新越好，还要看团队用到的中间件和构建工具支持到哪个版本。所以升级一般安排在季度初，留出两到三周的回归时间，别赶在版本发布前动。

---

### Q3. JDK 8 有哪些关键特性？现在还重要吗？

**口述答案**

8 是分水岭。Lambda 和 Stream 把函数式编程带进 Java，Optional 缓解空指针，接口可以有默认方法和静态方法，java.time 替换掉线程不安全的 Date 和 Calendar，永久代换成 Metaspace。

这些到今天还是面试和代码 review 的高频点，比如 Stream 的中间操作和终端操作怎么区分、并行流在 IO 密集场景为什么反而更慢、Optional 为什么不适合当方法参数。大量老系统还停在 8，所以这些特性必须熟。这部分面试里基本每轮都会问到，属于必须熟到条件反射的内容，不能只背结论。

---

### Q4. JDK 17 相比 11 有哪些值得说的变化？

**口述答案**

主要是语言层的模式匹配起步和平台层的强封装。record 让不可变数据类一行写完，sealed 限制继承体系，instanceof 模式匹配省掉强转。

平台层把 JDK 内部 API 默认强封装，反射访问 sun.misc 这类包要加 --add-opens。SecurityManager 被标记废弃。同时移除了 Nashorn 和实验性的 AOT、JIT 工具。所以从 11 升 17，业务代码改动不大，麻烦的是反射和第三方依赖。升级前先用 jdeps 扫一遍依赖，再补上 --add-opens，基本就能过。

---

### Q5. JDK 21 的虚拟线程解决了什么问题？

**口述答案**

解决的是阻塞式 IO 下线程太贵的问题。平台线程一对一映射内核线程，一个线程几 MB 栈，几千个就到顶了。虚拟线程由 JVM 调度，栈存在堆上，挂起时不占内核线程，几万个也没压力。

用法上不要池化，直接 Thread.ofVirtual 或者 newVirtualThreadPerTaskExecutor。要注意虚拟线程里用 synchronized 包住阻塞调用会钉住载体线程，JDK 24 的 JEP 491 已经修了。另外它不适合 CPU 密集任务，调度开销反而比平台线程高，这两点面试里经常被追问。

---

### Q6. JDK 21 除了虚拟线程还有什么？

**口述答案**

还有三块：

- 分代 ZGC 转正，把 ZGC 的低停顿和吞吐结合起来
- record patterns 支持在模式匹配里解构 record
- switch 的模式匹配转正，配合 sealed 能做穷尽性检查，漏分支编译期就报错

另外 Sequenced Collections 给集合补了统一的 first、last、reversed 接口，不用再区分 List 和 Deque 的写法。这几项合起来，写不可变数据和分支逻辑舒服很多。面试里常和 17 的 record、sealed 串起来问，考的是语言演进的主线。 这三块合起来才是 21 的完整面貌。

---

### Q7. JDK 25 作为最新 LTS 有什么值得关注？

**口述答案**

值得关注的有三块：

- Scoped Values 转正，用来替代 ThreadLocal 在虚拟线程场景下的传递问题，作用域结束自动释放
- 紧凑对象头转正，对象头压到 64 位，堆占用能明显下降
- 结构化并发还在预览，StructuredTaskScope 把一组子任务当成一个整体管理，失败就整体取消

另外模块导入声明和紧凑源文件也转正了，写小脚本不用再套 class。25 发布后 21 仍是最稳的过渡选择。对企业来说，25 的主要吸引力是 GC 和对象布局的优化，语言特性反而是次要的，升级前要先压测。

---

### Q8. OpenJDK 和 Oracle JDK 有什么区别？商用要注意什么？

**口述答案**

OpenJDK 是开源参考实现，Oracle JDK 是在它基础上加了商业支持的发行版。授权上 Oracle JDK 从 17 起用免费条款，免费商用但有到期后转收费的风险。OpenJDK 各发行版比如 Temurin、Zulu、Corretto 都是 GPLv2 加类路径例外，可以放心商用。

国内常用阿里 Dragonwell 和腾讯 Kona。生产环境一般选发行版而不是 Oracle JDK，补丁和升级路径更可控。选发行版还要看厂商的补丁节奏，安全漏洞的修复速度比版本号更重要。 这两个方法名只差一个单词，面试里经常故意混着问。

---

### Q9. javac 的 --release 和 -source、-target 有什么区别？

**口述答案**

-source 和 -target 只控制语法和字节码版本，不限制你调用的 API。所以在新 JDK 上编译、在旧 JRE 上运行，很可能用到旧版本没有的方法，运行时抛 NoSuchMethodError。

--release 除了设定版本，还会用对应版本的 API 签名做校验，编译期就能发现越界调用。所以交叉编译一律用 --release，Maven 里对应 maven.compiler.release，Gradle 用 toolchain，别再混用 sourceCompatibility 和 targetCompatibility。

---

### Q10. javap 是干什么的？什么时候会用到？

**口述答案**

javap 是字节码反汇编工具，把 class 文件还原成可读的字段、方法、常量池和指令。常用来验证语法糖的真实行为，比如泛型擦除后的 Signature、桥方法的 ACC_BRIDGE 标志、字符串拼接在 JDK 9 之后编译成 invokedynamic、lambda 编译成私有方法加 invokedynamic。

参数上 -c 看指令，-v 看常量池和属性，-p 显示私有成员。排查编译期问题时，javap 比看源码更直接，能确认编译器到底生成了什么。尤其是排查 NoSuchMethodError 这类问题，先 javap 确认调用点，比猜依赖快得多。

---

### Q11. jlink 和 jpackage 分别解决什么问题？

**口述答案**

jlink 裁剪运行时镜像。它基于模块系统，先用 jdeps 分析应用依赖哪些模块，再只把需要的模块打进镜像，一个 Spring Boot 应用的运行时能从两百多 MB 降到五六十 MB。

jpackage 是 JDK 14 起的打包工具，把应用和裁剪后的运行时打成 exe、dmg、deb 这类原生安装包，用户双击就能装，不需要预装 Java。两者通常配合使用，先 jlink 裁运行时，再 jpackage 打成安装包。如果应用不是模块化的，jlink 要先用 jdeps 推导模块，这一步容易失败，得留调试时间。

---

### Q12. jps 和 jstat 怎么用？

**口述答案**

jps 列出当前用户的 Java 进程和主类，-l 显示完整类名，-v 显示 JVM 参数，-m 显示 main 参数，排查前先用它拿 pid。

jstat 看 JVM 统计，最常用 -gcutil，按固定间隔打印各代使用率和 GC 次数、耗时，用来判断 GC 是不是频繁、老年代是不是快满了。两个工具都很轻量，生产上可以放心用，不像 jmap 导出堆快照会停顿。实际排查顺序是先 jps 拿 pid，再 jstat 看趋势，最后才用 jstack 和 jmap 做深度分析。另外 jstat 的 -gc 选项能看更细的分代容量变化。 别把 jstat 当实时监控用，它是采样不是告警。

---

### Q13. jstat -gcutil 的输出怎么读？

**口述答案**

输出里 S0、S1、E、O、M 分别是两个 Survivor、Eden、老年代、Metaspace 的使用百分比，CCS 是压缩类空间，YGC 和 YGCT 是年轻代 GC 次数和累计耗时，FGC 和 FGCT 是老年代次数和累计耗时，GCT 是总耗时。

判断主要看三点：FGC 是否持续增长、FGCT 占总运行时间的比例、以及 Full GC 之后老年代使用率能不能降下来。如果 FGC 在涨但老年代降不下来，基本就是内存泄漏，下一步直接导堆。另外 Metaspace 持续上涨通常是类加载泄漏，和堆内存是两条独立的排查线。

### Q14. 线上 CPU 飙高怎么排查？

**口述答案**

三步：

- 先用 top -Hp 找到进程里最耗 CPU 的线程，记下十进制 tid
- 再把 tid 转成十六进制，jstack 导出线程栈后按 nid 搜
- 最后看这个线程在干什么，停在业务方法上就顺着栈往下找，如果一直是 GC 线程在跑，那说明根因是内存不是 CPU

线上更常用 Arthas 的 thread -n 3，一步就能看到最忙的三个线程和它们的栈。还要区分用户态和内核态，内核态高往往是锁竞争或者系统调用。如果大量线程停在同一个方法上，还要回头看是不是限流没做好，或者下游超时引发了重试风暴。 排查完最好把线程栈留存下来，方便事后复盘。

### Q15. 死锁怎么排查？

**口述答案**

jstack 导出的线程栈会直接打印 Found one Java-level deadlock，把涉及的线程、持有的锁、等待的锁都列出来。

没有自动检测的话，就看处于 BLOCKED 状态的线程，加 -l 参数能看到它等的是哪个锁对象，再找哪个线程持有这个锁，形成环就是死锁。定位到代码后一般是加锁顺序不一致，统一加锁顺序，或者用 tryLock 带超时。线上更稳妥的做法是给锁加超时和降级，死锁一旦发生，重启只能止血不能治本。排查完记得在代码评审里补一条锁顺序规范，避免同类问题复发。

---

### Q16. 线上 OOM 怎么排查？

**口述答案**

先看异常信息里的区域。Java heap space 是堆，Metaspace 是元空间，unable to create native thread 是线程数打满，三种方向完全不同。

堆 OOM 要提前开 HeapDumpOnOutOfMemoryError 落 dump，再用 MAT 看支配树和 GC Roots 引用链，找谁在持有对象。常见原因是集合只增不减、缓存没设上限、大对象一次读进内存、ThreadLocal 用完没 remove。拿到 dump 后先看最大的几个对象，再看是不是同一个集合在无限增长。

---

### Q17. jmap 和 jcmd 有什么区别？生产上该用哪个？

**口述答案**

jmap 是老工具，-histo 看对象直方图，-dump 导堆快照，但 dump 时会 STW，对生产有影响。

jcmd 是 JDK 7 起的统一入口，一个命令覆盖 jmap、jstack、jinfo 的能力，比如 jcmd pid GC.heap_dump、Thread.print、VM.flags、VM.system_properties。新版本优先用 jcmd，jmap 在高版本上部分功能已经受限，而且 jcmd 的参数更清晰。脚本里统一用 jcmd，参数稳定，输出也更好解析。 生产环境优先保证可用性，能不停顿就不停顿。

---

### Q18. JFR 是什么？和传统 profiler 有什么区别？

**口述答案**

JFR 是 JDK 内置的飞行记录器，用环形缓冲区记录事件，开销通常在百分之一以内，可以长期开着。它记录的不只是 CPU 采样，还有 GC、锁竞争、线程调度、IO、异常和方法采样，事后用 JMC 按时间线还原现场。

传统 profiler 靠采样或字节码增强，开销大，一般只在压测时开。所以排查偶发的线上问题，JFR 比 profiler 更合适，可以配置持续记录，出问题时把最近几分钟的录制导出来。JFR 的另一个优势是跨版本稳定，JDK 11 之后用法基本一致，做性能基线很方便。 两者的定位不同，一个做长期观测，一个做定点压测。

### Q19. Arthas 常用命令有哪些？

**口述答案**

常用的有五个：

- dashboard 看整体面板，线程、内存、GC 一屏
- thread 看线程状态和 CPU 占用，thread -b 直接找阻塞别人的线程
- trace 看某个方法的调用链路和每层耗时
- watch 看入参、返回值和异常
- stack 看这个方法被谁调用

它 attach 到运行中的进程，不用重启，线上排查很方便。但别在高频方法上开 trace，会把应用拖慢，最好指定次数，只抓一次请求就停。除此之外还有 JDK 自带的 jcmd 和 JFR，简单场景先用自带工具，复杂链路再上 Arthas。

### Q20. 线上接口突然变慢，你会怎么定位？

**口述答案**

先分层定位。看监控是单机还是全机，全机就先查下游依赖和数据库。单机就用 Arthas 的 trace 看耗时卡在哪一层，再配合 jstack 看线程是不是都卡在同一个锁或者连接池上。

同时用 jstat -gcutil 看 GC 频率和老年代占用，排除 GC 抖动。最后看慢请求日志和链路追踪，确认是自身逻辑、下游超时还是数据库慢查询。顺序一定是从外到内，先排除下游和 GC，再看自身代码。定位完要把结论回填到监控和告警里，下一次同类问题应该由系统先发现。如果只有个别接口慢，优先查这条链路依赖的下游服务。
