## 1. 高并发场景选型题

### 1.1 高并发下为什么选 ConcurrentHashMap 而不是 HashMap / Hashtable？

**参考答案（三层递进）：**

| 方案 | 问题 | 结论 |
|------|------|------|
| HashMap | 并发 put 丢数据、JDK7 扩容死循环 | ❌ 绝不用于并发写 |
| Hashtable | 全方法一把锁，读读互斥，并发度 0 | ❌ 性能太差 |
| **ConcurrentHashMap** | CAS + 锁桶头节点，读无锁 | ✅ 并发读最优 |

**加分表达：** "选型不是背结论，是分析成本 — HashMap 的代价是数据正确性（丢/环），Hashtable 的代价是吞吐（全局锁），CHM 用锁粒度细化把代价降到桶级；JDK8 用 synchronized 锁桶是因为 JDK6+ 锁优化后它并不比 ReentrantLock 慢，还省去 try-finally。"

### 1.2 设计一个高并发线程池，参数怎么定？

```text
场景：订单创建接口，QPS 500，其中 IO 操作（DB+Redis）占比 80%
推算：
  单请求耗时 ~50ms（20ms CPU 计算 + 80% 时间等待 IO）
  核心线程数 = CPU 核数 × (1 + 等待/计算) = 8 × (1 + 4) = 40 左右
  队列：有界 ArrayBlockingQueue(2000)，拒绝策略 CallerRunsPolicy（削峰+保底）
  线程工厂：命名 order-exec-{n}，非守护线程
  线程池隔离：订单/库存/用户 三个独立池，防止互相拖垮
```

**追问变体：** 队列和拒绝策略为什么这样选？→ 有界防 OOM；CallerRuns 让调用线程兜底，削峰同时保证不丢任务（比抛异常温和）。如果 QPS 高峰远超处理能力怎么办？→ 前置限流（Sentinel/令牌桶）+ 消息队列削峰，线程池不是万能的。

### 1.3 什么场景用 ReentrantLock 而不是 synchronized？

**参考答案：**

```java
// 必须用 ReentrantLock 的场景
// ① 超时获取：防止永久阻塞
if (lock.tryLock(2, TimeUnit.SECONDS)) {
    try { /* 临界区 */ } finally { lock.unlock(); }
}
// ② 可中断：取消操作时释放
lock.lockInterruptibly();
// ③ 多条件队列：生产者-消费者，两个 condition 分别唤醒
Condition notFull = lock.newCondition();
Condition notEmpty = lock.newCondition();
```

**普通场景**（无上述需求）：synchronized — 语法简洁、JVM 锁优化成熟、自动释放不写错。

### 1.4 用 volatile 还是 AtomicInteger 还是 LongAdder 做计数器？

| 场景 | 选择 | 原因 |
|------|------|------|
| 状态标志（一写多读） | volatile | 只要求可见性 |
| 中低竞争计数 | AtomicInteger | CAS 自旋足够 |
| 高竞争计数（如埋点、统计） | **LongAdder** | 分段累加，争用分散 |
| 需要原子更新的复合操作 | AtomicReference + CAS 循环 | 单变量不够 |

## 2. 性能定位与线上排查题

### 2.1 线上 CPU 100% 怎么排查？

**参考答案（标准五步）：**

```bash
# ① 定位进程
top                          # 找 CPU 最高的 Java 进程 PID
# ② 定位线程（CPU 占用在 OS 线程上）
top -Hp <pid>                # 记录最高的线程 TID
# ③ 转十六进制（jstack 中 nid 是十六进制）
printf '%x\n' <TID>          # 如 0x2f3a
# ④ 看线程栈
jstack <pid> | grep -A 30 '0x2f3a'
# ⑤ 定位代码：栈顶业务方法 → 排查死循环/正则回溯/大对象分配
```

**常见根因：** 死循环、正则灾难性回溯（嵌套量词）、日志刷屏（log.info 高频调用）、GC 线程占高（堆不足 → 转移查堆）。

### 2.2 内存持续增长（疑似泄漏）怎么排查？

```bash
# ① 确认趋势：内存只涨不跌
jstat -gc <pid> 5000            # 看 heap 使用率曲线
# ② 触发堆转储（生产：-XX:+HeapDumpOnOutOfMemoryError 自动 dump）
jmap -dump:format=b,file=heap.hprof <pid>
# ③ MAT 分析：Dominator Tree → 保留大小 Top 对象 → GC Root 引用链
# ④ 定位泄漏模式
```

**高频泄漏模式：** 静态集合只增不减、ThreadLocal 未 remove（线程池线程长期存活）、缓存无淘汰策略（HashMap 当缓存）、Stream/连接未关闭。

**追问：** 为什么 MAT 能定位？→ 可达性分析：堆转储后 MAT 反查每个大对象的 GC Roots 引用路径，泄漏对象的路径上一定有"不该持有的持有者"（如 static 字段、线程栈）。

### 2.3 Full GC 频繁，代码没问题的前提下怎么调？

```text
① 先量化：jstat 看 Full GC 频率/耗时、各代占用
② 检查大对象：PretenureSizeThreshold 外的大对象直入老年代占空间
③ 检查参数：-Xms=-Xmx（避免抖动）、Survivor 够不够（对象晋升过快）
④ 换收集器：CMS 碎片 → G1（分区复制无碎片）；延迟敏感大堆 → ZGC
⑤ 停 System.gc()：RMI 定期 Full GC（-Dsun.rmi.dgc.client.gcInterval 调大）
```

## 3. 设计权衡与实战改造题

### 3.1 单例模式：为什么 DCL 要加 volatile？

```java
// 双重检查锁（DCL）
public class Singleton {
    private static volatile Singleton instance;    // ⚠️ volatile 不能省
    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查（无锁）
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查（有锁）
                    instance = new Singleton();    // 非原子！
                }
            }
        }
        return instance;
    }
}
```

**参考答案：** `new Singleton()` 三步骤：① 分配内存 ② 初始化字段 ③ 引用赋值。**②③ 可能被重排** — 线程 A 先执行③后②，线程 B 在第一检查处拿到"半初始化"对象。volatile 禁止重排，保证"先完成初始化再发布引用"。

**追问：** 为什么用局部变量再赋值（JDK 优化写法）？→ 减少 volatile 读次数，性能更好。

### 3.2 秒杀/限流场景：Semaphore 还是令牌桶？

| 工具 | 机制 | 适用 |
|------|------|------|
| Semaphore | 固定许可数，acquire 阻塞 | 控制并发连接数（连接池） |
| 令牌桶（Guava RateLimiter / 自研） | 按速率发放令牌 | **平滑限流**（突发+匀速） |
| 漏桶 | 恒定速率流出 | 削峰填谷（对突发不友好） |

**面试表达：** "限流本质是'流量整形'，令牌桶允许一定突发（桶容量），漏桶严格匀速；秒杀场景常是 网关层令牌桶 + 服务层信号量双保险，前端还做按钮置灰、后端做防重。"

### 3.3 异步任务：MQ 还是线程池还是 CompletableFuture？

| 方案 | 特点 | 场景 |
|------|------|------|
| 线程池 execute | 快、简单，但**丢失不可恢复** | 非关键异步（日志、通知） |
| MQ（RocketMQ/Kafka） | 可靠投递、削峰、重试 | 关键业务异步（订单状态同步） |
| CompletableFuture | 同进程编排、依赖组合 | 并行聚合调用（查库存+查用户+查优惠组装） |

**追问：** 发短信/订单推送用哪种？→ MQ：失败可重试、可追踪；直接线程池丢任务无法补偿。

## 4. 经典连环追问链

### 4.1 追问题：HashMap 一条链问到底

```text
Q1: HashMap 底层结构？          → 数组+链表+红黑树（JDK8）
Q2: 什么时候转红黑树？          → 链表≥8 且数组≥64
Q3: 为什么是 8？                → 泊松分布概率（千万分之六），防碰撞攻击
Q4: 为什么还要数组≥64？         → 数组太短先扩容让数据散开
Q5: 为什么容量是 2 的幂？       → (n-1)&hash 位运算取模；扩容元素只移"原位"或"原位+旧容量"
Q6: 线程安全吗？                → 不安全（丢数据；JDK7 头插死循环）
Q7: 并发用什么？                → ConcurrentHashMap
Q8: CHM 怎么保证并发？          → JDK8: CAS + synchronized 锁桶头 + volatile 读
Q9: 为什么 JDK8 放弃分段锁？    → 锁粒度细（桶级）、并发度随扩容提升、内存开销小
Q10: CHM 的 key/value 能是 null？→ 不能（设计选择），HashMap 可以
```

**答题策略：** 每答一层，主动把"为什么"讲出来 — 面试官问 Q3 时主动带出 Q4/Q5 的动机，展示体系化理解。

### 4.2 追问题：线程池一条链问到底

```text
Q1: 线程池核心参数？            → 7 参数
Q2: 任务提交执行流程？          → 核心线程→队列→非核心→拒绝
Q3: 队列为什么用有界？          → 无界 OOM
Q4: 拒绝策略选什么？            → 业务兜底 CallerRuns / 丢弃看场景
Q5: 核心线程数怎么定？          → CPU 密集 N+1；IO 密集 N×(1+等待/计算)
Q6: Executors 为什么不行？      → 无界队列/无界线程数
Q7: 线程池异常怎么处理？        → execute 吞异常 vs submit+get 抛异常
Q8: 线程池中的线程退出会怎样？  → Worker 执行完任务，keepAlive 后回收；异常退出由线程工厂补充
Q9: 怎么优雅关闭？              → shutdown（等任务）→ awaitTermination → shutdownNow（中断）
```

### 4.3 追问题：GC 一条链问到底

```text
Q1: 对象什么时候被回收？       → GC Roots 不可达
Q2: GC Roots 有哪些？           → 栈帧局部变量/静态字段/常量/JNI/锁对象
Q3: 怎么回收？                  → 标记-清除/复制/整理
Q4: 新生代为什么用复制？        → 存活率低（弱分代假说）
Q5: 老年代呢？                  → 存活率高，标记-整理
Q6: 选什么收集器？              → G1（默认）/ ZGC（大堆低延迟）
Q7: G1 为什么能控制停顿？       → Region 分区 + 收益优先回收 + 可设停顿目标
Q8: 线上 Full GC 频繁怎么办？   → 五步排查（见 04 模块 6.2）
```
