## 1. 集合体系总览

### 1.1 集合框架的整体结构？

```text
Collection（单列）
├── List（有序可重复）：ArrayList / LinkedList / Vector
├── Set（无序不可重复）：HashSet / LinkedHashSet / TreeSet
└── Queue（队列）：ArrayDeque / PriorityQueue / LinkedList

Map（键值对）
├── HashMap / LinkedHashMap / TreeMap
├── ConcurrentHashMap（并发）
└── Hashtable（古老同步类）
```

**追问：** Collection 和 Collections？→ Collection 是接口（集合根）；Collections 是工具类（排序/反转/同步包装）。Iterator 与 Iterable？→ Iterable 可被遍历（提供 iterator()），Iterator 是遍历器本身（hasNext/next/remove）。

### 1.2 fail-fast 与 fail-safe？

| 对比 | fail-fast（快速失败） | fail-safe（安全失败） |
|------|----------------------|----------------------|
| 机制 | 遍历时修改结构（add/remove）直接抛 ConcurrentModificationException | 遍历副本（CopyOnWriteArrayList、ConcurrentHashMap 的迭代器） |
| 实现 | modCount 计数器校验 | 快照/弱一致 |
| 代价 | 抛异常 | 读到的数据可能不是最新 |

```java
List<String> list = new ArrayList<>(List.of("a", "b"));
for (String s : list) {      // 增强 for 底层是 iterator
    if (s.equals("a")) list.remove(s);   // ❌ ConcurrentModificationException
}
// ✅ 用 iterator.remove() 或 Collectors 过滤
```

**追问：** 单线程里为什么也抛？→ modCount 被修改，迭代器校验 `expectedModCount != modCount` 即抛。CopyOnWriteArrayList 读多写少为什么高效？→ 写时复制数组，读无需锁（读的是快照）。

## 2. HashMap 全链路深挖

### 2.1 HashMap 底层数据结构？

**参考答案（JDK8）：**

| 版本 | 结构 |
|------|------|
| JDK7 | 数组 + 链表（头插法） |
| **JDK8** | **数组 + 链表 + 红黑树**（尾插法） |

| 关键参数 | 值 | 含义 |
|----------|-----|------|
| 默认容量 | 16 | 数组长度，2 的幂 |
| 负载因子 | 0.75 | size > 容量 × 0.75 触发扩容 |
| 树化阈值 | 8 | 链表长度 ≥ 8 且数组长度 ≥ 64 转红黑树 |
| 退化阈值 | 6 | 红黑树节点 < 6 转回链表 |
| 扩容倍数 | 2 | 容量翻倍，rehash |

**追问：**
- 为什么树化条件是 8？→ 泊松分布：负载因子 0.75 下，链表长度 8 的概率约千万分之六，极低 — 树化是防御性措施（抗哈希碰撞攻击）
- 为什么转红黑树还要数组 ≥ 64？→ 数组太短时优先扩容，让数据散开
- 为什么负载因子是 0.75？→ 时空权衡：0.75 时哈希碰撞率与空间浪费率平衡

**记忆点：**
> 🎯 **8 是"巧合概率"（泊松分布），64 是"散不开就先扩容"，0.75 是"时空平衡点"** — 三个数字背后的设计动机比数字本身重要。

### 2.2 HashMap put 的完整流程？

```text
put(key, value)
├── ① key.hashCode() → 扰动：hash ^ (hash >>> 16)
├── ② (n - 1) & hash → 桶下标
├── ③ 桶为空 → 直接 new Node 放入
├── ④ 桶非空 → equals 比较 key：
│       ├── 相同 → 覆盖 value（返回旧值）
│       └── 不同 → 挂链表（尾插）/ 红黑树插入
├── ⑤ 链表长度 ≥ 8 且数组 ≥ 64 → 树化
└── ⑥ size+1 > 阈值 → 扩容（resize，2 倍）
```

**追问：** 为什么容量必须是 2 的幂？→ 下标计算 `(n-1) & hash` 等价于取模且更快；扩容时元素要么原位要么移动"原下标 + 旧容量"，无需重新计算 hash（通过 hash & oldCap 判断）。

### 2.3 JDK7 扩容死循环问题？

**参考答案：** JDK7 头插法 + 并发扩容时，两个线程同时 rehash 可能形成环形链表 → `get` 时死循环。JDK8 改为**尾插法 + 高低位拆分**解决，但 **JDK8 并发仍不安全**：数据丢失、size 不准确。

**追问：** JDK8 还有哪些并发问题？→ 并发 put 相同 key 时互相覆盖（丢数据）、计数器竞态。所以并发场景**必须用 ConcurrentHashMap**。

### 2.4 HashMap 的遍历方式与性能？

| 方式 | 说明 | 适用 |
|------|------|------|
| entrySet() | 同时拿 key+value，性能最好 | 遍历操作 |
| keySet() + get() | 每个 key 再查一次，多一次 hash | 只遍历 key |
| values() | 只遍历 value | 只需要值 |
| forEach / 迭代器 | 增强 for 底层即迭代器 | 遍历中修改需迭代器 remove |

## 3. ConcurrentHashMap 并发设计

### 3.1 JDK7 vs JDK8 的实现区别？

| 对比项 | JDK7 | JDK8 |
|--------|------|------|
| 锁粒度 | **分段锁**（Segment 数组，每段一把锁，默认 16 段） | **CAS + synchronized**（锁单个桶头节点） |
| 结构 | Segment + HashEntry | 数组 + 链表/红黑树（同 HashMap） |
| 并发度 | 固定 16 | 随扩容提升，锁粒度更细 |
| 查询 | 分段定位 | CAS 无锁读 + volatile 保证可见性 |

**参考答案：**
- JDK8 用 `synchronized` 只锁**桶的头节点** — 不同桶的写入完全并行，并发度 = 桶数
- 读操作无需加锁：Node 的 val、next 用 volatile 修饰（JDK8 起）
- `size()` 用 baseCount + CounterCell 数组分段累加，避免全局锁

```java
// 初始化/扩容时的并发控制
// 桶为空 → CAS 放入（无锁）；桶非空 → synchronized(node) 锁头节点
```

**追问：**
- 为什么 JDK8 放弃分段锁？→ 分段锁粒度粗（16 段封顶）、内存开销大；锁单个桶粒度更细且能随扩容增长
- 为什么用 synchronized 不用 ReentrantLock？→ JDK6+ 锁优化后 synchronized 性能接近；代码更简洁（try-finally 无污染）
- put 时 key/value 为 null 会怎样？→ **抛 NPE**（不允许 null）；HashMap 允许。为什么？→ 设计选择：CHM 用 null 做内部标记，且无法区分"值为 null"与"不存在"

### 3.2 CHM 的弱一致性体现在哪？

- 迭代器遍历时可能看到遍历过程中新加入的元素（或漏掉）
- `get` 在扩容期间可能读到旧值（扩容搬运未完成）
- `size()` 是近似值（无锁累加，允许轻微偏差）

**追问：** 需要强一致怎么办？→ 加全局锁（如 Collections.synchronizedMap）或用 `computeIfAbsent` 的同步语义；绝大多数场景弱一致性足够。

## 4. List 家族

### 4.1 ArrayList vs LinkedList vs Vector？

| 对比 | ArrayList | LinkedList | Vector |
|------|-----------|------------|--------|
| 底层 | Object[] 数组 | 双向链表 | Object[]（方法 synchronized） |
| 随机访问 | **O(1)** | O(n) | O(1) |
| 中间插入/删除 | O(n)（搬移） | **O(1)**（找到节点后） | O(n) |
| 内存 | 连续，有扩容余量 | 每个节点多 2 个指针 | 同 ArrayList |
| 线程安全 | 否 | 否 | 是（已过时） |

**参考答案：** 无特殊理由**永远用 ArrayList** — 随机访问快、缓存友好（连续内存）、局部性优势大。LinkedList 只有在"大量头尾操作且同时频繁中间插入"时才值得（实际少）。

**追问：** ArrayList 扩容机制？→ 默认容量 10，满后扩容 **1.5 倍**（`oldCapacity + (oldCapacity >> 1)`），Arrays.copyOf 拷贝。预判容量用 `new ArrayList<>(expectedSize)` 避免频繁扩容。

### 4.2 ArrayList 的 Fast-fail 陷阱与 remove 坑？

```java
// ❌ 错误：边遍历边按索引删除，会漏删
for (int i = 0; i < list.size(); i++) {
    if (条件) list.remove(i);   // 删除后元素前移，i+1 跳过下一个
}
// ✅ 正确：从后往前删 或 迭代器 remove 或 removeIf
list.removeIf(条件);
```

## 5. Set 与 Map 家族

### 5.1 HashSet 去重原理？

**参考答案：** HashSet 底层就是 **HashMap**（只用 key，value 是固定占位对象）。去重依赖 key 的 `hashCode + equals`：先比 hashCode（找桶），再比 equals（判同）。

```java
// 去重失败的经典案例
class User {   // 没重写 hashCode/equals → 相同 id 算不同对象
    int id; String name;
}
// ✅ 重写 equals（id 相等即相等）+ hashCode（return id）
```

**追问：** LinkedHashSet 与 TreeSet？→ LinkedHashSet = 链表维持**插入顺序**；TreeSet = 红黑树，**有序**（自然顺序或 Comparator），O(log n) 操作。

### 5.2 LinkedHashMap 实现 LRU 缓存？

**参考答案：** LinkedHashMap 继承 HashMap，额外维护双向链表记录顺序。构造参数 `accessOrder=true` 时按**访问顺序**排列 — 每次 get 把节点移到链表尾，链表头即最久未使用（LRU）。

```java
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    public LRUCache(int capacity) {
        super(capacity, 0.75f, true);      // accessOrder = true
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;           // 超容量删除链表头
    }
}
```

**追问：** removeEldestEntry 什么时候被调用？→ put 成功后回调（afterNodeInsertion 钩子）。为什么不直接用 HashMap + 手动维护？→ 双链表 + 钩子方法省去自建链表结构。

### 5.3 TreeMap / Hashtable / Properties？

| Map | 底层 | 特点 | 场景 |
|-----|------|------|------|
| TreeMap | 红黑树 | 按键排序（自然/Comparator），O(log n) | 需要有序遍历、区间查询 subMap |
| Hashtable | 哈希表 | 全方法 synchronized，已过时 | 历史代码兼容 |
| Properties | Hashtable 子类 | 读写 .properties 配置 | Java 配置加载（已逐渐被 YAML 替代） |

**追问：** 为什么说 Hashtable 效率低？→ 所有方法加同一把锁，读读互斥，并发度 0。Collections.synchronizedMap 呢？→ 同样全局锁，但可灵活控制锁对象。

## 6. Java 21 Sequenced Collections

### 6.1 什么是 Sequenced Collections？

**参考答案：** JEP 431（JDK 21 正式）：为有序集合提供统一接口，解决"取第一个/最后一个元素"各集合 API 不一致的问题。

```java
// 新接口
interface SequencedCollection<E> extends Collection<E> {
    E getFirst();  E getLast();
    void addFirst(E);  void addLast(E);
    SequencedCollection<E> reversed();
}
// SequencedMap：firstEntry() / lastEntry() / reversed()
```

**追问：** 解决什么问题？→ 之前 List.get(0)/get(size-1) 与 Deque.getFirst/getLast 与 TreeSet.first/last 各有写法；现在统一。对 JDK8 项目有什么用？→ 无（需要 Java 21），但面试考察对新特性的敏感度。
