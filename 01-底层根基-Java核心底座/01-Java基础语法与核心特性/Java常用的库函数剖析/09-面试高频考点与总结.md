## 1. 必背考点：十二问

### 1.1 String 为什么不可变？三个后果？

**答题链**：final 类 + final 字段 → **① == vs equals（常量池共享）② 线程安全（不可变即安全）③ 缓存友好（哈希缓存/String 池）** → 拼接底层（+ → StringBuilder）。

### 1.2 split 的三个坑？

**答题链**：**正则元字符（split(".") 无效，需 \\. 或 Pattern.quote）+ 尾部空串丢弃（split(",", -1) 保留）+ 空串保留（事后过滤）** → "split("\\.", -1) 是稳妥写法"。

### 1.3 trim 与 strip 的区别？

**答题链**：trim 只去 ≤U+0020（**NBSP 不去**）；**strip（JDK 11）去所有 Unicode 空白** → isBlank（全空白判断）→ 现代首选 strip/isBlank。

### 1.4 循环拼接为什么用 StringBuilder？

**答题链**：`+` 每次 new StringBuilder → **O(n²) 复制**；StringBuilder 一个对象复用 → **O(n)** → StringBuffer 同步（多线程才用）→ StringJoiner 带分隔符。

### 1.5 Integer 缓存池与 == 陷阱？

**答题链**：**valueOf/装箱走缓存（-128~127）** → 127 == 127 true、128 == 128 false → `new Integer` 永不相等 → **包装类比较用 equals/intValue** → 拆箱 null 抛 NPE。

### 1.6 equals 重写的黄金模板？

**答题链**：**五步（自身 == / 类型检查 / null / 强转 / Objects.equals 逐字段）+ 同步 hashCode（Objects.hash）** → getClass vs instanceof 决策 → record 自动实现。

### 1.7 0.1 + 0.2 等于什么？

**答题链**：**0.30000000000000004（二进制无法精确表示 0.1）** → 金额用 BigDecimal、科学用 double、比较用阈值 → BigDecimal 构造用 String/valueOf（double 构造不精确）。

### 1.8 BigDecimal 的四个构造器？

**答题链**：**double 构造不精确（展开完整二进制值）+ String 构造精确（首选）+ valueOf 精确（内部转字符串）+ int 构造精确** → 除法必须指定 scale + RoundingMode（否则 ArithmeticException）→ 比较用 compareTo（equals 含 scale）。

### 1.9 SimpleDateFormat 为什么线程不安全？

**答题链**：内部 Calendar 字段共享（parse/format 修改共享状态）→ 多线程数据错乱 → **DateTimeFormatter 不可变线程安全（可静态共享）** → 新代码一律 java.time。

### 1.10 java.time 的核心设计？

**答题链**：**不可变 + 线程安全** → LocalDate 本地语义 / **Instant UTC 存储** → Period 人类差 / Duration 机器差 → 存储 UTC、展示按时区 → 月从 1 开始（vs Calendar 0）。

### 1.11 Optional 的正确用法？

**答题链**：**返回值用（find 类方法）、字段/参数/集合不用** → ofNullable 创建、orElse/orElseThrow 取值（orElseGet 懒加载）→ map 转换 + **flatMap 拍平（嵌套 Optional）** → 七反模式（get 裸用/字段 Optional 等）。

### 1.12 Collections vs Collection？

**答题链**：**接口 vs 工具类** → 现代替代（list.sort / List.of / copyOf）→ unmodifiable 视图（穿透）vs of 真不可变 → synchronizedXxx 三问题（全局锁/手动迭代锁/复合无原子）。

## 2. 高频陷阱题 12 连问

1. **结果**：`"a,b,,c".split(",")` 长度？（4——空串保留）
2. **对错**：`Integer a=127, b=127; a==b` 为 false。（❌ 缓存池内 true）
3. **结果**：`Integer a=128, b=128; a==b`？（false——超缓存）
4. **对错**：`new BigDecimal(0.1)` 等于 `new BigDecimal("0.1")`。（❌ double 构造不精确）
5. **结果**：`0.1 + 0.2 == 0.3`？（false）
6. **对错**：`trim()` 能去掉 NBSP。（❌ 只去 ≤0x20；strip 才行）
7. **结果**：`"hello".substring(1, 3)`？（"el"——左闭右开）
8. **对错**：SimpleDateFormat 可以静态共享。（❌ 线程不安全）
9. **结果**：`Optional.of(null)`？（抛 NPE——用 ofNullable）
10. **对错**：`Arrays.asList(1,2,3).add(4)` 合法。（❌ 固定大小视图）
11. **结果**：`Math.abs(Integer.MIN_VALUE)`？（还是负数——溢出）
12. **对错**：`new BigDecimal("1.0").equals(new BigDecimal("1.00"))`。（❌ false——scale 不同；compareTo 才是 0）

## 3. 高频追问速答

| 追问 | 速答 |
|------|------|
| split 和 StringTokenizer 区别？ | split 正则+数组；StringTokenizer 遗留（不要用） |
| String.valueOf(null) 返回？ | "null"（不抛 NPE） |
| Objects.equals 和 a.equals(b)？ | 前者 null 安全（推荐） |
| orElse 和 orElseGet？ | 前者总是创建默认值、后者懒加载（昂贵时用后者） |
| Integer 缓存范围能改吗？ | -XX:AutoBoxCacheMax（一般不调） |
| 金额为什么不用 double？ | 二进制表示不精确 → 累积误差 |
| Files.readString 版本？ | JDK 11 |
| 大文件怎么读？ | Files.lines / transferTo（流式） |
| LocalDate 线程安全吗？ | ✅ 不可变（vs SimpleDateFormat） |
| 方法引用和 Lambda 怎么选？ | 能引用就引用（可读性） |

## 4. 场景题：工具函数设计

**题目**：为团队设计一个"金额处理工具类"，要求安全、易用、防呆。

**答题框架**（按评分点展开）：

```text
① 核心原则：金额一律 BigDecimal（防 double 精度问题）
   - 构造：new BigDecimal(String) / valueOf（禁止 double 构造）
② 工具类设计：
   - final 类 + 私有构造器（工具类规范）
   - 静态方法：add/subtract/multiply（BigDecimal 包装）
   - 除法：强制 scale + RoundingMode.HALF_UP（防无限小数）
   - 比较：compareTo 包装（isGreaterThan 等语义化方法）
   - 格式化：setScale(2) + 千分位（DecimalFormat）
③ 防呆：
   - 入参判空（Objects.requireNonNull）
   - 金额非负校验（负数抛异常）
   - 统一舍入模式（配置化）
④ 与周边联动：
   - 数据库 DECIMAL(10,2) + 实体 BigDecimal
   - JSON 序列化：@JsonSerialize 金额格式
   - MyBatis：BigDecimal 原生支持
⑤ 加分点：
   - 谈"工具类规范"（final + 私有构造器 + 静态方法）
   - 谈性能（高频场景 BigDecimal 慢于 double——按场景权衡）
   - 谈不可变（BigDecimal 本身不可变，运算返回新对象）
```

## 5. 面试加分项：架构视角

**面试官追问"你怎么保证团队代码用对库函数"时的作答框架**：

```text
① 规范沉淀：团队工具类（金额/时间/字符串）封装正确姿势
   - 金额工具：BigDecimal 包装（String 构造/除法精度/compareTo）
   - 时间工具：LocalDate 包装 + 统一格式常量（DateTimeFormatter）
   - 判空规范：Objects.requireNonNull / 返回 emptyList 而非 null
② 代码评审清单（库函数相关）：
   - 金额用 BigDecimal？包装类用 equals？文件用 TWR？
   - 大文件流式？Optional 只在返回值？SimpleDateFormat 未共享？
③ 静态分析：SonarQube 规则（equals/hashCode/资源关闭/浮点比较）
④ 测试覆盖：黄金用例（127/128、0.1+0.2、空串 split）
```

**三个"谈资级"观点**：

| 观点 | 展开 |
|------|------|
| "库函数的坑都是'边界'的坑" | 缓存池边界（127/128）、浮点表示边界、字符串正则边界——边界测试覆盖一切 |
| "现代 API 消灭样板代码" | strip/readString/of 家族让"防御性样板"内建到语言 |
| "读源码的前提是懂库函数" | Spring/MyBatis 底层全是这些函数——懂函数才能读框架 |

## 6. 记忆口诀

```text
字符串：不可变、常量池；split 正则三坑、replace 字面量首选。
strip 胜 trim（JDK 11）、循环拼接 StringBuilder（O(n)）。
包装类：缓存池 127/128、包装比较用 equals、拆箱 null 抛 NPE。
equals 五步模板 + hashCode 同步（record 自动）。
浮点：0.1+0.2 不等于 0.3——金额 BigDecimal。
BigDecimal：String 构造、除法带精度、compareTo 比较。
时间：LocalDate 不可变、Instant 存 UTC、Formatter 线程安全。
Files：readString（11）、大文件流式、TWR 防泄漏。
Optional：返回值专用、ofNullable 创建、flatMap 拍平。
Collections：工具非接口、现代替代 of/sort。
```
