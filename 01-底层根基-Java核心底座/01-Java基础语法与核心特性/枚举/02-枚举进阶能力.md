## 1. 成员类体：每个常量的专属行为

**成员类体（Constant-Specific Class Body）**：每个枚举常量可以有自己的"类体"——重写方法：

```java
public enum Operation {
    PLUS {
        @Override
        public double apply(double x, double y) { return x + y; }
    },
    MINUS {
        @Override
        public double apply(double x, double y) { return x - y; }
    },
    TIMES {
        @Override
        public double apply(double x, double y) { return x * y; }
    },
    DIVIDE {
        @Override
        public double apply(double x, double y) { return x / y; }
    };

    public abstract double apply(double x, double y);   // 抽象方法：各常量实现
}

// 使用：多态分派（编译期确定常量，运行期选择行为）
double result = Operation.PLUS.apply(3, 4);    // 7.0
```

**原理**：每个带成员类体的常量编译为**匿名子类**：

```text
enum Operation {
    PLUS -> class Operation$1 extends Operation { apply() { + } }
    MINUS -> class Operation$2 extends Operation { apply() { - } }
}
→ "抽象方法 + 成员类体" = 枚举版的多态（每个常量是一个策略）
```

> 🎯 **核心要点**：成员类体 = "**每个常量一个匿名子类**"——**用多态替代 switch 分派**（策略模式的枚举版）；`apply()` 是 JDK 枚举教程的经典例子（Effective Java 作者所举）。

## 2. 抽象方法驱动的行为分派

**为什么要用抽象方法而不是 switch**：

```java
// ❌ 反模式：switch 分派（漏分支只在运行时发现 + 每处调用都写一遍）
public String describe(OrderStatus status) {
    switch (status) {
        case PENDING: return "等待支付";
        case PAID: return "已支付";
        // 新增状态 → 这里忘了加 → 静默返回 null！
        default: return "未知";
    }
}

// ✅ 枚举抽象方法：行为内聚在枚举里（新增状态必须实现 → 编译期强制）
public enum OrderStatus {
    PENDING { @Override public String describe() { return "等待支付"; } },
    PAID    { @Override public String describe() { return "已支付"; } },
    SHIPPED { @Override public String describe() { return "已发货"; } };

    public abstract String describe();
}
// 新增状态 → 编译器强制实现 describe() → 不会漏
```

**"为什么抽象方法更优"三理由**：

1. **编译期强制**：新增常量必须实现所有抽象方法（switch 会漏）；
2. **行为内聚**：每个常量的行为就在常量旁边（可读性）；
3. **多态调用**：调用方一行 `status.describe()`，无需分派逻辑。

> 🎯 **核心要点**：**"枚举抽象方法"消灭了"枚举 switch 分派"**——switch 漏分支是运行时静默问题，抽象方法是编译期强制；现代代码优先"行为入枚举"。

## 3. 实现接口

**枚举可以 implements 任意接口**——Java 8 默认方法让接口实现更实用：

```java
// 接口定义能力契约
public interface Payable {
    String channelName();
    boolean supports(String orderType);
}

// 枚举实现接口：渠道枚举实现支付能力
public enum PayChannel implements Payable {
    WECHAT {
        @Override public String channelName() { return "wechat"; }
        @Override public boolean supports(String type) { return !"international".equals(type); }
    },
    ALIPAY {
        @Override public String channelName() { return "alipay"; }
        @Override public boolean supports(String type) { return true; }
    },
    UNIONPAY {
        @Override public String channelName() { return "unionpay"; }
        @Override public boolean supports(String type) { return "domestic".equals(type); }
    };
}

// 使用：面向接口编程（多态）
Payable channel = PayChannel.WECHAT;
channel.channelName();    // "wechat"
```

**接口 + 枚举的组合价值**：

1. **面向接口使用**：业务代码依赖 `Payable` 而非具体枚举（可替换性）；
2. **多枚举统一能力**：多个枚举实现同一接口 → 统一调用（如所有"可支付类型"）；
3. **sealed 接口组合（JDK 17+）**：接口密封 + 枚举实现 → 受控分派（见 03 模块）。

> 🎯 **核心要点**：枚举实现接口 = "**让有限状态集合拥有统一契约**"——渠道/处理器/策略枚举实现接口，业务层面向接口编程，扩展新渠道只加一个常量（开闭原则）。

## 4. 枚举状态机：最经典的应用

**状态机（State Machine）**是枚举行为建模的巅峰应用——状态 + 转移 + 动作一体：

```java
public enum OrderState {
    PENDING {                          // 待支付
        @Override
        public OrderState next(Event event) {
            return switch (event) {     // 事件驱动转移
                case PAY_SUCCESS -> PAID;
                case CANCEL -> CANCELLED;
                default -> throw new IllegalStateException("待支付状态不支持: " + event);
            };
        }
    },
    PAID {                             // 已支付
        @Override
        public OrderState next(Event event) {
            return switch (event) {
                case SHIP -> SHIPPED;
                case REFUND -> REFUNDED;
                default -> throw new IllegalStateException("已支付状态不支持: " + event);
            };
        }
    },
    SHIPPED { ... },
    CANCELLED { @Override public OrderState next(Event e) { throw new IllegalStateException("终态"); } },
    REFUNDED { ... };

    public abstract OrderState next(Event event);   // 转移：每个状态自己的规则

    public enum Event { PAY_SUCCESS, CANCEL, SHIP, REFUND }
}

// 使用：状态机驱动订单流转
OrderState state = OrderState.PENDING;
state = state.next(OrderState.Event.PAY_SUCCESS);   // PAID
state = state.next(OrderState.Event.SHIP);          // SHIPPED
```

**状态机的收益**：

| 收益 | 说明 |
|------|------|
| 非法转移编译期可查 | 每个状态的 next 规则内聚，非法事件抛异常 |
| 终态显式 | CANCELLED/REFUNDED 的 next 直接拒绝 |
| 扩展新状态 | 加一个常量 + 实现 next（编译期强制） |
| 可测试 | 每个状态的事件矩阵可穷尽测试 |

> 🎯 **核心要点**：枚举状态机 = "**状态（常量）+ 转移（next 方法）+ 动作（成员类体）**"三位一体——**非法转移在运行时立即抛错而非静默错乱**，是订单/审批等流程建模的标准答案。

## 5. 枚举的静态成员与工具方法

**枚举支持静态成员**（与类一致）：

```java
public enum ErrorCode {
    PARAM_INVALID("400", "参数不合法"),
    NOT_FOUND("404", "资源不存在"),
    SERVER_ERROR("500", "系统繁忙");

    private final String code;
    private final String msg;
    ErrorCode(String code, String msg) { this.code = code; this.msg = msg; }

    // 静态工具方法：按 code 查找（含容错）
    public static ErrorCode fromCode(String code) {
        for (ErrorCode e : values()) {
            if (e.code.equals(code)) return e;
        }
        return SERVER_ERROR;    // 容错：未知 code 返回兜底
    }

    // 静态工厂：常用项快捷获取
    public static ErrorCode paramError() { return PARAM_INVALID; }

    // 实例方法
    public String code() { return code; }
    public String msg() { return msg; }
}
```

**常见工具方法模式**：

| 模式 | 用途 |
|------|------|
| `fromCode/fromValue` | 从持久化值（数据库/前端）反查枚举 |
| 缓存 `values()` | 高频调用时缓存数组（`values()` 每次新建） |
| `isValid` | 参数校验（前端传值合法性） |
| 按序工具 | 权限级别比较（`compareTo`） |

> 🎯 **核心要点**：静态工具方法 = "**枚举的自助服务**"——`fromCode`（反查）、缓存（性能）、校验（参数），把"枚举值 ↔ 外部表示"的转换内聚在枚举自身。

## 6. 进阶边界与陷阱

| 陷阱 | 表现 | 解法 |
|------|------|------|
| **可变字段** | 枚举常量字段被修改（破坏单例一致性） | 字段全部 `final` |
| **成员类体内加字段** | 每个常量有自己的状态（难以追踪） | 尽量不用；必须用则不可变 |
| **抽象方法过多** | 每个常量实现一堆方法（代码膨胀） | 区分"真行为"与"配置数据"——数据用字段、行为才用方法 |
| **枚举太大** | 十几个常量 + 各自类体（难读） | 考虑拆分为策略类（行为复杂时） |
| **switch 分派残留** | 外部 switch 处理枚举行为 | 迁入枚举（抽象方法/成员类体） |
| **泛型限制** | `enum E<T>` 不合法 | 用实例方法 + 强转（罕见需求） |

**"何时枚举够用、何时换策略类"**（判断）：

```text
行为简单（一两行/常量）→ 枚举成员类体（首选）
行为复杂（多方法/多依赖）→ 策略类 + 枚举做注册表：
  enum HandlerType { A(() -> new HandlerA()), B(() -> new HandlerB()) }
  → 枚举管"类型集合"，策略类管"复杂行为"
```

> 🎯 **核心要点**：进阶边界 = "**行为简单入枚举、行为复杂出策略**"——枚举成员类体是"轻量多态"，行为膨胀时用"枚举注册表 + 策略类"组合（两者不冲突，是互补）。
