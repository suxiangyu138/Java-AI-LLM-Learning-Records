## 1. SAM 语义与 @FunctionalInterface

**SAM（Single Abstract Method）**：函数式接口恰好只有一个抽象方法，lambda 表达式就是该方法的实现。编译器据此判断"这个 lambda 是谁的实现"，这是 lambda 类型推导的全部基础。

```java
@FunctionalInterface
public interface Validator<T> {
    boolean isValid(T target);          // 唯一抽象方法 → SAM
    // default/static 方法不限数量
}
```

`@FunctionalInterface` 是**编译期契约而非运行时机制**：标注后若接口出现第二个抽象方法，编译器直接报错——它把"设计意图"变成"机器检查"，防止后续维护者无意破坏。注意三条边界：

- **Object 的公开方法不算**：`equals/hashCode/toString` 不参与 SAM 计数
- **继承场景取"最抽象"**：接口继承接口时，抽象方法集合合并，仍须恰有一个
- **泛型接口仍是 SAM**：`interface Mapper<T> { T map(String s); }` 合法

## 2. 四大核心接口与变体家族

`java.util.function` 全部接口都由四原型派生，记住原型就能推断全部：

| 原型 | 抽象方法 | 语义 | 常见变体 |
|------|---------|------|---------|
| `Function<T,R>` | `R apply(T)` | 转换 | `BiFunction`、`UnaryOperator`、`BinaryOperator`、`IntFunction/LongToDoubleFunction`… |
| `Predicate<T>` | `boolean test(T)` | 判断 | `BiPredicate`、`IntPredicate`… |
| `Consumer<T>` | `void accept(T)` | 消费（有副作用） | `BiConsumer`、`IntConsumer`… |
| `Supplier<T>` | `T get()` | 供给（无参） | `BooleanSupplier`、`IntSupplier`… |

命名规律：前缀 `Bi` 双参、`Unary` 单参同型、`Binary` 双参同型、`Int/Long/Double` 是原始类型特化（**避免装箱**，见「装箱拆箱 泛型擦除」体系）。

使用建议：

- 优先用 JDK 既有接口，别急着自定义——语义对得上就复用
- 返回值/参数类型偏"领域"时（如 `Order` → `BigDecimal`），写 `Function<Order, BigDecimal>` 即可，无需自定义 `OrderCalculator` 接口
- 但**字段命名可读性**超过类型命名：`Function<Order, BigDecimal> totalPrice` 比 `OrderCalculator` 更冗长时，自定义接口更值

原始类型特化接口（`IntPredicate`、`LongFunction` 等）的使用判据：**数据量万级以上或热循环中**才值得用——它们免除装箱/拆箱（见「装箱拆箱 泛型擦除」体系），但牺牲了与泛型 API 的互操作（`IntStream.mapToInt` 与 `Stream<Integer>` 转换有成本）。默认写法 `Predicate<Integer>` 可读性更好，性能压测确认热点后再特化，提前特化属于过早优化。

## 3. 自建函数式接口的三大坑

自建接口高频踩三个坑，全部有解：

**坑一：受检异常无法直接抛出**。函数式接口的抽象方法默认不声明受检异常，`Files.readAllLines` 这类 IO 在 lambda 里直接编译失败：

```java
// ❌ 编译错误：unhandled checked exception
Function<String, List<String>> reader = Files::readAllLines;

// ✅ 方案一：自建"可抛异常"接口（三参等特殊签名只能自建）
@FunctionalInterface
interface ThrowingReader { List<String> read(String p) throws IOException; }

// ✅ 方案二：包装为 Runtime 异常（Spring 的 uncheck 工具、自写 wrapper）
Function<String, List<String>> reader = p -> {
    try { return Files.readAllLines(p); }
    catch (IOException e) { throw new UncheckedIOException(e); }
};
```

> ⚠️ 注意：Java 至今（2026，JDK 26）没有为函数式接口引入"类型化异常"——`throws` 子句里的类型不能被 lambda 利用。长期方案仍是包装，社区共识是"边界处包装、核心保持纯"（02 章）。补充方案三：`sneaky throw`（Lombok `@SneakyThrows` 或手写泛型擦除技巧）把受检异常"伪装"成非受检抛出，调用方按需 catch——简洁但隐式，团队若无统一规范不建议作为默认手段。

命名规范一并固化：**接口用名词（`PriceRule`、`ThrowingReader`），抽象方法用"动词 + 宾语"（`calculate`、`read`）**，与 JDK 接口风格（`test`/`apply`/`accept`/`get`）对齐；自建接口若无法用一个动词概括职责，多半是职责过宽，拆开。

**坑二：泛型擦除导致的重载冲突**。擦除后 `Function<String, String>` 与 `Predicate<String>` 是两个不同接口可以共存，但两个仅泛型不同的重载会撞车：

```java
void run(Function<String, String> f) {}     // 擦除后都是 Function
void run(Function<Integer, String> f) {}    // ❌ 同签名：两者冲突，编译失败
```

**坑三：三参以上接口必须自建**。JDK 核心接口止于 BiFunction，三参（如 `(score, weight, threshold) -> …`）需要手写：

```java
@FunctionalInterface
interface TriFunction<A, B, C, R> {
    R apply(A a, B b, C c);
}
```

## 4. 用 default 方法固化组合契约

自定义接口的最佳实践是**自带组合方法**——把组合逻辑固化进接口，调用方拿到的是"组装好的函数"，而不是一套待拼的零件：

```java
@FunctionalInterface
public interface PriceCalculator {
    BigDecimal calculate(Order order);

    // 组合：算完再加工（如统一舍入）
    default PriceCalculator andThen(UnaryOperator<BigDecimal> post) {
        return o -> post.apply(calculate(o));
    }

    // 组合：串联下一条规则（责任链）
    default PriceCalculator andThen(PriceCalculator next) {
        return o -> next.calculate(calculate(o).compareTo(BigDecimal.ZERO) > 0
                ? new Order(o.id(), o.items(), calculate(o)) : o);
    }

    static PriceCalculator of(PriceCalculator self) { return self; }
}
```

> 💡 **要点**：default 组合方法内部必须保持"返回新函数而非原地修改"——组合子永远返回新实例，这是函数式组合与"配置对象链式调用"（Builder 的 `setX().setY()`）的本质区别：前者产生新函数，后者修改同一对象。

## 5. 契约标注：参数、返回与并发

函数式接口通过注释与命名向调用方传递三类契约：

- **参数可空性**：`@Nullable` / `@NonNull`（JSpecify 或 IDE 注解）标注参数是否允许 null——lambda 大量使用 `Objects.requireNonNull` 做快速失败
- **返回值语义**：返回 `Optional` 表示"可能无值"（06 章），返回空集合而非 null
- **并发性承诺**：接口若被设计为可并行调用（如 Stream 的中间函数），文档注明"实现必须无状态、无副作用"——`Stream` 的 javadoc 对此有明确要求："the function must be non-interfering and stateless"

```java
/**
 * 计价规则。实现必须满足：
 * - 参数 @NonNull，返回结果仅依赖入参（纯函数）；
 * - 可被并行调用：禁止读写共享可变状态；
 * - 失败以 Result 表达，不抛业务异常。
 */
@FunctionalInterface
public interface PriceRule {
    @NonNull Result<BigDecimal> calculate(@NonNull Order order);
}
```

这条契约在 2026 年的并行编程语境下尤为重要：**函数式接口的契约 = 调用方对实现的信任清单**。实现者违反约定（在并行上下文里用可变状态），bug 只在压力下浮现，调试成本极高（09 章详述）。契约写进 javadoc + 注解还带来工具链收益：`@NonNull` 注解可被 IDE 静态检查与 JSpecify 校验器消费，把"运行时才暴露的 NPE"提前到编译期。

## 6. 设计决策：什么时候自定义接口

决策顺序建议：

1. 语义与 JDK 四原型相符 → 直接复用（90% 的场景）
2. 需要三参、受检异常、领域语义命名 → 自定义 + `@FunctionalInterface` + 组合 default 方法
3. 需要定义"业务规则类型"（如校验规则、计价规则集合）→ 自定义接口 + default 组合 + `static` 工厂，形成规则 DSL

警惕两个极端：为每个 lambda 建接口（类型爆炸）与清一色 `Function<Map<String,Object>, Map<String,Object>>`（语义丢失）。**命名是契约的一部分**：`Function<Order, BigDecimal>` 说"这是个转换"，`PriceCalculator` 说"这是计价规则"——后者在 code review 里不需要注释。

当自定义接口开始积累 default 组合方法与 `static` 工厂时，它其实已进化为**规则 DSL**——例如风控规则集：

```java
@FunctionalInterface
interface RiskRule {
    RiskVerdict evaluate(RiskContext ctx);

    default RiskRule and(RiskRule other) {
        return ctx -> evaluate(ctx).reject() ? verdict() : other.evaluate(ctx);
    }

    static RiskRule of(String name, Predicate<RiskContext> cond, RiskVerdict v) {
        return ctx -> cond.test(ctx) ? v : RiskVerdict.PASS;
    }
}
```

DSL 化的判断标准：**接口能否被组合成"读得懂的规则句子"**（如"限频规则 and 设备指纹规则"）。能——值得维护；不能——回到函数复用即可，别过度设计。最后一条铁律：**接口是公共契约，命名与组合方法一经发布即被调用方依赖**——组合语义（短路顺序、失败策略）写进 javadoc，改组合行为属于破坏性变更，要走版本评审。

> 🎯 **核心要点**：函数式接口设计 = SAM 一个抽象方法 + default 方法提供组合 + 契约（可空性/并发性/异常）写清楚。受检异常无类型化方案（2026 现状），包装在边界完成。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. SAM 语义 + `@FunctionalInterface` 编译期检查是函数式接口的地基，Object 方法与 default/static 方法不占名额；
> 2. 四原型（Function/Predicate/Consumer/Supplier）+ 变体命名规律（Bi/Unary/Binary/原始类型特化）覆盖 90% 场景；
> 3. 自建接口三大坑：受检异常（包装或自建 Throwing 接口）、泛型擦除重载冲突、三参以上必须手写。

**思考题**：
