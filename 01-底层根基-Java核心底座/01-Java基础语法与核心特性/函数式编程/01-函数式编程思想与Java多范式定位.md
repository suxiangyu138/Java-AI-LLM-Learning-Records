## 1. 函数式编程的三大支柱

函数式编程（Functional Programming, FP）有三大支柱，缺一即退化为"用 lambda 写命令式代码"：

1. **纯函数（Pure Function）**：输出只由输入决定，不产生任何外部影响。同一个输入永远得到同一个输出。
2. **不可变数据（Immutability）**：数据创建后不再变化，"修改"一律表达为"基于旧值创建新值"。
3. **无副作用执行（No Side Effects）**：函数体内不写文件、不打日志、不修改外部变量、不抛未声明的异常。

三者互为支撑：纯函数保证"怎么算都不出错"，不可变保证"数据在函数间共享不打架"，无副作用保证"调用顺序与次数不影响结果"。

```java
// 纯：同样的入参，永远同样的出参，且不影响任何外部状态
int addOne(int x) { return x + 1; }

// 不纯：① 依赖可变外部状态 ② 修改了外部状态 ③ 行为依赖时间
int next() { return counter++; }
```

> 🎯 **核心要点**：判断一段代码是否"函数式"，不看语法而看性质——能否安全地被缓存、被并行、被任意顺序调用。三大支柱的全部价值都从这三个"能否"派生。

## 2. 引用透明：一切推论的地基

**引用透明（Referential Transparency）**：表达式可以被它的计算结果替换，而程序行为不变。`2 + 3` 永远可以替换成 `5`；但 `counter++` 不能——替换后行为变了。

引用透明是纯函数 + 不可变数据的**必然产物**，也是工程师唯一真正需要的推论能力：

- **等式推理**：看到 `f(x)` 就知道它等于什么，无需阅读 f 的实现上下文
- **可替换性**：缓存结果、调整执行顺序、移到另一台机器，行为不变
- **可测试性**：不需要 mock 外部依赖、不需要准备环境状态，传参即可

反面教材是"时间敏感"代码：`System.currentTimeMillis()`、`Math.random()`、`UUID.randomUUID()` 都不引用透明——同一表达式两次求值结果不同，这决定了它们必须待在边界（见 02 章）。

## 3. 命令式 vs 声明式 vs 函数式

| 范式 | 关注点 | 表达方式 | 典型代表 |
|------|--------|---------|---------|
| 命令式 | **怎么做**（how） | 语句序列、循环、赋值修改状态 | C、Java 传统风格 |
| 声明式 | **做什么**（what） | 描述结果而非步骤 | SQL、正则、Java Stream |
| 函数式 | **什么是计算** | 数据流穿过纯函数、组合求值 | Haskell、Scala、Clojure |

三者不是互斥而是层次关系：函数式代码天然是声明式的（管线描述"要什么"），而声明式代码未必函数式（SQL 查询可以隐含可变会话状态）。

```java
// 命令式：三步手动折叠
int sum = 0;
for (int i = 0; i < prices.size(); i++) {
    if (prices.get(i) > 100) sum += prices.get(i);
}

// 函数式：声明"要什么"，执行细节交给运行时
int sum = prices.stream()
        .filter(p -> p > 100)
        .mapToInt(Integer::intValue)
        .sum();
```

两段代码行为一致，但第二段把"过滤 + 求和"拆成了可复用的纯函数链，每一环都能独立测试、独立替换、独立并行。

## 4. Java 的混合范式定位

Java 从设计上就是**命令式面向对象为主、函数式能力渐进增强**的混合语言，与纯函数式语言有本质差异：

- **可变是默认**：字段不写 `final` 就是可变的，对象无 "immutability by default"
- **null 无处不在**：Haskell/Scala 用类型系统消灭空值，Java 直到 Optional 也只是"约定"
- **异常是控制流**：纯函数式语言以值表达错误，Java 的受检异常是语言级机制
- **语句优先**：Java 是语句式语言（有 `if` 语句），函数式语言一切皆表达式

| 维度 | Haskell（纯 FP） | Scala（混合） | Kotlin（实用混合） | Java |
|------|-----------------|--------------|-------------------|------|
| 可变性 | 默认不可变 | 默认不可变 | 默认不可变 | 默认可变 |
| 空值 | 无（Maybe 类型） | 无（Option） | 可空类型 `T?` | null + Optional 约定 |
| 错误 | 值（Either） | 值（Either/Try） | 值/异常并用 | 异常为主 |
| 高阶函数 | 一等公民 | 一等公民 | 一等公民 | 函数式接口 + lambda |
| 函数式定级 | 纯函数式 | 函数式优先 | 混合 | **命令式优先，函数式可用** |

> 💡 **正确姿态**：Java 的函数式是"**战术武器**而非世界观"——在数据变换、管线组合、并发编排上用它，在 IO、长事务、复杂状态机上退回命令式。2026 年 Java 社区的主流共识是"务实混合"：用 Record + 不可变集合 + Stream + Optional 打造确定性核心，IO 与副作用留在边界（Manning《Data-Oriented Programming in Java》把这一模式称为"确定性核心 + 非确定性外壳"）。

## 5. 企业 Java 为什么需要 FP 思维

三个现实驱动力让 FP 从"学术兴趣"变成"工程刚需"：

1. **可测试性危机**：微服务时代，方法级测试成本由依赖复杂度决定。纯函数零 mock、零环境，是唯一"闭眼测"的代码。副作用越靠边界，测试金字塔的底座越稳。
2. **并发安全**：虚拟线程（JDK 21 定稿）让"每请求一线程"成为现实，但共享可变状态依然是数据竞态的温床。不可变数据 + 纯函数天然免锁——FP 是并发问题的"预防性架构"，而非事后加锁。
3. **AI 与数据处理管线**：RAG、向量检索、批处理、流式计算（Kafka Streams 的处理器 API 就是函数式模型）——2026 年 Java 后端几乎不可避免处理"数据经过多级变换"的场景，Stream/Gatherers/CompletableFuture 构成统一的可组合管线语言。

同时要给出反面清单，明确**哪些场景不该硬函数式**：

- **长事务与复杂状态机**：事务边界、回滚、补偿天然命令式，函数式包装只会让事务语义更难追踪
- **高频可变聚合**：每秒几十万次的计数/累加，可变长整型比不可变对象快几个数量级，该用 `LongAdder` 就用
- **框架回调密布的代码**：Spring 事务模板、MyBatis 映射器、Servlet 生命周期——框架强约束处顺势而为，不与框架的副作用模型对抗

判断原则一句话：**函数式处理"数据的流动"，命令式处理"系统的状态"**——流动的部分用函数式表达，状态的部分老老实实命令式。盲目"万物皆 lambda"与"函数式一无是处"同样危险。

## 6. 范式演进：从 Java 8 到 2026

Java 的函数式能力是一条"渐进补全"的演进线，理解顺序即理解全貌：

- **Java 8（2014）**：lambda + 函数式接口 + Stream + Optional——语法与核心 API 落地，函数式元年
- **Java 14-17**：switch 表达式、Record、sealed 类——**建模能力**补全：不可变数据有了语法级表达（Record），错误即值有了类型级表达（sealed）
- **Java 21-24**：switch 模式匹配定稿、虚拟线程、**Stream Gatherers 定稿（JEP 485）**——管线能力补全：自定义中间操作不再需要 workaround
- **Java 25-26**：LTS 基线（Scoped Values 定稿 JEP 506）；结构化并发（JEP 525）第 6 预览——**并发编排**即将走向标准化

> 🎯 **核心要点**：Java 8 给的是"语法"，17 给的是"建模"，24+ 给的是"管线扩展力"。2026 年的 Java 函数式实践 = Java 8 的 API + Java 17 的数据建模 + JDK 24 的 Gatherers + 虚拟线程时代的并发编排。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. FP 三支柱（纯函数/不可变/无副作用）与引用透明，价值全部落在"可缓存、可并行、可测试"三个能力上；
> 2. Java 是命令式优先的混合范式语言，函数式风格适用于数据变换与并发编排，副作用必须留在边界；
> 3. 演进主线：Java 8 语法 → 17 建模（Record/sealed）→ 24 管线（Gatherers）→ 25/26 并发（虚拟线程/结构化并发）。
