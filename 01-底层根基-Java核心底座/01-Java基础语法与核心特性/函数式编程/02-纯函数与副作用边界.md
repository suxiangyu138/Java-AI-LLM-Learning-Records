# 纯函数与副作用边界

> 纯函数的价值不在"优雅"而在"可信任"：它能被缓存、被并行、被任意重排。但真实系统总要读写 IO——所以函数式工程的核心手法不是消灭副作用，而是把副作用**赶到边界**，让核心保持纯

## 1. 纯函数的判定标准

一个函数是纯函数，当且仅当同时满足三条：

1. **确定性（Determinism）**：相同输入永远产生相同输出——不依赖时间、随机数、环境变量、外部状态
2. **无观察副作用（No Observable Side Effects）**：不修改任何函数外部可见的状态（全局变量、参数对象的字段、文件、数据库、日志）
3. **不抛出意外异常**：不因输入之外的原因失败（如 NullPointerException 之外，读取外部资源失败也算副作用）

```java
// ① 确定性：同一输入同一输出 ✅
double tax(double base, double rate) { return base * rate; }

// ② 副作用：修改了传入对象 —— 调用方毫不知情 ❌
void applyDiscount(Order o) { o.setAmount(o.amount * 0.9); }

// ③ 隐蔽依赖：读取了静态全局 —— 测试需先设置环境 ❌
double fee() { return FeeTable.getInstance().rate; }
```

> 💡 **判别捷径**：把函数调用处注释掉或复制一份，行为是否会变？把函数调用顺序打乱，结果是否会变？把函数结果缓存下来复用，是否安全？三个"是"就是纯函数。

## 2. 副作用七分类

工程中常见的副作用按"隐蔽程度"排序，越靠后越难发现：

| 类别 | 例子 | 隐蔽度 |
|------|------|:---:|
| IO | 写文件、写库、发 HTTP、打日志 | 明显 |
| 可变状态 | 改全局变量、改入参对象字段 | 中 |
| 异常 | 抛受检/非受检异常作为失败通道 | 中 |
| 随机性 | `Math.random()`、UUID | 中 |
| 时间 | `currentTimeMillis()`、`new Date()` | 高 |
| 外部查询 | 读配置中心、读环境变量 | 高 |
| 缓存写入 | 写静态 Map 缓存（需注意线程安全） | 高 |

关键认识：**日志也是副作用**。`Stream.forEach(System.out::println)` 本质上是副作用注入管线——它让流水线"每处理一个元素就影响一次外部世界"，串行时没事，并行时顺序与次数都不可控。

## 3. 确定性核心 + 非确定性外壳

既然纯函数做不了 IO，真实程序如何运转？答案是**架构分层**：

```text
┌─────────────────────────────── 非确定性外壳 ───────────────────────────────┐
│  Controller / 定时任务 / MQ 监听器 / WebSocket —— 一切的"入口"              │
│       │ 读入（DB/HTTP/用户输入）→ 组装成不可变输入                           │
│       ▼                                                                     │
│  ┌──────────────────── 确定性核心（纯函数组成）────────────────────┐        │
│  │  校验 → 计算 → 状态转移 → 领域决策（无 IO、无时间、无随机）       │        │
│  └─────────────────────────────────────────────────────────────────┘        │
│       │ 产出不可变结果（事件/命令/输出模型）                                 │
│       ▼                                                                     │
│  出口（写 DB / 发 MQ / 返回响应）—— 唯一的副作用执行点                        │
└───────────────────────────────────────────────────────────────────────────────┘
```

这一模式在 2026 年的多种语境下被重复命名：Manning《Data-Oriented Programming in Java》叫"确定性核心 + 非确定性外壳"（deterministic core, non-deterministic shell）；领域驱动设计里是"领域层纯模型 + 基础设施层适配器"；六边形架构里是"应用内部纯逻辑 + 端口适配器"。本质相同：**核心函数只做输入→输出，一切 IO 由外壳负责**。

## 4. 把副作用外推的三条路径

把"看起来不得不在函数里做的 IO"推到边界，常用三条路径：

1. **依赖参数化**：把"获取依赖"的动作变成参数传入，函数本身保持纯——这是依赖注入在函数式世界的形态。

```java
// 不纯：内部去查库
BigDecimal fee(Order o) { return feeRepo.find(o.zone); }

// 纯：费率作为入参，查询责任交给调用方
BigDecimal fee(Order o, BigDecimal zoneRate) { return o.amount.multiply(zoneRate); }
```

2. **回调/事件外抛**：核心函数只产出"意图"（命令、事件对象），由外壳执行。典型的 Outbox 模式即此思路——核心决定"该发什么通知"，外壳负责真正发送并保证投递。
3. **单测替换外壳**：纯核心直接传参测试；外壳只留薄薄一层"取数→调用→落库"，测试时用 mock 验证调用关系即可。

边界自身的工程要求也要落实，否则边界会成为新的混沌区：

- **边界要兜底**：核心不抛业务异常（用 Result 表达），边界负责重试、告警、补偿——"核心可以放心失败，边界必须处理失败"
- **边界要薄**：一段边界代码超过二十行就该怀疑——取数、调用、落库三件事之外，逻辑一律下沉核心
- **边界要可观测**：入口出口打点（耗时、成功失败、重试次数），核心函数无痕——线上排查先看边界日志，再看核心逻辑

## 5. 纯函数红利：memoize 与并行

纯函数三大红利中最具工程价值的是**可记忆化（memoization）**：结果只依赖输入，就可以用输入做键缓存输出，通用实现只需几行：

```java
public static <T, R> Function<T, R> memoize(Function<T, R> fn) {
    Map<T, R> cache = new ConcurrentHashMap<>();
    return t -> cache.computeIfAbsent(t, fn);
}

// 场景：汇率换算（同货币对结果可复用）、大数计算、字典查询
Function<String, BigDecimal> usdToCny = memoize(CurrencyService::latestRate);
```

注意两个前提：缓存 Map 必须线程安全（如上 ConcurrentHashMap），且**缓存命中率与键分布相关**——输入基数巨大时缓存反成内存负担，需要配合淘汰策略（如 Caffeine）。记忆化在 2026 年也催生了 Spring Cache 等注解式方案，但其原理正是"纯函数 + 键值缓存"。

并行红利留到 09 章展开，此处只给结论：**纯函数可以直接扔进并行流、ForkJoinPool、CompletableFuture，零同步成本**——这也是"确定性核心"能在高并发下免锁运行的根基。

纯函数还带来测试模板的简化：**传参即用例、断言即行为**，无需 mock、无需容器：

```java
@Test
void tax_计算纯函数_边界与主路径全覆盖() {
    assertThat(tax(BigDecimal.ZERO, new BigDecimal("0.13"))).isEqualByComparingTo("0");
    assertThat(tax(new BigDecimal("100"), new BigDecimal("0.13"))).isEqualByComparingTo("13");
    assertThat(tax(new BigDecimal("-5"), new BigDecimal("0.13")))   // 负数输入
            .isEqualByComparingTo("-0.65");
}
```

对比同场景的命令式版本（内部查费率、写日志、改对象），测试需要 mock 仓储、清理日志、断言对象状态——同样的覆盖，成本差一个量级。**测试成本是衡量"纯度"最直接的仪表盘**：函数越难测，越说明它有不该有的依赖。

## 6. 业务案例：订单价格计算重构

电商订单计价是经典的"副作用混入"场景，重构三步法：

```java
// 重构前：函数内部查费率、打日志、写折扣记录 —— 不可测、不可并行
BigDecimal compute(Order o) {
    log.info("compute order " + o.id);                       // 副作用
    BigDecimal rate = feeRepo.find(o.zone);                  // 外部查询
    BigDecimal discount = promoClient.query(o.userId);       // 外部查询
    o.setTotal(o.amount.multiply(rate).subtract(discount));  // 修改入参
    orderRepo.saveDiscount(o);                               // 副作用
    return o.getTotal();
}

// 重构后：纯函数只做计算，上下文由调用方组装
record PriceContext(BigDecimal zoneRate, BigDecimal discount) {}

BigDecimal compute(Order o, PriceContext ctx) {              // 纯 ✅
    return o.amount().multiply(ctx.zoneRate()).subtract(ctx.discount());
}
```

重构收益立现：`compute` 无需 Spring 容器即可单测（传两个参数完事）；并行计算多个订单零冲突；日志与落库由外壳统一负责、失败只影响外壳。计价规则（优惠叠加顺序、税费计算）全部变成可组合的纯函数链，业务变更只改核心、不碰边界。

> 🎯 **核心要点**：纯函数不是"做不到 IO 的残缺函数"，而是"把 IO 责任外包给边界的高内聚函数"。重构判据：核心函数越纯，边界越薄，系统可测性与并发安全性越强。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 纯函数 = 确定性 + 无观察副作用 + 不抛意外异常，判别靠"能否缓存/重排/并行"三问；
> 2. 副作用分七类，日志也算副作用；工程目标是"核心纯、边界 IO"，即确定性核心 + 非确定性外壳；
> 3. 副作用外推三路径（参数化/事件外抛/测试替换外壳），纯函数换来 memoize 与免锁并行两大红利。
