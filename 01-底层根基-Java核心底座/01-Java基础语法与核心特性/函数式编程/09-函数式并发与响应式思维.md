## 1. CompletableFuture：异步管线的函数式组合

`CompletableFuture<T>`（Java 8 引入）把"异步结果"建模为可组合的值——它本身就是一个"未来容器"，函数式组合子让它成为异步管线的基础设施：

```java
CompletableFuture<Order> orderFuture = CompletableFuture
        .supplyAsync(() -> orderService.load(id))          // 异步取数
        .thenApply(o -> orderService.calculate(o))          // 变换：纯函数
        .thenCompose(o -> orderService.paymentAsync(o))     // 拍平：返回新 Future
        .thenApply(Order::markPaid)
        .exceptionally(ex -> fallbackOrder(ex));            // 失败兜底：值语义
```

管线语义与 Stream 完全同构：`thenApply` = map（同步变换）、`thenCompose` = flatMap（异步变换）、`exceptionally` = 失败分支（错误的函数式表达，呼应 06 章"错误即值"）。组合矩阵：

| 组合子 | 语义 | 说明 |
|--------|------|------|
| `thenApply(f)` | 变换结果 | f 同步执行，返回 `CompletableFuture<R>` |
| `thenCompose(f)` | 结果触发新异步任务 | f 返回 Future，拍平避免嵌套 |
| `thenCombine(f, fn)` | 两个任务结果合并 | 并行执行，fn 收两个值 |
| `allOf` / `anyOf` | 多任务全部/任一完成 | 配合 `join` 聚合结果 |
| `exceptionally(f)` / `handle(f)` | 失败分支处理 | 恢复为值，管线不断 |

生产的两个关键配置点，缺一个就埋雷：

- **线程池显式指定**：`supplyAsync(fn, executor)` 必须传自有线程池——默认的 `commonPool` 与 parallel stream 共享，被占满时所有异步任务一起饿死。线程池大小按"阻塞型任务数上限"估算（I/O 型给 NIO 线程数 2-4 倍），并监控队列积压
- **异常不静默**：`whenComplete`/`exceptionally` 至少要打日志——`CompletableFuture` 的失败若不消费，异常被吞进"完成状态"里无人知晓，线上表现为"任务没执行"的诡异假象

## 2. thenApply vs thenCompose：异步世界的 map/flatMap

两者是面试高频对比，本质是 Optional/Stream 的 `map` vs `flatMap` 在异步域的复刻：

```java
// thenApply：变换后仍是"一层 Future"——f 返回 R 而非 Future<R>
CompletableFuture<String> name = userFuture.thenApply(User::name);   // ✅

// ❌ 反例：f 返回 Future 却不拍平 → Future<Future<...>> 嵌套
CompletableFuture<CompletableFuture<String>> nested =
        userFuture.thenApply(u -> repo.findNameAsync(u.id()));

// thenCompose：自动拍平 —— 等价于 flatMap
CompletableFuture<String> flat = userFuture.thenCompose(u -> repo.findNameAsync(u.id()));
```

判据一句话：**变换函数返回普通值用 thenApply，返回新 CompletableFuture 用 thenCompose**。嵌套 Future 是异步代码的第一大腐化信号，`thenCompose` 是唯一解药。

## 3. parallel stream 的纯函数约束

`parallelStream()` 是函数式管线最快的并行入口，但代价是严格的约束：**lambda 必须无状态、无干扰（non-interfering, stateless）**——这是 Stream javadoc 的明确契约（05 章契约论的具体案例）。

- 无状态：lambda 内不得读写共享可变状态（计数器、共享集合、`SimpleDateFormat`）
- 无干扰：不得修改流的底层数据源（遍历中改 List 结构）
- 共享资源限制：所有并行流共享公共 ForkJoinPool（`ForkJoinPool.commonPool()`），一个流占满线程会影响全应用；无法自定义池（`parallel()` 不支持传池，需自建 `ForkJoinPool` 包裹）

```java
// ✅ 合法：纯函数变换，安全并行
List<BigDecimal> totals = orders.parallelStream()
        .map(o -> o.amount().multiply(rate))     // 纯函数
        .toList();

// ❌ 非法：lambda 有状态（累加到共享集合）——数据竞态
List<BigDecimal> out = new ArrayList<>();
orders.parallelStream().forEach(o -> out.add(o.amount()));
```

> ⚠️ **2026 定位**：parallel stream 只适合 CPU 密集的纯变换；I/O 密集场景（每元素一次 RPC/DB 查询）应改用虚拟线程顺序执行或 `mapConcurrent`（07 章）——前者占满公共池，后者阻塞线程，都是 I/O 场景的错误工具。

## 4. 虚拟线程：函数式异步的新语境

虚拟线程（JDK 21 定稿，JEP 444）改写了并发的叙事：**阻塞不再昂贵**。每请求一线程的同步代码重回推荐序列，而函数式并发因此获得新语境：

- 同步代码 + 虚拟线程：可读性最好，无需 thenApply 链，代价是"阻塞式写法"——适合服务端编排
- CompletableFuture 链：保留"异步结果组合"的表达力，适合事件驱动与并行扇出（fan-out）
- 实践共识（2026）：**编排用虚拟线程顺序代码 + 并行扇出用 CompletableFuture/结构化并发**，二者互补而非替代

```java
// 虚拟线程：三路并行查询（try-with-resources 等待全部）
try (var scope = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<Price> a = scope.submit(() -> quoteA.fetch());
    Future<Price> b = scope.submit(() -> quoteB.fetch());
    return pickBest(a.get(), b.get());     // 阻塞式等待，成本极低
}
```

虚拟线程的三个适用边界要讲清（否则会踩"虚拟线程万能"的坑）：

- **不适合 CPU 密集**：虚拟线程不增加核心数，纯计算用平台线程数 = 核心数即可，虚拟线程反而增加调度开销
- **synchronized 锁 pinning**：持锁阻塞时可能钉住载体线程（JEP 491 已改善，但重锁仍可能 pin），锁竞争激烈处仍建议 `ReentrantLock`
- **有界的连接池是瓶颈**：虚拟线程数远大于数据库/HTTP 连接数时，池等待成为真正的限流点——并发度由下游资源决定，不是线程数

函数式视角的落点：虚拟线程让"同步代码可并发"，CompletableFuture 让"异步代码可组合"——**前者简单，后者可控**；混合使用时，边界放在"扇出/聚合"处（并行子任务用 CF 或结构化并发，编排主流程用虚拟线程同步写）最清晰。

## 5. 结构化并发与 Scoped Values

**结构化并发（Structured Concurrency）**：把并发任务建模为"一个单元"——子任务随父作用域生命周期统一管理，要么全部成功要么全部取消，杜绝线程泄漏。演进状态：JDK 21 预览（JEP 453）→ 第 5 预览（JEP 505，JDK 25）→ **第 6 预览（JEP 525，JDK 26）**，新增 `onTimeout()`、`allSuccessfulOrThrow()` 等方法，仍未定稿——生产使用需 `--enable-preview`。

```java
// JEP 525 形态（预览 API，以最终定稿为准）
try (var scope = StructuredTaskScope.open()) {
    Future<Order> order = scope.fork(() -> orderService.load(id));
    Future<User> user = scope.fork(() -> userService.load(orderId));
    scope.join();
    return new OrderDetail(order.resultNow(), user.resultNow());
}
```

**Scoped Values（JEP 506，JDK 25 定稿）**：取代 ThreadLocal 的可变继承传值——不可变、作用域约束、跨虚拟线程传递，与结构化并发天生配对。它与函数式范式的共鸣：**传值不传状态**——调用上下文以值形式显式传递，而非隐式可变全局。相比 ThreadLocal 的三个改进：不变量"只写一次"由运行时保证（写入后 `get` 永远返回同一值）、无泄漏（作用域退出即失效，没有 remove 纪律）、跨虚拟线程自动传播且不可被内层意外修改——把"隐式全局"改造为"显式作用域常量"。

```java
ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();
ScopedValue.where(REQUEST_ID, traceId).run(() -> handle());   // 作用域内可见
// 内部代码 ScopedValue.get() 读取，跨线程自动传播
```

## 6. Flow API 响应式流

`java.util.concurrent.Flow`（Java 9 引入）是响应式流的 JDK 标准：`Publisher`/`Subscriber`/`Subscription`/`Processor` 四接口，核心是**背压（backpressure）**——订阅方按需请求，生产方限量发放，避免"无限生产压垮消费"。

函数式视角的定位：Flow 是**推模型的异步数据流**（事件驱动、按需拉取），与 Stream（拉模型、按需生成）语义互补——前者适合消息/推送场景（如 `SubmissionPublisher`），后者适合集合/计算场景。选型对照：

| 维度 | Stream | Flow / 响应式流 |
|------|--------|----------------|
| 驱动方式 | 拉模型（终止操作触发） | 推模型（订阅者按需请求） |
| 背压 | 无（短路即停） | 有（`request(n)` 控制速率） |
| 典型场景 | 集合变换、批处理 | 消息推送、高吞吐事件流 |
| 实现 | JDK 内置 | `SubmissionPublisher` / Reactor / RxJava |

2026 年的生产事实：JDK 内置 Flow 主要作为**标准协议层**存在，多数团队通过 Reactor/RxJava 或消息中间件使用响应式范式，且后端 REST 场景大量回归虚拟线程同步写法——响应式仍是"合适场景的工具"，不是银弹。判断一句话：**数据在内存集合里流动用 Stream，数据在系统之间流动用响应式流/消息队列**。

> 🎯 **核心要点**：函数式并发全景 = CompletableFuture（组合）+ parallel stream（纯函数约束）+ 虚拟线程（同步回潮）+ 结构化并发（生命周期治理）+ Flow（背压协议）。2026 的分工结论：纯变换并行用 parallel stream/mapConcurrent，服务端编排用虚拟线程，扇出聚合用 CompletableFuture 或结构化并发。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. CompletableFuture 是异步版 Stream：thenApply=map、thenCompose=flatMap、exceptionally=错误值分支，嵌套 Future 必须拍平；
> 2. parallel stream 的契约是"无状态无干扰"，共享公共池 + I/O 场景禁用，改用虚拟线程或 mapConcurrent；
> 3. 2026 组合拳：虚拟线程做编排、结构化并发（JEP 525 第 6 预览）管生命周期、Scoped Values（JEP 506 定稿）传值不传状态。
