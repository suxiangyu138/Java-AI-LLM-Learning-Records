## 1. 递归范式：分解与聚合

函数式风格中，循环被"递归 + 不变式"取代：把问题拆成"一步 + 更小的同类问题"，递归调用处理小的，返回时聚合结果。三个经典形态：

```java
// 线性递归：n! = n * (n-1)!
long factorial(long n) {
    return n <= 1 ? 1 : n * factorial(n - 1);
}

// 树形递归：斐波那契（朴素版指数级，仅演示形态）
long fib(long n) {
    return n <= 1 ? n : fib(n - 1) + fib(n - 2);
}

// 尾递归：累加器模式（结果随调用下沉，最后一步就是递归调用本身）
long sum(long n, long acc) {
    return n == 0 ? acc : sum(n - 1, acc + n);
}
```

递归的工程价值：**无需循环变量、天然不可变**（每层栈帧是独立局部状态），逻辑自明。代价是栈帧消耗——这引出 JVM 的核心限制。

递归与 02 章 memoize 相遇还有一个经典组合——**记忆化递归**：重叠子问题（如斐波那契、爬楼梯、背包）的朴素递归是指数级的，用纯函数 + 缓存即可降为多项式级，且不改递归形态：

```java
Map<Long, Long> cache = new HashMap<>();           // 注意：需线程安全或单线程使用
long fibMemo(long n) {
    return cache.computeIfAbsent(n, x -> x <= 1 ? x : fibMemo(x - 1) + fibMemo(x - 2));
}
// 朴素 fib(50) 要算 2^50 次；记忆化后 O(n)
```

但记忆化有两个前提：**键必须幂等且有限基数**（输入空间无限时缓存无意义）、**缓存需考虑淘汰**（生产用 Caffeine 而不是裸 HashMap）。递归 + memoize 只适合"子问题重叠"的算法场景，业务代码中树遍历、解析器等"子问题不重叠"的递归不需要记忆化。

## 2. JVM 无尾调用优化：深递归的代价

**尾调用优化（Tail Call Optimization, TCO）**：尾递归调用不新开栈帧，而是复用当前帧并跳转——把递归变成循环，深度不再受限。JVM 至今（2026，JDK 26）未实现 TCO，原因包括：栈帧承载的安全信息（方法归属、监控、异常回溯）难以复用、与安全检查模型冲突、以及 hot spot 与栈帧语义的深度耦合。

现实后果：

- 默认线程栈约 1MB（`-Xss` 可调），深递归约在 **万级（10^3-10^4）调用** 时 `StackOverflowError`
- 递归深度超过数千的算法（大数组二分递归、深树遍历）在生产环境随时可能爆栈
- 配合虚拟线程（JDK 21 定稿）：虚拟线程栈同样受限（默认从少量内存按需增长），深递归在虚拟线程里同样危险

```java
sum(10_000_000, 0);   // ❌ StackOverflowError（尾递归也救不了：JVM 不优化尾调用）
```

结论：**Java 里"优雅的递归"止步于已知深度**（如树高 < 1000 的遍历）；对不可控深度，工程上选迭代、显式栈，或 trampoline。

## 3. Trampoline：手工还原尾递归

**Trampoline（蹦床）**：把"下一次调用"包装成可延迟对象，由循环驱动逐步执行——递归深度转移给堆，栈恒为 O(1)：

```java
sealed interface Step<T> permits Done, More {}
record Done<T>(T value) implements Step<T> {}
record More<T>(Supplier<Step<T>> next) implements Step<T> {}

<T> T trampoline(Step<T> step) {
    while (step instanceof More<T>(var next)) step = next.get();  // 循环驱动，无递归
    return ((Done<T>) step).value();
}

// 尾递归改写为"返回下一步"
Step<Long> sumStep(long n, long acc) {
    return n == 0 ? new Done<>(acc) : new More<>(() -> sumStep(n - 1, acc + n));
}

long sumSafe = trampoline(sumStep(10_000_000, 0));  // ✅ 千万级不再爆栈
```

工程判断：trampoline 在 Java 里更多是"知识点"而非日常武器——10 万级以下深度优先迭代，trampoline 的分配成本高于收益；它真正适用的是**函数式框架内部**（Stream 实现、Scala 互操作）、或"递归形态无法改写迭代"的算法（复杂树的重写遍历）。面试常问，生产少用，心中有数即可。

## 4. 惰性求值：Supplier 与 Lazy 模式

**惰性求值（lazy evaluation）**：值在**首次使用**时才计算。Java 方法参数是严格求值（先算后传），惰性要靠函数封装：`Supplier<T>` 就是"尚未计算的 T"。

```java
// 严格：无论是否命中，都先构建默认值
User u = find(id).orElse(new User());

// 惰性：只有真正缺失时才构建（06 章的 orElseGet 就是惰性 API）
User u = find(id).orElseGet(User::new);

// 通用 Lazy 封装：一次计算，多次复用（并发安全）
class Lazy<T> {
    private volatile T value;
    public T get(Supplier<T> compute) {       // 双重检查：线程安全 + 只算一次
        T v = value;
        if (v == null) synchronized (this) {
            if ((v = value) == null) value = v = compute.get();
        }
        return v;
    }
}
```

惰性的三个典型用途：**昂贵且可能不用的资源**（图片/配置/模型加载，AI 场景的模型懒加载是典型）、**循环依赖的构造**（对象图里 A↔B 用 Supplier 打破初始化顺序）、**无限结构的前缀**（下节）。

领域建模里的一个高频惰性案例——**懒加载的配置/规则对象**：规则表可能很大、加载可能依赖远程，但只有部分请求会触发规则求值：

```java
class PricingEngine {
    private final Lazy<Rules> rules = new Lazy<>();

    Result<BigDecimal> price(Order o) {
        Rules r = rules.get(this::loadRules);   // 首次调用才加载，之后复用
        return apply(o, r);
    }
}
```

代价要讲清楚：惰性把"失败的时机"推迟到首次使用——如果 `loadRules` 依赖外部服务，构造时看起来成功、首次调用才炸。**惰性适用于"慢"的权衡，不适用于"可能失败"的权衡**；可能失败的加载应显式预加载或在边界调用，别用 Lazy 藏雷。

## 5. 无限流：惰性管线的边界能力

Stream 的中间操作全部惰性，这让"无限流"成为可能——不真的存在无穷集合，而是"按需生成、短路即停"：

```java
// 无限流：自然数 → 过滤质数 → 取前 5 个即终止（短路）
List<Integer> primes = Stream.iterate(2, n -> n + 1)
        .filter(IsPrime::test)
        .limit(5)
        .toList();

// 注意：iterate 的"种子 + 函数"必须生成新值；终止操作缺一不可
```

配合要点：**无限流必须带短路终止操作**（`limit`/`takeWhile`/`findFirst`），且 `takeWhile`（Java 9+）优于 `filter + limit` 组合——前者在条件不满足时立刻停，后者会一直扫到 limit 满为止。惰性管线不是免费午餐：`skip(n)` 会真的迭代 n 个元素，`sorted` 需要缓存全量——**惰性豁免的是"用不到的部分"，不是"计算本身"**。

再补两个边界情形：`iterate` 与 `generate` 生成的是"无记忆"序列（前者可携带上次值，后者完全无状态），需要"按前值递推"用 `iterate`（质数、斐波那契都靠它），纯粹重复/随机供给用 `generate`；而 `distinct()`/`sorted()` 全量物化操作遇到无限流直接 OOM，无限流的处理只能走逐元素操作——这些限制不是 API 缺陷，而是"惰性 + 短路"语义的必然边界。

## 6. Java 惰性求值的边界

Java 的惰性是"手动封装的"而非语言内置，边界清晰：

| 语言/机制 | 惰性程度 |
|-----------|---------|
| Haskell | 默认全惰性（调用即惰性） |
| Scala `val` vs `lazy val` | 显式惰性关键字 |
| Java | **无语法级惰性**：一切靠 `Supplier`/Stream 显式封装 |

现实含义：方法参数一律严格求值（没有"按名传参"），条件表达式 `cond ? a : b` 是少数原生短路惰性的语法；`&&`/`||` 同理。因此"某参数可能昂贵且可能不用"时，接口设计要主动接收 `Supplier<T>` 而不是 `T`——这是把惰性写进契约的唯一途径。

> 🎯 **核心要点**：递归讲"怎么把问题变小"，惰性讲"什么时候真的算"。Java 里两者都要显式——深递归用迭代/trampoline（栈帧是硬限制），惰性用 Supplier/Stream（严格求值是默认）。理解"计算的时机可控"，就同时理解了这两章。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 递归的三种形态（线性/树形/尾递归），JVM 无 TCO，万级深度即爆栈，深递归改迭代或 trampoline；
> 2. 惰性靠 Supplier/Stream 显式封装，Lazy 模式用双重检查实现"只算一次"；
> 3. 无限流必须配短路终止操作，惰性豁免"用不到的部分"而非"计算本身"。
