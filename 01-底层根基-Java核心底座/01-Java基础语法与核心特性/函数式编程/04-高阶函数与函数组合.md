# 高阶函数与函数组合

> 高阶函数让"函数"成为可传递、可返回、可拼接的构建单元；函数组合（andThen/compose）则把散落的处理步骤拧成一条声明式管线。这是函数式风格在 Java 中最常被低估、也最实用的一组能力

## 1. 高阶函数：函数成为一等构建单元

**高阶函数（higher-order function）**：接收函数作为参数，或返回函数作为结果的函数。Java 中借助函数式接口（05 章详述）实现，典型形态：

```java
// 接收函数：把"校验规则"作为参数传入
boolean anyMatch(List<Item> items, Predicate<Item> rule) {
    for (Item it : items) if (rule.test(it)) return true;
    return false;
}

// 返回函数：根据折扣档位"生成"计算函数
Function<BigDecimal, BigDecimal> discountFunction(int tier) {
    return tier >= 3 ? p -> p.multiply(BigDecimal.valueOf(0.9))
                     : Function.identity();
}
```

高阶函数带来的是**行为参数化**：调用方把"做什么"注入，被调用方只负责"怎么编排"。Spring 里 `JdbcTemplate.query(sql, rowMapper)`、`RestTemplate.exchange(url, ...)` 的回调，本质都是高阶函数的框架化应用。

## 2. 组合子工具箱：andThen 与 compose

JDK 函数式接口内置了组合子，用它们把单步函数拼成复合函数：

| 接口 | 组合方法 | 语义 |
|------|---------|------|
| `Function<T,R>` | `f.andThen(g)` | 先 f 后 g：`g(f(x))` |
| `Function<T,R>` | `f.compose(g)` | 先 g 后 f：`f(g(x))` |
| `Predicate<T>` | `p.and(q)` / `p.or(q)` / `p.negate()` | 逻辑与/或/非 |
| `Consumer<T>` | `c1.andThen(c2)` | 先 c1 后 c2 |
| `UnaryOperator<T>` | `andThen` / `compose` | 同 Function |

```java
// 需求：文本 → trim → 大写 → 求长度
Function<String, Integer> len = String::length;
Function<String, Integer> pipeline = len.compose(String::toUpperCase).compose(String::trim);
// 等价于 len(uppercase(trim(s)))

// 需求：价格校验 = 非负 且 低于上限
Predicate<BigDecimal> valid = p -> p.signum() >= 0;
Predicate<BigDecimal> withinCap = p -> p.compareTo(cap) < 0;
Predicate<BigDecimal> rule = valid.and(withinCap).negate();  // 可读：非法价格
```

> 💡 **读法口诀**：`andThen` 按书写顺序从左到右执行（先 f 后 g），`compose` 从右往左读（先 g 后 f）。团队约定统一使用 `andThen`，可读性更好、方向更直观。

## 3. 管线化设计：数据流式流水线

组合子的高阶形态是**管线（pipeline）**：把业务处理拆成多个纯函数步骤，依次串联。每个步骤单一职责、独立测试，整条管线一眼可读：

```java
// 订单处理管线：校验 → 计价 → 折扣 → 记账（每步一个纯函数）
Order handle(Order o) {
    return Stream.<Function<Order, Order>>of(
        this::validate,
        this::calculate,
        this::applyPromo,
        this::settle
    ).reduce(Function.identity(), Function::andThen).apply(o);
}
```

这份写法的工程价值不止"好看"：

- **步骤可插拔**：新增"风控"环节只需往链上插一个函数，不动其他步骤
- **顺序显式化**：处理顺序写在唯一一处，review 一眼看清
- **单步可测**：每个函数独立传参测试，无需构造完整流程
- **条件装配**：管线本身就是可组合的值——按配置决定哪些步骤参与

```java
List<Function<Order, Order>> steps = new ArrayList<>();
steps.add(this::validate);
if (config.enablePromo()) steps.add(this::applyPromo);
steps.add(this::settle);
// 运行时动态组装
```

管线化的成本也要如实认知，避免"为函数式而函数式"：

- **调试栈变深**：管线中任何一步抛异常，栈里是 `lambda$applyPromo$12` 这类方法名——需要分段断点或 `Objects.requireNonNull` 精确失败点（10 章三板斧）
- **中间对象增多**：每步一个函数调用、参数对象多次传递，热路径上注意逃逸分析消化（03 章）
- **适合"同构数据流"**：所有步骤输入输出同型（如都是 `Order`）才适合函数链；步骤间数据形态频繁变化时，`Function` 链的类型会写得很难看——此时改用 Stream 管线（07 章）或普通方法调用更自然

## 4. 柯里化与部分应用

**柯里化（currying）**：把多参数函数拆成单参数函数链——每传入一个参数返回一个新函数。**部分应用（partial application）**：先固定部分参数，得到"少一个参数"的函数。两者在 Java 中都要手工实现，因为 JDK 函数式接口只到两参（BiFunction）：

```java
// 柯里化：rate 先行绑定，得到"算税"专用函数
Function<BigDecimal, Function<BigDecimal, BigDecimal>> tax =
        rate -> amount -> amount.multiply(rate);

Function<BigDecimal, BigDecimal> vat = tax.apply(new BigDecimal("0.13")); // 部分应用
BigDecimal due = vat.apply(new BigDecimal("100"));  // 113.00

// 两参接口的柯里化固定写法
BiFunction<Integer, Integer, Integer> add = Integer::sum;
Function<Integer, Function<Integer, Integer>> curried = a -> b -> add.apply(a, b);
```

实用场景：**配置先行绑定、数据后到**——报表组件先绑定税率/汇率参数生成专用函数，再把函数传给数据遍历逻辑；批量处理时同一份绑定函数反复复用，避免每行重复传参。

```java
// 批量场景：一次绑定折扣档位，N 行数据复用同一个函数
Function<BigDecimal, BigDecimal> priceFn = tax.apply(rate).andThen(discountFn(tier));

List<BigDecimal> totals = orders.stream()
        .map(o -> priceFn.apply(o.amount()))   // 每行只传"数据"，配置已绑定
        .toList();
```

注意柯里化的局限：嵌套 lambda 会让类型签名指数级膨胀（`Function<A, Function<B, Function<C, R>>>`），超过两参即可读性崩坏。实践中**部分应用（固定参数）比完整柯里化实用得多**——先绑定配置，剩下的留给调用方；完整柯里化多用于框架内部或 DSL 设计，业务代码慎用。

## 5. 设计模式函数式化：策略与装饰

经典设计模式在高阶函数面前被大幅"压缩"：

- **策略模式**：策略接口 + 实现类 N 个，压缩为一个 `Function`/`Predicate` 字段 + lambda 注入。策略集合变成 `Map<String, Function<...>>` 注册表，按 key 取策略——比 if-else 链与类继承都更直观

```java
Map<String, Function<Payment, Boolean>> payStrategies = Map.of(
    "wechat", PaymentService::payWechat,
    "alipay", PaymentService::payAlipay,
    "card",   PaymentService::payCard
);
payStrategies.get(payMethod).apply(payment);
```

- **装饰器模式**：包装类链压缩为 `andThen` 函数链——打点、重试、限流逐个包上去，形成"洋葱"

```java
Function<Request, Response> base = this::dispatch;
Function<Request, Response> decorated = base
        .andThen(log::trace)          // 包装：记录
        .andThen(metrics::record);    // 包装：埋点
```

模板方法、观察者同理：变化的部分提取为函数参数，不变骨架留在方法里。这不是"放弃设计模式"，而是用组合取代继承表达同样意图——模式依然在，只是从类级降到了函数级。

函数式装饰与 Spring AOP 容易混淆，分工要讲清：**AOP 管"横切"**（鉴权、事务、限流——与业务无关、按注解自动织入），**函数式装饰管"竖切"**（业务链上按顺序包装的步骤——打点、重试、降级策略）。AOP 适合"全系统统一"的切面，函数链适合"单条管线局部"的组装；前者改动影响面大（要过织入机制），后者只在调用点生效、可读性更强。实践中二者常组合：AOP 拦入口，函数链编排内部。

## 6. Java 表达高阶函数的边界

Java 表达高阶函数有天然短板，工程师需心中有数：

1. **无一等函数字面量**：lambda 只能转成函数式接口实例，不能独立存在；无法定义"函数的函数"这种直接类型，只能层层嵌套接口
2. **类型声明冗长**：`Function<Function<A,B>, Function<C,D>>` 层层嵌套，可读性断崖——超过两层建议引入类型别名或专用接口
3. **两参上限**：JDK 核心接口最多 BiFunction/BiPredicate/BiConsumer；三参需自建接口（05 章）
4. **受检异常**：函数式接口的抽象方法不抛受检异常，IO 操作在 lambda 里必须包装（05 章详述）
5. **类型别名缺失**：没有 Scala 的 `type` 关键字，函数签名只能完整书写——三参以上、嵌套泛型的签名可读性崩塌时，提取专用接口或补充类型注释，别硬扛

综合判断：高阶函数在 Java 里的甜区是"**一参一返回、纯变换、两步以内组合**"；超出甜区（多参、受检异常、深层嵌套），退回显式方法调用通常更诚实。

> 🎯 **核心要点**：组合子的价值 = 把"过程"变成可命名、可传递、可装配的"值"。管线化设计是高阶函数的最佳落点；遇到三层以上嵌套或受检异常，说明该考虑换一种表达了。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 高阶函数 = 行为参数化：把"做什么"注入，"怎么编排"留给自己；
> 2. 组合子 andThen/compose/and/or 把单步函数拼成管线，读法统一用 andThen 更直观；
> 3. 柯里化与部分应用手工实现，适合"配置先行、数据后到"；策略/装饰模式可函数化压缩，组合取代继承。

**思考题**：

1. `f.andThen(g)` 与 `f.compose(g)` 执行顺序差在哪？（→ 2 节）
2. 管线中的步骤如何按配置动态增删？（→ 3 节）
3. 柯里化与部分应用的区别是什么？（→ 4 节）
4. 什么信号出现时，说明"该把函数式表达换回类设计了"？（→ 6 节）
