# 不可变性与不可变数据

> 可变状态是并发 bug 与隐式耦合的第一来源。不可变性不是"不能改数据"，而是"把修改变成创建"——牺牲一点分配开销，换回推理、共享、并发的全面安全。Record 与不可变集合让 Java 的不可变建模从"自觉"变成"语法级"（JDK 25 LTS 的 Compact Object Headers 又降低了这份开销）

## 1. 不可变的价值：推理、共享、并发

不可变对象（immutable object）创建后状态永不改变。它的价值可以压缩成三句话：

- **推理成本降到零**：看到对象就知道它的值，任何方法不会偷偷改掉它——读代码不用追踪"谁动过这个字段"
- **共享变得安全**：同一个对象可以安全地传给任何方法、放进任何集合、交给任何线程，因为没人能改它——彻底消灭"传引用后被改"的隐式耦合
- **并发无需加锁**：不可变对象天然线程安全，读操作永远一致快照——这正是 02 章"确定性核心"能免锁并行的另一半基础

反例就是教科书级的 `SimpleDateFormat`：JDK 源码注释明确声明它非线程安全，因为内部可变状态在 `format()` 时被修改——Java 8 之前每个调用点都要新建实例或用 ThreadLocal。2026 年的正确替代是 `DateTimeFormatter`（不可变），一次创建全局共享，正是"用不可变替代锁"的官方实践。

## 2. 实现不可变的四个层次

Java 实现不可变有四个递进层次，日常开发按成本从低到高选用：

| 层次 | 手段 | 说明 | 成本 |
|:---:|------|------|:---:|
| 1 | `final` 字段 + 无 setter | 最基本；构造器内完整赋值 | 低 |
| 2 | 防御性拷贝 | 构造器/访问器拷贝数组、Date 等可变组件 | 中 |
| 3 | Record（JDK 16+） | 语法级不可变：final 字段 + 访问器 + equals/hashCode | 低 |
| 4 | 不可变集合 | `List.of`/`copyOf`/`toUnmodifiableList` | 低 |

防御性拷贝是"内部藏可变组件"时的必答题——即使字段是 `final`，若它指向一个可变对象（如 `Date`、`ArrayList`），外部仍能通过引用修改"不可变"对象的内部：

```java
public final class Period {                     // 声明了 final 不代表不可变
    private final Date start;                   // Date 本身可变！
    public Period(Date start) { this.start = new Date(start.getTime()); }  // 入参拷贝
    public Date start() { return new Date(start.getTime()); }              // 出参拷贝
}
```

## 3. Record：语法级不可变建模

Record（JEP 395，JDK 16 定稿）把"手写 5 样东西"压缩成一行声明：final 字段、全参构造器、访问器、`equals`/`hashCode`/`toString`。它取代了价值对象（value object）的样板代码，是 2026 年不可变建模的事实标准：

```java
public record OrderItem(long skuId, int quantity, BigDecimal price) {}
// 自动生成：private final 字段 + 构造器 + skuId()/quantity()/price() + equals/hashCode/toString

// "修改" = 创建新实例（with 模式）
OrderItem discounted = new OrderItem(item.skuId(), item.quantity(), item.price().multiply(newRate));
```

两个使用纪律：

- **组件必须不可变**：`record Box(List<String> items)` 内部仍是可变 List——应声明为 `List.of(...)` 或记录构造器内拷贝
- **紧凑构造器做校验**：不变量校验（非空、正数）写在紧凑构造器里，保证"任何合法 Record 一定满足约束"

```java
public record Money(BigDecimal amount, String currency) {
    public Money {
        Objects.requireNonNull(amount);
        if (amount.signum() < 0) throw new IllegalArgumentException("negative money");
    }
}
```

## 4. 不可变集合：真正不可变 vs 只读视图

JDK 9+ 提供了三族"不可变集合 API"，语义差异是高频面试点：

| API | 本质 | 修改行为 |
|-----|------|---------|
| `List.of(...)` / `Set.of` / `Map.of` | 真正不可变（值拷贝） | 抛 `UnsupportedOperationException` |
| `List.copyOf(c)` | 真正不可变（若 c 已是不可变则零拷贝复用） | 同上 |
| `Collections.unmodifiableList(c)` | 只读**视图**（包装原集合） | 视图上抛异常，**原集合仍可改** |

```java
List<String> raw = new ArrayList<>();
List<String> view = Collections.unmodifiableList(raw);  // 视图：raw 仍可改
List<String> frozen = List.copyOf(raw);                 // 冻结：raw 后续修改不影响
raw.add("x");   // view 变了，frozen 不变
```

纪律：**对外暴露集合一律返回不可变副本**（`List.copyOf` 或 `stream().toList()`），拒绝返回内部可变集合——这是防御性编程在集合层面的标准姿势。`Collectors.toUnmodifiableList()`（JDK 10+）与 `Stream.toList()`（JDK 16+）则是收集阶段的冻结手段。

配套的工程规范还有三条，写入团队约定即可避免大多数"可变泄漏"：

1. **getter 只出不进**：返回内部集合前 `List.copyOf(this.items)`；构造时若入参是可变集合也先拷贝——双向防泄漏
2. **遍历不改源**：`for (Item i : items) i.setX(...)` 修改元素是合法的（元素可变），但 `items.add/remove` 结构修改必须显式拷贝后操作
3. **状态字段清零**：实体里"剩余额度""累计次数"这类会变的量，不要因为追求不可变而塞进 record——它们是状态不是数据，留给状态转移函数或命令式字段

不可变与并发集合是互补而非替代：高并发写场景（计数、缓存）用 `ConcurrentHashMap`/`LongAdder` 这类并发原语，读多写少的共享配置用不可变快照（如 `Map.copyOf` 后发布）——后者零锁且天然一致，后者没有快照语义。

## 5. 可变状态显式化：状态转移函数

不可变世界如何处理"状态"？答案不是消灭状态，而是**把状态变成函数的参数与返回值**——状态转移函数（state transition function）：

```java
// 命令式：内部状态被各方法偷偷修改，全类共享，难追踪
class OrderState {
    private Status status;
    void pay() { if (status == CREATED) status = PAID; }
}

// 函数式：状态是值，流转是纯函数 —— 每一步可测、可重放、可审计
record OrderState(Status status) {
    OrderState pay() { return status == Status.CREATED ? new OrderState(Status.PAID) : this; }
}
```

这带来了两个额外红利：**可重放性**（把历史状态序列存下来即可回放、审计、调试，事件溯源就是此思想的持久化版本）与**可推导性**（非法迁移在编译期就能表达——sealed 接口配合模式匹配可穷举所有合法状态组合）。状态机的函数式表达是 2026 年后端设计的高频考点（幂等、履约、对账场景均适用）。

## 6. 性能权衡与 JIT 的补偿

不可变的主要代价是"修改 = 新建对象"，高频路径上产生分配压力。现代 JVM 有三级补偿：

1. **逃逸分析 + 标量替换**：对象未逃逸出方法时，JIT 直接把字段拆成寄存器/栈上值，堆分配被消除——短生命周期的小对象成本趋近于零
2. **Compact Object Headers（JEP 519，JDK 25 定稿）**：对象头从 96/128 位压缩到 64 位，堆占用普遍降低 10-20%，间接放大"大量小不可变对象"的可承受规模
3. **值类型（Valhalla，JEP 401，首个预览计划 JDK 28）**：未来的 value class 将提供"无身份、可展平"的值对象——不可变数据的内存红利将彻底兑现（见「装箱拆箱 泛型擦除/08」）

不可变对象还白送一个常被忽略的能力——**作为 Map 键与缓存键的安全**：`hashCode` 稳定不变，放入 `HashMap`/`ConcurrentHashMap` 后不会被"改字段"弄坏哈希桶定位。可变对象做键是经典内存泄漏源（键的哈希变了，元素永远取不出来），而 record 天然免疫。这也是 02 章 memoize 实现能直接用 record 输入做缓存键的底层保障：键不可变，缓存语义才成立。

实践结论：**先写不可变，遇到真实压测瓶颈再优化**。2026 年的 JVM 已经为不可变风格买单了大部分成本，而可变风格引入的并发与推理成本却始终要开发者自己扛。

> 🎯 **核心要点**：不可变 = 把"修改"重定义为"创建"。Record 管建模、不可变集合管容器、状态转移函数管状态、JIT/Valhalla 管成本——四件套齐了，可变代码就只剩"性能特例"一个存在理由。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 不可变换来推理、共享、并发三安全，代价由逃逸分析、Compact Object Headers（JDK 25）与未来的值类（JEP 401）逐级补偿；
> 2. 实现四层次：final 字段 → 防御性拷贝 → Record → 不可变集合；`List.copyOf` 才是真冻结，`unmodifiableList` 只是视图；
> 3. 状态不消灭，而是显式化为状态转移函数——可测、可重放、可审计。
