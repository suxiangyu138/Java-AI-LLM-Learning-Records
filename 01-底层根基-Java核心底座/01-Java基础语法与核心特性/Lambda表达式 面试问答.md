# Lambda表达式 面试问答

### Q1. Lambda 是什么？和匿名内部类有什么区别？

**口述答案**

Lambda 是函数式接口的简洁实现，本质是一段可以传递的行为，用来替代只含一个方法的匿名内部类。

两者在字节码层面完全不同。匿名内部类在编译期生成 `Outer$1.class`，Lambda 编译成 `invokedynamic` 指令，运行时由 `LambdaMetafactory` 动态生成实现类。`this` 的指向也不同，匿名内部类的 `this` 指向内部类实例，Lambda 的 `this` 指向外围实例。性能上 Lambda 首次链接有开销，之后 JIT 能内联，热点路径通常更快。面试常问它是不是语法糖，答到字节码层面就够。

---

### Q2. Lambda 的语法有哪些简化规则？

**口述答案**

完整形式是参数列表加箭头加方法体，比如 `(String a, String b) -> { return a + b; }`。简化规则有四条：

- 参数类型可以省略，编译器按目标类型推断
- 单参数时括号可以省略
- 方法体只有一句表达式时，大括号和 `return` 都可以省略
- 没有参数时必须保留空括号

边界是类型要么全写要么全不写，不能只给部分参数标类型。另外没有目标类型时编译器无法推断参数类型，必须显式声明，这一点在写工具方法时最容易踩。省略规则只影响写法，不影响语义。另外箭头两侧的空格不影响语义，但团队里要保持统一写法。

---

### Q3. 什么是函数式接口？@FunctionalInterface 有什么用？

**口述答案**

只有一个抽象方法的接口叫函数式接口，也就是 SAM。它可以有任意多个 `default` 方法和 `static` 方法，`Object` 继承来的方法不计入抽象方法数量。

`@FunctionalInterface` 是编译期校验注解，加上之后如果写出两个抽象方法会直接编译失败，起到文档和防错的作用。但它不是 Lambda 的必要条件，只要结构符合 SAM，不加注解也能用 Lambda 实现。接口可以加 `default` 方法，这也是函数式接口能平滑演进的原因，比如 `Comparator` 后来补了 `reversed`。

---

### Q4. 什么是目标类型？为什么 Lambda 需要它？

**口述答案**

Lambda 本身没有独立类型，它的类型由上下文决定，这个上下文叫目标类型。常见来源有四种：

- 变量赋值
- 方法参数
- 方法返回值
- 强制类型转换

目标类型决定了参数类型、返回值类型和允许抛出的异常，所以同一个 Lambda 在不同上下文里可以对应不同的函数式接口。边界在重载方法，两个重载都接受函数式接口时编译器可能推断不出来，需要显式强转告诉它选哪个。写 Lambda 之前先想清楚赋给哪个接口，参数和返回值自然就定了。常见的目标类型还有泛型方法的返回值和三元表达式，这两处最容易出错。上下文越明确，Lambda 越好写。

---

### Q5. Lambda 为什么要求捕获的变量是 effectively final？

**口述答案**

因为 Lambda 捕获的是局部变量的值拷贝，不是引用。如果允许后续修改，拷贝和原变量会不一致，执行时看到的可能是另一个值，语义就不可预期。

effectively final 指变量初始化后没有再被赋值，不要求显式加 `final`。实例字段和静态变量不受这个限制，因为它们通过 `this` 或类名访问，不算捕获。想在不同 Lambda 之间共享可变状态，用数组、`AtomicReference` 或者实例字段，别去绕编译器。循环变量最容易踩这个坑。名义上是 final，实质上是不可变引用，理解这一点比背结论重要。

---

### Q6. Lambda 里的 this 指向谁？和匿名内部类有什么不同？

**口述答案**

Lambda 里的 `this` 指向外围实例，和普通方法里的 `this` 完全一致。匿名内部类里的 `this` 指向内部类对象本身。

原因是 Lambda 不生成独立的方法上下文，它复用外围类的方法，所以没有自己的 `this`。这个差异在注册回调时最明显：用 Lambda 写监听器，`this` 拿到的是当前业务对象。用匿名内部类，得写 `Outer.this` 才能拿到外层对象。记这一条最实用的方式，Lambda 没有自己的作用域，匿名内部类有。写事件回调时如果两种写法混用，调试很容易被 this 绕晕。

---

### Q7. Java 内置的四大函数式接口分别是什么？

**口述答案**

`java.util.function` 里有四个基础接口：

- `Function<T, R>`：输入 T 输出 R，核心方法是 `apply`
- `Predicate<T>`：输入 T 输出 boolean，核心方法是 `test`
- `Consumer<T>`：输入 T 无返回值，核心方法是 `accept`
- `Supplier<T>`：无输入输出 T，核心方法是 `get`

此外还有 `BiFunction`、`UnaryOperator`、`BinaryOperator` 等扩展，以及 `IntFunction` 这类原始类型特化版本，用来避免装箱开销。选型时先看输入输出形态，再看是否需要原始类型特化。

---

### Q8. 方法引用有哪几种形式？

**口述答案**

方法引用是 Lambda 的简写，只有 Lambda 体是单纯调用一个已有方法、没有额外逻辑时才能用。四种形式：

- 静态方法引用：`Integer::parseInt`
- 实例方法引用：`str::length`
- 特定类型的任意实例：`String::length`，第一个参数作为接收者
- 构造器引用：`ArrayList::new`

数组构造器也能引用，比如 `String[]::new`，接收长度返回数组，在 `Stream.toArray` 里最常见。四种形式记不住时，先看方法是不是静态的、第一个参数是不是接收者，基本能判断出来。

---

### Q9. 构造器引用和数组构造器引用怎么用？

**口述答案**

构造器引用写成 `Class::new`，编译器按目标类型匹配对应的构造器，所以同一个类可以写出不同参数个数的引用。

数组构造器写成 `String[]::new`，它接收一个 int 参数返回数组，典型场景是 `stream.toArray(String[]::new)`。边界是无参构造和有参构造同时存在时，靠目标函数的参数列表来区分，推断不出来就编译失败，这时要显式写成 Lambda 或者加类型转换。数组引用在集合转数组时最常用，省掉手动 new 和一次拷贝。多维数组要写成 `String[][]::new`，参数是最外层长度。

---

### Q10. 方法引用和 Lambda 怎么选？

**口述答案**

优先用方法引用，它更短，方法名本身就说明了意图，可读性更好。

但只有 Lambda 体是单纯的方法调用时才能替换，一旦有额外逻辑，比如取反、拼接、判空，就必须用 Lambda。另外方法引用在重载场景下可能产生歧义，编译器无法确定指向哪个重载时，也要退回 Lambda 或者加显式类型。判断标准很简单：能一眼看出调的是哪个方法就用引用，看不出就用 Lambda。团队里统一风格比个人偏好重要。另外方法引用对调试不太友好，断点常常停在合成方法上，这一点要提前知道。风格统一以后，代码 review 也更快。

---

### Q11. Lambda 底层是怎么实现的？

**口述答案**

Lambda 编译后不生成独立的 class 文件，而是编译成 `invokedynamic` 指令，同时在类里记录一条 `BootstrapMethods` 表。

运行时第一次执行到这条指令，JVM 调用 `LambdaMetafactory.metafactory`，动态生成一个实现目标函数式接口的类，把 Lambda 体链接成方法句柄。之后调用都走生成的类，JIT 可以把 Lambda 体内联进调用方。所以 Lambda 不是匿名内部类的语法糖，两者的字节码形态完全不同，这也是它不需要单独 class 文件的原因。

---

### Q12. Lambda 的性能怎么样？

**口述答案**

首次调用有链接开销，要生成类、绑定方法句柄，所以启动阶段比匿名内部类略慢。

但生成之后调用路径很短，JIT 能把 Lambda 体内联进调用方，热点路径上通常比匿名内部类更快，因为后者多一层对象创建和虚方法调用。冷启动敏感的脚本场景可以权衡用匿名内部类，常规业务代码不用纠结这点差异。真正影响性能的是装箱次数和流的中间操作数量，不是 Lambda 语法本身，压测时先看这两项。冷启动敏感的场景可以预热，避免首请求抖动，预热成本摊到长期运行可以忽略，不必为这点开销换写法。

---

### Q13. 为什么 Lambda 不能访问非 final 的局部变量？从字节码角度说说。

**口述答案**

从字节码看，Lambda 体被编译成外围类的一个私有方法，捕获的局部变量作为参数传进去，所以捕获的其实是值拷贝。

如果允许变量后续修改，拷贝和原变量就不一致，Lambda 执行时看到的是旧值，语义会变得不可预期。用参数传递还意味着 Lambda 不能修改外部局部变量，这是语言层面的设计取舍。需要共享可变状态就用数组、`AtomicReference` 或者实例字段，它们的引用不变，内容可以改。所以它天然不支持修改变量，是值传递的直接结果。字节码里能看到捕获变量作为合成方法的入参。

---

### Q14. Lambda 和 Stream 怎么配合使用？

**口述答案**

核心是把行为参数化传给 Stream：`filter` 收 `Predicate`，`map` 收 `Function`，`forEach` 收 `Consumer`，`reduce` 收 `BinaryOperator`，`collect` 收 `Collector`。

比如从订单列表里筛出金额大于一百的，取商品名收集成 `List<String>`，一行就能写完。边界是每个 Lambda 只做一件事，链太长要拆成方法，不然调试和阅读都很难受。另外流只能消费一次，复用会抛 `IllegalStateException`，记住每个中间操作都返回新流，原流不变。

---

### Q15. Stream 的惰性求值是什么意思？

**口述答案**

中间操作是惰性的，`filter`、`map`、`sorted` 只是记录操作，不执行，直到遇到终端操作比如 `collect`、`forEach`、`count` 才真正跑一遍。

这个设计的收益是短路，比如 `findFirst` 配合 `filter`，找到第一个就停，不会处理全部元素。副作用是调试时看不到中间结果，要用 `peek` 或者拆开写。判断有没有终端操作，是排查流不执行的第一反应。另外 `sorted` 这类有状态操作会缓冲全部元素，惰性不代表免费。异常也只在终端操作时抛出，堆栈位置和预期不一致。理解这一点，才能解释流的执行时机。

---

### Q16. 并行流有什么坑？

**口述答案**

并行流底层用 `ForkJoinPool.commonPool`，默认线程数是 CPU 核数减一。

它适合计算密集、数据量大、无状态的操作，比如大批量数值计算。不适合 IO 密集，因为线程会被阻塞。也不适合有顺序依赖或者共享可变状态的操作，比如在 `forEach` 里往 `ArrayList` 加元素，会出现线程安全问题。commonPool 被阻塞会影响全局，IO 任务建议自己建 `ForkJoinPool`。并行度也不是越高越好，还要看数据分区是否均匀。收益要用压测验证，凭感觉切换经常是负优化。

---

### Q17. 什么时候需要自定义函数式接口？

**口述答案**

内置接口覆盖不了时才自定义，典型场景是需要抛受检异常，或者参数超过三个。

定义时只保留一个抽象方法，加 `@FunctionalInterface` 让编译器校验，参数名起得能自解释，比如用 `Order` 而不是 `T`。如果只是参数个数多，优先用 `BiFunction` 加柯里化，或者传一个上下文对象，别为了省事造一堆只用一次的接口。自定义接口要放在业务包里统一管理，命名按动作来，比如 `OrderHandler`，否则半年后没人记得它为什么存在。接口一旦公开就当成 API 维护，语义变更要谨慎。命名和语义稳定比数量重要。

---

### Q18. Lambda 里怎么处理受检异常？

**口述答案**

函数式接口的抽象方法没有声明 `throws`，所以 Lambda 里不能直接抛受检异常。三种处理方式：

- 在 Lambda 体内 `try-catch`，转成 `RuntimeException` 或业务异常
- 自定义一个带 `throws` 的函数式接口，比如 `ThrowingFunction`
- 用包装方法把受检异常转成非受检，统一在边界处理

推荐前两种，别用 sneaky throw 绕过编译器，那会让调用方失去异常声明。包装异常时保留原始 cause，日志里才能看到根因，统一异常处理层只处理转换后的业务异常。异常信息里保留业务上下文，方便定位。

---

### Q19. Lambda 在框架里有哪些典型应用？

**口述答案**

Lambda 在框架里到处都是，常见的落点有五个：

- 线程池提交任务用 `Runnable` 或 `Callable`
- 集合排序用 `Comparator.comparing`
- Spring 的 `JdbcTemplate` 用 `RowMapper` 把结果集转对象
- Spring Boot 启动时用 `ApplicationRunner`
- `CompletableFuture` 的 `thenApply`、`thenCompose`

理解目标类型，读这些 API 的签名会快很多。面试里被问到框架原理时，能指出某个参数是函数式接口，往往就是加分项。

---

### Q20. 使用 Lambda 有哪些常见坑？

**口述答案**

几个高频坑：

- 重载歧义，两个重载都接受函数式接口时编译器推断不出来，要显式强转
- 变量捕获要求 effectively final，循环里改计数器会编译失败
- Lambda 里的 `this` 指向外围实例，容易拿错对象
- 递归 Lambda 需要借助数组或 `AtomicReference` 持有自身引用
- 并行流里改共享集合会有线程安全问题

写之前先确认目标类型，大部分坑都能提前避开。另外 Lambda 的异常栈会显示合成方法名，排查时要看 cause 和行号，别被方法名带偏。把这几条写成 review 清单，比事后排查省时间。
