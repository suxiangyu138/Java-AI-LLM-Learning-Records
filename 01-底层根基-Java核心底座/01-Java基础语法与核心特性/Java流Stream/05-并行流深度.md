## 1. 并行流机制

> **背景**：并行流把流分成多个分片（Spliterator），在多个线程上并行处理，最后合并结果。
> **目的**：理解并行流的底层（commonPool）与使用前提。
> **适用范围**：数据量大 + 无状态 + 计算密集的场景。
> **不适用场景**：小数据/有状态/顺序敏感/IO 密集。

```text
并行流机制
├── ① 创建：list.parallelStream() 或 stream().parallel()
├── ② 分片：Spliterator 把数据拆成多段
├── ③ 执行：ForkJoinPool.commonPool()（全局共享！）
│   ├── 线程数：availableProcessors() - 1
│   └── ⚠️ 全局共享：一个任务阻塞 → 影响所有并行流
├── ④ 合并：combiner 合并分片结果
└── ⑤ 关键：collector 的 combiner 必须满足结合律

并行化条件（Spliterator）
├── ① 数据可拆分（List/数组易拆；链表难拆）
├── ② 元素处理无状态（不共享可变状态）
└── ③ 结果可合并（collector 结合律）
```

## 2. 实测性能数据

> 📊 实测（千万级数据，2026 测试）：

| 场景 | 串行 | 并行 | 加速比 |
|------|:---:|:---:|:---:|
| 随机数求和（千万） | 78ms | 23ms | **3.4x** |
| 数值求和 | - | - | 2.64x |
| 对象排序 | - | - | 2.30x |
| **字符串拼接** | 63ms | 152ms | **0.41x（变慢！）** |
| CPU 密集（重计算） | - | - | 3-5x |
| **IO 密集（数据库/HTTP）** | - | - | **收益甚微/更慢** |

```text
数据解读
├── ① 计算密集：并行收益明显（3-5 倍）
├── ② 轻量操作（拼接）：并行反而慢（拆分合并开销）
├── ③ IO 密集：阻塞线程 → 拖垮公共池 → 更慢
└── ④ 金句：并行不是「开了就快」——取决于任务性质
```

## 3. 适用场景判断

### 3.1 适用三条件

```text
并行流适用三条件（缺一不用）
├── ① 数据量大：十万级以上
│   ├── 小数据：拆分合并开销 > 收益
│   └── 经验分界：<1000 串行 / 1000-10万 串行 / >10万 评估并行
├── ② 每个元素处理独立（无状态）
│   ├── 不修改共享变量
│   └── 元素间无依赖
└── ③ 计算密集或操作耗时
    ├── 每个元素重计算（如 Math.sqrt 循环 200 次+）
    └── 纯 CPU 任务（无 IO 阻塞）
```

### 3.2 适用示例

```java
// ✅ 适用：计算密集型（每元素重计算）
List<Double> results = data.parallelStream()
    .map(x -> heavyComputation(x))   // 每元素耗时计算
    .toList();

// ✅ 适用：大量数据转换（无状态）
List<String> processed = bigList.parallelStream()
    .filter(x -> x != null)
    .map(String::trim)
    .toList();

// ✅ 适用：并行聚合（reduce 三参数/collect 并发）
long sum = bigList.parallelStream()
    .mapToLong(x -> x)
    .sum();                          // 原始流聚合安全

// ✅ 适用：并行去重收集（线程安全收集器）
Set<String> unique = bigList.parallelStream()
    .collect(Collectors.toConcurrentSet());   // 并发收集器
```

## 4. 不适用场景

### 4.1 禁用清单

```text
并行流禁用场景（⚠️）
├── ① 小数据量：拆分开销 > 收益（< 万级慎用）
├── ② 有状态操作：共享可变变量
│   ├── ❌ 并行 forEach 修改外部 List
│   └── ❌ 并行累加非线程安全计数器
├── ③ 顺序敏感：findFirst/sorted（并行反而慢）
├── ④ IO 密集：数据库/HTTP/文件
│   ├── 阻塞 commonPool 线程
│   └── 实测慢 3 倍（阻塞 + 排队）
├── ⑤ JDBC 查询：Connection 非线程安全
├── ⑥ 无限流：parallel 无限流 = CPU 飙升/OOM
└── ⑦ 共享资源：写入同一文件/连接池
```

### 4.2 不适用示例

```java
// ❌ 错误 1：并行修改共享 List
List<String> result = new ArrayList<>();
list.parallelStream()
    .forEach(s -> result.add(s));   // 线程不安全！ArrayIndexOutOfBounds
// ✅ 正确：用 collect（线程安全收集）
List<String> result = list.parallelStream()
    .collect(Collectors.toList());

// ❌ 错误 2：并行查数据库
orders.parallelStream()
    .forEach(o -> dao.query(o));    // 阻塞 + JDBC 非线程安全
// ✅ 正确：虚拟线程（见第 7 节）

// ❌ 错误 3：并行无限流
Stream.iterate(0, i -> i + 1).parallel().limit(100);
// 无限流的 parallel 拆分问题——CPU 飙升
```

## 5. 并行流陷阱

| # | 陷阱 | 表现 | 解法 |
|---|------|------|------|
| 1 | **共享 List 添加** | AIOOBE/数据丢失 | collect/toConcurrentMap |
| 2 | **非线程安全累加** | 结果错误 | 原始流 sum/原子类 |
| 3 | **findFirst 变慢** | 顺序敏感 | 用 findAny（非顺序场景） |
| 4 | **IO 阻塞公共池** | 全局卡顿 | 虚拟线程/自定义池 |
| 5 | **无限流 parallel** | CPU 飙升/OOM | 先 limit 再并行 |
| 6 | **系统属性改 commonPool** | 影响全局 | **禁止生产设置** |
| 7 | **forEach 顺序不确定** | 输出乱序 | forEachOrdered（牺牲性能） |
| 8 | **collect 结合律错误** | 并行结果错误 | 自定义 collector 满足结合律 |

> ⚠️ **禁止**：`System.setProperty("java.util.concurrent.ForkJoinPool.common.parallelism", "8")`——修改整个 JVM 的公共池行为，影响无关代码。

## 6. 自定义线程池

### 6.1 为什么需要自定义池

```text
commonPool 的问题
├── ① 全局共享：所有并行流共用（互相影响）
├── ② 一个阻塞任务 → 拖垮全部
└── ③ 无法控制线程数/隔离

自定义线程池（生产推荐）
├── ① 隔离：独立池（不干扰其他并行流）
├── ② 可控：线程数/命名/拒绝策略
├── ③ 监控：池指标可观测
```

### 6.2 实现方式

```java
// 方案：ForkJoinPool 执行并行流（避免 commonPool）
ForkJoinPool pool = new ForkJoinPool(4);   // 独立池（4 线程）

try {
    List<String> result = pool.submit(() ->
        list.parallelStream()
            .map(...)
            .toList()
    ).get();
} finally {
    pool.shutdown();
}

// 或 Spring 注入（生命周期管理）
@Bean
public ForkJoinPool parallelPool() {
    return new ForkJoinPool(
        Runtime.getRuntime().availableProcessors() / 2,
        ForkJoinPool.defaultForkJoinWorkerThreadFactory,
        null, false
    );
}
// ⚠️ 注意：并行流默认仍用 commonPool——
// 需在池的 submit 中执行才用自定义池
```

## 7. 并行流 vs 虚拟线程

### 7.1 解决不同问题

| 维度 | 并行流 | 虚拟线程（Java 21+） |
|------|:---:|:---:|
| 问题 | **数据并行** | **大量阻塞（IO）** |
| 场景 | 重计算压榨多核 | HTTP/DB/文件吞吐 |
| 线程数 | CPU 核数 - 1 | 数十万虚拟线程 |
| 阻塞影响 | ⚠️ 阻塞浪费线程 | ✅ 阻塞不占资源 |
| 适用 | 纯计算 | IO 密集 |

```text
实测对比（同等阻塞任务）
├── 固定 100 线程池：约 5 秒
├── 虚拟线程：约 0.6 秒（8 倍+）
└── 结论：IO 场景 → 虚拟线程；计算场景 → 并行流
```

### 7.2 虚拟线程示例（IO 场景）

```java
// IO 密集：用虚拟线程（不用并行流！）
List<Order> result = orders.stream()
    .map(Order::getId)
    .map(id -> Thread.ofVirtual().start(() -> dao.query(id)))  // 每任务虚拟线程
    .map(Thread::join)
    .toList();

// 或 Executors.newVirtualThreadPerTaskExecutor()
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Order>> futures = orders.stream()
        .map(o -> executor.submit(() -> dao.query(o.getId())))
        .toList();
    // 收集结果
}
```

> 🎯 **2026 选型**：**IO 密集（HTTP/DB/文件）→ 虚拟线程**；**纯计算/数据密集 → 并行流**——两者解决不同问题，不混用。

## 8. 决策流程

```text
是否使用并行流（决策树）
开始
 ├─ 数据量 > 10 万？
 │   └─ 否 → 串行（并行无收益）
 │
 ├─ 每个元素处理独立（无状态）？
 │   └─ 否 → 串行（有状态并行危险）
 │
 ├─ 计算密集（非 IO 阻塞）？
 │   ├─ 否（IO 密集）→ 虚拟线程（不是并行流！）
 │   └─ 是 → 下一步
 │
 ├─ 顺序敏感（findFirst 等）？
 │   └─ 是 → 串行或 findAny
 │
 ├─ 结果可合并（collector 结合律）？
 │   └─ 否 → 串行
 │
 └─ 全部满足 → 并行流 + 自定义池（可选）+ JMH 验证
     ├─ 实测加速？→ 保留
     └─ 实测变慢？→ 回串行（数据说话）
→ 金句：并行 = 条件全部满足 + 实测验证——不是默认开启
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 并行流机制：commonPool 全局共享（availableProcessors - 1）——**一个阻塞影响所有**
> 2. 实测数据：计算密集 3-5 倍；字符串拼接反而 0.41 倍——并行不是银弹
> 3. 适用三条件：数据量大（10 万+）+ 无状态 + 计算密集
> 4. 禁用清单：小数据/有状态/顺序敏感/IO 密集/JDBC/无限流
> 5. 并行陷阱：共享 List（用 collect）、findFirst 变慢（findAny）、**禁止改 commonPool 系统属性**
> 6. 自定义池隔离（ForkJoinPool submit）；IO 场景用**虚拟线程**（实测 8 倍+）
> 7. 决策树 + JMH 实测验证——**测量而非直觉**
