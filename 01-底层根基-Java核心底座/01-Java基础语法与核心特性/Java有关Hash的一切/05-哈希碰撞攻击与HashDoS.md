## 1. 碰撞为什么不可避免

### 1.1 鸽巢原理

```
Java hashCode 返回 int：2^32 ≈ 42.9 亿种取值
可能的 key（如 String）：无限多
→ 必然存在多个 key 映射到同一哈希值（碰撞）
```

### 1.2 生日悖论：碰撞比想象中来得早

随机选 n 个元素，出现碰撞的概率超过 50% 需要的元素数约为：

```
k ≈ 1.18 × √(2^32) ≈ 68,000  个不同 key 即有一半概率发生碰撞
```

> 💡 **工程含义**：6.8 万个 key 就可能碰到碰撞——所以"碰撞只是理论问题"是错的，它是日常就要面对的工程问题。不过普通业务 key 的碰撞是"均匀分散"的，对性能影响可忽略；攻击者要做的是**定向制造海量同桶 key**。

### 1.3 碰撞的两种形态

| 形态 | 发生方式 | 危害 |
|------|---------|------|
| 自然碰撞 | 随机 key 偶发 | 链表略长，性能影响微小 |
| 定向碰撞 | 攻击者构造 hashCode 相同的 key 集合 | 单桶链表爆长 → O(n)，可拖垮服务 |

## 2. HashDoS 攻击原理

### 2.1 攻击模型

```
攻击流程：
1. 找到目标语言的哈希弱点（如 Java String.hashCode 是公开公式）
2. 离线构造大量"哈希相同但内容不同"的 key
   String.hashCode = Σ s[i]*31^(n-i-1) → 反向工程可批量生成碰撞串
3. 把 key 塞进请求（HTTP POST 参数、JSON 字段名、Cookie）
4. 服务端自动绑定到 HashMap/Hashtable → 全部落进同一桶
5. 插入/查找从 O(1) 退化为 O(n) → CPU 100%、请求超时 → DoS
```

### 2.2 为什么"合法请求"就能打垮服务

- 攻击载荷是**语法完全合法**的普通参数，能通过所有常规校验（长度、格式）
- 服务端框架自动把请求参数转成 `Map<String, String>`（如 `@RequestParam Map`）
- 每个桶一条长链表，插入第 n 个元素要遍历 n 次 → n 个参数耗时 O(n²)
- 一台攻击机发几千请求即可占满单核 CPU

```
JDK 7 时代最坏情况：
单桶链表 10 万个节点 → 每次插入 10 万次 equals 比较
攻击者 2000 个请求 × 每个 1000 个碰撞参数 = 4 亿次比较
→ 单核 CPU 直接打满，服务雪崩
```

## 3. 真实攻击史：28C3 与影响面

### 3.1 时间线

| 时间 | 事件 |
|------|------|
| 2003 | Crosby & Wallach（USENIX 论文）首次系统阐述哈希碰撞 DoS |
| 2011-12 | 28C3 安全大会公开演示：对 Java、PHP、ASP.NET、Python、Ruby 的实战攻击 |
| 2012-2013 | 各语言生态集中修复（Java 7u40+、PHP 5.3.9+、Python 3.3+ 等） |

### 3.2 受影响面

| 语言/框架 | 典型场景 | 后果 |
|-----------|---------|------|
| Java（JDK 7 及以下） | 请求参数 Map、JSON 解析 | 链表 O(n)，最脆弱 |
| PHP | 表单数组参数 | 哈希表退化为链式 |
| ASP.NET | ViewState、参数 | 拒绝服务 |
| Python | dict | 哈希种子固定时可预计算 |

> ⚠️ **历史教训**：当年 Tomcat、Jetty 等中间件都中招——攻击面是"任何把不可信输入变成 Map key"的入口，而不仅仅是业务代码。

## 4. JDK 内置防御机制

### 4.1 第一道防线：JDK 8 红黑树化

```
链表长度 ≥ 8 且 容量 ≥ 64 → 转红黑树
最坏查找从 O(n) 降为 O(log n)
```

| 数据规模 | JDK 7 最坏耗时 | JDK 8 树化后 |
|----------|---------------|-------------|
| 1 万碰撞 key | ~10⁷ 次比较 | ~10⁴ 次 |
| 10 万碰撞 key | ~10¹⁰ 次比较 | ~10⁵ 次 |
| 100 万碰撞 key | ~10¹² 次（瘫痪） | ~10⁶ 次（仍吃 CPU） |

### 4.2 第二道防线：随机化种子

| 版本 | 机制 |
|------|------|
| JDK 7u40+（OpenJDK） | `-Djdk.map.althashing.threshold=512`：超过阈值改用**随机化备选哈希**，攻击者无法预计算碰撞集 |
| JDK 8u20+ | String 相关哈希种子在 JVM 启动时随机化（`String.hash32()`），碰撞集每次启动都失效 |
| JDK 8+ 通用 | 树化是主要防御，随机化作为补充 |

> 💡 **随机化的意义**：攻击者预计算碰撞集需要知道种子；种子随机后，**针对本轮 JVM 预计算的成本高到不可行**，且服务重启即失效。

### 4.3 容器层基础配置

```bash
# 容器内随机源不足会拖慢 JVM 启动（随机种子初始化阻塞）
java -Djava.security.egd=file:/dev/./urandom -jar app.jar
```

## 5. 剩余风险与攻击窗口

即使 JDK 8+，仍有窗口可打：

| 风险点 | 说明 |
|--------|------|
| 树化前窗口 | 链表 1-7 个时仍是 O(n)，洪水请求每次都在重建链表 |
| 容量 < 64 不树化 | 初始容量故意设小（如 16）时，攻击可让桶长期在"扩容-重建"循环中烧 CPU |
| 树构建成本 | 链表→树转换本身 O(n log n)，反复触发也耗 CPU |
| 红黑树仍非恒时 | 最坏 O(log n) 对超大输入仍可能被刷爆 |
| 其他哈希结构 | 非 HashMap 场景（HashSet、框架自带哈希表）不一定有树化兜底 |

> 🎯 **结论**：JDK 8+ 只是把攻击成本提高了几个数量级，**不是免疫**。真实生产必须叠加应用层防御。

## 6. 2026 分层防御最佳实践

### 6.1 防御总览（纵深防御）

```
第 1 层  运行时/JVM：JDK 8u20+、不设过小初始容量、随机源就绪
第 2 层  输入层：限制参数数量/长度、白名单字符集
第 3 层  框架层：不用 Map 接用户输入，用 DTO + 校验
第 4 层  边缘层：限流、WAF、参数数上限
第 5 层  可观测：桶分布监控、告警
```

### 6.2 各层落地清单

```yaml
# 第 2 层：输入层
- 限制请求参数数量（如 > 100 个参数 → 400）
- 限制 key 长度（如 ≤ 32 字符）
- key 字符集白名单（拒绝超长随机串）

# 第 3 层：框架层（重点！）
- ❌ @RequestParam Map<String,String> params   # 用户可控 key 直进 HashMap
- ✅ @RequestParam UserDTO user                 # 显式 DTO，字段固定、类型校验
- ❌ @RequestBody Map<String,Object>            # JSON 字段名直进 HashMap
- ✅ @RequestBody OrderDTO order                # 结构绑定 + Bean Validation

# 第 4 层：边缘层（Tomcat/网关）
- maxParameterCount=1000（Tomcat 连接器）
- maxPostSize 限制请求体
- 每 IP/Token 限流；WAF 识别碰撞模式

# 第 5 层：可观测
- 通过 JMX 监控桶链表长度分布
- 告警规则：任一桶持续 > 50 节点 → 熔断/排查
```

### 6.3 自定义类哈希的防御准则

```java
// ✅ 安全：组合不可变字段（Objects.hash 默认 31 多项式，分布良好）
public record Order(String orderNo, long userId) { }

// ❌ 危险：固定值、基于可预测序号、基于公开小值域
//   例：hashCode() 返回 1 → 所有元素进同一桶（自残式 HashDoS）
//   例：hashCode() 返回 id % 10 → 攻击者可轻易预测桶位置
```

> 💡 **借他山之石**：Python 3.4+ 用 **SipHash + 进程随机密钥**哈希字符串；Java 主流方案是"树化 + 随机化"，工程上等价——都让攻击者无法预计算。

## 7. 劣质 hashCode 自查与监控

### 7.1 自查清单

| 检查项 | 通过标准 |
|--------|---------|
| equals 与 hashCode 字段一致 | 参与两者计算的是同一组字段 |
| 字段不可变 | 放入集合后字段不会变 |
| 无固定值/小值域 | 分布宽度 ≥ 桶数数量级 |
| 乘数合理 | 31 或类似奇素数 |
| 无装箱热点 | 大数据量用 int 手写 |

### 7.2 简易分布测试

```java
// 用 10 万随机样本验证桶分布（JDK 17+ 可直接跑）
Map<Integer, Integer> bucketCount = new HashMap<>();
for (int i = 0; i < 100_000; i++) {
    int hash = new Key(randomString()).hashCode();
    bucketCount.merge(hash & 63, 1, Integer::sum);   // 64 桶模拟
}
// 期望：每桶约 1562 ± 容差；若个别桶 >> 均值 5 倍以上 → 哈希劣质
```

## 8. 面试高频考点

**Q1: HashDoS 是什么？** 构造大量哈希碰撞的 key（如 String 碰撞串）塞进请求，使服务端 HashMap 单桶链表爆长，插入/查找 O(1)→O(n)，CPU 打满的拒绝服务攻击。

**Q2: Java 怎么防御的？** JDK 8 红黑树化（链表≥8 且容量≥64 → O(log n)）+ 随机化种子（JDK 7u40+ althashing、8u20+ String 哈希种子随机）。

**Q3: 树化就够了吗？** 不够。树化前窗口、容量<64、树构建成本仍可被刷；必须叠加输入层（DTO 而非 Map）、边缘层（限流、maxParameterCount）防御。

**Q4: 为什么 String.hashCode 能批量构造碰撞？** 公式公开且确定：`Σ s[i]*31^(n-i-1)`，可反向工程生成任意数量同哈希字符串。

**Q5: 业务代码如何避免成为攻击面？** 不用 `Map` 接用户输入、限制参数数与 key 长度、自定义类用 Objects.hash 组合不可变字段。

---

> 🎯 **核心要点**：哈希碰撞是数学必然，HashDoS 是把它武器化。Java 的答案 = 树化兜底（成本上移）+ 随机化（预测失效）+ 应用层纵深防御（入口封堵）。三者缺一不可。
