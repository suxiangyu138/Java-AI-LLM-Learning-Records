## 1. 哈希的三重身份

| 类型 | 代表 | 设计目标 | 是否抗碰撞 | 用途 |
|------|------|---------|:---:|------|
| 非加密哈希 | Murmur3、xxHash | **快**、分布均匀 | 否（可预测） | 哈希表、分片、布隆过滤器 |
| 加密哈希 | SHA-256、SHA-3 | **不可逆**、强抗碰撞 | 是 | 数据完整性、数字签名 |
| 密码哈希 | Argon2id、bcrypt | **慢**、内存硬、抗 GPU | 是 | 密码存储 |

> 💡 **一句话区分**：哈希表要"快"，完整性要"强"，密码存储要"慢"。把三者混用是绝大多数安全事故的根源。

## 2. MD5 与 SHA 家族的兴衰

### 2.1 安全大事记

| 时间 | 事件 | 影响 |
|------|------|------|
| 2004 | MD5 碰撞被攻破（王晓云等） | MD5 全面淘汰 |
| 2017 | SHA-1 首个公开碰撞（SHAttered，Google） | SHA-1 全面淘汰 |
| 2018 | MD5 选择性前缀攻击（可伪造证书场景） | 任何场景禁用 |
| 2024+ | SHA-256 仍安全，但 SHA-1 已从 TLS 移除 | SHA-256 为当前最低标准 |

### 2.2 家族对比

| 算法 | 输出长度 | 现状 | Java 支持 |
|------|---------|------|-----------|
| MD5 | 128 bit | ❌ 已攻破 | JDK 1.0+（仅兼容遗留） |
| SHA-1 | 160 bit | ❌ 已攻破（2017 SHAttered） | JDK 1.0+ |
| SHA-256 / 512 | 256 / 512 bit | ✅ 安全，完整性校验标准 | JDK 1.4+ |
| SHA-3（Keccak） | 224/256/384/512 | ✅ 新一代标准（NIST 2015） | JDK 9+ |
| SHA-512/256 | 256 bit | ✅ 64 位平台优化 | JDK 9+ |

> ⚠️ **代码层面**：即使"只是做文件校验"，新代码也不应再写 `MessageDigest.getInstance("MD5")`——校验场景的碰撞同样可被利用（伪造文件）。一律 SHA-256 起步。

## 3. MessageDigest：Java 摘要 API

### 3.1 标准用法（JDK 17+ 含 HexFormat）

```java
// 计算字符串的 SHA-256 摘要
MessageDigest md = MessageDigest.getInstance("SHA-256");
byte[] digest = md.digest("hello".getBytes(StandardCharsets.UTF_8));

// JDK 17+：HexFormat 十六进制转换（告别手写 StringBuilder）
String hex = HexFormat.of().formatHex(digest);
// 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824

// 大文件分块更新（避免一次性加载整个文件）
MessageDigest md2 = MessageDigest.getInstance("SHA-256");
try (InputStream in = Files.newInputStream(path)) {
    byte[] buf = new byte[8192];
    int n;
    while ((n = in.read(buf)) > 0) md2.update(buf, 0, n);
}
byte[] fileDigest = md2.digest();
```

### 3.2 支持算法速查

```java
MessageDigest.getInstance("SHA-256");    // ✅ 首选
MessageDigest.getInstance("SHA3-256");   // ✅ SHA-3（JDK 9+）
MessageDigest.getInstance("MD5");        // ❌ 仅遗留兼容
MessageDigest.getInstance("SHA-1");      // ❌ 仅遗留兼容
```

## 4. HMAC：带密钥的消息认证

### 4.1 为什么需要 HMAC

```
普通哈希（SHA-256）：谁都能算 → 无法证明"消息确实来自对方"
HMAC = Hash(密钥 ∥ 消息)  ：只有持密钥者能算 → 可认证来源 + 防篡改
```

### 4.2 Java 实现

```java
// 密钥生成（HS256 用 32 字节密钥）
SecretKey key = new SecretKeySpec(secretKeyBytes, "HmacSHA256");

// 计算 HMAC
Mac mac = Mac.getInstance("HmacSHA256");
mac.init(key);
byte[] sig = mac.doFinal(payload.getBytes(StandardCharsets.UTF_8));

// 校验：重新计算后恒定时间比较（见第 7 节）
```

### 4.3 典型场景

| 场景 | 说明 |
|------|------|
| API 签名 | 请求参数 + 时间戳 → HMAC-SHA256，防篡改防重放 |
| JWT | HS256 签名即 HMAC-SHA256（对称密钥） |
| Webhook 回调 | 平台回调验签，防伪造事件 |
| 双因子挑战应答 | 服务端下发随机挑战，客户端用共享密钥应答 |

## 5. 密码哈希：为什么必须"慢"

### 5.1 快哈希存密码 = 裸奔

```
SHA-256 每秒可算 数十亿次（GPU 集群每秒 220 亿次 MD5）
→ 8 位弱口令暴力破解只需几小时
→ 即使加盐（防彩虹表），单次猜测成本依然极低

结论：密码哈希的"快"恰恰是致命弱点——攻击者暴力破解的速度 = 哈希速度
```

### 5.2 三个致命误区

| 误区 | 正确认知 |
|------|---------|
| "MD5 + 加盐就安全" | 盐只防彩虹表，不增加单次猜测成本；MD5 本身已碰撞 |
| "SHA-256 很安全，用来存密码" | SHA-256 本身不弱，但**快**= 破解快；通用哈希 ≠ 密码哈希 |
| "AES 加密存密码" | 可逆方案，拿到密钥即还原明文；密码必须**单向哈希** |

### 5.3 密码哈希的三要素

```
1. 单向：不可逆，无法还原明文
2. 慢：计算参数可调（目标：单次验证 250-500ms）
3. 盐：每用户随机独立盐（16 字节，SecureRandom），防彩虹表 + 防同密码碰撞
```

## 6. Argon2 / bcrypt / PBKDF2 选型

### 6.1 对比总表

| 算法 | 特点 | 内存硬 | Java 方案 | 参数建议（2026） | 适用 |
|------|------|:---:|----------|-----------------|------|
| **Argon2id** | 2015 密码哈希竞赛冠军，OWASP/NIST 首选 | ✅ | Bouncy Castle / argon2-jvm / Spring `Argon2PasswordEncoder` | 内存 ≥ 19 MiB（OWASP），迭代 ≥ 2，并行度 1 | 新项目首选，金融/政务 |
| **bcrypt** | 成熟通用，内置盐 | ❌ | jBCrypt / Spring `BCryptPasswordEncoder` | **cost ≥ 12**（12 ≈ 400ms） | 存量项目主流 |
| **PBKDF2** | JDK 原生（FIPS 合规） | ❌ | `SecretKeyFactory` + `PBKDF2WithHmacSHA256` | **迭代 ≥ 600,000**（NIST SP 800-132） | 强合规（FIPS 140-2）场景 |

### 6.2 Spring Security 实战

```java
// ⭐ 首选：Argon2id（新项目）
PasswordEncoder encoder = Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8();
// 默认参数：内存 16KB? 不——defaultsForSpringSecurity 提供 1.5MB/2 轮；
// 生产建议调大：new Argon2PasswordEncoder(16, 32, 1, 65536, 3)（64MB/3轮）

String hash = encoder.encode("userPassword");
encoder.matches("userPassword", hash);     // true
encoder.matches("wrong", hash);            // false

// 存量项目：bcrypt（cost 12 起）
BCryptPasswordEncoder bcrypt = new BCryptPasswordEncoder(12);
String hash = bcrypt.encode("userPassword");

// 合规场景：PBKDF2（JDK 原生，无第三方依赖）
SecretKeyFactory f = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256");
KeySpec spec = new PBEKeySpec("pwd".toCharArray(),
        salt /*16字节 SecureRandom*/, 600_000 /*迭代*/, 256);
byte[] hash = f.generateSecret(spec).getEncoded();
```

### 6.3 生命周期管理（2026 最佳实践）

| 实践 | 说明 |
|------|------|
| 新密码一律新算法 | 新注册/改密走 Argon2id |
| 懒迁移（Lazy Migration） | 登录成功时检测算法版本，旧算法自动升级重哈希入库，无需强制改密 |
| 参数定期上调 | 每 1-2 年评估：验证耗时目标 250-500ms |
| 限制登录尝试 | 防在线爆破（与哈希算法无关但必须做） |

## 7. 完整性校验与恒定时间比较

### 7.1 使用场景

| 场景 | 做法 |
|------|------|
| 文件下载校验 | 服务端发布 SHA-256 摘要，客户端比对 |
| 分片上传 | 每片 SHA-256，最后合并校验 |
| 日志防篡改 | 链式哈希（每行含上一行摘要） |
| 比对哈希/签名 | **恒定时间比较，禁止 == / Arrays.equals** |

### 7.2 为什么不能用 == 比较

```java
// ❌ 危险：逐字节比较遇到第一个不同就返回 false
//   攻击者可通过响应时间差推断摘要前几个字节 → 逐字节猜出签名
if (Arrays.equals(digestA, digestB)) { ... }

// ✅ 恒定时间：无论结果如何，耗时相同（JDK 8+ 保证）
if (MessageDigest.isEqual(digestA, digestB)) { ... }
```

> 🎯 **计时攻击**：哈希比较的时间与"首个不同字节的位置"相关，这个信息泄漏可被用于逐步逼近摘要。`MessageDigest.isEqual` 内部始终遍历全部字节，时间是常数。

## 8. 面试高频考点

**Q1: 密码为什么不能用 MD5/SHA-256 存？** 通用哈希设计目标是快——GPU 每秒数十亿次，暴力破解成本极低；加盐只防彩虹表不增加猜测成本。密码哈希必须慢（Argon2id/bcrypt/PBKDF2）。

**Q2: 三类哈希怎么区分？** 非加密（Murmur3，快）→ 哈希表/分片；加密（SHA-256，强抗碰撞）→ 完整性/签名；密码（Argon2id，慢+内存硬）→ 密码存储。

**Q3: 加盐的作用？** 防彩虹表、防相同密码相同哈希；盐必须每用户随机独立（SecureRandom 16 字节），禁止固定盐。

**Q4: Argon2 vs bcrypt vs PBKDF2？** Argon2id 内存硬抗 GPU，OWASP 首选（新项目）；bcrypt 成熟内置盐，cost≥12（存量）；PBKDF2 JDK 原生，迭代≥60 万（合规）。

**Q5: 为什么比较哈希要用恒定时间？** 普通 == 的耗时泄漏"首个不同字节位置"，可被计时攻击逐步还原摘要；MessageDigest.isEqual 恒定时间。

**Q6: HMAC 和 SHA-256 区别？** HMAC = 密钥参与的哈希，可认证来源与完整性；SHA-256 无密钥，只能校验内容未被改。

---

> 🎯 **核心要点**：三类哈希各司其职——哈希表要快（Murmur3）、完整性要强（SHA-256）、密码要慢（Argon2id）。Java 侧：`MessageDigest` 管摘要、`Mac` 管 HMAC、Spring Security 管密码。选型一句话：**密码 Argon2id/bcrypt，校验 SHA-256，索引分片 Murmur3**。
