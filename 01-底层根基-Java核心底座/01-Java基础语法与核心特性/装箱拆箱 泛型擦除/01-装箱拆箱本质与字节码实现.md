## 1. 从"甜蜜"到"陷阱"：一个经典面试题开场

```java
public class BoxedTrap {
    public static void main(String[] args) {
        Integer a = 100, b = 100;          // 缓存范围内
        Integer c = 1000, d = 1000;        // 缓存范围外
        Integer e = new Integer(100);      // 显式 new：永远新对象

        System.out.println(a == b);        // ① ？
        System.out.println(c == d);        // ② ？
        System.out.println(a.equals(b));   // ③ ？
        System.out.println(e == a);        // ④ ？
    }
}
```

**答案：`true / false / true / false`**——① 命中缓存，② 超出缓存各自 new，③ equals 比较值，④ `new` 强制新对象。

> 🎯 **核心要点**：这个题的全部"反直觉"都来自同一个机制——**自动装箱 = `Integer.valueOf()` 调用**，而 `valueOf` 有缓存。理解字节码后，这四个答案都是必然，不是记忆。

## 2. 自动装箱：valueOf 与缓存池

### 2.1 什么是自动装箱

**自动装箱（autoboxing）**：编译器在需要 `Integer`（引用类型）而代码提供了 `int`（值类型）时，**自动插入 `Integer.valueOf(int)` 调用**。它发生在编译期，JVM 层面根本没有"装箱指令"。

```java
// 源码：你写的
Integer boxed = 42;

// 编译后：等价于
Integer boxed = Integer.valueOf(42);
```

### 2.2 Integer.valueOf 的源码与缓存

```java
// java.lang.Integer（JDK 源码）
@IntrinsicCandidate
public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)   // 默认 [-128, 127]
        return IntegerCache.cache[i + (-IntegerCache.low)];
    return new Integer(i);                                  // 范围外：新建对象
}
```

关键点：

- **默认缓存范围 [-128, 127]**（Java 5 规范承诺的最低保证）；
- **`-XX:AutoBoxCacheMax=N`**（JDK 9+ 正式选项）可扩大 `Integer` 缓存上限（下限 -128 不可变）；
- 缓存数组是**类加载时一次性构建**的，驻留于堆上（老年代），不随 GC 回收；
- `@IntrinsicCandidate`：JIT 可能内联该调用。

### 2.3 为什么要有缓存

| 动机 | 说明 |
|------|------|
| 历史约定 | Java 5 规范要求 -128..127 范围内 `valueOf` 必须返回相同实例（小整数使用频繁） |
| 内存 | 小整数大量复用，避免百万个 1-127 的重复对象 |
| == 语义 | 规范内行为一致；超出范围依赖实现——**这是 == 陷阱的制度性根源** |

> ⚠️ **边界认知**：缓存范围是**实现细节**，只有 -128..127 是规范保证。不要写依赖"缓存外 == 一定 false"的代码——那是实现依赖，不是语言契约。生产代码永远用 `equals`。

## 3. 自动拆箱：intValue 与 NPE 的根源

### 3.1 什么是自动拆箱

**自动拆箱（unboxing）**：需要 `int` 而提供了 `Integer` 时，编译器插入 **`intValue()`** 调用：

```java
// 源码
Integer boxed = 42;
int primitive = boxed;

// 编译后
int primitive = boxed.intValue();
```

### 3.2 拆箱的三种隐蔽触发

```java
Integer boxed = null;

int a = boxed;                 // ① 显式赋值 → NullPointerException
Integer b = boxed + 1;         // ② 运算（+ 要求基本类型）→ NPE
if (boxed > 0) { }             // ③ 比较（> 要求基本类型）→ NPE
if (boxed == 0) { }            // ④ 混合比较：先拆箱再 == → NPE
```

| 场景 | 字节码真相 | 风险 |
|------|-----------|------|
| `int x = Integer` | `invokevirtual Integer.intValue()` | null → **NPE** |
| `Integer + 1` | 先 `intValue()` 再 `iadd` | null → NPE |
| `Integer == 0` | 先 `intValue()` 再 `if_icmpne`（**不是**引用比较！） | null → NPE |
| `Integer == Integer` | `if_acmpne` 引用比较（无拆箱） | 语义陷阱（见 03 章） |

> 💡 **判断口诀**：**== 两端只要有一边是基本类型，就必然拆箱**（混合比较）。两边都是包装类型才走引用比较——这是 03 章所有陷阱的总规则。

## 4. 字节码实证：javap 反编译

```java
public class BoxDemo {
    Integer add(Integer a, Integer b) {
        int sum = a + b;          // 拆箱 + 运算
        return sum;               // 装箱
    }
}
```

```bash
javac BoxDemo.java && javap -c -p BoxDemo
```

```text
public java.lang.Integer add(java.lang.Integer, java.lang.Integer);
  Code:
    0: aload_1
    1: invokevirtual #7   // Method Integer.intValue:()I     ← 拆箱 a
    4: aload_2
    5: invokevirtual #7   // Method Integer.intValue:()I     ← 拆箱 b
    8: iadd                                                    ← 加法
    9: istore_3
   10: iload_3
   11: invokestatic  #13  // Method Integer.valueOf:(I)Ljava/lang/Integer;  ← 装箱
   14: areturn
```

**三个可观察结论**：

1. 装箱 = `invokestatic Integer.valueOf`（静态方法，缓存逻辑在此发生）；
2. 拆箱 = `invokevirtual Integer.intValue`（实例方法，null 时 NPE 在此发生）；
3. **没有任何专用字节码指令**——Java 虚拟机指令集中不存在 "box/unbox" 指令（对比：String 拼接有 `invokedynamic` 专门优化）。

## 5. 触发点全集：哪些写法会装箱

| 触发场景 | 示例 | 装箱？ |
|---------|------|:---:|
| 直接赋值 | `Integer i = 42;` | ✅ |
| 方法传参（形参为包装类型） | `void f(Integer i); f(42);` | ✅ |
| 集合添加 | `list.add(42);` | ✅（List<Integer>） |
| 泛型方法实参 | `box(42)`，`<T> T box(T t)` 且 T=Integer | ✅ |
| 运算结果赋给包装 | `Integer i = 1 + 2;` | ✅（先算后装箱） |
| 三元表达式混合 | `Integer r = flag ? 1 : boxed;` | ✅（类型提升） |
| `switch(包装类型)` | `switch(Integer)` | ✅（自动拆箱） |
| `String.valueOf(包装)` | 无 | ❌ |
| 数组 | `Integer[] arr = {1, 2};` | ✅（**每个元素**装箱） |

> ⚠️ **最容易忽略**：**三元表达式**与 **switch** 的隐式拆箱，以及**数组初始化**的逐元素装箱——这四处是生产代码里装箱频率最高的"隐形热点"。

## 6. 包装类缓存池速查表

| 包装类 | 缓存范围 | 可否调大 | 说明 |
|--------|:---:|:---:|------|
| `Byte` | 全部 (-128..127) | 不需要 | 类型全值域 |
| `Short` | -128..127 | ❌ | 固定 |
| `Integer` | -128..127 | ✅ `-XX:AutoBoxCacheMax=N` | 最常讨论的缓存 |
| `Long` | -128..127 | ❌ | 固定（历史原因未做选项） |
| `Character` | 0..127（ASCII） | ❌ | 128..65535 每次新建 |
| `Boolean` | `TRUE`/`FALSE` 两个单例 | 不需要 | 无范围问题 |
| `Float`/`Double` | **无缓存** | ❌ | 浮点无小整数热点 |

```bash
# 扩大 Integer 缓存到 10000（-XX:AutoBoxCacheMax 是 product 选项，JDK 9+）
java -XX:AutoBoxCacheMax=10000 App
```

> 💡 **实践提示**：`-XX:AutoBoxCacheMax` 极少需要调——缓存数组常驻堆，调太大浪费内存；仅在"业务值域集中在 128..N 且 == 比较成风（不推荐）"的存量代码上作为过渡手段。

## 7. JEP 390：值类型类与 synchronized 警告

### 7.1 背景：包装类终将"无身份"

Project Valhalla 计划把包装类迁移为**值类（value class / primitive class）**——届时实例无身份、无监视器，`synchronized(包装类实例)` 会直接报错。为了让存量代码提前暴露问题，JDK 16 的 **JEP 390** 分三步走：

| 步骤 | 内容 | 版本 |
|------|------|:---:|
| 声明 | 包装类标记为**值类型类（value-based class）**（内部注解 `@jdk.internal.ValueBased`） | JDK 16 |
| 废弃 | 包装类**公开构造器废弃（for removal）**：`new Integer(1)` 产生警告 | JDK 16（JDK 21 警告级别升级） |
| 警告 | synchronized 值类型类实例 → 编译警告 + 运行时诊断 | JDK 16+ |

### 7.2 编译期与运行期警告

```java
// 编译期：javac 默认开启的 -Xlint:synchronization 警告
Integer counter = 0;
synchronized (counter) {        // warning: [synchronization] attempt to synchronize
    counter++;                  // on an instance of a value-based class
}
```

```java
// 运行期：绕过静态类型检查的同步（如 Object 引用持有 Integer）
Object o = Integer.valueOf(1);
synchronized (o) { }            // 编译无警告；运行期由 HotSpot 诊断
// -XX:DiagnoseSyncOnValueBasedClasses=1  → 视为致命错误（fatal error）
// -XX:DiagnoseSyncOnValueBasedClasses=2  → 输出日志 + JFR 事件
```

> 🎯 **核心要点**：**永远不要用包装类（尤其 Integer）做锁对象**——锁的身份语义在 Valhalla 落地后将彻底失效，`counter++` 在 `synchronized(counter)` 里也根本不安全（每次 `++` 都换了一个新 Integer 对象，锁等于没锁）。这是"装箱 + 同步"叠加的双重陷阱。

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 自动装箱 = `Integer.valueOf()`，自动拆箱 = `intValue()`——纯编译器行为，字节码可见、JVM 无专用指令；
> 2. 缓存池默认 -128..127（仅 Integer 可调上限 `-XX:AutoBoxCacheMax`），`==` 行为在缓存内外不一致是陷阱总根源；
> 3. JEP 390（JDK 16）把包装类定为值类型类：构造器废弃、synchronized 警告——为 Valhalla 值类铺路。

**思考题**：

1. `Integer c = 1000, d = 1000; c == d` 为什么是 false？valueOf 里发生了什么？（→ 2.2）
2. `boxed == 0` 和 `boxed == Integer.valueOf(0)` 的字节码差别？（→ 3.2）
3. 为什么说 `synchronized(Integer)` 是双重陷阱？（→ 7.2）
4. `-XX:AutoBoxCacheMax=10000` 后 `Integer.valueOf(5000)` 返回什么？（→ 6）
