# 泛型擦除机制深潜

## 1. 擦除的三步操作

javac 处理泛型时执行且只执行三个动作：

```text
① 替换：把类型参数替换为边界类型（无界 → Object，有界 → 上界）
② 检查：在需要类型转换的位置插入 checkcast 指令
③ 补桥：为保持多态性，生成桥方法（synthetic）
```

```java
// 源码
public class Box<T> {
    private T value;
    public void set(T v) { this.value = v; }
    public T get() { return value; }
}

// 擦除后的等价字节码形态（javap -c 观察）
public class Box {
    private Object value;
    public void set(Object v) { this.value = v; }    // ① T → Object
    public Object get() { return this.value; }
}
// 类文件属性：Signature: <T:Ljava/lang/Object;>Ljava/lang/Object;  ③ 的类型备份
```

> 🎯 **核心要点**：擦除发生在 **javac 阶段**，JVM 拿到的是"无泛型"的类。泛型类型信息只以 Signature 元数据形式保留——**JVM 不校验泛型，只校验擦除后的类型**。

## 2. 擦除规则速查

| 源码类型 | 擦除结果 | 说明 |
|---------|---------|------|
| `T`（无界） | `Object` | 最常见 |
| `T extends Number` | `Number` | 取上界 |
| `T extends Number & Comparable<T>` | `Number` | **取第一个上界**（类必须最前） |
| `T extends Comparable<T> & Serializable` | `Comparable` | 取第一个接口上界 |
| `List<String>` | `List` | 类型实参被丢弃 |
| `List<? extends Number>` | `List` | 通配符实参被整体丢弃（Signature 中记为 `+` 上界）；"通配符擦除为其上界"的规则作用于**类型变量边界**：如 `T extends List<? extends Number>` → T 擦除为 `List` |
| `List<?>` | `List` | 无界通配符 → Object |
| `List<? super Integer>` | `List` | super 通配符 → Object |
| `T[]`（泛型数组） | 擦除后边界类型的数组 | 但**不允许 new T[]**（见 05 章） |

```java
// 嵌套泛型：从外到内逐层擦除
Map<String, List<Integer>> map;   // → Map（运行时）
// Signature 中仍完整保留：Ljava/util/Map<Ljava/lang/String;Ljava/util/List<Ljava/lang/Integer;>;>;
```

## 3. Signature 属性：类文件里的"幽灵类型"

### 3.1 是什么

javac 在类文件里为泛型类/方法/字段额外生成 **Signature 属性**（JVMS §4.7.9.1），保存完整的泛型签名。它：

- **对类型检查透明**：JVM 的验证与执行只看擦除后的类型，Signature 只是"旁注"；
- **对反射可见**：`getGenericXxx()` 系列 API 读取的正是它（06 章）；
- **对工具可见**：IDE、Gson、MyBatis 等通过反射 API 间接使用。

```bash
# javap -v 查看 Signature 属性
javap -v -p Box.class
```

```text
  public T get();
    descriptor: ()Ljava/lang/Object;     ← 擦除后的真正签名（JVM 用它）
    flags: (0x0001) ACC_PUBLIC
    Signature: #12   // ()TT;            ← 泛型签名（javac 备份，工具读它）
```

### 3.2 三种形态的 Signature

| 载体 | Signature 内容 | 反射读取 API |
|------|---------------|-------------|
| 类 | `<T:...>Ljava/lang/Object;` | `getGenericSuperclass()`、`getGenericInterfaces()` |
| 方法 | `(TT;)TT;` | `getGenericReturnType()`、`getGenericParameterTypes()` |
| 字段 | `TT;` | `getGenericType()` |

> 💡 **理解角度**：擦除不是"删除类型信息"，而是"**降级**"——类型信息从"字节码指令语义"降级为"元数据"。JVM 执行路径不看它，反射路径看它。

## 4. checkcast：擦除后的安全执行点

### 4.1 在哪里插入

编译器在**读取泛型值的下游**插入 `checkcast` 指令（类型检查 + 强制转换）：

```java
// 源码
List<String> list = new ArrayList<>();
String s = list.get(0);          // get 返回 Object，赋给 String

// 字节码（javap -c）
invokeinterface List.get:()Object;    // 返回 Object
checkcast java/lang/String             // ← 编译器插入的类型检查
astore_1
```

```java
// 同理：泛型方法返回值
<T> T identity(T t) { return t; }
String x = identity("hello");
// 字节码：invokestatic identity:(Object)Object; checkcast String
```

### 4.2 checkcast 失败 = ClassCastException

```java
// 运行期 ClassCastException 的三条路径
// ① 原生类型混入（无编译检查的入口）
List raw = new ArrayList();
raw.add(42);                       // 编译警告 unchecked，运行时无检查（add 收 Object）
String s = (String) raw.get(0);    // 显式转型 → ClassCastException

// ② 泛型擦除后插的 checkcast
List<String> typed = raw;          // 编译警告
String s = typed.get(0);           // 隐式 checkcast → ClassCastException（编译器插入的）

// ③ 反射/反序列化注入错误类型
```

> 🎯 **核心要点**：擦除后类型安全的执行点就是 checkcast——**安全的粒度是"每次取值时"而非"入集合时"**。集合能混入错误类型（原生类型入口），只是取值时必炸。这也是"堆污染"（05 章）的运行期形态。

## 5. 桥方法：保多态的合成魔法

### 5.1 问题：擦除破坏了方法覆盖

```java
class Box<T> {
    T get() { return null; }                     // 擦除后：Object get()
}
class IntBox extends Box<Integer> {
    @Override
    Integer get() { return 42; }                 // 擦除后：Integer get()
}
// 问题：Object get() 与 Integer get() 签名不同 → 不是覆盖！
// 多态调用 b.get()（静态类型 Box）→ 找不到可覆盖的 Object get() → 编译失败
```

### 5.2 解法：编译器生成桥方法

```java
// javac 自动生成（synthetic + bridge 标志）：
class IntBox extends Box {
    Object get() {            // ← 桥方法：转发到真正的方法
        return this.get();    // 调 Integer get()
    }
    Integer get() { return 42; }    // 业务方法
}
```

```bash
javap -v IntBox
```

```text
  java.lang.Object get();                    ← 桥方法（flags: bridge, synthetic）
    descriptor: ()Ljava/lang/Object;
    flags: ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
    Code:
      0: aload_0
      1: invokevirtual #7 // Method get:()Ljava/lang/Integer;
      4: areturn

  java.lang.Integer get();                   ← 业务方法
    descriptor: ()Ljava/lang/Integer;
    flags: ACC_PUBLIC
```

### 5.3 桥方法的三类触发场景

| 场景 | 例子 | 桥方法形态 |
|------|------|-----------|
| 泛型覆盖（最常见） | `IntBox extends Box<Integer>` | 擦除签名 → 具体签名 |
| 协变返回（非泛型也有） | `class Sub extends Base { @Override String m() }`（Base.m 返回 Object） | Object m() 转发 String m() |
| 泛型 + 协变叠加 | 泛型接口实现 + 具体返回类型 | 同上组合 |

> ⚠️ **桥方法的可见副作用**：反射 `getDeclaredMethods()` 会看到桥方法（`isBridge()` 可判别）；实现 Comparator/Function 等泛型接口时不要被"多了个方法"吓到——那是正常的。

## 6. 泛型方法擦除与重载冲突

### 6.1 擦除签名冲突（编译错误）

```java
// ❌ 编译错误：两个方法擦除后签名相同
void f(List<String> l) {}        // 擦除后 f(List)
void f(List<Integer> l) {}       // 擦除后 f(List) —— 冲突！

// ✅ 不同参数个数/类型（擦除后不同）可以
void g(List<String> l) {}        // g(List)
void g(Set<String> s) {}         // g(Set) —— 可共存
```

| 规则 | 例子 |
|------|------|
| 仅类型实参不同的重载 | `List<String>` vs `List<Integer>` → **非法** |
| 仅通配符不同的重载 | `List<?>` vs `List<Object>` → 非法（擦除相同） |
| 泛型与非泛型共存 | `f(List)` 与 `f(List<String>)` → 非法（擦除后签名相同） |

### 6.2 泛型方法的静态类型（T 推断）

```java
static <T extends Comparable<T>> T max(List<T> list) { ... }
// 擦除后：static Comparable max(List list)
// 调用方获得 Comparable 静态类型 → 需要 checkcast 到具体类型（第 4 节）
```

### 6.3 不能泛型化的构造边界

```java
// 这些在擦除模型下注定不可行（05 章详述）：
// ❌ new T()
// ❌ new T[10]
// ❌ T.class（不能 newInstance）
// ❌ instanceof T
// ❌ 捕获原生异常 T extends Throwable 的 catch(T)
```

## 7. javap 实战：一次完整的反编译对照

```java
// 源码：Box.java
import java.util.List;
public class Box<T extends Number> {
    private T value;
    private List<String> names;

    public void set(T v) { value = v; }
    public <E> E pick(List<E> src, int idx) { return src.get(idx); }
    public T value() { return value; }
}
```

```bash
javac Box.java && javap -v -p Box
```

```text
字段：
  private T value;
    descriptor: Ljava/lang/Number;      ← 擦除为上界
    Signature: #14  // TT;               ← 泛型备份
  private java.util.List<java.lang.String> names;
    descriptor: Ljava/util/List;         ← 擦除为 List
    Signature: #16  // Ljava/util/List<Ljava/lang/String;>;

方法：
  public void set(T);
    descriptor: (Ljava/lang/Number;)V    ← T → Number
    Signature: #18  // (TT;)V
  public <E> E pick(java.util.List<E>, int);
    descriptor: (Ljava/util/List;I)Ljava/lang/Object;   ← E → Object
    Signature: #20  // <E:Ljava/lang/Object;>(Ljava/util/List<TE;>;I)TE;
  public T value();
    descriptor: ()Ljava/lang/Number;     ← T → Number
    Signature: #22  // ()TT;
```

> 💡 **观察结论**：descriptor（JVM 语义）与 Signature（泛型元数据）**成对出现**——前者是运行真相，后者是"历史档案"。任何"运行时能拿到泛型类型"的黑科技（06 章 TypeToken）都是靠 Signature 这条档案链。

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 擦除三步：替换类型参数为边界、插入 checkcast、生成桥方法——全部在 javac 完成，JVM 无泛型概念；
> 2. Signature 属性是被擦除类型的"元数据备份"：执行路径透明、反射路径可见，TypeToken 的原理基础；
> 3. 桥方法由"擦除破坏覆盖关系"催生，本质是编译器用合成转发方法保住多态。

**思考题**：

1. 为什么 `List<String>` 与 `List<Integer>` 不能做重载？（→ 6.1）
2. 从 `List<String>` 里取元素，类型检查发生在哪里？（→ 4.1）
3. 桥方法会被 IDE 显示出来吗？反射能看到吗？（→ 5.3）
4. Signature 属性对 JVM 验证器有什么用？对反射有什么用？（→ 3.1）
