## 1. Valhalla 要解决什么

```text
Java 对象模型的历史折中：
  原始类型（int）    → 快、紧凑、无对象语义
  引用类型（Integer）→ 灵活、有身份、有方法，但 4 倍内存 + 指针追逐

装箱的存在 = 被迫在两者间反复横跳
擦除的存在 = 为二进制兼容牺牲了运行时类型信息
```

**Project Valhalla 的双重目标**：

| 目标 | 内容 | 对应方案 |
|------|------|---------|
| 统一原始类型与类 | 让"int 一样便宜"的用户自定义类型成为可能 | **值类（value classes）**：JEP 401 |
| 让泛型性能追上特化 | 泛型代码（List<T>）获得接近专用实现的性能 | **泛型特化（generic specialization）**：Universal Generics / Parametric JVM |

> 🎯 **核心要点**：Valhalla 不是"消灭 int"，而是"让 `Integer` 获得 int 的性能"——值类实例在堆上、数组里可以**展平（flatten）**，没有对象头、没有指针、没有 GC 逐对象追踪。

## 2. JEP 401：值类（Value Classes）与对象

### 2.1 状态（截至 2026-08）

| 项目 | 状态 |
|------|------|
| JEP 编号 | [JEP 401: Value Classes and Objects (Preview)](https://openjdk.org/jeps/401) |
| 开发分支 | openjdk/valhalla 的 `lworld` 分支 |
| 首个预览并入主线 | **计划 2026-07**（约 19.7 万行的大合并，拆为 JDK-8317277 语言 / 8317278 JVM / 8317279 标准库 三个子 PR） |
| 目标版本 | **JDK 28**（首个预览，非转正） |
| 早期访问 | JDK 26 EA 构建已可试玩 `value class` 语法（`--enable-preview --source 26`） |
| 移植 | x64 先行；PPC64 / RISC-V / s390x 移植进行中（2026 年 6 月冻结前沟通中） |

### 2.2 语法与语义

```java
// 值类：定义（预览语法）
value class Point {
    private final int x;      // 值类字段必须 final
    private final int y;
    // 构造器、方法、接口实现……与普通类一致
    int sum() { return x + y; }
}

// 使用：与普通类完全相同
Point p = new Point(3, 4);
int s = p.sum();
Point[] pts = new Point[100];          // 数组元素可能被展平
```

| 语义 | 值类（value class） | 普通类 |
|------|:---:|:---:|
| 身份（identity） | **无** | 有 |
| `==` 比较 | **值比较**（逐字段） | 引用比较 |
| 可变性 | 不可变（final 字段） | 可变 |
| 监视器（synchronized） | **不支持**（无身份即无锁） | 支持 |
| `System.identityHashCode` | 无意义 | 有 |
| 对象头 | 可省略（展平时） | 必有 |
| 数组存储 | 可内联展平 | 引用 |

> ⚠️ **与 JEP 390 的呼应**：包装类被标记为值类型类、synchronized 警告（JDK 16）、构造器废弃（JDK 16/21）——全部是"值类化"前的**提前预警**。今天收到这些警告的代码，就是 Valhalla 落地后会行为改变（甚至报错）的代码。

## 3. 值类的超能力：展平与内联

### 3.1 内存形态对比

```text
普通类 Point 数组（现状）：
  Point[] = [引用][引用][引用]...        // 4B × N
             ↓       ↓
           对象1   对象2                  // 每个 16B+（头+字段）
  合计 ≈ 20B/元素

值类 Point 数组（Valhalla 展平后）：
  Point[] = [x,y][x,y][x,y]...          // 连续内联：8B/元素（两个 int）
  无对象头、无指针、无 GC 追踪
  合计 ≈ 8B/元素 —— 2-10× 密度提升（官方口径）
```

| 指标 | 现状（引用） | 值类展平后 |
|------|:---:|:---:|
| 100 万个 Point | ~20MB+ | **~8MB** |
| 顺序遍历 | 指针追逐、缓存行无效 | 连续内存、缓存友好 |
| GC 压力 | 每对象追踪 | 数组级整体处理 |
| CPU 缓存局部性 | 差 | 好 |

### 3.2 展平的实现机制（JVM 层）

```text
HotSpot 优化开关（Valhalla 分支）：
  - UseFieldFlattening：字段内联（对象内部字段直接展开）
  - UseArrayFlattening：数组元素展平
  - InlineTypePassFieldsAsArgs：值类按字段传参（而非引用）
  - UseACmpProfile：值类 == 比较的 profile
→ 这些是"优化"，不是"语义"：JVM 合规基线只需支持 ACC_IDENTITY / ACC_STRICT_INIT
  标志与新语义（acmp、ifnull、monitorenter），优化可关闭
```

> 💡 **设计哲学**：值类的**语义**（无身份、值比较）是规范强制的；**性能**（展平）是 JVM 优化可选的。这保证低端移植也能正确执行，高端平台自动获得性能。

## 4. JEP 402：包装类的迁移

### 4.1 草稿内容

**JEP 402: Enhanced Primitive Boxing / Classes for the Basic Primitives (Preview)**（草稿阶段）：

```text
目标：把 Integer、Long 等 8 个包装类迁移为"原始类"（primitive classes）
    → 装箱后的 Integer 获得与 int 同级的性能
    → List<Integer> 存储 Integer 时展平 → 泛型容器自动"特化级"性能
    → 与 JEP 390（值类型类警告）和 JEP 401（值类机制）闭环
```

| 环节 | 现状 | JEP 402 后 |
|------|------|-----------|
| `Integer` 实例 | 16B 对象 + 身份 | 值类：可展平、无身份 |
| `Integer[]` | 引用数组 + 对象散落 | 可能直接展平为 int[] 形态 |
| `List<Integer>` | 装箱 + 指针追逐 | 底层存储优化，API 不变 |
| `==`（两个 Integer） | 引用比较（陷阱） | 值比较（陷阱消失） |
| `synchronized(Integer)` | 警告（JEP 390） | **运行时报错** |

> ⚠️ **这就是 JEP 390 提前警告的完整逻辑链**：synchronized(包装类) 今天只是警告，值类落地后直接是错误——现在修，成本最低。

### 4.2 对 03 章陷阱的"自动治愈"

| 陷阱（03 章） | JEP 402 后 |
|--------------|-----------|
| `Integer c=1000, d=1000; c == d` → false | **== 变值比较** → true（与缓存无关） |
| 缓存边界行为差异 | 语义消失（值比较无缓存概念） |
| `Integer` 锁对象失效 | 直接报错（不再有静默失效） |
| 装箱内存放大 | 展平后接近 int |

> 🎯 **核心要点**：Valhalla 落地后，03 章一半的"陷阱"自动变为"正确行为"——但也意味着**存量代码依赖这些陷阱行为的（== 缓存外比较、包装类同步）需要提前修复**。

## 5. 泛型特化：绕过擦除而非移除擦除

### 5.1 官方路线

| 方案 | 状态 | 内容 |
|------|------|------|
| **Universal Generics**（草稿 JEP 8261529） | 草稿 | 泛型方法/类的多态特化：`List<int>` 语法级支持（远期） |
| **Parametric JVM** | 无草稿 | JVM 层按需生成特化版本 |
| **当前过渡手段** | 已生效 | JIT 的类型 profiling + 内联 + 去虚拟化（[Inside.java 2026-04: How the JVM Optimizes Generic Code](https://inside.java/2026/04/19/generics-optimization/)） |

### 5.2 关键承诺：擦除不被移除

```text
Valhalla 路线图明确：
  - 类型擦除是 Java 向后兼容的基石，不会移除
  - List<String> 的擦除行为永远不变（老字节码永远能跑）
  - 特化是"在擦除之外叠加"：JVM 为值类实参生成优化形态
  - 语法上 List<int> 未必出现；实际效果靠值类 + JVM 优化达成
```

```java
// 远期可能形态（Universal Generics 设想的语法，未定稿）
// List<int> numbers = ...;          // 特化容器（语法未定，勿当真）
// 确定性更高的路径：
value class Money { long cents; }    // 用户值类
List<Money> prices = ...;            // 既有语法，JVM 负责展平优化
```

> 💡 **一句话理解**：Valhalla 的路线是"**API 不动、实现动**"——`List<Integer>` 的源码与字节码不变，JVM 在底层把存储与比较变成特化形态。开发者无需重写集合代码。

## 7. 对开发者意味着什么

### 7.1 现在就该做的事

| 动作 | 理由 |
|------|------|
| 消灭 `synchronized(包装类)` | 值类落地后直接报错（JEP 390 已警告多年） |
| 消灭 `new Integer()`（若还有） | 构造器废弃中，值类化后行为变化 |
| 不依赖缓存外 `==` 结果 | 值类化后语义将变（值比较） |
| 大数据量数值场景用原始集合 | 等 Valhalla 期间的最优解（07 章） |
| 关注 `--enable-preview` 试验 | JDK 28 预览可试用，尽早暴露生态问题 |

### 7.2 不需要做的事（重要）

```text
❌ 不用重写 List<Integer> 代码 —— API 不变
❌ 不用等待 Valhalla 才能优化 —— 现有 JIT 已消除大量装箱（02 章）
❌ 不用害怕擦除 —— 擦除永远在，类型安全由 checkcast 守护
```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. Valhalla 双目标：JEP 401 值类（无身份、可展平，首个预览计划 JDK 28、2026-07 并入主线）+ 泛型特化（绕过擦除而非移除擦除）；
> 2. 值类把 `List<Integer>` 从"引用数组 + 16B 对象"变成"展平内联"，内存密度提升 2-10×，且 API 零改动；
> 3. 今天的三件事：修掉 synchronized(包装类)、停用 new Integer()、不依赖缓存外 ==——JEP 390 的警告就是为这一刻提前买单。
