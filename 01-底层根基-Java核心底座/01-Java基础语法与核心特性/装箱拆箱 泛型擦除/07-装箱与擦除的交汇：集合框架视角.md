# 装箱与擦除的交汇：集合框架视角

> `ArrayList<Integer>` 是 Java 类型系统两大折中的交汇点：擦除让内部数组变成 `Object[]`，装箱让每个元素变成堆对象——**"泛型集合存不了原始类型"与"装箱开销"是同一个问题的两面**。本章算清这笔账，并给出大数据量场景的正确替代

## 1. 存储真相：ArrayList<Integer> 内部长什么样

### 1.1 擦除后的源码

```java
// 你写代码时的视角
List<Integer> scores = new ArrayList<>();

// JDK 源码的真实形态（擦除后）
public class ArrayList<E> extends AbstractList<E> ... {
    Object[] elementData;        // ← 擦除后：E[] → Object[]
    public boolean add(E e) { ... }
    E elementData(int index) { return (E) elementData[index]; }   // ← 每次读取都强制转型
}
```

**三层叠乘**：

```text
① 泛型擦除：elementData 是 Object[]，不是 Integer[]
② 元素存储：add(42) → 必须先把 int 装箱成 Integer 对象，引用存入 Object[]
③ 元素读取：get(i) → Object 强制转型 Integer（checkcast）+ 调用方拆箱 intValue
```

### 1.2 写入与读取的完整字节码

```java
// 源码
scores.add(42);
int v = scores.get(0);

// 等价执行序列
scores.add(Integer.valueOf(42));            // 装箱（缓存外 → 分配对象）
Integer boxed = (Integer) scores.elementData[0];   // checkcast（擦除后插入）
int v = boxed.intValue();                   // 拆箱
```

> 🎯 **核心要点**：`List<Integer>` 的每个元素都要经历 **装箱（分配）→ 引用存储 → 转型检查 → 拆箱** 四步——这就是"集合框架视角"下的装箱+擦除联合成本。

## 2. 全链路成本：add 与 get 的隐式工作

| 操作 | 隐式动作 | 成本 |
|------|---------|------|
| `add(42)` | `Integer.valueOf(42)`（缓存外→分配）+ 数组写 | 分配 16B + 写引用 |
| `get(i)` | 读引用 + `checkcast` + `intValue()` | 指针跳转 + 类型检查 |
| 遍历 | 每元素解引用 + 拆箱 | 缓存行无效（对象散落） |
| `equals`/`contains` | 遍历元素逐个 `equals`（值比较） | 对象间接寻址 |
| `sort` | TimSort 移动引用（对象不动） | 比 int[] 排序好——**唯一优势** |

> 💡 **平衡认知**：`List<Integer>` 并非一无是处——**引用语义**（同一个 Integer 实例可被多处引用）、**可变性**（元素可整体替换）、**排序时只搬引用**是它的天然优势。代价是"数值型工作负载"下的空间与访存劣势。

## 3. int[] vs Integer[] vs List<Integer> 内存对比

以 100 万个数（值域大于 127，缓存不覆盖）为例：

| 容器 | 内存 | 布局 | 访存模式 |
|------|:---:|------|---------|
| `int[1_000_000]` | **~4 MB** | 连续 4B/元素 | 顺序缓存友好 |
| `Integer[1_000_000]` | 引用 4MB + 对象 16MB = **~20 MB** | 引用连续、对象散落 | 指针追逐 |
| `List<Integer>`（ArrayList） | 同上 ~20 MB + 容量余量 | 同 Integer[] | 同 Integer[] |
| 100 万全在缓存内（值 ≤127） | **~4 MB**（共享缓存实例） | 引用数组 + 复用实例 | 引用跳转（无新分配） |

```java
// 实测量级验证思路（自行跑）：创建 100 万整数容器后看堆
// List<Integer>：jmap -histo 会看到 100 万 + Integer 实例（16B × 100 万 ≈ 16MB）
// int[]：只有一个数组对象（4MB）
```

| 容器 | 遍历耗时（量级） | 说明 |
|------|:---:|------|
| `int[]` | 1×（基准） | 顺序读缓存行 |
| `Integer[]` | 2-4× | 对象散落，缓存行利用率低 |
| `List<Integer>` | 与 Integer[] 相当 | 多一层方法调用（JIT 会内联） |

## 4. Map 的双重装箱

```java
// HashMap<Integer, Long> 的键和值都装箱：双重成本
Map<Integer, Long> stats = new HashMap<>();
stats.put(12345, 9999999999L);       // key 装箱 Integer + value 装箱 Long
Long v = stats.get(12345);           // key 装箱（查找用）+ 读引用

// 极端场景：时间戳 → 计数（毫秒级 key，全在缓存外）
// 100 万条目 ≈ key 16B + value 24B 对象 + entry 节点 ≈ 50-60MB+
// 对比：两个 long[]（key + value 平行数组）≈ 16MB
```

| 优化手段 | 做法 | 收益 |
|---------|------|------|
| 平行数组 | `long[] keys, long[] values` + 二分 | 内存 3-4× 缩减 |
| `Long2IntOpenHashMap`（fastutil） | 原始 key/value 哈希表 | 内存与性能双优 |
| 避免自动装箱 key | 自定义 `long→int` 映射 | 消除查找时的分配 |

## 5. Stream 集合视角：特化流的取舍

```java
// 集合 → 流的两条路
List<Integer> list = ...;

// 路径 A：Stream<Integer> —— 集合里取出的对象原样流转，运算仍装箱
int sum = list.stream().mapToInt(x -> x).sum();       // 终点特化

// 路径 B：IntStream —— 从源头特化
int sum = list.stream().mapToInt(Integer::intValue).sum();   // 每元素拆箱一次
// 或集合本身是 int[] 时：
int sum = Arrays.stream(intArray).sum();              // 零装箱

// 反向：IntStream → 集合（boxed 是装箱的显式入口）
List<Integer> boxed = IntStream.range(0, 1000).boxed().toList();   // 1000 次装箱
```

| 场景 | 推荐 | 理由 |
|------|------|------|
| 源是 `int[]` | `Arrays.stream(int[])` | 全程原始流 |
| 源是 `List<Integer>` | `mapToInt(Integer::intValue)` 立即特化 | 尽早进入原始流 |
| 需要返回集合 | `boxed().toList()` 仅在终点 | 装箱集中在边界 |
| 大数聚合 | `IntStream.sum/average/min` | 特化实现无中间对象 |

## 6. 专用原始类型集合：fastutil 与 Eclipse Collections

### 6.1 为什么存在

JDK 泛型无法直接表达 `IntArrayList`——擦除决定 `List<Integer>` 只能是引用容器。第三方库用**代码生成**为每个原始类型生成专用集合：

| 库 | 代表类型 | 特性 |
|----|---------|------|
| [fastutil](https://fastutil.di.unimi.it/) | `IntArrayList`、`Int2IntOpenHashMap` | 内存紧凑、开箱即用、无依赖 |
| [Eclipse Collections](https://www.eclipse.org/collections/) | `IntList`、`IntIntMap` | 接口体系完整、流式 API |
| Trove（维护放缓） | `TIntArrayList` | 老牌，性能依然在线 |

```java
// fastutil 用法（与 JDK 集合 API 几乎同构）
import it.unimi.dsi.fastutil.ints.IntArrayList;
import it.unimi.dsi.fastutil.ints.Int2IntOpenHashMap;

IntArrayList list = new IntArrayList(1_000_000);
list.add(42);                        // 直接存 int，无装箱

Int2IntOpenHashMap map = new Int2IntOpenHashMap();
map.put(12345, 99);                  // 原始 key/value，无装箱
```

### 6.2 收益量级

| 对比项 | `ArrayList<Integer>` | `IntArrayList`（fastutil） |
|--------|:---:|:---:|
| 100 万元素内存 | ~20MB | **~4MB**（int[] 内部实现） |
| add 开销 | 装箱 + 可能扩容搬引用 | 纯数组写 |
| 遍历 | 指针追逐 + 拆箱 | 连续内存顺序读 |
| 查找（Map 场景） | 装箱 key + 对象节点链 | 开放寻址原始哈希 |

> ⚠️ **选型提示**：原始集合库的代价是**类型体系割裂**（`IntArrayList` 不是 `List<Integer>` 的子类型）——引入前评估团队熟练度与 API 迁移成本；数据量大（百万级）且是数值型热路径时收益显著。

## 7. JDK 为什么没有特化集合：设计与未来

### 7.1 历史答案：擦除 + 二进制兼容

```text
Java 5 设计泛型时曾讨论"特化"方案（为每个原始类型生成专用 List）：
  否决原因：
  ① 二进制兼容：老 List 字节码必须照常工作，特化类爆炸（List<int>、List<long>...）
  ② 类文件膨胀：8 个原始类型 × 泛型容器 = 指数级类数量
  ③ 开发与维护成本：JDK 团队无法为每种组合提供一等公民支持
  结论：擦除是"最小改动、最大兼容"的工程选择——代价就是今天看到的装箱
```

### 7.2 JDK 现有"特化"实例

| 特化对象 | 现状 |
|---------|------|
| `IntStream`/`LongStream`/`DoubleStream` | ✅ 特化（lambda 时代为性能补的课） |
| `OptionalInt`/`OptionalLong`/`OptionalDouble` | ✅ 特化 |
| `IntSummaryStatistics` 等 | ✅ 特化 |
| `ArrayList<Integer>` | ❌ 无特化（用户自担装箱） |
| 原始类型集合 | ❌ 依赖第三方 |

> 💡 **规律**：JDK 只对"函数式管道中间态"做特化，不对"存储容器"做——因为管道特化不破坏 List API 兼容，容器特化做不到。

### 7.3 未来答案：Valhalla 值类（08 章详述）

```text
value class 落地后：
  List<Integer> 不再是"引用数组 + 16B 对象"
  JVM 可在数组/容器内展平（flatten）值类实例
  → 装箱开销、对象头、指针追逐全部消失
  → 且不破坏既有 API（List<Integer> 照常编译运行）
  → 泛型容器无需改写即可获得特化级性能（JIT/VM 层完成）
```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. `List<Integer>` 的真相：擦除后内部是 `Object[]` + 读取强制转型，元素存取必装箱/拆箱——"泛型存不了原始类型"与"装箱开销"是同源问题；
> 2. 100 万数值：`int[]` 4MB vs `List<Integer>` ~20MB + 指针追逐；Map 场景双重装箱更严重；
> 3. 现阶段解法：`IntStream` 特化流 + fastutil 等原始集合；终极解法是 Valhalla 值类展平（不破坏 API 的"正统特化"）。
