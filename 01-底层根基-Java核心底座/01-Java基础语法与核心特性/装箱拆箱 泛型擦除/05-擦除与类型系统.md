## 1. 可具体化（reifiable）与不可具体化

### 1.1 定义

**可具体化类型（reifiable type）**：运行时拥有完整类型信息、可安全用于 `instanceof` / `new T[]` / 类型转换的类型。**不可具体化类型**：擦除后运行时信息不完整。

| 可具体化 ✅ | 不可具体化 ❌ |
|------------|-------------|
| 基本类型 `int` | `List<String>` |
| 原生类型 `List` | `List<? extends Number>` |
| 无界通配符 `List<?>` | `T`（类型变量） |
| `int[]`、`List[]` | `T[]` |
| 无限定泛型 `Map<K,V>` 作为边界外的裸类 | `Map<String, ? extends Number>` |

```java
// 判断口诀：类型里有没有"确定的类型实参"或"类型变量"
// List<?> 可具体化——因为运行时它就是个 List，检查安全
// List<String> 不可具体化——运行时是 List，instanceof 无法检查 String
```

### 1.2 为什么 instanceof 要区分

```java
// ✅ 合法：List<?> 可具体化
if (obj instanceof List<?>) { }

// ❌ 非法：编译错误
if (obj instanceof List<String>) { }      // 运行时 List 里没有 String 信息

// ❌ 非法：类型变量
<T> boolean isT(Object o) { return o instanceof T; }   // T 已擦除
```

> 🎯 **核心要点**：`instanceof` 的检查目标必须是**可具体化类型**。`List<?>` 能过是因为检查的是"是不是 List"（运行时信息足够）；`List<String>` 过不了是因为没人能在运行时验证"每个元素都是 String"。

## 2. 堆污染（Heap Pollution）

### 2.1 定义与产生路径

**堆污染**：一个变量被编译期静态类型声明为某种参数化类型，运行时却指向**不满足该类型参数约束**的对象——类型参数与实际内容错位。

```java
// 标准产生路径：原生类型与参数化类型混用
List<String> strings = new ArrayList<>();
List raw = strings;                 // ① 原生类型视图（warning: unchecked）
raw.add(42);                        // ② 混入 Integer —— 静态类型 System.out 无感知！
String s = strings.get(0);          // ③ 取值 → checkcast String → ClassCastException
```

```text
产生堆污染的三类入口：
① 原生类型 ↔ 参数化类型转换（最常见）
② 混入泛型 varargs（见第 5 节）
③ 反射 / 反序列化 / 不受信数据源直接构造对象图
```

### 2.2 为什么说这是"设计的代价"

| 维度 | 擦除泛型 | 假设的"真泛型"（如 C#） |
|------|---------|----------------------|
| 运行时类型检查 | 无（仅 checkcast 兜底） | 原生支持 |
| 集合混入异类 | 可能（原生类型入口） | 不可能 |
| 二进制兼容（Java 5 前代码） | ✅ 完美 | 需要重编译 |
| 泛型化集合框架改造 | 擦除实现，老代码零成本 | 运行时类型差异 |

> 💡 **权衡认知**：堆污染是 Java 选择**二进制兼容**（Java 5 的 List 就是今天的 List）的必然副作用。工程上接受它，但要用 `@SuppressWarnings("unchecked")` 的**最小作用域**约束它（见第 3 节）。

## 3. unchecked 警告地图

| 警告位置 | 代码 | 风险等级 | 处理 |
|---------|------|:---:|------|
| 原生类型赋值给参数化 | `List<String> l = rawList;` | 高 | 修数据源头；`Collections.checkedList` 兜底 |
| 参数化赋给原生 | `List raw = typedList;` | 中 | 尽量避免原生类型代码 |
| 泛型数组创建 | `new T[10]`（方法内） | 高 | 第 4 节绕行方案 |
| 泛型 varargs | `f("a", "b")` 传参到 `f(T...)` | 中 | `@SafeVarargs`（条件满足时） |
| 类型转换 | `(List<String>) obj` | 中 | 尽量用 `instanceof List<?>` 先判 |
| 反射构造 | `Class<T>.newInstance()` | 中 | 6.3 节 |
| 不确定类型捕获 | `rawList.add(anyObj)` | 高 | 用 `?` 通配符替代原生 |

```java
// 规范做法：checked collection 兜底（让运行时立即暴露混入）
List<String> safe = Collections.checkedList(new ArrayList<>(), String.class);
safe.add(42);        // ClassCastException 立即抛出（而不是延迟到取值）
```

> ⚠️ **压制警告的原则**：`@SuppressWarnings("unchecked")` 只加在**最小作用域**（单个语句/方法），并注释说明"为什么安全"——无条件压制是生产事故的温床。

## 4. 为什么 new T[] 非法：泛型数组的三条绕行路

### 4.1 非法根源

```java
// ❌ 编译错误：generic array creation
T[] arr = new T[10];

// 根源：数组在运行时携带组件类型（可具体化要求）
// 若允许 new T[10]，T 擦除后变成 new Object[10]——却对外宣称 T[]
// → 存储检查（ArrayStoreException 机制）与泛型类型参数互相矛盾
// 类比：Object[] o = new String[10]; o[0] = 42; → ArrayStoreException
//      若允许 T[]，T=String 时语义等同上面，但 String 信息已擦除，矛盾无法调和
```

### 4.2 三条绕行路

| 方案 | 写法 | 安全性 | 适用 |
|------|------|:---:|------|
| ① 数组改为 List | `List<T> list = new ArrayList<>()` | ✅ 最安全 | 大多数场景，首选 |
| ② 存 `Object[]`，访问时转型 | `Object[] arr; T get(i) { return (T) arr[i]; }` | ✅（受控） | 自定义容器内部实现 |
| ③ 传入 `Class<T>` 反射建数组 | `(T[]) Array.newInstance(clazz, n)` | ⚠️ 返回类型本身不可具体化，仍需 unchecked | 确实需要数组返回的 API |

```java
// 方案③ 是 JDK 集合框架自己的选择（ArrayList.toArray 内部）
public <T> T[] toArray(T[] a) {
    if (a.length < size)
        return (T[]) Arrays.copyOf(elementData, size, a.getClass());  // unchecked
    ...
}
```

### 4.3 绕行路背后的权衡

```text
方案② 的自我检查：
- 写入：用 E（擦除为 Object）接收 → 无法在编译期限制类型
- 读取：每次强制转型 + checkcast → 错误类型在读取点暴露（延迟暴露）
- 对比 int[]：原生数组有运行时的 ArrayStoreException 提前拦截
结论：泛型容器的类型安全 = 编译期接口 + 读取点 checkcast，比原生数组弱一档
```

## 5. varargs 泛型与 @SafeVarargs

### 5.1 为什么 varargs 会警告

```java
// 编译器展开：String... args → String[] args
// 但泛型 varargs：T... args → 展开为 T[] → new Object[]（泛型数组！）
static <T> List<T> concat(T... elements) { ... }
// 调用 concat("a", "b") → 编译器创建 Object[]{...} 传给方法
// → 方法内部把它当 T[] 用 → 潜在堆污染 → javac 警告：unchecked generic array
```

### 5.2 什么时候可以安全加 @SafeVarargs

**@SafeVarargs 适用条件**（JDK 9+ 放宽到 final/static/private 方法，此前仅 static/final/构造器）：

```java
// ✅ 安全：方法内部不把数组元素"泄漏"给外部可变结构
@SafeVarargs
static <T> List<T> asList(T... items) {
    List<T> list = new ArrayList<>();
    Collections.addAll(list, items);   // 只读 items，不向外暴露数组本身
    return list;
}

// ❌ 危险：数组本身被保存/暴露 → 调用方混入异类元素 → 堆污染
static <T> T[] bad(T... items) {
    return items;                       // 数组逃逸！
}
```

| 判断问题 | 安全则 |
|---------|:---:|
| 方法是否保存/返回 varargs 数组本身？ | 否 |
| 数组元素是否可能被外部以错误类型写入？ | 否 |
| 是否只有内部遍历、拷贝使用？ | 是 |

> 🎯 **核心要点**：`@SafeVarargs` 是"我保证不打乱数组类型"的承诺——承诺不保存、不返回、不外泄数组本身。乱加等于主动宣告堆污染窗口。

## 6. instanceof、异常与反射：擦除的禁区清单

### 6.1 禁区总表

| 操作 | 合法性 | 原因 |
|------|:---:|------|
| `instanceof List<String>` | ❌ | 不可具体化 |
| `instanceof List<?>` | ✅ | 可具体化 |
| `new T()` | ❌ | 运行时无类信息 |
| `new T[n]` | ❌ | 数组组件类型不可具体化 |
| `catch (T)` | ❌ | 异常类型必须是具体类（且 Throwable 子类） |
| `throw new T()`（T extends Throwable） | ⚠️ 创建时仍不行 | `new T()` 已非法 |
| `T.class` | ❌ | 类型变量无字面量 |
| `String.class`（具体类） | ✅ | 正常 |
| `(T) obj` | ⚠️ 允许但 unchecked | 擦除为 (Object) obj |
| 泛型类的 `getClass()` | ✅ | 返回 `Class<? extends Box>`（Box 而非 Box<Integer>） |

### 6.2 泛型与异常的合法用法

```java
// ✅ 泛型可以出现在"异常类型参数"上（有限但合法）
class BizException<T> extends Exception {   // 泛型异常类合法
    private final T detail;
}

// ✅ 方法声明抛出泛型上界（泛型抛出在签名层面合法）
<T extends Throwable> void rethrow(Exception e) throws T {
    throw (T) e;                            // 唯一合法的 unchecked 泛型转型
}
// 用途：精确类型检查异常（类似 Lombok sneakyThrow 的实现原理）
```

### 6.3 反射与禁区的配合（引出 06 章）

```java
// 反射创建泛型实例的经典三件套
Class<T> clazz = ...;          // ① 类型令牌（调用方传入具体 Class）
T obj = clazz.getDeclaredConstructor().newInstance();   // ② 反射构造
// ③ 数组：Array.newInstance(clazz, n)
// 所有"绕过擦除"的运行时方案，最终都依赖调用方提供 Class 对象——这就是 TypeToken 的出发点
```

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 可具体化是擦除模型的"分水岭"：`List<?>` 能 instanceof，`List<String>` 不能——运行时没有元素级类型信息；
> 2. 堆污染三入口（原生类型混用、泛型 varargs、反射/反序列化）的代价在读取点的 checkcast 引爆，`Collections.checkedList` 可提前引爆；
> 3. 泛型数组/异常/反射禁区不是"JVM 偷懒"，而是"数组的运行时类型检查与擦除在语义上不可调和"的必然。

**思考题**：

1. `List<?>` 为什么可具体化？它检查的是什么？（→ 1.2）
2. 为什么 `Collections.checkedList` 能提前抛出 ClassCastException？（→ 3）
3. `ArrayList.toArray(T[])` 里的 unchecked 转型为什么安全？（→ 4.2）
4. `@SafeVarargs` 能加在实例方法上吗（JDK 9 前后）？（→ 5.2）
