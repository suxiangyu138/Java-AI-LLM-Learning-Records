# 装箱拆箱的性能与内存

> 装箱的本质是"把 4 字节的栈上值变成 16 字节的堆对象"——在大批量数据处理下，这是 4-5 倍的内存放大与持续的 GC 压力。JIT 能救一部分（逃逸分析），救不了全部（逃逸的场景）

## 1. 内存成本：栈上 4 字节 vs 堆上 16 字节

### 1.1 对象内存布局（64 位 HotSpot，压缩指针默认开启）

```text
int（栈上/数组内）         4 字节
Integer（堆上对象）        ┌──────────────┐
                          │ mark word    │ 8 字节（锁/GC 状态/哈希）
                          │ klass 指针   │ 4 字节（压缩 class 引用）
                          │ int value    │ 4 字节（真实数据）
                          │ 对齐填充     │ 0 字节（16 已对齐 8）
                          └──────────────┘
                          合计 ≈ 16 字节（内含数据仅 4 字节，利用率 25%）
```

| 类型 | 内存 | 相对 int 放大 |
|------|:---:|:---:|
| `int` | 4 B | 1× |
| `Integer`（对象） | ~16 B | **4×** |
| `long` | 8 B | 1× |
| `Long`（对象） | ~24 B | **3×** |
| `Integer[]`（1M） | ~16MB（引用 4B×1M + 对象） | 对象散落，约 **4-5×** |
| `int[]`（1M） | ~4MB（连续内存） | 1× |

### 1.2 两个结构性劣势

```text
劣势一：数据密度
  int[]   → 4 字节/元素，连续内存，CPU 缓存友好（1 个 64B 缓存行装 16 个元素）
  Integer[] → 引用数组 4B/元素 + 每个元素 16B 对象散落堆中
              → 遍历 16 个元素要访问 16 个不相邻的缓存行 + 16 次解引用

劣势二：分配与回收
  每次装箱 = 一次堆分配 = 一次年轻代 GC 的候选对象
  批量装箱 10M 个 → 10M 次分配 → Young GC 频率显著上升
```

> 🎯 **核心要点**：装箱的代价是**结构性**的——不只多花 12 字节，还把"连续内存遍历"变成"指针追逐"，缓存局部性同时恶化。数据量越大、访问越密集，放大效应越明显。

## 2. 分配与 GC 压力

### 2.1 装箱分配生命周期

```text
Integer.valueOf(1000)  // 缓存外
    → 分配 16B 对象 → 存活于年轻代 → 短命对象 → Young GC 回收
    → 若逃逸到集合/全局 → 晋升老年代 → 增加老年代与 Full GC 负担
```

| 场景 | GC 影响 |
|------|---------|
| 临时运算的装箱（JIT 优化掉） | 几乎无（见第 3 节） |
| 大量短命装箱（解释执行/逃逸） | Young GC 频率与耗时上升 |
| 集合中长期驻留的包装对象 | 老年代膨胀，Full GC 压力 |
| 缓存范围内装箱 | 无分配（valueOf 返回缓存实例） |

### 2.2 与缓存池的交互

```java
// 幸运场景：值在缓存内 → valueOf 零分配
Integer a = 1, b = 1;      // 同一个缓存实例
// 不幸场景：值在缓存外 → 每次装箱都是新对象
Integer a = 5000, b = 5000;   // 两个不同对象（生产代码常见！）
```

> 💡 **推论**：`-XX:AutoBoxCacheMax` 提升缓存上限的收益是**减少热点值域的分配**——但默认 127 的设计是内存与分配的平衡，业务值域大时靠优化代码结构（第 5 节）更根本。

## 3. JIT 的救命稻草：逃逸分析与标量替换

### 3.1 机制

C2 编译器的**逃逸分析（Escape Analysis）**发现装箱对象未逃逸（未返回、未存入集合、未传给未知代码）时，执行**标量替换（Scalar Replacement）**：

```java
// 这段代码的装箱大概率被 JIT 消除
long sumSquares(int n) {
    long total = 0;
    for (int i = 0; i < n; i++) {
        Integer v = i * i;       // 装箱
        total += v;              // 立即拆箱用掉
    }
    return total;
}
// C2 分析：v 未逃逸 → 直接用栈上 int 计算 → 无分配
```

### 3.2 逃逸失败的七个条件（标量替换失效）

| 逃逸行为 | 示例 | 后果 |
|---------|------|------|
| 方法返回 | `return boxed;` | 必须真实对象 |
| 存入堆 | `list.add(boxed);` | 必须真实对象 |
| 传给未内联方法 | `external(boxed);` | 必须真实对象 |
| 身份敏感操作 | `==`、`System.identityHashCode()` | 需对象身份 |
| 同步 | `synchronized(boxed)` | 需对象监视器 |
| 反射访问 | `field.get(obj)` | 需真实对象 |
| 锁/内存屏障依赖 | `volatile` 包装引用 | 语义要求 |

```java
// 反例：看似"简单"的累加，其实完全逃逸（方法返回 → 无法标量替换）
static Integer getNext() { return counter++; }   // counter 为字段 → 逃逸
```

> ⚠️ **JIT 依赖是脆弱的**：解释执行与 C1 阶段没有标量替换；代码形态一变（返回、入集合、加锁）优化立即失效。**性能关键路径不要赌 JIT 消除装箱**——这是生产原则，不是学术建议。

## 4. 热点场景解剖：循环、集合与 Stream

### 4.1 循环装箱（经典反模式）

```java
// ❌ 反模式：每次迭代两个装箱（乘法结果 + 累加结果），且因返回逃逸无法消除
static Integer sumBoxed(int n) {
    Integer sum = 0;
    for (int i = 0; i < n; i++) {
        sum = sum + i;          // sum 拆箱 + i 拆箱？——不：sum 是 Integer，i 拆箱；
                                // sum + i 结果为 int → 装箱赋回 sum → 每轮一个 Integer
    }
    return sum;
}
// 规模 1000 万 → 约 1000 万个 Integer 对象（16B×10M ≈ 160MB 分配）

// ✅ 正确：全程 primitive
static int sumPrimitive(int n) {
    int sum = 0;
    for (int i = 0; i < n; i++) sum += i;
    return sum;
}
```

### 4.2 集合装箱（见 07 章详述，此处给结论）

```java
List<Integer> scores = new ArrayList<>(1_000_000);
for (int i = 0; i < 1_000_000; i++) scores.add(i);   // 100 万次装箱分配
// vs int[] 等价操作：零对象分配，快数倍
```

### 4.3 Stream 装箱

```java
// ❌ Stream<Integer> 隐式装箱
long count = list.stream()          // Stream<Person>
    .map(p -> p.getAge())           // 返回 int → 装箱成 Integer
    .filter(a -> a > 18)            // 拆箱比较
    .count();                       // 每个年龄一个装箱对象

// ✅ IntStream 特化（原始类型流，无装箱）
long count = list.stream()
    .mapToInt(Person::getAge)       // IntStream：int 在内部存储/处理
    .filter(a -> a > 18)
    .count();
```

| 流类型 | 内部元素 | 装箱 |
|--------|---------|:---:|
| `Stream<Integer>` | 引用 | ✅（每元素） |
| `IntStream` / `LongStream` / `DoubleStream` | 原始类型 | ❌ |
| `boxed()` / `mapToInt()` | 转换桥梁 | 转换处 |

> 🎯 **核心要点**：性能敏感的数据流水线**全程使用 IntStream/LongStream**，避免 `Stream<Integer>`；集合→流的起点也优先 `mapToInt` 而不是 `map`。

## 5. 优化模式工具箱

| 模式 | 做法 | 收益 |
|------|------|------|
| primitive 数组替代包装数组 | `int[]` 而非 `Integer[]` | 4× 内存 + 缓存友好 |
| 专用原始类型集合 | fastutil / Eclipse Collections / Trove | 大数据量 2-5× 性能 |
| IntStream 替代 Stream<Integer> | `mapToInt` 全程原始流 | 消除逐元素装箱 |
| 装箱边界控制在 API 层 | 重载 `sum(int[])` 而非只提供 `sum(Integer[])` | 调用方零成本 |
| 热点路径避免返回包装 | 内部方法返回 `int`，仅外部边界转换 | 保住标量替换 |
| 避免身份敏感操作 | 不 `==`、不同步、不 identityHashCode 包装对象 | 保住逃逸分析 |
| 合理利用缓存 | 小值域场景依赖 valueOf 缓存 | 零分配 |

```java
// 综合示例：数值计算引擎的正确姿势
class Stats {
    // 外部边界：一次装箱
    Integer average(int[] data) {
        return sum(data) / data.length;      // 仅此一处装箱
    }
    // 内部全程 primitive
    private int sum(int[] data) {
        int s = 0;
        for (int v : data) s += v;           // 零装箱
        return s;
    }
}
```

## 6. 实测量级参考

> ⚠️ 以下为**量级参考**（具体值随 JDK 版本、JIT 状态、硬件波动），用于建立直觉，不代表精确基准：

| 场景 | 量级结论 |
|------|---------|
| 1M 个 Integer 对象 | ~16MB 堆（vs 1M 个 int ~4MB） |
| 装箱循环 10M 次（无 JIT 消除） | 分配 ~160MB，Young GC 数轮 |
| 装箱循环 10M 次（标量替换生效） | 近似零分配 |
| Stream<Integer> 全链路 vs IntStream | IntStream 通常快 2-5×（数据量越大越明显） |
| Integer[] 随机访问 vs int[] | 有效带宽差距可达 3-5×（缓存行翻倍失效） |

```bash
# 观察装箱分配的实证工具
# 1. JFR 分配采样（Java 16+）：看热点分配是哪个对象
java -XX:StartFlightRecording=filename=alloc.jfr,settings=profile App
jfr print --events jdk.ObjectAllocationSample alloc.jfr
# 2. GC 日志：观察 Young GC 频率与对象体积
java -Xlog:gc App
# 3. 逃逸分析是否生效：-XX:+PrintEliminateAllocations（诊断用，正式环境勿开）
```

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 装箱的结构性代价：4 字节 → ~16 字节 + 指针追逐 + 堆分配，大数据量下 4-5× 内存放大与 GC 压力；
> 2. JIT 逃逸分析 + 标量替换可消除"未逃逸"装箱，但依赖代码形态——返回、入集合、身份操作都会打破优化；
> 3. 生产原则：性能关键路径用 `int[]`/`IntStream`/原始类型集合，把装箱限制在 API 边界。

**思考题**：

1. 为什么 `Integer[]` 遍历比 `int[]` 慢这么多，除了对象大小还有什么？（→ 1.2 缓存行）
2. 什么代码形态会"意外"让标量替换失效？（→ 3.2）
3. `map(p -> p.getAge())` 换成 `mapToInt(Person::getAge)` 消除了什么？（→ 4.3）
4. 怎么确认自己的热点代码装箱被 JIT 消除了？（→ 6）
