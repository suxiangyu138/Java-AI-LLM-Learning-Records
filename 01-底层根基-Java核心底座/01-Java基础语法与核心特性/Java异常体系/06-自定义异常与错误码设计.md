## 1. 自定义异常设计五要素

| 要素 | 规范 | 示例 |
|------|------|------|
| 命名 | 以 `Exception` 结尾，语义明确 | `OrderNotFoundException` |
| 继承 | 业务异常继承 `RuntimeException` | `class OrderNotFound extends BusinessException` |
| 构造器 | 覆盖常见签名（无参 / message / cause / message+cause） | `OrderNotFoundException(String id)` |
| 状态 | 携带错误码与上下文字段 | `errorCode`、`orderId` |
| 文档 | Javadoc 写明触发条件 | `@throws` 或类注释 |

**完整示例**（工程标准模板）：

```java
public class OrderNotFoundException extends RuntimeException {
    private final String errorCode = "ORDER_NOT_FOUND";
    private final String orderId;              // 上下文字段：排查直接用

    public OrderNotFoundException(String orderId) {
        super("订单不存在, orderId=" + orderId);
        this.orderId = orderId;
    }

    public OrderNotFoundException(String orderId, Throwable cause) {
        super("订单不存在, orderId=" + orderId, cause);
        this.orderId = orderId;
    }

    public String getErrorCode() { return errorCode; }
    public String getOrderId() { return orderId; }
}
```

**设计要点**：

1. **消息必带上下文**——`"订单不存在"` 没用，`"订单不存在, orderId=A123"` 才能直接定位；
2. **上下文字段独立存放**——方便全局处理器提取（如错误响应里回带 orderId），而不是从 message 里正则抠；
3. **构造器给足组合**——`new XxxException("...", cause)` 与 `new XxxException("...")` 都要有。

> 🎯 **核心要点**：自定义异常的两个职责——**语义化**（调用方/前端能看懂）与**携带上下文**（排障者能直接定位）。只写一个 `super("报错了")` 的自定义异常是伪需求。

## 2. 继承选择：为什么业务异常继承 RuntimeException

| 维度 | 继承 Exception（受检） | 继承 RuntimeException（非受检） |
|------|----------------------|------------------------------|
| 调用方 | 必须 catch/throws | 无需被迫处理 |
| 签名污染 | 层层 throws | 无 |
| 与框架配合 | Spring 事务/拦截器不友好 | **Spring 事务回滚默认捕获 RuntimeException** |
| 全局收口 | 需要每层手动 | 边界统一处理器 |
| 现代实践 | 极少（如 InterruptedException） | **默认选择** |

```java
// Spring 的默认行为：RuntimeException 触发事务回滚，受检异常不触发！
// 业务异常继承 RuntimeException → 业务失败自动回滚事务 —— 这是最关键的技术理由
public class BusinessException extends RuntimeException { ... }
```

**分层的两个基础类**：

```java
// 基础 1：业务异常 —— 业务规则失败（用户可理解、可提示）
public class BusinessException extends RuntimeException {
    private final String code;
    public BusinessException(String code, String message) { ... }
}

// 基础 2：系统异常 —— 基础设施/非预期失败（用户无需理解、要告警）
public class SystemException extends RuntimeException {
    public SystemException(String message, Throwable cause) { ... }
}

// 判断方法：用户能看到/能纠正 → Business；用户看不懂/需要修代码 → System
```

> ⚠️ 面试高频追问："业务异常为什么不继承受检异常？"答案链：签名污染 → 上层处理不了 → Spring 事务按 RuntimeException 回滚 → 全局处理器统一转响应——四连答完整。

## 3. 错误码设计：枚举、分段与文档化

**错误码的两种载体**：

| 方式 | 优点 | 缺点 |
|------|------|------|
| 字符串常量（`"ORDER_NOT_FOUND"`） | 语义清晰、可读 | 拼写错误无检查 |
| **枚举**（推荐） | 类型安全、集中管理、可携带消息 | 需要扩展时改枚举 |

**枚举承载错误码的标准模式**：

```java
public enum ErrorCode {
    // 通用错误：1000 段
    PARAM_INVALID("PARAM_INVALID", "参数不合法"),
    UNAUTHORIZED("UNAUTHORIZED", "未登录或登录过期"),

    // 订单错误：2000 段
    ORDER_NOT_FOUND("ORDER_NOT_FOUND", "订单不存在"),
    ORDER_ALREADY_SHIPPED("ORDER_ALREADY_SHIPPED", "订单已发货，无法操作"),
    ORDER_STATUS_INVALID("ORDER_STATUS_INVALID", "订单状态不允许该操作"),

    // 支付错误：3000 段
    PAY_CHANNEL_NOT_SUPPORTED("PAY_CHANNEL_NOT_SUPPORTED", "不支持的支付渠道"),
    PAY_BALANCE_INSUFFICIENT("PAY_BALANCE_INSUFFICIENT", "余额不足");

    private final String code;
    private final String defaultMessage;

    ErrorCode(String code, String defaultMessage) {
        this.code = code;
        this.defaultMessage = defaultMessage;
    }

    public String code() { return code; }
    public String defaultMessage() { return defaultMessage; }
}

// 异常携带枚举，消息可覆盖
public class BusinessException extends RuntimeException {
    private final ErrorCode errorCode;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.defaultMessage());
        this.errorCode = errorCode;
    }

    public BusinessException(ErrorCode errorCode, String message) {
        super(message);                    // 允许覆盖默认消息（如带上下文）
        this.errorCode = errorCode;
    }

    public ErrorCode errorCode() { return errorCode; }
}
```

**分段约定**：按模块分段（1000 通用 / 2000 订单 / 3000 支付…）——错误码表一眼可分类，前端也可以按段做统一处理（如 1000 段弹参数提示）。

> 🎯 **核心要点**：错误码的价值在**稳定性**——它是前后端、日志、告警共同引用的标识符，**一经发布不可随意变更**（前端可能已按它做分支），新增只增不改，删除需评估。

## 4. 按业务模块拆分的异常家族

**层次结构**（继承链设计）：

```text
RuntimeException
└── BusinessException（基础：code + message）
      ├── OrderException        —— 订单模块（ORDER_ 前缀）
      │     └── OrderNotFoundException
      │     └── OrderStatusException
      ├── UserException         —— 用户模块
      ├── PayException          —— 支付模块
      └── FileException         —— 文件模块
```

```java
// 模块基类：每个模块一个，携带模块前缀
public class OrderException extends BusinessException {
    public OrderException(ErrorCode code) { super(code); }
    public OrderException(ErrorCode code, String message) { super(code, message); }
}

// 具体异常：语义化命名，可直接被 handler 精准匹配
public class OrderNotFoundException extends OrderException {
    public OrderNotFoundException(String orderId) {
        super(ErrorCode.ORDER_NOT_FOUND, "订单不存在, orderId=" + orderId);
    }
}
```

**这种设计的三重收益**：

1. **catch 精准**：`catch (OrderException e)` 只拦订单业务失败；
2. **全局处理器分级**：`@ExceptionHandler(OrderNotFoundException.class)` 精确映射 404，`@ExceptionHandler(BusinessException.class)` 兜底 400；
3. **可扩展**：新增模块只需继承 BusinessException，不动既有层次。

## 5. 全局异常处理器：@RestControllerAdvice

**职责**：把"散落在各 Controller 的 try-catch"收敛到**一个入口**——Controller 不再捕获业务异常，只管调用：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 1. 精确处理：订单不存在 → 404 + 错误码
    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleOrderNotFound(OrderNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(ErrorResponse.of(e.errorCode(), e.getMessage(), e.getOrderId()));
    }

    // 2. 业务异常兜底 → 400 + 错误码
    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ErrorResponse> handleBusiness(BusinessException e) {
        return ResponseEntity.badRequest()
                .body(ErrorResponse.of(e.errorCode(), e.getMessage()));
    }

    // 3. 参数校验失败（jakarta validation）→ 400
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return ResponseEntity.badRequest().body(ErrorResponse.of("PARAM_INVALID", msg));
    }

    // 4. 系统异常兜底 → 500 + 不暴露内部细节
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleUnknown(Exception e) {
        log.error("未预期异常", e);                        // 完整堆栈进日志
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(ErrorResponse.of("SYSTEM_ERROR", "系统繁忙，请稍后重试"));   // 前端只见安全消息
    }
}
```

**三条纪律**：

| 纪律 | 说明 |
|------|------|
| 分级精确 | 业务异常 → 4xx + 错误码；系统异常 → 5xx + 模糊消息 |
| 不暴露内部 | 堆栈只进日志，响应体给安全消息（防止堆栈泄漏成为攻击信息） |
| 兜底必须存在 | 最后 `@ExceptionHandler(Exception.class)` 是防线，但**要记日志** |

> 🎯 **核心要点**：全局处理器是"异常语义"与"HTTP 契约"的翻译器——Controller 抛 `OrderNotFoundException`，前端收到 404 + 错误码 + 可读消息，日志里保留完整堆栈，三端各取所需。

## 6. 错误响应契约与前端协作

**统一响应结构**（与前端/调用方的稳定契约）：

```json
{
  "code": "ORDER_NOT_FOUND",
  "message": "订单不存在, orderId=A123",
  "traceId": "8f3a1b2c-...",
  "data": null,
  "timestamp": "2026-08-05T10:30:00Z"
}
```

```java
public record ErrorResponse(
        String code,          // 错误码：前端据此分支（稳定标识）
        String message,       // 可读消息：直接展示或提示
        String traceId,       // 追踪 ID：用户反馈问题时与日志关联
        Object data,          // 可选：补充上下文（如 orderId）
        String timestamp
) {
    public static ErrorResponse of(ErrorCode code, String message) {
        return new ErrorResponse(code.code(), message, TraceId.get(), null, Instant.now().toString());
    }
}
```

**协作要点**：

| 协作方 | 约定 |
|--------|------|
| 前端 | 以 `code` 分支处理（如 `ORDER_ALREADY_SHIPPED` 弹固定提示）；`traceId` 上报客服 |
| 日志 | 每个异常一次完整堆栈 + traceId 关联（MDC）——见 08 模块日志纪律 |
| 文档 | 错误码表随 API 文档发布，标注"新增只增不改" |

> 💡 **traceId 的价值**：用户反馈"下单失败了"→ 前端带 traceId → 日志按 traceId 检索 → 秒级定位完整调用链（与全链路追踪系统配合）。
