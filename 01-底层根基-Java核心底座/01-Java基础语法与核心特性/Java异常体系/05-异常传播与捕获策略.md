## 1. 异常传播机制：沿调用栈上行

**传播规则**：异常抛出后，**当前方法停止执行**，异常沿调用栈逐层上行——每层查找"有没有匹配的 catch"，找到就处理，找不到就继续上行，直到最外层（线程边界）：

```text
main()
  └→ service()   ←── 异常在这里被 catch 处理
        └→ dao()      ←── 异常在这里抛出
              └→ jdbc 调用（IOException/SQLException）
```

```java
public class PropagationDemo {
    public static void main(String[] args) {
        try {
            service();                    // ③ 在此被捕获
        } catch (RuntimeException e) {
            System.out.println("main 捕获: " + e.getMessage());
        }
    }

    static void service() { dao(); }      // ② 无 catch → 继续上行

    static void dao() {                   // ① 抛出
        throw new RuntimeException("数据库连接失败");
    }
}
```

**两个传播细节**：

1. **堆栈是"出生"时的快照**：异常在 `dao()` 创建时就记录了完整调用链——传播到 main 后 `printStackTrace()` 显示的仍是 dao 以下的完整链（这就是"异常链自带上下文"的原因）；
2. **非受检异常可以跨层穿透**：无需任何声明，直接从 dao 穿透 service 到 main——这正是"运行时异常穿透框架层"（Spring 事务回滚依赖它）的机制。

> 🎯 **核心要点**：传播机制决定了"在哪一层处理"是设计决策——底层不该处理上层才关心的异常，上层不该被底层细节污染，**边界层（入口）统一收口**（见 06 模块全局处理器）。

## 2. 捕获策略：捕获、上抛、还是包装

每个方法面对异常只有三种选择，**选择标准是"这一层能做什么"**：

| 策略 | 适用场景 | 示例 |
|------|---------|------|
| **捕获处理** | 这一层能恢复/降级/重试/提示 | 重试 3 次、缓存兜底、提示用户输入错误 |
| **声明上抛** | 这一层处理不了，上层才能决定 | DAO 层把 SQLException 上抛给 Service 决定 |
| **包装上抛** | 需要补充上下文，或转换语义 | 转业务异常 + 保留 cause |

```java
// 策略 1：捕获 + 降级（能恢复）
public String loadConfig() {
    try {
        return Files.readString(CONFIG_PATH);
    } catch (IOException e) {
        return DEFAULT_CONFIG;             // 降级：用默认配置
    }
}

// 策略 2：声明上抛（处理不了就传）
public void save(Order o) throws DataAccessException {
    orderDao.insert(o);                    // 底层异常直接透传（已是运行时）
}

// 策略 3：包装（补上下文）
public void createOrder(...) {
    try {
        orderDao.insert(order);
    } catch (DataAccessException e) {
        throw new OrderCreateException("创建订单失败, orderId=" + order.getId(), e);
    }
}
```

**判定口诀**：**"能恢复就捕获，不能恢复就包装，包装了没人关心就透传"**——最差的决策是"捕获了什么都不做"（吞异常，见 08 模块反模式）。

## 3. multi-catch 多异常捕获

**JDK 7（JEP 183）**：一个 catch 捕获多个不相关异常类型，用 `|` 分隔：

```java
// 旧写法：多个 catch 块处理相同逻辑
catch (IOException e) { logAndNotify(e); }
catch (SQLException e) { logAndNotify(e); }

// multi-catch
catch (IOException | SQLException e) {
    logAndNotify(e);                    // 同一个处理逻辑只写一遍
}
```

**三个硬规则**（面试易考）：

| 规则 | 说明 | 反例 |
|------|------|------|
| 类型间**不能有继承关系** | 有继承则编译器报错（父类能捕获子类，没必要） | `catch (IOException \| FileNotFoundException e)` ❌ |
| 变量**隐式 final** | 不能给 e 重新赋值 | `e = new IOException()` ❌ |
| 仍是单一变量 | 类型是它们的最近公共父类 | 调用只有公共父类才有的方法 |

> 💡 什么时候不值得用：两个异常的**处理逻辑不同**时不要硬凑 multi-catch——可读性优先于少写几行。

## 4. 精确重抛：JDK 7 的类型推断增强

**旧问题**（JDK 7 前）：catch 一个父类后重抛，编译器只会推断为父类类型，导致方法签名被迫声明宽泛的异常：

```java
// JDK 7 前：编译失败或签名被迫放宽
public void process() {
    try {
        riskyMethod();                       // throws IOException, SQLException
    } catch (Exception e) {                  // 捕获两个异常的公共父类
        throw e;                             // ❌ 编译器只当它是 Exception → 签名必须 throws Exception
    }
}
```

**JDK 7+ 精确重抛**：catch 参数是 **effectively final** 时，编译器按**实际抛出类型**推断：

```java
// JDK 7+：编译通过，签名保持精确
public void process() throws IOException, SQLException {   // 只声明实际会抛的
    try {
        riskyMethod();
    } catch (Exception e) {          // 统一处理逻辑
        log.warn("重试前记录", e);
        throw e;                     // ✅ 精确推断：这里实际重抛 IOException/SQLException
    }
}
```

**限制**：catch 参数若被重新赋值，则失去精确推断（变回声明的静态类型）——配合 effectively final 使用。

> 🎯 **核心要点**：精确重抛让"先统一记录/处理，再原样上抛"成为可能——**不需要为了日志而包装，不需要为记录而放宽签名**。

## 5. 包装与异常链：cause 的正确传递

**异常链**：包装异常时把底层异常作为 **cause** 传入，`getCause()` 一路挖到根因。

```java
// ✅ 正确：保留 cause —— 排查时能一路看到底层堆栈
throw new BizException("下单失败", e);          // cause = e
// e.getCause() → 原始 SQLException，含 SQL 语句与堆栈

// ❌ 错误 1：只传消息 —— 底层堆栈丢失，只能看到"下单失败"
throw new BizException("下单失败: " + e.getMessage());

// ❌ 错误 2：toString —— 消息冗长且仍无堆栈
throw new BizException(e.toString());
```

**异常链的传递规则**（构造器设计，见 06 模块）：

| 场景 | 构造器 |
|------|--------|
| 有 cause | `new XxxException("上下文", cause)` |
| 无 cause 但有上下文 | `new XxxException("上下文")` |
| 无上下文但有 cause | `new XxxException(cause)`（需要自定义支持） |

**日志里的最佳实践**：

```java
catch (Exception e) {
    log.error("订单 {} 处理失败", orderId, e);   // 上下文 + 完整堆栈
    throw new BizException("订单处理失败", e);   // 保留链上抛
}
// 注意：日志一次 + 包装上抛是允许的；"打印后重抛同一个异常"（printStackTrace + throw e）才是反模式（日志重复）
```

> ⚠️ **JDK 7+ 细节**：包装时新异常会自动把旧异常加入 suppressed（若构造函数未设置 cause）——但**显式传 cause 仍是正解**，语义清晰且 `getCause()` 是标准取法。

## 6. 转换边界：何时包装、何时透传

**转换边界**是分层架构中最容易被忽视的设计——每层的异常"语言"应统一：

| 层 | 抛出 | 说明 |
|----|------|------|
| DAO/数据层 | 数据访问异常（运行时） | 包装 SQLException 等，补 SQL/表名上下文 |
| Service/业务层 | **业务异常**（错误码 + 消息） | 业务规则失败；基础设施异常包装为系统异常 |
| Controller/入口层 | 不抛，交给全局处理器 | `@ExceptionHandler` 统一转响应 |
| 第三方对接 | 转为自己的异常语义 | 别让 OkHttp/Jackson 的异常直接裸奔到业务层 |

```java
// 分层包装示例
public class OrderService {
    private final OrderDao dao;

    public Order getOrder(String id) {
        try {
            return dao.findById(id);
        } catch (DataAccessException e) {              // 数据层异常
            throw new SystemException("DB 查询失败, orderId=" + id, e);   // 系统异常（记日志、告警）
        }
    }

    public void cancel(String id) {
        Order order = getOrder(id);
        if (order.isShipped()) {
            throw new BizException("ORDER_ALREADY_SHIPPED", "订单已发货，无法取消");  // 业务异常（提示用户）
        }
        // ...
    }
}
```

**包装的黄金法则**：

1. **包装必有新增信息**：只补充了上下文的包装才有价值（哪个订单、哪个文件、哪个接口）；
2. **透传不滥用**：底层运行时异常（如 NPE）不是"业务语义"，不该被包成业务异常——**bug 要原样暴露**；
3. **不层层包装**：同一异常被包装 5 层（每层套一个壳）是灾难——**每层只包装一次，且只有该层"有话说"时才包装**。

> 🎯 **核心要点**：异常转换的终极目标是**"错误语言统一 + 根因可追溯"**——调用方（前端/上层）看到业务异常的错误码与消息，排障者沿 cause 链看到底层堆栈，两者在同一个异常里各取所需。
