## 1. 编译器检查机制：受检异常如何被强制

**受检异常的强制规则**（javac 的编译期检查）：一个方法**可能抛出**受检异常时，必须二选一：

1. 在方法签名声明 `throws XxxException`（把责任上抛）；
2. 在方法体内 try-catch 处理掉。

两者都不做 → **编译错误**（`unreported exception IOException; must be caught or declared to be thrown`）。

```java
public void readConfig() {                    // ❌ 编译错误
    Files.readString(Path.of("config.json")); // readString 声明 throws IOException
}

public void readConfig() throws IOException { // ✅ 声明上抛
    Files.readString(Path.of("config.json"));
}

public void readConfig() {                    // ✅ 就地处理
    try {
        Files.readString(Path.of("config.json"));
    } catch (IOException e) {
        throw new ConfigLoadException(e);     // 包装后抛出（转型为自定义异常）
    }
}
```

**检查的三层语义**：

| 层 | 规则 | 例子 |
|----|------|------|
| 声明 | 方法 throws 了，调用方必须响应 | `readString` throws IOException |
| 传递 | 重写方法不能抛比父类更宽的受检异常 | 父类 throws IOException，子类 throws FileNotFoundException ✅ / Exception ❌ |
| 派生 | 接口/父类声明了，实现/子类继承义务 | 实现 `Runnable.run()` 不能抛受检异常（run 无 throws） |

> 🎯 **核心要点**：受检异常把"这个操作可能失败"写进了方法签名——调用方**无法假装失败不存在**。这是它的设计初衷，也是它所有弊端的根源。

## 2. 两种异常的定位差异

| 维度 | 受检异常（Checked） | 非受检异常（Unchecked） |
|------|-------------------|----------------------|
| 继承 | Exception 非 RuntimeException | RuntimeException |
| 编译器 | 强制处理 | 不强制 |
| 根因 | **外部环境**：文件缺失、网络断开、DB 不可用 | **程序 bug**：空指针、越界、参数非法 |
| 谁的责任 | 调用方（环境不可控） | 开发者（代码可修复） |
| 处理方式 | catch/throws | 预防：判空、校验、修逻辑 |
| 可恢复性 | 常可恢复（重试、降级、提示） | 通常不可恢复（要修代码） |
| 传播距离 | 必须显式声明，跨层可见 | 可任意穿透，无需声明 |

```java
// 受检：调用方被迫知道"可能失败"
public void upload(File f) throws IOException { ... }
// 调用方：try-catch 或继续 throws —— 无法假装上传一定成功

// 非受检：失败即 bug
public void send(Message m) {
    if (m == null) throw new IllegalArgumentException("消息不能为 null");
    // 不声明任何异常 —— 调用方无需被迫处理
}
```

**两者的经典类比**（面试讲法）：受检异常像"过安检"——系统强制你检查行李（文件/网络/DB 都可能出问题）；非受检异常像"交通规则"——默认你遵守（代码逻辑正确），违规（bug）时直接处罚（异常）。

## 3. 受检异常的三大弊端

| 弊端 | 表现 | 代价 |
|------|------|------|
| **样板代码污染** | 每个中间方法都要 try-catch 或 throws，`throws IOException` 在调用链上层层复制 | 可读性差，核心逻辑被异常代码淹没 |
| **破坏封装与演进** | 底层方法新增受检异常 → 所有上层方法签名被迫修改 | 违反开闭原则，牵一发动全身 |
| **无法处理也要被迫处理** | 很多受检异常上层根本处理不了，只能"catch 后重抛"或吞掉 | 催生 catch-and-ignore 反模式，比不检查更糟 |

```java
// 层层传递的样板（JDK 老 API 的经典体验）
public void a() throws IOException { b(); }
public void b() throws IOException { c(); }
public void c() throws IOException { Files.readString(path); }
// 新增一层方法就要再复制一行 throws —— 三个方法其实都"处理不了"，纯属传话

// 被迫 catch 却无事可做的反模式（被受检异常逼出来的）
try {
    Files.readString(path);
} catch (IOException e) {
    throw new RuntimeException(e);   // 包装成非受检 —— 最常见的"妥协"
}
```

**JDK 自身的转向**：新 API 大量放弃受检异常——`java.util.zip`、`java.time`、NIO 的许多新方法都抛非受检异常；`Files.readString` 仍受检，但 `Stream`/`Optional`/`CompletableFuture` 的新 API 全是非受检。**趋势明确：新代码默认 RuntimeException**。

> ⚠️ 为什么 Spring/MyBatis 全面转运行时异常（面试必答）：Spring 的 `DataAccessException`、MyBatis 的 `PersistenceException` 都是 RuntimeException——因为 DAO 层异常对 Service 层往往"处理不了"，强制声明只会污染每一层签名；转为运行时后，由**统一拦截器/事务代理**集中处理。

## 4. 2025 年仍在继续的设计之争

受检异常之争是 Java 社区最持久的辩论，2025 年依旧活跃：

**反对派（当代主流观点）**：

- 样板代码、Lambda 不兼容、接口演进困难（见第 3、5 节）；
- 逼出"catch 了不处理"的反模式；
- Kotlin 等新语言直接放弃受检异常；*Effective Java* 与 Spring 均建议 API 用非受检。

**支持派（类型安全视角）**：

- 2025 年仍有文章为受检异常辩护：它把"失败模式"写进签名，相当于 Rust 的 `Result<T, E>` / Haskell 的 `Either` 的**编译期版本**；
- 与 Rust 每处调用都要 `?` 不同，Java 声明一次即可自动传播，复杂方法里更简洁；
- 提出的改进方向：让 Lambda 能声明受检异常、支持泛型异常参数（`<E extends Exception> ... throws E`）。

**最新的活案例（2025-08）**：JDK 25 结构化并发 `StructuredTaskScope.join()` 抛出的 `FailedException` 是 RuntimeException——loom-dev 邮件列表上有人**建议改为受检异常**（因为子任务可能是抛 IOException 的 Callable，编译器应强制调用方面对失败），并提议 `joinUnchecked/joinChecked` 变体。这个讨论本身就是"受检 vs 非受检"的实时样本。

> 🎯 **核心要点**：面试答"受检 vs 非受检"的完整答案 = 机制（编译器强制）+ 哲学（外部失败 vs 程序 bug）+ 趋势（JDK/框架转向非受检）+ 争议（2025 仍在辩论）——能谈出最后一点是明显的加分项。

## 5. Lambda / Stream 与受检异常的冲突

**冲突的本质**：函数式接口的抽象方法**不声明受检异常**（`Runnable.run()`、`Function.apply()` 都是无 throws），而 Lambda 体里又不能"偷偷"抛受检异常——编译器直接报错。

```java
// ❌ 编译错误：File 操作抛 IOException，而 Function.apply 不声明受检异常
List<String> contents = files.stream()
        .map(f -> Files.readString(f))          // unreported exception IOException
        .toList();
```

**三种解法**（各有取舍）：

```java
// 解法 1：包装为运行时异常（最简单，工程首选）
.map(f -> {
    try { return Files.readString(f); }
    catch (IOException e) { throw new UncheckedIOException(e); }   // JDK 内置的包装类
})

// 解法 2：自定义"可抛受检异常的 Supplier"（通用方案）
@FunctionalInterface
interface ThrowingSupplier<T> {
    T get() throws Exception;
}
static <T> Supplier<T> unchecked(ThrowingSupplier<T> s) {
    return () -> { try { return s.get(); } catch (Exception e) { throw new RuntimeException(e); } };
}

// 解法 3：保持受检（极少用）—— 在 Lambda 外 try-catch 包裹整个流
try {
    List<String> r = files.stream().map(this::readStringUnchecked).toList();
} catch (Exception e) { ... }
```

> 💡 JDK 内置了四个"包装成非受检"的官方类：`UncheckedIOException`、`UncheckedParseException`、`UncheckedExecutionException`、`UncheckedIOException`——能用内置就用内置。

## 6. 新 API 设计的共识

**现代 Java 新 API 的设计共识**（JDK 自身 + 社区主流）：

| 场景 | 建议 | 原因 |
|------|------|------|
| 业务/框架 API | **继承 RuntimeException** | 不污染签名、由全局处理器统一收口 |
| 参数校验失败 | `IllegalArgumentException` / `IllegalStateException` | 程序 bug，预防为主 |
| 外部资源失败（IO/网络/DB） | 非受检 + 文档说明语义 | 与 Spring 一致，拦截器统一处理 |
| 极少数"调用方必须处理" | 才用受检 | 如 `InterruptedException`（中断必须被尊重） |
| 状态机非法转换 | 非受检 | 逻辑错误 |

```java
// 现代 API 设计示范：错误通过非受检异常 + 错误码表达
public class OrderService {
    public Order getOrder(String orderId) {
        Objects.requireNonNull(orderId, "orderId 不能为 null");     // 参数校验：IllegalArgumentException
        return orderRepository.findById(orderId)
                .orElseThrow(() -> new OrderNotFoundException(orderId));  // 业务异常：RuntimeException
        // 调用方无需被迫 try-catch —— 全局异常处理器负责转成 404 响应
    }
}
```

> 🎯 **核心要点**：新 API 的默认选择是**非受检异常 + 清晰的语义文档 + 全局统一处理**；受检异常只在"不处理就必然出错"的少数场景保留（中断、关闭等）。这条共识是 06 模块自定义异常设计的基础。
