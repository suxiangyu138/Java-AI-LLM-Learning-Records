## 1. Throwable：一切的根

Java 异常体系的顶层是 `Throwable`（可直接 throw/捕获的唯一类型）。注意两点：

- **类型本身**：`throw` 关键字只接受 `Throwable` 及其子类——`throw new String()` 是编译错误；
- **接口差异**：`Throwable` 实现 `Serializable`（异常可序列化传输），但实践中异常只作进程内传播，跨进程传输应转结构化错误响应（见 06 模块）。

```text
Throwable (java.lang)
├── Error                          —— JVM/系统级问题（不捕获）
│     ├── OutOfMemoryError
│     ├── StackOverflowError
│     ├── NoClassDefFoundError
│     └── AssertionError
└── Exception                      —— 应用级问题
      ├── RuntimeException         —— 非受检（unchecked）
      │     ├── NullPointerException / ArrayIndexOutOfBoundsException
      │     ├── ClassCastException / IllegalArgumentException
      │     └── ArithmeticException / IllegalStateException ...
      └── IOException 等（非 RuntimeException） —— 受检（checked）
            ├── IOException / FileNotFoundException / EOFException
            ├── SQLException / ClassNotFoundException / InterruptedException
            └── ParseException / TimeoutException ...
```

**两个关键判断**：

| 判断 | 规则 |
|------|------|
| 受检？ | 是 `Exception` 的子类且**不是** `RuntimeException` 的子类 |
| 该捕获？ | `Error` 不捕获；`Exception` 按策略捕获 |

> 🎯 **核心要点**：`RuntimeException` 是受检/非受检的**分界线**——这是整个体系最重要的一个类，所有判断都以它为准。

## 2. Error：JVM 级错误，为什么不捕获

**Error 的语义**：JVM 或系统层面的严重故障，程序**无法恢复、无法预期**。

| Error | 含义 | 应对 |
|-------|------|------|
| `OutOfMemoryError` | 堆/元空间等内存耗尽 | 排查泄漏、调 JVM 参数——**不是 catch 能解决的** |
| `StackOverflowError` | 栈溢出（递归无出口等） | 修代码（递归改循环）、调 -Xss |
| `NoClassDefFoundError` | 类加载失败 | 检查类路径/依赖冲突 |
| `AssertionError` | assert 失败 | 修代码 |

**为什么不要捕获 Error**：

1. **捕获了也处理不了**：内存都耗尽了，catch 块本身可能都跑不起来；
2. **掩盖致命信号**：吞掉 OOM 会让系统"带病运行"，后续行为不可预期；
3. **JVM 状态不可信**：Error 出现后堆内存可能已损坏，继续执行业务风险极高。

**唯一的例外**（全局兜底）：在 `UncaughtExceptionHandler` 或监控线程里**记录** Error 用于告警/优雅停机——是"记录并退出"而非"捕获并继续"。

```java
// 反例：试图捕获 OOM 后"继续跑"
try {
    cache.put(key, bigArray);        // 触发 OOM
} catch (OutOfMemoryError e) {       // ❌ 不解决任何问题
    // 空 catch —— 更糟
}
```

> ⚠️ 面试高频陷阱：`catch (Throwable e)` 会连 `Error`、`OutOfMemoryError` 一起捕获——除非是"记日志 + 重启"的最外层防线，否则这是反模式（见 08 模块）。

## 3. Exception：应用级异常与两大家族

**Exception 的语义**：应用程序运行中**可预期、可处理**的问题。两大分支：

| 分支 | 定义 | 编译器 | 典型 | 设计意图 |
|------|------|:------:|------|---------|
| RuntimeException（非受检） | 继承 RuntimeException | 不强制处理 | NPE、越界、参数非法 | **程序 bug**：判空/校验/修逻辑来规避 |
| 其他 Exception（受检） | 继承 Exception 非 RuntimeException | **强制处理**（catch 或 throws） | IO、SQL、中断 | **外部环境**：文件、网络、数据库等不可控因素 |

```java
// 受检异常：编译强制
public String readFile(String path) throws IOException {   // 不声明 → 编译失败
    return Files.readString(Path.of(path));
}

// 非受检异常：不强制
public int divide(int a, int b) {
    return a / b;                 // b=0 时抛 ArithmeticException —— 不声明也能编译
}
```

**两者处理哲学的根本差异**：

- **受检异常**：强制你面对"外部可能失败"——文件可能不存在、网络可能断开；
- **非受检异常**：假定你写对了代码——空指针是 bug，不该用 try-catch 兜，应该修逻辑。

> 🎯 **核心要点**："受检异常用 try-catch 处理、非受检异常用代码逻辑规避"——非受检异常的正确应对是**预防**（判空、参数校验、`Objects.requireNonNull`），而不是到处 try-catch。

## 4. 核心异常类速查

**非受检（RuntimeException 家族）**：

| 异常 | 触发场景 | 预防 |
|------|---------|------|
| NullPointerException | 调用 null 对象的方法/字段 | 判空、Optional、`requireNonNull` |
| ArrayIndexOutOfBoundsException | 数组越界 | 边界检查、增强 for |
| ClassCastException | 向下转型失败 | instanceof 判断 |
| IllegalArgumentException | 参数不合法（最常用） | 参数校验（前置条件） |
| IllegalStateException | 对象状态不合法 | 状态检查 |
| ArithmeticException | 除零等算术错误 | 除数判 0 |
| UnsupportedOperationException | 调用了不支持的操作 | 接口设计时说明 |
| NoSuchElementException | 空集合取元素 | `peek`/`isEmpty` 判断 |

**受检（常见）**：

| 异常 | 场景 | 处理 |
|------|------|------|
| IOException | 文件/网络读写失败 | 重试/降级/提示 |
| FileNotFoundException | 文件不存在 | 提示或兜底 |
| SQLException | 数据库访问失败 | 转数据访问层异常 |
| ClassNotFoundException | 类加载不到 | 检查依赖 |
| InterruptedException | 线程中断 | **恢复中断标志**再处理 |
| ParseException | 解析失败 | 提示输入错误 |
| TimeoutException | 超时 | 重试/降级 |

> 💡 `InterruptedException` 是最容易处理错的受检异常——正确惯例是 catch 后执行 `Thread.currentThread().interrupt()` 恢复中断标志，而不是吞掉（见 07 模块）。

## 5. 异常对象四要素

```java
try {
    throw new BizException("订单不存在", null);   // 先造一个带 cause 的
} catch (BizException e) {
    String msg = e.getMessage();        // ① message：描述
    StackTraceElement[] st = e.getStackTrace();   // ② 堆栈：性能大头
    Throwable cause = e.getCause();     // ③ cause：底层原因链
    Throwable[] suppressed = e.getSuppressed();   // ④ suppressed：被抑制的关闭异常（JDK 7+）
}
```

| 要素 | 说明 | 何时存在 |
|------|------|---------|
| message | 给人看的错误描述，**必须携带上下文**（哪个订单、哪个文件） | 构造时传入 |
| stackTrace | 调用链快照，构造时填充（可 `fillInStackTrace()` 覆盖） | 默认存在 |
| cause | 包装链：`new BizException("...", e)` 时保留底层原因 | 包装时设置 |
| suppressed | TWR 中 close() 失败被"抑制"的异常（见 04 模块） | JDK 7+，特殊场景 |

**异常链的工程价值**：线上排查时 `getCause()` 一路挖到根因——**包装异常不传 cause 等于把根因埋在日志深处**（见 05 模块异常链与 08 模块反模式）。

## 6. 读懂异常堆栈：从堆栈到根因

**异常堆栈是最重要的排障信息**——会读堆栈等于会排查 80% 的问题：

```text
java.lang.NullPointerException: Cannot invoke "String.length()"
        because "user.address.city" is null        ← JDK 15+ 精准消息：直接点名 city 为 null
        at com.example.service.OrderService.calc(OrderService.java:42)   ← 抛出点（最上面的一帧）
        at com.example.web.OrderController.get(OrderController.java:18)  ← 调用链逐帧向下
        at jdk.internal.reflect.NativeMethodAccessorImpl.invoke0(Native Method)
        ...
```

**读堆栈四步法**：

| 步骤 | 动作 | 要点 |
|------|------|------|
| ① 看异常类型 | 第一行 | NPE/IOE/业务异常 → 先分类定位 |
| ② 看消息 | 类型后面 | 精准 NPE 消息（JDK 15+）直接给答案 |
| ③ 看堆栈最上帧 | 第一个 `at` 行 | **抛出点**——问题发生在哪个类哪一行 |
| ④ 找"自己的代码" | 过滤框架帧 | `at com.example.*` 才是业务代码，`at java.*`/`at org.*` 多为传播经过 |

**堆栈的三个进阶认知**：

1. **cause 链要一路看完**：`Caused by:` 段是根因——异常可能被包装多层，**最底层的 Caused by 才是病根**（SQL 语句、文件路径通常在这里）；
2. **suppressed 别忽略**：`Suppressed:` 段（TWR 关闭失败）常藏着资源泄漏线索（见 04 模块）；
3. **堆栈是出生快照**：异常被创建时记录调用链，传播到哪都不变——所以"在哪抛的"永远指得出来。

```java
// 实操：日志里如何完整保留三层信息（类型/消息/堆栈）
catch (Exception e) {
    log.error("订单处理失败, orderId={}", orderId, e);
    // 输出含：异常类型 + 精准消息 + 完整堆栈 + Caused by 链 + Suppressed
}
```

> 🎯 **核心要点**：读堆栈的顺序是"**类型 → 消息 → 最上业务帧 → cause 链**"——框架帧是噪音，自己代码的最上帧 + 最底层 Caused by 才是定位组合。

## 7. 受检/非受检的黄金判断标准

**一句话判断法**：`X instanceof RuntimeException` → 非受检；否则若 `X instanceof Exception` → 受检；`Error` 单独一类。

```java
// 自写一个异常，如何判断？
class MyException extends Exception { }              // 受检（必须处理）
class MyRuntime extends RuntimeException { }         // 非受检（不强制）
class MyError extends Error { }                      // Error 系（不捕获）

// 判断链：
// Throwable → Exception → RuntimeException → 非受检
//             → 其他       → 受检
//         → Error              → 不捕获
```

**两个容易混淆的"看起来像"**：

| 直觉 | 实际 |
|------|------|
| `ClassCastException` 名字不带 Runtime → 以为是受检 | ✅ 它继承 RuntimeException → 非受检 |
| `InterruptedException` 名字带"异常"但经常被 try-catch → 受检 | ✅ 编译器强制 |

> 🎯 **核心要点**：判断标准只有一条——**继承链上有没有 RuntimeException**，与名字、场景无关。这是面试选择题的第一判据。
