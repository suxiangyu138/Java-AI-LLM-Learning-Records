## 1. 必背考点：十问

### 1.1 Error 与 Exception 的区别？

**答题链**：层次（JVM/系统级 vs 应用级）→ 可恢复性（不可恢复 vs 可预期可处理）→ 处理方式（不捕获 vs 按策略）→ 例外（全局兜底记录 Error 用于告警，但"记录并退出"而非"捕获并继续"）。

### 1.2 受检异常与非受检异常的区别？

**答题链**：判断标准（是否继承 RuntimeException）→ 编译器检查（强制 vs 不强制）→ 根因定位（外部环境 vs 程序 bug）→ 处理哲学（catch/throws vs 预防规避）→ 现代趋势（JDK/Spring 转向运行时，见 02 模块第 4 节设计之争）。

### 1.3 try-catch-finally 中 return 的执行顺序？

**答题链**：try 中 return 先**快照返回值** → 执行 finally → 返回快照 → finally 修改基本类型不影响、修改引用对象内容影响 → **finally 中 return 覆盖一切（禁止）**。字节码视角：finally 内联在 return 指令之前。

### 1.4 finally 什么时候不执行？

`System.exit(0)`、JVM 崩溃/断电、执行 finally 的线程被杀死——只有"JVM 或线程没了"才不执行；return/抛异常/break 都阻止不了。

### 1.5 try-with-resources 的原理？

**答题链**：语法（try 头声明 AutoCloseable）→ 编译器展开（隐式 finally + 主异常优先）→ 逆序关闭（先开后关）→ close 失败挂 **suppressed**（`getSuppressed()`）→ JDK 9 增强（引用外部 effectively final 变量）→ 2025 动态（Process 拟实现 AutoCloseable，JDK-8364361）。

### 1.6 为什么业务异常通常继承 RuntimeException？

**答题链**：签名污染（受检异常层层 throws）→ 上层处理不了被迫 catch-and-ignore → **Spring 事务默认按 RuntimeException 回滚** → 全局异常处理器统一收口 → 与 Lambda/Stream 兼容。

### 1.7 自定义异常怎么设计？

**答题链**：命名（XxxException 结尾）→ 继承（模块基类 + 具体异常）→ 构造器覆盖（无参/message/cause）→ **错误码（枚举）** → 上下文字段（orderId 等）→ 全局处理器分级映射。

### 1.8 线程池任务抛异常会怎样？

**答题链**：execute 走 UncaughtExceptionHandler（默认 stderr）→ submit 包进 Future（get 时 ExecutionException，**必须 getCause() 解包**）→ fire-and-forget 的 submit 异常静默丢失 → 线程本身不受影响继续复用。

### 1.9 怎么拿到子线程的异常？

**答题链**：三个通道——① 任务用 submit + get 捕获；② 设置 Thread.setDefaultUncaughtExceptionHandler 全局兜底；③ 结构化并发（JDK 23+）join 时聚合（JDK 25 抛 FailedException）。

### 1.10 异常性能为什么慢？怎么优化？

**答题链**：构造时 fillInStackTrace 捕获全栈（参考量级：10 万次正常 ~5ms vs 异常 ~180ms）→ 治本：不用异常做流程控制（先判断）→ 治标：重写 fillInStackTrace 跳过堆栈（仅限信号型异常）→ JIT 逃逸分析的现代视角。

## 2. 高频陷阱题 10 连问

1. **结果**：try 中 `return 1`，finally 中 `return 2`，方法返回几？（2——finally 覆盖；且 try 抛异常时也会被吞）
2. **对错**：`catch (IOException | FileNotFoundException e)` 能编译吗？（❌ 父子类型不能 multi-catch）
3. **结果**：`System.exit(0)` 后 finally 执行吗？（不执行）
4. **对错**：finally 修改基本类型返回值会影响最终返回。（❌ 快照机制）
5. **结果**：`catch (Exception e)` 能捕获 OutOfMemoryError 吗？（不能——Error 不是 Exception 的子类）
6. **对错**：子线程抛异常，父线程 try-catch 能捕获。（❌ 线程隔离，走 UncaughtExceptionHandler）
7. **结果**：`new BizException(e.getMessage())` 有什么问题？（丢 cause/堆栈——异常链断裂）
8. **对错**：try-with-resources 中资源按声明顺序关闭。（❌ 逆序，LIFO）
9. **结果**：`Future.get()` 抛 ExecutionException，真实异常在哪？（`getCause()`——直接 getMessage 拿到的是包装消息）
10. **对错**：`catch (Throwable t)` 是防御性编程。（❌ 反模式：连 OOM 一起吞）

## 3. 场景题：设计一个完整的异常体系

**题目**：给一个订单微服务设计异常体系，要求前后端可协作、可排查、可扩展。

**答题框架**（按评分点展开）：

```text
① 基础类分层：
   RuntimeException
   ├── BusinessException（code + message）   —— 业务失败（4xx）
   └── SystemException（message + cause）     —— 基础设施失败（5xx）

② 模块化：OrderException extends BusinessException
   ├── OrderNotFoundException（orderId 上下文）
   └── OrderStatusException（状态转换非法）

③ 错误码枚举：ErrorCode（ORDER_NOT_FOUND / ORDER_ALREADY_SHIPPED / PAY_...）
   —— 分段约定（1000 通用 / 2000 订单 / 3000 支付），新增只增不改

④ 全局处理器 @RestControllerAdvice：
   - 业务异常 → 400 + code + message
   - 参数校验 → 400 + PARAM_INVALID
   - 未预期异常 → 500 + 安全消息 + 完整日志

⑤ 契约：ErrorResponse(code, message, traceId, timestamp)
   —— traceId 关联日志，前端按 code 分支

⑥ 加分点：说清三个设计决策——
   为什么继承 RuntimeException（事务回滚 + 签名干净 + 全局收口）
   为什么错误码用枚举（类型安全 + 集中管理）
   为什么响应不暴露堆栈（安全 + 契约稳定）
```

## 4. 扩展追问：五道连环题

### 4.1 异常和错误码怎么选？（什么时候抛异常、什么时候返回错误码）

**答题链**：异常 = 罕见的、非预期分支（业务规则失败、环境失败）→ 错误码/返回值 = 预期的、高频分支（参数校验、查找失败返回 Optional）→ 性能视角（异常创建昂贵）→ 语义视角（异常带堆栈可排查；错误码是契约）→ **混合实践**：高频预期失败用返回值/Optional，低频非预期失败抛异常，全局统一转错误码响应。

### 4.2 为什么 Lambda 不能抛受检异常？

**答题链**：函数式接口的抽象方法不声明 throws → Lambda 体抛受检异常编译错误 → 解法：包装（UncheckedIOException 等官方类）、自定义 Throwing 接口、外层 try-catch。

### 4.3 Spring 事务为什么会回滚？受检异常为什么不回滚？

**答题链**：Spring 默认基于代理捕获 RuntimeException/Error → 触发事务回滚 → 受检异常默认提交（业务上"IO 失败但事务数据要保留"）→ 需要受检也回滚用 `@Transactional(rollbackFor = Exception.class)`。

### 4.4 线上异常排查的完整流程？

**答题链**：错误码分段定位模块 → 日志按 traceId 检索完整链路 → 看异常 cause 链挖根因 → 检查 suppressed（资源关闭失败）→ 结合监控（异常率、OOM 告警）→ 复现与修复 → 补测试（assertThrows）。

### 4.5 怎么让异常"看起来专业"？

**答题链**：消息带上下文（谁、什么、哪个 ID）→ 错误码稳定可文档化 → 包装保留 cause → 每层只包装一次 → 日志一次带全堆栈 → 不暴露内部实现细节（堆栈、SQL）给外部。

## 5. 面试加分项：异常处理的架构视角

面试官问完机制题后，常会追问"你们项目怎么做的"——以下三个架构视角是区分度来源：

### 5.1 全局异常处理的演进路线

```text
阶段 1：每个方法 try-catch + 手动转响应（重复代码、错误处理不统一）
阶段 2：AOP 统一异常拦截（@AfterThrowing 切面）—— 集中但侵入
阶段 3：Spring MVC 的 @ExceptionHandler + @ControllerAdvice（现代主流）
阶段 4：网关层统一错误码映射 + 服务层业务异常 + traceId 全链路（微服务时代）
```

**答法示范**："我们服务内用 @RestControllerAdvice 收口，错误码枚举分模块管理；网关层再做一次 HTTP 状态码与错误码的映射——服务内不关心 HTTP 协议，网关不关心业务语义。"

### 5.2 异常与可观测性（告警设计）

| 异常类型 | 告警策略 | 示例 |
|---------|---------|------|
| 业务异常（4xx 语义） | 不告警（预期失败） | 订单不存在、参数非法 |
| 系统异常（5xx 语义） | **按阈值告警** | DB 连接失败次数超 N |
| Error 级 | 立即告警 | OOM 出现即告警 + 堆转储 |
| 静默吞异常 | 无法告警（要治本） | 反模式治理 |

**答法要点**：告警不是"有异常就报"——**业务异常是正常流程的组成部分**，只有系统异常与 Error 才是告警对象；异常率（ERROR 日志量/请求量）比异常绝对数更有监控价值。

### 5.3 异常降级与容错

```java
// 容错三层：捕获 → 降级 → 兜底
public Order getOrder(String id) {
    try {
        return orderClient.fetch(id);            // 主路径：远程调用
    } catch (OrderServiceTimeoutException e) {   // 第一层：特定失败重试
        return orderClient.fetch(id);
    } catch (RemoteException e) {                // 第二层：降级到缓存
        Order cached = orderCache.get(id);
        if (cached != null) return cached;
        throw new OrderUnavailableException(id, e);  // 第三层：兜底失败，明确报错
    }
}
```

**答法要点**：降级链条的每一层都要**可解释**（为什么这层能兜住）+ **可观测**（降级命中要记指标），"降级了还不告诉任何人"等于没降级。

> 🎯 **核心要点**：架构视角的答题公式 = **演进路线（见过程）+ 分层职责（服务/网关）+ 可观测性（告警阈值）+ 容错链条（捕获→降级→兜底）**——能把这个框架讲清楚，异常处理就从"语法题"升维为"设计题"。

## 6. 记忆口诀

```text
Throwable 分两支：Error 认命不捕获，Exception 要处理。
受检不检看父类：Runtime 分界线，外部失败受检、逻辑 bug 运行时。
finally 必执行：JVM 没了才例外；return 快照在前，finally 别写 return。
资源管理用 TWR：逆序关闭 suppressed，主异常在前关异常挂。
包装保留 cause，消息带上上下文；能恢复就捕获，不能就包装，再不行就透传。
错误码枚举分段管，全局处理器收口；业务异常运行时，事务回滚靠它撑。
线程异常三通道：Handler、Future、结构化；中断标志必须恢复。
不用异常做流程，循环判断优先；日志一次全堆栈，traceId 串联全场。
```
