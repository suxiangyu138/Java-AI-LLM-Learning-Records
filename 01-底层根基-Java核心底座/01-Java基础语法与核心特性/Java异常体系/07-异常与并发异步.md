## 1. 线程中的异常去向：UncaughtExceptionHandler

**核心事实**：异常沿"调用栈"传播，而每个线程有自己的栈——**线程内的异常不会传播到启动它的线程**：

```java
public static void main(String[] args) {
    new Thread(() -> {
        throw new RuntimeException("子线程炸了");
    }).start();
    // main 里的 try-catch 完全接不住子线程的异常：
    // 子线程异常 → 线程结束 → 异常传给 UncaughtExceptionHandler（默认打印到 stderr）
    System.out.println("main 继续执行");      // ✅ 照常执行，子线程的异常不会中断 main
}
```

**异常去向链**（`Thread.dispatchUncaughtException`）：

```text
子线程抛出未捕获异常
→ Thread.uncaughtExceptionHandler（本线程自定义）
→ ThreadGroup.uncaughtException（默认 handler）
→ 打印堆栈到 stderr（默认行为 —— 线上经常"消失"的异常就是被这里吞掉的）
```

**正确姿势：设置全局 handler，让异常可观测**：

```java
// 全局兜底（应用启动时设置一次）
Thread.setDefaultUncaughtExceptionHandler((t, e) -> {
    log.error("线程 {} 未捕获异常", t.getName(), e);   // 记日志 + 告警
    // 可选择：优雅停机 / 重启线程
});

// 单线程自定义
Thread t = new Thread(task);
t.setUncaughtExceptionHandler((th, e) -> log.error("自定义处理", e));
```

> 🎯 **核心要点**：**"子线程异常"不会出现在父线程的 try-catch 里**——这是并发异常处理的第一性原理。让异常可观测的唯一办法：UncaughtExceptionHandler、任务结果捕获（下节）、或结构化并发（第 5 节）。

## 2. 线程池任务异常的三种处理

线程池吞异常的经典场景：`execute(Runnable)` 的任务异常走 UncaughtExceptionHandler；`submit(Callable)` 的异常被封装进 Future——**get() 之前谁都看不见**：

```java
ExecutorService pool = Executors.newFixedThreadPool(2);

// 方式 1：submit + Future.get() —— 异常在 get 时以 ExecutionException 抛出
Future<Integer> f = pool.submit(() -> { throw new RuntimeException("任务失败"); });
try {
    f.get();
} catch (ExecutionException e) {
    Throwable cause = e.getCause();        // ✅ 真正的任务异常在这里（必须解包！）
    log.error("任务执行失败", cause);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();    // 恢复中断
}

// 方式 2：execute(Runnable) —— 异常走线程的 UncaughtExceptionHandler（见第 1 节）
pool.execute(() -> { throw new RuntimeException("任务失败"); });   // 默认只打印 stderr，线上易丢

// 方式 3：包装任务 —— 捕获后转日志/回调（线程池内部兜底）
pool.execute(() -> {
    try { doWork(); }
    catch (Exception e) { log.error("任务异常", e); throw e; }     // 记录后原样重抛
});
```

**三个要点**：

| 要点 | 说明 |
|------|------|
| ExecutionException 必须解包 | 用 `getCause()` 拿真实异常，直接 `e.getMessage()` 拿到的是包装消息 |
| execute 与 submit 通道不同 | execute 走 Handler，submit 走 Future——按需选择 |
| 线程池不会因任务异常死亡 | 任务异常只影响该任务，线程继续复用——**但异常若无人查看=静默丢失** |

> ⚠️ **最隐蔽的坑**：`submit` 后从不 `get()`（Fire-and-forget）——任务异常永远藏在 Future 里，线上表现为"任务没执行"，排查无从下手。

## 3. CompletableFuture 的异常管道

CompletableFuture 把异常变成**管道中的一等公民**——异常沿着依赖链传递，直到被处理：

```java
CompletableFuture.supplyAsync(() -> fetchData())        // ① 可能抛异常
        .thenApply(data -> parse(data))                  // ② 正常数据继续
        .thenApply(parsed -> save(parsed))
        .exceptionally(e -> {                            // ③ 任一步骤抛异常 → 汇聚到这里
            log.error("处理失败", e.getCause());          // 注意：异常在 cause 里（CompletionException 包装）
            return FALLBACK_DATA;                        // 返回降级值，链条继续
        });

// 或者：显式处理
future.whenComplete((result, ex) -> {
    if (ex != null) {
        Throwable cause = ex instanceof CompletionException ? ex.getCause() : ex;
        log.error("异步失败", cause);
    }
});
```

**异常包装规则**（必须记住）：

| 情况 | 异常形态 |
|------|---------|
| supplyAsync/thenApply 等链式方法内部异常 | 包装为 **CompletionException**（`getCause()` 取真实异常） |
| handle 方法 | 直接接收异常参数（无包装） |
| join() 获取 | 抛 CompletionException；`get()` 抛 ExecutionException |

**处理方式速查**：

| 方法 | 行为 |
|------|------|
| `exceptionally(fn)` | 异常时返回降级值，链条继续（推荐） |
| `handle(fn)` | 成功/失败都处理，返回新结果 |
| `whenComplete(fn)` | 只观察，不改结果 |
| `completeExceptionally(ex)` | 手动让 future 失败 |

> 🎯 **核心要点**：异步管道里异常是**流动的**——用 `exceptionally` 在合适的位置"接住"并降级，用 `whenComplete` 记录，绝不默默让异常漂到无人区。**解包纪律**：拿到 CompletionException/ExecutionException 必取 `getCause()`。

## 4. 虚拟线程（JDK 21）的异常传播

**JDK 21（JEP 444 转正）虚拟线程**改变了异常传播的两个方面：

1. **未捕获异常不杀载体线程**：传统平台线程的未捕获异常会结束线程；虚拟线程的异常**路由到它的 UncaughtExceptionHandler**，底层载体线程（平台线程）不受影响，继续服务其他虚拟线程；

```java
// 每个虚拟线程抛异常，只会"自己结束"，不会波及线程池里的其他任务
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1000; i++) {
        executor.submit(() -> {
            if (Math.random() < 0.1) throw new RuntimeException("部分任务失败");
            return ok();
        });
        // 失败任务的异常：在 Future 里（submit）或 Handler（execute）
    }
}
```

2. **ThreadLocal 语义**：虚拟线程的 ThreadLocal 与平台线程不同（建议改用 ScopedValue，JDK 24 预览 / JDK 25 第四次预览）——异常处理代码若依赖 ThreadLocal 传递上下文（如 MDC），需要同步适配。

**对异常代码的实践影响**：

- 线程池 + 虚拟线程的**异常处理 API 不变**（还是 Handler / Future 那套）；
- 高并发下"异常只打印 stderr 就消失"的问题被放大（虚拟线程数量巨大）——**全局 UncaughtExceptionHandler + 日志是硬要求**；
- 阻塞操作（IO 等待）在虚拟线程上不再占用平台线程——但**异常处理不要阻塞**（如 catch 里做同步远程调用告警）。

> 💡 虚拟线程时代"用线程做并发的成本"趋近于零，但"异常可观测"的纪律反而更重要——任务量大了，藏起来的异常只会更多。

## 5. 结构化并发：StructuredTaskScope 与 FailedException

**JDK 23 转正（JEP 481）** 的结构化并发，把"子任务生命周期 + 异常聚合"交给语言：

```java
// 结构化并发：子任务异常在 join 时统一聚合
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Future<String> user = scope.fork(() -> fetchUser());      // 子任务
    Future<String> order = scope.fork(() -> fetchOrder());

    scope.join();                    // JDK 25 起：失败时抛 FailedException（RuntimeException）
    scope.throwIfFailed();           // 任一子任务失败 → 抛第一个失败异常（可选）
    // 全部成功才继续
    return new Response(user.resultNow(), order.resultNow());
}
```

**JDK 25 的 FailedException（时效性重点）**：

- `StructuredTaskScope.join()` 失败时抛 `FailedException`（RuntimeException），`getCause()` 是实际失败原因；
- 这是 2025 年受检/非受检之争的最新实例——loom-dev 有开发者主张它应该是**受检异常**（子任务可能是抛 IOException 的 Callable），提议 `joinUnchecked/joinChecked` 变体——**讨论仍在进行，未来可能调整**；
- 与旧模型对比：`Future.get()` 的 ExecutionException 需要每个调用方手动处理，结构化并发把"所有子任务的失败"收敛到 join 一处。

> 🎯 **核心要点**：结构化并发的异常哲学是"**要么全部成功，要么快速失败**"（ShutdownOnFailure 会在任一子任务失败时取消其他子任务）——异常从"散落各线程"变成"在 join 点集中"，配合 TWR 保证 scope 必然关闭。

## 6. 中断与 InterruptedException 的处理纪律

**InterruptedException 是最容易处理错的受检异常**——三条纪律：

```java
// 纪律 1：恢复中断标志（吞中断 = 自杀）
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();     // ✅ 恢复标志：让上层/调用方知道线程被要求中断
    throw new BizException("任务被中断", e); // 同时上抛（能抛则抛）
}
// ❌ 反例：catch (InterruptedException e) { }  —— 静默吞掉，线程"假装没被中断"，无法协作停机

// 纪律 2：能上抛就上抛（方法签名加 throws InterruptedException）
public void work() throws InterruptedException { Thread.sleep(100); }

// 纪律 3：Lambda/包装场景用"恢复 + 包装"（见 02 模块 Lambda 冲突）
executor.submit(() -> {
    try { Thread.sleep(100); }
    catch (InterruptedException e) { Thread.currentThread().interrupt(); throw new RuntimeException(e); }
});
```

**为什么恢复标志如此重要**：中断是线程协作停机的机制——`shutdownNow()`、超时、取消都通过"置中断标志"通知线程。吞掉 InterruptedException 等于**拒绝协作停机**，在优雅停机、任务取消场景下会造成线程无法退出。

> 🎯 **核心要点**：处理 InterruptedException 的黄金三连：**恢复标志 → 记录/上抛 → 交由上层决策**。任何一步缺失（尤其是吞掉）都是反模式。
