## 1. 十种反模式清单

| # | 反模式 | 表现 | 后果 | 正解 |
|:-:|--------|------|------|------|
| 1 | **空 catch 吞异常** | `catch (Exception e) { }` | 故障完全隐藏，线上"莫名不对" | 至少记录日志（带堆栈） |
| 2 | **捕获 Throwable/Error** | `catch (Throwable e)` | OOM 等致命错误被掩盖 | 只捕具体的 Exception 子类 |
| 3 | **捕获过于宽泛** | `catch (Exception e)` 处理一切 | 逻辑错误（NPE）也被当业务失败 | 捕获最具体的类型 |
| 4 | **finally 中 return/throw** | 见 03 模块第 3 节 | 覆盖返回值、吞异常 | finally 只做清理 |
| 5 | **打印后重抛** | `e.printStackTrace(); throw e;` | 日志重复、堆栈两处 | 记录一次，或包装后抛 |
| 6 | **丢 cause** | `new XxxException(e.getMessage())` | 底层根因丢失 | `new XxxException(msg, e)` |
| 7 | **用异常做流程控制** | 循环内 try-catch 判断"是否存在" | 性能灾难（见第 2 节） | 先判断/contains/判空 |
| 8 | **异常消息无上下文** | `throw new XxxException("失败")` | 无法定位哪个资源哪个用户 | 消息带 ID/路径等上下文 |
| 9 | **方法抛通用 Exception** | `throws Exception` | 调用方无法精准处理 | 抛具体类型或自定义异常 |
| 10 | **日志泄露敏感信息** | 异常消息含密码/身份证 | 安全风险 | 脱敏后再记 |

```java
// 反模式 7 演示：用异常做流程控制
// ❌ 每次循环迭代都构造异常 + 填堆栈 —— 10 万次 = 性能灾难
for (String id : ids) {
    try { orderService.get(id); } catch (OrderNotFoundException e) { continue; }
}
// ✅ 有 contains/判空就用判断；必须探测存在性时先查集合/用 Optional
```

> 🎯 **核心要点**：十条反模式的共同本质——**把异常当作"不可见的分支"或"廉价的信号"**。异常是"稀有且重要"的信息通道，必须：稀有地抛、具体地捕、完整地记。

## 2. 异常性能：创建开销与热点路径优化

**异常为什么慢**：构造时 `fillInStackTrace()` 捕获完整调用栈（遍历栈帧）——实测参考：

| 场景 | 耗时（10 万次） |
|------|:---------------:|
| 正常流程（无异常） | ~5ms |
| 抛异常并捕获 | ~180ms（约 36 倍） |

（数据来自社区基准测试，量级参考；具体数字随 JVM 与调用深度变化）

**优化手段**（按性价比排序）：

```java
// 手段 1：不用异常做流程控制（治本，见反模式 7）
// 手段 2：预判避免异常
if (map.containsKey(key)) return map.get(key);     // 而不是 catch NoSuchElementException
// 手段 3：延迟填充堆栈（治标）—— 已知"此异常只做信号不排障"时
public class LightException extends RuntimeException {
    @Override
    public synchronized Throwable fillInStackTrace() {
        return this;                     // 跳过堆栈捕获（构造开销大幅下降）
        // 代价：没有堆栈 —— 只能用于"状态信号"型异常，不能用于真正要排查的异常
    }
}
// 手段 4：堆栈只留帧数限制（JDK 21+ 可用 StackWalker 可控抓取，见第 4 节）
```

**热点路径的工程判断**：

| 场景 | 策略 |
|------|------|
| 参数校验失败（高频） | 返回错误码/`null`/Optional——不要抛异常 |
| 业务规则失败（低频） | 抛业务异常（频率低，成本可忽略） |
| 循环内的条件判断 | **先判断再操作**（contains/判空） |
| 批量处理中的单条失败 | 收集错误清单返回，不逐条抛 |

> ⚠️ **JIT 的现代视角**：异常创建本身经过逃逸分析后可能被优化（不实际填充堆栈），热点路径的真实成本取决于 JVM 优化状态——**但不要依赖这个不确定的优化**，设计上就不该用异常表达"预期中的分支"。

## 3. 日志纪律：一次记录、带上下文

**异常日志的黄金法则：每个异常恰好记录一次，且带足上下文**：

| 法则 | 说明 | 反例 |
|------|------|------|
| 一次记录 | 同一异常只 log 一次（记录后不要原样重抛再被上层记录） | 每层 catch 都 log → 同一堆栈 5 份 |
| 带上下文 | 消息里给"谁、什么、哪个" | `log.error("处理失败")` 无信息量 |
| 用占位符 | `log.error("订单 {} 处理失败", orderId, e)` 惰性求值 | 字符串拼接（无谓开销） |
| 全堆栈 | 传异常对象（最后一个参数）而非 `e.getMessage()` | 只记消息 → 无法定位代码行 |

```java
// ✅ 标准写法：上下文 + 完整堆栈 + 一次
catch (DataAccessException e) {
    log.error("订单 {} 支付回调落库失败, 渠道={}, 尝试次数={}", orderId, channel, retryCount, e);
    throw new PayException(ErrorCode.PAY_PERSIST_FAILED, "支付结果保存失败", e);
}

// ❌ 反例 1：每层都记
// ❌ 反例 2：只记消息
log.error("失败: " + e.getMessage());      // 堆栈没了，查不到代码行
```

**"记录后重抛"的正确姿势**：要么 `log + throw new 包装异常`（新异常由更高层记录）；要么只 `throw`（不 log，由全局处理器统一记录）——**二选一，绝不重复**。

**traceId 关联**（与 06 模块呼应）：日志框架 MDC 自动注入 traceId，异常堆栈自带追踪标识：

```java
// 入口过滤器：MDC.put("traceId", traceId);
// 异常日志自动带上 traceId → 按 traceId 检索完整调用链
log.error("订单处理异常, traceId={}", MDC.get("traceId"), e);
```

## 4. 现代工具：精准 NPE / StackWalker / 模式匹配

### 4.1 精准 NPE 消息（JDK 15+ 默认开启）

JDK 15（JEP 358 转正，默认开启）起，NPE 消息自动指出"哪个表达式、哪个字段为 null"：

```java
// JDK 14 前：java.lang.NullPointerException（只有一行，全靠猜）
// JDK 15+：
// Exception in thread "main" java.lang.NullPointerException:
//     Cannot invoke "String.length()" because "user.address.city" is null
//                                  ↑ 精确定位到 city 为 null
String len = user.getAddress().getCity().length();   // NPE 消息直接说清链条
```

> 💡 配合 `-XX:+ShowCodeDetailsInExceptionMessages`（默认开）可显示更多细节；这在排查"深链调用 NPE"时省去大量逐层猜测。

### 4.2 StackWalker（JDK 9+）：惰性、可过滤的堆栈

`getStackTrace()` 会**急切**捕获整条栈（成本高）；`StackWalker` **按需遍历、可过滤、线程安全**：

```java
// 旧：e.getStackTrace() 全量拷贝
// 新：只取需要的帧（APM/日志场景性能关键）
String caller = StackWalker.getInstance()
        .walk(frames -> frames
                .filter(f -> f.getClassName().startsWith("com.example"))
                .findFirst()
                .map(StackWalker.StackFrame::getMethodName)
                .orElse("unknown"));
```

### 4.3 模式匹配处理异常载荷（JDK 21+）

record + 模式匹配让异常的分支处理更干净（与 `Java面向对象/08` 衔接）：

```java
// 传统：instanceof + 强转
catch (Exception e) {
    if (e instanceof BusinessException be) {
        return ErrorResponse.of(be.errorCode(), be.getMessage());
    } else if (e instanceof DataAccessException) {
        return ErrorResponse.of("SYSTEM_ERROR", "数据库繁忙");
    }
    ...
}

// JDK 21+：switch 模式匹配 + 密封异常（若异常层次 sealed）
public ErrorResponse toResponse(Exception e) {
    return switch (e) {
        case BusinessException be when be.errorCode() == ErrorCode.UNAUTHORIZED
                -> ErrorResponse.of(401, "未登录");
        case BusinessException be -> ErrorResponse.of(be.errorCode(), be.getMessage());
        case DataAccessException dae -> ErrorResponse.of("SYSTEM_ERROR", "数据服务异常");
        case null -> ErrorResponse.of("SYSTEM_ERROR", "未知错误");
        default -> ErrorResponse.of("SYSTEM_ERROR", "系统繁忙");
    };
}
```

> 🎯 **核心要点**：现代异常处理的工具箱在升级——精准 NPE 免去逐层猜、StackWalker 让堆栈采集可控、模式匹配让多类型异常处理可穷尽。**"老工具 + 新语法"的组合是 2025 年面试的加分项**。

## 5. 与阿里巴巴 Java 开发手册规约衔接

**阿里巴巴 Java 开发手册（异常处理章节）核心规约**（与 `Java代码规范/05-异常处理与日志规范.md` 联动）：

| 规约 | 要点 | 本体系对应 |
|------|------|-----------|
| 【强制】finally 中禁止 return | 覆盖返回值与异常 | 03 模块第 3 节 |
| 【强制】异常不要用于流程控制 | 条件判断优先 | 08 模块第 2 节 |
| 【强制】catch 后必须处理或向上抛 | 空 catch 是重罪 | 08 模块第 1 节 |
| 【强制】捕获 Throwable 禁止 | 只捕 Exception 体系 | 01 模块第 2 节 |
| 【推荐】方法不要抛通用 Exception | 精准异常类型 | 08 模块第 1 节 |
| 【推荐】日志至少记录异常全堆栈 | 不用 `getMessage()` 代替 | 08 模块第 3 节 |
| 【参考】返回 null 不抛异常 | Optional / 空集合 | 02 模块第 6 节 |

> 🎯 **核心要点**：规约是对"本模块反模式清单"的制度化——**先懂为什么（机制），再背规约（纪律）**，两者结合才不会"背了规约还是踩坑"。
