## 1. 树化的目的

> **背景**：哈希冲突极端场景下链表退化 O(n)——树化把最坏情况从 O(n) 降到 O(log n)。
> **目的**：理解树化是「防极端」而非常规路径。
> **适用范围**：长冲突链的桶（恶意 key/差 hashCode）。

```text
树化的价值
├── ① 最坏情况优化：O(n) → O(log n)
│   ├── 链表 1000 个：查 1000 次
│   └── 红黑树 1000 个：查 10 次（log2 1000）
├── ② 防哈希碰撞攻击：恶意 key 同 hash → 桶退化
│   ├── 无树化：O(n) 查询（DoS 风险）
│   └── 有树化：O(log n)（可控）
└── ③ 定位：树化是「保险丝」不是「主路径」
    ├── 正常使用：链表 ≥8 概率千万分之六
    └── 触发即异常场景（极端冲突）
```

## 2. 树化双条件

> ⚠️ **树化双条件（面试陷阱）**：链表长度 ≥ 8 **且** 容量 ≥ 64——只满足长度会先扩容：

```java
// 源码（putVal 中）
if (binCount >= TREEIFY_THRESHOLD - 1)   // binCount ≥ 7（即链表 ≥8）
    treeifyBin(tab, hash);

final void treeifyBin(Node<K, V>[] tab, int hash) {
    int n, index;
    // 条件 2：容量 < 64 → 先扩容（不树化！）
    if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)
        resize();                        // 扩容（元素分散）
    else if ((e = tab[index = (n - 1) & hash]) != null) {
        // 链表 → 红黑树转换
    }
}
```

```text
双条件的逻辑
├── ① 条件 1：链表长度 ≥ 8（TREEIFY_THRESHOLD）
├── ② 条件 2：数组容量 ≥ 64（MIN_TREEIFY_CAPACITY）
├── ③ 容量 < 64 时：先扩容（为什么？）
│   ├── 扩容后元素分散（冲突减少）
│   ├── 树化成本 > 扩容收益（小容量时）
│   └── 一句话：小数组「分散」比「树化」更划算
└── ④ 面试答法：两个条件缺一不可（只说 8 是错的）
```

## 3. 为什么阈值是 8

> 🎯 **阈值 8 的依据：泊松分布**——负载因子 0.75 时链表长度 8 的概率极低（< 千万分之一）：

```text
泊松分布（λ = 0.5 时桶内元素概率）
├── 长度 0：约 60.7%
├── 长度 1：约 30.3%
├── 长度 2：约 7.6%
├── 长度 3：约 1.2%
├── 长度 4：约 0.15%
├── 长度 5：约 0.015%
├── 长度 6：约 0.001%
├── 长度 7：约 0.00009%
├── 长度 8：约 0.00000006（千万分之六）
└── 结论：正常使用链表 ≥8 几乎不可能

两个「8」的意义
├── ① 概率依据：正常场景到不了 8（树化几乎不触发）
├── ② 安全兜底：真到 8 = 异常冲突 → 树化防退化
└── ③ 金句：8 是「正常与异常」的分界线（数学依据）
```

---

## 4. 为什么退化阈值是 6

> 🎯 **退化阈值 6（UNTREEIFY_THRESHOLD）**——与 8 形成 6-8 缓冲区间，防边界震荡：

```text
为什么 6 而不是 7
├── ① 缓冲区间（6-8）：防「树化↔退化」频繁切换
│   ├── 若退化也是 8：元素在 7/8 间波动 → 反复转换
│   ├── 转换成本高（树 ↔ 链表重建）
│   └── 6-8 留 1 个元素缓冲
├── ② 6 与 8 差 2：实际工程「滞回」（Hysteresis）
│   ├── 类似比较器中的死区
│   └── 避免抖动
└── ③ 金句：6 和 8 是「防震荡」的设计（不是随意数字）

退化触发
├── ① 树节点 ≤ 6（删除/拆分后）
├── ② 扩容树拆分后节点少（split）
└── ③ 退化为链表（恢复常规路径）
```

## 5. 为什么用红黑树而非 AVL

> 🎯 **红黑树 vs AVL 的选择**——HashMap 场景下红黑树更合适：

| 维度 | 红黑树 | AVL 树 |
|------|:---:|:---:|
| 平衡度 | 宽松（黑高平衡） | 严格（左右高差 ≤1） |
| 查询 | O(log n)（略慢） | O(log n)（略快） |
| 插入/删除 | **快（旋转少）** | 慢（旋转多） |
| 适用 | 读写混合 | 读多写少 |

```text
HashMap 为什么选红黑树
├── ① 场景：读写混合（put/get 都有）
├── ② 红黑树插入/删除更快（旋转少——平衡代价小）
├── ③ AVL 查询略快但插入删除频繁旋转
├── ④ HashMap 的桶操作 = 读写混合 → 红黑树更平衡
└── ⑤ 金句：红黑树 = 「查询够快 + 写入不慢」的工程平衡
```

## 6. 树化与退化的完整链路

```text
链表 ↔ 树 完整链路
┌─────────────────────────────────────────────┐
│ put 追加 → 链表长度 ≥ 8？                     │
│   ├── 容量 ≥ 64？→ 树化（treeifyBin）        │
│   └── 容量 < 64？→ 扩容（分散后可能不到 8）   │
├─────────────────────────────────────────────┤
│ 树状态维持 → 删除/扩容拆分                    │
│   ├── 树节点 ≤ 6？→ 退化链表（untreeify）     │
│   └── 扩容拆分后节点少 → 退化                │
└─────────────────────────────────────────────┘

关键：6-8 缓冲防震荡（不会在 7/8 反复切换）
```

## 7. 树节点的内存代价

```text
树化的内存成本（为什么不能一律树化）
├── ① 内存对比：
│   ├── 链表节点 Node：约 32 字节
│   └── 树节点 TreeNode：约 56 字节（父子/红黑字段）
├── ② 树化内存 +75%：
│   ├── 5 个冲突元素：链表 160 字节 vs 树 280 字节
│   └── 短链树化 = 内存浪费
├── ③ 阈值设计的平衡：
│   ├── 8 以下：链表（内存优）
│   ├── 8-63：树化（性能兜底）
│   └── 容量 <64：扩容（分散优先）
└── ④ 金句：阈值 = 内存 × 性能的工程折中
```

---

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 树化目的：防极端冲突退化（O(n) → O(log n)）——「保险丝」不是主路径
> 2. **树化双条件**：≥8 且容量 ≥64（容量 <64 先扩容——面试陷阱）
> 3. 阈值 8 的依据：泊松分布（0.75 负载下概率千万分之六）——正常到不了
> 4. 退化 6：与 8 形成缓冲区间（滞回）——防树化/退化震荡
> 5. 红黑树 vs AVL：读写混合场景红黑树（插入删除旋转少）更合适
> 6. 树节点内存 +75%：阈值是「内存 × 性能」的折中
> 7. 完整链路：put → ≥8 → 树化/扩容 → 删除/拆分 → ≤6 → 退化
