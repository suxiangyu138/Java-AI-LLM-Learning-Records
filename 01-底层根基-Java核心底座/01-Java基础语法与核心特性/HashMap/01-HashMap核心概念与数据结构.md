## 1. HashMap 是什么

> **背景**：HashMap 是 Java 最常用的键值对集合——基于哈希表实现，平均 O(1) 查询。
> **目的**：理解 HashMap 的定位与基本特性。
> **适用范围**：键值存储/缓存/索引/分组。
> **不适用场景**：并发修改（用 ConcurrentHashMap）；需要顺序（用 LinkedHashMap/TreeMap）。

```text
HashMap 基本特性
├── ① 存储：键值对（Key-Value）
├── ② 查询：平均 O(1)（哈希定位）
├── ③ 允许：1 个 null key + 多个 null value
├── ④ 无序：不保证迭代顺序
├── ⑤ 非线程安全：并发需替代方案
└── ⑥ 实现：哈希表（数组 + 链表 + 红黑树）

典型场景
├── 缓存（本地 Map 缓存）
├── 数据索引（ID → 对象）
├── 分组统计（groupingBy 底层）
└── 配置存储（键值配置）
```

## 2. 底层数据结构演进

### 2.1 JDK 7 vs JDK 8（关键分水岭）

| 维度 | JDK 7 | JDK 8+（沿用至今） |
|------|:---:|:---:|
| 结构 | 数组 + 链表 | **数组 + 链表 + 红黑树** |
| 插入 | 头插法 | **尾插法** |
| 扰动 | 9 次位运算 | **2 次（hash ^ h>>>16）** |
| 扩容 | 全部重算 hash | **高低位拆分（免重算）** |
| 并发扩容 | **死循环（环形链表）** | 已修复（仍非安全） |
| 懒初始化 | 构造时创建 | **第一次 put 创建** |

> 🎯 **JDK 8 的三项核心改进**：红黑树（防冲突退化）、尾插法（修死循环）、高低位拆分（扩容高效）。

### 2.2 为什么需要三种结构

```text
三种结构的职责
├── ① 数组（桶）：哈希定位（O(1) 入口）
│   └── 问题：哈希冲突（多个 key 同一桶）
├── ② 链表：冲突处理（短链 O(n)）
│   └── 问题：冲突多时链表过长（O(n) 退化）
├── ③ 红黑树：防退化（长冲突 O(log n)）
│   └── 触发：链表 ≥ 8 且容量 ≥ 64
└── 金句：数组管定位、链表管冲突、红黑树管极端
```

## 3. 默认参数解析

### 3.1 核心参数

| 参数 | 默认值 | 说明 |
|------|:---:|------|
| **初始容量** | 16 | 桶数组长度（2 的幂） |
| **负载因子** | 0.75f | 扩容触发比例 |
| **扩容阈值** | 12（16×0.75） | size 超过触发扩容 |
| **树化阈值** | 8 | 链表长度 ≥ 8 |
| **退化阈值** | 6 | 树节点 ≤ 6 退链表 |
| **最小树化容量** | 64 | 容量 < 64 先扩容不树化 |

### 3.2 为什么负载因子是 0.75

> 🎯 **0.75 是时间与空间的折中**（面试必考）：

```text
负载因子 0.75 的权衡
├── 太高（如 1.0）：
│   ├── 空间利用率高（少扩容）
│   └── 冲突概率高（查询变慢）
├── 太低（如 0.5）：
│   ├── 冲突少（查询快）
│   └── 空间浪费（频繁扩容）
├── 0.75：泊松分布下冲突概率较低
│   ├── 链表长度 8 的概率 < 千万分之一
│   └── 空间与性能的平衡点
└── 金句：0.75 = 「空间不浪费 + 查询不慢」的工程平衡
```

## 4. 懒初始化机制

> **背景**：JDK 8+ 的 table 数组在构造时不创建——第一次 put 才初始化。
> **目的**：节省内存（空 Map 不占数组空间）。
> **适用范围**：所有 HashMap 实例。

```java
// 构造时：不创建数组（懒）
Map<String, String> map = new HashMap<>();
// table == null（此刻无数组——省内存）

// 第一次 put：才初始化容量
map.put("a", "1");
// table 创建（容量 16）

// 源码体现（putVal 中）
if ((tab = table) == null || (n = tab.length) == 0)
    n = (tab = resize()).length;   // 懒初始化：首次 resize 创建

// ⚠️ 源码中 resize() 承担两个职责：
// ① 首次 put 的初始化（扩容阈值 → 默认容量）
// ② 后续的扩容（容量 × 2）
```

```text
懒初始化的价值
├── ① 内存：空 Map 零数组开销
├── ② 性能：构造 O(1)（不预分配）
├── ③ 场景：大量「可能用不上」的 Map 声明
└── ④ 对比：Hashtable 构造即创建（11 容量）
```

## 5. Node 节点结构

```java
// HashMap 的核心节点（链表节点）
static class Node<K, V> implements Map.Entry<K, V> {
    final int hash;      // 扰动后的 hash（缓存——不用重算）
    final K key;         // 键（不可变）
    V value;             // 值（可变）
    Node<K, V> next;     // 链表下一节点（冲突链）
}

// 树节点（红黑树节点——继承 Node）
static final class TreeNode<K, V> extends LinkedHashMap.Entry<K, V> {
    TreeNode<K, V> parent;   // 父节点
    TreeNode<K, V> left;     // 左子
    TreeNode<K, V> right;    // 右子
    TreeNode<K, V> prev;     // 前驱（链表维护）
    boolean red;             // 红黑标记
}
```

```text
Node 设计要点
├── ① hash 缓存：节点存最终 hash（查找免重算）
├── ② key 不可变（final）：保证 hash 稳定
│   ├── ⚠️ 可变 key 的坑：修改 key 后 get 不到（hash 变了）
│   └── 生产：自定义 key 必须不可变 + 重写 hashCode/equals
├── ③ next 链表指针：冲突链
├── ④ TreeNode：红黑树节点（含前驱——树化/退化链表转换用）
└── ⑤ 内存对比：链表节点约 32 字节 vs 树节点约 56 字节
```

## 6. 与 Hashtable 的对比

| 维度 | HashMap | Hashtable |
|------|:---:|:---:|
| 线程安全 | ❌ | ✅（全方法 synchronized） |
| null key/value | ✅ 允许 | ❌ 不允许 |
| 初始容量 | 16 | 11 |
| 扩容 | ×2（2 的幂） | ×2+1 |
| 索引 | 位运算（2 的幂） | 取模 |
| 性能 | 高 | 低（全局锁） |
| 2026 定位 | **标准选择** | 过时（用 ConcurrentHashMap） |

```text
Hashtable 的问题
├── ① 全局 synchronized：所有方法同一把锁（并发度 1）
├── ② 不允许 null：get 无法区分「不存在」与「值为 null」
├── ③ 性能：高并发下锁竞争严重
└── ④ 结论：线程安全用 ConcurrentHashMap（不是 Hashtable）
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 结构演进：JDK 7（数组+链表）→ JDK 8+（数组+链表+红黑树）——三项改进（树/尾插/高低位拆分）
> 2. 默认参数：容量 16 + 负载因子 0.75（阈值 12）——**0.75 = 空间与时间的平衡**
> 3. 懒初始化：第一次 put 才建数组（resize 双职责：初始化 + 扩容）
> 4. Node 设计：hash 缓存 + key 不可变（可变 key 是坑）
> 5. vs Hashtable：非安全允许 null vs 全锁禁 null——**并发替代是 ConcurrentHashMap**
