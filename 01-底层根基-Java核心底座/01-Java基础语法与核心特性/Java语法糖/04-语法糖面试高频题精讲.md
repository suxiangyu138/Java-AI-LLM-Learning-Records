### 1.1 String s = "a" + "b" + "c" 创建了几个对象？

> **面试官意图**：考察对编译期常量折叠的理解，区分编译期优化与运行时行为

**标准答案（分层回答）：**

**表面层**：只创建了 1 个对象，即 `"abc"`。

**原理层**：
- Java 编译器在编译期会对常量字符串拼接进行 **常量折叠（Constant Folding）** 优化
- `"a" + "b" + "c"` 在编译期直接被计算为 `"abc"`
- 字节码中只出现 `ldc #abc` 一条指令，从常量池加载 `"abc"`
- 由于字符串常量池的存在，如果常量池已有 `"abc"`，则连对象都不会创建

```java
// 源代码
String s = "a" + "b" + "c";

// 编译后等价于
String s = "abc";
```

**字节码验证（javap -c 反编译）：**

```text
0: ldc           #7     // String abc
2: astore_1
3: return
```

可以看到只有一条 `ldc` 指令，`"a"`、`"b"`、`"c"` 三个字面量并未出现在字节码中。

> 💡 **关键区别**：如果拼接中包含变量（如 `String s = a + "b" + "c"`，其中 a 是变量），则编译器会使用 StringBuilder 或 invokedynamic 拼接，情况完全不同。

**加分项**：
- 指出 JDK 9 之前用 `StringBuilder`，JDK 9+ 改用 `invokedynamic` + `StringConcatFactory` 做动态拼接
- 区分编译期常量（`final String`）和运行期变量对拼接优化的影响
- 顺带讲清 `new String("abc")` 创建 1 个或 2 个对象的场景（堆对象 + 常量池对象）

**追问**：
```
问：String s = new String("a") + new String("b") 创建了几个对象？
答：4 个堆对象（两个 new String("a") 各 1 个，两个 new String("b") 各 1 个）
    + 常量池中 "a" 和 "b"（可能不新建）
    + StringBuilder
    + StringBuilder.toString() 返回的 new String("ab")
    实际创建了 6~8 个对象，但 "ab" 不会入常量池（除非显式 intern）
```

> 🎯 **核心要点**：字符串常量拼接在编译期折叠，不存在运行时拼接开销。混淆点要分清"常量拼接"和"变量拼接"两条路径。

### 1.2 Integer i1 = 100, i2 = 100; i1 == i2 和 Integer i1 = 200, i2 = 200; i1 == i2 分别输出什么？

> **面试官意图**：考察 Integer 缓存机制（自动装箱语法糖的底层实现）

**标准答案（分层回答）：**

**表面层**：
- `i1 == i2` 当值为 100 时：**输出 `true`**
- `i1 == i2` 当值为 200 时：**输出 `false`**

**原理层**：

```java
Integer i1 = 100;  // 编译为 Integer.valueOf(100)
Integer i2 = 100;  // 编译为 Integer.valueOf(100)

Integer i3 = 200;  // 编译为 Integer.valueOf(200)
Integer i4 = 200;  // 编译为 Integer.valueOf(200)

System.out.println(i1 == i2); // true
System.out.println(i3 == i4); // false
```

`Integer i = 100` 是自动装箱语法糖，编译后等价于 `Integer.valueOf(100)`。`valueOf` 源码：

```java
public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];
    return new Integer(i);
}
```

默认缓存范围是 `[-128, 127]`，100 在这个范围内，所以返回缓存中的同一个对象，`==` 比较为 `true`；200 不在范围内，每次调用都 `new Integer(200)`，两个不同对象，`==` 为 `false`。

**加分项**：
- 指出 `IntegerCache.high` 可以通过 JVM 参数 `-XX:AutoBoxCacheMax=<size>` 调整上限
- 指出 `==` 比较的是引用，应当用 `equals()` 比较值
- 顺带提及其他包装类的缓存：`Long` 也有 `[-128, 127]`，`Short`、`Byte` 也类似，`Float`、`Double` **没有**缓存

```text
| 包装类     | 缓存范围         | 说明                              |
|-----------|-----------------|-----------------------------------|
| Integer   | [-128, 127]     | 可通过 JVM 参数调高上限               |
| Long      | [-128, 127]     | 固定，不可调                         |
| Short     | [-128, 127]     | 固定                                |
| Byte      | 全部（-128~127） | 全部缓存（因为只有 256 个值）          |
| Character | [0, 127]        | ASCII 范围                          |
| Float     | 无              | 浮点数数量无限，不适合缓存              |
| Double    | 无              | 同上                                |
```

**追问**：
```
问：Integer i = new Integer(100); Integer j = new Integer(100); i == j 输出？
答：false。new 关键字强制在堆上创建新对象，不经过 valueOf 缓存机制
    无论值是否在缓存范围内，都创建新对象

问：int a = 100; Integer b = 100; a == b 输出？
答：true。int 和 Integer 比较时，Integer 会自动拆箱为 int
    比较的是数值，不是引用
```

> 🎯 **核心要点**：自动装箱是语法糖（`valueOf`），自动拆箱也是语法糖（`intValue`）。缓存机制是 valueOf 的实现细节，不是语言规范强制要求，但主流 JDK 都实现了。

### 1.3 for (int i : list) 中 list.remove(i) 会怎样？

> **面试官意图**：考察增强 for 循环（语法糖）的底层实现和 fail-fast 机制

**标准答案（分层回答）：**

**表面层**：会抛出 `ConcurrentModificationException`。

**原理层**：

增强 for 循环是语法糖，编译后等价于使用 `Iterator` 遍历：

```java
// 源代码
for (int i : list) {
    list.remove(i);
}

// 编译后等价于（伪代码）
Iterator<Integer> it = list.iterator();
while (it.hasNext()) {
    Integer i = it.next();    // 这里会检查 modCount
    list.remove(i);           // 直接调用 List.remove(), 修改了 modCount
}
```

`ArrayList` 的 `Iterator` 实现中有一个 `expectedModCount` 字段，每次调用 `next()` 都会检查：

```java
final void checkForComodification() {
    if (modCount != expectedModCount)
        throw new ConcurrentModificationException();
}
```

- `list.remove(i)` 会修改 `list.modCount++`
- 但迭代器内部的 `expectedModCount` 没有同步更新
- 下一次循环调用 `it.next()` 时，检测到 `modCount != expectedModCount`，抛出异常

**正确做法**：使用 `Iterator.remove()`：

```java
Iterator<Integer> it = list.iterator();
while (it.hasNext()) {
    Integer i = it.next();
    if (条件满足) {
        it.remove();  // 会同步更新 expectedModCount = modCount
    }
}
```

或者使用 JDK 8 的 `removeIf`：

```java
list.removeIf(i -> 条件满足);  // 底层也是用 Iterator 批量处理
```

> ⚠️ **注意**：即使使用 `Iterator.remove()`，也不能在增强 for 循环的语法糖中直接使用——因为增强 for 循环没有暴露 Iterator 对象。

**加分项**：
- 解释 fail-fast 和 fail-safe 的区别（CopyOnWriteArrayList 使用 fail-safe 迭代器）
- 指出 `ArrayList` 在删除元素后索引会变化，可能造成漏删或越界
- 提及 `ConcurrentModificationException` 发生在 `next()` 调用时，不一定是修改的 Immediate 位置

**追问**：
```
问：那用 for (int i = 0; i < list.size(); i++) 删除呢？
答：可以删除不抛异常，但要注意 i-- 维护索引，否则会漏删
    list.remove(i) 后，后面的元素前移，i++ 会跳过下一个元素

问：foreach 循环出现在哪个 Java 版本？原理是什么？
答：JDK 5 引入，编译为 Iterator + while 循环
    数组类型的 foreach 编译为普通 for 循环 + 下标访问
```

> 🎯 **核心要点**：增强 for 循环是 Iterator 的语法糖，遍历时不能通过集合自身的 remove/add 修改结构，必须使用迭代器的 remove 方法。

### 1.4 switch(str) 是怎么实现的？为什么 JDK 7 之前不支持 String？

> **面试官意图**：考察 switch 语法糖的编译原理和 JDK 演进

**标准答案（分层回答）：**

**表面层**：`switch(String)` 在 JDK 7 引入，编译器将其转换为 `hashCode + equals` 的 if-else 链或 `LookupSwitch`。

**原理层**：

```java
// 源代码
String str = "hello";
switch (str) {
    case "hello": break;
    case "world": break;
}
```

编译后的字节码逻辑等价于：

```java
// 编译后逻辑（简化）
String str = "hello";
int hash = str.hashCode();

if (hash == "hello".hashCode()) {      // 第一个 switch 表：hashCode 匹配
    if (str.equals("hello")) {          // 二次校验，防止 hash 碰撞
        // case hello 逻辑
    }
} else if (hash == "world".hashCode()) {
    if (str.equals("world")) {
        // case world 逻辑
    }
}
```

编译器生成两阶段匹配：
1. **第一阶段**：对每个 case 调用 `hashCode()`，生成 `tableswitch` 或 `lookupswitch` 字节码（基于整数 hash 的跳转表）
2. **第二阶段**：在匹配的 case 块内插入 `equals()` 调用，防止 hashCode 碰撞

```text
// JDK 7 switch(String) 反编译示意
0: aload_1                    // 加载 str
1: invokevirtual #7           // Method java/lang/String.hashCode()I
4: lookupswitch               // 基于 hash 码的跳转
        99162322: 36          // "hello" 的 hash
        113318802: 52         // "world" 的 hash
        default: 68
36: aload_1                   // 二次校验
37: ldc           #8          // String "hello"
39: invokevirtual #9          // Method java/lang/String.equals
42: ifeq          68          // 如果 equals 失败，跳到 default
45: // case hello 逻辑
...
```

**为什么 JDK 7 之前不支持 String？**

原因有两个：
1. **switch 字节码指令的限制**：`tableswitch`/`lookupswitch` 只支持 `int` 类型（包括 `byte`、`short`、`char`、`enum` 都能转为 int）。String 不是基础类型，不能直接映射为 int 索引
2. **性能考虑**：String 匹配需要 `equals()` 校验，hashCode 可能碰撞，需要额外的 equals 检查——这改变了 switch 原有的 O(1) 跳转语义

```text
| 支持类型            | 引入版本 | 字节码表示                |
|--------------------|---------|--------------------------|
| int, char, short, byte | 1.0  | tableswitch/lookupswitch |
| enum               | JDK 5   | 转为 int ordinal          |
| String             | JDK 7   | hashCode + equals 两阶段  |
```

**加分项**：
- 指出 `switch(null)` 会抛出 `NullPointerException`，因为对 `null` 调用 `hashCode()` 会 NPE
- 指出当 case 数量很少时（如 2~3 个），编译器可能直接优化为 `if-else` 链，不做跳转表
- 提及 `switch` 在 JDK 17+ 支持模式匹配（Pattern Matching for switch）

**追问**：
```
问：switch(enum) 是怎么实现的？会有什么坑？
答：switch(enum) 编译时获取 Enum 的 ordinal() 转为 int
    再做 tableswitch/lookupswitch
    坑：如果 enum 的常量顺序改变，switch 的行为会隐式改变
    所以不要依赖 Enum.ordinal() 做业务逻辑

问：String 的 switch 中，如果两个不同的 String hashCode 相同会怎样？
答：这正是需要 equals 二次校验的原因
    如果 case "AaAa" 和 case "BBBB"（hashCode 均为 2031744）
    编译器会在 hash 匹配后插入 equals 检查
```

> 🎯 **核心要点**：`switch(String)` 是编译器实现的语法糖，本质是 hashCode 跳转表 + equals 二次确认。底层 switch 字节码始终只支持 int。

### 1.5 try (InputStream is = new FileInputStream("test")) 底层怎么实现的？

> **面试官意图**：考察 try-with-resources 语法糖的编译期还原和异常抑制机制

**标准答案（分层回答）：**

**表面层**：try-with-resources 是 JDK 7 引入的语法糖，用于自动关闭实现了 `AutoCloseable` 的资源。

**原理层**：

```java
// 源代码
try (InputStream is = new FileInputStream("test")) {
    is.read();
}
```

编译器会将其转换为等价于：

```java
// 编译后等价逻辑
InputStream is = new FileInputStream("test");
Throwable primaryException = null;
try {
    is.read();
} catch (Throwable e) {
    primaryException = e;
    throw e;
} finally {
    if (is != null) {
        if (primaryException != null) {
            try {
                is.close();
            } catch (Throwable suppressed) {
                primaryException.addSuppressed(suppressed); // 抑制异常
            }
        } else {
            is.close();
        }
    }
}
```

关键点：
1. **双 try 嵌套**：外层 try 捕获业务异常，内层 try 捕获 close 异常
2. **Suppressed Exception 机制**：如果 try 块抛出了异常，同时 close() 也抛出了异常，close 的异常会被抑制（Suppressed），附加到主异常上
3. 通过 `Throwable.getSuppressed()` 可以获取被抑制的异常

```java
// 获取被抑制的异常
try (MyResource r = new MyResource()) {
    throw new RuntimeException("Main exception");
} catch (Exception e) {
    System.out.println("Main: " + e.getMessage());
    for (Throwable suppressed : e.getSuppressed()) {
        System.out.println("Suppressed: " + suppressed.getMessage());
    }
}
```

**多资源管理**：
```java
// 源代码
try (InputStream is = new FileInputStream("a");
     OutputStream os = new FileOutputStream("b")) {
    // 读写
}

// 编译后按声明顺序初始化，按 LIFO 顺序关闭
// 关闭顺序：os.close() → is.close()
```

**加分项**：
- 指出 `AutoCloseable` 和 `Closeable` 的区别：`Closeable` 继承自 `AutoCloseable`，`close()` 声明为抛出 `IOException`，而 `AutoCloseable` 抛出 `Exception`
- 指出 JDK 9 的增强：可以在 try 中使用 effectively-final 变量（`try (is; os) { ... }`）
- 指出在 JDK 7 之前只能手动在 finally 中关闭资源，代码冗长且容易遗漏

**追问**：
```
问：有没有可能在 try-with-resources 中"丢失"异常？
答：在 JDK 7 之前，如果 try 块和 finally 块都抛异常，
    finally 的异常会覆盖 try 块的异常——这是典型的异常丢失场景
    JDK 7 的 try-with-resources 通过 Suppressed Exception 解决了这个问题

问：多个资源关闭时发生异常，所有异常都会被捕获吗？
答：第一个关闭异常会被抑制到主异常，后续关闭异常也会被依次抑制
    但要注意，如果 close() 的顺序很重要，LIFO 是规范保证的
```

> 🎯 **核心要点**：try-with-resources 是 JDK 7 语法糖，编译器生成带 suppressed 异常处理的 finally 块。核心价值是解决了传统 try-finally 中异常丢失的问题。

## 2. 进阶陷阱（5道）

### 2.1 Lambda 表达式和匿名内部类有什么区别？

> **面试官意图**：考察 Lambda 的本质——它不只是"匿名内部类的语法糖"，两者有根本区别

**标准答案（分层回答）：**

**表面层**：Lambda 看起来像是匿名内部类的简化写法，但两者有本质区别。

**原理层**：

| 维度 | Lambda 表达式 | 匿名内部类 |
|------|--------------|-----------|
| 字节码生成 | invokedynamic + 不生成独立的 .class 文件 | 编译成独立的 `OuterClass$1.class` |
| this 引用 | this 指向外部类 | this 指向匿名内部类自身 |
| 作用域 | 不能定义与外部同名的局部变量（变量屏蔽） | 可以屏蔽外部变量 |
| 捕获变量 | 必须是 effectively final | 要求是 final（JDK 8 前）或 effectively final（JDK 8 后） |
| 实现方式 | invokedynamic + LambdaMetafactory | 编译时直接生成匿名类 |
| 性能 | 初次调用时生成目标函数接口实例，后续复用 | 每次调用生成新实例 |

**字节码对比：**

匿名内部类编译后会生成 `OuterClass$1.class` 文件，而 Lambda 在字节码中通过 `invokedynamic` 指令调用 `LambdaMetafactory`：

```text
// Lambda 反编译
invokedynamic #2, 0  // InvokeDynamic
                      // #0:accept:()Ljava/util/function/Consumer;

// 匿名内部类反编译
new             #2    // class OuterClass$1
dup
invokespecial   #3    // Method OuterClass$1."<init>":()V
```

**加分项**：
- 指出 Lambda 的 `this` 指向外部类，这是许多 Lambda 转匿名内部类重构时报错的原因
- 指出 Lambda 不生成额外的 .class 文件，减少了 JVM 的类加载开销
- 指出 Lambda 的捕获参数使用 `java.lang.invoke` 包，本质是方法引用和函数式接口的组合

**追问**：
```
问：那方法引用 :: 也是语法糖吗？和 Lambda 有什么关系？
答：方法引用是 Lambda 的另一种形式，本质相同
    Class::staticMethod 等价于 (args) -> Class.staticMethod(args)
    编译后同样使用 invokedynamic，但实现更高效（直接方法引用，省去一层委托）

问：所有 Lambda 都可以用匿名内部类替换吗？
答：技术上可以，但语义上有区别——Lambda 的 this 不同
    如果 Lambda 内部使用了 this，改为匿名内部类后 this 指向发生了变化
    这是最容易踩的坑
```

> 🎯 **核心要点**：Lambda 不是匿名内部类的语法糖！Lambda 的底层是 invokedynamic + 函数式接口，不产生独立 class 文件，this 指向外部类。关键区别在 this 引用和作用域规则。

### 2.2 List\<String\> list1 和 List\<Integer\> list2 在运行时 class 一样吗？

> **面试官意图**：考察泛型擦除（Type Erasure）机制，验证是否理解编译时和运行时的区别

**标准答案（分层回答）：**

**表面层**：运行时两个对象的 `getClass()` 返回完全相同的 `java.util.ArrayList.class`。

**原理层**：

Java 的泛型是编译期语法糖——**类型擦除（Type Erasure）**：

```java
List<String> list1 = new ArrayList<>();
List<Integer> list2 = new ArrayList<>();

System.out.println(list1.getClass() == list2.getClass()); // true
System.out.println(list1.getClass()); // class java.util.ArrayList
```

编译时类型擦除的过程：

```java
// 源代码（带泛型）
List<String> list1 = new ArrayList<>();
list1.add("hello");
String s = list1.get(0);

// 编译后（泛型擦除）
List list1 = new ArrayList();       // raw type，去掉 <String>
list1.add("hello");                 // add(Object) — 自动类型转换被移除
String s = (String) list1.get(0);  // 插入强制类型转换
```

**字节码验证：**

```text
// List<Integer> 和 List<String> 的字节码完全一样
// 都操作的是 Object 类型

// add
6: aload_1
7: invokevirtual #7   // Method java/util/ArrayList.add:(Ljava/lang/Object;)Z

// get
10: aload_1
11: invokevirtual #8  // Method java/util/ArrayList.get:(I)Ljava/lang/Object;
14: checkcast     #9  // checkcast 插入的类型转换（String 或 Integer）
```

> ⚠️ **注意**：Type 参数在运行时是完全不可知的，以下代码无法编译：

```java
if (list instanceof List<String>) { } // 编译错误！不可对参数化类型 instanceof
if (list instanceof List<?>) { }      // 正确，使用通配符
```

**加分项**：
- 指出擦除的例外：方法签名中的泛型在反射中存在（`Method.getGenericParameterTypes()` 通过 Signature 属性保留）
- 区分 `List<String>.class` 不存在（无法编译），但 `List.class` 存在
- 指出桥方法（Bridge Method）的存在：子类泛型方法在擦除后，编译器会生成桥方法维护多态

**追问**：
```
问：那反射能不能获取到 List<String> 中的 String 类型？
答：不能从 list 对象本身获取——运行时它就是 ArrayList
    但如果从字段的声明类型通过反射 Field.getGenericType() 可以获取
    因为字段的 Signature 属性在 class 文件中保留了泛型信息

问：泛型擦除有什么缺点？
答：1. 运行时无法知道类型参数，不能做 T t = new T() 或 new T[]
    2. 不支持基本类型做类型参数（List<int> 不行，要用 List<Integer>）
    3. 重载混淆：void foo(List<String>) 和 void foo(List<Integer>) 不能共存
    4. 性能开销：需要隐式类型转换和装箱拆箱
```

> 🎯 **核心要点**：Java 泛型是编译期语法糖，运行时全部擦除为 raw type。`ArrayList<String>` 和 `ArrayList<Integer>` 在运行时就是同一个 `ArrayList` 类。

### 2.3 StringBuilder vs StringBuffer vs 字符串 + 号的性能对比

> **面试官意图**：考察字符串拼接的底层优化、线程安全与性能权衡

**标准答案（分层回答）：**

**表面层**：
- 单线程下：`StringBuilder` ≈ 编译期 `+` 号（JDK 5~8 编译为 StringBuilder）
- 多线程下：`StringBuffer`（带 synchronized）
- 循环内 `+` 号：性能最差（每次循环都 new StringBuilder）

**原理层**：

**情况一：单行常量拼接**
```java
// 源代码
String s = "a" + "b" + "c";

// 编译后：常量折叠
String s = "abc";  // 只有 1 个对象，性能最优
```

**情况二：单行变量拼接（JDK 5~8）**
```java
// 源代码
String s = a + "," + b;

// 编译后：StringBuilder 链式调用
String s = new StringBuilder().append(a).append(",").append(b).toString();
```

**情况三：循环内拼接（性能陷阱）**
```java
// 糟糕写法——每次循环都 new StringBuilder
String s = "";
for (int i = 0; i < 1000; i++) {
    s = s + "," + i;  // 每次循环：new StringBuilder → append → toString → 丢弃
}

// 编译后（每次循环等价于）
for (int i = 0; i < 1000; i++) {
    String tmp = new StringBuilder().append(s).append(",").append(i).toString();
    s = tmp;
    // 下一次循环又 new 一个 StringBuilder
}
```

```text
| 拼接方式                    | 性能 | 线程安全 | 说明                            |
|----------------------------|------|---------|---------------------------------|
| 常量折叠 ("a"+"b")          | 最高 | 安全     | 编译期优化，运行时 0 开销           |
| StringBuilder.append       | 高   | 不安全   | 单线程最优选择                     |
| 单行 + 号 (编译器优化)       | 高   | 不安全   | 编译为 StringBuilder，效果一样     |
| StringBuffer.append        | 中   | 安全     | 方法级 synchronized               |
| 循环内 + 号                | 极差 | 不安全   | 每次循环创建 StringBuilder，性能灾难 |
| String.concat              | 低   | 不安全   | 每次返回新 String，不推荐           |
```

**JDK 9+ 的变化**：
- JDK 9+ 中 `+` 号的字符串拼接改用 `invokedynamic` + `StringConcatFactory`
- 运行时根据策略不同，可能使用 `StringBuilder` 或直接预分配 byte[] 数组
- 性能上 JDK 9+ 的 `+` 号在简单场景下可能优于手写 `StringBuilder`

**加分项**：
- 指出 `StringBuffer` 在 JDK 5 之前是唯一选择——当时 `+` 号不做优化
- 指出 `StringBuilder` 扩容策略：默认 16 个字符，扩容时 `old * 2 + 2`
- 建议在已知长度时传入初始容量：`new StringBuilder(capacity)` 避免扩容

**追问**：
```
问：StringBuffer 的线程安全是怎么实现的？
答：几乎所有 public 方法都用 synchronized 修饰
    但多个方法的组合操作（如 if(buffer.length()>0) buffer.append()）仍然需要外部同步

问：JDK 9 的 invokedynamic 拼接有什么好处？
答：将拼接策略推迟到运行时决定——JVM 可以动态选择最优策略
    - 小字符串用 byte[] 直接拼接，避免 StringBuilder 对象开销
    - 未来可以引入更激进的优化，无需修改字节码
```

> 🎯 **核心要点**：单行 `+` 号拼接已经由编译器优化（编译为 StringBuilder 或 invokedynamic），不需要手写 StringBuilder。但循环内 `+` 号是性能陷阱，必须手动使用 StringBuilder。

### 2.4 可变参数 void foo(String... args) 和 void foo(String[] args) 有什么区别？

> **面试官意图**：考察可变参数语法糖的编译还原和重载歧义问题

**标准答案（分层回答）：**

**表面层**：两者在编译后完全一样，都是 `String[]` 类型。但调用方式不同。

**原理层**：

```java
// 可变参数定义
void foo(String... args) {}

// 等价于（编译后）
void foo(String[] args) {}

// 注意：签名相同！所以两者不能同时定义（编译冲突）
// void foo(String[] args) {}  // 编译错误：已在 foo(String...) 中定义了该方法
```

**调用方式的区别：**

```java
// 可变参数调用方式更灵活
foo("a", "b", "c");       // 直接传多个参数
foo();                     // 可以不传参数，等价于 foo(new String[0])
foo(null);                 // 传 null

// 数组参数只能传数组
foo(new String[]{"a","b"}); // 两种都可
foo(new String[0]);          // 两种都可
```

**重载歧义问题**：

```java
public void bar(String s, String... args) {}
public void bar(String s, String[] args) {}  // 编译错误！不能重载

// 更隐蔽的歧义
public void baz(String s, String... args) {}
public void baz(String s, String arg) {}     // 合法

baz("hello");              // 调用哪一个？→ 调用 baz(String, String)
baz("hello", "world");     // 调用 baz(String, String...)
baz("hello", "world", "!");  // 只能调用 baz(String, String...)
```

> ⚠️ **可变参数的槽点**：
> 1. 可变参数必须是方法的**最后一个参数**
> 2. 可变参数的方法重载容易引起歧义，编译器优先匹配固定参数的方法
> 3. 传入 `null` 时，JVM 分不清是传了一个 null 数组还是数组元素是 null
> 4. 性能：每次调用可变参数方法会创建数组对象，对高频调用有轻微影响

**加分项**：
- 指出 `varargs` 和泛型同时使用的限制：`void foo(T... args)` 有堆污染警告（`@SafeVarargs` 可以抑制）
- 指出 JDK 7+ 引入 `@SafeVarargs` 注解，用于标记可变参数方法不会对参数数组做不安全操作
- 指出 PrintStream 的 `printf(String format, Object... args)` 是可变参数的经典应用

**追问**：
```
问：为什么可变参数方法在反射中会多出一层数组包装？
答：当 Method.invoke 调用可变参数方法时，如果传入的 Object[] 参数
    恰好是单个数组，JVM 可能将其整体作为第一个参数，而不是展开
    这就是反射调用可变参数方法时需要小心处理数组参数的原因

问：你能写一个不安全的可变参数方法吗？
答：可以，例如：
    static <T> void unsafe(T... args) {
        Object[] arr = (Object[]) args;  // 强制类型转换
        arr[0] = "hack";                 // 如果实际类型不是 String，会 ClassCastException
    }
    这就是 @SafeVarargs 的由来——方法作者保证不会如此操作
```

> 🎯 **核心要点**：可变参数是数组参数的语法糖，编译后完全相同。差异在调用时的灵活性，以及重载解析时的优先级规则。

### 2.5 Optional.ofNullable(x).orElse(getDefault()) 和 orElseGet() 的区别

> **面试官意图**：考察对调用者 eager 求值和惰性求值的区分——orElse 的参数总是会被计算

**标准答案（分层回答）：**

**表面层**：
- `orElse(getDefault())`：无论 Optional 中是否有值，`getDefault()` **都会被执行**
- `orElseGet(() -> getDefault())`：只有 Optional 为空时，`getDefault()` **才被执行**

**原理层**：

```java
// orElse 源码——参数已经传入，eager 求值
public T orElse(T other) {
    return value != null ? value : other;
}

// orElseGet 源码——Supplier 惰性求值
public T orElseGet(Supplier<? extends T> supplier) {
    return value != null ? value : supplier.get();
}
```

关键区别在于**调用时机**：

```java
// 性能陷阱：orElse 的参数在方法调用前就计算好了
Optional<String> opt = Optional.of("present");

// 即使 opt 有值，expensiveMethod() 仍然会被调用
String result = opt.orElse(expensiveMethod());   // expensiveMethod() 已执行

// 只有 opt 为空时才调用
String result = opt.orElseGet(() -> expensiveMethod());  // 未执行！
```

**实际影响**：

```java
// 场景一：默认值计算开销大（性能敏感）
// 错误——每次调用都执行默认方法
String config = opt.orElse(readFromDatabase());       // 永远执行 DB 查询
// 正确——只有为空时才查询
String config = opt.orElseGet(() -> readFromDatabase());

// 场景二：默认值产生副作用
// 错误——side effect 总会被触发
opt.orElse(logAndGetDefault());  // 日志总会打印
// 正确——仅空值时触发
opt.orElseGet(() -> logAndGetDefault());

// 场景三：默认值抛出异常
// 错误——即使 opt 有值也可能抛异常
opt.orElse(throw new RuntimeException("default"));  // 编译期就会执行 throw! 异常在 before 调用就发生了
// 正确
opt.orElseGet(() -> { throw new RuntimeException("default"); });
```

> ⚠️ **最隐蔽的坑**：`orElse(throw new X())` 实际上在参数求值时就已经抛出异常，永远不会进入 orElse 方法体。因为 Java 是 eager 求值，方法参数在调用前先计算完毕。

**加分项**：
- 指出 `orElse` 适合默认值是一个常量或已计算好的对象（无需额外开销）
- 指出 JDK 的 `orElseThrow(Supplier)` 也是惰性求值（JDK 10+）
- 指出 `orElse` 和 `orElseGet` 的性能差异在默认值计算轻量时几乎可以忽略，但在高并发场景下需要重视

**追问**：
```
问：orElse 的这种设计是 Java 语言限制还是 Optional 的 bug？
答：是 Java 语言的方法调用语义决定的——所有方法参数都是 eager 求值
    C# 的 ?? 运算符可以通过内置语法实现惰性求值，Java 缺乏这个语言特性
    所以 Optional 提供 orElseGet 作为补救，通过 Supplier 实现惰性

问：还有哪些类似的和 Optional 相关的陷阱？
答：1. Optional.get() 不检查就调用会 NoSuchElementException
    2. Optional.of() 不接受 null，ofNullable() 接受 null
    3. Optional 本身是对象，作为字段/参数/返回值都有性能开销
    4. Optional 不要作为方法参数！
```

> 🎯 **核心要点**：`orElse(T)` 参数是 eager 求值，无论 Optional 是否为空都执行；`orElseGet(Supplier)` 是惰性求值。这是 Java 语言调用规范（所有参数先计算后传参）决定的，不是 Optional 特有的。

### 3.1 Record 类和 Lombok @Data 有什么区别？

> **面试官意图**：考察对语言级特性 vs 编译期注解处理器的深入理解

**标准答案（分层回答）：**

**表面层**：两者都帮我们生成 getter、equals、hashCode、toString 等方法。但 Record 是语言内置，Lombok 是第三方库。

**原理层**：

| 维度 | Record（JDK 16+） | Lombok @Data |
|------|------------------|-------------|
| 定位 | 语言级不可让变数据载体 | 编译期代码生成工具 |
| 实现原理 | JEP 395，编译器直接生成规范方法 | 编译期注解处理器（APT），修改抽象语法树 |
| 继承性 | 隐式 final class，不能继承其他类 | 普通 class，可以继承 |
| 可变性 | 所有字段 final，不可变 | 不强制 final，可生成 setter |
| 序列化 | 序列化字段名与构造函数参数名绑定 | 默认序列化行为 |
| 兼容性 | JDK 16+ 才能使用 | JDK 6+ 可用 |
| 依赖 | 无，JVM 原生支持 | 需要引入 lombok 库 + IDE 插件 |
| 模式匹配 | Record 天然支持模式匹配解构 | 不支持 |
| 密封类 | 可以配合 sealed class 使用 | 不相关 |

**Record 的本质（字节码层面）：**

```java
// 源代码
public record Point(int x, int y) {}

// 编译后等价于
public final class Point extends java.lang.Record {
    private final int x;
    private final int y;

    // 规范构造器
    public Point(int x, int y) { this.x = x; this.y = y; }

    // 访问器方法——不是 getX()，是 x()
    public int x() { return this.x; }
    public int y() { return this.y; }

    // 自动生成
    public boolean equals(Object o) { /* 基于所有字段的比较 */ }
    public int hashCode() { /* 基于所有字段的 hash */ }
    public String toString() { /* 格式化输出 */ }
}
```

**Lombok 的本质**：
- Lombok 在编译期通过 `JSR 269（Pluggable Annotation Processing API）` + 非公开 API 修改 AST
- 直接在编译树中插入 getter/setter/equals/hashCode/toString 等方法的 AST 节点
- 字节码层面看就是一个普通 class，和手写的没有任何区别

**各有所长**：

```text
| 场景                          | 推荐选择  | 理由                          |
|------------------------------|----------|-------------------------------|
| 不可变数据传输对象（DTO）       | Record   | 语言级不可变，模式匹配，简洁      |
| JPA/Hibernate 实体            | Lombok   | 需要可变性，需要无参构造器        |
| 微服务间的消息/事件            | Record   | 不可变，天然线程安全             |
| 需要继承的 POJO               | Lombok   | Record 不能继承                 |
| 需要自定义 equals 逻辑         | Lombok   | 可以使用 @EqualsAndHashCode.Exclude |
| 需要自定义构造器               | 都支持   | Record 可以添加紧凑构造器        |
```

**加分项**：
- 指出 Record 可以通过紧凑构造器（Compact Constructor）做校验：`public Point { if (x < 0) throw ...; }`
- 指出 Record 可以自定义方法、实现接口，但不能添加实例字段
- 指出 `@Data` = `@Getter` + `@Setter` + `@EqualsAndHashCode` + `@RequiredArgsConstructor` + `@ToString`
- 指出 Lombok 的 `@Value` 才是不可变变体（所有字段 final）

**追问**：
```
问：Record 可以替代 DTO 中的 @Data 吗？有什么限制？
答：可以但有限制：
    1. Record 字段全部 final——适合查接口但不适合写接口
    2. Record 无无参构造器——不适合 ORM 框架（MyBatis/Hibernate）
    3. Record 不能继承——不适合领域模型中的继承体系

问：Record 的模式匹配怎么用？
答：JDK 21 中可以在 switch 中使用：
    Object obj = new Point(1, 2);
    if (obj instanceof Point(int x, int y)) {
        System.out.println(x + ", " + y);  // 直接解构
    }
```

> 🎯 **核心要点**：Record 是语言级的不可变数据载体语法糖（最终生成 final class），Lombok 是编译期的 APT 代码生成。两者不冲突，各自有最适合的场景。

### 3.2 Java 的 var 和 JavaScript 的 var 有什么区别？

> **面试官意图**：考察局部变量类型推断（var 语法糖）的本质，区分编译时类型和运行时类型

**标准答案（分层回答）：**

**表面层**：完全是两个不同概念。Java 的 var 是编译时类型推断，JavaScript 的 var 是运行时动态类型。

**原理层**：

```java
// Java var——编译时类型推断
var list = new ArrayList<String>();       // 编译推断：ArrayList<String>
var num = 42;                              // 编译推断：int
var str = "hello";                         // 编译推断：String

// 编译后（等价于）
ArrayList<String> list = new ArrayList<String>();
int num = 42;
String str = "hello";
```

```javascript
// JavaScript var——运行时动态类型
var x = 42;      // typeof x === 'number'
x = "hello";     // 可以重新赋值为不同类型的值
var x = true;    // 甚至可以重新声明！
```

| 维度 | Java var（JDK 10+） | JavaScript var |
|------|--------------------|---------------|
| 引入版本 | JDK 10（JEP 286） | ES1（1995） |
| 类型系统 | 强类型、静态类型 | 弱类型、动态类型 |
| 推断时机 | 编译期（编译时推断并固定） | 运行期（实际值决定类型） |
| 变量重赋 | 不能赋不同类型（类型已固定） | 可以赋任意类型 |
| 重新声明 | 不允许 | 允许（同一作用域重复 var） |
| 作用域 | 块级作用域 | 函数级作用域 |
| 字节码 | var 在字节码中不存在（已替换为具体类型） | 不存在字节码概念 |
| 可推断性 | 必须有初始化表达式且能推断具体类型 | 不需要 |

**Java var 的限制**：

```java
// 不能使用 var 的场景
var x;                              // 编译错误：没有初始化器
var y = null;                       // 编译错误：不能推断为 null 类型
var z = (a, b) -> a + b;            // 编译错误：Lambda 需要目标类型
var arr = {1, 2, 3};                // 编译错误：数组初始化器需要目标类型

// 需要使用 var 的场景
// 简化泛型嵌套类型声明
var map = new HashMap<String, List<Integer>>();
// 等价于：HashMap<String, List<Integer>> map = new HashMap<>();

// 简化链式调用中间类型
var result = service.processComplexData();
```

**加分项**：
- 指出 var 不能用于字段、方法参数、返回类型——只能用于局部变量
- 指出 var 不会降低代码可读性（JDK 的设计目标就是保留可读性），但滥用 var（如 `var x = foo()` 返回类型不明显）会降低可维护性
- 指出 Lambda 参数也可以用 var（JDK 11）：`(var a, var b) -> a + b`，用于配合注解

**追问**：
```
问：Java 的 val（JDK 14 preview）和 var 有什么区别？
答：val 由 Lombok 引入，声明不可变局部变量（final 的 var）
    Java 本身没有 val 关键字，Lombok 的 val 在编译期替换为 final + 具体类型

问：var 和泛型一起用有什么要注意的？
答：var 推断出的是编译时类型，可能存在泛型擦除问题：
    var list = new ArrayList<>();        // 推断为 ArrayList<Object>
    var list2 = new ArrayList<String>(); // 推断为 ArrayList<String>
```

> 🎯 **核心要点**：Java var 是严格的编译时语法糖——只在源代码中简化类型声明，字节码中已被具体类型替代。它没有改变 Java 的静态强类型本质，与 JavaScript 的运行时动态类型 var 完全不同。

### 3.3 枚举为什么可以实现线程安全的单例？单例模式用枚举好在哪里？

> **面试官意图**：考察枚举的编译原理和单例模式的经典实现对比

**标准答案（分层回答）：**

**表面层**：枚举单例是《Effective Java》推荐的最佳单例实现方式，JVM 保证了枚举实例创建的线程安全。

**原理层**：

**枚举的编译本质**：

```java
// 源代码
public enum Singleton {
    INSTANCE;

    public void doSomething() {}
}

// 编译后等价于（简化）
public final class Singleton extends Enum<Singleton> {
    public static final Singleton INSTANCE = new Singleton();

    private Singleton() {}

    public void doSomething() {}

    // 静态初始化块
    static {
        INSTANCE = new Singleton();
    }
}
```

枚举实例是 `static final` 字段，在**类加载阶段**由 JVM 保证线程安全：

- `static final` 字段在 `<clinit>()` 类初始化方法中赋值
- JVM 保证类的 `<clinit>()` 在类加载时只会被执行一次，且是线程安全的（JLS 12.4.2）
- 多个线程同时访问时，只有一个线程执行 `<clinit>()`，其他线程等待

**单例模式对比**：

| 实现方式 | 线程安全 | 防反射破坏 | 防序列化破坏 | 延迟加载 | 代码复杂度 |
|---------|---------|-----------|------------|---------|----------|
| 饿汉式 | 是 | 否 | 否 | 否 | 低 |
| 懒汉式（synchronized） | 是 | 否 | 否 | 是 | 中 |
| DCL（双重检查） | 是 | 否 | 否 | 是 | 高（需 volatile） |
| 静态内部类 | 是 | 否 | 否 | 是 | 中 |
| **枚举单例** | **是** | **是** | **是** | **否** | **最低** |

**枚举为什么防反射破坏？**

```java
// 反射创建枚举实例会抛异常
Constructor<Singleton> c = Singleton.class.getDeclaredConstructor();
c.setAccessible(true);
c.newInstance();
// 抛出：java.lang.NoSuchMethodException——枚举构造函数参数为 (String, int)
// 即使获取到真正的构造器 (String, int)，也会抛出：
// Cannot reflectively create enum objects (java.lang.reflect.Constructor.newInstance 源码拦截)
```

`Constructor.newInstance()` 源码中有针对枚举的判断：

```java
if ((clazz.getModifiers() & Modifier.ENUM) != 0)
    throw new IllegalArgumentException("Cannot reflectively create enum objects");
```

**枚举为什么防序列化破坏？**

- 枚举的序列化由 JVM 特殊处理
- 反序列化时，不是通过反射创建新对象，而是通过 `Enum.valueOf()` 返回已有的 INSTANCE
- 所以反序列化不会创建新的枚举实例

**加分项**：
- 指出枚举单例的缺点：不支持延迟加载（实例在类加载时就创建了）
- 指出可以通过枚举实现带参数的构造器：`INSTANCE("configValue")`
- 指出枚举可以实现接口，在单例中集成容器能力

**追问**：
```
问：如果枚举单例需要延迟加载怎么办？
答：用静态内部类 + 枚举：
    public class SingletonHolder {
        private enum EnumSingleton {
            INSTANCE;
            private final Singleton instance;
            EnumSingleton() { instance = new Singleton(); }
        }
        public static Singleton getInstance() {
            return EnumSingleton.INSTANCE.instance;
        }
    }

问：枚举在 JVM 中有哪些特殊处理？
答：1. 编译器生成 values() 方法——返回所有枚举值的数组副本
    2. valueOf(String) 通过名称查找枚举实例
    3. 枚举不能通过 newInstance 反射创建
    4. 枚举字段是 static final，但编译器做了特殊处理（values 数组的 clone 等）
```

> 🎯 **核心要点**：枚举单例不是语法糖——它是 JVM 底层对 enum 类型的特殊保障。类初始化过程的 JVM 锁 + 反射/序列化的安全拦截，使其成为《Effective Java》推荐的单例首选。

### 3.4 Stream API 是语法糖吗？它的性能一定比 for 循环好吗？

> **面试官意图**：考察对 Stream 底层实现的理解，以及在什么场景下选择用 Stream

**标准答案（分层回答）：**

**表面层**：Stream API 不是简单的语法糖，它是基于迭代器模式的 API 设计。性能方面不一定比 for 循环好，取决于数据量和操作复杂度。

**原理层**：

**Stream 不是语法糖，是 API 设计**

与之前讨论的语法糖（泛型擦除、自动装箱、增强 for 循环等）不同，Stream API 没有对应的编译期"去糖"过程。它的底层是：

1. **Spliterator**（可拆分迭代器）：Stream 的底层数据源访问器
2. **ReferencePipeline**：Stream 操作的管道封装（无状态/有状态操作）
3. **TerminalOp**：终止操作的实现（Reduce、Collect、ForEach 等）

```java
// Steam 的调用链（不是语法糖，是链式调用 + 管道模式）
list.stream()                         // 构建 Spliterator
    .filter(x -> x > 0)               // 构建无状态中间操作
    .map(String::valueOf)             // 构建无状态中间操作
    .sorted()                         // 构建有状态中间操作
    .collect(Collectors.toList());    // 终止操作（触发整个管道执行）
```

**性能对比**：

```text
| 场景                        | for 循环     | Stream（串行） | Stream（并行） |
|----------------------------|-------------|---------------|---------------|
| 简单操作（如过滤）+ 小数据量   | 最快        | 较慢（有开销）   | 最慢（线程开销） |
| 复杂操作 + 小数据量           | 较快        | 相当（Lambda 内联优化） | 最慢         |
| 简单操作 + 大数据量（10^5+）  | 快          | 相当           | 可能更快       |
| 多操作链 + 大数据量           | 中（多次循环） | 快（一次遍历） | 更快（分治）   |
| 多核 CPU + 大数据量（10^7+）  | 慢          | 快             | 最快（并行优势）|
```

**性能差异的根本原因**：

```java
// for 循环——直接内存操作，无额外抽象开销
int sum = 0;
for (int i = 0; i < list.size(); i++) {
    if (list.get(i) > 0) sum += list.get(i);
}

// Stream——有管道对象创建、Lambda 调用、Spliterator 遍历等开销
int sum = list.stream()
    .filter(x -> x > 0)
    .mapToInt(Integer::intValue)
    .sum();
```

**Stream 的开销来源**：
1. 创建 Stream 对象（ReferencePipeline 链）
2. Lambda 调用开销（虽然 invokedynamic 优化了，但仍有调用过站的 cost）
3. 基本类型装箱拆箱（除非用 `IntStream`、`LongStream`、`DoubleStream`）
4. Spliterator 的 `tryAdvance` / `forEachRemaining` 每次调用都是虚方法

**加分项**：
- 指出 IntStream/LongStream/DoubleStream 避免了装箱拆箱开销
- 指出 `.parallelStream()` 并不总是更快——有线程调度、拆分、合并的开销
- 指出 JDK 的自适应优化：Stream 在多次运行后 JIT 可以进行更激进的优化

**追问**：
```
问：什么时候应该选择 Stream，什么时候应该选择 for 循环？
答：选择 Stream
    - 需要链式操作（filter → map → reduce）
    - 大数据量需要并行处理
    - 代码可读性要求高（声明式优于命令式）
    选择 for 循环：
    - 小数据量，简单逻辑
    - 需要 break/return/continue 控制流
    - 性能极度敏感的场景
    - 处理 checked exception 更方便

问：parallelStream 的线程池可以配置吗？
答：默认使用 ForkJoinPool.commonPool()
    可以通过 System.setProperty("java.util.concurrent.ForkJoinPool.common.parallelism", "8")
    或在自定义 ForkJoinPool 中提交并行任务来控制
```

> 🎯 **核心要点**：Stream 不是语法糖，是基于 Spliterator 的声明式 API。性能不是它的设计目标（可读性和声明式才是），但大数据量 + 并行流下有优势。小数据量场景 for 循环更快。

### 3.5 javap 反编译看到的 String 拼接用了 invokedynamic 是什么意思？

> **面试官意图**：考察 JDK 9 的字符串拼接优化，invokedynamic 机制，以及和传统 StringBuilder 的区别

**标准答案（分层回答）：**

**表面层**：JDK 9+ 的字符串常量拼接不再使用 StringBuilder，而是使用 `invokedynamic` 指令动态调用拼接策略。

**原理层**：

**JDK 9 的变化**：

```java
// 源代码
String s = a + "," + b;

// JDK 5~8 反编译结果
String s = new StringBuilder().append(a).append(",").append(b).toString();

// JDK 9+ 反编译结果
String s = (String) INVOKEDYNAMIC makeConcatWithConstants(
    [a, b],               // 动态参数
    "(,)"     // 拼接模板（占位符 ）
);
```

**invokedynamic 的核心组件**：

```text
┌──────────────────────────────────────────────────────────┐
│                    invokedynamic 核心三要素               │
├────────────┬─────────────────────────────────────────────┤
│ Bootstrap  │ LambdaMetafactory 或 StringConcatFactory    │
│ Method     │ .makeConcatWithConstants()                   │
│ (BSM)      │                                              │
├────────────┼─────────────────────────────────────────────┤
│ CallSite   │ 静态或可变调用点                             │
│            │ 指向实际拼接方法的句柄                       │
├────────────┼─────────────────────────────────────────────┤
│ Method     │ 指向 BSM 返回的 CallSite 的目标方法         │
│ Handle     │ 运行时实际调用的拼接策略                     │
└────────────┴─────────────────────────────────────────────┘
```

**JDK 9+ 的拼接策略**：

`StringConcatFactory` 提供了多种策略，根据参数数量、JVM 配置动态选择：

| 策略 | 实现方式 | 适用场景 |
|------|---------|---------|
| `BC_SB` | 使用 StringBuilder（兼容模式） | 复杂拼接 |
| `BC_SB_SIZED` | 已知长度的 StringBuilder | 可预计算最终长度 |
| `BC_SB_SIZED_EXACT` | 精确长度的 StringBuilder | 长度精确可知 |
| `MH_SB_SIZED_EXACT` | MethodHandle 版本 | 同上，基于方法句柄 |
| `MH_INLINE_SIZE_EXACT` | **直接分配 byte[] 数组** | JDK 15 默认，最高效 |

**为什么 JDK 9 要改用 invokedynamic？**

1. **延迟决策**：拼接策略可以推迟到运行时决定，JVM 可以选择最优策略
2. **避免 StringBuilder 对象开销**：对于小字符串，直接操作 byte[] 更高效
3. **未来优化不需要重编译**：JDK 升级后，不用重新编译源代码就能获得新的拼接优化
4. **模板字符串铺垫**：为未来的 String Templates（JDK 21 Preview）做技术准备

**加分项**：
- 指出 `makeConcatWithConstants` 使用拼接模板（recipe），模板中的 `` 是参数占位符
- 指出 JDK 15 默认策略 `MH_INLINE_SIZE_EXACT` 直接预分配精确大小的 byte[]，写入后构造 String，减少了 StringBuilder 扩容的开销
- 指出循环内拼接在 JDK 9+ 也没有被特殊优化——循环体仍然需要手动使用 StringBuilder

**追问**：
```
问：invokedynamic 和普通方法调用相比有什么优势？
答：1. 方法调用策略可以推迟到运行时决定
    2. 支持动态语言的语言级特性（但 Java 的 invokedynamic 主要用于 Lambda 和字符串拼接）
    3. 允许 BSM 返回不同 CallSite，实现自适应的调用策略

问：为什么循环内的 + 号拼接 JDK 9+ 还是慢？
答：invokedynamic 虽然优化了单次拼接，但循环体每轮迭代仍然会：
    1. 构建参数数组或列表
    2. 调用 makeConcatWithConstants
    3. 分配新的 String 对象
    和 JDK 8 的 StringBuilder 循环内问题本质上一样——每次迭代都创建新对象
```

> 🎯 **核心要点**：JDK 9 的 invokedynamic 字符串拼接不是新的语法糖，而是拼接实现策略的升级。核心变化是从「编译期固定策略（StringBuilder）」变成「运行期动态选择」，让 JVM 可以选择最优的拼接方式。

### 4.1 使用 Sealed Class + Pattern Matching + Record 设计订单状态机

> **面试官意图**：考察 Java 17+ 新特性的综合运用，以及能否在实战中结合语言特性做领域建模

**标准答案：**

**设计目标**：用 Java 的语言级特性（非设计模式库）实现一个类型安全、编译期可验证的订单状态机。

```java
// 1. 密封类——订单状态的有限集合
// JDK 17+：sealed class 限定子类只能是指定的几种
public sealed interface OrderState
    permits PendingState, PaidState, ShippedState,
            DeliveredState, CancelledState, ReturnedState {

    // 每个状态可以关联一个描述
    String description();
}

// 2. 使用 Record 表示各状态——不可变，天然值对象
record PendingState(String paymentMethod, LocalDateTime createdAt)
    implements OrderState {
    public String description() { return "待支付：" + paymentMethod; }
}

record PaidState(String transactionId, LocalDateTime paidAt, BigDecimal amount)
    implements OrderState {
    public String description() { return "已支付：" + transactionId; }
}

record ShippedState(String logisticsNo, String carrier, LocalDateTime shippedAt)
    implements OrderState {
    public String description() { return "已发货：" + logisticsNo; }
}

record DeliveredState(LocalDateTime deliveredAt, String signatory)
    implements OrderState {
    public String description() { return "已签收：" + signatory; }
}

record CancelledState(String reason, LocalDateTime cancelledAt)
    implements OrderState {
    public String description() { return "已取消：" + reason; }
}

record ReturnedState(String returnNo, LocalDateTime returnedAt, String reason)
    implements OrderState {
    public String description() { return "已退货：" + returnNo; }
}

// 3. 订单实体
public class Order {
    private final String orderId;
    private OrderState state;        // 当前状态
    private final List<OrderState> history;  // 状态变更历史

    public Order(String orderId) {
        this.orderId = orderId;
        this.state = new PendingState("微信支付", LocalDateTime.now());
        this.history = new ArrayList<>();
        this.history.add(this.state);
    }

    // 状态转换方法——使用 Pattern Matching for switch（JDK 21+）
    public OrderState transit(OrderEvent event) {
        OrderState newState = switch (event) {
            // 模式匹配：匹配状态 + 事件的组合
            case PAY (PayEvent e) when state instanceof PendingState -> {
                var s = (PendingState) state;
                yield new PaidState(e.transactionId(), LocalDateTime.now(), e.amount());
            }
            case SHIP (ShipEvent e) when state instanceof PaidState -> {
                var s = (PaidState) state;
                yield new ShippedState(e.logisticsNo(), e.carrier(), LocalDateTime.now());
            }
            case DELIVER (DeliverEvent e) when state instanceof ShippedState -> {
                yield new DeliveredState(LocalDateTime.now(), e.signatory());
            }
            case CANCEL (CancelEvent e) when state instanceof PendingState -> {
                yield new CancelledState(e.reason(), LocalDateTime.now());
            }
            case RETURN (ReturnEvent e) when state instanceof DeliveredState -> {
                yield new ReturnedState(e.returnNo(), LocalDateTime.now(), e.reason());
            }
            default -> throw new IllegalStateException(
                "订单 " + orderId + " 当前状态 " + state + " 不允许事件 " + event
            );
        };

        // 更新状态并记录历史
        this.state = newState;
        history.add(newState);
        return newState;
    }

    // 获取当前状态——模式匹配解构
    public void printCurrentState() {
        if (state instanceof PendingState(var method, var createdAt)) {
            System.out.printf("待支付，支付方式：%s，创建时间：%s%n", method, createdAt);
        } else if (state instanceof ShippedState(var no, var carrier, var time)) {
            System.out.printf("已发货，物流号：%s，承运方：%s%n", no, carrier);
        }
        // Record 的 Pattern Matching 解构可以直接访问组件
    }
}

// 4. 事件类型——也用 sealed + record
public sealed interface OrderEvent permits PayEvent, ShipEvent,
    DeliverEvent, CancelEvent, ReturnEvent {}

record PayEvent(BigDecimal amount, String transactionId) implements OrderEvent {}
record ShipEvent(String logisticsNo, String carrier) implements OrderEvent {}
record DeliverEvent(String signatory) implements OrderEvent {}
record CancelEvent(String reason) implements OrderEvent {}
record ReturnEvent(String returnNo, String reason) implements OrderEvent {}
```

**为什么这种方式优于传统实现？**

| 维度 | 传统枚举 + switch | 这种设计 |
|------|------------------|---------|
| 类型安全 | `switch` 没有穷尽性检查 | sealead class 编译器检查所有子类 |
| 状态数据 | 需要额外 Map 或 class 存储 | Record 直接封装状态数据 |
| 模式匹配 | 需要 instanceof + 强制转换 | 自动解构，无需强制转换 |
| 非法状态 | 运行时才能发现 | 编译期 sealed 保证状态集合有限 |
| 不可变性 | 状态对象可变 | Record 天然不可变 |

> 🎯 **核心要点**：Sealed Class 限制了类型的有限集合，Record 提供了不可变的数据载体，Pattern Matching 提供了简洁的解构方式。三者结合可以写出类型安全、编译期验证的领域模型。

### 4.2 如何利用 try-with-resources 管理多个资源？释放顺序是怎样的？

> **面试官意图**：考察多资源管理的正确释放顺序和异常处理细节

**标准答案：**

**基本用法**：

```java
// 多资源声明——用分号分隔
try (InputStream is = new FileInputStream("input.txt");
     OutputStream os = new FileOutputStream("output.txt")) {

    byte[] buffer = new byte[1024];
    int len;
    while ((len = is.read(buffer)) != -1) {
        os.write(buffer, 0, len);
    }
}
```

**释放顺序（LIFO——后进先出）**：

```java
// 源代码：先声明 is，再声明 os
try (Resource r1 = new Resource("r1");
     Resource r2 = new Resource("r2");
     Resource r3 = new Resource("r3")) {
    // 使用资源
}
// 关闭顺序：r3.close() → r2.close() → r1.close()（LIFO）
```

**LIFO 顺序的验证**：

```java
class OrderedResource implements AutoCloseable {
    private final String name;
    OrderedResource(String name) { this.name = name; }
    @Override
    public void close() {
        System.out.println("Closing: " + name);
    }
}

// 输出：
// Closing: r3
// Closing: r2
// Closing: r1
```

**为什么是 LIFO？**

LIFO（Last-In-First-Out）释放顺序保证了资源的依赖安全：
- 如果资源之间存在依赖关系（如外层流包装内层流），先释放外层资源是安全的
- 例如：`BufferedWriter bw = new BufferedWriter(new FileWriter("test.txt"))`，应当先 flush 并关闭 bw，再关闭 FileWriter

**多资源异常处理机制**：

```java
// 源码
try (Resource r1 = new Resource("r1");
     Resource r2 = new Resource("r2")) {
    throw new RuntimeException("业务异常");
}

// 编译后等价逻辑
Resource r1 = null;
Resource r2 = null;
Throwable primary = null;
try {
    r1 = new Resource("r1");
    r2 = new Resource("r2");
    throw new RuntimeException("业务异常");
} catch (Throwable t) {
    primary = t;
    throw t;
} finally {
    // r2 先关闭（后进先出）
    if (r2 != null) {
        if (primary != null) {
            try { r2.close(); }
            catch (Throwable suppressed) { primary.addSuppressed(suppressed); }
        } else {
            r2.close();
        }
    }
    // r1 后关闭
    if (r1 != null) {
        if (primary != null) {
            try { r1.close(); }
            catch (Throwable suppressed) { primary.addSuppressed(suppressed); }
        } else {
            r1.close();
        }
    }
}
```

**JDK 9 增强（Effectively Final 变量）**：

```java
// JDK 9+：可以在 try 中使用 effectively-final 变量
InputStream is = new FileInputStream("a.txt");
OutputStream os = new FileOutputStream("b.txt");
try (is; os) {
    // 使用资源
}
// 这样可以使资源获取和 try 块分离，灵活性更高
```

> ⚠️ **常见坑点**：
> 1. 资源变量不在 try 块内声明就无法自动关闭
> 2. `try-with-resources` 不能和传统的 `try-catch-finally` 同时使用（资源关闭已经在 finally 中处理了）
> 3. 所有资源必须实现 `AutoCloseable` 或 `Closeable`
> 4. 多个资源时，任何一个资源的 `close()` 抛出异常都不影响其他资源的关闭

**追问**：
```
问：Nested try-with-resources 和 Multi-resource try-with-resources 有区别吗？
答：
// Nested——内层 stream 包装外层，自动处理
try (FileInputStream fis = new FileInputStream("a.txt")) {
    try (BufferedInputStream bis = new BufferedInputStream(fis)) {
        // ...
    }
}
// 等价于 Multi-resource，但更冗长。推荐用多资源声明形式。

问：如果 r1 的 close() 和 r2 的 close() 都抛异常，最终能捕获到几个异常？
答：主异常（来自 try 块）+ r2.close() 的异常（抑制）+ r1.close() 的异常（抑制）
    一共 3 个异常。但 r1.close() 如果也抛异常，它会被抑制到主异常上
    而不是覆盖 r2.close() 的抑制异常。这是 JDK 7 改进的关键点。
```

> 🎯 **核心要点**：多资源 try-with-resources 按声明顺序初始化，按 LIFO 顺序关闭。关闭异常被抑制（Suppressed）到主异常上，不会丢失。

### 5.1 Lambda 追问链：Lambda → invokedynamic → MethodHandle → CallSite

```
追问路径（从浅到深）：

Q1: Lambda 表达式在字节码层面是怎么调用的？
→ invokedynamic 指令 + LambdaMetafactory

Q2: invokedynamic 和普通方法调用（invokevirtual/invokestatic）有什么区别？
→ 普通调用在编译期已经确定调用目标
→ invokedynamic 在首次调用时由 Bootstrap Method 确定目标
→ 后续调用可以直接跳转（CallSite 已解析）

Q3: Bootstrap Method（BSM）是什么？在哪里定义的？
→ 每个 invokedynamic 指令在常量池中关联一个 BSM 的 MethodHandle
→ 对于 Lambda，BSM 是 LambdaMetafactory.metafactory()
→ BSM 接收参数：MethodHandles.Lookup, String, MethodType, MethodType, MethodHandle, MethodType

Q4: MethodHandle 是什么？和反射的 Method 有什么区别？
┌─────────────────────┬────────────────────┬─────────────────────┐
│ 对比项              │ MethodHandle        │ java.lang.reflect    │
├─────────────────────┼────────────────────┼─────────────────────┤
│ 访问控制检查         │ 创建时检查          │ 每次调用检查         │
│ 内联优化             │ 是（JIT 可直接内联） │ 难内联              │
│ 函数式               │ 可以绑定参数         │ 不可以              │
│ 性能                 │ 高（接近直接调用）    │ 低（反射有拦截）     │
│ 类型安全             │ 编译期类型匹配        │ 运行期类型转换       │
└─────────────────────┴────────────────────┴─────────────────────┘

Q5: CallSite 有哪些类型？分别有什么区别？
→ ConstantCallSite：永久指向同一个目标方法句柄（Lambda 用这个）
→ MutableCallSite：可以在运行时切换目标
→ VolatileCallSite：线程安全版本的可变 CallSite

Q6: Lambda 的 CallSite 是哪种？
→ 是 ConstantCallSite——Lambda 的目标方法一旦确定就不会改变
→ 因为 Lambda 的方法体是固定的，不会运行时改变
→ 但首次调用会触发 BSM 创建 CallSite，后续直接跳转

最终问题：所有 Lambda 在首次调用后，性能是否就和普通方法调用一样？
理论上接近，但仍有差别：
1. invokedynamic 指令本身比 invokevirtual 多一些开销
2. Lambda 生成的内部方法（Lambda 体）会被 JIT 编译
3. 经过 JIT 内联优化后，差距微乎其微
```

### 5.2 装箱追问链：装箱 → Integer.valueOf → 缓存机制 → 如何修改上限

```
追问路径（从浅到深）：

Q1: Integer i = 200 编译后是什么？
→ Integer.valueOf(200)

Q2: valueOf 的源码看过吗？
→ 见前面 1.2 节的源码

Q3: IntegerCache 的 high 默认是多少？怎么修改？
→ 默认 127，可以通过 JVM 参数修改：
    -XX:AutoBoxCacheMax=1000
→ 读取逻辑在 IntegerCache 的静态初始化块中：
    private static class IntegerCache {
        static final int low = -128;
        static final int high;
        static final Integer cache[];
        static {
            int h = 127;
            String integerCacheHighPropValue =
                VM.getSavedProperty("java.lang.Integer.IntegerCache.high");
            if (integerCacheHighPropValue != null) {
                try {
                    int i = parseInt(integerCacheHighPropValue);
                    i = Math.max(i, 127);
                    h = Math.min(i, Integer.MAX_VALUE - (-low) - 1);
                } catch (NumberFormatException nfe) {
                }
            }
            high = h;
            cache = new Integer[(high - low) + 1];
            int j = low;
            for (int k = 0; k < cache.length; k++)
                cache[k] = new Integer(j++);
        }
    }

Q4: 为什么不把缓存上限设得特别大（比如 1 亿）？
→ 每个 Integer 对象约 16 字节，缓存 1 亿个需要 1.6 GB 内存
→ 实践中缓存到 10000 或 65535 比较常见
→ 需要权衡内存和性能

Q5: 设置 AutoBoxCacheMax=10000 后，new Integer(5000) 也会走缓存吗？
→ 不会！new 关键字不会调用 valueOf()
→ 只有自动装箱（编译成 valueOf）才会走缓存
→ 显式 new Integer() 每次都是新对象

Q6: Boolean 有缓存吗？为什么？
→ Boolean 只有两个值：TRUE 和 FALSE，是静态 final 常量
→ 不存在"缓存"的概念——这两个值始终是同一个对象

Q7: Integer 的 == 在什么情况下一定是 false？
→ 1. 靠 new Integer() 创建的（不经过 valueOf）
→ 2. 值超出缓存范围且没有修改 AutoBoxCacheMax
→ 3. 一侧用了 new，一侧是自动装箱
```

### 5.3 泛型追问链：泛型擦除 → 桥方法 → Signature 属性 → 反射获取泛型

```
追问路径（从浅到深）：

Q1: 泛型擦除后，子类重写父类泛型方法是怎么保证多态的？
→ 编译器生成桥方法（Bridge Method）

Q2: 桥方法是什么？举个例子？
class Parent<T> {
    public T getValue() { return null; }
}
class Child extends Parent<String> {
    @Override
    public String getValue() { return "hello"; }
}
→ 编译后在 Child 中会生成一个桥方法：
    // 桥方法——返回类型 Object，调用了子类的 String 版本
    public Object getValue() {
        return this.getValue();  // 调用 String getValue()
    }
→ 这就是为什么 @Override 可以标记在返回类型不同的方法上

Q3: 反射能不能获取到泛型信息？
→ 对于字段和方法签名，如果声明中写了泛型，可以通过反射获取
→ 因为 class 文件的 Signature 属性保留了泛型信息：
    Field f = MyClass.class.getDeclaredField("list");
    Type t = f.getGenericType();  // ParameterizedType: List<String>
→ 但如果是局部变量的泛型，在运行时无法获取

Q4: Signature 属性在 class 文件中是怎么存的？
→ 对于字段和方法，class 文件可以有一个可选的 Signature 属性
→ 存储的是泛型签名的字符串形式：
    "Ljava/util/List<Ljava/lang/String;>;"
→ 反射的 getGenericType()/getGenericParameterTypes() 读取的就是这个

Q5: 为什么 List<String>.class 不能编译？
→ 因为泛型信息在运行时不存在
→ List.class 是唯一的
→ 参数化类型没有对应的 Class 对象

Q6: 泛型数组为什么不能直接创建？T[] arr = new T[10] 为什么编译错误？
→ 类型擦除后，new T[10] 变成 new Object[10]
→ 赋值给实际类型时，可能造成类型安全问题
→ 应该使用 (T[]) new Object[10] 并加上 @SuppressWarnings("unchecked")
→ 更好的方案：使用 ArrayList<T> 代替数组
```
