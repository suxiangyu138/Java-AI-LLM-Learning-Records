## 1. 构建与依赖管理

| 维度 | Java | Python |
|------|------|--------|
| 构建工具 | Maven / Gradle（声明式 + 生命周期） | 无编译步骤（解释执行） |
| 依赖管理 | pom.xml / build.gradle（版本矩阵 + 传递依赖） | pip / uv / poetry（requirements / pyproject.toml） |
| 锁文件 | 内置传递依赖解析（Maven 树） | pip-tools / uv lock（2024+ 标准实践） |
| 虚拟环境 | 无（JVM 隔离靠类加载器/容器） | venv / conda / uv（环境隔离是基本盘） |
| 构建产物 | jar/war 单体物、模块化 | wheel/sdist、无需"构建" |

Python 侧 2026 年的主角是 **uv**（Rust 实现的新一代工具）：比 pip 快一个数量级，同时管理依赖、虚拟环境与锁文件，逐步取代 poetry/pipenv 成为社区推荐。Java 侧的 Maven/Gradle 在"构建编排"（多模块、插件、生命周期）上无可替代，两者面对的复杂度不同——**Java 的复杂度在构建本身，Python 的复杂度在环境一致性**（"在我机器上能跑"）。

## 2. 类型检查：编译器 vs mypy/pyright

- **Java**：类型检查是编译的一部分——写错类型直接编译失败，CI 第一道门就是编译。零额外成本
- **Python**：运行时才验类型，工程化靠**类型标注 + 静态检查器**（mypy/pyright）补课——pyright 基于 TypeScript 实现、速度快，2026 年社区主流

```python
# 类型标注是"可选契约"——不标注也能跑，标注了才有检查
def calculate(amount: Decimal, rate: float) -> Decimal:
    return amount * Decimal(str(rate))       # mypy 可发现类型错误，解释器不会

# 严格模式的工程价值：CI 里跑 mypy --strict，错误在合并前暴露
```

工程含义：Python 项目的"类型纪律"是**团队自觉**（CI 强制才有用），Java 是**语言强制**。mypy/pyright 的标注成本（泛型、重载、回调类型）对新手不友好，但 2026 年的中型 Python 项目（FastAPI + Pydantic）已天然携带类型信息——Pydantic 模型的标注同时服务校验与检查器，收益明显。

## 3. 测试体系：JUnit vs pytest

| 维度 | Java | Python |
|------|------|--------|
| 测试框架 | JUnit 6.x / TestNG | pytest（事实标准） |
| 断言 | AssertJ（流式断言） | 内置 assert + pytest.raises |
| 参数化 | @ParameterizedTest | @pytest.mark.parametrize |
| Mock | Mockito | pytest-mock / unittest.mock |
| 覆盖率 | JaCoCo | coverage.py + pytest-cov |
| Fixture | @BeforeEach/@AfterEach | fixture 依赖注入（scope 管理） |

pytest 的 **fixture 机制**是效率王牌：`scope="session"` 的共享数据库、依赖注入式参数、autouse 自动应用——Java 侧要更多样板。但 Java 的测试生态**深度**占优：JUnit 扩展模型（参数解析、超时、顺序）、Spring Boot Test（切片测试、Testcontainers）与 CI 集成成熟度更高。两者都能支撑企业级测试金字塔，Python 的写法更短，Java 的体系更重。

测试哲学的差异延伸到**测试即文档**的程度：Java 侧 `@SpringBootTest` 与 Testcontainers 让"真实环境集成测试"成为家常便饭（起真实 Redis/MySQL 容器），Python 侧主流是 mock 与 SQLite 替身，真实依赖的集成测试靠 docker-compose 手工编排——这使 Java 的回归保障更"重而全"，Python 更"轻而快"。权衡建议：**核心业务（尤其跨服务调用）用 Java 的重测试体系，模型与工具类服务用 Python 的轻测试体系**——两边测试文化在混合架构里各司其职，不必统一。

## 4. 打包部署与容器化

- **Java**：构建出胖 jar（Spring Boot）直接 `java -jar`，或 GraalVM Native Image 编译为原生可执行（毫秒启动、6.5MB 级）；容器镜像有成熟的多阶段构建模板；JVM 调优（堆、GC）是运维必修
- **Python**：`pip install -r requirements` 或 uv sync；无"编译产物"，部署 = 代码 + 依赖 + 解释器版本；容器镜像大小（依赖 Python + 站点包）通常数百 MB，可用 slim 镜像/虚拟环境裁剪；无运行时调优概念，主要管**依赖版本锁定与 ABI 兼容**（Python 3.13/3.14 扩展 ABI 变化是运维痛点）

```dockerfile
# Python 镜像：版本锁定 + 非 root + 分层缓存（2026 标准模板）
FROM python:3.14-slim
COPY --from=uv /uv /usr/local/bin/uv
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev
COPY . .
USER app
```

部署哲学差异：Java 的"产物"概念（jar/镜像一次构建到处跑）与 JVM 一致性强；Python 的环境一致性依赖锁文件 + 镜像模板的纪律——uv.lock 是 2026 年"可复现部署"的默认答案。

## 5. 可观测性与排障

- **Java**：可观测性是 JVM 原生能力——JFR（飞行记录器，JDK 14+ 免费）、JMX、Arthas 动态诊断、Mat 堆分析；框架级集成（Micrometer → Prometheus/OTel）成熟，Java 是"最容易被监控的语言"之一
- **Python**：cProfile/py-spy（采样 profiler，免插桩）、tracemalloc；框架级埋点靠 OpenTelemetry Python SDK + 各框架插件；性能排障手段相对原始（无 JFR 等价物），**"慢在哪"通常靠 py-spy 采样 + 日志推理**

```bash
# Java：生产排障三板斧（无需重启）
jcmd <pid> JFR.start  /  jstack <pid>  /  arthas watch 类 方法

# Python：采样定位 CPU 热点
py-spy top --pid <pid>    # 每 N 秒采样调用栈，无需重启
```

排障哲学的差异：Java 的工具链让"黑盒排障"成为标准姿势（JFR 事故后复盘）；Python 更依赖日志质量与测试覆盖——这在大规模生产环境是真实的能力差，也是"Java 适合长寿命系统"的运维注脚。

CI/CD 与发布节奏的差异同样真实：Java 构建（Maven 生命周期 + 多模块 + 插件）天然适合"门禁式"流水线（编译、单测、集成测、静态检查、制品签名），Spring Boot 的 Actuator 健康检查是 K8s 探针的事实标准；Python 的流水线主要做 lint（ruff/black）、类型检查、pytest 与镜像构建——**CI 的"硬门禁"更少**，质量更多依赖工具纪律。发布上，Java 常打"镜像 + 滚动/蓝绿"（进程启动慢所以要探针配合），Python 镜像小、启动快，配合 uv.lock 可复现部署反而简单。两边在 2026 年的共同趋势是把质量左移（SonarQube/Semgrep、ruff 安全规则），但 Java 生态的"质量门禁栈"（Sonar + JaCoCo 覆盖率 + OWASP 依赖扫描）依然是更完整的工业标准。

## 6. 人才供给与存量维护

- **Java**：企业后端人才储备巨大且稳定（TIOBE 长期前列），存量系统海量——老项目维护（JDK 8→21 迁移、Spring Boot 升级）构成长期市场；**Java 工程师"稀缺性低、确定性高"**
- **Python**：数据科学/AI 人才增量快，但"纯 Python 后端工程师"供给小于 Java 后端；存量 Python 系统多为 AI/数据/自动化——**Python 工程师"稀缺性看赛道、流动性高"**
- 2026 新变量：AI 编程助手压低了两语言的入门成本——但**深度维护能力**（读五年老代码、排分布式故障）依然是 Java 工程师的护城河；Python 侧的新机会在"AI 应用工程师"（模型集成 + 后端）这一新岗位

招聘视角再补两组信号：**Java 岗位的"宽"**——金融、电商、云厂商、中间件公司全年大量供给，地域分布均匀，是"到哪都有饭吃"的底盘；**Python 岗位的"尖"**——AI 公司、数据平台、量化团队高薪集中在少数赛道，行情波动与 AI 融资周期强相关。对校招生的现实建议：**Java 保底、Python 增值**——先拿 Java 体系站稳（本仓库 01/02 层），再用 Python AI 能力（03 层）争取溢价岗位；对团队而言，**技术选型与招聘市场互相成全**——选 Java 意味着容易补人但同质竞争，选 Python 意味着人才溢价但供给聚焦，这个权衡直接影响扩产速度。

> 🎯 **核心要点**：工程化对比的本质是"体系化 vs 轻量化"——Java 的 Maven/JFR/Arthas 是几十年沉淀的工程体系，Python 的 uv/pytest/py-spy 是高效但需自觉纪律的工具集。Java 工程化适合"多人、长期、高可用"的系统，Python 工程化适合"小团队、快迭代、模型密集"的系统。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 依赖管理：Java 的复杂度在构建（Maven/Gradle），Python 的复杂度在环境一致性（venv + uv lock）；
> 2. 类型检查与测试纪律：Java 是语言/框架强制，Python 靠 mypy + pytest 自觉补课，CI 强制才有用；
> 3. 可观测性：JFR/Arthas 让 Java 具备黑盒排障能力，Python 用 py-spy + OTel 达到七成效果。

3. pytest 的 fixture 与 JUnit 的 @BeforeEach 差在哪？（→ 3 节）
4. 为什么说 JFR 是 Java 排障的"黑盒能力"？（→ 5 节）
