## 1. 选型决策树：六类场景六种结论

按"系统画像"判断，先对号入座：

| 场景 | 画像 | 结论 |
|------|------|------|
| 核心交易系统 | 订单/支付/库存、强一致、五年+ | **Java**（事务/治理/可观测是生死线） |
| 高并发网关/平台 | 万级 QPS、延迟敏感 | **Java**（虚拟线程 + JIT，单机吞吐） |
| 企业 AI 应用 | RAG/Agent、接业务系统 | **Java 为主体 + Python 模型服务**（混合架构） |
| 数据科学/训练 | notebook、实验、算法迭代 | **Python**（生态密度无对手） |
| 模型服务/推理 | vLLM/FastAPI 包装模型 | **Python**（推理生态 + 与训练同栈） |
| 内部工具/快速原型 | 管理后台、脚本、MVP | **Python**（Django Admin + 开发速度） |

决策口诀：**"钱与交易"选 Java，"模型与实验"选 Python，"都要"就混合**——真实公司里 70% 的场合答案是"混合"，剩下的 30% 才有资格二选一。选型不是信仰问题，是"系统画像 × 团队能力 × 维护预算"的交集。

做决策前还要过一遍**否决条件**，任何一条命中都要停下来重新谈：

- 团队只有 3 人且无 Java 经验，却要选 Java 微服务——先问"能不能用单体 + Python 起步"，规模上去了再演进
- 系统强一致 + 五年维护，却只有 Python 团队——补 Java 人员或外聘，比用 Python 硬扛交易核心的长期成本低
- 公司已有一套成熟 Java 中台，新 AI 项目却想全 Python——优先用混合架构接入中台能力，别另起炉灶
- 数据科学团队强烈依赖 Python 生态（微调/实验），业务却要 Java——这正是混合架构的标准场景，别互相说服

否决条件的本质是"**成本错配**"：语言不是问题，团队、治理、生态的错配才是问题。选型评审的标准模板就是"画像 + 否决条件 + 混合边界"三问。

## 2. 场景案例一：电商核心交易系统

**画像**：订单、库存、支付、对账；高并发促销；五年以上生命周期。

- **选 Java**：分布式事务（Seata）、库存扣减（Redis Lua + 分布式锁）、限流熔断（Sentinel）、微服务拆分（Spring Cloud）——每个需求都是 Java 生态的成熟主场；交易链路延迟敏感，JIT + 虚拟线程的单机吞吐直接换算成机器数与用户体验
- **Python 的角色**：电商的推荐系统、画像服务、风控模型——模型侧 Python 训练 + 服务化，通过 gRPC/消息接入 Java 交易主链路
- **结论**：核心链路全 Java；模型与个性化能力 Python 黑盒接入。这正是本仓库 04 层「SuGuangMall/FlavorDash」项目体系的现实蓝本——**交易代码用 Java 写，AI 能力用 Python 供**。

## 3. 场景案例二：企业 AI 应用平台

**画像**：企业内部 RAG/Agent 平台（知识库问答、文档助理、流程自动化）；要对接企业现有系统（权限、审批、工单）。

- **选混合（Java 主体）**：Agent 编排、工具调用、权限治理、审计日志——这些是"业务工程"，Java 的 Spring AI 2.0 + MCP 工具 + 微服务治理栈直接复用企业既有 Java 体系；62% 企业用 Java 写 AI 功能的数据在这里兑现
- **Python 的角色**：模型服务层（FastAPI + vLLM 包装）、Embedding/重排、微调任务——保持"模型侧 Python、应用侧 Java"的黑盒分工
- **结论**：这是 2026 年最典型的"Java 工程师 AI 转型"场景——Java 技能全部复用，只需补 LLM 协议与 RAG 知识（本仓库 03-AI 体系正是为此设计）

## 4. 场景案例三：数据分析与内部工具

**画像**：报表、数据探索、运营后台、一次性脚本；小团队、快交付。

- **选 Python**：pandas/notebook 分析闭环、Django Admin 三天出后台、脚本零构建——速度即价值
- **Java 的角色**：若数据量大且要长期稳定（数仓接口、数据平台底座），Java 的批处理生态（Spring Batch/Flink）更稳；但多数"分析 + 工具"场景 Python 全包
- **结论**：**速度敏感选 Python，稳定敏感选 Java**——这条规律在工具类场景里几乎永远正确

## 5. Java→Python 学习迁移图

Java 工程师学 Python 的正确顺序（借已有的工程心智，不从头学编程）：

| 心智复用 | Python 对照 | 学习要点 |
|---------|------------|---------|
| 变量与类型 | 动态类型 + 标注 | 忘掉"编译期检查"，拥抱 `Optional[T]` 标注 |
| 类与对象 | 类/`@dataclass`/协议 | `record` ≈ `@dataclass`，接口 ≈ Protocol |
| lambda | lambda/函数一等公民 | 更自由，直接传函数即可 |
| Stream | 列表推导/生成器 | `map/filter` 变成表达式语法 |
| 异常 | try/except | 无受检异常，别到处 catch |
| 构建 | uv/venv | 环境隔离是 Python 的第一课 |
| 测试 | pytest | fixture 比 @BeforeEach 灵活得多 |
| 后端 | FastAPI/Django | 对照 Spring 的控制器/ORM/DI 学映射 |

**最快路径**：直接做"用 FastAPI 重写一个 Spring CRUD"的小项目，映射式学习，一周即可上手；随后进本仓库 03-AI 的「Python 异步 + FastAPI」体系精进。

## 6. Python→Java 学习迁移图

Python 工程师学 Java 的顺序（反向映射）：

| 心智复用 | Java 对照 | 学习要点 |
|---------|----------|---------|
| 动态类型 | 静态类型 | 编译期契约，IDE 重构能力全开 |
| `@dataclass` | record | 语法更短但能力等价 |
| 鸭子类型 | 接口/sealed | 契约显式化，穷尽性检查 |
| 生成器/推导 | Stream | 管线心智一致，API 更长 |
| asyncio | 虚拟线程 | 同步代码 + 虚拟线程更简单 |
| pytest | JUnit + AssertJ | 样板多，生态深 |
| pip/venv | Maven/Gradle | 构建概念需从零建立 |
| Django | Spring Boot | 全家桶对全家桶，DI 是新概念 |

**最快路径**：对照写一遍"Spring Boot CRUD + JPA"，重点理解依赖注入容器与事务传播——这是 Python 生态没有的两个概念；随后走本仓库 01/02 层 Java 体系（面向对象 → 集合 → Spring）系统补课。

## 7. 双修路线图：结合本仓库

双修不是"学两门语言"，而是**建立"分工心智"**——看到需求先判断归属，再决定用哪边的知识。结合本仓库的落地路线：

1. **Java 主线**（本仓库 01/02 层）：核心业务工程能力——Java 面向对象 → 集合/异常/多线程 → Spring 全家桶 → 微服务/中间件。这是"钱与交易"线的全部弹药
2. **Python 辅线**（03-AI 层）：AI 与数据能力——Python 基础 → FastAPI → HuggingFace/推理部署 → RAG/Agent。这是"模型与实验"线的全部弹药
3. **合流点**（04 层 + 本体系）：双语言混合架构项目——用 Java 写业务 + FastAPI 模型服务 + gRPC 对接，把两条线焊在一起
4. **面试输出**（05 层 + 本体系 10 章）：把"分工心智"讲成项目话术——这是 2026 年 Java 工程师最有区分度的叙事

> 🎯 **核心要点**：选型的唯一正确姿势是"场景画像优先"——交易/高并发/治理选 Java，模型/实验/速度选 Python，企业 AI 选混合。双修的终点不是"两种语言都会"，而是"一眼看出需求该归哪边"的分工心智。

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 六类场景决策：交易/网关/治理 → Java；模型/数据/原型 → Python；企业 AI → 混合架构；
> 2. 迁移学习用"心智映射"：record↔dataclass、Stream↔推导式、pytest↔JUnit、Spring↔Django，一周上手；
> 3. 双修 = 分工心智：Java 主线（01/02 层）+ Python 辅线（03-AI 层）+ 混合项目合流（04 层）。
