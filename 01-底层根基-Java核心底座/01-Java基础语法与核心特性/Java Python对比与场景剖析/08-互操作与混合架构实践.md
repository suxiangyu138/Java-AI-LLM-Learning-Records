## 1. 集成方式全景：从进程级到进程内

Java 与 Python 的集成有五个层次，按"耦合度"从低到高：

| 层次 | 技术 | 耦合度 | 适用 |
|------|------|:---:|------|
| 1. 进程级 HTTP | REST/OpenAPI | 低 | 默认首选，无状态服务 |
| 2. 进程级 RPC | gRPC（protobuf） | 低 | 高性能、强类型契约 |
| 3. 异步消息 | Kafka/RabbitMQ/Redis | 低-中 | 解耦、削峰、事件驱动 |
| 4. 进程内子进程 | 子进程 + 管道/文件 | 中 | 调用 Python 脚本/CLI |
| 5. 进程内嵌入 | GraalPy（Truffle）/Jep（JNI） | 高 | 同 JVM 内互调，低延迟 |

选型铁律：**能进程级就不进程内**。进程级集成（HTTP/gRPC/消息）让两语言各自独立部署、扩容、故障隔离——2026 年混合架构的事实标准；进程内嵌入只服务于"延迟敏感 + 调用频繁"的窄场景（如把 Python 打分逻辑嵌进 Java 服务），代价是部署复杂、版本绑死。

## 2. HTTP/gRPC：混合架构的默认通道

最常用的两种进程级协议：

- **REST/OpenAPI**：Python 侧 FastAPI 自动生成 OpenAPI 文档，Java 侧用 `springdoc` 生成客户端或直接 `RestClient` 调用——开发快、调试直观（Swagger UI）；适合业务型集成
- **gRPC**：protobuf 定义契约（`.proto` 一文件双端生成代码），HTTP/2 多路复用 + 强类型——比 JSON 快且省流量；适合高频、低延迟的模型调用（Java 业务 → Python 推理服务）

```proto
// 双语言契约：一份 .proto 两端生成代码
syntax = "proto3";
service EmbeddingService {
    rpc Embed(EmbedRequest) returns (EmbedResponse);
}
message EmbedRequest { repeated string texts = 1; }
message EmbedResponse { repeated float vector = 2; }
```

```java
// Java 侧调用（stub 由 protoc 生成）
EmbeddingServiceGrpc.EmbeddingServiceBlockingStub stub = ...;
EmbedResponse r = stub.embed(req);
```

```python
# Python 侧实现（grpcio + grpcio-tools）
class EmbeddingService(EmbeddingService_pb2_grpc.EmbeddingServiceServicer):
    def Embed(self, request, context):
        return EmbeddingService_pb2.EmbedResponse(vector=model.encode(request.texts))
```

2026 年的新变量是 **MCP 协议**（06 章）：当"Python 侧是 Agent 编排、Java 侧是工具能力"时，MCP 成为第三种进程级通道——双方无需自定义契约，按协议注册/调用即可。

协议选型的三个工程细节：**契约版本管理**——protobuf 的 `field number` 一旦发布就是永久契约（只能新增不能改语义），OpenAPI 的 `version` 字段要配合 break-change 评审；**序列化成本**——JSON 对 Python 的 dict 与 Java 的 record 都是顺手格式，但高频小消息 gRPC 的二进制 proto 省一半带宽与解析时间；**错误语义**——跨语言调用的错误码必须两端共享枚举（`UNKNOWN/INVALID/OVERLOADED` 三态起步），否则"Python 抛了什么"在 Java 侧只能靠日志猜。混合架构的排障 90% 时间花在"契约不一致"上，先定义好这三件事，集成基本不会翻车。

## 3. 消息队列：异步解耦的粘合剂

异步场景（AI 任务重、耗时长）用消息解耦两端：Java 业务提交任务 → Kafka/RabbitMQ → Python 消费者执行（推理/微调/ETL）→ 结果回写（DB/消息）。要点：

- **幂等消费**：任务可重放（结果幂等）是异步架构的底线，两端都要实现
- **结果回写**：Python 侧完成后回写任务状态表或发结果消息，Java 侧轮询/订阅
- **监控打通**：traceId 跨语言传递（W3C 标准），两端 OTel 同一后端——否则"任务卡住"无法定位是 Java 没发还是 Python 没回

```python
# Python 消费者（Kafka）：幂等 + 结果回写
for msg in consumer:
    job_id, payload = parse(msg)
    result = model.infer(payload)
    db.mark_done(job_id, result)        # 幂等：同 job_id 重复执行无害
```

这套"Java 编排 + Python 执行"的任务流水线是 AI 平台的标配（异步推理、批处理、微调任务），也呼应本仓库「02-消息队列」与「04-项目能力」体系。

## 4. JVM 内嵌 Python：GraalPy 现状

**GraalPy**（Oracle GraalVM 的 Python 3 实现，Truffle 框架）是 2026 年"Python on JVM"的活跃答案：

- **状态**：活跃维护（graal-25.0.3，2026-05-22）；Python 3.12 兼容；纯 Python 性能约为 CPython 的 **4 倍**（官方基准套件，JIT 编译）
- **能力**：Maven 坐标 `org.graalvm.python:python-embedding` 直接嵌进 Java；与 JFR、Maven、Native Image 集成（Python 应用可编译为 ~6.5MB 原生二进制）；约 85% CPython 测试套件通过，97% 最热门 PyPI 包可安装
- **代价**：运行时较大（~90MB 语言运行时 + stdlib）；原生扩展模块支持仍属实验性；Java 互操作（类型转换、集合互访）已是一等公民

```java
// Java 里内嵌 Python：直接执行 Python 函数
try (var ctx = org.graalvm.polyglot.Context.create()) {
    var py = ctx.eval("python", "def score(x): return x * 2 + 1");
    long result = py.invokeMember("score", 21).asLong();   // 43
}
```

适用判断：GraalPy 适合"延迟敏感、Python 逻辑内嵌 Java 服务"的窄场景（风控打分、规则引擎的 Python 脚本扩展）；宽场景（独立模型服务）仍应走进程级集成。

两个实操注意点：**依赖锁版本**——GraalPy 不是 CPython 的 drop-in，`pip install` 的轮子只保证 CPython 兼容，用 GraalPy 时要查"原生扩展支持清单"（实验性），纯 Python 库则基本无碍；**上下文复用**——Truffle 上下文（`Context`）创建成本高，生产代码必须复用单例并关注线程模型（一个 Context 是否支持多线程访问要在文档确认）。另外 2026 年它的**替代品**也值得记住：纯"跑 Python 脚本"需求用子进程（无共享状态、隔离彻底），需要共享内存与零拷贝才考虑 JVM 内嵌——**复杂度阈值大约是"每请求一次互调、延迟要求亚毫秒"**，达不到这个量级就不要内嵌。

## 5. Jython 已死与 Project Detroit

Jython 的现状要讲透，避免过时认知：**Jython 停留在 Python 2.x，Maven Central 最后一次发布是 2024-08，项目实际停滞**——Python 2 已 EOL，任何新项目都不应使用。它的遗产由两条线继承：

- **GraalPy**（上述）：官方路线，Python 3 + JVM 集成，并提供 `--python.EmulateJython` 兼容选项与迁移指南
- **Project Detroit（OpenJDK）**：一个将 CPython 嵌入 JVM 的 OpenJDK 项目（issue 跟踪中，2026 仍在推进）——不同于 Jython 的"重实现"，它直接嵌入真正的 CPython；此外 Jep 走 JNI 嵌入 CPython 也是可选路径

判断：JVM 内嵌 Python 的未来在 **GraalPy（现役）与 Project Detroit（探索）** 之间，Jython 只是历史名词。Apache Camel 2026 年正在把 camel-python 从 Jython（Python 2.7 限制）迁移到 GraalPy，是生态转向的实证。

## 6. 领域分工模型：谁做核心、谁做模型

混合架构的最终形态是**领域分工**，按"离数据/业务 vs 离模型"分两条河：

| 领域 | 语言 | 理由 |
|------|------|------|
| 核心业务（订单/支付/库存/用户） | Java | 事务、强一致、微服务治理、长期维护 |
| 模型与数据（训练/推理/特征/实验） | Python | 生态密度、迭代速度、数据科学闭环 |
| 中间层（Agent 编排/RAG 管道） | Java 或 Python | 看团队：Java 侧治理强，Python 侧生态顺 |
| 数据管道（ETL/批处理） | Python（或两边） | 库生态（pandas/Spark）成熟 |

分工三原则：**模型服务无状态化**（黑盒、水平扩容）；**契约先行**（proto/OpenAPI/MCP 先定再开发）；**可观测跨语言**（traceId 贯通两端）。2026 年大厂 AI 平台与业务系统几乎都是这个形态，也是"Java + Python 双修"职业路线的现实依据——本仓库 04 层「Java-AI 能力建设 L1-L3」正是按此分工设计。

**团队协作的边界**也要定清楚，否则技术边界再清晰也白搭：版本发布上，Java 与 Python 服务各自发版、契约兼容由 CI 校验（proto 破坏性变更检查）；故障定责上，traceId + 统一日志平台是唯一仲裁依据，谁也别想"甩锅给另一种语言"；数据归属上，数据库与消息队列是共享的，但**每个表/主题必须有明确 owner（Java 或 Python 侧）**，跨语言改数据结构的流程要写进规范。混合架构失败的案例，多数不是技术不行，而是"职责与数据归属"没划清——这两件事要在立项第一天就钉死。

> 🎯 **核心要点**：集成五层次按"能进程级不进程内"选型；GraalPy 是 JVM 内嵌 Python 的现役答案（~4x CPython、Maven 可嵌入），Jython 已死、Project Detroit 在途；混合架构 = 核心业务 Java + 模型服务 Python，契约先行、traceId 贯通。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 集成按耦合度分五层，HTTP/gRPC/消息是默认通道，进程内嵌入（GraalPy）只服务延迟敏感窄场景；
> 2. GraalPy 25.0.3 活跃维护、Python 3.12 兼容、纯 Python 约 4 倍 CPython；Jython 止步 Python 2、被 Project Detroit/GraalPy 继承；
> 3. 领域分工：核心业务 Java（事务/治理/维护）、模型与数据 Python（生态/速度），契约先行 + 跨语言可观测。
