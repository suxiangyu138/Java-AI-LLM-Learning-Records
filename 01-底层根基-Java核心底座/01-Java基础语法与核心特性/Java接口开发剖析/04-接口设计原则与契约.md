## 1. ISP —— 接口隔离原则 {#1}

### 1.1 什么是 ISP？

```text
Interface Segregation Principle (接口隔离原则)

"不应该强迫客户端依赖它们不使用的方法"
—— Robert C. Martin

核心思想：
  胖接口 → 拆分为多个小接口
  让每个实现类只关心自己需要的方法
```

### 1.2 胖接口的危害

```java
// ❌ 胖接口 —— 所有门都要实现全部方法
public interface Door {
    void lock();
    void unlock();
    void open();
    void close();
    void playAlarm();      // 普通门不需要！
    void autoLock();       // 手动门不需要！
    void fingerprint();    // 密码锁不需要！
}

// 每个实现者被迫写一堆空方法或抛异常
public class WoodenDoor implements Door {
    public void lock() { /* 实现 */ }
    public void unlock() { /* 实现 */ }
    public void open() { /* 实现 */ }
    public void close() { /* 实现 */ }
    public void playAlarm() { /* ??? 木门没有报警 */ }
    public void autoLock() { /* ??? 木门不能自动 */ }
    public void fingerprint() { throw new UnsupportedOperationException(); }
}
```

```java
// ✅ 接口隔离 —— 按职责拆分
public interface Lockable {
    void lock();
    void unlock();
}
public interface Openable {
    void open();
    void close();
}
public interface Alarmable {
    void playAlarm();
}
public interface AutoLockable {
    void autoLock();
}
public interface BiometricAuthenticatable {
    boolean authenticate(BiometricData data);
}

// 每个实现只取自己需要的能力
public class WoodenDoor implements Lockable, Openable {
    // 只需实现 4 个方法
}
public class SmartSecurityDoor implements Lockable, Openable,
        Alarmable, AutoLockable, BiometricAuthenticatable {
    // 需要全部实现
}
```

### 1.3 接口拆分原则

```text
如何判断接口是否过胖？

1. 看实现类：如果某个方法在大部分实现类中都是空实现或抛异常 → 该拆分
2. 看调用方：如果调用方只用到接口中的 2-3 个方法 → 该拆分
3. 看变更原因：如果接口因不同原因被修改 → 该拆分 (SRP)

拆分粒度：
├── 角色接口 (Role Interface)：一个接口一个角色
│   └── 例：Runnable、Callable、Comparable
├── 能力接口 (Capability Interface)：一个接口一个能力
│   └── 例：Serializable、Cloneable、AutoCloseable
└── 聚合接口：通过 extends 组合多个角色接口
    └── 例：List extends Collection, Iterable
```

## 2. Effective Java 接口设计法则 {#2}

### 2.1 核心法则

| 条目 | 法则 | 核心思想 |
|:---:|------|---------|
| #21 | **为后代设计接口** | 接口发布后很难改，要极其谨慎 |
| #22 | **接口只用于定义类型** | 不要用接口来导出常量 |
| #23 | **类层次优于标签类** | 用多态替代 switch/if-else |
| #24 | **优先考虑静态成员类** | 辅助类型放接口内部 |

### 2.2 #21：为后代设计接口

```java
// ⚠️ 接口发布后，添加抽象方法 → 破坏所有现有实现！
// ⚠️ 接口发布后，即使用默认方法，也可能破坏现有实现！

// ── 默认方法的安全添加条件 ──
// 1. 新的默认方法不依赖实现类的内部状态
// 2. 默认实现对所有实现者都是"合理"的
// 3. 不与已有方法冲突（名称+签名）
// 4. 不改变已有方法的语义

// ✅ 安全的默认方法：纯工具性质
public interface Collection<E> {
    // 基于已有的抽象方法实现，不依赖实现细节
    default boolean isEmpty() {
        return size() == 0;          // 只依赖 size()
    }
}

// ⚠️ 危险的默认方法：依赖实现细节或可能冲突
public interface DataSource {
    Connection getConnection();

    // 危险：默认实现可能不适用于所有 DataSource
    default Connection getConnectionWithRetry() {
        for (int i = 0; i < 3; i++) {
            try { return getConnection(); }
            catch (SQLException e) { /* 重试 */ }
        }
        throw new RuntimeException("Failed after retries");
    }
    // 问题：没有配置超时、没有考虑连接池、没有记录日志
}
```

### 2.3 #22：不要用接口导出常量

```java
// ❌ 反模式：常量接口
public interface Constants {
    int MAX_SIZE = 100;
    String DEFAULT_NAME = "unknown";
    double PI = 3.14159;
}

public class MyService implements Constants {  // 糟糕！
    // 只是为了用 MAX_SIZE，污染了类型层次
}

// ✅ 替代方案1：枚举
public enum Config {
    ;  // 不定义枚举实例
    public static final int MAX_SIZE = 100;
    public static final String DEFAULT_NAME = "unknown";
}

// ✅ 替代方案2：final 工具类
public final class AppConstants {
    private AppConstants() {}  // 防止实例化
    public static final int MAX_SIZE = 100;
}

// 使用: AppConstants.MAX_SIZE
```

### 2.4 #23：接口层次优于标签类

```java
// ❌ 标签类：用一个字段标识类型，switch 到处飞
class Shape {
    enum Type { CIRCLE, RECTANGLE }
    Type type;           // ← 标签
    double radius;       // 只有 CIRCLE 用
    double width, height;// 只有 RECTANGLE 用

    double area() {
        return switch (type) {
            case CIRCLE    -> Math.PI * radius * radius;
            case RECTANGLE -> width * height;
        };
    }
}

// ✅ 接口层次：每种类型一个实现
interface Shape {
    double area();
}
record Circle(double radius) implements Shape {
    public double area() { return Math.PI * radius * radius; }
}
record Rectangle(double w, double h) implements Shape {
    public double area() { return w * h; }
}
// 添加新形状 → 添加新实现 → 不改已有代码 (开闭原则)
```

## 3. 接口演化与兼容性 {#3}

### 3.1 三种兼容性

```text
1. 源兼容 (Source Compatibility)
   → 现有代码不修改能否重新编译？
   → 接口加抽象方法 → ❌ 编译失败

2. 二进制兼容 (Binary Compatibility)
   → 现有 .class 文件能否在新的依赖上运行？
   → 接口加 default 方法 → ✅ 已有 .class 仍可运行

3. 行为兼容 (Behavioral Compatibility)
   → 程序的行为是否相同？
   → 改了 default 实现 → ⚠️ 行为可能变化
```

```java
// ── 演化示例 ──
// v1.0: 发布时的接口
public interface ConfigLoader {
    Properties load(String path);
}

// v2.0: 想添加带默认值的加载方法
public interface ConfigLoader {
    Properties load(String path);

    // ❌ 加抽象方法 → 破坏源兼容
    // Properties load(String path, Properties defaults);

    // ✅ 加默认方法 → 保持二进制兼容
    default Properties load(String path, Properties defaults) {
        Properties props = load(path);      // 依赖现有抽象方法
        defaults.forEach(props::putIfAbsent);
        return props;
    }
}
```

### 3.2 安全的演化策略

```text
接口演化安全清单：

1. ✅ 添加 default 方法（只要默认实现正确）
2. ✅ 添加 static 方法
3. ✅ 添加 private 方法
4. ✅ 将已有类型改为 sealed（限制实现）
5. ⚠️ 修改 default 方法语义（可能破坏行为兼容）
6. ❌ 添加抽象方法
7. ❌ 删除已有方法
8. ❌ 修改已有方法签名

演化黄金法则：
  "宁可添加新接口，不要修改旧接口"
```

### 3.3 @Deprecated 与迁移路径

```java
// ── 标准的三步废弃流程 ──
public interface PaymentService {

    // Step 1: 标记旧方法为 @Deprecated
    /**
     * @deprecated 自 2.0 起，使用 {@link #pay(PayRequest)} 替代
     */
    @Deprecated(since = "2.0", forRemoval = true)
    PayResult pay(BigDecimal amount, String method);

    // Step 2: 提供新的替代方法
    default PayResult pay(PayRequest request) {
        // 默认实现 → 调用旧方法（过渡期）
        return pay(request.getAmount(), request.getMethod());
    }

    // Step 3: 未来版本移除旧方法
}
```

## 4. 命名与文档规范 {#4}

### 4.1 接口命名模式

| 模式 | 示例 | 含义 |
|------|------|------|
| **-able / -ible** | `Comparable`, `Runnable`, `Serializable` | 具备某种能力 |
| **名词** | `Collection`, `Executor`, `Stream` | 表示一个抽象实体 |
| **-Handler** | `ExceptionHandler`, `HttpHandler` | 处理某事 |
| **-Provider** | `DataProvider`, `ServiceProvider` | 提供某事 |
| **-Listener** | `EventListener`, `ChangeListener` | 监听事件 |
| **-Factory** | `ConnectionFactory`, `BeanFactory` | 创建对象 |
| **-Strategy** | `CompressionStrategy` | 封装算法 |
| **I- 前缀** | ~~`IUserService`~~ | ❌ Java 不推荐 |
| **-Impl 后缀** | ~~`UserServiceImpl`~~ | ⚠️ 无奈之举，考虑更好的实现类名 |

```java
// ✅ 好的命名
public interface PaymentProcessor { }
public class StripePaymentProcessor implements PaymentProcessor { }
public class WeChatPaymentProcessor implements PaymentProcessor { }

// ⚠️ 中等的命名（信息量不足）
public interface PaymentService { }
public class PaymentServiceImpl implements PaymentService { }
```

### 4.2 Javadoc 契约文档

```java
/**
 * 支付服务接口 —— 处理支付请求并返回支付结果。
 *
 * <p>所有实现必须是<b>线程安全</b>的。
 *
 * <p>典型用法:
 * <pre>{@code
 *   PaymentResult result = paymentService.pay(
 *       new PayRequest(amount, currency, method));
 *   if (result.isSuccess()) {
 *       // 处理成功
 *   }
 * }</pre>
 *
 * @implSpec
 * 实现者必须确保：
 * <ul>
 *   <li>幂等性：同一笔请求重复调用返回相同结果</li>
 *   <li>超时控制：30 秒内必须返回（可配置）</li>
 * </ul>
 *
 * @implNote
 * 默认实现使用 {@link DefaultPaymentProcessor}，
 * 它基于 HTTP 调用第三方支付网关。
 */
public interface PaymentService {

    /**
     * 执行支付。
     *
     * @param request 支付请求，不能为 null
     * @return 支付结果，从不返回 null
     * @throws IllegalArgumentException request 中的 amount 为负数时
     * @throws PaymentTimeoutException 支付超时时
     * @throws PaymentFailedException 支付被银行拒绝时
     */
    PaymentResult pay(PayRequest request);
}
```

### 4.3 @implSpec vs @implNote

| 标签 | 用途 | 受众 |
|------|------|------|
| `@implSpec` | 实现规范——实现者**必须**遵守的约定 | 接口实现者 |
| `@implNote` | 实现备注——默认实现的具体做法（非必须） | 接口实现者（可选阅读） |

## 5. 接口契约测试 {#5}

### 5.1 什么是契约测试？

```text
契约测试 (Contract Test):
  不是测试某一个实现类，而是测试"所有实现类都应该满足的接口约定"

例：所有 List 实现都应满足：
  - add(e) 后 size() 增加 1
  - get(0) 返回刚添加的元素
  - remove(0) 后 size() 减少 1
```

```java
/**
 * 接口契约测试基类
 * 所有 PaymentService 的实现类继承此类即可获得免费测试
 */
public abstract class PaymentServiceContractTest {

    // 子类提供具体实现
    protected abstract PaymentService createPaymentService();

    @Test
    void shouldReturnSuccessForValidRequest() {
        PaymentService service = createPaymentService();
        PayRequest request = new PayRequest(
            new BigDecimal("100.00"), "CNY", "wechat");

        PaymentResult result = service.pay(request);
        assertNotNull(result);
        assertTrue(result.isSuccess());
    }

    @Test
    void shouldThrowExceptionForNegativeAmount() {
        PaymentService service = createPaymentService();
        PayRequest request = new PayRequest(
            new BigDecimal("-1.00"), "CNY", "wechat");

        assertThrows(IllegalArgumentException.class,
            () -> service.pay(request));
    }

    @Test
    void shouldRejectNullRequest() {
        PaymentService service = createPaymentService();
        assertThrows(NullPointerException.class,
            () -> service.pay(null));
    }

    @Test
    void shouldBeIdempotent() {
        PaymentService service = createPaymentService();
        PayRequest request = new PayRequest(
            new BigDecimal("100.00"), "CNY", "wechat");

        PaymentResult first = service.pay(request);
        PaymentResult second = service.pay(request);
        assertEquals(first.getTransactionId(), second.getTransactionId());
    }
}

// 具体实现只需一行代码即可获得全套测试
class WeChatPayServiceTest extends PaymentServiceContractTest {
    @Override
    protected PaymentService createPaymentService() {
        return new WeChatPayService(wechatConfig);
    }
}

class AlipayServiceTest extends PaymentServiceContractTest {
    @Override
    protected PaymentService createPaymentService() {
        return new AlipayService(alipayConfig);
    }
}
```

> 🎯 **核心要点**：设计接口的终极考验不是"现在能不能用"，而是"五年后还能不能安全地演化"。ISP 让接口小而精，契约文档让预期清晰，契约测试让实现可信——三管齐下，接口才能经得起时间考验。
