## 1. 设计决策树：Retention 是总开关

自定义注解的第一步不是写 @interface，而是回答三个问题，其中第一个决定一切：

1. **谁消费？**——javac（@Override 式编译检查）、APT 处理器（Lombok/MapStruct 式代码生成）、运行期反射/AOP（Spring 式行为增强）。没有消费者的注解只是装饰品，设计注解 = 设计"注解 + 消费者"的完整链路，两者要同一提交落地；
2. **@Retention 怎么选？**——只做编译期检查选 SOURCE（零字节码负担）；编译期生成选 CLASS（APT 能读、运行期不可见，JAR 依赖更干净）；运行期行为选 RUNTIME。**忘记写 @Retention 默认是 CLASS**，运行期消费者将永远读不到注解——这是自研注解的第一个经典事故；
3. **@Target 放多宽？**——宁窄勿宽：@RateLimit 只标方法，就别给 TYPE；范围宽的注解会在一年后出现在所有奇怪的位置。同时配套 `@Documented`（Javadoc 可见）与 `@Repeatable`（是否需要重复标注，如 @Sensitive 要标多个字段就不用 Repeatable，字段级天然单次）。

属性设计两个惯例：`value` 作为唯一属性时支持 `@MyAnn("x")` 省略写法（属性多于一个时 value 不能省略）；**新增属性必须带 default**——否则存量使用点全部编译失败，这是注解 API 向后兼容的唯一纪律。

## 2. 运行期反射消费：审计日志 / 限流 / 脱敏三案例

### 2.1 @MyLog 操作审计（AOP + SpEL）

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface MyLog {
    String module();          // 业务模块
    String action();          // 操作描述
    boolean recordArgs() default true;   // 是否记录入参
}

@Aspect @Component
public class LogAspect {
    @Around("@annotation(myLog)")
    public Object around(ProceedingJoinPoint pjp, MyLog myLog) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            Object result = pjp.proceed();
            save(myLog.module(), myLog.action(), "SUCCESS", cost(start), pjp.getArgs());
            return result;
        } catch (Throwable e) {
            save(myLog.module(), myLog.action(), "FAIL", cost(start), e.getMessage());
            throw e;
        }
    }
}
```

工程要点：@Around 切点用 `@annotation(myLog)` 把注解实例**绑定为切面方法参数**（比反射重读更优雅且零重复解析）；入参记录必须**脱敏**（密码/手机号字段先清洗再落库）；审计日志异步化（不阻塞主流程，牺牲实时性换性能）；描述支持 SpEL（`action = "'创建订单' + #order.id"`）是进阶玩法，但要防表达式注入。

### 2.2 @RateLimit 限流（Redis Lua 原子化）

接口限流的经典设计：注解声明维度与阈值，拦截器/切面在 Redis 执行 **Lua 脚本**（滑动窗口或令牌桶，Lua 保证判断+计数原子性），key 设计按 `rate:{接口}:{用户ID或IP}` 分层。注解属性三件套：`limit`（窗口内次数）、`window`（窗口秒数）、`key`（维度表达式）。降级策略必须内置：**Redis 故障时放行还是拒绝**——生产共识是"限流器故障放行 + 告警"，避免基础设施故障扩大为全站 503。

### 2.3 @Sensitive 脱敏（Jackson 序列化层）

```java
@Sensitive(strategy = SensitiveStrategy.PHONE)   // 138****1234
private String phone;
```

实现走 04 篇的定制序列化路线：自定义 `ValueSerializer`（Jackson 3 的基类，替代 2.x 的 JsonSerializer）+ `ContextualSerializer` 读取字段上的 @Sensitive 注解，按策略（手机号/身份证/银行卡）脱敏后输出。**脱敏放序列化层而非数据库层**的原因：原始数据保留在库里可审计，输出侧统一变形；日志、缓存、前端三处出口都能靠同一机制约束。注意 ContextualSerializer 的实例是 per-field 创建的，无状态假设不成立时会有并发坑。

## 3. 编译期 APT 消费：注解处理器实战

APT（JSR-269）链路：`AbstractProcessor.process()` 收到 `RoundEnvironment`，`getElementsAnnotatedWith()` 拿到被标注元素，用 `Elements/TypeElement/ExecutableElement` API 分析，`Filer` 写生成源文件，`Messager` 报错（**编译期报错是 APT 最大优势**——注解放错位置在 CI 就失败，而非运行期爆炸）。处理器注册两个姿势：传统 `META-INF/services/javax.annotation.processing.Processor` 手写 SPI 文件，或 **Google AutoService 的 @AutoService(Processor.class)** 自动生成注册文件（Maven/Gradle 引入 `annotationProcessor` 作用域）。

处理器的最小骨架：

```java
@AutoService(Processor.class)
@SupportedAnnotationTypes("com.example.Builder")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class BuilderProcessor extends AbstractProcessor {

    @Override
    public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment roundEnv) {
        for (Element e : roundEnv.getElementsAnnotatedWith(Builder.class)) {
            if (e.getKind() != ElementKind.CLASS) {
                processingEnv.getMessager().printMessage(ERROR, "@Builder 只能标注类", e);
                continue;                       // 编译期校验：注解放错位置直接报错
            }
            TypeElement type = (TypeElement) e;
            String generated = generateBuilderSource(type);   // 拼出 Builder 源码
            try (Writer w = processingEnv.getFiler()
                    .createSourceFile(type.getQualifiedName() + "Builder").openWriter()) {
                w.write(generated);
            } catch (IOException ex) {
                throw new RuntimeException(ex);
            }
        }
        return false;    // 不声明独占，允许其他处理器继续处理这些注解
    }
}
```

三个细节：`process` 会被**多轮调用**（每轮可能产生新类型，新类型上的注解下轮再处理，注意去重处理防止重复生成）；`return false` 表示注解共享（true 是声明独占，后续处理器不再收到）；`Messager.printMessage(ERROR, ...)` 是"把运行时错误提前到编译期"的钥匙，比任何运行期校验都便宜。

APT 的适用边界要诚实：**生成代码**（Builder、映射器、序列化器、Spring 元数据）与**编译期校验**（注解使用位置、命名规范、契约检查）是它的主场；需要"运行时动态行为"的场景（限流、事务、缓存）APT 无能为力。MapStruct 是 APT 的天花板案例——1.7.0.Beta2（2026-06-27）的最新能力直接示范了趋势：**JSpecify 感知**（`@NonNull` 源跳过判空、`@NonNull` 目标强制判空）、`@Mapper(accessibility = ...)` 配置生成类可见性、生成代码现代化（switch 表达式/diamond）。

> 🎯 **核心要点**：反射与 APT 的选型口诀——"行为在运行期动态发生"选 RUNTIME + 反射/AOP；"代码在编译期可以确定"选 CLASS + APT（性能更好、错误更早暴露）。

## 4. 元注解组合与 @AliasFor

**派生注解**是 Spring 体系的自研注解标准姿势：新注解的注解上叠框架注解，如 `@MyCacheable` 上叠 `@Cacheable`，Spring 扫描时经 `MergedAnnotations` 递归解析元注解链，行为与直接标 @Cacheable 等价。这比"拷贝框架注解属性"高明在**框架升级自动受益**（@Cacheable 新属性自动可用）。

**@AliasFor 解决属性透传**：派生注解想覆盖元注解的属性值时（`@MyCacheable(ttl = 60)` 传进 @Cacheable 的 key 表达式），用 `@AliasFor` 建别名桥。双向别名（A 指向 B 且 B 指向 A）要求值一致，冲突时 Spring 抛 `AnnotationConfigurationException`——这层校验是自研组合注解时的免费保险。`@AliasFor` 的原理是注解属性的**动态代理拦截**：读取属性时 Spring 生成的 Annotation 代理会沿别名链解析最终值，所以别名声明只影响框架侧读取，不影响注解本身的字节码结构。

## 5. 生产工程纪律与面试题

1. **性能纪律**：运行期反射读注解有开销（类加载后 JVM 会缓存注解实例，但 `getAnnotation` 每次调用有查找成本）——AOP 场景用 `@annotation(x)` 绑定参数一次解析，循环内禁止反复反射读注解。API 选型也分场景：`isAnnotationPresent` 只判断存在（最便宜）；`getAnnotation` 拿单实例（@Repeatable 注解在重复标注时用它拿会出问题）；`getAnnotationsByType` 才是 @Repeatable 的正确读取姿势（01 篇已述）——自研注解设计成 @Repeatable 时，消费端必须配套用对 API；
2. **可观测纪律**：自研注解天然是"元数据驱动"入口——@MyLog/@RateLimit 都应在监控面板有对应指标（限流命中率、审计失败数），注解不止简化代码，还在生产事故排查时提供语义线索；
3. **演进纪律**：注解 API 的兼容规则与公开 API 相同——新属性带 default、旧属性删之前留弃用窗口、@Retention 级别不轻易变更（CLASS→RUNTIME 会让所有消费者行为改变）；
4. **团队纪律**：自研注解必须有配套文档说明"消费者在哪、如何调试"——后来者看到 `@Sensitive` 只会问"为什么字段没脱敏"，答案藏在序列化器注册链路里；
5. **面试必答框架**：「手写一个 @RateLimit 怎么设计？」——@Target(METHOD)+@Retention(RUNTIME) → 拦截器/AOP 消费者 → Redis Lua 原子计数 → 降级策略；「APT 与反射选型？」——编译期确定选 APT（性能、早期报错），运行期动态选反射（灵活、可热改），并说出 Lombok（APT+AST hack）与 Spring（RUNTIME+AOP）两大代表的分野。
