# 09 测试注解剖析

> 测试注解体系由三层组成：JUnit 6 提供测试生命周期与参数化骨架、Mockito 提供替身（Test Double）声明、Spring Boot Test 提供容器集成。2026 年的主线变化：JUnit 6 拥抱虚拟线程并行与 JSpecify 空安全，Boot 4 用 @MockitoBean 替换被移除的 @MockBean

## 1. JUnit 6 生命周期与结构注解

JUnit 6（2025-09-30 发布，6.0.2 于 2026-01-06，Java 17 基线）延续 Jupiter 模型，核心注解与 JUnit 5 完全一致——升级主要是换版本号，这也是它相对 JUnit 4→5 大迁移的温和之处。

生命周期四注解的规则：`@BeforeAll/@AfterAll` 标注的方法**必须是 static**（除非类标注 `@TestInstance(TestInstance.Lifecycle.PER_CLASS)`，每类一个实例时 static 可省略，且 @BeforeAll 可访问实例字段）；`@BeforeEach/@AfterEach` 实例方法，每个测试方法前后执行。执行顺序：`@BeforeAll → (每个方法: 构造器 → @BeforeEach → @Test → @AfterEach) → @AfterAll`。`@Test` 本身无属性（JUnit 4 的 expected/timeout 已由断言与 @Timeout 取代）。

结构注解：`@DisplayName`（可读测试名，支持 emoji 但 CI 日志编码需确认）、`@Tag`（分类筛选，配合 Maven/Gradle 的 groups 过滤执行）、`@Disabled("原因")`（跳过，留原因字符串是团队规范——无理由的 @Disabled 是技术债）、`@Nested`（内嵌测试类，逻辑分组；JUnit 6 起 `@TestMethodOrder/@TestClassOrder` **递归继承到嵌套类**，顺序控制不再需要每个嵌套类重复标注）。

`@TestMethodOrder` 的常用实现：`MethodOrderer.OrderAnnotation`（配合 @Order 显式排序）、`MethodOrderer.Random`（暴露测试间隐式依赖的反向检测手段）。依赖测试执行顺序本身就是坏味道，顺序控制主要用于失败输出的可读性而非正确性。

## 2. 参数化与资源管理注解

`@ParameterizedTest` 家族让一个测试方法跑多组数据：`@ValueSource(strings/int/...)`（单参数）、`@CsvSource`（多参数，JUnit 6 起底层从 univocity 换为 **FastCSV**，RFC 4180 合规、错误定位更好）、`@CsvFileSource`（文件驱动，**JUnit 6 移除 lineSeparator 属性**，行尾自动检测）、`@MethodSource`（工厂方法提供 `Stream<Arguments>`，必须 static 除非 PER_CLASS）、`@EnumSource`、`@ArgumentsSource`（自定义提供器）。JUnit 6 中参数名默认**加引号**显示（`"a"`），由 `quoteTextArguments` 配置项控制。参数化测试的命名建议 `@ParameterizedTest(name = "{0} + {1} = {2}")`，失败时一眼定位数据组。

资源管理注解是 JUnit 近两个版本的发力点：`@TempDir`（注入临时目录，方法级默认每方法独立、类级共享；旧 `tempdir.scope` 配置已移除）、**`@AutoClose`（JUnit 5.11 引入、6 保留）**——标注 `AutoCloseable` 字段（文件流、DB 连接、HTTP 客户端、WireMock 实例），测试后自动按**声明逆序**关闭，即使测试失败也执行，替代手写 @AfterEach 清理样板；`@Timeout(2)` 类级/方法级声明超时（替代 JUnit 4 的 `@Test(timeout=)`）；`@RepeatedTest`（重复执行测稳定性，配合 `RepetitionInfo` 注入轮次）。

动态测试两个注解按需取用：`@TestFactory`（工厂方法返回 `DynamicTest` 集合，测试**在运行期动态生成**——适合"根据输入文件/接口清单批量生成测试"的场景）；`@TestTemplate`（模板方法，每次调用由一个扩展提供上下文——`@ParameterizedTest` 就是它的内置实现，自定义模板扩展用于同一测试多环境重放）。类级参数化 `@ParameterizedClass`（JUnit 6 强化）让整个测试类按参数组实例化多次，适合"同一套用例跑多组配置"的矩阵测试。

## 3. JUnit 6 变化：虚拟线程、JSpecify 与移除项

**@Parallelizable 与虚拟线程**是 JUnit 6 的招牌：`@Parallelizable(mode = Parallelizable.Mode.VIRTUAL)` 让测试跑在**虚拟线程**上——IO 密集型测试（数据库、HTTP、消息）数千并发只占用极少的平台线程，替代此前"配置 parallel 执行 + 线程池"的组合。注意并行默认行为的变化：迁移报告中部分场景 JUnit 6 默认并行，需要串行时类级标 `@Execution(ExecutionMode.SAME_THREAD)` 显式声明。

**JSpecify 空安全注解**全面覆盖 API 表面：`@Nullable/@NonNull/@NullMarked`（org.jspecify.annotations）——它们是**编译期契约**（IDE/NullAway/SpotBugs 消费），**不生成运行时检查**。与 Lombok 的 @NonNull（生成 NPE 检查代码）区分开，这是三个 @NonNull 中唯一"纯契约"的。

移除与弃用清单：Vintage 引擎**弃用**（JUnit 3/4 迁移桥，只做过渡）、`junit-platform-runner/junit-platform-jfr`（JFR 支持并入 launcher）移除、`@UseTechnicalNames` 移除、`MethodOrderer.Alphanumeric` 移除、JRE 17 以下枚举常量弃用。

## 4. Mockito 与 Spring Boot Test 注解

**Mockito 四注解**（配合 `@ExtendWith(MockitoExtension.class)`）：`@Mock`（纯替身，方法返回默认值）、`@Spy`（真实对象包装，部分方法替换——**注意 spy 上 `when(spy.m())` 会真实调用一次方法**，应改用 `doReturn(...).when(spy)`）、`@InjectMocks`（自动把 @Mock 注入被测对象——注入顺序：构造器 → setter → 字段，构造器首选，这也是"构造器注入设计利于测试"的印证）、`@Captor`（ArgumentCaptor 便捷声明）。strict stubs 模式下**未使用的打桩会抛 UnnecessaryStubbingException**——打桩按需声明，公共 setup 里的打桩要 `lenient()` 声明。

**Spring Boot 4 测试注解的最大变化**：`@MockBean/@SpyBean` **已移除**，替换为 Spring Test 官方 bean-override 体系——`@MockitoBean`（org.springframework.test.context.bean.override.mockito）与 `@MockitoSpyBean`。迁移注意两点：这两个注解**按类型或名称替换上下文中的 Bean**，且会**破坏测试上下文缓存**（不同测试类替换不同 Bean 时无法共享缓存，测试变慢）——所以先查为什么需要 mock，能用 @Profile 提供的测试 Bean 就别用运行时替换。

集成测试主力：`@SpringBootTest`（完整上下文，`webEnvironment = RANDOM_PORT` 走真实端口测 HTTP 链路）、切片测试 `@WebMvcTest`（只装配 Web 层，需显式补 @MockitoBean 依赖）/`@DataJpaTest`（只装配持久层，内嵌数据库）/`@DataRedisTest`/`@RestClientTest`——**切片优先于全量**是测试速度纪律。辅助注解：`@ActiveProfiles("test")`、`@Sql`（脚本初始化）、`@DirtiesContext`（污染上下文后重建——高频使用说明测试设计有问题）、`@Testcontainers` + `@Container`（真数据库环境，比内嵌数据库更贴近生产）。

环境条件与套件注解补齐拼图：`@EnabledIf/@DisabledIf`（按条件表达式/系统属性/环境变量启用禁用测试——注意 JUnit 5.6 起 scripting 支持被移除，表达式走 Java 语义而非脚本）；`@EnabledOnOs/@EnabledOnJre`（平台条件）；`@Suite` + `@SelectClasses/@SelectPackages`（套件聚合，JUnit 平台原生）；`@RegisterExtension`（**编程式**注册扩展实例，注解版 @ExtendWith 只能注册无参构造扩展，需要传配置时用编程式）。

**上下文缓存机制**是理解 Spring 测试速度的关键：TestContext 框架把 `ApplicationContext` 按**缓存键**（配置类、@ActiveProfiles、@TestPropertySource、webEnvironment、@MockitoBean 替换列表等组合）缓存复用——键相同的测试类共享已启动的上下文，键不同则冷启动新上下文（每次数秒）。由此推出三条纪律：profile/属性/替换列表尽量标准化减少键分叉；@MockitoBean 按测试类替换不同 Bean 会持续冷启动（比想象中慢得多，优先 @Profile 提供的测试 Bean）；@DirtiesContext 主动失效缓存，只在"测试确实污染了共享状态"时用。

Mockito 补充两件套：`@DoNotMock`（标注类型声明"此类型不应该被 mock"——给工具类/值对象立规矩，静态分析可配合拦截）；`ArgumentMatchers.any()/eq()` 的纪律——matcher 与原始值**不可混用**（`when(m.foo(any(), 1))` 抛 InvalidUseOfMatchersException），要么全 matcher 要么全原值。

## 5. 高频坑与面试题

1. **@BeforeAll 非 static 报错**：初学第一坑，或类级 @TestInstance(PER_CLASS)；
2. **@MockitoBean 缓存失效**：上下文缓存被 Bean 替换打碎，测试套件变慢的隐形杀手；
3. **@InjectMocks 字段注入静默**：字段名不匹配时字段悄悄为 null，构造器注入设计从源头消除；
4. **@TempDir 级联路径**：测试失败时目录保留便于排查，CI 环境注意磁盘清理；@TempDir 与 @AutoClose 组合即可覆盖"临时资源 + 显式资源"两类清理，测试里不应再出现手写 try-finally；
5. **面试必答框架**：「JUnit 6 相对 5 改了什么？」——Java 17 基线、@Parallelizable 虚拟线程并行、JSpecify 空安全注解、@AutoClose、Vintage 弃用与若干移除项；「@Mock/@Spy/@InjectMocks 区别？」——替身三形态：全假、半真（包真打桩）、被测对象注入器；「参数化测试 @ValueSource 与 @MethodSource 怎么选？」——单参数常量组用 ValueSource，需要对象构造/动态生成/多参数用 MethodSource 返回 Stream；
6. **「@MockBean 为什么被移除？」**——它是 Spring Boot 的胶水补丁，运行时替换容器 Bean 会破坏测试上下文缓存（测试套件显著变慢）且语义不透明；Spring Test 官方的 @MockitoBean/@MockitoSpyBean 以 bean-override 体系正式接管，显式声明"哪个 Bean 被替换"；
7. **「测试为什么优先切片？」**——@SpringBootTest 启动完整上下文每次数秒起，几十个测试类累计分钟级；@WebMvcTest/@DataJpaTest 只装配被测层，配合上下文缓存让增量编译的测试保持在毫秒-秒级，速度决定团队是否愿意频繁跑测试。
