## 1. 多态的定义与三要素

**多态（Polymorphism）**：同一个行为（方法调用）在不同对象上呈现出不同表现。

**运行时多态的三个必要条件（缺一不可）**：

1. **存在继承/实现关系**（子类继承父类 或 实现接口）；
2. **子类重写父类方法**（否则调用的是同一个实现，无"不同表现"）；
3. **父类引用指向子类对象**（向上转型，调用入口是抽象类型）。

```java
public abstract class Animal {
    public abstract String speak();
}

public class Dog extends Animal {
    @Override public String speak() { return "汪汪"; }
}

public class Cat extends Animal {
    @Override public String speak() { return "喵喵"; }
}

public class Zoo {
    public static void letSpeak(Animal a) {     // 参数是父类引用
        System.out.println(a.speak());          // 实际调用哪个 speak()？取决于对象
    }

    public static void main(String[] args) {
        Animal d = new Dog();                   // 父类引用指向子类对象
        Animal c = new Cat();
        letSpeak(d);   // 汪汪
        letSpeak(c);   // 喵喵
    }
}
```

> 🎯 **核心要点**：`Zoo` 只依赖 `Animal` 抽象——新增 `Pig` 子类时 `Zoo` 代码**零修改**，这就是"对扩展开放"（开闭原则）的机制来源。

## 2. 两种多态：编译时与运行时

| 维度 | 编译时多态（重载 Overload） | 运行时多态（重写 Override） |
|------|--------------------------|--------------------------|
| 发生位置 | 同一个类内的多个方法 | 父类与子类之间 |
| 决定时机 | **编译期**静态分派 | **运行期**动态分派 |
| 判断依据 | 方法名相同 + **参数列表不同** | 方法签名完全相同 |
| 返回值 | 不参与区分 | 相同或协变 |
| 关键字 | 无需注解 | `@Override` |
| 调用方代码 | 调用处已定死 | 引用类型是抽象，实际执行看对象 |

```java
public class Calculator {
    public int add(int a, int b) { return a + b; }
    public double add(double a, double b) { return a + b; }   // 重载：编译期选定
}

Animal a = new Cat();
a.speak();   // 编译期只知道"Animal 有 speak"，运行期派发到 Cat.speak —— 重写
```

## 3. 动态绑定机制：invokevirtual 与虚方法表

字节码层面，普通实例方法调用使用 `invokevirtual` 指令，JVM 在**运行时**根据对象实际类型查找方法：

```text
方法调用分派
├── 静态分派（编译期确定）
│   ├── invokestatic     —— 静态方法
│   ├── invokespecial    —— 构造器 / private / super 方法
│   └── 重载选择
└── 动态分派（运行期确定）
    └── invokevirtual    —— 普通实例方法（重写/多态的载体）
        └── 虚方法表（vtable）：JVM 为每个类建立方法地址表，
            子类重写的方法地址覆盖父类表项
            查找 = 按 vtable 索引 O(1) 查表，无需扫描继承链
```

**虚方法表（vtable）**：类加载时，JVM 在方法区为该类生成一张方法地址表；子类继承父类表并**覆盖被重写的方法项**。调用 `a.speak()` 时：

1. 根据 `a` 的对象头类型指针找到实际类的 vtable；
2. 按方法在表中的固定索引直接取出 `Cat.speak` 的入口地址；
3. 调用。

因此多态的运行时开销只有一次查表（JIT 内联后可进一步优化），**不是反射那种动态解析**。

> 💡 与静态绑定对比：`final`/`private`/`static` 方法不走 vtable，编译期即确定目标，JIT 可放心内联。这也是为什么性能敏感代码鼓励 `final` 方法。

## 4. 对象转型：向上与向下

| 转型 | 方向 | 语法 | 安全性 |
|------|------|------|--------|
| 向上转型（Upcasting） | 子类 → 父类 | `Animal a = new Dog()` | **自动**，永远安全，会丢失子类特有方法 |
| 向下转型（Downcasting） | 父类 → 子类 | `Dog d = (Dog) a` | **强制**，可能抛 `ClassCastException` |

```java
Animal a = new Dog();
a.speak();            // ✅ 多态正常
// a.fetchBall();     // ❌ 编译错误：Animal 引用看不到 Dog 特有方法

Dog d = (Dog) a;      // ✅ 实际就是 Dog，成功
Cat c = (Cat) a;      // ❌ 运行期 ClassCastException：Cat 不是 Dog 的实例
```

**向下转型的安全姿势——先 instanceof 判断**：

```java
if (a instanceof Dog dog) {          // Java 16+：模式匹配，直接声明绑定变量
    dog.fetchBall();
} else if (a instanceof Cat cat) {
    cat.climb();
}
```

> ⚠️ **转型陷阱**：向下转型前必须验证实际类型，否则线上偶发 `ClassCastException`。尤其从 `List`、`Map` 等集合取元素强转时，泛型擦除让编译期无法保证，运行期才炸。

## 5. instanceof 与现代模式匹配

**老写法**（instanceof + 强转 + 局部变量，三步样板）：

```java
if (a instanceof Dog) {
    Dog dog = (Dog) a;          // 冗余：类型已判断又强转一次
    dog.fetchBall();
}
```

**Java 16+ 模式匹配 for instanceof（JEP 394 转正）**——判断与绑定合一：

```java
if (a instanceof Dog dog) {
    dog.fetchBall();            // dog 已可用，且作用域被"流式分析"收紧
}

// 甚至支持嵌套模式与类型精化（Java 21+ 的 record 模式详见 08 模块）
if (shape instanceof Circle(Point center, double r) circle) {
    // 解构出 center 与 r
}
```

> 💡 模式匹配消除了"判断-强转-使用"三连样板，且**更安全**：编译器保证 `dog` 只能在判断通过的分支中使用。

## 6. 重载 vs 重写全景对比

| 对比维度 | 重载（Overload） | 重写（Override） |
|---------|----------------|----------------|
| 位置 | 同一个类中 | 子类与父类/接口间 |
| 方法名 | 必须相同 | 必须相同 |
| 参数列表 | **必须不同**（个数/类型/顺序） | **必须完全相同** |
| 返回类型 | 无关（不参与区分） | 相同或父类返回类型的子类（协变） |
| 访问修饰符 | 无关 | 不能比父类更严格 |
| 受检异常 | 无关 | 不能更宽泛 |
| 分派时机 | 编译期（静态分派） | 运行期（动态分派） |
| 多态类型 | 编译时多态 | 运行时多态 |
| 注解 | 无 | `@Override`（编译器校验） |

**协变返回类型**：重写方法可返回父类返回类型的子类。

```java
public class Parent {
    protected Object build() { return new Object(); }
}

public class Child extends Parent {
    @Override protected String build() { return "更具体的类型"; }  // ✅ 协变返回
}
```

> 🎯 **核心要点**：重载是"同名的多个方法"（编译期选），重写是"同名同签名的替换"（运行期派发）——两者互不干扰，可同时存在：子类既可以重写父类方法，也可以新增重载。

## 7. 重载的静态分派细节

编译器选择重载方法遵循"**最精确匹配**"原则（编译期确定，与运行期无关）：

```java
public class OverloadDemo {
    public void show(int i)          { System.out.println("int"); }
    public void show(long l)         { System.out.println("long"); }
    public void show(Integer i)      { System.out.println("Integer"); }
    public void show(Object o)       { System.out.println("Object"); }

    public static void main(String[] args) {
        OverloadDemo d = new OverloadDemo();
        int x = 1;
        d.show(x);            // int：精确匹配优先
        d.show(1L);           // long：精确匹配
        d.show((Integer) x);  // Integer：精确匹配
        d.show(null);         // Integer 或 Object 都匹配？→ 更精确者胜出：Integer
        // d.show((short) 1); // short → 无 short 重载 → 拓宽到 int
    }
}
```

**编译期选择顺序**：精确类型 → 拓宽（byte→short→int→long→float→double）→ 装箱 → 装箱后拓宽（Integer→Number→Object）→ 可变参数。`null` 选择最具体的引用类型。

> ⚠️ **重载 + 多态的著名坑**：重载按**引用类型**分派，重写按**实际类型**分派——同一个对象传给不同参数类型的重载方法，选中的是"引用类型对应的那个"，与对象真实类型无关。这是面试高频陷阱题（见 10 模块自测）。

## 8. 多态实战：面向接口的扩展设计

```java
// 1. 定义抽象（接口或抽象类）
public interface Payment {
    void pay(BigDecimal amount);
    String channelName();
}

// 2. 多个实现
public class WeChatPay implements Payment {
    @Override public void pay(BigDecimal amount) { /* 微信支付逻辑 */ }
    @Override public String channelName() { return "wechat"; }
}

public class Alipay implements Payment {
    @Override public void pay(BigDecimal amount) { /* 支付宝逻辑 */ }
    @Override public String channelName() { return "alipay"; }
}

// 3. 业务层只依赖抽象
public class OrderService {
    private final Payment payment;                 // 构造器注入具体实现

    public OrderService(Payment payment) {
        this.payment = payment;
    }

    public void checkout(Order order) {
        payment.pay(order.getAmount());            // 多态派发：具体是谁在 pay，OrderService 不关心
    }
}

// 4. 新增银联支付：新增一个类即可，OrderService 与已有实现零修改
public class UnionPay implements Payment {
    @Override public void pay(BigDecimal amount) { /* 银联逻辑 */ }
    @Override public String channelName() { return "unionpay"; }
}
```

**多态的收益**：解耦（业务层不依赖具体实现）、扩展性（新增实现零侵入）、一致性（所有实现共享同一契约）。这正是 Spring IoC「面向接口编程」的根基——容器通过多态注入不同的 Bean 实现。

**多态的代价**：抽象引入间接层，调试时要知道"实际类型是谁"；过度抽象会让代码难以追踪。判断标准：**是否真的存在"多种实现且未来可能增加"**，只有一个实现时不要为抽象而抽象。
