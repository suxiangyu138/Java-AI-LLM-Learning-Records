## 1. 为什么需要"现代三件套"

传统 Java 建模的三大痛点：

| 痛点 | 表现 | 现代解法 |
|------|------|---------|
| 样板代码 | POJO 的字段/构造器/getter/equals/hashCode/toString 六件套占 80% 行数 | **record**：声明即全部 |
| 继承失控 | 任何类都可以被任意继承，子类行为不可预期，层次不可控 | **sealed**：限定合法子类型集合 |
| 手写分派 | `instanceof` + 强转 + 手动枚举类型分支，漏分支只有运行时才炸 | **模式匹配**：编译器穷尽性检查 |

三者共同的思想：**让编译器替程序员做安全检查**——数据不可变（record）、子类型集合已知（sealed）、分支穷尽（模式匹配）。

> 🎯 **核心要点**：这不再是语法糖，而是把"运行时错误"前置为"编译期错误"——新增子类型时编译器直接报"未处理分支"，而非线上 `ClassCastException`。

## 2. record：不可变数据载体

**record（JEP 395，Java 16 转正）**：声明不可变数据载体的一行式语法。自动生成：私有 final 字段、全参构造器、访问器（`字段名()` 而非 `get字段名()`）、值语义的 `equals`/`hashCode`、`toString`。

```java
// 传统 POJO：约 40 行
public final class User {
    private final String name;
    private final int age;
    public User(String name, int age) { this.name = name; this.age = age; }
    public String getName() { return name; }
    public int getAge() { return age; }
    // equals / hashCode / toString 省略 30 行……
}

// record：1 行
public record User(String name, int age) { }
```

**record 的完整能力**：

```java
public record Order(String id, BigDecimal amount, LocalDateTime createdAt) {

    // 紧凑构造器：参数在字段赋值前，可做校验（不写参数列表与 this.x = x）
    public Order {
        if (amount == null || amount.compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException("金额非法: " + amount);
        }
        Objects.requireNonNull(id);
    }

    // 静态工厂：传统构造器的替代入口
    public static Order ofNow(String id, BigDecimal amount) {
        return new Order(id, amount, LocalDateTime.now());
    }

    // 实例方法：行为与数据共存
    public Order withAmount(BigDecimal newAmount) {
        return new Order(id, newAmount, createdAt);   // with* 风格：返回新对象
    }
}

var o = new Order("A1", BigDecimal.TEN, LocalDateTime.now());
o.id();              // 访问器，不是 getId()
o.amount();
o.equals(o);         // 值语义：字段全等即相等
o.hashCode();        // 字段参与哈希
```

**record 的关键约束**：

- 隐式 `final`，不可继承、不可被继承；
- 字段全 `final`，不可变；
- 不能声明实例字段（`private int x` 之外的字段均非法），但可有静态字段/常量；
- 不能有 `native` 方法；可重写自动生成的成员（如自定义 `toString`）；
- 组件可以有注解（如 `@Nullable`、校验注解），并自动传播到字段/参数/访问器。

> 💡 **record 与 JSON 序列化**：Jackson 2.12+ 原生支持 record；Spring Boot 2.5+ 可用 record 做 DTO。反序列化走规范构造器，天然执行紧凑构造器中的校验——这比传统 JavaBean 的 setter 校验更安全。

## 3. sealed：受控继承

**sealed（JEP 409，Java 17 转正）**：声明类/接口的**合法子类型白名单**，白名单之外的任何类都无法继承/实现它。

```java
public sealed interface Shape permits Circle, Square, Triangle {
    double area();
}

// 直接子类必须属于 permits 列表，且标记 final / sealed / non-sealed 之一
public record Circle(double radius) implements Shape {
    @Override public double area() { return Math.PI * radius * radius; }
}

public final class Square implements Shape {
    private final double side;
    public Square(double side) { this.side = side; }
    @Override public double area() { return side * side; }
}

public non-sealed class Triangle implements Shape { ... }  // non-sealed：恢复开放继承

// 不在 permits 中 → 编译错误
public class Rectangle implements Shape { }   // ❌ class is not allowed to extend sealed interface Shape
```

**三种子类型形态**：

| 形态 | 含义 | 用途 |
|------|------|------|
| `final` | 封死：不可再被继承 | 叶子节点（绝大多数） |
| `sealed` | 继续受控开放 | 中间层再分层级 |
| `non-sealed` | 恢复开放继承 | 需要逃逸的罕见情况（尽量避免） |

**sealed 与 final 的区别**：`final` 是"全禁"，sealed 是"白名单制"——`Shape` 知道并控制自己有哪些子类型，编译器因此能做**穷尽性分析**（第 4 节），这是 final 提供不了的。

> ⚠️ 规则细节：① sealed 类的直接子类必须**同包**（或同模块）；② permits 列表中的类必须**直接**继承 sealed 类；③ 被继承的 sealed 类不能是 `non-sealed` 的孙类之外——即白名单是"直接一层"的。

## 4. 模式匹配：从 instanceof 到嵌套解构

**第一代：instanceof 模式匹配（JEP 394，Java 16 转正）**——判断与绑定合一：

```java
// 旧：instanceof + 强转
if (o instanceof String) { String s = (String) o; s.length(); }

// 新
if (o instanceof String s) { s.length(); }          // 类型判断通过即绑定
```

**第二代：switch 模式匹配（JEP 441，Java 21 转正）**——用 switch 做类型分派 + 穷尽性检查：

```java
public static String describe(Shape s) {
    return switch (s) {                              // switch 表达式，匹配类型而非值
        case Circle c -> "圆，半径 " + c.radius();
        case Square sq -> "正方形，边长 " + sq.side();
        case Triangle t -> "三角形";
        // 无需 default：sealed 让编译器验证所有子类型都已覆盖，漏一个就编译报错
    };
}
```

**第三代：记录模式 + 守卫（record patterns，JEP 440，Java 21 转正）**——嵌套解构与条件过滤：

```java
public sealed interface Notification permits Email, Sms {}

public record Email(String to, String subject, String body) implements Notification {}
public record Sms(String phone, String text) implements Notification {}

public String render(Notification n) {
    return switch (n) {
        case Email(var to, var subject, var body) when subject.contains("urgent")
                -> "紧急邮件: " + subject;                       // 守卫条件
        case Email(var to, var subject, var body) -> "邮件: " + subject;
        case Sms(var phone, var text) -> "短信: " + text;
    };
}

// 嵌套解构：一层拿到底
public double distance(Point p) {
    return switch (p) {
        case Point(var x, var y) -> Math.hypot(x, y);
    };
}
```

**编译器保证的三件事**（手写 if-else 链永远做不到）：

1. **穷尽性**：sealed 层次的所有子类型必须覆盖，漏分支编译报错；
2. **无强转**：变量直接可用，杜绝 `ClassCastException`；
3. **域分析**：`case` 顺序敏感时自动识别不可达分支（如先 `String s` 再 `Object o` 合法，反之报错）。

> 🎯 **核心要点**：模式匹配把"多态"从"方法分派"延伸到"**数据分派**"——根据对象的结构（record 字段）决定行为，这在传统 OOP 中只能靠大量手写 if-else。

## 5. 三件套协同：领域模型实战

**案例：订单状态机**

```java
// 1. sealed 定义状态全集
public sealed interface OrderState permits Pending, Confirmed, Shipped, Cancelled {}

// 2. record 定义各状态的载荷数据
public record Pending(LocalDateTime createdAt) implements OrderState {}
public record Confirmed(LocalDateTime confirmedAt, String operatorId) implements OrderState {}
public record Shipped(String trackingNo, LocalDateTime shippedAt) implements OrderState {}
public record Cancelled(String reason, LocalDateTime cancelledAt) implements OrderState {}

// 3. 模式匹配实现状态机转换（穷尽 + 可读）
public class Order {
    private OrderState state;

    public Order(OrderState initial) { this.state = initial; }

    public OrderState cancel() {
        return switch (state) {
            case Pending p -> new Cancelled("用户取消", LocalDateTime.now());    // 只有待支付可取消
            case Confirmed c -> new Cancelled("已确认后取消", LocalDateTime.now());
            case Shipped s -> throw new IllegalStateException("已发货不可取消");
            case Cancelled c -> throw new IllegalStateException("已取消不可重复取消");
        };
    }
}
```

**收益**：状态集合受控（sealed）、状态数据不可变且自带校验（record）、转换逻辑穷尽且无 default 兜底（模式匹配）——新增状态时编译器强制所有 switch 补分支，**状态机的完整性由编译器保证**。

## 6. 转正时间线（重要，别被错误文章误导）

网上大量文章声称"record 模式匹配/密封类在 JDK 25 才转正"，**这是错的**。以官方 JEP 为准：

| 特性 | JEP | 预览 | 转正版本 |
|------|-----|------|:-------:|
| record（记录类） | JEP 395 | Java 14 预览 | **Java 16** |
| sealed（密封类） | JEP 409 | Java 15/16 预览 | **Java 17** |
| instanceof 模式匹配 | JEP 394 | Java 14 预览 | **Java 16** |
| switch 模式匹配 | JEP 441 | Java 17/19/20 预览 | **Java 21** |
| 记录模式（嵌套解构） | JEP 440 | Java 19/20 预览 | **Java 21** |
| 未命名变量与模式 | JEP 456 | — | **Java 22** |
| 原始类型模式匹配 | JEP 507 | 预览中 | 未转正（JDK 25 第三次预览） |

> 💡 判断网上教程是否靠谱的快捷方法：看它是否标注了 JEP 编号与转正版本。声称"JDK 25 转正 record 模式"的文章基本是 AI 生成的错误内容。

## 7. record / sealed 与 JDK 25 的最新进展

JDK 25（2025-09-16 发布，LTS）与本主题直接相关的真实变化：

| 变化 | 说明 |
|------|------|
| **JEP 513 灵活构造器体** | `super()` 前允许写语句（校验、static 方法预处理），详见 06 模块第 4 节 |
| **JEP 507 原始类型模式匹配（第三次预览）** | 允许 `int`/`long` 等原始类型参与模式匹配，需 `--enable-preview` |
| **JEP 456（Java 22）未命名变量 `_`** | `case _ ->` 替代 `default`，`_` 丢弃不需要的变量，提升可读性 |
| 生态支持 | Spring Boot 3.4+、Jackson 2.16+ 对 record / sealed 的序列化支持已成熟 |

```java
// Java 22+：用 _ 处理"不关心"的分支（替代 default 的现代写法）
String typeOf(Object o) {
    return switch (o) {
        case Integer i -> "int";
        case String s -> "string";
        case Object _ -> "other";    // 未命名模式：不绑定变量
    };
}
```

> ⚠️ 面向生产环境：Java 17/21（LTS）已覆盖三件套全部转正特性；JDK 25 的相关增量（JEP 513）为增强项。**学习三件套用 17+ 即可，不必等预览特性**。

## 8. 何时仍用传统类：权衡取舍

| 场景 | 选择 | 原因 |
|------|------|------|
| DTO / VO / 查询参数 / 返回值 | record | 不可变 + 值相等 + 校验 |
| 状态机状态 / 领域事件 | sealed + record | 受控子类型 + 数据载荷 |
| 银行账户等**有状态可变**业务对象 | 传统类 + 封装 | 需要方法修改状态、保持不变量 |
| 依赖注入的 Bean / Service | 传统类 | Spring 管理生命周期，需要可变代理 |
| 需要继承复用骨架 | 传统类/抽象类 | record 不可继承、sealed 限制白名单 |
| 与旧框架强绑定的 POJO（如 MyBatis 老版本） | 传统 JavaBean | 需要无参构造器 + setter 的框架不兼容 record |

**判断公式**：数据无行为或行为只读 → record；类型集合封闭且需要穷尽处理 → sealed + 模式匹配；有状态、有生命周期、被框架管理 → 传统类。三者不是替代关系，是**互补的工具箱**。
