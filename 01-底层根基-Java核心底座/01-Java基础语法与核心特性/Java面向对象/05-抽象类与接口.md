## 1. 抽象类：骨架与扩展点

**抽象类**：不能被实例化的类，可包含**抽象方法**（只有声明没有实现）与普通方法。它表达"一类事物的公共骨架 + 留给子类的扩展点"。

```java
public abstract class ReportGenerator {
    protected abstract String loadData();      // 抽象方法：子类必须实现
    protected abstract String format(String data);

    public final String generate() {           // 模板方法：固定算法骨架
        String data = loadData();              // 扩展点 1
        String report = format(data);          // 扩展点 2
        return "===== 报表 =====\n" + report;
    }
}

public class SalesReport extends ReportGenerator {
    @Override protected String loadData() { return "本月销售额 100 万"; }
    @Override protected String format(String data) { return "销售:" + data; }
}
```

**抽象类要点**：

- 抽象方法不能有方法体，**不能是 private**（子类要重写，`static/final` 同理不行）；
- 有抽象方法的类必须声明为 `abstract`；抽象类可以没有抽象方法（用于禁止实例化）；
- 抽象类**有构造器**（子类 `super()` 调用），接口没有。

> 🎯 **核心要点**：抽象类的价值是**代码复用 + 骨架锁定**——`generate()` 定义算法顺序，子类只填空（模板方法模式，见 09 模块）。

## 2. 接口演进史：从纯抽象到默认方法

接口的定义随 Java 版本一直在"变厚"，理解这段历史才能理解为什么接口有今天这些成员：

| 版本 | 变化 | 原因 |
|------|------|------|
| Java 7 及以前 | 只能有：抽象方法 + `public static final` 常量 | 纯粹的行为契约 |
| Java 8（JEP 335） | 新增 **default 方法**、**static 方法** | 集合库需要给 `List` 等加 `stream()` 等新方法，若加抽象方法所有实现类（如第三方集合库）都要改——默认方法实现**接口向后兼容升级** |
| Java 9（JEP 213） | 新增 **private 方法**、**private static 方法** | 多个 default 方法共享逻辑时，不想把实现细节暴露为 public 方法 |
| Java 16+ | 接口可声明 **record 嵌套**等现代语法 | 语法的自然延伸 |

```java
public interface Calculator {
    // Java 7 及以前的能力：常量 + 抽象方法
    String NAME = "Calculator";                  // 隐式 public static final

    double add(double a, double b);              // 隐式 public abstract

    // Java 8：默认方法与静态方法
    default double multiply(double a, double b) {
        return multiplyWithLog(a, b);            // 复用私有方法
    }

    static double negate(double a) { return -a; } // 工具方法，不归实例

    // Java 9：私有方法，仅供本接口内部复用
    private double multiplyWithLog(double a, double b) {
        return a * b;
    }
}
```

> 💡 接口里写 `public static final` 是隐式的，但**显式写出来是更清晰的工程实践**；接口常量容易泄漏实现细节，现代实践更推荐枚举或静态工厂。

## 3. 抽象类 vs 接口十维对比

| 对比维度 | 抽象类 `abstract class` | 接口 `interface` |
|---------|:----------------------:|:----------------:|
| 继承方式 | 单继承 | 多实现 |
| 构造器 | ✅ 有 | ❌ 无 |
| 实例字段 | ✅ 任意类型 | ❌ 仅 `public static final` 常量 |
| 方法实现 | ✅ 任意实现 | default/static/private 方法（Java 8/9） |
| 抽象方法 | ✅ | ✅（隐式 public abstract） |
| 访问修饰符 | 完整四档 | 成员默认 public |
| 设计语义 | is-a：是什么、共同骨架 | can-do：能做什么、行为契约 |
| 演化成本 | 新增抽象方法会破坏所有子类 | default 方法可无损扩展 |
| 耦合度 | 较高（子类依赖父类结构） | 极低（实现者只承诺行为） |
| 典型用途 | 模板方法、共享状态、代码复用 | 依赖倒置、策略、能力声明（Comparable、Runnable） |

**一句话总结**：抽象类"把共性的实现给子类"，接口"把共性的契约给实现者"。

> ⚠️ **常见错误**：`abstract class` 中所有方法都写 `abstract`，然后当接口用——既不能多实现，又限制死在继承树上；反之，用接口承载"要共享的字段"，必然失败（接口没有实例字段）。

## 4. 选择决策树

```text
需要"多个实现 + 未来扩展"？
├── 是，且存在多个不同实现 → 接口（默认优先，依赖倒置）
└── 是否还需要以下任一能力？
    ├── 共享可复用的方法实现/字段状态 → 抽象类（+ 接口）
    ├── 固定算法骨架，只留扩展点   → 抽象类（模板方法）
    └── 仅仅是行为能力声明（可比较、可运行） → 接口
```

**工程上的推荐组合**：**接口定义契约 + 抽象类提供骨架实现（可选）+ 具体类完成实现**——这是 JDK 自身的经典结构（如 `List` 接口 + `AbstractList` 抽象类 + `ArrayList` 具体类）：

```text
List（接口：契约）
 └── AbstractList（抽象类：共享骨架，如迭代器、subList 的实现）
      └── ArrayList / LinkedList（具体类：只填数据结构特有的方法）
```

**什么情况偏向抽象类**：需要 protected 成员给子类用、需要非 final 实例字段共享状态、模板方法需要骨架。**什么时候一定用接口**：类型要扮演多种角色（一个类既可比又可就绪）、需要被第三方实现、依赖注入与代理的场景（Spring AOP 代理接口时用的是 JDK 动态代理，代理类时才用 CGLIB——这是选型差异的底层原因）。

## 5. 默认方法的菱形冲突解决规则

类实现多个接口时，若两个接口有**同名同签名 default 方法**，冲突按三条规则解决（优先级从高到低）：

1. **类优先于接口**：类自己声明的方法（含继承自父类的）胜出；
2. **子接口优先于父接口**：更具体的接口 default 方法胜出；
3. **否则必须显式覆盖**：类必须重写该方法并指定调用哪个接口的默认实现（`接口名.super.方法()`）。

```java
public interface A {
    default void greet() { System.out.println("Hello from A"); }
}

public interface B {
    default void greet() { System.out.println("Hello from B"); }
}

public class Impl implements A, B {
    // 规则 3 触发：两个接口平级冲突，必须显式解决
    @Override
    public void greet() {
        A.super.greet();          // 指定调用 A 的默认实现
        B.super.greet();
    }
}
```

```java
public class Base {
    public void greet() { System.out.println("Hello from Base"); }
}

public class Impl2 extends Base implements A, B {
    // 规则 1 触发：父类方法胜出，什么都不用写
}
```

> 💡 `接口名.super.方法()` 语法只在实现类内部可用，是默认方法冲突的专用解决手段；`A.super.greet()` 表示调用 A 的默认实现，而非实例方法。

## 6. 函数式接口与 Lambda 协作

**函数式接口**：恰好只有一个抽象方法的接口（default/static/private 方法不计入），用 `@FunctionalInterface` 标注让编译器检查。

```java
@FunctionalInterface
public interface DiscountStrategy {
    BigDecimal apply(BigDecimal price);          // 唯一抽象方法
}

// 使用时一个 Lambda 就是一份实现 —— 接口从"契约"变成了"行为参数"
DiscountStrategy strategy = price -> price.multiply(BigDecimal.valueOf(0.8));
```

| 函数式接口 | 抽象方法 | 用途 |
|-----------|---------|------|
| `Function<T,R>` | `R apply(T)` | 转换 |
| `Predicate<T>` | `boolean test(T)` | 过滤条件 |
| `Consumer<T>` | `void accept(T)` | 消费副作用 |
| `Supplier<T>` | `T get()` | 延迟供应 |
| `Comparator<T>` | `int compare(T,T)` | 排序规则 |

> 🎯 **核心要点**：函数式接口把"多态"从"对象的不同实现"推进到"行为的不同实现"——策略模式在新代码里基本不再写实现类，直接传 Lambda（与 Lambda 系统衔接，详见 `Lambda表达式/` 知识系统）。

## 7. 实战：接口定契约、抽象类沉淀骨架

以支付渠道统一收单为例，展示三层结构：

```java
// 第 1 层：接口定义契约（业务层只依赖这一层）
public interface PayChannel {
    PayResult pay(PayRequest request);
    PayResult refund(RefundRequest request);
    String channelId();
}

// 第 2 层：抽象类沉淀公共骨架（签名验签、日志、重试）
public abstract class AbstractPayChannel implements PayChannel {
    @Override
    public final PayResult pay(PayRequest request) {
        long start = System.currentTimeMillis();
        try {
            validate(request);                  // 抽象方法：各渠道自己的校验
            signAndTrace(request);              // 公共逻辑：签名、埋点
            PayResult result = doPay(request);  // 抽象方法：真正的渠道调用
            logElapsed(start, channelId());
            return result;
        } catch (Exception e) {
            return retryAndRecord(e, request);  // 公共逻辑：重试与记账
        }
    }

    protected abstract void validate(PayRequest request);
    protected abstract PayResult doPay(PayRequest request);
    private void signAndTrace(PayRequest request) { /* 签名与全链路日志 */ }
    private void logElapsed(long start, String channelId) { /* 耗时监控 */ }
    private PayResult retryAndRecord(Exception e, PayRequest request) { /* 重试 + 落库 */ }
}

// 第 3 层：具体渠道实现只填差异
public class WeChatChannel extends AbstractPayChannel {
    @Override protected void validate(PayRequest r) { /* 微信特有校验 */ }
    @Override protected PayResult doPay(PayRequest r) { /* 调用微信 API */ }
    @Override public String channelId() { return "wechat"; }
}
```

**这套结构的三重收益**：

1. **依赖倒置**：业务层面向 `PayChannel` 接口编程，新增渠道零改动；
2. **骨架复用**：签名、日志、重试、监控等横切逻辑只写一遍；
3. **规则约束**：`final` 的 `pay()` 保证所有渠道必须走统一流程，无法绕过公共逻辑。

> ⚠️ 注意第 2 层的 `pay()` 被声明为 `final`——这正是模板方法安全性的来源：骨架锁定，只有扩展点开放。
