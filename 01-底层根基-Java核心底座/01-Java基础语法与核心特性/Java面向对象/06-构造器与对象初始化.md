## 1. 构造器基础与重载调用链

**构造器规则**：

- 名称与类名相同，无返回类型（连 `void` 都不写）；
- 构造器可以被重载（参数列表不同）；
- 构造器**不能**被 `abstract`/`static`/`final` 修饰，**不能**被重写；
- 访问权限通常 `public` 或 `private`（私有构造器用于单例/工具类）。

**重载构造器的链接——`this(...)` 必须第一行**：

```java
public class Order {
    private final String orderId;
    private final BigDecimal amount;
    private final LocalDateTime createdAt;

    // 主构造器：所有字段完整赋值
    public Order(String orderId, BigDecimal amount, LocalDateTime createdAt) {
        this.orderId = orderId;
        this.amount = amount;
        this.createdAt = createdAt;
    }

    // 便捷构造器：委托主构造器，补默认值
    public Order(String orderId, BigDecimal amount) {
        this(orderId, amount, LocalDateTime.now());   // 必须第一行
    }

    // 最简构造器：继续向上委托
    public Order() {
        this("UNKNOWN", BigDecimal.ZERO);
    }
}
```

> 💡 委托链设计原则：**只有"主构造器"负责真正赋值**，其余构造器只做参数默认化与校验后 `this(...)` 委托——避免每个构造器重复赋值逻辑。

## 2. 默认构造器与隐式 super()

**默认构造器规则**：

| 情况 | 行为 |
|------|------|
| 类中没有任何构造器 | 编译器自动生成无参构造器（`public` 或与类同权限） |
| 写了任意一个构造器 | **不再自动生成**无参构造器——注意此时 `new X()` 编译失败 |

```java
public class A { }                      // 隐式有无参构造器

public class B {                        // 显式构造器后：
    public B(int x) { }                 // 无参构造器消失，new B() 报错
}

public class C extends A { }            // C() 隐式调用 super()，A 有无参构造器 ✅
public class D extends B {
    public D() { super(1); }            // B 无无参构造器，必须显式 super(1)
}
```

> ⚠️ **经典编译错误**：父类只写了带参构造器，子类没写任何构造器 → 子类隐式 `super()` 找不到无参父类构造器 → 编译失败。解法：父类补无参构造器，或子类显式 `super(参数)`。

## 3. 初始化顺序全览

一个对象从类加载到构造器执行完毕的完整顺序（单类场景）：

```text
① 类加载：静态字段（按声明顺序）→ 静态块（按声明顺序）      —— 只执行一次
② new：分配内存 + 字段默认值（null/0/false）
③ 实例字段初始化（按声明顺序）与实例块（按声明顺序）交替执行
④ 构造器体执行
```

继承场景（父类先于子类，详见 03 模块第 6 节）：

```text
父类静态 → 子类静态 → 父类字段/实例块 → 父类构造器 → 子类字段/实例块 → 子类构造器
```

**字段初始化在构造器体之前**，意味着构造器体里读到的字段已经是赋值后的值：

```java
public class Demo {
    private final String name = "已初始化";   // 构造器体执行前已完成

    public Demo() {
        System.out.println(name);             // 输出"已初始化"而非 null
    }
}
```

## 4. JDK 25 灵活构造器体：super() 前终于可以写代码

**历史限制**：构造器中 `super(...)`/`this(...)` 之前不允许任何语句（除注释），这是 Java 长期被诟病的设计缺陷——想在父类构造器执行前做参数校验、赋值本地变量、预处理参数都不行，只能绕道静态方法：

```java
// 旧写法：校验与预处理必须挪到静态工厂里
public class Age {
    public Age(int age) {
        super(validate(age));          // 只能靠静态方法先算好
    }
    private static int validate(int age) {
        if (age < 0) throw new IllegalArgumentException();
        return age * 10;               // 预处理也挤在这里
    }
}
```

**JDK 25（JEP 513）灵活构造器体**：允许 `super()` 之前书写语句——只要语句**不读取被构造对象的实例字段、不调用实例方法**（对象尚未构造完成）：

```java
public class Age {
    public Age(int age) {
        if (age < 0) {                          // ✅ 现在可以直接校验
            throw new IllegalArgumentException("age 不能为负");
        }
        int effective = clamp(age);             // ✅ 调用 static 方法预处理
        super(effective);                       // super 终于可以靠后
    }
    private static int clamp(int v) { return Math.min(v, 200); }
}
```

**规则约束**（保证安全）：`super()` 前的语句只能访问参数与 `static` 成员——`this.字段`、`this.方法()` 依然禁止；`final` 字段若在 `super()` 前初始化则需注意初始化语义。该特性同时解决了"子类字段在父类构造器执行前初始化"的另一半问题（结合 03 模块的构造器调用可重写方法陷阱一起理解）。

> 🎯 **核心要点**：JEP 513 把"校验/预处理"放回构造器本体，消除了静态工厂的绕道——但约束依然明确：**super 前只准碰参数和静态成员**。

## 5. 六种单例写法对比

| 写法 | 线程安全 | 懒加载 | 序列化/反射安全 | 复杂度 | 评价 |
|------|:-------:|:-----:|:--------------:|:------:|------|
| 饿汉式（static final） | ✅ | ❌ | 基本安全 | ★ | 简单可靠，类加载即创建 |
| 懒汉式（synchronized 方法） | ✅ | ✅ | ❌ | ★ | 每次调用加锁，性能差 |
| 双重检查 DCL（volatile） | ✅ | ✅ | ❌ | ★★★ | 经典但易写错，需 volatile |
| 静态内部类 | ✅ | ✅ | ❌ | ★★ | 推荐：JVM 天然懒加载 |
| 枚举单例 | ✅ | ✅ | ✅ | ★ | **最佳**：反序列化/反射天然免疫 |
| 容器单例（Spring Bean） | ✅ | ✅ | - | - | 框架层面管理，业务无需自写 |

```java
// 饿汉式：类加载即创建，简单但可能白占内存
public class EagerSingleton {
    private static final EagerSingleton INSTANCE = new EagerSingleton();
    private EagerSingleton() { }
    public static EagerSingleton getInstance() { return INSTANCE; }
}

// 静态内部类：JVM 保证类初始化唯一性，天然懒加载 + 线程安全
public class HolderSingleton {
    private HolderSingleton() { }
    private static class Holder {
        private static final HolderSingleton INSTANCE = new HolderSingleton();
    }
    public static HolderSingleton getInstance() { return Holder.INSTANCE; }
}

// 双重检查锁：注意 volatile 必不可少
public class DclSingleton {
    private static volatile DclSingleton instance;   // volatile 防止指令重排暴露半初始化对象
    private DclSingleton() { }
    public static DclSingleton getInstance() {
        if (instance == null) {                      // 第一次检查：避免无谓加锁
            synchronized (DclSingleton.class) {
                if (instance == null) {              // 第二次检查：阻塞后再次确认
                    instance = new DclSingleton();   // 三步（分配/初始化/赋值）可能重排
                }
            }
        }
        return instance;
    }
}

// 枚举单例：最简单且防御最强
public enum EnumSingleton {
    INSTANCE;
    public void doSomething() { /* 业务方法 */ }
}
// 使用：EnumSingleton.INSTANCE.doSomething()
```

> ⚠️ **为什么枚举单例最强**：枚举由 JVM 保证实例唯一，构造器是 `private` 且**反射 `Constructor.newInstance()` 直接抛异常**，序列化反序列化也返回同一个实例——饿汉/懒汉/DCL/静态内部类这四种写法都需要额外防御（`readResolve()`、反射检查）。`Effective Java` 明确推荐枚举单例。

## 6. Builder 模式：手写与场景

**什么时候需要 Builder**：

- 字段多（4 个以上）且大量可选；
- 有必填与可选之分；
- 参数间存在依赖校验（如 `width` 与 `height` 需同时存在）；
- 对象不可变（无 setter，只能靠构造器——构造器重载组合爆炸）。

```java
public final class HttpRequest {
    private final String url;           // 必填
    private final String method;        // 默认 GET
    private final Map<String, String> headers;  // 可选
    private final String body;          // 可选

    private HttpRequest(Builder b) {
        this.url = b.url;
        this.method = b.method;
        this.headers = Map.copyOf(b.headers);   // 防御性拷贝
        this.body = b.body;
    }

    public static Builder builder(String url) { return new Builder(url); }

    public static class Builder {                // 静态内部类：不依赖外部实例
        private final String url;
        private String method = "GET";
        private final Map<String, String> headers = new HashMap<>();
        private String body;

        private Builder(String url) { this.url = url; }

        public Builder method(String method) { this.method = method; return this; }
        public Builder header(String k, String v) { headers.put(k, v); return this; }
        public Builder body(String body) { this.body = body; return this; }

        public HttpRequest build() {
            if (url == null || url.isBlank()) throw new IllegalStateException("url 必填");
            return new HttpRequest(this);        // 校验放在 build() 统一执行
        }
    }
}

// 使用：必填走构造、可选链式，可读性远胜 8 参构造器
HttpRequest req = HttpRequest.builder("https://api.example.com")
        .method("POST")
        .header("Content-Type", "application/json")
        .body("{\"name\":\"test\"}")
        .build();
```

> 💡 Builder 与构造器的取舍：字段 ≤ 3 个时构造器更简单直接；字段多且不可变时 Builder 值得；而**简单可变对象用 setter 就够**，不要为了模式而模式（详见 09 模块"过度设计"）。

## 7. 构造器设计规范与陷阱

| 规范/陷阱 | 说明 |
|----------|------|
| 构造器中**禁止调用可重写方法** | 父类构造器执行时子类字段未初始化，重写方法读到默认值（见 03 模块） |
| 构造器完成即"安全发布" | 不要在构造器中把 `this` 泄漏出去（如注册到监听器、传入线程），外部可能看到未构造完成的对象 |
| 构造器抛异常是合法的 | 参数非法时抛 `IllegalArgumentException` 是正确姿势，但要注意**部分字段已分配**的清理由 JVM 完成 |
| 拷贝构造器要深拷贝 | `new ArrayList<>(other.list)` 是浅拷贝一层，嵌套可变对象仍需逐层拷贝 |
| 大量参数禁止直接构造器 | 超过 4 个参数或大量可选参数 → Builder（上文） |
| 优先考虑静态工厂而非构造器 | 工厂方法有名字、可缓存、可返回子类型（`Integer.valueOf`、`LocalDate.of`） |

**静态工厂 vs 构造器速查**：

| 维度 | 构造器 | 静态工厂（如 `valueOf`/`of`/`from`） |
|------|--------|-------------------------------------|
| 命名 | 固定类名 | 可表达语义（`of`/`parse`/`cache`） |
| 每次调用 | 必新建对象 | 可返回缓存实例 |
| 返回类型 | 只能是本类 | 可返回接口或子类 |
| 条件构造 | 不支持 | 可返回 null 或抛异常 |
