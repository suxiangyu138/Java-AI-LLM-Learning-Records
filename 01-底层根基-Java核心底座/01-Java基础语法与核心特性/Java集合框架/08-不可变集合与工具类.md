## 1. 不可变集合三件套：List.of / Set.of / Map.of

**JDK 9（JEP 269）引入**——工厂方法创建**真正不可变**（immutable）的集合：

```java
List<String> l = List.of("a", "b", "c");
Set<Integer> s = Set.of(1, 2, 3);
Map<String, Integer> m = Map.of("a", 1, "b", 2);          // ≤10 对
Map<String, Integer> m2 = Map.ofEntries(
        Map.entry("a", 1), Map.entry("b", 2));            // 任意数量
```

**不可变的三层含义**：

| 维度 | 行为 |
|------|------|
| 不可增删改 | `add/remove/put` 全部抛 `UnsupportedOperationException` |
| 不可变元素引用 | 内部数组私有且无访问出口——但元素对象本身可变（`List.of(new StringBuilder())` 里的 sb 仍可 append） |
| 不可空 | **元素/键值均禁止 null**（构造即抛 NPE） |

**内部结构**（值得一提的优化）：`List.of` 的 0/1 元素是单例与静态内部类；`Set.of`/`Map.of` 的元素个数不同使用**不同专精内部类**（`MapN`/`Map1`/`SetN`），并做了**固定哈希桶优化**——大多数场景内存与性能都优于普通集合。

> 🎯 **核心要点**：`List.of` 是"构造即不可变"——它与"包装不可变视图"（unmodifiableList）的本质区别：**视图之下藏着可变原集合，任何人拿到原集合引用仍能改**；of 是"复制后再封死"，没有后门。

## 2. copyOf 与不可变视图的差异

**三种"不可变"手段对比**（面试高频）：

| 手段 | 版本 | 行为 | 特性 |
|------|------|------|------|
| `List.of(...)` | JDK 9 | 复制元素 → 封死 | 复制后与原集合**完全脱离** |
| `List.copyOf(c)` | JDK 10 | 同 of，但输入是已有集合 | 原集合改变不影响副本；若入参已是不可变 → 直接返回原对象（零拷贝） |
| `Collections.unmodifiableList(c)` | JDK 1.2 | **包装视图**，不复制 | 原集合可变 → 视图随之变；视图本身拒绝修改 |

```java
// unmodifiable 视图的"后门"演示
List<String> inner = new ArrayList<>(List.of("a"));
List<String> view = Collections.unmodifiableList(inner);
view.add("b");                    // ❌ UnsupportedOperationException
inner.add("b");                   // ✅ 原集合还能改！
System.out.println(view);         // [a, b] —— 视图被"穿透"了

// copyOf 的彻底隔离
List<String> safe = List.copyOf(inner);
inner.add("c");                   // safe 不受影响

// Set/Map 同名：Set.copyOf / Map.copyOf
```

**实战选型**：

| 需求 | 选择 |
|------|------|
| 常量配置、枚举数据（写死的内容） | `List.of` / `Set.of` / `Map.of` |
| 把运行期收集的数据"快照"发布 | `List.copyOf(list)`（还可额外保证快照不可变） |
| 需要保留原集合、且接受"视图随原变" | `Collections.unmodifiableList`（如内部字段对外暴露） |

> ⚠️ **防御性编程经典**：对外暴露内部 List 字段时，用 `Collections.unmodifiableList(this.items)` 让"调用方无法通过 getter 修改内部状态"（见面向对象 02 模块防御性拷贝）——**unmodifiable 视图的价值不在"防自己"而在"防调用方"**。

## 3. Collections 工具类全景

**Collections 是静态工具类**（不可实例化），与 Collection 接口的混淆点：**Collections（工具）≠ Collection（接口）**。

### 3.1 排序与查找

| 方法 | 说明 |
|------|------|
| `sort(list)` / `sort(list, cmp)` | 排序（见 07 模块） |
| `binarySearch(list, key)` | **必须先排好序**，否则结果未定义；返回负插入点（`-(插入点)-1`） |
| `reverse` / `shuffle` / `rotate` | 反转 / 洗牌 / 旋转 |
| `min` / `max` | 求极值（接受集合或比较器） |
| `fill(list, obj)` | 全部替换为同一对象 |

### 3.2 包装器三兄弟

```java
// 同步包装：线程安全但全局锁（见 06 模块第 7 节）
List<String> sync = Collections.synchronizedList(new ArrayList<>());

// 不可变包装：视图（见上节）
List<String> unmod = Collections.unmodifiableList(list);

// 类型检查包装：运行时类型门禁（防"原始类型泄漏"）
List<String> checked = Collections.checkedList(rawList, String.class);
```

### 3.3 单例与空集合（判空零分配）

```java
Collections.emptyList();   // 共享单例，判空返回它避免新建对象 —— 老代码常用
Collections.emptySet();
Collections.emptyMap();
Collections.singletonList("a");   // 单元素不可变集合，常用作入参
// JDK 9+ 更简洁：List.of() 空集合 / List.of("a") 单元素 —— 日常优先 of 系列
```

> 💡 判空返回 `Collections.emptyList()` 是常见优化模式——调用方拿到空集合不会 NPE（区别于返回 null），且零对象分配。JDK 9 后同样效果可写 `List.of()`。

## 4. Arrays 工具类全景

**Arrays 专攻数组**（List 管动态集合，Arrays 管原生数组与转换）：

| 能力 | 方法 | 要点 |
|------|------|------|
| 转列表 | `asList(T...)` | **固定大小**数组视图：不可增删、修改写穿数组（见 02 模块陷阱） |
| 排序 | `sort` / `parallelSort` | 基本类型双轴快排 / 对象归并（见 07 模块第 4 节） |
| 二分 | `binarySearch(arr, key)` | 必须先排序，未命中返回负插入点 |
| 拷贝 | `copyOf` / `copyOfRange` | 内部就是扩容/复制的实现基础（ArrayList 扩容用它） |
| 填充 | `fill(arr, v)` | 全部赋同值 |
| 比较 | `equals` / `deepEquals` | deep* 用于多维/嵌套数组 |
| 哈希 | `hashCode` / `deepHashCode` | 数组作为 Map 键前必须用 Arrays.hashCode |
| 字符串 | `toString` / `deepToString` | **数组直接 println 打印的是地址**，要看内容必须用它 |

```java
int[] arr = {3, 1, 2};
Arrays.sort(arr);                      // 原地排序
int idx = Arrays.binarySearch(arr, 2); // 1
int[] copy = Arrays.copyOf(arr, arr.length);   // 完整副本（深一层：元素是引用则共享）

// 数组转集合的正确姿势
List<Integer> list = Arrays.asList(1, 2, 3);          // 固定大小视图
List<Integer> growable = new ArrayList<>(Arrays.asList(1, 2, 3));  // 可变列表
List<Integer> immutable = List.of(1, 2, 3);           // 不可变（JDK 9+ 首选）
```

> ⚠️ **数组打印陷阱**：`System.out.println(arr)` 输出 `[I@1b6d3586`（类型+哈希）——必须 `Arrays.toString(arr)`；二维数组要 `deepToString`。`int[]` 与 `Integer[]` 的 asList 也完全不同（前者是单元素 `List<int[]>`），是经典坑。

## 5. 不可变集合的边界行为

| 操作 | 行为 |
|------|------|
| `add` / `remove` / `set` / `clear` | `UnsupportedOperationException` |
| `add(null)` 构造 | 构造时 `NullPointerException`（`List.of(null)` 直接抛） |
| 迭代器 `remove()` | `UnsupportedOperationException` |
| `subList` 再操作 | 同抛异常（视图同样不可变） |
| 排序 `list.sort(...)` | 抛异常（内部要交换元素） |
| 元素本身可变 | 允许且无法阻止（`List.of(new StringBuilder("a"))` 的元素可 append） |
| 与 Stream 结合 | `stream().filter(...).toList()` 结果也是不可变（JDK 16+） |

**不可变集合的好处**（为什么值得用）：

1. **线程安全**：无需任何同步即可共享——最廉价的并发方案；
2. **防意外修改**：常量、配置、内部状态不怕被改动；
3. **可安全缓存共享**：`String`、`Integer` 等不可变值的集合可放心复用同一实例；
4. **结构更优**：`of` 系列专精内部类省内存。

> 🎯 **核心要点**：不可变集合是"安全 + 省心"的默认选择——**能不可变就不可变**（Effective Java 的明确建议）：API 返回用不可变集合，配置项用 of 系列，只有"明确需要动态增删"时才用可变集合。

## 6. 实践：不可变集合的正确用法

**实践 1：配置常量**（防误改、可共享）：

```java
public static final Set<String> ALLOWED_CHANNELS = Set.of("wechat", "alipay", "unionpay");
public static final Map<String, String> HEADER_DEFAULTS = Map.of(
        "Content-Type", "application/json",
        "Accept", "application/json"
);
```

**实践 2：DTO 返回值**（发布数据快照）：

```java
public List<OrderDto> listOrders() {
    List<OrderDto> snapshot = orderDao.findAll().stream()
            .map(OrderDto::from)
            .collect(Collectors.toList());      // 收集为可变
    return List.copyOf(snapshot);              // 发布为不可变 —— 调用方无法篡改
}
// JDK 16+ 简化：.toList() 直接产出不可变列表
```

**实践 3：方法参数防御**：

```java
// 参数声明为不可变语义？—— 不行，接口不强制。
// 真正防御：内部复制
public void apply(List<String> channels) {
    this.channels = List.copyOf(channels);     // 复制入参，外部后续修改不影响内部状态
}
```

> ⚠️ 注意区分：`List.copyOf` 复制**一层**——若元素本身可变（如 List of List），外层不可变但内层仍可改；需要深度不可变必须元素也不可变（或使用 record + 不可变内部结构）。
