## 1. 测试的心态

> 🎯 **第一心态**：测试代码的质量 = 生产代码的质量——测试是交付物的一部分，不是「有时间再做」的附件。

```text
测试的三大价值
├── ① 可执行的文档：测试描述「这段代码承诺了什么」
├── ② 重构的安全网：没测试的重构是走钢丝
├── ③ 需求的对齐：写测试的过程就是确认需求的过程
→ 没有测试的代码 = 承诺了行为但无法验证的代码
```

| ❌ 反测试心态 | ✅ 测试心态 |
|-------------|-----------|
| 「先写功能，测试有空补」 | 「测试与代码同步交付」 |
| 「代码能跑就是对的」 | 「能跑 + 有测试证明它一直对」 |
| 「测试拖慢开发」 | 「测试避免返工，长期更快」 |

## 2. F.I.R.S.T 五原则

| 原则 | 含义 | 违例信号 |
|------|------|---------|
| **F**ast（快速） | 测试秒级运行 | 单测访问数据库/网络 |
| **I**ndependent（独立） | 测试互不依赖 | 测试有顺序要求 |
| **R**epeatable（可重复） | 任何环境都能跑 | 依赖系统时间/环境 |
| **S**elf-validating（自我验证） | 通过/失败自动判定 | 测试里有人工观察 |
| **T**imely（及时） | 测试及时编写 | 功能上线后补测试 |

```java
// ✅ 独立 + 可重复：用 Mock 隔离外部依赖
@Test
void refund_whenBalanceSufficient_shouldSucceed() {
    PaymentGateway gateway = mock(PaymentGateway.class);
    when(gateway.charge(any(), any())).thenReturn(success());

    OrderService service = new OrderService(gateway);
    OrderResult result = service.refund(order("ORD-1", 100.0));

    assertThat(result.isSuccess()).isTrue();
    verify(gateway).charge(eq("ORD-1"), any());   // 自我验证：行为断言
}

// ❌ 违例：依赖真实数据库 + 有执行顺序
@Test
void test1() { ... realDatabase.save(...); }   // 慢 + 依赖环境
```

## 3. 红绿重构：测试驱动开发

### 3.1 循环

```
红绿重构循环（TDD）
┌─────────────────────────────────────┐
│ ① Red（红）：先写一个失败的测试        │ ← 明确"想要什么行为"
│ ② Green（绿）：用最小代码让测试通过    │ ← 只做让它通过的事
│ ③ Refactor（重构）：清理代码保持测试绿  │ ← 质量与行为分离
└─────────────────────────────────────┘
        循环往复，每步都有测试保护
```

### 3.2 为什么先写测试

```text
先写测试的价值
├── ① 设计驱动：被迫先想"接口长什么样"（测试即设计）
├── ② 需求确认：测试写不出来 = 需求没想清楚
├── ③ 安全感：每步都有安全网，重构无压力
└── ④ 范围控制：只实现让测试通过的功能（天然 YAGNI）
```

### 3.3 实践示例

```java
// ① Red：先写失败测试（定义期望行为）
@Test
void isOverdue_whenExpired_shouldReturnTrue() {
    Order order = new Order(LocalDateTime.now().minusDays(31), "PAYING");
    assertThat(order.isOverdue(30)).isTrue();   // 方法还不存在 → 编译失败（红）
}

// ② Green：最小实现
public boolean isOverdue(int days) {
    return LocalDateTime.now().isAfter(createdAt.plusDays(days));
}

// ③ Refactor：清理（测试全绿时放心重构）
public boolean isOverdue(int days) {
    return Duration.between(createdAt, LocalDateTime.now()).toDays() > days;
}
```

> 💡 **Karpathy 2026 观察的印证**：AI 时代「先复现再修复」（Reproduce Before Fixing）——让 AI 修 bug 前先写一个复现问题的测试，修复的定义从「看起来好了」变成「测试变绿了」。

## 4. 测试金字塔

### 4.1 金字塔结构

```
        ▲ 端到端测试（少量）
       / \      验证完整用户流程（真环境）
      /   \
    / 集成测试 \   验证模块协作（真实依赖/模拟服务）
  /_____________\
 /   单元测试     \   验证单个方法/类（Mock 隔离，快而多）
/_________________\
```

| 层级 | 数量 | 速度 | 隔离 | 测什么 |
|------|:---:|:---:|:---:|--------|
| 单元测试 | 多（70%+） | 毫秒级 | Mock | 业务逻辑 |
| 集成测试 | 中（20%） | 秒级 | 真实依赖 | 模块协作 |
| 端到端 | 少（10%） | 分钟级 | 全真 | 用户流程 |

### 4.2 金字塔实践

```text
测试分配习惯
├── 业务规则 → 单元测试（最多、最快）
├── 数据访问/外部服务 → 集成测试（Testcontainers 等）
├── 核心用户旅程 → 端到端（每条主流程 1-2 条）
└── 倒金字塔（E2E 为主）→ 慢 + 脆 + 贵，是坏味道
```

## 5. 测试代码质量

### 5.1 测试与生产同等质量

```java
// ❌ 坏测试：难以理解、难以维护
@Test
void t1() {
    var x = svc.f(1);
    assertTrue(x);         // f(1) 是什么？断言什么？失败信息是什么？
}

// ✅ 好测试：命名即文档 + 三段式结构
@Test
void refund_whenOrderAlreadyRefunded_shouldRejectDuplicate() {
    // Given：已退款订单
    Order order = orderFixture.refunded();
    // When：再次退款
    OrderResult result = orderService.refund(order.getId());
    // Then：拒绝且不重复扣款
    assertThat(result.getStatus()).isEqualTo(REJECTED);
    assertThat(result.getReason()).contains("已退款");
    verify(paymentGateway, never()).charge(any(), any());
}
```

### 5.2 好测试五习惯

| # | 习惯 | 说明 |
|---|------|------|
| 1 | **命名 = 文档** | `method_whenCondition_shouldOutcome` 三段式 |
| 2 | **一个测试一个概念** | 一个断言主题，别塞 10 个断言 |
| 3 | **Given-When-Then** | 准备/执行/断言三区清晰 |
| 4 | **固定夹具** | 用 fixture 工厂，不用随机数据 |
| 5 | **断言行为不实现** | 断言结果，不断言内部实现细节 |

> 🎯 **测试的验收标准**：别人读你的测试，应该能回答三个问题——这段代码承诺了什么？怎么用？失败时会发生什么？

## 6. 覆盖率：行为护栏

### 6.1 覆盖率的正确认知

> ⚠️ **覆盖率是必要不充分指标**：100% 覆盖率不代表代码正确（可以断言了一堆废话），但覆盖率门禁能**暴露被忽视的行为**——它是护栏，不是目标。

```text
覆盖率的使用方式
├── ❌ 错误：追求 100% 覆盖率数字（形式主义）
├── ✅ 正确：覆盖率门禁作为 CI 行为护栏
│   ├── 新代码必须有测试（行覆盖门禁）
│   ├── 核心模块覆盖率目标（如 >80%）
│   └── 覆盖率下降 = 行为未被保障 = PR 拦截
└── 2026 补充：覆盖率门禁让「削弱行为检查」的改动可见
```

### 6.2 门禁配置示例

```xml
<!-- JaCoCo 覆盖率门禁（Maven 示例） -->
<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <executions>
    <execution>
      <id>check</id>
      <goals><goal>check</goal></goals>
      <configuration>
        <rules>
          <rule>
            <element>BUNDLE</element>
            <limits>
              <limit>
                <counter>LINE</counter>
                <value>COVEREDRATIO</value>
                <minimum>0.80</minimum>   <!-- 行覆盖率 ≥ 80% -->
              </limit>
            </limits>
          </rule>
        </rules>
      </configuration>
    </execution>
  </executions>
</plugin>
```

### 6.3 覆盖率盲区

```text
覆盖率看不出的三类问题
├── ① 边界条件未测（覆盖了行，没覆盖分支）
├── ② 错误路径未测（异常分支没断言）
├── ③ 行为错误（测了，但断言的是错误行为）
→ 习惯：分支覆盖 + 异常场景测试 + 行为断言，比行数更重要
```

## 7. AI 时代的测试习惯

> ⚠️ **2026 关键认知**：AI 默认只测试 happy path（快乐路径）——让 AI 生成测试时必须显式要求覆盖：**快乐路径 + 校验错误 + 边界用例 + 错误处理**。

### 7.1 AI 测试提示词要点

```text
让 AI 生成测试的四段式
【任务】为 OrderService.createOrder 编写单元测试
【约束】
- 覆盖场景：happy path / 金额为 null / 金额为负 / 商品不存在 / 重复提交
- 使用 JUnit5 + Mockito，禁止访问真实数据库
- 断言使用 assertThat，命名遵循 method_whenCondition_shouldOutcome
【输出】OrderServiceTest.java + 每个用例一句话意图
```

### 7.2 AI 时代测试四习惯

| # | 习惯 | 说明 |
|---|------|------|
| 1 | **测试先于 AI 代码** | 先写测试定义行为，再让 AI 实现（红绿重构的 AI 版） |
| 2 | **快乐路径是默认，必须显式补边界** | AI 只测 happy path——检查它漏了什么 |
| 3 | **每次 AI 改动必须全绿** | AI 改代码 → 跑全量测试 → 绿才合入 |
| 4 | **覆盖率门禁防回归** | 门禁让 AI 删测试/弱化断言的行为现形 |

> 🎯 **AI 时代测试金句**：**让 AI 交付的每个改动都配一个绿色测试套件 + 人工 diff 审查**——这区分了「交付更干净代码的团队」与「交付更快回归的团队」。

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 测试 = 可执行文档 + 重构安全网——质量与代码同步交付
> 2. F.I.R.S.T 五原则（快/独立/可重复/自验证/及时）+ 三段式命名
> 3. 红绿重构循环：先写失败测试 → 最小实现 → 重构；每步有安全网
> 4. 覆盖率是行为护栏不是目标（门禁 80%+，防 AI 弱化测试）；AI 时代显式要求边界场景 + 全绿门禁
