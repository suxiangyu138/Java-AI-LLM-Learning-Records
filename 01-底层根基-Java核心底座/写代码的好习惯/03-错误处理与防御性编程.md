## 1. 错误处理的心态

> 🎯 **第一心态**：假设一切都会出错——网络会断、数据库会挂、用户会输入任何东西、下游服务会超时。**写代码时先想「这行如果失败了会怎样」**，再想「这行怎么工作」。

```text
错误处理心态转变
├── ❌ 乐观心态：「这里不会出错」（出事时毫无准备）
├── ✅ 悲观心态：「这里一定会出错，我要决定失败的方式」
└── 金句：代码的正确路径只有一条，错误路径有无数条——
    每一条错误路径都是你写的代码，都要负责
```

| 常见事故 | 根因 |
|---------|------|
| 空指针 | 没做 null 校验 |
| 数据丢失 | 事务边界错误 |
| 静默失败 | catch 后吞掉异常 |
| 超时无响应 | 没设超时与降级 |
| 错误难查 | 日志无上下文 |

## 2. 异常优于错误码

### 2.1 对比

| 维度 | 错误码 | 异常 |
|------|:---:|:---:|
| 可读性 | 调用方必须检查 | 天然传播 |
| 遗漏风险 | 忘检查 = 静默失败 | 忘捕获 = 明显失败 |
| 上下文 | 无 | 可携带栈与消息 |
| 类型安全 | 弱 | 强（异常类型） |
| **2026 结论** | 遗留风格 | **现代标准** |

### 2.2 正确姿势

```java
// ❌ 错误码风格（调用方必须记得检查）
public int saveOrder(Order order) {
    if (order == null) return -1;          // -1 是什么？
    if (!validate(order)) return -2;       // -2 是什么？
    orderRepository.save(order);
    return 0;
}
// 调用方：int code = saveOrder(o); if (code != 0) { ... }  // 漏检查就静默失败

// ✅ 异常风格（失败不可忽略）
public void saveOrder(Order order) {
    if (order == null) throw new IllegalArgumentException("订单不能为 null");
    if (!validate(order)) throw new InvalidOrderException(order.getId());
    orderRepository.save(order);
}
```

### 2.3 异常习惯三规

```text
异常处理三规
├── ① 只在真正异常时用异常（不要用异常做流程控制）
├── ② 永不吞异常（catch 后至少要打日志）
└── ③ 边界转换异常（跨层转成有意义的上层异常，保留 cause）
```

```java
// ❌ 吞异常（最坏的坏习惯）
try {
    paymentGateway.charge(order);
} catch (Exception e) {
    // 什么都不做 —— 用户被扣了钱但订单还是未支付状态
}

// ✅ 处理异常（至少：日志 + 明确失败方式）
try {
    paymentGateway.charge(order);
} catch (PaymentException e) {
    log.error("支付失败，订单 {} 已标记失败", order.getId(), e);
    order.markPaymentFailed(e.getReason());
    throw new OrderProcessingException("订单支付失败", e);  // 向上抛出，保留 cause
}
```

## 3. 永不返回 null

### 3.1 为什么

> ⚠️ **null 是十亿美元的错误**（Tony Hoare 自述）——null 没有语义、不可验证、处处引爆空指针。好习惯：**用类型表达「可能不存在」**。

### 3.2 替代方案

```java
// ❌ 返回 null（调用方要记得判空，忘了就 NPE）
public Order findOrder(String id) { ... return null; }

// ✅ Optional（类型明确表达"可能不存在"）
public Optional<Order> findOrder(String id) { ... return Optional.empty(); }
// 调用方被迫处理不存在的情况
Order order = findOrder(id)
        .orElseThrow(() -> new OrderNotFoundException(id));

// ✅ 空对象模式（有默认行为的场景）
public Price getPrice() { return Price.ZERO; }   // 而不是 null

// ✅ 失败即异常（调用方无法忽略）
public Order getOrderOrThrow(String id) { ... throw new OrderNotFoundException(id); }
```

### 3.3 参数校验习惯（防御式输入）

```java
// 公共方法入口统一校验（fail-fast）
public void createOrder(CreateOrderCommand command) {
    Objects.requireNonNull(command, "创建订单命令不能为 null");
    if (command.getAmount() == null || command.getAmount() <= 0) {
        throw new InvalidOrderException("金额必须为正数");
    }
    ...
}
```

> 🎯 **统一规则**：**公共方法入口必须校验参数**（fail-fast），私有方法信任调用方。库函数级校验用 `Objects.requireNonNull`/断言，业务级用领域异常。

## 4. 错误信息与异常设计

### 4.1 错误信息四要素

```text
好错误信息 = 什么错了 + 哪个对象 + 期望什么 + 建议动作
├── ❌ "处理失败"（什么错了？）
├── ❌ "订单错误"（哪个订单？）
└── ✅ "订单 ORD-1001 退款失败：余额不足（当前余额 0.00 元），
         请充值后重试或联系客服"
```

### 4.2 异常体系设计

```java
// 领域异常体系（业务错误可识别、可映射）
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(String orderId) {
        super("订单不存在: " + orderId);
    }
}

public class InvalidOrderException extends RuntimeException {
    private final String orderId;          // 结构化上下文（可编程处理）
    public InvalidOrderException(String orderId, String reason) {
        super("订单校验失败 [" + orderId + "]: " + reason);
        this.orderId = orderId;
    }
}

// 全局异常映射（Web 层统一转 HTTP 状态码）
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ErrorBody> handleNotFound(OrderNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ErrorBody("ORDER_NOT_FOUND", e.getMessage()));
    }
}
```

### 4.3 异常粒度习惯

```text
异常粒度决策
├── 业务异常（订单/支付/库存）：领域异常类，全局映射
├── 技术异常（连接/超时）：包装后抛出，保留 cause
├── 框架异常：在边界转换为业务可见错误
└── 注意：不要为每个方法建异常类（异常类数量 = 维护成本）
```

## 5. 边界与防御性编程

### 5.1 五类必查边界

| 边界 | 问题 | 检查习惯 |
|------|------|---------|
| **数值边界** | 负数/零/溢出/超大 | 金额正数、分页 size 上限 |
| **字符串边界** | 空串/超长/特殊字符 | 长度限制、trim、校验 |
| **集合边界** | 空集合/超大集合 | isEmpty 检查、批处理 |
| **时间边界** | 空时间/未来时间/时区 | 必填校验、UTC 统一 |
| **并发边界** | 重复提交/超时 | 幂等键、超时设置 |

### 5.2 防御性编程要点

```java
// ① 幂等：重复调用无副作用（防重试/重复提交）
public void refund(String orderId, String requestId) {
    String dedupKey = "refund:" + orderId + ":" + requestId;
    if (redis.setIfAbsent(dedupKey, "1", Duration.ofMinutes(30))) {
        doRefund(orderId);       // 首次执行
    } else {
        log.info("重复退款请求已拦截: {}", requestId);
    }
}

// ② 超时：外部调用必须有超时（防无限等待）
paymentGateway.charge(order, Duration.ofSeconds(10));

// ③ 降级：下游失败时提供降级路径（缓存/默认值/拒绝）
```

### 5.3 「信任边界」习惯

```text
防御性编程的信任边界
├── 不可信：用户输入/外部 API/网络数据 → 全部校验
├── 半可信：内部服务调用 → 超时+重试+降级
├── 可信：自己库内数据 → 断言/契约
└── 原则：信任边界内少防御（代码清爽），边界外全防御（稳定安全）
```

## 6. 日志习惯

### 6.1 日志五原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **分级正确** | ERROR 真错误 / WARN 可恢复 / INFO 关键节点 / DEBUG 细节 |
| 2 | **带上下文** | 日志必须含业务标识（orderId/traceId/userId） |
| 3 | **带异常栈** | 打异常永远传 e（别只打 e.getMessage()） |
| 4 | **禁止敏感** | 密钥/手机号/身份证脱敏 |
| 5 | **关键节点必打** | 事务开始/结束/失败/外部调用 |

### 6.2 日志模板

```java
// ✅ 好日志：可查询、可关联、可定位
log.info("订单创建成功: orderId={}, amount={}, traceId={}",
         order.getId(), order.getAmount(), traceId);

// ❌ 坏日志：无法关联业务
log.info("success");                    // 谁的 success？
log.info("订单: " + order);             // toString 可能泄露敏感字段
```

> 🎯 **日志即排障基础设施**：生产问题定位速度 = 日志质量的直接函数——每条日志都要能回答「哪个业务对象、在哪个环节、发生了什么」。

## 7. 安全编码习惯

| # | 习惯 | 示例 |
|---|------|------|
| 1 | **输入校验防注入** | 参数化查询，禁止字符串拼接 SQL |
| 2 | **密钥永不硬编码** | 配置文件/密钥管理服务，禁止 `password=123456` 进代码 |
| 3 | **最小权限** | 数据库账号按需授权（只读/写分离） |
| 4 | **敏感数据脱敏** | 日志/响应中的手机号、身份证打码 |
| 5 | **依赖漏洞扫描** | CI 中 SCA 扫描（OWASP Dependency-Check） |
| 6 | **HTTPS/加密存储** | 传输与存储加密（密码 BCrypt） |

> ⚠️ **2026 补充**：AI 生成代码的默认值往往不安全（AI 倾向硬编码密钥/不校验输入）——**安全习惯从「自觉」变成「审查 AI 输出的固定检查项」**（详见 06 篇）。

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 悲观心态：先想「这行失败了会怎样」——错误路径也是你写的代码
> 2. 异常优于错误码；永不吞异常（catch 至少打日志）；永不返回 null（Optional/异常/空对象）
> 3. 好错误信息 = 什么错 + 哪个对象 + 期望 + 建议；公共方法入口 fail-fast 校验
> 4. 信任边界防御：边界外全校验、外部调用必超时必降级、重复请求必幂等
> 5. 日志五原则（带上下文/带异常栈/禁敏感）+ 安全六习惯——AI 时代这些成为审查 AI 输出的固定项
