## 1. 面试高频题与答题框架

### 1.1 命名与结构类

**Q1：你认为好代码的标准是什么？**

```text
答题框架：
① 可读性 > 炫技（代码阅读:编写 = 10:1）
② 可维护性：改需求成本低（结构/命名/职责清晰）
③ 可测试性：有测试证明行为
④ 可演进性：不过度设计（YAGNI）
⑤ 金句：写能工作的代码容易，写能活过真实世界的代码难
⑥ 加分：2026 视角——AI 时代纪律更重要
```

**Q2：DRY、KISS、YAGNI 怎么平衡？**

```text
① DRY：三处重复才抽象（两处是巧合，三处是模式）
② KISS：简单优先，每层抽象都是理解成本
③ YAGNI：不为预测需求设计（需求出现时你才真正理解）
④ 平衡：抽象服务于「实际出现的重复与变化」，
   不服务于「想象中的未来」
```

**Q3：函数设计有什么原则？**

```text
① 单一职责（一个函数一件事）
② 短小（<20 行理想）
③ 单层抽象（函数内同一抽象层级）
④ 少参数（≤3，多了封装对象）
⑤ 无副作用（不悄悄改全局状态）
```

### 1.2 注释与可读性类

**Q4：注释应该怎么写？**

```text
① 黄金法则：解释 Why 不解释 What（代码说明是什么）
② 五原则：Why/警告与后果/TODO 署名+日期/公共 API Javadoc/随代码更新
③ 自文档化优先：好名字 + 清晰结构 > 注释
④ 铁律：永不注释掉代码（Git 可恢复；注释代码会误导 AI）
⑤ 判断：需要注释才能看懂 → 先重构而非先写注释
```

### 1.3 错误处理类

**Q5：异常处理有什么好习惯？**

```text
① 异常优于错误码（不可忽略、可传播、带上下文）
② 永不吞异常（catch 至少打日志）
③ 永不返回 null（Optional/异常/空对象表达"可能不存在"）
④ 好错误信息四要素：什么错+哪个对象+期望+建议
⑤ 跨层转换异常保留 cause
```

**Q6：防御性编程怎么做？**

```text
① 悲观心态：假设一切会出错，先想失败方式
② 边界五查：数值/字符串/集合/时间/并发
③ 信任边界：外部输入全校验、外部调用必超时必降级、重复请求幂等
④ 公共方法入口 fail-fast 校验
```

### 1.4 测试类

**Q7：什么是 F.I.R.S.T 原则？**

```text
Fast 快速 / Independent 独立 / Repeatable 可重复 /
Self-validating 自我验证 / Timely 及时
→ 违例信号：单测访问数据库/测试有顺序/依赖环境
```

**Q8：讲讲你的 TDD（红绿重构）实践？**

```text
① 循环：Red（写失败测试）→ Green（最小实现）→ Refactor（清理）
② 价值：设计驱动/需求确认/安全网/天然 YAGNI
③ 加分：实际案例（如用 TDD 实现 xx 功能，测试先行解决了 xx 问题）
④ 2026 延伸：AI 修 bug 前先写复现测试（Karpathy 原则）
```

**Q9：覆盖率多少合适？**

```text
① 覆盖率是必要不充分：护栏不是目标
② 实践：核心模块门禁 80%+，新代码必须有测试
③ 覆盖率看不出：边界条件/错误路径/行为错误
④ 2026 延伸：覆盖率门禁是行为护栏——防 AI 弱化测试
```

### 1.5 Git 与审查类

**Q10：好 Git 提交有什么标准？**

```text
① 一个提交 = 一个逻辑变更
② Conventional Commits 规范（feat/fix/refactor/docs...）
③ 提交信息：做了什么 + 为什么 + 怎么验证
④ 每个提交可编译可测试（bisect 友好）
⑤ Git 历史 = 团队知识资产
```

**Q11：代码审查怎么看？**

```text
① 提交方：小 PR（<400 行）、有描述、带测试、自审过、CI 绿
② 审查方：及时/对事不对人/分严重度（P0/P1/P2）
③ 六查清单：正确性/可读性/健壮性/安全/测试/性能
④ 2026：AI 代码审查六重点（幻觉/夹带/风格/边界/安全/回归）
```

### 1.6 AI 时代类（2026 高频新增）

**Q12：AI 时代写代码的好习惯有什么变化？**

```text
① 核心论断：纪律更重要而非更少（84% 用 AI / 29% 信任）
② AI 代码必须审查（像审查新同事）
③ Karpathy 六原则：先想后写/简单优先/外科手术/目标驱动/先复现再修/沟通权衡
④ 空白画布陷阱：人搭骨架，AI 填充
⑤ 质量门禁自动化：机器守门、人守要害
```

**Q13：怎么让 AI 生成的代码质量更高？**

```text
① 约束五件套：AGENTS.md/严格类型/示例引用/计划模式/成功标准
② 成功标准 > 操作指令（"给它成功标准，看它执行"）
③ 明确测试要求：AI 默认只测快乐路径——显式要求边界+异常
④ 三道门禁：生成时检查/Pre-commit/PR 全绿
⑤ 金句：给 AI 成功标准而非操作指令
```

**Q14：你踩过什么编码习惯的坑？怎么改的？（行为题）**

```text
STAR 结构 + 真实案例：
S：xx 项目出现 xx 事故（如生产空指针/重复退款）
T：定位根因（未校验/未幂等/吞异常）
A：建立习惯（fail-fast 校验/幂等键/日志上下文/测试补全）
R：事故率下降 xx，沉淀为团队规范
→ 加分：说明习惯是「事故 + 复盘」沉淀出来的，不是背出来的
```

## 2. 习惯自检清单

```text
日常编码自检（提交前快速过一遍）
[ ] 命名：名字说明意图了吗？（不需要注释解释的名字）
[ ] 函数：单一职责？<20 行？无副作用？
[ ] 重复：有 3 处以上重复吗？（有就抽象）
[ ] 错误：异常处理了吗？没吞异常？错误信息有上下文？
[ ] 边界：空值/超长/负值/超时/重复请求检查了吗？
[ ] 安全：没有硬编码密钥？输入校验了吗？
[ ] 测试：核心场景有测试？边界与异常场景测了吗？
[ ] 日志：关键节点有日志？带业务上下文？无敏感信息？
[ ] Git：一个提交一个逻辑？信息规范？可编译？
[ ] 审查：自己先过一遍 diff？夹带改动检查了吗？
```

## 3. 五大常见误区

| # | 误区 | 真相 |
|---|------|------|
| 1 | 「代码能跑就行，习惯是加分项」 | 习惯决定维护成本——能跑只是起点 |
| 2 | 「注释越多越好」 | 注释讲 Why 不讲 What；注释掉的代码是谎言 |
| 3 | 「覆盖率 100% = 质量好」 | 覆盖率是护栏不是目标；边界与行为断言更重要 |
| 4 | 「AI 写的代码可以直接用」 | 84% 用 AI 但仅 29% 信任——审查是铁律 |
| 5 | 「习惯靠自觉就能养成」 | 格式化/Lint/门禁交给工具强制——机器守门人守要害 |

## 4. 30 天习惯养成路线

| 阶段 | 时间 | 目标 | 检验标准 |
|------|------|------|---------|
| **觉醒** | 1-7 天 | 审查自己的代码 | 用自检清单过完自己最近 1 个模块 |
| **改造** | 8-14 天 | 重构坏味道 | 删除注释掉的代码/魔法数字→常量/拆分长函数 |
| **巩固** | 15-21 天 | 测试 + Git 习惯 | 新代码全部带测试；提交规范统一 |
| **AI 化** | 22-30 天 | AI 协作习惯 | AGENTS.md 落地 + 三道门禁 + AI 输出全审查 |

> 🎯 养成秘诀：**习惯不是「知道」出来的，是「复盘的错误」长出来的**——每次事故都对应一条习惯，把习惯写进清单，让清单进 CI。

## 5. 一句话总结全系列

```text
01 命名结构：代码是给人读的——命名即文档，函数单职责
02 注释可读：注释讲 Why 不讲 What，永不注释掉代码
03 错误处理：悲观心态 + 异常优于错误码 + 永不返回 null
04 测试驱动：F.I.R.S.T + 红绿重构 + 覆盖率护栏
05 Git 审查：一提交一逻辑 + 规范信息 + PR 六查
06 AI 时代：纪律更重要——审查 AI 代码 + Karpathy 六原则 + 门禁自动化
07 面试：14 题框架 + 自检清单 + 30 天养成路线
```

> 🎯 **系列总结**：写代码的好习惯 = 一套「**让代码活过真实世界**」的工程纪律：命名与结构让它可读，错误处理让它健壮，测试让它可信，Git 与审查让它可演进，AI 时代的门禁让它可持续。2026 年的新命题是：**好习惯不再只是人的自觉，而是「人定义标准 + 机器执行门禁 + AI 在约束中产出」的工程体系**——掌握这套体系，你就掌握了 AI 时代最稀缺的能力：让代码（无论谁写的）保持高质量。
