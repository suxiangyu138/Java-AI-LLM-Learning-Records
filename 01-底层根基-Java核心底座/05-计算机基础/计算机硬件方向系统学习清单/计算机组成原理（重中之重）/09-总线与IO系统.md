# 09 总线与 IO 系统

## 1. 总线系统

总线 = 一组共享的传输线（数据线 + 地址线 + 控制线），连接 CPU、内存与外设：

```text
现代三层总线结构：
CPU 内部总线 → 内存总线（连接主存）
             → I/O 总线（PCIe，连接外设与扩展卡）
```

| 总线 | 2026 基线 | 带宽示例 |
|---|---|---|
| 内存总线 | DDR5 双通道 | ~70-100 GB/s |
| I/O 总线 | PCIe 6.0（64 GT/s） | x16 ≈ 256 GB/s |
| CPU 互连 | UPI/CCX 类 | 多路 CPU 间通信 |

总线性能 = 宽度 × 频率（每周期传输位数 × 每秒周期数）。PCIe 的演进：6.0 用 PAM4 信号（每符号 2 比特）把速率从 32 推到 64 GT/s——2026 年 PCIe 6.0 成为服务器标配，CXL 3.2 就建立在它之上。

## 2. 总线仲裁

多个设备同时请求总线时必须仲裁，两种策略：

| 策略 | 机制 | 特点 |
|---|---|---|
| 集中式 | 总线控制器统一裁决 | 简单；控制器是单点 |
| 分布式 | 设备自行协商（菊花链/自举） | 无单点；延迟略高 |

仲裁算法按优先级：**链式查询**（固定优先级，靠近控制器的优先）、**计数器定时查询**（公平轮转）、**独立请求**（可编程优先级）。现代 PCIe 用集中式仲裁（根复合体 RC 统一管理），NVMe SSD 与 GPU 通过仲裁共享带宽。

> 💡 考点的理解锚点：仲裁的本质是"**多对一的资源分配**"——和操作系统里的互斥锁、消息队列的消费分配是同一个问题在不同层次的映射。理解这个抽象，总线仲裁就记住了。

## 3. IO 的三种方式

| 方式 | 谁控制传输 | CPU 参与度 | 适用 |
|---|---|---|---|
| 程序查询 | CPU | 忙等轮询（占 CPU） | 低速简单设备 |
| 中断 | CPU（被通知） | 响应中断处理 | 中速设备（键盘/网卡） |
| DMA | DMA 控制器 | 发起后放手 | 高速批量（磁盘/GPU） |

三种方式的演进主线：**把 CPU 从"搬运工"逐步解放为"管理者"**。程序查询让 CPU 空转等待；中断让 CPU 只在数据就绪时介入；DMA 让数据在内存与设备间直通，CPU 只负责开始与结束。现代高速 IO 全部走 DMA。

## 4. 中断系统

中断是"设备主动找 CPU"的机制，完整流程：

```text
① 设备发中断请求（INTR）
② CPU 响应条件：指令结束 + 开中断（IF=1）
③ 保护现场：PC/寄存器压栈
④ 中断向量查表 → 转中断服务程序
⑤ 处理（读设备数据等）
⑥ 恢复现场 → 返回断点（IRET）
```

| 概念 | 说明 |
|---|---|
| 中断向量 | 中断号 → 服务程序入口的表项 |
| 中断优先级 | 可屏蔽（IF 控制）/不可屏蔽 NMI（故障） |
| 多重中断 | 高优先级可打断低优先级（嵌套） |
| 中断 vs 异常 | 中断外部异步；异常内部同步（缺页/除零/系统调用） |

中断对现代系统的意义远超 IO：**操作系统的一切事件驱动（时钟、调度、系统调用、缺页）都建立在中断/异常机制上**——没有中断就没有多任务操作系统。Java 视角：`interrupt()` 与硬件中断同名但机制不同，理解硬件中断有助于理解"响应式"的根源。

## 5. DMA 与通道

DMA（直接存储器访问）是高速 IO 的标准：

```text
① CPU 初始化 DMA：源地址、目的地址、字节数、方向
② DMA 控制器接管：内存 ↔ 设备直传（不经过 CPU）
③ 每传一个块，DMA 与 CPU 竞争内存总线（周期挪用）
④ 传输完成 → DMA 发中断通知 CPU
```

| 维度 | 程序查询 | 中断 | DMA |
|---|---|---|---|
| 每字节 CPU 开销 | 高（轮询/搬运） | 中（中断处理） | 低（仅初始化） |
| 传输粒度 | 字 | 字/块 | 块 |
| 磁盘/网络传输 | 不可用 | 勉强 | **标准** |

通道是 DMA 的进化：独立的 IO 处理器（有自己的指令系统），可执行复杂的 IO 程序——大型机时代的产物，现代被"智能设备控制器 + DMA"取代（NVMe 控制器内嵌处理器）。现代存储路径：**NVMe SSD 通过 PCIe DMA 直传数据，CPU 只做命令提交与完成回收**——这就是"高 IOPS 不烧 CPU"的硬件基础。

### 5.1 IO 方式的软件映射

三种 IO 方式在软件层有精确的对应物：程序查询 = 轮询（Java 的忙等自旋、传统阻塞读）、中断 = 事件驱动（Netty 的 selector 事件循环、Reactor 模型）、DMA = 零拷贝（Netty/Java NIO 的 DirectBuffer + transferTo，数据在内存与网卡间直传不经过用户态）——Netty 为什么快？因为它把"中断 + DMA"的硬件模式搬到了软件层：事件驱动（中断思想）+ 零拷贝（DMA 思想）。理解硬件 IO 的演进 = 理解高性能 IO 框架的设计动机。这也是"组成原理对 Java 后端"最直接的一课：高性能的答案早就写在硬件里。

补充一个实践视角：**IO 方式的选择本质是"CPU 时间 vs 延迟"的权衡**——程序查询省硬件但烧 CPU（适合极简嵌入式）、中断省 CPU 但引入上下文切换开销（适合中速设备）、DMA 省 CPU 但需要 DMA 控制器资源（适合高速批量）；Java 的 NIO 选型（同步阻塞 vs 非阻塞 vs 异步）是同一权衡的软件形态。

### 5.2 IO 栈的完整链路

现代一次网络读写的完整 IO 栈：应用（Java NIO）→ 内核（socket 缓冲）→ 网卡 DMA（数据直达内核缓冲）→ PCIe 总线 → 内存。高性能框架的优化全部发生在这条链上：零拷贝减少"内核↔用户"的复制（transferTo）、直接内存减少堆内复制（DirectBuffer）、多路复用减少中断次数（epoll 的事件批量通知）——**看懂这条链，就懂了 Netty 全部性能优化的动机**，这也是"IO 系统"章节对后端工程师的最高价值。

## 6. 常见误区速排

| 误区 | 事实 |
|---|---|
| "中断让 CPU 更忙" | 中断比轮询省 CPU（无事不打扰），忙的是响应处理 |
| "DMA 不需要 CPU" | 初始化与完成通知仍要 CPU，直传阶段才放手 |
| "总线是根大水管" | 总线是共享资源，仲裁与带宽分配决定实际吞吐 |
| "PCIe 只是显卡接口" | PCIe 是通用 IO 总线，SSD/NIC/CXL 全走它 |

## 7. 本模块小结


> 🎯 **核心要点**：总线 = 共享传输线 + 仲裁（集中式是现代标准）；IO 三方式 = CPU 逐步解放（查询→中断→DMA），高速设备全走 DMA + 中断通知；中断是操作系统的地基（时钟/调度/缺页全依赖它）；2026 锚点：PCIe 6.0（64 GT/s）成为总线基线、CXL 3.2 建立在它之上、NVMe 通过 DMA 直传实现高 IOPS 低 CPU 占用。Java 视角：理解中断与 DMA 才能真懂 NIO 的"非阻塞"与 Netty 的"零拷贝"为什么快。
