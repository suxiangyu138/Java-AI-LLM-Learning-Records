# 05 高速缓存 Cache

## 1. Cache 的工作原理

Cache 是主存与 CPU 之间的小容量高速缓存（SRAM，静态存储、无需刷新、快但贵），按块（Cache line，通常 64 字节）与主存交换数据：

```text
CPU 访问地址 → 查 Cache（命中：纳秒级返回）
             → 未命中：整块载入主存数据（几十上百周期）
平均访问时间 = 命中率 × 命中时间 + 未命中率 × 未命中代价
```

三个设计参数决定 Cache 的一切行为：**块大小**（大→空间局部性收益高但块内浪费）、**容量**（大→命中率高但贵且慢）、**相联度**（映射灵活性）。经典考题"块大小翻倍对命中率的影响"：开始上升（空间局部性）、之后下降（块内无用数据挤占容量）——存在最优块大小。

## 2. 三种映射方式

| 映射 | 规则 | 冲突 | 硬件成本 |
|---|---|---|---|
| 直接映射 | 主存块号 % Cache 块数 | 严重（同一位置互斥） | 最低 |
| 全相联 | 任意块可放任意位置 | 无冲突（需全比较） | 最高（比较器多） |
| 组相联 | 分组成组直接映射、组内全相联 | 折中 | 折中 |

组相联是现代 CPU 的标准选择：**8-16 路组相联**是 L1 的常见配置，L2/L3 相联度更高。理解映射的核心是"地址如何拆分成标记/组号/块内偏移"：

```text
组相联地址 = [标记 tag | 组号 index | 块内偏移 offset]
命中判定 = tag 相等 + 有效位为 1
```

相联度与命中率的关系：从直接映射升到 2 路就能回收大部分冲突未命中，4-8 路后收益递减——这是"相联度提升的边际效益递减"规律，也是为什么现代 CPU 用 8-16 路而不是全相联。

## 3. 替换算法

组满时需要替换，经典算法与效果：

| 算法 | 策略 | 硬件实现 |
|---|---|---|
| LRU（最近最少使用） | 替换最久未使用的块 | 近似实现（NRU 位/伪 LRU），全 LRU 太贵 |
| FIFO | 先进先出 | 简单但有抖动（刚调入的块可能马上被踢） |
| 随机 | 随机替换 | 极简，实际表现不差（现代 CPU 部分采用） |
| 最优 OPT | 替换未来最远使用的 | 理论下界，不可实现（仅用于评测） |

> 💡 考点理解：LRU 是"预测未来最不常用"的启发式，基于时间局部性假设——近期未用的将来也少用。实际硬件用近似实现，因为真 LRU 的计数器电路在 8 路以上成本失控。

## 4. 写策略

写操作的策略分两个维度：

| 维度 | 选项 | 说明 |
|---|---|---|
| 写命中 | 写直达（write-through）：立即写主存 | 简单，但每写都占内存带宽 |
| 写命中 | 写回（write-back）：只写 Cache，脏位标记 | 快，但需脏块回写逻辑 |
| 写未命中 | 写分配（fetch-on-write）：先载入再写 | 配合写回 |
| 写未命中 | 非写分配（no-write-allocate）：只写主存 | 配合写直达 |

现代 CPU 的主流组合：**写回 + 写分配**（L1/L2 内部），写直达用于需要强一致的场景（如某些 uncached 区域）。写回引入"脏块"概念：块被替换时必须先回写主存——这是"替换成本"的另一面。

## 5. 多级 Cache 与一致性

现代 CPU 的 Cache 是三级结构，各有分工：

```text
L1（指令/数据分离）≈ 1ns，几十 KB，8-16 路
L2 统一 ≈ 几 ns，几百 KB-MB
L3（多核共享）≈ 十几 ns，几十 MB
```

一致性问题是多核时代的核心：**一个核写了数据，其他核的 Cache 里旧副本怎么办**？硬件用缓存一致性协议解决（MESI 等，基于状态位：修改/独占/共享/无效）：

| 协议机制 | 说明 |
|---|---|
| MESI 状态 | 每块带 4 状态，写操作广播无效化其他核副本 |
| 写无效 vs 写更新 | 现代用写无效（无效化比广播新数据省带宽） |
| 伪共享 | 不同核改同一 Cache 行不同字节 → 无效化风暴（Java 面试高频） |

> 💡 伪共享是软件能直接踩的一致性坑：两个线程各改自己字段，但字段在同一 64 字节 Cache 行 → 互相无效化 → 性能雪崩。Java 解法：`@Contended` 注解、padding 对齐——组成原理直接指导 Java 并发性能优化。

### 5.1 Cache 思维在软件层的复制

Cache 的三机制（映射/替换/写策略）在软件缓存中被完整复制：哈希表 = 直接映射（冲突靠链表解决 = 相联度）、LRU 替换 = 缓存淘汰、写回/写直达 = 脏标记/同步写——Redis 的 LRU 淘汰、JVM 的 CMS/G1 卡表、数据库缓冲池全部是 Cache 思想的工程化。一个实用技巧：**用 Cache 心智分析软件性能问题**——"慢"先问"命中了吗"（数据在不在热层）、"为什么没命中"（容量/冲突/失效），这个诊断框架在硬件与软件层同样有效。Java 工程师理解 Cache，等于拿到一把通用的性能诊断钥匙。

补充一个诊断技巧：**"数组慢还是链表慢"要按数据规模回答**——小规模（几十个元素）两者差异可忽略（全在 Cache 行内），大规模才显现数量级差异；同样的道理适用于一切"数据结构选型"讨论，面试时给出规模分界点比直接背结论更有说服力。

## 6. 常见误区速排

| 误区 | 事实 |
|---|---|
| "Cache 越大越好" | 大→慢→贵，L1 几十 KB 是速度的必然 |
| "全相联最好" | 比较器成本爆炸，组相联 8-16 路是工程折中 |
| "写直达更安全" | 现代主流是写回+写分配，一致性靠 MESI 协议 |
| "伪共享是 CPU 的 bug" | 是软件数据布局与 Cache 行冲突的交互，可 @Contended 解 |

## 7. 本模块小结


> 🎯 **核心要点**：Cache 设计 = 三参数（块大小/容量/相联度）× 三机制（映射/替换/写策略）。组相联是现代标准（8-16 路），写回+写分配是主流组合，LRU 用近似实现。多核时代的一致性（MESI）与伪共享把 Cache 从"性能话题"升级为"正确性话题"。2026 锚点：AI 工作负载（大模型权重流式访问）对 Cache 是全新挑战，CXL 缓存一致性扩展把一致性范围延伸到系统级。深潜见"缓存与Cache"体系（8 篇）。
