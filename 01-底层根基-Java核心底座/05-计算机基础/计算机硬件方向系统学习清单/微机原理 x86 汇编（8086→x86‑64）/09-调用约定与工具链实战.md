# 调用约定与工具链实战
> ABI 规定函数如何互相调用，工具链决定你如何书写与观察汇编——SysV 与 Windows 两大约定、NASM 3.02 实战、objdump/gdb 反汇编调试，是现代汇编学习的落地三件套。

## 1. 为什么需要调用约定

两个函数（可能由不同编译器、不同语言生成）要互相调用，必须就"参数放哪、返回值放哪、谁负责保存寄存器、栈如何对齐"达成一致——这套规则就是调用约定（calling convention），是 ABI（应用二进制接口）的核心。没有它，C 调汇编、库与程序互调全都无法工作；有了它，"调用"就变成了纯机械的寄存器/栈操作——这正是 05 篇"参数传递四种方式"在现代的标准化形态。约定还决定可移植性：换一个 ABI，同一个二进制可能直接崩溃或数据错位——所以 ABI 一经发布几乎永不更改。

## 2. System V AMD64 ABI（Linux/macOS/BSD）

Unix 系的标准约定，规则清晰：

- **参数**：前 6 个整数/指针参数依次放 RDI、RSI、RDX、RCX、R8、R9；浮点参数放 XMM0-XMM7；第 7 个起压栈（从右向左）
- **返回值**：整数/指针在 RAX（128 位用 RDX:RAX 拼），浮点在 XMM0
- **寄存器归属**：易失（调用者保存）——RAX/RCX/RDX/RSI/RDI/R8-R11/XMM0-15；非易失（被调用者保存）——RBX/RBP/R12-R15，被调函数若使用必须 PUSH/POP 保护
- **栈**：call 指令执行前 RSP 须 16 字节对齐；**红区（red zone）**——RSP 下方 128 字节区域，叶函数（不再调用其他函数的函数）可以不经 RSP 调整直接使用，省掉 SUB RSP 指令；但内核代码必须 -mno-red-zone（中断会践踏红区）

一个典型函数序言：PUSH RBP / MOV RBP, RSP / SUB RSP, N——"建立栈帧"，与 8086 时代的 PUSH BP/MOV BP, SP 完全同构。

## 3. Windows x64 约定

Microsoft 的约定：前 4 个参数 RCX、RDX、R8、R9 + 32 字节 shadow space（调用者为被调方预留的"影子空间"，被调方可直接使用）；非易失寄存器 RBX/RBP/RSI/RDI/R12-R15；**没有红区**；栈 16 字节对齐。与 SysV 的差异是跨平台移植（Linux↔Windows）汇编与 C 互操作时最常见的坑：参数寄存器不同、易失集合不同、多 32 字节栈开销。还有一个移植细节：Windows x64 的易失寄存器包含 RDI/RSI（SysV 中它们是参数寄存器）——因为 Windows 用 RCX/RDX/R8/R9 传参，RDI/RSI 被解放成普通寄存器，编译器可以自由使用。记住一句话：**Linux 用 RDI 传第一个参数，Windows 用 RCX——同样的 C 函数，两份不同的汇编**。

## 4. C 与汇编互操作

汇编函数服务 C 调用的完整流程（遵守 SysV）：保存非易失寄存器 → 按参数顺序取参 → 处理 → 结果放 RAX → 恢复寄存器 → RET。C 侧只需声明外部函数原型（int add_int(int, int)）即可调用。符号名：SysV 不加前导下划线（Linux 上 add_int 就是 add_int），传统 32 位才加。一个完整例子：

```asm
; add_int.asm — int add_int(int a, int b) 返回 a+b
section .text
global add_int
add_int:
    mov eax, edi      ; 第一个参数在 edi
    add eax, esi      ; 第二个参数在 esi
    ret
```

C 侧 printf("%d", add_int(3, 5)) 编译链接即可运行——这是验证 ABI 理解最直接的实验。

## 5. 工具链实战：NASM 3.02

NASM（Netwide Assembler）是 2026 年 x86 汇编的事实标准，最新稳定版 3.02（2026-06-29 发布，2-clause BSD 许可）。工作流：nasm -f elf64 -o hello.o hello.asm（汇编成 64 位 ELF 目标文件；加 -g -F dwarf 生成调试信息）→ ld 或 gcc 链接 → 运行。NASM 用 Intel 语法（目的在前）：MOV RAX, 5。Linux 世界的另一种语法是 AT&T（GAS 默认，源在前）：MOVQ $5, %RAX——两者差异（立即数 $ 前缀、寄存器 % 前缀、内存操作数大小后缀）是阅读 Linux 内核汇编的拦路虎，建议至少能互译。

## 6. 反汇编与调试

**objdump**：objdump -d -M intel hello 以 Intel 语法反汇编（-M intel 是反汇编的默认姿势）；readelf -h/-S 看 ELF 头与节表；size 看各节大小。**gdb**：layout regs 实时寄存器窗口、si 单步执行一条指令、info registers、x/s $rsi 查看寄存器指向的字符串、disassemble 反汇编当前函数。反汇编的三大用途：读懂编译器输出（gcc -O2 -S 生成的汇编 + objdump 对照）、安全分析（CVE 补丁 diff、恶意软件分析——ROP gadget 查找是经典场景）、性能调优（perf top 看热点函数后反汇编定位）。现代逆向工具（Ghidra/IDA）的底层引擎同样建立在 objdump 式的反汇编之上。

## 7. 性能与可读性规范

现代场景里手写汇编的合理位置：SIMD 热点（视频编解码、加密）、启动代码、内核关键路径、编译器验证。99% 的代码应该让编译器生成汇编——但要学会"读"：gcc -O2 -S 输出、objdump 对照、用 perf 定位热点后检查生成代码是否合理。2026 年的实践标准：先写 C 并测量，热点用 intrinsics（C 层 SIMD 函数），最后才考虑内联汇编——手写汇编的收益大多来自"寄存器分配与指令选择"，而这些正是编译器最擅长的事。

## 8. 实战走读：编译器生成的汇编

把"读汇编"练成肌肉记忆的最好方法是走读编译器输出。用 gcc -O2 -S swap.c 编译：

```c
void swap(int *a, int *b) {
    int t = *a;
    *a = *b;
    *b = t;
}
```

生成的汇编只有四条指令：

```asm
mov  eax, DWORD PTR [rdi]   ; t = *a（t 不进内存，直接住寄存器）
mov  edx, DWORD PTR [rsi]   ; 读 *b
mov  DWORD PTR [rdi], edx   ; *a = *b
mov  DWORD PTR [rsi], eax   ; *b = t
ret
```

三个观察点：**参数进寄存器**（rdi/rsi 即 SysV 的前两个参数寄存器）；**局部变量 t 被寄存器化**（优化消除了"栈上局部变量"这个概念，8086 时代的 BP 栈帧在 O2 下常常整个消失）；**内存操作数直接参与传送**（MOV 的 mem↔reg 形态在此兑现）。读完这段再回头看 02/03 篇的寻址与 MOV 铁律——编译器就是在这些规则上做自动组合与优化的。进阶练习：打开 Godbolt（Compiler Explorer）输入任意函数，对比 -O0 与 -O2 的汇编差异，这是 2026 年学习"编译器在做什么"成本最低的方式。

> 🎯 **核心要点**：调用约定是"函数之间的宪法"（SysV 六参寄存器 + 红区 vs Windows 四参 + shadow space），工具链是"观察汇编的显微镜"（NASM 写、objdump 反、gdb 调试）；把 8086 学到的指令与寻址放到 64 位 ABI 语境里实战一遍，才算真正完成"从微机原理到现代开发"的落地。
