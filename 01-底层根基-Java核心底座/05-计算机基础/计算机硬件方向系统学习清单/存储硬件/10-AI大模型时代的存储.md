## 1. AI 存储的三个阶段

| 阶段 | IO 模式 | 核心需求 | 代表存储 |
|------|---------|---------|---------|
| 数据准备 | 海量顺序读 + 小文件随机读 | 吞吐、缓存 | 对象存储 + 高速缓存层 |
| 训练 | 大块顺序写（checkpoint）为主 | 带宽、低 P99 | 并行 FS / 本地 NVMe + 异步落盘 |
| 推理 | 低延迟读（权重）+ 高 IOPS（KV cache） | 延迟、IOPS、容量 | HBM→DRAM→CXL→SSD 分层 |

**存储是训练 MFU 的隐形杀手**：GPU 等数据时算力闲置，存储延迟直接折算成 GPU 利用率损失——这正是 2026 年存储被提到战略高度的原因。

## 2. 数据准备与数据集存储

### 2.1 数据形态问题

| 形态 | 例子 | 存储挑战 |
|------|------|---------|
| 海量小文件 | 百万级 JSONL/样本文件 | 小文件 IOPS 爆炸、元数据放大 |
| 大文件 | Parquet 分片（百 MB-数 GB） | 顺序读吞吐、预取 |
| 半结构化 | 图/多模态数据集 | 随机访问模式 |

### 2.2 缓存层方案

```text
对象存储（S3 底座，无限扩展） → 缓存层（本地 NVMe / Alluxio） → 训练节点
```

- **Alluxio**（2026-05 发布 AI 3.9）：POSIX 写缓存 + RDMA 读，单节点 7.6 GiB/s，线性扩展至 20 GiB/s，P99 < 2ms——对象存储之上的"数据热层"。
- 主流组合：JuiceFS（对象存储 + 元数据服务 + 本地缓存）/ CephFS / Lustre 各占一席。
- 训练 dataloader 侧：num_workers 多进程预取 + 内存缓冲，把"读盘"变成"读内存"。

## 3. Checkpoint：训练存储的最大痛点

### 3.1 问题规模

| 模型规模 | 单次 checkpoint 数据量 | 说明 |
|---------|:---:|------|
| 70B 参数 | >250GB | 权重 + 优化器状态 |
| 400B+ 参数 | 数 TB | 优化器状态占大头（Adam 需 2× 权重） |
| 全集群频率 | 每迭代-每小时 | 高频保存防中断 |

**两难**：checkpoint 太频繁 → GPU 等 IO，MFU 暴跌；太少 → 故障恢复损失大。**优化器状态精度压缩（FP8 计算 + FP16 存储）可让 checkpoint 减半。**

### 3.2 2026 解决方案矩阵

| 方案 | 原理 | 效果 |
|------|------|------|
| 异步 checkpoint | 训练进程把数据写本地 NVMe，后台异步上传 | 写延迟从网络级降到本地 NVMe 级 |
| Alluxio POSIX Write Cache | checkpoint 写本地缓存 + 异步持久化对象存储 | 7.6→20 GiB/s 线性扩展 |
| 计算型存储（SmartSSD） | 优化器更新（逐元素运算）卸载到 SSD 内 | 释放 HBM、零开销 checkpoint（SK 海力士 2026） |
| CXL 内存缓冲（JBOC） | 一箱 CXL SSD 做 checkpoint 暂存 | PCIe 级写延迟，免网络 |
| 精度压缩 | FP8 计算 + FP16 状态存储 | 数据量减半 |

> 💡 核心洞察：checkpoint 是"带宽问题"（单次写量大）而非"IOPS 问题"——所以解法围绕**写路径优化**：本地缓冲、异步落盘、计算卸载。

## 4. KV cache 卸载与 GPU 直连

### 4.1 推理的内存困境

- 长上下文 LLM 推理：KV cache 随上下文线性增长，单请求可达数十 GB → HBM 放不下。
- 传统解法：KV cache 溢出 → 换更大 GPU（贵）或丢精度（错）。

### 4.2 2026 架构：存储当内存用

| 层级 | 用途 | 延迟 |
|------|------|------|
| HBM | 活跃 KV cache / 权重 | ~ns |
| DRAM | 次热 KV cache | ~100ns |
| **CXL 内存** | 扩展 KV cache（Meta 实测：服务器数 -25%、缓存延迟 -29%） | ~300ns |
| **NVMe SSD** | 冷 KV cache / 上下文换出（Storage-Next） | ~50μs |

**NVIDIA Storage-Next + CMX**：GPU 绕过 CPU 直连 SSD（GPUDirect Storage 演进），把 KV cache 与模型权重换出到 NVMe——铠侠 CM10 系列明确支持 NVIDIA CMX。

**超高 IOPS SSD 需求**：KV cache 卸载是"小粒度随机 IO + 极高并发"——铠侠 GP1 系列（2026-08）512B 随机读 **1000 万 IOPS**、最高 50 DWPD，配第二代 XL-FLASH（低延迟闪存），目标即此场景。

### 4.3 收益数据

- Meta（ISCA 2026）：CXL 内存扩展 → 分布式推理服务器数量 **-25%**，缓存响应时间 **-29%**。
- 三星 PM1763（Gen6）：40GB LLM 权重加载 **1.4 秒**——模型热更新/换载不再是分钟级。

## 5. 向量数据库与索引存储

| 索引类型 | IO 模式 | 存储需求 |
|---------|---------|---------|
| HNSW | 多级邻接图，随机小读 | 低延迟随机读（NVMe 必须） |
| IVF | 倒排簇 + 顺序扫描簇内 | 顺序读友好 |
| 量化压缩（PQ/SQ） | 压缩向量读取 | 容量效率 |

- 向量库（Milvus/FAISS 等，详见本仓库 `03-AI.../Milvus` 体系）本质是"随机小 IO 高并发"负载——与 KV cache 卸载同一类需求，吃 IOPS 与 P99 延迟。
- 2026 趋势：向量索引 + 原始文档混合存储，索引 SSD 层、文档对象存储层。

## 6. 训练集群存储架构选型

### 6.1 三方案对比

| 方案 | 代表 | 吞吐 | 适用 | 局限 |
|------|------|:---:|------|------|
| 并行文件系统 | Lustre / GPFS | 数十-数百 GB/s | 超大规模训练（万卡） | 运维复杂、贵 |
| 分布式 FS + 对象底座 | JuiceFS / Alluxio | 数-数十 GB/s | 中大规模、云原生 | 需网络带宽支撑 |
| 本地 NVMe + 异步上传 | 各云自有 | 节点级 GB/s | 单机微调/小集群 | 无共享语义 |

### 6.2 冷热分层（成本主线）

```text
热层：NVMe（训练数据、活跃 checkpoint）→ 闪存级吞吐
温层：HDD 40TB+（数据集归档、checkpoint 保留）→ 每 TB 最低
冷层：磁带/对象归档（历史数据、合规）→ EB 级成本
```

- 2026 典型：Backblaze 用 HDD 层为 CoreWeave 等提供 AI 数据冷层；热层 QLC SSD（245TB 级）承接读密集。
- **容量规划公式**：数据集 ×(1+迭代膨胀率) + checkpoint 版本数 × 单次大小——checkpoint 保留策略是成本大头。

## 7. 2026 趋势与面试要点

### 7.1 FMS 2026 三大议题（2026-08 闪存峰会）

1. **Agent & Agent AI**：Agent 的状态持久化、工具调用轨迹存储 → 细粒度随机 IO 优化。
2. **KV cache 与 LLM 推理优化**：CXL 扩容 + SSD 卸载 + 高 IOPS 设备。
3. **AI 存储架构**：从"推理"叙事转向"Agent 工作流"——存储成为 AI 基础设施一等公民。

### 7.2 面试自测 6 题

1. checkpoint 为什么难？答：写量大（TB 级）+ 频率与 MFU 矛盾 → 异步/压缩/卸载。
2. KV cache 溢出了怎么办？答：分层卸载（HBM→DRAM→CXL→SSD）+ GPU 直连。
3. AI 存储选型看哪些指标？答：读=吞吐/延迟，写=带宽/P99，寿命=写入量/DWPD。
4. 为什么 QLC 能进数据中心？答：FDP 压 WAF + 读密集场景寿命达标。
5. CXL 解决了什么？答：内存池化/扩展，服务器减 25%（Meta 数据）。
6. 存储工程师与 GPU 的关系？答：GPU 等数据 = 算力浪费，存储延迟就是成本。

> 🎯 **核心要点**：AI 存储的本质是**用存储换显存、用带宽换时间**——checkpoint 用异步写路径保 MFU，KV cache 用 CXL/SSD 分层换 HBM 容量，GPU 直连绕过 CPU 减一跳延迟。2026 年的关键词是"内存中心化"：存储与内存的边界在 AI 负载下快速消失，能看懂"延迟连续谱上的数据放置"，就是 AI 基础设施时代最好的存储工程师。
