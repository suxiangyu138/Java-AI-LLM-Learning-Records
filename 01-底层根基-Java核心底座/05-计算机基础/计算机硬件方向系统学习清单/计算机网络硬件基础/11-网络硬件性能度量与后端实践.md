## 1. 度量体系：五个数字

| 指标 | 定义 | 衡量什么 | 典型数值 |
|------|------|---------|---------|
| 带宽（Bandwidth） | 链路理论速率 | 硬件能力上限 | 1G-800G |
| 吞吐（Throughput） | 实际传输速率 | 端到端真实能力 | 通常为带宽的 70-95% |
| PPS（每秒包数） | 转发/处理速率 | **小包场景的硬指标** | 线速 64B 时 1.488Mpps/Gbps |
| 延迟（Latency） | 单包端到端耗时 | 交互/同步敏感度 | 同机房 TCP 0.1-0.5ms、RoCE 1-3μs |
| 丢包率（Loss） | 丢失包占比 | 可靠性与拥塞信号 | 以太网尽力而为：正常 0，拥塞时升 |

**延迟的正确读法**：报"平均延迟"掩盖问题，要看**分布**——P99/P999 尾延迟决定分布式系统体验（一次慢调用拖垮整体）。RTT 组成：处理延迟（微秒级）+ 排队延迟（拥塞时主导）+ 传输延迟（距离/光速，跨洋约 60-70ms）+ 抖动（变化量）。

**吞吐 ≠ 带宽**的成因：协议开销（帧头/IFG 约 6%）、TCP 重传、拥塞、双工不匹配（历史坑）、小包场景 PPS 上限。**衡量"网络好没好"先看是吞吐型（大包流媒体）还是延迟型（交易/RPC）负载**——两类的调优方向完全相反。

## 2. 线速与 PPS 计算

**PPS 上限公式**（以太网）：

```
每包总开销 = 帧长(64B) + 前导码+SFD(8B) + 帧间间隙(12B) = 84B
线速 PPS = 端口速率 / (84B × 8bit)
100G 端口 ≈ 100G / 672bit ≈ 148.8 Mpps
800G 端口 ≈ 1.19 Gpps
```

**含义**：小包线速是网络设备与服务器最难达标场景——**包处理是每包固定成本，与包大小无关**。交换机宣称"线速"必须在 64B 下验证；服务器同样：40G 网卡 + 内核协议栈处理 64B 包可能只有几 Mpps（差两个数量级），大包（1500B）则轻松打满带宽。**"PPS 不够"和"带宽不够"是两个完全不同的病**：压测时先想清楚测哪个。

**Jumbo Frame 为什么香**：MTU 9000 时每包运 9KB，同样吞吐下包数降 6 倍——CPU/中断/交换机处理压力同步降。存储与大数据传输标配；代价：全网 MTU 必须一致，否则分片或黑洞（常见故障：跨网段 MTU 不一致导致的大包丢小包通）。

## 3. 压测工具选型

| 工具 | 测什么 | 场景 | 关键参数 |
|------|--------|------|---------|
| `ping` | 连通性、RTT、丢包 | 第一诊断 | 首包 vs 稳定值、TOS 区分优先级 |
| `iperf3` | 单流 TCP/UDP 吞吐 | 带宽基线 | `-P` 多流、`-R` 反向、`-t` 时长 |
| `netperf` | TCP/UDP 吞吐+RTT | 细粒度协议度量 | omni 模式、请求响应模式 |
| `sockperf` | 消息延迟（吞吐型网络测不准延迟） | 微秒级 RTT | under-load 模式 |
| `wrk` / `ab` | HTTP 层 QPS/延迟 | 应用层压测 | 连接复用、线程数、keep-alive |
| `hping3` | 高 PPS 小包、SYN flood | 小包/抗攻击基线 | 注意误伤线上 |
| `ethtool -S` | 网卡级计数器 | 卸载/队列/丢包归因 | rx_dropped、pause 帧计数 |

**测量纪律**：① 带宽压测必须多流（单流受单核限制，用 `-P 4/8`）；② 延迟压测要在**有负载下**测（空载延迟无意义，尾延迟才真实）；③ 压测前确认全链路 MTU 一致；④ **防火墙/云安全组先放行**（压测打到自己防护上是最常见乌龙）；⑤ 记录基线（网络基线 = 后期排障的对照系）。

## 4. 网卡层度量：ethtool 读法

```bash
ethtool eth0                # 速率/双工/驱动
ethtool -k eth0             # 卸载状态: tcp-segmentation-offload on? generic-receive-offload on?
ethtool -S eth0             # 计数器: rx_packets/rx_dropped/rx_missed/rx_crc_errors/rx_pause
ethtool -l eth0             # 队列数: Combined 8 等
ethtool -n eth0 rx-flow-hash tcp4 # RSS 哈希字段
```

**关键计数器的含义**：

| 计数器 | 意义 | 故障信号 |
|--------|------|---------|
| rx_dropped | 驱动/协议栈丢弃 | 缓冲不足、RPS backlog 溢出 |
| rx_missed / rx_fifo | **网卡硬件丢弃**（队列满） | 中断延迟过大、处理不过来 |
| rx_crc_errors / rx_frame_errors | 物理层误码 | 线缆/光模块/端口故障，先查物理层 |
| rx_pause / tx_pause | PFC/PAUSE 暂停帧 | **无损网络风暴指标**（RoCE 环境核心排查） |
| tx_timeout | 发送挂起 | 驱动 bug、队列卡死 |

`/proc/net/softnet_stat` 的 dropped 列是**软中断队列溢出**（RPS backlog 满）的直接证据——高 PPS 服务器必查。**"带宽显示满但吞吐只有一半"的经典排查**：查 rx_missed（网卡丢弃）→ 查 softnet_stat（软中断溢出）→ 查 IRQ 绑核是否均衡（单核打满）。

## 5. 中断、队列与多核

硬件与软件的最终交汇点：**网卡队列 → 中断 → 软中断（ksoftirqd）→ 协议栈 → socket**。

```
每队列: RX Ring → MSI-X 中断 → CPU 的软中断 → 协议栈 → 应用 socket
         ↑ 中断聚合窗口          ↑ irqbalance/手动亲和性
```

**多核利用率的三级检查**：
1. 队列数 = 核数？（`ethtool -l`，通常自动按核数）
2. 中断是否均衡？（`/proc/interrupts` 看各队列计数分布；`irqbalance` 或手动绑定）
3. 单核软中断是否打满？（`top` 看 `si` 列；打满 = RSS 哈希不均或负载集中在少数流）

**RSS 哈希的坑**：按五元组哈希对**大流（一条 10G 流）无效**——一条流只会进一个队列一个核。大流场景要么多流并行（应用层），要么用**超队列（Super Queue）/流级 RSS**（网卡按流权重分配，高端网卡才有）。**虚拟化叠加**：SR-IOV 的 VF 每队列一个中断，VM 内绑核与宿主 NUMA 错位会丢性能（见 07 篇）。

## 6. Java 后端与网络硬件

后端工程师的"网络硬件"体验全部发生在 socket 与内核之间，核心映射：

| Java 概念 | 底层硬件事实 | 实践含义 |
|-----------|-------------|---------|
| Socket 缓冲区（SO_RCVBUF/SNDBUF） | 内核内存，非网卡 | 调大缓冲 ≠ 网卡吞吐；window 与 RTT 的乘积决定吞吐上限（BDP） |
| NIO 非阻塞 | 每连接一事件驱动，协议栈单线程可管理海量连接 | 连接数与线程数解耦；瓶颈在 epoll 事件与网卡队列 |
| 虚拟线程（Java 21+） | 阻塞式 IO 挂载到内核线程 | 大量阻塞 IO 不再占线程；吞吐受限于网卡中断与协议栈，而非线程数 |
| `sendfile`/零拷贝 | DMA 直达网卡（见 03 篇） | 大文件传输用零拷贝：CPU 占用从每包拷贝降到接近零 |
| 连接池 | 复用 TCP 连接（避免握手+慢启动） | 新建连接的成本是 RTT×2+；连接池大小 = 吞吐需求/单连接吞吐 |
| 分布式 RPC 超时 | 网络尾延迟（P99 抖动） | 超时设置要按 P99 而非均值；重试要幂等+退避（防重试风暴放大拥塞） |
| 高并发写（AllReduce 类似模式） | incast 突发（多对一） | 服务端多队列+多核才能抗住瞬间扇入；反压/限流是网络卫生 |

**BDP（带宽延迟积）公式**：`吞吐上限 ≈ TCP 窗口 / RTT`。跨机房 RTT 5ms、窗口 64KB → 上限仅约 12.8MB/s——**高带宽下必须开窗口缩放（默认开）或增大缓冲**；这就是"延迟是吞吐之敌"的数学来源，也是后端调参（SO_RCVBUF、内核 tcp_rmem）的物理依据。

**典型 Java 服务网络调优顺序**（从硬件到应用）：
1. 确认网卡速率与队列（ethtool）与 CPU 绑定；
2. 确认卸载开启（TSO/GRO/checksum）；
3. 内核参数：`tcp_rmem/tcp_wmem`、`somaxconn`、`net.core.rmem_max`、文件描述符上限；
4. 应用：连接池、超时与重试、keep-alive 复用、零拷贝（`FileChannel.transferTo`）、响应式/虚拟线程承载并发；
5. 观测：P99 延迟 + 丢包 + 重传（`netstat -s` 的 TCP retrans 计数）。

> ⚠️ 后端误区：① 以为"网卡 40G 应用就能 40G"——单连接受窗口/单核限制，多连接才接近带宽；② 调大 socket 缓冲解决一切——缓冲只影响吞吐上限（BDP 匹配），延迟问题要靠减少路径与排队；③ 把"CPU 打满"全归因业务——先看 `si`（软中断）占比，可能只是网络卸载没开/队列不均衡。

## 7. 常见瓶颈与排查路径

| 现象 | 首查 | 根因示例 |
|------|------|---------|
| 吞吐只有带宽一半 | `ethtool -S` rx_missed、软中断溢出 | 单核打满（RSS 不均）、中断聚合过大 |
| 延迟突然飙升 | 抓包看重传、查 PFC 暂停计数 | RoCE 环境 PFC 风暴；TCP 重传风暴 |
| 小包场景 PPS 不足 | 压测 64B 对照 | 内核协议栈上限（需 XDP/DPDK 或接受现实） |
| 间歇性断流 | `ethtool -S` CRC 错误、光模块告警 | 光模块老化/线缆损坏（物理层先换线） |
| 跨机房传输慢 | 计算 BDP：窗口/RTT | 缓冲未匹配；或单流未多流化 |
| 连接建立超时 | 半连接队列（somaxconn）、SYN 重传 | 应用 accept 慢、连接数满 |
| 传输中数据损坏 | CRC 错误 + TCP 校验和失败 | 物理层故障或网卡故障（升级网卡固件） |

**排查方法论**：先物理层（ethtool 计数器/线缆/光模块）→ 再数据链路（PFC/CRC/队列）→ 再传输层（重传/窗口）→ 最后应用层——**自底向上，每层用计数器下结论，不靠猜**。

## 8. 调优检查单

**服务器侧（硬件视角）**：
- [ ] 网卡速率与链路协商一致（ethtool 确认，防止 1G 协商）
- [ ] 多队列开启、队列数 ≥ 核数、IRQ 绑核均衡
- [ ] 卸载全开（TSO/GRO/checksum/VLAN），隧道卸载开启（虚拟化场景）
- [ ] 中断聚合：吞吐场景调大、延迟场景调小
- [ ] 大页与 NUMA：收包核与应用核同 NUMA
- [ ] MTU：全网统一（9000 巨型帧或 1500，别混用）

**网络侧（硬件视角）**：
- [ ] 链路利用率监控（别等用户报障）
- [ ] 丢包/重传/PFC 计数器告警（以太网无丢包是理想，计数器必须盯着）
- [ ] 光模块光功率监控（劣化提前发现）
- [ ] 升级固件/驱动前先测兼容性（网卡固件 bug 是"幽灵故障"大户）

**应用侧（Java）**：
- [ ] 连接池与 keep-alive（降低握手成本）
- [ ] 超时按 P99 设置、重试退避+幂等
- [ ] 大文件用零拷贝
- [ ] 压测留基线，发布后对比（网络回归 = 性能回归的隐形元凶）

> 🎯 **核心要点**：网络性能 = 硬件能力（带宽/PPS/线速）× 主机配置（队列/中断/卸载/绑核）× 应用行为（连接/窗口/重试/压测）。五个数字（带宽/吞吐/PPS/延迟/丢包）对应五种病，先分型再查因；排查自底向上（物理层→链路→传输→应用），每一步用计数器下结论。Java 后端记住三件事：**吞吐上限由 BDP 决定、延迟看 P99、网络问题大多出在配置而非硬件**——把 ethtool 计数器读熟，就超过了 90% 的"网络玄学"。

## 9. 常用命令速查与面试速记

```bash
# 网卡状态
ethtool eth0                          # 速率/双工
ethtool -k eth0                       # 卸载状态
ethtool -S eth0 | grep -E "dropped|pause"   # 丢包/PFC 计数
ethtool -l eth0                       # 队列数

# 中断与负载
cat /proc/interrupts | grep eth0      # 各队列中断分布
top 按 '1' 看 si (软中断) 占比

# 协议栈与连接
netstat -s | grep -E "retrans|drop"   # TCP 重传/丢弃
ss -s                                 # socket 统计
cat /proc/net/softnet_stat            # 软中断溢出（第3列 dropped）

# 压测
iperf3 -c 10.0.0.2 -P 8 -t 60         # 8 流带宽
iperf3 -c 10.0.0.2 -u -b 40G          # UDP 丢包基线
sockperf throughput -i 10.0.0.2 --tcp # 延迟
```

**面试速记**：
1. 网络性能五个数字：带宽/吞吐/PPS/延迟/丢包——先分型再查因。
2. 线速 PPS = 速率 / (64+20)B×8；100G ≈ 148.8Mpps，800G ≈ 1.19Gpps。
3. 吞吐上限由 BDP 决定：窗口/RTT；高带宽低延迟必须大窗口。
4. 排查自底向上：物理层计数器 → 队列/中断 → 重传 → 应用；80% 的"网络慢"是主机配置问题。
5. 网卡调优三件套：多队列、卸载全开、IRQ 绑核；延迟场景关中断聚合。

## 10. 基线建立与典型调优案例

**建立网络基线**（可回滚、可对比的运维前提）：

1. 上线前记录：`ethtool -S` 全量计数、`/proc/net/softnet_stat`、`ss -s`、iperf 带宽、P99 延迟；
2. 每周快照对比：计数器增量（丢包/重传/暂停帧）与延迟趋势；
3. 变更（固件/驱动/内核参数）前后各测一轮，**留对照数据再变更**——"没有基线的网络运维就是靠猜"。

**案例 1：数据库跨机房同步慢**。症状：主备 RTT 3ms，同步带宽只有 200Mbps。分析：BDP = 3ms × 25MB/s（200Mbps）≈ 75KB 窗口即可，但默认窗口缩放受限；根因 `net.core.rmem_max` 与 `tcp_rmem` 上限低。调参后窗口匹配 BDP → 带宽翻 5 倍。**教训：高延迟链路先算 BDP，再谈"网络慢"**。

**案例 2：压测 QPS 上不去且 CPU 软中断打满单核**。分析：`/proc/interrupts` 显示 8 个队列只有 1 个在忙（RSS 哈希五元组把压测流全部打到一个队列）；`top` 的 `si` 单核 100%。解决：压测用多连接多源 IP（分散哈希）；或开流级 RSS。**教训：RSS 对单大流无效——先确认流量形态再谈队列数**。

**案例 3：AI 训练迭代时间周期性飙升**。症状：每轮训练间隔 5 分钟出现一次 10 秒级卡顿。分析：checkpoint 写存储与集合通信共享网络，突发互踩；`ethtool -S` 见 PFC 暂停帧激增。解决：checkpoint 走独立存储网络/VLAN、错峰调度、调大交换机无损队列缓冲。**教训：AI 场景的网络瓶颈往往不是"带宽"而是"突发互扰"**。
