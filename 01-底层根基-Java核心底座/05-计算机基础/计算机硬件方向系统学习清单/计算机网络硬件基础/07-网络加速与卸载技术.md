## 1. 为什么需要卸载：CPU 税量化

收一个网络包，CPU 要付出的代价（传统内核路径，x86 实测量级）：

| 环节 | 工作 | 典型开销 |
|------|------|---------|
| 中断 | 触发与处理 | 每包一次，数百纳秒-微秒级 |
| DMA 管理 | 描述符处理、缓冲管理 | 数十 ns |
| 协议栈 | 链路层→IP→TCP→socket | 数百 ns-数 μs |
| 拷贝 | 内核→用户态 | 内存带宽消耗 |
| 应用处理 | recv/发送 | 应用相关 |

**量级认知**：单核 CPU 处理传统路径约 **1-2 Mpps**（以太网收包 64B 时约 1.5Mpps 是常见单核极限）；而 100G 端口线速需要 148.8 Mpps、800G 需要 1.19 Gpps——**即使 64 核全忙也差一个数量级**。这就是卸载存在的理由：把固定开销（校验、切分、拷贝、中断）从 CPU 挪到网卡/专用硬件，让 CPU 只干应用的事。

## 2. 网卡卸载家族全景

| 卸载 | 方向 | 机制 | CPU 收益 | 备注 |
|------|------|------|---------|------|
| Checksum Offload | RX/TX | 硬件算/验 IPv4/TCP/UDP 校验和 | 每包省数十 CPU 周期 | 全平台默认开启 |
| TSO/GSO | TX | 64KB 大段一次交给网卡，硬件切段 | 段处理量降 10-40 倍 | GSO 是内核兜底版 |
| LRO/GRO | RX | 相邻小包合并为大包上交 | 协议栈处理数降 4-8 倍 | GRO 内核版更安全（防 TCP 时序破坏） |
| RSS/RPS/RFS | RX | 哈希分队列/分核 | 多核并行收包 | 见 03 篇 |
| XPS | TX | 队列绑核 | 免锁竞争 | 高吞吐必配 |
| VLAN Offload | RX/TX | 硬件插/剥 802.1Q 标签 | 免软件栈处理 | 服务器虚拟化标配 |
| 隧道 Offload | TX | VXLAN/Geneve 外层头硬件封装 | 云网络性能关键 | 依赖网卡支持（主流 10G+ 都支持） |
| 流分类 | RX | 按五元组/流表分流 | QoS/低延迟 | 网卡级 AC 能力 |
| 加密卸载 | RX/TX | IPsec/TLS 硬件加解密 | 加密吞吐翻倍级 | 高端网卡/DPU 才有 |
| RDMA | RX/TX | 内核旁路 + 零拷贝 + 卸载 | 微秒级延迟 | 见 09 篇 |

**开启检查**：`ethtool -k eth0` 查看所有卸载状态（tcp-segmentation-offload、generic-receive-offload、rx-checksumming 等），`ethtool -K` 开关。**坑点**：TSO/GRO 与抓包分析冲突（抓包看到的是合并后的大包）；虚拟化环境宿主机与虚拟机卸载必须协调（vhost 与 VM 内网卡卸载不匹配会导致性能退化）。

## 3. 多队列与中断优化

| 技术 | 解决的问题 | 机制 |
|------|-----------|------|
| RSS | 单核收包瓶颈 | 硬件五元组哈希 → 队列间接表 → 每队列独立 MSI-X 中断绑核 |
| RPS | 无硬件队列时软件分摊 | 内核按哈希把包重分发到各 CPU backlog |
| RFS | 队列与处理 CPU 错位（缓存漂移） | 跟踪流所在 CPU，把包导回处理它的核 |
| 中断聚合 | 高 PPS 下中断风暴 | 攒 N 包/等 T 微秒再中断（NAPI 配合） |
| Busy Poll | 低延迟 | 应用层忙轮询 socket，绕过中断 |

**调优准则**：吞吐场景开大聚合窗口（延迟换吞吐）；**低延迟场景（交易、AI 集合通信、游戏网关）关聚合或直接忙轮询**——这对矛盾是服务器网络调优的第一课。多队列绑核（irqbalance 或手动亲和性）决定包处理 CPU 是否跨 NUMA——**跨 NUMA 收包延迟与带宽损失显著**，高规格部署用 CPU 隔离 + 大页 + 绑核的组合拳。

## 4. 内核数据面加速：XDP 与 eBPF

**不绕开内核、而是让内核更快**的路线，2026 年已是 Linux 服务器网络的事实标准基础设施：

| 技术 | 层次 | 机制 | 场景 |
|------|------|------|------|
| XDP | 网卡驱动入口（协议栈之前） | eBPF 程序在包进入内核的第一跳执行（可卸载到网卡） | DDoS 丢弃、负载均衡（LB）、防火墙、观测 |
| eBPF | 内核各处钩子 | 沙箱虚拟机执行用户注入程序 | 追踪（tracepoint/kprobe）、网络（tc/套接字）、安全 |
| AF_XDP | 用户态与内核共享零拷贝 socket | XDP 程序把包直送用户态 | 高性能用户态收包（DPDK 的轻量替代） |

**性能量级**：XDP 单核可达 **10-30 Mpps**（纯丢弃场景），远高于协议栈的 1-2 Mpps，无需专用硬件；现代网卡（100G+）支持 XDP offload 到网卡流水线。**为什么重要**：传统内核"慢"的主因是协议栈的通用性（处理 TCP 状态、路由、iptables 钩子链），XDP 在包进入这套通用机制之前就用最简路径决策——**"早丢的包不用付出协议栈成本"**。云厂商的 4 层负载均衡（Cilium、Cloudflare）大量采用。

**eBPF 的边界**：适合"快速路径的决策与观测"，不适合复杂状态机与协议实现（TCP 状态机仍是内核的）；XDP 丢包/转发场景最强，要完整 TCP 栈仍得走协议栈或内核旁路。

## 5. 内核旁路：DPDK 与用户态协议栈

**彻底绕开内核协议栈**：应用在用户态直接管理网卡（用户态驱动 + 轮询 + 大页），数据零拷贝直达应用。

| 方案 | 机制 | 吞吐/延迟 | 代价 |
|------|------|----------|------|
| DPDK（Intel 生态） | 用户态 PMD 驱动轮询网卡、大页内存、CPU 绑核 | 单核数千万 PPS，微秒级 | 独占 CPU 核与网卡、要自己实现协议栈（或配用户态栈） |
| AF_XDP | 内核 XDP 程序把包零拷贝交给用户态 | 数 Mpps（省去轮询的 CPU 成本） | 仍需部分内核参与 |
| 用户态协议栈 | 配合 DPDK 的 TCP/IP 实现（如 mTCP、F-Stack、Seastar） | 单核可达数百万连接 | 与内核栈不共享 socket 语义，应用要改造 |
| RDMA | 网卡卸载的终极形态（03/09 篇） | 亚微秒级 | 依赖无损网络/特殊网卡 |

**工程现实**：
- DPDK 不是"免费午餐"——**独占 CPU 核、独占网卡端口、旁路内核**意味着：该网卡上不能用 ethtool/tcpdump、不能跑普通 TCP 服务，运维与排障成本高。
- **什么时候才值得**：40G+ 线速小包处理、核心网元（LB、网关、防火墙）、时延敏感高频交易、AI 集合通信。普通 Web 服务（大包、连接数高、延迟不敏感）**不需要也不应该**用 DPDK——内核路径 + 多队列 + 调优就够。
- 2026 趋势：**eBPF/XDP 正在蚕食 DPDK 的地盘**（轻量场景），DPDK 退守"必须裸金属性能"的场景；DPU 出现后，很多 DPDK 场景被"DPU 上硬件卸载 + 主机内核照常"取代（08 篇）——**"卸载到另一颗芯片"比"绕过内核"更划算**。

## 6. TOE：完整 TCP 卸载的兴衰

TOE（TCP Offload Engine）把整个 TCP 状态机放进网卡硬件。**历史教训**：
- 2000s 网络厂商（Broadcom、Chelsio、微软）力推，宣称"卸载 CPU 的 TCP 负担"；
- 结果：TCP 状态机复杂（重传、乱序、拥塞控制与内核语义细微差别），硬件实现与内核栈行为不一致导致调试噩梦；10G 时代软件栈在普通 CPU 上已能线速（大包场景），TOE 收益消失；被 NFS/TCP 应用兼容性问题拖累；
- **结局**：TOE 退出主流，只在特定场景存活（部分存储网卡、POWER 平台、Windows 老版本、RDMA 网卡的 TCP 加速）。
- 教训：**"卸载"要选对粒度**——固定格式的校验/切分/封装卸载是安全的；完整协议状态机（TCP）卸载不可行，因为协议的语义复杂性与生态兼容性（抓包、调优、升级）都绑定内核实现。RDMA 的成功恰恰因为它是"新协议 + 新 API"，不试图兼容 socket 语义。

## 7. 虚拟化网络加速

云/虚拟化环境，网络路径多一层虚拟交换机（OVS/bridge），CPU 税翻倍，需要专门加速：

| 方案 | 机制 | 性能 | 适用 |
|------|------|------|------|
| virtio-net | 标准半虚拟化设备（前后端共享队列） | 基线 | KVM/QEMU 默认 |
| vhost-net | 后端（宿主）侧用户态处理，减少上下文切换 | +30-50% | 通用场景 |
| vhost-user（DPDK） | 宿主侧 OVS 数据面用 DPDK | 数 Mpps/连接 | 云厂商高性能虚拟网络 |
| SR-IOV | 物理网卡切出 VF（虚拟功能），VM 直通 VF | 接近裸机 | 高吞吐网卡（NFV、AI 训练节点） |
| SmartNIC/DPU 卸载 | 虚拟交换/隧道封装在网卡硬件完成 | 接近线速且不占宿主 CPU | 超大规模云（见 08 篇） |

**SR-IOV 详解**：PF（物理功能）由宿主管理，切出多个 VF（带独立队列/中断），VM 直接驱动 VF——数据不经过宿主机协议栈，**吞吐接近裸机、CPU 占用几乎为零**。代价：VM 无法热迁移（网卡直通绑定物理机）、安全隔离依赖网卡（VF 间靠 MAC/队列隔离）。AI 集群节点（GPU 直通 + RoCE 直通）普遍用 SR-IOV。

## 8. 技术选型决策表

| 场景 | 推荐路线 | 不推荐 |
|------|---------|--------|
| 常规 Web/微服务（大包、连接多） | 内核路径 + 多队列绑核 + GRO/TSO 默认开启 + 中断聚合调优 | DPDK（过度工程） |
| 高 QPS 网关/LB（小包、高 PPS） | XDP/eBPF 快速路径；或 DPDK | 纯内核路径（PPS 不够） |
| 高频交易/超低延迟 | 忙轮询/AF_XDP/RDMA | 中断聚合（延迟不可控） |
| AI 集群集合通信 | RDMA（RoCE/IB）+ SR-IOV 直通 | 内核 TCP 路径 |
| 云厂商虚拟网络 | vhost-user + 隧道卸载，或 DPU 硬件卸载 | 纯软件 OVS（CPU 税不可承受） |
| 存储网络 | 巨型帧 + 多队列 + RDMA/NVMe-oF | TOE（历史证明失败） |

> 🎯 **核心要点**：卸载技术谱系 = 网卡硬件卸载（固定格式：checksum/TSO/GRO/RSS/隧道，安全且必备）→ 内核加速（XDP/eBPF：让内核在协议栈前快速决策，10-30 Mpps）→ 内核旁路（DPDK：绕过内核裸收，千万 PPS，代价独占）→ 协议级卸载（RDMA：新协议新 API，成功）→ 协议栈卸载（TOE：试图卸载 TCP，失败）。选型铁律：**收益必须大于运维代价，能加硬件就不绕过内核，卸载粒度宁小勿大**。

## 9. 每包成本模型与决策示例

**量化决策**：要不要上 XDP/DPDK？先算 CPU 账：

```
需求：40G 端口线速小包（64B）≈ 59.5 Mpps
方案 A 内核传统路径：单核 ~1.5Mpps → 需要 ~40 核专门收包（不可行）
方案 B XDP 丢弃/转发：单核 ~20Mpps → 3 核足够（可行，且不独占网卡）
方案 C DPDK：单核 ~30Mpps → 2 核（可行，但独占网卡+改应用）
结论：能 XDP 解决的不用 DPDK；DPDK 留给"必须裸机性能且愿意改造"的场景
```

**DPDK 最小架构认知**（不必会写，但要能看懂）：

```text
应用（用户态）
  ↓ 直接调用用户态驱动（PMD，e.g. ixgbe/ice）
  ↓ 轮询收包（无中断）→ 大页内存（2MB/1GB 页）零拷贝
DPDK 库 ← 绑定 CPU 核（独占）
网卡（被 DPDK 接管后，普通协议栈不可用该端口）
```

**真实世界决策案例**：
- 云厂商 4 层负载均衡：XDP/eBPF 为主（无需独占网卡、可热升级程序）；
- 运营商/骨干网关：DPDK（必须线速、流量模式固定、可接受独占）；
- 高频交易：忙轮询/AF_XDP（延迟决定性，吞吐不是）；
- 普通 Java Web：**什么都不用**（多队列 + 卸载 + 内核默认即够）——"技术选型的第一课是知道什么时候不该上新技术"。

## 10. 可观测性与容器网络

**网络加速技术选好之后，可观测性决定运维生死**：

| 工具 | 观测什么 | 适用 |
|------|---------|------|
| ethtool -S / softnet_stat | 网卡与软中断计数器 | 物理机基线 |
| `tc -s` | 队列/丢弃统计（qdisc） | 流量整形、限速验证 |
| eBPF（bpftrace/syscount） | 协议栈函数级追踪 | 深水区排障 |
| tcpdump + wireshark | 报文级取证 | 协议/时序问题 |
| 遥测（交换机 sFlow/IPFIX/INT） | 全网路径级观测 | 数据中心级 |

**容器/微服务环境的网络路径**（加一层虚拟化后 CPU 税重新出现）：容器→CNI（veth/bridge/macvlan）→宿主协议栈→网卡。**每层都是卸载技术的应用点**：CNI 层用 eBPF（Cilium）做策略与负载均衡（XDP 快路径）、宿主机用 vhost/SR-IOV 加速、DPU 方案把 CNI 数据面整个下沉到卡上。**"微服务网络性能" = 主机网络性能 × 虚拟层效率**——后端排查网络问题时要先分清：慢在内网链路、宿主机协议栈、还是容器网络层（kube-proxy/CNI）。

## 11. 巨型帧与卸载的黄金组合

**巨型帧（MTU 9000）为什么与卸载是"最佳拍档"**：TSO 把 64KB 大段切成 9KB 的巨型帧（而非 1.5KB 小帧），包数再降 6 倍；GRO 把 9KB 帧合并上报——**两层叠加后，同样 40G 流量，协议栈处理的包数只有默认配置的 1/36**：

```
默认：1500B MTU + TSO → 每 64KB 大段 44 个包
巨型帧：9000B MTU + TSO → 每 64KB 大段 8 个包（省 5/6）
再叠加 GRO 合并 → 协议栈只见 1/6 的包（再省 5/6）
```

**启用检查清单**：交换机端口 MTU 9216+（注意交换机"巨型帧"开关与端口速率无关）、路由路径所有设备 MTU 一致（否则大包分片或黑洞）、网卡 `mtu 9000`（`ip link set eth0 mtu 9000`）、虚拟化环境宿主与 VM 同步。**存储与 AI 网络标配巨型帧，Web 服务可不开**（小包流量收益有限，反而增加分片风险）。
