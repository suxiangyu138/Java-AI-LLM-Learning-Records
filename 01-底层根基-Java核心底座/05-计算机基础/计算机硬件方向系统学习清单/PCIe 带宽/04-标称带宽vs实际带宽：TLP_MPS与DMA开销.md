# 标称带宽 vs 实际带宽：TLP、MPS 与 DMA 开销
> 编码损耗（02 篇）只是第一道折扣，真正的"带宽黑洞"在协议层与系统层：每个 TLP 带 ~28 字节包头、读请求被 MPS/MRRS 拆分、IOMMU 与中断在 CPU 侧烧时间——大块连续传输能到 99% 效率，小块随机传输可以只剩七成不到。

## 1. TLP：PCIe 世界里一切数据都要"打包"

PCIe 事务层的最小传输单位是 TLP（Transaction Layer Packet，事务层包）。无论读写、配置、完成，所有数据都装进 TLP 传输。TLP 的结构决定了带宽的实际"载货率"：

```text
┌──────────┬──────────┬──────────┬──────────┬─────────┬─────────┐
│ Start(1B)│ Seq(2B)  │ Header   │ Payload  │ ECRC(4B)│ LCRC(4B)│
│ 帧起始   │ 序号     │ 12-16B   │ 数据(可变)│ 可选     │ 链路CRC  │
└──────────┴──────────┴──────────┴──────────┴─────────┴─────────┘
```

每个 TLP 的固定开销约 28 字节（帧起始 + 序号 + 12-16 字节头 + LCRC，ECRC 可选另加 4 字节）。载货率取决于 Payload 大小——即 MPS（Max Payload Size，最大有效载荷）：

- **MPS 256 字节**（多数消费级主板/芯片组的默认上限）：256/(256+28) ≈ **90% 效率**
- **MPS 512/1024 字节**（服务器默认，取决于 CPU）：效率 95%/97%
- **小块传输（64 字节缓存行读）**：64/(64+28) ≈ 70%——且这只是打包开销，还没算读请求本身"一去一回"的两次占用

一个关键工程事实：**MPS 的上限由链路上最弱的一环决定**——RC、Switch、Endpoint 中任何一个只支持 256 字节，整条链路就按 256 字节跑。主板 BIOS 里"Payload Size"的默认值往往就是 256，这也是"换了 Gen5 盘但测速上不去"的常见隐藏原因。

## 2. 读请求的拆分：MRRS 比 MPS 更重要

写传输把 MPS 填满即可；读传输多一层：**单次读请求（MRRS，Max Read Request Size）限制请求长度**，且 RC（根复杂体）通常把单次读请求压到 512 字节——即使 MPS 支持更大，读请求也被拆成多个小 TLP 在链路上流水执行。

后果很反直觉：**4KB 的 DMA 读会变成 8 个 512 字节请求，每个请求都要"读请求 TLP → 完成 TLP"一个往返**。请求-完成配对是 PCIe 读路径的固有成本——读带宽的真实瓶颈往往不是链路速率，而是"同时在途的请求数 × 往返时延"（带宽延迟积）。

调优手段：把 MRRS 从 128 提到 4096（配合 MPS 同步放大），对带宽饥饿型设备（NVMe、网卡）经常带来近 2 倍读吞吐提升——这是 09 篇"调优三板斧"的第一斧。代价是读延迟略有上升（更大的请求需要更长响应时间），IOPS 敏感型场景要权衡。

### 2.1 效率总表（真实测量口径）

| 场景 | 开销来源 | 可达效率 |
|------|---------|:---:|
| 4KB 大块连续写，MPS 4KB | 仅 TLP 包头 | >99% |
| 256B 典型块写，MPS 256 | TLP 包头 | ~90% |
| 64B 缓存行随机读 | TLP 包头 + 请求/完成往返 | ~70%（甚至更低） |
| 小 IO + 中断每笔打断 | 系统层（中断/上下文） | 视中断频率腰斩 |

**结论先行：大块连续传输贴近链路极限，小块随机传输被协议与系统双重打折**——这也是 NVMe 顺序读 12-14 GB/s 而 4K 随机只有 1-2M IOPS 的物理根源之一（另一根源在 NAND 与 FTL，属存储体系）。

## 3. 系统侧开销：DMA、IOMMU 与中断

链路层之外，CPU 侧还有三笔"隐形成本"：

**DMA（直接内存访问）**：PCIe 的常见用法是设备通过 DMA 直接读写主存，CPU 只在收尾时收到中断。DMA 本身是"零拷贝"的好东西，但 DMA 引擎的启动、页表描述符管理、完成通知都在消耗 CPU。端到端 NVMe 路径 50-100 µs 里，CPU 真正做的工作只有 1-2 µs——**其余全是设备时延与 PCIe 传输**，这条路已经优化到接近物理极限。

**IOMMU（I/O 内存管理单元）**：虚拟化与安全要求设备不能直接看见物理内存地址，IOMMU 做地址翻译。每次 DMA 翻译 0-100 ns（TLB 命中为 0）——看起来微不足道，但对每秒百万次 DMA 的设备（高速网卡、NVMe 多队列）就是 CPU 侧的真实负担。云服务器上 IOMMU 通常开启（SR-IOV 前提），物理机裸跑可关闭换性能。

**中断与合并**：一块"每包中断"的网卡在 1M 包/秒时每秒产生约 100 万次中断，每次约 200 ns 上下文切换，合计占满一个核的 20%。业界解法是中断合并（coalescing）：NVMe 攒 16 个完成才打断一次，或等待 100 µs 批量通知——**用延迟换 CPU**。工程基准：每核中断率控制在 ~5 万次/秒以下是健康线。

## 4. 从标称到实际的完整折扣链条

把 02 篇的编码损耗与本节所有开销串起来，一条 Gen5 x4 NVMe 的真实带宽账：

```text
Gen5 x4 理论单向带宽：      ~15.75 GB/s（编码后）
减去 TLP 包头（MPS 4KB）：  ~15.6 GB/s（>99%）
减去驱动/队列软件开销：     ~14-15 GB/s（实测旗舰盘顺序读）
减去 IOMMU/中断/调度抖动：  ~12-14 GB/s（真实可达）
```

链路效率 90%+，系统效率再砍 10-20%——**标称数字是物理极限，不是体验承诺**。规划任何 PCIe 带宽预算时按 0.75-0.85 折算"标称 → 实际"，与 `内存墙/05` 篇"HBM 标称按 0.8 折算"的原则完全一致：硬件数字永远要打折再用。

验证这条折扣链的方法：用 fio 跑顺序读（接近链路极限）与 4K 随机（协议层开销显形）两组对照，两组差距就是"协议 + 系统开销"的实测值；同一块盘在消费级与服务器平台上的差距，多数来自 MPS 默认值不同——**对照实验是穿透折扣链的唯一方法**（09 篇测量纪律）。

## 5. 读写不对称：posted 与 non-posted 事务

PCIe 的读写路径天生不对称，这是"为什么读比写难跑满"的协议根因：

- **写（Posted）**：发送端发出即忘（fire-and-forget），完成信号由链路层确认（CRC + 序号），不需要"完成包"回程——写流量可以满管道持续灌注
- **读（Non-Posted）**：必须等目标返回"完成包"（Completion），请求-完成配对。完成包回程占用同一链路的反向带宽——**读大块数据时，正向是请求（小）、反向是数据（大），双向都被占用**
- **完成超时（Completion Timeout）**：读请求发出后目标无响应，默认 50ms 级超时上报错误——读写混合负载下的偶发"卡顿"要往这里查（09 篇案例三的排查思路）

工程推论三条：顺序写比顺序读更容易贴满链路（无完成包回程），实测差异约 5-10%；随机读的灾难根源不是 NAND 而是"请求-完成往返 × 在途并发"——提高队列深度、放大 MRRS 是唯一出路（本节开头"带宽延迟积"在这里具体化）；完成包与数据包共用链路，**读为主的负载规划必须按单向带宽，不能按双向**——规格表上的"双向 512 GB/s"对读负载天然打对折。

### 5.1 队列深度与多队列：软件侧的"管道加粗"

设备侧同样有"带宽延迟积"：NVMe 的队列深度（queue depth）、网卡的描述符环数量决定单条链路能同时在途多少请求。工程事实：**在途请求数不足时，链路空闲等往返——带宽的瓶颈不在链路而在"并发度"**。多队列（每核一队列）的意义因此不止于核利用率：它让每个核都有独立的在途请求管道，把单队列的"串行等待"变成"并行流水"。SPDK、io_uring 与 NVMe 多队列结合，本质都是"提高并发度吃满链路"——这是 09 篇调优第二斧的理论依据。

### 5.2 MPS/MRRS 从哪看：配置空间的真相

MPS 与 MRRS 是设备配置空间里的可编程字段，但**生效值由 RC 与设备协商取小**——设备能力 4KB、RC 只支持 1KB，链路就用 1KB。查看与修改的三条路径：BIOS（Max Payload 全局策略）、`setpci`（读设备字段）、驱动参数（NVMe 的 max_sectors、网卡的 MTU/ring 参数）。三件套错位的典型症状：BIOS 支持 4KB 但驱动限制单次 I/O 大小，顺序吞吐正常、大块随机读写异常——**"大块好、小块差"优先查 MPS/MRRS**，与 5.1 节的队列深度组合成"随机性能排查双件套"。

> 🎯 **核心要点**：标称带宽要过四道折扣——编码（Gen6 前 1.5-20%）、TLP 包头（小包 24% 以上）、读请求拆分（MRRS 512B 限制 + 请求/完成往返）、系统开销（IOMMU/中断/队列）；大块连续传输可到 99%，小块随机只有七成；规划按 0.75-0.85 折算；最实用的优化杠杆是 MRRS 放大（读带宽近 2 倍）与中断合并（CPU 减负）。
