# 软件与调试视角：测量、诊断与优化
> 带宽问题的 80% 不是"不够"，而是"没跑满"——降速协商、NUMA 错位、MRRS 太小、中断风暴，每一样都能让标称带宽打个对折；而诊断的第一站永远是 lspci 的两行字。

## 1. lspci：读懂链路的真实状态

Linux 下一切 PCIe 诊断从 `lspci -vv` 开始——它直接暴露链路训练结果：

```bash
lspci -vv -s 01:00.0          # 查看 01:00.0 设备的完整能力

# 关键两行（NVMe 盘示例）：
# 01:00.0 Non-Volatile memory controller: ...
#     LnkCap: Port #0, Speed 32GT/s, Width x4, ASPM L1.2
#     LnkSta: Speed 32GT/s, Width x4, <LnkSta 是当前实际协商值>
```

判读规则：

- **LnkCap（Capability）是能力上限**：设备/插槽能支持的最高代数与通道数；**LnkSta（Status）是当前实际值**——两者必须相等，不等就是降速协商（05 篇）
- `Speed 32GT/s` = Gen5；`Speed 64GT/s` = Gen6。若盘是 Gen5 而 LnkSta 显示 8GT/s（Gen3），先查插槽代数和 BIOS 设置
- 同一输出里还有 MaxPayload/MaxReadReq 字段（MPS/MRRS 协商结果，04 篇 5.2 节）与 ASPM 状态；`nvidia-smi topo -m` 输出的 PIX/PXB/SYS 分别表示"同 PCIe 交换器 / 经 PCIe 交换器 / 经系统"——**带宽逐级递减的官方分级**，是判断 GPU 拓扑质量的第一手资料
- `Width x4` 若显示 x2/x1，多半是接触不良或转接卡降级——**先怀疑物理层，再怀疑软件**

常用配套命令：

```bash
lspci -tv                                   # 树状拓扑：设备挂哪颗 CPU/芯片组一目了然
lspci -s 00:03.0 -vv | grep -i link         # 快速过滤链路信息
dmidecode -t slot | grep -iE "Type|Width"   # 查看插槽物理规格（可选）
nvidia-smi topo -m                          # NVIDIA 视角的 GPU 拓扑与互连带宽矩阵
```

## 2. 带宽测量：从链路层到业务层的四级

"实际带宽多少"要分层测量，每层口径不同：

| 层级 | 工具 | 口径 | 说明 |
|------|------|------|------|
| 链路协商 | lspci LnkSta | 协商带宽 | 理论值，物理上限 |
| 设备吞吐 | fio（NVMe）、iperf3（网卡）、PassMark 卡 | 设备级 | 最能暴露 MPS/MRRS 配置问题 |
| DMA 路径 | pcm-pcie、perf stat | 实际传输 | 检查是否跑满链路 |
| 业务层 | 应用基准（模型加载秒数等） | 体验 | 一切优化的最终裁判 |

测量纪律三条：**一次只变一个变量**（改 MRRS 前先测基线）；**顺序读测链路上限、4K 随机测协议效率**（04 篇两种口径）；**双端验证**（主板 A 测出的数字在主板 B 可能不同——不同 CPU 的 MPS 默认值、不同 BIOS 的 bifurcation 配置都会改变结果）。

## 3. 八大高频问题的诊断表

| 症状 | 根因 | 验证手段 | 修复 |
|------|------|---------|------|
| 盘速只有标称一半 | 降速协商（Gen/lane） | lspci LnkCap vs LnkSta | 换插槽/查 BIOS/重新插拔 |
| 双 GPU 带宽不叠加 | x16 被拆 x8+x8 | lspci Width | 接受（物理限制）或单卡测试 |
| M.2 同时插满全慢 | 芯片组共享 x4 上行 | 拓扑确认 CPU 直连 vs PCH | 把关键盘换到 CPU 直连 M.2 |
| 顺序读只有 60% | MPS 停在 256B | lspci 查 MaxPayload | BIOS 调 Max Payload 512/1KB |
| 随机读吞吐极低 | MRRS 128B 限制 | 同上 + 带宽延迟积 | 调 MRRS 至 512-4KB |
| 高 PPS 时 CPU 飙高 | 中断风暴 | /proc/interrupts 计数 | 中断合并 + 多队列 RPS/XPS |
| 跨 socket 访问慢 | NUMA 错位 | lstopo/nvidia-smi topo -m | 设备/线程/内存三对齐 |
| 虚拟化环境带宽减半 | IOMMU 翻译 + vCPU 调度 | 对比裸机测速 | 接受或 P2P/直通优化 |

诊断顺序固定为：**先物理（LnkSta）→ 再配置（MPS/MRRS）→ 后系统（NUMA/中断）**——跳过第一步直接调软件，是最常见的无效优化。

## 4. 调优三板斧与性能红线

**第一斧：MPS/MRRS 对齐**。BIOS 把 Max Payload 设为 CPU 支持的上限（服务器常 512B-4KB），设备侧 MRRS 同步放大。对 NVMe/网卡这类顺序流量，收益可达近 2 倍；注意 IOPS 敏感场景（小块随机）放大 MRRS 反而增加延迟，需 A/B 实测。

**第二斧：中断与队列工程**。网卡/NVMe 多队列（每核一队列）+ 中断合并 + RPS/XPS 绑定，把每核中断率压到 ~5 万/秒以下；io_uring 把每次 I/O 的系统调用开销降 10 倍（小 IO 场景最值）。

**第三斧：NUMA 与亲和性**。设备所在 socket 的核处理它的中断与内存分配（`numactl --cpunodebind` + 驱动参数），跨 socket 的代价是 1-2 倍带宽差，零成本修复。

三条红线（写进巡检清单）：

- **ASPM 省电模式**（L1.2）在延迟敏感负载下关闭——省电与带宽不可兼得，LnkSta 里能看到 ASPM 状态
- **不要用 PCIe 做 GPU 间主力通信**（见 08 篇分工）——消费级双卡张量并行 32k+ 上下文是明确的性能悬崖
- **虚拟化环境按 0.7 系数规划带宽**（SR-IOV 的 IOMMU 翻译是真实开销，04 篇）
- **不要绕过测量直接下结论**——"看起来慢"必须走对照实验（单变量变更 + 复测）定位：先 LnkSta、再 MPS/MRRS、后系统三层，凭经验直接换硬件是预算浪费最常见的方式，也是排障最慢的方式（本节测量纪律与案例二）

## 5. 实战案例三则

**案例一：训练服务器 GPU 带宽减半（降速协商）**。现象：新到 8-GPU 服务器跑 70B 训练，吞吐只有验收值的 55%。排查：`lspci -vv` 发现 GPU 的 LnkSta 显示 Speed 8GT/s（Gen3）而 LnkCap 是 32GT/s——8 张卡全部协商到 Gen3。根因：主板 BIOS 的 PCIe 代数策略默认"兼容模式"，装机后未切换。修复：BIOS 切 Gen5 模式重启，LnkSta 全部回到 32GT/s，吞吐恢复 100%。教训：**新机器第一件事是核对 LnkCap vs LnkSta**（10 篇验收第 1 项）。

**案例二：NVMe 顺序读只有标称 60%（MPS 限制）**。现象：Gen5 盘标称 13 GB/s，实测 8 GB/s。排查：LnkSta 正常（32GT/s x4），fio 大块读确认 8.1 GB/s——正是 256B MPS 的效率（04 篇 2.1 表约 90%）乘链路上限再乘其余开销的结果。修复：BIOS 将 Max Payload 从 256 提到 1024，实测升至 11.8 GB/s。教训：**MPS 是 BIOS 默认配置里最容易被忽视的带宽杀手**。

**案例三：1Mpps 网卡打满一个核（中断风暴）**。现象：100G 网卡收包时单核 100%，吞吐上不去。排查：/proc/interrupts 显示中断全部落在 CPU0，且驱动默认不合并。修复：RSS 多队列 + irqbalance 亲和 + 中断合并（攒 16 包一断），CPU 占用降至 20%，吞吐恢复。教训：**带宽是链路的事，吞吐是整机的事**——软件路径不优化，链路一半带宽在等 CPU。

### 5.1 进阶工具：setpci 与 AER 日志

`setpci` 直接读写设备配置空间（危险但强）：可读 MPS/MRRS 实际值、强制改链路参数做实验（改前备份）；内核的 AER（Advanced Error Reporting）机制在 `dmesg` 里报告 PCIe 错误（校正错误、非校正错误），链路不稳定时（频繁重传、降速）AER 日志是定位信号完整性问题的第一现场——**"偶发卡顿 + AER 报错"组合出现，先怀疑物理层（03 篇），别急着调软件**。

### 5.2 性能计数器与链路健康度

链路层的数据面也有健康指标：Linux 的 PCIe 错误统计（/sys/bus/pci/devices/*/aer_dev_correctable 等）、驱动层的重传计数（NVMe 的 CRC 错误计数、网卡的 rx_missed）。**重传率是链路健康度最敏感的指标**——FEC 纠错正常时上层无感，但纠错频率骤升（AER 可校正错误激增）预示信号劣化：先于"卡顿"出现的降级信号，是排障的黄金窗口。定期采集这些计数器（与 10 篇巡检 SOP 合并），链路劣化可以做到"先预测、后故障"——这类"提前量"数据平时没人看，出事时就是定位时间的数量级差距。

## 6. 从诊断到预防：健康基线与趋势

诊断是事后的，预防才是工程。三句话建立预防体系：**第一，基线常态化**——新机器验收时把 LnkSta、实测峰值、重传计数全部存档（10 篇验收清单第 1 项），之后任何变更（BIOS、固件、插拔）后对比；**第二，趋势优于阈值**——单次数值说明不了问题，"重传计数周环比翻倍"才是信号，巡检脚本把计数器差值写入监控，告警用差值不用绝对值；**第三，变更即复测**——固件升级、BIOS 调整、硬件插拔后必须重跑链路与吞吐快照，绝大多数"神秘变慢"发生在变更后 48 小时内（案例一的教训）。预防体系的意义：**带宽问题 80% 是"没跑满"而非"不够"，而"没跑满"几乎总是配置漂移——抓住配置漂移，就抓住了全部**。

> 🎯 **核心要点**：PCIe 带宽问题的 80% 是"没跑满"而非"不够"——诊断永远从 lspci 的 LnkCap/LnkSta 对比开始（降速协商是头号杀手），按"物理 → 配置 → 系统"顺序排查八大高频问题；调优三板斧是 MPS/MRRS 对齐（顺序流量近 2 倍）、中断与队列工程（CPU 减负）、NUMA 三对齐（零成本修复）；三条红线：ASPM 慎开、PCIe 不做 GPU 主力互连、虚拟化打七折。
