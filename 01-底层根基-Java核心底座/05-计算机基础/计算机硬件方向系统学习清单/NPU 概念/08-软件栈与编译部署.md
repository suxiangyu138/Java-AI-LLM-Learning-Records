# 软件栈与编译部署
> "NPU 是软件定义的硬件"——没有编译器把模型翻译成 MAC 阵列的配置，没有运行时把 DMA 序列驱动起来，NPU 只是一块发热的硅片。本模块拆解从模型到硬件的完整链路。

## 1. 三层软件栈：框架 → 编译器 → 运行时

NPU 软件栈分三层，每层都在做"翻译"：

- **框架层**：PyTorch/ONNX——模型描述为计算图（算子 + 张量形状）
- **编译器层**：ONNX Runtime / TVM / MLIR / 各家专用编译器（CANN、Core ML 编译器、Qualcomm AI Engine Direct）——把计算图"落地"为硬件配置：算子映射到阵列、形状切分、数据流选择、内存分配、DMA 序列生成
- **运行时层**：NNAPI（Android）/ Core ML（Apple）/ Windows ML 与 Copilot Runtime（Windows）/ 各家 SDK——加载编译产物、驱动 NPU 执行、管理生命周期

编译器是灵魂：同一个模型，编译器选错数据流（03 篇）、内存布局或 DMA 重叠策略，性能可以差 5 倍——**NPU 的算力是硬件给的，效率是编译器给的**。

## 2. 编译器的三大决策

NPU 编译器在部署时要排定三件事：

- **算子映射**：每个 ONNX 算子落到哪种硬件单元——矩阵乘 → MAC 阵列，逐元素/激活 → 向量引擎，量化缩放 → 专用单元；不支持的算子要么融合进邻近算子、要么回退 CPU（回退即性能悬崖）
- **数据流与分块**：按 03 篇的三种数据流选择最适配的驻留策略；大张量按 SRAM 容量分块（tiling），块间用双缓冲 DMA 重叠
- **内存规划**：所有张量的片上/片外布局一次排定——权重驻留层、激活流式层、中间结果复用区，全部静态分配（NPU 没有动态内存管理）

三件决策的输出就是"编译产物"：硬件配置寄存器 + DMA 描述符序列 + 微码/指令流——**这就是静态图执行的完整含义**：运行时的每一步都在照单执行，没有硬件猜测。

三大决策之外还有第四件容易被忽略的：**运行时开销治理**——端到端延迟不只是 NPU 内核时间，还有框架分发、张量布局转换（NCHW/NHWC）、同步等待与缓存未命中。2026 年的实测经验：端到端延迟常是 NPU 内核时间的 2-3 倍，优化顺序是先查软件链（框架/驱动/布局），再谈硬件利用率——这也解释了为什么同一芯片在 ONNX Runtime 与厂商自研 SDK 下的表现差异可达 30%。

## 3. 量化：精度与吞吐的契约

NPU 的高效依赖低精度（02 篇），量化的落地有三种路径：

- **PTQ（训练后量化）**：模型训完后校准量化参数——快，但大模型/低比特（INT4）精度损失明显
- **QAT（量化感知训练）**：训练时就模拟量化误差——精度最好，是端侧 NPU 部署的标准路径（nanoNPU 的肺炎检测即用 QAT 验证）
- **混合精度**：敏感层（如注意力 QKV）保持 FP16、其余 INT8/INT4——编译器按敏感度分层选择精度，2026 年的主流工程实践

量化与 NPU 的关系是双向的：**硬件定义格式（INT8/INT4/FP8/MX），软件选择格式并补偿精度**——这与 `量化背后硬件约束/` 的"格式-硬件契约"完全一致，端侧 NPU 是这条契约最极端的执行者（INT4 端侧推理已普及）。

## 4. 端侧运行时：三巨头与"通用分母"

2026 年端侧部署的三条主路：

- **Apple Core ML**：闭源专用，模型必须转 Core ML 格式——质量最好但生态封闭
- **Android NNAPI**：Google 的硬件抽象层——统一入口，具体执行交给各家 NPU 的 vendor driver；性能取决于厂商驱动的质量
- **ONNX Runtime + Windows ML**：2026 年的"通用分母"——ONNX Runtime 提供统一执行环境，Windows Copilot Runtime 把系统级 AI 能力（Phi Silica 等）封装成 API；微软同时原生支持 MCP，系统 Agent 可以直接调用 NPU 能力

趋势判断（2026-2027）：**ONNX Runtime 成为端侧 AI 的通用底座**，各家 NPU 的差异被运行时适配层吸收——正如 CUDA 之于 GPU，ONNX Runtime 正在成为 NPU 生态的"类 CUDA"层，但没有 NVIDIA 的封闭性。

## 5. 算子覆盖率的治理：一张"支持清单"的生意

NPU 编译器支持的算子集合（算子覆盖率）决定模型的适配成本——这是 NPU 厂商与 CUDA 生态竞争的前线：每缺一个算子，模型要么融合掉、要么回退 CPU。2026 年的治理实践三件套：**算子清单管理**（部署前跑"算子扫描"脚本，列出全部不支持/回退算子并评估性能影响）、**融合补偿**（把不支持的算子并进邻近支持的算子——如把 LayerNorm 折叠进 GEMM 的激活通路）、**模型结构规避**（选择与 NPU 算子集匹配的模型家族——LLaMA 系普遍适配良好，含特殊算子的模型需重写部分结构）。经验值：主流 LLM 在 2026 年主流 NPU 上的算子覆盖率普遍 95%+，但"最后 5%"的回退算子可能拖慢整层 10-50 倍——**覆盖率数字要看"算子在计算图里的权重"而非"算子数量"**：一个 GEMM 算子顶一百个逐元素算子，20 个不支持的小算子可能远不如 1 个不支持的注意力算子致命。这也是 09 篇"端到端实测"的治理意义：清单 + 实测双保险。

## 6. 部署流程：端到端的九个步骤

2026 年端侧 NPU 部署的标准流程：选模型 → 导出 ONNX → 量化（PTQ/QAT）→ 精度验证 → 编译器离线编译 → 在目标设备验证性能 → 处理回退算子 → 封装运行时 → 灰度发布。两个易错点：一是**回退算子的隐形性能悬崖**（一个 unsupported 算子把整层拖到 CPU）；二是**精度与吞吐的跷跷板**（INT4 快 2 倍但敏感层掉点，必须按层混合）。所有步骤里，**"在目标设备验证"不可跳过**——编译器的静态排定无法预测真实带宽竞争（GPU 游戏与 NPU 推理抢同一内存总线），实测才是最终裁决。

> 🎯 **核心要点**：NPU 软件栈是"框架 → 编译器 → 运行时"三层翻译链，编译器排定算子映射、数据流与内存规划三件事，静态图执行意味着"没有硬件猜测"；量化是精度与吞吐的契约（QAT 是端侧标准路径，混合精度是主流工程实践）；2026 年 ONNX Runtime 正在成为 NPU 生态的"类 CUDA"通用底座，而"在目标设备实测"永远是部署流程不可跳过的一步——NPU 的效率一半在硅片，一半在软件。
