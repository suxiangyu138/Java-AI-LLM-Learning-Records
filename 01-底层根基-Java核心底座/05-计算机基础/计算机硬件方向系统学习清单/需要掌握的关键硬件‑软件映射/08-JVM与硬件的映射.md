# JVM 与硬件的映射
> JVM 是最懂硬件的软件：对象布局贴着缓存行设计、JIT 按指令集版本生成代码、GC 停顿是内存带宽的账单——2026 年的 GC 选型与调优，本质上是在"亚毫秒停顿"与"内存/CPU 预算"之间做硬件账。

## 1. 对象在内存里的样子：布局与缓存行

Java 对象在堆里的布局：对象头（Mark Word 8 字节 + Klass 指针 4/8 字节，JDK 24 实验性 Compact Object Headers 可压到 8 字节）+ 实例字段（按声明顺序与对齐规则排列）+ 填充。硬件视角的三个关注点：**对象头是锁与 GC 信息的"硬件锚点"**（偏向锁标记、GC 年龄都在 Mark Word 里——这就是为什么对象头能承载锁状态，07 篇）；**字段顺序影响缓存效率**（热字段分开则散落多个缓存行）；**引用数组遍历 = 指针追逐**（每个元素一次解引用，缓存命中率差于原始类型数组——所以 int[] 快于 Integer[]）。还有一个对齐细节：JVM 的对象与数组都按 8 字节对齐——这是 03 篇"对齐访问天然原子"在 JVM 里的实现前提，也是原子性保证的物理基础。JOL（Java Object Layout）工具可以打印任何对象的精确布局，是调优前"看清内存"的第一步。

## 2. 压缩指针：为什么 32GB 是分水岭

默认开启的 **-XX:+UseCompressedOops** 让 64 位 JVM 的引用只用 32 位（对齐 8 字节后可寻址 32GB 堆）——对象头小一半、缓存更友好、GC 更快。**堆超过 32GB 时压缩指针失效**，引用回到 8 字节，同样对象的内存占用与缓存压力显著上升——所以"32GB 堆 + 压缩指针"常常胜过"64GB 堆"。2026 年大堆（>32GB）场景的推荐是分代 ZGC（见第 4 节），但"压缩指针的收益"是选"多实例小堆 vs 单实例大堆"时的硬参数。一个经典算式：同负载下 2×32GB 实例（压缩指针开）通常优于 1×64GB 实例。

## 3. JIT 与指令集：代码在运行时"适配"硬件

JVM 的分层编译（C1 快速 + C2 深度优化）让热点方法获得"按本机 CPU 生成机器码"的机会：C2 会根据 CPU 特性选择指令（AVX2 向量化、BMI 位运算、`UseAVX` 系列开关），2026 年还会叠加 APX/AVX10.2 的支持（新一代 CPU 的 32 寄存器与 512 位向量——见 `微机原理 x86 汇编` 体系 10 篇）。C2 的另一个硬件适配是超线程（HT）感知：同一物理核的两个逻辑核共享执行单元，JIT 的指令调度会考虑 HT 竞争——"逻辑核数 ÷2 = 物理核数"是 Java 线程池默认大小（cpu 系数）的硬件依据，但 I/O 密集场景应当突破它。软件侧推论：**同一 .class 在不同 CPU 上性能不同是特性而非 bug**；"换新 CPU 服务自动变快"的另一半来自 JIT 的指令选择。观测手段：`-XX:+PrintAssembly`（需 hsdis）、JIT Watch 的编译日志、`-XX:+UnlockDiagnosticVMOptions -XX:+PrintCompilation`。

## 4. GC 与内存硬件：停顿是带宽的账单

GC 的代价本质是**内存带宽与访存模式**：标记阶段要遍历存活对象图（随机访存，缓存命中率低——GC 是内存墙最直接的受害者，见 `内存墙/06`）、复制/搬移阶段要读写堆（吃带宽）、TLB 覆盖（大页收益明显，02 篇）。2026 年的三选一（来自 Java Code Geeks 2026-04 实测数据）：**G1**（JDK 25 默认，JEP 523）通用稳妥，停顿 20-200ms；**分代 ZGC**（JDK 21 稳定，GenZGC）大堆低延迟之王——任意堆大小停顿 <1ms，代价是约 15-30% 额外内存（无压缩指针）与 5-10% CPU；**分代 Shenandoah**（JDK 21 稳定）内存受限场景更优——支持压缩指针，停顿 1-5ms，K8s 内存配额紧张时比 ZGC 安全（ZGC 的额外内存可能触发 OOMKill）。选型速查：堆 >32GB 且 P99<50ms → GenZGC；容器内存紧 → Shenandoah；默认 → G1。观测 GC 还有一个"形状"维度：G1 的停顿分布宽（偶发 Full GC 出现长停）、ZGC 的窄而密（持续亚毫秒小停）——JFR 的 GC pause 直方图能一眼区分两者，这决定了调优方向是"消灭 Full GC"还是"接受小停常态"。

## 5. JVM 调优的硬件依据：参数背后的物理量

一组"参数-硬件"对照：**-Xmx 与带宽**——堆越大 GC 扫描越多，超大堆（百 GB 级）的 YGC 频率与带宽预算要先算；**-XX:+UseLargePages**——TLB 命中率（02 篇），堆 >8GB 时通常值得开；**-XX:MaxRAMPercentage 与容器**——堆外（元空间、DirectBuffer、线程栈、JIT 代码）不占 Xmx 却占容器配额，2026 容器 Java 的标准预算"堆 ≤ 容器内存 60-70%"，剩余给堆外与 OS；**-XX:+UseContainerSupport**——自动按 cgroup 配额算默认堆（JDK 8u191+/10+）。还有一个被忽略的硬件账单：**线程栈与 JIT 代码缓存**——默认 1MB 线程栈 × 500 线程 = 500MB 虚拟空间（物理按需但页表/TLB 有成本），JIT 代码缓存默认上限数百 MB——容器内存预算要把它们算进去。调优方法论：**先量化再调参**——用 JFR/JMC 看 GC 停顿分布、内存增长曲线、锁与 IO 事件，参数是最后一步。

## 6. 未来：JEP 516 与更快的启动

2026 年的 JVM 硬件叙事还有两条：**JEP 516（GC-Neutral Format，Project Leyden）**——让 AOT 编译的对象缓存兼容任意 GC（此前 AOT 只绑定 G1），低延迟 GC 用户也能获得 20-50% 的启动加速（云原生弹性伸缩的直接收益）；**JDK 24 实验性 Compact Object Headers**——对象头 12→8 字节，堆密度提升。两者都在回答同一个问题：**JVM 如何把"内存与启动"的硬件成本再压低一档**——与 Serverless（10 篇）的冷启动诉求直接呼应。

> 🎯 **核心要点**：JVM 与硬件的映射是四笔账——**对象布局账**（头+字段+压缩指针，决定内存密度与缓存命中）、**JIT 账**（按指令集版本生成机器码，决定单线程速度）、**GC 账**（带宽与访存决定停顿，选型看堆大小与内存预算）、**容器账**（堆外也吃配额，预算先算后调）；2026 年的结论一句话：**默认 G1，大堆低延迟 GenZGC，内存紧 Shenandoah，一切先量化后调参**。
