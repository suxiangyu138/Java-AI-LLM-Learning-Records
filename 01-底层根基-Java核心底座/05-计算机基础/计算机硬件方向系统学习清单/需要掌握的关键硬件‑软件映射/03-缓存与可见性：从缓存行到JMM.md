# 缓存与可见性：从缓存行到 JMM
> volatile 为什么能"看见"别的线程的修改？synchronized 为什么有"锁的内存语义"？答案不在 Java 里，而在缓存行、MESI 协议与内存屏障组成的硬件世界里。

## 1. 缓存层级：为什么"等内存"是性能第一杀手

现代 CPU 的三级缓存：L1（每核 32-64KB，约 1ns）、L2（每核 0.5-2MB，约 3-5ns）、L3（共享 8-64MB，约 10-40ns），主存约 80-100ns——**每下一级慢一个数量级**（完整时延阶梯见 `内存墙/02`）。这意味着：一次主存访问的时间里 L1 能完成约 100 次访问；热点循环能不能"住进缓存"直接决定性能差 10 倍还是 100 倍。软件侧由此得到最重要的性能原则：**数据局部性**——时间局部性（刚用过的数据马上再用）与空间局部性（相邻数据一起用）是缓存友好的代码的共同特征；数组遍历快于链表、列存快于行存（按需读）、结构体紧凑排列，都是局部性的工程化。

## 2. 缓存行：缓存读写的最小单元

缓存不是按字节搬运的，而是按**缓存行**（cache line，x86 固定 64 字节）整行读写。这带来一个反直觉的事实：**你只改一个字节，硬件却搬了 64 字节**。软件侧的两个推论：相邻字段一起读的收益（结构体热字段靠拢）、以及"半个缓存行"的浪费（频繁写的字段与只读字段混在一起时，每次写都会连带写整行）。Java 中调整对象字段顺序、用 @Contended 注解（JDK 8+，JEP 142 的后续）隔离热字段，都是缓存行层面的工程手段。

## 3. 伪共享：两个线程的"隐形共享"

两个线程分别读写**互不相干**的变量，但这两个变量恰好落在同一缓存行时，硬件为了保证一致性会让整行在两个核之间来回失效——性能可暴跌一个数量级，且完全无法从代码逻辑看出原因（没有共享，却"共享"了）。经典案例：并发计数器数组、Disruptor 的 ring buffer 槽位、`AtomicLong` 相邻实例。解法三件套：字段 padding（把热字段补满 64 字节）、@Contended、让每个线程独享缓存行（线程局部缓冲 + 合并）。**识别伪共享靠工具**：perf 的 cache-misses 高而逻辑无共享、或 CPU 核间 ping-pong 现象。

## 4. MESI 与缓存一致性：可见性的硬件基础

多核共享缓存后出现新问题：核 A 改了变量，核 B 的缓存里还是旧值——硬件用**缓存一致性协议**（x86 用 MESI 族）解决：每个缓存行带状态（Modified/Exclusive/Shared/Invalid），写操作需要先"获得独占"（把其他核的副本置 Invalid），读操作共享。这就是"可见性"的物理含义：**一个核的修改要传遍其他核，靠的是缓存行的失效与重读，不是"内存被改了"**。软件侧的推论：volatile 读总是"新鲜的"、普通读可能读到旧缓存——一切并发可见性问题的根源都在这个协议上。

## 5. volatile 的硬件语义：屏障与写缓冲

volatile 在 Java 中的语义是"可见性 + 有序性"，在 x86 硬件上的实现是：volatile 写 = 普通写 + 写屏障（x86 上实际是带锁的写或 mfence 类指令，强制写缓冲落空、使其他核的缓存行失效）；volatile 读 = 普通读 + 读屏障（使本核缓存失效、强制重读）。为什么不直接"每次都读内存"？因为 CPU 有写缓冲（store buffer）来隐藏写延迟——它让"我写了自己立刻能看见、别人看不见"成为常态，屏障就是"把写缓冲冲进缓存/内存"的阀门。**理解了写缓冲，就理解了为什么 volatile 写比普通写贵**：它打断了 CPU 最依赖的异步化。

## 6. CAS 与原子指令：锁的硬件种子

"比较并交换"（CAS）是锁的原子基石：`LOCK CMPXCHG` 这类指令由硬件保证"读-比较-写"不可分割。x86 的实现机制有两种：**总线锁**（LOCK 前缀，锁住整个总线，代价大）与**缓存锁**（锁住缓存行，利用 MESI 的独占状态，代价小——现代 CPU 基本都用缓存锁）。软件侧：Java 的 Atomic 类、LongAdder、ConcurrentHashMap 的 CAS 路径全是这条指令；自旋锁"原地重试"策略成立的前提是 CAS 足够快（纳秒级）——但竞争激烈时 CAS 重试也吃总线与缓存行，这正是 07 篇"锁升级"的出发点。

## 7. JMM 与硬件内存模型：Java 如何翻译硬件

JVM 把各种硬件的内存模型（x86 的 TSO、ARM 的弱内存序）统一成 **JMM**：happens-before 规则 + volatile/synchronized 的语义，编译器与 JIT 在"JMM 保证不破坏"的约束下自由优化。关键映射：**x86 是 TSO（总存储序）**——读不重排过写、写写不重排，所以 x86 上很多在其他架构会出错的代码碰巧能跑对；**ARM/AArch64 是弱模型**——几乎什么都能重排，同样的 Java 代码在 ARM 上更容易暴露并发 bug。JMM 的价值正在于此：**把"每类硬件允许的重排"抽象成一条跨架构的契约**——你不需要记住 TSO 与弱模型的差别，只需要遵守 JMM 规则；这也解释了为什么"在本机 x86 上测不出的并发 bug，上 ARM 云服务器就崩了"。

> 🎯 **核心要点**：从缓存行到 JMM 是一条因果链——**缓存行决定搬运粒度（64B）、MESI 决定可见性（失效-重读）、写缓冲决定为什么需要屏障、CAS 决定锁的原子起点、JMM 决定 Java 跨架构的契约**；软件侧的全部落点是三条：追求局部性（快）、警惕伪共享（慢得隐形）、无条件遵守 JMM（正确性不可商量）。
