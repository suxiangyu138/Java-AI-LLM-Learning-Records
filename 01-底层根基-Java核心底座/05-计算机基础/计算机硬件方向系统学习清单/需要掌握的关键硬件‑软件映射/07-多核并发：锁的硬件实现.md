# 多核并发：锁的硬件实现
> synchronized 与 Lock 不是 JVM 的发明，而是"原子指令 + 缓存一致性 + 内核调度"三件硬件/系统原语的封装；看懂锁的硬件层级，才能回答"为什么锁竞争会拖垮吞吐"。

## 1. 原子操作：并发的最底层砖块

并发正确性的最小单元是"读-改-写不可分割"。硬件提供的原子操作：**原子指令**（x86 的 XCHG、CMPXCHG、ADD 等带 LOCK 前缀的变体）、**原子读/写**（对齐的 32/64 位访问天然原子）。JVM 的 AtomicInteger/AtomicLong、synchronized 的进入、ConcurrentHashMap 的扩容协助，全部落到这几条指令上。一个重要的硬件细节：**原子指令在"读"与"写"之间独占缓存行**（见 03 篇 MESI）——CAS 竞争的本质是缓存行的"ping-pong"：两个核反复把同一缓存行抢来抢去，内存总线与一致性流量成为瓶颈，这就是"高竞争 CAS 比锁还慢"的物理原因。

## 2. 缓存锁与总线锁：LOCK 前缀的两副面孔

x86 的 LOCK 前缀（锁住"读-改-写"）有两种实现：**总线锁**（LOCK# 信号锁住整个内存总线，其他核完全无法访问内存——粗暴但保证原子）与**缓存锁**（锁住缓存行，利用 MESI 的 Modified/Exclusive 状态——现代 CPU 几乎都走这条）。软件侧推论：**原子操作的成本不是固定的**——缓存锁时（低竞争）约几十周期，升级为总线锁或缓存行 ping-pong 时（高竞争）可以慢一个数量级。这就是为什么无锁算法只在"竞争低、临界区短"时赢：**无锁不是免费，而是把成本从"线程挂起"换成"缓存行争用"**。

## 3. 自旋 vs 挂起：futex 的抉择

锁的两种等待策略：**自旋**（原地重试 CAS，占用 CPU 但无调度开销——适合临界区极短）与**挂起**（线程睡入等待队列，释放 CPU 但付出 2-5µs 的上下文切换——适合临界区长或竞争激烈）。Linux 的 **futex**（快速用户态互斥）把两者结合：先用户态原子尝试（快路径，无系统调用）；失败才进内核挂起（慢路径，一次 futex 系统调用）。这就是 synchronized 重量级锁的底层。工程判断：**临界区在纳秒-微秒级用自旋/无锁，超过就挂起**——Java 的 synchronized 与 JUC 锁已经自动分层，但"锁粒度"（临界区大小）永远是程序员自己的决策。

## 4. synchronized 的升级路径：一次硬件旅程的封装

HotSpot 的 synchronized 从 JDK 6 起有四级状态：**偏向锁**（单线程重复进入，无原子操作——用对象头标记所有者）、**轻量级锁**（多线程交替，用 CAS 抢对象头——自旋语义）、**重量级锁**（竞争激烈，升级为监视器锁——futex 挂起）、以及膨胀/撤销的来回路径。这条升级链的每一级都在回答"当前竞争程度下，哪种硬件原语最划算"：无竞争用偏向（零成本）、低竞争用 CAS（几十周期）、高竞争用 futex（放弃 CPU 换公平）。调优含义：**锁的性能问题先看竞争度**（JFR/JMC 的锁分析），竞争高时改"锁粒度/锁分离"（分片、读写锁、无锁）比改 JVM 参数有效得多。

## 5. 无锁数据结构：ABA 与内存序

无锁队列（Michael-Scott）、无锁栈、原子计数器是高性能中间件（Disruptor、ConcurrentLinkedQueue、LongAdder）的骨架。三个硬件相关的坑：**ABA 问题**（CAS 比较时值"从 A 变 B 又变回 A"，比较会误判——用版本号/标记位解决）、**内存序**（无锁结构必须用带序的原子操作，x86 上 relaxed/acquire/release 大多编译成普通指令，但 ARM 上语义必须精确——这就是为什么无锁代码"在 x86 测不出问题"）、**伪共享**（03 篇——无锁结构的头尾指针/计数器的缓存行布局直接决定吞吐）。Disruptor 的 ring buffer 之所以快，本质是"预分配数组 + 无锁 + 缓存行填充"三件事的合成。

## 6. 伪共享实战：并发容器的缓存行设计

回到 03 篇的伪共享，看它在并发容器的真实形态：LongAdder 的 cells 数组（每个 cell 用 @Contended 填充 64 字节——让每个线程的计数器独占缓存行，彻底消除争用）；ConcurrentHashMap 的 counterCells（同款设计）；Disruptor 的 Sequence 对象（填充到 128 字节）。设计共识：**热字段每线程一份 + 各自独占缓存行 = 无争用**——"空间换并发"的硬件版。用 `-XX:-RestrictContended` 或工具（JOL、perf c2c）验证伪共享是进阶手段，但"热字段别挨着"应该是默认意识。

## 7. 从锁到架构：并发性能的硬件账本

把全篇合起来得到并发调优的决策顺序：**先看竞争是否存在**（锁分析/火焰图的锁热点）→ **竞争低：自旋/无锁/偏向**（微秒内临界区）→ **竞争高：拆粒度**（分片锁、读写锁、Striped 锁、每线程一份）→ **仍不够：改架构**（事件驱动消除共享态，见 04 篇）。一句总纲：**并发性能问题的本质是"共享数据的访问模式"问题，锁只是放大器**——缓存行争用（伪共享/CAS ping-pong）与调度（futex/上下文切换）是两笔不同的账，前者靠布局解决，后者靠粒度解决。

> 🎯 **核心要点**：锁的硬件实现是三层原语——**原子指令**（CAS 的砖）、**缓存一致性**（缓存锁 vs 总线锁，竞争即缓存行 ping-pong）、**futex**（自旋 vs 挂起的抉择）；synchronized 的升级路径就是"按竞争度选原语"的自动化；工程上的全部智慧浓缩为一句：**先消除共享（每线程一份、事件驱动），再谈锁的效率（粒度、无锁、缓存行布局）**。
