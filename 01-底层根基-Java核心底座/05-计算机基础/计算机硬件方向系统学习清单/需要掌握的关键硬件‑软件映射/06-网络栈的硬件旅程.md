# 网络栈的硬件旅程
> 一个网络请求从对端进程到你的应用代码，要穿过对端协议栈、网卡、交换机、再穿过你的网卡与协议栈——每一跳都有物理成本；P99 之所以难降，是因为长尾不在代码里，而在这些"旅程"的排队中。

## 1. 数据包的硬件旅程

数据包从网线到应用的全路径：网卡（PHY 收信号 → MAC 帧校验）→ 网卡 DMA 把数据写进内核的**环形缓冲区**（ring buffer，免 CPU 搬运）→ 硬中断唤醒 CPU → NAPI 收包、协议栈逐层处理（L2 以太网 → L3 IP → L4 TCP/UDP）→ 放入 socket 接收队列 → 应用 read 取走。两个关键设计：**DMA 让数据不进 CPU**（拷贝归内存控制器管）、**环形缓冲区是内核-网卡的共享队列**（生产者网卡、消费者内核）。软件侧结论：网络收发的 CPU 大头不在搬运而在协议处理——TCP 的确认、重传、拥塞状态机、socket 锁与队列管理，这部分 CPU 与业务无关（04 篇的 si 软中断）。

## 2. 中断聚合与 RSS：别让收包打满 CPU

每个包一个硬中断会打满 CPU，于是有三件套：**中断聚合**（网卡攒一批再中断）、**NAPI**（轮询代替中断，高负载下更高效）、**RSS 多队列**（网卡按哈希把不同连接散到多个队列/多个核，避免单核收包瓶颈）。软件侧的可观察物：`ethtool -l` 看队列数、`top` 的 si 占比、`/proc/interrupts` 看中断分布——**网卡队列数 < 核数时，收包热点会集中到少数核**，这是"CPU 占用不均"的隐藏原因之一。容器与虚拟化环境还要叠加 vhost/DPDK 的取舍（虚拟化收包再贵一层）。

## 3. TCP 的时延构成：物理极限在哪

一次 TCP 请求的时延账本：**RTT**（光速+排队，同城 0.5-1ms、跨洋 100-200ms——这是物理极限，任何调优改不了）、握手（新连接 +1.5 RTT，所以连接池/HTTP 复用价值巨大）、拥塞窗口爬升（慢启动，短连接低效）、重传（丢包惩罚=重传超时，动辄几十 ms——对 P99 是灾难）、Nagle/延迟 ACK 交互（小包被拖 40ms 的经典坑）。工程含义：**时延优化的天花板是 RTT，能优化的是"请求次数、连接复用、丢包率"**——跨地域调优先看 RTT 再看代码，是本篇最直接的建议。

## 4. socket 与 fd：连接数的真正瓶颈

每个 TCP 连接在服务端对应一个 socket 文件描述符（fd）+ 内核缓冲（收发各几十 KB）+ 协议控制块。连接数的三个瓶颈：**fd 上限**（ulimit -n，默认 1024 → 生产 65535+）、**内存**（10 万连接 × 收发缓冲 ≈ 数 GB 内核内存）、**epoll 管理效率**（万级连接对 epoll 无压力）。软件侧结论：高连接数场景（网关、推送、长连接）预算顺序是 fd → 内核缓冲内存 → CPU；"连接数百万"不是神话但也不是免费——每连接几十 KB 的账要算清楚。Java 侧注意：每线程栈内存与连接数无关（NIO），但 DirectBuffer 池与 fd 泄漏是两大经典事故源——"连接数没涨、fd 数涨"就是 NIO selector 泄漏的典型信号。

## 5. 协议栈卸载：把活交给网卡

现代网卡内置硬件加速：**TSO/GSO**（大段卸载——应用发 64KB，网卡拆成 MSS 分片，省 CPU 拆包）、**LRO/GRO**（收包聚合）、**Checksum 卸载**（校验和由网卡算）。软件侧：这些默认开启、一般无需配置，但要认识它们的副作用——抓包时看到的"大包"其实是 TSO 的效果，分析时必须关卸载或用 tcpdump 的对应选项；某些虚拟化/容器环境卸载不可用，CPU 成本会高出可见的比例。

## 6. 容器网络：额外跳数的代价

容器（K8s）的网络路径比宿主机多一跳：Pod → veth 对 → 网桥/OVS → （可选）iptables/ipvs/NAT → 宿主机网卡。多跳带来的成本：**额外的 CPU 处理**（每一跳都是内核包处理）、**NAT 的 conntrack 表**（高并发下连接跟踪表是热点与容量风险）、**iptables 规则匹配**（规则多则线性开销）。工程含义：K8s 高吞吐场景优先 ipvs（转发模式，哈希查找）而不是 iptables NAT；同节点 Pod 互访走本地网桥（快）；**跨节点流量先问 CNI 模式再问网络性能**——2026 年的 eBPF CNI（如 Cilium）把转发路径从"链式规则"改成"内核直通"，是容器网络性能的主流答案。

## 7. 为什么 P99 难降：长尾的共振

P99 的组成往往是"多个慢事件叠加"：网络排队（交换机突发）、GC 停顿（毫秒级，08 篇）、锁等待（07 篇）、连接池耗尽（排队理论：利用率超过 70% 后排队时延指数上升）、重传（偶发）。**长尾的数学本质是排队论**：利用率 90% 时平均等待是 10% 时的约 9 倍——"P99 突刺"通常不是某个 bug，而是资源利用率逼近临界点的系统性表现。另一个长尾来源是 GC 与网络的互扰：JVM 的 Stop-The-World 期间所有在途请求排队，P99 出现"周期性台阶"——低延迟系统要么用 ZGC 类亚毫秒 GC（08 篇），要么把 GC 频率与流量峰值错开。降 P99 的三个抓手：**降利用率**（扩容/削峰）、**拆大请求**（减小单请求跨度）、**隔离慢路径**（独立线程池/限流，防止一个慢依赖拖垮全局）——它们都直接作用于排队模型。

> 🎯 **核心要点**：网络栈的硬件旅程给后端三条硬约束——**DMA 与中断聚合决定收包 CPU**（RSS 多队列分摊）、**RTT 决定时延天花板**（优化只能压缩握手与重传）、**排队论决定 P99**（利用率越高尾巴越长）；容器网络与协议栈卸载是 2026 年两个"多一跳/少一活"的工程旋钮——理解了旅程，才能判断 P99 该查网卡、查内核还是查业务。
