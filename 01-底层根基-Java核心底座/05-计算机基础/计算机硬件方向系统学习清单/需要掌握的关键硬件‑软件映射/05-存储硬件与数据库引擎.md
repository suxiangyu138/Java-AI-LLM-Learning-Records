# 存储硬件与数据库引擎
> 数据库的一切设计——页、WAL、B+树、LSM、刷盘策略——都是对"磁盘是什么"的回应；2026 年的答案是 PCIe Gen6 NVMe：随机访问快如内存、顺序访问快如闪电，但"掉电丢数据"的物理本性从未改变。

## 1. 存储层级：磁盘在时延阶梯的什么位置

完整时延阶梯（与 `内存墙/02` 同源）：L1 缓存 ~1ns → 主存 ~100ns → NVMe SSD ~10-100µs → 机械盘 ~5-10ms。注意三个量级差：**内存比 NVMe 快约 1000 倍**（所以 buffer pool 命中与否是百倍级性能差）、**NVMe 比机械盘快约 100 倍**（随机 I/O 尤其如此）、**一次磁盘 I/O（微秒-毫秒级）里 CPU 能执行数万条指令**——数据库"一次 I/O 尽量多干活"（页、批量）的全部动机。时延阶梯的工程含义：把热点数据的 10% 从磁盘搬进内存，等于把那部分访问的时延从微秒级降到纳秒级——**缓存（buffer pool/page cache/Redis）是性价比最高的硬件投资**，这条铁律决定了一切数据库架构的层级结构。

## 2. HDD vs SSD：机械运动的物理差异

机械盘的慢是物理的：寻道（磁头移动，~4-10ms）与旋转等待（~2-4ms）——**随机访问比顺序访问慢百倍**，所以机械盘时代的一切优化都在"把随机变顺序"（预读、批量、日志顺序写）。SSD 没有寻道，随机读与顺序读差距缩小到个位数倍——但**写放大**（擦除按块 4MB 级、写入按页 4-16KB）与磨损均衡带来新的物理约束：随机小写是 SSD 最贵的操作。软件侧的全部推论：**顺序写永远比随机写好**（对 HDD 是百倍、对 SSD 也是几倍），这个"磁盘第一定律"决定了 WAL、LSM、binlog 全部采用"只追加"形态。

## 3. NVMe 与 2026 数字：存储性能的军备竞赛

NVMe 协议（直连 PCIe、多队列、免 SATA 协议转换）让 SSD 从"慢速外设"变成"高速设备"。2026 年 PCIe Gen6 进入商用：Micron 9650 是首款量产 Gen6 企业盘（2026-02 官宣）——随机读 550 万 IOPS、顺序读 28GB/s（约为 Gen5 的两倍）；Kioxia GP1 系列（FMS 2026-08）宣称**1000 万随机读 IOPS**（512B 块、XL-FLASH Gen2 低延迟 NAND、50 DWPD，面向 AI 内存扩展层）；业界路线图指向 1 亿 IOPS。工程含义：**单盘 IOPS 已接近"不稀缺"**，瓶颈从盘转移到 CPU 与软件栈（每 IOPS 的内核开销）——2026 年做存储性能优化，先查协议栈与锁，再查盘。

## 4. 页缓存与 fsync：持久化的真相

写文件并不等于写磁盘：write() 只把数据放进**页缓存**（page cache），真正落盘靠后台刷写或显式 fsync。于是有三个持久化等级：进程崩溃不丢（数据在页缓存，OS 活着）、OS 崩溃不丢（已刷盘）、**掉电不丢（fsync 完成）**——数据库的"持久性"指的是第三级。fsync 的代价=强制一次（或多次）真实写盘+等待完成，这就是为什么"每条 SQL 都 fsync"的事务提交那么慢（单次 fsync 0.1-数 ms）。页缓存还有读的一面：读文件先查页缓存，命中则零磁盘访问——数据库的"第二次读快"、Kafka 重复消费快都是页缓存在兜底；页缓存回写策略（vm.dirty_ratio 等脏页阈值）是"磁盘突然卡一下"的隐藏旋钮，批量回写与业务流量叠加时就出现 IO 突刺。工程演化：**group commit**（多个提交合并一次 fsync）、**双写/redo 先行**（MySQL 的 redo log 先落盘再改数据页）、SSD 的掉电保护电容（企业盘把"正在写的页"扛过去）——所有机制都在回答同一个问题：怎么在"少 fsync"与"掉电不丢"之间取平衡。

## 5. WAL 与刷盘策略：日志先行为什么赢

Write-Ahead Logging 的全部逻辑一句话：**随机小写太贵，先把它变成顺序大写的日志**。事务提交时只追加 redo log（顺序写，快），数据页的随机写推迟到后台批量合并（checkpoint/脏页刷写）。MySQL 的参数体系（innodb_flush_log_at_trx_commit=1/2、sync_binlog、doublewrite）本质是"fsync 频率与一致性等级"的旋钮：=1 每次提交 fsync（最安全最慢）、=2 每秒 fsync（OS 崩溃丢 1 秒，快 10 倍）——**生产选 1 还是 2，是"持久性承诺"与"吞吐"的取舍，不是配置洁癖**。2026 年 NVMe 时代 =1 的代价大幅下降（fsync 从 ms 级降到几十 µs），"全同步"重新变得可负担——硬件进步直接改写最佳实践。

## 6. B+树 vs LSM：数据结构如何迎合磁盘

B+树：面向"随机读要快"——数据有序放页里，点查一次树高（3-4 层=3-4 次 I/O）；代价是随机写会打散页（页分裂/页搬家），写入放大。LSM-Tree：面向"写入要快"——只追加到内存 memtable（顺序刷成 SSTable），后台 compaction 合并；代价是读要查多层（读放大）、点查可能多次 I/O，靠布隆过滤器缓解。**选型的硬件依据**：读多写少用 B+树（MySQL InnoDB）、写多读少用 LSM（RocksDB/Cassandra）；NVMe 时代两者的读写放大代价都被压缩，但"随机读 vs 顺序写"的物理权衡没有消失——只是阈值移动了。

## 7. 数据库配置的硬件依据

一组"配置-硬件"对照，用于理解而不是背参数：buffer pool 大小（能装进内存的热数据才是热的，其余靠 SSD 兜底——2026 年"大缓冲池 vs 高速盘"是两个预算方向）；innodb_page_size 与 SSD 4K/16K 对齐（页对齐减少读放大）；io_uring 支持（MySQL/Percona 8.x 与 MariaDB 可用——把提交与刷盘批量交给内核）；DWPD（每日整盘写入次数，写放大越高的负载越要吃高 DWPD 盘）；**随机 IOPS 预算**（QPS × 每次操作 I/O 数 = 需要的盘规格——先用公式算，再买盘）。

> 🎯 **核心要点**：存储与数据库的映射是一句话的家族史——**磁盘物理（寻道/擦除/掉电）→ 顺序写优先（WAL/LSM/追加日志）→ 随机读定价（B+树/缓冲池/页）→ fsync 是持久性的真相（group commit/双写）**；2026 年的 NVMe Gen6（数百万 IOPS）没有推翻任何一条原理，只是把"随机 I/O 很贵"的阈值推远了几倍——理解原理，新硬件永远只是"数字变一下"。
