# 系统调用与 I/O 模型
> I/O 慢的真正成本不在"读磁盘/收网络"本身，而在系统调用、内核态切换与等待机制——高并发架构的每一层设计（线程池、事件循环、零拷贝）都是在跟这三个成本博弈。

## 1. 系统调用：为什么"进一次内核"这么贵

read/write/send/recv 都是系统调用：用户态 → 内核态 → 执行 → 返回用户态。一次系统调用的典型成本 0.5-2µs（2026 年 x86 服务器），但**真实代价不在 CPU 时间，而在副作用**：模式切换要刷新部分 TLB、破坏流水线、可能触发缓存污染；syscall 指令本身（x86 的 syscall/sysret）虽快，但内核路径上的锁、调度、内存拷贝叠加后量级可观。工程含义：**单次 I/O 的操作次数（每秒系统调用数）是比"字节数"更硬的性能指标**——10 万 QPS 的业务若每请求 10 次系统调用就是 100 万次/秒，CPU 的很大一部分就烧在"进出内核"上。

## 2. 中断与软中断：硬件事件怎么进入软件

网卡收到数据包、磁盘完成 DMA 后，硬件通过**中断**通知 CPU（打断当前任务，执行内核处理函数）；为防高频中断把 CPU 打满，Linux 引入**软中断**（softirq/NAPI）：硬中断只做最小收尾，重活（协议栈处理）推迟到软中断批量执行，网卡也支持中断聚合（一次中断收多个包）。软件侧可见的现象：高 PPS 下 `top` 里 si（软中断）飙高、单核软中断热点——它说明"网络处理本身"吃掉了 CPU，而这部分 CPU 与业务代码无关、难以通过调业务优化，只能靠网卡卸载（第 4 节）与多队列（RSS，多核分担收包）缓解。

## 3. 阻塞 I/O 的代价：线程在"等"

阻塞模型下每个连接一个线程，线程在 read 上睡死（进程被移出运行队列，上下文切换约 2-5µs 且逐次累积）。线程 = 栈内存（默认 1-8MB 虚拟、实际数百 KB）+ 调度成本，于是"1 万连接 1 万线程"直接击穿内存与调度器——**这就是高并发 I/O 的第一课：不能让线程等于连接**。C10K 问题（2000 年前后的经典工程问题）的所有解法——多路复用、事件驱动——都是在拆掉"一线程一连接"的等式。

## 4. 多路复用：从 select 到 epoll

事件多路复用让一个线程"同时等"成千上万个 socket：select/poll 每次调用把全部 fd 集拷进内核、线性扫描（O(n) 且 1024 上限）；**epoll**（Linux）用内核事件表 + 就绪队列：注册一次（epoll_ctl）、等待就绪（epoll_wait 只返回有事件的 fd，O(事件数)）。这就是 NIO 与 Netty 的底层：Netty 的 EventLoop 线程 = 一个 epoll_wait 循环——"事件到了处理，没到就挂起"，单线程撑数万连接（并叠加多路复用 + 非阻塞 + 零拷贝）。epoll 的三件配套事实：水平触发 vs 边缘触发（Netty 默认水平）、惊群问题（SO_REUSEPORT 分担）、fd 上限（ulimit，连接数瓶颈之一是文件描述符）。

## 5. 五种 I/O 模型的硬件观

阻塞、非阻塞、多路复用、信号驱动、异步 I/O（AIO）——五种模型唯一的区别是"谁在等、等的时候线程干什么"：阻塞（线程等）、非阻塞（轮询，线程忙转）、多路复用（内核等，就绪通知）、信号驱动（内核等，信号通知）、异步（内核等 + 内核做，完成后通知）。2026 年 Linux 的异步答案主要是 **io_uring**（替代 AIO）：提交队列与完成队列环形共享内存，一次系统调用提交一批 I/O，完成由内核写回队列——把"每次 I/O 一次 syscall"降为"批量一次"，Java 侧 Netty 的 io_uring transport 已可用（Windows 的 IOCP 对应物）。选型认知：**同步多路复用（epoll）仍是 95% 场景的答案，io_uring 是压榨极端吞吐的进阶项**。

## 6. NIO/Netty 的硬件观：把"等"变成"收"

Netty 架构的三个设计全是硬件成本驱动的：**EventLoop 单线程串行**（避免多线程争缓存行与锁，用单线程换取无锁与局部性）；**堆外内存池**（DirectBuffer 直接给内核 DMA 用，免去堆内→堆外拷贝，ByteBuf 池化免 GC）；**零拷贝**（FileRegion/sendfile——文件发送从"用户态读+写"变成"内核态一次 DMA"，见下节）。这些设计对应的硬件事实是：缓存行争用、内存拷贝带宽（10Gbps 网卡满速约 1.25GB/s，一次多余拷贝就能吃掉可观带宽）、以及 GC 停顿对 I/O 时序的破坏。

## 7. 零拷贝：数据少搬一次

普通读-写路径：磁盘/网卡 → 内核缓冲（DMA）→ 用户缓冲（CPU 拷贝）→ 内核缓冲（CPU 拷贝）→ 网卡（DMA）——四次拷贝两次 CPU。**零拷贝**的目标是让数据在内核里直达：sendfile 从文件到 socket 只经过内核（DMA 两次，零 CPU 拷贝）；mmap + write 少一次用户态拷贝；io_uring 的固定缓冲进一步复用注册内存。软件侧落点：文件下载/代理转发这类"数据不过业务"的路径用 sendfile/FileRegion（Netty 已封装）；**零拷贝的收益是带宽与 CPU 双收**——高吞吐传输场景差异可达 30%+ CPU。

## 8. 高并发系统的第一课

把四条成本线合起来得到后端 I/O 架构的总纲：**系统调用次数要少**（多路复用 + 批量）、**等待不能占线程**（事件驱动）、**拷贝不能重复**（零拷贝 + 堆外）、**中断不能打满 CPU**（NAPI/聚合 + RSS 多队列）。Netty、Kafka、Redis（单线程事件循环）、Nginx 全部是这四条的实践者——看懂任何一款的高性能设计，都会发现它只是在"硬件成本清单"上逐个打勾。

> 🎯 **核心要点**：I/O 的硬件账本是三笔：**系统调用**（每次 0.5-2µs 但量级会叠加）、**等待**（阻塞线程的调度与内存成本）、**拷贝**（带宽被 CPU 拷贝吃掉）；架构层的答案一一对应：多路复用（省系统调用与线程）、事件循环（消灭阻塞）、零拷贝/堆外（省拷贝）——Netty 与 io_uring 的每个特性都能在这三笔账上找到出处。
