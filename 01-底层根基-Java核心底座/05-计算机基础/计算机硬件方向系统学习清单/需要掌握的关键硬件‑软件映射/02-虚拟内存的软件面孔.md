# 虚拟内存的软件面孔
> 每个进程都以为自己独占 64 位地址空间——这是 MMU 与页表变出的魔术；malloc 不分配内存、new 不分配内存，真正的分配发生在第一次访问的那个瞬间。

## 1. 虚拟地址与物理地址：一场精心设计的骗局

每个进程看到的地址空间（Linux 下低地址是代码/数据/堆、向上是共享库、顶部是栈）都是**虚拟地址**，与物理内存没有一一对应关系。CPU 访问任何地址都要经过翻译：虚拟地址 → MMU（内存管理单元）→ 物理地址。这套"骗局"带来三个软件侧的关键收益：**隔离**（进程 A 的地址 0x1000 与进程 B 的毫不相干，恶意/错误的越界访问无法碰别人的内存）、**超卖**（物理内存只有 16GB，却能同时运行几十个各占 4GB 空间的进程）、**懒加载**（分配地址不占物理页，用到才给）。理解"虚拟 ≠ 物理"，才能理解为什么"内存占用 4GB"的 Java 进程实际物理占用可能只有 2GB，反之亦然。

## 2. MMU 与 TLB：翻译的硬件路径

每次内存访问都查一次"虚拟→物理"映射表（页表）会慢到不可用——页表在内存里，等于每次访问多一次内存访问。两级硬件缓存解决这个问题：**TLB**（翻译后备缓冲）把最近用过的翻译结果缓存在 CPU 内，命中则零额外开销；MMU 负责查表与权限检查。TLB 的条目数有限（典型每核 64-1536 项），每个条目覆盖一页（通常 4KB）——所以**进程的工作集越大，TLB 缺失越多，地址翻译本身就成了瓶颈**。这就是大页（2MB/1GB 页）的全部意义：一个条目覆盖 512 倍地址，TLB 命中率大幅提升——MySQL buffer pool、JVM 堆这类大内存场景，大页的收益可到几个百分点。大页还有一个隐藏收益：页表树矮一层（2MB 页直接跳过 PMD 之下的层级），翻译本身的访存也减少了。

## 3. 页表与多级结构：为什么地址翻译要"分层"

现代页表是 4 级（x86-64 的 PGD/PUD/PMD/PTE）或 5 级（加 P4D）树状结构：虚拟地址的位段逐级索引，叶节点 PTE 才真正指向物理页并带权限位。多级的好处是**稀疏**——进程用了 1GB 堆，不需要为未使用的 63GB 地址建表；坏处是翻译要多次查表（4-5 次内存访问）——这正是 TLB 存在的第二个理由。2026 年的补充：页表的大小与遍历也吃内存带宽，超大内存机器（几百 GB 堆）上页表本身可达 GB 级，某些场景用 2MB 大页顺带把页表体积缩小 512 倍。

## 4. 页错误：缺页的代价有多大

访问一个"地址已分配、物理页还没有"的页面时，CPU 陷入缺页异常（page fault），由内核分配物理页、填页表、返回继续执行。缺页分两类：**minor fault**（物理页在，只差映射，微秒级）与 **major fault**（页面要从磁盘读回，毫秒级——这就是"冷启动慢"与"换出后访问慢"的硬件真相）。软件侧的关键认知：**首次访问堆内存、冷启动加载类文件、JIT 编译产物、mmap 文件首次读**，全部要过缺页；批量预热（启动时 touch 一遍）的本质就是提前把 major fault 变成 minor fault。用 `perf stat` 或 `/proc/PID/status` 的 minflt/majflt 可以直接观察。

## 5. malloc/new 的硬件旅程

malloc 与 Java 的 new 都"不分配内存"——malloc 大多时候只是从堆管理器拿一段已映射的虚拟地址（brk/sbrk 扩展堆，或 mmap 大块），new 也只是从 JVM 堆里划一块（JVM 启动时已一次性 mmap 大虚拟区）。真正的物理页分配发生在**首次写入**时：触发缺页 → 内核给零页 → 标记脏。三个推论：批量 new 大对象快的假象（物理分配被延迟了）；`-Xmx` 设多大都不立刻占物理内存；`/proc/PID/smaps` 的 RSS 才是真占用。这也解释了 JVM 为什么偏爱"一次性保留大虚拟区"——减少系统调用与页表操作。同一个机制还支撑着 mmap 文件映射：文件内容直接映射进地址空间，读写像内存操作，缺页时内核从文件读入——数据库与 Kafka 的页缓存利用、Java NIO 的 MappedByteBuffer 全建立在这条路径上，也是 05 篇 fsync 语义的伏笔。

## 6. 大页与透明大页：TLB 覆盖率的工程意义

大页两条路：**显式 HugeTLB**（系统预留 2MB/1GB 页池，应用通过 mmap 标志指定）与 **THP**（透明大页，内核自动把 mmap 大区域升级为大页，2026 年默认开启 madvise 模式）。收益是 TLB 命中率（上文）；代价是碎片化——大页分配失败时会回退或触发 compaction（可造成偶发抖动），数据库/容器场景常见"开了 THP 反而慢"的报告，因此很多生产系统用 madvise 模式或关闭。Java 侧：`-XX:+UseLargePages` 让 JVM 堆用大页，GC 的标记位图也受益于 TLB 命中。

## 7. OOM 与容器限制的硬件真相

Linux 的内存回收链条：页缓存可丢弃 → 匿名页可换出（swap）→ 还不成就 OOM Killer。容器（cgroup）的内存限制只是在链路上加了一道闸：超过 limit 时先回收再 OOM——这就是容器内 Java 进程被"杀掉"而宿主机没满的真实机制。软件侧对策：Java 的堆外内存（DirectByteBuffer/元空间/线程栈/JIT 代码）不计入 -Xmx 却计入容器配额，2026 年容器内 Java 调优的标准是"堆 + 堆外总预算 < limit 的 80%"；`-XX:+UseContainerSupport`（JDK 8u191+/10+）让 JVM 按容器配额自动算堆大小，但堆外仍需人工预算。

> 🎯 **核心要点**：虚拟内存的软件面孔是四层"错位"——**虚拟≠物理**（隔离与超卖）、**分配≠占用**（懒分配，首次写入才给页）、**映射≠读取**（major fault 的毫秒代价）、**堆≠全部**（堆外内存同样吃容器配额）；工程上能直接落地的手段只有两件：大页提高 TLB 命中、预热把 major fault 变 minor fault——其余都是认知，但认知决定排查方向。
