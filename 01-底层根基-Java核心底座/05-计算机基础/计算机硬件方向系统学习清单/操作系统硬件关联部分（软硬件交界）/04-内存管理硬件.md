## 1. MMU：虚拟地址的翻译官

**MMU（Memory Management Unit）** 是 CPU 内的硬件单元，职责一句话：**把 CPU 发出的虚拟地址翻译成物理地址**。

| 概念 | 说明 |
|------|------|
| 虚拟地址（VA） | 程序看到的地址（每个进程独立、连续、从 0 开始） |
| 物理地址（PA） | 实际访问 DRAM 的地址 |
| 页（Page） | 分配/保护的最小单位，4KB（x86） |
| 页表（Page Table） | VA→PA 的映射表，存在内存中，由内核维护 |
| **MMU** | 硬件查表引擎，逐级遍历页表完成翻译 |
| **TLB** | MMU 内部的地址翻译缓存（快表） |

```text
CPU 访问内存时（每条访存指令都走）：
  VA ──► MMU 查 TLB ──命中──► 直接得 PA
                  │
                  └─未命中──► 逐级查页表（内存多读几次）→ 得 PA → 回填 TLB
```

> 💡 **记住两条铁律**：(1) CPU 访存的每一个地址都要过 MMU，所以"虚拟内存零成本"是错觉——翻译成本被 TLB 分摊到可忽略，但 TLB miss 很贵（见 3 节）；(2) **页表由内核维护、MMU 消费**——内核改页表后必须让 MMU 失效旧 TLB（这就是 TLB shootdown，见 3.2）。

## 2. 多级页表：x86-64 的四级/五级结构

### 2.1 为什么需要多级

单级页表（32 位时代）：2^20 个页表项 × 4B = **4MB 每进程**，且要连续分配——太浪费。多级页表按需分配，且天然支持稀疏地址空间。

### 2.2 四级页表（默认，48 位虚拟地址）

| 层级 | 名称 | 每个进程数量 | 粒度 |
|:---:|------|:---:|------|
| 顶层 | PML4（Page Map Level 4） | 1 个（512 项） | 512GB |
| 3 | PDPT（页目录指针表） | 512 个 | 1GB |
| 2 | PD（页目录） | 512² 个 | 2MB |
| 1 | PT（页表） | 512³ 个 | 4KB |
| 0 | 页（PTE 指向物理页） | —— | 4KB |

```text
虚拟地址 48 位拆分（每级 9 位索引 + 12 位页内偏移）：
┌─────────┬─────────┬─────────┬─────────┬────────────┐
│ PML4[9] │ PDPT[9] │ PD[9]   │ PT[9]   │ offset[12] │
└─────────┴─────────┴─────────┴─────────┴────────────┘
  CR3 寄存器指向当前进程的 PML4 表（进程切换时 CR3 换值！）
```

**进程地址空间大小**：48 位 VA = 256TB（内核一半 + 用户一半 = 各 128TB）。这个上限远超任何物理内存——**虚拟地址空间大 ≠ 物理内存大**，靠按需分配（demand paging）和换页支撑。

### 2.3 五级页表（LA57，57 位虚拟地址）

| 维度 | 四级（默认） | 五级（LA57） |
|------|:---:|:---:|
| 虚拟地址位宽 | 48 | 57 |
| 地址空间 | 256TB | 128PB |
| 页表额外层级 | —— | +1 级（PML5） |
| 启用 | 默认 | 需 CPU 支持 + 内核编译 `CONFIG_X86_5LEVEL` |
| 成本 | —— | 多一次访存、TLB miss 更贵 |

LA57 主要服务**超大内存机器**（如 1TB+ 内存的数据库/搜索集群）或需要超大稀疏地址空间的场景（如持久内存、超大 mmap）。2026 年生产环境仍以四级为主。

### 2.4 页表占用估算

一个进程若使用 1GB 连续虚拟内存（256 个 2MB 页或 262144 个 4KB 页）：

| 方案 | 页表内存占用 | 说明 |
|------|:---:|------|
| 4KB 页 | ~4MB（PML4+PDPT+PD+PT 全链） | 每 4KB 页要一个 8B PTE |
| **2MB 大页** | ~8KB（PD 项直接指向 2MB 页） | **省 500 倍页表空间** |

这就是大页的核心价值之一：**页表瘦身 + TLB 命中率暴涨**（见下）。

## 3. TLB：地址翻译的高速缓存

### 3.1 TLB 命中的价值

| 指标 | 数据（典型 x86） |
|------|----------------|
| L1 TLB（指令/数据分离） | 约 64-1536 项 |
| L2 TLB（统一） | 约 1024-2048 项 |
| TLB 命中 | 1 周期 |
| TLB miss（走页表） | 内存多读 4 次 = 几十周期 |
| 2MB 大页 TLB | 1 项覆盖 2MB（=512 个 4KB 页） |

```text
场景：顺序扫描 1GB 数据，4KB 页 vs 2MB 大页
  4KB 页：需要 262144 次翻译，TLB 反复 miss（每 64-256 项就换一轮）
  2MB 页：需要 512 次翻译，TLB 完全覆盖 → 扫描速度可提升 5-20%
```

### 3.2 TLB shootdown：多核下的"换页表广播"

进程切换/页面回收时，内核要改页表；**但每个核的 TLB 是私有的**——必须通知所有核失效对应项，这个跨核广播叫 **TLB shootdown**：

```text
CPU0: 想解除一页映射（如 madvise(DONTNEED)、munmap、进程退出）
  │ 发 IPI（处理器间中断）给所有在跑的核
  ▼
CPU1-7: 收到 IPI → 暂停当前执行 → 失效 TLB 该项 → 发确认
  ▼
CPU0: 收集确认后继续
```

> ⚠️ **Java 联动**：JVM 的 `-XX:+UseTransparentHugePages`、GC 后的内存释放、`Thread.stop` 清理、进程退出都会触发 TLB shootdown。**高核数机器（96/192 核）上，TLB shootdown 风暴是真实存在的性能杀手**——这也是大页（TLB 项更少→shootdown 更少）与 NUMA 感知（08 篇）的意义。

## 4. 大页：HugePages 与 THP

### 4.1 两种大页机制

| 机制 | 使用方式 | 特点 |
|------|---------|------|
| **HugeTLB（显式）** | 预分配 + `mmap(MAP_HUGE)` / Java `-XX:LargePageSizeInBytes` | 确定性最好，需提前配置、管理困难 |
| **THP（透明大页）** | 内核自动把连续页合并为 2MB 页 | 零配置，但有碎片化/停顿风险（khugepaged 后台合并） |

```bash
# 查看/配置大页（Linux）
grep Huge /proc/meminfo          # HugePages_Total/Free
cat /sys/kernel/mm/transparent_hugepage/enabled   # always/madvise/never
echo madvise > /sys/kernel/mm/transparent_hugepage/enabled
```

### 4.2 大页与 JVM（重点）

JVM 对大页的经典姿势：

1. **堆用 THP（madvise 模式）**：`-XX:+UseTransparentHugePages` 让 JVM 堆映射页标记 MADV_HUGEPAGE，由内核合并——**堆越大越值得**（8GB 堆用 2MB 页只要 4096 个 TLB 项）。
2. **HugeTLB 直接分配**：`-XX:LargePageSizeInBytes=2m` + 系统预分配 HugeTLB——Oracle 文档推荐大数据量应用，但需运维配合（预留内存、重启失效）。
3. **Java 17+ 的 ZGC/Shenandoah**：分代 ZGC 对内存布局敏感，大页能减少 GC 遍历的页表开销，但注意 THP 与 ZGC 的已知交互（早期版本有 bug，需测试验证）。

> ⚠️ **THP 的坑**：khugepaged 合并大页时要移动页（relocate），对延迟敏感应用可能引入毫秒级停顿；`always` 模式对数据库类应用曾有明显问题。2026 年实践：**数据库/搜索类应用倾向显式 HugeTLB 或 madvise 模式，吞吐类 Java 应用用 madvise+UseTransparentHugePages 组合**。

## 5. 内存保护：NX/SMEP/SMAP/KASLR

现代 x86 四层防线的硬件根基：

| 机制 | 硬件支撑 | 防什么 |
|------|---------|--------|
| NX（W^X） | 页表 NX 位 | 数据页不可执行 → 防 shellcode 注入 |
| SMEP | CR4.SMEP | 内核态禁止执行用户页 → 防 ret2usr 提权 |
| SMAP | CR4.SMAP | 内核态禁止读写用户页（除非 stac）→ 防内核读用户态数据 |
| KASLR | 启动时随机化内核/模块基址 | 防 ROP 定位 gadget |
| MPK（Memory Protection Keys） | PKRU 寄存器 | 用户态对页的分区访问控制（Intel 最新，Java 暂未用） |

```text
SMEP 工作示意：
  攻击者让内核跳转到用户态 gadget（ret2usr）
  CPU: 检查目标页 U/S 位 + SMEP 位 → #PF 拒绝执行 → 攻击失败
```

## 7. Java/JVM 联动

| JVM 参数/行为 | 硬件内存机制 |
|-------------|------------|
| 堆 8GB + UseTransparentHugePages | THP 合并为 2MB 页 → TLB 命中率提升 |
| `-Xmx` 与 RSS | 堆是 mmap 的匿名映射（MAP_ANONYMOUS），按需分配 → RSS < Xmx 常见 |
| GC 压缩/移动对象 | 触发大量页表写 + 潜在 TLB shootdown |
| `-XX:+AlwaysPreTouch` | 启动时强制触碰全部堆页 → 提前建页、避免运行时缺页抖动 |
| 元空间/代码缓存 | 各自独立的 mmap 区域，NX 位保护（Metaspace 不可执行） |
| 直接内存（DirectByteBuffer） | 内核外的堆外内存，常配合大页（`-XX:MaxDirectMemorySize`） |

> 🎯 **给 Java 开发者的一句话**：`-Xmx` 只是"地址空间承诺"，真实物理内存靠缺页按需供给（所以首次 Full GC 前 RSS 才爬满）；想让堆访问快，不是加内存而是让 TLB 命中率高——大页 + NUMA 亲和 + PreTouch 是三大杠杆。

### 7.1 x86-64 地址空间布局详解

```text
x86-64 Linux 进程虚拟地址空间（48 位，256TB）：
┌────────────────────────────────────────────────┐
│ 0x0000000000000000                             │
│   用户空间（低 128TB）：代码/堆/mmap 区/栈      │
│   布局：代码 → 数据 → 堆（向上增长）            │
│         → mmap 区（共享库/大块分配，向下）      │
│         → 栈（向下增长）→ 随机化守卫            │
├────────────────────────────────────────────────┤
│ 0x00007fffffffffff = 用户空间顶（128TB 边界）    │
├────────────────────────────────────────────────┤
│   内核空间（高 128TB）：直接映射区/vmalloc/      │
│   模块/固定映射——所有进程共享同一份内核映射      │
└────────────────────────────────────────────────┘
```

关键含义：

| 现象 | 解释 |
|------|------|
| 为什么 JVM 默认堆上限受"地址空间"限制 | 32 位只有 4GB；64 位 128TB 用户空间，堆想多大都行（受物理内存+overcommit 限制） |
| 为什么内核映射在用户页表里却有保护 | PTE 的 U/S 位=0（Supervisor），用户态访问触发 #PF |
| 为什么共享库地址每次启动都变 | ASLR 随机化 mmap 基址，防攻击者固定跳转地址 |
| 为什么 `0x7f...` 开头的地址常见 | mmap 区从用户空间顶部往下分配 |

### 7.2 缺页、COW 与 mmap 实战

| 场景 | 硬件路径 | 影响 |
|------|---------|------|
| **demand paging**（按需建页） | 首次访问未映射页 → #PF → 内核分配物理页 → 回填页表 | 堆首次访问慢，所以 `-XX:+AlwaysPreTouch` 预触 |
| **COW（写时复制）** | fork() 时父子共享页（只读映射），任一写 → #PF → 复制 | Java 的 `ProcessBuilder`/JVM fork 依赖它 |
| **mmap 文件** | 文件映射到地址空间，首次读也走 #PF（读磁盘） | `MappedByteBuffer` 内存映射 IO 的原理 |
| 页回收/swap | 内存压力 → 内核写回脏页 → 标记 PTE 无效 | `vm.swappiness` 参数控制倾向 |

```bash
# 观察缺页（major/minor fault）
ps -o minflt,majflt,cmd -p $(pgrep -f java | head -1)
grep -E "pgfault|pgmajfault" /proc/vmstat
```

> 💡 **Java 实战结论**：`MappedByteBuffer`（FileChannel.map）本质是 mmap——读文件第一次访问缺页，但**后续访问走页缓存直读，零系统调用**；这比 read() 每次进内核快一个数量级。代价是映射区域不受 JVM 堆管理、需手动处理未映射（Java 9+ 有 `Cleaner` 方案）。

### 7.3 页面回收与 swap 的硬件路径

```text
内存压力 → 内核回收（kswapd 后台 / 直接回收）：
  ① 优先回收干净页（文件缓存，直接丢弃）
  ② 脏文件页 → 写回磁盘（同步/异步）
  ③ 匿名页（堆/栈）→ swap 到交换分区/文件
  ④ 被回收页的 PTE 置无效 → 下次访问重新缺页
```

| 参数 | 默认 | 作用 |
|------|:---:|------|
| `vm.swappiness` | 60 | 倾向回收匿名页 vs 文件页（DB 常调低到 1-10） |
| `vm.min_free_kbytes` | 动态 | 保留的紧急内存 |
| `vm.vfs_cache_pressure` | 100 | 目录/文件缓存回收倾向 |

> ⚠️ **Java 部署教训**：JVM 堆是匿名页——内存不足时可能被 swap（包括堆的冷页），导致 GC 停顿加剧、延迟飙高。**Java 服务上生产必须关闭 swap 或用 cgroup 限制**（`vm.swappiness=1`、`swapoff` 或容器内存限额），并预留堆外内存（元空间/直接内存/线程栈）余量。

### 7.4 内存碎片与 THP 分裂

| 问题 | 机制 | 应对 |
|------|------|------|
| 外部碎片 | 大量 4KB 页交错，凑不出 2MB 连续区域 | THP 后台合并（khugepaged） |
| THP 分裂 | 写保护缺页时大页分裂为小页 | 内核保留 `hugezeropage`（不碎裂） |
| 分配延迟尖峰 | 大页分配要压缩内存（compact） | `vm.compact_memory`、`transparent_hugepage=never` 权衡 |
| 页迁移 | NUMA 均衡/合并时搬页 | 延迟敏感应用关闭 `numa_balancing` |

> 💡 **取舍认知**：THP 不是免费午餐——它用"后台合并的 CPU + 偶尔的分配延迟"换"TLB 命中率"。**吞吐型 Java 应用收益明显；延迟敏感（<1ms 目标）应用建议 madvise 模式并实测**。ZGC/Shenandoah 对大页的交互需压测验证，不能照搬 G1 经验。

### 7.5 大页选型决策表

| 场景 | 推荐 | 理由 |
|------|------|------|
| Java 大堆（≥4GB）吞吐型 | THP(madvise) + UseTransparentHugePages | 堆访问局部性好，TLB 收益大 |
| Java 延迟敏感（<1ms 目标） | madvise 模式 + 压测验证 | THP 合并/分裂可能引入停顿 |
| 数据库（MySQL/PostgreSQL） | 显式 HugeTLB（2MB） | 确定性最好，`vm.nr_hugepages` 预分配 |
| 大数据/搜索（ES） | HugeTLB 或 madvise | 段合并受益于大页 |
| 直接内存/MMAP 大文件 | `MAP_HUGE_2MB` 显式 | 一次映射省页表 |

### 7.6 内存管理面试追问

**Q1：进程的虚拟地址空间是 128TB，页表多大？**
答：取决于使用量——只用了 1GB（2MB 大页）= 约 8KB 页表；全用 4KB 页则 4MB+。多级页表按需建立，所以"大地址空间"不等于"大页表"。

**Q2：为什么说 TLB miss 很贵？**
答：一次 miss 要额外走 4 级页表（4 次内存访问，每次 ~80ns = 320ns），而命中只要 1 周期——差距 100 倍+。大页把 512 个 4KB 页合并为 1 个 TLB 项，直接消灭大部分 miss。

**Q3：THP 和 HugeTLB 有什么区别？**
答：THP 是内核自动合并/分裂（透明，有停顿风险）；HugeTLB 是管理员预分配、显式使用（确定，需管理）。延迟敏感场景选后者。

**Q4：为什么 Java 堆 RSS 小于 Xmx？**
答：Xmx 只是地址空间承诺；物理页按需分配（demand paging），首次触碰才缺页分配——所以"内存不够用"要看 RSS 而不是 Xmx。

**Q5：mmap 和 read() 读文件的区别？**
答：mmap 把文件映射进地址空间，访问走缺页从页缓存取（后续零系统调用）；read() 每次进内核拷贝到用户缓冲区。mmap 适合大文件随机读（MappedByteBuffer），read 适合小数据频繁读。

**Q6：SMEP 和 SMAP 分别防什么？**
答：SMEP 防"内核执行用户态代码"（ret2usr 攻击）；SMAP 防"内核读写用户态内存"（需显式 stac 才可）——两者让内核与用户数据之间建立"单向玻璃"。

**Q7：KASLR 为什么不能完全防 ROP？**
答：KASLR 随机化内核基址，但"信息泄漏"（如 /proc/kallsyms 未限制、侧信道读基址）可绕过；且随机熵有限（约 9-24 位）。所以现代防御是组合拳：KASLR + SMEP/SMAP + 栈随机化 + 后量子签名（启动链），任何单点都不绝对安全。

**Q8：5 级页表（LA57）什么时候有用？**
答：虚拟地址从 48 位扩到 57 位（128PB）——1TB+ 内存机器、超大稀疏 mmap（如大内存数据库）、持久内存场景受益；普通 8-32GB 机器用 4 级即可，5 级反而多一次页表访存。

**Q9：为什么页表本身要受 TLB 管理？**——页表在内存里，查页表也要访存（4 级=4 次）；现代 CPU 有"页表缓存"（Paging-Structure Caches）加速**逐级查表本身**，所以 TLB miss 后不是 4×80ns 而是约几十周期。理解这条，才明白"TLB miss 为什么比 cache miss 贵 5-10 倍"。

**收官清单**：学完本篇应能回答——① 页表为什么多级？② 大页为什么快（两条理由）？③ TLB shootdown 什么时候发生？④ SMEP/SMAP 防什么？⑤ Java 堆 RSS 与 Xmx 的关系？⑥ 5 级页表给谁用？六问全过即毕业，进入 05 篇进程切换与调度。

**延伸阅读**：与「内存墙」体系联动——本篇文章讲"地址怎么翻译"，内存墙讲"物理内存为什么慢"，两者合起来才是完整的内存世界。

**补充：怎么用 perf 验证大页收益**——`perf stat -e dTLB-loads,dTLB-load-misses` 分别跑 4KB 页与 2MB 页的程序，miss 率从百分之几降到千分之几、吞吐提升 5-20%，就是大页价值的直观证据。**调优要"先测量再改参数"，perf 是这类测量的标准工具**。

## 8. 核心要点

> 🎯 **核心要点**：MMU 是地址翻译硬件，多级页表（4 级默认/5 级 LA57）让映射按需存在；TLB 是翻译缓存，miss 要再访存 4 次——大页（2MB/1GB）一箭双雕：页表瘦 500 倍 + TLB 覆盖提升 512 倍；内核改页表要广播 TLB shootdown，高核机器上这是隐藏开销；NX/SMEP/SMAP/KASLR 构成现代内存安全四防线；JVM 调优的本质一半在 MMU/TLB 这几页上。
