## 1. 从单核到多核：缓存结构

现代 x86 三级缓存（L1→L3）+ 每核私有的 TLB：

```text
        ┌──────────── CPU 0 ────────────┐  ┌──────────── CPU 1 ────────────┐
        │ L1d 32-48KB（数据，私有）      │  │ L1d 32-48KB（私有）           │
        │ L1i 32-64KB（指令，私有）      │  │ L1i 32-64KB（私有）           │
        │ L2 1-2MB（私有）              │  │ L2 1-2MB（私有）              │
        └──────────────┬───────────────┘  └──────────────┬───────────────┘
                       └────── L3（共享，环形/网格总线）──────┘
                                      │
                                 内存控制器（NUMA 节点边界！）
                                      │
                                     DRAM
```

| 层级 | 延迟（典型 2026 x86） | 大小 |
|------|:---:|:---:|
| L1 | ~1ns（4 周期） | 32-48KB |
| L2 | ~4ns | 1-2MB |
| L3 | ~12-40ns（NUMA 远端更高） | 32-192MB |
| DRAM | ~80-100ns（本节点） | 512GB+ |

**多核并发的核心问题**：L1/L2 是私有的，CPU0 改了变量，CPU1 的私有缓存还存着旧值——谁来负责同步？→ 缓存一致性协议。

## 2. 缓存一致性：MESI/MOESI 协议

### 2.1 缓存行的四种状态（MESI）

| 状态 | 含义 | 独占性 |
|------|------|:---:|
| M（Modified） | 已修改，脏，仅本核持有最新值 | 独占 |
| E（Exclusive） | 未修改，仅本核持有 | 独占 |
| S（Shared） | 未修改，多核共享 | 共享 |
| I（Invalid） | 无效（本核视图过时） | —— |

x86 实际使用 **MOESI**（多了 O 状态：数据既被本核修改又在多核共享），ARM 用 MESI 变体。

### 2.2 一致性动作：总线嗅探与目录协议

```text
CPU0 写变量 x（x 在 CPU1 的 L1 是 S 状态）：
  ① CPU0 发 Read For Ownership（RFO）到一致性网络
  ② CPU1 嗅探到 RFO → 把 x 置为 Invalid 并回传数据
  ③ CPU0 获得独占权 → 写入 L1（标记 M）
  ④ CPU1 下次读 x → 发读请求 → CPU0 回传（M→S 转换）
```

**关键结论**：多核共享变量每次写都要一次"跨核通信"（RFO + 失效），这就是：
- **共享变量比私有变量贵一个数量级**；
- **cache line 是 64B 粒度**——不是按字节同步！(见 5 节伪共享)
- 分布式系统的一致性协议（Raft、Paxos）与此**结构同构**：都需要"失效-确认"达成共识，只是网络比总线慢 6 个数量级。

## 3. 原子操作：从 LOCK 前缀到 CAS

### 3.1 为什么 `i++` 不原子

```text
i++ 的机器码：
  mov eax, [i]    ① 读
  add eax, 1      ② 加
  mov [i], eax    ③ 写
CPU0 执行完 ①，CPU1 也执行完 ① → 两个核都 +1 但 i 只 +1（丢失更新）
```

### 3.2 硬件原子原语

| 机制 | 说明 | 例子 |
|------|------|------|
| **LOCK 前缀** | 锁住缓存行/总线，使"读-改-写"在硬件层不可分割 | `lock inc [i]`、`lock cmpxchg` |
| **CAS**（Compare-And-Swap） | 比较+交换，成功返回旧值 | `cmpxchg`（配合 LOCK） |
| **xadd**（Fetch-And-Add） | 原子加并返回旧值 | `lock xadd` |
| ARM/RISC-V | Load-Reserved/Store-Conditional（LL/SC）或原子扩展（LSE） | `ldaxr/stxr`、`cas` |

> 💡 **关键认知**：现代 x86 的 LOCK 操作多数**不锁总线**（总线锁极慢），而是**锁缓存行**（cache-line locking）——核内执行时向一致性协议宣告"该行临时独占"。RFO+锁定+回写是硬件自动完成的，所以"原子"的代价 = 一次跨核同步。

### 3.3 Java 侧的映射

| Java 原语 | 底层实现 |
|-----------|---------|
| `AtomicInteger.incrementAndGet` | `lock xadd`（Unsafe.getAndAddInt） |
| `AtomicReference.compareAndSet` | `lock cmpxchg` |
| `LongAdder` | 分散到多个 cell 避免共享行争用（对抗 5 节伪共享） |
| synchronized | monitor（重量级锁）→ 偏向/轻量锁用 CAS → 膨胀 |

## 4. 内存屏障：重排序的约束

### 4.1 重排序从哪里来

| 来源 | 说明 |
|------|------|
| 编译器重排 | 只要单线程语义不变，随便排（JIT 也会！） |
| CPU 乱序执行 | 只要不违背架构内存模型，流水线可重排 |
| 存储缓冲/写合并 | 写操作先进 store buffer，异步进入缓存 |

### 4.2 x86 内存模型与屏障指令

x86 是**强模型**（TSO：只有 StoreLoad 可重排；读读/写写/读写基本保序），但仍需要屏障：

| 指令 | 作用 |
|------|------|
| `mfence` | 全屏障：之前所有读写完成后才执行之后 |
| `lfence` | 读屏障 |
| `sfence` | 写屏障 |
| `lock` 前缀 | 天然全屏障（附带语义） |

ARM 是**弱模型**（随便重排），需要 `dmb ish` 等显式屏障——**同样的 Java 代码在 ARM 上需要更多屏障指令**（JVM 按平台生成）。

### 4.3 volatile 的硬件语义（JMM 视角）

```text
volatile 写（x86 实现）：
  mov [i], eax
  mfence   ← volatile 写 = 普通写 + 全屏障
volatile 读：普通读（x86 上读天然可见性够用）

volatile 的四条 JMM 规则落到硬件：
  写-写屏障：volatile 写前的东西不会乱序到写后
  读-读屏障：volatile 读后的东西不会乱序到读前
  → 本质是"在一个内存序点上给所有人看的快照"
```

> ⚠️ **常见误解**：volatile 不保证原子性（`volatile int i; i++` 依旧不是原子的）；synchronized 的锁关系（Lock 前缀 + 互斥 + 内存屏障）才是 JMM 全部保证的载体。

## 5. 伪共享：最隐蔽的性能杀手

### 5.1 问题定义

**两个线程操作不同的变量，但这两个变量恰好落在同一个 64B cache line 上** → 每次写入都触发对方缓存行失效 → 看起来是独立变量，实际在互相"打架"：

```text
class Counter {           // 两个线程各写一个字段
    volatile long a;      // 0x00-0x07
    volatile long b;      // 0x08-0x0F  ← 与 a 同在 64B 行内！
}
线程1 疯狂写 a，线程2 疯狂写 b
  → 每写一次 a，线程2 的缓存行被 RFO 失效
  → 每写一次 b，线程1 的缓存行被 RFO 失效
  → 两个线程互相拖慢 10-100 倍！
```

### 5.2 解决：补齐到 64B

| 方案 | 做法 |
|------|------|
| 填充（padding） | 变量前后加 56 字节无用字段，占满整行 |
| `@Contended`（JDK 8+） | JVM 注解，自动对齐（需 `-XX:-RestrictContended`） |
| `LongAdder` 内部 | 每个 cell 带 `@Contended`，按核分散 |
| 数据结构设计 | 读写分离：读多写少字段放一个行，写多字段独立行 |

```java
@Contended            // JVM 自动填充
static final class Counter {
    volatile long a;
    volatile long b;
}
```

> 🎯 **检测手段**：`perf stat -e cache-misses` 对比；Linux 6.x+ 有 perf 的 false-sharing 检测支持；最简单粗暴：把类拆开或加 padding 对比吞吐。

## 6. NUMA 与拓扑感知

### 6.1 为什么要有 NUMA

核数增多后，所有核共享一个内存控制器成为瓶颈 → 拆成多个"节点"，每节点有自己的内存：

| 访问类型 | 延迟 | 带宽 |
|---------|:---:|------|
| 本节点内存（Local） | ~80ns | 高 |
| 跨节点内存（Remote） | ~120-150ns（+40-70%） | 低 |

### 6.2 调度与分配策略

| 策略 | 动作 | 工具 |
|------|------|------|
| 绑定核 | 进程固定到某节点核 | taskset/numactl |
| 绑定内存 | 内存优先本节点分配 | numactl --membind |
| 交错（interleave） | 平均分布（牺牲局部性换均衡） | --interleave=all |

```bash
numactl --hardware        # 查看节点拓扑
numactl --cpunodebind=0 --membind=0 ./java -jar app.jar
```

> ⚠️ **Java 教训**：JVM 大堆（几十 GB）默认可能跨节点分配（首触分配策略）——高吞吐服务建议 `numactl` 绑定或 `-XX:+UseNUMA`（JVM 的堆按节点交错，减少远程访问）。Kafka/ES 等中间件文档里都有 NUMA 章节，不是玄学。

## 7. TSX 事务内存与 2026 现状

**TSX（Transactional Synchronization Extensions，Intel）**：硬件事务内存——把一段代码声明为事务，冲突则回滚重试：

| 机制 | 说明 |
|------|------|
| RTM（Restricted Transactional Memory） | 软件控制事务边界（xbgin/xend/xabort） |
| 硬件冲突检测 | 事务内缓存行被其他核改动 → 回滚 |
| 收益 | 无锁并发：读读不互斥，写冲突才回滚 |

**2026 现状**：TSX 在早期被爆幽灵/熔断相关漏洞后一度默认禁用；Linux 7.0 起对支持 TSX 的 CPU（如较新的至强）**默认 auto 模式**开启，用于加速特定工作负载。Java 侧没有直接 API（JEP 无 TSX 计划），但 `LongAdder`、无锁队列等结构未来可能受益于硬件事务。

## 8. Java JMM 的硬件映射

| JMM 概念 | 硬件对应物 |
|---------|-----------|
| 工作内存（JMM 术语） | L1/L2 私有缓存 + store buffer |
| 主内存 | L3/DRAM |
| 可见性 | 缓存一致性协议（MESI/MOESI） |
| 有序性 | 编译器/CPU 重排序 + 屏障 |
| 原子性 | LOCK 前缀 / LL-SC |
| happens-before | 屏障序列：lock 前缀、volatile 写后 mfence、线程启动/join 的同步点 |

```text
JMM 与硬件的翻译口诀：
  为什么需要 volatile？→ 因为 CPU0 改的是私有 L1，CPU1 还看着旧 L1
  为什么 CAS 慢？→ 每次是一次 RFO 跨核通信
  为什么 LongAdder 快？→ 把共享行拆成多行，避开伪共享
  为什么 64 核上无锁还是慢？→ NUMA 远程访问 + 一致性协议压力
```

### 8.1 锁的硬件实现：从自旋锁到 synchronized

| 锁层级 | 实现 | 硬件支撑 | 开销 |
|--------|------|---------|:---:|
| **自旋锁（spinlock）** | 原子指令忙等（test-and-set/CAS 循环） | LOCK 前缀 | ~20-100ns/次获取 |
| 读写锁 | 读计数原子 + 写互斥 | CAS | 读并发时最省 |
| **futex（内核锁）** | 原子快路径 + 睡眠慢路径 | 原子指令 + syscall | 无争用 ~25ns，争用走内核 |
| Java synchronized 膨胀链 | 偏向锁 → 轻量锁(CAS) → 重量锁(monitor/futex) | 同 futex | 无争用 ~30-50ns |

```text
synchronized 的硬件叙事：
  偏向锁：单线程重复进入 → 一次 CAS 记线程号
  轻量锁：多线程交替 → 栈上锁记录 CAS 成功即可
  重量锁：争用 → 对象头指向 monitor（内核 futex 队列）
  结论：无争用同步 ≈ 一次原子操作；争用才进内核
```

> 💡 **Java 调优启示**：锁优化的本质是"让争用不发生"——LongAdder 拆分、读写锁分路、无锁数据结构（CAS 单点）都是把"锁的硬件成本"压到最低。2026 年虚拟线程普及后，`synchronized` 的 pinning 问题倒逼生态转向 `ReentrantLock`（其底层同为 futex 系）。

### 8.2 伪共享实测方法

```java
// 实验：两个线程分别写两个相邻 long，观察吞吐
@Contended   // 去掉该注解对比性能
static class Pair { volatile long a; volatile long b; }

// 结果预期（x86, 8 核+）：
// 无 @Contended：吞吐暴跌 5-50 倍（同一 cache line 打架）
// 有 @Contended：恢复正常（各占一行）
```

| 检测手段 | 做法 |
|---------|------|
| perf 对比 | `perf stat -e cache-misses` 加/减 padding 对比 |
| perf c2c（Cache-to-Cache） | Linux perf 的伪共享检测专用工具（`perf c2c report`） |
| 代码审查 | 找"相邻字段 + 高频写"模式（计数器、状态位、时间戳放一起） |
| 黑盒经验 | 吞吐随核数增加反而下降 → 高度怀疑伪共享 |

> ⚠️ **边界**：`@Contended` 只在 JDK 内部可用（`-XX:-RestrictContended` 放开）；第三方代码用 Padding 类或字段间塞 56 字节 `long[]` 占位。**伪共享只在"高频写"场景致命**——读多写少的共享字段影响可忽略。

### 8.3 LongAdder 深潜：为什么它比 AtomicLong 快

| 结构 | 原理 | 争用行为 |
|------|------|---------|
| AtomicLong | 单变量 + CAS | 高争用时所有线程打同一个 cache line → 缓存行弹跳（bouncing） |
| **LongAdder** | 基值 + N 个 cell 数组（每个 cell 独立行） | 线程哈希到不同 cell → 各打各的行 → 几乎无争用 |

```java
// LongAdder 关键设计（JDK 源码简化）：
// 1. cell[] 每个元素用 @Contended 占满 64B（防伪共享）
// 2. sum() 时遍历所有 cell + 基值
// 3. 争用检测：CAS 失败才扩容 cells（惰性扩容）
// 适用：高频计数、读少写多（统计指标）；不适用：需要精确值的并发控制
```

> 🎯 **选择准则**：需要"读当前值"作为控制逻辑（如限流计数）用 AtomicLong；只需要"最终统计"（指标、频次）用 LongAdder——后者的 sum 是快照式，不适合判断"此刻是否超阈值"。

### 8.4 内存屏障在 JVM 中的落点：GC 写屏障

| JVM 组件 | 屏障形态 | 硬件动作 |
|---------|---------|---------|
| G1 写屏障 | 对象引用赋值时插入（pre/post） | 普通写 + 队列记录（无全屏障） |
| ZGC 读屏障 | 读引用时检查（load barrier） | 普通读 + 条件分支 |
| JIT 生成的 volatile | volatile 写后 mfence | **全屏障**（贵） |
| 卡表更新（CMS/G1） | 赋值后标记脏卡 | 写内存 + 无屏障（靠后续） |

```text
GC 写屏障的硬件现实：
  屏障 ≠ 一定用 mfence（那是万不得已）
  现代 GC 用"无屏障逻辑 + 原子队列"实现低开销写屏障
  但跨线程可见性仍依赖：队列元素 CAS（原子性）+ 消费端屏障
```

> 💡 **设计启示**：屏障是"正确性的最小成本实现"——GC 只在引用赋值点插桩，比 synchronized 全临界区便宜一个数量级；Java 开发者设计无锁结构时同理：**能少一个屏障就少一个**（用数据隔离替代同步）。

### 8.5 并发硬件面试追问

**Q1：volatile 保证可见性的原理？**
答：volatile 写 = 普通写 + 全屏障（x86 上是 mfence），屏障让之前的写全部刷出 store buffer，后续读可见；一致性协议保证其他核读到最新值。它不保证原子性——`volatile i++;` 仍要加锁/CAS。

**Q2：为什么 CAS 在争用高时反而慢？**
答：每次 CAS 都是一次 RFO 跨核通信 + 缓存行弹跳——所有线程打同一行，串行化。LongAdder 拆 cell 的原理就是"把争用分散到不同行"。

**Q3：内存屏障是做什么的？**
答：约束编译器和 CPU 的重排序——x86 是强模型（TSO，只有写后读会重排），ARM 是弱模型（都可重排），所以 ARM 上同样的 Java 代码需要更多屏障，JVM 按平台生成。

**Q4：伪共享怎么发现和解决？**
答：检测 perf c2c 或对比 padding 前后吞吐；解决 = 变量按 64B 对齐隔离（@Contended/padding/字段分结构）。

**Q5：NUMA 下为什么跨节点访问慢？**
答：内存控制器在节点本地，远端访问走节点间互联（延迟 +40-70%）——进程要"核和内存同节点"（numactl 绑定），JVM 用 UseNUMA 让堆按节点分布。

### 8.6 无锁编程设计清单

| 原则 | 硬件依据 | 反例 |
|------|---------|------|
| 共享数据最小化 | 一致性协议成本与共享面成正比 | 大对象无锁化 |
| 写者尽量唯一 | 单写者免 RFO 争用 | 多线程写同一变量 |
| 缓存行隔离写热点 | 64B 粒度伪共享 | 计数器紧挨着放 |
| 读多写少用读写分离 | 读读不争用 | 全用 CAS |
| 失败重试要有界 | 忙等占核 | 无限自旋 |
| 顺序消费用环形队列 | 单写单读免锁 | 复杂链表 |

> 🎯 **无锁的本质**：不是"没有同步"，而是"把同步从互斥锁换成原子指令+内存序约束"——原子指令保证正确性，屏障保证顺序，数据布局保证性能。三者缺一，无锁即无安全。

**Q6：x86 是强内存模型，为什么还需要 volatile？**
答：强模型只约束"单核可见的顺序"，不约束**跨核的可见性时机**——CPU0 写的数据可能还在 store buffer 里，CPU1 读旧值。volatile 的屏障把 store buffer 刷出（或读侧等待），保证"写完成后其他核可见"。所以"模型强"≠"无需同步"。

**Q7：ARM 弱模型下写无锁代码要注意什么？**
答：x86 上"看起来没问题"的代码到 ARM（Graviton、手机芯片）可能重排失效——必须用 JMM 语义（volatile/Atomic）而不是"碰巧顺序"；JVM 在 ARM 上会自动插入 dmb 屏障，但**手动写的 JNI/Unsafe 代码需要显式屏障**，这是跨架构移植的第一坑。

**Q8：缓存一致性协议能保证"读到最新值"吗？**
答：MESI 保证"任何时刻每个地址只有一个权威值"（写者独占），所以读总是能得到"某个一致视图"；但**没有屏障时，你读到的不一定是"最新"**——因为 store buffer 里的写还没进缓存。可见性 = 一致性协议 + 屏障刷出，两者缺一不可。

## 9. 核心要点

> 🎯 **核心要点**：多核并发的硬件基础 = 私有缓存（L1/L2）+ 一致性协议（MESI/MOESI，64B 粒度）+ 原子指令（LOCK/CAS）+ 内存屏障；`i++` 不原子、volatile 管可见性不管原子性、伪共享是 64B 粒度导致的隐蔽杀手（用 @Contended/padding 对抗）；NUMA 下跨节点内存访问贵 40-70%（用 numactl/JVM NUMA 感知）；TSX 硬件事务在 2026 内核默认 auto 回归——把 JMM 翻译成硬件语言后，Java 并发优化的每个参数都有了依据。
