## 1. 特权级与三种 CPU 模式

操作系统需要回答的第一个硬件问题：**如何让用户程序无法破坏系统？** 答案是 CPU 内置的"特权级"——一个运行状态标志，决定了当前代码能执行什么指令、访问什么资源。

| CPU 状态 | 特权级（x86） | 能做什么 | 不能做什么 |
|---------|:---:|---------|-----------|
| 内核态（Kernel Mode） | Ring 0 | 所有指令、所有寄存器、直接访问物理内存、关中断 | —— |
| 用户态（User Mode） | Ring 3 | 普通运算、自己的虚拟内存、发起系统调用 | 特权指令（cli/lgdt/mov cr*）、访问内核地址、直接操作硬件 |

关键认知：

- **特权级是硬件属性不是软件约定**。CPU 在执行每条指令前，检查当前 CPL（Current Privilege Level）是否允许该指令/该内存访问，不允许就抛异常（#GP/#PF），操作系统接管。
- **操作系统自身也运行在 CPU 上**，只是它把自己放在最高特权级。内核态不是"另一个世界"，而是"Ring0 下执行的同一套指令"。
- **Linux 只用了 Ring0 和 Ring3 两级**（Ring1/2 留给了历史中的 OS/2、驱动等，现代 OS 不使用），ARM 64 的 EL0-EL3 则被用于 TEE 可信执行环境（EL3 跑安全固件，EL1 跑内核，EL0 跑用户态，EL2 跑 Hypervisor）。

> ⚠️ **常见误区**：用户态/内核态的切换不是"两个进程换班"，而是**同一条执行流在一个瞬间改变特权级**——CPU 执行流永不中断，只是换了"权限证件"和"栈"。

## 2. x86 特权级体系：Ring0-Ring3

### 2.1 特权指令清单

x86 把指令按危险程度分级，以下指令**只能在 Ring0 执行**（否则 #GP 异常）：

| 类别 | 指令示例 | 危害 |
|------|---------|------|
| 控制寄存器 | `mov cr0/cr3/cr4` | 关分页、换页表 = 内存崩塌 |
| 中断控制 | `cli/sti`、`lidt/lgdt` | 关中断 = 系统假死；改 IDT = 劫持 |
| 任务切换 | `ltr` | 伪造 TSS = 越权 |
| 调试 | `mov dr0-dr7` | 篡改硬件断点 |
| 系统管理 | `wrmsr`（写 MSR） | 改写硬件配置寄存器 |

### 2.2 一次模式切换的硬件动作（以 syscall 为例）

```text
用户态 (Ring3, 用户栈)
   │  执行 syscall 指令
   ▼
CPU 硬件自动完成（不需要软件参与）：
   ① 保存当前 RIP 到 RCX（syscall 专用）
   ② 保存 RFLAGS 到 R11
   ③ CPL 从 3 切到 0（隐式）
   ④ 从 MSR 读到内核入口地址 → RIP 跳转
   ⑤ 切换栈：RSP 从 MSR_IST 取内核栈（或由内核入口保存）
   ▼
内核态 (Ring0, 内核栈)
   │  执行内核代码 → sysret 返回
   ▼
用户态恢复：RCX→RIP、R11→RFLAGS、CPL 0→3
```

## 3. 保护机制：段、页与 DPL/RPL/CPL

x86 有**两层保护**，历史地看是段保护在前、页保护在后：

### 3.1 三个特权级字段

| 字段 | 含义 | 出处 |
|------|------|------|
| CPL | Current Privilege Level，当前运行代码的特权级 | CS 段寄存器的低 2 位 |
| DPL | Descriptor Privilege Level，段的访问门槛 | GDT/LDT 描述符、IDT 门描述符 |
| RPL | Requested Privilege Level，请求者的意图 | 段选择子的低 2 位 |

判断规则：**访问段内存要求 `max(CPL, RPL) <= DPL`**——即"特权级数值越小权限越高"（0 最高，3 最低）。

### 3.2 门描述符（Gate）：允许用户态"合法越级"

Ring3 不能直接跳进 Ring0 代码，唯一通道是 **门（Gate）**：

| 门类型 | 用途 | 现代 Linux 用法 |
|--------|------|----------------|
| 中断门（Interrupt Gate） | 处理中断/异常，进中断栈 | IDT 中所有中断/异常 |
| 陷阱门（Trap Gate） | 处理异常/系统调用，不开中断 | int 0x80 兼容入口 |
| 调用门（Call Gate） | 允许调用高特权函数 | 现代 OS 不用（改用 syscall） |
| 任务门（Task Gate） | 硬件任务切换 | 现代 OS 不用 |

### 3.3 页级保护：每页 4KB 的权限位

段保护是"大颗粒"，真正的精细保护在页表：

| 页表标志位 | 作用 |
|-----------|------|
| P（Present） | 页是否在物理内存 |
| R/W | 可写权限（Ring0 写只读页会被 SMEP/SMAP 之外的部分绕过，见 04 篇） |
| U/S | 0=仅内核可访问（Supervisor），1=用户可访问 |
| NX（No-Execute） | 禁止执行该页代码（DEP/W^X 的基础） |

> 💡 **现代 Linux 的内存保护组合拳**：NX 让栈/堆不可执行 → 防 shellcode；SMEP 让内核态禁止执行用户态页 → 防 ret2usr；SMAP 让内核态禁止读写用户态页（除非显式 stac/clac）→ 防内核读用户数据；KASLR 随机化内核基址 → 防 ROP 定位。这四件套在 04 篇展开。

## 4. 模式切换的四种路径

| 路径 | 触发者 | 机制 | 频率量级 | 说明 |
|------|-------|------|:---:|------|
| **系统调用** | 用户程序主动 | `syscall` 指令 | 万次/秒 | 唯一"合法"主动进内核的通道 |
| **中断** | 硬件异步 | 中断门 | 千-万次/秒 | 网卡/磁盘/时钟通知 |
| **异常** | CPU 自身 | 陷阱/故障门 | 偶发 | 缺页、除零、#GP |
| **调用门/far call** | 用户程序 | 门描述符 | 已废弃 | 现代 OS 不用 |

⚠️ 注意三者的关键差异：**中断是"异步的"**（CPU 执行到一半被打断，事后回到原处），**异常是"同步的"**（是当前指令的直接结果），**系统调用是"有意为之"**。三者都走 IDT（除了 syscall 指令直连 MSR 入口），但语义完全不同。

## 5. ARM 与 RISC-V 的对应设计

| 架构 | 特权级 | 对应关系 | 系统调用指令 |
|------|--------|---------|-------------|
| x86-64 | Ring0/3 | 内核/用户 | `syscall` |
| ARM AArch64 | EL0-EL3 | EL0 用户 / EL1 内核 / EL2 Hypervisor / EL3 固件+TEE | `svc #0`（Supervisor Call） |
| RISC-V | U/S/M/HS | U 用户 / S 内核 / M 机器（固件+HSM）/ HS Hypervisor | `ecall` |

ARM 与 RISC-V 把虚拟化层（EL2/HS）和可信执行环境（EL3/M）做成**明确的特权级**，比 x86 的 Ring 设计更"规整"——这也是 2026 年 ARM 服务器（AWS Graviton4/5、Azure Cobalt、Ampere）能稳占云市场的重要原因之一：硬件级隔离能力与 x86 对齐，而功耗/每核成本更低。

## 6. 2026 现状与 Java 视角

### 6.1 2026 年 CPU 市场速写（对特权级设计的影响）

| 平台 | 2026 状态 | 与软硬件交界的关联 |
|------|----------|-------------------|
| Intel Nova Lake（桌面/移动） | Coyote Cove P 核 + Arctic Wolf E 核，最多 52 核（S），LGA 1954，原计划 2026 年底（或有推迟） | P/E 核异构 → 调度器要识别核心类型（05 篇） |
| AMD Zen 6 | EPYC Venice 服务器 2026、桌面 Ryzen 10000 系列（AM5/AM6，TSMC 2nm） | 每核 2 线程 SMT、多 CCD → NUMA 拓扑更复杂（08 篇） |
| ARM 服务器 | Graviton4/5、Cobalt 100 持续扩张 | EL0-EL3 四层特权级原生支持虚拟化 |
| x86 与 ARM 共识 | 分页结构基本趋同（4KB 页 + 多级页表 + NX） | 04 篇内容两架构通用 |

> 💡 **P/E 核异构成 2026 桌面/移动的标配**：Linux 调度器（EEVDF）需要知道"大核/小核"才能正确分配任务——这是"软件如何感知硬件拓扑"的典型例子，也是 05 篇的重要主题。

### 6.2 Java 开发者需要记住的结论

1. **JVM 本身是用户态程序**：Java 代码全部跑在 Ring3，JVM 通过系统调用（mmap/read/write/thread 创建）与内核交互——所以 `System.currentTimeMillis()` 可能走 vDSO（见 07 篇），`new Thread()` 会进内核创建。
2. **volatile/CAS 不需要特权级**：它们是"同一特权级内的指令级保证"（LOCK 前缀、原子指令），与用户态/内核态无关——见 08 篇。
3. **虚拟线程迁移到 OS 线程时的 pinning 问题**（JEP 491）：当虚拟线程持有 `synchronized` 锁或调用 native 方法时被钉在载体线程上，与线程调度、CPU 亲和性直接相关——理解 05 篇的"调度器如何选 CPU"是深入 pinning 的前提。
4. **为什么 Java 没有"裸机"能力**：Ring3 下不能直接操作端口、不能关中断、不能读写 CR——所以 Java 做不了驱动/内核；做中间件（MySQL、Redis、Kafka）则完全够用，因为它们的性能边界在"怎么调用内核"，不在"绕过内核"。

### 6.3 特权级安全的教训：熔断与幽灵

2018 年的 Spectre/Meltdown 系列漏洞本质上**攻击的就是特权级边界**——CPU 乱序执行时提前访问了"不该访问"的内存，再通过侧信道（时序/缓存）把数据带出来：

| 漏洞 | 攻击对象 | 对特权级设计的教训 |
|------|---------|-------------------|
| Meltdown | 内核地址空间映射在用户态可见 | 内核页表隔离（KPTI）：用户态页表不再映射内核地址 |
| Spectre v1/v2 | 分支预测的投机执行 | 全 CPU 厂商微码更新 + 软件缓解（retpoline） |
| L1TF/Foreshadow | L1 cache 残留 | L1 缓存刷新 + 虚拟化加固 |
| 2023-2025 新变体 | 微架构侧信道持续演化 | 每次漏洞都导致内核/微码更新，性能损失 ~5-30%（旧机器） |

> 💡 **对系统设计的启示**：硬件特权级隔离不是绝对安全——它是"性能优先"的设计，侧信道攻击证明"边界要软硬结合"。现代 CPU 在乱序执行深度、预测器随机化（2026 年新架构普遍加入）上持续修补；操作系统则用 KPTI、Address Space Isolation 等软件手段兜底。

### 6.4 系统管理模式 SMM 与 Intel SGX

特权级之外还有两个"隐藏模式"，理解它们才能看懂 2026 年安全研究热点：

| 模式 | 特权级 | 用途 | 安全意义 |
|------|:---:|------|---------|
| **SMM（系统管理模式）** | Ring -1（最高） | 固件 ACPI 电源管理、热插拔 | 攻击者可借 SMM 漏洞完全控制机器（读内存、改固件） |
| **SGX（软件保护扩展）** | Enclave 模式 | 应用级可信执行环境（内存加密隔离） | 被 TDX/SEV 部分取代，2026 年已边缘化 |

- SMM 由 **SMI（系统管理中断）** 触发，代码跑在独立 SMRAM 中——普通内核态代码都看不到它，所以 SMM 漏洞是"防 AV 杀软"的高级攻击面；
- SGX 曾被 Intel 定位为机密计算基石，但 2026 年市场明显转向 TDX/SEV-SNP（见 10 篇）——**SGX 是"应用级"加密，TDX/SEV 是"整机级"加密**，后者对云用户更透明。

> 🎯 **本节小结**：特权级体系 = Ring0/3（常规）+ SMM/SGX（隐藏域）；2026 年新架构（Nova Lake/Zen 6）在侧信道随机化与机密计算硬件（TDX/SEV）上加码，特权级安全从"防止越权指令"演进为"防止越权观察"。

### 6.5 模式切换成本实测

| 测量对象 | 典型耗时 | 测量命令 |
|---------|:---:|---------|
| 空函数调用 | ~1-3ns | 微基准（JMH） |
| syscall 往返（getpid） | ~50-100ns | `perf stat -e cycles ./test` 或 eBPF |
| 中断处理（完整路径） | ~5-20μs | `perf sched` 观测 |
| 模式切换（用户→内核→用户） | ~100-300ns | `perf trace` 平均 |

```bash
# 用 perf 观察一次 read() 的完整开销
perf stat -e cycles,instructions,cache-misses,context-switches read -n 1 /dev/zero
```

> 💡 **工程结论**：模式切换本身（~100ns）很便宜，贵的是"切换带来的环境破坏"（TLB 部分失效、内核路径冷 cache、分支预测重置）。所以优化的方向永远是**减少切换次数**而不是"让切换更快"——vDSO、io_uring、批处理全是这个思路（见 03 篇）。

### 6.6 面试追问与答题范式

**Q1：用户态和内核态有什么区别？怎么切换？**
答：区别在特权级（Ring3 vs Ring0）——内核态能执行特权指令、访问全部内存，用户态不能；切换靠 syscall 指令（主动）或中断/异常（被动），硬件自动完成寄存器保存、特权级提升、栈切换。

**Q2：为什么说 Linux 只用了两级特权级？Ring1/2 干嘛的？**
答：Linux 设计上只用 0 和 3；1/2 留给驱动等中间层，但现代 OS 认为"驱动在内核态更方便管理"（性能+直接访问），放弃了中间特权级的复杂度。

**Q3：syscall 和 int 0x80 有什么区别？**
答：syscall 是硬件级快速入口（寄存器保存、MSR 直读入口地址，~50ns）；int 0x80 走 IDT+软件压栈（~1μs），x86-64 下已废弃仅兼容。

**Q4：熔断/幽灵漏洞为什么跟特权级有关？**
答：CPU 乱序执行提前访问了内核地址，侧信道把数据带出——说明特权级是"逻辑隔离"，物理侧信道（缓存时序）可绕过，需要 KPTI 等软件兜底。

> 🎯 **答题范式**：先答"特权级是 CPU 硬件属性"→ 举特权指令例子 → 讲切换硬件动作（syscall 三步）→ 落点到安全（SMM/侧信道）——按"机制→例子→成本→安全"四段式，覆盖面试官的所有追问方向。

**Q5：ARM 的 EL0-EL3 和 x86 的 Ring 有什么区别？**
答：结构不同——x86 的 Ring 是"数值越小权限越高"的一维设计（Linux 只用 0/3）；ARM 用 EL0-EL3 四级，每级职责明确（用户/内核/Hypervisor/固件+TEE），虚拟化和 TEE 是硬件级的"原生特权级"，这也是 ARM 服务器安全能力的卖点之一。

**Q6：内核态代码写错了会怎样？**
答：用户态崩溃只是进程退出（可重启）；内核态崩溃（panic）可能直接死机或数据损坏——因为内核管着页表、驱动、锁。这也是为什么内核代码要更谨慎、驱动优先用 Rust（内存安全），以及"改内核参数前先备份"的运维铁律。

**Q7：Java 为什么不能"直接操作硬件"（如写端口）？**
答：Ring3 下端口 IO、CR 寄存器、关中断全是特权操作，直接执行会 #GP 异常；JVM 只能通过系统调用请内核代劳。所以 Java 做中间件、做驱动是两条路——前者靠内核服务，后者必须进内核态（C/Rust）。

## 7. 核心要点

> 🎯 **核心要点**：特权级是 CPU 内置的信任边界——内核态 Ring0 拥有全部权力，用户态 Ring3 只能通过 syscall/中断/异常三条通道"合法越级"；模式切换由硬件完成关键步骤（保存寄存器、切栈、跳转），一次完整往返约 50-100ns，是理解系统调用、上下文切换成本（03/05 篇）的起点。
