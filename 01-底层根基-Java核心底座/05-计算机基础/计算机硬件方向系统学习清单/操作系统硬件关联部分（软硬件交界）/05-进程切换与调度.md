# 05 进程切换与调度

## 1. 上下文切换：一次完整的"换血"

**上下文切换（Context Switch）= 把 CPU 从执行进程 A 改为执行进程 B**，硬件+软件协作完成：

```text
① 触发：进程 A 时间片耗尽（时钟中断）/ 主动让出（sleep、IO 等待）
② 中断/系统调用入口保存 A 的寄存器现场（pt_regs）
③ 内核调度器（schedule()）选择下一个进程 B
④ 保存 A 的 TCB 指向的上下文（栈指针 RSP、PC、寄存器、FPU 状态）
⑤ 恢复 B 的上下文（寄存器、RSP、PC）
⑥ 若 B 与 A 不同进程（跨地址空间）：
     - CR3 换为 B 的 PML4 页表 → 整个 TLB 失效（冷启动）
     - 若跨 CPU，还要处理 cache 热度
⑦ iretq/sysret 回到 B 的用户态继续执行
```

### 1.1 切换的三要素

| 要素 | 切换内容 | 成本特征 |
|------|---------|---------|
| 寄存器 | 通用寄存器（16 个 ×8B） | 快（几十 ns） |
| 栈 | RSP 从 A 的内核栈换到 B 的内核栈 | 快（一次写） |
| **地址空间（CR3）** | 页表基址 + TLB 全部失效 | **贵**（见第 2 节） |
| FPU/SIMD 状态 | XMM/YMM 寄存器（AVX-512 为 512 位×32） | 首次使用才保存（惰性） |

> 💡 **线程 vs 进程切换的本质区别**：同进程的线程共享地址空间，切换**不换 CR3、不刷 TLB**，所以线程切换比进程切换便宜得多（~1-3μs vs ~5-20μs）。这就是"线程比进程轻量"的硬件根源。

## 2. 切换成本拆解：贵在哪里

| 成本项 | 量级 | 说明 |
|--------|:---:|------|
| 系统调用往返 | ~0.1μs | 基准 |
| **线程切换（同进程）** | ~1-3μs | 10-30 倍于 syscall |
| **进程切换（跨地址空间）** | ~5-20μs | 还要 TLB 全刷 |
| 切换后的缓存惩罚 | ~1-10μs | 新进程访问数据全 miss，cache 重建 |

**"隐形"开销比切换本身更贵**：

1. **TLB 全失效**：换 CR3 后前几百次访存全部 miss，每 miss 几十周期（04 篇）。
2. **缓存冷启动**：B 的数据在 L1/L2/L3 中全是"别人的数据"，首次访问 miss → 等内存。
3. **分支预测器失效**：B 的跳转历史全部清空。
4. **TLB shootdown 放大**：多核下切换进程还可能引发跨核 IPI（04 篇 3.2）。

> ⚠️ **工程结论**：高吞吐服务（Netty、Kafka）单线程+事件循环本质是**避免上下文切换**——把"切换"替换为"在同一个线程里多路复用"。Java 虚拟线程也是同一思路：大量逻辑线程映射到少量载体线程，切换在用户态 JVM 内完成（协程式切换，~100ns 级）。

## 3. TCB 与 TSS：切换的数据结构

| 结构 | 内容 | 谁用 |
|------|------|------|
| TCB（Task Control Block） | 进程所有状态：寄存器现场、栈指针、CR3、打开文件表、信号、内存描述符 | 内核软件 |
| TSS（Task State Segment） | 硬件要求的结构：内核栈指针、I/O 位图、IST 表 | CPU 硬件（x86 特有） |

**x86 的特殊性**：CPU 在特权级切换（用户→内核）时要**从 TSS 自动加载内核栈指针**——所以每个任务必须有一个 TSS（Linux 用 `set_tss_desc` 每 CPU 一个 + `ltr` 加载一次）。ARM 用 `SP_EL1`（内核栈指针寄存器）达成同样目的，比 TSS 更简洁。

## 4. 时间片与调度器

### 4.1 时间片从哪里来

```text
APIC timer 时钟中断（每 1ms 或按 HZ 频率触发）
  → 内核 tick 处理：当前进程 CPU 时间累加
  → 若超过时间片（如 4ms）→ 标记需要调度（TIF_NEED_RESCHED）
  → 中断返回路径检查标志 → 触发 schedule() → 上下文切换
```

| 参数 | 默认值（现代内核） | 说明 |
|------|:---:|------|
| HZ（内核节拍） | 250/300/1000（x86 默认 1000） | 时钟中断频率 |
| 时间片（CFS 时期） | 1-4ms 动态 | 按任务数加权分配 |
| 调度粒度 | ~1ms 级 | tick 驱动 |

### 4.2 调度器演进：从 O(1) 到 CFS 到 EEVDF

| 调度器 | 时代 | 核心思想 |
|--------|------|---------|
| O(1) | 2.6.0-2.6.22 | 优先级数组，O(1) 选择 |
| **CFS** | 2.6.23 - 6.5 | 红黑树按"虚拟运行时间"排序，完全公平 |
| **EEVDF**（Earliest Eligible Virtual Deadline First） | 6.6+（2023） | CFS 的演进：带"最早可用虚拟截止时间"，对延迟敏感任务更公平、交互式响应更好 |

```text
CFS 本质：vruntime（虚拟运行时间）最少的任务先跑
  └─ 每次时钟中断更新 vruntime → 塞回红黑树 → 取最左节点
EEVDF 改进：引入 eligible/deadline 双指标
  └─ 低延迟任务（交互式）获得更早的执行窗口，减少"饿着等"的毛刺
```

> 💡 **EEVDF 与 Java 的关系**：Java 的线程优先级（Thread.setPriority 1-10）映射到内核 nice 值，EEVDF 通过权重体现；低延迟 Java 服务调优（`-XX:ThreadPriorityPolicy=1` 或内核 nice 调整）在 EEVDF 下的效果与 CFS 时代需要重新验证。

## 5. 多核调度：负载均衡与亲和性

### 5.1 调度域（Scheduling Domain）

内核按硬件拓扑组织调度域：

```text
NUMA 节点域（每个 NUMA 节点一组 CPU）
  └─ 簇域（共享 L2 的核组）
      └─ 核域（SMT 兄弟核）
```

负载均衡（load_balance）在**域之间**周期迁移任务；迁移的代价是 cache 全冷——所以调度器有"均衡收益 vs 迁移成本"的权衡（wake_affine 等启发式）。

### 5.2 CPU 亲和性

| 手段 | 用法 | 场景 |
|------|------|------|
| taskset/cgroup cpuset | 绑定进程到指定核 | 数据库、网络服务绑定专用核 |
| `sched_setaffinity` | 编程式绑定 | 高性能中间件 |
| NUMA 亲和（mbind） | 内存分配绑定节点 | 配合"核-内存同节点" |

> ⚠️ **经典教训**：进程在 NUMA 节点 0 的核上跑，但内存却分配在节点 1 → 每次访问跨节点内存，延迟 +30-70%（08 篇 NUMA 详述）。`numactl --cpunodebind=0 --membind=0` 是标配操作。

## 6. 2026 演进：EEVDF 与 Time Slice Extension

### 6.1 Linux 7.0 Time Slice Extension（RSEQ 驱动）

Linux 7.0（2026-04）修复了一个十年老问题：**线程在临界任务执行到一半时被抢占**（如正在写日志、更新锁结构），导致微停顿（micro-stutter）。

| 机制 | 说明 |
|------|------|
| 名称 | Time Slice Extension（时间片扩展） |
| 原理 | 借助 RSEQ（Restartable Sequences，CPU 指令级重启原语）：线程主动声明"我正在做不可抢占的关键操作"，被选为抢占目标时，内核等待其完成（时间片延长），而不是硬切 |
| 收益 | 减少微停顿，交互与高频小任务体验提升 |

```c
// RSEQ 思想（简化）：声明临界区，被抢占时自动回滚重做
rseq_preempt_check();
critical_section_start();
... // 原子性操作
critical_section_end();
```

> 💡 **Java 联动**：RSEQ 未来也可能成为 JVM 无锁数据结构、GC 屏障的底层原语（JEP 相关讨论持续中）。2026 年 JVM 生态已在探索基于 RSEQ 的轻量同步。

### 6.2 虚拟化下的调度

| 场景 | 特点 |
|------|------|
| 物理机 | 调度器直接管理所有核 |
| 虚拟机（KVM） | vCPU 是宿主机的普通线程，被宿主 CFS/EEVDF 调度；虚拟 CPU 与物理 CPU 的对应关系决定延迟（10 篇详述） |
| 容器 | 与宿主机共享调度器，cgroup CPU 限额 + cpuset 绑定 |

## 7. Java 视角：线程与虚拟线程

| 概念 | 硬件/内核映射 | 切换成本 |
|------|--------------|:---:|
| Java 平台线程 | 1:1 映射 OS 线程（clone 创建） | ~1-3μs（内核切换） |
| **虚拟线程**（JEP 425/491，Java 21+） | 大量虚拟线程映射到少量载体线程；切换由 JVM 在用户态完成 | ~100ns 级（不进出内核） |
| ForkJoinPool | 工作窃取（work-stealing）在 JVM 层模拟负载均衡 | —— |

**虚拟线程的硬件含义**：它把"调度器"从内核搬到了 JVM——用户态调度意味着：
1. 切换不再经过 syscall/中断 → 无特权级切换、无 TLB shootdown；
2. 载体线程固定时 cache 保持热度 → 命中率显著提升；
3. 代价：`synchronized`/native 调用时被 pinning（JEP 491 优化了大部分场景）——**pinning 的根治需要理解 05+08 篇的调度与锁语义**。

> ⚠️ **Pinning 的本质**：虚拟线程被钉在载体线程上 = 失去用户态切换能力，退化为内核切换——所以写虚拟线程代码时要避免 `synchronized` 大临界区和 JNI 长调用（用 `java.util.concurrent` 锁替代）。

### 7.1 抢占模型：谁有资格打断谁

| 抢占类型 | 允许谁打断谁 | Linux 实现 |
|---------|-------------|-----------|
| 用户抢占 | 时钟中断到期后调度另一个用户任务 | 默认开启 |
| **内核抢占** | 内核态代码执行中可被调度 | `CONFIG_PREEMPT`（桌面/服务器默认） |
| 自愿抢占 | 内核代码显式让出（schedule()） | 自旋锁区域、原子上下文 |
| 实时抢占 | 任何上下文可被打断（RT 补丁并入 6.x） | `CONFIG_PREEMPT_RT`（工业/金融） |

```text
一个微妙问题：时钟中断返回路径为什么调度？
  中断返回时发现 TIF_NEED_RESCHED 置位 → 走 retint 路径调用 schedule()
  而不是中断处理里直接切——保证切换发生在"安全的返程点"
```

> 💡 **对 Java 的意义**：JVM 的 safepoint（GC 停顿点）与内核抢占类似——JVM 用 `SafepointSynchronize` 让所有线程在安全点等待 GC。两者设计同构：**都在"安全的切换点"而不是任意点打断执行流**，这是所有协作式机制（协程/虚拟线程/GC 安全点）的共同法则。

### 7.2 延迟测量与工具

| 指标 | 含义 | 工具 |
|------|------|------|
| 调度延迟（schedule latency） | 任务就绪到实际运行 | `cyclictest`（RT 场景标准工具） |
| 上下文切换次数 | 每秒切换频率 | `vmstat 1`（cs 列）、`pidstat -w` |
| 运行队列长度 | 就绪任务数 | `vmstat`（r 列）、`sar -q` |
| 抢占时延 | 中断到任务恢复 | perf trace、eBPF（`bcc` 工具） |

```bash
vmstat 1 | awk '{print "cs="$12" r="$1}'   # 每秒切换/就绪队列
pidstat -w 1 -p 12345                       # 单进程自愿/非自愿切换
```

> ⚠️ **Java 调优目标**：高吞吐服务追求"少切换"（cs 保持低）；低延迟服务追求"切换确定性"（时延抖动小）。虚拟线程把切换搬进 JVM 后，`vmstat cs` 会骤降——这是虚拟线程效果的直接观测指标。

### 7.3 RT 调度与 EDF 家族

| 调度策略 | 适用 | 抢占规则 |
|---------|------|---------|
| SCHED_OTHER（CFS/EEVDF） | 普通任务 | 时间片公平 |
| SCHED_FIFO | 实时（RT） | 高优先级先跑，不轮转（直到让出） |
| SCHED_RR | 实时（RT） | 同级轮转 |
| SCHED_DEADLINE | 硬实时 | EDF 截止时间最早先跑 |

```bash
# 查看/设置调度策略
chrt -p $$          # 查看当前 shell 调度策略
chrt -f 50 ./app    # FIFO 优先级 50
# 实时调度的坑：写死循环的 RT 任务可饿死系统（死循环优先级最高）
```

> ⚠️ **Java 与 RT**：JVM 默认可直接运行在 RT 调度下（`chrt` 启动即可），GC 线程会继承优先级——但 RT 策略下 Java 的 GC 停顿反而放大（无时间片保护）。除非硬实时场景（高频交易），否则 Java 服务用 CFS/EEVDF 即可；RT 留给专用工具线程。

### 7.4 虚拟线程与载体线程的绑定关系

```text
虚拟线程调度模型（Java 21+）：
  N 个虚拟线程（N 可达百万）→ M 个载体线程（M ≈ CPU 核数）
  每个载体线程跑一个 ForkJoinPool worker
  虚拟线程 park 时：JVM 现场保存到堆 → worker 切换到下一个
  pinning（JEP 491 已大幅缓解）：synchronized/native 时会钉住
```

| 场景 | 切换发生地 | 成本 |
|------|-----------|:---:|
| 虚拟线程 park/unpark | JVM 用户态（无内核参与） | ~100ns |
| 载体线程切换（JVM 内） | 同上 | ~100ns |
| 虚拟线程真正进内核 | IO 操作（read/write/epoll） | 内核往返 |
| pinning 后 | 退化为平台线程行为 | ~1-3μs |

> 🎯 **调优要点**：虚拟线程性能的三大前提——① 避免 synchronized 大临界区（防 pinning）② 载体线程数 = 核数（`-XX:ActiveProcessorCount` 对容器需校正）③ IO 操作本身要快（虚拟线程不解决慢 IO）。理解了载体线程与 CPU 的映射（05 篇），才能回答"为什么我的虚拟线程服务只用了 8 个核"。

### 7.5 切换与调度面试追问

**Q1：线程切换为什么比系统调用贵 10 倍？**
答：系统调用只是模式切换（不换页表，TLB 基本保住）；线程切换要换寄存器+栈+（跨进程时）CR3+TLB 全刷+cache 冷+分支预测失效——"环境重建"才是大头。

**Q2：进程切换和线程切换的区别？**
答：同进程线程共享地址空间，切换不换 CR3（~1-3μs）；进程切换换页表刷 TLB（~5-20μs）。所以"线程轻量"的根源在 MMU。

**Q3：CFS 和 EEVDF 的区别？**
答：CFS 按虚拟运行时间红黑树排序；EEVDF 增加"最早可用截止时间"，让延迟敏感任务获得更早执行窗口，减少交互式任务毛刺——2023 年合入（6.6），Linux 7.0 再加 RSEQ 时间片扩展。

**Q4：为什么 Linux 7.0 要用 RSEQ 做时间片扩展？**
答：线程在关键临界区（如写日志）被硬抢占会产生微停顿——RSEQ 让线程声明"关键段"，内核等它完成再切，把"抢占的确定性"交给用户态表达。

**Q5：容器里 Java 的 CPU 数为什么不准？**
答：JVM 通过 `ActiveProcessorCount` 探测可用核——容器配额（cpuset/cpu 限额）下若不显式设置会高估，导致线程池过大。这是调度拓扑感知的经典坑。

**Q6：虚拟线程 pinning 和上下文切换什么关系？**
答：pinning 时虚拟线程被钉在载体线程上——失去 JVM 用户态切换能力，退化为内核线程切换（~1-3μs vs ~100ns）。JEP 491 消除大部分 synchronized pinning，但 JNI/native 调用仍会钉——理解"切换在哪一层发生"是定位虚拟线程性能问题的钥匙。

**Q7：为什么说"高并发 ≠ 高线程数"？**
答：切换成本与线程数成正比（每个线程都要被调度）；且线程栈占内存（~1MB 虚拟/线程）。高并发正解是"少量线程 + 事件驱动"（Netty）或"海量虚拟线程 + 用户态切换"（JVM 调度）——底层都是同一个道理：**减少内核切换次数**。

**Q8：内核如何避免"频繁切换"？**——三件套：① 时间片加权（EEVDF 按负载分配）；② 唤醒亲和（wake_affine：被唤醒的线程尽量放回原核，保 cache 热度）；③ 调度延迟合并（tick 节流）。理解这些，就明白"为什么线程池大小不是越大越好"。

## 8. 核心要点

> 🎯 **核心要点**：上下文切换是"寄存器+栈+（跨进程时）页表"的三件套换血，线程切换 ~1-3μs、进程切换 ~5-20μs，隐性成本（TLB 全刷、cache 冷、分支预测失效）远超切换本身；时间片来自 APIC timer 时钟中断；调度器从 CFS 演进到 EEVDF，Linux 7.0 用 RSEQ 实现时间片扩展消除微停顿；Java 虚拟线程把调度搬到用户态，切换成本降两个数量级——理解"切换为什么贵"是选择线程模型的第一依据。
