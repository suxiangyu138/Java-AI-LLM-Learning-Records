## 1. 四类硬件时钟

| 时钟 | 精度 | 功耗/持续 | 用途 | 2026 状态 |
|------|:---:|:---:|------|----------|
| RTC（实时时钟） | 秒级 | 电池供电，断电仍走 | 系统启动时读初始时间 | 依然存在 |
| **TSC（时间戳计数器）** | **纳秒级** | 随 CPU 核心走 | **现代 Linux 默认时钟源** | Invariant TSC 保证恒定频率 |
| HPET | 微秒级 | 独立芯片 | 备用时钟源 | 基本被 TSC 取代 |
| APIC timer | 微秒级 | 每核一个 | **中断产生**（tick、调度） | 现代中断主力 |

```bash
# 查看系统时钟源
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
# 输出 tsc（现代 x86）或 hpet（虚拟机兜底）等
```

> 💡 **TSC 为什么是王者**：`RDTSC` 指令直接读 CPU 内置计数器（现代为恒频、每核独立但软件同步），耗时 ~20ns；HPET 要过总线（~1μs+）。Linux 的 `clock_gettime` 在 x86 上就是"读 TSC + 换算"，这就是 vDSO 里 20-50ns 的来源。

## 2. 时钟中断：内核的时间心跳

### 2.1 tick 机制

```text
APIC timer 每秒触发 HZ 次中断（x86 默认 1000）
  → 每次 tick：更新时间 → 检查当前进程时间片（05 篇）
  → 检查定时器到期 → 统计 CPU 时间（/proc/stat 数据源）
```

| 概念 | 值 | 说明 |
|------|:---:|------|
| HZ | 1000（x86 默认） | 时钟中断频率 |
| jiffies | 每 HZ 加 1 | 内核"心跳计数器"，`jiffies` 全局变量 |
| 时间片 | 1-4ms | 由 tick 驱动检查（05 篇） |

### 2.2 NOHZ：把没必要的 tick 关掉

每个 CPU 每秒 1000 次中断在空闲时纯属浪费。现代内核：

| 模式 | 行为 | 适用 |
|------|------|------|
| 周期 tick | 恒定 HZ 中断 | 传统默认 |
| **NO_HZ_IDLE**（默认） | 空闲 CPU 停止 tick | 通用场景，省电+降抖动 |
| **NO_HZ_FULL**（Full dynticks） | 运行中的 CPU 也关 tick（需要配置） | 低延迟/确定性计算（金融、高频交易） |

```bash
# 查看当前系统 tick 状态
grep -i nohz /proc/cmdline   # nohz_full= 等参数
```

## 3. 时间片与 jiffies 的黄昏

历史：时间片 = jiffies 计数（每 tick 减 1）；现代：调度器改用**高精度计时**（ns 级，CFS/EEVDF 用 vruntime 纳秒计算），jiffies 退化为传统接口兼容物。

| 时代 | 时间片实现 | 精度 |
|------|-----------|:---:|
| 2.4 及以前 | 纯 jiffies 计数 | 1ms |
| 2.6-6.5（CFS） | 按 vruntime 权重计算（ms 级） | 1ms |
| 6.6+（EEVDF） | deadline 计算（ns 级） | **ns 级** |
| 7.0（2026） | + Time Slice Extension（RSEQ） | 关键任务可延长 |

## 4. 高精度定时：hrtimer 与 NOHZ

### 4.1 内核定时器两代

| 定时器 | 时代 | 精度 | 实现 |
|--------|------|:---:|------|
| timer wheel | 2.4-2.6.15 | 1/HZ（ms 级） | 多级时间轮 |
| **hrtimer** | 2.6.16+ | **ns 级** | 红黑树 + 硬件定时器（APIC timer 重编程） |

hrtimer 原理：把红黑树中**最近到期**的定时器编程进 APIC timer → 到期即触发中断，精度不再受 HZ 限制。这就是 `sleep(1ms)` 在 Linux 上真的能睡 ~1ms（而不是 1/HZ=1ms 取整）的原因。

### 4.2 高精度时钟的代价与取舍

| 姿势 | 行为 | 场景 |
|------|------|------|
| `usleep(1)` | 每次都重编程硬件定时器 | 短睡眠密集 → 中断风暴 |
| `nanosleep` + 队列合并 | 同一 tick 内的睡眠合并 | 吞吐场景 |
| **忙等（spin/自旋）** | 无中断，占核 | 纳秒级等待、RT 场景 |

> ⚠️ **Java 事实**：`Thread.sleep(1)` 的 JVM 实现调用 `clock_nanosleep`，Linux 上实际睡 **~1.0-1.1ms**（含调度延迟）；`LockSupport.parkNanos` 也走 hrtimer——所以**纳秒级 sleep 不可能精确，Java 也逃不过这个物理约束**。

## 5. 三种时间语义：墙上/单调/进程时间

| 时钟 | 语义 | 硬件来源 | Java API |
|------|------|---------|---------|
| CLOCK_REALTIME（墙上） | 真实世界时间，**可被 NTP 调整（回拨！）** | TSC + 内核换算 + NTP 偏移 | `System.currentTimeMillis()`、`Instant` |
| CLOCK_MONOTONIC（单调） | 单调递增，不受 NTP 影响 | TSC | `System.nanoTime()`、`Duration` |
| 进程 CPU 时间 | 本进程消耗的 CPU 时间 | 调度器统计 | `ThreadMXBean` |

```text
为什么 currentTimeMillis 会"跳变"？
  NTP 发现系统慢了 500ms → 内核直接调整 CLOCK_REALTIME 偏移
  → 依赖墙上时间算超时/延时的代码瞬间失真
  → 所以分布式超时/计时一律用 nanoTime（单调时钟）
```

> 🎯 **Java 铁律**：**计时用 `System.nanoTime()`（单调），定时刻用 `Instant`/`LocalDateTime`（墙上），二者永不混用**。`nanoTime` 的精度来源是 TSC，Linux x86 上实际分辨率为 ns 级——但分辨率高 ≠ 精度高（受频率漂移影响，相对计时够用）。

## 6. 分布式时间同步：NTP 与 PTP

| 协议 | 精度 | 机制 | 场景 |
|------|:---:|------|------|
| NTP | ms 级（局域网）~10ms（公网） | 网络对时 + 内核偏移调整 | 通用服务器 |
| **PTP（IEEE 1588）** | 亚微秒级 | **硬件时间戳**（网卡打时间戳，精确测量网络延迟） | 金融、5G、分布式数据库 |

```text
NTP 工作原理（简化）：
  客户端: 请求包带发送时间 t1 → 服务器记录到达 t2、回复 t3 → 客户端收到 t4
  往返延迟 = (t4-t1)-(t3-t2)；时钟偏移 = ((t2-t1)+(t3-t4))/2
  → 内核逐步调整 CLOCK_REALTIME 偏移量（不直接跳变）
```

| 场景 | 时间精度要求 | 手段 |
|------|:---:|------|
| 日志时间戳 | 秒级 | NTP 即可 |
| 分布式锁/事务（Seata、Raft） | **不依赖时钟**（逻辑时钟/单调时钟） | 用内部序号代替时间 |
| 金融撮合/TSDB 排序 | 亚毫秒级 | PTP + 硬件时间戳 |

> ⚠️ **分布式系统的第一条铁律**：**不要依赖跨机器的时间比较做正确性判断**——服务器时钟漂移是常态（±ms 级），分布式事务、ID 生成、缓存过期设计都必须以"单调时钟+逻辑序号"为准。雪花算法对时钟回拨的防范就是典型（见雪花算法体系）。

## 7. 虚拟机与容器中的时间

| 场景 | 问题 | 解决方案 |
|------|------|---------|
| 虚拟机 | 时钟中断频率不稳、TSC 跨物理核不一致 | KVM 提供**半虚拟化时钟**（kvm-clock），虚拟机内 TSC 被虚拟化截获或直通 |
| 容器 | 与宿主机共享内核，`gettimeofday` 走 vDSO 直读宿主机 TSC | 天然精确；但 `nohz_full` 参数隔离对容器内延迟有影响 |
| 暂停/迁移 | VM 暂停后时钟漂移 | NTP/PTP 自动纠正 + 硬件 RTC 兜底 |

```bash
# 虚拟机内查看时钟源（出现 kvm-clock 属正常）
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
```

## 8. Java 视角：时间 API 的硬件之路

| Java API | 硬件路径 | 耗时量级 |
|---------|---------|:---:|
| `System.currentTimeMillis()` | vDSO → TSC 换算（**无 syscall**） | ~20-50ns |
| `System.nanoTime()` | vDSO → TSC（单调） | ~20-50ns |
| `Thread.sleep(1)` | clock_nanosleep → hrtimer | ~1ms+ |
| `LockSupport.parkNanos(1)` | 同上 | 无法保证 1ns（最小 ~100μs 级） |
| `Instant.now()` | 同 currentTimeMillis（JVM 内封装） | ~50ns 级 |

```java
// 时间测量的正确姿势
long start = System.nanoTime();        // 单调：测量耗时
doWork();
long costNanos = System.nanoTime() - start;

// 反例：不要用 currentTimeMillis 测耗时
// 墙钟可能被 NTP 回拨 → 负数耗时
```

### 8.1 时间问题排查清单

| 症状 | 可能原因 | 排查命令 |
|------|---------|---------|
| `date` 突然跳变 | NTP 大步长调整（stratum 差过大） | `timedatectl status`、`chronyc tracking` |
| Java 日志时间错乱 | 容器时区未挂载（TZ 环境变量缺失） | `date` vs `cat /etc/timezone`、`TZ=Asia/Shanghai` |
| 定时任务提前/延后 | cron 与 NTP 校正竞争 | `timedatectl show -p NTP` |
| VM 时间漂移大 | 缺 kvm-clock/virtio clock | `cat /sys/devices/system/clocksource/...` |
| 高并发下 `nanoTime` 异常 | CPU 频率切换（旧 TSC） | `grep constant_tsc /proc/cpuinfo` |

```bash
# 排查时间问题三连
timedatectl                              # 时区/NTP 状态
chronyc sources -v                       # NTP 源与偏差
cat /sys/devices/system/clocksource/clocksource0/current_clocksource  # 时钟源
```

> ⚠️ **真实事故案例**：某分布式系统用 `System.currentTimeMillis()` 算缓存过期，NTP 回拨 3 秒导致缓存集体失效打爆数据库——修复方案就是换成基于单调时钟的 TTL（nanoTime + 偏移量），从此与 NTP 无关。

### 8.2 时间戳在日志与监控中的坑

| 坑 | 说明 | 规避 |
|----|------|------|
| 日志时间戳乱序 | 多线程写日志，本地时间被 NTP 调整 | 日志组件用单调时钟打点，展示时再转墙上时间 |
| 监控曲线"负延迟" | 采集端与主机时钟不同步 | 监控系统统一用 NTP+PTP 或单调时钟 |
| 数据库 `NOW()` 跳变 | 依赖墙钟的排序字段失真 | 自增 ID/逻辑时间代替 |
| 时间戳精度不一致 | 毫秒 vs 纳秒混用 | 统一精度标准（如统一微秒） |
| 时区混乱 | 服务器 UTC、应用 +8 | 全链路统一 UTC 存储，展示层转换 |

> 🎯 **铁律**：**存储和计算用 UTC/单调时钟，展示才转本地时区**——这是日志、数据库、监控系统的共同最佳实践。

### 8.3 CLOCK_BOOTTIME：跨越睡眠的单调时钟

| 时钟 | 暂停期间走不走 | 用途 |
|------|:---:|------|
| CLOCK_MONOTONIC | 不走（挂起时冻结） | 进程内计时 |
| **CLOCK_BOOTTIME** | 走（包含挂起时间） | 系统级超时（重启/挂起后仍准确） |
| CLOCK_REALTIME | 走（但可被 NTP 调整） | 墙上时间 |

```text
容器/虚拟机场景的意义：
  宿主机挂起或 VM 暂停 → MONOTONIC 冻结 → 依赖它的超时会"多等"
  BOOTTIME 不受影响 → 内核级超时（TCP 重传、锁超时）用 BOOTTIME
  Java 的 System.nanoTime() 基于 MONOTONIC——VM 迁移/暂停期间需注意
```

### 8.4 高精度时间戳的硬件来源：PTP 与 NIC

| 精度需求 | 方案 | 硬件依赖 |
|---------|------|---------|
| 1ms | NTP | 无特殊要求 |
| 100μs | 优化 NTP（本地源） | 低延迟网络 |
| **亚微秒** | PTP（IEEE 1588） | **网卡硬件时间戳**（TSU），软件打点无效 |

```text
为什么软件打点到不了亚微秒？
  软件路径：应用 → 内核 → 驱动 → 网卡（几十 μs 随机延迟）
  PTP 路径：网卡硬件在收帧瞬间打时间戳（ns 级，零软件延迟）
  所以金融撮合/5G 基站用 PTP + 支持 HW Timestamp 的网卡
```

> 💡 **Java 场景**：绝大多数 Java 系统不需要亚微秒时间——NTP 毫秒级足够；需要跨机精确排序（TSDB 写入顺序、日志相关性）时优先考虑"逻辑序 + 接收端时间戳"，而不是追 PTP。

### 8.5 时间与定时面试追问

**Q1：System.currentTimeMillis 为什么快（~20ns）？**
答：命中 vDSO——内核把 clock_gettime 的实现直接映射进用户态，读 TSC 换算即可，零系统调用。

**Q2：sleep(1) 真的睡 1ms 吗？**
答：hrtimer 精度到 ns，但实际睡眠 ~1-1.1ms（调度延迟）；且最小睡眠粒度受内核 tick/唤醒合并影响，短睡眠密集场景（<1ms）建议忙等或合并。

**Q3：为什么分布式系统不能用墙上时间？**
答：NTP 会回拨 CLOCK_REALTIME（校正时可能跳变）；跨机时钟本身有偏差——超时/锁/过期判断必须用单调时钟或逻辑时钟（序号）。

**Q4：时钟中断 1000 次/秒，会占多少 CPU？**
答：每次 tick ~1-2μs 处理，约 0.1-0.2% CPU——但空闲 CPU 的 tick 已被 NO_HZ_IDLE 关闭；NOHZ_FULL 可让运行中的 CPU 也免 tick（低延迟场景）。

**Q5：虚拟机里时间准不准？**
答：有 kvm-clock 半虚拟化时钟兜底（精度与宿主机相当）；但 VM 暂停/迁移期间 MONOTONIC 冻结、墙钟靠 NTP 追平——所以 VM 内的超时设计要用 BOOTTIME 语义。

### 8.6 定时任务与 Java 生态

| 定时器 | 底层 | 精度 | 适用 |
|--------|------|:---:|------|
| `Timer`（JDK 老 API） | 单线程+堆 | ms | 已淘汰 |
| `ScheduledThreadPoolExecutor` | 延迟队列+线程池 | ms 级 | 通用 |
| `HashedWheelTimer`（Netty） | 时间轮 | ms 级 | 海量定时器（连接超时） |
| 分布式调度（XXL-Job） | 数据库/Redis 轮询 | 秒级 | 集群任务 |
| quartz | 触发调度 | ms 级 | 复杂 cron |

> 💡 **硬件视角的选型准则**：单机纳秒-微秒级 → hrtimer/自旋；ms 级海量 → 时间轮（分摊唤醒）；跨机 → 靠网络时间（秒级精度上限）。**定时器的选择本质是"时钟精度 × 数量 × 跨机"三个维度的权衡**。

### 8.7 高精度计时的工程实践清单

| 实践 | 做法 | 原理 |
|------|------|------|
| 耗时测量 | `System.nanoTime()` 差值 | 单调时钟不受 NTP 影响 |
| 超时判断 | 单调时钟 + 偏移量（禁止墙钟） | 防 NTP 回拨导致误超时 |
| 频率统计 | 单调时钟窗口计数 | 窗口一致才可比 |
| 调度器精度 | 依赖 hrtimer（内核） | 与 Java 无关但影响 sleep 精度 |
| 日志时间戳 | 采集时用单调，展示转墙钟 | 防乱序 |
| 跨机排序 | 逻辑序号代替时间 | 时钟不同步的根源规避 |

> ⚠️ **最后一道防线**：即使全部照做，也要接受"计算机时间不是物理时间"——硬件的 TSC 有漂移、NTP 有步进、VM 有暂停。所有对时间的依赖都要有容错（超时容忍、重试、逻辑时钟兜底），这是分布式系统设计的第一课。

**补充：为什么服务器要装 NTP 而非手调时间？**——手调 date 是"直接跳变"（所有依赖墙钟的逻辑瞬间失真）；NTP 是"渐进微调 + 大步长时平滑"（slew/step 策略可配置）。`timedatectl set-ntp true` 让 chronyd 管理校正，日志里用 `date` 看到的分秒偏差就是它的工作痕迹。

**再补：hrtimer 与 Java 定时任务的关系**——Java 的 ScheduledThreadPoolExecutor 在 JVM 内部用优先级队列组织（用户态），到期后调用 `parkNanos` 或 `Object.wait` 交给内核 hrtimer 唤醒。所以"定时器数量多"时 JVM 内排序（时间轮/堆）先分摊一遍，只有"最近到期"的才真正交给内核——这正是时间轮（Netty HashedWheelTimer）存在的硬件理由。

**延伸阅读**：时间与分布式系统的纠缠（时钟回拨、逻辑时钟）在「雪花算法」体系中有更细的工程展开——ID 生成器对时钟回拨的防御就是本篇文章原则的实战应用。

**补充：一张时间开销速查表**——`currentTimeMillis` ~20-50ns（vDSO）；`nanoTime` ~20-50ns（vDSO）；`sleep(1ms)` ~1.05ms；`wait(10)`（有锁）~10ms+ 调度延迟；`ScheduledExecutor` 到期 ~1ms 精度；网络 RTT ~100μs-1ms。**先记住这张表，写代码时"该用哪种时间"自然有数**——这也是为什么性能敏感代码禁用 `sleep(1)` 做节流的硬件理由。

**最后一句**：时间是系统里最容易被"想当然"的维度——把"时间会跳变"刻进设计习惯，分布式系统一半的坑就绕开了。带着"时间不可靠"的警醒进入下一站：多核并发硬件基础。

**本篇知识闭环**：TSC 是"快时钟"、APIC timer 是"中断时钟"、hrtimer 是"软件定时"、NTP/PTP 是"跨机同步"——四层时钟各司其职，共同支撑"sleep、调度、超时、日志、分布式协作"的全部时间语义。

## 9. 核心要点

> 🎯 **核心要点**：硬件时钟四件套中 TSC 是性能王者（vDSO 直接读，无 syscall）；APIC timer 产生时钟中断驱动时间片与调度；hrtimer 让内核定时精度到纳秒级，NOHZ 把空闲 tick 关掉；时间语义必须分清——**计时用单调时钟（nanoTime）、定时刻用墙上时钟、分布式正确性不依赖跨机时间**；虚拟化下时钟由半虚拟化时钟源保障。Java 的 `currentTimeMillis` 20ns 与 `sleep(1)` 的 1ms+ 之间的鸿沟，正是 TSC 直读与 hrtimer 中断两条路径的物理差异。
