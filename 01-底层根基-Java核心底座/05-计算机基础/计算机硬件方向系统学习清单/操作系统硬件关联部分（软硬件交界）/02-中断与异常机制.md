# 02 中断与异常机制

> 中断是硬件对操作系统的"敲门"：网卡收到包、磁盘读完数据、时钟到点——都是中断把 CPU 从用户代码里拽进内核。异常则是 CPU 对执行流自身的"报警"。两者共用一张 IDT 表，却语义完全不同

## 1. 三类事件：中断、异常与系统调用

| 维度 | 中断（Interrupt） | 异常（Exception） | 系统调用 |
|------|:---:|:---:|:---:|
| 来源 | 硬件外部（设备） | CPU 内部（指令执行） | 软件主动 |
| 是否同步 | **异步**（随时可能到） | **同步**（指令的直接结果） | 同步 |
| 是否可预测 | 不可预测 | 可预测（缺页、除零） | 主动发起 |
| 返回值 | 回到被打断的指令继续 | 分三种情况（见下） | 回到调用处 |
| 典型例子 | 网卡 RX、磁盘完成、时钟 | 缺页 #PF、除零 #DE、#GP | read()、write() |

异常的三种返回语义（这是最容易混淆的点）：

| 异常类型 | 返回点 | 例子 | 处理方式 |
|---------|-------|------|---------|
| Fault（故障） | 返回**当前指令**重新执行 | 缺页 #PF | 内核填好页后重跑 |
| Trap（陷阱） | 返回**下一条**指令 | 断点 int 3、溢出 | 调试器接管 |
| Abort（中止） | 不返回，系统级错误 | 硬件错误 #MC | 记录后终止 |

> 💡 **int 3 断点是陷阱不是中断**：GDB 下断点本质是往指令里写 0xCC，CPU 执行到它产生 #BP 陷阱，调试器在异常处理里接管。所以"中断"这个中文词经常被滥用——严格说，**异常是 CPU 自己抛的，中断是硬件敲的**。

## 2. IDT 与中断向量

x86 用 **IDT（Interrupt Descriptor Table）** 把事件编号映射到处理函数：中断向量号 → 门描述符 → 处理入口地址。

### 2.1 向量号分配

| 范围 | 用途 | 说明 |
|:---:|------|------|
| 0-31 | **CPU 保留异常** | 不可修改，硬件定义 |
| 32-255 | 可编程中断 | Linux 从中分配 IRQ |

CPU 保留的常用异常向量：

| 向量 | 名称 | 触发场景 |
|:---:|------|---------|
| 0 | #DE 除零 | `i / 0` |
| 6 | #UD 非法指令 | 执行未知 opcode |
| 13 | #GP 通用保护 | 特权级违规、越界访问 |
| 14 | #PF 缺页 | 页不存在/权限不足 |
| 3 | #BP 断点 | int 3 |

### 2.2 IDT 加载与安全

```asm
; 内核启动时：
sidt  ; 查看当前 IDT（Ring0 才能执行）
lidt  [idtr]  ; 加载 IDT 基址（Ring0 才能执行）
```

⚠️ **IDT 是内核安全核心**：如果攻击者能改写 IDT，等于劫持所有中断/异常——所以 IDT 本身放在内核只读区域，`lidt` 是特权指令。Windows 曾出现过利用 IDT 攻击的旧漏洞（针对 32 位内核），现代内核把 IDT 放进只读页并启用 SMEP/SMAP 防御（见 01/04 篇）。

## 3. 中断控制器：8259 → APIC → MSI/MSI-X

中断不是设备直接连 CPU——经过**中断控制器**路由。三代数控器演进：

| 时代 | 控制器 | 能力 | 问题 |
|------|--------|------|------|
| 1980s | 8259 PIC（可编程中断控制器） | 级联最多 15 个 IRQ | 单 CPU、无优先级抢占细节、慢 |
| 1990s+ | **APIC**（本地 + I/O APIC） | 多核路由、256 向量、IRQ 重映射 | 仍走"中断线" |
| 2000s+ | **MSI/MSI-X**（消息信号中断） | 设备写内存地址产生中断、每队列独立中断 | 需要 PCIe 支持 |

### 3.1 MSI-X 是现代高性能设备的标配

**MSI-X 的本质**：设备通过 PCIe 总线向指定内存地址（APIC 页）写一个 32 位消息 → 直接触发指定 CPU 的指定中断向量。核心优势：

1. **每个队列一个中断**：NVMe 硬盘 16-64 个队列，每个队列绑定一个 MSI-X 向量和独立 CPU——这就是"多队列 + 中断负载均衡"的硬件基础，Kafka/Redis 等靠它摊平中断开销。
2. **免共享中断线**：传统 IRQ 共享（多个设备一个 IRQ）要遍历所有驱动，MSI-X 免掉。
3. **中断亲和性可编程**：`echo 2 > /proc/irq/85/smp_affinity` 就是改写 MSI-X 路由。

```bash
# 查看设备的中断分布（Linux）
cat /proc/interrupts | grep -E "eth0|nvme"
# 输出中 1-32 为 CPU 编号，可看到每个 CPU 处理的该设备中断次数
```

## 4. 一次中断的完整处理流程

以网卡收到数据包为例：

```text
① 网卡收到数据帧 → DMA 写入内存的 RX 环形队列（不占 CPU！）
② 网卡通过 MSI-X 发出中断 → 本地 APIC 接收
③ CPU 硬件动作：
    - 保存当前上下文（寄存器、RFLAGS 等压入当前栈/中断栈）
    - 查 IDT 找到中断门 → 特权级切到 Ring0 → 跳转入口
    - 关中断（IF 清 0，中断门默认关）
④ 内核入口代码（entry_64.S 的 common_interrupt）：
    - 保存所有寄存器到 pt_regs
    - 调 do_IRQ() → 查 irq_desc 表 → 找对应驱动
    - 驱动 handler：读设备状态、确认中断（ack）、处理数据
⑤ 处理完 → 恢复寄存器 → iretq 返回用户态（或内核态继续）
```

### 4.1 两次关中断的时机（容易混淆）

| 时机 | 谁关的 | 何时重开 |
|------|--------|---------|
| 进入中断门时 | 硬件自动 | 中断处理程序内重新开（`sti`/`local_irq_enable`） |
| 临界区（spinlock 区域） | 内核软件 | 退出临界区 |

> ⚠️ **为什么进中断门默认关中断**：防止同一中断递归重入、防止中断打断中断导致栈溢出。但 Linux 中断处理程序通常会很快 `sti` 重开中断——因为"关中断太久"是现代内核最忌惮的性能/延迟杀手（关中断期间连时钟都不准）。

### 4.2 中断栈：不在用户栈上处理

Ring0 处理中断时**不能继续用用户栈**（防跳板攻击、防溢出），x86 提供了：

- **TSS.IST（Interrupt Stack Table）**：最多 7 个独立中断栈，供不同优先级中断使用（现代 Linux 用 IST 给 #DF、#NMI、#MC 等关键异常分配专用栈）。
- 普通中断用**内核栈**（每任务 16KB，`THREAD_SIZE`），异常时切换到它。

## 5. 上半部与下半部：软中断的诞生

中断处理必须"快"（因为关着中断或锁），但工作量大（处理几十个网络包）。Linux 的答案：**拆两半**。

| 部分 | 执行上下文 | 特点 | 例子 |
|------|-----------|------|------|
| **上半部**（hardirq） | 中断上下文，禁止抢占 | 快进快出：ack、标记、收包到队列 | 网卡 handler 只把 skb 挂到 backlog |
| **下半部**（softirq） | 软中断上下文/进程上下文 | 慢活：协议栈处理、IO 完成 | net_rx_schedule → 网络协议栈 |

下半部的三种实现（演进史）：

| 机制 | 时代 | 特点 | 现状 |
|------|------|------|------|
| softirq | 2.3 引入 | 内核线程 ksoftirqd 或中断返回时执行，性能最好 | 网络栈仍用它 |
| tasklet | softirq 的封装 | 可动态注册 | 新代码禁止使用（文档明示） |
| workqueue | 1990s 至今 | 跑在**进程上下文**，可睡眠，通用 | **新代码首选**（`schedule_work`） |

> 💡 **为什么 Java 感知不到中断**：Java 应用跑在进程上下文，中断处理对它是"透明的"——但感知不到不等于无成本：每秒几万次硬中断会吃 CPU 时间片、污染 cache、加剧 TLB 压力（这就是为什么 Kafka/Redis 部署要 `irqbalance` 或手动设置中断亲和性）。

## 6. 多核环境下的中断分发

单核时代中断都打向一个 CPU，多核时代必须路由：

| 机制 | 说明 |
|------|------|
| **IRQ affinity** | 把某个 IRQ 绑定到指定 CPU：`echo 3 > /proc/irq/85/smp_affinity`（二进制位图） |
| **irqbalance** | 守护进程自动均衡各 CPU 中断负载 |
| **RPS/RFS**（软件） | 接收包处理在软件层按流哈希到多核（`/proc/sys/net/core/rps_cpus`） |
| **多队列 + MSI-X** | 硬件层每队列独立中断向量 → 天然多核并行（NVMe、10G/100G 网卡标配） |

**中断亲和性调优的经典问题**：收包中断在 CPU2，应用进程却在 CPU8 → 数据从 CPU2 的 cache 跨核到 CPU8（缓存一致性开销）。最佳实践是"中断、应用、内存分配尽量同核/同 NUMA 节点"——这正对应 08 篇的 NUMA 亲和性。

## 7. 中断与 Java 应用的关系

| 现象 | 中断层面的解释 |
|------|---------------|
| `top` 里 %si（软中断）高 | 网络/磁盘中断处理量大，常见于高吞吐 IO 服务 |
| epoll 的 ET 模式"惊群" | 多线程同时 epoll_wait 时 EPOLLIN 事件唤醒多个线程（与中断无关，但同属"事件驱动"模型） |
| JVM Full GC 时 `safe point` 停顿 | 依赖**安全点中断**：所有线程跑到安全点（相当于"软件中断"）才停——涉及 CPU 计数中断（safepoint polling） |
| 延迟抖动（P99 毛刺） | 网卡中断风暴、`sysctl net.core.netdev_budget` 耗尽预算导致收包延迟 |
| Java NIO 本质 | `epoll_wait` 是系统调用，epoll 事件由内核在**中断上下文**收包、软中断处理协议栈后置入就绪队列——一条链路：网卡中断 → softirq → epoll 就绪 → 系统调用返回 |

> 🎯 **一句话给 Java 开发者**：你的 NIO 服务每收到一个包，都经历了"网卡 MSI-X 中断 → 内核收包 → 软中断协议栈 → epoll 队列 → read() 系统调用"这条完整链路——中断是链路的起点，理解它才知道为什么 `net.core.rmem_max`、IRQ 亲和性这些参数能影响 Java 服务的 P99。

### 7.1 中断风暴（Interrupt Storm）与防护

**中断风暴**：设备以远超处理能力的速度发中断，CPU 忙于进/出中断上下文，正常任务饿死——表现为主机 CPU 100% 而业务几乎无吞吐：

| 常见诱因 | 排查手段 | 防护措施 |
|---------|---------|---------|
| 网卡丢包重传风暴 | `ethtool -S eth0` 看 drop/err 计数 | 调大 ring buffer、关小 irq coalescing 冲突参数 |
| 坏设备疯狂发 MSI | `perf top` 看中断占比、/proc/interrupts 突增 | 隔离坏设备、升级固件 |
| 虚拟化中断失控 | 宿主 `top` 看 %si 高 | KVM 侧 APICv/PI 生效检查 |
| NMI 看门狗误报 | dmesg 查 NMI 日志 | 调 watchdog 参数 |

```bash
# 快速定位中断风暴
watch -n1 "cat /proc/interrupts | head -20"   # 观察哪个中断号暴涨
top -n1 | head -5                              # %si（软中断）%hi（硬中断）占比
perf stat -e irq_vectors:* -a sleep 2          # 统计中断向量分布
```

> ⚠️ **关键认知**：中断风暴的根治靠"降频"——中断合并（irq coalescing）、NAPI 轮询切换、多队列分摊；`/proc/irq/N/smp_affinity` 绑定只是"摊平"，不是"减少"。

### 7.2 NMI 与机器检查异常（#MC）

常规中断之外有两类特殊事件：

| 事件 | 特点 | 处理 |
|------|------|------|
| **NMI（不可屏蔽中断）** | 无法被 `cli`/`sti` 屏蔽 | 硬件看门狗（watchdog）、性能计数器溢出、SMI |
| **#MC（机器检查异常）** | 硬件自检发现严重错误（内存 ECC 错误、总线错误） | 内核 MCE 处理：记录、隔离坏页、必要时 panic |

```bash
# 查看硬件错误记录（Intel MCE 日志）
dmesg | grep -i "mce\|machine check"
journalctl -k | grep -i "corrected\|uncorrected"
```

> 💡 **ECC 内存与 MCE**：服务器内存带 ECC 纠错——单比特错误自动纠正（corrected，dmesg 有记录），双比特错误触发 #MC（uncorrected）→ 内核标记该物理页隔离（HWPoison），避免后续访问踩雷。**这正是"服务器为什么必须用 ECC 内存"的硬件层答案**：数据完整性不是靠软件，是 CPU 检测+OS 隔离。

### 7.3 IRQ 与 irqdomain：中断号的抽象层

| 层级 | 编号体系 | 说明 |
|------|---------|------|
| 硬件向量 | 0-255（APIC） | 设备实际触发 |
| Linux IRQ 号 | 动态分配（如 85） | `/proc/interrupts` 中看到的 |
| irqdomain 映射 | 硬件中断线 ↔ Linux IRQ 号 | 支持 MSI-X 动态分配、CPU 亲和性 |

```text
irqdomain 的现代意义：
  老式设备：固定 IRQ 线（PCI 中断共享）
  现代设备：MSI-X 动态分配向量 → 每个队列独立 IRQ 号
  内核用 irqdomain 把"哪个设备哪个队列"组织成树状结构，
  IRQ 亲和性/负载均衡/虚拟化直通都基于这个抽象
```

> 💡 **对排查的意义**：`/proc/interrupts` 的第一列是 Linux IRQ 号，`/proc/irq/N` 目录里有 `affinity_hint`（驱动建议的亲和 CPU）与 `effective_affinity`（实际生效）——调中断亲和性先看这两个文件，而不是瞎绑定。

### 7.4 中断延迟的测量与解读

| 测量点 | 含义 | 工具 |
|--------|------|------|
| 中断产生到 CPU 响应 | 硬件+向量处理 | 逻辑分析仪（硬件） |
| 中断到上半部完成 | 内核路径 | ftrace（irqsoft） |
| 中断到应用可见 | 完整链路 | `perf sched`、bcc `hardirqs` |

```bash
# 观测硬中断/软中断耗时分布
bcc/tools/hardirqs.py 2>/dev/null || perf trace -e irq_vectors:* -a sleep 5
```

| 延迟量级 | 环节 | 优化 |
|:---:|------|------|
| ~1μs | 硬件识别+压栈 | 无（硬件） |
| ~2-5μs | 内核中断入口+上半部 | 精简 handler |
| ~5-15μs | 软中断处理+协议栈 | NAPI 预算、RSS |
| ~10-100μs | 应用唤醒（调度延迟） | 实时优先级、CPU 亲和 |

> 💡 **关键认知**：中断延迟的"大头"往往不在中断本身，而在**唤醒应用的那一跳**（调度延迟）——所以低延迟网络应用的优化重点是"epoll 返回后立刻被调度"（绑定核+RT 优先级），而不是纠结中断处理快 1μs。

### 7.5 中断与信号：两个容易混淆的"通知"

| 维度 | 中断 | 信号（signal） |
|------|------|---------------|
| 来源 | 硬件设备 | 内核/进程软件 |
| 目标 | CPU 当前执行流（内核处理） | 指定进程（用户态处理） |
| 语义 | 硬件事件（收包、时钟） | 软件事件（SIGKILL、SIGPIPE） |
| 处理位置 | 中断上下文（不能睡） | 进程上下文（可睡） |
| Java 对应 | 无直接对应 | `Runtime.addShutdownHook`、`kill -9` 不可捕获 |

> ⚠️ **区分要点**：中断打断的是 CPU，信号打断的是进程；中断处理在内核态"替设备干活"，信号处理在用户态"通知应用"。Java 的 SIGINT/SIGTERM 优雅停机就是信号机制，而网卡收包是中断机制——两者一条链路（中断收包 → 唤醒进程），但语义完全不同。

**补充：缺页异常（#PF）为何是性能分析的富矿**——每次内存首次访问、COW 复制、swap 换入都会触发 #PF；`ps -o minflt,majflt` 与 `/proc/vmstat` 的 pgfault 计数是判断"内存行为健康度"的第一指标：majflt 突增 = swap 活动 = 系统在"假死"边缘。

**再补一条：内核怎么区分"该修好的异常"和"该杀的异常"？**——缺页（#PF）是可恢复 Fault（内核填页后重跑指令）；除零（#DE）是不可恢复 Fault（内核向进程发 SIGFPE）；非法指令（#UD）同理发 SIGILL。**异常的"语义分工"决定进程生死**，Java 的 ArithmeticException 底层就是 #DE → SIGFPE → JVM 转译。

## 8. 核心要点

> 🎯 **核心要点**：中断=硬件异步敲门（走 IDT 中断门，处理要快），异常=CPU 同步报警（Fault 重跑当前指令/Trap 跑下一条/Abort 终止），系统调用=软件主动申请；现代硬件用 MSI-X 让每个设备队列拥有独立中断向量并绑定指定 CPU；内核用"上半部+下半部"把必须快的和可以慢的分开；多核下中断亲和性是性能调优的第一杠杆。
