## 1. 启动链路全景

```text
① 按下电源键 → 电源就绪 → CPU 复位
② CPU 从固定地址取第一条指令（x86: UEFI 固件入口；旧式: 0xFFFF0 跳 BIOS）
③ 固件（UEFI）自检（POST）→ 枚举设备 → 建立服务环境
④ Secure Boot 校验引导器签名
⑤ UEFI 按 BootOrder 加载引导器（GRUB2/shim）
⑥ 引导器加载内核（bzImage 压缩镜像）+ initramfs 到内存
⑦ 内核解压自举 → 建立页表/IDT → 启动各子系统
⑧ 内核挂载 initramfs 根文件系统 → 执行 /init（systemd）
⑨ systemd 并行启动服务 → 挂载真实根 → 登录界面/容器运行时
```

> 💡 **第一行代码在哪**：x86 CPU 复位后从 `0xFFFFFFF0`（UEFI 时代映射到固件 ROM）取第一条指令——即**固件**是第一段执行的代码，它比操作系统更"底层"，属于硬件与软件的中间层。

## 2. 固件演进：BIOS → UEFI

| 维度 | BIOS（Legacy） | UEFI（现代） |
|------|---------------|-------------|
| 时代 | 1981-2010s | 2010s 起主导，2020s 全面取代 |
| 接口 | 16 位实模式、int 0x10/0x13 中断 | 64 位 C 语言 API（Boot Services） |
| 磁盘分区 | MBR（最多 4 主分区，2TB 上限） | **GPT**（128+ 分区，EBR 容量无上限） |
| 启动方式 | 磁盘第一个扇区 512B 代码 | **EFI 系统分区（ESP，FAT32）** 中的 .efi 文件 |
| 扩展 | 选项 ROM 硬编码 | **驱动可加载模块**（从 ESP/固件存储读） |
| 安全 | 无信任链 | Secure Boot（签名校验） |
| 配置存储 | CMOS | **NVRAM**（efibootmgr 管理启动项） |

```bash
# UEFI 时代常用命令
efibootmgr -v                # 查看启动项
ls /sys/firmware/efi/        # 存在 = 当前是 UEFI 启动
dmesg | grep -i uefi
```

> ⚠️ **GPT 与 MBR 的分工**：分区表由固件规范决定——UEFI 强制 GPT，BIOS 用 MBR（Linux 下 GPT 也可被 BIOS 引导器读，但 ESP 是 UEFI 的核心标志）。**2026 年所有主流发行版/云镜像均为 UEFI+GPT**。

## 3. Secure Boot 与 TPM 2.0

### 3.1 信任链（Chain of Trust）

```text
UEFI 固件（内置微软/厂商根证书）
  → 校验 shim（第一级引导器，微软签名）
  → shim 校验 GRUB2（发行版密钥签名）
  → GRUB2 校验内核 + initramfs
  → 内核校验模块签名（Linux 7.0 起支持 ML-DSA 后量子签名！）
```

| 环节 | 校验方式 | 2026 状态 |
|------|---------|----------|
| 固件→shim | 微软 UEFI CA 签名 | 标配 |
| shim→GRUB | 发行版 MOK 密钥 | 标配 |
| GRUB→内核 | 发行版签名 | 标配 |
| 内核模块 | 模块签名 | 7.0 加入 ML-DSA 后量子算法，移除 SHA-1 |

### 3.2 TPM 2.0 的角色

| 能力 | 用途 |
|------|------|
| PCR 寄存器（测量值） | 记录启动链每步的哈希，篡改即检测 |
| 密封（Sealing） | 密钥只在 PCR 值匹配时释放（防启动链被改后解密磁盘） |
| 远程证明 | 云/企业环境验证主机固件可信度 |

> 💡 **2026 现状**：TPM 2.0 是 Windows 11 强制要求，Linux 发行版（systemd 自带 `systemd-cryptenroll`）用 TPM 自动解锁 LUKS 磁盘成为主流姿势——安全性与可用性兼得。

## 4. bootloader：GRUB2 与 shim

| 引导器 | 职责 | 备注 |
|--------|------|------|
| **shim** | 被固件验证的第一环，再验证 GRUB | 微软签名，解决"发行版密钥不被固件信任" |
| **GRUB2** | 显示菜单、加载内核与 initramfs、传启动参数 | 功能最全（链式加载、多系统） |
| systemd-boot | 极简 UEFI 引导器 | 单系统/容器镜像场景更轻 |

GRUB2 的核心动作：

```bash
# 内核 + initramfs 加载（GRUB 配置核心）
linux /vmlinuz-7.2.0 root=UUID=xxxx ro quiet intel_iommu=on
initrd /initramfs-7.2.0.img
```

> 💡 **内核是"压缩自举"的**：`bzImage` 是自解压镜像——GRUB 只负责把它读到内存，解压、建页表、设 IDT 全是内核自己干（见第 5 节）。这也是"为什么内核更新要重启"的根源：启动期初始化不可热替换。

## 5. 内核启动六阶段

| 阶段 | 动作 | 关键机制 |
|:---:|------|---------|
| 1 解压自举 | 压缩镜像自解压到内存 | 实模式→保护模式→长模式切换 |
| 2 早期页表 | 建立 1:1 映射 + 内核映射 | CR3 指向初始页表 |
| 3 基础初始化 | 设 GDT/IDT、切换栈、读 CPU 特性 | CPUID 探测、MSR 设置 |
| 4 子系统启动 | 内存管理（mm_init）、调度器、中断 | 从"单个 CPU"到"多核启动"（BSP 唤醒 AP） |
| 5 设备驱动 | 枚举 PCIe、加载驱动、注册中断 | ACPI/设备树驱动来源（第 6 节） |
| 6 用户态接力 | 挂载 initramfs → exec /init | 移交 systemd |

**多核启动细节**：BSP（引导 CPU）先跑，通过 **SIPI（Startup IPI）** 唤醒 AP（应用 CPU），每个 AP 独立初始化自己的本地 APIC、页表副本——这就是"启动时 CPU0 忙、其他核排队"的硬件原因。

## 6. 硬件描述：ACPI 与设备树

内核如何知道机器上有哪些硬件？两种描述机制：

| 机制 | 平台 | 形式 | 内容 |
|------|------|------|------|
| **ACPI** | x86（UEFI 配套） | 固件提供表（内存中） | 电源管理、设备枚举、热插拔、中断路由表（MADT） |
| **设备树（DT）** | ARM/RISC-V（嵌入式起家） | 二进制 .dtb 文件 | 设备拓扑、寄存器地址、中断号、时钟 |

```bash
# ACPI 表查看
ls /sys/firmware/acpi/tables/     # DSDT、MADT、FADT...
# 设备树查看（ARM 设备）
ls /proc/device-tree/
```

> 💡 **为什么 ARM 服务器能跑 Linux**：设备树/ACPI 让同一内核无需重新编译就能适配不同硬件——ARM 服务器领域 2026 年已普遍采用 ACPI（服务器统一）与 DT（边缘设备）。"内核与硬件解耦"正是从这套描述机制开始的。

## 7. initramfs 与 systemd 并行启动

| 概念 | 作用 |
|------|------|
| **initramfs**（早期根文件系统） | 临时根：包含加载真实根所需的驱动（磁盘、加密、LVM）——因为真实根可能加密/在 RAID 上，早期阶段没有驱动访问不到 |
| systemd | 1 号进程，管理所有服务 |

```text
systemd 并行启动模型：
  ┌─ 挂载真实根（switch_root）─→ 启动 systemd（PID 1）
  ├─ systemd 按依赖图并行启动服务（默认 128 个 Job 并发）
  ├─ 关键路径：本地服务 → 网络 → 容器运行时/sshd
  └─ 统计：现代发行版 10-30 秒到登录界面
```

| 启动阶段 | 耗时占比（典型） |
|---------|:---:|
| 固件 POST | 5-15% |
| 引导器+内核 | 10-20% |
| systemd 服务 | 60-80%（大部分时间在这） |

## 8. 容器 vs 虚拟机启动：交界视角

| 维度 | 虚拟机 | 容器 |
|------|--------|------|
| 是否启动固件/内核 | **完整启动链路**（固件→引导→内核） | 不启动！复用宿主机内核 |
| 启动时间 | 30s-2min | <1s |
| 隔离边界 | 硬件（虚拟 CPU/内存/IO） | 内核功能（namespace/cgroup） |
| 启动动作 | 固件校验+驱动加载 | 仅 clone + 挂载 + exec |
| 内核态代码 | 独立的客户机内核 | 共享宿主内核（漏洞影响面大） |

> 🎯 **一句话**：容器快是因为**跳过了整个软硬件交界**（固件/引导/驱动），直接在内核的命名空间里 clone 一个"进程视图"；虚拟机慢是因为要复刻一遍完整的启动故事。云原生时代"秒级启动"的本质是"不做启动"。

### 8.1 启动故障排查清单

| 故障现象 | 定位阶段 | 排查手段 |
|---------|---------|---------|
| 电源灯亮无显示 | 固件 POST | 看板载诊断灯/蜂鸣码、拔外设逐项测 |
| 卡在固件 Logo | 固件自检 | 检查内存条/磁盘/启动项顺序 |
| `No bootable device` | 引导器阶段 | `efibootmgr -v` 查启动项、ESP 分区是否损坏 |
| Secure Boot 错误 | 信任链 | 查看固件日志、MOK 管理（`mokutil`） |
| 内核 panic 重启 | 内核启动 | `dmesg` 看最后日志、`systemd-boot`/GRUB 加 `nomodeset` |
| 卡在"Waiting for device" | initramfs | 确认根分区 UUID 与 fstab 一致 |
| 服务启动慢 | systemd | `systemd-analyze blame` 查耗时服务 |

```bash
# systemd 启动分析三板斧
systemd-analyze                       # 总启动时间（固件/内核/用户态分段）
systemd-analyze blame                 # 按服务耗时排序
journalctl -b -1 -p err               # 上一次启动的错误日志
```

> ⚠️ **关键定位原则**：启动故障先分"段"——固件段（无画面）、引导段（无 bootable device）、内核段（panic 前 dmesg）、用户态段（systemd 服务）。90% 的"起不来"在磁盘/分区/UUID 三件事。

### 8.2 内核启动参数速查

| 参数 | 作用 | 场景 |
|------|------|------|
| `root=UUID=...` | 指定根文件系统 | 磁盘变更后 UUID 失效是头号启动故障 |
| `quiet splash` | 静默启动 | 排障时去掉，看完整启动输出 |
| `nomodeset` | 禁用显卡模式设置 | 显卡驱动导致黑屏 |
| `intel_iommu=on` | 开启 IOMMU | 虚拟化直通/DMA 隔离 |
| `nohz_full=1-7` | Full dynticks CPU 隔离 | 低延迟工作负载 |
| `isolcpus=1-7` | 从调度器隔离 CPU | RT/专用核 |
| `systemd.unit=emergency.target` | 进入救援模式 | 系统起不来时修复 |

### 8.3 云镜像与容器镜像的启动对比

| 维度 | 云主机镜像（UEFI 启动） | 容器镜像（不启动固件） |
|------|------------------------|----------------------|
| 内容 | 分区表 + 内核 + initramfs + 发行版 | 只含应用运行时（Java + 依赖） |
| 启动动作 | 固件校验 → 引导 → 内核 → systemd | 直接 exec 入口程序 |
| 启动耗时 | 30s-2min | <1s（首次拉取镜像除外） |
| 安全信任 | Secure Boot 信任链 | 镜像签名 + 运行时隔离 |

> 💡 **K8s 视角**：Pod 的"容器"不含内核；Pod 里的 pause 容器是"初始化网络命名空间"的占位符——**容器编排的"启动"完全绕开了 09 篇的固件-内核链路**，所以秒级伸缩才可能。理解这点，"为什么容器不能改内核参数"（除非 privileged）也就自然清楚了。

### 8.4 固件更新与安全基线

| 事项 | 实践 |
|------|------|
| 固件版本跟踪 | 订阅厂商 CVE 公告（BIOS/UEFI 漏洞是"物理级"风险） |
| 更新节奏 | 云服务器由云商管理；裸金属需季度评估 |
| Secure Boot 策略 | 关闭会打开物理攻击面（evil maid 攻击），生产保持开启 |
| TPM 用途 | 磁盘加密（LUKS+TPM 自动解锁）+ 远程证明 |
| 后量子签名 | Linux 7.0 起内核模块支持 ML-DSA——发行版逐步切换 |

> ⚠️ **2026 安全基线**：裸金属服务器三件套 = UEFI Secure Boot 开启 + TPM 2.0 激活 + 固件季度更新；虚拟化环境由云商托管固件，但要在租户侧验证机密计算与启动证明能力（见 10 篇）。

### 8.5 启动与固件面试追问

**Q1：按下电源键后第一行代码在哪？**
答：CPU 复位后从固定地址（UEFI 映射的固件 ROM）取第一条指令——固件先执行（POST+初始化），然后按 BootOrder 加载引导器。

**Q2：UEFI 和 BIOS 的区别？**
答：BIOS 是 16 位实模式+MBR+512B 引导扇区（2TB/4 分区上限）；UEFI 是 64 位+GPT+ESP 分区里的 .efi 文件+Secure Boot——现代平台全用 UEFI。

**Q3：Secure Boot 怎么保护启动链？**
答：信任链——固件验 shim（微软签名）→ shim 验 GRUB（发行版密钥）→ GRUB 验内核/模块（内核 7.0 起支持 ML-DSA 后量子签名）；任何一环被篡改即拒绝启动。

**Q4：initramfs 是干什么的？**
答：临时根文件系统，包含访问"真实根"所需的驱动（磁盘、加密、LVM）——没有它，加密根分区在早期阶段根本无法解锁挂载。

**Q5：为什么容器启动只要 1 秒而虚拟机要 1 分钟？**
答：容器跳过整个固件-内核链路（共享宿主内核，直接 clone+exec）；虚拟机要完整走一遍"固件校验→引导→内核初始化→驱动加载→systemd"。

### 8.6 systemd 常用排查命令

| 命令 | 用途 |
|------|------|
| `systemd-analyze blame` | 服务启动耗时排序 |
| `systemd-analyze critical-chain` | 关键路径（启动链路瓶颈） |
| `journalctl -b -1 -p err` | 上次启动错误日志 |
| `systemctl list-units --failed` | 失败服务 |
| `systemctl status sshd` | 单服务状态与日志 |
| `systemd-analyze security` | 服务安全基线评分 |

> 💡 **排查思路**：启动慢 → 先 critical-chain 找关键路径 → 对耗时服务看日志（常见元凶：网络等待、数据库连接超时、日志磁盘满）。"启动优化"的工程本质是让关键路径上的服务并行+尽快就绪。

### 8.7 云租户视角的启动与固件基线

| 场景 | 基线要求 |
|------|---------|
| 虚拟机（云商托管固件） | 验证 Secure Boot 状态、启用 TPM 直通（vTPM）、检查启动链日志 |
| 裸金属 | UEFI Secure Boot + TPM 2.0 + 固件季度更新 + BMC/带外管理加固 |
| 容器宿主 | 内核版本跟踪（CVE-2026-31431 等）、不可变 OS 镜像（如 Flatcar） |
| 合规审计 | 启动链证明（TPM 远程证明）作为审计证据链一环 |

> 🎯 **一句话收官**：启动与固件是"可信计算基（TCB）"的物理载体——云上的每台实例，信任都始于固件第一行代码。2026 年 TPM+Secure Boot+机密计算的组合，让"不可信硬件"成为历史命题。

**补充：BIOS 时代如何引导现代内核？**——兼容模式（CSM）下 BIOS 读 MBR 512B → 引导代码 → GRUB → 内核实模式入口。2026 年 CSM 已被 UEFI 全面取代（Windows 11/新发行版强制 UEFI），但理解"512B 引导扇区 → 二级引导器 → 内核"的链路，仍是读懂引导器代码的基础。

**再补：内核参数怎么落地生效？**——GRUB 把 cmdline 传给内核（`/proc/cmdline` 可见），一部分由内核直接消费（root、quiet），一部分由驱动/子系统消费（intel_iommu、nohz_full）。**改完要更新 GRUB 配置**（`grub2-mkconfig`/`update-grub`）才会写入下一次启动，临时生效用 `sysctl`（运行时）。

**延伸阅读**：systemd 细节与容器运行时（Docker 等）在「Linux 操作系统」「Docker」体系中有完整展开——本篇文章是它们共同的"启动学"基础。

**补充：启动性能优化的三大抓手**——① 固件段：关无用外设自检（POST 缩短）；② 引导段：内核参数 `quiet` + 精简 initramfs（`dracut --hostonly`）；③ 用户态：systemd 并行度拉满 + 关键服务提前（`systemd-analyze critical-chain` 找瓶颈）。**云上容器场景则另有一条路：跳过启动（预热镜像/快照）**——记住"优化启动"和"跳过启动"是两种不同的问题。

**最后一句**：每次开机都是一次"硬件与软件的重新认识"——读一次 `dmesg` 启动日志，比看十篇博客更懂你的机器。

## 9. 核心要点

> 🎯 **核心要点**：启动链路 = 固件（BIOS→UEFI 已全面换代，GPT+ESP+Secure Boot 标配）→ shim/GRUB2（信任链校验，内核 7.0 支持 ML-DSA 后量子签名）→ 内核自举六阶段（BSP 唤醒 AP 多核启动）→ ACPI/设备树描述硬件 → initramfs 过渡 → systemd 并行拉起服务；TPM 2.0 把启动链测量变成可证明的信任锚；容器"启动快"的本质是跳过了整个固件-内核交界——这套链路也是排查"为什么服务器起不来/启动慢"的第一张地图。
