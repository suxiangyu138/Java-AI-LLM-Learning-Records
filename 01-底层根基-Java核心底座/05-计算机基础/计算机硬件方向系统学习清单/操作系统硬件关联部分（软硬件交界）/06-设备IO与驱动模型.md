# 06 设备 IO 与驱动模型

## 1. 设备如何被看见：MMIO 与端口 IO

CPU 与外设通信有两种地址空间：

| 方式 | 机制 | 现代状态 |
|------|------|---------|
| 端口 IO（PIO） | 专用 IN/OUT 指令访问 64KB IO 端口空间 | 仅遗留（RTC、部分早期设备） |
| **MMIO（内存映射 IO）** | 设备的寄存器映射到物理地址空间，用普通访存指令读写 | **现代标准** |

```text
MMIO 工作方式：
  设备寄存器（如网卡控制寄存器）被映射到某段物理地址
  CPU 执行 mov [0xFE000000], eax → 实际是写网卡寄存器
  好处：无专用指令、与 cache 协同（可设置 uncacheable）
  坑：MMIO 地址不能过 TLB/缓存（标记 UC），否则读到脏数据
```

> 💡 **区分 MMIO 与 DMA**：MMIO 是"CPU 读写设备的寄存器"（控制面），DMA 是"设备自己读写内存"（数据面）。控制用 MMIO、数据用 DMA——这是所有现代设备的通用分工。

## 2. PCIe 配置空间与设备发现

系统启动时（或热插拔时），操作系统通过 **PCIe 配置空间**发现设备：

| 配置空间字段 | 含义 |
|-------------|------|
| Vendor ID / Device ID | 设备身份（0x8086 = Intel） |
| BAR（Base Address Register） | 设备的 MMIO 基址（由内核分配） |
| Class Code | 设备类别（网卡/磁盘/显卡） |
| Capability 列表 | 支持的扩展能力（MSI-X、SR-IOV、P2P） |

```bash
lspci -vvv          # 查看设备与能力（MSI-X、SR-IOV 等）
lspci -s 01:00.0 -xxx   # 原始配置空间
```

驱动加载流程：内核枚举 PCIe 设备 → 按 Vendor/Device ID 匹配驱动表 → 驱动 probe → 分配 BAR → 注册中断 → 设备可用。**现代 Linux 设备驱动可用 Rust 编写**（Linux 7.0 起 Rust 驱动正式转正，见 10 篇）。

## 3. IO 完成的三种方式：轮询、中断、DMA

### 3.1 控制流：轮询 vs 中断

| 方式 | CPU 行为 | 延迟 | CPU 占用 | 适用 |
|------|---------|:---:|:---:|------|
| 轮询（Polling） | 循环读设备状态寄存器 | 最低（无上下文切换） | 高（占满一个核） | 高吞吐网络（DPDK）、NVMe 高 IOPS 场景 |
| 中断（Interrupt） | 设备通知 → 进内核处理 | ~5-20μs | 低 | 通用场景 |

> ⚠️ **中断的代价悖论**：中断省 CPU 但每事件有固定开销（~5-20μs 的完整中断路径）；轮询把 CPU 占死但无切换。NVMe 极速设备（单盘百万 IOPS）中断风暴反而拖垮 CPU——所以现代方案是 **混合模式**：中断触发 → 高负载时切换为轮询（NAPI 的 busy-poll、NVMe poll queues）。

### 3.2 数据流：DMA（Direct Memory Access）

```text
无 DMA（PIO 传输，早期硬盘/低速设备）：
  CPU: 从设备寄存器读 1 字节 → 写内存 → 再读下 1 字节（每字节都占 CPU）

有 DMA（所有现代块/网络设备）：
  ① 驱动在内存中建好 DMA 缓冲区（内核页，物理连续或 IOMMU 映射）
  ② 把缓冲区地址+长度写入设备 DMA 描述符（经 MMIO）
  ③ 设备 DMA 引擎自行把数据写入内存（CPU 完全空闲！）
  ④ 设备发完成中断（或写完成位）→ CPU 处理数据
```

**DMA 的代价**：DMA 缓冲区要"钉住"（不换页）、地址要对齐、cache 一致性由总线/协议保证——现代 x86 通过 **IOMMU 的 cache-coherent DMA 窗口**解决，PCIe 设备访问内存默认走一致性路径（x86 是 cache-coherent DMA；部分 ARM SoC 需要显式管理）。

## 4. DMA 与 IOMMU：隔离的搬运工

### 4.1 没有 IOMMU 的隐患

设备 DMA 写内存 = 设备获得任意物理内存访问权。**恶意/故障设备可以直接改写内核内存**（经典 DMA 攻击：FireWire 设备 5 秒拿 root）。传统保护只针对 CPU 访存，管不了设备。

### 4.2 IOMMU（VT-d / AMD-Vi / ARM SMMU）

| 能力 | 说明 |
|------|------|
| 设备侧地址翻译 | 设备发出的 DMA 地址（IOVA）映射到物理地址，隔离设备 |
| 域隔离 | 设备只能访问内核分配给它的页（每设备/每虚拟化域独立） |
| 中断重映射 | 中断重映射表限制设备能触发的中断向量（防伪造 MSI 攻击） |
| 虚拟化直通 | 让 VM 直接拥有设备而不绕过隔离（见 10 篇） |

```text
启用状态（Linux）：
  kernel cmdline: intel_iommu=on / amd_iommu=on
  /sys/kernel/iommu_groups/ 下按组列出设备隔离情况
```

> ⚠️ **IOMMU 的代价**：每次 DMA 要查翻译表（类似 TLB，IOMMU 有 IOTLB）——高吞吐 IO 有 5-15% 开销；所以追求极限性能的 DPDK 场景会关闭 IOMMU 或用直通模式（安全性下降，需设备可信）。2026 云厂商普遍开启 IOMMU（安全默认）并靠 SR-IOV VF 直通分摊开销。

## 5. 多队列与 SR-IOV

### 5.1 多队列（Multi-queue）

现代网卡/NVMe 控制器有多个硬件队列（16-256 个），每个队列绑定一个 MSI-X 中断和专用 CPU：

```text
队列 0 ←→ 中断 0 ←→ CPU0   （收包/IO 处理全部本地化）
队列 1 ←→ 中断 1 ←→ CPU1
...
好处：无锁并行、cache 亲和、中断负载均衡（02 篇 6 节）
```

### 5.2 SR-IOV：一个物理设备拆出多个虚拟设备

| 概念 | 说明 |
|------|------|
| PF（Physical Function） | 物理设备，宿主驱动管理 |
| VF（Virtual Function） | 虚拟设备：独立的队列/中断/配置空间子集，可直接分配给虚拟机 |
| 分配方式 | `echo 1 > .../sriov_numvfs`，然后把 VF 透传给 VM（VFIO） |

SR-IOV 的价值：VM 里的网卡**不经过虚拟交换（virtio 路径）**，直接独占队列，性能接近裸机——云厂商 10G/25G/100G 网卡标准做法。

## 6. 用户态驱动：DPDK 与零拷贝

传统 IO 路径的每次数据要过内核（系统调用+拷贝），极限性能需要**绕开内核**：

| 方案 | 做法 | 代价 |
|------|------|------|
| **DPDK**（数据面） | 轮询模式 PMD 驱动直接操作网卡，用户态收发包 | 占满核、放弃内核网络栈、不能跑通用服务 |
| **io_uring**（控制面保留） | 内核异步 IO，免中断+免拷贝（固定缓冲、多队列） | 仍需内核路径（但成本接近零） |
| **spdk**（NVMe 版 DPDK） | 用户态直接操作 NVMe 队列 | 同 DPDK |

```text
传统路径：网卡 → 内核协议栈 → socket → 用户态（多次拷贝+系统调用）
DPDK 路径：网卡 → 用户态 PMD（轮询）→ 应用（一次拷贝甚至零拷贝）
收益：收包延迟从 ~10μs 级降到 ~1μs 级，吞吐 10G 线速（单核可胜任）
```

> 💡 **Java 生态 2026 现实**：Netty 仍基于 epoll/NIO（内核路径）；Java 侧想用 io_uring 需要 JNI 封装（Netty-incubator 有 io_uring 模块，仍实验性）；DPDK 主要用于网关/防火墙/负载均衡（C/C++ 实现，如 VPP）。**Java 中间件该懂的是"何时需要绕过内核"而不是盲目上 DPDK**——io_uring 已覆盖 90% 的优化空间。

## 7. IO 路径全景：从 Java 到磁盘

```text
Java FileChannel.write()  →  libc write() → syscall
  → VFS（虚拟文件系统）→ 页缓存（page cache，先写缓存！）
  → 文件系统层（ext4/xfs）组织元数据
  → 块层：构造 bio → 提交到 NVMe 驱动队列（多队列）
  → 驱动：填 DMA 描述符 → 设备 DMA 搬数据 → 完成中断（或 poll）
  → 写完成 → 页缓存标记脏页 → 后台回写（pdflush）
```

| 环节 | 硬件/内核机制 | 可调参数 |
|------|-------------|---------|
| 页缓存 | 内核内存直接当缓存（mmap 文件等于共享这份缓存） | `vm.dirty_ratio`、`vm.dirty_writeback_centisecs` |
| 块层队列 | NVMe 多队列（每核一队列） | `nr_requests`、`iosched`（none） |
| DMA | 设备直接写内存 | IOMMU 开关、`dma_map` 页对齐 |
| 完成通知 | MSI-X 中断或 poll 模式 | IRQ 亲和性、`nvme.poll_queues` |

### 7.1 NAPI 与中断收包预算

现代网络驱动用 **NAPI（New API）** 混合轮询与中断：

```text
NAPI 生命周期：
  ① 网卡收包 → 发中断 → 驱动 handler 注册 poll 回调，禁用该队列中断
  ② 内核 softirq 周期调用 poll：批量收包直到预算（budget）耗尽
  ③ 处理完 backlog → 重新启用中断 → 回到 ①
效果：流量低时中断驱动（低延迟），流量高时轮询驱动（低 CPU 开销）
```

| 参数 | 默认值 | 含义 |
|------|:---:|------|
| `net.core.netdev_budget` | 300 | 每次 softirq 最多处理包数 |
| `net.core.netdev_budget_usecs` | 8000 | 每次 softirq 最多处理时长（μs） |
| `net.core.busy_poll` | 0 | 应用层 busy-poll 开关 |

> ⚠️ **Java 联动**：`netdev_budget` 过小 → 高流量下收包延迟（P99 毛刺）；过大 → softirq 占用 CPU 过多（%si 高、业务线程饿）。Kafka/ES 压测时这两个参数是"吞吐 vs 延迟"的经典旋钮。

### 7.2 块 IO 调度器：从电梯算法到无调度

| 调度器 | 时代 | 思路 | 2026 状态 |
|--------|------|------|----------|
| CFQ | 2.6.18-5.x | 完全公平队列，按进程排队 | 已移除 |
| **mq-deadline** | 5.0+ | 按扇区排序（电梯）+ 截止时间 | 传统盘默认 |
| **none** | 5.0+ | 直接把请求交给 NVMe 硬件队列 | **NVMe 默认**（硬件队列数=核数） |

> 💡 **为什么 NVMe 用 none**：NVMe 控制器自带每核多队列 + 硬件调度，内核再做软件排序是纯浪费——"软件把控制权交还硬件"是 NVMe 时代的标志性设计。

### 7.3 io_uring 的三种优化叠加

| 优化层 | 机制 | 收益 |
|--------|------|------|
| 提交/完成环形队列 | 批量提交（IORING_ENTER_GETEVENTS） | 系统调用次数 ÷N |
| 固定缓冲（registered buffers） | 预注册内存，免每 IO 映射 | 消除 map/unmap 开销 |
| 固定文件（registered files） | 预打开 fd，免每 IO 文件查找 | 消除 open 表查找 |
| 多队列 + 每核 SQ | io_uring 实例绑定 CPU | 免锁 + 缓存亲和 |

```bash
# 查看 io_uring 支持与使用情况
grep io_uring /proc/filesystems   # io_uring 文件系统挂载
perf stat -e io_uring:* -p PID     # 统计提交/完成
```

### 7.4 从软中断到 epoll：网络收包全链路

```text
① 网卡 MSI-X 中断 → 硬中断上下文（极短）
② softirq（NET_RX_SOFTIRQ）批量收包：
     - 从 RX 队列取 skb → 协议栈（IP/TCP）处理
     - TCP 数据就绪 → 置位 socket 可读 → 唤醒等待线程
③ 应用 epoll_wait 返回 → read() 取数据
链路耗时量级：同机回环 ~5-20μs；跨机（网卡+RTT）~50-200μs
```

| 优化点 | 手段 | 效果 |
|--------|------|------|
| 减少拷贝 | `sendfile`/零拷贝（mmap） | 省 1-2 次拷贝 |
| 减少唤醒 | epoll 边缘触发 + 一次读全 | 省系统调用次数 |
| 减少中断 | NAPI 高负载切轮询 | 降 %si |
| 减少上下文 | 每个队列绑定专核（RPS/RSS） | 缓存亲和 |

### 7.5 存储 IO 完成路径与 Poll 模式

| 完成方式 | 机制 | 延迟 | 场景 |
|---------|------|:---:|------|
| 中断完成 | 设备发完成中断 → 内核唤醒等待者 | 5-20μs 抖动 | 通用 |
| **Poll 模式** | 驱动轮询完成队列（无中断） | 最低、最稳定 | 高 IOPS（NVMe poll queues） |
| 混合 | 先轮询短窗口，超时切中断 | 折中 | 现代驱动默认策略 |

```bash
# NVMe 开启 poll 队列（内核参数）
nvme.poll_queues=4
# io_uring 显式轮询
io_uring_setup 时 IORING_SETUP_IOPOLL
```

> 💡 **为什么 poll 模式在数据库场景流行**：延迟分布是"确定性"追求——中断路径的 5-20μs 抖动对 P99 敏感负载不可接受；轮询把延迟压到 ~2-5μs 且方差极小。代价是占满一个核。2026 年 Redis/MySQL 高性能部署普遍开启 NVMe poll + io_uring。

### 7.6 IO 路径面试追问

**Q1：为什么数据库不用 CPU 拷贝数据而用 DMA？**
答：DMA 让设备直接写内存，CPU 完全空闲——1GB/s 的磁盘吞吐若靠 CPU 搬运会吃满 2-4 核；DMA 只占用"一次描述符设置+一次完成中断"。

**Q2：IOMMU 为什么是安全必需？**
答：没有 IOMMU 时设备 DMA 可写任意物理内存（FireWire 攻击 5 秒拿 root）；IOMMU 把设备限制在分配域内，虚拟化直通也靠它隔离。

**Q3：SR-IOV 和 virtio 的区别？**
答：virtio 是半虚拟化（前后端共享内存队列，有宿主软件参与）；SR-IOV VF 是硬件级独立设备（独占队列+中断），可直通给 VM，性能接近裸机但不能热迁移。

**Q4：DPDK 为什么能比内核快 10 倍？**
答：绕开内核——用户态轮询（零中断）、零拷贝、零系统调用、独占核；代价是占 CPU、放弃内核网络栈。io_uring 是"90% 收益、10% 代价"的折中。

**Q5：Java NIO 的性能瓶颈在哪？**
答：epoll 只是通知，数据路径仍是 read()+拷贝；瓶颈 = 系统调用次数 + 用户态/内核态拷贝次数。Netty 优化 = 批量读写 + DirectBuffer 复用 + 零拷贝（fileChannel.transferTo）。

### 7.7 IO 参数调优清单（Java 服务视角）

| 参数 | 推荐值 | 场景 |
|------|--------|------|
| `net.core.rmem_max/wmem_max` | 16-64MB | 高吞吐网络 |
| `net.ipv4.tcp_rmem/tcp_wmem` | 自适应范围调大 | 长连接大流量 |
| `vm.dirty_ratio` | 5-10（DB） | 控制回写平滑 |
| `vm.dirty_writeback_centisecs` | 500-1000 | 回写频率 |
| `fs.aio-max-nr` | 65536+ | io_uring/aio 场景 |
| `netdev_budget` | 300-600 | 软中断预算 |

> ⚠️ **原则**：每个参数都有代价——调大缓冲区=内存占用上升，调大 budget=%si 升高。用监控（延迟/吞吐/CPU 分布）驱动调整，不要盲目"调大就是好"。

### 7.8 常见 IO 故障速查

| 症状 | 定位方向 | 常见根因 |
|------|---------|---------|
| 网卡 %si 飙高 | `ethtool -S`、NAPI 预算 | 小包风暴、中断风暴、ring buffer 过小 |
| 磁盘 IO 延迟高 | `iostat -x` 看 await/avgrq | 队列深度不足、碎片化、NVMe 固件 |
| 网络延迟抖动 | `ping -i 0.01`、`ss -i` | 软中断抢 CPU、TCP 重传、物理链路 |
| IO 吞吐上不去 | `sar -d`、perf 定位 | 单队列瓶颈（未开多队列）、IOMMU 开销 |
| Java 服务 P99 毛刺 | 分层观测（网络/内核/GC） | 收包延迟（netdev_budget）、GC 停顿、锁争用 |

> 🎯 **排查方法**：IO 问题一律"从设备向上分层"——先看设备层（iostat/ethtool）→ 内核层（软中断/调度）→ 应用层（GC/锁）。每一层的指标都对得上，才能锁定根因；直接猜应用层是新手最常见的错误。

**补充：PCIe 与 IO 的关系一句话**——PCIe 是"设备接入 CPU 的公路"：DMA 走它、MSI-X 走它、SR-IOV 的 VF 也走它；带宽/延迟的上限由 PCIe 通道决定（如 NVMe 走 x4 Gen4/5 ≈ 8/16GB/s）。IO 优化的天花板一半在 PCIe 协议层——与「PCIe 带宽」体系联动阅读效果最佳。

**再补：内核 IO 栈的"分层职责"**——VFS（文件抽象）→ 页缓存（缓存层）→ 文件系统（元数据/布局）→ 块层（bio 排队）→ 驱动（DMA）。排查 IO 问题时的"一层一层排除"就靠这张图：缓存命中率高但慢=文件系统层；await 高=设备层。**分层清晰，排障才快**。

**收官清单**：学完本篇应能回答——① MMIO 和 DMA 的分工？② 轮询/中断/DMA 各适用什么？③ IOMMU 为什么是安全必需？④ SR-IOV 和 virtio 的区别？⑤ NAPI 是怎么混合轮询与中断的？五问全过即毕业，进入 07 篇时钟定时器与时间。

**延伸阅读**：与「PCIe 带宽」「存储硬件」体系联动——IO 路径的物理载体是 PCIe 总线与存储介质，三篇合起来才是一条完整的"数据流"故事。

**补充：一个判断 IO 瓶颈的速查法则**——延迟高先看设备（await/svc）、吞吐低先看队列（队列深度/多队列是否开启）、抖动大先看软中断（%si/irqbalance）。**三条路对应三种根因**，几乎覆盖 90% 的 IO 排查场景——把这张表贴在工位上，比背任何参数都管用。

**最后一句**：IO 优化的终点不是"绕开内核"，而是"让内核以最少的参与完成最多的数据搬运"——DMA、多队列、io_uring 都是这句话的注脚。带着"数据流"的地图进入下一站：时钟定时器与时间。

**本篇知识闭环**：从 MMIO 控制面、DMA 数据面，到 IOMMU 隔离、SR-IOV 虚拟化，再到 NAPI/io_uring 的性能边界——IO 的全貌就是"谁控制、谁搬运、谁隔离、谁加速"四个问题的答案。

## 8. 核心要点

> 🎯 **核心要点**：CPU 控制设备用 MMIO（控制面），数据搬运交给 DMA（数据面）；IO 完成通知三选一——轮询（最快最费核）、中断（省核有延迟）、混合（NAPI/busy-poll）；IOMMU 是设备版 MMU，提供 DMA 隔离与虚拟化直通，代价是 5-15% 开销；SR-IOV 让一个设备拆成多个 VF 直达 VM；DPDK/io_uring 是"绕开内核"的两种姿势，Java 生态以 io_uring 为主；理解整条 IO 路径后，`vm.dirty_ratio`、IRQ 亲和、poll_queues 这些参数才真正可控。
