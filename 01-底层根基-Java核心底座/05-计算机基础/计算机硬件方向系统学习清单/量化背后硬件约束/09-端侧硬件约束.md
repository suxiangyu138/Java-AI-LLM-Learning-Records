# 端侧硬件约束：CPU 与手机 NPU 上的量化部署
> 端侧的约束比数据中心更硬：内存单位 GB、功耗单位瓦、NPU 生态碎片化——量化在这里从"优化"变成"能不能跑"的生存问题。

## 1. GGUF：端侧量化的事实标准

llama.cpp 的 GGUF 格式是 2026 年端侧推理的事实标准：单文件内嵌 tokenizer、聊天模板与元数据，量化档位从 Q2_K 到 Q8_0 全覆盖。数据层面，GGUF 占 Hugging Face 量化模型下载量的 70%+，约 40% 的移动 AI 应用通过 libllama.so 调用。INT4 档位的典型选择：

- **Q4_K_M**：体积约为 FP16 的 30%，质量保留 96-98%
- **IQ4_XS**：更小、精度略降，适合小内存设备
- **Q8_0**：接近无损（~99.7%），体积减半

端侧量化的带宽逻辑与 GPU 相同（少搬字节 = 低延迟），但**第一约束是容量**：手机 8-16 GB 内存，iOS 会话还被限制在 4096 token 上下文——3B 模型 Q4_K_M 约 2.5 GB，是多数手机"实时响应"的上限，旗舰机才能流畅跑 7B Q4（约 15-18 t/s）。

### 1.1 GGUF 量化档位全景：Q2 到 Q8 的取舍

| 档位 | 体积占比 | 质量 | 典型用途 |
|------|:---:|------|---------|
| Q2_K | ~15% | 明显损失 | 内存极小的老设备/演示 |
| Q3_K_M | ~20% | 中度损失 | 2GB 内存设备 |
| Q4_K_M | ~30% | 96-98% | 生产默认，甜点 |
| Q5_K_M | ~35% | ~99% | 精度敏感任务 |
| Q6_K | ~45% | ~99.5% | 大内存设备 |
| Q8_0 | ~55% | ~99.7% | 准无损基线 |

档位选型与硬件的关系：**体积决定能否装下（容量），吞吐由 CPU/GPU 带宽决定（速度），质量决定可用性**。Q4_K_M 是绝大多数场景的起点，Q5/Q6 仅在"内存有余量且精度回归失败"时升级——每升一档，内存压力与电量消耗同步上升，移动端往往为 1% 的精度付出 10% 的续航。

## 2. Apple Silicon：统一内存是优势，NPU 是遗憾

Apple 的 M 系列用统一内存架构（CPU/GPU/ANE 共享内存），量化模型直接受益：**没有 PCIe/HBM 拷贝开销，权重从统一内存直读**，等效带宽利用率高。M3 Ultra 跑 70B Q4_K_M 约 12 t/s，M2 Pro 上 7B Q4 约 32-45 t/s。

但 2026 年的现状是：**llama.cpp 走 Metal GPU 后端，不充分使用 Neural Engine**。想要 ANE 加速必须换引擎：ONNX Runtime CoreML 执行提供器、MLC LLM、ExecuTorch 或商业引擎。Apple 的 NPU（ANE）算力强但生态封闭——这是端侧"硬件有能力、软件没接通"的典型。

### 2.1 Apple Silicon 量化实测量级

| 机型 | 7B Q4_K_M | 70B Q4_K_M |
|------|:---:|:---:|
| M1/M2 基础款 | 12-25 t/s | 不可用（内存不足） |
| M2 Pro / M3 | 32-45 t/s | — |
| M3 Ultra | — | ~12 t/s |

两个量级结论：**7B Q4 是 Apple Silicon 的吞吐甜点**（30-45 t/s 达到流畅交互线）；**70B Q4 只有 Ultra 级芯片的 192GB 统一内存能装下**，且 12 t/s 仅是"能用"而非"流畅"。统一内存的副作用：**模型占用的内存与系统共享**，跑 70B 模型时整机应用体验会被压缩——部署前要按"模型内存 + 系统开销"做总账。

## 3. Qualcomm Hexagon NPU：能力与接通的剪刀差

高通阵营（骁龙）的量化链路是 QNN（Qualcomm Neural Network）生态：ONNX Runtime QNN 执行提供器 + ExecuTorch QNN delegate 是主流路径，Snapdragon 8 Gen 3 的 Hexagon NPU 跑 7B Q4 约 15 t/s，MediaTek Dimensity 9300 的 APU 790 约 18-30 t/s。

llama.cpp 自己的 Hexagon 后端仍是 "In Progress"，Adreno GPU 走 OpenCL 且标为"成熟中"；社区方案 ggml-hexagon（FastRPC/dspqueue 把 ggml 移植到 cDSP/HTP）能跑全量化矩阵乘，但仍是实验性 fork。**结论：真要用 NPU 算力，别等 llama.cpp，直接用 ONNX Runtime/MLC LLM/ExecuTorch**。

## 4. 端侧 NPU 的量化格式与容量铁律

NPU 侧的量化和 GPU 侧格式不完全同构：QNN/CoreML 生态主要吃 INT8/INT16 对称量化（激活 INT8 居多），INT4 权重支持的 NPU 尚在普及；MX 格式（MXFP4）在端侧几乎无原生支持——**端侧 4-bit 主要仍是 INT4 权重专用，配合 INT8 激活的混合精度**。

容量与功耗是端侧量化存在的全部理由：

- 功耗墙：手机连续跑大模型会触发热降频，量化省的内存带宽直接降低功耗（DRAM 访问是大头）
- 内存墙：8 GB 手机装 7B Q4 后余量紧张，系统内存与应用争夺
- 上下行网络：端云混合架构下，量化决定多少逻辑能在端上完成

### 4.1 功耗与热降频：端侧独有的第三约束

服务器量化省的是电费，端侧量化省的是**续航与散热**：DRAM 访问功耗占比高，量化减半/减到 1/4 的权重搬运直接延长续航；但连续推理仍会触发热降频——手机 SoC 的稳态性能可能只有峰值的 50-70%。**实测方法：连续跑 5 分钟吞吐曲线**，以稳态值（而非峰值）作为体验基准。这也是"1B-3B 是手机实时响应天花板"论断的物理根源：更大模型 = 更长内存访问时间 = 更早触发降频 = 体验崩塌。

### 4.2 iOS 与 Android 的系统性差异

两个平台对量化部署的约束并非对称：

- **iOS**：App 沙箱与内存限制更严，部分设备会话被限制在 4096 token 上下文；ANE 加速必须走 CoreML 转换，自定义量化层存在算子支持边界，未覆盖的算子自动降级到 CPU/GPU
- **Android**：内存管理更宽松但硬件碎片化严重（骁龙/天玑/麒麟的 NPU 指令互不通用），QNN/ExecuTorch 的 NPU 路径需按 SoC 型号逐一适配——"同一份 INT4 模型在安卓全机型跑 NPU"在 2026 年仍是理想

跨平台工程上的务实选择：**NPU 只加速算子密集的稳定路径，复杂分支（工具调用、多模态）退回 CPU/GPU 通用路径**——用"混合执行"规避 NPU 算子覆盖不完整的问题，量化位宽按最弱链路（CPU 路径）统一，避免同一模型两套格式的维护成本。

## 5. 端侧选型决策：先定引擎，再定格式

1. 确定推理引擎：llama.cpp（CPU/Metal，生态最广）→ ONNX Runtime（NPU 接入，CoreML/QNN）→ MLC LLM/ExecuTorch（编译期优化，部署复杂）
2. 确定格式：CPU/GPU 路径用 GGUF（Q4_K_M 起步）；NPU 路径走 INT8 或框架量化格式
3. 确定模型规模：1B-3B 是手机实时响应甜点，7B 是旗舰上限，更大模型交给云侧
4. 验证热降频下的稳态吞吐：峰值 t/s 没有意义，连续推理 5 分钟后的吞吐才是体验

### 5.1 端云混合的架构落点

端侧量化的终极形态不是"全端上"，而是**端云分工**：

- 端上跑小模型（1-3B Q4）承担：隐私敏感任务（本地笔记、支付、健康数据）、低延迟交互（语音助手首响）、断网兜底
- 云侧跑大模型承担：复杂推理（长链思考、多步工具调用）、知识密集任务（RAG 检索）、多模态

分工的边界由三个量决定：**隐私等级**（敏感数据不出端）、**延迟预算**（首响 <100ms 的交互留端上）、**任务复杂度**（超出端模型能力上限转云端）。量化位宽在这一架构里是"端上模型能不能承担更多任务"的唯一旋钮——位宽降一档，端上可承载的任务范围就扩一圈。

> 🎯 **核心要点**：GGUF（Q4_K_M）是端侧事实标准，70%+ 下载量、96-98% 质量保留；Apple 统一内存让量化模型直接受益，但 llama.cpp 走 Metal 不充分用 ANE；高通 Hexagon 的算力要靠 ONNX Runtime QNN/ExecuTorch 接通，llama.cpp 原生后端未成熟；端侧第一约束是内存与功耗——量化决定模型能不能装下、电池能撑多久；1B-3B Q4 是手机实时响应上限，7B 是旗舰天花板。
