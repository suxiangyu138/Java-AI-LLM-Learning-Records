## 2. E-R 模型

### 2.1 三大要素

| 要素 | 说明 | 图形表示 | 对应数据库 |
|------|------|----------|-----------|
| 实体（Entity） | 客观存在的事物 | 矩形 | 数据表 |
| 属性（Attribute） | 实体的特征 | 椭圆 | 字段 |
| 关系（Relationship） | 实体之间的关联 | 菱形 | 外键/中间表 |

### 2.2 关系类型

| 关系 | 示例 | 实现 |
|------|------|------|
| 一对一（1:1） | 用户 ↔ 身份证 | 任意一方加外键 + UNIQUE |
| 一对多（1:N） | 部门 → 员工 | "多"方加外键（员工表加 dept_id） |
| 多对多（M:N） | 学生 ↔ 课程 | 新建中间表 |

### 2.3 属性类型

| 属性类型 | 说明 | 示例 |
|----------|------|------|
| 简单属性 | 不可再分 | 年龄、性别 |
| 复合属性 | 可再分为多个子属性 | 地址（省+市+区+街道） |
| 多值属性 | 一个实体有多个值 | 电话号码（多个） |
| 派生属性 | 可从其他属性计算得出 | 年龄（从生日派生出） |
| 空值属性 | 属性值暂时未知 | 手机号（注册时可选） |

### 2.4 实体 VS 属性选择原则

> **经验法则**：如果一个对象有自己的属性，则应将其建模为实体而非属性。

```
错误：用户的地址直接存为一个 VARCHAR 字段
正确：地址作为独立的 Address 实体，与 User 关联（可支持多地址）
```

## 3. E-R 图到关系模式的转换

### 3.1 转换规则

| E-R 结构 | 转换方式 |
|----------|----------|
| 实体 | 创建一张表 |
| 属性 | 表的字段 |
| 主键 | 表的主键 |
| 1:1 关系 | 在任意一方加外键 |
| 1:N 关系 | 在 N 方加外键 |
| M:N 关系 | 创建中间表（含两个外键） |

### 3.2 示例

```sql
-- 实体 1：Department
-- 实体 2：Employee
-- 关系：1:N（一个部门有多个员工）

CREATE TABLE department (
    id   BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL
);

CREATE TABLE employee (
    id       BIGINT PRIMARY KEY AUTO_INCREMENT,
    name     VARCHAR(50) NOT NULL,
    dept_id  BIGINT,
    FOREIGN KEY (dept_id) REFERENCES department(id)
);

-- 实体 1：Student
-- 实体 2：Course
-- 关系：M:N
CREATE TABLE student_course (
    student_id BIGINT,
    course_id  BIGINT,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student(id),
    FOREIGN KEY (course_id) REFERENCES course(id)
);
```

## 4. 范式理论

范式是衡量关系模式设计优劣的标准。**通常满足 3NF 即可**，过分规范化可能导致查询性能下降。

### 4.1 第一范式（1NF）

**要求**：每个列都是原子的，不可再分。

```
❌ 违例：address = "北京市海淀区中关村"（可拆分成省/市/区）
✅ 正确：province, city, district 分开存储
```

### 4.2 第二范式（2NF）

**要求**：满足 1NF + 非主键列完全依赖于主键（消除部分依赖）。

```
❌ 违例：(order_id, product_id, product_name, quantity)
   product_name 只依赖于 product_id，不是完全依赖于联合主键
✅ 正确：拆分为 order_item 表和 product 表
```

### 4.3 第三范式（3NF）

**要求**：满足 2NF + 非主键列不传递依赖于主键（消除传递依赖）。

```
❌ 违例：(user_id, dept_id, dept_name)
   dept_name 通过 dept_id 传递依赖于 user_id
✅ 正确：dept_name 仅在 department 表中存，user 表存 dept_id
```

### 4.4 BCNF（鲍依斯-科得范式）

**要求**：每个决定因素都是候选键。BCNF 是 3NF 的加强版。

### 4.5 范式总结

| 范式 | 核心要求 | 主要解决的问题 |
|------|----------|--------------|
| 1NF | 列不可再分 | 非原子数据 |
| 2NF | 非主键列完全依赖主键 | 部分依赖导致的冗余 |
| 3NF | 非主键列不传递依赖主键 | 传递依赖导致的冗余 |
| BCNF | 每个决定因素都是候选键 | 3NF 未覆盖的特殊情况 |

> ⚠️ **实际开发中满足 3NF 已经足够**。过渡规范化会导致太多表 JOIN，影响查询性能。

## 5. 规范化与反规范化

### 5.1 规范化的优缺点

| 优点 | 缺点 |
|------|------|
| 消除数据冗余 | 查询需 JOIN 多个表，性能下降 |
| 避免更新异常（插入/删除/修改异常） | 逻辑更复杂 |
| 数据一致性更好 | 建模工作量增加 |

### 5.2 反规范化

反规范化是在性能要求高的场景，适当冗余字段以减少 JOIN。

| 场景 | 反范式做法 | 优点 | 缺点 |
|------|-----------|------|------|
| 订单列表需显示用户名 | orders 表冗余 username | 避免 JOIN users 表 | 用户名变更需同步更新 |
| 文章列表需显示评论数 | articles 表冗余 comment_count | 避免 COUNT 子查询 | 增删评论时需维护计数 |
| 商品列表需显示销量 | products 表冗余 sales_count | 避免 SUM 聚合查询 | 下单/退款时需更新 |

### 5.3 设计原则

> 先满足 3NF，在性能瓶颈处适度反范式——范式化是理论指导，反范式是工程权衡。

> 🎯 **好的数据库设计是项目成功的基石**——表结构在项目初期确定后，后期改造成本极高。建议在写第一行代码之前，先把 E-R 图画好、把表结构设计好。
