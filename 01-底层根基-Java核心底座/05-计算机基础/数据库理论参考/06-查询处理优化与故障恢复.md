# 查询处理、优化与故障恢复
> 查询处理将 SQL 转化为执行计划，查询优化选择最优的执行路径，故障恢复确保系统崩溃时数据不丢失。本文涵盖查询处理流程、代价估计、查询优化策略及数据库恢复技术。

## 1. 查询处理流程

```
SQL 语句 → 语法分析 → 查询重写 → 查询优化 → 执行计划 → 执行引擎 → 结果
```

| 步骤 | 说明 |
|------|------|
| 语法分析 | 检查 SQL 语法，生成语法树 |
| 查询重写 | 将 SQL 转为关系代数表达式（如视图展开、谓词下推） |
| 查询优化 | 选择代价最小的执行计划 |
| 执行引擎 | 按照执行计划执行，返回结果 |

## 2. 代价估计与查询优化

### 2.1 代价衡量

查询优化器基于以下因素估算代价：

| 代价因素 | 说明 |
|----------|------|
| 磁盘访问代价 | 数据块读取次数（最主要因素） |
| CPU 代价 | 数据处理时间 |
| 内存代价 | 排序、哈希操作的内存使用 |
| 通信代价 | 分布式场景下的数据传输 |

### 2.2 关系代数等价变换

查询优化器利用等价规则重写查询：

| 规则 | 说明 | 示例 |
|------|------|------|
| 选择下推 | 先做选择再做连接 | `σ(JOIN)` → `JOIN(σ)` |
| 投影下推 | 尽早减少列数 | 尽早 SELECT 需要的列 |
| 连接顺序 | 小表先连接 | 减少中间结果集大小 |

### 2.3 基于代价的优化

```
优化器为每个可能的执行方案估算代价，选择代价最小的方案。

输入：
  - SQL 语句
  - 表统计信息（行数、分布、索引信息）
  - 系统配置（IO 代价、CPU 代价）

输出：代价最小的执行计划
```

## 3. 常用优化策略

### 3.1 选择下推

```sql
-- 优化器自动将 WHERE 条件下推到 JOIN 之前执行
SELECT * FROM users u JOIN orders o ON u.id = o.user_id WHERE u.age > 18;
-- 等价于：
SELECT * FROM (SELECT * FROM users WHERE age > 18) u JOIN orders o ON u.id = o.user_id;
```

### 3.2 连接算法

| 算法 | 复杂度 | 适用场景 |
|------|--------|----------|
| 嵌套循环连接 | O(n*m) | 小表驱动大表 |
| 块嵌套循环连接 | O(n*m/k) | 有足够缓存 |
| 索引嵌套循环连接 | O(n*log m) | 有索引 |
| 归并连接 | O(n+m) | 两表已排序 |
| 哈希连接 | O(n+m) | 等值连接，无索引 |

### 3.3 物化视图

```sql
-- MySQL 8.0+ 不支持物化视图，但可以通过触发器或 Event 模拟
-- Oracle/PostgreSQL 原生支持
CREATE MATERIALIZED VIEW mv_sales_summary AS
SELECT product_id, SUM(amount) AS total FROM sales GROUP BY product_id;
```

## 4. 故障分类

### 4.1 故障类型

| 故障类型 | 说明 | 影响 | 恢复方式 |
|----------|------|------|----------|
| 事务故障 | 事务执行中发生逻辑错误、死锁或被强制终止 | 该事务的数据可能不完整 | undo log 回滚 |
| 系统崩溃（宕机） | 断电、OS 崩溃导致内存数据丢失 | 已提交数据可能尚未写入磁盘 | redo log 重做 |
| 介质故障 | 磁盘损坏、数据文件丢失 | 所有数据丢失 | 备份 + 归档日志恢复 |

### 4.2 存储层次

```
稳定存储器                              ──── 磁盘（持久化）
易失性存储器（缓冲池）                  ──── 内存（断电丢失）
```

## 5. 恢复机制与日志

### 5.1 三大日志

| 日志 | 作用 | 存储位置 | 说明 |
|------|------|----------|------|
| **redo log** | 崩溃恢复，保证持久性 | 磁盘（提前写入，WAL） | 记录已提交但尚未写入磁盘的修改 |
| **undo log** | 事务回滚 + MVCC 版本链 | 磁盘 | 保存修改前的旧值 |
| **binlog** | 主从复制、数据归档 | 磁盘 | MySQL 特有，逻辑日志 |

### 5.2 WAL（Write-Ahead Logging）

**先写日志，再写磁盘**——这是保证事务持久性的核心机制。

```
事务提交流程：
1. 将修改写入 redo log buffer（内存）
2. redo log 写入磁盘（fsync）
3. 事务返回 COMMIT OK
4. 脏页后续由 Checkpoint 异步刷入磁盘
```

### 5.3 Checkpoint

Checkpoint 机制将内存中已修改的数据页（脏页）写入磁盘，减少崩溃恢复时的回放量。

| 类型 | 说明 |
|------|------|
| 模糊 Checkpoint | 只记录 Checkpoint 位置，不强制立即刷脏页 |
| 锐 Checkpoint | 将所有脏页写入磁盘（性能开销大） |

### 5.4 ARIES 恢复算法

InnoDB 使用 ARIES（Algorithms for Recovery and Isolation Exploiting Semantics）：

| 阶段 | 操作 |
|------|------|
| 分析阶段 | 从 Checkpoint 开始扫描 redo log，确定需要回滚的事务 |
| Redo 阶段 | 重做所有已提交但未写入磁盘的修改 |
| Undo 阶段 | 回滚所有未提交事务的修改 |

### 5.5 恢复策略

```sql
-- 备份恢复
mysqldump -u root -p bookstore > bookstore_backup.sql
mysql -u root -p bookstore < bookstore_backup.sql

-- 基于时间点的恢复（point-in-time recovery）
mysqlbinlog binlog.000001 | mysql -u root -p
```

> 💡 **操作之前先备份**。介质故障的唯一恢复手段就是备份 + 归档日志，定期做备份是 DBA 最基本也是最重要的职责。
