## 1. 操作系统的定义与功能

### 1.1 定义

操作系统（OS）是管理和控制计算机硬件与软件资源的系统软件，是计算机系统中所有软硬件资源的管理者和协调者。

```
应用程序（Java / Spring / Nginx / MySQL）
       |
  操作系统（内核 + 系统调用 + 文件系统 + 驱动）
       |
  硬件（CPU + 内存 + 磁盘 + 网卡）
```

### 1.2 核心作用

| 作用 | 说明 |
|------|------|
| **资源管理** | 统一管理 CPU、内存、存储、外设 |
| **提供接口** | 用户接口（GUI/CLI）+ 程序接口（系统调用） |
| **调度与协调** | 调度应用程序运行，协调多程序并发 |
| **抽象封装** | 将硬件差异封装为统一接口，实现跨平台 |

### 1.3 五大核心功能

| 功能模块 | 核心任务 | Java 后端关联 |
|----------|----------|---------------|
| **处理机管理** | CPU 调度与分配 | 线程池配置、多线程调度 |
| **存储器管理** | 内存分配、虚拟内存 | JVM 堆内存、GC 机制 |
| **设备管理** | 外设控制、I/O 调度 | NIO、Netty、文件读写 |
| **文件管理** | 文件存储、目录组织 | File I/O、日志存储 |
| **用户接口管理** | 命令/图形/系统调用 | 应用程序请求 OS 服务 |

> 💡 **Java 关联**：Java 的跨平台特性（一次编写，到处运行）根源于 OS 的硬件抽象层。JVM 通过封装不同 OS 的系统调用，为 Java 程序提供统一的运行接口。

## 2. 操作系统的发展历程

### 2.1 发展阶段

```
无 OS（人工操作） → 单道批处理 → 多道批处理 → 分时系统 → 实时系统 → 通用 OS
```

| 阶段 | 时间 | 特点 | 问题 |
|------|------|------|------|
| 人工操作 | 1940s | 用户独占机器，手工插拔 | CPU 利用率极低 |
| 单道批处理 | 1950s | 作业自动过渡，内存单一程序 | CPU 等待 I/O |
| 多道批处理 | 1960s | 内存多道程序，CPU 与 I/O 并行 | 无交互能力 |
| 分时系统 | 1970s | 时间片轮转，多用户交互 | 响应时间要求高 |
| 实时系统 | 1980s | 严格时间约束，确定性响应 | 灵活性差 |
| 现代通用 OS | 1990s+ | 分时+实时+网络+分布式 | 复杂度高 |

### 2.2 多道批处理系统的意义

多道批处理系统的出现标志着操作系统的**成熟**。其核心思想是：在内存中同时存放多道程序，它们在管理程序的控制下交替运行，共享 CPU 和 I/O 设备。

> ⚠️ 多道程序设计的目的是**提高 CPU 利用率**，而非提高吞吐量。吞吐量的提升是 CPU 利用率提高的自然结果。

## 3. 操作系统的四大特征

| 特征 | 定义 | 说明 |
|------|------|------|
| **并发（Concurrency）** | 多个程序在一段时间内同时运行 | 宏观同时，微观交替（≠ 并行：同一时刻真正同时） |
| **共享（Sharing）** | 系统资源被多个并发程序共同使用 | 互斥共享（打印机）/ 同时共享（磁盘） |
| **虚拟（Virtual）** | 将物理资源抽象为逻辑资源 | 时分复用（CPU 分时）/ 空分复用（虚拟内存） |
| **异步（Asynchrony）** | 程序执行以不可预知的速度推进 | 走走停停，OS 保障最终结果正确 |

> 💡 **并发与并行的区别**：并发是逻辑上的同时（单核交替执行），并行是物理上的同时（多核真正同时）。Java 多线程是并发的，在多核 CPU 上才可能实现并行。

## 4. 操作系统的分类

### 4.1 按使用环境分类

| 类型 | 特点 | 典型系统 | 适用场景 |
|------|------|----------|----------|
| **批处理系统** | 批量作业，无交互 | 早期 IBM 系统 | 大规模计算 |
| **分时系统** | 时间片轮转，多用户交互 | Unix/Linux | 通用计算 |
| **实时系统（硬实时）** | 严格时间约束 | VxWorks, QNX | 工业控制 |
| **实时系统（软实时）** | 尽量满足时间要求 | Linux 实时变体 | 多媒体 |
| **分布式系统** | 多机协同，资源共享 | 集群 OS | 大数据、云 |

### 4.2 按应用场景分类

| 类型 | 特点 | 示例 |
|------|------|------|
| **桌面操作系统** | 图形化界面、易用性 | Windows、macOS |
| **服务器操作系统** | 稳定性、安全性、并发 | CentOS、Ubuntu Server |
| **嵌入式操作系统** | 轻量化、低功耗 | Android、FreeRTOS |
| **实时操作系统（RTOS）** | 响应时间确定性 | FreeRTOS、QNX |

### 4.3 按硬件结构分类

- **单机 OS**：管理单台计算机
- **网络 OS**：提供网络通信能力
- **分布式 OS**：多机统一管理，对外呈现为单一系统

## 5. 操作系统体系结构

### 5.1 三种架构对比

| 架构 | 特点 | 优点 | 缺点 | 示例 |
|------|------|------|------|------|
| **单内核（Monolithic）** | 所有模块运行在核心态 | 高效、模块间通信快 | 稳定性差，一个错误可导致系统崩溃 | 早期 Linux |
| **微内核（Microkernel）** | 核心模块在核心态，其他在用户态 | 稳定性高、扩展性好 | 性能损失（频繁 IPC） | Mach、QNX |
| **混合内核（Hybrid）** | 结合两者优点 | 兼顾效率与稳定性 | 设计复杂 | 现代 Linux、Windows NT |

### 5.2 架构示意图

```
单内核                      微内核                    混合内核
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   用户态         │    │   用户态         │    │   用户态         │
│ ┌─────────────┐ │    │ ┌───────┐       │    │ ┌───────┐       │
│ │ 应用程序     │ │    │ │ 文件系统 │       │    │ │ 文件系统 │       │
│ └─────────────┘ │    │ │ 设备驱动 │       │    │ │ 设备驱动 │       │
│                 │    │ │ 网络栈  │       │    │ └───────┘       │
├─────────────────┤    │ └───────┘       │    ├─────────────────┤
│   内核态         │    ├─────────────────┤    │   内核态         │
│ ┌─────────────┐ │    │   微内核        │    │ ┌─────────────┐ │
│ │ 进程管理     │ │    │ ┌───────┐       │    │ │ 进程管理     │ │
│ │ 内存管理     │ │    │ │IPC    │       │    │ │ 内存管理     │ │
│ │ 文件系统     │ │    │ │调度   │       │    │ │ IPC + 调度  │ │
│ │ 设备驱动     │ │    │ │内存   │       │    │ └─────────────┘ │
│ │ 网络栈       │ │    │ └───────┘       │    └─────────────────┘
│ └─────────────┘ │    └─────────────────┘
└─────────────────┘
```

## 6. 内核态与用户态

### 6.1 概念

- **内核态（核心态）**：CPU 可以访问所有内存和指令，运行 OS 内核代码
- **用户态**：CPU 只能访问受限内存和指令，运行应用程序代码

### 6.2 权限隔离

| 维度 | 内核态 | 用户态 |
|------|--------|--------|
| 权限等级 | 最高（Ring 0） | 最低（Ring 3） |
| 内存访问 | 全部物理内存 | 仅进程虚拟空间 |
| 指令集 | 全部指令（含特权指令） | 受限指令 |
| 系统调用 | 处理方 | 发起方 |
| 崩溃影响 | 系统崩溃（内核恐慌） | 仅该进程崩溃 |

### 6.3 切换流程

```
用户态 → 系统调用/中断 → 保存上下文 → 切换到内核态
→ 执行内核代码 → 恢复上下文 → 返回用户态
```

> ⚠️ **用户态与内核态的切换是 I/O 操作的核心开销**。每次系统调用都涉及上下文切换，频繁切换会显著影响性能。Java NIO 的设计目标之一就是减少系统调用次数。

## 7. 系统调用

### 7.1 定义与作用

系统调用是**应用程序请求 OS 服务的唯一入口**，是用户态程序访问内核资源的桥梁。

### 7.2 系统调用分类

| 类别 | 系统调用示例 | Java 对应 |
|------|-------------|-----------|
| **进程控制** | `fork()`, `exec()`, `wait()` | `ProcessBuilder`, `Runtime.exec()` |
| **线程管理** | `clone()`, `pthread_create()` | `new Thread()` |
| **内存管理** | `brk()`, `mmap()`, `munmap()` | JVM 堆分配, `DirectByteBuffer` |
| **文件操作** | `open()`, `read()`, `write()`, `close()` | `FileInputStream`, `FileOutputStream` |
| **设备管理** | `ioctl()`, `read()`, `write()` | NIO Channel |
| **网络通信** | `socket()`, `bind()`, `connect()`, `send()` | `java.net.Socket` |
| **信息维护** | `getpid()`, `time()`, `stat()` | `System.currentTimeMillis()` |

### 7.3 系统调用 vs 库函数

| 对比 | 系统调用 | 库函数 |
|------|----------|--------|
| 运行级别 | 内核态 | 用户态 |
| 开销 | 大（上下文切换） | 小 |
| 示例 | `read()` | `fread()`（C 库封装 read）|
| Java 关联 | JNI 调用 | Java API 封装 |

> 💡 Java 的 `System.out.println()` 底层经过：Java API → JNI → OS 系统调用 `write()`，每次调用都涉及用户态/内核态切换。

## 8. 中断与异常

### 8.1 分类

| 类型 | 来源 | 触发方式 | 示例 |
|------|------|----------|------|
| **外中断（中断）** | 外部设备 | **异步**（随机发生） | 时钟中断、键盘输入、网卡数据 |
| **内中断（异常）** | CPU 内部 | **同步**（指令执行时） | 除零、缺页、非法指令、越界 |

### 8.2 中断处理流程

```
中断请求 → 中断响应（保存现场） → 中断处理 → 恢复现场 → 中断返回
```

| 步骤 | 说明 |
|------|------|
| 1. 中断请求 | 设备或 CPU 内部发出中断信号 |
| 2. 中断响应 | CPU 保存当前程序计数器（PC）和寄存器 |
| 3. 中断处理 | 根据中断向量表找到处理程序并执行 |
| 4. 恢复现场 | 恢复寄存器、PC 等上下文 |
| 5. 中断返回 | 回到被中断的程序继续执行 |

### 8.3 Java 关联

| Java 概念 | OS 底层机制 |
|-----------|-------------|
| `NullPointerException` | OS 内存访问异常（段错误）封装 |
| `Thread.interrupt()` | 向 OS 发送中断信号 |
| `synchronized` | OS 互斥锁 + 阻塞/唤醒信号 |
| 服务稳定性 | OS 中断处理效率直接影响 Java 服务响应 |

## 9. 操作系统设计哲学

### 9.1 十大设计原理

| # | 哲学原理 | 核心思想 | 技术体现 |
|---|----------|----------|----------|
| 1 | **层次架构** | 系统分层设计，下层为上层提供服务 | OSI 模型、文件系统层次 |
| 2 | **没有对错** | 设计决策取决于应用场景和权衡 | 调度算法选择 |
| 3 | **懒人哲学** | 能不做就不做，延迟执行 | 写时复制（Copy-on-Write）、惰性求值 |
| 4 | **让困于人** | 复杂问题交给用户空间处理 | 微内核设计 |
| 5 | **留有余地** | 预留资源应对未来需求 | 多级反馈队列 |
| 6 | **子虚乌有（虚拟化）** | 物理资源抽象为逻辑资源 | 虚拟内存、虚拟机 |
| 7 | **时空转换** | 时间换空间或空间换时间 | 虚拟内存（时间换空间）、缓存（空间换时间）|
| 8 | **认证分离与权利分离** | 权限与认证分离 | Linux 用户/组权限模型 |
| 9 | **简单为美** | 追求设计的简洁性 | Unix "一切皆文件" |
| 10 | **适可而止** | 在复杂度和性能之间找到平衡 | 多级页表设计 |

### 9.2 Java 后端的核心启示

| 原理 | Java 实战 |
|------|-----------|
| **层次架构** | JVM 封装 OS 差异，应用代码无需关注底层 |
| **懒人哲学** | GC 延迟回收、线程池懒加载、懒初始化 |
| **时空转换** | 缓存（空间换时间）、连接池（空间换时间） |
| **虚拟化** | JVM 本身是应用级虚拟机 |

## 10. 虚拟化与云计算

### 10.1 虚拟化的本质

```
物理硬件 → 虚拟化层（Hypervisor / 容器引擎） → 虚拟环境
                ↓                        ↓
           资源抽象                   环境隔离
```

### 10.2 硬件虚拟化 vs 容器虚拟化

| 对比维度 | 硬件虚拟化（VM） | 容器虚拟化（Docker） |
|----------|-----------------|---------------------|
| 虚拟化层位置 | 物理硬件之上 | 物理机 OS 之上，共享 OS 内核 |
| 隔离性 | **极强**（完全隔离） | 中等（共享内核） |
| 资源开销 | 大（需运行完整 OS） | **小**（仅包含应用及依赖） |
| 启动速度 | 慢（分钟级） | **快**（秒级） |
| 部署复杂度 | 高 | **低**（镜像打包，一键部署） |

### 10.3 云计算三大服务模式

| 服务模式 | 云厂商提供 | 用户负责 | Java 后端常见场景 |
|----------|-----------|----------|-------------------|
| **IaaS** | ECS、OSS、虚拟网络 | OS 安装、环境配置、服务部署 | 单体服务、定制化环境 |
| **PaaS** | 运行环境（JVM）、数据库、中间件 | 业务代码开发、应用部署 | 微服务、弹性伸缩 |
| **SaaS** | 现成软件 | API 调用 | 云数据库、云中间件 |

### 10.4 Docker 部署 Java 服务

```dockerfile
FROM openjdk:8-jdk-alpine
WORKDIR /app
COPY target/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

```bash
# 构建与运行
docker build -t my-service:v1.0 .
docker run -d -p 8080:8080 --name my-container my-service:v1.0
```

> ⚠️ **Docker 中 Java OOM 的坑**：容器内存限制 + JVM 未感知容器限制，需显式设置 `-Xmx`。JDK 10+ 的 `-XX:+UseContainerSupport` 可自动感知 CGroup 限制。

### 10.5 JVM 与虚拟化的关系

| 概念 | 说明 |
|------|------|
| **JVM** | 应用级虚拟机，解决 Java 跨平台问题 |
| **Docker/VM** | 系统级虚拟化，为 JVM 提供独立、一致的运行环境 |

> 💡 JVM 与虚拟化是**协同关系**：JVM 解决语言跨平台，Docker/VM 解决运行环境跨平台。

## 11. 主流操作系统实例对比

### 11.1 UNIX / Linux / Windows 对比

| 操作系统 | 核心定位 | I/O 核心机制 | Java 后端适配重点 | 实战场景 |
|----------|----------|--------------|-------------------|----------|
| **UNIX** | 理论基石 | `select()` 多路复用 | 跨平台路径、文件权限 | 传统程序兼容 |
| **Linux** | 主流生产环境 | `epoll()`（ET/LT） | fd 限制优化、epoll 适配、Swap 优化 | 高并发 RPC、消息队列 |
| **Windows** | 本地开发环境 | **IOCP**（I/O 完成端口） | 路径分隔符、句柄管理、线程优先级 | 本地开发调试 |

### 11.2 核心差异点

| 差异点 | Windows | Linux |
|--------|---------|-------|
| 虚拟内存映射 | 效率较低 | 高效 |
| 内存回收 | 被动式 | 主动式 |
| 线程栈管理 | 默认 1MB，不可调 | 可调整（`-Xss`）|
| 文件系统 | NTFS（大小写不敏感） | EXT4/XFS（大小写敏感）|
| 路径分隔符 | `\`（反斜杠） | `/`（正斜杠）|
| 最大文件描述符 | 默认 1024（句柄） | 默认 1024（可调 `ulimit -n 65535`）|

> 💡 **适配建议**：生产环境优先选择 Linux；本地开发 Windows 时注意路径分隔符差异；跨平台部署使用 `File.separator` 或 `Path.of()`。

### 11.3 Linux vs Windows I/O 机制

| 机制 | Linux | Windows |
|------|-------|---------|
| I/O 多路复用 | `epoll`（事件驱动） | **IOCP**（完成端口） |
| 零拷贝 | `sendfile()` | `TransmitFile()` |
| 异步 I/O | Linux AIO | IOCP（原生异步） |
| Java 映射 | NIO Selector（epoll） | NIO Selector（select 模拟） |

> 💡 Windows 的 IOCP 是真正的异步 I/O 模型，比 Linux 的 epoll 更高效。Java AIO 在 Windows 上性能优于 Linux。
