# 死锁的本质与四个必要条件

> 死锁是一组进程/线程/事务互相持有对方需要的资源、谁也无法前进的"僵局"。判定死锁只有一把尺子——Coffman 四条件；区分死锁与饥饿、活锁，是正确讨论一切死锁策略的前提

## 1. 死锁的精确定义

### 1.1 教科书定义（Tanenbaum）

> 一组进程中的每个进程都在等待一个"只有本组中其他进程才能引发的事件"（通常是释放资源），则该组进程死锁。

### 1.2 三个特征拆解

```text
特征一：互锁（circular wait）——A 等 B、B 等 A（或更长的环）
特征二：全员阻塞——组内所有进程都处于等待态，没有进程能主动推进
特征三：永不自行解除——没有外部干预（剥夺/终止/超时），等待无限持续
```

### 1.3 一个标准示例

```java
// Java 版 ABBA：两个线程各持一把锁，等待对方的那把
// 线程 T1：synchronized(A) → synchronized(B)
// 线程 T2：synchronized(B) → synchronized(A)

public class ClassicDeadlock {
    static final Object A = new Object();
    static final Object B = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (A) {
                sleep(50);                     // 确保 T2 也拿到 B
                synchronized (B) { }           // 等 B —— B 被 T2 持有
            }
        });
        Thread t2 = new Thread(() -> {
            synchronized (B) {
                sleep(50);
                synchronized (A) { }           // 等 A —— A 被 T1 持有
            }
        });
        t1.start(); t2.start();
        // 结果：两个线程永久阻塞（jstack 显示 "Found one Java-level deadlock"）
    }
}
```

> 🎯 **核心要点**：死锁的本质是**等待关系成环**——理解了这个，04/05 章的资源分配图、等待图、检测算法全部是"画环找环"。

## 2. 资源分类：可重用与可消费

| 类型 | 定义 | 例子 | 与死锁的关系 |
|------|------|------|-------------|
| **可重用资源（reusable）** | 用完归还、可反复使用 | CPU、内存、磁盘、文件、锁、数据库行 | **死锁的主战场** |
| **可消费资源（consumable）** | 生产-消费，用完消失 | 信号量令牌、消息队列中的消息、中断 | 消费死锁较少见（如缓冲区空等待生产、满等待消费的环） |

```java
// 可消费资源的死锁示例（较少见但真实存在）
// 进程 P1：等 M2 的消息（由 P2 生产）……但 P1 持有 M1 的消息
// 进程 P2：等 M1 的消息（由 P1 生产）……但 P2 持有 M2 的消息
// 双方都"持有旧消息等新消息" → 生产-消费环形等待
```

> 💡 **理解意义**：死锁预防策略（03 章）对两类资源手段不同——可重用资源可"剥夺后归还"，可消费资源一旦消费就没了，无法剥夺。

## 3. Coffman 四个必要条件

> 1971 年 Coffman 提出：**四个条件同时成立**才可能死锁；只要破坏任意一个，死锁就不可能发生。这是整个死锁处理策略的基石。

### 3.1 条件一：互斥（Mutual Exclusion）

```text
资源同一时刻只能被一个进程使用（或占用）
例：打印机、行锁、同步块
```

| 讨论 | 说明 |
|------|------|
| 为什么必须 | 资源可共享（如只读文件）时，等待永不发生 |
| 能否破坏 | **基本不能**——互斥是很多资源的本质属性（锁、打印机的设计目的） |
| 破坏方式 | 只有"共享化改造"（如数据库用共享锁替代排他锁），绝大多数场景不可行 |

### 3.2 条件二：持有并等待（Hold and Wait）

```text
进程持有至少一个资源，同时等待获取被其他进程持有的额外资源
例：T1 持有 A，等 B；T2 持有 B，等 A
```

| 破坏方式 | 做法 | 代价 |
|---------|------|------|
| 预分配（一次性申请全部） | 事务开始前一次获取所有资源 | 资源利用率低、易饿死、难预估 |
| 申请前先释放已有 | 等待新资源前释放旧资源 | 业务逻辑复杂化 |
| 数据库：一次 `SELECT ... FOR UPDATE` 按序锁全 | 同预分配思想 | 长事务风险 |

### 3.3 条件三：不可剥夺（No Preemption）

```text
已分配的资源不能被强行取走，只能由持有者主动释放
```

| 破坏方式 | 做法 | 代价 |
|---------|------|------|
| 超时抢占 | 等待超时后释放已持有的资源 | 重试风暴、业务副作用 |
| Java：`tryLock(timeout)` | 拿不到第二把锁就释放第一把 | 需要处理部分完成状态 |
| 进程级抢占 | 强杀持有者 | 极端手段 |

### 3.4 条件四：循环等待（Circular Wait）

```text
存在进程集合 P1..Pn，P1 等 P2 的资源，P2 等 P3 的……Pn 等 P1 的资源
```

| 破坏方式 | 做法 | 代价 |
|---------|------|------|
| **全局锁序**（最实用） | 所有进程按同一顺序获取资源 | 需全局约定，跨系统难统一 |
| 资源编号 | 先拿编号小的资源 | 语义束缚（资源层次） |
| 数据库：统一 `ORDER BY 主键` | 多行加锁按主键排序 | 简单有效（06 章） |

> 🎯 **核心要点**：四条件中**前三个是资源/需求的属性**（大多不可改），**循环等待是代码行为的产物**（可全局规范）——所以工程上 95% 的死锁修复都落在"锁序规范"上。

## 4. 死锁 vs 饥饿 vs 活锁

三者常被混淆，但性质完全不同：

| 维度 | 死锁 | 饥饿（starvation） | 活锁（livelock） |
|------|------|-------------------|-----------------|
| 进程状态 | 所有进程阻塞（等资源） | 进程"活着"但永远得不到调度/资源 | 进程反复重试但永不推进 |
| 资源 | 被环内进程持有，不流动 | 资源在流动，就是不轮到自己 | 资源在让来让去 |
| 本质 | 循环等待（结构问题） | 调度不公平（策略问题） | 让出逻辑错误（代码问题） |
| 是否可自行恢复 | 否 | 否（长期） | **可**（运气/外部条件变化） |
| 典型例子 | 转账 ABBA | 短任务优先策略下长任务饿死；哲学家就餐拿不到筷子 | 两个进程检测到对方也让步，同时退让、同时重试，无限循环 |
| 检测方式 | WFG 找环 | 等待时间阈值 | 观察行为模式（难） |
| 常见对策 | 锁序、超时、检测解除 | 公平调度（FIFO、老化）、`ReentrantLock(true)` | 随机退避（指数退避、加随机抖动） |

```java
// 活锁示例：无随机退避的冲突重试
while (true) {
    if (tryLockA()) {
        if (tryLockB()) { break; }
        unlockA();           // 检测到失败就释放
        // 若两个线程总在"同时释放+同时重试" → 活锁
    }
}
// 修复：重试前 Thread.sleep(50 + random(100)) —— 随机抖动打破同步
```

> ⚠️ **辨析考题**：面试常问"死锁 vs 活锁 vs 饥饿"——标准答法是三者的**关键区别在资源**：死锁=资源被环内成员持有且不流动；饥饿=资源一直在流动但轮不到自己；活锁=资源在流动但流动本身是空转。

## 5. 死锁判定方法论

### 5.1 四步判定流程

```text
给定一个"卡死"场景，按顺序回答：
① 有互斥资源吗？          （无 → 不是死锁）
② 有进程持有资源又等资源吗？  （无 → 不是死锁）
③ 资源能被强行剥夺吗？      （能 → 不会是死锁）
④ 等待关系成环吗？          （不成环 → 不是死锁）
四问全"是" → 死锁
```

### 5.2 与竞态条件（race condition）的关系

```text
竞态条件：多线程访问共享可变数据，结果依赖执行时序 → 结果错误（可能碰巧正确）
死锁：等待关系成环，线程永久阻塞 → 结果缺失（永远不产生）
两者是"错误形态"的两种极端：
  竞态 → 该同步没同步（同步缺失）
  死锁 → 同步过头/同步方式错误（同步冲突）
一个关注"错误值"，一个关注"卡死"——都需要锁，但用锁的方式截然相反
```

## 6. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 死锁 = 互斥 + 持有等待 + 不可剥夺 + 循环等待，四条件同时成立，缺一不可；
> 2. 前三条件是资源本质属性（难改），循环等待是代码行为（可规范）——这就是"全局锁序"成为主流的根本原因；
> 3. 死锁（资源不流动）/饥饿（轮不到）/活锁（空转让渡）三者要能从资源角度清晰辨析。

**思考题**：

1. 只读文件被多个进程共享时，会不会有死锁？（→ 3.1 互斥条件）
2. 为什么说"破坏互斥"在实际系统中几乎不可行？（→ 3.1）
3. 哲学家就餐问题满足哪几个条件？怎么破？（→ 02/03 章）
4. 一个进程"永远等不到 CPU"是死锁吗？（→ 4 饥饿）
