## 1. 为什么内核需要静态死锁检测

### 1.1 内核死锁的特殊性

```text
用户态（Java）：死锁 = 业务 Bug，jstack 可查，重启可救
内核态：死锁 = 系统级故障
  ① 持锁代码路径极长：锁经过驱动/文件系统/内存管理层层嵌套
  ② 中断上下文：自旋锁持有时不能睡眠 → 等待即死机
  ③ 无用户态"重启"选项：检测必须前置（编译/开发期）而非事后
  ④ 内核锁数量庞大：子系统各自约定，人肉审计不现实
```

### 1.2 三类检测手段的层次

| 手段 | 时机 | 代表 | 定位 |
|------|------|------|------|
| 静态校验 | 编译/开发期 | sparse 等 | 语法级 |
| **动态校验** | 运行期（开发环境） | **lockdep、DEPT** | 本章主角 |
| 运行时兜底 | 运行期（生产） | hung task、watchdog | 最后防线 |

> 🎯 **核心要点**：内核死锁检测的重心在"**开发期动态校验**"——让死锁在测试环境就暴露，而不是等生产环境卡死。

## 2. lockdep：锁序校验器

### 2.1 原理：构建全局锁序图

```text
lockdep 在运行期记录每次"锁的获取顺序"：
  例：代码路径 P 先拿 L1 再拿 L2 → 记录依赖 L1 → L2
     （哈希化保存，内存开销很小）

构建完整"锁依赖图"后，检测规则：
  若某路径记录 L1 → L2，另一路径记录 L2 → L1
  → 依赖图中出现环 → 报告潜在死锁

输出信息（/proc/lockdep 与 dmesg）：
  "possible circular locking dependency detected"
  并附两条路径的完整调用栈（谁先拿了什么、再等什么）
```

### 2.2 关键设计

| 设计 | 说明 |
|------|------|
| 开关注入 | `CONFIG_LOCKDEP` 编译进内核；`lockdep_on/off` 可切换 |
| 类（class）抽象 | 以"锁的静态地址"归类，同一代码点不同实例算一类（避免实例爆炸） |
| 校验时机 | 运行时首次发现新依赖序时触发（不是每次加锁）——开销可控 |
| 误报与关闭 | 误报时该依赖序可被标记/忽略；**首次报告后停止**（防止刷屏） |
| 二十年战绩 | 捕获大量真实内核死锁，2026 年仍在发现新问题（CVE-2026-46304） |

### 2.3 为什么只认"锁序"

```text
lockdep 的世界观：死锁 = 锁获取顺序冲突
它只跟踪 lock/unlock 对（mutex、spinlock、rwsem 等经典锁原语）
→ 覆盖了"互斥锁死锁"这个大类的绝大多数

但这个模型有个结构性盲区：
  内核同步并不只有"锁"——
  等待 completion、等待 folio 锁释放、等待 DMA fence、
  等待 RCU 宽限期……这些"等待事件"同样能形成死锁环
```

## 3. lockdep 的盲区

| 盲区 | 场景 | 为什么 lockdep 看不见 |
|------|------|---------------------|
| **folio 锁** | `lock_page()` 等按位等待锁（wait-on-bit） | 不是经典 lock/unlock 原语，无获取顺序可记录 |
| **completion** | `wait_for_completion()` 等事件完成 | 没有"持有资源"概念，只有等待关系 |
| **DMA fence** | GPU/DRM 的跨上下文等待 | 等待-唤醒跨驱动层 |
| **waitqueue 一般模式** | 任意自定义等待 | 同上 |
| **读锁** | rwsem/rwlock 的读路径 | 处理不完善（读锁不互斥，但与写锁组合可能成环） |
| **跨上下文** | 等待发生在与获取不同的上下文 | 上下文间的关系未被建模 |

```text
共性：这些同步原语的死锁 = "等待事件"成环，而不是"锁序"成环
  A 等 B 的 folio 释放，B 等 C 的 completion，C 等 A 的锁
  → 环存在，但 lockdep 的锁序图里根本没有这些节点
```

> ⚠️ **现实后果**：lockdep 对 folio/等待类死锁"睁眼瞎"——2026 年的 LKDTM 实验证实：三个 folio 锁死锁场景，lockdep **一个都检测不到**（见第 5 节）。

## 4. DEPT：依赖跟踪器（2025-2026）

### 4.1 一句话定位

> DEPT（DEPendency Tracker）由 Byungchul Park（SK hynix/SK Telecom）提出：**不问"锁的顺序"，而问"每个等待在等哪个事件"**——把死锁检测从"锁序图"推广到"任意等待/事件依赖图"。

### 4.2 核心模型：S / W / E 三元组

```text
对每个上下文（context）记录三个状态：
  [S] start：事件上下文开始的位置
  [W] wait：上下文在哪里等待某个事件
  [E] event：该事件在哪里发生（由谁触发）

依赖图构建：
  事件 E 的发生依赖"唤醒 E 的上下文先执行到 E 点"
  等待 W 阻塞在事件 E 上
  → 构建"谁等谁"的依赖边

死锁判定：
  依赖图出现环 → 死锁（与 WFG 同一数学：环 = 死锁）
```

```text
与 lockdep 的本质差异：
  lockdep：记录"获取顺序对"（L1→L2）→ 只覆盖锁
  DEPT：记录"等待→事件"（W→E）→ 覆盖一切同步原语
    ——folio 锁、completion、DMA fence、waitqueue 全部可以建模
```

### 4.3 状态（截至 2026-08）

| 项目 | 状态 |
|------|------|
| 补丁系列 | v19（2026-07，40 个补丁，基于 v7.0 重基） |
| 合并状态 | **未合并**，实验性，`CONFIG_DEPT` 可选开启 |
| 架构 | 仅 x86_64 与 arm64 |
| 与 lockdep 关系 | **互补而非替代**：lockdep 管锁序校验，DEPT 管依赖检查，两者并行 |
| 已知问题 | 误报仍需注解打磨（mm/block/drm/net 各子系统）；Sashiko AI 审查指出 3 处高危潜在 bug（数据竞争、RCU 释放、PREEMPT_RT 自旋锁） |

### 4.4 演进亮点（v16→v19）

```text
v16：RCU 误报修复；dept_set_page_usage() 等页面使用注解 API
v17：Rust 辅助函数（wait_for_completion）；感知 lockdep_set_lock_cmp_fn()
v18：文档迁移 Documentation/dev-tools/；enter_from_user_mode() 统一钩子
v19：移除 recover-event 跟踪（减轻评审负担，转为外部维护）；SUNRPC 补丁获 Reviewed-by
```

## 5. LKDTM 验证实验

### 5.1 实验设计（2026-05 加入 lkdtm）

```text
三个新的内核崩溃用例（crash type）用于验证死锁检测器：
  FOLIO_LOCK_AA：单线程对 folio 锁自锁（AA 死锁）
  FOLIO_LOCK_ABBA：双线程 folio 锁 ABBA
  FOLIO_MUTEX_LOCK_ABBA：folio 锁 + mutex 混合 ABBA
```

### 5.2 结果对照

| 用例 | lockdep | DEPT | hung task |
|------|:---:|:---:|:---:|
| FOLIO_LOCK_AA | ❌ 检测不到 | ❌ 缺该场景 | ✅ 超时兜底 |
| FOLIO_LOCK_ABBA | ❌ 检测不到 | ⚠️ 误判为 AA 死锁 | ✅ |
| FOLIO_MUTEX_LOCK_ABBA | ❌ 检测不到 | ✅ 正确检测 | ✅ |

> 💡 **实验结论**：DEPT 思路正确（能抓住 lockdep 完全看不见的 ABBA），但分类与场景覆盖仍需打磨——这正是它未合并、继续迭代的原因。**双检测器并存**（lockdep 管锁序 + DEPT 管依赖 + hung task 兜底）是演进方向。

## 6. hung task：运行时兜底检测

```text
内核的"最后防线"（不是死锁检测器，是症状检测器）：

机制：
  每个任务定期记录"当前是否在调度"（t->sched_state / 挂起计数）
  内核线程（khungtaskd）周期性扫描：
    任务超过 hang_task_timeout_secs（默认 120s）没有调度
    → 打印任务栈 + 相关锁信息 → 可选 panic（hung_task_panic=1）

定位：lockdep/DEPT 是"开发期找结构问题"
      hung task 是"生产期抓症状"——不区分死锁/活锁/长阻塞，只看"卡住没"
```

| 对比 | lockdep/DEPT | hung task |
|------|:---:|:---:|
| 目标 | 结构预防（开发期） | 症状兜底（生产期） |
| 能否给出成因 | 能（依赖图/锁序） | 不能（只给栈） |
| 覆盖范围 | 检测过的代码路径 | 一切卡住的场景 |
| 误报 | 有（注解可消） | 有（长 I/O 任务误报，需调阈值） |

## 7. 实战案例与 CVE

| 案例 | 时间 | 说明 |
|------|------|------|
| coresight 设备注册死锁 | 2026-02 | lockdep 报告设备注册/注销的死锁 → 触发重构补丁 |
| **CVE-2026-46304** | 2026 | lockdep 发现 **nvmet-wq** workqueue 的锁嵌套问题（kernel 7.0.0-rc3）——锁序校验在 2026 年仍在捕获真实内核漏洞 |

> 🎯 **核心要点**：lockdep 二十年如一日地在"开发期拦截内核死锁"（2026 年还有 CVE 产出）；DEPT 把它从"锁序"推广到"等待-事件依赖"；hung task 兜底生产。三层组合 = 内核死锁防护的完整纵深。

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. lockdep 用"锁获取顺序图"在开发期拦截死锁——只覆盖经典锁原语，对 folio 锁/completion/DMA fence 等"等待事件"型同步是盲区；
> 2. DEPT（v19，2026，未合并）用 S/W/E 依赖跟踪把检测推广到任意同步原语——LKDTM 实验证明它能抓住 lockdep 看不见的 ABBA，但分类仍需打磨；
> 3. 内核死锁防护 = lockdep（锁序）+ DEPT（依赖，演进中）+ hung task（症状兜底）三层纵深。

**思考题**：

1. 为什么内核死锁检测要放在开发期而非生产期？（→ 1.1）
2. lockdep 的"锁序图"和 WFG（05 章）有什么关系？（→ 2.1：都是"等待关系成环"）
3. folio 锁死锁为什么 lockdep 看不见？（→ 3）
4. DEPT 的 S/W/E 三元组与 WFG 的"节点/边"如何对应？（→ 4.2：等待 W 是节点，依赖边是"等谁"）
