## 1. 高频面试题 16 问

### Q1：死锁的四个必要条件？

> 答：① 互斥——资源一次只能被一个进程使用；② 持有并等待——持有一个资源同时等待另一个；③ 不可剥夺——资源只能由持有者主动释放；④ 循环等待——等待关系成环。四条件同时成立才可能死锁，**破坏任意一个即可预防**（Coffman，1971）。
> 参考：01 章 3 节

### Q2：死锁、饥饿、活锁的区别？

> 答：关键看资源——死锁：资源被环内成员持有且**不流动**，全员阻塞；饥饿：资源**一直在流动**但调度不公平轮不到自己，进程活着；活锁：资源**在流动但空转让渡**，进程反复让步重试永不推进（如无随机退避的冲突重试）。死锁是结构问题（环），饥饿是策略问题（不公平），活锁是代码问题（让出逻辑）。
> 参考：01 章 4 节

### Q3：哲学家就餐问题怎么死锁？三种解法？

> 答：5 人同时拿起左手筷子等右手——循环等待。解法：① 最多 4 人同时上桌（破坏循环等待，限制并发）；② 先拿编号小的筷子（全局锁序）；③ 一次性拿两支、拿不到就放（预分配）。面试加分：解法②就是生产环境的"按 ID 排序加锁"原型。
> 参考：02 章 1 节、03 章 5 节

### Q4：怎么预防死锁？工程上最常用哪种？

> 答：破坏四条件——互斥基本不可破（资源本质）；持有等待用预分配（一次性获取）；不可剥夺用超时/抢占（tryLock/TTL）；循环等待用**全局锁序**（最实用：零运行开销、资源利用率高）。生产组合拳：锁序防环 + 超时兜底 + 随机退避防活锁。数据库场景 ~95% 死锁源于多表更新顺序不一致，统一 `ORDER BY 主键` 即可。
> 参考：03 章、06 章 3.3

### Q5：银行家算法是怎么工作的？

> 答：维护四张表（Available/Max/Allocation/Need），每次请求按三步走：① 检查 `Request ≤ Need`（合法性）；② 检查 `Request ≤ Available`（可行性）；③ 试探分配后跑安全性检查（贪心找"Need ≤ Work"的进程，完成就回收资源），存在安全序列则批准，否则拒绝。核心思想：**先假想、后验证、再提交**，保证系统只进入安全状态。生产不用它的原因：需要预先知道每个进程的最大需求（现实中拿不到）。
> 参考：04 章

### Q6：安全状态和不安全状态什么关系？

> 答：安全状态 = 存在安全序列（所有进程可依次完成）⇒ 一定无死锁；不安全状态 ⇏ 死锁（只是有可能）。集合关系：安全 ⊂ 无死锁；死锁 ⊂ 不安全。银行家算法只允许进入安全状态。
> 参考：04 章 2/7 节

### Q7：死锁检测的原理？InnoDB 怎么做的？

> 答：维护等待图（WFG：节点=事务，边=等待关系），**找环 = 死锁**（DFS 三色标记 / Tarjan SCC）。InnoDB：锁等待发生时触发检测，遍历 WFG，发现环则回滚"修改行数最少"的事务，返回 ERROR 1213 (40001) 供应用重试；检测有上限（wait-for 超 200 事务或 100 万锁即判死锁回滚），`innodb_lock_wait_timeout`（默认 50s）兜底检测失效场景。
> 参考：05 章、06 章 2 节

### Q8：innodb_deadlock_detect=OFF 有什么风险？

> 答：动机是热点行高并发下 WFG 遍历成为 CPU 瓶颈。风险：① 死锁不再即时解除，事务持锁等到超时 → 连接池耗尽级联雪崩；② `LATEST DETECTED DEADLOCK` 永远为空（不是没死锁，是没检测——排查陷阱）；③ 真死锁频繁时系统直接卡死。2026 共识：检测本身极少导致故障，真正危险的是失控的锁竞争；仅压测证明瓶颈 + 应用有重试闭环时才关。
> 参考：06 章 3.2

### Q9：数据库死锁怎么处理？应用侧怎么配合？

> 答：数据库：InnoDB 自动回滚受害者 + 返回 40001；应用：捕获 40001 重试**整个事务**（含前置查询），带指数退避 + 随机抖动 + 限次。预防：多行更新统一锁序、事务短小、`SKIP LOCKED` 队列化、监控锁等待而非只盯死锁数。
> 参考：08 章 3/4 节

### Q10：分布式系统死锁为什么难检测？怎么解？

> 答：难在无全局等待图——资源跨节点、通信延迟、无天然图所有者、各节点单独看都健康。检测架构：集中式（有单点与陈旧数据）、分层式（本地+摘要边）、全分布式（CMH 探测：probe 沿等待链追逐，回到发起者=有环）。生产普遍做法：本地快速检测 + 跨节点超时/租约兜底 + 全链路 trace 事后分析。
> 参考：06 章 4/5 节

### Q11：wait-die 和 wound-wait 的区别？

> 答：都是时间戳预防协议（老事务 TS 小）。wait-die：老等少→等待，少等老→**少自己回滚**（只回滚年轻者，无回滚传播，但年轻者可能饥饿）；wound-wait：老等少→**老伤害少**（夺资源让少回滚），少等老→等待（无饥饿，但回滚传播）。本质是"时间戳版的全局锁序"——等待边方向一致，环不可能形成。
> 参考：06 章 6.1

### Q12：Saga 为什么能避免分布式死锁？

> 答：死锁需要"跨节点持锁等待"；Saga 让每个服务只管自己的本地事务，提交即释放锁，失败用**补偿（undo）**而非等待 → 跨服务持锁等待结构被消灭。代价：最终一致性（补偿期间数据短暂不一致）、补偿逻辑复杂。
> 参考：06 章 6.2

### Q13：lockdep 是什么？怎么检测死锁？

> 答：Linux 内核锁序校验器（CONFIG_LOCKDEP）：运行期记录每次锁获取顺序（L1→L2 依赖边），构建全局锁序图，发现两条路径顺序相反（L1→L2 与 L2→L1）即报"possible circular locking dependency"，附两条调用栈。只覆盖经典锁原语——folio 锁、completion、DMA fence 等"等待事件"同步是盲区。
> 参考：07 章 2/3 节

### Q14：DEPT 是什么？和 lockdep 什么关系？

> 答：DEPT（DEPendency Tracker，2025-2026 实验性补丁，v19 未合并）：不问锁顺序，问"每个等待在等哪个事件"——跟踪 S（上下文开始）/W（等待点）/E（事件点），构建等待-事件依赖图，找环判死锁。覆盖 lockdep 盲区（LKDTM 实验：folio 锁 ABBA 死锁 lockdep 全看不见，DEPT 能抓到）。与 lockdep 互补并存：lockdep 管锁序、DEPT 管依赖、hung task 兜底。
> 参考：07 章 4/5 节

### Q15：怎么用 jstack 定位 Java 死锁？

> 答：`jstack <pid>` 自动检测并输出 "Found one Java-level deadlock" 段：读每个线程的 `locked <地址>` 与 `waiting to lock <地址>`，同一地址出现在"T1 的 locked"和"T2 的 waiting"即为环的边；对照栈行号找到加锁点。程序化检测用 `ThreadMXBean.findDeadlockedThreads()`（覆盖监视器+JUC 锁）。
> 参考：08 章 2 节

### Q16：怎么防止"锁序"被破坏（治理层面）？

> 答：① 加锁收敛到统一工具类（如 `LockOrder.enter(a, b)` 内部排序），禁止裸锁；② 代码评审清单检查"两条路径加锁顺序相反"；③ 分布式锁 key 字典序；④ 数据库多行更新 ORDER BY 主键；⑤ 静态检查工具（SpotBugs 等）。锁序是"约定"，靠工具与评审落地而非自觉。
> 参考：08 章 5/7 节

### 追问：分布式锁死锁与单机死锁的区别？（深挖向）

> 答：单机死锁有全局检测者（JVM 的 jstack、InnoDB 的 WFG），分布式**没有全局等待图**——所以策略重心不同：单机靠"检测+解除"，分布式靠"预防+超时"（锁序、TTL 租约、Saga）。另一差异：分布式还有"持有者消失"型死锁（崩溃后锁不释放，02 章 6 节）——单机不存在此问题。面试加分：把 06 章的 wait-die/wound-wait 与 CMH 探测讲出来。
> 参考：02 章 6 节、06 章

### 追问：锁升级与死锁有关系吗？

> 答：无直接关系——锁升级（偏向→轻量→重量）是 synchronized 的性能优化路径，不产生等待环；但重量级锁竞争加剧会**提高死锁发生概率**（等待更多），且轻量锁自旋消耗 CPU 会放大锁序错误的后果。面试可借此展示"性能机制与正确性机制的区分"。
> 参考：JUC 体系 03-synchronized 与锁升级

### 追问：如何设计一个"无死锁"的系统？

> 答：三层设计——① 结构层：全局锁序（所有资源排序获取）+ 无跨服务持锁（Saga 化）；② 机制层：超时兜底（tryLock/TTL）+ 随机退避防活锁；③ 检测层：JFR/监控告警（死锁计数、锁等待指标）+ 故障演练。面试答"设计题"要有层次：结构上不可能 → 机制上兜底 → 检测上发现。
> 参考：08 章 5 节

### 追问：死锁和活锁在线上怎么区分？（排障向）

> 答：看资源与线程状态——死锁：线程 BLOCKED/WAITING 且资源不流动（jstack 能直接检测 "Found one Java-level deadlock"，08 章）；活锁：线程 RUNNABLE 但反复重试不前进（jstack 看不出异常——CPU 占用高 + 日志大量重试）。区分手段：抓线程栈（死锁定位环）vs 观察重试模式（活锁定位退避缺失）。加分项：活锁的修复是加随机退避（03 章）。
> 参考：01 章 4 节、08 章 2 节

### 追问：数据库死锁日志怎么快速定位业务代码？（实战向）

> 答：四步——① 看 LATEST DETECTED DEADLOCK 的"五要素"（事务 ID/语句/等待锁/持有锁/受害者，08 章 3 节）；② 找两条 SQL 的锁序（是否 UPDATE id=1→2 与 id=2→1 反向）；③ 回业务代码定位加锁顺序（事务内语句顺序）；④ 修复 = 统一 ORDER BY 主键或拆分事务。加分项：开 `innodb_print_all_deadlocks` 拿全量现场（06 章），应用侧 40001 重试闭环兜底。
> 参考：06 章 3 节、08 章 3 节

### 追问：死锁与数据库事务隔离级别有关系吗？（综合向）

> 答：间接相关——隔离级别越高（RR > RC），锁的范围越大（间隙锁），死锁概率越高（06 章）；但死锁的**直接成因**是锁序与持锁时长，与隔离级别无必然关系。工程实践：业务允许时用 READ COMMITTED 减少间隙锁死锁；锁序规范对所有隔离级别都适用。加分项：说明"MVCC 减少的是读写阻塞，不是死锁"——读旧版本快照不参与锁等待。
> 参考：06 章 3 节、08 章 5 节

## 2. 易错点清单

| # | 易错点 | 正确认知 |
|---|--------|---------|
| 1 | "循环等待 = 死锁" | 循环等待只是四条件之一，缺任一条件（如资源可剥夺）就不会死锁 |
| 2 | "不安全状态 = 死锁" | 不安全只是"有可能死锁"，安全状态才严格无死锁 |
| 3 | "银行家算法需要知道 Need" | 它还需要**Max**（最大需求声明）——这是生产不用的主因 |
| 4 | "资源分配图有环 = 死锁" | 多实例资源时，有环只是"可能死锁" |
| 5 | "InnoDB 死锁检测是定时任务" | 是**锁等待瞬间**触发的即时检查（毫秒级） |
| 6 | "LATEST DETECTED DEADLOCK 为空 = 无死锁" | 检测被关闭时它也永远为空 |
| 7 | "40001 重试当前语句即可" | 必须**重放整个事务**（前置查询结果可能已过期） |
| 8 | "死锁重试越多越好" | 无退避的重试形成活锁；无限次重试形成雪崩 |
| 9 | "lockdep 能检测一切内核死锁" | 只覆盖经典锁序；等待类同步是盲区 |
| 10 | "Saga 是最终一致性替代" | Saga 不是不用锁，是**消灭跨服务持锁**——锁仍在，只是不跨节点 |

## 3. 知识体系一句话串讲

```text
死锁 = 等待关系成环（互斥 + 持有等待 + 不可剥夺 + 循环等待）
        │
        ├── 预防（03）：锁序（破环）/ 预分配（破持有）/ 超时（破不可剥夺）
        ├── 避免（04）：银行家算法 —— 假想分配 + 安全性检查 → 只进安全状态
        ├── 检测（05）：资源分配图 → WFG 找环（DFS/Tarjan）
        │     └── 解除：终止 / 剥夺 / 回滚（InnoDB 回滚最小事务 → 40001 重试）
        │
        ├── 数据库（06）：2PL 结构性代价；InnoDB 参数三件套
        │     └── 分布式：无全局图 → CMH 探测 / 超时租约 / wait-die·wound-wait / Saga
        ├── 内核（07）：lockdep 锁序图（20 年）→ DEPT 依赖图（2026 实验）→ hung task 兜底
        └── 工程（08）：jstack 找环 → 锁序+超时+退避 → 监控锁等待 → 评审清单
```

## 4. 快速自测（含答案）

1. **死锁四条件缺一可吗？** 可——破坏任一即可预防（01 章）。
2. **哲学家就餐的最小死锁环？** 5 人同时拿左手筷（02 章）。
3. **银行家算法的四张表？** Available/Max/Allocation/Need（04 章）。
4. **安全序列存在 = ？** 安全状态，无死锁（04 章）。
5. **WFG 找环的算法？** DFS 三色标记 / Tarjan SCC（05 章）。
6. **InnoDB 回滚谁？** 修改行数最少的事务，返回 40001（06 章）。
7. **innodb_lock_wait_timeout 默认值？** 50s（06 章）。
8. **wait-die 谁可能饥饿？** 年轻事务（反复 die）（06 章）。
9. **lockdep 的检测对象？** 锁获取顺序（锁序图），非等待事件（07 章）。
10. **jstack 找死锁搜什么？** "Found one Java-level deadlock"（08 章）。
11. **40001 重试的纪律？** 重放整个事务 + 退避 + 限次（08 章）。
12. **DEPT 的 S/W/E 各是什么？** 上下文开始/等待点/事件点（07 章）。
