# 死锁预防：破坏四个必要条件

> 预防 = 让死锁在结构上不可能发生。四条路分别对应四个条件：破坏互斥（基本不可行）、破坏持有等待（预分配）、破坏不可剥夺（超时抢占）、破坏循环等待（全局锁序）——工程上 90% 的实践都落在最后一条

## 1. 预防的总体框架

```text
死锁处理策略谱系（从"预防"到"放任"）：
┌─────────────────────────────────────────────────┐
│ 预防（Prevention）  静态保证，死锁不可能发生       │ ← 本章
│ 避免（Avoidance）   动态判断，拒绝不安全的分配    │ ← 04 章（银行家）
│ 检测+解除（Detection） 允许发生，发现后打破环      │ ← 05 章
│ 忽略（Ostrich）     假装没有，代价最低            │ ← 多数 OS 现状
└─────────────────────────────────────────────────┘
预防是唯一"零运行成本"（无检测开销）但"设计成本最高"的策略
```

## 2. 破坏互斥：为什么基本不可行

### 2.1 思路

让资源可同时共享（如把排他锁改为共享锁/读写锁），消除"等待"的存在基础。

### 2.2 现实

| 资源 | 能否共享化 | 原因 |
|------|:---:|------|
| 打印机 | ❌ | 输出会交错，物理上必须互斥 |
| 数据库行 | 部分 | 读可共享，**写必须互斥**——写互斥是数据一致性的根基 |
| Java 同步块 | ❌ | synchronized 的语义就是互斥 |
| 文件（只读场景） | ✅ 可 | 只读文件多进程共享无死锁——但引入写就回到互斥 |

### 2.3 结论

```text
互斥不是"实现缺陷"，而是"资源语义"。
把互斥资源改造成共享 = 牺牲正确性换取无死锁 —— 没有人会这么做。
唯一现实化的变形：读写锁（共享锁/排他锁）——读读可共享，写与其他互斥，
  它减少的不是"死锁"，而是"等待概率"。
```

> 🎯 **核心要点**：破坏互斥在理论上成立、工程上不可行——它作为"预防路径"存在的意义是**让我们把注意力转向后三条**。面试答"四条都怎么破"时，第一条要给出"基本不可行"的判断依据。

## 3. 破坏持有并等待：预分配

### 3.1 两种做法

```text
做法一：一次性申请（all-at-once）
  进程开始时申请全部所需资源，全部到手才执行
  → 执行期间不再等资源 → 持有等待条件被破坏

做法二：先释放再等待（release-then-wait）
  等待新资源前，先释放已持有的
  → 等待期间不持有 → 条件被破坏
```

### 3.2 Java 实现：一次性获取两把锁

```java
// 转账场景：同时获取两把锁（拿不到第二把就释放第一把）
public void transfer(Account a, Account b, int amount) throws InterruptedException {
    // 循环重试（配合随机退避防活锁）
    while (true) {
        if (a.lock.tryLock()) {                    // 第一把
            try {
                if (b.lock.tryLock()) {            // 第二把
                    try { transferCore(a, b, amount); return; }
                    finally { b.lock.unlock(); }
                }
            } finally {
                a.lock.unlock();                   // 拿不到 b 就释放 a
            }
        }
        Thread.sleep(ThreadLocalRandom.current().nextLong(10, 100));  // 退避防活锁
    }
}
```

### 3.3 代价

| 代价 | 说明 |
|------|------|
| 资源利用率低 | 一次申请的资源可能大部分时间用不上 |
| 易饥饿 | 所需资源长期不齐的进程可能一直等不到 |
| 预估困难 | 进程很难提前知道全部所需资源（尤其运行时动态分配） |
| 长持有窗口 | 预分配导致持有时间长，间接增加其他进程等待 |

> 💡 **适用判断**：预分配适合"资源集合固定、规模小、执行时间短"的场景（如两账户转账）；不适合"资源动态增长"的长任务。

## 4. 破坏不可剥夺：超时与抢占

### 4.1 思路

允许系统**强行取走**已分配的资源——等待超时后，持有者被剥夺。

### 4.2 三种实现

| 实现 | 机制 | 例子 |
|------|------|------|
| 等待超时 | 等待超时后**释放自己已持有的资源**并重试 | Java `tryLock(timeout)`、Redis TTL |
| 持有者超时 | 资源本身有租约，超时自动失效 | 分布式锁 TTL（02 章 6 节） |
| 抢占剥夺 | 系统强制回收资源（含杀掉持有者） | 进程终止、事务回滚 |

```java
// Java：带超时的锁获取
ReentrantLock lock = new ReentrantLock();
if (lock.tryLock(3, TimeUnit.SECONDS)) {       // 3 秒拿不到就放弃
    try { doWork(); }
    finally { lock.unlock(); }
} else {
    // 降级/重试/记录
}
```

### 4.3 代价与风险

```text
风险一：部分完成状态
  释放"拿到的第一把锁"时，业务可能已做了一半 → 需要补偿逻辑

风险二：重试风暴
  多线程同时超时同时重试 → 活锁化 → 需要随机退避

风险三：剥夺成本
  被剥夺的进程状态要回滚 —— 只对可回滚资源（事务）可行
  打印机等不可回滚资源（已打印一半）无法剥夺
```

> 🎯 **核心要点**：超时是"最通用的兜底"（连分布式环境都只能靠它），但它只是**把死锁变成异常**——真正无死锁还要靠锁序。生产策略 = 锁序防环 + 超时兜底 + 随机退避防活锁。

## 5. 破坏循环等待：全局锁序

### 5.1 思路

给所有资源定义**全局顺序**，任何进程都严格按顺序获取资源——等待关系永远指向"编号更大"的方向，环在结构上不可能形成。

```text
资源编号：R1 < R2 < R3 < ... < Rn
规则：任何进程必须先申请编号小的资源
→ 等待边永远从"小编号持有者"指向"大编号等待者"→ 有向无环
→ 反证：若存在环 R1→R2→...→R1，则编号严格递增又回到自身 —— 矛盾
```

### 5.2 三个应用实例

| 域 | 实现 |
|----|------|
| Java 多线程 | 按对象唯一 ID 排序加锁（02 章转账修复） |
| MySQL | 多行更新统一 `ORDER BY 主键`（06 章） |
| Redis 分布式锁 | 按 key 字典序获取（02 章 6 节） |

```java
// 通用模式：比较器 + 排序获取
void lockInOrder(List<Resource> resources) {
    resources.sort(Comparator.comparing(r -> r.id));   // 全局顺序
    for (Resource r : resources) r.lock();
}
```

### 5.3 失效场景（必须知道的边界）

| 失效场景 | 说明 |
|---------|------|
| 顺序不全局统一 | A 模块按 ID、B 模块按名称 → 两套顺序 = 无顺序 |
| 动态引入新资源 | 新资源没纳入排序（编号冲突） |
| 顺序与业务冲突 | 锁序与业务访问顺序不一致 → 需要重构调用方 |
| 跨系统协调 | 分布式下全局顺序需要全团队约定（schema 文档、代码评审把关） |

> ⚠️ **工程现实**：锁序的难点**不在技术而在治理**——它是"约定"，需要评审、文档、自动化检查（如把加锁调用集中到统一工具类，禁止裸锁）。

## 6. 四种预防策略权衡表

| 策略 | 破坏条件 | 实现成本 | 运行开销 | 资源利用率 | 饥饿风险 | 生产适用度 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| 共享化改造 | 互斥 | 高 | 低 | 高 | 低 | ★☆☆（基本不可行） |
| 预分配 | 持有等待 | 中 | 低 | **低** | **高** | ★★☆（固定资源集合） |
| 超时抢占 | 不可剥夺 | 低 | 中（重试） | 中 | 中 | ★★★（兜底必备） |
| **全局锁序** | 循环等待 | **中（治理成本）** | **零** | 高 | 低 | ★★★★（首选） |

```text
结论：
  全局锁序 = 零运行时开销 + 最高资源利用率 + 最低饥饿风险
  → 单机场景的"正统答案"
  超时 = 唯一不依赖全局约定的方案 → 分布式场景的"唯一兜底"
  预分配 = 特定场景（固定资源）可用
```

> 💡 **组合拳**：生产系统通常"锁序 + 超时 + 随机退避"三件套：锁序防环、超时防无限等待、退避防活锁。三者缺一都可能出事故。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 预防四路对应四条件：互斥不可破、持有等待用预分配、不可剥夺用超时、循环等待用全局锁序；
> 2. 全局锁序是首选——零运行开销、靠治理保证，工程师的日常工作就是"给锁排顺序"；
> 3. 超时把死锁变成异常，是分布式场景的唯一兜底；但超时+重试不防活锁，必须加随机退避。
