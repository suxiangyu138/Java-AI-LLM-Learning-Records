# 死锁检测与解除

> 检测 = 允许死锁发生，然后用等待图（WFG）找环；解除 = 终止进程、剥夺资源或回滚事务。这是 InnoDB 的真实策略（WFG + 回滚最小事务），也是工程上"预防失效后"的最后防线

## 1. 检测策略的整体定位

```text
预防（03 章）：死锁不可能发生 —— 结构保证
避免（04 章）：死锁不被允许进入 —— 动态拒绝
检测（本章）：死锁允许发生 —— 发生后发现并打破
忽略：假装不存在 —— 实际成本最低（多数 OS 日常选择）
```

**检测策略的适用条件**：

| 条件 | 说明 |
|------|------|
| 死锁发生频率低 | 检测成本才划算（高频死锁说明代码有结构问题，该预防） |
| 有解除手段 | 能找到受害者并安全回滚（事务天然可回滚） |
| 检测成本可控 | 图遍历频率与规模在可接受范围 |

> 💡 **现实判断**：OS 层大多"忽略"（死锁极少见）；**数据库层必然检测**（锁竞争频繁、事务可回滚——InnoDB 就是 WFG 检测的教科书实现，06 章详述）。

## 2. 资源分配图与等待图

### 2.1 资源分配图（Resource Allocation Graph）

```text
两种节点：进程节点（圆圈）与资源节点（方框）
两类边：请求边 Pi → Rj（Pi 请求 Rj）；分配边 Rj → Pi（Rj 分配给 Pi）

示例：P1 持 R1，等 R2；P2 持 R2，等 R1
  P1 ──请求──▶ R2 ──分配──▶ P2 ──请求──▶ R1 ──分配──▶ P1   （环！）
```

**判定规则**：

| 图形态 | 结论 |
|--------|------|
| 无环 | 无死锁 |
| 有环，且环内资源**只有单个实例** | 死锁 |
| 有环，但环内某资源有多个实例 | **可能**死锁（环只是必要条件） |

### 2.2 等待图（Wait-For Graph，WFG）

检测时的简化：把资源节点折叠掉，直接画"进程 → 等待 → 进程"：

```text
WFG：节点 = 进程/事务；边 Pi → Pj 表示"Pi 等待 Pj 持有的资源"
判定：有环 ⇔ 死锁（对单实例资源严格成立）

InnoDB 视角的 WFG：
  节点 = 事务；边 T1 → T2 表示"T1 等待 T2 持有的行锁"
  新事务等待时加边，锁释放时删边
```

> 🎯 **核心要点**：资源分配图是"教学形态"，WFG 是"实现形态"——所有真实的死锁检测器（InnoDB、分布式系统）都在维护 WFG 并查环。04 章银行家算法回答"怎么避免"，本章 WFG 回答"怎么发现"。

## 3. 找环算法：DFS 与 SCC

### 3.1 DFS 找环（单环判定，O(V+E)）

```java
// 等待图存为邻接表：graph[u] = [v1, v2, ...]（u 等待 v1、v2 的资源）
boolean hasCycle(int n, List<List<Integer>> graph) {
    int[] color = new int[n];            // 0=未访问 1=访问中 2=已完成
    for (int i = 0; i < n; i++) {
        if (color[i] == 0 && dfs(i, graph, color)) return true;
    }
    return false;
}
boolean dfs(int u, List<List<Integer>> graph, int[] color) {
    color[u] = 1;                        // 进入：标记访问中
    for (int v : graph.get(u)) {
        if (color[v] == 1) return true;  // 遇到"访问中"的节点 → 后向边 → 有环！
        if (color[v] == 0 && dfs(v, graph, color)) return true;
    }
    color[u] = 2;                        // 完成
    return false;
}
```

```text
三色标记法要点：
  白色（未访问）→ 灰色（访问中）→ 黑色（已完成）
  灰色节点被再次遇到 = 后向边 = 环
  复杂度 O(V + E)，一次完整遍历找全部环需对每个起点跑
```

### 3.2 Tarjan/Kosaraju SCC（找全部死锁环）

```text
强连通分量（SCC）：互相可达的节点集合
死锁环 ⇔ SCC（或 SCC 的一部分）
Tarjan 算法：O(V+E) 一次遍历找全部 SCC
生产用途：死锁检测器找到环后，还要"选受害者"——SCC 给出环内全部成员
```

### 3.3 检测时机

| 时机 | 做法 | 例子 |
|------|------|------|
| 持续检测 | 每次资源请求失败时检查 | InnoDB（等待发生时触发） |
| 周期检测 | 定时器触发 | 分布式检测器（如每 5s） |
| 事件触发 | 等待超时/监控阈值时 | 业务层兜底 |

## 4. 检测时机与开销

### 4.1 检测成本的现实问题

```text
单机 WFG：图很小（几十~几百节点），O(V+E) 微秒级 → 持续检测可行
InnoDB：等待发生时检查 → 高并发下可能成为瓶颈
   → 官方限制：wait-for 列表超 200 个事务，或需检查超过 100 万个锁
     直接判死锁并回滚："TOO DEEP OR LONG SEARCH IN THE LOCK TABLE WAITS-FOR GRAPH"
   → 极端场景可关检测（innodb_deadlock_detect=OFF）改用超时（06 章）
分布式 WFG：图跨节点、有延迟 → 检测成本高 → 靠超时/探测（06 章）
```

### 4.2 超时检测（最朴素的检测）

```java
// 等待超时即视为"疑似死锁"——不精确但零图维护成本
long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(3);
while (!lock.tryLock(100, TimeUnit.MILLISECONDS)) {
    if (System.nanoTime() > deadline) {
        throw new TimeoutException("疑似死锁，放弃等待");   // 交由上层重试/降级
    }
}
```

| 检测方式 | 精度 | 成本 | 误判风险 |
|---------|:---:|:---:|:---:|
| WFG 找环（InnoDB） | 精确 | 中（等待时触发） | 无（环=死锁） |
| 超时检测 | 不精确 | 低 | 长事务被误杀/真死锁被拖死 |
| 心跳/租约 | 不精确 | 低 | 网络抖动误判 |

## 5. 解除策略：终止、剥夺与回滚

### 5.1 三种解除手段

| 手段 | 做法 | 例子 | 代价 |
|------|------|------|------|
| **终止进程** | 杀进程（或杀环中部分） | 数据库杀会话 | 进程状态丢失；部分执行结果无效 |
| **剥夺资源** | 强制回收已分配资源给他人 | OS 抢占、Redis 锁 TTL 过期 | 被剥夺者状态损坏 |
| **回滚** | 撤销部分/全部执行 | 事务回滚、检查点恢复 | 需要日志/检查点支撑 |

### 5.2 终止策略的两个问题

```text
问题一：终止哪些？
  方案 A：全部终止 —— 简单但浪费（环内可能大部分已近完成）
  方案 B：逐个终止 —— 先杀一个，检测还有环吗？没有→解除；还有→再杀一个
           （逐出环的"最小代价法"）

问题二：终止成本如何衡量？
  ✗ 不是"哪个进程最好杀"，而是"杀谁总代价最小"：
  - 优先级（先杀低优先级）
  - 已用 CPU 时间（杀刚启动的）
  - 还要多久完成（杀接近完成的——注意反向直觉：接近完成的杀掉浪费最多，通常先杀"刚起步"的）
  - 占用了多少资源（杀占用少的）
  - 是否交互式（优先杀批处理）
```

### 5.3 InnoDB 的解除实践（工程范本）

```text
InnoDB 检测到环后：
  选择受害者 = 修改行数最少（insert/update/delete 最少）的事务
  回滚该事务 → 返回 ERROR 1213 (40001)
  应用侧：捕获 40001 后重试整个事务（通常立即成功，因为对方已提交或回滚）
```

## 6. 受害者选择与饥饿防护

### 6.1 选择标准汇总

| 标准 | 原则 | 理由 |
|------|------|------|
| 修改行数（InnoDB） | 少者回滚 | 回滚成本低 |
| 事务开始时间 | 年轻者回滚 | 已做工作少 |
| 优先级 | 低者终止 | 业务权重 |
| 资源占用 | 少者终止 | 损失小 |
| 迭代终止（OS） | 每次只杀一个 | 避免过度终止 |

### 6.2 饥饿防护

```text
问题：固定"杀年轻事务"策略下，老事务若反复死锁，年轻事务被反复牺牲
      → 年轻事务永远被牺牲 = 饥饿
方案：回滚次数记录 —— 被回滚次数超过阈值的进程不再优先牺牲
      （InnoDB 的 victim 选择考虑 rollback count，避免同一事务被反复牺牲）
```

## 7. 检测 vs 预防 vs 避免：策略总表

| 维度 | 预防 | 避免 | 检测+解除 |
|------|:---:|:---:|:---:|
| 死锁能否发生 | 不能（结构） | 不能（动态拒绝） | **能（发生后打破）** |
| 需要什么信息 | 资源顺序约定 | 每个进程的 Max | 无（只需等待关系） |
| 运行开销 | 零 | 每次分配 O(n²m) | 检测图遍历 + 回滚成本 |
| 资源利用率 | 中（锁序束缚） | 高（理论上） | 高 |
| 适用场景 | 单机可控代码 | 教学/理论 | **数据库、生产兜底** |
| 工程代表 | 锁排序规范 | 银行家（几乎不用） | **InnoDB WFG** |

> 💡 **决策直觉**：三层策略不是互斥而是互补——生产系统"预防为主（锁序）、检测兜底（InnoDB/JFR）、超时防线（最后手段）"三层叠加。

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 检测 = 维护等待图（WFG）+ 找环（DFS/Tarjan），环 = 死锁；InnoDB 在每次锁等待时触发，是生产级范本；
> 2. 解除三手段：终止、剥夺、回滚——InnoDB 选"修改行数最少的事务"回滚并返回 40001 供应用重试；
> 3. 检测有成本上限（InnoDB 200 事务/100 万锁阈值），极端场景降级为超时；受害者选择要注意防饥饿。

**思考题**：

1. 资源分配图有环但资源多实例时，为什么只是"可能死锁"？（→ 2.1）
2. 三色标记找环，遇到灰色节点为什么一定有环？（→ 3.1）
3. InnoDB 为什么选"修改行数最少"的做受害者？（→ 5.3/6.1）
4. 反复被选为受害者的年轻事务如何防止饥饿？（→ 6.2）
