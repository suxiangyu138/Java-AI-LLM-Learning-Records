## 1. Java 死锁排查三件套

| 工具 | 场景 | 命令/API |
|------|------|---------|
| **jstack** | 线上快速确认 | `jstack <pid>`（自动检测并输出死锁段） |
| **ThreadMXBean** | 代码内/监控自动检测 | `findDeadlockedThreads()` |
| **jcmd / JFR** | 历史采样、转储文件 | `jcmd <pid> Thread.print`、JFR `jdk.ThreadDump` |
| Arthas | 交互式诊断 | `thread -b`（一键找阻塞线程） |

```java
// ThreadMXBean 自动检测（监控脚本/健康检查用）
ThreadMXBean tmx = ManagementFactory.getThreadMXBean();
long[] deadlocked = tmx.findDeadlockedThreads();     // 返回死锁线程 ID
if (deadlocked != null) {
    ThreadInfo[] infos = tmx.getThreadInfo(deadlocked, true, true);
    // 组装告警：线程名 + 锁持有 + 锁等待 + 栈
}
```

> 💡 **要点**：`findDeadlockedThreads()` 检测的是"监视器死锁 + JUC 锁死锁"（`findMonitorDeadlockedThreads()` 只看监视器）——用前者。

## 2. jstack 实战：一次完整定位

### 2.1 现场

```bash
jstack 12345 > dump.txt
```

### 2.2 关键输出解读

```text
Found one Java-level deadlock:
=============================
"T1":
  waiting to lock monitor 0x00007f8d (object 0x...2f18, java.lang.Object),
  which is held by "T2"
  T1 stack trace:
  at DeadlockDemo.lambda$main$0(DeadlockDemo.java:22)   ← 卡在 synchronized(B)
  - waiting to lock <0x...2f28> (a java.lang.Object)
  - locked <0x...2f18> (a java.lang.Object)             ← 已持有 A

"T2":
  waiting to lock monitor 0x00007f8d (object 0x...2f18, java.lang.Object),
  which is held by "T1"
  T2 stack trace:
  at DeadlockDemo.lambda$main$1(DeadlockDemo.java:30)   ← 卡在 synchronized(A)
  - waiting to lock <0x...2f18>
  - locked <0x...2f28>                                  ← 已持有 B

Found 1 deadlock.
```

### 2.3 三分钟定位流程

```text
① jstack 拿转储 → 搜 "deadlock"（jstack 已自动完成找环）
② 读两个线程的 "locked <地址>" 与 "waiting to lock <地址>"：
   同一地址出现在"T1 的 locked"和"T2 的 waiting" → 环的边
③ 对照源码行号（DeadlockDemo.java:22/30）→ 找到两把锁的获取点
④ 修复：按 5 节规范（锁序/合并锁/tryLock）
```

> ⚠️ **陷阱**：jstack 只在**触发时**抓到现场；瞬时死锁（偶发）可配合 `-XX:+PrintConcurrentLocks`、JFR 线程采样，或用 `jcmd <pid> Thread.dump_to_file -format=json` 定时采样对比。

## 3. MySQL 死锁现场解读

### 3.1 拿现场：SHOW ENGINE INNODB STATUS

```sql
SHOW ENGINE INNODB STATUS\G
-- 死锁段在 "LATEST DETECTED DEADLOCK" 节（检测关闭时为空！）
```

```text
------------------------
LATEST DETECTED DEADLOCK
------------------------
*** (1) TRANSACTION:
TRANSACTION 244021, ACTIVE 0 sec, thread declared inside InnoDB
mysql tables in use 1, locked 1
LOCK WAIT 1 lock struct(s), heap size 1136, 1 row lock(s)
MySQL thread id 8356, OS thread handle 13986, query id 3821 ...
UPDATE t SET v=1 WHERE id=1            ← 事务 1 正在执行的语句

*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS space id 7 page no 4 n bits 72 index PRIMARY of table `test`.`t`
Record lock, heap no 5 PHYSICAL RECORD: ...
*** (2) TRANSACTION:
TRANSACTION 244022, ACTIVE 0 sec ...
UPDATE t SET v=1 WHERE id=2
*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index PRIMARY of table `test`.`t`
*** (2) ROLLING BACK TRANSACTION (2)     ← 受害者：事务 2 被回滚
```

### 3.2 五要素速读法

| 要素 | 在日志哪里 | 意义 |
|------|-----------|------|
| 事务 ID | `TRANSACTION 244021` | 关联慢日志/监控 |
| 执行语句 | `UPDATE ...` | 冲突点 |
| 等待的锁 | `WAITING FOR THIS LOCK` 段的 RECORD LOCKS | 哪一行、哪个索引 |
| 锁持有 | 对方事务的语句与锁 | 环的另一边 |
| 受害者 | `ROLLING BACK TRANSACTION (2)` | 谁被回滚（= 应用要重试的） |

### 3.3 线上排查决策树

```text
收到死锁告警（错误日志 / innodb_print_all_deadlocks / 应用 40001 计数）
│
├─ 死锁偶发（< 阈值）？
│   └─ 应用重试闭环已就位 → 观察，无需处理（2PL 的固有成本）
├─ 死锁高频？
│   ├─ 两条 SQL 是否顺序相反（UPDATE id=1→2 vs id=2→1）？
│   │   └─ 是 → 统一 ORDER BY 主键（解决 ~95% 问题）
│   ├─ 是否存在范围锁冲突（间隙锁）？
│   │   └─ 是 → 缩短事务 / 调整隔离级别 / 改唯一索引
│   └─ 是否热行高并发？
│       └─ 是 → 拆分热点 / SKIP LOCKED / 队列化
└─ 全部无果 → 开 innodb_print_all_deadlocks 拿全量现场再分析
```

## 4. 应用层重试模式

### 4.1 MySQL 40001 重试（标准模板）

```java
// 死锁 = 可重试错误（对方已回滚，重试大概率成功）
@RetryableDeadlock
public void transfer(int fromId, int toId, int amount) {
    for (int attempt = 0; attempt < 3; attempt++) {
        try (Connection conn = dataSource.getConnection()) {
            conn.setAutoCommit(false);
            // 锁序：SELECT ... WHERE id IN (...) ORDER BY id FOR UPDATE
            lockRows(conn, List.of(fromId, toId));
            executeUpdate(conn, "UPDATE account SET balance=balance-? WHERE id=?", amount, fromId);
            executeUpdate(conn, "UPDATE account SET balance=balance+? WHERE id=?", amount, toId);
            conn.commit();
            return;
        } catch (SQLException e) {
            if (isDeadlock(e)) {                    // 40001 或 1205（超时）
                retryBackoff(attempt);              // 指数退避 + 随机抖动
                continue;
            }
            throw e;                                // 非死锁错误原样抛出
        }
    }
    throw new RetryExhaustedException("转账重试 3 次仍失败");
}
```

| 错误码 | 含义 | 处理 |
|:---:|------|------|
| 40001 (ER_LOCK_DEADLOCK) | 死锁被检测并回滚 | 重试整个事务（含前置 SELECT） |
| 1205 (ER_LOCK_WAIT_TIMEOUT) | 锁等待超时 | 判断是否需要重试（可能仍持有锁，退避更久） |

> ⚠️ **重试纪律**：重试必须**重放整个事务**（不能只重放失败的语句——前置查询结果可能已过期）；必须退避（否则并发重试形成活锁）；必须限次（否则雪崩）。

### 4.2 Java 锁的确定性修复（非重试类）

```java
// 三选一：
// 方案 A：全局锁序（首选）
public void transfer(Account a, Account b, int amount) {
    Account first = a.id < b.id ? a : b;    // 按 id 排序
    Account second = a.id < b.id ? b : a;
    synchronized (first) { synchronized (second) { ... } }
}
// 方案 B：tryLock 超时 + 回退
// 方案 C：并发度上限（Semaphore）—— 从概率上压制竞争
```

## 5. 预防规范：锁序 + 超时 + 退避

### 5.1 团队级三件套规范

```text
规范一：全局锁序
  - 多锁获取一律按固定顺序（对象 id / 字典序 / 主键序）
  - 加锁入口收敛到统一工具类（LockOrder.enter(lockA, lockB)），禁止裸锁
  - 代码评审检查"两条路径的加锁顺序是否相反"

规范二：超时兜底
  - 所有可能阻塞的锁获取带超时（tryLock(timeout) / 数据库锁等待阈值）
  - 分布式锁必须带 TTL + 续期 + 唯一标识

规范三：退避防活锁
  - 重试/回退一律加随机抖动（ThreadLocalRandom.nextLong）
  - 禁止"无退避忙等 + 同步释放"的冲突重试模式
```

### 5.2 数据库侧预防规范

| 规范 | 说明 |
|------|------|
| 多行更新统一排序 | `UPDATE ... WHERE id IN (...) ORDER BY id`（或先 SELECT 排序再加锁） |
| 事务短小 | 不加锁做 RPC/IO；批量提交（每 ~50 行） |
| 队列消费 | `FOR UPDATE SKIP LOCKED`（让等待消失） |
| 索引设计 | 让加锁走索引而非全表扫描（全表扫描 = 大范围锁 = 死锁放大器） |
| 隔离级别 | 业务允许时用 READ COMMITTED（消除部分间隙锁死锁） |

## 6. 监控指标与告警

| 指标 | 来源 | 告警阈值建议 |
|------|------|-------------|
| 死锁计数（应用侧 40001） | 应用日志/指标 | > 0 即告警（死锁不该是常态） |
| `Innodb_row_lock_current_waits` | `SHOW GLOBAL STATUS` | 突增告警 |
| 锁等待时延（LOCK WAIT 事件） | performance_schema / INNODB_METRICS | P99 超基线告警 |
| 线程 BLOCKED 计数（Java） | JMX `getThreadCount`+状态 | 持续 > 0 告警 |
| 连接池活跃/等待 | 连接池指标 | 池耗尽告警（死锁级联的早期信号） |
| 长事务时长 | information_schema.INNODB_TRX | > 10s 告警 |

```text
监控哲学：死锁数本身是"果"，锁竞争是"因"。
只看死锁数 → 检测关了你就瞎了（06 章 3.2 的 LATEST DETECTED DEADLOCK 为空陷阱）
看锁等待与连接池 → 检测关不关都看得见
```

## 7. 代码评审死锁检查清单

```text
□ 1. 是否存在两个方向相反的加锁路径？（最优先）
□ 2. 锁是否藏进方法调用链深处（嵌套锁）？
□ 3. 是否有"持锁等待"（持锁期间调用可能阻塞的方法）？
□ 4. 分布式锁是否带 TTL/续期/唯一标识？
□ 5. 数据库多行更新是否排序？事务是否包含非 DB 操作？
□ 6. 重试逻辑是否带退避与限次？（防活锁与雪崩）
□ 7. 是否用包装类/缓存对象做锁？（JEP 390 警告类）
□ 8. 锁粒度是否过大？（全表锁 vs 行锁）
□ 9. 新增并发代码是否配套了监控指标？
□ 10. 静态检查：SpotBugs 的 DM_MONITOR_SYNCHRONIZED、MySQL 死锁测试用例
```

> 🎯 **核心要点**：死锁预防是**组织行为**而非个人技巧——统一锁序工具类、评审清单、监控告警三者缺一不可。单靠"程序员小心"必然在某个版本引入反向加锁。

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 定位：jstack 自动找环 + ThreadMXBean 程序化检测 + MySQL `LATEST DETECTED DEADLOCK` 五要素速读，三分钟可定位；
> 2. 修复：40001 重试要"重放整个事务 + 退避 + 限次"；确定性修复是全局锁序（解决 95% 场景）；
> 3. 预防：锁序 + 超时 + 退避三件套，靠工具类收敛、评审清单、监控告警落地为组织规范。

**思考题**：

1. `findDeadlockedThreads()` 与 `findMonitorDeadlockedThreads()` 的区别？（→ 1）
2. jstack 抓到"waiting to lock"地址怎么确认成环？（→ 2.3：同一地址出现在对方 locked 中）
3. 死锁重试为什么必须重放整个事务？（→ 4.1 重试纪律）
4. 为什么监控"锁等待"比监控"死锁数"更可靠？（→ 6）
