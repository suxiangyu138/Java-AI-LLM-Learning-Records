# 死锁避免：银行家算法

> 预防是在"结构上"让死锁不可能发生；避免是在"运行时"动态判断每一次分配是否安全——银行家算法就是最著名的动态避免算法。它因"需要提前知道每个进程的最大需求"在生产中几乎不可用，但至今是操作系统的必考算法

## 1. 避免 vs 预防：动态安全性的思想

```text
预防（Prevention，03 章）：静态规则 → 死锁"结构上不可能"
   例：全局锁序 —— 不管运行时怎么走，环都不存在

避免（Avoidance，本章）：动态检查 → 死锁"运行时不发生"
   例：银行家算法 —— 每次分配前模拟"将来能否全部完成"
   若分配后系统可能进入死锁（不安全状态）→ 拒绝这次分配
```

**银行家算法的思想来源**：银行家发放贷款时，只有确信"即使所有客户同时要求最大额度，银行也能逐一满足"才放贷——系统分配资源同理。

## 2. 安全状态与安全序列

### 2.1 定义

> **安全状态（safe state）**：系统存在一个**安全序列**——按该序列逐个执行，每个进程都能依次获得其最大需求并完成（完成后释放资源供后续进程使用），最终所有进程完成。

### 2.2 关键性质

| 性质 | 说明 |
|------|------|
| 安全状态 ⇒ 无死锁 | 存在完成顺序，死锁不可能出现 |
| 不安全状态 ⇏ 死锁 | 只是"有可能死锁"，未必真的发生 |
| 避免的策略 | 只允许系统进入安全状态（拒绝会导致不安全的分配） |

```text
逻辑关系（集合包含）：
安全状态 ⊂ 无死锁状态；死锁状态 ⊂ 不安全状态
```

## 3. 银行家算法的四张表

假设 n 个进程、m 类资源：

| 矩阵 | 含义 | 记法 |
|------|------|------|
| `Available[m]` | 每类资源的**剩余可用数** | 全局向量 |
| `Max[n][m]` | 每个进程的**最大需求**（事先声明） | 只读输入 |
| `Allocation[n][m]` | 每个进程**当前已分配**数 | 动态更新 |
| `Need[n][m]` | 每个进程**还需要的**数 | `Need = Max − Allocation` |

```text
不变量：对任意进程 i、资源 j：
  Need[i][j] = Max[i][j] − Allocation[i][j] ≥ 0
  Allocation[i][j] ≤ Max[i][j]
```

## 4. 安全性检查算法

输入四张表，输出"是否安全 + 安全序列"：

```text
Step 1 初始化：Work = Available；Finish[i] = false（i = 1..n）
Step 2 找一个进程 i：Finish[i] == false 且 Need[i] ≤ Work
Step 3 若找到：Finish[i] = true；
           Work = Work + Allocation[i]（该进程完成，归还资源）
           回到 Step 2
      若找不到：
          所有 Finish[i] == true  → 系统安全，序列即记录顺序
          存在 Finish[i] == false → 系统不安全
```

```java
// 伪代码实现
boolean isSafe(int[][] need, int[][] alloc, int[] available) {
    int n = need.length, m = available.length;
    int[] work = available.clone();
    boolean[] finish = new boolean[n];
    List<Integer> seq = new ArrayList<>();

    for (int done = 0; done < n; done++) {          // 最多 n 轮
        boolean found = false;
        for (int i = 0; i < n; i++) {
            if (!finish[i] && needLe(need[i], work)) {
                for (int j = 0; j < m; j++) work[j] += alloc[i][j];
                finish[i] = true;
                seq.add(i);
                found = true;
                break;
            }
        }
        if (!found) return false;                   // 这轮无人可完成 → 不安全
    }
    return true;                                    // 全部完成 → 安全
}
```

## 5. 资源请求算法

进程 i 请求资源向量 `Request[i]` 时：

```text
Step 1 合法性：Request[i] ≤ Need[i]？
         否 → 报错（请求超过声明需求，非法）
Step 2 可行性：Request[i] ≤ Available？
         否 → 让进程等待（当前资源不足）
Step 3 试探分配（假想）：
     Available' = Available − Request[i]
     Allocation'[i] = Allocation[i] + Request[i]
     Need'[i] = Need[i] − Request[i]
Step 4 安全性检查：对试探后的状态跑第 4 节算法
         安全 → 正式分配（状态提交）
         不安全 → 撤销试探，进程等待（拒绝本次请求）
```

> 🎯 **核心要点**：银行家算法的灵魂是 **"先假想、后验证、再提交"**——分配前先问"给了你，大家将来还完得成吗？"答不出"能"，就不给。

## 6. 手算推演：完整例题

### 6.1 初始状态（经典 5 进程 3 资源，A=10 B=5 C=7）

| 进程 | Allocation | Max | Need(=Max−Alloc) |
|------|:---:|:---:|:---:|
| P0 | 0 1 0 | 7 5 3 | **7 4 3** |
| P1 | 2 0 0 | 3 2 2 | **1 2 2** |
| P2 | 3 0 2 | 9 0 2 | **6 0 0** |
| P3 | 2 1 1 | 2 2 2 | **0 1 1** |
| P4 | 0 0 2 | 4 3 3 | **4 3 1** |

```text
Available = (10,5,7) − 各行 Allocation 之和(7,2,5) = (3,3,2)
```

### 6.2 安全性检查（判断当前状态）

```text
Work = (3,3,2)
轮1：P1(1,2,2) ≤ (3,3,2) ✅ → Work = (3,3,2)+(2,0,0) = (5,3,2)
轮2：P3(0,1,1) ≤ (5,3,2) ✅ → Work = (5,3,2)+(2,1,1) = (7,4,3)
轮3：P4(4,3,1) ≤ (7,4,3) ✅ → Work = (7,4,3)+(0,0,2) = (7,4,5)
轮4：P0(7,4,3) ≤ (7,4,5) ✅ → Work = (7,4,5)+(0,1,0) = (7,5,5)
轮5：P2(6,0,0) ≤ (7,5,5) ✅ → Work = (7,5,5)+(3,0,2) = (10,5,7)

安全序列：P1 → P3 → P4 → P0 → P2 → 系统处于安全状态 ✅
```

### 6.3 请求处理：P1 请求 (1,0,2)

```text
① Request(1,0,2) ≤ Need₁(1,2,2) ✅
② Request(1,0,2) ≤ Available(3,3,2) ✅
③ 试探分配：
   Available = (2,3,0)
   Allocation₁ = (3,0,2)    Need₁ = (0,2,0)
④ 安全性检查（新状态）：
   Work = (2,3,0)
   轮1：P1(0,2,0) ≤ (2,3,0) ✅ → Work = (5,3,2)
   轮2：P3(0,1,1) ≤ (5,3,2) ✅ → Work = (7,4,3)
   轮3：P4(4,3,1) ≤ (7,4,3) ✅ → Work = (7,4,5)
   轮4：P0(7,4,3) ≤ (7,4,5) ✅ → Work = (7,5,5)
   轮5：P2(6,0,0) ≤ (7,5,5) ✅ → Work = (10,5,7)
   安全 ✅ → 批准 P1 的请求
```

### 6.4 反例：P0 请求 (0,2,0)

```text
① Request(0,2,0) ≤ Need₀(7,4,3) ✅
② Request(0,2,0) ≤ Available(3,3,2) ✅
③ 试探：Available = (3,1,2)；Allocation₀ = (0,3,0)；Need₀ = (7,2,3)
④ 安全检查：
   Work = (3,1,2)
   轮1：P1(1,2,2) ≤ (3,1,2)？❌ → 无人可完成 → 不安全！
   → 拒绝 P0 的请求（P0 等待）
```

> 💡 **面试手算要点**：做题三步——① 算 Need；② 算 Available；③ 贪心找序列（每轮找"Need ≤ Work"的进程，找到就分配其 Allocation 给 Work）。若某轮找不到 → 不安全。

## 7. 安全状态/不安全状态/死锁状态的关系

```text
                     全部状态
              ┌───────────────────────┐
              │   不安全状态（含死锁）   │
              │   ┌───────────────┐   │
              │   │ 死锁状态       │   │
              │   │   （成环）     │   │
              │   └───────────────┘   │
              └───────────────────────┘
  安全状态 ⊂ 非死锁状态
  死锁状态 ⊂ 不安全状态（死锁必不安全；不安全未必死锁）

  银行家算法的作用：把系统"钉在"安全状态内
  → 死锁在运行期永远不被允许进入
```

## 8. 优缺点与生产现实

| 优点 | 缺点 |
|------|------|
| 资源利用率高于预防策略 | 需要**提前声明每个进程的最大需求**——现实中不可行 |
| 运行期动态判断，不过度限制 | 进程数量/资源类变动时需重新建模 |
| 理论完备（安全性判定可证明） | O(n²m) 复杂度在进程多时开销可观 |
| — | 进程的 Max 需求是"最坏估计"，导致资源闲置（利用率反而不高） |

### 生产现实

```text
操作系统：没有主流 OS 用银行家算法做通用资源分配
数据库：InnoDB 不用它（用 WFG 检测，05/06 章）
现实选择：
  单机 → 锁序预防（零开销）
  数据库 → 检测 + 回滚（InnoDB 的做法）
  分布式 → 超时 + 重试（无法全局建模）
银行家算法的价值：教科书必考 + 面试必问 + 理解"安全状态"思想
```

> 🎯 **核心要点**：银行家算法回答"为什么死锁避免在生产中不流行"——它需要一个现实中拿不到的信息（每个进程的最大需求），因此**它作为思想（安全性预判）比作为算法（实际调度）更值钱**。面试答此题要同时给出"算法流程"与"不实用的原因"两个层次。

## 9. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 银行家算法 = 分配前"假想分配 + 安全性检查"（Need ≤ Work 贪心推进），不安全就拒绝；
> 2. 安全状态 ⇒ 无死锁；不安全状态 ⇏ 死锁——算法只保证"不进入不安全状态"；
> 3. 生产不用它的根本原因：需要预先声明最大需求；现实用"锁序预防 + WFG 检测 + 超时"。

**思考题**：

1. 安全状态为什么一定无死锁？（→ 2.1 安全序列定义）
2. 算法为什么先检查 `Request ≤ Need`？（→ 5 合法性）
3. P0 请求 (0,2,0) 被拒后会发生什么？（→ 6.4：P0 阻塞等待，系统保持安全）
4. 若两个进程的 Max 都未知，算法还能工作吗？（→ 8 生产现实）
