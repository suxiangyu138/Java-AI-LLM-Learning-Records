## 1. 2PL：数据库并发控制与死锁的来源

### 1.1 两阶段锁协议（2PL）

保证可串行化的标准协议——事务分两个阶段：

```text
增长阶段（growing）：只能加锁，不能释放
收缩阶段（shrinking）：只能释放，不能加锁

变体：
  Strict 2PL：排他锁持有到事务提交/回滚 —— 避免级联回滚（InnoDB 的默认行为）
  Rigorous 2PL：所有锁持有到提交 —— 更强
  Conservative（静态）2PL：执行前一次性锁全部 —— 不等待，因此无死锁
```

### 1.2 2PL 与死锁

```text
2PL 保证可串行化，但不防止死锁：
  T1: lock(A) → wait lock(B)
  T2: lock(B) → wait lock(A)   → 环

多行更新顺序不一致 = 最常见的 2PL 死锁来源：
  T1: UPDATE t SET ... WHERE id=1 → UPDATE t SET ... WHERE id=2
  T2: UPDATE t SET ... WHERE id=2 → UPDATE t SET ... WHERE id=1   → 死锁
```

> 🎯 **核心要点**：死锁是 2PL 的**结构性代价**——要串行化就要锁，要锁就可能成环。所以数据库领域从不幻想"无锁"，只研究"检测快不快、回滚贵不贵、怎么降低发生概率"。

## 2. InnoDB 死锁检测机制

### 2.1 检测流程（官方文档 17.7.5.2）

```text
触发时机：事务请求的行锁/表锁无法立即授予时
步骤：
  ① 维护等待图（wait-for graph）：节点=事务，边=等待关系
  ② 新等待边加入时，检查是否成环（死锁检测器 DeadlockChecker::check_and_resolve）
  ③ 成环 → 回滚"最小"事务（insert/update/delete 行数最少者）
  ④ 被回滚事务返回 ERROR 1213 (40001)：Deadlock found when trying to get lock
检测粒度：毫秒级完成，不是定时任务——是"锁等待瞬间"的即时检查
```

### 2.2 检测上限（防检测自身成为瓶颈）

| 阈值 | 行为 |
|------|------|
| wait-for 列表超过 **200 个事务** | 直接判定死锁并回滚"发起检查的事务" |
| 检查超过 **1,000,000 个锁** | 同上 |

```text
触发时报错（SHOW ENGINE INNODB STATUS 可见）：
  "TOO DEEP OR LONG SEARCH IN THE LOCK TABLE WAITS-FOR GRAPH,
   WE WILL ROLL BACK FOLLOWING TRANSACTION."
意义：等待图遍历本身有 CPU 成本——高并发热点行上，
      每次锁等待都触发全图遍历可能成为新瓶颈（见 3.2）
```

### 2.3 检测不到的死锁：超时兜底

| 场景 | 说明 |
|------|------|
| `innodb_deadlock_detect=OFF` | 检测关闭，全靠超时 |
| `LOCK TABLES` 表锁 | 表锁不参与 InnoDB WFG |
| 其他存储引擎的锁 | WFG 只覆盖 InnoDB 锁 |

> ⚠️ 这些场景由 **`innodb_lock_wait_timeout`（默认 50 秒）** 兜底：等待超时 → 回滚**当前语句**（除非开 `innodb_rollback_on_timeout` 才回滚整个事务）。

## 3. InnoDB 参数与 2026 生产实践

### 3.1 参数全景表

| 参数 | 默认 | 作用 | 生产建议 |
|------|:---:|------|---------|
| `innodb_deadlock_detect` | ON | 死锁检测总开关（动态，8.0.22+ 可 SET GLOBAL） | 默认开；仅在检测成为瓶颈且压测验证后关闭 |
| `innodb_lock_wait_timeout` | 50s | 锁等待超时（检测失效时的兜底） | 高并发写压到 **5-10s**（OLTP 可 1-2s） |
| `innodb_rollback_on_timeout` | OFF | 超时后回滚当前语句 vs 整个事务 | **建议 ON**（防语句级回滚留下部分一致性问题） |
| `innodb_print_all_deadlocks` | OFF | 每次死锁都写错误日志（不只最新一次） | 排查期开，平时开也行（量小） |

### 3.2 innodb_deadlock_detect=OFF 的权衡（高危操作）

```text
动机：热点行高并发下，每次锁等待的全图遍历成为 CPU 瓶颈
      （官方手册明确：众多线程等待同一锁时检测"can cause a slowdown"）
收益：锁等待路径的 CPU 开销下降
风险：
  ① 死锁不再即时解除 → 事务持锁等到 50s 超时 → 连接池耗尽 → 级联雪崩
  ② SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 永远为空
     —— 不是没死锁，是检测被绕过了（排查陷阱！）
  ③ 真死锁频繁时系统直接卡死
结论：仅在"压测证明检测是瓶颈 + 应用已实现 40001 重试"后谨慎使用；
     2026 年实践共识：检测本身极少导致故障，真正危险的是失控的锁竞争
```

### 3.3 2026 最佳实践清单

| 实践 | 说明 |
|------|------|
| **锁序一致** | ~95% 死锁源于多表更新顺序不一致 → `SELECT ... FOR UPDATE` 统一 `ORDER BY 主键` |
| 事务短小 | 不把 RPC/文件 I/O 放进事务；批量写 `INSERT ... ON DUPLICATE KEY UPDATE` |
| 队列消费 | `SELECT ... FOR UPDATE SKIP LOCKED` 分发任务（锁竞争直接消失） |
| 监控重点 | 看 **LOCK WAIT 计数与时延**（`INNODB_METRICS`/status）而不是只看死锁数——死锁是果，锁竞争是因 |
| 重试闭环 | 应用捕获 40001 后重试整个事务（含前置查询，保证可重复） |
| 错误日志 | 排查期开 `innodb_print_all_deadlocks`，拿全量死锁现场 |

## 4. 分布式死锁为什么难

### 4.1 与单机的本质差异

```text
单机数据库：锁管理器拥有全局等待图 → 检测 = 本地图遍历（简单）
分布式系统：
  ① 无全局视图 —— 资源跨节点/跨服务/跨队列/跨缓存
  ② 通信延迟 —— 等待信息本身可能迟到（误判/漏判）
  ③ 无天然"图所有者" —— 没人拥有完整依赖图
  ④ 每部分看起来都健康 —— 服务 A 等 B，B 等 C，C 等 A，
     每个节点自身无异常，整体卡死（可观测性盲区）
```

### 4.2 分布式死锁的典型场景

```text
场景一：跨库事务（XA）
  事务 T1：DB1 锁行 A → 等 DB2 的行 B
  事务 T2：DB2 锁行 B → 等 DB1 的行 A
  → 两个数据库各自无环，全局成环

场景二：微服务调用链 + 分布式锁
  服务 A：lock(订单) → 调 B 服务（B 内部 lock(库存) → 等 C...）
  服务 C：lock(库存)... → 等 lock(订单) → 跨服务环

场景三：消息队列 + 幂等锁
  消费方 A 持锁处理消息 m1，等 m2；消费方 B 持锁处理 m2，等 m1
```

## 5. 分布式 WFG 检测：三种架构

### 5.1 架构对比

| 架构 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **集中式** | 收集器服务汇总各节点的等待边，统一查环 | 实现简单、全局视图 | 单点故障、数据可能过期 |
| **分层式** | 每个分片本地检测 + "摘要边"跨片升级 | 带宽可控、局部快速 | 分层协议复杂 |
| **全分布式** | 消息传递探测算法（无中心） | 无单点、隐私友好 | 网络开销、实现难 |

### 5.2 CMH 探测算法（Chandy–Misra–Haas，全分布式代表）

```text
思想：边沿追逐（edge chasing）
步骤：
  ① 事务 Ti 阻塞时，沿等待链向下游发送 probe 消息
     probe = (initiator, Ti, Tj)：标识"Ti 发起的探测，当前在 Tj 处"
  ② 每个收到 probe 的阻塞事务继续转发
  ③ 若 probe 回到 initiator → 存在环 → 死锁确认，回滚发起者或最小者
优点：近实时、可扩展、无需中心
代价：需要可靠消息传递；网络流量随等待链长度增长
改进：时间戳剪枝（只转发"边时间戳晚于 cutoff"的 probe，减少流量）
```

### 5.3 工程化的分布式检测（2026 实践共识）

```text
实际生产几乎不追求"完美全局图"，而是组合：
  ① 本地快速检测：每个节点自己的 WFG（InnoDB/Redis 各自管自己）
  ② 跨节点靠超时/租约：等待超过阈值即放弃（最普遍）
  ③ 边缘分析：监控系统对"互相等待的调用链"做静态关联分析
  ④ 可观测性：全链路 trace + 等待关系采集 → 事后分析环
```

## 6. 分布式预防：wait-die、wound-wait 与租约

### 6.1 时间戳预防协议（消除环的结构手段）

```text
给每个事务分配时间戳 TS（老事务 TS 小）
规则只允许等待边"从年轻指向年长"（或反之）→ 方向一致 → 不可能成环

wait-die（等待-死亡）：
  老事务等年轻事务 → 等待（die 的意思是年轻事务会死）
  年轻事务等老事务 → 直接 abort（die）后重试
  → 特点：只回滚年轻事务；无回滚传播；但年轻事务可能反复死（饥饿风险）

wound-wait（伤害-等待）：
  老事务等年轻事务 → 老事务"伤害"年轻者：夺资源并让年轻者回滚
  年轻事务等老事务 → 等待
  → 特点：回滚传播（被伤害者可能已做大量工作）；但老事务优先，无饥饿
```

| 协议 | 老等少 | 少等老 | 回滚方向 | 饥饿 |
|------|:---:|:---:|:---:|:---:|
| wait-die | 等待 | 自己回滚 | 只回滚年轻者 | 年轻者可能饿 |
| wound-wait | 伤害年轻者 | 等待 | 可回滚年老者**所伤害的年轻者** | 无 |

> 💡 **本质**：wait-die/wound-wait 是"时间戳版的全局锁序"——用时间戳定义顺序，等待边只朝一个方向。这与 03 章"资源编号锁序"是同一个数学思想，只是应用在事务层。

### 6.2 工程级预防手段

| 手段 | 做法 | 对应破坏的条件 |
|------|------|:---:|
| 跨服务锁序 | 分布式锁按 key 字典序获取 | 循环等待 |
| NOWAIT / SKIP LOCKED | 冲突立即放弃（PostgreSQL NOWAIT、MySQL SKIP LOCKED） | 持有并等待 |
| 锁租约（lease） | 锁带 TTL，超时自动失效 | 不可剥夺 |
| 幂等重试 | 冲突后重试整个操作 | （兜底，非预防） |
| **Saga 模式** | 长事务拆为本地事务 + 补偿；**不跨服务持锁** | 持有并等待（根治） |

```text
Saga 为何是分布式死锁的"根治方案"：
  死锁需要"跨节点持有+等待"——Saga 让每个服务只管自己的本地事务
  提交后释放锁，后续步骤失败用补偿（undo）而非等待
  → 跨服务的"持锁等待"结构被消灭 → 分布式死锁失去土壤
代价：最终一致性（补偿期间数据短暂不一致）、补偿逻辑复杂
```

## 7. 误判防护与受害者选择

### 7.1 分布式检测的误判防护（2026 实践）

| 手段 | 说明 |
|------|------|
| 边老化（edge aging） | 等待边存在 **200ms~2s** 以上才判定死锁（容忍瞬时等待） |
| 连续确认 | 环跨多次检查仍存在才解除（防瞬时环） |
| TTL 边过期 | 等待边有 TTL，超时自动删除（防陈旧数据误判） |
| 稳定操作 ID | 重试携带同一操作 ID，防止重试被误判为新死锁 |
| 向量时钟 | 跨节点一致性快照（理论手段，工程较少用） |

### 7.2 受害者选择

| 标准 | 说明 |
|------|------|
| 最年轻/最小事务 | 已做工作最少 |
| 修改行数最少（InnoDB） | 回滚代价最小 |
| 优先级最低 | 业务权重 |
| 回滚次数保护 | 被回滚多次的事务不再优先牺牲（防饥饿） |

## 9. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. InnoDB = 生产级 WFG 检测范本：等待时触发、回滚最小事务、返回 40001 供重试；200 事务/100 万锁是检测自身的安全阀；
> 2. 分布式死锁难在"没有全局图"——检测靠集中/分层/CMH 探测，生产普遍用超时+租约兜底；
> 3. 分布式的最优解是**预防**：时间戳协议（wait-die/wound-wait）是"时间戳版全局锁序"，Saga 则从结构上消灭跨服务持锁。
