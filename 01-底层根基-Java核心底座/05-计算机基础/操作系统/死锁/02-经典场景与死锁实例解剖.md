## 1. 哲学家就餐问题

### 1.1 问题设定（Dijkstra，1965）

```text
5 个哲学家围圆桌而坐，每人左手边一支筷子（共 5 支）
思考 → 饿了 → 拿起左手筷子 → 拿起右手筷子 → 吃面 → 放下两支筷子 → 思考
约束：筷子是互斥资源，一次只能被一个哲学家使用
```

### 1.2 死锁演示

```java
// 直观版：每个哲学家"先拿左手再拿右手"
void eat(int i) {
    lock(chopstick[i]);               // 左手
    lock(chopstick[(i + 1) % 5]);     // 右手
    eatNoodles();
    unlock(chopstick[(i + 1) % 5]);
    unlock(chopstick[i]);
}
// 5 个哲学家同时拿起左手筷子 → 每人等右手 → 右手都是别人的左手 → 死锁
```

四条件对照：筷子互斥 ✅ 持有左手等右手 ✅ 筷子不可剥夺 ✅ 五人循环等待 ✅

### 1.3 三种经典解法

| 解法 | 思想 | 破坏的条件 | 代价 |
|------|------|:---:|------|
| 最多 4 人同时上桌 | 限制并发 | 循环等待 | 引入信号量 `eating = 4` |
| 先拿编号小的筷子 | 全局锁序 | 循环等待 | 语义不自然（先右手再左手） |
| 一次性拿两支（拿不到就放） | 预分配 + 回退 | 持有并等待 | 可能饥饿 |

```java
// 解法二（全局锁序）的实现
void eat(int i) {
    int first = Math.min(i, (i + 1) % 5);
    int second = Math.max(i, (i + 1) % 5);
    lock(chopstick[first]);            // 永远先拿编号小的
    lock(chopstick[second]);
    ...
}
```

> 🎯 **核心要点**：哲学家就餐是"循环等待"的完美教学模型——它的三种解法正好对应 03 章的三种预防手段。面试问"哲学家就餐怎么防死锁"，答全三种解法即可封顶。

## 2. 转账 ABBA：锁顺序反转

### 2.1 问题设定

```java
// ❌ 危险版本：按"转账方向"加锁——两个方向同时转账必死锁
public void transfer(Account from, Account to, int amount) {
    synchronized (from) {                    // T1: lock(A)
        synchronized (to) {                  //     lock(B)
            from.debit(amount);
            to.credit(amount);
        }
    }
}
// T1: transfer(A, B)  → 持 A 等 B
// T2: transfer(B, A)  → 持 B 等 A   → 死锁
```

### 2.2 两个事实性坑

```text
坑一：单线程内不会死锁，但并发下"方向相反"的调用必然成环
坑二：即使方向相同，也可能死锁：
     T1: transfer(A, B)；T2: transfer(B, C)；T3: transfer(C, A) —— 三角环！
```

### 2.3 标准修复：按标识排序

```java
// ✅ 修复：对账户 ID 排序，永远先锁小 ID
public void transfer(Account a, Account b, int amount) {
    Account first = a.id < b.id ? a : b;
    Account second = a.id < b.id ? b : a;
    synchronized (first) {
        synchronized (second) {
            a.debit(amount);
            b.credit(amount);
        }
    }
}
// 任意方向转账都按 (min, max) 顺序加锁 → 等待关系永不反向 → 无环
```

> 💡 **教训提炼**：ABBA 是生产环境最高频死锁（约占数据库死锁的 95%，见 06 章）。凡是"两把及以上锁"的场景，第一步就是**定义全局顺序**。

## 3. 嵌套锁与反向加锁

### 3.1 嵌套锁（nested locks）

```java
// 同一线程重复获取同一把锁 → 可重入（synchronized/ReentrantLock 都支持）→ 不死锁
synchronized (lock) {
    synchronized (lock) { ... }     // 可重入：计数 +1，不死锁
}
// 不同线程持不同锁再交叉等 → 死锁（本质同 ABBA，只是锁藏在方法调用链里）

// 隐藏版本：锁 A 的方法内部调用需要锁 B 的方法，另一条路径反向调用 → 死锁
void m1() { synchronized (A) { helper(); } }    // helper 内 synchronized(B)
void m2() { synchronized (B) { helper(); } }    // 反向 → 死锁
// 这种"锁藏在调用链深处"的死锁最难排查（jstack 也难一眼看出）
```

### 3.2 类锁与实例锁的"混合锁序"陷阱

```java
// 类锁（static synchronized）与实例锁（synchronized）是两把不同的锁
// 若代码既锁类又锁实例，且两条路径顺序相反 → 死锁
```

## 4. Java 多线程死锁实例

### 4.1 完整可运行实例

```java
import java.util.concurrent.CountDownLatch;

public class DeadlockDemo {
    static final Object RESOURCE_A = new Object();
    static final Object RESOURCE_B = new Object();

    public static void main(String[] args) throws InterruptedException {
        CountDownLatch latch = new CountDownLatch(2);

        Thread t1 = new Thread(() -> {
            synchronized (RESOURCE_A) {
                System.out.println("T1: locked A, waiting B...");
                sleepQuietly(100);                 // 确保交错
                synchronized (RESOURCE_B) {        // 等 B（T2 持有）
                    System.out.println("T1: got B");
                }
            }
            latch.countDown();
        }, "T1");

        Thread t2 = new Thread(() -> {
            synchronized (RESOURCE_B) {
                System.out.println("T2: locked B, waiting A...");
                sleepQuietly(100);
                synchronized (RESOURCE_A) {        // 等 A（T1 持有）
                    System.out.println("T2: got A");
                }
            }
            latch.countDown();
        }, "T2");

        t1.start(); t2.start();
        latch.await();      // 永远不会完成
    }
    static void sleepQuietly(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) {} }
}
```

### 4.2 三域对照表（同一死锁，三种技术栈）

| 域 | 资源 | 等什么 | 检测方式 |
|----|------|--------|---------|
| Java 多线程 | 对象监视器/ReentrantLock | 另一把锁 | `jstack` 自动识别 + ThreadMXBean |
| MySQL 事务 | 行锁/表锁 | 另一事务持有的行 | InnoDB WFG 检测，回滚最小事务 |
| Redis 分布式 | 锁 key | 另一节点持有的 key | **无检测**（只能靠 TTL 超时） |

## 5. MySQL 行锁死锁实例

### 5.1 经典场景：反向更新

```sql
-- 事务 T1                       事务 T2
BEGIN;                           BEGIN;
UPDATE t SET v=1 WHERE id=1;     UPDATE t SET v=1 WHERE id=2;
UPDATE t SET v=2 WHERE id=2;     UPDATE t SET v=2 WHERE id=1;   -- 死锁！
COMMIT;                          COMMIT;
-- InnoDB 检测到环 → 回滚 T2（修改行数少的一方）→ 返回 ERROR 1213
```

### 5.2 更隐蔽的场景：先查后改的间隙锁死锁

```sql
-- 两个事务都"先 SELECT 后 UPDATE 同一范围"，RR 隔离级别下间隙锁交错
-- 事务 A：SELECT ... WHERE status='P' FOR UPDATE（锁住范围与间隙）
-- 事务 B：INSERT 新行（需要间隙锁）→ 与 A 的间隙锁互斥 → 等 A
-- 事务 A：INSERT 新行（需要间隙锁）→ 与 B 互斥 → 环
```

### 5.3 MySQL 侧处置三板斧

| 手段 | 内容 |
|------|------|
| 靠检测 | InnoDB WFG 自动回滚最小事务（06 章详述） |
| 靠规范 | 多行更新统一 `ORDER BY 主键`；长事务拆短 |
| 靠重试 | 应用捕获 `ERROR 1213 (40001)` 后重试整个事务 |

## 6. Redis 分布式锁死锁实例

### 6.1 场景：无 TTL 的分布式锁

```java
// ❌ 危险：锁没有过期时间（TTL）
// 节点 A 拿锁后崩溃 → 锁永远在 → 所有其他节点永久等待
// 这不是"循环等待"型死锁，而是"持有者消失"型——同样造成永久阻塞
boolean got = redis.setnx("lock:order:1001", nodeId);   // 无 EX 过期
if (got) {
    try { process(); }
    finally { redis.del("lock:order:1001"); }   // 崩溃后这行永远不执行
}
```

### 6.2 循环等待型：多把分布式锁

```java
// 节点 A：lock("order") → lock("stock")
// 节点 B：lock("stock") → lock("order")   → 跨节点 ABBA
// 与单机 ABBA 完全同构，只是锁在 Redis
```

### 6.3 修复套路

| 修复 | 说明 |
|------|------|
| 必须设 TTL | `SET key val NX EX 10`——破坏"不可剥夺"（超时兜底） |
| 全局锁序 | 多把锁按 key 字典序获取 |
| 一次性获取 | 用 Lua 脚本原子获取多把锁（预分配思想） |
| 看门狗续期 | 业务长于 TTL 时自动续期（Redisson 的 watchdog） |
| 唯一标识防误删 | 删除前校验 value 是本人（防 A 超时后 B 持锁、A 删掉 B 的锁） |

> ⚠️ **分布式与单机的关键差异**：单机死锁有 JVM/DB 帮你检测；分布式**没有全局检测者**——所以分布式侧的策略重心从"检测"转向"预防 + 超时兜底"（06 章继续展开）。

## 7. 场景规律总结

```text
所有死锁实例的共性模式：
┌─────────────────────────────────────────────┐
│  模式一：反向加锁（ABBA）                      │
│    A→B 与 B→A 两个方向并发                     │
│    实例：转账、反向 UPDATE、双 Redis 锁        │
│    修复：全局锁序（按 ID/字典序）              │
├─────────────────────────────────────────────┤
│  模式二：嵌套锁深度耦合                        │
│    锁藏在方法调用链中，两个方向调用             │
│    实例：服务 A 内部锁 + 服务 B 内部锁交叉调用   │
│    修复：锁层级规范、单锁化改造                 │
├─────────────────────────────────────────────┤
│  模式三：持有者消失（分布式特有）               │
│    持锁者崩溃/网络分区，锁不释放                │
│    实例：无 TTL 的 Redis 锁                    │
│    修复：TTL + 续期 + 唯一标识                  │
└─────────────────────────────────────────────┘
```

> 🎯 **核心要点**：死锁实例千变万化，但**修复手段永远只有三个选项**——排序（破坏环）、超时（破坏不可剥夺）、预分配（破坏持有等待）。看到任何"卡死"场景，先归类，再选手段。
