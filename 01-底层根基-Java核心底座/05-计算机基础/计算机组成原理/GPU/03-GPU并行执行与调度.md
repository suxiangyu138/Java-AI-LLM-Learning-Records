## 1. 三层并行模型

### 1.1 Grid → Block → Thread

```
Grid（网格）：一次 kernel 启动的全部线程
 ├── Block 0（线程块）→ 分配到 SM 0
 ├── Block 1 → 分配到 SM 1
 ├── ...
 └── Block N → 分配到 SM k

Block（块）：软件组织的线程组（上限 1024 线程）
 └── 32 个线程为一组 → warp（硬件执行单位）
```

| 层 | 数量级 | 归属 | 通信范围 |
|------|:---:|------|---------|
| Grid | 数百万线程 | 一次 kernel | 全局内存 + 原子 |
| Block | 数千 | 一个 SM | 共享内存（快！） |
| Warp | 每块 N/32 | 一个调度器 | 无（同执行） |

### 1.2 为什么要有 Block

```
① 块内共享内存：协作计算需要"片上快速通信"
② 块是调度单位：块大小决定负载均衡粒度
③ 块内同步原语：__syncthreads() 只同步块内线程

设计约束：块内线程数 ≤ 1024；块数越多调度越灵活
```

## 2. 线程块到 SM 的映射

### 2.1 分配规则

```
每个 SM 同时驻留多个块（受资源限制）：
  驻留块数 ≤ min(块上限 32, 寄存器够用, 共享内存够用)

负载均衡：GPU 硬件按"先到先得"分配空闲 SM
  块数 > SM 数 → 排队执行（后发的块等前批完成）

示例：16 SM、每 SM 驻留 8 块 → 同时 128 块在飞
  总块数 1024 → 分 8 批跑完
```

### 2.2 资源限制的具体算法

```
一个块需要：T 线程 × R 寄存器 + S 字节共享内存
一个 SM 提供：64K 寄存器 + 228KB 共享内存 + 最大 2048 线程

驻留块数 = min( 2048/T, 64K/(T×R), 228KB/S, 32块上限 )

例：块 256 线程 × 40 寄存器：
  2048/256 = 8 块（线程限制）
  64K/(256×40) = 6.4 → 6 块（寄存器限制，胜出！）
```

> 💡 推论：**寄存器是占用率的第一杠杆**——同样 256 线程块，寄存器 32 → 8 块驻留；寄存器 64 → 4 块。减少寄存器使用（如 `__launch_bounds__`）直接换并发度。

### 2.3 负载均衡的两种情况

| 场景 | 均衡性 | 对策 |
|------|:---:|------|
| 块内工作均匀 | 好 | 默认 |
| 块间工作不均 | 差（最长块拖慢整体） | 更多小块 / 动态工作分配（原子取任务） |

```
经典教训：固定任务分块（静态划分）在数据稀疏时失衡
  解法：线程池模式 —— 每线程循环原子取下一个任务（dynamic parallelism 简化版）
```

## 3. warp 调度与延迟隐藏

### 3.1 调度器的工作

```
每 SM 4 个 warp 调度器，每周期每个调度器发射 1 条指令（1 个 warp）
  4 调度器 × 每周期 1 warp × 32 线程 = 每周期 128 线程吞吐

就绪判定：warp 的指令不依赖未完成的结果（操作数已就绪）
访存指令发出后：warp 进入等待 → 调度器换下一个就绪 warp
```

### 3.2 延迟隐藏的数学

```
关键公式：需要多少个 warp 才能藏住延迟？
  隐藏延迟所需 warp 数 ≈ 访存延迟 / 发射间隔
  L2/HBM 延迟 ~500 周期，每 warp 发射间隔 4 周期（4 调度器分摊）
  → 需要 ~500/4 ≈ 128 个 warp 全速隐藏？（实际 64 驻留已相当好）

直觉：GPU 没有"等"，只有"换"—— 只要驻留 warp 足够多，
  任何单 warp 的等待都会被其他 warp 的工作填满
```

### 3.3 调度器选择策略

```
简单轮转（round-robin）：公平但可能发射"等操作数"的 warp
贪婪（greedy）：优先发射就绪 warp —— 现代 GPU 的近似做法
两种都只需少量状态位 —— GPU 调度器比 CPU 调度器简单两个数量级
```

## 4. 占用率：并发度的量化

### 4.1 定义

```
占用率 = 实际驻留线程 / SM 最大驻留线程（2048）

100% 占用率 = 64 warp 驻留 = 2048 线程/SM
```

### 4.2 占用率与性能的关系（误区警示）

```
误区：占用率越高越好
真相：占用率是"延迟隐藏的能力"，不是性能本身
  - 计算密集型（无访存等待）：50% 占用率可能已跑满
  - 访存密集型：需要高占用率填满带宽

诊断方法：
  A 类负载（算力瓶颈）：占用率 30-50% 已够
  B 类负载（带宽瓶颈）：占用率 80%+ 才有救
  → 先判断瓶颈类型，再调占用率
```

### 4.3 调节占用率的工具

| 手段 | 作用 | 代价 |
|------|------|------|
| `__launch_bounds__(256, 8)` | 限制线程数/块，编译器压寄存器 | 可能溢出 |
| 减小块大小 | 更多块、更灵活 | 块间同步开销 |
| 减少共享内存 | 更多块驻留 | 访存变多 |
| maxrregcount | 全局寄存器上限 | 溢出风险 |

> 🎯 经验法则：**占用率调优是"延迟隐藏预算"的分配**——先测负载是算力瓶颈还是带宽瓶颈，再决定压寄存器还是加线程。盲目追求 100% 占用率是新手第一误区。

## 5. 分支发散及其代价

### 5.1 发散的定义

```
SIMT 的残酷现实：一个 warp 内所有线程必须执行同一条指令
  if (tid % 2 == 0) { A(); } else { B(); }
  → warp 先执行 A 分支（偶数线程干活，奇数线程空转）
  → 再执行 B 分支（奇数干活，偶数空转）

代价：两条路径串行执行 —— 吞吐减半（理想情况）
发散深度：if-else 嵌套 → 指数级串行
```

### 5.2 避免发散的工程手段

```
① 数据重排：把同类数据聚到一起（按分支条件排序/分桶）
② 数学替代：用位运算/绝对值替代分支（predication，编译期）
③ 更细粒度：让发散发生在 warp 边界而非 warp 内
④ 循环内分支：尽量提到循环外（hoisting）

示例：
  坏：if (data[i] > 0) sum += data[i];      // warp 内一半 true
  好：将 data 按正负分组后分别规约           // warp 内全同

性能量级：完全发散可致 32× 退化 —— 比占用率影响大得多
```

### 5.3 发散 vs CPU 分支预测

```
CPU：预测分支 → 错了回滚（成本几周期）
GPU：不预测 → 串行执行所有路径（成本随发散深度线性增长）

哲学对照：CPU 用"猜"省钱，GPU 用"全做"保正确
  → GPU 程序员的职责 = 保证 warp 内线程走同一条路
```

## 6. 同步与内存模型

### 6.1 同步层级

| 同步范围 | 原语 | 成本 |
|---------|------|:---:|
| 块内 | `__syncthreads()` | 低（共享内存屏障） |
| 网格级 | 原子操作 / 协作组 | 中高（L2 原子） |
| 跨 kernel | kernel 边界（隐式同步） | 高（整个 GPU 空闲等待） |

### 6.2 内存可见性模型

```
GPU 内存模型（近似规则）：
  块内：__syncthreads() 保证共享内存读写有序
  全局：原子操作 + 内存栅栏（__threadfence）
  主机：cudaDeviceSynchronize() + 页锁定/流管理

与 CPU 对照：GPU 没有缓存一致性协议（无 MESI！）
  一致点集中在 L2 —— 简化硬件，同步责任交给软件
```

> ⚠️ 大坑提醒：块间"假装同步"（用原子计数模拟网格屏障）要极其小心——它需要"所有块都在飞"，块数多于驻留量时必然死锁（经典 CUDA 陷阱）。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 块怎么分配？ | 硬件先到先得；资源（寄存器/共享内存）限制驻留数 |
| 延迟怎么藏？ | 驻留 warp 轮换：一个等访存，其他干活 |
| 占用率是什么？ | 驻留线程/上限；按负载类型调，不是越高越好 |
| 发散代价？ | warp 串行走各路，深度发散可致 32× 退化 |
| 一致性怎么办？ | 无硬件协议，L2 聚合 + 软件同步 |
