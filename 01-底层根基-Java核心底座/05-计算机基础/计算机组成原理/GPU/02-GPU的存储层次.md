## 1. GPU 存储金字塔

```
┌───────────────────────────────────────────┐
│ 寄存器（Register）  ~1周期  256KB/SM       │ 最快、最小
├───────────────────────────────────────────┤
│ 共享内存（Shared）  ~5-10周期  ~228KB/SM   │ 块内共享、可编程
├───────────────────────────────────────────┤
│ L1 Cache           ~10周期    与共享合并   │ 硬件缓存
├───────────────────────────────────────────┤
│ L2 Cache           ~100-200周期 数十MB     │ 全 GPU 共享
├───────────────────────────────────────────┤
│ HBM（显存）         ~400-700周期 192-288GB │ 容量与带宽来源
├───────────────────────────────────────────┤
│ 主机内存（PCIe）    微秒级                 │ 最慢，CPU/GPU 边界
└───────────────────────────────────────────┘
```

> ⚠️ 与 CPU 的关键差异：GPU 各级容量远小于 CPU 对应层，但**带宽大得多**——L2 内带宽可达数十 TB/s，HBM 8-22 TB/s。GPU 用"带宽喂并行"，不用"容量养局部性"。

## 2. 寄存器堆：并发度的预算

### 2.1 规模与角色

```
每 SM 寄存器堆：64K × 32 位 = 256KB（H100 级，各代相似）
角色：线程现场存储 —— 隐藏延迟的物理基础（切换零成本）

分配：编译期静态分配（无重命名！）
  每个线程用 R 个寄存器 → 每 SM 最多驻留 64K / R 个线程

示例（H100，每线程最多 255 个）：
  线程用 32 个寄存器 → 最多 2048 线程/SM（100% 占用率）
  线程用 128 个寄存器 → 最多 512 线程/SM（25% 占用率）
```

### 2.2 寄存器压力 vs 占用率的博弈

```
寄存器多 → 每个线程更"强壮"（少溢出）→ 但线程数少 → 延迟隐藏差
寄存器少 → 线程多（占用率高）→ 但可能溢出到本地内存 → 带宽开销

工程答案：__launch_bounds__ 显式限制每线程寄存器数
  CUDA 优化经典套路：maxrregcount 调参，找吞吐拐点
```

> 💡 对照：CPU 有 200-500 个物理寄存器做重命名；GPU 的 64K 寄存器/SM 是"把并发预算直接给程序员管理"——没有重命名，因为线程切换本身就免费。

## 3. 共享内存与 L1

### 3.1 共享内存（Shared Memory）

```
位置：SM 内（与 L1 合并，可配置划分，最大 ~228KB）
带宽：每 SM TB/s 级（比 L2 快一个量级）
语义：块内所有线程可读写 —— 块内通信的"快车道"
本质：可编程缓存（程序员显式管理，无替换策略）

用途：
  ① 块内数据交换（避免走全局内存）
  ② 数据复用（矩阵分块、卷积滑动窗口）
  ③ 广播（一个值被整块用）

代价：显式管理（拷贝/同步）、容量小、bank 冲突（见下）
```

### 3.2 Bank 冲突（Bank Conflict）

```
共享内存按 32 个 bank（每 bank 4B）组织：
  同周期不同线程访问不同 bank → 并行（32 线程 1 周期）
  多个线程访问同一 bank → 冲突 → 串行化（2 路冲突 = 2 倍延迟）

例：float s[32][32]；
    s[threadIdx.x][i] 连续访问 → 线程 i 访问 bank i → 无冲突 ✅
    s[i][threadIdx.x] 跨步访问 → 全部访问 bank 0 → 32 路冲突 ❌

技巧：padding（+1 列）、按步长偏移、换布局
```

### 3.3 L1：硬件缓存的配角

```
L1（与共享内存合并）：自动缓存全局内存访问
命中率低时作用有限 —— GPU 程序员默认"不用 L1 玄学"，
  热点数据手动放共享内存（显式 > 隐式）
```

## 4. L2 与全局内存

### 4.1 L2：全 GPU 共享的最后防线

| 性质 | 值 |
|------|:---:|
| 容量 | 数十 MB（B200 双 die 共享大 L2） |
| 带宽 | 数十 TB/s |
| 角色 | 跨 SM 共享、原子操作、一致性点 |
| 命中场景 | 数据复用（模型权重、KV Cache 局部） |

### 4.2 合并访问（Coalescing）—— 头号优化

```
GPU 全局内存按 128B 段访问：
  一个 warp（32 线程）同时访问连续地址 → 一趟 128B 完成 ✅
  散乱访问 → 拆成多趟 → 带宽浪费 4-32 倍

示例：
  c[i] = a[i] + b[i]（连续下标）→ 完美合并 ✅
  c[perm[i]]（间接索引）→ 完全发散 ❌（最慢模式之一）

性能差距：合并 vs 不合并 可达 10-100 倍 —— 比算法本身的常数重要
```

### 4.3 持久化（Persisting）与流（Streaming）

```
L2 支持持久化提示（cudaAccessPolicyWindow）：
  热点张量钉在 L2，流式数据绕过 —— CPU 锁存行思想的 GPU 版
流式标记（evict_first）：一次性数据不污染 L2
```

## 5. HBM：高带宽内存的工程奇迹

### 5.1 为什么 GPU 不用普通 DRAM

```
GPU 对带宽的渴求：计算速度增长 >> 内存带宽增长（带宽墙）
  普通 DDR5 带宽 ~50GB/s（每通道），GPU 要 8-22 TB/s —— 差 160-400 倍

HBM 的解法：3D 堆叠 + 超宽总线
  DDR：64 位总线 × 高频率
  HBM：1024 位总线/堆叠 × 多层堆叠（8-16 层）→ 带宽靠"宽"而非"快"
```

### 5.2 HBM 演进表（2025-2026 实测数据）

| 世代 | GPU | 容量 | 带宽 | 堆叠 |
|------|-----|:---:|:---:|:---:|
| HBM3 | H100 | 80GB | 3.5 TB/s | 8-Hi |
| HBM3e | B200 | 192GB | 8 TB/s | 12-Hi |
| HBM3e | B300 | 288GB | 8 TB/s | 12-Hi |
| **HBM4** | Rubin（2026） | 288GB | **22 TB/s** | 新一代堆叠 |
| HBM4e | Rubin Ultra（2027） | ~1TB/4GPU | 8 TB/s/GPU | — |

### 5.3 HBM 的成本与瓶颈

```
制造：TSV（硅通孔）+ 堆叠工艺，良率敏感、产能紧张
供应：SK 海力士/三星/美光 —— 2025-2026 产能被 NVIDIA 包圆，价格涨 20%+
GPU 成本中 HBM 占比可达 50%+ —— 显存即成本

带宽的决定性：LLM 推理是"带宽饥渴型"负载
  生成一个 token 要读完整权重 → 推理吞吐 ∝ 显存带宽
  这就是 Blackwell→Rubin 带宽 8→22TB/s（2.75×）远超算力提升的原因
```

## 6. 带宽为王的推论

### 6.1 三条推论

```
推论 1：算力提升要配带宽提升
  B200：算力 2.25 PF FP8 vs H100 989 TF（2.3×）
        带宽 8 vs 3.5 TB/s（2.3×）—— 严格同步，带宽墙锁死

推论 2：访存模式决定成败
  同一算法，合并 vs 发散可以差 100 倍 —— 优化 GPU 程序先看访存

推论 3：显存容量决定"能跑什么模型"
  192GB 跑不了 405B 参数模型（需 2×288GB 或拆分）
  显存容量 = 模型规模上限，带宽 = 吞吐上限
```

### 6.2 与 CPU 存储设计的对照

| 维度 | CPU | GPU |
|------|-----|-----|
| 优化目标 | 延迟（少缺失） | 带宽（多并行） |
| 缓存策略 | 大容量自动缓存 | 显式共享内存 + 合并访问 |
| 管理方式 | 硬件透明 | 程序员主导 |
| 关键公式 | AMAT = 命中时间 + 缺失率 × 惩罚 | 吞吐 = 带宽 / 每元素字节数 |

> 🎯 **核心要点**：GPU 存储的一切设计都在回答一个问题——**如何在 100 万个线程同时访存时不堵车**。答案是：带宽堆满（HBM 宽总线）、局部快车（共享内存）、乘客排序（合并访问）。理解"带宽为王"，就理解了 FlashAttention 为什么把中间结果留在片上、为什么 KV Cache 是推理优化的头号目标。

## 7. 小结

| 问题 | 答案 |
|------|------|
| GPU 存储最缺什么？ | 带宽（算力增速 >> 带宽增速） |
| 寄存器堆的角色？ | 并发度预算（每线程寄存器数 ↔ 驻留线程数） |
| 共享内存为何快？ | SM 内 TB/s 带宽 + 显式管理；警惕 bank 冲突 |
| 头号优化是什么？ | 合并访问（128B 段对齐，连续下标） |
| HBM 为什么宽？ | 1024 位总线 × 堆叠，带宽靠宽度不靠频率 |
