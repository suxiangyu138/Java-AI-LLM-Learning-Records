## 1. 寄存器分配的决策空间

### 1.1 问题定义

```
输入：中间表示（IR），含无限多个"伪寄存器"（虚拟变量）
输出：把伪寄存器映射到有限的真实寄存器（16-32 个）
约束：同时活跃（live）的变量数 > 寄存器数时，部分变量必须溢出到内存

目标：最小化溢出次数（每次溢出 = 一次内存访问 = 慢 10-100 倍）
```

### 1.2 为什么重要

```
访存 vs 寄存器：1 次 load/store ≈ 4-100 周期 vs 1 周期
寄存器分配质量直接决定代码性能 —— 它是编译器后端最重要的优化之一
GCC/LLVM 的优化级别（-O1/-O2/-O3）的主要区别之一就在分配激进程度
```

> 🎯 一句话：**寄存器分配是"把无限变量塞进有限寄存器"的调度问题**——变量多、寄存器少时，谁被溢出是性能的分水岭。

## 2. 活性分析与活跃区间

### 2.1 活性（Liveness）

一个变量在程序点 p 上**活跃** = 它的值在 p 之后还会被使用（读）。

```c
int f(int a, int b) {
    int c = a + b;    // c 定义（def）
    int d = c * 2;    // c 最后使用（use）→ 此后 c 不再活跃
    return d;
}
// c 的活跃区间：[定义点, 最后使用点]
```

### 2.2 活跃区间（Live Range）与冲突

```
活跃区间 = 变量"活着"的指令区间（用线性坐标表示）

冲突（Interference）：两个变量的活跃区间重叠 → 不能共享同一寄存器

变量 a:  |████████████|
变量 b:      |██████████|        ← a、b 冲突
变量 c:                      |██|  ← c 与 a、b 都不冲突（可复用寄存器）
```

**活性方程（数据流分析）**：

```text
in[n]  = use[n] ∪ (out[n] − def[n])     // 入口活跃 = 使用 + (出口活跃 − 定义)
out[n] = ∪ in[后继]                     // 出口活跃 = 所有后继入口活跃的并集
迭代求解直到不动点 —— 经典数据流分析
```

> 💡 这是编译器课程必考的数据流方程，也是静态分析（如死代码消除）的共用基础。理解"活跃区间冲突 → 建图 → 着色"三步，就理解了分配器的骨架。

## 3. 图着色分配器

### 3.1 从冲突图到 K 着色

```
冲突图（Interference Graph）：
  节点 = 变量；边 = 活跃区间冲突

问题转化：给每个节点分配一个寄存器编号（颜色），
        相邻节点颜色必须不同 → 图的 K 着色问题
        K = 可用寄存器数（如 15 个整数寄存器）
```

### 3.2 Chaitin 算法（经典实现）

```
① 建冲突图
② 简化（Simplify）：反复移除度数 < K 的节点（压栈），
   这些节点"一定能着色"（贪心：邻居颜色最多 K-1 个）
③ 溢出（Spill）：若剩余节点度数都 ≥ K → 选一个"最不活跃的"
   标记为溢出候选，移除继续
④ 着色（Assign）：按入栈逆序回填颜色，遇溢出候选 → 插入保存/加载
⑤ 必要时基于溢出代价迭代（重新分配，再溢出直到成功）
```

### 3.3 一个微型示例

```c
// 4 个变量、2 个寄存器（K=2）的简化推演
int f() {
    int a = 1;      // a: 活到 x 处
    int b = 2;      // b: 与 a 冲突
    int x = a + b;  // x: 与 a、b 都冲突（都还活着）
    int c = x * 3;  // c: 与 x 冲突，但与 a、b 不冲突
    return c;
}
// 冲突图：a-b、a-x、b-x、x-c 共 4 条边
// K=2：a 度数2、b 度数2、x 度数3、c 度数1
// → c 先出栈（度数1<K）→ x 度数仍高 → 溢出 x（或选其他启发式）
// 结果：a、b、c 用 2 个寄存器轮转，x 溢出到栈 —— 每次使用 x 加一次 load
```

## 4. 溢出：寄存器不够怎么办

### 4.1 溢出代价与选择

```
溢出一次：变量从"寄存器"降级为"栈槽"（home slot）
  每次使用：load 进寄存器 → 用 →（可选）store 回栈
  代价 = 2 次内存访问 + 寄存器压力

启发式选择溢出对象：
  ① 溢出代价低（使用频率低、活跃区间小）
  ② 邻居多（移除后能释放大量度）
  ③ 循环内变量绝不优先溢出（循环体 ×N 次执行放大代价）
```

### 4.2 编译器缓解溢出的手段

| 手段 | 做法 | 效果 |
|------|------|------|
| 重新关联（Rematerialization） | 常量/地址可重新计算，不 store | 省掉保存 |
| 循环不变代码外提 | 把循环内不变计算移出 | 减少活跃区间重叠 |
| 栈槽复用 | 不冲突的溢出变量共用栈槽 | 减小栈帧 |
| 寄存器压力导向调度 | 指令调度时错开活跃区间 | 减少峰值压力 |
| 线性扫描+融合 | 后端多种分配器按需选择 | 提高整体质量 |

### 4.3 观察溢出：经典代码

```c
// 编译后频繁访问 [rbp-8] 之类栈偏移 = 溢出信号
int heavy(int n) {
    int a, b, c, d, e, f, g, h, i, j, k;   // 11 个变量 > 可用寄存器
    ...
}
// -O0 时所有变量都"溢出"（每个变量固定栈槽）
// -O2 时大部分进寄存器，仅压力大的溢出
```

> ⚠️ 经验法则：`-O0` 调试构建因"全溢出"慢 3-10 倍；JIT 的 C1/C2 分层编译本质上也是"分配质量分档"——C1 快速线性扫描，C2 全量图着色。

## 5. 线性扫描与其他策略

### 5.1 线性扫描（Linear Scan，JIT 主流）

```
思想：按活跃区间起点排序，顺序扫描分配
  活跃区间开始 → 分配空闲寄存器
  活跃区间结束 → 释放寄存器
  无空闲 → 溢出当前区间中"结束最晚"的

特点：O(n) 线性时间、实现简单、结果接近图着色（95%+ 质量）
应用：HotSpot C1、V8 等 JIT 的标配（编译时间敏感）
```

### 5.2 各场景的分配器选型

| 场景 | 分配器 | 原因 |
|------|--------|------|
| GCC/Clang -O2 | 图着色 + 迭代改进 | 编译时间可接受，追求代码质量 |
| JIT（C1/V8） | 线性扫描 | 编译延迟必须低（毫秒级） |
| JIT 热点（C2/Graal） | 图着色 | 热点代码值得多花编译时间 |
| 寄存器窗口架构 | 硬件分配器 | SPARC 窗口避免软件保存（见 08） |

## 6. 实战：反汇编观察分配质量

### 6.1 同一函数的三种编译质量

```c
int sum(int *arr, int n) {
    int s = 0;
    for (int i = 0; i < n; i++) s += arr[i];
    return s;
}
```

```asm
; GCC -O0（全溢出，性能最差）
sum:
    push rbp
    mov  rbp, rsp
    mov  [rbp-24], rdi          ; arr 存栈槽
    mov  [rbp-28], esi          ; n 存栈槽
    mov  [rbp-4], 0             ; s 存栈槽（每次迭代都要 load/store！）
    jmp  .cond
.loop:
    mov  eax, [rbp-4]           ; load s
    mov  edx, [rbp-24]          ; load arr
    mov  ecx, [rbp-28]          ; load n（其实应缓存）
    ... 每次迭代 4+ 次内存访问

; GCC -O2（寄存器化，性能最佳）
sum:
    xor  eax, eax               ; s 在 eax
    test esi, esi
    jle  .done
.loop:
    add  eax, [rdi]             ; 直接内存操作数（无显式 load）
    add  rdi, 4
    sub  esi, 1
    jnz  .loop
.done:
    ret
; 差异：-O0 每迭代 ~6 次内存访问 vs -O2 只有 1 次 —— 快 5-10 倍
```

### 6.2 分配器的"人格"

| 观察点 | 高质量分配的特征 |
|--------|----------------|
| 循环内栈访问 | 应几乎为零（循环变量/累加器全寄存器化） |
| LEA 使用 | 大量 LEA 替代加法（不污染标志 + 地址计算） |
| 寄存器复用 | 同一寄存器承载多个非冲突变量 |
| 内存操作数 | `add eax,[rdi]` 融合 load——省独立 load 指令 |

> 🎯 **核心要点**：寄存器分配是编译器"把 C 语言翻译成机器性能"的最后一公里。读懂反汇编中的栈访问密度，就能判断分配质量；这也解释了为什么 JVM 的 JIT（-Xcomp 全编译 vs 分层）会有数量级的吞吐差异。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 分配的输入输出？ | 无限伪寄存器 → 有限真实寄存器映射 |
