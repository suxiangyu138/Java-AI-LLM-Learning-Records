## 1. 存储金字塔顶端

### 1.1 金字塔定位

```
┌──────────────────────┐
│  寄存器（~1 周期）     │  ← 本体系的主角：0-300 字节/核
├──────────────────────┤
│  L1 Cache（4-5 周期） │
├──────────────────────┤
│  L2 / L3 Cache        │
├──────────────────────┤
│  DRAM（200-500 周期） │
└──────────────────────┘
```

寄存器是唯一**不在 Cache 体系之内**、由指令集直接寻址的存储：`add rax, rbx` 直接操作两个寄存器，不存在"命中/缺失"的概念——**寄存器访问永远不会缺失**。

### 1.2 关键性质

| 性质 | 说明 |
|------|------|
| 访问时间 | ~1 周期（与 CPU 同频，无旁路） |
| 容量 | 每核合计 <1KB（16-32 个 × 64 位） |
| 寻址方式 | 指令内直接编码寄存器编号，无地址计算 |
| 管理方式 | **软件（编译器/程序员）显式管理** |
| 一致性 | 无一致性协议（单线程内天然独占） |

> 🎯 一句话定位：寄存器是"编译器的手写缓存"——把什么放进寄存器、何时释放，由编译器在编译期决定，而不是像 Cache 那样靠硬件运行时猜。

## 2. 物理实现：触发器与寄存器堆

### 2.1 存储单元：触发器

寄存器用**边沿触发 D 触发器**（DFlip-Flop）实现——不是 SRAM 位单元。两者对比：

| 维度 | 触发器（寄存器用） | SRAM 位单元（Cache 用） |
|------|:---:|:---:|
| 单元晶体管数 | 6-8+ 个/位（D 锁存器约 6） | 6T |
| 读写 | 同步时钟边沿，任意位可独立写 | 行选择后整行读写 |
| 速度 | 更快（无预充/读放延迟） | 稍慢（位线预充） |
| 面积 | 大 2-3 倍 | 小 |
| 用途 | 寄存器堆、流水线级间 | Cache、TLB |

> 💡 这就是"寄存器快但贵"的物理根源：每个寄存器位都带独立的时钟输入和读写逻辑，而 Cache 位单元靠共享位线批量操作——**用面积换时间**。

### 2.2 寄存器堆（Register File）

全部寄存器组织成一个多端口存储阵列：

```text
寄存器堆（以 32 × 64bit、4 读 2 写端口为例）
┌────────────────────────────┐
│  Port A: 地址→数据         │  同周期最多 4 个读操作数
│  Port B: 地址→数据         │  同周期最多 2 个写结果
│  Port C: 地址→数据         │
│  Port D: 地址→数据         │
│  Port E/W: 地址←数据       │
└────────────────────────────┘
```

多端口的意义：一条指令 `mul rax, rbx, rcx` 需要在**同一周期**读出 3 个源操作数、写回 1 个结果——端口数直接决定流水线的发射宽度。

### 2.3 端口与功耗

```
端口数 P → 位线数量 ×P、译码逻辑 ×P、面积 ×P² 量级增长
RISC-V 经典设计：32 位寄存器堆 2 读 1 写（3R1W）适合标量流水线
高性能核心：4R2W-10R+（Zen 5 支持多端口同时读）
代价：寄存器堆占核心面积 5-15%，功耗占比更高
```

## 3. 寄存器 vs Cache：三大本质区别

| 维度 | 寄存器 | Cache |
|------|--------|-------|
| **管理主体** | 编译器/程序员显式分配 | 硬件自动管理（替换算法） |
| **寻址** | 指令直接编码编号（0-31），无地址计算 | 需要 Tag/Index/Offset 分解 + 比较 |
| **一致性** | 无一致性协议，单线程独占 | 多核共享需 MESI 等协议 |
| **访问粒度** | 单寄存器（8/16/32/64 位） | 整行（64B） |
| **缺失** | 不存在 | 命中/缺失决定延迟 |
| **保存开销** | 切换时保存全部（几十字节） | 无需显式保存（自然失效） |

**三个深层推论**：

```
① 编译器管理 → 程序员可见、可控制
   快慢由分配质量决定：循环变量放寄存器 → 快 10-100 倍

② 无地址计算 → 无寻址延迟
   load 需要 TLB + Cache 两级命中才能拿数据；寄存器直接可用

③ 无一致性 → 多线程共享变量无法放寄存器
   这就是 volatile 的语义：禁止编译器把共享变量缓存到寄存器
```

> ⚠️ 注意第 ③ 点的 Java 语义：`volatile` 字段读写强制走内存（或等价可见性屏障），而普通局部变量可被 JIT 分配进物理寄存器——**局部变量快的秘密正在于此**。

## 4. 为什么寄存器数量这么少

### 4.1 四个约束

| 约束 | 说明 |
|------|------|
| 指令编码位 | 3 位可编码 8 个、5 位可编码 32 个寄存器——每加一位都吃掉指令密度 |
| 面积成本 | 寄存器堆是多端口全定制单元，32 个 64 位寄存器已占核心面积 5-15% |
| 上下文切换 | 寄存器越多，进程切换保存/恢复越贵（APX 扩到 32 个后 xsave 变大） |
| 物理端口 | 每个新寄存器都要为所有读端口布线，端口数决定发射宽度 |

### 4.2 16 vs 32：x86 的历史包袱与 APX 破局

```
x86：8086 只有 8 个 16 位寄存器（AX BX CX DX SI DI BP SP）
     x86-64 扩到 16 个（加 R8-R15）——20 多年未变
2023：Intel APX 宣布再加 16 个（R16-R31）→ 32 个 GPR
     用新 EVEX/REX2 前缀扩展编码，仅 64 位模式生效
     SPEC 仿真：负载减少 ~10%、存储减少 ~20%（见 08-前沿扩展）
```

> 💡 数量悖论：编译器总嫌寄存器不够（溢出代价高），硬件设计总嫌寄存器太多（面积与编码）。32 个 GPR 是当前生态的平衡点。

## 5. 寄存器视角的程序执行模型

### 5.1 一条指令的生命周期

```text
mov rax, [rbx+8]      ; 从内存取值到寄存器
add rax, rcx          ; 寄存器运算（1 周期）
mov [rdi], rax        ; 结果写回内存

执行路径：
  [rbx+8] 内存地址 → TLB 翻译 → L1 Cache 命中 → 数据进入 rax
  ↑ 这条 load 可能消耗 4-5 周期且可能缺失
  add 直接读 rax/rcx → 1 周期，零风险
```

### 5.2 寄存器值的"生命期"（引出 07 模块）

```text
变量 x 从定义到最后一次使用 → 活跃区间（live range）
活跃区间的重叠程度决定需要几个寄存器
若寄存器不够 → 编译器把部分变量"溢出"（spill）到栈上 → 性能损失
```

> 🎯 **核心要点**：寄存器是"零延迟、零缺失、零寻址"的存储——一切 CPU 性能优化的第一原则就是把热点数据留在寄存器里。读本章后应能回答：为什么函数参数用寄存器传（04）、为什么循环变量是寄存器分配的第一优先（07）。

## 6. 实战：观察寄存器

### 6.1 用 gdb 观察寄存器现场

```text
(gdb) break main
(gdb) run
(gdb) info registers          # 查看全部通用寄存器
rax            0x401126         4198694
rbx            0x0              0
rcx            0x4011f0         4198896
rdx            0x7fffffffe218   140737488347672
rsi            0x1              1
rdi            0x7fffffffe228   140737488347688
rsp            0x7fffffffe1d0   0x7fffffffe1d0
rip            0x401126         0x401126 <main+11>
eflags         0x202            [ IF ]
```

```bash
# 查看内存地址对应的值：寄存器是"指路牌"
(gdb) x/4gx $rdi        # 查看 rdi 指向的 4 个 8 字节值
(gdb) print $rax        # 打印寄存器值
(gdb) info registers xmm0  # 浮点/向量寄存器
```

> 💡 崩溃排查套路：程序崩溃时先看 `rip`（崩在哪条指令）、`rsp`（栈是否被破坏）、`rax`（返回值/系统调用号）、`rdi/rsi`（函数参数）——四个寄存器就能定位大部分 bug。

### 6.2 用反汇编观察寄存器操作

```bash
objdump -d ./app | head -40     # 观察指令的寄存器操作数
# 关键观察：函数开头 push rbp/rbx/r12-r15（被调用者保存的"宣誓"）
#          函数结尾 pop 恢复 → 调用者视角寄存器"从未变过"
```

### 6.3 寄存器与调试的三条经验

```
① 被调用者保存寄存器（RBX/RBP/R12-15）在函数边界必须一致
   → 调试器靠这个约定跨函数回溯调用栈（DWARF 展开规则）
② volatile 局部变量的值不会留在寄存器（每次读写都访问内存）——调试时可见
③ 优化代码中"变量不存在"≠ bug：-O2 后局部变量常被合并/消除，
   无法在 gdb 中看到 → 用 -O0 或 debug 构建调试
```
