## 1. 问题：架构寄存器的数量瓶颈

### 1.1 乱序执行（OoO）的前提

现代 CPU 每个周期发射 4-8 条指令，乱序窗口内可能有 **50-200 条指令同时在飞**。但架构寄存器只有 16-32 个：

```asm
; 这段代码中 rax 被反复重写（WAR/WAW 风险）
mov rax, [x]       ; ① 读旧值
add rax, 1         ; ② 改
mov rax, [y]       ; ③ 又改（与 ① 冲突）
```

如果所有指令都共享同一组物理存储，乱序执行就不可能——每条写寄存器的指令都会破坏其他在飞指令的源值。

### 1.2 两条出路

```
出路 A：限制乱序深度（简单但性能封顶）
出路 B：硬件提供"看不见的额外寄存器"——物理寄存器堆 + 重命名 ← 现代所有高性能 CPU
```

## 2. 重命名的核心思想

### 2.1 架构寄存器 vs 物理寄存器

```
架构寄存器（Architectural Register）：ISA 定义的 16/32 个 —— 软件视角
物理寄存器（Physical Register）：硬件实际存储 —— 可能 200-500 个 —— 硬件视角

重命名（Renaming）：每条写指令的结果写入"新的物理寄存器"，
                   并更新映射表：架构寄存器 → 最新物理寄存器
```

### 2.2 一个直观示例

```asm
mov rax, [x]       ; ① rax → PR1
add rax, 1         ; ② rax → PR2（映射表指向 PR2，PR1 仍保留旧值）
mov rax, [y]       ; ③ rax → PR3（PR2 的值仍被后续读使用）
```

```text
执行时刻：① 还没完成时，② 已经可以启动（读 PR1？不——② 读的是 ① 的结果，
所以 ② 必须等 ①；但 ③ 与 ① 无依赖，③ 可以先于 ① 完成！

等价效果：硬件仿佛拥有 3 个 rax —— 乱序度不受架构寄存器数限制
```

> 🎯 重命名的本质：**把程序中的"假共享"（同一寄存器名）拆成"真独立"（不同物理寄存器）**——就像 Java 里把共享变量改成线程私有副本一样，消除竞争。

## 3. 三种依赖与重命名的价值

### 3.1 依赖分类（Tomasulo 算法视角）

| 依赖 | 原名 | 性质 | 重命名能否消除 |
|------|------|------|:---:|
| RAW（读后写） | 真依赖 | 数据必须先算出来 | ❌ 不能（本质依赖） |
| WAR（写后读） | 反依赖 | 只是"寄存器名复用" | ✅ 消除 |
| WAW（写后写） | 输出依赖 | 只是"寄存器名复用" | ✅ 消除 |

```asm
mov rax, [x]     ; A：写 rax
mov rbx, rax     ; B：读 rax → 与 A 是 RAW（真依赖，必须等 A）
mov rax, [y]     ; C：写 rax → 与 A 是 WAW（假依赖），与 B 无依赖
mov rcx, rbx     ; D：读 rbx → 与 B 是 RAW

重命名后：A 写 PR1，C 写 PR3 —— C 无需等 A/B，可以立刻执行
```

### 3.2 为什么重命名意义巨大

```
典型比例：SPEC 整数负载中，WAR/WAW 假依赖占寄存器依赖的 30-50%
消除假依赖 → 指令并行度提升 → 每周期指令数（IPC）显著上升
—— 这是"同频率下现代 CPU 比 20 年前快 3-5 倍"的主要来源之一
```

## 4. 硬件结构：RAT、PRF 与 ROB

### 4.1 三件套结构图

```text
        重命名阶段                    提交阶段          
┌─────────────────────────┐  ┌─────────────────────────┐
│ RAT 重命名表            │  │ ROB 重排序缓冲          │
│ 架构寄存器→物理寄存器   │  │ 在飞指令按序排队        │
│ 记录旧映射（供回滚）    │  │ 结果+状态+目标          │
└─────────────────────────┘  └─────────────────────────┘
             │                            │             
     分配新物理寄存器             按序提交/异常回滚     
             │                            │             
┌──────────────────────────────────────────────────────┐
│ 物理寄存器堆 PRF（200-500 个）                       │
│ 每个物理寄存器：数据 + 就绪位（多端口并发）          │
└──────────────────────────────────────────────────────┘
```

| 结构 | 职责 | 关键点 |
|------|------|--------|
| RAT（Register Alias Table） | 架构→物理映射 | 每周期可重命名 4-8 条指令（端口数量） |
| PRF（Physical Register File） | 所有结果的实际存储 | 每个物理寄存器有"就绪位"驱动旁路 |
| ROB（Reorder Buffer） | 按序提交/回滚 | 记录每条在飞指令的旧映射（撤销用） |
| 空闲列表（Free List） | 分配未用物理寄存器 | 用尽则停顿（重命名停顿） |

### 4.2 一条指令的完整旅程

```text
① 分配：从 Free List 拿一个物理寄存器 PRi（若空列表耗尽 → 发射停顿）
② 更新：RAT[rax] = PRi；旧映射 PRold 压入 ROB 条目
③ 执行：算完后写 PRi，置"就绪位"
④ 提交：按序到达 ROB 头 → 架构寄存器正式"更新"（其实 RAT 早就指向了）
       旧物理寄存器回收进 Free List（若无其他在读）
⑤ 分支预测错误：从 ROB 中该分支条目起"洗掉"，RAT 恢复成分支点的快照
```

## 5. 推测执行与回滚

### 5.1 为什么需要回滚

分支预测错误时，错误路径上的指令已经改写了 RAT 和物理寄存器——**必须恢复到分支点状态**，否则程序语义被污染。

### 5.2 两种恢复策略

| 策略 | 做法 | 代价 |
|------|------|------|
| 逐条撤销（ROB 回滚） | 按 ROB 逆序恢复每条指令的旧映射 | 回滚时间长（几十周期） |
| 检查点（Checkpoint） | 周期性地保存整个 RAT 快照，预测错误直接恢复快照 | 快照存储大（RAT 32 项 × 9 位/项 × 多快照） |

现代 CPU 混合使用：每周期维护 1-2 个"深检查点"，其余靠 ROB 撤销。

### 5.3 与安全问题的联系

```
推测执行会把数据写进物理寄存器（痕迹）→ 侧信道攻击载体之一
见《缓存与Cache/06-安全模块》——Meltdown 正是"权限异常的推测指令
仍留下可观测痕迹"的实例
```

## 6. 物理寄存器堆的规模与代价

### 6.1 规模参考（公开文献数据）

| 内核 | 整数 PRF | 浮点 PRF | 架构寄存器 |
|------|:---:|:---:|:---:|
| Intel Skylake | ~180 | ~168 | 16 |
| 现代高性能核（Zen/大核） | 200-400 | 300-500 | 16-32 |
| 示例：Zen 4/5 | 224+ | 320+ | 16 |

> ⚠️ 以上为公开分析文献的近似值，不同来源口径不同；重点掌握数量级与设计逻辑。

### 6.2 成本分析

```
面积：每个物理寄存器 = 64 位触发器 + 就绪位 + 端口逻辑
     400 个 PRF ≈ 25KB —— 比 L1 Cache 小，但多端口密度极高
功耗：每次访问全端口广播 → 重命名/读端口是功耗热点
延迟：PRF 越大，读取延迟越高 → 过大的 PRF 反而拖慢 1 周期关键路径

设计平衡：PRF 规模 ≈ 乱序窗口大小 × 每条指令写结果数
        窗口 300 条、60% 写 → 约 180-300 个物理寄存器
```

### 6.3 前沿：寄存器堆与 APX

```
Intel APX 把架构寄存器扩到 32 个 → 每核需要更多物理寄存器支撑
      → 重命名表翻倍（RAT 条目 32 个）
      → PRF 容量相应扩大（具体数量厂商未披露）
启示：架构寄存器数不是免费的 —— 每一次扩编都牵动重命名/PRF/上下文切换
```

> 🎯 **核心要点**：重命名让"寄存器不够用"变成伪命题——软件写代码时只需关心 16-32 个寄存器，硬件悄悄准备了几百个。这也是"源代码里反复使用一个变量 vs 多个变量"性能几乎无差别的硬件原因（JIT 场景同理）。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 重命名解决什么？ | WAR/WAW 假依赖，扩大乱序窗口有效深度 |
| 三件套是什么？ | RAT（映射）、PRF（存储）、ROB（排序/回滚） |
| 真依赖能消除吗？ | 不能——RAW 是数据本质依赖 |
| 预测错误怎么恢复？ | ROB 逐条撤销 + 检查点快照混合 |
| 为什么 PRF 不能无限大？ | 面积/功耗/延迟三角，量级 200-500 个 |
