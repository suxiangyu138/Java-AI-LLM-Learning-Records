## 1. Intel APX：x86 的 32 寄存器时代

### 1.1 背景：16 个 GPR 的 20 年瓶颈

```
x86-64（2003）定下 16 个 GPR 后 20 年未变
编译器长期抱怨：寄存器不够 → 溢出 → 性能损失
ARM/RISC-V 的 31/32 个 GPR 反而后来居上
2023-07：Intel 发布 APX 规范，Intel 与 AMD 在 x86 EAG 共同推进
```

### 1.2 APX 新增内容

| 特性 | 说明 |
|------|------|
| **R16-R31（EGPR）** | GPR 从 16 扩到 **32 个**（仅 64 位模式） |
| NDD（新目标） | 三操作数非破坏格式：`sub r31, rax, r15`（不覆盖源） |
| NF（无标志） | 抑制状态标志写入，消除假依赖 |
| PUSH2/POP2 + PPX | 成对保存/恢复加速（配合上下文切换） |
| 条件加载/比较 | fault-suppressing `cmov`、`ccmp`/`ctest` |
| ZU SETcc | 零扩展 0/1 生成，消除部分寄存器依赖 |
| jmpabs | 64 位绝对直接跳转 |
| 编码 | 新 EVEX/REX2 前缀（兼容旧代码） |

### 1.3 落地状态（截至 2026-08 检索）

| 环节 | 状态 |
|------|------|
| 硬件 | **Diamond Rapids**（Xeon 6 后继）为服务器首发；客户端预计 Panther Lake/Nova Lake |
| 编译器 | GCC 14 部分支持（`-mapxf`）；**GCC 15（2025-06）完整实现**，LLVM 跟进 |
| Linux 内核 | 6.16+ 基本就绪；KVM 虚拟化支持 2026-03 仍在收尾（R16-R31 状态处理） |
| 预期收益 | SPEC 整数仿真：**load 减 ~10%、store 减 ~20%**，面积/功耗代价极小 |

```asm
; APX 三操作数示例（NDD）—— 传统写法需要额外 mov
; 传统：mov rdx, rax; add rdx, r15   （2 条 + 1 次假依赖）
; APX： sub r31, rax, r15            （1 条，不破坏 rax）
```

> 🎯 意义：这是 x86 自 64 位化以来最大的一次寄存器架构演进，直接回应"RISC 寄存器多"的批评——**寄存器数量终于不再是 x86 的短板**（详见 [02-通用寄存器](02-通用寄存器与指令集.md) 的编码讨论）。

## 2. ARM SVE 与 SME：可伸缩向量与矩阵

### 2.1 SVE（Scalable Vector Extension）

```
Z0-Z31：可伸缩向量寄存器（长度由实现定义，128-2048 位）
P0-P15：谓词寄存器（逐通道掩码，支持向量化 if-else）
设计哲学：指令集不绑定向量长度 —— 同一二进制跑不同长度硬件
         （软件用 VL 查询长度，whiledo/whilelt 处理边界）
```

### 2.2 SME（Scalable Matrix Extension）：矩阵寄存器 ZA

| 特性 | 说明 |
|------|------|
| ZA 阵列 | 二维矩阵寄存器（SVL×SVL 位，最大 16KB+） |
| 访问形式 | ZA0H（水平行切片）/ ZA0V（垂直列切片） |
| 工作方式 | 流式模式（Streaming SVE，与普通 SVE 切换） |
| 核心指令 | 外积（outer product）：矩阵乘的硬件原语 |
| 规模 | SME2 状态约 16KB+，是 AMX 的 2 倍——上下文切换成本巨大 |

### 2.3 SME2（2024-2025 落地）新增寄存器操作

```
① 多向量操作：Z 寄存器按组使用（Z0.S-Z1.S 连续，或 Z0.H/Z4.H/Z8.H/Z12.H 跨步）
② ZA 多切片：一次访问 2-4 个行/列切片（ZA0H.B[w12,0:1]）
③ 多向量组：单/双/四向量组按 Wv 寄存器 + 偏移选择（模 SVL 运算）
④ 查表解压缩：2/4 位数据 → 8/16/32 位容器（量化模型加速）
⑤ BNN 外积：XNOR-计数指令（1 位二进制神经网络）

实际影响：移动端（Cortex-X925 等新核）+ 服务器端矩阵加速
```

> ⚠️ SME 的寄存器状态高达 16KB+：OS 需按需分配（Linux 默认流式模式外退出）；这印证了 [06-上下文切换](06-上下文切换与状态保存.md) 的"状态膨胀税"判断。

## 3. RISC-V V 扩展：向量寄存器的开源形态

### 3.1 规范状态

```
RVV 1.0：2019 冻结、2021 正式批准
实现：v0-v31 向量寄存器 + vl/vtype/vstart/vlenb CSR
参数：VLEN（实现定义，128-65536 位）、ELEN（元素位宽，≤64）、LMUL（长度乘数）
```

### 3.2 设计要点

| 机制 | 说明 |
|------|------|
| vl（向量长度） | 当前向量元素数——软件自适应硬件宽度 |
| vtype | 元素类型、LMUL、Sew 编码 |
| vsetvli | 设置 vl/vtype 的关键指令（每循环一次） |
| 掩码 | v0 可作掩码寄存器（M 位宽） |
| 与 SVE 对比 | 同样"长度不可知"，但用 vl 显式控制 vs SVE 隐式 + 谓词 |

```asm
# RVV 示例：vsetvli 获取当前硬件长度
vsetvli t0, a1, e32, m1   # t0 = vl（min(a1, VLEN/32)），元素 32 位
vle32.v  v1, (a0)         # 装载 a1 个元素到 v1
vadd.vv  v2, v1, v1       # 向量加
vse32.v  v2, (a2)         # 存回
```

> 💡 定位：RVV 是"开放指令集上的向量标准"——RISC-V 服务器（Ventana、Tenstorrent、阿里玄铁）与 AI 加速器正把它推向主流；与 x86 AVX-512 的固定长度、ARM SVE 的可伸缩路径并列第三条路线。

## 4. GPU 寄存器堆：规模换吞吐

### 4.1 规模对比（量级数据）

| 平台 | 寄存器资源 | 单指令粒度 |
|------|-----------|-----------|
| CPU（Zen 5） | 16 架构 + ~240 物理 | 32/64 位标量 |
| NVIDIA SM（H100） | **64K × 32 位/SM**（256KB） | 32 位（可合并 64 位） |
| AMD RDNA3 | 每通道 256 VGPR + 128 SGPR | 32 位 VGPR |
| Intel Xe | 每 EU 128 GRF（256B） | 通用寄存器文件 |

### 4.2 GPU 设计逻辑

```
为什么 GPU 寄存器堆这么大？
  ① 隐藏延迟：GPU 靠"线程切换"而非缓存命中隐藏访存延迟
     每个在飞 warp 需要完整寄存器现场 → 寄存器堆 = 并发度
  ② 无重命名：SIMT 架构多数据单指令，寄存器静态分配
     编译器一次分配、不重命名 → 寄存器是"编译器资源预算"
  ③ 面积取舍：寄存器堆可占 SM 面积 20-30%
     每 SM 64K 寄存器 / 每个线程最多 255 个 → 决定最大常驻线程数
```

```text
关键权衡（CUDA 可观测）：
  maxrregcount 调大 → 单线程寄存器多 → 溢出少，但常驻线程少 → 延迟隐藏差
  调小 → 并发高，但可能溢出（本地内存）→ 带宽开销
  —— GPU 编程中"寄存器压力 vs 占用率"是头号性能调优杠杆
```

### 4.3 与 CPU 的哲学对照

| 维度 | CPU | GPU |
|------|-----|-----|
| 寄存器规模 | 小而快（几十个） | 大而多（数千-数万） |
| 分配方式 | 编译器 + 硬件重命名 | 编译器静态分配（无重命名） |
| 隐藏延迟手段 | 乱序 + 重命名 | 大量线程切换（warp 调度） |
| 溢出代价 | 栈（快） | 本地内存（慢，需小心） |

## 5. 历史形态：寄存器窗与旋转寄存器

### 5.1 SPARC 寄存器窗（Register Windows）

```
全局寄存器 g0-g7（8 个）+ 窗口（in/local/out 各 8 个 × 8-32 个窗口）
call 时窗口自动推进：out 变被调用者的 in —— 参数传递零拷贝
窗口溢出由硬件陷阱触发（溢出到内存）—— 编译器只需保证窗口数内嵌套

优点：函数调用省保存/恢复（上下文切换全部省掉）
缺点：窗口数限制调用深度；上下文切换要搬整个窗口栈（大）
结局：SPARC 生态专用，x86/ARM 均未采纳
```

### 5.2 Itanium 旋转寄存器（Rotating Register File）

```
GR 128 个（r32-r127 可旋转）+ FR 128 个 + 谓词 64 个
循环展开时寄存器编号自动"旋转"——软件流水无需代码展开的别名
结局：IA-64 终结（2020s 停产），但"旋转窗口"思想影响后续向量/软件流水研究
```

> 💡 历史启示：寄存器架构的每一次激进创新（窗口/旋转）都败给了"与既有生态的兼容成本"；而 APX/SME/RVV 的成功路径是"增量扩展 + 软件栈协同"。

## 6. 趋势总结

| 趋势 | 证据 | 方向 |
|------|------|------|
| 寄存器数量扩容 | APX R16-R31（2023-2026） | 32 GPR 成 x86 新常态 |
| 向量/矩阵大状态 | SVE Z、SME ZA、RVV v、AVX-512/AMX | 状态尺寸 KB 级膨胀 |
| 上下文切换税上升 | AMX 8KB、SME 16KB | 懒加载、按需分配成为 OS 标配 |
| 编译器协同升级 | GCC 15 完整 APX、LLVM RVV 成熟 | 新寄存器依赖工具链先行 |
| GPU 规模寄存器 | SM 256KB 寄存器堆 | 寄存器=并发度，编译器预算管理 |

> 🎯 **核心要点**：2023-2026 的寄存器演进主线是"**容量与形态的再扩张**"——x86 补上数量短板（APX）、ARM/RISC-V 打开可伸缩向量与矩阵形态、GPU 早已把寄存器推到规模极致。不变的是第一性原理：**寄存器仍是最快、最贵、由软件显式管理的存储**。
