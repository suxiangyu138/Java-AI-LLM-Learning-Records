## 1. 系统级 IO 概述

### 1.1 核心思想：一切皆文件

Unix 系统的最大设计智慧之一，就是将所有可进行 I/O 操作的资源统一抽象为**"文件"**：

| 资源类型 | 文件抽象 | 操作方式 |
|----------|----------|----------|
| 磁盘文件 | 普通文件 | open/read/write |
| 键盘/显示器 | 标准输入/输出 | read/write |
| 网络端口 | 套接字文件 | socket/read/write |
| 进程通信 | 管道文件 | pipe/read/write |

**两个关键优势：**

| 优势 | 说明 |
|------|------|
| **接口统一** | 一套系统调用（`open`、`read`、`write`、`close`）操作所有 I/O 设备 |
| **状态统一** | 内核为每个打开的文件维护统一的状态信息，通过"文件描述符"间接操作 |

### 1.2 用户态与内核态

| 运行级别 | 权限 | 可访问的资源 |
|----------|------|-------------|
| **用户态（Ring 3）** | 受限 | 只能访问自己的内存空间 |
| **内核态（Ring 0）** | 最高权限 | 可访问所有系统资源（内存、设备、进程） |

> 💡 所有 I/O 操作必须通过系统调用完成——这是"系统级 I/O"与"用户级 I/O"的本质区别。

## 2. 文件描述符与核心系统调用

### 2.1 文件描述符（fd）

文件描述符是内核为每个打开的文件分配的非负整数，是 I/O 操作的"唯一标识"：

| 文件描述符 | 用途 |
|-----------|------|
| `0`（STDIN_FILENO） | 标准输入 |
| `1`（STDOUT_FILENO） | 标准输出 |
| `2`（STDERR_FILENO） | 标准错误 |

**关键规则：**
- fd 分配遵循"最小未使用整数"原则
- fd 是进程级资源，进程终止时内核自动关闭所有 fd
- 建议主动调用 `close()` 避免 fd 泄漏

### 2.2 核心系统调用

**open：打开/创建文件**

```c
int open(const char *pathname, int flags, mode_t mode);
```

| 参数 | 说明 |
|------|------|
| `pathname` | 文件路径 |
| `flags` | 访问模式（`O_RDONLY`、`O_WRONLY`、`O_RDWR`） |
| `mode` | 文件权限位（仅在 `O_CREAT` 时有效） |

**read：从文件读取数据**

```c
ssize_t read(int fd, void *buf, size_t count);
```

| 返回值 | 含义 |
|--------|------|
| >0 | 实际读取的字节数（可能小于 count） |
| 0 | 读取到文件末尾（EOF） |
| -1 | 失败，设置 errno |

> ⚠️ **"部分完成"问题**：`read` 和 `write` 返回的实际字节数可能小于请求的字节数，必须循环调用：

```c
// 正确写法：循环调用 read 直到读取到 EOF
ssize_t n;
char buf[1024];
while ((n = read(fd, buf, sizeof(buf))) > 0) {
    // 处理读取到的数据
}
if (n == -1) {
    perror("read error");
    exit(1);
}
```

**write：写入数据到文件**

```c
ssize_t write(int fd, const void *buf, size_t count);
```

**close：关闭文件**

```c
int close(int fd);
```

> ⚠️ `close()` 失败可能导致 fd 泄漏，长期运行会耗尽系统资源。

**lseek：修改文件当前位置**

```c
off_t lseek(int fd, off_t offset, int whence);
```

| `whence` 取值 | 说明 |
|---------------|------|
| `SEEK_SET` | 以文件开头为基准 |
| `SEEK_CUR` | 以当前位置为基准 |
| `SEEK_END` | 以文件末尾为基准 |

## 3. I/O 重定向与文件共享

### 3.1 I/O 重定向

本质是"修改进程文件描述符表的映射关系"，通过 `dup2` 系统调用实现：

```c
int dup2(int oldfd, int newfd);
// 示例：将标准输出重定向到文件
dup2(fd, STDOUT_FILENO);
```

### 3.2 文件共享（三表模型）

| 表 | 作用 | 共享范围 |
|----|------|----------|
| **进程文件描述符表** | 记录 fd 与文件表项的映射 | 每个进程独有 |
| **文件表（打开文件表）** | 记录文件位置、引用计数、访问权限 | 所有进程共享 |
| **v-node 表** | 记录文件元数据（类型、大小、磁盘地址） | 所有进程共享 |

## 4. I/O 性能优化

### 4.1 减少系统调用次数

| 方案 | 说明 |
|------|------|
| **增大缓冲区大小** | 设置为 4KB、8KB（与页大小一致） |
| **批量处理数据** | 避免频繁的小字节读写 |

### 4.2 减少数据拷贝次数

| 方案 | 说明 |
|------|------|
| **内存映射（mmap）** | 将磁盘文件直接映射到进程的虚拟地址空间 |
| **零拷贝（sendfile）** | 数据直接在内核空间传输，无需经过用户空间 |
| **分散-聚集 I/O（readv/writev）** | 一次性读写多个不连续的缓冲区 |

### 4.3 Java I/O 模型

| 模型 | 特点 | 适用场景 |
|------|------|---------|
| **BIO** | 同步阻塞，一连接一线程 | 低并发场景 |
| **NIO** | 同步非阻塞，Selector 多路复用 | 高并发场景 |
| **AIO** | 异步非阻塞，OS 完成后回调 | 高性能场景 |

### 4.4 零拷贝示例（Java）

```java
// 传统方式：数据从磁盘 → 内核缓冲区 → 用户缓冲区 → Socket 缓冲区
// 零拷贝方式：数据从磁盘 → 内核缓冲区 → 直接发送到网络
FileChannel channel = new FileInputStream("file.txt").getChannel();
channel.transferTo(0, channel.size(), socketChannel);
```

## 5. 异常控制流（ECF）

### 5.1 本质定义

**异常控制流（Exceptional Control Flow, ECF）** 是程序执行流程的"非预期跳转"，其本质是系统对"正常执行逻辑被打断"这一场景的统一处理机制。

| 类型 | 特点 | 示例 |
|------|------|------|
| **常规控制流** | PC 按顺序递增，可预测 | if-else、for 循环、函数调用 |
| **异常控制流** | PC 突然跳转到无关地址，不可预测 | 键盘中断、缺页异常、系统调用 |

### 5.2 核心价值

1. **连接硬件与软件**：硬件通过异常触发机制，将外部事件通知给软件
2. **实现多任务并发**：通过定时器中断触发进程上下文切换
3. **处理异常与错误**：通过异常控制流跳转至处理程序，避免程序崩溃

> 🎯 没有异常控制流，就没有现代操作系统的多任务、I/O 响应、错误处理等核心功能。

---

## 6. 四大异常类型

| 异常类型 | 触发方式 | 来源 | 处理结果 | 典型示例 |
|----------|----------|------|----------|----------|
| **中断（Interrupt）** | 异步 | 外部设备 | 返回下一条指令继续执行 | 定时器中断、I/O 中断 |
| **陷阱（Trap）** | 同步 | 应用程序主动触发 | 返回下一条指令继续执行 | 系统调用（`fork`、`execve`） |
| **故障（Fault）** | 同步 | 程序错误指令 | 修复后返回当前指令，否则终止 | 缺页异常、被零除 |
| **终止（Abort）** | 同步 | 严重错误 | 强制终止进程，不返回 | 总线错误、非法指令 |

### 6.1 中断（Interrupt）
- 异步触发，与当前执行的指令无关
- 常见场景：定时器中断（进程切换）、I/O 中断、Ctrl+C

### 6.2 陷阱（Trap）
- 核心应用：所有系统调用都是陷阱的体现
- 核心系统调用原语：`fork()`、`execve()`、`wait()`、`exit()`

### 6.3 故障（Fault）
- 最典型示例：**缺页异常**——访问的虚拟页未加载到物理内存时，缺页处理程序将其从磁盘加载后重新执行指令

### 6.4 终止（Abort）
- 常见场景：总线错误、非法指令、双重故障

### 6.5 异常处理流程

```
异常事件发生 → 获取异常号 → 查询异常表 → 跳转至异常处理程序
```

## 7. 进程与上下文切换

### 7.1 进程的创建与生命周期

| 系统调用 | 作用 |
|----------|------|
| `fork()` | 创建子进程（复制父进程的地址空间） |
| `execve()` | 加载新程序替换当前进程 |
| `waitpid()` | 等待子进程结束 |
| `exit()` | 终止进程 |

### 7.2 上下文切换

**上下文切换的核心流程（由异常控制流驱动）：**

```
触发异常（如定时器中断）
  → 保存当前进程上下文到 PCB
  → 调度器选择下一个就绪进程
  → 恢复新进程的上下文
  → 切换执行
```

> ⚠️ **性能影响**：上下文切换的开销较大，涉及内核态与用户态的切换、上下文的保存与恢复，过多切换会降低系统性能。每次切换约 100~1000 个 CPU 周期。

### 7.3 进程地址空间

```
0xFFFFFFFF  +------------------+
            |  内核空间        |
0xC0000000  +------------------+
            |      栈          |
            +------------------+
            |      堆          |
            |    共享库        |
            |   .bss 段       |
            |   .data 段      |
            |   .text 段      |
0x00000000  +------------------+
```

## 8. 信号机制

### 8.1 信号的本质

信号是**软件层面的异步异常通知**，是操作系统向进程发送的通知机制。

| 信号 | 编号 | 默认行为 | 说明 |
|------|------|----------|------|
| `SIGINT` | 2 | 终止进程 | 键盘 Ctrl+C |
| `SIGSEGV` | 11 | 终止 + Core | 段错误（非法内存访问） |
| `SIGKILL` | 9 | 终止进程 | 不可捕获、不可忽略 |
| `SIGSTOP` | 19 | 暂停进程 | 不可捕获、不可忽略 |
| `SIGPIPE` | 13 | 终止进程 | 向已关闭的管道写数据 |

### 8.2 信号的处理流程

```
信号产生 → 内核在目标进程的信号位图中标记信号
→ 进程从内核态返回用户态时递送信号
→ 进程响应（默认行为 / 忽略 / 自定义处理）
```

### 8.3 关键注意事项

| 要点 | 说明 |
|------|------|
| **不可捕获信号** | `SIGKILL`（9）和 `SIGSTOP`（19）无法被捕获或忽略 |
| **信号掩码** | 通过 `sigprocmask()` 阻塞指定信号 |
| **可重入函数** | 信号处理函数中只能调用可重入函数（如 `write()`） |
| **volatile 与 sig_atomic_t** | 信号处理函数中访问的全局变量需使用 `volatile` 声明 |

## 9. 并发编程概述

### 9.1 并发 vs 并行

| 概念 | 定义 | 硬件要求 |
|------|------|----------|
| **并发（Concurrency）** | 多个逻辑控制流在时间上重叠执行 | 可在单核心 CPU 上实现 |
| **并行（Parallelism）** | 多个逻辑控制流同时真正执行 | 依赖多核 CPU 硬件支持 |

> 💡 并发是"管理多个任务"，并行是"同时执行多个任务"。并发是并行的基础，并行是并发的高级形态。

### 9.2 并行等级

| 并行类型 | 描述 |
|---------|------|
| **指令级并行（ILP）** | 流水线、乱序执行、SIMD |
| **线程级并行（TLP）** | 多核、超线程 |
| **任务级并行（DLP）** | 多服务器、分布式系统 |

## 10. 三种并发实现方法

### 10.1 基于进程的并发

通过 `fork`、`exec`、`waitpid` 等系统调用创建子进程：

| 优点 | 缺点 |
|------|------|
| 资源隔离性好，安全性高 | 进程创建/销毁及上下文切换开销大 |
| 模型清晰易懂 | IPC 通信复杂且效率低 |

> **适用场景**：需要完全隔离资源的场景，如多个独立的应用程序。

### 10.2 基于 I/O 多路复用的并发

通过 `select` / `poll` / `epoll` 在一个进程内调度多个逻辑控制流：

| 优点 | 缺点 |
|------|------|
| 单进程运行，数据共享简单 | 编码复杂，状态机设计难度高 |
| 无进程上下文切换开销 | 无法充分利用多核处理器 |

> **适用场景**：I/O 密集型、并发粒度较大的场景，如高并发网络服务器。

### 10.3 基于线程的并发（最常用）

每个进程启动时默认有一个主线程，通过 `pthread_create` 创建对等线程：

| 优点 | 缺点 |
|------|------|
| 兼具内核自动调度和地址空间共享 | 共享地址空间导致竞态条件、死锁 |
| 线程创建/销毁开销小 | 一个线程崩溃可能导致整个进程崩溃 |

> **适用场景**：通用且高效的并发方案，适用于 CPU 密集型与 I/O 密集型混合的场景。

### 10.4 三种方法对比

| 方案 | 牺牲 | 换取 |
|------|------|------|
| 基于进程 | 效率（高开销） | 安全性（资源隔离） |
| 基于 I/O 多路复用 | 编程复杂度 | 高效率（无进程切换） |
| 基于线程 | 安全风险（竞态条件） | 效率与灵活性的平衡 |

## 11. 线程安全与同步机制

### 11.1 竞态条件

> ⚠️ **竞态条件的本质**：CPU 调度的随机性与共享数据的可修改性的冲突。

例如，两个线程同时对 `count` 执行 `count++` 操作：

```c
// count++ 并非原子操作，拆解为三步：
// 1. 读取 count 到寄存器
// 2. 寄存器 + 1
// 3. 写回 count
// 两个线程可能同时读取到相同值，导致增量小于预期
```

### 11.2 同步机制

#### 信号量（Semaphore）

定义为一个非负整数全局变量，仅能通过 P、V 两种原子操作修改：

| 操作 | 语义 |
|------|------|
| **P 操作** | 信号量 s 减 1，若为负数则当前线程挂起 |
| **V 操作** | 信号量 s 加 1，若有线程挂起则唤醒一个 |

#### 互斥锁（Mutex）

信号量的特殊形式（二元信号量，初始值为 1），保证同一时刻只有一个线程进入临界区。

> 💡 **锁的粒度原则**：粗粒度锁导致线程阻塞频繁，细粒度锁增加管理复杂度，需平衡选择。

#### 条件变量（Condition Variable）

用于解决线程间的"等待-唤醒"协作场景，必须与互斥锁配合使用：

| 接口 | 说明 |
|------|------|
| `wait` | 释放锁 + 阻塞线程（原子操作） |
| `signal` | 唤醒一个阻塞线程 |
| `broadcast` | 唤醒所有阻塞线程 |

### 11.3 死锁

**死锁产生的四个必要条件：**

| 条件 | 说明 |
|------|------|
| **互斥** | 资源只能被一个线程占用 |
| **持有并等待** | 线程持有一个资源的同时，等待另一个资源 |
| **不可剥夺** | 线程已持有的资源不能被强制剥夺 |
| **循环等待** | 多个线程形成循环等待资源的链条 |

**解决方案：**
- **预防**：破坏必要条件（如资源有序分配）
- **检测与恢复**：检测到死锁后终止部分线程释放资源

### 11.4 Java 并发优化建议

| 注意事项 | 说明 |
|----------|------|
| 避免不必要的共享数据 | 使用不可变数据（只读）从根本上避免竞态条件 |
| 合理控制锁的粒度 | 根据共享数据范围选择合适的锁粒度 |
| 避免死锁 | 遵循资源有序分配原则，及时释放锁 |
| 利用 CAS | 使用 `AtomicInteger`、`LongAdder` 减少锁竞争 |
| 避免伪共享 | 使用 `@Contended` 注解或分段技术 |

## 12. 程序性能优化

### 12.1 性能瓶颈的三大来源

| 层面 | 核心瓶颈 | 说明 |
|------|----------|------|
| **硬件层面** | 处理器与内存的性能鸿沟 | CPU 运算速度远快于内存访问速度 |
| **编译器层面** | 优化能力的边界 | 无法处理存储器别名、跨函数优化 |
| **代码层面** | 逻辑冗余与资源浪费 | 循环内重复计算、频繁函数调用 |

### 12.2 代码级优化

| 技巧 | 说明 |
|------|------|
| **消除循环低效率** | 将循环不变操作移到循环外 |
| **减少过程调用** | 内联高频调用的函数 |
| **消除不必要的存储器引用** | 使用局部变量替代全局变量 |
| **循环展开** | 一次处理多个元素，减少迭代次数 |
| **多个累积变量** | 打破数据依赖链，提升指令级并行度 |

```c
// 低效版本
for (int i = 0; i < strlen(s); i++) { }

// 优化版本
int len = strlen(s);
for (int i = 0; i < len; i++) { }
```

### 12.3 性能评估指标

| 指标 | 说明 |
|------|------|
| **执行时间与吞吐量** | 最直观的性能指标 |
| **相对性能（T_old / T_new）** | 衡量优化效果 |
| **每元素的周期数（CPE）** | 衡量循环性能的关键指标 |

### 12.4 Amdahl 定律

> 🎯 **系统某部分加速后，整体性能提升受限于该部分在总执行时间中的占比。**

```
加速比 = 1 / ((1 - 可优化比例) + 可优化比例 / 优化倍数)
```

**核心启示**：遵循"二八定律"——20% 的代码占用 80% 的执行时间，优化的重点应是这 20% 的瓶颈代码。

### 12.5 优化的核心原则

| 原则 | 说明 |
|------|------|
| **正确性优先** | 优化不能改变程序功能 |
| **先测量后优化** | 通过剖析工具（`perf`、`gprof`）定位瓶颈 |
| **注重可移植性** | 避免依赖特定处理器特性的优化 |
| **平衡优化成本** | 过度优化会增加代码复杂度 |

---

## 13. 总结

### 13.1 系统级 IO 核心

| 要点 | 说明 |
|------|------|
| **核心抽象** | 一切皆文件——通过统一的系统调用接口屏蔽设备差异 |
| **底层本质** | 用户态与内核态的交互，上下文切换和数据拷贝是核心开销 |
| **核心 API** | 围绕 fd 掌握 `open`、`read`、`write`、`close`、`lseek` |
| **优化方向** | 减少系统调用、减少数据拷贝、使用缓冲区、非阻塞 IO |

### 13.2 异常控制流核心

```
一个本质：打破程序顺序执行的突发控制流跳转
两个协同：硬件（CPU）负责触发，软件（内核）负责处理
四大类型：中断（异步硬件）、陷阱（系统调用）、故障（可恢复）、终止（致命）
两大机制：上下文切换（多进程并发）、信号（软件异步通知）
```

### 13.3 并发编程核心

```
核心概念（并发与并行）
→ 三种实现方法（进程、I/O 多路复用、线程）
→ 核心痛点（竞态条件、死锁）
→ 同步机制（信号量、互斥锁、条件变量）
```

> 🎯 **性能优化核心思想**：通过消除性能瓶颈、最大化利用系统资源，在不改变程序功能的前提下，实现执行效率的量级提升。性能优化是一个"测量 → 定位 → 优化 → 验证"的闭环过程。
