## 1. 问题定义：为什么需要一致性

### 1.1 不一致从哪里来

每个核心都有私有 L1/L2，同一地址的数据可能同时存在于多个核的缓存中。当核 0 修改了自己的副本，核 1 的旧副本就成了**过期数据（stale）**：

```java
// 两个线程共享同一对象
int x = shared.value;   // 核 0 把 x=0 读进自己的 L1
shared.value = 42;      // 核 1 在自己的 L1 里写了 42（Write-Back，还没落主存）
// 此时核 0 再读 shared.value 仍是 0 —— 不一致！
```

### 1.2 一致性协议的定义

**缓存一致性协议（Cache Coherence Protocol）**：一套规则，保证对同一地址的读写访问在所有核上表现为**串行化顺序**——即存在一个全局视角下"先发生的写先被看到"。

注意区分两个概念：

| 概念 | 对象 | 内容 |
|------|------|------|
| **缓存一致性**（Coherence） | 单个地址 | 该地址各核副本永远一致 |
| **内存一致性模型**（Consistency） | 多个地址 | 多地址访问的全局顺序约束（TSO、SC 等） |

> ⚠️ 教科书陷阱：一致性只解决"同一变量各核看到的值相同"，不保证"你写完 a 再写 b，别人先看到 b"——那是内存序（memory ordering）的问题。Java `volatile` 同时管两者。

## 2. 协议状态机演化

### 2.1 MSI：起点

每行三态：**M**odified（已修改）、**S**hared（共享）、**I**nvalid（无效）。缺陷：从 S 升级到 M 必须广播"无效化"，无独占态优化。

### 2.2 MESI：加入 E 态（工业标准）

| 状态 | 含义 | 副本情况 | 写操作 |
|------|------|---------|--------|
| **M** Modified | 本核修改过，数据最新 | 唯一副本 | 直接写，无需广播 |
| **E** Exclusive | 独占但未修改 | 唯一副本 | 直接写（静默升级 M） |
| **S** Shared | 与其他核共享 | 多副本 | 必须先广播无效化 |
| **I** Invalid | 无效 | — | 需重新取数 |

**E 态的价值**：读入后发现无其他副本 → E 态，写时静默变 M，**省掉一次无效化广播**——这对单线程工作负载的收益巨大。

### 2.3 扩展家族

| 协议 | 新增状态 | 解决的问题 | 使用者 |
|------|---------|-----------|--------|
| MOESI | **O**wned | S 态写回时无需"抢总线"（dirty 共享） | AMD（Zen 系） |
| MESIF | **F**orward | 多副本时指定唯一"转发者"，减少响应风暴 | Intel（Nehalem 起） |

**O 态详解**：AMD 中一个核可以把"最新但共享"的数据保持在自己缓存里（O），其他核持有干净副本（S）。写回主存时可以缓行——但**O 行仍是唯一"新数据源头"**，其他核缺失时必须由 O 核供数。

### 2.4 状态全集速查

```
M（Modified）  本核最新，唯一副本，主存过期
E（Exclusive） 本核唯一副本，主存最新
S（Shared）    多核共享，主存最新（MOESI 中 S 不是最新源）
O（Owned）     本核最新，但其他核共享（MOESI 特有，主存过期）
F（Forward）   多核共享中的"指定转发者"（MESIF 特有）
I（Invalid）   无效
```

## 3. 监听式 vs 目录式

### 3.1 两种实现机制对比

| 维度 | 监听（Snooping） | 目录（Directory） |
|------|-----------------|------------------|
| 原理 | 所有核监听互连总线上的一切请求 | 目录记录每行的持有者集合，按需定向通知 |
| 通信 | 广播（每个请求全核可见） | 点对点（只通知相关核） |
| 扩展性 | 核数 ≥8-16 即带宽饱和 | 可扩展到数百核 |
| 延迟 | 低（无需查目录） | 略高（先查目录） |
| 代表 | 早期多核、嵌入式 | 现代服务器、异构系统 |

### 3.2 为什么监听式撑不住

```
16 核，每核 1 条请求/10 周期 → 总线需承载 16 条/10 周期 = 1.6 条/周期
单周期总线仅能承载 1-2 条 → 饱和，请求排队，延迟雪崩
```

### 3.3 目录的代价与缓解

```
存储开销 ≈ O(核数) 位/行（每个核一位"持有位图"）
512 核、256MB LLC：目录开销约为主存容量的 2%（含稀疏/压缩方案）
```

**稀疏目录（Sparse Directory）**：只为"在缓存中的行"建目录项（LRU 管理），目录容量远小于主存——现代大核 CPU 的实际做法。2025 年芯片化（chiplet）架构进一步升级为**两级目录**（见第 6 节）。

## 4. 状态转换与消息流

### 4.1 核心消息类型

| 消息 | 方向 | 含义 |
|------|------|------|
| Read Miss | 核→总线/目录 | 请求读数据 |
| Write Miss / Invalidate | 核→总线/目录 | 请求写权限 |
| Invalidate Acknowledge | 其他核→请求核 | 确认已作废副本 |
| Data Response | 持有核→请求核 | 供数（O/F/M 核或内存） |

### 4.2 一个完整转换示例：E → M → S → I

```text
① 核 0 读 x，无副本 → 广播 Read Miss → 内存返回数据，核 0 进入 E
② 核 0 写 x → E 静默转 M（无广播，省一次流量）
③ 核 1 读 x → 广播 Read Miss → 目录发现核 0 有 M → 命令核 0 回写并供数
   核 0 数据转 S，核 1 进入 S（两个共享副本）
④ 核 1 写 x → 广播 Invalidate → 核 0 收到后 S→I，核 1 得独占 S→E→M
```

### 4.3 伪共享的协议视角

当两个核各自写同一行的**不同字节**时，协议层面仍按"行"粒度失效——每写一次都触发 Invalidate 广播 + 供数，性能断崖。这引出下一节。

## 5. 伪共享：False Sharing

### 5.1 定义与代价

```java
public class Counter {
    public volatile long countA;   // 核 0 疯狂写
    public volatile long countB;   // 核 1 疯狂写（同一 64B 行！）
}
// 两个字段恰在同一缓存行：每次 countA++ 都会让核 1 的行失效，
// 核 1 重新拉行时又让核 0 的行失效 → 互踢（ping-pong），性能可跌 100 倍
```

**核心机理**：一致性协议以**行**为粒度工作，而并发编程以**字段**为粒度共享。字段相邻 ≠ 共享，但协议不关心——它只看到"行被写"。

### 5.2 检测与修复

**检测**：

```bash
# Linux perf：观察 cache-misses 与 cycles 不成比例地高
perf stat -e cache-misses,cache-references,cycles ./multi_thread_app
# 或使用 perf c2c（cache-to-cache 传输检测）定位具体地址
perf c2c record ./multi_thread_app && perf c2c report
```

**修复三板斧**：

| 手段 | 做法 | 适用 |
|------|------|------|
| 字段填充（padding） | 热字段间填充至行边界（64B 对齐） | 结构体字段级 |
| 线程本地存储（TLS） | 每线程独立计数，最后归并 | 计数器类场景 |
| Java `@Contended` | JDK 内部注解，`-XX:-RestrictContended` 开放 | HotSpot 共享字段 |
| 按核对齐分配 | 每个 CPU 一个对象副本（`ThreadLocal`） | 高争抢热点 |

```java
// Java 8+ 中常见的 padding 手法（等价于 @Contended）
public class PaddedLong {
    public volatile long value;
    public long p1, p2, p3, p4, p5, p6, p7;  // 填充到 64B 边界
}
```

> ⚠️ 伪共享与 `volatile` 关系：普通字段的 false sharing 常被编译优化掩盖（无可见性要求时），但 `volatile`/`AtomicLong` 强制"写即失效"，伪共享被彻底暴露——这也是 `LongAdder`（分段计数）存在的根本原因。

## 6. 现代芯片的一致性实现

### 6.1 拓扑与互连

| 厂商 | 互连结构 | 一致性方式 |
|------|---------|-----------|
| Intel 桌面（ARL） | 环形总线（ring） | 广播 + 分布式 snoop 过滤器，L3 承载目录信息 |
| AMD（Zen 系） | Infinity Fabric + CCD 内互连 | CCD 内监听、CCD 间目录（MOESI 全局） |
| Intel 至强（Xeon） | 网状互连（mesh） | 目录式，按 socket 分段 |
| 双路及以上 | UPI / 跨 socket | NUMA 感知目录，跨 socket 延迟 100ns+ |

### 6.2 Chiplet 时代的两级目录（2025）

单片大核 CPU 的集中目录无法扩展，2025 年研究提出**两级层次目录**：

```
第一级：计算芯粒（CCD）内部 In-Cache 目录——管核间一致性
第二级：I/O 芯粒（IOD）上独立目录——管芯粒间一致性
```

- 目录存储从 O(N²) 降到 O(n²+...)（n=每芯粒核数）
- 新增数据转发机制：读缺失可直接从共享芯粒拿有效副本，降低 LLC 缺失率
- **模块化**：加新芯粒只需换第二级目录，无需重设计协议

### 6.3 CORD（ISCA 2025）：目录侧排序

面向 CPU-GPU 多处理单元：在**目录处**为直写访问定序，消除"源处理器→目录"往返。实测性能 +24%、流量 −13%、硬件开销 <1%。

## 7. 芯片级一致性：CXL 与异构

### 7.1 CXL 缓存一致性

CXL（Compute Express Link）把一致性扩展到**设备**：CXL Type 1/2 设备（加速器、智能网卡）通过 CXL.cache 协议共享主机的缓存一致性域。

2025-2026 研究（HPCA'26 C3）：验证了 MESI-MESI、MESI-MOESI、MESI-MESIF 等异构簇通过 CXL 互连的可行性——**不同厂商、不同协议的簇在 CXL 上统一协调**，这是异构计算一致性的路线图。

### 7.2 一致性 vs 带宽的工程权衡

```
一致性强（MESI 全状态广播）   → 延迟低但扩展差
目录式（定向无效化）          → 扩展好但路径长
CXL 异构一致性                → 统一域但引入设备延迟与安全面
```

> 🎯 **核心要点**：一致性协议是"以行粒度的失效广播换取多核正确性"的工程妥协。理解 MESI 状态机 + 伪共享机理，足以解释 90% 的多核性能问题——它们都是"行粒度"与"字段粒度"错配的表现。
