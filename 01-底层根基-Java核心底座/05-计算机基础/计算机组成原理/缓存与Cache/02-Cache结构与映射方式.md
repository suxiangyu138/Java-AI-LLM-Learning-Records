## 1. 缓存的基本构成单元

### 1.1 Cache Line（缓存行）

缓存与主存交换的最小单位，现代 CPU 统一为 **64 字节**（部分服务器芯片用 128 字节行）。每行包含三部分：

```text
┌────────────┬──────────┬──────────────────────────┐
│ Valid 位   │ Tag 位   │ Data（64 字节，8×8B）      │
│ 是否有效   │ 地址标记  │ 实际数据 + 可选 ECC 校验位  │
└────────────┴──────────┴──────────────────────────┘
```

- **Valid 位**：行是否持有有效数据（刚上电时全无效）
- **Tag 位**：记录该行存储的主存地址高位，用于命中判定
- **Dirty 位**（写回缓存才有）：行数据是否比主存新，决定驱逐时是否回写

### 1.2 三个维度：Line / Set / Way

| 术语 | 含义 | 类比 |
|------|------|------|
| Line | 一行缓存，基本单元 | 房间 |
| Set（组） | 一个候选集合，含若干行 | 楼层 |
| Way（路） | 每组的行数 = 相联度 | 每层房间数 |

```
组相联缓存（4-way）示意图：

  Set 0:  [Line][Line][Line][Line]      ← way 0..3
  Set 1:  [Line][Line][Line][Line]
  ...
  Set 63: [Line][Line][Line][Line]

容量 = Set 数 × Way 数 × 行长
```

## 2. 三种映射方式

### 2.1 直接映射（Direct-Mapped）：1-way

主存地址按 `index = 地址 mod 组数` 固定映射到唯一一行。

```text
优点：硬件极简（只需一次比较）、命中时间最短
缺点：冲突缺失严重——两个频繁访问的地址只要同余就互相驱逐
```

### 2.2 全相联（Fully Associative）：1 set

任意地址可放任意行，只有 Tag 没有 Index。

```text
优点：无冲突缺失（只有容量缺失）
缺点：Tag 比较需要与所有行并行进行，成本随容量线性爆炸
      仅用于 TLB（容量小、对冲突极度敏感）等特殊场景
```

### 2.3 组相联（Set-Associative）：N-way（折中方案）

```
index = 地址 mod 组数；同一组内 N 个位置任选
```

| 映射 | 冲突缺失 | 硬件成本 | 实际应用 |
|------|:---:|:---:|---------|
| 直接映射 | 严重 | 最低 | 早期 CPU、部分指令缓存 |
| 组相联 | 适中 | 适中 | **主流选择（8-16 way）** |
| 全相联 | 无 | 极高 | TLB、Victim Cache |

> 💡 现代所有 CPU 缓存都是组相联。相联度从 4-way（低端 L1）到 16-way（L2/L3）不等；相联度翻倍可显著降低冲突缺失，但成本上升（比较器、选择器面积与功耗）。

## 3. 地址分解与位宽计算

### 3.1 地址三分法

64 位虚拟地址按如下拆解（以 48KB 12-way、64B 行的 L1D 为例）：

```text
┌──────────────────────┬────────────┬────────────┐
│ Tag（高位）           │ Index（组号）│ Offset（行内）│
│ 用于命中判定           │ 选择 Set    │ 行内字节偏移   │
└──────────────────────┴────────────┴────────────┘
```

### 3.2 计算步骤与示例

```
已知：容量 48KB，12-way，行长 64B，地址 64 位

Step 1  Offset = log₂(64) = 6 位
Step 2  每 set 容量 = 12 × 64B = 768B
Step 3  Set 数 = 48KB / 768B = 64 组 → Index = log₂(64) = 6 位
Step 4  Tag = 64 − 6 − 6 = 52 位

Tag 比较位宽 52 位，硬件需要 52 路并行比较器（每 way 一个）
```

**常见配置速查表**：

| 缓存 | 容量 | 相联度 | 行长 | Set 数 | Index | Offset | Tag(64位) |
|------|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| Zen 5 L1D | 48KB | 12-way | 64B | 64 | 6 | 6 | 52 |
| Zen 5 L1I | 32KB | 8-way | 64B | 64 | 6 | 6 | 52 |
| Zen 5 L2 | 1MB | 16-way | 64B | 1024 | 10 | 6 | 48 |
| Zen 5 L3（每 CCD） | 32MB | 16-way | 64B | 32768 | 15 | 6 | 43 |
| Lion Cove L0D | 48KB | 12-way | 64B | 64 | 6 | 6 | 52 |

### 3.3 边界与陷阱

- **行长不是 2 的幂？** 不存在——硬件要求行长、Set 数均为 2 的幂，否则 Index/Offset 无法用位段提取
- **Tag 必须包含完整高位吗？** 是的，否则两个不同地址可能"共行"导致数据错乱；ECC 开销也因此随容量增长
- **Offset 超过行长？** 访问 64B 行内的任意字节都算命中，银行化（banking）设计允许行内多次并行访问

## 4. 相联度与硬件实现的权衡

### 4.1 面积-速度-命中率三角

| 指标 | 提高相联度的影响 |
|------|----------------|
| 冲突缺失率 | 下降（每 Set 候选多） |
| 命中时间 | 上升（选择器变慢，多路 MUX 深度增加） |
| 面积/功耗 | 上升（比较器、存储阵列、替换逻辑） |
| 能量/访问 | 上升（每路都要读 Tag） |

### 4.2 设计权衡的现实答案

- **L1**：追求低延迟 → 中小容量（32-48KB）+ 中相联度（8-12 way）
- **L2**：追求面积效率与低冲突 → 大容量 + 高相联度（16 way）
- **L3**：共享、延迟不敏感 → 超大容量 + 高相联度（16-20 way），容忍更高延迟

> ⚠️ 教科书常混淆：**组数 = 容量 /（相联度 × 行长）**。相联度上升时组数下降、Index 位变少、Tag 位变多——这就是"相联度提高→冲突缺失减少但 Tag 比较变贵"的代数根源。

## 5. 虚拟索引与物理索引

### 5.1 问题的由来

CPU 访存用的是虚拟地址（VA），而缓存里存的是物理地址（PA）对应的数据。索引时机决定了延迟：

| 方案 | 索引 | Tag | 延迟 | 问题 |
|------|------|-----|------|------|
| PIPT | 物理地址 | 物理地址 | 需先做 TLB 翻译（串行，+延迟） | 简单安全，慢 |
| VIPT | 虚拟地址 | 物理地址 | 索引与 TLB 并行 | 页大小 ≥ 缓存大小×相联度时无别名 |
| VIVT | 虚拟地址 | 虚拟地址 | 最快 | 进程切换需清空（上下文换名），现代已弃用 |

### 5.2 同义与异名问题

- **同义（Synonym）**：两个虚拟地址映射同一物理页 → 同一数据可能被缓存两份，写入时需保证一致性
- **异名（Aliasing）**：同一虚拟地址因进程切换映射不同物理页 → 缓存里残留旧进程数据

**消除异名的工程条件**：当 `页大小 ≥ 组相联度 × 行长` 时，同一页内所有地址的 Index 相同（Index 落在页内偏移），VIPT 天然无别名。例如 4KB 页、48KB 12-way L1D：`Index 6 位 + Offset 6 位 = 12 位 < 12 位页偏移`，恰好满足。

```
经典困境：缓存越大 → Index 位越多 → 越容易超出页偏移位 → 
要么缩小缓存、要么提高相联度（减少 Index 位）、要么转 PIPT
```

> 💡 这就是为什么 L1 一直维持"小容量 + 高相联度"：除了延迟，虚拟索引的别名约束也把容量压在了页大小以内。L2/L3 没有此约束（必须等 TLB），可以自由做大。

## 6. 现代微架构中的 Cache 结构实例

### 6.1 AMD Zen 5（2024-2025，数据截至 2025 年发布资料）

| 缓存 | 容量 | 相联度 | 说明 |
|------|:---:|:---:|------|
| L1D | 48KB | 12-way | 3 周期命中，多端口支持 2-3 读 1 写 |
| L1I | 32KB | 8-way | 3 周期命中 |
| L2 | 1MB | 16-way | 每核私有，14 周期 |
| L3 | 32MB/CCD | 16-way | CCD 内共享，约 50 周期；X3D 版叠加至 96MB/CCD |

### 6.2 Intel Lion Cove（Lunar Lake 2024 / Arrow Lake 2025）

| 缓存 | 容量 | 相联度 | 说明 |
|------|:---:|:---:|------|
| L0D | 48KB | 12-way | 新增"第 0 级"数据缓存 |
| L1D | 192KB | 12-way | 社区称为 L1.5；实测吸收大量 L1D 缺失 |
| L1I | 64KB | 16-way | |
| L2 | 2.5MB（LNL）/ 3MB（ARL） | 10-way | 3MB 为全新层级 |
| L3 | 12MB（LNL）/ 36MB（ARL） | — | LNL 无 E 核 L3 访问权 |

> 🎯 **核心要点**：Cache 结构设计 = 在「命中延迟、冲突缺失、面积功耗、虚拟别名」四个约束下求最优解。能徒手算出任意配置的 Tag/Index/Offset 位宽，是组成原理面试的标配技能。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 缓存最小单元？ | 64B 缓存行（Valid + Tag + Data） |
| 主流映射方式？ | 组相联（直接映射冲突多，全相联成本高） |
| 怎么算位宽？ | Offset=log₂行长，Index=log₂组数，Tag=地址宽−Index−Offset |
| 相联度影响什么？ | 冲突缺失↓ vs 命中延迟/面积↑，还有 VIPT 别名约束 |
| VIPT 何时安全？ | 页大小 ≥ 相联度 × 行长 |
