## 1. 为什么需要多级缓存

单级缓存无法同时满足三个目标：

```
延迟要低  → 缓存必须小（近核放置、命中时间短）
容量要大  → 缓存必须大（容纳工作集）
成本要省  → SRAM 面积=芯片面积的 ~50%+，贵
```

多级方案用"每级各司其职"化解矛盾：

| 级别 | 核心使命 | 延迟 | 容量 |
|------|---------|:---:|:---:|
| L1 | 最快响应，拦截 ~90% 访问 | 4-5 周期 | 32-192KB/核 |
| L2 | 弥补 L1 缺失，私有大容量 | 12-15 周期 | 1-3MB/核 |
| L3 (LLC) | 跨核共享、过滤 DRAM 访问 | 40-80 周期 | 12-192MB |
| 内存侧缓存 | 缓解 DRAM 延迟（部分平台） | ~100 周期 | 8MB-数 GB |

> 💡 判断多级是否有效：**每级缺失率应该阶梯式下降**——L1 缺失率 5-10%、L2 缺失率 30-50%（对 L1 缺失而言）、L3 缺失率 5-20%（对 L2 缺失而言）。若某级几乎不拦截（如 L3 命中率只有 1%），说明工作集超出该级能力，该级就是在白付延迟。

## 2. 三级缓存的职责分工

### 2.1 L1：指令与数据分离

```
L1I（指令缓存）：32-64KB，只读，配合分支预测器预取
L1D（数据缓存）：32-192KB，读写，多端口银行化
```

分离的原因：指令流与数据流局部性模式完全不同；分离让取指与访存并行不冲突。

### 2.2 L2：核内"最后防线"

- 每核私有（Intel）或每核私有（AMD），1-3MB
- 容量大、相联度高（16-way），专门吸收 L1 缺失
- Intel Arrow Lake 将 L2 扩到 3MB/核——用大 L2 换低 L3 依赖（其 L3 延迟实测偏高）

### 2.3 L3/LLC：共享缓存与一致性枢纽

- 多核共享，是核间数据交换的"会合点"（snoop 过滤器通常挂在 LLC 侧）
- 承担协议角色：记录各核持有状态（目录信息常内嵌在 L3 Tag 中）
- 容量：Intel 桌面 36MB、AMD 每 CCD 32MB（X3D 达 96MB）、服务器可达 256MB+

## 3. 包含性模型

| 模型 | 定义 | 优点 | 缺点 | 代表 |
|------|------|------|------|------|
| **Inclusive 包含** | 高层缓存包含低层全部行 | 一致性查询快（看 L3 就知道谁有） | 容量浪费（重复存储） | AMD Zen2+ L3、Intel 老架构 |
| **Exclusive 独占** | 各层存储互不重叠 | 总有效容量最大 | 缺失时数据需"交换"（迁移开销） | Zen 1 L3（victim cache 形态） |
| **Non-inclusive 非包含** | 不完全包含也不完全排除 | 折中，无强制复制 | 一致性查询要逐级查 | 现代 Intel LLC、多数新设计 |

> ⚠️ **两个易错细节**：
> 1. AMD Zen 的 L2 与 L1D 之间是**独占/受害者关系**——L1 驱逐的行进 L2，L2 是 L1 的 victim cache，这与"L2 包含 L1"的直觉相反。
> 2. 包含性缓存的隐蔽陷阱：**高层驱逐会触发低层连带失效**（inclusive invalidation）——L3 容量不足时反而放大 L1 缺失。

## 4. 2025 主流微架构实测

数据来源：Chips and Cheese 等机构实测（2024-2025 发布微架构，检索于 2026-08）。

### 4.1 延迟对比（核心周期数）

| 指标 | AMD Zen 5 | Intel Lion Cove（ARL 285K） | Intel Lion Cove（LNL 200V） |
|------|:---:|:---:|:---:|
| L1 命中 | ~4 周期 | ~4-5 周期 | ~4-5 周期 |
| L2 命中 | ~14 周期 | ~16+ 周期 | ~16+ 周期 |
| L3 命中 | ~50 周期 | **80+ 周期** | ~52 周期 |
| DRAM 访问 | ~484 周期 | **565+ 周期** | — |

### 4.2 容量配置

| 配置 | Zen 5 | Arrow Lake (285K) | Lunar Lake |
|------|:---:|:---:|:---:|
| L0D / L1D | 48KB L1D | 48KB L0 + **192KB L1.5** | 48KB L0 + 192KB L1.5 |
| L1I | 32KB | 64KB | 64KB |
| L2 | 1MB/核 | **3MB/核** | 2.5MB/核 |
| L3 | 32MB/CCD | 36MB | 12MB（P 核簇共享） |
| 特色 | 最快 DRAM 路径 | 最大 L2、L1.5 抢戏 | 8MB 内存侧缓存、E 核无 L3 |

### 4.3 设计哲学差异

- **Zen 5**：中小 L2 + 快 L3 + 快 DRAM 路径，"整体快"
- **Arrow Lake**：超大 L2 + L1.5 吸收局部缺失，掩盖其 L3/DRAM 延迟劣势——实测 525.x264 等负载中 L1.5 甚至取代 L2 成为主要数据源
- **Lunar Lake**：L3 延迟最低但容量小，E 核无 L3 且远离环形总线，大工作集负载性能骤降（520.omnetpp 较 ARL 同核慢 45%）

> 🎯 **启示**：缓存层级设计没有唯一正解——"总容量 vs 各级延迟"是每代产品的权衡点。理解延迟/容量矩阵比死记数字重要（数字每代都变）。

## 5. 预取与带宽

### 5.1 硬件预取（无需代码配合）

| 预取器 | 检测模式 | 备注 |
|--------|---------|------|
| Stream | 连续地址流 | L1/L2 标配 |
| Stride | 固定步长 | 覆盖矩阵行遍历 |
| 下一行（Next-Line） | 顺序读取 | 最简单，几乎零误判 |

### 5.2 软件预取

```c
// x86: prefetcht0 预取到 L1；prefetcht1/t2 预取到 L2/L3
for (int i = 0; i < N; i++) {
    __builtin_prefetch(&data[i + 64]);   // 提前 64 次迭代预取
    process(data[i]);
}
```

**Java 无标准预取指令**（JIT 会针对循环自动插入），但 `-XX:+UsePrefetch` 等 JVM 标志与 JIT 的循环优化（loop unrolling）可产生等效效果。

### 5.3 带宽墙

```
单核带宽需求：4 GHz × 每周期取 32B 指令 + 2×16B 数据 = 约 32-64 GB/s
单核 DRAM 带宽配额：L3 缺失占比虽低，但峰值仅 ~1/核共享的 50-100 GB/s
```

多核聚合时 LLC 成为带宽瓶颈——**L3 命中带宽远高于 DRAM 带宽**（L3 内带宽可达 1TB/s 级），所以"尽量让数据死在 L3 里"是并行优化第一原则。

## 6. 性能度量：从 perf 数据定位问题

### 6.1 关键指标

| 指标 | 含义 | 健康值 |
|------|------|--------|
| L1D 命中率 | 数据访问局部性 | >90% |
| LLC (L3) 命中率 | 工作集 vs 容量 | >60%（依赖负载） |
| MPKI（每千指令缺失数） | 归一化的缺失率 | 越低越好；>10 需警惕 |
| 带宽利用率 | DRAM 读/写带宽占用 | <80% 否则受带宽墙限制 |

### 6.2 使用 perf 定位

```bash
perf stat -e cycles,instructions,cache-references,cache-misses,stalled-cycles-frontend,stalled-cycles-backend ./app

# 归一化：每千指令缺失数
perf stat -e cache-misses,instructions ./app | awk '{print $1/1000}'
```

**分析流程**：

```
① stalled-cycles-backend 高 + cache-misses 高
   → 内存延迟敏感：看工作集/局部性/预取
② L3 命中率低但 L1 命中率正常
   → 工作集 > L3 容量：分块（blocking/tiling）
③ 多线程下 cache-misses 高但单线程正常
   → 伪共享或 NUMA 失衡（见 05-缓存一致性协议）
④ 带宽接近上限
   → 数据压缩、SoA 布局、减少不必要的拷贝
```

## 7. 缓存优化技术实战

### 7.1 循环分块（Cache Blocking / Tiling）

```java
// 矩阵乘法 C = A × B，朴素实现每访问 B 的列都跨行（缓存行利用率 1/N）
// 分块：把计算切成 tile×tile 的子块，让子块全部驻留 L1/L2
for (int ii = 0; ii < N; ii += TILE)
    for (int jj = 0; jj < N; jj += TILE)
        for (int kk = 0; kk < N; kk += TILE)
            for (int i = ii; i < ii + TILE; i++)
                for (int j = jj; j < jj + TILE; j++)
                    for (int k = kk; k < kk + TILE; k++)
                        C[i][j] += A[i][k] * B[k][j];
// TILE 取 16-64，使 A/B 子块尺寸 ≈ 2×TILE²×8B 匹配 L1 容量
```

> 💡 分块大小的黄金法则：**子块集合（A 块 + B 块 + C 块）总大小应 ≤ L2 容量的一半**（留出预取与其他数据余量）。

### 7.2 数据布局

| 技术 | 原理 | 典型收益 |
|------|------|---------|
| 结构体拆分（Hot/Cold split） | 热字段聚到同一行 | 行利用率翻倍 |
| SoA vs AoS | 同类字段连续 | 遍历时行利用率 100% |
| 字段重排（按访问频率） | 冷字段垫到行尾 | 减少不必要加载 |
| 大页（HugePages） | 减少 TLB 缺失 | 大工作集性能 +10-30% |
| `@Contended`（Java） | 消除伪共享 | 多线程争抢场景显著 |

### 7.3 优化优先级

```
1. 先减访问次数（算法级）      → 缓存优化之前先减少访存总量
2. 再提行利用率（布局级）      → 每个 64B 行都要"物尽其用"
3. 后调访问顺序（循环级）      → 分块、交换、融合
4. 最后考虑预取（提示级）      → 软件预取是最后的武器
```

> 🎯 **核心要点**：多级缓存优化的本质是"让每级缓存拦截自己该拦的访问"——L1 拦时间局部性，L3 拦共享工作集，DRAM 只碰强制缺失。perf 数据告诉你哪级失守，优化技术负责补位。
