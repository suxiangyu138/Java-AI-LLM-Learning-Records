## 1. 侧信道的基础：缓存时序差异

### 1.1 一切攻击的根基

缓存命中与缺失存在 **50-200 倍**的时序差：

```text
L1 命中：~1ns        DRAM 缺失：~60-100ns
```

攻击者只要能在自己的进程中精确测量一次内存访问的耗时，就能**推断受害者进程的访存足迹**——而访存足迹往往与密钥位、隐私数据直接相关。

### 1.2 攻击者的视角

攻击者在同一物理机上运行恶意代码（云租户、浏览器 JS、恶意 App），通过共享缓存侧信道把"受害者是否访问过地址 X"这一信息，转换为时间测量。共享载体包括：L3（跨核共享）、TLB、分支预测器、存储缓冲区。

> 💡 侧信道本质：**不读数据，只读"痕迹"**。攻击者合法地访问自己的内存，从中提取受害者的秘密。

## 2. 三大经典攻击原语

| 原语 | 流程 | 特点 | 典型用途 |
|------|------|------|---------|
| **Flush+Reload** | ① `clflush` 清掉共享行 ② 受害者运行 ③ 重读该行计时 | 命中→受害者访问过 | 密文索引追踪（AES）、按键记录 |
| **Prime+Probe** | ① 攻击者填满缓存组（Prime）② 受害者运行 ③ 重新访问探测（Probe） | 无需共享内存，测量组占用 | 云环境跨租户攻击 |
| **Evict+Time** | ① 驱逐目标行 ② 受害者运行 ③ 测受害者耗时 | 无需 clflush，测受害者而非自己 | 早期 Spectre 变体 |

```text
Flush+Reload 判定逻辑：
  t = measure(load(secret_addr))
  t < 阈值 → 命中 → 受害者（或先前加载路径）访问过该地址 → 秘密位 = 1
  t > 阈值 → 缺失 → 未访问 → 秘密位 = 0
```

**现代测量困境**：浏览器/OS 限制高精度定时器（`performance.now()` 加抖动、禁止 `rdtsc` 直读）后，攻击者转向测量"被驱逐后自身访问耗时"等间接方式——详见第 6 节 ExfilState。

## 3. Spectre 与 Meltdown

### 3.1 Meltdown（CVE-2017-5754）：越权读内核

**机理**：乱序执行在权限检查完成前就加载了内核地址的数据（加载微操作完成后才抛出异常），数据虽未提交，但**残留在了缓存中**——异常处理后缓存痕迹仍在，用 Flush+Reload 取回。

```
用户态读取内核地址 → 乱序加载（数据进缓存）→ 权限异常（丢弃结果）
→ 攻击者用侧信道从缓存中恢复数据 → 内核内存泄漏
```

**缓解**：KPTI（内核页表隔离）——内核地址映射从用户页表中移除，用户态根本无法发起"可侧信道的访问"。

### 3.2 Spectre（CVE-2017-5753/5715）：训练分支预测器

**机理**：不碰权限边界，而是**利用分支预测**：预测器被训练成"走错误分支"，错走的路径上执行了越界访问，其缓存痕迹被侧信道读取。

```
① 训练：多次传入合法 index，让分支预测器"记住"会通过
② 攻击：传入越界 index，CPU 仍按预测通过（推测执行）
③ 分支内用越界数据索引数组 → 该数组对应行被载入缓存
④ 分支回退，结果作废——但缓存痕迹留下
⑤ Flush+Reload 找出是哪一行被加载 → 恢复越界数据
```

**Spectre 不绕过权限检查**，它把"被检查的边界"骗过去——所以 KPTI 对它无效，需要另一套缓解。

### 3.3 变体谱系（截至 2025，Arm 安全公告口径）

| 变体 | CVE | 名称 | 缓解状态 |
|------|-----|------|---------|
| V1 | CVE-2017-5753 | 边界检查绕过 | 仍需软件缓解（`nospec` 指令序列） |
| V2 | CVE-2017-5715 | 分支目标注入 | 新核心仅需跨上下文保护 |
| V3 | CVE-2017-5754 | Meltdown | KPTI/KVAS |
| V4 | CVE-2018-3639 | 推测存储绕过 | 风险下调，缓解可选 |
| — | CVE-2022-23960 | Spectre-BHB（分支历史注入） | 新核心仅需跨上下文保护 |

> ⚠️ 注意：多数现代核心已硬件修复 Meltdown 与 V2 的跨上下文攻击，但 **V1（边界检查绕过）至今没有硬件彻底解法**——任何新核心的推测路径上仍要做软件级 `csdb`/`lfence` 防护。

## 4. 完整攻击链示例

以 Spectre-V1 读取越界数组为蓝本（教学简化版）：

```c
// 受害者侧（存在漏洞的代码）
if (idx < array1_size) {              // 边界检查
    temp &= array2[array1[idx] * 64]; // 推测执行路径：idx 越界时仍执行！
}
```

```text
攻击步骤：
Step 1  Flush array2 的所有缓存行（清空痕迹基准）
Step 2  反复调用 victim(合法 idx) 训练分支预测器
Step 3  调用 victim(恶意 idx)：CPU 推测执行，把 array1[idx] 的值
        变成 array2 的偏移 → 对应行被载入缓存
Step 4  顺序重读 array2 每行计时 → 唯一命中行 = 越界数据值
Step 5  重复（每次恢复 1 字节），逐字节拖出目标内存
```

**浏览器场景（2018 年真实威胁）**：网页 JS 用 `performance.now()` 计时，跨域读取浏览器内核内存——这是当年 Chrome 紧急上线 Site Isolation、Firefox 默认禁用 SharedArrayBuffer 的直接原因。

## 5. 缓解措施与性能代价

### 5.1 缓解矩阵

| 层次 | 手段 | 针对 |
|------|------|------|
| 微码/固件 | 分支预测器刷新（IBRS/STIBP）、`lfence` 序列 | V2、V1 |
| OS 内核 | KPTI 页表隔离 | V3 Meltdown |
| 编译器 | Retpoline（返回指令替代间接跳转） | V2 |
| 浏览器 | Site Isolation、计时器降精度、禁 SharedArrayBuffer | 网页侧信道 |
| 硬件（研究） | IOS（Squash 时失效）、Pre-cache（2025） | 推测路径缓存污染 |
| 硬件（新核心） | 推测路径不写入缓存（部分设计）、增强分支历史隔离 | V2/BHB |

### 5.2 性能代价（2018 年以来的实测共识）

| 场景 | 代价 |
|------|------|
| 系统调用密集负载 | 10-30% 降速（KPTI 页表切换） |
| 部分微基准（macOS） | 2-4 倍 |
| 早期 Intel 微码 | 稳定性问题被回滚（2018 年 1 月） |
| 浏览器 Site Isolation | 内存占用 +10-13% |

> 💡 权衡本质：**安全缓解是"为每一处推测路径付延迟"**——指令层 `lfence` 串行化流水、KPTI 每次系统调用切换页表、Retpoline 把间接调用变成返回序列。这就是"预测执行换性能、性能又得还回去"的循环。

## 6. 2025 最新进展

### 6.1 AMD 瞬态调度器攻击（TSA，2025）

AMD 公开确认了一类新漏洞，影响 Ryzen（Zen 2/3/4）、Threadripper、EPYC（米兰/热那亚）等全线产品：

- 机理：CPU 在"错误完成"（false completion）状态下按错误数据执行，产生可测量的时序差异
- 影响：泄漏 OS 内核内存与 CPU 内部状态
- 前提：本地访问 + 任意代码执行（非远程/网页可利用）

### 6.2 ExfilState（ACM CCS 2025）：无定时器的侧信道

CISPA 与 Google 的研究：

- 背景：现代 ARM64 系统收紧高精度定时器，传统计时攻击受限
- 方法：**模糊测试自动发现"把缓存状态泄漏进架构状态"的指令序列**——无需计时即可判定缓存命中/缺失
- 覆盖：160 台设备、37 种微架构（手机/笔记本/云服务器）
- 成果：发现 5 个未文档化侧信道（2 个可靠可利用），并演示**无定时器 Spectre 变体**与缓存 AES 密钥恢复

### 6.3 硬件防御研究

| 方案 | 出处 | 思路 |
|------|------|------|
| IOS（Invalidation on Squash） | 2024 | 推测加载被撤销时立即失效对应行，关闭缓存隐藏信道 |
| Pre-cache | 2025-11 | 阻止被撤销指令向缓存写入数据，低开销恢复乱序执行安全 |
| 定时器无关防御 | CCS'25 | 受害算法检测"自身行被驱逐"即中止敏感计算 |

> 🎯 **核心要点**：缓存侧信道没有"补丁了事"的终点——每个新的微架构优化（更激进的推测、更大的缓存、更聪明的预取）都可能引入新信道。2025 年的教训是：**攻击面从"需要精确计时"演进到"无需计时"**，防御也必须从软件补丁前移到微架构设计。

## 7. 对开发者的启示

### 7.1 后端工程视角

- **不要在自研代码里实现加密**（密钥索引模式是经典泄漏源）；用规范库（OpenSSL/BoringSSL，其常数时间实现已抗缓存侧信道）
- 云上敏感数据：理解租户间共享缓存的现实，敏感工作负载用专用实例/机密计算（SGX/SEV）
- JVM 场景：`Random` 类历史上因计时差异被攻击——用 `SecureRandom`；敏感字符串避免 `String.intern()` 共享池
- 伪共享与侧信道同源：都源于"行粒度共享"，`@Contended` 类修复同时兼顾两者
