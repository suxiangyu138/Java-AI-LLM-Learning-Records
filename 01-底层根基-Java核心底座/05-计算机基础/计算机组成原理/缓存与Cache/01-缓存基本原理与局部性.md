## 1. 存储墙：缓存存在的理由

### 1.1 问题的根源：三大存储器性能鸿沟

| 层次 | 典型延迟 | 相对 CPU 周期 | 每 GB 成本 |
|------|---------|--------------|-----------|
| 寄存器 | ~0.3 ns | 1-2 周期 | 极高（芯片内） |
| L1 Cache | ~1 ns | 4-5 周期 | 高（SRAM） |
| L2 Cache | ~3 ns | 12-14 周期 | 中高 |
| L3 Cache | ~10 ns | 40-50 周期 | 中 |
| DRAM 主存 | ~60-80 ns | 200-500 周期 | 低 |
| NVMe SSD | ~10-100 μs | 万-十万周期 | 极低 |

**存储墙（Memory Wall）**：处理器性能自 2000 年代起以每年 ~50% 的速度提升，而 DRAM 延迟每年仅改善 ~5%。差距以指数方式扩大——若完全依赖主存，现代 5GHz CPU 每访问一次内存就要空等约 100 纳秒，即 500 个周期，运算单元绝大部分时间在"发呆"。

> ⚠️ 注意：今天的瓶颈早已不是"计算慢"，而是"等数据慢"。对内存密集型负载，CPU 利用率经常只有 10%-30%，其余时间全部阻塞在访存上。

### 1.2 缓存的解题思路

缓存不降低 DRAM 延迟（物理无法改变），而是**用高速 SRAM 拦截大部分访存请求**：

```
CPU 请求数据
   │
   ├── 命中 Cache（约 90%-99% 的访问）→ ~4-50 周期拿到数据 ✅
   │
   └── 缺失（1%-10% 的访问）→ 下钻到下一层 → 200+ 周期（但不常发生）
```

关键洞察：**只要命中率足够高，平均访存时间就由缓存延迟主导，而非 DRAM 延迟**。而命中率之所以能高，完全依赖局部性原理。

## 2. 局部性原理

### 2.1 两类局部性

| 类型 | 定义 | 典型场景 | 硬件如何利用 |
|------|------|---------|-------------|
| **时间局部性** | 刚被访问的数据短期内还会被访问 | 循环变量、累加器、热点函数 | 行驻留在缓存中等待再次访问 |
| **空间局部性** | 被访问数据附近的数据很快会被访问 | 数组顺序遍历、连续对象字段 | 按 64B 行整块调入，捎带邻居 |

### 2.2 程序局部性示例

```java
// 时间局部性：变量 sum 在每次迭代都被访问
// 空间局部性：data[i] 顺序访问，i 与 i+1 在同一缓存行（或相邻行）
long sum = 0;
for (int i = 0; i < data.length; i++) {
    sum += data[i];          // data 整块从 DRAM 调入，循环期间全部命中 L1
}
```

### 2.3 局部性的定量观察

经典统计数据（90 年代至今依然成立）：

- 程序中 **90% 的执行时间集中在 10% 的代码**上（时间局部性的宏观体现）
- 顺序访问的数组遍历，L1 命中率可超过 **99%**
- 随机访问（如哈希表、指针追逐）命中率可能跌破 50%，性能差 10-100 倍

## 3. 缓存的基本工作模型

### 3.1 命中、缺失与三种缺失

| 术语 | 定义 | 示例 |
|------|------|------|
| 命中 (Hit) | 数据在缓存中，直接返回 | 循环第二次读 sum |
| 缺失 (Miss) | 数据不在缓存，需下钻下一层 | 首次访问 data[i] |
| 强制缺失 (Compulsory) | 数据从未进过缓存，不可避免 | 冷启动访问 |
| 容量缺失 (Capacity) | 缓存装不下工作集，行被驱逐 | 工作集 > 缓存容量 |
| 冲突缺失 (Conflict) | 行因映射约束被驱逐（容量够用） | 两个高冲突地址同组相争 |

> 💡 三种缺失对应三种解法：强制缺失→加大行/预取；容量缺失→加大缓存；冲突缺失→提高相联度。性能优化先诊断"缺的是哪种"。

### 3.2 多级缺失模型

现代缓存是"下一级缓存 + 主存"的多级结构，缺失惩罚是分级的：

```
L1 缺失 → L2（约 10-15 周期）
L2 缺失 → L3（约 40-50 周期，共享）
L3 缺失 → DRAM（约 200-500 周期）
```

每一级缓存的存在都是为了"稀释"下一级的惩罚：L1 拦截 ~90% 的访问，L2 再拦截 L1 缺失的 ~90%，L3 负责跨核共享与再过滤。

## 4. AMAT：量化缓存的收益

### 4.1 核心公式

```
AMAT = 命中时间 (Hit Time) + 缺失率 (Miss Rate) × 缺失惩罚 (Miss Penalty)
```

- **命中时间**：缓存响应一次命中所花时间（含 Tag 比较）
- **缺失率**：访问中未命中的比例
- **缺失惩罚**：缺失后从下一层取数额外花的时间

### 4.2 计算示例：单级 vs 多级

**示例 1：单级 64KB L1，命中时间 2ns，缺失率 5%，DRAM 惩罚 60ns**

```
AMAT = 2 + 0.05 × 60 = 2 + 3 = 5 ns
```

对比无缓存（60ns）提速 12 倍；对比理想缓存（2ns）损失 2.5 倍。命中率只差 1 个百分点（5%→4%），AMAT 变为 `2 + 0.04×60 = 4.4ns`——**缺失率对 AMAT 的贡献与缺失惩罚成正比，惩罚越大越要压缺失率**。

**示例 2：二级缓存（经典教科书题）**

```
L1：命中时间 1ns，缺失率 8%
L2：命中时间 10ns，局部缺失率（L2 未命中 L1 缺失的比例）95%
DRAM 惩罚：100ns

AMAT = 1 + 0.08 × (10 + 0.95 × 100) = 1 + 0.08 × 105 = 9.4 ns
```

无 L2 时 AMAT = `1 + 0.08×100 = 9ns`——看似 L2 反而更慢？注意：**L2 让 DRAM 访问占比从 8% 降到 0.08×0.95=7.6% 的近似水平，真正的收益在更低的全局缺失率场景**（如 L1 缺失率 10%、L2 局部缺失率 50% 时：`1+0.1×(10+0.5×100)=7ns` vs 无 L2 `11ns`）。L2 是否值得，取决于工作集的"两层分离度"。

### 4.3 缺失惩罚为什么如此昂贵

一次 L3 缺失的完整路径（以 Zen 5 实测 ~484 核心周期为例）：

```
发出地址 → 核内 Tag 查询（~4 周期）
→ L2 查询（+10 周期）→ L3 查询（+36 周期）
→ 检测到跨 CCD/跨 socket 需要 → 一致性协议查询（+几十周期）
→ DRAM 行激活 + 列读取（~100+ 周期）
→ 数据沿总线/互连返回（+几十周期）
→ 填充各级缓存（+几周期）
```

> 🎯 **核心要点**：AMAT 的价值在于把"缓存好不好"量化成一个可计算的数。面试与优化实战中，凡是"加了缓存为什么没提速"的问题，都要回归这个公式：要么命中率没上去，要么缺失惩罚没被稀释。

## 5. 程序中的局部性与反例

### 5.1 循环顺序：行优先 vs 列优先

```c
// 假设 M[i][j] 按行存储（row-major），64 字节行 = 16 个 int
// ✅ 行优先遍历：完美空间局部性，命中率 ~100%
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += M[i][j];

// ❌ 列优先遍历：每次访问换一行，命中率 ~1/16，性能差一个数量级
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += M[i][j];
```

这是"循环交换（loop interchange）"优化的底层依据，也是 Java 二维数组 `int[N][N]`（本身是对象数组）性能反直觉的根源之一。

### 5.2 步长与缓存行利用

| 访问模式 | 每 64B 行利用的字节 | L1 命中率（近似） |
|---------|:---:|:---:|
| 顺序步长 4B（int 数组） | 64/64 = 100% | ~99% |
| 步长 64B（跳过整行） | 4/64 ≈ 6% | 低（每行只用一次） |
| 随机访问 | 不适用 | 50% 以下 |

### 5.3 数据结构布局：AoS vs SoA

```text
AoS（Array of Structures）: [x0,y0,z0][x1,y1,z1]... → 只算 x 时每行浪费 2/3
SoA（Structure of Arrays）: [x0,x1,...][y0,y1,...][z0,z1,...] → 全连续，行利用率 100%
```

GPU（CUDA）编程与数据库列式存储（Parquet/ORC）都是 SoA 思想的规模化应用——**列存本质上就是为空间局部性服务的数据布局革命**。

## 6. 缓存的普遍性：局部性的泛化

缓存思想无处不在，理解 CPU Cache 后可以一通百通：

| 场景 | 缓存 | 局部性形式 |
|------|------|-----------|
| CPU | L1/L2/L3 | 指令/数据访问 |
| 内存 | TLB（页表缓存） | 页表项访问的时间局部性 |
| 操作系统 | 页缓存（Page Cache） | 文件读写的局部性 |
| 数据库 | Buffer Pool | 热点行/索引页 |
| 网络 | CDN、HTTP 缓存、Redis | 热点内容的访问聚集 |
| Java 后端 | 本地缓存 + Redis 多级缓存 | 用户维度、商品维度的访问热点 |

> 💡 反向规律：**局部性越强，缓存收益越大；分布越均匀（无热点），缓存越无效**。所有缓存失效的根本原因都一样——访问模式不满足局部性假设。

## 7. 小结

| 要掌握的能力 | 关键内容 |
|------------|---------|
| 解释"为什么要缓存" | 存储墙：CPU 与 DRAM 延迟差距呈指数扩大 |
| 说明缓存为什么有效 | 局部性原理：时间 + 空间，命中率 90%+ |
| 计算缓存性能 | AMAT = 命中时间 + 缺失率 × 缺失惩罚 |
| 区分缺失类型 | 强制 / 容量 / 冲突，对应不同解法 |
| 写出局部性好的代码 | 顺序遍历、行优先、SoA、避免随机指针追逐 |

> 🎯 **核心要点**：缓存是对"DRAM 太慢"这一物理约束的工程投降——既然延迟降不下来，就用高命中率让延迟「平均化」。下一模块进入缓存内部，看它是用什么结构（行/组/路）实现高命中的。
