## 1. 流水线的基本原理

### 1.1 从串行到重叠

```
串行（多周期）：
I1: [取指][译码][执行][访存][写回]
I2:                              [取指][译码][执行][访存][写回]

流水线（5 级重叠）：
I1: [取指][译码][执行][访存][写回]
I2:       [取指][译码][执行][访存][写回]
I3:             [取指][译码][执行][访存][写回]
I4:                   [取指][译码][执行][访存][写回]
```

**关键性质**：
- 稳态下每个时钟完成一条指令 → 吞吐提升 5 倍（5 级）
- 每条指令的延迟（Latency）不变（仍 5 周期），吞吐（Throughput）翻倍
- 加速比上限 = 级数（理想情况）

### 1.2 级间寄存器与级延迟

```text
每级之间插入流水线寄存器（Pipeline Register）：
  作用：暂存本级的输出，供下一级下一个周期使用
代价：每级多 ~1-2 级间延迟（寄存器建立/传输时间）

推论：级数越多，每级逻辑越短 → 频率可以更高
      但级间开销占比越大 → 边际收益递减
```

> 💡 现代核心流水线 15-25 级：理论上级数越多频率越高，但级间寄存器的开销与分支惩罚（错判后 20 级全清）让"过深"得不偿失——这正是"频率路线"（深流水）败给"IPC 路线"（宽发射）的历史原因。

### 1.3 流水线加速比公式

```
理想加速比 = 级数 K
实际加速比 = K × 周期数 / (K × 周期数 + 停顿周期数)
→ 停顿（stall）越多，加速比越接近 1 —— 冒险是流水线的天敌
```

## 2. 三类冒险

| 冒险 | 本质 | 例子 | 消除手段 |
|------|------|------|---------|
| **结构冒险** | 硬件资源不够 | 一条总线取指+访存争用 | 分离缓存/总线、硬件加价 |
| **数据冒险** | 数据依赖 | 上一条结果下一条要用 | 转发、停顿、乱序 |
| **控制冒险** | 分支不知去向 | 分支指令还没算完 | 分支预测、延迟槽 |

> 🎯 一句话记忆：**结构冒险是"抢资源"，数据冒险是"等数据"，控制冒险是"走错路"**——现代 CPU 的微架构设计几乎全是在跟这三兄弟搏斗。

## 3. 数据冒险与转发

### 3.1 三种数据冒险（RAW/WAR/WAW）

以 5 级流水为例：

```asm
add r1, r2, r3    ; 第 5 级写回 r1
sub r4, r1, r5    ; 第 3 级就要读 r1 —— 早了 2 级！
```

| 冒险 | 发生场景 | 现代流水线 |
|------|---------|-----------|
| RAW（读后写） | 后指令读前指令的结果 | **必须解决**（转发+停顿） |
| WAR（写后读） | 后指令写、前指令读同一寄存器 | 乱序中才出现（重命名解决，见下） |
| WAW（写后写） | 两条都写同一寄存器 | 乱序中才出现（重命名解决） |

### 3.2 转发（Forwarding / Bypassing）

```
问题：add 的 ALU 结果第 5 级才写回，sub 第 3 级就要用
解法：把 add 在第 4 级（EX 完成）的结果"抄近路"直送 sub 的 ALU 输入

┌── add 执行级输出 ───────────────┐
│        ↓ 旁路（转发总线）          │
│  sub 执行级 ALU 输入 ←───────────┘
│        ↓
```

**转发覆盖的冒险**：EX→EX、MEM→EX 两类最紧迫的 RAW 全部消除；只剩"Load 结果被立即使用"仍需 1 周期停顿（load-use 冒险）。

```asm
lw   r1, 0(r2)     ; 第 4 级（MEM）才有数据
add  r3, r1, r4    ; 第 3 级就要用 → 转发来不及 → 插 1 个气泡
```

### 3.3 停顿与气泡（Bubble）

```
lw    [取指][译码][执行][访存][写回]
add         [取指][译码]█[执行]...   ← █ = 1 周期气泡（无意义空操作）
```

> ⚠️ 工程经验：load-use 停顿是标量流水线最常见的性能损耗（可占执行时间 5-15%）；现代乱序核心靠"提前发起 load"（OoO 窗口）几乎消除——详见 [03-超标量与乱序执行](03-超标量与乱序执行.md)。

## 4. 控制冒险与分支预测

### 4.1 问题：分支让流水线"不知道该抓哪条指令"

```
beq r1, r2, L      ; 第 4 级（MEM）才知道跳不跳
add r3, r4, r5     ; 若跳转，这条已经白抓了
```

朴素解法（停顿 3 周期）让分支占 20% 的指令付出 60% 的惩罚——不可接受。

### 4.2 分支预测的演进

| 预测器 | 原理 | 准确率 |
|--------|------|:---:|
| 静态预测（向后跳） | 循环向后分支总是跳 | ~60-70% |
| 1 位历史 | 上次跳→这次跳 | ~80% |
| **2 位饱和计数器** | 跳两次才算"倾向于跳" | ~90% |
| 全局历史（GHR） | 用前面分支的模式预测 | ~95% |
| **TAGE（现代标配）** | 多级历史表，长度自适应 | **>97%** |
| 神经预测器（研究） | 感知机预测 | 98%+ 但硬件贵 |

### 4.3 现代预测器组合

```
现代核心 = TAGE 主预测器 + 循环预测器（loop predictor）+ 间接分支预测器
预测正确率 >97% → 分支惩罚分摊到每条指令不足 0.1 周期
实测价值：预测器面积仅占核心 1-2%，贡献 IPC 提升 15-25%
```

**分支目标缓冲（BTB）**：缓存"这条分支跳去哪"——避免每次都要算目标地址。

> 💡 侧信道插曲：预测器状态（GHR 等）是共享资源，可被时序测量推断——Spectre V2/BHB 攻击的载体（详见 `缓存与Cache/06` 模块）。

## 5. 结构冒险与资源设计

### 5.1 经典结构冒险与对策

| 冲突 | 传统问题 | 现代对策 |
|------|---------|---------|
| 取指 vs 访存 | 同一总线 | L1I/L1D 分离（哈佛核心） |
| 寄存器堆读写 | 读口不够 | 多端口寄存器堆（4 读 2 写+） |
| 译码带宽 | 一次只能译一条 | 宽译码器（4-8 宽） |
| 写回冲突 | 多指令同时想写回 | 多写端口 / 乱序写回 |

### 5.2 设计权衡：资源加钱 vs 结构冒险

```
结构冒险的本质是"资源不够"
解法：加资源（面积/功耗）或容忍冒险（停顿）
工程答案：关键路径资源加倍（多端口、双缓存），非关键资源共享
—— 用面积换吞吐是微架构的通用手段
```

## 6. 现代流水线：深度与宽度

### 6.1 现代核心流水线形态（以 Zen 5 为参照）

```text
前端：取指 → 预译码 → 译码 → 分派（每周期 6-8 条）
调度：重命名 → 乱序调度 → 发射（4-8 宽）
执行：整数/浮点/加载/分支多执行单元并行
提交：按序提交 → 精确异常

总深度：约 20-30 级（含分支预测错误惩罚的回滚成本）
```

### 6.2 深流水 vs 宽发射的路线之争（历史）

```
深流水路线（Pentium 4）：31 级 → 频率 3.8GHz，但分支惩罚 31 周期、功耗爆炸
宽发射路线（Athlon 64/酷睿）：12-20 级 → 频率 3GHz，IPC 高 50%+
结局：宽发射胜 —— 2005-2025 所有主流核心都是"中深度 + 宽发射"
2025 现状：频率封顶 ~5GHz，IPC 靠"更宽 + 更聪明"（见 03 模块）
```

### 6.3 流水线的现代挑战

| 挑战 | 表现 | 对策 |
|------|------|------|
| 前端瓶颈 | 取指/译码供不上执行 | uop cache、预译码、宽取指（32B+） |
| 分支惩罚 | 每深 1 级，预测错误代价 +1 | 缩短提交路径、快恢复 |
| 功耗 | 级间寄存器 30%+ 功耗 | 时钟门控、协同调度 |
| 设计复杂度 | 验证困难 | 形式化验证、随机测试 |

> 🎯 **核心要点**：流水线的本质是"用重叠换吞吐、用硬件换停顿"——转发消灭数据冒险、预测消灭控制冒险、多端口消灭结构冒险。读懂冒险三兄弟，就掌握了评估任何 CPU 微架构的框架。
