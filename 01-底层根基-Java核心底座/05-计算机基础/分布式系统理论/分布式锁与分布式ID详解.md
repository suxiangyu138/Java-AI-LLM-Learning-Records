# 分布式锁与分布式ID详解

> 分布式锁保证多节点对共享资源的互斥访问；分布式ID在分布式环境下生成全局唯一标识。二者是分布式系统最常用的基础组件。

## 一、分布式锁

### 1.1 为什么需要分布式锁？

单机锁（synchronized、ReentrantLock）只对同一个 JVM 内的线程有效。分布式环境下，多个服务实例需要互斥访问共享资源（如防止重复扣款、防止缓存击穿时重复查库），必须用分布式锁。

### 1.2 实现方案对比

| 方案 | 原理 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **Redis** | `SET NX PX` + Lua 脚本解锁 | 性能极高、部署简单 | 主从切换可能丢锁 | ⭐⭐⭐⭐⭐ |
| **ZooKeeper** | 临时顺序节点 + Watch | 强一致性、自动释放（Session 过期） | 性能低于 Redis、较重 | ⭐⭐⭐⭐ |
| **etcd** | Lease + 事务 | 强一致性、Raft 协议 | 部署较新、生态待完善 | ⭐⭐⭐⭐ |
| **MySQL** | `INSERT` 唯一索引 + `FOR UPDATE` | 简单、无需额外组件 | 性能差、无自动过期 | ⭐⭐ |

### 1.3 Redis 分布式锁（Redisson 方案）

**基础实现（有缺陷）**：
```java
// 加锁
SET lock_key unique_value NX PX 30000

// 解锁（Lua 脚本保证原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**Redisson 的改进（生产级）**：

| 特性 | 实现方式 |
|------|---------|
| **可重入** | 用 Hash 结构存 `{threadId: count}` |
| **自动续期** | Watch Dog 定时续期，默认每 10s 检查，续到 30s |
| **红锁（RedLock）** | 多 Redis 实例加锁，多数派成功才算成功 |
| **公平锁** | 基于 Redis 队列实现先到先得 |
| **读写锁** | 读读共享、读写互斥 |

### 1.4 ZooKeeper 分布式锁

```
加锁：
  在 /lock 下创建临时顺序节点
  获取 /lock 下所有子节点，按序号排序
  如果自己是最小节点 → 获取锁成功
  如果不是 → Watch 前一个节点

释放：
  删除自己的临时节点 → 触发下一个节点的 Watch
```

| 特性 | 实现方式 |
|------|---------|
| **自动释放** | 客户端断开 → Session 过期 → 临时节点自动删除 |
| **公平性** | 顺序节点天然保证先到先得 |
| **羊群效应** | 只 Watch 前一个节点（不是 Watch 所有）避免惊群 |

### 1.5 分布式锁的常见问题

| 问题 | 说明 | 解决方案 |
|------|------|---------|
| **锁过期** | 业务还没执行完，锁自动过期了 | Redisson Watch Dog 自动续期 |
| **误删锁** | 线程 A 的锁过期，线程 B 获取锁，A 执行完删了 B 的锁 | 解锁前验证 value 是否是自己设置的 |
| **主从丢锁** | Redis 主节点宕机，从节点还未同步锁数据 | RedLock（多实例）/ ZK（强一致） |
| **可重入** | 同一线程多次获取同一把锁 | Hash 记录重入次数 |

## 二、分布式ID

### 2.1 为什么需要分布式ID？

单机用自增主键就行。分库分表后，多个库的自增 ID 会重复 → 需要全局唯一的 ID 生成方案。

### 2.2 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **UUID** | 随机生成 128 位 | 最简单，无依赖 | 无序（B+树插入性能差）、太长、无业务含义 |
| **数据库自增** | MySQL `AUTO_INCREMENT` | 简单、有序 | 单点瓶颈、不适合分库分表 |
| **号段模式** | 每次从 DB 取一个号段，内存分配 | 高性能、有序 | 依赖 DB，号段用完后短暂阻塞 |
| **Snowflake** | 时间戳 + 机器ID + 序列号 | 高性能、趋势递增、去中心化 | 依赖时钟，时钟回拨有问题 |
| **Redis 自增** | `INCR` / `INCRBY` | 简单、高性能 | 持久化可能丢号（RDB 间隔） |
| **美团 Leaf** | 号段 + Snowflake 双模式 | 生产验证、高可用 | 需要部署 Leaf 服务 |

### 2.3 Snowflake（雪花算法）详解

```
64位长整型：
┌─────┬─────────────────────┬───────────┬────────────┐
│ 1位  │      41位           │   10位     │    12位     │
│ 符号 │   毫秒时间戳          │  机器ID    │  序列号      │
│ (0)  │ (约69年，从基准时间)   │ (最多1024) │ (每毫秒4096) │
└─────┴─────────────────────┴───────────┴────────────┘

理论 QPS：4096 / ms ≈ 409.6 万/秒
```

**Snowflake 的时钟回拨问题**：

| 处理策略 | 做法 |
|---------|------|
| **拒绝生成** | 回拨时直接抛异常（简单粗暴） |
| **等待恢复** | 回拨时间短，等待追上上次时间 |
| **备用机器ID** | 回拨时换一个机器ID |
| **扩展位** | 用额外位记录回拨次数（美团 Leaf 方案） |

### 2.4 美团 Leaf 方案

| 模式 | 说明 |
|------|------|
| **Leaf-segment（号段）** | 双 Buffer 优化：当前号段消耗到 10% 时异步加载下一个号段，号段用完时无缝切换 |
| **Leaf-snowflake** | 用 ZooKeeper 持久顺序节点注册 workerID，解决时钟回拨 |

## 三、面试高频问题

**Q1：Redis 分布式锁和 ZK 分布式锁怎么选？**
> 性能优先选 Redis（Redisson），一致性优先选 ZK。大部分场景 Redis 够用（QPS 几千以内），涉及资金安全用 ZK。

**Q2：Redisson 的 Watch Dog 是什么原理？**
> 加锁时默认 leaseTime = -1（不设置过期）→ Watch Dog 每 10s 检查，如果线程还活着且持有锁 → 续期到 30s。保证锁不会在业务执行完之前过期。

**Q3：Snowflake 时钟回拨怎么办？**
> 美团 Leaf 方案：ZK 注册 workerID + 记录上次时间戳。回拨 < 5ms → 等待；回拨 > 5ms → 换新 workerID 或抛异常。

**Q4：分布式 ID 为什么需要趋势递增？**
> MySQL InnoDB 用 B+ 树聚簇索引，递增 ID 插入性能最好（追加到末尾，不分裂页面）。UUID 随机插入导致大量页分裂和磁盘随机 IO。

---

## 📖 核心要点速记

1. **分布式锁**：Redis（性能高/AP）vs ZK（一致性强/CP），按场景选
2. **Redis 锁三要素**：`SET NX PX` + Lua 原子解锁 + Watch Dog 续期
3. **ZK 锁**：临时顺序节点 + Watch 前一个 → 公平锁 + 自动释放
4. **分布式 ID**：Snowflake（趋势递增/去中心化）→ 美团 Leaf（生产验证）
5. **UUID 不推荐**：无序导致 B+ 树性能差
