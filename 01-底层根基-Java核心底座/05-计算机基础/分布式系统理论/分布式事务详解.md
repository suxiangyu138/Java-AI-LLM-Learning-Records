# 分布式事务详解

> 分布式事务解决的是跨多个数据库/服务的操作如何保证原子性——要么全部成功，要么全部回滚。这是分布式系统中最棘手的工程问题之一。

## 一、分布式事务问题来源

### 1.1 场景示例：下单扣库存

```
下单服务（Order）                    库存服务（Inventory）
  │                                       │
  ├─ 插入订单表 ───────── OK                │
  │                                       │
  ├─ 调用库存服务扣库存 ──────────────→ 扣库存失败！
  │                                       │
  ├─ 怎么办？订单已插入，库存没扣           │
  │   → 需要回滚订单                        │
  │   → 但两个操作在不同数据库               │
  └─ 这就是分布式事务问题
```

### 1.2 分布式事务的难点

| 难点 | 说明 |
|------|------|
| **网络不可靠** | RPC 调用可能超时，不知道对方是否执行成功 |
| **部分失败** | 一个服务成功、另一个失败，回滚困难 |
| **并发冲突** | 多个事务同时操作同一数据 |
| **性能代价** | 分布式协调开销远大于单机事务 |

## 二、刚性事务：XA/2PC/3PC

> **刚性事务**：强一致性，遵循 ACID。代表方案是 XA 规范下的 2PC、3PC。

### 2.1 XA 规范

XA 定义了**事务管理器（TM）**和**资源管理器（RM）**之间的接口。
- RM：数据库（MySQL、Oracle 等）
- TM：协调者（应用服务器、事务框架）

### 2.2 两阶段提交（2PC）

```
阶段一：Prepare（投票阶段）
  TM → 所有 RM：Prepare（准备提交，但不真正提交）
  RM → TM：Yes（准备好了）/ No（不行）

阶段二：Commit（提交阶段）
  如果所有 RM 都返回 Yes：
    TM → 所有 RM：Commit（真正提交）
  如果任意 RM 返回 No 或超时：
    TM → 所有 RM：Rollback（全部回滚）
```

### 2.3 2PC 的问题

| 问题 | 说明 |
|------|------|
| **同步阻塞** | Prepare 后 RM 锁住资源，等待 TM 指令，期间其他事务无法访问 |
| **单点故障** | TM 挂了，所有 RM 一直阻塞等待 |
| **数据不一致** | 如果 Commit 阶段 TM 挂了且只发了部分 Commit → 部分提交部分未提交 |
| **保守性** | 一个 RM 失败导致全部回滚，成功率低 |

### 2.4 三阶段提交（3PC）—— 2PC 的改进

增加了**预提交阶段**和**超时机制**：

```
阶段一：CanCommit（询问）
  TM → RM：可以提交吗？
  RM → TM：Yes/No

阶段二：PreCommit（预提交）
  TM → RM：预提交（执行操作但不提交）
  RM → TM：ACK

阶段三：DoCommit（提交）
  TM → RM：最终提交
```

> 3PC 引入超时后 RM 可以自行决定提交或回滚，减少了阻塞。但带来新的不一致风险（部分 RM 超时回滚、部分提交）。实际上 3PC 极少使用。

## 三、柔性事务：TCC/Saga/本地消息表

> **柔性事务**：遵循 BASE 理论，追求最终一致性而非强一致性。互联网主流方案。

### 3.1 TCC（Try-Confirm-Cancel）

| 阶段 | 操作 | 说明 |
|------|------|------|
| **Try** | 资源预留 | 检查 + 锁定资源（冻结库存、预扣余额） |
| **Confirm** | 确认执行 | 真正执行业务（扣减冻结库存） |
| **Cancel** | 回滚补偿 | 释放 Try 阶段预留的资源 |

**示例：下单 + 扣库存 + 扣余额**

```
Try：
  订单服务：创建"处理中"订单
  库存服务：冻结库存（可售库存-1，冻结库存+1）
  余额服务：冻结余额

Confirm（全部 Try 成功）：
  订单服务：订单状态→"已支付"
  库存服务：冻结库存→真正扣减
  余额服务：冻结余额→真正扣减

Cancel（任一 Try 失败）：
  订单服务：订单状态→"已取消"
  库存服务：冻结库存释放
  余额服务：冻结余额释放
```

**TCC 的优缺点**：

| 优点 | 缺点 |
|------|------|
| 无数据库锁，性能高 | 代码侵入性强（每个接口要写 Try/Confirm/Cancel 三套逻辑） |
| 不依赖底层数据库 | 空回滚、悬挂、幂等性问题需要额外处理 |
| 适用于高并发场景 | 业务改造成本高 |

### 3.2 Saga

> 长事务拆分为多个本地事务，每个本地事务有对应的**补偿事务**。本地事务依次执行，失败则逆序执行补偿。

```
正向：T1 → T2 → T3 → ... → Tn
      │    │    │
      ▼    ▼    ▼
补偿：C1 ← C2 ← C3 ← ... ← Cn（反向执行）
```

**两种实现模式**：

| 模式 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **编排式（Choreography）** | 各服务通过事件驱动，自行决定下一步 | 松耦合 | 流程分散，难以追踪 |
| **编排式（Orchestration）** | 中央编排器控制流程 | 集中管控，清晰可追踪 | 编排器成为单点 |

### 3.3 本地消息表 + 最终一致性

> 通过本地消息表保证"业务操作"与"消息发送"的原子性：

```
业务操作 + 插入消息表 → 在同一本地事务中完成
定时任务扫描消息表 → 发送 MQ → 下游消费
下游消费成功后 → 回调更新消息状态/删除消息
```

| 组件 | 作用 |
|------|------|
| 本地消息表 | 保存待发送的消息，与业务数据同库 |
| 定时任务 | 扫描未发送消息，投递到 MQ |
| 消息队列 | 解耦上下游，保证可靠投递 |
| 幂等消费 | 下游做去重，防止重复消费 |

### 3.4 可靠消息最终一致性（RocketMQ 事务消息）

```
半消息（Half Message）：
  Producer → MQ：发半消息（消费者暂不可见）
  Producer → 执行本地事务
  成功 → MQ Commit → 消费者可见
  失败 → MQ Rollback → 消息删除

回查机制：
  MQ 未收到 Commit/Rollback → 回查 Producer
  Producer → 检查本地事务状态 → Commit/Rollback
```

## 四、方案对比与选型

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|---------|
| **XA/2PC** | 强一致 | ⭐ 低 | ⭐ 低 | 传统企业应用，对一致性要求极高 |
| **TCC** | 最终一致 | ⭐⭐⭐⭐ 高 | ⭐⭐⭐⭐ 高 | 高并发扣减（库存、余额） |
| **Saga** | 最终一致 | ⭐⭐⭐ 中 | ⭐⭐⭐ 中 | 长事务流程（订单流程、旅行预订） |
| **本地消息表** | 最终一致 | ⭐⭐⭐ 中 | ⭐⭐ 低 | 简单异步场景（积分发放、通知） |
| **可靠消息** | 最终一致 | ⭐⭐⭐⭐ 高 | ⭐⭐ 低 | 基于 MQ 的异步解耦场景 |

### 选型决策树

```
需要强一致性？
  ├── 是 → XA/2PC（接受性能代价）
  └── 否 → 最终一致性即可
           ├── 同步调用，需要补偿逻辑？
           │     ├── 高并发扣减 → TCC
           │     └── 长流程 → Saga
           └── 异步解耦？
                 ├── 已有 MQ → 可靠消息
                 └── 无 MQ → 本地消息表
```

## 五、主流框架

| 框架 | 支持方案 | 语言 | 特点 |
|------|---------|------|------|
| **Seata** | AT/TCC/Saga/XA | Java | 阿里开源，AT 模式零侵入，国内最流行 |
| **RocketMQ** | 事务消息 | Java | 可靠消息方案 |
| **DTM** | TCC/Saga/XA/二阶段消息 | Go/Java/Python | 跨语言支持，Go 生态首选 |
| **EasyTransaction** | TCC/可靠消息/补偿 | Java | 轻量级 |
| **ByteTCC** | TCC | Java | 轻量 TCC 框架 |

### Seata AT 模式原理（零侵入）

```
一阶段：
  业务 SQL + 回滚日志（undo_log）在同一本地事务中提交
  → 自动生成反向 SQL（回滚用）

二阶段（异步）：
  全部成功 → 删除 undo_log（异步）
  有失败 → 根据 undo_log 执行反向 SQL → 删除 undo_log
```

> AT 模式通过代理数据源自动记录 undo_log，对业务代码零侵入，是 Java 生态最常用的分布式事务方案。

## 六、面试高频问题

**Q1：2PC 有什么缺点？为什么互联网不用？**
> 同步阻塞（锁资源等协调者）、单点故障（协调者挂了全阻塞）、性能差。互联网追求高并发低延迟，等不起锁。

**Q2：TCC 的"空回滚"和"悬挂"是什么？**
> 空回滚：Try 还没执行（或超时），Cancel 先到了 → Cancel 要能处理"未 Try"的情况。悬挂：Cancel 比 Try 先到，后续 Try 到了不能执行 → Try 要检查是否已 Cancel。

**Q3：你项目里怎么处理分布式事务？**
> 核心业务走本地事务 + MQ 可靠消息 + 下游幂等消费。复杂扣减（资金、库存）用 Seata AT 模式。账务对账做最终一致性兜底。

**Q4：Seata AT 和 TCC 怎么选？**
> AT 零侵入，适合简单 CRUD；TCC 需要手写补偿逻辑，但性能更好、更可控。大部分场景直接用 AT，只有极致性能要求才用 TCC。

## 📖 核心要点速记

1. **刚性 vs 柔性**：2PC（强一致/低性能） vs TCC/Saga（最终一致/高性能）
2. **TCC**：Try 预留 → Confirm 确认 / Cancel 回滚
3. **Saga**：正向流程 + 反向补偿，适合长事务
4. **本地消息表**：业务+消息同库事务 → 定时投递 → 幂等消费
5. **落地方案**：Seata（Java 首选）/ RocketMQ 事务消息 / 自研对账
6. **通用原则**：能不用分布式事务就不用，先考虑业务流程优化
