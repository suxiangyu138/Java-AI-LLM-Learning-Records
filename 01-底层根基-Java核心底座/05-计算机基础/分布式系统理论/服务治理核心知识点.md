## 一、服务发现与注册

### 1.1 为什么需要服务发现？

微服务实例是动态的——扩容缩容、重启、故障迁移，IP 和端口不断变化。服务发现让调用方无需硬编码地址，动态获取可用实例。

### 1.2 核心模型

```
Provider（服务提供者）
    │ 1. 注册（启动时将 IP:Port 注册到注册中心）
    ▼
Registry（注册中心）
    │ 2. 发现（Consumer 查询 Provider 列表）
    ▼
Consumer（服务消费者）
    │
    └─ 3. 调用（直连 Provider，通常客户端负载均衡）
    
    │ 4. 心跳/健康检查（Provider 定期续约）
    ▼
Registry ← Provider 心跳失败 → 剔除不可用实例
```

### 1.3 主流注册中心对比

| 注册中心 | CAP | 健康检查 | 特点 | 生态 |
|---------|-----|---------|------|------|
| **Nacos** | CP+AP | TCP/HTTP/MySQL 三种 | 注册+配置一体化，阿里开源 | Spring Cloud Alibaba |
| **Eureka** | AP | 心跳（客户端主动上报） | 自我保护机制，Netflix 开源（停更） | Spring Cloud Netflix |
| **Consul** | CP | Agent 健康检查 | 健康检查强大，支持多数据中心 | Spring Cloud Consul |
| **ZooKeeper** | CP | 临时节点 + Session | 强一致性，但选主期间不可用 | Dubbo |
| **etcd** | CP | Lease 续约 | 简单可靠，K8s 的核心存储 | gRPC、K8s |

### 1.4 自我保护机制（Eureka）

> 短时间内心跳丢失比例超过阈值（默认 85%）→ 进入自我保护模式，不剔除任何实例。

目的：防止网络抖动导致大规模误剔除。代价：可能调用到故障节点。

## 二、负载均衡

### 2.1 常见算法

| 算法 | 原理 | 适用场景 |
|------|------|---------|
| **随机** | 随机选一个节点 | 节点性能均等 |
| **轮询** | 按顺序轮流转 | 节点性能均等、请求处理时间相近 |
| **加权轮询** | 按权重分配（如 Nginx upstream weight） | 节点性能不均衡 |
| **最小连接数** | 选当前活跃连接最少的节点 | 长连接、处理时间差异大 |
| **一致性哈希** | 相同 key 路由到同一个节点 | 缓存亲和性、有状态服务 |
| **最快响应** | 选历史响应时间最短的 | 对延迟敏感 |

### 2.2 客户端 vs 服务端负载均衡

| 对比维度 | 客户端负载均衡 | 服务端负载均衡 |
|---------|--------------|--------------|
| 代表实现 | Ribbon、LoadBalancer（Spring Cloud） | Nginx、F5、LVS |
| 负载均衡位置 | 调用方进程中 | 独立中间层 |
| 优点 | 无额外网络跳转，延迟低 | 集中管控，跨语言通用 |
| 缺点 | 多语言需各自实现 | 额外一跳，增加延迟 |
| 典型架构 | Spring Cloud + Ribbon | Nginx 反向代理 |

## 三、限流

### 3.1 为什么需要限流？

防止突发流量打垮系统——如秒杀、爬虫、恶意攻击。

### 3.2 常见算法

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **固定窗口** | 每个时间窗口（如 1s）内最多 N 个请求 | 简单 | 边界突发（窗口交界处两倍流量） |
| **滑动窗口** | 细分窗口，统计最近一个完整窗口的请求数 | 平滑 | 内存消耗略大 |
| **漏桶** | 请求先进桶，固定速率流出 | 严格平滑输出 | 无法应对突发流量 |
| **令牌桶** | 固定速率生成令牌，请求需获取令牌 | 允许一定突发 | 实现稍复杂 |
| **滑动日志** | 记录每次请求时间戳，精确到毫秒 | 精确 | 内存消耗大 |

### 3.3 令牌桶详解（最常用）

```
令牌桶容量 = burst
令牌生成速率 = rate（个/秒）

请求 → 需要 1 个令牌
  有令牌 → 取令牌，放行
  无令牌 → 限流拒绝

例：rate=100/s, burst=200
  正常：每秒 100 个请求
  突发：如果桶满了，瞬间可以处理 200 个
```

### 3.4 主流实现

| 方案 | 类型 | 适用场景 |
|------|------|---------|
| **Guava RateLimiter** | 单机令牌桶 | 单服务限流 |
| **Sentinel** | 分布式 + 单机 | 阿里开源，功能最全（限流+熔断+降级） |
| **Redis + Lua** | 分布式滑动窗口 | 分布式限流（如 Nginx + Redis） |
| **Nginx limit_req** | 漏桶 | 网关层限流 |
| **网关限流** | Kong/APISIX 插件 | API 级别限流 |

## 四、熔断与降级

### 4.1 核心概念

| 概念 | 含义 | 目的 |
|------|------|------|
| **熔断** | 下游故障时，快速失败不再调用，防止级联故障 | 保护系统 |
| **降级** | 核心功能不可用时，返回兜底结果 | 保证基本可用 |
| **限流** | 超过阈值拒绝请求 | 防止过载 |

### 4.2 熔断器状态机

```
         失败次数达阈值
  ┌────────┐              ┌─────────┐
  │ CLOSED │ ───────────→ │  OPEN   │
  │ (正常)  │              │ (熔断)   │
  └────────┘              └────┬─────┘
       ▲                       │
       │              等待时间窗口过期
       │          ┌────────────┘
       │          ▼
       │    ┌──────────┐
       └─── │HALF_OPEN │
            │ (试探)    │
            └──────────┘
              放少量请求试探
              成功 → CLOSED
              失败 → OPEN
```

### 4.3 主流框架

| 框架 | 特点 |
|------|------|
| **Sentinel** | 阿里开源，限流+熔断+降级+系统自适应保护，Dashboard 可视化 |
| **Hystrix** | Netflix 开源（已停更），线程池隔离/信号量隔离 |
| **Resilience4j** | 轻量级，Java 函数式编程，Hystrix 替代品 |
| **Sentinel vs Hystrix** | Sentinel 性能更好、规则更灵活、有控制台 |

## 五、API 网关

### 5.1 核心功能

| 功能 | 说明 |
|------|------|
| **路由转发** | 根据 URL/Header 将请求路由到对应服务 |
| **统一鉴权** | 在网关层验证 Token，无需每个服务各自校验 |
| **限流熔断** | 网关层防护，不把压力传导到后端 |
| **日志监控** | 统一记录请求日志、耗时统计 |
| **协议转换** | HTTP → gRPC / Dubbo |
| **灰度发布** | 按 Header/Cookie 路由到不同版本服务 |

### 5.2 主流网关对比

| 网关 | 语言 | 特点 | 性能 |
|------|------|------|------|
| **Spring Cloud Gateway** | Java | WebFlux 异步非阻塞，Spring 生态 | 中 |
| **Kong** | OpenResty(Lua) | 插件丰富，企业级 | 高 |
| **APISIX** | OpenResty(Lua) | 性能和功能均优于 Kong | 高 |
| **Zuul 1.x** | Java | 同步阻塞（已淘汰） | 低 |
| **Nginx** | C | 反向代理+负载均衡，基础网关 | 极高 |

## 七、面试高频问题

**Q1：Sentinel 和 Hystrix 的区别？**
> Hystrix 已停更。Sentinel 支持更多规则（热点参数、系统规则）、有控制台实时监控、性能更好（无额外线程池开销）。

**Q2：Nacos 和 Eureka 的区别？**
> Nacos 支持 CP+AP 双模式、配置中心一体化；Eureka 仅 AP、仅注册中心、已停更。新项目无脑选 Nacos。

**Q3：服务发现中，注册中心挂了怎么办？**
> 客户端有本地缓存（服务列表），可以继续用缓存通信。但新实例无法注册、故障实例无法剔除。

**Q4：一致性哈希在负载均衡中怎么用？**
> 将节点 hash 值映射到环上，请求 key 的 hash 落在某个节点区间就路由到该节点。节点增减只影响相邻节点，适合有状态服务（如缓存取模）。

## 📖 核心要点速记

1. **服务发现**：Nacos（首选）> Consul > Eureka（退役）
2. **负载均衡**：客户端（Ribbon/LoadBalancer）vs 服务端（Nginx）
3. **限流**：令牌桶（最常用）→ Sentinel / Guava RateLimiter
4. **熔断**：CLOSED → OPEN → HALF_OPEN → CLOSED
5. **网关**：Spring Cloud Gateway（Java）/ APISIX（高性能）
6. **配置中心**：Nacos（轻量）/ Apollo（功能强）
