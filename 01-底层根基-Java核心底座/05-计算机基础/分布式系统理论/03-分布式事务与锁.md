# 分布式事务与锁
> 分布式事务解决跨服务/跨库操作的原子性问题；分布式锁解决多节点互斥访问共享资源的问题。两者都是分布式系统中最棘手的工程问题。

## 1. 分布式事务概述

### 1.1 场景示例：下单扣库存

```
下单服务（Order）                    库存服务（Inventory）
  │                                       │
  ├─ 插入订单表 ───────── OK               │
  │                                       │
  ├─ 调用库存服务扣库存 ──────────────→ 扣库存失败！
  │                                       │
  ├─ 怎么办？订单已插入，库存没扣           │
  │   → 需要回滚订单                        │
  │   → 但两个操作在不同数据库               │
  └─ 这就是分布式事务问题
```

### 1.2 分布式事务的难点

| 难点 | 说明 |
|------|------|
| **网络不可靠** | RPC 调用可能超时，不知道对方是否执行成功 |
| **部分失败** | 一个服务成功、另一个失败，回滚困难 |
| **并发冲突** | 多个事务同时操作同一数据 |
| **性能代价** | 分布式协调开销远大于单机事务 |

## 2. 刚性事务：XA/2PC/3PC

> **刚性事务**：强一致性，遵循 ACID。代表方案是 XA 规范下的 2PC、3PC。

### 2.1 XA 规范

XA 定义了**事务管理器（TM）**和**资源管理器（RM）**之间的接口。

| 角色 | 说明 |
|------|------|
| **RM（Resource Manager）** | 数据库（MySQL、Oracle 等） |
| **TM（Transaction Manager）** | 协调者（应用服务器、事务框架） |

### 2.2 两阶段提交（2PC）

```
阶段一：Prepare（投票阶段）
  TM → 所有 RM：Prepare（准备提交，但不真正提交）
  RM → TM：Yes（准备好了）/ No（不行）

阶段二：Commit（提交阶段）
  如果所有 RM 都返回 Yes：
    TM → 所有 RM：Commit（真正提交）
  如果任意 RM 返回 No 或超时：
    TM → 所有 RM：Rollback（全部回滚）
```

### 2.3 2PC 的问题

| 问题 | 说明 |
|------|------|
| **同步阻塞** | Prepare 后 RM 锁住资源，等待 TM 指令，期间其他事务无法访问 |
| **单点故障** | TM 挂了，所有 RM 一直阻塞等待 |
| **数据不一致** | Commit 阶段 TM 挂了且只发了部分 Commit → 部分提交部分未提交 |
| **保守性** | 一个 RM 失败导致全部回滚，成功率低 |

### 2.4 三阶段提交（3PC）

增加了**预提交阶段**和**超时机制**：

```
阶段一：CanCommit（询问）
  TM → RM：可以提交吗？
  RM → TM：Yes/No

阶段二：PreCommit（预提交）
  TM → RM：预提交（执行操作但不提交）
  RM → TM：ACK

阶段三：DoCommit（提交）
  TM → RM：最终提交
```

> 3PC 引入超时后 RM 可以自行决定提交或回滚，减少了阻塞。但带来新的不一致风险（部分 RM 超时回滚、部分提交）。实际上 3PC 极少使用，**面试了解即可**。

## 3. 柔性事务：TCC/Saga/本地消息表

> **柔性事务**：遵循 BASE 理论，追求最终一致性而非强一致性。互联网主流方案。

### 3.1 TCC（Try-Confirm-Cancel）

| 阶段 | 操作 | 说明 |
|------|------|------|
| **Try** | 资源预留 | 检查 + 锁定资源（冻结库存、预扣余额） |
| **Confirm** | 确认执行 | 真正执行业务（扣减冻结库存） |
| **Cancel** | 回滚补偿 | 释放 Try 阶段预留的资源 |

**示例：下单 + 扣库存 + 扣余额**

```
Try：
  订单服务：创建"处理中"订单
  库存服务：冻结库存（可售库存-1，冻结库存+1）
  余额服务：冻结余额

Confirm（全部 Try 成功）：
  订单服务：订单状态→"已支付"
  库存服务：冻结库存→真正扣减
  余额服务：冻结余额→真正扣减

Cancel（任一 Try 失败）：
  订单服务：订单状态→"已取消"
  库存服务：冻结库存释放
  余额服务：冻结余额释放
```

**TCC 的优缺点：**

| 优点 | 缺点 |
|------|------|
| 无数据库锁，性能高 | 代码侵入性强（每个接口要写 Try/Confirm/Cancel 三套逻辑） |
| 不依赖底层数据库 | 空回滚、悬挂、幂等性问题需要额外处理 |
| 适用于高并发场景 | 业务改造成本高 |

> ⚠️ TCC 典型问题：**空回滚**（Cancel 在 Try 之前到达，需识别并忽略）和**悬挂**（Cancel 先到后 Try 才到，需拒绝执行）。

### 3.2 Saga

> 长事务拆分为多个本地事务，每个本地事务有对应的**补偿事务**。本地事务依次执行，失败则逆序执行补偿。

```
正向：T1 → T2 → T3 → ... → Tn
      │    │    │
      ▼    ▼    ▼
补偿：C1 ← C2 ← C3 ← ... ← Cn（反向执行）
```

**两种实现模式：**

| 模式 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **编排式（Choreography）** | 各服务通过事件驱动，自行决定下一步 | 松耦合 | 流程分散，难以追踪 |
| **编排式（Orchestration）** | 中央编排器控制流程 | 集中管控，清晰可追踪 | 编排器成为单点 |

> 注意：中文资料中常将 Orchestration 误译为"编排式"，实际两者都是编排 —— Choreography 是各服务自协调，Orchestration 是中央协调器。

### 3.3 本地消息表 + 最终一致性

> 通过本地消息表保证"业务操作"与"消息发送"的原子性：

```
业务操作 + 插入消息表 → 在同一本地事务中完成
定时任务扫描消息表 → 发送 MQ → 下游消费
下游消费成功后 → 回调更新消息状态/删除消息
```

| 组件 | 作用 |
|------|------|
| 本地消息表 | 保存待发送的消息，与业务数据同库 |
| 定时任务 | 扫描未发送消息，投递到 MQ |
| 消息队列 | 解耦上下游，保证可靠投递 |
| 幂等消费 | 下游做去重，防止重复消费 |

### 3.4 可靠消息最终一致性（RocketMQ 事务消息）

```
半消息（Half Message）：
  Producer → MQ：发半消息（消费者暂不可见）
  Producer → 执行本地事务
  成功 → MQ Commit → 消费者可见
  失败 → MQ Rollback → 消息删除

回查机制：
  MQ 未收到 Commit/Rollback → 回查 Producer
  Producer → 检查本地事务状态 → Commit/Rollback
```

## 4. 方案对比与选型

### 4.1 总体对比

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|---------|
| **XA/2PC** | 强一致 | ⭐ 低 | ⭐ 低 | 传统企业应用，对一致性要求极高 |
| **TCC** | 最终一致 | ⭐⭐⭐⭐ 高 | ⭐⭐⭐⭐ 高 | 高并发扣减（库存、余额） |
| **Saga** | 最终一致 | ⭐⭐⭐ 中 | ⭐⭐⭐ 中 | 长事务流程（订单流程、旅行预订） |
| **本地消息表** | 最终一致 | ⭐⭐⭐ 中 | ⭐⭐ 低 | 简单异步场景（积分发放、通知） |
| **可靠消息** | 最终一致 | ⭐⭐⭐⭐ 高 | ⭐⭐ 低 | 基于 MQ 的异步解耦场景 |

### 4.2 选型决策树

```
需要强一致性？
  ├── 是 → XA/2PC（接受性能代价）
  └── 否 → 最终一致性即可
           ├── 同步调用，需要补偿逻辑？
           │     ├── 高并发扣减 → TCC
           │     └── 长流程 → Saga
           └── 异步解耦？
                 ├── 已有 MQ → 可靠消息
                 └── 无 MQ → 本地消息表
```

## 5. 主流框架

| 框架 | 支持方案 | 语言 | 特点 |
|------|---------|------|------|
| **Seata** | AT/TCC/Saga/XA | Java | 阿里开源，AT 模式零侵入，国内最流行 |
| **RocketMQ** | 事务消息 | Java | 可靠消息方案 |
| **DTM** | TCC/Saga/XA/二阶段消息 | Go/Java/Python | 跨语言支持，Go 生态首选 |
| **EasyTransaction** | TCC/可靠消息/补偿 | Java | 轻量级 |

### Seata AT 模式原理（零侵入）

```
一阶段：
  业务 SQL + 回滚日志（undo_log）在同一本地事务中提交
  → 自动生成反向 SQL（回滚用）

二阶段（异步）：
  全部成功 → 删除 undo_log（异步）
  有失败 → 根据 undo_log 执行反向 SQL → 删除 undo_log
```

> AT 模式通过代理数据源自动记录 undo_log，对业务代码零侵入，是 Java 生态最常用的分布式事务方案。

## 6. 分布式锁

### 6.1 为什么需要分布式锁？

单机锁（synchronized、ReentrantLock）只对同一个 JVM 内的线程有效。分布式环境下，多个服务实例需要互斥访问共享资源（如防止重复扣款、防止缓存击穿时重复查库），必须用分布式锁。

### 6.2 实现方案对比

| 方案 | 原理 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **Redis** | `SET NX PX` + Lua 脚本解锁 | 性能极高、部署简单 | 主从切换可能丢锁 | ⭐⭐⭐⭐⭐ |
| **ZooKeeper** | 临时顺序节点 + Watch | 强一致性、自动释放 | 性能低于 Redis、较重 | ⭐⭐⭐⭐ |
| **etcd** | Lease + 事务 | 强一致性、Raft 协议 | 部署较新、生态待完善 | ⭐⭐⭐⭐ |
| **MySQL** | INSERT 唯一索引 + FOR UPDATE | 简单、无需额外组件 | 性能差、无自动过期 | ⭐⭐ |

### 6.3 Redis 分布式锁（Redisson 方案）

**基础实现：**

```java
// 加锁
SET lock_key unique_value NX PX 30000

// 解锁（Lua 脚本保证原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**Redisson 的改进（生产级）：**

| 特性 | 实现方式 |
|------|---------|
| **可重入** | 用 Hash 结构存 `{threadId: count}` |
| **自动续期** | Watch Dog 定时续期，默认每 10s 检查，续到 30s |
| **红锁（RedLock）** | 多 Redis 实例加锁，多数派成功才算成功 |
| **公平锁** | 基于 Redis 队列实现先到先得 |
| **读写锁** | 读读共享、读写互斥 |

### 6.4 ZooKeeper 分布式锁

```
加锁：
  在 /lock 下创建临时顺序节点
  获取 /lock 下所有子节点，按序号排序
  如果自己是最小节点 → 获取锁成功
  如果不是 → Watch 前一个节点

释放：
  删除自己的临时节点 → 触发下一个节点的 Watch
```

| 特性 | 实现方式 |
|------|---------|
| **自动释放** | 客户端断开 → Session 过期 → 临时节点自动删除 |
| **公平性** | 顺序节点天然保证先到先得 |
| **羊群效应** | 只 Watch 前一个节点（不是 Watch 所有）避免惊群 |

### 6.5 分布式锁的常见问题

| 问题 | 说明 | 解决方案 |
|------|------|---------|
| **锁过期** | 业务还没执行完，锁自动过期了 | Redisson Watch Dog 自动续期 |
| **误删锁** | 线程 A 的锁过期，线程 B 获取锁，A 执行完删了 B 的锁 | 解锁前验证 value 是否是自己设置的 |
| **主从丢锁** | Redis 主节点宕机，从节点还未同步锁数据 | RedLock（多实例）/ ZK（强一致） |
| **可重入** | 同一线程多次获取同一把锁 | Hash 记录重入次数 |

### 6.6 选型建议

> **性能优先**选 Redis（Redisson），**一致性优先**选 ZK（ZooKeeper）。大部分场景 Redis 够用（QPS 几千以内），涉及资金安全用 ZK。

## 7. 分布式 ID

### 7.1 为什么需要分布式 ID？

单机用自增主键就行。分库分表后，多个库的自增 ID 会重复 → 需要全局唯一的 ID 生成方案。

### 7.2 方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **UUID** | 随机生成 128 位 | 最简单，无依赖 | 无序（B+树插入性能差）、太长、无业务含义 |
| **数据库自增** | MySQL AUTO_INCREMENT | 简单、有序 | 单点瓶颈、不适合分库分表 |
| **号段模式** | 每次从 DB 取一个号段，内存分配 | 高性能、有序 | 依赖 DB，号段用完后短暂阻塞 |
| **Snowflake** | 时间戳 + 机器ID + 序列号 | 高性能、趋势递增、去中心化 | 依赖时钟，时钟回拨有问题 |
| **Redis 自增** | INCR / INCRBY | 简单、高性能 | 持久化可能丢号（RDB 间隔） |
| **美团 Leaf** | 号段 + Snowflake 双模式 | 生产验证、高可用 | 需要部署 Leaf 服务 |

### 7.3 Snowflake（雪花算法）

```
64位长整型：
┌─────┬─────────────────────┬───────────┬────────────┐
│ 1位  │      41位           │   10位     │    12位     │
│ 符号 │   毫秒时间戳          │  机器ID    │  序列号      │
│ (0)  │ (约69年，从基准时间)   │ (最多1024) │ (每毫秒4096) │
└─────┴─────────────────────┴───────────┴────────────┘

理论 QPS：4096 / ms ≈ 409.6 万/秒
```

**时钟回拨问题处理策略：**

| 处理策略 | 做法 |
|---------|------|
| **拒绝生成** | 回拨时直接抛异常（简单粗暴） |
| **等待恢复** | 回拨时间短，等待追上上次时间 |
| **备用机器ID** | 回拨时换一个机器ID |
| **扩展位** | 用额外位记录回拨次数（美团 Leaf 方案） |

### 7.4 美团 Leaf 方案

| 模式 | 说明 |
|------|------|
| **Leaf-segment（号段）** | 双 Buffer 优化：当前号段消耗到 10% 时异步加载下一个号段，号段用完时无缝切换 |
| **Leaf-snowflake** | 用 ZooKeeper 持久顺序节点注册 workerID，解决时钟回拨 |

> 💡 为什么需要趋势递增？MySQL InnoDB 用 B+ 树聚簇索引，递增 ID 插入性能最好（追加到末尾，不分裂页面）。UUID 随机插入导致大量页分裂和磁盘随机 IO。

## 📖 核心要点速记

1. **刚性 vs 柔性**：2PC（强一致/低性能） vs TCC/Saga（最终一致/高性能）
2. **TCC**：Try 预留 → Confirm 确认 / Cancel 回滚
3. **Saga**：正向流程 + 反向补偿，适合长事务
4. **本地消息表**：业务+消息同库事务 → 定时投递 → 幂等消费
5. **落地方案**：Seata（Java 首选）/ RocketMQ 事务消息 / 自研对账
6. **分布式锁**：Redis（性能高/AP）vs ZK（一致性强/CP），按场景选
7. **Redis 锁三要素**：SET NX PX + Lua 原子解锁 + Watch Dog 续期
8. **分布式 ID**：Snowflake（趋势递增/去中心化）→ 美团 Leaf（生产验证）
9. **通用原则**：能不用分布式事务就不用，先考虑业务流程优化
