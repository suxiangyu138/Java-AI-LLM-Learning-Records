# CAP 与 BASE 理论详解

> CAP 定理和 BASE 理论是分布式系统的两大基石理论。CAP 告诉我们"鱼和熊掌不可兼得"，BASE 则给出了"退而求其次"的工程实践方案。

## 一、CAP 定理

> 2000年由 Eric Brewer 提出，2002年被证明。一个分布式系统**不可能同时满足**一致性、可用性和分区容错性。

### 1.1 三个维度

| 维度 | 含义 | 通俗解释 |
|------|------|---------|
| **C（Consistency）一致性** | 所有节点同一时刻看到的数据完全相同 | 写完之后，任意节点读到的都是最新数据 |
| **A（Availability）可用性** | 每个非故障节点都能在合理时间内返回合理响应 | 服务一直可用，不会返回错误或超时 |
| **P（Partition Tolerance）分区容错** | 网络分区（节点间通信中断）发生时，系统仍能正常运行 | 部分节点失联，系统不崩溃 |

### 1.2 为什么 CAP 不能三者兼得？

```
场景：两个节点 A、B，网络断开

   如果保证 C（一致性）：
     写 A 成功后，B 必须同步 → 网络断开了 → B 同步失败
     → 只能拒绝写入 → 牺牲了 A（可用性）

   如果保证 A（可用性）：
     写 A 成功即返回，B 暂时不同步 → A 和 B 数据不一致
     → 牺牲了 C（一致性）

   P（分区容错）是分布式系统的必然要求：
     → 网络分区不可避免（交换机故障、网线断、网络抖动）
     → 必须在 C 和 A 之间做取舍
```

### 1.3 CAP 的工程实践

| 选择 | 代表系统 | 做法 | 适用场景 |
|------|---------|------|---------|
| **CP（保一致性）** | ZooKeeper、etcd、Consul | 分区时拒绝写入，牺牲可用性 | 配置中心、服务发现、分布式锁 |
| **AP（保可用性）** | Eureka、Cassandra、DynamoDB | 分区时允许写入，最终一致 | 电商商品展示、社交媒体 feed |
| **CA** | 传统关系型数据库（单机） | 不分区的单机系统 | **不是真正的分布式系统** |

### 1.4 CAP 的常见误解

| 误解 | 正解 |
|------|------|
| "CAP 是三选二" | 不准确。P 是必须保证的（网络分区客观存在），实际是 CP vs AP |
| "放弃了 C 就没有任何一致性" | 放弃的是强一致性，可以通过最终一致性弥补 |
| "CA 系统也是分布式" | CA 系统没有考虑分区容错，本质是单机系统 |

## 二、BASE 理论

> BASE 是 CAP 定理中 AP 方案的延伸，是互联网大规模分布式系统的工程实践总结。

### 2.1 BASE 含义

| 字母 | 全称 | 含义 |
|------|------|------|
| **BA** | Basically Available | 基本可用：允许损失部分可用性（响应时间变长、功能降级），但系统整体可用 |
| **S** | Soft State | 软状态：允许系统中的数据存在中间状态，该状态不影响系统整体可用性 |
| **E** | Eventually Consistent | 最终一致性：不要求数据实时一致，但保证经过一段时间后最终达到一致 |

### 2.2 BASE vs ACID

| 对比维度 | ACID（数据库事务） | BASE（分布式系统） |
|---------|-------------------|-------------------|
| 核心思想 | 强一致性、强约束 | 弱一致性、高可用 |
| 一致性 | 强一致性（写后立即可读） | 最终一致性（可能短暂不一致） |
| 可用性 | 可能牺牲（锁等待） | 高可用优先 |
| 隔离性 | 严格隔离（串行化） | 弱隔离（允许并发冲突） |
| 适用场景 | 金融交易、库存扣减 | 社交网络、内容分发、搜索引擎 |
| 典型实现 | MySQL InnoDB 事务 | DNS、CDN、NoSQL |

### 2.3 最终一致性的五种变体

| 变体 | 含义 | 示例 |
|------|------|------|
| **因果一致性** | 有因果关系的操作按顺序被看到 | 先发帖后评论，所有人看到评论前先看到帖子 |
| **读己之写** | 用户总能读到自己的最新写入 | 发微博后自己刷新立刻看到 |
| **会话一致性** | 同一会话内读到最新值 | 同一浏览器窗口内操作一致 |
| **单调读** | 不会读到比之前更旧的数据 | 刷新不会看到数据"回退" |
| **单调写** | 同一进程的写操作串行化 | 写操作按顺序执行 |

## 三、CAP 到 BASE 的演进

```
CAP 定理（理论）
    │
    ├── CP 路线：ZooKeeper、etcd（配置/协调场景）
    │
    └── AP 路线 →
              │
              BASE 理论（工程实践）
                  │
                  ├── 最终一致性：DNS、CDN、主从复制
                  ├── 柔性事务：TCC、Saga、本地消息表
                  └── 补偿机制：对账、重试、回滚
```

## 四、主流系统的 CAP 分类

| 系统 | 类型 | CAP 选择 | 说明 |
|------|------|---------|------|
| ZooKeeper | 协调服务 | **CP** | 集群半数以上存活才可服务，Leader 挂了选主期间不可用 |
| etcd | 协调服务 | **CP** | Raft 协议，强一致性，选主期间不可写入 |
| Consul | 服务发现 | **CP** | 默认 CP 模式，也有 AP 选项 |
| Eureka | 服务发现 | **AP** | 优先可用，节点挂了不剔除，客户端有本地缓存 |
| Nacos | 配置+发现 | **CP + AP** | 配置中心 CP 模式，服务发现可选 AP 模式 |
| Redis Cluster | 缓存 | **AP** | 主从异步复制，网络分区可能丢数据 |
| MySQL 主从 | 数据库 | **AP** | 异步/半同步复制，从库可能读到旧数据 |
| TiDB | NewSQL | **CP**（默认） | Raft 多副本，强一致性 |
| Cassandra | NoSQL | **AP** | 最终一致性，可调一致级别 |
| MongoDB | NoSQL | **CP**（默认） | 副本集选举，主挂了只读不可写 |

## 五、面试高频问题

**Q1：CAP 为什么不能同时满足？**
> 网络分区发生时，要在一致性和可用性之间取舍——要一致性就得拒绝写入（牺牲可用），要可用性就得接受不一致。

**Q2：说一个你遇到的 CAP 取舍的实际案例？**
> 电商秒杀库存扣减用 Redis（AP）可能出现超卖 → 事后对账补偿；核心扣款走 MySQL 事务（偏 CP）。同一系统不同场景选不同策略。

**Q3：BASE 和 ACID 是什么关系？**
> ACID 是传统单机数据库的事务模型，BASE 是分布式系统的高可用实践总结。现代系统通常是核心业务用 ACID（MySQL），外围业务用 BASE（Redis/Cache/ES 索引异步更新）。

**Q4：Paxos/Raft 解决了 CAP 中的什么问题？**
> 它们解决的是 CP 系统中**如何达成一致性**的问题——用多数派投票机制保证即使部分节点故障，集群仍能就某个值达成一致。

## 📖 核心要点速记

1. **CAP**：P 必须保，C 和 A 二选一 → 不是三选二
2. **CP**：强一致，选主期间不可用（ZooKeeper、etcd）
3. **AP**：高可用，接受最终一致（Eureka、DNS）
4. **BASE**：基本可用 + 软状态 + 最终一致
5. **实战口诀**：钱相关的 CP，体验相关的 AP
