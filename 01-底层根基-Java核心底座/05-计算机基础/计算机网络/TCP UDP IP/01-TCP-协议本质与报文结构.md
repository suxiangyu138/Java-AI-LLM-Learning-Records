# TCP 协议本质与报文结构

> TCP（RFC 9293）提供**可靠的、有序的、面向连接的字节流**服务——它的全部设计（序列号、确认、窗口、重传）都从"字节流"与"不可靠网络"这两个前提出发。理解段结构，是理解后面一切机制（握手/重传/拥塞）的起点

## 1. TCP 的三个本质承诺

```text
① 可靠：发送方确认收到；丢失则重传 —— 应用层"无丢失"的错觉
② 有序：数据按字节序交付 —— 应用层"无乱序"的错觉
③ 字节流：不保留报文边界 —— 应用自己定义消息边界
   （write 3 次可能合并成一个段发送；read 1 次可能收到半个消息）

"面向连接"的另一层含义：
  连接状态（序列号/窗口/拥塞）在两端各自维护，网络中间设备无状态
  → 中间设备（路由器/负载均衡）只转发，不理解 TCP 语义
  → 这正是 QUIC 把状态搬到"连接 ID"上的动机（05 章）
```

> 🎯 **核心要点**：TCP 的"可靠"是**端到端**的（两端负责），不是逐跳的（路由器不管）——这决定了所有机制的落点都在两端的内核协议栈。

| 字段 | 位宽 | 作用 |
|------|:---:|------|
| 源/目的端口 | 16+16 | 四元组之两元（+IP 另两元） |
| **序列号** | 32 | 本报文首字节的字节流编号 |
| **确认号** | 32 | **期望收到**的下一个字节号（= 已收齐 + 1） |
| 头长 | 4 | 首部长度（单位 4 字节，最小 5） |
| 标志位 | 6 | URG/ACK/PSH/RST/SYN/FIN |
| 窗口大小 | 16 | 接收方通告的可用缓冲（最大 65535，需缩放选项） |
| 校验和 | 16 | 伪首部 + 首部 + 数据 |
| 选项 | 可变 | MSS / 窗口缩放 / SACK / 时间戳 |

> ⚠️ **核心记忆点**：确认号是"期望的下一个"，不是"刚收到的最后一个"——`seq=1000, ack=2000` 表示"我已收齐 1999 及之前，请你从 2000 开始发"。

## 3. 序列号与确认号机制

### 3.1 字节流编号

```text
发送 4KB 数据，MSS=1460：
  段1: seq=1,       len=1460 → 覆盖 1..1460
  段2: seq=1461,    len=1460 → 覆盖 1461..2920
  段3: seq=2921,    len=1460 → 覆盖 2921..4380
  收齐 → ack=4381（期望下一个）

序列号不是从 0 开始（ISN 随机化，防伪造与旧连接串扰）
```

### 3.2 累积确认

```text
TCP 确认是"累积式"：ack=N 表示"N 之前全部收到"
  → 中间丢一个段，后续段的确认也停住（即使后来者已到）
  → 这就是"一个包丢失导致后续全等"（重传后才能前进）
  → SACK 选项打破这个限制（03 章）
```

## 4. 常用选项：MSS / 窗口缩放 / SACK / 时间戳

| 选项 | 作用 | 必要性 |
|------|------|--------|
| **MSS** | 通告本端可接收的最大段大小（默认 1460 = 1500 MTU − 20 IP − 20 TCP） | 握手期必带 |
| **窗口缩放**（WS） | 把 16 位窗口放大到 30 位（因子 2^N） | **高 BDP 必需**（08 章） |
| **SACK** | 选择性确认：明确报告"丢了哪段、收到哪段" | 丢包场景高效重传 |
| **时间戳**（TS） | RTT 测量 + 防序列号回绕（PAWS） | 高带宽必需 |
| 快速打开（TFO） | 握手期带数据（0-RTT 前身） | 可选 |

```bash
# 查看本机协商结果
ss -tin | head -20
# 关注：wscale:7（窗口缩放生效） sack（SACK 开启）ts（时间戳）
```

## 5. 四元组与连接标识

```text
TCP 连接 = (源IP, 源端口, 目的IP, 目的端口)
  任一元素不同 = 不同连接
  例：同 IP 同端口，但来源 IP 不同 → 不同连接（服务器可挂百万连接）

推论：
  ① 服务器并发连接数 = 四元组组合数（受端口/fd/内存限制——并发体系 06 章）
  ② NAT 下四元组被改写 → 连接迁移困难（QUIC 用连接 ID 解决）
  ③ 负载均衡按四元组哈希保持连接亲和（并发体系 08 章）
```

## 6. TCP vs UDP：一句话对照

| 维度 | TCP | UDP |
|------|:---:|:---:|
| 可靠性 | 可靠（重传/确认） | 尽力而为 |
| 有序性 | 有序字节流 | 无序数据报 |
| 连接 | 面向连接（三次握手） | 无连接 |
| 拥塞控制 | 有（丢包/延迟感知） | 无（应用自管） |
| 头部 | 20B+（选项多） | 8B |
| 适用 | Web/文件/数据库 | 实时/音视频/DNS/QUIC |

> 💡 **注意**：TCP vs UDP 的完整对比在 05 章展开——此处只需建立"可靠性换实时性"的直觉。

## 7. 应用层消息边界：字节流的"粘包/拆包"问题

### 7.1 问题根源

```text
TCP 是字节流（无消息边界，第 1 节承诺③）：
  发送 3 次 write（各 100B）→ 接收方可能 1 次 read 收 300B（粘包）
  发送 1 次 write（300B）→ 接收方可能分 3 次 read（拆包）

→ 应用层必须自己定义"消息边界"——这是所有 TCP 应用的第一课
```

### 7.2 三种边界方案

| 方案 | 做法 | 优缺点 | 代表 |
|------|------|--------|------|
| 定长消息 | 每条固定 N 字节 | 简单但浪费 | 老旧协议 |
| 分隔符 | 消息以 `\n`/`\r\n` 结束 | 简单；正文不能含分隔符 | HTTP/1.1 头、Redis RESP |
| **长度前缀** | 4 字节长度 + 消息体 | 灵活、主流 | **HTTP/2 帧、MQTT、Netty LengthFieldBasedFrameDecoder** |

```java
// 长度前缀方案（解码端核心逻辑）
ByteBuffer lenBuf = ...;          // 先读 4 字节长度
int len = lenBuf.getInt();
while (bytesRead < len) {         // 拆包：数据没到齐继续等
    ch.read(bodyBuf);
}
handleMessage(bodyBuf);           // 粘包：循环读完所有完整消息

// Netty 直接内置：LengthFieldBasedFrameDecoder(4, 0, 4, 0, 4)
// → 框架层面解决，业务不用手写
```

### 7.3 与 HTTP 的对应

```text
HTTP/1.1：头用 \r\n 分隔 + Content-Length 定义体边界（两种方案混用）
HTTP/2：彻底二进制分帧（9 字节帧头含 Length——长度前缀的标准化）
→ 消息边界方案的选择是应用协议设计的核心决策
```

### 7.4 TCP 头部观察实战（结合 07 章排障）

```text
抓一个 HTTPS 数据包验证本章知识：
  tcpdump -nn 'tcp port 443' -c 5

  观察点：
  ① 源/目的端口（四元组之两元）
  ② seq/ack 递增（字节流编号）
  ③ Flags [P.] 带数据、[.] 纯确认
  ④ Options: (mss 1460, nop, wscale 7, sackOK, ts val ...)

```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. TCP 承诺可靠/有序/字节流——可靠是端到端的（两端内核负责，中间设备无状态）；
> 2. 段结构记忆重点：序列号（首字节编号）、确认号（期望的下一个）、窗口（接收能力通告）；
> 3. 四元组定义连接；MSS/窗口缩放/SACK/时间戳四个选项决定了大带宽时代的性能上限。

**思考题**：

1. 确认号为什么是"期望的下一个"？（→ 2 表 + 3.1）
2. 累积确认的缺点是什么？SACK 怎么补？（→ 3.2）
3. 为什么路由器不理解 TCP 语义？（→ 1 面向连接的含义）
4. 窗口缩放为什么在高带宽长时延场景必须？（→ 4 + 08 章 BDP）
