# UDP 协议深潜

> UDP 只有 8 字节头部与"尽力而为"的承诺——无连接、无重传、无拥塞控制，却因此获得低延迟与高吞吐。它的真正价值不在"裸用"，而在作为**可靠传输的构建底座**：QUIC 在 UDP 上重造了 TCP 的一切（2026 年 HTTP/3 采用已过临界点）

## 1. UDP 的本质：数据报与尽力而为

```text
UDP（RFC 768，1980）的三个"没有"：
  ① 没有连接：发送前无需握手（一发即走）
  ② 没有确认/重传：丢了就丢了（应用自管）
  ③ 没有拥塞控制：发送速率由应用决定（内核不管）

语义：数据报（datagram）——每次 send 是一个独立报文，保留边界
  → 接收方一次 recv 恰好收到一个完整报文（TCP 是字节流，01 章）

价值坐标：
  可靠性 → TCP（Web/文件/数据库）
  实时性 → UDP（音视频/游戏/DNS）
  构建能力 → UDP 之上自己造协议（QUIC）
```

> 🎯 **核心要点**：UDP 不是"残缺的 TCP"，而是"**把控制权交给应用**"的协议——延迟敏感场景，应用宁可自己做丢失处理，也不想要 TCP 的重传抖动。

## 2. 8 字节头部全解

```text
 0                   1                   2                   3
├─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┤
│        源端口（16）        │        目的端口（16）        │
├─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┤
│       长度（16）          │        校验和（16）           │
└─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┘
```

| 字段 | 说明 |
|------|------|
| 源/目的端口 | 同 TCP（四元组标识通信双方） |
| 长度 | UDP 头部+数据总长（最小 8） |
| 校验和 | **可选**（IPv4 下可为 0；IPv6 下必填）——校验整个数据报 |

```text
UDP 校验和覆盖"伪首部 + UDP 头 + 数据"：
  伪首部 = 源IP/目的IP/协议号/长度（从 IP 头借来）
  → 防止 IP 地址错配（校验和跨层验证）
```

## 3. UDP vs TCP：全维度对比

| 维度 | TCP | UDP |
|------|:---:|:---:|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 确认+重传 | 尽力而为 |
| 有序性 | 有序字节流 | 无序数据报 |
| 拥塞控制 | 有（cwnd 动态） | 无（应用自管） |
| 流量控制 | 有（rwnd 通告） | 无 |
| 头部 | 20B+（选项） | **8B** |
| 状态 | 每连接内核状态 | 无状态（内核不维护） |
| 单包开销 | 高（握手/确认） | 低（一发即走） |
| 实时性 | 重传抖动（延迟不稳） | 稳定低延迟 |
| 适用 | Web/文件/DB/消息 | DNS/音视频/游戏/QUIC 底座 |

```text
工程记忆：
  TCP = "可靠但延迟抖动"（重传把延迟拉长）
  UDP = "快但可能丢"（应用用 FEC/重发自行权衡）
  选择依据：丢一包"无所谓"→ UDP；丢一包"完蛋"→ TCP 或 QUIC
```

## 4. 为什么 QUIC 选择 UDP 而不是新 TCP

```text
表面答案：TCP 协议栈在内核、演进慢（新特性要过 IETF + 内核评审 + 全网部署）
深层答案（RFC 9000 的设计约束）：
  ① 中间设备不可信：NAT/防火墙/LB 对未知 TCP 选项会丢弃/篡改
     → 新 TCP（如 Fast Open）部署十年覆盖率仍低
  ② UDP 是中立的"通行证"：现有网络默认放行 53（DNS）/443
     → QUIC 走 UDP:443 = 复用 HTTPS 的放行规则，穿透率最高
  ③ 用户态实现：TCP 语义在内核改不动；UDP 之上随便造
     → QUIC 全部用户态（连接迁移/0-RTT/多路复用自由迭代）
  ④ 内核态演进缓慢：TCP 新特性要等发行版 → UDP 之上月级迭代

结论：UDP 是"可编程的传输层基座"，QUIC 在它之上实现了
     现代版 TCP（可靠性 + 拥塞控制 + 多路复用 + 加密）
```

## 5. UDP 之上的可靠传输：QUIC 与 KCP

### 5.1 QUIC（RFC 9000，2021）

```text
QUIC = UDP + 可靠性/拥塞控制/多路复用/TLS 1.3
  逐层对照：
    UDP          → 基座（数据报）
    QUIC 层      → 连接（CID）、流（多路复用）、重传、拥塞控制（CUBIC/BBR 可插拔）
    TLS 1.3      → 内建加密
    HTTP/3       → 应用（网络高并发体系 07 章）

关键能力（UDP 无连接 ≠ QUIC 无连接！QUIC 有自己的连接）：
  连接迁移：连接 ID 识别，四元组变化不断连
  0-RTT：会话恢复后首包即带数据
  无队头阻塞：流独立确认
2026 状态：浏览器 95%+、头部网站 34-40% 采用（HTTP/3 体系）
```

### 5.2 KCP：游戏场景的可靠 UDP

```text
KCP：游戏/实时通信的可靠 UDP 协议（G 语言实现）
  特性：快速重传（跳过已 ACK 的数据）、延迟容忍、拥塞窗口可配
  vs QUIC：KCP 更轻（无 TLS/无多路复用），专注低延迟可靠交付
  适用：自研游戏同步、实时交互 —— 视频/语音场景还可直接裸 UDP
```

## 6. UDP 高并发应用场景

| 场景 | 为什么用 UDP | 可靠性处理 |
|------|-------------|-----------|
| DNS | 单包查询、延迟敏感 | 应用层重试（TCP 兜底大响应） |
| 音视频（RTP） | 丢帧可接受、延迟不能抖 | FEC 前向纠错 + 重传关键帧 |
| 游戏同步 | 状态快照可覆盖旧状态 | 快照合并（只发最新） |
| 实时监控/日志 | 高吞吐低优先 | 丢弃不阻塞 |
| 负载均衡健康检查 | 轻量探活 | 无 |
| **QUIC/HTTP3** | 可靠+低延迟都要 | QUIC 层全做 |

```text
高并发注意（UDP 服务器）：
  ① 无连接状态 → 单进程可服务海量客户端（epoll 管 fd）
  ② 防风暴：UDP 洪泛（反射放大攻击，见第 7 节）
  ③ 应用层必须做"连接"抽象（客户端标识/超时/去重）
```

## 7. UDP 的坑与安全

| 问题 | 说明 | 防御 |
|------|------|------|
| **反射放大攻击** | 伪造源 IP 发小请求 → 服务器回放大响应 → 受害者被打爆（DNS/NTP/SSDP 经典） | 响应限速、源校验（uRPF）、关闭开放递归 |
| 无握手防伪造 | 无三次握手 = 无源地址验证 | 应用层挑战-响应（QUIC 的 Retry 机制） |
| 无拥塞控制 | 恶意/失控发送打爆网络 | 应用自限速、入口限流 |
| 分片脆弱 | 大 UDP 报文 IP 分片易被丢弃 | 保持 < MTU（1472）；QUIC 用 PMTU 探测 |

> ⚠️ **生产教训**：开放 UDP 服务前必须考虑反射放大面（2026 年 DDoS 报告里 UDP 放大仍是主力）；QUIC 等现代协议用 Retry/地址验证补上"无握手"的洞。

## 8. UDP 工程实践：选型清单与常见错误

### 8.1 UDP 服务器实现要点

```java
// Java UDP 服务端骨架（单线程可服务海量客户端——无连接状态）
DatagramSocket socket = new DatagramSocket(8080);
byte[] buf = new byte[1500];                       // 避免分片：≤ MTU
DatagramPacket pkt = new DatagramPacket(buf, buf.length);
while (true) {
    socket.receive(pkt);                            // 阻塞收包
    // 无连接 → 用源地址标识客户端（应用层"会话"抽象）
    InetAddress client = pkt.getAddress();
    handle(client, pkt.getData(), pkt.getLength());
    socket.send(response);
}
```

### 8.2 选型决策清单

```text
用 UDP 的判定标准（逐条回答）：
  □ 丢一包可接受（应用有 FEC/重发/最新值覆盖）？
  □ 延迟稳定性优先于可靠性？
  □ 不需要服务器侧连接状态？
  全"是" → UDP（或 UDP 之上的轻量可靠层）

配套工程：
  □ 应用层心跳/超时（无连接 = 无自动断连检测）
  □ 防放大攻击（关闭开放服务、限速——04/06 章）
  □ 大消息分片策略（保持 < MTU 或自己分片重装）
  □ 乱序容忍（应用按序号丢弃旧包/重排）
```

### 8.3 常见错误清单

| 错误 | 后果 | 对策 |
|------|------|------|
| 发送 > MTU 的大报文 | IP 分片被中间设备丢弃 | 报文 ≤ 1472（以太网） |
| 无应用层超时 | 客户端消失后状态永不清理 | 心跳 + 超时淘汰 |
| 不做乱序/丢包处理 | 数据错乱（音视频花屏） | 序号 + 时间戳 + 容忍策略 |
| 开放服务无限速 | 成为放大攻击放大器 | RRL/源校验/关闭开放 |
| 校验和关闭（IPv4 可设 0） | 数据静默损坏 | 保持校验和开启 |

## 9. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. UDP = 无连接 + 尽力而为 + 数据报——延迟可控、状态为零，把可靠性决定权交给应用；
> 2. QUIC 选 UDP 的根本原因：TCP 在内核演进不动、中间设备不可信，UDP 是可编程的"中立基座"；
> 3. 裸 UDP 的坑：反射放大、无源验证、无拥塞控制——现代用法是"UDP 之上造可靠层"（QUIC/KCP）。
