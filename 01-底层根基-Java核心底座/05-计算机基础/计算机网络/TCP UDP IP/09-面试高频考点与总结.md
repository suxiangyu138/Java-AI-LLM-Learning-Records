## 1. 高频面试题 18 问

### Q1：TCP 三次握手为什么不是两次或四次？

> 答：目的是"双向可达确认 + 同步两个序列号"。两次握手的问题：客户端 SYN 滞留网络中，服务器收到旧 SYN 回 SYN+ACK 后**单方面认为连接建立**（半开连接占资源），而客户端无法确认服务器可达——只有第三次 ACK 到达，服务器才能确认"客户端收到了自己的应答"。四次则第三次已完成全部信息交换，第四次无新增信息。**三次 = 最小完备**。
> 参考：02 章 1 节

### Q2：四次挥手为什么是四次？

> 答：TCP 全双工，两个方向独立关闭。① 客户端 FIN（我不再发了）；② 服务器 ACK（知道了，但我还有数据要发）；③ 服务器发完数据后 FIN（我也发完了）；④ 客户端 ACK。②③ 在"服务器恰好无剩余数据"时可合并为一段（表现为三次挥手）。**挥手四次源于半关闭语义**，与握手三次原因不同。
> 参考：02 章 3 节

### Q3：TIME_WAIT 是什么？为什么等 2MSL？

> 答：主动关闭方发送最后 ACK 后进入 TIME-WAIT，等待 2MSL（Linux 默认 60s×2=120s）。两个目的：① 保证最后 ACK 可靠送达（丢失则对方重传 FIN，需重新应答）；② 让旧连接滞留报文在网络中消亡，防止四元组复用后旧报文串扰新连接。**不是缺陷而是正确性设计**。生产处理：连接复用根治、`tcp_tw_reuse` 次选（并发体系 06 章）。
> 参考：02 章 5 节

### Q4：TCP 怎么保证可靠传输？

> 答：三件套——① 确认：累积 ACK（期望的下一个序号），SACK 选项精确报告丢失块；② 重传：超时重传（RTO 动态估计 + Karn 算法防歧义）、快速重传（3 个 DupACK 触发，RTT 级恢复）、SACK 精确重传；③ 窗口：滑动窗口流水线发送。可靠性是**端到端**的（两端内核负责），中间设备无状态。
> 参考：01 章 1 节、03 章

### Q5：滑动窗口和拥塞窗口的区别？

> 答：接收窗口（rwnd）= 接收方能力通告（流量控制，管"接收方装不装得下"）；拥塞窗口（cwnd）= 发送方自测网络容量（拥塞控制，管"网络扛不扛得住"）。**发送上限 = min(rwnd, cwnd)**。流量控制依据对端通告，拥塞控制依据丢包/延迟信号。
> 参考：03 章 7 节

### Q6：拥塞控制三个阶段？

> 答：① 慢启动：每 ACK +1 段（指数增长 1→2→4...），快速探测带宽，到 ssthresh 或丢包为止；② 拥塞避免：每 RTT +1 段（线性），缓慢逼近容量；③ 快速恢复：3 DupACK → cwnd 减半线性恢复；超时 → cwnd=1 重新慢启动（网络严重拥塞）。整体呈"锯齿波"（AIMD：加性增、乘性减）。
> 参考：04 章 1 节

### Q7：CUBIC 和 BBR 的区别？

> 答：核心差异在**拥塞信号**——CUBIC 用丢包（丢包=拥塞假设，三次函数增长，与 RTT 无关地快速恢复）；BBR 用**带宽×延迟测量**（瓶颈带宽 BtlBw × 最小 RTT 模型），不因丢包减窗，主动控制队列占用（反 bufferbloat）。适用：深缓冲高带宽 CUBIC 足够；高丢包/浅缓冲/移动网络 BBR 优势大。2026 现状：Linux 默认仍是 CUBIC，BBR 一行启用（v1 级），BBRv3 需定制内核。
> 参考：04 章 3/4/6 节

### Q8：快速重传为什么是 3 个 DupACK？

> 答：1-2 个 DupACK 可能是网络乱序（到达即确认，后续会补确认）；3 个连续 DupACK 才足以判定"该段确实丢失"（后面数据都在流动，唯独它没到）。阈值是"乱序 vs 丢失"的工程折中。
> 参考：03 章 3.2

### Q9：RTT 怎么估计？Karn 算法解决什么？

> 答：SRTT = (1−α)·SRTT + α·RTT，RTO = SRTT + 4×RTTVAR（下限 1s，RFC 6298）。Karn 算法解决**重传歧义**：重传后的 ACK 无法区分是"原段"还是"重传段"的确认，其 RTT 样本不可信 → 重传期间不采样，下次成功传输再启用。时间戳选项（TS）让每个 ACK 携带精确 RTT，歧义消失。
> 参考：03 章 4 节

### Q10：SACK 是什么？为什么重要？

> 答：选择性确认——接收方在 ACK 中报告"已收到的乱序块"（如 ack=1461, sack 1 2921-4380），发送方精确知道"丢了哪个、哪个没丢"，只重传缺失段。没有 SACK 时累积确认会"因一个丢包而让后续段白等一个 RTT"。现代内核默认开启，高丢包链路（移动/跨洋）吞吐差距可达数倍。
> 参考：03 章 2 节

### Q11：UDP 和 TCP 怎么选？

> 答：按可靠性需求——丢一包无所谓（音视频/游戏快照/DNS）：UDP（低延迟、无重传抖动）；丢一包完蛋（Web/文件/消息）：TCP；两者都要（可靠+低延迟）：**QUIC**（UDP 之上的可靠层，2026 年 HTTP/3 已过临界量）。另注意 UDP 无拥塞控制，应用需自限速；开放 UDP 服务需防反射放大。
> 参考：05 章 3/6/7 节

### Q12：为什么 QUIC 选择 UDP？

> 答：① TCP 语义在内核，演进不动（新特性需 IETF+内核+全网部署，10 年覆盖率低）；② 中间设备不可信（NAT/LB/防火墙会丢未知 TCP 选项）；③ UDP:443 复用 HTTPS 的放行规则，穿透率最高；④ UDP 之上用户态自由实现（连接迁移/0-RTT/多路复用快速迭代）。QUIC 在 UDP 上重造了"现代 TCP"。
> 参考：05 章 4 节

### Q13：IPv4 分片机制？为什么要避免？

> 答：报文 > MTU 时中间路由器拆分（标识/标志 MF/片偏移三件套，接收端重组）。避免原因：① 任一分片丢失 → 整包无法重组 → 上层重传整包（更糟）；② 分片易被防火墙丢弃；③ 中间设备 CPU 负担。现代解法：PMTUD（DF 标志 + ICMP 反馈）与 MSS 钳制——"ping 通但 HTTP 打不开"的头号原因就是 MSS/MTU 错配。
> 参考：06 章 2/3 节

### Q14：IPv6 相比 IPv4 的关键变化？

> 答：① 128 位地址（SLAAC 即插即用，无 DHCP 依赖）；② 仅源端分片（路由器不再分片）；③ 无首部校验和（端到端保证）；④ 无广播（用组播）；⑤ 不需要 NAT（地址充足）；⑥ 固定 40B 首部 + 扩展头链。2026-03 全球采用率首破 50%（Google 口径 50.10%）；区域差异大（法国 80%+ vs 意大利 17%）；移动网络领先（~70%），多数仍是双栈。
> 参考：06 章 5/6 节

### Q15：BDP 是什么？为什么影响吞吐？

> 答：带宽延迟积 = 带宽 × RTT（网络中在途数据量）。TCP 吞吐 ≤ 窗口/RTT，窗口必须 ≥ BDP 才能跑满带宽。例：10Gbps×100ms → BDP=125MB，默认 64KB 窗口只能跑 ~5Mbps → 必须窗口缩放 + 大 rmem/wmem。
> 参考：08 章 1 节

### Q16：窗口缩放（Window Scaling）是什么？

> 答：TCP 首部窗口字段只有 16 位（最大 64KB），高 BDP 场景不够用。握手期协商缩放因子（Shift 0-14）：实际窗口 = 值 × 2^Shift（最大 ~1GB 级）。现代内核默认启用（`ss -tin` 看 wscale）。**别关它**——高带宽长时延连接的命根子。
> 参考：03 章 5.2、08 章

### Q17：TSO/GRO 是什么？排障时为什么先关它们？

> 答：硬件卸载——TSO 发送侧网卡把大包拆成 MSS 段（省 CPU），GRO 接收侧网卡合并小包交内核（省收包次数），RSS 多队列分散多核。偶发网卡/驱动 bug 会导致校验错误/低吞吐/随机失败——排障第一步 `ethtool -K eth0 tso off gro off` 验证是否卸载问题。
> 参考：08 章 3 节

### Q18：抓包怎么定位网络问题？

> 答：三信号——① 看握手：只有 SYN 无响应（防火墙/未监听/队列满）、SYN 重发（链路丢包）；② 看重传：同一 seq 重复 + RTO 间隔 = 超时重传（丢包）、3 DupACK + 快速重传 = 单段丢失、SACK 报告 = 精确恢复；③ 看窗口：win 0 = 应用消费慢、低窗口持续 = 应用层问题。判断口诀：乱序不重传、重传才是丢。
> 参考：07 章

### 追问：为什么 TCP 有"粘包"而 UDP 没有？（综合向）

> 答：TCP 是字节流（无消息边界，01 章）——多次 write 可能合并传输（粘包）、一次 write 可能拆分（拆包），应用层必须自定义边界（定长/分隔符/长度前缀）；UDP 是数据报（05 章）——每次 send 是一个完整报文，recv 恰好收一个。面试加分：给出长度前缀方案（HTTP/2 帧/Netty LengthFieldBasedFrameDecoder）。
> 参考：01 章 7 节

### 追问：tcpdump 抓包显示"重传"就一定是网络丢包吗？（排障向）

> 答：不一定——① 网络乱序（Out-of-Order）会被误判（到达即确认）；② 路径切换（LB/多路径漂移）引发重传风暴；③ 中间设备缓冲溢出（周期性重传，bufferbloat）；④ 真丢包（RTO 重传间隔 200ms+ 指数退避）。判断口诀：乱序不重传、重传才是丢；但要先排除乱序与路径切换再归因链路（07 章）。
> 参考：03 章 8 节、07 章

### 追问：IPv6 部署对服务器工程师意味着什么？（运维向）

> 答：四件事——① 监听 `::`（IPv6 通配）与 AAAA 记录（双栈）；② 防火墙/安全组补 v6 规则（常被遗漏）；③ 日志与监控兼容 v6 地址；④ CDN/云 LB 确认双栈。2026 数据：全球采用率破 50%（Google 口径 50.10%），移动 ~70%——纯 IPv6 客户端越来越多，不做双栈 = 丢用户（06 章）。
> 参考：06 章 6/7 节

### 追问：UDP 能保证"不丢包"吗？怎么做？（协议设计向）

> 答：裸 UDP 不保证；但可以在 UDP 之上实现可靠层——序号 + 确认 + 重传（应用层 TCP），或 QUIC/KCP（现成方案，05 章）。工程选择：全量可靠用 QUIC（连接/流/拥塞齐全）；轻量可靠用 KCP（游戏场景）；部分可靠用"最新值覆盖"（音视频丢旧包无所谓）。加分项：说明"UDP 的优势是可控性——可靠性策略由业务决定而非协议强加"。
> 参考：05 章 4/5 节

## 2. 易错点清单

| # | 易错点 | 正确认知 |
|---|--------|---------|
| 1 | "三次握手为了确认双方在线" | 是"确认双向可达 + 同步序列号"——两次握手半开连接的推演才见功力 |
| 2 | "挥手四次与握手三次对称" | 挥手四次源于**半关闭**（服务器可能还有数据），与握手原因不同 |
| 3 | "TIME_WAIT 是浪费" | 是防旧报文串扰的正确性设计，2MSL 的双重目的要答全 |
| 4 | "滑动窗口 = 拥塞窗口" | 接收窗口（通告）vs 拥塞窗口（自测），发送上限 = min 二者 |
| 5 | "慢启动 = 慢" | 慢启动是**指数**增长（快！），"慢"指从小窗口保守起步 |
| 6 | "CUBIC 是丢包触发减半" | 是三次函数增长（时间函数与 RTT 无关），丢包仍是信号之一 |
| 7 | "BBR 已进主线默认" | 2026 主线上 BBR v3 仍未默认（需定制内核），默认仍是 CUBIC |
| 8 | "UDP 没校验和" | IPv4 下可选，IPv6 下必填；覆盖伪首部跨层验证 |
| 9 | "QUIC 是 UDP" | QUIC 在 UDP **之上**实现了自己的可靠层（连接/重传/拥塞） |
| 10 | "IPv6 已全面普及" | 2026-03 才首破 50%，区域差异巨大，多数仍是双栈 |
| 11 | "窗口越大越好" | 窗口 = 每连接内存，百万连接 × 大窗口 = 内存爆炸（预算联动） |
| 12 | "TSO 关了更稳" | 默认该开（省 CPU）；关掉是**排障手段**而非常态 |

## 3. 知识体系一句话串讲

```text
IP（找路）：IPv4 32 位/CIDR/NAT/分片（三件套+MTU 错配是坑）
           → IPv6 128 位/SLAAC/仅源端分片（2026 全球破 50%）
TCP（送稳）：
  ├─ 连接：三次握手（双向可达）→ 11 状态机 → 四次挥手（半关闭）→ TIME_WAIT（2MSL 防串扰）
  ├─ 可靠：累积 ACK + SACK → 超时重传（RTO=SRTT+4·RTTVAR，Karn 防歧义）
  │        → 快速重传（3 DupACK）→ 滑动窗口（rwnd 流量控制）
  └─ 拥塞：慢启动（指数）→ 拥塞避免（线性）→ 快速恢复（减半）
           → CUBIC（默认，三次函数）→ BBR（带宽×延迟测量，v3 待入主线）
UDP（送快）：8B 头/数据报/无状态 → 实时场景 → QUIC 底座（现代 TCP 的载体）
排障与调优：分层定位 → 抓包三信号（握手/重传/窗口）→ BDP 公式 → sysctl/卸载/队列
```

## 4. 快速自测（含答案）

1. **三次握手的核心目的？** 双向可达确认 + 同步序列号（02 章）。
2. **TIME_WAIT 等待时长？** 2MSL = 120s（Linux 默认）（02 章）。
3. **快速重传触发条件？** 连续 3 个 DupACK（03 章）。
4. **Karn 算法解决？** 重传歧义（RTT 样本不可信）（03 章）。
5. **发送上限公式？** min(rwnd, cwnd)（03 章）。
6. **Linux 默认拥塞控制？** CUBIC（04 章）。
7. **BBR 的核心信号？** 瓶颈带宽 × 最小 RTT（非丢包）（04 章）。
8. **QUIC 的传输底座？** UDP（用户态可靠层）（05 章）。
9. **IPv6 采用率里程碑？** 2026-03 Google 口径首破 50%（06 章）。
10. **"ping 通但 HTTP 打不开"头号原因？** MSS/MTU 错配（06/07 章）。
11. **BDP 公式？** 带宽 × RTT；窗口必须 ≥ BDP（08 章）。
12. **排障三信号？** 握手（建连）、重传/DupACK/SACK（丢包）、窗口（应用消费）（07 章）。
