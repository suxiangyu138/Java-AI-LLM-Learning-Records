## 1. 三次握手：为什么恰好三次

### 1.1 流程

```text
客户端                        服务器
  │  SYN=1, seq=x ──────────→│  LISTEN
  │                          │  （收到 SYN → SYN-RCVD）
  │  ←────── SYN=1,ACK=1, seq=y, ack=x+1 │
  │  ACK=1, seq=x+1, ack=y+1 ─→│  （收到 ACK → ESTABLISHED）
  │  ESTABLISHED              │
```

| 步 | 报文 | 传递的信息 |
|:---:|------|-----------|
| ① | SYN(seq=x) | 客户端：我能发（同步初始序列号 x） |
| ② | SYN+ACK(seq=y, ack=x+1) | 服务器：我收到了你的 x，这是我的 y |
| ③ | ACK(ack=y+1) | 客户端：我收到了你的 y —— 双方确认"双向可达" |

### 1.2 为什么不能是两次

```text
核心：确认"双方都能收发" + 同步两个序列号

两次握手的缺陷（经典推演）：
  客户端 SYN 在网络中滞留（超时重发并建连成功，旧 SYN 延迟到达服务器）
  服务器收到旧 SYN → 回 SYN+ACK → 客户端发现不是新连接的响应 → 忽略
  → 服务器认为连接已建立（半开），浪费资源等待永远不来的数据
  → 两次握手无法让"服务器"确认"客户端收到了自己的应答"

四次呢？第三次 ACK 已确认双向；第四次是冗余（无新增信息）——三次是"最小完备"
```

> 🎯 **核心要点**：三次握手的最小完备性 = "**客户端确认服务器可达（②的到达）+ 服务器确认客户端可达（③的到达）**"——两次缺后一半，四次多无信息。面试从"丢包/滞留"角度论证两次不安全。

### 1.3 握手阶段的超时

```text
SYN 丢失 → 客户端重传（指数退避：1s → 2s → 4s → 8s → 16s → 32s → 64s）
  默认最多 6 次（127s 后放弃）→ 应用看到 connect timeout
服务端优化：tcp_syn_retries / tcp_synack_retries 控制重试
```

## 2. SYN 洪泛攻击与防御

```text
攻击：伪造海量 SYN（不完成握手）→ 服务器 SYN 队列被占满
  → 正常连接无法建立（半连接队列满，见并发体系 06 章）

防御体系：
  ① SYN Cookies（核心）：不分配队列资源，用"序列号 = 函数(地址,端口,时间)"
     的 Cookie 应答；合法 ACK 回来时验证 Cookie 重建连接
     → 无状态防占资源（Linux net.ipv4.tcp_syncookies=1）
  ② 缩短超时：tcp_synack_retries 降低（占队列时间变短）
  ③ 限速：入口防火墙 SYN 限速/丢弃（CP 层面）
  ④ 扩容：tcp_max_syn_backlog 加大（治标）
```

## 3. 四次挥手：为什么不是三次

### 3.1 流程

```text
客户端（主动关闭）            服务器（被动关闭）
  │  FIN=1, seq=u ──────────→│  ESTABLISHED → FIN-WAIT-1
  │  ←────── ACK=1, ack=u+1 │  CLOSE-WAIT（应用还在写数据！）
  │  FIN-WAIT-2              │
  │  （服务器继续发剩余数据）   │
  │  ←────── FIN=1, seq=v   │  应用关闭 → LAST-ACK
  │  ACK=1, ack=v+1 ────────→│  CLOSED
  │  TIME-WAIT（2MSL）        │
  │  CLOSED                  │
```

### 3.2 为什么是四次而不是三次

```text
TCP 是"全双工"——两个方向的字节流各自独立关闭：
  ① 客户端 FIN：我发完了（但还能收）
  ② 服务器 ACK：知道了（但我还要发）
  ③ 服务器 FIN：我也发完了
  ④ 客户端 ACK：知道了

合并可能：②③ 可合并为一次（服务器恰好无剩余数据）
  → 表现为三次挥手（FIN+ACK 与 FIN 同一段）——正常现象

对比握手三次：握手双方"同时"就绪；挥手是"异步"的（一方可能还在发）
```

> ⚠️ **高频考点**：挥手四次不是因为"对称"，而是因为**半关闭语义**——服务器收到 FIN 后可能还有数据要发，ACK 与 FIN 必须分开。

## 4. TCP 11 状态机全图

```text
                        ┌─────────┐
                建立    │ CLOSED  │   关闭
              ┌────────┤         ├────────┐
              ▼        └─────────┘        ▼
           SYN-SENT                  TIME-WAIT
              │    (被动方)               ▲
              ▼        ┌─────────┐       │
         (主动方)       │  LISTEN │       │
              │        └─────────┘       │
              │            ▼             │
              │        SYN-RCVD          │
              ▼            │             │
              └────► ESTABLISHED ◄───────┘
                        │      │
              (主动关闭) ▼      ▼ (被动关闭)
            FIN-WAIT-1      CLOSE-WAIT
              │                │
              ▼                ▼
            FIN-WAIT-2      LAST-ACK
              │                │
              └──────► CLOSED ◄┘
```

| 状态 | 归属 | 含义 |
|------|:---:|------|
| LISTEN | 服务器 | 等待连接 |
| SYN-SENT / SYN-RCVD | 双方 | 握手进行中 |
| ESTABLISHED | 双方 | 正常传输 |
| FIN-WAIT-1 / 2 | 主动关 | 已发 FIN / 等对方 FIN |
| CLOSE-WAIT | 被动关 | 已收 FIN，等应用关闭（**应用没 close = 泄漏点**） |
| LAST-ACK | 被动关 | 已发 FIN 等最后 ACK |
| TIME-WAIT | 主动关 | 等 2MSL |
| CLOSED | - | 结束 |

> ⚠️ **排障要点**：`CLOSE-WAIT` 大量堆积 = **应用忘了调用 close**（代码 bug）；`TIME-WAIT` 大量堆积 = 短连接场景正常（并发体系 06 章处理）。

## 5. TIME_WAIT 与 2MSL 深潜

### 5.1 为什么主动关闭方要等 2MSL

```text
① 保证最后一个 ACK 到达（丢失则对方重传 FIN，需重新应答）
   → 等 2MSL：足以覆盖 FIN 重传 + 新 ACK 往返
② 防旧连接报文串扰新连接：
   → 2MSL 后，旧连接的任何滞留报文都已在网络中消亡
   → 四元组复用（新连接同 IP 同端口）不会收到旧报文

MSL = 报文最大生存时间（Linux 默认 60s）→ 2MSL = 120s
```

### 5.2 谁进 TIME_WAIT

```text
只有主动关闭方进 TIME_WAIT：
  HTTP 短连接：客户端通常主动关闭 → 客户端 TIME_WAIT 多
  服务器主动关闭（如 keep-alive 超时由服务端关）→ 服务器 TIME_WAIT 多

生产处理（并发体系 06 章已述，此处从状态机视角总结）：
  ① 连接复用（根治——不关闭就不产生）
  ② tcp_tw_reuse（出站复用，有时序权衡）
  ③ 长连接 + 服务端控制关闭时机
```

## 6. 半关闭与连接保活

### 6.1 半关闭（shutdown）

```java
// 半关闭：只关一个方向（还能收/发）
socket.shutdownOutput();    // 发 FIN（告诉对方"我不再发了"）
socket.shutdownInput();     // 只关读
// 用途：协议约定"我发完了你给结论"（如 HTTP 请求体结束）
```

### 6.2 保活机制

```text
TCP keepalive（内核层）：
  空闲 tcp_keepalive_time（默认 2h）后开始探测
  每 tcp_keepalive_intvl（75s）一次，共 tcp_keepalive_probes（9）次失败则断开
  → 默认太慢，生产调短（并发体系 06 章参数表）

应用层心跳（业务层）：
  WebSocket ping/pong、自定义心跳 —— 快且语义清晰
  生产推荐：应用心跳为主，内核 keepalive 兜底
```

## 7. 同时打开与同时关闭

```text
同时打开（simultaneous open）：
  双方同时发 SYN → 各自收到对方 SYN 后回 SYN+ACK → 直接 ESTABLISHED
  罕见（需双方同时发起），TCP 规范支持

同时关闭（simultaneous close）：
  双方同时发 FIN → 都进 FIN-WAIT-1 → 都收 FIN 后回 ACK
  → 都进 TIME-WAIT → 各自 2MSL 后关闭
  正常连接管理不需要关注（被动方通常先发完再关）
```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 三次握手=双向可达的最小确认（两次不安全、四次冗余）；四次挥手=全双工半关闭语义（ACK 与 FIN 因"可能还有数据"而分开）；
> 2. 11 状态机排障要点：CLOSE-WAIT 堆积=应用没 close，TIME-WAIT=主动关闭方的正确性等待（2MSL 防串扰）；
> 3. SYN 洪泛靠 SYN Cookies 无状态防御；保活用应用心跳为主、内核 keepalive 兜底。

**思考题**：

1. 为什么"两次握手 + 超时重传"仍不安全？（→ 1.2 滞留 SYN 推演）
2. 挥手在什么情况下表现为三次？（→ 3.2 ②③合并）
3. `CLOSE-WAIT` 堆积说明什么？（→ 4 排障要点）
4. TIME_WAIT 为什么必须等 2MSL 而不是 1MSL？（→ 5.1 ①+②）
