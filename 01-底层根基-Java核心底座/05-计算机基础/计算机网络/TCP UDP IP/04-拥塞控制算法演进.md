## 1. 拥塞控制的总框架：三大阶段

```text
拥塞窗口 cwnd 的三大阶段（Reno 系经典框架）：
  ① 慢启动（Slow Start）：
     每收到 ACK，cwnd += 1 段（指数增长：1 → 2 → 4 → 8 ...）
     目的：快速探测可用带宽（指数探路）
     结束：cwnd ≥ ssthresh（阈值）→ 转拥塞避免
          或 发生丢包 → cwnd 减半（快速恢复）或归 1（超时）

  ② 拥塞避免（Congestion Avoidance）：
     每 RTT，cwnd += 1 段（线性增长：+1/RTT）
     目的：缓慢逼近网络容量（避免突然拥塞）

  ③ 快速恢复（Fast Recovery）：
     丢包（3 DupACK）→ cwnd 减半 → 线性恢复
     超时 → cwnd = 1（从头慢启动）—— 网络已严重拥塞

  曲线：指数爬坡 → 线性逼近 → 丢包减半 → 再线性……
  → "锯齿波"（sawtooth），AIMD（加性增、乘性减）本质
```

> 🎯 **核心要点**：传统拥塞控制的共同前提——**"丢包 = 网络拥塞"**。这个假设在浅缓冲路由器时代成立；在深缓冲/无线网络中失真（丢包≠拥塞），正是 BBR 革命的起点。

## 2. Reno / NewReno：丢包即拥塞的经典模型

```text
Reno（1988，BSD 网络栈经典）：
  慢启动 → ssthresh 转线性 → 3 DupACK 快速重传+快速恢复（cwnd 减半）
  超时 → cwnd=1 重新慢启动

缺陷：一个窗口内多段丢失时恢复很差
  （快速恢复只重传一个段，其余等超时 → 吞吐崩塌）

NewReno（1996）：改进快速恢复——
  收到"部分 ACK"（确认了部分重传数据）继续停留在快速恢复
  → 一个窗口内可连续恢复多个丢失段
  → 成为 2000s 标准（Linux 至今内置）

Reno 家族定位：无 SACK 时代的标准；SACK 时代被 CUBIC 取代
```

## 3. CUBIC：默认算法的三次函数

### 3.1 机制

```text
CUBIC（2008，Linux 2.6.19 起默认）：
  不用"每 RTT +1"的线性增长，而用三次函数（立方）：
    W = C·(t − K)³ + Wmax
    丢包后从 Wmax 出发，快速恢复到 Wmax 附近（立方段陡峭）
    → 接近 Wmax 后放缓（平台段平缓，长时间占用带宽）

关键特性：
  ① 与 RTT 无关（t 是绝对时间）：
     → 高带宽长时延（RTT 大）连接不再被"每 RTT +1"拖慢
     → 解决 Reno 的 RTT 不公平（RTT 小的连接抢带宽）
  ② 快速恢复：丢包后迅速回满（BIC 思想的平滑化）
  ③ 公平性：长期看与其他 CUBIC 流公平分享
```

### 3.2 适用性判断

```text
CUBIC 强项：高带宽（10Gbps+）、深缓冲链路、数据中心/骨干
CUBIC 弱项：浅缓冲链路（丢包误判拥塞）、无线/移动（丢包率高）
  → 弱网场景反而被丢包信号惩罚 → BBR 的机会
```

## 4. BBR：带宽测量革命

### 4.1 思想转变

```text
传统（丢包信号）：丢包 → 减窗 —— 但丢包可能不是拥塞！
BBR（2016，Google）：
  不再用丢包做信号，而是直接测量两个量：
  ① 瓶颈带宽（BtlBw）：max(传输速率采样)——带宽多大
  ② 最小 RTT（RTprop）：min(RTT 采样)——延迟多低
  发送速率 = BtlBw（模型：瓶颈链路带宽 × 时间 = 最优发送量）

运行模式（四相循环）：
  STARTUP（探测带宽）→ DRAIN（排空队列）→ PROBE_BW（带宽维持）
  → PROBE_RTT（延迟探测）

效果（Google 实测）：
  高丢包/浅缓冲链路：吞吐数倍于 CUBIC
  YouTube/Google 基础设施部署后带宽利用率大幅提升
```

### 4.2 BBR v2 / v3 演进

| 版本 | 改进 | 状态 |
|------|------|:---:|
| BBR v1（2016） | 带宽+延迟模型 | Linux 5.4+ 内核自带 |
| BBR v2（2021-2022） | 增加**丢包率/ECN 信号**混合（收敛性更好、公平性更好） | 未进主线（曾预计 5.16 落空） |
| **BBR v3** | v2 的进一步打磨（IETF 草案 draft-ietf-ccwg-bbr-05，2026-03） | **2026 仍未进主线默认** |

## 5. BBR vs CUBIC 对比

| 维度 | CUBIC | BBR |
|------|:---:|:---:|
| 拥塞信号 | 丢包（+ 时间） | **带宽 × 延迟测量**（丢包仅参考） |
| 缓冲区占用 | 填满深缓冲（bufferbloat） | **不填队列**（主动控制队列占用） |
| 高丢包链路 | 吞吐暴跌（丢包即减窗） | 吞吐稳定（丢包不惩罚） |
| 浅缓冲链路 | 误判拥塞、吞吐低 | 优势最大 |
| 深缓冲+低丢包（数据中心） | 持平或略优 | 持平 |
| 公平共存 | 与其他 CUBIC 公平 | 与 CUBIC 共存需 ECN/丢包信号（v2/v3 改善） |
| 队列延迟 | 高（填缓冲） | 低（模型直接避免） |
| 部署现状 | **Linux 默认** | 可选模块（v1 内核自带；v3 需定制内核） |

```text
一句话选型：
  默认场景（公网 Web/API）→ CUBIC 足够（保持默认最稳）
  高丢包/移动/浅缓冲专线 → BBR 明显收益（sysctl 一行启用）
  大数据传输/跨国链路 → BBR 值得试（压测对比后再定）
```

## 6. 2026 现状：BBRv3 与内核状态

```text
（2026-08 检索结论，版本信息可能有出入，以内核主线为准）

主线默认：CUBIC 仍是 net.ipv4.tcp_congestion_control 默认值
BBRv3 主线状态：有说法称 6.13 已并入"BBR 最新实现"；
  也有来源称 v3 仍未入主线（主流发行版内核仅 BBR v1/v2 能力）
  → 结论：**主流发行版内核（Ubuntu/Debian/RHEL 系列）默认 CUBIC，
    BBR 需显式启用；BBRv3 要 XanMod 等定制内核或手动编译**
IETF：draft-ietf-ccwg-bbr-05（2026-03，Experimental，9 月到期）
RHEL 官方内核：不能合入非上游 BBRv3 代码（合规限制）——需 ELRepo/定制
验证技巧：sysctl 显示 bbr ≠ BBRv3！
  modinfo tcp_bbr | grep version  → version: 3 才是真 v3
```

> ⚠️ **工程提醒**：别被"BBR 加速"营销文带偏——**生产默认 CUBIC 是稳定的正确选择**；BBR 启用前压测（同链路 A/B 对比吞吐与时延），且确认内核模块版本。

## 7. 配置与验证

```bash
# 1. 启用 BBR（Linux 5.4+，v1 级能力）
modprobe tcp_bbr
sysctl -w net.ipv4.tcp_congestion_control=bbr
sysctl -w net.core.default_qdisc=fq        # fq 队列是 BBR pacing 的前提！

# 2. 验证
sysctl net.ipv4.tcp_congestion_control    # bbr
sysctl net.core.default_qdisc             # fq
modinfo tcp_bbr | grep version            # 确认模块版本（是否 v3）

# 3. 查看连接实际使用的算法
ss -tin | grep -o 'cong \w*'
```

```text
BBR 与 fq 的绑定关系：
  BBR 依赖"发送 pacing"（平滑限速）→ 必须配合 fq（公平队列）qdisc
  只设 bbr 不设 fq：BBR 降级（pacing 失效）
```

## 8. 拥塞控制问题的延伸与实测方法

### 8.1 拥塞控制的另一面：bufferbloat

```text
bufferbloat（缓冲膨胀）：
  路由器大缓冲 → 丢包信号被"吸收" → 发送方继续提速
  → 队列堆积 → 延迟暴涨（而吞吐不变）

现象：链路"满速但卡顿"（P95 延迟飙升）
检测：RTT 在满载时显著增大（对比空闲 RTT）

对策：
  ① 主动队列管理（AQM）：fq_codel / cake（08 章 qdisc）
  ② BBR 类算法（不填队列，04 章 4 节）
  → 现代拥塞控制 = 吞吐 + 延迟双目标（不再是"只管不丢包"）
```

### 8.2 实测方法：如何判断"该换算法"

```text
压测 A/B 对比（同链路、同参数）：
  ① iperf3 单流：吞吐（该链路实际容量）
  ② 满载时 RTT：空闲 vs 满载（bufferbloat 指标）
  ③ 丢包率：中间链路（ping -f 大包探测 MSS）
  ④ 混合流量：业务压测（真实请求的 P99）

决策依据（2026 共识）：
  公网/移动/浅缓冲 → BBR 值得试（对比数据说话）
  数据中心/内网深缓冲 → CUBIC 足够（换算法收益小）
  混布环境 → 需评估公平性（BBR 与 CUBIC 共存时的带宽分配）
```

### 8.3 快速自查清单

```text
□ 当前算法：sysctl net.ipv4.tcp_congestion_control
□ 队列：sysctl net.core.default_qdisc（BBR 需 fq）
□ 模块版本：modinfo tcp_bbr（v3 需定制内核，04 章）
□ 满载 RTT 是否暴涨（bufferbloat 体检）
□ 拥塞信号是否被中间设备干扰（ECN 支持情况）
```

## 9. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 传统拥塞控制三阶段（慢启动/拥塞避免/快速恢复）以"丢包=拥塞"为信号，CUBIC 用三次函数解决高带宽场景，仍是 Linux 默认；
> 2. BBR 用"瓶颈带宽 × 最小 RTT"模型替代丢包信号——高丢包/浅缓冲链路收益巨大，且主动控制队列延迟（反 bufferbloat）；
> 3. 2026 现实：默认 CUBIC 最稳；BBR 一行启用（v1 级）；BBRv3 需定制内核，验证用 modinfo 而非 sysctl。

**思考题**：

1. 为什么"丢包=拥塞"在深缓冲/无线链路失真？（→ 1 核心要点）
2. CUBIC 为什么与 RTT 无关？（→ 3.1 时间函数）
3. BBR 如何避免 bufferbloat？（→ 5 队列占用行）
4. 为什么 BBR 必须配 fq？（→ 7 pacing）
