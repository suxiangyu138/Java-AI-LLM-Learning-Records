# DNS 解析流程：递归与迭代

> 一次域名解析 = 客户端问递归器、递归器逐级问权威：根 → TLD → 权威，每级返回"下一步去哪问"。递归器负责查到底（替你做），权威服务器只回答自己管辖的域——区分这两类角色，就理解了 DNS 的全部流量模型

## 1. 两个角色：递归解析器与权威服务器

| 角色 | 谁 | 职责 | 例子 |
|------|-----|------|------|
| **递归解析器**（Recursive Resolver） | 替客户端"查到底" | 逐级询问 + 缓存 | ISP DNS、8.8.8.8、1.1.1.1、内网 DNS |
| **权威服务器**（Authoritative） | 只回答自己"授权"的域 | 直接返回权威答案（不递归） | 阿里云 DNS 托管、Cloudflare DNS |

```text
职责边界：
  递归器 = 问路者（帮客户端跑腿，缓存结果）
  权威 = 指路人（只知道自己管辖的域，从不替别人回答）

安全含义（06 章）：
  攻击对象通常是"递归器"（投毒缓存）
  权威服务器是"数据源头"（被攻破=记录被改）
```

## 2. 完整解析链路：www.example.com 的一生

```text
① 客户端（浏览器）→ 本地递归器：
     "www.example.com 的 A 记录是什么？"（递归查询：你帮我查到底）

② 递归器 → 根服务器（.）：
     "com 域归谁管？" → 根返回 com 的 NS 列表（委派信息）

③ 递归器 → com TLD 服务器：
     "example.com 归谁管？" → com 返回 example.com 的 NS 列表

④ 递归器 → example.com 权威服务器：
     "www.example.com 的 A 记录？" → 权威返回 A 记录 + TTL

⑤ 递归器缓存结果 → 返回客户端

 客户端            递归器            根 .             com            example.com 权威
   │──递归──▶│──迭代①──▶│
   │         │◀─com NS──│
   │         │──迭代②──────▶│
   │         │◀─example NS──│
   │         │──迭代③────────────────────────▶│
   │         │◀──── A 记录 ───────────────────│
   │◀──答案───│
```

> 🎯 **核心要点**：链路中只有**第一跳是递归**（客户端→递归器），后续都是递归器发起的**迭代查询**——每次只问"下一步去哪"，权威从不替别人回答。缓存让②③④在热查询时被跳过（第 4 节）。

## 3. 递归查询 vs 迭代查询

| 维度 | 递归查询 | 迭代查询 |
|------|:---:|:---:|
| 谁发起 | 客户端 → 递归器 | 递归器 → 各级权威 |
| 期望 | "你帮我查到底，直接给我答案" | "你告诉我下一步问谁"（或给最终答案） |
| 谁承担工作 | 递归器 | 权威只做"指路"（轻量） |
| 缓存 | 递归器缓存完整结果 | 各级权威无缓存概念 |

```text
根服务器为什么能扛全球查询（每秒百万级）：
  ① 根只做"委派指路"（返回 TLD 的 NS），负载极轻
  ② Anycast 把 13 个"逻辑根"分布在数百个物理节点（07 章）
  ③ 递归器缓存委派信息（根/TLD 的查询占比极小）
```

## 4. 缓存在链路中的作用

```text
缓存层级（05 章详述，此处给链路视角）：
  客户端（浏览器/OS）→ 递归器 → （权威不缓存自身，只出数据）

命中路径：
  热域名：客户端缓存命中 → 零网络查询（最快）
  半热域名：客户端未命中 → 递归器命中 → 1 次 UDP 往返
  冷域名：全链路未命中 → 完整迭代（根+TLD+权威 3-4 次往返）

TTL 的递减与重置：
  权威返回 TTL=300 → 递归器存 300s → 返回给客户端时同样 300s
  → 每层独立计时，各自过期
```

## 5. 权威应答 vs 非权威应答

```text
dig 输出里的关键行（08 章实战）：
  ;; flags: qr aa rd ra
              ↑
   aa（Authoritative Answer）= 应答来自权威服务器本身
   rd = 递归期望；ra = 递归可用

非权威应答：来自递归器缓存（aa 标志缺失）
  → 两种"非权威"：
    ① 递归器缓存命中（正常，但可能是旧数据——TTL 内）
    ② 中间网络设备伪造（污染/劫持——06 章）

排障含义：
  查"真实记录"用 dig @权威服务器直接查（跳过递归器）
  查"用户实际看到的"用 dig @递归器（含缓存效果）
```

## 6. 解析时延分解

```text
一次冷解析的时延账本（公网典型值）：
  客户端 → 递归器：1 RTT（~5-20ms）
  递归器 → 根：1 RTT（~10-30ms，anycast 就近）
  递归器 → TLD：1 RTT
  递归器 → 权威：1 RTT
  总计：3-4 RTT（~30-120ms）

热解析（递归缓存命中）：1 RTT（~5-20ms）
本地缓存命中：0 RTT（0-2ms）

优化手段：
  ① 本地/递归缓存（大头）
  ② DNS 预取（浏览器 prefetch）
  ③ 内网部署递归器（省跨网 RTT）
  ④ HTTPDNS/DoH 直连（跳过 ISP 递归，07 章）
```

## 7. 解析链路的故障定位与优化

### 7.1 每一跳的故障特征

| 故障点 | 现象 | 排查命令 |
|--------|------|---------|
| 客户端 → 递归器 | 全部解析失败/超时 | `dig @递归器IP` 无响应 |
| 递归器 → 根 | 冷域名解析慢（递归器缓存被清） | `dig +trace` 看根跳耗时 |
| 递归器 → TLD | 特定 TLD 失败（如 .com 挂） | `dig com NS +trace` |
| TLD → 权威 | NS 委派错误/权威不可达 | `dig @权威IP` 对比 |
| 权威应答错误 | 记录与预期不符 | `dig @ns1.域名` 直接查权威 |

### 7.2 递归器选型与优化

```text
客户端侧优化：
  ① 就近递归器（内网部署 vs 公共 8.8.8.8——跨网 RTT 差异大）
  ② 多递归器冗余（resolv.conf 配 2 个 nameserver）
  ③ 解析缓存调优（系统/应用层缓存 TTL 内的结果）

服务端侧优化（自建递归器）：
  ① 前置缓存层（dnsmasq/Unbound 的缓存）
  ② 预热（预取热点域名——冷启动解析风暴）
  ③ 监控：缓存命中率、平均解析时延、SERVFAIL 率

公共递归器选择（07 章）：1.1.1.1（快）、8.8.8.8（稳）、内网自建（可控）
```

### 7.3 典型场景：冷启动解析风暴

```text
问题：新集群/新容器大规模启动 → 海量冷域名查询同时穿透
  → 递归器压力暴涨 + 权威被查询风暴打满 → 解析超时连锁

对策：
  ① 应用层预热（启动时预解析关键域名）
  ② 递归器扩容/限速平滑
  ③ 权威侧限速 + 缓存（07 章 RRL）
  ④ 容器镜像内置 /etc/hosts 常用项（绕过 DNS）
```

### 7.4 解析超时的判定与处理

```text
判定（分两类）：
  ① 递归器侧超时：客户端请求发出后无响应
     → 检查递归器负载/连通性（UDP 53 被防火墙拦？）
  ② 权威侧超时：dig +trace 看某跳无响应
     → 该权威不可达/被限速/中间设备丢弃 EDNS 大包

处理顺序：
  换公共递归器对比（8.8.8.8）→ 排除本地问题
  dig +trace 定位故障跳 → 权威 vs 链路
  检查 EDNS（OPT 记录被中间设备丢弃 = 常见疑难，04 章）
  应用层兜底：解析超时重试 + 缓存上次结果（降级）
```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 链路 = 客户端问递归器（递归）+ 递归器逐级问权威（迭代：根→TLD→权威），权威只答自己管辖的域；
> 2. 缓存让热解析从 3-4 RTT 降到 1 RTT 甚至 0——递归器是缓存的主要载体；
> 3. 排障时"查真实记录"用 `dig @权威`，"查用户所见"用 `dig @递归`——aa 标志区分权威/非权威。

**思考题**：

1. 根服务器为什么负载极轻？（→ 3 只做委派 + Anycast）
2. 递归器缓存了"委派信息"吗？（→ 4/3：NS 记录也在缓存里）
3. 权威应答与非权威应答怎么从 dig 判断？（→ 5 aa 标志）
4. 冷解析为什么需要 3-4 个 RTT？（→ 6）
