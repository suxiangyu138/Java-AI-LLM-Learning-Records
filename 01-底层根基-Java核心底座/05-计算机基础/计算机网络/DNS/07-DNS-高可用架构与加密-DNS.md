## 1. 高可用基石：多权威与 Anycast

### 1.1 权威服务器的高可用形态

```text
单点形态（不推荐）：一台权威 → 挂 = 域名全挂（连 IP 都查不到）
高可用形态：
  ① 多 NS：至少 2 个权威（不同机房/不同厂商）
     → 递归器查询失败自动换下一个 NS
  ② Anycast：同一 NS 域名/IP 发布到多地点（BGP 广播）
     → 就近接入（低延迟）+ 单点故障自愈
     → 攻击分散（06 章）

生产形态（托管商提供）：
  阿里云/Cloudflare DNS：anycast 全球节点 + 99.99% SLA
  自建：至少 2 台 + 主备同步（zone transfer AXFR）
```

### 1.2 根服务器为什么"13 台"却不挂

```text
13 个"逻辑根"（a.root-servers.net ~ m.root-servers.net）
  = 13 组 IP，实际 1000+ 物理节点（Anycast）
  → 全球任意地区都有最近的根节点
  → 单节点被攻击/故障 → 其他节点无缝接管
```

## 2. GSLB：DNS 之上的全局负载均衡

```text
GSLB（Global Server Load Balancing）：
  权威服务器根据"客户端来源"动态返回不同的 IP（不是静态记录！）

  用户 A（上海）→ 返回华东节点 IP
  用户 B（纽约）→ 返回美东节点 IP
  用户 C（移动网络）→ 返回移动出口近的节点

关键技术：
  ① 客户端子网（ECS，EDNS 选项）：递归器携带客户端真实 IP 段
     → 无 ECS 时只能按"递归器位置"近似
  ② 健康检查：后端挂 → 自动停止返回其 IP（第 3 节）
  ③ 权重/容量：按节点负载分配

形态对比：
  GSLB（DNS 层）vs LB（流量层，网络高并发体系 08 章）：
   GSLB 管"去哪个机房"（IP 级别）
   LB 管"机房里去哪台机器"（四层/七层转发）
   → 分层组合：GSLB 选机房 → LB 选机器
```

## 3. 健康检查与自动切换

```text
GSLB 的决策输入 = 健康检查结果：
  探测方式：HTTP 探活 / TCP 端口 / ICMP
  探测频率：秒级（5-30s）
  失败判定：连续 N 次失败 → 摘除（不再返回该节点 IP）

切换的真相（05 章 TTL 联动）：
  权威侧已摘除 → 但缓存里的旧 IP 还有效（TTL 内）
  → 用户实际切换时间 ≈ 探测周期 + TTL
  → "秒级容灾"靠：小 TTL + 快探测 + 多节点冗余

生产建议：
  关键域名 TTL ≤ 60s（GSLB 场景）
  故障演练定期验证切换路径（记录已改但用户仍连旧 IP = 演练失败）
```

> 🎯 **核心要点**：DNS 高可用 = **冗余（多 NS + Anycast）+ 感知（健康检查）+ 快速（小 TTL）**——三件事缺一不可，光有"双权威"不感知故障也只是"多了一个挂点"。

## 5. 加密 DNS：DoH / DoT / DoQ

| 协议 | 传输 | 端口 | 特点 |
|------|------|:---:|------|
| **DoH**（RFC 8484） | HTTPS（HTTP/2/3） | 443 | 与 Web 流量同端口（难被防火墙区分）；浏览器集成 |
| **DoT**（RFC 7858） | TLS | 853 | 专用端口（易被防火墙识别拦截）；实现简单 |
| DoQ（RFC 9250） | QUIC | 853 | 低延迟 + 0-RTT（新兴） |

```text
DoH vs DoT 的核心差异：
  DoT：独立 853 端口 → 可被"按端口阻断"（某些地区/防火墙）
  DoH：443 端口 + HTTPS 伪装 → 难以识别 → 穿透性强
  → 企业管控的视角：DoH 更难拦截（安全策略挑战）
```

## 6. 2026 加密现状与浏览器默认

```text
（2026-08 检索数据）
全球 DNS 流量加密比例：~20%（DoH + DoT）
  → 其余 ~80% 仍是明文（ISP 可窥探）
  Android 上 DoT 占比 ~15%（移动端最高）

浏览器/OS 默认（2020 年起逐步）：
  Firefox：美国用户 DoH 默认（2020）
  Chrome："DNS Secure"（2020）——OS 解析器支持时自动升级 DoH
  Windows 11：设置里可配 DoH 模板
  macOS：mobileconfig 配置 DoH

DoH 采用史：0% → 30%（两年，浏览器部署的威力——零用户配置）
```

> ⚠️ **企业安全视角**：DoH 让内网 DNS 管控出现缝隙（客户端直连公共 DoH）——企业方案：内网部署自己的 DoH 解析器 + 强制浏览器策略（Chrome DnsOverHttpsMode）+ 防火墙放行名单。

## 7. HTTPDNS：移动端绕开传统解析

```text
问题（移动端）：
  ① ISP 递归器劫持/污染/缓存异常 → 解析结果不可信
  ② 运营商 LocalDNS 与权威不一致 → 调度失真（GSLB 失效）
  ③ 解析慢（LocalDNS 递归链路差）

HTTPDNS 方案：
  客户端直接 HTTP 请求"解析服务"（如 223.5.5.5 的 HTTP API）
  → 绕过 LocalDNS，直接拿权威级结果
  → 附带：精准调度（ECS 精确到客户端）、防劫持（HTTPS）、秒级切换

应用：移动 App 标配（短视频/直播/支付类对解析质量敏感）
  实现：SDK 集成 + 结果缓存 + 失败回退传统 DNS
```

## 8. 域名迁移与切换的工程流程

### 8.1 权威 DNS 服务商迁移（最敏感的 DNS 操作）

```text
迁移 = 改 NS 记录（全球生效受旧 NS 的 TTL 约束）

标准流程：
  □ 1. 新服务商建好全部 Zone 记录（双写——新旧一致）
  □ 2. 对比校验：脚本比对新旧权威的所有记录
  □ 3. 提前降 NS 记录的 TTL（1-2 天，05 章 SOP）
  □ 4. 切换 NS 记录（指向新服务商）
  □ 5. 观察：dig @新权威 验证；监控解析错误率
  □ 6. 保留旧服务商 2 个 TTL 周期（回滚窗口）
  □ 7. 确认后注销旧服务商（防"僵尸记录"）

⚠️ 迁移事故高发点：
  新 Zone 漏记录（邮件 MX 缺失 → 邮件中断）
  NS 记录在旧服务商还有缓存 → 双活期不一致
  DNSSEC 密钥未迁移 → 解析 SERVFAIL（06 章）
```

### 8.2 域名切换的三种形态对照

| 形态 | 改动点 | 生效速度 | 风险 |
|------|--------|:---:|------|
| 改 A/AAAA | 记录值 | TTL 内 | 低（可回滚） |
| 改 CNAME（接入 CDN） | 记录类型 | TTL 内 | 中（需确认目标有效） |
| 改 NS（换托管） | 委派 | 旧 TTL + 传播 | 高（全量记录迁移） |

### 8.3 演练建议

```text
□ 定期演练：GSLB 故障切换演练（摘除节点 → 验证流量迁移）
□ 快照机制：迁移前全量导出记录（回滚即恢复）
□ 监控：解析成功率、解析时延、SERVFAIL 率的告警阈值
→ 域名是"数字资产"：变更流程化 + 监控常态化
```

## 9. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 高可用 = 多权威（NS 冗余）+ Anycast（就近+抗 D）+ GSLB（健康检查动态调度），切换速度受"探测周期 + TTL"约束；
> 2. 加密 DNS 三件套：DoH（443 伪装，浏览器默认）、DoT（853 专用）、DoQ（QUIC 低延迟）——2026 年加密流量约 20%，浏览器与 OS 已默认支持；
> 3. 移动端用 HTTPDNS 绕开运营商 LocalDNS（防劫持 + 精准调度）；企业需管好 DoH 缝隙（自建加密解析 + 浏览器策略）。

3. 故障切换时间由哪两个因素决定？（→ 3）
