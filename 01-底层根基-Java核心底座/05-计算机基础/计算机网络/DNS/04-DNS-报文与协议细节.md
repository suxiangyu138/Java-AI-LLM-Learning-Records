## 1. 报文结构：三段式

```text
DNS 报文 = 头部（固定 12 字节）+ 问题段 + 回答段（+授权段+附加段）

┌────────────────────────────┐
│ 头部（12 字节，固定）        │ ← 会话 ID + 标志 + 计数
├────────────────────────────┤
│ 问题段（Question）          │ ← 查询什么（域名+类型）
├────────────────────────────┤
│ 回答段（Answer）            │ ← 查询结果（RR 列表）
├────────────────────────────┤
│ 授权段（Authority）         │ ← 委派/权威信息（NS 等）
├────────────────────────────┤
│ 附加段（Additional）        │ ← 附带信息（A 记录、EDNS 选项）
└────────────────────────────┘
```

## 2. 12 字节头部与标志位

```text
 0                   1                   2                   3
├─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┤
│            Transaction ID（16）   │   标志（16）              │
├─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┤
│      QDCOUNT（问题数）           │      ANCOUNT（回答数）      │
├─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┬─┤
│      NSCOUNT（授权数）           │      ARCOUNT（附加数）      │
└─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┴─┘
```

| 字段 | 位宽 | 含义 |
|------|:---:|------|
| Transaction ID | 16 | **会话标识**（投毒攻击的对齐对象，06 章） |
| QR | 1 | 0=查询 1=响应 |
| Opcode | 4 | 标准查询=0 |
| AA | 1 | 权威应答（02 章） |
| TC | 1 | 截断标志（响应被截断 → 客户端应换 TCP） |
| RD | 1 | 递归期望（客户端 → 递归器） |
| RA | 1 | 递归可用（递归器应答） |
| RCODE | 4 | 状态码（NOERROR/NXDOMAIN/SERVFAIL/REFUSED） |
| 计数四连 | 16×4 | 问题/回答/授权/附加各多少条 |

```text
常用 RCODE：
  NOERROR(0)：正常（可能 0 条回答 = 存在但无该类型）
  NXDOMAIN(3)：域名不存在（负缓存的对象，05 章）
  SERVFAIL(2)：递归器上游失败（权威不可达/超时）
  REFUSED(5)：递归器拒绝（策略/仅内网）
```

## 3. 问题段与回答段

```text
问题段（QDCOUNT=1 典型）：
  QNAME（域名，长度前缀编码）QTYPE（A=1/AAAA=28/MX=15...）QCLASS（IN=1）

回答段（ANCOUNT 条 RR）：
  名称 + 类型 + 类 + TTL + RDLENGTH + RDATA
  → 与 03 章五元组一一对应

长度前缀编码（wire format）：
  www.example.com → 03www07example03com00
  ←每标签 1 字节长度 + 内容，00 结束
  → 指针压缩：重复的域名（回答段常复用问题段）用 2 字节指针
```

## 4. UDP 53 为主与 TCP 回退

| 传输 | 何时用 | 原因 |
|------|--------|------|
| **UDP 53** | 绝大多数查询 | 快（1 个包一来回）、无连接开销 |
| TCP 53 | ① 响应截断（TC=1）② 大响应（zone 传输 AXFR/IXFR）③ EDNS 无法协商 | 可靠、无 512B 限制 |

```text
现代趋势：UDP 大包（EDNS）解决 90% 的"截断问题"，
  TCP 主要留给区域传输与极端大响应
K8s 内网场景：DNS 查询量大 → 注意 UDP 队列与 conntrack 压力
```

## 5. EDNS(0)：突破 512 字节

```text
历史：DNS 应答最大 512 字节（UDP），大响应只能截断+TCP（慢）
EDNS(0)（RFC 6891）：
  附加段带 OPT 伪记录（类型 41）：
    UDP 载荷大小（客户端通告，典型 1232-4096）
    扩展 RCODE、DNSSEC DO 位（要求签名记录）
    ECS（客户端子网）等选项

现代必需性：
  DNSSEC 记录（RRSIG/NSEC）让响应轻松超 512B → 无 EDNS 无 DNSSEC
  大 TXT 记录（SPF/DKIM 多段）也需大 UDP
  2026 现状：主流递归器/权威全面支持；企业防火墙/中间设备
  对 OPT 伪记录的丢弃/篡改仍是疑难杂症
```

> 🎯 **核心要点**：EDNS(0) 是"DNS 的现代底座"——UDP 大包 + DNSSEC + ECS 都依赖它。排障时"解析超时/截断"先看中间设备是否处理 OPT 记录。

## 6. 放大攻击：报文级原理

```text
DNS 反射放大（06 章详述，此处给报文级机制）：
  攻击者伪造源 IP = 受害者
  发送小查询（如 ANY example.com，~60B）
  权威返回大响应（几百字节~几 KB）
  → 流量放大系数可达 30-50×

  ┌────────┐  小查询(源=受害者)  ┌────────┐
  │ 攻击者 ├────────────────────→│ 递归器 │
  └────────┘                     │        │
                                 │ 放大30x│
  ┌────────┐  大响应 → 受害者     │        │
  │ 受害者 │←───────────────────┤        │
  └────────┘                     └────────┘

防御：
  递归器侧：限速、限制 ANY、RRL（响应限速）、关闭开放递归
  受害者侧：DDoS 防护（Anycast/清洗）
```

## 7. 抓包解读 DNS 报文

### 7.1 tcpdump 抓 DNS

```bash
# 抓 DNS 查询/响应（UDP 53 或 TCP 53）
tcpdump -i eth0 -nn port 53 -c 10

# 输出解读
14:22:01.123 10.0.0.1.53123 > 8.8.8.8.53: 33154+ A? example.com. (29)
              └源端口┘     └目的┘  └事务ID┘ └类型┘└域名┘    └报文长度┘
14:22:01.145 8.8.8.8.53 > 10.0.0.1.53123: 33154 1/0/1 A 93.184.215.14 (45)
                                         └ID匹配┘└回答/授权/附加数┘└答案┘
```

### 7.2 关键判读点

| 特征 | 含义 |
|------|------|
| 事务 ID 匹配（33154 ↔ 33154） | 应答与查询对应（不匹配 = 异常/投毒嫌疑） |
| `1/0/1`（回答/授权/附加） | 回答数、委派信息数、附加信息数 |
| 响应中带 `TC` 标志 | 截断 → 客户端应重试 TCP |
| 响应中带 `RCODE` 非 0 | NXDOMAIN/SERVFAIL/REFUSED（04 章状态码） |
| 大响应（>512B） | EDNS 协商生效（OPT 记录） |

### 7.3 投毒攻击的抓包特征（06 章呼应）

```text
可疑特征：
  ① 应答的事务 ID 与查询不匹配却被接受（递归器漏洞）
  ② 应答中夹带"额外记录"（权威段/附加段异常丰富——Kaminsky 手法）
  ③ 同一查询的多个应答竞争（攻击者在爆破）
  → 防御视角：现代递归器随机端口 + 0x20 编码让伪造应答"对不上号"
```

### 7.4 报文大小与性能

```text
报文大小决定查询成本：
  小查询（~30-60B）：1 个 UDP 包一来回（最优）
  大响应（DNSSEC/大 TXT，几百 B~KB）：依赖 EDNS 协商
  超 4096B：递归器可能降级 TCP（多一个 RTT）

优化要点：
  ① 记录精简（TXT 合并/减少冗余 NS）
  ② EDNS 通告合理（1232B 是 IPv6 路径安全值，勿贪大）
  ③ 避免 ANY 查询（响应巨大 = 放大器风险，06 章）
  ④ 监控：大响应比例（>512B 的查询占比）作为健康指标

→ 报文大小管理 = DNS 性能与安全的交叉点
```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 报文三段式（头部 12B + 问题 + 回答/授权/附加），关键标志：TC（截断）、AA（权威）、RCODE（NXDOMAIN/SERVFAIL）；
> 2. UDP 53 为主、TCP 回退（截断/大传输）；EDNS(0) 用 OPT 伪记录把 UDP 提到 4KB——DNSSEC 的前提；
> 3. 放大攻击 = 伪造源 IP + 小查询换大响应（放大 30-50×），防御在递归器侧（RRL/关闭开放递归）。

**思考题**：

1. TC=1 表示什么？客户端该怎么做？（→ 2/4）
2. 为什么没有 EDNS 就没有 DNSSEC？（→ 5）
3. NXDOMAIN 与 SERVFAIL 的差异？（→ 2 RCODE）
4. 放大攻击为什么选"开放递归器"做放大器？（→ 6）
