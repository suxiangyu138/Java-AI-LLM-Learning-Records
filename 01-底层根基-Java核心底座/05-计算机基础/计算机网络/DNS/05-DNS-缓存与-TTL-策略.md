# DNS 缓存与 TTL 策略

> 缓存是 DNS 的性能引擎，TTL 是它的"一致性旋钮"：TTL 越大越快（但变更生效慢），越小越灵活（但权威压力大）。发版前降 TTL、故障切换靠 TTL、缓存投毒打的是 TTL——**TTL 是 DNS 工程里最重要的一个数**

## 1. 缓存体系：从浏览器到递归器

```text
四级缓存（每级独立计时、独立命中）：
  ① 浏览器缓存：chrome://net-internals/#dns（Chrome）
     → 命中：0 网络请求（最快）
  ② OS 缓存：系统解析器（libc/resolver）
     → 命中：无系统调用外的网络
  ③ 递归器缓存：ISP/公共递归器（8.8.8.8/1.1.1.1/内网）
     → 命中：1 次 UDP 往返
  ④ 权威服务器：**不缓存自己的数据**（数据源，只出数据）

链路视角（02 章）：越靠近客户端命中，时延越低
```

| 层级 | 缓存时长控制 | 谁能清理 |
|------|------------|---------|
| 浏览器 | TTL（+浏览器策略） | 清缓存/F5 |
| OS | TTL | ipconfig /flushdns（Win）/dscacheutil（mac） |
| 递归器 | TTL（+厂商策略） | 管理员清理（如 `rndc flush`） |

> 🎯 **核心要点**：TTL 是"所有缓存层"的统一时钟——**权威把 TTL 写进记录，每一级缓存都按它倒计时**。改 TTL 影响的是"缓存多久"，不是"缓存在哪"。

## 2. TTL 机制：递减、重置与覆盖

```text
递减：记录进入缓存时开始倒计时（权威返回 TTL=300 → 缓存里每秒 -1）
过期：倒计时到 0 → 记录被丢弃 → 下次查询重新穿透
重置：重新查询拿到新记录（新 TTL 重新计时）

TTL 的三种设置位置（03 章）：
  ① Zone 级 $TTL：默认值（给所有记录）
  ② 记录级 TTL：单条覆盖
  ③ SOA negative TTL：负缓存专用

组合语义：CNAME 链取 min(TTL)——链上任何一节过期都会整体重新解析
```

## 3. TTL 的工程权衡

| 维度 | TTL 小（如 30s） | TTL 大（如 86400s） |
|------|:---:|:---:|
| 解析速度 | 缓存少 → 常穿透（慢） | 缓存长 → 快 |
| 权威压力 | 高（查询穿透多） | 低 |
| 变更生效 | **快**（30s 内全球生效） | 慢（最长 1 天） |
| 故障恢复 | 快（换 IP 迅速生效） | 慢（用户持续访问旧 IP） |
| 典型用途 | 动态调度/故障演练/发版窗口 | 静态资源/CDN 记录/稳定服务 |

```text
生产默认值参考：
  域名 A 记录：300-600s（平衡）
  CDN/CNAME 记录：60-300s（调度灵活）
  静态资源相关（很少改）：3600+
  紧急变更前：提前降到 60s（见第 4 节）
```

## 4. 发版与故障切换的 TTL 策略

### 4.1 发版（IP 切换）标准流程

```text
① 提前 1-2 天：TTL 降到 60s（让全球缓存"缩水"）
   → 递归器/浏览器上的旧记录会在 1 分钟内过期
② 切换：修改 A 记录指向新 IP（生效 = 1 个 TTL）
③ 观察稳定后：TTL 恢复 300-600s
   → 若切错了，60s 内可回滚

为什么不能直接改：
  旧 TTL=86400 → 改记录后，全球缓存仍持有旧 IP 最多 24h
  → 用户"一半新一半旧"持续一天
```

### 4.2 故障切换的两种形态

| 形态 | 机制 | 切换速度 |
|------|------|:---:|
| 主动切换 | 手动改记录（提前降 TTL） | 分钟级 |
| 被动容灾（GSLB 健康检查） | 监控发现权威后端挂 → 自动改应答（07 章） | 秒-分钟级（受 TTL 限制） |

```text
关键认知：DNS 故障切换的速度上限 = TTL + 探测周期
  → 真·秒级容灾不能只靠 DNS（要负载均衡层健康检查，07 章）
```

## 5. 负缓存：查无此名的缓存

```text
负缓存（Negative Caching）："不存在"的答案也缓存
  NXDOMAIN（域名不存在）：按 SOA negative TTL 缓存（默认 300s）
  无该记录类型（NOERROR 0 条）：同样缓存

作用：
  防止"不存在的域名"反复穿透（防递归器被垃圾查询打爆）
  → 拼写错误/新注册域名的解析风暴保护

工程影响：
  新注册域名/新加记录 → 用户可能拿到"不存在"最长 negative TTL 时间
  → 新建域名时把 SOA negative TTL 设小（如 60s）
```

## 6. 缓存投毒：TTL 的攻击面

```text
投毒（Cache Poisoning）原理：
  攻击者伪造 DNS 响应（冒充权威）
  递归器若接受 → 毒记录进入缓存 → 用户访问被导向恶意 IP
  → 攻击窗口 = TTL 时长（毒记录活多久，攻击持续多久）

  Kaminsky 攻击（2008，06 章详述）：不依赖"猜对已有缓存"，
  通过猜测 Transaction ID + 端口批量爆破注入
  → 防御：0x20 编码、端口随机化、DNSSEC

TTL 视角：毒记录 TTL 常被设为最大值（86400）→ 受害者中毒后"一天内反复被导向" 
```

## 7. 缓存相关的排障

| 症状 | 缓存视角的判断 |
|------|---------------|
| 改了记录不生效 | 逐级检查：权威（dig @权威）→ 递归（dig @8.8.8.8）→ 本地 |
| 部分用户新 IP、部分旧 IP | 缓存渐进过期（TTL 未提前降）——正常但需等待 |
| 新域名解析不了 | 负缓存（negative TTL 内）→ 等过期或清递归缓存 |
| 不同地区结果不一致 | GSLB 正常差异 vs 递归器缓存不一致 |
| 解析忽快忽慢 | 缓存命中率波动（TTL 太小 + 冷热不均） |

```bash
# 缓存链路排查三步
dig @ns1.example.com www.example.com A   # ① 权威真相
dig @1.1.1.1 www.example.com A +ttlid    # ② 公共递归所见（看 TTL 剩余）
nslookup www.example.com                 # ③ 本地缓存所见
```

## 8. TTL 决策速查表与变更 SOP

### 8.1 场景化 TTL 推荐

| 场景 | TTL 建议 | 理由 |
|------|:---:|------|
| 普通网站 A 记录 | 300-600s | 平衡速度与灵活 |
| CDN CNAME | 60-300s | 调度灵活（节点调整快） |
| 邮件 MX/SPF | 3600+ | 极少变更，查询量大 |
| 故障演练/发版窗口 | 60s（提前 1-2 天降） | 切换/回滚快 |
| GSLB 动态调度 | 30-60s | 健康检查联动（07 章） |
| 静态资源子域 | 86400 | 几乎不变 |
| 新建域名/新记录 | negative TTL 设 60s | 防负缓存坑 |

### 8.2 DNS 变更标准流程（SOP）

```text
□ 1. 评审：变更内容、影响面（是否影响邮件/证书验证）
□ 2. 提前降 TTL（变更前 1-2 天，至少覆盖旧 TTL 时长）
□ 3. 变更：修改记录（serial 递增，03 章）
□ 4. 验证：dig @权威 → @公共递归 → 本地（02 章三视角）
□ 5. 观察：全球生效（旧 TTL 时间内仍有渐进）
□ 6. 回滚预案：保留旧记录值，随时切回
□ 7. 稳定后恢复 TTL（观察 24-48h）
```

### 8.3 常见 TTL 事故复盘

```text
事故一：直接改 A 记录未降 TTL（旧 TTL=86400）
  → 用户最长 24 小时访问旧 IP → 割接事故
事故二：新域名解析"时有时无"
  → 负缓存（negative TTL）导致：先查无 → 缓存"不存在" → 加记录后仍报错
事故三：多级 TTL 叠加
  → CNAME 链取 min（03 章）——链上任一节点缓存长都会拖慢整体生效
```

## 9. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 四级缓存（浏览器/OS/递归器/权威=数据源）共用 TTL 时钟；命中越靠客户端越快；
> 2. TTL 是"速度与灵活性"的旋钮：默认 300s 起步，发版/切换前降到 60s，稳定后恢复——这是 DNS 变更的标准动作；
> 3. 负缓存保护递归器、投毒利用 TTL 延长攻击窗口——TTL 同时是工程旋钮与安全变量。
