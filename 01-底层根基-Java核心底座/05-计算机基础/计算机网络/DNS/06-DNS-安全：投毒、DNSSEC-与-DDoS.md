## 1. DNS 的信任模型缺陷

```text
经典 DNS（无 DNSSEC）的信任链：明文 + 无验证
  ① 查询与响应都明文 → 中间人可看可改（ISP 劫持/运营商广告注入）
  ② 递归器"相信"收到的响应 → 无法区分真伪（凭 16 位 ID + 端口猜）
  ③ 权威与递归之间的链路无认证 → 谁都能冒充

三个现实后果：
  投毒（缓存被伪造响应污染）
  劫持（中间人改应答 → 用户被导向恶意站）
  窥探（明文查询 → ISP/攻击者看到你查了什么）

→ DNSSEC 解决"验证"，DoH/DoT 解决"加密"（07 章）
→ 2026 现实：两者都未全覆盖（校验率 36%、加密流量 20%）
```

## 2. 缓存投毒与 Kaminsky 攻击

### 2.1 经典投毒（2008 前的形态）

```text
目标：让递归器缓存"伪造的 A 记录"（www.example.com → 恶意 IP）

经典攻击流程：
  ① 递归器缓存里"没有"目标记录（等它过期或首次查询）
  ② 攻击者向递归器发"询问"（www.example.com A）——迫使递归器发起真实查询
  ③ 同时疯狂伪造"响应"（猜测 Transaction ID 与源端口，04 章）
  ④ 猜中 → 递归器接受伪造应答 → 缓存中毒

猜中概率：16 位 ID × 端口（旧实现固定端口）
  → 传统 ID 爆破：2^16 组合，暴力可行
```

### 2.2 Kaminsky 攻击（2008，Dan Kaminsky）

```text
突破：不需要"等目标记录过期"——攻击任意不存在的随机子域名！
  ① 问递归器：随机名. example.com（如 abc123.example.com）
      → 递归器必然未缓存 → 必然向上游查询
  ② 同一应答里塞入"伪造的 example.com NS/额外记录"
      → 递归器把 example.com 的 NS 也缓存了 → 后续查询全被导向恶意权威
  ③ 海量随机子域名循环 → 把整个域"接管"

危害升级：
  经典投毒：一次只能毒一条记录（且要等过期）
  Kaminsky：批量毒 NS → 整个域被劫持，且可重复利用
  → 该发现直接推动了 DNSSEC 的加速部署（2008 年后）
```

## 3. 缓解手段：随机化、0x20 与端口

| 手段 | 机制 | 效果 |
|------|------|------|
| **源端口随机化** | 递归器用随机端口发查询（不再是固定 53） | 猜测空间 = ID × 端口 = 2^16 × 2^16（暴力不可行） |
| **Transaction ID 随机** | ID 随机化（基础防御） | 同上的一部分 |
| **0x20 编码** | 查询域名随机大小写，响应必须逐字符匹配 | 攻击者难预测大小写组合（再次扩大猜测空间） |
| **DNSSEC** | 签名验证（根治） | 伪造响应直接验证失败 |
| 权威侧 | 递归器仅接受"匹配问题段"的响应 | 基础过滤 |

```text
现状评估：
  现代递归器（BIND 9.5+/Unbound/knot）默认端口随机化
  → Kaminsky 式爆破在"现代递归器"上已不可行（猜测空间足够大）
  → 但网络中间设备（劫持者）仍可篡改 —— 这是 DNSSEC/DoH 的战场
```

> 🎯 **核心要点**：投毒攻防是"猜测空间"的军备竞赛——随机化把难度从 2^16 提到 2^32+，现代递归器已防住"爆破型"投毒；**防不住的**是中间人篡改（需要 DNSSEC）与窥探（需要加密）。

## 4. DNSSEC：签名链与验证

### 4.1 机制

```text
DNSSEC（RFC 4033-4035）：给 DNS 数据加数字签名，验证"数据确实来自权威"

签名链（信任锚定）：
  根（信任锚，内置）→ .com（DS→KSK）→ example.com（DS→KSK）→ 记录（RRSIG）

关键记录：
  DNSKEY：域的公钥（KSK 密钥签名密钥 / ZSK 区域签名密钥）
  DS：子域的 DNSKEY 摘要（父域发布的"指纹"，连接信任链）
  RRSIG：每条记录的签名
  NSEC/NSEC3：证明"不存在"（防枚举/防 NXDOMAIN 伪造）

验证流程：
  查询 → 递归器拿到 RRSIG → 用 DNSKEY 验签
  → DNSKEY 用父域 DS 验证（逐级到根）
  → 验证失败 → SERVFAIL（拒绝伪造应答）
```

### 4.2 价值与代价

| 价值 | 代价 |
|------|------|
| 防投毒/防篡改（数据真实） | 部署复杂（密钥轮换/签名管理） |
| 防 NXDOMAIN 伪造（NSEC） | 响应变大（RRSIG 加量）→ 依赖 EDNS |
| 为 DoH 提供"端到端信任" | NSEC 枚举漏洞（NSEC3 缓解但复杂） |

## 5. DNSSEC 的部署现状（2026）

```text
（2026-08 检索，APNIC Labs 2026-04 测量）

验证率（用户侧"经过完整验证递归器"）：
  全球：~36%
  欧洲领先：~46%（瑞典 ~86%、荷兰 ~76%）
  美/亚多数区域低于全球均值

签名率（域侧）：
  .com 区域签名率：~4-5%（远低于验证率！）
  .nl：~60%（注册局 SIDN 激励计划的成功样本）
  → 全球数百个 TLD 中仅少数强制/激励签名

结论：
  "能验证"的递归器（36%）>> "被签名"的域（个位数百分比）
  → 大量用户解析"未签名域"时 DNSSEC 无验证意义（返回非签名数据）
  → 20 年部署史：DNSSEC 是"技术正确但推广缓慢"的经典案例
```

> ⚠️ **工程提醒**：域名要不要上 DNSSEC？——**先确认托管商支持 + 密钥轮换流程**；错误部署（密钥丢失/DS 不匹配）会导致整个域解析失败（SERVFAIL），比不部署更严重。

## 6. DDoS：反射放大与 Anycast 对抗

### 6.1 反射放大（04 章已给报文原理）

```text
攻击链：伪造源 IP（受害者）+ 小查询 → 大响应放大 30-50×
放大器：开放递归器（允许任何人查询）——最大的放大器
实测：DNS 放大是 DDoS 攻击的常客（2026 年 DDoS 报告仍列前茅）

防御：
  ① 关闭开放递归（只服务内网/授权客户）
  ② 递归器 RRL（Response Rate Limiting，响应限速）
  ③ 限制 ANY 查询（放大器的最爱——返回所有记录）
  ④ 权威侧：限速 + 分片防护
```

### 6.2 Anycast 抗 DDoS

```text
Anycast：同一 IP 在多个物理地点广播（BGP）
  → 全球用户自动就近接入（低延迟）
  → 攻击流量被"分散"到最近节点 → 单点压力下降
  → 攻击者无法集中打一个目标（清洗/容量分散）

部署形态：
  根服务器（13 个逻辑根 = 数百物理节点）
  公共递归器（1.1.1.1 在 300+ PoP；8.8.8.8 全球）
  权威 DNS 托管（Cloudflare/Akamai 等）

效果：攻击者打"最近的节点"，只影响局部；配合清洗流量持续服务
```

## 7. 企业 DNS 安全清单

```text
□ 递归器：仅内网开放（防开放递归放大器）；开启端口随机化
□ 权威：双区域多节点 + 限速；开启 RRL
□ 域名：评估 DNSSEC（先确认托管商支持与密钥轮换流程）
□ 传输：内网 DNS 之间考虑 DoT（防中间人改内网解析）
□ 客户端：部署 DoH/DoT 公共解析（07 章）或内网加密解析
□ 监控：异常查询量（放大攻击前兆）、SERVFAIL 率、解析一致性
□ 防枚举：重要域名用 NSEC3 防 zone 遍历
□ 测试：定期验证 dnspod/权威的响应未被中间设备篡改
```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. DNS 信任模型缺陷 = 明文 + 无验证；投毒攻防是"猜测空间"军备竞赛（随机化已防住爆破，中间人篡改仍需 DNSSEC）；
> 2. DNSSEC 用 DS→DNSKEY→RRSIG 签名链根治伪造，但 2026 现实：验证率 ~36%、.com 签名率仅 4-5%——部署前确认托管商支持；
> 3. DDoS 侧：关开放递归 + RRL 防放大；Anycast 分散流量是权威/递归侧的抗 D 标配。
