# DNS 的本质与域名空间

> DNS（Domain Name System）把"人类可读的域名"翻译成"机器可用的 IP"——但它远不止翻译：别名、邮件路由、服务发现、流量调度都长在域名空间这棵树上。理解层级命名空间，是理解一切 DNS 行为的地基

## 1. DNS 的三重职责

```text
① 解析（正向）：域名 → IP
     www.example.com → 93.184.215.14
 ② 反向解析：IP → 域名（PTR 记录，反查域 in-addr.arpa）
     → 日志审计、邮件反垃圾（PTR 校验）
 ③ 服务发现与元数据：
     邮件路由（MX）、服务定位（SRV）、
     安全授权（CAA）、域名验证（TXT/SPF/DKIM）
```

> 🎯 **核心要点**：DNS 是"互联网的目录服务"——不只是 A 记录。生产里大量系统（邮件、证书签发、K8s 服务发现、CDN 调度）都依赖 DNS 记录承载元数据。

## 2. 为什么需要 DNS：IP 直连的四个问题

| 问题 | 说明 | DNS 的解法 |
|------|------|-----------|
| 人类记不住 | IP 无意义、会变 | 域名可读、稳定 |
| 服务迁移 | IP 变了客户端不知道 | 域名不变，改记录 |
| 负载均衡 | 单 IP = 单点 | 一个域名多个 A 记录（DNS 轮询） |
| 就近接入 | 全球用户需要就近节点 | GSLB 按位置返回不同 IP（07 章） |

```text
核心价值：解耦"名字"与"位置"
  → 名字（域名）稳定，位置（IP）可变
  → 所有 CDN/云厂商的流量调度都建立在"改 DNS 记录"这个动作上
```

## 3. 层级域名空间

```text
域名空间是一棵树，从根向下分层：

                     .（根）
            ┌─────────┼─────────┐
           com      org       cn      ← TLD（顶级域）
          ┌──┴──┐             │
       example  baidu       com.cn   ← 二级域（注册域）
          │                   │
        www  api           example.com.cn  ← 子域（三级+）
                                    （sub.example.com.cn）

完全限定名（FQDN）：www.example.com.   ← 从叶子到根，以点结尾
```

| 层级 | 例子 | 由谁管理 |
|------|------|---------|
| 根 | `.`（13 个根服务器集群） | ICANN |
| TLD | `com`、`org`、`cn` | 注册局（Registry） |
| 二级域 | `example.com` | 注册人（Registrant） |
| 子域 | `api.example.com` | 注册人自行划分 |

## 4. FQDN 与名称规则

```text
FQDN（Fully Qualified Domain Name）：完整的、以根结尾的域名
  www.example.com.     ← 完整（结尾点 = 根）
  www.example.com      ← 常见写法（省略结尾点，语义相同）

名称规则：
  总长 ≤ 253 字符；单标签 ≤ 63 字符
  字符：字母/数字/连字符（-）
  大小写不敏感（DNS 存储时规范化小写）
  下划线（_）仅用于特殊记录（SRV/TXT 的 _service._proto）

相对名 vs 绝对名：
  BIND zone 文件里 example.com. 结尾点是"绝对"；不带点是"相对当前域"
  → 写配置最常见的坑（08 章）
```

## 5. TLD 分类与注册体系

### 5.1 TLD 三分类

| 分类 | 例子 | 说明 |
|------|------|------|
| 通用顶级域（gTLD） | com、org、net、**newgTLD**（.app、.dev、.xyz） | 2013 年后新增数百个 |
| 国家/地区码（ccTLD） | cn、jp、de、uk | 按国家分配 |
| 基础设施域 | arpa（反向解析） | 特殊用途 |

### 5.2 注册生态链

```text
ICANN（管理根/政策）
  └─ 注册局（Registry，如 Verisign 管 .com）
       └─ 注册商（Registrar，如阿里云/GoDaddy）
            └─ 注册人（Registrant，你）
DNS 托管（Hosting）：注册商或第三方提供权威服务器
  → 关键概念：域名"注册"在注册商，"解析"靠权威 DNS 服务器（可分离）
```

> 💡 **常见误解**：买了域名 ≠ 有 DNS 解析——注册后必须把 NS 记录指向你的权威服务器（或托管商的），解析才生效。

## 6. DNS 的分布式本质

```text
DNS 为什么是"分布式"的（而非中央数据库）：
  ① 单点会挂：集中式解析 = 互联网的致命单点
  ② 数据量爆炸：全球域名数亿，单库不可行
  ③ 写少读多：改记录极少，查记录极多 → 缓存 + 分层分担

设计推论：
  每个域只在自己"授权"的权威服务器上管理记录（授权 = 数据自治）
  查询靠"委派链"（根委派 TLD，TLD 委派二级域……）
  缓存让热点查询不穿透到权威层

规模感（2026 检索）：
  全球公共递归解析器日均处理 1.5+ 万亿次查询
  Google Public DNS 单家超 1 万亿次/日
```

### 6.1 DNS 在生态中的三个经典联动

```text
① CDN 接入（域名 + 权威记录 + GSLB）：
   域名 NS 指向 CDN 托管 → CDN 权威按客户端位置返回节点 IP
   → 一次"改 NS 记录"完成 CDN 接入（07 章 GSLB 详述）

② 证书签发验证（域名归属证明）：
   Let's Encrypt 等 CA 用 DNS-01 挑战：要求你在域名 TXT 记录里
   放一个随机 token → 证明"你控制该域" → 签发证书
   → 自动化签发的前提是"能快速改 DNS 记录"（API 化的 DNS 托管）

③ 邮件投递信誉：
   接收方查 SPF（TXT）/DKIM（TXT）/MX/PTR 验证发件域
   → DNS 记录直接决定邮件进收件箱还是垃圾箱（03 章）
```

## 7. 域名空间的工程实践

### 7.1 内网域设计规范

```text
内部域名建议（RFC 6762 保留域）：
  ✅ .internal / .local（mDNS 保留）——绝不注册、绝不冲突
  ❌ 用公共域名的子域做内网（如 corp.example.com）
     风险：与公网解析冲突、证书管理混乱、子域劫持面
  → 现代推荐：内网独立域（如 corp.internal）+ 公网域分离

命名规范：
  环境分离：dev/api/prod 子域 vs 独立域
  服务命名：<service>.<env>.<domain>（K8s 风格：svc.ns.cluster.local）
  避免：下划线（除 SRV/TXT 特殊前缀）、大小写混用
```

### 7.2 域名生命周期管理

```text
□ 注册：注册商选择（续费提醒/转移政策）
□ 到期续费：过期后注册商有赎回期（redeem period）——成本极高
□ 转移：ICANN 转移锁（60 天规则）
□ 隐私保护：WHOIS 隐私服务
□ 审计：域名清单 + 负责人 + 到期日（防"域名遗忘"事故）

⚠️ 常见事故：
  域名到期未续 → 被抢注 → 业务全线故障 + 品牌损失
  子域无人管理 → 子域接管（subdomain takeover）漏洞
   → 定期扫描无主子域（CNAME 指向已释放资源 = 接管风险）
```

### 7.3 证书与 DNS 的联动（03 章回顾）

```text
DNS-01 挑战依赖"能快速改 DNS 记录"（自动化签发的关键）：
  ① DNS 托管 API 化（改 TXT 记录自动化）
  ② 权威更新延迟（TTL 小 → 签发快）
  → 证书自动化（ACME）与 DNS 自动化是同一套基础设施
```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. DNS 三重职责：解析（A/AAAA）、服务元数据（MX/SRV/CAA/TXT）、反向（PTR）——远不止"翻译"；
> 2. 域名空间是分层树（根→TLD→二级→子域），FQDN 以点结尾，委派链决定谁管理哪一层；
> 3. DNS 是"读多写少"的分布式系统：分层授权 + 缓存 + 委派——这决定了它的性能（缓存）与安全（投毒）特性。
