## 1. 五类状态码总览

| 类别 | 含义 | 代表 |
|:---:|------|------|
| 1xx | 信息性（继续/升级） | 100 Continue、**103 Early Hints** |
| 2xx | 成功 | 200 OK、201 Created、204 No Content |
| 3xx | 重定向 | 301/302/303/304/307/308 |
| 4xx | 客户端错误 | 400/401/403/404/405/409/422/429 |
| 5xx | 服务端错误 | 500/502/503/504 |

```text
记忆法：1 拿信息、2 成功了、3 换地方、4 你的错、5 我的错
```

## 2. 重定向家族：301/302/303/307/308 全解析

### 2.1 六兄弟对比（面试必考）

| 状态码 | 永久性 | 方法保持 | 典型场景 |
|:---:|:---:|:---:|------|
| **301** Moved Permanently | 永久 | 方法**可能被改写**（GET→GET；POST→GET 历史上常变） | 域名迁移、HTTP→HTTPS |
| **302** Found | 临时 | 方法可能被改写 | 临时跳转（登录后跳转等） |
| **303** See Other | 临时 | **强制改 GET** | POST 后跳结果页（PRG 模式） |
| **307** Temporary Redirect | 临时 | **严格保持**（POST 仍 POST） | API 临时迁移 |
| **308** Permanent Redirect | 永久 | **严格保持** | 永久迁移且方法敏感 |

```text
关键差异维度：
  ① 永久 vs 临时（影响 SEO 与浏览器缓存）
  ② 是否保持原方法（301/302 历史上把 POST 改 GET——现代浏览器对
     GET/HEAD 安全方法外的改 GET 行为已收敛；307/308 强制保持）

工程选择：
  表单提交后跳转结果页 → 303（PRG 模式，防刷新重复提交）
  API 端点永久迁移（POST 接口） → 308（保持方法 + 永久）
  普通页面跳转 → 302 临时 / 301 永久（按业务）
```

### 2.2 PRG 模式（Post-Redirect-Get）

```java
// 表单提交 → 303 跳转 → GET 结果页
// 作用：刷新结果页时是 GET（安全幂等），不再重复提交表单
@PostMapping("/order")
public String createOrder(...) {
    orderService.create(...);
    return "redirect:/order/" + id;    // Spring 生成 303
}
```

## 3. 4xx 客户端错误细节

| 状态码 | 含义 | 要点 |
|:---:|------|------|
| 400 Bad Request | 请求语法错误 | 参数缺失/格式错 |
| 401 Unauthorized | **未认证**（没凭证） | 响应带 `WWW-Authenticate` 提示如何认证 |
| 403 Forbidden | **已认证但无权限** | 语义上与 401 区分 |
| 404 Not Found | 资源不存在 | 注意：**API 常故意返回 404 而非 403 防信息泄露** |
| 405 Method Not Allowed | 方法不支持 | 响应带 `Allow` 头 |
| 409 Conflict | 资源冲突 | 版本冲突/唯一约束 |
| 422 Unprocessable Entity | 语义校验失败 | 业务校验错误（非语法） |
| 429 Too Many Requests | 限流 | 响应带 `Retry-After` |

```text
401 vs 403（高频考点）：
  401 = "你是谁？"（缺凭证）→ 客户端应携带凭证重试
  403 = "你不够格"（凭证有效但权限不足）→ 客户端不该重试

404 vs 403 的安全策略：
  隐藏资源是否存在 → 一律返回 404（防枚举攻击）
```

## 4. 5xx 服务端错误细节

| 状态码 | 含义 | 场景 |
|:---:|------|------|
| 500 Internal Server Error | 未处理异常 | 兜底 |
| 501 Not Implemented | 方法未实现 | 网关不支持 |
| 502 Bad Gateway | 上游返回无效响应 | **网关层最常见** |
| 503 Service Unavailable | 过载/维护中 | 负载均衡摘除、熔断 |
| 504 Gateway Timeout | 上游超时 | 网关等待上游超时 |

```text
网关链路的状态码语义（Nginx 视角）：
  502：上游连接被拒/响应无效（上游挂了）
  503：自身过载（限流/连接池满）
  504：上游处理超时（上游活着但慢）

生产建议：
  5xx 必须告警（业务错误率 = 5xx 占比）
  503 应带 Retry-After 头（负载均衡/客户端可据此退避）
```

## 5. 304 与条件请求

```text
304 Not Modified 是"协商缓存"的心脏（03 章详述）：
  客户端带条件头（If-None-Match: <etag> / If-Modified-Since: <date>）
  服务器比对：
    未变化 → 304（无主体，客户端用缓存副本）
    已变化 → 200 + 新主体

304 的语义本质：不返回资源，只回答"没变"

易错点：
  304 不应带主体（Content-Length: 0）
  304 要带 ETag/Last-Modified（供下次校验）
  浏览器收到 304 自动使用缓存，无需应用干预
```

## 6. 103 Early Hints（2026）

### 6.1 机制（RFC 8297）

```text
服务器在"最终响应未就绪"时，先发 103 携带 Link 头：
  103 Early Hints
  Link: </style.css>; rel=preload; as=style
  Link: </font.woff2>; rel=preload; as=font; crossorigin
  （最终响应就绪后再发 200）

作用：浏览器在服务器"思考时间"（TTFB）里就预加载关键资源
      → 隐藏服务器生成延迟 → LCP 提升 15-25%（宣传口径）
要求：仅 HTTP/2/3（HTTPS）下有效
```

### 6.2 2026 采用现状（检索结论）

| 维度 | 现状 |
|------|------|
| 浏览器 | Chrome/Edge 94+、Safari 16.4+、Firefox 102+（flag） |
| 框架 | 多数支持（如 TanStack 标实验性；Rails/Shakapacker 实现） |
| **瓶颈** | **CDN 大量剥离 103**——2025-10 实测 GitHub/Google/Shopify 等一线站点均未成功送达端用户；Heroku/DigitalOcean/AWS ALB 有传输问题 |
| Cloudflare | 支持最成熟：从缓存 HTML 的 Link 头**代发 103**（仅 .html/.htm/.php/无后缀、200/301/302、preload/preconnect） |
| CloudFront | 无原生支持（需 Lambda@Edge 或源站实现） |
| 注意 | 103 可能在鉴权前发出（未登录用户先收到 103 再收 403）；过度提示反而抢带宽 |

> 🎯 **核心要点**：103 是"想法很好、链路没跟上"的典型——服务端/浏览器都就绪，**CDN 剥离是主要障碍**。实践：走 Cloudflare 且资源为公开稳定静态资源时可用；否则回归"200 里带 Link 头"的降级方案（预连接收益仍在，只是不隐藏 TTFB）。

## 7. 错误处理最佳实践

### 7.1 API 错误响应设计

```java
// 统一错误结构（错误码 + 可读信息 + 请求关联）
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    ResponseEntity<ApiError> handleBiz(BizException e) {
        return ResponseEntity.status(e.getHttpStatus())
            .body(new ApiError(e.getCode(), e.getMessage(), requestId()));
    }
}
// ApiError: {"code":"ORDER_NOT_FOUND","message":"订单不存在","requestId":"x-123"}
```

| 原则 | 说明 |
|------|------|
| 状态码语义准确 | 401/403/409/422 用对，不全部 400 |
| 错误码稳定 | 客户端按 code 处理，不解析 message |
| 不泄露内部信息 | 500 的堆栈只进日志，不返回客户端 |
| 幂等可重试 | 4xx 不重试、5xx 可重试（配合 Retry-After/退避） |
| 全链路追踪 | 响应带 requestId，日志关联 |

### 7.2 状态码使用对照表（业务场景 → 推荐码）

| 业务场景 | 推荐状态码 |
|---------|:---:|
| 查询成功 | 200 |
| 创建成功 | 201（+ Location 头） |
| 删除成功/无内容 | 204 |
| 表单校验失败 | 422（或 400） |
| 未登录 | 401 |
| 无权限 | 403 |
| 资源不存在 | 404 |
| 重复提交（幂等冲突） | 409 |
| 依赖下游失败 | 502（网关）/ 503（降级） |
| 限流 | 429 |

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 五类状态码=服务器语义浓缩：2xx 成功、3xx 换地方（301/308 永久、302/307 临时、303 强制 GET）、4xx 你的错、5xx 我的错；
> 2. 304 是协商缓存的"无内容成功"，103 是 2026 年"服务端与浏览器就绪、CDN 剥离卡脖子"的新特性；
> 3. 生产规范：错误码稳定 + 状态码语义准确 + 5xx 告警 + 4xx 不重试 5xx 可重试。
