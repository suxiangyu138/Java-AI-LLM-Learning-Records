# HTTP/2 协议深潜

> HTTP/2（RFC 9113，2015）把 HTTP 从文本协议改造成二进制分帧协议：一个连接上并发多路"流"、HPACK 压掉重复头部、流量控制防失控——它解决了 HTTP/1.1 的响应按序阻塞，却把队头阻塞留在了 TCP 层（这正是 HTTP/3 的登场理由）

## 1. HTTP/2 的三大设计

```text
HTTP/2（RFC 9113，2015 定稿）三大设计：
  ① 二进制分帧：文本 → 帧（HEADERS/DATA 等），机器友好、解析高效
  ② 多路复用：一个 TCP 连接并发多条"流"，每流一个请求-响应
  ③ 头部压缩：HPACK（静态表 + 动态表 + 哈夫曼）

目标（对照 HTTP/1.1 的痛点）：
  响应按序阻塞（应用层 HOL）→ 流并发解决
  头部重复传输浪费 → HPACK 解决
  每域 6 连接 → 单连接多路复用解决
```

## 2. 二进制分帧与帧类型

### 2.1 帧结构

```text
Frame = 9 字节固定头 + 负载
  ┌───────────────┬──────────────┬──────────┐
  │ Length(24bit) │ Type(8bit)   │ Flags(8) │
  ├───────────────┼──────────────┼──────────┤
  │ R(1) Stream ID(31bit)                 │
  └───────────────┴───────────────────────┘
  负载（Length 字节）
```

### 2.2 主要帧类型

| 帧 | 作用 |
|----|------|
| HEADERS | 请求/响应头（+标志位 END_HEADERS/END_STREAM） |
| DATA | 主体数据 |
| SETTINGS | 连接参数协商（并发流上限等） |
| WINDOW_UPDATE | 流量控制窗口更新 |
| PUSH_PROMISE | 服务器推送（已弃用实践） |
| RST_STREAM | 取消单个流（比断开连接精细） |
| PING | 连接保活/RTT 测量 |
| GOAWAY | 优雅关闭连接 |

> 💡 **对比认知**：HTTP/1.1 是"文本行解析"，HTTP/2 是"定长头帧解析"——分帧让"一个连接里区分多个逻辑流"成为可能。

## 3. 流与多路复用

### 3.1 流模型

```text
一个 TCP 连接 = 多条并发的"流"（stream）
每个流：独立编号（客户端发起为奇数，服务器为偶数）
       独立状态机（open → half-closed → closed）
       独立请求-响应生命周期

  ┌───────────────────────────── TCP 连接 ─────────────────────────────┐
  │ 流 1:  GET /a  ────────────────────────────────→ 200 /a            │
  │ 流 3:  GET /b  ────────────→ 200 /b（不等 /a）                     │
  │ 流 5:  POST /c ───────────────────────────→ 201 /c                 │
  └─────────────────────────────────────────────────────────────────────┘
  响应不再按请求顺序 —— 应用层队头阻塞解除（05 章对比）
```

### 3.2 关键规则

```text
① 流并发上限：SETTINGS_MAX_CONCURRENT_STREAMS（服务器可设，默认不小）
② 流取消：RST_STREAM 只影响单流（HTTP/1.1 只能断连接）
③ 请求-响应映射：流 ID 天然对应，无需序号对齐
④ 服务器推送（PUSH_PROMISE）：
   曾为"服务器主动推资源"设计
   现实：与浏览器缓存逻辑冲突、利用率低，Chrome/Edge 已禁用
   → 已被 103 Early Hints（02 章）取代
```

## 4. HPACK：头部压缩

### 4.1 原理

```text
头部压缩 = 静态表 + 动态表 + 哈夫曼编码
  静态表（61 项预置）：常见头（:method: GET、:status: 200 等）→ 1 字节索引
  动态表：连接内双方共有的"最近见过的头"（索引增量更新）
  哈夫曼：对静态/动态表外的值做熵编码

例子（首请求后）：
  第一次请求完整编码 Headers: {":method": "GET", ":path": "/a"}
  第二次请求（同连接）：这些头在动态表中 → 只传索引 → 几字节
```

### 4.2 收益与代价

| 维度 | HTTP/1.1 | HTTP/2 + HPACK |
|------|:---:|:---:|
| 每次请求的头部 | 全量文本（~500B+） | 首次全量，之后索引 |
| 典型页面 50 资源 | 头部 ~25KB 冗余 | 显著压缩 |
| 代价 | - | 动态表有内存占用；**CRIME 类攻击面**（压缩+加密 → 需要防 CRIME，实现内置防护） |

> 🎯 **核心要点**：HPACK 把"每请求都带一遍 Cookie/User-Agent"的浪费降到个位数字节——这是 HTTP/2 单连接复用大量请求的前提（否则头部开销会抵消多路复用收益）。

## 5. 流量控制与流优先级

### 5.1 流量控制（WINDOW_UPDATE）

```text
为什么需要：单连接多流 → 某流无限制发送会挤占其他流带宽
机制：连接级 + 流级双窗口（类似 TCP 滑动窗口，但作用于应用层）
  SETTINGS_INITIAL_WINDOW_SIZE（默认 65535 字节）协商窗口
  WINDOW_UPDATE 帧调整窗口
作用：慢流不被快流饿死；突发受控

生产提示：大响应（视频/文件）需调大窗口，否则吞吐受限
```

### 5.2 流优先级（已弱化）

```text
PRIORITY 帧/头：流依赖树（依赖 + 权重）
现实：浏览器实现差异大、与代理冲突多、收益有限
2026 实践：多数场景忽略优先级（HTTP/3 的优先级设计也在重构）
```

## 6. 连接层队头阻塞：TCP 的阴影

```text
HTTP/2 解决了"响应按序"（应用层 HOL），但：
  所有流共享一个 TCP 连接 → TCP 保证字节有序
  某流一个包丢失 → 内核等待重传 → 该连接上所有流的数据都被阻塞

  ┌─ TCP 连接（有序字节流）────────────────┐
  │ 流1 数据  [丢失！]  流2 数据（已就绪）    │
  │ 内核：等待重传流1 的包 → 流2 卡住（尽管完整）│
  └─────────────────────────────────────────┘

结果：丢包率越高，HTTP/2 相对 HTTP/1.1（多连接）的优势越小
  10% 丢包下：HTTP/2 可能不如 HTTP/1.1（多连接分散风险）
  → 这是 HTTP/3/QUIC 的核心动机（网络高并发体系 07 章）
```

## 7. 协商与部署：ALPN 与 h2c

### 7.1 协商机制

| 协商方式 | 说明 | 现状 |
|---------|------|:---:|
| **ALPN**（TLS 扩展） | TLS 握手中协商 `h2` / `http/1.1` | HTTPS 下标准 |
| h2c（明文升级） | `Upgrade: h2c` 或 prior knowledge | 极少用（浏览器不支持 h2c 明文） |

```text
实际结论：HTTP/2 事实要求 HTTPS（ALPN 协商）
  Nginx：listen 443 ssl http2;（1.25.1+ 建议独立 http2 on;）
```

### 7.2 部署检查

```bash
# 验证 HTTP/2 生效
curl -sI --http2 https://example.com | head -1
# HTTP/2 200
# 无 --http2 时可用 nghttp / DevTools Protocol 列确认
```

## 8. 生态关系：gRPC 与 WebSocket

| 技术 | 与 HTTP/2 的关系 |
|------|------------------|
| **gRPC** | 直接构建于 HTTP/2：HTTP/2 流 = RPC 调用；支持流式（双向）依赖多路复用 |
| WebSocket | **不依赖 HTTP/2**（独立协议，通过 HTTP/1.1 Upgrade）；HTTP/2 生态曾有 WebSocket over HTTP/2 草案（已放弃） |
| Server-Sent Events | 单工流式（HTTP/1.1 chunked 即可），HTTP/2 下多路复用天然兼容 |

```text
选型视角：
  gRPC：内部服务间 RPC（二进制、流式、跨语言）——HTTP/2 基建
  WebSocket：浏览器实时双向（聊天/游戏）——独立长连接
  SSE：服务器单向推送（消息通知）——最轻量
```

## 9. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. HTTP/2 三设计：二进制分帧（帧结构）、流多路复用（应用层 HOL 解除）、HPACK（头部索引化）；
> 2. 残余问题：单 TCP 连接内的传输层队头阻塞——丢包时所有流一起等，这是 HTTP/3 的动机；
> 3. 部署事实：HTTP/2 ≈ HTTPS 专属（ALPN），gRPC 是其生态的最大受益者，服务器推送已被 103 Early Hints 取代。

**思考题**：

1. HTTP/2 解决了哪种队头阻塞？留下哪种？（→ 3.1/6）

3. 为什么浏览器禁用 HTTP/2 服务器推送？（→ 3.2）
4. gRPC 为什么选 HTTP/2 作底座？（→ 8）
