## 1. keep-alive：连接复用的历史转折

### 1.1 HTTP/1.0 时代：每请求一连接

```text
HTTP/1.0：请求完即断开（Connection: close）
代价（每请求）：
  TCP 三次握手（1 RTT）
  TLS 握手（2 RTT，HTTPS 时代更痛）
  TCP 慢启动（每连接都要重新爬坡）

页面 50 个资源 → 50 个连接 → 50×(握手+慢启动) 延迟
```

### 1.2 HTTP/1.1：keep-alive 默认开启

```text
Connection: keep-alive（HTTP/1.1 默认；HTTP/1.0 需显式）
效果：连接复用于多个请求 → 握手与慢启动只付一次

生产注意：
  ① keep-alive 有超时（Nginx keepalive_timeout 65s）与上限（keepalive_requests）
  ② 高并发下连接数 = 并发客户端数（连接管理见网络高并发体系 06 章）
  ③ HTTP/1.0 客户端仍发 Connection: close → 服务端兼容
```

## 2. 管线化：理论的胜利与现实的失败

### 2.1 设想

```text
管线化（pipelining）：一个连接上连续发多个请求，无需等响应
  GET /a → GET /b → GET /c（连续发出）
  ← /a ← /b ← /c（按序响应）
理想：一个 RTT 传送多个请求
```

### 2.2 为什么失败

| 问题 | 说明 |
|------|------|
| **队头阻塞** | 响应必须**按序返回**——/a 慢，/b /c 的响应即使就绪也得排队等 |
| 服务器支持差 | 多数服务器实现不完整（Nginx 默认关闭） |
| 重试语义复杂 | 管线中某请求失败，后续请求是否重发？ |
| 代理兼容 | 中间层对管线化处理不一 |

```text
结论：管线化"生于理论、死于队头阻塞"——它最大的遗产是
      让业界看清"单连接串行响应"是死路 → 促成 HTTP/2 的多路复用
```

## 3. 队头阻塞：HTTP/1.1 的原罪

```text
定义：前一个响应未完成，后续响应无法开始（即使已就绪）

来源：HTTP/1.1 的响应必须按请求顺序返回（保证对应关系）
     + 同一连接串行传输

危害：
  页面 N 个资源 → 慢的排前面 → 后面的全部等待
  （浏览器并发 6 连接缓解，但 6 个慢请求仍会堵住 6 条通道）

三个层面的队头阻塞（区分！）：
  HTTP/1.1 层：响应按序 → 应用层 HOL（本章）
  TCP 层：丢包重传阻塞 → 传输层 HOL（HTTP/2 的痛，06 章）
  解决：HTTP/2 用流解决应用层；QUIC 用独立流解决传输层
        （网络高并发体系 07 章）
```

> 🎯 **核心要点**：队头阻塞分两层——HTTP/1.1 的"响应按序"是协议层问题（HTTP/2 解决）；TCP 的"丢包全阻"是传输层问题（QUIC 解决）。面试把两层说清是加分项。

## 4. 浏览器并发连接限制

```text
限制：每域名并发连接数（HTTP/1.1 时代）
  早期规范建议 2，现代浏览器实际 6（HTTP/1.x）

影响与对策：
  资源多的页面 → 6 连接排队 → 慢
  对策一：域名分片（sharding）：static1.example.com / static2.example.com
          → 6×N 并发（HTTP/2 时代应废弃——反模式！）
  对策二：资源合并（雪碧图/JS 合并）——减少请求数
  对策三：升级 HTTP/2（单连接多路复用，连接数限制失去意义）

⚠️ HTTP/2 下的分片反模式：
  分片抵消了 HPACK 共享上下文/单连接的优势
  且每个新域名增加 DNS+TLS 开销 → 应合并回原域
```

## 5. Host 头与虚拟主机

```text
HTTP/1.0：请求行只有路径（GET /index.html）
  → 一台服务器只能托管一个站点（IP 即站点）

HTTP/1.1：Host 头必须携带（400 若缺失）
  → 一台服务器（一个 IP）按 Host 路由到不同虚拟主机

  GET /index.html HTTP/1.1
  Host: blog.example.com          ← 虚拟主机路由依据

生产场景：
  Nginx server_name 按 Host 匹配 → 虚拟主机
  反代按 Host 转发（proxy_set_header Host $host）
  ⚠️ 注意：Host 头注入攻击（08 章）——信任 Host 前需校验白名单
```

## 6. chunked 编码与 Content-Length

### 6.1 两种主体边界机制（互斥）

| 机制 | 原理 | 适用 |
|------|------|------|
| `Content-Length: N` | 明确主体字节数 | 响应体**已知大小** |
| `Transfer-Encoding: chunked` | 分块：每块 = 长度\r\n 内容\r\n，最后 0\r\n | **流式/动态生成**（大小未知） |

```text
chunked 报文示例：
  HTTP/1.1 200 OK
  Transfer-Encoding: chunked

  4\r\n
  Wiki\r\n
  5\r\n
  pedia\r\n
  0\r\n
  \r\n
```

### 6.2 工程要点

```text
① 互斥规则：两者同时出现 = 请求走私攻击特征（08 章）
② 流式响应（SSE/大文件/实时日志）必须 chunked
③ Java：Servlet 3.1+ 异步流式输出自动 chunked
④ 压缩与 chunked 可叠加（gzip + chunked）
```

## 7. 范围请求与断点续传

### 7.1 机制

```http
# 客户端请求部分内容
Range: bytes=0-1023
# 服务器响应（206 Partial Content）
HTTP/1.1 206 Partial Content
Content-Range: bytes 0-1023/1048576
Accept-Ranges: bytes
```

### 7.2 应用场景

| 场景 | 说明 |
|------|------|
| 断点续传 | 下载中断后从断点继续（下载器/大文件） |
| 视频拖拽 | 播放器只请求需要的字节段 |
| 分片下载 | 多连接并行下载（P2P 思维） |

```text
配合条件：
  服务器需支持 Accept-Ranges: bytes（Nginx 默认）
  不支持时：返回 200 全量（客户端应兼容）
  多段：Range: bytes=0-99,200-299（复杂，多数场景单段足够）
```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. HTTP/1.1 的三大遗产：keep-alive（连接复用，沿用至今）、管线化（死于响应按序）、队头阻塞（催生 HTTP/2）；
> 2. 浏览器 6 连接限制用"域名分片"破解——HTTP/2 时代是反模式，应合并回单域；
> 3. 细节三件套：Host 头（虚拟主机路由）、chunked（流式边界，与 Content-Length 互斥）、Range（断点续传/视频拖拽）。

3. 为什么 HTTP/2 下域名分片是反模式？（→ 4）
4. `Content-Length` 与 `Transfer-Encoding` 同现意味着什么？（→ 6.2）
