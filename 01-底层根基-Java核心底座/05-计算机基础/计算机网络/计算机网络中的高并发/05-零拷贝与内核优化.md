## 1. 传统路径：四次拷贝的浪费

以"读取磁盘文件 → 发给客户端"为例（传统 read + write）：

```text
用户进程          用户缓冲区 ──────────────── 用户缓冲区
                     ↑ 拷贝③（write）          │
                     │                        ↓
内核              页缓存（page cache） ── 拷贝④ ──→ socket 发送缓冲区
                     ↑ 拷贝①（磁盘→页缓存）     ↓
磁盘 ────────────────┘                   网卡（DMA）
```

| # | 拷贝 | 参与者 | 代价 |
|:---:|------|--------|------|
| ① | 磁盘 → 内核页缓存 | **DMA（不占 CPU）** | 低 |
| ② | 页缓存 → 用户缓冲区 | CPU | **高（read 系统调用）** |
| ③ | 用户缓冲区 → socket 发送缓冲 | CPU | **高（write 系统调用）** |
| ④ | 发送缓冲 → 网卡 | DMA（发送时） | 低 |

```text
问题本质：
  ②③ 是 CPU 参与的拷贝（每次拷贝：读内存+写内存+缓存失效）
  加上 2 次系统调用（read/write）的上下文切换（各 ~1-2µs）
  文件传输场景：CPU 时间大量耗在"搬运"而非"业务"
```

## 2. 零拷贝的本质：谁该搬数据

```text
零拷贝（zero-copy）的目标不是"不拷贝"，而是"少让 CPU 搬 + 少切换上下文"：

三种手段：
  ① 共享：用户态直接映射内核缓冲区（mmap）→ 省拷贝②
  ② 内核内搬：内核里直接页缓存→socket（sendfile）→ 省②③和一次系统调用
  ③ 绕过：DMA 直传 / io_uring 接收侧零拷贝 → 省 CPU 搬运
```

| 手段 | 减少 | 场景 |
|------|------|------|
| mmap | ②用户态拷贝 | 文件读取 + 内存操作 |
| sendfile | ②③ + read/write 两次系统调用 | **文件发送（最常用）** |
| splice | 同 sendfile，但支持任意 fd | 管道/协议转换 |
| io_uring ZC | 发送侧零拷贝 + 接收侧 ZC Rx | 极限网络转发 |

## 3. mmap：共享内核缓冲区

```java
// mmap：把文件页缓存映射到用户空间 —— 读文件不走 read 拷贝
FileChannel channel = FileChannel.open(path);
MappedByteBuffer buf = channel.map(FileChannel.MapMode.READ_ONLY, 0, fileSize);
// 之后 buf.get() 直接读页缓存 —— 省去"页缓存→用户缓冲"的拷贝
```

```text
mmap 的语义：
  用户进程与内核共享同一块物理页（页缓存）
  read 时：缺页中断 → 从磁盘读入页缓存 → 用户直接访问（无需再拷贝）
  写时：写页缓存 → 脏页异步刷盘

优点：大文件随机访问极快（省 1 次 CPU 拷贝）
代价：
  ① 映射占用虚拟地址空间（大文件映射压力）
  ② 缺页中断（首次访问每个页都有一次）
  ③ 脏页回写时机不可控（写后崩溃可能丢数据——需 fsync）
```

## 4. sendfile：内核内部搬运

### 4.1 机制

```c
ssize_t sendfile(int out_fd, int in_fd, off_t *offset, size_t count);
// 内核内部：页缓存 → socket 发送缓冲，全程不经过用户态
```

```text
sendfile 路径（从 4 次拷贝 → 2 次 + 1 次系统调用）：
  磁盘 → 页缓存（DMA）
  页缓存 → socket 发送缓冲（内核内拷贝，无用户态参与）
  socket 缓冲 → 网卡（DMA）

进一步优化（scatter-gather，无需内核内拷贝）：
  sendfile 支持 SG-DMA 时：页缓存 → 网卡直接 DMA
  → 2 次拷贝（DMA×2，CPU 全程不搬数据）
```

### 4.2 适用条件

```text
✅ 发送完整文件（静态资源服务器、CDN 回源）
❌ 需要"边读边改"（加鉴权头、压缩）—— 必须经过用户态
✅ Nginx 静态文件发送默认用 sendfile（sendfile on;）
```

## 5. splice：任意两个 fd 之间

```c
ssize_t splice(int fd_in, loff_t *off_in, int fd_out, loff_t *off_out, size_t len, unsigned int flags);
// 通过管道在两个 fd 间搬运数据，内核内完成
// 典型：文件 → 管道 → socket；协议栈处理时可插入用户态动作
```

```text
sendfile vs splice：
  sendfile：文件 → socket（专用路径，性能最好）
  splice：任意 fd 组合（文件/管道/socket/设备）
  → 需要"文件内容经过协议转换再发"时用 splice 链
```

## 6. Java 实战：FileChannel.transferTo

### 6.1 一行代码的零拷贝

```java
// Java NIO 的零拷贝 API：内部调用 sendfile（Linux）
public void serveFile(SocketChannel socket, Path file) throws IOException {
    try (FileChannel fc = FileChannel.open(file)) {
        long pos = 0, size = fc.size();
        while (pos < size) {
            pos += fc.transferTo(pos, size - pos, socket);   // 零拷贝发送
        }
    }
}
```

| Java API | 内核机制 | 场景 |
|---------|---------|------|
| `FileChannel.transferTo` | sendfile | 文件 → socket（**零拷贝**） |
| `FileChannel.transferFrom` | 对应接收侧 | socket → 文件 |
| `MappedByteBuffer`（mmap） | mmap | 文件随机访问 |
| `SocketChannel.write(ByteBuffer)` | 普通 write | 通用（非零拷贝） |

### 6.2 对比基准（量级参考）

```text
大文件发送（如 100MB）：
  传统 read+write：CPU 参与 ~200MB 的搬运（两次拷贝）
  transferTo：CPU 零搬运（DMA 完成），吞吐可提升 1-3 倍，CPU 占用显著下降
  → 静态文件服务器（Nginx/Netty 静态服务）的标配
```

> ⚠️ **限制**：`transferTo` 要求**目标 socket 是阻塞模式**（NIO 非阻塞通道会退化为普通拷贝）；Netty 内部有 `FileRegion` 封装（同样基于 sendfile）。

## 7. io_uring 时代的零拷贝（2026）

### 7.1 发送侧零拷贝

```text
io_uring 的零拷贝发送：
  注册固定缓冲区（IORING_REGISTER_BUFFERS）→ 提交 send/发送请求
  → 内核直接引用用户缓冲区（绕过 socket 缓冲拷贝）
  配合 multishot + registered files：单请求处理链优化到极致
```

### 7.2 接收侧零拷贝（Linux 6.15 ZC Rx，2025-2026 新能力）

```text
ZC Rx（Zero-Copy Receive，内核 6.15+）：
  传统接收：网卡 DMA → 内核缓冲 → 拷贝到用户缓冲（CPU 参与 1 次）
  ZC Rx：网卡 DMA 直接到用户态预注册的缓冲区（跳过内核缓冲拷贝）
  实测：单核即可饱和 200Gbps 接收

意义：网络转发型负载（代理/网关/CDN）的接收侧瓶颈被移除
现状：依赖网卡驱动支持；需要预注册大块连续内存；生态逐步跟进
```

### 7.3 2026 零拷贝全景

| 技术 | 路径 | 状态 |
|------|------|:---:|
| mmap | 用户态映射页缓存 | 成熟 |
| sendfile | 内核内文件→socket | 成熟（Nginx 标配） |
| splice | 任意 fd 管道搬运 | 成熟 |
| io_uring 发送 ZC | 注册缓冲直发 | 成熟（liburing） |
| **io_uring 接收 ZC（6.15+）** | 网卡 DMA 直入用户缓冲 | 2026 新星 |

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 传统文件传输 4 次拷贝中 2 次 CPU 参与是浪费——零拷贝的本质是"让 CPU 少搬、让内核管搬、让 DMA 直搬"；
> 2. 生产标配：静态文件用 `sendfile`（Nginx `sendfile on` / Java `transferTo`），从 4 次拷贝降到 2 次 DMA；
> 3. 2026 前沿：io_uring 发送零拷贝成熟，Linux 6.15 ZC Rx 让接收侧也直入用户缓冲（单核 200Gbps）——网络转发型负载是最大受益者。

3. 为什么"需要改内容"的场景不能用 sendfile？（→ 4.2）
4. `transferTo` 在非阻塞通道上会怎样？（→ 6 限制）
