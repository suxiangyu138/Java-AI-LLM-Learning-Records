## 1. 高频面试题 18 问

### Q1：什么是 C10K 问题？怎么解决的？

> 答：2001 年前后提出的"单服务器 1 万并发连接"问题。本质是线程模型成本爆炸：每连接一线程，1 万线程吃光内存（~8MB 栈×万）与调度（内核上下文切换）。解法是事件驱动：多路复用（epoll 一个线程监视海量 fd）+ 非阻塞 + 回调，Nginx/Node.js 为代表。空闲连接在事件驱动下成本趋零。
> 参考：01 章

### Q2：五种 I/O 模型？epoll 属于哪种？

> 答：阻塞、非阻塞、多路复用、信号驱动、异步。epoll 是**多路复用（就绪模型）**：内核通知"可以读了"，数据由用户态 read 搬运（同步）；io_uring 才是异步（完成模型）：内核拷贝完数据再通知。Java 的 NIO 是"非阻塞+多路复用"，不是异步。
> 参考：02 章

### Q3：select/poll/epoll 的区别？

> 答：① select：fd 位图固定 1024、每次调用全量拷贝+O(n) 扫描；② poll：链表解除数量限制，但仍是全量拷贝+扫描；③ epoll：内核持状态（红黑树存注册 fd、就绪链表存就绪 fd、回调通知），注册一次永不拷贝，取就绪 O(1)。三者本质差距：select/poll 内核无状态、epoll 有状态。
> 参考：03 章 1/2/3 节

### Q4：epoll 的 LT 和 ET 区别？

> 答：LT（水平触发，默认）：缓冲区一直有数据就反复报告（读不完下次还报，不易丢事件）；ET（边缘触发）：只在"空→非空"瞬间报一次（必须循环 read 到 EAGAIN 读完，否则事件丢失）。ET 省 epoll_wait 触发次数（系统调用少）但要求读循环；Netty 底层用 ET，业务自写默认 LT 更稳。
> 参考：03 章 4 节

### Q5：epoll 为什么快？底层数据结构？

> 答：三要素——① 内核红黑树维护注册 fd（增删改查 O(log n)，无需每次拷贝集合）；② 数据到达通过回调（ep_poll_callback）直接进就绪链表，不用轮询发现；③ epoll_wait 直接返回就绪链表（O(1) 取就绪，只处理活跃的）。对比 select 每次 O(n) 扫描+拷贝。
> 参考：03 章 3 节

### Q6：io_uring 是什么？比 epoll 强在哪？

> 答：Linux 5.1+ 的异步 I/O 框架：两个共享内存环形队列（SQ 提交/CQ 完成），内核与用户态共享内存零拷贝传请求；SQPOLL 模式下提交请求零系统调用。基准（2026）：20 万连接 100Gbps 下 epoll 2.1M req/s vs io_uring 3.4M vs io_uring+SQPOLL 4.8M。2026 现状：数据库/存储已标配（PG17/18、MySQL/InnoDB、RocksDB），Web 服务仍以 epoll 为主（Nginx/Redis/Go/Node）；合成基准收益在生产会缩水（43%→8%），且有安全史与可观测性代价。
> 参考：03 章 6/7 节

### Q7：Reactor 模式？三种线程模型？

> 答：Reactor = 就绪通知 + 事件分发（epoll 的用户态投影）：Reactor 事件循环等就绪事件 → dispatch 到 EventHandler。三种模型：① 单线程（accept+读+业务+写全一线程，Redis 模型，业务必须快）；② 多线程（Reactor 收分发 + 工作线程池做业务）；③ 主从（Main Reactor 只 accept + 多个 Sub Reactor 分管连接读写，Netty 模型，连接亲和无锁）。演进逻辑：解耦业务 → 解耦 accept + 并行读写。
> 参考：04 章

### Q8：Netty 的 EventLoop 是什么？为什么连接绑定单个 EventLoop？

> 答：EventLoop = 单线程事件循环（封装 Selector+线程池），Group 分 boss（accept）与 worker（读写）。**一个连接的一生只在一个 EventLoop 上**：该连接所有事件按序处理（天然顺序性、Handler 无并发）、连接内无锁；代价是慢 Handler 阻塞同 EventLoop 的其他连接——重操作要交给独立业务线程池。
> 参考：04 章 4 节

### Q9：零拷贝是什么？Java 怎么用？

> 答：减少 CPU 参与的拷贝。传统文件发送 4 次拷贝（DMA+CPU+CPU+DMA），sendfile 后剩 2 次 DMA（CPU 零搬运，Nginx `sendfile on`）。Java 用 `FileChannel.transferTo`（内部 sendfile），一行代码实现零拷贝发送。mmap 是另一种（用户态映射页缓存，省一次拷贝）。2026 前沿：io_uring 零拷贝发送成熟 + Linux 6.15 ZC Rx 接收侧直入用户缓冲（单核 200Gbps）。
> 参考：05 章

### Q10：TIME_WAIT 为什么多？怎么解决？

> 答：主动关闭方发最后 ACK 后等 2MSL（60s）——防旧报文串扰的正确性设计。高并发短连接下客户端端口池（默认 ~2.8 万）被 TIME_WAIT 占满 → 新连接失败。对策：① 首选连接复用（keep-alive/连接池，根治）；② `tcp_tw_reuse=1`（出站复用）；③ 扩大 `ip_local_port_range`；④ 服务端 `tcp_fin_timeout` 缩短。**注意 `tcp_tw_recycle` 已废弃**（NAT 下出事故，内核 4.12 移除）。
> 参考：06 章 2 节

### Q11：backlog 是什么？连接建立失败看哪？

> 答：accept 队列长度 = min(应用 backlog, `somaxconn`)；三次握手分 SYN 队列（半连接）与 accept 队列（全连接）。accept 队列满 → 内核丢 ACK → 连接建立失败；`ss -lnt` 看 Recv-Q 堆积、`netstat -s` 看 SYN 丢弃。**accept 队列满本质是应用消费慢**（accept 不及时），不是内核问题。
> 参考：06 章 1 节

### Q12：Nagle 和延迟 ACK 为什么造成 40ms 延迟？

> 答：Nagle（发送侧）等 ACK 合小包；延迟 ACK（接收侧）等 40ms 凑数据。小包交互时叠加：发送方 Nagle 等 ACK 才能发下一个，接收方延迟 40ms 才回 ACK → 每个交互 +40ms。解法：交互式服务 `setTcpNoDelay(true)`（TCP_NODELAY 关 Nagle）；大包批量传输场景则保留。
> 参考：06 章 3 节

### Q13：HTTP keep-alive 和连接池是什么关系？

> 答：同一思想的两端——keep-alive 是协议层"连接复用"（HTTP/1.1 默认），连接池是客户端实现（池化复用、空闲回收、超时校验）。收益：省握手（TCP 1RTT + TLS 1.3 1RTT = 2-3 RTT 归零）、服务器连接数有界、TIME_WAIT 压力下降。应用层高并发第一定律：能复用就不新建。
> 参考：07 章 1 节

### Q14：HTTP/2 的队头阻塞？HTTP/3 怎么解决？

> 答：HTTP/2 在**一个 TCP 连接**上多路复用多个流——TCP 保证有序，某流丢包 → 整个连接重传等待 → 所有流阻塞。QUIC（HTTP/3）把传输搬到 UDP：每流独立序号与确认，流 A 丢包只重传流 A，无队头阻塞；另加 1-RTT/0-RTT 握手与连接迁移（连接 ID 而非四元组）。2026 数据：浏览器 95%+、头部网站 34-40%、Cloudflare 边缘流量 35%；弱网（10% 丢包）比 HTTP/2 快 60%+。
> 参考：07 章 2/3 节

### Q15：WebSocket 和 HTTP 的关系？高并发注意什么？

> 答：WebSocket 通过 HTTP Upgrade 建立（101 响应），之后是独立双向帧协议。高并发注意：每连接常驻（连接数=在线数）→ 必须事件驱动；应用层心跳（ping/pong）；移动网络断线重连。降级路径：SSE（单向）+ 轮询。
> 参考：07 章 5 节

### Q16：四层和七层负载均衡区别？怎么组合？

> 答：四层（LVS/云 NLB）看 IP+端口，直接转发报文，性能极高但无内容感知；七层（Nginx/ALB）解析 HTTP 内容，可路由/重写/限流/缓存/灰度。经典组合：LVS 抗流量入口（百万连接）→ Nginx 精分（路由）→ 应用集群。
> 参考：08 章 2/4 节

### Q17：LVS 三种模式？DR 为什么性能最高？

> 答：DR（改写 MAC 直转）、TUN（隧道封装）、NAT（地址转换）。DR 最高是因为**响应不经过 LB**：LB 只处理请求流量，回程压力为零；NAT 的请求+响应都过 LB，出口带宽是瓶颈。生产：同机房 DR、跨机房 TUN、小场景 NAT。
> 参考：08 章 3 节

### Q18：一致性哈希解决了什么？QUIC 对负载均衡的挑战？

> 答：一致性哈希 = 哈希环 + 虚拟节点：key 定向到固定节点（缓存/会话保持），节点增减只影响 1/n 的 key（最小迁移）。QUIC 挑战：连接迁移让四元组变化 → 传统 L4 哈希失效；解法是 QUIC 感知 LB（按连接 ID 哈希，HAProxy 2.6+/Envoy 已支持）+ 后端无状态化（终极解）。
> 参考：08 章 6/7 节

### 追问：Nginx 为什么能扛百万连接？（架构向深挖）

> 答：三个设计——① 多进程 × 每进程事件驱动（epoll 管海量 fd，03 章）；② 异步非阻塞处理（worker 只做事件分发，业务不阻塞事件循环）；③ 零拷贝（sendfile 静态文件，05 章）+ 多路 accept（multi_accept）。对比：Apache 的每连接一线程模型在万级连接即崩。加分项：worker_connections × worker_processes = 单机连接上限的配置公式（07 章 6 节）。
> 参考：03 章、07 章 6 节

### 追问：虚拟线程和 Netty 怎么选？（框架选型向）

> 答：看瓶颈与团队——虚拟线程（JDK 21+）：同步代码 + 多路复用底座，I/O 密集场景吞吐足够、可维护性最高；Netty：事件驱动 + 精细控制（背压/零拷贝/协议定制），极致吞吐与特殊协议场景。趋势：两者可共存（Netty 上跑虚拟线程 Handler）。加分项：说明"虚拟线程不替代 Netty，替代的是 BIO 与手写线程池"。
> 参考：04 章、虚拟线程体系

### 追问：亿级 QPS 的架构长什么样？（架构综合向）

> 答：分层展开——① DNS/GSLB 就近接入（DNS 体系 07 章）；② LVS 四层抗流量（08 章）；③ Nginx 七层路由/限流（08 章）；④ 应用层无状态化（水平扩展）；⑤ 缓存（Redis）与异步（MQ）削峰；⑥ 数据层分库分表/读写分离。核心思想：每一层都"水平扩展 + 无状态"，瓶颈永远在下游依赖而非入口。加分项：说出"缓存穿透/击穿/雪崩"的防御。
> 参考：08 章、体系联动

## 2. 易错点清单

| # | 易错点 | 正确认知 |
|---|--------|---------|
| 1 | "NIO 是异步 IO" | Java NIO = 非阻塞 + 多路复用（epoll 投影），数据仍自己搬；AIO/io_uring 才是异步 |
| 2 | "非阻塞 = 异步" | 非阻塞是"调用立即返回"，异步是"内核搬完数据通知"——两个维度 |
| 3 | "epoll 也要每次拷贝 fd 集合" | 内核持状态（红黑树），注册一次；select/poll 才每次拷贝 |
| 4 | "ET 比 LT 更安全" | ET 更危险：读不完丢事件；LT 才是"读不完下次还报" |
| 5 | "零拷贝 = 不拷贝" | 是"CPU 不参与搬数据"（DMA 仍拷贝）；sendfile 是内核内搬运 |
| 6 | "TIME_WAIT 是 bug" | 是防旧报文串扰的正确性设计，只能绕不能灭 |
| 7 | "tcp_tw_recycle 能用" | 已废弃（4.12 移除），NAT 环境会导致连接异常 |
| 8 | "accept 队列满 = 内核问题" | 是应用 accept 太慢（消费端问题） |
| 9 | "HTTP/2 没有队头阻塞" | 连接内多流共享 TCP，丢包时全连接阻塞 |
| 10 | "QUIC 是纯性能升级" | 弱网/移动场景收益最大（60%+）；干净网络收益有限（3-5%）；且要处理 UDP 放行、LB 兼容、0-RTT 重放 |
| 11 | "NAT 模式 LVS 性能最高" | DR 最高（响应不回程）；NAT 回程是瓶颈 |
| 12 | "io_uring 全面超越 epoll" | 2026 共识：数据库标配 io_uring，Web 仍是 epoll 当打；生产收益缩水+安全史+可观测性盲区 |

## 3. 知识体系一句话串讲

```text
C10K（线程太贵）──→ 事件驱动
  │
  ├─ 内核层：epoll（红黑树+就绪链表+LT/ET）──→ io_uring（SQ/CQ 环、2026 数据库标配）
  │     │
  │     ├─ 模式层：Reactor（就绪分发，Netty）── Proactor（完成分发，io_uring）
  │     ├─ 数据层：零拷贝（mmap/sendfile/transferTo → io_uring ZC）
  │     └─ TCP 层：backlog 双队列 / TIME_WAIT 端口池 / Nagle×延迟ACK / keepalive
  │
  ├─ 应用层：keep-alive + 连接池 → HTTP/2 单连接多路复用（队头阻塞）
  │          → HTTP/3 QUIC（无队头阻塞 + 0-RTT + 连接迁移，2026 临界量）
  │          → WebSocket 常驻连接（必须事件驱动）
  │
  └─ 架构层：四层 LVS（DR 抗流量）→ 七层 Nginx（路由）→ 集群
            分发三哲学：轮询 / 最少连接 / 一致性哈希
            → QUIC 时代：LB 感知连接 ID + 无状态后端
```

## 4. 快速自测（含答案）

1. **C10K 的破局范式？** 事件驱动（多路复用+非阻塞+回调）（01 章）。
2. **epoll 的三个数据结构？** 红黑树（注册）、就绪链表（就绪）、等待队列（阻塞）（03 章）。
3. **LT 与 ET 一句话？** 有数据就报 vs 从无到有报一次（03 章）。
4. **io_uring 相对 epoll 的本质？** 就绪模型→完成模型，共享内存环零系统调用（03 章）。
5. **Netty 的连接亲和？** 一连接一 EventLoop，天然顺序、连接内无锁（04 章）。
6. **sendfile 减少到什么程度？** 2 次 DMA（CPU 零搬运）（05 章）。
7. **TIME_WAIT 的根治方案？** 连接复用（keep-alive/连接池）（06 章）。
8. **40ms 延迟的元凶？** Nagle × 延迟 ACK 叠加（06 章）。
9. **HTTP/2 队头阻塞的根源？** 单 TCP 连接上多流共享传输（07 章）。
10. **LVS 最高性能模式？** DR（响应不经 LB）（08 章）。
11. **一致性哈希的适用？** 缓存路由/会话保持，节点增减最小迁移（08 章）。
12. **QUIC 对 L4 LB 的破坏？** 连接迁移使四元组哈希失效，需按 CID 哈希（08 章）。
