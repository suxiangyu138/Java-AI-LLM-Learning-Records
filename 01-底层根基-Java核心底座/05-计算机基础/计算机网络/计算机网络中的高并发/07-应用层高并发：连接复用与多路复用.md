## 1. 连接复用：keep-alive 与连接池

### 1.1 HTTP keep-alive：省握手

```text
HTTP/1.0：每请求一连接（Connection: close 默认）→ 每次 TCP+TLS 握手
HTTP/1.1：keep-alive 默认开启 → 连接复用

一次握手的成本（连接建立时间）：
  TCP 三次握手：1 RTT
  TLS 1.3：1 RTT（旧 TLS 1.2：2 RTT）
  → 新连接总计 2-3 RTT，复用连接 = 0 RTT 起步

高并发场景（10 万 QPS）：
  短连接：每请求 1 个连接 → 握手风暴 + TIME_WAIT 海量（06 章）
  keep-alive：每客户端 1-6 个连接常驻 → 握手与端口压力骤减
```

### 1.2 连接池：客户端的 keep-alive

```java
// 客户端连接池（HTTP 客户端/数据库客户端同理）：
// 复用已建立连接，避免每请求新建 —— 高并发客户端的第一优化
// 例：Apache HttpClient 连接池、OkHttp 连接池、数据库连接池

// 要点：
//  1. 池大小 = 目标并发（太大浪费 fd，太小排队）
//  2. 空闲回收与超时（IdleConnectionMonitor）
//  3. 连接校验（归还前检测是否已断）
```

| 连接管理 | 短连接 | 连接池/keep-alive |
|---------|:---:|:---:|
| 每请求握手 | 2-3 RTT | 0 |
| 服务器连接数 | QPS × 并发客户端 | 有界（池大小） |
| TIME_WAIT 压力 | 高 | 低 |
| 复杂度 | 低 | 中（池管理） |

> 🎯 **核心要点**：应用层高并发第一定律——**能复用连接就不要新建**。服务器靠 keep-alive，客户端靠连接池，两端缺一不可。

## 2. HTTP/2：单连接多路复用与队头阻塞

### 2.1 核心能力

```text
HTTP/2（RFC 9113，2015）：
  二进制分帧：请求/响应拆成帧（HEADERS/DATA）
  多路复用：一个 TCP 连接上并发多个"流"（stream），每流一个请求-响应
  头部压缩：HPACK（静态+动态字典）
  服务器推送（已废弃于 2026 实践）与优先级

收益：并发请求不再需要多个连接；一个连接承载所有流
```

### 2.2 队头阻塞（HOL blocking）——HTTP/2 的软肋

```text
HTTP/2 的多路复用在"一个 TCP 连接"上：
  TCP 保证有序 → 某流的一个包丢失 → 整个连接重传等待
  → 该连接上的所有流全部阻塞（哪怕其他流的数据完好）

对比：
  HTTP/1.1 keep-alive：多连接 → 丢包只影响一个连接（但连接数多）
  HTTP/2：单连接 → 丢包 = 全连接阻塞（连接数少但更脆弱）
  弱网/高丢包下：HTTP/2 反而比 HTTP/1.1 慢（实测 10% 丢包时 +60% 差距被 QUIC 反超）

  2026 现状：HTTP/2 仍是 Web 主流（浏览器默认 HTTP/2 over TLS），
  但其队头阻塞正是 HTTP/3 的诞生动机
```

## 3. HTTP/3 QUIC：无队头阻塞的传输（2026）

### 3.1 架构

```text
HTTP/3 = HTTP 语义 + QUIC 传输（RFC 9000, 2021）+ TLS 1.3 内建

QUIC 核心设计（解决 HTTP/2 的两个痛点）：
  ① 流内独立：一个连接内多个"流"，每流独立序号与确认
     → 流 A 丢包只重传流 A，流 B 的数据照常交付（无队头阻塞）
  ② 握手合并：首次 1-RTT（TCP+TLS 的 1+1 RTT 合并），回访 0-RTT
  ③ 连接迁移：连接 ID 识别连接（而非四元组）
     → Wi-Fi→蜂窝切换不断连
  ④ 全部用户态实现（内核只处理 UDP）→ 快速迭代
```

### 3.2 2026 采用现状（检索数据）

| 维度 | 数据 |
|------|------|
| 浏览器 | **95%+** 主流浏览器支持；全球约 93% 用户可用 |
| 网站 | 头部 1000 万网站约 **34-40%** 服务 HTTP/3（W3Techs/维基百科口径） |
| 云厂商 | Cloudflare 边缘流量约 **35%**；Meta 自有流量约 **75%** |
| 流媒体 | 大型 OTT 的字节流量 60-80% 走 HTTP/3 |
| 地域 | 移动优先市场领先（印度 29%、巴西 29%、意大利 30%——弱网收益最大） |

### 3.3 性能数据（弱网是主场）

```text
基准（明尼苏达→多数据中心）：
  小站：+15-20%；内容型：+25-35%；SPA：+30-40%（对比 HTTP/2）
  10%+ 丢包下：比 HTTP/2 快 60%+，比 HTTP/1.1 快 50%+
  干净网络：收益有限（3-5%）——QUIC 的价值在弱网与移动场景

实验室（10Gbps，quic-go）：
  4 流 QUIC：8.1Gbps / 12ms RTT
  单流 TCP+TLS：4.2Gbps / 22ms RTT
```

### 3.4 部署注意

| 事项 | 说明 |
|------|------|
| UDP 放行 | 需允许 443/80 的 UDP（很多防火墙默认拦） |
| 负载均衡 | L4 LB 需 QUIC 感知（连接迁移打破四元组哈希，HAProxy 2.6+ 支持）——08 章 |
| 0-RTT 安全 | 重放风险：仅幂等请求可用 0-RTT |
| 调试 | 需 QUIC 专用工具（qlog/SSLKEYLOGFILE） |
| 服务端支持 | Nginx 1.25.0+ 内建；Caddy 默认开；Envoy v1.28+ 原生监听 |

## 4. QUIC 的工程化参数

| 参数 | 默认 | 高并发建议 | 说明 |
|------|:---:|:---:|------|
| `max_concurrent_streams` | 100 | 1000-2000 | 单连接并发流上限（CDN 调高） |
| `initial_max_data` | 较小 | 10MiB | 连接级数据量窗口 |
| `idle_timeout` | 30s | 30s+ | 空闲断开（对心跳类调整） |
| 流优先级 | - | 按业务 | 视频首帧/小包优先 |

```text
生产堆栈（Envoy/Nginx/Cloudflare）都已暴露上述旋钮；
ASP.NET Core 10 的 QUIC 栈：首字节时延 -30%（握手 42ms→29ms，内部基准）
```

## 5. WebSocket：真正的长连接

| 维度 | HTTP keep-alive | WebSocket |
|------|:---:|:---:|
| 协议 | HTTP（请求-响应） | 独立帧协议（升级自 HTTP 101） |
| 方向 | 客户端发起 | **双向**（服务器可主动推送） |
| 典型场景 | 常规 API | 聊天/推送/实时协作/游戏 |
| 连接数量 | 客户端数 × 池大小 | 每客户端 1 连接常驻 |
| 心跳 | 无（靠超时） | 应用层 ping/pong |

```text
高并发注意：
  ① WebSocket 连接是"常驻空闲连接" → 服务器连接数 = 在线用户数
     → 必须事件驱动（每连接一线程 = 灾难）——虚拟线程/Reactor 皆可
  ② 心跳与断线重连：移动网络下连接漂移是常态
  ③ 消息推送可降级：SSE（单向）+ 轮询（低并发兜底）
```

## 6. Nginx 高并发配置实战

```nginx
# nginx.conf 高并发核心配置（百万级连接目标）
worker_processes auto;                        # 进程数 = 核数（事件驱动模型）
worker_rlimit_nofile 1000000;                 # 进程 fd 上限（配合 ulimit）

events {
    use epoll;                                 # Linux 默认；多路复用器
    worker_connections 102400;                 # 每 worker 连接上限（102400×核数）
    multi_accept on;                           # 一次 accept 多个连接
    accept_mutex off;                          # 多 worker 轮询 accept（内核分担）
}

http {
    sendfile on;                               # 零拷贝（05 章）
    tcp_nopush on;                             # 大包合发
    keepalive_timeout 65;                      # HTTP keep-alive 时长
    keepalive_requests 1000;                   # 单连接最大请求数
    server {
        listen 80 backlog=4096;                # accept 队列（06 章）
        listen 443 ssl http2;                  # HTTP/2（TLS 下）
        listen 443 quic reuseport;             # HTTP/3（QUIC，1.25.0+）
        http3 on;
    }
}
```

```text
Nginx 高并发模型总结：
  多进程（每核一个）× 事件驱动（epoll）× 零拷贝（sendfile）
  → 单机轻松扛百万连接（静态资源场景）
```

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 应用层第一定律是"连接复用"：服务器 keep-alive + 客户端连接池，握手与 TIME_WAIT 压力同时消失；
> 2. HTTP/2 用单连接多路复用换来了"连接内队头阻塞"，QUIC（HTTP/3）用独立流彻底解决——2026 年已过临界点（浏览器 95%+、头部网站 34-40%）；
> 3. WebSocket 是"每用户常驻连接"模式，必须事件驱动支撑；Nginx 高并发 = 多进程 × epoll × sendfile 三件套。

**思考题**：

1. HTTP/2 的队头阻塞发生在哪一层？（→ 2.2：TCP 连接层）
2. QUIC 为什么能"连接迁移"？（→ 3.1：连接 ID 而非四元组）
3. 为什么弱网下 QUIC 优势最大？（→ 3.3）
4. WebSocket 高并发为什么必须事件驱动？（→ 5）
