## 1. 为什么要负载均衡：单机极限与集群

```text
单机极限（2026 参考）：
  CPU：32 核 × 每核 ~10-15 万 QPS（简单请求）→ 单机 ~几百万 QPS 理论
  现实：应用逻辑/GC/DB 把单机压在 ~1-10 万 QPS
  → 业务高并发必然走向集群

集群 = 多台服务器 + 统一入口（负载均衡器）
负载均衡的四个职责：
  ① 分流：把请求按算法分给后端
  ② 容错：健康检查剔除故障节点
  ③ 扩展：加机器即加容量（水平扩展）
  ④ 会话保持：粘性会话/无状态化
```

```text
分层结构（经典三层）：
  客户端 → DNS（域名→IP）
          → 四层 LB（LVS/云 LB：IP+端口转发）
          → 七层 LB（Nginx：按 URL/Host 路由）
          → 应用服务器集群
          → 数据库/缓存集群
```

> 🎯 **核心要点**：负载均衡是"单机到集群"的桥梁——它不产生吞吐，只负责"把流量均匀、正确地分给能干活的人"。

## 2. 四层 vs 七层：两种分流粒度

| 维度 | 四层（L4） | 七层（L7） |
|------|-----------|-----------|
| 工作层次 | 传输层（TCP/UDP 端口） | 应用层（HTTP 内容） |
| 看到什么 | IP + 端口 | URL、Host、Cookie、请求头 |
| 转发方式 | 直接转发报文（性能极高） | 代理请求（可改写、可缓存） |
| 性能 | ~百万级连接/请求 | 十万级（有协议解析成本） |
| 能力 | 基础分流、限流 | 路由、重写、限流、缓存、鉴权、灰度 |
| 代表 | **LVS**、云 LB（SLB/NLB）、HAProxy（tcp 模式） | **Nginx**、HAProxy（http 模式）、云 ALB |
| 典型组合 | 外层 LVS 抗流量 → 内层 Nginx 做路由 | 经典双栈架构 |

```text
工程组合（大厂标配）：
  入口：LVS（四层，扛百万并发连接）
  中间：Nginx（七层，路由/限流/静态）
  后端：应用集群（业务）
  → "LVS 抗打，Nginx 精分" 
```

## 3. LVS：内核级四层负载均衡

### 3.1 三种模式

| 模式 | 转发方式 | 性能 | 特点 |
|------|---------|:---:|------|
| **DR（Direct Routing）** | 改写 MAC，直接回包 | **最高** | 响应不经过 LB（LB 只处理请求）；要求 RS 与 LB 同网段/VIP 绑定 |
| TUN（隧道） | IP 封装隧道转发 | 高 | 支持跨网段（RS 需支持 IPIP） |
| NAT | 地址转换转发 | 中 | RS 只需普通服务器；**响应也经 LB**（回程瓶颈） |

```text
DR 模式为何吞吐最高：
  请求：客户端 → LB（改写 MAC 后转发给 RS）
  响应：RS 直接回客户端（不经 LB）——LB 只承载请求流量，回程压力为零
  对比 NAT：请求+响应都经 LB → LB 出口带宽=总流量（瓶颈）

生产选择：同机房场景几乎都是 DR；跨机房用 TUN；小型场景 NAT 足够
```

### 3.2 LVS 的高可用：keepalived

```text
LVS 本身是内核模块（无守护进程）→ 需要 keepalived 做：
  ① VIP 管理：主备漂移（VRRP 协议）
  ② 后端健康检查：RS 挂了自动摘除
  ③ 配置下发：把 IPVS 规则灌给内核

高可用形态：主 LVS + 备 LVS（VIP 漂移）+ N 台 RS
```

## 4. Nginx：七层应用网关

### 4.1 作为负载均衡器的配置

```nginx
http {
    upstream backend {                      # 后端集群定义
        server 10.0.0.1:8080 weight=3;      # 权重
        server 10.0.0.2:8080;
        server 10.0.0.3:8080 down;          # 手动下线
        keepalive 64;                       # 到后端的连接池（复用）
    }
    server {
        listen 80;
        location /api/ {
            proxy_pass http://backend;
            proxy_next_upstream error timeout;   # 失败重试下一个
        }
    }
}
```

### 4.2 七层能做的四层做不到的事

```text
① 内容路由：/api → A 集群，/static → 静态（sendfile）
② 灰度发布：按 Header/Cookie 分流（canary）
③ 限流熔断：ngx_http_limit_req / 慢启动
④ 缓存：静态资源边缘缓存（proxy_cache）
⑤ 安全：WAF 规则、防 CC
代价：协议解析的 CPU 成本 —— 所以大流量先经 LVS 再进 Nginx
```

## 5. DNS 轮询与云负载均衡

### 5.1 DNS 轮询：最"低层"的分流

```text
域名解析返回多个 A 记录 → 客户端随机/顺序选择 IP
  example.com → 10.0.0.1 / 10.0.0.2 / 10.0.0.3

优点：实现零成本、天然地理分布
缺点：
  ① 无健康检查（IP 挂了客户端才知道，依赖 TTL 刷新）
  ② 粒度粗（按 IP 而非连接/请求）
  ③ 缓存滞后（TTL 期间无法调整）
用途：多数据中心入口分流、CDN 调度（GSLB 的现代形态）
```

### 5.2 云负载均衡（SLB/ALB/NLB）

| 云 LB | 层级 | 特点 |
|-------|:---:|------|
| SLB/NLB | 四层 | 大流量入口、百万并发 |
| ALB | 七层 | HTTP 路由、与 K8s Ingress 集成 |
| 全球加速（GA/GTM） | DNS+ | 就近接入、跨区域容灾 |

> 💡 **部署范式**：云上标准形态 = 云 LB（入口）→ K8s Ingress/Nginx（路由）→ Pod 集群。与自建 LVS+Nginx 是同一架构思想的托管版。

## 6. 分发算法：三种哲学

| 算法 | 原理 | 适用 | 问题 |
|------|------|------|------|
| **轮询（RR）** | 按序轮流 | 请求量均匀、节点同配 | 慢节点拖累（无感知） |
| 加权轮询 | 按权重分配 | 异构机器 | 权重需人工维护 |
| **最少连接（LC）** | 分给连接最少者 | 长连接/耗时差异大 | 需要实时连接数统计 |
| **一致性哈希** | 按 key 哈希到固定节点 | **会话保持**、缓存路由 | 节点变化需虚拟节点平滑 |
| IP 哈希 | 同 IP 同节点 | 会话保持（简单方案） | 粒度粗、NAT 下失效 |

```text
三种哲学的区分（面试答法）：
  轮询 = "平均主义"（适合同质请求）
  最少连接 = "按劳分配"（适合差异负载）
  一致性哈希 = "定向分发"（适合有状态/缓存场景）
  
一致性哈希要点：
  哈希环 + 虚拟节点（防节点稀疏导致倾斜）
  节点增减只影响 ~1/n 的 key（最小迁移）
  是 Redis 集群分片、缓存路由的基础算法
```

## 7. QUIC 时代的均衡挑战（2026）

### 7.1 问题：四元组哈希失效

```text
传统 L4 LB 按 (srcIP, srcPort, dstIP, dstPort) 哈希选后端：
  → 同一连接始终到同一后端（连接亲和）
  → TCP 三次握手后 LB 无需再决策

QUIC 的破坏：
  ① 连接迁移：客户端换网络 → 四元组全变 → 哈希目标漂移
  ② 0-RTT：第一个数据包就要"决策"，无握手期给 LB 学习
  ③ 连接 ID：真正的连接标识是 CID，不是四元组
```

### 7.2 解法

| 方案 | 说明 |
|------|------|
| QUIC 感知 LB | 解析 QUIC 包头（含 CID）做哈希——HAProxy 2.6+、Envoy、云厂商均已支持 |
| CID 保持 | LB 记录 CID→后端映射（迁移后仍路由到原后端） |
| UDP 支持 | LB 必须处理 UDP 443 流量（不止 TCP） |
| 应用层替代 | 无状态化后端 + 会话数据外置（Redis）——终极解：后端无状态，无需亲和 |

> ⚠️ **部署注意**：HTTP/3 上线前，检查链路中的每层 LB/防火墙/监控是否支持 UDP 与 QUIC——否则出现"浏览器支持但连接建立失败"的怪现象。

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 负载均衡 = 单机到集群的桥梁，四层（LVS，抗流量）与七层（Nginx，精路由）组合是经典双栈；
> 2. LVS DR 模式因"响应不经过 LB"吞吐最高；分发算法三哲学：轮询/最少连接/一致性哈希各司其职；
> 3. QUIC 时代 L4 均衡必须感知连接 ID（HAProxy 2.6+/Envoy 已支持），无状态后端是终极解。

**思考题**：

1. 为什么 LVS DR 模式吞吐最高？（→ 3.1：响应不经 LB）
2. 七层负载均衡能做什么四层做不到的事？（→ 4.2）
3. 一致性哈希解决什么场景？（→ 6）
4. QUIC 连接迁移为什么让传统 L4 LB 失效？（→ 7.1）
