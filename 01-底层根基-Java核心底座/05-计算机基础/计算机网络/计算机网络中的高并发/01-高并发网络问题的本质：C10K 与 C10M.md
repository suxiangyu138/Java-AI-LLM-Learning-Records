## 1. C10K 问题：从一个提问开始

### 1.1 历史背景

1999-2001 年，Dan Kegel 的 [C10K 页面](http://www.kegel.com/c10k.html) 提出：**一台服务器同时服务 10,000 个客户端**（C10K = 10K 并发连接）。当时的主流做法是"每连接一个进程/线程"，而 1 万线程已经触及 OS 极限。

```text
1999-2001 年的服务器现实：
  内存：256MB - 1GB（每线程栈 ~8MB 虚拟内存 → 1 万线程 = 80GB 虚拟空间）
  CPU：单核 - 双核
  操作系统：Linux 2.2/2.4（select 上限 1024 个 fd）
  结论：每连接一线程在 1 万连接面前彻底破产
```

### 1.2 为什么是"1 万"这个数字

```text
1 万连接 × 每连接 1 线程：
  内存：~8MB 栈/线程（虚存）→ 80GB（远超可用内存）
  CPU：万级线程的上下文切换 → 大量时间耗在内核调度
  fd：select 单次监视上限 1024 → 需要分块轮询
  → 三座大山（内存/CPU/fd）全部触顶
```

> 🎯 **核心要点**：C10K 的本质不是"网络慢"，而是"**操作系统资源模型与并发规模不匹配**"——线程的 1:1 内核映射在万级连接下既费内存又费调度。

## 2. 每连接成本模型

### 2.1 四项核心成本

| 成本项 | 内容 | 量级（2026 参考） |
|--------|------|------------------|
| **内存** | 连接对应的内核缓冲区（收发）、应用缓冲区 | 每连接 ~几十 KB（内核 + 用户态合计） |
| **文件描述符** | 每连接一个 fd；进程上限、系统上限 | 默认 1024 → 生产调到 100 万 |
| **CPU** | 处理每包数据的协议栈成本（校验和、分片、拥塞控制） | 万级连接 × 低速率 = 空闲轮询浪费 |
| **调度** | 每线程上下文切换（线程模型）或事件分发（事件模型） | 线程切换微秒级 × 万级 = 灾难 |

```text
关键公式（并发连接估算）：
  服务器并发上限 ≈ min(
      内存预算 / 每连接内存,
      文件描述符上限,
      CPU 能力 / 每连接 CPU 成本
  )
  2026 的典型值：32GB 内存服务器可扛 ~100 万连接（事件驱动 + 调优后）
```

### 2.2 两种成本结构对比

| 模型 | 每连接固定成本 | 每活跃连接成本 | 空闲连接成本 |
|------|:---:|:---:|:---:|
| 每连接一线程 | ~8MB 栈（虚拟） | 一次线程调度 | **照占线程（大）** |
| 事件驱动 | ~几十 KB 缓冲区 | 一次事件分发 | **几乎为零（小）** |

> 💡 **理解关键**：绝大多数连接是"空闲的"（长连接/轮询/聊天）。线程模型为**每个空闲连接**支付完整线程成本；事件驱动只为**活跃事件**支付成本——这就是 C10K 的分水岭。

## 3. 线程模型 vs 事件驱动模型

| 维度 | 线程模型（每连接一线程） | 事件驱动（多路复用 + 回调） |
|------|:---:|:---:|
| 代表 | Apache 2.2、早期 Tomcat BIO | Nginx、Redis、Netty、Node.js |
| 并发上限 | 数千（受线程数限制） | 数十万~百万 |
| 代码形态 | 同步阻塞（简单直觉） | 回调/状态机（复杂） |
| CPU 密集任务 | 能利用多核（多线程并行） | 单线程内串行（需多进程/多 EventLoop） |
| 空闲连接 | 浪费线程 | 几乎零成本 |
| 编程难度 | 低（阻塞语义） | 高（回调地狱、背压处理） |

```text
2020 年代的第三形态：虚拟线程（JUC 体系）
  "每连接一个虚拟线程" = 线程模型的代码形态 + 事件驱动的资源成本
  → 但虚拟线程底层仍依赖多路复用器（内核 epoll/io_uring）
  → 网络高并发的"内核地基"永远不变，变的只是用户态模型
```

## 4. 问题演进：C10K → C100K → C1M → C10M

| 量级 | 时代 | 主要挑战 | 破局技术 |
|:---:|------|---------|---------|
| C10K | 2001 前后 | 线程模型破产 | **epoll/kqueue**、事件驱动（Nginx/Node.js） |
| C100K | 2010s | 内存与 fd 优化 | 连接池化、缓冲区调优、64 位内核 |
| C1M | 2015s | 内核协议栈压力 | 调优（tcp_tw_reuse 等）、多核分散（SO_REUSEPORT） |
| C10M | 2013+ 讨论 | **协议栈本身**成为瓶颈 | 用户态协议栈（DPDK/XDP）、内核旁路 |

```text
C10M 的提出（2013 年 RTS 会议）：
  1M 连接时代还能靠"调优内核"，10M 连接时：
  - 中断风暴：每个包触发软中断 → CPU 全被中断吃掉
  - 协议栈成本：每包在协议栈走一遍（校验/队列/调度）
  - 解法思路：内核旁路（DPDK 用户态驱动）、XDP/eBPF 早期处理、
    大页内存、CPU 亲和（每核专用队列）
```

> ⚠️ **现实判断**：C10M 属于"演示性指标"（单机 1000 万连接已用 DPDK/专用硬件验证过），业务服务器现实目标仍是 C100K~C1M 级——**把 C10M 技术用进业务系统 = 过度设计**。生产语境下的"高并发"是百万连接级。

## 5. 2026 的现实：百万连接的服务器

### 5.1 单机能力参考

```text
2026 年主流服务器（32 核 / 32GB+）事件驱动栈的实测量级：
  - 100 万并发 TCP 长连接（聊天/推送类）：可行（epoll + 调优）
  - 20 万并发 HTTP 短连接（Web 服务）：常规
  - 单连接多路复用（HTTP/2 流）：200K 流 × p99 80µs（io_uring 优化后）
  - 极限压测：200K 连接 100Gbps 下，epoll 2.1M req/s ↔ io_uring+SQPOLL 4.8M req/s
```

### 5.2 生产环境的"高并发"分层

| 层 | 手段 | 量级 |
|----|------|:---:|
| 单机内核 | epoll/io_uring + TCP 调优 | ~100 万连接 |
| 单机应用 | Reactor/多 EventLoop + 零拷贝 | 数十万 QPS |
| 集群 | 负载均衡（LVS/Nginx）+ 水平扩展 | 无限（加机器） |

> 🎯 **核心要点**：2026 年单机百万连接是"可达的常规指标"，代价是整套技术栈的正确（多路复用 + 事件驱动 + 调优）；再往上不是"单机问题"而是"架构问题"（08 章）。

### 5.3 案例：百万连接聊天室的完整技术栈

以"100 万在线用户的 IM 推送服务"为例，看 C10K 各层方案如何组合：

| 层 | 方案 | 承载 |
|----|------|------|
| 内核 | epoll（或 io_uring）+ TCP 调优（06 章） | 100 万并发 TCP 连接 |
| 应用模型 | 主从 Reactor（Netty/自定义），每连接一个虚拟线程或 Handler | 读写分发不阻塞 |
| 内存 | 每连接几十 KB 缓冲 × 100 万 ≈ 30-50GB（要预算！） | 连接状态 |
| 协议 | 自定义二进制帧 / WebSocket 心跳（07 章） | 保活与消息 |
| 横向扩展 | LVS 四层入口 + 网关路由（08 章） | 多机分摊 |
| 状态外置 | 会话存 Redis（无状态后端） | 任意节点承接 |

```text
关键推论：100 万连接不是"某一层的胜利"——
  内核、模型、内存预算、协议、集群五层缺一不可。
  面试答 C10K 相关题时，能说出"单机连接数要配内存预算"是加分项。
```

## 6. 每连接成本的现代细账（C10M 视角的推演）

### 6.1 10M 连接的资源分解（2013 年经典推演）

```text
目标：单机 1000 万并发连接（C10M），逐项算账：

内存：
  每连接内核收发缓冲（各 16KB 起）→ 10M × 32KB ≈ 320GB ✗
  对策：调小缓冲（tcp_rmem/wmem 下限 4KB）→ ~80GB（仍昂贵）
  用户态每连接状态（~1KB）→ 10GB

CPU：
  每包软中断处理（校验和/队列）→ 10M 连接 × 心跳级流量
  = 每秒数千万包 → 单核协议栈 ~1-2M pps 封顶
  对策：RSS 多队列分散多核 + 大页 + CPU 亲和
  → 协议栈本身是瓶颈 → 内核旁路（DPDK/XDP）的必要性

文件描述符：
  10M 连接 = 10M fd → ulimit/fs.file-max 调至 1000 万级（可行）
  事件驱动（epoll）监视 10M fd：红黑树 ~O(log n) 注册（可行）
```

### 6.2 结论：C10M 的四个"必须"

```text
① 必须事件驱动（每连接线程 = 内存与调度双重爆炸）
② 必须小缓冲（内存预算与连接数成反比）
③ 必须多核分散（RSS/SO_REUSEPORT——单核协议栈有 pps 上限）
④ 必须旁路或卸载（DPDK/XDP/硬件 offload——协议栈占 CPU）

业务现实（再次强调）：
  单机百万连接 = 常规工程（第 5 节）
  单机千万连接 = 专用基建（DPDK/定制栈）
  再往上 = 集群问题（08 章负载均衡）
  → 面试答"C10M"：先给成本分解，再给四必须，最后落回工程现实
```

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. C10K 的本质是"线程的 1:1 内核映射在万级连接下成本爆炸"——内存、fd、调度三座大山；
> 2. 破局范式是事件驱动（多路复用 + 回调）：只为活跃事件付费，空闲连接成本趋零；
> 3. 演进史 C10K→C10M：epoll 解决"监视"，调优解决"资源"，DPDK/XDP 解决"协议栈"——业务现实目标是百万连接级。

**思考题**：

1. 为什么空闲连接在事件驱动模型下"几乎零成本"？（→ 2.2）
2. 虚拟线程与事件驱动是什么关系？（→ 3 第三形态）
3. C10M 为什么需要内核旁路（DPDK）？（→ 4）
4. 单机 100 万连接在 2026 年意味着什么？（→ 5.1）
