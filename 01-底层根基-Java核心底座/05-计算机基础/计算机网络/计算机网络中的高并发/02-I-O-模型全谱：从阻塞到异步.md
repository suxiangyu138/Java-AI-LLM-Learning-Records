# I/O 模型全谱：从阻塞到异步

## 1. 两个维度的定义：阻塞性与异步性

```text
维度一：阻塞 vs 非阻塞（调用者的视角）
  阻塞：系统调用不返回，直到数据就绪（read 卡住等数据）
  非阻塞：系统调用立即返回（可能返回 EAGAIN"数据还没来"）

维度二：同步 vs 异步（数据搬运的视角）
  同步：数据从内核→用户缓冲区的拷贝由"调用者"完成（read 自己拷）
  异步：数据拷贝由内核完成，完成后通知（aio_read/io_uring：内核拷完发完成事件）
```

> ⚠️ **常见混淆**："非阻塞"不等于"异步"——非阻塞的 read 仍要**你自己**把数据从内核拷贝到用户缓冲区；异步则是**内核帮你拷完**再告诉你。Java 语境里 NIO 其实是非阻塞+同步，AIO 才是真异步。

## 2. 五种 I/O 模型总览

以"read 数据"为例：

| # | 模型 | 发起调用 | 数据就绪时 | 数据搬运 | 代表 |
|:---:|------|---------|-----------|---------|------|
| ① | 阻塞式（BIO） | `read` 卡住 | 返回并拷贝 | 调用者 | 传统 socket、Tomcat BIO |
| ② | 非阻塞式 | 返回 EAGAIN 忙等 | 轮询发现后拷贝 | 调用者 | 自旋轮询（几乎不用） |
| ③ | 多路复用（IO 多路复用） | `epoll_wait` 等就绪 | 通知就绪，再 `read` | 调用者 | **Nginx/Netty/Redis** |
| ④ | 信号驱动式 | `sigio` 信号通知 | 信号处理中拷贝 | 调用者 | 少用（信号开销） |
| ⑤ | 异步式（AIO） | `io_uring` 提交请求 | 内核完成并拷贝 | **内核** | io_uring/AIO、Windows IOCP |

```text
关键区分：③ 多路复用 = "内核通知'可以读了'，你自己读"
          ⑤ 异步     = "内核读完了，把结果给你"
  epoll 是③；io_uring 是⑤（可兼做③的替代）
```

## 3. 模型对比：从阻塞到异步的演进

### 3.1 ① 阻塞式（BIO）：简单但费线程

```java
// 每连接一个线程，阻塞在读上
while (true) {
    Socket s = serverSocket.accept();        // 阻塞等连接
    new Thread(() -> {
        byte[] buf = new byte[1024];
        s.getInputStream().read(buf);        // 阻塞等数据 —— 线程卡死在这
        handle(buf);
    }).start();
}
// 问题：1 万连接 = 1 万线程（C10K 的根源）
```

### 3.2 ② 非阻塞式：不卡线程但忙等

```java
s.setNonBlocking(true);
while (true) {
    int n = s.getInputStream().read(buf);    // 立即返回：有数据返回字节数，没数据返回 -1/EAGAIN
    if (n > 0) { handle(buf); }
    // 否则：继续循环轮询 —— CPU 空转
}
// 问题：轮询消耗 CPU，没有"等通知"的机制
```

### 3.3 ③ 多路复用：等一批 fd 的通知（本体系主角）

```java
// 一个线程监视 10 万个 fd："哪个可读就通知我"
Selector selector = Selector.open();           // Java NIO 封装 epoll
for (SocketChannel ch : allChannels) {
    ch.register(selector, SelectionKey.OP_READ);   // 注册关心的事件
}
while (true) {
    selector.select();                          // 阻塞等就绪事件（内核通知）
    for (SelectionKey key : selector.selectedKeys()) {
        if (key.isReadable()) {
            SocketChannel ch = (SocketChannel) key.channel();
            ch.read(buf);                       // 就绪后 read 不阻塞
            handle(buf);
        }
    }
}
// 本质：把"等数据"从每个连接一个线程，变成"一个线程等所有连接"
```

### 3.4 ⑤ 异步式：内核搬数据，完成通知（2020s 主角）

```java
// io_uring（C 层面语义）：提交 read 请求 → 内核拷贝完 → 完成队列通知
// io_uring_prep_read(sqe, fd, buf, len, 0);   // 提交读请求
// io_uring_wait_cqe(ring, &cqe);              // 等完成通知（数据已拷好）
// 用户态不再执行拷贝，只消费完成事件
```

## 4. Java 视角：BIO / NIO / AIO

| 维度 | BIO | NIO（实际是 NIO + 多路复用） | AIO |
|------|:---:|:---:|:---:|
| 全称 | Blocking IO | Non-blocking IO | Asynchronous IO |
| 模型 | ①阻塞式 | ②非阻塞 + ③多路复用 | ⑤异步 |
| 内核机制 | 无（阻塞） | epoll（Linux）/ kqueue | io_uring（新）/ epoll 模拟 |
| 数据搬运 | 调用者 | 调用者（就绪后 read） | 内核 |
| 回调位置 | 无 | 事件循环内处理 | 完成回调（线程池执行） |
| 代表 | Tomcat BIO（已废弃） | **Netty、Tomcat NIO** | JDK AIO（Windows IOCP 可用性较好；Linux 上性能平平） |
| 现状 | 淘汰 | **生产主流** | 生产中少用（Netty 不用 AIO，改用 NIO+epoll；io_uring 是新方向） |

```java
// 关键认知：Java 的 NIO 不是"异步"！
// NIO 的 Selector.select() 是"同步等待就绪通知"，数据还是要自己 read
// 真异步（内核完成拷贝）在 Java 层 = AIO / 未来 io_uring 绑定
// Netty 选择 NIO（epoll）而非 AIO 的原因：Linux AIO 实现长期性能差，
//   epoll + 用户态事件循环已经足够快；io_uring 成熟后是下一个候选
```

> 🎯 **核心要点**：Java 生态里"NIO = epoll 多路复用"是主流；AIO 在 Linux 上历史上不争气；2026 年 io_uring 作为真异步方向正在渗透（数据库先行，Java 运行时有 Monoio/Glommio 等 Rust 方案，Java 生态尚在跟进）。

## 5. 同步异步 × 阻塞非阻塞矩阵

```text
                阻塞（调用不返回）          非阻塞（调用立即返回）
同步       ┌─────────────────────┬──────────────────────────┐
（自己搬运）│ ① 阻塞 IO（BIO）      │ ② 非阻塞 IO（轮询）        │
          │    经典 socket        │   忙等轮询，几乎不用       │
          ├─────────────────────┼──────────────────────────┤
          │ ③ 多路复用（就绪通知） │                          │
          │    epoll + read      │                          │
          │    ——"等"是阻塞的，     │                          │
          │    "读"是同步的        │                          │
异步       ├─────────────────────┼──────────────────────────┤
（内核搬运）│ ⑤ 异步 IO（io_uring） │  ④ 信号驱动（sigio）       │
          │    AIO/IOCP           │  边缘案例                │
          └─────────────────────┴──────────────────────────┘
```

| 组合 | 特点 | 代表 |
|------|------|------|
| 同步 + 阻塞 | 最简单，线程利用率低 | BIO |
| 同步 + 非阻塞 | 无意义（轮询浪费 CPU） | 教学用 |
| **同步 + 多路复用** | 一个线程管海量 fd，**事件驱动核心** | epoll/NIO/Netty |
| **异步 + 完成通知** | 内核搬数据，调用方只消费结果 | io_uring/AIO/IOCP |

## 6. 虚拟线程与 I/O 模型的再思考

```text
虚拟线程（JUC 体系）出现后，I/O 模型的"用户态形态"变了：
  代码形态：同步阻塞（像 BIO，好写）
  资源成本：事件驱动（像 NIO，省钱）

但注意底层不变：
  JDK 的 socket 实现（NioSocketImpl）底层仍是多路复用（epoll/selector）
  虚拟线程的"阻塞" = 注册到 selector + 挂起（park）
  数据就绪 → unpark → 恢复执行
  → 虚拟线程是"模型 ③（多路复用）之上的同步代码包装"
  真正的模型 ⑤（内核搬运）仍需 io_uring 级支持
```

| 层 | 选择 |
|----|------|
| 内核 | epoll（成熟）或 io_uring（性能，生态跟进中） |
| 语言运行时 | Netty（事件驱动）或 虚拟线程（同步代码） |
| 框架 | 两者并存：Spring WebFlux（事件驱动）vs Spring MVC+虚拟线程（同步） |

## 7. I/O 模型的工程选型全景

### 7.1 生产场景的模型选择

| 场景 | 推荐模型 | 理由 |
|------|---------|------|
| Web 服务（Tomcat/Spring） | NIO 多路复用（虚拟线程包装） | 高并发 + 代码同步 |
| 网关/代理（Nginx/Envoy） | 多路复用事件驱动 | 海量连接 + 低开销 |
| 数据库引擎 | io_uring（Proactor） | 磁盘+网络混合 I/O（03 章） |
| 低延迟交易 | 专用用户态栈/io_uring | 极致延迟控制 |
| 简单工具/脚本 | 阻塞式 | 复杂度最低 |

### 7.2 Java 生态的演进对照

```text
BIO（已淘汰）→ NIO（Netty/Tomcat NIO，现行主流）
→ 虚拟线程（JDK 21+，同步代码 + 多路复用底座）
→ io_uring 绑定（JEP 未来方向，Java 27+ 生态跟进中）

演进本质：代码形态（同步化）与资源成本（事件驱动）的逐步兼得
  → "既要同步代码的简单，又要多路复用的吞吐"是 Java 生态主线
```

### 7.3 选型决策树

```text
高并发网络编程选型：
  ① 需要极致吞吐（百万级 QPS）？
     → 事件驱动框架（Netty/Nginx 系）
  ② 需要代码可维护性优先？
     → 虚拟线程 + 同步代码（I/O 密集时吞吐足够）
  ③ 磁盘 + 网络混合、尾时延敏感？
     → io_uring 系（数据库引擎思路）
  ④ 团队技能与生态？
     → 默认选型：主流框架 + 多路复用（风险最低）
  → 结论：模型服从场景，场景服从团队
```

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 阻塞/非阻塞看"调用是否立即返回"，同步/异步看"数据谁搬"——epoll 是同步多路复用，io_uring 才是真异步；
> 2. 五种模型里生产主角是③多路复用（epoll 系），2020s 起⑤异步（io_uring）在数据库/存储领域成为新标配；
> 3. Java 的 NIO 不是异步；虚拟线程是"多路复用底座的同步代码包装"——内核地基不变。

**思考题**：

1. "非阻塞"为什么不等于"异步"？（→ 1 两个维度）
2. epoll 属于哪种模型？数据搬运谁负责？（→ 2 表格）
3. 为什么 Netty 用 NIO 而不用 AIO？（→ 4）
4. 虚拟线程的"阻塞"在内核层对应什么？（→ 6）
