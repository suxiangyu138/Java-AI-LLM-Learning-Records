## 1. IP组播

### 1.1 什么是IP组播

IP组播是一种"一对多"的通信模式：发送者将数据发送到一个特定的组播地址，所有加入该组播组的接收者都能收到数据，未加入的主机则无法接收。

> **💡 组播可以类比为"广播电台"：发送者是电台，组播地址是电台频率，接收者是调到该频率的收音机。**

### 1.2 组播 vs 单播 vs 广播

| 对比维度 | 单播 (Unicast) | 广播 (Broadcast) | 组播 (Multicast) |
|---------|---------------|-----------------|-----------------|
| 通信模式 | 一对一 | 一对所有 | 一对多 |
| 资源占用 | 发送者为每个接收者单独发送，带宽消耗大 | 发送一次，但占用所有主机资源 | 发送一次，路由器转发至组成员，带宽利用率高 |
| 跨网段支持 | 支持 | 不支持 | 支持（需开启组播路由） |
| 适用场景 | 点对点通信（HTTP、FTP） | 全局通知（ARP） | 实时多接收者通信（视频会议、直播） |

### 1.3 组播地址

IPv4组播地址范围：`224.0.0.0` ~ `239.255.255.255`（D类地址）

| 分类 | 地址范围 | 说明 |
|------|---------|------|
| 本地链路组播地址 | `224.0.0.0` ~ `224.0.0.255` | 仅本地局域网有效，路由器不转发 |
| 全球组播地址 | `224.0.1.0` ~ `238.255.255.255` | 可跨网段传播 |
| 管理权限组播地址 | `239.0.0.0` ~ `239.255.255.255` | 私有组播地址，仅特定域内有效 |

常用保留地址：
- `224.0.0.1`：本地局域网内所有主机
- `224.0.0.2`：本地局域网内所有组播路由器
- `224.0.1.1`：NTP网络时间协议

> **⚠️ 组播地址是"组的标识"，不是某个具体主机的地址。主机加入组播组后，会监听该组播地址的数据包。**

### 1.4 IGMP协议

IGMP（互联网组管理协议）是主机与组播路由器之间的通信协议，核心作用是管理组播组成员。

**核心流程：**
1. **加入组**：主机向路由器发送IGMP加入消息
2. **保持**：路由器定期查询网段内主机是否仍在组内
3. **退出**：主机发送IGMP退出消息，或超时未响应

### 1.5 Java实现组播

Java通过`java.net.MulticastSocket`类实现组播通信。

**核心API：**

| 方法 | 说明 |
|------|------|
| `joinGroup(InetAddress group)` | 加入组播组 |
| `leaveGroup(InetAddress group)` | 退出组播组 |
| `send(DatagramPacket p, byte ttl)` | 发送组播数据报 |
| `receive(DatagramPacket p)` | 接收组播数据报（阻塞） |
| `setTimeToLive(int ttl)` | 设置TTL值 |
| `setSoTimeout(int timeout)` | 设置接收超时 |

**TTL参数：**

| TTL值 | 范围 |
|-------|------|
| 0 | 仅本地主机 |
| 1 | 仅本地局域网（默认值） |
| > 1 | 可跨多个路由器 |

**组播发送者：**

```java
public class MulticastSender {
    private static final String MULTICAST_IP = "224.0.0.1";
    private static final int MULTICAST_PORT = 8888;
    private static final int TTL = 1;

    public static void main(String[] args) throws Exception {
        try (MulticastSocket socket = new MulticastSocket()) {
            socket.setTimeToLive(TTL);
            InetAddress group = InetAddress.getByName(MULTICAST_IP);

            String msg = "Hello from multicast sender";
            DatagramPacket packet = new DatagramPacket(
                msg.getBytes("UTF-8"), msg.length(), group, MULTICAST_PORT);
            socket.send(packet);
            System.out.println("组播消息已发送");
        }
    }
}
```

**组播接收者：**

```java
public class MulticastReceiver {
    private static final String MULTICAST_IP = "224.0.0.1";
    private static final int MULTICAST_PORT = 8888;

    public static void main(String[] args) throws Exception {
        try (MulticastSocket socket = new MulticastSocket(MULTICAST_PORT)) {
            InetAddress group = InetAddress.getByName(MULTICAST_IP);
            socket.joinGroup(group);
            System.out.println("已加入组播组：" + MULTICAST_IP);

            byte[] buffer = new byte[1024];
            DatagramPacket packet = new DatagramPacket(buffer, buffer.length);
            socket.receive(packet);

            String msg = new String(packet.getData(), 0, packet.getLength(), "UTF-8");
            System.out.println("收到组播消息：" + msg);

            socket.leaveGroup(group);
        }
    }
}
```

> **💡 组播注意事项：发送者无需加入组播组；接收者必须先调用`joinGroup()`；发送和接收端口必须一致；测试时确保在同一局域网。**

## 2. 多媒体网络

### 2.1 多媒体数据传输特征

多媒体数据（音频、视频）的传输与传统文本数据有本质区别：

| 特征 | 说明 | 后端影响 |
|------|------|---------|
| **高带宽需求** | 视频数据量大（1080p约4-8Mbps） | 带宽规划、压缩策略 |
| **实时性要求** | 延迟敏感（通话延迟<150ms） | UDP优先、关闭Nagle算法 |
| **丢包容忍** | 少量丢包不影响感知 | 无需100%可靠传输 |
| **时序要求** | 音视频同步、播放顺序 | RTP时间戳、序列号 |

### 2.2 流媒体协议

| 协议 | 全称 | 传输层 | 作用 |
|------|------|--------|------|
| **RTSP** | 实时流协议 | TCP | 音视频控制（播放、暂停、推流控制） |
| **RTP** | 实时传输协议 | UDP | 多媒体数据实时传输，附带时间戳/序列号 |
| **RTCP** | 实时传输控制协议 | UDP | 监控RTP传输质量（延迟、丢包率） |
| **RTMP** | 实时消息协议 | TCP | Adobe推流协议（直播场景） |
| **HLS** | HTTP Live Streaming | TCP | Apple流媒体协议（m3u8+ts分片） |
| **HTTP-FLV** | HTTP + FLV | TCP | 基于HTTP的流媒体（Web直播） |

### 2.3 视频/音频编码

| 类型 | 编码 | 特点 | 适用场景 |
|------|------|------|---------|
| **视频编码** | H.264 | 主流编码，兼容性最好 | 通用场景 |
| | H.265/HEVC | 压缩率比H.264高50% | 4K/8K超高清 |
| | AV1 | 开源免费，压缩率更高 | Web端流媒体 |
| **音频编码** | AAC | 主流音频编码，音质好 | 通用音频场景 |
| | MP3 | 兼容性最广 | 传统音频格式 |
| | Opus | 低延迟，适合实时通信 | VoIP、视频会议 |

### 2.4 传输优化

| 优化点 | 方案 |
|--------|------|
| **UDP场景** | 应用层主动分片（MTU≤1400字节），避免IP层分片丢失 |
| **TCP场景** | 关闭Nagle算法（`TCP_NODELAY`），增大接收缓冲区 |
| **自适应码率** | 根据RTT和丢包率动态选择码率 |
| **CDN加速** | 多媒体节点部署CDN，降低传输延迟 |

```java
// 应用层主动分片
private static final int MTU_SIZE = 1400;

public List<byte[]> fragmentPacket(byte[] data) {
    List<byte[]> fragments = new ArrayList<>();
    for (int i = 0; i < data.length; i += MTU_SIZE) {
        int end = Math.min(i + MTU_SIZE, data.length);
        fragments.add(Arrays.copyOfRange(data, i, end));
    }
    return fragments;
}
```

### 2.5 QoS（服务质量）

| 机制 | 说明 | 实现 |
|------|------|------|
| **DiffServ（区分服务）** | 报文标记优先级（DSCP），逐跳行为 | 网络层标记，路由器调度 |
| **IntServ（综合服务）** | 端到端资源预留（RSVP） | 预留带宽，保证质量 |
| **流量整形** | 限制流量速率，平滑突发流量 | 令牌桶、漏桶算法 |

## 3. 无线网络与移动网络

### 3.1 无线网络

**WiFi标准演进（IEEE 802.11）：**

| 标准 | 频段 | 最大速率 | 发布年份 |
|------|------|---------|---------|
| 802.11a | 5GHz | 54Mbps | 1999 |
| 802.11b | 2.4GHz | 11Mbps | 1999 |
| 802.11g | 2.4GHz | 54Mbps | 2003 |
| 802.11n (WiFi 4) | 2.4/5GHz | 600Mbps | 2009 |
| 802.11ac (WiFi 5) | 5GHz | 3.5Gbps | 2013 |
| 802.11ax (WiFi 6/6E) | 2.4/5/6GHz | 9.6Gbps | 2019 |

**无线网络核心特征：**

| 特征 | 说明 | 后端影响 |
|------|------|---------|
| **高误码率** | 信号受距离、障碍物影响 | TCP重传频繁，延迟增加 |
| **带宽波动** | 受用户数量、信号强度影响 | 需自适应码率 |
| **干扰敏感** | 2.4GHz频段干扰严重 | 推荐5GHz频段 |
| **连接不稳定** | 设备移动导致断连 | 需断线重连机制 |

### 3.2 移动网络

**移动网络架构（简化）：**

```
移动设备 -> 基站(eNB/gNB) -> 核心网(EPC/5GC) -> 互联网 -> 后端服务器
```

**4G vs 5G 对比：**

| 对比项 | 4G LTE | 5G NR |
|--------|--------|-------|
| 峰值速率 | 1Gbps | 20Gbps |
| 用户面延迟 | 50-100ms | 1-10ms |
| 连接密度 | 10万设备/km² | 100万设备/km² |
| 核心架构 | EPC（专用硬件） | 5GC（服务化架构/SBA） |
| 关键技术 | OFDMA、MIMO | 毫米波、网络切片、URLLC |

**5G三大应用场景：**

| 场景 | 全称 | 特点 | 典型应用 |
|------|------|------|---------|
| **eMBB** | 增强移动宽带 | 高速率 | 4K/8K视频、AR/VR |
| **URLLC** | 超可靠低延迟通信 | 低延迟、高可靠 | 自动驾驶、工业控制 |
| **mMTC** | 大规模机器类通信 | 海量连接 | IoT传感器、智能抄表 |

> **💡 5G核心创新：网络切片（Network Slicing）——在一套物理网络上切分出多个虚拟网络，各自满足不同业务的SLA要求。**

### 3.3 移动网络对后端的影响

| 挑战 | 影响 | 优化方案 |
|------|------|---------|
| **高延迟** | 接口响应慢 | 合理设置超时时间 |
| **带宽波动** | 传输不稳定 | 数据压缩、分片上传 |
| **频繁切换** | 连接中断 | 接口幂等性、断点续传 |
| **高丢包率** | TCP重传增多 | 指数退避重试 |

**超时配置建议：**

| 网络类型 | 连接超时 | 读超时 | 写超时 |
|----------|---------|--------|--------|
| 4G | 5000-8000ms | 3000-5000ms | 5000-8000ms |
| 5G / WiFi | 3000-5000ms | 1000-3000ms | 3000-5000ms |

> **⚠️ 无线网络的不稳定性要求后端必须进行TCP优化：合理设置超时、实现指数退避重试、接口幂等设计。**

**指数退避重试实现：**

```java
@Configuration
@EnableRetry
public class RetryConfig {
    @Bean
    public RetryTemplate retryTemplate() {
        RetryTemplate template = new RetryTemplate();

        ExponentialBackOffPolicy backoff = new ExponentialBackOffPolicy();
        backoff.setInitialInterval(100);    // 初始间隔100ms
        backoff.setMultiplier(2);           // 每次翻倍
        backoff.setMaxInterval(800);        // 最大间隔800ms
        template.setBackOffPolicy(backoff);

        SimpleRetryPolicy retryPolicy = new SimpleRetryPolicy();
        retryPolicy.setMaxAttempts(3);      // 最多重试3次
        template.setRetryPolicy(retryPolicy);

        return template;
    }
}
```

## 4. CDN与网络优化

### 4.1 CDN核心架构

CDN（内容分发网络）通过在全球部署边缘节点，将内容缓存到离用户最近的节点，降低访问延迟。

**核心组件：**

| 组件 | 作用 |
|------|------|
| **源站（Origin Server）** | 内容的原始来源 |
| **边缘节点（Edge Node）** | 缓存内容的分布式服务器 |
| **调度系统（DNS/GSLB）** | 将用户请求路由到最优边缘节点 |
| **缓存系统** | 静态资源（图片、视频、HTML）的缓存策略 |

**CDN访问流程：**

```
用户请求 -> DNS调度 -> 就近边缘节点（命中则直接返回）
                     -> 未命中则回源站拉取 -> 缓存到边缘节点 -> 返回用户
```

**CDN核心优势：**

| 优势 | 说明 |
|------|------|
| **降低延迟** | 边缘节点靠近用户，网络跳数减少 |
| **减轻源站压力** | 静态内容由边缘节点处理 |
| **DDoS防护** | 边缘节点吸收攻击流量 |
| **高可用** | 多节点冗余，单节点故障自动切换 |

### 4.2 负载均衡

| 层级 | 技术 | 说明 |
|------|------|------|
| **L4负载均衡** | IP+端口转发 | 基于TCP/UDP四层信息，如LVS、F5 |
| **L7负载均衡** | HTTP/HTTPS内容分发 | 基于URL、Cookie、Header，如Nginx、HAProxy |
| **DNS负载均衡** | 域名解析多IP | 按地域轮询返回不同IP |

```nginx
# Nginx反向代理与负载均衡配置示例
http {
    upstream backend {
        server 192.168.1.10:8080 weight=3;
        server 192.168.1.11:8080 weight=2;
        server 192.168.1.12:8080 backup;  # 备用节点
    }

    server {
        listen 80;
        location /api/ {
            proxy_pass http://backend;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_read_timeout 30s;
        }

        location /static/ {
            root /var/www/static;
            expires 7d;  # 静态缓存7天
        }
    }
}
```

### 4.3 网络性能优化

| 技术 | 说明 |
|------|------|
| **带宽扩容** | 升级传输介质和网络设备 |
| **QoS流量调度** | 为关键业务分配优先级 |
| **边缘计算** | 计算资源部署到网络边缘，降低延迟 |
| **连接池** | 复用TCP连接，减少三次握手开销 |
| **HTTP/2多路复用** | 单一TCP连接并发传输多个请求 |

## 5. 网络应用架构模式

### 5.1 C/S模式（客户端/服务器）

最经典的网络应用模式，核心是"客户端主动请求，服务器被动响应"。

| 阶段 | 说明 |
|------|------|
| 部署准备 | 服务器监听端口，客户端安装应用 |
| 连接建立 | 客户端发起TCP三次握手 |
| 交互操作 | 客户端请求 -> 服务器处理 -> 返回响应 |
| 连接关闭 | 客户端完成操作后关闭连接 |

**特点：**
- 优势：分工明确、交互体验好、安全性高
- 劣势：需单独安装客户端、维护成本高
- 适用：即时通讯（微信/QQ）、FTP工具、工业监控

### 5.2 B/S模式（浏览器/服务器）

C/S模式的变体，以浏览器作为客户端。

| 阶段 | 说明 |
|------|------|
| 部署准备 | 服务器部署Web服务（Nginx/Apache） |
| 请求发起 | 用户输入URL，浏览器发起HTTP请求 |
| 交互操作 | 服务器处理业务，返回响应 |
| 结果展示 | 浏览器渲染网页 |

**特点：**
- 优势：无需安装、跨平台、维护成本低
- 劣势：交互体验受浏览器限制
- 适用：Web网站（百度/淘宝）、在线办公系统

### 5.3 P2P模式（对等网络）

无固定服务器，网络中的每个节点既是客户端也是服务器。

| 特点 | 说明 |
|------|------|
| 优势 | 去中心化、资源利用率高、抗风险能力强 |
| 劣势 | 安全性差、节点在线状态不稳定 |
| 适用 | BT下载、迅雷、区块链网络、分布式视频会议 |

### 5.4 混合模式

实际应用中通常采用混合架构：

```
前端（浏览器/APP）
    -> CDN边缘节点（静态资源加速）
    -> 负载均衡层（Nginx/LVS）
    -> 后端服务集群（Spring Boot微服务）
        -> 中间件层（Redis缓存、MQ异步）
        -> 数据层（MySQL、MongoDB）
```

### 5.5 模式选择指南

| 场景 | 推荐模式 | 原因 |
|------|---------|------|
| 大众互联网应用 | B/S | 无需安装、维护成本低 |
| 高交互工业应用 | C/S | 交互体验好、功能强 |
| 文件共享分发 | P2P | 去中心化、带宽利用高 |
| 大规模用户服务 | 混合（B/S + CDN + 负载均衡） | 兼顾体验、性能、可用性 |

> **🎯 总结：网络进阶知识体系的核心是理解不同场景下的技术选型。组播适合一对多实时通信，多媒体网络侧重带宽和延迟的平衡，无线/移动网络要求后端具备更强的容错和自适应能力，CDN和负载均衡是保障大规模服务的基石。**
