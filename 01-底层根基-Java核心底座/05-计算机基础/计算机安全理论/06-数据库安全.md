## 1. 访问控制与权限

```sql
-- 最小权限原则：应用账号只需要 CRUD
CREATE USER 'app_user'@'%' IDENTIFIED BY 'strong_password';
GRANT SELECT, INSERT, UPDATE, DELETE ON mydb.* TO 'app_user'@'%';
-- ❌ 永远不要: GRANT ALL / GRANT DROP / GRANT CREATE

-- 只读账号（BI / 数据分析）
GRANT SELECT ON mydb.* TO 'readonly_user'@'10.0.%';  -- 限制 IP 段

-- 定期审计权限
SELECT user, host, authentication_string FROM mysql.user;
SHOW GRANTS FOR 'app_user'@'%';
```

```text
数据库安全矩阵：
┌──────────────────────────────────────┐
│ 网络层: 防火墙 IP 白名单 + SSL/TLS    │
│ 认证层: 强密码 + 证书认证             │
│ 授权层: 最小权限 GRANT               │
│ 数据层: 加密 + 脱敏 + 备份           │
│ 审计层: 日志 + 告警                   │
└──────────────────────────────────────┘
```

## 2. 数据加密

```sql
-- 静态加密 (TDE: Transparent Data Encryption)
-- MySQL 8.0+ / PostgreSQL / SQL Server 内置
ALTER TABLE users ENCRYPTION='Y';    -- MySQL 表级加密

-- 列级加密（应用层）
-- 用 AES 加密敏感字段，密钥存储在 KMS（不在代码里！）
UPDATE users SET
    phone = AES_ENCRYPT('13800138000', @key_id)
WHERE id = 123;
```

```java
// Java 应用层加密实践
public class SensitiveDataEncryptor {
    // 从 KMS（AWS KMS/HashiCorp Vault）获取密钥
    private final SecretKey key = kmsClient.getKey("db-encryption-key");

    public String encrypt(String plaintext) {
        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        cipher.init(Cipher.ENCRYPT_MODE, key);
        byte[] iv = cipher.getIV();  // GCM 需要随机 IV
        byte[] encrypted = cipher.doFinal(plaintext.getBytes());
        return Base64.getEncoder().encodeToString(iv) + ":" +
               Base64.getEncoder().encodeToString(encrypted);
    }
}
```

## 3. SQL 注入防御深入

```text
第一道防线：预编译（解决 99% 的注入）
  → PreparedStatement / MyBatis #{}

第二道防线：输入校验
  → 类型检查 (id 必须是 Long)
  → 长度限制 (username 最大 50 字符)
  → 白名单 (ORDER BY 的列名必须在允许列表)

第三道防线：最小权限
  → app_user 没有 DROP/ALTER 权限
  → 即使被注入了也做不了大破坏

第四道防线：WAF / RASP
  → Web Application Firewall 检测 SQL 注入模式
  → 运行时自我保护（如阿里 RASP）
```

### 二次注入

```text
攻击场景：
  1. 用户注册用户名: admin' -- 
  2. 存入数据库时转义了 → admin\' --
  3. 后续修改密码时: UPDATE users SET password='xxx' WHERE username='admin' -- '
     → 所有 admin 用户的密码被改了！（- 注释掉了后面的条件）

防御：任何时候取出的数据再次用于 SQL 时，仍然要参数化！
```

## 4. 审计与脱敏

```sql
-- 审计日志（MySQL Enterprise / PostgreSQL pgaudit）
-- 记录所有 DDL 和敏感 DML
SET GLOBAL log_audit = ON;

-- 查询审计日志
SELECT * FROM mysql.audit_log
WHERE command_class = 'delete' AND sql_text LIKE '%users%';
```

```java
// 数据脱敏（日志中隐藏敏感信息）
public class LogMasker {
    public static String maskPhone(String phone) {
        return phone.replaceAll("(\\d{3})\\d{4}(\\d{4})", "$1****$2");
        // 138****8000
    }

    public static String maskEmail(String email) {
        return email.replaceAll("(.{2}).*(@.*)", "$1***$2");
        // al***@example.com
    }
}
```

## 核心要点回顾

- 权限最小化：应用账号只给 CRUD，不给 DDL
- 静态加密 TDE + 列级加密 AES，密钥放 KMS
- SQL 注入四层防御：预编译 → 输入校验 → 最小权限 → WAF
- 二次注入：从 DB 取出的数据再次用于 SQL 仍需参数化
- 数据脱敏：日志/测试环境绝不暴露真实 PII
