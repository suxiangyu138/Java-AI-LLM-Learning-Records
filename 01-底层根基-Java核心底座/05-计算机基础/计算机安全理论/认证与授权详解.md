# 认证与授权详解

> 认证（Authentication）是"你是谁"，授权（Authorization）是"你能做什么"。二者是后端安全的两大核心支柱，每行代码都在回答这两个问题。

## 一、认证机制

### 1.1 主流认证方式对比

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **Session-Cookie** | 服务端存 Session，客户端传 Cookie（Session ID） | 服务端可控（可强制下线） | 分布式需共享 Session、CORS 不友好 |
| **JWT** | 服务端签发 Token，客户端存 Token，每次请求携带 | 无状态、跨域友好、适合微服务 | 无法强制失效、Payload 可读 |
| **HTTP Basic** | `Authorization: Basic base64(user:pass)` | 极简 | 明文（需 HTTPS）、无过期 |
| **API Key** | 分配固定密钥，客户端携带 | 简单 | 不够灵活、泄露后难撤销 |
| **OAuth 2.0** | 第三方授权代理 | 标准、安全、灵活 | 复杂 |
| **mTLS** | 双向 TLS 证书认证 | 企业级安全 | 证书管理成本高 |

### 1.2 Session vs JWT

| 对比 | Session-Cookie | JWT |
|------|---------------|-----|
| 存储位置 | 服务端存储 | 客户端存储 |
| 状态 | 有状态 | 无状态 |
| 水平扩展 | 需共享 Session（Redis） | 天然支持 |
| 强制下线 | ✅ 删除 Session | ❌ 只能等过期或加黑名单 |
| 跨域 | Cookie 受同源限制 | Header 跨域自由 |
| 大小 | 仅 Session ID（小） | Token 较大（可压缩） |
| 适用场景 | 单体应用、后台管理 | 微服务、移动端、API |

### 1.3 JWT 结构

```
eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiIxMjMifQ.xxx-signature-xxx
├─ Header（算法类型）  ├─ Payload（载荷）  ├─ Signature（签名）

Header（Base64）:
{
  "alg": "RS256",
  "typ": "JWT"
}

Payload（Base64，⚠ 可读！不要放敏感信息）:
{
  "sub": "123",          // 用户 ID
  "iat": 1680000000,     // 签发时间
  "exp": 1680014400,     // 过期时间（4h后）
  "roles": ["USER"]
}
```

### 1.4 JWT 生产最佳实践

- **Access Token**：15 分钟 ~ 2 小时，放在内存（不存 localStorage）
- **Refresh Token**：7~30 天，HttpOnly Secure Cookie
- **签名算法**：RS256（非对称）优于 HS256
- **黑名单**：Redis 存失效的 jti（Token ID）
- **轮换 Refresh Token**：每次刷新换新的 Refresh Token（防重放）

## 二、授权模型

### 2.1 常见模型

| 模型 | 全称 | 核心思想 | 适用场景 |
|------|------|---------|---------|
| **ACL** | Access Control List | 为每个资源列出可访问的用户 | 简单文件权限 |
| **RBAC** | Role-Based Access Control | 用户→角色→权限 | 企业应用（最通用） |
| **ABAC** | Attribute-Based Access Control | 基于属性（用户/资源/环境/操作）动态判断 | 复杂权限场景 |
| **PBAC** | Policy-Based Access Control | 策略引擎评估访问规则 | 云平台 IAM |

### 2.2 RBAC 三张表

```
users               roles              permissions
┌────┬──────┐      ┌────┬─────┐      ┌────┬──────────────┐
│ id │ name │      │ id │ name│      │ id │ code         │
├────┼──────┤      ├────┼─────┤      ├────┼──────────────┤
│ 1  │ 张三  │      │ 1  │ admin│     │ 1  │ user:read    │
└────┴──────┘      │ 2  │ user │      │ 2  │ user:write   │
                   └────┴─────┘      │ 3  │ order:read   │
                                     └────┴──────────────┘

user_roles          role_permissions
┌─────────┬─────────┐  ┌─────────┬──────────────┐
│ user_id │ role_id │  │ role_id │ permission_id│
├─────────┼─────────┤  ├─────────┼──────────────┤
│    1    │    1    │  │    1    │      1       │
└─────────┴─────────┘  │    1    │      2       │
                       │    1    │      3       │
                       │    2    │      1       │
                       │    2    │      3       │
                       └─────────┴──────────────┘
```

### 2.3 RBAC vs ABAC

```
RBAC：if (user.hasRole("admin")) → 能有所有权限
ABAC：if (user.dept == doc.dept AND doc.security == "internal" AND time.hour in 9..18)
```

RBAC 适合权限边界清晰的场景（如后台管理系统90%的场景），ABAC 适合细粒度动态权限（如文档协作系统的行级权限）。

## 三、OAuth 2.0 与 OpenID Connect

### 3.1 OAuth 2.0 四种授权模式

| 模式 | 适用场景 | 流程复杂度 |
|------|---------|-----------|
| **授权码模式（Authorization Code）** | 有后端的 Web 应用（最安全） | ⭐⭐⭐ |
| **简化模式（Implicit）** | 纯前端 SPA（已不推荐，改用 PKCE） | ⭐ |
| **密码模式（Password）** | 第一方应用（已废弃） | ⭐⭐ |
| **客户端凭证（Client Credentials）** | 服务间调用 | ⭐ |

### 3.2 授权码模式 + PKCE（当前推荐）

```
1. 用户点击 "使用微信登录"
   → 重定向到微信授权页

2. 用户授权
   → 微信返回 code 到回调地址

3. 后端用 code + code_verifier → 换 access_token
   POST /oauth/token
   { code, code_verifier, client_id, redirect_uri }

4. 微信返回 access_token + refresh_token + id_token

5. 后端用 access_token → 请求用户信息
   GET /userinfo
   Authorization: Bearer {access_token}

6. 后端创建本地用户 → 签发自己的 JWT/Session
```

### 3.3 OAuth 2.0 中的 Token 类型

| Token | 用途 | 受众 | 生命周期 |
|-------|------|------|---------|
| **Access Token** | 访问资源 | 资源服务器 | 短期（小时） |
| **Refresh Token** | 刷新 Access Token | 授权服务器 | 长期（天/周） |
| **ID Token**（OIDC） | 携带用户身份信息 | 客户端 | 短期 |
| **Authorization Code** | 换 Token 的凭证 | 授权服务器 | 极短（分钟） |

### 3.4 OpenID Connect（OIDC）

> OIDC = OAuth 2.0 + 身份认证层。OAuth 解决"授权"，OIDC 解决"认证"。

```
OAuth 2.0：给你 access_token → 你能代表用户访问资源
OIDC：    给你 id_token（JWT）→ 告诉你这个用户是谁
```

OIDC 新增字段（id_token 中）：
- `sub`：用户唯一标识
- `iss`：签发者
- `aud`：受众（client_id）
- `email`、`name`、`picture` 等标准 claims

## 四、SSO 单点登录

> 一次登录，多系统通行。

### 4.1 核心机制

```
┌──────────────┐
│   SSO 服务器   │ ← 统一认证中心
└──────┬───────┘
       │ 共享登录态（全局 Session / Token）
  ┌────┼────┐
  ▼    ▼    ▼
系统A  系统B  系统C

流程：
1. 用户访问系统A → 未登录 → 重定向到 SSO
2. SSO 验证 → 签发 Ticket → 重定向回系统A + ticket
3. 系统A 用 ticket → SSO 验证 → 创建本地会话
4. 用户访问系统B → 未登录 → 重定向到 SSO
5. SSO 已登录 → 直接签 Ticket → 系统B 免登录
```

### 4.2 主流 SSO 协议

| 协议 | 类型 | 现状 |
|------|------|------|
| **CAS** | 经典 SSO 协议 | 高校/传统企业 |
| **SAML 2.0** | XML 企业联邦 | 企业 SaaS（Salesforce、Office 365） |
| **OIDC** | OAuth 2.0 + JWT | 现代 Web/移动端（现代首选） |

## 五、Spring Security 核心

### 5.1 过滤器链

```
请求 → SecurityContextPersistenceFilter → UsernamePasswordAuthenticationFilter
    → BasicAuthenticationFilter → ... → FilterSecurityInterceptor → Controller

核心过滤器：
- SecurityContextPersistenceFilter：请求开始加载 SecurityContext，结束存储
- UsernamePasswordAuthenticationFilter：处理表单登录
- BasicAuthenticationFilter：处理 HTTP Basic 认证
- FilterSecurityInterceptor：授权决策（AccessDecisionManager）
```

### 5.2 认证流程

```
1. Filter 拦截请求 → 提取认证信息（用户名密码/Token/Cookie）
2. 创建 Authentication 对象（未认证状态）
3. AuthenticationManager → AuthenticationProvider
     ↓
4. UserDetailsService.loadUserByUsername()
     ↓
5. 密码校验（PasswordEncoder.matches()）
     ↓
6. 成功 → Authentication 标记为已认证 → 存入 SecurityContext
7. 失败 → 抛出 AuthenticationException
```

### 5.3 授权流程

```java
// 方法级安全
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) { ... }

@PreAuthorize("hasPermission(#order, 'WRITE')")
public void updateOrder(Order order) { ... }

// 基于表达式的权限
@PreAuthorize("@orderService.isOwner(#id) or hasRole('ADMIN')")
public Order getOrder(Long id) { ... }
```

## 六、面试高频问题

**Q1：Session 和 JWT 的区别？各自适用场景？**
> Session：有状态，服务端存储，适合单体/后台管理（需强制下线）。JWT：无状态，客户端存储，适合微服务/API/移动端（天然分布式扩展）。现代常用：JWT（Access Token 短）+ Redis 黑名单（实现强制下线）。

**Q2：OAuth 2.0 的授权码模式为什么安全？**
> Access Token 从不经过浏览器，只出现在后端通信中。浏览器只见到一次性的 code，即使泄露也无法使用（需要 client_secret）。PKCE 进一步加强，防止拦截 code。

**Q3：怎么设计 RBAC 权限系统？**
> 用户表 → 角色表 → 权限表（资源:操作），中间表关联。常用五表：users、roles、permissions、user_roles、role_permissions。需要更灵活时加用户-权限直连和权限分组。

**Q4：Spring Security 怎么实现"一个接口多种角色可访问"？**
> `@PreAuthorize("hasAnyRole('ADMIN', 'MANAGER')")` 或自定义 `hasPermission()` 表达式，或实现自定义 `PermissionEvaluator`。

## 📖 核心要点速记

1. **认证 vs 授权**：认证 = 你是谁，授权 = 你能做什么
2. **Session**：有状态/可控/JWT：无状态/灵活 → 非二选一，常组合用
3. **OAuth 2.0**：授权码 + PKCE（Web）/ 客户端凭证（服务间）
4. **RBAC**：用户→角色→权限，三表核心，企业应用90%够用
5. **SSO**：CAS（传统）/ OIDC（现代）/ SAML（企业）
6. **Spring Security**：过滤器链 + AuthenticationManager + AccessDecisionManager
