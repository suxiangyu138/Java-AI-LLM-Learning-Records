## 1. 认证机制对比

> 认证（Authentication）是"你是谁"，授权（Authorization）是"你能做什么"。

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **Session-Cookie** | 服务端存 Session，客户端传 Cookie（Session ID） | 服务端可控（可强制下线） | 分布式需共享 Session、CORS 不友好 |
| **JWT** | 服务端签发 Token，客户端存储携带 | 无状态、跨域友好、适合微服务 | 无法强制失效、Payload 可读 |
| **HTTP Basic** | `Authorization: Basic base64(user:pass)` | 极简 | 明文（需 HTTPS）、无过期机制 |
| **API Key** | 分配固定密钥，客户端携带 | 简单 | 不够灵活、泄露后难撤销 |
| **OAuth 2.0** | 第三方授权代理 | 标准、安全、灵活 | 复杂 |
| **mTLS** | 双向 TLS 证书认证 | 企业级安全 | 证书管理成本高 |

## 2. Session vs JWT

| 对比 | Session-Cookie | JWT |
|------|---------------|-----|
| 存储位置 | 服务端存储 | 客户端存储 |
| 状态 | 有状态 | 无状态 |
| 水平扩展 | 需共享 Session（Redis） | 天然支持 |
| 强制下线 | 删除 Session | 只能等过期或加黑名单 |
| 跨域 | Cookie 受同源限制 | Header 跨域自由 |
| 大小 | 仅 Session ID（小） | Token 较大（可压缩） |
| 适用场景 | 单体应用、后台管理 | 微服务、移动端、API |

> 现代常用组合：JWT（Access Token 短）+ Redis 黑名单（实现强制下线能力）。

## 3. JWT 结构与最佳实践

### 3.1 JWT 结构

```
eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiIxMjMifQ.xxx-signature-xxx
+------------------+---------------------+--------------------+
| Header（算法类型）| Payload（载荷）     | Signature（签名）  |
+------------------+---------------------+--------------------+

Header（Base64 解码）:
{
  "alg": "RS256",
  "typ": "JWT"
}

Payload（Base64 解码，可读！不要放敏感信息）:
{
  "sub": "123",          // 用户 ID
  "iat": 1680000000,     // 签发时间
  "exp": 1680014400,     // 过期时间
  "roles": ["USER"]
}
```

### 3.2 生产最佳实践

- **Access Token**：15 分钟 ~ 2 小时，放在内存（不存 localStorage）
- **Refresh Token**：7~30 天，HttpOnly Secure Cookie
- **签名算法**：RS256（非对称）优于 HS256（对称，密钥泄露可伪造）
- **黑名单**：Redis 存失效的 jti（Token ID）
- **轮换 Refresh Token**：每次刷新换新的 Refresh Token（防重放）

## 4. 授权模型

| 模型 | 全称 | 核心思想 | 适用场景 |
|------|------|---------|---------|
| **ACL** | Access Control List | 为每个资源列出可访问的用户 | 简单文件权限 |
| **RBAC** | Role-Based Access Control | 用户 -> 角色 -> 权限 | 企业应用（最通用） |
| **ABAC** | Attribute-Based Access Control | 基于属性（用户/资源/环境/操作）动态判断 | 复杂权限场景 |
| **PBAC** | Policy-Based Access Control | 策略引擎评估访问规则 | 云平台 IAM |

## 5. RBAC 设计与实现

### 5.1 五表设计

```
users                roles               permissions
+----+------+       +----+------+       +----+--------------+
| id | name |       | id | name |       | id | code          |
+----+------+       +----+------+       +----+--------------+
| 1  | 张三 |       | 1  | admin|       | 1  | user:read     |
+----+------+       | 2  | user |       | 2  | user:write    |
                    +----+------+       | 3  | order:read    |
                                        +----+--------------+

user_roles              role_permissions
+---------+---------+   +---------+--------------+
| user_id | role_id |   | role_id | permission_id|
+---------+---------+   +---------+--------------+
|    1    |    1    |   |    1    |      1       |
+---------+---------+   |    1    |      2       |
                        |    1    |      3       |
                        |    2    |      1       |
                        |    2    |      3       |
                        +---------+--------------+
```

### 5.2 核心 SQL 设计

```sql
-- 五张表结构
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE roles (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE permissions (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    code VARCHAR(100) UNIQUE NOT NULL  -- 如 "user:read", "order:write"
);

CREATE TABLE user_roles (
    user_id BIGINT NOT NULL,
    role_id BIGINT NOT NULL,
    PRIMARY KEY (user_id, role_id)
);

CREATE TABLE role_permissions (
    role_id BIGINT NOT NULL,
    permission_id BIGINT NOT NULL,
    PRIMARY KEY (role_id, permission_id)
);
```

> 根据业务复杂度，可添加用户-权限直连或权限分组来提升灵活性。

## 6. RBAC vs ABAC

```
RBAC：if (user.hasRole("admin")) -> 拥有所有权限
ABAC：if (user.dept == doc.dept AND doc.security == "internal" AND time.hour in 9..18)
```

| 对比 | RBAC | ABAC |
|------|------|------|
| 抽象层次 | 角色（粗粒度） | 属性（细粒度） |
| 配置复杂度 | 低 | 高 |
| 维护成本 | 低 | 高（策略可能相互冲突） |
| 适用场景 | 权限边界清晰的后台管理系统 | 文档协作等行级/列级动态权限 |

> RBAC 覆盖企业应用 90% 的场景。需要更细粒度时，可引入 ABAC 作为补充。

## 7. OAuth 2.0

### 7.1 四种授权模式

| 模式 | 适用场景 | 流程复杂度 |
|------|---------|-----------|
| **授权码模式（Authorization Code）** | 有后端的 Web 应用（最安全） | 高 |
| **简化模式（Implicit）** | 纯前端 SPA（已不推荐，改用 PKCE） | 低 |
| **密码模式（Password）** | 第一方应用（已废弃） | 中 |
| **客户端凭证（Client Credentials）** | 服务间调用 | 低 |

### 7.2 授权码模式 + PKCE（当前推荐）

```
1. 用户点击"使用微信登录"
   -> 重定向到微信授权页

2. 用户授权
   -> 微信返回 code 到回调地址

3. 后端用 code + code_verifier -> 换 access_token
   POST /oauth/token
   { code, code_verifier, client_id, redirect_uri }

4. 微信返回 access_token + refresh_token + id_token

5. 后端用 access_token -> 请求用户信息
   GET /userinfo
   Authorization: Bearer {access_token}

6. 后端创建本地用户 -> 签发自己的 JWT/Session
```

## 8. OAuth 2.0 Token 类型

| Token | 用途 | 受众 | 生命周期 |
|-------|------|------|---------|
| **Access Token** | 访问资源 | 资源服务器 | 短期（小时级） |
| **Refresh Token** | 刷新 Access Token | 授权服务器 | 长期（天/周级） |
| **ID Token（OIDC）** | 携带用户身份信息 | 客户端 | 短期 |
| **Authorization Code** | 换 Token 的凭证 | 授权服务器 | 极短（分钟级） |

## 9. OpenID Connect

> OIDC = OAuth 2.0 + 身份认证层。OAuth 解决"授权"，OIDC 解决"认证"。

```
OAuth 2.0：给你 access_token -> 你能代表用户访问资源
OIDC：     给你 id_token（JWT）-> 告诉你这个用户是谁
```

OIDC 在 id_token 中新增的标准 claims：
- `sub`：用户唯一标识
- `iss`：签发者
- `aud`：受众（client_id）
- `email`、`name`、`picture` 等标准用户信息

## 10. SSO 单点登录

> 一次登录，多系统通行。

### 10.1 核心机制

```
+------------------+
|   SSO 服务器     |  <- 统一认证中心
+--------+---------+
         | 共享登录态（全局 Session / Token）
    +----+----+
    |    |    |
    v    v    v
   系统A  系统B  系统C

流程：
1. 用户访问系统A -> 未登录 -> 重定向到 SSO
2. SSO 验证 -> 签发 Ticket -> 重定向回系统A + ticket
3. 系统A 用 ticket -> SSO 验证 -> 创建本地会话
4. 用户访问系统B -> 未登录 -> 重定向到 SSO
5. SSO 已登录 -> 直接签 Ticket -> 系统B 免登录
```

### 10.2 主流 SSO 协议

| 协议 | 类型 | 现状 |
|------|------|------|
| **CAS** | 经典 SSO 协议 | 高校/传统企业 |
| **SAML 2.0** | XML 企业联邦 | 企业 SaaS（Salesforce、Office 365） |
| **OIDC** | OAuth 2.0 + JWT | 现代 Web/移动端（首选） |

## 11. Spring Security 核心

### 11.1 过滤器链

```
请求 -> SecurityContextPersistenceFilter -> UsernamePasswordAuthenticationFilter
    -> BasicAuthenticationFilter -> ... -> FilterSecurityInterceptor -> Controller

核心过滤器：
- SecurityContextPersistenceFilter：请求开始加载 SecurityContext，结束存储
- UsernamePasswordAuthenticationFilter：处理表单登录
- BasicAuthenticationFilter：处理 HTTP Basic 认证
- FilterSecurityInterceptor：授权决策（AccessDecisionManager）
```

### 11.2 认证流程

```
1. Filter 拦截请求 -> 提取认证信息（用户名密码/Token/Cookie）
2. 创建 Authentication 对象（未认证状态）
3. AuthenticationManager -> AuthenticationProvider
     |
4. UserDetailsService.loadUserByUsername()
     |
5. 密码校验（PasswordEncoder.matches()）
     |
6. 成功 -> Authentication 标记为已认证 -> 存入 SecurityContext
   失败 -> 抛出 AuthenticationException
```

### 11.3 配置示例

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            // 前后端分离场景通常关闭 CSRF
            .csrf(AbstractHttpConfigurer::disable)
            // 会话管理设置为无状态（适配 JWT）
            .sessionManagement(session ->
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            // 接口权限控制
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .requestMatchers("/api/user/**").hasRole("USER")
                .anyRequest().authenticated()
            )
            // 添加 JWT 认证过滤器
            .addFilterBefore(
                new JwtAuthenticationTokenFilter(),
                UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}
```

### 11.4 方法级安全

```java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) { ... }

@PreAuthorize("hasPermission(#order, 'WRITE')")
public void updateOrder(Order order) { ... }

@PreAuthorize("@orderService.isOwner(#id) or hasRole('ADMIN')")
public Order getOrder(Long id) { ... }
```

## 12. Java 安全编码实践

### 12.1 输入校验（JSR-380）

```java
public class CreateUserRequest {

    @NotBlank @Size(min=3, max=20)
    @Pattern(regexp = "^[a-zA-Z0-9_]+$")  // 白名单
    private String username;

    @NotBlank @Size(min=8, max=128)
    private String password;

    @Email @Size(max=100)
    private String email;

    @Min(0) @Max(150)
    private Integer age;

    @Pattern(regexp = "^1[3-9]\\d{9}$")
    private String phone;
}
```

### 12.2 输出最小化

```java
// 使用 DTO 避免返回敏感字段
@GetMapping("/user/{id}")
public UserDTO getUser(@PathVariable Long id) {
    User user = userMapper.selectById(id);
    return UserDTO.builder()
        .id(user.getId())
        .username(user.getUsername())
        .avatar(user.getAvatar())
        .build();  // 不返回 password, idCard 等
}
```

### 12.3 错误处理

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handle(Exception e) {
        String traceId = UUID.randomUUID().toString();
        log.error("Internal error, traceId: {}", traceId, e);
        return ResponseEntity.status(500)
            .body(new ErrorResponse("INTERNAL_ERROR",
                "服务内部错误，请稍后重试", traceId));
    }
}
```

### 12.4 安全编码规范清单

- 禁止硬编码敏感信息（密钥、密码、数据库地址），统一存储在配置中心
- 避免使用 `System.out.println()`，统一使用日志框架，禁止打印敏感信息
- 接口参数必须进行校验（JSR-380 注解：`@NotNull`、`@NotBlank`、`@Pattern`）
- 禁止使用过期/不安全的 API（如 Vector、Hashtable；MD5、DES）
- 异常处理统一，避免抛出详细堆栈给前端，仅返回通用错误提示

## 13. 安全开发生命周期 SDL

| 阶段 | 安全实践 |
|------|----------|
| **需求设计** | 识别安全需求，进行威胁建模（如 STRIDE 模型） |
| **编码阶段** | 遵循安全编码规范，使用安全框架，Code Review |
| **测试阶段** | 安全测试：SAST（静态扫描）+ DAST（动态渗透测试）+ 漏洞扫描 |
| **部署阶段** | 安全配置服务器、中间件、数据库；最小权限原则 |
| **运维阶段** | 持续监控安全事件，及时修复漏洞，定期安全审计 |

### 安全工具

| 工具类型 | 工具 | 作用 |
|----------|------|------|
| **静态代码扫描** | SonarQube、FindBugs | 编码阶段扫描安全漏洞（SQL 注入、XSS、硬编码密钥） |
| **漏洞扫描** | OWASP ZAP、Nessus | 部署后扫描应用漏洞 |
| **依赖检查** | OWASP Dependency-Check | 扫描第三方依赖已知漏洞 |
| **日志审计** | ELK、Graylog | 监控关键操作日志，发现异常行为 |

## 核心要点速记

1. **认证 vs 授权**：认证 = 你是谁，授权 = 你能做什么
2. **Session**：有状态/可控；**JWT**：无状态/灵活 -> 常组合使用
3. **RBAC 五表**：users -> roles -> permissions + 两张中间表
4. **OAuth 2.0**：授权码 + PKCE（Web）/ 客户端凭证（服务间）
5. **OIDC** = OAuth 2.0 + 身份层，id_token 用 JWT 格式
6. **SSO**：CAS（传统）/ OIDC（现代）/ SAML（企业）
7. **Spring Security**：过滤器链 + AuthenticationManager + @PreAuthorize
8. **安全编码**：输入校验 + 输出最小化 + 错误脱敏 + 日志脱敏
9. **SDL**：需求 -> 编码 -> 测试 -> 部署 -> 运维，全流程覆盖
