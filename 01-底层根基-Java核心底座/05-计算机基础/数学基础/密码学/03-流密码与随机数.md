## 1. 流密码原理

### 1.1 定义

**流密码**：用密钥生成伪随机密钥流，与明文逐位/逐字节异或。

```text
加密：C = P ⊕ keystream
解密：P = C ⊕ keystream（异或自反）

与 OTP 的对照（01 模块）：
  OTP 用真随机密钥且只用一次——完美但不可用
  流密码用"伪随机"密钥流（密钥+IV 确定生成）——实际可用
  安全性 = 密钥流不可预测（计算安全）
```

### 1.2 分组 vs 流

| 维度 | 分组密码（AES） | 流密码（ChaCha20） |
|------|:---:|:---:|
| 单位 | 128 位分组 | 逐字节/字 |
| 填充 | 需要（CTR 模式除外） | 不需要 |
| 硬件加速 | AES-NI 极快 | 软件快、硬件简单 |
| 错误传播 | 模式相关 | 无（逐位独立） |
| 典型场景 | 服务器、存储 | 移动端、嵌入式、TLS |

## 2. ChaCha20

### 2.1 构造（Bernstein 设计）

```text
ChaCha20：基于 ARX（加-旋转-异或）的流密码
  核心：20 轮（10 轮双回合）对 4×4 状态矩阵运算
  输入：256 位密钥 + 96 位 nonce + 计数器
  输出：512 位密钥流块/次（可并行生成）

ARX 优势：
  无 S 盒（省查表 → 常数时间实现简单 → 抗时序侧信道）
  软件实现极快（无 AES-NI 的平台上完胜 AES）

ChaCha20-Poly1305：AEAD 组合（02 模块的流密码版）
  TLS 1.3 的两个默认套件之一
```

### 2.2 为什么 ChaCha20 流行（2025 现实）

```text
① 移动端：无 AES 硬件加速时软件速度优势明显
② 常数时间友好：ARX 结构天然抗时序侧信道
③ 简单可审计：实现约 100 行 C，审计成本低
④ 标准地位：TLS 1.3 / SSH / WireGuard 全部支持

对照：AES 靠硬件指令称王（服务器），ChaCha 靠软件效率（移动端）
  —— 两者并存是现代 TLS 的常态
```

### 2.3 其他流密码的状态

| 算法 | 状态 |
|------|------|
| RC4 | ❌ 已破（偏差攻击，WPA 的教训） |
| Salsa20 | 被 ChaCha 取代（同作者） |
| AES-CTR | 分组密码当流密码（GCM 内部） |
| ChaCha20 | ✅ 现代标准 |

## 3. 随机数的三类层级

### 3.1 TRNG / PRNG / CSPRNG

| 类型 | 全称 | 来源 | 特性 | 用途 |
|------|------|------|------|------|
| TRNG | 真随机数生成器 | 物理熵源（热噪声/时钟抖动） | 不可预测、慢 | 种子来源 |
| PRNG | 伪随机数生成器 | 确定性算法（如线性同余） | 可预测！ | 仿真/游戏（非密码） |
| CSPRNG | 密码学安全伪随机 | 密码学算法（如 ChaCha/哈希） | 不可预测 | 密钥/IV/随机数 |

```text
关键区分：
  PRNG（Random）可被预测 —— 用于统计/游戏没问题
  CSPRNG（SecureRandom）不可预测 —— 密码学唯一选择

数学定义（CSPRNG）：给定前 n 个输出，预测第 n+1 个不可行
  （下一位不可预测性 = 密码随机性的标准）
```

### 3.2 熵与种子

```text
熵源（Linux /dev/urandom、Windows BCryptGenRandom）：
  收集系统噪声（中断时序、硬件随机指令 RDRAND）

播种链：
  物理熵 → 种子（256 位）→ CSPRNG 状态 → 输出流
  种子质量决定一切：种子弱 → 输出可预测

工程现实（2025）：
  现代 OS 的 CSPRNG 出厂即播种（硬件 RNG + 启动熵）
  应用层几乎不需要自己播种（用 OS 接口即可）
  Java SecureRandom 默认使用 OS 熵源
```

> 🎯 核心认知：**随机性的价值 = 熵的不可预测性**。密码学随机数不是"够乱"而是"不可预测"——这与 `信息论/01` 的熵定义直接对应：可预测序列熵低，无论它看起来多"乱"。

## 4. 熵与播种

### 4.1 种子熵的量化

```text
种子需要多少熵？与算法安全强度匹配：
  AES-256 密钥需要 256 位熵
  生日攻击对 IV：96 位 IV 在 2⁴⁸ 次使用后碰撞概率过半
  → IV 用 CSPRNG 随机生成（每加密一次）

熵的浪费与枯竭：
  嵌入式设备熵源贫乏（无硬件 RNG 时）
  → 用"多次采样 + 哈希"累积熵（熵累积器）
  → 或硬件 TRNG 芯片（现代手机/服务器标配）
```

### 4.2 Linux 的 /dev/urandom 与 getrandom

```text
现代推荐：getrandom() 系统调用（无文件句柄、永不阻塞）
  /dev/urandom 自 Linux 4.8 起与 getrandom 等价（充分播种后）

Java 的对应：
  SecureRandom.getInstanceStrong() —— 阻塞式（适合密钥生成）
  默认 SecureRandom —— 非阻塞（适合一般用途）
  注意：Tomcat/Spring 默认随机源可配置（启动慢可能与熵有关）
```

## 5. 密码学随机数在 Java 中

### 5.1 SecureRandom 的正确用法

```java
// 正确：SecureRandom（CSPRNG）
SecureRandom sr = new SecureRandom();
byte[] iv = new byte[12];
sr.nextBytes(iv);                  // GCM 的 96 位 IV
byte[] key = new byte[32];
sr.nextBytes(key);                 // AES-256 密钥

// 错误：java.util.Random —— 可预测（线性同余），禁止用于密码
Random r = new Random();           // 时间种子 → 可暴力搜索
byte[] badKey = new byte[32];
r.nextBytes(badKey);               // ❌ 密钥可被预测
```

### 5.2 常见随机性错误

| 错误 | 后果 |
|------|------|
| 用 Random 生成密钥/IV | 密钥可预测 → 全部加密失效 |
| 用时间戳做种子 | 可暴力枚举种子 |
| 手写"随机"算法 | 数学上可预测 |
| 复用 IV/随机数 | 碰撞攻击（GCM 灾难） |
| 忽略 SecureRandom 阻塞 | 熵不足时启动卡顿（少数平台） |

## 6. 随机数失败案例

### 6.1 历史事故

| 事件 | 根因 | 教训 |
|------|------|------|
| 2012 Sony PS3 签名 | ECDSA 随机数 k 复用 | 随机数复用 = 私钥泄露 |
| 2013 Android 密钥漏洞 | Java Random 弱种子 | 必须用 CSPRNG |
| 2019 韩国加密货币 | 弱随机密钥生成 | 熵不足的代价是资金 |
| 2023 多次 ECDSA 复用 | 熵源故障（IoT 设备） | 审计随机数质量 |

### 6.2 随机数的工程清单

```text
① 密钥/IV/盐：一律 CSPRNG（Java SecureRandom / OS 接口）
② 种子：交给 OS（内核已做好熵收集）
③ 检测：签名前验证随机数唯一性（k 复用检测）
④ 审计：生产环境监控"熵耗尽"告警
⑤ 备选：确定性签名（EdDSA 天然无 k 复用问题）优先于 ECDSA
```

> 🎯 **核心要点**：随机数是密码学的"地基中的地基"——密钥、IV、盐、签名随机数全部依赖不可预测性。一次随机数失败（复用/弱种子）就能击穿整个加密体系（PS3 事故是经典证明）。**工程铁律：密码场景永远 SecureRandom，永远不自己"造随机数"。**
