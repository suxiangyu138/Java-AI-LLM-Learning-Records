## 1. 为什么必须现在迁移

### 1.1 量子威胁的两条路径

```text
路径 1：Shor 算法（分解/DLP）——破 RSA/ECC/DH
  需要容错量子计算机（当前约 10³ 逻辑比特 vs 所需 10⁶+）

路径 2：Harvest-now-decrypt-later（HNDL）——现在就偷
  攻击者记录今天的加密流量 → 量子时代解密
  → 长生命周期数据（健康/政府/商业机密）已在风险中

2026 威胁评估（Mosca/Piani 报告）：
  10 年内出现"密码学相关量子计算机"（CRQC）概率 28-49%
  Google/Cloudflare 已把 Q-Day 预估提前到 2029
```

### 1.2 迁移为什么不能等

```text
密码迁移的特性：**启动慢、完成慢**
  从标准定稿到全栈落地：5-10 年（算法→库→协议→信任库→设备）
  2035 年全面退役经典算法的窗口已开启（NIST IR 8547）
  → 2026 年不开始，2030 年就来不及

对称侧的安慰：AES-256 只受 Grover 减半影响（128 位安全仍达标）
  → 迁移重点全在非对称：KEM（密钥交换）与签名
```

## 2. NIST 后量子标准

### 2.1 标准家族（2024-2026）

| 标准 | 算法 | 用途 | 状态 |
|------|------|------|------|
| FIPS 203 | **ML-KEM**（Kyber） | 密钥封装（替代 ECDH/RSA-KEM） | 2024-08 定稿 |
| FIPS 204 | **ML-DSA**（Dilithium） | 数字签名（替代 ECDSA/RSA） | 2024-08 定稿 |
| FIPS 205 | SLH-DSA（SPHINCS+） | 签名（哈希基，备用） | 2024-08 定稿 |
| FIPS 206 | FN-DSA（Falcon） | 签名（NTRU 格） | 2025 草案，2026 定稿中 |
| — | HQC | KEM（码基，备用） | 2025-03 选定，草案 2026 |

### 2.2 ML-KEM 与 ML-DSA 的关键参数

| 参数集 | 安全级别 | 公钥/密文大小 | 场景 |
|--------|:---:|:---:|------|
| ML-KEM-512 | 128 级 | 800B / 768B | 轻量 |
| **ML-KEM-768** | 192 级 | 1184B / 1088B | **TLS 混合默认** |
| ML-KEM-1024 | 256 级 | 1568B / 1568B | 高安全 |
| **ML-DSA-65** | 128 级 | 1952B / 3309B | 证书首选 |
| ML-DSA-87 | 256 级 | 2592B / 4627B | 高安全（证书 5.5KB） |

```text
直观对比：X25519 公钥 32B vs ML-KEM-768 公钥 1184B（37 倍）
  → 尺寸是后量子密码的主要工程代价（见阻点 1）
```

## 3. 混合 TLS：会话层的量子化

### 3.1 混合方案（RFC 9794，2024-12）

```text
X25519MLKEM768：经典 + 量子双轨密钥交换
  客户端发送：X25519 公钥（32B）+ ML-KEM-768 公钥（1184B）= 1216B
  服务器返回：X25519 公钥 + ML-KEM 密文（1120B）
  会话密钥 = HKDF(经典共享密钥 ‖ 量子共享密钥)

混合的智慧：
  ① 双保险：任何一侧被破，另一侧仍安全
  ② 兼容：经典系统可回退（协商失败走纯 X25519）
  ③ 渐进：无需一次性迁移全部基础设施
```

### 3.2 浏览器与生态的落地

| 组件 | 状态（2026 初） |
|------|----------------|
| Chrome | X25519MLKEM768 默认（v124 起），30%+ 全球 TLS 1.3 握手 |
| Firefox | v132 支持；v135 起 HTTP/3 用 ML-KEM |
| Cloudflare | 60%+ 人工 TLS 流量混合保护（2026-04 达 65%+） |
| 延迟开销 | 中位 +1.5ms、尾部 +7ms（可接受） |
| 兼容问题 | 0.34% 源站拒绝大 ClientHello（HRR 回退） |

```text
关键事实：会话密钥的量子化已在大规模发生
  —— 浏览器强制推动，服务器无需改动代码（标准机制）
```

## 4. 迁移的落地实况（2025-2026）

### 4.1 库与平台支持

| 层 | 状态 |
|----|------|
| OpenSSL 3.5（2025-04 LTS） | 首个原生 ML-KEM/ML-DSA/SLH-DSA 的主流 TLS 栈 |
| Go 1.24（2025-02） | crypto/mlkem；crypto/tls 默认 X25519MLKEM768 |
| BoringSSL | ML-KEM 进默认群组 |
| Java（BouncyCastle） | ML-KEM 1.78、ML-DSA 1.79（2024-2025） |
| OpenSSH 10.0+ | 默认混合后量子密钥交换 |
| AWS | KMS/ACM/Secrets Manager 混合 PQC TLS（2025-04） |
| Google Cloud | Load Balancer 量子安全 KEX：2026-10 默认启用 |
| Windows 11 24H2 | Authenticode 支持 ML-DSA（代码签名） |

```text
Java 侧现状：
  JDK 内置尚需 provider（BouncyCastle 提供 ML-KEM/ML-DSA）
  JCA 注册：KeyAgreement "ML-KEM"、Signature "ML-DSA"
  → 2026 年 Java 应用启用混合 TLS 主要靠 OpenSSL/BC 集成
```

### 4.2 速度性能

```text
ML-KEM 性能（OpenSSL 3.5 微基准，量级数据）：
  ML-KEM-768 密钥生成+封装+解封装 ≈ 0.10ms
  X25519 ≈ 0.20ms（合计）—— 与经典同级，不是瓶颈
瓶颈在**尺寸**（握手包大 → 网络往返与中间设备处理）
```

## 5. 签名与证书的困境

### 5.1 现状的不对称

```text
会话密钥：✅ 已量子安全（混合 KEM 铺开中）
服务器证书：❌ 仍是 ECDSA P-256 / RSA-2048 签名
  → 证书被记录 → 量子时代可被伪造（HNDL 的证书版本）

2026 状态：
  浏览器默认协商 ML-DSA 证书：未发生（草案 2026-05 仍在 WGLC）
  公开根 CA 签发 ML-DSA 根：0 个（信任库未接纳）
  复合签名（ML-DSA-65 + ECDSA P-256）：草案 2026-03 WGLC，RFC 目标 2026 Q4
```

### 5.2 证书迁移路线

```text
顺序（业界共识）：
  ① 混合 TLS 终结（已发生，浏览器驱动）
  ② 内部 CA 复合签名（2026-2027，组织可控）
  ③ 代码签名（CNSA 2.0 强制，Windows 已支持）
  ④ S/MIME 邮件签名
  ⑤ 公开根 CA（2027-2028+，受信任库节奏约束）

根本约束：根 CA 的 ML-DSA 需要 FIPS 140-3 验证的 HSM
  → CMVP 排队 200+ 项、14-22 个月积压 → 公开根迁移 2027 起
```

## 6. 迁移的五大阻点

| 阻点 | 现状（2026） | 影响 |
|------|-------------|------|
| **FIPS 140-3 验证滞后** | 无模块获 ML-KEM 证书；AWS-LC FIPS 3.0 排队中 | 合规系统无法启用 |
| **证书尺寸** | ML-DSA-87 叶子 5.5KB、SLH-DSA 8.8KB | CT 日志 8-16KB 上限被顶爆 |
| **库版本错配** | 混合栈可能静默降级到经典群 | 无错误提示 → 假安全 |
| **信任库节奏** | 无 ML-DSA 根进浏览器信任库 | 公开证书迁移 2027+ |
| **设备存量** | WEF 估计 200 亿+ 设备需升级/替换 | 长尾拖慢整体 |

```text
工程对策：
  ① 协议级记录协商群（检测是否真混合，不靠猜）
  ② 证书清单 + 尺寸预算规划（CBOM）
  ③ 加密敏捷性设计（算法可插拔，NIST CSWP 39）
  ④ 先内部后公开、先会话后证书的分阶段
```

## 7. 时间线与行动清单

### 7.1 监管时间线

| 时间 | 事件 |
|------|------|
| 2024-08 | NIST FIPS 203/204/205 定稿 |
| 2025-2026 | 混合 TLS 铺开（浏览器/云/库） |
| 2026 | CNSA 2.0：网络设备必须支持并优先；EU 关键基础设施过渡开始 |
| 2027-01 | 美国新采购必须 CNSA 2.0 合规 |
| 2030 | RSA-2048/P-256 弃用（NIST IR 8547）；CNSA 2.0 全强制 |
| 2035 | 经典算法禁用；NIST 体系全面后量子 |

### 7.2 组织行动清单（2026 视角）

```text
立即（2026）：
  ① 启用混合 TLS（依赖 OpenSSL 3.5/Go 1.24/BC 等已支持栈）
  ② 建立密码资产清单（CBOM）：TLS 端点、证书、算法分布
  ③ 检查"静默降级"：日志记录协商的 named_group

短期（2026-2027）：
  ④ 内部 CA 升级复合签名（ML-DSA-65 + ECDSA）
  ⑤ 代码签名启用 ML-DSA（Windows 24H2+）
  ⑥ 密码库升级到支持 PQC 的版本

中期（2027-2030）：
  ⑦ 跟踪公开根 CA 的 ML-DSA 接纳
  ⑧ 敏感数据生命周期审计（HNDL 风险评估）
  ⑨ 算法敏捷性改造（协议层可插拔）

个人开发者视角：
  Java 侧通过 BouncyCastle 已可用 ML-KEM/ML-DSA；
  Spring Boot/Netty 的 TLS 配置关注 OpenSSL 后端版本
```

> 🎯 **核心要点**：2026 年的后量子迁移 = "会话层已量子化，证书层刚开始"。混合 TLS（RFC 9794）是第一个大规模落地的量子安全组件（Chrome 30%+ 握手、Cloudflare 65%+ 流量）；证书与信任库的迁移受 FIPS 验证、CT 尺寸与信任库节奏约束，要到 2027-2030。**工程师现在能做的：启用混合、记录协商、建立清单、关注栈版本。**
