## 1. TLS 1.3 协议解剖

### 1.1 设计目标（vs TLS 1.2）

```text
TLS 1.3（RFC 8446，2018）：
  ① 简化握手：1-RTT（原来 2-RTT）
  ② 移除不安全特性：无 RC4/压缩/重协商（CRIME/BREACH 教训）
  ③ 前向保密强制：握手密钥全部临时生成（ECDHE）
  ④ 密码套件简化：AEAD 必备、静态 RSA 密钥交换删除
  ⑤ 0-RTT：恢复会话免握手（安全权衡）

2026 状态：TLS 1.3 占主流（>90% 的 TLS 流量）
```

### 1.2 握手流程（1-RTT 简化版）

```text
① ClientHello：客户端随机数 + 支持的群（X25519 等）+ key_share
② ServerHello：服务器随机数 + 选群 + key_share（+ 证书）
③ 双方计算 ECDHE 共享密钥 → HKDF 派生会话密钥
④ 加密 Finished 消息互验（密钥确认）
⑤ 应用数据（AES-256-GCM / ChaCha20-Poly1305）

密码套件（2025 主流）：
  TLS_AES_256_GCM_SHA384 / TLS_CHACHA20_POLY1305_SHA256
密钥交换：X25519（经典）+ X25519MLKEM768（混合，08 模块）
证书签名：ECDSA P-256 / RSA-2048（2026 仍是，待迁移）
```

### 1.3 前向保密（Forward Secrecy）

```text
问题：静态密钥长期有效 → 服务器私钥泄露 = 历史流量全部可解
前向保密：每次会话用临时密钥（ECDHE）
  → 私钥泄露只能解当前会话，历史流量安全

工程推论：TLS 1.3 默认前向保密
  （无需配置；这是 1.3 相对 1.2 的最大安全改进）
```

## 2. JWT：认证令牌的密码学

### 2.1 JWT 结构

```text
JWT = Header.Payload.Signature（三段 Base64URL）
  Header：{"alg": "RS256", "typ": "JWT"}
  Payload：claims（sub/exp/iat 等）
  Signature：按 alg 签名

无状态认证：服务器验证签名即可，无需会话存储
  → 微服务/分布式认证的标配
```

### 2.2 签名算法选型（安全重点）

| 算法 | 类型 | 状态 |
|------|------|------|
| HS256 | HMAC（对称，同密钥签名验证） | ⚠️ 密钥共享，仅内部 |
| RS256 | RSA-PSS（非对称） | ✅ 标准（公钥验证） |
| ES256 | ECDSA P-256 | ✅ 可用（注意 k 随机数） |
| EdDSA | Ed25519 | ✅ 现代推荐 |
| **none** | 无签名 | ❌ 禁止（经典攻击） |

```text
JWT 经典攻击：
  ① alg=none 注入：移除签名（须配置拒绝）
  ② HS256 混淆：用 RSA 公钥当 HMAC 密钥（算法混淆攻击）
  ③ 过期未校验、密钥硬编码

防御：白名单算法 + 库的默认安全配置（jjwt 等现代库已防）
```

### 2.3 会话 vs 令牌

| 方案 | 服务端状态 | 吊销 | 适用 |
|------|:---:|:---:|------|
| Session Cookie | 有 | 即时 | 单体应用 |
| JWT（短期） | 无 | 难（需黑名单） | 分布式/API |
| JWT（长期） | 无 | 难 | 移动端刷新模式 |

> 💡 工程结论：JWT 用**短期（15 分钟级）+ 刷新令牌（可吊销）**组合；永久的 JWT 是安全反模式。

## 3. SSH 与 WireGuard

### 3.1 SSH 的密码学

```text
SSH 协议（OpenSSH）：
  密钥交换：X25519（2025 默认已混合 ML-KEM，见 08）
  主机认证：Ed25519（现代默认）/ ECDSA / RSA
  会话加密：ChaCha20-Poly1305 / AES-GCM

2026 现实：OpenSSH 10.0+ 默认混合后量子密钥交换
  → SSH 是"先于 TLS 完成会话层量子化"的协议
```

### 3.2 WireGuard（现代 VPN）

```text
WireGuard 设计（2020s 新标准）：
  每个对端一对密钥（X25519 静态 + 临时）
  加密：ChaCha20-Poly1305
  精简：<4000 行代码（可审计性 = 安全性的工程体现）

对比 OpenVPN/IPsec：配置简单、性能好、攻击面小
  → Linux 内核内置，现代云原生 VPN 首选
```

## 4. 侧信道攻击

### 4.1 侧信道家族

| 类型 | 泄露途径 | 经典案例 |
|------|---------|---------|
| 时序攻击 | 运算时间差异 | RSA 私钥位推断（Kocher 1996） |
| 功耗攻击 | 芯片功耗曲线 | AES 密钥恢复（DPA） |
| 缓存攻击 | 缓存命中差异 | **Spectre/Meltdown 家族** |
| 电磁/声学 | 电磁辐射 | 远程密钥恢复（研究级） |
| 故障注入 | 诱导错误 | RSA-CRT 故障攻击 |

```text
原理：密码运算的"物理足迹"泄露密钥信息
  时序：私钥位 0/1 的运算时间不同
  缓存：密钥索引的访问模式（查表位置）→ 命中/缺失可测
```

### 4.2 防御：常数时间实现

| 手段 | 说明 |
|------|------|
| 常数时间算法 | 运算时间与输入无关（Montgomery 阶梯） |
| 查表消除 | 避免密钥索引查表（S 盒访问模式） |
| 指令级 | 条件分支替换为位掩码运算 |
| 硬件支持 | AES-NI（硬件指令，天然常数时间） |
| 库的选择 | 用维护良好的密码库（OpenSSL/BoringSSL/JDK） |

> ⚠️ 软件层注意（Java）：`String.equals`/`Arrays.equals` 非常数时间——密码比较用 `MessageDigest.isEqual`；避免在安全敏感代码中用分支依赖密钥位。

### 4.3 Spectre/Meltdown 与密码学

```text
2025 状态：Spectre 变体仍在（Arm 公告持续更新，见 缓存与Cache/06）
  对密码库的影响：查询表模式可被缓存侧信道探测
  缓解：常数时间 + 新硬件设计（推测路径不写缓存）

工程结论：永远不要在自研代码里实现加密原语
  —— 常数时间实现的坑远比想象深
```

## 5. 密钥管理

### 5.1 密钥生命周期

```text
生成（CSPRNG/HSM）→ 存储（KMS/HSM）→ 使用（内存）
→ 轮换（定期/事件）→ 吊销（泄露）→ 销毁（彻底）

原则：
  ① 密钥分级：根密钥（离线）→ 数据密钥（在线，信封加密）
  ② 最小权限：进程只持有需要的密钥
  ③ 轮换：数据密钥频繁、根密钥低频
  ④ 分离：加密密钥与签名密钥分开（风险隔离）
```

### 5.2 信封加密（Envelope Encryption）

```text
方案：用数据密钥（DEK）加密数据；用主密钥（KEK）加密 DEK
  存储：密文 + 加密的 DEK（信封）
  收益：主密钥数量少（好管理）；DEK 可频繁轮换

云原生实现：AWS KMS / GCP KMS / Azure Key Vault
  Java：JCE + 云 SDK 的标准集成模式
```

### 5.3 秘密管理工具

| 场景 | 工具 |
|------|------|
| 配置密钥 | 环境变量 / 密钥服务（Vault） |
| 云密钥 | KMS（信封加密） |
| 本地密钥 | 文件 + 权限（避免源码仓库！） |
| 硬件保护 | HSM（金融/根 CA） |
| 容器 | Kubernetes Secrets + 外部密钥服务 |

## 6. 常见工程错误清单

| 错误 | 后果 | 修复 |
|------|------|------|
| 密钥硬编码在源码 | 泄露即全毁 | 外部化 + KMS |
| 弱随机（Random/时间种子） | 密钥可预测 | SecureRandom |
| 用 SHA-1/MD5 做安全 | 碰撞伪造 | SHA-256+ |
| 裸 RSA/无填充 | 确定性+可延展 | OAEP/PSS |
| JWT alg=none | 伪造令牌 | 算法白名单 |
| 自实现加密/签名 | 侧信道/数学错误 | 用标准库 |
| 比较用 equals | 时序泄露 | MessageDigest.isEqual |
| 日志打印密钥/令牌 | 直接泄露 | 脱敏 + 审计 |
| 不轮换/不吊销 | 泄露窗口扩大 | 自动化轮换 |

## 7. 安全审计清单

```text
① 传输层：TLS 1.3 + 前向保密 + 证书链完整？
② 会话：短期 JWT + 刷新令牌可吊销？
③ 存储：口令 argon2id、数据信封加密？
④ 随机：全部 SecureRandom？
⑤ 密钥：KMS 管理、定期轮换、无硬编码？
⑥ 代码：无自研密码原语、常数时间比较？
⑦ 日志：无密钥/令牌泄露？
⑧ 依赖：密码库及时升级（含后量子支持，08 模块）？
```

> 🎯 **核心要点**：协议层是"密码学的战场"——TLS 1.3 把前向保密与 AEAD 变成默认，JWT 的算法混淆与 alg=none 是工程师最常踩的坑，侧信道让"自研实现"成为禁区。**系统安全的 90% 是配置正确性与密钥管理，只有 10% 是算法选择。**
