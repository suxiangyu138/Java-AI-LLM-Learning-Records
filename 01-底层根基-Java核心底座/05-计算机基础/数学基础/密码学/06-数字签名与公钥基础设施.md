## 1. 数字签名的作用

### 1.1 签名提供的保证

| 保证 | 含义 |
|------|------|
| 认证性 | 签名者身份（私钥持有者） |
| 完整性 | 消息未被篡改（签名随内容失效） |
| 不可否认性 | 签名者无法抵赖（法律意义） |

```text
签名流程（Ed25519/ECDSA 通用）：
  签名：σ = Sign(H(m), 私钥)
  验证：Verify(H(m), σ, 公钥) → 有效/无效

对比 MAC（04 模块）：
  MAC 对称（收发同密钥）→ 无法向第三方证明
  签名非对称（私签公验）→ 可公开验证 = 信任体系的基础
```

### 1.2 签名的使用场景

| 场景 | 签名对象 | 意义 |
|------|---------|------|
| HTTPS | 服务器证书 | 确认服务器身份 |
| 代码签名 | 软件包 | 防篡改、来源可信 |
| 软件更新 | 更新包 | 防恶意替换 |
| 区块链 | 交易 | 所有权证明 |
| S/MIME | 邮件 | 邮件认证 |

## 2. X.509 证书

### 2.1 证书的结构

```text
X.509 v3 证书的主要内容：
  ① 主体（Subject）：持有者信息（域名/组织）
  ② 公钥：持有者的公钥（RSA/ECC/ML-DSA）
  ③ 签发者（Issuer）：CA 名称
  ④ 有效期：notBefore/notAfter
  ⑤ 扩展：SAN（域名列表）、密钥用途、CT 日志引用
  ⑥ 签名：CA 对以上内容的签名（信任的关键）

证书的本质：CA 用签名把"公钥 ↔ 身份"绑定起来
```

### 2.2 证书格式与编码

| 格式 | 编码 | 用途 |
|------|------|------|
| PEM | Base64 + 头尾标记 | 传输/配置（.crt/.pem） |
| DER | 二进制 | 内部处理 |
| PKCS#12 | 证书+私钥加密打包 | 导入导出（.p12/.pfx） |

```text
Java 查看证书：
  keytool -printcert -file server.crt
  openssl x509 -in server.crt -text -noout
  —— 排查 TLS 问题的第一步
```

## 3. 信任链与 CA 体系

### 3.1 信任链（Chain of Trust）

```text
信任传递：
  根 CA（内置信任库）→ 中间 CA → 叶子证书（服务器）
  验证：逐级向上，直到"我信任的根"

浏览器内置：约 100+ 根证书（Mozilla/Apple/Microsoft 信任库）
  根证书自签名（自己的密钥签自己）——信任的起点（"Trust on first use"）

密钥层级（对应现实安全）：
  根密钥：离线保存（HSM，几乎不直接签发）
  中间 CA 密钥：在线签发叶子证书（可轮换）
  叶子密钥：短期有效（90 天，见生命周期）
```

### 3.2 信任模型的弱点

| 弱点 | 说明 | 缓解 |
|------|------|------|
| 根密钥泄露 | 攻击者可伪造任意证书 | 离线+HSM+轮换 |
| 中间 CA 被攻陷 | 签发恶意证书 | CT 监控、短有效期 |
| 商业 CA 失误 | 错误签发（历史事件） | CT 公开审计 |
| 信任库膨胀 | 根越多攻击面越大 | 信任库瘦身 |

> 🎯 核心认知：**PKI 的安全性不是数学而是运营**——签名算法只是起点，根密钥保管、CA 审计、证书透明度才是信任体系的真正防线。

## 4. 证书透明度（CT）

### 4.1 解决的问题

```text
问题：CA 被攻陷/失误时，恶意证书会被悄悄签发并使用
  （2011 DigiNotar 事件：错误签发 500+ 证书，用户无法察觉）

CT（Certificate Transparency）：
  所有公开证书必须提交到公开日志（追加式、防篡改）
  → 任何人可审计"谁签发了什么"
  → 恶意证书一旦出现即被监控发现
```

### 4.2 CT 机制

```text
签发流程：证书 → CT 日志（SCT 证明）→ 浏览器验证 SCT → 接受
  日志：Merkle 树结构（追加不可篡改，可验证一致性）
  监控：第三方可实时扫描新证书

现状：主流浏览器要求公开证书必须带 SCT
  → CT 已成 HTTPS 的强制组件（2018 年起）

2026 挑战：后量子证书变大 → CT 日志大小限制成为迁移阻点（08 模块）
```

## 5. 证书生命周期管理

### 5.1 生命周期流程

```text
申请 → 签发 → 部署 → 监控 → 轮换 → 吊销/过期

关键指标（2025-2026 趋势）：
  有效期：从 398 天 → 90 天（Let's Encrypt/Google 推动）
  自动化：ACME 协议（Let's Encrypt 自动签发续期）
  管理：证书库存清单（CBOM）成为迁移前提（08 模块）
```

### 5.2 吊销机制

| 机制 | 原理 | 问题 |
|------|------|------|
| CRL | 吊销列表（下载） | 延迟、大小 |
| OCSP | 在线查询 | 隐私、可用性（OCSP 失败时） |
| OCSP Stapling | 服务器代查 | 主流方案（仍依赖缓存） |
| 短有效期 | 吊销需求最小化 | **现代趋势（90 天）** |

```text
2026 实践：90 天证书 + ACME 自动化 + CT 监控
  → "吊销"逐渐被"快速过期"取代（轮换优先于吊销）
```

## 6. TLS 中的证书使用

### 6.1 服务器身份验证流程

```text
TLS 握手（简化）：
  ① ClientHello（支持套件/群）
  ② ServerHello + 证书（X.509 链）
  ③ 客户端验证：签名 → 信任链 → 有效期 → 域名匹配 → CT
  ④ 密钥交换（ECDHE/ML-KEM）→ 会话密钥
  ⑤ 加密通信（AES-GCM/ChaCha20）

验证失败任一环节 → 中止连接（浏览器红锁）
  —— 证书验证是 TLS 安全的"身份层"
```

### 6.2 常见 TLS 证书问题排查

| 现象 | 原因 |
|------|------|
| 证书过期 | 未续期（90 天轮换遗漏） |
| 链不完整 | 缺中间证书（只发了叶子） |
| 域名不匹配 | SAN 缺失/错误 |
| 自签名 | 内部系统/测试（需显式信任） |
| 吊销状态 | OCSP 查询失败（stapling 未配） |

> 💡 Java 工程注意：JDK 自带信任库（cacerts）只含公开根——内部 CA 证书需手动导入，否则 `PKIX path building failed`。

## 7. 2026 的证书挑战

### 7.1 后量子证书的困境（与 08 模块呼应）

```text
现状：TLS 会话密钥已混合量子化，但服务器证书仍是 ECDSA/RSA
  → 证书被记录后可在量子时代被伪造（Harvest-now 威胁）

难点：
  ① 证书大小：ML-DSA-87 叶子 5.5KB vs ECDSA ~1KB
     → CT 日志大小限制（8-16KB）成瓶颈
  ② 信任库：根 CA 尚未有 ML-DSA 根（等待 FIPS 140-3 验证）
  ③ 浏览器：尚未默认协商 ML-DSA 证书（2026 标准未定）

路线：复合签名（ML-DSA-65 + ECDSA P-256）先过渡（2026 草案）
  → 纯 ML-DSA 证书预计 2027-2028
```

### 7.2 证书管理行动清单（2026）

```text
① 建立证书清单（CBOM）：知道有哪些证书、什么时候过期
② 启用自动化轮换（ACME 90 天）
③ 配置 OCSP Stapling
④ 监控 CT 日志（发现未知证书）
⑤ 评估后量子证书升级路径（内部 CA 先行，见 08 模块）
```

> 🎯 **核心要点**：PKI 是把"数学签名"变成"社会信任"的工程系统——X.509 绑定身份、CA 传递信任、CT 公开审计、轮换控制风险。2026 年它正经历成立以来最大的技术迁移：从 ECDSA/RSA 证书走向复合/后量子证书，其节奏由信任库、CT 日志与浏览器共同决定（详见 08 模块）。
