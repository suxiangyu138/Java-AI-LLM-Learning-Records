## 1. 为什么需要冗余

### 1.1 噪声的现实

```text
任何物理传输/存储都有噪声：
  无线：干扰、衰落；有线：串扰；存储：磁/闪存退化
  误码率现实：无保护传输 10⁻³~10⁻⁶ 量级
  需求：数据完整性 10⁻⁹~10⁻¹⁵ 以上

解法：按信道编码定理（03 模块），冗余可以"买到"任意可靠性
  代价：码率（有效信息占比）下降
```

### 1.2 检错 vs 纠错

| 类型 | 行为 | 应用 |
|------|------|------|
| 检错（EDC） | 发现错误 → 请求重传 | 网络（TCP/以太网） |
| 纠错（ECC） | 发现并修复错误 | 存储、无线（不能重传） |
| 混合 | 纠少量 + 检出更多 | 磁盘（ECC 扇区） |

```text
设计原则：
  可重传的场景（网络）→ 检错即可（省冗余）
  不可重传的场景（磁盘、无线广播）→ 必须纠错
```

## 2. 检错码：奇偶校验与 CRC

### 2.1 奇偶校验

```text
最简单：n−1 位数据 + 1 位校验（使总 1 的个数为偶数/奇数）
  能力：检出奇数个比特错误
  局限：偶数个错误漏检（50% 盲区）

工程：早期内存奇偶校验（现已被 ECC 取代）、串口校验
```

### 2.2 CRC（循环冗余校验）

```text
原理：把数据视为 GF(2) 上的多项式，除以生成多项式 g(x)，
  余数作为校验码（4-64 位）

CRC-32 能力：
  检出所有奇数位错误
  检出所有 ≤ 32 位突发错误
  长度 2³² 内的双错检出率极高（>99.99999998%）

工程应用：
  Ethernet 帧尾 CRC-32、ZIP 完整性、磁盘校验、网络校验
  Java：java.util.zip.CRC32
```

```java
// CRC-32（Java 内建）
CRC32 crc = new CRC32();
crc.update(data);
long value = crc.getValue();   // 校验值，存储/传输后比对
```

### 2.3 校验和（Checksum）

```text
累加和/异或和：比 CRC 弱但更快
  UDP 头校验和、IP 头校验和（简单加和）
  现代存储用更强的 CRC/ECC；校验和仅用于头部
```

## 3. 汉明码：单比特纠错

### 3.1 编码原理

```text
汉明码 (7,4)：4 位数据 + 3 位校验（可纠 1 位错误）
  校验位位置：2 的幂（1, 2, 4）
  每位校验位覆盖：二进制位包含该位置的所有数据位
  → 出错时，错位位置 = 失效校验位的编号之和（校正子）

编码示例：数据 1011（d4=1 d3=0 d2=1 d1=1）
  p1 覆盖位 {1,3,5,7}：p1 ⊕ d1 ⊕ d2 ⊕ d4 = 0 → p1 = 0
  p2 覆盖位 {2,3,6,7}：p2 ⊕ d1 ⊕ d3 ⊕ d4 = 0 → p2 = 1
  p4 覆盖位 {4,5,6,7}：p4 ⊕ d2 ⊕ d3 ⊕ d4 = 0 → p4 = 0
  发送：p1 p2 d1 p4 d2 d3 d4 = 0 1 1 0 1 0 1

接收端：重算三个校验 → 校正子 = 错位编号（0 表示无错）
  例：第 5 位翻转 → 涉及 p1、p4 的校验失败 → 校正子 101 = 5 ✓
```

### 3.2 工程变体

| 变体 | 能力 | 场景 |
|------|------|------|
| 汉明 (7,4) | 纠 1 错 | 教学经典、早期内存 |
| 扩展汉明 | 纠 1 错 + 检 2 错 | 更实用（SEC-DED） |
| SEC-DED | 单纠双检 | **现代 ECC 内存**（72 位条上的 8 位校验） |

> 💡 ECC 内存为什么贵：每 64 位数据加 8 位校验（SEC-DED）——检测并纠正单比特翻转、检测双比特翻转。服务器内存的标配，数据中心的"隐形保险"。

## 4. Reed-Solomon 码

### 4.1 原理：多项式插值的检错视角

```text
RS 码把数据视为多项式系数，编码输出多项式在若干点上的取值：
  数据 k 个符号 → 多项式次数 k−1 → 采样 n 个点（n > k）
  任意 ≤ t 个点出错仍能恢复原多项式（插值 + 纠错）

有限域基础：运算在 GF(2⁸) 上进行（初等数论/05 模块的域！）
  每个符号 1 字节 → 高效硬件实现
```

### 4.2 能力与应用

| 特性 | 内容 |
|------|------|
| 纠错能力 | 可纠 t 个符号错误（n = k + 2t） |
| 突发纠错 | 连续多字节损坏也能恢复（符号级而非比特级） |
| 应用 1 | CD/DVD/蓝光（跨扇区交错 RS） |
| 应用 2 | QR 码（RS 纠错 7-30%） |
| 应用 3 | RAID 6（双盘故障恢复 = 双校验 RS） |
| 应用 4 | 航天遥测（Voyager 用过） |

> 🎯 直觉：RS 码是"多项式在多点取值"的冗余——数据藏进多项式，部分采样损坏也无妨。它是存储与消费电子的"标准纠错"，也是 GF(2⁸) 有限域理论最成功的工程落地。

## 5. LDPC 码

### 5.1 原理与突破

```text
LDPC（低密度奇偶校验码）：稀疏校验矩阵定义的线性码
  校验方程：H·c = 0（多数校验方程只涉及少量变量）

1993 年 Turbo 码首次逼近香农极限，2000 年代 LDPC 后来居上：
  "Shannon limit" 差距缩小到 0.1 dB 以内（工程可达极限）

迭代解码：置信传播（BP）算法
  变量节点与校验节点之间反复传递"软信息"（概率）
  迭代收敛 → 逼近最大似然解码
```

### 5.2 应用版图

| 场景 | 标准 |
|------|------|
| 5G NR 数据信道 | LDPC（URLLC 增强型） |
| WiFi（802.11ax） | LDPC 可选 |
| 光纤通信 | 400G/800G 光模块 LDPC |
| SSD 闪存 | LDPC 固件（NAND 可靠性随制程下降的救星） |
| DVB 卫星 | LDPC 级联 |

> ⚠️ 注意区分：5G 的**控制信道用极化码**（短码更优），数据信道用 LDPC（长码更优）——两个"逼近容量"的码按场景分工。

## 6. 极化码（Polar）

### 6.1 信道极化的思想

```text
极化码（Arikan 2009）是首个"理论上证明可达容量"的编码：
  把 N 个"相同噪声"的信道，通过线性变换变成
    N·C 个"几乎无噪"信道 + N·(1−C) 个"几乎全噪"信道
  → 只在无噪信道上发信息（信息位），全噪信道发固定值（冻结位）

神奇之处：码长趋于无穷时，极化达到完美二分
  → 严格证明可达香农容量（不像 LDPC 只是"实践逼近"）
```

### 6.2 5G 应用与工程

```text
5G NR 控制信道：极化码（短码、低时延场景优势）
  配合 CRC 做"提前终止"（CRC-aided list decoding）

对比 LDPC：
  LDPC：长码好（数据）、迭代解码延迟高
  Polar：短码好（控制）、列表解码可硬件化
  → 5G 数据/控制分工的数学依据
```

## 7. 编码的工程选择

| 场景 | 编码 | 理由 |
|------|------|------|
| 以太网/TCP | CRC-32 检错 | 可重传 → 检错即可 |
| ECC 内存 | SEC-DED | 单纠双检，延迟敏感 |
| SSD/NAND | LDPC | 高纠错能力，适应 NAND 退化 |
| CD/QR/RAID6 | RS | 突发/符号级纠错 |
| 5G 数据 | LDPC | 逼近容量，长码 |
| 5G 控制 | Polar | 短码极化优势 |
| 数字电视 | LDPC + BCH 级联 | 双层保护 |

### 工程决策框架

```text
① 能否重传？能 → 检错（CRC）；不能 → 纠错（ECC 家族）
② 错误形态？突发多字节 → RS；随机单比特 → 汉明/SEC-DED
③ 码长与延迟？长码高吞吐 → LDPC；短码低延迟 → Polar
④ 复杂度预算？硬件面积/解码功耗 vs 纠错增益
```

> 🎯 **核心要点**：信道编码 = "用冗余买可靠性"的工程艺术——从 1 位的奇偶校验到逼近香农极限的 LDPC/极化码，60 年演进把"理论容量"变成了 5G 物理层与数据中心存储的现实。选码四问（重传？形态？码长？预算？）覆盖 90% 工程场景。

## 8. 小结

| 问题 | 答案 |
|------|------|
| 检错 vs 纠错怎么选？ | 可重传检错（CRC），不可重传纠错（ECC） |
| 汉明码能力？ | 纠 1 错（SEC-DED 单纠双检 = ECC 内存） |
| RS 码基础？ | GF(2⁸) 多项式插值，突发纠错（QR/RAID6） |
| LDPC 强在哪？ | 长码逼近容量 0.1dB 内（5G 数据/SSD/光通信） |
| 极化码的意义？ | 首个理论可达容量（5G 控制信道） |
| 5G 为何两种码？ | 数据长码 LDPC、控制短码 Polar 各取所长 |
