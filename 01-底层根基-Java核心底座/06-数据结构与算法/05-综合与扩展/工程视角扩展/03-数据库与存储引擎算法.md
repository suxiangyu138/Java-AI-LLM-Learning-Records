## 1. B+树：MySQL 索引的算法本质

### 1.1 为什么是 B+树（对比四选一）

| 结构 | 磁盘 IO（树高） | 范围查询 | 写性能 | 结论 |
|------|:---:|:---:|:---:|------|
| 哈希表 | O(1) | ❌ | ✅ | 只等值快 |
| 二叉搜索树（红黑） | O(log n)≈30 层 | ✅ | 中 | 树高 = IO 次数，太高 |
| B 树 | O(log n)≈4 层 | 中（需回溯） | 中 | 内节点存数据，页利用率低 |
| **B+树** | **≈3-4 层** | **✅ 叶子链表** | ✅ | **工程标准答案** |

### 1.2 B+树 vs B 树的三个关键差异

| 差异 | 为什么 B+ 更优 |
|------|------|
| 数据只在叶子 | 内节点可装更多 key → 树更矮 → IO 更少 |
| 叶子双向链表 | 范围查询免回溯，顺序扫描快 |
| 叶子节点独立 | 页分裂时内节点只更新指针，更稳定 |

### 1.3 工程参数（MySQL InnoDB）

| 参数 | 值 | 计算 |
|------|:---:|------|
| 页大小 | 16 KB | 一次磁盘 IO 单位 |
| 单页可存 key | 约 1200+ | 16KB / (8B key + 6B 指针) |
| 树高 3 层 | 约 1200² 叶子 | 可存数亿行，且 3 次 IO 定位 |
| 一次索引查找 | 约 3-4 次磁盘 IO | 内存命中后更少 |

### 1.4 树高 = IO 次数的推导（面试必答）

```text
B+树每层一次磁盘 IO（根节点常驻内存，可省一次）
3 层 B+树 = 3 次 IO：
  第 1 层（根）约 1200 个指针 → 第 2 层 1200 个节点
  第 2 层 1200 × 1200 ≈ 144 万个叶子指针 → 千万级数据 3 次 IO
对比红黑树：10⁶ 数据树高约 20 → 20 次 IO → 慢一个量级
结论：B+树把「每次定位」压缩到 3-4 次磁盘 IO，这是选它的核心
```

> 🎯 面试必答：**树高 = IO 次数**——B+树把「IO 次数」压到 3-4 次，这就是 MySQL 选它的核心原因。B 树内节点存数据会减少扇出、增加树高。

### 1.5 索引失效的算法本质

| 失效场景 | 原因（数据结构视角） |
|------|------|
| 最左前缀不符 | 联合索引按列字典序组织，跳列即失去有序性 |
| 函数/运算 on 列 | 索引存原值，`f(col)` 无法走有序查找 |
| 隐式类型转换 | 比较双方便值域不同，无法用 B+树有序性 |
| 范围查询右侧 | `a > 5 AND b < 3`——a 的范围打破了 b 的有序 |

### 1.6 回表与覆盖索引（工程追问）

```text
聚簇索引（主键）：叶子存整行数据 → 主键查询一次定位
二级索引：叶子存主键值 → 查二级索引后还需回表找行
覆盖索引：查询列都在二级索引中 → 免回表（减少 IO）
示例：SELECT id, name WHERE name='x'，若 (name, id) 联合索引
      → 覆盖索引直接出结果，无需回表
```

## 2. LSM-Tree：写优化的存储引擎

### 2.1 LSM 的分层写入

```text
写入：先写内存 MemTable（有序跳表/树）+ WAL 日志
    → MemTable 满 → 冻结 → 刷盘 SSTable（有序文件，不可变）
    → 后台合并（Compaction）：把多层小文件归并为大文件
读取：MemTable → 各层 SSTable（二分/布隆过滤跳过）
```

### 2.2 B+树 vs LSM 选型（高频对比）

| 维度 | B+树（InnoDB） | LSM（RocksDB/LevelDB/HBase） |
|------|:---:|:---:|
| 写 | 随机写（页分裂、写放大） | **顺序写**（append + 合并） |
| 读 | **快**（定位即读） | 慢（多层合并查 + 布隆） |
| 空间 | 紧凑 | 有冗余（多层副本） |
| 适用 | OLTP 读多写少 | **写多读少、写入峰值大** |
| 工程代表 | MySQL InnoDB | RocksDB、HBase、TiKV、ClickHouse 部分 |

### 2.3 关键权衡

| 术语 | 含义 | 代价 |
|------|------|------|
| 写放大 | 数据被合并重写多次 | 高写入量时 SSD 寿命 |
| 读放大 | 一次查询查多层 | 布隆过滤器缓解 |
| 空间放大 | 多层冗余 | 定期 Compaction |

> 🎯 一句话分法：**读多写少 → B+树；写多读少 → LSM**。LSM 用「读和空间的代价」换「顺序写」，是 HBase/RocksDB 这类海量写入系统的根基。

## 3. 哈希索引与自适应哈希

| 类型 | 结构 | 用途 | 局限 |
|------|------|------|------|
| 显式哈希索引 | 哈希表 | 等值查询（MEMORY 引擎） | 无范围、无排序 |
| InnoDB 自适应哈希 | 内存层缓存 | 热点等值查询加速（自动） | 不可控、占内存 |
| 为什么主键用 B+ | 范围与排序 | 主键也建 B+树 | — |

```text
InnoDB 自适应哈希：对频繁访问的索引页建立内存哈希
访问路径：B+树定位 → 页在 AHI 中命中 → 跳过树遍历
⚠️ 它是「加速器」不是「索引」：自动启用、不可 DDL 创建
```

### 3.1 什么时候哈希索引赢（面试推导）

```text
哈希索引 = 等值 O(1)，范围查询退化全扫
B+树 = 等值 O(log n)，范围 O(log n + k)
决策：
  纯等值查询（如 Redis key-value）→ 哈希
  含范围/排序/前缀 → B+树
  多条件组合过滤 → 位图（OLAP）
```

## 4. Join 算法与查询优化

### 4.1 三种 Join 算法

| 算法 | 原理 | 复杂度 | 适用 |
|------|------|:---:|------|
| Nested Loop Join | 外层逐行 × 内层查找 | O(N×M) | 小表驱动大表 + 内层有索引 |
| Hash Join | 小表建哈希，大表探测 | O(N+M) | 等值连接、无索引 |
| Merge Join | 两表排序后归并 | O(N+M) | 已排序/索引有序 |

### 4.2 工程要点

```text
驱动表选择：小表驱动大表（NLJ 场景）——每次外循环查内表
索引驱动：内层连接列有索引 → NLJ 内层退化为 O(log n)
Hash Join：MySQL 8.0.18+ 引入，等值连接默认候选
⚠️ 高频考点：join 的 on 列不加索引 = 全表扫描内层
```

### 4.3 Hash Join 为什么适合无索引大表（追问）

```text
NLJ 无索引：内层全表扫 O(N×M) → 海量数据不可用
Hash Join：
  ① 选小表建哈希（内存放得下）
  ② 大表逐行探测哈希 → 每次 O(1)
  总代价 O(N+M) + 哈希构建
  内存放不下 → 分桶（分区哈希）→ 逐桶处理
```

## 5. 外部排序与位图索引

### 5.1 外部排序（海量数据 ORDER BY）

| 阶段 | 做法 |
|------|------|
| 分块排序 | 内存放不下的数据分成多个有序块（归并排序思路） |
| 多路归并 | k 路归并（败者树/堆优化取最小值） |
| 代价 | IO 次数 = 归并轮数 × 数据量 |

```text
排序原理：归并排序的「外存版」
10 GB 数据 + 1 GB 内存 → 10 个有序块 → 多路归并
优化：增大归并路数 k（堆实现）→ 减少归并轮数
IO 次数 = log_k(块数) × 数据量（k 越大轮数越少）
```

### 5.2 位图索引（分析型数据库）

| 维度 | 说明 |
|------|------|
| 结构 | 每个取值一个位图，行号 → 位 |
| 查询 | AND/OR 位运算秒级过滤 |
| 适用 | 低基数列（性别、状态）、OLAP 分析 |
| 代表 | Oracle、ClickHouse（部分） |
| 对比 B+树 | 位图适合「多条件组合过滤」，B+树适合「定位单行」 |

## 6. 数据库面试算法问题清单

| 问题 | 一句话答案 |
|------|------|
| 为什么 B+树而不是红黑树？ | 树高 = IO 次数：红黑树 20 层 vs B+树 3-4 层 |
| B 树和 B+树的区别？ | 数据只在叶子 + 叶子链表（范围查询免回溯） |
| 联合索引为什么最左？ | B+树按列字典序组织，跳列失去有序性 |
| LSM 为什么写快？ | 顺序写 + 后台合并，牺牲读 |
| Join 的 on 不加索引会怎样？ | NLJ 内层全表扫 → O(N×M) |
| 覆盖索引是什么？ | 查询列都在索引里 → 免回表 |

> 🎯 **核心要点**：数据库 = 数据结构 × IO 成本——**B+树（读多）、LSM（写多）、哈希（等值）、位图（低基数列）**四个结构对应四种访问模式；Join 三算法对应「有没有索引、是不是等值」；外部排序是归并的工程化。面试把「为什么选它」落到「IO 次数 / 写放大 / 读放大」上，数据库原理题全部打通。
