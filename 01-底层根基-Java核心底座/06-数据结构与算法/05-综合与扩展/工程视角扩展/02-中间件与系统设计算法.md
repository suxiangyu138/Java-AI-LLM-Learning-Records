## 1. LRU 缓存：双向链表 + 哈希

### 1.1 原理

| 组件 | 作用 | 复杂度 |
|------|------|:---:|
| HashMap | key → 节点定位 | O(1) |
| 双向链表 | 维护访问序（最近在头） | O(1) 移动 |

### 1.2 核心操作（三个 O(1)）

```text
get(key)：
  命中 → 节点移到链表头
  未命中 → 返回 -1
put(key, value)：
  已存在 → 更新值 + 移到头部
  不存在 → 头部插入；超容量 → 删除尾部节点
```

### 1.3 手写完整实现（面试必考）

```java
/** LRU 手写版：HashMap 定位 + 双向链表移动 */
class LRUCache {
    static class Node {
        int key, val; Node prev, next;
        Node(int k, int v) { key = k; val = v; }
    }
    private final int cap;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0), tail = new Node(0, 0);

    public LRUCache(int capacity) {
        cap = capacity;
        head.next = tail; tail.prev = head;   // 哨兵节点省去判空
    }

    public int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        moveToHead(n);                        // 访问 → 移到头部
        return n.val;
    }

    public void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) { n.val = value; moveToHead(n); return; }
        Node node = new Node(key, value);
        map.put(key, node);
        addToHead(node);
        if (map.size() > cap) {               // 超容量淘汰尾部
            Node last = tail.prev;
            removeNode(last);
            map.remove(last.key);
        }
    }

    private void addToHead(Node n) { n.next = head.next; n.prev = head;
        head.next.prev = n; head.next = n; }
    private void removeNode(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void moveToHead(Node n) { removeNode(n); addToHead(n); }
}
// 要点：哨兵 head/tail 消除「空表」特判；map 删除与链表删除必须同步
```

### 1.4 工程位置与变体

| 场景 | 应用 |
|------|------|
| Redis | 内置近似 LRU（随机采样淘汰，非严格） |
| MySQL | Buffer Pool 的 LRU 分代（old/new 区） |
| 手写题 | 「手写 LRU」是系统设计必考第一题 |
| 变体 | LFU（按频率）、TinyLFU（Caffeine 默认） |

> 🎯 面试必答：**HashMap 给 O(1) 定位，双向链表给 O(1) 移动**——单链表做不到 O(1) 删任意节点（要改前驱）。哨兵节点是消除边界特判的工程技巧。

## 2. 一致性哈希：分布式分片

### 2.1 为什么朴素取模不行

| 问题 | 表现 |
|------|------|
| 扩容/缩容全量迁移 | 3 节点 → 4 节点，约 3/4 数据搬家 |
| 热点不均匀 | 数据倾斜到某节点 |

### 2.2 一致性哈希原理

```text
把哈希值空间组织成环（0 ~ 2³²-1）
节点哈希到环上；数据哈希到环上 → 顺时针找最近节点
节点增删只影响【该节点与其前驱之间】的数据 → 迁移量 1/n
```

| 改进 | 解决的问题 |
|------|------|
| 虚拟节点 | 节点少时数据分布不均；每个物理节点映射 100-200 个虚拟节点 |
| 平衡性 | 虚拟节点 + 环均匀分布 |

### 2.3 迁移量计算（面试推导）

```text
假设 n 个节点均匀分布在一个环上，每个节点「管辖」环的 1/n
新增节点后：只有新节点前驱的管辖范围被切走一半
→ 受影响数据量 = 1/n × 1/2？不对——只影响前驱节点管的那一段
精确说法：新增节点接管其【顺时针前驱】与它之间的那段
→ 迁移量 ≈ 1/(n+1)（均匀分布时）
取模法迁移量 ≈ n/(n+1) → 一致性哈希把迁移从 O(n) 降到 O(1/n)
```

### 2.4 工程位置

| 中间件 | 用法 |
|------|------|
| Redis Cluster | 哈希槽（16384 槽）——类似思路，槽固定便于迁移 |
| Memcached 客户端 | 一致性哈希分布式缓存 |
| 分库分表中间件 | 一致性哈希路由（扩容少迁移） |
| 负载均衡 | 相同 key 落到同一后端（session 粘滞） |

> ⚠️ 追问点：一致性哈希「尽量少迁移」不是「不迁移」；虚拟节点解决的是**分布均匀**而非**单调性**。

## 3. 限流算法四件套

| 算法 | 原理 | 特点 | 实现 |
|------|------|------|------|
| 固定窗口 | 每秒/每分钟计数归零 | 突刺（窗口边界双倍流量） | 计数器 |
| 滑动窗口 | 细粒度时间片滚动 | 平滑，内存稍高 | 环形数组/日志 |
| 令牌桶 | 匀速放令牌，桶满弃 | **允许突发**（桶容量=突发上限） | 计数器 + 定时 |
| 漏桶 | 匀速出水，超限丢弃 | **严格匀速**，无突发 | 队列 |

### 3.1 令牌桶 vs 漏桶（最常考）

| 维度 | 令牌桶 | 漏桶 |
|------|------|------|
| 突发 | ✅ 允许（桶内积令牌） | ❌ 不允许 |
| 丢弃策略 | 令牌不足即拒 | 队列满即丢 |
| 适用 | 允许突发流量（网关/API） | 必须匀速（消息推送、视频流） |
| 工程代表 | Guava RateLimiter（平滑令牌桶） | Nginx limit_req（漏桶） |

### 3.2 令牌桶实现（懒计算版本）

```java
/** 令牌桶：懒计算——只有请求时才算「应补多少令牌」，无需定时器 */
class TokenBucket {
    private final long cap;          // 桶容量（突发上限）
    private final double rate;       // 每秒补充令牌数
    private double tokens;
    private long lastRefill;

    public TokenBucket(long cap, double rate) {
        this.cap = cap; this.rate = rate;
        this.tokens = cap;
        this.lastRefill = System.currentTimeMillis();
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        tokens = Math.min(cap, tokens + (now - lastRefill) / 1000.0 * rate);
        lastRefill = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;
    }
}
// 要点：时间差换算令牌，避免每秒定时线程；synchronized 保证原子
```

> 🎯 一句话分法：**「允许抖动」选令牌桶，「必须平滑」选漏桶**——接口限流基本都选令牌桶。

## 4. 布隆过滤器与位图

### 4.1 布隆过滤器（Bloom Filter）

| 维度 | 说明 |
|------|------|
| 结构 | 位数组 + k 个哈希函数 |
| 判定 | 存在「可能在」（有误判）；不存在「一定不在」（无漏判） |
| 误判率 | 约 `(1 - e^(-kn/m))^k`，工程取 1% 量级 |
| 删除 | 不支持（计数布隆可支持） |
| 空间 | 千万级元素只用几十 MB |

```text
插入 x：k 个哈希 → 置位 1
查询 y：k 个哈希 → 任一为 0 → 一定不在；全为 1 → 可能在
参数：m = 位数组长度，n = 元素数，k = 哈希数
最优：k ≈ (m/n)·ln2；误判率 1% 时 m/n ≈ 9.6 位/元素
```

### 4.2 工程应用表

| 场景 | 用法 |
|------|------|
| 缓存穿透防护 | Redis 前挡一层：不存在的 key 直接拦截 |
| 爬虫 URL 去重 | 海量 URL 判重 |
| 垃圾邮件/内容过滤 | 黑名单「一定不在」快速放行 |
| 数据库 | HBase 用布隆过滤加速行键检查 |
| 位图（BitSet） | 用户签到、在线状态、亿级去重（1 位/元素） |

## 5. 跳表与 Trie：Redis 与路由的骨架

### 5.1 跳表（Skip List）

| 维度 | 说明 |
|------|------|
| 结构 | 多层有序链表，上层为下层「快速通道」 |
| 复杂度 | 查/插/删 O(log n)（期望） |
| 对比平衡树 | 实现简单、区间遍历自然、无旋转 |
| 唯一大牌 | **Redis ZSet 用跳表**（配合哈希） |

### 5.2 为什么 Redis ZSet 用跳表而不用红黑树

```text
① 区间查询（ZRANGEBYSCORE）：跳表从起点顺序遍历，红黑树需中序
② 实现与调试成本：跳表远低于红黑树
③ 概率平衡：期望 O(log n)，工程实践足够
④ 内存：层数期望 O(log n)，指针开销可接受
```

### 5.3 Trie（字典树）

| 应用 | 说明 |
|------|------|
| 前缀匹配 | 路由表（网关）、自动补全 |
| 单词统计 | 词频、敏感词过滤（AC 自动机 = Trie + KMP 失配链） |
| 空间优化 | 压缩 Trie（Radix Tree）→ **Linux 路由表 / Nginx / Redis 集群槽定位** |
| 复杂度 | 插入/查询 O(单词长度)，与集合大小无关 |

## 6. 系统设计题的五分钟算法框架

```text
拿到系统设计题，前五分钟按算法角度列组件：

① 缓存层：LRU/LFU（LinkedHashMap 或手写双向链表）
② 分片层：一致性哈希 + 虚拟节点（Redis Cluster 用 16384 槽）
③ 防穿透：布隆过滤器挡「不存在的 key」
④ 限流层：令牌桶（允许突发）——网关标配
⑤ 去重/统计：位图（亿级签到/在线）
⑥ 有序结构：跳表（排行榜 ZSet）、Trie（路由前缀）

每个组件一句话说明「算法依据」：
  LRU——O(1) 定位 + O(1) 移动
  一致性哈希——迁移量从 O(n) 降到 1/(n+1)
  布隆——空间换时间，无漏判
```

> 🎯 **核心要点**：中间件算法五个「算法 ↔ 中间件」对应关系——**LRU ↔ Redis/缓存、一致性哈希 ↔ 分片路由、令牌桶 ↔ 网关限流、布隆 ↔ 缓存穿透防护、跳表 ↔ Redis ZSet**。系统设计题里说得出这五组对应，再加一句「为什么」（O(1) 定位、少量迁移、允许突发），设计题直接稳。手写 LRU 与令牌桶（懒计算）两个代码建议各练三遍。
