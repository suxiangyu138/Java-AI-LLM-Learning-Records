## 1. 倒排索引：搜索引擎的核心结构

### 1.1 正排 vs 倒排

| 类型 | 组织方式 | 查询 |
|------|------|------|
| 正排 | 文档 → 词项列表 | 知道文档查词（如「文档 3 有哪些词」） |
| **倒排** | **词项 → 文档列表** | **知道词查文档（搜索的本质）** |

```text
倒排结构：
"Java" → [doc1, doc4, doc7]
"算法" → [doc1, doc3]
查询 "Java 算法" → 取交集 [doc1]

工程增强：
  · 跳表/位图加速求交（Elasticsearch 用位图 RoaringBitmap）
  · 文档频率 df 加权 → TF-IDF / BM25 相关性排序
```

### 1.2 工程要点

| 点 | 说明 |
|------|------|
| 构建 | 文档分词 → 词项 → 文档列表（外部排序/归并） |
| 压缩 | 差值编码 + 可变字节（省 50-80% 空间） |
| 求交 | 倒排链合并 = 多路归并/位图 AND |
| 分词 | Trie/AC 自动机做词典匹配 |
| 代表 | Elasticsearch、Lucene（BM25 + 倒排 + FST 词典） |

### 1.3 倒排链求交 = 多路归并（算法对应）

```text
两个词项的倒排链：都是有序数组（docId 升序）
求交 = 双指针/归并：两指针扫描，相等则收集
多词查询 = k 路归并 / 选最短链为基准二分
对应本体系：归并排序的「合并」步骤 + 二分查找
⚠️ 这就是为什么搜索引擎核心算法全是「数据结构 + 归并」
```

> 🎯 面试必答：**倒排索引 = 「词 → 文档列表」的哈希式映射**，搜索的「查词」从此从全表扫描变成字典查找 + 列表求交。

## 2. TopK：推荐与排序的公共组件

### 2.1 三大解法对比

| 解法 | 复杂度 | 适用 |
|------|:---:|------|
| 全排序 | O(n log n) | n 小、要全序 |
| **堆**（维护 k 大小） | O(n log k) | 海量流式数据（默认） |
| 快选（partition） | 期望 O(n) | 只要第 k 大、内存可容 |

### 2.2 流式 TopK 的堆做法

```java
/** 求最大 TopK：小顶堆，堆顶是第 k 大 */
PriorityQueue<Integer> heap = new PriorityQueue<>();   // 小顶堆
for (int x : data) {
    if (heap.size() < k) heap.offer(x);
    else if (x > heap.peek()) { heap.poll(); heap.offer(x); }
}
// 复杂度 O(n log k)；⚠️ 求「最大 k」用小顶堆（堆顶是门槛）
```

### 2.3 工程场景

| 场景 | 用法 |
|------|------|
| 推荐候选召回 | 海量 item 取 Top 100 → 排序模型精排 |
| 热榜/热搜 | 流式维护 TopK + 时间衰减 |
| 数据库 order by limit | 索引有序时避免全排 |
| 大文件 TopK | 内存堆 + 分块扫描（外部化） |

### 2.4 堆 vs 快选的选型（追问）

```text
堆：O(n log k)，流式友好（数据到达即可处理），内存 O(k)
快选：期望 O(n)，一次性（数据全在内存），可无序输出
决策：
  流式/超大数据 → 堆
  一次性 + 只要一个值 → 快选（常数更优）
  需要有序 TopK → 堆（k 个自动有序输出）
```

## 3. PageRank：图的矩阵幂

### 3.1 原理

```text
网页 = 节点，链接 = 有向边
PR(A) = (1-d) + d · Σ PR(Bᵢ) / L(Bᵢ)
（Bᵢ 链向 A 的页面，L(Bᵢ) 是 Bᵢ 的出度，d ≈ 0.85 阻尼因子）

矩阵形式：PR 向量 = 转移矩阵 M × PR 向量（幂迭代）
收敛：反复乘 M，PR 向量趋于平稳分布（马尔可夫链）
```

| 算法知识点 | 对应 |
|------|------|
| 矩阵 × 向量迭代 | 快速幂的「迭代版」 |
| 收敛性 | 马尔可夫链平稳分布（d 保证遍历性） |
| 复杂度 | 稀疏矩阵 × 向量 = O(边数) 每轮，几十轮收敛 |
| 变体 | Personalized PageRank（推荐）、随机游走采样 |

### 3.2 为什么需要阻尼因子 d（追问）

```text
没有 d 的问题：
  ① 悬挂节点（无出链）会「吸收」PR，其他节点归零
  ② 强连通子图之间可能不收敛（循环陷阱）
d 的作用：
  ① 每步以概率 d 沿链接跳转、以 1-d 随机跳转任意节点
  ② 保证转移矩阵不可约 + 非周期 → 马尔可夫链必有平稳分布
  工程取值 0.85：收敛快（约 50-100 轮）且结果合理
```

> 🎯 一句话：**PageRank = 图上矩阵幂迭代到收敛**——矩阵乘向量就是「沿边传播权重」，这是图算法（遍历、传播）在推荐/搜索中的应用模板。

## 4. ANN 向量检索：从暴力到近似

### 4.1 精确 vs 近似

| 方法 | 复杂度 | 说明 |
|------|:---:|------|
| 暴力扫描 | O(n·d) | 精确，百万级即慢 |
| KD-Tree / 空间划分 | 高维退化 | 低维有效，高维「维度灾难」 |
| **HNSW**（分层可导航小世界图） | O(log n) 期望 | **工程默认**（Milvus/FAISS） |
| IVF-PQ（倒排 + 乘积量化） | 亚线性 | 压缩 + 分区，海量首选 |
| LSH（局部敏感哈希） | 哈希桶 | 近似召回 |

### 4.2 HNSW 直觉

```text
多层图：上层稀疏（快速到达目标区域），底层密集（精确近邻）
搜索：从最上层入口，每层贪心下降，最后一层取近邻
工程事实：HNSW 是 2024-2026 向量数据库（Milvus/FAISS/qdrant）的默认索引
```

### 4.3 为什么暴力在高维失效（追问）

```text
KD-Tree 按维度划分空间，低维（≤10）切分高效
高维（≥100）：绝大多数点在切割面上 → 剪枝无效 → 退化为全扫
「维度灾难」：高维空间距离分布趋同，最近邻区分度下降
解决：近似方法（HNSW 图检索、PQ 量化）用召回率换速度
```

### 4.4 工程选型

| 场景 | 索引 |
|------|------|
| 千万级以下、追求召回 | HNSW |
| 亿级、内存受限 | IVF-PQ（先分区后量化） |
| 快速原型 | 暴力 + 批处理 |
| 混合过滤（标量 + 向量） | 倒排 + 向量组合（Milvus 混合检索） |

## 5. 算法在 AI 应用中的位置

| AI 环节 | 背后的基础算法 |
|------|------|
| RAG 检索 | 向量检索（HNSW）+ TopK + 重排 |
| 推荐 | TopK 召回 + 排序模型 + PageRank/协同过滤 |
| 大模型推理 | 矩阵乘法（GPU 并行）、KV Cache（缓存）、量化（压缩） |
| 分词器 | Trie/BPE（字节对编码，类似字典树贪心合并） |
| Agent 工具调用 | 匹配/分类 + 有限状态机编排 |
| 数据去重 | 哈希 + 布隆过滤器 + SimHash |

### 5.1 RAG 流水线的算法环节（工程视角）

```text
① 文档入库：切块 → 向量化（Embedding）→ 写入向量库（HNSW 索引）
② 查询阶段：query 向量化 → ANN 检索 TopK → 重排（RRF/模型）
③ 拼装：TopK 文本 + 用户问题 → LLM 生成
每个环节的算法基础：向量索引（图/哈希）、TopK（堆）、
重排（排序）、拼装（模板/上下文窗口）
```

## 6. 检索系统面试问题清单

| 问题 | 一句话答案 |
|------|------|
| 搜索引擎怎么做到「查词」？ | 倒排索引：词 → 文档列表，求交 + BM25 排序 |
| TopK 用什么？ | 堆 O(n log k)，流式友好 |
| PageRank 是什么？ | 图上的矩阵幂迭代，马尔可夫链收敛 |
| 向量检索为什么用近似？ | 精确检索高维退化（维度灾难），HNSW 换召回率保速度 |
| RAG 怎么召回？ | 向量化 + ANN TopK + 重排 |
| 海量 URL 去重？ | 布隆过滤器（可容忍误判时）/ 哈希 |

> 🎯 **核心要点**：现代 AI 工程的四个算法骨架——**倒排（查词）、TopK 堆（取顶）、矩阵幂迭代（传播）、ANN（向量近邻）**。本体系学的每个基础算法，都在 AI 系统里以「工程组件」的形式出现：堆在推荐里叫「召回排序」，矩阵迭代在 PageRank 里叫「权重传播」，哈希在去重里叫「SimHash」。**学算法 → 理解 AI 工程，这条链路在本篇合拢。**
