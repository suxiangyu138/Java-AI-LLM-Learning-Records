## 1. 扩容触发与流程

**扩容（Resize）**：当 `size > capacity × α` 时，容量翻倍并全部键重新定位。

```text
触发条件: size > capacity × 0.75（默认 α）

例: 容量 16 → 第 13 个键插入时触发
    新容量 32 → 第 25 个键插入时再触发

扩容流程:
  ① 新建 2 倍容量数组
  ② 遍历所有桶（链表/树）
  ③ 每个键重新定位（新容量取模）
  ④ 旧数组回收
```

```java
// HashMap.resize 核心（概念）
final Node<K,V>[] resize() {
    Node<K,V>[] oldTab = table;
    int oldCap = oldTab.length;
    int newCap = oldCap << 1;            // ① 容量翻倍（2 的幂）
    Node<K,V>[] newTab = new Node[newCap];

    // ② 遍历所有桶
    for (int j = 0; j < oldCap; j++) {
        Node<K,V> e = oldTab[j];
        if (e != null) {
            // ③ JDK8: 按 hash 的扩容位拆成高低两链（见第 3 节）
            splitBucket(e, j, newTab, newCap);
        }
    }
    return newTab;
}
```

| 步骤 | 操作 | 复杂度 |
|------|------|:---:|
| ① 新数组 | 容量 ×2 | O(newCap) |
| ② 遍历桶 | 全部桶 | O(m) |
| ③ 重定位 | 每键一次 | O(n) |
| 总计 | — | **O(n)** |

> 💡 扩容后 α 从 0.75 回到 0.375——**冲突减半、查找更快**；这是「扩容不是负担而是性能重置」的视角。

## 2. 扩容的代价与摊还

### 2.1 最坏 vs 摊还

```text
单次扩容: O(n)（10 万键 → 10 万次重哈希）
摊还成本: 每次插入分摊 O(1)

摊还论证:
  每次扩容后容量翻倍
  → 扩容成本 O(capacity) 被 capacity/2 次插入摊平
  → 每次插入摊还 O(1)

类比: 动态数组（ArrayList）的扩容摊还——完全相同
```

| 视角 | 成本 |
|------|:---:|
| 单次扩容最坏 | O(n) |
| 插入摊还 | **O(1)** |
| 频繁扩容（无预分配） | 插入变慢（每次到阈值） |

### 2.2 扩容的连锁效应

```text
扩容时:
  ① 全部键重哈希（CPU 开销）
  ② 旧数组垃圾回收（GC 压力）
  ③ 树化桶拆链（结构重建）
  ④ 扩容瞬间查询暂停（大 Map 明显）

→ 扩容是「廉价均摊、偶发昂贵」的操作
→ 生产大 Map 需预分配（第 4 节）
```

> ⚠️ 超大 Map 的扩容是性能抖动源——10 亿键的 Map 扩容一次 = 10 亿次重哈希 + 数 GB 内存分配；预分配（已知规模）或分片（负载均衡）是标准解法。

## 3. JDK8 的拆链优化

### 3.1 为什么能位运算拆链

```text
扩容前: index = hash & (oldCap - 1)
扩容后: index = hash & (newCap - 1) = hash & (2×oldCap - 1)

关键: newCap = 2×oldCap（2 的幂）
  → 新 index = 旧 index 或 旧 index + oldCap
  → 由 hash 的第 oldCap 位决定（hash & oldCap）

例: oldCap = 16（hash 第 4 位决定）:
  hash = 0x1F:  旧桶 15，hash&16=16 → 新桶 31
  hash = 0x0F:  旧桶 15，hash&16=0  → 新桶 15
```

### 3.2 拆链实现

```java
// JDK8 链表拆链（免重哈希，位运算判断）
Node<K,V> loHead = null, loTail = null;     // 低位链（留在原桶）
Node<K,V> hiHead = null, hiTail = null;     // 高位链（移新桶）

do {
    Node<K,V> next = e.next;
    if ((e.hash & oldCap) == 0) {           // 扩容位为 0 → 低位
        if (loTail == null) loHead = e;
        else loTail.next = e;
        loTail = e;
    } else {                                 // 扩容位为 1 → 高位
        if (hiTail == null) hiHead = e;
        else hiTail.next = e;
        hiTail = e;
    }
    e = next;
} while (e != null);

if (loTail != null) { loTail.next = null; newTab[j] = loHead; }          // 原桶
if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; } // 新桶
```

| 对比 | 重哈希（朴素） | 拆链（JDK8） |
|------|:---:|:---:|
| 每键成本 | 重新算 index | **1 次位与判断** |
| 链表顺序 | 可能反转 | **保持原序**（并发友好） |
| 复杂度 | O(n) 哈希计算 | O(n) 位运算 |

> 🎯 **面试加分**：JDK8 扩容的「**位运算拆链**」——利用 2 的幂特性（newCap = 2×oldCap），只需判断 `hash & oldCap` 的 0/1 就能决定去留（原位或 +oldCap），且保持链表顺序（避免 JDK7 的死链 bug）。

## 4. 预分配策略

### 4.1 为什么预分配

```text
已知将插入 N 个键，直接用默认容量:
  → 多次扩容（每次 O(capacity) 重哈希）
  → 插入总成本远超 O(N)

预分配容量 = N / α + 1:
  → 一次到位，零扩容
  → 插入摊还成本最优
```

### 4.2 预分配公式

```java
// 预分配容量计算
int expectedSize = 10000;
// 容量 = expectedSize / 0.75 + 1（向上取整）
Map<String, Integer> map = new HashMap<>((int) (expectedSize / 0.75f) + 1);

// 简化记忆: capacity ≈ 1.34 × expectedSize
```

| 期望键数 | 默认容量过程 | 预分配容量 |
|---------|:---:|:---:|
| 1000 | 16→32→64→128→256→512→1024（6 次扩容） | 1334（0 次） |
| 10000 | 10 次扩容 | 13334 |
| 1000000 | 17 次扩容 | 1333334 |

> 💡 扩容次数公式：`⌈log₂(N/16)⌉` 次（默认初始 16）——100 万键约 17 次扩容；预分配直接归零。

## 5. 扩容与预分配实战

### 5.1 实战场景

```java
// 场景 1: 批量导入（预分配）
List<User> users = loadUsers();               // 已知 10 万
Map<Long, User> map = new HashMap<>((int) (users.size() / 0.75f) + 1);
for (User u : users) map.put(u.getId(), u);   // 零扩容

// 场景 2: 未知规模（预分配估算）
Map<String, String> map = new HashMap<>(1024);  // 给个合理初始

// 场景 3: 读多优化（低 α）
Map<String, Integer> map = new HashMap<>(1024, 0.5f);  // 更快更费空间
```

### 5.2 扩容问题排查表

| 症状 | 原因 | 对策 |
|------|------|------|
| 批量插入慢 | 多次扩容 | 预分配 |
| 大 Map 偶发卡顿 | 扩容抖动 | 预分配/分片 |
| 内存占用高 | α 太小 | 调大 α |
| 查找慢 | α 太大 | 调小 α/扩容 |
| GC 频繁 | 频繁扩容分配 | 预分配 |

**面试追问**：

| 追问 | 答题要点 |
|------|---------|
| 扩容代价？ | O(n) 重哈希，摊还 O(1) |
| JDK8 拆链原理？ | hash & oldCap 位判断去留 |
| 预分配公式？ | N/α + 1（≈1.34×N） |
| 扩容后 α？ | 0.75 → 0.375（性能重置） |
| 什么时候预分配？ | 已知规模/大集合/批量导入 |
| 扩容会反转链表吗？ | JDK8 保持原序（修 JDK7 死链） |

> 🎯 **核心要点**：本节验收——扩容触发（size > cap×α）、流程（×2 + 重哈希）、摊还 O(1) 论证；JDK8 位运算拆链（hash & oldCap → 原位/+oldCap，保持顺序）；预分配公式（N/α+1）与收益（扩容归零）；「扩容是性能重置」与「预分配是最佳实践」的工程双视角。
