# 01 - 装填因子的原理与影响

## 1. 装填因子的定义

**装填因子（Load Factor）**：`α = n / m`——键数 n 与桶数 m 的比值。

```text
α = 键数 / 桶数

例: 100 个键进 128 个桶 → α ≈ 0.78
    100 个键进 64 个桶  → α ≈ 1.56
    100 个键进 256 个桶 → α ≈ 0.39

工程直觉:
  α < 1: 桶比键多（空间宽松）
  α > 1: 键比桶多（链地址可容忍，定址危险）
```

| α 值 | 含义 | 场景 |
|:---:|------|------|
| 0.5 | 每桶平均 0.5 键 | 空间浪费但极快 |
| 0.75 | 每桶平均 0.75 键 | **工程默认** |
| 1.0 | 每桶平均 1 键 | 临界 |
| 2.0 | 每桶平均 2 键 | 链地址可容忍 |

> 💡 α 的物理意义：**平均每桶的键数**——α=0.75 即平均每桶 0.75 个键（约 47% 桶空、35% 桶 1 键）。

## 2. α 与性能的关系

### 2.1 α → 冲突频率 → ASL

```text
完整链条:
  α 增大 → 每桶键数增多 → 冲突概率上升 → ASL 上升

ASL（链地址）:
  成功: ASL ≈ 1 + α/2
  失败: ASL ≈ 1 + α

α 与 ASL 关系表:
  α=0.5  成功 1.25  失败 1.5
  α=0.75 成功 1.375 失败 1.75
  α=1.0  成功 1.5   失败 2.0
  α=2.0  成功 2.0   失败 3.0
```

### 2.2 α 的三种效应

| 效应 | 说明 | 危害 |
|------|------|------|
| 冲突增多 | 每桶键多 | ASL 上升 |
| 桶长偏斜 | 长链概率升 | 最坏退化 |
| 树化触发 | 桶长 ≥ 8 | 结构转换开销 |

> 🎯 **核心关系**：**α 线性影响 ASL**（α 翻倍 ASL 约翻倍）——这就是为什么 α 要保持「足够小」；但 α 太小空间浪费，所以「0.75 是折中」。

## 3. 0.75 的由来

### 3.1 Java HashMap 的默认值

```java
// HashMap 源码
static final float DEFAULT_LOAD_FACTOR = 0.75f;

// 扩容触发点: size > capacity × 0.75
// 例: 容量 16 → 12 个键时扩容
//     容量 128 → 96 个键时扩容
```

### 3.2 为什么是 0.75（三大理由）

```text
① 时空均衡:
   0.5 以下: 空间浪费 >50%
   0.75:     空间用 75%，ASL 仅 1.375
   1.0+:     空间用满，但冲突明显增多

② 泊松论证（随机哈希假设）:
   α=0.75 时桶长服从泊松分布:
     P(≥8) = 0.00000006（千万分之六）
   → 正常数据「不可能」触发树化
   → 0.75 让树化成为「异常信号」而非常态

③ 经验验证:
   大量基准测试表明 0.75 附近性能/空间比最优
```

> ⚠️ **面试必答**：0.75 不是拍脑袋——**时空均衡 + 泊松论证（树化阈值 8 的数学前提）**；读多场景可调低（如 0.5 更快更费空间）、写多场景可调高（如 1.0 省空间略慢）。

## 4. α 的时空权衡

### 4.1 权衡矩阵

```text
α 小（如 0.5）:
  + 冲突少、ASL 低、查找快
  - 空间浪费（一半桶空）

α 大（如 1.0）:
  + 空间利用率高
  - 冲突多、ASL 高、树化风险

α 的取值 = 时间成本 × 空间成本的折中
```

| α | 空间利用率 | ASL 成功 | 场景 |
|:---:|:---:|:---:|------|
| 0.5 | 50% | 1.25 | 读极多 |
| 0.75 | 75% | 1.375 | **通用** |
| 1.0 | 100% | 1.5 | 内存紧张 |
| 1.5+ | 超载 | 1.75+ | 链地址容忍 |

### 4.2 工程调 α

```java
// Java 手动指定装填因子
Map<String, Integer> map = new HashMap<>(16, 0.5f);    // 读多：更快更费空间
Map<String, Integer> map = new HashMap<>(16, 1.0f);    // 写多：省空间略慢

// 注意: 大多数场景用默认 0.75 即可
// 调 α 前先问: 是内存贵还是时间贵？
```

> 💡 调 α 的工程判断：**内存便宜选 0.5-0.75（读快）、内存紧张选 1.0（省空间）**；但 α 是「调音旋钮」不是「救火开关」——冲突爆炸时调 α 不如检查哈希函数。

## 5. 不同结构的 α 约束

### 5.1 链地址 vs 开放定址

| 维度 | 链地址 | 开放定址 |
|------|:---:|:---:|
| α 上限 | **可 > 1**（链表承担） | **必须 < 1**（满则死循环） |
| 推荐 α | 0.75（Java） | 0.5-0.7（Redis/Python） |
| α=1.5 | ✅ 可用（ASL 1.75） | ❌ 崩溃风险 |
| 扩容需求 | α > 1 也可撑 | 必须提前扩容 |

```text
开放定址的 α 硬约束:
  α → 1 时探测序列几乎全满 → 插入死循环
  因此开放定址 α 上限 ~0.7（预留空位）

链地址的 α 弹性:
  链表吸收超载 → α 1.5-2 仍可用（只是变慢）
  → 这是 Java 选链地址的原因之一
```

### 5.2 各语言默认 α

| 语言/容器 | α 默认 | 结构 |
|-----------|:---:|------|
| Java HashMap | 0.75 | 链地址 + 树 |
| Python dict | 0.66 | 开放定址 |
| Go map | 0.65（桶 8 槽） | 开放定址变体 |
| C++ unordered_map | 1.0 | 链地址 |
| Redis dict | 1.0（触发 rehash） | 链地址 |

> 🎯 **工程对比**：Java/C++（链地址）α 可以 ≥1；Python/Go（开放定址）α 必须 <0.7——**结构决定 α 约束**，这是哈希工程选型的重要维度。

**面试追问**：

| 追问 | 答题要点 |
|------|---------|
| α 定义？ | n/m（键/桶） |
| 0.75 为什么？ | 时空均衡 + 泊松论证 |
| α 与 ASL？ | 成功 ≈ 1+α/2 |
| 扩容时机？ | size > capacity × α |
| 开放定址 α 限制？ | 必须 < 1（死循环风险） |
| 什么时候调 α？ | 读多调低、内存紧调高 |

### 5.3 实践案例

```text
案例: 内存 1GB 存 1000 万用户 ID

α = 0.5:   桶 2000 万（约 160MB）→ 查找最快
α = 0.75:  桶 1334 万（约 107MB）→ 默认均衡
α = 1.0:   桶 1000 万（约 80MB）→ 内存最省

结论: 内存充足选 0.75，极端读多选 0.5
```

> 🎯 **核心要点**：本节验收——α = n/m 的定义与物理意义（平均每桶键数）；α → 冲突 → ASL 的链条（ASL ≈ 1+α/2）；0.75 的两大理由（时空均衡 + 泊松论证树化前提）；链地址（可 >1）与开放定址（必须 <1）的 α 约束差异；「内存便宜选小 α、内存紧张选大 α」的工程判断。
