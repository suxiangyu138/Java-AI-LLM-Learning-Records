## 1. 冲突的本质

**冲突（Collision）**：不同键经过哈希得到相同桶下标——**鸽笼原理保证冲突必然发生**（键域 > 桶域）。

```text
键域（无限）→ 桶域（有限）→ 必有多个键同桶

例: 键 1..10000，桶 100 个
  → 平均每桶 100 个键
  → 碰撞不可避免（除非完美哈希）

影响: 冲突导致桶内线性查找
  → 冲突严重时 O(1) 退化 O(n)
```

| 冲突程度 | 桶长 | 查找复杂度 |
|---------|:---:|:---:|
| 完美哈希 | 1 | O(1) |
| 正常哈希 | 0-3（泊松） | O(1) 平均 |
| 严重冲突 | n | **O(n) 退化** |
| 恶意冲突 | n（全同桶） | O(n) 攻击 |

> 💡 冲突不可消除，只能**控制**——好的哈希函数（01 模块）+ 好的冲突策略（本模块）+ 合理的装填因子（[装填因子 α](../装填因子 α/)专题）。

## 2. 冲突解决的三种策略

### 2.1 链地址法（Chaining，Java HashMap）

```java
// 链地址法：同桶元素用链表/红黑树串联
// Java HashMap: 链表 → 树化（≥8 且容量 ≥64）→ 退化（≤6）
Map<Integer, String> map = new HashMap<>();

// 桶结构:
// [0] → null
// [1] → ("a",v1) → ("i",v2) → null     ← 链
// [2] → null
```

| 特性 | 说明 |
|------|------|
| 结构 | 桶数组 + 链表/树 |
| 优点 | 实现简单、删除容易、装填因子可 >1 |
| 缺点 | 指针开销、缓存不友好 |
| 树化 | 链表 ≥ 8 且容量 ≥ 64 转红黑树 |

### 2.2 开放定址法（Open Addressing）

```text
冲突时探测下一个空位:
  线性探测: idx = (h(k) + i) mod m     ← 简单但聚集
  二次探测: idx = (h(k) + i²) mod m    ← 减少聚集
  双重哈希: idx = (h1(k) + i·h2(k)) mod m ← 最好

例（线性探测，m=7）:
  插入 10(h=3), 17(h=3 冲突), 24(h=3 冲突)
  10 → 桶3；17 → 桶4（探测）；24 → 桶5（再探测）
```

| 对比 | 链地址 | 开放定址 |
|------|:---:|:---:|
| 空间 | 数组 + 指针 | 纯数组 |
| 删除 | 容易 | 需「墓碑」标记 |
| 装填因子 | 可 > 1 | **必须 < 1**（满则死循环） |
| 缓存 | 差 | 好（连续数组） |
| 工程 | Java HashMap | 删除频繁场景 |

### 2.3 再哈希（Rehashing）

```text
h(k) 冲突时用第二个哈希函数:
  idx = h1(k) 冲突 → h2(k) → h3(k) ...

优点: 更均匀
缺点: 计算多次哈希（变慢）
```

> 🎯 **记忆**：链地址 = 挂链（Java 默认）、开放定址 = 找空位（Redis 字典）、再哈希 = 换函数——三策略对应三种工程权衡。

## 3. HashDoS 攻击

**HashDoS（哈希碰撞拒绝服务）**：攻击者构造大量**同哈希值的键**——使哈希表退化为链表，插入/查询 O(n) → CPU 耗尽。

```text
攻击流程:
① 找到哈希函数的碰撞模式（如 Java String: 31 倍可反推）
② 构造 N 个同哈希字符串
③ 全部插入服务器 HashMap → 全部进同一桶（链表）
④ 每次查询 O(n) → 服务器 CPU 100%

经典案例: 2003 年 PHP/Java 哈希碰撞 DoS（URL 参数名攻击）
```

**三层防御**：

| 层级 | 防御 | 原理 |
|------|------|------|
| ① 随机种子 | 哈希起点随机化 | 攻击者无法预知碰撞模式 |
| ② 树化 | 链表 ≥ 8 转红黑树 | 最坏 O(n) → O(log n) |
| ③ 布隆前置 | 快速拒绝异常键 | 空间换时间拦截 |

```java
// Java 8+ 的防御（内建）
// ① String 哈希种子随机（JVM 启动时）
// ② HashMap 链表树化（≥8 且容量 ≥64）
// ③ 字符串哈希的「惰性」缓存

// 应用层防御：限制输入长度/频率
if (param.length() > 64) { reject(); }        // 长键是攻击特征
rateLimit("hash-requests", 100, 1, TimeUnit.SECONDS);
```

> ⚠️ **面试必答**：HashMap 树化不是性能优化而是**安全防御**——正常数据链表 ≥ 8 概率千万分之六（01 模块泊松论证），达到 8 说明哈希失效（大概率是攻击）。

## 4. 布隆过滤器

**布隆过滤器（Bloom Filter）**：位数组 + 多个哈希函数——**空间极小**的「可能存在」判断器（允许误判、不允许漏判）。

```java
// 布隆过滤器实现
class BloomFilter {
    private final BitSet bits = new BitSet(1 << 20);   // 位数组
    private static final int[] SEEDS = {3, 7, 11, 17}; // 多哈希种子

    void add(String key) {
        for (int seed : SEEDS) {
            int hash = (key.hashCode() * seed) & 0x7fffffff;
            bits.set(hash % bits.size());              // 多个位置 1
        }
    }

    boolean mightContain(String key) {
        for (int seed : SEEDS) {
            int hash = (key.hashCode() * seed) & 0x7fffffff;
            if (!bits.get(hash % bits.size())) return false;  // 有位为 0 = 必不存在
        }
        return true;                                   // 全为 1 = 可能存在
    }
}
```

| 特性 | 说明 |
|------|------|
| 误判（假阳性） | 可能说「存在」实为不存在（位被其他键置 1） |
| 漏判（假阴性） | **绝不可能**（存在则所有位必为 1） |
| 删除 | 不支持（可计数布隆） |
| 空间 | 每个键 ~10 位（vs 哈希表几十字节） |

**误判率公式**：

```text
m 位、k 个哈希、n 个键:
  误判率 p ≈ (1 - e^(-kn/m))^k
  最优 k = (m/n)·ln2 ≈ 0.693·(m/n)

例: m/n = 8（每键 8 位）→ p ≈ 2%
     m/n = 16 → p ≈ 0.04%
```

**工程应用**：

| 场景 | 用法 |
|------|------|
| 缓存穿透 | 查询前先问布隆（不存在直接拒绝） |
| 黑名单 | 空间亿级键的快速判断 |
| LevelDB/RocksDB | SSTable 键存在性预筛 |
| 爬虫去重 | URL 是否已访问 |
| 反垃圾 | 邮件/评论快速过滤 |

> 💡 布隆过滤器的价值：**用少量误判换空间数量级下降**——10 亿键只需 ~1GB 位数组；「宁可错杀（假阳性）、不可放过（假阴性）」的场景是它的主场。

## 5. 工程防御全景

| 风险 | 防御手段 | 层级 |
|------|---------|------|
| 键模式聚集 | 质数取模 / 扰动函数 | 哈希函数 |
| 恶意碰撞 | 随机种子 + 树化 | JVM 内建 |
| 缓存穿透 | 布隆过滤器 | 应用层 |
| 长键攻击 | 输入长度限制 | 网关 |
| 高频攻击 | 限流 | 网关 |
| 慢哈希滥用 | 拒绝加密哈希当表哈希 | 设计 |

**哈希函数选型速查**：

```text
整数键       → 质数取模 / (n-1)&hash（2 的幂）
字符串键     → Java hashCode（31 倍）
对象键       → 31 倍组合 + equals 配套
分布式分配   → 一致性哈希（环 + 虚拟节点）
存在性预筛   → 布隆过滤器（多哈希 + 位数组）
安全场景     → SHA-256 等加密哈希（不可作表哈希）
```

> 🎯 **核心要点**：本节验收——冲突必然性（鸽笼原理）与三策略（链地址/开放定址/再哈希）；HashDoS 攻击链（碰撞构造 → 全同桶 → O(n) 退化）与三层防御（随机种子/树化/布隆）；布隆过滤器的「可误判不可漏判」特性与误判率公式；工程选型速查表；衔接[哈希冲突](../哈希冲突/)（解决策略专题）与[装填因子 α](../装填因子 α/)（性能量化）。
