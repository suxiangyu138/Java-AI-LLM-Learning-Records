## 1. 选型决策树

```text
数据结构选型
├── 需要按键取值？
│   ├── 需要有序/区间 → 红黑树（TreeMap）
│   ├── 键是连续整数 → 数组
│   └── 纯取值（无序） → 哈希表（HashMap）
├── 需要有序遍历/区间？
│   ├── 内存 → 红黑树/跳表
│   └── 磁盘 → B+ 树（数据库）
├── 需要最坏保证（防攻击）？
│   ├── 是 → 红黑树（O(log n)）
│   └── 否 → 哈希表（O(1) 平均）
├── 需要 O(1) 头尾操作？
│   └── 双端队列（ArrayDeque）
└── 需要任意位置 O(1) 插删？
    └── 链表（已知位置）
```

**决策口诀**：

```text
速度优先 → 哈希（O(1) 平均）
有序优先 → 红黑树/跳表
保证优先 → 红黑树（最坏 O(log n)）
区间优先 → 跳表/TreeMap
缓存优先 → 数组
组合需求 → 组合结构（哈希+链表=LRU）
```

> 🎯 **选型本质**：没有万能结构——每次选型都是一次「复杂度 × 有序性 × 保证 × 缓存」的加权决策。

## 2. 工程案例库

### 2.1 案例总表

| 场景 | 选择 | 结构 | 理由 |
|------|------|------|------|
| 用户 Session | HashMap | 哈希 | 按键取值 |
| 排行榜 | TreeMap | 红黑树 | 有序 + 取极值 |
| LRU 缓存 | LinkedHashMap | 哈希+链表 | O(1) 查找+移动 |
| 数据库索引 | B+ 树 | B 树 | 磁盘 I/O |
| 消息去重 | HashSet | 哈希 | O(1) 判存在 |
| 路由表 | Radix Tree | Trie | 前缀匹配 |
| 单词频率 | HashMap | 哈希 | 计数 |
| 范围统计 | TreeMap.subMap | 红黑树 | 区间 |
| 最近访问 | LinkedHashSet | 哈希+链 | 保序去重 |
| 分布式分配 | 一致性哈希 | 哈希环 | 最小迁移 |

### 2.2 三个经典案例详解

```java
// 案例 1: LRU 缓存（哈希 + 链表）
// LinkedHashMap 一行实现
class LRUCache extends LinkedHashMap<Integer, Integer> {
    private final int capacity;

    LRUCache(int capacity) {
        super(capacity, 0.75f, true);        // accessOrder=true: 访问排序
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
        return size() > capacity;            // 超容量淘汰最久未用
    }
}
// 哈希 O(1) 定位 + 链表 O(1) 移动 = LRU ✓
```

```java
// 案例 2: 排行榜（红黑树）
TreeMap<Integer, List<String>> scoreBoard = new TreeMap<>();
scoreBoard.put(100, List.of("Alice"));       // 分数 → 玩家
scoreBoard.put(95, List.of("Bob"));
int top = scoreBoard.lastKey();              // 最高分 O(log n)
NavigableMap<Integer, List<String>> top10 =
    scoreBoard.descendingMap();              // 倒序（排行榜）

// 有序 + 极值 = 红黑树的舞台
```

```java
// 案例 3: 范围统计（红黑树区间）
TreeMap<Long, Integer> orders = new TreeMap<>();   // 时间戳 → 订单数
long start = System.currentTimeMillis() - 86400000L;
long end = System.currentTimeMillis();
Map<Long, Integer> last24h =
    orders.subMap(start, true, end, true);   // 区间查询 O(log n + k)
// 哈希表做不到区间——这是 TreeMap 不可替代的场景
```

> 💡 三个案例覆盖三种「哈希做不到」的能力：LRU（组合）、排行榜（有序极值）、区间统计（subMap）——**哈希不是终点，组合与有序结构才是工程全貌**。

## 3. 复杂度权衡精讲

### 3.1 时空权衡

```text
空间 × 时间矩阵:

哈希表:   空间 O(n) → 时间 O(1) 平均（空间换时间）
红黑树:   空间 O(n)+指针 → 时间 O(log n) 保证
数组:     空间 O(n) 连续 → 时间 O(1) 下标
链表:     空间 O(n)+指针 → 时间 O(1) 已知位置插删
跳表:     空间 O(n log n) → 时间 O(log n) 平均
```

### 3.2 数据规模的影响

| 规模 | 哈希优势 | 树优势 |
|:---:|---------|--------|
| 小（<1000） | 不明显（常数主导） | 缓存友好可能更快 |
| 中（10⁴-10⁶） | **O(1) 优势明显** | O(log n) 可接受 |
| 大（>10⁶） | 内存压力（桶数组） | 指针开销 |
| 超大（分布式） | 一致性哈希 | B+ 树（磁盘） |

> ⚠️ **小数据陷阱**：n < 1000 时哈希的 O(1) 优势可能被常数抵消——线性扫描/数组有时更快（缓存友好）；「O(1) vs O(log n)」只在数据量足够大时才有意义。

### 3.3 混合场景的复杂度

```text
场景: 日志系统「按键查 + 时间范围查」
方案 1（单结构）: 哈希（有键查无区间）✗
方案 2（单结构）: TreeMap（有区间 O(log n) 键查）△
方案 3（双结构）: HashMap + TreeMap 冗余 ✓
  键查: HashMap O(1)
  区间: TreeMap O(log n + k)

启示: 混合需求用「多结构冗余」——空间换多能力
```

## 4. 面试选型话术

| 面试问题 | 标准答案 |
|---------|---------|
| HashMap 和 TreeMap 怎么选？ | 纯按键取值哈希；有序/区间/最坏保证 TreeMap |
| 哈希为什么不万能？ | 无序 + 无最坏保证 + 空间开销 |
| LRU 为什么哈希+链表？ | 哈希 O(1) 定位 + 链表 O(1) 移动 |
| 排行榜用什么？ | TreeMap（有序 + lastKey 极值） |
| 区间查询为什么不用哈希？ | 哈希无序无法区间——TreeMap.subMap |
| 跳表 vs 红黑树？ | 跳表简单 + 区间友好（Redis ZSet） |
| 什么时候数组快于哈希？ | 键连续整数 + 缓存敏感 |
| 数据库为什么 B+ 树？ | 磁盘 I/O 次数 = 树高 |
| 选型总原则？ | 先问需求（取值/有序/区间/保证）再选结构 |

**面试话术模板**：

```text
「选型先问三个问题:
  ① 需要按键取值吗？→ 哈希（无序）/树（有序）
  ② 需要最坏保证吗？→ 红黑树（O(log n)）
  ③ 需要区间/有序吗？→ 树/跳表（哈希做不到）
  三个答案组合 → 结构确定」
```

> 🎯 **面试亮点**：能主动说出「先问需求再选结构」的框架 + 三个经典案例（LRU/排行榜/区间统计）——比背复杂度表高一个段位。

## 5. 选型速记卡

```text
五结构一句话:
  哈希: O(1) 平均 · 无序 · 速度王
  数组: O(1) 下标 · 缓存王 · 连续键
  链表: O(1) 已知插删 · LRU 搭档
  红黑: O(log n) 保证 · 有序 · TreeMap
  跳表: O(log n) 平均 · 区间 · Redis

选型四句:
  要速度 → 哈希
  要有序 → 树
  要保证 → 红黑
  要区间 → 跳表/TreeMap

工程组合:
  哈希 + 链表 = LRU
  哈希 + 树 = 键查 + 区间
  数组 + 哈希 = 下标 + 键查
```

> 🎯 **核心要点**：选型验收——决策树闭眼可走（取值/有序/保证/区间四问）；三个工程案例（LRU 组合/排行榜/区间统计）能讲透；小数据陷阱（n<1000 常数主导）与混合场景（多结构冗余）；面试话术框架（先问需求再选结构）；至此哈希 6 个主题目录全部完成——哈希体系闭环。
