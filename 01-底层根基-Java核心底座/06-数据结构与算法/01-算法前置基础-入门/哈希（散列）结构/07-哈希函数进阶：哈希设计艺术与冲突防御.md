## 1. 哈希函数的设计原则

### 1.1 五大原则

| 原则 | 含义 | 反例 |
|------|------|------|
| 确定性 | 同一输入必然同一输出 | 用随机数做哈希 |
| 均匀性 | 输出在值域均匀分布 | 只取低 8 位 |
| 高效性 | 计算开销小 | 对整个对象做加密哈希 |
| 雪崩效应 | 输入微变 → 输出剧变 | 返回 length % 10 |
| 一致性 | 与 equals 协作（Java 对象） | equals 变了 hash 不变 |

```
⚠️ Java 对象哈希的特有约束：
  equals 相等 → hashCode 必须相等（契约）
  参与哈希的字段必须是不可变的（或不可变时缓存）

⚠️ 工程哈希的取舍：
  均匀性 > 雪崩效应 > 高效性
  哈希表场景：分布均匀最重要（决定链表长度分布）
```

### 1.2 三类哈希的定位（核心认知）

| 类型 | 目标 | 代表 | 用途 |
|------|------|------|------|
| 非加密哈希 | 快 + 均匀 | Murmur3、31 多项式 | 哈希表、分片 |
| 加密哈希 | 不可逆 + 抗碰撞 | SHA-256、SHA-3 | 完整性、签名 |
| 密码哈希 | 慢 + 内存硬 | Argon2、bcrypt | 密码存储 |

> 💡 **关键区分**：哈希表要"快"，完整性要"强"，密码要"慢"。三者不可混用。完整体系见 [Java有关Hash的一切](../../../01-Java基础语法与核心特性/Java有关Hash的一切/00-Hash总览.md)。

## 2. 设计实例：String 的 31 与 Murmur

### 2.1 String.hashCode：31 的工程智慧

```java
// JDK String.hashCode：h = 31·h + c（加权多项式）
int hash = 0;
for (char c : value) hash = 31 * hash + c;

// 为什么 31：
//   ① 奇素数 → 乘偶数会丢失低位信息
//   ② JVM 优化：31·h = (h << 5) - h（移位+减法）
//   ③ 分布与性能的经验折中（Effective Java 实测）
```

### 2.2 常用哈希函数对比

| 函数 | 原理 | 均匀性 | 速度 | 适用 |
|------|------|:---:|:---:|------|
| 31 多项式 | 加权和 | 良 | 快 | String（JDK 内置） |
| DJB2 | h = h·33 + c | 良 | 快 | 通用字符串 |
| FNV-1a | 异或+乘 | 良 | 快 | 通用 |
| Murmur3 | 混合字节块 | 优 | 快 | Guava/分片/布隆 |
| xxHash | 高速混合 | 优 | 极快 | 大数据量 |

```
⚠️ 面试表达：
"String 用 31 加权多项式——质数乘子 + JVM 移位优化，
 分布和性能均衡。工程上追求更均匀的分布
 用 Murmur3（Guava Hashing.murmur3_32()）。"
```

### 2.3 劣质哈希的代价

```
哈希质量 → 桶分布 → 操作复杂度：
  均匀哈希：期望 O(1)
  劣质哈希：数据挤进少数桶 → 链表长 → O(n)

量化：n 个元素 m 个桶，均匀时最长链表 ≈ log n / log log n
       全挤一桶 → 链表 = n → 查询 O(n)

⚠️ 面试表达：
"哈希质量决定期望复杂度——均匀分布是 O(1) 的前提。
 固定值哈希（return 1）是最恶劣的实现：所有元素同桶。"
```

## 3. 冲突解决：链地址 vs 开放寻址

### 3.1 两种方案对比

| 维度 | 链地址（HashMap） | 开放寻址 |
|------|:---:|:---:|
| 结构 | 数组 + 链表/树 | 纯数组（线性探测等） |
| 冲突处理 | 同桶挂链 | 顺延找下一个空位 |
| 删除 | 简单（摘链） | ⚠️ 复杂（不能直接置空，需墓碑） |
| 缓存友好 | 链表节点跳跃 | ✅ 数组连续 |
| 装载因子上限 | 0.75（链表）/0.5（树化前） | ≤ 0.5-0.7（超过急剧退化） |
| 代表 | HashMap | IdentityHashMap、Redis 字典、Java 的 ThreadLocalMap |

```
线性探测的删除陷阱：
  删除中间元素后直接置 null → 后续探测链断裂
  → 必须用"墓碑"（标记删除）或惰性删除

⚠️ 面试表达：
"链地址对删除友好、对缓存不友好（节点分散）；
 开放寻址对缓存友好（连续数组）但对删除敏感。
 HashMap 选链地址——工程上删除频繁，树化兜底
 恶意输入；开放寻址用在装载率可控的字典。"
```

### 3.2 Java 中的开放寻址实例

```java
// IdentityHashMap：线性探测（引用哈希）
// ThreadLocalMap：线性探测（ThreadLocal 弱引用键）
// ⚠️ 两者的共同点：元素少、生命周期短 → 开放寻址内存紧凑
```

## 4. 负载因子与扩容策略

### 4.1 负载因子（load factor）的本质

```
负载因子 α = 元素数 / 桶数
α 决定冲突密度：
  α = 0.75：期望链长 0.75，性能与空间的折中点
  α → 1：冲突剧增，性能断崖
  α → 0：空间浪费严重

⚠️ HashMap 选 0.75 的依据：
  泊松分布：α=0.75 时链长 ≥ 8 的概率 < 1e-8
  （树化阈值 8 的数学来源）

⚠️ 不同结构的推荐 α：
  链地址：0.75（可容忍）
  开放寻址线性探测：≤ 0.5（超过急剧退化）
  Cuckoo 哈希：≈ 0.5（最多两次哈希）
```

### 4.2 扩容策略对比

| 策略 | 做法 | 代价 | 代表 |
|------|------|------|------|
| 倍增扩容 | 容量 ×2（2 的幂） | 全量重哈希 O(n) | HashMap |
| 素数扩容 | 容量选素数 | 重哈希但分布更均匀 | Hashtable（2n+1） |
| 渐进式扩容 | 分多次迁移（每次操作搬一点） | 单次 O(1) | Redis 字典 |
| 无扩容 | 容量固定 | 链无限长 | 小字典 |

```
⚠️ 渐进式扩容（Redis 的做法）：
  扩容不是一次完成——每次增删查顺带迁移几个桶
  避免"一次扩容卡顿"（大字典全量迁移毫秒级停顿）
  ⚠️ 面试表达："大字典全量扩容会卡顿；
   渐进式扩容把迁移摊到每次操作，单次 O(1)。"
```

### 4.3 初始容量实践

```java
// 预期放入 n 个元素：
// 容量 ≥ n / 0.75 才能避免扩容 → 建议 n·4/3 + 1
Map<String, Integer> map = new HashMap<>(expected / 3 * 4 + 1);
// ⚠️ 面试表达："初始化给足容量避免中途扩容——
//   扩容是 O(n) 全量重哈希，频繁扩容浪费严重。"
```

## 5. HashDoS 与防御体系

### 5.1 攻击原理

```
攻击者构造大量"哈希相同"的 key（String.hashCode 公式公开可逆推）
→ 全部落入同一桶 → 链表爆长 → 插入/查找 O(1) → O(n)
→ CPU 打满 → 拒绝服务（DoS）

⚠️ 攻击面：请求参数 Map、JSON 解析、Cookie 等
  任何"用户可控 key 进哈希表"的入口
```

### 5.2 四层防御体系

| 层次 | 手段 | 说明 |
|------|------|------|
| ① 树化兜底 | 链表 ≥8 且容量 ≥64 → 红黑树 | 最坏 O(log n)（JDK 8+） |
| ② 随机化 | 哈希种子启动时随机 | 碰撞集无法预计算 |
| ③ 输入限制 | 参数数/长度限制、DTO 代替 Map | 应用层第一道门 |
| ④ 边缘防护 | 限流、WAF、maxParameterCount | 网络层兜底 |

```
⚠️ 完整内容见 [05-哈希碰撞攻击与HashDoS](../../../01-Java基础语法与核心特性/Java有关Hash的一切/05-哈希碰撞攻击与HashDoS.md)
```

> 🎯 **面试必答**："JDK 8 的树化把 HashDoS 从 O(n) 兜到 O(log n)；随机化种子让预计算碰撞集失效；但应用层仍要用 DTO 替代 Map 接参、限制参数数量——纵深防御。"

## 6. 哈希的工程应用全景

### 6.1 应用矩阵

| 应用 | 哈希的角色 | 关键点 |
|------|-----------|--------|
| HashMap/HashSet | 定位桶 | 均匀 + 冲突解决 |
| 布隆过滤器 | 位图定位 | 不误漏判只可能误判 |
| 一致性哈希 | 节点路由 | 扩缩容只影响 1/n |
| 缓存键 | 数据定位 | Redis key 设计 |
| 去重 | 指纹 | 内容哈希（MD5/SHA） |
| 负载均衡 | 会话粘滞 | ip_hash 一致性 |
| 安全 | 密码/签名 | Argon2/SHA-256/HMAC |

### 6.2 哈希的经典变形

```
① 布隆过滤器：m 位 + k 哈希 → 空间换误判率
   → 详细见 [06-工程实践一致性哈希与布隆过滤器](../../../01-Java基础语法与核心特性/Java有关Hash的一切/06-工程实践一致性哈希与布隆过滤器.md)
② 一致性哈希：环 + 虚拟节点 → 分布式扩缩容
③ 双重哈希：两个哈希函数 → 布隆过滤器/双哈希表
④ 完美哈希：静态集合 → 无碰撞（编码式，如 DNA 4 进制）
```

## 7. 哈希的分布式形态

### 7.1 分片哈希家族

| 方案 | 规则 | 特点 |
|------|------|------|
| 取模 | hash % n | 简单但扩容全量重排 |
| 一致性哈希 | 环 + 虚拟节点 | 扩容只影响 1/n |
| 固定槽 | CRC16 % 16384 | Redis Cluster（槽迁移） |
| 分桶 | 桶哈希 + 桶内再哈希 | 两级路由 |

### 7.2 哈希与数据结构的融合

```
哈希 + 其他结构 = 复合数据结构：
  哈希 + 链表 = LinkedHashMap（LRU）
  哈希 + 数组 = 380 题（O(1) 随机获取）
  哈希 + 双向链表 = LRU Cache（146）
  哈希 + 二叉堆 = 前 K 高频（347）
  哈希 + 前缀树 = 自动补全

⚠️ 面试表达：
"哈希给出 O(1) 查找，链表/堆给出顺序或最值，
 复合结构是 LeetCode 高频设计题（146/380/460）的
 标准答案——两个结构各司其职、指针互指。"
```

## 8. 面试要点与追问

### 8.1 面试话术模板

```
"哈希函数要均匀、高效、确定。冲突解决选型：
 链地址（HashMap）删除友好，开放寻址缓存友好但删除复杂。
 负载因子 0.75 是时空折中（泊松分布支撑树化阈值 8）。
 恶意输入有 HashDoS 风险 → 树化 + 随机化 + 输入层防御。
 分布式的哈希用一致性哈希/固定槽，见专门模块。"
```

### 8.2 高频追问 TOP 8

| # | 追问 | 标准回答 |
|:---:|------|------|
| 1 | 哈希函数要满足什么？ | 确定/均匀/高效/雪崩 + equals 契约 |
| 2 | 链地址 vs 开放寻址？ | 删除友好 vs 缓存友好；删除敏感 |
| 3 | 负载因子为什么 0.75？ | 时空折中；泊松分布支撑树化阈值 |
| 4 | 扩容代价？ | O(n) 重哈希；渐进式扩容摊薄 |
| 5 | HashDoS 怎么防？ | 树化 + 随机种子 + 输入限制 + 边缘防护 |
| 6 | 劣质哈希代价？ | 全挤一桶 → O(n) |
| 7 | 编码式完美哈希？ | 字符集小 + 长度短 → 进制数直接表示 |
| 8 | 哈希复合结构？ | 哈希+链表/堆/数组 → 146/380/347 |

### 8.3 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 固定值哈希 | 全部同桶 O(n) | 组合字段 + 质数乘子 |
| 开放寻址直接置空删除 | 探测链断裂 | 墓碑标记 |
| 初始容量过小 | 频繁扩容 | n/0.75 + 1 |
| 哈希表用加密哈希 | 性能暴跌 | 非加密哈希（Murmur） |
| 忽略 HashDoS | 线上被拖垮 | 纵深防御 |

> 🎯 **核心要点**：哈希函数 = **均匀性**（设计）+ **冲突解决**（链/开放寻址）+ **负载控制**（0.75 与扩容）+ **安全**（HashDoS 防御）。工程应用四兄弟——布隆、一致性哈希、复合结构、分布式分片——各有专门体系承接。
