## 1. 为什么需要 B 树

**问题的根源：磁盘比内存慢 10⁵ 倍**。

```text
内存访问:   ~100ns（纳秒）
磁盘 I/O:   ~10ms（毫秒）
差距:       100,000 倍！

平衡二叉树（内存）:  10 亿数据树高 ~30 层
  → 每次查找 30 次指针跳转（内存纳秒级）✓ 可接受

但如果树在磁盘上:
  → 每次访问节点 = 一次磁盘 I/O（毫秒级）
  → 30 次 I/O = 300ms！查询一次要 0.3 秒 ✗ 灾难
```

**B 树的解法**：**一个节点装几百个键**（一页 = 16KB 能装 ~1000 键）→ 树高从 30 降到 3-4 → **3-4 次磁盘 I/O 完成查找**。

| 结构 | 树高（10 亿数据） | 磁盘 I/O 次数 |
|------|:---:|:---:|
| 红黑树/AVL | ~30-60 层 | 30-60 次 ❌ |
| B 树（页 1000 键） | 3 层 | **3 次** ✅ |
| B+ 树（页 1000 键） | 3 层 | **3 次** ✅ |

> 🎯 **核心动机一句话**：**「树高 = 磁盘 I/O 次数」——B 树用「节点多键」换「树更矮」，把 I/O 从几十次降到个位数**。

## 2. B 树的定义与阶

**B 树（B-Tree）**：满足以下性质的**多路平衡搜索树**（1960 年代发明，B 常被认为代表 Balanced/Bayer）：

| 性质 | 说明 |
|------|------|
| ① 多路 | 每个节点最多 m 个孩子（m 为**阶**） |
| ② 有序 | 节点内键升序；孩子间隔对应键区间 |
| ③ 平衡 | **所有叶子在同一层**（完美平衡） |
| ④ 键数约束 | 非根节点键数 ∈ [⌈m/2⌉-1, m-1] |
| ⑤ 根特例 | 根节点至少 1 个键（可不满） |

```text
m=5 的 B 树（每个节点 2-4 个键，3-5 个孩子）:

                [20 | 40 | 60 | 80]           ← 根（可不满）
               /    |     |     |    \
        [10|15] [25|30] [45|50] [65|70] [85|90|95]
        叶子全部同层 ✓
```

**B 树 vs 二叉搜索树**：

| 维度 | BST | B 树 |
|------|-----|------|
| 每节点键数 | 1 | **m-1 个** |
| 孩子数 | 2 | **m 个** |
| 树高 | log₂n | **log_B n** |
| 平衡 | 可能退化 | 完美平衡（叶子同层） |
| 存储介质 | 内存 | **磁盘（页）** |

> 💡 记忆：**BST 是 m=2 的 B 树特例**——B 树是二叉搜索树的多路一般化。

## 3. 键数范围与节点结构

### 3.1 键数约束（核心公式）

```text
阶 m 的 B 树:

非根节点:   ⌈m/2⌉ - 1 ≤ 键数 ≤ m - 1
            ⌈m/2⌉   ≤ 孩子数 ≤ m

根节点:     1 ≤ 键数 ≤ m - 1

例: m=5 → 非根键数 2-4，孩子数 3-5
    m=4 → 非根键数 1-3（这就是 2-3-4 树！）
```

> ⚠️ **为什么是 ⌈m/2⌉-1**：保证删除时「借键/合并」总有兄弟可处理——**一半是平衡的底线**（类似红黑树的黑高约束）。

### 3.2 节点结构

```java
// B 树节点的概念结构（一个节点 = 一个磁盘页）
class BTreeNode {
    int[] keys;              // 键数组（有序，最多 m-1 个）
    BTreeNode[] children;    // 孩子指针（最多 m 个）
    int keyCount;            // 当前键数
    boolean isLeaf;          // 是否叶子
}
```

```text
节点内结构（m=5，4 个键 5 个孩子）:

        [ k1 | k2 | k3 | k4 ]
       /     |    |    |     \
     c1    c2   c3   c4     c5

区间语义: c1 子树所有键 < k1 < c2 子树所有键 < k2 < ...
```

> 💡 一个节点 = **一个磁盘页**（InnoDB 16KB）——读一个节点就是一次页 I/O；节点内键有序 → 可用二分查找。

## 4. 树高公式与 I/O 分析

### 4.1 树高上界

```text
阶 m 的 B 树，n 个键，树高 h:

h ≤ log_⌈m/2⌉((n+1)/2) + 1

直觉: 每层至少 ⌈m/2⌉ 个分支（键数下限保证）
      → 节点数指数增长 → 树高对数级

m=1000（页装 ~1000 键）:
  n = 10 亿 → h ≈ 3 层
  n = 1 万亿 → h ≈ 4 层
```

### 4.2 实际 I/O 成本估算

```text
MySQL InnoDB: 页 16KB，主键 8 字节 + 指针 6 字节
→ 每页可装约 1000+ 个键

1 亿行数据:
  B+ 树: 树高 3 层 = 根（常驻内存）+ 2 次磁盘 I/O
  → 单行查询 ~2 次 I/O ≈ 20ms（vs 红黑树 60 次 = 600ms）

对比: B 树把查询从「秒级」降到「毫秒级」——30 倍差距
```

| 数据量 | 红黑树 I/O | B+ 树 I/O | 差距 |
|--------|:---:|:---:|:---:|
| 100 万 | ~20 次 | 2-3 次 | ~7× |
| 10 亿 | ~30 次 | 3 次 | ~10× |
| 1 万亿 | ~40 次 | 4 次 | ~10× |

> 🎯 **面试必答**：10 亿数据用 B+ 树只需 **3-4 次磁盘 I/O**——根节点常驻内存（1 次内存访问），真正磁盘 I/O 只有 2-3 次。

## 5. B 树与 2-3-4 树/红黑树

### 5.1 三者关系

```text
2-3-4 树:  m=4 的 B 树特例（每节点 1-3 键）
    ↓ 二叉化
红黑树:    2-3-4 树的二叉树编码（红节点 = 附加键）
    ↓ 一般化
B 树:     任意阶 m 的多路平衡树

关系: B 树 ⊇ 2-3-4 树 ⊇（等价）红黑树
```

| 树 | 阶 | 每节点键数 | 树高 | 场景 |
|----|:---:|:---:|:---:|------|
| 红黑树 | 2 | 1 | 2·log₂n | 内存通用容器 |
| 2-3-4 树 | 4 | 1-3 | log₄n | 教学（红黑树前身） |
| B 树 | 100-2000 | m-1 | log_B n | 磁盘索引 |

### 5.2 分裂/合并与旋转的对应

| B 树操作 | 红黑树对应 |
|---------|-----------|
| 插入分裂（中键上提） | 叔叔红 → 变色上提 |
| 删除合并（下溢） | 兄弟黑 → 变色上移 |
| 删除借键 | 兄弟红 → 旋转借键 |

> 💡 **概念打通**：红黑树的旋转/变色 = B 树分裂/合并的二叉树编码——学完 B 树回头看红黑树，修复逻辑豁然开朗（红黑树体系 02 模块的等价关系正是此意）。
