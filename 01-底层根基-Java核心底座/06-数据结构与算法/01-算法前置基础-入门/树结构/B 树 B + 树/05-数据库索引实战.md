## 1. InnoDB 索引结构

**InnoDB 的索引 = B+ 树**，表数据存储在两个结构中：

```text
InnoDB 存储结构:
  ├── 聚簇索引（主键索引）: 叶子存「整行数据」
  └── 二级索引（普通索引）: 叶子存「主键值」

页大小: 16KB（一页一个 B+ 树节点）
主键: 8 字节 BIGINT + 6 字节指针 = 14 字节
→ 每页约 1170 个键 → 树高 3 层 ≈ 2000 万行
→ 树高 4 层 ≈ 20 亿行
```

```text
聚簇索引（主键 id）:
        [id 路由层]          ← 内部节点（纯键）
       /   |    \
    [1|2] [5|6] [9|10]      ← 叶子（整行数据: id+name+age...）
     ↓ ↓     ↓
   (1,张三) (5,王五) ...

二级索引（name）:
        [name 路由层]
       /    |    \
    [张三] [李四] [王五]     ← 叶子（存主键 id）
      ↓      ↓      ↓
    id=1   id=3   id=5      ← 指向聚簇索引
```

> 🎯 **核心认知**：**InnoDB 的表 = 一棵以主键为序的 B+ 树**（聚簇索引）——「表即索引」，这就是为什么主键必须存在且唯一。

## 2. 聚簇索引 vs 二级索引

| 维度 | 聚簇索引 | 二级索引 |
|------|---------|---------|
| 谁建的 | 主键（自动） | 普通索引（手动） |
| 叶子内容 | **整行数据** | **主键值** |
| 数量 | **只有 1 个** | 可多个 |
| 查找 | 一次 B+ 树 | 两次（+回表） |
| 数据有序 | 按主键物理有序 | 逻辑有序 |

```sql
-- 聚簇索引直接命中（一次 B+ 树）:
SELECT * FROM users WHERE id = 5;

-- 二级索引需回表（两次 B+ 树）:
SELECT * FROM users WHERE name = '张三';
-- ① name 索引找主键 id=1
-- ② 聚簇索引按 id=1 找整行
```

**为什么聚簇索引只有 1 个**：数据只能按一种物理顺序存储——主键序；二级索引存主键（而非行指针）的原因：主键变更时只需更新二级索引的叶子值，行移动不影响（**主键不变 → 二级索引免维护**）。

> 💡 **主键设计启示**：InnoDB 推荐**自增/单调主键**——插入只在 B+ 树最右叶子追加（无分裂移动）；UUID 主键随机插入 → 频繁页分裂 → 性能退化（面试高频考点）。

## 3. 回表与覆盖索引

### 3.1 回表（Table Lookup）

```text
SELECT * FROM users WHERE name = '张三'
  ① 二级索引（name 树）: 找到主键 id = 1     ← 1 次 B+ 树
  ② 聚簇索引（id 树）:   按 id=1 找整行       ← 1 次 B+ 树
  → 共 2 次 B+ 树查找（回表）

回表代价: 每次多一次 B+ 树 I/O
优化方向: 消除回表 → 覆盖索引
```

### 3.2 覆盖索引（Covering Index）

```sql
-- 查询列全部在索引中 → 免回表:
CREATE INDEX idx_name_age ON users(name, age);

SELECT name, age FROM users WHERE name = '张三';
-- ①② 都在 name_age 索引的叶子里 → 直接返回 ✓ 零回表

-- 对比（需要回表）:
SELECT * FROM users WHERE name = '张三';   -- 还要取其他列 → 回表
```

| 索引类型 | 查询匹配 | 是否回表 |
|---------|---------|:---:|
| 无索引 | 全表扫描 | — |
| 普通二级索引 | `SELECT *` | ✅ 回表 |
| 覆盖索引 | 查询列 ⊆ 索引列 | ❌ 免回表 |

> 🎯 **面试必答**：覆盖索引 = 「查询的列全部被索引覆盖，叶子直接返回」——`SELECT 索引列` 免回表是 SQL 优化的第一手段。

## 4. 联合索引与最左前缀

### 4.1 联合索引的 B+ 树结构

```sql
CREATE INDEX idx_team_age ON employees(team, age);
-- 先按 team 排序，同 team 再按 age 排序
```

```text
联合索引 (team, age) 的叶子:
  (研发, 25) → (研发, 30) → (研发, 35) → (产品, 28) → (产品, 32)
  team 有序 → 同 team 内 age 有序
```

### 4.2 最左前缀原则

```text
索引 (a, b, c) 能匹配的查询:
  WHERE a = ?            ✅ 走索引（只用 a）
  WHERE a = ? AND b = ?  ✅ 走索引（a+b）
  WHERE a = ? AND b = ? AND c = ?  ✅ 全用
  WHERE b = ?            ❌ 不走（缺最左 a）
  WHERE a = ? AND c = ?  ⚠️ 部分（a 用索引，c 无法用）

原因: B+ 树按 (a,b,c) 整体排序——缺前缀则无从定位
```

| 查询条件 | 索引利用 | 原因 |
|---------|:---:|------|
| a | ✅ 完整 | 最左匹配 |
| a+b | ✅ 完整 | 前缀连续 |
| a+b+c | ✅ 完整 | 全列 |
| b 或 b+c | ❌ | 缺 a，无法定位 |
| a+c | ⚠️ 仅 a | c 跳跃（中间断档） |

> ⚠️ **面试高频**：`WHERE a=1 AND c=2` 中 c 不走索引（b 缺失，a 与 c 之间有断档）——联合索引「前缀连续才有效」。

## 5. 索引优化实践

### 5.1 索引设计原则

| 原则 | 说明 |
|------|------|
| 主键单调 | 自增/BIGINT（避免页分裂） |
| 选择性高列优先 | 区分度大的列做前缀（如 email > gender） |
| 控制索引数量 | 每索引一棵 B+ 树（写放大） |
| 覆盖索引优先 | 查询列 ⊆ 索引列 |
| 大字段不索引 | TEXT/BLOB 不适合（页利用率崩溃） |
| 前缀索引 | `INDEX(name(10))` 截断索引大字段 |

### 5.2 常见索引失效场景

| 场景 | 原因 | 对策 |
|------|------|------|
| `WHERE age+1 = 20` | 函数运算破坏索引 | 改写 `age = 19` |
| `WHERE name LIKE '%张%'` | 前导通配符 | 改为 `'张%'` 或全文索引 |
| `WHERE a = 1 OR b = 2` | OR 难用联合索引 | UNION 拆开 |
| 隐式类型转换 | `WHERE phone = 138...`（字符串列） | 引号包裹 |
| `WHERE a = ? ORDER BY b` | 排序字段不在索引 | 联合索引 (a,b) |

### 5.3 用 EXPLAIN 验证

```sql
EXPLAIN SELECT name FROM users WHERE team = '研发' AND age > 30;
-- 关注: possible_keys（可用索引）
--       key（实际使用）
--       type（ref > range > index > ALL）
--       Extra（Using index = 覆盖索引 ✓，Using filesort = 需优化）
```

> 💡 `EXPLAIN` 的 `type` 从好到差：`const > ref > range > index > ALL`——**index/ALL 是优化信号**；`Extra` 出现 `Using filesort` 说明排序没走索引。

## 6. 索引面试问答

| 问题 | 标准答案 |
|------|---------|
| InnoDB 为什么用 B+ 树？ | 范围查询 + 页利用率 + 树高 = I/O 次数 |
| 聚簇索引和二级索引区别？ | 聚簇叶子存整行（1 个）；二级存主键（多个） |
| 什么是回表？ | 二级索引 → 主键 → 聚簇索引查行 |
| 什么是覆盖索引？ | 查询列全在索引 → 免回表 |
| 最左前缀是什么？ | 联合索引按前缀连续使用（缺最左失效） |
| 为什么主键要自增？ | 单调插入避免页分裂（UUID 随机插入退化） |
| 索引越多越好？ | 否——每索引一棵 B+ 树，写放大 |
| 10 亿数据树高几层？ | InnoDB 3-4 层（页 1170 键） |
| 为什么大字段不适合索引？ | 页键容量暴跌 → 树高暴增 |
| 与 LSM 树对比？ | 读多 B+、写多 LSM（顺序写 + 后台合并） |

> 🎯 **核心要点**：索引实战验收——聚簇/二级/回表/覆盖四概念默写；最左前缀的三种匹配情况（完整/部分/失效）；「主键自增防页分裂」「EXPLAIN 看 type」两个实战技能；面试话术：**「InnoDB 表 = 一棵主键 B+ 树，二级索引 = 主键的 B+ 树，一切优化围绕减少 B+ 树次数」**。B+ 树代码实现见 06 模块。
