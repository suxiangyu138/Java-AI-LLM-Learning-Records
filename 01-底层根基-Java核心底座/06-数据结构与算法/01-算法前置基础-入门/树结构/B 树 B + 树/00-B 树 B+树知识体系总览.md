## 4. 核心概念速查

| 概念 | 一句话说明 | 所在模块 |
|------|-----------|---------|
| B 树 | 多路平衡搜索树（每节点多键） | 01 |
| 阶 m | 每个节点最多 m 个孩子 | 01 |
| 键数范围 | ⌈m/2⌉-1 ~ m-1（非根） | 01 |
| 树高 | log_B n（B=页装键数，3-4 层） | 01 |
| 磁盘 I/O | 每次访问节点 = 一次 I/O | 01 |
| 分裂 | 节点满时中键上提（插入） | 02 |

| B+ 树 | 数据只在叶子 + 叶子链表 | 04 |
| 聚簇索引 | InnoDB 主键索引（叶子存整行） | 05 |
| 回表 | 二级索引查主键再查聚簇 | 05 |
| 最左前缀 | 联合索引的匹配原则 | 05 |

## 5. 术语表

| 术语 | 英文 | 定义 |
|------|------|------|
| 阶 | Order m | 节点最多孩子数 |
| 内部节点 | Internal Node | 非叶非根节点 |
| 叶子节点 | Leaf Node | 无孩子的节点（B+ 树存数据） |
| 分裂 | Split | 节点满时拆成两个 + 中键上提 |
| 合并 | Merge | 兄弟节点合并（下溢修复） |
| 借键 | Borrow | 从兄弟借一个键（下溢修复） |
| 下溢 | Underflow | 键数 < ⌈m/2⌉-1 |
| 页 | Page | 磁盘 I/O 的最小单位（InnoDB 16KB） |
| 聚簇索引 | Clustered Index | 叶子存整行数据的索引 |
| 二级索引 | Secondary Index | 叶子存主键（需回表） |
| 回表 | Table Lookup | 二级索引 → 主键 → 聚簇索引查行 |
| 覆盖索引 | Covering Index | 查询列全在索引内（免回表） |

## 6. 常见问题 FAQ

| 问题 | 一句话答案 |
|------|-----------|
| 为什么数据库用 B 树不用红黑树？ | 树高 = I/O 次数；B 树页装千键树高 3-4，红黑树 60 层 = 60 次 I/O |
| B 树和 B+ 树谁更常用？ | 数据库几乎全用 B+（范围查询 + 页利用率） |
| 为什么 B+ 树数据只在叶子？ | 非叶子全是键 → 页装更多键 → 树更矮 |
| 叶子链表有什么用？ | 范围查询连续读（B 树需中序回溯） |
| 分裂/合并是谁发明的？ | 2-3-4 树是 m=4 的特例（B 树一般化） |
| InnoDB 为什么用 B+ 不用 B？ | 聚簇索引 + 范围查询是 MySQL 核心场景 |
| 索引为什么不能太长？ | 页装键数下降 → 树高增加 → I/O 变多 |

## 9. 复杂度全景表

| 操作 | B 树 | B+ 树（InnoDB） | 红黑树 |
|------|:---:|:---:|:---:|
| 查找（I/O 或指针） | O(log_B n) | O(log_B n) | O(log n) |
| 插入 | O(log_B n) + 分裂 | 同 + 链表维护 | O(log n) + ≤2 旋转 |
| 删除 | O(log_B n) + 合并 | 同 + 链表维护 | O(log n) + ≤3 旋转 |
| 范围查询 | O(log_B n + k) 随机 | **O(log_B n + k) 顺序** | O(n)（需遍历） |
| 空间 | O(n) | O(n)（键略冗余） | O(n) |

## 11. FAQ 扩展（面试追问）

| 问题 | 完整答案 |
|------|---------|
| B 树和 B+ 树都叫 B，有什么关系？ | B+ 树是 B 树的变体：数据只在叶子 + 叶子链表 |
| 为什么叫「多路」？ | 每节点多个键/孩子（vs 二叉树两个） |
| 页大小影响什么？ | 页越大装键越多 → 树越矮 → I/O 越少（16KB 是权衡） |
| 为什么根节点可以不满？ | 树从根「长高」，根是分裂的产物，天然可不满 |
| 删除时借键和合并哪个优先？ | 兄弟富余先借（不改变树高），都穷再合并 |
| 索引为什么能加速排序？ | B+ 叶子链表天然有序，ORDER BY 走索引免 filesort |
| 为什么少用 `SELECT *`？ | 触发回表（覆盖索引失效） |
| LIKE 查询什么时候走索引？ | `'张%'` 前缀匹配走；`'%张'` 不走 |
| 为什么联合索引把选择性高的放前面？ | 剪枝更快（区分度大的列先过滤） |
| 主键用雪花 ID 可以吗？ | 单调性优于 UUID（趋势递增可接受） |

|---------|-----------|---------------|
| BST 有序性 | 左 < 根 < 右 | B 树的节点内有序 + 孩子区间 |
| BST 退化问题 | 有序插入变链表 | B 树用「多路 + 平衡」根治 |

| 2-3-4 树分裂 | 中键上提 | m=4 的 B 树（直接复用） |
| 磁盘局部性 | 顺序读 >> 随机读 | 叶子链表 + 页连续存储 |

## 13. 一句话速记卡

```text
B 树:   多路 + 叶子同层 + 键数半满约束
B+ 树:  B 树 + 数据只在叶子 + 叶子链表
InnoDB: 表 = 聚簇 B+ 树；二级索引存主键
面试:   树高 = I/O；3-4 层打天下
```

> 🎯 **核心要点**：B 树家族的灵魂一句话——**「树高 = 磁盘 I/O 次数」**，一切设计（多路、B+ 叶子链表）都围绕「让树更矮、让读取更连续」；学习主线：B 树（多路平衡）→ B+ 树（工程优化）→ InnoDB（实战应用）；与红黑树/AVL 的对比（内存 vs 磁盘）是树的体系收官之问。
