# 04 - B+ 树与 B 树对比

> B+ 树 = B 树的工程进化：**数据只在叶子 + 叶子链表**——两个改动换来「范围查询连续读」与「页利用率翻倍」，是数据库索引的事实标准。

## 1. B+ 树的结构

**B+ 树**：所有数据（记录/指针）都存储在**叶子节点**，内部节点只存**键**（作为路由指针）。

```text
B 树:                          B+ 树:
      [20|40|60]                    [20|40|60]        ← 内部节点只存键
     /   |   |   \                /    |    |    \
 [10|15] [25] [45] [70]     [10|15|25|30|45|50|70|80] ← 叶子存全部数据
  数据分散在各层                       ↓
                                   叶子链表: [10|15] → [25|30] → [45|50] → [70|80]

B 树: 数据在内部节点也能找到
B+ 树: 数据只在叶子（内部是纯路由）
```

| 维度 | B 树 | B+ 树 |
|------|------|-------|
| 数据存储 | 所有节点 | **仅叶子** |
| 内部节点 | 键 + 数据 | **纯键（路由）** |
| 叶子链表 | ❌ | **✅ 双向链表** |
| 查找路径 | 可能提前终止 | 必须到叶子 |

> 💡 B+ 树的查找**总是到叶子**——所有查找路径等长（完美平衡 + 数据只在叶子），查询时间稳定。

## 2. 两个关键改动

### 2.1 改动一：数据只在叶子

```text
收益 1: 页利用率翻倍
  B 树内部节点: 键 + 数据指针 → 一页装 1000 键
  B+ 树内部节点: 纯键 → 一页装 2000+ 键
  → 树更矮 → I/O 更少

收益 2: 内部节点更小 → 可常驻内存
  B+ 树前 2-3 层内部节点可全部缓存
  → 实际磁盘 I/O 只剩叶子层 1-2 次
```

### 2.2 改动二：叶子链表

```text
收益: 范围查询连续读
  B 树范围查询 [30, 70]:
    中序遍历回溯（父子来回跳）→ 随机 I/O

  B+ 树范围查询 [30, 70]:
    找到 30 后沿叶子链表顺序读 → 顺序 I/O
  → 顺序 I/O 比随机 I/O 快 10-100 倍！
```

> 🎯 **两个改动的本质**：数据只叶子 = 「空间换时间」（内部腾出更多键位）；叶子链表 = 「顺序换随机」（把回溯变成连续读）——全部围绕磁盘特性优化。

## 3. 范围查询的优势

```java
// B+ 树范围查询 [low, high]（概念）
// ① 找到 low（或第一个 ≥ low 的叶子）
// ② 沿叶子链表顺序扫描直到 > high
List<Integer> rangeQuery(BPlusTree tree, int low, int high) {
    List<Integer> res = new ArrayList<>();
    LeafNode leaf = tree.findLeaf(low);       // ① 定位（树高次 I/O）
    while (leaf != null) {
        for (int key : leaf.keys) {
            if (key > high) return res;       // ② 超出上界停止
            if (key >= low) res.add(key);
        }
        leaf = leaf.next;                     // ③ 叶子链表推进
    }
    return res;
}
```

**为什么数据库场景离不开 B+ 树**：

```text
SQL 典型查询: SELECT * FROM orders WHERE date BETWEEN '2026-01-01' AND '2026-01-31'

B+ 树: 定位 1 月 1 日（2-3 次 I/O）→ 叶子链表顺序扫 31 天数据
B 树:  中序回溯跨节点（每次回溯一次随机 I/O）

范围查询占比: 业务查询 80%+ 是范围/排序
→ B+ 树的叶子链表是「为范围查询而生」
```

## 4. 全面对比表

| 维度 | B 树 | B+ 树 |
|------|:---:|:---:|
| 数据存储 | 所有节点 | **仅叶子** |
| 内部节点 | 键 + 数据 | **纯键** |
| 叶子链表 | ❌ | ✅ |
| 查找 | 可能提前命中 | 必须到叶子（路径等长） |
| 范围查询 | 中序回溯（随机 I/O） | **链表顺序读** |
| 页键容量 | 少（数据占位） | **多（纯键）** |
| 树高 | 略高 | **略低** |
| 单点查询 | 可能更快（提前命中） | 同（I/O 同阶） |
| 插入/删除 | 分裂/合并 | 同（额外维护链表） |
| 实现复杂度 | ★★★ | ★★★★ |
| 应用 | 文件系统（ext4 早期） | **关系型数据库（InnoDB）** |

**B 树的幸存场景**：

| 场景 | 为什么用 B 树 |
|------|--------------|
| 单点查询极频繁 | 内部节点命中可提前返回（省叶子 I/O） |
| 无范围查询需求 | 不需要叶子链表 |
| MongoDB WiredTiger | 文档模型单点读多、存储引擎兼容 |

> 💡 工程结论：**数据库/文件系统 90% 用 B+ 树**；B 树的「提前命中」优势在缓存命中率高时几乎可忽略——所以 B+ 树全面胜出。

## 5. B+ 树的代价

**任何设计都有代价**（面试加分点）：

| 代价 | 说明 |
|------|------|
| 实现复杂 | 叶子链表维护（插入/删除/分裂时的指针更新） |
| 内部键冗余 | 键在内部和叶子各存一份（空间略增） |
| 单点查询路径长 | 必须到叶子（无提前命中） |
| 叶子上限 | 叶子存数据后键容量受限（数据行大时） |

```text
InnoDB 的真实权衡:
  聚簇索引: 叶子存整行 → 每页行数少 → 树高可能 4 层
  二级索引: 叶子存主键 → 每页键多 → 树高 3 层
  → 控制行宽（避免大字段）就是控制树高
```

> ⚠️ 面试常见误区：「B+ 树比 B 树快」——**单点查询两者同阶**（都 O(log_B n) I/O）；B+ 的胜利在**范围查询 + 页利用率**，不是所有场景。

## 6. 选型速查表

```text
需要索引？
├── 关系型数据库（范围/排序多） → B+ 树（InnoDB）
├── 文档数据库（单点读多） → B 树（MongoDB）
├── 文件系统（块管理） → B 树变体（ext4 Htree）
├── 内存有序 Map → 红黑树（TreeMap）
├── 日志写多 → LSM 树（LevelDB）
└── 稀疏索引 → Radix Tree（PostgreSQL）
```

**面试一句话**：

```text
B+ 树 = B 树 + 数据只在叶子 + 叶子链表
  → 页利用率翻倍（树更矮）
  → 范围查询顺序读（快 10-100 倍）
  → 数据库索引的事实标准
```

### 5.1 叶子链表的维护细节

```text
插入触发分裂时的链表更新:
  [10|15|20|25] 满 → 插入 22 → 分裂
  [10|15] → [20|22] → [25]
    │          │        │
    └──────────┴────────┘   ← next 指针重连（O(1)）

删除触发合并时的链表更新:
  [10|15] + [20] → 合并 [10|15|20]
    │                 │
    └─────────────────┘   ← 移除中间节点（O(1)）

注意: 分裂/合并时链表重连是 B+ 树独有的维护成本
```

### 5.2 面试对比补充

| 对比问题 | B 树 | B+ 树 |
|---------|------|-------|
| 单点查询谁快？ | 可能提前命中（略快） | 必须到叶子 |
| 范围查询谁快？ | 中序回溯（随机 I/O） | **链表顺序读（快 10-100 倍）** |
| 页利用率谁高？ | 数据占内部节点 | **纯键更高** |
| 实现谁复杂？ | ★★★ | ★★★★（链表） |
| 工程谁常用？ | MongoDB/ext4 | **InnoDB/PostgreSQL** |

### 5.3 一句话总结卡

```text
B+ 树 = B 树 + 两个工程优化:
  ① 数据只在叶子 → 内部纯键 → 页利用率翻倍 → 树更矮
  ② 叶子链表 → 范围查询顺序读 → 快 10-100 倍
数据库选 B+ 不选 B: 因为业务查询 80% 是范围/排序
```

> 🎯 **核心要点**：B+ 验收——两个改动的收益（数据只叶子 = 页利用率、叶子链表 = 范围查询）；「单点查询两者同阶、B+ 胜在范围」的精确表述；InnoDB 聚簇/二级索引的树高差异（05 模块展开）；「B+ 不是更快，是更适合数据库场景」的工程认知。
