# 06 - 红黑树 vs AVL vs B 树

> 平衡树三兄弟的终局对比：红黑树（写多读少）、AVL（读多写少）、B 树（磁盘场景）——理解「为什么工程默认红黑树」与「为什么数据库用 B 树」，是面试树的收官题。

## 1. 三树定位

| 树 | 一句话定位 | 典型应用 |
|----|-----------|---------|
| 红黑树 | **写多读少**的平衡 BST，旋转少 | TreeMap/TreeSet、HashMap 树化、Linux 调度器 |
| AVL 树 | **读多写少**的严格平衡树，查询最快 | 查找密集、几乎不增删的场景 |
| B 树 | **磁盘/块设备**场景的多路平衡树 | 数据库索引（InnoDB）、文件系统（ext4） |

> 🎯 记忆锚点：**红黑树 = 工程默认**、**AVL = 查询极致**、**B 树 = 磁盘为王**——三种场景三种最优。

## 2. 红黑树 vs AVL 树

### 2.1 平衡标准不同

| 维度 | 红黑树 | AVL 树 |
|------|--------|--------|
| 平衡标准 | 黑色平衡（最长 ≤ 2×最短） | 高度平衡（左右高差 ≤ 1） |
| 树高 | ≤ 2·log₂(n+1)（约 1.44~2 倍 log n） | ≤ 1.44·log₂(n+1)（更矮） |
| 查找 | O(log n)（略慢，树更高） | **O(log n)（最快，树最矮）** |
| 插入修复 | ≤ 2 次旋转 | ≤ 1 次旋转（但**可能回溯整条路径**） |
| 删除修复 | ≤ 3 次旋转 | 可能 O(log n) 次旋转（回溯到根） |
| 写操作代价 | **旋转少，写更快** | 旋转多，写更慢 |

### 2.2 为什么工程默认红黑树

```text
AVL 的优势（查找）: 树更矮 → 每步少比较 1-2 层
                   但：查找密集型才明显

红黑树的优势（写）: 插入最多 2 次旋转、删除最多 3 次
                   AVL 删除可能旋转 O(log n) 次
                   → 频繁增删时红黑树常数小得多

结论: 通用数据结构（Map/Set）增删查均衡 → 红黑树
      只读不改（构建后恒定查询） → AVL
```

> 💡 **面试一句话**：红黑树是「牺牲一点查找常数、换取写操作旋转更少」的工程折中——TreeMap 的 put/remove 频繁，选红黑树；只读场景（如预构建的静态索引）选 AVL。

## 3. 红黑树 vs B 树

### 3.1 场景的本质差异

| 维度 | 红黑树 | B 树 |
|------|--------|------|
| 存储介质 | 内存（指针访问 O(1)） | **磁盘（块读取，一次 I/O 按页）** |
| 节点键数 | 1 | **数百**（页大小决定） |
| 树高 | O(log n) | **O(log_B n)（B=页能装键数）** |
| 查询代价 | 指针跳转 | **磁盘 I/O 次数**（树高即 I/O） |
| 数据局部性 | 差（指针跳跃） | 好（页内连续） |

### 3.2 为什么数据库用 B 树不用红黑树

```text
红黑树（内存）: 10 亿数据树高 ≈ 60 层
               每层一次指针跳转（内存纳秒级）→ 可接受

B 树（磁盘）:  一个页（16KB）能装几千个键
               10 亿数据树高 ≈ 3-4 层
               每层一次磁盘 I/O（毫秒级）→ 树高即生死
               3 次 I/O vs 60 次 I/O = 20 倍差距
```

**B+ 树的进一步优化**（InnoDB 用 B+ 而非 B）：
- 数据只在叶子：非叶子全是指针 → 页装更多键 → 树更矮；
- 叶子链表相连：**范围查询连续读**（B 树范围查询要中序遍历回溯）。

> 💡 衔接：[B 树 B + 树](../B 树 B + 树/)体系详细展开；数据库索引的工程细节见 MySQL 体系。

## 4. 选型决策树

```text
需要平衡树结构？
├── 存储介质是磁盘/需要批量读？ → B 树 / B+ 树（数据库、文件系统）
├── 内存结构，读写均衡？ → 红黑树（TreeMap/HashMap 树化）
├── 内存结构，只读/查找密集？ → AVL 树
├── 需要有序 + 区间查询？ → 红黑树（TreeMap floor/ceiling）
└── 键范围小且固定？ → 哈希表（O(1)，无需有序时）
```

## 5. 面试问答速查

| 问题 | 答案要点 |
|------|---------|
| 红黑树和 AVL 怎么选？ | 写多选红黑（旋转少）、读多选 AVL（树矮查询快） |
| 为什么 TreeMap 用红黑树？ | 增删查均衡 + 最坏 O(log n) 有保证 |
| HashMap 为什么树化用红黑树？ | 链表退化最坏 O(n)，红黑树兜底 O(log n) |
| 数据库为什么 B 树？ | 磁盘 I/O 按页，B 树树高 = I/O 次数，页多键矮树 |
| B 树 vs B+ 树？ | B+ 数据只在叶子（更矮）+ 叶子链表（范围查询友好） |
| 红黑树最坏复杂度？ | 任何操作 O(log n)（性质保证） |
| 手写红黑树？ | 几乎不考完整实现；考性质、修复思想、选型 |

### 5.1 工程实例全表

| 系统 | 使用的树 | 原因 |
|------|---------|------|
| Java TreeMap/TreeSet | 红黑树 | 有序 + 写频繁 |
| Java HashMap（≥8 桶） | 红黑树 | 恶意哈希兜底 |
| Linux CFS 调度器 | 红黑树 | 进程增删频繁 |
| epoll | 红黑树 | 大量 fd 动态管理 |
| Nginx 定时器 | 红黑树 | 时间有序 + 频繁更新 |
| C++ std::map | 红黑树 | 同上 |
| MySQL InnoDB | B+ 树 | 磁盘 I/O + 范围查询 |
| PostgreSQL | B+ 树 + Radix | 索引多样性 |
| MongoDB | B 树（WiredTiger） | 读优化 |
| ext4 文件系统 | B 树（extent） | 磁盘块管理 |

### 5.2 数据规模对比（树高直觉）

```text
n = 10 亿（10⁹）:
  AVL       树高 ≈ 30 层（1.44·log₂n）
  红黑树    树高 ≈ 60 层（上限 2·log₂n）
  B+ 树     树高 ≈ 3-4 层（页 1000 键）

内存访问: 30-60 次指针跳转（纳秒级）→ 都能接受
磁盘访问: 3-4 次 I/O vs 30-60 次 I/O → B 树碾压
```

### 5.3 最终面试复盘

| 问题 | 一句话答案 |
|------|-----------|
| 平衡树三种怎么选？ | 写多红黑、读多 AVL、磁盘 B 树 |
| 红黑树最坏保证？ | 任何操作 O(log n) |
| B+ 树 vs B 树？ | B+ 数据只在叶子 + 叶子链表范围查询 |
| 为什么 HashMap 树化？ | 链表退化 O(n) 兜底（恶意哈希防御） |
| 树的学习路径？ | 二叉树 → BST → 平衡树 → B 树 |

> 🎯 **核心要点**：收官验收——三句话选型（写多红黑、读多 AVL、磁盘 B 树）；「红黑树旋转少 vs AVL 树矮」的权衡；「B 树树高 = 磁盘 I/O 次数」的数据库视角；面试到此，树的体系闭环：二叉树（形态）→ BST（有序）→ 红黑树/AVL（平衡）→ B 树（磁盘）。姊妹篇见[AVL 树](../AVL 树（平衡二叉搜索树）/)。
