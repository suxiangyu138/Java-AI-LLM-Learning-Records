## 1. 红黑树模型：五条性质

### 1.1 五条性质（面试必背）

```text
红黑树 = BST + 每个节点有颜色（红/黑）+ 五条规则:

  ① 每个节点非红即黑
  ② 根节点必须是黑色
  ③ 叶子（NIL 空节点）都是黑色
  ④ 红色节点的两个孩子必须都是黑色（不能有连续红）
  ⑤ 从任一节点到其所有叶子（NIL）的每条路径，
     包含相同数量的黑色节点（黑高相同）

推论: 最短路径 = 全黑；最长路径 = 红黑交替——
  最长 ≤ 2 × 最短（性质 ④⑤ 保证）

⚠️ 记忆口诀: "根黑叶黑不连红、黑高相同五条规"
```

> 🎯 **五性质的面试价值**："**'根黑叶黑不连红、黑高相同'——五条性质决定'最长 ≤ 2×最短'的弱平衡**。能背五条 + 推出 2 倍界，红黑树的面试第一关就过了。"

## 2. 为什么弱平衡就够

### 2.1 2 倍界的推导

```text
性质 ⑤: 任意路径黑高相同 = h
性质 ④: 红不连 → 每条路径至多一半是红
→ 最短路径（全黑）≥ h、最长路径 ≤ 2h
→ 最长 ≤ 2 × 最短 → 树高 ≤ 2·log₂n → O(log n) ✓

对比 AVL: 高度差 ≤ 1 → 树高 ≤ 1.44·log n
红黑树树高约 2·log n——稍高但同阶

⚠️ 为什么"够":
  2·log n 仍是指数级压缩（n=10⁶ → 40 层）——
  O(log n) 的保证不因"弱"而失效
```

### 2.2 代价换来的收益

```text
AVL 严格: 增删可能 O(log n) 次旋转
红黑树弱: 插入最多 2 次旋转、删除最多 3 次——
  变色为主、旋转少量 → 增删维护便宜

⚠️ 核心权衡:
  "AVL 用'更多旋转'换'更低树高'（查询快）
   红黑树用'稍高树高'换'更少旋转'（增删快）
   ——工程增删频繁 → 红黑树胜出"
```

> 🎯 **弱平衡的智慧**："**'2 倍界仍是指数压缩 + 旋转降到最多 2 次'——红黑树用'稍高'换'增删便宜'**。理解这个权衡，就理解了红黑树统治工程的原因。"

## 3. 插入：变色与旋转

### 3.1 插入流程（讲清即可，不要求手撕）

```text
红黑树插入（新节点默认红色）:
  ① BST 插入（新节点红——尽量少破坏性质）
  ② 若违反性质（红红相连）→ 按叔叔节点颜色分情形修复:

  情形一（叔叔是红）: 变色——
    父/叔叔变黑、祖父变红 → 祖父可能继续违反 → 上溯

  情形二（叔叔是黑/空 + 直线型）: 旋转——
    LL/RR: 旋转祖父 + 变色
  情形三（叔叔是黑/空 + 折线型）: 双旋——
    LR/RL: 先旋父再旋祖父 + 变色

  ⚠️ 最多 2 次旋转（情形一可能多轮变色但无旋转）

⚠️ 面试定位:
  "插入 = BST 插入 + 红红修复——
   叔叔红变色、叔叔黑旋转——最多 2 次旋转"
  能讲清三种情形即可，完整手撕是竞赛
```

> 🎯 **插入的面试表达**："**'新节点红 → 红红冲突 → 叔叔红变色、叔叔黑旋转'——红黑树插入的三种情形一句话讲清**。'最多 2 旋转'的结论是面试必答点。"

## 4. AVL vs 红黑树：工程选型

| 维度 | AVL | 红黑树 |
|------|:---:|:---:|
| 平衡程度 | 严格（|h|≤1） | 弱（2 倍界） |
| 树高 | ≤ 1.44·log n | ≤ 2·log n |
| 查询 | **更快**（树矮） | 稍慢 |
| 插入旋转 | 最坏 O(log n) 次 | **最多 2 次** |
| 删除旋转 | 最多 O(log n) 次 | 最多 3 次 |
| 工程应用 | 少（读多写少场景） | **默认（TreeMap 等）** |

```text
⚠️ 面试一句话:
  "查询多用 AVL（树矮快）、增删频繁用红黑树（旋转少）——
   工程实际全用红黑树（HashMap/TreeMap 都是）"
```

> 🎯 **选型的一句话**："**'读多写少 AVL、增删频繁红黑'——工程默认红黑树（TreeMap/TreeSet/C++ map）**。能讲出'为什么'（旋转次数差异）而非只背结论，选型题就满分了。"

## 5. 工程应用：TreeMap 与 HashMap 树化

### 5.1 TreeMap/TreeSet（红黑树）

```java
// Java TreeMap: 底层红黑树——
//   O(log n) 增删查 + 有序遍历 + floor/ceiling
TreeMap<Integer, String> map = new TreeMap<>();
map.put(3, "c"); map.put(1, "a"); map.put(2, "b");
map.firstKey();      // 1（最小键）
map.floorKey(2);     // 2（≤ 2 的最大键）
map.higherKey(1);    // 2（> 1 的最小键）

// ⚠️ 有序 API: TreeMap/TreeSet 的红黑树价值——
//   哈希给不了的"有序性"由红黑树提供
//   应用: 有序集合、区间查询、动态排名
```

### 5.2 HashMap 树化（8/6 阈值）

```java
// HashMap（JDK 8+）: 桶内链表过长 → 红黑树——
//   链表长度 ≥ 8 且容量 ≥ 64 → 树化（treeifyBin）
//   红黑树节点 ≤ 6 → 退化链表
//   为什么 8: 泊松分布概率 ≈ 0.00000006（防哈希洪水）

// ⚠️ 工程真相:
//   树化是"防御机制"不是常态——正常数据几乎不触发
//   与平衡树专题的关联: 红黑树的 O(log n) 让恶意哈希攻击失效

// ⚠️ 面试表达:
//   "HashMap 桶内 8 个后树化——防哈希洪水；
//    6 个退化——防树链抖动（8 与 6 间隔缓冲）"
```

> 🎯 **工程应用的两道题**："**TreeMap 的红黑树给'有序性'、HashMap 树化给'防攻击'——两个工程现场让红黑树从理论变现实**。面试被问'哪里用到红黑树'，答这两个 + C++ map + Linux 内核就是完整答案。"

## 6. 红黑树 vs B 树：数据库为什么选 B+

### 6.1 对比

| 维度 | 红黑树 | B+ 树 |
|------|:---:|:---:|
| 面向 | 内存 | 磁盘 |
| 结构 | 二叉树 | 多路（数百键/节点） |
| 树高 | ~2·log₂n | 3-4 层（10⁹ 数据） |
| 节点大小 | 2 键 | 与磁盘页对齐（4KB/16KB） |
| 关键操作 | 旋转/变色 | 分裂/合并 |
| 应用 | TreeMap/内核 | **数据库索引** |

### 6.2 为什么数据库不用红黑树

```text
数据库索引的瓶颈是磁盘 I/O——
  ① B+ 树节点 = 磁盘页 → 一次 I/O 读数百键
  ② 红黑树节点 = 2 键 → 同样数据需数十倍 I/O
  ③ B+ 树高 3-4 层 → 查询 3-4 次 I/O；红黑树 20+ 次

⚠️ 面试必答:
  "红黑树面向内存（旋转/变色）、
   B+ 树面向磁盘（页对齐 + 多路矮树）——
   数据库索引要减少 I/O 次数 → B+ 树"
```

> 🎯 **红黑 vs B 树的定位**："**'内存用红黑、磁盘用 B+'——I/O 效率是分水岭**。面试高频对比题：能讲'页对齐 + 树高 3-4 层'，就答到原理层了。"
