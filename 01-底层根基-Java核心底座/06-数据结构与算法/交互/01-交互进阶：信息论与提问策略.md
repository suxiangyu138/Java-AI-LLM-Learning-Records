## 1. 信息论：提问次数的理论下界

### 1.1 信息量的度量

```
一次提问能消除多少不确定性？
  答案有 k 种可能（等概率）→ 消除 log₂k 位信息
  总共要区分 N 种可能 → 至少需要 log₂N 位

⚠️ 提问次数下界（重要直觉）：
  猜 1..n 的数字：下界 = ⌈log₂n⌉ 次（二分达到）
  找出 n 个中坏的一个（1 次检测）：log₂n 次

⚠️ 面试表达：
"信息论给下界——每次提问最多带来 log₂(答案数) 位
 信息，总不确定性 log₂N 位 → 至少 ⌈log₂N⌉ 次。
 二分提问每次都恰好拿到 1 位 → 达到下界（最优）。"
```

### 1.2 非等概率答案的信息量

```
答案概率不均等时：
  信息量 = -Σ pᵢ·log₂pᵢ（熵）
  ⚠️ 非均匀 → 信息量 < log₂k → 需要更多提问
  （或设计"高信息量"的提问：把答案概率分开）

⚠️ 应用直觉：
  guess() 返回 3 种（-1/0/1）→ 理想 1.58 位/次
  但 -1 与 1 的分布可能不均 → 实际略少

⚠️ 面试表达：
"guess() 三分答案每次最多 1.58 位，但二分
 策略只用'大了/小了'两态 → 实际就是二分 1 位/次。
 信息论解释二分为什么最优：总 log₂n 位 / 每次 1 位。"
```

### 1.3 下界在实际题目中的体现

| 题目 | 不确定性 | 下界 | 实际 |
|------|---------|:---:|:---:|
| 374 猜数字 | log₂n | ⌈log₂n⌉ | 二分 ⌈log₂n⌉ ✓ 最优 |
| 278 找第一个坏版本 | log₂n | ⌈log₂n⌉ | 二分 ✓ |
| 1095 山脉目标 | 2×log₂n | ~2log₂n | 三段二分 ~2log₂n ✓ |
| 1533 找最大索引 | log₂n | ⌈log₂n⌉ | 区间比较 ✓ |

## 2. 二分交互：最标准的提问模式

### 2.1 交互二分与数组二分的差异

```
数组二分：nums[mid] 直接可读（无代价）
交互二分：答案通过 API 获取（每次提问有"次数"成本）

⚠️ 共同点：都依赖"单调性"（isBadVersion 的坏版本单调）
  交互二分的特殊性：
  ① 次数受限（题目给定上限）
  ② 提问本身可能有"噪声"（少数题）

⚠️ 面试表达：
"交互二分与普通二分同构——关键是识别'单调性质'：
 isBadVersion 从 false 变 true 后不再变回 → 二分边界。"
```

### 2.2 交互二分的模板（374/278 通用）

```java
/** 374 猜数字：guess(mid) 返回 -1/0/1 */
public int guessNumber(int n) {
    int lo = 1, hi = n;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;      // ⚠️ 防溢出
        int res = guess(mid);              // ⚠️ API 提问
        if (res == 0) return mid;
        if (res == -1) hi = mid - 1;       // 猜大了
        else lo = mid + 1;                 // 猜小了
    }
    return -1;
}

/** 278 第一个错误版本：布尔 API */
public int firstBadVersion(int n) {
    int lo = 1, hi = n;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (isBadVersion(mid)) hi = mid;   // ⚠️ 坏版本 → 边界左移（含 mid）
        else lo = mid + 1;                 // 好版本 → 排除
    }
    return lo;
}
// ⚠️ 模板差异：374 用 lo<=hi（值存在）；278 用 lo<hi（找边界）
// ⚠️ 面试表达："两种模板——'查值'（lo<=hi 返回 mid）
//   与'找边界'（lo<hi 收敛到第一个满足位置）。"
```

### 2.3 交互二分的变体

```
① 答案范围非 1..n（浮点/大范围）→ 扩大范围再二分
② 提问有成本（次数限制）→ 先估算下界再精确二分
③ 答案多次查询（如猜多个数）→ 每次独立二分

⚠️ 面试表达：
"交互题先画'单调性质'——isBadVersion 的布尔
 单调、guess 的三态有序——再套二分模板。"
```

## 3. 三分与峰值交互

### 3.1 852/1095 山脉数组

```
山脉数组：先严格升后严格降（单峰）
找峰顶：
  nums[mid] < nums[mid+1] → 上升 → 峰在右
  nums[mid] > nums[mid+1] → 下降 → 峰在左（含 mid）

⚠️ 本质：峰值二分（分治/06 有完整版）——"方向判定"
  不是三分！三分是"三个相邻点比较"，此题两相邻点即可
```

```java
/** 852. 山脉数组的峰顶索引 */
public int peakIndexInMountainArray(int[] arr) {
    int lo = 0, hi = arr.length - 1;
    while (lo < hi) {
        int mid = lo + (hi - lo) / 2;
        if (arr[mid] < arr[mid + 1]) lo = mid + 1;   // 上升段
        else hi = mid;                               // 下降段（含 mid）
    }
    return lo;
}
// ⚠️ 面试表达："峰值二分不需要三分——
//   比较相邻两点判断'所在段'（升/降），
//   每步丢弃一半，O(log n)。"
```

### 3.2 1095：双 API 协同的峰值查找

```
⚠️ 注意：1095 是"直接数组访问"（MountainArray.get(i)），
  不是 API 返回三态——但 get(i) 有访问次数限制（100 次）
  → 本质仍是"带预算的交互"

流程：
  ① 二分找峰顶（约 log n 次 get）
  ② 左半（升序）二分 target
  ③ 右半（降序）二分 target（反转比较）
  总访问 ≤ 3·log n ≤ 100 ✓
```

## 4. 双 API 协同：信息的分工

### 4.1 1533. 找最大整数索引

```
数组被分成若干组（每组大小 groupSize），
compare(a,b,c,d) 返回"更大的一组"（或相等）
⚠️ 每次提问比较两组 → 一次淘汰一半组 → log₂(组数) 次
```

```java
/** 1533. 找最大整数的索引（区间比较 API） */
public int getIndex(ArrayReader reader) {
    int n = reader.length();
    int lo = 0, hi = n - 1;

    while (lo < hi) {
        int len = hi - lo + 1;
        int half = len / 2;
        // 按 groupSize 分组：左半、右半、余数
        int cmp = reader.compare(lo, lo + half - 1,
                                 lo + half, lo + half * 2 - 1);
        if (cmp == 0) return lo + half;       // ⚠️ 相等 → 中间是最大值
        if (cmp < 0) lo = lo + half;          // 右半更大 → 去右
        else hi = lo + half - 1;              // 左半更大 → 去左
    }
    return lo;
}
// ⚠️ 边界细节：奇偶长度处理（余数单独比较）
// ⚠️ 面试表达："1533 每次提问比较两半——
//   一次淘汰一半 → log₂n 次。API 的语义
//   （哪组更大）直接决定二分方向。"
```

### 4.2 双 API 的协同模式

```
模式一：两个 API 各管一件事（get 定位 + isBad 判定）
模式二：一个 API 多语义（guess 返回三态）
模式三：API 组合出单调性质（比较两段 → 淘汰一段）

⚠️ 面试表达：
"多 API 交互题先回答：每个 API 提供什么信息？
 信息如何组合成'方向判定'？——方向判定是
 一切二分交互的核心。"
```

## 5. 并行提问：一次问多个

### 5.1 并行提问的思想

```
串行：每次问一个，n 次问完
并行：一次问 k 个（如"这个数在 1..10 的哪个区间"）
  ⚠️ 一次问题的答案种类数 = 信息量上限

例：称重问题（12 个球找假球）
  天平一次 3 种结果（左重/右重/平衡）→ log₂3 位/次
  12 个球 × 假球可能重/轻 = 24 种情况
  下界 = ⌈log₃24⌉ = 3 次（可行！）

⚠️ 面试表达：
"并行提问的信息论：一次 k 态提问 = log₂k 位。
 称重 3 次能处理 3³=27 种情况 > 24 → 恰好够。
 设计提问要让答案均匀分布（信息量最大）。"
```

### 5.2 信息论驱动的提问设计

```
设计原则：
  ① 让每个答案的可能性尽量均匀（信息量最大）
  ② 答案数多 → 单次信息量大 → 总次数少
  ③ 最坏情况分析（保证次数上界）

⚠️ 应用：猜数字的"一次问 10 个"变体
  答案 0-9 均匀 → 每问 1 位十进制 → log₁₀n 次
  （n=1000 → 3 次，对比二进制 10 次）
```

## 6. 交互题的边界与容错

### 6.1 边界清单

| 边界 | 处理 |
|------|------|
| 提问次数上限 | 先估算：log₂n 与题目上限对比 |
| API 返回语义 | 仔细读（-1=大了还是小了？） |
| 空输入/单元素 | 提前返回（不经 API） |
| 奇偶长度 | 中点的取整方向一致 |
| 越界访问 | 检查 API 范围（MountainArray 边界） |

### 6.2 容错设计

```
① 次数预算监控：统计提问次数，接近上限告警
② API 异常：catch 后降级（二分退化为线性）
③ 结果验证：找到答案后二次确认（多问一次）

⚠️ 面试表达：
"交互题先算'预算'——每次提问成本 vs 题目上限；
 二分 O(log n) 几乎总是够。异常场景：
 API 可能失败时降级为线性重试。"
```

### 6.3 交互题的调试技巧

```
① 本地模拟：自己实现 API（测试驱动）
② 打印提问序列：检查二分方向
③ 边界推演：n=1/2/3 的手推
④ 验证单调性假设：提问序列是否符合预期

⚠️ 常见坑：
  死循环（lo<hi 与 mid 取整不匹配）
  方向写反（-1/1 的语义理解错）
  越界调用 API（MountainArray 索引）
```

## 7. 面试要点与追问

### 7.1 面试话术模板

```
"交互题先画信息流：每个 API 给什么信息？
 信息能否形成'方向判定'（单调性）？
 能 → 二分（O(log n) 次提问，信息论证明最优）。
 预算检查：log₂n ≤ 题目上限 ✓。
 边界：空输入提前返回、mid 防溢出、语义仔细核对。"
```

### 7.2 高频追问 TOP 8

| # | 追问 | 标准回答 |
|:---:|------|------|
| 1 | 为什么二分最优？ | 每次 1 位信息，log₂n 下界恰好达到 |
| 2 | 三分 vs 峰值二分？ | 峰值用相邻两点判定方向，不是三分 |
| 3 | 双 API 怎么协同？ | 每个 API 的信息组合成方向判定 |
| 4 | 提问次数怎么算？ | log₂n（二分）；并行提问 logₖN |
| 5 | 称重 3 次够吗？ | 3³=27 > 24 种情况（信息论下界） |
| 6 | 交互与普通二分的区别？ | 有次数成本 + API 语义需先理解 |
| 7 | 单调性怎么发现？ | isBadVersion 类布尔单调；数组升降段 |
| 8 | 预算不够怎么办？ | 换更高效提问 / 并行提问 / 预处理 |

### 7.3 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| API 语义理解反 | 二分方向错 | 先读 -1/0/1 含义 |
| lo<hi 与 mid 取整不匹配 | 死循环 | 模板统一 |
| 越界调用 | 异常 | 范围检查 |
| 忘估算次数 | 超预算 | log₂n 先算 |
| 边界 n=1 直接二分 | 越界 | 提前返回 |
