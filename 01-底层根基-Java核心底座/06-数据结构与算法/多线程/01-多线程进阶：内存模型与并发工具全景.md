## 1. JMM 与 happens-before

### 1.1 为什么需要 JMM

```
多线程两大问题根源：
  ① 可见性：CPU 缓存（L1/L2/L3）→ 线程读到的可能不是最新值
  ② 有序性：编译器/CPU 指令重排 → 执行顺序可能改变

JMM（Java 内存模型）= 规范"什么时候一定可见、什么时候不能重排"
  共享变量存在主内存；线程操作自己的工作内存（缓存副本）
  → 需要"同步"机制把改动刷回主内存
```

### 1.2 happens-before 八大规则（面试必背）

| # | 规则 | 含义 |
|:---:|------|------|
| 1 | 程序顺序规则 | 单线程内，书写顺序的后续操作可见前面操作 |
| 2 | 锁规则 | 解锁 happens-before 后续加锁（同一个锁） |
| 3 | volatile 规则 | volatile 写 happens-before 后续读 |
| 4 | 传递性 | A 先于 B、B 先于 C → A 先于 C |
| 5 | 线程启动规则 | start() happens-before 该线程的所有操作 |
| 6 | 线程终止规则 | 线程的所有操作 happens-before join() 返回 |
| 7 | 中断规则 | interrupt() happens-before 被中断线程检测到中断 |
| 8 | 对象终结规则 | 构造完成 happens-before finalize() |

> 🎯 **面试必答句**："volatile 写-读、synchronized 解锁-加锁、线程 start/join 都建立 happens-before 关系，保证可见性与有序性。"

### 1.3 as-if-serial 与重排序

```
重排序允许，但必须保证"单线程语义不变"（as-if-serial）
  例：a=1; b=2; 可能重排为 b=2; a=1（无依赖）
  但：a=1; b=a+1; 不能重排（b 依赖 a）

⚠️ 多线程下重排序的破坏性：
  双检锁（DCL）单例：
    实例化 = ① 分配内存 ② 初始化对象 ③ 引用赋值
    重排为 ①③② → 其他线程拿到"未初始化完成"的对象
    → volatile 禁止重排（JDK 5+ 语义完善）
```

## 2. 线程生命周期与中断机制

### 2.1 六状态机（Thread.State）

```
  NEW ──start()──► RUNNABLE ──获锁失败──► BLOCKED（synchronized 等待）
                     │  ▲                    │
        sleep/join/  │  │ 超时/唤醒/join返回   ▼
        wait(超时)   │  └────────────────── TIMED_WAITING
        wait()       │                        │
        ├───────────┴────► WAITING ───────────┘
        ▼                                   ▲
  TERMINATED（run 结束/异常）                notify/notifyAll

⚠️ 关键区别：
  BLOCKED：等锁（synchronized 排队）
  WAITING：等条件（wait/join/park）
  TIMED_WAITING：带超时的等待
```

### 2.2 sleep / wait / join / yield 对比

| 方法 | 释放锁？ | 用途 | 异常 |
|------|:---:|------|------|
| Thread.sleep(t) | ❌ 不释放 | 暂停执行 | InterruptedException |
| Object.wait() | ✅ 释放 | 等条件，配合 notify | InterruptedException |
| Thread.join() | ✅ 释放（内部 wait） | 等线程结束 | InterruptedException |
| Thread.yield() | ❌ | 让出 CPU（提示性） | 无 |
| LockSupport.park() | ❌ | 线程挂起 | 无（响应 interrupt） |

> ⚠️ **高频陷阱**：`sleep` 不释放锁！面试常问"sleep 和 wait 的区别"——**wait 释放锁，sleep 不释放**。

### 2.3 中断机制（协作式）

```java
// 中断不是强制终止，而是"礼貌地请求"：被中断线程自行决定何时响应
Thread t = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {   // 检查中断
        try {
            Thread.sleep(100);
        } catch (InterruptedException e) {
            // ⚠️ ① 恢复中断标志（sleep 会清除标志！）
            Thread.currentThread().interrupt();
            // ② 决定退出
            return;
        }
    }
});
t.interrupt();                        // 发送中断请求

// 最佳实践：
//   catch 后要么重新中断（传递标志），要么退出，不要吞掉异常
//   方法签名声明 throws InterruptedException → 向上传递中断
```

## 3. synchronized 的底层与锁演进

### 3.1 字节码层面

```java
// synchronized 方法：方法级标志 ACC_SYNCHRONIZED
// synchronized 块：monitorenter / monitorexit 指令对
// 底层基于 Monitor（监视器锁），对象头 Mark Word 存锁状态
```

### 3.2 锁升级四阶段（JDK 6+）

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁（竞争激烈时升级，不可降级）

偏向锁     ：第一次持有者记录线程 ID，后续无竞争直接进（单线程场景）
轻量级锁   ：CAS 自旋抢锁，短临界区友好（多线程轻度竞争）
重量级锁   ：OS 互斥量，线程阻塞-唤醒（重度竞争）

⚠️ 锁消除/锁粗化（JIT 优化）：
  无逃逸对象的 synchronized → 直接消除
  相邻多次加锁 → 合并为一次（减少开销）
```

### 3.3 ReentrantLock vs synchronized（JDK 6+ 后）

| 维度 | synchronized | ReentrantLock |
|------|:---:|:---:|
| 用法 | 关键字，自动释放 | 需手动 lock/unlock（finally） |
| 锁粒度 | 块/方法 | 更灵活（可跨方法） |
| 可中断 | ❌ | ✅ lockInterruptibly() |
| 超时 | ❌ | ✅ tryLock(timeout) |
| 公平性 | 非公平 | ✅ 可配公平 |
| 多条件 | ❌（一个条件队列） | ✅ Condition 多个 |
| 性能（JDK 6+） | 与 Lock 相当 | 与 synchronized 相当 |

> 🎯 **选型建议**：默认 synchronized（简洁、自动释放、JVM 可优化）；需要**超时/可中断/多条件/公平**时用 ReentrantLock。

## 4. CAS 与原子类

### 4.1 CAS 原理

```
CAS（Compare And Swap）：
  if (内存值 == 期望值) 则 内存值 = 新值（原子指令）
  失败 → 自旋重试（乐观锁）

优点：无锁（无阻塞、无上下文切换）→ 轻量级竞争性能好
缺点：
  ① ABA 问题：值 A→B→A，CAS 察觉不到（加版本号解决）
  ② 自旋消耗 CPU：高竞争下一直空转
  ③ 只能操作一个变量
```

### 4.2 原子类家族

```java
// 基本原子类
AtomicInteger ai = new AtomicInteger(0);
ai.incrementAndGet();                    // i++ 原子版
ai.compareAndSet(期望值, 新值);           // CAS 核心

// 字段原子类（不装箱）
AtomicIntegerFieldUpdater / VarHandle（JDK 9+）

// ABA 解决：带版本号
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(0, 0);
ref.compareAndSet(0, 10, 0, 1);          // 值+版本都匹配才更新

// 高并发计数首选（分片思想）
LongAdder la = new LongAdder();          // 内部 Cell[] 分片累加
la.increment();                          // 竞争分散到各 Cell
la.sum();                                // 求和（近似）
// ⚠️ 场景：Counter 高频累加（如 QPS 统计）→ LongAdder 快于 AtomicLong
//   需要精确一致的值（如 ID 生成）→ AtomicLong
```

## 5. volatile 深入：DCL 单例的演变

### 5.1 volatile 的读写语义

```
volatile 写：刷新到主内存（后续读可见）—— 建立 happens-before
volatile 读：从主内存读取（不读缓存）
禁止重排序：读写边界不允许跨越（内存屏障）

⚠️ volatile 不保证原子性：
  volatile int i;  i++;  → 读-改-写三步，仍可能丢更新
  → 计数用 AtomicInteger / 锁
```

### 5.2 DCL 单例（面试高频）

```java
class Singleton {
    private static volatile Singleton instance;   // ⚠️ volatile 必须

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                   // ① 快速检查（无锁路径）
            synchronized (Singleton.class) {      // ② 加锁检查
                if (instance == null) {
                    instance = new Singleton();   // ③ 创建
                }
            }
        }
        return instance;
    }
}
// 为什么 volatile 必须：
//   new Singleton() = 分配内存 → 初始化 → 赋值引用（可能重排为 分配→赋值→初始化）
//   线程 B 在"赋值后、初始化前"读到 instance → 拿到半成品
//   volatile 禁止这个重排 → 安全
```

## 6. 并发工具全景

### 6.1 五大协调工具对比

| 工具 | 语义 | 可复用 | 等待方 | 典型场景 |
|------|------|:---:|------|---------|
| CountDownLatch | 倒数 N 次归零放行 | ❌ 一次性 | await 的线程 | 等待 N 个任务完成 |
| CyclicBarrier | N 个线程到齐会合 | ✅ 可循环 | 每个线程互相等 | 分阶段并行计算 |
| Semaphore | 许可数量控制 | ✅ | acquire 的线程 | 限流、资源池 |
| Phaser | 分阶段栅栏（可动态增减） | ✅ | 各阶段参与者 | 复杂分阶段任务 |
| Exchanger | 两线程交换数据 | ✅ | 交换双方 | 缓冲区对换 |

```java
// CountDownLatch：等 N 个任务
CountDownLatch latch = new CountDownLatch(3);
for (int i = 0; i < 3; i++) new Thread(() -> {
    doWork();
    latch.countDown();          // 完成一个 → 倒数 -1
}).start();
latch.await();                  // 3 个都完成才继续
// ⚠️ 与 join 的区别：latch 不持有线程引用，解耦

// CyclicBarrier：N 个线程会合后一起出发
CyclicBarrier barrier = new CyclicBarrier(3, () -> System.out.println("齐了！"));
// 每个线程：work(); barrier.await(); → 3 个 await 齐了才放行（可循环）
```

### 6.2 无锁编程与 CompletableFuture

```java
// 线程间协作进阶：CompletableFuture（回调式，无等待）
CompletableFuture.supplyAsync(() -> fetchFromDb())
    .thenApplyAsync(data -> process(data))
    .thenAcceptAsync(result -> save(result));
// ⚠️ 并发题场景：需要"等待/通知"语义时优先原生工具；
//   编排多异步任务用 CompletableFuture
```

> 🎯 **选型口诀**：**等完成** → CountDownLatch；**到齐出发** → CyclicBarrier；**限流/交接** → Semaphore；**分阶段** → Phaser；**交换** → Exchanger。

## 7. 死锁完整体系

### 7.1 四个必要条件（全满足才死锁）

```
① 互斥：资源一次只能被一个线程占用
② 占有且等待：持有资源的同时等待别的资源
③ 不可剥夺：资源不能被强行抢走
④ 循环等待：A 等 B、B 等 C、C 等 A（环）

⚠️ 面试必答："四个条件缺一不可，破坏任意一个即可避免死锁"
```

### 7.2 死锁实例与检测

```java
// 经典死锁：两个线程交叉加锁
// 线程1：synchronized(A) { synchronized(B) { } }
// 线程2：synchronized(B) { synchronized(A) { } }
// → 各持一把等另一把 → 永久阻塞

// 检测：jstack <pid> → 输出 "Found one Java-level deadlock"
// 或：jconsole 线程页 → 死锁检测按钮
```

### 7.3 避免策略

| 策略 | 手段 | 例子 |
|------|------|------|
| 破坏循环等待 | 全局一致加锁顺序 | 所有线程按 A→B→C 顺序加锁 |
| 破坏占有且等待 | 一次拿全部 | 哲学家"要么两叉一起拿，要么都不拿" |
| 破坏不可剥夺 | 超时放弃 | tryLock(3s) 失败则释放已有锁 |
| 破坏互斥 | 无锁化 | CAS / 不可变对象 |

```
活锁（Livelock）：不阻塞但互相让位，永远不前进（如两人让路）
饥饿（Starvation）：长期抢不到锁（公平锁可缓解）
⚠️ 面试加分："死锁 vs 活锁：死锁是'等'，活锁是'让'——都在原地打转"
```

## 8. 线程池与并发题

### 8.1 核心参数与提交

```java
// 线程池七参数（面试必背）：
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        2,                                // corePoolSize 核心线程
        4,                                // maximumPoolSize 最大线程
        60, TimeUnit.SECONDS,             // 空闲存活时间
        new ArrayBlockingQueue<>(100),    // 任务队列
        Thread::new,                      // 线程工厂
        new ThreadPoolExecutor.AbortPolicy());  // 拒绝策略（默认抛异常）

// 提交方式：
pool.submit(() -> doWork());              // 有返回值 Future
pool.execute(() -> doWork());             // 无返回值（Runnable）
// 关闭：
pool.shutdown();                          // 不再接受新任务，跑完存量
pool.awaitTermination(10, TimeUnit.SECONDS);  // 等待结束（或超时）
```

### 8.2 并发题里用线程池的注意点

```
① 验证"并发执行"：提交 N 个任务后用 CountDownLatch 统一等待
② 提交即执行不保证：任务可能排队 → 验证顺序用 Future.get()
③ 共享可变状态：任务间传值用 CompletableFuture / 原子类
④ 拒绝策略：队列满时 AbortPolicy 抛异常 → 需要处理

⚠️ 面试表达：
"并发题验证用线程池提交 + CountDownLatch 汇聚——
 既能控制并发度，又能验证所有线程都执行完。"
```

## 9. 面试要点与追问

### 9.1 面试话术模板

```
"并发三要素：互斥（synchronized/Lock）、可见性（volatile）、
 有序性（happens-before 规则）。
 这题我用【工具】：【方案描述】。
 关键点：等待必须 while（防虚假唤醒）、
 标志加 volatile、锁在 finally 释放。
 如果需要精确唤醒用 Condition，顺序交接用 Semaphore。"
```

### 9.2 进阶追问 TOP 8

| # | 追问 | 标准回答 |
|:---:|------|------|
| 1 | happens-before 是什么？ | 8 条规则：程序顺序/锁/volatile/传递/start/join/interrupt/finalize |
| 2 | sleep 和 wait 区别？ | wait 释放锁（配合 notify），sleep 不释放 |
| 3 | 锁升级过程？ | 偏向 → 轻量（CAS 自旋）→ 重量（OS 互斥） |
| 4 | CAS 缺点？ | ABA（加版本号）、自旋 CPU、单变量 |
| 5 | DCL 为什么加 volatile？ | 禁止"分配-赋值-初始化"重排，防半成品对象 |
| 6 | CountDownLatch vs CyclicBarrier？ | 一次性等完成 vs 可循环到齐会合 |
| 7 | 死锁四条件？ | 互斥/占有等待/不可剥夺/循环等待，破坏任一即防 |
| 8 | 活锁 vs 死锁？ | 死锁阻塞等待；活锁不停让位不前进 |

### 9.3 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| sleep 里持锁 | 性能阻塞 | 用 wait 释放锁 |
| CAS 无版本号 | ABA 误更新 | AtomicStampedReference |
| 加锁顺序不一致 | 死锁 | 全局统一顺序 |
| 线程池忘关闭 | 资源泄漏 | shutdown + awaitTermination |
| volatile 计数 | 丢更新 | AtomicInteger / 锁 |
