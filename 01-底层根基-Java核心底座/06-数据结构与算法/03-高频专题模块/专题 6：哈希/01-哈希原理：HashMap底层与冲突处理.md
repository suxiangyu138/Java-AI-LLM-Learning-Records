## 1. 哈希表模型：数组定位 + 冲突解决

```text
哈希表 = 数组（桶）+ 哈希函数 + 冲突解决:

  ① 哈希函数: key → 数组下标（int hashCode → index）
  ② 冲突: 不同 key 映射到同一 index（必然存在——鸽巢原理）
  ③ 解决: 拉链法（Java）/ 开放寻址（ThreadLocalMap）/ 再哈希（Redis）

复杂度:
  平均 O(1) get/put/remove（均匀哈希下）
  最坏 O(n)（全部冲突挂同一链）/ O(log n)（树化后）

⚠️ 关键认知: "O(1) 是平均/期望值，不是绝对保证——
  哈希函数质量 + 负载因子 + 冲突解决共同决定实际性能"
```

> 🎯 **面试主线**："**'数组定位 → 冲突处理 → 扩容迁移 → 极端优化'四件事**是 HashMap 面试的总纲——JDK 8 的每个设计（扰动/树化/高低链）都能归到其中一件。"

## 2. 冲突解决的四种方案

| 方案 | 原理 | 代表 | 优缺点 |
|------|------|------|------|
| 链地址法（拉链） | 冲突挂链表/红黑树 | Java HashMap | 实现简单、删除方便、装载因子可 >1；缓存不友好 |
| 开放寻址 | 冲突后找下一个空位 | ThreadLocalMap（线性探测） | 内存连续缓存友好；负载因子敏感（≤0.75）、删除需标记 |
| 再哈希法 | 冲突换哈希函数 | Redis 字典 | 均匀性更好；实现复杂 |
| 公共溢出区 | 冲突统一放单独区 | 教材方案 | 简单；溢出区可能变大 |

```text
开放寻址三种探测:
  线性探测: index+1, +2…（易聚集——主聚集）
  平方探测: +1, +4, +9…（缓解聚集）
  双重哈希: 第二个哈希函数决定步长（最均匀）

⚠️ 面试表达: "Java 用拉链法——冲突少时链表 O(1)，
   冲突极端时树化 O(log n)；开放寻址适合负载因子低、
   缓存敏感的场景（ThreadLocalMap 就是线性探测）。"
```

## 3. HashMap 演进：JDK7 死循环 → JDK8 红黑树

### 3.1 演进对照

| 维度 | JDK 7 及以前 | JDK 8 及以后 |
|------|:---:|:---:|
| 结构 | 数组 + 单向链表 | 数组 + 链表 + **红黑树** |
| 插入 | 头插法 | **尾插法** |
| 最坏查询 | O(n) | **O(log n)**（树化后） |
| 扩容并发 | 头插 → **环形链表死循环** | 尾插 → 无死循环（仍不安全） |
| 冲突优化 | 无 | 链表 ≥8 且容量 ≥64 → 树化 |

```text
JDK7 死循环原理（经典八股）:
  并发扩容时两个线程同时 rehash → 头插法导致链表反向
  → 环形链表 → get 死循环、CPU 100%
JDK8 修复: 尾插法保持原顺序 + 高低链拆分 → 无环

⚠️ 结论: JDK8 只解决了死循环——
  数据覆盖、size 错误、ConcurrentModificationException 仍在
  → 并发场景必须 ConcurrentHashMap（CAS + 细粒度锁）
```

> 🎯 **演进主线**："**HashMap 的每次演进都是'防御更坏输入'——树化防哈希洪水、尾插防并发死循环、扰动防分布不均**。能讲出'为什么改'比背'改了什么'高级。"

## 4. 扰动函数与 2 的幂容量

### 4.1 扰动函数（高低位混合）

```java
// HashMap.hash(key) 的核心（JDK 8）:
static final int hash(Object key) {
    int h = key.hashCode();
    return h ^ (h >>> 16);        // ① 高 16 位与低 16 位异或
}
// 作用: 让高位特征参与寻址（低 16 位与桶数取与时）
//   例: 容量 16 → (n-1)=15 → 只用低 4 位 → 高 28 位浪费
//   扰动后高 16 位"混入"低 16 位 → 冲突概率降低
```

### 4.2 为什么容量必须是 2 的幂（三连问）

```text
① 位运算替代取模: index = (n−1) & hash（等价 hash % n，快得多）
② 分布均匀: n−1 的二进制低位全 1（如 15 = 1111）→ 哈希低位全参与
   （n 不是 2 的幂 → n−1 有 0 位 → 部分位永远用不上 → 分布不均）
③ 扩容高效: 扩容翻倍时用 hash & oldCap 判断——
   结果 0 → 留在原位；非 0 → 移到"原位 + oldCap"
   → 免去全量重新计算哈希（JDK8 的高低链拆分）

⚠️ 指定容量: new HashMap(10) 实际容量 = 16（≥10 的最小 2 的幂）
   预估容量公式: 预期元素数 / 0.75 + 1 再取 2 的幂（避免频繁扩容）
```

> 🎯 **2 的幂三连答**："**效率（位运算）、均匀（低位全 1）、扩容（高低链免重算）**——三个理由缺一不可，是 HashMap 面试的第一追问。"

## 5. 负载因子 0.75 与扩容机制

### 5.1 为什么是 0.75

```text
负载因子 α = size / capacity:
  α 过大（如 1）→ 冲突多、链表长、查询退化
  α 过小（如 0.5）→ 空间浪费、频繁扩容

0.75 = 时间与空间的平衡点:
  泊松分布下 α=0.75 时桶内链表长度分布极佳
  （长度 ≥8 概率 ≈ 0.00000006）
  → 实验与统计的双重最优（面试答"折中 + 统计支撑"）
```

### 5.2 扩容机制（resize）

```text
触发: size > threshold（threshold = capacity × 0.75）
  默认 16 × 0.75 = 12 → 第 13 个元素触发扩容
规则: 容量翻倍（16→32→64…），上限 2^30
JDK8 优化: 高低链拆分——
  (e.hash & oldCap) == 0 → 低位链（留在原位）
  (e.hash & oldCap) != 0 → 高位链（移到 原位 + oldCap）
  → 免全量重算哈希，且保持链内相对顺序（配合尾插防环）

摊还分析: 单次插入平均 O(1)——扩容的 O(n) 搬迁摊到 n 次插入
```

> 💡 **面试表达**："扩容 = 翻倍 + 高低链拆分——**`hash & oldCap` 判断新位置，O(1) 每条链判断，不用重新算哈希**。这是 JDK8 相对 JDK7 的重大优化。"

## 6. 树化阈值 8/6/64：泊松分布的防御

### 6.1 三个数字

| 阈值 | 值 | 含义 |
|------|:---:|------|
| TREEIFY_THRESHOLD | 8 | 链表长度 ≥8 → 尝试树化 |
| UNTREEIFY_THRESHOLD | 6 | 红黑树节点 ≤6 → 退化为链表 |
| MIN_TREEIFY_CAPACITY | 64 | 数组容量 ≥64 才允许树化 |

```text
为什么是 8（泊松分布）:
  负载因子 0.75 + 理想随机哈希下，
  链表长度 ≥8 的概率 ≈ 0.00000006（千万分之六）
  → 正常数据几乎不可能触发树化
  → 树化是"防御机制"而非"性能优化":
     防的是恶意构造大量同哈希 key 的哈希洪水攻击（DoS）

为什么 6 与 8 之间隔 2:
  预留缓冲——避免元素在 7/8 之间波动时
  树与链表频繁互转（转换有开销）

为什么容量 <64 不树化:
  此时扩容（摊还 O(1)）比树化（O(log n)）更划算
  → 先扩容再考虑树化
```

> 🎯 **8 的面试答法**："**树化是防哈希洪水的防御机制——泊松分布下链表到 8 的概率是千万分之六，正常数据不会触发；容量 <64 时扩容比树化划算，所以双条件缺一不可**。'防御而非优化'是关键表述。"

## 7. 线程安全与手写哈希表

### 7.1 线程安全替代方案

| 方案 | 机制 | 定位 |
|------|------|------|
| ConcurrentHashMap（JDK8） | CAS + synchronized 锁单桶 | ✅ 首选（细粒度） |
| Collections.synchronizedMap | 全局锁 | 简单但效率低 |
| Hashtable | 全方法 synchronized | 已过时 |
| 业务加锁 | 自定义 | 灵活但易错 |

```text
JDK8 ConcurrentHashMap:
  桶为空 → CAS 直接放（无锁）
  桶非空 → synchronized 锁该桶头节点（只锁一个桶！）
  → 并发度 = 桶数，远超全局锁

⚠️ 面试谈资: "哈希洪水攻击 = 构造同哈希 key 塞满一桶
   → O(n²) DoS；Java 防御 = 随机化种子 + 红黑树化 +
   容器层参数限制（Tomcat maxParameterCount）"
```

### 7.2 手写哈希表（拉链法 + 扩容）

```java
/**
 * 手写哈希表（链地址法）——面试手撕标准
 * 数组 + 链表 + 负载因子扩容
 */
class MyHashMap {
    private static class Node {
        int key, value;
        Node next;
        Node(int key, int value) { this.key = key; this.value = value; }
    }

    private Node[] buckets;
    private int size = 0;
    private static final double LOAD_FACTOR = 0.75;

    public MyHashMap() { buckets = new Node[16]; }   // 初始容量 16

    public void put(int key, int value) {
        int idx = hash(key);                          // ① 定位桶
        Node head = buckets[idx];
        for (Node cur = head; cur != null; cur = cur.next) {
            if (cur.key == key) { cur.value = value; return; }   // ② 已存在 → 更新
        }
        Node newNode = new Node(key, value);          // ③ 头插新节点
        newNode.next = head;
        buckets[idx] = newNode;
        if (++size > buckets.length * LOAD_FACTOR) resize();     // ④ 超阈值扩容
    }

    public int get(int key) {
        int idx = hash(key);
        for (Node cur = buckets[idx]; cur != null; cur = cur.next) {
            if (cur.key == key) return cur.value;     // ⑤ 链表查找
        }
        return -1;
    }

    private int hash(int key) { return (key ^ (key >>> 16)) & (buckets.length - 1); }

    private void resize() {                           // ⑥ 扩容翻倍 + 重哈希
        Node[] old = buckets;
        buckets = new Node[old.length * 2];
        size = 0;
        for (Node head : old) {
            for (Node cur = head; cur != null; ) {
                Node next = cur.next;
                put(cur.key, cur.value);              // 简化: 重新插入
                cur = next;
            }
        }
    }
}
// ⚠️ 面试要点: 讲清"定位 → 冲突链查找 → 扩容"三步
//   进阶: 扩容用高低链拆分（hash & oldCap）免全量重插
```

> 🎯 **手写哈希表的面试价值**："**能 10 分钟手写'数组 + 链表 + 扩容'的哈希表，说明真懂而非背八股**——705/706 设计题就是它的直接考察，'定位 → 冲突 → 扩容'三步是全部内容。"

> 🎯 **核心要点**：HashMap 通关四件事——**① 四件事主线**（数组定位/冲突/扩容/极端优化）；**② 关键数字**（0.75、8/6/64、2 的幂、>>>16）；**③ 演进故事**（JDK7 头插死循环 → JDK8 尾插 + 树化 + 高低链）；**④ 手写哈希表**（链地址 + 扩容）。**HashMap 是 Java 后端面试八股之王——能把'为什么'讲成一条线（泊松/防御/折中），就超过了 90% 的候选人**。
