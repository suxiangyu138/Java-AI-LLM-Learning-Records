## 一、动态规划

> 动态规划（Dynamic Programming，DP）通过将原问题分解为子问题、存储子问题解来避免重复计算，是以空间换时间的核心算法设计思想。

### 1.1 核心三要素

《算法导论》明确 DP 的适用场景需同时满足三个核心条件：

#### 1.1.1 重叠子问题

原问题可分解为若干个重复出现的子问题，而非独立子问题。

| 对比 | 示例 | 是否可用 DP |
|------|------|-----------|
| 反例 | 查询所有用户列表 + 查询单个用户详情 | 独立子问题，不可用 |
| 正例 | 计算用户的多级权限继承关系 | 父权限、子权限校验逻辑重复，可用 |

> **后端落地**：通常用备忘录模式（数组、HashMap、Spring Cache）存储子问题解，对应自顶向下 DP。

#### 1.1.2 最优子结构

原问题的最优解依赖于其子问题的最优解。

**后端示例**：订单分账场景，需将订单金额按不同比例分给多个角色（商家、平台、服务商），要求分账后各方金额合规且总损耗最小。该问题的最优解，依赖于每个角色分账的最优比例这一子问题的最优解。

> ⚠️ 后端业务中的最优往往不是数学上的最优，而是符合业务规则的约束最优（如合规优先、性能优先）。

#### 1.1.3 无后效性

子问题的解一旦确定，就不会被后续其他子问题的求解所影响。

| 对比 | 示例 | 是否满足 |
|------|------|---------|
| 反例 | 用户等级升级——升级到 VIP2 后，VIP1 的升级条件变化 | 有后效性，不可用 |
| 正例 | 用户积分累计计算——当前积分仅依赖于上一次积分和本次新增积分 | 无后效性，可用 |

### 1.2 DP 实现框架

**第一步：定义状态**。状态是子问题的描述，Java 后端中需与业务模型绑定：

```java
// 商品库存最优分配：dp[i][j] 表示前 i 个仓库分配 j 库存时的最优利用率
int[][] dp = new int[n + 1][capacity + 1];
```

> 💡 对于复杂状态，可定义专门的 DP 状态类封装核心属性，避免多维数组可读性差。

**第二步：确定状态转移方程**。需结合业务规则推导：

```text
场景：接口限流的最优令牌分配
状态定义：dp[t] 表示第 t 分钟的令牌剩余量
状态转移方程：dp[t] = min(dp[t-1] + 生成速率, 令牌上限) - 消耗令牌数
```

**第三步：初始化边界**。需额外考虑业务异常场景：

```java
int[] dp = new int[totalAmount + 1];              // 数组预留边界
Map<Integer, Integer> memo = new HashMap<>(size);  // HashMap 预分配容量
dp[0][0] = 0;  // 0个仓库、0库存时利用率为0
```

**第四步：计算最优解**。

| 计算方式 | 对应《导论》 | 适用场景 | Java 实现 |
|---------|-------------|---------|---------|
| 自顶向下 | 递归 + 备忘录 | 子问题数量不确定、业务逻辑复杂 | 递归 + HashMap/Spring Cache |
| 自底向上 | 迭代 + 数组 | 子问题数量固定、性能要求高 | 数组/ArrayList + Redis 缓存 |

### 1.3 自顶向下 vs 自底向上

| 维度 | 自顶向下（递归+备忘录） | 自底向上（迭代+数组） |
|------|----------------------|---------------------|
| 实现方式 | 递归分解，存储已解子问题 | 从小规模迭代递推至原问题 |
| 空间复杂度 | 较高（递归栈 + 备忘录） | 较低（可滚动优化） |
| 编码难度 | 较低，符合直观思维 | 较高，需把握递推顺序 |
| 性能 | 有递归调用开销 | 无递归开销，通常更快 |

**滚动数组优化示例**（$O(1)$ 空间）：

```java
public int fibonacci(int n) {
    if (n <= 1) return n;
    int prev2 = 0, prev1 = 1;
    for (int i = 2; i <= n; i++) {
        int cur = prev1 + prev2;
        prev2 = prev1;
        prev1 = cur;
    }
    return prev1;
}
```

### 1.4 Java 后端实战

#### 场景1：订单金额拆分（对应钢条切割问题）

**业务需求**：将总金额拆分为优惠券 + 现金 + 积分三部分，积分不超过 30%，优惠券不超过 50%，求积分最大化。

```java
public int[] splitOrderAmount(int totalAmount) {
    int[] dp = new int[totalAmount + 1];
    int maxPoint = (int) (totalAmount * 0.3);
    int maxCoupon = (int) (totalAmount * 0.5);
    for (int i = 1; i <= totalAmount; i++) {
        for (int point = 0; point <= maxPoint; point++) {
            int coupon = Math.min(i - point, maxCoupon);
            if (i - point - coupon >= 0)
                dp[i] = Math.max(dp[i], point);
        }
    }
    int p = dp[totalAmount];
    int c = Math.min(totalAmount - p, maxCoupon);
    return new int[]{c, totalAmount - p - c, p};
}
```

> 💡 将钢条长度替换为订单金额，切割收益替换为积分抵扣金额，融入业务规则（抵扣上限）。


### 1.5 注意事项

| 避坑点 | 说明 | 建议 |
|--------|------|------|
| 不盲目使用 DP | 很多问题不满足三要素 | 先判断是否满足重叠子问题 + 最优子结构 + 无后效性 |
| 平衡性能与空间 | $O(n^2)$ 空间可能导致内存溢出 | 滚动数组优化、Redis 替代内存存储 |
| 结合后端框架 | DP 不能脱离框架存在 | 用 Spring AOP 封装、缓存中间件存备忘录 |
| 遍历顺序错误 | 背包遍历方向易混淆 | 0-1 背包一维逆序，完全背包一维正序 |

## 二、贪心算法

> 在每一步选择中都采取当前最优的选择，期望最终结果是全局最优。核心优势是高效、简洁，无需回溯。

### 2.1 核心前提

**最优子结构**：原问题的最优解包含子问题的最优解。例如后端接口限流中，每个时间片的令牌分配最优解组合起来就是整个限流周期的最优解。

**贪心选择性质**：通过局部最优的选择能构造出全局最优解。这一性质是贪心与 DP 的核心区别——DP 需记录所有子问题解并回溯，而贪心当下选最好的，无需回溯。

> ⚠️ 贪心的短视性既是优势也是局限。若一味贪心分配资源给当前请求量最大的接口，可能导致其他核心接口因资源不足崩溃。

### 2.2 与动态规划对比

| 算法 | 核心逻辑 | 时间复杂度 | 后端典型场景 | Java 注意点 |
|------|---------|-----------|-------------|-------------|
| **贪心** | 局部最优推全局，无回溯 | 通常 $O(n \log n)$ | 限流、调度、资源分配、压缩 | 需验证贪心选择性质 |
| **DP** | 记录子问题解，回溯选最优 | 通常 $O(n^2)$ | 缓存优化、路径规划、复杂调度 | 控制空间复杂度 |
| **分治** | 拆分解子问题再合并 | 通常 $O(n \log n)$ | 大数据排序、分布式任务拆分 | 注意合并效率 |

### 2.3 经典案例

#### 2.3.1 活动选择问题（任务调度）

**理论基础**：选择结束时间最早的活动，能得到全局最优解。映射到后端：服务器多任务调度，选择最多不冲突的任务。

```java
public class GreedyTaskScheduler {
    static class Task {
        String taskId; long startTime, endTime; int priority;
        Task(String id, long s, long e, int p) {
            taskId = id; startTime = s; endTime = e; priority = p;
        }
    }

    private final Lock lock = new ReentrantLock();

    public ArrayList<Task> scheduleTasks(Task[] tasks) {
        lock.lock();
        try {
            if (tasks == null || tasks.length == 0) return new ArrayList<>();
            // 结束时间升序 -> 同结束时间按优先级降序
            Arrays.sort(tasks, Comparator.comparingLong(Task::getEndTime)
                    .thenComparingInt((a, b) -> Integer.compare(b.priority, a.priority)));

            ArrayList<Task> result = new ArrayList<>();
            result.add(tasks[0]);
            long lastEnd = tasks[0].endTime;
            for (int i = 1; i < tasks.length; i++) {
                if (tasks[i].startTime >= lastEnd) {
                    result.add(tasks[i]);
                    lastEnd = tasks[i].endTime;
                }
            }
            return result;
        } finally { lock.unlock(); }
    }
}
```

**后端优化要点**：`ReentrantLock` 保证线程安全；增加任务优先级解决结束时间冲突；Lambda 排序保持 $O(n \log n)$。

#### 2.3.2 哈夫曼编码（日志压缩）

**理论基础**：频率高的字符分配短编码、频率低的分配长编码，构建最优前缀编码。映射到后端：日志压缩减少存储，微服务数据传输降低网络开销。

```java
public class HuffmanCoder {
    static class Node {
        char data; int freq; Node left, right;
        Node(char d, int f) { data = d; freq = f; }
    }

    private Map<Character, String> encode = new HashMap<>();
    private Map<String, Character> decode = new HashMap<>();

    public String compress(String log) {
        if (log == null || log.isEmpty()) return "";
        Map<Character, Integer> freq = new HashMap<>();
        for (char c : log.toCharArray()) freq.put(c, freq.getOrDefault(c, 0) + 1);

        PriorityQueue<Node> pq = new PriorityQueue<>(Comparator.comparingInt(n -> n.freq));
        freq.forEach((k, v) -> pq.add(new Node(k, v)));

        while (pq.size() > 1) {
            Node l = pq.poll(), r = pq.poll();
            Node m = new Node('\0', l.freq + r.freq);
            m.left = l; m.right = r; pq.add(m);
        }

        buildCode(pq.poll(), "");
        StringBuilder sb = new StringBuilder();
        for (char c : log.toCharArray()) sb.append(encode.get(c));
        return sb.toString();
    }

    private void buildCode(Node n, String code) {
        if (n == null) return;
        if (n.left == null && n.right == null) {
            encode.put(n.data, code);
            decode.put(code, n.data);
            return;
        }
        buildCode(n.left, code + "0");
        buildCode(n.right, code + "1");
    }

    public String decompress(String bits) {
        StringBuilder res = new StringBuilder();
        StringBuilder cur = new StringBuilder();
        for (char c : bits.toCharArray()) {
            cur.append(c);
            if (decode.containsKey(cur.toString())) {
                res.append(decode.get(cur.toString()));
                cur.setLength(0);
            }
        }
        return res.toString();
    }
}
```

**后端优化**：`PriorityQueue` 实现 $O(n \log n)$ 贪心合并；反向映射表支持解压；可封装为 Spring Bean 集成到日志框架。

| 场景 | 推荐工具 | 说明 |
|------|---------|------|
| 排序 | `Arrays.sort()` / `Collections.sort()` | 双轴快排 $O(n \log n)$ |

1. 抽象为经典贪心模型（活动选择、资源分配）

3. 小流量测试：上线前验证策略合理性

### 2.5 常见坑点

| 坑点 | 场景 | 避坑 |
|------|------|------|
| 忽略贪心选择性质 | 满减优惠用贪心选最高价商品，无法达门槛 | 改用 DP |
| 未考虑业务复杂性 | 接口限流用固定策略，无法适配流量波动 | 动态调整策略 + 优先级机制 |
| 性能优化不足 | 日志压缩用 ArrayList 存节点导致排序慢 | 使用 `PriorityQueue` |
| 忽略边界场景 | 任务列表为空或时间重叠严重 | 添加边界处理 + 默认方案 |

## 三、摊还分析

> 摊还分析（Amortized Analysis）打破单次操作最坏复杂度的局限，通过计算操作序列总代价得到平均代价（摊还代价），更客观地评价数据结构的实际性能。

### 3.1 核心价值

| 对比 | 特点 | 局限 |
|------|------|------|
| 最坏情况分析 | 关注单次操作上限 | 过于悲观 |
| 平均情况分析 | 依赖概率分布假设 | 实际概率难准确建模 |
| **摊还分析** | 不依赖概率，关注序列总代价上界 | 需保证分析前提成立 |

对于 Java 后端的价值：

| 价值点 | 说明 |
|-------|------|
| **理解 JDK 底层** | HashMap 扩容、ArrayList 增长、ArrayDeque 操作的高效性均依赖摊还分析 |
| **规避性能陷阱** | 线性扩容会导致摊还失效，平均性能退化为 $O(n)$ |
| **优化自定义组件** | 设计缓存、队列时通过摊还分析平衡单次代价，提升吞吐量 |

### 3.2 三种核心方法

| 方法 | 核心思想 | 适用场景 |
|------|---------|---------|
| **聚合分析** | 先算总账再平均分 | 基础场景，简单直接 |
| **核算法** | 提前预支信用支付 | 含多种操作类型的序列 |
| **势能法** | 状态映射势能变化 | 复杂数据结构（动态数组、哈希表） |

#### 3.2.1 聚合分析

**核心思想**：对于 $n$ 个操作的序列，证明最坏情况总代价 $T(n)$，则摊还代价为 $T(n)/n$。

**案例：ArrayList 的 add 操作（$n$ 次从空列表开始）**

```text
- 扩容触发：容量 1 → 2 → 4 → 8 → ... → 2^k (2^k >= n)
- 第 i 次扩容复制 2^(i-1) 个元素
- 总复制代价：1 + 2 + 4 + ... + 2^(k-1) < 2n
- 总插入直接代价：n（每次 O(1)）
- 总代价 T(n) = O(n)，摊还 O(n)/n = O(1)
```

```java
public class MyArrayList {
    private int[] arr = new int[capacity = 1];
    private int size;

    public void add(int val) {
        if (size == capacity) {
            capacity *= 2;
            int[] newArr = new int[capacity];
            System.arraycopy(arr, 0, newArr, 0, size);
            arr = newArr;
        }
        arr[size++] = val;
    }
}
```

> 💡 扩容频率随容量增长呈指数级降低，总代价被 $n$ 次操作平均后仍为 $O(1)$。

#### 3.2.2 核算法

**核心思想**：为不同操作赋予不同摊还代价（预支费用）。摊还高于实际时差额存为信用，摊还低于实际时用信用弥补。

> ⚠️ **约束**：任何时刻总信用不能为负。

**案例：栈的 push（代价 1）/pop（代价 1）/multipop（代价 k）**

```text
分配：push 摊还 2（存 1 信用到元素），pop 摊还 0，multipop 摊还 0
验证：pop 次数 ≤ push 次数，总信用始终非负
总摊还代价 ≤ 2n，单次 O(1)
```

```java
public class MyStack {
    private int[] arr = new int[capacity = 1];
    private int top = -1;

    public void push(int val) {
        if (top == capacity - 1) {
            capacity *= 2;
            int[] newArr = new int[capacity];
            System.arraycopy(arr, 0, newArr, 0, top + 1);
            arr = newArr;
        }
        arr[++top] = val;
    }
}
```

#### 3.2.3 势能法

**核心思想**：将信用绑定到整个数据结构的状态，用势函数 $\Phi$ 映射，摊还代价 = 实际代价 + 势能变化。

$$C^*(i) = C(i) + \Phi(D_i) - \Phi(D_{i-1})$$

> ⚠️ **约束**：$\Phi(D_i) \ge \Phi(D_0)$，确保总摊还代价 $\ge$ 总实际代价。

**案例：HashMap 的 put 操作分析**

```text
势函数：Φ(D) = max(2*size - capacity, 0)

1. 未扩容 put：
   实际代价 1，势能 +2，摊还代价 3 = O(1)

2. 扩容 put（size = capacity*0.75 时触发，容量翻倍）：
   实际代价 = capacity + 1（插入 + 迁移）
   操作前势能 = 0.5*capacity，操作后势能 = 0
   势能变化 = -0.5*capacity
   摊还代价 = 0.5*capacity + 1
   平摊到之前每次插入后，单次 put 仍为 O(1)
```

```java
public class MyHashMap {
    private Node[] table = new Node[capacity = 16];
    private int size;
    static class Node { int key, val; Node next;
        Node(int k, int v) { key = k; val = v; } }

    public void put(int key, int val) {
        if (size >= capacity * 0.75f) {
            capacity *= 2;
            Node[] nt = new Node[capacity];
            for (Node n : table) {
                while (n != null) {
                    int idx = n.key & (capacity - 1);
                    Node next = n.next;
                    n.next = nt[idx]; nt[idx] = n; n = next;
                }
            }
            table = nt;
        }
        int idx = key & (capacity - 1);
        table[idx] = new Node(key, val);
        size++;
    }
}
```

> 💡 若扩容策略改为线性（每次 +1），势函数无法满足约束，平均性能退化到 $O(n)$。

### 3.3 后端实战

#### 组件选型

| 场景 | 推荐组件 | 摊还代价 | 不推荐 | 原因 |
|------|---------|---------|-------|------|
| 栈 | `ArrayDeque` | $O(1)$ | `Stack` | 同步开销 |
| 频繁尾部操作 | `ArrayList` | $O(1)$ | `LinkedList` | 无局部性 |
| 频繁中间插入 | `LinkedList` | $O(1)$ | `ArrayList` | 需搬移 |
| 哈希 | `HashMap` / `ConcurrentHashMap` | $O(1)$ | `Hashtable` | 全局锁 |

#### 规避性能陷阱

| 陷阱 | 场景 | 后果 | 解决 |
|------|------|------|------|
| 线性扩容替代倍增 | 自定义数组每次 +1 | 总代价 $O(n^2)$，摊还 $O(n)$ | 倍增扩容 |
| 高频触发扩容 | HashMap 初始容量不合理 | 额外内存拷贝和哈希迁移 | 预设初始容量 |
| 并发扩容风暴 | JDK 7 ConcurrentHashMap | 总迁移代价超 $2n$ | 升级 JDK 8+ |

#### 自定义组件优化

| 场景 | 问题 | 方案 |
|------|------|------|
| LRU 缓存淘汰 | 每次访问更新节点位置 | 双向链表 + 哈希表 $O(1)$ |
| 批量淘汰过期节点 | 单次淘汰 $O(n)$ | 核算法平摊到每次访问 |
| 批量任务处理 | 批量执行 $O(k)$ | 聚合分析平摊到每个任务 |

## 四、算法对比与选型

### 4.1 DP vs 贪心 vs 分治

| 维度 | 动态规划 | 贪心算法 | 分治算法 |
|------|---------|---------|---------|
| **子问题关系** | 重叠、相互依赖 | 选择后只剩一个子问题 | 独立、不重叠 |
| **决策方式** | 记录所有子问题解并回溯 | 局部最优，无需回溯 | 递归分解后合并 |
| **时间复杂度** | 通常 $O(n^2)$ | 通常 $O(n \log n)$ | 通常 $O(n \log n)$ |
| **核心条件** | 最优子结构 + 重叠子问题 + 无后效性 | 最优子结构 + 贪心选择性质 | 可分解为独立子问题 |
| **正确性** | 保证全局最优 | 需严格证明 | 保证全局最优 |
| **空间复杂度** | 较高（存子问题解） | 较低 | 递归栈空间 |
| **编码复杂度** | 中等偏高 | 低 | 中等 |
| **经典问题** | 背包、LCS、编辑距离 | 活动选择、哈夫曼、Dijkstra | 归并排序、快排 |

### 4.2 后端场景推荐

| 业务场景 | 推荐算法 | 原因 |
|---------|---------|------|
| 接口缓存优化 | 动态规划（备忘录） | 重叠子问题明显，缓存复用中间结果 |
| 定时任务调度 | 贪心算法 | 按结束时间排序，选最多不冲突任务 |
| 日志压缩存储 | 贪心算法（哈夫曼） | 频率统计后贪心合并，压缩率高 |
| 服务路由优化 | 贪心算法（Dijkstra） | 单源最短路径，无需回溯 |
| 优惠券最优组合 | 动态规划（背包） | 含约束条件，需全局最优 |
| 集群拓扑构建 | 贪心算法（Kruskal/Prim） | 最小生成树，贪心策略成立 |
| 海量数据排序 | 分治算法（归并） | 子问题独立，适合分布式 |
| 数据库分表策略 | 动态规划 | 数据分布均匀性需全局优化 |

> ⚠️ **选型原则**：子问题独立无重叠 → 分治；子问题重叠 + 只需局部最优 → 验证贪心选择性质后使用贪心；子问题重叠 + 需全局最优 → 动态规划；分析数据结构操作序列整体性能 → 摊还分析。

## 总结

> 🎯 **三大算法设计技术核心要点**：
>
> **动态规划**：以空间换时间，三要素（重叠子问题、最优子结构、无后效性）缺一不可。自顶向下（递归+备忘录）适合业务复杂场景，自底向上（迭代+数组）适合性能敏感场景。后端中广泛应用于缓存优化、资源分配、最优策略计算。
>
> **贪心算法**：以局部最优推全局最优，核心前提是最优子结构与贪心选择性质。简洁性与高效性完美适配后端高并发高可用诉求，在任务调度、接口限流、日志压缩中发挥不可替代的作用。但需牢记局部最优未必等于全局最优，落地前需严格验证适用边界。
>
> **摊还分析**：弱化单次、聚焦整体，为理解 HashMap、ArrayList、ArrayDeque 等 JDK 核心组件的底层设计提供理论支撑。三种方法（聚合分析、核算法、势能法）从不同角度计算操作序列总代价，得到一致结论。选择倍增扩容而非线性扩容、合理设置初始容量等细节直接决定摊还分析是否有效。
>
> **选型铁律**：分治用于独立子问题，贪心用于可证明贪心选择性质的场景，DP 用于需全局最优的重叠子问题场景，摊还分析用于评价数据结构的操作序列整体性能。将算法理论与 Java 工程实践结合，平衡可读性、性能与可维护性，才是算法落地的核心意义。
