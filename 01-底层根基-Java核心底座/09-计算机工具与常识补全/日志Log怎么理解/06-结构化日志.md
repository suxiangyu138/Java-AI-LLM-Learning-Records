## 1. 为什么需要结构化日志

> **背景**：传统文本日志「给人看」——但采集平台（ELK）需要「机器可解析」。文本解析（正则/Grok）脆弱且性能差。
> **目的**：JSON 结构化让日志「即数据」——字段可索引、可统计、可告警。
> **适用范围**：需要采集/分析的生产系统。
> **不适用场景**：本地开发（文本可读性更好）。

```text
文本 vs 结构化（JSON）
├── 文本日志的问题：
│   ├── 解析靠正则（Grok 模式脆弱）
│   ├── 异常堆栈跨行（解析困难）
│   ├── 字段不可索引（搜索/统计难）
│   └── 自定义解析规则（每项目一套）
├── JSON 日志的优势：
│   ├── 机器可直接解析（无正则）
│   ├── 字段可索引（Kibana 直接搜）
│   ├── 异常堆栈完整封装（不跨行）
│   ├── MDC 字段自动包含
│   └── 采集平台原生支持
└── 金句：结构化日志 = 「日志即数据」——采集/分析/告警全打通
```

## 2. JSON 日志格式


## 3. Logback JSON 配置

### 3.1 依赖与配置

```xml
<!-- 依赖：logstash-logback-encoder -->
<dependency>
    <groupId>net.logstash.logback</groupId>
    <artifactId>logstash-logback-encoder</artifactId>
    <version>7.3</version>
</dependency>
```

```xml
<!-- logback-spring.xml：JSON 输出 -->
<appender name="JSON_FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
    <file>${LOG_PATH}/app.json.log</file>
    <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
        <fileNamePattern>${LOG_PATH}/app.%d{yyyy-MM-dd}.%i.json.log</fileNamePattern>
        <maxFileSize>100MB</maxFileSize>
        <maxHistory>30</maxHistory>
    </rollingPolicy>
    <!-- JSON Encoder（核心） -->
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
        <includeMdc>true</includeMdc>              <!-- 包含 MDC -->
        <includeCallerData>false</includeCallerData>
        <customFields>{"application":"order-service"}</customFields>
    </encoder>
</appender>
```

### 3.2 自定义字段（Composite Encoder）

```xml
<!-- 自定义 JSON 字段（精细控制） -->
<encoder class="net.logstash.logback.encoder.LoggingEventCompositeJsonEncoder">
    <providers>
        <timestamp/>
        <logLevel/>
        <threadName/>
        <loggerName/>
        <message/>
        <mdc/>                        <!-- 所有 MDC 字段 -->
        <stackTrace/>                 <!-- 异常堆栈 -->
        <!-- 自定义字段 -->
        <pattern>
            <pattern>
                {
                  "application": "order-service",
                  "traceId": "%X{traceId:-}",
                  "userId": "%X{userId:-}"
                }
            </pattern>
        </pattern>
    </providers>
</encoder>
```

## 4. Log4j2 JSON 配置

### 4.1 JsonTemplateLayout（原生）

```xml
<!-- Log4j2：自带 JSON 布局（无需第三方） -->
<Appenders>
    <RollingFile name="JSON" fileName="${LOG_PATH}/app.json.log"
                 filePattern="${LOG_PATH}/app.%d{yyyy-MM-dd}.%i.json.log">
        <JsonTemplateLayout>
            <eventTemplate>
                {
                  "timestamp": {"$resolver": "timestamp"},
                  "level": {"$resolver": "level"},
                  "thread": {"$resolver": "thread"},
                  "logger": {"$resolver": "logger"},
                  "message": {"$resolver": "message"},
                  "traceId": {"$resolver": "mdc", "key": "traceId"},
                  "userId": {"$resolver": "mdc", "key": "userId"},
                  "exception": {"$resolver": "exception"}
                }
            </eventTemplate>
        </JsonTemplateLayout>
    </RollingFile>
</Appenders>
```

### 4.2 选择建议

```text
JSON 方案选择（2026）
├── Logback：logstash-logback-encoder（第三方但成熟）
│   ├── LogstashEncoder（快速）
│   └── CompositeJsonEncoder（精细字段控制）
├── Log4j2：JsonTemplateLayout（原生内置）
│   ├── 无需额外依赖
│   └── 模板灵活（eventTemplate）
├── 选型：
│   ├── 已用 Logback → logstash encoder（主流）
│   └── 已用 Log4j2 → JsonTemplateLayout（零依赖）
└── 金句：目标一致（JSON 输出）——按现有框架选方案
```

## 5. 字段设计规范

### 5.1 字段命名规范

```text
JSON 日志字段规范（2026 团队标准）
├── ① 时间：@timestamp（ISO 8601 含时区）
├── ② 级别：level（info/error——小写）
├── ③ 线程：thread
├── ④ 日志器：logger（类名）
├── ⑤ 链路：traceId（MDC）
├── ⑥ 应用：application（服务名）
├── ⑦ 消息：message
├── ⑧ 异常：exception（对象含堆栈）
├── ⑨ 业务：orderId/userId/tenantId（MDC 或结构化消息）
└── ⑩ 性能：durationMs（统一单位 ms）

字段规范要点
├── ① 命名统一（camelCase 或 snake_case 选一）
├── ② 单位明确（durationMs 不是 duration）
├── ③ 类型一致（amount 是数字不是字符串）
├── ④ 避免嵌套过深（采集解析成本）
└── ⑤ 金句：字段规范 = 「采集平台的可视化基础」——规范决定查询体验
```

### 5.2 ECS（Elastic Common Schema）

```text
ECS（Elastic Common Schema）——2026 趋势
├── ① 标准字段体系：统一命名（log.level/process.thread）
├── ② 生态集成：Filebeat/ES 原生支持
├── ③ 好处：跨应用统一（不同服务同字段名）
├── ④ 迁移：文本 → ECS JSON 逐步
└── ⑤ 金句：ECS = 「日志字段的普通话」——大团队/多服务的规范
```

## 6. Key-Value 消息模式

### 6.1 什么是 KV 模式

> **背景**：日志消息里写 `<KEY>=<VALUE>`——采集平台自动提取为字段（无需完整 JSON 结构化）。

```text
KV 模式（消息内嵌键值）
log.info("订单创建 orderId={} amount={} durationMs={}",
         orderId, amount, durationMs);
// 消息文本：订单创建 orderId=ORD-1001 amount=299.0 durationMs=45

采集解析
├── ① Logstash KV filter：自动提取键值
├── ② 效果：orderId 变成可查询字段
├── ③ 优点：文本可读 + 机器可提取
└── ④ 适用：消息级结构化（轻量方案）

规范
├── 键名固定（orderId 不写 order_id/oid）
├── 值无空格（或引号包裹）
├── 数字保持数字（durationMs=45）
└── 金句：KV 是「文本可读 + 字段可查」的平衡方案
```

## 7. 结构化日志实践

### 7.1 完整实践（Java）

```java
// ① 业务日志（结构化消息）
log.info("订单创建 orderId={} amount={} durationMs={}",
         order.getId(), order.getAmount(), costMs);
// → JSON: {"message": "订单创建 orderId=ORD-1001 amount=299.0 durationMs=45"}

// ② MDC 注入业务字段（JSON 自动包含）
MDC.put("orderId", order.getId());
log.info("订单状态变更");
// → JSON: {"message": "订单状态变更", "orderId": "ORD-1001"}

// ③ 异常日志（堆栈完整封装）
log.error("支付失败 orderId={} code={}",
          order.getId(), e.getCode(), e);
// → JSON: {"message": "...", "exception": {"stack_trace": "..."}}

// ④ 指标型日志（KV 可统计）
log.info("接口耗时 path=/api/orders durationMs={} status={}",
         costMs, 200);
// → Logstash 提取 path/durationMs/status 字段
```

### 7.2 实践注意

```text
结构化日志注意
├── ① 本地开发：控制台用文本（可读）
├── ② 生产文件：JSON（采集）
├── ③ 双输出：CONSOLE（文本）+ JSON_FILE（生产）
├── ④ ⚠️ 敏感字段：JSON 同样脱敏（见 04 篇）
├── ⑤ 中文：charset UTF-8（JSON 乱码问题）
└── ⑥ 性能：JSON 编码有开销（异步日志缓解）
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 结构化日志 = 「日志即数据」——JSON 让采集/分析/告警全打通
> 2. 标准 JSON 字段：时间/级别/线程/logger/traceId/message/exception + 业务字段
> 3. Logback 方案：logstash-logback-encoder（LogstashEncoder/CompositeJsonEncoder）
> 4. Log4j2 方案：JsonTemplateLayout（原生零依赖）
> 5. 字段规范：命名统一/单位明确/类型一致——**规范决定查询体验**
> 6. KV 模式：文本可读 + 字段可提取（轻量方案）；ECS 是字段「普通话」（大团队）
> 7. 实践：本地文本 + 生产 JSON 双输出——JSON 同样脱敏
