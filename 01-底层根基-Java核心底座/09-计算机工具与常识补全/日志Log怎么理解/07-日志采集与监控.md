## 1. 日志采集架构

> **背景**：日志在应用产生——采集/存储/分析是独立的链路（与应用解耦）。
> **目的**：理解「应用 → 采集 → 存储 → 分析」的分层。
> **适用范围**：生产环境的日志可观测性。
> **前提假设**：应用输出 JSON 结构化日志（见 06 篇）。

```text
采集架构（2026 主流）
┌────────┐  写文件  ┌────────┐  采集  ┌────────┐  传输  ┌────────┐  索引  ┌────────┐
│ 应用     │ ──────→ │ 日志文件 │ ─────→ │ Filebeat│ ─────→ │ Logstash│ ─────→ │ Elastic│
│ (JSON)  │         │        │        │ (轻量)  │        │ (解析)  │        │ search │
└────────┘         └────────┘        └────────┘        └────────┘        └───┬────┘
                                                                              │ 查询
                                                                         ┌────┴────┐
                                                                         │ Kibana  │
                                                                         │ (分析)  │
                                                                         └─────────┘

两条路径
├── 方案 A：Filebeat → Logstash → ES（标准，解耦）
├── 方案 B：Filebeat → ES（直连，轻量——JSON 无需解析）
└── 方案 C：Logstash 直接接收（Socket——较少）
```

## 2. ELK 全链路

### 2.1 ELK 组件

| 组件 | 作用 | 端口 |
|------|------|:---:|
| **Elasticsearch** | 日志存储与索引 | 9200/9300 |
| **Logstash** | 采集/解析/过滤 | 5044 |
| **Kibana** | 可视化与查询 | 5601 |
| **Filebeat** | 轻量日志采集器 | - |

```text
ELK 各组件职责
├── ① Filebeat：轻量采集（读文件 → 发 Logstash/ES）
│   ├── 低资源占用（Go 编写）
│   └── 断点续读（state 记录）
├── ② Logstash：解析/过滤/增强
│   ├── Grok/Dissect（文本解析）
│   ├── KV/JSON（结构化提取）
│   └── 字段增强（时间戳/环境）
├── ③ Elasticsearch：存储与检索
│   ├── 索引（按天：app-2026.08.04）
│   └── 全文/聚合查询
└── ④ Kibana：可视化
    ├── Discover（搜索日志）
    ├── Dashboard（仪表盘）
    └── Alerting（告警）
```

### 2.2 快速验证（Docker Compose）

```yaml
# docker-compose.yml（ELK 快速启动）
services:
  elasticsearch:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.x

      - discovery.type=single-node

    depends_on: [elasticsearch]
```

## 3. Filebeat 采集配置

```yaml
# filebeat.yml（采集应用日志）
filebeat.inputs:
  - type: filestream          # 现代类型（替代 log）
    enabled: true
    paths:
      - /var/log/app/*.json.log    # 采集 JSON 日志
    fields:
      application: order-service   # 附加字段
    fields_under_root: true        # 字段到根

output.logstash:
  hosts: ["logstash:5044"]         # 发往 Logstash

# 或直连 ES（JSON 无需解析时）
# output.elasticsearch:
#   hosts: ["elasticsearch:9200"]
#   index: "app-{application}-%{+yyyy.MM.dd}"
```

```text
Filebeat 要点
├── ① filestream 类型（新）替代 log（旧）
├── ② paths：采集哪些文件（JSON 文件）
├── ③ fields：附加环境字段（应用名/环境）
├── ④ 断点续读：崩溃后从上次位置继续
├── ⑤ 多行合并：JSON 单行日志无需（文本需 multiline）
└── ⑥ 金句：Filebeat 是「搬运工」——不解析只传输
```

## 4. Logstash 解析

### 4.1 基础配置

```ruby
# logstash.conf
input {
  beats {
    port => 5044          # 接收 Filebeat
  }
}

filter {
  # JSON 日志直接解析（结构化）
  json {
    source => "message"
    target => "log"
  }

  # 时间戳规范
  date {
    match => ["@timestamp", "ISO8601"]
  }

  # 移除原始消息（减少存储）
  mutate {
    remove_field => ["message", "log"]
  }
}

output {
  elasticsearch {
    hosts => ["elasticsearch:9200"]
    index => "app-%{application}-%{+yyyy.MM.dd}"
  }
}
```

### 4.2 文本日志解析（Grok）

```ruby
# 文本日志（非 JSON）用 Grok 解析
filter {
  grok {
    match => { "message" =>
      "%{TIMESTAMP_ISO8601:timestamp} %{LOGLEVEL:level} \[%{DATA:thread}\] %{DATA:logger} \[%{DATA:traceId}\] - %{GREEDYDATA:msg}"
    }
  }
}
# ⚠️ 2026 建议：新系统直接 JSON（Grok 脆弱）
# 金句：Grok 是「文本解析的兜底」——JSON 是正解
```

## 5. Kibana 分析与查询

### 5.1 常用查询

```text
Kibana 查询（KQL/DSL）
├── ① 基本搜索：
│   level:ERROR                       # 错误日志
│   traceId:a1b2c3d4e5f6              # 链路串联（核心！）
│   orderId:ORD-1001                  # 按业务字段
├── ② 组合：
│   level:ERROR AND application:order-service
│   message: "支付失败" OR "超时"
├── ③ 时间范围：近 15 分钟/1 小时/自定义
├── ④ 聚合统计：
│   ├── ERROR 数量趋势
│   ├── 接口耗时分布（durationMs）
│   └── 按服务/级别分组
└── ⑤ 金句：traceId 搜索 = 一次请求的全部日志（时间线）

排查场景（Kibana 工作流）
├── ① 用户报障 → 时间 + 订单号
├── ② 搜 orderId → 找到 traceId
├── ③ 搜 traceId → 全链路日志
├── ④ 时间线查看 → 定位失败环节
└── ⑤ 看 exception → 根因
```

### 5.2 Dashboard 设计

```text
日志 Dashboard（2026 推荐面板）
├── ① 错误总览：ERROR 数量趋势（按服务）
├── ② 慢请求：durationMs P95/P99
├── ③ 接口状态：HTTP 状态码分布
├── ④ 链路健康：traceId 成功/失败比例
├── ⑤ 资源：磁盘/内存（结合指标）
└── ⑥ 金句：Dashboard = 「日志的仪表盘」——一屏看健康
```

## 6. 日志告警

### 6.1 告警配置（Kibana Alerting）

```text
日志告警场景（2026 常用）
├── ① ERROR 数量阈值：5 分钟 ≥ 10 次
├── ② 特定错误出现：支付失败/连接超时
├── ③ 接口耗时超标：durationMs P95 > 2s
├── ④ 无日志（静默）：服务无输出（可能挂）
├── ⑤ 特定 traceId 缺失：链路断裂
└── ⑥ 安全事件：登录失败激增

告警配置要点
├── ① 阈值合理（避免误报/漏报）
├── ② 告警渠道：邮件/钉钉/企业微信/飞书
├── ③ 收敛：同问题合并（防告警轰炸）
├── ④ 升级：P1 → 值班；P2 → 白天处理
└── ⑤ 金句：告警 = 「日志的哨兵」——问题出现先于用户发现
```

### 6.2 告警示例（Elasticsearch Watcher）

```json
{
  "trigger": { "schedule": { "interval": "5m" } },
  "input": {
    "search": {
      "request": {
        "indices": ["app-*"],
        "body": {
          "query": {
            "bool": {
              "filter": [
                { "term": { "level": "ERROR" } },
                { "range": { "@timestamp": { "gte": "now-5m" } } }
              ]
            }
          }
        }
      }
    }
  },
  "condition": { "script": { "source": "ctx.payload.hits.total.value >= 10" } },
  "actions": {
    "webhook": { "webhook": { "url": "https://hooks.example.com/alert" } }
  }
}
```

## 7. 替代方案对比

| 方案 | 特点 | 适用 |
|------|------|------|
| **ELK** | 功能全、生态大、资源重 | 标准选择 |
| **Loki** | 轻量、便宜（只索引标签） | 中小团队/K8s |
| **Datadog** | SaaS、APM 集成 | 有预算/全球化 |
| **Graylog** | 中量级、GELF 协议 | 中等规模 |
| **云日志服务** | 云厂商托管（SLS/CLS） | 已用云厂商 |

```text
方案选型（2026）
├── ① 标准选择：ELK（自建/托管）
├── ② 轻量替代：Loki + Grafana（K8s 场景友好）
├── ③ 云托管：阿里 SLS/腾讯 CLS/华为 LTS（免运维）
├── ④ SaaS：Datadog（预算充足）
├── ⑤ 选型依据：规模 × 预算 × 运维能力
└── ⑥ 金句：日志采集的目标是「可查询」——方案是手段
```

## 8. 采集运维要点

```text
日志采集运维（2026 要点）
├── ① 磁盘管理：滚动策略 + totalSizeCap（见 03 篇）
├── ② 索引管理：ILM（索引生命周期）——按天索引 + 过期删除
├── ③ 容量规划：单条日志大小 × 量 × 保留期
├── ④ 性能：采集端资源（Filebeat 轻量）/ES 写入压力
├── ⑤ 时区统一：时间戳含时区（ISO 8601）
├── ⑥ 幂等：重复采集去重（file_id + offset）
├── ⑦ 安全：日志含敏感信息（脱敏——见 04 篇）
└── ⑧ 灾备：ES 集群高可用（多节点）

常见问题
├── ⚠️ 采集不到：路径/权限/Filebeat 状态
├── ⚠️ 解析失败：JSON 非法（编码/截断）
├── ⚠️ 索引增长快：ILM 策略未配置
└── ⚠️ 时区错乱：时间戳无时区信息
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 采集链路：应用（JSON）→ Filebeat（搬运）→ Logstash（解析）→ ES（存储）→ Kibana（分析）
> 2. **结构化 JSON 是采集的基础**——Grok 文本解析是兜底（脆弱）
> 3. Filebeat 要点：filestream 类型 + fields 附加环境 + 断点续读
> 4. Kibana 核心查询：level/traceId/orderId——**traceId 串联全链路**
> 5. 告警场景：ERROR 阈值/特定错误/耗时超标/静默——阈值合理 + 收敛 + 升级
> 6. 方案选型：ELK（标准）/Loki（轻量）/云托管（免运维）/Datadog（SaaS）
> 7. 运维要点：滚动策略 + ILM 索引管理 + 时区统一 + 脱敏
