## 1. 语言国际化能力对比

> **背景**：字符串模型决定国际化基础——「字符串是字节数组还是 Unicode 序列」是关键分野。
> **目的**：理解各语言国际化能力，选型与排障有据。
> **适用范围**：多语言开发；国际化需求的项目。
> **前提假设**：2026 年所有主流语言源码默认 UTF-8。

| 语言 | 字符串模型 | Unicode 支持 | 国际化 API | 2026 评价 |
|------|-----------|:---:|-----------|:---:|
| **Java** | char[]（UTF-16）+ Compact Strings | ✅ 原生 | ✅ java.text/Locale | ⭐⭐⭐⭐⭐ |
| **C++** | 字节数组（std::string） | ⚠️ 需 ICU | ⚠️ 弱（C++20 改善） | ⭐⭐ |
| **PHP** | 字节序列（无编码信息） | ⚠️ 需 mbstring | ⚠️ intl 扩展 | ⭐⭐⭐ |
| **JS** | UTF-16 序列（原生） | ✅ 原生 | ✅ ECMA-402 | ⭐⭐⭐⭐ |
| **Python** | str（Unicode 原生） | ✅ 原生 | ✅ 标准库 | ⭐⭐⭐⭐⭐ |
| **Go** | 字节 + rune | ✅ 原生 | ⚠️ 基础 | ⭐⭐⭐⭐ |

> 🎯 **结论**：**Java/Python/JS 原生支持 Unicode（字符串是字符序列）；C++/PHP 字符串是字节序列（需库/扩展补足）**——这是国际化能力的根本分野。

## 2. Java：原生 Unicode 支持

### 2.1 设计特点

> **背景**：Java 从 1995 年诞生就设计为 Unicode——char 16 位、String 是字符序列。
> **目的**：跨语言/跨平台的一致性（Java 的口号 "write once, run anywhere" 也包括文字）。
> **适用范围**：大型企业应用、多语言系统。
> **不适用场景**：需要极致内存效率的极简场景。

```text
Java 的国际化设计
├── ① 字符串模型：char[]（UTF-16）
│   ├── Java 9+ Compact Strings（Latin-1 优化为 byte[]）
│   └── char = UTF-16 单元（BMP 外需代理对）
├── ② 编码支持：java.nio.charset（全编码）
│   ├── StandardCharsets.UTF_8 等常量
│   └── Charset.forName("GBK") 等动态获取
├── ③ 国际化 API：java.text + java.util
│   ├── Collator（排序）/ DateFormat / NumberFormat
│   ├── Locale（语言+地区）
│   └── ResourceBundle（资源文件）
├── ④ 默认编码：Java 18+ UTF-8（JEP 400）
└── ⑤ 码点支持：codePoint API（代理对安全）
```

### 2.2 Java 国际化实战

```java
// 编码转换（Java 标准）
String text = "中文测试";
byte[] utf8 = text.getBytes(StandardCharsets.UTF_8);   // UTF-8 字节
byte[] gbk = text.getBytes(Charset.forName("GBK"));    // GBK 字节
String back = new String(gbk, Charset.forName("GBK")); // 解码

// Locale 与格式化
Locale zhCN = Locale.SIMPLIFIED_CHINESE;
Locale enUS = Locale.US;

// 数字格式化（不同地区格式不同）
NumberFormat nf = NumberFormat.getNumberInstance(zhCN);
nf.format(1234567.89);   // 1,234,567.89（中文也是逗号）

// 日期格式化
DateFormat df = DateFormat.getDateTimeInstance(
    DateFormat.MEDIUM, DateFormat.MEDIUM, zhCN);
df.format(new Date());   // 2026-8-4 17:00:00

// 排序（中文按拼音）
Collator collator = Collator.getInstance(zhCN);
collator.compare("张", "王");   // 按拼音（张 zhang > 王 wang）

// 资源文件（i18n 标准做法，见 05 篇）
ResourceBundle bundle = ResourceBundle.getBundle("messages", zhCN);
bundle.getString("welcome");   // messages_zh_CN.properties
```

## 3. C++：标准库的短板与 ICU

### 3.1 历史问题

> **背景**：C++ 的 std::string 本质是字节数组——不含编码信息；wchar_t 宽度跨平台不一致。
> **目的**：理解 C++ 国际化的痛点与解决方案。
> **适用范围**：C++ 项目的国际化需求。
> **不适用场景**：无国际化需求的内部工具（std::string 够用）。

```text
C++ 国际化的历史痛点
├── ① std::string = 字节数组（不知道是什么编码）
├── ② wchar_t 宽度不可移植：
│   ├── Windows：2 字节（UTF-16）
│   └── Linux：4 字节（UTF-32）
├── ③ C++98/03 无 Unicode 原生类型
├── ④ 标准库无 Locale 感知的字符串处理
└── ⑤ 结论：C++ 国际化「靠自己」（ICU 等）

演进（C++11+）
├── char16_t/char32_t + u16string/u32string
├── C++20：std::u8string（UTF-8 明确类型）
├── C++20：std::format（格式化）
└── 2026 提案 P3688R6：标准 ASCII 工具函数
    （ascii_is_digit/ascii_to_lower——明确 ASCII 边界）
```

### 3.2 ICU 解决方案

```text
ICU（International Components for Unicode）
├── 工业级 Unicode 库（IBM 主导，开源）
├── 能力：编码转换/排序/格式化/断词/正则
├── C++ 绑定：icu4c
├── 替代：Boost.Locale（封装 ICU）
└── 场景：C++ 项目的正规国际化方案

C++ 工程建议（2026）
├── ① 内部统一 UTF-8（u8string）
├── ② 边界转换用 ICU（编码可靠）
├── ③ 排序/格式化用 ICU（Collator/NumberFormat）
├── ④ 避免裸 wchar_t（跨平台陷阱）
└── ⑤ 性能优先 + 可接受 ICU 依赖才选 C++ 国际化
```

## 4. PHP：mbstring 与 intl

### 4.1 模型与问题

> **背景**：PHP 字符串是「二进制安全的字节序列」——不内置编码信息。
> **目的**：理解 PHP 国际化依赖扩展的原因。
> **适用范围**：PHP Web 开发的国际化。
> **前提假设**：现代 PHP 开发强制 UTF-8 + mbstring。

```text
PHP 字符串模型
├── ① 字符串 = 字节数组（无编码元数据）
├── ② 内置函数是字节级（strlen 是字节数！）
│   ├── strlen("中文") = 6（3 字符 × 2？不，UTF-8 是 3 字节 × 2 = 6）
│   └── ⚠️ 字节级函数处理多字节 = 乱码/截断
├── ③ 解决方案：mbstring 扩展
│   ├── mb_strlen（字符数）
│   ├── mb_substr（安全截断）
│   ├── mb_convert_encoding（转换）
│   └── mb_check_encoding（校验）
└── ④ intl 扩展：封装 ICU（排序/格式化/本地化）

PHP 8+ 改善
├── 8.0：mb_check_encoding 增强
├── 8.0：Stringable 等
└── 底层模型未变（仍需 mbstring 纪律）
```

### 4.2 PHP 国际化实践

```php
<?php
// PHP UTF-8 纪律（2026 标准）
header('Content-Type: text/html; charset=utf-8');
mb_internal_encoding('UTF-8');      // 设置内部编码

// 字符数（不是字节数！）
$len = mb_strlen('中文测试');        // 4（strlen 会是 12）

// 安全截断（不切半个字符）
$sub = mb_substr('中文测试', 0, 2);  // "中文"

// 编码转换（GBK → UTF-8）
$utf8 = mb_convert_encoding($gbk, 'UTF-8', 'GBK');

// 校验（防止非法 UTF-8）
if (!mb_check_encoding($input, 'UTF-8')) {
    // 拒绝/清理（安全要点！）
}

// 国际化（intl 扩展）
$fmt = new NumberFormatter('zh_CN', NumberFormatter::DECIMAL);
echo $fmt->format(1234567.89);      // 1,234,567.89
```

## 5. JavaScript：ECMA-402 国际化 API

### 5.1 字符串模型

> **背景**：JS 字符串原生是 UTF-16 序列——Unicode 支持内置；ECMA-402 提供国际化 API。
> **目的**：理解 JS 的 Unicode 处理与国际化标准。
> **适用范围**：浏览器/Node.js 的国际化。
> **注意**：JS 的 length 也是 UTF-16 单元数（Emoji 算 2）。

```javascript
// JS 字符串的 Unicode 特性
"😊".length;                    // 2（UTF-16 单元！）
[...'😊'].length;               // 1（迭代器按码点）
Array.from('😊').length;        // 1

// 码点访问
'😊'.codePointAt(0);            // 0x1F60A
String.fromCodePoint(0x1F60A);  // '😊'
```

### 5.2 ECMA-402（2027 规范）

```javascript
// ECMA-402 国际化 API（浏览器/Node 原生）
// 数字格式化
new Intl.NumberFormat('zh-CN').format(1234567.89);
// "1,234,567.89"

// 货币
new Intl.NumberFormat('zh-CN', {
    style: 'currency', currency: 'CNY'
}).format(1234.5);
// "¥1,234.50"

// 日期
new Intl.DateTimeFormat('zh-CN').format(new Date());
// "2026/8/4"

// 排序（语言感知）
['张', '王', '李'].sort(new Intl.Collator('zh-CN').compare);
// 按拼音排序

// 相对时间
new Intl.RelativeTimeFormat('zh-CN').format(-3, 'day');
// "3 天前"

// 复数规则（国际化难点）
new Intl.PluralRules('en').select(2);   // "other"
```

> 🎯 **ECMA-402 的意义**：国际化 API 成为语言标准（2027 规范持续演进）——**排序/格式化/复数不再手写**，用 Intl 对象。

## 6. 语言选型建议（2026）

### 6.1 按需求的选型

```text
国际化需求 → 语言选型
├── 强国际化（多语言产品/企业应用）→ Java（原生最强）/ Python
├── Web 前端国际化 → JS（Intl 原生）
├── 中文为主 + 快速开发 → PHP（mbstring 纪律）/ Java
├── 性能极致 + 可接受 ICU → C++
├── 微服务/云原生 → Go（UTF-8 原生 + 基础 i18n）
└── 数据科学/脚本 → Python（Unicode 原生）

决策要点
├── ① 字符串模型：字符序列（Java/Python/JS）vs 字节数组（C++/PHP）
├── ② 标准库覆盖：Locale/排序/格式化是否内置
├── ③ 默认编码：UTF-8 是否默认（Java 18+/Python 3/Go 是）
└── ④ 生态：第三方库成熟度（ICU/ICU4J）
```

### 6.2 通用最佳实践（跨语言）

```text
跨语言国际化最佳实践（2026）
├── ① 内部统一 UTF-8（字符串/文件/数据库）
├── ② 边界显式转换（文件/数据库/网络入口出口）
├── ③ 排序/格式化用标准库 API（不手写）
├── ④ Locale 显式指定（不依赖默认——土耳其 i 陷阱）
├── ⑤ 用户输入校验编码（非法 UTF-8 拒绝/清理）
├── ⑥ 字符串长度用「字符数」而非「字节数」（多字节语言）
├── ⑦ 源码文件 UTF-8（编译器/IDE 配置）
└── ⑧ 数据库 utf8mb4（MySQL 完整 Unicode）
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. **语言分野**：Java/Python/JS 字符串是字符序列（原生 Unicode）；C++/PHP 是字节数组（需 ICU/mbstring）
> 2. Java 国际化全家：Charset + Locale + Collator/DateFormat/NumberFormat + ResourceBundle——原生最强
> 3. C++ 痛点：std::string 无编码信息 + wchar_t 宽度不可移植——正规方案用 ICU（C++20 u8string 改善）
> 4. PHP 纪律：一切多字节操作走 mbstring（mb_strlen/mb_substr/mb_convert_encoding）+ intl 扩展
> 5. JS 的 ECMA-402：Intl.NumberFormat/DateTimeFormat/Collator/PluralRules——国际化成为语言标准
> 6. 通用实践：内部 UTF-8 + 边界转换 + 显式 Locale + 编码校验——**跨语言一致**
