## 1. 心态第一：代码是给人读的

> 🎯 **第一习惯**：写代码时假设「下一位维护者是一个知道你家地址的暴力狂」——他会带着愤怒读你的代码。代码的**阅读时间与编写时间之比约为 10:1**，每一次「写得更快」都以「读得更慢」为代价。

```
代码的读者优先级
├── ① 6 个月后的自己（最常读，最容易被自己坑）
├── ② 团队同事（共同维护）
├── ③ 代码审查者（PR 时逐行读）
└── ④ 编译器/解释器（最不重要，它不挑剔）
→ 结论：可读性 > 炫技；表达意图 > 展示聪明
```

| ❌ 反面心态 | ✅ 正面心态 |
|-----------|-----------|
| 「能跑就行」 | 「能跑 + 能改 + 能查」 |
| 「先写后改」 | 「边写边按习惯」 |
| 「这代码没人看」 | 「下一任维护者就是我自己」 |

## 2. 命名七原则

### 2.1 原则速查

| # | 原则 | 示例 |
|---|------|------|
| 1 | **意图揭示**：名字说明「为什么存在、做什么」 | ❌ `d` ✅ `elapsedTimeInDays` |
| 2 | **避免误导**：不用与含义不符的缩写 | ❌ `hp` ✅ `currentPage` |
| 3 | **可发音**：能读出来的名字 | ❌ `genymdhms` ✅ `generationTimestamp` |
| 4 | **可搜索**：全局可唯一搜索到 | ❌ `x` ✅ `MAX_ORDER_AMOUNT` |
| 5 | **方法动词、类名词** | ✅ `getOrders()` / `OrderService` |
| 6 | **一致术语**：同一概念永远同一名字 | 统一 `fetch` 或统一 `query`，不混用 |
| 7 | **命名即文档**：好名字消灭注释需求 | ✅ `isOrderExpired(order)` 无需注释 |

### 2.2 命名决策表

```java
// 好的命名示例（Java）
public class OrderService {
    private final OrderRepository orderRepository;
    private final PaymentGateway paymentGateway;

    // ✅ 意图揭示：方法名说明行为 + 预期结果
    public OrderResult refundExpiredOrder(String orderId) { ... }

    // ✅ 布尔方法用 is/has/can 前缀
    public boolean isRefundable(Order order) { ... }

    // ❌ 反例：泛泛而谈
    public void process(String id) { ... }      // 处理什么？
    public Object data;                          // 什么数据？
    public List<String> list;                    // 谁的列表？
}
```

> 💡 **命名即重构**：如果你需要注释解释名字，通常说明名字不够好——**先改名，再考虑加注释**。改名是最高性价比的重构（2026 年 AI 最可靠的机械改动）。

## 3. 函数设计五规则

### 3.1 规则速查

| # | 规则 | 标准 | 反面 |
|---|------|------|------|
| 1 | **单一职责** | 一个函数只做一件事 | 函数名是「and」连接的 |
| 2 | **短小** | 理想 <20 行 | 一屏放不下 |
| 3 | **单层抽象** | 函数内代码同一抽象层级 | 业务逻辑混 SQL 细节 |
| 4 | **少参数** | 0-3 个最佳；超 3 个封装对象 | 6 个裸参数 |
| 5 | **无副作用** | 函数不悄悄改全局状态 | 查询方法偷偷改缓存 |

### 3.2 函数示例

```java
// ❌ 反面：又长又杂，三个职责混在一起
public void saveOrder(HttpRequest request) {
    String orderId = request.getParameter("id");           // 解析
    String json = request.getBody();                        // 解析
    Order order = objectMapper.readValue(json, Order.class); // 反序列化
    if (order.getAmount() == null) { throw new IllegalArgumentException(); } // 校验
    order.setStatus("PAYING");
    orderRepository.save(order);                            // 持久化
    paymentGateway.notify(order);                           // 通知（副作用！）
    log.info("saved: " + orderId);                          // 日志
}

// ✅ 正面：每个函数一个职责，同级抽象
public void saveOrder(HttpRequest request) {
    Order order = parseOrder(request);      // 解析（第一层抽象）
    validateOrder(order);                    // 校验
    orderRepository.save(order);             // 持久化
}

private Order parseOrder(HttpRequest request) {
    String orderId = requireId(request);     // 解析内部再分层
    return objectMapper.readValue(request.getBody(), Order.class)
            .withId(orderId);
}

private void validateOrder(Order order) {
    if (order.getAmount() == null) {
        throw new InvalidOrderException("订单金额不能为空", order.getId());
    }
}
```

### 3.3 参数对象封装

```java
// ❌ 6 个裸参数
public void createOrder(String userId, String productId, int quantity,
                        BigDecimal price, String address, String couponId) { }

// ✅ 参数对象封装（>3 个参数时）
public void createOrder(CreateOrderCommand cmd) { }

record CreateOrderCommand(String userId, String productId, int quantity,
                          BigDecimal price, String address, String couponId) { }
```

## 4. 四大原则：DRY / KISS / YAGNI / SOLID

### 4.1 DRY（不重复自己）

> ⚠️ **关键边界**：**两个重复是巧合，三个重复才是模式**——不到三处不要急着抽象，过早抽象是另一种重复（重复了错误的抽象）。

```text
DRY 正确姿势
├── ❌ 两处相似代码就抽公共方法（可能为时过早）
├── ✅ 三处及以上重复 → 抽象（2026 重构指南共识）
└── ⚠️ 抽的是「逻辑」不是「外观」：同样逻辑但形式不同也算重复
```

### 4.2 KISS（保持简单）

```text
KISS 决策表
├── 简单实现能达成 → 用简单的（未来证明复杂再升级）
├── 聪明的实现带来什么收益？→ 无收益 = 砍掉
├── 每多一层抽象 = 多一个理解成本
└── 金句：简单是最高级的复杂（简单 ≠ 简陋，而是无多余）
```

### 4.3 YAGNI（不需要就别做）

```text
YAGNI 反模式
├── ❌ 「以后可能会用到多租户，现在先设计上」
├── ❌ 「这个接口加个泛型版本，更通用」
├── ❌ 预测性抽象 / 预测性参数 / 预测性配置
└── ✅ 实际需求出现时再抽象——那时你才真正理解需求
```

### 4.4 SOLID（面向对象五大原则）

| 原则 | 一句话 | 违例信号 |
|------|--------|---------|
| **S** 单一职责 | 一个类一个理由去改变 | 类名含「And」 |
| **O** 开闭 | 对扩展开放、对修改关闭 | 改旧代码才能加新功能 |
| **L** 里氏替换 | 子类可替换父类且行为正确 | 子类抛出父类不抛的异常 |
| **I** 接口隔离 | 客户端不需要的方法别放接口 | 接口有一堆空实现 |
| **D** 依赖反转 | 依赖抽象不依赖实现 | new 具体类散落各处 |

> 🎯 **2026 务实提醒**：原则是路标不是教条——**忘记僵硬的教条和武断的规则**，在可读性、性能与交付速度间做权衡。SOLID 服务于可维护性，不为原则而原则。

## 5. 坏味道识别

### 5.1 常见坏味道清单

| 坏味道 | 信号 | 解法 |
|--------|------|------|
| **长函数** | 一屏放不下 | 提取方法 |
| **巨型类** | 职责混杂 | 拆分/抽取 |
| **重复代码** | Ctrl+C/V 痕迹 | 提取（≥3 处） |
| **魔法数字** | 裸数字 86400 | 命名常量 |
| **长参数列表** | 4+ 裸参数 | 参数对象 |
| **注释掉的代码** | 历史遗留 | **直接删除（Git 有历史）** |
| **霰弹式修改** | 改一个需求动 5 个文件 | 重构内聚 |
| **依恋情结** | 函数依赖别的类数据 | 移动方法 |

### 5.2 坏味道处理的优先级

```text
坏味道处理优先级（投入产出比）
├── P0：删除注释掉的代码（零风险，立即做）
├── P0：魔法数字 → 常量（零风险）
├── P1：重复代码提取（≥3 处）
├── P1：长函数拆解
├── P2：巨型类拆分（需测试保障）
└── P3：架构级重构（绞杀者模式，长期）
```

## 6. 重构六技术（2026）

> 📊 2026 年重构指南：六种技术覆盖约 **90%** 的清理工作：

| # | 技术 | 说明 | 风险 | AI 协助度 |
|---|------|------|:---:|:---:|
| 1 | **提取方法 + 重命名** | 最安全、最机械 | 低 | ✅✅（AI 最可靠） |
| 2 | **抽象化重构** | 三处重复才抽象 | 中 | ⚠️ 人工判断 |
| 3 | **条件转多态** | 消灭膨胀的 if/switch 树 | 中 | ⚠️ |
| 4 | **红绿重构** | TDD 安全网下激进重构 | 低（有测试） | ✅ |
| 5 | **预备性重构** | Kent Beck：让改变变容易，再做容易的改变 | 低 | ✅ |
| 6 | **绞杀者模式** | 遗留系统渐进替换 | 低 | ⚠️ |

> 💡 **Kent Beck 预备性重构**：改代码前先问「这个改变为什么这么难？」——先重构让改变变容易，再做改变本身。**重构提交与功能提交分离**，让审查者看清每个提交的意图。
