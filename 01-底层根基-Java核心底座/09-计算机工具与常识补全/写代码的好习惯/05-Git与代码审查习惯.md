## 1. Git 提交的好习惯

### 1.1 提交粒度

> 🎯 **黄金法则**：**一个提交 = 一个逻辑变更**——能独立描述「为什么」的变更单元。

```text
提交粒度决策
├── ✅ 好：新增订单导出功能（一个逻辑单元）
├── ✅ 好：修复退款并发 bug（一个逻辑单元）
├── ❌ 坏：改了订单模块 + 顺手改了日志配置 + 格式化代码（三个逻辑混一起）
├── ❌ 坏：大提交（100 文件）——无法审查、无法回滚、无法 blame
└── 检验：提交信息能一句话说完 = 粒度合适
```

### 1.2 提交习惯三规

| 规则 | 说明 |
|------|------|
| **小步提交** | 功能完成一个单元就提交（不要憋大招） |
| **可编译提交** | 每个提交都应是可编译/可测试的状态（bisect 友好） |
| **勿提交生成物** | 构建产物/依赖/密钥进 .gitignore |

> 💡 **提交即检查点**：小步提交让 `git bisect` 能定位问题引入的提交，让 `git revert` 能精准回滚单个功能。

## 2. 提交信息规范

### 2.1 Conventional Commits 规范

```text
<type>(<scope>): <subject>        # 标题（≤50 字符）

<body>                             # 正文：为什么 + 怎么验证

<footer>                           # 关联：issue / breaking change
```

| Type | 用途 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(order): 新增订单导出功能` |
| `fix` | 修复 bug | `fix(refund): 修复并发重复退款` |
| `refactor` | 重构（不改行为） | `refactor(order): 提取校验逻辑` |
| `docs` | 文档 | `docs: 更新部署文档` |
| `test` | 测试 | `test(order): 补充边界用例` |
| `chore` | 杂项 | `chore: 升级依赖版本` |
| `perf` | 性能优化 | `perf(query): 缓存热点查询` |

### 2.2 好提交信息示例

```text
fix(refund): 修复并发场景下重复退款

订单关闭与退款回调并发时，退款逻辑可能执行两次，
导致客户收到两笔退款。增加幂等键（requestId）拦截重复请求。

验证：新增并发测试用例 refund_shouldBeIdempotent，全量测试通过。
```

### 2.3 提交信息质量对照

| ✅ 好 | ❌ 坏 |
|-------|------|
| `fix(order): 修复金额精度丢失（Double→BigDecimal）` | `fix bug` |
| `feat(search): 支持分页与排序参数` | `update` |
| `refactor(auth): 提取 Token 校验为独立组件` | `整理代码` |

> 🎯 **Git 历史 = 团队知识资产**：好的提交历史让新人通过 `git log` 就能理解项目演进——「为什么这么设计」都写在提交里。

## 3. 分支与合并策略

### 3.1 常用策略对比

| 策略 | 适用 | 特点 |
|------|------|------|
| **Git Flow** | 复杂发布（多版本并行） | 分支多、规则重 |
| **GitHub Flow** | 持续交付（主流 2026） | 单 main + 功能分支 + PR |
| **Trunk-based** | CI/CD 极速团队 | 短分支/直接合入 main |

### 3.2 GitHub Flow 实践（推荐）

```text
GitHub Flow 工作流
├── main 永远可部署（一切以 main 为基准）
├── 功能分支：feature/xxx（短命，几天内合并）
├── 提交：小步提交 + 规范信息
├── PR：功能完成 → 提 PR → 审查 → CI 绿 → 合并
└── 合并后删除分支
→ 优点：简单、直观、适合持续交付团队
```

```bash
# 功能分支实践
git checkout -b feature/order-export
# ...小步提交...
git push origin feature/order-export
# 提 PR → 审查 → CI 通过 → squash merge
```

### 3.3 合并方式选择

| 方式 | 效果 | 适用 |
|------|------|------|
| **Squash Merge** | 功能压成一个提交 | 功能分支（历史干净，推荐） |
| **Rebase Merge** | 线性历史 | 需要保留每个小提交 |
| **Merge Commit** | 保留分支历史 | 长功能/多协作者 |

## 4. 代码审查流程

### 4.1 审查的价值

> 📊 行业共识：代码审查是缺陷发现率最高、成本最低的质量手段——且 2026 年 AI 时代审查成为「必须」而非「建议」（AI 生成代码默认不信任，见 06 篇）。

### 4.2 PR 规范（提交方习惯）

```text
好 PR 的五个要素
├── ① 小：单功能、可审查（<400 行变更）
├── ② 有描述：做了什么 + 为什么 + 怎么验证
├── ③ 有测试：功能变更必须带测试
├── ④ 自审过：提 PR 前自己先过一遍 diff
├── ⑤ CI 绿：流水线全通过再请求审查
└── PR 模板示例：
    ## 变更内容
    ## 为什么
    ## 验证方式（测试/截图）
    ## 影响范围
```

### 4.3 审查方习惯

```text
审查者四习惯
├── ① 及时响应：当天审完（拖慢审查 = 拖慢交付）
├── ② 对事不对人：批评代码不批评作者
├── ③ 区分严重度：P0 阻塞 / P1 应改 / P2 建议
└── ④ 给予认可：好设计也值得点赞（正反馈循环）
```

## 5. 审查清单

### 5.1 通用审查清单（六查）

| # | 检查项 | 具体问题 |
|---|--------|---------|
| 1 | **正确性** | 边界条件？并发安全？空值？ |
| 2 | **可读性** | 命名清晰？函数短小？注释解释 Why？ |
| 3 | **健壮性** | 错误处理？超时？幂等？ |
| 4 | **安全性** | 注入？硬编码密钥？权限？ |
| 5 | **测试** | 测试覆盖核心场景？边界与异常？ |
| 6 | **性能** | 循环内 SQL？无谓的重复计算？ |

### 5.2 AI 代码审查专属清单（2026 新增）

```text
AI 生成代码的审查重点（与人写代码不同）
├── ① 幻觉检查：方法/类/依赖是否真实存在
├── ② 夹带检查：是否改动了任务外的文件（AI 常顺手改）
├── ③ 风格一致性：是否与既有代码风格一致（AI 倾向自创）
├── ④ 边界遗漏：AI 默认只处理快乐路径
├── ⑤ 安全默认值：硬编码密钥/不校验输入（AI 默认不安全）
└── ⑥ 回归风险：是否影响现有功能（AI 常误改相关代码）
```

## 6. 重构与提交的关系

### 6.1 Kent Beck 预备性重构

> 💡 **预备性重构**：改代码前先问「为什么这个改变这么难？」——先重构让改变变容易，再做改变本身。

```text
重构与功能分离提交
├── commit 1: refactor(order) 提取校验逻辑（纯重构，行为不变）
├── commit 2: feat(order) 新增金额校验规则（功能）
└── 价值：
    ├── 审查者看清每个提交的意图
    ├── 重构出错可单独回滚（不影响功能）
    └── git bisect 定位准确
```

### 6.2 重构提交的验证

```text
重构提交的验证习惯
├── 重构前：全量测试绿（安全网确认）
├── 重构后：全量测试依然绿（行为未变证明）
├── 禁止：重构与功能混在一个提交（无法验证行为不变）
└── 金句：重构不改变行为——测试全绿就是重构成功的证据
```

## 7. 技术债管理

### 7.1 技术债的正确认知

> 🎯 **技术债不是耻辱**：它是快速交付的合理代价——问题不在有债，在于**无记录、无计划、无偿还**的隐形债。

```text
技术债四象限（Martin Fowler）
├── ① 有意+短期：快速上线，记录 TODO（合理）
├── ② 有意+长期：计划内重写（可接受但需排期）
├── ③ 无意+短期：代码混乱未察觉（危险）
└── ④ 无意+长期：无人知晓的烂账（致命——最难还）
→ 习惯：把技术债变成「记录在案、可见、有优先级」的清单
```

### 7.2 技术债管理习惯

| 习惯 | 做法 |
|------|------|
| **记录** | 发现即记录（TODO 带署名/Issue/债清单文档） |
| **量化** | 估算偿还成本（复杂度/风险评分） |
| **排期** | 每迭代预留 10-20% 时间偿还 |
| **童子军** | 改到哪清理到哪（顺手小重构） |
| **预防** | 新代码质量门禁（防止新增债务） |

> 🎯 **2026 AI 时代警示**：AI 生成的代码若没有质量门禁，技术债会以 10 倍速度累积（AI Slop）——**技术债管理从「自觉」变成「门禁强制」**。

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 一个提交 = 一个逻辑变更；每个提交可编译可测试（bisect 友好）
> 2. Conventional Commits 规范 + 描述「为什么」——Git 历史是团队知识资产
> 3. GitHub Flow（main 可部署 + 功能分支 + PR）是 2026 主流；PR 小而有描述、当天审完
> 4. 重构与功能分提交（测试绿 = 行为不变证明）；技术债记录在案、每迭代偿还 10-20%
