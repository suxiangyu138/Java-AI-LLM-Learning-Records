## 1. 注释的黄金法则

> 🎯 **黄金法则**：注释解释 **Why（为什么）**，不解释 **What（是什么）**——「是什么」代码自己会讲，「为什么」只有人知道。

```java
// ❌ 反面：解释 What（代码已经说了）
// 遍历订单列表并计算总价
double total = 0;
for (Order o : orders) {
    total += o.getAmount();
}

// ✅ 正面：解释 Why（代码之外的知识）
// 按业务规则：已关闭订单不参与财报统计（与财务约定 2024-Q3）
for (Order o : orders) {
    if (!o.isClosed()) {
        total += o.getAmount();
    }
}
```

| 该注释的 | 不该注释的 |
|---------|-----------|
| 为什么这么写（业务约束） | 代码在做什么 |
| 为什么不用另一种写法 | 显而易见的逻辑 |
| 历史决策（踩过的坑） | 方法名已说明的内容 |
| 警告与陷阱（勿动） | 逐行翻译代码 |

## 2. 注释五原则

| # | 原则 | 说明 | 示例 |
|---|------|------|------|
| 1 | **解释 Why** | 业务规则/历史背景/设计取舍 | `// 时区统一用 UTC，避免夏令时问题` |
| 2 | **警告与后果** | 高风险区域提示 | `// 此方法有副作用：会发送通知，勿在事务中调用` |
| 3 | **TODO 带责任** | TODO 必须署名 + 日期 | `// TODO(张工, 2026-08): 接入新支付网关后移除兼容层` |
| 4 | **Javadoc 公共 API** | 公共接口必须文档 | `/** 按订单号查询，不存在返回 Optional.empty() */` |
| 5 | **注释随代码更新** | 改代码必改注释 | 注释过期比没有注释更危险 |

> ⚠️ **注释是债务**：注释需要维护，过期的注释误导读者——**宁可没有注释，不要错误注释**。每条注释都是「为什么值得写」的证明。

## 3. 自文档化代码

### 3.1 什么是自文档化

**自文档化**：代码本身即文档——好名字 + 清晰结构让读者无需注释就能理解：

```java
// ❌ 需要注释才能懂
if (d > 30) { expire(); }

// ✅ 自文档化（名字说明一切）
if (order.isOverdue(30)) { order.markExpired(); }
```

### 3.2 自文档化四件套

```text
自文档化技术
├── ① 意图命名：isOverdue 比 d > 30 更说明意图
├── ② 提取方法：把逻辑块变成动词命名的方法
├── ③ 常量命名：MESSAGE_TTL_SECONDS = 86400 代替 86400
├── ④ 结构表达：用类型/类结构表达约束（如 record/不可变）
└── 目标：注释数量趋近于零，但可读性不降反升
```

> 💡 **判断标准**：如果一段代码需要注释才能看懂，先重构代码而不是写注释——**注释是最后的补充，不是第一的依靠**。

## 4. API 文档习惯

### 4.1 Javadoc 规范（Java 公共 API）

```java
/**
 * 创建订单。
 *
 * <p>创建成功后订单状态为 PAYING，并触发支付网关通知。
 *
 * @param command 创建订单命令（必填）
 * @return 创建后的订单信息
 * @throws InvalidOrderException 订单参数不合法（金额为空/商品不存在）
 * @throws OrderLimitExceededException 用户当日下单数超限
 */
public Order createOrder(CreateOrderCommand command) { ... }
```

### 4.2 文档要点对照

| 内容 | 说明 | 反面 |
|------|------|------|
| **契约说明** | 前置条件/后置条件/副作用 | 只写参数列表 |
| **异常声明** | 何时抛什么异常 | 不写异常 |
| **示例代码** | 复杂 API 附使用示例 | 无示例 |
| **版本标记** | @since/@deprecated | 无版本信息 |

### 4.3 文档的「写多少」决策

```text
文档密度决策
├── 公共 API（被外部调用的）：必须完整 Javadoc
├── 内部私有方法：自文档化优先，必要时一行 Why
├── 业务规则复杂处：块注释解释业务背景
└── 过度文档 = 噪音：每行都注释 = 没有注释
```

## 5. 可读性工程

### 5.1 可读性五要素

| 要素 | 习惯 | 示例 |
|------|------|------|
| **空行分组** | 逻辑块之间空一行 | 校验 / 业务 / 持久化三段 |
| **缩进统一** | 团队格式化工具强制 | Prettier / Black / Spotless |
| **命名一致** | 同概念同词 | 全用 fetch 或全用 query |
| **小步提交** | 一次提交一个逻辑变更 | 便于 blame 追溯 |
| **结构先行** | 大方法先列骨架再填细节 | 注释骨架或按序拆分 |

### 5.2 格式化工具是底线

```text
2026 年可读性基线（工具强制，不靠自觉）
├── 格式化器：Black(Python) / Prettier(JS/TS) / Spotless(Java)
├── Linter：Ruff / ESLint / Checkstyle
├── 类型检查：mypy strict / pyright / 编译器
├── Pre-commit hooks：提交前自动运行
└── CI 门禁：格式不合规直接 CI 失败
→ 原则：把可读性变成机器检查，而非人的自觉
```

## 6. 注释坏味道与处置

### 6.1 注释坏味道清单

| 坏味道 | 表现 | 处置 |
|--------|------|------|
| **注释掉的代码** | 大段历史代码用 // 屏蔽 | **直接删除**（Git 历史里能找到） |
| **冗余注释** | 解释显而易见的事 | 删除 |
| **误导注释** | 代码改了注释没改 | 修正或删除 |
| **日志式注释** | `// 2026-01-01 修复 bug` | 交给 Git 历史 |
| **归属注释** | `// 张三写的，别动` | 交给 Git blame |
| **框式注释** | 大段 `/* ===== */` 装饰 | 精简 |

### 6.2 处置铁律

> ⚠️ **铁律：永不注释掉代码——要么删除，要么保留执行。** 注释掉的代码是「不会执行的谎言」：它误导读者以为该逻辑存在，还占维护成本。Git 是完美的时间机器，恢复它只需 `git log -S` 一条命令。

```bash
# 找回被删代码（Git 时间机器）
git log -S "deletedMethodName" --oneline   # 找到删除它的提交
git show <commit> -- path/to/file          # 查看当时的完整代码
```

> 🎯 **2026 补充**：注释掉的代码还有一个新危害——**AI 会把注释掉的代码误认为有效逻辑**（AI 读上下文时会把它当作参考模式）。删除它，既为人也为 AI。

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 黄金法则：注释解释 Why 不解释 What——「是什么」交给代码
> 2. 注释五原则：Why/警告/TODO 署名/公共 API Javadoc/随代码更新
> 3. 自文档化四件套（意图命名/提取方法/常量命名/结构表达）——注释是最后补充
> 4. 铁律：**永不注释掉代码**（Git 可恢复；且注释代码会误导 AI）；格式化/Lint 交给工具强制
