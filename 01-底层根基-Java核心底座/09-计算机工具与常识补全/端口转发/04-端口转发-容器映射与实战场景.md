## 1. Docker 端口映射

### 1.1 -p 参数详解

> **背景**：容器默认有独立网络命名空间——容器内端口宿主不可达。`-p` 做宿主机端口 → 容器端口映射（底层是 iptables DNAT）。
> **目的**：把容器服务暴露到宿主机/外部。
> **适用范围**：Docker 单机部署的服务暴露。
> **前提假设**：宿主机端口未被占用；防火墙（ufw/firewalld）放行宿主机端口。

```bash
# 格式：-p [宿主机IP:]宿主机端口:容器端口[/协议]

# 最简（随机映射宿主端口，不推荐生产）
docker run -p 8080 myapp            # 宿主随机端口 → 容器 8080
docker port <容器>                  # 查看实际映射

# 标准（指定宿主端口）
docker run -p 8080:8080 myapp

# 指定协议
docker run -p 8080:8080/tcp -p 53:53/udp myapp

# 仅本地访问（安全：不暴露公网）
docker run -p 127.0.0.1:8080:8080 myapp

# 多个端口
docker run -p 8080:8080 -p 5005:5005 myapp

# 端口范围（批量）
docker run -p 8000-8005:8000-8005 myapp
```

### 1.2 运行后的管理

```bash
# 查看映射
docker ps                          # PORTS 列显示映射
docker port <容器>                 # 详细映射列表

# 运行中容器补映射（新版本支持）
docker update --publish-add 9090:9090 <容器>

# docker-compose 写法
services:
  app:
    ports:
      - "8080:8080"                # 标准映射
      - "127.0.0.1:5005:5005"      # 仅本机（调试端口）
      - "53:53/udp"                # UDP
```

## 2. Docker 网络模式与转发

### 2.1 网络模式对比

| 模式 | 端口暴露 | 适用 | 性能 |
|------|---------|------|:---:|
| **bridge（默认）** | `-p` 映射（iptables DNAT） | 单机标准 | 中 |
| **host** | 直接用宿主端口（无映射） | 高性能/特殊 | 最好 |
| **none** | 无网络 | 隔离场景 | - |
| **overlay** | Swarm 跨主机 | 集群 | 中 |

### 2.2 host 模式的注意

```bash
# host 模式：容器直接用宿主机网络（-p 无效！）
docker run --network host myapp
# ⚠️ 容器监听的端口就是宿主端口——无需 -p 也无法用 -p
# ⚠️ 端口冲突：容器端口与宿主已有服务冲突即失败
# ✅ 适用：性能敏感/UDP 组播/端口不可预测的服务
```

### 2.3 容器间通信（不走 -p）

```text
容器间通信（无需端口映射）
├── ① 同 bridge 网络：直接用服务名/容器名互访
│   docker run --network mynet --name app1 ...
│   docker run --network mynet --name app2 ...
│   app2 访问 app1：http://app1:8080（容器名解析）
├── ② 同宿主机不同网络：--link（旧）或共同网络
└── ③ 外部访问容器：才需要 -p 映射
→ 关键认知：-p 是「宿主↔容器」的桥，不是「容器↔容器」的桥
```

## 3. Kubernetes 端口暴露三方式

### 3.1 三种方式对比

| 方式 | 层级 | 场景 | 适用 |
|------|:---:|------|:---:|
| **port-forward** | 开发调试 | 本地访问 Pod（临时） | ⭐⭐⭐⭐⭐ |
| **NodePort** | 节点端口 | 集群外简单访问 | ⭐⭐⭐ |
| **LoadBalancer** | 云负载均衡 | 云环境公网暴露 | ⭐⭐⭐⭐ |
| **Ingress** | 七层路由 | HTTP 服务正式暴露 | ⭐⭐⭐⭐⭐ |

### 3.2 NodePort（节点端口暴露）

```yaml
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  type: NodePort
  selector:
    app: order
  ports:
    - port: 8080              # 集群内访问端口
      targetPort: 8080        # Pod 容器端口
      nodePort: 30080         # 节点暴露端口（30000-32767）
# 访问：http://任意节点IP:30080
```

### 3.3 Ingress（生产标准）

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: order-ingress
spec:
  rules:
    - host: order.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: order-service
                port:
                  number: 8080
# 前提：集群已部署 Ingress Controller（Nginx/Traefik）
# 生效链路：DNS → Ingress Controller → Service → Pod
```

### 3.4 三种方式的选择

```text
K8s 暴露方式选择
├── 开发调试 → kubectl port-forward（最轻量）
├── 临时外部访问 → NodePort（不依赖云 LB）
├── 云环境公网 → LoadBalancer（云厂商 LB + 安全组）
├── HTTP 服务正式 → Ingress（域名/HTTPS/路由）
└── 生产标准组合：Ingress + Service（ClusterIP）
```

## 4. kubectl port-forward 调试

### 4.1 用法

```bash
# Pod 端口转发（本地调试利器——零配置暴露）
kubectl port-forward pod/order-xxxxx 8080:8080

# Service 端口转发
kubectl port-forward svc/order-service 8080:8080

# Deployment（自动选 Pod）
kubectl port-forward deployment/order 8080:8080

# 多端口
kubectl port-forward pod/xxx 8080:8080 5005:5005

# 绑定指定地址（远程访问调试）
kubectl port-forward --address 0.0.0.0 pod/xxx 8080:8080
# ⚠️ 默认绑定 127.0.0.1；--address 0.0.0.0 才对外暴露（注意安全！）

# 指定 namespace
kubectl -n prod port-forward pod/xxx 8080:8080
```

### 4.2 应用场景与限制

```text
port-forward 场景
├── ✅ 本地连集群内数据库（kubectl port-forward svc/mysql 3306:3306）
├── ✅ 调试 Pod 内的服务（抓包/接口测试）
├── ✅ 访问集群内未暴露的管理端口
└── ⚠️ 限制：
    ├── 单会话临时（断开即失效）
    ├── 走 API Server 中转（性能有限）
    └── 生产流量不适用（用 Service/Ingress）
```

## 5. 云安全组与防火墙配合

### 5.1 安全组是「云上的防火墙」

> ⚠️ **容器/云端口转发的完整链路**：`安全组（云）→ 宿主防火墙（ufw/firewalld）→ iptables DNAT → 容器`——任何一层拦截都访问不通：

```text
云环境端口暴露链路（三层都要放行！）
① 云安全组：入方向规则（云控制台）
   例：放行 8080/tcp 来源 0.0.0.0/0（或指定 IP）
② 宿主防火墙：ufw/firewalld（如果启用）
   sudo ufw allow 8080/tcp
   # 或 firewall-cmd --add-port=8080/tcp
③ Docker 映射：-p 8080:8080（iptables DNAT 自动）
→ 经典故障：安全组放了、Docker 映射了，但宿主 ufw 没放行 → 不通
```

### 5.2 云平台端口转发注意

```text
云平台专项注意
├── ① 国内云：对外提供 Web 服务需 ICP 备案（80/443 未备案禁开放！）
├── ② 安全组最小化：只开必要端口 + 限定来源 IP
├── ③ 高危端口：22/3389 改高位端口或限定来源
├── ④ 安全组 vs 防火墙：两层都要配（纵深防御）
└── ⑤ 云 LB 场景：流量经 LB → 安全组 → 实例——LB 层先放行
```

## 6. 容器转发陷阱清单

| # | 陷阱 | 现象 | 解法 |
|---|------|------|------|
| 1 | **-p 后端口占用** | 启动报 bind 失败 | 换端口/杀占用进程 |
| 2 | **host 模式用 -p** | 映射无效（host 无网络隔离） | host 模式不写 -p |
| 3 | **容器间用 -p 互访** | 绕远且易错 | 同网络用容器名直连 |
| 4 | **只配安全组没配宿主防火墙** | 外部不通本地通 | 三层链路都放行 |
| 5 | **K8s NodePort 超范围** | 30000-32767 之外报错 | 用范围内端口 |
| 6 | **port-forward 断连** | 终端关闭即断 | 用 tmux 或 kubectl 后台 |
| 7 | **0.0.0.0 绑定暴露** | 调试端口被公网访问 | 默认 127.0.0.1 + 用时开 |
| 8 | **重启丢映射** | 容器重启 -p 丢失 | compose/编排文件声明 |

## 7. 核心要点

> 🎯 **核心要点**：
> 1. Docker -p 底层是 iptables DNAT——宿主机端口被占用即启动失败
> 2. 容器间通信走网络名直连，-p 只负责「宿主↔容器」桥接
> 3. K8s 四方式：port-forward（调试）/NodePort（临时）/LoadBalancer（云公网）/Ingress（生产 HTTP）
> 4. 云暴露三层链路：安全组 → 宿主防火墙 → Docker 映射——**任一层拦截都不通**（经典故障）
> 5. 国内合规：80/443 对外 Web 需 ICP 备案；高危端口（22/3389）改高位或限来源
