## 1. 排查场景全景

> **背景**：端口排查三类场景——启动失败（被占）、连不上（未监听/防火墙）、看不到（绑定地址）。
> **目的**：建立「症状 → 命令 → 结论」的排查框架。
> **适用范围**：所有平台（Windows/Linux/macOS）。

```text
三类排查场景
├── ① 启动失败：「Port 8080 was already in use」
│   ├── 目标：找到占用进程 → 杀掉或换端口
├── ② 连不上：「Connection refused/timeout」
│   ├── 目标：服务是否监听 + 防火墙 + 绑定地址
├── ③ 看不见：「端口没出现在列表」
│   └── 目标：绑定地址问题（127.0.0.1 vs 0.0.0.0）
→ 金句：先分清「启动失败」还是「连不上」——排查路径完全不同
```

## 2. Windows 排查命令

### 2.1 netstat 基本用法

```cmd
:: 查看所有端口及占用
netstat -ano

:: 查看指定端口（找到 PID——关键！）
netstat -ano | findstr "8080"

:: 根据 PID 查看对应进程
tasklist | findstr "PID号"

:: 或一步到位（PowerShell）
Get-NetTCPConnection -LocalPort 8080
Get-Process -Id <PID>
```

### 2.2 Windows 完整流程

```cmd
:: ① 查端口占用（得到 PID）
netstat -ano | findstr "8080"
::   TCP    0.0.0.0:8080    0.0.0.0:0    LISTENING    12345
::                                                       ↑ PID

:: ② 查 PID 对应进程（判断能否杀）
tasklist | findstr "12345"
::   java.exe     12345  Console  1   1,234 KB

:: ③ 杀进程（确认是多余的）
taskkill /PID 12345 /F

:: ④ 验证端口释放
netstat -ano | findstr "8080"    :: 无输出 = 已释放

:: 附加技巧
:: 查看监听端口列表
netstat -ano | findstr "LISTENING"
:: 查看 TIME_WAIT 数量（端口耗尽诊断）
netstat -ano | findstr "TIME_WAIT" | find /c /v ""
```

## 3. Linux 排查命令

### 3.1 ss（现代首选）

```bash
# ss（socket statistics）——现代 Linux 首选（快）
ss -tlnp                    # 所有 TCP 监听（含进程）
ss -ulnp                    # UDP 监听
ss -tlnp | grep 8080        # 指定端口
#   LISTEN 0 100 0.0.0.0:8080 0.0.0.0:* users:(("java",pid=12345,fd=52))
#                                                       ↑ 进程

# 按进程查
ss -tlnp | grep java        # java 占用的端口
```

### 3.2 lsof 与 netstat

```bash
# lsof（按文件描述符查）
lsof -i :8080               # 指定端口占用
#   java  12345 user  52u  IPv6 123456  TCP *:8080 (LISTEN)
lsof -i :8080 -P -n         # 不解析主机名（更快）
lsof -p 12345 | grep TCP    # 某进程的 TCP 连接

# netstat（传统）
netstat -tlnp | grep 8080
netstat -tunap               # 全部 TCP/UDP 连接

# 杀进程
kill 12345                   # 优雅停止
kill -9 12345                # 强制（最后手段）

# 验证
ss -tlnp | grep 8080         # 无输出 = 已释放
```

### 3.3 macOS 补充

```bash
# macOS 用 lsof（netstat 参数不同）
lsof -i :8080
lsof -iTCP -sTCP:LISTEN      # 所有监听端口
kill -9 <PID>
```

## 4. 端口状态解读

### 4.1 TCP 状态一览

| 状态 | 含义 | 排查提示 |
|------|------|---------|
| **LISTEN** | 服务在监听 | 服务正常启动 |
| **ESTABLISHED** | 已建立连接 | 正常通信中 |
| **TIME_WAIT** | 连接关闭等待 | 高并发时堆积（正常但可优化） |
| **CLOSE_WAIT** | 对方关闭、本端未关 | **程序 bug**（连接未正确关闭） |
| **SYN_SENT** | 正在发起连接 | 目标不可达/防火墙 |
| **SYN_RECV** | 收到连接请求 | 半连接（可能被攻击） |
| **CLOSED** | 已关闭 | 正常 |

```text
状态解读要点
├── ① 服务没启动：端口无 LISTEN
├── ② CLOSE_WAIT 堆积：程序未关闭连接（🔴 bug 信号）
│   └── 常见：连接池泄漏/异常未 finally 关闭
├── ③ TIME_WAIT 多：短连接高频（高并发场景）
│   └── 优化：连接复用/调优参数
└── ④ SYN_RECV 多：可能 SYN 洪水（安全告警）
```

### 4.2 CLOSE_WAIT 实战（Java 场景）

```text
CLOSE_WAIT 堆积的排查（Java 后端常见）
├── ① 症状：连接数持续增长（ss -tan | grep CLOSE_WAIT）
├── ② 根因：响应流未关闭
│   ├── InputStream/OutputStream 未 close
│   ├── 异常路径未关闭（缺 finally/try-with-resources）
│   └── HTTP 客户端连接未释放
├── ③ 解法：try-with-resources（自动关闭）
├── ④ 验证：修复后 CLOSE_WAIT 不再增长
└── ⑤ 金句：CLOSE_WAIT 堆积 = 「连接开了没关」——资源泄漏
```

## 5. 常见排查流程

### 5.1 启动失败流程

```text
「Port already in use」排查流程
├── ① 确认端口：报错信息（8080）
├── ② 找占用进程：
│   ├── Windows：netstat -ano | findstr 8080 → PID
│   ├── Linux：ss -tlnp | grep 8080 → PID
│   └── 判断进程：tasklist（Win）/ ps -p PID -f（Linux）
├── ③ 决策：
│   ├── 自己的残留 → 杀掉（taskkill/kill）
│   ├── 别的服务在用 → 换端口（--server.port=8081）
│   └── 系统服务 → 绝不动（换端口）
└── ④ 验证：重新启动成功
```

### 5.2 连不上流程

```text
「服务连不上」排查流程（三层）
├── ① 服务在监听？（ss -tlnp | grep 端口）
│   ├── 无 LISTEN → 服务没启动/启动失败
│   └── 有 LISTEN → 下一步
├── ② 绑定地址？（LISTEN 行的地址）
│   ├── 127.0.0.1 → 仅本机（外部连不上！）
│   └── 0.0.0.0 → 对外（下一步）
├── ③ 防火墙/网络？
│   ├── 本机：ufw status / firewall-cmd --list-all
│   ├── 云：安全组入方向
│   └── 网络：nc -vz host 端口
└── ④ 金句：连不上按「监听 → 绑定 → 防火墙 → 网络」四步
```

## 6. 实战案例复盘

### 案例 1：Spring Boot 启动报端口占用

```text
现象：启动报 "Port 8080 was already in use"
排查：
① ss -tlnp | grep 8080
   → LISTEN ... java,pid=24567（旧实例没停干净）
② ps -p 24567 -f
   → 是上一个测试实例（残留进程）
③ kill 24567（优雅）→ 等 2 秒 → ss 确认释放
④ 重新启动 ✅
教训：IDE 停止应用 ≠ 进程结束（可能后台残留）
预防：启动脚本先检查端口/统一端口规划
```

### 案例 2：外部访问不到本地服务

```text
现象：本机 curl localhost:8080 通，外部访问不通
排查：
① ss -tlnp | grep 8080
   → LISTEN 127.0.0.1:8080（绑定仅本机！）
② 原因：应用配置 address=127.0.0.1（或 Spring server.address）
③ 解法：改绑定 0.0.0.0（server.address=0.0.0.0）
④ 验证：外部 nc -vz host 8080 通 ✅
教训：绑定地址是「连不上」的高频根因
预防：对外服务默认绑定 0.0.0.0（调试端口才绑 127.0.0.1）
```

### 案例 3：容器端口映射后外部不通

```text
现象：docker run -p 8080:8080 后外部访问不通
排查：
① docker exec 容器 curl localhost:8080 → 通（容器内 OK）
② curl localhost:8080（宿主）→ 通（映射 OK）
③ 外部 nc -vz host 8080 → 不通
④ 检查：云安全组没放行 8080！→ 控制台添加 ✅
教训：容器映射只解决「容器 ↔ 宿主」，外部还需防火墙/安全组
预防：三层链路（安全组 → 防火墙 → 映射）部署前验证
```

## 7. 防火墙与端口

### 7.1 常见防火墙命令

```bash
# ufw（Ubuntu）
sudo ufw status                      # 查看
sudo ufw allow 8080/tcp              # 放行
sudo ufw allow from 203.0.113.0/24 to any port 22  # 限源
sudo ufw deny 3306                   # 拒绝

# firewalld（RHEL/CentOS）
sudo firewall-cmd --list-all         # 查看
sudo firewall-cmd --add-port=8080/tcp --permanent
sudo firewall-cmd --reload

# iptables（底层）
sudo iptables -L -n                  # 查看
sudo iptables -A INPUT -p tcp --dport 8080 -j ACCEPT
```

```text
防火墙排查要点
├── ① 服务监听 ≠ 防火墙放行（两层独立！）
├── ② 放行方向：入站（INPUT）还是出站
├── ③ 限源放行：管理端口只允许办公 IP
├── ④ 云安全组：控制台层（本机防火墙之外）
└── ⑤ 金句：防火墙是「最后一层」——监听 OK 但不通先查防火墙
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 三类排查场景：启动失败（被占）/连不上（监听/防火墙）/看不见（绑定地址）——先分类再排查
> 2. Windows 三连：netstat -ano | findstr 端口 → tasklist | findstr PID → taskkill /PID /F
> 3. Linux 双工具：ss -tlnp（现代首选）/ lsof -i :端口——kill PID 后 ss 验证
> 4. 状态解读：CLOSE_WAIT 堆积 = 连接未关闭（bug）；TIME_WAIT 多 = 短连接高频
> 5. 连不上四步：监听 → 绑定地址 → 防火墙 → 网络
> 6. 三个实战案例：残留进程（kill）/127.0.0.1 绑定（改 0.0.0.0）/安全组未放行（三层链路）
