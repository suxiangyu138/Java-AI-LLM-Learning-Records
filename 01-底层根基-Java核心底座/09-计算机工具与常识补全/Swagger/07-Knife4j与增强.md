## 1. Knife4j 是什么

Knife4j 是国产开源的 Swagger 文档增强框架（基于 springfox 起步、2024 起全面适配 springdoc）——**它不改变契约（还是 OpenAPI），改变的是 UI 与文档体验**：在 Swagger UI 之上提供生产级能力（离线文档、聚合、鉴权、全局参数、接口搜索、增强的模型展示）。定位一句话：**「原生 Swagger UI 是够用的基线，Knife4j 是生产友好的增强」**。

它与 springdoc 的关系：**springdoc 生成契约、Knife4j 渲染增强 UI**——同一契约、两种呈现（`knife4j-openapi3-jakarta-spring-boot-starter` 依赖替代 UI starter）；契约端点（`/v3/api-docs`）不变，UI 入口变（`/doc.html`）。**「换 UI 不换契约」**——底层能力（契约生成、注解体系）完全复用本体系 03/04 篇的内容。

## 2. 增强能力清单

Knife4j 相对原生 UI 的核心增强（生产团队的痛点驱动）：

**离线文档**——一键导出 HTML/Markdown/Word 文档——**内网交付与评审刚需**（原生 UI 是网页，离线文档可分发）；**接口聚合**——多服务文档在一个入口聚合（网关场景——05 篇「一个入口看全部服务」的落地）；**全局参数**——全局 Header 参数配置（traceId、token 等统一注入 UI 调试）；**鉴权增强**——文档访问的登录鉴权（对接 Spring Security——08 篇管控的 UI 侧配合）；**接口搜索**——按路径/描述搜索（接口多时的高频需求）；**模型展示增强**——请求/响应模型的关系图展示；**调试增强**——复制 curl 命令、调试历史。

**「增强都是生产痛点」**——逐条对号：给甲方交付 → 离线文档；微服务 → 聚合；调试带 token → 全局参数；文档要登录 → 鉴权——**痛点存在才需要 Knife4j**，没有痛点原生 UI 完全够用。

## 3. 接入与配置

```xml
<!-- 替换 springdoc 的 ui starter，契约生成不变 -->
<dependency>
    <groupId>com.github.xiaoymin</groupId>
    <artifactId>knife4j-openapi3-jakarta-spring-boot-starter</artifactId>
    <version>4.5.0</version>   <!-- 2026 常用线，查最新 -->
</dependency>
```

```yaml
knife4j:
  enable: true                # 启用增强
  setting:
    language: zh_cn           # 中文界面
    enable-search: true       # 接口搜索
    enable-doc: true          # 离线文档导出
    enable-footer: false
springdoc:
  api-docs:
    version: openapi_3_1
```

**接入要点**：**依赖替换**（去掉 springdoc 的 `-ui` starter，用 Knife4j starter——契约生成核心仍在 springdoc）；**UI 入口变化**（`/doc.html` 替代 `/swagger-ui.html`——原端点可重定向）；**与 springdoc 版本配套**（Knife4j 版本对应 springdoc 版本线——查兼容矩阵）。**契约与注解零改动**——换 UI 的成本极低（依赖 + 配置）。

## 4. 聚合文档

微服务场景的文档聚合是 Knife4j 的高频卖点——**一个入口看全部服务**：

```yaml
knife4j:
  enable-aggregation: true
  cloud:
    enable: true
    route-auth:               # 聚合时的服务鉴权配置
      enable: true
    routes:
      - name: 用户服务
        uri: user-service     # 服务名（网关解析）
        location: /v3/api-docs
      - name: 订单服务
        uri: order-service
        location: /v3/api-docs
```

**聚合的两种形态**：**网关聚合**（Knife4j 在网关侧聚合各服务的 `/v3/api-docs`——微服务文档统一入口）；**独立聚合服务**（专门的文档服务聚合）。**聚合的价值**：开发/测试/对接方「一个 URL 看全部接口」；**聚合的前提**：各服务契约端点可达（网关路由打通）。**「聚合是微服务文档的标配工程」**——服务多了各自为政的 UI 就是灾难。

## 5. 与原生 UI 的选型

| 维度 | 原生 Swagger UI | Knife4j |
|------|----------------|---------|
| 契约能力 | 相同（同一 springdoc 契约） | 相同 |
| UI 体验 | 标准（够用） | 增强（搜索/模型/中文） |
| 离线文档 | 无（网页） | 有（HTML/MD/Word 导出） |
| 多服务聚合 | 手动（Explore 切换） | 原生支持 |
| 全局参数 | 无 | 有 |
| 文档鉴权 | 需自研 | 内置支持 |
| 依赖 | springdoc 官方 | 第三方（社区维护） |

**选型逻辑**：**单服务、内网开发、团队无特殊需求 → 原生 UI**（少一个第三方依赖）；**微服务多应用、要交付文档、要中文体验 → Knife4j**（痛点驱动的增强）。**「先原生后 Knife4j」是常见路径**（痛点出现再换——换的成本低：依赖 + 配置）。**注意**：Knife4j 是社区项目——版本跟随 springdoc 有滞后——锁版本 + 升级前查兼容（09 篇升级纪律同样适用）。

## 6. 常见坑

**坑一：依赖配错**。Knife4j 3.x（springfox）配 springdoc 3——版本线混淆——查兼容矩阵（Knife4j 4.x 对 springdoc 2/3）。

**坑二：UI 入口找不到**。`/doc.html` 404——`knife4j.enable: true` 未开或路径被拦截。

**坑三：聚合路由不通**。服务间网络/网关路由——先单服务 curl `/v3/api-docs` 验证。

**坑四：离线文档导出空白**。契约字段描述缺失——离线文档质量 = 注解质量（03 篇）。

**坑五：全局参数污染**。全局 header 与接口参数重名冲突——配置参数名与接口参数协调。

**坑六：生产环境开着**。Knife4j 也是暴露面——08 篇生产管控同样适用（doc.html 也禁用/鉴权）。

**坑七：Knife4j 与 springdoc 版本错配**。Knife4j 4.x 有对应的 springdoc 版本线——升级 springdoc 后 Knife4j 不兼容——升级按「springdoc → Knife4j → 验证」顺序，锁版本对。

**坑八：聚合文档的鉴权混乱**。聚合各服务的文档但各服务认证不同——聚合层统一鉴权 + 各服务契约端点放行聚合来源——「聚合的权限模型」先设计再配置。

**坑九：离线文档与在线契约脱节**。「导出的 Word 是老版本」——离线文档也要版本化（导出时标注契约版本/日期）——「离线文档是一次性快照，别当长期资产」。

**坑十：追求 Knife4j 的高级功能忽略基础**。调试、聚合都想要但契约描述稀烂——增强 UI 渲染的是同一份契约——「先注解质量后增强功能」。

**Knife4j 的国内实践语境**：Knife4j 在国内团队的高渗透率源于三个现实——**文档交付**（给甲方/外包的离线 Word/PDF 文档是验收要求——原生 UI 给不了）；**中文体验**（界面语言、中文文档生成——原生 UI 英文为主）；**微服务聚合**（国内 Spring Cloud 微服务占比高——聚合文档是标配需求）。**「选型不是崇洋媚外问题，是需求匹配问题」**——原生 UI 的「零第三方依赖」对某些团队是加分项，Knife4j 的「生产增强」对另一些团队是刚需——**按团队需求清单对照选型表（第 5 节），别按流行度选**。**无论选哪个，契约资产化（06 篇）与生产管控（08 篇）的纪律不变**——UI 只是视图，契约与安全是底线。
