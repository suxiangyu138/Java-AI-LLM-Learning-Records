# 03-注解体系
> 定位：注解是「文档的原料」——springdoc 生成骨架，注解补质量；核心是让每个接口、每个参数、每个字段都「可理解」，而「可理解」的验收标准是「AI 也能读懂」。

## 1. 注解分层

springdoc 注解按「文档结构」分层，与 OpenAPI 契约的层级一一对应：

```text
契约结构                对应注解
├── info（标题/版本）     OpenAPIDefinition
├── tags（分组）          @Tag（Controller 级）
├── paths（接口）
│   ├── operation         @Operation（方法级）
│   │   ├── parameters    @Parameter（参数级）
│   │   └── responses     @ApiResponse（响应级）
└── schemas（模型）        @Schema（字段级/DTO 级）
```

**「注解是契约的代码侧表达」**——注解写得好，生成的 OpenAPI 契约（`/v3/api-docs`）就完整；契约完整，UI 展示、客户端生成、AI 调用全部受益。**注解的黄金比例**：结构信息（路径/方法/类型）springdoc 自动推断，注解只补「语义信息」（描述、示例、约束说明）——**别用注解重复结构，用注解补语义**。

## 2. 接口层：@Operation

@Operation 是接口级描述注解，最常用的字段：

```java
@Operation(
    summary = "查询用户",                    // UI 列表里的一句话摘要（必写）
    description = "按 ID 查询用户详情，返回完整用户信息",  // 展开后的详细描述
    tags = {"用户"},                        // 覆盖分组（一般用 @Tag 不用这个）
    deprecated = true                       // 标记废弃（UI 置灰显示）
)
```

**summary 是接口的「标题」**——UI 列表、搜索、AI 工具发现都靠它——「写清 summary」是文档质量的第一要求；**description 写「行为语义」**（返回什么、有什么边界——如「不存在返回 404」）；**deprecated 配合版本化**（接口废弃时标记——RESTful 体系的 Sunset 语义在文档侧的表达）。

## 3. 参数层：@Parameter

参数描述注解——路径参数、查询参数、请求头：

```java
@GetMapping("/search")
public Page<UserDto> search(
    @Parameter(description = "搜索关键词", example = "张", required = true)
    @RequestParam String keyword,
    @Parameter(description = "页码，从 0 开始", example = "0")
    @RequestParam(defaultValue = "0") int page,
    @Parameter(hidden = true)              // 隐藏参数（如内部标识）
    @RequestHeader("X-Trace-Id") String traceId
)
```

要点：**example 参数是「调试的默认值」**——Try it out 自动填示例，调试零输入成本；**required 与 @RequestParam 的 required 一致**（重复声明以注解为准）；**`hidden = true` 隐藏内部参数**（traceId 这类不该出现在文档的）；**description 写参数语义**（「页码从 0 开始」这类约定在描述里，调用方不用猜）。

## 4. 响应层：@ApiResponse

响应描述注解——**「每个状态码都描述」是文档完整性的标准**：

```java
@GetMapping("/{id}")
@Operation(summary = "查询用户")
@ApiResponse(responseCode = "200", description = "成功", content = @Content(schema = @Schema(implementation = UserDto.class)))
@ApiResponse(responseCode = "404", description = "用户不存在")
@ApiResponse(responseCode = "500", description = "服务端错误")
public UserDto getUser(@PathVariable Long id) { ... }
```

要点：**默认只有 200 会被推断**——404/400/500 不写就没有（UI 里看不到失败场景）；**200 的 content 可自动推断**（返回类型即 schema）——显式写是为了控制；**错误响应的描述与 [[../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 错误格式]] 呼应**（RFC 9457——错误响应也要文档化）。**「文档完整 = 每个状态码都有」**——接口的失败行为是调用方最需要知道的。

## 5. 模型层：@Schema

DTO 字段描述注解——**文档质量的另一半在模型**：

```java
public record CreateUserRequest(
    @Schema(description = "用户名", example = "zhangsan", minLength = 3, maxLength = 20)
    String username,
    @Schema(description = "密码", minLength = 8, writeOnly = true)   // 只写不读：响应中不显示
    String password,
    @Schema(description = "角色", example = "ADMIN", allowableValues = {"ADMIN", "USER"})
    String role
) {}
```

要点：**example 是字段的「人类示例」**（生成文档与 AI 调用都受益）；**约束注解（@NotBlank 等）springdoc 自动转成 schema 约束**（minLength 等不必重复写）；**`writeOnly`/`readOnly` 表达「只写/只读」**（密码只写、ID 只读）；**`allowableValues` 限定枚举**（@Valid 的枚举校验已自动推断——重复写要一致）；**record 与 DTO**——Java 17 record 完全支持（springdoc 自动识别）。

## 6. 分组与全局：@Tag 与 @SecurityRequirement

**@Tag（Controller 级）**——接口分组：`@Tag(name = "用户管理", description = "用户模块的增删改查")`——UI 左侧的组；**分组粒度**：按业务模块（用户/订单/支付）——**「标签即模块地图」**：分组合理，UI 可读性翻倍。**@SecurityRequirement**——接口的认证要求声明：

```java
@SecurityRequirement(name = "bearerAuth")
@GetMapping("/me")
public UserDto me() { ... }
```

**配合 OpenAPI 的 securitySchemes 声明**（`@OpenAPIDefinition` 里定义 bearerAuth 方案——04 篇）——**「这个接口要带什么凭证」在文档里可见**——UI 的 Authorize 按钮与 Try it out 联动。

## 7. 描述质量

「文档质量 = 描述质量」——三个层次的验收标准：**第一层（结构完整）**——每个接口有 summary、每个参数有 description、每个状态码有 @ApiResponse——**机器可查**（扫描注解统计）；**第二层（语义可读）**——描述能回答「这个接口干什么、参数什么含义、失败返回什么」——**人可读**（对接方不问你就能用）；**第三层（AI 可用）**——描述是「给 AI 的使用说明」——**2026 新标准**：把文档丢给 LLM 问「怎么创建用户」——答对了说明合格（09 篇 MCP 集成的前提）。**「写描述的时间」是文档工程的投资**——第三层标准下，描述质量直接决定「API 能否被 AI 正确调用」。

## 8. 常见坑

**坑一：注解重复结构**。@Operation 里写返回值类型（自动推断）——冗余——只补语义。

**坑二：404/400 不写**。UI 只有 200——调用方不知道失败场景——每个状态码都描述。

**坑三：example 不写**。Try it out 每次手填——示例是调试与 AI 的默认值。

**坑四：hidden 不用**。内部参数暴露在文档——hidden 隐藏。

**坑五：@Schema 重复约束**。@NotBlank 已自动转——重复写不一致会打架——以校验注解为准。

**坑六：枚举不声明**。allowableValues 与校验不一致——调用方传错值 422——统一声明。

**坑七：描述写「接口」不写「语义」**。description: "查询用户接口"——等于没写——「按 ID 查询，返回完整信息，不存在 404」。

**坑八：@ApiResponse 与全局异常处理的重复**。全局异常处理器（[[../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 错误格式]]）返回统一错误结构——@ApiResponse 的错误 content 也要指向统一错误 schema——「错误结构文档化」与「错误结构实现」同源（共用错误 DTO）。

**注解的团队规范**（把「注解怎么写」变成团队约定）：**Controller 级必写 @Tag**（name + description——分组与模块说明）；**方法级必写 @Operation**（summary 必须、description 按需——description 写「行为语义」不写「接口说明」）；**参数级**：description + example（必填参数 required 与校验一致）；**模型级**：DTO 字段 description + example（约束交给校验注解自动转）；**错误响应**：非 200 状态码全部 @ApiResponse。**规范的可检查性**：注解规范写进 PR 评审清单（「新接口有没有 summary/example/错误响应」——评审时逐项勾）——**「注解规范是文档质量的团队契约」**——个人自觉 + 评审把关双保险。
