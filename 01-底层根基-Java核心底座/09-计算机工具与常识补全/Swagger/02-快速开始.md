## 1. 依赖引入

Spring Boot 3.x/4.x 项目接入 springdoc 只需一条依赖（2026 锁 3.1.0）：

```xml
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version>3.1.0</version>
</dependency>
```

要点：**`-webmvc-` 是 Spring MVC 版**（WebFlux 项目用 `-webflux-` 版）；**`-ui` 后缀带 Swagger UI**（只要契约不要 UI 用不带 ui 的 `-webmvc` 版）；**Maven 中央仓库直接可用**——无需额外仓库。**Boot 版本配套**：springdoc 3.1.0 对应 Boot 4.1.0；Boot 3.4.x 用 3.0.x 系列（兼容矩阵见 springdoc 官网）——**锁 springdoc 版本时查对应 Boot 兼容**。

## 2. 基础配置

application.yml 的最小配置（不配也能跑——默认值开箱即用，配了更可控）：

```yaml
springdoc:
  api-docs:
    enabled: true              # 契约端点开关（生产关闭见 08 篇）
    path: /v3/api-docs         # 契约 JSON 路径（默认）
    version: openapi_3_1       # 输出 OpenAPI 3.1 格式（2026 推荐）
  swagger-ui:
    path: /swagger-ui.html     # UI 入口（默认）
    tags-sorter: alpha         # 标签排序
    operations-sorter: method  # 操作排序
    display-request-duration: true
```

**版本选择**：`openapi_3_1`（默认已是 3.1？——显式声明保证输出 3.1 契约）——3.1 与 JSON Schema 2020-12 对齐，`nullable` 写法变化（`type: [string, 'null']`）；**排序配置**让 UI 可读性提升（按标签/方法排序替代默认的随机序）。

## 3. 三个端点

接入后默认暴露三个端点：

| 端点 | 内容 | 用途 |
|------|------|------|
| `/v3/api-docs` | OpenAPI JSON 契约 | 程序消费（客户端生成、契约测试） |
| `/v3/api-docs.yaml` | YAML 契约 | 人读/导入其他工具 |
| `/swagger-ui.html` | Swagger UI 界面 | 浏览与调试 |

**验证姿势**：浏览器开 `/swagger-ui.html`（UI 可用）；`curl /v3/api-docs | jq '.openapi'`（契约版本——应输出 `3.1.0`）；**三端点是文档体系的入口**——契约端点给机器、UI 端点给人（04 篇详述契约内容结构）。

## 4. 第一个接口文档

零注解的 Controller 也能出文档——springdoc 扫描自动生成（方法名当操作名、参数推断类型），但**可读性很差**。第一个「像样的」文档从两个注解开始：

```java
@RestController
@RequestMapping("/api/users")
@Tag(name = "用户管理", description = "用户的增删改查接口")
public class UserController {

    @GetMapping("/{id}")
    @Operation(summary = "查询用户", description = "按 ID 查询用户详情")
    public UserDto getUser(@PathVariable Long id) {
        return userService.get(id);
    }

    @PostMapping
    @Operation(summary = "创建用户")
    public UserDto create(@Valid @RequestBody CreateUserRequest req) {
        return userService.create(req);
    }
}
```

启动应用 → 打开 `/swagger-ui.html`——看到「用户管理」标签组、两个操作的描述——**「自动生成骨架 + 注解补质量」**：springdoc 生成了结构（路径、方法、参数、响应模型），`@Tag`/`@Operation` 补上语义（分组、摘要、描述）。**文档质量的起点是「每个接口都有 summary + description」**——没有描述的操作在 UI 里只是一行 URL。

## 5. UI 初体验

Swagger UI 的四个核心区（05 篇详解）：**顶部 Explore 栏**（切换契约来源——默认本地 `/v3/api-docs`）；**左侧标签组**（按 @Tag 分组的接口列表）；**接口详情**（展开后：参数、请求体、响应结构——模型定义自动展示）；**Try it out**（在线调试——填参数 → Execute → 看真实响应——开发期自测利器）。

**第一个调试动作**：展开 `GET /api/users/{id}` → Try it out → 填 id → Execute——看到真实响应与响应码——**「文档 + 调试合一」是 Swagger UI 的价值时刻**：不用切 Postman 就能验证接口。

**升级到 Boot 4 的注意事项**：Spring Boot 4.1（2026 主线）配 springdoc 3.1.0——**兼容矩阵是硬约束**（springdoc 版本与 Boot 主版本强绑定）：Boot 3.x → springdoc 2.x/3.0.x；Boot 4.x → springdoc 3.1.x——**升级 Boot 必升 springdoc**（反之亦然）；**Boot 4 的变化对文档的影响**——`spring.mvc` 配置项更名、部分 MVC 注解行为调整——springdoc 3.1 已适配——**「升级 Boot 后文档异常」先查 springdoc 版本配套**。**多环境接入建议**：dev 环境接入即可看到全部效果（UI/调试/契约），test 环境按需保留契约端点（自动化测试消费），prod 按 08 篇管控。

## 6. 常见坑

**坑一：还在用 springfox**。不支持 Boot 3——2026 一律 springdoc（01 篇）。

**坑二：版本不配套**。springdoc 3.1.0 配 Boot 3.3 报错——查兼容矩阵锁版本。

**坑三：WebFlux 项目用 webmvc 依赖**。启动报错——用 `-webflux-` 版。

**坑四：UI 打不开 404**。`springdoc.swagger-ui.path` 配错或 `api-docs.enabled=false`——检查配置与端点（03 篇端点清单）。

**坑五：接口没出现在文档里**。Controller 不在扫描路径（`springdoc.packages-to-scan`）或不是 `@RestController`——确认扫描范围（04 篇）。

**坑六：契约是 3.0 不是 3.1**。`springdoc.api-docs.version` 未配或配错——显式 `openapi_3_1`。

**坑七：生产环境暴露**。Swagger 上线忘关——08 篇生产管控——「开发开着、生产必关」。

**坑八：`springdoc.api-docs.version` 配了没生效**。配置前缀拼错（`springdoc.api-docs` 与 `springdoc.swagger-ui` 两级）——YAML 缩进/键名核对——以 springdoc 官方文档为准。

**坑九：安全框架拦截文档端点**。Spring Security 默认拦截所有请求——`/swagger-ui/**`、`/v3/api-docs` 被 401/403——开发环境放行（08 篇认证管控的「放行」侧配置）。

**坑十：依赖冲突（springdoc 与 springfox 并存）**。老项目残留 springfox 依赖——注解冲突、行为异常——移除 springfox 依赖与配置。

**坑十一：接口返回类型复杂时文档模型乱**。泛型（`Page<UserDto>`）、Map 返回——schema 推断不理想——用 `@Schema(implementation = ...)` 显式指定或定义明确的 DTO（「文档友好的返回类型设计」——返回类型即文档质量）。

**坑十二：上传/下载接口文档体验差**。文件参数（`MultipartFile`）与流式响应（`ResponseEntity<Resource>`）默认展示不友好——`@Parameter` 描述 + `content = @Content(mediaType = "application/octet-stream")` 声明——「特殊接口要特殊文档化」。

**坑十三：测试环境与开发环境契约不同步**。dev 改了接口、test 没部署——两边 UI 看到的文档不一样——「文档看的是部署环境的契约」——对接方指定环境看文档，别跨环境对照。

**坑十四：中文文档乱码**。契约里中文描述乱码——`sonar.sourceEncoding` 的同类问题——**UTF-8 编码贯穿**（`server.servlet.encoding` + 文件编码）+ `springdoc` 无特殊编码配置（跟随 Spring 全局）。

**坑十五：`@Validated` 与文档约束不同步**。类级 `@Validated`（方法参数校验）的约束 springdoc 能识别，但部分自定义校验注解不映射——文档显示「无约束」而实际校验失败——**「文档的约束展示以标准校验注解为准」**——自定义校验逻辑在描述里写明。

**坑十六：只扫主包不扫子模块**。多模块 Maven 项目子模块 Controller 缺失——`packages-to-scan` 覆盖子模块包名——「多模块项目的文档扫描配置是接入必做项」——子模块的 Controller 与 DTO 才能进入契约。

**「十分钟闭环」的验收标准**：**契约可读**——`curl /v3/api-docs | jq '.openapi, .paths | keys'` 输出 3.1.0 与接口路径列表；**UI 可看**——浏览器打开 `/swagger-ui.html` 看到你的 Controller 分组；**接口可调**——Try it out 执行一个 GET 拿到真实响应——**三个动作全过 = 接入成功**。**接入了以后**：别急着写满注解——先扫一个真实接口看「零注解文档长什么样」，理解 springdoc 自动生成的能力边界（哪些推断、哪些要注解），再按 03 篇补注解——**「先看生成再补注解」是理解注解价值的最快路径**。
