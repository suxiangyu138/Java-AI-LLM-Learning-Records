## 1. 代码优先 vs 契约优先

两条路线的本质差异——「契约从哪来」：

**代码优先（Code-first）**——springdoc 默认路径：先写 Controller 与注解 → 启动时生成契约。**优点**：零额外成本（文档随代码走）、类型安全（契约来自真实代码）；**缺点**：契约是「代码的投影」（设计决策在代码里做）、契约评审滞后（先写码后见契约）。

**契约优先（Spec-first）**——先写 OpenAPI 契约（Swagger Editor/Stoplight）→ 评审契约 → 生成骨架/实现。**优点**：契约先行评审（接口设计先于编码）、前后端并行（前端按契约 Mock 开发）；**缺点**：契约与实现可能漂移（需要契约测试兜底）、维护两份资产。

**2026 的实践共识**：**小团队/快速迭代 → 代码优先**（springdoc 够用）；**对外 API/多团队协作 → 契约优先**（契约是跨团队合同）。**两种路线可以融合**：设计期用契约优先的思路（先讨论接口再写码），实现期用 springdoc 生成——「契约思维 + 代码生成」是务实姿态（[[../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 体系]] 08 篇的 Spec-first 详解）。

## 2. 契约导出与分发

springdoc 的契约就是资产——**「文档是产物，契约是资产」**：

**导出姿势**：`curl /v3/api-docs > openapi.json`（或 yaml 端点）；**分发场景**：**导入 Postman**（Postman → Import → OpenAPI——契约变调试集合——「文档变可执行调试集」）；**导入 Stoplight/Redoc**（专业文档渲染）；**给客户端生成器**（下节）；**版本化入库**（CI 里导出契约提交到 `api-docs/` 目录——契约进仓库 = 契约可评审可追溯——「契约是代码资产的一部分」）。

**契约分发的纪律**：**契约导出进 CI**（每次构建导出最新契约——别手导）；**契约版本与 API 版本对应**（v1/v2 契约分开存）；**对外发布**（第三方接入的契约包——JSON + 变更说明）。

## 3. 客户端生成

**从契约生成客户端是「契约资产化」的杀手级应用**——手写 HTTP 客户端 → 生成类型安全客户端：

```bash
# OpenAPI Generator（2026 主流——Swagger Codegen 的继任者）
npx @openapitools/openapi-generator-cli generate \
  -i openapi.json \
  -g typescript-axios \        # 目标语言/框架（java、python、typescript-fetch...）
  -o generated-client
```

```java
// 生成的 Java 客户端用法（类型安全、零手写）
UserApi api = new UserApi(new ApiClient().setBasePath("https://api.example.com"));
UserDto user = api.getUser(42L);    // 方法名/参数/返回类型都来自契约
```

**生成的客户端价值**：**类型安全**（契约定义的类型 → 编译期检查）；**零手写**（前端/第三方不用自己拼请求）；**同步契约**（契约更新 → 重新生成——「客户端与契约同步」而非「客户端与后端口头同步」）。**生成物纪律**：生成的代码带 DO NOT EDIT 头（手改丢失——重新生成覆盖）；**生成进 CI**（契约变更自动重新生成 + 构建验证）。

## 4. 契约测试

**契约测试是「文档漂移」的根治**——验证「契约声明 vs 实现响应」一致：

**Dredd**（契约 → 发起真实请求 → 校验响应是否符合契约）：`dredd` 工具读 OpenAPI 契约，对每个操作发起请求（用契约里的 example 作参数），比对响应结构（状态码、字段、类型）——**不一致即失败**——「实现违反了契约」被机器发现；**Pact**（消费者驱动契约测试——消费者定义期望 → 提供者验证——前后端各自的契约测试）；**springdoc 侧的轻量姿势**——集成测试里断言 `/v3/api-docs` 的结构（契约快照测试：改契约 = 改快照 = 评审可见）。

**契约测试的落地节奏**：先快照测试（最便宜）→ 加 Dredd（真实验证）→ 消费方 Pact（多团队协作）——**「文档漂移」从「靠人记」变成「机器拦」**。

## 5. 契约驱动协作

契约驱动的团队协作流——「契约是团队的中枢」：

```text
设计（契约/注解）→ 评审（契约 PR——接口设计评审）→ 实现（后端/前端并行）
→ 契约测试（CI 拦漂移）→ 发布（契约版本化）→ 消费（UI/生成客户端/AI 工具）
```

**契约驱动 vs 代码驱动的团队差异**：**评审对象**——代码优先评代码、契约优先评契约（接口设计在编码前定稿）；**并行能力**——契约确定后前端按 Mock 开发（不等后端）；**变更管理**——契约 diff 即接口变更（破坏性变更检测——RESTful 体系 oasdiff 的输入）。**「契约驱动」不是「放弃代码优先」**——是「把契约当一等公民」：无论契约从哪来（手写或生成），它都进评审、进 CI、进版本管理——**「契约的治理程度」决定文档体系是工具还是资产**。

## 6. 常见坑

**坑一：契约导出手动作**。改代码忘导——契约过期——CI 里自动导出。

**坑二：生成客户端手改**。重新生成覆盖丢失——DO NOT EDIT 纪律。

**坑三：契约测试不做**。文档漂移无人知——快照 + Dredd 进 CI。

**坑四：代码优先就没有契约设计**。注解写得多烂契约就多烂——先想「接口该怎么设计」再写码（契约思维）。

**坑五：契约不版本化**。接口改了契约没改——契约进仓库、版本对应。

**坑六：客户端生成只在本地**。生成物不一致——生成进 CI。

**坑七：契约测试只测成功路径**。契约里的 example 全对、真实业务 422/404 没覆盖——Dredd 配多组示例（含失败场景）——「契约测试的覆盖 = 契约的质量」。

**坑八：前端不用生成客户端**。「我手写 axios 就行」——契约变更后手写代码不知道——生成客户端让「契约变了编译期就报错」——手写是「默默用错」的温床。
