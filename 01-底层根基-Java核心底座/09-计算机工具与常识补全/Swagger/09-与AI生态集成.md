## 1. AI 时代的 API 文档

2026 年 API 的消费方多了一个重要角色——**AI agent**：Claude、Cursor、各类 Agent 框架通过工具调用（Tool Calling）操作外部系统。agent 调用 API 的方式与人类完全不同：**它不会打开 Swagger UI 浏览**——它读的是**契约与描述**（OpenAPI 文档 / MCP 工具定义）——**「文档是给 AI 的使用说明」**。

这个转变的工程含义：**文档质量从「人可读」升级为「机器可读且语义准确」**——描述含糊的接口（「查询用户」vs「按 ID 查询用户，返回昵称、头像、邮箱，不存在返回 404」）在 AI 手里是两个完全不同的工具——**描述准确与否决定 agent 调用成功与否**。**「API 可被 AI 使用」成为 2026 的 API 设计目标**——[[../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 体系]] 08 篇与 [[../../../03-AI大模型应用开发/06-MCP协议与Agent%20Skill/MCP学习/MCP%20核心架构（CS%20客户端‑服务器）/00-MCP核心架构知识体系总览|MCP 体系]] 的交叉视角。

## 2. MCP 集成机制

**MCP（Model Context Protocol）** 是 AI 工具的标准协议——工具以「工具定义」（名称 + 描述 + 参数 schema）暴露给 agent。**springdoc 3.x 的核心新能力：把已文档化的 REST 端点自动转成 MCP 工具**——机制：

```text
@RestController（已注解）→ springdoc 契约（OpenAPI）→ MCP 工具定义（AI 可发现）
  语义映射：@Operation.summary → 工具名/描述
            @Parameter/@Schema → 参数 schema
            @McpToolDescription → AI 优化描述（3.1 新增）
```

**「REST 端点零改造变成 AI 工具」**——不用写专门的 MCP 服务器——现有后端即工具源——这是「文档资产」的二次变现：**文档写好了，AI 集成是白送的**。集成后：Claude Desktop、Cursor 等 MCP 客户端可发现并调用你的 API（配合 [[../../../02-后端核心技术%20微服务%20分布式%20云原生/06-Spring全家桶/Spring%20AI/00-Spring%20AI总览|Spring AI 体系]] 的 MCP 集成）。

## 3. 接入配置

```xml
<!-- 在 springdoc 基础上加 MCP starter -->
<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-mcp</artifactId>
    <version>3.1.0</version>
</dependency>
```

```yaml
springdoc:
  ai:
    mcp:
      enabled: true          # 开启 MCP 工具暴露
```

```java
@GetMapping("/orders/{id}")
@Operation(summary = "查询订单", description = "按 ID 查询订单详情")
@McpToolDescription("按订单 ID 查询订单详情，返回订单状态与金额；不存在返回 404")
public OrderDto getOrder(@PathVariable Long id) { ... }
```

**接入要点**：**`@McpToolDescription` 是 AI 专用的描述**（3.1 新增）——比 @Operation.description 更「AI 友好」：**写清「做什么、输入什么、返回什么、失败什么」**——agent 靠描述决定「要不要调、怎么调、结果怎么用」；**安全操作分类**（下节）；**契约与 MCP 描述的一致性**（两处描述别打架——@McpToolDescription 覆盖 @Operation 的描述用于 AI）。

## 4. Guardrails 与人工确认

**「AI 调 API」的安全问题：agent 可能执行危险操作**（删数据、转账、下单）——springdoc 3.x 的 guardrails（护栏）机制：

**安全操作 vs 变更操作分类**——按 HTTP 方法自动分类：GET（安全——agent 可自由调用）；POST/PUT/DELETE（变更——**默认要求人工确认**）；**Human-in-the-Loop**——变更操作执行前需人工批准——「AI 提议、人确认、系统执行」；**配置调整**——可按端点覆盖分类（`@McpToolDescription` 或配置标记「允许 agent 直接执行」的端点——白名单式放开）。

**Guardrails 的工程意义**：**「AI 能读文档 ≠ AI 能乱操作」**——读（GET）放开、写（POST/PUT/DELETE）人工确认——这是「AI 接入企业系统的安全基线」——与 [[../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 体系]] 09 篇的授权治理呼应（agent 的调用也要过授权与审计）。

## 5. MCP Dashboard

springdoc 3.x 内置 **MCP Dashboard**（Web UI）——AI 工具的管理界面：**查看**——哪些端点被暴露为 AI 工具（工具列表、描述、参数 schema）；**测试**——手动调用工具验证（agent 场景的「Try it out」）；**管理**——工具启停、guardrail 配置。**「AI 工具的管理入口」**——运维与安全人员不用懂 MCP 协议也能管理「AI 能调什么」——这是「文档 → AI 工具」工程化的管理面。

## 6. 文档质量 = AI 可用性

**「文档质量直接决定 API 能否被 AI 正确调用」**——AI 调用失败的三大文档原因与解法：

**描述含糊**——「查询用户」没说查什么、返回什么——agent 不敢调或误用——**描述写「做什么 + 输入 + 返回 + 失败」四要素**（03 篇第三层标准）；**示例缺失**——参数没 example——agent 编参数（编错 422）——**example 是 AI 的参数模板**；**错误契约缺失**——没有 404/400 的响应描述——agent 不知道失败场景——**状态码全覆盖**（03 篇）。**验收动作**：把契约丢给 LLM 问「如何用这个 API 查询订单并处理不存在的情况」——答得对 = AI 可用（[[../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 体系]] 08 篇的 agent 测试同款动作）。

## 7. 常见坑

**坑一：MCP 描述与 @Operation 打架**。两处描述不一致——AI 与人对不上——以 @McpToolDescription 为准，语义统一。

**坑二：变更操作没有 guardrail**。agent 直接删数据——默认人工确认，白名单式放开。

**坑三：示例缺失**。AI 编参数——example 全配。

**坑四：错误契约缺失**。agent 不会处理失败——404/400/500 全描述。

**坑五：安全操作与变更操作分不清**。POST 误标安全——分类按方法 + 人工评审。

**坑六：生产暴露 MCP**。AI 工具端点也走 08 篇管控——认证 + 审计。

**坑七：只开不测**。MCP 集成后没验证 agent 实际调用——用 MCP 客户端实测一遍。

**坑八：所有端点都暴露给 AI**。内部管理接口、批量操作接口变成 AI 工具——AI 的操作面要「按需暴露」（工具白名单）——「AI 能看到的接口 = AI 能操作的接口」。

**坑九：没有审计 AI 调用**。agent 调用 API 与传统调用同轨审计——AI 调用也要 trace（谁在调、调了什么、结果如何）——「AI 调用是新的审计维度」。

**坑十：描述里带「只有人类才懂」的梗**。「参考上一个接口」「懂的都懂」——AI 不懂梗——描述要自包含（单工具可理解）——「AI 不会上下文联想，每个工具描述都要独立成立」。

**坑十一：参数 schema 与 AI 心智不符**。「枚举值」描述用缩写或内部代号——AI 不知道 `S1/S2` 是什么——枚举值写全称或描述映射（「S1 = 待处理」）——「AI 的参数理解依赖 schema 的自解释性」。

**坑十二：MCP 集成与既有网关鉴权冲突**。agent 经 MCP 调 API 要过网关——网关的鉴权（Token 体系）与 MCP 的认证配置要打通——「AI 调用的认证链路先于集成设计」。
