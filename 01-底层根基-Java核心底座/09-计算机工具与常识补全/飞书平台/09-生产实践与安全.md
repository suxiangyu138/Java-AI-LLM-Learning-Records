## 1. 消息限流：防刷屏

**消息限流防两件事：飞书频控 + 用户被刷屏**。**飞书侧频控**：**每个应用有 QPS/每日消息上限**（超限报错——**05 篇错误处理**）——**批量推送要控制速率**（分批 + 退避）。**用户侧刷屏**：**告警风暴/CI 失败连发**——**一条条推 = 群被刷爆、重要消息被淹没**。**防刷屏的三个手段**：**合并**（同类消息合并成一条卡片——**"10 个服务失败"比 10 条消息好**）；**分级**（P0 立即推、P1 延迟聚合、P2 只进记录——**08 篇告警分级**）；**节流**（同一事件 N 分钟内只推一次——**状态变化推送：失败 → 恢复只推两条**）——"**消息限流是'对接收者注意力的尊重'：宁可少推，不可刷屏**"。

## 2. 回调的 3 秒超时

**飞书回调要求服务端 3 秒内响应**——**超时 = 飞书重试/丢弃**（00 篇基线）。**3 秒约束下的正确姿势**：**先返 200 再异步处理**：

```java
// 错误姿势：回调里同步调用 AI/查库（可能 10 秒）→ 超时被重试
// 正确姿势：回调里只做"接收确认"（返回 200），重活异步执行
@PostMapping("/webhook/feishu")
public String onEvent(@RequestBody String body) {
    eventService.enqueue(body);      // 入队异步处理（消息队列/线程池）
    return "{\"code\":0}";           // 立即返回 200
}
```

**异步化的三个注意**：**顺序**（同一事件的后续处理要保序——**队列按事件维度分区**）；**去重**（异步处理前按 event_id 去重——**第 3 节**）；**结果主动推送**（**AI 生成完再主动推消息**——"回调是通知，不是执行"——00 篇误区五）。

## 3. 幂等与去重

**飞书事件可能重复推送**（网络重试/平台重发）——**不处理 = 重复执行副作用**（重复发消息/重复建记录）。**去重的两个手段**：**event_id 去重**（**每个事件有唯一 event_id**——处理前查"是否已处理"（Redis setnx/数据库唯一键——**幂等四件套，Java 分布式框架体系交叉**））；**业务幂等**（**以业务 ID 为准**——重复的"创建需求"事件，用需求 ID 唯一约束拦截）。**三个实践**：**入队前去重**（异步队列消费前过滤）；**处理中幂等**（**操作本身可重放**——重复执行结果一致）；**处理完记录**（**已处理的 event_id 落库/缓存**）——"**事件处理默认幂等：同一事件处理两次，结果必须相同**"。

## 4. 密钥管理

**飞书的密钥家族**：**App Secret**（换 token——**最高危**）；**verification_token/encrypt_key**（回调验签解密）；**Webhook token**（群机器人推送权限）。**密钥管理的五条纪律**（00 篇误区六）：**不进代码/仓库**（环境变量/配置中心——**Git 历史里出现过 = 已泄露**）；**按环境隔离**（dev/prod 用不同应用/不同密钥——**测试别碰生产**）；**定期轮换**（**泄露风险随时间积累**——开发者后台重置）；**泄露立即处理**（**发现泄露 → 重置密钥 → 查审计**——"**泄露处置的黄金时间是分钟级**"）；**最小分发**（**谁需要才给谁**——CI 里用 masked 变量，08 篇）——"**密钥是应用的钥匙串：每把钥匙都要锁好、记档、能轮换**"。

## 5. 权限最小化与审计

**应用的权限最小化**（03 篇 scope 纪律的运维版）：**只申请需要的 scope**（**im:message.group_msg（读群里所有消息）这类敏感权限谨慎**）；**定期盘点**（应用权限清单季度检查——**没用的权限移除**）；**可用范围控制**（**机器人/应用只对需要的部门/群可用**）。**审计的三件事**：**应用调用日志**（**谁调了什么 API——异常调用可追溯**）；**事件处理日志**（**处理了什么事件、结果如何**）；**权限变更记录**（**scope/可用范围变更留痕**）——"**权限最小化是'少暴露'，审计是'可追溯'——一个防出事，一个查出事**"。

## 6. 机器人运维

**机器人也是服务：要运维**——**机器人运维的五个方面**：**健康检查**（**长连接是否在线**——断线重连机制；Webhook 是否可达）；**日志**（**消息收发/事件处理日志**——排障依据）；**监控**（**消息量/错误率/回调延迟**——异常趋势）；**版本管理**（**应用版本发布/回滚**——03 篇）；**值班**（**机器人故障的响应人**——"机器人挂了，人要顶上"）。**运维的常用命令**：**SDK 日志级别**（开发 INFO、生产 WARN）、**健康端点**（`/health` 探活）、**重连机制**（**长连接断线自动重连**——SDK 内置）——"**机器人运维的底线：挂了要有人知道、知道要能修**"。

## 7. 生产检查清单

- [ ] 消息限流：合并/分级/节流已配置（防刷屏）
- [ ] 回调 3 秒内返回 200，重活异步化
- [ ] event_id 去重 + 业务幂等（重复事件无副作用）
- [ ] 密钥全部在环境变量/配置中心，代码零密钥
- [ ] 权限最小化（scope 只申请需要的，可用范围受控）
- [ ] 应用/事件调用有日志（可审计）
- [ ] 机器人长连接健康检查 + 自动重连
- [ ] 消息监控（量/错误率/延迟）已接入
- [ ] 定时任务（周报/巡检）有失败告警
- [ ] 应用版本发布/回滚流程明确（03 篇）

## 8. 五个常见坑

- **坑一**：告警连发刷屏——**合并 + 分级 + 节流；尊重接收者注意力**（第 1 节）；
- **坑二**：回调同步处理重活——**超时重试风暴；先返 200 再异步**（第 2 节）；
- **坑三**：事件重复不幂等——**重复建数据/发消息；event_id + 业务幂等**（第 3 节）；
- **坑四**：密钥写进配置仓库——**泄露即事故；环境变量 + 轮换**（第 4 节）；
- **坑五**：机器人挂了没人知道——**健康检查 + 监控 + 值班**（第 6 节）。
