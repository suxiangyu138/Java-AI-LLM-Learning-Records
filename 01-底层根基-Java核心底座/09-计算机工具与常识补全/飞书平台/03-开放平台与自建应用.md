## 1. 开放平台是什么

**飞书开放平台（open.feishu.cn）是开发者接入飞书的门户**——**它提供三类东西**：**应用管理**（创建/配置/发布你的应用——**本体系 03-05 篇**）；**API 文档**（消息/多维表格/文档/日历等全部接口）；**开发者工具**（SDK：Java/Go/Python、调试工具、沙箱）。**"应用"是开放平台的中心概念**——**一切能力都挂在应用上**：**机器人、API 调用、事件订阅、卡片交互**——"**没有应用，就没有 API 调用资格**"。**开放平台的演进**（00 篇基线）：**基础 API → 事件驱动 + 开放文档 → 云原生网关 + 安全合规**——**2026 年的开放平台能力成熟**：事件订阅延迟 <800ms、加密与签名、多语言 SDK——"**开放平台是飞书的'API 层'：六件套的能力都通过它暴露给开发者**"。

## 2. 创建自建应用

**自建应用（Enterprise Self-built App）是企业内部开发的应用**——**创建流程五步**：**① 登录开发者后台**（open.feishu.cn → 开发者后台）；**② 创建企业自建应用**（填名称/描述/图标——**名称即门面**）；**③ 配置凭证**（拿到 App ID/Secret——第 3 节）；**④ 开启能力**（机器人开关——第 4 节）；**⑤ 申请权限**（scope——第 5 节）。**创建后的三个关键配置页**：**凭证与基础信息**（App ID/Secret）、**权限管理**（scope 申请）、**事件与回调**（订阅配置）。**应用的类型**：**自建应用**（企业内部——**本体系主角**）、**商店应用**（对外发布——**开发者生态**，了解即可）——"**程序猿在飞书的第一件事：建一个自建应用，拿到 App ID/Secret**"——**这一步是所有 API 调用的起点**。

## 3. App ID 与 App Secret

**App ID 与 App Secret 是应用的"身份证 + 钥匙"**——**App ID**（应用的公开标识——`cli_xxx` 格式——**请求里带它**）；**App Secret**（应用的密钥——**换取 access_token 用**——**绝不泄露**）。**两个凭证的用法**（05 篇详讲）：**App ID + App Secret → tenant_access_token**（应用身份令牌 → 调 API）；**App ID + App Secret + 用户授权 → user_access_token**（用户身份令牌）。**凭证的三条纪律**：**App Secret 不进代码**（环境变量/配置中心——**09 篇密钥管理**）；**凭证泄露立即重置**（开发者后台重新生成——**旧 Secret 立即失效**）；**凭证与发布版本绑定**（改凭证后要重新发布应用）——"**App Secret 是应用的心脏：泄露 = 你的应用被别人操控**"（00 篇误区六）。

## 4. 应用能力：机器人开关

**应用能力（App Capabilities）是"应用能做什么"的开关**——**最核心的是"机器人"能力**：**在应用详情页开启机器人**——**开启后应用拥有一个"机器人身份"**（可被添加进群、收发消息、发卡片）——"**不开启机器人，应用就没有'嘴'和'耳朵'**"。**其他应用能力**：**网页**（应用有 Web 页面——H5 能力）、**小程序**（飞书内的小程序）、**权限模板**（批量授权）。**机器人开关与权限的关系**：**开关决定"能力有没有"**（能不能收发消息），**权限（scope）决定"能碰什么数据"**（能读谁的聊天/文档）——"**能力是'会不会'，权限是'能不能'——两个都要配**"。**开发者的第一步**：**建应用 → 开机器人 → 加进自己的群 → 测试收发**——"**机器人开关是自建应用的'开机键'**"。

## 5. 权限体系：scope

**权限（scope）决定应用能访问什么数据**——**申请制**（开发者后台 → 权限管理 → 申请，**管理员审批后生效**）。**核心权限速查**（00 篇基线）：

| 权限 | 用途 |
|------|------|
| im:message.p2p_msg:readonly | 接收单聊消息 |
| im:message.group_at_msg:readonly | 接收群聊 @机器人的消息 |
| im:message:send_as_bot | 机器人发文本/卡片 |
| cardkit:card:write | 创建/更新消息卡片 |
| im:chat:create / im:chat | 建群/获取群信息 |
| docx:document | 创建/编辑文档 |
| bitable:app | 多维表格读写 |

**权限的三个纪律**：**最小化**（只申请需要的——**im:message.group_msg（读群里所有消息）很敏感，确需才申请**）；**一次性申请**（第一次就把消息/卡片/文档/表格相关权限配齐——**避免反复补权限重新发版**）；**发布生效**（**权限修改后要发布新版本**——"**权限配了没发版 = 没配**"）——"**权限是应用的'边界'：scope 越大，责任越大**"。

## 6. 事件与回调配置

**事件与回调（Event & Callback）是"飞书主动通知你的应用"的通道**——**配置在"开发配置 → 事件与回调"**。**订阅方式两种**（05 篇详讲）：**长连接（WebSocket）**——**推荐**（无需公网地址、延迟低）；**HTTP 回调（Webhook）**——需公网请求地址。**必须订阅的两个事件**：**im.message.receive_v1**（收到用户消息——**机器人的"耳朵"**）；**card.action.trigger**（用户点击卡片按钮——**交互回调**，04 篇）。**配置的四个注意**：**订阅后要发布版本才生效**；**Webhook 模式要处理验签**（encrypt_key/verification_token——**05/09 篇**）；**事件可能重复推送**（**用 event_id 去重**——09 篇）；**回调要 3 秒内响应**（先返 200 再异步——09 篇）——"**事件订阅是机器人的'神经系统'：配置好事件，应用才能感知世界**"。

## 7. 发布版本与可用范围

**应用的生命周期以"版本"为单位**——**每次修改（权限/事件/能力）都要"创建版本 → 发布"才生效**：**① 创建版本**（版本号 + 更新说明——**变更留痕**）；**② 发布**（自建应用可能需要企业管理员审批）；**③ 可用范围**（应用/机器人对谁可用——**全员或指定部门/群**）。**发布流程的三个要点**：**发布 = 生效**（配置改了没发布 = 没生效——**排障先查版本**）；**可用范围影响机器人**（机器人只在可用范围内能被添加——**收不到消息先查范围**）；**版本历史**（**回滚**：发布旧版本恢复）——"**发布版本是应用的'上线'：配置是代码，发布是部署**"——**开发联调期用测试版本，正式启用再发布**。

## 8. 五个常见坑

- **坑一**：机器人能力没开就调消息 API——**报错/无权限；先开机器人开关**（第 4 节）；
- **坑二**：权限申请了没发布版本——**权限不生效；发布后重试**（第 7 节）；
- **坑三**：收不到消息先怀疑代码——**先查可用范围/机器人是否在群/事件是否订阅**（第 6 节）；
- **坑四**：App Secret 写进代码/仓库——**泄露即被劫持；环境变量 + 泄露立即重置**（第 3 节）；
- **坑五**：权限一次申请太少反复补——**每补一次发一次版；第一次配齐消息/卡片/文档/表格**（第 5 节）。
