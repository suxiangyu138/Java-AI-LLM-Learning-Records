## 1. 集成的四类场景

**程序猿把飞书接进开发链路的四类场景**（04 篇机器人的落地）：**CI/CD 通知**——构建/部署结果推群（**GitLab/Jenkins 集成**）；**监控告警**——异常告警直达告警群（**日志监控体系集成**）；**定时报告**——周报/巡检/数据汇总自动推送；**审批对接**——审批流与开发流程联动（**发布审批**）。**四类场景的共性**：**"通知自动化"**——**把"人盯着看"变成"机器人替你看"**——"**集成的价值公式：一次集成，永久免盯**"。**集成的起点**：**一个群机器人（Webhook）就能跑前三类**（04 篇——零开发），**应用机器人（完整 API）用于交互场景**——"**先 Webhook 跑起来，再升级应用机器人**"。

## 2. CI/CD 通知：构建结果进群

**CI/CD 通知是最高频的集成**——**GitLab CI 的集成**（GitLab 体系交叉：`../../../../02-后端核心技术 微服务 分布式 云原生/05-开发流程工具/GitLab/00-GitLab总览.md`）：

```yaml
# .gitlab-ci.yml 末尾加通知 job（群机器人 Webhook）
notify:
  stage: deploy
  script:
    - curl -X POST -H 'Content-Type: application/json' \
        -d '{"msg_type":"interactive","card":{
             "header":{"title":{"tag":"plain_text","content":"构建结果"}},
             "elements":[{"tag":"div","text":{"tag":"lark_md",
               "content":"**$CI_PROJECT_NAME** $CI_JOB_STATUS\n分支: $CI_COMMIT_BRANCH"}}]}}' \
        $FEISHU_WEBHOOK_URL
  only: [main]
```

**CI/CD 通知的三个设计**：**成功/失败分群**（**失败推告警群（@责任人）、成功推汇总群**）；**卡片带上下文**（项目/分支/提交——**失败不用翻流水线就能定位**）；**失败卡片带"查看日志"链接**（**一键跳转**）——"**通知的终点是'减少跳转'：群里看到结果，链接直达详情**"。

## 3. 监控告警：异常直达告警群

**监控告警集成让"故障第一时间到人"**（日志监控指标体系交叉：`../../../../02-后端核心技术 微服务 分布式 云原生/07-工程运维基础/运维/日志监控指标/`）：**告警系统（Prometheus/自研）→ 触发告警 → 推送到告警群**。**实现两种姿势**：**Webhook 直推**（告警系统配置飞书 Webhook——**简单**）；**告警平台转发**（告警平台统一管理 → 飞书/钉钉多通道分发——**告警治理**）。**告警集成的三个设计**：**告警分级**（P0/P1 推群 + @值班人、P2 只记录——**别让群被噪音刷屏**）；**告警卡片带处理入口**（"确认/升级"按钮——**卡片交互的价值场景**，04 篇）；**告警合并**（同类告警合并成一条——**风暴抑制**）——"**告警的终点不是'发出去'，是'被处理'——卡片上的确认按钮就是处理闭环的起点**"。

## 4. 定时报告：周报与巡检

**定时报告让"周期性的活"自动化**——**三类定时报告**：**周报/日报**（**aily 自动生成**——07 篇 AI 能力；或从多维表格数据汇总生成——06 篇）；**服务巡检**（定时检查服务状态 → 汇总推送——**早上到工位看到巡检报告**）；**数据报表**（多维表格数据定时汇总 → 仪表盘截图/数据推群）。**实现姿势**：**定时任务（XXL-Job/系统 cron）→ 调飞书 API/Webhook 推送**；**多维表格的定时自动化**（06 篇——**平台内配置**：定时汇总推群）——"**定时报告是'机器人的日常班'：固定时间、固定格式、固定接收人——把'每周手动汇总'变成'每周自动送达'**"。

## 5. 审批对接：流程自动化

**审批对接让"流程自动化"**——**场景**：**发布审批**（代码合并/部署前走飞书审批流 → **审批通过事件 → 自动触发部署**）；**权限申请**（开环境权限走审批 → 通过后自动开通）。**实现机制**（05 篇事件订阅）：**订阅审批事件**（`approval.instance.created` 等）→ **审批状态变化 → 触发后续动作**——"**审批是'人工确认的闸门'：闸门通过，程序自动放行**"。**审批对接的三个设计**：**审批流与发布流程绑定**（**发布记录里能看到审批链**——审计留痕）；**审批通过才执行**（**事件触发部署任务**——部署系统收到信号再动）；**超时兜底**（**审批超时提醒**——别让流程卡死）——"**审批对接是'人工与自动的握手'：人在飞书点通过，系统在后台自动执行**"。

## 6. 集成架构设计

**飞书集成的通用架构**（应用机器人场景）：**入口层**（消息/卡片/事件——**长连接或 Webhook**）；**处理层**（业务逻辑——**命令解析/卡片回调处理**）；**能力层**（飞书 API 调用——**发消息/读写表格**）；**数据层**（业务数据——**多维表格/自有数据库**）。**架构的三个原则**：**薄入口**（**消息进来只做解析，重逻辑异步化**——3 秒响应约束，09 篇）；**无状态**（**事件处理可重放**——event_id 去重 + 幂等）；**可观测**（**机器人处理日志**——"**机器人也是服务，要有日志与监控**"）。**部署形态**：**独立服务**（常驻——**长连接要求**）；**云函数/定时任务**（Webhook/定时场景）——"**飞书集成服务的架构 = 普通后端服务：入口薄、逻辑清、可观测**"。

## 7. 集成案例：发布通知闭环

**完整案例：发布流程的飞书闭环**（00 篇基线的工程落地）：

```text
① GitLab 构建（CI 流水线）
② 构建结果 → 飞书群（卡片：项目/分支/状态）
③ 通过 → 审批人收到审批任务（发布审批流）
④ 审批通过事件 → 触发部署任务
⑤ 部署结果 → 推回同一个群（卡片更新：✅ 已上线 v1.2）
⑥ 发布记录 → 写入多维表格（版本/内容/时间/审批人）
```

**闭环的三个价值**：**全程留痕**（**每个环节都有记录——审计**）；**状态可查**（**群里/表格里都能查到发布历史**）；**人工只出现在"审批"一环**（**其余全自动**）——"**集成闭环的终点：人在关键决策点（审批）把关，机器干完其余所有事**"。

## 8. 五个常见坑

- **坑一**：CI 通知成功失败一个群——**噪音淹没重点；失败告警群 + 成功汇总群**（第 2 节）；
- **坑二**：告警不合并——**告警风暴刷屏；同类合并 + 分级**（第 3 节）；
- **坑三**：集成服务无日志——**机器人出问题无从查；处理日志必留**（第 6 节）；
- **坑四**：审批超时无人管——**流程卡死；超时提醒兜底**（第 5 节）；
- **坑五**：Webhook token 硬编码在 CI 配置——**泄露刷群；变量注入（GitLab 的 masked 变量）**（第 2 节）。
