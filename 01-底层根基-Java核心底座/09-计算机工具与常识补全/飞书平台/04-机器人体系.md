## 1. 三类机器人全景

**飞书的机器人分三类**（能力从弱到强）：**群机器人（自定义机器人）**——**群里添加、Webhook 推送**（只能"说"不能"听"）；**应用机器人**——**自建应用的机器人身份**（能说能听能交互——**03 篇机器人开关的产物**）；**aily 智能体**——**2026 年 AI 对话机器人**（上下文感知、主动交付、常驻联系人列表）。**三类机器人的选型**：

| 类型 | 能力 | 适用 |
|------|------|------|
| 群机器人 | 推送消息（Webhook） | ⭐ 简单通知（CI 结果/告警） |
| 应用机器人 | 收发消息/卡片/事件订阅 | ⭐ 完整交互（对话/工单/审批） |
| aily 智能体 | AI 对话/主动交付 | AI 场景（周报/数据分析） |

——"**推送用群机器人（零开发），交互用应用机器人（完整能力），AI 用 aily**"——**程序猿最常打交道的是前两类**。

## 2. 群机器人：Webhook 推送

**群机器人（自定义机器人）是"零开发"的通知方案**——**用法三步**：**① 群设置 → 群机器人 → 添加自定义机器人**（拿 Webhook 地址）；**② 向 Webhook POST 消息**（JSON 格式）；**③ 群内收到消息**。**Webhook 推送的两种消息**（00 篇基线）：

```json
// 文本消息
POST https://open.feishu.cn/open-apis/bot/v2/hook/{token}
{ "msg_type": "text", "content": { "text": "构建成功：order-service v1.2" } }

// 消息卡片（富文本 + 交互按钮）
{ "msg_type": "interactive",
  "card": { "header": { "title": { "tag": "plain_text", "content": "构建结果" } },
            "elements": [ { "tag": "div", "text": { "tag": "lark_md", "content": "✅ 成功" } } ] } }
```

**群机器人的三个特点**：**零开发**（curl 就能推——**CI 脚本里直接调**）；**单向**（只能推不能收——**交互要应用机器人**）；**token 即权限**（**Webhook token 泄露 = 群被刷屏**——**加签名校验或定期轮换**）。**适用场景**：**CI/CD 构建结果、监控告警、定时报告**（08 篇）——"**群机器人是'通知的第一档'：一行 curl 把消息推进群**"。

## 3. 应用机器人：完整能力

**应用机器人是自建应用的机器人身份**（03 篇机器人开关）——**比群机器人多三件事**：**能收消息**（单聊/群 @——`im.message.receive_v1` 事件订阅）；**能发交互卡片**（CardKit 2.0——第 5 节）；**能调全部 API**（多维表格/文档/日历——**05 篇**）。**应用机器人的使用流程**：**建应用 → 开机器人 → 申请权限（im:message.*）→ 订阅事件 → 发布版本 → 添加进群**——"**应用机器人是'通知的第二档'：群机器人只会说，它会听、会想、会做**"。**与用户的交互形态**：**单聊**（用户直接找机器人对话——**工单/问答**）；**群 @**（群里 @机器人触发——**命令式交互**："@运维机器人 查一下服务状态"）——"**应用机器人 = 群里的'自动同事'：@它就能干活**"。

## 4. 消息类型

**机器人能发的消息类型**（msg_type）：**text**（纯文本）；**post**（富文本：@人/链接/加粗）；**image**（图片）；**file**（文件）；**interactive**（**消息卡片**——主力）；**share_chat**（分享群）。**选型主线**：**简单通知用 text/post、复杂展示与交互用 interactive（卡片）**——"**文本是短信，卡片是 App 页面——展示质量选卡片**"。**消息的工程细节**：**@人 通知**（post 消息里 @user_id——**重要消息直达**）；**消息频率**（**别刷屏**——多条合并成一条卡片，09 篇限流）；**消息长度**（长文本用卡片折叠——**可读性**）——"**消息质量 = 接收者的注意力：把多条合并、把重点 @人**"。

## 5. 消息卡片：迷你前端

**消息卡片（Message Card）是飞书消息的"富交互形态"**——**为什么说它是"迷你前端"**：**卡片有结构**（header + elements——**JSON 2.0 定义**）；**卡片有交互**（按钮/表单/下拉——**点击回调到你的服务**）；**卡片有状态**（**可更新**——按钮点了卡片变"已处理"）。**卡片的常用元素**（CardKit 2.0）：**header**（标题 + 颜色）；**div**（文本块——**支持 lark_md 格式**）；**button**（按钮——**交互入口**）；**action**（表单/下拉）；**hr**（分割线）；**note**（注释）。**卡片的开发**（05 篇 API）：**申请 cardkit:card:write 权限** → **发送 interactive 消息** → **用户点击 → card.action.trigger 回调** → **更新卡片**——"**卡片是'消息里的应用'：通知 + 操作一步完成（'构建失败'卡片上直接点'重试'）**"。

## 6. 卡片交互：回调与状态更新

**卡片交互的完整闭环**（00 篇基线）：

```text
机器人发卡片（含按钮）
  → 用户点击按钮
  → 飞书回调 card.action.trigger 到你的服务（03 篇事件订阅）
  → 服务端处理（执行业务/查数据）
  → 更新卡片（按钮变"已处理"、内容刷新）或发新消息
```

**实现的三件事**：**订阅回调**（card.action.trigger 事件——**03 篇**）；**处理回调**（解析 action 值——**按钮的 value 字段**）；**更新卡片**（调用更新卡片 API——**交互后的状态反馈**）。**三个工程要点**：**回调验签**（encrypt_key/verification_token——**05/09 篇**）；**回调幂等**（用户可能重复点击——**按 action 唯一标识去重**）；**3 秒响应**（先返 200 再异步处理——**09 篇**）——"**卡片交互是'消息里的业务闭环'：通知 → 操作 → 反馈，一步不离开聊天窗口**"。

## 7. 机器人的应用场景

**机器人的四个经典场景**（08 篇展开）：**CI/CD 通知**——构建/部署结果推群（卡片带"查看日志"按钮）；**监控告警**——异常告警推告警群（卡片带"确认/升级"按钮）；**自动化助手**——@机器人查服务状态/执行命令（**值班机器人**）；**业务流转**——工单提交/审批通知（用户和机器人对话提交，卡片确认）。**场景设计的心法**：**"机器人替代的是'人肉盯'和'人肉转发'"**——**凡是要人盯着看的、要人手动转发的，都是机器人的候选场景**——"**机器人不是玩具，是'把通知与操作自动化'的工程手段**"。

## 8. 五个常见坑

- **坑一**：交互需求用群机器人——**群机器人只能推；交互用应用机器人**（第 1 节）；
- **坑二**：Webhook token 泄露不处理——**群被刷屏；加签名/轮换**（第 2 节）；
- **坑三**：卡片按钮点击没反应——**card.action.trigger 没订阅/没发布版本；排障顺序**（第 6 节）；
- **坑四**：卡片不更新——**交互后要调更新 API；按钮点了卡片还是原样 = 体验断裂**（第 6 节）；
- **坑五**：消息刷屏——**多条合并成卡片；通知频率克制**（第 4 节）。
