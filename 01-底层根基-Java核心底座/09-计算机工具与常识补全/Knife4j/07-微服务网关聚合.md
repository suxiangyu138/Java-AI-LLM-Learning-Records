# 07 - 微服务网关聚合

> 🎯 微服务时代文档的痛点：每个服务一个 doc.html，联调要记 N 个地址。解法有三：knife4j-admin 注册中心聚合、网关统一入口转发、knife4j-front 纯前端独立部署。聚合方案的选择 = 架构复杂度与运维成本的权衡

## 1. 微服务文档的三类痛点

微服务架构下文档管理必然遇到三个问题：

- **入口分散**：user-service/order-service/gateway 各有 doc.html，联调时记 N 个 URL
- **版本漂移**：各服务独立发版，文档版本与服务版本难对应（文档聚合 + 版本号展示才能对齐）
- **网络隔离**：内网多服务端口不便全部暴露，聚合到网关统一入口是标准解

解决思路统一：**文档聚合到单一入口**——所有服务的 /v3/api-docs 汇总到一个页面，按服务分 tab。三个方案（admin/网关/front）的区别在"聚合逻辑放在哪一层"。

## 2. 方案一：knife4j-admin 注册中心

knife4j-admin 是 Knife4j 生态的云端文档注册管理中心：

```text
架构：
├── 每个微服务：引入 knife4j 依赖，启动后自动向 admin 注册
├── knife4j-admin：独立部署的注册中心（管理所有服务的文档元信息）
└── 访问端：doc.html 从 admin 拉取服务列表，按服务切换文档
```

能力：**服务注册与发现**（服务上线自动出现在文档中心）、**文档元信息管理**（版本/分组/描述）、**网关聚合支持**（admin 与网关聚合配合：网关转发 + admin 管理注册）。

适用场景：**服务数量多（10+）且动态变化**的团队——注册中心让"新增服务自动入文档"成为可能，不需要手动维护聚合配置。

## 3. 方案二：网关聚合

网关（Spring Cloud Gateway）聚合是主流方案：每个服务暴露 /v3/api-docs，网关把请求转发到各服务聚合。

```text
请求路径设计：
网关 /v3/api-docs/user/** → user-service 的 /v3/api-docs
网关 /v3/api-docs/order/** → order-service 的 /v3/api-docs
doc.html 配置多个文档源 → 一个页面看所有服务
```

实现要点（Spring Cloud Gateway + SpringDoc）：网关不自己生成文档，只做**路由转发**；各服务保持自己的 /v3/api-docs；doc.html 侧的 springdoc.group-configs 或前端配置把各服务作为独立分组。SpringDoc 官方提供网关聚合的 RouteLocator 配置方式（`springdoc.swagger-ui.urls` 或 OpenApiResource 转发）。

**优点**：不引入新组件（复用网关基建）、路径清晰（URL 语义化）。**缺点**：网关要维护路由规则，服务多时配置增长。

## 4. 方案三：knife4j-front 独立部署

knife4j-front 是纯前端静态版本：不依赖 Java 后端，直接加载各服务的 OpenAPI 文档：

```text
架构：
├── knife4j-front：静态资源独立部署（Nginx/任意静态服务器）
└── 数据源：直接请求各服务的 /v3/api-docs（或经网关）
```

适用场景：**非 Java 项目**（Node/Go/Python 服务只要暴露 OpenAPI JSON 就能用 Knife4j 界面）、**不想动服务端**（前端独立升级不影响业务服务）、**文档展示与业务隔离**（静态站 + CDN）。

**关键约束**：浏览器跨域——knife4j-front 请求各服务 /v3/api-docs 需要 CORS 支持或同域反向代理。配置方式：前端配置文件声明各文档源 URL。

## 5. 三方案选型对比

| 维度 | knife4j-admin | 网关聚合 | knife4j-front |
|------|--------------|----------|---------------|
| 新增组件 | admin 服务 | 无（复用网关） | 静态站 |
| 服务注册 | 自动 | 手动路由 | 手动配置 |
| 非 Java 支持 | 弱 | 中 | 强 |
| 运维成本 | 中（多一个服务） | 低 | 低 |
| 适用规模 | 10+ 服务动态变化 | 3-10 服务固定 | 异构语言/轻量 |

**选型逻辑**：服务少且固定 → 网关聚合（零新增组件）；服务多且动态 → admin（自动注册）；异构语言或纯展示 → front（最轻）。**升级路径**：网关聚合起步 → 服务多了升级 admin——聚合方案可平滑演进。

## 6. 聚合后的调试与安全

聚合带来两个新问题：

**调试**：聚合页面调试接口时请求发往"文档源地址"（各服务直连或经网关）——跨服务调试要注意 CORS 与网络可达；统一走网关转发可保证路径一致。

**安全**：聚合页成为**所有服务文档的单点入口**——一旦泄露，全部接口签名暴露。安全基线：聚合入口必须加认证（basic/网关鉴权）；各服务的 /v3/api-docs 也要按需屏蔽（production 配置各服务独立生效）；聚合页部署在内网/VPN 后。

## 7. 实战：网关聚合配置示例

```yaml
# gateway 的 springdoc 聚合配置（RouteLocator 方式）
spring:
  cloud:
    gateway:
      routes:
        - id: user-service-docs
          uri: lb://user-service
          predicates:
            - Path=/api-docs/user/**
          filters:
            - RewritePath=/api-docs/user/(?<segment>.*), /v3/api-docs/$\{segment}
        - id: order-service-docs
          uri: lb://order-service
          predicates:
            - Path=/api-docs/order/**
          filters:
            - RewritePath=/api-docs/order/(?<segment>.*), /v3/api-docs/$\{segment}
```

```yaml
# 各服务的 springdoc 配置（保证组内文档完整）
springdoc:
  group-configs:
    - group: default
      packages-to-scan: com.example.controller
```

```yaml
# 前端（或 doc.html 所在服务的配置）声明多个文档源
springdoc:
  swagger-ui:
    urls:
      - name: 用户服务
        url: /api-docs/user/v3/api-docs
      - name: 订单服务
        url: /api-docs/order/v3/api-docs
```

验证：访问聚合入口 → 用户服务/订单服务两个 tab → 各 tab 数据来自对应服务 → 调试请求经网关转发成功。**注意**：网关聚合的路径重写（RewritePath）是最高频的配置坑——路径不匹配时表现为 tab 加载 404/空文档。

聚合方案与团队协作的配合：**聚合入口是文档的"唯一官方地址"**——团队文档、招聘对接、外部合作都引用聚合入口而非各服务地址；聚合页的 tab 命名与服务命名一致（user-service 就叫"用户服务"），降低认知成本。运维侧：聚合入口的健康检查（tab 能加载 = 各服务 /v3/api-docs 可达）纳入监控——服务挂了文档 tab 会白屏，这是"文档可用性"的隐性指标，排查联调问题时常被忽略。聚合方案落地时还有一条纪律：**文档服务独立于业务部署**（聚合入口不随某个业务服务重启而抖动），配合 CI 发布流水线自动刷新文档源配置，让"文档中心"成为稳定的基础设施而非附属品。
