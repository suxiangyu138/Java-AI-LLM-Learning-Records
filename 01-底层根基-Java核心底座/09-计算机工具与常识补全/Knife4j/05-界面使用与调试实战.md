## 1. 界面布局：doc.html 地图

```text
doc.html 布局（左右分栏）：
├── 左侧：分组列表（@Tag 分组 + 排序）→ 分组内接口列表
│   ├── 接口方法标识（GET 绿 / POST 蓝 / PUT 橙 / DELETE 红）
│   ├── 必填参数标记（红色 * 号）
│   └── 接口摘要（@Operation summary）
├── 右上：全局搜索框 / Authorize / 文档管理（离线导出）
└── 右侧主区：选中接口的详情
    ├── 参数区（路径/query/header/body 分块）
    ├── 调试区（发送按钮 + 参数编辑）
    └── 响应区（状态码/头/体/耗时）
```

布局要点：**方法颜色即类型**（看颜色就知道是什么操作）；**必填标记**（红色 * 提示缺参）；**分组可折叠**（大项目只关注自己的组）。Knife4j 基于 Vue + Ant Design 构建，布局与操作习惯贴合国内团队——这就是它相比原生 Swagger UI 的体验优势。

## 2. 接口调试完整流程

```text
① 选中接口 → ② 查看参数（必填项红色标记）
③ 填参数（example 直接可用）→ ④ 点"发送"（Debug 调试）
⑤ 看响应（状态码/头/体/耗时）→ ⑥ 调试失败排查参数
```

调试的四个高频操作：**填 example**（注解给的示例直接点用）；**切换参数类型**（JSON/表单）；**增删参数行**（动态参数）；**复制 curl**（交接给同事）。调试注意点：**Body 参数的 JSON 格式要合法**（报 400 多半是 JSON 语法错或字段名不符，先看响应体错误信息）；**query 参数与路径参数分开放**（路径参数在 URL 路径里填，query 在查询参数区）。

## 3. 文件上传与 multipart 调试

```java
@Operation(summary = "上传文件")
@PostMapping("/upload")
public Result upload(
        @Parameter(description = "文件") @RequestPart("file") MultipartFile file,
        @Parameter(description = "备注") @RequestParam String note) { ... }
```

doc.html 中 multipart 接口的调试：**参数类型显示为 file**，点击选择本地文件；其他表单字段（note 等）正常填。三个注意点：**文件大小受后端限制**（Spring 默认 1MB，配 multipart.max-file-size）；**文件类型与 Content-Type**（application/json 的接口不能传文件）；**调试上传成功看响应**（返回文件 ID/URL 即成功，常见 500 是存储路径问题）。

## 4. 分页与鉴权接口调试

**分页接口**：参数一般为 page/size（或 pageNum/pageSize），example 写死默认值（page=1, size=10）方便直接调试；排序参数（sortBy/order）可选填。**鉴权接口**：先 Authorize 填 token（04 篇），或全局参数配 Authorization——调试 401 时先检查"是否带了认证头"（看调试请求的实际 header），再检查 token 是否过期。

```text
分页调试三步：填 page=1&size=10 → 发送 → 看返回的 total 与当前页数据
鉴权调试三步：Authorize 填 token → 发送 → 401 时核对 token 与 header
```

调试中遇到 401/403 的排查顺序：**先确认请求带了认证头（Knife4j 请求详情里可见）→ 再确认 token 有效（后端日志/解码 JWT）→ 后确认权限（角色是否够）**——与生产排错逻辑一致。

## 5. 多 tab 与多文档

doc.html 支持多 tab 展示多个接口文档（分组即 tab）；配合 knife4j-admin（07 篇）可在一个页面聚合多个服务的文档。

```text
单服务：分组 = tab（用户服务/订单服务/管理端）
微服务：服务 = tab（user-service/order-service/gateway）
```

多 tab 的价值：**跨组对照调试**（下单流程跨"订单服务"与"用户服务"两个 tab 时对照参数）；**微服务联调**（聚合后一个页面调所有服务，不用记多个地址）。tab 切换后调试参数保留（全局缓存），跨 tab 对照成本低。

## 6. 响应解读：五段信息

调试响应分五段展示，各自用途：

| 段 | 内容 | 用途 |
|----|------|------|
| 状态码 | 200/400/401/500 | 第一判断（是否成功） |
| 响应头 | Content-Type/Set-Cookie 等 | 类型/会话/缓存头确认 |
| 响应体 | JSON 数据 | 业务数据（主要看这里） |
| 响应时间 | 毫秒 | 性能初判（>1s 要查） |
| Curl | 请求命令 | 复现/交接 |

响应排查流程：**状态码定方向**（4xx 参数/权限问题，5xx 后端问题）→ **响应体看细节**（错误信息 message）→ **响应时间定性能**（慢接口去后端查）。**把响应体与接口文档对照**——返回字段与 @Schema 不一致说明实现与文档漂移，要修代码或注解。

## 7. 调试实战演练

一个完整演练：**"登录 → 鉴权查询用户"** 流程：

```text
① 登录接口（POST /api/auth/login）：填用户名密码 → 发送 → 拿 token
② Authorize 填 token（Bearer xxx）
③ 查询用户接口（GET /api/users/{id}）：填 id → 发送
④ 200 返回用户数据 = 全流程验证通过
⑤ 复制 curl 贴给前端同事作为对接基准
```

演练的价值：**验证了完整业务链路**（认证 → 业务接口），**产出了交接物**（curl 命令），**发现了文档盲区**（如果某步参数不清晰，说明注解要补）。建议每个新模块上线前，用 Knife4j 走一遍核心流程——这是文档质量与接口质量的最后一道人工验证。

补充两个日常提效习惯：**把 Knife4j 当"接口快速验证台"**——写前端联调前先在这里确认响应结构，省得"前端写错字段名"来回扯皮；**调试失败时先看 Knife4j 生成的 curl**——curl 里的请求与界面发送的完全一致，把 curl 在终端重跑一遍能区分"界面问题"与"后端问题"。文档不仅是"给别人看的"，更是自己开发时的第一调试工具。

与测试体系的配合：Knife4j 调试验证通过后，**curl 命令可以直接改造成接口测试用例**（JUnit + MockMvc/RestTemplate 或 Postman 导入）——调试成果沉淀为自动化测试，避免"联调通过了、回归没人管"。这个"调试 → curl → 测试用例"的转换链是文档工具价值最大化的工作流：Knife4j 解决即时验证，测试体系解决持续回归，两者互补不重叠。
