## 1. 为什么文档安全是大事

API 文档泄露的实际危害不是"文档被看"，而是**攻击面的完整暴露**：

- **接口签名泄露**：攻击者拿到全部接口路径、参数、返回结构——等于拿到了攻击地图
- **内部信息泄露**：controller 包名、实体字段、业务逻辑描述（@Operation 写得太详细时）
- **调试入口泄露**：doc.html 在线调试可直接对接口发请求——未鉴权的接口等于裸奔

**认知基线**：doc.html 与 /v3/api-docs 在生产环境默认"不该存在"——不是"应该保护"，是"默认不该开"。上线检查把"文档是否暴露"列为必查项，与"数据库密码是否硬编码"同级。

## 2. 生产屏蔽：production 配置

```yaml
knife4j:
  enable: true
  production: true        # ★ 生产屏蔽（最高优先级）
```

production=true 的行为：**doc.html 返回 404**、/v3/api-docs 数据不可访问——彻底关闭文档入口。要点：

- **production 与 enable 的关系**：enable 全环境保持 true（否则 dev 也打不开），屏蔽交给 production——多环境配置见 06 篇
- **生效机制**：Knife4j 拦截器在生产模式下拦截文档访问路径
- **验证姿势**：生产部署后 curl `http://生产地址/doc.html` 应返回 404

**注意**：production 屏蔽的是 Knife4j 的增强层，springdoc 的 /v3/api-docs 与 swagger-ui 路径需要单独处理（springdoc.api-docs.enabled=false 或 Security 拦截）。

## 3. basic 认证：密码保护

需要"内网可看、外网不可看"或"预发环境验证"时，用 basic 认证：

```yaml
knife4j:
  enable: true
  basic:
    enable: true
    username: docviewer
    password: ${KNIFE4J_DOC_PASSWORD}     # 密码走环境变量，不硬编码
```

basic 认证的工程要点：**密码不硬编码**（环境变量/配置中心注入，与数据库密码同等对待）；**弱口令是摆设**（admin/123456 等于没设，暴力破解成本低）；**basic 只保护 doc.html 入口**——直接访问 /v3/api-docs 需要 Spring Security 配合拦截。

## 4. Spring Security 放行清单

项目用了 Spring Security 时，**默认所有请求被拦截**——doc.html 会被 401 拦下，需要放行：

```java
@Configuration
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                // 文档相关路径放行（开发/测试环境）
                .requestMatchers(
                    "/doc.html",
                    "/webjars/**",
                    "/v3/api-docs/**",
                    "/swagger-resources/**",
                    "/favicon.ico"
                ).permitAll()
                .anyRequest().authenticated()
            );
        return http.build();
    }
}
```

**放行的正确姿势**：放行清单按环境区分——`@Profile("dev")` 的 Security 配置放行文档路径，生产环境不放行（文档被 Security 拦截，双保险）。**最小暴露原则**：`/v3/api-docs/**` 只放行必要子路径（如 /v3/api-docs/default）；不放行的路径 Security 天然拦截。**常见错误**：放行写得太宽（`/**` 全放行等于没安全）或漏掉 webjars（doc.html 样式加载失败）。

## 5. 三层安全模型

```text
第一层：生产屏蔽（production=true）
  效果：doc.html 与文档数据 404，公众不可见
  适用：对外生产环境

第二层：basic 认证（knife4j.basic）
  效果：有密码才能看文档（保护 doc.html 入口）
  适用：内网/预发/受限访问

第三层：Spring Security / 网关鉴权
  效果：路径级拦截（/doc.html 与 /v3/api-docs 全拦）
  适用：有统一安全框架的项目

组合策略：
├── 纯内网系统：production=true + basic（双保险）
├── 有 Security 的项目：production=true + Security 不放行文档路径
└── 微服务：聚合入口认证 + 各服务独立屏蔽（07 篇）
```

**三层的关系不是"选一层"而是"叠加"**：production 是第一道（公众视角），basic 是第二道（知道地址的人也要密码），Security 是第三道（路径级强制）——生产环境至少两道，重要系统三道全上。

## 6. 安全清单与审计

上线前安全清单（10 项）：

| # | 检查项 | 标准 |
|---|--------|------|
| 1 | 生产环境 doc.html 访问 | 404（curl 验证） |
| 2 | 生产环境 /v3/api-docs | 不可达 |
| 3 | basic 密码 | 环境变量注入，非硬编码 |
| 4 | Security 放行 | 按环境区分，生产不放行 |
| 5 | 注解敏感信息 | @Schema example 无密码/密钥 |
| 6 | 内部路径泄露 | paths-to-match 限定 /api/** |
| 7 | 聚合入口 | 有认证（微服务场景） |
| 8 | 日志无文档 URL 泄露 | 错误日志不打印 doc.html 完整地址 |
| 9 | 灰度/预发环境 | basic 保护 |
| 10 | 定期审计 | 每版本发布复查文档暴露状态 |

**审计节奏**：发布流水线加一步"文档暴露检测"（curl 检查生产 doc.html 状态码），自动化替代人工记忆——文档安全与代码安全一样需要持续验证。

安全配置的两个进阶场景：**内网但敏感的系统**（金融/政务）——即使内网也要 production=true，文档走审批制（需要时临时开 + 日志审计）；**多环境策略**——dev/test 全开、预发（staging）basic 保护、生产全屏蔽，三级环境三级策略，写进部署手册。安全是"环境策略"不是"一次配置"——每个环境都有明确的文档开放等级，审核发布时按环境核对。

安全配置的落地检查还有一个容易被忽视的环节：**文档里的调试信息本身可能泄露环境细节**——@Operation 描述里不要写内网 IP、数据库表名、部署路径；example 里不要放真实数据（用脱敏示例）；错误响应描述不要暴露堆栈信息。文档安全不止"文档关不关"，还有"文档内容藏什么"——敏感信息从注解源头就杜绝，比事后清理可靠。

另一个隐性入口：**聚合文档与第三方文档引用**（07 篇的聚合入口、离线文档外发）——导出给外部合作方的离线文档要过一遍敏感信息检查（导出前用脚本扫描 description/example 里的 IP 与密钥模式）；文档外发要记录（谁、什么时候、什么版本）——文档是资产，外发要可追溯。安全基线从"技术配置"延伸到"管理流程"，两层配合才完整。最后的提醒：**安全配置的验收要"从攻击者视角"做**——不登录、不带 cookie、curl 直接访问 doc.html 与 /v3/api-docs，能拦住的才是真的安全；"浏览器里打不开"不等于"别人打不开"，绕过 UI 直连端点才是攻击者的姿势。
