# 03 - 注解体系与文档模型

> 🎯 文档质量 = 注解质量。Knife4j 4.x 的注解体系 = OpenAPI 3 标准注解（@Tag/@Operation/@Parameter/@Schema）+ 增强注解（@ApiOperationSupport/@DynamicParameter/@ApiSort）。标准注解管"内容"，增强注解管"呈现与排序"

## 1. 文档模型：注解如何变成文档

注解 → 文档的完整链路：

```text
@Tag/@Operation/@Parameter/@Schema 注解
  → SpringDoc 扫描（配置阶段读取控制器与实体类）
  → OpenAPI 文档对象（/v3/api-docs 的 JSON）
  → Knife4j 前端渲染（doc.html 分组/排序/展示）
```

两个推论：**注解缺失 = 文档缺失**（没加 @Operation 的接口在文档里只有路径与方法名）；**增强注解不改变 OpenAPI 数据结构**（@ApiSort 只影响 Knife4j 的呈现顺序，/v3/api-docs 里没有排序字段）。所以增强注解的生效依赖 Knife4j 渲染层，标准注解则对任何 UI 生效。

## 2. 标准注解：OpenAPI 3 五件套

| 注解 | 位置 | 作用 |
|------|------|------|
| @Tag | 控制器类 | 接口分组标签（name + description） |
| @Operation | 方法 | 接口说明（summary 标题 + description 详情） |
| @Parameter | 方法参数 | 参数说明（description/required/example） |
| @Schema | 实体类/字段 | 模型说明（description/example/required） |
| @ApiResponse | 方法 | 响应说明（code/description/response） |

```java
@Tag(name = "订单管理", description = "订单查询与操作")
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @Operation(summary = "分页查询订单", description = "支持按状态筛选")
    @ApiResponse(responseCode = "200", description = "查询成功")
    @GetMapping
    public PageResult<Order> page(
            @Parameter(description = "页码", example = "1") @RequestParam int page,
            @Parameter(description = "每页条数", example = "10") @RequestParam int size) { ... }
}
```

**注解质量三原则**：description 写"做什么 + 边界"而非重复方法名；参数 example 必须给（调试时直接可用）；响应说明覆盖错误码（400/404/500）。**注解是给调用方看的合同**——把"别人会用这个接口"当标准来写。

## 3. 实体建模：@Schema 与嵌套

```java
@Schema(description = "订单实体")
public class Order {
    @Schema(description = "订单 ID", example = "10001")
    private Long id;

    @Schema(description = "订单状态", example = "PAID")
    private OrderStatus status;          // 枚举

    @Schema(description = "订单项列表")
    private List<OrderItem> items;       // 嵌套实体
}
```

实体建模要点：**@Schema 标注每个字段**（否则文档只显示字段名与类型）；**嵌套实体自动展开**（SpringDoc 递归解析 List<OrderItem> 等结构）；**枚举自动生成可选值**（OrderStatus 的枚举值列表）；**循环引用处理**（A 引用 B、B 引用 A 时用 @Schema(accessMode = READ_ONLY) 或忽略字段避免文档膨胀）。Models 标签页（05 篇）以树形展示全部实体——**Models 是实体的总目录，接口参数是具体用法**。

## 4. 增强注解：排序与忽略

```java
@ApiSort(1)                                          // 分组排序（控制器类上）
@ApiOperationSupport(order = 1)                      // 接口排序（方法上）
public class UserController {

    @ApiOperationSupport(order = 2)
    @GetMapping("/{id}") public User get(...) { ... }

    @ApiOperationSupport(order = 1, ignoreParameters = {"id"})  // 忽略某参数
    @PostMapping public User create(...) { ... }
}
```

| 增强注解 | 作用 |
|----------|------|
| @ApiSort | 分组（Tag）排序 |
| @ApiOperationSupport(order) | 接口排序 |
| @ApiOperationSupport(ignoreParameters) | 忽略指定参数（如从父类继承的无关参数） |
| @DynamicParameter(s) | Map 动态参数文档化 |

排序价值：**文档顺序 = 业务使用顺序**——登录接口在前、核心流程其次、管理接口最后，比默认的字母序可读性强一个量级。注意增强注解对 OpenAPI 数据无影响（第 1 节），换 swagger-ui.html 看就是原始顺序。

## 5. 动态参数：Map 接口的文档化

Map 类型的接口参数（如通用配置接口 `Map<String, Object>`）SpringDoc 无法解析字段，用动态参数注解显式声明：

```java
@ApiOperationSupport(
    dynamicParameters = @DynamicParameter(
        name = "config",
        description = "配置项",
        required = true,
        example = "{\"key\":\"value\"}",
        dataTypeClass = Object.class
    )
)
@PostMapping("/config")
public Result saveConfig(@RequestBody Map<String, Object> config) { ... }
```

适用场景：**通用查询条件**（Map 承载过滤条件）、**配置接口**、**扩展字段**（前端传自定义属性）。动态参数让"无法静态建模"的接口也有可读文档——这是 Knife4j 相对纯 SpringDoc 的差异化能力之一。

## 6. 注解规范：团队文档质量红线

把注解规范写进团队约定（可配合 Spotless/自定义检查）：

```text
必做清单：
├── 所有控制器类 @Tag（name 与 description 都写）
├── 所有对外方法 @Operation（summary 必填）
├── 所有参数 @Parameter（description 必填，example 尽量给）
├── 所有实体字段 @Schema（description 必填）
└── 错误响应 @ApiResponse（400/404/500 至少覆盖）
禁做清单：
├── 不写 description 只写方法名重复
├── 用中文标点破坏 example（调试直接复制用）
├── 敏感字段（密码/密钥）出现在 @Schema example
└── 接口无注释就发布（文档是合同）
```

**文档质量检查进 CI**：可用 openapi-diff 类工具对比 /v3/api-docs 变更，或脚本检查关键注解覆盖率——文档与代码一样需要回归测试。红线意识：**接口文档是给外部调用方的合同，草率的文档 = 低质量的接口信任**。

一个注解体系与业务规范衔接的实践：**接口版本管理用注解表达**——新版本接口在 @Operation 描述里标注版本（"v2：新增 xxx 字段"）并 deprecate 旧接口；配合 @Tag 分组把 v1/v2 接口分区展示，调用方在文档里就能看到迁移指引。注解不仅是"当前接口的说明书"，还可以是"接口演进的历史记录"——把版本信息写进文档，比让调用方翻 changelog 友好得多。

注解还有一个被低估的价值：**它是 AI 时代的结构化语料**——AI 编程助手（Copilot 类工具）补全接口时依赖上下文中的注解；接口调用方用 AI 生成请求代码时，@Schema 的字段描述直接决定生成质量。**把注解写好 = 给 AI 一份高质量的结构化接口说明**——这是 2026 年注解规范的新意义，也是"文档即资产"在 AI 时代的延伸。

注解命名与团队规范的衔接：**注解的 description 要与接口文档规范模板一致**（问题域词汇统一，"订单"不写成"订单一"），避免一个接口多套说法；**枚举字段的 @Schema 描述里列出可选值含义**（PAID=已支付），比让调用方猜状态码强；**版本敏感接口标注 @Operation(deprecated = true)**，文档里显示废弃标记，引导调用方迁移——文档的"退役管理"与"上线管理"同样重要。

一个容易被忽略的注解细节：**@Tag 的 name 会出现在 URL 分组与文档标题中，命名要稳定**——改名会导致文档分组变化、外部引用失效；@Operation 的 summary 是列表页唯一展示的文本，要写成"动词 + 对象"（"查询用户详情"）而非名词（"用户详情"）；@Parameter 的 example 必须合法（JSON 接口给 JSON 示例、枚举给枚举值）——非法 example 在调试时直接误导。注解是"写给人看的合同"，稳定性和可用性比"写得多"更重要。
