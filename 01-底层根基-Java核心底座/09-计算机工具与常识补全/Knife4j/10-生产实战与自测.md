## 1. 实战：用户中心 API 文档端到端

**目标**：Boot 3 用户中心项目，Knife4j 文档做到"能看、能调、能导出、生产不可见"。

**① 依赖与配置**：

```xml
<dependency>
    <groupId>com.github.xiaoymin</groupId>
    <artifactId>knife4j-openapi3-jakarta-spring-boot-starter</artifactId>
    <version>4.5.0</version>
</dependency>
```

```yaml
springdoc:
  group-configs:
    - group: 认证模块
      packages-to-scan: com.example.auth.controller
    - group: 用户模块
      packages-to-scan: com.example.user.controller
knife4j:
  enable: true
  production: ${KNIFE4J_PRODUCTION:false}     # 生产环境注入 true
  setting:
    language: zh_cn
  basic:
    enable: ${KNIFE4J_BASIC:false}
    username: docviewer
    password: ${KNIFE4J_PASSWORD:}
```

**② 注解规范落地**（@Tag + @Operation + @Parameter + @Schema 全覆盖，见 03 篇）——这是文档质量的 80%。

**③ 分组与排序**：认证模块 @ApiSort(1)、用户模块 @ApiSort(2)，模块内接口按业务顺序排序。

**④ 安全配置**（application-prod.yml）：`knife4j.production: true`；Security 放行仅 dev/test profile（08 篇三层模型）。

**⑤ 验证与交付**：

```bash
# 开发验证
curl http://localhost:8080/v3/api-docs | jq '.paths | keys'   # 数据源完整
# 生产验证（部署后）
curl -I http://生产地址/doc.html        # 期望 404
curl -I http://生产地址/v3/api-docs      # 期望不可达
# 离线文档：doc.html → 文档管理 → 导出 Markdown 进 docs/api/ 提交
```

**⑥ 核心流程走查**：Knife4j 调试"登录 → 查用户"全链路（05 篇演练），curl 交接给前端。

## 3. 报错速查十条

| # | 错误 | 根因 | 解法 |
|---|------|------|------|
| 1 | doc.html 404 | enable 未开/依赖未生效 | knife4j.enable=true；核对依赖 |
| 2 | 依赖冲突 | 手动加了 springdoc-openapi | 删除，4.x 内置 |
| 3 | NoClassDefFoundError | starter 与 Boot 版本不匹配 | Boot 3 用 jakarta starter |
| 4 | 接口不显示 | 扫描包配错 | 核对 packages-to-scan |
| 5 | Security 拦截 | 未放行文档路径 | dev/test 放行清单（08 篇） |
| 6 | 生产能看文档 | production 未配 | production=true |
| 7 | 离线导出失败 | 文档数据异常 | 先查 /v3/api-docs |
| 8 | 调试 401 | 认证头缺失/token 无效 | Authorize 配 token；核对 header |
| 9 | 网关聚合空文档 | RewritePath 路径不匹配 | 核对路由重写（07 篇） |
| 10 | 迁移后异常 | 残留官方依赖 | dependency:tree 清理 |

## 4. 面试三范式

**价值式**：Knife4j 解决什么问题？——Swagger UI 的三大痛点：界面单调信息密度低、调试体验弱、无法离线交付。Knife4j 作为增强层解决：文档可排序可搜索可导出、在线调试带 curl 生成与全局参数、微服务聚合单一入口、生产安全三层防护。2026 双线（官方 4.x + Next 5.x）解决 Spring 升级的延续性。

**技术式**：核心机制？——增强层架构（规范层 OpenAPI 3 + 解析层 SpringDoc + 增强层 Knife4j）；注解体系（标准五件套 + 增强注解）；配置分层（springdoc 管生成、knife4j 管呈现）；安全三层（production/basic/Security）；聚合三方案（admin/网关/front）。

**生产式**：你踩过什么坑？——Boot 3 用错 starter（javax/jakarta 冲突）；生产文档忘屏蔽（production 是发布检查项）；手动加 springdoc 依赖冲突；Security 放行过宽；网关 RewritePath 配错聚合空文档；注解 example 泄露敏感信息。

**追问四连**：增强注解对 OpenAPI 数据有影响吗？production 与 enable 的关系？网关聚合与 admin 的选型？Next 迁移为什么只换坐标？

## 5. 简历呈现写法

```text
主导团队 API 文档体系落地（Knife4j + SpringDoc，Boot 3）
- 统一注解规范与分组排序，接口文档覆盖率 100%，离线文档随版本归档
- 落地生产安全三层防护（production 屏蔽 + basic 认证 + Security 放行），文档暴露风险归零
- 设计网关聚合方案，微服务文档单一入口，联调效率提升约 50%
```

要点：量化（覆盖率/效率）、点名机制（三层防护/网关聚合）、体现工程治理（规范 + 安全 + 架构）而非"集成了工具"。加分写法是附上"文档质量闭环"：注解规范 → CI 检查 → 评审走查 → 离线归档——面试官看到的是你把它当"工程体系"管理，而不是"装了个插件"。

后端方向面试的一个延伸话题：**"接口文档与接口测试如何统一"**——结合本体系的 Knife4j 调试与测试体系的接口测试，答出"OpenAPI 契约驱动"（Swagger 体系 06 篇）的完整链条（注解 → 文档 → 契约 → 测试）会让回答有高度。文档不是终点，契约驱动开发（CDD）才是接口工程的完整形态。**毕业时的自我检视**：把 10 篇的练习题全部做一遍（集成跑通、注解规范、安全三层、聚合方案、Next 评估），自测 20 题答对 15 题以上——达到这个标准，你就是团队里"接口文档体系"的负责人人选。
