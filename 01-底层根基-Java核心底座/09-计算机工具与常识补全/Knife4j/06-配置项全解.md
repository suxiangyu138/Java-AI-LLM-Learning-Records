## 1. 配置分层：springdoc.* 与 knife4j.*

Knife4j 的配置天然分两层，混用是最常见的配置错误：

```yaml
springdoc:      # 文档数据层：决定"文档里有什么"
  api-docs:
    path: /v3/api-docs        # OpenAPI 数据路径
  group-configs:              # 分组
    - group: default
      packages-to-scan: com.example.controller

knife4j:       # 增强层：决定"doc.html 怎么用"
  enable: true                # 增强开关（doc.html 前提）
  production: false           # 生产屏蔽
  basic:                      # HTTP 认证
    enable: false
```

**分层心智**：springdoc 管"文档生成"（扫描/分组/路径），knife4j 管"文档呈现与访问"（开关/认证/屏蔽）。**doc.html 404 查 knife4j.enable，接口缺失查 springdoc 扫描配置**——按层排查，问题定位快十倍。

## 2. springdoc.* 配置全解

| 配置 | 默认 | 作用 |
|------|------|------|
| springdoc.api-docs.path | /v3/api-docs | OpenAPI JSON 路径 |
| springdoc.api-docs.enabled | true | 关闭后文档完全不可用 |
| springdoc.packages-to-scan | 空 | 扫描包（全应用时可不配） |
| springdoc.paths-to-match | /** | 匹配路径 |
| springdoc.group-configs | — | 分组（group/packages-to-scan/paths-to-match） |
| springdoc.show-actuator | false | 是否暴露 actuator 端点文档 |

常用组合：**单模块**（不配扫描，全应用生效）；**多模块**（按包分组）；**限定暴露**（paths-to-match 只匹配 `/api/**`，内部端点不泄露）。**springdoc 配置变更后需要重启**（配置阶段读取，非动态）。

## 3. knife4j.* 配置全解

| 配置 | 默认 | 作用 |
|------|------|------|
| knife4j.enable | false | 增强模式开关（doc.html 生效前提） |
| knife4j.production | false | true 时 doc.html 返回 404（生产屏蔽） |
| knife4j.setting.language | zh_cn | 界面语言（zh_cn/en） |
| knife4j.setting.enable-footer | true | 页脚开关 |
| knife4j.setting.enable-open-api | true | 文档接口开关 |
| knife4j.basic.enable | false | HTTP basic 认证 |
| knife4j.basic.username/password | — | basic 凭据 |
| knife4j.basic.type | BASIC | 认证类型 |

**生产必配组合**：`knife4j.production: true`（彻底屏蔽）+ `knife4j.basic.enable: true`（若内网需要访问则加认证）——两者不冲突：production 关闭 doc.html，basic 保护仍开的场景（如预发环境）。**enable 与 production 的优先级**：production=true 时即使 enable=true 也屏蔽——生产屏蔽是最高优先级。

## 4. 多环境配置

```yaml
# application-dev.yml（开发）
knife4j:
  enable: true
  production: false

# application-test.yml（测试）
knife4j:
  enable: true
  production: false

# application-prod.yml（生产）
knife4j:
  enable: true        # 保持 true 但 production 屏蔽
  production: true
```

多环境配置的工程纪律：**开发/测试开文档、生产屏蔽**——按 Profile 分别配置，而不是代码里写死。另一种做法是 `@Profile({"dev","test"})` 条件装配配置类，但 yml 分环境更直观。**注意**：`knife4j.enable` 各环境都要 true（否则 dev 也打不开 doc.html），屏蔽靠 production 而非 enable——这是最常见的配置误区。

## 5. 编程式配置：OpenAPI Bean

部分能力只能编程式配置：

```java
@Configuration
public class OpenApiConfig {

    @Bean
    public OpenAPI customOpenAPI() {
        return new OpenAPI()
            .info(new Info()
                .title("订单平台 API")
                .version("1.0.0")
                .description("订单平台对外接口文档")
                .contact(new Contact().name("平台组").email("dev@example.com")))
            .addSecurityItem(new SecurityRequirement().addList("bearerAuth"))
            .components(new Components().addSecuritySchemes("bearerAuth",
                new SecurityScheme()
                    .name("bearerAuth")
                    .type(SecurityScheme.Type.HTTP)
                    .scheme("bearer")
                    .bearerFormat("JWT")));
    }
}
```

编程式配置典型场景：**文档全局信息**（title/version/description/contact——doc.html 顶部的展示内容）；**安全方案声明**（JWT/OAuth2 的 OpenAPI 安全定义，配合 Authorize 调试）；**全局响应头/标签**。注意：编程式配置的优先级高于 yml（OpenAPI Bean 是数据源，yml 是补充）。

## 6. 配置排查方法论

```text
配置问题的排查顺序：
① doc.html 能打开吗？
   否 → knife4j.enable 是否 true；依赖是否正确
② 接口缺失/多余？
   否 → springdoc 扫描配置（packages-to-scan/paths-to-match）
③ 文档内容不对（分组/信息）？
   否 → OpenAPI Bean 与 yml 冲突
④ 生产能访问？
   否 → production/basic 配置
⑤ 认证不生效？
   否 → basic 与 Spring Security 的叠加（08 篇）
```

**黄金规则：先数据源后呈现**——`/v3/api-docs` 有内容吗？有 → 问题在 knife4j 层；无 → 问题在 springdoc/注解层。配置排查 80% 的问题在这两层之间定位。

配置管理的两个工程建议：**配置集中化**——Knife4j 与 springdoc 的配置集中在一个 `api-doc.yml` 或配置类里，避免散落在多个 application.yml；**配置即文档**——把配置注释写清楚（每个 key 的用途与取值），新成员接入手册直接看配置注释就能理解文档体系。配置的命名已经自解释（enable/production/basic），注释的价值在于说明"为什么这么配"（如 production 为什么必须 true）。

## 7. 配置与注解的分工边界

配置与注解都能影响文档，但分工清晰：

```text
配置管"文档的结构与访问"：
├── 哪些包/路径进文档（扫描）
├── 分成几个组（分组）
├── 文档开不开、谁能看（enable/production/basic）

注解管"文档的内容"：
├── 接口叫什么、怎么用（@Operation/@Parameter）
├── 实体长什么样（@Schema）
└── 分组顺序（@ApiSort）
```

**判断标准**：一个问题能用注解解决就不用配置（注解随代码走、可审查）；涉及"扫描范围/访问控制"只能用配置。常见误用：用注解做扫描限制（应该用 springdoc 配置）、用配置写接口说明（应该用注解）——越界使用会导致"配置与注解不一致"的隐性文档漂移。团队约定里写清这条边界，文档体系的演进才不会失控。

一个配置调优实战：**生产环境只想暴露部分接口文档**（对外的 /api/public/** 开放、内部 /api/internal/** 隐藏）——用 springdoc 的 paths-to-match 限定扫描范围即可实现"部分文档化"；配合 Security 放行清单（08 篇）做到"公开接口有文档、内部接口无痕迹"。这种"选择性暴露"是 B 端 SaaS 的常见需求，配置与安全两层配合完成，比代码里写条件判断干净得多。

**配置变更的测试纪律**：任何 springdoc/knife4j 配置修改后，验证三件事——/v3/api-docs 内容符合预期（数据层）、doc.html 打开与分组正确（呈现层）、生产环境仍屏蔽（安全层）。配置是"全局性的"，一个配置错误影响所有接口的文档——把配置验证写进发布检查单，与代码测试同等对待。配置文件的 git 历史同样要审查（配置变更也可能引入安全回归），这是"配置即代码"的实践含义。配置管理最终要形成一份"文档配置速查卡"（每个 key 的用途、取值、踩坑），新成员接入文档体系时按卡配置，配置问题的咨询量能再降一半。实践中的配置模板应区分"基础模板"（enable + 分组，90% 项目够用）与"完整模板"（基础 + basic + 多环境 + 编程式），团队按项目等级选用——**配置不是越多越好，够用且可维护才是标准**。
