## 1. 离线文档导出：交付给非技术方

入口：doc.html → 文档管理 → 离线下载。四种格式各有用途：

| 格式 | 特点 | 适用 |
|------|------|------|
| Html | 界面与在线版几乎一致 | 交付最常用（可直接打开） |
| Markdown | 纯文本可进 Git/文档系统 | 团队协作、版本管理 |
| Word | 可编辑、格式规范 | 评审会议、正式合同 |
| PDF | 不可编辑、版式固定 | 验收归档、外部交付 |

工程实践：**离线文档随版本走**——每个发布版本导出一次 Markdown 进代码仓库的 docs/api/ 目录（与版本 tag 对应），或接入 CI 在发布流水线自动导出（离线文档的生成可脚本化，见 09 篇的 API 访问）。Markdown 版可通过第三方工具再转 PDF/Word，但 **Knife4j 直接导出的格式质量最高**——评审/验收场景优先直接用导出物，避免二次转换失真。

## 2. 全局参数：批量调试的钥匙

全局参数在"swagger 全局设置"中配置，作用域是整个 doc.html 的所有接口调试：

```text
支持两种类型：
├── header：Authorization、X-Trace-Id、X-Tenant-Id 等请求头
└── query：公共查询参数（如 pageSize 默认值、lang）
```

典型场景：**认证头统一注入**（全局配一个 Authorization 后所有接口调试自动携带，不用每个接口手填）；**租户/追踪 ID**（微服务场景统一传 X-Tenant-Id 与 traceId）。全局参数与 Authorize 的区别：Authorize 是认证流程（05 篇），全局参数是任意 header/query 的静态注入——两者叠加使用。

**注意**：全局参数是"调试辅助"，不是接口定义——它不会出现在 /v3/api-docs 的文档数据里，只影响 Knife4j 的调试请求。文档化公共参数仍要用 @Parameter（03 篇）。

## 3. 在线调试增强

Knife4j 调试器的能力对比原生 Swagger UI 强一截：

- **无限参数**：动态增删参数行（普通 UI 只能调试固定参数）
- **文件上传**：multipart 类型接口直接选文件调试
- **自定义请求头**：单次调试临时加 header
- **JSON/XML 示例**：请求体自动生成示例，可编辑后发送
- **响应完整信息**：状态码、响应头、响应时间、响应体分开展示
- **Curl 命令生成**：一键复制当前请求的 curl 命令（复现/交接/脚本化）
- **全局缓存调试信息**：调试参数页面刷新后保留（切换 tab 不丢）

调试增强的工程价值：**前端没写好也能验证后端**——用 Knife4j 直接调接口确认契约，前端对接时以 curl 命令为基准复现；响应时间帮助快速定位慢接口。**curl 命令是交接神器**：把 curl 贴给同事/贴进 issue，问题复现零沟通成本。

## 4. 接口排序与全局搜索

- **排序**：@ApiSort 控制分组顺序、@ApiOperationSupport(order) 控制接口顺序（03 篇）——文档顺序 = 业务使用顺序
- **全局搜索**：doc.html 顶部全局搜索框，按接口路径/摘要/标签实时过滤——接口几十上百时，搜索是效率钥匙

排序与搜索的组合使用：**排序定义"文档叙事"**（新手指引按序阅读），**搜索定义"查找路径"**（老手直接搜接口名）。两者服务不同人群，配置时都要做——只排序不搜索，大项目找接口靠翻；只搜索不排序，新人不理解业务结构。

## 5. Authorize 授权模块

内置授权模块简化带认证接口的调试：

- 支持 **JWT**：填 token 后所有调试请求自动带 `Authorization: Bearer <token>`
- 支持 **OAuth2**：配置 client 后走授权流程获取 token
- 与全局参数的区别：Authorize 是"认证凭据"语义（可触发 OAuth2 流程），全局参数是"静态头注入"

```text
使用流程：Authorize → 填 token / OAuth2 配置 → 授权
→ 后续所有接口调试自动携带认证头
```

注意边界：**Authorize 是调试辅助，不是安全机制**——它不保护接口（保护靠后端鉴权），只是帮调试者少填认证头。生产环境文档本身的安全靠 08 篇的 production/basic。

## 6. Models 树形展示

doc.html 的 Models 标签页以树形组件展示全部实体模型：

- 实体列表 → 展开字段 → 字段类型/描述/示例逐层展示
- 嵌套实体（List<OrderItem> 等）自动展开为树的分支
- 与接口页的关系：Models 是"实体总目录"，接口页的请求/响应引用具体实体

Models 的用途：**契约审查**——评审时先在 Models 页确认实体字段（有没有多余字段/缺字段），再进接口页看用法；**字段溯源**——前端对接时查"这个字段从哪来"。

## 7. 增强功能的适用边界

| 能力 | 强项 | 不要用来 |
|------|------|----------|
| 离线导出 | 交付/归档 | 替代在线文档（版本同步成本高） |
| 在线调试 | 联调/复现 | 替代 Postman 复杂流程（断言/环境管理） |
| Authorize | 调试认证 | 生产安全（无保护作用） |
| 全局参数 | 公共头注入 | 文档化参数（不影响 API 数据） |
| Curl 生成 | 交接复现 | 复杂流程脚本化（用 Postman/脚本） |

一句话边界：**Knife4j 是"接口文档 + 轻量调试"，不是全功能 API 客户端**——重流程（断言、环境、协作）交给 Postman/APIFox（见测试体系），Knife4j 的价值在"文档与调试一体"。
