## 1. 为什么必须分环境

> **背景**：dev/test/prod 环境的数据库、中间件、密钥、日志级别完全不同——一套配置跑所有环境必然出事故。
> **目的**：环境隔离：开发不碰生产数据、测试验证真实行为、生产使用最高安全标准。
> **适用范围**：任何有独立部署环境的中大型项目。
> **前提假设**：环境差异通过配置表达，代码零环境判断（`if(env=="prod")` 是反模式）。

```text
不分环境的后果（真实事故）
├── 开发连了生产数据库 → 误删生产数据
├── 测试打生产日志 → 日志里出现测试数据
├── 生产开了 debug 日志 → 性能下降 + 敏感信息泄露
├── 生产用开发密钥 → 认证失败/安全隐患
└── 本质：环境差异是「配置问题」不是「代码问题」
    → 分环境配置 = 环境风险的隔离墙
```

| 维度 | dev | test | prod |
|------|-----|------|------|
| 数据 | 模拟/脱敏 | 测试数据 | **真实数据** |
| 日志级别 | DEBUG | INFO | INFO/WARN |
| 密钥 | 测试密钥 | 测试密钥 | **真实密钥（加密）** |
| 监控 | 无 | 基础 | **全量** |
| 变更 | 随意 | 按迭代 | **审批+灰度** |

## 2. Profile 机制详解

### 2.1 基本机制

> 🎯 **Profile = 环境选择开关**：`spring.profiles.active` 指定激活的环境，Spring 加载 `application-{profile}.yml` 覆盖基础配置：

```yaml
# application.yml（基础配置——所有环境共享）
spring:
  application:
    name: order-service
  profiles:
    active: dev          # ⚠️ 默认激活 dev（开发友好）
                          # 生产必须用环境变量覆盖！
server:
  port: 8080
```

```yaml
# application-dev.yml（dev 专属覆盖）
server:
  port: 8081
spring:
  datasource:
    url: jdbc:mysql://dev-db:3306/order_dev
    username: dev_user

logging:
  level:
    root: DEBUG          # 开发开 DEBUG
```

```yaml
# application-prod.yml（prod 专属覆盖）
server:
  port: 8080
spring:
  datasource:
    url: jdbc:mysql://prod-db:3306/order
    username: prod_user
    password: ${DB_PASSWORD}    # 密码环境变量注入！

logging:
  level:
    root: INFO
```

### 2.2 激活的三种方式（优先级递增）

```bash
# 方式 1：配置文件默认（最弱，建议只写 dev）
java -jar app.jar
# → 用 application.yml 里的 spring.profiles.active

# 方式 2：环境变量（部署推荐）
SPRING_PROFILES_ACTIVE=prod java -jar app.jar

# 方式 3：命令行（最强）
java -jar app.jar --spring.profiles.active=prod

# 多环境同时激活（合并场景，如 prod + redis-cluster）
--spring.profiles.active=prod,redis-cluster
```

### 2.3 Profile 的条件控制（代码层）

```java
// 按环境控制 Bean 加载（谨慎使用——环境判断进代码是反模式，个别场景合理）
@Profile("prod")
@Service
public class ProdMetricsService implements MetricsService { }

// 配置文件中的 Profile 条件（YAML 多文档）
spring:
  config:
    activate:
      on-profile: dev
---
server:
  port: 8081
```

## 3. 分环境文件命名规范

### 3.1 命名规则

```text
分环境文件命名（Spring Boot 标准）
├── application.yml                # 基础（共享默认）
├── application-dev.yml           # dev
├── application-test.yml          # test
├── application-staging.yml       # 预发布（可选）
├── application-prod.yml          # prod
└── application-{任意}.yml        # 规则：任意合法 profile 名

⚠️ 易错点：
├── profile 名与文件名必须完全一致（大小写敏感！）
├── 文件后缀统一 .yml（.yaml 混用可能加载不到）
├── 不存在的 profile 不报错——静默使用基础配置（危险！）
└── 命名规范：dev/test/staging/prod 是团队约定，用词统一
```

### 3.2 文件内容分工

```text
基础文件（application.yml）放什么
├── ✅ 通用默认：线程池、超时、格式、开关默认值
├── ✅ 服务名、端口默认
├── ❌ 不放：任何环境的数据库地址、密码、环境差异

环境文件（application-prod.yml）放什么
├── ✅ 该环境的中间件地址
├── ✅ 该环境的日志级别
├── ✅ 该环境的资源配额
├── ⚠️ 密码：占位符 ${DB_PASSWORD}（值由外部注入）
└── ❌ 不放：明文密码/密钥
```

## 4. 环境切换方式

### 4.1 切换矩阵（2026 标准）

| 环境 | 激活方式 | 配置来源 |
|------|---------|---------|
| **本地开发** | application.yml 默认 dev | 包内 + 本地外部文件 |
| **CI 测试** | `--spring.profiles.active=test` | 包内 + CI 环境变量 |
| **容器化部署** | `SPRING_PROFILES_ACTIVE=prod` 环境变量 | 包内 + ConfigMap/Secret |
| **K8s 生产** | Deployment env 注入 | ConfigMap + Secret + Nacos |

### 4.2 生产环境切换铁律

```text
生产环境激活的铁律
├── ① 生产 profile 绝不写在 application.yml 里
│   （万一默认激活 prod + 本地跑 = 连生产库！）
├── ② 生产激活必须外部注入（环境变量/命令行）
├── ③ 生产环境永远不连开发数据库（物理隔离）
├── ④ 部署脚本显式声明：SPRING_PROFILES_ACTIVE=prod
└── ⑤ 启动日志确认激活环境（日志第一行打印 profile）
```

> ⚠️ **经典事故**：application.yml 里 `active: prod` + 开发本地启动 → 本地连了生产数据库 → 误操作生产数据。**默认 profile 永远写 dev，生产用外部注入**。

## 5. 环境隔离红线

### 5.1 隔离清单（红线级）

```text
环境隔离红线（违反 = 生产事故）
├── ① 数据库隔离：dev/test/prod 独立库，绝不共享
├── ② 中间件隔离：Redis/MQ 独立实例（prod 绝不共用 dev 的）
├── ③ 对象存储隔离：bucket 按环境分
├── ④ 密钥隔离：环境专属密钥（prod 密钥只存在于 prod 配置源）
├── ⑤ 数据隔离：dev/test 用脱敏数据（真实用户数据绝不进测试库）
└── ⑥ 域名/回调隔离：支付回调/第三方回调按环境配置不同地址
```

### 5.2 隔离的实现手段

| 手段 | 说明 |
|------|------|
| **Nacos Namespace** | 按环境物理隔离配置（dev/test/prod 独立命名空间） |
| **K8s Namespace** | 按环境隔离部署 |
| **独立账号** | 每个环境独立数据库账号（prod 账号最小权限） |
| **环境变量注入** | 环境专属值运行时注入（不落配置文件） |
| **配置审计** | 定期检查「prod 配置是否包含 dev 地址」 |

### 5.3 防止「混环境」的工程手段

```text
防混环境四道防线
├── ① 配置层：Nacos Namespace 物理隔离 + 环境变量注入
├── ② 启动层：启动日志打印激活环境 + 数据库地址（人工可查）
├── ③ 监控层：prod 告警「配置了 dev 地址」的异常模式
├── ④ 权限层：开发账号无 prod 配置的写权限
└── 终极：prod 数据库账号由 DBA 单独管理（开发无密码）
```

## 6. 本地开发环境实践

### 6.1 本地配置策略

```yaml
# application.yml（本地开发默认）
spring:
  profiles:
    active: dev

# application-dev.yml（本地开发）
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/order_dev
    username: root
    password: localpass        # 本地明文可接受（不提交生产密钥）

# ⚠️ 本地与生产的差异点
├── 本地：localhost 中间件 + DEBUG 日志 + 测试密钥
├── 生产：K8s 环境变量 + INFO 日志 + Secret
└── 中间层：用 spring.config.import 或外部文件覆盖
```

### 6.2 本地开发常用技巧

```text
本地开发配置技巧
├── ① 本地 profile 专属文件：application-local.yml
│   （比 dev 更细：本地内存数据库 H2/内嵌 Redis）
├── ② 命令行临时覆盖：--server.port=9090（不动文件）
├── ③ 环境变量文件：.env + IDE 加载（dotenv 插件）
├── ④ 依赖外部服务：Testcontainers 起本地中间件
└── ⑤ 团队统一：本地配置模板入库（application-local.example.yml）
```

## 7. 容器化多环境

### 7.1 K8s 多环境方案

```yaml
# K8s 多环境的标准做法（以 prod 为例）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: prod              # ① 环境 = K8s Namespace
spec:
  template:
    spec:
      containers:
      - name: app
        image: registry/order-service:1.2.0
        env:
        - name: SPRING_PROFILES_ACTIVE
          value: prod          # ② 环境激活
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:      # ③ 敏感信息 Secret
              name: db-secret
              key: password
        envFrom:
        - configMapRef:        # ④ 普通配置 ConfigMap
            name: order-config
```

### 7.2 容器化环境配置规范

```text
容器化多环境规范
├── ① 环境激活：SPRING_PROFILES_ACTIVE 环境变量（绝不在镜像内写死）
├── ② 普通配置：ConfigMap（按环境独立）
├── ③ 敏感配置：Secret（加密存储 + RBAC 权限）
├── ④ 镜像不变：同一镜像跑所有环境（配置全外部化）
├── ⑤ 配置变更：改 ConfigMap → 滚动重启（或动态刷新）
└── ⑥ 构建与运行分离：构建时不注入环境（环境只属于运行时）
```

## 8. 常见事故与防护

### 8.1 事故清单（真实案例模式）

| # | 事故 | 根因 | 防护 |
|---|------|------|------|
| 1 | **本地连了生产库** | application.yml 默认 prod | 默认 dev + 生产外部注入 |
| 2 | **测试数据污染生产** | dev/test 共用库 | 独立库 + 权限隔离 |
| 3 | **生产 DEBUG 日志** | 日志级别没分环境 | 分环境文件控制级别 |
| 4 | **profile 拼写错误** | `pro` 而非 `prod` | 启动日志确认 + 部署脚本校验 |
| 5 | **密码进代码库** | 明文写 yml 提交 | gitignore + 密钥扫描（gitleaks） |
| 6 | **配置中心混环境** | 所有环境共用 Nacos 命名空间 | Namespace 物理隔离 |
| 7 | **灰度连错库** | 新环境配置漏改 | 配置基线检查（diff prod 配置） |

### 8.2 事故排查流程

```text
环境配置事故排查四步
├── ① 确认激活环境：启动日志 "The following profiles are active: prod"
├── ② 确认配置来源：/actuator/env/{key} 看 source（哪个环境文件/配置源）
├── ③ 确认值：是否该环境应有的值（对比部署脚本）
├── ④ 查变更：配置最近改动（Nacos 变更历史/ConfigMap 版本）
└── 预防：启动脚本里加「环境确认」打印（环境+数据库地址+版本）
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 分环境 = 环境风险的隔离墙：数据/中间件/密钥/日志全隔离，代码零环境判断
> 2. Profile 机制：`application-{profile}.yml` 覆盖基础配置；**默认 profile 写 dev，生产必须外部注入**（防本地连生产库）
> 3. 命名铁律：profile 名与文件名完全一致（大小写敏感）；不存在的 profile 静默用基础配置（危险）
> 4. 环境隔离红线：数据库/中间件/密钥/回调地址全隔离；Nacos Namespace 物理隔离
> 5. 容器化：镜像不变 + ConfigMap 普通配置 + Secret 敏感信息 + 环境变量激活
