## 1. 外部化配置的本质

> **背景**：配置必须随部署环境变化（dev 的数据库 ≠ prod 的数据库），而代码不能变——外部化配置就是「配置与代码分离，运行时可覆盖」。
> **目的**：一套 jar 包，任意环境运行；敏感信息不进包；运维可在不重新部署的情况下调整参数。
> **适用范围**：所有 Spring Boot 服务；容器化部署（Docker/K8s）尤甚。
> **前提假设**：多个配置来源按优先级合并；**高优先级覆盖低优先级的同名 key**。
> **不适用场景**：纯本地单机工具（外部化收益低）；配置极其简单的小脚本。

```text
外部化配置的本质
├── 代码：不变（一套 jar）
├── 配置源：多个（包内/外部文件/环境变量/命令行/配置中心）
├── 规则：优先级高者覆盖同名 key（merge 不是 replace）
└── 结果：同一 jar 在 dev/test/prod 读取到不同配置
```

| 关键认知 | 说明 |
|---------|------|
| **覆盖 vs 合并** | 高优先级覆盖**同名 key**；不同 key 全部生效（合并） |
| **优先级来源** | PropertySource 列表顺序（后注册的优先） |
| **调试入口** | `/actuator/env` 看每个 key 的来源与最终值 |

## 2. 14 级优先级全景

### 2.1 完整优先级表（从高到低）

| 级 | 配置来源 | 典型场景 | 何时用 |
|:--:|---------|---------|--------|
| 1 | **命令行参数** `--key=value` | 启动时临时覆盖 | 调试/一次性的参数 |
| 2 | **JVM 系统属性** `-Dkey=value` | 启动脚本注入 | 与启动器结合 |
| 3 | **SPRING_APPLICATION_JSON** | 环境变量 JSON | 复杂配置注入 |
| 4 | **JNDI 属性** | 传统 Tomcat 外置部署 | 遗留架构 |
| 5 | **操作系统环境变量** | Docker/K8s 注入 | **容器化首选** |
| 6 | **Nacos 配置中心** | 分布式配置 | 微服务标准 |
| 7 | **外部 config/ 目录** | jar 包旁目录 | 传统部署 |
| 8 | **外部当前目录** | jar 包同目录 | 传统部署 |
| 9 | **classpath:/config/** | 包内 config 目录 | 打包定制 |
| 10 | **classpath:/application.yml** | 包内默认 | 默认值 |
| 11 | **application-{profile}.yml** | Profile 专属 | 分环境覆盖 |
| 12 | **@PropertySource** | 自定义配置文件 | 特殊加载 |
| 13 | **bootstrap.yml** | 引导配置 | 配置中心地址 |
| 14 | **代码默认值** `${key:default}` | 代码兜底 | 最后防线 |

### 2.2 分组记忆法

```text
优先级分组记忆（按「谁最灵活谁最高」）
├── 运行期临时（1-2）：命令行 > JVM 参数 —— 调试用
├── 环境注入（3-5）：SPRING_APPLICATION_JSON > 环境变量 —— 部署用
├── 远程集中（6）：Nacos —— 分布式标准
├── 文件位置（7-10）：外部的 > 包内的，config/ > 根
├── 环境专属（11）：Profile 文件 —— 分环境默认
└── 兜底（12-14）：自定义源 > bootstrap > 代码默认值
```

> 🎯 **记忆口诀**：**命令行最高，代码默认最低；外部的压包内的，环境变量压配置中心（除命令行）**。

## 3. 环境变量的宽松绑定

### 3.1 宽松绑定规则

> 🎯 **环境变量 → Spring 属性的自动映射**（松散绑定）：点变下划线、小写变大写、`-` 变 `_`：

```text
Spring 属性         环境变量
server.port    →    SERVER_PORT
server.port    →    server.port（也支持）
myapp.timeout-ms → MYAPP_TIMEOUTMS
myapp.hostList →  MYAPP_HOSTLIST（数组特殊处理，见下）

⚠️ 注意：环境变量名中不能有 "." 和 "-"（shell 限制）——
   → 所以映射规则：. → _，- → _
```

### 3.2 环境变量注入实战（Docker/K8s 首选）

```bash
# 直接启动
SERVER_PORT=8081 DB_PASSWORD=xxx java -jar app.jar

# Docker
docker run -e SERVER_PORT=8081 -e DB_PASSWORD=xxx myapp:1.0

# K8s ConfigMap（明文配置）
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  SERVER_PORT: "8081"
  MYAPP_TIMEOUTMS: "5000"
---
# K8s Deployment 注入
envFrom:
  - configMapRef:
      name: app-config

# K8s Secret（敏感信息）
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: password
```

### 3.3 环境变量的边界与陷阱

```text
环境变量注入的边界
├── ✅ 适合：端口/地址/密码/开关/单值配置
├── ❌ 不适合：复杂嵌套结构（数组/Map/多层级）——用 SPRING_APPLICATION_JSON
├── ⚠️ 数组注入：MYAPP_HOSTS_0=node1 / MYAPP_HOSTS_1=node2（下划线索引）
├── ⚠️ 布尔陷阱：环境变量 "false" 字符串 → 绑定 Boolean 需 Spring 转换
├── ⚠️ 类型陷阱：环境变量全是字符串——"0808" 绑 int 可能失败
└── ⚠️ 优先级陷阱：环境变量 > 配置中心 > 包内 yml——同名 key 环境变量赢
```

### 3.4 SPRING_APPLICATION_JSON（复杂配置注入）

```bash
# 复杂结构用 JSON 环境变量
SPRING_APPLICATION_JSON='{"server":{"port":8081},"myapp":{"timeout-ms":5000}}' java -jar app.jar

# 优先级：低于 JVM 参数、高于普通环境变量
# 适用：K8s 中注入复杂配置（不用建大量环境变量）
```

## 4. 外部配置文件（jar 包外）

### 4.1 加载位置与优先级

```text
外部配置文件加载顺序（同级内）
├── ① ./config/application.yml      ← 最高（jar 包同目录下的 config 目录）
├── ② ./application.yml             ← 其次（jar 包同目录）
├── ③ classpath:/config/application.yml  ← 包内 config
└── ④ classpath:/application.yml    ← 包内根（最低）

注意：同级目录下 .properties 优先级高于 .yml（Spring 规则）
```

### 4.2 使用场景与权衡

```text
外部配置文件场景
├── ✅ 传统部署：jar + 旁挂 config/ 目录（改配置不重打包）
├── ✅ 测试环境：外部配置覆盖包内默认
├── ❌ 容器化：环境变量/ConfigMap 更规范（外部文件进镜像麻烦）
└── 权衡：外部文件灵活但「配置散落」——生产规范优先环境变量
```

### 4.3 外部配置目录示例

```text
部署目录结构（传统方式）
/app/
├── app.jar                    # 应用
├── config/                    # 外部配置（优先级最高）
│   ├── application.yml        # 环境覆盖（数据库地址等）
│   └── application-prod.yml   # prod 专属
└── logs/                      # 日志
```

## 5. 命令行与 JVM 参数

### 5.1 命令行参数（优先级最高）

```bash
# 命令行参数覆盖一切（含环境变量）
java -jar app.jar --server.port=8081 --myapp.timeout-ms=5000

# 数组/复杂参数
java -jar app.jar --myapp.hosts[0]=node1 --myapp.hosts[1]=node2

# Spring 特定参数
java -jar app.jar --spring.profiles.active=prod
```

### 5.2 JVM 系统属性

```bash
# -D 参数（优先级仅次于命令行）
java -Dserver.port=8081 -jar app.jar

# 区别：
# --key=value → 命令行参数（优先级最高）
# -Dkey=value → JVM 系统属性（第二）
# 两者都传 → 命令行赢
```

### 5.3 使用边界

```text
命令行/JVM 参数的权衡
├── ✅ 适合：启动脚本中的临时调整、CI 注入、调试
├── ❌ 不适合：长期配置（写在启动脚本里的配置难审计）
├── 规范：生产环境用环境变量（可审计）+ 配置中心（可管理）
│   命令行参数只用于「临时」与「启动器默认」
└── 安全：不要在命令行传密码（ps 可见！）——用环境变量/文件注入
```

> ⚠️ **安全提示**：`ps aux` 能看到进程命令行——**密码/密钥绝不传命令行参数**（`--password=xxx` 是安全反模式），用环境变量或密钥文件。

## 6. 合并机制：覆盖不是替换

### 6.1 核心规则

> 🎯 **配置合并规则**：多个配置源按优先级**合并（merge）**——同名 key 高优先级覆盖，不同 key 全部保留：

```yaml
# 包内 application.yml（低优先级）
server:
  port: 8080
myapp:
  timeout-ms: 3000
  enabled: true

# Nacos 配置中心（高优先级）
server:
  port: 9090                    # 覆盖 → 8080 → 9090
myapp:
  timeout-ms: 5000              # 覆盖 → 3000 → 5000
  # enabled 未配置 → 保留包内 true

# 最终生效：
# server.port=9090, myapp.timeout-ms=5000, myapp.enabled=true
```

### 6.2 合并的边界情况

```text
合并机制的边界
├── ⚠️ Map/List 类型：整体替换还是合并？
│   ├── Map：同名 key 深度合并（Spring 默认）
│   └── List：整体替换（不做元素级合并！）
├── ⚠️ 部分覆盖的错觉：高优先级只写了部分 key——
│   其余 key 保留低优先级的值（这是特性不是 bug）
└── ⚠️ 配置中心删除 key：Nacos 删掉 key 后
    → 回退到低优先级源的值（本地兜底生效！）
```

## 7. bootstrap.yml 的特殊地位

### 7.1 作用与时机

> **背景**：bootstrap.yml 在 Spring Boot 应用启动的**最早期**加载（引导阶段），用于在 application.yml 之前初始化配置中心连接。
> **目的**：配置中心的地址、命名空间等「引导配置」必须在业务配置加载前就绪。
> **优先级**：加载最早但优先级**最低**（任何其他源都可覆盖）。

```yaml
# bootstrap.yml —— 只放引导配置（配置中心地址等）
spring:
  application:
    name: order-service
  cloud:
    nacos:
      config:
        server-addr: 192.168.1.200:8848
        namespace: prod
        group: DEFAULT_GROUP
        file-extension: yaml
```

### 7.2 Spring Boot 2.4+/3.x 的变化（重要）

```text
bootstrap.yml 的版本差异
├── Spring Boot 2.4 之前：bootstrap.yml 默认生效
├── Spring Boot 2.4+：默认禁用 bootstrap 机制！
│   ├── 恢复方式 1：引入 spring-cloud-starter-bootstrap 依赖
│   └── 恢复方式 2：用 spring.config.import 在 application.yml 导入
├── Spring Boot 3.x：纯 Spring Boot 不加载 bootstrap.yml
│   （仅引入 Spring Cloud 2023+ 依赖才保留）
└── 2026 推荐：用 spring.config.import 替代 bootstrap.yml
```

```yaml
# Spring Boot 3.x 推荐：spring.config.import 导入配置中心
spring:
  config:
    import: nacos:order-service.yaml  # 显式导入
  cloud:
    nacos:
      config:
        server-addr: 192.168.1.200:8848
```

## 8. 分层配置实践（推荐架构）

### 8.1 配置分层模型（2026 企业标准）

```text
配置分层（从低到高）
┌────────────────────────────────────────────────┐
│ 第 4 层：运行期注入（最高）                       │
│   命令行参数 / JVM 参数 / 环境变量 / K8s Secret   │
│   → 放：密码、密钥、端口、部署专属参数            │
├────────────────────────────────────────────────┤
│ 第 3 层：配置中心（Nacos/Apollo）                │
│   → 放：业务开关、限流阈值、日志级别（动态刷新）  │
├────────────────────────────────────────────────┤
│ 第 2 层：外部配置文件（jar 包旁 config/）        │
│   → 放：测试/本地环境的中间件地址                │
├────────────────────────────────────────────────┤
│ 第 1 层：包内 application.yml（最低）            │
│   → 放：通用固定配置（线程池/超时/格式/默认开关）  │
└────────────────────────────────────────────────┘
```

### 8.2 每层放什么（内容规范）

| 层 | 放什么 | 不放什么 |
|----|--------|---------|
| 包内 yml | 通用默认值、日志格式、线程池、开关默认 | ❌ 密码、数据库地址、环境差异 |
| 外部文件 | 本地/测试中间件地址 | ❌ 生产敏感信息 |
| 配置中心 | 业务开关、阈值、动态参数 | ❌ 密码（如需则加密） |
| 环境变量/Secret | 密码、密钥、AK、生产专属 | ❌ 复杂结构（用 JSON/配置中心） |

### 8.3 分层的好处与权衡

```text
分层配置的优势
├── ① 安全：敏感信息不进包、不进代码库
├── ② 灵活：改开关无需重新部署（配置中心）
├── ③ 兜底：配置中心挂了本地 yml 顶上（降级）
├── ④ 审计：环境变量/Secret 可审计

权衡与代价
├── ① 复杂度上升：多来源 = 多排查点（需 actuator 辅助）
├── ② 团队纪律要求高：每层放什么必须有规范
└── ③ 简单项目别过度：单机小应用用包内 + 环境变量足够
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 14 级优先级：命令行 > JVM 参数 > 环境变量 > Nacos > 外部文件 > 包内 > Profile > 代码默认
> 2. 覆盖是「合并」不是「替换」：同名 key 高者赢，不同 key 全保留；List 整体替换、Map 深度合并
> 3. 环境变量宽松绑定（`server.port` ↔ `SERVER_PORT`）是容器化首选注入方式；复杂结构用 SPRING_APPLICATION_JSON
> 4. 密码绝不传命令行（ps 可见）；bootstrap.yml 在 Spring Boot 2.4+ 默认禁用，3.x 用 spring.config.import
> 5. 分层配置：包内放通用默认、配置中心放动态开关、环境变量放敏感信息——每层职责清晰
