## 1. 配置安全的风险全景

> **背景**：配置文件的敏感性常被低估——密码/密钥/token 一旦进入代码库或日志，等于把大门钥匙交给攻击者。
> **目的**：敏感信息「不进代码库、不进日志、不落明文」。
> **适用范围**：所有 Java 服务（任何有数据库/第三方 API 的项目）。
> **前提假设**：默认不信任——所有配置文件都可能被泄露（仓库克隆/日志导出/镜像下载）。

```text
敏感配置泄露的后果（真实事件）
├── 数据库密码泄露 → 拖库/删库（最高危）
├── 云 AK/SK 泄露 → 云资源被滥用（账单爆炸）
├── 支付密钥泄露 → 资金损失
├── API token 泄露 → 第三方服务被盗用
└── 本质：**配置泄露 = 系统边界的失守**——攻击者拿到合法凭据

泄露途径 TOP 5
├── ① 代码库提交（.env/yml 进 Git——最高频！）
├── ② 日志打印配置值（启动时打印全部配置）
├── ③ Docker 镜像包含配置（构建时注入）
├── ④ 配置文件被下载（错误配置的静态目录）
└── ⑤ 命令行参数（ps 可见）
```

## 2. 敏感配置管理四方案

### 2.1 方案总览（按安全强度排序）

| 方案 | 安全强度 | 复杂度 | 适用 |
|------|:---:|:---:|------|
| **环境变量注入** | ⭐⭐⭐ | 低 | 容器化部署（基础） |
| **K8s Secret** | ⭐⭐⭐⭐ | 中 | K8s 部署（标准） |
| **密钥管理服务（KMS/Vault）** | ⭐⭐⭐⭐⭐ | 高 | 强安全要求/大厂 |
| **配置加密（静态加密）** | ⭐⭐⭐⭐ | 中 | 配置中心场景 |

### 2.2 决策树

```text
敏感配置管理选型
 │
 ├─ 单体/简单部署？
 │   ├─ 环境变量注入（够用）
 │   └─ 或 外部配置文件（仅测试环境）
 │
 ├─ K8s 部署？
 │   ├─ Secret（标准）→ 可升级 KMS 加密
 │   └─ External Secrets Operator（对接 Vault/AWS）
 │
 ├─ 强合规/大厂？
 │   └─ Vault / 云 KMS（动态密钥/自动轮换）
 │
 └─ 配置中心（Nacos）？
     └─ 加密存储（AES）+ 解密注入
```

## 3. 环境变量与 Secret 注入

### 3.1 环境变量注入（基础方案）

```yaml
# application.yml 中只留占位符（无默认值——缺失即失败！）
spring:
  datasource:
    password: ${DB_PASSWORD}          # ❌ 不能有默认值（防静默用错）
  redis:
    password: ${REDIS_PASSWORD}
myapp:
  api-key: ${PAYMENT_API_KEY}
```

```bash
# 部署注入（docker run）
docker run -e DB_PASSWORD=xxx -e REDIS_PASSWORD=yyy myapp:1.0

# 直接运行
DB_PASSWORD=xxx java -jar app.jar
```

### 3.2 K8s Secret（标准方案）

```yaml
# ① 创建 Secret（base64 编码，非加密但独立存储）
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  password: eHh4eA==            # base64（echo -n "xxx" | base64）
---
# ② 注入（Deployment）
apiVersion: apps/v1
kind: Deployment
spec:
  template:
    spec:
      containers:
      - name: app
        env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: password
```

### 3.3 Secret 的进阶（2026 标准）

```text
K8s Secret 的进阶实践
├── ① Secret 本身 base64 非加密——用 KMS 加密（云厂商 K8s 支持）
├── ② External Secrets Operator：Secret 由 Vault/AWS 动态生成
├── ③ 权限控制：RBAC 限制 Secret 读取
├── ④ 轮换策略：定期轮换（External Secrets 自动）
└── ⑤ 审计：谁读了 Secret（审计日志）
```

> ⚠️ **Secret 的边界**：K8s Secret 不是「安全系统」而是「隔离系统」——真正加密用 KMS/Vault，Secret 负责权限与隔离。

## 4. 配置加密方案

### 4.1 场景：配置中心里的敏感值

> **背景**：Nacos/Apollo 上的配置含密码时，明文存储 → 控制台可看、导出可读。
> **方案**：敏感值加密存储（AES），应用启动时解密。

```yaml
# Nacos 上的配置（加密存储）
spring:
  datasource:
    password: ENC(3F9aKd8sXpQ2...加密后的密文)
```

```java
// 解密器（Jasypt 或自定义）
@Configuration
public class CryptoConfig {
    @Bean
    public StringEncryptor stringEncryptor() {
        // 密钥从环境变量注入（解密密钥绝不落文件！）
        String secretKey = System.getenv("CONFIG_ENCRYPT_KEY");
        return new AesStringEncryptor(secretKey);
    }
}
```

### 4.2 加密方案的权衡

| 维度 | 明文 + 环境变量 | 配置加密（ENC） |
|------|:---:|:---:|
| 配置中心可读性 | 明文（控制台可见） | 密文（控制台不可读）✅ |
| 泄露后风险 | 直接可用 | 需密钥（有缓冲）✅ |
| 复杂度 | 低 | 中（密钥管理） |
| 密钥存放 | 环境变量 | 环境变量/KMS |
| 动态修改 | 直接改 | 需加密工具再改 |

> 🎯 **结论**：**配置中心的敏感值一律加密存储（ENC）+ 解密密钥走 KMS/环境变量**——双保险：配置泄露 + 密钥泄露缺一不可才能解密。

### 4.3 加密工具链

```text
常用加密方案
├── Jasypt（Java 生态最常用）
│   ├── 依赖：jasypt-spring-boot-starter
│   └── 加密：java -cp jasypt.jar org.jasypt.intf.cli.JasyptPBEStringEncryptionCLI
├── 云 KMS（阿里云 KMS/腾讯云 KMS）
│   ├── 密钥托管在云（更安全）
│   └── SDK 解密（网络调用）
└── Vault（HashiCorp）
    ├── 动态密钥（数据库密码按需生成）
    └── 应用集成：spring-cloud-vault
```

## 5. 日志与监控脱敏

### 5.1 日志打印配置的风险

```text
风险场景
├── ① 启动日志打印全部配置（含密码）——最常见！
├── ② 异常堆栈里带 SQL（含连接串/账号）
├── ③ 业务日志拼接敏感字段（手机号/身份证）
└── ④ 调试日志输出 token/密钥
```

### 5.2 脱敏方案

```java
// 方案 1：启动日志不打印敏感配置（配置源打印排除）
// 日志配置：只打印非敏感 key
log.info("启动完成, port={}, profile={}", port, profile);
// ❌ log.info("配置: {}", properties);   // toString 可能含密码！

// 方案 2：统一脱敏工具（日志过滤器）
public class SensitiveDataMasker {
    private static final Pattern[] PATTERNS = {
        Pattern.compile("(password\\s*[=:]\\s*)([^\\s,;]+)"),
        Pattern.compile("(token\\s*[=:]\\s*)([^\\s,;]+)"),
    };
    public static String mask(String log) {
        for (Pattern p : PATTERNS) {
            log = p.matcher(log).replaceAll("$1***");
        }
        return log;
    }
}

// 方案 3：logback 过滤器（全局生效）
// 配置 LogstashEncoder + 脱敏字段配置
```

### 5.3 监控与指标脱敏

```text
监控脱敏要点
├── ① 指标标签：不携带 token/密码等敏感标签
├── ② 追踪链路：trace 中脱敏（手机号打码）
├── ③ 告警消息：异常信息脱敏后再发
└── ④ Nacos 审计：配置导出/查看权限控制
```

## 6. 密钥泄露检测

### 6.1 检测工具链（2026 标准）

```text
密钥泄露检测三件套
├── ① 提交前：IDE 插件 + pre-commit hook（gitleaks）
├── ② CI 中：gitleaks scan（每个 PR 自动扫）
├── ③ 定期：历史仓库扫描（gitleaks 全量）
└── ④ 在线：GitHub Secret Scanning（官方自动检测）

安装与使用：
  # gitleaks（Go 编写，快速）
  gitleaks detect --source . --report-format json
  gitleaks detect --log-opts="--all"       # 全历史扫描
```

### 6.2 检测规则示例

```yaml
# gitleaks 自定义规则（.gitleaks.toml）
[[rules]]
id = "aws-access-key"
description = "AWS Access Key"
regex = '''AKIA[0-9A-Z]{16}'''

[[rules]]
id = "jdbc-password"
description = "JDBC URL with password"
regex = '''jdbc:[a-z]+://[^"']*password=[^"']+'''
```

### 6.3 防止误提交的工程手段

```text
防误提交五道防线
├── ① .gitignore：.env*、*.pem、*.key、application-local.yml
├── ② pre-commit hook：gitleaks pre-commit（本地拦截）
├── ③ CI 门禁：gitleaks scan 失败 = 构建失败
├── ④ 敏感文件模板：application.example.yml（无真实值，可提交）
├── ⑤ 配置分离：真实配置永不入库（.gitignore + 外部注入）
```

## 7. 泄露事故响应

### 7.1 响应流程（SOP）

```text
密钥泄露事故响应六步
├── ① 确认泄露：git 历史/日志/公网扫描确认泄露范围
├── ② 立即轮换：**第一时间吊销/轮换密钥**（不是先删代码！）
├── ③ 清理历史：git filter-repo 清除历史中的密钥
│   git filter-repo --replace-text <(echo "xxx==>***")
├── ④ 通知相关方：云厂商（AK 泄露）/第三方（API key）
├── ⑤ 排查影响：检查异常访问日志（泄露期间的行为）
└── ⑥ 复盘预防：规则入库（gitleaks 规则）+ 流程改进
```

> ⚠️ **铁律**：**先轮换密钥，再清理历史**——删除提交不撤销泄露，轮换才是止血；git 历史中的密钥即使删除也视为已泄露（公网爬虫可能已索引）。

### 7.2 轮换机制的工程化

```text
密钥轮换设计（生产必备）
├── ① 可轮换：密钥集中管理（环境变量/Secret/KMS）——改一处全部生效
├── ② 双密钥过渡：新旧密钥并存窗口期（平滑轮换）
├── ③ 轮换演练：定期演练（季度）确认流程可用
└── ④ 动态密钥：Vault 按需生成（轮换自动化）
```

## 8. 安全配置清单

```text
配置安全总检查（上线前过一遍）
[ ] 代码库无敏感信息？（gitleaks 扫描通过）
[ ] .gitignore 覆盖 .env*/*.pem/*.key/application-{env}.yml？
[ ] 配置文件只有占位符（${DB_PASSWORD}），无默认密码？
[ ] 启动日志不打印敏感配置？

[ ] K8s Secret 有 RBAC 权限控制？

[ ] 命令行不传密码（ps 可见检查）？
[ ] Docker 镜像内无明文配置（构建时不注入环境）？
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 配置泄露 = 系统边界的失守——泄露途径 TOP1 是代码库提交（.env/yml 进 Git）
> 2. 四方案按需选：环境变量（基础）→ K8s Secret（标准）→ KMS/Vault（强安全）→ 配置加密（配置中心）
> 3. 配置中心敏感值加密存储（ENC）+ 解密密钥走 KMS——双保险设计
> 4. 日志脱敏是「隐性安全」：启动日志不打印配置、异常堆栈脱敏、监控标签无敏感
> 5. 泄露响应铁律：**先轮换再清理**；gitleaks 三道防线（pre-commit/CI/全量扫描）防误提交
