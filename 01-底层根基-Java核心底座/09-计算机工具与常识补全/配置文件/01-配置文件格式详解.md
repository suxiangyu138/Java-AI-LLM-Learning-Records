## 1. 五种格式全景对比

| 维度 | properties | YAML | TOML | JSON | INI |
|------|:---:|:---:|:---:|:---:|:---:|
| **层级支持** | ❌ 扁平 | ✅ 缩进 | ✅ 表格 | ✅ 嵌套 | ✅ Section |
| **注释支持** | ✅ `#` | ✅ `#` | ✅ `#` | ❌ | ✅ `;`/`#` |
| **类型系统** | 全字符串 | 弱（自动推断） | ✅ 完善 | ✅ 基础 | 全字符串 |
| **可读性** | 差（扁平冗长） | ⭐ 最佳 | 好 | 中 | 中 |
| **解析陷阱** | 转义/编码 | 类型推断/缩进 | 少 | 无注释/尾逗号 | 少 |
| **Java 生态** | Spring 传统 | **Spring Boot 主流** | 构建工具 | 工具配置 | 少 |
| **2026 地位** | 遗留兼容 | **服务配置标准** | 构建配置标准 | 数据交换 | 遗产 |

> 🎯 **结论先行**：**服务配置选 YAML、构建配置选 TOML、Java 遗留系统保留 properties、程序间数据交换选 JSON、INI 仅维护旧系统**——各归其位，不要混用。

## 2. properties：Java 的传统

### 2.1 背景与定位

> **背景**：properties 是 Java 自 JDK 1.0 就有的原生配置格式（`java.util.Properties` 直接读取），Spring 早期配置的事实标准。
> **目的**：扁平 key=value 简单配置。
> **适用范围**：简单配置、遗留系统、Java 标准库生态。
> **不适用场景**：复杂嵌套结构、需要类型区分的配置、大配置（扁平结构难读）。

### 2.2 语法规范

```properties
# application.properties 语法
# 注释：# 开头

# 基本键值（= 或 : 分隔）
server.port=8080
app.name=订单系统

# 中文字符（注意编码！）
app.title=用户中心

# 转义规则（\ 是转义符）
message=hello\ world          # \ 空格 = 空格（properties 特殊）
path=D:\\data\\logs           # \\ 表示一个 \

# 多行（续行符 \）
description=这是第一行\
          这是第二行

# 列表（逗号分隔字符串，需代码解析）
server.hosts=192.168.1.1,192.168.1.2
```

### 2.3 关键陷阱

| # | 陷阱 | 表现 | 解法 |
|---|------|------|------|
| 1 | **编码问题** | 中文乱码 | 文件存 UTF-8，`Properties.load(reader)` 用 Reader 读取 |
| 2 | **\ 转义** | `C:\data` 变 `C:data` | 双写 `\\` 或改用 `/` |
| 3 | **无类型** | 全部是字符串 | 代码侧转换（`Integer.parseInt`） |
| 4 | **扁平冗长** | 嵌套配置超长 | 改用 YAML |
| 5 | **ISO-8859-1 默认** | `load(InputStream)` 默认 Latin-1 | 用 `load(Reader)` 或 `loadFromXML` |

```java
// 正确读取（避免编码陷阱）
Properties props = new Properties();
try (Reader reader = Files.newBufferedReader(
        Paths.get("app.properties"), StandardCharsets.UTF_8)) {
    props.load(reader);                     // Reader 方式：UTF-8
}
// ❌ props.load(new FileInputStream("app.properties")); // InputStream 默认 Latin-1！
```

### 2.4 优势与劣势（权衡）

| 优势 | 劣势 |
|------|------|
| Java 原生支持（零依赖） | 无层级（嵌套配置靠前缀硬拼） |
| 简单直接 | 无类型 |
| Spring 全版本兼容 | 中文编码陷阱 |
| | 大配置可读性差 |

## 3. YAML：2026 服务配置主流

### 3.1 背景与定位

> **背景**：YAML 1.2（2009 定稿）因「面向人的数据序列化」设计理念，被 Spring Boot/K8s/Docker Compose 选中成为服务配置事实标准。
> **目的**：人类可读的层级配置。
> **适用范围**：Spring Boot、K8s、Docker Compose、CI（GitHub Actions）、中间件配置。
> **不适用场景**：程序间高吞吐数据交换（应 JSON/二进制）、需要精确类型区分的大配置。

### 3.2 语法规范

```yaml
# application.yml 语法
server:
  port: 8080                # 整数
  servlet:
    context-path: /api      # 字符串

app:
  name: 订单系统              # 中文无需引号
  debug: false              # 布尔
  ratio: 0.85               # 浮点
  description: |
    多行文本
    第二行                  # | 保留换行
  single: >-
    折叠文本
    单行                    # >- 折叠为单行
  list:
    - item1                # 列表
    - item2
  map:
    key1: value1            # 嵌套映射
    key2: value2
  env: ${DB_HOST:localhost}  # 占位符（Spring 支持）
```

### 3.3 四大陷阱（每个都可能引发事故）

```yaml
# ⚠️ 陷阱 1：类型推断（最危险）
version: 1.0              # → 被解析为浮点数 1.0！代码拿 String 得到 "1.0"
version: "1.0"            # ✅ 加引号保字符串
port: 0808                # → 八进制？或 808？不同解析器不同！
port: "0808"              # ✅ 引号保原样
no: false                 # → 字符串 "no" 被解析为布尔 false！
no: "no"                  # ✅ 引号

# ⚠️ 陷阱 2：缩进错误
server:
    port: 8080            # 4 空格
  port: 8081              # 2 空格 → 解析失败（同一层级不同缩进）
# 规则：同级必须同缩进；严禁 Tab（YAML 不允许 Tab 缩进！）

# ⚠️ 陷阱 3：字符串被折叠/转义
msg: "含\"引号\"的字符串"    # 双引号内转义
msg: '含"引号"的字符串'      # 单引号内不转义（推荐）

# ⚠️ 陷阱 4：多文档与锚点（看不懂的写法）
---                       # 多文档分隔符（误写导致只读第一段）
defaults: &defaults        # 锚点定义
  timeout: 30
service: *defaults         # 别名引用（拷贝）
```

### 3.4 校验工具（CI 必加）

```bash
# YAML 校验（配置事故的第一道防线）
python -c "import yaml,sys; yaml.safe_load(open('application.yml'))"  # 语法校验
yamllint application.yml          # 规范检查（缩进/重复键/行宽）
# CI 中：校验失败 = 构建失败（防止带病配置上线）
```

### 3.5 优势与劣势（权衡）

| 优势 | 劣势 |
|------|------|
| 层级清晰（缩进即结构） | 类型推断陷阱（引号纪律） |
| 支持注释（配置可解释） | Tab/缩进严格（新人易错） |
| 生态主流（Spring/K8s/CI） | 不适合程序间交换（解析慢） |
| 锚点/多文档（高级复用） | 大文件性能差 |

## 4. TOML：构建配置新锐

### 4.1 背景与定位

> **背景**：TOML（Tom's Obvious Minimal Language，2013）为「消除配置歧义」而生——明确的类型、无缩进依赖、无类型推断陷阱。
> **目的**：项目构建配置与工具配置。
> **适用范围**：Cargo.toml、pyproject.toml、部分现代工具。
> **不适用场景**：Spring Boot（生态未接纳）、需要注释丰富的服务配置（YAML 更合适）。

### 4.2 语法规范

```toml
# Cargo.toml 风格
[package]                    # 表格（类似 Section）
name = "my-app"              # 字符串（必须引号）
version = "0.1.0"            # 字符串（版本号按字符串处理）
edition = "2021"

[dependencies]               # 子表格
serde = "1.0"                # 字符串版本
tokio = { version = "1", features = ["full"] }  # 内联表

[server]
host = "localhost"
port = 8080                  # 整数（类型明确！）
debug = false                # 布尔（类型明确！）

[server.tls]                 # 嵌套表格
enabled = true
cert = "/etc/tls/cert.pem"

[[servers]]                  # 数组表（对象数组）
name = "node1"
[[servers]]
name = "node2"
```

### 4.3 与 YAML 的关键差异（为什么 TOML 无类型陷阱）

```text
TOML vs YAML 的类型安全性
├── YAML：version: 1.0 → 自动推断为浮点（歧义）
├── TOML：version = "1.0" → 引号就是字符串（无歧义）
├── YAML：缩进决定层级（Tab/空格错误 → 静默错层）
├── TOML：表格名决定层级（[a.b] 明确，无缩进依赖）
└── 结论：TOML 牺牲了一点简洁，换来了确定性
```

### 4.4 优势与劣势（权衡）

| 优势 | 劣势 |
|------|------|
| 类型明确（无推断陷阱） | 层级表达不如 YAML 直观 |
| 无缩进依赖（少一类错误） | 生态集中在构建工具 |
| 规范简单（学习成本低） | 表达复杂嵌套笨拙 |

## 5. JSON：程序化配置

### 5.1 背景与定位

> **背景**：JSON 是程序间数据交换的事实标准，也用于需要「程序安全解析」的配置场景。
> **目的**：程序化配置、工具配置、无注释要求的配置。
> **适用范围**：.editorconfig 之外的现代工具（tsconfig.json/package.json）、API 配置。
> **不适用场景**：需要注释的团队配置（JSON 无注释）、人类频繁编辑的配置。

### 5.2 关键限制与替代

```json
{
  "server": {
    "port": 8080,
    "host": "localhost"
  },
  "features": ["cache", "rate-limit"]
}
```

```text
JSON 作为配置的三大限制
├── ① 无注释：配置无法解释「为什么这个值是 30」
│   → 替代：JSONC（带注释的 JSON）/ JSON5（宽松版）
├── ② 尾逗号非法：手改易错
├── ③ 严格引号：单引号非法（手写痛苦）
└── 结论：程序生成/消费用 JSON；人类手写配置优先 YAML
```

## 6. INI：Windows 遗产

### 6.1 定位与现状

> **背景**：INI 源于 1980 年代 Windows 3.x 系统配置。
> **目的**：Section + key=value 的简单分组配置。
> **适用范围**：Windows 系统配置、旧工具。
> **不适用场景**：新项目（层级浅、无类型、生态弱）。

```ini
; config.ini（分号注释）
[database]
host=localhost
port=3306
name=mydb

[log]
level=info
path=./logs/app.log
```

## 7. 格式选型决策与权衡

### 7.1 选型决策树

```text
配置文件格式选择
 │
 ├─ Java 服务配置？
 │   ├─ Spring Boot → YAML（2026 主流）
 │   └─ 遗留项目   → properties（保持兼容）
 │
 ├─ 构建工具配置？
 │   ├─ Rust/Python → TOML（Cargo/pyproject 标准）
 │   └─ Node.js     → JSON（package.json 标准）
 │
 ├─ 容器/基础设施？
 │   └─ YAML（K8s/Docker Compose 标准）
 │
 ├─ 程序间交换？
 │   └─ JSON（或二进制 Protobuf）
 │
 └─ 旧系统维护？
     └─ INI/properties（原样保持）
```

### 7.2 权衡要点（选型必读）

| 决策点 | 权衡 | 建议 |
|--------|------|------|
| YAML vs properties | YAML 层级清晰但类型陷阱；properties 简单但扁平 | Spring Boot 新项目统一 YAML |
| YAML vs TOML | YAML 生态大但缩进严格；TOML 类型安全但生态窄 | 服务配置 YAML、构建配置 TOML |
| 注释需求 | JSON 无注释 → 配置不可解释 | 人类配置选 YAML/TOML |
| 程序生成配置 | YAML 序列化慢；JSON 成熟 | 程序生成选 JSON |
| 团队新人成本 | YAML 缩进错误高频 | CI 加 yamllint 强制校验 |

### 7.3 企业规范建议（避免混用事故）

```text
团队配置格式规范（2026 推荐）
├── 统一 YAML：Spring Boot 服务配置只用 application.yml（删除 properties 防冲突）
├── 同层级下 properties 优先级高于 yml（Spring 规则）——
│   同时存在时 properties 生效，极易踩坑 → 统一只留一种
├── 工具配置跟随工具生态（package.json/tsconfig.json 不强行改）
└── CI 校验：yamllint + 配置格式校验脚本入门禁
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 五格式定位：YAML（服务配置）/TOML（构建配置）/properties（遗留）/JSON（程序交换）/INI（遗产）
> 2. YAML 四大陷阱：类型推断（`1.0`→浮点）、缩进（禁 Tab）、引号纪律、多文档——CI 必加 yamllint
> 3. properties 三大坑：编码（`load(Reader)` 用 UTF-8）、`\` 转义、无类型
> 4. TOML 的价值在类型确定性（无推断歧义）——构建配置场景胜过 YAML
> 5. 团队规范：统一 YAML 防「properties 优先级高于 yml」的同名冲突事故
