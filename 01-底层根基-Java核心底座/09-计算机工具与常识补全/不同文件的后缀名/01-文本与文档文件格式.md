## 1. 纯文本类

| 后缀 | 全称 | 编码 | 打开方式 | 说明 |
|:----:|------|------|---------|------|
| **.txt** | Text File | UTF-8/GBK/ANSI | 任意文本编辑器 | 纯文本，无格式 |
| **.log** | Log File | UTF-8/ASCII | 文本编辑器 | 程序运行日志 |
| **.md** | Markdown | UTF-8 | VS Code/Typora/Obsidian | 轻量标记语言 |
| **.csv** | Comma-Separated Values | UTF-8 | Excel/文本编辑器 | 表格数据，逗号分隔 |
| **.tsv** | Tab-Separated Values | UTF-8 | Excel/文本编辑器 | 表格数据，Tab 分隔 |
| **.sql** | SQL Script | UTF-8 | DataGrip/Navicat | SQL 脚本（建表/查询） |
| **.sh** | Shell Script | UTF-8 | bash/zsh | Linux/macOS 脚本 |
| **.bat** | Batch File | ASCII/GBK | cmd.exe | Windows 批处理 |
| **.ps1** | PowerShell Script | UTF-8 | PowerShell | Windows 自动化脚本 |

> 💡 **纯文本的判断标准**：能用任何文本编辑器打开且不出现乱码——本质是「字节流可被字符集解码」。`file` 命令可确认：`file README.md` → `Unicode text, UTF-8 text`。

## 2. 编码原理深入：UTF-8 / GBK / BOM

### 2.1 编码的本质

> 🎯 **编码 = 字符 ↔ 字节的映射规则**。同一个「中」字，不同编码的字节完全不同——解码错误就出现乱码。

```text
「中」字在不同编码中的字节
├── UTF-8：E4 B8 AD（3 字节，国际标准）
├── GBK：D6 D0（2 字节，中文 Windows 默认）
├── UTF-16：4E 2D（2 字节，Java char 内部表示）
└── 结论：文件本身不含「编码声明」，解码错了就乱码
```

### 2.2 编码选择决策

| 编码 | 特点 | 何时用 |
|------|------|--------|
| **UTF-8** | 国际通用、ASCII 兼容、Web 标准 | **默认首选**（2026 事实标准） |
| **UTF-8 BOM** | 开头带 `EF BB BF` 三字节标记 | ⚠️ Windows 记事本默认——程序读取会多 3 字节 |
| **GBK/GB2312** | 中文双字节 | 遗留系统/中文 Windows 老文件 |
| **UTF-16** | 固定双字节 | Java 内部、Windows 系统文件 |
| **ASCII** | 7 位 128 字符 | 纯英文内容 |

### 2.3 BOM 陷阱实战

```bash
# BOM 陷阱：记事本保存的 UTF-8 文件带 BOM（EF BB BF）
$ hexdump -C file.txt | head -1
00000000  ef bb bf 48 65 6c 6c 6f  ← EF BB BF 就是 BOM！

# Java/Node.js 读取会得到 ﻿Hello（首字符异常）
# Python 读取报错：'utf-8' codec can't decode byte 0xef in position 0

# 处理方案
dos2unix file.txt                        # 一并转换行符
sed -i '1s/^\xEF\xBB\xBF//' file.txt     # 去掉 BOM
# 编辑器：VS Code 右下角 UTF-8 → 保存为 "UTF-8"（无 BOM）
```

> ⚠️ **BOM 三字节的连锁反应**：JSON 解析报错、YAML 首键名带 ﻿、Shell 脚本首行 `#!/bin/bash` 前有 BOM → `command not found`。

## 3. 换行符：跨平台第一坑

### 3.1 三种换行符

```text
换行符差异（肉眼看不见，工具看得见）
├── Windows：  \r\n（CRLF，2 字节）
├── Linux/macOS： \n（LF，1 字节）
└── 旧 Mac：  \r（CR，已淘汰）

→ hexdump 查看：
  $ hexdump -C file.txt
  41 42 0d 0a 43 44  ← 0d 0a = CRLF（Windows 文件）
```

### 3.2 换行符引发的经典事故

```text
⚠️ 事故一：.sh 脚本在 Windows 编辑后上传 Linux
   → 每行末尾带 \r → 执行报错 "command not found"（第一行）
   → 修复：dos2unix script.sh

⚠️ 事故二：Git 仓库换行符混乱
   → 同一文件在 Windows 和 Linux 上 diff 全是差异
   → 修复：.gitattributes 统一规则
     *.sh   text eol=lf
     *.bat  text eol=crlf
     *.md   text eol=lf

⚠️ 事故三：Java 读取文件按 \n 分割
   → Windows 文件每行尾巴带 \r → 字符串出现 \r 残留
   → 修复：trim() 或按 \r?\n 正则分割
```

> 🎯 **跨平台铁律**：**文件内容用 LF、显示按平台**——Git 配置 `core.autocrlf=true`（Windows）/ `input`（Linux），团队 `.gitattributes` 统一声明。

## 4. 标记语言类

| 后缀 | 语言 | 用途 | 转目标 |
|:----:|------|------|:----:|
| **.md** | Markdown | 文档、README、Wiki | HTML, PDF |
| **.html / .htm** | HyperText Markup Language | 网页结构 | 浏览器直接渲染 |
| **.xml** | eXtensible Markup Language | 配置、数据交换 | 被程序解析 |
| **.xhtml** | XML + HTML | 严格版 HTML | 浏览器 |
| **.tex** | LaTeX | 学术论文排版 | PDF, DVI |
| **.rst** | reStructuredText | Python 文档 | HTML, PDF |
| **.adoc** | AsciiDoc | 技术文档 | HTML, PDF, DocBook |

### 4.1 XML 与 HTML 的本质区别

```xml
<!-- XML：标签可自定义、严格闭合、区分大小写、属性必须引号 -->
<?xml version="1.0" encoding="UTF-8"?>
<users>
    <user id="1">
        <name>Alice</name>
        <email>alice@example.com</email>
    </user>
</users>

<!-- HTML：标签预定义、解析容错（不闭合也能渲染） -->
<!DOCTYPE html>
<html>
<head><title>Page</title></head>
<body><h1>Hello</h1></body>
</html>
```

| 维度 | XML | HTML |
|------|-----|------|
| 标签定义 | 自定义（DTD/XSD 约束） | 预定义（W3C 标准） |
| 严格性 | 严格闭合、大小写敏感 | 容错解析 |
| 用途 | 数据交换/配置 | 网页呈现 |
| 解析器 | SAX/DOM/StAX | 浏览器渲染引擎 |

### 4.2 XML 相关扩展名

| 后缀 | 说明 |
|:----:|------|
| **.xsd** | XML Schema 定义（约束 XML 结构） |
| **.dtd** | 文档类型定义（旧式约束） |
| **.xsl / .xslt** | XML 转换样式表（XML → HTML/XML） |
| **.svg** | SVG 图形（本质是 XML！） |
| **.pom** | Maven 项目对象模型（本质是 XML） |

## 5. Markdown：文档生态核心

### 5.1 为什么 Markdown 是 2026 文档事实标准

```text
Markdown 的生态地位
├── 代码仓库：README.md（GitHub/GitLab 默认渲染）
├── 知识管理：Obsidian/Notion 的本地格式
├── 技术写作：掘金/CSDN/知乎文章编辑格式
├── AI 时代：LLM 训练与输出的常见格式（结构化）
└── 转换生态：pandoc 一链转 PDF/HTML/docx
→ 掌握 .md = 掌握现代技术文档的通用语
```

### 5.2 Markdown 核心语法速查（10 个够用）

```markdown
# 一级标题
## 二级标题

**加粗**  *斜体*  `行内代码`  ~~删除线~~

- 无序列表项
1. 有序列表项

> 引用块
> 🎯 强调提示

[链接文本](https://example.com)
![图片说明](image.png)

```java
// 代码块（指定语言高亮）
System.out.println("Hello");
```

| 表头1 | 表头2 |
|-------|-------|
| 单元格 | 单元格 |

- [ ] 任务清单未完成
- [x] 任务清单已完成
```

### 5.3 Markdown 渲染链

```text
.md → 解析器（CommonMark/GFM）→ HTML → 渲染
├── GitHub 渲染：GFM（GitHub Flavored Markdown，含表格/任务清单）
├── 本地渲染：Typora/VS Code 预览
└── 文档链：pandoc → PDF/docx/epub（发布）
→ 注意：不同平台渲染差异（锚点/表格宽度）——写文档时用标准语法
```

## 6. 数据交换类

| 后缀 | 格式 | 可读性 | 用途 | 对比 |
|:----:|------|:----:|------|------|
| **.json** | JavaScript Object Notation | ✅ 好 | Web API、配置文件 | 最通用，体积小 |
| **.yaml / .yml** | YAML Ain't Markup Language | ✅ 极好 | 配置文件（K8s/Docker Compose） | 比 JSON 更可读 |
| **.xml** | XML | ⚠️ 冗长 | 旧系统、SOAP、Maven POM | 标签冗余，渐被替代 |
| **.csv** | CSV | ✅ 好 | 数据导出/导入/Excel | 表格数据最简单格式 |
| **.toml** | Tom's Obvious Minimal Language | ✅ 极好 | Rust/Cargo, Python 项目 | 简洁，适合配置 |
| **.proto** | Protocol Buffers | ❌ 不可读 | gRPC 接口定义 | 需编译为代码 |
| **.ndjson / .jsonl** | JSON Lines | ✅ 好 | 日志流、大数据处理 | 每行一个 JSON 对象 |

```yaml
# YAML 示例（K8s Deployment）——层级用缩进表达
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: app
        image: user-service:1.0
```

```toml
# TOML 示例（Cargo.toml）——层级用 [table] 表达
[package]
name = "my-app"
version = "0.1.0"

[dependencies]
serde = "1.0"
tokio = { version = "1", features = ["full"] }
```

### 6.1 数据格式选型决策

| 维度 | JSON | YAML | XML | TOML | CSV |
|------|:---:|:---:|:---:|:---:|:---:|
| 可读性 | 好 | 极好 | 差（冗长） | 极好 | 好 |
| 层级支持 | ✅ | ✅ | ✅ | ✅ | ❌ 扁平 |
| 注释支持 | ❌ | ✅ | ✅ | ✅ | ❌ |
| 类型系统 | 基础 | 弱（字符串陷阱） | 无 | 完善 | 无 |
| 生态 | 最全 | 好 | 老牌 | 中 | 最广 |
| 场景 | API/配置 | 服务配置 | 遗留系统 | 项目配置 | 表格数据 |

> 🎯 **选型口诀**：API 用 JSON、服务配置用 YAML、项目构建配置用 TOML、遗留对接用 XML、表格数据用 CSV——各归其位。

## 7. JSON 语法与陷阱

### 7.1 JSON 语法规范（容易写错的地方）

```json
{
  "string": "双引号必须（单引号非法！）",
  "number": 42,
  "float": 3.14,
  "boolean": true,
  "null": null,
  "array": [1, 2, 3],
  "object": {"nested": "允许"},
  "escaped": "含\"引号\"和\\反斜杠"
}
```

### 7.2 JSON 五大陷阱

| # | 陷阱 | 表现 | 解法 |
|---|------|------|------|
| 1 | **尾逗号非法** | `[1,2,3,]` 解析失败 | 严格 JSON 不允许尾逗号 |
| 2 | **单引号非法** | `{'a':1}` 解析失败 | 只能双引号 |
| 3 | **注释不支持** | 加注释就报错 | 用外部文档/`_comment` 字段 |
| 4 | **数字精度丢失** | 大整数 `9007199254740993` 变 9007199254740992 | 长整数用字符串 |
| 5 | **重复键** | 后覆盖前（静默） | 解析器去重检测 |

```bash
# JSON 校验与格式化
cat file.json | python -m json.tool        # 校验+格式化
jq . file.json                              # 查询/过滤（JSON 瑞士军刀）
jq '.users[] | select(.age > 30)' file.json # 条件查询
```

## 8. CSV 的转义规则

### 8.1 CSV 的基本规则（RFC 4180）

```text
CSV 三条铁律
├── ① 字段含逗号 → 必须用双引号包裹："Alice, Bob"
├── ② 字段含双引号 → 双引号翻倍转义："say ""Hi"""
├── ③ 字段含换行 → 双引号包裹（允许字段内换行）
└── ④ 表头可选但推荐（Excel 默认第一行当表头）
```

### 8.2 CSV 陷阱实战

```csv
# 正确示例（含逗号与引号的字段）
name,remark,amount
"Alice, Zhang","说 ""你好""",100.50
Bob,"第二行
继续",200

# ⚠️ 常见坑：
# ① 中文 Excel 打开 UTF-8 CSV 乱码 → 需带 BOM 或用 GBK
# ② Excel 保存 CSV 用系统分隔符（中文 Windows 用逗号，欧洲用分号）
# ③ 数字前导零丢失：0012 → 12（Excel 自动转数字）
```

### 8.3 CSV vs 其他表格格式

| 维度 | CSV | Excel (.xlsx) | Parquet |
|------|:---:|:---:|:---:|
| 可读性 | 文本可读 | 需 Office | 二进制 |
| 类型 | 全是字符串 | 强类型 | 强类型列式 |
| 体积 | 大 | 中 | **小（压缩）** |
| 适用 | 小数据交换 | 人工编辑 | 大数据分析 |

## 9. 电子文档类：Office 文件解剖

### 9.1 电子文档总览

| 后缀 | 类型 | 打开方式 | 特点 |
|:----:|------|---------|------|
| **.pdf** | Portable Document Format | Adobe Reader/浏览器 | 跨平台、不可编辑 |
| **.docx** | Word 文档 | Word/WPS | Office Open XML |
| **.xlsx** | Excel 表格 | Excel/WPS | 电子表格 |
| **.pptx** | PowerPoint 演示 | PPT/WPS | 演示文稿 |
| **.odt** | Open Document Text | LibreOffice | 开源文档格式 |
| **.epub** | Electronic Publication | 电子书阅读器 | 可重排电子书 |
| **.mobi / .azw** | Mobipocket/Kindle | Kindle | Kindle 电子书 |

### 9.2 Office 文件的真实结构（关键认知）

> 🎯 **docx/xlsx/pptx 的本质是 ZIP 压缩包**——改后缀为 `.zip` 解压后全是 XML 文件。这就是 Java 用 POI 操作 Office、Python 用 openpyxl 的原因。

```text
.docx 解压后的结构（解剖）
├── [Content_Types].xml      ← 内容类型声明
├── word/
│   ├── document.xml         ← 文档正文（XML！）
│   ├── styles.xml           ← 样式定义
│   └── media/               ← 嵌入图片
├── _rels/
│   └── document.xml.rels    ← 关系映射
└── docProps/
    ├── core.xml             ← 作者/时间元数据
    └── app.xml              ← 应用信息
```

### 9.3 PDF 的结构与处理

```text
PDF 的结构
├── 文件头：%PDF-1.x（版本号）
├── 对象树：目录（Catalog）→ 页面（Pages）→ 内容流（Content Stream）
├── 交叉引用表：对象偏移索引（快速定位）
└── 尾部：trailer + startxref（入口）

处理工具
├── 查看：浏览器/Adobe Reader
├── 合并拆分：pdftk / pdfunite
├── 转文本：pdftotext / Python pdfplumber
└── 生成：报告工具（iText/ReportLab/wkhtmltopdf）
```

## 11. 打开与转换工具速查

| 需求 | 工具/命令 |
|------|---------|
| Markdown → HTML | `pandoc input.md -o output.html` |
| Markdown → PDF | `pandoc input.md --pdf-engine=xelatex -o output.pdf` |
| Markdown → docx | `pandoc input.md -o output.docx` |
| JSON 格式化/校验 | `cat file.json \| python -m json.tool` 或 `jq .` |
| JSON 查询 | `jq '.items[].name' file.json` |
| XML 格式化 | `xmllint --format file.xml` |
| XML 校验（XSD） | `xmllint --schema schema.xsd file.xml` |
| CSV 查看 | `column -s, -t file.csv`（Linux） |
| 文件编码转换 | `iconv -f GBK -t UTF-8 file.txt -o out.txt` |
| 换行符转换 | `dos2unix file.txt` / `unix2dos file.txt` |
| 大文件查看 | `less file.log`（Linux）/ Large Text File Viewer（Win） |
| 文件类型识别 | `file xxx`（魔数识别，不依赖后缀名） |
| docx 内容提取 | `unzip -p file.docx word/document.xml` |
