## 1. 可执行文件与系统库

### 1.1 跨平台对比

| 平台 | 可执行文件 | 动态库 | 静态库 | 目标文件 |
|------|:-------:|:-----:|:-----:|:------:|
| **Windows** | `.exe` | `.dll` | `.lib` | `.obj` |
| **Linux** | 无后缀(ELF) | `.so` | `.a` | `.o` |
| **macOS** | 无后缀(Mach-O) / `.app` | `.dylib` | `.a` | `.o` |
| **Android** | `.apk` / `.aab` | `.so` | `.a` | - |
| **iOS** | `.ipa` | `.dylib` / `.framework` | `.a` | - |

```text
Linux 可执行文件为什么没有后缀？
├── Linux 通过文件权限判断可执行（x 位），不依赖后缀名
├── file 命令查看真实类型：
│   $ file /usr/bin/java
│   /usr/bin/java: ELF 64-bit LSB executable, x86-64
└── Windows 则强制 .exe 后缀（创建进程 API 依赖扩展名）

Windows 可执行家族：
  .exe  → 直接执行
  .msi  → Windows Installer 安装包
  .com  → 旧式 DOS 可执行文件
  .bat  → 批处理脚本（文本）
  .cmd  → NT 批处理
  .ps1  → PowerShell 脚本（2026 最常用！）
  .vbs  → VBScript 脚本
```

## 2. PE / ELF / Mach-O 三大可执行格式

### 2.1 魔数与整体结构

> 🎯 **三大可执行格式对应三大操作系统**——它们决定了「一个可执行文件跑在哪个平台」：

| 格式 | 平台 | 魔数 | 文件头 |
|------|------|:---:|--------|
| **PE** | Windows | `MZ`（4D 5A） | DOS 头 + PE 头 |
| **ELF** | Linux/Unix | `\x7FELF`（7F 45 4C 46） | ELF 头 |
| **Mach-O** | macOS/iOS | `FE ED FA CE`（32位）<br>`CF FA ED FE`（64位） | Mach 头 |

```text
三大格式的结构对比（本质相同：头 + 段 + 符号）
├── PE（Windows）：
│   ├── MZ 头（DOS 兼容）→ PE 头 → 节表（.text/.data/.rsrc）
│   └── 关键：导入表（依赖哪些 DLL）、导出表
├── ELF（Linux）：
│   ├── ELF 头 → 程序头表（段）→ 节头表（节）
│   └── 关键：.text（代码）/ .data（数据）/ .dynsym（动态符号）
└── Mach-O（macOS）：
    ├── Mach 头 → Load Commands → 段（__TEXT/__DATA）
    └── 关键：代码签名（Gatekeeper 强制验证）

验证命令：
  $ file /bin/ls          → ELF 64-bit
  $ file notepad.exe      → PE32+ executable
  $ xxd -l 4 /bin/ls      → 7f 45 4c 46
```

### 2.2 为什么 Windows 可执行文件不能跑在 Linux

```text
三大隔离层
├── ① 格式不同：PE vs ELF 的加载器各不认识对方
├── ② 系统调用不同：Win32 API vs POSIX
└── ③ 库不同：kernel32.dll vs libc.so

解决方案：
├── Wine：在 Linux 上实现 Win32 API（兼容层）
├── 虚拟机：完整运行 Windows
└── 容器（Docker）：不是模拟！容器共享宿主内核——
    Linux 容器里不能跑 Windows 程序（除非 Wine）
```

### 2.3 移动应用包

| 后缀 | 说明 | 本质 |
|:----:|------|------|
| **.apk** | Android 安装包 | ZIP + classes.dex + AndroidManifest |
| **.aab** | Android App Bundle（新发布格式） | 按设备分发优化 |
| **.ipa** | iOS 安装包 | ZIP + Mach-O 二进制 + 签名 |
| **.app** | macOS 应用包 | 目录（内含 Mach-O） |

## 5. 图片格式

### 5.1 位图格式总览

| 后缀 | 格式 | 压缩 | 特点 | 适用 |
|:----:|------|:---:|------|------|
| **.jpg / .jpeg** | JPEG | 有损 | 体积小、摄影最佳 | 照片/网页 |
| **.png** | PNG | 无损 | 支持透明、清晰 | 截图/UI/图标 |
| **.gif** | GIF | 无损(256色) | 动图、8 位色 | 简单动图 |
| **.webp** | WebP | 有损/无损 | 体积比 JPEG 小 25-35% | **Web 现代格式** |
| **.avif** | AVIF | 有损/无损 | 比 WebP 再小 30% | Web 下一代 |
| **.bmp** | BMP | 无压缩 | 原始像素、巨大 | 遗留 |
| **.tiff** | TIFF | 无损/有损 | 专业印刷 | 摄影/印刷 |
| **.raw / .arw / .cr2** | 相机 RAW | 原始数据 | 保留全部信息 | 摄影后期 |
| **.heic** | HEIF | 有损 | iPhone 默认 | 手机照片 |

### 5.2 网页图片选型（2026）

```text
Web 图片选型决策
├── 照片/复杂图 → WebP / AVIF（体积最小）
├── 截图/UI/透明 → PNG / WebP 无损
├── 图标 → SVG（矢量，任意缩放）
├── 动图 → WebP 动图 / GIF（兼容旧）
└── 对比体积（同一张图）：
    JPEG 100KB → WebP ~70KB → AVIF ~50KB
→ 2026 主流：全站 WebP，AVIF 渐进升级（浏览器兼容已 >90%）
```

## 6. 图像编码原理：位图 vs 矢量

### 6.1 两类图像的本质

| 维度 | 位图（栅格） | 矢量 |
|------|:---:|:---:|
| 存储 | 像素点阵（逐像素） | 数学公式（点/线/曲线） |
| 放大 | 模糊/锯齿（失真） | **任意缩放无损** |
| 体积 | 随分辨率增长 | 与复杂度相关 |
| 代表 | jpg/png/webp/bmp | **svg**/ai/eps |
| 适用 | 照片/截图 | Logo/图标/插画 |

```xml
<!-- SVG 本质是 XML（矢量）——放大 1000 倍依然清晰 -->
<svg width="100" height="100">
  <circle cx="50" cy="50" r="40" fill="#1677FF"/>
  <rect x="20" y="20" width="60" height="10" fill="white"/>
</svg>
```

### 6.2 有损 vs 无损

```text
压缩两派
├── 有损（JPEG/WebP/AVIF）：
│   ├── 丢弃人眼不敏感的细节 → 体积小
│   └── 反复保存质量逐次下降（编辑时用无损中间格式！）
├── 无损（PNG/GIF/BMP）：
│   ├── 字节级还原 → 质量不变
│   └── 体积大（照片用 PNG 是浪费）
└── 编辑工作流：
    拍摄/导出 RAW → 编辑（无损）→ 最终导出 WebP/JPEG（有损）
    金句：有损格式只用于「最终交付」，不用于「编辑中间态」
```

### 6.3 图片魔数与工具

```bash
# 图片魔数（file 命令识别）
file photo.jpg   # JPEG image data, JFIF standard 1.01
file logo.png    # PNG image data, 512 x 512, 8-bit/color RGBA

# 批量转换（2026 常用）
cwebp photo.jpg -o photo.webp              # JPEG → WebP
avifenc photo.jpg -o photo.avif            # JPEG → AVIF
convert a.png b.jpg                        # ImageMagick 万能转换
```

## 7. 音频格式

### 7.1 音频格式总览

| 后缀 | 格式 | 类型 | 特点 | 适用 |
|:----:|------|:---:|------|------|
| **.wav** | WAV | 无损未压缩 | PCM 原始数据 | 录音/编辑 |
| **.mp3** | MP3 | 有损 | 最通用（128-320kbps） | 音乐/播客 |
| **.aac** | AAC | 有损 | 比 MP3 音质更好 | iTunes/流媒体 |
| **.flac** | FLAC | 无损压缩 | 音质无损体积减半 | 无损音乐收藏 |
| **.ogg / .opus** | OGG/Opus | 有损 | Opus 低延迟高音质 | 语音/游戏 |
| **.m4a** | M4A | 有损/无损 | Apple 生态（AAC/ALAC） | iOS |
| **.midi** | MIDI | 指令集 | 不是声音是乐谱！ | 电子乐器 |

### 7.2 音频编码原理

```text
音频数字化三步
├── 采样（Sample）：每秒采样次数 = 采样率（44.1kHz CD 标准）
├── 量化（Quantization）：每个采样点精度 = 位深（16bit/24bit）
└── 编码（Encoding）：压缩方式
    ├── 无压缩：WAV = 采样率 × 位深 × 声道（CD 一分钟约 10MB）
    ├── 有损：MP3/AAC 丢弃人耳不敏感频率
    └── 无损：FLAC 用算法压缩但可完整还原

体积公式：WAV 大小 = 采样率 × 位深/8 × 声道数 × 秒数
  例：44.1kHz × 16bit × 2声道 × 60s ≈ 10.6MB/分钟
```

> 🎯 **选型**：编辑用 WAV（无损中间态）、通用分享 MP3/AAC（体积小）、无损收藏 FLAC、语音场景 Opus（低延迟）。

## 8. 视频格式：容器 vs 编码

### 8.1 核心认知：容器 ≠ 编码

> 🎯 **视频文件的本质 = 容器（壳）+ 编码（核）**——`.mp4` 只是壳，里面装的可能是 H.264 也可能是 H.265：

```text
容器（Container）：管「怎么装」
├── .mp4  ← 最通用（H.264/HEVC）
├── .mkv  ← 功能全（多音轨/字幕/章节，盗版分发最爱）
├── .avi  ← 古老（兼容差）
├── .mov  ← Apple 生态
├── .webm ← Web 标准（VP9/AV1）
└── .ts   ← 直播流分段

编码（Codec）：管「怎么压」
├── H.264 (AVC)  ← 2010 年代标准（兼容性最好）
├── H.265 (HEVC) ← 比 H.264 省 50% 体积（专利授权问题）
├── VP9          ← Google 免费替代
├── AV1          ← 2026 新标准（省 30% vs HEVC，免专利费）
└── 音频轨：AAC / AC3 / Opus

验证工具：
$ ffprobe video.mp4        # 查看容器与编码详情
$ ffmpeg -i video.mkv -c:v libx264 -c:a aac out.mp4   # 转码
```

### 8.2 视频格式选型（2026）

| 场景 | 容器/编码 | 理由 |
|------|----------|------|
| Web 播放 | **MP4 + H.264** | 浏览器全兼容 |
| 流媒体平台 | H.265/AV1 | 省带宽成本 |
| 本地收藏 | MKV + H.265 | 多轨 + 体积小 |
| 视频会议 | WebM + VP9/Opus | Web 实时 |
| 剪辑中间态 | 无压缩/ProRes | 编辑质量优先 |

> ⚠️ **兼容性铁律**：给用户/浏览器分发用 **MP4 + H.264 + AAC**（全设备可播）；其他格式都是「懂行的人」的选择。

## 9. 字体与证书文件

### 9.1 字体格式

| 后缀 | 格式 | 特点 | 适用 |
|:----:|------|------|------|
| **.ttf** | TrueType | 最通用（曲线字体） | 全平台 |
| **.otf** | OpenType | TTF 增强（排版特性） | 专业排版 |
| **.woff / .woff2** | Web Open Font | 压缩的 Web 字体 | **Web（woff2 是标准）** |
| **.eot** | Embedded OpenType | IE 遗留 | 已淘汰 |

```css
/* Web 字体引用（.woff2） */
@font-face {
  font-family: 'MyFont';
  src: url('myfont.woff2') format('woff2');
  font-display: swap;
}
```

### 9.2 证书文件（TLS/HTTPS 基础设施）

| 后缀 | 格式 | 内容 | 说明 |
|:----:|------|------|------|
| **.pem** | PEM | Base64 文本（证书/密钥） | **最通用**（Nginx/OpenSSL） |
| **.crt / .cer** | 证书 | PEM 或 DER | 公钥证书（扩展名常混用） |
| **.key** | 私钥 | PEM/DER | ⚠️ 私钥绝不泄露！ |
| **.csr** | 证书签名请求 | PEM | 申请证书用 |
| **.p12 / .pfx** | PKCS#12 | 二进制（证书+私钥打包） | Java/Windows 常用 |
| **.jks** | Java KeyStore | Java 专用 | Java 应用 |
| **.der** | DER | 二进制证书 | 少用 |

```bash
# 证书操作速查（OpenSSL）
openssl x509 -in cert.pem -text -noout      # 查看证书详情
openssl s_client -connect example.com:443   # 检查线上证书
openssl pkcs12 -export -out cert.p12 -inkey key.pem -in cert.pem  # 转 p12

# 查看 PEM 内容（Base64 文本，可直接 cat）
cat cert.pem
-----BEGIN CERTIFICATE-----
MIIB...（Base64）
-----END CERTIFICATE-----
```

> ⚠️ **安全铁律**：`.key` / `.p12`（含私钥）文件**永不提交 Git、永不进代码库**——私钥泄露 = HTTPS 防线全失。用 `.gitignore` + 密钥管理服务（KMS/Vault）管理。

## 10. 核心要点

> 🎯 **核心要点**：
> 1. 三大可执行格式（PE `MZ` / ELF `\x7FELF` / Mach-O `FEEDFACE`）对应三大系统——格式+系统调用+库三重隔离
> 2. 图片选型：Web 用 WebP/AVIF、UI 用 PNG/SVG、摄影 JPEG；**有损格式只用于最终交付**（编辑用无损中间态）
> 3. 音视频核心认知：**容器（壳）≠ 编码（核）**——mp4+H.264+AAC 是兼容性铁律；AV1 是 2026 免专利费新标准
> 4. 证书：.pem 最通用、.key 私钥永不泄露、.p12 打包证书+私钥（Java 生态）
> 5. file 命令按魔数识别真实格式——改名伪装骗不了它（安全场景按内容校验）
