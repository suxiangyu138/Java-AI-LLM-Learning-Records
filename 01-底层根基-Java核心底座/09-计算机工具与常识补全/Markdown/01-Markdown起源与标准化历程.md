## 1. 诞生背景与设计哲学

2004 年，技术博主 John Gruber 与 Aaron Swartz 创造了 Markdown。当时 HTML 是写网页的唯一途径——`<h1>`、`<p>`、`<a href="">` 让纯文本写作变成一场标签体操。Gruber 的目标只有一个：**让文档在源码状态下就具备可读性**。

这个目标决定了 Markdown 的三条设计哲学，也是它与 HTML、LaTeX、AsciiDoc 分道扬镳的根本原因：

- **可读性优先于表达力**：`# 标题` 明显比 `<h1>标题</h1>` 更接近人类笔记的书写习惯，代价是语法表达能力受限——Markdown 从设计上就不追求完整描述排版
- **纯文本可移植**：不依赖任何专有格式，任何编辑器可打开，Git diff 逐行可读，工具迁移成本接近零
- **容错宽松**：解析失败不报错，最坏情况退化为普通文本，绝不阻断阅读

第一版实现 `Markdown.pl` 是一个约 1000 行的 Perl 正则脚本。用正则解析标记语言在今天看来是「结构性错误」——它无法正确表达嵌套、上下文依赖等真正的解析问题，这是后来所有分歧的技术源头。

一个常被引用的设计信条是「可读性高于一切」（readability is paramount）：格式存在的意义是让文档在**未渲染状态下**依然像一份结构化文档。这条信条解释了 Markdown 的诸多「反常识」取舍——为什么强调用 `*` 和 `_` 两种标记（贴近手写习惯）、为什么链接定义可以集中写在文末（阅读时不干扰正文）、为什么语法解析失败时静默退化而非报错（打断写作是最大的罪）。也解释了它为什么没有表格、没有脚注、没有公式——这些在 2004 年的语法体系里都被认为「会破坏源码可读性」。

> **关键认知**：Markdown 从诞生起就没有正式语法规范（grammar），只有一份「有歧义的散文描述」和一个参考实现。这是旧时代所有解析器行为不一的根本原因。

## 2. 方言混战时期

2004 到 2014 年，Markdown 迅速成为技术写作事实标准，但也陷入了十年的分裂。问题链条非常清晰：

1. `Markdown.pl` 正则实现的边界行为充满未定义区域（嵌套列表怎么算？`*` 与 `_` 强调边界？代码块与列表缩进冲突？）
2. 各平台（GitHub、Stack Overflow、Reddit、PHP 系 CMS）各自实现解析器，遇到未定义区域就自行决定
3. 没有测试套件，没有一致性验证，分歧逐年累积

到 2010 年前后，同一份文档在不同解析器下可以渲染出完全不同的结构——嵌套列表层级错乱、强调标记失效、代码块被吃掉，成为文档作者的日常困扰。「按我的渲染器来」成为社区常态，写文档被迫「一门方言写一遍」。

分歧的典型样本至今仍可复现：`*foo*` 与 `_foo_` 在词内（`foo_bar_baz`）是否触发强调，各实现态度不同；列表项内容的缩进量（2 格还是 4 格算子内容）没有统一答案；`#` 标题与 `#hashtag` 的边界判断标准不一。这些问题不是「细节瑕疵」——它们直接决定同一份技术文档在 GitHub、Stack Overflow、Reddit 上的可读性，是当年工程师的日常摩擦成本。

这段历史留下的遗产至今可见：Obsidian 的 callout、Typora 的公式语法、Discord/Slack 的行内变体，都是方言时代「各建各的」思路的延续。

## 3. CommonMark 标准化

转折点在 2012 年。Stack Overflow 联合创始人 Jeff Atwood 发表《The Future of Markdown》，公开呼吁：「Markdown 需要一份标准，并配套测试套件」。文章戳中了所有人的痛点，但真正把标准做出来的是哲学家兼程序员 John MacFarlane（Pandoc 作者）。

2014 年 9 月，CommonMark 计划启动，带来三件套：

- **严格规范**：把「有歧义的散文」重写成可判定的形式化规则，明确每个未定义区域的行为
- **参考实现 cmark**：C 语言编写，规范即实现、实现即规范，消除二次解释
- **测试套件**：数百个 `.md → .html` 用例对，任何实现都必须跑通才算兼容（0.31.2 版本已积累 600 余例）

CommonMark 的赌注是：**一致性比灵活性重要**。它主动放弃了部分「聪明但不统一」的行为，换取所有合规解析器渲染结果一致。此后 markdown-it、micromark、goldmark 等主流实现纷纷声明兼容 CommonMark，方言混战时代实质终结。

标准化的另一条战线在协议层：2016 年 3 月，IETF 发布 RFC 7763，把 `text/markdown` 注册为正式媒体类型（同时在 RFC 7764 中给出 Markdown 方言的指导说明）。这意味着 `Content-Type: text/markdown` 从「社区约定」升级为「协议事实」——HTTP 内容协商、邮件附件、Web API 都可以用标准方式声明「这是一份 Markdown」。它为后来的 AI 文档分发（`Accept: text/markdown` 协商）埋下了基础设施。

## 4. GFM 与平台演进

GitHub 早在 2009 年就开始扩展 Markdown（自动链接、任务列表等），2017 年 3 月正式发布 **GitHub Flavored Markdown（GFM）规范**——基于 CommonMark 的严格超集，增加五组扩展：

| 扩展 | 语法示例 | 说明 |
|------|---------|------|
| 表格 | `\| a \| b \|` | 管道语法，带对齐控制 |
| 任务列表 | `- [x] done` | 勾选框，GitHub 上可交互 |
| 删除线 | `~~text~~` | 双波浪号 |
| 自动链接 | `https://...` 裸链接 | 不必写 `<>` |
| tagfilter | — | 安全扩展，转义 9 个危险 HTML 标签 |

「严格超集」是精确定义：**合法 CommonMark 文档在 GFM 中必然合法，反之不成立**。这保证了 GFM 生态能向下兼容全部 CommonMark 工具链。

GFM 规范本身在 2019 年 4 月更新到 v0.29-gfm 后**再无修订**，但 GitHub 平台侧持续演进：2023 年 12 月上线 Alerts（五种提示块），2026 年 2 月推出「Agentic Workflows in Markdown」技术预览（用 Markdown 写 GitHub Actions 工作流）。这形成了 2026 年最独特的模式——

> **冻结的规范，演进的渲染器**：规范保持稳定以保护生态，新能力通过平台行为发布。了解一个新语法时，先问「这是规范的一部分，还是某个平台的实现」，这是跨平台文档写作的第一原则。

## 5. 2026 年现状与演进逻辑

截至 2026 年，两条版本线各自清晰：

- **CommonMark**：最新版 v0.31.2（2024-01-28 发布），仍是全体工具链的事实基线；1.0 尚未发布，规范论坛 2026 年仍有少量议题讨论（如「1.0 前必须解决的 6 个问题」）
- **GFM**：规范冻结于 v0.29-gfm（2019-04），平台能力持续加码（Alerts、Mermaid、LaTeX、Agentic Workflows）

为什么十年不发 1.0 反而更稳？三个机制在起作用：

1. **向后兼容承诺**：规范明确「已发布版本的文档在新版本中行为不变」，0.x 只做增补不做破坏，工具链敢于长期跟进
2. **测试套件即契约**：兼容性由 600+ 用例定义而非版本号，实现方跑通套件即可声明兼容，版本号只是快照
3. **生态锁定效应**：Micromark、markdown-it、goldmark、cmark、CommonMark-java 全部对齐 0.31.x，任何破坏性修订都要付全生态代价

对使用者的现实建议：把 CommonMark 0.31.2 作为语法基线下限，把 GFM 作为事实上的日常方言，其他平台扩展（Obsidian callout、MDX 组件）视为「渐进增强」——降级后仍是合法文档。

---

> **核心要点**：Markdown 的历史是「个人项目 → 方言分裂 → 规范统一 → 冻结演进」的标准案例。记三个版本锚点：原始 Markdown（2004 无规范）、CommonMark 0.31.2（严格基线）、GFM 0.29（事实方言）。遇到任何渲染怪象，先回到「规范定义了没有」这个问题上找答案。
