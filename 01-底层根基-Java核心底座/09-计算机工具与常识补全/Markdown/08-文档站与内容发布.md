## 1. 静态站点生成器全景

技术文档的发布工具分两代。第一代是通用 SSG（Hugo、Jekyll、Eleventy）——快、灵活，但导航、搜索、暗色模式都要自己配。第二代是 **docs-first 框架**（2026 年主流），把文档站的必备功能内置，开箱即用：

- **VitePress**：Vite + Vue 驱动，Markdown-first 极简配置，开发服务器启动亚秒级
- **Docusaurus 3**：React 驱动，Meta 系项目（React/Redux/Jest）在用，**内置版本化文档**
- **Astro Starlight**：Astro 之上，任何前端框架的组件都能用（islands 架构），默认达到 Lighthouse 100 分
- **MkDocs Material**：Python 生态，插件生态最成熟
- **Hugo**：构建速度最快（Go），博客 + 文档通吃

生态体量参考（周下载量口径，2026）：Docusaurus 约 3M、VitePress 约 2M、Starlight 约 200K——Starlight 体量最小但增长最快。

### 构建原理：一次编译，静态交付

所有 SSG 共享同一条流水线，理解它就能理解「为什么文档站比手工 HTML 快且一致」：

```text
源文件（Markdown + frontmatter）
   │  ① 解析（第 04 篇的两阶段解析器）
   ▼
AST → 路由生成（文件路径 → URL 映射）
   │  ② 套布局（侧边栏/目录/页脚来自配置与 frontmatter）
   ▼
HTML 页面 + 静态资源
   │  ③ 附加能力（代码高亮、搜索索引、llms.txt）
   ▼
dist/ 静态产物 → 任意静态托管
```

三个关键收益：

- **构建期完成全部重活**：语法高亮、TOC、搜索索引在构建时生成，运行时零计算，因此 Lighthouse 轻松满分
- **搜索结果离线可用**：VitePress 用 MiniSearch、Starlight 用 Pagefind——构建时把全文切成片段建索引，浏览器本地检索，不需要 Algolia 之类的外部服务（这也是「内置搜索」与「需要 API Key 的搜索」的本质区别）
- **链接可在构建期校验**：死链导致构建失败而非上线后 404，把问题左移到本地

代价是「重新构建才能更新内容」——对文档站是特性而非缺陷：每次变更都经过完整校验，产物可回滚、可审计。

## 2. 三大框架选型

| 维度 | Starlight（Astro） | VitePress | Docusaurus 3 |
|------|-------------------|-----------|--------------|
| 底层技术 | Astro | Vite + Vue | React |
| 内置搜索 | Pagefind（离线免费） | MiniSearch 本地 | Algolia 为主 |
| 版本化文档 | 手动 | 手动 | **内置（CLI 一键）** |
| i18n | 支持 | 支持 | 成熟内置 |
| MDX | 是 任何框架组件 | 是 Vue 组件 | 是 React 组件 |
| 最适合 | 现代开源工具文档（默认推荐） | Vue/Vite 生态 | 需要多版本文档 + React |

决策路径：

1. **需要同时维护多个版本文档**（如 v1/v2 API 并存）→ Docusaurus 3，这是它无法被替代的核心差异点
2. **Vue/Vite 生态项目** → VitePress，Markdown-first，上手最快
3. **其余情况（现代工具文档默认解）** → Astro Starlight，Lighthouse 满分、组件自由、增长最快
4. **Python 生态 / 极简主义** → MkDocs Material；**博客与文档一体** → Hugo 或 Astro 内容集合

三者产物都是静态 HTML，部署方式完全一致，且迁移成本对简单文档站不高——**先用最顺手的，体系庞大了再按需迁移**。

## 3. MDX 与组件化内容

**MDX = Markdown + JSX**，经编译后文档变成组件模块，可直接 import 组件、传 props、写表达式：

```mdx
import Tabs from '@theme/Tabs';

# 安装指南

<Tabs>
  <TabItem value="maven">Maven 依赖配置…</TabItem>
  <TabItem value="gradle">Gradle 依赖配置…</TabItem>
</Tabs>
```

MDX 解决的真实问题：**文档里的交互需求**——标签页、可运行示例、API 参数表自动生成、按版本切换代码。Docusaurus 的 `.mdx`、Next.js 文档、Astro 的 MDX 集成都基于它。

编译原理值得理解，因为它解释了 MDX 的能力边界：MDX 编译器把 Markdown 部分按标准解析成 AST，再把 JSX 片段编译为 JavaScript 表达式，最终**整篇文档成为一个可 import 的组件模块**。所以文档能拿 props、能条件渲染、能引用项目里的真实组件——它已不是「被解析的文本」而是「源代码」。这直接推出一条工程建议：**MDX 文件应当纳入 lint 与类型检查**（ESLint 处理 JSX 部分），否则组件语法错误只会在构建时才暴露。

边界必须说清楚：

- **MDX 不是纯文本**：脱离编译链不可读，GitHub 上只显示源码，AI 工具对 MDX 的处理也不如纯 Markdown 稳定
- **适用判据**：文档需要「组件能力」时用 MDX，否则老老实实 Markdown——组件的滥用会把文档站变成需要维护的前端项目
- Astro 提供折中方案：`.md` 保持纯 Markdown，需要组件时才用 `.mdx`

## 4. Frontmatter Schema 与内容集合

站点规模变大后，frontmatter 是第一个失控点——字段拼写错误、类型不一致、必填缺失，往往到构建时才报错。**内容集合（Content Collections）**是 2026 的标准解法（Astro 首创，Docusaurus/VitePress 有类似机制）：

```typescript
// src/content.config.ts —— 用 Zod schema 定义 frontmatter 契约
import { defineCollection, z } from 'astro:content';

const blog = defineCollection({
  type: 'content',
  schema: z.object({
    title: z.string(),
    date: z.coerce.date(),
    tags: z.array(z.string()).default([]),
    draft: z.boolean().default(false),
  }),
});

export const collections = { blog };
```

收益链条：**构建时校验**（字段写错立即失败而非上线后 404）+ **类型推断**（`post.data.title` 有补全）+ **一致性**（全站 frontmatter 同构）。读取时通过 `getCollection()` 拿到已校验数据：

```typescript
const posts = await getCollection('blog', ({ data }) => !data.draft);
```

与 Obsidian 的协作：Obsidian 属性面板只支持扁平 YAML，社区 loader（如 `astro-loader-obsidian`）把 vault 当内容集合读，自动解析 `[[双链]]` 与 `![[嵌入]]`。**约定优于配置**：新建文档前先看 schema 文件，字段名以 schema 为准。

## 5. 发布链路与多形态输出

### 5.1 部署平台

三大框架都是静态产物，主流托管平台：

- **GitHub Pages**：零成本、与仓库同源（Actions 直接发布）；注意 Pages 用 Jekyll/kramdown 渲染时与 GFM 行为不同（Alerts、Mermaid 可能失效），SSG 产物则无此问题

GitHub Pages 最小部署流水线（以 VitePress 为例，其他框架换构建命令即可）：

```yaml
name: deploy-docs
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  build-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run docs:build      # 构建即校验：死链会在这里失败
      - uses: actions/upload-pages-artifact@v3
        with: { path: docs/.vitepress/dist }
      - uses: actions/deploy-pages@v4
```
- **Vercel / Netlify**：Git 推送即部署，PR 预览环境是文档评审利器
- **Cloudflare Pages**：全球边缘分发，与 Workers 生态联动

### 5.2 多形态输出

一份 Markdown 源码按需转出多种形态：

| 目标 | 工具 | 说明 |
|------|------|------|
| HTML 站点 | VitePress/Docusaurus/Starlight | 主发布形态 |
| PDF | Pandoc + LaTeX / Typora 导出 | 交付文档、课程材料 |
| DOCX | Pandoc | 需按模板交付的场景 |
| 幻灯片 | Marp / Slidev | Markdown 直接生成演示 |
| 电子书 | Pandoc（EPUB） | 个人知识库归档 |

**Pandoc** 是万能转换器（Markdown ↔ HTML/PDF/DOCX/EPUB/LaTeX 全支持），输入输出格式可自由组合，是「格式矩阵」的枢纽工具。

### 5.3 面向 AI 的发布（2026 新增）

文档站现在还要发布「给 Agent 读的版本」：`llms.txt`（站点索引）、`llms-full.txt`（全文拼接）、markdown 端点。三大框架都有对应插件（`docusaurus-plugin-llms`、`vitepress-plugin-llms`、`starlight-llms-txt`），构建时自动生成。这一主题的完整展开见第 09 篇。

---

> **核心要点**：文档站选型三问——要版本化吗（Docusaurus）、生态是什么（VitePress/Starlight）、需要组件吗（MDX）。内容集合 + Zod schema 是 frontmatter 失控的解法。发布不止 HTML：Pandoc 负责格式矩阵，llms.txt 负责 AI 可读性。
