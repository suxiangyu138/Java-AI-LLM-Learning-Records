# 05 - 文档阅读方法论

> 读 Markdown 文档有三层：渲染层读「内容」，源码层读「结构」，AST 层读「行为」。会读源码层的工程师，能一眼看出文档的组织方式、坏味道与真实意图；会读 AST 层的人，能解释任何渲染差异。本篇给出完整方法论

## 1. 三层阅读法

同一份 `.md` 文件在三个层次上是三种东西，选择正确的层次决定了阅读效率：

| 层次 | 你看的是什么 | 适用场景 |
|------|-------------|---------|
| **渲染层** | 排版后的标题/表格/图 | 消费内容：学知识、看 API 文档 |
| **源码层** | 标记符号 + 内容的混合文本 | 理解结构：评估文档质量、学习他人写法、排查渲染问题 |
| **AST 层** | 解析后的语法树 | 解释行为：锚点生成、渲染差异、写文档工具 |

多数人只停留在渲染层。但**源码层是工程师的主场**——GitHub 的 diff、评审、搜索都发生在源码层，能快速读源码层的人，在代码评审文档、接手他人项目时优势明显。

> 三层不是逐层递进，而是按需切换：内容存疑时切源码层核对，渲染异常时切 AST 层推理。

## 2. 源码速读技巧

源码层速读的目标是「30 秒内建立文档地图」。按以下顺序扫描：

1. **扫块级骨架**：只看行首字符——`#` 标题、`-`/`1.` 列表、`>` 引用、`|` 表格、` ``` ` 代码块。骨架一小时内可扫完一篇长文档，内容细节按需回读
2. **抓空行分段**：空行是块级边界的主要信号。连续无空行的正文 = 一个段落（即使多行）；空行分隔 = 新块。源码里「看起来换行了」不代表渲染后换行
3. **识别行内标记密度**：加粗（`**`）通常是作者划的重点；`code` span 是术语/标识符。标记密度的分布本身是信息——某段全是加粗说明那是速记区，某段全是代码说明那是实操区
4. **定位元数据块**：文件顶部 `---` 包裹的 frontmatter 是文档的「身份证」（见下节），先看它可判断文档用途与平台
5. **看尾部导航**：本仓库体系文档尾部固定有「下一模块 / 返回总览」，别人项目常是「See also / Related」。尾部导航反推出文档在体系中的位置

**坏文档信号**（源码层一眼可辨）：标题层级跳跃（`#` 直接跳 `####`）；代码块不标语言；大量裸 URL；全文无空行（紧凑到不可读）；用 HTML 标签代替 Markdown 基本语法（`<h2>` 代替 `##`）；README 里贴整屏的截图代替文本。

## 3. 元数据与 frontmatter 阅读

frontmatter 是文件顶部以 `---` 包裹的 YAML 块（部分系统用 `+++` 包裹 TOML），被解析器剥离后供工具消费：

```yaml
---
title: 设计文档
date: 2026-08-18
tags: [api, backend]
draft: true
---
```

读到 frontmatter 时的判断链：

- **有 `draft: true`**：草稿未发布，内容可能未完成——文档站通常不渲染它
- **有 `slug`/`permalink`**：URL 被显式指定，锚点与链接要按它推算
- **有 `tags`/`categories`**：文档属于分类系统，先跳去分类页看全局
- **纯 Obsidian 库**：`aliases`（别名）、`cssclasses` 控制显示；注意 Obsidian 属性面板只支持**扁平键值**，嵌套 frontmatter 是其他工具的逻辑

同一个字段在不同系统含义可能不同（`date` 在 Hugo 是发布时间、在 Astro 是自定义字段），**以目标系统的 schema 为准**——Astro 的 content collections 会用 Zod schema 校验，写成文档前先核对 schema。

## 4. 渲染差异调试方法

「本地正常、GitHub 上乱了」是 Markdown 高频问题。系统化调试四步：

1. **复现最小案例**：把出问题的片段单独存成小文件分别在两处渲染，排除上下文干扰
2. **判断块级还是行内**：块级问题（列表错乱、表格失效）先查空行与缩进；行内问题（强调失效、链接吞字）查边界字符
3. **对照规范定位**：到 CommonMark 规范里搜对应章节——规范写了的就是实现 Bug（换解析器验证），规范没写的（Alerts、脚注细节）就是平台方言，只能用「目标平台支持矩阵」规避
4. **验证锚点**：中文标题、含标点的标题、重复标题的锚点最容易出问题——实际点击一次，不要在脑内推导

> **高频差异源**：表格前缺空行（GitHub 宽松、严格实现报错）、嵌套列表的缩进量（2 格 vs 4 格在不同宽松度实现下表现不同）、HTML 与 Markdown 混写在块内行为、行尾两空格的硬换行被编辑器自动去除。

## 5. 平台阅读技巧与锚点体系

### 5.1 GitHub 上高效读文档

- **Outline 按钮**：长 README/文档右上角自动生成大纲面板，长文档先开大纲再跳读
- **按键 `t`**：在仓库页激活文件查找器，大仓库里秒开目标文件
- **按键 `.`**：把仓库切换为网页版 VS Code（github.dev），全文搜索、跳转定义全部可用，不克隆也能读代码级内容
- **行号链接**：点击行号（Shift 点第二处）生成 `#L10-L20` 锚点链接，评审沟通的通用语言
- **`?plain=1` 参数**：强制查看 Markdown 源码；`raw` 按钮同理，用于核对「编辑器显示」与「网页渲染」的差异
- **按键 `y`**：把当前 URL 固定到具体 commit（permalink），引用给他人时不受后续修改影响

### 5.2 锚点生成规则

锚点 = 标题纯文本 → 小写 → 去标点符号 → 空格转 `-`。中文保留（「## 核心概念」→ `#核心概念`）。三条实践推论：

- 标题尽量不含标点，锚点可预测，链接不用试错
- 同一文档重复标题的锚点会加 `-1` 后缀，写作时避免重复标题
- 跨文档链接的锚点必须与目标标题**逐字符一致**，改标题等于改接口——重命名标题后用链接检查工具（如 lychee）全量验证

### 5.3 长文档速读策略

拿到一篇 2000 行以上的长文档：

1. 先读目录/大纲，建立章节地图
2. 泛读所有二级标题，标记要精读的章节
3. 全文扫「关键句标记」——加粗、`> ` 总结块、速查表，这些是作者压缩过的高密度区
4. 代码块按需回读：速读时只看语言标注与首行，确认技术栈后再精读
5. 尾部找导航与参考来源，跳转到同级文档补齐上下文

---

> **核心要点**：阅读能力 = 层次选择能力。渲染层消费内容、源码层理解结构、AST 层解释行为。速读先扫块级骨架与空行边界，frontmatter 判断文档性质，渲染问题按「最小复现 → 块级/行内 → 规范对照」三步定位。锚点是文档的接口，改标题等于改接口。
