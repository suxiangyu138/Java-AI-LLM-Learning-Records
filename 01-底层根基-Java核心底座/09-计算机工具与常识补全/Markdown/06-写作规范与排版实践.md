## 1. 文档结构规范

### 1.1 标题层级纪律

- 一篇文档只有一个 `#` 一级标题，其余全用 `##` 及以下
- **层级不可跳跃**：`##` 之后直接出现 `####` 是结构断裂——读者的大纲视图与样式都会错乱
- 标题即导航：标题文本会被生成目录、锚点、搜索索引，写标题时按「读者会搜什么词」来写，而不是按「作者想说什么」

### 1.2 文档骨架

技术文档的标准骨架（按需裁剪，但顺序不轻易变）：

```text
# 标题
> 一句话定位（读到这里就知道要不要读下去）

## 目录（长文档必备）

## 1. 背景与目标（为什么读这篇）
## 2. 核心内容（分模块展开）
## 3. 边界与异常（出错怎么办）
## 4. 权衡与选型（为什么不选另一条路）
## 5. 实践清单（读者明天能做什么）

## 参考来源
```

「一句话定位」是成本最低、收益最高的规范：读者 3 秒内决定继续读还是离开，比任何开场白都有效。

### 1.3 篇幅与聚合纪律

- 单篇聚焦一个主题，**相关知识点聚合而非拆碎**：三篇 500 字的薄文档不如一篇 1500 字的完整文档——拆碎会切断上下文，读者被迫来回跳转
- 文档之间靠「导航链接」串联，而非靠「复制粘贴」重复内容；发现两处内容重复时，合并到一处、另一处留链接
- 一篇写不完时按「独立可读性」拆分：拆出的每篇都应有自己的定位句与完整闭环

## 2. 中文排版规范

中文技术文档排版的核心规则只有一组，但执行率极低——它显著区分「随手写」与「专业文档」。

| 规则 | 正确示例 | 错误示例 |
|------|---------|---------|
| 中英文之间加空格 | 使用 `uv` 创建虚拟环境 | 使用`uv`创建虚拟环境 |
| 中文与数字之间加空格 | 延迟约 200 毫秒 | 延迟约200毫秒 |
| 中文用全角标点 | 结论：可行。 | 结论:可行. |
| 完整英文句用半角标点 | This is a test. | This is a test。 |
| 专有名词大小写正确 | GitHub、Java、MySQL | github、mysql |
| 数字与单位 | 8GB、15%（不加空格，团队内统一） | 8 GB 与 8GB 混用 |

要点说明：

- 中英文之间加空格本应由排版引擎自动完成，但浏览器 CSS `text-spacing` 尚未普及，只能手动补——这是「为什么必须手写空格」的完整答案
- 代码块、命令、URL 内部不适用中文排版规则；行内代码两侧的空格属于中英混排空格
- 工具兜底：`pangu.js`（自动加空格）、Typora（自动排版）、CI 中挂 pangu 检查脚本

## 3. 内容呈现规范

### 3.1 论述优先，表格为辅

表格只服务三类场景：**对比**（方案 A vs B）、**速查**（命令表）、**清单**（检查项）。机制原理、演进逻辑、权衡分析必须用文字论述——用表格承载论述会产生「每个单元格一句话、逻辑断裂」的伪信息。

判断标准：如果一个表格拆开文字依然通顺，说明它该是文字；如果文字拆开看不出差异，说明它该是表格。

### 3.2 代码块纪律

- **必须标注语言**：```java / ```yaml / ```bash ——不标注则无高亮、无复制按钮语义，部分平台还会按纯文本处理
- 展示 Markdown 语法时嵌套围栏：外层用四个反引号包裹，内层三个
- 修改对比用 `diff` 语言标注展示增删行
- 代码只保留核心片段：贴 200 行上下文不如贴 20 行关键逻辑加一句说明

### 3.3 列表与强调

- 列表项**逐行排列**：清单/题目/步骤每项独占一行，挤在一行长段里读者无法定位
- 嵌套不超过两层：需要三层时说明内容该拆成新章节
- 加粗只用于核心术语与关键结论，全文加粗等于没有加粗
- 块引用留给三类用途：定位句（开头）、警告（`> `）、总结（`> `）

## 4. 链接与代码规范

### 4.1 链接规范

- **相对链接优于绝对链接**：仓库内部跳转用 `./01-xxx.md`，克隆、改名、换域名后依然可用
- **路径空格必须 `%20` 编码**：`[文档](./图 1.png)` 在多数平台断链，必须写成 `./图%201.png`
- **锚点与标题逐字符一致**：中文锚点保留汉字、去掉标点；改标题后全量跑链接检查
- 裸 URL 用 `<...>` 包裹或转成文字链接；外链给出「读者为什么该点」的一句话说明
- 参考来源的每条给**可点击超链接 + 简短说明**，而不是纯文字罗列

### 4.2 行内代码的使用边界

行内代码（反引号）承载三类内容：**代码标识符**（`ObjectMapper`）、**命令**（`pip install`）、**文件路径**（`.github/workflows/`）。不要用它做「强调」——需要强调用加粗，两者语义不同。

## 5. 反模式清单

| 反模式 | 问题 | 替代做法 |
|--------|------|---------|
| 开场白铺垫（「在当今时代…」） | 浪费读者时间 | 直接给定位句 + 正文 |
| 结尾客套（「希望对你有帮助」） | 无信息量 | 写到最后一个知识点直接结束 |
| 标题层级跳跃 | 大纲/样式错乱 | 逐级递进 |
| 无语言代码块 | 无高亮、难检索 | 始终标语言 |
| 用表格堆砌论述 | 逻辑断裂、难读 | 论述优先，表格限对比/速查 |
| 一段话塞 5 个要点 | 无法定位 | 列表逐行展开 |
| 全文加粗 | 强调失效 | 只标核心术语与结论 |
| 截图代替文本 | 不可搜索、不可复制、AI 读不到 | 文本 + 代码块呈现 |
| 复制粘贴造成的重复内容 | 双份维护、必然漂移 | 合并 + 链接 |
| 相对路径带空格未编码 | 链接失效 | `%20` 编码 |
| 版本信息缺失（「最新版本」） | 半年后即过期 | 写明版本号与日期 |

---

> **核心要点**：规范的本质是「降低读者的认知成本」。结构规范保证导航顺畅，中文排版保证阅读流畅，呈现规范保证信息密度，链接规范保证可达性。写好之后用两条自检收尾：**读者无需找作者能否看懂、能否复现、能否排错**；以及**把文档在 GitHub 与纯文本编辑器各读一遍**。
