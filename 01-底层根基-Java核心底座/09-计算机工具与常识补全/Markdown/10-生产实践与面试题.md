## 1. 生产避坑清单

### 1.1 渲染类（跨平台一致性）

- 表格前不空行、分隔行缺失 → 表格不渲染（最高频）
- 列表后接代码块，缩进没算上标记宽度（`- ` 是 2 格、`1. ` 是 3 格）→ 代码块脱离列表
- 全文缩进不统一（2 格 vs 4 格）→ 4 格行意外变成缩进式代码块
- 相对链接路径带空格未编码 → `%20` 编码是硬要求
- 中文锚点靠脑补推算 → 含标点的标题必须实际点击验证
- 用 HTML 标签搭布局 → 各平台宽松度不同，纯 Markdown 结构最稳

### 1.2 协作类（团队一致）

- 不配置 lint 与格式化 → 全仓库风格五种写法，diff 噪声淹没实质修改
- 规则全开或全关 → 正确姿势是「保留防错规则 + 豁免风格规则并注明理由」
- frontmatter 字段各写各的 → 用 schema（内容集合）约束，构建时校验
- 复制粘贴生成重复内容 → 双份必然漂移，合并到一处 + 链接
- 参考来源写「官网」不写链接与日期 → 半年后无从复核

### 1.3 工程类（发布与安全）

- CI 用 `npx` 在线拉最新版 lint → 规则升级导致全仓库莫名标红，必须锁版本
- 外链检查放进每次 PR 流水线 → 对方站点抖动导致误报，外链移到定期任务
- 用户输入的 Markdown 直接渲染 → 三层防护（转义原始 HTML + sanitize 白名单 + CSP）缺一不可
- Agent 读取的文档不设防 → 间接提示注入面，外部内容按不可信数据处理

## 2. 文档仓库治理实战

规模化（千篇级）文档仓库的四个核心机制，本知识库（5,700+ 篇）的真实方案：

**分层治理**：根级文档套 markdownlint 严格规则（豁免 MD013/MD024/MD033/MD034/MD041/MD060 等中文场景规则并在配置注释理由）；知识库正文走自有规范（11 篇模板、参考来源带超链接、提示块无 emoji），不纳入通用 lint 全量扫描——两套规则各自稳定，互不打架。

**供应链硬化**：CI 中第三方 action 锁镜像 digest（`@sha256:...`），npm 依赖走 lockfile + 缓存。文档仓库的流水线常年无人维护，「锁」是半年后还能跑绿的前提。

**离线确定性**：仓库内相对链接用离线脚本全量校验（无网络依赖、零抖动）；workflow 手动触发，日常提交不等 CI，本地脚本完成结构校验。

**脚本化自检**：小节编号唯一性（X.Y 不重复不跳章）、围栏代码块闭合、锚点与标题一致性、文档无 emoji——新文档入库前跑一遍，比人工 review 千篇可靠。

## 3. 面试高频题

**Q1：Markdown 和 HTML 是什么关系？为什么不用 HTML 写文档？**

详细版：Markdown 是 HTML 的「子集生成器」——它的解析产物就是 HTML，定位是「写作层」而非「渲染层」。不用 HTML 直接写的原因有三：可读性（`# 标题` vs `<h1>`）、token 效率（AI 场景差 3-5 倍）、工具通用性（纯文本可 diff 可迁移）。需要 HTML 才能表达的排版（精确布局、复杂表格）说明需求已超出 Markdown 边界，应上文档站框架或模板系统。

背诵版：Markdown 是 HTML 的写作层抽象，胜在可读性、token 效率和工具通用性；超出表达能力的需求应换渲染层方案，而不是硬写 HTML。

**Q2：CommonMark 解决了什么问题？为什么十年不发布 1.0？**

详细版：解决的是「同一文档在不同解析器渲染不同」的方言混战：提供严格规范 + 参考实现 cmark + 600 多个测试用例，一致性由用例定义。不发 1.0 是主动选择：0.x 只增不改（向后兼容承诺），测试套件即契约，生态（所有主流解析器）已对齐 0.31.x——版本号 1.0 没有增量价值，破坏性修订反而要付全生态代价。

背诵版：CommonMark 用「规范+参考实现+测试套件」三件套终结方言混战；0.x 只增不改，兼容性由用例定义，1.0 是仪式感不是必需品。

**Q3：Markdown 为什么难解析？**

详细版：三个原因——无形式文法（规范是散文规则）、上下文相关（同一行含义取决于所在块结构）、优先级与回退复杂（`*` 是强调还是列表标记取决于位置）。所以必须两阶段解析：块级阶段行驱动维护块栈，行内阶段用分隔符栈处理强调嵌套。第一版用正则实现是历史原罪，也是后来十年分歧的源头。

背诵版：无文法、上下文相关、优先级复杂，必须两阶段解析（块级行驱动 + 行内分隔符栈），正则实现必然出错。

追问预案：面试官可能追问「惰性延续是什么」——引用/列表内未写标记的续行仍归属当前块，规范强制所有实现一致。

**Q4：Markdown 渲染的 XSS 怎么防？**

详细版：三层——解析层转义全部原始 HTML（GitHub 的 tagfilter 是平台实现）；净化层对输出 HTML 做白名单过滤（DOMPurify / OWASP Java HTML Sanitizer）；CSP 兜底限制内联脚本。原则：用户输入永远不可信，三层全做才有效，只做 `escapeHtml` 等于没做。

背诵版：转义 → sanitize 白名单 → CSP，三层缺一不可。

**Q5：解析器怎么选型？（Java 场景）**

详细版：先定需求——严格合规选 commonmark-java（行为对齐规范、API 简洁）；功能全（表格/脚注/公式混用）选 flexmark-java；前端实时预览用 markdown-it（插件生态）或 marked（轻量）+ DOMPurify。选型变量是「合规严格度、功能扩展集、体积、插件生态」四维，AI 流式场景额外看增量解析能力。

背诵版：严格用 commonmark-java，功能全用 flexmark，前端 markdown-it + DOMPurify；流式场景加增量解析要求。

**Q6：LLM 流式输出的 Markdown 怎么渲染？**

详细版：核心问题是朴素实现在每个 chunk 到达时全量重解析，累计 O(n²)。解法利用 CommonMark 块级按行推进特性：按行缓冲，冻结已完结块只渲染一次，只从最后一个不稳定块 offset 重解析，均摊 O(1)。配套处理：未闭合标记宽容渲染（当普通文本，闭合后升级样式）、光标渲染在解析后文本流末端。

背诵版：增量解析——冻结完结块、只重解析尾部不稳定区，避免全量重解析的二次复杂度；未闭合标记宽容降级。

**Q7：团队文档规范怎么落地？**

详细版：三层次门禁——编辑器层（lint 扩展实时提示）、提交层（pre-commit 检查改动文件）、CI 层（全量校验，不过不合并）。规则策略是「保留防错规则（结构/围栏/文件尾换行）、豁免风格规则（行长度/重复标题）并注明理由」。再用格式化器消灭风格争论，lint 只管格式化管理不到的项（链接有效性、标题结构）。

背诵版：三层门禁 + 规则取舍（防错保留、风格豁免）+ 格式化和 lint 分工，CI 锁版本防规则漂移。

**Q8：AGENTS.md 和 llms.txt 的区别？**

详细版：面向对象不同——AGENTS.md 是**仓库级**、给编码 Agent 的操作指令（构建命令、约定、禁区），层级发现「最近优先」，工厂中立（Linux Foundation），6 万+ 项目采用；llms.txt 是**站点级**、给任意 LLM 的文档索引（H1 + 摘要 + 链接列表 + Optional 区），不是正式标准，约 10% 网站采用。共同点：都是「让 AI 正确消费内容」的约定文件，且都是提示注入面，需按不可信内容防护。

背诵版：AGENTS.md 管仓库内 Agent 操作（指令），llms.txt 管站点文档索引（导航）；一个管「怎么做」，一个管「读什么」。

**Q9：文档站三大框架怎么选？**

详细版：Docusaurus 3 独有内置版本化文档，是它不可替代的场景；VitePress 面向 Vue/Vite 生态，Markdown-first 上手最快；Astro Starlight 是现代工具文档默认解（Lighthouse 满分、组件自由、增长最快）。三者产物都是静态 HTML，部署与迁移成本可控，先选顺手的。

背诵版：要版本化选 Docusaurus，Vue 生态选 VitePress，默认选 Starlight。

**Q10：改了文档标题后怎么保证链接不断？**

详细版：锚点是文档的接口——标题变更等于接口变更。工程做法三层：写作时标题避免标点（锚点可预测）；变更后用链接检查工具（lychee 等）全量扫描相对链接与锚点；CI 中把链接检查设为离线确定性任务（仓库内链接必查，外链定期查）。

背诵版：标题即接口——锚点可预测（标题少标点）+ 变更全量链路检查 + CI 离线校验仓库内链接。

## 4. 答题模板

四类问题的通用框架（面试与文档复盘通用）：

1. **原理题**（Q2/Q3）：定位（解决什么问题）→ 机制（怎么解决）→ 边界（没解决什么）→ 实践影响
2. **方案题**（Q5/Q9）：需求维度拆解 → 候选逐项对照 → 决策依据 → 风险与回退
3. **安全题**（Q4）：威胁模型 → 分层防护 → 每层失效的后果 → 兜底策略
4. **工程题**（Q6/Q7/Q10）：问题量化（复杂度/误报率）→ 方案 → 落地路径（分层/分阶段）→ 验证手段

## 5. 速记表

| 主题 | 一句话结论 |
|------|-----------|
| 标准 | CommonMark 0.31.2 是基线，GFM 0.29 是方言，其他都是平台扩展 |
| 解析 | 块级行驱动 + 行内分隔符栈，两阶段；正则实现必错 |
| 安全 | 转义 + sanitize + CSP 三层；用户输入永不可信 |
| 渲染差异 | 先问「规范定义了没有」，再问「目标平台支持没有」 |
| 性能 | 流式渲染增量解析，避免 O(n²)；解析器按场景选型 |
| 规范 | 防错规则保留、风格规则豁免并注明理由 |
| 门禁 | 编辑器 → pre-commit → CI 三层，锁版本防漂移 |
| 大仓库 | 分层治理 + 离线确定性 + 脚本化自检 |
| AI 生态 | AGENTS.md 管操作指令、llms.txt 管文档索引，人工编写拒绝自动生成 |
| 写作 | 读者无需找作者即可看懂、决策、复现、排错 |

---

> **核心要点**：Markdown 的工程化 = 语法基础 × 渲染原理 × 规范纪律 × 自动化门禁。避坑清单贴在工位上，面试题的口述版背着走，治理方案按仓库规模取用——这套体系的终点不是「会用 Markdown」，而是「让文档成为团队和 AI 都可信赖的资产」。
