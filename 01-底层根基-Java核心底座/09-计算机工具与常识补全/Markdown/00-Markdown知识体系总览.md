# 00 - Markdown 知识体系总览

> Markdown 是程序员的母语式文档格式——2004 年诞生于「让纯文本也能优雅阅读」的个人项目，2026 年已是「人读源码、机器渲染、AI 训练语料」三位一体的通用标记语言。本系列从起源到解析原理、从语法到 AI 时代的 AGENTS.md，一次学透

## 3. 学习路线推荐

```text
快速上手（1 天）：02-核心语法全解 → 06-写作规范与排版实践 → 动手改写一篇 README
工程落地（1 周）：05-文档阅读方法论 → 07-工具链与自动化 → 在项目里配置 markdownlint + CI
深度理解（持续）：01-起源与标准化 → 04-解析原理与渲染机制 → 03-扩展语法与方言 → 09-AI 时代
```

三条路线的分工：快速上手解决「会写」；工程落地解决「写得规范、管得住」；深度理解解决「知其所以然」——为什么同一份文档在 GitHub、Obsidian、VS Code 里长得不一样，为什么规范冻结了十年反而更稳。

## 4. 核心概念速查

| 概念 | 一句话解释 |
|------|-----------|
| **Markdown** | 2004 年 John Gruber 与 Aaron Swartz 创造的轻量标记语言，目标是「纯文本可读，渲染后美观」 |
| **CommonMark** | 2014 年发起的严格规范 + 参考实现，终结方言混战的事实标准（最新 0.31.2） |
| **GFM** | GitHub Flavored Markdown，CommonMark 的严格超集，加表格/任务列表/删除线/自动链接 |
| **CommonMark 是子集** | 合法 CommonMark 文档在 GFM 中一定合法；反之不成立 |
| **方言** | 各平台对规范的扩展实现——GitHub、GitLab、Obsidian、Typora 渲染结果并不完全一致 |
| **frontmatter** | 文件顶部的 `---` 包裹的 YAML 元数据块，被解析器剥离后供站点生成器使用 |
| **mdast / hast** | Markdown 抽象语法树 / HTML 抽象语法树，解析与渲染之间的中间表示 |
| **两阶段解析** | 块级阶段（按行切块）→ 行内阶段（块内解析行内元素），CommonMark 的核心解析模型 |
| **tagfilter** | GFM 安全扩展，转义 `<script>` 等 9 个危险标签，防止渲染 XSS |
| **MDX** | Markdown + JSX，允许在文档中直接使用组件，被 Docusaurus/Next.js 采用 |
| **AGENTS.md** | 面向编码 Agent 的仓库级指令文件，2025-08 由 OpenAI 提出，2025-12 移交 Linux Foundation |
| **llms.txt** | 站点根目录的 LLM 友好索引文件，2024-09 由 Jeremy Howard 提出，被 AI 爬取工具消费 |
| **渲染差异** | 规范未定义区域由各实现自行决定，导致同一文档跨平台表现不同——本体系第 05 篇专治 |
| **流式渲染** | LLM 逐 token 输出 Markdown 的实时渲染问题，需增量解析避免二次复杂度 |

## 5. 一图看懂 Markdown

```text
Markdown 的三重身份

   ┌─────────────┐     解析      ┌─────────────┐
   │  纯文本源码  │ ──────────→  │  渲染后 HTML │
   │  (.md 文件)  │ ←──────────  │  (网页/PDF)  │
   └─────────────┘   人读源码      └─────────────┘
          │                              │
          │ 天然可读                     │ 平台渲染
          ↓                              ↓
   ┌─────────────┐                ┌─────────────┐
   │ Git diff 友好│                │ GitHub 网页  │
   │ 编辑器可编辑 │                │ Obsidian 库  │
   │ LLM 训练语料 │                │ 文档站/幻灯片 │
   └─────────────┘                └─────────────┘

一句话：一份源码，三种用途——人读、机器渲染、AI 消费
```

Markdown 的全部设计取舍都围绕这张图展开：为什么它坚持纯文本（Git diff 与工具通用）、为什么规范要严格（跨渲染器一致）、为什么 AI 时代它地位不降反升（训练语料 + 结构化程度恰到好处）。

### 常见困惑与本系列的对应答案

每个学 Markdown 的人都会撞上几堵墙，这些问题在本系列里都有专篇回答：

- 「为什么我的表格不渲染？」→ 第 02 篇高频陷阱 + 第 05 篇渲染差异调试
- 「为什么 GitHub 上好好的，换到别的平台就乱了？」→ 第 01 篇方言生态 + 第 03 篇兼容策略
- 「规范都说 30 分钟学完，为什么我还写得一团糟？」→ 第 06 篇——语法≠规范，专业文档是一套纪律
- 「解析器那么多，我该用哪个？」→ 第 04 篇选型逻辑（Java 场景给了 commonmark-java / flexmark 对照）
- 「LLM 流式输出的 Markdown 渲染为什么会卡？」→ 第 04 篇增量解析 + 第 09 篇流式渲染工程
- 「AGENTS.md、llms.txt 到底是什么，要写吗？」→ 第 09 篇——2026 年新增的文档发布形态

### 本系列的组织约定

正文 10 篇统一遵守四条约定：每篇约 2000 字聚焦一个主题；篇首定位句说明「这篇解决什么问题」；篇尾「核心要点」是压缩后的结论区（可作为复习入口）；「参考来源」给出可点击的外链与日期，便于核实时效性。阅读时建议先读定位句与核心要点各一遍，再决定是否精读正文。
