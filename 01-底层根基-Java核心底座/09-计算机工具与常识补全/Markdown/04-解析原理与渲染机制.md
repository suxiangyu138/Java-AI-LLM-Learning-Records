## 1. 为什么 Markdown 难解析

Markdown 不是「简单版 HTML」，而是一种解析难度被严重低估的格式，三个结构性原因：

1. **无形式文法**：规范是散文规则集合，不是 BNF/ABNF 文法。解析器无法用「扫描 → 语法分析」的常规路线，只能逐条实现规范中的判定规则（dedent、delimiter run、link reference definition 等）
2. **上下文相关**：同一行文本的含义取决于它所在的块结构。例如 `    code`（4 空格）在段落中只是空格，在列表项内是延续段落，在代码块后是普通内容——脱离上下文的逐行正则注定出错
3. **优先级与回退复杂**：`[foo]: /url` 是链接定义，但写在代码块里就是字面量；`*` 既可能是强调也可能是列表标记，取决于行首位置

原罪在于第一版 `Markdown.pl` 用正则实现。正则无法表达嵌套计数、无法回溯块结构，这套实现缺陷被早期生态照抄，成为十年方言分歧的技术源头。

## 2. 两阶段解析模型

CommonMark 定义的解析架构是所有合规实现的共同骨架：

```text
源文本
   │
   ▼
┌─────────────────┐   块级阶段（block phase）：逐行读取
│  Block Parser    │   维护「未闭合块栈」，判断每行归属于
│  行驱动 · 栈结构  │   哪个块（标题/列表/引用/代码块/段落）
└─────────────────┘
   │  产出：块结构树（叶子节点含原始文本）
   ▼
┌─────────────────┐   行内阶段（inline phase）：对每个叶子块
│  Inline Parser   │   解析强调/代码/链接等行内元素
│  delimiter 扫描   │   用分隔符栈处理嵌套与边界
└─────────────────┘
   │
   ▼
AST（抽象语法树）→ 渲染为 HTML/其他目标
```

两个易被忽略的关键机制：

- **惰性延续（lazy continuation）**：引用块与列表项中未写标记的续行仍归入当前块，规范明确允许——这是「不写 `>` 也是引用」的由来，跨平台必须一致
- **行内分隔符栈**：强调的边界判定（delimiter run 规则）用栈式两遍扫描实现，`*a **b* c**` 这类歧义嵌套的最终结果由规范逐条钉死，不是实现自由发挥

## 3. 解析器实现对比

主流实现按语言与定位分四类：

| 解析器 | 语言 | 体积（gzip） | 定位 |
|--------|------|:---:|------|
| cmark / cmark-gfm | C | — | 参考实现，GitHub 生产在用 |
| commonmark.js | JS | 48 KB | 严格 CommonMark，语法树可检查 |
| markdown-it | TS/JS | 53 KB | 插件生态最成熟，规则可配置 |
| micromark | TS/JS | 15 KB | unified 生态底层，规格严格、需自行组装 |
| marked | TS/JS | 较小 | 速度导向，历史上有安全告警 |
| goldmark | Go | — | Hugo 默认引擎，严格 CommonMark |
| flexmark-java | Java | — | Java 生态功能最全（表格/公式/图表 50+ 扩展） |
| commonmark-java | Java | — | 严格 CommonMark，API 简洁，扩展点规范 |

选型逻辑（以 Java 后端为例）：

- **文档渲染服务、需要严格合规**：`commonmark-java`，API 干净、行为与规范对齐，适合「文档解析成 AST 后做二次处理」的场景
- **富功能渲染（表格/脚注/公式/定义列表混用）**：`flexmark-java`，扩展齐全，代价是依赖体积与配置复杂度
- **前端实时预览**：`markdown-it`（插件生态）或 `marked`（轻量），配 DOMPurify
- **流式场景**：`micromark` 的块级按行推进特性可做增量解析（见下节）

```java
// commonmark-java：源码 → AST → HTML，可插入自定义节点处理
Parser parser = Parser.builder().build();
Node document = parser.parse(markdownSource);
HtmlRenderer renderer = HtmlRenderer.builder()
        .escapeHtml(true)          // 转义原始 HTML，防 XSS 的第一道闸
        .build();
String html = renderer.render(document);
```

> **解析器 ≠ 安全**：`escapeHtml(true)` 只转义原始 HTML 标签，若文档内容来自用户输入，仍需在输出侧做 sanitize。解析器的职责是「理解结构」，不是「信任内容」。

## 4. 渲染管线与 AST 生态

现代工具链普遍采用「多段 AST 管线」：

```text
Markdown 源码 → [解析] → mdast（Markdown 语法树）
              → [转换] → hast（HTML 语法树）
              → [序列化] → HTML 字符串 / React 组件树 / PDF
```

JavaScript 生态的 unified/remark/rehype 把这条管线标准化：插件挂在任一阶段（把 `##` 标题加锚点、给代码块加高亮、把链接改写为卡片），**一次性构建出文档站、目录、搜索索引**。这是文档站框架（VitePress/Docusaurus/Astro）的底层原理，也是「Markdown 不只是文本，还是数据管道输入」的含义。

AST 也解释了锚点生成原理：标题节点的纯文本 → 小写 → 去标点 → 空格转 `-`，产出的即为 URL 锚点。中文标题的锚点保留汉字、去掉标点，这正是「中文锚点有时猜不准」的原因——带标点的标题锚点必须实际渲染验证。

## 5. 流式渲染与安全渲染

### 5.1 流式增量解析

LLM 逐 token 输出 Markdown 已成为标配场景，朴素实现有个隐藏陷阱：**每个 chunk 到达时全量重新解析**，单次成本线性增长、整个流累计呈二次复杂度（O(n²)）。2026 年 deepseek-harness 的架构记录给出了标准解法：

1. 利用 CommonMark 块级解析「按行推进」的特性，按行缓冲后触发解析
2. 只保留最后 1-2 个块为「不稳定区」（可能被新行改写），之前的块冻结
3. 冻结块只渲染一次，重解析只从最后一个冻结块的 offset 开始——整个区间均摊 O(1)

这个思路对所有实时 Markdown 渲染（对话界面、协作文档、日志面板）都适用。

### 5.2 安全渲染三道闸

Markdown 渲染是 XSS 的经典入口，防护分层：

1. **解析层**：`escapeHtml` 转义全部原始 HTML；GitHub 的 tagfilter 是这一层的平台实现（转义 9 个危险标签）
2. **净化层**：输出 HTML 过 DOMPurify（前端）或 OWASP Java HTML Sanitizer（后端），白名单制过滤标签与属性
3. **内容安全策略**：CSP 头限制内联脚本，作为最后兜底

> **防护原则**：用户输入永远按「不可信」处理——允许 Markdown 子集、禁止原始 HTML、净化输出，三件事全做才算安全。只见 `escapeHtml` 就上线，等于把 XSS 留给下一位维护者。

---

> **核心要点**：Markdown 解析 = 块级（行驱动、栈结构）+ 行内（分隔符栈）两阶段，所有合规实现共享这套模型。渲染管线经 mdast → hast 到目标格式，是文档站的底层原理。工程上记住三点：解析器选型对齐场景、流式渲染用增量解析避免 O(n²)、用户内容必须三层防护。
