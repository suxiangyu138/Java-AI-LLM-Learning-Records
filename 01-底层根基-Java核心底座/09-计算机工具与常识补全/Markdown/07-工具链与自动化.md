## 1. 编辑器选型

2026 年的编辑器格局按「工作流」而非「功能列表」划分：

| 编辑器 | 定位 | 预览方式 | 价格 | 适用场景 |
|--------|------|---------|:---:|---------|
| **VS Code** | 代码编辑器 + 扩展 | 分屏预览（`Ctrl+K V`） | 免费 | 与代码同仓库的文档、README、技术写作 |
| **Typora** | 专注写作 | 内联 WYSIWYG | 约 $14.99 | 长文、课程材料、方案文档 |
| **Obsidian** | 个人知识库 | 分屏 + 双链图谱 | 个人免费 | 长期笔记、Zettelkasten、知识库 |
| **MarkText** | Typora 开源替代 | 内联 WYSIWYG | 免费 | 不想付费的 WYSIWYG 场景 |
| **Joplin** | 跨端笔记 | 分屏 | 免费 | 多设备同步笔记 |

选型逻辑：**文档跟着代码走就选 VS Code**（Git 集成、全局正则替换、终端一体）；**纯写作选 Typora**（零干扰、导出 PDF/DOCX/EPUB 一条龙）；**个人知识积淀选 Obsidian**（双链、Dataview 把笔记变数据库）。三者不互斥——「Typora 起草 → Obsidian 沉淀 → VS Code 随项目发布」是常见组合，纯文本格式决定了切换成本只是一个下午。

VS Code 必装扩展：**Markdown All in One**（快捷键/自动目录）、**Markdown Preview Enhanced**（导出/图表）、**markdownlint**（实时规范提示）。

## 2. Lint 规则体系

**markdownlint** 是事实标准（Node.js，基于 micromark 解析器），定义 MD001–MD060 编号规则，社区口径 53 条。规则按性质分四类：

| 类别 | 代表规则 | 说明 |
|------|---------|------|
| 结构类 | MD001 标题层级递增、MD025 单一 H1、MD041 首行 H1 | 影响大纲与导航 |
| 排版类 | MD009 行尾空格、MD012 连续空行、MD013 行长度、MD047 文件尾换行 | 影响渲染与 diff |
| 语法类 | MD033 内联 HTML、MD034 裸 URL、MD040 代码块语言、MD046 代码块风格统一 | 影响一致性与可移植性 |
| 表格类 | MD055/MD056/MD058/MD060 管道符风格 | 统一表格书写 |

配置文件 `.markdownlint.json`（或 cli2 的 `.markdownlint-cli2.yaml`）按需开关。**规则不是越多越好**——中文技术文档里的高频豁免：

- `MD013`（行长度）：中文无自然空格断行，长链接与表格必然超长，通用做法是关闭
- `MD024`（重复标题）：多章节都有「常见问题」「实践清单」是合理结构
- `MD033`（内联 HTML）：徽章、`<kbd>`、折叠块需要
- `MD034`（裸 URL）：参考来源条目常直接给出

原则：**保留能防错的结构规则（MD001/MD040/MD047），豁免与本项目风格冲突的排版规则**，并在配置文件中注释豁免理由。

## 3. 格式化与新一代工具

### 3.1 格式化工具

- **Prettier**：最流行的通用格式化器，Markdown 支持是「顺带能力」，配置项极少（几乎不可调）
- **mdformat**：Python 生态，严格 CommonMark 输出，插件扩展 GFM
- **rumdl fmt / mdlint format**：新一代 Rust 工具内置格式化

格式化与 lint 的分工：**格式化器改文件，linter 定罪**。团队里先上格式化器（消灭风格争论），再用 lint 守住格式化器管不到的规则（标题结构、链接有效性）。

### 3.2 Rust 新势力（2025-2026）

markdownlint 的 Rust 重写版在 2025-2026 集中出现，核心卖点是速度与 LSP：

- **rumdl**：86-88 条规则（含 markdownlint 全部 53 条 + 链接校验/脚注/嵌套围栏扩展），内置自动修复、LSP server、pre-commit、多方言 flavor（mkdocs/mdx/obsidian/pandoc）。2026-02 基准：478 个文件冷启动 **217ms vs markdownlint-cli2 的 2.2s**（约 10 倍）
- **mado**：38 条规则，无自动修复，胜在极快（77ms）
- **markdownlint-rs / mdlint**：提供 `mdlint migrate` 迁移命令，直接读 markdownlint-cli2 配置

判断：**存量项目继续用 markdownlint-cli2**（生态最稳、编辑器集成最广）；**新项目或大仓库可试 rumdl**——兼容 markdownlint 配置与规则编号，迁移成本低，LSP 与速度收益明显。

## 4. CI 集成与质量门禁

### 4.1 门禁三层次

文档质量门禁按「越靠左越便宜」原则分三层：

1. **编辑器层**（实时）：VS Code markdownlint 扩展即时标红，写的时候就改
2. **提交层**（pre-commit）：husky + lint-staged 或 pre-commit 框架，只检查改动文件
3. **CI 层**（PR/手动的最后闸门）：全量校验，不过不合并

### 4.2 GitHub Actions 最小实现

```yaml
name: docs-check
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npx markdownlint-cli2 "docs/**/*.md"   # 格式规则
      - run: npx lychee --offline "docs/**/*.md"    # 相对链接检查
```

两个工程细节决定流水线是否「可长期存活」：

- **依赖锁版本 + 缓存**：`npm ci` 配合 lockfile 精确锁定，避免 `npx` 在线拉新版导致规则漂移（规则一升级，全仓库莫名标红）
- **链接检查区分线上/离线**：外链检查受网络与对方站点影响必然抖动，CI 里默认只查仓库内相对链接（离线、确定性），外链检查放到定期任务里跑

## 5. 大规模文档仓库治理

以本知识库（5,700+ 篇中文技术文档）的真实方案为例，四个治理决策：

**决策一：分层治理，不搞一刀切。** 根级文档（README/CHANGELOG/CONTRIBUTING/CLAUDE.md）套用 markdownlint 严格规则（仅豁免 8 条中文场景规则并注明理由）；知识库正文遵循自有规范（11 篇模板、单篇 2000 字、参考来源格式），不纳入 markdownlint 全量扫描——通用规则会与体系规范互相打架，全量标红等于没有门禁。

**决策二：供应链硬化。** CI 中第三方 action 用**不可变 digest 锁镜像**（`docker://rhysd/actionlint@sha256:...`），npm 依赖走 lockfile + 缓存。文档仓库的 CI 常年无人维护，锁版本是「半年后还能跑绿」的前提。

**决策三：可离线、可复现。** 链接检查用纯离线脚本校验相对链接完整性，杜绝网络抖动误报；workflow 改为手动触发——日常提交不等待 CI，结构+字数双校验在本地脚本完成。

**决策四：脚本化自检。** 大仓库的质量靠脚本而非肉眼：中文字数统计（门禁区间 2000-2500）、小节编号唯一性校验、锚点与标题一致性检查、代码围栏闭合校验。新文档入库前跑一遍，比人工 review 千篇文档可靠得多。

> **治理心法**：文档仓库的 CI 与代码仓库目标不同——代码 CI 求「严格全量」，文档 CI 求「长期可跑、低误报、关键项必拦」。宁可规则少而稳定，不要规则多而常年飘红被无视。

---

> **核心要点**：工具链三段式——编辑器解决体验、lint + 格式化解决一致性、CI 解决不可回退。规则取舍原则是「保留防错规则、豁免风格规则并写明理由」。大仓库治理的关键词：分层、锁版本、离线确定性、脚本自检。
