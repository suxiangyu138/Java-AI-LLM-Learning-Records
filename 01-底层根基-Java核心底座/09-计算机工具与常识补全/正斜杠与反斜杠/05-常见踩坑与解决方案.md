## 2. 坑 1：8 个反斜杠的传说

### 2.1 事故现场

> ⚠️ 传说：替换一个反斜杠需要 8 个反斜杠——**是真的，在「嵌套正则」场景下**：

```java
// 场景：用正则把 Windows 路径中的 \ 替换为 /
String path = "D:\\data\\orders.csv";

// 第一层：字符串中的 \ 需要转义
"\\"          // 表示一个 \ 字符

// 第二层：replaceAll 的第一个参数是正则
// 正则中匹配字面 \ 需要写成 \\
// 字符串再转义一次 → "\\\\"

path.replaceAll("\\\\", "/");    // ✅ 4 个反斜杠（两层转义）
// 输出：D:/data/orders.csv

// 第三层：如果目标替换字符串含 $ 或 \（replaceAll 替换串也有特殊含义！）
path.replaceAll("\\\\", "\\\\"); // 想把 \ 换成 \\ → 替换串也要转义
// 替换串中 \\ 表示一个字面 \ —— 想要两个 \ 得写 \\\\
// → 总计 8 个反斜杠：正则 4 个 + 替换串 4 个
```

### 2.2 优雅解法

```java
// ✅ 解法 1：用非正则 API（replace 不做正则解析）
path.replace("\\", "/");          // 字符串替换，零转义陷阱！

// ✅ 解法 2：Java 9+ Matcher.quoteReplacement
path.replaceAll("\\\\", Matcher.quoteReplacement("\\"));

// ✅ 解法 3：NIO Path（根本不用替换）
Paths.get(path).toString();       // 系统格式
Path.of(path).normalize().toString();
```

> 🎯 **结论**：**能不用正则就不用**——`String.replace`（非正则）处理字面替换；只有真正需要正则时才面对 4 个反斜杠；遇到 `$`/`\` 替换串再用 `quoteReplacement`。

## 3. 坑 2：正则双重转义

### 3.1 事故现场

```java
// 需求：判断字符串是否包含反斜杠
String path = "D:\\data";

// ❌ 错误写法
path.matches(".*\\..*");      // 匹配的是「任意字符 + 点」？还是 \？
// 正则 \\ = 匹配字面 \？ 在 Java 字符串中 "\\" 就是 \ 字符，
// 所以 ".*\\..*" 的正则是 .*\.  —— \. 匹配的是「点」！
// 结果：完全不是想要的行为

// ✅ 正确写法（正则匹配字面 \ 需要 \\，字符串再转义 → \\\\）
path.matches(".*\\\\..*");    // 正则 .*\\..* = 任意字符+反斜杠+任意字符
```

### 3.2 各语言对照

| 语言 | 匹配 `\` 的正则写法 | 说明 |
|------|-------------------|------|
| Java | `"\\\\"` | 字符串转义 + 正则转义 |
| Python | `r"\\"` | 原始字符串只需正则层 |
| JS | `/\\/` 字面量 | 正则字面量免字符串层 |
| JS（字符串） | `"\\\\"` | new RegExp 时需双层 |

```python
# Python 对比（原始字符串拯救世界）
import re
path = r"D:\data"
re.search(r"\\", path)         # ✅ r"\\" = 正则 \\ = 匹配字面 \
re.search("\\\\", path)        # ⚠️ 等价但难读（双重转义）
re.split(r"[\\/]", path)       # ✅ 字符类写法更优雅
```

> 🎯 **结论**：**优先字符类 `[\\/]`（同时匹配两种斜杠，转义最少）；Python 永远用 `r"..."`；JS 用正则字面量 `/.../`**。

## 4. 坑 3：Linux 上的 Windows 路径

### 4.1 事故现场

```text
事故：代码在 Windows 上开发正常，部署到 Linux 直接崩

❌ 代码：File file = new File("D:\\data\\orders.csv");
→ Linux 上：创建了一个名为 D:\data\orders.csv 的文件/目录？
→ 实际上：new File 不会报错，但文件根本不存在 → NPE/FileNotFound

❌ 代码：String path = "C:\\Users\\admin\\logs";
→ Linux 上没有 C:\Users → 读写失败
```

### 4.2 根因与解法

```text
根因：Windows 开发环境「能用」掩盖了硬编码路径问题
├── Windows 上跑：路径恰好存在 → 看似正常
├── Linux 上跑：路径不存在 → 崩溃
└── 本质：硬编码绝对路径 + 反斜杠 = 双重跨平台炸弹

解法（按优先级）：
├── ① 相对路径：new File("data/orders.csv")（基于工作目录）
├── ② 配置注入：${DATA_DIR}（部署时指定）
├── ③ 路径库：Paths.get("data", "orders.csv")（自动分隔符）
└── ④ 双平台 CI：Windows + Linux 矩阵测试（早发现）
```

> ⚠️ **补充坑**：即使在 Windows 上，硬编码 `C:\Users\张三` 也换机器就挂——**绝对路径 + 用户名 + 中文目录 = 三重脆弱**。配置文件、上传目录、日志目录全部外部注入。

## 5. 坑 4：URL 中的反斜杠

### 5.1 事故现场

```java
// 需求：把文件路径拼进 API 请求
String filePath = "D:\\data\\report.pdf";

// ❌ 错误：直接拼接
String url = "https://api.example.com/files/" + filePath;
// 结果：https://api.example.com/files/D:\data\report.pdf
// → 服务器 404 / 参数解析错误 / 甚至 URL 非法

// ✅ 正确：先转正斜杠 + URL 编码
String normalized = filePath.replace("\\", "/");      // D:/data/report.pdf
String encoded = URLEncoder.encode(normalized, StandardCharsets.UTF_8);
String url = "https://api.example.com/files/" + encoded;
```

### 5.2 各场景 URL 处理

```java
// Spring 返回文件下载（路径转 URL 安全）
String downloadUrl = "/api/files/" + URLEncoder.encode(filename, "UTF-8");

// JavaScript 前端（浏览器自动处理 /）
const url = `/api/files/${encodeURIComponent(filename)}`;

// 注意：路径参数中的 / 需要 %2F
// /api/search?path=a/b     → 服务器看到 path=a 和 b 两部分？
// /api/search?path=a%2Fb   → path 整体是 a/b ✅
```

> 🎯 **结论**：**拼 URL 前：`\` → `/`（replace），再 URL 编码；路径型参数中的 `/` 编码为 `%2F`**。

## 6. 坑 5：Docker 挂载路径失败

### 6.1 事故现场（Windows 上 Docker）

```text
事故：Windows 上 docker run -v C:\data:/app/data 报错

❌ docker run -v C:\data:/app/data myapp
→ 报错：Docker Desktop 无法解析 C:\data（反斜杠被当转义）

✅ Windows PowerShell 中：
docker run -v C:/data:/app/data myapp        # 正斜杠 ✅
docker run -v "C:\data:/app/data" myapp      # 引号包裹 ✅
docker run -v "$(pwd):/app/data" myapp       # 变量 ✅

✅ Docker Compose（yaml 中统一 /）：
services:
  app:
    volumes:
      - ./data:/app/data          # 相对路径 + / ✅
      - C:/data:/app/data         # 绝对路径用 / ✅
```

### 6.2 Git Bash 中的 Docker

```bash
# Git Bash 中 Windows 路径被转换问题
# ❌ docker run -v C:\data:/data ...  （\c 被解释）
# ✅ MSYS_NO_PATHCONV=1 docker run -v C:\data:/data ...  （禁用转换）
# ✅ 或统一正斜杠
docker run -v C:/data:/data ...
```

> 🎯 **结论**：**Docker 挂载统一 `/`（`C:/data` 或 `./data`）；PowerShell 中可用引号包裹反斜杠路径；Git Bash 异常时加 `MSYS_NO_PATHCONV=1`**。

## 7. 坑 6：脚本换行与 BOM 的连锁反应

### 7.1 事故现场

```text
事故：Windows 上编辑的 .sh 上传 Linux 执行报错

❌ bash deploy.sh
→ deploy.sh: line 1: $'\r': command not found

根因：Windows 编辑器保存为 CRLF 换行 + 可能带 BOM
├── CRLF：每行末尾的 \r 被 bash 当作命令
├── BOM：文件头的 EF BB BF 让 #!/bin/bash 失效
└── 双重问题叠加

✅ 解法：dos2unix deploy.sh    # 转 LF
✅ 预防：.gitattributes 声明 *.sh text eol=lf
✅ 预防：编辑器默认 LF + UTF-8 无 BOM
```

### 7.2 批处理反向事故

```bat
:: Windows 上执行 Linux 风格的 .bat？
:: bat 需要 CRLF（LF 也可能能跑但部分命令异常）
:: 用 unix2dos 转换
```

> 🎯 **结论**：**脚本类文件（.sh/.py 首行 shebang）必须 LF + 无 BOM**——`.gitattributes` 统一声明是团队根治方案。

## 8. 坑 7：配置文件转义

### 8.1 事故现场

```properties
# ❌ application.properties 错误写法
file.upload-path=C:\data\uploads
# → \d \u 被当作转义！实际值变成 C:datauploads（\ 丢失）

# ✅ 正确写法
file.upload-path=C:\\data\\uploads    # 双写
file.upload-path=C:/data/uploads      # 推荐：正斜杠
```

```json
// ❌ JSON 错误（前端拿到的路径不对）
{ "path": "C:\data\app" }     // \d \a 是非法转义 → JSON 解析失败！

// ✅ JSON 正确（\\ 双写）
{ "path": "C:\\\\data\\\\app" }   // 注意：JSON 中 \\ 表示一个 \

// ✅ 更推荐：直接存正斜杠
{ "path": "C:/data/app" }
```

### 8.2 环境变量传递

```text
环境变量传路径（跨平台）：
├── Windows 设置：set DATA_DIR=C:\data（系统设置，无转义问题）
├── Linux 设置：export DATA_DIR=/data
├── 程序读取：System.getenv("DATA_DIR") → 原样读取（无转义）
└── 结论：环境变量是传路径的最佳通道（绕过配置文件转义）
```

> 🎯 **结论**：**配置文件写路径优先 `/`；properties/JSON 必须写 `\` 时双写；传路径用环境变量可完全绕开转义问题**。

## 9. 坑 8：用户输入路径穿越

### 9.1 事故现场

```java
// ❌ 高危：直接拼接用户输入
String filename = request.getParameter("filename");   // ../../etc/passwd
File file = new File(uploadDir + "/" + filename);      // 路径穿越！
// 攻击者可用 ../ 读取/覆盖任意文件（CWE-22 高危漏洞）

// ✅ 安全写法
String safeName = Paths.get(filename).getFileName().toString();  // 只取文件名
Path target = Paths.get(uploadDir).resolve(safeName).normalize();
if (!target.startsWith(Paths.get(uploadDir).toAbsolutePath())) {
    throw new SecurityException("非法路径");
}
```

### 9.2 防护清单

```text
路径安全防护四件套
├── ① basename：只取文件名部分（去掉所有目录）
├── ② normalize + startsWith：校验解析后仍在允许目录
├── ③ 白名单扩展名：.jpg/.png/.pdf 允许，其他拒绝
└── ④ 随机文件名：UUID 命名存储（彻底切断用户可控路径）
→ 金句：用户输入永远不可信——路径拼接前必须净化
```

## 10. 坑 9：Git 换行符与路径

### 10.1 事故现场

```text
事故：Windows 开发 + Linux 部署 → git diff 全是差异

根因：同一文件在 Windows 被存为 CRLF，Linux 为 LF
├── 每次切换平台提交，全文件 diff
├── 合并冲突频发（换行符差异算冲突）
└── 追溯历史困难（每行都被改过）

✅ 根治：.gitattributes 统一声明
*.java   text eol=lf
*.sh     text eol=lf
*.bat    text eol=crlf
*.md     text eol=lf
*.png    binary

✅ 配合：core.autocrlf=true（Windows）/ input（Linux）
```

### 10.2 Git 路径与斜杠

```bash
# Git 命令中的路径：统一 /（git 内部也是 / 语义）
git add src/main/java/App.java        # ✅
git add src\main\java\App.java        # Windows cmd 也能跑（git 兼容）

# 文件名含反斜杠/特殊字符
git add "./weird\\name.txt"           # 转义处理
```

> 🎯 **结论**：**`.gitattributes` 声明换行符策略是团队跨平台协作的第一行配置**；Git 命令路径用 `/`。

## 11. 坑 10：Windows 保留字符

### 11.1 非法文件名

```text
Windows 文件名的保留字符（创建文件时报错）
├── < > : " / \ | ? *     ← 9 个非法字符
├── 保留名：CON PRN AUX NUL COM1-9 LPT1-9
├── 结尾不能是空格或点：file.txt.（非法）
└── 长度限制：完整路径 ≤ 260 字符（长路径需 \\?\ 前缀）

跨平台代码注意：
├── Linux 允许 : 和 *（Windows 非法）→ 同一文件名两平台命运不同
├── 创建文件前清洗：replaceAll("[<>:\"/\\\\|?*]", "_")
└── macOS 注意：文件名大小写不敏感（File.txt 与 file.txt 冲突）
```

### 11.2 中文文件名

```text
中文文件名的跨平台注意
├── 编码：Windows 内部 UTF-16、Linux UTF-8——现代 API 无碍
├── 但 URL 引用必须编码：中文名 → encodeURIComponent
├── 下载响应：Content-Disposition 需要 RFC 5987 编码
└── 结论：中文文件名可以，但传输/存储用编码规范化
```

## 12. 排查方法论

### 12.1 斜杠问题排查三步

```text
遇到斜杠/路径问题，按三步排查：
├── ① 确认环境：这个代码跑在哪个平台？
│   ├── Windows 原生 / Linux / Git Bash / WSL / Docker
│   └── 每环境对 \ 的处理不同（先定位环境）
├── ② 确认场景：这是哪一层？
│   ├── 文件系统（路径分隔符）
│   ├── 网络（URL 只能 /）
│   ├── 字符串（转义）
│   └── 正则（双重转义）
└── ③ 确认写法：对照五场景规则（02 篇）找正确写法
    → 80% 问题在这三步内解决
```

### 12.2 调试工具

```bash
# 看真实路径（不猜）
pwd                    # 当前目录（Linux 语义）
echo $PWD              # 真实路径
cygpath -w /c/data     # Git Bash 转 Windows 路径
cygpath -u 'C:\data'   # Windows 转 Unix 路径

# 看字符串真实内容（不猜转义）
printf '%q' "D:\\data"    # 显示转义后的真实值
python3 -c 'print(repr(r"D:\data"))'   # Python repr 显示真实字符

# 看文件类型（不猜格式）
file xxx
```

## 13. 核心要点

> 🎯 **核心要点**：
> 1. 8 个反斜杠是真的（正则 4 + 替换串 4）——但解法是「别用正则」（`String.replace` 字面替换）
> 2. 正则匹配 `\`：Java `"\\\\"` / Python `r"\\"` / JS `/\\/`；字符类 `[\\/]` 最优
> 3. 硬编码 Windows 路径 + 反斜杠 = 双平台炸弹——相对路径 + 配置注入 + 双平台 CI
> 4. URL 拼路径先 `\`→`/` 再编码；Docker 挂载统一 `/`；脚本必须 LF 无 BOM
> 5. 用户输入路径必须净化（basename + normalize + startsWith）防穿越
> 6. 排查三步：环境 → 场景 → 对照规则；用 `cygpath`/`repr` 看真实值不靠猜
