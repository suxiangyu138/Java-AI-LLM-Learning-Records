## 1. 实战：支付模块端到端设计

**目标**：在一个电商单体中设计支付模块（模块化单体），产出设计文档 + ArchUnit 规则，通过评审。

**① 需求分解**：

```text
需求：支持多种支付方式（微信/支付宝/余额）、支付回调、退款、对账
功能模块：支付发起、支付回调处理、退款、对账查询
变化点（已验证）：支付方式会新增（渠道扩展是确定性变化）
```

**② 边界设计**（理由表）：

```text
├── 支付模块：语义独立（支付领域规则）→ 业务域维度拆分
├── 订单模块：强一致事务（支付与订单状态联动）→ 不拆（模块化单体内部协调）
├── 通知模块：流量差异（回调风暴不拖垮核心）→ 流量维度拆分
└── 对账查询：低频重查询（不抢在线连接）→ 流量维度拆分
```

**③ 接口契约**（节选）：

```java
// api 包：支付模块对外契约
public interface PaymentServicePort {
    PaymentResult initiatePayment(PaymentRequest request);   // 发起支付（同步，返回支付单）
    PaymentResult handleCallback(PaymentCallback callback);  // 渠道回调（异步入口）
    RefundResult refund(RefundRequest request);              // 退款（同步强一致）
    List<PaymentRecord> queryPayments(PaymentQuery query);   // 对账查询
}

// 出站 Port：模块内部定义，基础设施实现
public interface PaymentGatewayPort {
    ChannelResult createChannelOrder(PaymentRequest request); // 渠道下单
    ChannelResult queryChannelStatus(String channelOrderId);
}
```

**④ 内部结构**（依赖向内）：

```text
payment/
├── api/（PaymentServicePort + DTO）
├── application/（PaymentService 用例：编排 + 状态机）
├── domain/（Payment/Refund 领域模型 + 状态流转规则）
└── infrastructure/（Gateway 适配器：微信/支付宝实现 PaymentGatewayPort）
```

**⑤ 边界强制**（ArchUnit）：

```kotlin
// 规则：支付模块外部只能依赖 api 包；内部依赖指向 domain
noClasses().that().resideInAPackage("..payment.internal..")
    .should().dependOnClassesThat().resideInAPackage("..order.internal..")
```

**⑥ 通信设计**：发起支付同步（要立即拿支付单）；回调异步（渠道回调风暴不阻塞主链路）；退款同步（强一致）；通知跨模块副作用用事件（OrderPaid 事件，过去时命名）。

**⑦ ADR 记录**：ADR-001 支付模块边界与订单模块的关系（为什么独立又为什么共享事务边界）。

**⑧ 评审**：四问——最大风险（渠道回调幂等）；最高代价决策（支付单数据模型）；变化局部性（新增支付渠道只动 infrastructure）；规模失效点（回调积压 → 独立线程池/独立队列）。

## 3. 常见设计错误速查

| # | 错误 | 根因 | 解法 |
|---|------|------|------|
| 1 | 按层平铺包结构 | 把分层当组织 | 按功能分包（04 篇） |
| 2 | Controller 写业务逻辑 | 穿透 | 下沉用例层 |
| 3 | 接口 10+ 方法 | 胖接口 | 按使用场景拆（I） |
| 4 | 返回 null/魔法值 | 返回设计缺失 | Optional/异常/结果对象 |
| 5 | 循环依赖 | 依赖方向未控 | 抽共同依赖/依赖倒置 |
| 6 | 跨模块直接调内部类 | 边界未强制 | ArchUnit 规则 + api 包 |
| 7 | 全同步调用链 | 通信选型缺失 | 异步改造（MQ/事件） |
| 8 | 微服务硬拆 | 边界不清就拆 | 回模块化单体（07 篇） |
| 9 | Service 300+ 行 | 职责混杂 | 按职责拆（S） |
| 10 | 无 ADR | 决策无记录 | 关键决策补 ADR |

## 4. 面试三范式

**价值式**：模块级设计解决什么问题？——大型代码库的三大痛点：改一处炸一片（耦合）、新需求不知道放哪（边界不清）、测试写不动（结构不可测）。模块化设计用高内聚低耦合 + 边界强制 + 接口契约解决：变更局部化、定位明确化、测试可行化。2026 共识：模块化单体优先，边界设计先于部署形态。

**技术式**：核心机制？——边界三维度（业务域/流量/变更频率）；SOLID 五原则（D 依赖倒置是解耦关键）；分层依赖方向（禁止穿透/单向/稳定依赖）；接口契约四要素 + Port 落地；ArchUnit 强制边界 + 度量指标（CR≥0.8/CMCD）进 CI；通信选型三维度（一致性/时序/耦合容忍度）。

**生产式**：你踩过什么坑？——按层平铺包导致跨模块调用爆炸（改按功能分包）；Controller 穿透到 DAO（ArchUnit 拦下）；胖接口 15 个方法（按场景拆 3 个）；全同步链路过慢（异步改造）；无 ADR 导致三个月后没人知道为什么这么设计（补 ADR 文化）。

**追问四连**：模块化单体 vs 微服务怎么选？ArchUnit 强制哪些规则？接口版本化怎么做？技术债怎么治理？

## 5. 简历呈现写法

```text
主导支付模块架构设计（模块化单体 + 边界强制）
- 按业务域/流量/变更频率三维度划分模块边界，输出设计文档 + ADR 6 份
- 落地 ArchUnit 架构测试 + CI 门禁，跨模块违规从月均 5 次降至 0
- 设计 Port 接口契约（4 接口 12 方法），新支付渠道接入从 3 天降至 0.5 天
```

要点：量化（违规次数/接入时间）、点名机制（ArchUnit/Port/ADR）、体现决策（模块化单体而非微服务，理由可讲）。**与 L1 简历的差异**：L1 写"能读懂/能落地"，L2 写"能设计/能决策"——决策权是分水岭。
