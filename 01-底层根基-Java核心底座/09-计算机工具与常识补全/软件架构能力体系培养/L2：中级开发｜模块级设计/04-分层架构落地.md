## 1. 分层的本质：依赖方向规则

分层的本质不是"把代码放进几层"，而是**给依赖方向立规矩**：

```text
分层 = 依赖方向规则
├── 上层依赖下层（规则：只能向下）
├── 依赖单向流动（规则：禁止回环）
├── 依赖指向稳定方向（规则：稳定依赖原则）
└── 禁止穿透（规则：每层只与相邻层交互）
```

理解了"分层 = 规则"，三个常见困惑自动解开：**"三层还是四层"不重要**（粒度选择而已）；**"层数越多越好"是误解**（每层都是成本，够用即止）；**"分层架构过时了"不成立**（微服务内部依然是分层，只是换了个名字）。

分层的价值：**变更隔离**（改数据层不动业务层）、**可替换**（换数据库/框架只动一层）、**可测试**（各层独立测试）、**认知负载**（每层职责单一）。

## 2. 经典三层：中小应用的地基

三层架构（表现层 → 业务逻辑层 → 数据访问层）是中小型应用最实用的起点：

```text
表现层（Controller）：HTTP 适配、参数校验、响应组装
业务逻辑层（Service）：业务规则、事务边界、编排
数据访问层（Repository）：数据库交互、持久化

规则：Controller → Service → Repository，禁止跳层
```

三层的好处：结构清晰、上手快、团队共识度高——**适合业务复杂度不高的中小应用**。三层的问题：**中间层容易臃肿**（所有逻辑堆进 Service）；**领域逻辑散落**（业务规则散在 Service 与 Repository 之间）。升级路径：业务复杂后，把 Service 里的领域逻辑下沉为领域层（演进到整洁/DDD 分层）。

## 3. 整洁架构：依赖向内

整洁架构（Clean Architecture）的核心是**依赖规则**：依赖必须向内——实体/用例层不依赖任何外部实现，接口适配与框架在最外层。

```text
外层（框架/数据库/UI）→ 接口适配层 → 用例层（Use Case）→ 实体层
依赖方向：向内，越内越纯（无框架依赖、无 IO）
```

```text
分层示例（按功能组织）：
├── entities/        实体层（纯业务对象，无注解依赖）
├── usecases/        用例层（业务规则；定义 Input/Output Port 接口）
├── adapters/        适配层（Controller 实现 Input Port，Repository 实现 Output Port）
└── infrastructure/  框架层（Spring/JPA/数据库连接等）
—— web 与 persistence 都依赖中间的 services（通过接口），services 不依赖外部
```

整洁架构的价值：**业务核心独立于技术**（换框架/换数据库不碰核心）、**测试友好**（用例层纯 Java 可测）、**复杂度可控**（大型复杂系统的长期可维护）。代价：**初期成本高**（抽象多、样板代码多）——2026 共识：大型复杂系统用，中小应用三层更务实。

## 4. 六边形架构：核心与适配器

六边形架构（Ports & Adapters）与整洁架构同一思想，表达方式不同：**业务核心在中心，所有外部交互（HTTP/DB/消息）都是外围适配器**。

```text
         ┌── 适配器（REST 入站）──┐
         │                       │
外部系统 ─┤  业务核心（领域模型）  ├─ 外部系统
         │    Port 接口          │
         └── 适配器（JPA 出站）──┘

入站 Port：外部如何调用核心（用例接口）
出站 Port：核心如何调用外部（仓储/网关接口）
适配器：把外部技术翻译成 Port 语义
```

六边形与整洁的区别：**表达焦点不同**——整洁强调层与依赖向内，六边形强调"核心与外围"的对称（入站/出站 Port 成对）。适用：**外部交互多样的系统**（同时有 REST/消息/文件三通道）。四层模型案例（Kolors）：接入层（协议适配/鉴权限流）→ 业务逻辑层（工作流编排）→ 领域服务层（限界上下文）→ 数据访问层（Repository）。

## 5. 两条铁律：禁止穿透与单向依赖

无论哪种分层模型，两条铁律不变：

**铁律一：禁止穿透**——每一层只能调用下一层的接口，禁止跳层调用。

```text
违反穿透的典型：
├── Controller 直接调 DAO（跳过 Service/领域）
│   → 无鉴权、无业务校验、无 DTO 转换
├── Service 直接用 JDBC（跳过 Repository）
│   → 数据访问实现侵入业务逻辑
├── 用例层直接 new 框架对象（跳过适配器）
│   → 业务核心被技术绑定
```

**铁律二：依赖单向流动**——依赖不能回环，且指向更稳定的方向。

```text
稳定依赖原则：依赖方向指向更稳定的模块
├── 业务规则（稳定）← 框架（易变）依赖业务
├── 领域模型（稳定）← 数据库实现（易变）
└── 变化快的依赖变化慢的，反过来就错

循环依赖 = 分层失败：A 依赖 B、B 依赖 A
├── 编译/构建层面可能通过（Java 允许），架构层面是缺陷
├── 修复：抽出共同依赖（C 层），或依赖倒置（都依赖接口）
```

**工程落地**：两条铁律要用工具强制（07 篇的 ArchUnit/依赖分析），否则"偶尔跳一层"会逐渐变成常态——架构腐化不是一夜发生的，是每次"图方便跳层"累积的。

## 6. 按功能分包而非按层平铺

2026 年实践共识：**包结构按功能/业务组织，不按层平铺**。

```text
❌ 按层平铺（传统但问题多）：
├── controller/（所有接口）
├── service/（所有服务）
├── repository/（所有数据访问）
└── entity/（所有实体）
问题：改订单功能要跨 4 个包翻找；包内类无业务关联

✅ 按功能分包：
├── order/
│   ├── OrderController       （适配层）
│   ├── OrderService          （用例层）
│   ├── OrderRepository       （出站 Port）
│   └── Order.java            （实体）
├── payment/
│   └── ...（同构）
—— 一个功能的所有代码在一处，边界即包边界
```

按功能分包的价值：**变更定位**（改订单功能去 order 包）、**边界落地**（模块边界 = 顶层包边界，ArchUnit 直接约束）、**团队协作**（功能团队各管各的包）。分层仍然存在——它是包**内部**的依赖方向规则，不是包的组织方式。

## 7. 分层架构的腐化信号

| 信号 | 含义 | 修复 |
|------|------|------|
| Controller 出现业务逻辑 | 层职责漂移 | 下沉到 Service/用例层 |
| Service 直接操作 SQL | 穿透 | 走 Repository/出站 Port |
| 依赖方向反向（下层依赖上层） | 依赖倒置未做 | 抽接口反转依赖 |
| 循环依赖出现 | 分层失效 | 抽共同依赖或依赖倒置 |
| 层间用具体类互调 | 抽象缺失 | 补 Port 接口 |
| "就这一次跳层"发生三次 | 腐化起点 | ArchUnit 门禁拦截 |

**腐化的本质**：分层是规则，规则不强制就会漂移。ArchUnit 等工具把铁律变成测试（07 篇），腐化信号从"评审发现"变成"CI 拦截"——这是 2026 年架构治理的核心实践。

## 8. 练习

1. 用"依赖方向规则"解释分层，说出三条规则
2. 对比三层/整洁/六边形的适用场景
3. 找出你项目的三个穿透案例并修复
4. 把项目的按层平铺包改为按功能分包（小范围试点）
5. 画项目依赖图，找出循环依赖与反向依赖

---

> 🎯 **核心要点**：分层 = 依赖方向规则（禁止穿透 + 单向 + 指向稳定），不是包结构。三种模型同一规则不同粒度：三层（中小应用）、整洁（大型复杂）、六边形（外部交互多样）。包结构按功能组织、分层是包内规则。铁律要用工具强制，腐化是"图方便跳层"累积的——ArchUnit 拦在 CI。
