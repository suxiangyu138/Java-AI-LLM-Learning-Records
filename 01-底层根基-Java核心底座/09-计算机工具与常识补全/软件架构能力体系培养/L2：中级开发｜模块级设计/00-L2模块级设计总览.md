## 1. L2 定位：从看懂到设计

软件架构能力分四层递进：**L1 看懂架构**（能读懂项目结构与调用链）→ **L2 设计模块**（能独立设计一个模块的边界、接口与分层）→ **L3 子系统架构**（多模块协同与子系统划分）→ **L4 全局架构**（系统级权衡与演进）。

L2 的标志性能力三问：

- 新需求来了，你知道**放在哪个模块**、模块边界怎么划
- 你能画出**模块的接口契约**（输入/输出/依赖方向），让同事无歧义实现
- 你的模块**可测试、可替换、变更影响可控**——改一处不炸一片

L2 与 L1 的差异不是"知识更多"，而是**决策权**：L1 理解别人的决策，L2 为自己的模块做决策。毕业标准：独立完成一个中等复杂度模块的设计文档，通过架构评审。

## 4. 与 L1/L3/横向能力的关系

| 体系 | 主题 | L2 的衔接 |
|------|------|-----------|
| L1（看懂架构） | 读代码/读模式/读数据 | L2 的设计能力建立在 L1 的读懂能力之上 |
| 横向通用能力 | 权衡/ADR/C4/评审/技术债 | L2 用横向的评审清单与 ADR 表达设计决策 |
| L3（子系统架构） | 多模块协同 | L2 的模块接口是 L3 子系统协作的砖块 |

**学习顺序**：L1 → 横向（评审/ADR 部分）→ L2 → L3。横向能力贯穿各层——L2 阶段重点用"架构评审"与"ADR"两个工具。

## 6. 核心概念速查

| 概念 | 一句话 |
|------|--------|
| 高内聚 | 模块只因一种原因变化，职责一句话能说清 |
| 低耦合 | 模块间通过接口交互，不依赖实现细节 |
| SOLID | 单一职责/开闭/里氏/接口隔离/依赖倒置 |
| 限界上下文 | DDD 的模块边界：同一名词不同含义就应拆分 |
| 防腐层 | 两个模块"语言"不同时的翻译层 |
| 依赖方向 | 依赖单向流动、指向更稳定的方向 |
| 禁止穿透 | 每层只调下一层接口，禁止跳层 |
| Port 接口 | 用例层定义接口，外部实现依赖倒置 |
| 模块化单体 | 单部署单元 + 严格模块边界（2026 优先） |
| ArchUnit | Java 架构约束测试工具（编译期/CI 强制） |
| Cohesion Ratio | 内聚比：内部调用边/模块节点（理想 ≥0.8） |
| 跨模块调用密度 | CMCD：跨模块调用边指标，CI 门禁用 |
| 接口隔离 | 小而聚焦的接口优于臃肿"胖"接口 |

## 7. 七大常见误区

1. **"模块 = 包"**——包是代码组织，模块是职责边界；包结构可能违反模块边界（按层平铺 vs 按功能分包）
2. **"SOLID 是越多越好"**——机械套用（每个类一个方法、处处留扩展点）会把系统拆碎，原则服务判断
3. **"接口越多越灵活"**——接口是契约也是成本，语义稳定比数量重要
4. **"微服务=模块化"**——2026 共识：小中团队先模块化单体，微服务是痛点驱动的演进而非默认
5. **"边界靠自觉"**——架构原则必须工具强制（ArchUnit/CI 门禁），"大家都遵守"是伪命题
6. **"分层=包结构"**——分层是依赖方向规则，不是 controller/service/repository 平铺包
7. **"依赖倒置=依赖注入"**——DI 是手段，依赖倒置是"高层不依赖低层实现"的方向原则
