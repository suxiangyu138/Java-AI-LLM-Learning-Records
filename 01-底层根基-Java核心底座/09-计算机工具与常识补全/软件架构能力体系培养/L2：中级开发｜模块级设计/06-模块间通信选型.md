## 1. 通信选型的三个决策维度

模块间通信方式的选择，本质是三个维度的权衡：

```text
维度一：一致性需求
├── 强一致（调用方要立即确认结果）→ 同步
├── 最终一致（稍后确认即可）→ 异步

维度二：时序需求
├── 要结果才能继续（下单要拿订单号）→ 同步
├── 不用等结果（发通知/更新统计）→ 异步

维度三：耦合容忍度
├── 可接受直接调用（同模块/强关联）→ 方法调用
├── 需要解耦（跨模块/跨团队/多消费者）→ 消息/事件
```

三个维度组合出的答案就是选型结果——**先回答"要不要同步结果"，再谈具体技术**。选型错误的表现：同步需求用了异步（调用方拿不到结果，业务被迫轮询/补偿）；异步场景用了同步（发通知阻塞主流程，性能被拖累）。

## 2. 同步 RPC：强一致的默认

同步 RPC（同进程方法调用 / 跨进程 gRPC/Dubbo）适合"需要立即返回结果、强一致性"的场景：

```text
适用场景：
├── 下单要立即拿订单号 → 订单模块同步调用
├── 登录要立即验证 → 认证模块同步调用
├── 查询依赖另一模块的数据 → 同步读取

同步 RPC 的技术形态：
├── 同进程：直接方法调用（经 Port 接口，05 篇）
├── 同进程解耦：Spring 事件/领域事件（进程内异步）
├── 跨进程：gRPC/Dubbo（内部服务，性能好）
└── 跨语言：REST（兜底，见下节）

同步的代价：
├── 调用链延迟 = 各环节延迟之和（链路越长越慢）
├── 依赖可用性：被调方挂 → 调用方失败（需要超时/熔断/降级）
└── 级联故障：A→B→C，C 挂 → B 挂 → A 挂
```

**同步通信的工程底线**：超时必设（防无限等待）、熔断必配（防级联）、降级预案（被调方挂时的兜底）。同步通信的可靠性工程（超时/重试/熔断）见微服务相关体系，L2 阶段要建立"同步 = 依赖可用性"的意识。

## 3. REST/HTTP：开放与跨语言

REST 是**跨语言、跨团队、对外开放**的通信形态：

```text
适用场景：
├── 对外开放 API（第三方/前端）
├── 跨语言服务（Java ↔ Go/Node）
├── 跨团队边界（团队 A 的服务被团队 B 消费）
└── 低频调用（性能要求不高）

REST 的优势：
├── 语言无关（HTTP 标准）
├── 生态成熟（网关/负载均衡/监控全套）
├── 调试容易（curl/Postman/APIFox）
└── 文档化（OpenAPI/Knife4j 直接对接）

REST 的代价：
├── 性能开销（序列化 + HTTP 层开销）
├── 接口治理成本（版本/文档/兼容）
└── 弱类型（字段错误运行时才发现）
```

**选型判断**：同一组织内的高性能内部调用用 RPC（gRPC/Dubbo），跨边界/跨语言/对外用 REST。内部"为了将来开放"提前上 REST 是过度设计——开放时再暴露网关层即可。

## 4. 消息队列：异步削峰

消息队列（MQ）解决**异步、削峰、可靠性**三类问题：

```text
适用场景：
├── 削峰：秒杀订单量激增 → 消息排队，消费端按能力处理
├── 解耦：下单后要发通知/更新库存/记账 → 发消息，各消费者独立
├── 可靠性：任务失败可重试（消息不丢，消费失败回队列）
└── 异步链路：报表生成/邮件发送（不阻塞主流程）

MQ 的关键属性（选型三件套）：
├── 可靠性：消息不丢（生产确认 + 消费确认）
├── 顺序性：局部有序（同 key 消息有序）
├── 幂等性：消费端幂等（重复消费无害）——消费者必做
└── 积压处理：消费能力 < 生产速度 → 扩容消费者/分区

MQ 的代价：
├── 最终一致（消息到达有延迟，两端状态短暂不一致）
├── 运维复杂度（集群/监控/积压告警）
└── 调试困难（链路跨进程，问题定位要链路追踪）
```

**MQ 的铁律**：消费端幂等必做（消息可能重复投递）；积压监控必配（消费滞后是故障前兆）。MQ 的深度知识（可靠性/顺序/死信）见消息队列体系，L2 只需要掌握选型判断与幂等纪律。

## 5. 事件驱动：一对多与解耦

事件驱动（Event-Driven）是**一对多通知**与**最大解耦**的形态：

```text
适用场景：
├── 一对多：订单创建 → 多个模块都关心（通知/库存/分析）
├── 演进解耦：新消费者加入不影响发布者（发布者不知道谁在听）
├── 跨模块副作用：订单状态变 → 发布事件，副作用由监听者处理
└── 领域事件：领域模型内的事件（DDD 的事件驱动）

事件驱动 vs 消息队列：
├── 消息队列：生产者明确"发给谁"（点对点/队列语义）
├── 事件驱动：发布者不关心谁消费（发布/订阅语义）
└── 实现上常共用 MQ/消息中间件，语义不同

事件驱动的纪律：
├── 事件命名：过去时（OrderCreated 而非 CreateOrder）——事件是"已发生的事实"
├── 事件内容：携带必要数据（订单 ID + 关键字段），不携带大对象
├── 事件版本：事件结构会变，带版本字段
└── 事件风暴排查：发布者与消费者的状态一致性要可追踪（幂等 + 补偿）
```

**事件 = 事实记录**：事件驱动把"命令"（要做什么）与"事件"（已发生什么）分开——发布者只管记录事实，消费者自己决定反应。这是跨模块副作用（通知/统计/级联更新）最干净的解耦方式。

## 6. 决策表与组合使用

```text
快速决策表：
┌─────────────┬──────────────────┬──────────────────┐
│ 需求         │ 同进程           │ 跨进程           │
├─────────────┼──────────────────┼──────────────────┤
│ 强一致要结果 │ 方法调用(Port)   │ RPC/gRPC/Dubbo   │
│ 开放/跨语言  │ —                │ REST             │
│ 异步削峰     │ 进程内事件       │ 消息队列         │
│ 一对多通知   │ 领域事件         │ 事件总线/MQ      │
└─────────────┴──────────────────┴──────────────────┘

组合示例（下单链路）：
├── 下单验证：同步（订单模块 → 用户模块，RPC/方法调用）
├── 库存扣减：同步强一致（重要）或消息最终一致（可接受延迟）
├── 发通知/统计：异步（消息/事件，不影响主链路）
└── 风控检查：异步事件（不阻塞下单，事后处理）
```

**组合的工程原则**：同一条业务链路上，**强一致环节用同步、可容忍延迟的用异步**——全同步链路慢且脆弱，全异步链路复杂且一致性难。混合使用是常态，决策表是起点不是终点。

## 7. 通信的工程代价

选择通信方式的隐性代价常被低估：

| 代价 | 同步 | 异步/MQ/事件 |
|------|------|--------------|
| 延迟 | 链路累加 | 引入 MQ 一跳延迟 |
| 可用性依赖 | 被调方可用性 | MQ 可用性 |
| 一致性 | 强一致简单 | 最终一致要补偿 |
| 调试 | 链路追踪 | 更难（跨进程） |
| 测试 | 简单 | 契约/集成测试成本 |

**代价最小化原则**：**能同进程方法调用就不跨进程**——模块化单体（07 篇）的核心价值之一就是把大部分通信留在进程内方法调用，跨进程只留给真正需要独立部署的边界。通信方式的选择要"够用即可"，每多一种通信形态，系统就多一套复杂度。

## 8. 练习

1. 用三维度（一致性/时序/耦合）分析你项目的三个跨模块调用
2. 给一个"下单 → 扣库存 → 发通知"链路设计通信方案
3. 对比消息队列与事件驱动的语义差异（举一个混淆案例）
4. 为你的模块设计幂等策略（消费重复消息怎么办）
5. 评估：把模块化单体中的 RPC 改回方法调用会带来什么

---

> 🎯 **核心要点**：通信选型 = 三维度决策（一致性/时序/耦合容忍度）→ 四形态（同步 RPC 强一致、REST 开放跨语言、MQ 异步削峰、事件一对多解耦）。工程底线：同步必配超时熔断、MQ 消费必幂等、事件是"已发生的事实"（过去时命名）。代价最小化：能进程内方法调用就不跨进程——模块化单体优先。
