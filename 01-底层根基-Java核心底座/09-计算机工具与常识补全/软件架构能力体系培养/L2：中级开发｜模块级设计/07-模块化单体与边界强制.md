## 1. 模块化单体：单部署 + 严格边界

模块化单体（Modular Monolith）的定义：**单一可部署单元，内部按模块严格划分边界**——模块之间像微服务一样有清晰接口与依赖规则，但共享一个进程、一个数据库、一次部署。

```text
模块化单体结构：
├── 一个可部署单元（一个 Jar/War/镜像）
├── 内部模块（限界上下文，03 篇的边界）
│   ├── 模块 A（订单）← 模块间只能通过模块 API 交互
│   ├── 模块 B（支付）
│   └── 模块 C（通知）
├── 模块 API：公开接口（05 篇 Port）
└── 共享基础设施：数据库/消息/日志（按需隔离）

边界规则：
├── 禁止跨模块直接访问对方内部类/数据
├── 禁止跨模块直接访问对方数据库表
├── 跨模块副作用用事件（06 篇）
└── 模块依赖方向单向（04 篇铁律）
```

**与"普通单体"的区别**：普通单体是"一个大 Classpath 随便互相调"；模块化单体是"一个进程内模拟微服务边界"。与微服务的区别：**部署单元一个 vs 多个**——这是所有权衡的根源。

## 2. 为什么模块化单体优先（2026 共识）

2026 年实践共识明确：**模块化单体是大多数团队的默认起点**，微服务是痛点驱动的演进而非默认架构。

```text
模块化单体的优势：
├── 简单性：一次部署、一个进程、一个日志流
├── 事务一致：跨模块事务在同一数据库（强一致简单）
├── 开发效率：本地启动一个应用即可开发调试
├── 重构成本低：模块边界错误改起来快（进程内）
└── 性能好：模块间通信是方法调用（无网络开销）

微服务的优势（模块化单体缺的）：
├── 独立扩展：只扩热点模块
├── 独立部署：高频模块独立发版
├── 技术异构：不同模块不同技术栈
└── 团队自治：团队边界 = 服务边界
```

**决策判断**：需要独立扩展/独立部署/团队自治了吗？没有 → 模块化单体；出现明确痛点（某个模块扩展受限、发版互相拖累）→ 评估抽取微服务。**模块化单体不是"过渡态"而是"终态之一"**——很多系统永远不需要微服务，模块化单体就是最佳形态。

## 3. 模块化单体的边界规则

边界规则的落地需要**代码结构配合**（04 篇按功能分包）：

```text
Java 模块化单体结构：
├── com.example/
│   ├── order/          # 模块 A
│   │   ├── api/        # 对外接口（Port，其他模块只能依赖这里）
│   │   ├── internal/   # 内部实现（其他模块禁止访问）
│   │   └── OrderApplicationService 等
│   ├── payment/        # 模块 B（同构）
│   └── shared/         # 共享核心（跨模块复用的纯逻辑）

规则映射到结构：
├── 模块 API 放 api 包（公开）
├── 内部实现放 internal（通过架构测试禁止外部引用）
├── 跨模块调用只允许 api 包（ArchUnit 断言）
└── shared 只放"无业务语义"的纯工具（业务共享用模块 API）
```

**模块 API 的设计是模块化单体的关键**：API 包即模块的"服务接口"（05 篇的 Port），internal 包即实现。规则：**依赖模块 api 包 = 合法，依赖 internal 包 = 架构违规**——这条规则交给工具强制（下节）。

## 4. ArchUnit：Java 架构测试

ArchUnit 是 Java 生态的架构约束测试工具：**把架构规则写成单元测试，跑在 CI 里**——架构违规 = 测试失败。

```kotlin
// ArchUnit 规则示例（JUnit 5）
@AnalyzeClasses(packages = ["com.example"])
class ArchitectureTest {

    // 规则一：模块只能依赖其他模块的 api 包
    @ArchTest
    val modulesOnlyDependOnApi = noClasses()
        .that().resideInAPackage("..internal..")
        .should().dependOnClassesThat()
        .resideInAPackage("..internal..")

    // 规则二：依赖方向（controller 不依赖 repository）
    @ArchTest
    val layeredArchitecture = layeredArchitecture()
        .consideringAllDependencies()
        .layer("Controller").definedBy("..controller..")
        .layer("Service").definedBy("..service..")
        .layer("Repository").definedBy("..repository..")
        .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
        .whereLayer("Repository").mayOnlyBeAccessedByLayers("Service")

    // 规则三：禁止循环依赖
    @ArchTest
    val noCyclicDependencies = slices()
        .matching("com.example.(*)..")
        .should().beFreeOfCycles()
}
```

ArchUnit 的价值：**规则代码化**（架构评审的结论变成可执行测试）、**违规早期拦截**（CI 红灯，而非评审会才发现的腐化）、**演进安全**（重构时规则守护）。**使用纪律**：规则从 3-5 条核心规则起步（模块依赖方向/禁止穿透/循环依赖），不要一上来写 50 条——规则也是维护成本。

## 5. 其他语言的边界工具

| 语言 | 工具 | 能力 |
|------|------|------|
| Java/Kotlin | ArchUnit | 依赖方向/分层/循环/包规则 |
| Java | jdeps + 自定义脚本 | JDK 自带依赖分析 |
| JS/TS | dependency-cruiser | 模块边界/循环依赖/CI 集成 |
| .NET | NDepend | 依赖图/耦合度量/规则 |
| Go | internal 包机制 + go list | 语言级边界（internal 编译期强制）+ 审计 |
| 通用 | 架构测试 + CI 脚本 | 扫描 import 语句违反规则 |

**Go 的 internal 机制**值得单独说明：Go 在**语言层面**强制包可见性（仅同模块父路径含 internal 的代码可导入），配合 `go list -deps` 审计依赖、`go mod graph` + Graphviz 生成解耦拓扑图——语言级强制 + 工具审计的组合是边界治理的参考范式。其他语言没有语言级强制，全部依赖工具（ArchUnit 等）。

## 6. 耦合度量与 CI 门禁

边界强制的量化闭环（01 篇指标的落地）：

```text
指标一：Cohesion Ratio（内聚比）= 模块内部调用边 / 模块内节点数
  理想 ≥ 0.8；低于 0.5 → 模块内部不相关，边界可疑

指标二：Cross-Module Call Density（跨模块调用密度）= 跨模块调用边 / 总调用边
  设阈值（如 ≤ 0.2），超标 = 耦合过强

CI 门禁闭环：
├── 收集：依赖分析工具（ArchUnit 报告/依赖图）产出指标
├── 阈值：与团队约定（内聚比 ≥ 0.8、跨模块密度 ≤ 阈值）
├── 门禁：CI 流水线检查，超标红灯
└── 复盘：红灯 → 评审边界（不是改阈值掩盖）
```

**指标的作用与边界**：指标把"感觉耦合高"变成"数据说话"；但指标是**边界设计的辅助验证**，不是设计出发点——为凑指标改架构是本末倒置。门禁的价值在"防止无声腐化"：架构腐化是渐进的（每次"就一次"跳层），CI 门禁让腐化在发生时被发现。

## 7. 从模块化单体到微服务

模块化单体到微服务的演进路径（痛点驱动）：

```text
抽取微服务的信号：
├── 扩展痛点：某个模块资源需求特殊（独立扩缩容）
├── 部署痛点：高频发版被低频模块拖累
├── 团队痛点：团队边界与模块边界冲突（多团队协作摩擦）
└── 技术痛点：某模块需要不同技术栈

抽取步骤（一次抽一个）：
├── ① 模块边界清晰（模块化单体已保证）→ 抽取成本最低
├── ② 通信方式迁移：方法调用 → 接口 + RPC/消息
├── ③ 数据迁移：共享库 → 独立数据（最难，最后做）
└── ④ 独立部署：部署单元拆分 + 网关接入

模块化单体 → 微服务的优势：
模块化单体的边界就是微服务的服务边界——演进是"拆部署单元"而非"重新设计"
```

**模块化单体是微服务的"最佳预备队"**：边界已划好，抽取是机械动作；直接上微服务的团队往往边界混乱（分布式单体，下节）。演进决策（何时抽、抽哪个）见 L3/L4 与横向能力的架构演进。

## 8. 反模式：纳米服务与分布式单体

两个微服务化的反面教材：

```text
反模式一：纳米服务（Nano-services）
├── 表现：模块拆得比类还细（一个服务一个方法）
├── 后果：通信密集（每个操作都是网络调用）、事务破碎、运维爆炸
├── 根因：把"技术分层"当"服务边界"（每个层一个服务）
└── 修正：按业务域聚合回模块化单体/合理粒度服务

反模式二：分布式单体（Distributed Monolith）
├── 表现：服务边界混乱，服务间紧耦合（共享数据库/直接调用内部表）
├── 后果：微服务的成本全付了、收益全没有（部署隔离但耦合未解）
├── 根因：模块化单体没做好就拆微服务（边界不清）
└── 修正：回到模块化单体把边界划清楚，再重新演进
```

**两个反模式的共同教训**：**边界设计先于部署形态**——边界不清，单体是屎山、微服务是分布式屎山。模块化单体优先的根本理由：在最低成本下把边界设计做对。
