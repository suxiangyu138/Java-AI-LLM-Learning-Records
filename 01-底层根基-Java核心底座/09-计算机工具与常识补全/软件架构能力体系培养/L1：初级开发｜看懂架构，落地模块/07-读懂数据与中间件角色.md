## 1. 数据面全景：库 / 缓存 / 消息

**架构的"数据面"由三类组件构成**：**数据库（DB）**——**系统的'记忆'**：事实数据持久化（MySQL/PostgreSQL）；**缓存（Redis）**——**系统的'便签'**：热点数据快速存取（读多写少的数据）；**消息队列（MQ）**——**系统的'邮局'**：异步解耦的通信（RocketMQ/Kafka）。**L1 读懂数据面的三问**：**每张表存什么**（业务事实）；**Redis 里放了什么**（热点/会话/锁）；**MQ 里流着什么**（异步事件/任务）——"**数据面是架构的'下半身'：看懂数据怎么存、怎么快、怎么流，架构就立体了**"。**与 05 篇的关系**：**数据流（05 篇）的终点是落库（DB）、途经缓存（Redis）、可转异步（MQ）**——"**代码面管'怎么走'，数据面管'走到哪'**"。

## 2. 读表结构

**读表结构（Schema）是理解业务事实的入口**——**表的阅读四要素**：**表名**（订单表 order、用户表 user——**表名即业务实体**）；**主键与唯一键**（主键 id、唯一键（order_no）——**数据唯一性的约定**）；**字段**（列名 + 类型 + 约束——**业务字段即业务事实**）；**外键关系**（逻辑关联——**订单表关联用户表**——**Java 项目多不建物理外键，靠字段关联**）。**读表的方法**：**先看核心表**（业务主表：order/user——**业务的主干**）；**再看关联表**（订单明细/订单状态流转——**主表的延伸**）；**最后看字典表**（状态枚举/配置表——**业务字典**）。**工具**：**Navicat/DBeaver 看表结构**、**看建表 SQL**（`SHOW CREATE TABLE`）——"**表结构是业务的'静态快照'：一张表回答'系统记住什么事实'**"（数据库体系交叉：`../../../../02-后端核心技术 微服务 分布式 云原生/01-关系型数据库/`）。

## 3. ORM 映射：实体与表

**ORM（对象关系映射）是"Java 对象 ↔ 数据库表"的桥梁**——**L1 的日常主力是 MyBatis-Plus**（MyBatisPlus 体系交叉：`../../../../02-后端核心技术 微服务 分布式 云原生/MyBatisPlus/`）。**读懂 ORM 的三个映射**：**类 ↔ 表**（`@TableName("order")`——**实体类对应表**）；**字段 ↔ 列**（`@TableField("order_no")` 或驼峰自动转下划线——**orderNo ↔ order_no**）；**主键策略**（`@TableId(type = IdType.ASSIGN_ID)`——**雪花 ID 等**，雪花算法体系交叉）。**Mapper 的读法**：**接口方法 ↔ SQL**（`selectById` 等内置方法、`@Select` 注解 SQL、XML 里的自定义 SQL）——"**Mapper 是'表与代码的翻译官'：看 Mapper 就知道一张表在代码里怎么被操作**"。**L1 的注意**：**SQL 写在哪**（注解 vs XML vs 内置方法——**项目风格要统一**）；**逻辑删除**（`deleted` 字段——**删除是标记不是物理删**，`@TableLogic`）——"**看懂 ORM = 看懂'表在代码里的投影'**"。

## 4. Redis 在项目中的角色

**Redis 在项目里的四个常见角色**（Redis 体系交叉：`../../../../02-后端核心技术 微服务 分布式 云原生/02-非关系型数据库/Redis/`）：**缓存**（**读多写少的热点数据**——商品信息/配置——**key 命名通常带业务前缀**：`order:detail:123`）；**分布式锁**（**并发互斥**——Redisson，Java 分布式框架体系交叉）；**会话/登录态**（**token 存储**——Token 体系交叉）；**计数器/限流**（**访问计数/接口限流**——Redis 原子操作）。**读懂 Redis 用法的三问**：**存了什么**（看 key 前缀——**业务模块 + 数据类型**）；**为什么用 Redis 不用 DB**（**读多写少/热点/需要 TTL**——**Redis 的角色 = 架构的决策**）；**一致性怎么处理**（缓存与 DB 的双写/失效策略——**更新先更库再删缓存等约定**）——"**Redis 的角色是'架构决策'：看到 Redis 缓存，就要问'缓存了什么、为什么、怎么失效'**"。

## 5. MQ 在项目中的角色

**MQ（消息队列）在项目里的三个角色**（消息队列体系交叉：`../../../../02-后端核心技术 微服务 分布式 云原生/03-消息队列/`）：**异步解耦**（**不关键的操作异步化**——下单后发通知，不用等通知完成——"**主流程更快的代价是'通知可能延迟'**"）；**削峰填谷**（**高峰期消息排队，下游匀速消费**——秒杀/大促场景）；**事件广播**（**一个事件多个消费者**——订单创建 → 通知服务 + 积分服务 + 报表服务）。**读懂 MQ 用法的三问**：**什么消息在流**（Topic/队列名——**业务事件**）；**谁在消费**（消费者代码——**消息的终点**）；**失败怎么办**（重试/死信——**消息可靠性约定**）——"**MQ 是架构的'异步血脉'：看到 MQ，就问'哪段流程被异步化了、为什么'**"（事件驱动架构的载体，03 篇）。

## 6. 配置文件里的数据面

**数据面在配置文件里的投影**（02 篇配置文件的深读）：**数据源配置**（`spring.datasource.url`——**连哪个库**；多数据源/读写分离——**架构的数据分层**）；**Redis 配置**（`spring.data.redis.host`——**缓存/锁/会话的地址**）；**MQ 配置**（`rocketmq.name-server`——**消息的地址**）；**缓存配置**（`spring.cache` 或自定义——**缓存开关与过期策略**）。**配置文件读数据面的方法**：**先看数据源**（核心库）、**再看中间件地址**（Redis/MQ——**用没用、连哪**）、**最后看自定义配置**（业务相关的缓存 key 前缀/超时时间——**项目的数据约定**）——"**配置文件是数据面的'接线图'：数据面在哪、怎么连，配置里一目了然**"。

## 7. 五个常见坑

- **坑一**：只看代码不看表结构——**业务事实在表里；先读核心表再读代码**（第 2 节）；
- **坑二**：Redis key 乱猜——**看 key 前缀与代码里的常量定义；'存了什么'先问代码**（第 4 节）；
- **坑三**：看到 MQ 不知道谁消费——**搜消费者代码；'消息去哪'是必答三问之一**（第 5 节）；
- **坑四**：缓存与 DB 一致性不考虑——**更新了 DB 没清缓存 = 脏数据；看项目的一致性是约定**（第 4 节）；
- **坑五**：ORM 的 SQL 位置不看——**注解/XML/内置混用 = 维护灾难；跟随项目风格**（第 3 节）。

## 8. 练习 5 题

1. 数据面三组件与类比？"记忆/便签/邮局"？
2. 读表结构四要素？核心表/关联表/字典表的顺序？
3. ORM 的三个映射？逻辑删除是什么？
4. Redis 的四个角色？"存了什么/为什么/怎么失效"三问？
5. MQ 的三个角色？"什么消息/谁消费/失败怎么办"三问？

> 🎯 **核心要点**：数据面 = **DB（记忆）+ Redis（便签）+ MQ（邮局）**——"**表结构是业务快照、ORM 是表在代码里的投影、中间件角色是架构决策**"——看到缓存/消息就问"为什么"，是 L1 读懂数据面的钥匙。
