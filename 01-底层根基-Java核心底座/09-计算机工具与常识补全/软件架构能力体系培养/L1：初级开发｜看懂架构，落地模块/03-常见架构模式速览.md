## 1. 架构模式是什么

**架构模式（Architecture Pattern）是"解决一类问题的成熟骨架"**——**先人踩过的坑、总结出的最佳结构**，你直接套用。**类比**：**做菜的"菜系"**——**分层架构是"本帮菜"（家常稳妥）、微服务是"分子料理"（复杂精致）**——**L1 的日常在"本帮菜"里，但要知道其他菜系的存在**。**架构模式的本质**：**"组织代码的方式"**——同一需求，不同模式组织方式不同、代价不同——**模式没有绝对优劣，只有适合与否**（取舍是架构师的事，L1 先会识别）。**L1 的定位**：**会识别（这是分层）、会理解（为什么分层）、会遵循（按模式写代码）**——设计模式的选择是 L2 的事。

## 2. 分层架构：最普遍的模式

**分层架构（Layered Architecture）是软件世界最普遍的模式**：**系统按职责分成若干层，上层依赖下层，层内高内聚、层间低耦合**——"**各层各司其职，请求自上而下流动**"。**经典的分层**（Java Web 系）：

```text
表现层（Controller）    ← 接收请求、参数校验、返回响应
业务层（Service）       ← 业务逻辑、事务边界、规则编排
数据访问层（DAO/Mapper） ← 数据库操作、ORM 映射
数据层（MySQL/Redis）   ← 数据存储
```

**分层的三个价值**：**可维护**（改数据库不影响 Controller——**层间解耦**）；**可复用**（Service 可被多个 Controller 调用）；**可测试**（每层可独立测试——Mock 下层）。**分层的代价**：**性能损耗**（请求穿层有开销——**但正确性优先于微性能**）——"**分层架构是'用一点性能换大量可维护性'的交易，绝大多数系统值得做**"。

## 3. 三层架构与 MVC

**三层架构与 MVC 是两件常被混淆的事**：**三层架构（Three-Tier）是"物理分层"**——**表现层/业务层/数据层**（对应客户端/应用服务器/数据库服务器——**可以部署在不同机器**）；**MVC（Model-View-Controller）是"表现层内部的分工"**——**Model（数据）、View（视图）、Controller（控制器）**——**MVC 是三层架构里"表现层"的实现方式**。**关系一句话**：**"三层架构是整栋楼的楼层设计，MVC 是第一层的内部装修"**。**Spring MVC 的映射**：Controller（C）→ 返回 JSON/视图（V）→ 数据模型（M）——**前后端分离时代**：**View 交给前端（Vue/React），后端只留 Controller + Model（JSON 响应）**——"**L1 在 Spring Boot 项目里看到的'Controller-Service-Mapper'，就是分层架构的 Java 形态**"（04 篇包结构）。

## 4. 模块化单体：2026 主流

**模块化单体（Modular Monolith）是 2026 年多数团队的最佳点**：**应用内部按业务划分模块（订单模块/支付模块/用户模块），但整体仍是一个部署单元**——"**单体的部署简单 + 模块的边界清晰**"。

```text
模块化单体：
  order 模块（controller/service/mapper 自成一套）
  payment 模块（controller/service/mapper 自成一套）
  user 模块
  → 模块间通过"模块接口"协作，不直接访问对方内部
  → 整体打成一个 jar/war 部署
```

**为什么它优于"一坨单体"**：**模块边界 = 未来的服务边界**——**哪天要拆微服务，模块就是现成的服务候选**——"**模块化单体是'留好拆分的路，先不拆'**"。**为什么它优于直接微服务**：**微服务的分布式复杂性（网络/事务/部署）不是每个团队都该背**——"**能用单体解决的问题，别用微服务制造问题**"（2026 架构共识，00 篇基线）。**L1 的认知**：**多数项目你会遇到"模块化单体"**——**04 篇的包结构与 08 篇的落地纪律都在这个模式下展开**。

## 5. 微服务：了解级

**微服务（Microservices）：系统拆成多个独立部署的小服务，各自独立开发/部署/扩缩**。**L1 只需要了解四个要点**：**拆分单位**（按业务能力拆——订单服务/支付服务）；**通信方式**（HTTP/RPC——**服务间网络调用**，Java 分布式框架体系交叉：`../../../../02-后端核心技术 微服务 分布式 云原生/08-分布式系统与架构/Java分布式框架/`）；**代价**（分布式事务、链路追踪、部署编排——**复杂性全在"分布式"三个字**）；**何时需要**（团队规模大、独立扩缩需求强、模块边界稳定——**"确实需要时才上"**）。**L1 的定位**：**认识微服务的形态**（网关/注册中心/服务调用），**不深挖**——微服务架构是 L3 的主题——"**微服务是'知道有这回事'，模块化单体是'每天在写'**"。

## 6. 其他模式：看一眼

**另外三种模式，L1 看一眼知道存在即可**：**事件驱动架构（Event-Driven）**——组件通过事件（消息）异步通信（**松耦合但难追踪**——RocketMQ/Kafka 是载体，消息队列体系交叉）；**客户端-服务器（Client-Server）**——**最基础的形态**（浏览器-服务器就是它）；**管道-过滤器（Pipe-Filter）**——数据流经一串处理单元（**ETL/数据处理场景**）。**识别线索**：**项目里有大量"事件发布/订阅"代码 → 事件驱动**；**有消息队列做核心业务流转 → 事件驱动倾向**；**普通 CRUD 系统 → 分层**——"**L1 能说出'这是分层 + 局部事件驱动'，已经超过 80% 的初级开发**"。

## 7. 如何识别项目的架构模式

**识别四步**：**① 看部署形态**（一个应用还是多个服务——**单部署单元 = 单体系**）；**② 看包结构**（有没有清晰的 controller/service/mapper 分层——**有 = 分层架构**；按业务分包 = 模块化单体倾向，04 篇）；**③ 看模块边界**（业务模块间有没有"接口隔离"——**有 = 模块化单体**）；**④ 看通信方式**（模块间直接方法调用 = 单体系；HTTP/消息 = 微服务/事件驱动）。**识别产出**：**一句话描述项目的架构**——"**这是一个分层架构的模块化单体：Controller-Service-Mapper 三层，订单/支付/用户三个业务模块**"——**这句话就是 L1 架构能力的"自我介绍"**（10 篇毕业汇报用）。

## 8. 五个常见坑

- **坑一**：把三层架构和 MVC 混为一谈——**三层是楼层设计，MVC 是第一层装修**（第 3 节）；
- **坑二**：项目是单体就瞧不起——**单体不是原罪，'一坨没有边界的单体'才是**；模块化单体现在是主流（第 4 节）；
- **坑三**：一提架构就想到微服务——**L1 的日常 90% 是分层/三层**；微服务是了解级（第 5 节）；
- **坑四**：背模式定义不会识别——**先会识别（四步法）再谈理解**（第 7 节）；
- **坑五**：觉得模式越多越高级——**模式是取舍不是勋章**；"用一点性能换大量可维护性"才是分层存在的理由（第 2 节）。
