## 1. 系统级需求：功能之外的约束

系统级需求（非功能需求 NFR）是架构设计的输入——功能需求决定"做什么"，NFR 决定"做成什么样、多快、多稳、多贵"：

- **性能**：吞吐量（QPS/TPS）、延迟（P50/P95/P99）、并发量
- **可用性**：SLA 百分比、故障恢复时间（RTO）、数据丢失容忍（RPO）
- **容量**：峰值流量、数据规模、增长预期（五年）
- **安全**：等级保护、数据合规（个人信息保护法/等保）
- **成本**：预算上限、单位成本约束
- **运维**：部署节奏、可观测性要求、团队规模
- **演进**：技术栈约束、存量系统兼容、组织边界

**NFR 的收集难点**：业务方说不出"QPS 多少"（只会说"大促不能挂"）——架构师要**把业务语言翻译成数字**（01 篇翻译官能力）："大促不能挂" → 峰值 QPS 预估 + P99 延迟目标 + 可用性承诺。NFR 不量化，架构设计就是猜。

## 2. NFR 量化：把质量属性变成数字

NFR 量化的标准格式：**指标 + 数值 + 场景/条件**。示例：

- 吞吐量：核心交易接口 QPS ≥ 10,000（峰值 5 分钟均值）
- 延迟：核心接口 P99 ≤ 200ms（非缓存命中场景）
- 可用性：SLA 99.99%（年停机 ≤ 52.6 分钟）
- 恢复：RTO ≤ 5 分钟（主可用区故障）、RPO ≤ 5 分钟（数据丢失容忍）
- 容量：数据量年增长 2 倍，支持 5 年规划（30% 预留——06 篇）
- 成本：单笔交易成本 ≤ X 元（FinOps 视角——08 篇）

量化的三个要点：

- **数值必须可测量**：有监控可验证，否则是口号
- **数值必须有场景**：99.9% 在什么故障场景下
- **数值必须分等级**：核心链路 vs 非核心，不同承诺

**量化基准参考**（2026 架构设计手册）：吞吐 QPS ≥ 10,000、延迟 ≤ 200ms、RTO ≤ 5 分钟、可用性 99.99%——这是"主流业务系统"的常见基线，具体项目按业务价值调整。**量化的意义**：有了数字才能做容量规划（06 篇）、韧性设计（05 篇）、成本核算（08 篇）——数字是全局设计的共同语言。

## 3. 性能预算：端到端延迟的分配

性能预算（Performance Budget）把端到端延迟目标**分配到每个环节**——每个环节拿到自己的延迟份额，超预算即违规。端到端 200ms 预算的分配示例（订单接口）：

- 网关/鉴权：20ms（10%）
- 服务间调用（RPC × 3 跳）：90ms（45%）
- 业务处理：40ms（20%）
- 数据库/缓存：40ms（20%）
- 序列化/网络开销：10ms（5%）

预算的治理：

- **每环节可测量**：各环节埋点，超预算能定位
- **预算分配有依据**：不是拍脑袋，基于实测与推算
- **预算随架构变化重分配**：引入新环节要重新分配
- **超预算的环节要优化或重新谈判**：不是默默超支

**性能预算的价值**：**延迟问题从"事后排查"变成"事前约束"**——没有预算，接口慢了是"查一下哪里慢"；有预算，接口慢了是"哪一环超支了"（对应预算表）。性能预算与 03 篇的 NFR 一脉相承：NFR 给总目标，预算给分解，监控给验证。

## 4. SLA 设计：承诺什么

SLA（服务等级协议）是系统对业务的量化承诺——**承诺要设计，不是随口说**：

SLA 设计的三个要素：

- **承诺什么**：可用性（99.99%）、延迟（P99 200ms）、容量（QPS）
- **承诺的边界**：哪些场景不计入（计划维护/不可抗力/客户端问题）
- **承诺的度量**：怎么测量（监控口径、统计窗口、告警定义）

SLA 的代价意识：

- 99.9% → 99.99% 的工程代价差一个数量级（架构复杂度/成本）
- SLA 是"花钱买的"：每提高一个 9，成本翻倍级增长
- 承诺的合理性：按业务价值定——交易系统值 99.99%，后台报表 99.9% 足够
- 承诺要可达成：先实测后承诺（没有数据支撑的 SLA 是画饼）

SLA 的治理：

- 监控要覆盖 SLA 指标（可观测性三支柱——L3 09 篇）
- 未达标的复盘：为什么、怎么修、承诺要不要调整
- SLA 是动态的：业务阶段变了，SLA 要重新评估

**SLA 设计的关键判断**：**"多少个九"是业务决策不是技术决策**——架构师提供"每个九的成本"，业务决定"买几个九"。把技术选项翻译成业务选择（01 篇），SLA 设计就成功了一半。

## 5. 业务战略对齐：架构支撑业务

架构目标必须与业务战略对齐——**架构不是"技术最佳"，是"业务阶段最佳"**：

对齐的检查框架：

- **业务阶段**：验证期（快速试错 → 架构简单优先）vs 成长期（支撑增长 → 弹性优先）vs 成熟期（精细化运营 → 成本/治理优先）
- **业务方向**：平台化/国际化/数据驱动——架构要预留对应能力
- **业务节奏**：发布频率（周更 vs 月更）决定架构的模块化程度
- **业务约束**：合规（金融/医疗）、组织（团队边界=服务边界候选）

错位的典型：

- 验证期业务用大厂架构（03 篇：自行车装飞机发动机）
- 成长期业务用单体硬撑（增长压垮架构，重构成本更高）
- 成熟期业务不治理（成本失控/技术债爆炸）

**架构与业务的契约**：架构师要能回答"这个架构支撑了什么业务目标"——答不出，说明架构与业务脱节。L4 的每个设计决策都要回扣业务价值（为什么值得这个复杂度/成本）。

## 6. 合规与约束清单

合规是**不可妥协的约束**（不是权衡项）：

- **数据合规**：个人信息保护法（PIPL）、数据出境评估
- **行业合规**：等保（2.0/3.0）、金融/医疗专项
- **数据留存**：日志保留期限、审计要求
- **供应链**：开源许可、依赖安全（SBOM）

约束清单（设计前的检查）：

- 数据存储位置（境内/境外——影响部署架构）
- 数据加密要求（传输/存储加密——影响链路设计）
- 审计要求（操作留痕——影响日志设计）
- 技术栈限制（信创/采购清单——影响选型范围）
- 团队与预算约束（人力/时间/成本——影响方案规模）

**合规的架构影响**：合规约束经常改变架构形态（数据本地化 → 区域部署；审计要求 → 全链路日志；等保 → 安全架构加固）——**合规检查前置**（设计前就拉清单），后补合规的成本是重构级。

## 7. 从需求到架构目标

系统级需求收敛为**架构目标**（架构设计的验收标准）：

架构目标文档（L4 设计文档的第一节）：

- 业务背景与战略（1 段话：为什么做、业务阶段）
- 量化 NFR（吞吐/延迟/可用性/恢复——第 2 节格式）
- 容量与增长（峰值/数据规模/五年预期）
- 合规约束清单（不可妥协项）
- 成本边界（预算上限/单位成本）
- 非目标（明确不做什么——防架构膨胀）

架构目标的验收：

- 每个设计决策能回扣目标（"这个选择服务哪个目标"）
- 目标可测量（有监控可验证）
- 目标与业务对齐（业务方认可这些数字）

**目标的工程价值**：架构目标是设计、评审、治理的共同基准——评审问"这个方案满足目标吗"，度量看"目标达成率"。没有目标的架构评审是"凭感觉挑方案"。

## 8. 练习

1. 为你所在系统写一份 NFR 量化清单（指标/数值/场景）
2. 给一个接口画 200ms 性能预算分配表
3. 评估你系统 SLA 的合理性（承诺 vs 实测 vs 代价）
4. 盘点你系统的合规约束清单（有哪些影响架构的约束）
5. 写一份架构目标文档（含非目标），找业务方确认数字
