## 1. 服务架构演进史：模式的选择

全局架构的模式选择建立在演进史认知上（《凤凰架构》的演进主线）：

- 单体：简单直接，规模小时最优
- SOA：服务化 + ESB（总线过重，被微服务取代）
- 微服务：服务自治 + API 网关（当前主流）
- 后微服务：服务网格（治理下沉到基础设施）
- 无服务：Serverless（运行时也外包）

演进规律：

- 每一代解决上一代的治理痛点，同时引入新复杂度
- 演进不是"必须走到头"——停在最适合的阶段就好
- 选型看业务阶段（02 篇），不是看技术代际

**架构师的模式认知**：不是"越新越好"，是"每个模式适配一种业务阶段"——单体适配验证期、模块化单体适配成长期（L2 07 篇）、微服务适配多团队规模化、Serverless 适配弹性波动。**演进正确姿势**：随业务痛点渐进演进，不跳级（跳级 = 过度设计）。

## 2. 微服务：何时用、何时不用

微服务的适用判断（2026 共识——模块化单体优先，痛点驱动演进）：

微服务的触发条件（L2 07 篇扩展）：

- 团队：多个团队需要自治（团队边界 = 服务边界候选）
- 扩展：模块间资源需求差异大（独立扩缩容）
- 部署：发版节奏差异大（独立发布）
- 技术：模块需要异构技术栈
- 规模：服务数量 10+（少于 10 个服务，微服务的成本大于收益）

微服务的代价（必须清楚）：分布式复杂度（网络/一致性/链路追踪）、运维复杂度（部署/监控/治理）、团队要求（DevOps 能力）、反模式（纳米服务/分布式单体——L2 07 篇）。

判断框架：团队能自治吗（不能 → 模块化单体）？痛点真实吗（"觉得该拆" vs "明确被拖累"）？复杂度预算够吗？

**微服务的正确打开方式**：**从模块化单体演进**（边界已划好，抽取是机械动作）——直接上微服务大多得到分布式单体（L2 07 篇反模式）。

## 3. 分布式基石：CAP 与一致性

分布式系统的第一课是 CAP 定理：**网络分区时，一致性与可用性不可兼得**——架构师必须明确"分区时保哪个"：

CAP 的核心认知：

- 网络分区不可避免（故障是常态）
- 分区时必须选择：CP（保一致性，拒绝服务）或 AP（保可用性，暂时不一致）
- 不分区时三者可兼得（但分区必然发生，所以必须先选）

CP vs AP 选型（按业务）：强一致业务（账户/库存）→ CP（ZooKeeper/etcd/单库事务）；可用优先业务（浏览/通知）→ AP（缓存/消息/多副本）；混合：核心链路 CP、非核心 AP。

一致性级别：强一致（读必最新）/最终一致（异步复制/消息）/读己之写（用户操作立即可见）——选择依据：业务容忍度 + RPO。

**CAP 的工程应用**：数据库选型（关系型 CP vs NoSQL AP）、复制模式（同步/异步）、缓存策略（一致性缓存 vs 过期缓存）——每个一致性选择都有 CAP 依据。**架构师面试高频题**：CAP 三选二——标准答案：分区时二选一，不是任何时候三选二。

## 4. 分布式事务：SAGA/TCC/可靠事件

分布式事务是跨服务数据一致性的落地（CAP 之后的工程问题）：

分布式事务方案对比：

- **两阶段提交（2PC）**：强一致，但阻塞/性能差（现代系统少用，只用于极小范围）
- **TCC（Try-Confirm-Cancel）**：业务补偿，强一致，实现复杂
- **SAGA（长事务）**：链式补偿，最终一致，适合长流程
- **可靠事件（本地消息表/事务消息）**：最终一致，性能好

SAGA 的要点：

- 正向：A → B → C（每步本地事务）
- 反向：失败时补偿（C 失败 → 补偿 B → 补偿 A）
- 编排方式：编排器（中心化）vs 协同（事件驱动）
- 幂等与补偿的完备性（补偿逻辑要覆盖所有失败路径）

可靠事件（本地消息表）：

- 本地事务写业务 + 事件表（同事务）
- 定时任务/消息投递事件
- 消费者幂等消费
- 实现简单可靠，是"最终一致"的实用选择

**分布式事务的工程原则**：**能不用就不用**——先通过边界设计（L2/L3）把事务控制在单服务内；必须跨服务的，按业务价值选方案（强一致 TCC、最终一致 SAGA/可靠事件），完备性用故障注入测试验证（05 篇韧性）。

## 5. 多级分流：缓存/CDN/负载均衡

全局架构的流量治理（《凤凰架构》的"透明多级分流"）：

多级分流体系（从客户端到服务端）：

- 客户端缓存：浏览器缓存（静态资源 max-age）
- CDN：静态内容边缘分发（图片/JS/视频）
- 负载均衡：流量分发（DNS/网关/Nginx）
- 服务端缓存：Redis 等（热点数据）
- 数据库层：连接池/读写分离

各级的作用与代价：

- 越靠近客户端，减少的请求越"便宜"（不占服务器）
- CDN 命中省全网流量；Redis 命中省数据库
- 缓存一致性：每级缓存都有自己的失效策略（TTL/主动失效/版本）
- 多级缓存的核心指标：各级命中率（监控必配）

流量的治理原则：

- 静态与动态分离（静态走 CDN，动态走服务）
- 热点识别（热点数据进缓存，避免穿透）
- 削峰（消息队列承接突发——L2 06 篇）
- 限流（网关/服务端限流保护下游）

**多级分流的架构意义**：它是"容量规划"的杠杆（06 篇）——缓存命中率提升 10%，后端容量需求显著降低。**先设计分流再算容量**，反了会过度购买资源。

## 6. 云原生 2.0：从构建到治理

2026 云原生 2.0 的核心转变：**最大挑战从"如何拆分服务"变成"如何管理成百上千个微服务间的动态依赖"**：

云原生 2.0 的治理体系：

- **服务网格（Istio 等）**：流量治理下沉基础设施
  - 服务发现/负载均衡/熔断（数据面）
  - 策略下发/监控（控制面）
- **多集群联邦**：跨集群统一治理（K8s Federation）
- **边缘自治**：边缘节点轻量 Agent 本地自愈
- **分层治理模型**：核心区用集中式控制平面（全局策略一致性），边缘区用轻量化 Agent（本地快速响应）

服务网格的价值：

- 业务代码零侵入（治理在 Sidecar/基础设施层）
- 流量可观测（mTLS/全链路指标）
- 灰度/金丝雀发布的基础设施化
- 代价：Sidecar 资源开销/运维复杂度（网格不是免费的）

**服务网格的适用判断**：服务数量多（数十+）、需要统一流量治理/加密/灰度 → 值得；服务少 → Sidecar 开销不划算。**2026 趋势**：网格向多集群联邦与边缘自治演进——治理从单集群走向全局。

## 7. 无服务与边缘计算

无服务（Serverless）与边缘计算是**特定场景的补充形态**（不替代微服务）：

- **Serverless**（FaaS + 托管运行时）：弹性极致、免运维，适用弹性波动/事件驱动/短任务，不适用长连接与强一致核心链路
- **边缘计算**：把计算下沉到网络边缘（低延迟/带宽节省/离线自治），适用 IoT/车联网

**按场景混布**（核心链路常规架构 + 弹性场景 Serverless）是 2026 主流——混布的关键是"接缝设计"：弹性组件与核心链路通过标准接口解耦，避免冷启动/超时限制拖累核心路径。

## 8. 模式选型的决策树

全局架构模式决策树（按顺序自问，答案自然收敛）：

- 验证期 → 单体/模块化单体（简单优先）
- 多团队自治需要？否 → 模块化单体（L2 07 篇）；是 → 微服务（从单体演进抽取）
- 流量治理复杂？否 → API 网关足够；是 → 服务网格
- 弹性波动场景？→ 混布 Serverless
- 边缘/低延迟场景？→ 边缘计算
- 所有场景：先多级分流 + 明确一致性策略

**决策树的使用**：**不跳级**（验证期不微服务）、**不叠加**（全上通常过度）、**痛点驱动**（有痛点才演进）。
