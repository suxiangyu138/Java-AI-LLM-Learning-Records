## 1. 选型的本质：低成本解决业务问题

选型的本质（2026 共识）：**用最低的成本（复杂度/金钱/人力）解决核心业务问题，支撑业务可持续演进**——不是选"最先进"的技术，是选"最匹配"的技术。

选型的判断框架：

- **业务价值**：这个技术解决什么业务问题（没有业务问题的选型是技术表演）
- **复杂度成本**：引入后团队要学多少、运维要扛多少
- **替换成本**：选错了换的代价（锁定效应）
- **演进空间**：业务增长后是否够用（够用到什么程度）

选型心智的转变：

- 不问"哪个技术最好"——没有最好，只有匹配
- 不问"大厂用什么"——大厂方案适配其体量（自行车装飞机发动机）
- 要问"我们业务的这个阶段，需要什么复杂度"
- 要问"这个方案失败/过时的代价是什么"

**复杂度预算**：架构的复杂度是预算制——每引入一个技术（消息队列/微服务/向量库），就花掉一份复杂度预算。预算花在业务价值最高的地方（02 篇的业务对齐），不花在"技术好看"上。

## 2. 过度设计的三个根源

2026 年选型"内卷"的三个根源（识别它们，90% 的过度设计可避开）：

**根源一：脱离业务价值的技术军备竞赛**

- 表现：为"技术先进"选型（K8s 全家桶/微服务/多活，业务只要单体）
- 后果：复杂度远超业务需要，团队被技术拖垮
- 解药：每个选型回扣业务问题（"这个技术解决什么业务问题"）

**根源二：迷信大厂方案**

- 表现：照搬大厂架构（其亿级体量/千人团队/专用团队维护）
- 后果：给自行车装飞机发动机——维护成本远超收益
- 解药：学习大厂的"思路与权衡"，不照搬其"方案"（适配场景）

**根源三：对未来需求的过度焦虑**

- 表现："万一用户破亿"就提前分库分表/微服务化
- 后果：90% 的业务永远不会遇到想象中的亿级流量；预留变负债
- 解药：面向已验证的增长做最小化预留（下节）

**三个根源的共同特征**：**为"未来假设"支付"当前成本"**——假设不成立，成本全沉没。纪律：当前需求的成本当前付，未来需求的成本未来付（到那时信息更多、决策更准）。

## 3. 前瞻性设计 vs 过度设计

两者的边界（Kent Beck 简单设计四原则 + 2026 实践）：

**前瞻性设计（推荐——做）**

- 特征：最小化预留——接口抽象、模块边界（成本低、方向确定）
- 依据：业务确定性演进方向（已规划的增长/已确认的扩展）
- 示例：新支付渠道已验证会来 → 支付渠道接口抽象
- 代价：低（抽象的成本可接受）

**过度设计（反对——不做）**

- 特征：完整扩展能力——提前实现所有扩展点（成本高、方向假设）
- 依据：不确定假设（"万一"型需求）
- 示例："万一用户破亿"提前分库分表 → 需求未落地，长期技术债
- 代价：高（未落地的扩展能力 = 永久负债）

判断标准：

- 方向确定吗？（确定 → 前瞻；不确定 → 不做）
- 成本可承受吗？（低 → 做；高 → 等需求）
- 可以晚点做吗？（可以 → 晚点做，信息更多决策更准）

**一句话边界**：**为"已验证会来"的变化做抽象，为"万一会来"的变化不做**——延迟决策是架构师的重要能力。

## 4. 选型四步法

标准选型流程（可复用的方法论）：

1. **需求定义**：解决什么业务问题（回扣 02 篇目标）、约束条件（团队/合规/成本/时间）、成功标准
2. **候选对比**：成熟主流 + 1-2 个新锐、对比维度（能力/成熟度/生态/团队/成本）、保留 2-3 个深入
3. **基准测试**（关键验证）：真实业务场景压测（非官方数字）、性能与稳定性（吞吐/延迟/失败表现）、团队试用（上手成本实测）
4. **决策 + ADR**：综合评估、ADR 记录（背景/决策/被否决方案/影响）、上线后回看验证

**四步法的纪律**：步骤一二快（半天到一天），步骤三要投入（基准测试不能省）；步骤四要留痕（ADR 是复盘材料）。**选型没有"一次决策终身正确"**——定期重估（技术雷达心态）。

## 5. 评估维度：成熟度/生态/团队/成本

选型评估的四个核心维度（缺一不可）：

**维度一：技术成熟度**

- 版本状态：稳定版 vs beta（生产用稳定版）
- 社区活跃：issue 响应/版本节奏/维护者
- 踩坑记录：已知问题是否影响你的场景
- 生命周期：会不会很快过时（技术雷达）

**维度二：生态兼容性**

- 与你技术栈的集成度（Spring/云厂商/监控体系）
- 周边生态（工具/插件/人才市场）
- 锁定风险：换的代价（专有 API vs 标准协议）

**维度三：团队技能匹配度**

- 团队是否有人会用（学习成本）
- 人才市场供给（招人难易）
- 团队维护能力（出了问题谁扛）

**维度四：成本控制**

- 授权/许可成本（商业 vs 开源）
- 基础设施成本（资源消耗）
- 运维人力成本（自建 vs 托管）
- 迁移成本（存量系统替换）

**评估的权重**：四个维度按业务场景加权——金融项目"成熟度"权重高（稳字当头），创新项目"生态"权重高（快速集成），初创"成本"权重高（活下来优先）。**选型评估表**（四维度打分 + 权重 + 理由）是评审的标准材料。

## 6. 基准测试：选型的最终验证

基准测试是选型四步法的**最终验证环节**（不能只看官方 benchmark）：

基准测试的纪律：

- 用真实业务场景（官方 benchmark 数字 ≠ 你的场景）
- 测试环境接近生产（数据量/并发/网络拓扑）
- 测三件事：吞吐、延迟、稳定性（故障表现）
- 对比要同条件（同数据/同配置/同机器）
- 结果要有记录（报告存档，选型依据可追溯）

基准测试的常见错误：

- 用官方 benchmark 代替实测（环境不同，数字失真）
- 默认配置对比（候选都要调优后再比）
- 只测性能不测运维（部署/监控/升级的难易也是选型因素）
- 忽略长稳（跑 30 分钟 vs 跑 3 天，内存泄漏才现形）

基准测试的输出：

- 性能数据表（吞吐/延迟对比）
- 稳定性观察（长跑/故障注入表现）
- 易用性反馈（团队试用报告）
- 最终选型建议 + 理由（供决策）

**基准测试的投入产出**：一次扎实的基准测试（1-2 周）避免的错误（选错中间件/数据库）代价是重构级——**选型错误成本远高于测试成本**。

## 7. 选型常见陷阱

| 陷阱 | 表现 | 解法 |
|------|------|------|
| 追逐最新 | 新框架 beta 上生产 | 生产用稳定版，新锐进实验 |
| 只比性能 | 忽略成熟度/生态/团队 | 四维度综合评估 |
| 官方数字迷信 | benchmark 直接采信 | 真实场景实测 |
| 大厂照搬 | 方案不适配体量 | 学思路不学方案 |
| 免费=便宜 | 忽略运维人力成本 | 算总拥有成本（TCO） |
| 一次定终身 | 选完不重估 | 定期技术雷达/重估 |
| 决策无记录 | 选型理由没写 | ADR 必写（被否决方案） |

**陷阱的共同根源**：**选型被"技术偏好"驱动而非"业务价值"驱动**——把"我喜欢"与"它适合"分开，是架构师选型成熟的标志。

## 8. 练习

1. 分析你最近一次选型的决策依据（有没有业务价值回扣）
2. 用"前瞻 vs 过度"判断你项目里 3 个预留设计
3. 走一遍四步法：为一个新需求做选型（含 ADR）
4. 设计一份四维度评估表并给两个候选打分
5. 分析一个"大厂方案照搬"案例的适配问题
