# 05-质量属性与NFR
> 定位：质量属性（-ilities）是架构的「验收契约」——NFR 定义要可验收、要追踪到架构选择；「性能要好」不是 NFR，「P99 < 200ms」才是；质量属性是权衡（02 篇）与评审（07 篇）的共同原料。

## 1. 质量属性全景

质量属性（Quality Attributes，俗称 -ilities）是架构的「非功能面」——功能需求说「做什么」，质量属性说「做得怎么样」。全景地图（按维度分组）：

**性能族**——性能（延迟/吞吐）、可扩展性（Scalability——加资源能否线性扩容）、容量（Capacity）；**可靠族**——可用性（Availability——SLA 百分比）、可靠性（Reliability——无故障时间）、可恢复性（Recovery——故障恢复时间 RTO/数据丢失容忍 RPO）；**安全族**——机密性、完整性、可用性（CIA 三元组）+ 合规（GDPR/等保）；**演进族**——可维护性（Maintainability）、可测试性（Testability）、可扩展性（Extensibility——加功能不改结构）、可移植性（Portability）；**运营族**——可观测性（Observability——日志/指标/追踪）、可部署性（Deployability）、可配置性。

**质量属性的核心地位**：**架构选择 = 质量属性的权衡**（02 篇）——「选缓存」是在「性能 vs 一致性」之间取舍——**「质量属性是架构决策的坐标系」**——没有质量属性定义，权衡无从谈起、评审没有依据、NFR 验收没有标准。

## 2. NFR 的定义标准

NFR（非功能需求）的质量标准——**「不可验收的 NFR 等于没有」**：

| ❌ 伪 NFR | ✅ 可验收 NFR |
|---------|-------------|
| 系统要快 | P95 响应时间 < 200ms（压测场景定义） |
| 要可靠 | 月度可用性 ≥ 99.9%（SLA 定义） |
| 要安全 | 无高危漏洞（扫描工具 + 修复时限） |
| 要可扩展 | 单节点 2000 QPS，水平扩容线性提升 |

**可验收 NFR 的三要素**：**指标**（延迟/吞吐/可用性/漏洞数——可测量）；**阈值**（< 200ms / ≥ 99.9% / = 0——可判定）；**场景**（什么条件下测——「压测 100 并发 × 10 分钟」——脱离场景的阈值无法验证）。**NFR 的书写规范**：每条 NFR 对应「质量属性 + 指标 + 阈值 + 场景 + 验收方式」——**「验收方式」是 NFR 与测试的接口**（压测脚本/监控告警/安全检查——NFR 要能「验收」不能只「承诺」）。

## 3. NFR 与架构选择的映射

**「每条 NFR 都要能追踪到架构选择」**——NFR 不是挂在墙上的口号，而是架构决策的输入与验收：

**映射的姿势**——「P99 < 200ms」这条 NFR → 架构选择：缓存（Redis）、连接池、索引、CDN——**评审时问「这条 NFR 靠什么架构选择达成」**——答不出 = NFR 是口号；**「架构选择要回验 NFR」**——选择缓存后要验证「缓存是否达成了 P99 < 200ms」——**「NFR ↔ 架构选择」是双向的：需求驱动选择、选择回验需求**。

**冲突的质量属性**（权衡的典型场景）：**可用性 vs 一致性**（CAP——分区时保哪个）；**性能 vs 安全**（加密开销）；**演进 vs 简单**（分层 vs 过度设计）——**「冲突的 NFR 要显式排序」**——「优先保证一致性，性能可接受 P99 500ms」——排序写进决策记录（03 篇 ADR 的 Consequences）。

## 4. 差距分析

差距分析（Gap Analysis）是 NFR 治理的实用工具——「现状 vs 目标 vs 差距 vs 优先级」四栏：

```text
| 质量属性 | 目标 NFR | 现状 | 差距 | 优先级 | 行动 |
|---------|---------|------|------|--------|------|
| 性能 | P99 < 200ms | P99 800ms | 4x 差距 | 高 | 缓存 + 索引（Q3） |
| 可用性 | 99.9% | 99.5% | 0.4% | 高 | 多副本 + 故障演练 |
| 安全 | 无高危漏洞 | 3 个高危 | 3 个 | 中 | 依赖升级（Q2） |
| 可测试性 | 覆盖率 ≥ 70% | 45% | 25% | 低 | 测试基建投入 |
```

**差距分析的产出**：**差距清单**（哪些 NFR 未达标——可量化）；**优先级排序**（风险 × 影响——高风险的先治）；**行动项**（每项差距对应架构/工程动作 + 期限——**「差距分析是 NFR 治理的路线图」**——与 08 篇技术债治理的路线图同构（债是「技术债」的差距，这里是「NFR 债」的差距）。

## 5. NFR 检查清单

架构评审（07 篇）与项目启动时的 NFR 检查清单（按项目裁剪）：

- [ ] 性能：P95/P99 阈值 + 压测场景定义
- [ ] 容量：峰值 QPS 预估 + 扩容路径
- [ ] 可用性：SLA 目标 + RTO/RPO 定义
- [ ] 安全：威胁模型 + 安全扫描 + 合规要求
- [ ] 可观测性：日志/指标/追踪 + 告警阈值
- [ ] 可部署性：发布流程 + 回滚机制
- [ ] 可维护性：代码质量门禁（SonarQube 等）
- [ ] 可测试性：测试策略 + 覆盖率目标
- [ ] 数据：数据保留策略 + 备份恢复（RPO/RTO）
- [ ] 每条 NFR：指标 + 阈值 + 场景 + 验收方式 + 负责人

**「检查清单是启动会的一页纸」**——项目立项时 NFR 检查清单过一遍——「上线后才发现要 99.9%」是 NFR 缺失的典型事故——**NFR 在启动时定义、在设计时映射、在验收时验证**。

## 6. 常见坑

**坑一：NFR 不可验收**。「系统要快」——没有指标阈值场景——伪 NFR。

**坑二：NFR 与架构脱节**。NFR 写在文档里、架构选型不看它——映射缺失——「NFR 是墙上的口号」。

**坑三：冲突属性不排序**。一致性 vs 性能不声明优先级——实现时随意取舍——显式排序。

**坑四：场景不定义**。「P99 < 200ms」但没说多少并发——压测 1 并发达标、100 并发不达标——场景必写。

**坑五：差距不治理**。差距分析做完放抽屉——差距清单要行动项 + 期限。

**坑六：NFR 启动时不查**。上线前才发现——NFR 检查清单在立项时过。

**坑七：NFR 没有负责人**。「性能是大家的」= 没人负责——每条 NFR 有 owner。

**NFR 与架构评审、技术债的联动**（本体系三篇的闭环）：**评审（07 篇）以 NFR 为输入**——ATAM 的场景就是 NFR 的测试用例（「NFR 定义 → 评审场景 → 架构对照」）；**债治理（08 篇）与 NFR 相关**——「NFR 未达标的差距」就是「NFR 债」（差距分析清单与技术债清单统一治理——「性能不达标」既是一条差距也是一笔债）；**fitness functions（09 篇）是 NFR 的自动化验收**——「架构约束校验」本质是「可自动化的 NFR 校验」——**「NFR 从定义到治理的完整链路：定义（本篇）→ 评审（07）→ 债（08）→ 自动化（09）」**——NFR 不是文档章节，是贯穿架构治理全流程的原料。
