## 1. 治理的目标

架构治理（Governance）的目标一句话：**「让架构持续符合质量属性目标」**（05 篇 NFR）——不是「管住团队」而是「保证架构不腐化」：**架构腐化的典型路径**——设计时符合目标 → 演进中「临时方案」叠加 → 约束被绕过 → NFR 悄然失守——**治理是在腐化发生前/早期介入的机制**。

**治理的 2026 姿态：「赋能改变而非阻止改变」**（01 篇）——传统治理是「审批」（架构委员会卡人——慢且对抗）；现代治理是「自动化 + 文化」（fitness functions 自动校验 + 团队自治 + 架构师引路）——**「治理的产出是「团队能安全地做正确的事」，不是「团队做不了事」**——治理工具的演进：人肉审批 → 检查单 → 自动化校验（下节）。

## 2. Fitness Functions 适应度函数

**Fitness Function（适应度函数）= 自动化校验架构约束的检查**——「架构的单元测试」——持续验证系统是否仍符合架构目标：

**常见形态**（Java 生态）：**ArchUnit**——Java 架构约束测试（「Service 层不得依赖 Repository 层以外的类」「只有 Controller 可以访问 Web 包」——依赖规则即测试）；**NetArchTest**（.NET 对应）、**dependency-cruiser**（JS/TS 依赖图校验）；**包/依赖检查**——循环依赖检测、包边界校验；**质量门禁**——覆盖率阈值、复杂度阈值（SonarQube——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/开发/代码质量/00-代码质量管理体系总览|代码质量体系]] 的门禁机制）。

```java
// ArchUnit 示例：依赖规则即测试
@AnalyzeClasses(packages = "com.example.order")
public class ArchitectureTest {
    @Test
    void service_should_not_depend_on_controller() {
        classes().that().resideInAPackage("..service..")
            .should().notDependOnClassesThat().resideInAPackage("..controller..")
            .check(new ClassFileImporter().importPackages("com.example.order"));
    }
}
```

**Fitness Functions 的价值**：**约束持续生效**（每次 CI 都校验——「临时绕过」在合并前被拦——架构约束从「口头约定」变成「机器执行」）；**变更可安全演进**（改架构时跑 fitness——「约束破坏」立即暴露——演进有安全网）；**治理自动化**（替代人肉审批的重复检查——「治理的成本从人时变成机器时」）。

## 3. Tech Radar 技术雷达

**Tech Radar（技术雷达）**——团队技术选型的共识视图：四象限（Adopt/Trial/Assess/Hold）分类技术：

**四个环的含义**：**Adopt（采用）**——团队推荐使用的成熟技术；**Trial（试验）**——值得试点验证的技术；**Assess（评估）**——值得关注的技术（调研中）；**Hold（暂缓）**——不推荐/停止使用的技术（有坑、过时、被替代——**「Hold 是防「简历驱动选型」（06 篇反模式）的武器——「新技术来了先看雷达在哪个环」**）。

**雷达的运作**：**定期更新**（季度/半年评审——新技术的评估结果入环）；**团队共识**（雷达是团队的选型决策记录——「为什么它被 Hold」有依据（ADR 配合——**「雷达 = 选型决策的集合视图」**）；**发布形态**（团队内网页面/文档——「选型先看雷达」是团队默认动作）。**雷达的价值**：**选型视野统一**（团队不各自为政地试新技术）；**技术债预防**（Hold 的技术不新引入——「雷达管入口」）。

## 4. 参考架构与标准

**参考架构（Reference Architecture）**——团队沉淀的「标准架构模板」：**微服务参考架构**（服务拆分规范、网关、注册中心、可观测性标配）、**Monolith First 参考架构**（模块化单体模板）、**事件驱动参考架构**（消息规范、事件命名、Outbox 标配）——**「参考架构 = 已验证的最佳实践固化」**——新项目按参考架构起步（「不重复发明架构」）；**参考架构的治理**：**与模式库（06 篇）配合**（参考架构是「我们验证过的模式组合」）；**随实践演进**（季度评审更新——参考架构不是铁律是共识）。

**标准化的边界**：**「标准到能执行、松到能演进」**——过度标准化（什么都规定）扼杀创新（治理的「赋能而非阻止」）；缺乏标准（什么都能）导致混乱——**「标准的粒度 = 风险敏感度」**（高风险领域（支付/安全）严标准，低风险领域松标准）。

## 5. 演进式架构

**演进式架构（Evolutionary Architecture）**——「把变化当作设计的一部分」的架构观：**架构不是「一次设计完」而是「持续演进」**（与 Big Upfront Design 反模式对照，06 篇）——演进式架构的支撑三要素：**可演进性作为一等质量属性**（NFR 里显式定义「系统应能支持 X 方向的演进」——05 篇）；**fitness functions 作为演进安全网**（每次演进跑校验——「改架构不破坏约束」——第 2 节）；**增量演进**（小步变更 + 持续验证——Strangler Fig 模式——「大重构拆成小演进」）。

**演进式架构与 ADR/评审**：**演进 = 新决策 + 决策记录**（每次演进是一条新 ADR——Superseded 旧 ADR——决策链即演进史，03 篇）；**评审是演进的关卡**（每次重大演进过评审——07 篇）——**「治理让演进有序：fitness 管约束、ADR 管决策、评审管关卡」**。

## 6. 变更治理

**变更治理（Change Governance）**——「架构约束变更」与「违反约束」的治理机制：**约束变更流程**——架构约束（fitness functions 的规则）本身可变更（业务演进需要）——**变更走评审 + ADR**（「为什么约束要变」有记录——防「约束悄悄放松」）；**违反治理（Waiver）**——「临时绕过约束」的审批机制：**waiver 治理规范**——临时豁免要申请（原因 + 期限 + 责任）；**到期自动升级**（豁免到期未解决 → 自动升级告警——「临时豁免变成永久豁免」是腐化路径——**「豁免要有到期机制」**）；**豁免率是治理健康度指标**（豁免率高 = 约束与业务脱节——约束该调整了）。

## 7. 常见坑

**坑一：治理 = 审批**。人肉卡人——自动化（fitness）+ 文化。

**坑二：fitness 只写不跑**。约束测试写了不进 CI——约束失效——fitness 进流水线。

**坑三：约束不可变更**。约束是铁律不可动——业务演进时约束僵化——约束变更走 ADR。

**坑四：豁免无期限**。临时豁免永久化——到期自动升级。

**坑五：雷达不更新**。雷达是历史文物——定期评审。

**坑六：参考架构当铁律**。标准扼杀演进——「标准到能执行、松到能演进」。

**坑七：治理只做一次**。运动式治理——持续机制（CI 校验 + 定期评审）。
