## 3. 学习路线推荐

**路线一：设计基础（1-2 天）**——01 → 02 → 03 → 10。目标：掌握子系统识别与模块化原则，能画出子系统边界。

**路线二：契约与数据（3-4 天）**——路线一 + 04 → 05。目标：接口契约设计 + 数据设计，能产出子系统设计文档的核心部分。

**路线三：完整设计（一周）**——路线二 + 06 → 09。目标：性能/可靠性/安全/可观测四维设计全覆盖，独立完成子系统设计文档。

**先厘清定位**：本体系是纵向级别体系之一——与 [[../L1：初级开发｜看懂架构，落地模块|L1]]（看懂架构落地模块）、[[../L2：中级开发｜模块级设计|L2]]（模块内设计）、[[../L4：架构师｜全局系统架构|L4]]（全局架构）构成成长阶梯：**L3 是「一个子系统的设计者」**——横向通用方法论（[[../横向通用能力/00-横向通用能力总览|横向通用能力]]）提供权衡/ADR/NFR/评审工具，本体系把这些工具用在「子系统设计」这个场景。

## 4. 核心概念速查

| 概念 | 一句话 |
|------|-------|
| 子系统 | 系统的语义边界单元（业务能力聚合） |
| Common Closure | 同一原因变化的类聚一起（边界识别原则） |
| 依赖规则 | 依赖指向稳定方向（内聚的依赖向内） |
| 独立团队测试 | 「能否由独立团队拥有」——子系统边界的检验 |
| 深模块 | 简单接口隐藏复杂实现（复杂度拉进模块） |
| 复杂度三指标 | change amplification / cognitive load / unknown unknowns |
| 显式 API 面 | 公共接口明示 + 排除内部实现（黑盒设计） |
| 可替换性测试 | 能否仅凭接口重写模块（契约完整性的检验） |
| 数据所有权 | 数据有且只有一个拥有者子系统 |
| 性能预算 | NFR 的性能指标分解到子系统的预算表 |
| 故障模式分析 | 枚举故障 + 设计对应韧性机制 |
| 幂等 | 重复执行结果一致（接口与消费的可靠性基础） |
| 威胁建模 | 安全设计前置：资产/威胁/缓解 |
| 三支柱 | 日志/指标/追踪（可观测性） |
| 运维就绪 | 设计时考虑部署/配置/监控/回滚 |

## 5. 常见误区

**误区一：子系统按技术层划分**。「Controller 子系统、Service 子系统」——按业务能力划分（订单子系统、支付子系统）——技术层划分是「技术耦合的伪装」（03 篇反模式）。

**误区二：接口 = 方法的集合**。接口是「契约」——含数据模型、错误语义、版本、兼容策略——「方法列表只是契约的骨架」。

**误区三：把内部数据模型当公共契约**。DTO 直接暴露数据库表结构——调用方与实现耦合——「暴露内部模型 = 伪装成模块化的紧耦合」。

**误区四：子系统设计不含非功能**。只画功能模块图——性能/可靠性/安全/可观测是设计的一部分（06-09 篇）——「NFR 缺失的子系统设计是半成品」。

**误区五：抽象越多越好**。为「将来可能的变化」抽象一切——YAGNI——「为已知变化设计，不为猜测变化设计」。

**误区六：边界画完就完事**。边界是「设计 + 治理」——依赖方向要校验（ArchUnit）、契约要版本化——「边界不治理会悄悄腐化」。

**误区七：设计文档写完就扔**。设计文档是「活的」（与代码同演进）——组件目录、契约、ADR 配套——「文档过期 = 设计失效」。
