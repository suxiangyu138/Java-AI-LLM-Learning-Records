# 02-子系统识别与边界

## 1. 子系统的本质

**子系统 = 系统的语义边界单元**——一组「因同一业务目的而聚合」的能力与数据，对外通过显式契约协作（04 篇）。子系统的本质判断：**它是一段「可独立理解的业务故事」**——「订单子系统」讲的是「订单从创建到完成的生命周期」，「支付子系统」讲的是「资金从发起到结算」——**「子系统是业务叙事的边界，不是代码结构的边界」**。

**子系统 vs 模块 vs 服务**：粒度递进——模块（模块内代码组织）< 子系统（业务能力聚合，可独立团队拥有）< 服务（可独立部署——子系统的一种部署形态）——**「子系统是逻辑概念，服务是部署概念」**——模块化单体里子系统是模块边界（内部边界），微服务里子系统是服务边界（网络边界）——**「L3 设计的是逻辑子系统，部署形态由 L4 决定」**。

## 2. 识别方法：业务能力地图

子系统识别的标准方法——**业务能力地图（Business Capability Map）**：**第一步，列出业务能力**——从业务视角枚举「系统要做什么」：「订单管理、支付结算、库存管理、用户管理、营销活动、报表分析」——**能力是业务名词，不是技术名词**；**第二步，聚合相关能力**——按「业务故事」聚合（订单 + 履约 + 售后 = 订单子系统；支付 + 退款 + 对账 = 支付子系统）；**第三步，检验聚合**——每个聚合是否「可独立理解、有清晰边界、有独立数据」；**第四步，画边界**——子系统清单 + 一句话职责（**「每个子系统有一句能讲清的话」是边界清晰的标志**）。

**「从业务开始，不从技术开始」**——「先有技术方案再往上套业务」是边界错位的根源——**「业务能力地图是边界的原材料」**。

## 3. Common Closure 原则

Common Closure Principle（共同封闭原则）——**「因同一原因变化的类/模块聚在一起」**——边界识别的高阶原则：**「把一起变化的放一起，把不同步变化的隔开」**：

**应用姿势**：**变化分析**——「哪些代码会因同一个业务需求一起改」（订单价格规则变化 → 订单子系统的价格模块一起改）；**边界划分的检验**——「两个模块因同一原因经常一起改 → 该合并；几乎不同步改 → 该分离」；**与依赖方向的配合**——「变化频繁的模块应该被稳定模块依赖，而非反向」（依赖指向稳定——03 篇依赖规则）。**「边界是变化边界的映射」**——**「子系统的边界应该对齐业务的演化边界」**——业务怎么变，子系统就怎么切——这是 Common Closure 的深层含义。

## 4. 边界检验：独立团队测试

**「独立团队测试」——边界是否正确的终极检验**：**「这个子系统能否由一个独立团队拥有并交付」**——检验的四个问题：**职责独立吗**——子系统能否独立理解（一句职责讲得清）；**接口独立吗**——能否仅凭契约协作（不需要理解内部实现——黑盒，04 篇）；**数据独立吗**——数据所有权清晰（自己的数据自己管，05 篇）；**变化独立吗**——子系统内部变化不需要其他子系统同步配合（Common Closure）。

**检验的用途**：**边界识别的验收**（画完边界过一遍独立团队测试——四个问题都答「是」边界才成立）；**团队组织的输入**（「一个团队一个子系统」是现代组织的标准形态——**「边界设计 = 团队边界设计」**——边界错了，团队协作就错）。

## 5. 边界与数据所有权

**数据所有权（Data Ownership）是边界的内涵**——「每个数据项有且只有一个拥有者子系统」：**拥有的含义**——数据的写入与变更只有拥有者可以做，其他子系统通过契约读写（「别人要数据，问拥有者要，不能自己动库」）；**共享数据的边界问题**——「多子系统共用一张表」是边界失效的信号（反模式——「共享数据库」）；**数据所有权与契约**——「拥有者通过接口暴露数据（04 篇），消费者通过接口获取」——**「数据所有权 = 边界的物理表达」**——边界不只是代码的边界，是数据的边界（05 篇展开）。

## 6. 常见反模式

**反模式一：按技术层划分**——Controller 子系统/Service 子系统——技术耦合的伪装——按业务能力。**反模式二：上帝子系统（God Subsystem）**——一个子系统承载过多职责（「公共子系统」往往是垃圾桶）——职责不清晰就拆。**反模式三：共享数据库**——多子系统共用表——边界失效——数据所有权。**反模式四：边界画在技术方便处**——「这个表放这方便」——边界画在业务语义处。**反模式五：边界过细**——子系统切到模块级（「用户登录子系统」）——边界过细 = 协作成本高——「子系统的粒度与团队规模匹配」。
