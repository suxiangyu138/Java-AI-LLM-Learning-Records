## 1. 接口 = 契约

**「接口不是方法的集合，是契约」**——方法的集合只定义了「能调什么」，契约还定义了「怎么调、返回什么、失败怎么办、怎么演进」——**「接口是子系统之间的法律文件」**：调用方基于契约开发（不依赖实现），实现方基于契约变更（不破坏调用方）——**「契约让双方独立演进」是接口设计的根本目的**。

**契约思维 vs 方法思维的差异**：方法思维问「这个接口有哪些方法」；契约思维问「这个接口的完整语义是什么」——参数约束、返回结构、错误语义、幂等性、并发语义、版本兼容——**「契约思维是 L3 的标志」**——L2 设计模块接口（方法级），L3 设计子系统契约（协议级）。

## 2. 显式 API 面

**显式 API 面（Explicit API Surface）——公共接口明示 + 内部实现排除**：**明示什么**——对外接口（方法/端点/事件）、数据模型（DTO/事件结构）、错误语义（错误码/异常类型）、通信机制（REST/gRPC/事件）；**排除什么**——内部模型（数据库实体、内部工具类）、内部实现细节（缓存策略、算法）、内部依赖（「调用方不需要知道的都是内部」）。

**显式 API 面的工程落地**：**API 目录**——子系统的公共接口清单（名称、职责、版本——组件目录，09 篇设计文档的一部分）；**黑盒纪律**——「调用方只能通过 API 目录接触子系统」——**「内部实现类被外部直接使用 = API 面失守」**（代码评审检查项——「这个类在 API 面外被引用了」）；**信息隐藏**（[[../../../04-设计模式/01-面向对象设计原则与UML|设计原则]] 的模块级应用）——「接口暴露最少必要信息」。

## 3. 黑盒设计与可替换性测试

**黑盒设计（Black-box Design）——接口定义不含实现细节**：**「可替换性测试」是黑盒设计的检验**——「仅凭接口文档，能否重写这个子系统」——三个问题：**接口完整吗**（重写需要的信息接口都有吗）；**语义清晰吗**（参数约束、错误行为、边界条件是否无歧义）；**无实现泄漏吗**（接口里有没有「实现才知道的隐式约定」——如「调用前必须先调 init」——隐式约定 = 黑盒破裂）。

**可替换性测试的用途**：**接口质量验收**（新接口设计完「试替换」一遍——按文档重写 mock 实现——写不出来 = 文档不全）；**演进安全**（替换实现不换接口——「接口稳定，实现随意换」——**可替换性 = 子系统可演进性的保障**（Strangler Fig 迁移的接口前提）。

## 4. 契约的组成

一份完整的子系统接口契约（以 REST 接口为例——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 体系]] 的子系统版）：**接口定义**——方法/路径/参数（含类型与约束）；**数据模型**——DTO 结构（字段、类型、可选性、示例——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|契约设计]]）；**错误语义**——错误码/错误结构/错误场景（「每个错误码的含义与调用方的处理建议」）；**行为语义**——幂等性（是否幂等、幂等键）、一致性（最终一致/强一致）、并发语义（乐观锁）；**版本与兼容**——版本号、变更策略（向后兼容承诺）、废弃流程；**非功能声明**——性能预期（P95）、限流策略、可用性承诺——**「契约的完整度 = 调用方无需问人即可集成」**。

## 5. 契约优先与版本化

**契约优先（Contract-first）——先定契约再写实现**：**子系统间协作的默认姿势**——「先约定接口（OpenAPI/事件结构），双方并行开发」（前端与后端、本子系统与依赖子系统——**契约是并行开发的边界**）；**契约的载体**——OpenAPI（REST）、proto（gRPC）、事件 schema（消息——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/03-消息队列/消息队列理论与实战/00-消息队列理论与实战总览|消息队列体系]] 的事件契约）；**契约的版本化**——**语义化版本（major.minor.patch——major 破坏性变更）** + 向后兼容策略（新增字段兼容、删除字段破坏——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/RESTful%20API/00-RESTful%20API总览|RESTful 版本化]]）；**契约的治理**——契约进仓库、变更走评审（ADR——[[../横向通用能力/03-架构决策记录ADR|横向 ADR]]）、破坏性变更检测自动化（oasdiff 类工具——[[../横向通用能力/09-治理与演进|治理]] 的契约维度）。

## 6. 同步与异步接口

**接口的两种协作模式，按场景选择**：**同步接口（REST/gRPC）**——请求-响应、即时结果——适用「需要结果才能继续」的场景（查询、简单操作）；**异步接口（消息/事件）**——发送即返回、结果后续通知——适用「解耦、削峰、长流程」的场景（订单状态流转、通知）——**选型标准**：**需要结果吗**（要 → 同步；不要 → 异步）；**能容忍延迟吗**（不能 → 同步；能 → 异步）；**需要削峰解耦吗**（需要 → 异步）。

**异步接口的契约特殊性**：**事件结构即契约**（事件 schema 版本化——「消费者按版本消费」）；**at-least-once 语义**（消费方要幂等——[[../横向通用能力/06-架构模式知识地图|模式地图]] 的幂等与 Outbox）；**失败语义**（投递失败/消费失败的重试与死信——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/03-消息队列/消息队列理论与实战/00-消息队列理论与实战总览|消息队列体系]] 的可靠性）。

## 7. 常见坑

**坑一：接口 = 方法列表**。契约四要素（定义/数据/错误/行为）缺错误与行为——调用方全靠问。

**坑二：暴露内部模型**。DTO 透出数据库实体——耦合——显式 API 面。

**坑三：隐式约定**。「调用前先调 X」——黑盒破裂——语义写进契约。

**坑四：不版本化**。接口改了调用方崩——语义化版本 + 兼容策略。

**坑五：同步异步混用不清**。该异步的同步（长流程阻塞）——按选型标准。

**坑六：契约不治理**。契约不进仓库、不评审——破坏性变更悄悄上——契约治理（进仓 + 评审 + 检测）。

**坑七：重写不验**。接口改完不验证「可替换性」——按文档重写 mock 验证。
