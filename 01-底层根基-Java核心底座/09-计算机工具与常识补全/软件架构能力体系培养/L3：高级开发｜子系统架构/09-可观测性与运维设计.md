## 1. 可观测性思维

**可观测性（Observability）——「系统内部状态能否从外部输出推断」**——**「上线后系统是不可见的」是最差的设计**：故障时只能「重启试试」——可观测性设计的目标：**「故障时能回答三个问题：发生了什么、为什么、影响多大」**。

**可观测性的设计前置**——不是「上线后再接监控」而是**设计时定义「这个子系统要观测什么」**：**关键路径可观测**（核心链路的日志/指标/追踪齐备）；**故障路径可观测**（异常、重试、降级有迹可循——「故障发生时是最需要可观测性的时刻」）；**业务可观测**（业务指标——订单量、支付成功率——「业务健康度」）。**「可观测性是 NFR 之一」**（[[../横向通用能力/05-质量属性与NFR|可观测 NFR]]——「关键路径 P99 可查询、异常可告警」）。

## 2. 三支柱：日志/指标/追踪

可观测性的三支柱（[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|日志监控体系]] 的子系统版）：**日志（Logs）**——事件记录（「发生了什么」——请求日志、错误日志、审计日志——详情维度）；**指标（Metrics）**——数值度量（「系统怎么样」——QPS、延迟、错误率、资源——趋势维度）；**追踪（Traces）**——请求链路（「请求经过了谁」——跨服务调用链——关联维度）——**「日志看细节、指标看趋势、追踪看链路」**——三支柱配合：指标异常 → 追踪定位链路 → 日志看细节。

**三支柱的实现**：**日志**——结构化日志（JSON——机器可解析——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|日志体系]] 的 loguru/logback 结构化）；**指标**——Micrometer/Prometheus（[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|JVM 监控]] 的指标族）；**追踪**——OpenTelemetry（trace id 贯穿——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|OTel 体系]]）。

## 3. 日志设计

子系统日志设计的要点（L3 视角的日志规范）：**日志分类**——请求日志（方法/路径/状态/耗时/trace id）、错误日志（异常栈——堆栈只进日志不进响应）、审计日志（敏感操作——谁/何时/做了什么——[[../横向通用能力/05-质量属性与NFR|安全 NFR]] 的审计要求）、业务日志（业务事件——订单状态流转）；**日志规范**——**结构化**（JSON——字段可查询——「日志是数据不是文本」）、**上下文贯穿**（trace id + 用户 id——「一条请求的所有日志能串起来」）、**脱敏**（敏感字段打码——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|日志脱敏]] 纪律——手机号/Token 不打明文）；**日志分级**——级别语义（INFO 业务/DEBUG 调试/WARN 隐患/ERROR 故障——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|级别治理]]）——**「日志量治理」**——生产日志量预算（全量请求日志 vs 采样——量大时采样——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|成本三件]]）。

## 4. 指标与告警

**指标设计**（L3 的指标清单）：**RED 指标**（请求维度——Rate 请求率/Errors 错误率/Duration 延迟——**「每个子系统都有 RED」**）；**USE 指标**（资源维度——Utilization 利用率/Saturation 饱和/Errors 错误——CPU/内存/连接池/磁盘）；**业务指标**（订单量、转化率——业务健康度）；**指标打点**——关键路径打点（P99 是核心——[[../横向通用能力/05-质量属性与NFR|性能 NFR]] 的监控面）。

**告警设计**：**告警阈值**（P99 超预算、错误率超 1%、连接池饱和——**「阈值来自 NFR/预算」**——不是拍脑袋）；**告警分级**（P1 立即响应/ P2 当班处理/P3 记录跟进——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|告警分级]]）；**告警疲劳治理**（阈值校准——「告警多到没人看 = 没有告警」——[[../横向通用能力/05-质量属性与NFR|SLO 驱动的告警]]——「告警要少而准」）。

## 5. 分布式追踪

**分布式追踪（Distributed Tracing）——跨子系统请求链路的关联**：**trace id 贯穿**——请求入口生成 trace id → 全链路传递（HTTP 头/消息头）→ 各子系统日志与 span 带同一 trace id——**「trace id 是分布式排障的索引」**——「报障时给 trace id，全链路日志/span 一键拉出」；**span 与链路**——每个子系统的处理是一个 span（开始/结束/耗时/状态）——链路视图（OpenTelemetry + Jaeger/Zipkin——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|OTel 体系]]）；**追踪的设计配合**——**「子系统要透传 trace 上下文」**（HTTP 拦截器/消息生产者消费者——「不透传 = 链路断裂」——**「trace 透传是 L3 的接口设计一部分」**（04 篇契约的横切面）。

## 6. 运维就绪设计

**运维就绪（Operability）——设计时考虑运维**：**部署设计**——发布流程（灰度/回滚——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/CI%20CD灰度发布|CI/CD 体系]]）、配置管理（配置外置——环境变量/配置中心——「配置即代码」）；**优雅停机**——停机时先摘流量再停服务（处理完在途请求——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/SpringBoot%20Web/00-SpringBootWeb总览|优雅停机]] 的实现）；**健康检查**——就绪/存活探针（K8s——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/11-云原生/Docker/00-Docker总览|容器化]] 的探针设计——**「健康检查端点设计在开发期，不是运维期」**）；**运维文档**——部署手册、故障手册（故障模式分析的运维面——07 篇的故障清单 → 故障手册）。

## 7. 常见坑

**坑一：可观测性事后补**。上线再接监控——设计时定观测清单。

**坑二：日志无结构**。文本日志不可查询——结构化 JSON。

**坑三：trace 不透传**。链路断裂——trace id 贯穿是设计一部分。

**坑四：告警无阈值依据**。拍脑袋告警——阈值来自 NFR/预算。

**坑五：告警疲劳**。告警多到没人看——少而准。

**坑六：无健康检查**。探针是运维期才想——设计期定义端点。

**坑七：无优雅停机**。停机杀请求——摘流量再停。
