## 1. 性能设计思维

**「性能是设计出来的，不是调出来的」**——架构层面的性能决策（缓存、异步、索引、批量）在设计期定，运行期调优（JVM 参数、SQL 微调）只能救急——**「设计期的性能决策决定性能的天花板」**。

**性能设计的三个前提**：**性能目标是 NFR 的一部分**（[[../横向通用能力/05-质量属性与NFR|可验收 NFR]]——「P95 < 200ms」而非「要快」）；**性能设计贯穿设计流程**（不是最后一步——每个设计决策问「对性能的影响」——[[../横向通用能力/02-架构权衡与决策|权衡]] 的性能维度）；**性能有代价**（缓存的一致性代价、异步的复杂度代价——「性能手段是权衡不是免费午餐」——**「性能优化是有预算的投资」**。

## 2. 性能预算

**性能预算（Performance Budget）——把系统的性能 NFR 分解到子系统/链路**：**预算的分解**——端到端 P95 200ms → 网关 10ms + 服务 A 80ms + 服务 B 60ms + 存储 40ms + 余量 10ms——**「每个环节有性能配额，超配即超标」**；**预算的用途**——**设计约束**（「这个环节只有 80ms——同步调用两次就不够——设计要异步/批量」）；**评审依据**（设计评审检查「预算表」——每个环节的耗时估算与手段）；**验收基准**（压测对照预算——「哪个环节超预算」定位性能问题）。

**预算表的形态**（设计文档的一部分）：链路环节 × 预算耗时 × 设计手段 × 验证方式——**「性能预算让性能从口号变成可执行的约束」**。

## 3. 容量规划

**容量规划（Capacity Planning）——按业务预期算资源需求**：**三步**：**业务量预估**——峰值 QPS、数据量增长（「未来一年的业务预期」——来自产品/运营——不确定就做场景假设：乐观/基准/悲观三档）；**资源测算**——单请求资源成本（CPU/内存/IO——压测或经验值）→ 总资源需求（QPS × 单请求成本）；**容量设计**——「当前规模怎么部署 + 增长怎么扩」（水平扩容路径——无状态服务好扩、数据库是瓶颈——**「容量规划的核心是识别扩容瓶颈」**）。

**容量规划与性能的关系**：**性能是「单请求多快」，容量是「系统能扛多少」**——性能达标 ≠ 容量达标（单请求 100ms 但 1000 QPS 就崩）——**「性能 + 容量一起设计、一起验证」**（压测的并发梯度验证容量拐点——[[../横向通用能力/05-质量属性与NFR|容量 NFR]]）。

## 4. 设计级性能手段

L3 的性能手段库（设计期可决策的手段，按「投入产出」排序）：**索引与查询优化**——数据库索引、查询改写（最便宜、最高频——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MySQL|MySQL 体系]]）；**缓存**（05 篇——读多写少的热点——性能收益最大）；**异步化**——同步改异步（不需要结果的操作走消息——削峰 + 解耦——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/03-消息队列/消息队列理论与实战/00-消息队列理论与实战总览|消息队列]]）；**批处理**——逐条改批量（批量写、批量查——IN 查询替代循环）；**并发设计**——并行调用（无依赖的多个调用并行——异步编排）、连接池/线程池调优；**数据架构**——读写分离、分库分表（量大时的架构手段——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MySQL|MySQL 体系]] 的高可用与分片）。

**手段选择的顺序**：**先查询优化 → 缓存 → 异步/批量 → 架构手段**——「从便宜到贵」——**「性能手段是递增的投资，不是一开始就上最强手段」**（防过度设计——03 篇反模式）。

## 5. 压测与验证

**性能设计的验证靠压测**（设计 → 实现 → 压测 → 对照预算）：**压测方法论**——变并发梯度（10/50/100/200...）找拐点（吞吐停滞/延迟陡增的并发值）、记录 P50/P95/P99、区分 TTFT/吞吐（[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/MySQL%20Redis%20MQ%20运维相关故障现象|运维体系]] 的压测纪律）；**压测工具**——JMeter/Locust/wrk（[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/测试|测试体系]]）；**压测结果的使用**——对照性能预算（哪个环节超预算 → 定位手段）、得出容量拐点（生产配额 = 拐点的一半——余量纪律）、回归基准（每次性能相关改动后跑基准——「性能回归测试」）。

## 6. 性能治理

**性能的持续治理**（设计后的保鲜）：**性能基准进 CI**（关键链路的压测基准——改动触发基准对比——「性能回归在合入前被发现」——[[../横向通用能力/09-治理与演进|fitness functions]] 的性能版）；**性能监控**（生产 P95/P99 监控 + 告警——[[../../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/日志监控指标/00-日志监控指标总览|日志监控体系]]）；**性能评审**（重大改动的性能影响评审——「这个改动会不会突破预算」）；**性能债**（性能欠账记账——[[../横向通用能力/08-技术债治理|技术债治理]] 的性能维度——「性能不达标的差距」入债清单）。

## 7. 常见坑

**坑一：上线后调优**。性能设计缺失的补救——设计期定预算与手段。

**坑二：性能目标不可验收**。「要快」——预算表 + 压测基准。

**坑三：只测单请求**。不测并发——容量拐点未知——并发梯度压测。

**坑四：缓存不防三问**。穿透击穿雪崩（05 篇）——三问必答。

**坑五：手段一次上满**。上来就分库分表——从便宜到贵。

**坑六：压测不照预算**。压测完没对照预算表——定位超预算环节。

**坑七：性能不治理**。基准不进 CI、监控不设——性能回归无人知。
