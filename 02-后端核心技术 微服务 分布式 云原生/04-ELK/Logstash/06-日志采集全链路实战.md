## 1. 全链路架构总览

```text
SpringBoot 应用（JSON 结构化日志）
    │ logback 输出到文件
    ▼
Filebeat（每台服务器，采集 + 压缩 + 断点）
    │ 5044 / TLS
    ▼
Logstash（解析清洗 + 路由 + 富化）
    │ 批量写入
    ▼
Elasticsearch（Data Stream + ILM 热温冷删）
    │
    ▼
Kibana（Discover 检索 + Dashboard 看板 + Alerting 告警）
```

| 环节 | 组件 | 关键配置点 |
|:---:|------|------|
| ① 应用侧 | logback 输出 JSON | 统一格式：ts/level/service/msg/requestId |
| ② 采集 | Filebeat | 路径、multiline、断点 |
| ③ 管道 | Logstash | json 解析、date 校准、脱敏、路由 |
| ④ 存储 | ES Data Stream + ILM | rollover、保留期 |
| ⑤ 展示 | Kibana | 看板结构、告警规则 |

## 2. 第一步：应用侧结构化日志

### 2.1 为什么日志要 JSON 化

```text
文本日志：依赖 grok 正则猜格式，解析慢、易漂移
JSON 日志：logstash json 插件直接结构化，快且稳

收益：
  · 免正则：解析成本降到最低
  · 字段天然语义化（level/service/requestId 直接可检索）
  · 与 traceId 打通：日志链路追踪
```

### 2.2 logback JSON 配置（SpringBoot）

```xml
<!-- logback-spring.xml：JSON 格式输出 -->
<configuration>
    <appender name="JSON_FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_PATH:-/app/logs}/app.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>${LOG_PATH:-/app/logs}/app.%d{yyyy-MM-dd}.log</fileNamePattern>
            <maxHistory>7</maxHistory>
        </rollingPolicy>
        <encoder class="net.logstash.logback.encoder.LogstashEncoder">
            <customFields>{"service":"order-service","environment":"prod"}</customFields>
        </encoder>
    </appender>
    <root level="INFO">
        <appender-ref ref="JSON_FILE"/>
    </root>
</configuration>
```

### 2.3 输出效果与 MDC 上下文

```json
{"@timestamp":"2026-08-07T14:00:01.123Z",
 "level":"ERROR",
 "message":"订单超时",
 "service":"order-service",
 "environment":"prod",
 "logger_name":"com.demo.OrderService",
 "requestId":"abc123",           // 来自 MDC
 "user_id":10001,                // 来自 MDC
 "stack_trace":"java.util.concurrent.TimeoutException: ..."}
```

```java
// 代码中写入 MDC（链路追踪贯穿）
MDC.put("requestId", traceId);
MDC.put("user_id", String.valueOf(userId));
logger.error("订单超时: {}", orderId);
```

> 🎯 实战要点：**MDC 放关键上下文（requestId/userId）**，日志检索时按 requestId 拉全链路，是排障效率的分水岭。

## 3. 第二步：Filebeat 边缘采集

### 3.1 filebeat.yml 核心配置

```yaml
# filebeat.yml
filebeat.inputs:
  - type: filestream          # 9.x 推荐 filestream 类型
    id: order-service-logs
    enabled: true
    paths:
      - /app/logs/app.log
    # 多行合并（Java 堆栈）：9.x 用 multiline 配置块
    multiline:
      type: pattern
      pattern: '^\{'          # JSON 行起始标志（非缩进行）
      negate: true
      match: after

output.logstash:
  hosts: ["logstash-node:5044"]
  # ssl.certificate_authorities: ["/etc/filebeat/certs/ca.crt"]

setup.ilm.enabled: false      # 数据流/索引管理交给 ES 模板
```

### 3.2 Filebeat 关键机制

| 机制 | 说明 |
|------|------|
| 断点续读 | registry 记录读取位置，重启不丢不重 |
| 背压 | Logstash 慢时自动暂停采集 |
| 压缩 | 默认 gzip 压缩传输 |
| filestream vs log | filestream 是 9.x 推荐的新输入类型 |
| multiline | 堆栈合并放在采集侧（比 Logstash 侧轻） |

## 4. 第三步：Logstash 管道设计

### 4.1 生产管道示例

```ruby
# /etc/logstash/pipeline.d/logs.conf
input {
  beats {
    port => 5044
    host => "0.0.0.0"
  }
}

filter {
  # ① JSON 解析（应用日志已是 JSON）
  json {
    source => "message"
  }

  # ② 时间校准（用日志自带时间）
  date {
    match => ["@timestamp", "ISO8601"]
  }

  # ③ 脱敏（敏感字段移除）
  mutate {
    remove_field => ["password", "token"]
  }

  # ④ 富化标记
  mutate {
    add_field => { "ingest_time" => "%{+yyyy-MM-dd'T'HH:mm:ss.SSSZ}" }
    add_tag => ["processed"]
  }

  # ⑤ 解析失败标记保留原始
  if "_jsonparsefailure" not in [tags] {
    mutate { remove_field => ["message"] }
  }
}

output {
  # 主链路：写数据流
  elasticsearch {
    hosts => ["http://es-node1:9200", "http://es-node2:9200"]
    data_stream => "true"
    data_stream_type => "logs"
    data_stream_dataset => "app"           # → logs-app.app-*
    user => "logstash_internal"
    password => "${ES_PASSWORD}"
    dead_letter_queue_enable => true
  }

  # 失败解析单独索引，盯配置漂移
  if "_jsonparsefailure" in [tags] {
    elasticsearch {
      hosts => ["http://es-node1:9200"]
      index => "parse-failures-%{+YYYY.MM.dd}"
    }
  }
}
```

### 4.2 管道设计的五个注意点

| # | 注意点 | 说明 |
|:---:|------|------|
| 1 | data_stream 模式 | 9.x 推荐，自动对接 ILM |
| 2 | 失败单独索引 | 发现日志格式漂移 |
| 3 | 环境变量密码 | 不把密码写死配置 |
| 4 | 语法校验 | 上线前 `--config.test_and_exit` |
| 5 | PQ 开启 | 重要链路开持久队列 |

## 5. 第四步：ES 数据流与 ILM

### 5.1 数据流（Data Stream）结构

```text
logs-app.app-*（数据流别名）
  ├─ .ds-logs-app.app-2026.08.06-000001（热）
  ├─ .ds-logs-app.app-2026.08.07-000002（热）
  └─ ... 按 rollover 自动滚动
```

### 5.2 ILM 策略（30 天保留）

```yaml
# ES 侧创建策略
PUT _ilm/policy/logs-30d
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_size": "50gb", "max_age": "1d" }
        }
      },
      "cold": {
        "min_age": "7d",
        "actions": {
          "searchable_snapshot": {
            "snapshot_repository": "logs-backup"
          }
        }
      },
      "delete": {
        "min_age": "30d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

### 5.3 索引模板（自动套用）

```yaml
# 模板：logs-app.app-* 自动绑定 ILM 策略
PUT _index_template/logs-app
{
  "index_patterns": ["logs-app.app-*"],
  "template": {
    "settings": {
      "number_of_shards": 3,
      "number_of_replicas": 1,
      "index.lifecycle.name": "logs-30d"
    }
  }
}
```

> 🎯 实战要点：**Data Stream + 模板 + ILM 三件套**——Logstash 只管写，滚动、降温、删除全自动。

## 6. 第五步：Kibana 看板与告警

### 6.1 看板结构（生产标准）

```text
┌─────────────────────────────────────────────┐
│ Metric：今日错误数 / 平均延迟 / 每秒吞吐      │
├──────────────┬──────────────┬───────────────┤
│ 错误趋势（面积）│ 错误 Top 接口  │ 延迟 P95（折线）│
├──────────────┴──────────────┼───────────────┤
│ 按服务堆叠柱状图              │ 错误级别环形图  │
└─────────────────────────────┴───────────────┘
```

### 6.2 告警规则（ES|QL 示例）

```sql
-- 规则：5 分钟内 ERROR 数超 10 触发
FROM logs-app.app-*
| WHERE level == "ERROR" AND @timestamp > now() - 5m
| STATS error_count = COUNT(*) BY service, environment
| WHERE error_count >= 10
```

```text
动作：Webhook（钉钉/企业微信）+ 邮件双通道
内容：服务名、错误数、时间窗、直达 Discover 深链
```

## 7. 全链路排错手册

### 7.1 分段排查法

```text
Kibana 没数据？
 ├─ Filebeat 有采集吗？→ filebeat 日志 / registry 检查
 ├─ Logstash 有收到吗？→ stdout dots 调试 / Stats API events.in
 ├─ ES 有数据吗？→ Dev Tools 查询数据流
 └─ Kibana 数据视图对吗？→ 索引模式与时间字段
```

### 7.2 各环节排错命令

| 环节 | 命令/操作 |
|------|------|
| Filebeat | `filebeat test config`、`filebeat test output`、看自身日志 |
| Logstash | `--config.test_and_exit`、stdout 调试、`curl :9600/_node/stats` |
| ES | `GET _cat/indices/logs-*`、`GET logs-app.app-*/_count` |
| Kibana | 数据视图检查、Dev Tools 直接查 |

### 7.3 常见故障速查

| 故障 | 原因 | 修复 |
|------|------|------|
| 链路无数据 | Filebeat 断点/路径错 | 检查 filestream 路径与 registry |
| Logstash 收不到 | 端口/网络/防火墙 | telnet 5044 测试 |
| 写入失败 | ES 认证/映射冲突 | 看 DLQ、ES 日志 |
| 看板无数据 | 数据视图时间字段错 | 重建数据视图 |
| 时间错乱 | 未做 date 校准 | Logstash date 插件覆盖 @timestamp |
| 堆栈被拆行 | multiline 没配 | 采集侧 multiline 合并 |

## 8. 生产演进路线

### 8.1 阶段演进

| 阶段 | 架构 | 适用规模 |
|:---:|------|------|
| 1 单体直连 | Filebeat → ES（简单解析走 Ingest） | 单机/小团队 |
| 2 引入管道 | Filebeat → Logstash → ES | 中型（解析复杂） |
| 3 队列削峰 | Filebeat → Kafka → Logstash → ES | 大流量/多租户 |
| 4 平台化 | 多数据流 + 权限空间 + 告警体系 + 容量治理 | 企业级 |

### 8.2 演进决策点

```text
何时引入 Logstash？→ 解析复杂/多输出/要 PQ 时
何时引入 Kafka？   → 峰值 > 处理能力 / 需要重放 / 多消费
何时分层空间？    → 多团队共用集群时（Spaces + 索引前缀）
何时做容量治理？  → 日志量增长 > 磁盘扩容速度时（ILM 先行）
```

> 🎯 **核心要点**：日志全链路五步——**应用 JSON 化（免正则）→ Filebeat 采集（断点+压缩）→ Logstash 管道（json/date/脱敏/DLQ）→ ES 数据流 + ILM（自动滚动降温）→ Kibana 看板 + 告警**。排错按「Kibana → ES → Logstash → Filebeat → 应用」逐段上溯，每段都有对应验证命令。架构演进从「直连」到「平台化」的每一步都有明确触发条件，别在第一步就上 Kafka。
