## 1. 选型决策树

### 1.1 完整决策树

```text
分布式 ID 选型（从简单到复杂）：

① 单库单表？
   ├── 是 → DB 自增（最优）→ 结束
   └── 否 → 继续

② 需要不可猜测（令牌/密钥）？
   ├── 是 → UUIDv4（随机）→ 结束
   └── 否 → 继续

③ 需要严格递增（对外/金融/可解释）？
   ├── 是 → 号段模式（Leaf-segment）→ 结束
   └── 否 → 继续

④ 64 位预算（BIGINT 兼容/存储紧张）？
   ├── 是 → 雪花/变体（Leaf-snowflake）
   │     ├── 容器弹性 → UidGenerator 风格
   │     └── 固定部署 → Leaf/自研
   └── 否 → UUIDv7（128 位，新默认）

⑤ 特殊需求？
   分片内嵌 → Instagram 风格（13 位分片）
   超大规模机器 → Sonyflake（16 位）
   时间隐私 → 脱敏/编码
```

### 1.2 关键判断问题

| 问题 | 指向 |
|------|------|
| 单库吗？ | DB 自增 |
| 需要不可猜吗？ | UUIDv4 |
| 需要严格递增吗？ | 号段 |
| 64 位够吗/必须吗？ | 雪花/变体 |
| 否则？ | **UUIDv7（新默认）** |

```text
2025-2026 的简化判断：
  大多数新场景 → UUIDv7（默认）
  特殊需求 → 按上述分支
  → 雪花是"64 位预算"的专用选择
```

> 🎯 核心认知：**2025-2026 的选型已简化——默认 UUIDv7**，只有四个明确分支离开默认：单库（DB 自增）、不可猜测（v4）、严格递增（号段）、64 位预算（雪花）。雪花不再是"默认选择"，而是"64 位场景的最优解"。

## 2. 场景对照表

### 2.1 按需求对照

| 需求 | 方案 | 理由 |
|------|------|------|
| 单库主键 | DB 自增 | 最优（零成本） |
| 分布式主键 | **UUIDv7** | 有序 + 零协调 + 标准 |
| 64 位主键 | 雪花/Leaf | BIGINT 兼容 |
| 对外订单号 | 号段 | 严格递增 + 可解释 |
| 订单号（雪花） | 雪花 + 脱敏 | 64 位 + 防泄露 |
| 公共令牌 | UUIDv4 | 不可猜测 |
| 分片路由 | Instagram 风格 | ID 内嵌分片 |
| 容器弹性 | UidGenerator 风格 | 自动机器号 |
| 高吞吐 | 本地方案（雪花/v7） | 本地生成 |

### 2.2 按系统对照

| 系统类型 | 推荐 | 说明 |
|---------|------|------|
| 电商订单 | 号段或雪花+脱敏 | 递增 + 可解释/安全 |
| 社交内容 | UUIDv7 | 分布式 + 有序 |
| 日志/事件 | UUIDv7 | 时间有序（分析友好） |
| 金融流水 | 号段 | 严格递增（审计） |
| 消息 ID | 雪花/UUIDv7 | 高性能本地 |
| 会话/令牌 | UUIDv4 | 不可猜测 |
| 分库分表 | Instagram/雪花 | 分片信息内嵌 |

```text
注意：一个系统多个 ID 用途 → 多方案并存
  主键 v7 + 订单号号段 + 令牌 v4
  → 不是"一个方案打天下"
```

## 3. 2025-2026 新默认

### 3.1 为什么 UUIDv7 成为新默认

```text
UUIDv7 新默认的驱动（2024-2026）：
  ① RFC 9562 标准化（2024-05）
  ② PG 18 原生 uuidv7()（2025-09）
  ③ Java 26 原生 UUID.ofEpochMillis()（2026）
  ④ 零协调（无机器号/无回拨防御）
  ⑤ 时间有序（B-tree 友好）

对比雪花的"运维税"：
  机器号分配/回拨防御（02/03 模块）
  → v7 免去（随机唯一）

共识（2025-2026 检索）：
  "除非 64 位预算/不可猜/单库排序，
   否则 UUIDv7 是新默认"
```

### 3.2 雪花的保留场景

```text
雪花仍然最优的场景（2025-2026）：
  ① 64 位 BIGINT 兼容（存量表/存储预算）
  ② ID 需内嵌机器/分片信息（路由）
  ③ 极致延迟（0.12ms 基准）
  ④ 既有雪花体系（迁移成本）

评估问题：
  "128 位索引成本可接受吗？"
  可接受 → v7（新默认）
  不可接受 → 雪花（Leaf）

迁移判断：
  新表 v7 + 存量雪花（并存）
  全量迁移仅在收益显著时（索引/WAL）
```

### 3.3 混合策略（推荐）

```text
推荐的混合策略（2026）：
  新业务/新表：UUIDv7（默认）
  存量 BIGINT：雪花/Leaf（维持）
  严格递增：号段（Leaf-segment）
  令牌：UUIDv4

好处：
  渐进采用（无大爆炸迁移）
  各取所长（方案匹配需求）
  风险可控（逐步验证）

实施：
  按表/业务灰度
  统一 ID 服务抽象（切换透明）
```

## 4. 生产清单

### 4.1 部署前检查

```text
分布式 ID 生产清单：
  ① 方案选择（决策树过一遍）
  ② 唯一性验证（并发压测无重复）
  ③ 回拨防御（雪花：等待/拒绝/监控）
  ④ 机器号管理（冲突检测）
  ⑤ JS 精度（字符串序列化）
  ⑥ 信息泄露评估（对外字段）
  ⑦ 性能压测（生成/写入）
  ⑧ 监控告警（回拨/生成异常）
```

### 4.2 运维与监控

```text
ID 系统的运维：
  监控指标：
    生成 TPS/延迟（应用）
    回拨次数/量（雪花）
    机器号冲突（自动分配时）
    重复 ID 检测（定期抽样）

告警：
  回拨异常（频率突增）
  机器号冲突（严重）
  生成延迟升高（异常）

审计：
  机器号分配记录（ZK/DB）
  回拨事件日志
  方案变更记录
```

### 4.3 故障处理

```text
ID 系统故障：
  雪花回拨大（拒绝）→ 切换备用/人工
  机器号冲突 → 立即修复（重复 ID 风险）
  ID 重复（已发生）→ 数据修复（主键冲突处理）

预防：
  回拨防御配置（NTP slew-only）
  机器号分配自动化（防人为错误）
  重复检测（定期）

恢复：
  备用生成器切换
  重复数据处理（人工/脚本）
  → 教训沉淀（根因分析）
```

## 5. 常见错误

### 5.1 错误清单

| 错误 | 后果 | 对策 |
|------|------|------|
| 机器号硬编码 | 部署冲突 = 重复 ID | 自动分配 |
| 忽略回拨 | 重复 ID（静默） | 回拨处理 + 监控 |
| 前端直接收 Long | JS 精度丢失 | 字符串序列化 |
| 令牌用雪花 | 可预测（安全） | UUIDv4 |
| 全系统一个方案 | 需求不匹配 | 按用途多方案 |
| 忽视 128 位成本 | 索引膨胀 | 预算评估 |
| 无重复检测 | 重复不可见 | 定期抽样 |

### 5.2 最佳实践总结

```text
ID 生成最佳实践（2025-2026）：
  ① 默认 UUIDv7（新项目）
  ② 64 位场景雪花（Leaf 变体）
  ③ 严格递增用号段
  ④ 令牌用 UUIDv4
  ⑤ 字符串序列化（防 JS 精度）
  ⑥ 回拨防御 + 监控（雪花）
  ⑦ 机器号自动分配（防冲突）
  ⑧ 内外 ID 分离（安全）

"简单优先"原则：
  单库用自增（不要引入复杂度）
  能 v7 就 v7（少运维）
  雪花留给必要场景
```
