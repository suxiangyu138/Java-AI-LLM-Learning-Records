## 1. 生成性能基准

### 1.1 方案对比（2025-2026 检索）

| 方案 | TPS（万） | P99（ms） | 外部依赖 |
|------|:---:|:---:|------|
| 雪花（64 位） | 28.4 | 0.12 | 无 |
| UUIDv7 | 32.1 | 0.03 | 无 |
| Redis INCR | 14.2 | 1.8 | Redis |
| TiKV Timestamp | 19.6 | 0.45 | TiKV+PD |

```text
数据解读：
  本地生成（雪花/v7）：延迟极低（0.03-0.12ms）
  中心协调（Redis/TiKV）：延迟高一个量级（0.45-1.8ms）
  → 协调成本 = 延迟的物理根源

生成吞吐：
  本地方案均百万级 TPS（单机）
  中心方案受限于中心节点（万-十万级）

结论：性能上"本地生成"完胜
  → 性能不是 UUIDv7/雪花 vs 中心方案的问题
  → 是"选哪个本地方案"的问题
```

### 1.2 本地方案的细微差异

```text
雪花 vs UUIDv7（生成侧）：
  雪花：位运算（移位+或）——极快
  v7：时间戳 + 随机数（SecureRandom 或 PRNG）
  → 差异在"随机数生成成本"

实测（Go 基准）：
  v7：32.1 万 TPS（随机生成并行友好）
  雪花：28.4 万 TPS（序列号串行同步）
  → 量级相同（百万级），差异无工程意义

注意：
  基准环境/实现差异大
  关键结论：本地方案都"够快"
  → 性能不决定选型（其他维度决定）
```

> 🎯 核心认知：**性能的结论简单——本地生成（雪花/v7）远优于中心协调（Redis/TiKV），而本地方案之间（雪花 vs v7）性能同量级**。性能维度上"选哪个本地方案"无所谓；真正决定选型的是位数预算、协调成本与运维负担（05/08 模块）。

## 2. B-tree 索引影响

### 2.1 有序 vs 随机

```text
ID 顺序对 B-tree 索引的影响：
  有序 ID（雪花/v7）：
    新 ID > 旧 ID → 插入最右叶子
    → 页分裂少、缓存命中高、WAL 顺序写

  随机 ID（UUIDv4）：
    新 ID 随机位置 → 插入任意叶子
    → 页分裂多、缓存抖动、WAL 随机写
    → "瑞士奶酪"索引（空洞多）

量化（2025-2026 检索）：
  随机索引：约 2 倍索引大小、2-3 倍 WAL 体积
  → 有序性是索引性能的第一要素
```

### 2.2 局部性原理

```text
时间有序的局部性收益：
  ① 新数据集中（最右叶子）→ 页缓存命中高
  ② 批量插入顺序写（WAL 友好）
  ③ 范围查询高效（相邻 ID = 相邻数据）

反例（随机 ID）：
  插入分散 → 页缓存被"洗牌"
  冷热数据混存 → 缓存效率低

工程含义：
  主键选择影响数据库整体性能
  时间有序主键（v7/雪花）是默认选择
  → 除非有"不可猜测"需求（v4 公共令牌）
```

## 3. 数据库写入实测

### 3.1 实测数据

```text
PostgreSQL 18 基准（2025-2026 检索）：
  UUIDv7 插入：比 v4 快 ~30%
  v7 索引：比 v4 小 ~25%

Buildkite 案例（v4 → v7 迁移）：
  WAL 体积减少 ~50%
  → 有序性的数据库级收益

解读：
  插入快：页分裂少 + 缓存命中
  索引小：无"空洞"（碎片少）
  WAL 少：顺序写（追加 vs 随机）

注意：
  收益大小取决于负载（写密集收益大）
  读多场景收益较小（索引大小仍影响）
```

### 3.2 64 vs 128 位的影响

```text
BIGINT（64 位）vs UUID（128 位）索引：
  索引叶子：8 字节 vs 16 字节（2 倍）
  索引大小：约 2 倍（同数据量）
  缓存占用：约 2 倍

量化：
  1000 万行：
    BIGINT 索引：~80MB（8B × 1.25 系数）
    UUID 索引：~160MB（16B × 1.25）
  → 128 位的主要成本（存储/内存）

权衡：
  v7 的索引收益（有序）vs 128 位成本（2 倍）
  实测：有序 v7 仍优于随机 v4（快 30%）
  vs 雪花：v7 索引 2 倍于雪花（64 位）
  → 64 位预算场景雪花仍有优势
```

## 4. 性能优化

### 4.1 生成侧优化

```text
本地生成的优化：
  雪花：
    序列号用原子/无锁（减少同步）
    位运算（已最优）
  雪花 v7：
    随机数用 PRNG（非 SecureRandom——性能）
    单调计数器（M1，原子）

常见误区：
  用 SecureRandom 生成 v7 → 慢（安全随机）
  正确：时间 + PRNG（唯一性够用）
  → 安全随机只用于令牌（v4）

序列/计数器优化：
  原子（AtomicLong）
  线程本地（每线程序列空间）
  → 消除同步瓶颈
```

### 4.2 数据库侧优化

```text
主键写入优化：
  ① 有序主键（v7/雪花）——基础
  ② 填充因子调整（有序插入可调低）
  ③ 批量导入（COPY/批量 INSERT）
  ④ 避免随机主键（v4 弃用于表主键）

索引优化：
  聚簇（PG CLUSTER BY 时间序）
  索引压缩（前缀压缩）
  → 有序性放大（索引更紧凑）

2025-2026 实践：
  新表默认 uuidv7（PG 18 一行配置）
  存量随机主键 → 评估迁移（WAL/索引收益）
```

## 5. 性能与选型

### 5.1 性能维度的结论

```text
性能维度的选型结论：
  ① 本地生成 > 中心协调（量级差距）
  ② 雪花 vs v7：同量级（不决定选型）
  ③ 有序 > 随机（索引/WAL 收益显著）
  ④ 64 vs 128：索引 2 倍（预算场景）

最终选型（性能视角）：
  性能不是主要矛盾
  主要矛盾：位数预算 × 运维负担 × 标准
  → 08 模块的完整决策
```

### 5.2 性能验证方法

```text
生产前的性能验证：
  ① 生成基准（TPS/延迟——本地方案易达标）
  ② 数据库写入压测（插入吞吐/索引大小）
  ③ 缓存影响（页缓存命中率对比）

压测工具：
  自研微基准（生成器）
  pgbench（PG 写入）
  对比实验（v7 vs 雪花 vs v4）

指标关注：
  P99 延迟（生成）
  插入 TPS（数据库）
  索引/WAL 大小（存储）
```

> 🎯 **核心要点**：性能结论清晰——**本地生成（雪花/v7）延迟 0.03-0.12ms 远优于中心协调（Redis 1.8ms）**；雪花 vs v7 同量级（不决定选型）；**有序 ID 的 B-tree 收益显著**（PG18 实测 v7 比 v4 快 30%、WAL 少 50%）；128 位索引是 v7 相对 64 位雪花的成本（2 倍）。性能维度的结论：选型看"位数预算 × 运维负担"，性能只要选"本地 + 有序"就达标。
