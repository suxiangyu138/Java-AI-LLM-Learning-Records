## 1. 方案总览

### 1.1 五大方案

| 方案 | 机制 | 协调 | 有序 | 位数 |
|------|------|:---:|:---:|:---:|
| DB 自增 | AUTO_INCREMENT | DB 中心 | ✅ | 64 |
| 号段模式 | DB 批量分配 | DB 中心 | ✅ | 64 |
| Redis INCR | 原子自增 | Redis | ✅ | 64 |
| UUID | 随机/时间 | 无 | ❌/✅ | 128 |
| 雪花 | 时间+机器+序列 | 无 | ✅ | 64 |

```text
方案的两个维度：
  协调（中心 vs 本地）：
    中心：DB/Redis（严格递增但依赖）
    本地：UUID/雪花（零协调但需设计）
  有序性：
    递增（索引友好）vs 随机（索引碎片）

选择的核心：
  协调成本 vs 索引性能 vs 位数预算
```

### 1.2 需求五要素

```text
分布式 ID 的需求五要素：
  ① 唯一性（必须）
  ② 趋势递增（索引/分页友好）
  ③ 高性能（本地优先）
  ④ 高可用（无单点）
  ⑤ 安全（不可猜测/不泄露）

方案权衡：
  无方案全满足 → 按场景取舍
  唯一性：所有方案都满足
  其他四要素决定选型
```

> 🎯 核心认知：**五大方案 = "中心协调 vs 本地生成"的两极谱系**——DB/Redis 严格递增但依赖中心，UUID/雪花零协调但各有取舍（UUID 无序/雪花要机器号）。选型本质：在协调成本、索引性能、位数预算之间取平衡。

## 2. DB 自增与号段模式

### 2.1 DB 自增

```text
DB 自增（AUTO_INCREMENT）：
  单库单表场景的最优解（无协调成本）

特点：
  严格递增、简单、有序
  局限：单点（分库分表后失效）

分库分表的扩展：
  ① 步长法：每库不同步长（i*N + 库号）
  ② 号段法：每库分配区间（见下）
  ③ 雪花/UUID：彻底本地化

适用：
  单库场景（不可替代的最优）
  分库场景的基线（对比其他方案）
```

### 2.2 号段模式（Segment）

```text
号段模式：DB 批量分配 ID 区间（段）

流程：
  ① 应用向 DB 申请一段（如 1000-1999）
  ② 应用本地发放（内存递增）
  ③ 段用完 → 申请下一段

特点：
  减少 DB 压力（一次申请一段）
  批量分配（性能）
  依赖 DB（段耗尽时申请）

美团 Leaf-segment 的增强：
  双缓冲：预加载下一段（无缝切换）
  动态步长：按消费速度调整段大小
  剩余 20% 告警

性能：~50k QPS（4C8G）
  适用：高可用 + 严格递增（金融）
```

### 2.3 号段的优劣

| 优点 | 缺点 |
|------|------|
| 严格递增 | 依赖 DB（段耗尽） |
| 高吞吐（批量） | 段空洞（重启浪费） |
| 可审计 | 运维（DB 表） |
| 回拨免疫（无时钟） | 中心化（单点风险） |

```text
适用判断：
  需要严格递增（排序/对外）→ 号段
  可接受趋势递增 → 雪花/UUIDv7
  金融/审计场景 → 号段（可解释）

2025-2026 状态：
  Leaf-segment/TinyID 成熟
  严格递增需求仍是号段的领地
```

## 3. Redis INCR

### 3.1 原理

```text
Redis INCR：Redis 原子自增生成 ID

流程：
  INCR key：原子 +1（返回新值）
  可组合前缀（日期 + 自增：202608060001）

特点：
  原子（无并发问题）
  严格递增（单 key）
  简单（一行命令）

局限：
  依赖 Redis（可用性/性能）
  单 key 瓶颈（热点）
  数据持久性（RDB 可能丢）
```

### 3.2 适用与优化

```text
适用：
  中低并发（万级 TPS）
  已有 Redis 基础设施
  需要简单递增（订单号等）

优化：
  多 key 分片（key 前缀分片）
  批量（INCRBY）
  Lua（组合逻辑）

基准（2025-2026 检索）：
  Redis INCR：14.2 万 TPS、P99 1.8ms
  （对比雪花 28.4 万/0.12ms——延迟高一个量级）

注意：
  依赖 Redis 高可用（主从/集群）
  递增可用但性能非最优
  → 中低并发场景的简单选择
```

## 4. UUID 家族

### 4.1 UUID 版本

| 版本 | 机制 | 有序 | 特点 |
|------|------|:---:|------|
| v1 | MAC + 时间 | ✅ | 泄露 MAC（弃用） |
| v4 | 随机（122 位） | ❌ | 不可猜测（公共令牌） |
| v7 | 时间（48ms）+ 随机 | ✅ | **新默认（RFC 9562）** |

```text
v4（随机 UUID）：
  唯一性：2¹²²（天文数字）
  无序：索引碎片化（"瑞士奶酪"）
  适用：公共令牌（不可猜测）

v7（RFC 9562，2024-05 标准化）：
  48 位毫秒时间戳 + 74 位随机
  时间有序（B-tree 友好）
  零协调（无机器号）
  → 详见 05 模块（重点）
```

### 4.2 UUID 的优劣

```text
UUID 家族（v4/v7）：
  优点：
    零协调（本地生成）
    唯一性极强（随机位）
    回拨免疫（唯一性不依赖时钟）
    标准（RFC 9562 跨语言）

  缺点：
    128 位（索引 2 倍开销）
    v4 无序（索引碎片）
    时间戳泄露（创建时间可推断）

2025-2026 关键变化：
  v7 解决"有序"短板（时间戳打头）
  → 128 位成本 vs 零协调收益的权衡
  → 成为分布式表新默认（05/08 模块）
```

## 5. 雪花与变体

### 5.1 雪花的定位（本目录核心）

```text
雪花（64 位）：
  本地生成（零协调）
  趋势递增（时间戳）
  64 位紧凑（BIGINT）

对比其他方案：
  vs DB/号段：无中心依赖（本地）
  vs Redis：无外部依赖（本地）
  vs UUID：64 位紧凑（vs 128 位）
  → 64 位预算 + 本地 + 有序的最优解

代价（02/03 模块）：
  时钟回拨防御
  机器号管理
  → 变体（Leaf）解决

基准（2025-2026 检索）：
  雪花：28.4 万 TPS、P99 0.12ms（最优延迟）
```

### 5.2 方案组合（生产常见）

```text
生产实际（多方案并存）：
  主键/分片键：雪花或 UUIDv7（本地 + 有序）
  对外订单号：号段（严格递增 + 可解释）
  公共令牌：UUIDv4（不可猜测）
  中低并发自增：Redis INCR

原则：按用途选择
  不同字段不同方案（不是"一个方案打天下"）
  → 08 模块的选型决策树
```

## 6. 对比矩阵与选择

### 6.1 全面对比

| 维度 | DB 自增 | 号段 | Redis | UUIDv4 | UUIDv7 | 雪花 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| 位数 | 64 | 64 | 64 | 128 | 128 | 64 |
| 有序 | ✅严格 | ✅严格 | ✅严格 | ❌ | ✅ | ✅趋势 |
| 协调 | DB | DB | Redis | 无 | 无 | 无 |
| 回拨 | 免疫 | 免疫 | 免疫 | 免疫 | 唯一免疫 | 需防御 |
| 性能 | 低 | 高 | 中 | 高 | 高 | 最高 |
| 单点 | 是 | 是 | 是 | 无 | 无 | 无 |
| 安全 | — | — | — | ✅不可猜 | 时间泄露 | 机器泄露 |

```text
性能基准（Go 实测，2025-2026 检索）：
  雪花：28.4 万 TPS / P99 0.12ms
  UUIDv7：32.1 万 TPS / P99 0.03ms
  Redis INCR：14.2 万 / 1.8ms
  TiKV：19.6 万 / 0.45ms

B-tree 影响（06 模块量化）：
  有序 ID（雪花/v7）→ 最右叶子插入（索引高效）
  随机 ID（v4）→ 索引 2 倍大小、WAL 2-3 倍
```

### 6.2 场景对照

| 场景 | 推荐 |
|------|------|
| 单库单表 | DB 自增（最优） |
| 严格递增（对外/金融） | 号段（Leaf-segment） |
| 中低并发简单 | Redis INCR |
| 公共令牌（不可猜） | UUIDv4 |
| 64 位预算 + 有序 | 雪花/变体（Leaf） |
| **128 位可接受 + 有序** | **UUIDv7（新默认）** |

### 6.3 趋势（2025-2026）

```text
2025-2026 的选型趋势：
  UUIDv7 成为"新默认"（时间有序 + 零协调 + 原生支持）
  雪花退居"64 位预算"场景
  号段保留"严格递增"领地
  v4 用于安全场景（不可猜测）

关键驱动：
  RFC 9562 标准化（2024-05）
  PG 18 / Java 26 原生支持
  → 采用成本大幅下降
  → 详见 05/08 模块
```

> 🎯 **核心要点**：五大方案覆盖"中心协调（DB/Redis）→ 本地生成（UUID/雪花）"全谱系——DB 自增单库最优、号段严格递增、Redis 简单依赖、UUIDv4 不可猜测、雪花 64 位紧凑、**UUIDv7 时间有序 + 零协调（2025-2026 新默认）**。选型本质：位数预算（64 vs 128）与协调成本（中心 vs 本地）的权衡；生产实践是多方案并存（按字段用途选择）。
