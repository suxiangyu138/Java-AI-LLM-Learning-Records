## 1. RFC 9562 背景

### 1.1 标准化的动机

```text
RFC 9562（2024-05）：UUID 新标准（替代 RFC 4122）

背景：
  UUID v1-v5 有 20 年历史（4122 时代）
  分布式场景需要"时间有序"的 UUID（v1 泄露 MAC、不实用）
  社区涌现大量方案（ULID/KSUID/雪花/Instagram）
  → 16 个社区设计被收录为 v7 的动机

目标：
  v6：重新排序的 v1（时间优先）
  v7：全新设计（时间 + 随机）
  v8：自定义（实验）

2025-2026 状态：
  v7 成为分布式 ID 的推荐默认
  v6/v8 相对小众
```

### 1.2 v7 的设计目标

```text
UUIDv7 的设计目标：
  ① 时间有序（B-tree 友好）
  ② 零协调（本地生成）
  ③ 唯一性（随机位 + 时间）
  ④ 标准（跨语言/平台）
  ⑤ 不回拨依赖（唯一性靠随机）

一句话定位：
  "雪花的有序 + UUID 的零协调"
  → 128 位版本的"雪花替代品"
```

> 🎯 核心认知：**UUIDv7 = "雪花的优点（时间有序）+ UUID 的优点（零协调）"**——RFC 9562（2024-05）把它标准化，PG 18/Java 26 原生支持让采用成本趋零。2025-2026 它成为分布式表的新默认（除非 64 位预算或安全需求另有选择）。

## 2. UUIDv7 结构

### 2.1 128 位布局

UUIDv7 的 128 位结构（RFC 9562 布局，共 128 位）：

| 字段 | 位数 | 值 | 作用 |
|------|:---:|-----|------|
| unix_ts_ms（时间戳） | 48 | Unix 毫秒（最高位） | **排序关键**：原始字节比较 = 时间排序（无需解析） |
| ver（版本） | 4 | 0111 | v7 标识 |
| rand_a | 12 | 单调性控制（M1 为计数器） | 同毫秒内排序（见 3 节三方法） |
| var（变体位） | 2 | 10 | RFC 变体标识（固定值，非随机） |
| rand_b | 62 | 随机 | 唯一性 |

合计：48 + 4 + 12 + 2 + 62 = **128 位**；随机位共 74（rand_a 12 + rand_b 62，M1 时 rand_a 作计数器）。

特点：

- 时间戳在最高位 → B-tree 局部性极好
- 随机 74 位 → 唯一性极强

### 2.2 文本表示

```text
UUIDv7 的文本形式（标准）：
  8-4-4-4-12（32 位十六进制）
  例：018f4f3a-2b7c-7a00-9f2e-1234567890ab

时间戳可提取（第 1-3 组）：
  018f4f3a2b7c → 毫秒时间戳（可解析创建时间）

存储：
  原生类型（PG uuid / Java UUID）
  二进制 16 字节

与雪花对比：
  UUIDv7：128 位（16 字节）
  雪花：64 位（8 字节）
  → 索引开销 2 倍（权衡点）
```

## 3. 单调性三方法

### 3.1 问题：同毫秒内的顺序

```text
时间戳 48 位毫秒 → 同毫秒内无时间信息
  → 同毫秒生成多个 ID 时顺序不定（若 rand_a 随机）

RFC 9562 §6.2 定义三种单调性方法：
  Method 1：固定位计数器（rand_a 作计数器）
  Method 2：单调随机（rand_a 递增）
  Method 3：亚毫秒时间戳（rand_a 存亚毫秒分数）

目的：同毫秒内的排序（提升索引局部性）
```

### 3.2 三种方法对照

| 方法 | 机制 | 特点 |
|------|------|------|
| M1 固定计数器 | rand_a 作 0-4095 计数器 | 确定性（同雪花序列） |
| M2 单调随机 | rand_a 递增随机 | 折中（随机 + 递增） |
| M3 亚毫秒 | rand_a 存亚毫秒 | 时间精度更高 |

```text
实现选择：
  M1：高吞吐场景（计数器 4096/ms）
  M2：通用（随机 + 单调）
  M3：时间敏感（亚毫秒排序）

平台采用：
  PostgreSQL 18：Method 3（亚毫秒）
  ULID monotonic：类似 M2

Java 26 的注意：
  原生 UUID.ofEpochMillis() 的 rand_a 纯随机
  → 同毫秒内乱序（高吞吐需自己加计数器）
  → 官方指引：M1 计数器（原子序列 0-4095）
```

## 4. 平台支持

### 4.1 支持矩阵（2025-2026）

| 平台 | 支持 | 说明 |
|------|------|------|
| PostgreSQL 18 | ✅ 原生 | uuidv7() / uuid_extract_timestamp() |
| Java 26 | ✅ 原生 | UUID.ofEpochMillis() |
| Go | ✅ 库 | 多种实现（单调可配） |
| MySQL | ⚠️ 应用层 | UUID() 是 v1 风格（需应用生成） |
| 各语言库 | ✅ | RFC 9562 实现普遍 |

```text
PostgreSQL 18（2025-09-25）：
  原生 uuidv7() 函数
  uuid_extract_timestamp()（提取时间）
  迁移：ALTER TABLE ... SET DEFAULT uuidv7()
  → 一行 SQL 完成 v4 → v7 迁移

Java 26：
  原生 UUID.ofEpochMillis()
  注意：rand_a 纯随机（同毫秒乱序）
  → 高吞吐需自定义计数器（M1）
```

### 4.2 采用成本的变化

```text
2024-2026 的采用成本变化：
  2024 前：需第三方库（自实现）
  2024-05：RFC 9562 标准化（明确规范）
  2025-09：PG 18 原生（数据库侧）
  2026：Java 26 原生（应用侧）
  → 采用成本趋零（新默认的底气）

工程含义：
  新项目直接用 UUIDv7（零依赖）
  存量迁移：PG 一行 SQL（v4 → v7）
  高吞吐：加 M1 计数器（小改造）
```

## 5. vs 雪花算法

### 5.1 全面对照

| 维度 | UUIDv7 | 雪花 |
|------|:---:|:---:|
| 位数 | 128（16 字节） | 64（8 字节） |
| 时间戳 | 48 位毫秒 | 41 位毫秒（自纪元） |
| 协调 | 无（随机唯一） | 无（机器号唯一） |
| 机器号 | 无（免运维） | 需分配（运维税） |
| 回拨 | 唯一性免疫（排序受影响） | 需防御（02 模块） |
| 单调性 | 三方法（可配） | 序列（内置） |
| 信息泄露 | 时间（1ms 精度） | 时间 + 机器号 |
| 索引开销 | 2 倍（128 vs 64） | 紧凑 |
| JS 精度 | 128 位字符串（安全） | 64 位超 2⁵³（需字符串） |
| 标准 | RFC 9562（跨语言） | 事实标准（变体多） |

### 5.2 各自的最优场景

```text
UUIDv7 最优：
  ① 无机器号管理（云/容器/K8s）
  ② 跨语言/跨系统（标准）
  ③ 128 位索引可接受
  ④ 回拨免疫（唯一性安全）
  ⑤ 新项目（零依赖原生支持）

雪花最优：
  ① 64 位预算（BIGINT 兼容/存储紧张）
  ② 需要 ID 内嵌机器信息（分片路由）
  ③ 极致延迟（0.12ms 基准）
  ④ 存量 BIGINT 表（不迁移）

2025-2026 共识：
  "除非 64 位预算/公共令牌不可猜/单库排序，
  否则 UUIDv7 是新默认"
```

### 5.3 迁移视角

```text
雪花 → UUIDv7 的迁移考虑：
  ① 存量 BIGINT 主键（历史数据）
  ② 索引大小增长（2 倍）
  ③ 分片路由（雪花内嵌分片 vs v7 无）
  ④ 业务代码（Long → String/UUID）

迁移建议：
  新表直接 v7（存量不动）
  或：新业务 v7 + 旧业务雪花（并存）
  → 按表/业务渐进（不必全量迁移）

2025-2026 现实：
  新项目默认 v7（减少运维）
  存量雪花继续（迁移成本 > 收益时）
```

## 6. 采用建议

### 6.1 采用决策

```text
采用 UUIDv7 的条件：
  ① 128 位索引可接受（存储/性能）
  ② 不需要 ID 内嵌机器/分片信息
  ③ 机器号管理是负担（云/弹性）
  ④ 回拨免疫有价值（时钟不可控环境）

不采用（保留雪花）的条件：
  ① 严格 64 位预算（BIGINT）
  ② ID 需携带分片/机器信息
  ③ 存量雪花体系（迁移成本）

混合策略（推荐）：
  新业务 v7 + 存量雪花
  → 渐进采用（无大爆炸迁移）
```

### 6.2 实现注意

```text
UUIDv7 实现注意：
  ① 单调性（高吞吐加 M1 计数器）
  ② 排序（原始字节比较 = 时间序）
  ③ 存储（原生类型/二进制）
  ④ 前端（128 位文本，无精度问题）

Java 26 实践：
  UUID.ofEpochMillis()（基础）
  自定义单调（M1 计数器）：
    rand_a 原子序列 0-4095 → 溢出进下毫秒

数据库实践：
  PG 18：uuidv7() 默认值
  MySQL：应用生成（UUIDv7 库）
```

> 🎯 **核心要点**：UUIDv7 = 48 位毫秒时间戳（高位）+ 74 位随机——时间有序（B-tree 友好）+ 零协调（随机唯一）+ 标准（RFC 9562）。三大优势：**免机器号（云/容器友好）、回拨唯一性免疫、原生支持（PG 18/Java 26）**；代价是 128 位索引。vs 雪花的本质：128 位零协调 vs 64 位紧凑——2025-2026 共识"v7 为新默认，雪花留在 64 位预算场景"。
