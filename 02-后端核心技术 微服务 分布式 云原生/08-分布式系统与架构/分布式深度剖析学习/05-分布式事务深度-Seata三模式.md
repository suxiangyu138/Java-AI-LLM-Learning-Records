# 05 - 分布式事务深度：Seata 三模式

> **核心摘要**：分布式事务的完整谱系：**强一致**（XA/2PC）→ **最终一致**（AT/TCC/Saga/本地消息表/MQ 事务消息）。Seata（2026 事实标准）四种模式：XA（DB 级强一致）、AT（无侵入自动回滚）、TCC（业务补偿）、Saga（长事务编排）。选型口诀：**数据一致性优先 → AT；强一致 → XA；高性能 → TCC；长流程 → Saga**。

## 1. 分布式事务的谱系与选型总览

> **背景**：微服务拆分后，一次业务操作跨多个库/多个服务——单库 ACID 失效。
> **目的**：建立「先选一致性模型，再选技术方案」的框架。
> **适用范围**：订单、支付、库存、积分等跨服务写链路。

```text
分布式事务谱系
├── 强一致（同步阻塞，短事务）
│   ├── XA / 2PC：数据库原生支持（万无一失但慢）
│   └── Seata XA 模式：XA 的 Seata 封装
├── 最终一致（异步/补偿，长事务）
│   ├── AT 模式：无侵入（自动快照回滚）
│   ├── TCC：业务显式补偿（Try-Confirm-Cancel）
│   ├── Saga：长流程编排（状态机 + 补偿）
│   ├── 本地消息表：DB 表做可靠投递
│   └── MQ 事务消息：消息中间件保证投递
└── 金句：先回答「能不能接受最终一致」，再谈方案

选型总览（一句话版）
├── 数据绝对不能错 + 允许慢 → XA
├── 常规微服务 + 不想改业务代码 → AT（最常用）
├── 高并发 + 愿意写补偿逻辑 → TCC
├── 长流程 + 流程可逆 → Saga
└── 异步解耦 + 可靠投递 → MQ 事务消息/本地消息表
```

## 2. XA / 2PC：强一致方案

> 🎯 **XA（2PC 的 SQL 标准实现）**——数据库原生事务的分布式延伸：准备阶段 + 提交阶段：

```text
2PC 两阶段提交
├── 阶段一 Prepare：协调者问所有参与者「能提交吗？」
│   ├── 每个参与者本地执行 SQL → 锁资源 → 返回 YES/NO
│   └── 都返回 YES → 阶段二；任一 NO → 全部回滚
├── 阶段二 Commit/Rollback：
│   ├── 协调者广播 COMMIT → 所有参与者提交
│   └── 协调者广播 ROLLBACK → 所有参与者回滚
└── 核心：阶段一锁资源 + 阶段二统一提交——「大家都同意才交」

XA 的致命缺点（为什么不是默认选择）
├── ① 同步阻塞：Prepare 后资源锁定直到 Commit（长事务拖死库）
├── ② 协调者单点：协调者挂了 → 参与者阻塞等待
├── ③ 不适用长事务：锁持有时间 = 整个业务时间
└── 适用：短事务 + 强一致（银行跨行转账）
```

```java
// Seata XA 模式（SQL 层面强一致，业务代码不变）
@GlobalTransactional
public void transfer() {
    // 两个数据源（不同库）自动纳入 XA 全局事务
    accountMapper.decrease();  // 扣钱
    accountMapper.increase();  // 加钱
}
```

> 💡 **XA 的现代判断**：性能代价大 + 不适合互联网高并发——**2026 多数团队直接跳过 XA 用 AT**；XA 仅在「DB 对 XA 支持好 + 强一致硬要求 + 低并发」时考虑。

## 3. Seata AT 模式：无侵入自动回滚

> 🎯 **AT（Automatic Transaction）是 Seata 的招牌**——**业务代码零侵入**，自动生成快照、自动回滚、自动加全局锁：

```text
AT 模式执行流程
├── ① 业务 SQL（用户只写普通 UPDATE！）
│   └── UPDATE account SET balance = balance - 100 WHERE id = 1
├── ② Seata 拦截器自动完成三件事：
│   ├── 前置镜像：执行前先 SELECT 记录旧值（balance=500）
│   ├── 执行 SQL：真正执行更新（balance=400）
│   └── 后置镜像：记录新值（balance=400）
├── ③ 提交阶段：全局事务成功 → 删除镜像，正式提交
├── ④ 回滚阶段：全局事务失败 → 用镜像恢复
│   └── 反 SQL：UPDATE balance = 500 WHERE id = 1 AND balance = 400
│       → 带 where 校验（防脏写覆盖，见全局锁）
└── 金句：AT = 「自动做镜像 + 自动反写」——你只管写业务 SQL

全局锁（AT 的并发控制）
├── 写隔离：全局事务提交前，被改的行加「全局锁」
│   └── 其他事务操作同一行 → 等待（本地锁 + 全局锁双检查）
├── 读隔离：默认读已提交（快照读）
│   └── 需要强读隔离 → SELECT FOR UPDATE（代价大）
└── 死锁风险：全局锁等待超时（默认 1s 可配）
```

**AT 的代价与局限**：

```text
├── 性能：每次写多 2 次 SELECT + 镜像存储 + 全局锁检查
│   └── 适用：写并发中等（几千 TPS 内）
├── 侵入点：需要 undo_log 表（每个参与库建一张）
├── 不支持 DDL：仅 DML（表结构变更不自动回滚）
├── 不支持 SELECT FOR UPDATE 强一致读（性能权衡）
└── 大事务不适用：镜像量大 + 锁时间长
```

## 4. TCC：业务补偿模式

> 🎯 **TCC（Try-Confirm-Cancel）**——把事务拆成三段业务动作，由业务代码显式实现补偿（不是自动反写，是业务级反操作）：

```text
TCC 三阶段（以「订单+扣库存」为例）
├── Try（预留资源）：冻结库存 10 件 / 冻结余额 100 元
│   └── 不真正扣减，只「占位」
├── Confirm（确认）：真正扣减库存 / 真正扣款
│   └── 所有 Try 成功 → 执行 Confirm（幂等）
├── Cancel（取消）：释放冻结的库存 / 退回余额
│   └── 任一 Try 失败 → 执行所有 Cancel（幂等）
└── 金句：Try 留后路，Confirm 定乾坤，Cancel 是后悔药

TCC 与 AT 的本质区别
├── AT：Seata 自动做镜像反写（业务无感）
├── TCC：业务自己写 Try/Confirm/Cancel 三个方法
├── TCC 优点：更灵活（可处理「不可自动回滚」的资源）
│   └── 案例：发短信、调第三方接口（无镜像可反）
├── TCC 缺点：开发成本高（每个接口写三段 + 幂等）
└── 适用：并发高 + 需要精细控制的资源预留
```

```java
// TCC 接口声明（@TwoPhaseBusinessAction 标记三方法）
public interface OrderTccService {
    @TwoPhaseBusinessAction(name = "orderTcc", commitMethod = "confirm", rollbackMethod = "cancel")
    void prepare(Order order);   // Try：冻结资源
    boolean confirm(Order order);// Confirm：确认（必须幂等）
    boolean cancel(Order order); // Cancel：取消（必须幂等）
}
```

> ⚠️ **TCC 的硬要求**：Confirm/Cancel **必须幂等**（重试可能发生）；Confirm/Cancel 失败要重试——补偿逻辑本身要可恢复。

## 5. Saga：长事务编排

> 🎯 **Saga 专为「长流程 + 不可回滚」设计**——每一步有正向动作 + 反向补偿，流程失败则逆向补偿：

```text
Saga 模式（以「下单→扣款→发券→发货」为例）
├── 正向链：T1 → T2 → T3 → T4（每一步有 C1..C4 补偿）
├── T3 失败 → 逆序补偿：C2 → C1
│   └── 注意：T3 之前已成功的不回滚，用补偿「对冲」
├── 与 TCC 的区别：
│   ├── TCC：预留-确认（两阶段，资源冻结）
│   └── Saga：直接执行 + 失败补偿（无预留，天然长事务）
├── 编排方式：
│   ├── 编排式（Orchestration）：中心协调者调用各服务（Seata Saga 状态机）
│   └──  choreography（编排-事件）：服务间事件驱动（无中心，难监控）
└── 适用：旅行预订、订单全流程、跨服务长流程

Seata Saga 状态机（可视化编排）
├── YAML/JSON 定义状态机：每个状态 = 服务调用 + 补偿
├── 状态持久化：流程可断点恢复
└── 配套：Saga 控制台可视化流程
```

```text
Saga vs TCC 选型
├── 流程 > 3 步 + 步骤不可预留 → Saga
├── 步骤少 + 资源可冻结 → TCC
├── Saga 无全局锁 → 并发冲突业务侧自控
└── 金句：Saga 管「流程」，TCC 管「资源」
```

## 6. 本地消息表与 MQ 事务消息

> 🎯 **「事务 + 消息」两派**——不依赖 Seata 的轻量最终一致方案：

```text
方案一：本地消息表（可靠消息最终一致）
├── ① 业务操作 + 写消息表（同一个本地事务！）
│   └── 伪代码：@Transactional { 业务SQL; INSERT INTO msg_log(...); }
├── ② 定时任务扫消息表：status=0 → 投递 MQ → 标记 status=1
├── ③ 投递失败重试（指数退避）；消费方幂等
└── 优点：纯 DB 方案，无中间件依赖；缺点：表膨胀/轮询延迟

方案二：MQ 事务消息（RocketMQ 支持，Kafka 无）
├── ① 发送半消息（prepare，不可见）
├── ② 本地事务执行
├── ③ 事务成功 → commit 半消息（消费方可见）
├── ④ 事务失败 → rollback（消费方不可见）
├── ⑤ 半消息超时未决 → MQ 回查本地事务结果（最终一致）
└── 优点：无轮询、延迟低；缺点：依赖 MQ 事务能力

对比
├── 本地消息表：万金油（任何 MQ 都能用）
├── MQ 事务消息：体验好（RocketMQ 生态）
└── 核心要点（两者共同）：投递是「尽力而为 + 重试」，消费必须幂等
```

## 7. 模式对比与选型

| 维度 | XA | AT | TCC | Saga | 本地消息表/MQ事务 |
|------|:---:|:---:|:---:|:---:|:---:|
| 一致性 | 强一致 | 最终一致 | 最终一致 | 最终一致 | 最终一致 |
| 业务侵入 | 无 | **无** | **高（三方法）** | 高（补偿方法） | 中（消息表） |
| 性能 | 差 | 中 | **高** | 高 | 高 |
| 长事务 | ❌ | 短中 | 中 | ✅ | ✅ |
| 回滚方式 | DB 级 | 自动镜像 | 业务补偿 | 流程补偿 | 补偿消息 |
| 锁 | DB 全局锁 | Seata 全局锁 | 无（预留替代） | 无 | 无 |
| 适用 | 金融短事务 | **常规微服务** | 高并发预留 | 长流程 | 异步解耦 |

**选型决策树**：

```text
跨服务写操作来了
├─ 能接受最终一致吗？
│   ├─ 不能（强一致）→ XA / AT+强隔离（或用单库事务）
│   └─ 能 → 继续
├─ 愿意改业务代码写补偿吗？
│   ├─ 不愿意 → AT 模式（Seata，90% 场景首选）
│   └─ 愿意 → 继续
├─ 流程长吗（>3 步）？
│   ├─ 长 → Saga（状态机编排）
│   └─ 短 → TCC（资源预留）
└─ 有现成 MQ 且可异步吗？
    ├─ 可异步 → MQ 事务消息/本地消息表（解耦最彻底）
    └─ 必须同步 → 回到 Seata AT/TCC
```

## 8. Seata 架构与部署

> 🎯 **Seata 组件三件套**——TC（事务协调器）/ TM（事务管理器）/ RM（资源管理器）：

```text
Seata 架构（2026 现状）
├── TC（Transaction Coordinator）：独立部署的服务端
│   ├── 全局事务注册/提交/回滚决策
│   └── 高可用：集群 + 注册中心（Nacos）
├── TM（Transaction Manager）：业务方客户端
│   ├── @GlobalTransactional 标记 → TM 向 TC 发起全局事务
│   └── 业务代码里就是注解 + 普通 SQL
├── RM（Resource Manager）：数据源代理
│   ├── 代理数据源：拦截 SQL 生成镜像/全局锁
│   └── undo_log 表落镜像
└── 部署拓扑：
    ├── Seata Server × N（Nacos 注册）
    ├── 业务服务引入 seata-spring-boot-starter
    └── 每个参与库建 undo_log 表

落地配置要点
├── undo_log 表结构（AT 模式必建）
├── 全局事务超时（默认 60s）
├── 全局锁等待超时（默认 1s）
└── 事务分组（vgroup）：seata.xxx.tx-service-group
```

```sql
-- undo_log 表（每个参与 AT 的库都要建）
CREATE TABLE undo_log (
  id            BIGINT NOT NULL AUTO_INCREMENT,
  branch_id     BIGINT NOT NULL,
  xid           VARCHAR(128) NOT NULL,
  context       VARCHAR(128) NOT NULL,
  rollback_info LONGBLOB NOT NULL,   -- 前后镜像序列化
  log_status    INT NOT NULL,
  log_created   DATETIME NOT NULL,
  PRIMARY KEY (id), UNIQUE KEY ux_undo_log (xid, branch_id)
) ENGINE = InnoDB;
```

## 9. 常见问题排查

| 现象 | 根因 | 对策 |
|------|------|------|
| 全局事务不回滚 | @GlobalTransactional 未生效 | 检查拦截器配置/注解位置 |
| 全局锁等待超时 | 长事务占锁 | 缩短事务时间/提高全局锁超时/换 TCC |
| undo_log 表缺失 | 库没建表 | 逐库建表（AT 必建） |
| 回滚失败 | 镜像反写 where 不匹配（数据被外部改了） | 排查脏写来源（禁止绕过事务直改） |
| 性能骤降 | 大事务/全局锁竞争 | 拆小事务 + 调整锁超时 |
| 与 ShardingSphere 冲突 | 数据源代理叠加 | 整合配置（见 [[06-分库分表与读写分离]]） |

> 💡 **生产建议**：Seata 也支持「AT + TCC」混用（部分服务 AT、部分 TCC）——大厂实践是按服务定制模式，不追求单模式全家桶。

## 10. 核心要点

> 🎯 **核心要点**：
> 1. **谱系**：强一致（XA）→ 最终一致（AT/TCC/Saga/消息方案）
> 2. **2PC/XA**：Prepare 锁资源 + Commit 统一——短事务强一致，性能差
> 3. **AT = 无侵入自动回滚**：前置/后置镜像 + 反 SQL + 全局锁——常规首选
> 4. **TCC = 业务三段**：Try 预留、Confirm 确认、Cancel 补偿——幂等是硬要求
> 5. **Saga = 长流程补偿**：正向执行 + 逆序补偿，状态机编排
> 6. **消息两派**：本地消息表（万金油）/ MQ 事务消息（RocketMQ 半消息+回查）
> 7. **选型口诀**：不写补偿→AT；高并发可写→TCC；长流程→Saga；可异步→消息
> 8. **Seata 三组件**：TC 服务端 + TM 注解 + RM 代理；undo_log 表必建
