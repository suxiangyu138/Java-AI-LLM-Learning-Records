## 1. 可观测性三支柱

> **背景**：微服务 10+ 实例，一个请求跨 5 个服务——「系统为什么慢」无法靠单机日志回答。
> **目的**：理解三支柱分工，知道排障时看什么。
> **适用范围**：所有分布式系统（2026 生产标配）。

```text
三支柱（Logging / Metrics / Tracing）
├── ① 日志（Logs）：事件记录（ERROR 堆栈/业务日志）
│   ├── 回答：发生了什么（精确但碎片化）
│   └── 关键：全链路 traceId 串起来（见第 5 节）
├── ② 指标（Metrics）：聚合数值（QPS/延迟/错误率/资源）
│   ├── 回答：系统健康度（宏观趋势，Prometheus 生态）
│   └── 关键：RED 四金指标（Rate/Errors/Duration）
├── ③ 追踪（Traces）：请求全链路（跨服务调用树）
│   ├── 回答：请求在哪个环节慢（微观路径，第 2 节）
│   └── 关键：traceId + span 树
└── 金句：日志看「细节」，指标看「趋势」，追踪看「路径」

排障实战流程
├── ① 指标发现：延迟 P99 升高
├── ② 追踪定位：trace 显示慢在 Redis 调用（跨服务路径）
├── ③ 日志深挖：对应 traceId 捞完整日志
└── ④ 修复验证：发布后指标回落
```

## 2. 链路追踪：原理与标准

> 🎯 **链路追踪的核心数据结构**：**Trace（一次请求）+ Span（一个调用单元）+ traceId 传播**：

```text
Trace 与 Span
├── Trace：一次完整请求（如「下单」）——树状结构
├── Span：树上的一个节点（调用服务 A / 查 Redis / 写 DB）
│   ├── spanId：本节点 ID
│   ├── parentSpanId：父节点（拼出调用树）
│   ├── 属性：服务名/操作名/耗时/状态
│   └── 时间线：开始时间 + 结束时间
└── 示例：
    Trace（下单）
    ├── Span: order-service/placeOrder（1.2s）
    │   ├── Span: user-service/getUser（200ms）
    │   ├── Span: Redis/GET cart（15ms）
    │   └── Span: MQ/SEND orderCreated（30ms）
    └── 跨进程：每个服务只上报自己那段的 Span → 汇聚成树

traceId 传播（跨服务的关键机制）
├── HTTP：Header 传递（W3C: traceparent）
│   ├── 前端→网关：生成 traceId → 传给每个下游
│   └── 每个服务透传：X-Trace-Id（或标准 traceparent）
├── MQ：消息体带 traceId（消费端继承）
├── 线程池：ThreadLocal 传递（注意线程复用要清理）
└── 金句：traceId 是「分布式排障的身份证」——日志/指标都能关联
```

## 3. OpenTelemetry 与 SkyWalking

> 🎯 **2026 标准与落地的分工**：**OpenTelemetry（CNCF 标准）负责采集规范，SkyWalking 负责展示**：

```text
OpenTelemetry（OTel，2026 事实标准）
├── 定位：采集规范 + SDK + 导出（三合一标准）
│   ├── 规范：Trace/Metric/Log 的统一数据模型
│   ├── SDK：Java/Go/Python 等语言接入（自动埋点）
│   └── 导出：OTLP 协议 → 后端（Jaeger/Prometheus/云厂商）
├── Java 接入：javaagent -javaagent:opentelemetry-javaagent.jar
│   ├── 零代码自动埋点（HTTP/DB/MQ/框架全覆盖）
│   └── 2026 新特性：eBPF 免埋点方案（观测面扩展）
└── 金句：OTel 是「数据面的普通话」——统一格式，可插拔后端

SkyWalking（Apache，国内主流全栈 APM）
├── 定位：完整的 APM 平台（追踪 + 指标 + 拓扑 + 告警）
├── 组件：
│   ├── Agent：Java agent 自动埋点
│   ├── OAP Server：分析 + 存储（ES 后端）
│   └── UI：调用拓扑图/慢请求/服务依赖
├── 核心价值：调用拓扑（Service Map）——一图看懂服务依赖
└── 对比选型
    ├── SkyWalking：开箱即用、中文文档、国内主流
    ├── Jaeger：追踪专注、轻量、与 OTel 结合
    ├── Zipkin：老牌、功能朴素
    └── Grafana Tempo/云厂商：按基础设施选
```

## 4. 采样策略与成本

> 🎯 **全量追踪的成本扛不住**（每个请求 N 个 span 的存储/计算）——采样是工程必修：

```text
采样率与成本曲线
├── 100% 采样：精确但成本爆炸（大流量系统存不下）
├── 1% 采样：便宜但「问题请求」可能没被采到
├── P99 慢请求天然概率低 → 低采样率下很难抓到
└── 金句：采样是「概率与成本的交易」——按需动态调整

采样策略（2026 实践）
├── ① 固定比例采样：head-based（请求入口抛硬币）
│   ├── 简单；慢请求/错误请求易漏
├── ② 动态采样：tail-based（按 Span 结果决定保留）
│   ├── 慢 span/错误 span 必采，正常请求抽样
│   └── 需要缓冲（等完整结果）——推荐方案
├── ③ 关键路径必采：支付/下单接口 100% 采样
│   └── 非核心查询 1%——分级采样
└── ④ 错误全采：错误 trace 永不采样掉（错误率低，成本可控）

工程基线（参考）
├── 常规服务：10% 采样 + 错误必采 + 关键路径 100%
├── 核心交易链路：100% 采样（成本换确定性）
└── 存储策略：span 详情保留 7-30 天 + 聚合指标长期
```

## 5. 日志规范与全链路日志

> 🎯 **日志是排障的「最后证据」**——规范三要素：traceId、结构化、级别纪律：

```text
日志规范三要素
├── ① traceId 必打：MDC（Mapped Diagnostic Context）
│   └── Java：logback MDC.put("traceId") → 过滤器自动注入
│   └── 效果：日志平台按 traceId 搜索 = 全链路日志聚合
├── ② 结构化：JSON 格式（logstash-logback-encoder）
│   ├── {"time":..., "level":"ERROR", "traceId":"...", "service":"order"}
│   └── 可被日志平台（ELK/Loki）解析检索
└── ③ 级别纪律：ERROR 只给真异常（不是业务提示）
    ├── ERROR 过多 → 告警失效（狼来了）
    └── 规范：业务拒绝 = WARN/INFO，系统异常 = ERROR

全链路日志聚合方案
├── ELK（Elasticsearch + Logstash + Kibana）：老牌
├── Loki + Grafana：轻量（2026 主流增长）
└── 云厂商日志服务（阿里云 SLS 等）：国内常用
```

```xml
<!-- logback 接入 traceId（MDC 自动注入） -->
<pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - traceId:%X{traceId} %msg%n</pattern>
```

## 6. 指标监控与告警

> 🎯 **指标四金指标 + Prometheus/Grafana 生态**：

```text
RED 四金指标（请求纬度）
├── Rate：QPS（流量变化）
├── Errors：错误率（健康度）
├── Duration：延迟（P50/P95/P99——P99 是体验真相）
└── USE（资源纬度）：Utilization/Saturation/Errors（CPU/内存/连接池）

基础设施（2026 主流）
├── Prometheus：采集 + 存储（拉模式）
├── Grafana：可视化面板
├── Alertmanager：告警（分级：P1 立即 / P2 15 分钟）
└── 告警规则要点
    ├── P99 > 1s 持续 5 分钟 → 告警
    ├── 错误率 > 1% 持续 3 分钟 → 告警
    └── 磁盘/连接池使用率 > 85% → 告警
```

## 7. 面试冲刺：全系列高频考点

### 🟢 ID 篇（[[02]]）

**Q1：雪花算法 64 位怎么分的？为什么趋势递增？**

```text
答：1 符号位 + 41 位毫秒时间戳 + 10 位机器 ID + 12 位序列号。
时间戳放高位 → 数值随时间递增；同毫秒序列号递增。
核心公式：(ts-epoch)<<22 | workerId<<12 | sequence。
```

**Q2：时钟回拨怎么办？**

```text
答：四级容错——① 小回拨等待追平；② 大回拨拒绝生成（抛异常/启动校验）；
③ 备用时钟/序列号补偿；④ NTP 监控 + 告警。
核心：回拨不可怕，可怕的是没预案。
```

### 🔵 锁篇（[[03]]）

**Q3：Redis 分布式锁怎么一步步演进？**

```text
答：SETNX（死锁）→ SETNX+EXPIRE（非原子）→ SET NX EX+token（误删）
→ Lua 原子校验删除 → Redisson（看门狗续期）。
面试加分：能手写 Lua 删除脚本。
```

**Q4：看门狗原理？传 leaseTime 有什么区别？**

```text
答：默认 30s 租约，每 10s（1/3）自动续期，业务跑多久锁活多久，
客户端崩溃则 30s 内自动释放。传了 leaseTime → 看门狗不启用，
到期强制过期（业务可能没跑完）。
```

**Q5：Redlock 的争议？**

```text
答：Kleppmann 三点质疑——① GC 停顿导致锁过期后旧持有者还在操作；
② 时钟漂移影响有效性判断；③ 无 Fencing Token。
Antirez 反驳：理论正确但工程可规避。结论：强一致用 ZK/etcd（CP）。
```

### 🟣 缓存篇（[[04]]）

**Q6：穿透/击穿/雪崩区别和治理？**

```text
答：穿透=查不存在的 key（空值缓存/布隆过滤器）；
击穿=热点 key 过期瞬间（互斥锁重建）；
雪崩=批量 key 过期（TTL 随机化 + 多级缓存）。
```

**Q7：缓存双写一致性怎么做？**

```text
答：Cache Aside（写后删缓存）→ 延迟双删（删-sleep-再删）
→ binlog 订阅（Canal）异步删除。原则：接受短暂旧值 + TTL 收敛，
一致性预算花在数据库事务。
```

### 🔴 事务篇（[[05]]）

**Q8：Seata AT 模式原理？**

```text
答：无侵入自动回滚——SQL 执行前后自动记录前置/后置镜像，
全局失败时用镜像反写恢复（带 WHERE 校验防脏写），
全局锁保证写隔离。业务代码零侵入。
```

**Q9：AT 和 TCC 区别？怎么选？**

```text
答：AT 自动镜像回滚（无侵入）；TCC 业务写 Try/Confirm/Cancel
三方法（高侵入但灵活，能处理不可自动回滚的资源）。
常规选 AT；高并发/资源预留选 TCC；长流程选 Saga。
```

### 🟠 分片篇（[[06]]）

**Q10：分片键怎么选？**

```text
答：四标准——① 查询频率最高；② 分布均匀；③ 不可变；
④ 容忍范围查询退化为广播。选错 = 查询全路由 + 热点片。
```

**Q11：分库分表扩容怎么做？**

```text
答：取模分片扩容 = 全量重分片（停机迁移/双写迁移）。
2026 主流：预分片（一次分够）+ 冷热归档，永远不触发扩容手术。
```

### 🟡 幂等篇（[[07]]）

**Q12：接口幂等怎么做？**

```text
答：四件套——① 数据库唯一索引（最硬）；② 状态机 WHERE 校验
（防重复+防回退）；③ 去重表（消息消费）；④ 幂等框架（请求级
去重 + 结果缓存）。原则：锁可能失效，幂等永不失效。
```

## 8. 核心要点

> 6. **四金指标**：Rate/Errors/Duration + USE——P99 是体验真相
