## 1. 分布式事务的问题域

**"跨库写入"是分布式事务的问题域**：一个业务动作要写多个库（订单库 + 库存库 + 积分库）——**任何一个库写失败，整体一致性怎么办**。**先划清边界**：**单库内的事不是分布式事务**（数据库本地事务解决）；**能异步解耦的不用强一致**（发消息 vs 同步调用的选择）——"**分布式事务的起点是'先把问题域缩小'：真正需要强一致的业务，比你以为的少得多**"。**三个典型真场景**：**跨服务扣款 + 记账**（钱不能丢）、**下单 + 扣库存**（高并发下的一致性）、**对账类**（最终一致即可）。**代价认知**：**分布式事务的代价 = 性能（额外通信与锁）+ 复杂度（补偿逻辑）**——**"每引入一个分布式事务方案，都要问：这笔业务值得吗？"**

## 2. 方案谱系：从强一致到最终一致

```text
强一致（同步）                   最终一致（异步）
Seata AT/TCC ─ Seata SAGA ─ 本地消息表/Outbox ─ 事务消息 ─ 对账补偿
  [实时一致]                                        [延迟一致]
```

**谱系的三个刻度**：**一致性强度**（强一致 vs 最终一致）、**同步/异步**（调用方等不等结果）、**复杂度**（补偿逻辑/回查/对账的投入）。**选择心法**：**从右往左选**——**先看能否最终一致（异步/对账），不行再上强一致**——"**能异步解决的别上强一致，能本地消息解决的别上全局事务**"——大多数"订单 + 通知"类业务在右边就解决了。

## 3. Seata：强一致三模式

**Seata（2019 阿里巴巴开源）是 Java 分布式事务的事实标准框架**——专精体系深潜（`../../Spring组件汇总/Spring Cloud 微服务全家桶（分布式）/Spring Cloud Alibaba（阿里实现，属于 Spring Cloud 生态实现）/Seata：分布式事务/`），**本体系讲三模式选型**：

**AT 模式（自动补偿）**：**无侵入**——框架记录 SQL 执行前后快照（undo_log），失败自动回滚——"**最省心：业务代码零侵入，代价是性能（快照 + 锁）**"——适合**中低并发、SQL 简单**；**TCC 模式（手动补偿）**：**Try/Confirm/Cancel 三段式**——业务自己写补偿逻辑——"**最灵活：性能好，代价是补偿代码全手写**"——适合**高性能 + 业务可拆三段**（扣款/预留资源）；**SAGA 模式（长事务）**：**编排式**（每步一个子事务 + 补偿），**适合长流程、跨系统、不需要实时回滚**（预订流程）。

**Seata 的选型主线**：**"AT 省心但慢、TCC 快但累、SAGA 适合长流程"**——**新项目默认 AT 起步，性能不够再 TCC，长流程用 SAGA**。**注意**：Seata 的全局锁与事务隔离（全局写锁）在高并发下是瓶颈——**"Seata 不是万能：高并发扣库存场景，回到 04 篇的 Redis 锁 + 幂等更实际"**。

## 4. Outbox：本地消息表模式

**Outbox（本地消息表）是 2026 年"事务 + 消息"的务实默认**——**核心思想：把"写业务数据"和"发消息"放进同一个本地事务**：

```text
同一本地事务：
  ① INSERT INTO orders(...)                 # 业务数据
  ② INSERT INTO outbox(msg_type, payload, status)  # 消息落表
本地事务提交后：
  ③ 独立发送器轮询 outbox 表 status=PENDING 的记录 → 发 MQ
  ④ 发送成功 → status=已发送（或 MQ 消费成功 → 删除记录）
```

**为什么它能保证"业务成功 = 消息必达"**：**业务与消息同库同事务**——要么都成功要么都失败；**发送器是独立组件**（定时轮询/监听 binlog）——**发失败就重试**（状态机：PENDING → 已发送）——"**本地消息表把'分布式事务'降级成'本地事务 + 重试'——复杂度降一个量级**"。**三个注意**：**outbox 表要幂等消费**（消费方按业务 ID 去重，第 6 节）；**发送器要支持批量与重试退避**；**数据清理**（已消费的记录定期归档删除）。

## 5. 事务消息与本地消息表对比

**事务消息（RocketMQ 的 half message）**：**消息先发半事务状态 → 本地事务执行 → 提交/回滚消息**——**MQ 侧保证"消息与本地事务同生死"**。**与 Outbox 的对比**：

| 维度 | Outbox（本地消息表） | 事务消息 |
|------|---------------------|---------|
| 依赖 | 业务库（任何 MQ 都行） | RocketMQ 等支持半事务的 MQ |
| 实现 | 业务表 + 发送器轮询 | MQ 事务钩子 + 回查 |
| 复杂度 | 低（表 + 轮询） | 中（半事务 + 回查机制） |
| 通用性 | ⭐ 与 MQ 无关 | 绑定特定 MQ |

**选型主线**：**已用 RocketMQ 用事务消息（MQ 自带能力）；用 Kafka/其他 MQ 用 Outbox**（不依赖 MQ 特性）——"**Outbox 是'自己实现的事务消息'，事务消息是'MQ 内置的 Outbox'——殊途同归，看你的 MQ 给不给**"（消息队列体系交叉：`../../03-消息队列/`）。

## 6. 幂等设计

**幂等：同一个请求执行多次，结果与执行一次相同**——**分布式系统里重试是常态**（网络超时重试、MQ 重复投递、用户双击），**幂等是"重试的安全网"**——"**分布式系统的写接口，默认都要幂等，幂等是免费的午餐（早做便宜晚做贵）**"。**四件套方案**：

**唯一键防重**：业务请求带唯一业务号（订单号），**唯一索引/唯一约束拦截重复插入**——"**数据库唯一键是最强的幂等防线**"；**防重表**：独立表存"已处理请求号"，处理前 INSERT 尝试（冲突 = 已处理）——"**唯一键的显式版，适合跨表业务**"；**状态机**：订单状态 PENDING → PAID → SHIPPED——**只有特定状态转移才允许**（重复的 PAID 请求在状态检查时被挡）——"**状态机是业务幂等的自然表达**"；**分布式锁**：关键路径加锁（04 篇）——**锁是幂等的兜底不是主角**（先唯一键/状态机，锁留给"必须互斥"的场景）。**幂等设计的位置**：**每个写接口的入口**（Controller/消费者）——"**幂等不是事后补丁，是写接口的默认设计约束**"。

## 7. 方案选型

| 场景 | 方案 |
|------|------|
| 高并发扣库存 | Redis 锁 + 原子 SQL（04/06 篇，**不需要分布式事务**） |
| 中低并发跨库强一致 | Seata AT（省心） |
| 高性能 + 业务可拆三段 | Seata TCC（累但快） |
| 长流程编排 | Seata SAGA |
| 业务 + 消息必达 | Outbox（默认）或 RocketMQ 事务消息 |
| 对账兜底 | 定时对账 + 补偿（最终一致的最后防线） |

**选型主线一句话**："**先问能不能异步（Outbox/对账），再问要不要强一致（Seata），最后才考虑锁与补偿的组合——幂等是全程的默认设计**"。

## 8. 五个常见坑

- **坑一**：所有跨服务操作都上 Seata——**性能与复杂度爆炸；大多数场景 Outbox/异步就够**（第 7 节）；
- **坑二**：Outbox 消费不幂等——**重复投递重复处理；消费方按业务 ID 去重**（第 6 节）；
- **坑三**：重试无退避——**重试风暴；指数退避 + 上限**（消息队列体系交叉）；
- **坑四**：幂等只在"想起来的接口"做——**写接口默认幂等是约束不是可选项**（第 6 节）；
- **坑五**：对账补偿没有——**最终一致的最后防线缺失；定时对账是生产标配**（第 7 节）。
