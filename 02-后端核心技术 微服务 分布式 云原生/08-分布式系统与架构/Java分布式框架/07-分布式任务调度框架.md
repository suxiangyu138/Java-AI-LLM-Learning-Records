## 1. 单机 Cron 的三个死穴

**单机定时任务（@Scheduled/Quartz）在分布式环境有三个死穴**：**机器挂了任务丢**（单点故障——凌晨的批处理跑一半机器宕机，任务直接消失）；**多机器重复跑**（部署 3 个实例，每个实例的 Cron 都触发——**同一任务执行 3 次**——扣款/发消息类任务直接事故）；**大数据量没分片**（10 万用户的通知要一台机器慢慢跑，**不能拆成 3 台并行**）。**分布式任务调度框架解决这三件事**：**高可用**（任务不因单机故障丢失——另一台接棒）、**不重复**（同一时刻只有一台执行）、**可分片**（任务按 shard 拆给多台并行）。**2026 的现实**：**@Scheduled 只适合"单实例 + 无状态"的应用**；**任何"多实例部署 + 定时任务"的应用都该用调度框架**——"**定时任务在分布式时代的默认选择是调度框架，不是 Cron**"。

## 2. 三强对比总览

| 维度 | XXL-Job | ElasticJob | PowerJob |
|------|:---:|:---:|:---:|
| 架构 | 集中式（调度中心 + 执行器） | 去中心（ZK 协调） | 集中式（服务器 + worker） |
| 分片能力 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 调度精度 | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐（时间轮毫秒级） |
| 监控/控制台 | ⭐⭐⭐⭐（完整） | ⭐⭐⭐（无官方） | ⭐⭐⭐⭐⭐（内置看板） |
| 社区活跃 | ⭐⭐⭐⭐⭐（23.4k stars） | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| 学习成本 | 低（开箱即用） | 高 | 中 |
| 编排（DAG） | 弱 | 弱 | ⭐ 强 |

**读表方法**：**XXL-Job 赢在"省心"、ElasticJob 赢在"分片"、PowerJob 赢在"未来"**——**没有绝对王者，按场景选**（第 7 节生产实践）。

## 3. XXL-Job：务实默认

**XXL-Job（2015 许雪里开源，美团体系，23.4k stars）是中文社区最活跃的调度框架**——**集中式架构**：**调度中心**（独立 Java Web 应用：任务配置/触发/日志/管理 UI）+ **执行器**（嵌入业务应用的组件，接收 HTTP 调度请求执行任务）。**防重复机制**：**数据库悲观锁**（`SELECT ... FOR UPDATE` 锁任务行，调度中心多实例也只有一个能触发）——"**XXL-Job 的调度中心可以集群部署，DB 锁保证'同一时刻一个触发者'**"。**任务分发**：**自研 RPC**（调度中心 → 执行器的 HTTP 调用）。**能力**：**故障转移**（执行器挂了换一个）、**分片广播**（sharding 参数传给执行器，各实例按 index/total 分片）、**阻塞策略**（串行/丢弃后续/覆盖之前）。**选型判断**：**中小项目、快速上线、要完整 UI → XXL-Job**——"**开箱即用、文档全、社区问答多——务实默认没有之一**"（一次 180+ 任务从 ElasticJob 迁到 XXL-Job 的 2026 案例：ZK 依赖多余、分片用不上、无控制台"盲跑"是三大迁移理由）。

## 4. ElasticJob：去中心强分片

**ElasticJob（当当 2015 开源，Apache ShardingSphere 子项目）**——**去中心化**：**没有调度中心**——**执行器自己触发**（每实例都按时间表判断"该不该我跑"），**ZK 协调一切**：任务分片分配、主节点选举、节点增减感知与重新分片。**核心优势：弹性分片**——**节点增减自动重新分片**（数据清洗/分布式 ETL/报表的大批量任务：10 台跑 10 片，加 2 台自动变 12 片）——"**ElasticJob 的分片是'自动感知'的，XXL-Job 的分片是'手动传参'的**"。**两个代价**：**ZK 强依赖**（多一个中间件 = 多一个故障点——**网络抖动触发重新分片/重新选举，任务抖动**）；**无官方控制台**（任务状态"盲跑"——**100+ 任务的团队运维靠猜**）。**选型判断**：**海量数据、弹性扩缩、分片是刚需 → ElasticJob**；**否则别为分片能力背上 ZK 依赖**（第 7 节）。

## 5. PowerJob：新一代编排

**PowerJob（2020 前后开源，4.3k stars）是新一代调度框架**——**四个新东西**：**无锁调度**（乐观锁版本号替代 DB 悲观锁——**调度中心高并发不锁表**）；**时间轮**（**毫秒级调度精度**——对比 Cron 分钟级）；**DAG 工作流编排**（**任务依赖：A 成功才跑 B**——复杂流程的原生支持，XXL-Job/ElasticJob 的弱项）；**内置监控与全链路追踪**（看板 + 执行日志链路）。**能力**：MapReduce 分布式计算、多租户、Java/脚本/SQL 多任务类型。**2026 案例**：**百万级日任务从 Quartz 迁到 PowerJob，执行成功率 92% → 99.5%**——"**新一代的差距在精度、编排与可观测**"。**代价**：**较新**（存量兼容/社区规模不及 XXL-Job）、概念多（学习曲线中等）。**选型判断**：**复杂工作流（DAG 依赖）、毫秒级精度、云原生 → PowerJob**——"**XXL-Job 是现在的答案，PowerJob 是'复杂到 XXL-Job 不够用'时的答案**"。

## 6. 调度机制对比：DB 锁 vs ZK vs 无锁

**三强背后是三种"谁来保证不重复触发"的机制**：**XXL-Job 用 DB 悲观锁**（`SELECT FOR UPDATE`——**实现最简单、依赖最轻（业务库就行），但高并发下锁表是瓶颈**——任务少没问题，任务多/调度频率高时锁竞争）；**ElasticJob 用 ZK 选举**（**主节点决定分片与触发——强一致但依赖 ZK 可用性**，网络抖动 = 任务抖动，03 篇 ZK 场景）；**PowerJob 用乐观锁**（版本号 CAS——**无锁竞争、高并发友好，但实现复杂**）。**机制的选型含义**：**任务量级小（几十个）任何机制都够**；**任务量级大（几百上千个）XXL-Job 的 DB 锁要监控锁等待**；**追求极致并发调度选 PowerJob**——"**调度机制的差异，在任务量小时无感，在量大时决定天花板**"。

## 7. 生产实践

**任务调度生产七要点**：其一，**调度中心 ≥ 2 节点**（高可用——XXL-Job 集群靠 DB 锁、PowerJob 靠乐观锁）；其二，**执行器集群 + 路由策略**（轮询/一致性哈希/故障转移/分片广播——**按任务类型选**：普通任务轮询、有状态任务一致性哈希、批处理分片广播）；其三，**心跳与失联处理**（执行器心跳 ~30s，失联自动摘除——**故障转移的前提是"知道谁死了"**）；其四，**幂等设计**（重试/故障转移会导致重复执行——**唯一 ID + 状态机 + 防重表**，05 篇第 6 节——"**调度框架保证'任务会跑'，不保证'只跑一次'——幂等是任务代码的责任**"）；其五，**阻塞策略**（上次没跑完怎么办：串行等待/丢弃/覆盖——**长任务用串行，短任务用丢弃**）；其六，**分片参数化**（`shardIndex/shardTotal` 决定"我这片处理哪段数据"——**分片任务要能幂等续跑**）；其七，**监控与告警**（任务失败告警、执行时长告警、调度中心负载——"**定时任务是夜里出事的重灾区，告警是标配**"）。

## 8. 五个常见坑

- **坑一**：任务代码不幂等——**故障转移/重试重复执行；幂等是任务的第一要求**（第 7 节）；
- **坑二**：调度中心单节点——**调度中心挂了任务全停；≥2 节点**；
- **坑三**：为分片能力引入 ZK 依赖（选 ElasticJob）但业务用不上分片——**多一个故障点；XXL-Job 分片够用就别上 ZK**（第 4 节）；
- **坑四**：阻塞策略不配——**上次没跑完这次又触发，任务叠加；按任务特性选串行/丢弃**；
- **坑五**：任务失败无告警——**批处理凌晨失败到早上才发现；失败告警是标配**（第 7 节）。
