## 1. 选型的原则

**技术选型的四条原则，比任何框架对比都重要**：其一，**"团队熟悉度优先"**——**新框架的学习成本是隐性成本**（出问题没人会修 = 最大的风险）——"**选团队会的，不选网上吹的**"；其二，**"够用就好"**——**功能过剩的框架是负债**（ElasticJob 的 ZK 依赖案例：分片用不上还多一个故障点，07 篇）——"**选型是减法：去掉用不上的能力**"；其三，**"生态与人才匹配"**——框架的招聘难度/社区活跃/文档质量是长期成本（XXL-Job 社区活跃 = 招人容易问答多）；其四，**"演进路径要留"**——**当前选择不能堵死未来迁移**（协议选 HTTP/2 系 = 将来跨语言/云原生都顺）——"**选型不是选'最好的'，是选'最合适的 + 有退路的'**"。

## 2. 三大技术栈全景

**01 篇提过三栈，这里给完整配套**：

**栈一：Dubbo 栈（性能优先）**——**Dubbo 3（Triple）+ Nacos + Redisson + XXL-Job + Sentinel**——**内部 RPC 高性能、中文生态成熟、治理全家桶**——适用：**服务多、调用密、团队 Java 熟**的业务系统（电商/交易后台）。

**栈二：Spring Cloud 栈（生态优先）**——**Spring Cloud（Gateway/Feign/LoadBalancer）+ Nacos + Sentinel + Seata**（全家桶专精体系）——**HTTP 标准、与 Spring 生态无缝、开发效率高**——适用：**Spring 技术栈标准团队、快速迭代**的产品线。

**栈三：云原生栈（基础设施优先）**——**K8s（Service/Ingress）+ gRPC + etcd + Istio（可选）+ PowerJob**——**K8s 收编注册发现/负载均衡，框架退到业务层**——适用：**绿地项目、多语言团队、K8s 已就位**——"**云原生栈的哲学：能交给平台的不自己造**"。

**三栈的共同件**：**Redisson 锁、Outbox/Seata 事务、一致性哈希分片、Redis 限流**——**"锁、事务、调度、限流是跨栈的公共件，RPC 与注册是栈的分水岭"**——选栈时先定"通信层"（RPC/注册），公共件按 04-08 篇单件选。

| 问题 | 2026 默认 | 备选 | 依据 |
|------|----------|------|------|
| RPC | Dubbo 3（Java 内） | gRPC（多语言） | 02 篇 |

## 4. 演进路径：从单体到云原生

**大多数系统不是绿地，演进路径比终态重要**：

**阶段一：单体 + 缓存**——单应用 + Redis（锁/限流开始出现）——**不引入分布式框架**（锁用 Redisson、限流用 RateLimiter 就够）；**阶段二：服务拆分 + RPC**——**拆服务 → Dubbo/Spring Cloud + Nacos**——分布式问题集中爆发（锁/事务/调度全上）；**阶段三：治理成熟**——Sentinel 规则化、Seata/Outbox 规范、XXL-Job 统一调度——**"框架到位不是终点，治理到位才是"**；**阶段四：云原生化**——**K8s 部署 → 服务发现逐步收编 → （可选）Mesh**——**存量 Dubbo/Spring Cloud 迁 K8s 是渐进过程**：先容器化跑通，再让 K8s 承担部分基础设施职能，**RPC 协议与业务代码不动**——"**演进原则：一次只动一层，业务代码最后动**"。

## 5. 混合架构

**大系统往往是混合的**，三种常见混合：**Dubbo + Spring Cloud 共存**——**核心交易链 Dubbo（性能）、外围标准接口 Spring Cloud**——**通过网关互调**（Dubbo 的 REST 暴露与 Spring Cloud 互通——02 篇 Triple 的 HTTP/1 能力）；**自研 + 开源混用**——**核心链路自研（完全可控）、通用件开源**；**云原生 + 存量共存**——**新服务 gRPC + K8s、存量 Dubbo 继续跑**（双注册中心：新服务注册 etcd/Nacos、存量 Dubbo 注册 Nacos——**网关统一入口**）。**混合架构的三个纪律**：**边界清晰**（哪些服务走哪条栈写清楚）；**互调走标准**（跨栈调用走 HTTP/gRPC 标准协议——**别让 Dubbo 协议跨栈裸奔**）；**治理不分裂**（限流/监控/日志统一平台——**栈可以两套，可观测必须一套**）。

## 6. 架构评审清单

- [ ] 每个问题都有明确选型（七大件表填全）
- [ ] 选型与团队技能匹配（会的人能维护）
- [ ] 无"功能过剩"引入（用不上的能力没背上）
- [ ] 跨栈互调走标准协议（HTTP/gRPC）
- [ ] 可观测统一（日志/监控/链路一套）
- [ ] 注册中心/调度中心等高危件 ≥ 2 节点
- [ ] 锁/幂等/重试的语义明确（04/05 篇）
- [ ] 演进路径有文档（当前在哪个阶段、下一步是什么）
- [ ] 故障演练做过（注册中心挂/锁服务挂/调度中心挂）
- [ ] 每引入一个框架，写清"它解决什么问题、挂了怎么办"

**"评审清单的最后一条是灵魂：每加一个框架 = 加一个故障点——答不上'挂了怎么办'，就别上"**。

## 7. 五个常见坑

- **坑一**：按"网上最佳实践"选型不按团队——**最佳实践是别人的；团队会修才是自己的**（第 1 节）；
- **坑二**：七件各选各的不管协同——**注册中心/锁/调度要能共用一个 Redis/ZK 集群；画全景图评审**（第 6 节）；
- **坑三**：绿地项目直接全云原生——**云原生栈的学习与运维成本高；团队没 K8s 经验先 Spring Cloud/Dubbo**（第 4 节）；
- **坑四**：混合架构治理分裂——**两套栈两套监控 = 故障时两眼一抹黑；可观测统一**（第 5 节）；
- **坑五**：框架上了没有故障预案——**注册中心挂了怎么办/锁服务挂了怎么办；演练过才算数**（第 6 节）。
