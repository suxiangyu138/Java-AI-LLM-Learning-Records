## 1. 寻址问题：数据放哪台机器

**分布式存储/缓存的核心问题：一条数据应该放在哪台机器上**——**寻址（routing）算法决定"key → 节点"的映射**。**寻址的三个目标**：**均匀**（数据与流量摊平——热点均衡）；**可迁移**（节点增减时移动最少的数据）；**可查询**（给定 key 能快速算出在哪个节点）。**两个经典答案**：**取模哈希**（简单但迁移爆炸）与**一致性哈希**（迁移最小化）——**"寻址算法的好坏，用'加一台机器要搬多少数据'来衡量"**。**场景**：缓存集群（Redis Cluster）、消息分区（Kafka 的 partition 分配）、负载均衡（一致性哈希路由）、任务分片（07 篇）。

## 2. 取模哈希的致命伤

**取模哈希：hash(key) % N**——key 映射到 0..N-1 的桶。**致命伤在扩容**：**N 从 3 变 4，hash 结果全部重算——几乎所有 key 的桶号都变了，等于全部数据迁移**——"**加一台机器，全集群搬家**"——生产上"扩容就是大事故"的根源。**另一个问题**：**数据分布依赖 N 的质数性**（hash % 12 与 % 12 的桶不均衡——**取模的桶数与哈希质量耦合**）。**取模不是不能用**：**数据量小、不扩容、静态分片**（如按月分表）用取模没问题——"**取模是静态世界的答案，动态世界（扩缩容常态化）要一致性哈希**"。

## 3. 一致性哈希原理

**一致性哈希（Consistent Hashing，Karger 1997）**：**把哈希空间组织成首尾相接的环（0 到 2^32-1）**——**节点与 key 都哈希到环上**——**key 归属"顺时针遇到的第一个节点"**：

```text
环（2^32 空间）：
  N1 节点在 100    → 管辖 (80, 100] 区间的 key
  N2 节点在 300    → 管辖 (100, 300] 区间的 key
  N3 节点在 600    → 管辖 (300, 600] 区间的 key
  ... 新增 N4 在 200 → 只接管 (100, 200] 区间（原来 N2 的），其他节点零迁移
```

**为什么只迁移 1/n**：**新增节点只"截胡"环上它的前任节点的一段区间**——**只有落在该区间的 key 换归属，其他 key 不动**——"**扩容从'全量搬家'变成'局部让位'**"。**删除节点同理**：**它的区间并入后继节点，只影响一段**。**代价**：**hash 质量依赖节点在环上的分布**——**节点少时分布不均（倾斜）**——虚拟节点解决（第 4 节）。

## 4. 虚拟节点：解决倾斜

**问题**：3 个节点哈希到环上可能挤在一起——**大段区间归一个节点，数据与流量全压给它**（热点倾斜）。**虚拟节点（virtual node）方案**：**每个物理节点在环上放 N 个虚拟副本**（如 100-200 个，`N1-v1, N1-v2, ...`）——**虚拟节点均匀铺满环，key 落到谁的虚拟节点就归谁**——"**虚拟节点 = 物理节点的'分身'，分身铺满环 = 分布自动均匀**"。**两个额外收益**：**负载均衡粒度更细**（虚拟节点数可调，权重差异化——强的物理节点多放副本）；**故障隔离粒度更细**（一个虚拟节点区间受影响，物理节点整体仍然均匀）。**工程惯例**：**虚拟节点 100-200 个/物理节点**（太多浪费内存，太少不均匀）——"**虚拟节点是工程对理论的修补：理论均匀靠哈希，工程均匀靠分身**"。

## 5. 工程实现：Redis Cluster 与代理

**一致性哈希的工业实现两大家**：

**Redis Cluster**：**16384 个固定槽（slot）**——`key 归属 = CRC16(key) % 16384`，**槽分配到节点**（节点增减时**槽整体迁移**，只搬槽对应的数据）——"**Redis Cluster 是'一致性哈希思想的槽化实现'：槽是固定的'虚拟节点'，节点是槽的容器**"——**为什么固定槽更好**：**迁移以槽为单位（可控、可监控）、key 归属计算确定（CRC16 固定）、槽迁移支持增量搬迁**（Redis 体系交叉：`../../02-非关系型数据库/Redis/`）。

**代理方案（一致性哈希代理）**：**代理层（如 twemproxy/自研网关）维护"虚拟节点环 → 物理节点"映射**——客户端连代理、代理按环路由——**Java 侧自研缓存分片/负载均衡常用**（如 Dubbo 的一致性哈希负载均衡就是虚拟节点环实现，02 篇治理）。**选型主线**：**缓存用 Redis Cluster（标准件）；自研分片/路由用一致性哈希环**（虚拟节点 100+）——"**能用标准件用标准件，自研环留给'标准件不覆盖'的场景**"。

## 6. 哈希一致性 vs 强一致性

**一致性哈希是"数据分布"算法，不是"数据一致性"协议**——**别混淆两个"一致性"**：**哈希一致性**（数据放哪——寻址问题）vs **强一致性**（数据是否最新——共识问题，Paxos/Raft/ZAB，分布式系统理论体系）。**一个分布式存储系统的完整认知**：**一致性哈希决定"key 去哪个节点"，共识协议决定"节点间的数据怎么对齐"**——"**寻址管分布，共识管一致——两层各司其职，面试别混**"。**实践结合**：**Redis Cluster 的哈希槽只管路由**，主从复制 + 故障转移管一致性——"**槽位是地图，主从是备份，缺一不可**"。

## 7. 五个常见坑

- **坑一**：拿取模哈希做动态分片——**扩容全量迁移；动态集群用一致性哈希**（第 2 节）；
- **坑二**：一致性哈希不配虚拟节点——**节点少时严重倾斜；每物理节点 100+ 虚拟节点**（第 4 节）；
- **坑三**：把一致性哈希当强一致——**它只管放哪，不管新不新；一致性靠复制/共识**（第 6 节）；
- **坑四**：自己实现哈希环——**边界与 bug 多（哈希碰撞/节点删除后的区间合并）；Redis Cluster 或成熟库**（第 5 节）；
- **坑五**：忽略数据迁移的"迁移窗口"——**槽迁移期间数据读不到/写失败要客户端重定向；迁移在低峰做**（第 5 节）。
