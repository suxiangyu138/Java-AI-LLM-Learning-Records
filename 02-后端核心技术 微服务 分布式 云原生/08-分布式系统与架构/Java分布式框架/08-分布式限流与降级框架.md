## 1. 三个概念：限流 / 降级 / 熔断

**流量治理的三个动作，先分清语义**：**限流（Rate Limiting）**——**"进不来就拒"**：单位时间内最多放 N 个请求，超出的拒绝（429）或排队——**保护自己**（服务不被流量打垮）；**降级（Degradation）**——**"不行就退而求其次"**：主路径失败时走备选（返回缓存数据/默认值/简化逻辑）——**保底可用**；**熔断（Circuit Breaker）**——**"不行就别试了"**：连续失败达到阈值就打开断路器，**一段时间内直接短路**（不发起真实调用），让下游喘口气——**防止雪崩**（A 挂 → B 重试打爆 → C 也挂）。**三者关系**：**限流管"进"、熔断管"出"、降级管"替代"**——"**限流防自己被打垮，熔断防拖垮别人，降级保功能不消失**"（后端分布式名词通俗解释体系交叉：`../../09-Web开发全流程/后端 分布式常用名词通俗解释/`）。

## 2. 限流算法家族

**限流算法的四个经典**：**固定窗口**——每秒一个窗口计数，超限拒绝——**实现最简单但窗口边界突刺**（59.9s 与 60.1s 各放满 = 一秒内双倍流量）；**滑动窗口**——按时间细分为小格，滑窗统计——**平滑了突刺，代价是内存（每格计数）**；**漏桶（Leaky Bucket）**——**恒定速率流出**，进多了溢出丢弃——**"速率绝对平稳"**（削峰填谷，适合保护下游恒定处理能力）；**令牌桶（Token Bucket）**——**匀速放令牌，请求拿令牌才放行**，桶满则令牌作废——**"允许突发"**（积攒的令牌可支撑瞬间并发）——**最常用**（Sentinel/Guava 默认）。**选型主线**：**"要平滑削峰用漏桶，要容忍突发用令牌桶"**——**绝大多数场景令牌桶**；**固定窗口留给"精度无所谓"的场景**。

## 3. Sentinel：Java 侧事实标准

**Sentinel（2018 阿里巴巴开源）是 Java 流量治理的事实标准**——专精体系深潜（`../../Spring组件汇总/Spring Cloud 微服务全家桶（分布式）/Spring Cloud Alibaba（阿里实现，属于 Spring Cloud 生态实现）/Sentinel：流量控制熔断降级/`），**本体系讲定位与选型**。**三个看家能力**：**流量控制**（QPS/并发线程数限流 + 预热/排队等高级模式）；**熔断降级**（慢调用比例/异常比例/异常数三种策略）；**系统保护**（系统负载自适应——**BBR 算法：负载高时自动收紧入口**）。**架构**：**Sentinel 客户端**（嵌入业务，资源埋点）+ **控制台**（Dashboard：规则管理/监控）。**规则持久化**（推模式：控制台 → Nacos → 客户端）。**2026 定位**：**Spring Cloud/Dubbo 生态的默认治理件**（Spring Cloud Alibaba 集成、Dubbo 集成）——"**Java 微服务的流量治理，Sentinel 是'全家桶标配'**"。

## 4. Redis 令牌桶：轻量自研

**不用 Sentinel 时，Redis + Lua 实现令牌桶是轻量默认**（Redisson 也有现成 RateLimiter）：

```java
// Redisson 现成限流器（4.6.1，04 篇同源）
RRateLimiter limiter = redisson.getRateLimiter("api:order:create");
limiter.trySetRate(RateType.OVERALL, 100, 1, RateIntervalUnit.SECONDS);  // 全局每秒 100
boolean ok = limiter.tryAcquire();        // 拿不到令牌 = 限流

// 或自定义 Lua（Redis Lua 脚本体系交叉：../../02-非关系型数据库/Redis/Lua脚本/ 04 篇）
// 令牌桶原子脚本：key 存令牌数与时间戳，取令牌 INCR 递减
```

**Redis 限流的三个特点**：**分布式天然**（Redis 是共享状态——多实例的计数统一，第 6 节）；**毫秒级**（Lua 原子执行）；**轻量**（不引入控制台/规则体系）。**代价**：**Redis 是额外一跳**（每请求一次 Redis 往返——**高 QPS 下 Redis 本身可能成瓶颈**）；**无控制台/无规则热更新**（规则改代码）。**选型判断**：**简单限流（单接口 QPS）用 Redisson RateLimiter**；**要规则管理/熔断降级/系统保护上 Sentinel**——"**Redis 限流是'一把梭'，Sentinel 是'军火库'——接口少用前者，体系治理用后者**"。

## 5. Resilience4j 与其他备选

**Resilience4j**：**纯 Java 的弹性库**（熔断/限流/重试/隔离/超时五件）——**轻量（无外部依赖/无控制台）、函数式 API（装饰器模式）**——"**Sentinel 是治理平台，Resilience4j 是弹性工具箱**"。**对比**：Sentinel 有 Dashboard/规则中心/系统保护，Resilience4j 轻便但**规则改动要发版**（除配置中心动态化）。**其他**：**Spring Cloud CircuitBreaker**（Spring Cloud 的熔断抽象——封装 Resilience4j/Sentinel，有专精体系）、**网关限流**（Gateway 的 RequestRateLimiter 用 Redis 实现——入口层限流，Spring Cloud Gateway 专精体系交叉）。**选型主线**：**"接入层限流用网关（Redis 令牌桶），业务层治理用 Sentinel，轻量单体用 Resilience4j"**——"**限流要分层：网关挡第一波，业务层精确治理**"。

## 6. 分布式限流的协调问题

**单机限流（Guava RateLimiter/本地计数）在多实例下失效**：**3 个实例各限 100 QPS = 整体 300**——**"限流不分布式 = 白限流"**。**分布式限流的三个姿势**：**Redis 集中计数**（令牌桶/滑动窗口存 Redis——**共享状态，精确但每请求一跳**，第 4 节）；**网关层统一限流**（流量全过网关，**入口一处计数**——最常用的"分布式"姿势：网关限流 + 业务层本地限流兜底）；**本地限流 + 配额分摊**（每实例限 N/实例数——**无 Redis 依赖但配额不均**：热点实例先打满）。**2026 实践**：**入口网关限流（精准 + 单点）+ 业务层 Sentinel（规则治理）**——"**分布式限流的本质是'在哪一层统一计数'：选网关就是选'流量必经点'**"。

## 7. 生产实践

**限流降级生产七要点**：其一，**限流值要有依据**（压测出来的容量——**别拍脑袋设 100 QPS，压测知道真实上限**）；其二，**限流响应要友好**（429 + Retry-After + 提示文案——**别让用户看到裸 500**）；其三，**热点参数限流**（商品详情页按商品 ID 限流——**全局限流挡不住"单热点"打爆**）；其四，**熔断阈值要校准**（失败率/慢调用阈值按业务容忍度——**太敏感误熔断，太迟钝防不住**）；其五，**降级要有兜底数据**（缓存/默认值/上次结果——**降级不是"返回空"，是"返回可用的东西"**）；其六，**规则可动态调整**（Nacos 推送规则——**大促前调阈值不用发版**）；其七，**监控与告警**（限流触发量、熔断开合次数——**"限流触发量是容量信号：触发量长期高 = 该扩容了"**）。

## 8. 五个常见坑

- **坑一**：单机限流当分布式用——**多实例总配额失控；网关/Redis 统一计数**（第 6 节）；
- **坑二**：限流值拍脑袋——**压测出容量再设值**（第 7 节）；
- **坑三**：熔断后无降级——**熔断只断路不给替代；降级数据要有**（第 1 节）；
- **坑四**：Redis 限流在超高 QPS 下自身成瓶颈——**本地限流 + Redis 粗粒度结合，或网关层限流**；
- **坑五**：规则写死在代码——**调整要发版；规则中心（Nacos/控制台）动态推送**（第 7 节）。
