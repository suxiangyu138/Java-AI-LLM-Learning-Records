## 1. RPC 的本质

**RPC（Remote Procedure Call，远程过程调用）让调用方"像调本地方法一样调远程服务"**——本质是"**本地调用语义 + 网络传输**"的包装。**RPC 的三个核心决策**：**序列化**（对象怎么变成字节：Hessian2/JSON/protobuf）；**传输协议**（字节怎么走：TCP 自定义协议/HTTP/HTTP2）；**治理**（怎么找到服务、怎么负载均衡、怎么容错——依赖注册中心，03 篇）。**一次 RPC 调用的完整路径**：**代理（本地调用）→ 序列化 → 网络发送 → 服务端反序列化 → 执行业务 → 结果返回**——"**RPC 框架替你干了'网络 + 序列化 + 寻址'三件事，你只写接口**"——这也是"框架是透明的"幻觉来源（坑一：远程调用不是本地调用，超时/失败语义完全不同）。

## 2. Dubbo 3：Java 生态的 RPC 之王

**Apache Dubbo 是 Java 生态最成熟的 RPC 框架**（2011 开源，阿里巴巴背景）：**接口即服务**——Java 接口定义服务契约，`@DubboService` 暴露、`@DubboReference` 注入，**开发体验最接近本地调用**；**服务治理是看家本领**——注册发现（Nacos/ZK/K8s）、负载均衡、重试、超时、降级、灰度全内置；**性能**——二进制协议（旧 Dubbo2 协议 TCP + Hessian2）曾以"快"著称，**3.x 的 Triple 协议把性能与标准统一**（第 3 节）。

**2026 版本基线：3.2.20**——主流组合 **Dubbo 3 + Spring Boot 3 + JDK 17/21 + Nacos**。**三件事要知道**：其一，**Dubbo 3 兼容 Dubbo 2 存量接口**（升级平滑，2.x 协议仍可发布——**新协议 Triple 是默认，旧协议用于存量互通**）；其二，**注册模型从"接口级"升级到"应用级"**（3.x 元数据中心：接口信息与应用信息分离——**大规模集群的注册压力大减**，10 万接口级 vs 应用级的差别）；其三，**云原生方向**——K8s 部署支持、**Proxyless Mesh**（不注入 sidecar，SDK 直连）——"**Dubbo 3 是'旧协议兼容 + 新标准拥抱'的过渡性版本，方向是标准与云原生**"。

## 3. Triple 协议：HTTP/2 + gRPC 兼容

**Triple 是 Dubbo 3 的默认协议，三个关键词：HTTP/2、gRPC 兼容、流式**：

**基于 HTTP/2**——多路复用（一条连接并发多请求）、头部压缩、TLS 原生支持——"**Dubbo2 的自定义 TCP 协议性能虽好，但标准性差；Triple 把性能与标准统一**"；**与 gRPC 协议完全兼容**——**Triple 客户端可以调 gRPC 服务端、gRPC 客户端可以调 Triple 服务端**（协议层互通）——"**Dubbo 与 gRPC 的战争在协议层结束了：Triple 就是 gRPC 的 Dubbo 化包装**"；**四种通信模型**——unary（一元，最常用）、客户端流式、服务端流式、**双向流式**——聊天/流式响应的协议基础；**额外能力**——**Java 接口直接用**（不必强制 IDL/protobuf，与原生 gRPC 的差别）、curl/浏览器可访问（HTTP/1 也能跑）、TLS/背压/限流内置。

**Triple 的战略意义**：**"Dubbo 的服务治理能力 + gRPC 的协议标准"合体**——开发者用 gRPC 协议通信、白拿 Dubbo 治理——"**协议层的墙拆了，剩下的竞争在治理与生态**"。

## 4. gRPC：跨语言标准

**gRPC（Google，2015）是跨语言 RPC 的事实标准**：**HTTP/2 + protobuf（IDL 先行）**——服务定义写在 `.proto` 文件，**protoc 生成各语言客户端/服务端代码**（Java/Go/Python/…），**接口契约跨语言共享**——"**proto 是契约，代码是生成物**"。**特点**：**强类型契约**（proto3 的字段约束）、**四种流式模型**（同 Triple）、**HTTP/2 生态**（TLS/负载均衡原生）、**多语言**（Java/Go 是主力，Rust 等跟进）。**代价**：**IDL 强制**（要学 proto 语法、改契约要重新生成代码——对比 Dubbo 的"Java 接口即契约"）、Java 生态的治理能力要自己搭（gRPC 只解决通信，服务发现/治理要配 grpc-lb 或框架）。**2026 定位**：**多语言系统的互调标准**（Go 服务 ↔ Java 服务）、**云原生栈的默认 RPC**（K8s + gRPC 组合，01 篇栈三）——"**单语言 Java 内网 Dubbo 够用，多语言/云原生 gRPC 更标准**"。

## 5. Dubbo vs gRPC vs OpenFeign

| 维度 | Dubbo 3 | gRPC | OpenFeign（Spring Cloud） |
|------|---------|------|--------------------------|
| 契约 | Java 接口 | proto IDL | Java 接口（HTTP 语义） |
| 协议 | Triple（HTTP/2） | HTTP/2 | HTTP/1.1（REST） |
| 序列化 | 多选（protobuf/Hessian2/JSON） | protobuf | JSON |
| 治理 | ⭐ 全家桶内置 | 需自己配 | Spring Cloud 全家桶 |
| 跨语言 | Java 为主（Go/Rust 跟进） | ⭐ 多语言标准 | 弱（HTTP 直调） |
| 适用 | Java 内部高性能 | 多语言/云原生 | Spring 生态标准 |

**选型主线**：**Java 单体生态内、性能敏感 → Dubbo；多语言互调/云原生 → gRPC；Spring 生态纯 HTTP 标准 → OpenFeign**——"**协议收敛到 HTTP/2 的 2026，选型比的是'治理能力'与'生态匹配'，不再是'快不快'**"（OpenFeign 详见 Spring Cloud 专精体系）。

## 6. 服务治理能力

**Dubbo 的治理能力是它的护城河**，五件核心：**负载均衡**（随机/轮询/一致性哈希/最短响应——默认随机）；**容错**（failover 重试/failfast/failsafe/failback——**默认 failover，重试次数默认 2，非幂等接口必须关重试**）；**超时**（**优先级：方法级 > 接口级 > 消费方全局 > 提供方全局**——最小粒度生效）；**路由与灰度**（条件路由/标签路由——灰度发布的 RPC 侧实现）；**降级与熔断**（mock 降级、与 Sentinel 集成限流）。**治理的运维面**：**Dubbo Admin 控制台**（服务列表/调用链/动态配置）——"**RPC 框架的终局不是'能调通'，是'调不通时能查、流量异常时能治'**"。

## 7. 生产要点

**Dubbo/gRPC 生产六要点**：其一，**非幂等接口禁重试**（failover 重试会重复扣款——**写接口 failfast 或重试幂等化**）；其二，**超时分级设置**（方法级覆盖全局——"**慢接口单独给超时，别让全局 3s 一刀切**"）；其三，**别在 RPC 线程里做阻塞业务**（gRPC 的 IO 线程被业务阻塞 = 全体请求排队——**业务逻辑异步化**）；其四，**避免 ThreadLocal 在共享线程池泄漏**（线程复用导致上下文串号——**用后清理或参数传递**）；其五，**注册中心本地缓存**（注册中心挂了服务照常调用——**启动时缓存地址列表，ZK 断连降级可用**）；其六，**优雅上下线**（先摘流量再关服务——**发布时服务提供方先标记下线再停机**，与 08 篇发布纪律呼应）。

## 8. 五个常见坑

- **坑一**：把 RPC 当本地调用——**网络抖动/超时/序列化失败是常态；try-catch + 超时 + 重试策略是标配**；
- **坑二**：写接口开 failover 重试——**非幂等操作重复执行；写接口关重试或做幂等**（05 篇）；
- **坑三**：超时全局一刀切——**慢接口被误杀重试风暴；方法级分级**；
- **坑四**：gRPC 用 JSON 序列化——**gRPC 强类型契约的卖点就是 protobuf；别退化成 JSON RPC**；
- **坑五**：注册中心挂了大惊小怪——**客户端本地缓存兜底；重点是"缓存了没有"，不是"中心挂了没有"**（03 篇）。
