## 1. 注册中心与协调的本质

**注册中心解决"服务地址会变"的问题**：服务启动时**注册**（把自己的地址写进目录），消费者调用前**发现**（从目录查到可用地址列表），服务下线时**注销**——**"注册中心是分布式系统的通讯录"**。**协调（coordination）是注册中心的延伸能力**：分布式锁（04 篇）、选举（主节点）、配置发布、任务分片——**本质都是"多个进程对同一份数据的可靠读写与监听"**。**关键认知**：注册中心是**分布式系统的单点信任根**——**它的可用性决定整个系统的可用性**（挂了还能靠客户端本地缓存兜底，02 篇要点五），所以**部署至少 3 节点集群**（多数派容错）——"**注册中心不是'一个服务'，是'一个可信的分布式状态源'**"。

## 2. ZooKeeper：ZAB 的工程实现

**ZooKeeper（ZK，2008 雅虎开源）是 ZAB 协议（原子广播）的工程实现**——ZAB 保证**强一致性**（写操作全局有序，读任何节点结果一致——线性一致性）——"**ZK 是分布式系统理论 02 篇 ZAB 的活教材**"。**数据模型**：**树形 znode**（类似文件系统）——**持久节点/临时节点（会话结束自动删除）/顺序节点（自动编号）**——"**临时 + 顺序**"组合是分布式锁/选举的基石（04 篇）。**监听机制**：**Watcher**——节点变化通知客户端（注册一次、触发一次——**重新注册是常见坑**）。

**2026 定位**：**Java 服务注册的"前任主流"**——Nacos 兴起后 ZK 退场到专业场景：**强公平分布式锁（金融级）**、**任务调度分片协调（ElasticJob 的注册表，07 篇）**、**元数据管理（Kafka 的 broker 注册，跨体系）**——"**ZK 不是过时，是'什么都做'退到'强一致协调'**"。**运维成本**：Java 进程、内存模型（znode 全量在内存，**数据量大就 OOM**）、会话心跳维护——**"ZK 的问题是运维重，不是能力弱"**。

## 3. etcd：Raft 的工程实现

**etcd（CoreOS，2013）是 Raft 共识协议的工程实现**——同样强一致（线性一致性），**K8s 的配套存储**（K8s 的所有状态存在 etcd）——"**etcd 是 Raft 的活教材，也是云原生的事实状态库**"。**与 ZK 的三个差异**：**API 是 gRPC + KV**（扁平 key-value，不是树形 znode——用前缀模拟目录）；**事务能力**（`Txn` 比较-执行，锁的原子性基础）；**性能更好**（Raft 与 ZAB 同为多数派协议，etcd 的批量与流式优化吞吐更高——**介于 Redis 与 ZK 之间**）。**分布式锁**：临时有序键 + TTL（租约）——**与 ZK 锁同构但用租约替代会话**。

**2026 定位**：**K8s 生态的强一致选择**——服务注册（云原生栈）、配置存储、**分布式锁（K8s 环境顺理成章）**。**Java 侧的短板**：**Java 客户端生态不成熟**（官方 etcd4j/Jetcd 维护一般、与 Spring 集成弱）——"**etcd 在 K8s 里强，在 Java 业务代码里弱——Java 团队选它要有理由**"。

## 4. Nacos：2026 Java 注册主流

**Nacos（2018 阿里巴巴开源）是 2026 年 Java 服务注册的事实主流**（专精体系深潜：`../../Spring组件汇总/Spring Cloud 微服务全家桶（分布式）/Spring Cloud Alibaba（阿里实现，属于 Spring Cloud 生态实现）/Nacos：注册中心 + 配置中心/`）。**三个关键设计**：**CP/AP 可切换**（临时实例走 AP——注册中心场景可用性优先；持久实例走 CP）——"**注册中心要 AP（挂了还能用旧数据），协调要 CP（数据必须一致）——Nacos 让你按需切**"；**注册与配置一体**（一个组件干两件事，少一个运维件）；**轻量**（Java 实现、部署简单、中文文档）。**2026 趋势**：**Nacos 3.x**（性能与稳定性持续迭代），**Dubbo 栈也默认 Nacos 注册**（02 篇）——"**Java 系注册中心的一统者**"。

## 5. 三选一对比

| 维度 | ZooKeeper | etcd | Nacos |
|------|-----------|------|-------|
| 一致性 | 强（ZAB） | 强（Raft） | 可切（AP/CP） |
| 数据模型 | 树形 znode | KV（前缀目录） | KV/服务模型 |
| 生态绑定 | Java 经典 | K8s 原生 | Spring/Dubbo 生态 |
| Java 客户端 | Curator 成熟 | 生态弱 | 官方完善 |
| 运维成本 | 重（内存模型） | 中 | 轻 |
| 2026 场景 | 强一致协调/公平锁 | K8s 配套 | **Java 注册主流** |

**选型主线**：**Java 服务注册 → Nacos（默认）；强一致协调/金融级公平锁 → ZK；K8s 生态/云原生 → etcd**——"**注册中心选 Nacos 省心，协调场景选 ZK 老练，云原生选 etcd 顺势**"。

## 6. 数据模型与 Java 客户端

**ZN KNACOS 三家的数据操作都围绕"节点 + 监听"**：ZK 的 znode + Watcher、etcd 的 key + Watch、Nacos 的服务列表 + 订阅——**"注册中心的本质 API 只有四个：写（注册）、读（发现）、删（注销）、监听（变化通知）"**。**Java 客户端**：**ZK 用 Curator**（Apache 封装：连接管理/重试/锁/选举——**别用原生 ZK client 裸写**，Curator 的 ConnectionStateListener 处理会话过期是生产必需品）；**etcd 用 Jetcd**（官方 Java 客户端，功能全但社区活跃度一般）；**Nacos 用官方 client**（或 Spring Cloud Alibaba 自动集成）。**会话过期处理**：**ZK 会话过期 = 临时节点全删 = 服务注册丢失**——客户端要监听 Expired 事件并重建——"**会话过期是注册中心客户端的第一大坑，Curator 帮你处理，原生写你踩坑**"。

## 7. 生产要点

**注册中心生产六要点**：其一，**集群 ≥ 3 节点**（多数派容错——2 节点挂 1 就废，4 节点与 3 节点容错一样，**奇数节点**）；其二，**客户端本地缓存**（注册中心故障时用缓存地址继续调用——**启动时拉全量、运行时增量监听**，02 篇要点五的落地）；其三，**心跳与过期配置**（ZK 会话超时 sessionTimeout 设 10-30s；Nacos 临时实例心跳 5s——**太短网络抖动误杀，太长故障感知慢**）；其四，**数据量治理**（ZK 全量内存——**别往里塞大配置**，大配置放配置中心/对象存储）；其五，**监控**（节点数、会话数、读写延迟、选举事件——**选举频繁 = 网络抖动信号**）；其六，**优雅下线**（服务停机前主动注销，别等会话超时被动删——**发布纪律**，08 篇呼应）。

## 8. 五个常见坑

- **坑一**：注册中心单节点部署——**它就是单点故障；≥3 节点集群**（第 7 节）；
- **坑二**：Watcher 注册一次就完——**ZK 监听是 one-shot，触发后要重新注册；用 Curator 的持久监听**；
- **坑三**：往 ZK 塞大配置/大数据——**全量内存模型，数据量大了 OOM；配置中心分责**；
- **坑四**：会话超时设太短——**网络抖动集体注销再注册（惊群）；10-30s 起步**；
- **坑五**：注册中心挂了业务全挂——**没有本地缓存兜底；启动全量拉取 + 增量监听是标配**（第 7 节）。
