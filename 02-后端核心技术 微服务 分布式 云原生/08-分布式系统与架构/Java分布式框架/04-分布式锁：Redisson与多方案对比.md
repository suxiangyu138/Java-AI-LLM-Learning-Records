## 1. 为什么需要分布式锁

**多台机器抢同一资源时，synchronized/JVM 锁都失效**（每台机器一个 JVM）——**分布式锁是"跨进程的互斥原语"**。**典型场景**：**库存扣减**（并发超卖）、**幂等控制**（防重复下单/重复支付）、**任务调度互斥**（多实例定时任务只让一台跑，07 篇）、**缓存重建**（热点 key 并发回源）。**分布式锁的三个硬性要求**：**互斥**（同一时刻只有一个持有者）、**防死锁**（持有者挂了锁要能释放——TTL/会话过期）、**防误删**（只能释放自己持有的锁——**value 标识 + Lua 原子判断**）。**三个要求之外还有工程诉求**：**可重入**（同一线程重复获取）、**续期**（任务超长锁别自动过期）、**公平**（排队 vs 抢——业务决定）。**"锁的价值不在锁本身，在'持锁期间业务安全'"**——**持锁代码要短、要幂等、要有兜底**。

## 2. Redisson：Redis 锁的工程化

**Redisson 是 Redis 生态的 Java 分布式对象框架**（2026-08 基线 **4.6.1**，2026-06-18 发布；3.x/4.x 双线），**把 Redis 从缓存变成"分布式原语平台"**——锁只是它的能力之一（还有信号量/布隆过滤器/延迟队列/限流器等）。**加锁的姿势**：

```java
RLock lock = redisson.getLock("stock:1001");       // 可重入锁
lock.lock(30, TimeUnit.SECONDS);                    // 手动超时（防死锁）
try {
    // 业务代码：扣库存
} finally {
    lock.unlock();                                  // 必须释放
}
// 或自动续期姿势：lock.lock()（不传参）→ 看门狗每 10s 续期到 30s
```

**底层原理**：**Redis Lua 脚本原子执行**（SET NX EX + 线程标识 + 计数，配合 Lua 释放时校验 value）——**Redis 的 Lua 原子性是分布式锁的基石**（Redis Lua 脚本体系交叉：`../../02-非关系型数据库/Redis/Lua脚本/` 04 篇）——"**setnx + expire 两步是玩具，Lua 一步是工程**"。

## 3. 锁家族全景

**Redisson 的锁家族覆盖了互斥的全部形态**：

| 锁 | 语义 | 场景 |
|------|------|------|
| Lock（可重入） | 同线程可重入 + 看门狗续期 | ⭐ 默认选择 |
| FairLock（公平锁） | FIFO 排队，先到先得 | 抢购/资源分配要公平 |
| ReadWriteLock | 读读共享/写写互斥 | 读多写少的缓存场景 |
| MultiLock | 多把锁一起加（都成功才算） | 多资源原子操作 |
| RedLock | 多节点独立锁（红锁） | 跨 Redis 主节点的强一致尝试 |
| Semaphore | 信号量（N 个许可） | 限流/资源池 |
| CountDownLatch | 倒计数（N 个完成后放行） | 多任务汇聚 |

**选型主线**：**99% 场景 Lock 就够了**（可重入 + 续期 + 防死锁三件套内置）；**要排队公平用 FairLock**（注意公平锁性能开销）；**读多写少用 ReadWriteLock**；**RedLock 争议大（第 7 节），默认不用**。

## 4. 看门狗与锁语义

**看门狗（watchdog）是 Redisson 最著名的机制**：**lock.lock() 不传超时时，后台线程每 10 秒检查一次，若锁还在且业务没结束，自动把锁的 TTL 续到 30 秒**——"**任务没跑完，锁不自动过期**"——解决"任务执行超过锁 TTL 导致锁提前释放、别人抢走锁"的经典问题。**看门狗的三个认知**：其一，**只在"不传超时"时生效**（传了超时 = 手动模式，超时到即释放——**默认 30s 续期周期，锁的租期与续期循环匹配**）；其二，**看门狗是"续期"不是"不死"**——**业务线程死掉（无异常但卡死），锁最终还是会过期释放**（持锁进程崩溃时锁最多晚 30s 释放）；其三，**释放条件**——unlock 必须由持有线程调（Redisson 内部校验线程标识——**A 线程不能解 B 线程的锁**，防误删的工程实现）。**锁语义口诀**："**可重入防自己、看门狗防提前过期、线程标识防误删、Lua 保证原子**"。

## 5. ZooKeeper 锁：强公平

**ZK 锁的原理**（ZAB 强一致背书，03 篇）：**客户端创建"临时顺序节点"**（`/locks/stock-1001-0000000123`）→ **检查自己是不是最小的节点** → 是则拿到锁 → 不是则**监听前一个节点**（Watcher）→ 前一个删除（释放）时唤醒自己再检查——"**排队机制：谁序号小谁先拿，天然 FIFO 公平**"。**三个特点**：**强公平**（无惊群、无饥饿——金融级场景看重）；**自动防死锁**（会话过期 → 临时节点自动删除）；**数百毫秒延迟**（ZAB 写 + 会话心跳——**比 Redis 的毫秒级慢一个量级**）。

**Java 姿势**：**别写原生 ZK 锁，用 Curator 的 InterProcessMutex**（可重入、自动重试、会话处理内置）——"**ZK 锁本身简单，难的是会话管理——Curator 全包了**"。**2026 定位**：**金融级强公平场景**（对账/审批流/资源分配要"绝对公平"）——"**Redis 锁快，ZK 锁稳，公平性要求压过性能要求时选 ZK**"。

## 6. etcd 锁与数据库锁

**etcd 锁**：**临时有序键 + TTL（租约）**——与 ZK 锁同构（Raft 强一致背书），**租约替代会话**做自动释放；**K8s 环境顺势**（etcd 已存在），Java 客户端生态弱（03 篇短板）——"**K8s 团队有 etcd 就用 etcd，没有不必为锁引入**"。

**数据库锁**（悲观锁 SELECT FOR UPDATE / 乐观锁版本号）：**最朴素但问题最多**——**悲观锁**：行锁占用 + 长事务拖垮连接池（**持锁期间别做远程调用**）；**乐观锁**：版本号 CAS，冲突就重试——**适用低并发且"锁就在库里"的场景**（扣库存用 `UPDATE ... SET stock=stock-1 WHERE id=? AND stock>0` 一条 SQL 原子完成，**根本不需要分布式锁**——"**能用数据库原子操作解决的，别引入锁框架**"）。

## 7. 红锁争议

**RedLock（红锁）**：**在 N（通常 5）个独立 Redis 主节点上都加锁，多数（N/2+1）成功才算拿到**——设计目标：**规避"单 Redis 主从切换丢锁"**（主节点挂了没同步，从节点顶上时锁没了——两个客户端同时持锁）。**争议**（Martin Kleppmann vs Redisson 作者 Salvatore 的著名论战）：**红锁在"非同步时钟 + 网络分区"下依然可能双持锁**——**且 5 节点部署成本高、故障场景复杂**。**2026 的共识**：**绝大多数场景不需要红锁**——"**锁的可靠性是'业务容忍度'问题：扣库存类场景 Redis 锁够用（丢了最多超卖可对账），绝对安全场景（金融转账）直接上 ZK 强一致锁，红锁是中间的尴尬方案**"。

## 8. 多方案选型

| 方案 | 一致性 | 性能 | 公平 | Java 生态 | 适用 |
|------|:---:|:---:|:---:|:---:|------|
| Redisson | 最终（Redis） | ⭐ 毫秒级 | 可配公平 | ⭐ 成熟 | ⭐ 高并发默认 |
| ZK（Curator） | 强（ZAB） | 数百毫秒 | ⭐ FIFO | 成熟 | 金融级强公平 |
| etcd | 强（Raft） | 中 | FIFO | 弱 | K8s 环境顺势 |
| 数据库 | 事务保证 | 慢 | — | — | 低并发/库内解决 |

**选型主线**：**"高并发默认 Redisson；绝对公平/绝对安全选 ZK；K8s 有 etcd 就 etcd；能数据库原子操作解决的不上锁"**——**"锁是最后手段：先看能否用原子操作/幂等设计绕开锁，绕不开再选锁"**（05 篇幂等与 02 篇 Redis Lua 交叉）。

## 9. 五个常见坑

- **坑一**：setnx + expire 两步原生实现——**不是原子，进程崩了锁永不释放；用 Redisson 或 Lua 一步**；
- **坑二**：lock 不传超时也不用看门狗（裸 tryLock(1s)）——**任务 2s 没跑完锁就没了；看门狗或合理超时**；
- **坑三**：finally 里不 unlock——**锁泄漏；try-finally 是铁律**（Java 异常体系交叉）；
- **坑四**：持锁期间做慢操作（远程调用/长事务）——**锁的持有时间 = 系统的串行时间；持锁代码尽量短**；
- **坑五**：所有场景上 RedLock——**部署成本高 + 争议大；默认单 Redis 锁，绝对安全上 ZK**（第 7 节）。
