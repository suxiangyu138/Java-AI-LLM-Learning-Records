## 1. 分布式协调概述

```
分布式协调 = 多个节点就"状态"达成共识

四大典型场景：
┌─────────────┬──────────────────┬─────────────────────┐
│  分布式锁    │  配置中心         │  服务发现            │  Leader 选举    │
├─────────────┼──────────────────┼─────────────────────┼─────────────────┤
│ 同一时刻     │ 配置变更实时      │ 消费者发现           │ 集群中选出一个   │
│ 只有一个节点  │ 同步到所有节点    │ 可用服务实例         │ Leader 处理请求  │
│ 执行关键操作  │                  │                     │                 │
└─────────────┴──────────────────┴─────────────────────┴─────────────────┘
```

## 2. ZooKeeper 深度

### 2.1 核心特性

| 特性 | 说明 |
|------|------|
| **数据模型** | 类文件系统的树形节点（ZNode） |
| **一致性** | CP 系统（ZAB 协议），顺序一致性 |
| **会话机制** | 客户端与 ZK 建立 Session，心跳保活 |
| **Watch 机制** | 客户端可监听 ZNode 变化，一次触发 |
| **临时节点** | 会话断开自动删除（⭐ 分布式锁的基础） |

### 2.2 数据模型

```
/ (root)
├── /config
│   ├── /config/db-url      = "jdbc:mysql://..."
│   └── /config/redis-host  = "10.0.1.10:6379"
├── /locks
│   └── /locks/order-001    (临时顺序节点)
├── /services
│   └── /services/user-service
│       ├── /services/user-service/192.168.1.10:8080  (临时节点)
│       └── /services/user-service/192.168.1.11:8080
└── /election
    └── /election/leader     (临时节点)
```

### 2.3 四种 ZNode

| 类型 | 特点 | 典型用途 |
|------|------|----------|
| **持久节点** | 显式删除才消失 | 配置数据 |
| **临时节点** | 会话断开自动删除 | 服务注册、分布式锁 |
| **持久顺序节点** | 持久 + 名称带递增序号 | — |
| **临时顺序节点** | 临时 + 名称带递增序号 | ⭐ 分布式锁（羊群效应优化） |

### 2.4 Watch 机制

```java
// 监听 /config/db-url 的变化
zk.getData("/config/db-url", event -> {
    if (event.getType() == NodeDataChanged) {
        String newValue = new String(zk.getData("/config/db-url", true, null));
        refreshDataSource(newValue);  // 热更新数据源
    }
}, null);
```

> ⚠️ **Watch 是一次性的**：触发后需要重新注册。Curator 框架封装了循环注册。

## 3. etcd 深度

### 3.1 核心特性

| 特性 | 说明 |
|------|------|
| **数据模型** | 扁平 KV 存储，支持前缀查询 |
| **一致性** | CP 系统（Raft），强一致性 |
| **Lease 机制** | 租约（TTL），类似 ZK Session |
| **Watch 机制** | 监听 key 或前缀，支持历史版本 |
| **MVCC** | 多版本并发控制，历史版本可查 |
| **事务** | CAS 操作（Compare-And-Swap） |

### 3.2 etcd vs ZooKeeper

| 维度 | ZooKeeper | etcd |
|------|-----------|------|
| 共识协议 | ZAB | Raft |
| 数据模型 | 树形 ZNode | 扁平 KV + 前缀 |
| Watch | 一次性 | 流式（持续监听） |
| 版本 | — | MVCC 多版本 |
| 社区 | Apache | CNCF（K8s 后端存储） |
| Go/云原生 | 较重（Java） | ⭐ 原生（Go） |

## 4. 分布式锁实现

### 4.1 基于 ZooKeeper

```java
// Curator 框架 — 分布式锁（推荐）
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order");

if (lock.acquire(10, TimeUnit.SECONDS)) {
    try {
        // 执行业务逻辑
    } finally {
        lock.release();
    }
}
```

**ZK 分布式锁原理**：
```
1. 所有线程在 /locks 下创建临时顺序节点
2. 序号最小的节点获得锁
3. 其他节点 Watch 前驱节点（非所有节点，避免羊群效应）
4. 前驱释放 → Watch 触发 → 自己成为最小节点 → 获得锁
5. 会话断开 → 临时节点自动删除 → 锁自动释放
```

### 4.2 基于 Redis

```bash
# 单机 Redis 分布式锁
SET lock_key unique_value NX EX 30

# 释放锁（Lua 脚本保证原子性）
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

```java
// Redisson — 生产级 Redis 分布式锁
RLock lock = redisson.getLock("order:1001");
lock.lock(30, TimeUnit.SECONDS);
try {
    // 业务逻辑
} finally {
    lock.unlock();
}
```

### 4.3 ZK vs Redis 分布式锁

| 维度 | ZooKeeper | Redis |
|------|-----------|-------|
| 一致性 | ✅ CP，强一致 | ⚠️ AP，主从延迟丢锁 |
| 性能 | ⭐⭐ 一般 | ⭐⭐⭐ 高 |
| 自动释放 | ✅ Session 断开自动删 | 需设置 TTL |
| 公平锁 | ✅ 顺序节点天然支持 | 需额外实现 |
| 适用场景 | 强一致性场景（金融） | 高性能场景（秒杀） |

> ⚠️ **Redlock 争议**：Redis 作者提出的多节点分布式锁方案，但 Martin Kleppmann（DDIA 作者）指出其在时钟跳跃场景下有安全性问题。

## 5. 配置中心

### 5.1 核心能力

| 能力 | 说明 |
|------|------|
| 动态刷新 | 配置变更后应用无需重启 |
| 版本管理 | 配置变更历史可追溯回滚 |
| 灰度发布 | 部分实例先更新配置 |
| 权限控制 | 不同应用/环境权限隔离 |

### 5.2 方案对比

| 方案 | 存储 | 实时推送 | 特点 |
|------|------|:---:|------|
| **Nacos** | MySQL/内置 | ✅ 长轮询 | ⭐ 阿里，配置+注册二合一 |
| **Apollo** | MySQL | ✅ HTTP 长轮询 | 携程，功能最完善的配置中心 |
| **Spring Cloud Config** | Git/SVN | ❌ 需 Bus | 与 Spring 深度集成 |
| **Consul** | 内置 KV | ✅ | 服务发现+配置二合一 |

## 6. 服务发现与注册中心

### 6.1 注册中心对比

| 方案 | CAP | 健康检查 | 实时推送 | 生态 |
|------|:---:|:---:|:---:|------|
| **Nacos** | AP/CP 可切换 | ✅ TCP/HTTP/MySQL | ✅ | ⭐ 阿里 Spring Cloud |
| **Eureka** | AP | 心跳 + 自我保护 | ❌ 客户端轮询 | Netflix，趋于停维 |
| **Consul** | CP | ✅ 多级健康检查 | ✅ | HashiCorp 生态 |
| **ZooKeeper** | CP | Session 心跳 | ✅ Watch | 经典但较重 |

### 6.2 自我保护机制

```
Eureka 自我保护模式：
  → 15 分钟内心跳失败率 > 85% → 进入自我保护
  → 不再剔除任何实例
  → 宁可保留坏实例，也不能误删好实例

意义：防止网络抖动导致大规模误剔除，保证可用性
```

## 7. 选型对比

| 场景 | 推荐 | 理由 |
|------|:---:|------|
| K8s 环境配置/协调 | **etcd** | K8s 原生后端存储 |
| Spring Cloud 微服务 | **Nacos** | 注册+配置一体，阿里生态 |
| 分布式锁（强一致性） | **ZooKeeper/etcd** | CP 系统 |
| 分布式锁（高性能） | **Redis (Redisson)** | 性能最优 |
| 老牌企业中间件 | **Apollo + ZK** | 成熟稳定 |

> 🎯 **趋势**：K8s 环境用 etcd，Spring Cloud 用 Nacos，小项目直接 Redis，没有绝对的最好只有最适合。
