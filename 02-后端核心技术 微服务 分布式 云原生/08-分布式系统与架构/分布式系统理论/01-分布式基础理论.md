## 1. 分布式系统概述

### 1.1 定义

分布式系统是由多个**独立自治节点**通过网络互联、协同完成统一任务的系统，用户无需感知内部架构，仅看到统一的服务入口。其与计算机网络的核心区别在于：分布式系统具备全局资源管理能力和透明性。

### 1.2 核心目标

解决单机系统的四大局限：

| 局限 | 说明 | 分布式解决方案 |
|------|------|----------------|
| **性能瓶颈** | 单机 CPU、内存、网络处理能力有限 | 多节点并行处理，QPS 线性扩展 |
| **存储上限** | 单机硬盘容量无法承载海量数据 | 多节点分散存储，实现 PB/EB 级存储 |
| **高可用性** | 单机故障导致服务完全不可用 | 多节点冗余备份，部分故障仍可运行 |
| **地理分布** | 全球用户访问延迟高 | 不同地区部署节点，降低访问延迟（CDN） |

### 1.3 核心特征

| 特征 | 说明 |
|------|------|
| **多节点协同** | 节点通过 RPC、HTTP、消息队列实现协作 |
| **资源共享** | 节点共享存储、计算资源，对外提供统一接口 |
| **无全局时钟** | 各节点有自己的本地时钟，需逻辑时钟解决事件顺序 |
| **故障独立性** | 节点可独立宕机，系统需具备容错能力 |

### 1.4 核心挑战

| 挑战 | 具体问题 |
|------|----------|
| **网络不可靠** | 延迟、丢包、分区（脑裂）是常态；跨机房延迟可达 100ms+ |
| **数据一致性** | 多节点存储数据时，副本同步存在延迟 |
| **节点故障** | 宕机、重启或"脑死亡"（进程存活但无法通信） |
| **并发冲突** | 多个节点同时操作同一资源 |
| **负载均衡** | 避免热点节点过载，应对动态扩容/缩容 |

## 2. CAP 定理

> 2000 年由 Eric Brewer 提出，2002 年被证明。一个分布式系统**不可能同时满足**一致性、可用性和分区容错性。

### 2.1 三个维度

| 维度 | 含义 | 通俗解释 |
|------|------|---------|
| **C（Consistency）一致性** | 所有节点同一时刻看到的数据完全相同 | 写完之后，任意节点读到的都是最新数据 |
| **A（Availability）可用性** | 每个非故障节点都能在合理时间内返回合理响应 | 服务一直可用，不会返回错误或超时 |
| **P（Partition Tolerance）分区容错** | 网络分区发生时，系统仍能正常运行 | 部分节点失联，系统不崩溃 |

### 2.2 为什么 CAP 不能三者兼得？

```
场景：两个节点 A、B，网络断开

  如果保证 C（一致性）：
    写 A 成功后，B 必须同步 → 网络断开了 → B 同步失败
    → 只能拒绝写入 → 牺牲了 A（可用性）

  如果保证 A（可用性）：
    写 A 成功即返回，B 暂时不同步 → A 和 B 数据不一致
    → 牺牲了 C（一致性）

  P（分区容错）是分布式系统的必然要求：
    → 网络分区不可避免（交换机故障、网线断、网络抖动）
    → 必须在 C 和 A 之间做取舍
```

### 2.3 CAP 的工程实践

| 选择 | 代表系统 | 做法 | 适用场景 |
|------|---------|------|---------|
| **CP（保一致性）** | ZooKeeper、etcd、Consul | 分区时拒绝写入，牺牲可用性 | 配置中心、服务发现、分布式锁 |
| **AP（保可用性）** | Eureka、Cassandra、DynamoDB | 分区时允许写入，最终一致 | 电商商品展示、社交媒体 feed |
| **CA** | 传统关系型数据库（单机） | 不分区的单机系统 | **不是真正的分布式系统** |

### 2.4 常见误解

| 误解 | 正解 |
|------|------|
| "CAP 是三选二" | 不准确。P 是必须保证的（网络分区客观存在），实际是 CP vs AP |
| "放弃了 C 就没有任何一致性" | 放弃的是强一致性，可以通过最终一致性弥补 |
| "CA 系统也是分布式" | CA 系统没有考虑分区容错，本质是单机系统 |

> 💡 **实战口诀**：钱相关的 CP，体验相关的 AP。

## 3. BASE 理论

> BASE 是 CAP 定理中 AP 方案的延伸，是互联网大规模分布式系统的工程实践总结。

### 3.1 BASE 含义

| 字母 | 全称 | 含义 |
|------|------|------|
| **BA** | Basically Available | 基本可用：允许损失部分可用性（响应时间变长、功能降级），但系统整体可用 |
| **S** | Soft State | 软状态：允许系统中的数据存在中间状态，该状态不影响系统整体可用性 |
| **E** | Eventually Consistent | 最终一致性：不要求数据实时一致，但保证经过一段时间后最终达到一致 |

### 3.2 BASE vs ACID

| 对比维度 | ACID（数据库事务） | BASE（分布式系统） |
|---------|-------------------|-------------------|
| 核心思想 | 强一致性、强约束 | 弱一致性、高可用 |
| 一致性 | 强一致性（写后立即可读） | 最终一致性（可能短暂不一致） |
| 可用性 | 可能牺牲（锁等待） | 高可用优先 |
| 隔离性 | 严格隔离（串行化） | 弱隔离（允许并发冲突） |
| 适用场景 | 金融交易、库存扣减 | 社交网络、内容分发、搜索引擎 |
| 典型实现 | MySQL InnoDB 事务 | DNS、CDN、NoSQL |

### 3.3 最终一致性的五种变体

| 变体 | 含义 | 示例 |
|------|------|------|
| **因果一致性** | 有因果关系的操作按顺序被看到 | 先发帖后评论，所有人看到评论前先看到帖子 |
| **读己之写** | 用户总能读到自己的最新写入 | 发微博后自己刷新立刻看到 |
| **会话一致性** | 同一会话内读到最新值 | 同一浏览器窗口内操作一致 |
| **单调读** | 不会读到比之前更旧的数据 | 刷新不会看到数据"回退" |
| **单调写** | 同一进程的写操作串行化 | 写操作按顺序执行 |

### 3.4 一致性分级总览

| 级别 | 说明 |
|------|------|
| **强一致性** | 写完成后，所有读请求立刻看到最新数据 |
| **弱一致性** | 短暂数据不一致 |
| **最终一致性** | 短暂延迟后数据自动一致 |

## 4. CAP 到 BASE 的演进

```
CAP 定理（理论）
   │
   ├── CP 路线：ZooKeeper、etcd（配置/协调场景）
   │
   └── AP 路线 →
             │
             BASE 理论（工程实践）
                 │
                 ├── 最终一致性：DNS、CDN、主从复制
                 ├── 柔性事务：TCC、Saga、本地消息表
                 └── 补偿机制：对账、重试、回滚
```

## 5. 主流系统的 CAP 分类

| 系统 | 类型 | CAP 选择 | 说明 |
|------|------|---------|------|
| ZooKeeper | 协调服务 | **CP** | 集群半数以上存活才可服务，选主期间不可用 |
| etcd | 协调服务 | **CP** | Raft 协议，强一致性，选主期间不可写入 |
| Consul | 服务发现 | **CP** | 默认 CP 模式，也有 AP 选项 |
| Eureka | 服务发现 | **AP** | 优先可用，节点挂了不剔除，客户端有本地缓存 |
| Nacos | 配置+发现 | **CP+AP** | 配置中心 CP 模式，服务发现可选 AP 模式 |
| Redis Cluster | 缓存 | **AP** | 主从异步复制，网络分区可能丢数据 |
| MySQL 主从 | 数据库 | **AP** | 异步/半同步复制，从库可能读到旧数据 |
| TiDB | NewSQL | **CP**（默认） | Raft 多副本，强一致性 |
| Cassandra | NoSQL | **AP** | 最终一致性，可调一致级别 |
| MongoDB | NoSQL | **CP**（默认） | 副本集选举，主挂了只读不可写 |

## 6. FLP 不可能定理

> 在异步通信的分布式系统中，即使只有一个节点可能故障，也不存在一个确定性算法能在有限时间内达成共识。

**工程应对**：用超时机制打破纯异步假设，实际系统中可以实现共识（只是可能超时）。

## 📖 核心要点速记

1. **分布式系统本质**：多节点协同，突破单机局限
2. **CAP**：P 必须保，C 和 A 二选一 -- 不是三选二
3. **CP**：强一致，选主期间不可用（ZooKeeper、etcd）
4. **AP**：高可用，接受最终一致（Eureka、DNS）
5. **BASE**：基本可用 + 软状态 + 最终一致
6. **FLP**：异步网络下不可能有限时间达成共识 -- 用超时解决
