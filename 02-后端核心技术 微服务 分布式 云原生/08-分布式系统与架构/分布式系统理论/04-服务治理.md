## 1. 服务发现与注册

### 1.1 为什么需要服务发现？

微服务实例是动态的 —— 扩容缩容、重启、故障迁移，IP 和端口不断变化。服务发现让调用方无需硬编码地址，动态获取可用实例。

### 1.2 核心模型

```
Provider（服务提供者）
    │ 1. 注册（启动时将 IP:Port 注册到注册中心）
    ▼
Registry（注册中心）
    │ 2. 发现（Consumer 查询 Provider 列表）
    ▼
Consumer（服务消费者）
    │
    └─ 3. 调用（直连 Provider，通常客户端负载均衡）
    
    │ 4. 心跳/健康检查（Provider 定期续约）
    ▼
Registry ← Provider 心跳失败 → 剔除不可用实例
```

### 1.3 主流注册中心对比

| 注册中心 | CAP | 健康检查 | 特点 | 生态 |
|---------|-----|---------|------|------|
| **Nacos** | CP+AP | TCP/HTTP/MySQL 三种 | 注册+配置一体化，阿里开源 | Spring Cloud Alibaba |
| **Eureka** | AP | 心跳（客户端主动上报） | 自我保护机制，Netflix 开源（已停更） | Spring Cloud Netflix |
| **Consul** | CP | Agent 健康检查 | 健康检查强大，支持多数据中心 | Spring Cloud Consul |
| **ZooKeeper** | CP | 临时节点 + Session | 强一致性，选主期间不可用 | Dubbo |
| **etcd** | CP | Lease 续约 | 简单可靠，K8s 的核心存储 | gRPC、K8s |

### 1.4 自我保护机制（Eureka）

> 短时间内心跳丢失比例超过阈值（默认 85%）→ 进入自我保护模式，不剔除任何实例。

目的：防止网络抖动导致大规模误剔除。代价：可能调用到故障节点。

> 💡 **注册中心挂了怎么办？** 客户端有本地缓存（服务列表），可以继续用缓存通信。但新实例无法注册、故障实例无法剔除。

## 2. 负载均衡

### 2.1 常见算法

| 算法 | 原理 | 适用场景 |
|------|------|---------|
| **随机** | 随机选一个节点 | 节点性能均等 |
| **轮询** | 按顺序轮流转 | 节点性能均等、请求处理时间相近 |
| **加权轮询** | 按权重分配 | 节点性能不均衡 |
| **最小连接数** | 选当前活跃连接最少的节点 | 长连接、处理时间差异大 |
| **一致性哈希** | 相同 key 路由到同一个节点 | 缓存亲和性、有状态服务 |
| **最快响应** | 选历史响应时间最短的 | 对延迟敏感 |

### 2.2 客户端 vs 服务端负载均衡

| 对比维度 | 客户端负载均衡 | 服务端负载均衡 |
|---------|--------------|--------------|
| 代表实现 | Ribbon、LoadBalancer（Spring Cloud） | Nginx、F5、LVS |
| 位置 | 调用方进程中 | 独立中间层 |
| 优点 | 无额外网络跳转，延迟低 | 集中管控，跨语言通用 |
| 缺点 | 多语言需各自实现 | 额外一跳，增加延迟 |
| 典型架构 | Spring Cloud + LoadBalancer | Nginx 反向代理 |

## 3. 限流

### 3.1 为什么需要限流？

防止突发流量打垮系统 —— 如秒杀、爬虫、恶意攻击。

### 3.2 常见算法

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **固定窗口** | 每个时间窗口（如 1s）内最多 N 个请求 | 简单 | 边界突发（窗口交界处两倍流量） |
| **滑动窗口** | 细分窗口，统计最近一个完整窗口的请求数 | 平滑 | 内存消耗略大 |
| **漏桶** | 请求先进桶，固定速率流出 | 严格平滑输出 | 无法应对突发流量 |
| **令牌桶** | 固定速率生成令牌，请求需获取令牌 | 允许一定突发 | 实现稍复杂 |
| **滑动日志** | 记录每次请求时间戳，精确到毫秒 | 精确 | 内存消耗大 |

### 3.3 令牌桶详解（最常用）

```
令牌桶容量 = burst
令牌生成速率 = rate（个/秒）

请求 → 需要 1 个令牌
  有令牌 → 取令牌，放行
  无令牌 → 限流拒绝

例：rate=100/s, burst=200
  正常：每秒 100 个请求
  突发：如果桶满了，瞬间可以处理 200 个
```

### 3.4 主流实现

| 方案 | 类型 | 适用场景 |
|------|------|---------|
| **Guava RateLimiter** | 单机令牌桶 | 单服务限流 |
| **Sentinel** | 分布式 + 单机 | 阿里开源，功能最全（限流+熔断+降级） |
| **Redis + Lua** | 分布式滑动窗口 | 分布式限流（如 Nginx + Redis） |
| **Nginx limit_req** | 漏桶 | 网关层限流 |
| **网关限流** | Kong/APISIX 插件 | API 级别限流 |

## 4. 熔断与降级

### 4.1 核心概念

| 概念 | 含义 | 目的 |
|------|------|------|
| **熔断** | 下游故障时，快速失败不再调用，防止级联故障 | 保护系统 |
| **降级** | 核心功能不可用时，返回兜底结果 | 保证基本可用 |
| **限流** | 超过阈值拒绝请求 | 防止过载 |

### 4.2 熔断器状态机

```
          失败次数达阈值
  ┌────────┐              ┌─────────┐
  │ CLOSED │ ───────────→ │   OPEN  │
  │ (正常)  │              │ (熔断)   │
  └────────┘              └────┬─────┘
       ▲                       │
       │              等待时间窗口过期
       │          ┌────────────┘
       │          ▼
       │    ┌──────────┐
       └─── │HALF_OPEN │
            │ (试探)    │
            └──────────┘
              放少量请求试探
              成功 → CLOSED
              失败 → OPEN
```

### 4.3 主流框架

| 框架 | 特点 |
|------|------|
| **Sentinel** | 阿里开源，限流+熔断+降级+系统自适应保护，Dashboard 可视化 |
| **Hystrix** | Netflix 开源（已停更），线程池隔离/信号量隔离 |
| **Resilience4j** | 轻量级，Java 函数式编程，Hystrix 替代品 |

> Sentinel vs Hystrix：Sentinel 性能更好、规则更灵活、有控制台，新项目首选。

## 7. 分布式缓存

### 7.1 缓存分层架构

```
                    命中率       延迟
浏览器缓存 (HTTP Cache)     →    ~0ms
CDN 边缘缓存               →    10~50ms
Nginx 本地缓存             →    <1ms
应用本地缓存 (Caffeine)     →    <1ms     (JVM 内)
分布式缓存 (Redis)          →    1~5ms    (网络+内存)
数据库 (MySQL)             →    10~100ms  (磁盘)
```

### 7.2 缓存三大问题及解决方案

| 问题 | 场景 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 查不存在的数据 → 每次穿透到 DB | ① 布隆过滤器过滤不存在的 key ② 缓存空值（短 TTL） |
| **缓存击穿** | 热点 key 过期 → 大量并发打到 DB | ① 互斥锁：一个线程查 DB 重建，其他等待 ② 逻辑过期 + 异步更新 |
| **缓存雪崩** | 大量 key 同时过期 → DB 崩溃 | ① TTL 加随机值 ② 多级缓存 ③ 限流熔断兜底 |

### 7.3 缓存更新策略

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **Cache Aside** | 读：先缓存，miss 则查 DB；写：先更新 DB，再删缓存 | 最常用，简单 | 可能出现短暂不一致 |
| **Read/Write Through** | 缓存层代理 DB，读写都走缓存 | 缓存与 DB 强一致 | 实现复杂 |
| **Write Behind** | 异步批量写回 DB | 写入性能极高 | 缓存挂了丢数据 |

### 7.4 Cache Aside "先删缓存还是先更 DB"

```
先删缓存 + 后更 DB：
  A 删缓存 → B 读（缓存 miss，读 DB 旧值）→ B 写缓存（旧值）→ A 更 DB（新值）
  → 缓存中是旧值！不一致！

先更 DB + 后删缓存（推荐）：
  A 读缓存 miss → 读 DB 旧值 → B 更 DB 新值 → B 删缓存 → A 写缓存旧值
  → 概率极低（A 写缓存必须在 B 删缓存之后），99.9% 场景够用

兜底方案：设置合理过期时间 + 延迟双删（更 DB 后延迟几百 ms 再删一次）
```

### 7.5 Redis 集群模式

| 模式 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **主从复制** | 一主多从，读写分离 | 简单、读扩展 | 手动故障转移 | 小型项目 |
| **哨兵（Sentinel）** | 监控主从，自动故障转移 | 自动 HA | 不能水平扩展写 | 中型项目 |
| **Cluster** | 16384 个槽，多主多从 | 水平扩展，自动故障转移 | 跨槽操作受限 | 大型项目 |

### 7.6 淘汰策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| `noeviction` | 内存满拒绝写入 | 严格不能丢 |
| `allkeys-lru` | 所有 key 中淘汰最久未用的 | 通用（推荐） |
| `volatile-lru` | 有过期时间的 key 中淘汰 LRU | 部分 key 永久 |
| `allkeys-lfu` | 所有 key 中淘汰最少使用的 | 热点明显 |
| `volatile-ttl` | 淘汰即将过期的 | 对 TTL 敏感 |

## 8. 消息队列

### 8.1 为什么需要 MQ？

| 作用 | 说明 | 无 MQ 的问题 |
|------|------|-------------|
| **异步** | 非核心流程异步处理，快速返回 | 用户等所有步骤完成，体验差 |
| **解耦** | 上下游通过 MQ 通信，互不依赖 | 直接 RPC，下游挂了上游也挂 |
| **削峰** | 突发流量暂存 MQ，下游平滑消费 | 流量高峰打垮下游 |
| **日志/数据分发** | 一个消息多方消费 | 需要维护多个推送通道 |

### 8.2 主流 MQ 对比

| 对比维度 | Kafka | RocketMQ | RabbitMQ | Pulsar |
|---------|-------|----------|----------|--------|
| **语言** | Java/Scala | Java | Erlang | Java |
| **吞吐量** | ⭐⭐⭐⭐⭐ 百万级 | ⭐⭐⭐⭐⭐ 十万~百万 | ⭐⭐⭐ 万级 | ⭐⭐⭐⭐⭐ |
| **延迟** | ms 级 | ms 级 | μs 级 | ms 级 |
| **事务消息** | ❌（需自己实现） | ✅ 原生支持 | ❌（需自己实现） | ❌ |
| **顺序消息** | 分区内有序 | ✅ 全局/分区有序 | 队列内有序 | 分区内有序 |
| **延时消息** | ❌ | ✅ 18 个级别 | 插件支持 | ✅ |
| **集群模式** | 分布式 | 分布式（NameServer 轻量） | 主从 | 分布式（存算分离） |
| **适用场景** | 大数据/日志/流处理 | 电商/金融业务消息 | 企业级/RPC 低延迟 | 多租户/云原生 |

### 8.3 Kafka 核心概念

```
Producer ─→ [Broker-1] [Broker-2] [Broker-3]
              │  Topic: order
              │  Partition-0 (Leader)──→ Replica (Follower)
              │  Partition-1 (Leader)──→ Replica (Follower)
              │  Partition-2 (Leader)──→ Replica (Follower)
              │
Consumer ─→  Consumer Group
              ├─ Consumer-1 → 消费 Partition-0,1
              └─ Consumer-2 → 消费 Partition-2
```

| 概念 | 说明 |
|------|------|
| **Topic** | 消息的逻辑分类 |
| **Partition** | 物理分片，一个 Topic 多个 Partition → 并行读写 |
| **Offset** | 消息在 Partition 中的唯一序号 |
| **Consumer Group** | 消费者组，组内每个消费者独占不同 Partition |
| **ISR** | In-Sync Replicas，与 Leader 保持同步的副本集合 |
| **HW/LEO** | High Watermark（已提交的最高 offset）/ Log End Offset |

### 8.4 消息可靠性保证

| 维度 | 配置 | 说明 |
|------|------|------|
| **生产端** | `acks=all`（Kafka） | 所有 ISR 确认才返回成功 |
| **Broker 端** | 多副本 + ISR + `unclean.leader.election.enable=false` | 不在 ISR 中的副本不能选为 Leader |
| **消费端** | 手动提交 offset，处理完再提交 | 防止自动提交导致丢消息 |

### 8.5 消息幂等性与顺序性

**幂等方案：**

| 方案 | 做法 |
|------|------|
| **数据库唯一键** | 用消息 ID 做唯一索引，INSERT IGNORE |
| **Redis SETNX** | 消息 ID 做 key，只有第一次设置成功 |
| **业务状态机** | 订单状态"已支付"不能重复扣款 |

**顺序保证：**

| 场景 | Kafka 方案 | RocketMQ 方案 |
|------|-----------|--------------|
| 全局有序 | 1 Topic 1 Partition（牺牲并行度） | 1 Topic 1 Queue |
| 局部有序 | 相同 key 发到同一 Partition | 相同 ShardingKey 发到同一 Queue |

## 📖 核心要点速记

1. **服务发现**：Nacos（首选）> Consul > Eureka（退役）
2. **负载均衡**：客户端（Ribbon/LoadBalancer）vs 服务端（Nginx）
3. **限流**：令牌桶（最常用）→ Sentinel / Guava RateLimiter
4. **熔断**：CLOSED → OPEN → HALF_OPEN → CLOSED
5. **网关**：Spring Cloud Gateway（Java）/ APISIX（高性能）
6. **配置中心**：Nacos（轻量）/ Apollo（功能强）
7. **缓存三大问题**：穿透（布隆/空值）→ 击穿（互斥锁/永不过期）→ 雪崩（TTL 随机/多级/限流）
8. **缓存更新**：先更 DB，后删缓存（Cache Aside）
9. **Redis 集群**：主从 → 哨兵 → Cluster（按规模升级）
10. **MQ 选型**：大数据→Kafka，业务→RocketMQ，低延迟→RabbitMQ
11. **消息可靠三要素**：生产端 ack + Broker 持久 + 消费端手动提交
