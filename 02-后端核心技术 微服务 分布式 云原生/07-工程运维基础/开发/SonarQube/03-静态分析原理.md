## 1. 静态分析做什么

静态分析 = **不运行代码的代码检查**：分析器把源码解析成语法树与语义模型，在模型上跑规则引擎（模式匹配、数据流、符号执行），输出「问题清单」。与动态分析（测试、运行期检查）互补：静态能查「测试没覆盖的路径」与「编译期看不见的风险」（资源泄漏、并发隐患、注入），动态能查「实际行为对不对」——**「静态查风险、动态查行为」**是质量体系的分工（[[../代码质量/00-代码质量管理体系总览|代码质量体系]] 的全景）。

SonarQube 的分析发生在服务器端：Scanner 采集源码与编译产物 → 服务器构建模型跑规则 → 结果入库。**分析的语言差异**：Java 等编译型语言需要编译产物（`sonar.java.binaries`——02 篇坑四）；解释型语言（Python/JS）直接扫源码。**分析的精度差异**：部分规则是「语法模式匹配」（查「代码长得像什么」），部分是「数据流分析」（查「值怎么流动」——注入、泄露类漏洞）——**Community Build 的安全分析只有模式匹配，无数据流污点分析**（01 篇局限）。

## 2. 七类问题

SonarQube 把分析结果分为七类，理解分类才能正确处置：

**Bug（缺陷）**——确定会出错或极可能出错的代码（空指针、资源未关、死循环）；**Vulnerability（漏洞）**——可利用的安全弱点（SQL 注入、XSS、硬编码密钥——模式匹配类）；**Code Smell（坏味道）**——可维护性问题（重复代码、过长方法、死代码）——不立即出错但积累技术债；**Security Hotspot（安全热点）**——「需要人工审查」的可疑点（弱随机数、危险 API 使用）——**不是确定漏洞，是「请确认这里安全吗」**；**Coverage（覆盖率）**——测试覆盖的行/分支比例（不是问题，是度量）；**Duplication（重复）**——重复代码块；**Complexity（复杂度）**——圈复杂度等（可维护性度量）。

**处置优先级**：Bug/Vulnerability 是「必须修」（门禁拦截）；Code Smell 是「按债治理」（Clean as You Code 的增量纪律）；Security Hotspot 是「人工审查」（确认安全 → 标记「安全」，确认问题 → 转 bug 修复）。**「七类问题」的认知价值**：报告里的每一项都知道「该谁处理、多紧急、怎么算完成」。

## 3. 规则引擎与 6500+ 规则

规则是分析的最小单元——「某模式 + 触发条件 + 严重级 + 修复建议」。**2026 基线：6500-7000+ 条确定性规则**（跨 16-20+ 语言，Community；35+ 语言商业版）。规则的来源：**内置规则**（SonarSource 官方规则库——质量最高、持续更新）；**社区规则**（插件市场——第三方语言/框架规则）；**自定义规则**（自研插件——团队专属规范，07 篇）。

**规则的生命周期**：规则会随版本更新（新规则加入、旧规则调整、废弃规则移除）——**「规则集是活物」**：每月版本升级后，Quality Profile 里的规则集合可能变化（新规则默认激活与否看配置）——升级纪律见 09 篇。**规则的「为什么」**：每条规则的详情页有「为什么有害 + 示例 + 修复建议」——**让开发者理解而非盲从**，是规则能被执行的根基。

## 4. Clean as You Code

**2026 的核心理念——Clean as You Code（保持新代码干净）**：**只治理「新代码」的质量，而不是一次修完所有历史问题**。逻辑很简单：存量项目的问题可能上千，门禁卡全量 → 没人能通过 → 门禁形同虚设；卡「新代码」→ 每个 PR 的增量质量达标即可合入 → 代码库随时间变干净（新代码占的比例持续增长）。

**「新代码」的定义**：默认是「本次分析以来变更的代码」（New Code Period，下节）——只有新增/修改的行参与门禁判定。**「Clean as You Code」的落地组合**：门禁条件针对 New Code（新代码的 bug/覆盖率/债务比）；存量问题走专项治理（定期修债周、按模块分批）；**「新债为零、旧债排队」**是团队共识。

## 5. New Code Period

New Code Period（新代码周期）是 Clean as You Code 的边界定义——「从什么时候开始算新代码」：

**默认设置**：首次分析后，从「上次分析」开始算新代码（增量模式）；也可以按日历设置（如「最近 30 天」）或按版本（如「从 v2.0 开始」）。**门禁与 New Code 的关系**：门禁条件默认针对 New Code（`New Bugs`、`Coverage on New Code`、`New Duplications`）——**只卡新增行**。

**工程细节**：**New Code 的准确性依赖分析历史**——首次分析没有基线（全部算旧代码）；**改代码行也算 New Code**（修改了旧行 → 该行重新进入新代码判定）；**CI 与 PR 场景**（商业版 PR 分析天然按 diff；Community Build 单 main 分析靠版本周期设置——05 篇补偿）。

## 6. 技术债与度量

**技术债（Technical Debt）**——修复所有 Code Smell 的估计工作量（时间单位，如「3 天 4 小时」）——**「债」的隐喻**：欠债要还利息（维护成本随债累积），但还债有优先级（高利息的先还）。**债务比（Debt Ratio）**——技术债 ÷ 重写代码的估计成本——门禁的常用条件（如「新代码债务比 < 5%」）。

**核心度量家族**（Dashboard 与门禁的原料）：**问题数**（按 severity/类型）；**覆盖率**（行/分支）；**重复率**（重复代码占比）；**复杂度**（圈复杂度——可维护性代理指标）；**技术债**（时间量 + 债务比）。**度量的使用纪律**：**指标是趋势工具不是排名工具**——跨团队排名制造内卷（「覆盖率越高越好」的军备竞赛）；正确用法是「看自己的趋势」（这周 vs 上周）、「门禁设底线」（新代码达标即可）。

## 7. 分析的局限

**静态分析查不到什么**：**业务逻辑正确性**（「订单金额算错」查不出来——那是测试与审查的事）；**跨服务问题**（微服务间的接口契约问题——单项目分析看不到）；**运行时环境问题**（配置、依赖版本、性能——静态分析管不到）；**设计层面的问题**（架构腐化、模块耦合——指标能提示不能判定）。**误报的现实**：任何规则集都有误报（上下文特殊、框架约定、生成代码）——**误报治理是平台运营的日常**（07 篇：少而准的规则集 + 标记机制）。**「分析器说没问题 ≠ 没问题」**——它是质量体系的起点不是终点。

## 8. 常见坑

**坑一：把所有类型当 bug 修**。Code Smell 也当紧急 bug——按类型处置（Bug/Vuln 必修、Smell 按债、Hotspot 审查）。

**坑二：门禁卡全量指标**。存量问题卡死团队——Clean as You Code，只卡新代码。

**坑三：安全热点当漏洞**。Hotspot 是「请人工确认」——审查后标记，不是自动修。

**坑四：首次分析没基线**。New Code 判定需要历史——首次全量算旧代码，正常。

**坑五：覆盖率军备竞赛**。追求 100% 制造垃圾测试——门禁设底线，别内卷。

**坑六：以为分析器全覆盖**。静态查不到业务正确性与运行时问题——配合测试与审查。
