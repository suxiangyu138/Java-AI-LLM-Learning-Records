# 04-质量门禁与质量指标
> 定位：质量门禁是 SonarQube 最有力的机制——一组条件决定「代码能不能合入」；门禁设计的核心是「只卡新代码、底线而非完美」，让质量从「靠自觉」变成「靠机制」。

## 1. 质量门禁是什么

Quality Gate（质量门禁）= **一组可配置的条件集合**：每次分析后，SonarQube 对照条件判定「通过 / 失败」——**失败 = 代码质量不合格**。门禁的意义在「自动执行」：不用人肉 review 检查「覆盖率够不够、有没有新 bug」——分析完自动判定，CI 流水线按结果拦截（05 篇）——**「质量底线是机器执行的，不是口头承诺的」**。

**门禁的两种视角**：**平台内门禁**——Dashboard 显示 Passed/Failed，问题列表按门禁状态筛选；**流水线门禁**——CI 里 `waitForQualityGate` 等步骤读取门禁结果，失败则流水线失败（构建不发布）。**「门禁拦截什么」**：默认门禁（`Sonar way`）是「新代码」条件——新代码有问题即失败——**存量问题不拦**（03 篇 Clean as You Code 的落地载体）。

## 2. 指标家族

门禁条件的原料——指标家族（03 篇度量的展开），按「新旧」两维组织：

**新代码指标**（New Code，门禁主力）：`New Bugs`（新缺陷数）、`New Vulnerabilities`（新漏洞数）、`New Code Smells`（新坏味道）、`New Security Hotspots`（新安全热点）、`Coverage on New Code`（新代码覆盖率）、`New Duplications`（新重复率）、`New Debt Ratio`（新代码债务比）。**全量指标**（Overall，存量治理与趋势）：`Bugs`、`Vulnerabilities`、`Coverage`、`Duplications`、`Debt Ratio`、`Reliability Rating`（可靠性评级 A-F）、`Security Rating`。

**指标的可操作门槛**：`Quality Gate Status` 本身也是条件（嵌套门禁）；**评级的语义**（A=无 Blocker/Critical 问题，B=有 Critical 无 Blocker……F=有 Blocker）——评级用于存量健康度，不常用于门禁。

## 3. 门禁条件设计

**默认门禁（Sonar way）**——开箱即用的一组条件，是「社区共识底线」：新代码无 Blocker/Critical 问题（`New Bugs=0` 实质）、新代码覆盖率 ≥ 80%、新代码重复率 < 3%、新代码债务比 < 5%——**先跑默认门禁再定制**。

**定制门禁的决策框架**——按团队阶段与场景：

| 条件 | 推荐值 | 理由 |
|------|--------|------|
| New Bugs/Vulnerabilities | 0（硬性） | 新代码带 bug/漏洞不该合入 |
| Coverage on New Code | 60-80%（场景化） | 核心模块高、工具类低 |
| New Duplications | < 3% | 重复是新债之源 |
| New Debt Ratio | < 5% | 坏味道别欠新账 |
| New Security Hotspots | 0 未审查 | 热点必须人工确认 |

**设计原则**：**条件用「新代码」不用「全量」**（存量卡死团队）；**底线而非完美**（覆盖率 80% 是底线不是目标——目标 90% 靠团队自觉）；**核心模块与工具模块分门禁**（同一平台不同项目不同 Gate——`@Component` 工具类覆盖率要求放宽）；**条件可解释**（每条条件团队都能讲「为什么是这个数」——不能解释的数是玄学）。

## 4. 门禁与流水线

门禁的威力在流水线——「不合格代码进不了 main」：

```yaml
# GitLab CI 示例（05 篇完整姿势）
sonarqube-check:
  stage: test
  script:
    - sonar-scanner -Dsonar.token=$SONAR_TOKEN
    - sonar-quality-gate-check       # 读取门禁结果，失败则退出非零
  allow_failure: false               # 门禁失败 = 流水线失败 = 不发布
```

**流水线门禁的三个要点**：**门禁读取时机**——分析是异步的（Scanner 提交 → 服务器分析 → 结果入库），CI 里必须「轮询等待分析完成」再读门禁（05 篇 `waitForQualityGate`）；**失败即拦**——`allow_failure: false`（门禁失败流水线失败——「可以失败但必须显式知晓」）；**门禁结果可视化**——PR 装饰（商业版）或 CI 注释（Community 补偿，05 篇）。

## 5. 门禁设计决策

门禁设计是「质量治理」的决策——三个高频问题与答案：

**问题一：门禁太严还是太松**。太严（全量指标、覆盖率 90%）→ 团队绕路（suppress 滥用、改门禁）；太松（只卡 Blocker）→ 形同虚设。**答案：从默认门禁起步，按「被卡住的问题是否合理」迭代**——每次门禁失败都是「校准门禁」的机会：拦住了真问题 → 保持；拦住了误报/无关项 → 调规则或调条件。

**问题二：存量代码怎么办**。Clean as You Code：新代码卡门禁、存量走专项治理（修债周、按模块分批、债务比趋势监控）——「存量债」是「已知的债」，排期还，不是「未知的雷」。

**问题三：门禁失败的处理流程**。**门禁失败 ≠ 禁入**——失败要「人工看报告」：真问题 → 修复再合入；误报 → 标记 False Positive 重扫；紧急发布 → 显式豁免（记录在案、限期修）——**「显式豁免」比「静默绕过」健康**（豁免留痕，债可追踪）。

**门禁的可见性设计**——门禁机制要「可被看见」才有效：**Dashboard 门禁状态置顶**（项目页第一眼就是绿/红）；**CI 流水线的门禁 stage**（每次提交都看到红绿）；**PR 装饰**（商业版——评审时直接看到）；**定期门禁报告**（周报里带「门禁通过率」——趋势比单次红绿更有治理价值）。「**不可见的门禁 = 不存在的门禁**」——机制落地要配套可见性，不然门禁红了没人知道、绿了没人庆祝，机制就退化成后台数据。

## 6. 门禁的落地流程

从零落地质量门禁的六步：**第一步，跑默认门禁**（Sonar way 开箱）——扫第一个项目建立基线；**第二步，校准规则集**（07 篇）——关掉团队明确不需要的规则（少而准）；**第三步，定制门禁**——按团队阶段调条件（新代码为主）；**第四步，CI 集成**（05 篇）——`waitForQualityGate` + `allow_failure: false`；**第五步，PR 反馈**——商业版 PR 装饰或 CI 注释补偿（Community）；**第六步，治理节奏**——门禁失败例会过（修 or 豁免）、存量债排期、指标趋势月报。**「六步走完，质量机制闭环」**——从「靠人盯」到「机器卡」。

## 7. 常见坑

**坑一：门禁卡全量**。存量上千问题——永远红——团队绕路——Clean as You Code。

**坑二：覆盖率 100% 门禁**。逼出垃圾测试与作弊——底线 60-80%。

**坑三：门禁失败静默跳过**。`allow_failure: true` 永久开着——门禁形同虚设——显式豁免留痕。

**坑四：所有项目一个门禁**。工具类与核心模块同条件——分项目门禁。

**坑五：误报不治理**。误报堆积 → 团队不信任报告 → 门禁被架空——误报标记 + 规则裁剪（07 篇）。

**坑六：门禁只挂平台不挂 CI**。Dashboard 红了没人看——流水线拦截才是执行。
