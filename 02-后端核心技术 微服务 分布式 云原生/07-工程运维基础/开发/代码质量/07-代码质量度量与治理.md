## 1. 代码质量度量指标

### 1.1 五维度质量模型

| 维度 | 英文 | 子指标 | 测量工具 |
|------|------|--------|----------|
| **可靠性** | Reliability | Bug数量、严重Bug数 | SpotBugs, SonarQube |
| **安全性** | Security | 漏洞数、安全热点数 | SonarQube Security, OWASP Dependency Check |
| **可维护性** | Maintainability | 代码异味数、圈复杂度、重复率 | PMD, SonarQube |
| **覆盖率** | Coverage | 行覆盖率、分支覆盖率 | JaCoCo |
| **重复率** | Duplications | 重复代码行数、重复文件数 | PMD CPD, SonarQube |

### 1.2 核心度量指标

| 指标 | 说明 | 计算公式/方式 | 预警阈值 |
|------|------|--------------|----------|
| **圈复杂度** (Cyclomatic Complexity) | 方法的独立路径数 | = 判定节点数 + 1 (if/for/while/case每个+1) | > 15 → 建议重构 |
| **认知复杂度** (Cognitive Complexity) | 代码理解难度 | SonarQube专有算法（嵌套+递归增加权重） | > 15 → 建议重构 |
| **技术债务比率** | 修复所有问题所需时间 vs 重写时间 | SonarQube: (修复成本/开发成本)×100% | > 5% → 需要治理 |
| **代码重复率** | 重复代码占比 | 重复行数/总行数×100% | > 3% → 需消除 |
| **注释密度** | 注释行占比 | 注释行/总行数×100% | < 10% → 可能注释不足; > 40% → 可能过度 |
| **方法长度** | 每个方法平均行数 | 总行数/方法数 | > 30 → 方法过长 |

### 1.3 代码异味分类

| 异味类型 | 典型例子 | 严重程度 | 工具检测 |
|----------|----------|----------|----------|
| **Blob/上帝类** | 一个类干了所有事情(>1000行) | Critical | PMD TooManyMethods |
| **长方法** | >50行的方法，嵌套4层+ | Major | PMD, SonarQube |
| **长参数列表** | 方法参数>4个 | Major | PMD, Checkstyle |
| **特性依恋** | 方法过度使用其他类的数据 | Minor | SonarQube |
| **数据泥团** | 一组数据总是一起出现但未封装为对象 | Minor | 人工审查 |
| **霰弹式修改** | 改一个功能要修改很多类 | Major | Git历史分析 |
| **switch语句** | 多处switch(type)可改用多态 | Minor | PMD, SonarQube |

## 2. 技术债务度量与管理

### 2.1 什么是技术债务

> 🎯 技术债务 = 为了短期交付速度而做出的质量妥协。每笔债务都有"利息"——降低后续开发速度。

```
技术债务类型：
├── 蓄意债务（Deliberate）：明知不完美，为赶发布故意妥协
│   例："先hardcode配置，下个迭代迁到配置中心"
│
├── 无意债务（Inadvertent）：不知道更好的做法，或经验不足
│   例："不知道要对用户输入做XSS过滤"
│
├── 位腐烂债务（Bit Rot）：代码随着时间自然过时
│   例：依赖库5年未升级，新特性无法使用
│
└── 策略债务（Strategic）：为做架构决策选择而留下的老方案
    例：双写新旧两个数据源直到切换完成
```

### 2.2 SonarQube技术债务量化

```text
SonarQube 技术债务计算公式：
修复成本 = Σ(每个代码异味 × 该规则的修复时间)

规则修复时间示例：
- Blocker Bug: 3小时
- Critical Bug: 1小时  
- Major Code Smell: 30分钟
- Minor Code Smell: 10分钟

技术债务比率 = 修复成本 / 重写整个项目的成本 × 100%
```

### 2.3 债务管理策略

| 策略 | 说明 | 适用 |
|------|------|------|
| **债务登记** | 在Backlog中登记所有已知技术债务 | 所有项目 |
| **债务墙** | 新建代码不允许引入新债务（Clean as You Code） | CI/CD质量门禁 |
| **债务预算** | 每个迭代拿出10-20%时间偿还债务 | 敏捷团队 |
| **债务冲刺** | 专门安排1-2个迭代集中清理 | 积累严重时 |
| **破产重写** | 债务太重直接重写模块 | 万不得已 |

## 3. 质量门禁体系设计

### 3.1 分层质量门禁

```
第1层：IDE层（编码时）
  ↓  SonarLint 实时检查 → 0 Blocker + 0 Critical
  ↓  提交代码前所有IDE警告已解决
  
第2层：Pre-commit层（提交前）
  ↓  git hook: checkstyle + spotbugs + 单元测试
  ↓  本地 mvn verify 必须通过
  
第3层：CI层（PR合并前）
  ↓  GitHub Actions/Jenkins 自动运行全量检查
  ↓  Quality Gate 不通过 → 阻断合并
  ↓  - Test pass rate: 100%
  ↓  - Coverage: ≥ 80% (line), ≥ 70% (branch)
  ↓  - No Blocker/Critical issues
  ↓  - Duplications < 3%
  
第4层：定期审计（迭代结束时）
  ↓  SonarQube Quality Gate Review
  ↓  安全漏洞扫描（OWASP Dependency Check）
  
第5层：发布前（Release前）
  ↓  完整回归测试
  ↓  性能基准测试（是否低于基线）
  ↓  安全渗透测试
```

### 3.2 SonarQube Quality Gate配置

```yaml
# SonarQube Quality Gate 推荐配置
name: "Enterprise Quality Gate"

conditions:
  # 可靠性
  - metric: new_bugs
    op: GT
    error: "0"           # 新增Bug > 0 → 阻断

  # 安全性
  - metric: new_vulnerabilities
    op: GT
    error: "0"           # 新增漏洞 > 0 → 阻断
  
  - metric: new_security_hotspots_reviewed
    op: LT
    error: "100"         # 安全热点审查率 < 100% → 阻断

  # 可维护性
  - metric: new_code_smells
    op: GT
    error: "0"           # 新增代码异味 > 0 → 阻断（严格）

  - metric: new_technical_debt_ratio
    op: GT
    error: "5"           # 技术债务比率 > 5% → 阻断

  # 覆盖率
  - metric: new_coverage
    op: LT
    error: "80"          # 新代码覆盖率 < 80% → 阻断

  - metric: new_branch_coverage
    op: LT
    error: "70"          # 新分支覆盖率 < 70% → 阻断

  # 重复率
  - metric: new_duplicated_lines_density
    op: GT
    error: "3"           # 重复率 > 3% → 阻断
```

### 3.3 质量门禁灰度上线策略

```
Phase 1（软上线）：仅告警不阻断，收集数据 2周
Phase 2（部分阻断）：阻断Blocker Bug和漏洞，其他告警 2周
Phase 3（全面上线）：全部条件阻断
```

## 4. 代码规范落地策略

### 4.1 落地四步法

```
1. 文档化 → 制定团队编码规范（基于Google Java Style或Alibaba Java Guide）
2. 工具化 → 配置Checkstyle/PMD/SpotBugs规则
3. 自动化 → 集成到CI/CD，自动检查自动阻断
4. 习惯化 → 开发者提交前自己就跑过检查（IDE集成）
```

### 4.2 规则分级

| 级别 | 定义 | 违反后果 | 示例 |
|------|------|----------|------|
| **强制(MUST)** | 违反即Bug | CI阻断合并 | SQL注入、空指针、资源泄露 |
| **推荐(SHOULD)** | 绝大多数情况遵守 | CI告警+Review标记 | 圈复杂度>15、方法>50行 |
| **可选(MAY)** | 按团队偏好 | 不阻断 | 注解位置、import顺序 |

### 4.3 排除与例外机制

```java
// 全局排除：构建工具排除不需要检查的文件
// checkstyle-suppressions.xml
<suppressions>
    <suppress files=".*[\\/]generated[\\/].*" checks=".*"/>
    <suppress files=".*DTO\.java" checks="MagicNumber"/>
</suppressions>

// 局部排除：特定代码行
@SuppressWarnings("PMD.AvoidCatchingGenericException")
public void legacyWrapper() {
    try { legacyCall(); }
    catch (Exception e) { log.error(e); } // 遗留代码兼容
}

// 不要滥用排除！每个@SuppressWarnings都要注释WHY
```

## 5. 质量治理的组织保障

### 5.1 角色与责任矩阵

| 角色 | 质量职责 |
|------|----------|
| **开发者** | 对自己的代码质量负首要责任，提交前自查 |
| **Tech Lead** | 制定团队编码规范，Review重要PR |
| **架构师** | 制定架构质量红线（不允许跨层调用等） |
| **QA/测试** | 验证质量流程是否被遵守 |
| **DevOps** | 维护CI/CD质量门禁，确保线是红的就无法合并 |

### 5.2 质量文化建设

```
短期（1-3个月）：
  → 引入SonarLint，每人安装IDE插件
  → CI中加入覆盖率检查（仅告警不阻断）
  → 每周Code Review Retrospective（复盘好/坏审查案例）

中期（3-6个月）：  
  → CI：SonarQube Quality Gate（先软后硬）
  → 技术债务看板可视化（Jira/Dashboard）
  → 每月"质量日"（集中修复技术债务）

长期（6-12个月）：
  → 质量指标纳入团队KPI
  → 技术债务比率持续下降趋势
  → 新人Onboarding包含代码质量培训
```

### 5.3 质量仪表盘

| 指标 | 当前值 | 目标值 | 趋势 |
|------|--------|--------|------|
| 新增Blocker Bug | 0 | 0 | ✅ |
| 行覆盖率 | 76% | ≥80% | 📈+2% |
| 技术债务比率 | 8.2% | <5% | 📉-0.5% |
| 重复率 | 4.1% | <3% | 📉-0.3% |

---

> 🎯 **质量治理核心原则**：不要期望一步到位——先度量 → 再设定目标 → 工具化自动化 → 持续改进。质量不是检测出来的，是"内建"出来的。
