## 1. 多端适配全景

**跨端的现实：「一次编写、按平台适配」**——同一套代码在不同平台有差异：**UI 差异**（导航栏样式、弹窗组件平台各异）、**API 差异**（平台 API——支付、分享、登录各平台不同）、**能力差异**（平台能力——微信的订阅消息、支付宝的芝麻信用）。**适配的三种层次**：**统一层**（uni API/内置组件——自动适配——大多数场景）；**条件编译层**（平台差异代码——`#ifdef`——少数场景）；**独立层**（完全不同的页面/模块——单独实现——极少数场景）——**「适配的纪律：尽量用统一层、差异用条件编译、特殊用独立实现」**——**「业务代码保持平台无关」是跨端工程的黄金准则**。

## 2. 条件编译实战

条件编译的完整姿势（04 篇入门 + 本篇实战）：

```js
// JS 条件编译
// #ifdef MP-WEIXIN
import wxPay from './pay-weixin'
// #endif
// #ifdef MP-ALIPAY
import alipayPay from './pay-alipay'
// #endif

// 模板条件编译
<!-- #ifdef H5 -->
<view>H5 专属内容</view>
<!-- #endif -->

// 样式条件编译
/* #ifdef APP-PLUS */
.nav { height: calc(100vh - 88rpx); }
/* #endif */
```

**实战要点**：**平台标识全集**——`MP-WEIXIN`/`MP-ALIPAY`/`MP-TOUTIAO`/`H5`/`APP-PLUS`（App）/`APP-HARMONY`（鸿蒙）；**`#ifndef` 反向编译**（除 X 外都编译）；**差异的封装**——**「条件编译尽量收拢到独立文件」**（支付封装 `pay.js` 内部条件编译——业务调用统一 `pay()`——「条件编译的边界：业务层看不到平台差异」）。

## 3. 平台差异清单

高频平台差异清单（开发中会遇到的）：**导航栏**——各平台返回按钮/胶囊样式差异（自定义导航栏的适配——`navigationStyle: custom` 自定义方案）；**支付**——微信支付（`uni.requestPayment` + 平台参数——后端下单签名——[[../项目从开始开发到上线全流程/00-项目全流程知识体系总览|支付流程]]）、支付宝支付参数不同；**登录**——`uni.login` 各平台返回的 code 语义不同（微信 code → openid、支付宝 code → userId）；**分享**——微信（`onShareAppMessage`）、各平台分享 API 差异；**发布/审核**——各平台后台配置不同（09 篇）；**鸿蒙端**——部分 CSS 选择器/伪元素不支持、部分 API 未对齐（01 篇——鸿蒙适配注意）。

## 4. 双线程模型与 setData

**性能的核心约束——双线程模型**（01 篇）：逻辑层（JSCore）与视图层（WebView）分离——**setData 是唯一的通信通道**：

```js
// ❌ 大数据量一次性 setData（卡顿根源）
const list = []
for (let i = 0; i < 10000; i++) list.push({ ... })
this.list = list          // 一次性传 1 万条

// ✅ 分页 + 局部更新
// 数据分页加载（一次 20 条）+ 只更新变更字段
```

**setData 的性能纪律**：**数据量控制**（一次 setData 的数据量要小——大列表分页/虚拟列表）；**频率控制**（避免高频 setData——滚动/动画中的数据更新要节流）；**路径更新**（`this.list[0].name = 'x'`——局部字段更新——避免整对象重传）；**「setData 是序列化传输」**（大数据量 = 序列化开销 + 渲染开销——**「页面卡顿的第一排查项是 setData 的量与频」**）。

## 5. 包体积优化：分包

**微信小程序主包 2MB 限制**（总包 20MB 级别）——**分包加载是标配设计**：**分包机制**——主包（启动必须的页面）+ 分包（按需加载的页面——用户进入分包页面时才下载）——`pages.json` 配置：

```json
{
  "pages": [{ "path": "pages/index/index" }],
  "subPackages": [
    { "root": "pages/order", "pages": ["list/list", "detail/detail"] }
  ]
}
```

**分包的工程决策**：**分包边界**——按业务模块分（订单/购物车/个人中心——**「低频或独立模块进分包」**——启动路径的页面留主包）；**体积治理**——静态资源压缩（图片转 base64 权衡/CDN 外链）、组件按需引入（07 篇）、三方库精简（「引入库先看体积」）——**「2MB 是硬约束，分包与体积治理是设计的一部分」**。

## 6. 列表与图片性能

长列表与图片是小程序性能的两大场景：**长列表**——**虚拟列表**（只渲染可视区——`recycle-list` 或自定义虚拟列表——千条以上列表的标配）；**分页加载**（07 篇——上拉加载——「一次 20 条」）；**列表项组件化**（组件渲染开销——列表项抽组件 + `v-for` 的 key）；**图片性能**——**懒加载**（image 的 `lazy-load` 属性——滚动到才加载）；**尺寸压缩**（CDN 图片按需尺寸——`?imageView2/0/w/200` 类处理——「图片是包体积与流量的第一大户」）；**雪碧图/占位**（多小图合并、加载占位——体验优化）。

## 7. 常见坑

**坑一：条件编译散落业务代码**。到处 #ifdef——封装到独立文件——业务层平台无关。

**坑二：一次 setData 传大列表**。卡顿——分页 + 局部更新。

**坑三：不分包**。主包超 2MB 上传失败——分包按模块。

**坑四：列表全量渲染**。千条 v-for 卡——虚拟列表。

**坑五：图片不懒加载**。首屏加载慢——lazy-load + 尺寸压缩。

**坑六：组件库全量引入**。包体积爆炸——按需引入。

**坑七：忽略平台差异**。微信能跑支付宝报错——平台差异清单过一遍。

**性能排障的流程**（「小程序卡了」的排查顺序）：**第一问数据量**——setData 传了多少（万条列表？——分页/虚拟列表）；**第二问频率**——高频更新（滚动/动画中 setData？——节流/局部更新）；**第三问渲染**——列表项复杂度（复杂组件重复渲染？——组件拆分 + key）；**第四问资源**——图片（大图未压缩？——懒加载 + 尺寸）；**第五问包体积**——启动慢（主包大？——分包）——**「卡顿排障五问：量 → 频 → 渲染 → 资源 → 包」**——按序排查，先数据后代码。

**启动性能**——**首屏速度的优化**：分包（主包只留启动路径——08 篇）、首屏数据接口合并（一个聚合接口替代多个串行请求——「首屏请求数 = 首屏速度」）、骨架屏（首屏占位——体验）、图片首屏优化（首屏图片压缩/懒加载非首屏）——**「启动性能的指标：首屏时间——优化的目标是首屏请求链路最短」**。
