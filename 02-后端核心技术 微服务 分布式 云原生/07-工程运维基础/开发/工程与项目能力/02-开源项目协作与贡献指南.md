## 1. 为什么要参与开源

### 1.1 对个人成长的价值

| 维度 | 具体收益 |
|------|----------|
| **简历加分** | 真实项目贡献比"XX 管理系统课设"有说服力得多，面试官会重点关注 |
| **代码能力** | 阅读顶级项目源码，学习架构设计、设计模式、工程规范的最佳途径 |
| **协作能力** | 学会与全球开发者协作——异步沟通、Code Review、版本管理 |
| **技术影响力** | 长期贡献可成为 Committer / Maintainer，在社区建立个人品牌 |
| **面试素材** | 贡献的每个 PR 都是面试中"你最挑战的项目"的绝佳回答素材 |
| **网络资源** | 认识业界大牛，获得内推、工作机会 |

> 💡 **数据点**：GitHub 2024 年报告显示，有持续开源贡献的开发者获得面试回应的概率比纯学历背景者高 40%。

### 1.2 贡献层级金字塔

```
Level 5: Maintainer / PMC        ← 项目决策者
Level 4: Core Contributor          ← 频繁贡献核心模块
Level 3: Active Contributor        ← 定期提交 Bug Fix / Feature
Level 2: Occasional Contributor    ← 偶尔修 Bug / 加文档
Level 1: First-time Contributor    ← 修 Typo / 补文档
```

> 🎯 目标不是"一步登天"——从 Level 1 开始，每次贡献都向上一步。

## 2. GitHub 协作工作流详解

### 2.1 Fork & Pull 工作流（标准流程）

```
原始仓库（upstream）
    ↑ PR
Fork 仓库（origin）
    ↑ git push
本地仓库
    ↑ git commit
工作区
```

### 2.2 完整步骤

**第一步：Fork 仓库**

在 GitHub 上点击目标仓库的 `Fork` 按钮，将仓库复制到自己的 GitHub 账号下。

**第二步：Clone 到本地**

```bash
# 克隆自己的 Fork
git clone https://github.com/your-username/project.git
cd project

# 添加上游仓库（原始仓库）
git remote add upstream https://github.com/original-owner/project.git

# 验证远程仓库
git remote -v
# origin    https://github.com/your-username/project.git (fetch/push)
# upstream  https://github.com/original-owner/project.git (fetch/push)
```

> 💡 添加 `upstream` 是关键步骤——后续需要从上游同步最新代码。

**第三步：创建功能分支**

```bash
# 确保基于最新的上游 main 分支
git fetch upstream
git checkout upstream/main -b feat/add-user-avatar
```

分支命名规范：

| 前缀 | 含义 | 示例 |
|------|------|------|
| `feat/` | 新功能 | `feat/add-login-page` |
| `fix/` | Bug 修复 | `fix/null-pointer-in-auth` |
| `docs/` | 文档修改 | `docs/update-readme` |
| `refactor/` | 重构 | `refactor/extract-validator` |
| `test/` | 测试相关 | `test/add-user-service-test` |
| `chore/` | 构建/配置 | `chore/update-dependencies` |

**第四步：开发与提交**

```bash
git add .
git commit -m "feat: add user avatar upload API"
```

**第五步：推送并创建 PR**

```bash
# 推送到自己的 Fork
git push origin feat/add-user-avatar

# 在 GitHub 上创建 PR：origin/feat/add-user-avatar → upstream/main
```

**第六步：响应 Review**

```bash
# 收到 review 意见后，在本地修改
git add .
git commit -m "fix: address review comments - add input validation"

# 推送后自动更新 PR
git push origin feat/add-user-avatar
```

**第七步：PR 合并后清理**

```bash
# 切回 main，同步上游
git checkout main
git fetch upstream
git merge upstream/main

# 删除本地和远程的分支
git branch -d feat/add-user-avatar
git push origin --delete feat/add-user-avatar
```

## 3. Conventional Commits 约定式提交

### 3.1 基本格式

```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### 3.2 类型速查

| 类型 | 含义 | 是否触发版本发布 |
|------|------|------------------|
| `feat` | 新功能 | 是（minor） |
| `fix` | Bug 修复 | 是（patch） |
| `docs` | 文档变更 | 否 |
| `style` | 代码格式调整（不影响功能） | 否 |
| `refactor` | 重构（既不修 Bug 也不加功能） | 否 |
| `perf` | 性能优化 | 是（patch） |
| `test` | 增加或修改测试 | 否 |
| `chore` | 构建/工具/配置变更 | 否 |
| `ci` | CI 配置变更 | 否 |
| `build` | 构建系统变更 | 否 |

### 3.3 示例

```bash
# 基本用法
feat: add user avatar upload API

# 带作用域
feat(auth): add OAuth2 login support

# 带 breaking change（! 表示不兼容变更）
feat(api)!: change user id from integer to UUID

# 带正文和脚注
fix: fix NPE when user is deleted concurrently

When a user is deleted while another request is reading,
a NullPointerException occurs in UserService.getById().

Closes #1234
```

### 3.4 为什么必须用 Conventional Commits

| 理由 | 说明 |
|------|------|
| **自动生成 CHANGELOG** | `standard-version` 等工具根据 commit 类型自动生成发布日志 |
| **语义化版本自动推断** | `feat` → minor，`fix` → patch，`!` → major |
| **PR 标题自动匹配** | GitHub 可根据 squash merge 的 commit 格式生成 PR 标题 |
| **便于 Code Review** | Reviewer 一眼看出每个 commit 的类型和变更范围 |

## 4. 写好 Pull Request

### 4.1 PR 模板结构

```markdown
## Description
<!-- 描述改了什么以及为什么改 -->

## Related Issue
<!-- 关联的 Issue 编号 -->
Closes #123

## Type of Change
- [ ] Bug fix (non-breaking)
- [ ] New feature (non-breaking)
- [ ] Breaking change
- [ ] Documentation update

## How Has This Been Tested?
- [ ] Unit tests
- [ ] Integration tests
- [ ] Manual testing

## Screenshots (if applicable)

## Checklist
- [ ] My code follows the project's style guidelines
- [ ] I have added tests that prove my fix/feature works
- [ ] All existing tests pass
- [ ] Documentation has been updated
```

### 4.2 PR Title 规范

PR 标题 = 一次较好的 commit message：

```text
✅ 好的 PR 标题
feat: add user avatar upload with S3 storage
fix: handle NullPointerException in concurrent user deletion
docs: update API documentation for pagination

❌ 不好的 PR 标题
fix bug                                    # 太模糊
Update UserService.java                    # 只说了改了哪个文件
WIP                                        # 不完整
asdfasdf                                   # 无意义
```

### 4.3 PR Description 黄金法则

**What — Why — How — Testing** 四要素缺一不可：

```markdown
## What
添加用户头像上传功能，支持通过 S3 存储文件。

## Why
用户需要上传个人头像以完善个人资料页面。

## How
- 在 `UserController` 中新增 `POST /users/{id}/avatar` 端点
- 使用 AWS S3 SDK 存储文件，返回 CDN URL
- 限制文件大小不超过 5MB，格式仅支持 JPG/PNG/WebP

## Testing
- 新增单元测试覆盖文件校验逻辑
- 新增集成测试验证 S3 上传流程
- 手动测试了 1MB / 5MB / 10MB 三种文件大小的边界情况
```

## 5. PR 最佳实践

### 5.1 保持 PR 小而精

| 指标 | 推荐值 | 说明 |
|------|--------|------|
| **代码行数** | < 400 行 | 超过 400 行的 PR 被 Review 的概率下降 50% |
| **文件数** | < 15 个 | 分散在太多文件的 PR 难以追踪 |
| **Commit 数** | < 5 个 | 便于逐 commit review |
| **涉及功能** | 1 个 | 一个 PR 只做一件事 |

> ⚠️ **不要在一个 PR 里同时做三件事**：修 Bug + 加功能 + 重构。这会延长 Review 周期，增加被拒绝风险。拆分多个小 PR，逐个合并。

### 5.2 Atomic Commits（原子提交）

每个 commit 代表一个完整的、可独立工作的变更：

```bash
# ✅ 良好的 commit 序列
1. refactor: extract file validation into separate util
2. feat: add avatar upload endpoint with S3 support
3. test: add unit tests for file validation

# ❌ 不好的 commit 序列
1. WIP: working on it
2. fix: fix the previous commit
3. real fix: oh actually fix it properly
4. chore: forgot to add file
```

### 5.3 Rebase Before PR

在推送 PR 之前，确保代码基于最新的上游 main：

```bash
git fetch upstream
git rebase upstream/main
# 解决冲突后
git push origin feat/add-user-avatar --force-with-lease
```

> 💡 用 `--force-with-lease` 而非 `--force`，前者会检查是否有人同时推送了你的分支，防止覆盖他人提交。

### 5.4 PR 的 Do's and Don'ts

| Do | Don't |
|----|-------|
| PR 标题写清楚变更内容 | PR 标题写 "fix" 或 "update" |
| Description 说明 what/why/how | 留空 description |
| 关联 Issue（`Closes #123`） | 没有关联 Issue |
| 保持 PR < 400 行 | 提交 2000+ 行的巨无霸 PR |
| 先 Rebase 再推送 | 在主分支上直接修改 |
| 及时响应 Review 意见 | 一周后才回复 Review |

## 6. Code Review 礼仪与技巧

### 6.1 作为提交者（Author）

**提交 PR 之前**：

- [ ] 自测通过，现有测试全部通过
- [ ] 新增了必要的测试覆盖
- [ ] 检查过 diff，没有遗留的调试代码、TODO 注释
- [ ] 本地运行 lint/checkstyle 没有告警

**收到 Review 意见时**：

| 情况 | 正确做法 |
|------|----------|
| 意见合理 | 立即修改，commit 并 push，回复"已修复，请再次审查" |
| 意见不明确 | 回复"你的意思是指 XXX 吗？能否再详细说明？" |
| 有不同意见 | 先解释你的设计考量，接受更好的方案 |
| 错误的建议 | 礼貌解释为什么不可行（"这里需要考虑线程安全，所以用了 ConcurrentHashMap"） |

> ⚠️ **不要对 review 意见产生抵触情绪**。Code Review 针对的是代码，不是你这个人。最糟糕的反应是："这个我试过不行"但不去验证就拒绝了。

### 6.2 作为审查者（Reviewer）

**Review 原则**：

```text
对事不对人，聚焦代码质量而非个人能力
给出具体建议，而非笼统否定
区分"必须改"和"可以改"——标记 severity
及时 Review，不要让 PR 等一周
```

| 建议类型 | 措辞示例 |
|----------|----------|
| **必须修改** | "这里存在 NPE 风险，当 `user` 为 null 时会导致空指针，建议加 null 检查" |
| **建议修改** | "这个方法的复杂度有点高（15 行），考虑拆分为两个小方法？" |
| **疑问/讨论** | "这里用 `ArrayList` 而不是 `LinkedList` 有什么特别的考量吗？" |
| **表扬** | "这个单测的边界覆盖写得很全面，赞" |

```text
✅ 好的 Review 反馈
"建议用 Optional 代替直接返回 null，这样调用方不需要每次都做 null 检查"

❌ 不好的 Review 反馈
"这代码好烂"   ← 只批评不给建议
"改一下"      ← 没说明改什么
"你这里错了"   ← 没有解释为什么错、怎么改
```

### 6.3 Review Checklist

| 审查维度 | 关注点 |
|----------|--------|
| **正确性** | 逻辑对不对？边界情况处理了吗？并发安全吗？ |
| **可读性** | 命名是否清晰？注释是否必要且准确？ |
| **测试** | 有测试吗？覆盖了正常路径和异常路径吗？ |
| **性能** | 有没有不必要的数据库查询？循环里有没有性能问题？ |
| **安全** | 输入做了校验吗？有 SQL 注入/XSS 风险吗？ |

## 7. 如何找到值得贡献的项目

### 7.1 从日常工具入手

最自然（也最有效）的方式：**你在用的工具**。

```text
- 使用 Spring Boot 时发现了文档笔误 → 修复
- 使用 VS Code 插件遇到 Bug → 报告 Issue 或修复
- 使用某框架时觉得某块文档不够清晰 → 补充文档
```

> 💡 你越深度使用一个工具，越容易发现可以改进的地方——不管是文档、性能还是 Bug。

### 7.2 主动寻找的渠道

| 渠道 | 说明 | 链接 |
|------|------|------|
| **Good First Issue** | GitHub 为新手标记的友好 Issue | `label:good-first-issue` |
| **Help Wanted** | 项目明确寻求帮助的 Issue | `label:help-wanted` |
| **Awesome Lists** | 按领域分类的优质项目列表 | `awesome-java`, `awesome-spring` |
| **GSOC / OSPP** | Google Summer of Code / 中科院开源之夏 | 带 mentor 的正式项目 |
| **First Timers Only** | 专为首次贡献者设计的 Issue | [firsttimersonly.com](https://www.firsttimersonly.com) |

**搜索命令**：

```bash
# 搜索特定语言的好入门 Issue
label:good-first-issue language:java

# 搜索特定领域的项目
label:help-wanted topic:spring-boot

# 搜索 size 标记（项目标记 PR 的规模）
label:size/small label:help-wanted
```

### 7.3 选择项目的评估维度

| 评估维度 | 加分 | 减分 |
|----------|------|------|
| **活跃度** | 近期有 commit，Issue/PR 在一周内得到回复 | 超过半年没有合并 PR |
| **社区氛围** | 有 `CONTRIBUTING.md`、有 `Code of Conduct` | 维护者态度差、对新手不友好 |
| **技术栈匹配** | 你熟悉的语言/框架 | 完全陌生的技术栈 |
| **Issue 质量** | Issue 描述清晰、有复现步骤 | Issue 描述模糊、无人维护 |
| **CI 完善度** | 有自动化测试、lint、CI 流水线 | 没有 CI，手动测试 |

## 8. 源码阅读技巧

### 8.1 阅读路径（由浅入深）

```
1. README + 官方文档     → 了解项目定位和核心概念
2. 项目结构概览           → 模块划分、包结构
3. 核心接口/抽象类        → 了解扩展点
4. 核心数据模型           → 理解业务核心实体
5. 启动/初始化流程        → 了解项目从哪开始
6. 一次请求的完整调用链    → 从入口到出口
7. 重点模块/设计亮点      → 如缓存设计、线程模型
```

### 8.2 核心方法：跟踪一次请求

以 Spring MVC 为例，从 `DispatcherServlet` 开始跟踪：

```
DispatcherServlet.doDispatch()
  → HandlerMapping.getHandler()      ← 找到对应的 Controller
  → HandlerAdapter.handle()          ← 执行 Controller 方法
    → 拦截器 preHandle()
    → Controller 方法执行
    → 拦截器 postHandle()
  → ViewResolver.resolveViewName()    ← 视图解析
  → 拦截器 afterCompletion()
```

> 💡 每次阅读源码时，带着一个具体问题："Spring 是怎么处理 `@Autowired` 的？"——带着问题去追踪代码，比从头读到尾效率高 10 倍。

### 8.3 辅助工具

| 工具 | 用途 |
|------|------|
| **IntelliJ IDEA** | `Ctrl+N` 查找类，`Ctrl+Alt+左/右` 导航，`Ctrl+Alt+U` 继承树 |
| **Sourcegraph** | 在线源码搜索，跨仓库跳转 |
| **Git Blame** | 查看每行代码是谁、什么时候、为什么写的 |
| **Git Log** | `git log --oneline --graph --all` 查看分支演进 |
| **代码可视化** | [CodeSee](https://www.codesee.io/) 可视化调用图 |

### 8.4 笔记方法

```markdown
## 类: DefaultThreadPoolExecutor

### 核心字段
- `corePoolSize`: 核心线程数，即使空闲也不回收
- `maximumPoolSize`: 最大线程数
- `workQueue`: 阻塞队列，存储待执行任务

### 执行流程
提交任务 → 
  1. 工作线程数 < corePoolSize → 新建线程执行
  2. 工作线程数 >= corePoolSize → 放入 workQueue
  3. 队列满 → 新建线程直到 maximumPoolSize
  4. 超过 maximumPoolSize → RejectedExecutionHandler

### 设计亮点
- Worker 继承 AQS 实现独占锁，用于线程中断控制
- `ctl` 字段用高 3 位存状态、低 29 位存线程数 → 一个 int 存两个值
```

## 9. Git 进阶协作技能

### 9.1 Rebase —— 保持历史干净

```bash
# 将当前分支的提交"移植"到上游最新代码之上
git fetch upstream
git rebase upstream/main

# 交互式 rebase —— 整理本地 commit
git rebase -i HEAD~3
```

交互式 rebase 支持的操作：

| 命令 | 含义 |
|------|------|
| `pick` | 保留该 commit |
| `reword` | 修改 commit message |
| `squash` | 合并到前一个 commit |
| `fixup` | 合并到前一个 commit（丢弃 message） |
| `drop` | 删除该 commit |

### 9.2 Squash —— 合并多个 Commit

PR 被 merge 前的常见操作——将多个 WIP/Fixup commit 合并为一个整洁的 commit：

```bash
# 将最近的 3 个 commit 合并
git rebase -i HEAD~3

# 编辑器中将后两个的 pick 改为 squash
pick abc123 feat: add avatar upload
squash def456 fix: address review feedback
squash ghi789 fix: add null check

# 合并后推送（需要 force push）
git push origin feat/add-avatar --force-with-lease
```

### 9.3 Cherry-pick —— 选择性移植

将某个分支上的特定 commit 移植到当前分支：

```bash
# 将 commit abc123 的变更应用到当前分支
git cherry-pick abc123

# 同时移植多个 commit
git cherry-pick abc123 def456
```

> 💡 Cherry-pick 用于：hotfix 从修复分支移植到 main、或从 main 移植到 release 分支。

### 9.4 Bisect —— 二分查找引入 Bug 的 Commit

```bash
# 开始 bisect
git bisect start
git bisect bad          # 当前版本有问题
git bisect good v1.0    # v1.0 是好的

# Git 会 checkout 中间版本，你测试后标记
git bisect good         # 当前版本没问题
# 或
git bisect bad          # 当前版本有问题

# 找到第一个问题 commit 后结束
git bisect reset

# 一行命令自动化
git bisect run ./run-tests.sh
```

### 9.5 Git 协作配置建议

```bash
# 设置用户信息
git config --global user.name "Your Name"
git config --global user.email "your@email.com"

# 默认远程推送方式
git config --global push.default current

# 开启 rebase 模式拉取代码
git config --global pull.rebase true

# 设置 git 比较算法
git config --global diff.algorithm histogram

# 别名
git config --global alias.s "status -sb"
git config --global alias.l "log --oneline --graph --all"
git config --global alias.undo "reset --soft HEAD~1"
```

## 10. 开源许可证指南

### 10.1 常见许可证对比

| 许可证 | 类型 | 商用 | 修改后闭源 | 专利授权 | 说明 |
|--------|------|------|-----------|----------|------|
| **MIT** | 宽松 | 允许 | 允许 | 隐含 | 最简单，只需保留版权声明 |
| **Apache 2.0** | 宽松 | 允许 | 允许 | 明确 | 比 MIT 多了专利授权条款 |
| **GPL v3** | 强 Copyleft | 允许 | **不允许** | 明确 | 修改或衍生必须开源 |
| **LGPL v3** | 弱 Copyleft | 允许 | 仅库可链接闭源 | 明确 | 修改库必须开源 |
| **AGPL v3** | 强 Copyleft | 允许 | **网络使用也要求开源** | 明确 | 即使通过网络提供服务也必须开源 |
| **BSD 2/3** | 宽松 | 允许 | 允许 | 无 | 与 MIT 类似，BSD 3 禁止背书 |
| **MPL 2.0** | 弱 Copyleft | 允许 | 允许（修改的文件需开源） | 隐含 | 文件级别 Copyleft |

### 10.2 如何选择

```text
你的项目
├── 想被广泛采用，尽可能减少法律障碍 → MIT（最安全的选择）
├── 大公司使用，需要专利保护 → Apache 2.0
├── 强制所有衍生品开源 → GPL v3
├── 库（Library），允许闭源链接 → LGPL v3 / Apache 2.0
└── 云服务项目，防止被 SaaS 化 → AGPL v3
```

> 💡 GitHub 对新建仓库的默认推荐：**MIT License**。

### 11.5 维护者心态

```text
好的开源项目维护 ≈ 70% 沟通 + 20% 代码 + 10% 社区管理

时间分配建议：
- 40% 审查和合并 PR
- 20% 回复 Issue 和讨论
- 20% 写代码（新功能/重构）
- 10% 文档和发布
- 10% 社区建设
```

> ⚠️ **避免燃烧**：开源维护者的 burnout 是个真实问题。设置清晰的边界——明确 Issue 回复时间、不接受无讨论的 PR、必要时招募 co-maintainer。

## 12. 常见误区与避坑指南

### 12.1 新手常见误区

| 误区 | 正确做法 |
|------|----------|
| "等我学好了再参与" | 修复文档 typo 就是极好的入门，不用等 |
| "一上来就想做大功能" | 从 Good First Issue 开始，先理解项目 |
| "不讨论就直接写代码提交 PR" | 大功能先在 Issue 中讨论方案，得到维护者同意后再开始 |
| "PR 越大越好" | 小而精的 PR 更容易被合并 |
| "被拒绝就是失败" | 被拒绝是正常的——根据反馈改进再次提交 |
| "只关注代码" | 文档、测试、Issue 回复都是重要贡献 |

### 12.2 时间管理

```text
第一阶段：成为深度用户（1-2 周）
  每天使用项目→记录遇到的问题→查看 Issue 是否已有解决

第二阶段：小步贡献（1-3 个月）
  周末 2-3 小时，从文档、typo、小 Bug 开始

第三阶段：持续贡献（3 个月+）
  每周 5-10 小时，逐步深入核心模块
```

### 12.3 面试中如何呈现开源贡献

```text
❌ 不好：
"我给 Spring Boot 提交过 PR"

✅ 好：
"我给 Spring Boot 修复了一个关于 @ConfigurationProperties 绑定嵌套类时的空指针问题。
我通过复现 Bug → 阅读 PropertySources 绑定逻辑源码 → 定位到 DefaultConversionService 缺少对嵌套路径的处理 → 提交修复。
这个 PR 在 3 天内被合并，还收到了 Spring 团队的感谢。"

重点：
1. 具体的问题是什么
2. 你如何分析和定位
3. 你用了什么方案修复
4. 结果如何
```
