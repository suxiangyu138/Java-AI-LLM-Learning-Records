## 1. 技术文档的价值

| 价值 | 说明 |
|------|------|
| **降低认知成本** | 别人花1小时读文档 vs 花1周读代码 |
| **减少重复沟通** | 文档回答了80%的常见问题 |
| **知识传承** | 人走了文档还在，不是"离职=知识消失" |
| **提升个人影响力** | 写出好文档是技术影响力的放大器 |

> ⚠️ 代码会告诉你"What"和"How"，但文档和注释才能告诉你"Why"。

## 2. 文档分类与写作模板

### 2.1 文档金字塔

```
        ╱   RFC/ADR   ╲      架构决策记录（极少，每决策一个）
       ╱  架构设计文档   ╲     重大架构变更（少量）
      ╱  技术方案文档      ╲    每个功能模块一个（适量）
     ╱  API文档+README     ╲   每个服务/接口必须有
    ╱   代码注释             ╲  每一行需要解释的代码
   ╱────────────────────────────╲
```

### 2.2 README 标准模板

```markdown
# 项目名
一句话描述项目是做什么的

## 快速开始
```bash
git clone xxx && cd xxx && mvn spring-boot:run
```

## 功能特性
- 特性1
- 特性2

## 技术栈
- Java 17 + Spring Boot 3.x
- MySQL + Redis + RocketMQ

## 项目结构
src/main/java/com/example/
├── controller/    # REST API
├── service/       # 业务逻辑
├── repository/    # 数据访问
├── config/        # 配置
└── common/        # 公共类

## API文档
启动后访问 http://localhost:8080/doc.html

## 部署
参考 docs/deployment.md

## 贡献指南
参考 CONTRIBUTING.md
```

### 2.3 设计文档关键要素

> 设计文档最核心的价值不是"记录做了什么"，而是**记录当初为什么做了这个决策**。

```markdown
# 设计文档：[功能名称]

## Context（背景）
- 为什么需要这个功能？（业务驱动力）
- 有哪些约束？（时间、技术栈、兼容性）
- 相关方是谁？

## Decision（决策）
- 我们决定怎么做？
- 为什么选择这个方案？（对比了哪些方案）
- 架构图/时序图（一图胜千言）

## Consequences（后果）
- 正面：解决了什么问题
- 负面：引入了什么新复杂度/技术债务
- 风险：什么情况下这个决策需要重新审视
```

## 3. 代码注释规范

### 3.1 什么需要注释

| 需要注释 | 不需要注释 |
|----------|-----------|
| **WHY** 为什么这样实现 | ~~WHAT~~ 代码已经说了做什么 |
| 非显而易见的逻辑 | ~~HOW~~ 读代码就能知道的实现 |
| 临时方案/TODO/FIXME | 冗余的Javadoc（getter/setter） |
| 公开API（Javadoc） | 每行都注释 |
| 魔法数字的来源 | — |

### 3.2 注释示例

```java
// ❌ 无用注释
/** 设置用户名 */
public void setUsername(String username) { this.username = username; }

// ✅ 有价值的注释
/**
 * 计算订单总价。
 * 注意：优惠券折扣在总价计算后才应用，因此此方法返回的是折前价格。
 * 如果订单包含预售商品，预售商品的价格按定金计算而非全款。
 */
public BigDecimal calculateTotalPrice(Order order) { ... }

// ✅ TODO格式：JIRA号 + 责任人 + 日期
// TODO(PROJ-1234, zhangsan, 2024-02-01): 临时方案，后续需迁到配置中心

// ✅ 解释"为什么"
// 使用手动提交而非自动提交，因为需要在同一个事务中
// 发送MQ消息——如果MQ发送失败，整个事务回滚
```

## 4. API文档写作

### 4.1 接口文档标准要素

```markdown
## GET /api/users/{id} — 获取用户详情

**描述**：根据用户ID获取用户基本信息

**路径参数**
| 参数 | 类型 | 必填 | 说明 |
|------|------|:---:|------|
| id | Long | ✅ | 用户ID |

**响应示例**
```json
{
  "code": 200,
  "data": {
    "id": 1,
    "name": "张三",
    "email": "zhangsan@example.com",
    "createdAt": "2024-01-01T00:00:00"
  }
}
```

**错误码**
| code | 说明 |
|------|------|
| 404 | 用户不存在 |
| 400 | 用户ID格式错误 |

**注意事项**
- 已注销用户返回 404
- 非公开用户字段（手机号）不返回
```

### 4.2 Swagger注解速查

```java
@Operation(summary = "获取用户详情", description = "根据用户ID获取用户基本信息")
@ApiResponses({
    @ApiResponse(responseCode = "200", description = "成功"),
    @ApiResponse(responseCode = "404", description = "用户不存在")
})
@GetMapping("/api/users/{id}")
public ApiResponse<User> getUser(
    @Parameter(description = "用户ID", example = "1")
    @PathVariable Long id) {
    ...
}
```

## 5. 文档维护与版本管理

### 5.1 文档即代码

```text
原则：
1. 文档和代码放在同一个仓库（docs/ 目录或 *.md 文件）
2. 文档变更走和代码一样的PR流程
3. 代码变更时同步更新相关文档（在PR Checklist中强制）
4. 文档有Owner（谁写了谁负责维护）

❌ 反模式：
  - 用Word/Confluence写设计文档（无法Git追溯、无法Review）
  - "等我有空再补文档"（永远不会补）
```

### 5.2 文档过期提示

```markdown
<!-- 放在文档头部 -->
> ⚠️ 本文档最后更新于 2024-01-15，如有疑问请联系 @zhangsan
```

## 6. 常见写作误区

| 误区 | 改进 |
|------|------|
| "这个很简单，不用写文档" | 简单是相对的——对写的人简单，对读的人不一定 |
| 只写WHAT不写WHY | 代码已经说了WHAT，文档的价值在于WHY |
| 文档太长没人看 | 分层：TL;DR(30秒) → 正文(5分钟) → 附录(需要时读) |
| 画图用PPT截图 | 用Mermaid/PlantUML（文本→可Git管理+可搜索） |
| 写完不Review | 请没参与开发的人读一遍，看能不能理解 |

### Mermaid 架构图示例

```markdown
​```mermaid
sequenceDiagram
    User->>OrderService: POST /api/orders
    OrderService->>InventoryService: 扣减库存
    InventoryService-->>OrderService: 扣减成功
    OrderService->>MQ: 发送延迟消息(30min)
    OrderService-->>User: 订单创建成功
    
    Note over MQ,OrderService: 30分钟后
    MQ->>OrderService: 超时消息
    OrderService->>OrderService: 检查支付状态
    alt 未支付
        OrderService->>InventoryService: 恢复库存
    else 已支付
        OrderService->>OrderService: 忽略
    end
​```
```

> 🎯 **衡量文档质量的唯一标准**：一个没有参与开发的人，读完文档后能否理解系统并开始贡献代码。
