## 1. 测试金字塔

### 1.1 金字塔结构

```
测试金字塔（2026 标准配比）：
  单元测试 70%：毫秒级、不依赖外部资源
  集成测试 20%：真实 DB/MQ（TestContainers）
  E2E 测试 10%：核心业务链路（慢/脆）

⚠️ 面试必答：
"测试金字塔 70/20/10——
 单元多（快）、集成中（真环境）、
 E2E 少（慢且脆）；微服务补契约测试。"
```

### 1.2 为什么这个比例

```
单元测试：
  快（毫秒）→ 可频繁跑（每次提交）
  定位准（知道哪坏了）

E2E 测试：
  慢（分钟）→ 只能少量
  脆（环境依赖）→ 维护成本高

⚠️ 面试必答：
"'快测试多跑、慢测试少跑'——
 金字塔的配比是'成本 vs 价值'的最优解；
 反模式：冰淇淋塔（E2E 多单元少）。"
```

## 2. 单元测试

### 2.1 Java 单元测试栈

```java
// JUnit 5 + Mockito（Java 标准组合）
import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.*;

class OrderServiceTest {

    @Test
    void 金额不足时抛业务异常() {
        // ① 准备（Given）
        OrderService service = new OrderService(mockRepo());
        // ② 执行（When）
        assertThrows(BizException.class,
            () -> service.create(new Order(100)));
        // ③ 断言（Then）
    }

    @Test
    void 调用仓储保存订单() {
        OrderRepo repo = mock(OrderRepo.class);
        OrderService service = new OrderService(repo);
        service.create(new Order(10));
        verify(repo).save(any(Order.class));    // 验证调用
    }
}
```

### 2.2 单元测试原则

```
AAA 模式：Arrange（准备）→ Act（执行）→ Assert（断言）

⚠️ 反模式：
  ❌ 测试依赖真实 DB/网络（那是集成测试）
  ❌ 一个测试测多个行为（应拆）
  ❌ 断言实现细节（应断言行为）

⚠️ 面试必答：
"单元测试三原则——AAA 结构、
 只测单类行为（mock 外部）、
 断言行为而非实现；
 好测试 = 快速 + 独立 + 可读。"
```

## 3. 集成测试与 TestContainers

### 3.1 TestContainers（2026 标准）

```java
// ⚠️ TestContainers：测试用真实容器（DB/MQ/Redis）
// 解决"测试环境与生产不一致"
@SpringBootTest
@Testcontainers
class OrderIntegrationTest {

    // ① 启动真实 MySQL 容器
    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.4");

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", mysql::getJdbcUrl);
    }

    @Test
    void 订单落库后可查询() {
        // 真实数据库集成验证
    }
}
```

> 🎯 **要点**：TestContainers = "测试环境与生产一致"——容器起真实中间件，避免 H2 模拟与生产差异。2026 集成测试标配。

## 4. 契约测试与 E2E

### 4.1 契约测试（微服务关键）

```
契约测试：验证"服务间 API 约定"一致
  Spring Cloud Contract / Pact

价值：
  消费者与提供者独立开发（API-first 配套）
  提供者改动 → 契约测试即时发现破坏

⚠️ 面试必答：
"契约测试 = 微服务的'接口协议测试'——
 提供者按契约实现、消费者按契约 mock，
 防止接口破坏在联调期才暴露。"
```

### 4.2 E2E 测试

```
E2E（端到端）：
  完整用户链路（UI → API → DB）
  工具：Playwright / Cypress / Selenium

⚠️ 原则：
  只覆盖核心业务链路（10%）
  独立测试环境（staging）
  稳定选择器（data-testid）

⚠️ 面试必答：
"E2E 只测核心链路、放独立环境、
 用稳定选择器——慢且脆所以少而精。"
```

## 5. 覆盖率与质量门禁

### 5.1 覆盖率指标

```
覆盖率类型：
  行覆盖（statement）
  分支覆盖（branch）⚠️ 更有意义
  方法覆盖

目标（2026）：
  单元测试覆盖率 ≥ 80%（有意义覆盖）
  核心模块 100%（支付/权限等）

⚠️ 面试必答：
"覆盖率是手段不是目标——
 追求 80% '有意义覆盖'（关键分支/核心逻辑），
 不是 100% 行覆盖（可能全是无意义断言）。"
```

### 5.2 门禁配置（JaCoCo）

```java
// pom.xml：JaCoCo 覆盖率门禁
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <executions>
        <execution>
            <goals><goal>check</goal></goals>
            <configuration>
                <rules>
                    <rule>
                        <element>BUNDLE</element>
                        <limits>
                            <limit>
                                <counter>BRANCH</counter>   <!-- ⚠️ 分支覆盖 -->
                                <value>COVEREDRATIO</value>
                                <minimum>0.80</minimum>    <!-- 80% -->
                            </limit>
                        </limits>
                    </rule>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
<!-- ⚠️ 覆盖率不达标 → 构建失败（质量门禁） -->
```

## 6. TDD 与测试文化

### 6.1 TDD 流程

```
TDD（测试驱动开发）红绿重构：
  ① 写失败测试（红）
  ② 最小实现让测试通过（绿）
  ③ 重构（保持测试绿）

⚠️ 面试必答：
"TDD 红绿重构三循环——
 先写测试（明确需求）、
 最小实现（快速通过）、
 重构（保持质量）。
 好处：测试先行 = 设计先行。"
```

### 6.2 测试文化

```
企业测试文化：
  ① 每次提交跑测试（CI 门禁）
  ② 新代码必须有测试（评审检查）
  ③ 测试与代码同仓库（同步演进）
  ④ 慢测试持续优化（不累积）

⚠️ 面试必答：
"测试文化 = '测试是代码的一部分'——
 与业务代码同库同步演进，
 CI 强制 + 评审检查保证落地。"
```
