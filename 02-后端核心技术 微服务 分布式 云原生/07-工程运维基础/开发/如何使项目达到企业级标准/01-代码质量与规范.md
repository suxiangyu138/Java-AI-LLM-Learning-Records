## 1. 编码规范体系

### 1.1 规范层次

```
编码规范三层：
  ① 风格规范：命名、格式（统一工具强制）
  ② 设计规范：SOLID、分层、单一职责
  ③ 领域规范：业务规则、错误处理约定

⚠️ 面试必答：
"规范三层——风格（工具强制定）、
 设计（SOLID/分层）、领域（业务约定）。
 风格靠工具、设计靠评审、领域靠文档。"
```

### 1.2 Java 企业规范要点

| 维度 | 规范 | 说明 |
|------|------|------|
| 命名 | 驼峰 + 语义化 | 类 PascalCase、方法 camelCase |
| 方法 | ≤ 20 行 | 单一职责，超长即拆 |
| 接口 | 最小化 | 只暴露必要方法 |
| 错误 | 异常分层 | 业务异常/系统异常分离 |
| 依赖 | 显式声明 | 禁止隐式/循环依赖 |
| 注释 | 必要而非冗余 | 说明"为什么" |
| 包结构 | 分层清晰 | controller/service/repository |

```java
// 规范示例：分层调用（禁止跨层）
// Controller → Service → Repository
// ⚠️ 禁止 Controller 直接操作 Repository

// 错误处理规范：业务异常 vs 系统异常
public class BizException extends RuntimeException { }   // 业务（可预期）
// 系统异常：运行时异常 + 全局异常处理器
```

## 2. API-first 设计

### 2.1 设计先行

```
API-first = 先设计 API 再实现（契约驱动）

流程：
  ① 定义 API 契约（OpenAPI 文档）
  ② 评审契约（团队确认）
  ③ 生成文档/客户端/桩
  ④ 实现

⚠️ 面试必答：
"API-first = 契约先行——
 接口文档（OpenAPI）是团队共识，
 前后端并行开发、契约测试保证一致。"
```

### 2.2 RESTful API 规范

| 原则 | 示例 |
|------|------|
| 资源命名（复数名词） | `/users`、`/orders` |
| HTTP 方法语义 | GET 查/POST 建/PUT 改/DELETE 删 |
| 状态码语义 | 200/201/400/401/403/404/500 |
| 版本化 | `/api/v1/users` |
| 统一响应 | `{code, message, data}` |
| 分页 | `?page=1&size=20` + 元信息 |

```
⚠️ 面试必答：
"RESTful 规范五要点——资源化命名、
 方法语义、状态码、版本化、统一响应。
 版本化是破坏性变更的护栏。"
```

## 3. Code Review 流程

### 3.1 审查原则

```
Code Review 最佳实践：
  ① 小 PR（< 300 行）——大 PR 审不动
  ② 每次提交必审（质量门禁）
  ③ 关注设计 > 挑错字
  ④ 及时反馈（24 小时内）
  ⑤ 无指责文化（对代码不对人）

⚠️ 面试必答：
"Code Review 黄金法则——PR 要小（好审）、
 必须审（门禁）、看设计（不只是 bug）、
 快反馈（24h）、对事不对人。"
```

### 3.2 审查清单

```
✅ 逻辑正确性：边界/异常处理
✅ 设计合理性：分层/职责/复用
✅ 性能隐患：N+1 查询、循环内请求
✅ 安全问题：注入/越权/敏感信息
✅ 测试覆盖：新逻辑有测试
✅ 代码规范：命名/格式（工具已查）
✅ 兼容性：接口变更影响评估
```

## 4. 静态检查与质量门禁

### 4.1 静态检查工具

| 语言 | 工具 | 作用 |
|------|------|------|
| Java | Checkstyle / SpotBugs | 风格/缺陷 |
| Java | SonarQube | 综合质量（复杂度/重复/坏味道） |
| JS/TS | ESLint / tsc | 风格/类型 |
| 通用 | CodeQL | 安全扫描 |
| 依赖 | Trivy / OWASP DC | 漏洞扫描 |

```java
// Maven 集成：checkstyle + spotbugs 绑定 verify 阶段
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-checkstyle-plugin</artifactId>
    <configuration>
        <failOnViolation>true</failOnViolation>   <!-- ⚠️ 违规即失败 -->
    </configuration>
</plugin>
```

### 4.2 分层质量门禁（2026）

```
三层门禁：
  ① 代码级：静态分析 + 安全扫描（CI 必过）
  ② 验证级：单元测试覆盖率 ≥ 80% + 集成测试 + 契约测试
  ③ 部署级：健康检查 + 性能基准 + 合规检查

⚠️ 面试必答：
"质量门禁三层——代码、验证、部署，
 每层不通过即阻断；覆盖率 80% 是
 '有意义覆盖'而非 100% 行覆盖。"
```

## 5. 技术债务管理

### 5.1 债务识别

```
技术债务来源：
  ① 赶工妥协（注释 TODO、跳过测试）
  ② 旧系统遗留（重复代码、硬编码）
  ③ 规范缺失（无测试的模块）

度量：
  SonarQube 技术债务估算（修复时间）
  重复代码率、圈复杂度

⚠️ 面试必答：
"技术债务要'量化 + 偿还计划'——
 用 SonarQube 估算、按风险排序、
 重构伴随功能迭代（boy-scout 原则）。"
```

### 5.2 偿还策略

```
偿还四策略：
  ① 增量重构：小步重构（不阻塞业务）
  ② 债务清单：记录并排优先级
  ③ 测试护航：重构先补测试（防回归）
  ④ 停止累积：新代码零债务（门禁兜底）

⚠️ 面试必答：
"偿还策略 = 先补测试再重构 +
 债务清单排序 + 新代码门禁兜底；
 '边重构边加测试'防重构引入 bug。"
```

> 🎯 **核心要点**：代码质量体系 = **规范三层**（风格/设计/领域）+ **API-first**（契约先行 + RESTful 五要点）+ **Code Review**（小 PR + 必须审 + 看设计）+ **三层门禁**（静态/测试/部署）+ **债务管理**（量化 + 测试护航）。"质量内建"的落地 = 规范 + 审查 + 门禁三件套。
