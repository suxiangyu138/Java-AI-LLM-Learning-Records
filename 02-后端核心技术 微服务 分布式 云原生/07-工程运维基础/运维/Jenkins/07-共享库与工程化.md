## 1. 共享库：流水线的代码复用

```text
问题：10 个服务 10 份 Jenkinsfile，同样的 Docker 构建逻辑复制 10 遍
     → 改一处构建逻辑要改 10 个仓库

共享库（Shared Library）：把公共逻辑抽成一个 Git 仓库，所有流水线引用
  仓库结构：jenkins-shared-library（独立 Git 仓库）
  配置：Manage Jenkins → Global Pipeline Libraries（指定 Git 地址 + 凭证）
```

```groovy
// 流水线里引用共享库（@Library 注解）
@Library('shared-library') _
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                mavenBuild('demo')                    // 共享库函数（一行调用）
                dockerPush('demo', "${VERSION}")      // 公共逻辑不再重复
            }
        }
    }
}
```

> 🎯 共享库的价值：**"公共逻辑一处维护，所有流水线同步升级"**——构建/推送/通知/部署的通用步骤收敛进共享库，业务 Jenkinsfile 只剩"编排"（跟"公共代码抽公共类"同一思想，[07](07-共享库与工程化.md) 是它的 CI 版）。

## 2. 共享库结构：vars 与 src

```text
共享库仓库结构（约定）：
  jenkins-shared-library/
  ├── vars/                    # 全局变量（即函数，推荐方式）
  │   ├── mavenBuild.groovy    # 用 mavenBuild(...) 调用
  │   └── dockerPush.groovy
  ├── src/                     # Groovy 类（复杂逻辑）
  │   └── com/company/ci/Utils.groovy
  ├── resources/               # 静态资源（模板文件等）
  └── Jenkinsfile              # 共享库自身 CI（自举）
```

```groovy
// vars/mavenBuild.groovy（vars 函数：定义 call 方法）
def call(String project, String opts = '-B clean package') {
    sh "mvn -B ${opts}"
    // 公共逻辑：缓存/报告/超时统一处理
    junit 'target/surefire-reports/*.xml'
}

// vars/dockerPush.groovy
def call(String image, String version) {
    withCredentials([usernamePassword(credentialsId: 'harbor-cred',
            usernameVariable: 'H_USER', passwordVariable: 'H_PASS')]) {
        sh """
            docker build -t harbor.local/${image}:${version} .
            docker login harbor.local -u \$H_USER -p \$H_PASS
            docker push harbor.local/${image}:${version}
        """
    }
}
```

| 组织方式 | 适用 | 调用 |
|---------|------|------|
| `vars/*.groovy` | 简单函数（推荐 80% 场景） | `函数名(args)` |
| `src/` 类 | 复杂对象/状态 | `new Utils().method()` |
| `resources/` | 模板/配置文件 | `libraryResource()` |

> 🎯 推荐模式：**vars 函数 + 约定命名**——`mavenBuild`、`dockerPush`、`notifySlack`、`deployK8s` 这类"动作函数"，Jenkinsfile 变成可读的编排清单。

## 3. 多分支流水线

```groovy
// 多分支流水线（Multi-branch Pipeline）——每分支自动建流水线
// 新 Job 类型：Multi-branch Pipeline
// 配置：Git 地址 + 分支发现策略 + Jenkinsfile 路径

// Jenkinsfile 里用 branch 判断分支行为：
pipeline {
    agent any
    triggers {
        // 分支索引定期扫描（发现新分支自动建流水线）
        pollSCM('H/5 * * * *')
    }
    stages {
        stage('Build') {
            when { branch 'main' }          // 仅主分支构建
            steps { sh 'mvn -B package' }
        }
        stage('Deploy') {
            when {
                branch 'main'               // 主分支才部署
                environment name: 'DEPLOY', value: 'true'
            }
            steps { sh 'deploy.sh' }
        }
        stage('Tag 版本') {
            when { tag pattern: 'v*', comparator: 'REGEXP' }   // 打 tag 时触发
            steps { sh 'release.sh' }
        }
    }
}
```

| 多分支能力 | 说明 |
|-----------|------|
| 分支自动发现 | 新分支自动建流水线（按发现策略） |
| 分支级构建 | `when { branch }` 控制各分支行为 |
| PR 检查 | PR 分支自动跑构建（提交流水线） |
| Tag 触发 | `when { tag }` 打 tag 触发发布 |

> 🎯 面试点：**"多分支流水线 = 分支即环境"**——feature 分支构建验证、main 分支部署测试、tag 触发发布，一个 Job 自动管理所有分支的流水线（不再手工为分支建 Job）。

## 4. Webhook 与触发工程化

```text
触发工程化（从"轮询"到"推送"）：
  ❌ SCM Polling：每 5 分钟查一次 Git（延迟 + 空轮询）
  ✅ Webhook：push 瞬间通知（零延迟）

Webhook 配置（GitLab 示例）：
  GitLab → Settings → Webhooks
  URL: http://jenkins:8080/project/{job-path}
  Secret Token: 与 Jenkins Job 配置一致
  触发事件：Push events / Merge request events
```

```groovy
// Jenkinsfile 里声明触发器（GitLab 插件）
pipeline {
    triggers {
        gitlab(triggerOnPush: true,
               triggerOnMergeRequest: true,
               secretToken: '${GITLAB_WEBHOOK_SECRET}')   // 凭证引用
    }
}
```

| 触发场景 | 工程化做法 |
|---------|-----------|
| push 触发 | Webhook（非轮询） |
| PR/MR 触发 | Webhook + 分支流水线 |
| 定时构建 | cron（`H` 哈希分钟防同时挤爆） |
| 依赖触发 | 上游 Job 成功后触发（build 步骤） |
| 手动发布 | 参数化手动触发（带审批，见发布篇） |

> ⚠️ Webhook 三个坑：① **Jenkins URL 必须对 Git 平台可达**（内网地址用内网 Webhook）；② 安全令牌要配对（Git 平台 + Jenkins 双侧配置）；③ 公网 Jenkins 必须 HTTPS + 鉴权（[04 §6](04-凭证与安全.md) 加固清单）。

## 5. Jenkinsfile 工程规范

```text
Jenkinsfile 工程规范（团队标准）：
  □ 存放位置：仓库根目录（或 Jenkinsfile/ 目录）
  □ 命名：Jenkinsfile（默认）/ Jenkinsfile.build（多流水线）
  □ 版本控制：Jenkinsfile 进 Git（随代码走，走 PR 审查）
  □ 阶段命名：动词 + 对象（Checkout / Build / Test / Deploy）
  □ 参数化：环境/分支参数化（02 §6）
  □ 凭证引用：withCredentials + 语义化 ID（04）
  □ 超时兜底：options { timeout } 必须
  □ 清理：post { always { cleanWs() } }
  □ 复用：公共逻辑进共享库（§1）
  □ 可读性：每个 stage 有 purpose（why 注释）
```

```groovy
// 规范示例：带 purpose 的 stage
stage('Build') {
    // purpose: 编译 + 打包，产出 jar 与镜像
    steps { mavenBuild('demo') }
}
```

> 🎯 团队工程化本质：**Jenkinsfile 是"代码"，不是"配置"**——进 Git、走审查、可测试、可复用。2026 的 AI 辅助趋势（Copilot 生成流水线）也要求 Jenkinsfile 结构化清晰，机器才好生成与维护。

## 6. 流水线即代码的组织

```text
组织演进三阶段：
  ① 单体：每个仓库一份 Jenkinsfile，逻辑内嵌
  ② 共享库：公共逻辑抽离，Jenkinsfile 只剩编排
  ③ 平台化：流水线模板（参数化模板）+ 自服务（开发者提交参数建流水线）

平台化价值：
  · 新服务上线 = 提交配置（不写流水线代码）
  · 规范强制（模板内置质量门禁/安全扫描）
  · 审计清晰（配置变更走审批）
```

| 阶段 | 形态 | 适用规模 |
|------|------|---------|
| 单体 | 仓库自带 Jenkinsfile | 小团队 |
| 共享库 | Jenkinsfile + 共享库 | 中型（推荐） |
| 平台化 | 模板 + 自服务 | 大型组织 |
