## 1. 凭证为什么是头等大事

```text
Jenkins 是"机器人的账房"：
  · 持有 Git 凭证（代码读写）
  · 持有制品库凭证（推送镜像/制品）
  · 持有服务器凭证（SSH 部署）
  · 持有云凭证（K8s/云 API）

一个凭证管理漏洞 = 攻击者拿到整条发布链的钥匙
  · Jenkins CVE 历史 + 插件漏洞 = 攻击面
  · 默认管理员/弱密码 = 一键沦陷

正确姿势：凭证集中在 Credentials 库 → 按需最小授权 → 日志永不出现明文
```

> 🎯 安全认知：**"Jenkins 的安全等级 = 它持有凭证的安全等级"**——把 Jenkins 当"钥匙保管箱"来治理，而不是"一个 CI 工具"。

## 2. Credentials 五类凭证

| 凭证类型 | 存储内容 | 典型场景 |
|---------|---------|---------|
| **Username with password** | 账号密码 | Git 账号/Harbor 登录 |
| **SSH Username with private key** | SSH 私钥 | Git SSH/GitLab/服务器部署 |
| **Secret text** | 任意字符串 | API Token/密钥 |
| **Secret file** | 整个文件 | kubeconfig/证书文件 |
| **Certificate** | 证书 | 客户端证书认证 |

```groovy
// 凭证使用（withCredentials 注入，绝不写死在脚本）
pipeline {
    agent any
    stages {
        stage('Push Image') {
            steps {
                withCredentials([
                    usernamePassword(credentialsId: 'harbor-cred',
                                     usernameVariable: 'H_USER',
                                     passwordVariable: 'H_PASS'),
                    string(credentialsId: 'slack-token',
                           variable: 'SLACK_TOKEN')
                ]) {
                    sh 'docker login -u $H_USER -p $H_PASS harbor.local'
                    sh 'docker push harbor.local/demo:v1'
                    sh 'curl -H "Authorization: Bearer $SLACK_TOKEN" ...'
                }
            }
        }
    }
}
```

> ⚠️ **凭证三不**：① 不写死在 Jenkinsfile/Groovy；② 不打进构建日志（`echo $H_PASS` 都是泄漏）；③ 不放进仓库。`withCredentials` 自动屏蔽日志中的敏感值（`****`），这是它必须用的原因。

## 3. withCredentials：安全注入

```groovy
// 凭证注入的完整姿势
withCredentials([
    usernamePassword(credentialsId: 'gitlab-cred',
                     usernameVariable: 'GIT_USER',
                     passwordVariable: 'GIT_PASS'),
    sshUserPrivateKey(credentialsId: 'deploy-key',
                      keyFileVariable: 'SSH_KEY',          // 私钥写成文件
                      usernameVariable: 'SSH_USER'),
    file(credentialsId: 'kube-config', variable: 'KUBECONFIG')
]) {
    // ① shell 里用环境变量（自动屏蔽日志）
    sh 'docker login -u "$GIT_USER" -p "$GIT_PASS" registry.gitlab.com'

    // ② SSH 部署（私钥文件）
    sh 'ssh -i "$SSH_KEY" -o StrictHostKeyChecking=no $SSH_USER@server "deploy.sh"'

    // ③ K8s 部署（kubeconfig 文件）
    sh 'kubectl --kubeconfig "$KUBECONFIG" apply -f k8s/'
}
```

| 凭证场景 | 正确姿势 |
|---------|---------|
| Git 账号 | Jenkins 系统 Git 配置引用 credentialId |
| 制品库推送 | withCredentials + docker login |
| 服务器部署 | SSH 私钥凭证 + ssh -i |
| K8s 部署 | Secret file（kubeconfig）+ --kubeconfig |
| 外部 API | Secret text + 环境变量 |

> 🎯 凭证生命周期：**创建（Manage Jenkins → Credentials）→ 授权（权限矩阵控制谁能用）→ 轮换（定期更新）→ 回收（离职/泄露立即删）**。2026 实践：凭证 ID 用语义化命名（`harbor-cred`/`prod-deploy-key`），别用随机串。

## 4. 权限矩阵：谁能用什么

```text
Jenkins 权限模型（Authorization）：
  · 默认：Anyone can do anything（❌ 必须改！）
  · 推荐：Matrix-based security（矩阵授权）

矩阵授权维度：
  · 全局：Administer / Read / Build / Configure 等
  · Job 级：Build / Configure / Delete / Workspace
  · 按用户/用户组 逐格打勾
```

```text
最小权限矩阵（生产推荐）：
  管理员组：Administer（全部）
  开发者组：Job Read + Build（构建）+ Workspace（看日志）
  运维组：Configure（改配置，无 Administer）
  访客：Read only（只读）

配置入口：Manage Jenkins → Security → Authorization
```

| 权限项 | 说明 |
|--------|------|
| Administer | 全部管理（少给人） |
| Build | 触发构建 |
| Configure | 修改 Job 配置 |
| Read | 查看 |
| Workspace | 查看工作区文件 |
| Credentials | 查看/使用凭证（**单独管理**） |

> ⚠️ 权限常见事故：**开发要"看日志"被给了 Administer**——正确给 `Read + Workspace` 即可。矩阵授权坚持"最小够用"，Jenkins 权限不是福利。

## 5. Agent 安全边界

```text
Agent 是信任的延伸：
  · Agent 上执行的流水线代码（Jenkinsfile 来自仓库！）可能被恶意修改
  · 仓库被攻破 → Jenkinsfile 被注入恶意 sh → Agent 执行
  · Agent 能访问的（网络/凭证/文件）= 攻击者的

信任模型：
  ① Jenkinsfile 来源可信？（受保护分支禁止 PR 注入）
  ② Agent 最小权限（专用用户，别用 root）
  ③ Agent 与生产网络隔离（构建机 ≠ 生产机）
```

| Agent 安全措施 | 说明 |
|---------------|------|
| 专用运行用户 | 别 root 跑 Agent（Docker 场景 `user: root` 需评估） |
| 网络隔离 | Agent 仅能访问必要服务（Git/制品库） |
| 动态 Agent | 一次性容器/Pod（用完即焚，最安全，见 06） |
| 凭证不出 Master | Agent 上不落凭证文件（withCredentials 注入环境变量） |
| 分支保护 | 受保护分支的 Jenkinsfile 才可信（PR 合并前审查） |

> ⚠️ 2026 供应链安全背景：**"流水线代码是攻击链一环"**（CI 投毒——[OWASP 供应链篇](../../../09-Web开发全流程/Web%20高阶知识/07-Web安全攻防.md) 的 A03 类别）——Jenkinsfile 与依赖一样需要审查，受保护分支 + PR 评审是底线。

## 6. Jenkins 安全加固清单

```text
生产上线安全自检（照着打勾）：
  □ 默认管理员已改强密码 + 启用二次认证（2FA 插件）
  □ 授权从 "Anyone can do anything" 改为矩阵权限
  □ 凭证最小授权 + 定期轮换（无"永久共享"凭证）
  □ Jenkins 端口不暴露公网（内网 + 反向代理 + HTTPS）
  □ CSRF 保护开启（默认开，别关）
  □ 插件最小化 + 定期安全更新（CVE 关注）
  □ 禁用 Script Console 的普通用户访问（Groovy 即 RCE）
  □ Agent 专用用户（非 root）+ 网络隔离
  □ 构建日志脱敏（withCredentials 统一注入）
  □ 定期备份（含凭证库，见 08）
  □ 升级：LTS 基线 + 安全补丁（Java 21 环境）
```

| 高危项 | 风险 | 解法 |
|--------|------|------|
| Script Console 公开 | **Groovy 控制台 = 远程代码执行** | 仅管理员 |
| 公网裸奔 8080 | 爆破/漏洞利用 | 反代 + HTTPS + 内网 |
| 插件泛滥 | 攻击面扩大 | 最小化 + 更新 |
| 凭证写日志 | 泄露 | withCredentials |
| 弱密码/默认配置 | 一键沦陷 | 强密码 + 2FA + 矩阵 |

> 🎯 一句话安全观：**"Jenkins 的攻击面 = Web 面 + 插件面 + 凭证面"**——三个面都按最小化治理；尤其记住 **Script Console（脚本控制台）是 RCE 入口**，绝不给普通用户。
