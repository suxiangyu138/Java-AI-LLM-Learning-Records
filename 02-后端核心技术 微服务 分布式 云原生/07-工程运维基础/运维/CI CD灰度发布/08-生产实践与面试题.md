## 1. 发布平台四维度评估

选择/自建发布平台时评估四个维度（2026 企业视角）：

| 维度 | 关键问题 | 反面案例 |
|------|---------|---------|
| **审批分层** | 按环境/风险/变更类型分层审批了吗？ | 所有变更走同一条审批链（低效） |
| **灰度原生能力** | 放量节奏/指标观测/异常判断/自动暂停回退是否平台内置？ | 各团队自己拼脚本（不可控） |
| **回滚可执行性** | 回滚的是镜像/配置/数据库联动变更？能否标准化复用？ | 回滚靠人肉（发布时手忙脚乱） |
| **审计闭环** | 谁发了哪个版本、到哪个环境、审批人、是否灰度、是否回滚，是否一条记录？ | 发布记录散落（出问题无从追溯） |

```text
自建 vs 采购判断：
  团队 < 20 人：用现成工具组合（GitLab CI + ArgoCD）足够
  大团队/强合规：评估企业级发布平台（四维度打分）
  关键：平台能力解决"受控"，不是"能发版"就行
```

> 🎯 **四维度的本质**：发布平台不是"自动执行工具"，是**"生产变更控制面"**——审批、灰度、回滚、审计四位一体。

## 2. 工具链组合方案

| 方案 | 组合 | 适合 |
|------|------|------|
| 轻量起步 | GitHub Actions + Harbor + kubectl | 小团队/单体 |
| GitLab 全家桶 | GitLab CI + Harbor + ArgoCD | 已用 GitLab |
| 传统过渡 | Jenkins + Harbor + ArgoCD | 存量 Jenkins |
| **云原生标配** | GitLab CI/GitHub Actions + Harbor + ArgoCD + Argo Rollouts | **推荐** |
| 极致云原生 | Tekton + Harbor + ArgoCD + Rollouts + Istio | 高要求团队 |

```text
配套组件（安全与运维）：
  Trivy（镜像扫描）/ SonarQube（代码质量）
  Sealed Secrets / cert-manager（安全）
  Prometheus + Grafana（监控，见日志监控指标体系）
```

> 💡 **选型原则**：组合越简单越好——每加一个工具就多一份运维成本；**先跑通"构建→镜像→部署→回滚"最小闭环，再叠加灰度/GitOps**。

## 3. 落地路线图

```text
第一阶段：最小闭环（1 周）
  代码提交 → 自动构建测试 → 镜像推送 → 手动部署 → 手动回滚
  产出：CI 跑通 + 部署可复现

第二阶段：门禁与质量（1-2 周）
  测试门禁 + SonarQube + Trivy 扫描
  产出：不通过不能上线

第三阶段：灰度发布（2 周）
  Argo Rollouts 金丝雀（10-30-60-100）+ 指标自动回滚
  产出：发布可控可回滚

第四阶段：GitOps（2 周）
  ArgoCD 管理部署 → CI 只改 Git
  产出：部署走 Code Review + 审计闭环

第五阶段：平台化（持续）
  发布平台/审批分层 → 多环境联动 → 自动决策
```

| 阶段 | 关键度量 |
|------|---------|
| 最小闭环 | 交付周期（提交→上线） |
| 门禁 | 上线成功率/漏洞拦截数 |
| 灰度 | 发布故障率/回滚次数 |
| GitOps | 部署自动化率/审计覆盖率 |

## 4. 落地检查清单

### 4.1 流水线检查

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | Pipeline as Code | 流水线在 Git（可审查） |
| 2 | 镜像 tag 唯一 | 版本/流水线 ID（可回滚） |
| 3 | 门禁是阻断 | exit-code/失败即停（非提醒） |
| 4 | 发布按钮 | 生产 manual/input（持续交付） |
| 5 | 失败回滚 | post/rollout 失败处理 |
| 6 | 凭证管理 | 零硬编码（secrets/credentials） |

### 4.2 发布检查

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | 发布策略明确 | 滚动/灰度/蓝绿按变更类型选 |
| 2 | 灰度三件套 | 节奏 + 指标 + 自动回滚 |
| 3 | DB 兼容 | 新旧版本共用数据库 |
| 4 | 回滚演练 | 灰度异常演练过 |
| 5 | 发布可审计 | 谁/何时/什么版本/是否回滚 |
| 6 | 监控联动 | 发布后指标对比（灰度 vs 稳定） |

## 5. 高频避坑清单

| # | 坑 | 规避 |
|---|----|------|
| 1 | CI 直接 kubectl | CI 只改 Git（GitOps）或受限权限 |
| 2 | 镜像 latest | 版本/流水线 ID（无法回滚） |
| 3 | 门禁是提醒 | 阻断（exit-code 1） |
| 4 | 生产自动部署 | 先持续交付（发布按钮） |
| 5 | 灰度只看绝对值指标 | 灰度 vs 稳定组对比 |
| 6 | 发布不带 DB 兼容 | 迁移向后兼容是前置条件 |
| 7 | 回滚只回镜像 | 配置/数据联动回滚要设计 |
| 8 | 密钥进 Git/镜像 | Sealed Secrets + 扫描 |
| 9 | 平台能力堆砌 | 从最小闭环起步再叠加 |
| 10 | 忽略审计 | 发布全链路留痕（四维度） |

## 6. 面试题

| 题目 | 答题要点 |
|------|---------|
| CI/CD/DevOps 区别？ | CI=集成测试；CD=交付（可发布）/部署（自动上线）；DevOps=文化 |
| Pipeline as Code 是什么？ | 流水线定义进 Git（Jenkinsfile/.gitlab-ci.yml），版本化可审查 |
| 质量门禁怎么设计？ | 分层：提交（编译单测）→ PR（扫描覆盖率）→ 发布（依赖镜像扫描）→ 生产（灰度指标）；门禁必须阻断 |
| 蓝绿 vs 金丝雀？ | 蓝绿=双环境切换（秒级回滚、双倍资源）；金丝雀=渐进放量（10-30-60-100、指标观察） |
| 灰度三件套？ | 放量可控 + 指标可观测 + 异常自动回滚 |
| 深红发布是什么？ | 按请求属性（Header/Cookie/用户组）精确路由 + 渐进染色 + Git 回滚 |
| 回滚三层？ | 代码（镜像）、配置（Nacos 历史）、数据（迁移逆向，能前修不后滚） |
| GitOps 是什么？ | Git 为唯一事实来源，控制器自动同步集群；部署走 Code Review |
| ArgoCD 同步原理？ | 对比 Git 期望 vs 集群实际 → 差异同步 → selfHeal 漂移纠正 |
| CI 与 GitOps 怎么协作？ | CI 只更新 Git 镜像 tag，不碰集群；ArgoCD 检测 Git 变更自动部署 |
| Argo Rollouts 有什么用？ | 金丝雀/蓝绿渐进交付 + AnalysisTemplate 指标分析自动回滚 |
| 发布平台四维度？ | 审批分层、灰度原生能力、回滚可执行性、审计闭环 |
| 镜像 tag 规范？ | 应用:版本-环境 + CI 流水线 ID；禁止 latest |
| 上线后怎么验证？ | 灰度 vs 稳定组指标对比 + 健康检查 + 冒烟测试（APIFox apifox run） |

## 7. 核心要点

> 🎯 **核心要点**：
> - 四维度评估：审批分层/灰度原生/回滚可执行/审计闭环——发布平台是"变更控制面"；
> - 五阶段落地：最小闭环 → 门禁 → 灰度 → GitOps → 平台化；
> - 推荐组合：GitLab CI/GitHub Actions + Harbor + ArgoCD + Argo Rollouts；
> - 避坑 Top3：CI 直接操作集群、镜像 latest、门禁不阻断；
> - 面试主线：概念 → Pipeline as Code → 门禁 → 发布策略 → 灰度落地 → GitOps → 平台四维度；
> - 与仓库其他体系联动：质量门禁接 APIFox 测试、监控接日志监控指标、密钥接 Git 体系。
