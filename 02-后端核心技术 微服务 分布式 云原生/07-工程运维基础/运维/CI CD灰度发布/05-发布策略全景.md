## 1. 发布策略对比总览

| 策略 | 原理 | 风险 | 回滚速度 | 资源成本 | 适用 |
|------|------|------|---------|---------|------|
| 滚动更新 | 逐个替换实例 | 中（混合期） | 分钟级 | 低 | 默认日常发布 |
| 蓝绿 | 双环境切换 | 低 | **秒级** | 双倍 | 高可用系统 |
| 金丝雀 | 小流量渐进放量 | 低 | 秒级（切流） | 中 | 新功能/大改动 |
| 深红发布 | 按属性精确路由 | 极低 | **秒级**（Git 回退） | 中 | 敏感变更/VIP |
| A/B 测试 | 分桶验证业务效果 | 低 | 秒级 | 中 | 业务实验 |

> 🎯 **选型主线**：日常小变更 → 滚动；重要发布 → 灰度；可用性极致 → 蓝绿；业务实验 → A/B；精确控制 → 深红。

## 2. 滚动更新（Rolling Update）

```text
原理：新版本实例逐个替换旧版本（K8s 默认策略）
  更新前：3 个 v1
  → 创建 1 个 v2（maxSurge=1）→ 就绪后删 1 个 v1（maxUnavailable=0）
  → 循环直到全部 v2
```

```yaml
# K8s 滚动更新配置
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1            # 最多超出期望副本数 1 个
    maxUnavailable: 0      # 不允许不可用（保证容量）
```

```bash
kubectl set image deployment/order-service app=order-service:1.0.4
kubectl rollout status deployment/order-service   # 等待完成
kubectl rollout undo deployment/order-service     # 回滚
```

| 优点 | 缺点 |
|------|------|
| 零额外资源 | 混合期新旧版本并存（兼容性问题） |
| 自动完成 | 回滚需逐个替换（分钟级） |
| 无流量切换动作 | 发布过程无法精确控制流量比例 |

> 💡 滚动更新的隐藏要求：**新旧版本必须兼容**（数据库迁移向后兼容）——混合期两个版本同时服务流量。

## 3. 蓝绿部署（Blue-Green）

```text
原理：维护两套完全独立环境（蓝=当前生产，绿=新版本）
  部署绿环境 → 验证 → 切换 Service selector → 秒级切换
```

```text
蓝绿环境：
  Blue (v1.0.3)  ← Service 当前指向
  Green (v1.0.4) ← 新版本（验证通过后切换）
  切换：Service selector version: blue → green
```

```bash
# 切换（秒级）
kubectl patch service order-service \
  -p '{"spec":{"selector":{"version":"green"}}}'

# 回滚（再切回）
kubectl patch service order-service \
  -p '{"spec":{"selector":{"version":"blue"}}}'
```

| 优点 | 缺点 |
|------|------|
| **切换秒级、回滚秒级** | 双倍资源（成本高） |
| 无混合期 | 数据库兼容仍需处理（两环境共用 DB） |
| 验证充分（绿环境全量验证） | 环境漂移风险（长期不清理） |

> ⚠️ **蓝绿的核心矛盾**：**环境是双的，数据库是单的**——数据库变更必须在两环境兼容（向后兼容迁移），否则切换后即故障。

## 4. 金丝雀/灰度发布（Canary）

### 4.1 原理与放量节奏

```text
小流量渐进放量：
  v1 (100%) → v2 (10%) → v2 (30%) → v2 (60%) → v2 (100%)
  每步观察核心指标：错误率/延迟/资源
  异常 → 自动回滚 v1（切流秒级）
```

| 放量阶段 | 流量比例 | 观察重点 |
|----------|---------|---------|
| 金丝雀启动 | v2 10% | 错误率/关键链路 |
| 扩大 | v2 30% | 延迟/资源占用 |
| 过半 | v2 60% | 容量/稳定性 |
| 全量 | v2 100% | 最终验证 |

### 4.2 实现方式

```bash
# 方式 1：副本比例（简单）
# v1 3 副本 + v2 1 副本 → v2 占 25%（Service selector 匹配两版本）
kubectl scale deployment/order-v1 --replicas=3
kubectl scale deployment/order-v2 --replicas=1   # v2 25%
kubectl scale deployment/order-v2 --replicas=3   # 逐步放大
```

```text
方式 2：权重路由（精确）
  Istio VirtualService weight: 90/10
  网关/负载均衡按权重分流
  Argo Rollouts（K8s 原生渐进交付，见 06）
```

> 🎯 **灰度核心能力三件套**：**放量可控**（比例/节奏）、**指标可观测**（错误率/延迟）、**异常自动回滚**（阈值触发）——三缺一就不是合格的灰度。

## 5. 深红发布（Dark Red Launch）

2026 年出现的精细化发布理念，脱胎于金丝雀但更精确：

```text
核心差异：
  金丝雀：按百分比随机分流
  深红：按请求属性精确路由

路由维度：
  请求头（userId、region、渠道）
  Cookie（内部员工/测试用户）
  业务属性（VIP 用户、灰度名单）
```

```text
深红发布流程：
  ① 精确制导：按请求头/Cookie/业务属性路由（不是随机百分比）
  ② 渐进染色：流量从 0% 缓慢可控增加（每步依赖关键指标）
  ③ 实时观测：与监控告警深度集成（自动判断继续/暂停/回滚）
  ④ 秒级回滚：回滚 = Git 提交回退（git revert）→ GitOps 自动恢复
```

| 优点 | 缺点 |
|------|------|
| 精确到目标用户（内部先测） | 实现复杂度高（路由规则） |
| 风险隔离（VIP 先体验） | 依赖完善的可观测性 |
| 回滚极简（Git 回退） | 团队要求高 |

> 💡 落地形态：网关/Service Mesh 按 header 路由 + GitOps 版本回退——**"灰度名单 + 自动观测 + Git 回滚"是深红的三支柱**。

## 6. A/B 测试与发布

```text
A/B 与灰度的区别：
  灰度：技术验证（新版本没毛病吗？）→ 追求稳定
  A/B：业务验证（哪个版本效果好？）→ 追求业务指标

A/B 场景：
  页面改版效果（转化率）
  算法调整（点击率）
  定价策略（下单率）
```

| 维度 | 灰度发布 | A/B 测试 |
|------|---------|---------|
| 目的 | 技术稳定性 | 业务效果 |
| 分流 | 渐进放量到全量 | 长期分桶对比 |
| 判定 | 错误率/延迟 | 业务指标（转化率） |
| 结束 | 全量切换 | 胜者全量 |

> 💡 实践中常组合：**先灰度（技术验证）→ 全量后 A/B（业务对比）**——或直接用 A/B 平台承载灰度（分桶即放量）。

## 7. 回滚策略

| 发布方式 | 回滚动作 | 速度 | 注意 |
|---------|---------|------|------|
| 滚动更新 | `kubectl rollout undo` | 分钟级 | 逐个替换 |
| 蓝绿 | Service selector 切回 | 秒级 | 蓝环境保留 |
| 金丝雀 | 流量权重回 0% | 秒级 | 旧版本实例在 |
| 深红 | Git revert（GitOps 同步） | 秒级 | 配置/代码一并回退 |

```text
回滚分层：
  ① 代码回滚（镜像切回旧版本）
  ② 配置回滚（Nacos 配置历史版本）
  ③ 数据回滚（数据库迁移逆向）——最复杂，需提前设计

⚠️ 数据回滚原则：
  能向前修复（补丁）就不向后回滚（数据逆迁移风险大）
  数据库迁移必须向后兼容（发布前置条件）
```

> 🎯 **回滚设计的核心问题**：**回滚的是镜像、配置还是数据库联动变更？**——发布前就要想清楚，临时想 = 发布时手忙脚乱。

## 8. 发布策略选型

```text
选型决策：
  日常小变更 → 滚动更新（零成本）
  重要功能/大改动 → 金丝雀灰度（10-30-60-100）
  可用性极致/支付类 → 蓝绿（双倍资源换秒级回滚）
  敏感变更/VIP 先试 → 深红（精确路由）
  业务效果验证 → A/B
  数据库大迁移 → 专门方案（影子库/双写），不混在发布策略里
```

| 团队阶段 | 推荐起点 |
|----------|---------|
| 无发布策略 | 滚动更新 + 回滚演练 |
| 有 CI/CD | 金丝雀灰度（Argo Rollouts） |
| 高可用要求 | 蓝绿 + 灰度组合 |
| 成熟平台 | 全策略 + 自动决策 |

## 9. 核心要点

> 🎯 **核心要点**：
> - 五策略定位：滚动（默认）、蓝绿（秒级回滚）、金丝雀（渐进放量）、深红（精确路由）、A/B（业务实验）；
> - 灰度三件套：放量可控 + 指标可观测 + 异常自动回滚；
> - 蓝绿核心矛盾：环境双、数据库单——DB 变更必须兼容；
> - 滚动更新前提：新旧版本兼容（混合期并存）；
> - 深红 2026 新理念：按请求属性路由 + Git 回滚（GitOps 联动）；
> - 回滚三层：代码/配置/数据——数据回滚"能向前修就不向后滚"；
> - 发布策略不是越复杂越好：**匹配团队成熟度**。
