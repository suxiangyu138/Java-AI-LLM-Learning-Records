# 01-分层排查方法论
> 网络问题的本质是"分层定位"：故障现象 → 映射到层 → 用对应工具确认——先分清"哪一层"，再谈"怎么修"

## 1. 分层模型

```text
应用层（HTTP/HTTPS/gRPC）      ← curl -v / 应用日志
传输层（TCP/UDP）              ← telnet / ss / tcpdump
网络层（IP/路由）              ← ping / traceroute
链路层（MAC/交换机）           ← 物理排查（网线/交换机）
DNS（域名解析）                ← nslookup / dig
```

| 层 | 回答的问题 | 关键工具 |
|----|-----------|---------|
| DNS | 域名解析对吗？ | nslookup、dig、hosts 文件 |
| 网络层 | IP 通吗？ | ping、traceroute |
| 传输层 | 端口通吗？ | telnet、nc、ss |
| 应用层 | HTTP 通吗？ | curl -v、浏览器 DevTools |
| 全层 | 到底发生了什么？ | tcpdump、Wireshark |

## 2. 故障现象 → 层映射表

| 现象 | 可能层 | 首要确认 |
|------|--------|---------|
| "Unknown host" / 域名解析失败 | DNS | `nslookup 域名` |
| "Connection timed out" | 网络层/防火墙 | `ping` → `traceroute` |
| "Connection refused" | 传输层（端口未监听） | `telnet ip port`、`ss -tlnp` |
| "No route to host" | 网络层（路由） | `traceroute` |
| 请求超时但端口通 | 应用层（服务慢/连接池满） | 应用日志、`ss -tnp` 状态 |
| 偶发失败/重置 | 传输层（RST/队列溢出） | `tcpdump`、`ss -s` 统计 |
| HTTPS 证书错误 | 应用层（TLS） | `openssl s_client` |
| 时快时慢 | 网络层/应用层 | 抓包 + 应用日志对比 |

> 🎯 **核心动作**：看到现象先问"这是哪一层的问题"——**大多数排查浪费在跨层乱试**。

## 3. 排查顺序：由外到内

```text
客户端 → 网络路径 → 服务端 → 应用

① 域名解析：nslookup domain（DNS 层）
② 网络连通：ping ip（网络层）
③ 路径质量：traceroute ip（网络路径）
④ 端口连通：telnet ip port（传输层）
⑤ 协议验证：curl -v http://...（应用层）
⑥ 服务端视角：ss -tnp / 应用日志 / 抓包
```

```bash
# 标准五连（最小工具集）
nslookup api.example.com            # ① DNS
ping -c 3 10.0.0.5                  # ② 网络
traceroute -n 10.0.0.5              # ③ 路径
telnet 10.0.0.5 8080                # ④ 端口
curl -v http://10.0.0.5:8080/health # ⑤ HTTP
```

> 💡 每一步"通了/不通"都缩小一半排查范围：五连之后问题通常只剩"服务端应用"或"防火墙策略"。

## 4. 两端视角

### 4.1 客户端视角

```bash
# 本机到目标：连接状态与路由
ss -tnp | grep 8080            # 连接状态（SYN_SENT/ESTABLISHED...）
ip route                       # 路由表
curl -v                        # 应用层细节（DNS/TLS/HTTP）
```

### 4.2 服务端视角

```bash
# 目标机器：端口监听与连接状态
ss -tlnp | grep 8080           # 端口监听了吗？
ss -tnp state syn-recv | wc -l # 半连接堆积？
ss -tn state established | wc -l   # 当前连接数
ss -s                          # TCP 统计（timewait 等）
netstat -s | grep -i reset     # RST 统计
```

> ⚠️ **看两端是铁律**：客户端说"连不上"，服务端 `ss -tlnp` 一看端口没监听——问题立刻定位（应用没起/防火墙），不用再猜。

## 5. 抓包：最终裁判

```bash
# 服务端抓包（端口 8080）
tcpdump -i any -nn port 8080 -w /tmp/cap.pcap

# 客户端抓包（目标 IP）
tcpdump -i any -nn host 10.0.0.5 and port 8080

# 只看握手
tcpdump -nn 'tcp[tcpflags] & tcp-syn != 0'

# 分析（Wireshark 或 tshark）
tshark -r /tmp/cap.pcap -Y "tcp.flags.reset==1"
```

| 抓包看点 | 结论 |
|----------|------|
| 只看到 SYN，无 SYN-ACK | 网络丢包/防火墙拦截 |
| SYN-ACK 发出但无 ACK | 客户端侧问题/半连接 |
| RST 回复 | 端口未监听/防火墙 reject |
| 握手成功但请求无响应 | 应用层问题（不归网络管） |

> 🎯 **抓包定论的场景**：客户端说通、服务端说通、但业务就是失败——**只有抓包能看清中间到底发生了什么**（防火墙丢弃/代理介入/负载均衡重置）。

## 6. 排查决策树

```text
应用报"连不上"
  ├─ nslookup 域名解析失败？
  │     ├─ 是 → DNS 问题（见 04）
  │     └─ 否 ↓
  ├─ ping IP 不通？
  │     ├─ 是 → 网络层（路由/防火墙/物理）
  │     └─ 否 ↓
  ├─ telnet 端口不通？
  │     ├─ 是 → 传输层：服务端监听？防火墙？
  │     └─ 否 ↓
  ├─ curl HTTP 失败？
  │     ├─ 是 → 应用层：服务端应用问题（见 05/06）
  │     └─ 否 → 业务层：参数/业务逻辑问题
  │
  └─ 偶发/时好时坏？
        └─ 抓包 + 统计（见 03：RST/TIME_WAIT/队列）
```

## 7. 核心要点

> 🎯 **核心要点**：
> - 分层定位是唯一正确方法：现象 → 层 → 工具 → 结论；
> - 五连最小集：nslookup → ping → traceroute → telnet → curl -v；
> - 两端视角：客户端"连不上"时先看服务端 `ss -tlnp`；
> - 抓包是最终裁判：说不清时抓包定论，不靠猜；
> - 偶发问题看统计：`ss -s`（TIME_WAIT）、`netstat -s`（RST）、队列长度。
