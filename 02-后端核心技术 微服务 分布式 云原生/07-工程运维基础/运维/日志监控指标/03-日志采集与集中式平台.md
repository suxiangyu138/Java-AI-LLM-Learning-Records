## 1. 集中式日志解决的问题

```text
微服务时代的日志困境：
  日志散落在 N 台机器 → 排查问题逐台登录 grep
  请求跨服务流转 → 各服务日志割裂，无法串联
  磁盘空间 → 单机日志保留期有限

集中式平台的价值：
  统一采集 → 一个界面全文/标签检索 → 跨服务串联 → 长期留存
```

| 困境 | 集中式解法 |
|------|-----------|
| 日志分散 | 采集器（DaemonSet）统一收集 |
| 无法串联 | traceId 字段检索（配合 MDC，见 [02](02-Logback配置与生产实践.md)） |
| 单机保留短 | 集中存储（对象存储长期留存） |
| 无法聚合分析 | 标签查询/聚合/告警联动 |

## 2. 采集架构

```text
应用容器（JSON 日志输出 stdout/文件）
  → 节点采集器（DaemonSet：Alloy / Fluent Bit / Filebeat）
      ├─ 附加标签（namespace/pod/container/服务名）
      └─ 推送
           ├─ Loki（标签索引存储）
           └─ Elasticsearch（全文索引存储）
  → Grafana / Kibana 统一查询
```

| 采集器 | 定位 | 2026 状态 |
|--------|------|-----------|
| **Grafana Alloy** | 统一采集器（指标+日志+追踪） | ✅ 推荐（Promtail 已弃用） |
| Fluent Bit | 轻量日志采集（EFK 链路） | ✅ 活跃 |
| Filebeat | Elastic 生态采集 | ✅ 活跃 |
| Promtail | Loki 专属采集 | ⚠️ 已弃用（迁移 Alloy） |

> ⚠️ **2026 迁移提示**：Promtail 已弃用，Loki 采集统一迁移到 **Grafana Alloy**（River DSL 配置，DaemonSet 部署，同时抓指标/采日志/转发追踪）。

## 3. EFK vs Loki 选型

| 维度 | EFK（ES + Fluent Bit + Kibana） | Loki（+ Alloy + Grafana） |
|------|-------------------------------|---------------------------|
| 索引方式 | **全文索引整个日志内容** | 仅索引标签（namespace/pod/服务），不索引内容 |
| 查询能力 | 极强全文检索、复杂聚合 | 标签查询 + 时间范围 + 模式匹配（全文较弱） |
| 资源消耗 | 高（RAM/CPU 大，HA 至少 3 节点） | 低（可扩展至对象存储） |
| 成本 | 高（大规模"太贵"） | **低（较 ES 降约 70%）** |
| 集成 | 独立 Kibana | 与 Grafana/Prometheus 生态**统一** |
| 性能 | 全文索引查询快但存储贵 | 标签查询 p50 1.8s（5 亿行） |

| 场景 | 选型 |
|------|------|
| 大多数 K8s 日志场景（按服务/时间/模式查） | **Loki**（低成本 + Grafana 一体） |
| 非结构化内容全文检索/取证式文本挖掘 | EFK/OpenSearch |
| 复杂聚合分析、合规要求 | EFK |
| 已有 Prometheus + Grafana 监控体系 | **Loki**（生态统一） |

> 🎯 2026 结论：**大多数团队的 K8s 日志场景，PLG（Prometheus + Loki + Grafana）是更优选择**；ES 留给"深度全文检索"刚需。

## 4. Loki：标签索引式日志

### 4.1 核心设计

```text
Loki 只索引元数据标签，不索引日志内容：
  标签：{service="order-service", namespace="prod", pod="xxx"}
  内容：JSON 日志行原样存储

查询：按标签过滤 + 时间范围 + LogQL 内容匹配
```

```text
# LogQL 查询示例
{service="order-service", env="prod"} |= "ERROR"          # 含 ERROR
{service="order-service"} | json | level="error"           # JSON 字段过滤
{namespace="prod"} |= "traceId=a1b2c3d4"                  # 按 traceId 串联
```

| 特性 | 说明 |
|------|------|
| 标签驱动 | 只索引标签（服务/命名空间/容器） |
| LogQL | 标签过滤 + 内容匹配 + JSON 解析 |
| 存储 | 对象存储（S3/MinIO）扩展 |
| 保留策略 | 保留 API + 对象存储生命周期策略 |
| OTLP 接入 | 原生支持 OTLP 端点接收日志 |

### 4.2 避坑：标签基数

> ⚠️ **标签基数爆炸**（与 Prometheus 同源问题）：pod 名、随机 ID 等**无界值不能做标签**——会撑爆 chunk 索引、拖慢所有查询。标签用低基数维度（服务/环境/命名空间），高基数信息放日志内容。

## 5. 检索与排障流程

```text
排障标准路径（LGTM 联动）：
① Grafana 指标面板发现异常（如错误率飙升）
② 点进 Loki 按 service + 时间范围查 ERROR 日志
③ 日志中拿到 traceId → 点进 Tempo 查看全链路
④ 定位瓶颈服务 → 回到该服务日志深挖
```

| 排障动作 | 查询 |
|----------|------|
| 某服务某时段错误 | `{service="order-service"} |= "ERROR" \| json` |
| 某用户全链路 | 跨服务检索日志内容匹配 `userId=1001` |
| 某 trace 全链路 | 跨服务检索日志内容匹配 `traceId=a1b2c3d4` |
| 慢请求定位 | 指标（p99 飙升）→ 日志（该时段）→ 链路（瓶颈节点） |

> 🎯 三支柱联动是排障效率的核心：**指标找现象、日志找现场、链路找根因**（详见 [06](06-可观测性三支柱与OpenTelemetry.md)）。

## 6. 脱敏与安全

### 6.1 日志脱敏（应用侧优先）

| 数据类型 | 脱敏示例 |
|----------|---------|
| 手机号 | `138****1234` |
| 身份证 | `110***********1234` |
| 密码/Token | `******` |
| 银行卡 | `6222 **** **** 1234` |

```java
// 方案 1：Logback 自定义 Filter/Converter 脱敏
// 方案 2：JSON 日志 + 采集端正则脱敏
// 方案 3：Logstash/Alloy 采集时字段脱敏
```

### 6.2 平台安全

| 措施 | 说明 |
|------|------|
| 访问控制 | Grafana/Loki 按团队分权限（只能看本服务日志） |
| 加密传输 | 采集器 → 平台走 TLS |
| 留存合规 | 按合规要求设定保留期（如日志 180 天） |
| 审计 | 谁查了什么日志可追溯 |

> ⚠️ 合规红线：**身份证/密码/密钥不能进日志**——脱敏在应用侧做（最可靠），平台侧做兜底。

## 7. 日志治理

| 治理项 | 做法 |
|--------|------|
| 级别策略 | 生产 INFO 起步；ERROR 必须告警联动 |
| 噪声过滤 | 采集端过滤重复日志/健康检查日志 |
| 采样 | 高频 INFO 按比例采样（保留 ERROR 全量） |
| 量级控制 | 单日志大小限制（如单条 ≤ 8KB） |
| 保留策略 | 按环境分层（dev 7 天 / prod 180 天） |
| 成本监控 | Loki 写入量/存储量监控（`LokiDiskUsageHigh > 85%` 告警） |

> 💡 日志治理目标：**留得住（成本可控）、找得到（结构良好）、信得过（不泄露）**。

## 8. 核心要点

> 🎯 **核心要点**：
> - 集中式三价值：统一检索、跨服务串联（traceId）、长期留存；
> - 2026 采集：Alloy 统一采集器（Promtail 已弃用）；
> - 选型：大多数 K8s 场景 Loki（成本低 70% + Grafana 一体）；深度全文检索才上 ES；
> - Loki 双红线：标签只用低基数维度、监控磁盘写入量；
> - 排障路径：指标（现象）→ 日志（现场）→ 链路（根因）；
> - 脱敏在应用侧（JSON 日志字段级），平台侧兜底；
> - 治理四问：留得住？找得到？信得过？告警联得上？
