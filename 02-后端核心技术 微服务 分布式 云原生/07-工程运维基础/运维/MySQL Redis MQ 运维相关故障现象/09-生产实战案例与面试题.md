## 1. 案例一：MySQL 连接数满（连接泄漏）

```text
现象：应用偶发 "Too many connections"，重启后恢复，几小时后复发
```

```text
排查：
① Threads_connected 曲线：持续爬升（泄漏特征）
② processlist：大量 Sleep 连接堆积
③ 应用连接池监控：active 持续占满
④ 代码审查：某服务连接未归还（异常路径缺 finally）

解决：修复泄漏 + 连接池验证 + 连接数告警（>80%）
```

| 教训 | 说明 |
|------|------|
| 爬升曲线 = 泄漏 | 不是突发（突发是陡升） |
| 重启只缓解 | 泄漏不修必复发 |
| 监控要早 | 连接数 >80% 告警 |

## 2. 案例二：慢查询拖垮数据库

```text
现象：高峰期数据库 CPU 100%，接口大面积超时
```

```text
排查：
① processlist 快照：多条长 time 查询（同一 SQL 模式）
② EXPLAIN：type=ALL 全表扫描 + rows 千万级
③ 慢日志确认：该 SQL 从某次发布后开始变慢
④ 根因：新需求加的查询无索引（发布引入）

解决：加复合索引 → CPU 回落 → 索引评审入发布流程
```

| 教训 | 说明 |
|------|------|
| 快照对比 | 连续两次 processlist 对比 |
| 变更回溯 | 慢 SQL 与发布对应 |
| 索引评审 | 新查询 SQL 评审入流程 |

## 3. 案例三：死锁导致订单失败

```text
现象：订单接口偶发失败，报 "Deadlock found"
```

```text
排查：
① SHOW ENGINE INNODB STATUS：死锁现场（两个事务的 SQL）
② 发现：订单创建与库存扣减顺序不一致
③ 根因：多服务/多线程以不同顺序更新订单与库存表

解决：统一加锁顺序 + 死锁重试（业务幂等）
```

| 教训 | 说明 |
|------|------|
| 死锁现场要取 | SHOW ENGINE INNODB STATUS（恢复后没了） |
| 顺序一致 | 多表更新固定顺序 |
| 重试兜底 | 死锁自动回滚，业务重试 |

## 4. 案例四：主从延迟读到旧数据

```text
现象：用户下单后查询订单状态一直显示旧状态
```

```text
排查：
① SHOW REPLICA STATUS：Seconds_Behind_Master 持续增长
② Last_SQL_Error：无错误
③ 主库 binlog 分析：大事务（批量更新）
④ 根因：后台批量任务大事务 → 从库重放慢

解决：批量任务分批（小事务）+ 写后读强一致场景走主库
```

| 教训 | 说明 |
|------|------|
| 大事务是元凶 | 批量任务分批执行 |
| 读一致性分级 | 写后读走主库 |
| 延迟告警 | Seconds_Behind_Master > N 告警 |

## 5. 案例五：Redis 大 key 阻塞

```text
现象：Redis 偶发整体变慢（所有接口延迟抖动）
```

```text
排查：
① slowlog：发现 HGETALL 耗时 1s+（大 hash）
② memory usage：某 key 占用 500MB
③ 根因：hash 存了全量用户在线状态（无界增长）

解决：拆 key（按天/按分片）+ 删除用 UNLINK + 大 key 巡检
```

| 教训 | 说明 |
|------|------|
| 慢日志第一证据 | slowlog get |
| 无界 key 是根源 | 所有集合类 key 评估上限 |
| 删除用 UNLINK | DEL 大 key 是二次事故 |

## 6. 案例六：Redis 内存淘汰丢缓存

```text
现象：缓存命中率骤降，接口变慢（回源数据库）
```

```text
排查：
① info memory：evicted_keys 激增
② maxmemory 已达上限
③ 根因：缓存 key 无 TTL 持续增长（缓存泄漏）

解决：TTL 规范（所有缓存 key 必设 TTL）+ 内存扩容 + 淘汰告警
```

| 教训 | 说明 |
|------|------|
| evicted_keys 是信号 | 淘汰 = 内存不够 |
| TTL 规范 | 缓存 key 必设过期 |
| 命中率监控 | <80% 告警 |

## 7. 案例七：Kafka 消息堆积

```text
现象：订单消息消费延迟达小时级
```

```text
排查：
① consumer-groups：LAG 持续增长（开始时间 = 大促开始）
② 消费速率：消费正常但 < 生产
③ 分区数：3 个分区（消费者扩容上限 = 3）
④ 根因：大促流量激增 + 分区不足

解决：分区扩容（重建主题）+ 消费者扩容 + 消费逻辑优化
```

| 教训 | 说明 |
|------|------|
| LAG 拐点 = 开始时间 | 与流量事件对应 |
| 分区是并行度 | 扩容前先看分区数 |
| 大促预案 | 容量评估 + 弹性扩分区 |

## 8. 案例八：重复消费导致重复下单

```text
现象：用户偶发收到重复下单通知/重复扣款
```

```text
排查：
① 消费者日志：同一消息处理多次（offset 提交前崩溃）
② 幂等检查：下单接口无幂等
③ 根因：至少一次语义 + 无幂等

解决：消息带业务唯一键 + DB 唯一约束 + 幂等表
```

| 教训 | 说明 |
|------|------|
| 至少一次是默认 | 不是 Bug，是语义 |
| 幂等是铁律 | 唯一键 + DB 唯一约束 |
| 资金类必幂等 | 下单/扣款/转账 |

## 10. 面试题

| 题目 | 答题要点 |
|------|---------|
| MySQL 连接数满怎么排查？ | Threads_connected 趋势（爬升=泄漏）+ processlist + max_connections |
| 慢查询怎么优化？ | EXPLAIN 三列（type/rows/key）→ 索引/分页/改写 |
| 死锁和锁等待的区别？ | 互相等待（立即检测回滚）vs 单向等待（50s 超时） |
| 主从延迟的原因？ | 大事务/慢 SQL 重放/SQL 线程错误/从库负载 |
| 误删数据怎么恢复？ | 备份（起点）+ binlog（增量）+ 时间/位置（停止点） |
| Redis 淘汰策略？ | noeviction/allkeys-lru/volatile-lru/LFU；evicted_keys 增长 = 内存不够 |
| Redis 为什么变慢？ | 慢命令（KEYS/大集合全量）/大 key/持久化 fork/淘汰/swap |
| 大 key 怎么处理？ | 拆 key/分片/UNLINK 删除/巡检 |
| 消息堆积怎么排查？ | LAG 拐点 → 生产 vs 消费速率 → 分区数 → 失败原因 |
| 重复消费怎么办？ | 幂等：唯一业务键 + DB 唯一约束 |
| 怎么保证消息不丢？ | 三环节：生产确认 + Broker 副本 + 消费手动确认 |
| 死信堆积怎么办？ | 积压量 → 错误头分类 → 回放/修码/隔离 |
| Kafka 恰好一次？ | 事务 + 幂等生产者（限 Kafka 内）；DB 用 Outbox |
| 顺序消息怎么保证？ | 同 key 同分区 + 单消费者（牺牲并行度） |

## 11. 核心要点

> 🎯 **核心要点**：
> - 八案例八教训：泄漏爬升、慢查询追发布、死锁取现场、大事务、无界 key、TTL、分区并行度、幂等铁律；
> - 跨中间件避坑 Top3：不看监控、不幂等、无限重试；
> - 面试主线：连接/慢查询/锁/主从/误删（MySQL）→ 淘汰/大 key/慢命令（Redis）→ 堆积/重复/顺序/死信（MQ）；
> - 方法论回顾：监控先行 + 变更回溯 + 根因检验 + 复盘防复发；
> - 与体系联动：监控告警看日志监控指标、网络类故障看网络问题排查、发布变更看 CI/CD 灰度发布。
