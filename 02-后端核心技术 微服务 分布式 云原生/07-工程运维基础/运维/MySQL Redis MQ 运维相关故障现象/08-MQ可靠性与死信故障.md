## 1. 故障一：丢消息

### 1.1 丢消息的三个环节

```text
丢消息三环节：
  ① 生产端丢：发送失败未重试 / acks 设置不当
  ② Broker 丢：副本不足 / 刷盘策略
  ③ 消费端丢：处理前提交 offset / 自动提交时机
```

### 1.2 各 MQ 可靠性配置

```text
Kafka：
  生产：acks=all + retries + 幂等生产者（enable.idempotence）
  存储：replication.factor=3 + min.insync.replicas=2
  消费：enable.auto.commit=false（处理成功再提交）

RocketMQ：
  生产：同步发送 + 重试（默认 2 次）
  消费：消费成功后 ACK（Broker 才移除）

RabbitMQ：
  生产：publisher confirms（发布确认）
  消费：手动 ACK（basic.ack）
  存储：持久化队列 + 消息持久化
```

| 环节 | Kafka | RocketMQ | RabbitMQ |
|------|-------|----------|----------|
| 生产确认 | acks=all | 同步发送 | confirms |
| 副本 | RF=3 + ISR | 主从同步 | 仲裁队列 |
| 消费确认 | 手动提交 offset | 消费成功后 ACK | 手动 ACK |

> 🎯 **丢消息排查主线**：**先确认语义边界**（至少一次 vs 恰好一次）→ 逐环节查配置（生产确认/Broker 副本/消费确认）→ 三者都对齐才谈"不丢"。

## 2. 故障二：死信堆积

### 2.1 死信机制

```text
死信（DLQ/DLT）：消费失败重试耗尽后的归宿

Kafka：error.<topic>.<group>（需显式开启 + 有 group）
RocketMQ：%DLQ%<group>（重试 16 次后自动进）
RabbitMQ：<queue>.dlq（autoBindDlq + x-death 计数）
```

### 2.2 死信堆积的排查

```bash
# Kafka：死信主题积压
kafka-consumer-groups --describe --group dlq-consumer

# RabbitMQ：死信队列积压
rabbitmqctl list_queues name messages | grep dlq

# 死信消息的错误头（Kafka）
# x-exception-message / x-exception-stacktrace —— 失败原因在头里！
```

```text
死信排查三步：
  ① 积压量（堆积了 = 有人在持续失败）
  ② 错误头/日志（x-exception-message——失败原因）
  ③ 分类处理：
      瞬时故障 → 回放（修复后重发）
      永久故障（数据/代码）→ 修代码/人工处理
      毒丸消息 → 隔离（停车场队列）
```

> 🎯 **死信堆积 = 持续失败的直接证据**：**先看错误信息分类**——瞬时故障回放、永久故障修代码、毒丸隔离；死信有积压必须**秒级告警**（见日志监控指标体系）。

## 3. 故障三：延迟消息不触发/错乱

### 3.1 各 MQ 延迟实现

```text
Kafka：无原生延迟消息（需自研/时间轮方案）
RocketMQ：延迟等级（1s/5s/10s/30s/1m/2m...18 个等级）
RabbitMQ：延迟插件（delayed exchange）或 DLQ+TTL
```

### 3.2 常见故障

| 故障 | 原因 | 解决 |
|------|------|------|
| 延迟不准 | RocketMQ 只能选等级（不能任意秒） | 接受等级粒度/自研 |
| 延迟消息丢失 | 延迟队列重启丢数据 | 持久化 + 恢复机制 |
| 顺序错乱 | 延迟与普通消息混用 | 分主题/分队列 |
| RabbitMQ 延迟失效 | 插件未装/交换器类型错 | 装插件 + delayed-exchange |

> 💡 **RocketMQ 延迟的坑**：**只能选 18 个固定等级**（不能延迟 37 秒）——业务要任意延迟需自研（时间轮/Redis 延迟队列）。

## 4. 故障四：事务消息不一致

### 4.1 解决的问题

```text
场景：本地事务（写 DB）+ 发消息 的一致性
  先写库再发消息 → 消息发送失败 = DB 有数据但没消息
  先发消息再写库 → 消费端可能读到未提交数据

RocketMQ 事务消息：半消息机制解决
  （详见 RocketMQ 体系：半消息 → 本地事务 → 确认/回查）
```

### 4.2 故障排查

| 故障 | 原因 | 解决 |
|------|------|------|
| 消息未发送 | 本地事务失败未确认 | 正常（半消息被回查/回滚） |
| 消息重复 | 回查重投 | 消费幂等 |
| 事务卡住 | 本地事务回调异常 | 回查机制兜底（超时回查） |
| Kafka 事务 | 只保证 Kafka 内（消费+生产） | DB+Kafka 需 Outbox 模式 |

> 🎯 **跨系统一致性方案对比**：RocketMQ 事务消息（半消息+回查）；**Kafka + DB 用 Outbox 模式**（本地事务写 outbox 表 + 定时/CDC 发消息）——**事务消息只解决"MQ 与本地事务"的耦合，不解决任意系统间**。

## 5. 可靠性对比与配置基线

### 5.1 语义对比

| MQ | 默认语义 | 最强语义 |
|----|---------|---------|
| Kafka | 至少一次 | **恰好一次**（事务+幂等，限 Kafka 内） |
| RocketMQ | 至少一次 | 至少一次 + 事务消息（DB 一致性） |
| RabbitMQ | 至少一次 | 至少一次（confirms+ACK） |

### 5.2 生产配置基线

```text
Kafka 生产基线：
  acks=all
  enable.idempotence=true
  replication.factor=3
  min.insync.replicas=2
  enable.auto.commit=false（消费）

RabbitMQ 生产基线：
  publisher-confirm-type=correlated
  spring.rabbitmq.listener.simple.acknowledge-mode=manual
  持久化交换器/队列/消息

RocketMQ 生产基线：
  同步发送 + 重试
  AUTO_ACKNOWLEDGE 消费（成功后 ACK）
```

> ⚠️ **可靠性配置是"安全垫"不是"万无一失"**：即使配置齐全，**消费幂等仍是最后防线**（重复与顺序问题永远存在）——可靠性 = 配置 + 幂等 + 监控三件套。

## 6. 核心要点

> 🎯 **核心要点**：
> - 丢消息三环节：生产（acks/confirms）→ Broker（副本/刷盘）→ 消费（手动确认）；
> - 死信堆积三步：积压量 → 错误头（x-exception-message）→ 分类（回放/修码/隔离）；
> - 延迟消息：RocketMQ 18 等级限制、RabbitMQ 插件、Kafka 需自研；
> - 事务消息：RocketMQ 半消息+回查；Kafka+DB 用 Outbox；
> - 生产基线：acks=all + RF=3 + 手动确认 + 幂等；
> - 可靠性 = 配置 + 幂等 + 监控三件套——**幂等是最后防线**。
