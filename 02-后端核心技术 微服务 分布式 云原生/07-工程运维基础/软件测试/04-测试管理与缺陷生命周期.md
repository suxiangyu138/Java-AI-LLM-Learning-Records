## 1. 测试计划与策略

### 1.1 测试计划核心要素

```text
测试计划模板：
1. 测试范围：测什么、不测什么（防止范围蔓延）
2. 测试目标：通过标准（如：0个Critical Bug、覆盖率>80%）
3. 测试环境：硬件/软件/数据
4. 测试策略：各阶段用什么方法（单元→白盒、系统→黑盒）
5. 资源分配：谁测、什么时候测、需要多少时间
6. 风险分析：哪些模块Bug多/时间紧/依赖不明确
7. 日程安排：测试阶段+里程碑+交付物
8. 退出标准：达到什么条件可以停止测试
```

### 1.2 测试优先级排序

| 优先级 | 含义 | 判断标准 |
|:---:|------|------|
| **P0** | 必测 | 核心业务流程、涉及资金、安全漏洞 |
| **P1** | 应测 | 常用功能、高并发接口 |
| **P2** | 可测 | 辅助功能、低频率使用 |
| **P3** | 缓测 | 几乎不用、即将下线的功能 |

```text
测试工作量分配（建议比例）：
    核心模块: 50%
    常用功能: 30%
    辅助功能: 15%
    边缘功能: 5%
```

### 1.3 测试退出标准

```text
退出标准示例（满足以下全部条件方可结束测试）：
□ 计划测试用例 100% 执行完成
□ P0/P1 Bug 全部修复并验证通过
□ P2 Bug 98% 修复
□ 核心接口回归测试通过
□ 性能基线不低于上一版本
□ 安全扫描无 High/Critical 漏洞
```

## 2. 缺陷生命周期管理

### 2.1 标准Bug生命周期

```text
                ┌──────────┐
                │  New     │  ← 测试提交Bug
                │  (新建)  │
                └────┬─────┘
                     │ 开发确认
                     ↓
                ┌──────────┐
         ┌──────│ Assigned │──────┐
         │      │ (已分配) │      │
         │      └────┬─────┘      │
         │           │ 开发修复    │
         │           ↓            │
         │      ┌──────────┐     │
         │      │ Resolved │     │  ← 拒绝修复？（Duplicate/Won't Fix/Can't Reproduce）
         │      │ (已解决) │     │
         │      └────┬─────┘     │
         │           │ 测试验证    │
         │           ↓            │
         │      ┌──────────┐     │
         │      │ Verified │     │
         │      │ (已验证) │     │
         │      └────┬─────┘     │
         │           │ 关闭       │
         │           ↓            │
         │      ┌──────────┐     │
         └─────→│ Closed   │←────┘
                │ (已关闭) │
                └──────────┘
                     ↑
                ┌──────────┐
                │ Reopened │  ← 验证不通过，重新打开
                │ (重新打开)│
                └──────────┘
```

### 2.2 Bug报告模板

```markdown
## Bug标题：[模块] 简短描述（≤20字）

**严重等级**: P0 / P1 / P2 / P3
**优先级**: High / Medium / Low
**环境**: Chrome 120, Windows 11, 测试环境

**复现步骤**:
1. 登录 → 进入用户管理
2. 点击"删除"按钮
3. 点击"确认删除"

**实际结果**: 删除失败，弹出"系统异常"

**期望结果**: 用户被成功删除，列表刷新

**附件**: [截图/日志/HAR文件]
```

### 2.3 Bug严重等级 vs 优先级

| 严重等级(Severity) | 优先级(Priority) | 示例 |
|:---:|:---:|------|
| Blocker | 立即 | 系统崩溃、支付失败 |
| Critical | 当天 | 核心功能不可用但可绕过 |
| Major | 本周 | 功能缺失但有替代方案 |
| Minor | 下版本 | UI错位、文案错误 |
| Trivial | 排期 | 建议性改进 |

> ⚠️ 严重等级=技术角度影响范围；优先级=业务角度修复紧迫度。两者不完全等价。

## 3. 测试报告与度量

### 3.1 测试报告关键指标

| 指标 | 计算方式 | 说明 |
|------|----------|------|
| **测试用例执行率** | 已执行/计划总数×100% | ≥ 95% |
| **测试用例通过率** | 通过数/已执行×100% | 期望≥ 98% |
| **Bug发现率** | 每日新增Bug数 | 趋势下降→质量在提升 |
| **Bug修复率** | 已修复/总数×100% | P0/P1必须100% |
| **Bug重开率** | 重开Bug/总数×100% | 应< 5%（修了又坏） |
| **缺陷密度** | Bug数/KLOC(千行代码) | 1-5正常，<1 优秀 |

### 3.2 测试摘要报告模板

```markdown
# 测试报告：v2.3.0

## 测试概览
- 测试周期：2024-01-08 ~ 01-15
- 测试环境：测试环境集群
- 测试范围：用户模块、订单模块、支付模块

## 执行统计
| 指标 | 数值 |
|------|------|
| 计划用例 | 320 |
| 执行用例 | 315 (98.4%) |
| 通过用例 | 308 (97.8%) |
| 失败用例 | 7 (需修复3个，已知限制4个) |

## Bug统计
| 严重等级 | 发现 | 修复 | 未修复 |
|---------|:---:|:---:|:---:|
| P0 | 1 | 1 | 0 |
| P1 | 5 | 5 | 0 |
| P2 | 12 | 9 | 3 |
| P3 | 8 | 4 | 4 |

## 风险评估
- ✅ 核心业务流程回归通过
- ⚠️ 高并发场景下偶尔超时（P2，下版本优化）
- ✅ 安全扫描无新增漏洞

## 结论
建议发布 ✅ （未修复P2/P3均已确认影响可控，下版本计划修复）
```

## 4. 测试团队角色分工

| 角色 | 职责 | 产出物 |
|------|------|--------|
| **测试经理** | 制定测试策略、资源协调、进度跟踪 | 测试计划、测试报告 |
| **测试分析师** | 需求分析、用例设计 | 测试用例、需求追溯矩阵 |
| **测试工程师** | 执行用例、提交Bug、回归验证 | Bug报告、测试记录 |
| **自动化测试工程师** | 编写自动化脚本、维护框架 | 自动化测试代码 |
| **性能测试工程师** | 场景设计、压测执行、分析瓶颈 | 性能测试报告 |

> 💡 **中小团队的测试分工**：通常开发自己负责单元测试+集成测试，测试工程师负责系统测试+验收测试+性能测试。

---

> 🎯 **核心原则**：测试管理不是"多测几个用例"，而是"用有限的资源测最重要的东西"。
