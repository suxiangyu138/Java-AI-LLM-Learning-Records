## 1. 选型对比：APIFox vs Postman vs JMeter

| 维度 | APIFox | Postman | JMeter |
|------|--------|---------|--------|
| 定位 | API 全生命周期一体化 | 接口调试 + 生态 | 性能/压力测试 |
| 接口调试 | ✅ 定义驱动 | ✅ | ⚠️ 非主场景 |
| 接口文档 | ✅ 内置自动生成 | ⚠️ 需组合 | ❌ |
| Mock | ✅ 智能 Mock + 期望 | ⚠️ Mock Server | ❌ |
| 功能测试 | ✅ 套件/场景/断言 | ✅ Runner + Newman | ✅ 线程组 + 断言 |
| **性能测试** | ⚠️ 有限（接口级） | ❌ | ✅ **专业**（并发/阶梯/分布式压测） |
| 脚本语言 | JS | JS | Groovy/BeanShell |
| CI 集成 | `apifox run` | `newman` | `jmeter -n -t` |
| 中文/国内 | ✅ | ⚠️ | ✅ |
| AI 能力 | ✅ 自愈/Agent/MCP | ⚠️ Copilot | ❌ |

| 场景 | 推荐 |
|------|------|
| 日常接口调试 + 文档 + Mock | **APIFox**（一体化） |
| 团队 API 契约管理 | **APIFox**（定义驱动） |
| 已有 Postman 生态/国际团队 | Postman |
| **性能/压力测试** | **JMeter**（APIFox 不做性能压测的活） |
| AI Agent 驱动的 API 测试 | **APIFox**（CLI+Skill 独有） |

> 🎯 **选型结论**：APIFox 与 JMeter **不是竞品**——前者做"接口正确性"，后者做"系统性能"。生产团队常见组合：APIFox（功能/契约/回归）+ JMeter（性能/压测）。

## 2. 团队落地路线图

```text
第一阶段：调试统一（1 周）
  全员用 APIFox 调试 → 迁移 Postman Collection → 统一环境管理

第二阶段：契约显性化（2 周）
  后端定义接口 → 前端文档/Mock 联调 → 公共数据模型复用

第三阶段：测试自动化（1 个月）
  核心接口用例 → 业务场景编排 → 测试套件 → 定时任务

第四阶段：CI 门禁（持续）
  apifox run 接入流水线 → 失败拦截 → 报告可视化

第五阶段：AI 化（可选）
  文档自愈 → CLI+Skill 接入 Agent → MCP 调试
```

| 阶段 | 关键产出 | 度量 |
|------|---------|------|
| ① 调试统一 | 接口库完整 | 接口覆盖率 |
| ② 契约显性 | 文档/Mock 可用 | 前后端并行效率 |
| ③ 测试自动化 | 回归套件 | 核心接口用例覆盖率 |
| ④ CI 门禁 | 流水线拦截 | 回归通过率趋势 |
| ⑤ AI 化 | 自愈/Agent | 文档更新耗时 |

## 3. 安全机制与最佳实践

### 3.1 客户端安全（2026-05 升级）

| 机制 | 说明 |
|------|------|
| 沙盒机制（Sandbox） | 脚本在沙盒中执行，隔离高风险操作 |
| 上下文隔离 | 脚本与主进程隔离 |
| 授权确认 | 数据库连接、调用外部程序、动态加载 npm 包等高风险操作需授权 |

### 3.2 团队安全最佳实践

| # | 实践 | 说明 |
|---|------|------|
| 1 | Token 不入仓库 | `APIFOX_ACCESS_TOKEN` 走 CI secrets |
| 2 | 敏感信息用变量 | 密码/密钥放环境变量（不入接口定义） |
| 3 | 权限最小化 | 只读成员不赋编辑权 |
| 4 | 分支保护 | main 分支合入需确认（尤其 AI 分支） |
| 5 | 审计 | 定期检查成员操作与变更记录 |
| 6 | 自托管合规 | 数据合规要求用自托管 Mock Runner |

> ⚠️ **AI 时代安全提醒**：AI 分支 + cli-schema 是"AI 写入防护"两道闸——**不用 AI 分支直接让 Agent 改主分支 = 未审查的自动化修改**。

## 4. 高频避坑清单

| # | 坑 | 现象 | 规避 |
|---|----|------|------|
| 1 | 环境变量作用域混乱 | 接口用了旧环境变量 | 用 `${VAR}` 前确认当前环境；局部 > 环境 > 全局 |
| 2 | 脚本 API 混用 | `pm.*` 与内置 API 混用出错 | 迁移用兼容层；新脚本统一内置 API |
| 3 | Mock 当测试 | 联调通过但接口有 bug | Mock 是开发手段，测试必须真实环境 |
| 4 | 断言只看状态码 | 业务错误漏检 | 业务码/字段值/计算逻辑断言 |
| 5 | 场景用例不提取变量 | 下单用例 orderId 写死 | 后置脚本提取 → 下一步插值 |
| 6 | CI 不设门禁 | 测试失败照样部署 | `--fail-on-error` |
| 7 | Token 硬编码 | 仓库泄露 | secrets/环境变量 |
| 8 | 导入后脚本不检查 | Postman 脚本迁移后静默失效 | 迁移后逐条验证脚本 |
| 9 | 忽略定时任务 | 回归靠人工触发 | 每日定时 + 失败通知 |
| 10 | AI 直接改主分支 | 未审查修改污染项目 | 强制 AI 分支 + cli-schema |

## 5. Java 后端场景实践

### 5.1 契约先行开发

```text
① 后端在 APIFox 定义接口（含数据模型）
② 前端用 Mock 开发（零阻塞）
③ 后端实现 + 自愈联动（重构自动更新）
④ 联调切真实环境
⑤ apifox run 回归门禁
```

### 5.2 与 Spring Boot 生态联动

| 联动点 | 说明 |
|--------|------|
| OpenAPI 导出 | 导出 OpenAPI → SpringDoc/OpenAPI Generator 生成 Controller 骨架 |
| 契约测试 | 接口定义 → 生成契约测试（配合 Testcontainers） |
| MCP 调试 | Spring AI MCP Server 用 APIFox 验证（见 [07](07-AI能力与MCP调试.md)） |
| 文档自愈 | Apifox Helper 插件感知 Java 代码变更 |

### 5.3 典型 Java 团队配置

```text
环境：dev（本地）/ test（测试服务器）/ prod（生产只读）
变量：baseUrl、token（后置脚本提取）、签名参数（前置脚本生成）
套件：核心链路套件（每日定时）+ 变更定向套件（CI 触发）
通知：企业微信/钉钉（失败告警）
```

## 6. 面试题

| 题目 | 答题要点 |
|------|---------|
| APIFox 与 Postman 的本质区别？ | 定位不同：Postman 是调试工具，APIFox 是 API 全生命周期（定义驱动，文档/Mock/测试联动） |
| 接口定义驱动是什么意思？ | 定义一次 → 文档自动生成、Mock 自动推导、测试自动关联、代码自动生成 |
| 场景用例解决了什么问题？ | 接口单独对 ≠ 链路通：token 流转、状态依赖、数据关联只有链路测试覆盖 |
| 测试套件静态/动态模式？ | 静态：精确指定固定回归集；动态：规则筛选最新用例（持续集成） |
| 断言为什么不能只看状态码？ | 状态码通过 ≠ 业务正确：业务码、字段值、计算逻辑都要校验 |
| `apifox run` 在 CI 中怎么用？ | `--fail-on-error` 门禁 + junit 报告 + secrets 管 Token |
| 文档自愈是什么原理？ | 感知代码变更 → AST 扫描 → 语义对齐（字段重命名识别）→ 依赖映射修复 → 人工确认 |
| MCP 调试能做什么？ | 作为 MCP Client 调试 Server 的 Tools/Resources/Prompts（STDIO + Streamable HTTP） |
| APIFox 能替代 JMeter 吗？ | 不能：JMeter 做性能压测，APIFox 做接口正确性/契约/回归——互补关系 |
| AI 分支的价值？ | AI 修改先隔离、可审查、可回滚——AI 也要走"Code Review" |

## 7. 核心要点

> 🎯 **核心要点**：
> - 选型：功能/契约/回归用 APIFox，性能压测用 JMeter——互补不互替；
> - 落地五阶段：调试统一 → 契约显性 → 测试自动化 → CI 门禁 → AI 化；
> - 安全三件套：Token 走 secrets、沙盒脚本隔离、AI 分支防护；
> - 避坑 Top3：断言只看状态码、场景不提取变量、CI 不设门禁；
> - Java 实践：契约先行 + OpenAPI 联动 + MCP 验证 + 文档自愈；
> - 面试主线：定义驱动 → 场景链路 → CI 门禁 → AI 三件套。
