# 03-测试生命周期与嵌套测试

> 生命周期回调定义了测试的「五段式」执行模型，@Nested 与实例生命周期（PER_CLASS）则决定测试如何组织与共享状态。掌握它们才能写出顺序无关、互不污染的可靠测试。

## 1. 生命周期执行模型

### 1.1 五段式顺序

```java
@BeforeAll  static void 一次：类加载后，所有测试之前（连接池、环境准备）
  @BeforeEach          每个测试前（构造对象、启动临时资源）
    @Test              被测方法
  @AfterEach           每个测试后（清理临时数据、关闭游标）
@AfterAll   static void 一次：所有测试之后（释放连接池）
```

```java
@BeforeAll
static void initPool() { /* 只跑一次：建立连接池 */ }

@BeforeEach
void setUp() {
    order = new Order(100, 50);          // 每个测试独立的对象
}

@AfterEach
void tearDown() {
    cache.clear();                        // 清理共享状态
}

@Test
void deduct() { order.deduct(30); assertEquals(70, order.getRemaining()); }
```

### 1.2 执行细节

- 默认 `@BeforeAll/@AfterAll` 必须为 **static**（PER_CLASS 模式下可非 static）；
- `@BeforeEach/@AfterEach` 可声明在父类、`@Nested` 外层与接口 default 方法中——继承规则：**先父类后子类**执行 Before，**先子类后父类**执行 After；
- 任一生命周期方法抛异常 → 该测试标记失败，后续生命周期仍按正常顺序收尾（After 系列**总会执行**）；
- **一个测试类可以有多个** `@BeforeEach`（JUnit 4 不行），顺序不定（不做保证），所以不要把顺序敏感的初始化拆到多个方法。

## 2. 实例生命周期与状态共享

### 2.1 PER_METHOD vs PER_CLASS

| 维度 | PER_METHOD（默认） | PER_CLASS |
|------|-------------------|-----------|
| 实例数 | 每个测试方法一个实例 | 整个类共享一个实例 |
| 字段状态 | 天然隔离（每次新建） | 测试间共享，需自清理 |
| `@BeforeAll/@AfterAll` | 必须 static | 可非 static |
| 并行 | 无限制 | 与并行执行有交互（见 05 模块） |
| 适用 | 默认、隔离优先 | 依赖注入初始化昂贵、无状态测试、按序共享数据 |

```java
@TestInstance(TestInstance.Lifecycle.PER_CLASS)
class HeavySetupTest {
    private final ExpensiveClient client;

    HeavySetupTest() {                       // 非 static @BeforeAll 可用构造器替代
        client = new ExpensiveClient();      // 只初始化一次
    }
}
```

> ⚠️ **共享可变状态是测试污染的根源**：PER_CLASS 下若测试 A 修改了字段而 B 依赖原始值，B 失败且表现为「顺序相关」。要么字段不可变，要么在 `@BeforeEach` 中重置。

### 2.2 状态共享的正确姿势

```java
private static final String USER_ID = "u-001";   // 常量共享：安全

@Test
void a_creates_user() { service.create(USER_ID); }

@Test
void b_uses_user() {
    assumeTrue(service.exists(USER_ID));          // 假设前序副作用，失败则跳过而非假失败
    assertEquals("u-001", service.get(USER_ID).id());
}
```

> 💡 测试间数据依赖是反模式；如果必须依赖，用「假设前置条件已满足」显式声明，让缺失依赖表现为 skipped 而非 passed/failed。

## 3. 执行顺序控制

默认顺序是确定性的（JUnit 5 起引入），但**故意不明显**，避免测试依赖顺序。JUnit 6 提供 `MethodOrderer.Default`/`ClassOrderer.Default` 作为该默认策略的显式名字。

### 3.1 方法排序策略

| `@TestMethodOrder(MethodOrderer.Xxx.class)` | 行为 |
|------|------|
| `MethodName` | 按方法名字典序（经典但脆弱：重命名即乱序） |
| `DisplayName` | 按显示名 |
| `OrderAnnotation` | 按 `@Order(n)` 升序 |
| `Random` | 随机（暴露顺序依赖） |
| `Default` | JUnit 6 新增：与默认相同的确定性顺序 |

```java
@TestMethodOrder(MethodOrderer.OrderAnnotation.class)
class PaymentTest {
    @Test @Order(1) void verify_card() { }
    @Test @Order(2) void charge() { }
    @Test @Order(3) void settle() { }
}
```

> ⚠️ JUnit 6 中 `MethodOrderer.Alphanumeric` 已移除，用 `Default` 或 `MethodName` 替代。**顺序注解只应服务于「可读性叙事」，任何要求顺序才能跑过的测试都是设计缺陷**。

### 3.2 JUnit 6 的顺序改进

- `@TestMethodOrder` 会**继承进 @Nested 内层类**；
- 内层类顺序默认确定性（但仍不明显），可显式用 `@TestClassOrder(ClassOrderer.OrderAnnotation.class)` + `@Order` 控制 `@Nested` 类之间的执行顺序；
- 注意：`@Nested` 内层类不能使用 `@TestInstance(PER_CLASS)`，且不支持 `@BeforeAll/@AfterAll` 以外生命周期的静态方法。

### 1.3 生命周期与接口 default 方法

Jupiter 支持在**接口的 default 方法**中声明生命周期回调，配合继承体系形成「测试基座」复用：

```java
public interface DbTestSupport {
    @BeforeEach
    default void initDataSource() { /* 每个测试前初始化数据源 */ }

    @AfterEach
    default void cleanupData() { /* 清理测试数据 */ }
}

class UserRepositoryTest implements DbTestSupport {
    @Test
    void insert() { /* 自动获得 init/cleanup */ }
}
```

**接口回调与类回调并存时的顺序**：同一测试类中，接口/父类声明的 `@BeforeEach` 先于子类自身执行；`@AfterEach` 相反。多接口 + 父类混用时顺序不做保证——**保持回调幂等**，不要在生命周期方法之间制造顺序敏感逻辑。

> 💡 接口 default 生命周期适合「跨多个测试类的公共资源契约」（数据源、缓存清理、固定时区），比继承父类更灵活（Java 单继承限制）。

## 4. @Nested 嵌套测试

### 4.1 动机与结构

`@Nested` 用非静态内部类把同一主题的测试组织成树，内层类**自动继承外层实例**（字段、BeforeEach），实现「共享上下文 + 分组叙事」：

```java
class OrderServiceTest {

    private OrderService service;
    private Order order;

    @BeforeEach
    void setUp() {
        service = new OrderService();
        order = new Order(100);
    }

    @Nested
    @DisplayName("扣减库存")
    class DeductStock {

        @Test
        void 余额充足时扣减成功() { /* 复用外层 order/service */ }

        @Test
        void 余额不足时抛出异常() {
            order.deduct(200);
            assertThrows(InsufficientBalanceException.class, () -> service.pay(order));
        }
    }

    @Nested
    class Refund { /* 独立的叙事分组 */ }
}
```

### 4.2 生命周期继承规则

| 场景 | 执行顺序 |
|------|---------|
| 外层 `@BeforeEach` + 内层 `@BeforeEach` | 先外层后内层 |
| 内层 `@AfterEach` + 外层 `@AfterEach` | 先内层后外层 |
| 内层继承外层字段 | 是（实例变量直接可见） |
| 内层是否能访问外层私有方法 | 是（同一顶层类编译单元） |

### 4.3 限制

- `@Nested` 类必须**非 static** 内部类；
- 默认每个测试方法 new 一个内层实例，但**同一个内层类的所有测试共享外层实例**？—— 不：默认 PER_METHOD 下，内层类的每个测试方法都会重建「外层实例 + 内层实例」整条链；
- 不能声明构造器参数（无参构造）；
- 内层类不支持 `@TestInstance(PER_CLASS)`。

> 💡 嵌套深度建议 ≤ 2 层：超过 3 层测试树会变成可读性负担。`@Nested` 的价值在于「语境共享 + 叙述分组」，不是为了追求层级。

### 4.4 嵌套测试实战模式

**模式：状态机驱动分组**——按业务状态组织 `@Nested`，每层显式声明前置：

```java
class OrderTest {

    @Nested
    @DisplayName("草稿状态")
    class Draft {
        @BeforeEach
        void setDraft() { order = OrderFactory.draft(); }

        @Test void 草稿可提交() { }
        @Test void 草稿不可退款() { assertThrows(...); }
    }

    @Nested
    @DisplayName("已支付状态")
    class Paid {
        @BeforeEach
        void setPaid() { order = OrderFactory.paid(); }

        @Test void 已支付可退款() { }
    }
}
```

**模式：Given-When-Then 叙事**——内层类名作为 Given，测试方法名表达 When-Then：

```java
class CartServiceTest {

    @Nested
    class 购物车为空 {
        @Test void 结算时提示空购物车() { }
    }

    @Nested
    class 购物车有商品 {
        @BeforeEach void addItems() { ... }
        @Test void 结算成功生成订单() { }
    }
}
```

> 💡 嵌套测试的价值排序：**可读性 > 复用性**。内层类共享外层 Setup 只是副产品，真正的收益是把「同主题测试」折叠成一棵可导航的树。

## 5. 常见反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 测试依赖另一个测试的执行结果 | 顺序耦合，单跑/并行必挂 | 独立准备数据（Given 阶段自给自足） |
| `@BeforeEach` 做复杂业务准备 | 隐藏依赖，失败难定位 | 用测试工厂方法显式构造，或 builder 模式 |
| 共享静态字段存可变状态 | 并行/顺序均可能污染 | 不可变常量或每次重建 |
| 用 `Thread.sleep` 等待异步 | 慢 + 脆弱 | Awaitility / 轮询直到条件 |
| `@AfterEach` 里写业务断言 | 收尾方法职责错位 | 断言永远在测试方法内 |
| 依赖 `@TestMethodOrder` 才能通过 | 测试耦合 | 消除顺序依赖，Random 排序验证 |

> 🎯 **核心要点**：生命周期模型的本质是「每个测试独立、可重复、可并行」——@BeforeEach/@AfterEach 负责每测重置，@AfterAll 负责全局收尾，PER_CLASS 只在你明确理解共享代价时启用；@Nested 是组织工具而非状态工具，内层继承外层的只是「构造上下文」而非「执行顺序」。
