## 1. 核心思想：用有限用例发现最多缺陷

### 1.1 测试用例设计的三问

| 问题 | 含义 |
|------|------|
| **测什么？** | 确定测试对象和范围（功能、接口、异常、边界） |
| **怎么测？** | 选择测试方法和数据（等价类、边界值、判定表等） |
| **够不够？** | 评估覆盖率和测试充分性 |

### 1.2 两大原则

> 💡 **原则一：穷举不可能，抽样是必然。** 一个输入域为 1~100 的整数参数，如果穷举需要 100 个用例；加上其他参数组合，用例数呈指数爆炸。必须用科学方法选取代表性样本。

> 💡 **原则二：缺陷非均匀分布**。80% 的 Bug 集中在 20% 的模块，而 Bug 在边界、组合、异常路径上的密度远高于正常路径。方法的意义就在于对准这些高发区域。

## 2. 等价类划分法

### 2.1 定义

将输入域划分为若干 **互不相交** 的等价类，每个等价类中的值在测试中具有"等价"的行为——测一个代表值等价于测整个类。

| 类型 | 定义 | 示例（年龄输入） |
|------|------|-----------------|
| **有效等价类** | 符合需求的、合法的输入 | `[1, 150]` 范围内的整数 |
| **无效等价类** | 不符合需求的、非法的输入 | `≤ 0`、`> 150`、非数字、空值 |

> ⚠️ **重要规则**：每个无效等价类**必须单独设计用例**（因为一个无效输入可能阻断后续校验，无法同时验证多个无效类）；有效等价类可以合并。

### 2.2 等价类表（完整示例）

**需求**：系统接受年龄输入，类型为整数，合法范围为 1~150（含边界），必填。

| 输入项 | 有效等价类 | 编号 | 无效等价类 | 编号 |
|--------|-----------|------|-----------|------|
| **年龄** | 1 ≤ age ≤ 150 的整数 | EC-01 | age ≤ 0 | EC-02 |
| | | | age > 150 | EC-03 |
| | | | 非整数（小数、字符） | EC-04 |
| | | | 空值 / null | EC-05 |

**另一种常见格式（结构化等价类表）：**

| 输入条件 | 有效类 | 无效类 |
|----------|--------|--------|
| **数据类型** | 整数 | 浮点数、字符串、布尔值、null |
| **数值范围** | 1 ~ 150 | < 1（含0和负数）、> 150 |
| **是否必填** | 输入值 | 空值（未输入） |

### 2.3 从等价类表到测试用例

| 用例ID | 覆盖等价类 | 输入 | 预期结果 | 说明 |
|--------|-----------|------|----------|------|
| TC-01 | EC-01: 有效类 | 25 | 成功 | 有效边界内 |
| TC-02 | EC-02: ≤ 0 | 0 | 提示"年龄必须≥1" | 下边界外 |
| TC-02b | EC-02: ≤ 0 | -5 | 提示"年龄必须≥1" | 负数 |
| TC-03 | EC-03: > 150 | 200 | 提示"年龄不能超过150" | 上边界外 |
| TC-04 | EC-04: 非整数 | 25.5 | 提示"请输入整数" | 浮点数 |
| TC-04b | EC-04: 非整数 | abc | 提示"请输入数字" | 字符串 |
| TC-05 | EC-05: 空值 | (空) | 提示"年龄不能为空" | 必填校验 |

> 🎯 **注意**：每个无效等价类一个独立用例（TC-02/TC-03/TC-04/TC-05 不能合并），有效等价类只用一个用例（TC-01）即可。

### 2.4 更多等价类划分示例

| 场景 | 输入类型 | 有效等价类 | 无效等价类 |
|------|---------|-----------|-----------|
| 手机号 | 11位数字，以1开头 | 1[3-9]XXXXXXXXX | 非1开头、不足11位、超过11位、含字母 |
| 密码 | 8~20位字母+数字 | 符合长度和字符要求 | 长度<8、长度>20、纯字母、纯数字、含特殊符号 |
| 邮箱 | 标准格式 | user@domain.tld | 无@、无域名、无用户名、含空格 |
| 金额 | 0.01~99999.99两位小数 | 符合范围和精度 | <0.01、>99999.99、三位小数、负数 |

## 3. 边界值分析法

### 3.1 为什么 Bug 常在边界？

> ⚠️ 开发者的常见错误：
> - **数组越界**：`int[] arr = new int[10]; arr[10] = 1;`（索引 0~9，访问了 arr[10]）
> - **循环偏移**：`for (int i = 0; i <= arr.length; i++)`（多了一次）
> - **比较运算符**：`if (age >= 150)` 写成了 `if (age > 150)`
> - **整数溢出**：`int total = price * count;` 当 price=20000, count=100000 时溢出

边界值分析正是针对这类问题的系统性方法。

### 3.2 取点策略

对于取值范围 `[min, max]`（闭区间），选取 7 个关键点：

```
min-1, min, min+1, 正常值, max-1, max, max+1
```

| 符号 | 含义 | 年龄示例（1~150） |
|------|------|------------------|
| min-1 | 下边界外（无效） | 0 |
| min | 下边界上（有效） | 1 |
| min+1 | 下边界内（有效） | 2 |
| normal | 正常值 | 75 |
| max-1 | 上边界内（有效） | 149 |
| max | 上边界上（有效） | 150 |
| max+1 | 上边界外（无效） | 151 |

**完整测试用例：**

| 用例ID | 输入 | 理由 |
|--------|------|------|
| BV-01 | 0 | min-1，验证下边界外 |
| BV-02 | 1 | min，验证下边界 |
| BV-03 | 2 | min+1，验证下边界内 |
| BV-04 | 75 | 中间值 |
| BV-05 | 149 | max-1，验证上边界内 |
| BV-06 | 150 | max，验证上边界 |
| BV-07 | 151 | max+1，验证上边界外 |

### 3.3 常见数据类型的边界值

| 数据类型 | 边界值分析 |
|----------|-----------|
| **整数范围** | 最小值-1, 最小值, 最小值+1, ..., 最大值-1, 最大值, 最大值+1 |
| **浮点数精度** | 0.009, 0.01, 0.011 （金额保留两位小数） |
| **字符串长度** | 空串, 长度1, 长度n-1, 长度n, 长度n+1 |
| **数组/集合长度** | 空, 大小1, 大小n-1, 大小n, 大小n+1 |
| **时间/日期** | 边界秒、跨年、2月28/29日、闰年判断 |

### 3.4 边界值 + 等价类 = 黄金组合

> 🎯 **实践中，等价类 + 边界值通常结合使用**：先用等价类划分有效/无效域，然后在每个域的边界处取点测试。这是最基础、最高效的用例设计组合。

```text
流程：需求分析 → 等价类划分 → 边界值确定 → 测试用例生成
                                          ↓
                                  等价类表 → 每个类的边界值
```

## 4. 判定表法

### 4.1 定义

当输入条件之间存在 **逻辑组合关系** 时，判定表能系统性地枚举所有条件组合，避免遗漏。

### 4.2 判定表结构

| 组成部分 | 含义 | 说明 |
|----------|------|------|
| **条件桩 (Condition Stub)** | 列出所有输入条件 | 如：是否是VIP、金额是否>100 |
| **条件项 (Condition Entry)** | 各条件的状态取值 | T/F（真/假） |
| **动作桩 (Action Stub)** | 列出所有可能的结果 | 如：通过、拦截 |
| **动作项 (Action Entry)** | 各组合对应的动作 | 每个组合对应的预期结果 |

### 4.3 完整示例：优惠券使用规则

**需求描述：**
- 如果用户是 **VIP会员** **且** 订单金额 **> 100**  **且** 优惠券 **未过期**，则可以使用优惠券；
- 其余情况 **一律不能使用**，并给出具体提示信息（VIP提示、金额提示、过期提示）。

**步骤1：确定条件和动作**

| 条件 | 标识 | 取值 |
|------|------|------|
| 是否是VIP？ | C1 | T / F |
| 金额 > 100？ | C2 | T / F |
| 优惠券未过期？ | C3 | T / F |

| 动作 | 标识 | 说明 |
|------|------|------|
| 可使用优惠券 | A1 | 减免金额 |
| 提示"仅限VIP" | A2 | C1=F 时触发 |
| 提示"金额不足" | A3 | C2=F 时触发 |
| 提示"优惠券已过期" | A4 | C3=F 时触发 |

**步骤2：构建全组合判定表（3条件 = 8种组合）**

| 组合# | C1: 是VIP | C2: 金额>100 | C3: 未过期 | 动作 |
|-------|-----------|-------------|-----------|------|
| 1 | T | T | T | **A1: 可使用** |
| 2 | T | T | F | A4: 提示已过期 |
| 3 | T | F | T | A3: 提示金额不足 |
| 4 | T | F | F | A3 + A4 |
| 5 | F | T | T | A2: 提示仅限VIP |
| 6 | F | T | F | A2 + A4 |
| 7 | F | F | T | A2 + A3 |
| 8 | F | F | F | A2 + A3 + A4 |

**步骤3：化简判定表**

> 💡 如果某些条件组合的动作完全一致，可以合并（用 `-` 表示"任意值"）。

观察上面的表：只要 C1=F，无论 C2/C3 是什么，都会触发 A2（提示仅限VIP），所以可以化简：

| 组合# | C1: 是VIP | C2: 金额>100 | C3: 未过期 | 动作 |
|-------|-----------|-------------|-----------|------|
| 1 | T | T | T | A1: 可使用 |
| 2 | T | T | F | A4: 提示已过期 |
| 3 | T | F | — | A3: 提示金额不足 |
| 4 | F | — | — | A2: 提示仅限VIP |

从 8 个组合化简为 4 个规则。

**步骤4：生成测试用例**

| 用例ID | 规则 | VIP | 金额 | 券未过期 | 预期结果 |
|--------|------|-----|------|---------|----------|
| DT-01 | 规则1 | T | 150 | T | 优惠券可用，减免金额 |
| DT-02 | 规则2 | T | 150 | F | 提示"优惠券已过期" |
| DT-03 | 规则3 | T | 50 | T/F | 提示"订单金额不足100元" |
| DT-04 | 规则4 | F | 任意 | 任意 | 提示"仅限VIP会员使用" |

### 4.4 判定表法适用场景

| 适用 ✅ | 不适用 ❌ |
|--------|----------|
| 业务规则复杂的场景（保险、金融、风控） | 条件之间有关联依赖无法独立 |
| 条件数量适中（3~6个条件最佳） | 条件过多（>10个 → 组合爆炸） |
| 每个条件的取值是布尔值（T/F） | 条件的取值是连续数值（先等价类化） |

> ⚠️ **条件数量问题**：n 个条件 → 2^n 种组合。6 个条件 = 64 种，8 个条件 = 256 种。条件过多时考虑正交实验法简化。

## 5. 因果图法

### 5.1 定义

因果图是判定表的前置步骤，它用图形化的方式表达 **输入条件（因）** 与 **输出结果（果）** 之间的逻辑关系，然后转化为判定表。

### 5.2 因果图基本符号

| 符号 | 名称 | 关系 | 真值表 |
|------|------|------|--------|
| `C1 --- M1` | 恒等 (Identity) | C1=T → M1=T | C1=T,T=F  → M1=T,F |
| `C1 o---o M1` | **~** 非 (NOT) | C1=F → M1=T | C1=T,T=F → M1=F,T |
| `C1 o---o M1` | **V** 或 (OR) | C1 或 C2=T → M1=T | FF=F, 其他=T |
| `C1 o---o M1` | **^** 与 (AND) | C1 且 C2=T → M1=T | TT=T, 其他=F |
| `C1 o---o C2 (E)` | 互斥 (Exclusive) | C1 和 C2 最多一个为T | 不能同时为T |
| `C1 o---o C2 (I)` | 包含 (Inclusive) | C1 和 C2 至少一个为T | 不能同时为F |
| `C1 o---o C2 (R)` | 要求 (Requires) | C1=T 时 C2 必须=T | — |
| `C1 o---o C2 (M)` | 屏蔽 (Masks) | C1=T 时 C2 必须=F | — |

### 5.3 完整示例

**需求**：饮料自动售货机
- 投入 **1元硬币** 或 **2元硬币** 可购买饮料（售价2元）
- 投入 2 元时直接出货
- 投入 1 元时需再投入 1 元才出货
- 金额不足时显示"余额不足"

**步骤1：分析因果关系**

| 条件（因） | 标识 |
|-----------|------|
| 投入1元硬币 | C1 |
| 投入2元硬币 | C2 |
| 累计金额 = 2元 | C3（中间节点，由C1、C2计算得出） |

| 结果（果） | 标识 |
|-----------|------|
| 出货 | E1 |
| 提示"余额不足" | E2 |
| 退币 | E3 |

**步骤2：画出因果图（文本表示）**

```
C1 (1元) ──╮
           ├── AND ──→ C3 (累计=2元) ──╮
C2 (2元) ──╯                          ├──→ E1 (出货)
                                      │
               NOT ──→ C3=F ──────→ E2 (余额不足)
```

**步骤3：转化为判定表**

| 组合 | C1: 1元 | C2: 2元 | 中间: 累计=2元 | 动作 |
|------|---------|---------|---------------|------|
| 1 | T | F | F(需再投1元) | E2: 余额不足 |
| 2 | F | T | T | E1: 出货 |
| 3 | T | T | T(超了) | E1+E3: 出货+退多余 |
| 4 | F | F | F | E2: 余额不足 |

**步骤4：生成测试用例**

| 用例 | 动作 | 预期 |
|------|------|------|
| 投1元 | 投1元 | 提示余额不足，需再投1元 |
| 投2元 | 投2元 | 直接出货 |
| 投1元→再投1元 | 投1元→再投1元 | 累积2元，出货 |
| 投1元→再投2元 | 投1元→再投2元 | 累积3元，出货+退1元 |

> 🎯 **因果图的本质**：是判定表的"设计图纸"，帮助测试分析人员理清复杂条件关系后再填表，避免直接填表时遗漏逻辑约束（如互斥、包含、屏蔽关系）。

## 6. 正交实验法

### 6.1 组合爆炸问题

假设有 4 个因素，每个因素 3 个水平：
- 穷举组合：3⁴ = **81 个用例**
- 正交实验法：用 L₉ 正交表只需 **9 个用例**，覆盖所有两两组合

> 💡 **核心思想**：正交实验法基于**每两个因素的所有水平组合至少出现一次**的原则，用远少于穷举的用例覆盖"因素间的交互影响"。

### 6.2 正交表的基本概念

| 术语 | 含义 | 示例 |
|------|------|------|
| **因素 (Factor)** | 输入变量 | 浏览器、操作系统、网络 |
| **水平 (Level)** | 每个因素的取值 | Chrome/Edge/Firefox |
| **正交表 (Orthogonal Array)** | 实验安排矩阵 | L₉(3⁴) |
| **L₉(3⁴)** | 9次实验，最多4因素，每因素3水平 | — |

### 6.3 完整示例：搜索结果测试

**因素与水平：**

| 因素 | 水平1 | 水平2 | 水平3 |
|------|-------|-------|-------|
| A: 搜索引擎 | Google | Bing | 百度 |
| B: 浏览器 | Chrome | Edge | Firefox |
| C: 网络环境 | WiFi | 4G | 宽带 |
| D: 搜索关键词 | 短词(1字) | 中词(3字) | 长句(10字+) |

**选择正交表**：4 因素 3 水平 → L₉(3⁴) 正交表

**L₉(3⁴) 正交表结构：**

| 实验号 | A: 搜索引擎 | B: 浏览器 | C: 网络 | D: 关键词 |
|--------|------------|-----------|---------|----------|
| 1 | Google | Chrome | WiFi | 短词 |
| 2 | Google | Edge | 4G | 中词 |
| 3 | Google | Firefox | 宽带 | 长句 |
| 4 | Bing | Chrome | 4G | 长句 |
| 5 | Bing | Edge | 宽带 | 短词 |
| 6 | Bing | Firefox | WiFi | 中词 |
| 7 | 百度 | Chrome | 宽带 | 中词 |
| 8 | 百度 | Edge | WiFi | 长句 |
| 9 | 百度 | Firefox | 4G | 短词 |

**验证两两覆盖**：在 9 个用例中，任意两个因素的任意水平组合**恰好出现一次**。比如：
- (Google, Chrome) 出现在实验1
- (Google, Edge) 出现在实验2
- (Bing, 4G) 出现在实验4
- ... 所有 36 种两两组合（4选2 × 3×3 = 36）各出现一次

### 6.4 常用正交表参考

| 正交表 | 说明 | 用例数 vs 穷举 |
|--------|------|---------------|
| L₄(2³) | 3因素2水平 | 4 vs 8 |
| L₈(2⁷) | 7因素2水平 | 8 vs 128 |
| L₉(3⁴) | 4因素3水平 | 9 vs 81 |
| L₁₆(4⁵) | 5因素4水平 | 16 vs 1024 |
| L₁₈(3⁷) | 7因素3水平 | 18 vs 2187 |

> ⚠️ **注意**：正交实验法假设因素之间**无高阶交互作用**（即三因素以上交互可忽略），这在软件测试中通常是合理的。如果怀疑有高阶交互，需增加用例。

### 6.5 正交实验法的适用场景

| 场景 | 说明 |
|------|------|
| 配置兼容性测试 | 多浏览器 × 多OS × 多网络环境 |
| 参数组合测试 | 多输入参数不同取值组合 |
| 数据库查询测试 | 多字段不同的筛选条件组合 |
| API接口兼容测试 | 不同版本 × 不同协议 × 不同认证方式 |

## 7. 场景法

### 7.1 定义

场景法基于**用户使用系统的实际业务流程**来设计用例。一个"场景"就是一条用户操作路径。与判定表/等价类不同，场景法关注的是**业务流程的完整流转**，而非单个输入条件。

### 7.2 基本流 + 备选流

| 类型 | 含义 | 说明 |
|------|------|------|
| **基本流 (Basic Flow)** | 用户正常完成业务的全过程 | 无任何异常、所有步骤顺利通过 |
| **备选流 (Alternative Flow)** | 基本流的变体 | 异常处理、分支条件、可选路径 |
| **异常流 (Exception Flow)** | 系统出错或用户中断 | 超时、网络断开、系统崩溃 |

### 7.3 场景矩阵

> 💡 基于流程图分析→提取场景路径→生成场景矩阵

**场景矩阵生成规则：**
- R1 = 基本流
- R2 = 基本流 + 备选流1
- R3 = 基本流 + 备选流2
- R4 = 基本流 + 备选流3
- R5 = 基本流 + 备选流1 + 备选流2
- ...以此类推

### 7.4 完整示例：电商下单

**步骤1：画出业务流程图（文本描述）**

```text
登录 ─→ 搜索商品 ─→ 加入购物车 ─→ 结算 ─→ 选择地址 ─→ 支付 ─→ 完成
  │          │            │          │         │         │
  │          ↓            ↓          ↓         ↓         ↓
  │      ⚠️ 无结果    ⚠️ 库存不足  ⚠️ 未选地址  ⚠️ 余额不足
  │          │            │          │         │
  ↓          ↓            ↓          ↓         ↓
 ⚠️ 未登录 → 重新搜索 → 提示缺货 → 提示选择 → 选择其他支付
                                    → 新增地址
```

**步骤2：提取场景（基本流 + 备选流）**

| 场景ID | 路径 | 说明 |
|--------|------|------|
| **S-01** | 基本流 | 登录 → 搜索 → 加购物车 → 结算 → 选择地址 → 支付成功 → 完成 |
| **S-02** | 备选流1-无搜索结果 | 搜索 → 无结果 → 提示"未找到商品" → 返回搜索 |
| **S-03** | 备选流2-库存不足 | 加购物车 → 结算 → 库存不足 → 提示"缺货" → 取消订单 |
| **S-04** | 备选流3-未选地址 | 结算 → 未设置地址 → 提示"请添加收货地址" → 新增地址 → 继续 |
| **S-05** | 备选流4-余额不足 | 支付 → 余额不足 → 提示 → 选择其他支付方式 → 重新支付 |
| **S-06** | 备选流5-支付超时 | 支付 → 超时未支付 → 订单自动取消 → 提示用户 |
| **S-07** | 异常流-网络中断 | 支付中 → 网络断开 → 提示网络异常 → 恢复后重试 |
| **S-08** | 异常流-未登录下单 | 未登录 → 加购物车 → 结算 → 跳转登录页 → 登录后继续 |

**步骤3：生成详细测试用例**

以 S-01（基本流）为例：

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 输入正确账号密码登录 | 登录成功，跳转首页 |
| 2 | 搜索"华为手机" | 显示搜索结果列表 |
| 3 | 选择一款手机加入购物车 | 提示"已加入购物车"，购物车+1 |
| 4 | 点击"去结算" | 进入订单确认页 |
| 5 | 选择已保存的地址 | 地址信息正确显示 |
| 6 | 点击"立即支付" | 跳转支付页面 |
| 7 | 选择支付方式并确认 | 支付成功，跳转订单详情页 |
| 8 | 查看订单状态 | 状态为"待发货" |

### 7.5 场景法 vs 判定表

| 维度 | 场景法 | 判定表 |
|------|--------|--------|
| **关注点** | 业务流程的完整路径 | 条件逻辑的组合 |
| **粒度** | 宏观（多个步骤） | 微观（单个步骤的判断） |
| **适用** | 端到端业务流程 | 复杂业务规则 |
| **产出** | 场景矩阵 + 场景用例 | 条件组合表 |
| **结合** | 场景法中的每个步骤可以进一步用判定表设计 | — |

## 8. 状态转换测试

### 8.1 定义

状态转换测试关注的是系统/对象**在不同状态之间的迁移**，适用于具有明确状态机的系统（订单、工作流、会话）。

### 8.2 核心元素

| 元素 | 含义 |
|------|------|
| **状态 (State)** | 系统在某一时刻的稳定状况 |
| **事件 (Event)** | 触发状态转换的动作或输入 |
| **转换 (Transition)** | 从一个状态到另一个状态的迁移 |
| **初始状态** | 对象创建后的第一个状态 |
| **终止状态** | 对象生命周期结束的状态（通常有"终态"标记） |

### 8.3 状态转换图 → 状态转换表 → 测试用例

**核心流程：**

```text
状态转换图 (State Diagram)
      ↓
状态转换表 (State Transition Table)
      ↓
测试用例 (Test Cases)
```

### 8.4 完整示例：订单状态机

**状态定义：**

| 状态 | 标识 | 说明 |
|------|------|------|
| 待支付 | PENDING_PAY | 订单已创建，等待用户支付 |
| 已支付 | PAID | 用户已付款，等待商家处理 |
| 已发货 | SHIPPED | 商家已发货，等待用户收货 |
| 已完成 | COMPLETED | 用户确认收货，订单完成 |
| 已取消 | CANCELLED | 订单被取消（终态） |
| 退款中 | REFUNDING | 用户申请退款 |
| 已退款 | REFUNDED | 退款完成（终态） |

**状态转换图：**

```text
    ┌────────────┐  支付   ┌────────┐  发货   ┌─────────┐  收货   ┌───────────┐
    │  PENDING   │ ─────→ │ PAID   │ ─────→ │ SHIPPED │ ─────→ │ COMPLETED │
    │  _PAY      │         │        │         │         │        │           │
    └─────┬──────┘         └───┬────┘         └────┬────┘        └───────────┘
          │                    │                   │
          │ 取消               │ 退款申请          │ 退款申请
          ↓                    ↓                   ↓
    ┌────────────┐      ┌────────────┐      ┌───────────┐
    │ CANCELLED  │      │ REFUNDING  │ ──→ │ REFUNDED  │
    │ (终态)     │      │            │      │ (终态)    │
    └────────────┘      └────────────┘      └───────────┘
```

**状态转换表：**

| 当前状态 | 事件 | 下一个状态 | 是否有效 |
|---------|------|-----------|---------|
| PENDING_PAY | 支付 | PAID | ✅ |
| PENDING_PAY | 取消 | CANCELLED | ✅ |
| PENDING_PAY | 发货 | — | ❌（未支付不能发货） |
| PENDING_PAY | 退款 | — | ❌（未支付无款可退） |
| PAID | 发货 | SHIPPED | ✅ |
| PAID | 退款申请 | REFUNDING | ✅ |
| PAID | 支付 | — | ❌（重复支付） |
| PAID | 取消 | CANCELLED | ✅（部分系统允许） |
| SHIPPED | 收货 | COMPLETED | ✅ |
| SHIPPED | 退款申请 | REFUNDING | ✅ |
| SHIPPED | 发货 | — | ❌（重复发货） |
| COMPLETED | 退款申请 | REFUNDING | ✅（售后） |
| REFUNDING | 退款处理 | REFUNDED | ✅ |
| REFUNDED | 任何操作 | — | ❌（终态） |
| CANCELLED | 任何操作 | — | ❌（终态） |

**测试用例生成：**

| 用例ID | 前置状态 | 操作 | 预期新状态 | 覆盖类型 |
|--------|---------|------|-----------|---------|
| ST-01 | PENDING_PAY | 用户支付 | PAID | 有效转换 |
| ST-02 | PENDING_PAY | 用户取消 | CANCELLED | 有效转换 |
| ST-03 | PENDING_PAY | 管理员发货 | 提示"未支付" | 无效转换 |
| ST-04 | PAID | 商家发货 | SHIPPED | 有效转换 |
| ST-05 | PAID | 用户再次支付 | 提示"已支付" | 无效转换 |
| ST-06 | PAID | 用户申请退款 | REFUNDING | 有效转换 |
| ST-07 | SHIPPED | 用户确认收货 | COMPLETED | 有效转换 |
| ST-08 | SHIPPED | 商家再次发货 | 提示"已发货" | 无效转换 |
| ST-09 | COMPLETED | 申请售后退款 | REFUNDING | 有效转换 |
| ST-10 | REFUNDING | 平台处理退款 | REFUNDED | 有效转换 |
| ST-11 | REFUNDED | 任何操作 | 提示"订单已关闭" | 终态保护 |
| ST-12 | CANCELLED | 用户支付 | 提示"订单已取消" | 终态保护 |

### 8.5 状态转换测试的测试覆盖准则

| 覆盖级别 | 说明 | 要求 |
|----------|------|------|
| **单步覆盖** | 每个有效转换至少执行一次 | 最基础 |
| **全状态覆盖** | 每个状态至少访问一次 | 基础要求 |
| **全转换覆盖** | 所有有效+无效转换都执行 | 全面 |
| **路径覆盖** | 所有状态-事件路径都执行 | 最严格（通常不必要） |
| **N步切换覆盖** | 所有N步转换序列 | 介于转换和路径之间 |

> 💡 **实践中**：全状态覆盖 + 全转换覆盖是推荐标准。路径覆盖可能导致用例爆炸（状态机有环路时路径无限）。

## 9. 错误推测法

### 9.1 定义

依赖测试人员的**经验和直觉**，猜测系统哪些地方容易出错，针对性地设计测试用例。这不是一种"结构化"方法，而是等价类/边界值/判定表等方法的**补充**。

### 9.2 常见的"容易错"模式

| 类别 | 容易出错的地方 |
|------|---------------|
| **数值处理** | 除零、负数、大数（溢出）、精度损失、空值 |
| **字符串** | 空串、超长、特殊字符、HTML注入、SQL注入、Unicode |
| **集合** | 空集合、单元素集合、满容量、并发修改 |
| **边界** | 0和1、最大值最小值、日期：02-29, 00:00, 23:59 |
| **并发** | 竞态条件、死锁、ABA问题、重入 |
| **文件** | 不存在、权限不足、格式错误、已打开、磁盘满 |
| **网络** | 超时、断连、重试、DNS解析失败、负载均衡 |
| **状态** | 重复操作、逆序操作、中断恢复、已删除对象 |
| **缓存** | 缓存穿透、缓存雪崩、数据不一致 |
| **第三方** | 接口返回异常、降级、熔断、限流 |

### 9.3 错误推测检查清单示例

```text
□ 输入为空时系统表现如何？
□ 连续快速点击提交按钮会怎样？
□ 网络请求超时后是否自动重试？重试多少次？
□ 同时打开两个页面操作同一数据会怎样？
□ 文件上传大小刚好超过限制会怎样？
□ 非常规操作顺序（如先收货再付款）？
□ 数据库中数据被手动修改或删除会怎样？
□ 日期跨越闰年、时区、夏令时？
□ 输入包含 emoji 或零宽字符？
□ 并发下单抢购时库存是否超卖？
```

> ⚠️ **错误推测法的局限性**：依赖于个人经验，无法系统化，不能保证覆盖度。适合作为其他方法的**补充**而不是**替代**。团队可以使用"Bug 大本营"（历史 Bug 汇总表）来积累错误推测的经验库。

## 10. 探索性测试

### 10.1 定义

探索性测试（Exploratory Testing, ET）不同于传统的"先写用例再执行"模式，而是**同时进行测试设计、测试执行和测试学习**。测试人员在测试过程中不断探索系统行为，实时调整测试方向。

### 10.2 与传统脚本测试的对比

| 维度 | 脚本测试 (Scripted Testing) | 探索性测试 (Exploratory Testing) |
|------|---------------------------|--------------------------------|
| **用例** | 事先编写，严格按步骤执行 | 边测边发现，实时生成 |
| **设计时间** | 测试执行前集中设计 | 测试执行过程中持续设计 |
| **覆盖** | 预定义，可度量 | 取决于测试人员的探索路径 |
| **文档** | 详细的测试用例文档 | 探索笔记、Session报告 |
| **发现Bug类型** | 期望的、可预见的 | 意外的、深层的 |
| **适用阶段** | 回归测试、验收测试 | 新功能探索、安全测试、可用性测试 |
| **自动化** | 适合自动化 | 本质是手工（但可借助工具辅助） |

### 10.3 Session-Based Test Management (SBTM)

> 💡 **SBTM 是探索性测试的结构化框架**，将探索过程组织为一个个"Session"，每个 Session 有明确的**任务目标**和**时间盒**。

**SBTM Session 结构：**

```text
┌─────────────────────────────────────┐
│        探索测试 Session              │
│  ┌───────────────────────────────┐  │
│  │ 任务描述 (Mission)            │  │
│  │ "探索支付功能的边界条件"      │  │
│  ├───────────────────────────────┤  │
│  │ 时间盒 (Time Box): 45分钟    │  │
│  ├───────────────────────────────┤  │
│  │ Session 记录 Sheet:          │  │
│  │  - 测试的区域                 │  │
│  │  - 设计/执行的测试            │  │
│  │  - 发现的缺陷                 │  │
│  │  - 覆盖的功能点               │  │
│  │  - 测试笔记/疑问              │  │
│  │  - 下一步建议                 │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

### 10.4 SBTM 报告模板

| 字段 | 内容 |
|------|------|
| Session ID | ET-20260727-001 |
| 测试人员 | 张三 |
| 任务 | 探索"跨天订单"的状态转换 |
| 时间 | 2026-07-27 14:00 ~ 14:45 |
| 测试区域 | 订单模块：跨天支付、跨天取消 |
| 执行用例数 | 12 个 |
| 发现Bug数 | 3 个（1个严重，2个一般） |
| 覆盖的功能点 | 订单超时取消、次日支付、次日退款 |
| 测试笔记 | 跨天支付后订单时间显示有误 |
| 建议 | 建议增加支付时间戳的时区处理 |

### 10.5 什么时候用探索性测试

| 场景 | 说明 |
|------|------|
| **新功能首次测试** | 脚本用例还没写好，先用ET快速摸清功能 |
| **安全测试** | 攻击路径本身需要探索 |
| **可用性测试** | 真实用户的非预期操作 |
| **脚本测试的补充** | 脚本测完后的自由探索 |
| **时间紧迫** | 来不及写完整脚本时 |

> ⚠️ **不要过度依赖探索性测试**。没有脚本的ET无法回归、覆盖率难以度量、质量取决于个人能力。最佳实践是"脚本测试 + 探索性测试"结合。

## 11. 方法选择决策表

### 11.1 按测试场景选择

| 场景类型 | 推荐方法 | 理由 |
|---------|----------|------|
| **输入有明确取值范围** | 等价类 + 边界值 | 减少用例，捕获边界Bug |
| **多个条件组合决定结果** | 判定表 | 系统性枚举组合 |
| **条件多（>6）且需要缩减** | 正交实验法 | 用最少用例覆盖两两组合 |
| **业务流程图清晰** | 场景法 | 关注用户操作路径 |
| **系统有明确状态机** | 状态转换测试 | 覆盖所有状态迁移 |
| **需要补充非预期场景** | 错误推测法 | 基于经验补漏 |
| **新功能/需求模糊** | 探索性测试 | 边测边学 |
| **配置兼容性矩阵** | 正交实验法 | 多因素多水平的组合优化 |
| **API参数校验** | 等价类 + 边界值 + 错误推测 | 输入校验最有效 |
| **数据库CRUD操作** | 等价类 + 边界值 + 状态转换 | 数据类型+记录状态 |
| **复杂业务规则引擎** | 因果图 → 判定表 | 先画因果再填表 |
| **用户界面流程测试** | 场景法 + 探索性测试 | 流程 + 意外操作 |
| **支付/金融系统** | 全方法组合 | 高可靠性要求 |
| **回归测试** | 脚本化场景法 + 正交实验 | 快速验证已有功能 |

### 11.2 方法选择流程图

```text
是否有明确的输入取值范围？
    ├── 是 → 等价类 + 边界值（基础必备）
    └── 否 → 是否有条件组合逻辑？
                ├── 是 → 条件数 ≤ 6？
                │         ├── 是 → 判定表法（→ 因果图辅助）
                │         └── 否 → 正交实验法
                └── 否 → 是否有业务流程路径？
                            ├── 是 → 场景法
                            └── 否 → 是否有状态变化？
                                        ├── 是 → 状态转换测试
                                        └── 否 → 错误推测法 + 探索性测试
```

### 11.3 方法组合策略（推荐）

> 🎯 **高质量测试用例设计 = 等价类/边界值（基础） + 判定表/场景法（逻辑/流程） + 错误推测法（补充）**

| 优先级 | 方法 | 作用 |
|--------|------|------|
| **P0 - 必做** | 等价类 + 边界值 | 覆盖所有输入域，确保基础正确性 |
| **P1 - 核心** | 判定表 或 场景法 | 覆盖逻辑组合或业务流程 |
| **P2 - 强化** | 状态转换测试 | 针对有状态系统 |
| **P3 - 补充** | 错误推测法 + 探索性测试 | 发现边界外的Bug |
| **P4 - 优化** | 正交实验法 | 减少组合用例数量 |

## 总结：用例设计方法全景

| 方法 | 核心思想 | 最佳搭档 | 发现Bug类型 |
|------|---------|---------|------------|
| 等价类划分 | 分类抽样，减少用例 | 边界值分析 | 功能缺失 |
| 边界值分析 | 边界最容易出错 | 等价类划分 | 数组溢出、越界 |
| 判定表方法 | 不遗漏任何组合 | 因果图 | 逻辑遗漏 |
| 因果图法 | 可视化条件关系 | 判定表 | 复杂规则 |
| 正交实验法 | 两两覆盖降维 | 等价类 | 配置兼容 |
| 场景法 | 模拟真实用户 | 判定表 | 流程阻断 |
| 状态转换 | 状态机覆盖率 | 场景法 | 非法状态迁移 |
| 错误推测 | 经验驱动的补漏 | 上述所有方法 | 非预期异常 |
| 探索性测试 | 边测边学 | 脚本测试 | 深层/意外Bug |

> 🎯 **测试设计的成熟度演进**：
> - **Level 1（新手）**：只凭感觉点，不考虑覆盖
