## 1. 软件维护概述

### 1.1 维护的真实占比

```text
软件全生命周期成本分布:
  开发: ~20%
  维护: ~80%  ← 这才是软件真正的成本大头！

维护时间分布（经典论文 Lientz & Swanson, 1980）:
  适应性维护: 25%  (适应新环境)
  完善性维护: 50%  (新增/改进功能)
  纠错性维护: 21%  (修Bug)
  预防性维护: 4%   (防患未然)
```

### 1.2 维护的本质挑战

| 挑战 | 说明 | 对策 |
|------|------|------|
| **代码理解** | 维护者通常不是原开发者 | 好的注释+设计文档+命名 |
| **牵一发动全身** | 改一处导致远处崩溃 | 单元测试覆盖 + 解耦设计 |
| **文档过时** | 代码改了文档没改 | 文档即代码（Markdown in Git） |
| **技术债务累积** | 每次改都加一点"捷径" | 定期重构+债务管理 |
| **士气问题** | 维护工作被视为"低级工作" | 认可维护价值，轮岗制度 |

## 2. 四种维护类型

### 2.1 四种维护对比

| 类型 | 定义 | 触发条件 | 占比 | Java示例 |
|------|------|----------|:---:|----------|
| **纠错性** | 修复发现的Bug | 生产事故/测试失败 | 21% | 修复NPE |
| **适应性** | 适应外部环境变化 | OS升级/JDK升级/依赖变更 | 25% | javax→jakarta迁移 |
| **完善性** | 新增功能/改进性能 | 用户需求/业务要求 | 50% | 增加导出功能 |
| **预防性** | 防止未来问题 | 代码审查/架构评估 | 4% | 拆分God Class |

### 2.2 维护成本对比

```text
同一功能的不同实现方式的维护成本：

方案A（清晰设计）：
  public Order createOrder(OrderDTO dto) {
      validate(dto);
      Order order = orderFactory.create(dto);
      order = orderRepository.save(order);
      eventPublisher.publish(new OrderCreatedEvent(order));
      return order;
  }
  维护成本: ★☆☆☆☆（意图清晰、修改风险低）

方案B（"聪明"但难懂的设计）：
  public Order createOrder(OrderDTO dto) {
      return Stream.of(dto)
          .filter(this::validate)
          .map(orderFactory::create)
          .peek(orderRepository::save)
          .peek(o -> eventPublisher.publish(new OrderCreatedEvent(o)))
          .findFirst().orElseThrow();
  }
  维护成本: ★★★★★（过度使用Stream、难以调试、peek有副作用）

结论：代码的可读性直接决定维护成本。写"聪明"代码本质是把维护成本转移给后来人。
```

## 3. 重构：改善既有代码设计

### 3.1 重构的定义

> Martin Fowler: **重构 = 在不改变代码外部行为的前提下，改善其内部结构。**

```text
重构 ≠ 重写 (Rewrite)

重构：小步快跑、持续改进、测试保护、外部行为不变
重写：推倒重来、周期长、风险高、可能丢失隐藏的业务逻辑
```

### 3.2 常见坏味道与重构手法

| 坏味道 (Code Smell) | 重构手法 | Java示例 |
|---------------------|----------|----------|
| **过长方法** (>50行) | 提取方法 (Extract Method) | 将一段逻辑提取为独立方法 |
| **过大的类** (>500行) | 提取类 (Extract Class) | 将部分职责移到新类 |
| **过长参数列表** (>4个) | 引入参数对象 | 封装为DTO |
| **重复代码** | 提取方法/抽取超类 | DRY原则 |
| **Switch语句** | 多态替换条件 | 策略模式 |
| **特性依恋** | 移动方法 | 方法移到它最常访问的类 |
| **数据泥团** | 提取类 | 总一起出现的字段封装为对象 |
| **发散式变化** | 提取类 | 一个类因多种原因被修改 |
| **霰弹式修改** | 移动方法/字段 | 一个变化需要修改多个类 |
| **注释过多** | 重命名/提取方法 | 好代码自注释，注释解释WHY |

### 3.3 重构安全网

```text
重构三步安全保障：
1. 重构前 → 确保有足够的测试覆盖（至少核心路径）
2. 重构中 → 小步修改 + 频繁运行测试
3. 重构后 → 测试全部通过，方可继续下一处

没有测试的重构 ≈ 不带安全绳攀岩
```

### 3.4 重构示例：提取方法


## 4. 技术债务管理

### 4.1 技术债务四象限

```text
                蓄意 (Deliberate)
                     │
         Quadrant I  │  Quadrant II
         "我们知道    │  "我们不知道
          但选择欠债" │   但选择欠债"
         例：为赶发布│  例：用了不知道
         hardcode配置│  有bug的第三方库
  鲁莽 ──────────────┼────────────── 谨慎
  (Reckless)         │           (Prudent)
         Quadrant III│  Quadrant IV
         "我们不知道│  "我们知道且
          怎么做好"  │   有计划还债"
         例：经验不足│  例：先MVP后
         写出烂代码  │   重构优化
                     │
                 无意 (Inadvertent)
```

> 💡 好团队管理的是 Quadrant II 和 IV（有意识的债务），差团队积累的是 Quadrant I 和 III。

### 4.2 技术债务管理策略

```text
1. 识别: SonarQube技术债务分析 + 代码审查标记
2. 登记: 在Backlog中创建"技术债务"类型的Task
3. 量化: 估算修复成本（人天）+ 利息成本（每月浪费的时间）
4. 优先级: 高利息债务优先偿还
5. 预算: 每个Sprint拿出15-20%时间还债
6. 监控: 债务比率趋势图（不能只借不还）
```

## 5. 遗留系统现代化策略

### 5.1 现代化路径选择

| 策略 | 做法 | 风险 | 适用 |
|------|------|:---:|------|
| **封装** | 用API包装遗留系统 | ✅ 低 | 系统稳定但不方便集成 |
| **重写** | 推倒重来 | ❌ 高 | 万不得已 |
| **迁移** | 逐步将功能移到新系统 | ⚠️ 中 | 推荐方案 |
| **重构** | 在原系统内改善 | ✅ 低-中 | 系统可维护但需要现代化 |
| **替换** | 用现成产品/开源替代 | ⚠️ 中 | 非核心差异化功能 |

### 5.2 绞杀者模式 (Strangler Fig Pattern)

```text
       ┌─────────────┐
       │  遗留单体    │
       │  ┌─────────┐ │
       │  │新-用户服务│ │  ← 先提取一个模块
       │  └─────────┘ │
       │  ┌─────────┐ │
       │  │新-订单服务│ │  ← 再提取第二个
       │  └─────────┘ │
       │  ┌─────────┐ │
       │  │   遗留   │ │  ← 逐步缩小
       │  └─────────┘ │
       └─────────────┘
                ↓ 最终
    ┌──────┐ ┌──────┐ ┌──────┐
    │ 用户  │ │ 订单  │ │ 支付  │  ← 遗留系统被完全替换
    └──────┘ └──────┘ └──────┘

核心思想：不一次性替换，而是逐步"绞杀"遗留系统，
         每次提取一个模块到新架构，直到遗留系统为空。
```

## 6. 逆向工程与再工程

| 概念 | 定义 | 产出 |
|------|------|------|
| **逆向工程** | 从代码/可执行文件还原设计信息 | 类图、数据模型、调用关系 |
| **再工程** | 逆向工程→理解→改善→正向工程 | 改善后的系统 |
| **重构** | 不改变外部行为的内部改善 | 同功能更优代码 |

```text
遗留系统现代化的推荐路径：
  1. 逆向工程：生成当前系统的架构图、数据流图（自动化工具+人工补充）
  2. 建立测试：为核心路径添加特征测试（Characterization Tests）
  3. 渐进重构：每次修改一个小模块 + 测试保护
  4. 绞杀迁移：用新架构逐步替换旧模块
```
