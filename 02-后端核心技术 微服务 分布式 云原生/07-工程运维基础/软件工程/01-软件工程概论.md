## 1. 软件工程的定义与核心问题

### 1.1 IEEE标准定义

> **软件工程 (Software Engineering)** = 将系统化的、规范化的、可量化的方法应用于软件的开发、运行和维护。

| 关键词 | 含义 | 与传统"写代码"的区别 |
|--------|------|-------------------|
| **系统化 (Systematic)** | 有章可循，不是随性而为 | 不是"想到哪写到哪" |
| **规范化 (Disciplined)** | 遵循方法论和最佳实践 | 不是"能跑就行" |
| **可量化 (Quantifiable)** | 质量、进度、成本可度量 | 不是"差不多完成了" |

### 1.2 软件工程的三个层次（Fritz Bauer模型）

```
        ┌─────────────────────────────┐
        │        工具 (Tools)          │ ← IDE、CI/CD、静态分析、测试框架
        │    ┌─────────────────────┐   │
        │    │    方法 (Methods)     │   │ ← 面向对象、敏捷、DDD、TDD
        │    │  ┌───────────────┐   │   │
        │    │  │ 过程 (Process) │   │   │ ← 瀑布、Scrum、DevOps
        │    │  └───────────────┘   │   │
        │    └─────────────────────┘   │
        └─────────────────────────────┘

底层（过程）：定义开发活动的框架和顺序
中间（方法）：提供技术上的"怎么做"
顶层（工具）：为方法和过程提供自动化支持
```

> 🎯 软件工程 = 过程 + 方法 + 工具 的三位一体。三者缺一不可：只有工具没有过程是混乱，只有过程没有方法是僵化。

## 2. 软件危机与工程化诉求

### 2.1 什么是软件危机

> 1968年NATO会议首次提出"软件危机"概念 — 软件项目的失败率惊人地高。

| 典型问题 | 1968年 | 至今依然存在 |
|----------|--------|-------------|
| 超出预算 | OS/360超预算400% | Standish Group: 66%项目超预算 |
| 超出时间 | 大量项目延期或取消 | 仅35%项目按时完成 |
| 质量低下 | Bug频发、难以维护 | 软件缺陷造成的经济损失年超万亿 |
| 需求不清 | 交付后发现不是客户想要的 | Agile也不能完全解决 |
| 维护困难 | 改一处崩十处 | 维护成本占软件全生命周期80% |

### 2.2 根本原因

```text
软件的本质特征导致了工程化困境：

1. 不可见性 (Invisibility)
   软件没有物理形态，无法像建筑一样直观看到进度
   → 80%完成 ≠ 工程80%。可能最后20%花80%时间

2. 复杂性 (Complexity)
   软件是人类创造的最复杂的人造物之一
   → 状态爆炸、交互复杂、没有两个组件完全相同

3. 可变性 (Conformity)
   软件必须适应已有系统、法律、硬件、用户习惯
   → 外部约束持续变化，软件必须跟着变

4. 易变性 (Changeability)
   软件修改成本远低于硬件，因此需求变更是常态
   → 变更是软件的本质特征，不是意外
```

> 💡 软件危机的本质 = 凭直觉和经验开发，无法应对软件本身的复杂性。解决之道 = 工程化（方法、工具、过程）。

## 3. 软件工程的四大核心活动

### 3.1 核心活动

| 活动 | 英文 | 核心问题 | 关键产出 |
|------|------|----------|----------|
| **需求** | Requirements | 做什么？ | SRS需求规格说明书 |
| **设计** | Design | 怎么做？ | 架构设计、详细设计 |
| **实现** | Implementation | 做出来 | 代码、可运行系统 |
| **验证** | Verification & Validation | 做对了吗？ | 测试报告、验收报告 |
| **维护** | Maintenance | 持续运行和演进 | 补丁、新版本 |

### 3.2 成本分布（全生命周期）

```text
软件全生命周期成本分布（平均值）：

          ┌─────────────┐
          │   维护 67%   │  ← 最大的成本！远超开发
          ├─────────────┤
          │  实现 13%   │
          ├──────┤        │
          │设计 8%│      │
          ├──────┤      │
          │需求 4%│     │
          │测试 8%│    │
          └──────────────┘

关键启示：
  ✅ 前期（需求+设计）投入不足 → 后期（维护）成本成倍增加
  ✅ 需求阶段修复一个Bug成本=1×，编码阶段=10×，生产阶段=100×
```

## 5. 软件工程职业道德与规范

### 5.1 ACM/IEEE职业道德准则（精简）

| 原则 | 含义 |
|------|------|
| **公众利益** | 软件应造福社会而不造成伤害（波音737 MAX教训） |
| **客户和雇主** | 以客户利益为先，不隐瞒风险 |
| **产品质量** | 交付达到专业标准的产品 |
| **独立判断** | 不受利益冲突影响专业判断 |
| **管理伦理** | 公平对待团队成员，促进道德实践 |
| **专业发展** | 持续学习、分享知识 |
| **同行支持** | 尊重同行、协助同行职业发展 |
| **自我** | 终身学习、反思改进 |

> ⚠️ **真实案例**：大众排放门（软件检测到测试环境就降低排放）、Theranos（虚假技术宣传）、波音737 MAX（MCAS系统缺陷隐瞒）。软件工程师的职业道德不是空话。
