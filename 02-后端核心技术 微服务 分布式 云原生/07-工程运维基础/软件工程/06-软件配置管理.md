## 1. 配置管理概述

### 1.1 SCM的四大核心活动

> SCM (Software Configuration Management) = 软件配置管理。也称为"版本控制+变更管理+构建管理"的综合体。

| 活动 | 目的 | 工具/方法 |
|------|------|-----------|
| **配置标识** | 唯一标识每个配置项（代码/文档/环境） | 命名规范、版本号 |
| **配置控制** | 管理变更请求和审批流程 | CCB(变更控制委员会)、PR Review |
| **配置状态报告** | 追踪配置项的状态变化 | Git log、发布记录、审计日志 |
| **配置审计** | 验证配置项的一致性和完整性 | 自动化检查、定期审计 |

### 1.2 配置项分类

```text
软件配置项 (SCI) 包括：
  ├── 源代码 (.java, .vue, .sql)
  ├── 配置文件 (application.yml, Dockerfile, k8s yaml)
  ├── 文档 (设计文档、API文档、README)
  ├── 测试 (测试用例、测试数据、测试脚本)
  ├── 构建产物 (.jar, .war, Docker image)
  └── 环境定义 (docker-compose.yml, Terraform)
```

## 2. 版本控制核心概念

### 2.1 集中式 vs 分布式

| 维度 | 集中式 (SVN) | 分布式 (Git) |
|------|-------------|-------------|
| 仓库位置 | 唯一中央服务器 | 每人本地完整仓库 |
| 离线工作 | ❌ 不可 | ✅ 完全离线 |
| 分支操作 | ⚠️ 慢（网络） | ✅ 快（本地） |
| 合并能力 | ⚠️ 弱 | ✅ 强（三路合并） |
| 学习曲线 | ✅ 简单 | ⚠️ 中高 |

### 2.2 Git核心对象模型

```text
Git 四个工作区域：
  工作区 (Working Directory) → git add → 暂存区 (Staging Area)
    → git commit → 本地仓库 (Local Repository)
    → git push → 远程仓库 (Remote Repository)

Git 三大对象：
  Blob    — 文件内容（不存文件名）
  Tree    — 目录结构（文件名→Blob的映射）
  Commit  — 快照（指向Tree对象 + 父Commit + 元信息）
```

### 2.3 语义化版本

```text
版本号: MAJOR.MINOR.PATCH

MAJOR: 不兼容的API变更
  1.x.x → 2.0.0: 删除/修改了公开API
  
MINOR: 向后兼容的新功能
  1.1.0 → 1.2.0: 新增功能，但不破坏旧接口

PATCH: 向后兼容的Bug修复
  1.1.0 → 1.1.1: 修复Bug，无新功能

预发布版本:
  1.0.0-alpha.1, 1.0.0-beta.2, 1.0.0-rc.1
```

## 3. 分支策略深度对比

### 3.1 GitFlow

```text
分支结构：
  main      ←┐ 正式发布（每次合并=一次Release）
              │
  develop   ←┤ 开发主线
    │        │
    ├── feature/xxx  → 功能分支（从develop拉，合并回develop）
    ├── release/x.x  → 发布分支（从develop拉，合并回main+develop）
    └── hotfix/xxx   → 热修复（从main拉，合并回main+develop）

优点: ✅ 结构清晰、适合定期发布、多人并行开发
缺点: ❌ 分支多、合并频繁、CI/CD不友好、不适合持续部署
适用: 有固定发布周期的传统软件（如企业软件、App Store应用）
```

### 3.2 Trunk-Based Development

```text
分支结构：
  main   ← 唯一长期分支
    │
    └── short-lived feature branches (存活<2天)

原则:
  ✅ 小批量频繁合并（每日至少一次）
  ✅ Feature Flag控制未完成功能
  ✅ 分支存活 < 2天
  ✅ 基于主干的持续集成

优点: ✅ CI/CD极致友好、合并冲突少、代码库始终可发布
缺点: ❌ 需要Feature Flag能力、对开发者规范要求高
适用: 互联网SaaS、微服务、需要持续部署的团队
```

### 3.3 GitHub Flow

```text
分支结构：
  main   ← 唯一长期分支，始终可部署
    │
    └── feature/xxx  → 功能分支（从main拉，PR合并回main）

简化版Trunk-Based:
  ✅ 分支命名规范: feature/xxx, bugfix/xxx, hotfix/xxx
  ✅ PR + Code Review + CI通过 = 合并到main
  ✅ main合并后自动部署
```

### 3.4 选择决策矩阵

| 因素 | GitFlow | Trunk-Based | GitHub Flow |
|------|:---:|:---:|:---:|
| 团队规模 | >10人 | 任何 | 2-10人 |
| 发布频率 | 周/月 | 天/小时 | 天 |
| 需要多版本维护 | ✅ | ❌ 不适用 | ❌ |
| CI/CD成熟度 | 中 | 高 | 中高 |
| 代码Review强度 | 中 | 高 | 中 |

## 4. 变更管理与CCB

### 4.1 CCB变更控制委员会

> CCB (Change Control Board) = 变更控制委员会 — 评估和审批变更请求的决策组织。

```text
CCB组成：项目经理 + 技术Leader + 测试Leader + 产品经理

CCB决策类型：
  ✅ 批准 → 排入计划
  ⏸️ 推迟 → 下个版本
  ❌ 拒绝 → 明确告知原因+替代方案
  ↩️ 退回 → 需要更多信息
```

### 4.2 变更影响分析

```text
每个变更请求必须评估：
  ├── 工作量：开发×天 + 测试×天
  ├── 影响范围：涉及哪些模块/服务
  ├── 风险：失败概率和影响程度
  ├── 依赖：是否阻塞其他任务
  └── 优先级：是否必须本次发布？能否推迟？
```

## 5. 持续集成与持续交付

### 5.1 CI/CD成熟度模型

```text
Level 1: 手动构建 → 无版本控制、手动编译打包
Level 2: 每日构建 → 每天自动编译+冒烟测试
Level 3: 持续集成 (CI) → 每次提交自动构建+测试
Level 4: 持续交付 (CD) → CI通过后自动部署到预发布环境
Level 5: 持续部署 (CD) → 自动部署到生产环境
```

### 5.2 持续集成六大实践

| 实践 | 说明 |
|------|------|
| **单一代码仓库** | 所有人共享同一个仓库 |
| **自动化构建** | 一条命令完成编译/打包 |
| **自测试构建** | 构建自动运行测试 |
| **每日提交** | 每人每天至少提交一次 |
| **快速构建** | <10分钟完成构建+测试 |
| **生产环境克隆** | 测试环境尽量接近生产 |

## 6. 配置管理最佳实践

```text
DO ✅:
  ├── 所有配置项纳入版本控制（除密钥外）
  ├── Commit Message遵循Conventional Commits规范
  ├── 一次Commit只做一件事（单一目的）
  ├── PR尽量小（<400行，更容易Review）
  ├── 分支存活时间短（<2天合并回主干）
  ├── main分支始终可部署（保护分支+CI门禁）
  └── 配置与代码分离（配置文件≠代码库，环境变量管理密钥）

DON'T ❌:
  ├── 提交二进制文件到代码仓库（用Artifactory/Nexus）
  ├── 提交密钥/密码/Token（即使用环境变量后也要git清除历史）
  ├── 强制推送共享分支（git push --force很危险）
  ├── 提交未完成的代码到main（编译都过不了）
  └── "先合并再修测试"（CI失败时严禁合并）
```

---

> 🎯 配置管理的本质不是Git命令，而是**让团队协作有序、让变更可追溯、让发布可回滚**。
