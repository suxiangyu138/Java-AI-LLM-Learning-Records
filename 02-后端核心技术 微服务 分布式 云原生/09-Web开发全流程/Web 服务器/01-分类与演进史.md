## 1. 四类服务器分类

| 类别 | 代表 | 处理什么 | 并发模型 | 典型场景 |
|------|------|---------|---------|---------|
| **静态 Web 服务器** | Nginx / Apache / Caddy / IIS | 静态文件、缓存 | 事件驱动/多进程 | 托管前端、下载站 |
| **动态（应用）服务器** | Tomcat / Jetty / Undertow / ASP.NET Core | 业务代码 → 动态内容 | 线程池/虚拟线程 | API、业务系统 |
| **反向代理服务器** | Nginx / Caddy / HAProxy / Envoy | 请求分发、TLS、缓存、限流 | 事件驱动 | 统一入口、微服务网关上游 |
| **边缘/CDN 服务器** | Cloudflare / 云 CDN / OpenResty | 全球分发、WAF、边缘计算 | 全球节点 | ToC 站点、防 DDoS |

> 🎯 分类的本质是**职责分工**：现代架构中"一个服务器干所有事"已绝迹——静态由 Web 服务器管、动态由应用服务器管、流量入口由反代/边缘管。**"Web 服务器"狭义上指前两类，广义含反代**。

## 2. HTTP 演进如何倒逼服务器换代

| 协议 | 时代 | 对服务器的要求 | 对应技术 |
|------|------|---------------|---------|
| HTTP/1.0（1996） | 每请求一连接 | 连接管理简单，进程模型够用 | Apache prefork |
| HTTP/1.1（1997） | Keep-Alive 长连接 | **连接变长**→ 连接数暴涨 → 每连接一进程破产 | Apache worker/event、Nginx |
| HTTP/2（2015） | 多路复用 | 单连接并发流；推送 | 现代服务器全支持 |
| HTTP/3（2022+） | QUIC/UDP | 连接迁移、0-RTT；**改 UDP 需要服务器重写 IO 层** | Caddy/Nginx 1.25+/Cloudflare |

> 🎯 **Keep-Alive 是服务器历史的转折点**：长连接意味着"空闲连接占资源"——每连接一进程（prefork）在 2000 年代 C10K 问题面前崩溃，事件驱动（Nginx）应运而生。**理解 C10K 就理解了 Nginx 为何存在**。

## 3. 进程模型演进：从 fork 到事件驱动

```text
1995 ──────────────────────────────────────────────────────── 2026
fork 每连接（Apache prefork）→ 线程每连接（worker）→ 事件驱动（Nginx/Caddy）→ 混合（Tomcat NIO+池）
  1 连接 = 1 进程              1 连接 = 1 线程            1 进程 = 万级连接        事件 + 工作线程池
```

| 模型 | 代表 | 连接/资源 | 优点 | 缺点 |
|------|------|:---:|------|------|
| **prefork**（进程） | Apache | 1 连接 1 进程（~10MB） | 隔离性好、兼容老模块 | 内存爆炸，千连接即极限 |
| **worker**（线程） | Apache / IIS | 1 连接 1 线程（~1MB） | 比进程轻 | 线程切换成本、共享状态 |
| **event**（事件驱动） | Nginx / Caddy / Node | 1 进程万级连接 | 内存极小、并发极高 | 阻塞代码致命、调试难 |
| **混合**（NIO+池） | Tomcat / Jetty | 事件 + 线程池 | 兼顾并发与同步编程 | 架构复杂 |

> 🎯 面试金句：**"Nginx 用事件驱动解决 C10K（1 万并发连接），Apache 的 prefork 模型 1 连接 1 进程必然先内存耗尽"**——为什么高并发选 Nginx 的历史根源。

## 4. 三十年级别史

```text
1991  CERN httpd（万维网第一个服务器，单进程单文件）
1995  Apache 诞生（NCSA httpd 的补丁版）→ 1996 起份额第一，统治 20 年
1996  IIS 1.0（Windows NT 内置）→ 微软生态标配
1998  lighttpd（轻量事件驱动，早期嵌入式/视频站）
2004  Nginx 1.0 发布（C10K 时代主角）→ 2010s 起份额反超 Apache
2010  Cloudflare 成立 → CDN 边缘崛起，2019 年起成为"最大服务器"
2015  Caddy 发布（自动 HTTPS 引爆）→ 2026 年份额约 3%，个人/中小站首选
2020+ 云原生时代：Ingress/网关/边缘计算进一步"服务器隐形化"
```

| 时代 | 霸主 | 衰落原因 |
|------|------|---------|
| 1996-2010 | Apache | 进程模型重、配置复杂，难抗高并发 |
| 2010-2020 | Nginx | 事件驱动 + 简洁配置 + 反代生态 |
| 2020- | Cloudflare 类边缘 | 大站全面 CDN 化；服务器"下沉"为边缘基础设施 |

> 💡 反直觉事实：**Cloudflare 不是传统意义的"Web 服务器软件"，却是 2026 年份额第一的服务器（边缘）**——W3Techs 把它计为服务器。选型视角要包含"托管在 CDN 边缘"这一选项。

## 5. 动态内容的处理方式变迁

| 时代 | 方案 | 说明 |
|------|------|------|
| 1990s | **CGI** | 每请求 fork 一个进程执行脚本——性能地狱 |
| 2000s | **模块内嵌**（mod_php / mod_wsgi） | 解释器打进 Web 服务器进程，快但耦合 |
| 2000s | **应用服务器**（Tomcat / JBoss） | 动态内容独立成应用服务器 |
| 2010s | **FastCGI**（PHP-FPM / uwsgi） | 独立进程池 + 进程间通信，动静分离雏形 |
| 2020s | **API 服务器 + 反代**（Nginx→Tomcat/Boot） | 完全分离：Web 服务器只反代，应用只出 API |
| 2025+ | **边缘函数**（Cloudflare Workers / 边缘 Node） | 计算搬到 CDN 边缘，服务器进一步消失 |

```text
典型现代链路：
浏览器 → Cloudflare CDN（静态缓存/WAF）
       → Nginx（反代 + TLS 终止 + 限流）
       → Spring Boot 集群（API，虚拟线程/异步）
```

> 🎯 主线认知：**"动态处理"从 Web 服务器内部一步步被剥离开**（CGI → 模块 → 独立应用服务器 → 反代 → 边缘）——今天的 Web 服务器几乎不做业务计算，只做流量管道。这与 [05-Web服务器与应用服务器分工](05-Web服务器与应用服务器分工.md) 直接衔接。
