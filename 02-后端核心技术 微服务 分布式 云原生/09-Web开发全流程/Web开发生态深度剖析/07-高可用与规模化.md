## 1. 高可用架构全景

```
高可用演进：
  单机 → 集群（多实例）→ 多机房 → 异地多活

集群核心目标：
  消除单点故障（SPOF）
  水平扩展能力（加机器提升容量）

⚠️ 面试必答：
"高可用 = 消除单点 + 水平扩展——
 应用多实例、数据主从、负载均衡分流；
 每层都要考虑'挂了怎么办'。"
```

## 2. 负载均衡

### 2.1 负载均衡层级

```
负载均衡三层：
  DNS 层：域名 → 多 IP（地域分流）
  接入层：Nginx/LVS（七层/四层）
  应用层：服务发现（微服务内负载）

⚠️ 面试必答：
"负载均衡三层——DNS（地域）、
 Nginx（接入）、注册中心（服务间）；
 各层职责不同、层层分担。"
```

### 2.2 负载均衡算法

| 算法 | 原理 | 适用 |
|------|------|------|
| 轮询 | 依次分配 | 无状态默认 |
| 加权轮询 | 按权重 | 异构机器 |
| IP 哈希 | 同 IP 同节点 | 会话保持 |
| 最小连接 | 连接少的优先 | 长连接场景 |

```
⚠️ 面试必答：
"轮询（默认）、加权（异构）、
 IP 哈希（会话黏性）、最小连接（长连接）；
 会话场景配合 Redis 共享更优（免黏性）。"
```

## 3. Nginx 核心应用

### 3.1 三大角色

```
Nginx 核心三大角色：
  ① 静态服务器：高效服务静态资源
  ② 反向代理：请求转发 + 负载均衡
  ③ 网关能力：限流、缓存、安全

⚠️ 面试必答：
"Nginx 三角色——静态（快）、
 反向代理（转发 + 均衡）、网关（限流缓存）；
 是 Java Web 标配接入层。"
```

### 3.2 配置示例

```nginx
# 反向代理 + 负载均衡
upstream backend {
    server 10.0.0.1:8080 weight=3;    # 加权
    server 10.0.0.2:8080 weight=1;
    keepalive 32;                     # 连接复用
}

server {
    listen 80;
    # 静态资源（Nginx 直接服务，不落 Tomcat）
    location /static/ {
        root /data/www;
        expires 30d;                  # 缓存 30 天
    }
    # 动态请求（转发 Tomcat）
    location /api/ {
        proxy_pass http://backend;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
    # 限流（防刷）
    limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
    location /api/login {
        limit_req zone=api burst=20;
        proxy_pass http://backend;
    }
}
```

> 🎯 **要点**：Nginx 黄金组合——静态 Nginx 服务（expires 缓存）+ 动态转发 Tomcat + 限流防刷。**动静分离**是标准架构。

## 4. 限流熔断降级

### 4.1 稳定性三板斧

```
① 限流：保护系统不超载
   算法：令牌桶/漏桶/滑动窗口
   粒度：接口/IP/用户

② 熔断：故障快速失败（防雪崩）
   状态：关闭 → 打开 → 半开（试探恢复）

③ 降级：非核心让路
   场景：查询降级缓存、写降级队列

⚠️ 面试必答：
"三板斧——限流（防超载）、
 熔断（防雪崩）、降级（保核心）；
 高可用系统的自我保护机制。"
```

### 4.2 限流实现

```java
// 单机限流（Guava RateLimiter）
RateLimiter limiter = RateLimiter.create(100);   // 每秒 100
if (!limiter.tryAcquire()) {
    throw new TooManyRequestsException();
}

// 分布式限流（Redis + Lua，原子性）
// Lua 脚本：INCR + 过期时间实现滑动窗口
// 或使用 Sentinel（限流熔断一体）
```

```
⚠️ 面试必答：
"单机 Guava、分布式 Redis + Lua / Sentinel——
 限流要'原子'（Redis Lua 脚本保证）；
 Sentinel 提供限流/熔断/降级一体化。"
```

## 5. 数据高可用

### 5.1 数据库高可用

```
数据库高可用方案：
  主从复制：读扩展 + 容灾（异步/半同步）
  读写分离：主写从读
  双机热备：主备切换（MHA/Orchestrator）
  分库分表：数据量大时的扩展（ShardingSphere）

⚠️ 面试必答：
"数据高可用——主从（容灾）、
 读写分离（读扩展）、主备切换（自动故障）、
 分库分表（容量扩展）。"
```

### 5.2 缓存高可用

```
Redis 高可用：
  主从复制 + 哨兵（自动故障切换）
  Cluster 集群（分片 + 高可用）
  持久化：RDB（快照）+ AOF（日志）

⚠️ 面试必答：
"Redis 高可用——哨兵（自动切换）、
 集群（分片扩容）、RDB+AOF（持久化）；
 缓存雪崩防护（随机过期）配套。"
```

## 6. 可观测与告警

### 6.1 监控体系

```
可观测三支柱（Web 视角）：
  Metrics：Prometheus + Grafana（QPS/延迟/错误）
  Logs：ELK（结构化日志 + traceId）
  Traces：OTel + Jaeger（全链路）

⚠️ 面试必答：
"监控三支柱——指标（趋势）、
 日志（细节）、链路（路径）；
 排查流程：指标发现 → 链路定位 → 日志确认。"
```

### 6.2 告警设计

```
告警原则：
  ① 少而准（每告警必有行动）
  ② 分级（P0 立即/P1 当日/P2 本周）
  ③ 防风暴（聚合/抑制）
  ④ 带处置文档（runbook）

⚠️ 面试必答：
"告警少而准 + 分级 + 防风暴——
 告警疲劳（噪音）比没告警更危险。"
```

---

> 🎯 **核心要点**：高可用体系 = **集群架构**（消除单点 + 水平扩展）+ **负载均衡**（DNS/Nginx/注册中心三层 + 四算法）+ **Nginx**（动静分离 + 限流）+ **三板斧**（限流/熔断/降级）+ **数据高可用**（主从/哨兵/分片）+ **可观测**（三支柱 + 告警分级）。"每层问自己：挂了怎么办"是高可用设计的思维。
