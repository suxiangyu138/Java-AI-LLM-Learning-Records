## 1. 问题：集群下的 Session 困境

```text
现象：应用部署多实例后，用户"被反复踢下线"
原因：请求被负载均衡到不同实例 → 各实例内存 Session 不共享
      实例 A 存了登录态 → 下次请求到实例 B → 找不到 Session
```

```text
请求流转：
用户 → Nginx（轮询）→ 实例 A（有 Session）✅
用户 → Nginx（轮询）→ 实例 B（无 Session）❌ 被踢下线
```

> 🎯 **核心矛盾**：Session 是"每实例内存"，而用户请求会"随机到任意实例"——**会话状态必须从"实例本地"变成"所有实例共享"**。

## 2. 方案对比：复制/粘滞/集中式

| 方案 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **Session 复制** | 节点间广播同步（每节点全量） | 无单点 | **广播风暴**（节点多就爆炸） | ≤4 节点小集群 |
| **粘滞会话** | LB 将同用户固定到同节点（ip_hash） | 零改造 | 节点宕机会话全丢；负载不均 | 临时过渡/开发 |
| **集中式存储** | Session 存 Redis，所有实例统一读写 | **生产首选** | 需引入 Redis + 序列化 | 任意规模 |

> 🎯 **2026 结论**：**集中式（Redis）是生产标准**——复制有风暴上限、粘滞有单点风险；**Spring Session + Redis 是 Java 生态主流实现**。

## 3. Spring Session：统一抽象

```text
Spring Session = 会话存储抽象层：
  业务代码不变（还是 HttpSession API）
  存储可换（Redis/JDBC/Hazelcast）
  过滤器拦截 → SessionRepositoryRequestWrapper 替换 request
  → 所有 Session 操作指向集中存储
```

```text
架构：
HttpSession API（业务）
  → Spring Session（SessionRepository 抽象）
      ├─ RedisIndexedSessionRepository（Redis，主流）
      ├─ JdbcIndexedSessionRepository（JDBC）
      └─ 其他实现
```

> 🎯 **Spring Session 的价值**：**业务零改动**——继续写 `session.setAttribute`，底层存储自动切换到 Redis；换存储只改依赖与配置。

## 4. Spring Session + Redis 落地

```xml
<dependency>
    <groupId>org.springframework.session</groupId>
    <artifactId>spring-session-data-redis</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

```yaml
# application.yml
spring:
  session:
    store-type: redis                # 会话存储：Redis
    timeout: 30m                     # 会话超时
    redis:
      namespace: my-app:session      # 命名空间（多应用隔离）
  data:
    redis:
      host: redis.example.com
      port: 6379
      password: ${REDIS_PASSWORD}
```

```java
// 业务代码零改动：还是 HttpSession
@PostMapping("/login")
public String login(@RequestParam String username, HttpSession session) {
    session.setAttribute("user", username);   // 自动存 Redis
    return "ok";
}
```

```bash
# 验证 Redis 中的 Session
redis-cli keys "my-app:session:*"
redis-cli ttl "my-app:session:xxx"     # 超时生效
```

| 配置 | 说明 |
|------|------|
| `store-type: redis` | 存储切 Redis |
| `namespace` | 多应用隔离前缀 |
| `timeout` | 会话超时（同步 Redis TTL） |
| 序列化 | 对象必须可序列化（见第 6 节） |

> 🎯 **落地三件事**：加依赖 + 配 store-type/redis + **保证 Session 对象可序列化**——业务代码不用改。

## 5. 粘滞会话（Sticky Session）细节

```nginx
# Nginx ip_hash：同 IP 固定同后端（粘滞的一种）
upstream backend {
    ip_hash;
    server 192.168.1.100:8080;
    server 192.168.1.101:8080;
}
```

| 粘滞的局限 | 说明 |
|-----------|------|
| 节点宕机 | 该节点用户会话全丢（无共享） |
| 负载不均 | 大 IP 段用户集中到同一节点 |
| 扩容/缩容 | 会话迁移问题 |
| 适用 | **临时过渡**（最终仍要集中式） |

> ⚠️ **粘滞的定位**：零改造的"止血方案"——**生产长期方案是集中式**；粘滞 + 集中式可组合（粘滞减少 Redis 访问，集中式保底）。

## 6. Session 序列化与注意事项

```text
Redis 存储 Session 的序列化要求：
  ① 存入对象 implements Serializable
  ② 避免大对象（Redis 内存/网络）
  ③ 避免不可序列化成员（连接/流）

常见坑：
  ❌ 存了不可序列化对象 → 运行时序列化异常
  ❌ 存了大对象（List 全量数据）→ Redis 内存暴涨
  ❌ 存了带内部状态的组件 → 反序列化后状态错乱
```

| 注意事项 | 说明 |
|----------|------|
| 对象可序列化 | Serializable + serialVersionUID |
| 控制大小 | Session 只放"必要数据"（用户 ID/权限，不放全量列表） |
| 命名空间 | 多应用共用 Redis 时隔离前缀 |
| 安全 | Redis 加密码 + 网络隔离 |

> 💡 **Session 瘦身原则**：Session 只放**用户标识 + 必要状态**（userID/角色），详细数据用 ID 回查——**"存 ID 不存全量"是分布式 Session 的容量纪律**。

## 7. 核心要点

> 🎯 **核心要点**：
> - 集群困境：Session 在实例内存，请求随机到实例——必须共享；
> - 三方案：复制（≤4 节点，有风暴）、粘滞（零改造，单点风险）、**集中式 Redis（生产首选）**；
> - Spring Session = 存储抽象：业务代码零改动，Redis/JDBC 可换；
> - 落地三件事：依赖 + store-type/redis 配置 + 对象可序列化；
> - 粘滞是止血不是根治（宕机丢会话）；
> - 序列化纪律：可序列化 + 瘦身（存 ID 不存全量）+ 命名空间隔离；
> - 面试主线：困境 → 三方案对比 → Spring Session 原理 → 落地配置。
