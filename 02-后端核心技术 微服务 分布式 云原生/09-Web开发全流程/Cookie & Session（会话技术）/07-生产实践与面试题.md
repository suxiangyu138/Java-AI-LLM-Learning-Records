## 1. 生产配置基线

### 1.1 Cookie 基线

```yaml
# Spring Boot 生产 Cookie 配置
server:
  servlet:
    session:
      timeout: 30m                    # 会话超时
      cookie:
        http-only: true               # 防 XSS 窃取
        secure: true                  # 仅 HTTPS
        same-site: lax                # CSRF 第一道防线（显式配置，防默认值回归）
        max-age: 1800                 # 30 分钟（与 timeout 对齐）
```

| 配置项 | 值 | 防护 |
|--------|-----|------|
| http-only | true | XSS 窃取 |
| secure | true | 明文窃听 |
| same-site | lax | CSRF |
| timeout | 30m | 长会话风险 |

### 1.2 Session 基线

```yaml
# 分布式 Session（集群必备）
spring:
  session:
    store-type: redis                 # 集中式存储
    timeout: 30m
  data:
    redis:
      host: ${REDIS_HOST}
      password: ${REDIS_PASSWORD}
```

```text
会话安全基线（代码）：
  登录：changeSessionId()（防固定攻击）+ 存最小数据
  登出：invalidate() + 清 Cookie
  校验：getSession(false) 判断登录态
  对象：可序列化 + 瘦身（存 ID 不存全量）
```

## 2. 常见组合方案

| 场景组合 | 方案 |
|----------|------|
| 单体/小集群 + 传统 Web | Servlet Session（内存） |
| 集群 + 管理端 | Spring Session + Redis |
| 前后端分离 SPA | Session（SameSite）+ 或 JWT |
| 移动端 + 第三方 | **JWT 双 Token** |
| 微服务 + 内部认证 | JWT（共享密钥验签） |
| 混合（2026 常态） | Web 用 Session，API 用 JWT |

```text
混合方案示例：
  前端 Web：Session + Redis（可控登录态，可踢人）
  移动端 API：JWT 双 Token（无 Cookie 依赖）
  微服务间：JWT 或内部 Token（验签直通）
```

> 🎯 **2026 选型主基调**：**"JWT 全面替代 Session"已不是共识**——登录态用 Session（可撤销），接口认证用 JWT（无状态）；**按场景混合是成熟团队的常态**。

## 3. 高频避坑清单

| # | 坑 | 规避 |
|---|----|------|
| 1 | 认证 Cookie 无 HttpOnly | XSS 直接偷 ID——必设 |
| 2 | 登录不轮换 SessionID | 会话固定攻击——changeSessionId |
| 3 | 登出不失效不清 Cookie | 残留会话可被利用——invalidate + 清 |
| 4 | JSP 默认创建 Session | 内存浪费——page session=false / 纯 API 用 false |
| 5 | 集群不共享 Session | 用户被反复踢——Spring Session + Redis |
| 6 | Session 存大对象/不可序列化 | Redis 内存暴涨/序列化异常——瘦身 |
| 7 | JWT Payload 放敏感数据 | 可解码泄露——只放可公开信息 |
| 8 | JWT 无过期/长过期 | 泄露无法撤销——短效 + 双 Token |
| 9 | 前端 localStorage 存 Token | XSS 可读——HttpOnly Cookie/内存 |
| 10 | SameSite 依赖默认 | 默认行为可能回归——显式配置 |

## 4. 面试题

| 题目 | 答题要点 |
|------|---------|
| Cookie 和 Session 的区别？ | 存储位置（客户端 vs 服务器）、数据可见性、大小、生命周期 |
| Session 的原理？ | HTTP 无状态 → SessionID（Cookie）→ 服务器找 Session；"数据在服务器，标识在客户端" |
| getSession() 和 getSession(false)？ | 有取无建 vs 有取无 null（登录判断用 false） |
| Session 什么时候创建？ | getSession() 调用时；JSP 默认创建是坑 |
| 关浏览器等于登出吗？ | 不等于——只删了客户端 Cookie，服务器 Session 活到超时 |
| 分布式 Session 方案？ | 复制（≤4 节点）、粘滞（单点风险）、**Redis 集中（生产首选）** |
| Spring Session 原理？ | 过滤器替换 request → SessionRepository 抽象 → Redis 存储，业务零改动 |
| 会话固定攻击怎么防？ | 登录成功 `request.changeSessionId()` 轮换 ID |
| CSRF 怎么防？ | SameSite=Lax（浏览器）+ CSRF Token（Spring Security 默认） |
| HttpOnly 有什么用？ | 防 XSS 用 JS 读取认证 Cookie |
| JWT 结构？ | Header.Payload.Signature；签名保证完整性不保证机密性 |
| JWT 和 Session 怎么选？ | Session 可撤销（服务器掌控）；JWT 无状态跨域但不可撤销——按场景 |
| 双 Token 是什么？ | Access（短效 15m）+ Refresh（长效 7-30d）——缩小泄露窗口 |
| JWT 的坑？ | 密钥弱/算法混淆/Payload 敏感/无过期/localStorage 存储 |

## 5. 核心要点

> 🎯 **核心要点**：
> - 生产基线：Cookie 三件套（HttpOnly/Secure/SameSite 显式）+ Session Redis + 登录轮换/登出失效；
> - 组合方案：Web 登录态 Session、移动端/第三方 JWT 双 Token、微服务 JWT——混合是常态；
> - 避坑 Top3：HttpOnly 不设、登录不轮换、集群不共享；
> - 面试主线：Cookie/Session 区别 → Session 原理与生命周期 → 分布式三方案 → 四威胁防护 → JWT 结构/双 Token/选型；
> - 会话技术是"无状态 HTTP 的补丁"：从 Cookie → Session → 分布式 → JWT 的演进主线贯穿理解。
