## 1. SessionID 的传递方式

```text
SessionID 三种传递：
  ① Cookie（主流）：Set-Cookie: JSESSIONID=xxx
  ② URL 重写：/profile;jsessionid=xxx（Cookie 禁用时）
  ③ 隐藏字段（表单）
```

| 方式 | 原理 | 场景 |
|------|------|------|
| Cookie | 自动携带 | **主流**（HttpOnly 保护） |
| URL 重写 | URL 附加 jsessionid | Cookie 禁用兜底（安全差：URL 会进日志/被分享） |
| 隐藏字段 | 表单内传递 | 特定表单流程 |

> 🎯 **Cookie 是最佳传递方式**：自动携带 + HttpOnly 保护；URL 重写是"兜底"（JSESSIONID 暴露在 URL——会进访问日志、被复制分享，**生产不推荐**）。

## 2. Session 创建时机

```text
关键认知：Session 不是"连接时创建"，是"代码调用 getSession() 时创建"

创建时机：
  ① 登录成功（显式 getSession() + 存用户信息）——正确姿势
  ② JSP 页面（JSP 默认内置 session 对象 → 自动创建）——旧式陷阱
  ③ 误用 getSession()（每次请求创建新 Session）——错误
```

| 场景 | 行为 | 建议 |
|------|------|------|
| 登录 | `getSession()` + setAttribute | ✅ 正确 |
| 业务接口 | `getSession(false)` 判断 | ✅ 正确 |
| JSP 页面 | 默认创建 | ⚠️ 页面加 `<%@ page session="false" %>` |
| 静态资源 | 不涉及 | - |

> ⚠️ **Session 创建的经典坑**：**每个 JSP 页面默认创建 Session**——访问一个 JSP 就产生一个无意义 Session（内存浪费）；纯 API 项目用 `getSession(false)` 避免误建。

## 3. Session 失效机制

```text
失效四途径：
  ① 超时：超过 maxInactiveInterval 未活动（默认 30 分钟）
  ② 登出：session.invalidate()
  ③ 服务器重启：内存 Session 全部丢失（除非持久化）
  ④ 手动：removeAttribute/remove（局部）
```

| 失效方式 | 触发 | 说明 |
|----------|------|------|
| 超时 | 超过 maxInactiveInterval | 默认 30 分钟无活动 |
| 登出 | `invalidate()` | 立即失效（标准姿势） |
| 重启 | 服务器重启 | 内存丢失（分布式方案见 04） |
| 浏览器关闭 | **不影响服务器 Session** | 会话 Cookie 没了，但服务器 Session 还活着直到超时 |

> ⚠️ **"关浏览器 = 登出"是误解**：关闭浏览器只删了客户端 Cookie（JSESSIONID 丢了），**服务器 Session 仍存活到超时**——换个浏览器带同一 ID 仍有效；这也是"无登出按钮的系统"的隐患。

## 4. Cookie 禁用场景（URL 重写）

```text
用户禁用 Cookie → SessionID 无法经 Cookie 传递
Servlet 容器的兜底：URL 重写（encodeURL）
```

```java
// 正确姿势：所有带 Session 的链接用 encodeURL
resp.sendRedirect(resp.encodeRedirectURL("/profile"));
// /profile 或 /profile;jsessionid=xxx（Cookie 不可用时自动附加）

// JSP 链接
<a href="<%= response.encodeURL("/profile") %>">个人中心</a>
```

| 场景 | 说明 |
|------|------|
| Cookie 可用 | encodeURL 返回原 URL（无变化） |
| Cookie 禁用 | 自动附加 `;jsessionid=xxx` |
| 生产建议 | 一般假设 Cookie 可用；URL 重写有泄露风险 |

> 💡 **encodeURL 是标准 API**：容器自动判断 Cookie 是否可用——**写了 encodeURL 的应用在"禁 Cookie"场景也能工作**（代价是 URL 带 ID 的安全问题）。

## 5. 会话生命周期全景

```text
生命周期时间线：
  ① 登录（getSession + 存用户）→ Session 创建
  ② 会话中（每次请求 Cookie 带 ID → 找到 Session）
  ③ 无活动超时（30 分钟）→ 失效
  ④ 登出（invalidate）→ 立即失效
  ⑤ 或：服务器重启 → 内存 Session 全丢（分布式存储方案 04 解决）

风险窗口：
  登出后 SessionID 复用（固定攻击）——登出必须 invalidate + 清 Cookie
```

## 6. 会话与登录流程实战

```java
// 登录（创建 Session）
@PostMapping("/login")
public String login(@RequestParam String username, HttpSession session) {
    // ① 校验用户名密码（此处简化）
    // ② 创建/获取 Session 并存入用户
    session.setAttribute("user", username);
    session.setMaxInactiveInterval(1800);       // 30 分钟超时
    // ③ 防止固定攻击：登录成功后轮换 SessionID
    //     （容器/框架支持时 request.changeSessionId()）
    return "登录成功";
}

// 登出（失效 Session）
@PostMapping("/logout")
public String logout(HttpSession session, HttpServletResponse response) {
    // ① 使 Session 失效
    session.invalidate();
    // ② 清除客户端 Cookie（同名 + Max-Age=0）
    Cookie cookie = new Cookie("JSESSIONID", "");
    cookie.setMaxAge(0);
    cookie.setPath("/");
    response.addCookie(cookie);
    return "已登出";
}

// 校验（登录判断）
@GetMapping("/profile")
public String profile(HttpSession session) {
    Object user = session.getAttribute("user");
    return user == null ? "未登录" : "用户: " + user;
}
```

> 🎯 **登录流程三要点**：存用户信息（setAttribute）+ 超时设置 + **登录成功轮换 SessionID（防固定攻击）**；登出两要点：invalidate + 清 Cookie。

## 7. 核心要点

> 🎯 **核心要点**：
> - SessionID 传递：Cookie 主流、URL 重写兜底（有泄露风险）、隐藏字段；
> - Session 创建时机：`getSession()` 才创建（JSP 默认创建是坑，纯 API 用 false）；
> - 失效四途径：超时（30 分钟）/登出/重启/手动；
> - **"关浏览器 ≠ 登出"**：服务器 Session 活到超时（无登出按钮系统的隐患）；
> - encodeURL 让应用兼容"禁 Cookie"（代价是 URL 泄露）；
> - 登录：存用户 + 轮换 ID（防固定攻击）；登出：invalidate + 清 Cookie；
> - 生命周期全景：创建 → 使用 → 超时/登出 → 失效。
