# 04 重复请求治理：幂等与防抖

## 1. 重复请求从哪来：三个真实场景

**通俗**：同一个请求重复多次，结果和调用一次完全一样——调用 1 次扣 10 元，调用 10 次也只能扣 10 元，不能扣 100 元。

| 场景 | 重复来源 | 例子 |
|------|---------|------|
| **① 网络重试** | 客户端超时重发（请求其实已成功） | 支付回调超时 → 网关重试 → 重复扣款 |
| **② 用户手抖/双击** | 用户连点提交按钮 | 下单按钮连点 → 下两单 |
| **③ 消息重投** | MQ 至少一次投递，消息重复消费 | 加积分消息重复 → 积分翻倍 |

> 🎯 关键认知：**网络层永远不能保证"恰好一次"**——客户端可能超时重试、MQ 至少投递一次、浏览器可能双击。所以**幂等不是优化，是正确性的底线**：凡涉及资金、库存、积分的写操作，后端必须幂等。

## 2. 幂等的定义与判断标准

```text
f(f(x)) = f(x)     数学定义：同一个操作做两次 = 做一次
```

| 操作 | 是否天然幂等 | 说明 |
|------|:---:|------|
| GET 查询 | ✅ | 读多少次结果一样 |
| DELETE 删除 | ✅（大多） | 删不存在的返回成功（可按 id 删） |
| PUT 全量更新 | ✅（规范下） | 整体替换，重复提交值一样 |
| POST 新增 | ❌ | 每次都插入新行 |
| 扣减类（扣库存/扣款） | ❌ | 扣两次就是两次的钱 |

> ⚠️ 反直觉点：**"删除"不总是幂等**——`DELETE /order/100` 重复调用，第一次 200、第二次 404，对调用方就是"结果不一致"；所以很多系统删除接口也设计成幂等（删不存在的也返回成功）。

## 3. 幂等四方案（面试必考）

### 3.1 方案一：数据库唯一约束（最硬核）

**通俗**：让数据库替你做最后一道防线——同一笔业务只能插入一次，插第二次直接报唯一键冲突。

```java
// ① 业务流水表带唯一键（订单号 + 业务类型）
CREATE TABLE payment_flow (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id      VARCHAR(32) NOT NULL,       -- 业务唯一键
    pay_amount    DECIMAL(10,2) NOT NULL,
    status        VARCHAR(16) NOT NULL,
    UNIQUE KEY uk_order (order_id)            -- ★ 幂等靠它：同订单只能插一条
);

// ② 插入时捕获冲突 → 已处理过，直接返回旧结果
try {
    paymentFlowRepository.save(flow);          // 第一次：插入成功
} catch (DataIntegrityViolationException e) { // 第二次：唯一键冲突
    return "该订单已处理，勿重复提交";
}
```

| 优点 | 缺点 |
|------|------|
| 绝对可靠（数据库保证，任何入口都拦得住） | 只防"插入型"重复，防不住"更新型"重复 |

### 3.2 方案二：状态机（防重复流转）

**通俗**：订单状态只能按固定顺序走——已支付不能再次支付、已发货不能再次发货，状态一错就拒绝。

```java
// ① 状态流转校验（每次更新都带上"当前状态"条件）
@Modifying
@Query("update OrderEntity o set o.status = :to where o.id = :id and o.status = :from")
int transition(@Param("id") Long id, @Param("from") OrderStatus from, @Param("to") OrderStatus to);

// ② 影响行数为 0 = 状态已不是期望值 → 重复请求被挡住
int rows = orderRepository.transition(orderId, OrderStatus.PENDING, OrderStatus.PAID);
if (rows == 0) {
    return "订单状态已变更，请刷新";       // 重复支付/重复回调都到这
}
```

| 优点 | 缺点 |
|------|------|
| 天然贴合业务（订单生命周期就是状态机） | 需要状态流设计清晰；只防"状态流转"类操作 |

### 3.3 方案三：唯一令牌（Token，最通用）

**通俗**：每个请求先领一张"一次性入场券"，处理时验票——票只能用一次。

```java
// ① 前端打开页面/下单前，先向后端申请 token
@PostMapping("/order/token")
public String token() {
    String token = UUID.randomUUID().toString();
    redisTemplate.opsForValue()
        .setIfAbsent("order:token:" + token, "1", Duration.ofMinutes(10));
    return token;                              // 返回给前端
}

// ② 提交时带 token，后端"验票 + 销毁"原子操作
@PostMapping("/order")
public Order create(@RequestBody CreateOrderReq req) {
    Boolean first = redisTemplate.opsForValue()
        .setIfAbsent("order:token:" + req.token(), "1", Duration.ofMinutes(10));
    // 第一次：setIfAbsent 成功返回 true → 放行
    // 重复：key 已存在返回 false → 拒绝（同一 token 只能用一次）
    if (!Boolean.TRUE.equals(first)) {
        throw new BizException("重复提交，请勿多次点击");
    }
    return orderService.create(req);
}
```

| 优点 | 缺点 |
|------|------|
| 通用（任何写操作都能套） | 依赖 Redis 可用性；Redis 与业务库不同事务（极端双写问题可加唯一键兜底） |

> 💡 令牌方案生产细节：**"验票+销毁"必须原子**（`setIfAbsent` 一把完成），先查再删两步操作在高并发下会放行两个重复请求——这是方案三最常见的实现 bug。

### 3.4 方案四：Redis 幂等标记（轻量）

```text
处理前：SETNX biz:order:100 "done"（存在则拒绝）
处理后：完成时设置标记
配合：标记带 TTL（防 key 无限堆积）
```

| 优点 | 缺点 |
|------|------|
| 简单、性能好 | 只防"短时间窗口"重复；Redis 异常时失去保护 |

### 3.5 四方案对比与组合

| 方案 | 防什么 | 可靠性 | 复杂度 | 首选场景 |
|------|--------|:---:|:---:|---------|
| 唯一约束 | 插入型重复 | ★★★★★ | 低 | **支付流水、积分流水（资金必用）** |
| 状态机 | 状态流转重复 | ★★★★★ | 中 | **订单生命周期（下单/支付/发货）** |
| 唯一令牌 | 通用写操作 | ★★★★（依赖 Redis） | 中 | **用户提交类（防双击）** |
| Redis 标记 | 短窗口重复 | ★★★ | 低 | 轻量接口、网关层 |

> 🎯 生产组合拳：**用户层用令牌（防手抖）+ 业务层用状态机（防乱序）+ 资金层用唯一约束（防漏网）**——三层叠加，任何一个入口的重复请求都拦得住；面试答"幂等怎么做"答到这三层组合基本满分。

## 4. 防抖与节流：前端重复触发的两把锁

**通俗**：防抖——短时间多次触发，只执行**最后一次**；节流——固定时间间隔内，最多执行**一次**。

### 4.1 防抖（Debounce）

```text
连续输入 "j" "ja" "jav" "java"（每 100ms 一次）
防抖（等待 500ms）：
  j → 重置计时 … ja → 重置 … jav → 重置 … java → 停顿 500ms → 才发请求
结果：只发了 1 次搜索请求（最后一次）
```

```js
// 防抖：停顿 500ms 后才执行（搜索框）
function debounce(fn, delay = 500) {
    let timer = null;
    return function (...args) {
        clearTimeout(timer);                    // 每次触发重置计时器
        timer = setTimeout(() => fn.apply(this, args), delay);
    };
}
const search = debounce((kw) => api.search(kw), 500);
```

### 4.2 节流（Throttle）

```text
用户疯狂滚动（每 10ms 触发一次）
节流（每 1000ms 最多一次）：
  → 第 1ms 执行 … 第 1000ms 执行 … 第 2000ms 执行
结果：1 秒最多触发 1 次
```

```js
// 节流：固定间隔最多执行一次（滚动加载/按钮连点）
function throttle(fn, interval = 1000) {
    let last = 0;
    return function (...args) {
        const now = Date.now();
        if (now - last >= interval) {           // 距上次够久了才执行
            last = now;
            fn.apply(this, args);
        }
    };
}
const loadMore = throttle(() => api.loadMore(), 1000);
```

### 4.3 防抖 vs 节流对比（面试易混）

| 维度 | 防抖（Debounce） | 节流（Throttle） |
|------|-----------------|-----------------|
| 行为 | 连续触发只执行**最后一次** | 固定间隔**最多执行一次** |
| 场景 | 搜索框、输入校验（等停顿） | 滚动加载、拖拽、按钮连点（控频率） |
| 例子 | 你打完字停 500ms 才搜 | 每秒最多加载一次下一页 |
| 记忆 | "我等你不敲了再干" | "我定时干一次，中间不干" |

## 5. 前后端分工：谁防什么

| 层 | 手段 | 防什么 | 能防 |
|----|------|--------|------|
| **前端** | 防抖/节流 + 按钮置灰 | 用户手抖、疯狂触发 | 正常用户 ✅ |
| **后端** | 幂等（令牌/状态机/唯一约束） | 网络重试、消息重投、恶意刷单 | **一切重复 ✅** |

> ⚠️ **前端防抖 ≠ 后端幂等**：防抖防的是"用户层面的一次触发"，防不住"客户端超时重试、MQ 重投、脚本刷单"——这些请求前端压根没参与。**凡涉及钱的接口，后端幂等是底线，前端防抖只是体验优化**。

## 6. 边界与陷阱

| # | 陷阱 | 症状 | 解法 |
|---|------|------|------|
| ① | 令牌"先查后删"两步走 | 高并发下重复放行 | 用 `setIfAbsent` 原子操作（3.3 节） |
| ② | 唯一约束没兜底 | Redis 挂了令牌全失效 → 重复下单 | 资金类必须数据库唯一键兜底（3.5 节） |
| ③ | 扣减类用"读-改-写"做幂等 | 两个请求都读到 100，都减 10 = 只减一次但结果错 | 条件更新/乐观锁（[MySQL 事务与锁](../../01-关系型数据库/MySQL/03-事务与锁机制.md)） |
| ④ | 幂等键设计太宽 | 用户两次正常操作被误判重复 | 幂等键 = 业务唯一键（订单号/流水号），不含时间戳等易变值 |
| ⑤ | 幂等键设计太窄 | 真正重复的请求漏网 | 同一业务的所有重复入口共用同一个键（回调 + 手动 + 重试） |
| ⑥ | 幂等检查与业务不同事务 | 检查通过、业务失败，下次重试没机会 | 标记在业务事务内写（同一库同事务） |
| ⑦ | 只防 POST 不防回调 | 回调重试照样重复 | 回调接口同样做幂等（唯一约束最稳） |
| ⑧ | TTL 设太短 | 长时间后合法重试被拒 | 令牌 TTL > 业务最长处理时间 |

> 🎯 幂等设计自检四问：① 幂等键是什么？（业务唯一键）② 幂等检查在哪一步？（处理入口）③ 幂等标记和业务是否同事务？（同一库）④ 重复请求返回什么？（原结果/友好提示，不报错）——四问过了再上线。
