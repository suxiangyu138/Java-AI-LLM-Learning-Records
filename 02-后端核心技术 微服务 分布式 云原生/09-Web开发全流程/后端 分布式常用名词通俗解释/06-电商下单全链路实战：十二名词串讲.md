## 1. 场景设定：大促秒杀下单

| 项目 | 数值 | 说明 |
|------|------|------|
| 用户量 | 100 万同时在线 | 30% 在抢购页 |
| 秒杀 QPS | 峰值 10 万/秒 | 平时 500/秒 |
| 商品 | 1 件爆品 × 1 万件库存 | 热点数据集中 |
| 系统 | 微服务：网关 → 商品服务 → 订单服务 → 支付服务 + MySQL 分片 + Redis + MQ | — |
| 硬约束 | 不能超卖、不能重复扣款、系统不能崩 | 正确性 + 可用性 |

## 2. 全链路时序图（十二名词落点）

```text
用户（100 万）
  │
  ▼
① 网关层 ────────────── 限流【限流】：按 IP/用户 QPS 限流，超 10 万/秒直接拒绝（防刷）
  │
  ▼
② 商品详情 ──────────── 缓存【缓存】：商品信息预热进 Redis，详情读缓存不落库（扛 9 万读）
  │
  ▼
③ 点击"立即秒杀" ─────── 幂等【幂等】：前端先领 Token（防抖【防抖】：按钮连点只发一次）
  │
  ▼
④ 库存预扣（Redis 原子）── 条件扣减：DECR 库存 > 0 才放行（防超卖，Lua 原子）
  │
  ▼
⑤ 秒杀请求入队 ───────── 削峰【削峰】：请求写 MQ 队列（10 万/秒 → 队列缓冲）
  │                       解耦【解耦】：下单服务只收消息，不直接对接用户流量
  ▼
⑥ 订单服务消费 ───────── 异步【异步】：按 2000 TPS 消费队列，用户"排队中"不阻塞
  │                       幂等【幂等】：消息带订单号，重复投递被唯一约束挡住
  │
  ▼
⑦ 写订单库（分片） ────── 分片【分片】：订单按 user_id 分片落库（10 张表）
  │                       状态机【幂等】：订单状态 PENDING→PAID 只能走一次
  │
  ▼
⑧ 支付回调 ──────────── 幂等【幂等】：支付回调按流水号唯一约束，重复回调只处理一次
  │                       最终一致：支付成功消息 → 异步发短信/加积分（解耦+异步）
  ▼
⑨ 依赖故障时 ─────────── 熔断【熔断】：支付服务超时 → 熔断器打开 → 返回"稍后查询"
                         降级【降级】：推荐/历史订单接口直接关掉，保下单主流程
                         隔离【容错】：支付依赖独立线程池，拖垮不了订单服务
                         背压【背压】：MQ 积压超阈值 → 告警 + 暂停秒杀入口（源头降速）
                         雪崩【雪崩】：以上全部没做 → 全链路崩溃（反面教材）
```

## 3. 逐环节拆解：每一步为什么这么设计

### 3.1 入口：限流 + 防抖 + 缓存

| 环节 | 用的名词 | 为什么 | 细节 |
|------|---------|--------|------|
| 网关 | **限流** | 10 万 QPS 全放进来，任何服务都扛不住 | 按 IP + 用户双维度；快速失败返回"已售罄/稍后重试" |
| 详情页 | **缓存** | 9 万读请求打 MySQL 必崩 | 商品信息预热 Redis；读多写少典型场景 |
| 按钮 | **防抖** | 用户连点 10 次 = 10 个请求 | 前端按钮置灰 + 防抖只发一次（体验层） |

> 💡 第一层防线目标：**把 10 万 QPS 里的 9 万"纯读"用缓存吃掉，剩下的 1 万"真下单"才进业务链路**——入口层挡得越多，后面越轻松。

### 3.2 下单：令牌幂等 + Redis 预扣 + MQ 削峰

```java
// 下单入口（聚合了幂等 + 削峰 + 异步）
@PostMapping("/seckill/order")
public String seckill(@RequestParam Long userId, @RequestParam Long skuId,
                      @RequestParam String token) {
    // ① 幂等：令牌验票（防重复提交）
    if (!redisTemplate.opsForValue()
            .setIfAbsent("seckill:token:" + userId + ":" + skuId, "1",
                    Duration.ofSeconds(30))) {
        return "重复提交，请勿多次点击";
    }

    // ② 防超卖：Redis 原子扣库存（Lua 保证原子）
    Long stock = redisTemplate.execute(seckillLua, List.of("stock:" + skuId));
    if (stock == null || stock < 0) {
        return "已售罄";
    }

    // ③ 削峰：请求进 MQ，异步下单
    orderProducer.send(new SeckillMsg(userId, skuId, generateOrderNo()));  // 订单号=幂等键
    return "排队中，请稍后查询结果";       // 立即返回，不阻塞
}
```

| 设计点 | 对应名词 | 防的是什么 |
|--------|---------|-----------|
| 令牌 setIfAbsent | 幂等 | 同一用户重复提交 |
| Lua 原子扣库存 | （防超卖） | 并发扣成负数 |
| MQ 入队 + 立即返回 | **削峰 + 异步 + 解耦** | 10 万瞬时流量压垮数据库 |

### 3.3 消费端：状态机 + 唯一约束双保险

```java
// 订单服务消费秒杀消息（幂等 + 状态机双保险）
@Transactional
public void createOrderFromMsg(SeckillMsg msg) {
    // ① 幂等第一层：消息携带订单号，DB 唯一约束兜底
    try {
        orderRepository.insert(msg.orderNo(), msg.userId(), ...);
    } catch (DataIntegrityViolationException e) {
        log.warn("重复消息：{}", msg.orderNo());      // 已存在，直接跳过
        return;
    }

    // ② 状态机：扣库存 + 订单状态流转（条件更新）
    int rows = inventoryRepository.deduct(skuId, 1);  // UPDATE ... WHERE stock >= 1
    if (rows == 0) {
        orderRepository.transition(msg.orderNo(), PENDING, FAILED);  // 库存不足
        return;
    }
    orderRepository.transition(msg.orderNo(), PENDING, PAID);
    // ③ 解耦异步：发支付成功事件 → 短信/积分/对账各自消费
    orderEventPublisher.publish(new OrderPaidEvent(msg.orderNo()));
}
```

| 设计点 | 对应名词 | 防的是什么 |
|--------|---------|-----------|
| 唯一约束 + 异常捕获 | 幂等 | MQ 重复投递、消费失败重试 |
| 条件更新扣库存 | （防超卖） | 读-改-写并发窗口 |
| 状态机流转 | 幂等 | 重复支付回调、乱序消息 |
| 发事件消息 | **解耦 + 异步** | 短信/积分不阻塞订单主流程 |

### 3.4 支付回调与数据存储

| 环节 | 名词 | 细节 |
|------|------|------|
| 支付回调 | **幂等** | 回调可能重复 N 次：按"支付流水号"唯一约束，第二次直接返回已处理 |
| 订单落库 | **分片** | 按 user_id 分片（`user_id % 10`），"我的订单"查询命中单片 |
| 订单号 | （分布式 ID） | 雪花/UUIDv7 生成，不能依赖自增（跨片唯一） |
| 积分/短信 | **解耦 + 异步 + 最终一致** | 消费支付成功消息；失败重试 + 对账兜底 |

### 3.5 故障时的保命设计

| 故障 | 手段 | 用户看到 | 为什么不死 |
|------|------|---------|-----------|
| 支付服务变慢 | **超时 + 熔断 + 降级** | "支付处理中，请稍后查看" | 熔断后不再打支付，订单服务线程不被占死 |
| 推荐服务挂了 | **降级** | 默认推荐位 | 非核心功能让路，下单不受影响 |
| 支付依赖占满线程 | **隔离** | 无感知 | 独立线程池，烧自己的池不烧全服务 |
| MQ 积压暴涨 | **背压**（监控 → 暂停秒杀入口） | 秒杀暂停提示 | 源头降速，不把消费端拖死 |
| 什么措施都没有 | **雪崩** | 全站 503 | ——反面教材：B 慢 → A 线程耗尽 → C 也挂 |

## 4. 故障演练：链路里每个环节崩了会怎样

| 演练场景 | 系统行为 | 用户结果 | 结论 |
|---------|---------|---------|------|
| Redis 宕机 | 详情读缓存 miss → 落库被压垮（雪崩） | 页面打不开 | 必须 Redis 高可用 + 本地缓存兜底 |
| MQ 宕机 | 秒杀请求发不进去 | "排队中"但无结果 | MQ 集群高可用；入口熔断提示"活动繁忙" |
| 订单库主库挂了 | 写不可用 | 下单失败 | 分片后单片故障影响面 = 10% 用户（分片的隐藏收益） |
| 支付回调重复 10 次 | 唯一约束挡住 9 次 | 只扣一次款 | 幂等的价值 |
| 秒杀消息重复 100 次 | 唯一约束 + 状态机双挡 | 只下一单 | 幂等的价值 |
| 消费端处理慢 | 队列积压 → 背压告警 → 暂停入口 | 秒杀暂缓，系统不崩 | 削峰 + 背压组合 |

> 🎯 演练启示：**同一场事故，有幂等是"扣款一次"，没幂等是"扣款十次"；有熔断是"功能降级"，没熔断是"全站瘫痪"**——这就是十二个名词存在的意义：它们不是概念，是灾难发生时"系统还活着"的原因。

## 5. 面试问答演练（10 问）

| # | 问题 | 满分回答要点 |
|---|------|-------------|
| ① | MQ 三大作用？ | 解耦（业务剥离）、异步（主流程不等次要）、削峰（洪峰缓冲）（[01 篇](01-解耦与异步.md) 第 4 节） |
| ② | 限流和削峰区别？ | 限流拒绝超阈值请求；削峰排队缓冲延后处理（[02 篇](02-流量治理：限流、削峰与背压.md) 4.2） |
| ③ | 令牌桶 vs 漏桶？ | 令牌桶允许突发（攒令牌）；漏桶强制匀速（[02 篇](02-流量治理：限流、削峰与背压.md) 2.5） |
| ④ | 熔断 vs 降级？ | 熔断被动（下游故障断开调用）；降级主动（压力大舍弃次要）（[03 篇](03-容错保护：熔断、降级与雪崩.md) 第 6 节） |
| ⑤ | 怎么防雪崩？ | 五件套：超时、限流、熔断、降级、隔离（[03 篇](03-容错保护：熔断、降级与雪崩.md) 第 7 节） |
| ⑥ | 幂等怎么做？ | 三层组合：令牌（防手抖）+ 状态机（防乱序）+ 唯一约束（防漏网）（[04 篇](04-重复请求治理：幂等与防抖.md) 3.5） |
| ⑦ | 防抖和节流？ | 防抖执行最后一次（搜索框）；节流固定间隔一次（滚动加载）（[04 篇](04-重复请求治理：幂等与防抖.md) 4.3） |
| ⑧ | 缓存穿透/击穿/雪崩？ | 不存在/单个热点过期/成片过期（[05 篇](05-数据扩展：缓存与分片.md) 2.4） |
| ⑨ | 分片键怎么选？ | 让高频查询命中单片；订单按 user_id 分片（[05 篇](05-数据扩展：缓存与分片.md) 第 5 节） |
| ⑩ | 秒杀怎么防超卖？ | 三层：Redis 原子预扣（Lua）+ 数据库条件更新（WHERE stock>=1）+ 唯一约束兜底（本页 3.2/3.3） |

> 💡 面试心法：**答概念题先给一句话定义（通俗），再给例子（秒杀/下单），再给实现细节（方案/参数）**——本系列每篇的 🎯 段落就是按这个结构准备的。

## 6. 一页速记版

```text
【流量治理】来的人太多怎么办
  限流：超阈值直接拒绝           → 令牌桶/滑动窗口，Sentinel
  削峰：超阈值排队慢慢处理       → MQ 积压 + 限速消费
  背压：告诉上游慢点发           → 反应式流 / 监控积压喊停

【容错保护】出故障怎么办
  超时：不等注定失败的调用       → 连接 + 读超时
  熔断：下游故障断开调用         → 三态/六态状态机（Resilience4j）
  降级：压力大舍弃次要功能       → 兜底：默认值/缓存/空数据
  隔离：故障关进独立池子         → 线程池/信号量隔离
  雪崩：以上都没做 → 全链路崩    → 五件套缺一不可

【一致性 & 重复】重复请求怎么办
  幂等：重复执行结果一致         → 令牌 + 状态机 + 唯一约束（三层）
  防抖：连续触发只执行最后一次   → 前端，搜素框 500ms
  （节流：固定间隔最多一次 → 滚动加载）

【数据扩展】数据太大/太慢怎么办
  缓存：热数据放 Redis           → 防穿透(空值) 防击穿(锁) 防雪崩(随机TTL)
  分片：拆多份存储               → 哈希/范围，分片键选高频查询

【架构】让上面更容易实现
  解耦：强绑定拆开，A 坏不搞死 B → MQ
  异步：不等慢任务，先返回       → 线程池 / MQ
  MQ 三大作用：解耦 + 异步 + 削峰
```
