## 1. 耦合的代价：一个真实的坏例子

**通俗**：下单的时候，代码里直接调用发短信、加积分。**下单接口要等短信、积分全部执行完才返回。短信服务挂了，下单直接失败**——用户买不了东西，只是因为一条营销短信没发出去。

```java
// 反模式：下单方法里"亲手"做所有事（强耦合）
public OrderEntity createOrder(OrderDto dto) {
    OrderEntity order = orderRepository.save(dto.toEntity());

    smsService.send("下单成功");        // ① 等短信（可能 3 秒超时、可能抛异常）
    pointsService.addPoints(10);        // ② 等积分（可能失败）
    logService.record(order.getId());   // ③ 等日志
    return order;                       // 全部做完才返回 → 慢、脆、耦合
}
```

| 问题 | 表现 | 根源 |
|------|------|------|
| 慢 | 接口耗时 = 下单 + 短信 + 积分 + 日志 之和 | 串行等待所有次要任务 |
| 脆 | 短信服务一挂，下单直接失败 | 次要故障变成主要故障 |
| 僵 | 想加"发优惠券"要改下单代码 | 职责没有边界 |
| 难扩 | 短信要扩容，只能整条链路一起变 | 两个团队改同一段代码 |

> 🎯 **核心矛盾**：下单（核心）和短信/积分（次要）被绑死在同一个请求里——**它们本来就没有"必须同生共死"的关系**。

## 2. 解耦的三层演进

**通俗**：把"必须当场做完的事"和"可以稍后做、甚至不做也行的事"分开。

| 演进阶段 | 做法 | 效果 | 代价 |
|---------|------|------|------|
| **① 直调降级（最简）** | 次要调用包 try-catch，失败不影响下单 | 短信挂了下单也能成 | 异常要吞得讲究；耗时仍在 |
| **② 异步线程池（进程内）** | 次要任务丢线程池，不阻塞主流程 | 快 + 不影响主流程 | 重启丢任务；线程池满照样拖垮 |
| **③ MQ 解耦（进程间）** | 下单成功 → 发消息 → 短信/积分各自消费 | **故障隔离 + 独立扩容 + 削峰** | 引入消息中间件，要学可靠性 |

```java
// 推荐姿势：MQ 解耦
public OrderEntity createOrder(OrderDto dto) {
    OrderEntity order = orderRepository.save(dto.toEntity());
    orderEventPublisher.publish(new OrderCreatedEvent(order.getId(), dto));  // 只发一条消息
    return order;                                    // 立即返回，短信/积分由消费者异步处理
}
```

> 🎯 判断标准一句话：**调用方与被调方是"必须同成功同失败"的关系吗？**——是（扣库存与下单），保持同步直调；不是（短信、积分、日志、统计），解耦异步。**强一致的事不能异步化**，这是新手最常踩的坑。

### 2.1 解耦的正确打开方式：领域事件

```text
下单服务（生产者）                       短信服务（消费者）
     │  ① 下单成功                             │
     │  ──发布 OrderCreatedEvent──► MQ ──► ────│ 收到消息 → 发短信
     │  ② 立即返回用户"下单成功"                 │ 收到消息 → 加积分
     │  ③ 即使短信服务宕机，消息还在 MQ 里等着    │ 恢复后继续消费
```

| 收益 | 说明 |
|------|------|
| 故障隔离 | 消费者挂了不影响生产者（消息滞留，恢复后补发） |
| 独立演进 | 加"发优惠券"新消费者，下单代码一行不改 |
| 独立扩容 | 短信量大，单独给消费组加机器 |
| 削峰缓冲 | 瞬时洪峰先积压，消费端按能力慢慢处理（[02 篇](02-流量治理：限流、削峰与背压.md)） |

> ⚠️ 反模式提醒：**为了解耦而滥用 MQ**——两个服务明明是同步强一致的（比如下单必须扣库存），硬塞 MQ 变成最终一致，只会把"事务问题"变成"更难调的分布式问题"。解耦的度：**能同步搞定的，别为了"架构好看"引入 MQ**。

## 3. 异步的四种实现方式

**通俗**：不用等这件事做完，直接返回，后台慢慢做——点完菜拿号走人，菜做好通知你。

| 方式 | 粒度 | 适用 | 局限 |
|------|------|------|------|
| **线程池**（CompletableFuture） | 进程内任务 | 日志、统计、发邮件等轻任务 | 重启丢任务；池满阻塞主流程 |
| **MQ** | 跨服务任务 | 业务解耦 + 削峰 + 可靠性要求 | 需要中间件；有延迟与重复 |
| **异步框架**（Reactive/WebFlux） | IO 密集型全链路 | 高并发 IO 场景 | 学习曲线陡；排查复杂 |
| **延迟任务**（定时/延迟队列） | 非实时任务 | 超时关单、日终对账 | 时间粒度有限制 |

```java
// 线程池异步（轻任务够用）
@Async("taskExecutor")                 // 需要 @EnableAsync
public void recordLog(Long orderId) {
    logService.record(orderId);        // 返回 Future，不阻塞调用方
}

// CompletableFuture 编排（多个异步任务）
CompletableFuture.allOf(
        asyncSms.send(order),
        asyncPoints.add(order)
).join();
```

> 🎯 选型一句话：**进程内小任务用线程池，跨服务/要可靠性/要削峰用 MQ，高 IO 全链路异步才上响应式**——90% 的业务场景，线程池 + MQ 就够了。

## 4. MQ 三大作用（面试高频）

**通俗**：MQ（消息队列）像"快递中转站"——你不必亲手把东西送到对方手里，扔进快递站，对方有空了来取。

### 4.1 解耦

| 维度 | 直调 | 走 MQ |
|------|------|-------|
| 失败影响 | 短信挂 → 下单失败 | 短信挂 → 下单照常，消息排队等它恢复 |
| 新增业务 | 改下单代码 | 加一个消费者，代码零改动 |
| 依赖方向 | 下单依赖短信（上行依赖） | 双方只依赖 MQ（下行独立） |

### 4.2 异步

| 维度 | 串行直调 | MQ 异步 |
|------|---------|---------|
| 耗时 | 下单 200ms + 短信 200ms + 积分 200ms = **600ms** | 下单 200ms + 发消息 5ms = **205ms** |
| 用户感知 | 等 600ms | 秒回 |

### 4.3 削峰

**通俗**：瞬间大量请求涌过来，不直接打垮数据库，把请求排队缓冲，慢慢处理。

```text
1 万 QPS 洪峰 ──► MQ 队列（积压缓冲）──► 消费端按 1000 QPS 能力消化
                                    └─ 高峰过去，慢慢追平积压
```

> ⚠️ **削峰不是提升处理速度，是把瞬时洪峰摊平到一段时间处理**——用户会有延迟，但系统不会崩（秒杀场景典型，[02 篇](02-流量治理：限流、削峰与背压.md) 有完整设计）。

> 🎯 面试必答：**"MQ 三大作用是什么？"**——解耦（业务之间剥离依赖）、异步（主流程不等次要任务）、削峰（瞬时流量缓冲，平缓压力）；进阶加分：**消息可靠性三大投递语义**（at-most-once/at-least-once/exactly-once）、顺序性、积压处理——详见 [消息队列理论与实战](../../03-消息队列/消息队列理论与实战/00-消息队列知识体系总览.md)。

### 4.4 主流 MQ 一句话选型（2026）

| MQ | 一句话定位 | 典型场景 |
|----|-----------|---------|
| Kafka | 吞吐之王，日志/流处理标配 | 大数据、日志、埋点 |
| RocketMQ | 阿里系，事务消息/延迟消息完善 | 电商订单、事务一致性 |
| RabbitMQ | 轻量灵活，路由模型丰富 | 中小团队、复杂路由 |
| Pulsar | 云原生架构，多租户/分层存储 | 大集群、存储计算分离 |
| Redis Stream | 轻量队列，随缓存顺手用 | 简单任务队列（非核心） |

> 💡 选型口诀：**要吞吐选 Kafka、要事务消息选 RocketMQ、要轻选 RabbitMQ、要云原生选 Pulsar**——深度对比见 [消息队列选型](../../03-消息队列/消息队列理论与实战/08-选型与生产实践.md)。

## 5. 异步化的代价：最终一致性

**通俗**：同步是"我们当场对好账"，异步是"回头慢慢对账，只要最后对上就行"——**异步让出了强一致，换来的是快和解耦**，但这个账必须"最后对得上"。

### 5.1 从 ACID 到 BASE

| 模型 | 含义 | 代价 |
|------|------|------|
| ACID（同步直调） | 强一致：要么全成、要么全不成 | 慢、耦合、不可扩展 |
| BASE（异步+MQ） | 最终一致：基本可用、软状态、最终一致 | 有一致性窗口，要补偿 |

### 5.2 保证"最后对得上"的三种方案

```text
方案一：本地消息表（通用，最简单可靠）
  下单事务（本地）         定时任务/消费端
  ┌────────────────┐    ┌────────────────────┐
  │ ① 写订单表        │    │ 轮询未确认消息 → 发送    │
  │ ② 写消息表(同事务) │ ─► │ 消费成功 → 标记已确认    │
  └────────────────┘    └────────────────────┘

方案二：事务消息（RocketMQ 独有）
  半消息（先确认事务） → 本地事务成功 → commit 消息 → 消费者可见
                     → 本地事务失败 → rollback 消息

方案三：binlog 订阅（Canal）
  数据库变更 → binlog → 同步到 MQ/ES/Redis（无侵入，不写业务代码）
```

| 方案 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| 本地消息表 | 实现简单、通用 | 多一张表、定时扫描有延迟 | **通用首选** |
| 事务消息 | 无定时扫描、毫秒级可靠 | 依赖 RocketMQ | 已用 RocketMQ 的项目 |
| binlog 订阅 | 对业务零侵入 | 需要 Canal 组件、学习成本 | 数据同步场景（ES/缓存） |

> ⚠️ **分布式事务的正确认知**：能不用分布式事务就不用——**先用"本地事务 + 消息"保证自己这一端可靠，跨系统靠最终一致 + 对账补偿**；强一致跨库场景（资金）才上 Seata/两阶段提交（详见 [消息队列分布式事务](../../03-消息队列/消息队列理论与实战/07-分布式事务与消息队列.md)）。

## 6. 边界与陷阱

| # | 陷阱 | 症状 | 解法 |
|---|------|------|------|
| ① | **强一致操作被异步化** | 下单成功但库存没扣（超卖） | 扣库存必须与下单同事务/同步 |
| ② | 消费者没做幂等 | 消息重投 → 重复发短信/重复加积分 | [04 篇](04-重复请求治理：幂等与防抖.md) 幂等四方案 |
| ③ | 消息丢失 | 极端情况下任务静默消失 | 生产者 confirm + 消费者手动 ack（[可靠性三语义](../../03-消息队列/消息队列理论与实战/02-消息可靠性：三大投递语义.md)） |
| ④ | 消费失败不重试 | 一条坏消息卡死消费进度 | 重试 + 死信队列（[延迟死信](../../03-消息队列/消息队列理论与实战/05-延迟消息与死信队列.md)） |
| ⑤ | 顺序要求被忽略 | 先到的更新反而后执行 | 顺序消息/分区内有序（[顺序消息](../../03-消息队列/消息队列理论与实战/03-顺序消息与有序性.md)） |
| ⑥ | 异步任务无监控 | 任务在后台悄悄失败没人知道 | 消费指标监控 + 告警 + 对账任务 |
| ⑦ | 线程池无界 | 大量任务排队 → 内存耗尽 | 有界队列 + 拒绝策略（CallerRuns） |

> 🎯 异步化自检五问：① 这个任务失败会影响核心流程吗？（不会才异步）② 消息会重复吗？消费端幂等了吗？③ 消息会丢吗？投递确认做了吗？④ 消费失败怎么办？有重试和死信吗？⑤ 任务积压了怎么发现？（监控）——**五问全过，才敢上线**。
