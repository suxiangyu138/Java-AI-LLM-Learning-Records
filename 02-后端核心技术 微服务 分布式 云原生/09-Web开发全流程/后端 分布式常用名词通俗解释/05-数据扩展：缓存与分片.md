## 1. 缓存：热数据放快处

**通俗**：商品详情，不用每次查 MySQL，放到缓存，直接读缓存返回——常用工具放桌面，不每次去仓库翻。

```text
读请求 ──► 查 Redis（1ms）─► 命中：直接返回 ✅
                  └─► 未命中：查 MySQL（10ms+）→ 写回 Redis → 返回
```

| 存储 | 读性能 | 容量 | 成本 | 用途 |
|------|:---:|:---:|:---:|------|
| 内存（进程内） | 纳秒级 | 小 | 低 | 热点单机缓存（Caffeine） |
| Redis | 毫秒级 | 大 | 中 | **分布式缓存（主力）** |
| MySQL | 毫秒~秒级 | 大 | 高 | 数据主存 |

> 🎯 什么时候该上缓存：**读多写少 + 读流量超过数据库承受 + 数据变更不频繁**（商品详情、用户会话、字典）——写多读少/强一致数据（库存、余额）缓存要非常小心。

## 2. 缓存三大坑：穿透、击穿、雪崩（面试必考）

### 2.1 缓存穿透

**通俗**：查一个**根本不存在**的 key（如 `id=-1` 的商品）——缓存里没有，每次都直接打到数据库，恶意刷不存在的数据 = 数据库被白打。

```text
攻击：连续请求 id=-1/-2/-999 等不存在商品
  Redis：都没有（null 不缓存）→ 每次落库
  MySQL：被不存在的查询打满
```

| 解法 | 做法 | 适用 |
|------|------|------|
| **缓存空值** | 不存在的也缓存 5 分钟（value=null） | 通用首选 |
| 布隆过滤器 | 查前先判断"可能存在吗"（不存在直接返回） | 大规模不存在查询（如手机号查号） |
| 参数校验 | 非法 id 提前拦截 | 入口防线 |

```java
// 缓存空值：防止穿透
Object v = redis.get(key);
if (v == null) {
    Product p = productRepository.findById(id).orElse(null);
    if (p == null) {
        redis.set(key, "EMPTY", Duration.ofMinutes(5));   // 空值也缓存，短 TTL
        return null;
    }
    redis.set(key, p, Duration.ofMinutes(30));
}
```

### 2.2 缓存击穿

**通俗**：一个**热点 key 恰好过期**，瞬间大量请求同时打向数据库——数据库同时被几百个"重建缓存"的请求打满。

| 解法 | 做法 | 说明 |
|------|------|------|
| **互斥锁** | 只有第一个请求查库，其余等它 | `SETNX lock:key`，重建完放行 |
| 逻辑过期 | 缓存永不过期，过期时间写在 value 里，读到过期异步重建 | 无锁无阻塞，但数据有一瞬旧 |
| 热点永不过期 + 后台刷新 | 活动期间手动延长 TTL | 运营手段 |

```java
// 互斥锁重建：防止击穿
public Product getProduct(Long id) {
    String key = "product:" + id;
    Product p = (Product) redis.get(key);
    if (p != null) return p;

    Boolean locked = redis.opsForValue()
        .setIfAbsent("lock:product:" + id, "1", Duration.ofSeconds(3)); // 抢锁
    if (Boolean.TRUE.equals(locked)) {
        try {
            p = productRepository.findById(id).orElseThrow();
            redis.set(key, p, Duration.ofMinutes(30));   // 重建 + 缓存
            return p;
        } finally {
            redis.delete("lock:product:" + id);          // 释放锁
        }
    }
    Thread.sleep(50);                                     // 没抢到锁的等一会儿
    return getProduct(id);                                // 重读缓存
}
```

### 2.3 缓存雪崩

**通俗**：大量 key **同时过期**（或 Redis 整个宕机）——所有请求同时落库，数据库瞬间被打垮。

| 场景 | 解法 |
|------|------|
| 大量 key 同时过期 | **过期时间加随机值**（`TTL + random(0,300s)`），错峰过期 |
| Redis 宕机 | ① 集群高可用（[Redis 哨兵/Cluster 系列](../../02-非关系型数据库/Redis/)）；② 多级缓存（本地 Caffeine 兜底）；③ 限流 + 熔断保护数据库 |

### 2.4 三兄弟对比表（面试必答）

| 维度 | 穿透 | 击穿 | 雪崩 |
|------|------|------|------|
| 查什么 | **不存在的 key** | **一个热点 key** 过期 | **大量 key** 同时过期 |
| 后果 | 恶意流量打库 | 一个热点把库打满 | 成片过期打库 |
| 类比 | 查一个不存在的人 | 明星同一天退休 | 全城人同一天退休 |
| 解法 | 缓存空值/布隆 | 互斥锁/逻辑过期 | 随机 TTL/高可用 |

> 🎯 面试口诀：**"穿透是查不存在的（空值/布隆），击穿是单个热点过期（互斥锁），雪崩是成片过期或宕机（随机 TTL + 高可用）"**——三个词说清区别，是缓存题的标准开场。

## 3. 缓存一致性：双写怎么不错乱

**通俗**：数据既在数据库又在缓存，两边更新顺序错了，用户就看到旧数据——一致性窗口是缓存的"原罪"，只能缩小、不能消灭。

### 3.1 三种更新策略

| 策略 | 流程 | 问题 |
|------|------|------|
| **Cache Aside（推荐）** | 读：先查缓存，miss 查库回填；写：**先更新库，再删缓存** | 删除失败会有一致性窗口 |
| 先删缓存再写库 | 删缓存 → 写库 | **窗口期更大**（删除后、写库前，请求读到旧值又回填）|
| 双写缓存 | 写库同时写缓存 | 并发写库乱序 → 缓存被旧值覆盖（最坑） |

```text
Cache Aside 正确姿势：
写请求：UPDATE 数据库 ✅ → DELETE 缓存
读请求：GET 缓存 → miss → SELECT 数据库 → 回填缓存

为什么是"删缓存"而不是"更新缓存"？——更新是"无脑覆盖"，并发写乱序会覆盖成旧值；
删除后读请求会重新回填，"谁最后写库谁就是新值"，天然正确。
```

### 3.2 一致性增强三板斧

| 手段 | 解决 | 说明 |
|------|------|------|
| **延迟双删** | 删除缓存后延迟 1s 再删一次 | 兜住"读回填旧值"的窗口（MySQL 主从同步场景） |
| **binlog 订阅（Canal）** | 写库后自动删/刷新缓存 | 不写业务代码，可靠（[01 篇](01-解耦与异步.md) 5.2） |
| 消息队列异步失效 | 删缓存失败重试 | 删除操作走 MQ，失败重投 |

> ⚠️ **一致性 vs 性能的取舍红线**：**资金/库存类数据别放缓存**（或只做"缓存只读 + 强校验"）——一致性窗口里卖超了库存是事故；电商经典方案是"库存预热到 Redis + 扣减走 Lua 原子操作 + 数据库兜底对账"。

## 4. 分片：装不下就拆开

**通俗**：用户表 1 亿条，一张表扛不住，按用户 ID 拆分到 10 张表——就是分库分表。

### 4.1 拆分的四个层次

| 层次 | 做法 | 解决 | 代价 |
|------|------|------|------|
| 垂直分表 | 把宽表的列拆到多张表（订单主表 + 订单扩展表） | 行宽、冷热分离 | 查询要 join/两次 |
| 垂直分库 | 按业务拆库（订单库/用户库/商品库） | 单库压力、职责边界 | 跨库事务变分布式事务 |
| **水平分表** | 同结构表拆多份（user_0 ~ user_9） | **单表数据量** | 跨表查询、聚合难 |
| **水平分库** | 同结构拆到多库多表（ds_0.user_0 ...） | 单库容量 + 并发 | 最复杂，最后手段 |

```text
水平拆分示例：user_id % 10 → 10 张表
user_id=123 → 123 % 10 = 3 → user_3 表
user_id=456 → 456 % 10 = 6 → user_6 表
```

### 4.2 何时该分片（别过度设计）

| 信号 | 阈值参考 | 先做什么 |
|------|---------|---------|
| 单表数据量 | **> 1000 万 ~ 2000 万行**（MySQL 参考线） | 先优化索引/归档冷数据 |
| 单库 QPS | 压测超过容量 60% | 先上缓存/读写分离 |
| 单表写入 | 写热点集中在尾部行（自增主键） | 归档/分区表（PARTITION）先试 |

> ⚠️ **分片是最后手段，不是第一选择**：1000 万行以内，索引 + 归档 + 读写分离就能解决 90% 的问题；分片带来的复杂度（跨片查询、分布式事务、扩容）是巨大的——**过早分片是架构反模式**（面试可以主动讲这个观点，加分）。

## 5. 分片键：拆哪一列有讲究

**通俗**：分片键决定一条数据去哪张表——选对了，几乎所有查询都只打一张表；选错了，每次查询都要扫所有表。

| 分片算法 | 做法 | 优点 | 缺点 |
|---------|------|------|------|
| **哈希取模** | `user_id % N` | 数据均匀 | 扩容要迁移（2 的幂次缓解） |
| **一致性哈希** | 环形哈希 | **扩容迁移少** | 实现复杂，可能不均匀 |
| **范围分片** | 按时间/ID 区间拆 | 范围查询友好、天然归档 | 热点倾斜（新数据全在一个片） |
| 业务维度 | 按租户/地域拆 | 隔离清晰 | 大租户/大区仍倾斜 |

| 场景 | 推荐分片键 | 原因 |
|------|-----------|------|
| 订单表 | `user_id`（或租户 id） | 用户查自己的订单是 90% 的查询 |
| 消息/日志表 | 时间范围 | 天然按时间归档查询 |
| 用户表 | `user_id` | 单点查询为主 |

> 🎯 分片键选择标准：**让"最频繁的查询"变成"单片查询"**——订单按 user_id 分片后，`WHERE user_id=?` 直接命中一张表；反之按 order_id 分片，查"我的订单"要扫 10 张表。**分片键一旦定了，几乎改不动**（改了要全量数据迁移），是决策成本最高的设计。

## 6. 分片后的新问题

| 问题 | 表现 | 解法 |
|------|------|------|
| **跨片查询** | 按非分片键查询要扫所有片 | ① 建立"索引表"（id → 分片路由）；② 冗余存储（ES 做全量检索）；③ 接受扫全片（低频） |
| **分布式事务** | 跨片更新不能本地事务 | 尽量"同片事务"设计；必须跨片用 TCC/消息最终一致（[消息队列分布式事务](../../03-消息队列/消息队列理论与实战/07-分布式事务与消息队列.md)） |
| **扩容/数据迁移** | 加机器要重新分布数据 | 一致性哈希 / 2 的幂次扩容（从 8 片扩 16 片只迁移一半）；提前规划容量 |
| **全局唯一主键** | 自增 id 每个片独立，会撞 | [分布式 ID（雪花算法/UUIDv7）](../../08-分布式系统与架构/雪花算法/04-分布式ID方案全景.md) |
| **聚合统计** | count/sum 要聚合所有片 | 预聚合表 / 离线数仓 |
| **排序分页** | 全局第 3 页 = 每片第 3 页再合并 | 用分片键过滤后再排序；或搜索引擎兜底 |

> 💡 生产现实：**分片之上通常再叠一层"读写分离 + 缓存 + 归档"**——能用缓存扛的读请求根本不落库，分片的收益才真正兑现；同时引入 [ShardingSphere](https://shardingsphere.apache.org/) 这类中间件托管分片路由与读写分离，业务代码不感知。

## 7. 缓存与分片的分工

| 维度 | 缓存 | 分片 |
|------|------|------|
| 解决什么 | **读得快**（热数据） | **装得下**（海量数据） |
| 数据形态 | 冗余副本（与库不同步） | 完整数据（分割存放） |
| 数据丢失 | 可接受（重查库回填） | 不可接受（数据本体） |
| 一致性 | 允许窗口（要管理） | 必须强一致（同片内） |
| 成本 | Redis 内存贵，按热点存 | 磁盘便宜，全量存 |
| 一句话 | 缓存治"慢"，分片治"大" | — |

> 🎯 组合套路（大厂通用架构）：**分片解决容量（库拆开）→ 缓存解决热点（热数据进 Redis）→ 读写分离解决并发（读走从库）→ ES 解决复杂检索（全文/聚合）**——四层各管一段，每层问题都小。
