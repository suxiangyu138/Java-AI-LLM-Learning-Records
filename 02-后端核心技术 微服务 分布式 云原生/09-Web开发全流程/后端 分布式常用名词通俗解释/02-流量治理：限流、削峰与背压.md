# 02 流量治理：限流、削峰与背压

> **通俗**：限流——超阈值直接拒绝；削峰——超阈值排队缓冲慢慢处理；背压——下游扛不住就喊上游降速。本讲：限流四算法、Sentinel 三种流控效果、秒杀削峰设计、背压与反应式流。

## 1. 为什么必须流量治理

**通俗**：系统设计时的容量是"按平均流量"配的，但线上流量是"尖峰"——秒杀、大促、热点事件瞬间几倍于均值。没有流量治理，第一个尖峰就把数据库打崩了。

```text
请求量
 │            ╭──╮
 │           ╭╯  ╰╮            ← 尖峰：超容量 3 倍
 │          ╭╯    ╰╮
 │      ╭───╯      ╰───╮
 │  ════╪═══════════════════ ← 容量红线：只扛得住平均值
 │  ════╪═══════════════════ ← 安全线
 └─────┴──────────────────→ 时间
        没治理 → 红线上面的流量全部"打到系统崩溃"
```

| 不治理的后果 | 表现 |
|-------------|------|
| 数据库连接耗尽 | 慢查询堆积 → 连接池打满 → 全站 503 |
| 线程池耗尽 | 请求排队超时 → 雪崩（[03 篇](03-容错保护：熔断、降级与雪崩.md)） |
| 连锁扩散 | 一个接口被刷爆 → 拖垮整个服务 → 上游也挂 |

> 🎯 核心心法：**容量永远不可能按峰值设计（贵），所以超出的部分必须有"去处"**——限流（拒绝）、削峰（缓冲）、背压（源头降速），三者就是超峰流量的三个去处。

## 2. 限流四算法（面试必考）

**通俗**：限制请求数量，只放行一部分，多余直接拒绝——商场限流放号，人满了就不让进。

### 2.1 固定窗口

```text
把时间切成 1 秒一个窗口，每窗口最多放 N 个请求，满了就拒。
窗口 1: [0s~1s] 放 100 个（满）
窗口 2: [1s~2s] 再放 100 个
问题：0.9s~1.1s 这 0.2 秒里实际放了 200 个 → 临界突刺
```

| 特点 | 说明 |
|------|------|
| 实现 | 计数器（每秒重置），最简 |
| 缺陷 | **窗口临界突刺**：边界前后各打满一个窗口 = 双倍流量 |

### 2.2 滑动窗口

```text
窗口是"滑动"的：任意 1 秒内的请求数 ≤ N。
0.5s~1.5s、1.2s~2.2s…… 每个 1 秒切片都校验。
实现：把窗口切成小格（如 10 格），滑动统计。
```

| 特点 | 说明 |
|------|------|
| 改进 | 消灭临界突刺（窗口粒度越小越平滑） |
| 代价 | 比固定窗口多一份内存/计算 |

### 2.3 漏桶

```text
桶 = 固定容量缓存，漏口 = 恒定速率。
进水多快都行，但出水永远是匀速 → 流量被"整形"成均匀的。
│░░░░│← 请求进来
│░░  │← 缓存（有容量上限，满了丢/拒）
└────┘
   ╲___╱ 恒定速率流出（如 100 req/s）
```

| 特点 | 说明 |
|------|------|
| 本质 | 强制**匀速**，平滑突发 |
| 缺陷 | 突发流量无法"快速消费"（即使系统有余力也只能匀速） |

### 2.4 令牌桶

```text
桶里按速率放令牌（如 100 个/秒），请求必须"拿一个令牌"才能通过。
空闲时桶里攒满令牌（如 200），突发时可以一次性消耗 → 允许突发！
│●●●│← 令牌池（攒到上限）
  ╲  请求来了拿一个令牌 → 放行；没令牌 → 拒绝
```

| 特点 | 说明 |
|------|------|
| 本质 | 允许**突发**（攒的令牌）但平均速率受限 |
| 优势 | **互联网限流首选**（允许正常突发，挡住超峰） |
| 典型 | Guava RateLimiter、Sentinel 快速失败 |

### 2.5 四算法对比总表

| 算法 | 能否应对突发 | 平滑性 | 实现成本 | 典型场景 |
|------|:---:|:---:|:---:|---------|
| 固定窗口 | ⚠️ 临界突刺 | 差 | 最低 | 简单计数 |
| 滑动窗口 | ✅ | 中 | 低 | **API 网关限流（主流）** |
| 漏桶 | ❌（强制匀速） | 最好 | 中 | 流量整形、削峰填谷 |
| 令牌桶 | ✅ | 好 | 中 | **接口限流（主流）** |

> 🎯 面试必答：**"令牌桶和漏桶的区别？"**——漏桶输出**恒定速率**（不管输入多猛，输出永远匀速，天然整形）；令牌桶允许**突发**（桶里攒的令牌可以一次花光），平均速率受控。选型：**允许突发选令牌桶，要求匀速选漏桶**。

## 3. 限流维度与工具落地

### 3.1 限流维度

| 维度 | 限什么 | 例子 |
|------|--------|------|
| QPS 限流 | 每秒请求数 | 接口最多 1000 QPS |
| 并发线程数限流 | 同时处理中的请求数 | 最多 200 并发，超了直接拒绝 |
| 热点参数限流 | 按参数值单独限 | 商品 A 被刷 → 只限商品 A 的请求 |
| 用户/IP 限流 | 按调用方限 | 每用户每秒 5 次 |

> 💡 **热点参数限流**是 Sentinel 独有亮点：秒杀场景"大部分流量打向同一个商品"，按普通 QPS 限流会误伤其他商品——按参数（商品 ID）分别限流，精准保护热点。

### 3.2 工具落地（2026 现状）

| 工具 | 状态 | 定位 |
|------|------|------|
| **Sentinel**（阿里） | **活跃维护**（1.8.6+），Hystrix 停更（2018）后的主流替代 | 限流 + 熔断 + 系统自适应保护，Spring Cloud Alibaba 标配 |
| **Resilience4j** v2.4.0 | 活跃，已支持 Spring Boot 4 / Spring Cloud 5 | 轻量模块化：熔断/限流/重试/舱壁分模块 |
| Gateway 限流 | 网关层统一限流 | 入口第一道防线（按路由/IP/用户） |

```yaml
# Sentinel 限流规则（控制台/Nacos 动态下发，不重启生效）
resource: /order/create          # 资源（接口）
grade: 1                         # 0=线程数 1=QPS
count: 1000                      # 阈值
controlBehavior: 0               # 流控效果：0=快速失败(令牌桶) 1=WarmUp(预热) 2=排队等待(漏桶)
```

| Sentinel 流控效果 | 对应算法 | 适用 |
|-------------------|---------|------|
| 快速失败 | 令牌桶 | 默认；直接拒绝超限请求 |
| **Warm Up 预热** | 冷启动令牌桶 | 系统刚启动，阈值从低逐步升到目标（防冷系统被冲垮） |
| **排队等待** | 漏桶 | 削峰填谷：超限请求排队匀速放行 |

> ⚠️ 落地提醒：① 限流阈值按**压测**定（别拍脑袋：目标 RT/错误率下的最大 QPS）；② 限流位置分层——**网关限流量（入口）、服务限业务（核心接口）、DB 前限最狠（最后防线）**；③ 被限流要有"可感知的响应"（友好提示/排队页），不能干等。

## 4. 削峰：把洪峰摊平成缓坡

**通俗**：不拒绝请求，而是把请求先"存"起来，让后端以自己扛得住的速度慢慢处理——水坝蓄洪，错峰放水。

### 4.1 经典秒杀削峰设计

```text
用户（100 万）                    MQ                     订单服务
     │  ① 点击"立即秒杀"                 │                      │
     │ ──秒杀请求────────► 秒杀队列（积压） ──► 按 2000 TPS 慢慢消费 ──► 写库
     │  ② 返回"排队中"                   │  高峰过去慢慢消化积压        │
     └─ 用户端轮询/推送：排队结果 ─────────────────────────────────►
```

| 步骤 | 做什么 | 对应名词 |
|------|--------|---------|
| ① 入口拦截 | 秒杀按钮 → 请求先写 Redis 预扣 + 进 MQ 队列 | 削峰（缓冲） |
| ② 排队消费 | 订单服务固定速率消费队列 | 削峰（摊平） |
| ③ 结果异步通知 | 处理完推送"成功/失败" | 异步（[01 篇](01-解耦与异步.md)） |
| ④ 兜底 | 队列积压监控 + 消费扩容 | 背压感知（第 5 节） |

> 💡 削峰三板斧：**① 读侧缓存扛住（商品信息全走 Redis）；② 写侧队列缓冲（请求进 MQ 排队）；③ 消费侧限速（按数据库能力固定速率消费）**——缺一个，峰就削不平。

### 4.2 削峰 vs 限流的区别（面试对比）

| 维度 | 限流 | 削峰 |
|------|------|------|
| 超阈值流量 | **拒绝**（返回错误） | **缓冲**（排队延后处理） |
| 用户感知 | 立即失败："请稍后重试" | 有延迟："排队中" |
| 系统状态 | 压力不累积 | 压力累积在队列 |
| 适用 | 防刷、保护非核心 | 秒杀、大促等"可以等"的业务 |

> 🎯 一句话：**限流丢请求，削峰存请求**——能接受"稍等片刻"的业务用削峰，不能等的用限流。

## 5. 背压：让上游慢点发

**通俗**：下游处理速度跟不上上游，上游要降速，不能一股脑猛推数据——传送带堆满了，按暂停键让上游等一下。

### 5.1 三个典型场景

| 场景 | 谁太慢 | 背压怎么实现 |
|------|--------|-------------|
| 生产者 → MQ | 消费者慢，消息越堆越多 | 监控积压量 → 告警/暂停生产/消费扩容 |
| TCP 传输 | 接收方处理不过来 | TCP 协议自带流控（滑动窗口自动降速） |
| 响应式编程 | 订阅者处理慢 | Reactive Streams：`request(n)` 拉取式背压 |

### 5.2 响应式背压（Reactive Streams）

```text
无背压（推）：生产者 1000 条/s 猛推 ──► 消费者只能吃 100 条/s → 崩溃
有背压（拉）：消费者 "我一次只能吃 100 条" ◄── request(100) ── 生产者每次只发 100
```

```java
// WebFlux / Reactor 示例：消费者声明一次要多少，天然背压
Flux.range(1, 10_000)
    .onBackpressureBuffer(100)        // 缓冲上限 100，满了报错（而不是无限堆积）
    .subscribe(consumer, Subscriber::request, 100);   // 每次拉 100 条
```

> 💡 背压与限流的本质区别：**限流是"我自己挡"，背压是"我告诉源头慢点"**——背压是更优雅的方案，但要求上游是"自己人"（同一套系统）；面对外部调用方（App、第三方），只能限流。

## 6. 三兄弟对比与组合

### 6.1 一张表分清

| 维度 | 限流 | 削峰 | 背压 |
|------|------|------|------|
| 作用位置 | 入口（自己侧） | 中间（队列） | 源头（上游） |
| 超量流量 | 拒绝 | 排队 | 降速 |
| 用户感知 | 立即失败 | 延迟完成 | 无感（上游自己降） |
| 实现 | Sentinel/Gateway | MQ | 反应式流/TCP 流控 |
| 控制方 | 服务自己 | 服务自己 | 需要上游配合 |

### 6.2 组合姿势（大促实战）

```text
外部流量 ──► 网关限流（挡刷子、挡超峰）──► 服务限流（按接口/热点参数）
     │                                        │
     └──► 秒杀业务：请求进 MQ 排队（削峰）──► 消费端按容量消费（暗含背压感知）
     │
     └──► 监控积压 → 积压过大 → 通知上游降速（背压）/ 紧急扩容
```

> 🎯 面试加分回答模板：**"你们的流量治理怎么做的？"**——"四层：① 网关按 IP/用户限流挡外部超峰；② 服务内 Sentinel 按 QPS + 热点参数限流（快速失败 + Warm Up）；③ 秒杀等可等待业务请求进 MQ 排队削峰，消费端按数据库容量限速；④ 队列积压监控告警，积压超阈值自动扩容消费组或暂停生产（背压）"。
