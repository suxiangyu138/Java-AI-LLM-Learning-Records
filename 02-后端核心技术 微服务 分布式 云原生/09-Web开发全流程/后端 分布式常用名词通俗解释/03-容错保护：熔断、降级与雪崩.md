# 03 容错保护：熔断、降级与雪崩

> **通俗**：熔断——下游故障，直接"断开"不再调用它，防止连锁卡死；降级——压力大，主动关掉非核心功能保核心业务；雪崩——一个服务挂了，连锁把整条链路搞崩。本讲：雪崩链路 → 超时兜底 → 熔断状态机 → 降级策略 → 舱壁隔离 → 防雪崩五件套。

## 1. 雪崩：多米诺骨牌是怎么倒的

**通俗**：服务 B 挂了，A 大量请求 B 全部超时，大量线程卡死，A 线程耗尽，A 也挂；A 挂了又导致调用 A 的 C 也挂——连锁灾难。

```text
        正常                        故障传播
   ┌───┐    ┌───┐              ┌───┐     ┌───┐
   │ C │──►│ A │──►│ B │       │ C │──► │ A │──x──│ B │（B 挂了）
   └───┘    └───┘    └───┘     └───┘     └───┘
                                          A 的 200 个线程全部在等 B 超时
                                          A 线程耗尽 → A 也挂
┌───┐──►┌───┐      ┌───┐        ┌───┐──x─┌───┐
│ D │──►│ C │──►  │ A │  ← 等  │ D │──x─│ C │（C 也挂）
└───┘    └───┘      └───┘        └───┘    └───┘  ……整条链路全崩
```

| 雪崩的传导过程 | 原因 |
|--------------|------|
| B 响应变慢（不是挂，是慢） | 数据库连接池打满/GC/下游依赖慢 |
| A 的线程全部阻塞等待 B | **没设超时**，每个请求等默认 30s/60s |
| A 线程池耗尽，新请求排队 | 慢请求占着线程不放 |
| A 自己开始拒绝/超时 | 雪崩从"B 慢"变成"A 挂" |
| 调用 A 的 C 也开始等 A | 故障逐级向上传播 |

> 🎯 雪崩的本质：**慢请求占着资源不放，资源耗尽后再快的请求也进不来**——所以防雪崩的第一动作不是"熔断"，是**超时**（别让一个慢请求无限期占线程）。

## 2. 第一道防线：超时

**通俗**：不等一个注定失败的调用——连接超时 + 读超时都设上，最多等 2 秒，等不到就当它失败。

```java
// HTTP 客户端超时（RestClient 示例）
RestClient.builder()
    .requestFactory(new JdkClientHttpRequestFactory(client -> {
        client.connectTimeout(Duration.ofSeconds(1));    // 连接超时：连不上快速失败
        client.readTimeout(Duration.ofSeconds(3));       // 读超时：等响应最多 3 秒
    }))
    .build();

// 数据库/Redis 超时同理
spring.datasource.hikari.connection-timeout: 3000     # 拿连接最多等 3 秒
spring.data.redis.timeout: 2s                          # Redis 操作最多 2 秒
```

| 超时类型 | 防什么 |
|---------|--------|
| 连接超时 | 防"连不上还傻等"（网络分区、服务宕机） |
| 读超时 | 防"响应慢还一直等"（慢查询、GC、下游堆积） |
| 连接池获取超时 | 防"池打满了还无限排队" |

> ⚠️ 超时设多少？**读超时 ≈ 下游 P99 响应时间 × 2~3**（太短误伤、太长形同虚设）；超时后**必须配兜底**（降级返回值），不能超时了就抛异常——否则只是把"慢"变成"错"。

## 3. 熔断：故障源的断路开关

**通俗**：下游服务故障，直接"断开"，不再继续调用它，防止连锁卡死——保险丝短路就断，不烧坏整个电路。

### 3.1 经典三态状态机

```text
       失败率超阈值（如 50%）
  ┌────────────────────────────┐
  ▼                            │
CLOSED（关闭/正常）          OPEN（打开/熔断）
  │ 所有请求放行                │ 所有请求快速失败（不再调下游）
  │                            │ 等 5 秒
  └──────── 成功多就恢复 ◄──────┤
               │               │
               │         HALF_OPEN（半开）
               │         放行少量试探请求
               └──失败 → 重新熔断；成功 → 恢复关闭
```

| 状态 | 行为 | 触发 |
|------|------|------|
| CLOSED | 正常放行，统计失败率 | — |
| OPEN | **拒绝所有请求**（快速失败/走兜底） | 滑动窗口内失败率超阈值（如最近 6 个请求失败 3 个） |
| HALF_OPEN | 放行少量试探请求 | 熔断等待时间到（如 5 秒） |
| 恢复 | 试探成功 → CLOSED；失败 → OPEN | 试探结果决定 |

```yaml
# Resilience4j 熔断配置（2.4.0，2026 当前线）
resilience4j:
  circuitbreaker:
    instances:
      orderService:
        slidingWindowType: COUNT_BASED        # 窗口：按次数 / TIME_BASED 按时间
        slidingWindowSize: 10                 # 最近 10 次调用统计
        minimumNumberOfCalls: 5               # 最少 5 次才开始算失败率
        failureRateThreshold: 50              # 失败率 ≥50% 熔断
        waitDurationInOpenState: 5s           # OPEN 等 5 秒进半开
        permittedNumberOfCallsInHalfOpenState: 3   # 半开放行 3 个试探
        ignoreExceptions:                     # 业务异常不计入失败（404/409 等）
          - com.example.BusinessException
```

> 💡 Resilience4j 比经典三态更细，共**六态**：CLOSED / OPEN / HALF_OPEN / DISABLED（禁用熔断）/ FORCED_OPEN（强制熔断，人工干预）/ METRICS_ONLY（只统计不熔断）——生产场景常用 DISABLED/METRICS_ONLY 做灰度观察。状态与指标可通过 Actuator 端点（`/actuator/circuitbreakers`）实时查看。

### 3.2 Sentinel 熔断三策略

| 策略 | 触发条件 | 适用 |
|------|---------|------|
| **慢调用比例** | 慢调用（如 >2s）占比超阈值 | 下游变慢（最常见） |
| **异常比例** | 异常占比超阈值 | 下游报错 |
| **异常数** | 异常次数超阈值 | 报错绝对数量大 |

> 🎯 面试必答：**"熔断和超时什么关系？"**——超时是"单次调用"的限制（等多久），熔断是"整体调用"的开关（还调不调）——超时防单个慢请求占线程，熔断防大量无效调用持续打向故障下游；**熔断的前提是超时**（没有超时的调用永远进不了熔断统计，因为它根本不会"失败"）。

### 3.3 熔断 vs 限流（易混点）

| 维度 | 熔断 | 限流 |
|------|------|------|
| 触发原因 | 下游**故障** | 自己**流量超峰** |
| 作用对象 | 特定下游依赖 | 自身入口流量 |
| 恢复机制 | 试探恢复（半开） | 流量降下来自然恢复 |
| 一句话 | 它坏了，我不调它 | 人太多了，我挡一挡 |

## 4. 降级：保核心舍次要

**通俗**：系统压力大，主动关掉非核心功能，保住核心业务——大促高峰期，下单支付必须保，商品推荐、用户头像、历史订单直接返回简化兜底数据。

### 4.1 降级四时机

| 触发时机 | 动作 | 例子 |
|---------|------|------|
| **熔断后** | 被熔断的依赖走兜底 | 推荐服务熔断 → 返回"默认推荐" |
| **超时后** | 等不到就返回兜底 | 库存查询超时 → 显示"充足"（慎用） |
| **主动开关** | 运维手动切降级开关 | 大促前主动关推荐/日志降级 |
| **自动探测** | 资源水位超标自动降级 | CPU/内存/队列积压超阈值 → 自动关非核心 |

### 4.2 兜底返回值的四种姿势

| 兜底策略 | 返回什么 | 适用 |
|---------|---------|------|
| 默认值 | 固定数据（热门商品列表、默认头像） | 推荐、展示类 |
| 缓存数据 | 返回上次成功的数据（可能过期） | 列表、详情（stale-while-error） |
| 空数据 | 返回空列表/空提示 | 非核心模块 |
| 拒绝提示 | 明确返回"功能暂不可用" | 真正非必需的功能 |

```java
// 降级代码范式（Sentinel @SentinelResource + fallback）
@SentinelResource(value = "recommend",
        fallback = "recommendFallback")          // 熔断/限流/异常时走兜底
public List<Product> recommend(Long userId) {
    return recommendService.recommend(userId);   // 可能失败的调用
}

public List<Product> recommendFallback(Long userId, Throwable ex) {
    return List.of(defaultHotProducts());        // 返回默认推荐，核心下单不受影响
}
```

> ⚠️ 降级设计红线：**降级返回的数据要"看起来合理"**——返回空列表比返回 500 好，但显示"库存充足"这种假数据会让用户下单后失败（更要命）。**宁可明确降级（推荐功能暂停），不要降级造假数据（库存永远充足）**。

## 5. 隔离：把故障关进笼子

**通俗**：不同的依赖各用各的线程池/连接，一个依赖把它的池子耗光了，也影响不到别的依赖——分舱的邮轮，一个舱进水不会沉整艘船。

| 隔离方式 | 原理 | 优点 | 缺点 |
|---------|------|------|------|
| **线程池隔离** | 每个下游依赖一个独立线程池 | 隔离彻底，故障依赖占满自己的池，不影响其他 | 线程开销大（每池 10~50 线程） |
| **信号量隔离** | 每依赖限制并发数（不换线程） | 开销小（无线程切换） | 隔离弱（同进程共享线程，故障只影响并发额度） |
| 连接池隔离 | 每依赖/每库独立连接池 | 防连接耗尽 | 配置多 |

> 💡 工具对应：Hystrix 主打线程池隔离；**Sentinel 默认信号量隔离**（省线程开销，阿里压测过 10 万并发场景）；Resilience4j 两种都提供（`Bulkhead` 模块：`ThreadPoolBulkhead` / `SemaphoreBulkhead`）。

## 6. 熔断 vs 降级 vs 隔离（面试对比）

| 维度 | 熔断 | 降级 | 隔离 |
|------|------|------|------|
| 触发 | **被动**（检测到下游故障） | **主动**（压力大/手动开关） | 设计期（提前分舱） |
| 对象 | 对"故障的下游"断开 | 对"非核心功能"关闭 | 对所有依赖分池 |
| 类比 | 保险丝（短路就断） | 大促砍掉推荐位 | 邮轮分舱（进水不沉） |
| 恢复 | 半开试探自动恢复 | 开关关闭即恢复 | 无恢复概念 |
| 关系 | 降级是熔断后的**兜底动作** | 熔断是降级的**触发条件之一** | 隔离是让熔断/降级**更精准**的底座 |

> 🎯 一句话关系：**熔断是"开关"，降级是"开关打开后走哪条路"，隔离是"把每条路建在不同的楼里"**——三者配合：隔离保证故障不扩散（楼不塌），熔断保证不打无效仗（路断了），降级保证用户还有得用（换条路）。

## 7. 防雪崩五件套

| 手段 | 防什么 | 在哪一层 |
|------|--------|---------|
| **① 超时** | 慢请求占线程 | 所有调用 |
| **② 限流** | 超峰流量打崩自己 | 入口（[02 篇](02-流量治理：限流、削峰与背压.md)） |
| **③ 熔断** | 反复打向故障下游 | 依赖调用 |
| **④ 降级** | 故障时给用户兜底 | 业务层 |
| **⑤ 隔离** | 故障不扩散 | 架构层（线程池/连接池/分舱） |

> 🎯 面试必答：**"怎么防止雪崩？"**——五件套分层答：① 调用设超时（连接+读），慢请求不占线程；② 入口限流，超峰流量挡在外面；③ 下游故障熔断，快速失败不走无效调用；④ 熔断/超时后降级，返回兜底数据；⑤ 线程池/信号量隔离，故障依赖不拖垮整体——**超时、限流、熔断、降级、隔离，缺一不可**。加分句：再加**全链路压测 + 故障演练**（Chaos Engineering），让雪崩在测试环境先崩一次。
