## 1. 为什么优先断点而非 console.log

> **背景**：新手用 console.log 输出变量排查；专业开发者用断点——断点提供完整运行时信息且不污染代码。
> **目的**：理解断点调试的优势，建立「断点优先」的习惯。
> **适用范围**：前端 JS/TS 调试；Node.js 后端调试。
> **不适用场景**：线上临时排查（用日志断点/Overrides，见第 4 节）。

```text
console.log vs 断点
├── console.log 的痛点：
│   ① 污染代码（调试完要删）
│   ② 只有输出瞬间的信息（看不到上下文）
│   ③ 改代码要重新部署/刷新
├── 断点的优势：
│   ① 零污染（不修改代码）
│   ② 完整运行时信息（变量/调用栈/作用域）
│   ③ 可控执行（单步跟踪）
└── 金句：console.log 是「猜」、断点是「看」——2026 调试第一原则
```

## 2. 文件导航快捷键

### 2.1 Sources 面板导航

| 快捷键 | 功能 |
|:---:|------|
| `Ctrl+P` | **快速打开文件**（模糊搜索） |
| `Ctrl+P` + `:行号` | 打开文件并跳转行（app.js:120） |
| `Ctrl+Shift+O` | 搜索当前文件的函数/符号 |
| `Ctrl+Shift+F` | 所有脚本全局搜索 |
| `Ctrl+G` | 跳转到行号 |
| `Ctrl+Shift+P` | 命令菜单（Sources 面板） |
| `Ctrl+[` / `]` | 面板切换 |

### 2.2 文件导航实战

```text
定位报错代码（最快路径）
├── ① Console 报错 → 点击报错位置（文件:行号）
├── ② 直接进入 Sources 对应文件对应行
├── ③ 或 Ctrl+P 输入文件名 → 输入 :行号
└── ④ Ctrl+Shift+F 搜索关键字（找不到文件时）

搜索技巧
├── Ctrl+P 支持模糊匹配（app 匹配 App.jsx）
├── Ctrl+Shift+O 找函数（输入函数名片段）
└── 全局搜索（Ctrl+Shift+F）支持正则
```

## 3. 断点控制核心键

### 3.1 断点控制四键（肌肉记忆）

| 快捷键 | 功能 | 说明 |
|:---:|------|------|
| `F8` | **继续执行**（Resume） | 跳到下一个断点 |
| `F10` | **单步跳过**（Step Over） | 执行当前行（不进入函数） |
| `F11` | **单步进入**（Step Into） | 进入函数内部 |
| `Shift+F11` | **单步跳出**（Step Out） | 跳出当前函数 |

### 3.2 断点设置

| 操作 | 快捷键/方式 | 说明 |
|------|:---:|------|
| 切换断点 | `F9` / `Ctrl+B` | 当前行断点开关 |
| 禁用所有断点 | `Ctrl+F8` | 全部停用（保留位置） |
| 运行到某行 | 右键 → Continue to here | 无需断点直达 |
| 断点编辑 | 右键断点 → Edit | 条件断点设置 |

```text
调试三键的使用场景
├── F10 单步跳过：主流程跟踪（函数内部不关心时）
├── F11 单步进入：深入函数内部（看具体逻辑）
├── Shift+F11 跳出：函数看完了快速返回
├── F8 继续：跳过无关代码到下一个断点
└── 组合：先 F10 走主流程 → 关键处 F11 深入 → Shift+F11 返回
```

## 4. 高级断点类型

### 4.1 条件断点（循环调试神器）

```text
条件断点：满足条件才暂停
├── 设置：右键断点 → Edit breakpoint → 输入条件
├── 场景 1：循环第 99 次出错
│   → 断点设在循环内，条件 index === 99
├── 场景 2：特定参数才暂停
│   → 条件 orderId === 'ORD-1001'
├── 场景 3：状态变化才暂停
│   → 条件 this.status === 'FAILED'
└── 收益：避免手动跳过 N 次（或设置后 F8 直达）
```

### 4.2 日志断点（Logpoint）

```text
日志断点：不暂停只打印（线上调试神器）
├── 设置：右键断点 → Add logpoint → 输入表达式
├── 效果：断点处执行 console.log（不中断执行）
├── 场景 1：线上环境加日志（不修改代码！）
├── 场景 2：高频循环打点（暂停会卡死）
└── 场景 3：确认某行是否执行（埋点验证）
→ 对比：普通断点看「状态」、日志断点看「轨迹」
```

### 4.3 其他高级断点

| 断点类型 | 设置方式 | 场景 |
|---------|---------|------|
| **XHR/Fetch 断点** | Sources → XHR/fetch breakpoints → 输入 URL 关键词 | 定位接口请求发起处 |
| **异常断点** | Sources → 暂停图标 → Break on exceptions | 异常自动暂停 |
| **事件断点** | Event Listener Breakpoints → 勾选 click 等 | 定位事件处理 |
| **DOM 断点** | Elements 右键 → Break on | 定位 DOM 修改（02 篇） |
| **数据断点** | 右键变量 → Break on → Property modifications | 定位变量被改 |

```text
异常断点的使用（2026 推荐开启）
├── ① Sources 面板勾选「Break on exceptions」
├── ② 代码抛异常时自动暂停（含未捕获的）
├── ③ 配合 Pause on uncaught exceptions 选项
├── ④ 直接看到异常发生时的调用栈
└── 收益：不用猜哪里抛错——异常即断点
```

## 5. 调试面板使用

### 5.1 调试时看什么

```text
断点暂停后的四个面板
├── ① Watch：监视表达式（右键变量 → Add to watch）
├── ② Call Stack：调用栈（从哪来——先看这个！）
├── ③ Scope：作用域变量（当前可用变量）
├── ④ Breakpoints：所有断点列表（管理/禁用）
└── 使用顺序：先 Call Stack（来源）→ 再 Scope（变量）→ Watch（跟踪）

调试技巧
├── ① 悬停变量查看值（内联显示）
├── ② 右键变量 → Add to watch（持续跟踪）
├── ③ 异步函数：Call Stack 的 Async 标记（定位异步来源）
├── ④ 忽略库代码：右键 → Blackbox script（跳过 node_modules）
└── ⑤ 金句：停在断点先看 Call Stack——「我从哪来」
```

### 5.2 Blackbox / Skip Files

```text
忽略第三方代码（调试聚焦）
├── ① DevTools：右键第三方文件 → Blackbox script
├── ② VS Code：launch.json 配置 skipFiles
├── 效果：F11 单步进入时跳过被忽略文件
├── 收益：调用栈只显示业务代码（不被库代码淹没）
└── 场景：Vue/React 调试——跳过框架内部实现
```

## 6. Node.js 调试

### 6.1 Node 后端调试（与浏览器同套断点）

```bash
# 方式 1：Chrome DevTools 附加
node --inspect-brk app.js        # 启动并等待调试器
# 打开 Chrome → chrome://inspect → 点击 Inspect
# → 获得与浏览器一致的断点体验！

# 方式 2：VS Code 集成（推荐）
# 创建 .vscode/launch.json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "node",
      "request": "launch",
      "name": "Debug App",
      "program": "${workspaceFolder}/app.js",
      "skipFiles": ["<node_internals>/**"]
    }
  ]
}
# 然后 F5 启动调试（断点/变量/调用栈全套）
```

### 6.2 Node 调试注意

```text
Node 调试要点
├── ① --inspect-brk：首行暂停（等调试器连接）
├── ② --inspect：不暂停直接运行
├── ③ 端口默认 9229（--inspect=9230 指定）
├── ④ 生产环境禁用 --inspect（安全风险！）
├── ⑤ VS Code attach 模式：连已运行进程
└── ⑥ 性能分析：node --prof 或 Chrome Memory 面板
```

## 7. 断点调试实战流程

### 7.1 完整流程（键盘流）

```text
JS Bug 断点调试键盘流
┌──────────────────────────────────────────┐
│ ① Ctrl+Shift+J 打开 Console 看报错        │
│ ② 点击报错位置 → Sources 定位             │
│ ③ F9 在可疑行设置断点                     │
│ ④ 右键断点 → Edit → 条件（如需要）        │
│ ⑤ 刷新页面（Ctrl+R）触发断点              │
│ ⑥ F10 单步跳过跟踪主流程                  │
│ ⑦ 关键函数 F11 深入 / Shift+F11 跳出      │
│ ⑧ 看 Call Stack 确认调用来源              │
│ ⑨ Watch 跟踪关键变量变化                  │
│ ⑩ 找到根因 → 修改代码 → Ctrl+R 验证       │
└──────────────────────────────────────────┘
```

### 7.2 常见问题

```text
断点调试常见问题
├── ⚠️ 断点没触发：
│   ① 刷新页面了吗？（F5/Ctrl+R）
│   ② 文件是压缩版？（需要 Source Map）
│   ③ 代码被优化？（生产构建禁用断点）
├── ⚠️ F11 进了第三方库：Blackbox 忽略
├── ⚠️ 异步调试难：异步函数第一行设断点（别 Step Into）
├── ⚠️ 断点管理：Breakpoints 面板统一禁用/删除
└── ⚠️ 改了源码断点位置变了：重新加载（Ctrl+R）
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. **断点优先于 console.log**——零污染 + 完整运行时信息（2026 调试第一原则）
> 2. 调试三键：F8 继续 / F10 单步跳过 / F11 单步进入（+Shift+F11 跳出）——肌肉记忆
> 3. 文件导航：Ctrl+P（+`:行号`）/Ctrl+Shift+O（符号）/Ctrl+Shift+F（全局）
> 4. 高级断点：条件断点（循环 N 次）/日志断点（线上零污染）/XHR 断点/异常断点
> 5. 暂停后先看 **Call Stack**（我从哪来）→ Scope（变量）→ Watch（跟踪）
> 6. Blackbox 忽略第三方代码——调用栈只显示业务代码
> 7. Node.js 调试：--inspect-brk + chrome://inspect 或 VS Code F5（launch.json）
