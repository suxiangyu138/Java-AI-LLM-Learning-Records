## 1. 为什么要异步：线程被慢请求占满

```text
容器默认线程模型（Tomcat 默认 maxThreads=200）：
  请求A ──> 线程1 在等外部 API（2 秒）── 占着
  请求B ──> 线程2 在等数据库（1 秒） ── 占着
  请求C ──> 线程3 在等 MQ（3 秒）    ── 占着
  ...
  第 201 个请求 ──> 排队（acceptCount 满则拒绝/丢弃）
```

| 场景 | 线程占用 | 问题 |
|------|---------|------|
| CPU 密集（计算 50ms） | 短 | 线程很快释放，无需异步 |
| IO 密集（调外部 API/DB 慢查询 2s+） | 长 | 200 线程只能扛 ~100 QPS |
| 长轮询/SSE/WebSocket 握手 | 极长 | 线程被"挂起"不干活 |

> 🎯 **异步的本质**：把"等待 IO 完成"从容器线程里拿出去——容器线程**立即返回**去处理别的请求，等业务线程完成后由容器**恢复**响应。同样的 200 线程，异步模型能扛的并发量高一个数量级。

## 2. Servlet 3.0 异步：AsyncContext

### 2.1 核心流程

```java
@WebServlet(value = "/async/order", asyncSupported = true)   // ⚠️ 必须开启
public class OrderAsyncServlet extends HttpServlet {

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) {
        // 1. 进入异步模式（拿到 AsyncContext）
        AsyncContext async = req.startAsync();
        async.setTimeout(30_000);          // 超时默认 30s，超时触发 AsyncListener.onTimeout

        // 2. 提交业务任务到自己的线程池（不占容器线程）
        executor.execute(() -> {
            try {
                // 长耗时：调支付 API、查库存、发 MQ...
                OrderResult result = orderService.process();

                // 3. 用异步线程写响应
                async.getResponse().setContentType("application/json");
                async.getResponse().getWriter().write(result.toJson());

                // 4. 通知容器：异步处理完成，可以提交响应
                async.complete();
            } catch (Exception e) {
                async.dispatch("/error");   // 出错 → 内部转发到错误页
            }
        });
        // 5. doPost 立即返回 → 容器线程马上被回收去处理下一个请求
    }
}
```

### 2.2 AsyncContext 核心 API

| API | 作用 |
|-----|------|
| `req.startAsync()` / `startAsync(req, resp)` | 进入异步模式（后者可传自定义包装对象） |
| `async.complete()` | **正常结束**：响应可提交 |
| `async.dispatch(path)` | 内部转发到另一资源（相当于异步版 forward） |
| `async.setTimeout(ms)` | 超时时间；<=0 表示永不超时 |
| `async.addListener(AsyncListener)` | 监听 onStart/onComplete/onTimeout/onError |
| `async.start(Runnable)` | 容器提供线程执行（**不推荐**，线程池不受控） |
| `async.getRequest()/getResponse()` | 获取原始 Request/Response |
| `async.getServletContext()` | 异步线程里取 Context（ServletContext 线程安全） |

### 2.3 生命周期状态机

```text
        startAsync()         业务线程                容器线程
请求 ───────────────> [ASYNC_STARTED] ──complete()──> [ASYNC_COMPLETED]
                          │ 超时                          │
                          ├──> onTimeout ──> dispatch/complete 或容器自动处理
                          │ 异常
                          └──> onError
```

| 事件 | 默认容器行为 |
|------|-------------|
| 超时 | 容器自动 complete（响应可能空）；建议 onTimeout 里 dispatch 到错误页 |
| 业务线程抛异常 | 容器记录日志，按未捕获异常处理 |
| 应用退出/容器关闭 | 未完成的异步请求被强制完成或丢弃 |

> ⚠️ **致命坑：异步请求不 complete 就是泄漏**。每个 startAsync 都是一个"挂账"连接，只开不关最终耗尽容器资源。完整闭环 = `complete()` 或 `dispatch()` 二选一，且放在 finally 语义下（配合超时兜底）。

### 2.4 异步下的过滤器

```java
// 异步请求经过 Filter 链时（dispatcherType=ASYNC 也会过链）
public class AsyncFilter implements Filter {
    public void doFilter(req, resp, chain) {
        if (req.isAsyncStarted()) {
            chain.doFilter(req, resp);   // 异步段：链上每个 Filter 都需放行
        } else {
            chain.doFilter(req, resp);
        }
    }
}
// 注册时需加 ASYNC 类型：
// reg.addMappingForUrlPatterns(EnumSet.of(DispatcherType.REQUEST, DispatcherType.ASYNC), true, "/*");
```

> ⚠️ 异步请求的两次 Filter 链（REQUEST 段 + ASYNC 段）是经典坑源：Filter 若只注册 REQUEST，异步阶段不执行；若在 REQUEST 段拦截了请求却没放行 ASYNC 段，异步响应可能"卡死"。

## 3. Servlet 3.1 非阻塞 IO：Listener 机制

异步（AsyncContext）解决**线程占用**；非阻塞 IO（Listener）解决**读写阻塞**——读不完 body、写不完响应时不再阻塞线程。

### 3.1 非阻塞读：ReadListener

```java
@WebServlet(value = "/async/upload", asyncSupported = true)
public class AsyncUploadServlet extends HttpServlet {
    protected void doPost(HttpServletRequest req, HttpServletResponse resp) {
        AsyncContext async = req.startAsync();
        ServletInputStream in = req.getInputStream();
        ByteArrayOutputStream out = new ByteArrayOutputStream();

        in.setReadListener(new ReadListener() {
            @Override
            public void onDataAvailable() {          // 数据到达（可多次）
                try {
                    int len;
                    byte[] buf = new byte[8192];
                    while (in.isReady() && (len = in.read(buf)) != -1) {
                        out.write(buf, 0, len);      // ⚠️ 必须读到 isReady() 返回 false
                    }
                } catch (IOException e) {
                    async.complete();
                }
            }

            @Override
            public void onAllDataRead() {            // 读完了
                try {
                    // 处理 body（此时不阻塞容器线程）
                    async.getResponse().getWriter().write("received " + out.size());
                } catch (IOException e) { /* ... */ }
                async.complete();
            }

            @Override
            public void onError(Throwable t) {       // 出错
                async.complete();
            }
        });
        // doPost 返回，容器线程释放；数据到达时容器用 NIO 事件回调 onDataAvailable
    }
}
```

### 3.2 非阻塞写：WriteListener

```java
ServletOutputStream out = resp.getOutputStream();
out.setWriteListener(new WriteListener() {
    @Override
    public void onWritePossible() {              // 可写时回调
        try {
            while (out.isReady()) {
                out.write(nextChunk());          // 写一块，返回 false 则等下次回调
            }
        } catch (IOException e) { /* ... */ }
    }

    @Override
    public void onError(Throwable t) { /* ... */ }
});
```

| 关键方法 | 语义 |
|---------|------|
| `isReady()` | 是否还能继续读/写（false → 等待事件回调） |
| `onDataAvailable()` | 读方向：有数据了 |
| `onAllDataRead()` | 读方向：body 读完 |
| `onWritePossible()` | 写方向：缓冲区可写了 |
| `onError(t)` | 任一方出错 |

> ⚠️ **事件回调语义**：Listener 回调由容器 NIO 线程触发（不是业务线程）；回调里**不能长时间阻塞**（回调线程被卡住会影响整个容器）。回调里别做同步数据库查询。

## 4. Servlet 6.1 ByteBuffer IO

```java
// 6.1 新增：非阻塞 API 支持 ByteBuffer，告别 byte[] 搬运
ServletInputStream in = req.getInputStream();
ByteBuffer buf = ByteBuffer.allocate(8192);
while (in.isReady()) {
    int n = in.read(buf);      // 直接读入 ByteBuffer（6.1 新 API）
    if (n == -1) break;
    buf.flip();
    process(buf);
    buf.clear();
}

// 写方向同理
ServletOutputStream out = resp.getOutputStream();
out.write(ByteBuffer.wrap(bytes));   // 6.1 新 API
```

> 💡 6.1 之前非阻塞 IO 只能传 `byte[]`（每次分配/回收），ByteBuffer 支持池化与零拷贝链路（直接内存 → socket），高吞吐场景有意义。定位为**体验增强**而非范式革命，旧代码完全兼容。

## 5. Tomcat NIO 连接器线程模型

```text
                    ┌──────────────────┐
   Socket 建立 ──>  │  Acceptor 线程    │ 只做 accept()，接收连接
                    └────────┬─────────┘
                             ▼
                    ┌──────────────────┐
                    读写就绪事件 ──>   │  Poller 线程（Selector）│
                    1~2 个，监听所有连接的 IO 事件
                             ▼ 事件就绪
                    ┌──────────────────┐
                    │   Worker 线程池   │ maxThreads（默认 200）
                    │ 执行 service()   │ 业务代码在这里跑
                    └──────────────────┘
```

| 组件 | 数量 | 职责 |
|------|:---:|------|
| Acceptor | 1（可配多） | accept 新连接，注册到 Selector |
| Poller | 1-2 | Selector 轮询 IO 就绪事件 |
| Worker | 默认 200 | 执行 Servlet service()（业务线程） |
| Blocking 模式 | - | 老模型：每连接一线程（BIO），早废弃 |

> 🎯 **异步与非阻塞的配合**：AsyncContext + ReadListener 后，业务线程**不参与** body 读取与响应写回——读写由 Poller 事件驱动，业务线程只在数据齐了才被唤醒干活。这就是"事件驱动 + 线程池"的完整链路。

## 6. 异步 vs 虚拟线程

```text
传统异步（AsyncContext + Listener）：
  主动让出线程 ──> 状态机复杂（complete/dispatch/超时/事件回调）
  代价：代码割裂、心智负担大

虚拟线程（JDK 21+ / Tomcat 11）：
  线程廉价到"阻塞也不怕" ──> 直接写同步代码
  代价：依赖 JDK 21+，需容器支持（Tomcat 11 内置 VirtualThreadExecutor）
```

| 维度 | 传统异步 | 虚拟线程 |
|------|---------|---------|
| 代码风格 | 回调/状态机，割裂 | **普通同步代码**，零改动 |
| 适用 JDK | 任意 | 21+（Tomcat 11 起） |
| 线程成本 | 复用固定线程池 | 每任务一个廉价线程 |
| 高吞吐 | 靠复用 | 靠数量（百万级） |
| 栈深/调试 | 回调栈难追踪 | 完整调用栈 |
| 适配度 | Servlet 规范原生（3.0+） | 容器特性（Tomcat 11 专属） |

> 🎯 **时代结论（2026-08）**：新项目在 JDK 21+ 上**优先虚拟线程**（同步代码 + 虚拟线程 = 简单且高吞吐）；存量/低版本项目仍用 AsyncContext + 非阻塞 IO。两者不冲突：虚拟线程内部仍可开非阻塞 IO（但收益变小）。相关背景见 [虚拟线程体系](../../../01-底层根基-Java核心底座/02-JUC%20多线程%20高并发编程/虚拟线程/00-虚拟线程知识体系总览.md) 与 [Tomcat](../Tomcat/00-Tomcat总览与核心概念.md)。

## 7. 异步场景决策表与避坑

| 场景 | 需要异步？ | 说明 |
|------|:---:|------|
| 纯计算（<100ms） | ❌ | 直接同步处理，异步反而增加复杂度 |
| 短 DB 查询（<200ms） | ❌ | 线程池足够 |
| 调外部慢 API（1s+） | ✅ | AsyncContext 释放容器线程 |
| SSE / 长轮询 / 大文件流 | ✅ | 连接长期挂起，必须异步 |
| WebSocket | 容器已异步 | 规范自带 |
| 高 QPS + IO 密集 | ✅ | 见上节选虚拟线程或异步 |

| 避坑 | 说明 |
|------|------|
| 忘记 `asyncSupported=true` | 启动不报错，startAsync() 运行时抛 IllegalStateException |
| 不调用 complete/dispatch | 异步请求泄漏，最终耗尽连接 |
| 超时设成永不（<=0） | 配合其他兜底（心跳/最大时长），否则风险无限 |
| 用 `async.start()` | 容器内部 Executor 不受控，高并发可能打满——**用业务自己的线程池** |
| 回调里阻塞 | ReadListener 回调阻塞 → 卡住 Poller 事件循环 |
| 对异步请求注册 Filter 漏 ASYNC 类型 | 异步阶段无 Filter，事务/日志上下文断裂 |
| 异常后不 complete | try-catch 内必须 complete/dispatch 之一 |
