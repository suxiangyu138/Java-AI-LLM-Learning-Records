## 1. 生命周期五阶段

```text
  类加载        实例化         初始化          服务            销毁
 ┌──────┐    ┌────────┐    ┌─────────┐    ┌────────┐    ┌────────┐
 │ Load │───>│ 构造方法 │───>│ init()  │───>│service()│───>│destroy()│
 └──────┘    └────────┘    └─────────┘    └────────┘    └────────┘
   类加载器    首次请求或    恰好 1 次       每个请求      容器关闭/
   加载字节码   load-on-     (容器线程)     N 次          应用卸载
               startup                       (并发)
```

| 阶段 | 触发时机 | 调用次数 | 谁触发 |
|------|---------|:---:|------|
| 类加载 | 容器启动扫描 or 首次请求 | 1 | 类加载器 |
| 实例化（构造方法） | 首次请求 or `load-on-startup` | 1 | 容器（反射） |
| `init()` | 实例化之后立即 | **恰好 1 次** | 容器 |
| `service()` | 每个请求 | N 次（并发） | 容器线程 |
| `destroy()` | 容器关闭/应用卸载 | 1 | 容器 |

> 🎯 记忆口诀：**"一建一始一毁，服务无数"**——构造 1 次、init 1 次、destroy 1 次、service N 次。**init/destroy 是单线程串行**，service 是多线程并发。

```java
@WebServlet("/lifecycle")
public class LifecycleServlet extends HttpServlet {

    // 无参构造：容器通过反射调用，不能由开发者手动 new
    public LifecycleServlet() {
        System.out.println("1. 实例化：" + Thread.currentThread().getName());
    }

    // init(ServletConfig)：必须 super.init(config)，否则 getServletConfig() 返回 null
    @Override
    public void init(ServletConfig config) throws ServletException {
        super.init(config);              // GenericServlet 保存 config 引用
        System.out.println("2. 初始化，加载资源：连接池/配置/预热缓存");
    }

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) {
        System.out.println("3. 服务：" + Thread.currentThread().getName());
    }

    @Override
    public void destroy() {
        System.out.println("4. 销毁：关闭连接池/注销 JMX");
    }
}
```

### 1.1 两个关键设计

| 设计 | 说明 |
|------|------|
| **延迟实例化** | Servlet 默认"首次请求才加载"，减少启动负担（代价：首请求慢） |
| **单例共享** | 一个 Servlet 类只创建一个实例，被所有请求共享——线程安全问题由此而来 |

> 💡 为什么不用"每请求一实例"？CGI 的教训：创建对象成本高，且 Session/Context 全局状态无法共享。Servlet 选择了**实例共享 + 线程隔离**的折中。

## 2. 实例化时机：懒加载 vs load-on-startup

### 2.1 数值语义

| 配置值 | 行为 |
|--------|------|
| 负数 / 不配置 | **懒加载**：首次请求时才实例化 + init（默认） |
| `0` 或正整数 | **启动时加载**：应用启动时实例化 + init，数字越小越早 |
| 相同正整数 | 容器按不确定顺序加载（规范不保证顺序，避免使用相同值） |

```java
// 注解方式
@WebServlet(value = "/warm", loadOnStartup = 1)
public class WarmUpServlet extends HttpServlet { }

// web.xml 方式
<servlet>
    <servlet-name>warm</servlet-name>
    <servlet-class>com.demo.WarmUpServlet</servlet-class>
    <load-on-startup>1</load-on-startup>
</servlet>
```

### 2.2 使用场景

- ✅ 需要**预热**的 Servlet：连接池、缓存、字典加载（首请求不能慢）
- ✅ Spring MVC 的 `DispatcherServlet`（必须尽早初始化，否则首请求去拼凑框架）
- ❌ 普通业务 Servlet：懒加载即可，避免启动拖慢

> ⚠️ 误解澄清：`load-on-startup` **不保证所有 Servlet 都启动时加载**——它只对配置了该属性的生效；且它影响的是"何时初始化"，与映射无关。

## 3. init 重载陷阱与正确姿势

```java
// ❌ 陷阱：覆盖了有参 init(ServletConfig)，忘记 super.init(config)
@Override
public void init(ServletConfig config) {
    // 没有调用 super.init(config)！
    // 后果：getServletConfig() / getInitParameter() 返回 null → NPE
}

// ✅ 推荐：只覆盖无参 init()，由 GenericServlet 帮你保存 config
@Override
public void init() throws ServletException {
    // 安全：GenericServlet.init(ServletConfig) 会先保存 config 再调用本方法
    String encoding = getServletConfig().getInitParameter("encoding");
}
```

> 🎯 **最佳实践**：永远只覆盖无参 `init()`；若必须覆盖有参版本，第一行必须是 `super.init(config)`。这是 JDK 源码 `GenericServlet.init(ServletConfig)` 的设计（保存引用 → 回调无参 init()）。

### 3.1 init 抛异常时

- 抛 `UnavailableException`（永久）：容器直接**放弃该 Servlet**，后续请求 404/503
- 抛普通异常：容器记录日志，Servlet 不可用，但容器继续运行

## 4. service 分发与 doXxx

```java
// HttpServlet.service(req, resp) 的核心分发逻辑（7 个方法分发）
protected void service(HttpServletRequest req, HttpServletResponse resp) {
    String method = req.getMethod();
    switch (method) {
        case "GET"    -> doGet(req, resp);
        case "POST"   -> doPost(req, resp);
        case "PUT"    -> doPut(req, resp);
        case "DELETE" -> doDelete(req, resp);
        case "HEAD"   -> doHead(req, resp);      // 默认走 doGet 并丢弃 body
        case "OPTIONS" -> doOptions(req, resp);  // 返回允许的方法
        case "TRACE"  -> doTrace(req, resp);     // 回显，安全风险建议禁用
        default -> resp.sendError(SC_NOT_IMPLEMENTED);  // 含 PATCH（规范未定义）
    }
}
```

| 陷阱 | 说明 |
|------|------|
| **覆盖 service()** | 分发逻辑整体失效，所有方法都进你的代码——除非做自定义协议，否则别碰 |
| **覆盖 doHead()** | Servlet 6.0 起规范不再要求容器走应用覆盖的 doHead（默认容器实现），头应只返回 header |
| **HEAD/OPTIONS** | 容器默认实现通常够用，业务代码无需处理 |
| **TRACE** | 反射型 XSS 载体，生产建议容器层禁用（Tomcat `allowTrace="false"` 默认） |

## 5. destroy 的边界语义

```java
@Override
public void destroy() {
    // 容器会：
    // 1. 停止向该 Servlet 分发新请求（正在执行的请求继续跑完）
    // 2. 调用本方法（仅一次）
    // 3. 然后才卸载类/回收实例
}
```

| 边界情况 | 行为 |
|---------|------|
| 正在执行的请求 | 容器**不会打断**，destroy 与最后一批 service 可能并发 |
| 容器强制关闭 | destroy 可能不被调用（如 kill -9） |
| destroy 内访问 Session | 规范不保证 Session 仍有效，别在 destroy 里做业务 |
| 热部署 | 旧应用 destroy → 新应用初始化，顺序有保证 |

> ⚠️ **资源释放别放 Servlet 里做**：连接池/线程池应交给容器级管理（如 Spring 容器关闭钩子、[Listener 监听器](../Listener%20监听器/00-Listener监听器总览.md)的 contextDestroyed）。Servlet destroy 只清理**本类私有的临时资源**。

## 6. 单例多线程模型

```text
               ┌─────────────── 容器线程池（默认 200）───────────────┐
               │  Thread-1 ──┐                                     │
 请求1 ──────> │  Thread-2 ──┼──> 同一个 Servlet 实例 ──> service() │
 请求2 ──────> │  Thread-3 ──┘        （单例）          (并发执行)   │
 请求3 ──────> └─────────────────────────────────────────────────┘
```

| 变量位置 | 线程安全 | 原因 |
|---------|:---:|------|
| 局部变量 / 方法参数 | ✅ | 每个线程独立栈帧 |
| `init()` 中初始化且**只读**的成员变量 | ✅ | 初始化完成后不再变化 |
| 可写的成员变量 | ❌ | 所有请求线程共享同一实例 |
| ThreadLocal | ✅（要清理） | 线程级隔离，但线程池复用需 remove() |
| 静态变量 | ❌ | JVM 全局共享，比成员变量更危险 |

```java
@WebServlet("/counter")
public class CounterServlet extends HttpServlet {
    // ❌ 成员变量：多线程共享，i++ 非原子 → 计数错乱
    private int count;

    // ❌ 静态变量：更危险（跨应用）
    private static Map<String, Object> cache = new HashMap<>();

    // ✅ 只读成员：init 里赋值后永不变 → 安全
    private DataSource dataSource;

    // ✅ ThreadLocal：线程隔离（用后必须 remove）
    private static final ThreadLocal<Long> startTime = new ThreadLocal<>();

    @Override
    public void init() {
        dataSource = createDataSource();   // 只写一次，安全
    }

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) {
        startTime.set(System.currentTimeMillis());   // 每线程独立
        // ... 业务
        startTime.remove();                          // ⚠️ 不 remove → 线程池复用泄漏
    }
}
```

## 7. 线程安全铁律与方案对比

| 方案 | 复杂度 | 性能 | 适用场景 |
|------|:---:|:---:|---------|
| **避免可写成员变量**（首选） | 低 | 好 | 默认习惯，无状态 Servlet |
| 局部变量传递 | 低 | 好 | 所有请求内数据 |
| ThreadLocal | 中 | 较好 | 线程级上下文（当前用户/日志 traceId） |
| synchronized / 锁 | 中 | 差 | 确需共享状态时（用 ConcurrentHashMap 兜底） |
| ~~SingleThreadModel~~ | - | - | **Servlet 6.0 已从 API 中移除**（2.4 起废弃） |

> 🎯 **铁律**：Servlet **默认线程不安全**，容器不提供任何同步保障——"无状态 Servlet"是唯一的黄金标准。这与 Spring MVC 单例 Controller 的约束完全一致。

> ⚠️ 关于 `SingleThreadModel`：老教程还在讲"实现它就能串行化"，**这是错的**——它自 Servlet 2.4 起废弃，Servlet 6.0 正式从 API 移除，用它在现代容器里会编译失败。面试答"Serializable 与线程安全无关；SingleThreadModel 已死"就是加分项。

## 8. 虚拟线程下的 Servlet（Tomcat 11）

Tomcat 11 支持 JDK 21+ 的虚拟线程，提供 `VirtualThreadExecutor` 作为连接器线程池实现：

| 维度 | 平台线程（默认 200） | 虚拟线程（JDK 21+） |
|------|------|------|
| 线程成本 | 1MB 栈/线程，200 上限 | 按需创建，百万级 |
| 阻塞语义 | 阻塞占线程 | 阻塞自动让出 carrier 线程 |
| 适用 | 常规 Web | 高并发 + IO 密集（RPC/DB 慢调用） |
| 配置 | `maxThreads` | `tomcat.util.VirtualThreadExecutor` / 配置参数 |

```text
Tomcat 11 启用虚拟线程（server.xml）：
<Executor name="vthreads" className="org.apache.catalina.core.VirtualThreadExecutor"/>

注意：虚拟线程解决的是"线程数量瓶颈"，不解决共享状态竞争——
Servlet 的"无状态"铁律在虚拟线程时代依然成立。
```

> 🎯 关联阅读：Servlet 异步处理（[06-异步处理与非阻塞IO](06-异步处理与非阻塞IO.md)）与虚拟线程是两条互补路线——前者主动释放容器线程，后者把容器线程换成"几乎免费"的虚拟线程；**新项目（JDK 21+）优先虚拟线程，传统项目用异步 + NIO**。

## 9. 容器视角：Tomcat 如何管理生命周期

```text
Tomcat Catalina 组件层级：
Server
 └─ Service
     ├─ Connector（HTTP/NIO，解析请求）
     └─ Engine
         └─ Host
             └─ Context（一个 Web 应用）
                 └─ Wrapper（一个 Servlet）
                     ├─ load()      → 类加载 + 实例化 + init()
                     ├─ allocate()  → 获取实例（单例）
                     ├─ service()   → 调用请求处理
                     └─ unload()    → destroy()
```

| Tomcat 组件 | 对应生命周期环节 |
|------------|-----------------|
| `StandardWrapper.loadServlet()` | 反射实例化 → 构造方法 → init() |
| `Wrapper.allocate()` | 返回单例实例（无 SingleThreadModel 逻辑了） |
| 容器关闭流程 | 先 stop 各 Context（触发 destroy）→ 再停 Connector |
| 热部署 | Context.reload()：旧 Wrapper unload → 新 Wrapper load |

> 💡 面试加分：能说出"Tomcat 的 **StandardWrapper** 负责单个 Servlet 的加载与调度"就体现了源码级理解；配合 [Tomcat](../Tomcat/00-Tomcat总览与核心概念.md) 体系食用更佳。
