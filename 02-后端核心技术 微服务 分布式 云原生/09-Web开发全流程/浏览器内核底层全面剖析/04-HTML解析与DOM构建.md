## 1. 解析器：有状态机 + 错误恢复

HTML 解析器（Blink 的 HTMLParser、Gecko 的 nsHtml5Parser）是**有状态机**：逐字节推进，每个 token 触发状态迁移。它不按 XML 的严格规则工作，而是按 WHATWG 规范的"容错算法"——**遇到错误不报错，而是恢复后继续解析**。

典型容错行为：未闭合的 `<p>` 自动补全、错误嵌套的标签自动调整位置（如 `<b><i>x</b>y</i>` 解析为 `<b><i>x</i></b><i>y</i>`）、`<table>` 内非法内容被移出表格。这是"脏 HTML 也能渲染"的根源，也是为什么 HTML 解析无法像 XML 一样逐行处理——解析器维护一个栈（open elements stack）与插入模式（insertion modes）表，行为由规范精确驱动。

**"解析器构建 DOM"是增量过程**：每解析一个 token 就更新 DOM，而不是等全部文本读完。因此浏览器能边下载边渲染（渐进式渲染），`document.write()` 能中途插入内容——这也是同步脚本能阻塞解析的原因。

## 2. DOM 与 CSSOM 双构建

解析过程中两个树并行构建：

- **DOM**（文档对象模型）：HTML 元素的树形结构，JS 通过它操作页面
- **CSSOM**（CSS 对象模型）：样式表解析结果。关键区别：CSS 规则是**级联依赖**的——后出现的规则可能覆盖先前的，所以 CSSOM 必须等样式表**全部解析完**才能确定最终样式（05 篇展开）

CSSOM 的构建特性决定了两个工程结论：**样式表是渲染阻塞资源**（样式未就绪不能安全绘制，否则会闪变 FOUC）；**CSS 规则顺序影响性能**——选择器匹配是"从右向左"的，`.container .item` 先找 `.item` 再向上验证祖先，深嵌套 + 低效选择器在大型站点上成本可观。

## 3. 阻塞规则：CSS 与同步 JS

解析器遇到什么会停？

| 资源 | 是否阻塞 | 原因 |
|------|:---:|------|
| `<link rel="stylesheet">` | 阻塞渲染（不阻塞解析） | CSSOM 未完成不能安全绘制 |
| 同步 `<script>`（无 async/defer） | 阻塞解析与渲染 | 脚本可能查询 DOM 或 document.write |
| `<script>` 之前的 CSS | 间接阻塞 | 脚本可能读样式（getComputedStyle），必须先等 CSSOM |
| async/defer 脚本 | 不阻塞 | 各自时机执行 |
| 图片/字体 | 不阻塞解析 | 异步加载，字体影响文本绘制但不阻塞 DOM |

**关键链路**：`<script>` 标签前的 CSS 会同时阻塞脚本执行——"CSS 阻塞 JS，JS 阻塞解析"，所以最佳实践是 CSS 放 head（并行下载）、JS 用 async/defer 或放 body 尾部。同步脚本对解析的阻塞 = 浏览器必须完整下载并执行脚本，才能继续构建后面的 DOM——这是首屏速度的第一杀手。

## 4. 预扫描器：解析暂停但下载不停

主解析器被 CSS/同步 JS 阻塞时，**预扫描器（preload scanner）**继续扫描原始 markup，提前发现 `<img>`、`<script>`、`<link>`、`<video>` 并发出下载请求。

这个机制的意义：阻塞期间"解析暂停但下载不停"。没有它，同步脚本后面的所有资源都要等脚本执行完才被发现——首屏资源串行化。现代引擎的预扫描器还会读取 `fetchpriority` 属性并按优先级排序请求。

**工程推论**：`<script>` 放 body 开头会延迟后面所有资源的发现时机（虽然有预扫描器，但 script 标签本身要下载执行）。把阻塞脚本降到最少、资源标签尽量靠前，是配合预扫描器的最优姿势。

## 5. 脚本执行时机：async / defer / module

| 属性 | 下载时机 | 执行时机 | DOM 可用性 |
|------|----------|----------|-----------|
| 同步 | 解析时（阻塞） | 下载完立即 | 执行点之前 |
| `async` | 并行 | 下载完立即（可能乱序） | 不保证 |
| `defer` | 并行 | DOM 解析完成后、DOMContentLoaded 前 | 完整 DOM |
| `type="module"` | 并行 | 类似 defer + 依赖解析 | 完整 DOM |

规则速记：**async 是"下载完就跑"，defer 是"解析完才跑"**。多脚本依赖顺序时用 defer（保序）；独立分析脚本用 async（最快执行）；模块脚本天然 defer 且支持 import 依赖图。执行时机还影响 DOMContentLoaded 的触发：所有 defer 脚本执行完后才触发。

三个容易踩的细节：**async 脚本可能阻塞 DOMContentLoaded**（如果下载慢、在 DOMContentLoaded 前完成）；**动态插入的 `<script src>` 默认是 async 语义**（不保证顺序，依赖链要在代码里用 Promise 编排）；**`<link rel="modulepreload">` 可预加载模块依赖图**，配合 import 图避免深依赖的串行下载。生产页面"脚本全 defer + 关键路径预加载"是最稳的基线组合。

## 6. 编码与解析性能实践

- **字符编码**：`<meta charset>` 必须靠近头部（规范建议前 1024 字节内），否则解析器需先猜编码再回退重解析；服务端 HTTP 头 `Content-Type: charset` 优先级最高
- **`<base>` 与 `document.write()`**：`document.write` 会让预扫描器失效（动态写入内容无法预扫描），现代站点应禁用
- **parse 阶段测速**：Chrome 性能面板的 "Parse HTML" 时长可量化解析成本，海量节点页面（万级 div）解析本身就是瓶颈
- **流式解析**：现代引擎支持流式解析（边下载边构建），服务端不要开启压缩延迟/缓冲 gzip 前等待整个页面生成——TTFB 与首字节解析直接挂钩
- **模板引擎的代价**：服务端渲染（SSR）产出的 HTML 越大解析越慢，但相比客户端 JS 组装 DOM（先下载再逐节点 createElement）仍快一个数量级——解析器的吞吐远高于 JS 操作 DOM 的速度，这是"SSR 首屏更快"的底层原因之一
- **iframe 解析独立**：每个 iframe 有自己的解析器与 DOM 树，但共享同一渲染进程（同源时）——iframe 内长解析会占用共享主线程，拖慢父页面；`loading="lazy"` 可延迟 iframe 解析时机
