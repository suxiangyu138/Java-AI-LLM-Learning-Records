## 1. 为什么必须多进程

单进程浏览器的历史教训明确：一个标签页崩溃 → 整个浏览器崩溃；恶意网页可以直接读写整个进程内存（无沙箱边界）；渲染死循环卡死全部页面。多进程模型同时解决三个问题：

- **崩溃隔离**：渲染进程崩溃只关对应标签页，浏览器与其它标签不受影响
- **安全隔离**：渲染进程运行在沙箱中，即使被攻破也难以触及系统资源
- **性能隔离**：一个页面的长任务不阻塞其它页面的渲染

代价同样明确：每个进程都有独立内存与 IPC 开销，**进程数越多内存占用越高**——这是 Chromium 内存大户的根源，也是 Firefox 选择"平衡"路线的原因。

## 2. Chromium 进程家族

| 进程 | 职责 | 崩溃影响 |
|------|------|----------|
| 浏览器主进程 | UI、导航、进程管理 | 全浏览器 |
| 渲染进程（每标签/每站点） | HTML/CSS/JS、合成器帧生成 | 单标签 |
| GPU/Viz 进程 | 合成聚合、GL/Vulkan/Metal 命令 | 图形重启动 |
| 网络服务进程 | 网络栈、DNS、缓存 | 重新连网 |
| 存储/设备/音频等服务进程 | IndexedDB、设备访问 | 局部 |

一个关键认识：**渲染进程不止一个角色**——每个渲染器内部有主线程（JS/布局/绘制）、合成器线程、光栅线程、IO 线程，渲染进程负责生成"合成器帧"，最终由 Viz 进程聚合成全局帧。GPU 驱动崩溃只重启 Viz，不拖垮浏览器。

## 3. Site Isolation：站点隔离

Site Isolation（2018 起逐步默认）把隔离粒度从"标签页"细化到"站点"：**每个跨源 iframe 拥有独立渲染进程**。

- 安全价值：恶意 iframe 无法通过同进程的共享内存读取父页面数据（Spectre 类侧信道攻击的防线）；`document.domain` 等跨文档访问被真正隔开
- 架构影响：主 frame 与各 iframe 进程各自生成合成器帧，由 Viz 聚合；视觉属性（视口大小、设备缩放）通过同步令牌（sync token）传播，聚合器等待所有 fragment 提交同令牌帧，避免混帧
- 代价：跨域 iframe 数量直接推高进程数与内存；IPC 帧同步增加合成延迟

浏览器里打开 `chrome://process-internals` 可观察隔离实况——一个多 iframe 页面会对应多个渲染进程。

## 4. Mojo：面向服务架构

Chromium 从"单体内嵌组件"重构为 Mojo 面向服务架构（Services）：

- 网络、存储、设备访问、文件系统等拆分为独立服务，运行在独立进程中，通过 Mojo 消息管道（IPC）通信
- 渲染进程不直接访问网络/磁盘，而是**经浏览器进程请求网络服务**——所有网络流量集中经过权限与安全策略检查（CORB、Safe Browsing、证书策略）
- 收益：服务可独立崩溃重启、可跨平台复用（Chromium 嵌入式者只启所需服务）、权限边界清晰

对开发的启示：渲染进程的任何 `fetch()` 都要穿过"缓存判断 → Service Worker → DNS → 建连 → TLS → HTTP 编码"的完整服务链（03 篇展开）。

## 5. Firefox：e10s 与 Fission

Firefox 的多进程路线是"先跑起来再逐步收紧"：

- **e10s（Electrolysis）**：2016 年从单进程转为多进程，默认内容进程上限约 4 个——用"多标签共享渲染进程"换取更低内存占用，代价是标签间隔离弱于 Chromium
- **Fission**：对标 Site Isolation 的站点级隔离，2019 年启动、渐进默认。与 Chromium 不同，Firefox 用**共享内存 + 结构化克隆**做进程间大对象传递（ArrayBuffer、图像数据直接传指针），在 WebGL/WebAssembly 场景比 Chromium 的序列化拷贝更高效
- **独立 GPU 进程**：macOS 上默认启用，WebGPU/WebGL/WebRender 崩溃不再拖垮整个浏览器

选型启示：内存敏感场景（大量标签页的低配设备）Firefox 的共享进程策略有优势，但隔离安全上 Chromium 更激进——这是"资源 vs 安全"的路线分歧。

## 6. WebKit2 与 iOS 特殊性

- **WebKit2**：页面内容运行在独立 WebContent 进程，另有共享 Network 进程等角色，强调能效与系统图形栈整合
- **iOS 特殊性**：WKWebView 内嵌网页与 Safari 渲染行为高度一致（同为 WebKit），iOS 上不存在"换内核"——**开发者必须按 WebKit 行为兼容 iOS**，`backdrop-filter` 软件渲染、WebRTC 编码延迟等差异在 iOS 上无法绕开
- **欧盟例外**：DMA 之后欧盟用户 2026 年可用 Blink 版 Chrome iOS、Gecko 版 Firefox iOS，但仍是独立 SKU，非欧盟 iOS 用户不受影响

## 7. 进程模型的代价与启示

| 模型 | 隔离粒度 | 内存代价 | 崩溃影响面 |
|------|----------|----------|-----------|
| Chromium | 每站点一进程 | 最高 | 最小（单 iframe 崩溃单进程） |
| Firefox | 默认 4 进程 + Fission | 中 | 中 |
| WebKit2 | 每 WebContent 一进程 | 中 | 中 |

对开发者的三条启示：**多进程让"刷新页面"成为万能修复**（渲染进程崩溃后自动重建，行为上像"页面闪一下"）；**iframe 是资源大户**——每跨域 iframe 一个进程，广告联盟一页挂 10 个 iframe 内存立涨；**内存指标要看进程级**——Chrome 任务管理器看每个渲染进程的占用，才能定位"哪个站点在吃内存"。

调试实践中两个常用入口：`chrome://process-internals` 查看 Site Isolation 实况（每个跨域 iframe 对应一个独立渲染进程）；`chrome://service-internals` 查看 Mojo 服务状态。前端排查"某个 iframe 卡住"时，先确认它是不是独立进程——若是，可直接在该进程上单独观察 CPU/内存，不用等主 frame 一起排查。反之，同源 iframe 共享渲染进程意味着一个死循环能拖死整页——这是 Site Isolation 粒度（站点而非 frame）留下的边界。
