## 1. 内核是什么：渲染引擎 + JS 引擎

浏览器内核（browser engine）由两个独立部件构成：

- **渲染引擎**（Rendering Engine，又称排版引擎）：把 HTML/CSS/图片解析、计算、绘制为屏幕像素。负责 DOM、CSSOM、布局、绘制、合成
- **JavaScript 引擎**：执行脚本实现动态行为。V8（Chrome）、SpiderMonkey（Firefox）、JavaScriptCore（Safari）

两者历史上深度耦合，现代已完全独立：V8 可脱离浏览器运行（Node.js、Deno），渲染引擎可换 JS 引擎（WebKit 曾支持 JSC/SpiderMonkey/V8 三种）。因此"内核"一词日常指渲染引擎，但完整的内核能力 = 两者协作——渲染引擎提供 DOM 接口，JS 引擎通过绑定层操作它，绑定层性能（如 IDL 调用开销）直接影响页面速度。

这个区分对开发者有实际意义：**性能问题的归因**——"页面慢"要先分清是渲染问题（布局/绘制/合成）还是 JS 问题（编译/GC/事件循环），两者优化手段完全不同。

## 2. 渲染引擎的六大子系统

| 子系统 | 职责 | 对应本篇 |
|--------|------|----------|
| HTML 解析器 | HTML 文本 → DOM 树 | 04 篇 |
| CSS 解析器 | CSS 文本 → CSSOM | 04/05 篇 |
| 布局引擎 | DOM+CSSOM → 几何位置 | 05 篇 |
| 绘制引擎 | 几何 → 绘图命令 → 像素 | 06 篇 |
| 合成器 | 图层 → 最终帧（GPU） | 07 篇 |
| 网络栈 | 资源获取（HTTP/DNS/TLS） | 03 篇 |

外加存储层（Cookie/localStorage/IndexedDB）与安全层（沙箱/权限/CORB）。这六个子系统各有独立数据结构与调度策略，现代引擎的架构演进（RenderingNG/Stylo/WebRender）基本都是逐个子系统现代化。

## 3. 三大阵营谱系

**Blink（Chrome/Edge/Opera/Brave/Android WebView）**：起源于 1998 年 KDE 的 KHTML → 2001 年被苹果选用改名 WebKit → 2013 年 Google 分叉 WebCore 改名 Blink。激进多进程 + Mojo 服务化，2026 年完成 RenderingNG 现代化。

**Gecko（Firefox）**：1998 年 Netscape 开源，Mozilla 全资维护，三大引擎中唯一非 WebKit 系。通过 Electrolysis（e10s）转向多进程，Fission 实现站点隔离，Stylo（Rust 写的 CSS 引擎）并行化样式计算，WebRender 把绘制交给 GPU。

**WebKit（Safari 与全部 iOS 浏览器）**：Apple 维护，自 WebKit2 起多进程（WebContent 进程 + 共享 Network 进程），强调能效与系统图形栈深度整合。iOS 上 WKWebView 与 Safari 行为一致，Safari 是 iOS 事实上的兼容性基准。

**历史教训**：Blink 与 WebKit 同源，但 10 年分叉积累了可观差异——`backdrop-filter` 在 WebKit 上可能走软件渲染掉帧、多层嵌套 `subgrid` 轨道计算规则不同、`scroll-behavior: smooth` 缓动曲线不同。**"同源"不代表"同行为"**，兼容性测试必须覆盖三引擎。

三家的工程投入方向也能说明哲学差异：Chromium 把资源投在**隔离与安全**（Site Isolation、Mojo 服务化、Viz 独立进程）与**渲染架构现代化**（RenderingNG）；Mozilla 把资源投在**并行与效率**（Stylo 并行样式、WebRender GPU 绘制）与**隐私**（Total Cookie Protection、多态指纹防护）；Apple 把资源投在**能效与系统整合**（Metal、低功耗模式下的节能策略、与 macOS/iOS 图形栈深度绑定）。开发者可以据此预判：同一页面在不同引擎上的瓶颈归属不同——Chromium 可能输在内存、Firefox 可能输在特性覆盖、Safari 可能输在渲染路径选择（如软件回退）。

## 4. 2026 格局与关键动态

- **三大引擎均完成现代化**：Blink（RenderingNG 含 LayoutNG/PaintNG）、Gecko（Stylo + WebRender）、WebKit（Metal）。2026 年"引擎性能差异"的叙事从架构转向实现细节与资源分配策略
- **欧盟 DMA 打破 WebKit 垄断**：2024 年 3 月 DMA 生效，苹果必须在欧盟允许非 WebKit 引擎。2026 年 Chrome iOS 的 Blink 版已向欧盟用户推出（独立 SKU），Firefox iOS 的 Gecko 版 2025 试点、2026 扩大 rollout；**欧盟以外地区不变**，开发者仍须按 WebKit 兼容 iOS
- **单一化风险**：Chromium 在桌面统治地位压倒性。Blink 不实现的功能几乎不算标准（WebKit 的 new 特性常被标准组无视）；Blink 的 CVE 同时影响 Chrome/Edge/Brave/Arc 与整个 Electron 生态——"一个 CVE 打穿半个 Web"
- **Firefox 脆弱性受关注**：全职 Gecko 工程师估计仅剩个位数到低两位数（2010 年代中期数百人），引擎过度依赖 Mozilla 单一组织，且 Mozilla 超 80% 收入来自 Google 搜索合作

## 5. 新兴引擎：Servo 与 Ladybird

- **Servo**：Mozilla 发起的 Rust 实验引擎，放弃后重新活跃。亮点是 Rust 内存安全 + 极致并行（Layout 并行化），WebRender 就是从 Servo 移植到 Firefox 的成果
- **Ladybird**：SerenityOS 项目的浏览器，2026 年接近 alpha。LibWeb + LibJS 全自研，纯社区驱动，无公司背书
- **LibWeb/Flow 等**：更多小型独立实现涌现

它们短期不会改变市场份额，但意义在于：**打破 Blink 单一实现主导标准的局面**——多个独立实现是标准真正"可互操作"的保障，也是 Web 生态对抗单一化的最后防线。

## 6. 五个边界

- **不处理协议语义**：HTTP 状态码语义、缓存头设计属协议层（Web 高阶知识体系），内核只实现
- **不含 Web 框架**：React/Vue 是运行在内核之上的应用层，内核提供 DOM/渲染原语
- **不含 DevTools 业务逻辑**：调试协议是内核接口，工具层独立
- **不做网络服务**：Nginx/服务器是另一端，内核是客户端终点
- **不决定网页设计**：性能优化提供手段，不决定产品策略

另一个常被忽略的边界是**内核的更新节奏**：Blink 约 4 周一版（Chrome 滚动发布），Gecko 约 4 周，WebKit 跟随 Safari 年度大版本 + 系统更新。这意味着 WebKit 的**新特性落地与 iOS 系统版本强绑定**——`backdrop-filter` 这类 2019 年 Chrome 就支持的属性，在 iOS 上直到近两年才稳定，开发者做兼容判断时不能只看"标准里有没有"，要看"目标引擎版本里实没实现"（caniuse 的引擎版本列）。这也是本体系与"标准学习"类资料的分工：标准告诉你"应该怎样"，内核告诉你"实际怎样"。
