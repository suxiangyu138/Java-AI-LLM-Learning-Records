## 1. 关键渲染路径：首屏的时间账

CRP（Critical Rendering Path）是"从 HTML 请求到首次绘制"的必经步骤链：

```
HTML → 解析 → CSSOM → 样式计算 → 布局 → 绘制 → 合成 → 像素
        ↖ 阻塞资源（CSS/同步 JS）在这里排队
```

**时间账的数学**：关键资源（CSS、阻塞 JS）的下载是串行链上的门禁——每个阻塞资源都让后续阶段整体后移。优化 CRP 的三个杠杆：

1. **减少关键资源数**：内联首屏 CSS/JS、按需加载
2. **缩短关键路径长度**：async/defer 解除阻塞、preload 提前发现
3. **降低关键字节数**：压缩、tree-shaking、代码分割

现代引擎的预扫描器（04 篇）已把"发现"提前，但**下载与执行仍是门禁**——CRP 优化的本质是把阻塞资源的体积与数量压到最小。

## 2. Web Vitals 与内核机制的映射

| 指标 | 定义 | 内核环节 | 主要优化 |
|------|------|----------|----------|
| LCP | 最大内容绘制 | 解析 + 图像解码 + 布局 | 预加载 LCP 图、fetchpriority、裁图 |
| INP | 交互到下一帧 | JS + 样式/布局 + 提交 | 长任务切块、防抖动、避免强制同步布局 |
| CLS | 布局偏移 | 布局阶段 | 预留尺寸、contain、避免插入导致重排 |
| TTFB | 首字节 | 网络栈 | 服务端提速、CDN、HTTP/3 |
| FCP | 首次绘制 | 解析 + 首帧绘制 | 减少阻塞资源、内联关键 CSS |

**CLS 的内核解释**：无尺寸图片/广告插入 → 布局重排 → 已绘制像素全部移位。`aspect-ratio` 预留 + `contain` 隔离是内核级解法。LCP 的常见误判：不是"首屏最大元素"的问题，而是"它什么时候被解析+解码+绘制完"的问题——预加载与解码优先级直接决定。

## 3. INP：交互到下一帧

INP 度量"从用户交互到下一帧更新"的延迟，分解为三段：

- **输入延迟**：事件分派前的等待（主线程正忙）
- **处理时间**：事件回调 + 样式/布局/绘制
- **呈现延迟**：提交 → 光栅 → 合成（Commit 耗时是重要信号）

对应内核环节的优化：输入延迟 → 消灭长任务；处理时间 → 防布局抖动、减少重排范围；呈现延迟 → 控制层数、减少光栅负担。**INP < 200ms 的目标要求单次交互的主线程工作 < 50ms**（帧预算）——任何长于 50ms 的回调都直接超预算。

## 4. 长任务与帧预算

帧预算（frame budget）：60Hz 显示下每帧 16.7ms，浏览器渲染工作通常占其中 8-10ms，**留给 JS 的预算只有 ~10ms**。超过即掉帧。

- **长任务（long task）**：主线程连续占用 > 50ms 的任务。每个长任务都至少造成一帧丢失，且阻塞输入（INP）
- **切块（chunking）**：大计算拆成多个 < 50ms 的微任务（`setTimeout(0)`/`scheduler.postTask`/yield），让渲染与输入插队
- **`scheduler.yield()`**（现代 API）：主动让出主线程给渲染——比 setTimeout(0) 更及时
- **Web Worker/OffscreenCanvas**：把计算与绘制移出主线程——主线程只保留 DOM 相关与合成

核心认识：**渲染是分时复用的**——JS 与渲染共享主线程，JS 长时间霸占 = 渲染饥饿 = 掉帧 + INP 劣化。

## 5. 层治理：will-change 与层爆炸

06 篇的机制落地成治理规则：

| 规则 | 原理 |
|------|------|
| will-change 动画前加、结束移除 | 每层 GPU 内存（4K 层 33MB），常驻浪费 |
| 避免防御性 z-index | 堆叠上下文 = effect 节点，每帧随 commit 传递 |
| iframe/video 少叠放 | 硬件内容独立层，叠放引发连锁提升 |
| contain: paint 隔离大子树 | 阻断绘制传播，跳过整棵子树的绘制/布局 |
| 层数 < 50（DevTools 验证） | 层爆炸的量化阈值 |

**判断动画该走哪条路**：transform/opacity → 合成器（不占主线程）；布局属性 → 主线程（必然）；两者混合 → 拆成两层动画或接受主线程成本。不要"为了动画而加层"——先确认动画属性可合成，再加 will-change。

## 6. 调优清单：按成本排序

按"投入产出比"排序的实战清单：

1. **网络层**：HTTP/3 开启、缓存头配好、预加载 LCP 资源（收益最大、成本最低）
2. **阻塞治理**：async/defer 全部脚本、内联关键 CSS、移除 render-blocking 插件
3. **图片**：srcset/AVIF、尺寸匹配、解码优先级（高收益）
4. **JS 层**：长任务切块、防布局抖动、避免强制同步布局（中收益）
5. **布局层**：contain 隔离列表项、避免深层 DOM（中收益）
6. **绘制层**：层数治理、will-change 生命周期、避免大背景重绘（低频率高收益）
7. **GC 层**：热路径不分配、对象形状稳定（对 SPA 长会话显著）

**黄金法则：先测量再优化**——性能面板确认瓶颈在哪个阶段，再选对应清单项，禁止凭感觉乱调。

## 7. 测量方法论

1. **实验室 vs 现场**：Lighthouse（实验室，可复现）+ CrUX/RUM（现场，真实分布）。两者结合，不要只看一个
2. **性能面板四段读法**：Network（下载）→ Performance（主线程时间线）→ Rendering（绘制/合成）→ Memory（内存/GC）
3. **禁用缓存测首屏**：模拟真实用户首次访问；开启缓存测回访
4. **内核差异对比**：同一页面分别在 Chrome/Firefox/Safari 测，先确认是"引擎差异"还是"实现问题"
5. **量化基准**：改前改后各跑 5 次取 P95，避免单次噪声。指标变化 < 5% 视为测量误差
