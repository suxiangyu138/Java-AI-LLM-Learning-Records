## 1. 样式级联：ComputedStyle 的诞生

样式计算（style calculation）把 CSSOM 规则应用到每个元素，产出 ComputedStyle。核心机制：

- **级联（cascade）**：同一属性多个来源按优先级合并——用户代理样式 < 用户样式 < 作者样式；同来源按选择器特异性与出现顺序
- **特异性（specificity）**：内联样式 > ID > 类/属性/伪类 > 元素/伪元素，同特异性后出现者胜
- **继承**：可继承属性（font、color 等）沿树向下传递，无显式值时不重算

现代引擎的优化：Blink 的规则哈希（按选择器分组索引）避免全量规则匹配每个元素；Gecko 的 Stylo 用 Rust 并行计算样式，多核利用率显著高于 Blink 的单线程样式阶段。**样式计算是"每元素 × 每规则"的复杂度**，选择器越简单、规则总量越少，计算越快——这也是 CSS-in-JS 运行时生成大量规则会导致样式计算变慢的原因。

## 2. 布局 vs 重排 vs 回流

| 概念 | 含义 | 触发 |
|------|------|------|
| 布局（layout） | 计算几何：位置 + 大小 + 层级 | 初始布局、DOM 变化 |
| 重排（reflow） | 布局的重新执行 | 尺寸/位置/内容变化 |
| 回流（reflow，同义） | 同上 | 同左 |
| 重绘（repaint） | 已有布局重画像素 | 颜色/背景等不影响几何的变化 |
| 合成（compositing） | 图层重组 | transform/opacity 变化 |

工程上"重排"与"回流"同义（reflow 的两种译法）。**重排比重绘贵**：重排需要重新计算几何并传播给后代（布局是自顶向下、宽度自底向上两趟），重绘只重画像素。触发重排的典型操作：读写 `offsetWidth/getBoundingClientRect` 后修改样式（强制同步布局）、修改内容、窗口 resize。

**布局抖动（layout thrashing）**：循环里"读一个布局属性 → 改一个样式"交替执行，每次读都强制同步刷新布局，性能灾难。修复：先统一读后统一写，或改用 `ResizeObserver` 监听变化。

## 3. LayoutNG：不可变片段树

Chromium 的 LayoutNG 彻底重写了布局架构，核心输出是**不可变片段树（Immutable Fragment Tree）**：

- 每个 fragment 代表 DOM 元素的一部分（打印分页、多列时可分多个），**布局完成后不可变**，不允许"向上引用"
- 数据单向流动（父→子），从而支持**增量布局**：只重新布局变化子树的片段，未变化部分直接复用
- 内联内容用扁平列表表示（对象 + 后代数量元组），配合游标 API（MoveToNext/MoveToNextLine/CursorForChildren）供无障碍树、getClientRects 等消费者高效遍历

对比旧版 Block Layout 的"全树重排 + 可变 Box 树"：LayoutNG 让滚动、动画与布局计算解耦，配合属性树实现 O(1) 属性更新。**"布局结果不可变"是 RenderingNG 一切并行的前提**——只有不可变，才能安全地在不同线程持有布局快照。

## 4. 布局算法的核心逻辑

布局是两趟过程：**自顶向下**确定约束（宽度、包含块、可用空间），**自底向上**确定尺寸（内容撑开的高度）。核心概念：

- **包含块（containing block）**：定位参照系，static/relative 用父内容盒，absolute 用最近定位祖先，fixed 用视口
- **格式化上下文（BFC/IFC/FFC/GFC）**：块级、行内、flex、grid 各自的行盒规则——BFC 决定 margin 合并与浮动包含，flex 的 main/cross 轴计算，grid 的轨道计算
- **行盒模型**：line-height、baseline、inline 元素的垂直对齐，行内内容超宽触发换行与断字
- **断点**：打印/多列布局中 fragment 的分割点

实际面试高频：**BFC 的特性**（内部 margin 不向外合并、浮动被包含、不与浮动重叠）与触发方式（overflow≠visible、display: flow-root/inline-block、position: absolute/fixed、flex/grid 容器）。

## 5. contain：切断级联与布局传播

`contain` 属性是现代布局优化的核心武器：

- `contain: paint`：**隔离边界**——后代不能绘制到容器外，祖先的绘制变化不影响容器内，可跳过大型子树的绘制/布局
- `contain: layout`：隔离布局——容器内部重排不向外传播，创建新的 BFC
- `contain: size`：尺寸已知，跳过内容测量（需固定宽高，否则内容被裁剪）
- `contain: content`（= layout + paint + style）：不设 size 的安全组合

使用场景：卡片列表（每卡片 content contain）、固定尺寸组件（size contain）、大列表虚拟化。注意：`contain: size` 若内容变化会溢出隐藏——尺寸必须自给自足。

## 6. 样式失效与增量更新

样式/布局的失效（invalidation）决定"一次改动重算多少"：

- 旧架构：class 变化 → 全树样式重算 + 全树布局
- 现代：**增量失效**——class 变化只标记对应元素及其后代（按选择器类型传播范围），`contain` 进一步切断传播
- 样式失效不必然触发布局：只有影响几何的属性（width/height/margin/position 等）才进布局阶段，color/background 只触发重绘，transform/opacity 直接进合成

**理解失效范围 = 性能调优的核心**：改 `width` 会传播给兄弟与祖先（布局依赖宽度），改 `transform` 只影响自身合成层。这也是"动 transform 不动 layout"这句铁律的底层原因。

## 7. 布局性能实践

1. **读写分离**：避免布局抖动（读布局属性后立即改样式 = 强制同步布局）
2. **不动布局属性**：动画/高频更新用 transform/opacity 替代 width/left/top
3. **contain 隔离**：列表项加 `contain: content`，固定尺寸组件加 `contain: size`
4. **避免深层 DOM**：布局成本随深度增长，拍平结构 + 合理嵌套
5. **避免强制同步布局的 API**：getBoundingClientRect/offsetWidth/scrollTop 批量读
6. **ResizeObserver 替代 scroll/resize 监听里的同步测量**
