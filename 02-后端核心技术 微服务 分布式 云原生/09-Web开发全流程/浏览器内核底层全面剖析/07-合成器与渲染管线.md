## 1. 渲染管线 12 阶段与调度器

渲染管线由 `cc::Scheduler` 驱动：它把 VSync 对齐的 BeginFrame 消息转换成一个状态机，典型低延迟流程为：

```
BeginImplFrame → BeginMainFrame → Commit → ReadyToActivate
→ Activate → ReadyToDraw → Draw
```

关键设计特性：

- **Commit 边界的流水线化**：主线程释放 commit 互斥锁后立即开始下一帧的 BeginMainFrame，而合成器仍在光栅化/绘制当前帧——管线重叠，不串行
- **高延迟模式**：主线程错过调度器截止时间时，合成器直接绘制现有 active tree 并切换"高延迟"模式，保证至少还有一帧可显示
- **慢光栅化只阻塞激活不阻塞提交**：active tree 全程可绘制，光栅化繁忙时页面仍可交互
- **阶段级跳过**：合成器驱动的滚动和 transform/opacity 动画可完全跳过样式、布局、预绘制、绘制——"每帧做最小有效工作"

## 2. 三棵树：多缓冲模型

合成器维护三棵树实现流水线：

| 树 | 状态 | 角色 |
|----|------|------|
| Main | 主线程状态的镜像 | 每次 Commit 时更新 |
| Pending | 光栅化进行中 | 暂存区，不可绘制 |
| Active | 当前可绘制 | 存活到下一个 pending 树激活 |

**激活（Activation）是原子一步**：光栅化完成后，pending 树整棵切换为 active。滚动与合成器动画在复杂提交处理期间仍流畅，正是因为 active tree 从不被中途修改——这就是多缓冲的价值。

## 3. 属性树：O(1) 更新

每个 Web 文档有四棵独立的属性树：

- **Transform**（变换）：translate/scale/rotate
- **Clip**（裁剪）：裁剪路径与区域
- **Effect**（效果）：opacity、滤镜、混合
- **Scroll**（滚动）：滚动边界、链、溢出方向

对比旧的单一 Layer Tree（更新需遍历整棵树 O(N)）：属性树**按关注点解耦**，每层通过 ID 引用属性树节点，实现 **O(1) 属性更新**——改一个 transform 只更新一个节点，不遍历层树。合成器端动画直接操作属性树节点，在绘制时应用，主线程完全不知情。

## 4. 合成器动画：为什么只有 transform/opacity

合成器线程能独立运行的动画只有 `transform` 和 `opacity` 两个属性，原因是：**它们不影响布局几何，也不改变绘制顺序**——transform 只是绘制时的坐标变换，opacity 只是 alpha 叠加。因此合成器可以用属性树节点直接驱动。

其他属性（width、left、background 等）都要回退主线程动画：主线程每帧重跑样式/布局/绘制，主线程繁忙（长任务、JS 卡顿）就产生 jank。这就是"**动 transform 不动 layout**"的底层原理——不是习惯，是内核架构决定的。

```css
/* 合成器动画：60fps 稳定 */
@keyframes slide {
  to { transform: translateX(100px); }
}
/* 主线程动画：主线程一卡就掉帧 */
@keyframes slideOld {
  to { left: 100px; }
}
```

## 5. 离主线程滚动

滚动树包含合成器所需全部元数据（滚动边界、链、溢出方向），因此**滚动默认完全在主线程之外**：主线程被长任务阻塞 50ms 时，合成器仍可直接更新滚动树的 transform 节点实现平滑滚动。

但有一个致命例外：**页面注册了非 passive 的 wheel/touchmove 监听器**——合成器无法确定监听器是否调用 `preventDefault()`，必须等主线程，jank 重新出现。对策：滚动类监听器全部 `{ passive: true }`，让合成器恢复自主权。这也是 Chrome 默认把 wheel/touchstart/touchmove 监听器强制 passive 的原因。

## 6. Viz 聚合：多进程帧合成

Site Isolation 下每个渲染进程（主 frame + 各跨源 iframe）各自生成合成器帧，最终由 **Viz 进程**的显示合成器线程统一处理：

- **SurfaceAggregator**：把所有渲染器的合成器帧 + 浏览器 UI 聚合成一个全局合成器帧；DrawQuads 按从后到前排序，为遮罩、滤镜、旋转内容设置中间渲染通道
- **DirectRenderer**：Viz GPU 主线程发出实际 GL/Vulkan/Metal 命令
- **同步令牌（sync token）**：视觉属性（设备缩放、视口大小）通过 widget 传播并携带令牌，聚合器等待所有 fragment 提交同令牌帧，避免混合不同视觉属性的帧

Viz 运行在专用进程：**GPU 驱动崩溃不拖垮浏览器**，重启 Viz 即恢复。这也是 02 篇进程模型的价值落点。

## 7. VSync 与掉帧

- 合成器以**显示刷新率对齐**（60/90/120/144 Hz）发射帧，通过 VSync 同步避免撕裂
- 掉帧（jank）的三种来源：主线程长任务（阻塞 BeginMainFrame）、光栅化超时（阻塞激活）、纹理上传延迟（GPU 队列排满）
- **INP 的三段映射**：输入延迟（事件分派）→ 处理时间（JS/样式/布局）→ 呈现延迟（提交/光栅/合成）。Commit 耗时是 INP 的重要信号——Chrome 性能面板的 Rendering 视图可直接观察

排查掉帧顺序：主线程时间线（长任务）→ 合成器线程（光栅/上传）→ GPU（VSync 丢失）。三者独立监控，先分线程再查原因。

DevTools 的三个观察入口：**Rendering → Layer borders** 高亮合成层边界（验证层数治理效果）；**Rendering → Paint flashing** 高亮重绘区域（发现意外全屏重绘）；**Performance 面板的 Frames 视图**直接标注每帧的丢失原因（主线程/合成器/光栅）。实践技巧：怀疑合成问题时先确认元素"是不是独立层"——`translate3d(0,0,0)` 曾是强行提升层的惯用技巧，但在 RenderingNG 时代已无必要且会浪费 GPU 内存，正确姿势是只对真正动画中的元素声明 will-change。
