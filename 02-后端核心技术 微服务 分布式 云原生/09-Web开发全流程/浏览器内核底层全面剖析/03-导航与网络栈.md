## 1. 导航全流程六阶段

一次页面导航在浏览器中被拆分为六个阶段：

1. **URL 解析与安全检查**：确定 scheme/host、搜索意图判定、blocklist 与 Safe Browsing 策略检查
2. **DNS 查询**：域名 → IP。命中浏览器 DNS 缓存则零开销；支持 DNS over HTTPS（DoH）加密查询
3. **建立连接**：HTTP/1.1/2 走 TCP+TLS，HTTP/3 走 QUIC（UDP）。同源已复用连接时此阶段为空
4. **发送请求**：HTTP/2/3 多路复用承载多个资源请求；跨域触发预检条件时先发 OPTIONS
5. **接收响应**：status/headers/body 处理、MIME sniffing、CORB（跨源读取保护）
6. **重定向与提交导航**：最终内容确定后，浏览器进程选择/准备渲染进程开始解析

DevTools 里看 Network 面板：DNS Lookup、Initial connection、SSL 阶段为空，说明这些成本已通过连接复用或预连接提前支付——**导航性能优化的本质是把阶段 2-4 的成本提前**。

## 2. 多层缓存：请求可能根本不出网

请求是否出网，浏览器先做三层本地判断：

```
内存缓存（最快）→ 磁盘缓存 → Service Worker 拦截 → 才真正出网
```

- **强缓存命中**（`Cache-Control: max-age`）：请求根本不触网卡，DevTools 显示 `from disk cache`/`from memory cache`
- **协商缓存**（`ETag`/`Last-Modified`）：仍走一次网络，服务端返回 304，省的是 body 下载
- **Service Worker**：可编程代理，静态资源用 cache-first、API 用 network-first、其余 stale-while-revalidate

工程实践：内容哈希 URL + `max-age=31536000, immutable` 做静态资源激进缓存；HTML 用 `no-cache` + ETag 每次协商；API 短 TTL + `stale-while-revalidate`。CDN 侧配好 `Vary: Accept-Encoding, Accept` 防缓存污染。

## 3. HTTP/2 的遗憾与 HTTP/3/QUIC

HTTP/2 解决 HTTP/1.x 的多路复用，但基于 TCP 有三个无法回避的缺陷：

| 缺陷 | 机制 | 后果 |
|------|------|------|
| 队头阻塞 | TCP 层丢包重传阻塞所有流 | 一个包丢失，页面所有资源等待 |
| 建连延迟 | TCP 握手 + TLS 握手 = 2-3 RTT | 移动弱网下体验显著 |
| 连接迁移难 | TCP 依赖四元组 | 切换 Wi-Fi/蜂窝连接重建 |

HTTP/3 基于 QUIC（UDP 上实现可靠传输）解决全部三个：首次连接 1 RTT、后续 0 RTT；TLS 1.3 内置在传输层；连接 ID 不随 IP 变化，移动切换无缝续连；每个流独立丢包重传，真多路复用。

**部署判断**：服务器响应头带 `Alt-Svc: h3=":443"; ma=86400` 宣告支持 HTTP/3，Chrome 的 `chrome://net-internals/#http2` 可查连接详情。Nginx 侧 `listen 443 quic reuseport` 开启。

## 4. 预加载家族：把等待提前

浏览器在导航阶段主动降低关键路径延迟的机制：

- **预加载扫描器（preload scanner）**：主 HTML 解析器被 CSS/同步 JS 阻塞时，扫描器继续扫原始 markup，提前发现图片/脚本/样式表并发出请求——"解析暂停但下载不停"
- **`<link rel="preload">`**：显式声明当前页需要的资源（如 LCP 图片），比发现时机更早下载
- **`fetchpriority="high"`**：提高关键资源（LCP 元素）的请求优先级
- **Early Hints（HTTP 103）**：服务端在生成主响应期间先发 preconnect/preload 线索
- **Speculation Rules API**：JSON 规则描述可预取/预渲染的 URL，让高概率导航提前完成（Chrome 专属能力）
- **DNS prefetch / preconnect**：提前解析域名、建连，把导航阶段 2-3 的成本前移

## 5. Network Service：集中式网络访问

Chromium 中网络访问全部集中在 Network Service（独立进程或服务）：

```
fetch() → 缓存判断 → Service Worker 拦截 → 域名解析 → 路由决策
        → TCP/QUIC 建连 → TLS 协商 → HTTP 编码 → 分段封装 → 网卡发包
```

渲染进程不直接访问网络，而是经浏览器进程请求网络服务——所有流量集中经过浏览器的权限与安全策略（CORB、证书策略、Safe Browsing）。这也是 Site Isolation 的配套：即使渲染进程被攻破，网络凭据与权限仍受保护。

## 6. 性能指标映射

| 指标 | 目标 | 对应网络阶段 |
|------|------|------|
| TTFB | < 800ms | 阶段 1-5（服务端响应头到达） |
| FCP | < 1.8s | 首次绘制（含解析与渲染） |
| LCP | < 2.5s | 最大内容绘制（图片/文本） |
| INP | < 200ms | 交互响应（渲染管线） |
| CLS | < 0.1 | 布局稳定性 |

网络优化的核心原则：**TTFB 看服务端与连接，LCP 看预加载与优先级，INP/CLS 看渲染管线**——网络栈只能解决前两个，后两个需要 05-09 篇的渲染知识。

几个容易误判的细节：**DNS 是分层缓存**（浏览器缓存 → 系统缓存 → DoH 解析），首访慢但回访几乎零成本，预连接（preconnect）真正省的是 TCP+TLS 握手；**重定向是隐藏的成本**——每次 3xx 都重新走一遍导航阶段，`curl -IL` 检查重定向链，把重定向次数压到 0-1；**Service Worker 注册后首访仍有成本**（SW 文件本身要下载执行），离线收益从第二次访问才开始；**HTTP/3 的 0 RTT 有重放风险**（0-RTT 数据可能被重放），敏感写请求不要依赖 0-RTT。

**连接复用（connection reuse）是最大的隐藏优化**：HTTP/1.1 同源默认 6 个连接、HTTP/2/3 单连接多路复用。同源资源分散到多个域名（域名分片）在 HTTP/1.1 时代能提速，在 HTTP/2+ 时代反而**有害**——分片打破多路复用、增加握手成本，现代实践是"同源聚合"。判断当前协议：DevTools Network 面板看 Protocol 列（h2/h3），低于 h2 优先升级服务器。连接池还受浏览器"空闲超时"管理（约 5 分钟），定时器类轮询请求会把连接保持在活跃期，避免频繁重建。注意同源判定本身也影响复用：跨域请求（CORS）的连接复用只看主机与端口，与 CORS 头无关——只要 host/port 相同就复用，预检（OPTIONS）只发生在需要读响应头的场景。
