## 1. 三引擎架构对比总表

| 维度 | Blink（Chromium） | Gecko（Firefox） | WebKit（Safari） |
|------|------|------|------|
| JS 引擎 | V8 | SpiderMonkey | JavaScriptCore |
| 进程模型 | 每站点一进程 + 服务化 | e10s 4 进程 + Fission | WebKit2 WebContent |
| 样式引擎 | 单线程 + 规则哈希 | Stylo（Rust 并行） | 单线程 |
| 绘制 | PaintNG + 光栅线程 | WebRender（GPU） | Metal |
| 布局 | LayoutNG 片段树 | 块/行布局 + Stylo 配合 | 传统布局 |
| 合成 | cc::Scheduler + Viz | WebRender 合成 | 系统合成 |
| 核心哲学 | 隔离与安全 | 平衡与效率 | 能效与系统整合 |

**差异的实践意义**：CSS 实现细节（subgrid/backdrop-filter/scroll-behavior）、WebRTC 编码延迟（Safari 高 200-400ms）、内存占用（Chromium 最高）、低端设备表现（Firefox 共享进程更省）——性能与兼容性都要按引擎分别验证。

## 2. 兼容性测试：只测 Chrome 等于没测

- **只测 Chrome 覆盖了 Blink 一个引擎**，而桌面还有 Gecko（Firefox）与 WebKit（Safari/macOS），移动端 iOS 全员 WebKit——三引擎缺一不可
- **测试矩阵**：Chrome（Blink+V8）、Firefox（Gecko+SpiderMonkey）、Safari（WebKit+JSC），每引擎至少覆盖桌面与移动视口
- **iOS 特殊性**：欧盟外 iOS 只有 WebKit 行为，`backdrop-filter` 软件渲染、WebRTC 延迟等差异无法绕开，必须单独验收
- **自动化策略**：Playwright/Selenium 三引擎跑回归 + 真实设备 Safari 抽查——自动化覆盖功能、真机覆盖性能与触摸行为

## 3. 未来趋势与演进方向

- **Chromium**：Non-Blocking Commit（快照 Blink 数据实现并行拷贝，移除主线程阻塞，crbug.com/1255972 原型）；Off-Main-Thread Compositing（Layerize 移到工作线程）；Vulkan 多线程命令缓冲
- **Firefox**：Fission 全覆盖、WebRender 继续演进、GPU 进程默认化
- **WebKit**：Metal 现代化、DMA 压力下欧盟分支（Blink/Gecko iOS 版）形成对照测试资源
- **新兴引擎**：Servo（Rust 并行布局）重新活跃、Ladybird（LibWeb+LibJS）接近 alpha——多实现是标准互操作性的保障
- **单一化风险**：Blink 左右标准 + Electron 生态放大 CVE 影响——浏览器多样化是 Web 健康的底线

## 4. 面试三范式

**价值式**：为什么懂内核？——所有前端性能问题的根因都在内核：掉帧是渲染管线的事、卡顿是 JS 引擎与主线程分时的事、首屏慢是 CRP 门禁的事。不懂内核的优化是猜，懂的优化是按机制定位。

**技术式**：核心机制怎么讲？——按"渲染管线 + JS 引擎"两条线：渲染线（导航→解析→布局→绘制→合成，三棵树/属性树/合成器动画/瓦片光栅化），JS 线（四层编译/隐藏类 IC/去优化/分代 GC）。关键数字：帧预算 16.7ms、INP 200ms、层内存 8-33MB、Minor GC <1ms。

**生产式**：你实际解决过什么？——层爆炸治理（will-change 生命周期）、INP 优化（长任务切块 + 防布局抖动）、首屏优化（预加载 + 阻塞治理）、移动端掉帧（瓦片驱逐/纹理上传）。

**追问四连**：为什么只有 transform/opacity 能合成器动画？非 passive 监听器为什么破坏滚动？去优化为什么不可逆？只测 Chrome 为什么危险？

## 5. 简历呈现写法

```text
主导前端性能优化，基于浏览器内核机制定位并解决三类问题
- 通过属性树/合成器分析定位层爆炸，优化 will-change 生命周期，移动端掉帧率下降 40%
- 重构长任务为可中断切块 + 读写分离，INP 从 320ms 降至 140ms
- 落地 CRP 优化（预加载/阻塞治理/HTTP3），LCP 从 3.2s 降至 1.8s
```

要点：用指标量化（INP/LCP/掉帧率）、点名内核机制（属性树/合成器/CRP）、体现"按机制定位"而非"试出来的"。

一个加分写法是附上"排查方法论"：例如"先看 Frames 视图确认掉帧归属主线程还是合成器，再用 Performance 时间线定位长任务与强制同步布局，最后按调优清单落地"——面试官最看重的是**你能复述一套可验证的排查路径**，而不是零散知识点。后端开发者面试本体系时，侧重点可放在：Chromium 多进程与 JVM 内存模型的类比（进程隔离 vs 堆内隔离）、网络栈与服务器端的呼应（HTTP/3 两端视角）、V8 编译管线与 JIT/GC 的通用原理（HotSpot 与 Orinoco 的分代对比）。
