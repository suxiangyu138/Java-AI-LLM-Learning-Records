## 1. Paint：显示列表与 Paint Chunks

绘制阶段（Blink 的 PaintNG）不直接画像素，而是生成**显示列表（display list）**——一组绘图命令序列："画这个矩形、填这个颜色、贴这张图"。关键机制：

- **PaintController 缓存**：显示项按子树缓存，未变化的子树直接复制上次的显示项——"这次只重画变化的部分"
- **Paint Chunks**：显示项按共享的属性树状态（PropertyTreeState）分组。同一 chunk 内的项共享变换/裁剪/效果状态，是下一步图层化的输入单元
- **属性树状态 O(1) 更新**：chunk 通过 ID 引用属性树节点，属性变化（transform 动画）不用重画显示列表，只更新节点值

显示列表是"懒绘制"的：滚动到新区域才生成对应命令。Paint 本身很快，真正的成本在光栅化。

## 2. Layerize：图层化决策

图层化把 Paint Chunks 合并为合成层（layer），目标是**在 GPU 内存与变更成本之间权衡**：

- 默认策略：合并 chunks 成尽量少的层（省内存）
- **不合并**的条件：chunk 的属性树状态预期会在合成器线程变化——合成器滚动区域、transform 动画层、opacity 动画层
- 每个合成层 = 一块 GPU 纹理 + 属性树节点 + 合成器簿记

图层是滚动和动画流畅的基础：**层内的重绘只需重画该层纹理**，层与层独立光栅化、独立上传。但层不是免费的——每层都有 GPU 内存与合成开销，层的目标是"够用"，不是"越多越好"。

## 3. 层提升与层爆炸

哪些元素会被提升为独立层（promotion）：

| 触发条件 | 例子 |
|----------|------|
| 显式声明 | `will-change: transform/opacity` |
| 3D/GPU 变换 | `translate3d`、`transform: perspective` |
| 硬件内容 | `<video>`、加速 canvas、iframe |
| 活动动画 | 正在运行的 transform/opacity 动画 |
| 重叠修正 | 元素压在动画层上方，被迫提升 |

**重叠修正会引发"层爆炸"**：一个动画层出现后，压在它上面的所有元素都被提升，连锁反应成百上千层。合成器的**层挤压（squashing）**机制应对：把仅为重叠原因提升的元素合并进共享后备纹理，但挤压有上限，超出仍会爆炸。

**will-change 的内存账**：全高清层约 8MB、4K 层约 33MB（RGBA 纹理）。建议动画开始前添加、结束后移除，而不是常驻——这是最常见的 will-change 滥用。

## 4. Raster：瓦片光栅化

光栅化把显示列表变成像素（位图），核心是**瓦片化（tiling）**：

- 视口划分为 256×256 或 512×512 的瓦片
- **只光栅化可见和即将可见的瓦片**——滚动时仅移动现有瓦片位置，偶尔为新内容光栅化新瓦片
- 内存压力时瓦片被驱逐，滚动出现**棋盘格（checkerboarding）**——低内存设备的典型卡顿信号

光栅化在渲染进程的光栅线程执行，结果上传为 GPU 纹理。**纹理上传延迟**在带宽受限的移动设备上会导致掉帧——这是移动端"滚动卡"的常见根因之一。

## 5. 图像解码：最贵的光栅子步骤

光栅一个含图片的瓦片时，**图像解码是成本最高的子步骤**（解码 JPEG/PNG/WebP/AVIF 到像素）——比几何绘制贵一个数量级。

- 解码在**专用解码线程**运行，不阻塞主线程
- 软/GPU 路径各有独立缓存；解码结果缓存命中则跳过
- **image-rendering 与尺寸**：解码大图（原图 4000px）但显示小尺寸（200px），解码浪费显著——服务端按需裁图 + `srcset` 是标准解法

现代格式选择：AVIF/WebP 解码成本高于 JPEG 但体积小得多（省带宽），低端设备上要权衡"下载省 vs 解码贵"。

另一个高频场景是**背景图与滚动**：固定背景（`background-attachment: fixed`）在部分引擎上每帧重绘整个背景层，移动端掉帧重灾区——`fixed` 背景建议换成 `transform: translateZ(0)` 分层或干脆去掉固定效果。大面积的渐变背景同理：渐变是逐像素计算的，大面积渐变的光栅成本远高于纯色，用图片或分层规避。

## 6. GPU 与 CPU 光栅路径

三种缓冲区提供者对应三条路径：

| 路径 | 机制 | 适用 |
|------|------|------|
| ZeroCopy | 直接 GPU 内存，零拷贝 | 桌面 GPU |
| OneCopy | CPU 绘制后上传 | 混合场景 |
| GpuRaster | GPU 命令缓冲直接光栅 | 高负载桌面 |

GPU 光栅因 GPU 上下文锁而**单线程化**——这是新版代码路径采用 Vulkan 的动机之一（Vulkan 多线程命令缓冲）。绘制最终由合成器帧（compositor frame）承载：描述如何拼接光栅化内容并用 GPU 高效绘制（surface、render surface、GPU 纹理瓦片、Quad 描述纹理输入与变换）。

## 7. 绘制性能实践

1. **控制层数**：Layers 面板数层（DevTools → Rendering → Layer borders），正常页面 < 50 层，数百层即爆炸
2. **will-change 生命周期**：动画开始前加、结束移除
3. **避免不必要的堆叠上下文**：防御性 `z-index: 1` 添加 effect 节点，每帧随 commit 传递
4. **图片尺寸匹配**：srcset 裁图，避免大图小显
5. **contain: paint**：隔离绘制边界，祖先变化不触发大子树重绘
6. **视频/iframe 独立层**：硬件内容天然成层，叠放其上会连锁提升
