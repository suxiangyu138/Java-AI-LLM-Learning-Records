## 3. 学习路线推荐

**路线一：快速上手（1-2 天）**——01 → 02 → 03 → 04 → 10。目标：能设计并实现一个规范的后端 REST API。

**路线二：工程规范（3-5 天）**——路线一 + 05 → 06 → 07。目标：幂等键、版本化、分页、统一格式全套落地。

**路线三：契约与生产（一周）**——路线二 + 08 → 09。目标：Spec-first 工作流 + CI 契约测试 + 安全限流，可交付生产级 API。

**先厘清分工**：本体系是「后端设计深潜版」——资源模型、幂等、版本化、契约工程的完整决策逻辑；前端视角的速查版见 [[../10-前端知识拓展/RESTful%20接口设计、统一返回格式/00-RESTful接口设计知识体系总览|RESTful 接口设计与统一返回格式体系]]（URL 规范、状态码选择、分页的五篇速查）。HTTP 协议基础见 [[../Web%20高阶知识/00-Web高阶知识总览|Web 高阶知识体系]]（REST 语义与状态码的协议层背景）；Spring 实现层见 [[../SpringBoot%20Web/00-SpringBootWeb总览|SpringBoot Web 体系]]（Controller 与拦截器）。

## 4. 核心概念速查

| 概念 | 一句话 |
|------|-------|
| 资源 | API 的操作对象（订单/用户），URL 表达的是资源不是动作 |
| 集合/元素 | `/orders`（集合）与 `/orders/123`（元素）两级模型 |
| 幂等 | 同一请求执行多次结果一致（GET/PUT/DELETE 天然幂等） |
| Idempotency-Key | 请求头幂等键——2026 标志实践，重试安全网 |
| RFC 9457 | 错误响应标准格式（type/title/status/detail/instance） |
| 409 Conflict | 资源状态冲突（库存不足、版本冲突） |
| 422 语义错误 | 请求体合法但语义不通过（业务校验失败） |
| URL 版本化 | `/v1/orders`——2026 推荐版本策略 |
| Sunset 头 | 通知客户端版本即将下线的响应头 |
| cursor 分页 | 游标分页——大数据集稳定分页 |
| OpenAPI 3.1 | API 契约标准（文档 + 生成 + 测试的源头） |
| Spec-first | 先写契约再写代码的工程工作流 |
| oasdiff | OpenAPI 破坏性变更检测工具 |
| HATEOAS | 响应中带链接的演进风格（多数项目不采用） |

## 5. 常见误区

**误区一：URL 里写动词**。`/getUsers`、`/createOrder` 是 RPC 不是 REST——资源名词 + HTTP 方法表达动作。

**误区二：所有请求都返回 200**。业务失败也 200 + 业务码——状态码是协议语义，200 表示成功；错误该用 4xx/5xx。

**误区三：POST 重试不安全**。2026 年这是不可接受的——幂等键让 POST 也可安全重试（AI agent 与弱网移动端的刚需）。

**误区四：400 通吃客户端错误**。400 语法错误、422 语义错误、409 状态冲突——细分状态码让客户端能编程处理。

**误区五：错误信息裸奔**。堆栈、SQL、内部路径进错误响应——安全红线，生产只给通用 500。

**误区六：上线了才想版本化**。没有 /v1 的 API 一旦被消费就改不了——从第一天就版本化。

**误区七：先写代码后写文档**。文档补写总是滞后失真——Spec-first，契约先行，文档是产物不是事后工作。

**误区八：分页只有 offset**。大数据集 offset 分页会退化（深翻页）——cursor 分页该上就上。

**误区九：契约是文档不是工程**。OpenAPI 写了就完事——契约是自动化源头（Mock/SDK/测试/破坏性检测），不进 CI 的契约等于没写。

**误区十：错误信息越详细越好**。堆栈、SQL 原文进错误响应——信息泄露——生产只给通用 500，细节进日志。

九个误区的共同根源只有一个：**把 API 设计当成「写接口」而不是「定契约」**。RESTful 的本质是把「接口长什么样」变成显式的、可评审的、机器可读的契约——URL 是资源地图、方法是操作语义、状态码是结果语言、OpenAPI 是契约载体、幂等键是重试安全网。带着「写接口」的心态，命名、错误、版本、幂等这些环节必然漏；换成「定契约」的心智——先契约后代码、先评审后合入、先检测后发布——整个体系的每一篇都有了落点。

**学习姿态的约定**：API 设计的每个决策都要「设计 + 验证」——资源模型画完资源图再写端点清单；状态码选完写个最小 Controller 验证行为；幂等键实现后并发打两发验证只执行一次；契约写完用 Swagger UI 实际调一遍。本体系代码以 Java/Spring 为主（后端视角），前端配合见 [[../10-前端知识拓展/RESTful%20接口设计、统一返回格式/00-RESTful接口设计知识体系总览|前端速查版]]——前后对照补全代码面；实现细节对照 [[../SpringBoot%20Web/00-SpringBootWeb总览|SpringBoot Web 体系]]。
