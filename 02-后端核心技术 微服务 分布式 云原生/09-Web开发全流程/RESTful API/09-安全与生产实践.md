## 1. 认证与授权

API 安全的两个层次，缺一不可（[[../10-前端知识拓展/Token/00-Token总览|Token 体系]] 的完整鉴权方案）：**认证（你是谁）**——2026 三种形态按场景选：**OAuth 2.1 + OIDC**（用户型应用，授权码 + PKCE——社交登录与 SSO 的标准）；**JWT Bearer**（API 间无状态认证——短 TTL + 轮换）；**API Key**（服务间简单认证——必须支持轮换、只走 HTTPS、放 header 不放 URL）。**授权（你能做什么）**——角色/权限模型 + **对象级授权（BOLA 是 API 安全头号漏洞）**——每个资源访问校验归属（用户 A 的 token 访问 `/orders/123` 时校验 123 属于 A——04 篇 403 与 [[../10-前端知识拓展/Token/09-安全红线与攻防|Token 攻防]] 的越权治理）。

**API 安全的三条铁律**：**HTTPS 全覆盖**（无 HTTP 明文端点——TLS 终止在网关或 LB，[[../Web%20高阶知识/03-HTTPS与TLS深入|TLS 体系]]）；**认证中间件统一**（网关或框架层统一验签——不信任单个 Controller 自己验）；**错误响应不泄露内部**（04 篇红线——堆栈/SQL/内部路径绝不出网）。

## 2. 限流：三头协议

限流（Rate Limiting）是 API 生产的第一道闸——防滥用、防抓取、防雪崩。**2026 的三头协议**（客户端可编程处理）：

```text
响应头（限流命中或每响应携带）：
X-RateLimit-Limit: 100         每窗口上限
X-RateLimit-Remaining: 87      剩余额度
X-RateLimit-Reset: 1723456789  窗口重置时间
429 响应带：Retry-After: 30    请 X 秒后重试
```

**限流算法**：令牌桶（允许突发、平滑速率——推荐）、滑动窗口（精确计数）、固定窗口（简单但边界突刺）。**限流维度**：按 IP（基础）、按用户/API Key（业务）、按端点（敏感接口单独配额）——三层叠加。**限流策略的工程实现**：Redis 计数（`INCR + EXPIRE` 固定窗口，或 Lua 脚本滑动窗口）；网关层限流（Nginx/网关组件——集中治理，[[../07-工程运维基础/运维/Nginx%20基础|Nginx 体系]] 的 limit_req）。

**429 的客户端语义**：客户端收到 429 必须退避（`Retry-After` 优先），指数退避 + 抖动，**429 不算 5xx**（是「你太快了」不是「我坏了」）。**限流与幂等键的配合**：限流按键维度（Idempotency-Key 不计入配额或单独配额——重试不该被限流误伤，05 篇）。

## 3. 敏感数据治理

API 是敏感数据的出口——治理三个方向：

**响应裁剪**：**不泄露数据库 schema**（内部字段 `internal_remark`、外键 ID、审计字段不进响应——DTO 层裁剪，不直接返回实体）；**不返回多余敏感字段**（身份证、手机号按需返回——列表接口脱敏 `138****1234`，详情接口按权限）；**密码/令牌永不出网**（数据库里的密码哈希在响应中不存在——哈希都不给）。

**请求防护**：**输入校验是安全层**（注入攻击：SQL 注入走参数化、XSS 走转义——[[../Web%20高阶知识/07-Web安全攻防|Web 安全]] 体系；超长输入限制——防 DoS）；**上传文件类型与大小校验**；**ID 枚举防护**（对外 UUID，04 篇 404 语义配合）。**日志脱敏**——请求日志里的密码、Token、身份证要脱敏（04 篇错误红线 + 下节日志）。

**数据分级**：给字段分级（公开/内部/敏感）——**敏感字段的接口设计**：单独端点 + 权限校验 + 审计日志（「谁看了手机号」要可查）——**「敏感数据可审计」是生产 API 的底线**。

## 4. 日志与可观测

API 的可观测三支柱（日志/指标/追踪——[[../07-工程运维基础/运维/日志监控指标|日志监控体系]] 的 API 侧落地）：

**访问日志**：每条请求——方法、路径（**脱敏后的**——查询参数里可能有敏感值）、状态码、耗时、用户 ID、trace id——**trace id 贯穿请求全链路**（响应头 `X-Request-Id` 返回给客户端——客户端报障时报 trace id，服务端按 id 查日志——「客户端报障可定位」是生产基本盘）；**错误日志**：堆栈只进日志不进响应（04 篇）、按错误码聚合；**业务审计**：敏感操作（删除、导出、权限变更）记录「谁、何时、做了什么」——独立审计存储。

**指标**：QPS、P50/P95/P99 延迟、错误率（按状态码族）、限流命中数——监控告警的输入；**告警阈值**：P99 超基线、5xx 率超 1%、429 激增（限流命中剧增可能是攻击）。**日志与契约的配合**：错误码进日志（按错误码聚合失败原因——04 篇错误码设计的可观测价值）。

## 5. 性能基线

API 性能的三层基线，逐层治理：

**第一层：响应时间**——P99 目标（内部 API 200ms、对外 API 500ms 是常见基线）——慢接口定位：数据库查询（最常因——N+1、缺索引）、外部调用（加超时与降级）、序列化（大响应体）。**第二层：缓存**——GET 接口的 `Cache-Control`（浏览器/CDN 缓存——[[../Web%20高阶知识/02-HTTP缓存体系|HTTP 缓存]]）、服务端缓存（热点数据 Redis）、数据库查询缓存（谨慎）；**第三层：批量与分页**——列表必分页（07 篇）、批量操作批量接口（N+1 次调用的客户端行为 → 服务端批量端点）、响应体精简（fields 参数）。

**压测纪律**：上线前压测（变并发梯度找拐点——[[../07-工程运维基础/运维/MySQL%20Redis%20MQ%20运维相关故障现象|中间件运维]] 的方法论）；**性能问题的排查顺序**：慢接口 → 看 trace（哪一段耗时）→ 数据库 EXPLAIN → 缓存命中率 → 代码热点——**先测量后优化，无基准不优化**。

## 6. 生产检查清单

- [ ] HTTPS 全覆盖（无明文端点）
- [ ] 认证统一（网关/框架层） + 授权（含对象级 BOLA 校验）
- [ ] 限流三头（Limit/Remaining/Reset + Retry-After）
- [ ] 错误统一 RFC 9457，无堆栈/SQL 泄露
- [ ] 敏感字段裁剪与脱敏、日志脱敏、审计可查
- [ ] 输入校验（注入/超长/上传限制）、对外 UUID 防枚举
- [ ] trace id 贯穿 + 访问日志 + 错误聚合
- [ ] 指标监控（QPS/P99/错误率/429） + 告警
- [ ] 幂等键（写操作强制） + 版本化（/v1/ + Sunset）
- [ ] OpenAPI 契约在 CI（lint + oasdiff + 契约测试）

## 7. 常见坑

**坑一：限流只有 IP 维度**。抓取方换 IP 绕过——用户/Key 维度跟上。

**坑二：429 不带 Retry-After**。客户端瞎等——三头 + Retry-After。

**坑三：日志打完整参数**。查询参数里的手机号进日志——脱敏。

**坑四：错误码不进日志聚合**。失败原因查不到——错误码与日志联动。

**坑五：DTO 直接返回实体**。数据库字段全暴露——裁剪层。

**坑六：无压测上线**。拐点未知——上线即事故——压测留余量（生产配额 = 拐点的一半）。

**坑七：BOLA 不测**。越权用例缺失——「A 的 token 访问 B 的资源必须 403」进测试。
