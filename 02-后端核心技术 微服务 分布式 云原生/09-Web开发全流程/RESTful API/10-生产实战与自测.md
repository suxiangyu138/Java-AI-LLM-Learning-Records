## 1. 实战：订单 API 全流程

把全体系知识点压进一个项目：设计订单资源 → 写契约 → 实现（错误处理 + 幂等）→ 测试验收。

**第一步，契约（OpenAPI 摘要——完整契约是 08 篇的产物）**：

```yaml
paths:
  /v1/orders:
    post:
      description: 创建订单（幂等：Idempotency-Key 必填）
      parameters:
        - name: Idempotency-Key
          in: header
          required: true
          schema: { type: string, format: uuid }
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/CreateOrder' }
      responses:
        '201':
          description: 创建成功
          headers: { Location: { schema: { type: string } } }
          content: { application/json: { schema: { $ref: '#/components/schemas/Order' } } }
        '409': { description: 库存不足/状态冲突 }
        '422': { description: 字段校验失败 }
        '429': { description: 限流 }
  /v1/orders/{id}:
    get:
      responses:
        '200': { content: { application/json: { schema: { $ref: '#/components/schemas/Order' } } } }
        '404': { description: 不存在 }
```

**第二步，实现（Java/Spring 视角的核心要点）**：

```java
@PostMapping("/v1/orders")
public ResponseEntity<Order> create(@Valid @RequestBody CreateOrder dto,
                                    @RequestHeader("Idempotency-Key") String key) {
    // 幂等键查重（05 篇）→ 业务创建 → 201 + Location
    Order order = orderService.createWithIdempotency(dto, key);
    return ResponseEntity.created(URI.create("/v1/orders/" + order.getId())).body(order);
}

@GetMapping("/v1/orders/{id}")
public Order get(@PathVariable String id) {
    return orderService.get(id);        // 不存在抛 404（全局异常处理映射）
}

// 全局异常处理（04 篇——RFC 9457 统一出口）
@RestControllerAdvice
class ApiExceptionHandler {
    @ExceptionHandler(ValidationException.class)
    ProblemDetail handleValidation(ValidationException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, e.getMessage());
    }
}
```

**第三步，验收五连**：**契约对吗**——curl 按契约文档调每个端点，响应与契约一致；**错误对吗**——非法 JSON 400、校验失败 422（字段级 errors[]）、不存在 404、重复键回放原响应；**幂等对吗**——同键两次 POST 只创建一条，第二次返回第一次的响应；**限流对吗**——连打 101 次返回 429 + Retry-After；**安全对吗**——错误响应无堆栈、日志无敏感字段、A 用户 token 访问 B 的订单 403。

## 2. 生产配置模板与纪律清单

**资源**：名词复数 + kebab-case + 嵌套 ≤2 层；**方法**：矩阵语义（POST 201+Location、DELETE 204）；**错误**：RFC 9457 统一 + 字段级 errors[] + 错误码进 OpenAPI；**幂等**：写操作强制 Idempotency-Key（Redis NX + TTL 24h，成功失败都存）；**版本**：/v1/ 从第一天 + Sunset 头 + 90 天弃用期；**分页**：小数据 offset / 大数据 cursor，page_size 上限 100；**契约**：Spec-first + CI 四道闸（lint/oasdiff/契约测试）；**安全**：HTTPS + 统一认证 + BOLA 对象级校验 + 限流三头 + 日志脱敏 + trace id；**性能**：P99 基线 + 压测拐点留 50% 余量。

## 3. 报错速查十条

| 现象 | 原因 | 处理 |
|------|------|------|
| 非法 JSON 返回 500 | 反序列化异常未映射 | 全局异常处理 → 400 |
| 校验失败返回 400 | 未用 422 语义 | 区分语法/语义错误 |
| POST 重复创建 | 无幂等键 | 强制 Idempotency-Key |
| 同键重试仍执行 | 键未查重/锁失效 | Redis NX 原子性检查 |
| 客户端收到堆栈 | 异常未兜底 | 全局 500 处理 |
| 404 全部返回 | 无权限也 404 | 防枚举（有意）或区分 |
| 分页深翻页变慢 | offset 深偏移 | cursor 分页 |
| 契约与实现不符 | 无契约测试 | Dredd 进 CI |
| 429 客户端疯狂重试 | 无 Retry-After | 三头 + Retry-After |
| 字段改了客户端崩 | 破坏性变更未走流程 | oasdiff + 版本化 |
| 限流误伤幂等重试 | 重试请求被限流拦 | 幂等键单独配额 |
| 契约测试只在本地 | CI 不跑契约 | 契约测试进流水线 |

## 4. 面试三范式

**价值式**：「我设计的订单 API——幂等键让 AI agent 与弱网客户端安全重试，重复下单事故归零；RFC 9457 错误格式让前端一次解析全端点通用；Spec-first 工作流让契约评审进 PR，文档永远与实现一致。」——先讲事故率与工程收益，再讲手段。

**技术式**：「REST 的本质是资源化——URL 说是什么、方法说做什么、状态码说结果如何；PUT 幂等替换、PATCH 局部修改；幂等键 = 操作唯一标识，服务端按键存结果、重复回放；RFC 9457 的 type 是错误分类主键，客户端按 type 分支。」——原理到「为什么」，别停在「规范是这么写的」。

**生产式**：「从第一天版本化（/v1/ + Sunset 头 + 弃用期）；CI 四道闸（lint/oasdiff/契约测试）；BOLA 是头号漏洞（对象级授权独立设计）；限流三头 + Retry-After；trace id 贯穿让客户端报障可定位。」——版本、契约、授权、可观测四点是区分度。

**追问四连**：PUT 与 PATCH 的幂等差异？（整体替换天然幂等，局部修改视实现——用赋值不用运算）｜幂等键怎么实现？（Redis NX 锁 + 存结果回放，成功失败都存）｜破坏性变更怎么识别？（oasdiff 自动化 + 移除/改类型/改语义清单）｜400/422/409 怎么分？（语法/语义/状态）。
