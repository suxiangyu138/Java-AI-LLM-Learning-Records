# 04-状态码与错误处理
> 定位：状态码是「结果如何」的协议语言，错误格式是「为什么失败」的机器可读答案——2026 年的标准是 RFC 9457 Problem Details + 字段级校验错误数组，让客户端不用解析散文就能编程处理。

## 1. 状态码家族

状态码是「协议语义」不是「业务码」——它的职责是让客户端与中间件（网关、监控）无业务知识也能判断结果：

**2xx 成功**——200（GET/PUT/PATCH 成功）、201（POST 创建成功 + Location 头）、204（删除成功/无内容）。**4xx 客户端错误**——400（请求语法错误/非法 JSON）、401（未认证）、403（无权限）、404（资源不存在）、405（方法不允许）、409（状态冲突）、422（语义校验失败）、429（限流）。**5xx 服务端错误**——500（未预期）、502（网关上游错误）、503（服务不可用/维护）、504（网关超时）。

**使用纪律**：**状态码表达「结果类别」，错误码表达「具体原因」**——客户端按状态码分支（401 去登录、429 退避重试、5xx 稍后重试），按错误码细化处理（下节）；**不自定义 4xx/5xx 语义**（如用 400 表示「用户不存在」）——协议语义被打破，客户端无法通用处理。

## 2. 选择决策：4xx 细分

4xx 是错误处理的主战场，选错码客户端就无法编程处理：

**400 Bad Request**——请求「语法」问题：非法 JSON、参数类型错误、必填字段缺失（结构层面）。**422 Unprocessable Entity**——请求体「合法但语义不通过」：用户名已存在、年龄小于 18、邮箱格式错（业务校验层面）。**409 Conflict**——资源「当前状态」不允许该操作：已审核的订单不能改、库存不足、版本冲突（乐观锁）——**409 与 422 的分界：422 是「值不对」，409 是「状态不对」**。

**401 vs 403**——401 未认证（没登录/令牌过期——客户端该去刷新/登录），403 已认证但无权限（授权失败——重试无用）；**混淆的后果**：客户端把 403 当 401 会无限重登。**404 的信息边界**——「资源不存在」与「无权限查看」都返回 404（防资源枚举）是安全实践（09 篇）；**405**——方法不允许（资源存在但该方法未实现——`GET /orders/123` 没实现返回 405 + Allow 头）。

## 3. RFC 9457 错误格式

**RFC 9457（2023 年发布，取代 RFC 7807）是 2026 年错误响应的标准格式**——统一结构、机器可读、全端点一致：

```json
{
  "type": "https://api.example.com/errors/order-invalid",
  "title": "Order Invalid",
  "status": 422,
  "detail": "订单金额与明细不符",
  "instance": "/orders",
  "errors": [
    { "field": "items[2].price", "code": "price_mismatch", "message": "单价与商品不符" }
  ]
}
```

字段语义：**type**——错误类型的机器可读标识（URL 形式，指向错误文档）；**title**——人类可读的短标题（稳定，可 i18n）；**status**——HTTP 状态码（冗余但便于日志与中间件）；**detail**——人类可读的详细描述（面向开发者）；**instance**——出错的具体 URL（排查定位）；**errors[]**——字段级错误数组（下节）。**2026 实践要点**：所有端点统一这个结构（成功响应不需要包壳——错误才需要标准格式）；`type` 是错误分类的主键（客户端按 type 分支比按 message 字符串匹配可靠）；`detail` 面向开发者不面向最终用户（用户文案在客户端渲染）。

## 4. 字段级校验错误

表单类 API 最常见的失败是「多个字段一起错」——RFC 9457 的 `errors[]` 数组承载字段级错误，客户端可直接渲染行内错误：

```json
{
  "type": "https://api.example.com/errors/validation-failed",
  "title": "Validation Failed",
  "status": 422,
  "errors": [
    { "field": "email", "code": "invalid_format", "message": "邮箱格式不正确" },
    { "field": "password", "code": "too_short", "message": "密码至少 8 位" },
    { "field": "items[0].quantity", "code": "exceeds_stock", "message": "库存不足" }
  ]
}
```

设计要点：**field 用 JSONPath 式路径**（`items[2].price`——嵌套字段可定位）；**code 是机器可读错误码**（客户端映射到 i18n 文案与行为）；**一次性返回全部校验错误**（不是「发现一个错就返回」——客户端要的是「一次提交列出所有问题」）；**message 面向开发者**（用户文案客户端映射）。**「校验错误不漏报」的工程实现**：服务端校验框架收集全部错误（Spring 的 MethodArgumentNotValidException 天然如此，配合 04 篇的全局异常处理）。

## 5. 错误码设计

业务错误码是「状态码之下的细分」——两种主流设计：

**方案一：type URL 即错误码**——`https://api.example.com/errors/order-invalid`——错误即文档，客户端按 type 匹配。**方案二：独立错误码字段**——`"code": "ORDER_ALREADY_APPROVED"`——枚举字符串，OpenAPI 里声明。**推荐：type 为主 + code 为辅**——type 做分类（`validation-failed`），code 做具体原因（`price_mismatch`）——两层粒度，客户端可按需选择匹配深度。

**错误码的治理纪律**：**错误码进 OpenAPI 文档**（客户端可生成类型）；**错误码稳定**（改码 = 破坏性变更，走 06 篇版本化流程）；**错误码全局唯一**（不按端点重复定义同义码）；**错误码是契约的一部分**（与字段、端点同级管理）。

## 6. 错误响应安全红线

错误信息是信息泄露的高发地带——三条红线：

**绝不返回堆栈**——异常堆栈进响应 = 代码结构、依赖版本、内部路径全暴露；生产环境全局异常处理兜底 500 + 通用文案（堆栈只进日志）。**绝不返回 SQL/内部路径**——数据库错误原文、文件系统路径是攻击者的地图。**绝不返回内部用户信息**——「用户 5 存在但密码错」这类文案泄露账号状态（[[../10-前端知识拓展/Token/09-安全红线与攻防|Token 安全体系]] 的防枚举纪律）。**标准做法**：生产错误响应统一 `500 {"title": "Internal Server Error"}`（或 RFC 9457 格式），细节全在服务端日志（带 trace id 关联——09 篇日志治理）。

## 7. 服务端错误与重试

5xx 的客户端处理策略：**500/502/503/504 值得重试**（服务端瞬时故障），**但 5xx 重试要有限制**（指数退避 + 抖动 + 上限，3-5 次）——无限重试会放大故障（重试风暴，[[../10-前端知识拓展/Token/00-Token总览|Token 体系]] 09 篇与 [[../07-工程运维基础/运维/MySQL%20Redis%20MQ%20运维相关故障现象|中间件运维]] 的同类纪律）；**503 响应带 `Retry-After` 头**（服务端告知重试时间）；**429 限流响应**带 `Retry-After` + 限流三头（`X-RateLimit-Limit/Remaining/Reset`，09 篇）——客户端按头重试而不是瞎猜；**5xx 重试的幂等配合**——写操作重试必须有幂等键（05 篇）。

## 8. 常见坑

**坑一：业务失败返回 200**。业务码藏 body——状态码语义被破坏，监控与客户端无法通用判断——错误用 4xx/5xx。

**坑二：400 通吃**。语义错误也 400——客户端无法区分「改请求」与「改状态」——422/409 细分。

**坑三：错误格式全端点不一致**。每个 Controller 各写各的错误结构——RFC 9457 统一 + 全局异常处理器。

**坑四：错误码不进文档**。客户端只能靠 message 字符串匹配——错误码进 OpenAPI。

**坑五：生产返回堆栈**。忘了全局 500 兜底——堆栈泄漏。

**坑六：429 不带 Retry-After**。客户端瞎等或狂试——Retry-After + 限流三头。
