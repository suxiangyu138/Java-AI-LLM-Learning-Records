## 1. 方法矩阵

五个核心方法各自承担一种操作语义，全部设计决策以此为骨架：

| 方法 | 语义 | 幂等 | 安全 | 典型响应 |
|------|------|:---:|:---:|---------|
| GET | 读取资源 | ✅ | ✅ | 200 + 资源 |
| POST | 创建资源/触发动作 | ❌ | ❌ | 201 + Location |
| PUT | 整体替换 | ✅ | ❌ | 200 / 204 |
| PATCH | 局部修改 | ⚠️ 视实现 | ❌ | 200 / 204 |
| DELETE | 删除 | ✅ | ❌ | 204 |

**安全方法**（GET）：只读不产生副作用——可以安全缓存、预取、爬虫抓取；**幂等方法**：执行一次与执行多次结果一致——客户端可以安全重试（网络超时后重发，不担心重复创建）。这两个属性是「客户端能否安全重试」的协议级保证——**设计 API 时把每个端点标上「幂等？安全？」两个标签，重试策略（05 篇幂等键）就清晰了**。

## 2. 幂等性与安全方法

**幂等 ≠ 结果不变**——`PUT /orders/123` 把订单改成 A，再执行一次还是 A（结果一致）；但第一次执行与第二次执行之间如果别的请求把它改成 B，第三次 PUT 会把它改回 A——幂等保证的是「重复同一请求的最终状态一致」，不是「请求之间无人打扰」。

**GET 天然安全且幂等**（只读）；**PUT/DELETE 天然幂等**（整体替换/删除——删除不存在的资源也是「删除成功」语义，返回 404 或 204 看约定）；**POST 天然不幂等**（每次创建新资源）；**PATCH 的幂等性取决于实现**——`{"status": "approved"}` 是幂等的（幂等修改），`{"count": count + 1}` 不是（累加操作）——**PATCH 用「赋值」不用「运算」**，运算逻辑放服务端事务里。

**重试语义的落地**：GET 超时 → 直接重发（安全）；PUT/DELETE 超时 → 直接重发（幂等）；POST 超时 → 不确定创建没有——**这就是幂等键的用武之地**（05 篇：POST 带 Idempotency-Key，服务端按键去重）。

## 3. GET：读取

GET 的完整语义与注意点：**无请求体**——GET 不带 body（规范禁止，部分客户端/网关会丢弃），查询参数都走 URL query；**可缓存**——响应可带 `Cache-Control`，CDN/浏览器缓存是 GET 的性能红利（[[../Web%20高阶知识/02-HTTP缓存体系|HTTP 缓存]]）；**集合与元素**——`GET /orders`（列表，07 篇分页）、`GET /orders/123`（详情）。

三个工程细节：**列表接口默认分页**（07 篇——不分页的列表是隐患）；**详情接口的字段集合**（详情 vs 列表字段不同——列表瘦、详情胖，字段选择参数 `?fields=` 可选）；**GET 不应有副作用**——「GET /orders/123 把订单标记为已读」违反安全方法语义（已读标记是状态修改，用 PATCH），违反的后果是爬虫/预取/缓存会触发副作用。

## 4. POST：创建

POST 的语义是「在集合中创建新资源」或「触发不可幂等的动作」：

**创建成功返回 201 + Location 头**——`Location: /orders/456` 告诉客户端新资源在哪（客户端无需自己拼 URL）；**响应体**返回新资源（常用）或空（约定）；**客户端 ID vs 服务端 ID**——服务端生成 ID 是默认；客户端生成 ID（UUID）时用 `PUT /orders/{client_id}` 或 POST 带 `Idempotency-Key`——**幂等键本质上就是「客户端提供的操作 ID」**（05 篇）。

**POST 的另类用法**：不创建资源但触发动作（批量重算、导入）——这类「动作 POST」要显式声明（02 篇 RPC 扩展），且同样需要幂等键保护（重试不重复执行）。

## 5. PUT 与 PATCH：替换与修改

PUT 与 PATCH 是新人最容易混的一对：

**PUT = 整体替换**——`PUT /orders/123` 的 body 是完整订单，服务端用 body 整体覆盖资源——缺失字段 = 清空/回默认（客户端要承担「完整状态」的职责）；幂等（相同 body 重复执行结果一致）。

**PATCH = 局部修改**——body 只含要改的字段：`PATCH /orders/123 {"status": "approved"}`——缺失字段不动。**PATCH 是 2026 的事实标准**（RFC 5789 定义；JSON Merge Patch 与 JSON Patch 两种格式，团队约定一种）。

**选型**：**能用 PATCH 就用 PATCH**——PUT 的「整体替换」语义在真实场景很少用（客户端通常不知道完整状态）；PUT 保留给「客户端全量同步」场景（配置同步、客户端持有完整状态）。**PUT vs PATCH 的面试必问点**：幂等性差异（PUT 天然幂等、PATCH 视实现）+ 语义差异（替换 vs 修改）。

## 6. DELETE：删除

DELETE 的语义与实现细节：**返回 204 No Content**（删除成功无内容返回——不是 200 带空 body）；**幂等性语义**——删除不存在的资源：返回 404（严格）或 204（宽松：目标状态已达成）。**团队约定一种**并在 OpenAPI 里写清楚（08 篇）——推荐 404（语义明确，客户端能区分「从未存在」与「刚被删」）。

**删除的实现模式**：**物理删除**（真正删行——数据不可恢复，谨慎）；**逻辑删除/软删除**（`deleted_at` 标记——可恢复、保留审计，REST 视角 DELETE 照常返回 204，实现层软删）；**停用**（状态改为 inactive，资源仍可 GET——语义上是 PATCH status，不是 DELETE）。**DELETE 与幂等键**：DELETE 天然幂等无需键，但「删除 → 重试」与「删除 → 重建」的竞态要靠业务处理（先查后删的补偿）。

## 7. 方法误用的典型场景

**场景一：GET 带 body 查询**。复杂查询（多条件数组）塞 body——违反 GET 语义（无 body），要么参数拆分到 query（复杂查询用专用查询端点，07 篇），要么换 POST（「查询端点 POST /orders/search」是实践中的妥协方案，显式声明）。

**场景二：POST 当万能方法**。所有操作都 POST（RPC 残留）——方法语义失去信息量，客户端无法预判幂等与缓存行为。

**场景三：更新用 PUT 但传部分字段**。部分更新走 PUT——缺失字段被清空——PATCH。

**场景四：删除返回 200 + 对象**。200 带删除对象（个别风格）——204 是标准；200 会让客户端以为「响应体是资源」。

**场景五：PATCH 做累加运算**。`{"count": +1}` 非幂等——用赋值语义或服务端事务。

## 8. 常见坑

**坑一：GET 有副作用**。已读标记放 GET——爬虫预取触发——副作用操作走 PATCH。

**坑二：POST 创建不返回 Location**。客户端无法知道新资源 ID——201 + Location。

**坑三：PUT 部分更新**。字段被清空事故——PATCH。

**坑四：DELETE 返回 200**。客户端等 body——204。

**坑五：409 与 422 混用**。状态冲突（已审核不能改）用 409，字段语义错误用 422——04 篇。

**坑六：PATCH 的 body 格式不约定**。JSON Merge Patch 与 JSON Patch 混用——团队选一种，OpenAPI 声明。
