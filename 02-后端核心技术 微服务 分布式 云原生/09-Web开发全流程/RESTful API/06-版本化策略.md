# 06-版本化策略

## 1. 为什么必须版本化

API 的消费方是你管不到的：客户端应用、第三方开发者、AI agent——**「改一下字段」对你是小改动，对消费方是线上事故**（前端崩溃、agent 解析失败、数据丢失）。版本化不是「要不要」的问题，是「从哪一天开始」的问题：

**从第一天就版本化**——即使你确信「内部 API 不会变」：一旦被消费，没有版本号 = 无法演进（改 = 破坏所有人，不改 = 背着技术债）。**「以后再说」的代价**：上线后第一个破坏性变更需求出现时，你要么加 /v1 前缀（所有客户端改 base_url——你承诺过不破坏的），要么背着「永不改变」的枷锁——**从第一天加 /v1/ 的成本是零，不加的代价是全量迁移**。

**版本化的语义**：版本承诺的是「契约的兼容性」——v1 客户端的请求在 v1 端点永远按 v1 语义工作；新能力加在 v2（或兼容扩展），旧行为在 v1 保留到弃用期结束。

## 2. 版本策略对比

四种主流的版本表达方式，2026 的推荐与理由：

| 策略 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| **URL 路径** | `/v1/orders` | 显式、可缓存、日志可查、所有客户端都支持 | 代码要维护多套路由 |
| **Header** | `API-Version: 2026-05-01` | URL 干净 | 客户端易漏配、网关要透传、「看不见的版本」制造工单 |
| **Query 参数** | `?api_version=1` | 实现简单 | 可缓存性差、日志污染、参数易被业务参数混淆 |
| **媒体类型** | `Accept: application/vnd.api+json;version=1` | 内容协商正统 | 实现成本最高、工具链支持弱 |

**2026 共识：URL 路径版本是明确推荐**——显式（人人可见）、可缓存（CDN 按 URL 缓存）、日志可查（grep `/v1/` 即分离流量）、对一切客户端友好（curl 到浏览器到 agent 都天然支持）。Header 版本的「隐形」问题是致命伤：客户端漏配头 = 静默用了默认版本 = 升级事故。**约定**：路径版本用整数（`/v1/`、`/v2/`），不用日期/语义化版本号（`/v1.2/` 粒度太细）。

## 3. URL 路径版本最佳实践

```text
/v1/orders        v1 版本全部端点
/v2/orders        v2 版本全部端点
```

**路由实现**（Spring 视角）：版本前缀在路由层统一（`@RequestMapping("/v1/orders")` 或网关层加前缀）；**内部共享**：v1 与 v2 的 Controller 可共享 Service 层（版本只变「接口形态」不变「业务逻辑」——接口适配层 vs 业务层分离）。**默认版本**：不带版本号的请求（`/orders`）——**不提供默认**（强制显式版本）或重定向到最新版（提供便利）——推荐强制显式（默认版本 = 隐式版本，客户端悄悄升级）。

**版本的粒度**：**整包版本化**（整个 API 一个版本号）是默认——简单一致；**局部版本化**（个别端点先 v2）是高级玩法（破坏性变更只影响个别端点时）——团队成熟后再考虑。**版本与资源**：`/v1/orders/123` 的「资源身份」是 `/orders/123`，版本只是契约版本——缓存键、日志聚合、监控看板都要按「去版本」后的资源聚合（否则 v1/v2 流量分离，看不出总量）。

## 4. 破坏性变更识别

**什么算破坏性变更**（要开新版本或走弃用流程）——**移除字段/端点**（客户端解析崩溃）；**改变字段类型**（string → number，客户端比较逻辑全错）；**改变语义**（`status` 的取值范围变了）；**改变状态码**（客户端按码分支）；**收紧校验**（原来能过现在 422）；**改变响应嵌套结构**。**什么不算破坏性变更**（可兼容扩展）——**新增字段**（客户端多读一个字段无害）；**新增端点**；**新增可选参数**；**宽松校验**（原来 422 现在通过）；**扩展枚举值**（客户端要容错未知值）。

**2026 的工程化检测**：**oasdiff**——OpenAPI 契约的 diff 工具，CI 里自动检测「这次改动是否破坏性」——破坏性变更在合并前被拦住，人工评审的遗漏由工具兜底（08 篇 CI 工具链）。**「扩展枚举值」的兼容细节**：客户端必须「未知值不崩溃」（服务端保证不了客户端，但文档要写明容错要求）。

## 5. 弃用与下线流程

版本的生命周期管理——**弃用（Deprecation）→ 下线（Sunset）**：

**弃用通知**：v1 计划下线时，**所有 v1 响应带 `Deprecation: true` 头**（RFC 8594，标准弃用头）；文档标注「Deprecated」；**Sunset 头**（`Sunset: 2026-12-31`）告知具体下线时间——**客户端与工具能自动感知**（不靠邮件通知）。**弃用期**：90 天是底线，推荐 6 个月（搜索结果的共识）——给客户端迁移窗口；**迁移路径**：文档提供「v1 → v2 变更指南」（字段映射表是标配）；**下线**：到期后返回 410 Gone（不是 404——410 语义是「曾经存在现在没了」，客户端能区分）。

**弃用期的沟通纪律**：弃用信息进 changelog（API 变更日志是文档的一部分，08 篇）；**「静默下架」是事故**——客户端在未知中崩溃，投诉无处可查。

## 6. 多版本并存治理

多版本并存是常态（N-1 支持：同时维护最新版与上一版）：

**并存原则**：**至少支持 N-1**（v2 上线时 v1 仍运行到弃用期结束）；**版本间流量可观测**（监控按版本拆分——v1 流量为零才能安心下线）；**版本间数据兼容**（v2 返回的新字段，v1 不返回——底层数据模型共享但响应裁剪）。

**并存成本治理**：**接口适配层薄化**——v1/v2 的 Controller 只做「请求/响应形态转换」，业务逻辑在共享 Service——版本并存成本 ≈ 适配层代码，不是业务双份；**新版本不复制老 bug**——v2 修 bug 不回填 v1（v1 是冻结的契约）；**版本数量封顶**——超过 2 个活跃版本的并存是架构失控的信号（要么弃用流程失效，要么版本粒度太细）。

## 7. 常见坑

**坑一：不加版本号**。被消费后无法演进——从第一天 /v1/。

**坑二：Header 版本**。客户端漏配头 → 默认版本静默升级——URL 路径显式。

**坑三：破坏性变更静默上**。删字段不改版本——客户端崩溃——oasdiff 检测 + 弃用流程。

**坑四：弃用期为零**。「今天通知明天删」——90 天起步，Sunset 头明示。

**坑五：下线返回 404**。410 Gone 才是「曾存在已下线」——客户端可区分。

**坑六：v1/v2 业务逻辑双份**。改一处忘一处——适配层薄化，业务共享。

**坑七：版本在 body 里**。`{"version": 2}`——无法路由、无法缓存——版本必须在 URL。
