## 1. 资源识别：第一步

资源识别的质量决定 API 的质量——三个问题帮你把业务域翻译成资源：

**业务名词是什么**——订单、用户、商品、发票……名词即资源候选；动词（下单、结算）不是资源，是资源上的操作（方法表达）。

**名词之间的关系**——「用户拥有订单」→ 嵌套（`/users/5/orders`）；「订单包含商品」→ 嵌套或子资源（`/orders/1/items`）。**从属关系用嵌套，独立实体用平级**——「商品」单独存在（`/products`），不是谁的私有财产；「订单明细」只属于订单（`/orders/1/items`）。

**资源的生命周期**——创建（POST）、读取（GET）、更新（PUT/PATCH）、删除（DELETE）四个动作都要覆盖——资源设计以 CRUD 为骨架，扩展操作（审核、发布）是「状态流转」用 PATCH 表达（03 篇）。

**资源与实体的区别**：同一实体可以有多个资源视图——订单的「列表视图」与「详情视图」；「订单汇总」是计算资源（`GET /orders/summary`，07 篇讨论）——先识别实体，再设计视图，最后才定 URL。

## 2. URL 命名规范

2026 年收敛的 URL 命名规范，团队约定优于个人风格：

**全小写 + kebab-case**——`/order-items` 而不是 `/orderItems`/`/OrderItems`——小写避免大小写敏感的混乱（部分服务器不区分、缓存键区分），kebab-case 在 URL 中可读性最好（`/user-profiles` 一眼分词）。

**名词复数表达集合**——`/orders` 表示「订单集合」，`/orders/123` 表示「集合中的一个元素」——复数是行业默认（GitHub、Stripe 皆如此），一致即可。

**不用文件扩展名**——`/orders.json` 是历史遗留（内容协商用 `Accept` 头，不是 URL 后缀）；不用版本号前缀之外的前缀（`/api/` 前缀可选，但 `/api/v1/orders` 与 `/v1/orders` 二选一保持一致）。

**ID 与标识**——路径参数用数字 ID（`/orders/123`）或 UUID（`/orders/a3f9...`）——**对外 API 用 UUID 防枚举**（数字 ID 可遍历，配合 09 篇授权才安全）；slug（`/articles/rest-101`）用于可读性优先的场景。

## 3. 集合、元素与嵌套

资源层级的三级模型，嵌套不超过两层：

```text
/orders                   集合（GET 列表 / POST 创建）
/orders/123               元素（GET 详情 / PUT 整体替换 / PATCH 局部 / DELETE）
/orders/123/items         子集合（GET 该订单的明细列表）
/orders/123/items/456     子元素（GET 明细详情）
```

**嵌套的取舍**：嵌套表达「强从属」——明细离开订单无意义，天然嵌套；但「用户的订单」也可以平级（`/orders?user_id=5` 过滤查询）——**嵌套 vs 过滤的决策**：资源数量少、关系固定 → 嵌套；资源独立存在、查询维度多 → 平级 + 过滤参数。**嵌套过深的信号**：`/users/5/orders/1/items/2` 三层以上说明资源模型出问题了——要么中间层级不该嵌套，要么该引入新的顶级资源（如「订单项」独立为 `/order-items`）。

**集合操作**：批量创建（POST 数组）、批量删除（DELETE 带 ids 参数）——REST 无标准批量语义，团队约定 + OpenAPI 文档明确（08 篇）。

## 4. 查询参数与过滤

集合资源的查询参数规范化——过滤、排序、分页、字段选择四类各就各位：

```text
GET /orders?status=paid&user_id=5&sort=-created_at&page=2&page_size=20
     └─过滤───────────┘  └─排序────┘ └─分页───────────────┘
```

**过滤**：`?status=paid` 精确匹配；范围用 `?price_min=10&price_max=100`；多值 `?status=paid,cancelled` 或 `?tag=a&tag=b`（团队约定一种）。**排序**：`?sort=created_at` 升序、`?sort=-created_at` 降序（负号前缀是常见约定）；多字段 `?sort=-created_at,id`。**字段选择**（稀疏字段）：`?fields=id,name`——移动端省流量的高级功能，可选。**搜索**：`?q=关键词` 与过滤区分——过滤是结构化条件，搜索是模糊匹配（可以走独立搜索端点）。

**参数命名一致性**：`page_size` 还是 `limit`、`user_id` 还是 `userId`——选一套全 API 统一（07 篇分页与命名规范）；参数用 snake_case 是 URL 惯例（与 JSON 字段的 camelCase 约定区分——URL 与 JSON 各按自己规范，02 篇与 07 篇分别约定）。

## 5. 常见反模式

**反模式一：动词 URL**。`/getOrders`、`/createUser`——RPC 思维残留；动词表达的操作全部可由「名词 + 方法」表达。

**反模式二：动作 URL 化**。`/orders/123/approve`——「审核订单」是状态流转，`PATCH /orders/123 {"status": "approved"}`；确实无法资源化的操作（重算、导入）可以保留动作端点，但要显式声明是 RPC 扩展（01 篇边界）。

**反模式三：大小写混用**。`/OrderItems`、`/user_orders` 混搭——一套 API 一种风格，kebab-case 统一。

**反模式四：裸 ID 无上下文**。`/api/getData?id=123`——看不出是什么资源；`/orders/123` 自带语义。

**反模式五：深层嵌套**。四层 URL 是资源模型出错的信号——重构资源识别。

**反模式六：URL 里带动作状态**。`/orders/123/paid`——「已支付」是订单的状态属性，不是独立资源；用 `PATCH status` 或过滤查询。

**资源设计的实战方法**（把「设计」从感觉变成流程）：**画资源图**——白板上列出业务名词与关系（订单-用户-商品-支付），标出「从属」与「独立」——30 分钟的资源图比三个月后重构 URL 便宜得多；**写端点清单**——把每个资源的 CRUD + 特殊操作列成表格（方法 + 路径 + 简述），评审就评这张表；**契约先行**——端点清单落成 OpenAPI（08 篇），评审 diff 的就是契约。**资源模型的演进**：业务加新名词（优惠券）→ 新增资源而非改旧资源——资源模型是「增量演进」的，破坏性修改（改名/改层级）走 06 篇版本化流程。

## 6. 设计检查清单

- [ ] 资源是业务名词，操作由 HTTP 方法表达
- [ ] URL 全小写 + kebab-case + 名词复数
- [ ] 集合/元素/子资源层级清晰，嵌套 ≤2 层
- [ ] 对外 ID 用 UUID（防枚举），内部可用数字
- [ ] 过滤/排序/分页参数全 API 一致命名
- [ ] 无动词 URL、无动作状态 URL、无扩展名
- [ ] 每个资源的 CRUD 四方法齐全（不能做的显式返回 405）
- [ ] 资源模型能覆盖业务操作（不能覆盖的显式声明 RPC 端点）

**URL 稳定性与契约承诺**：URL 一旦发布就是契约的一部分——**「URL 不随实现变」是稳定性的底线**：内部重构（改服务拆分、改表结构）不应反映到 URL；只有「业务语义变化」才该改 URL（走版本化）。**对外 URL 的保守策略**：宁可多设计一层（`/v1/` 前缀、资源层级预留），不可少——上线后加 `/v2` 容易，把 `/orders` 改成 `/orders-v2` 是灾难。**URL 文档化**：每个端点一句「做什么」进 OpenAPI 的 summary/description（08 篇）——URL 自解释 + 文档补语义，是「URL 可被 AI agent 理解」的基础。
