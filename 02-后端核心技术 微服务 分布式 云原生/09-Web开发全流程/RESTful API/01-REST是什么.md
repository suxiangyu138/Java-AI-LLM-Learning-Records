## 1. REST 的起源与本质

REST（Representational State Transfer，表述性状态转移）是 Roy Fielding 在 2000 年博士论文中提出的架构风格——它不是协议、不是标准、没有「REST 认证机构」，而是一组设计约束的集合。**「RESTful API」= 遵循这些约束的 HTTP API**；「REST 风格」= 一种把「状态」当作「资源」来表述与转移的心智模型。

理解 REST 的关键转变：**把 API 从「动作清单」变成「资源地图」**——RPC 风格问「我要调用什么函数」（`/getOrder?id=1`），REST 风格问「我要操作什么资源」（`GET /orders/1`）。URL 描述「是什么」，HTTP 方法描述「做什么」，状态码描述「结果如何」——三者各司其职，这是 REST 一切设计决策的根源。

## 2. 六约束

Fielding 定义的六个约束，现代实践中已有所弱化但仍是理解 REST 的框架：

**客户端-服务器**——客户端与服务器独立演进（前端换框架不影响后端）；**无状态**——每个请求自包含全部信息，服务器不存客户端会话（Token 鉴权正是为满足此约束演化而来，见 [[../10-前端知识拓展/Token/00-Token总览|Token 体系]]）；**缓存**——响应可标记缓存性，减少重复传输（[[../Web%20高阶知识/02-HTTP缓存体系|HTTP 缓存]] 的语义基础）；**统一接口**——资源识别、表述、自描述消息、HATEOAS 四要素（本体系 02-07 篇的全部内容都是「统一接口」的展开）；**分层系统**——中间层（网关、代理）可透明插入；**按需代码**——服务器可下发代码（现代实践中几乎不用，小程序/JS 下载场景的边缘形态）。

**2026 的现实**：无状态约束与「服务端会话」存在张力（会话方案把状态放回服务器，但通过共享存储维持「请求无状态」的外观）；HATEOAS（超媒体驱动）在现代 API 中基本不落地（07 篇讨论）；按需代码被安全实践排斥——**六约束是「理想模型」，生产 API 是「按场景取舍」**——但资源化与统一接口这两条是底线，违反它们就不是 RESTful。

## 3. 资源化思考

把业务域翻译成资源模型是 REST 设计的核心技能——两步翻译：

**第一步，识别资源**：业务名词即资源——订单、用户、商品、支付——以及它们的关系（用户下的订单、订单里的商品）。**第二步，设计资源层级**：集合（`/orders`）+ 元素（`/orders/123`）+ 子资源（`/orders/123/items`）——嵌套表达「从属关系」，不超过两层（超过说明资源识别有问题）。

```text
RPC 风格（反模式）              REST 风格
GET /getOrder?id=123      →    GET    /orders/123
POST /createOrder         →    POST   /orders
POST /deleteOrder         →    DELETE /orders/123
POST /updateOrderStatus   →    PATCH  /orders/123  {status}
GET /getUserOrders?uid=5  →    GET    /users/5/orders
```

翻译的检验标准：**「能不能用资源 + 方法表达」**——表达不出（如「批量重算」）说明要么资源模型错了，要么该用 RPC 端点（08 篇讨论边界）；**「URL 是否稳定」**——资源不随操作变化（`/orders/123` 无论是查是改都是它），URL 稳定性是客户端缓存与书签的基础。

## 4. 2026 现状与选型

2026 年的 API 生态是三分天下，REST 是默认选项：

| 风格 | 特点 | 场景 |
|------|------|------|
| REST | 资源化、HTTP 原生、缓存友好、生态最全 | **默认首选**，绝大多数 Web/移动 API |
| GraphQL | 客户端指定字段、单端点、强类型 | 多端字段差异大、客户端驱动查询 |
| gRPC | 二进制、强类型、流式、高性能 | 服务间调用、微服务内部、低延迟 |

**选型判断**：面向浏览器与第三方的 API → REST（HTTP 缓存、CDN、工具生态无可替代）；客户端查询需求复杂多变 → GraphQL；服务间高性能调用 → gRPC。**「REST 过时了」是伪命题**——2026 年主流平台（Stripe、GitHub、AWS）仍以 REST 为对外 API 标准，GraphQL 与 gRPC 是特定场景的补充而非替代——REST 的生态优势（缓存、CDN、工具、教程、OpenAPI 契约链）让它在「对外、通用、长期」场景没有对手。**「RESTful 与否」的判定**：满足「资源化 URL + 方法语义 + 状态码语义 + 契约化」四条即算合格的 REST API——不追求教条式的完全合规。**AI agent 时代的 API 设计**（09/10 篇）也以 REST + OpenAPI 契约为底座——agent 通过 OpenAPI 发现与调用 API，契约质量成为「API 可被 AI 使用」的前提。

## 6. 五条边界

**不是标准**——没有权威机构认证「RESTful」，约定优于配置，团队规范比教条重要。

**不是所有 API 的答案**——批量操作、复杂查询、服务间高性能调用，REST 表达吃力时换工具（gRPC/GraphQL/RPC 端点）。

**不解决安全**——认证、授权、限流是独立工程（09 篇），REST 只管表达。

**不保证一致性**——分布式事务、最终一致性是数据层问题，API 层只能设计好接口形态。

**不是性能优化**——N+1 查询、慢接口是实现问题；REST 的资源化反而可能鼓励过多请求（GraphQL 的卖点之一）。
