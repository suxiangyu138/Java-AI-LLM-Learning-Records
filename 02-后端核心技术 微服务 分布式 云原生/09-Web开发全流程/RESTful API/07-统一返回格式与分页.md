## 1. 统一返回格式之争

「成功响应要不要包壳」是 API 设计的长青争论，2026 的主流答案是分场景：

**裸返回（推荐）**——成功响应直接返回资源本体：`200 {"id": 1, "name": "..."}`；错误走 RFC 9457（04 篇）。理由：**语义干净**（状态码已表达成败，包壳冗余）、**OpenAPI 表达自然**（响应 schema 就是资源）、**无历史包袱**（前端速查版「统一返回格式」的 `{code, message, data}` 壳源于「HTTP 状态码不可靠」的旧时代，2026 已不成立）。

**包壳（历史方案）**——`{"code": 0, "message": "success", "data": {...}}`——**它解决的问题（业务码表达错误）已被 RFC 9457 取代**；它的代价是每层解析都要剥壳、OpenAPI schema 要包一层。**2026 决策**：新项目用裸返回 + RFC 9457；存量项目保持包壳（改动是全客户端迁移）。**统一格式的底线**：无论裸还是壳，**全 API 一种格式**——成功格式统一、错误格式统一（RFC 9457）、分页格式统一——「每个 Controller 各写各的」才是真正的罪。

## 2. 分页：offset vs cursor

分页是列表接口的必选项（不分页的列表是隐患），两种方案的取舍：

| 维度 | Offset 分页 | Cursor 分页 |
|------|-----------|-------------|
| 实现 | `?page=2&page_size=20`（偏移量） | `?cursor=xxx&limit=20`（游标） |
| 深翻页 | **退化**（偏移越大越慢，`OFFSET 100000`） | 稳定（`WHERE id > cursor` 走索引） |
| 数据变动 | 翻页时新增/删除 → 重复/跳项 | 稳定（游标锚定位置） |
| 实时性 | 弱（快照偏移） | 强（游标即位置） |
| 客户端友好 | 简单（页码跳转、UI 页码器） | 复杂（只有「下一页」，无页码跳转） |
| 适用 | 小数据集、管理后台、页码 UI | 大数据集、实时流（订单流、消息流） |

**选型标准**：**数据集小（万级内）+ 需要页码跳转 UI → offset**；**数据集大（十万+）或实时变动（新增频繁）→ cursor**。**2026 趋势**：camera-ready 的 API（Stripe、GitHub 的游标方案）越来越多——但「后台管理列表用 offset」仍是合理选择——**按场景选，不按流行选**。

## 3. 分页响应结构

分页响应的标准结构（元数据与数据同返，团队统一）：

```json
{
  "items": [ { "id": 1 }, { "id": 2 } ],
  "pagination": {
    "next_cursor": "abc123",        // cursor 方案：下一页游标（无 = 到底）
    "has_more": true                // 是否还有下一页（客户端驱动「加载更多」）
  }
}
```

```json
// offset 方案的元数据（列表页 UI 需要）
{ "items": [...], "total": 342, "page": 1, "page_size": 20, "total_pages": 18 }
```

设计要点：**分页参数名统一**——`page`/`page_size`（offset）或 `cursor`/`limit`（cursor）全 API 一致；**page_size 有上限**（默认 20、最大 100——防「一次拉全表」）；**cursor 不透明**（客户端把 cursor 当不透明字符串——base64 编码的排序键，不解码不拼接）；**返回 `has_more`**（cursor 方案的关键字段——客户端判断是否还有下一页，不用猜）；**total 是 offset 方案的代价**（COUNT 查询在数据量大时也慢——大数据集用 cursor 就没有 total 的负担）。

## 4. 排序与过滤

排序与过滤的规范化（02 篇查询参数的展开）：

**排序**：`?sort=-created_at,id`——字段白名单（防注入与暴露内部字段——服务端维护可排序字段列表，非法字段 400）；多字段按逗号、负号前缀降序。**过滤**：精确匹配 `?status=paid`；范围 `?price_min=&price_max=`；多值 `?status=paid,cancelled`（或重复参数，团队选一）。

**复杂查询的边界**：多条件组合 + 嵌套过滤（「近 30 天 + 金额 > 100 + 含某商品的订单」）——query 参数会爆炸——两个方案：**专用查询端点**（`POST /orders/search`——POST 带查询条件 body，显式声明是查询端点，不是创建）；**GraphQL 化**（查询复杂度超过 REST 表达力时考虑，01 篇选型）。**过滤参数的校验**：枚举字段的非法值返回 400（不是静默忽略——静默忽略 = 客户端以为过滤生效了，数据却不对）。

## 5. 命名一致性

命名的混乱让客户端为「同一概念的不同写法」写适配代码——一致性是工程素养：

**字段命名**：JSON 字段 camelCase（`createdAt`、`userId`——JavaScript 生态默认）或 snake_case（`created_at`——Python/Java 传统）——**选一套全 API 统一**；**2026 倾向**：camelCase 是前端生态事实标准（OpenAPI 工具链默认），与前端速查版对齐。**URL 参数**：snake_case（`page_size`、`user_id`——URL 惯例）——**URL 与 JSON 可以不同规范，各自一致即可**（02 篇）。

**响应字段的语义一致**：同一概念全 API 同名（用户 ID 不叫 `uid` 又叫 `userId`）；时间格式统一 ISO 8601（带时区 `2026-08-10T12:00:00Z`——不带时区的时间是灾难）；金额用「最小单位整数」（分/厘——浮点数金额是财务事故根源）还是「十进制字符串」（`"12.34"`——避免浮点误差，Stripe 用整数分、部分 API 用字符串，选一种并文档声明）；**null 与缺失**——`null` 表示「值不存在」、缺字段表示「字段不适用」——统一约定。

## 6. HATEOAS 讨论

HATEOAS（超媒体驱动）——REST 六约束「统一接口」的第四要素：响应中带资源链接（`"links": {"self": "/orders/123", "approve": ...}`），客户端靠链接导航而非硬编码 URL。**2026 的现实**：**基本不落地**——理由：客户端工具链支持弱、OpenAPI 契约已承担「发现」职责（契约比链接更可靠）、动态链接让客户端逻辑更复杂。**少数场景有价值**：状态机驱动的资源（订单状态流转的可用操作链接——客户端免硬编码状态→动作映射）；**结论**：默认不做 HATEOAS，链接信息用 OpenAPI + 文档表达；状态机场景可局部引入。

## 7. 常见坑

**坑一：包壳 + RFC 9457 混用**。成功包壳、错误 RFC 9457——客户端要写两套解析——选一套（推荐裸 + RFC 9457）。

**坑二：分页无上限**。`page_size=100000` 拉全表——上限 100。

**坑三：大数据集用 offset**。深翻页拖垮数据库——cursor。

**坑四：cursor 让客户端解码**。文档写了「cursor 是 base64 排序键」——客户端解码依赖内部格式——不透明字符串契约。

**坑五：时间不带时区**。`2026-08-10 12:00`——跨时区客户端全错——ISO 8601 + Z。

**坑六：金额用浮点**。`12.34` 的浮点误差——整数分或字符串。

**坑七：过滤静默忽略非法值**。客户端以为生效了——400 显式拒绝。
