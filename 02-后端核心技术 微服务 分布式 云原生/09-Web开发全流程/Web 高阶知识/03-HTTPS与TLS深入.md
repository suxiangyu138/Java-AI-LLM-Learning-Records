## 1. HTTPS 全景与 2026 现状

| 事实 | 数据 |
|------|------|
| HTTPS 占比 | 页面加载 **94%**（Firefox 遥测，2026） |
| TLS 1.3 | 加密流量 **~70-73%**（2026），事实标准 |
| TLS 1.2 | 剩余 ~27-30%（老企业栈为主） |
| TLS 1.0/1.1/SSL3 | 全面弃用（浏览器/云平台默认禁用） |
| 后量子混合 | TLS 1.3 连接中 **~15% 已用混合密钥交换**（2026 初，逐月增长） |
| Let's Encrypt | 累计签发 40 亿+ 证书，覆盖 3.6 亿+ 站点 |

```text
HTTPS = HTTP + TLS（安全套接层在传输层之上）
  HTTP（应用层）
  TLS（安全层：加密/认证/完整性）
  TCP（传输层）
```

> 🎯 一句话：**HTTPS 做三件事**——加密（内容只有双方能读）、认证（确认对面是真身）、完整性（内容没被篡改）。94% 的页面已全 HTTPS，新项目没有任何理由开 HTTP。

## 2. 证书体系：信任从哪来

### 2.1 信任链

```text
根证书（内置在操作系统/浏览器）——信任的锚
   └─ 中间 CA 证书（根签名）——日常签发用
        └─ 服务器证书（中间 CA 签名）——站点实际使用
             例：Let's Encrypt 根 → ISRG Root X1 → R3 中间 → 你的站点证书
```

| 环节 | 说明 |
|------|------|
| 信任锚 | 操作系统/浏览器内置 ~150 个根 CA |
| 证书链 | 服务器必须下发**完整链**（站点证书 + 中间证书） |
| 验证过程 | 浏览器沿链验证签名，直到信任根；同时校验域名（SAN）、有效期、吊销状态 |
| 吊销检查 | OCSP（在线状态查询）/ CRL（吊销列表） |

> ⚠️ 经典故障：**"证书链不完整"（chain incomplete）**——服务器只发了站点证书没发中间证书，浏览器认不出 → 502/证书错误。部署时务必带上完整链，排障见 [网络问题排查](../../07-工程运维基础/运维/网络问题排查/00-网络问题排查总览.md) 的 TLS 坑。

### 2.2 证书类型

| 类型 | 验证深度 | 签发速度 | 显示 | 适用 |
|------|---------|---------|------|------|
| DV（域名验证） | 只验证域名所有权 | 分钟级 | 锁形图标 | **绝大多数站点**（Let's Encrypt 即 DV） |
| OV（组织验证） | 验证企业真实性 | 天级 | 企业信息 | 企业官网 |
| EV（扩展验证） | 最严格 | 天级+ | 地址栏公司名（已淡化） | 金融/大品牌（浏览器已淡化 EV 标识） |

> 🎯 2026 现状：**DV + 自动签发（ACME）是绝对主流**；EV 的浏览器差异化展示已取消（Chrome 2020 起），EV 商业价值大幅缩水。自签证书只用于内网/开发（可用 Caddy 的本地 CA，见 [Web 服务器 Caddy](../Web%20服务器/03-Caddy与自动HTTPS时代.md)）。

## 3. TLS 1.2 握手：四个来回的往事

```text
TLS 1.2 完整握手（ECDHE 密钥交换，约 2 RTT）：
客户端                        服务器
  │── ClientHello（支持算法/随机数）──>│
  │<─ ServerHello + 证书 + ServerKeyExchange + ServerHelloDone ─│
  │── ClientKeyExchange + ChangeCipherSpec + Finished ──>│
  │<──── ChangeCipherSpec + Finished ────│
  │════ 应用数据（加密）═════════════════│
```

| 步骤 | 内容 |
|------|------|
| ClientHello | 客户端支持的 TLS 版本、加密套件、随机数 |
| ServerHello | 服务端选定套件 + 证书 + ECDHE 参数 |
| 密钥交换 | ECDHE：双方各生成临时密钥对 → 计算共享密钥（**前向保密**） |
| 协商结束 | 双方确认 Finished → 开始加密通信 |
| RSA 模式（旧） | 客户端用服务器公钥加密"预主密钥"——**无前向保密**（私钥泄露则历史流量全解密） |

> 💡 前向保密（Forward Secrecy）：ECDHE 的临时密钥用完即弃——即使服务器私钥未来泄露，也解不开已记录的历史流量。RSA 密钥交换做不到。**TLS 1.3 直接强制 ECDHE，废除了 RSA 密钥交换**。

## 4. TLS 1.3 握手：一个来回的现在

```text
TLS 1.3 完整握手（1 RTT）：
客户端                         服务器
  │── ClientHello（含 key_share：直接带 ECDHE 参数）──>│
  │<── ServerHello（含 key_share）+ 证书 + Finished ──│
  │── Finished ──>│
  │════ 应用数据 ══════════════════════════════════════│

TLS 1.3 会话恢复（0 RTT，PSK）：
  │── ClientHello（带 PSK + early data）──>│
  │════ 首包应用数据直接发出 ════│
```

| TLS 1.3 改进 | 说明 |
|-------------|------|
| **握手 1-RTT** | 客户端预发 ECDHE 参数，少一个来回 |
| **0-RTT 恢复** | PSK（预共享密钥）恢复时首包即数据（有重放风险，只用于幂等请求） |
| 强制前向保密 | 废除 RSA 密钥交换，只留 ECDHE |
| 精简套件 | 去掉旧/弱算法，套件从 37 个减到 5 个（配置更简单） |
| 简化握手 | 移除了不安全的压缩、重协商 |

> 🎯 面试必答：**"TLS 1.3 把握手从 2-RTT 压到 1-RTT（恢复 0-RTT），靠的是客户端预发密钥参数 + PSK 恢复 + 强制前向保密"**——这是 2026 年 70%+ 加密流量的底座。

## 5. TLS 1.2 vs 1.3 对比

| 维度 | TLS 1.2 | TLS 1.3 |
|------|:---:|:---:|
| 完整握手 | 2-RTT | **1-RTT** |
| 会话恢复 | 1-RTT（session ticket） | **0-RTT**（PSK + early data） |
| 前向保密 | 可选（RSA 套件无） | **强制** |
| 加密套件 | 37 个（易配错） | 5 个（简单安全） |
| 支持的密钥交换 | RSA/ECDHE/DHE | 仅 ECDHE/PSK |
| 2026 份额 | ~27-30% | **~70-73%** |
| 兼容 | 老系统必须 | 老客户端不支持（2020 前的极老设备） |

> 💡 部署现实：**同时开启 TLS 1.2 + 1.3**（1.2 给老客户端兜底），关闭 1.0/1.1。生产配置见 [Nginx SSL 章节](../Nginx/10-Nginx-SSL与安全加固.md)。

## 6. 双向 TLS（mTLS）

```text
单向 TLS（HTTPS）：只验证服务器证书（浏览器场景）
双向 TLS（mTLS）：双方互验证书
  客户端 ──ClientHello──> 服务器
  客户端 <──服务器证书── 服务器
  客户端 ──客户端证书──> 服务器（多了这一步！）
  → 服务器验证客户端证书身份后建立连接
```

| 场景 | 说明 |
|------|------|
| 微服务内部通信 | 服务间互认（Service Mesh/Istio 标配） |
| 内部 API 网关 | 凭证书而非口令认证机器 |
| 设备认证 | IoT 设备证书鉴权 |
| 金融/政务专线 | 双向强认证 |

> ⚠️ mTLS 运维成本高（证书发放/轮换/吊销管理），**只用于机器间通信，不用于用户认证**（用户认证走 OAuth/Token）。K8s 场景由 Service Mesh 透明处理。

## 7. HSTS 与安全强化

```http
# 响应头：强制浏览器只走 HTTPS
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

# 效果：
#  · 浏览器记住该域只允许 HTTPS（防止降级攻击/首次 HTTP 劫持）
#  · includeSubDomains：子域一并强制
#  · preload：提交到浏览器内置 HSTS 列表（域名级强制）
```

| 强化项 | 说明 |
|--------|------|
| HSTS | 防"HTTPS 网站被强制降级成 HTTP" |
| **HSTS 部署顺序坑** | 先在"纯 HTTPS 稳定后"再开 preload（否则 HTTP 永远进不来，无法撤销） |
| 证书自动续期 | ACME（Caddy 自动 / certbot） |
| 证书监控 | 到期前告警（续期失败兜底） |

> ⚠️ 反代/网关层统一处理：HSTS 头由**入口层**（Nginx/CDN）下发，应用层不必重复——多一层少一层都行，别冲突。详见 [Nginx 安全头章节](../Nginx/10-Nginx-SSL与安全加固.md)。

## 8. 性能优化与部署要点

| 优化项 | 收益 | 做法 |
|--------|------|------|
| **TLS 1.3** | 少一个 RTT | 升级/配置默认优先 |
| 会话恢复（ticket） | 复用握手结果 | 服务端默认开启（Nginx `ssl_session_cache`） |
| **OCSP Stapling** | 省一次证书状态查询 | Nginx 开启 |
| 会话票据轮换 | 安全性 | 定期轮换 PSK 密钥 |
| 证书链最小化 | 握手包更小 | 只发必要中间证书 |
| ALPN | HTTP/2 协商 | 握手时带上 h2 协议（见 04） |

```nginx
# Nginx TLS 性能三件套
ssl_protocols TLSv1.2 TLSv1.3;
ssl_session_cache shared:SSL:10m;     # 会话缓存
ssl_session_tickets on;               # 会话票据（多节点共享恢复）
ssl_stapling on;                      # OCSP Stapling
```

> 🎯 性能结论：**TLS 在现代硬件上开销 < 5%**（AES-NI/ChaCha20 硬件加速）——"HTTPS 慢"早已是伪命题；真正的延迟大头是 RTT（握手来回），所以 TLS 1.3 + 会话恢复 + HTTP/3（见 [04-HTTP2与HTTP3](04-HTTP2与HTTP3.md)）才是优化主线。
