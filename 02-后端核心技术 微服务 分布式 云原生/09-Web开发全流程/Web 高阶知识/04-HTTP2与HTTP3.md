## 1. HTTP/1.1 的三大痛点

| 痛点 | 表现 | 根源 |
|------|------|------|
| **队头阻塞** | 同一连接请求必须排队（串行） | 请求-响应一一对应，无并发 |
| **连接数上限** | 浏览器单域 6 个连接 | 连接是并发唯一手段 |
| **头部冗余** | 每次请求重复 Cookie/UA 等大头 | 文本协议无压缩（gzip 只压 body） |

```text
HTTP/1.1 的并发假象：
  浏览器开 6 条 TCP 连接 × 每连接串行
  → 100 个资源 = 至少 17 轮串行等待（含握手）
  → 域名分片（static.example.com 等）是当年的"土解法"
```

> 🎯 一个机制解决前两点（多路复用）、一个机制解决第三点（HPACK）——这就是 HTTP/2 的全部。

## 2. HTTP/2 核心机制

### 2.1 二进制帧 + 多路复用

```text
HTTP/1.1（文本）:        HTTP/2（二进制帧）:
GET /a.js ──────┐       一个 TCP 连接 = 多条流（stream）
GET /b.css ─────┤       每条流拆成帧交错传输：
GET /c.png ─────┼────>  [a.js 帧][c.png 帧][b.css 帧][a.js 帧][c.png 帧]...
（6 连接串行）           接收端按流 ID 重组
```

| 概念 | 说明 |
|------|------|
| 帧（Frame） | 最小传输单位（头部帧/数据帧） |
| 流（Stream） | 一个请求-响应 = 一条流（ID 标识） |
| 多路复用 | 单连接上多条流交错传输，互不阻塞 |
| 优先级 | 流可设优先级/依赖（图片让位给关键 JS） |
| 流量控制 | 每流窗口控制（防慢消费拖垮内存） |

### 2.2 HPACK 头部压缩

```text
原理：头字段表 + 哈夫曼编码
  · 静态表：61 个高频头（method:GET 等，1 字节表示）
  · 动态表：连接内增量（Cookie 等大头只传一次，后续引用索引）
  · 单请求头部从 ~800B 压到 ~10B
```

### 2.3 ALPN 协商与 Server Push（已死）

```text
TLS 握手时 ALPN 扩展协商协议：
  客户端："我支持 h2, http/1.1"
  服务端选 h2 → 同一连接直接 HTTP/2（无额外往返）

HTTP/2 Server Push：服务端"主动推"资源 —— 已废弃！
  · 浏览器缓存/资源调度常与推送冲突（推了不用的资源）
  · Servlet 6.1 / Tomcat 11 已移除支持（见 [Servlet 演进](../Servlet/01-规范演进史与版本矩阵.md)）
  · 现代替代：103 Early Hints（提前发 Link 头）与 HTTP/3 推流
```

> 💡 队头阻塞解决到什么程度？HTTP/2 解决了**应用层**队头阻塞（多路复用），但帧仍跑在 TCP 上——TCP 丢包重传仍会阻塞整条连接的所有流，这就是"TCP 队头阻塞"，HTTP/3 要解决它。

## 3. HTTP/2 的遗留问题

| 遗留问题 | 表现 |
|---------|------|
| **TCP 队头阻塞** | 一个包丢失 → 整条连接重传等待 → 所有流全卡 |
| 连接迁移差 | 手机切 Wi-Fi/4G → TCP 连接断开重建（握手 + 慢启动） |
| 握手开销 | TLS 1.3 1-RTT 仍存在（0-RTT 有重放风险） |
| 多路复用放大慢请求 | 一条慢流占连接，需流量控制精调 |

> 🎯 一句话：**HTTP/2 把"应用层队头阻塞"治好了，但"传输层队头阻塞"还在**——因为 TCP 保证有序交付，一个丢包就得等重传。换掉 TCP 才能根治 → QUIC。

## 4. HTTP/3 与 QUIC

```text
HTTP/3 = 把 HTTP/2 的语义搬到 QUIC（UDP 之上）：
  HTTP/2 帧格式（不变）
  QUIC 传输层（取代 TCP+TLS 的组合）
  UDP 承载

QUIC 的四个核心能力：
  ① 独立流：丢包只影响该流（TCP 队头阻塞根治）
  ② 连接迁移：连接 ID 与 4 元组解耦（切网络不断连）
  ③ 内置 TLS 1.3：握手与传输协商合一（1-RTT/0-RTT）
  ④ 0-RTT：重连直接发数据（幂等请求）
```

| QUIC 能力 | 解决的问题 | 场景收益 |
|-----------|-----------|---------|
| 独立流隔离 | TCP 队头阻塞 | 弱网/丢包环境提升显著 |
| 连接迁移 | 移动网络切换 | 手机端体验（地铁/电梯） |
| 内置 TLS 1.3 | 握手往返 | 首屏速度 |
| 0-RTT | 重连延迟 | 高频 API 调用 |

> ⚠️ 0-RTT 的重放风险：早到的数据可能被重放（同一请求发两次）——**0-RTT 只适合幂等请求**（GET/HEAD），服务端对 POST 等非幂等请求应禁用 early data。

## 5. 2026 采用现状

| 指标 | 数据（2026） |
|------|-------------|
| HTTP/2 流量占比 | **~51-55%**（绝对主力） |
| HTTP/3 站点支持率 | **~40%**（W3Techs 2026-08；Top 站点 44-45%） |
| HTTP/3 流量占比 | **~21-34%**（Cloudflare 网络 ~31%，2026-02） |
| HTTP/1.x 占比 | **27.8%**（2026-07 仍存） |
| 浏览器支持 | 全部主流引擎支持 HTTP/3（92-97%+），不支持自动回退 HTTP/2 |

```text
增长放缓的原因：
  · 强网（有线/5G 满信号）下 TCP 吞吐常优于 QUIC（实现成熟度）
  · 大量 bot/老客户端/代理不回退到 3
  · 企业内网基础设施未更新
```

> 🎯 落地结论：**新项目全链路开 HTTP/2（成本为零）；HTTP/3 按环境开**（ToC 移动端/弱网场景收益大，内网/ToB 收益有限）。别被"40% 站点支持"误导——支持 ≠ 流量都走它。

## 6. 升级路径与配置

### 6.1 服务器层（Nginx 示例）

```nginx
# HTTP/2：TLS 上 ALPN 协商，一行配置
server {
    listen 443 ssl http2;          # HTTP/2 随 TLS 自动协商
    http2_push_preload on;         # 可选：103 Early Hints
}

# HTTP/3（QUIC，Nginx 1.25+/主线）
server {
    listen 443 ssl;
    listen 443 quic reuseport;     # QUIC 监听
    http3 on;
    add_header Alt-Svc 'h3=":443"; ma=86400';   # 宣告支持 HTTP/3
}
```

### 6.2 应用层注意事项

| 事项 | 说明 |
|------|------|
| 帧缓冲内存 | 多路复用下并发流多 → 注意内存（Tomcat `http2` 相关配置） |
| 连接复用 | HTTP/2 单连接，连接池概念弱化（JDK HttpClient 自动适配） |
| Server Push | **别再实现**（规范已废弃） |
| 长连接保活 | 连接数少 → 连接级超时配置更重要 |
| 监控 | 按协议版本分桶看指标（HTTP/3 与 2 分开统计） |

> 💡 落地联动：Boot 4 / Tomcat 11 默认支持 HTTP/2（`server.http2.enabled`）；证书与 ALPN 由 [03-HTTPS与TLS深入](03-HTTPS与TLS深入.md) 的 TLS 层负责——HTTP/2 不额外配置即随 TLS 生效。

## 7. 对比总表与选型

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|:---:|:---:|:---:|
| 传输 | TCP | TCP | **UDP（QUIC）** |
| 并发模型 | 多连接串行 | 单连接多路复用 | 单连接多路复用 + 独立流 |
| 队头阻塞 | 连接级 | 应用层解决/TCP 层残留 | **传输层根治** |
| 头部压缩 | 无 | HPACK | QPACK（分流场景优化） |
| 握手 | - | TLS 1.2/1.3 | **内置 TLS 1.3** |
| 连接迁移 | 不支持 | 不支持 | **原生支持** |
| 复杂度 | 低 | 中 | 高（排查工具生态仍在追赶） |
| 2026 流量 | ~11-28% | **~51-55%** | ~21-34% |

```text
选型速记（2026）：
  · 默认：HTTP/2 全开（必选）
  · ToC 移动/弱网：加 HTTP/3（QUIC）
  · 内网/ToB/合规严：HTTP/2 足够
  · 老客户端兜底：ALPN 自动回退（无需人工处理）
```
