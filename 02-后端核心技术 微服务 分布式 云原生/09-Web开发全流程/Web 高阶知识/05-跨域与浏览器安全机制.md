## 1. 同源策略：浏览器的安全基石

```text
同源判定：协议 + 域名 + 端口 三者全同
  https://app.example.com:443          ← 基准
  https://app.example.com:8443   不同源（端口）
  http://app.example.com         不同源（协议）
  https://api.example.com        不同源（域名）
  https://www.example.com        不同源（子域也算）
```

| 同源策略管什么 | 说明 |
|---------------|------|
| DOM 访问 | 跨域脚本不能读写其他源的 DOM |
| Cookie | 按域隔离（+ SameSite 控制跨站） |
| fetch/XHR | **跨域请求默认被拦截**（CORS 放行例外） |
| 存储 | localStorage/IndexedDB 按源隔离 |

> 🎯 面试认知：**同源策略是浏览器（客户端）的安全策略，不是服务器的**——请求实际上发出去了（服务器能看到），只是**响应被浏览器拦截**。所以"服务器没看到请求"是错的，"浏览器不让你读响应"才对。

## 2. CORS 协议全流程

### 2.1 简单请求 vs 预检请求

```text
简单请求（不触发预检）：GET/HEAD/POST + 简单头（Content-Type 限三种）
  浏览器直接发 → 响应里没有 Access-Control-Allow-Origin → 拦截并报错

预检请求（Preflight）：复杂场景（自定义头/JSON Content-Type/PUT 等）
  浏览器先发 OPTIONS 预检：
    OPTIONS /api/users
    Origin: https://app.example.com
    Access-Control-Request-Method: POST
    Access-Control-Request-Headers: authorization,content-type
  服务器回应放行规则：
    Access-Control-Allow-Origin: https://app.example.com
    Access-Control-Allow-Methods: POST,GET,PUT,DELETE
    Access-Control-Allow-Headers: authorization,content-type
    Access-Control-Max-Age: 3600          ← 预检结果缓存 1 小时
  浏览器确认放行后才发真实请求
```

### 2.2 响应头族

| 响应头 | 作用 |
|--------|------|
| `Access-Control-Allow-Origin` | 允许的来源（`*` 或具体源） |
| `Access-Control-Allow-Methods` | 允许的方法 |
| `Access-Control-Allow-Headers` | 允许的请求头 |
| `Access-Control-Expose-Headers` | **允许 JS 读取的响应头白名单** |
| `Access-Control-Allow-Credentials` | 是否允许携带 Cookie（`true`） |
| `Access-Control-Max-Age` | 预检结果缓存秒数 |

> ⚠️ **Expose-Headers 是隐藏坑**：响应头的 `X-Trace-Id`、`X-Total-Count` 默认 JS 读不到（只能读 CORS 安全列表里的 6 个头）——必须 `Access-Control-Expose-Headers: X-Trace-Id, X-Total-Count` 显式放行。

## 3. 预检请求与 Credentials

### 3.1 什么时候触发预检

| 触发条件 | 例子 |
|---------|------|
| 非简单方法 | PUT/DELETE/PATCH |
| 自定义头 | Authorization、X-Custom-* |
| Content-Type 非三种简单值 | application/json |
| 非简单请求头 | Range 之外的自定义 |

### 3.2 Credentials（带 Cookie 的跨域）

```http
# 跨域要带 Cookie（常见于域名不同但共享会话）：
# 请求侧：fetch(url, { credentials: 'include' })
# 响应侧：
Access-Control-Allow-Origin: https://app.example.com   ← 不能是 *
Access-Control-Allow-Credentials: true                 ← 必须显式开

# ⚠️ 双限制：Allow-Origin 用 * 时 + Credentials 浏览器直接拒绝
```

> 🎯 安全铁律：**`Access-Control-Allow-Origin: *` 与 `Credentials: true` 不能同时用**（浏览器强制）——生产 CORS 必须是具体白名单源，别用 `*` 图省事。参考 [SpringBoot Web CORS 配置](../SpringBoot%20Web/03-WebMvcConfigurer定制全解.md)。

## 4. CORS 常见配置错误

| # | 错误 | 现象 | 解法 |
|:---:|------|------|------|
| 1 | Allow-Origin 配 `*` | 带凭据请求失败 | 白名单 + 动态回显 Origin |
| 2 | 预检被拦截（401） | 网关/Filter 拦了 OPTIONS | 预检请求直接放行 204 |
| 3 | 忘了 Expose-Headers | JS 读不到自定义头 | 显式暴露 |
| 4 | 两层都配 CORS | 预检重复/冲突 | 网关与应用二选一 |
| 5 | 回显 Origin 未校验 | 任意站点可带凭据 | 白名单校验后回显 |
| 6 | Max-Age 不配 | 每次请求都预检 | 配 3600+ 缓存 |

> ⚠️ 预检与安全框架的经典冲突：Spring Security/Nginx auth 默认会拦 OPTIONS 预检 → 需要显式放行（`DisallowPreflightRequests` 关 / 白名单）。排查顺序：DevTools 看是"预检失败"还是"真实请求被拦"。

## 5. SameSite 与 CSRF 的边界

```text
同源（Same-Origin）：协议+域名+端口
同站（Same-Site）：仅注册域（eTLD+1，端口协议无关）
  · https://app.example.com 与 https://api.example.com 是"同站不同源"
  · SameSite 管的是"跨站"，CORS 管的是"跨源"
```

| SameSite 值 | Cookie 携带行为 | 防什么 |
|------------|----------------|--------|
| `Lax`（默认） | 顶级导航（链接跳转）带，跨站子请求不带 | 防 CSRF（表单/图片/iframe 触发的跨站请求） |
| `Strict` | 跨站一律不带 | 最严（用户体验损失：外站链接进来是未登录态） |
| `None; Secure` | 跨站也带（必须 HTTPS） | 第三方登录/单点登录场景才用 |

> 🎯 分工认知：**CORS 管"响应能不能读"，SameSite 管"Cookie 带不带"**——两者都是 CSRF 防线的一部分。SameSite=Lax 默认值已挡掉绝大多数 CSRF（跨站表单自动请求不带 Cookie）；完整 CSRF 防线（Token 双重验证）见 [会话安全体系](../Cookie%20%26%20Session（会话技术）/05-会话安全与防护.md) 与 [07-Web安全攻防](07-Web安全攻防.md)。

## 6. 浏览器安全响应头全解

```http
# 生产必配安全头六件套
Strict-Transport-Security: max-age=31536000; includeSubDomains    # 强制 HTTPS（见 03）
Content-Security-Policy: default-src 'self'; script-src 'self'    # 内容白名单
X-Content-Type-Options: nosniff                                   # 禁止 MIME 嗅探
X-Frame-Options: DENY                                             # 禁止被 iframe 嵌入
Referrer-Policy: strict-origin-when-cross-origin                  # 控制来源信息外泄
Permissions-Policy: geolocation=(), camera=()                     # 禁敏感 API
```

| 头 | 防什么 | 要点 |
|----|--------|------|
| **CSP** | XSS 与注入 | 最强大也最容易配错（先 report-only 观察再强制） |
| X-Content-Type-Options | 类型混淆攻击 | 一行解决 |
| X-Frame-Options | 点击劫持 | `frame-ancestors`（CSP 2.0）可替代 |
| Referrer-Policy | 信息泄露 | 默认 `strict-origin-when-cross-origin` |
| Permissions-Policy | 权限滥用 | 按需禁用摄像头/定位等 |

```http
# CSP 示例（前端 SPA 场景）
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.example.com;   # 脚本白名单
  style-src 'self' 'unsafe-inline';            # 内联样式（必要时）
  img-src 'self' data: https:;                 # 图片来源
  connect-src 'self' https://api.example.com;  # fetch/XHR 目标
  frame-ancestors 'none'                       # 禁 iframe 嵌入
```

> ⚠️ CSP 上线三步：**① 只加 CSP 头观察（report-only）→ ② 收集违规报告 → ③ 修正白名单后强制**。直接强制上线大概率把业务打挂（内联脚本/外部 CDN 被拦）。

## 7. 消灭跨域：反代同域方案

```text
终极方案：让"跨域"不存在
  浏览器 → 同域 Nginx → /api/* 反代到后端（源站换 Host 头即可）
  
  app.example.com/       → SPA 静态资源（Nginx 托管）
  app.example.com/api/   → 反代到 api 集群（浏览器视角同域！）

  收益：
  · 零 CORS 配置（同源没有预检没有白名单）
  · Cookie 天然同域可带（SameSite 无冲突）
  · 少一次跨域排查面
```

| 方案 | 适用 | 代价 |
|------|------|------|
| **反代同域**（推荐） | 自有前端 + 自有后端 | 无（标准架构） |
| CORS 白名单 | 第三方前端/开放 API | 配置与安全面 |
| JSONP（历史） | 只 GET、防 CSRF 差的遗留 | 已淘汰 |

> 🎯 结论：**能同域就同域**（Nginx 反代或网关统一入口，见 [Nginx 体系](../Nginx/00-Nginx知识体系总览.md)）；CORS 留给"确实跨域"的场景（开放平台、第三方嵌入）。"为什么前后端分离还要配 CORS"——因为域名没统一，架构上先解决域名再谈 CORS。
