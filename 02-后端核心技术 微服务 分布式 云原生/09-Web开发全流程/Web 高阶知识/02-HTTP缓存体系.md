## 1. 缓存位置全景

```text
请求 → 浏览器缓存（内存/磁盘）→ 代理/CDN 缓存 → 源站（应用）
         │ 命中：0 网络请求      │ 命中：就近返回
         └── 由响应头决定 ────────┘
```

| 缓存位置 | 谁控制 | 典型 | 命中效果 |
|---------|--------|------|---------|
| 浏览器内存缓存 | Cache-Control | 当前会话资源 | 0 请求 0 网络 |
| 浏览器磁盘缓存 | Cache-Control + 磁盘 | 跨会话资源 | 0 请求 |
| 中间代理缓存 | s-maxage/public | 企业代理 | 局域网内 0 回源 |
| **CDN 边缘缓存** | s-maxage / CDN 规则 | 静态资源/图片 | 就近节点返回 |
| Service Worker | 应用代码 | PWA/离线 | 完全可控 |

> 🎯 核心思维：**缓存是"空间换带宽"的分层体系**——最贵的请求（回源到应用）由最外层（CDN/浏览器）拦截；设计目标 = 让每个资源在"正确的位置"缓存"正确的时间"。

## 2. 强缓存：不发请求

```http
# 响应头示例
Cache-Control: max-age=3600        # 1 小时内直接使用缓存，不发任何请求
Expires: Wed, 08 Aug 2026 12:00:00 GMT   # 老字段（HTTP/1.0），被 max-age 覆盖
```

```text
强缓存命中流程：
浏览器有缓存副本，且 max-age 未过期 → 直接用副本
  · 无网络请求（DevTools Network 显示 "from disk cache"/"from memory cache"）
  · 服务器完全不知情（不产生日志/流量）
```

> ⚠️ 强缓存的"坑"：**过期时间内的更新客户端永远看不到**——所以"改了文件但用户还在用旧版"几乎都是强缓存问题。解法只有一个：**内容变则 URL 变**（见 §7 版本化）。

## 3. 协商缓存：304 免传输

```http
# 第一次响应
HTTP/1.1 200 OK
ETag: "a1b2c3"                     # 资源指纹（内容哈希/版本号）
Last-Modified: Tue, 05 Aug 2026 08:00:00 GMT

# 后续请求（浏览器自动带上）
GET /app.js HTTP/1.1
If-None-Match: "a1b2c3"            # ETag 优先
If-Modified-Since: Tue, 05 Aug 2026 08:00:00 GMT

# 未变化 → 304（无 body，浏览器用缓存副本）
HTTP/1.1 304 Not Modified
```

| 字段对 | 原理 | 优先级 | 缺陷 |
|--------|------|:---:|------|
| `ETag` / `If-None-Match` | 强校验：内容指纹 | **高** | 弱 ETag 需计算成本 |
| `Last-Modified` / `If-Modified-Since` | 弱校验：修改时间 | 低 | 秒级粒度、内容还原可能不同 |

> 🎯 面试点：**为什么 ETag 优先于 Last-Modified？** ① 时间只有秒级粒度（同秒修改无法区分）；② 时间相等 ≠ 内容相同（内容回滚/代理改写）；③ ETag 是强校验（内容变一定变），Last-Modified 是弱校验。304 仍然**发请求**（只是省 body）——与强缓存"不发请求"本质不同。

## 4. Cache-Control 全参数

| 指令 | 语义 | 典型值 |
|------|------|--------|
| `max-age=<秒>` | **强缓存时长**（相对时间） | `max-age=2592000`（30 天） |
| `s-maxage=<秒>` | CDN/共享代理缓存时长（覆盖 max-age） | `s-maxage=600` |
| `no-cache` | **每次请求都要重新验证**（允许缓存，但用前验证） | 动态 HTML |
| `no-store` | **禁止任何缓存**（敏感数据） | 订单/支付响应 |
| `public` | 任何缓存（含 CDN/代理）可存 | 静态资源 |
| `private` | 仅浏览器可缓存（代理不可） | 个性化页面 |
| `must-revalidate` | 过期后必须回源验证，不得用过期副本 | 强缓存到期语义 |
| `stale-while-revalidate` | 过期后先用旧副本，同时后台刷新 | 体验优化 |
| `immutable` | 内容永不变化（配合版本化 URL） | `max-age=31536000, immutable` |

```http
# 组合示例（一套典型生产策略）
静态资源：Cache-Control: public, max-age=31536000, immutable
HTML 页面：Cache-Control: no-cache                    # 每次协商
API 数据： Cache-Control: no-store                    # 敏感不缓存
CDN 接口： Cache-Control: public, s-maxage=60         # 边缘缓存 60s
```

> ⚠️ 语义易混三连：`no-cache`（**要验证**，不是不缓存）、`no-store`（**真不缓存**）、`immutable`（**永不验证**）。`no-cache` 是最被误解的指令——它的意思是"缓存可以存，但每次用之前必须回源确认"。

## 5. 启发式缓存与历史机制

```text
无任何缓存头时的浏览器行为（启发式缓存）：
  HTTP/1.0 时代响应没有 Cache-Control
  → 浏览器用 Last-Modified 推算："距上次修改多久，就缓存多久的 10%"
  → 不可控！可能缓存到不该缓存的页面
```

| 历史机制 | 说明 | 现状 |
|---------|------|------|
| `Expires` | HTTP/1.0 绝对时间 | 被 max-age 取代（时钟偏移问题） |
| `Pragma: no-cache` | HTTP/1.0 禁用缓存 | 兼容遗留 |
| 启发式缓存 | 无头时按 Last-Modified 猜测 | **不可靠，生产必须显式设置** |

> 💡 教训：**生产响应永远显式带 Cache-Control**——依赖浏览器"猜"缓存是事故源头（页面被缓存成旧版、数据被缓存泄漏）。

## 6. 缓存策略设计

| 资源类型 | 策略 | 原因 |
|---------|------|------|
| 版本化静态资源（app.abc123.js） | `public, max-age=31536000, immutable` | 内容变 URL 变，可永久缓存 |
| 未版本化静态资源 | `no-cache` 或短 max-age | 无法区分版本 |
| HTML（入口页） | `no-cache` | 需感知最新资源引用 |
| API 查询接口 | 按场景：`no-store` / 短 `s-maxage` | 数据一致性 |
| 图片/媒体 | `max-age=30d` + 版本化 | 大文件收益最高 |
| 支付/敏感接口 | `no-store` | 安全红线 |

```yaml
# Spring Boot 落地（对应策略）
spring:
  web:
    resources:
      cache:
        cachecontrol:
          max-age: 30d            # 静态资源 30 天
          cache-public: true
      chain:
        strategy:
          content:
            enabled: true         # 内容哈希版本化
```

> 🎯 设计铁律：**缓存策略 = 资源类型 × 更新频率 × 一致性要求**。三个维度定了，策略表直接照抄；别对"统一缓存策略"心存幻想——HTML、JS、API 的缓存语义天然不同。落地配置见 [SpringBoot Web 静态资源](../SpringBoot%20Web/06-静态资源与SPA路由.md) 与 [Nginx 缓存章节](../Nginx/06-Nginx-缓存与优化.md)。

## 7. 缓存更新：版本化是钥匙

```text
版本化的本质：内容与 URL 绑定。
  内容变了 → 文件名变（哈希/版本号）→ 新 URL → 新缓存条目
  旧 URL 继续被旧缓存服务（无害），新 URL 拉新内容

构建工具自动完成（Vite/Webpack）：
  app.js → app.a1b2c3.js（内容哈希）
  index.html 里引用自动更新
```

| 方式 | 例子 | 适用 |
|------|------|------|
| 内容哈希（推荐） | `app.a1b2c3.js` | 构建产物 |
| 版本号 | `app-v2.js` | 手动控制 |
| 查询参数（不推荐） | `app.js?v=2` | 部分 CDN 不缓存带 ? 资源 |

> ⚠️ 反模式警告：**"清了缓存才能看到新版本"是缓存设计失败的标志**。正确设计下，发布新版本无需用户清缓存（HTML no-cache + 资源版本化）。面试答"如何解决缓存更新问题"的标准答案就是版本化 URL。

## 8. 常见缓存问题排障

| 现象 | 根因 | 解法 |
|------|------|------|
| 改了代码用户还是旧版 | 资源未版本化 + 长缓存 | 版本化 URL（§7） |
| 页面内容突然过期闪烁 | 无缓存头 → 启发式缓存 | 显式 Cache-Control |
| 接口数据被缓存 | API 响应可被缓存（200） | no-store 或 s-maxage 收紧 |
| 登录后还是旧数据 | 私有数据被代理缓存 | `private` 而非 `public` |
| 304 但想强缓存 | 协商缓存每次请求 | 版本化 → 长 max-age |
| CDN 缓存不更新 | CDN 规则未对齐 s-maxage | 检查 CDN 缓存规则 |

> 🎯 排障工具：DevTools Network（看 Size 列的 `from cache`/304 与响应头）→ `curl -I` 看实际头 → 逐层检查（浏览器→CDN→源站）。与 [网络问题排查](../../07-工程运维基础/运维/网络问题排查/00-网络问题排查总览.md) 的 HTTP 层方法配套。
