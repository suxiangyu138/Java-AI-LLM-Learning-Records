## 1. 生产化检查清单

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | 镜像固定版本 | 生产禁止 `latest`；用 `my-app:1.0.3` |
| 2 | 敏感信息环境变量化 | 密码走 `.env`（不入 Git）或 secrets；YAML 零硬编码 |
| 3 | 资源限制 | `deploy.resources.limits` + JVM `-Xmx` ≤ 容器内存 80% |
| 4 | 健康检查 | 每个服务配 healthcheck + `start_period`（慢启动应用） |
| 5 | 依赖就绪 | `depends_on` 用 `condition: service_healthy` |
| 6 | 日志轮转 | `logging.options.max-size` + `max-file`（防磁盘写满） |
| 7 | 重启策略 | `restart: unless-stopped` |
| 8 | 数据持久化 | 有状态服务（MySQL/Redis）挂命名卷；`external: true` 防误删 |
| 9 | 网络隔离 | DB/Redis 放 `internal: true` 网络，仅 app 暴露端口 |
| 10 | 版本字段 | 移除已废弃的 `version:` 字段 |
| 11 | 镜像安全 | 来自私有 Registry + 漏洞扫描（见上级 `../04-镜像发布与仓库分发.md`） |
| 12 | 配置验证 | `docker compose config` 输出无误再上线 |

```yaml
# 生产核心服务模板（要点）
services:
  app:
    image: registry:5000/order-app:${APP_VERSION}
    restart: unless-stopped
    depends_on:
      db: { condition: service_healthy }
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/actuator/health"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 40s
    deploy:
      resources:
        limits: { cpus: '1', memory: 1G }
    logging:
      options: { max-size: "10m", max-file: "3" }
    environment:
      DB_PASSWORD: ${DB_PASSWORD:?必须设置}
```

## 2. 生产部署流程

```text
① 构建镜像（多阶段 Dockerfile）→ 推送私有 Registry
② 服务器拉取 compose 文件 + .env（.env 不入 Git，手动放置）
③ docker compose -f compose.yaml -f compose.prod.yaml config    # 验证
④ docker compose -f compose.yaml -f compose.prod.yaml pull      # 预拉取
⑤ docker compose -f compose.yaml -f compose.prod.yaml up -d     # 启动
⑥ docker compose ps + curl health 验证                          # 验证
⑦ 更新：pull 新镜像 → up -d（自动重建配置变化的服务）
```

```bash
# 更新发布（镜像变化自动重建）
docker compose pull app
docker compose up -d app

# 回滚
docker compose up -d app@sha256:旧镜像摘要   # 或直接改回旧版本号
```

## 3. Compose Bridge：转换 Kubernetes 清单

Compose 到 K8s 的官方转换工具：

```bash
docker compose convert --format kubernetes -f compose.yaml
# 生成：Deployment / Service / PersistentVolumeClaim / ConfigMap / Secret / Ingress
```

| 映射关系 | Compose | Kubernetes |
|----------|---------|------------|
| 服务 | services | Deployment + Service |
| 卷 | volumes | PersistentVolumeClaim |
| 配置 | configs | ConfigMap |
| 敏感数据 | secrets | Secret |
| 端口 | ports | Service（NodePort/LoadBalancer） |
| 健康检查 | healthcheck | liveness/readinessProbe |
| 依赖 | depends_on | initContainer（迁移类） |

```bash
# 使用场景
# ① 本地 → 云上迁移：本地 Compose 验证 → convert → kubectl apply
# ② CI/CD 多环境：同一套 Compose 定义转 K8s 清单
# ③ 学习映射：直观对比两套声明式配置
```

> 💡 **注意**：转换不是 100% 等价——`extends`、`profiles`、部分字段需手动调整；转换结果是迁移**起点**而非终点。

## 4. Compose 与 Swarm / K8s 的定位

| 维度 | Compose（单机） | Swarm（多机轻量） | K8s（企业级） |
|------|----------------|-------------------|---------------|
| 节点数 | 1 | 3-10 | 10+ |
| 复杂度 | 低 | 中 | 高 |
| 自动扩缩 | ❌（手动 scale） | ✅ service scale | ✅ HPA |
| 自愈 | ✅ restart | ✅ 跨节点调度 | ✅ 完整 |
| 滚动更新 | 手动 | ✅ service update | ✅ rollout |
| 适用 | **开发/测试/小型生产** | 中小型生产 | 大型/云原生 |

> 🎯 **2026 定位**：profiles、watch、GPU 支持、Bake 集成让 Compose 能扛**单节点**的生产级工作负载——只要适合单节点，Compose 足够；超过单节点再上 Swarm/K8s。

## 5. 故障排查三板斧

```bash
# 第 1 板斧：状态与配置
docker compose ps                          # 服务状态（Up/Exit/healthy/unhealthy）
docker compose config                      # 合并后配置是否如预期
docker compose config --services           # 服务列表

# 第 2 板斧：日志与进程
docker compose logs -f app                 # 应用日志（报错现场）
docker compose logs --tail=200 app         # 只看末尾
docker compose top app                     # 容器内进程
docker compose exec app bash               # 进入容器排查

# 第 3 板斧：资源与网络
docker compose ps --format "table {{.Name}}\t{{.Status}}\t{{.Ports}}"   # 端口映射核对
docker network inspect <network>           # 网络成员与 IP
docker compose exec app ping db            # 连通性
docker compose exec db mysqladmin ping     # 依赖就绪
```

## 6. 高频故障速查表

| # | 现象 | 成因 | 解决 |
|---|------|------|------|
| 1 | 服务一直 `starting`（不 healthy） | healthcheck 配置错误或应用慢启动 | `docker compose ps` 看状态；调 `start_period`；`docker inspect` 看 Health 日志 |
| 2 | app 连接 db 失败 | depends_on 未用 service_healthy | 长语法 + condition: service_healthy |
| 3 | 端口被占用 | 其他容器/进程占用 | 换映射端口；`ss -tlnp` 排查 |
| 4 | 卷权限 denied | 挂载目录权限不足 | 宿主机 `chmod`；或容器内 `runAsUser` 匹配 |
| 5 | 变量为空/未替换 | .env 未在同目录；变量名拼写 | `docker compose config` 看插值结果；`--no-env-resolution` 对比 |
| 6 | 服务没启动（无报错） | 在 profile 中但未激活 | `--profile xxx up`；`COMPOSE_PROFILES` 检查 |
| 7 | 重建不生效 | 配置未变化（缓存哈希相同） | `up -d --force-recreate`；或改配置 |
| 8 | 日志占满磁盘 | 未配 max-size | 加 logging options；清理 `/var/lib/docker/containers` 大日志 |
| 9 | 时间不一致 | 容器未设时区 | 所有服务 `TZ: Asia/Shanghai`；JVM 同步 |
| 10 | watch 不触发 | 服务无 build 属性 / 路径错 | 仅 build 服务生效；检查 `path` 相对路径与 ignore |

## 7. 面试题

| 题目 | 答题要点 |
|------|---------|
| Compose 与 docker run 的区别？ | 声明式 vs 命令式：多容器编排、配置版本化、依赖管理 |
| depends_on 的三种 condition？ | service_started（顺序）/ service_healthy（就绪）/ service_completed_successfully（一次性任务） |
| Compose 多文件合并规则？ | 后覆盖前；标量覆盖、序列按索引、映射按 key；`config` 验证 |
| profiles 解决什么问题？ | 可选服务按需启动（监控/调试/测试库），一份文件多场景 |
| Watch 三种 action 怎么选？ | 源码 sync、依赖清单 rebuild、启动期配置 sync+restart |
| Compose 能上生产吗？ | 单节点可以：固定版本/健康检查/资源限制/日志轮转/网络隔离齐全即可 |
| Compose 怎么迁移 K8s？ | Compose Bridge：`docker compose convert --format kubernetes`；映射表（Deployment/Service/PVC/ConfigMap/Secret） |
| 环境变量插值与 .env？ | `${VAR:-def}` 默认值、`.env` 只做插值不注入容器、`env_file` 才是注入 |

## 8. 核心要点

> 🎯 **核心要点**：
> - 生产 12 项清单：版本固定、密码环境变量化、资源+JVM 匹配、healthcheck+start_period、service_healthy、日志轮转、unless-stopped、external 卷、internal 网络、去 version 字段、镜像扫描、config 验证；
> - 部署六步：build → 放文件 → config 验证 → pull → up → 验证；更新靠 pull+up 自动重建；
> - 迁移 K8s 用 Compose Bridge（转换是起点，非终点）；
> - 排查三板斧：ps（状态）→ logs（报错）→ exec/网络（根因）；
> - 定位：单节点生产 Compose 够用，超单节点上 Swarm/K8s。
