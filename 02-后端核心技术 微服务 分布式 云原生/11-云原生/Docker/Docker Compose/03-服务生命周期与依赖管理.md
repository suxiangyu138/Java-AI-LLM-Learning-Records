## 1. up / down / start / stop 语义对比

| 命令 | 做什么 | 容器 | 网络 | 卷 | 适用 |
|------|--------|:---:|:---:|:---:|------|
| `docker compose up -d` | 创建缺失资源 + 启动/重建 | 创建/重建 | 创建 | 创建 | **日常启动** |
| `docker compose start` | 仅启动已存在的停止容器 | 不动 | 不动 | 不动 | 快速恢复 |
| `docker compose stop` | 停止所有容器（不删除） | 保留 | 保留 | 保留 | 暂停环境 |
| `docker compose down` | 停止 + 删除容器和网络 | **删除** | **删除** | 保留 | 清理环境 |
| `docker compose down -v` | 停止 + 删除容器/网络/卷 | 删除 | 删除 | **删除** | ⚠️ 彻底清理（丢数据） |
| `docker compose down --remove-orphans` | 清理非本文件管理的容器 | 删除孤儿 | - | - | 残留清理 |

> ⚠️ **数据红线**：`down` 保留卷（数据不丢）；`down -v` 删除卷（**数据库数据丢失**）。`restart`/`stop`/`start` 全程不动卷。

## 2. 容器重建规则

`up` 何时重建容器：

```text
① 镜像 ID 变化（image 标签指向新镜像 / 重新 build）
② 服务配置变化（ports/environment/volumes/command 等任一字段变化）
③ 强制重建：docker compose up -d --force-recreate
④ 不重建：docker compose up -d --no-recreate（仅启动缺失的）
```

| 场景 | 行为 |
|------|------|
| 改了 environment 后 `up -d` | 容器重建（配置变化检测） |
| 改了卷内容（未改配置） | **不重建**，卷数据保留 |
| 重新 `build` 后 `up -d` | 镜像 ID 变化 → 重建 |
| 只改 `.env` 变量值 | 变量插值变化 → 配置变化 → 重建 |

> 💡 **判断重建与否**：`docker compose up -d` 输出的 `Recreating xxx` / `Starting xxx` 字样——理解"配置哈希"决定是否重建，是 Compose 心智模型的核心。

## 3. healthcheck：健康检查完整参数

```yaml
services:
  app:
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/actuator/health"]
      # 或 ["CMD-SHELL", "curl -f http://localhost:8080/actuator/health || exit 1"]
      interval: 30s        # 检查间隔（默认 30s）
      timeout: 3s          # 单次检查超时（默认 30s）
      retries: 3           # 连续失败几次判为 unhealthy（默认 3）
      start_period: 40s    # 启动宽限期：期间失败不计入 retries（默认 0）
      start_interval: 5s   # 启动期间检查间隔（可选，v2.19+）
      disable: false       # 禁用健康检查
```

| 参数 | 默认 | 语义 |
|------|------|------|
| `interval` | 30s | 两次检查的间隔 |
| `timeout` | 30s | 单次检查超时即失败 |
| `retries` | 3 | 连续失败 N 次 → unhealthy |
| `start_period` | 0 | **启动宽限期**：慢启动应用（Spring Boot）必须配置，否则启动即被误判 |
| `start_interval` | interval | 宽限期内更密集的检查（可选） |

> 💡 **Java 实践**：Spring Boot 需引入 `spring-boot-starter-actuator`，检查 `/actuator/health`；`start_period` 建议 ≥ 应用实际启动时间（30-60s），避免启动期间被误判重启。

**状态查看**：

```bash
docker compose ps                      # 显示 healthy / unhealthy / starting
docker inspect <container> --format '{{.State.Health.Status}}'
```

## 4. restart 策略

| 策略 | 行为 | 适用 |
|------|------|------|
| `no` | 不自动重启（默认） | 一次性任务 |
| `always` | 任何退出都重启 | 数据库等核心服务 |
| `on-failure` | 仅非零退出码重启 | 应用服务（崩溃自愈） |
| `unless-stopped` | 除手动 stop 外都重启 | **生产推荐**（兼顾手动维护） |

```yaml
services:
  app:
    restart: unless-stopped
  worker:
    restart: on-failure
    # 限制重启次数（可选）：重启间隔
    deploy:
      restart_policy:
        condition: on-failure
        delay: 5s
        max_attempts: 5
```

> 💡 `restart`（顶层）与 `deploy.restart_policy`（Swarm 部署时生效）是两套机制：单机 `up` 用顶层，Swarm 用 deploy。

## 5. depends_on + healthcheck 组合实战

```yaml
services:
  app:
    image: my-app:1.0
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    # 应用自身也配健康检查（供上层依赖/编排判断）
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8080/actuator/health"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 40s

  db:
    image: mysql:8.0
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-u", "root", "-p123456"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
```

```text
启动时序（组合效果）：
redis 容器启动 → 健康检查通过 → db 容器启动 → 健康检查通过
→ app 容器启动 → 自身健康检查 → 全部 healthy 完成
```

## 6. 资源限制：deploy 与顶层写法

### 6.1 单机 Compose（顶层 deploy 也可用，但语义为"仅 Swarm 生效"）

```yaml
services:
  app:
    deploy:
      resources:
        limits:
          cpus: '1'            # 最多 1 核
          memory: 1G           # 最多 1G
        reservations:
          cpus: '0.5'
          memory: 512M
```

> ⚠️ **注意**：`deploy.resources` 官方语义是 Swarm 部署时生效；单机 `docker compose up` 在部分版本不强制。单机可靠做法：`docker compose up --compatibility` 或直接在服务级使用运行时限制。

### 6.2 内存限制与 JVM 匹配（Java 核心）

```yaml
services:
  app:
    image: my-app:1.0
    environment:
      JAVA_OPTS: "-Xms512m -Xmx1g -XX:+UseContainerSupport"
    deploy:
      resources:
        limits:
          memory: 1G     # 容器 1G，JVM Xmx 1G（≤80% 更安全：Xmx 800M）
```

> 💡 铁律：`Xmx ≤ 容器内存的 80%`——容器 1G 配 `-Xmx800m`（详见上级 `../08-Docker安全与资源限制.md`）。

## 7. 一次性任务服务（run / 迁移）

```yaml
services:
  migrate:
    image: flyway/flyway
    command: migrate
    volumes:
      - ./sql:/flyway/sql
    depends_on:
      db:
        condition: service_healthy

  app:
    image: my-app:1.0
    depends_on:
      migrate:
        condition: service_completed_successfully   # 迁移完成才启动应用
```

```bash
# 手动运行一次性命令
docker compose run --rm migrate          # 运行后删除容器
docker compose run --rm app bash         # 进入应用容器调试
docker compose run --rm -e DEBUG=true app  # 覆盖环境变量
```

| 命令 | 说明 |
|------|------|
| `docker compose run <service>` | 运行一次性任务（不依赖 up 的状态） |
| `--rm` | 运行结束自动删除容器（推荐） |
| `--service-ports` | 启用服务的端口映射（调试场景） |
| `docker compose exec <service> <cmd>` | 在运行中的容器内执行命令 |

## 8. 核心要点

> 🎯 **核心要点**：
> - 生命周期五命令：up（创建+启动）、start/stop（不动资源）、down（删容器网络）、down -v（删卷=丢数据）；
> - 重建规则：镜像 ID 或配置哈希变化才重建；卷数据永不因重建丢失；
> - healthcheck 五参数：`start_period` 是慢启动应用的救命参数（Spring Boot 必配）；
> - restart 生产首选 `unless-stopped`（可手动维护）；崩溃自愈用 `on-failure`；
> - 依赖三件套：`depends_on(service_healthy)` + 依赖方 healthcheck + 一次性迁移服务 `service_completed_successfully`；
> - Java 资源铁律：Xmx ≤ 容器内存 80%。
