## 1. 原生复制：设计

### 1.1 什么是原生复制

```text
Pulsar 的跨地域复制：
  复制是"命名空间的属性"（不是外部组件）

机制：
  租户注册到多个集群（allowed-clusters）
  命名空间设置复制集群（set-clusters）
  → 该命名空间的 topic 自动跨集群复制

对比 Kafka：
  Kafka：MirrorMaker 2（外部组件，独立集群）
  Pulsar：复制内建（namespace 属性）
  → 运维简单（无需独立复制集群）
```

### 1.2 复制的定位

```text
复制的类型：
  异步复制（默认）：本地 ack 后后台复制
  同步复制（PIP-37）：跨区域同步写（极少用）

一致性：
  异步 = 最终一致（AP 优先）
  区域内：分区内线性一致
  跨区域：最终一致（可观测 backlog）

适用：
  多活（多区域写入）
  容灾（热备）
  数据就近（读优化）
```

> 🎯 核心认知：**复制是 Pulsar 的内建能力**——配置 namespace 的集群列表即可，无需部署外部复制组件（对比 Kafka MirrorMaker）。异步复制默认（AP），区域内线性一致，跨区域最终一致——这是"可用性优先"的设计选择。

## 2. 复制机制

### 2.1 复制流程

```text
复制的执行（broker 内建）：
  源集群 broker 内启动"复制线程"（replicator）：
    ① 作为源集群的内部消费者（消费本地 topic）
    ② 作为目标集群的内部生产者（写入目标 topic）
  目标 broker 写入本地 BookKeeper

防环机制：
  复制消息带 replicatedFrom 属性
  → 收到已复制消息的集群不再转发（避免循环）

拓扑：
  全网格（mesh）时 replicatedFrom 防止 A→B→A 循环
```

### 2.2 配置步骤

```bash
# ① 注册集群
pulsar-admin clusters create us-east \
  --url http://us-east-broker:8080
pulsar-admin clusters create eu-west \
  --url http://eu-west-broker:8080

# ② 租户允许两个集群
pulsar-admin tenants create orders \
  --allowed-clusters us-east,eu-west

# ③ 命名空间启用复制
pulsar-admin namespaces set-clusters orders/us-east \
  --clusters us-east,eu-west

# ④ （Pulsar 4.0+）按 topic 覆盖复制（合规场景）
pulsar-admin topics set-replication-clusters \
  persistent://orders/us-east/sensitive-topic \
  --clusters us-east
# 敏感 topic 只在本地（不复制）
```

### 2.3 复制的一致性细节

```text
复制语义：
  至少一次（at-least-once）
  顺序：同分区内有序复制（源端顺序保持）

观察与监控：
  pulsar_replication_backlog（复制积压）
  → 跨区域延迟可观测（最终一致）

限流：
  namespace 级复制限流（保护 WAN）
  per-namespace replication dispatch-rate

生产建议：
  复制积压监控（WAN 延迟/故障信号）
  区域间带宽规划（复制流量）
```

## 3. 复制拓扑

### 3.1 四种拓扑

| 拓扑 | 结构 | 适用 |
|------|------|------|
| 全网格（Mesh） | N×(N−1) 条链路 | 2-3 区域多活（带宽允许） |
| 中心辐射（Hub-and-Spoke） | 2×(N−1) 条链路 | 4+ 区域（线性扩展） |
| 主备（Active-Passive） | 单向复制 | 容灾（1 写区域） |
| 汇聚（Aggregated） | 边缘 → 中心 | 分析汇聚（只读中心） |

```text
拓扑选择（2026 建议）：
  1 个写区域 → Active-Passive（容灾热备）
  2-3 区域 → Mesh（多活，带宽允许）
  4+ 区域 → Hub-and-Spoke（链路数线性）
  分析场景 → Aggregated（边缘推中心）

核心权衡：
  Mesh：延迟低但链路多（N²）
  Hub：链路少但中心瓶颈（转发跳数）
  → 按区域数与带宽规划
```

### 3.2 多活模式（Active-Active）

```text
多活（多区域可写）：
  各区域独立接收写入（本地 ack）
  复制到其他区域（异步）

冲突处理：
  同 topic 多区域写入 → 消息都有（不同消息）
  顺序：各区域本地顺序（跨区域无全局序）
  → 业务需处理（如订单 ID 全局唯一）

适用：
  IoT（设备就近写）
  用户就近（低延迟写）
  计费/订单（区域独立 + 全局聚合）
```

### 3.3 主备模式（DR）

```text
主备（容灾热备）：
  主区域写入 + 复制到备区域
  备区域只读（或可切主）

故障切换（DR 流程）：
  ① 主区域故障检测
  ② 流量切换（DNS/LB → 备区域）
  ③ 备区域提升为主（继续服务）

恢复：
  主区域恢复 → 反向复制/切回
  → 注意消息回流的处理（replicatedFrom）

2026 建议：
  备区域元数据本地化（不跨 WAN）
  复制积压监控（DR 就绪度）
  定期演练（故障切换验证）
```

## 4. Replicated Subscriptions

### 4.1 问题：跨区域消费

```text
跨区域消费的挑战：
  消费者在 A 区域消费 → 故障 → 切到 B 区域
  B 区域的订阅游标在哪？
  → 无复制：B 从头消费（重复处理）

Replicated Subscriptions：
  订阅游标状态跨集群复制（周期快照）
  消费者切换到其他区域 → 从上次未 ack 位置继续

启用（客户端）：
  .replicateSubscriptionState(true)（Java 客户端）
```

### 4.2 机制与语义

```text
机制：
  订阅游标定期以"快照标记"复制到其他集群
  目标集群的订阅游标跟进

语义：
  至少一次（切换时可能少量重放）
  有界重放（游标快照间隔内）

配置：
  客户端启用（replicateSubscriptionState）
  命名空间支持（订阅复制策略）

适用：
  多区域消费的 HA（消费者切换）
  跨区域负载均衡（消费者分布区域）
```

### 4.3 与复制的关系

```text
两层复制（重要区分）：
  消息复制：topic 数据跨集群（namespace 属性）
  订阅复制：消费游标跨集群（客户端启用）
  → 数据复制 ≠ 消费位置复制

组合场景：
  消息复制 + 订阅复制 = 完整的多区域消费 HA
  只复制消息：消费者切换需重放（或手动 seek）

工程建议：
  多区域消费 HA → 两者都启用
  只读分析（无消费者切换）→ 只复制消息
```

## 5. 容灾架构

### 5.1 容灾层级

```text
Pulsar 的容灾设计（多层）：
  ① 集群内：BookKeeper 多副本（节点故障）
  ② 区域内：多集群（可选）
  ③ 跨区域：复制（区域故障）

区域故障场景：
  区域 A 故障 → 流量切区域 B
  → B 有 A 的复制数据（异步复制有窗口）

RPO/RTO：
  异步复制：RPO = 复制积压（秒-分钟级）
  故障切换：RTO = 检测 + 切换（分钟级）
  → 按业务容忍度配置
```

### 5.2 容灾实践（2026 建议）

```text
部署建议（跨地域）：
  ① 每区域独立集群（本地元数据，不跨 WAN）
  ② BookKeeper ensemble 不跨区域（同步写代价大：
     跨区域 p99 60-180ms vs 区域内 3-8ms）
  ③ 复制按 namespace 配置（业务级）
  ④ 订阅复制（消费 HA）

容灾演练：
  定期区域故障演练（切换/恢复）
  复制积压监控（DR 就绪）
  数据校验（复制完整性）

对比 Kafka 容灾：
  Kafka：MirrorMaker 2 + 手动/脚本切换
  Pulsar：原生复制 + namespace 切换
  → 运维更简单
```

### 5.3 区域策略设计

```text
按业务设计复制策略：
  核心业务（订单/支付）：
    双活复制（mesh）或主备（DR）
    RPO 目标：秒级（复制积压监控）
  一般业务（日志/通知）：
    单区域 + 备份（可容忍丢）
  合规数据：
    不复制（per-topic 覆盖，Pulsar 4.0+）

关键指标：
  复制积压（pulsar_replication_backlog）
  复制速率（WAN 带宽）
  切换演练时间（RTO 实测）
```

> 🎯 **核心要点**：跨地域复制是 Pulsar 的内建能力（namespace 属性）——四种拓扑（Mesh/Hub/主备/汇聚）按区域数与带宽选择；异步默认（AP），区域内线性一致、跨区域最终一致。**消息复制 + 订阅复制（replicated subscriptions）组合**才能实现完整的多区域消费 HA。容灾实践：区域本地元数据、ensemble 不跨区域、复制积压监控、定期演练。

## 6. 对比 Kafka MirrorMaker

### 6.1 能力对照

| 维度 | Pulsar（原生） | Kafka（MirrorMaker 2） |
|------|:---:|:---:|
| 复制组件 | 内建（broker 内） | 独立集群（Connect） |
| 配置 | namespace 属性 | 配置文件 + 部署 |
| 防环 | replicatedFrom 属性 | 内部 topic 追踪 |
| 订阅复制 | 原生（replicated subscriptions） | 需额外处理 |
| 拓扑 | namespace 级（灵活） | 连接器配置 |
| 运维 | 简单（无额外组件） | 需管理 Connect 集群 |
| 监控 | 内建指标 | MirrorMaker 指标 |

### 6.2 工程结论

```text
Pulsar 复制的优势：
  ① 无独立复制集群（省运维）
  ② namespace 级配置（业务粒度）
  ③ 订阅复制内建（消费 HA）
  ④ 拓扑灵活（按 namespace）

Kafka MirrorMaker 的现实：
  功能成熟但运维重（独立 Connect 集群）
  拓扑管理复杂（多集群多连接器）

选型影响（08 模块）：
  多地域是核心需求 → Pulsar 显著优势
  （IoT/数字孪生/订单管理等多区域写入场景）
```

> 🎯 **核心要点**：Pulsar 的跨地域复制 = 内建能力（对比 Kafka 的外部组件）——拓扑灵活、订阅复制原生、运维简单。2026 年它在 IoT/数字孪生/多区域订单场景被定位为"操作上更简单"的选择。容灾核心三件事：**区域本地元数据、复制积压监控、定期切换演练**。
