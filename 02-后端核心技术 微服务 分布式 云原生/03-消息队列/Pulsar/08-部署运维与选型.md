## 1. 版本选择

### 1.1 版本线（2026）

| 版本线 | 状态 | 说明 |
|--------|------|------|
| v4.2.x | 当前稳定 | **新部署推荐**（2026-03 发布） |
| v4.0.x | LTS | 长期支持（2024-10 发布） |
| v3.0.x | LTS | 保守选择（避免 4.x 破坏性变更） |

```text
v4.x 的关键变更（选择注意）：
  PIP-457：移除 V1 topic 命名与 V1 Admin API
    → 只有 V2 三级命名（persistent://tenant/ns/topic）
  PIP-464：严格 Avro schema 验证
  etcd 元数据移除（用 ZK 或 Oxia）
  Flume/Twitter 连接器移除

选型建议：
  新部署 → v4.2.x（当前稳定）
  存量稳定 → v3.0.x（保守）
  v4.0 LTS：需要 Oxia 部分支持或 replicated subscriptions 强化
```

### 1.2 升级注意

```text
从 3.x → 4.x 的注意：
  ① V1 命名/topic 迁移（PIP-457）
  ② Admin API 兼容性检查
  ③ etcd 元数据迁移（如使用）
  ④ Avro schema 严格化验证

升级流程：
  ① 预检（兼容性扫描）
  ② 灰度（部分 broker）
  ③ 回滚预案（版本兼容）
  ④ 验证（生产流量）

运维建议：
  版本选择 = 稳定优先（新特性按需）
  升级频率 = 补丁级（4.2.x 小版本）
```

## 2. 部署方式

### 2.1 部署形态

| 方式 | 适用 |
|------|------|
| Docker Compose | 开发/测试 |
| Kubernetes（Helm） | **生产标准** |
| 裸机/VM | 传统 |
| 云服务（TDMQ 等） | 托管 |

```text
K8s 部署（生产主流）：
  Pulsar Helm Chart（官方）
  组件：
    Broker（无状态，HPA 扩展）
    BookKeeper（StatefulSet，存储）
    ZooKeeper（元数据）
  运算符：Pulsar Operator（高级管理）
```

### 2.2 K8s 部署要点

```text
资源规划（K8s）：
  Broker：CPU 密集（无状态，可 HPA）
  Bookie：存储密集（StatefulSet，PVC）
  ZK：元数据（3 节点）

存储：
  Bookie 用本地 SSD（PVC 本地卷）
  分层存储（S3）减轻 BK 容量

网络：
  服务发现（broker lookup）
  跨集群（复制）——WAN 规划

生产清单：
  资源限制（内存/CPU）
  反亲和（broker/bookie 分布）
  持久卷（bookie 数据）
  监控（Prometheus）
```

### 2.3 云托管（2026）

```text
云服务选择：
  腾讯 TDMQ（Pulsar 版）——国内主流（计费核心验证）
  自建（K8s）——控制力
  其他云（AWS 等无原生 Pulsar 托管？——评估）

TDMQ 经验（参考）：
  承载腾讯计费核心（支付/对账/监控）
  单集群 QPS 超 10 万
  服务 100 万+ 结算商户（180+ 国家）
  → Pulsar 的生产级验证（多租户/多地域）

选择：
  云上省运维 → TDMQ/托管
  自建控制 → K8s + Helm
```

## 3. 监控与运维

### 3.1 监控指标

| 类别 | 指标 | 告警 |
|------|------|------|
| 消息 | 生产/消费速率、backlog | backlog 持续增长 |
| Broker | 连接数、请求延迟 | 异常突增 |
| BookKeeper | 磁盘、写入延迟 | 磁盘水位 |
| 复制 | replication_backlog | 跨区域积压 |
| 元数据 | ZK 健康 | 节点故障 |
| 租户 | 配额使用率 | >80% |

```text
监控工具：
  Prometheus + Grafana（Pulsar 指标导出）
  官方指标：pulsar_* 系列
  健康检查：/metrics、/admin/v2/brokers/health

关键指标详解：
  backlog：订阅未消费（积压治理，理论 04）
  publish/deliver 速率：吞吐
  storage 使用：容量规划
  replication_backlog：跨区域健康
```

### 3.2 运维清单

```text
日常运维：
  ① 容量监控（BK 磁盘/租户配额）
  ② 积压治理（backlog 分析/扩容）
  ③ 复制监控（跨区域积压）
  ④ 版本升级（补丁）
  ⑤ 分层存储检查（卸载健康）

故障处理：
  Broker 故障：无状态（自动接管）
  Bookie 故障：ledger 修复（自动）
  ZK 故障：多数派（高可用）
  区域故障：流量切换（DR 流程）

演练：
  节点故障（混沌）
  区域切换（DR）
  备份恢复
```

### 3.3 备份与恢复

```text
备份策略：
  消息数据：BookKeeper 多副本（节点级冗余）
  长期保留：分层存储（S3 即备份）
  元数据：ZK 快照

恢复：
  节点故障：自动（副本）
  区域故障：复制数据（其他区域）
  误删 topic：按保留期（分层存储可恢复）

容灾级别（对应理论 06）：
  集群内：多副本（RPO=0）
  跨区域：异步复制（RPO=积压）
```

## 4. 性能与容量规划

### 4.1 性能基准（2025-2026）

| 指标 | 参考值 |
|------|--------|
| 吞吐 | 百万级 msg/s（多 broker） |
| P99 延迟 | 20-35ms（跨 BookKeeper 一跳） |
| 单 broker 吞吐 | 数十万 msg/s |
| 最大 topic | 百万级 |

```text
延迟构成（02 模块）：
  Broker 处理 + BookKeeper 写入（多一跳）
  → P99 20-35ms 的物理原因

优化方向：
  批量（吞吐）
  压缩（网络/存储）
  Bookie 配置（Journal SSD）
  分区并行（吞吐）
```

### 4.2 容量规划

```text
容量规划四要素：
  ① Broker 数：按吞吐（CPU）
  ② Bookie 数：按存储 × 副本（E:Qw:Qa）
  ③ 元数据：ZK/Oxia（小集群）
  ④ 分层存储：S3（长期保留）

计算示例：
  吞吐 100 万 msg/s、消息 1KB：
    Broker：4-8 台（数十万/台）
    存储：100 万 × 1KB × 3 副本 = 3GB/s 写入速率
    → Bookie 磁盘按速率 × 保留时间
    → 7 天热数据 + S3 长期

规划要点：
  热窗口（BK 容量）
  长期保留（S3 成本）
  峰值 vs 均值（弹性扩容）
```

### 4.3 弹性实践

```text
弹性扩展（三层分离红利）：
  加 Broker：无数据迁移（元数据操作）
  加 Bookie：新 ledger 均衡
  减容：按负载缩容（无状态）

K8s 弹性：
  HPA（Broker 按 CPU）
  存储扩容（Bookie PVC）

对比 Kafka：
  加 broker = 分区重分配（数据迁移）
  → Pulsar 弹性是架构红利（02 模块）
```

## 5. vs Kafka 选型框架

### 5.1 决策矩阵

| 需求 | Pulsar | Kafka |
|------|:---:|:---:|
| 多租户（SaaS/中台） | ✅ 原生 | ❌ 需自建 |
| 多地域复制 | ✅ 原生 | ⚠️ MirrorMaker |
| 百万 topic | ✅ | ❌ |
| 单地域吞吐 | 高 | **更高** |
| 低延迟（<10ms） | ⚠️ 20-35ms | ✅ ~5ms |
| 弹性扩展 | ✅ 无迁移 | ⚠️ 数据迁移 |
| 队列+流双模式 | ✅ 原生 | ⚠️ KIP-932 |
| 生态（大数据） | 良好 | **更丰富** |
| 运维复杂度 | 中（三组件） | 低-中（KRaft 简化） |

### 5.2 选型流程

```text
选型五问：
  ① 需要多租户？→ Pulsar（显著优势）
  ② 需要多地域？→ Pulsar（原生复制）
  ③ 需要百万 topic？→ Pulsar
  ④ 极致吞吐/低延迟？→ Kafka
  ⑤ 大数据生态深度？→ Kafka（Flink/Spark 最成熟）

典型结论：
  SaaS/中台/多地域/IoT → Pulsar
  大数据管道/单地域高吞吐 → Kafka
  两者都强需求 → 评估混合（Pulsar + Kafka 连接器）

AI 场景（2026）：
  百万 topic（每客户/每模型）→ Pulsar
  数据管道（模型训练喂数）→ Kafka
```

### 5.3 迁移路径

```text
Kafka → Pulsar 的迁移：
  ① Kafka 协议兼容（KOP）：
     Kafka 客户端直连 Pulsar（协议层迁移）
  ② 双跑过渡：两者并行 → 逐步切流
  ③ 连接器：Kafka connector（Pulsar IO）

Pulsar → Kafka（少见）：
  连接器反向
  通常因生态需求

迁移注意：
  订阅语义差异（分区 vs 订阅模型）
  多租户/多地域能力重塑（迁移后的新能力）
```

## 6. 2026 生态与趋势

```text
Pulsar 生态（2026）：
  版本：v4.x 稳定（简化/现代化）
  元数据：Oxia 演进（替代 ZK 的方向）
  云服务：腾讯 TDMQ（国内）、自建 K8s
  社区：活跃（Apache 顶级项目）

趋势：
  ① Oxia 全面替代 ZK（演进中）
  ② AI 工作负载（百万 topic 场景）
  ③ 分层存储成为标配（存储成本）
  ④ Kafka 协议兼容强化（迁移路径）
```
