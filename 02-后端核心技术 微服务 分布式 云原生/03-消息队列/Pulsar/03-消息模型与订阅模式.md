## 1. 订阅模式总览

### 1.1 四种订阅

| 订阅 | 分发语义 | 适用 |
|------|---------|------|
| Exclusive | 单消费者独占 topic | 严格有序、单消费者 |
| Failover | 主消费者 + 备消费者 | 有序 + 高可用 |
| Shared | 多消费者轮询（负载均衡） | 高吞吐、无序 |
| Key_Shared | 按 key 分发（同 key 同消费者） | 有序 + 并行 |

```text
订阅 = 消费者的"视图"：
  一个 topic 可有多个订阅（互不影响）
  每个订阅有独立游标（消费位置）
  订阅类型决定"消息如何分发"

选择的核心问题：
  需要顺序吗？→ Exclusive/Failover/Key_Shared
  需要并行吗？→ Shared/Key_Shared
  需要高可用吗？→ 非 Exclusive
```

### 1.2 订阅与消费者的关系

```text
关键规则（Exclusive/Failover）：
  消费者数量 ≤ 订阅允许值
  Exclusive：1 个消费者（多了报错）
  Failover：1 主 + N 备（主挂备上）

Shared/Key_Shared：
  消费者数量不限（负载均衡）
  消息按规则分发给消费者

注意（vs Kafka 的差异）：
  Kafka：分区级分配（消费者 ≤ 分区）
  Pulsar Shared：消息级分发（消费者可 > 分区）
  → Pulsar 的并行模型更灵活
```

> 🎯 核心认知：**订阅模式 = 消息分发的"策略旋钮"**——同一个 topic 可以用不同订阅服务不同需求（Exclusive 管顺序、Shared 管吞吐、Key_Shared 管"有序+并行"）。这是 Pulsar"消息+流双模式"的实现机制（01 模块）。

## 2. Exclusive 与 Failover

### 2.1 Exclusive（独占）

```text
Exclusive 语义：
  同一时刻只有一个消费者（独占订阅）
  新消费者加入 → 旧消费者被拒绝/替换

特性：
  消息严格按序（单消费者）
  无并行（吞吐受限）

适用：
  严格顺序 + 单消费者（全局有序）
  测试/管理场景

注意：
  消费者故障 → 订阅无消费者（消息堆积）
  → 生产一般用 Failover（高可用版）
```

### 2.2 Failover（故障转移）

```text
Failover 语义：
  主消费者（active）处理全部消息
  备消费者（standby）待命（不消费）
  主故障 → 备接管（游标续接）

特性：
  顺序保持（单消费者处理）
  高可用（自动切换）

切换细节：
  游标：订阅游标持久（BK 中）
  备接管：从游标位置继续
  切换延迟：检测 + 重连（秒级）

适用：
  严格顺序 + 高可用（核心业务）
  消费端单线程处理（顺序要求）
```

### 2.3 对比

| 维度 | Exclusive | Failover |
|------|:---:|:---:|
| 消费者数 | 1（严格） | 1 主 + N 备 |
| 顺序 | ✅ | ✅ |
| 高可用 | ❌（故障即停） | ✅（自动切换） |
| 适用 | 测试/管理 | 有序核心业务 |

```text
选择建议：
  生产有序场景 → Failover（不要用 Exclusive）
  Exclusive 只用于"明确单消费者且无需 HA"
```

## 3. Shared 与 Key_Shared

### 3.1 Shared（共享）

```text
Shared 语义：
  消息轮询分发给多个消费者（负载均衡）
  每个消费者处理一部分（并行）

特性：
  高吞吐（多消费者并行）
  无序（消息跨消费者乱序）
  无保证的公平（轮询近似）

消息分发：
  消息级别分发（非分区级别）
  消费者可 > 分区数（对比 Kafka）

适用：
  高吞吐 + 无序（日志、通知、任务队列）
  消费端可并行（无顺序依赖）
```

### 3.2 Key_Shared（键共享）

```text
Key_Shared 语义：
  按消息 key 分发（同 key → 同消费者）
  不同 key 并行（不同消费者）

特性：
  有序（同 key 严格有序）
  并行（不同 key 并行处理）

实现：
  消费者需声明 key 范围（或自动分配）
  消息按 key 哈希到消费者

适用：
  需要"按实体有序 + 整体并行"：
    订单（按订单 ID 有序）
    用户（按用户 ID 有序）
  → 消息队列理论的"分区顺序"（03 模块）
```

### 3.3 选择框架

| 需求 | 订阅 |
|------|------|
| 全局有序 + 单消费者 | Exclusive |
| 全局有序 + HA | Failover |
| 高吞吐 + 无序 | Shared |
| 按 key 有序 + 并行 | **Key_Shared** |
| 高吞吐 + HA + 无序 | Shared（消费者多） |

```text
Key_Shared 注意：
  消息需带 key（否则退化为 Shared）
  消费者管理 key 范围（开销）
  顺序 = 同 key 内有序（跨 key 无序）

工程建议：
  90% 场景：Shared（吞吐）或 Key_Shared（有序并行）
  Failover：严格顺序核心业务
```

## 4. 消费语义与 ACK

### 4.1 ACK 机制

```text
ACK（确认）：
  消费者处理完成 → ack（通知 Broker）
  游标推进（消息不再重投）

ACK 类型：
  单条 ack：逐条确认
  批量 ack：一批确认（高效）
  负 ack（nack）：处理失败 → 重新投递

投递语义：
  默认至少一次（ack 前故障 → 重投）
  消费端需幂等（同 消息队列理论 02 模块）

ACK 超时：
  未 ack 消息超时 → 重新投递（redelivery）
  → 消费慢的场景调大超时
```

### 4.2 游标管理

```text
游标（Cursor/Subscription Position）：
  订阅的消费位置（存于 BookKeeper）

操作：
  重置（seek）：从任意位置重新消费
  跳过：跳过部分消息
  延迟：从特定时间开始

游标的价值（流式）：
  新订阅可"从头消费"（完整流）
  重置游标可"重放"（故障恢复/分析）

工程：
  游标持久化（BK）→ 消费者重启续接
  复制（05 模块：replicated subscriptions）
```

### 4.3 死信与重试

```text
死信队列（DLQ）：
  消费失败 N 次 → 死信 topic（隔离）

重试机制：
  延迟重试（重试 topic + 延迟）
  投递次数限制

配置：
  死信策略（maxDeliveries）
  重试延迟（分级）

（与 消息队列理论 05 模块的延迟/死信呼应）
```

## 5. 顺序保证

### 5.1 顺序的层级

| 层级 | 订阅 | 保证 |
|------|------|------|
| 全局有序 | Exclusive/Failover | 全 topic 有序 |
| 分区有序 | 分区 topic + 单消费者 | 分区内有序 |
| Key 有序 | Key_Shared | 同 key 有序 |
| 无序 | Shared | 无保证 |

```text
顺序与并行的权衡（通用规律）：
  顺序保证越强 → 并行度越低
  Key_Shared = "有序+并行"的最佳平衡

分区 topic 的顺序：
  单分区内有序（分区顺序）
  跨分区无序（除非单消费者）
  → 与 Kafka 的分区顺序一致
```

### 5.2 破坏顺序的场景

```text
顺序破坏的来源：
  ① Shared 多消费者（天然无序）
  ② 消费失败重投（乱序）
  ③ 消费者故障切换（游标回退）

对策：
  ① 需要顺序 → 不用 Shared
  ② 失败处理 → 阻塞重试/死信（不跳过）
  ③ 幂等消费（兜底）

（与 消息队列理论 03 模块的顺序章节呼应）
```

## 6. 订阅工程实践

### 6.1 订阅选择清单

```text
① 业务需要顺序吗？
  全局有序 → Exclusive（非生产）/Failover（生产）
  按 key 有序 → Key_Shared
  无序可接受 → Shared

② 需要高可用吗？
  是 → Failover/Shared（多消费者）
  否 → 任意

③ 吞吐需求？
  高 → Shared/Key_Shared（并行）
  低 → 任意

④ 消费端能力？
  单线程（顺序）→ Exclusive/Failover
  多线程（并行）→ Shared/Key_Shared
```

### 6.2 订阅监控

```text
关键指标：
  游标落后（backlog）：订阅未消费消息数
  消费速率：每秒处理数
  重投率：失败重投比例
  死信率：进 DLQ 比例

告警：
  backlog 持续增长（消费跟不上）
  重投率突增（消费端异常）

（与 消息队列理论 04 模块积压治理呼应）
```

### 6.3 常见错误

| 错误 | 后果 |
|------|------|
| 生产用 Exclusive | 消费者故障即停 |
| 顺序需求用 Shared | 乱序 |
| 不处理 ack 超时 | 重复投递 |
| 无死信策略 | 失败消息无限重试 |
| 忽视幂等 | 重投导致重复处理 |
| key 缺失用 Key_Shared | 退化为 Shared（乱序） |

> 🎯 **核心要点**：订阅模式是 Pulsar 的消息分发核心——Exclusive/Failover 保顺序、Shared 保吞吐、Key_Shared 保"有序+并行"。工程三纪律：**顺序需求选对模式、消费端幂等（至少一次语义）、死信/重试策略必配**。订阅（而非分区）是 Pulsar 的并行模型单位——这让它的消息分发比 Kafka 更灵活。
