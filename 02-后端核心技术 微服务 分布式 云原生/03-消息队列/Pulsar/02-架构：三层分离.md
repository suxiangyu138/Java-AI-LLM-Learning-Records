## 1. 三层架构总览

### 1.1 架构分层

```text
Pulsar 的三层（存储与计算分离）：
  ① Broker（计算层）：路由/订阅/复制（无状态，不存数据）
  ② BookKeeper（存储层）：消息持久化（ledger）
  ③ 元数据存储：topic 归属/命名空间策略（ZooKeeper/Oxia）

┌─────────────────────────────────────┐
│ Broker（无状态，可水平扩展）            │
│  路由 | 订阅管理 | 复制 | 协议         │
├─────────────────────────────────────┤
│ BookKeeper（Bookie 集群，持久化）      │
│  Ledger（追加写）| Journal（WAL）     │
├─────────────────────────────────────┤
│ 元数据（ZK/Oxia）：topic 归属/策略      │
└─────────────────────────────────────┘
```

### 1.2 三层分离的价值

| 能力 | 实现机制 |
|------|---------|
| 弹性扩展 | 加 broker = 元数据操作（无数据迁移） |
| 存储独立 | BookKeeper 独立扩展（容量/性能） |
| 即时故障切换 | broker 无状态（数据在 BK） |
| 多地域 | 复制基于存储层（05 模块） |
| 百万 topic | 元数据与数据分离 |

```text
对比 Kafka（一体架构）：
  Kafka：broker = 计算 + 存储（分区日志本地盘）
  扩展：加 broker → 分区重分配（数据迁移）
  → Pulsar 的弹性 = 架构红利（分离设计）
```

> 🎯 核心认知：**三层分离是 Pulsar 一切能力的架构根源**——无状态 Broker 让扩展与故障切换"即时"，BookKeeper 让存储独立扩展，元数据分离让百万 topic 可行。对比 Kafka 的"计算存储一体"，这是两种架构哲学的具象化。

## 2. 无状态 Broker

### 2.1 Broker 的职责

```text
Broker 做什么（无状态，不存数据）：
  ① 路由：topic 分区归属（ownership）
  ② 订阅管理：游标/消费组状态
  ③ 复制：跨地域复制（05 模块）
  ④ 协议：生产/消费 API（Kafka 兼容协议可选）
  ⑤ 策略执行：配额/限流/认证

Broker 不做什么：
  不存储消息数据（在 BookKeeper）
  不持有分区副本（ownership 可转移）

无状态的推论：
  故障切换：新 broker 接管（即时）
  水平扩展：加 broker 即扩容（无需数据迁移）
  滚动升级：逐个替换（无状态）
```

### 2.2 Topic 归属（Ownership）

```text
Topic 分区的归属管理：
  每个分区由唯一 broker 负责（owner）
  归属记录在元数据存储

负载均衡：
  分区在新 broker 间重新分配（ownership 迁移）
  迁移 = 元数据更新（数据不动！）

故障处理：
  broker 故障 → 归属转移到健康 broker
  → 消费者重连（秒级）

对比 Kafka：
  分区重分配 = 数据复制（GB-TB 级）
  Pulsar = 元数据操作（毫秒级）
```

## 3. BookKeeper 存储层

### 3.1 Ledger 模型

```text
BookKeeper（Apache 顶级项目，源自 Yahoo 2011）：
  存储单元：Ledger（只写一次、追加式日志）
  存储节点：Bookie（每个 ledger 分布到多个 bookie）

Ledger 特性：
  ① 追加写（WORM：write-once, read-many）
  ② 条带化（striping）：片段分布多个 bookie
  ③ 多副本（E:Qw:Qa 控制）
  ④ 日志（Journal）+ 数据（Ledger 目录）分离

消息写入：
  消息 → ledger 片段（entry）→ 分布到 ensemble
  → 满足 Qa 后确认
```

### 3.2 E:Qw:Qa 副本模型

```text
E:Qw:Qa 三元组（默认 5:3:2）：
  E（Ensemble）：参与的 bookie 数（5）
  Qw（Write Quorum）：写入副本数（3）
  Qa（Ack Quorum）：确认副本数（2）

写入流程：
  消息 → 条带化到 E 个 bookie 的子集
  → 写入 Qw 个副本
  → Qa 个确认后返回成功

可靠性含义：
  Qa=2、Qw=3：容忍 1 个副本故障（写仍成功）
  E=5：ensemble 内有冗余（故障自动更换）

对比 Kafka ISR：
  Kafka：ISR（同步副本集合）
  Pulsar：E:Qw:Qa（更细粒度的副本控制）
  → 可用性与延迟的独立调优
```

### 3.3 Journal 与 Ledger 分离

```text
Bookie 的两类磁盘：
  Journal（日志盘）：顺序写（WAL）
    → 写路径（延迟关键）
  Ledger 目录（数据盘）：ledger 数据
    → 读路径（容量关键）

设计意义：
  写走 Journal（顺序写，快）
  读走 Ledger 目录（随机读，容量）
  → 读写 IO 分离（性能优化）

故障恢复：
  Journal 重放（崩溃后）
  Ledger 自动修复（recovery worker）
```

## 4. 元数据存储

### 4.1 角色与演进

```text
元数据存储的职责：
  ① topic 归属（哪个 broker 负责）
  ② 命名空间策略（保留/配额/复制）
  ③ 租户定义

演进：
  ZooKeeper：默认（传统）
  Oxia：Pulsar 4.x 引入（Pulsar 自研元数据服务）
  etcd：已移除（v4.2 起不再支持）

2026 状态：
  ZK 仍默认（成熟）
  Oxia 部分支持（4.x，替代 ZK 的演进方向）
  → 新部署可评估 Oxia（生产建议 ZK 稳定）
```

### 4.2 配置存储（Configuration Store）

```text
两套元数据存储：
  本地元数据存储（每集群）：
    topic 归属、命名空间策略
  配置存储（共享，跨集群）：
    租户/命名空间定义（跨集群一致）

配置存储的意义：
  跨地域复制的基础：
    租户在多个集群注册（allowed-clusters）
    策略随 topic 跨集群跟随
  → 05 模块的复制依赖它

2026 建议（跨地域）：
  每区域本地元数据存储（不跨 WAN）
  配置存储按需共享
  → 避免跨地域元数据延迟
```

## 5. 消息写入路径

### 5.1 完整链路

```text
生产消息的路径：
  ① Producer → Broker（协议处理）
  ② Broker → BookKeeper（写入 ledger）
  ③ BookKeeper 确认（Qa 副本）
  ④ Broker → Producer 确认（ack）

延迟构成：
  Broker 处理（毫秒级）
  BookKeeper 写入（网络 + 磁盘）
  → 多一跳 = P99 20-35ms 的根源（对比 Kafka 5ms）

优化手段：
  批量（batch）：多条消息一次写（吞吐）
  压缩：减少网络/存储
  分区并行：提高吞吐
```

### 5.2 读路径与缓存

```text
消费消息的路径：
  ① Consumer → Broker（订阅游标）
  ② Broker → BookKeeper 读取（或缓存）
  ③ 消息 → Consumer

读取优化：
  Broker 缓存（热消息内存）
  BookKeeper 读（缓存友好）
  → 尾读性能好（最新消息快）

游标（订阅位置）：
  存于 BookKeeper（持久）
  复制（05 模块 replicated subscriptions）
```

## 6. 弹性与故障处理

### 6.1 水平扩展

```text
扩展 Broker：
  加节点 → 新节点注册 → 分区 ownership 重分配
  → 无数据迁移（对比 Kafka 重分布）
  → 秒级生效

扩展 BookKeeper：
  加 bookie → 新 ledger 使用新 ensemble
  → 存量数据不动（渐进均衡）
  → 容量/性能独立扩展

扩展的独立性：
  计算瓶颈 → 加 broker
  存储瓶颈 → 加 bookie
  → 三层分离的弹性红利
```

### 6.2 故障处理

| 故障 | 处理 | 影响 |
|------|------|------|
| Broker 故障 | ownership 转移（元数据更新） | 秒级重连 |
| Bookie 故障 | ledger 修复（ensemble 更换） | 写入继续（Qa 冗余） |
| 元数据故障 | ZK/Oxia 集群（多数派） | 无（高可用） |
| 网络分区 | 多数派原则 | 少数派降级 |

```text
故障设计的要点：
  三层各自独立高可用：
    Broker：无状态（可替换）
    BookKeeper：多副本（数据安全）
    元数据：多数派（协调可靠）
  → 任何单层故障不影响整体

容灾（跨地域）：
  原生复制（05 模块）
  区域故障 → 其他区域继续服务
```

> 🎯 **核心要点**：Pulsar 架构 = 无状态 Broker（计算）+ BookKeeper（存储，E:Qw:Qa 副本）+ 元数据（ZK/Oxia）三层分离。每个决策都服务于弹性：加 broker 无迁移、加 bookie 独立扩、故障切换即时。理解三层分离，就理解了 Pulsar 与 Kafka 的架构差异根源（弹性 vs 吞吐），以及为什么它适合云原生/多租户/多地域场景。
