## 1. 多租户的设计目标

### 1.1 什么是多租户

```text
多租户（Multi-tenancy）：
  一个 Pulsar 集群服务多个"租户"（业务/客户/团队）
  每个租户有独立的：
    认证与授权（谁能访问）
    资源配额（存储/流量上限）
    策略（保留/复制/限流）

设计目标：
  ① 共享基础设施（成本）
  ② 逻辑隔离（安全与互不干扰）
  ③ 独立策略（各租户按需配置）
```

### 1.2 为什么多租户重要

```text
场景（SaaS/中台）：
  一个消息平台服务多个业务线/客户
  每个租户需要：
    独立 topic 命名空间（不冲突）
    独立权限（不能互相访问）
    独立配额（一个租户不拖垮别人）

对比"一个集群一个业务"：
  多租户 = 基础设施共享 + 逻辑隔离
  → 成本效益与安全性的平衡

Pulsar 的多租户是"一等公民"（架构设计）
  对比 Kafka：无原生多租户（需自建/多集群）
```

> 🎯 核心认知：**多租户 = "共享集群 + 独立策略"**——tenant 是隔离边界，namespace 是策略单元，topic 是消息实体。这让一个集群服务千级租户成为可能（Pulsar 对比 Kafka 的王牌能力）。

## 2. 三级层级

### 2.1 层级结构

```text
tenant（租户）→ namespace（命名空间）→ topic（主题）

完整 topic 名（V2）：
  persistent://tenant/namespace/topic
  例：persistent://orders/us-east/order-events

各层职责：
  tenant：组织边界（业务单元/客户/应用域）
    - 创建时指定 allowed-clusters、admin-roles
  namespace：策略单元（一组 topic 共享策略）
    - 保留/TTL/配额/复制/限流
  topic：消息实体（分区/订阅）
```

### 2.2 创建与管理

```bash
# 创建租户（指定允许的集群与管理员）
pulsar-admin tenants create orders \
  --allowed-clusters us-east,eu-west \
  --admin-roles order-admin

# 创建命名空间
pulsar-admin namespaces create orders/us-east

# 设置命名空间策略（保留/复制等，见下节）
pulsar-admin namespaces set-retention orders/us-east \
  --size 10G --time 7d
```

```text
层级设计的价值：
  命名空间 = 策略"继承单元"
    → 组内 topic 自动继承策略
    → 批量管理（一个 namespace 一套策略）

工程：
  按业务/环境划分 namespace：
    orders/us-east（生产）
    orders/test（测试）
  → 策略独立、互不干扰
```

## 3. 命名空间策略

### 3.1 策略类型

| 策略 | 作用 | 命令 |
|------|------|------|
| 保留（Retention） | 消息保留时长/大小 | set-retention |
| TTL | 未消费消息过期 | set-message-ttl |
| 发布限流 | 生产速率上限 | set-publish-rate |
| 分发限流 | 消费速率上限 | set-dispatch-rate |
| 存储配额 | 命名空间存储上限 | set-storage-quota |
| 持久性 | 副本数（E:Qw:Qa） | set-persistence |
| 复制 | 跨地域集群列表 | set-clusters |

### 3.2 关键策略详解

```bash
# 保留策略（流式语义：消息保留即使已消费）
pulsar-admin namespaces set-retention orders/us-east \
  --size 10G --time 7d
# 消息保留 7 天或 10GB（满足其一即清理）

# TTL（队列语义：未消费消息过期）
pulsar-admin namespaces set-message-ttl orders/us-east \
  --messageTTL 3600
# 未消费消息 1 小时后过期（队列场景）

# 配额（租户保护）
pulsar-admin namespaces set-storage-quota orders/us-east \
  --size 50G
# 超过配额 → 拒绝写入（防单租户拖垮集群）
```

```text
保留 vs TTL 的区别（重要）：
  Retention：消息保留（即使已消费）——流式语义
  TTL：未消费消息过期——队列语义
  → 双模式（01 模块）的策略实现

限流的价值（多租户）：
  publish-rate：租户生产上限（防洪峰打爆）
  dispatch-rate：消费上限（防消费端异常）
  → "一个租户不拖垮别人"的保障
```

## 4. 租户隔离

### 4.1 隔离的层次

```text
租户隔离的四层：
  ① 认证：谁能访问集群（token 等）
  ② 授权：谁能访问哪个 tenant/namespace
  ③ 配额：资源上限（存储/流量）
  ④ 策略：保留/复制（按租户配置）

认证（Authentication）：
  JWT token（默认推荐）
  TLS 证书、OAuth2 等

授权（Authorization）：
  角色（admin/producer/consumer）
  基于 tenant/namespace 的权限
  → 租户间互不可见
```

### 4.2 权限管理

```bash
# 创建租户与角色
pulsar-admin tenants create orders \
  --admin-roles order-admin

# 授予权限（租户级/命名空间级）
pulsar-admin namespaces grant-permission orders/us-east \
  --role order-service --actions produce,consume

# 撤销权限
pulsar-admin namespaces revoke-permission orders/us-east \
  --role order-service

# 角色模型：
#   admin：管理权限（全部）
#   produce：生产
#   consume：消费
#   functions：函数管理
```

### 4.3 隔离的保证

```text
隔离的工程保证：
  ① 命名空间隔离：topic 名含 tenant（不可冲突）
  ② 权限隔离：跨租户访问被拒（认证+授权）
  ③ 配额隔离：资源上限（防干扰）
  ④ 策略隔离：保留/限流独立（互不影响）

安全最佳实践：
  JWT 认证启用（生产必配）
  最小权限原则（按需授权）
  租户间数据加密（可选）

对比 Kafka：
  Kafka：ACL 基于 topic 前缀（无租户概念）
  → 租户管理需应用层/多集群
  → Pulsar 的隔离是"原生"的
```

## 5. 多租户工程实践

### 5.1 租户规划

```text
租户划分原则：
  按组织边界：业务线/客户/环境
  按隔离需求：数据敏感度/合规要求

常见划分：
  按业务：orders、payments、inventory
  按环境：prod、staging、test（或 namespace 级）
  按客户（SaaS）：customer-A、customer-B

命名空间划分：
  按区域/环境：orders/us-east、orders/eu-west
  按团队：orders/checkout、orders/fulfillment

建议：
  租户少而清晰（10-100 级）
  命名空间灵活（策略单元）
```

### 5.2 配额与容量规划

```text
配额设计（防干扰）：
  存储配额：按租户业务量估算（+30% 余量）
  发布限流：按峰值吞吐（+安全系数）
  分发限流：按消费能力

监控与告警：
  每租户使用量（存储/吞吐）
  配额使用率（>80% 告警）
  限流触发次数（配额不足信号）

容量规划：
  集群总容量 = Σ 租户配额（+集群余量）
  超卖策略：配额总和可 > 集群（弹性场景）
  → 生产按实际需求平衡
```

### 5.3 多租户的运维

```text
运维清单：
  ① 租户生命周期（创建/审计/回收）
  ② 配额定期 review（业务增长）
  ③ 权限审计（最小权限检查）
  ④ 租户隔离验证（渗透测试）
  ⑤ 成本分摊（按租户统计用量）

2026 状态：
  Pulsar 多租户成熟（生产验证）
  腾讯 TDMQ（Pulsar）多租户服务数百万商家
  → 大规模多租户的实践验证
```

## 6. 对比 Kafka 的租户隔离

### 6.1 能力对照

| 维度 | Pulsar | Kafka |
|------|:---:|:---:|
| 租户概念 | 原生（tenant） | 无（topic 前缀模拟） |
| 隔离层次 | tenant/namespace/topic | topic 级 ACL |
| 配额 | 原生（存储/限流） | 无原生（需自建） |
| 策略继承 | namespace 级（批量） | 无 |
| 多集群共享 | 原生（allowed-clusters） | 多集群管理复杂 |
| 适用 | SaaS/中台/多业务 | 单业务/大数据 |

### 6.2 工程含义

```text
Kafka 的多租户现实：
  ACL 按 topic 前缀（粗粒度）
  配额需第三方/自研
  多业务隔离 → 常开多集群（成本高）

Pulsar 的价值：
  一个集群服务千级租户（成本低）
  隔离/配额/策略原生（安全）
  租户跨集群（allowed-clusters 灵活）

选型影响（08 模块）：
  需要多租户（SaaS/中台）→ Pulsar 显著优势
  单业务高吞吐 → Kafka（无租户需求）
```

> 🎯 **核心要点**：多租户是 Pulsar 的架构级能力（非附加）——tenant/namespace/topic 三级层级 + 认证授权 + 配额限流 + 策略继承。工程三要点：**租户按组织边界划分、配额必配（防干扰）、最小权限授权**。对比 Kafka 的"topic 前缀模拟"，Pulsar 的原生多租户让"一个集群服务千级租户"成为现实——这是 SaaS/中台场景选型 Pulsar 的首要理由。
