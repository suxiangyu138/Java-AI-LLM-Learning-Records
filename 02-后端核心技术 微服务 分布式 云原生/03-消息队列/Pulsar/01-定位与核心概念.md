## 1. Pulsar 的定位

### 1.1 一句话定位

```text
Pulsar：云原生的分布式消息与流平台
  （Apache 顶级项目，Yahoo 2015 开源）

核心定位：
  一个平台同时提供：
    队列（Queue）：点对点消息（消费即完成）
    流（Stream）：持久化事件流（可重放）
    事件（Event）：多租户/多地域的分布式事件

对比：
  Kafka：以"日志流"为核心（流平台）
  RocketMQ：以"业务消息"为核心（队列）
  Pulsar：两者合一（消息+流）
```

### 1.2 设计目标

```text
Pulsar 的设计目标（从架构出发）：
  ① 弹性：存储与计算独立扩展（三层分离）
  ② 多租户：一个集群服务多业务（隔离）
  ③ 多地域：原生复制（跨地域容灾）
  ④ 规模：百万 topic（每客户一 topic）
  ⑤ 统一：队列 + 流 + 事件一体

这些目标直接决定了它的架构（02 模块）
  与 Kafka"分区日志"路线形成对照
```

> 🎯 核心认知：**Pulsar = "消息 + 流"的统一平台**——订阅模式决定语义（Exclusive=队列、Shared=负载均衡、流式=可重放），一个系统覆盖多种消息需求。这是它与 Kafka（流优先）和 RocketMQ（队列优先）的本质区别。

## 2. 核心概念

### 2.1 概念层级

```text
Pulsar 的层级（V2 命名，3 级）：
  tenant（租户）→ namespace（命名空间）→ topic（主题）

完整 topic 名（V2）：
  persistent://tenant/namespace/topic
  例：persistent://orders/us-east/order-events

V1 命名（已废弃，PIP-457 在 v4.2 移除）：
  persistent://prop/cluster/ns/topic（4 级）
  → v4.2 起只有 V2 3 级命名

层级的意义：
  tenant：组织边界（业务/客户）
  namespace：策略单元（保留/配额/复制）
  topic：消息实体
```

### 2.2 Topic 与分区

| 概念 | 说明 |
|------|------|
| Topic | 消息的逻辑主题（持久/非持久） |
| 分区（Partition） | 并行单位（分区 topic） |
| 订阅（Subscription） | 消费者的"视图"（见 03 模块） |
| Ledger | BookKeeper 的存储单元（02 模块） |

```text
Topic 类型：
  persistent（持久）：数据落 BookKeeper（默认）
  non-persistent（非持久）：内存流（低延迟可丢）

分区 topic：
  自动创建（分区数配置）
  分区在 broker 间分布（ownership）
  分区内有序（跨分区无序）

订阅：每个 topic 可多个订阅
  → 不同业务各自消费（互不影响）
```

### 2.3 消息生命周期

```text
消息的完整路径：
  生产者 → Broker → BookKeeper（ledger）→ 订阅分发 → 消费者

关键特性：
  持久化：消息落 BookKeeper（acks 确认后）
  重放：订阅从任意位置消费（流式）
  保留：按保留策略（大小/时间）
  分层：冷数据可卸载对象存储（06 模块）
```

## 3. 消息+流：双模式

### 3.1 两种语义的对照

| 维度 | 队列（Queue） | 流（Stream） |
|------|:---:|:---:|
| 消费后 | 删除/游标推进（不重放） | 可重放（游标可重置） |
| 典型订阅 | Exclusive/Shared | Failover/Key_Shared |
| 使用场景 | 任务/通知 | 事件溯源/分析 |
| 数据保留 | 短（消费即弃） | 长（可回溯） |

```text
Pulsar 的双模式实现：
  同一 topic、同一存储（BookKeeper）
  差异只在"订阅语义"与"保留策略"

对比 Kafka：
  Kafka 本质是"日志"（消费组推进 offset）
  队列语义需额外机制（KIP-932 Share Groups，2025 才补）

对比 RocketMQ：
  RocketMQ 本质是"队列"（消费即完成）
  流式语义较弱

→ Pulsar 从设计上就是双模式（无需额外机制）
```

### 3.2 订阅与保留的组合

```text
订阅（消费视图）：
  一个 topic 可有多个订阅（独立游标）
  订阅类型决定分发语义（03 模块）

保留（数据生命周期）：
  保留策略独立于订阅
  消息保留 N 天/大小（即使已消费）
  → 新订阅可从头消费（流式）

组合价值：
  业务 A：Shared 订阅（队列语义，消费即弃）
  业务 B：Failover 订阅（流语义，重放分析）
  同一 topic 服务两种需求 ✓
```

## 4. 与 Kafka 的哲学差异

### 4.1 架构哲学对照

| 维度 | Kafka | Pulsar |
|------|:---:|:---:|
| 存储 | 分区日志（broker 本地盘） | BookKeeper（独立存储层） |
| 扩展 | 加 broker = 数据迁移 | 加 broker = 元数据操作（无迁移） |
| 租户隔离 | 无原生（集群/应用层） | 原生（tenant/namespace） |
| 多地域 | MirrorMaker（外部组件） | 原生复制（namespace 属性） |
| Topic 规模 | 数万分区 | 百万级 |
| 存储与计算 | 一体 | 分离 |

```text
哲学差异的根源：
  Kafka：把"分区日志"做到极致（追加写/零拷贝）
  Pulsar：把"存储与计算分离"做到极致（弹性/租户/地域）

各自的代价：
  Kafka：弹性扩展需数据重分布；多租户需自建
  Pulsar：多一跳（BookKeeper 写路径）；延迟略高（P99 20-35ms）
```

### 4.2 吞吐与延迟的现实

| 指标 | Kafka 4.x | Pulsar 4.x |
|------|:---:|:---:|
| 单地域吞吐 | 605 MB/s（百万 TPS） | 百万级 msg/s |
| P99 延迟 | ~5ms | 20-35ms |
| 扩展弹性 | 数据迁移 | 即时（无迁移） |
| 百万 topic | 难 | 原生 |

```text
性能结论（2025-2026 检索共识）：
  Kafka：单地域原始吞吐与延迟更优
  Pulsar：弹性/租户/多地域/百万 topic 更优
  → 选型看需求（08 模块详述）

AI 场景（2026）：
  Pulsar 的百万 topic 适合"每客户/每模型一 topic"
  → AI 工作负载的差异化优势
```

## 5. 适用场景

### 5.1 适用场景

| 场景 | Pulsar 的优势 |
|------|--------------|
| 多租户 SaaS | 原生隔离（tenant/namespace） |
| 跨地域业务 | 原生复制（多活） |
| 百万 topic | 每客户/每设备一 topic |
| 队列+流混合 | 双模式（一个平台） |
| 云原生弹性 | 存算分离（秒级扩展） |
| IoT/数字孪生 | 多地域写入 + 大 topic 数 |

### 5.2 不适用/谨慎场景

| 场景 | 原因 | 替代 |
|------|------|------|
| 极致低延迟（<10ms） | BookKeeper 多一跳 | Kafka/RabbitMQ |
| 单地域高吞吐优先 | Kafka 原始吞吐更优 | Kafka |
| 简单队列（小规模） | 架构重 | RabbitMQ |
| 已有 Kafka 生态 | 迁移成本 | 维持 Kafka |

### 5.3 2026 生态定位

```text
Pulsar 的生态位置（2026）：
  云原生消息/流的差异化选择
  腾讯 TDMQ（Pulsar）承载计费核心（百万 QPS 验证）
  多地域/IoT/AI 工作负载的推荐平台

选型一句话：
  需要多租户/多地域/百万 topic → Pulsar
  需要单地域极致吞吐 → Kafka
  → 详见 08 模块完整框架
```

> 🎯 **核心要点**：Pulsar = 消息+流统一平台——订阅模式决定语义（队列/流/事件），三层架构支撑弹性，原生多租户与多地域复制是差异化王牌。与 Kafka 的哲学差异（存算分离 vs 分区日志）决定了各自优势：Kafka 赢吞吐延迟、Pulsar 赢弹性租户地域。2026 年百万 topic 的 AI 场景是 Pulsar 的新战场。
