## 1. 整体架构分层

```text
┌─────────────────────────────────────────────────────┐
│                    客户端层                           │
│   Producer API  │  Consumer API  │  Admin API        │
├─────────────────────────────────────────────────────┤
│                    网络层                             │
│   SocketServer → KafkaApis → ReplicaManager          │
├─────────────────────────────────────────────────────┤
│                    复制层                             │
│   Controller → Partition Leader → ISR 管理            │
├─────────────────────────────────────────────────────┤
│                    存储层                             │
│   Log → LogSegment → .log / .index / .timeindex      │
├─────────────────────────────────────────────────────┤
│                    OS 层                              │
│   页缓存 (Page Cache) → 磁盘 (顺序 I/O)               │
└─────────────────────────────────────────────────────┘
```

| 层 | 职责 | 核心组件 |
|------|------|----------|
| **客户端层** | 提供生产/消费 API、Admin 操作 | `KafkaProducer`、`KafkaConsumer` |
| **网络层** | 接收请求、分发到对应处理逻辑 | `SocketServer`、`KafkaApis` |
| **复制层** | 管理分区副本、Leader 选举、ISR 维护 | `Controller`、`ReplicaManager` |
| **存储层** | 消息持久化、日志分段、索引构建 | `LogManager`、`LogSegment` |
| **OS 层** | 利用页缓存和零拷贝加速读写 | Page Cache、sendfile |

## 2. Topic 与 Partition

### 2.1 逻辑视图 vs 物理视图

```text
【逻辑视图】                               【物理视图】
Topic: "user-events"                    Broker 1         Broker 2         Broker 3
┌─────────────────┐                    ┌─────────┐      ┌─────────┐      ┌─────────┐
│   Partition 0    │──────────────→    │ P0 (L)  │      │ P0 (F)  │      │ P1 (F)  │
│   Partition 1    │──────────────→    │ P2 (F)  │      │ P1 (L)  │      │ P2 (L)  │
│   Partition 2    │──────────────→    │         │      │         │      │         │
└─────────────────┘                    └─────────┘      └─────────┘      └─────────┘
                                             L = Leader, F = Follower
```

### 2.2 分区数如何决定

| 因素 | 影响 |
|------|------|
| **吞吐量** | 分区越多，并发度越高 → 吞吐越大 |
| **消费者数** | 一个分区只能被消费组中一个消费者消费 → 消费者数 ≤ 分区数 |
| **端到端延迟** | 分区过多增加 Leader 选举和文件句柄开销 |
| **内存占用** | 每个分区在 Broker 上占用内存（索引 + 缓存） |

> 🎯 **经验公式**：分区数 = max(目标吞吐 / 单分区吞吐, 消费者数)。单分区吞吐约 10~20 MB/s（取决于配置）。

### 2.3 为什么单 Partition 内有序

```text
Partition 0: [msg0, msg1, msg2, msg3, msg4, msg5, ...]
             ←──── 严格有序（按写入时间）────→

Partition 1: [msg0, msg1, msg2, msg3, msg4, msg5, ...]
             ←──── 严格有序 ————→

→ Partition 0 和 Partition 1 之间无序！
→ 跨 Partition 保序：指定消息 Key，相同 Key 路由到同一 Partition
```

## 3. 日志存储模型

### 3.1 文件布局

```text
/data/kafka-logs/
├── my-topic-0/                    ← Topic "my-topic", Partition 0
│   ├── 00000000000000000000.log   ← 日志文件（消息数据）
│   ├── 00000000000000000000.index ← 偏移量索引
│   ├── 00000000000000000000.timeindex ← 时间戳索引
│   ├── 00000000000000102500.log   ← 下一段日志
│   ├── 00000000000000102500.index
│   └── 00000000000000102500.timeindex
├── my-topic-1/
│   └── ...
└── __consumer_offsets-0/          ← 内部位移主题
    └── ...
```

### 3.2 LogSegment 详解

```text
一个 LogSegment 由三个文件组成：

┌──────────────────────────────────────────────────┐
│  00000000000000000000.log（实际消息数据）           │
│  ┌──────┬──────────┬──────────┬──────────┬──────┐│
│  │ msg0 │  msg1    │  msg2    │  msg3    │ ...  ││
│  │ Key  │  Key     │  Key     │  Key     │      ││
│  │ Value│  Value   │  Value   │  Value   │      ││
│  │ Head │  Headers │  Headers │  Headers │      ││
│  └──────┴──────────┴──────────┴──────────┴──────┘│
├──────────────────────────────────────────────────┤
│  00000000000000000000.index（稀疏索引）             │
│  相对 Offset → 物理位置                             │
│  ┌───────┬──────────┐                            │
│  │   0   │  position │ ← 不是每条，跳着记录          │
│  │  100  │  position │                            │
│  │  200  │  position │   index.interval.bytes      │
│  └───────┴──────────┘                             │
├──────────────────────────────────────────────────┤
│  00000000000000000000.timeindex（时间戳索引）       │
│  时间戳 → 相对 Offset                               │
└──────────────────────────────────────────────────┘
```

### 3.3 消息格式（V2 Record Batch）

```text
Record Batch（消息批次 — 压缩的最小单位）
┌──────────────────────────────────────────────────┐
│ Base Offset │ Length │ Partition Leader Epoch    │
│ Magic(2)    │ CRC    │ Attributes(压缩类型...)     │
│ Last Offset Delta │ First Timestamp              │
│ Max Timestamp     │ Producer ID / Epoch / Seq    │
├──────────────────────────────────────────────────┤
│ Record 1: Length │ Attributes │ Timestamp Delta  │
│          Offset Delta │ Key │ Value │ Headers    │
├──────────────────────────────────────────────────┤
│ Record 2: ...                                    │
│ Record 3: ...                                    │
└──────────────────────────────────────────────────┘

优势（vs V1）：
  ✅ 批量压缩，压缩率更高
  ✅ 变长字段，节省空间
  ✅ 支持时间戳精度提升
```

### 3.4 如何通过 Offset 找到消息

```text
查询 Offset = 3880 的消息：

Step 1: 二分查找 LogSegment
  → 文件名范围 [2500.log, 5000.log] → 落在 2500.log

Step 2: 查找 .index 稀疏索引
  → 3880 不在索引中 → 找到 ≤3880 的最大索引项（3800 → position X）
  
Step 3: 从 position X 顺序扫描 .log
  → 3800 开始 → 3801 → 3802 ... → 3880 ✅

时间复杂度：O(log(segment数)) + O(index扫描) + O(offset差值扫描)
```

## 4. ISR 与高水位机制

### 4.1 核心概念

```text
Partition 0（Replication Factor = 3）
┌──────────────────────────────────────────────────────┐
│  Leader (Broker 1)                                   │
│  ┌───┬───┬───┬───┬───┬───┬───┐                      │
│  │ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │                      │
│  └───┴───┴───┴───┴───┴───┴───┘                      │
│            ↑LEO=7                                    │
│        ↑HW=4                                         │
├──────────────────────────────────────────────────────┤
│  Follower (Broker 2)                                 │
│  ┌───┬───┬───┬───┬───┐                               │
│  │ 0 │ 1 │ 2 │ 3 │ 4 │  ← 已同步                      │
│  └───┴───┴───┴───┴───┘                               │
│  ↑LEO=5          ↑HW=4                               │
├──────────────────────────────────────────────────────┤
│  Follower (Broker 3)                                 │
│  ┌───┬───┬───┐                                       │
│  │ 0 │ 1 │ 2 │  ← 滞后中...                          │
│  └───┴───┴───┘                                       │
│  ↑LEO=3  ↑HW=2                                       │
└──────────────────────────────────────────────────────┘

ISR = {Broker 1, Broker 2}  ← Broker 3 掉队，不在 ISR 中
```

**关键水位线：**

| 术语 | 全称 | 含义 |
|------|------|------|
| **LEO** | Log End Offset | 下一条待写入消息的 offset |
| **HW** | High Watermark | 所有 ISR 副本都已确认的最大 offset，消费者最多读到此处 |
| **ISR** | In-Sync Replicas | 与 Leader 保持同步的副本集合 |

### 4.2 ISR 伸缩机制

```text
Follower 进入 ISR 条件：
  ✅ replica.lag.time.max.ms（默认 30s）内追上 Leader

Follower 踢出 ISR 条件：
  ❌ 超过 replica.lag.time.max.ms 仍未追上 Leader

旧版参数 replica.lag.max.messages（按消息条数）已废弃！
→ 原因：消息大小不均，条数判断不准
```

## 5. 日志清理与压缩

### 5.1 两种清理策略

```text
策略一：delete（删除，默认）
  → 按时间：log.retention.hours=168（7天）
  → 按大小：log.retention.bytes=-1（不限制）
  
  Segment 文件超过保留时间 → 直接删除整个 Segment

策略二：compact（压缩）
  → 保留每个 Key 的最新 Value
  → 适用场景：数据库变更日志（CDC）
  
  压缩前：[K1→A] [K2→B] [K1→C] [K3→D] [K2→E]
  压缩后：[K1→C] [K3→D] [K2→E]  ← 每个 Key 只保留最新
```

### 5.2 日志清理参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `log.cleanup.policy` | delete | delete / compact / delete,compact |
| `log.retention.hours` | 168 | 保留时间（小时） |
| `log.retention.bytes` | -1 | 总大小限制 |
| `log.segment.bytes` | 1GB | Segment 大小，超过则滚动 |
| `log.segment.ms` | 7天 | Segment 时间，超过则滚动 |
| `min.cleanable.dirty.ratio` | 0.5 | 压缩触发阈值（脏数据比例） |

### 5.3 清理线程模型

```text
LogCleaner 线程池 ──→ 后台扫描 LogSegment
                  │
                  选择最脏的 Segment 压缩
                  │
                  新建 .clean 文件
                  │
                  原子替换原 Segment
```

## 6. 零拷贝原理

### 6.1 传统数据传输（4 次拷贝）

```text
传统 sendfile（4 次拷贝，2 次上下文切换）

磁盘 → Read Buffer（内核） → 用户态 Buffer → Socket Buffer（内核） → 网卡
      ① DMA copy            ② CPU copy        ③ CPU copy              ④ DMA copy

上下文切换：用户态 ↔ 内核态 × 2
```

### 6.2 Kafka 零拷贝（2 次拷贝）

```text
Kafka sendfile（2 次 DMA 拷贝，0 次 CPU 拷贝）

磁盘 → Read Buffer（内核） ──→ Socket Buffer（内核） → 网卡
      ① DMA copy         sendfile 描述符传递      ② DMA copy

上下文切换：仅 1 次（系统调用）
```

**关键收益：**

| 指标 | 传统模式 | 零拷贝模式 | 提升 |
|------|----------|------------|:---:|
| CPU 拷贝 | 2 次 | 0 次 | ∞ |
| DMA 拷贝 | 2 次 | 2 次 | — |
| 上下文切换 | 2 次 | 1 次 | 50% |
| CPU 占用 | 高 | 低 | 60%↓ |

> 💡 Kafka 的 Java 代码中通过 `FileChannel.transferTo()` 调用 OS 的 `sendfile` 系统调用实现零拷贝。

### 6.3 零拷贝 + 页缓存 = Kafka 高吞吐基石

```text
生产者写入：
  消息 → JVM 堆 → OS 页缓存 → 异步刷盘
                          ↓
消费者读取：             如果命中页缓存
  消息 ← JVM 堆 ← OS 页缓存（零拷贝 sendfile）
                          ↓
                      如果未命中 → 磁盘读取（高效顺序读）
```

## 7. 与 RabbitMQ 存储模型对比

| 维度 | Kafka | RabbitMQ |
|------|-------|----------|
| **存储模型** | 顺序追加日志 | 消息队列（消费即删） |
| **消息回溯** | ✅ Offset 回放 | ❌ 消费后立即删除 |
| **磁盘使用** | 顺序写 + 批量 = 高效 | 随机写（索引） = 开销高 |
| **文件管理** | Segment 轮转 + 过期清理 | 队列文件持续增长 |
| **内存依赖** | 低（依赖页缓存） | 高（内存队列） |
| **积压能力** | 极高（磁盘有多大，积多少） | 受限（内存/磁盘都易瓶颈） |
| **单 Partition 吞吐** | 10~20 MB/s | <1 MB/s |

## 存储核心要点总结

| 要点 | 一句话 |
|------|--------|
| **分区模型** | Topic → Partition → LogSegment → 三段索引 |
| **消息查找** | 文件名二分 + 稀疏索引 + 顺序扫描 |
| **高可用** | ISR 集合 + HW 水位 → Leader 宕机自动切换 |
| **顺序性** | 单 Partition 内有序，跨 Partition 通过 Key 保序 |
| **清理机制** | delete（按时间/大小）或 compact（按 Key 去重） |
| **零拷贝** | `transferTo` → `sendfile` → DMA 直传网卡 |
| **页缓存** | 消息先入 OS 缓存 → 消费者直接读取，减少磁盘 IO |
