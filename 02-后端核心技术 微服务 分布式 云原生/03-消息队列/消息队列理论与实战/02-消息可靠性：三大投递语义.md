## 1. 消息可能丢在哪：可靠性链路

### 1.1 三环节模型

```text
消息的生命链路由三个环节组成，任何一环都可能丢：

  生产端 → ① 发送失败/未确认 → Broker
  Broker → ② 落盘前宕机/副本不足 → 存储
  Broker → ③ 消费失败/位点异常 → 消费端

可靠性设计 = 每个环节的"防丢配置" + 消费端的"幂等兜底"
```

### 1.2 丢消息的常见场景

| 环节 | 丢失场景 | 防丢手段 |
|------|---------|---------|
| 生产 | 网络超时未确认（实际已写入） | 重试 + 幂等 |
| 生产 | 同步发送失败被吞异常 | 发送回调/重试 |
| 存储 | 单副本 + 宕机 | 多副本 + acks=all |
| 存储 | 刷盘延迟（内存未落盘） | 同步刷盘（性能换可靠） |
| 消费 | 自动提交位点后处理失败 | 手动 ACK + 处理后提交 |
| 消费 | 处理逻辑抛异常未处理 | 重试 + 死信 |

> 🎯 核心认知：**"消息不丢"不是中间件的默认行为，而是三端配置 + 应用代码共同保证的结果**。默认配置（如 Kafka 自动提交）在生产环境必须显式调整。

## 2. 三大投递语义

### 2.1 语义定义

| 语义 | 含义 | 实现代价 |
|------|------|---------|
| 最多一次（At-most-once） | 消息可能丢，但绝不重复 | 最低（自动提交） |
| 至少一次（At-least-once） | 消息不丢，但可能重复 | 中（ACK 重投） |
| 恰好一次（Exactly-once） | 不丢不重 | 最高（事务/幂等） |

```text
三者的关系：
  最多一次：发送后不管（丢消息可接受）
  至少一次：失败重投（重复可接受，靠幂等消重）
  恰好一次：Kafka 幂等生产者 + 事务 + 读已提交

工程现实：
  绝大多数业务选择"至少一次 + 消费端幂等"
  —— 因为端到端恰好一次的成本极高且难以证明
```

### 2.2 为什么"恰好一次"难

```text
端到端恰好一次需要三处同时保证：
  ① 生产端：幂等发送（重试不重复）
  ② 存储端：事务性写入（消息要么在要么不在）
  ③ 消费端：恰好处理一次（处理与位点提交原子）

即使中间件全部支持（Kafka 事务），
  消费端"处理业务 + 提交位点"的原子性仍需应用配合
  （如消费写库后再提交——两处事务无法跨系统原子）
```

## 3. 生产端可靠性

### 3.1 发送方式对比

| 方式 | 行为 | 可靠性 | 适用 |
|------|------|:---:|------|
| 发后即忘（fire-and-forget） | 不等待结果 | ❌ | 日志类可丢 |
| 同步发送 | 等待确认 | ✅ | 核心业务 |
| 异步发送（回调） | 回调通知结果 | ✅ | 高吞吐核心业务 |

### 3.2 发送确认（acks）与重试

```text
Kafka 的 acks 三档（RocketMQ 的同步刷盘/异步刷盘类似）：
  acks=0  不等待确认（可能丢）
  acks=1  首领副本落盘即确认（首领宕机可能丢）
  acks=all 所有 ISR 副本确认（最可靠）

重试的正确姿势：
  ① 必须开重试（网络抖动是常态）
  ② 重试要幂等（生产端幂等见下）
  ③ 重试有上限 + 失败落库（人工补偿入口）
```

### 3.3 生产端幂等

```text
问题：发送超时 → 重试 → 消息可能已写入 → 重复消息

Kafka 幂等生产者（enable.idempotence=true）：
  生产者 ID + 序列号 → Broker 去重
  → 重试不产生重复消息（单分区内保证）

RocketMQ 事务消息（07 模块）：半消息 + 确认
  → 生产端"要么发要么不发的原子性"

工程兜底：消息 ID 去重表（消费端幂等，见第 6 节）
```

## 4. 存储端可靠性

### 4.1 副本与刷盘

```text
两个维度：
  ① 副本数（横向冗余）：多副本 → 单节点故障不丢
  ② 刷盘策略（纵向持久）：内存 → 磁盘的时机

Kafka：ISR 副本 + 可配置刷盘（默认依赖 OS 页缓存 + 副本兜底）
RocketMQ：同步/异步刷盘（同步刷盘单点更强，副本补短板）
RabbitMQ：Quorum 队列（Raft 复制，4.0 起唯一复制选项）

工程默认（生产）：
  副本 ≥ 3（至少 2）
  关键数据开同步/强一致确认
```

### 4.2 ISR 与确认（详见 06 模块）

```text
ISR（In-Sync Replicas）：与首领保持同步的副本集合
  acks=all → 写入所有 ISR 才确认
  副本落后 → 踢出 ISR（容忍部分副本故障）

极端情况：ISR 只剩首领 → acks=all 退化为单点
  → 可靠性配置的边界（min.insync.replicas 兜底）
```

## 5. 消费端可靠性：ACK 与重投

### 5.1 ACK 机制

| 中间件 | 确认机制 | 关键配置 |
|--------|---------|---------|
| Kafka | 位点提交（offset commit） | 自动/手动提交 |
| RocketMQ | 消费确认（ACK） | 集群/广播模式 |
| RabbitMQ | 消息确认（basic.ack） | 手动/自动确认 |

```text
手动 ACK 的正确顺序（防丢核心）：
  ① 拉取消息
  ② 处理业务（写库/调下游）
  ③ 处理成功 → 提交位点/ACK
  ④ 处理失败 → 不提交 → 重投/死信

错误顺序（常见丢消息原因）：
  先提交后处理 → 处理失败消息已丢
  自动提交 → 处理中宕机 → 重启后位点已过
```

### 5.2 消费重试与幂等

```text
失败重投的两种形式：
  ① 同队列重试（重投原队列，可能乱序）
  ② 重试队列（RocketMQ 16 级重试、Kafka 自定义重试 Topic）

重投必然带来重复消费 → 消费端必须幂等
  —— 这是"至少一次"语义的必然推论
```

## 6. 幂等消费：至少一次的必修课

### 6.1 为什么必须幂等

```text
重复消费的来源（无法彻底避免）：
  ① 生产端重试（幂等生产者只保证单分区内）
  ② 消费端失败重投
  ③ 消费端处理成功但 ACK 丢失
  ④ 消费者重启（位点回退）

结论：只要选"至少一次"，就必须消费幂等
```

### 6.2 幂等方案对比

| 方案 | 原理 | 适用 | 注意 |
|------|------|------|------|
| 唯一键去重表 | 消息 ID/业务键 + 唯一索引 | 写库场景 | 需事务（写库+去重同事务） |
| Redis SETNX | 处理前设锁（带过期） | 快速去重 | 过期时间与处理时长匹配 |
| 状态机校验 | 检查业务状态（已处理则跳过） | 有明确状态流转 | 状态本身要原子 |
| 数据库乐观锁 | version 字段比对 | 更新类 | 冲突重试 |
| Kafka 事务消费 | 处理与位点原子 | 流处理 | 复杂度高 |

```java
// 唯一键去重（写库场景标准姿势）
@Transactional
public void handle(OrderMessage msg) {
    // ① 先去重：insert 唯一键（消息ID）
    // ② 冲突（DuplicateKeyException）→ 已处理过，直接返回
    // ③ 成功 → 处理业务（写订单表等）
    // 去重与业务在同一事务 → 原子性保证
}
```

### 6.3 幂等设计的边界

| 边界 | 说明 |
|------|------|
| 去重表膨胀 | 定期清理（TTL 或归档） |
| 跨系统幂等 | 每个系统各自幂等（去重键约定） |
| 时间窗 | 去重只在"可能重复的时间窗"内有效 |
| 非幂等操作 | 扣款/发券必须幂等键或状态机 |

> 🎯 **核心要点**：可靠性的工程答案 = **生产端重试 + 存储端副本 + 消费端手动 ACK + 消费幂等**。其中"至少一次 + 幂等"是 99% 业务的最优解——不追求理论上的恰好一次，而是用幂等把"重复"变成"无害"。丢消息的排查也按三环节定位：先看配置（acks/刷盘/提交方式），再看代码（重试/幂等/手动 ACK）。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 消息丢在哪三环节？ | 生产发送、Broker 存储、消费处理 |

| 为什么选"至少一次+幂等"？ | 恰好一次端到端成本极高 |
