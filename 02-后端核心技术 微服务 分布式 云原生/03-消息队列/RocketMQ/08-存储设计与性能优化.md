## 1. 存储设计全景

```text
RocketMQ 存储核心三件套：

┌──────────────────────────────────────────────────┐
│                                                  │
│   CommitLog         ConsumeQueue       IndexFile │
│   ┌────────┐       ┌────────┐        ┌────────┐ │
│   │ 混合存储 │       │ 消费索引 │        │ 消息检索 │ │
│   │ 顺序写  │       │ 按队列分│        │Key/时间 │ │
│   │ 固定1GB │       │ 5.72MB  │        │ 400MB  │ │
│   └────────┘       └────────┘        └────────┘ │
│        ↑                ↑                ↑       │
│        └────────────────┼────────────────┘       │
│                         │                        │
│            所有文件通过 MappedByteBuffer 操作       │
│                                                  │
└──────────────────────────────────────────────────┘

核心思想：
  ✅ 写：所有消息顺序追加到 1 个 CommitLog → 100% 顺序写
  ✅ 读：通过 ConsumeQueue（20B/条）→ CommitLog 位置 → 随机读
  ✅ 检：通过 IndexFile（Key Hash）→ 快速定位
```

## 2. CommitLog 详解

### 2.1 文件组织

```text
CommitLog 存储目录：
  /data/rocketmq/store/commitlog/
  ├── 00000000000000000000   (1GB)
  ├── 00000000001073741824   (1GB)
  ├── 00000000002147483648   (1GB)
  └── ...

文件命名：文件名 = 该文件第一个字节的物理偏移量（20位数字）
  00000000000000000000 → offset 0
  00000000001073741824 → offset 1073741824 (1GB)
  
为什么固定 1GB？
  → 方便映射（MappedByteBuffer 建议 ≤ 2GB）
  → 方便清理（按文件删除过期数据）
  → 减少文件描述符
```

### 2.2 MappedByteBuffer 工作原理

```text
传统 I/O vs 内存映射 I/O：

传统 read/write：
  Application → JVM Heap Buffer → OS Kernel Buffer → Disk
  (4 次拷贝，3 次上下文切换)

MappedByteBuffer (mmap)：
  Application Memory ←─→ OS Page Cache ←─→ Disk
  (直接操作内存地址，OS 负责同步)
  (0 次额外拷贝，无上下文切换)

RocketMQ 使用 MappedFile 封装：
  public class MappedFile {
      private MappedByteBuffer mappedByteBuffer;
      private AtomicInteger wrotePosition;   // 当前写入位置
      private AtomicInteger flushedPosition; // 已刷盘位置
      private int fileSize;                  // 文件大小（默认1GB）
  }
```

### 2.3 CommitLog 写入流程

```text
消息写入 CommitLog 流程：

① Producer 发送消息到 Broker
② Broker 获取 CommitLog 写入锁（putMessageLock）
    ⚠️ 串行化！所有 Topic 的消息都要争抢这把锁
③ 序列化消息 → 写入 MappedByteBuffer
    → 更新 wrotePosition（先写内存）
④ 根据刷盘策略决定何时返回：
    ├── ASYNC_FLUSH → 立即返回 Producer ✅（性能高）
    └── SYNC_FLUSH → 调用 mappedByteBuffer.force()
                      → 等待 OS 刷盘→ 返回 Producer
```

## 3. ConsumeQueue 详解

### 3.1 文件结构

```text
ConsumeQueue 文件组织：

  /data/rocketmq/store/consumequeue/
  └── Topic-A/
      ├── 0/                             ← Queue ID
      │   ├── 00000000000000000000       ← 起始偏移量
      │   └── 00000000000006000000
      ├── 1/
      └── 2/

每条 ConsumeQueue 条目（20 字节）：
  ┌──────────────────┬──────────────────┬───────────┐
  │ commitLogOffset   │   size           │  tagHash  │
  │     (8 bytes)     │   (4 bytes)      │ (8 bytes) │
  └──────────────────┴──────────────────┴───────────┘

每个 ConsumeQueue 文件 ≈ 5.72MB（600万条 × 20B / 文件）
  30万条 × 20B（默认）≈ 6MB ← 比 CommitLog(1GB) 小得多
```

### 3.2 异步构建机制

```text
ConsumeQueue 不是写 CommitLog 时同步构建的！

异步构建流程：
① 消息写入 CommitLog → ReputMessageService 被唤醒
② ReputMessageService 从 CommitLog 解析消息
③ 根据 Topic + QueueId → 分发到对应 ConsumeQueue
④ 追加 20 字节条目到 ConsumeQueue

定时触发：
  → ReputMessageService 每隔 1ms 检查一次
  → 或 CommitLog 有新数据时自动触发

延迟影响：
  → ConsumeQueue 构建有毫秒级延迟
  → 消费者可能晚几 ms 才能消费到刚写入的消息
```

### 3.3 消费定位

```text
消费者要消费 Topic-A, Queue=0, Offset=100：

① 打开 Topic-A/0/ 的 ConsumeQueue 文件
② 定位到第 100 个条目（× 20B = offset 2000）
③ 读取 20 字节 → 得到 CommitLog 物理偏移量 + 消息大小
④ 用物理偏移量 → 定位 CommitLog 文件
⑤ 读取完整消息 → 返回 Consumer

⏱ 耗时：
  ConsumeQueue 读 → 顺序读，很快（微秒级）
  CommitLog 读 → 随机读，依赖页缓存（毫秒级）
```

## 4. 刷盘机制

### 4.1 两种刷盘策略

```text
刷盘 = 将内存中的数据写入磁盘

┌────────────────┬──────────────┬──────────────┐
│                │  ASYNC_FLUSH │  SYNC_FLUSH  │
├────────────────┼──────────────┼──────────────┤
│  刷盘时机       │  后台定时     │  立即同步     │
│  Producer 等待  │  不等待       │  等待刷盘完成  │
│  吞吐量         │  高           │  低（1/10）  │
│  延迟           │  低           │  高          │
│  数据安全        │  可能丢       │  不丢        │
│  Broker 宕机    │  丢最近消息   │  不丢        │
│  OS 宕机        │  可能丢       │  不丢        │
└────────────────┴──────────────┴──────────────┘
```

### 4.2 异步刷盘参数

```properties
# Broker 配置
flushDiskType=ASYNC_FLUSH

# 异步刷盘线程
flushCommitLogTimed=false           # 定时刷盘
flushIntervalCommitLog=500          # 500ms 刷一次（默认）
flushCommitLogLeastPages=4          # 至少 4 页（16KB）才刷
flushCommitLogThoroughInterval=10000 # 10s 强制刷一次

# 同步刷盘
flushDiskType=SYNC_FLUSH
syncFlushTimeout=5000               # 同步刷盘超时（5s）
```

### 4.3 可靠性权衡

```text
数据丢失场景分析（ASYNC_FLUSH）：

Broker 宕机（进程崩溃）：
  → MappedByteBuffer 还在 OS 页缓存
  → OS 会负责刷盘
  → 通常不丢数据 ✅

OS 宕机/断电：
  → 页缓存中的数据丢失
  → 丢失最近 500ms 的消息
  → ⚠️ 通过主从同步保障（Slave 可能已收到）

如果要零丢失：
  → SYNC_FLUSH + SYNC_MASTER
  → 或使用 DLedger（Raft Log 已持久化）
```

## 5. 主从同步

### 5.1 同步复制流程

```text
SYNC_MASTER 模式：

Producer                 Master                    Slave
   │ ① send(msg)           │                        │
   │ ─────────────────────→│                        │
   │                        │ ② 写入 CommitLog (内存) │
   │                        │ ③ 发送 msg to Slave    │
   │                        │ ──────────────────────→│
   │                        │                        │ ④ 写入 CommitLog
   │                        │                        │ ⑤ 返回 ACK
   │                        │ ⑥ Slave ACK ←─────────│
   │ ⑦ 返回 SUCCESS        │                        │
   │ ←─────────────────────│                        │

刷盘策略配合：
  Master ASYNC_FLUSH + Slave ASYNC_FLUSH：
    → 通常不丢（双份数据在内存）
    → 双机同时宕机才丢

  Master ASYNC_FLUSH + Slave SYNC_FLUSH：
    → Slave 已落盘
    → 确保至少一份数据在磁盘
```

### 5.2 同步参数

```properties
# 主从同步配置
brokerRole=SYNC_MASTER               # Master 等待 Slave 确认
# 或 brokerRole=ASYNC_MASTER         # Master 不等待

# Slave 配置
haListenPort=10912                   # HA 通信端口
haSendHeartbeatInterval=5000         # 心跳间隔
haHousekeepingInterval=60000         # 连接清理间隔

# Slave 同步策略
haTransferBatchSize=32768            # 每次传输 32KB
haSlaveFallBehindMax=268435456       # Slave 落后 256MB → 认为不同步
```

## 6. 文件恢复与过期清理

### 6.1 崩溃恢复

```text
Broker 宕机重启 → 恢复流程：

① 加载 CommitLog
   → 从最后一个 CommitLog 文件开始
   → 倒序检查每条消息的 CRC 校验
   → 找到最后一个完整消息 → 截断后面的损坏数据

② 重建 ConsumeQueue
   → 从 CommitLog 恢复 ConsumeQueue 条目
   → 保证 ConsumeQueue 与 CommitLog 一致

③ 恢复消费进度
   → 从 consumerOffset.json 加载
   → 可能回退（文件 5s 持久化一次）

④ 恢复 Index
   → 从 CommitLog 重建 IndexFile
```

### 6.2 过期文件清理

```text
清理策略：

① 时间过期（默认）
   fileReservedTime=72            # 保留 72 小时
   deleteWhen=04                  # 凌晨 4 点执行清理

② 磁盘空间触发
   diskMaxUsedSpaceRatio=75       # 磁盘使用率 > 75% → 提前清理

③ 手动清理
   直接删除过期的 CommitLog 文件即可
   对 ConsumeQueue：对应的 Consumer 已消费完的可清理

清理流程：
  ① 检查文件最后修改时间 > fileReservedTime
  ② 检查文件是否被消费引用
  ③ 满足条件 → 删除
```

### 6.3 清理参数

```properties
fileReservedTime=72                # 保留时间（小时）
deleteWhen=04                      # 清理执行时间（凌晨4点）
diskMaxUsedSpaceRatio=75           # 磁盘使用率阈值
deleteCommitLogFilesInterval=100   # 清理间隔（ms）
destroyMapedFileIntervalForcibly=120000 # 强制释放 MappedFile 超时
```

## 7. 性能优化实战

### 7.1 写优化

```properties
# 1. ASYNC_FLUSH（异步刷盘）— 性能提升巨大
flushDiskType=ASYNC_FLUSH

# 2. ASYNC_MASTER（异步复制）
brokerRole=ASYNC_MASTER

# 3. 扩大 CommitLog 文件
mappedFileSizeCommitLog=1073741824  # 1GB（减少文件切换）

# 4. 使用 TransientStorePool（堆外内存池）
transientStorePoolEnable=true
transientStorePoolSize=5            # 5 个 1GB 的堆外 Buffer
# 写入路径：消息 → 堆外内存 → CommitLog（减少 GC 影响）
```

### 7.2 读优化

```properties
# 1. ConsumeQueue 扩大
mapedFileSizeConsumeQueue=6000000  # 600万条/文件

# 2. 页缓存优化 — 让 OS 有更多内存管理页缓存
# JVM 堆不要太大 → 留内存给 OS
-Xms8g -Xmx8g  # 32GB 机器建议只给 JVM 8G，其余给 OS 页缓存

# 3. 关闭不必要的功能
autoCreateTopicEnable=false        # 关闭自动创建
enablePropertyFilter=false         # 不需要 SQL92 过滤时可关闭
```

### 7.3 网络优化

```properties
# Netty 相关
serverSocketSndBufSize=131072      # Socket 发送缓冲 128KB
serverSocketRcvBufSize=131072      # Socket 接收缓冲 128KB
serverPooledByteBufAllocatorEnable=true  # 开启内存池
useEpollNativeSelector=true        # Linux 开启 Epoll
```

## 8. JVM 与 OS 调优

### 8.1 Broker JVM 配置

```bash
# 生产 Broker JVM 推荐（32GB 机器）
JAVA_OPT="${JAVA_OPT} -server -Xms8g -Xmx8g -Xmn4g"
JAVA_OPT="${JAVA_OPT} -XX:MetaspaceSize=128m -XX:MaxMetaspaceSize=320m"
JAVA_OPT="${JAVA_OPT} -XX:+UseG1GC"
JAVA_OPT="${JAVA_OPT} -XX:G1HeapRegionSize=16m"
JAVA_OPT="${JAVA_OPT} -XX:G1ReservePercent=25"
JAVA_OPT="${JAVA_OPT} -XX:InitiatingHeapOccupancyPercent=30"
JAVA_OPT="${JAVA_OPT} -XX:+AlwaysPreTouch"        # 启动时预分配内存

# 直接内存（堆外）
JAVA_OPT="${JAVA_OPT} -XX:MaxDirectMemorySize=15g" # MappedByteBuffer 使用
```

### 8.2 OS 参数

```bash
# /etc/sysctl.conf

# 虚拟内存 — 少用 swap
vm.swappiness=1
vm.dirty_background_ratio=5
vm.dirty_ratio=60

# 最大文件句柄
# /etc/security/limits.conf
rocketmq soft nofile 655360
rocketmq hard nofile 655360

# 最大内存映射数量
vm.max_map_count=655360

# 磁盘调度器（SSD 设为 noop/deadline）
echo noop > /sys/block/sdb/queue/scheduler
```

## 性能调优速查表

| 优化方向 | 参数 | 影响 |
|----------|------|:---:|
| **异步刷盘** | flushDiskType=ASYNC_FLUSH | 吞吐 +10x |
| **异步复制** | brokerRole=ASYNC_MASTER | 延迟 -50% |
| **堆外内存池** | transientStorePoolEnable=true | 减少 GC 暂停 |
| **OS 页缓存** | JVM 堆 < 总内存 50% | 读命中率 |
| **Epoll** | useEpollNativeSelector=true | 网络吞吐 |
| **关闭自动创建** | autoCreateTopicEnable=false | 稳定性 |
| **G1GC** | -XX:+UseG1GC | GC 暂停可控 |

> 🎯 核心公式：**削峰靠异步，可靠靠副本，极速靠内存** — ASYNC_FLUSH + 多副本 + 大内存页缓存 = 生产最佳实践。
