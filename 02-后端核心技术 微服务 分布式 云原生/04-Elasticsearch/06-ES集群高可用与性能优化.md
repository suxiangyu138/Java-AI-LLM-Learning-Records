## 1. 集群架构设计

### 1.1 架构图

```text
                  Client
                     ↓
              Nginx / 负载均衡
                     ↓
       ┌─────────────┬──────────────┬─────────────┐
       ↓             ↓              ↓             ↓
    Node-1        Node-2         Node-3        Node-4
  ┌────────┐   ┌────────┐    ┌────────┐    ┌────────┐
  │P0 R1 R3│   │P1 R2 R4│    │P3 R0 R2│    │ P4 R2  │
  │Master ★│   │ Data   │    │ Data   │    │ Data   │
  └────────┘   └────────┘    └────────┘    └────────┘

  P = Primary Shard（主分片，写入口）
  R = Replica Shard（副本，读负载 + 故障转移）
  ★ = 集群主节点
```

### 1.2 高可用保障机制

| 机制 | 说明 | 影响 |
|------|------|------|
| 主分片故障 | 对应副本分片提升为主分片 | 无中断，自动完成 |
| 数据节点宕机 | 分片自动迁移到其他节点 | 短暂影响，自动恢复 |
| Master 节点宕机 | 集群自动选举新 Master | 几秒内恢复 |
| 网络分区 | 过半 Master 存活则集群继续 | 脑裂时可能有数据丢失 |
| 水平扩展 | 加节点即自动分配分片 | 无需手动干预 |

### 1.3 集群状态颜色

| 颜色 | 含义 | 影响 |
|:----:|------|------|
| GREEN | 所有主分片和副本分片都已正常分配 | 正常 |
| YELLOW | 主分片正常，部分副本未分配 | 可读可写，有丢失风险 |
| RED | 部分主分片未分配 | 数据不可用，需立即排查 |

## 2. 节点角色分离

### 2.1 四种节点角色

| 角色 | `node.master` | `node.data` | `node.ingest` | 职责 |
|------|:-------------:|:-----------:|:-------------:|------|
| Master | true | false | false | 集群管理、选举 |
| Data | false | true | false | 存储、查询、聚合 |
| Ingest | false | false | true | 数据预处理管道 |
| Coordinating | false | false | false | 请求路由、结果归并 |

### 2.2 生产配置

```yaml
# Master 节点
node.master: true
node.data: false
node.ingest: false

# Data 节点
node.master: false
node.data: true
node.ingest: false

# Coordinating 节点（可选）
node.master: false
node.data: false
node.ingest: false
```

### 2.3 节点规模推荐

| 集群规模 | Master | Data | Coordinating |
|----------|:------:|:----:|:-----------:|
| 小（< 5 节点） | 3 混合 | — | — |
| 中（5-20） | 3 专用 | 按需 | 可选 1-2 |
| 大（20+） | 3 专用 | 按需 | 2+ 专用 |

Master 节点数量总是奇数（3 或 5），偶数节点无法形成多数派。

## 3. Master 选举与脑裂

### 3.1 选举机制

ES 使用基于 Bully 算法的改进版进行选主：

```text
1. 当前 Master 心跳超时（默认 30s）
2. 候选节点发起选举投票
3. 获得超过半数（N/2 + 1）投票的节点成为新 Master
4. 新 Master 发布集群状态更新
```

### 3.2 脑裂场景

```text
原集群: [M1★, M2, M3, D1, D2, D3]

      网络分区
         ↓
    [M1★, D1]          [M2, M3, D2, D3]
        ↓                    ↓
    M1 仍是 Master       M2 选为新 Master★

    两个 Master 同时接受写入 → 数据不一致！
```

### 3.3 防止脑裂

```yaml
# ES 7.x+ 自动计算：N/2 + 1（N 为 Master 候选节点数）
# 3 个 Master → 至少 2 个存活
# 5 个 Master → 至少 3 个存活

# 发现与选主配置
discovery.seed_hosts:
  - 192.168.1.10:9300
  - 192.168.1.11:9300
  - 192.168.1.12:9300
cluster.initial_master_nodes:
  - master-1
  - master-2
  - master-3
```

> ⚠️ 公式：`minimum_master_nodes = N / 2 + 1`，一个 Master 节点不能独自决定成为 Master。

## 4. 分片设计与路由

### 4.1 分片数量确定

```text
核心原则：单分片数据量在 20-50GB
总数据量 500GB → 主分片数 = 500 / 30 ≈ 16-20
节点数 >= 主分片数 * (副本数 + 1) / 每个节点分片数
```

| 分片数 | 缺点 |
|:------:|------|
| 过多 | 元数据开销大，聚合合并耗时，GC 压力大 |
| 过少 | 分片太大，迁移慢，无法利用多节点并行 |

### 4.2 副本数建议

| 环境 | 副本数 | 说明 |
|------|:------:|------|
| 开发 | 0 | 省资源 |
| 生产（单机房） | 1 | 可容忍 1 个节点宕机 |
| 生产（核心业务） | 2 | 可容忍 2 个节点宕机 |

### 4.3 路由算法

```text
shard = hash(_routing) % number_of_primary_shards
```

```json
// 自定义 routing 查询，只查一个分片
GET /orders/_search?routing=user_123
{
  "query": { "match": { "user_id": "user_123" } }
}
```

### 4.4 机架感知

```yaml
cluster.routing.allocation.awareness.attributes: rack_id
node.attr.rack_id: rack1
```

```text
      Rack-1              Rack-2
   ┌──────────┐       ┌──────────┐
   │ P0 R1    │       │ R0 P1    │
   │ P2 R0    │       │ R2 P3    │
   └──────────┘       └──────────┘

P0 和 R0 不在同一机架 → 整个机架宕机不丢数据
```

### 6.2 安全下线节点

```json
    "cluster.routing.allocation.exclude._name": "node-to-remove"
```

## 7. 写入性能优化

### 7.1 Bulk 批量写入

```java
public void bulkInsert(List<Goods> list) {
    List<IndexQuery> queries = list.stream()
        .map(g -> new IndexQueryBuilder().withId(String.valueOf(g.getId())).withObject(g).build())
        .collect(Collectors.toList());

    ListUtil.split(queries, 1000).forEach(batch -> {
        BulkOperations ops = restTemplate.opsForBulk()
            .bulkOperation(IndexOperations.IndexAction.INDEX);
        ops.add(batch);
        BulkResponse response = ops.execute();
        if (response.hasFailures()) {
            log.error("Bulk 部分失败: {}", response.buildFailureMessage());
        }
    });
}
```

### 7.2 写入期优化

```json
// 导入前
PUT /my_index/_settings
{
  "refresh_interval": "-1",
  "number_of_replicas": 0
}

// 导入后恢复
PUT /my_index/_settings
{
  "refresh_interval": "1s",
  "number_of_replicas": 1
}
```

### 7.3 写入优化 Checklist

| 优化项 | 调整 | 效果 |
|--------|------|:----:|
| 调大 Refresh Interval | 1s → 30s 或 -1 | 减少 Segment 生成 |
| 关闭副本 | 先设 0，写完再开 | 减少一倍写入量 |
| 异步 Translog | `durability: async` | 减少磁盘 fsync |
| 增加 Bulk 大小 | 每批 5-15MB | 减少网络往返 |
| 多线程并发写 | 线程数 ≈ 节点数 | 提升吞吐 |

## 8. 查询性能优化

### 8.1 优化速查

| 优化项 | 说明 | 效果 |
|--------|------|:----:|
| filter 代替 must | 不计算评分 + 结果可缓存 | 提升 30-50% |
| 限制返回字段 | `_source` 只返回需要的字段 | 减少网络 IO |
| search_after 代替深分页 | 深度分页性能稳定 | 避免 OOM |
| 避免 script 查询 | 脚本无法缓存 | 强制使用索引 |
| 路由优化 | 自定义 routing 减少分片 | 减少分片扫描 |

### 8.2 filter 缓存机制

```json
// ✅ 推荐：filter 自动缓存
{
  "bool": {
    "must": [{ "match": { "title": "手机" } }],
    "filter": [
      { "term": { "status": "ACTIVE" } },
      { "range": { "price": { "gte": 1000 } } }
    ]
  }
}

// ❌ 避免：must 不会缓存
{
  "bool": {
    "must": [
      { "match": { "title": "手机" } },
      { "term": { "status": "ACTIVE" } }
    ]
  }
}
```

> 💡 filter 结果会被 ES 自动缓存（Node Query Cache），相同条件的重复查询几乎零开销。

### 8.3 Force Merge 与慢日志

```json
// 只读索引合并 Segment
POST /logs-2025-01/_forcemerge?max_num_segments=1
```

```yaml
# 慢查询日志
index.search.slowlog.threshold.query.warn: 10s
index.search.slowlog.threshold.query.info: 5s
index.indexing.slowlog.threshold.index.warn: 10s
```

## 9. 索引设计优化

### 9.1 Mapping 设计原则

```json
PUT /my_index
{
  "settings": { "number_of_shards": 3, "number_of_replicas": 1 },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "title": {
        "type": "text", "analyzer": "ik_max_word",
        "fields": { "keyword": { "type": "keyword" } }
      },
      "price": { "type": "float" },
      "status": { "type": "keyword", "norms": false },
      "internal_code": { "type": "keyword", "index": false, "doc_values": false }
    }
  }
}
```

| 原则 | 说明 |
|------|------|
| 显式 Mapping | 禁用 `dynamic`，使用 `strict` 模式 |
| 多字段 | text + keyword 同时支持搜索和聚合 |
| 禁用不必要功能 | `index: false`, `doc_values: false`, `norms: false` |

### 9.2 冷热分离 + ILM

```json
PUT _ilm/policy/my_policy
{
  "policy": {
    "phases": {
      "hot":  { "min_age": "0ms",  "actions": { "rollover": { "max_size": "50GB", "max_age": "1d" } } },
      "warm": { "min_age": "7d",   "actions": { "forcemerge": { "max_num_segments": 1 }, "allocate": { "require": { "data_type": "warm" } } } },
      "cold": { "min_age": "30d",  "actions": { "allocate": { "require": { "data_type": "cold" } } } },
      "delete": { "min_age": "90d", "actions": { "delete": {} } }
    }
  }
}
```

| 节点角色 | 配置 | 数据 |
|---------|------|------|
| Hot 节点 | 高性能 SSD | 近 7 天数据，频繁写入和查询 |
| Warm 节点 | 普通 SSD | 7-30 天数据，偶尔查询 |
| Cold 节点 | HDD | 30 天以上数据，极少查询 |

## 10. JVM 与硬件优化

### 10.1 堆内存配置

```text
# jvm.options
-Xms16g
-Xmx16g
```

| 原则 | 说明 |
|------|------|
| 不超过物理内存 50% | 剩下给 OS Page Cache |
| 不超过 32GB | JVM 指针压缩限制（Compressed Oops） |
| 初始堆 = 最大堆 | 避免动态调整开销 |

### 10.2 硬件推荐

| 硬件 | 推荐 | 原因 |
|------|------|------|
| 磁盘 | SSD，首选 NVMe | ES 严重依赖磁盘 I/O |
| 内存 | 64GB+（堆 16-32G + OS Cache） | Lucene 依赖 OS Page Cache |
| CPU | 8 核+ | 查询、索引、合并都吃 CPU |
| 网络 | 万兆 | 节点间数据传输 |

### 10.3 GC 配置

```text
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:G1HeapRegionSize=4m
-XX:+ParallelRefProcEnabled
-XX:+DisableExplicitGC
```

> 💡 ES 堆内存之外的内存归 OS 管理。OS Page Cache 会缓存倒排索引文件，物理内存要远大于 JVM 堆内存。64GB 物理内存的机器，通常分配 16-32GB 给 JVM，剩余给 OS Cache。

## 11. 监控与故障排查

### 11.1 常用监控命令

```json
// 集群健康
GET _cluster/health

// 节点状态
GET _cat/nodes?v&h=name,heap.percent,ram.percent,cpu,disk.used_percent

// 分片分布
GET _cat/shards?v

// 未分配分片原因
GET _cluster/allocation/explain

// 热点线程
GET _nodes/hot_threads

// 线程池
GET _cat/thread_pool?v&h=node_name,name,active,queue,rejected
```

### 11.2 告警指标

| 指标 | 告警阈值 | 说明 |
|------|:--------:|------|
| Heap Used | > 80% | JVM 堆使用率过高 |
| CPU | 持续 > 80% | 计算资源瓶颈 |
| Disk Used | > 85% | 磁盘即将写满 |
| GC 时间 | > 1s 频繁出现 | GC 停顿影响性能 |
| Thread Pool Rejected | > 0 | 请求被拒绝 |
| Unassigned Shards | > 0 | 分片未分配 |

### 11.3 常见故障

| 故障 | 原因 | 解决方案 |
|------|------|----------|
| 集群 RED | 主分片丢失 | `_cluster/allocation/explain` 查原因；恢复快照或 reroute |
| 集群 YELLOW | 副本未分配 | 增加节点或等待自动分配 |
| 写入拒绝 | bulk 队列满 | 加节点或降低写入速率 |
| 查询超时 | 慢查询 / 数据量大 | 优化查询（filter 代替 must）|
| 磁盘满 | 日志未清理 | 清理旧索引，配置 ILM |
| GC 频繁 | 堆过小或大聚合 | 增大堆；检查大聚合查询 |

## 12. 面试核心要点

**Q: RED/YELLOW/GREEN 各是什么意思？**
GREEN：主副分片都正常。YELLOW：主分片正常，副本未分配。RED：主分片未分配，数据不可用。

**Q: 脑裂怎么防止？**
`minimum_master_nodes = N/2 + 1`（ES 7.x+ 自动计算）。3 个 Master 节点至少存活 2 个才能选举。

**Q: 写入性能怎么优化？**
四步走：批量写入（Bulk 5-15MB）+ 关闭副本 + 调大 refresh_interval + 异步 translog。多线程并发写。

**Q: 为什么 JVM 堆内存不超过 32GB？**
JVM 使用 Compressed Oops（对象指针压缩），32GB 以下指针为 32 位。超过后指针变 64 位，内存消耗翻倍。

**Q: filter 和 must 的区别？**
filter 不计算 _score，结果自动缓存；must 计算 BM25 相关性分数，不缓存。性能敏感场景优先用 filter。

**Q: 主分片数可以修改吗？**
创建后不可修改。路由公式 `hash(_id) % number_of_primary_shards` 依赖分片数。如需修改，必须 Reindex。

> 🎯 **核心原则**：角色分离保稳定，批量写入保速度，filter 缓存保查询，SSD + 大内存保性能。
