## 1. 微服务安全架构：网关统一认证模式

### 1.1 两种主流架构

```text
模式一：网关认证 + 服务互信
  ┌──────┐   JWT   ┌──────────┐  JWT透传  ┌────────────┐
  │ 客户端 │ ─────▶ │  网关      │ ───────▶ │ 服务A/服务B  │
  └──────┘         │ 验签+鉴权  │  (信任透传) │ 各自再验/信任 │
                   └──────────┘           └────────────┘
模式二：服务各自校验
  ┌──────┐   JWT   ┌──────────┐   JWT   ┌────────────┐
  │ 客户端 │ ─────▶ │  网关      │ ─────▶ │ 服务A(自己验签) │
  └──────┘         │ 只做转发  │        └────────────┘
                   └──────────┘
```

| 维度 | 网关统一认证 | 服务各自校验 |
|------|:---:|:---:|
| 实现成本 | 低（安全集中在网关） | 高（每服务配置一遍） |
| 内网安全 | 依赖内网信任 | 强（纵深防御） |
| 服务间调用 | 需透传/传播身份 | 天然携带 |
| 典型场景 | 中小微服务、内部系统 | 金融/高安全要求 |

### 1.2 网关侧（Spring Cloud Gateway + Security）

```java
// 网关：只验签不发业务（JWT 校验 + 白名单路由）
@Bean
SecurityWebFilterChain gatewayChain(ServerHttpSecurity http) throws Exception {
    return http
        .csrf(csrf -> csrf.disable())
        .authorizeExchange(ex -> ex
            .pathMatchers("/auth/**", "/public/**").permitAll()
            .anyExchange().authenticated())
        .oauth2ResourceServer(rs -> rs.jwt(Customizer.withDefaults()))
        .build();
}
```

**身份透传的两种做法：**

| 做法 | 机制 | 适用 |
|------|------|------|
| 透传 JWT | 网关原样转发 Bearer 头 | 服务端信任网关（内网） |
| 改写身份头 | 网关解析后注入 `X-User-Id`/`X-Roles` | 后端不集成 Security 的轻服务 |
| 重新签发 | 网关签发内部短令牌 | 内外部令牌体系隔离 |

> ⚠️ **安全注意**：透传 JWT 时服务端**绝不能信任客户端直传的 `X-User-Id` 头**（客户端可伪造）——身份头必须由网关重写覆盖，或用 `ForwardedFor` 类标准机制。**"信任头"只来自可信边界**。

## 2. 测试：SecurityMockMvc 全解

### 2.1 认证测试

```java
// 注解式（推荐）
@SpringBootTest
@AutoConfigureMockMvc
@WithMockUser(username = "alice", roles = {"USER"})          // 假用户
// @WithMockUser(authorities = {"SCOPE_order:read"})          // 权限维度
// @WithUserDetails("alice")                                  // 走真实 UserDetailsService
// @WithOAuth2User / @WithJwt                               // OAuth2 场景
public class OrderControllerTest {

    @Test
    void adminOnly() throws Exception {
        mockMvc.perform(get("/api/admin"))
               .andExpect(status().isForbidden());   // 无 ADMIN 角色 → 403
    }
}
```

### 2.2 授权测试的三大断言

| 断言 | 语义 |
|------|------|
| `status().isOk()` | 放行 |
| `status().isUnauthorized()` | 未认证（401） |
| `status().isForbidden()` | 已认证无权限（403） |

```java
@Test
@WithMockUser(roles = "ADMIN")
void adminCanAccess() throws Exception {
    mockMvc.perform(get("/api/admin"))
           .andExpect(status().isOk());
}
```

### 2.3 CSRF 与请求级测试

```java
// 表单 POST 需要 CSRF 令牌
mockMvc.perform(post("/do-login")
        .with(csrf())                    // SecurityMockMvcRequestPostProcessors.csrf()
        .param("username", "alice")
        .param("password", "pw"))
    .andExpect(status().is3xxRedirection());

// 无状态 API
mockMvc.perform(post("/api/order")
        .with(jwt().jwt(jwt -> jwt.claim("scope", "order:write")))   // JWT 场景
        .contentType(MediaType.APPLICATION_JSON)
        .content("{\"sku\":\"1\"}"))
    .andExpect(status().isOk());
```

> 💡 **测试纪律**：升级 7.0 前为每条授权规则写测试（PathPattern 差异、dispatch 授权、CSRF 默认值全是静默行为）——**授权测试是迁移的安全网**。

## 3. 迁移到 7.0：完整清单

### 3.1 前置准备（6.5 阶段）

- [ ] 清空所有 deprecation 警告（7.0 删除所有已弃用 API）
- [ ] 6.5 试用 `PathPatternRequestMatcherBuilderFactoryBean` 演练新匹配规则
- [ ] 授权规则测试全覆盖（升级后逐条验证）
- [ ] 评估 CSRF 默认值变化的影响面（Boot 4 起 API 默认开 CSRF）

### 3.2 代码迁移清单

| 6.x 写法 | 7.0 写法 |
|---------|---------|
| `http.authorizeRequests()` | `http.authorizeHttpRequests()` |
| `http.and()` | Lambda DSL（唯一合法） |
| `antMatchers("/x/**")` | `requestMatchers("/x/**")`（PathPattern 规则） |
| `@EnableGlobalMethodSecurity` | `@EnableMethodSecurity` |
| `AuthorizationManager#check` | `#authorize` |
| `WebSecurityConfigurerAdapter` | `SecurityFilterChain` Bean |
| `MvcRequestMatcher`/`AntPathRequestMatcher` | `PathPatternRequestMatcher` |
| Jackson 2 序列化 | Jackson 3（`tools.jackson`），兼容依赖可选 |
| `spring-authorization-server` 独立依赖 | 并入 Security 核心（版本 7.0.0） |
| `@EnableAuthorizationServer` | `OAuth2AuthorizationServerConfigurer` |
| Password grant | 授权码 + PKCE（或 client_credentials） |

### 3.3 行为变化核对（最容易"静默"的部分）

- [ ] dispatch（forward/error）默认参与授权 → `/error` 可能 401
- [ ] CSRF 默认覆盖 API → 无状态接口 403
- [ ] `typ` 头默认校验 → 非标准签发方令牌被拒
- [ ] PKCE 默认强制 → 老授权服务器握手失败
- [ ] 尾斜杠不再匹配、中间 `**` 非法
- [ ] 复杂 SpEL `access()` 建议改写 AuthorizationManager
- [ ] Remember-Me 令牌格式（Jackson 3）变化 → 用户需重新登录

## 5. 面试高频 15 问

**核心机制：**

**Q1：Spring Security 的过滤器链是怎么工作的？**
请求按序穿过 SecurityFilterChain：SecurityContextHolderFilter 恢复身份 → CsrfFilter 校验 → 认证过滤器（表单/Basic/JWT）→ ExceptionTranslationFilter 翻译异常 → AuthorizationFilter 判定放行。认证异常 401，授权异常 403。（01 篇）

**Q2：认证与授权的区别？**
认证=验证凭据建立身份（AuthenticationManager→Provider）；授权=按身份权限判定能否访问（AuthorizationManager#authorize）。前者管"你是谁"，后者管"你能干什么"。（01/03 篇）

**Q3：PasswordEncoder 演进？为什么 MD5 不行？**
MD5 无盐快算彩虹表秒破 → BCrypt 内置盐+自适应成本 → Argon2 内存密集抗 GPU/ASIC（7.0 推荐默认）。DelegatingPasswordEncoder 用 {id} 前缀支持渐进迁移。（02 篇）

**Q4：7.0 有哪些新特性？**
原生 MFA（FactorGrantedAuthority）、模块化配置（Customizer Bean）、授权服务器并入核心、PKCE 默认、Password4j、SPA CSRF DSL（csrf.spa()）、WebClient/RestTemplate OAuth2 支持。（02/05/09 篇）

**Q5：@PreAuthorize 与 @PostAuthorize 区别？**
前者方法执行前校验（权限控制）；后者执行后对返回值校验（数据级控制）。@PostAuthorize 已发生副作用，适合读操作。（04 篇）

**Q6：异步线程里为什么拿不到 SecurityContext？怎么解决？**
ThreadLocal 不跨线程；用 DelegatingSecurityContextExecutor/AsyncTaskExecutor 包装传播，或手动传递。（01/04 篇）

**Web 防护：**

**Q7：CSRF 是什么？Boot 4 升级后接口全 403 为什么？**
CSRF=跨站伪造写请求（Cookie 自动携带）。Boot 4 + Security 7 CSRF 默认覆盖 API；无 Cookie 会话（JWT）可关，Cookie 会话 SPA 用 csrf.spa()。（05 篇）

**Q8：CORS 与 CSRF 的区别？**
CORS=浏览器跨域读取的授权声明；CSRF=防伪造写请求的令牌校验。一个管"允许读"，一个管"不许伪造写"。（05 篇）

**OAuth2：**

**Q9：OAuth2 四种角色与授权码流程？**
资源所有者/客户端/授权服务器/资源服务器。授权码流程：authorize → 用户同意 → 授权码 → 换令牌 → 验签访问。授权码一次性+短效+PKCE 绑定。（07/09 篇）

**Q10：PKCE 防什么？为什么 7.0 默认强制？**
防授权码劫持：恶意应用截获回调授权码也无法换令牌（没有 code_verifier）。OAuth 2.1 精神是收紧安全默认值，7.0 对保密客户端也默认 requireProofKey。（07 篇）

**Q11：密码模式为什么被移除？替代方案？**
客户端代持用户密码违反最小权限原则，风险极大。替代：授权码+PKCE（用户场景）/ client_credentials（机器场景）。（07 篇）

**Q12：JWT 资源服务器的校验链？7.0 新增什么？**
签名、exp、nbf、iss、aud（推荐）、typ（7.0 默认）。typ 不校验可导致混淆攻击（非 JWT 令牌冒充）。（08 篇）

**Q13：JWT 与不透明令牌怎么选？**
JWT 本地验签高性能无状态；不透明令牌 introspection 联网校验可即时撤销。高频 API 用 JWT，强撤销要求用不透明。（08 篇）

**Q14：Spring Authorization Server 现状？**
1.5.x 为最后独立版本，2025-11 并入 Spring Security 7.0 核心；配置模型 OAuth2AuthorizationServerConfigurer；新增 PKCE 默认、动态注册默认、MFA。（09 篇）

**架构：**

**Q15：微服务安全怎么设计？**
网关统一认证（验签+鉴权+白名单）→ 服务信任网关或各自验签（纵深）；身份透传用可信边界重写头，禁止信任客户端直传头；OAuth2 三件套 + JWT + Redis 会话/黑名单组合。（06/10 篇）

## 6. 版本特性速查（2026）

| 版本线 | 关键能力 | 本体系章节 |
|--------|---------|:---:|
| Spring Security 7.0（2025-11-17 GA） | MFA 原生、模块化配置、授权服务器并入、PKCE 默认、Password4j、csrf.spa()、JWT typ 校验 | 01-09 |
| Spring Security 7.0.6 / 7.1.0（2026-06） | CVE 修复（SAML 反序列化、XSS、开放重定向、X.509 冒用） | 10 |
| Spring Authorization Server 1.5.x | 最后独立代际；并入后版本号跟随 7.0.0 | 09 |
| Spring Boot 4.x | CSRF 默认覆盖 API、Jackson 3、JSpecify | 05/10 |

> 💡 **支持周期提醒**：Spring Security 7.0 开源支持至 **2026-12-31**、企业支持至 2027-12-31；7.1 已发布，生产环境及时跟进补丁版本（6 月批次含多项 CVE 修复）。

> 🎯 **核心要点**：生产实践 = 架构（网关统一认证 + 纵深防御）+ 测试（授权规则全覆盖）+ 迁移（先 6.5 清警告再升 7.0）+ 自查（漏洞清单常驻）。面试 = 理解机制胜过背配置——能讲"为什么删缓存""为什么 PKCE 默认""为什么 typ 要校验"的人，才是真的懂安全。
