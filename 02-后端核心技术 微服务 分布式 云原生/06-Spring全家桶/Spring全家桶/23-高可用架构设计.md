## 2. 高可用核心指标与设计原则

### 2.1 可用性指标（SLA）

系统可用性通常用 **SLA（Service Level Agreement）** 来衡量，以"几个9"来表示：

| SLA 等级 | 可用性百分比 | 年停机时间 | 月停机时间 | 周停机时间 | 典型场景 |
|---------|------------|-----------|-----------|-----------|---------|
| 1个9 | 90% | 36.5 天 | 73 小时 | 16.8 小时 | 个人开发环境 |
| 2个9 | 99% | 3.65 天 | 7.3 小时 | 1.68 小时 | 内部管理系统 |
| **3个9** | **99.9%** | **8.76 小时** | **43.8 分钟** | **10.1 分钟** | **中小型商业应用** |
| **4个9** | **99.99%** | **52.56 分钟** | **4.38 分钟** | **1.01 分钟** | **互联网金融、电商** |
| **5个9** | **99.999%** | **5.26 分钟** | **26.3 秒** | **6.05 秒** | **支付核心、电信、银行核心** |
| 6个9 | 99.9999% | 31.5 秒 | 2.63 秒 | 0.605 秒 | 航天、军事系统 |

> 💡 每增加一个 9，系统复杂度和成本大约增加 10 倍。对于大多数互联网业务，**4个9（99.99%）是合理的目标**，追求 5 个 9 以上的成本往往超过预期收益。

### 2.2 MTBF 与 MTTR

可用性的计算公式为：

```text
Availability = MTBF / (MTBF + MTTR)
```

- **MTBF（Mean Time Between Failures，平均无故障时间）**：系统两次故障之间的平均运行时长，衡量系统的可靠性。
- **MTTR（Mean Time To Recovery，平均恢复时间）**：从故障发生到系统完全恢复的平均时长，衡量系统的可恢复性。

| 指标 | 定义 | 提升手段 |
|------|------|---------|
| MTBF | 平均无故障时间 | 代码质量、冗余部署、优雅降级、故障隔离 |
| MTTR | 平均恢复时间 | 自动化监控告警、自动故障转移、预案演练、混沌工程 |

> 💡 **提升可用性的核心思路**：要么让系统更可靠（增加 MTBF），要么让系统恢复更快（减少 MTTR）。在工程实践中，**减少 MTTR 的成本通常低于增加 MTBF**，因此自动化故障恢复是优先策略。

### 2.3 设计原则总览

| 原则 | 英文 | 核心思想 | 典型实现 |
|------|------|---------|---------|
| **冗余** | Redundancy | 消除单点故障（SPOF） | 多副本部署、多机房部署、主从切换 |
| **隔离** | Isolation | 故障范围控制，防止雪崩 | 线程池隔离、机房隔离、微服务独立部署 |
| **限流** | Rate Limiting | 保护系统不被突发流量冲垮 | Nginx限流、Sentinel限流、令牌桶 |
| **降级** | Degradation | 牺牲非核心功能保核心功能 | 关闭非核心功能、返回兜底数据 |
| **熔断** | Circuit Breaker | 自动切断故障调用链路 | Sentinel熔断、Resilience4j、Hystrix |
| **重试** | Retry | 临时故障自动恢复 | Spring Retry、指数退避重试 |
| **幂等** | Idempotency | 重复请求不产生副作用 | 唯一约束、Token机制、状态机 |
| **补偿** | Compensation | 最终一致性保障 | 事务补偿、TCC、Saga模式 |
| **无状态** | Stateless | 任意节点可处理任意请求 | JWT Token、集中式Session |
| **自动化** | Automation | 减少人工操作失误 | 自动部署、自动扩缩容、自动故障恢复 |

### 2.4 CAP 定理在高可用设计中的权衡

CAP 定理指出，分布式系统无法同时满足 **一致性（Consistency）**、**可用性（Availability）** 和 **分区容错性（Partition Tolerance）** 三个特性，最多只能同时满足两个。

```text
         CP（放弃可用性）
        / \
       /   \
      /     \
     /       \
    C -------- A
    一致性    可用性
       \     /
        \   /
         \ /
         P
     分区容错性
```

在高可用架构设计中，通常面临以下选择：

| 场景 | CAP 选择 | 理由 |
|------|---------|------|
| 支付系统、库存扣减 | CP | 数据一致性优先，牺牲部分可用性 |
| 商品详情、用户评论 | AP | 可用性优先，允许短暂不一致 |
| 分布式配置中心（Nacos） | AP（AP模式下） | 保证服务可用，配置最终一致 |
| 分布式注册中心（Eureka） | AP | 宁可返回过期数据，也不让服务不可用 |

> 🎯 **高可用架构的核心取舍**：在大多数互联网场景中，我们选择 **AP + 最终一致性** 的路线。通过幂等设计、补偿机制、消息队列等手段，在保证可用性的前提下，实现数据的最终一致。

## 3. 多集群部署架构

### 3.1 单机房部署（Single DC）

**架构图**：

```text
┌─────────────────────────────────────┐
│            单一数据中心               │
│                                     │
│  ┌────────┐  ┌────────┐  ┌────────┐ │
│  │ Nginx  │  │ Nginx  │  │ Nginx  │ │
│  │ (主)   │  │ (备)   │  │ (备)   │ │
│  └───┬────┘  └────────┘  └────────┘ │
│      │                               │
│  ┌───┴──────────────────────┐       │
│  │     Gateway 集群          │       │
│  └───┬──────────────────────┘       │
│      │                               │
│  ┌───┴──────────────────────┐       │
│  │     应用服务集群           │       │
│  │  [S1] [S2] [S3] [S4]    │       │
│  └───┬──────────────────────┘       │
│      │                               │
│  ┌───┴──────────────────────┐       │
│  │    MySQL 主从集群          │       │
│  │    主库 ↔ 从库1 ↔ 从库2   │       │
│  └──────────────────────────┘       │
└─────────────────────────────────────┘
```

| 项目 | 说明 |
|------|------|
| 优点 | 架构简单、网络延迟低（内网通信）、运维成本低、数据强一致容易实现 |
| 缺点 | 存在单点机房风险（机房断电、光纤被挖断）、无法应对区域级灾难 |
| 适用 | 创业初期、非关键业务系统、对成本敏感的中小型企业 |
| SLA | 99% ~ 99.9%（受限于机房可用性） |

### 3.2 同城双活（Same-City Active-Active）

在同一城市部署两个数据中心，同时承载业务流量。

**架构图**：

```text
                    ┌──────────────────────┐
                    │   DNS / GSLB 全局负载均衡 │
                    │   智能解析 + 健康检查     │
                    └──────────┬──────────────┘
                               │
          ┌────────────────────┼────────────────────┐
          │                    │                    │
  ┌───────▼─────────┐  ┌───────▼─────────┐
  │  数据中心 A（同城）│  │  数据中心 B（同城）│
  │                 │  │                 │
  │  ┌──────────┐   │  │  ┌──────────┐   │
  │  │ LVS/Nginx │   │  │  │ LVS/Nginx │   │
  │  └─────┬────┘   │  │  └─────┬────┘   │
  │  ┌─────▼────┐   │  │  ┌─────▼────┐   │
  │  │ Gateway  │   │  │  │ Gateway  │   │
  │  └─────┬────┘   │  │  └─────┬────┘   │
  │  ┌─────▼────┐   │  │  ┌─────▼────┐   │
  │  │ 应用服务  │   │  │  │ 应用服务  │   │
  │  │ 集群     │   │  │  │ 集群     │   │
  │  └─────┬────┘   │  │  └─────┬────┘   │
  │        │        │  │        │        │
  │  ┌─────▼────┐   │  │  ┌─────▼────┐   │
  │  │ MySQL A  │   │  │  │ MySQL B  │   │
  │  │ (主←→主) │◄──┼──┼──►│ (主←→主) │   │
  │  └──────────┘   │  │  └──────────┘   │
  │                 │  │                 │
  │  ┌──────────┐   │  │  ┌──────────┐   │
  │  │ Redis A  │◄──┼──┼──►│ Redis B  │   │
  │  └──────────┘   │  │  └──────────┘   │
  └─────────────────┘  └─────────────────┘
```

| 项目 | 说明 |
|------|------|
| 数据同步 | MySQL 主主同步（双向复制）、Redis 跨机房复制 |
| 流量分配 | DNS 轮询 + GSLB 智能解析（按运营商、按权重） |
| 切换时间 | 分钟级（DNS 解析生效 TTL + 健康检查检测时间） |
| 优点 | 利用率高（两个机房同时承载流量）、切换速度快、RPO≈0（同城专线延迟 < 2ms） |
| 缺点 | 无法应对区域性灾难（同城地震、洪水）、主主同步存在数据冲突风险 |
| 适用 | 中小型互联网公司、金融行业同城灾备 |
| SLA | 99.99% |

> ⚠️ **同城双活的核心风险**：MySQL 主主同步可能产生数据冲突（如两个机房同时修改同一条记录），建议采用"按业务维度拆分写流量"（如用户ID奇偶分库），或使用 Semi-Sync 复制避免数据丢失。

| 适用 | 金融、支付、大型互联网企业 |
| SLA | 99.995% |

### 3.4 异地多活（Multi-Site Active-Active / 单元化架构）

在全球或全国多个地域部署完整的业务单元，每个单元独立处理本区域的用户请求。

**架构图**：

```text
┌─────────────────────────────────────────────────────────────────┐
│                     GSLB 全局负载均衡（用户就近接入）              │
│            DNS 智能解析 → 按用户地理位置路由                       │
└───────┬─────────────┬─────────────┬───────────────┬────────────┘
        │             │             │               │
┌───────▼──────┐ ┌─────▼──────┐ ┌───▼──────┐  ┌─────▼──────┐
│  单元 1      │ │  单元 2    │ │  单元 3  │  │  单元 N    │
│  华北区      │ │  华东区    │ │  华南区  │  │  海外区    │
│              │ │            │ │          │  │            │
│ ┌──────────┐ │ │ ┌────────┐ │ │ ┌──────┐ │  │ ┌────────┐ │
│ │ APP 集群  │ │ │ │APP集群 │ │ │ │APP.. │ │  │ │APP集群 │ │
│ ├──────────┤ │ │ ├────────┤ │ │ ├──────┤ │  │ ├────────┤ │
│ │ MySQL    │ │ │ │MySQL   │ │ │ │MySQL │ │  │ │MySQL   │ │
│ │ (主)     │ │ │ │(主)    │ │ │ │(主)  │ │  │ │(主)    │ │
│ ├──────────┤ │ │ ├────────┤ │ │ ├──────┤ │  │ ├────────┤ │
│ │ Redis    │ │ │ │Redis   │ │ │ │Redis │ │  │ │Redis   │ │
│ ├──────────┤ │ │ ├────────┤ │ │ ├──────┤ │  │ ├────────┤ │
│ │ MQ       │ │ │ │MQ      │ │ │ │MQ    │ │  │ │MQ      │ │
│ └──────────┘ │ │ └────────┘ │ │ └──────┘ │  │ └────────┘ │
│  数据范围：  │ │  数据范围：│ │  数据范围│  │  数据范围：│
│  user_id%N  │ │  user...  │ │  user... │  │  user...   │
│  = 0        │ │  = 1      │ │  = 2     │  │  = N-1     │
└──────────────┘ └────────────┘ └──────────┘  └────────────┘
```

**单元化架构的核心要素**：

1. **数据分片（Sharding）**：按用户维度将数据水平切分到各个单元，每个单元只处理本单元的数据。
2. **流量路由**：根据用户标识（user_id）将请求路由到正确的单元。
3. **单元自治**：每个单元拥有完整的业务能力（应用 + 数据库 + 缓存 + MQ），不依赖跨单元调用。
4. **跨单元通信**：全局唯⼀数据通过消息队列异步同步。

| 项目 | 说明 |
|------|------|
| 数据分片策略 | user_id % N、user_id 按地理范围划分、按业务类型划分 |
| 跨单元数据 | 全局配置数据全单元复制，用户数据按分片归属 |
| 扩容方式 | 增加单元数，对存量数据做 rehash 迁移 |
| 跨单元延迟 | 异地 20~100ms（专线） |
| 优点 | 无限扩展能力（水平扩容）、区域级容灾、用户体验好（就近接入） |

## 4. 限流降级熔断兜底方案

### 4.1 分层保护架构

```text
                        ┌──────────────┐
                        │   用户请求    │
                        └──────┬───────┘
                               │
                    ┌──────────▼──────────┐
        第1层       │    Nginx 限流        │  ← ngx_http_limit_req_module
                    │    (接入层限流)      │    连接数限制、请求速率限制
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
        第2层       │  Gateway 限流        │  ← RequestRateLimiter
                    │  (网关层限流)        │    Redis 令牌桶
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
        第3层       │  Sentinel 限流       │  ← QPS 限流、线程数限流
                    │  (服务层限流)        │    热点限流、集群限流
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
        第4层       │  线程池隔离          │  ← 线程池隔离、信号量隔离
                    │  (资源隔离层)        │    防止级联故障
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
        第5层       │  降级兜底            │  ← 默认返回值、本地缓存
                    │  (业务兜底层)        │    Mock 服务、Fallback
                    └─────────────────────┘
```

> 💡 分层限流的核心思想：**越靠近用户端，限流粒度越粗；越靠近服务端，限流粒度越精细**。Nginx 限制总入口流量，Gateway 限制 API 维度流量，Sentinel 限制方法维度流量。

### 4.2 Nginx 层限流

Nginx 提供两个核心限流模块：

#### 4.2.1 ngx_http_limit_req_module（请求速率限制）

```nginx
# 定义限流区域：rate=10r/s 表示每秒 10 个请求
# burst=20 表示最大突发 20 个请求
# nodelay 表示不延迟处理突发请求
http {
    # 定义共享内存区域，用于存储请求计数
    # $binary_remote_addr 以客户端 IP 为限流维度
    limit_req_zone $binary_remote_addr zone=mylimit:10m rate=10r/s;

    # 基于 Server 级别的限流
    limit_req_zone $server_name zone=serverlimit:10m rate=100r/s;

    # 基于 URI 级别的限流
    limit_req_zone $request_uri zone=urilimit:10m rate=50r/s;

    server {
        listen 80;
        server_name api.example.com;

        location /api/ {
            # 应用限流
            limit_req zone=mylimit burst=20 nodelay;

            # 超过限流后的返回码
            limit_req_status 429;

            proxy_pass http://backend;
        }

        location /api/order/ {
            # 更严格的限流：订单接口 5r/s
            limit_req zone=ordermlimit:10m rate=5r/s burst=10 nodelay;
            limit_req_status 429;
            proxy_pass http://order_backend;
        }

        location /api/login/ {
            # 登录接口限流：1r/s，防止暴力破解
            limit_req zone=loginlimit:10m rate=1r/s burst=5 nodelay;
            limit_req_status 429;
            proxy_pass http://login_backend;
        }
    }
}
```

#### 4.2.2 ngx_http_limit_conn_module（并发连接数限制）

```nginx
http {
    # 定义连接数限制区域
    limit_conn_zone $binary_remote_addr zone=connlimit:10m;
    limit_conn_zone $server_name zone=server_conn:10m;

    server {
        listen 80;
        server_name api.example.com;

        location /api/ {
            # 每个 IP 最大并发连接数 20
            limit_conn connlimit 20;
            # 限制单个服务器最大连接数 500
            limit_conn server_conn 500;
            # 超过限制返回 503
            limit_conn_status 503;

            proxy_pass http://backend;
        }

        location /download/ {
            # 下载接口：限制每个 IP 同时 5 个连接
            limit_conn connlimit 5;
            limit_conn_status 503;
            proxy_pass http://download_backend;
        }
    }
}
```

### 4.3 Gateway 层限流

Spring Cloud Gateway 基于 Redis 令牌桶算法实现 `RequestRateLimiter` 过滤器。

#### 4.3.1 依赖配置

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis-reactive</artifactId>
</dependency>
```

#### 4.3.2 基于 Path 的限流配置

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/order/**
          filters:
            - name: RequestRateLimiter
              args:
                # 限流 Key 解析器 Bean 名称
                key-resolver: "#{@pathKeyResolver}"
                # 令牌桶每秒填充速率
                redis-rate-limiter.replenishRate: 100
                # 令牌桶最大容量
                redis-rate-limiter.burstCapacity: 200
                # 每秒请求数，按需返回给客户端
                redis-rate-limiter.requestedTokens: 1
            - StripPrefix=1

        - id: user-service
          uri: lb://user-service
          predicates:
            - Path=/api/user/**
          filters:
            - name: RequestRateLimiter
              args:
                key-resolver: "#{@userKeyResolver}"
                redis-rate-limiter.replenishRate: 200
                redis-rate-limiter.burstCapacity: 400
```

#### 4.3.3 Key Resolver 实现

```java
import org.springframework.cloud.gateway.filter.ratelimit.KeyResolver;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import reactor.core.publisher.Mono;

/**
 * Gateway 限流 Key 解析器
 */
@Configuration
public class RateLimiterConfig {

    /**
     * 按请求路径限流：不同路径分配不同速率
     */
    @Bean
    public KeyResolver pathKeyResolver() {
        return exchange -> Mono.just(
            exchange.getRequest().getURI().getPath()
        );
    }

    /**
     * 按用户 ID 限流：每个用户独立限流
     */
    @Bean
    public KeyResolver userKeyResolver() {
        return exchange -> Mono.just(
            exchange.getRequest().getHeaders()
                .getFirst("X-User-Id") != null
                ? exchange.getRequest().getHeaders().getFirst("X-User-Id")
                : exchange.getRequest().getRemoteAddress().getHostString()
        );
    }

    /**
     * 按客户端 IP 限流
     */
    @Bean
    public KeyResolver remoteAddrKeyResolver() {
        return exchange -> Mono.just(
            exchange.getRequest().getRemoteAddress().getAddress().getHostAddress()
        );
    }
}
```

### 4.4 Sentinel 层限流

Sentinel 是面向分布式系统的流量防卫兵组件，提供限流、熔断降级、系统保护等能力。

#### 4.4.1 核心概念

| 概念 | 说明 |
|------|------|
| 资源（Resource） | 被 Sentinel 保护的 API、方法、代码块 |
| 规则（Rule） | 定义如何保护资源的策略（流控规则、降级规则、热点规则） |
| Slot Chain | 规则检查的责任链模式 |
| 统计数据 | 秒级滑动窗口统计 QPS、RT、异常数等指标 |

#### 4.4.2 流控模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **QPS** | 每秒请求数限流 | 接口限流、API 限流 |
| **线程数** | 并发线程数限流 | 数据库连接池、慢调用隔离 |

**配置示例**：

```java
import com.alibaba.csp.sentinel.annotation.SentinelResource;
import com.alibaba.csp.sentinel.slots.block.BlockException;
import com.alibaba.csp.sentinel.slots.block.RuleConstant;
import com.alibaba.csp.sentinel.slots.block.flow.FlowRule;
import com.alibaba.csp.sentinel.slots.block.flow.FlowRuleManager;
import jakarta.annotation.PostConstruct;
import org.springframework.stereotype.Service;

import java.util.ArrayList;
import java.util.List;

@Service
public class SentinelFlowConfig {

    /**
     * 初始化流控规则
     */
    @PostConstruct
    public void initFlowRules() {
        List<FlowRule> rules = new ArrayList<>();

        // 规则1：QPS 限流 - createOrder 接口最大 100 QPS
        FlowRule qpsRule = new FlowRule();
        qpsRule.setResource("createOrder");
        qpsRule.setGrade(RuleConstant.FLOW_GRADE_QPS);  // QPS 模式
        qpsRule.setCount(100);                           // 阈值
        qpsRule.setLimitApp("default");                  // 默认不区分调用来源
        qpsRule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_DEFAULT); // 快速失败
        rules.add(qpsRule);

        // 规则2：线程数限流 - slowMethod 最大并发 10
        FlowRule threadRule = new FlowRule();
        threadRule.setResource("slowMethod");
        threadRule.setGrade(RuleConstant.FLOW_GRADE_THREAD); // 线程数模式
        threadRule.setCount(10);
        threadRule.setLimitApp("default");
        rules.add(threadRule);

        FlowRuleManager.loadRules(rules);
    }
}
```

#### 4.4.3 流控效果

| 效果 | 说明 | 适用场景 |
|------|------|---------|
| **快速失败**（默认） | 超出阈值直接抛出 BlockException | 对延迟敏感、需要快速响应的接口 |
| **Warm Up** | 阈值从 coldFactor 逐步提升到设定值，避免冷启动雪崩 | 缓存预热、数据库连接池初始化 |
| **排队等待** | 匀速通过，超出等待时间的请求失败 | 削峰填谷，处理突发流量 |

**Warm Up 配置**：

```java
FlowRule warmUpRule = new FlowRule();
warmUpRule.setResource("warmUpResource");
warmUpRule.setGrade(RuleConstant.FLOW_GRADE_QPS);
warmUpRule.setCount(1000);                             // 最终阈值 1000 QPS
warmUpRule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_WARM_UP);
warmUpRule.setWarmUpPeriodSec(10);                      // 预热时间 10 秒
// 默认 coldFactor = 3，起始阈值为 1000 / 3 ≈ 333 QPS
```

**排队等待配置**：

```java
FlowRule queuedRule = new FlowRule();
queuedRule.setResource("queuedResource");
queuedRule.setGrade(RuleConstant.FLOW_GRADE_QPS);
queuedRule.setCount(500);                               // 匀速通过 500 QPS
queuedRule.setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER);
queuedRule.setMaxQueueingTimeMs(500);                    // 最长排队等待 500ms
```

#### 4.4.4 Sentinel 资源注解使用

```java
import com.alibaba.csp.sentinel.annotation.SentinelResource;
import com.alibaba.csp.sentinel.slots.block.BlockException;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/order")
public class OrderController {

    /**
     * 限流：createOrder 资源 QPS 超过 100 时限流
     * fallback：业务异常降级
     * blockHandler：限流/熔断触发的降级
     */
    @SentinelResource(
        value = "createOrder",
        blockHandler = "createOrderBlockHandler",
        blockHandlerClass = OrderBlockHandler.class,
        fallback = "createOrderFallback",
        fallbackClass = OrderFallback.class
    )
    @PostMapping("/create")
    public Result createOrder(@RequestBody OrderDTO orderDTO) {
        // 业务逻辑
        return Result.success(orderService.create(orderDTO));
    }
}

/**
 * 限流降级处理类
 */
public class OrderBlockHandler {

    /**
     * 注意：静态方法，参数必须与原始方法一致 + BlockException 参数
     */
    public static Result createOrderBlockHandler(OrderDTO orderDTO, BlockException ex) {
        // 记录限流日志
        System.err.println("【限流触发】createOrder 被限流：" + ex.getMessage());
        // 返回友好的限流提示
        return Result.error(429, "系统繁忙，请稍后重试");
    }
}

/**
 * 业务异常降级
 */
public class OrderFallback {

    public static Result createOrderFallback(OrderDTO orderDTO, Throwable ex) {
        System.err.println("【降级触发】createOrder 异常：" + ex.getMessage());
        return Result.error(500, "服务异常，请稍后重试");
    }
}
```

#### 4.4.5 熔断降级规则

Sentinel 熔断降级支持三种熔断策略：

##### 慢调用比例（Slow Call Ratio）

```java
import com.alibaba.csp.sentinel.slots.block.degrade.DegradeRule;
import com.alibaba.csp.sentinel.slots.block.degrade.DegradeRuleManager;
import com.alibaba.csp.sentinel.slots.block.degrade.circuitbreaker.CircuitBreakerStrategy;

import java.util.ArrayList;
import java.util.List;

public class DegradeRuleConfig {

    public static void initSlowCallRule() {
        List<DegradeRule> rules = new ArrayList<>();

        DegradeRule slowCallRule = new DegradeRule("slowMethod")
            .setGrade(CircuitBreakerStrategy.SLOW_REQUEST_RATIO.getType())  // 慢调用比例
            .setCount(500)                      // 慢调用阈值：RT > 500ms 算慢调用
            .setTimeWindow(30)                  // 熔断时长：30秒（半开恢复时间）
            .setStatIntervalMs(2000)            // 统计时长：2秒
            .setMinRequestAmount(10)            // 触发熔断的最小请求数：10
            .setSlowRatioThreshold(0.5);        // 慢调用比例阈值：50%

        rules.add(slowCallRule);
        DegradeRuleManager.loadRules(rules);
    }
}
```

#### 4.4.6 熔断器状态机

```text
                    ┌─────────────────────────┐
                    │     CLOSED（关闭状态）      │
                    │   正常工作，请求正常通过    │
                    └───────────┬─────────────┘
                                │
                  触发条件：慢调用/异常比例/异常数
                  超过阈值
                                │
                                ▼
                    ┌─────────────────────────┐
                    │     OPEN（开启状态）        │
                    │   请求直接降级，不执行业务    │
                    │   等待 TimeWindow 超时      │
                    └───────────┬─────────────┘
                                │
                  TimeWindow 超时后，进入 HALF_OPEN
                                │
                                ▼
                    ┌─────────────────────────┐
                    │   HALF_OPEN（半开状态）     │
                    │   允许少量探测请求通过      │
                    └───────────┬─────────────┘
                                │
                    ┌───────────┴─────────────┐
                    │                         │
             探测请求成功                  探测请求失败
                    │                         │
                    ▼                         ▼
            ┌──────────────┐         ┌──────────────┐
            │   CLOSED     │         │    OPEN      │
            │  恢复正常    │         │  再次熔断    │
            └──────────────┘         └──────────────┘
```

#### 4.4.7 热点限流

```java
import com.alibaba.csp.sentinel.slots.block.flow.param.ParamFlowRule;
import com.alibaba.csp.sentinel.slots.block.flow.param.ParamFlowRuleManager;
import com.alibaba.csp.sentinel.annotation.SentinelResource;

import java.util.Arrays;

public class HotParamRuleConfig {

    public static void initHotParamRule() {
        ParamFlowRule rule = new ParamFlowRule("getProduct")
            .setParamIdx(0)           // 对第一个参数限流（productId）
            .setCount(100);           // 单机阈值 100 QPS

        // 针对特定商品 ID 设置不同阈值
        // 参数值为 10001（爆款商品），阈值 10 QPS
        rule.setParamFlowItemList(
            Arrays.asList(
                new ParamFlowItem().setObject("10001").setCount(10)
            )
        );

        ParamFlowRuleManager.loadRules(Arrays.asList(rule));
    }
}

@Service
public class ProductService {

    @SentinelResource(value = "getProduct", blockHandler = "getProductBlockHandler")
    public Product getProduct(Long productId) {
        // 热点参数 productId 若为 10001（爆款），限流更严格
        return productDao.selectById(productId);
    }

    public Product getProductBlockHandler(Long productId, BlockException ex) {
```

### 4.7 限流算法对比

| 算法 | 原理 | 优点 | 缺点 | 适用场景 | 实现复杂度 |
|------|------|------|------|---------|-----------|
| **计数器** | 固定时间窗口内计数达到阈值后拒绝 | 实现简单、内存占用小 | 存在临界问题（时间窗口切换瞬间流量可以翻倍） | 简单接口限流 | ⭐ |
| **滑动窗口** | 将时间窗口分成多个小格子，滑动统计 | 解决了计数器临界问题，精度可调 | 内存占用高于计数器 | 通用限流场景 | ⭐⭐ |
| **令牌桶** | 匀速生成令牌存入桶中，请求消耗令牌 | 允许一定突发流量，平滑输出 | 需要配置合理的速率和容量 | API 限流、Gateway 限流 | ⭐⭐⭐ |
| **漏桶** | 请求以固定速率流出，超出桶容量则丢弃 | 输出流量绝对平滑，无突发 | 无法应对突发流量，可能导致大量请求被拒 | 保护下游系统（数据库、MQ） | ⭐⭐⭐ |

**滑动窗口算法代码示例**：

```java
import java.util.LinkedList;
import java.util.Queue;

/**
 * 滑动窗口限流算法
 */
public class SlidingWindowRateLimiter {
    private final long windowSizeMs;       // 窗口大小（毫秒）
    private final int maxRequests;         // 窗口内最大请求数
    private final Queue<Long> timestamps;  // 请求时间戳队列

    public SlidingWindowRateLimiter(long windowSizeMs, int maxRequests) {
        this.windowSizeMs = windowSizeMs;
        this.maxRequests = maxRequests;
        this.timestamps = new LinkedList<>();
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();

        // 移除窗口外的过期时间戳
        while (!timestamps.isEmpty() && now - timestamps.peek() > windowSizeMs) {
            timestamps.poll();
        }

        // 检查是否超出阈值
        if (timestamps.size() < maxRequests) {
            timestamps.offer(now);
            return true;  // 通过
        }

        return false;  // 限流
    }
}
```

**令牌桶算法代码示例**：

```java
import java.util.concurrent.atomic.AtomicLong;

/**
 * 令牌桶限流算法（基于时间戳计算）
 */
public class TokenBucketRateLimiter {
    private final long capacity;           // 桶容量
    private final long refillRate;         // 令牌补充速率（个/秒）
    private final AtomicLong tokens;       // 当前令牌数
    private volatile long lastRefillTime;  // 上次补充时间

    public TokenBucketRateLimiter(long capacity, long refillRate) {
        this.capacity = capacity;
        this.refillRate = refillRate;
        this.tokens = new AtomicLong(capacity);
        this.lastRefillTime = System.currentTimeMillis();
    }

    public boolean tryAcquire(long permits) {
        refill();
        while (true) {
            long currentTokens = tokens.get();
            if (currentTokens < permits) {
                return false;  // 令牌不足
            }
            if (tokens.compareAndSet(currentTokens, currentTokens - permits)) {
                return true;   // 获取成功
            }
            // CAS 失败重试
        }
    }

    private void refill() {
        long now = System.currentTimeMillis();
        long elapsed = now - lastRefillTime;
        if (elapsed > 0) {
            long newTokens = elapsed * refillRate / 1000;
            if (newTokens > 0) {
                // 补充令牌，不超过容量
                tokens.accumulateAndGet(newTokens, (current, added) ->
                    Math.min(current + added, capacity));
                lastRefillTime = now;
            }
        }
    }
}
```

**漏桶算法代码示例**：

```java
import java.util.concurrent.atomic.AtomicLong;

/**
 * 漏桶限流算法
 */
public class LeakyBucketRateLimiter {
    private final long capacity;          // 桶容量
    private final long leakRate;          // 漏水速率（个/秒）
    private final AtomicLong water;       // 当前水量
    private volatile long lastLeakTime;   // 上次漏水时间

    public LeakyBucketRateLimiter(long capacity, long leakRate) {
        this.capacity = capacity;
        this.leakRate = leakRate;
        this.water = new AtomicLong(0);
        this.lastLeakTime = System.currentTimeMillis();
    }

    public boolean tryAcquire() {
        // 先漏水
        leak();

        // 尝试加水
        while (true) {
            long currentWater = water.get();
            if (currentWater >= capacity) {
                return false;  // 桶满了，拒绝请求
            }
            if (water.compareAndSet(currentWater, currentWater + 1)) {
                return true;   // 加水成功
            }
        }
    }

    private void leak() {
        long now = System.currentTimeMillis();
        long elapsed = now - lastLeakTime;
        if (elapsed > 0) {
            long leaked = elapsed * leakRate / 1000;
            if (leaked > 0) {
                water.accumulateAndGet(leaked, (current, l) ->
                    Math.max(0, current - l));
                lastLeakTime = now;
            }
        }
    }
}
```

## 5. 接口幂等设计方案

### 5.1 什么是幂等性

**幂等性（Idempotency）** 是指无论调用接口多少次（一次或多次），产生的实际效果与调用一次完全相同。

> 💡 幂等性是高可用系统中"重试安全"的基石。没有幂等保证，网络超时重试就会导致重复下单、重复扣款等严重生产事故。

### 5.2 为什么需要幂等

| 场景 | 问题描述 | 后果 |
|------|---------|------|
| **网络超时重试** | 客户端发出请求后超时，重试导致多次请求到达服务端 | 重复下单、重复支付 |
| **MQ 消息重复消费** | 消息队列保证 At-Least-Once 投递，Consumer 可能收到重复消息 | 重复扣减库存、重复发货 |
| **前端重复提交** | 用户快速点击"提交"按钮，连续发送多个请求 | 重复创建订单、重复退款 |
| **第三方回调重试** | 支付回调、短信回调等会重复推送 | 重复更新订单状态、重复发放积分 |
| **定时任务重复执行** | 集群中多个节点同时执行同一任务 | 重复对账、重复发送通知 |

### 5.3 六种幂等方案详解

#### 方案一：数据库唯一约束

**原理**：利用数据库表的唯一索引约束，重复插入时抛出 DuplicateKeyException，捕获后返回已有数据。

**适用场景**：创建订单、注册账号、创建支付单等"插入"场景。

```java
/**
 * 订单表 - 利用 order_no 唯一约束保证幂等
 */
@Entity
@Table(name = "t_order",
       uniqueConstraints = @UniqueConstraint(name = "uk_order_no", columnNames = "order_no"))
public class Order {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "order_no", nullable = false, length = 64)
    private String orderNo;  // 业务单号，全局唯一

    @Column(name = "user_id")
    private Long userId;

    @Column(name = "amount")
    private BigDecimal amount;

    @Column(name = "status")
    private String status;  // NEW / PAID / SHIPPED / DONE / CANCELLED
}

/**
 * 订单服务 - 唯一约束幂等实现
 */
@Service
@Slf4j
public class OrderService {

    @Autowired
    private OrderMapper orderMapper;

    /**
     * 创建订单 - 幂等实现
     */
    public Result createOrder(OrderCreateDTO dto) {
        // 1. 前置检查：order_no 必须存在（由业务层生成）
        if (dto.getOrderNo() == null || dto.getOrderNo().isEmpty()) {
            return Result.error("订单号不能为空");
        }

        // 2. 尝试插入，利用数据库唯一约束
        Order order = new Order();
        order.setOrderNo(dto.getOrderNo());
        order.setUserId(dto.getUserId());
        order.setAmount(dto.getAmount());
        order.setStatus("NEW");

        try {
            orderMapper.insert(order);  // 唯一约束冲突会抛出异常
            log.info("订单创建成功：orderNo={}", dto.getOrderNo());
            return Result.success(order);
        } catch (DuplicateKeyException e) {
            // 3. 唯一约束冲突说明订单已存在，查询返回已有订单
            log.warn("订单已存在，返回已有订单：orderNo={}", dto.getOrderNo());
            Order existingOrder = orderMapper.selectByOrderNo(dto.getOrderNo());
            return Result.success(existingOrder);
        }
    }
}
```

#### 方案二：Redis Token 机制

**原理**：业务请求前先获取一个不重复的 Token，业务提交时必须携带该 Token，服务端校验并删除 Token（通过 Redis `SET NX` + Lua 保证原子性）。

**适用场景**：前端防重复提交、支付收银台、关键业务操作。

```text
时序：
┌──────────┐                    ┌──────────┐                    ┌──────────┐
│  前端     │                    │  后端     │                    │  Redis   │
└────┬─────┘                    └────┬─────┘                    └────┬─────┘
     │  1. GET /api/token             │                              │
     │ ─────────────────────────────► │                              │
     │                                │  2. SET token_id "1" NX EX 60│
     │                                │ ────────────────────────────►│
     │  3. 返回 token_id              │                              │
     │ ◄───────────────────────────── │                              │
     │                                │                              │
     │  4. POST /api/order + token    │                              │
     │ ─────────────────────────────► │                              │
     │                                │  5. Lua: GET + DEL token    │
     │                                │ ────────────────────────────►│
     │                                │  6. token 校验通过          │
     │  7. 返回订单结果               │                              │
     │ ◄───────────────────────────── │                              │
     └────────────────────────────────┘──────────────────────────────┘
```

**后端代码实现**：

```java
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.Arrays;
import java.util.UUID;
import java.util.concurrent.TimeUnit;

/**
 * Token 幂等服务
 */
@Service
public class IdempotentTokenService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    // Lua 脚本：原子性 GET 并 DEL，防止并发问题
    private static final String CHECK_AND_DEL_LUA =
        "local val = redis.call('GET', KEYS[1]); " +
        "if val == ARGV[1] then " +
        "    redis.call('DEL', KEYS[1]); " +
        "    return 1; " +
        "else " +
        "    return 0; " +
        "end;";

    /**
     * 创建幂等 Token（前端在提交业务请求前调用）
     */
    public String createToken(String bizKey) {
        String token = UUID.randomUUID().toString().replace("-", "");
        String redisKey = buildTokenKey(bizKey);
        // SET NX EX 60：存在则返回 false，否则设置并设置过期时间 60 秒
        Boolean success = redisTemplate.opsForValue()
            .setIfAbsent(redisKey, token, 60, TimeUnit.SECONDS);
        if (Boolean.TRUE.equals(success)) {
            return token;
        }
        throw new BusinessException("请勿重复获取Token");
    }

    /**
     * 校验并删除 Token（业务提交时调用）
     */
    public boolean checkAndDeleteToken(String bizKey, String token) {
        String redisKey = buildTokenKey(bizKey);
        DefaultRedisScript<Long> script = new DefaultRedisScript<>(CHECK_AND_DEL_LUA, Long.class);
        Long result = redisTemplate.execute(script, Arrays.asList(redisKey), token);
        return Long.valueOf(1L).equals(result);
    }

    private String buildTokenKey(String bizKey) {
        return "idempotent:token:" + bizKey;
    }
}

/**
 * 订单 Controller - 使用 Token 机制防重复提交
 */
@RestController
@RequestMapping("/order")
public class OrderController {

    @Autowired
    private IdempotentTokenService tokenService;

    @Autowired
    private OrderService orderService;

    /**
     * 获取幂等 Token
     */
    @GetMapping("/token")
    public Result<String> getToken(@RequestParam String bizKey) {
        String token = tokenService.createToken(bizKey);
        return Result.success(token);
    }

    /**
     * 提交订单 - 带 Token 幂等校验
     */
    @PostMapping("/submit")
    public Result submitOrder(@RequestBody OrderSubmitDTO dto) {
        // 1. 幂等校验
        boolean idempotent = tokenService.checkAndDeleteToken(
            dto.getBizKey(), dto.getToken());
        if (!idempotent) {
            return Result.error("重复提交，请勿频繁操作");
        }

        // 2. 执行业务逻辑
        return orderService.createOrder(dto);
    }
}
```

#### 方案三：状态机（Status Machine）

**原理**：业务单据状态按预定义方向流转，禁止逆向或跳过中间状态。利用数据库行锁或乐观锁保证状态更新的原子性。

**适用场景**：订单状态流转、审批流、物流状态更新。

```text
状态流转方向（不可逆）：
                         ┌─────────┐
                         │   NEW   │
                         └────┬────┘
                              │
                              ▼
                         ┌─────────┐
                    ┌───►│  PAID   │◄───┐
                    │    └────┬────┘    │
                    │         │         │
                    │         ▼         │
                    │    ┌─────────┐    │
                    │    │SHIPPED  │    │
                    │    └────┬────┘    │
                    │         │         │
                    │         ▼         │
                    │    ┌─────────┐    │
                    │    │ DELIVERED│   │
                    │    └────┬────┘    │
                    │         │         │
                    │         ▼         │
                    │    ┌─────────┐    │
                    └────┤  DONE   │    │
                         └─────────┘    │
                              │         │
                              ▼         │
                         ┌─────────┐    │
                         │CANCELLED│────┘
                         └─────────┘
```

```java
/**
 * 订单状态枚举
 */
public enum OrderStatus {
    NEW(0),
    PAID(1),
    SHIPPED(2),
    DELIVERED(3),
    DONE(4),
    CANCELLED(5);

    private final int code;

    OrderStatus(int code) { this.code = code; }

    public int getCode() { return code; }

    /**
     * 检查状态流转是否合法
     * NEW → PAID/SHIPPED/DONE: ❌ 非法（必须按顺序）
     * NEW → PAID: ✅ 合法
     * PAID → SHIPPED: ✅ 合法
     * PAID → NEW: ❌ 非法（禁止逆向）
     * SHIPPED → DELIVERED: ✅ 合法
     * 任意状态 → CANCELLED: ✅ 合法（但 PAID 前取消需退款）
     */
    public boolean canTransitionTo(OrderStatus target) {
        // 状态码递增表示正向流转
        if (target == CANCELLED) {
            return this != DONE;  // 已完成的订单不能取消
        }
        return target.getCode() == this.getCode() + 1;  // 只能前进到下一个状态
    }
}

/**
 * 订单状态机更新 - 保证幂等
 */
@Service
@Slf4j
public class OrderStatusMachineService {

    @Autowired
    private OrderMapper orderMapper;

    /**
     * 更新订单状态（幂等）
     */
    @Transactional
    public boolean updateOrderStatus(String orderNo, OrderStatus targetStatus) {
        // 1. 锁定查询（行锁）
        Order order = orderMapper.selectByOrderNoForUpdate(orderNo);
        if (order == null) {
            throw new BusinessException("订单不存在");
        }

        OrderStatus currentStatus = OrderStatus.valueOf(order.getStatus());
        log.info("订单状态流转：orderNo={}, {}→{}", orderNo, currentStatus, targetStatus);

        // 2. 检查状态流转合法性
        if (!currentStatus.canTransitionTo(targetStatus)) {
            log.warn("非法状态流转：orderNo={}, {}→{}",
                orderNo, currentStatus, targetStatus);
            return false;
        }

        // 3. 如果目标状态和当前状态相同，直接返回成功（幂等）
        if (currentStatus == targetStatus) {
            log.info("订单已经是目标状态，跳过：orderNo={}, status={}", orderNo, targetStatus);
            return true;
        }

        // 4. 更新状态
        int updated = orderMapper.updateStatusByOrderNo(orderNo, targetStatus.name());
        return updated > 0;
    }
}
```

#### 方案四：乐观锁（Optimistic Lock）

**原理**：使用版本号 `version` 字段，更新时检查版本号是否匹配。CAS（Compare And Swap）思想。

**适用场景**：库存扣减、账户余额变更、配置更新等高并发更新场景。

```java
/**
 * 库存表 - 乐观锁版本号
 */
@Entity
@Table(name = "t_inventory")
public class Inventory {
    @Id
    private Long skuId;

    @Column(name = "stock")
    private Integer stock;       // 库存数量

    @Column(name = "version")
    private Integer version;     // 乐观锁版本号
}

/**
 * MyBatis Mapper
 */
public interface InventoryMapper {

    @Select("SELECT * FROM t_inventory WHERE sku_id = #{skuId}")
    Inventory selectById(Long skuId);

    /**
     * 乐观锁更新：version 条件 + 自增
     */
    @Update("UPDATE t_inventory SET stock = stock - #{delta}, " +
            "version = version + 1 " +
            "WHERE sku_id = #{skuId} AND version = #{version} " +
            "AND stock >= #{delta}")
    int deductStock(@Param("skuId") Long skuId,
                    @Param("delta") Integer delta,
                    @Param("version") Integer version);
}

/**
 * 库存扣减服务 - 乐观锁幂等
 */
@Service
@Slf4j
public class InventoryService {

    @Autowired
    private InventoryMapper inventoryMapper;

    /**
     * 扣减库存 - 乐观锁 + 重试
     */
    public boolean deductStock(Long skuId, Integer delta, int maxRetries) {
        for (int i = 0; i < maxRetries; i++) {
            // 1. 读取当前版本
            Inventory inventory = inventoryMapper.selectById(skuId);
            if (inventory == null) {
                throw new BusinessException("SKU不存在");
            }

            // 2. 检查库存是否充足
            if (inventory.getStock() < delta) {
                log.warn("库存不足：skuId={}, stock={}, need={}", skuId, inventory.getStock(), delta);
                return false;
            }

            // 3. 乐观锁更新
            int rows = inventoryMapper.deductStock(skuId, delta, inventory.getVersion());
            if (rows > 0) {
                log.info("库存扣减成功：skuId={}, delta={}, remain={}",
                    skuId, delta, inventory.getStock() - delta);
                return true;
            }

            // 4. 版本冲突，重试
            log.warn("乐观锁冲突，重试第{}次：skuId={}", i + 1, skuId);
        }

        throw new BusinessException("系统繁忙，请稍后重试");
    }
}
```

#### 方案五：去重表（Deduplicate Table）

**原理**：为需要幂等的操作建立独立的去重表，利用唯一约束或主键来确保每个业务 Key 只执行一次。

**适用场景**：MQ 消息消费幂等、支付回调幂等、第三方回调幂等。

```java
/**
 * 去重表 - 用于消息消费幂等
 */
@Table(name = "t_idempotent_record",
       uniqueConstraints = @UniqueConstraint(
           name = "uk_idempotent_key", columnNames = "idempotent_key"))
public class IdempotentRecord {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "idempotent_key", nullable = false, length = 128)
    private String idempotentKey;    // 幂等 Key

    @Column(name = "biz_type", nullable = false, length = 32)
    private String bizType;          // 业务类型：order_pay / inventory_deduct / coupon_send

    @Column(name = "status", nullable = false, length = 16)
    private String status;           // PROCESSING / SUCCESS / FAILED

    @Column(name = "result_json", columnDefinition = "TEXT")
    private String resultJson;       // 执行结果（JSON化）

    @Column(name = "create_time")
    private LocalDateTime createTime;

    @Column(name = "update_time")
    private LocalDateTime updateTime;
}

/**
 * MQ 消息消费 - 去重表幂等
 */
@Component
@Slf4j
public class OrderMessageConsumer {

    @Autowired
    private IdempotentService idempotentService;

    @Autowired
    private OrderPayService orderPayService;

    /**
     * 消费支付成功消息 - 保证幂等
     */
    @RabbitListener(queues = "order.pay.success.queue")
    public void handlePaySuccess(PaySuccessMessage message) {
        // 构造幂等 Key（业务唯一标识）
        String idempotentKey = "pay_success:" + message.getOrderNo() + ":" + message.getPayId();

        // 执行并记录幂等
        idempotentService.execute(idempotentKey, "order_pay", () -> {
            log.info("处理支付成功消息：orderNo={}, payId={}",
                message.getOrderNo(), message.getPayId());
            orderPayService.processPaySuccess(message.getOrderNo(), message.getPayId());
            return null;
        });
    }
}

/**
 * 幂等服务 - 去重表实现
 */
@Service
@Slf4j
public class IdempotentService {

    @Autowired
    private IdempotentRecordMapper idempotentRecordMapper;

    /**
     * 幂等执行
     * 记录状态机：PROCESSING → SUCCESS / FAILED
     */
    @Transactional
    public <T> T execute(String idempotentKey, String bizType, Supplier<T> supplier) {
        // 1. 尝试插入去重记录（初始状态 PROCESSING）
        IdempotentRecord record = new IdempotentRecord();
        record.setIdempotentKey(idempotentKey);
        record.setBizType(bizType);
        record.setStatus("PROCESSING");
        record.setCreateTime(LocalDateTime.now());

        try {
            idempotentRecordMapper.insert(record);
        } catch (DuplicateKeyException e) {
            // 2. Key 已存在，查询执行结果
            IdempotentRecord existing = idempotentRecordMapper.selectByKey(idempotentKey);
            if ("SUCCESS".equals(existing.getStatus())) {
                log.info("幂等命中，返回已有结果：key={}", idempotentKey);
                return JSON.parseObject(existing.getResultJson(), /* 目标类型 */ null);
            }
            if ("FAILED".equals(existing.getStatus())) {
                throw new BusinessException("业务执行失败，幂等 Key=" + idempotentKey);
            }
            // PROCESSING 状态说明正在处理中
            throw new BusinessException("请求正在处理中，请勿重复提交");
        }

        // 3. 执行业务
        try {
            T result = supplier.get();
            // 4. 更新状态为 SUCCESS
            idempotentRecordMapper.updateStatusByKey(idempotentKey, "SUCCESS",
                JSON.toJSONString(result));
            return result;
        } catch (Exception e) {
            // 5. 更新状态为 FAILED
            idempotentRecordMapper.updateStatusByKey(idempotentKey, "FAILED", e.getMessage());
            throw e;
        }
    }
}
```

#### 方案六：分布式锁（Redisson）

**原理**：基于 Redisson 分布式锁，在执行业务前加锁，业务完成后释放锁。同一 Key 同时只有一把锁能获取成功。

**适用场景**：既有幂等需求又需要互斥执行的场景（如账户扣款、红包领取、秒杀扣减）。

```java
import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

import java.util.concurrent.TimeUnit;

/**
 * 红包领取服务 - Redisson 分布式锁实现幂等
 */
@Service
@Slf4j
public class RedPacketService {

    @Autowired
    private RedissonClient redissonClient;

    @Autowired
    private RedPacketMapper redPacketMapper;

    /**
     * 领取红包 - 分布式锁保证幂等
     */
    public Result claimRedPacket(Long userId, String packetId) {
        // 构造锁 Key
        String lockKey = "redpacket:claim:" + packetId + ":" + userId;

        RLock lock = redissonClient.getLock(lockKey);

        try {
            // 尝试加锁，等待 5 秒，锁持有时间 10 秒
            boolean locked = lock.tryLock(5, 10, TimeUnit.SECONDS);
            if (!locked) {
                return Result.error("系统繁忙，请稍后重试");
            }

            // 1. 检查是否已经领取过（内部幂等检查）
            if (redPacketMapper.hasClaimed(packetId, userId)) {
                log.info("用户已领取过红包：userId={}, packetId={}", userId, packetId);
                return Result.success("已领取");
            }

            // 2. 执行业务逻辑
            int rows = redPacketMapper.deductAndClaim(packetId, userId);
            if (rows > 0) {
                log.info("红包领取成功：userId={}, packetId={}", userId, packetId);
                return Result.success("领取成功");
            }

            return Result.error("红包已领完");
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return Result.error("系统异常");
        } finally {
            // 释放锁（确保幂等标识已写入数据库）
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 5.4 六种方案对比

| 方案 | 实现复杂度 | 性能 | 可靠性 | 适用场景 | 局限性 |
|------|-----------|------|--------|---------|--------|
| **唯一约束** | ⭐ | 高（数据库主键索引） | 高（数据库保证） | 创建订单、注册 | 仅适用于 INSERT 场景 |
| **Redis Token** | ⭐⭐⭐ | 高（Redis 内存操作） | 中（Redis 异常影响） | 前端防重复提交 | 需要额外一次 Token 获取请求 |
| **状态机** | ⭐⭐ | 高 | 高 | 订单状态流转 | 仅适用于有状态流转的场景 |
| **乐观锁** | ⭐⭐ | 高（CAS 无锁） | 中（并发冲突时需重试） | 库存扣减、余额更新 | 高冲突时重试开销大 |
| **去重表** | ⭐⭐⭐ | 中（数据库写入） | 高 | MQ 消费、支付回调 | 需额外建表，需定期清理 |
| **分布式锁** | ⭐⭐⭐ | 中（锁开销） | 高（Redisson 可靠） | 秒杀、红包、互斥场景 | 锁超时需要合理设置 |

### 5.5 幂等 Key 生成策略

| 场景 | 幂等 Key 生成规则 | 示例 |
|------|------------------|------|
| 订单创建 | `order:{userId}:{bizId}` | `order:10086:20260726120000` |
| 支付回调 | `pay_callback:{orderNo}:{payId}` | `pay_callback:ORD20260726001:PAY202607260001` |
| MQ 消息 | `mq:{topic}:{msgId}` | `mq:order_pay:MSG-20260726-001` |
| 库存扣减 | `deduct:{skuId}:{batchNo}` | `deduct:SKU001:BATCH20260726001` |
| 用户操作 | `action:{userId}:{actionType}:{targetId}` | `action:10086:like:ARTICLE001` |

> 💡 **幂等 Key 设计原则**：包含业务信息 + 唯一标识。避免使用时间戳作为唯一标识（存在极低概率重复）。建议使用 UUID、雪花算法 ID 或 Redis INCR 生成全局唯一 ID。

**自定义 WeightedLoadBalancer 实现缓慢启动**：

```java
import com.alibaba.cloud.nacos.NacosServiceInstance;
import org.springframework.cloud.client.ServiceInstance;
import org.springframework.cloud.loadbalancer.core.RoundRobinLoadBalancer;
import org.springframework.cloud.loadbalancer.support.LoadBalancerClientFactory;
import reactor.core.publisher.Mono;

import java.time.LocalDateTime;
import java.time.temporal.ChronoUnit;

/**
 * 自定义负载均衡器 - 实现服务 WarmUp
 * 新启动的实例在启动后 5 分钟内权重逐渐增加
 */
public class WarmUpLoadBalancer extends RoundRobinLoadBalancer {

    private static final long WARM_UP_DURATION_MS = 5 * 60 * 1000;  // 5 分钟预热

    public WarmUpLoadBalancer(LoadBalancerClientFactory factory) {
        super(60, factory);
    }

    @Override
    public Mono<Response<ServiceInstance>> choose(Request request) {
        return super.choose(request).map(response -> {
            ServiceInstance instance = response.getServer();
            if (instance instanceof NacosServiceInstance nacosInstance) {
                // 获取服务启动时间（在注册元数据中记录）
                String startTimeStr = nacosInstance.getMetadata().get("start-time");
                if (startTimeStr != null) {
                    LocalDateTime startTime = LocalDateTime.parse(startTimeStr);
                    long elapsed = ChronoUnit.MILLIS.between(startTime, LocalDateTime.now());
                    if (elapsed < WARM_UP_DURATION_MS) {
                        // 预热期权重降低：权重 = (运行时间 / 预热时间)
                        double warmUpFactor = (double) elapsed / WARM_UP_DURATION_MS;
                        // 以 warmUpFactor 概率处理请求，否则重新选择另一个实例
                        if (Math.random() > warmUpFactor) {
                            return new Response<>(null);  // 跳过此实例
                        }
                    }
                }
            }
            return response;
        });
    }
}
```

## 7. 数据高可用设计

### 7.1 MySQL 高可用

#### 7.1.1 主从复制架构

**三种复制模式对比**：

| 模式 | 原理 | 数据安全性 | 性能影响 | 适用场景 |
|------|------|-----------|---------|---------|
| **异步复制** | Master 写入 binlog 后立即返回，不等待 Slave 确认 | 低（主库宕机可能丢数据） | 高 | 对性能要求高、可接受少量数据丢失 |

| **组复制（Group Replication / MGR）** | Paxos 协议在多个节点间达成共识 | 极高 | 低 | 最⾼可用性要求的场景 |

### 7.2 分库分表（ShardingSphere）

#### 7.2.1 分片策略

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **Range（范围分片）** | 按 ID 范围划分，如 1~1000万 → 库1，1001万~2000万 → 库2 | 扩容简单（追加新分片），查询范围友好 | 数据倾斜（热点数据集中在最新分片） | 按时间分片的日志数据 |
| **Mod（取模分片）** | `user_id % N`，N 为分片数 | 数据分布均匀，实现简单 | 扩容需要重新分配数据（Rehash） | 用户数据、订单数据 |
| **Hash（哈希分片）** | `hash(biz_key) % N` | 数据分布均匀 | 同样存在 Rehash 问题 | 场景同上，但 Key 非数字 |
| **一致性哈希** | 哈希环 + 虚拟节点 | 扩容时数据迁移量最小 | 实现复杂度高 | 超大规模集群 |

## 8. 服务无状态设计

### 8.1 有状态 vs 无状态

| 维度 | 无状态（Stateless） | 有状态（Stateful） |
|------|-------------------|-------------------|
| 定义 | 服务实例不保存业务数据，所有请求可被任意实例处理 | 服务实例保存业务数据，同一用户的请求必须路由到同一实例 |
| 部署 | 可任意扩缩容，新节点直接加入即可 | 扩缩容需要迁移状态数据 |
| 故障恢复 | 实例宕机不影响，其他实例继续处理 | 实例宕机会丢失状态数据 |
| 负载均衡 | 任意分发，无需 Stickiness | 需要 Sticky Session |
| 可测试性 | 高（无状态依赖） | 低（需要准备状态） |
| 典型实现 | RESTful API（无 Session） | WebSocket 连接、Session 会话 |

> 💡 **无状态设计是高可用的前提**：只有无状态的服务才能实现真正的水平扩展和任意故障转移。

### 8.2 Session 迁移方案

#### 8.2.1 方案对比

| 方案 | 实现方式 | 优点 | 缺点 |
|------|---------|------|------|
| **JWT Token** | 用户信息加密存储在 Token 中，服务端不维护 Session | 完全无状态、跨语言、跨域友好 | Token 无法主动失效（需黑名单）、Payload 大小有限 |
| **Redis 集中 Session** | Session 数据存储在 Redis，所有服务实例共享 | 可主动管理 Session、兼容传统 Servlet Session | 依赖 Redis 高可用、增加网络开销 |
| **Cookie + Session ID** | 服务端存储 Session，客户端只存 Session ID | 成熟方案、技术简单 | 有状态、无法水平扩展 |

#### 8.2.2 JWT Token 无状态认证

```java
/**
 * JWT Token 工具类 - 无状态认证
 */
@Component
public class JwtTokenProvider {

    @Value("${jwt.secret}")
    private String secretKey;

    @Value("${jwt.expiration:86400000}")  // 默认 24 小时
    private long expirationMs;

    /**
     * 生成 Token（不包含敏感信息）
     */
    public String generateToken(Long userId, String username, String role) {
        Map<String, Object> claims = new HashMap<>();
        claims.put("userId", userId);
        claims.put("username", username);
        claims.put("role", role);

        return Jwts.builder()
            .setClaims(claims)
            .setSubject(String.valueOf(userId))
            .setIssuedAt(new Date())
            .setExpiration(new Date(System.currentTimeMillis() + expirationMs))
            .signWith(SignatureAlgorithm.HS256, secretKey.getBytes(StandardCharsets.UTF_8))
            .compact();
    }

    /**
     * 解析 Token（无状态，不需要查询数据库或 Redis）
     */
    public Claims parseToken(String token) {
        return Jwts.parser()
            .setSigningKey(secretKey.getBytes(StandardCharsets.UTF_8))
            .parseClaimsJws(token)
            .getBody();
    }

    /**
     * 校验 Token 有效性
     */
    public boolean validateToken(String token) {
        try {
            parseToken(token);
            return true;
        } catch (JwtException | IllegalArgumentException e) {
            return false;
        }
    }
}
```

### 8.3 本地缓存问题与双层缓存架构

**问题**：当使用 Caffeine 本地缓存时，不同服务实例的缓存数据不一致。

**解决方案**：两层缓存架构

```text
┌─────────────────────────────────────────────────────────┐
│                     应用程序                              │
│                                                         │
│  ┌──────────────────────────────────────────┐           │
│  │        L1：Caffeine 本地缓存              │           │
│  │  极速（纳秒级）、每个实例独立、容量有限    │           │
│  └────────────────┬─────────────────────────┘           │
│                   │ 未命中                              │
│  ┌────────────────▼─────────────────────────┐           │
│  │        L2：Redis 分布式缓存               │           │
│  │  较慢（毫秒级）、集群共享、容量大          │           │
│  └────────────────┬─────────────────────────┘           │
│                   │ 未命中                              │
│  ┌────────────────▼─────────────────────────┐           │
│  │        L3：数据库（DB）                    │           │
│  │  最慢、持久化                              │           │
│  └──────────────────────────────────────────┘           │
└─────────────────────────────────────────────────────────┘
```

```java
/**
 * 两级缓存实现
 */
@Component
public class TwoLevelCacheService {

    @Autowired
    private StringRedisTemplate redisTemplate;

    // L1 本地缓存：Caffeine
    private final Cache<String, String> localCache = Caffeine.newBuilder()
        .maximumSize(10000)                    // 最大 10000 条
        .expireAfterWrite(30, TimeUnit.SECONDS)  // 写入后 30 秒过期
        .recordStats()                         // 记录命中率统计
        .build();

    /**
     * 获取缓存值 - 先查本地，再查 Redis
     */
    public String get(String key) {
        // 1. 查本地缓存
        String value = localCache.getIfPresent(key);
        if (value != null) {
            return value;
        }

        // 2. 查 Redis 缓存
        value = redisTemplate.opsForValue().get(key);
        if (value != null) {
            // 回填本地缓存
            localCache.put(key, value);
            return value;
        }

        return null;  // 未命中
    }

    /**
     * 更新缓存 - 同时更新本地和 Redis
     * 广播通知其他实例清除本地缓存（Redis Pub/Sub）
     */
    public void put(String key, String value) {
        redisTemplate.opsForValue().set(key, value, 5, TimeUnit.MINUTES);
        localCache.put(key, value);

        // 广播清除其他实例本地缓存
        redisTemplate.convertAndSend("cache:invalidate", key);
    }
}
```

### 8.4 定时任务避免重复执行

**问题**：在集群环境中，同一定时任务会在所有节点上同时执行，导致重复处理。

**解决方案对比**：

| 方案 | 原理 | 复杂度 | 可靠性 |
|------|------|--------|--------|
| **@SchedulerLock** | 基于 Redis/数据库的分布式锁，任务执行时加锁 | ⭐⭐ | 中 |
| **XXL-JOB** | 调度中心统一调度，执行器接收任务执行 | ⭐⭐⭐ | 高 |
| **Quartz 集群** | 基于数据库行锁的任务调度 | ⭐⭐⭐ | 高 |

**@SchedulerLock 示例**：

```java

    public void calculateDailyOrderStats() {
        // 业务逻辑：统计昨日订单数据
        System.out.println("执行订单统计任务...");
    }
}
```

## 9. 高频踩坑与误区

### 9.1 六大常见陷阱

| 编号 | 误区 | 错误表现 | 正确做法 | 影响等级 |
|------|------|---------|---------|---------|
| 1 | **误以为 99.9% 就"够用"** | 年停机 8.76 小时，一次数据库迁移 + 应用发布就耗尽 | 根据业务重要性选择 SLA，核心链路至少 99.99% | 🔴 严重 |
| 2 | **幂等设计遗漏导致重复扣款** | 网络超时重试导致同一订单重复扣款 | 所有写接口必须按方案实现幂等，特别是支付和库存 | 🔴 严重 |
| 3 | **限流粒度太粗或太细** | 全系统共享一个限流阈值，一个接口被刷导致全站不可用；或每个方法都限流，配置爆炸 | Nginx/Gateway/Sentinel 三层分级限流，按业务重要性区分阈值 | 🟡 中等 |
| 4 | **灰度发布未充分验证就全量** | 金丝雀验证 5 分钟无问题即全量，结果慢 SQL 导致全站瘫痪 | 灰度周期至少观察 30 分钟以上，监控错误率、RT、CPU 等指标 | 🔴 严重 |
| 5 | **无状态设计被本地缓存破坏** | 使用本地 Ehcache 缓存用户 Session 信息，导致请求必须 stickiness | Session 放 Redis，本地缓存只放全量只读数据（配置、类目） | 🟡 中等 |
| 6 | **熔断超时设置不合理** | 熔断 TimeWindow 设为 5 秒，下游服务尚未恢复就 HALF_OPEN 再次熔断 | TimeWindow 至少 30 秒以上，配合指数退避重试 | 🟡 中等 |
| 7 | **重试导致雪崩** | 服务 A 调用 B 超时后立即重试 5 次，B 的负载瞬间增加 5 倍 | 使用指数退避 + 随机抖动（Exponential Backoff + Jitter），限制最大重试次数 | 🔴 严重 |
| 8 | **单点故障（SPOF）未识别** | Nginx 单节点部署，Nginx 挂掉后全站不可用 | Nginx 至少主备部署，前端加 LVS/Keepalived 或云负载均衡器 | 🔴 严重 |

### 9.2 误区一：99.9% 可用性"够用"

```text
误解场景：
    某创业公司核心交易系统采用单机房部署，SLA 承诺 99.9%。
    一年中发生：
      - 数据库主从切换：30 分钟
      - 应用发布重启：20 分钟 × 6 次 = 2 小时
      - 机房网络抖动：40 分钟
      - 意外宕机恢复：1.5 小时
    合计：~5 小时，看似还在 99.9% 内。

    但是！如果这 5 小时发生在"双十一"当天，直接导致：
      - 数百万订单丢失
      - 用户投诉淹没客服
      - 品牌信誉受损

正确做法：
    核心交易链路按 99.99% 设计（年停机 < 53 分钟），
    非核心链路可以容忍 99.9%。
```

### 9.3 误区二：幂等设计遗漏

```text
案例：重复扣款事故

时序：
1. 用户点击"提交订单"
2. 前端 POST /order/create
3. 网络超时（实际服务端已成功创建订单）
4. 前端自动重试，再次发送 POST /order/create
5. 服务端再次执行扣款逻辑
6. 结果：同一订单被扣款两次 ❌

根因分析：
    - 前端未做按钮防重复（disabled）
    - 后端未做幂等校验
    - 数据库无唯一约束兜底

解决方案：
    - 前端：提交后按钮置灰 + loading
    - 后端：Token 机制或唯一约束
    - 数据库：order_no 唯一索引兜底
```

### 9.4 误区三：限流配置不合理

```text
错误配置：
    # Nginx 只配了一个全局限流
    limit_req_zone $binary_remote_addr zone=all:10m rate=100r/s;

    问题：
      - /api/login 接口被暴力破解时，全站限流触发
      - 正常用户也无法访问
      - 恶意流量占满所有限流配额

正确做法（分级限流）：
    - /api/login：1r/s（防止暴力破解）
    - /api/order：50r/s（核心业务，较高配额）
    - /api/search：200r/s（读多写少，较高配额）
    - /api/report：5r/s（报表查询，低配额）
    - 未匹配接口：10r/s（兜底限制）
```

### 9.5 误区四：灰度发布验证不充分

```text
典型事故：
1. 开发完成 v2.0 订单服务
2. 金丝雀发布到 1 台机器，分配 5% 流量
3. 观察 5 分钟：错误率正常
4. 全量发布 100% 流量
5. 5 分钟后数据库连接池被打满，慢查询堆积
6. 回滚后 20 分钟恢复

根因：
    - 金丝雀验证时间太短（5 分钟）
    - 5% 流量下数据库连接池未达到瓶颈
    - 监控指标不全（只看了错误率，没看连接池使用率）

正确做法：
    ✅ 灰度 5% → 观察 ≥ 30 分钟 → 灰度 30% → 观察 ≥ 30 分钟 → 全量
    ✅ 关注指标：错误率、RT（P50/P95/P99）、CPU、内存、连接池、GC
    ✅ 设置自动回滚阈值（错误率 > 1% 自动回滚）
```

### 9.6 误区五：重试导致雪崩

```text
错误的重试策略：
    @Retryable(value = Exception.class, maxAttempts = 5)
    public Order createOrder(OrderDTO dto) { ... }

    当下游数据库响应变慢时：
      - 第一次请求：超时等待 2 秒
      - 重试第一次：又等待 2 秒 ← 队列积压
      - 重试第二次：再等待 2 秒
      - 重试第三次：...
      - 最终：线程池被阻塞，请求积压，服务雪崩

正确做法：
    @Retryable(
        value = {TimeoutException.class, IOException.class},
        maxAttempts = 3,
        backoff = @Backoff(delay = 200, multiplier = 2, maxDelay = 5000)
    )
    public Order createOrder(OrderDTO dto) { ... }

    使用指数退避：200ms → 400ms → 800ms（乘数 2）

    进一步优化：添加随机抖动（Jitter）
      delay = delay * (1 + random(0, 0.5))
      避免多个请求同时重试导致"惊群效应"
```

### 习题 4：本地缓存问题

某团队在微服务中使用 Caffeine 本地缓存用户信息，缓存时间设为 1 小时。当用户通过"账号管理"修改个人信息后，出现部分服务读取到旧数据的问题。

**问题**：
1. 为什么会出现数据不一致？
2. 如何解决（至少 2 种方案）？
3. 哪些数据适合放在本地缓存？

<details>
<summary>参考答案</summary>

```text
1. 原因：Caffeine 是本地缓存，每个 JVM 实例维护独立的缓存。
   用户修改信息只更新了被路由到的实例的缓存，其他实例的缓存还是旧数据。

2. 解决方案：
   方案 A：两级缓存（本地+Redis）
     - 写入：更新 DB → 更新 Redis → 广播缓存失效消息
     - 读取：查本地 → 查 Redis → 查 DB
     - 优点：兼顾性能和一致性
     - 缺点：架构复杂

   方案 B：Redis 集中缓存（去掉本地缓存）
     - 所有实例共享 Redis 缓存
     - 优点：完全一致、实现简单
     - 缺点：多一次网络开销

   方案 C：短过期时间
     - 本地缓存过期时间设为 10 秒
     - 用户可以接受最多 10 秒的不一致
     - 优点：实现简单
     - 缺点：缓存命中率降低

3. 适合本地缓存的数据：
   - 配置信息（Nacos 配置、系统参数）
   - 类目树（商品类目、地域层级）
   - 字典数据（状态码、枚举值映射）
   - 白名单数据（IP 白名单、接口权限）

   这些数据的共性：全量只读、变化极低、一致性要求不严格。
```
</details>

某服务调用外部支付网关的超时时间为 3 秒，支付网关偶尔会出现 502 或超时。

**问题**：
1. 设计合理的重试策略（含重试次数、间隔、退避策略）。
2. 重试时需要保证什么？
3. 如果支付网关连续失败，如何保护自身不被拖垮？

<details>
<summary>参考答案</summary>

```text

   @Retryable(
       value = {TimeoutException.class, HttpServerErrorException.class},
       maxAttempts = 3,
       backoff = @Backoff(delay = 1000, multiplier = 2, maxDelay = 10000)
   )

   重试间隔：1 秒 → 2 秒 → 4 秒（指数退避）

   - 支付接口必须有幂等 Key（如 orderNo + paySeq）
   - 支付网关根据幂等 Key 去重
   - 防止同一笔订单被扣款多次

3. 自身保护：
   - 熔断器：连续失败率达到 50% 时熔断 30 秒
   - 线程池隔离：支付调用线程池独立，max=10，queue=20
   - 舱壁模式：不占用 Tomcat 线程
```

```java
 * 秒杀库存扣减 - Redis Lua 原子操作

@Component

    @Autowired
    private StringRedisTemplate redisTemplate;

    // Lua 脚本：原子扣减库存，返回扣减结果
    // KEYS[1]: 库存 Key（seckill:stock:{activityId}）
    // KEYS[2]: 去重 Key（seckill:user:{activityId}:{userId}）
    // ARGV[1]: 用户 ID
    // ARGV[2]: 扣减数量
    private static final String DEDUCT_STOCK_LUA =
        "if redis.call('EXISTS', KEYS[2]) == 1 then " +           // 用户已抢购
        "    return {err='DUPLICATE'}; " +
        "end; " +
        "local stock = redis.call('GET', KEYS[1]); " +           // 获取库存
        "if not stock or tonumber(stock) < tonumber(ARGV[2]) then " +  // 库存不足
        "    return {err='SOLD_OUT'}; " +
        "end; " +
        "redis.call('DECRBY', KEYS[1], ARGV[2]); " +             // 扣减库存
        "redis.call('SET', KEYS[2], 1, 'EX', 86400); " +         // 记录用户已抢购
        "return {ok='SUCCESS'}; ";
```

## 14. 精通拓展补充-P2

### 14.1 混沌工程（Chaos Engineering）

混沌工程通过主动注入故障来验证系统的容错性和韧性。

#### 14.1.1 核心原则

```text
混沌工程实验流程：

1. 定义稳态（Steady State）
   → 定义系统的正常行为指标（如：P99 RT < 500ms，错误率 < 0.1%）

2. 提出假设（Hypothesis）
   → "当订单服务的一个实例宕机时，系统仍能正常处理请求"

3. 注入故障（Inject Fault）
   → 通过 ChaosBlade 关闭一个订单服务实例

4. 观察验证（Verify）
   → 检查系统指标是否仍在稳态范围内

5. 改进系统（Improve）
   → 如果假设不成立，改进系统架构
```

#### 14.1.2 ChaosBlade 实验示例

**关闭 Pod 实验**：

```bash
# 安装 ChaosBlade

tar -xzf chaosblade-1.7.3-linux-amd64.tar.gz

# 创建实验：杀死 order-service 的一个 Pod

  --namespace default \
  --labels app=order-service \
  --count 1 \
  --kubeconfig ~/.kube/config
```

**注入网络延迟实验**：

```bash

  --namespace default \
  --labels app=inventory-service \
  --delay-ms 500 \
  --offset-ms 100 \
  --kubeconfig ~/.kube/config
```

**CPU 负载实验**：

```bash

  --namespace default \
```

**综合实验脚本**：

```bash
#!/bin/bash
# 混沌工程综合实验：核心链路稳定性验证

# 设定稳态指标
STEADY_ERROR_RATE=0.01      # 错误率 < 1%
STEADY_P99_RT=1000          # P99 RT < 1000ms

echo "=== 混沌实验开始 ==="

echo "1. 注入故障：关闭 order-service 一个实例"
blade create k8s pod-kill \
  --namespace default \
  --labels app=order-service \
  --count 1

echo "2. 观察 30 秒"
sleep 30

echo "3. 注入故障：inventory-service 网络延迟 500ms"
blade create k8s pod-network-delay \
  --namespace default \
  --labels app=inventory-service \
  --delay-ms 500

echo "4. 观察 60 秒"
sleep 60

echo "5. 检查稳态指标"
# 假设通过 Prometheus API 获取指标
ERROR_RATE=$(curl -s "http://prometheus:9090/api/v1/query?query=error_rate" | jq -r '.data.result[0].value[1]')
P99_RT=$(curl -s "http://prometheus:9090/api/v1/query?query=p99_rt" | jq -r '.data.result[0].value[1]')

if (( $(echo "$ERROR_RATE < $STEADY_ERROR_RATE" | bc -l) )) && \
   (( $(echo "$P99_RT < $STEADY_P99_RT" | bc -l) )); then
    echo "✅ 实验通过：系统韧性正常"
else
    echo "❌ 实验失败：系统韧性不足"
    echo "   错误率: $ERROR_RATE (阈值: $STEADY_ERROR_RATE)"
    echo "   P99 RT: $P99_RT (阈值: $STEADY_P99_RT)"
fi

echo "6. 清理实验"
blade destroy --all
echo "=== 混沌实验结束 ==="
```

#### 14.1.3 混沌工程成熟度模型

| 等级 | 名称 | 特征 | 实施方式 |
|------|------|------|---------|
| L0 | 无 | 没有任何故障注入手段 | - |
| L1 | 手动 | 人工编写 ChaosBlade 命令，手动执行 | 开发自测 |
| L2 | 自动化 | 通过 CI/CD 流水线定时执行混沌实验 | Jenkins/GitLab CI |
| L3 | 平台化 | 自建混沌工程平台（如阿里 AHAS、字节混沌平台） | 平台化调度 |
| L4 | 智能 | 自动识别薄弱环节，智能编排实验，自动回滚 | AI 驱动 |

### 14.3 单元化架构（Unit Architecture）

#### 14.3.1 什么是单元化

单元化架构是将业务按用户维度分成若干"单元"，每个单元包含完整的业务栈（应用 + 数据），独立处理本单元的用户请求。

```text
┌────────────────────────────────────────────────────────────────────┐
│                       统一入口 / 网关层                              │
│                GSLB 就近路由 + 单元路由层（user_id % N）             │
└───────┬──────────────┬──────────────┬──────────────┬──────────────┘
        │              │              │              │
┌───────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐
│  单元 0      │ │  单元 1    │ │  单元 2    │ │  单元 3    │
│  华北        │ │  华东      │ │  华南      │ │  海外      │
│              │ │            │ │            │ │            │
│  应用层       │ │  应用层    │ │  应用层    │ │  应用层    │
│  ┌────────┐  │ │ ┌────────┐ │ │ ┌────────┐ │ │ ┌────────┐ │
│  │APP     │  │ │ │APP     │ │ │ │APP     │ │ │ │APP     │ │
│  └────────┘  │ │ └────────┘ │ │ └────────┘ │ │ └────────┘ │
│              │ │            │ │            │ │            │
│  数据层       │ │  数据层    │ │  数据层    │ │  数据层    │
│  ┌────────┐  │ │ ┌────────┐ │ │ ┌────────┐ │ │ ┌────────┐ │
│  │MySQL   │  │ │ │MySQL   │ │ │ │MySQL   │ │ │ │MySQL   │ │
│  │Redis   │  │ │ │Redis   │ │ │ │Redis   │ │ │ │Redis   │ │
│  │MQ      │  │ │ │MQ      │ │ │ │MQ      │ │ │ │MQ      │ │
│  └────────┘  │ │ └────────┘ │ │ └────────┘ │ │ └────────┘ │
│              │ │            │ │            │ │            │
│  数据范围：  │ │  数据范围：│ │  数据范围：│ │  数据范围：│
│  user_id%4  │ │  user_id%4 │ │  user_id%4 │ │  user_id%4 │
│  = 0        │ │  = 1       │ │  = 2       │ │  = 3       │
└──────────────┘ └────────────┘ └────────────┘ └────────────┘
```

#### 14.3.2 单元化架构的关键技术

| 技术维度 | 方案 | 说明 |
|---------|------|------|
| 单元路由 | GSLB + 网关路由层 | 根据 user_id 或地理位置路由到目标单元 |
| 数据分片 | 用户维度水平分片 | 每个单元拥有独立的数据库、缓存、消息队列 |
| 全局数据 | 配置中心 + 全局缓存 | 类目、配置等全量数据通过 MQ 同步到所有单元 |
| 跨单元事务 | MQ 异步 + 最终一致 | 尽量避免跨单元调用，必要时用 TCC/Saga |
| 单元间通信 | RocketMQ/ Kafka 跨机房复制 | 异步消息保证最终一致性 |
| 容灾切换 | 单元级故障转移 | 故障单元的用户流量切换到其他单元 |

#### 14.3.3 从两地三中心到单元化的演进路径

```text
阶段 1：两地三中心

│ 北京生产  │    │ 上海生产  │    │ 广州灾备  │
│ 1/2 流量  │    │ 1/2 流量  │    │ 0 流量   │

  数据全量复制     数据全量复制     异步复制

     └──────────────────┴──────────────┘
               共享数据库集群
  → 问题：数据库成为瓶颈，无法水平扩展

阶段 2：数据分片 + 多活
┌──────────┐    ┌──────────┐    ┌──────────┐
│ 单元 0    │    │ 单元 1    │    │ 单元 2    │
│ user%3=0 │    │ user%3=1 │    │ user%3=2 │

  → 优点：数据层解耦，可水平扩展
  → 挑战：跨单元查询、全量数据同步

阶段 3：单元化 + 全球部署
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐

  → 优点：用户就近接入，低延迟
  → 挑战：跨区域数据同步，法规合规（GDPR）
```

### 14.4 大厂高可用架构案例

#### 14.4.1 阿里双11高可用架构

```text
阿里双11高可用关键手段：

1. 全链路压测
   - 提前 3 个月开始全链路压测
   - 按 1:1 比例模拟真实流量
   - 发现瓶颈，逐个击破

2. 容量规划（Capacity Planning）
   - 根据历年数据预测峰值 QPS
   - 按峰值 1.5 倍预留资源
   - 云资源弹性伸缩

3. 单元化架构（Set化）
   - 按用户 ID 分为若干单元
   - 每个单元独立处理请求
   - 单元级故障不影响其他单元

4. 限流降级
   - 多级限流：接入层 → 应用层 → 数据层
   - 非核心业务降级（如买家秀、推荐）
   - 读写分离，读可降级为缓存

5. 全链路跟踪
   - EagleEye 全链路追踪
   - 实时监控每一个调用
   - 自动告警 + 预案执行

6. 混沌工程
   - 故障注入验证系统韧性
   - 红蓝对抗（红队攻击、蓝队防守）
   - 故障自愈（自动检测 + 自动恢复）
```

#### 14.4.2 美团高可用实践

```text
美团高可用架构特点：

1. 同城双活 + 异地灾备
   - 北京、上海同城双活
   - 异地灾备中心

2. 服务治理
   - 基于 Sentinel 的限流降级
   - 基于 CAT 的实时监控
   - 基于 ConfigCenter 的动态配置

3. 热点探测
   - 实时检测热点 Key（如爆款商品、热门店铺）
   - 热点 Key 本地缓存 + Sentinel 热点限流
   - 避免热点打垮缓存集群

4. 数据库高可用
   - MySQL 主从 + MHA 自动切换
   - 分库分表（ShardingSphere）
   - 读写分离 + 连接池隔离

5. 发布策略
   - 灰度发布 + 自动回滚
   - 全链路灰度（流量打标）
   - 平滑上下线
```

#### 14.4.3 字节跳动高可用实践

```text
字节跳动高可用架构特点：

1. 微服务 + Service Mesh
   - 大规模使用 Istio + Envoy
   - 统一的流量管理和熔断降级
   - 非侵入式接入（无需修改代码）

2. 自适应限流
   - 基于 CPU/Load/RT 的动态限流
   - 系统自动调整限流阈值
   - 支持按调用方/按接口差异化限流

3. 多集群部署
   - 全球多机房部署
   - 就近接入 + 异地容灾
   - 跨机房流量调度

4. 持续混沌
   - 常态化混沌实验
   - 自动注入故障 + 自动验证
   - 混沌实验作为发布前置条件
```

### 14.5 高可用架构设计 Checklist

```text
□ 可用性目标：是否明确了 SLA 目标？
□ 单点故障：是否存在 SPOF？是否有多副本冗余？
□ 部署架构：单机房/同城双活/两地三中心/异地多活？
□ 分层限流：Nginx + Gateway + Sentinel 三层限流是否齐全？
□ 熔断降级：非核心业务是否有降级兜底？
□ 幂等设计：所有写接口是否都有幂等保障？
□ 灰度发布：新版本是否经过灰度验证？
□ 无损上线：Readiness Probe + WarmUp 是否配置？
□ 优雅关闭：PreStop Hook + Graceful Shutdown 是否配置？
□ 数据高可用：MySQL 主从 + Redis 哨兵/Cluster 是否就绪？
□ 备份策略：全量 + 增量备份是否配置？RPO/RTO 是否达标？
□ 无状态设计：Session 是否迁移到 Redis/JWT？
□ 本地缓存：是否考虑了一致性问题？
□ 定时任务：是否有分布式锁防重复执行？
□ 重试策略：是否使用了指数退避 + 随机抖动？
□ 监控告警：核心指标是否都有监控和告警？
□ 混沌工程：是否定期进行故障注入演练？
□ 容量规划：是否按峰值 1.5 倍预留资源？
□ 预案文档：故障时是否有应急预案并定期演练？
□ 复盘改进：每次故障后是否进行了复盘和改进？
```

> 🎯 **高可用架构设计的核心理念**：没有一个系统天生高可用。高可用是通过**冗余设计**消除单点、通过**限流降级熔断**保护系统、通过**幂等重试**保证数据正确、通过**灰度发布**降低变更风险、通过**混沌工程**验证韧性——最终达到"系统在任何故障场景下都能对外提供稳定服务"的目标。

---

> 🎯 **本章总结**：高可用架构设计是分布式系统中的核心非功能性能力，涵盖多集群部署、限流降级熔断、幂等设计、灰度发布、数据高可用与无状态设计等关键维度，是架构师从 P1 迈向 P2 的必修课。通过本章的学习，读者应能够独立设计中小型互联网系统的高可用架构方案，并具备阅读和分析大厂高可用实践的能力。
