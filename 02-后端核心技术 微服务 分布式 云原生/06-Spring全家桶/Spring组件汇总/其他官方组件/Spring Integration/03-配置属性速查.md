## 1. spring.integration.* 属性表

| 属性 | 默认值 | 说明 |
|------|--------|------|
| `spring.integration.error.require-subscribers` | `true` | 错误通道无订阅者时是否报错（false=静默丢弃） |
| `spring.integration.error.ignore-failures` | `false` | 错误处理本身失败是否吞掉 |
| `spring.integration.poller.fixed-delay` | — | 全局默认轮询间隔（秒） |
| `spring.integration.poller.max-messages-per-poll` | 1 | 每次轮询最大取消息数 |
| `spring.integration.channel.max-broadcast-subscribers` | 2147483647 | PublishSubscribe 通道最大订阅者数 |
| `spring.integration.channel.max-unicast-subscribers` | 2147483647 | Direct/Executor 等单播通道最大订阅者数 |
| `spring.integration.jdbc.initialize-schema` | `embedded` | JdbcMessageStore 建表策略（always/embedded/never） |
| `spring.integration.jdbc.schema` | `classpath:.../schema.sql` | JDBC 存储建表脚本位置 |
| `spring.integration.management.default-logging-enabled` | `true` | 端点默认日志开关 |
| `spring.integration.management.observation-patterns` | — | 启用 Micrometer 观测的端点模式（7.x） |

```yaml
spring:
  integration:
    error:
      require-subscribers: true     # 错误无处可去时快速暴露（开发）
    poller:
      fixed-delay: 5
      max-messages-per-poll: 10
    jdbc:
      initialize-schema: never      # 生产：JdbcMessageStore 表已由 DBA 建好
```

> 🎯 **高频三配**：`error.require-subscribers`（错误可见性）、`poller.*`（全局轮询节奏）、`jdbc.initialize-schema`（存储建表）。

## 2. 错误处理配置

| 场景 | 配置/做法 |
|------|----------|
| 错误快速暴露（开发） | `spring.integration.error.require-subscribers: true`（默认）——没订阅者直接抛错 |
| 生产静默降级 | `require-subscribers: false` + 显式 errorChannel 订阅（记录+告警） |
| 错误重试 | 在 errorChannel 端点接 RetryTemplate / 死信队列 |
| 幂等消费 | 端点 + idempotent receiver（MessageGroupStore 判重） |

> ⚠️ 经验：**生产别把错误静默吞掉**——宁可 require-subscribers=true 让错误快速炸出来，配合监控告警；静默丢消息是最难排查的事故。

## 3. 轮询配置

| 方式 | 配置 | 说明 |
|------|------|------|
| 全局默认 | `spring.integration.poller.fixed-delay` / `max-messages-per-poll` | 所有未显式指定 poller 的轮询端点 |
| 局部覆盖 | `@Poller(fixedDelay = "5s", maxMessagesPerPoll = 100)` | 注解端点（适配器/网关） |
| DSL 局部 | `.poller(p -> p.fixedDelay(5_000).maxMessagesPerPoll(100))` | IntegrationFlow 内 |
| 定时任务源 | cron 表达式 | `@Scheduled` 风格触发源 |

> 💡 轮询语义：`fixedDelay`（上次执行完再等 N）/ `fixedRate`（按开始时间间隔，可能并发重叠）——处理慢的端点用 fixedDelay 防堆积。

## 4. 通道容量配置

| 需求 | 做法 |
|------|------|
| QueueChannel 容量 | `new QueueChannel(1000)`（满则阻塞发送线程，天然背压） |
| 广播上限保护 | `spring.integration.channel.max-broadcast-subscribers` |
| 单播上限保护 | `spring.integration.channel.max-unicast-subscribers`（>1 时报错，防误连多订阅者） |
| ExecutorChannel 线程池 | Bean 注入 `TaskExecutor`（可配虚拟线程） |

> 🎯 背压设计：**QueueChannel 有界容量 + 阻塞发送 = 消费慢则生产停**——这正是 6.0 Spring Batch 生产者-消费者模型同款思路。

## 5. 存储与初始化配置

| 存储 | 初始化方式 | 生产要点 |
|------|-----------|---------|
| JdbcMessageStore | `spring.integration.jdbc.initialize-schema=always/embedded/never` | 生产 `never` + DBA 执行官方 schema |
| RedisMessageStore | 无表（Redis 键） | 注意 TTL 与序列化器 |
| MongoMessageStore | 集合自动建 | 索引按查询建 |

> ⚠️ 表前缀/多租户：JdbcMessageStore 建表脚本支持前缀配置（构造器 `new JdbcMessageStore(ds, prefix)`）——多租户隔离时按前缀分表。

> 🎯 配置心智模型：**yaml 管"全局默认与错误可见性"，通道容量/存储/轮询细节走 Bean/DSL 配置**——先定错误策略（第 2 节），再定轮询节奏，最后定存储形态。
