## 1. 与其他模块的集成地图

```text
                  spring-tx（事务契约层）
        ┌──────────┬──────────┬──────────┬──────────┐
        ↓          ↓          ↓          ↓          ↓
  spring-jdbc   spring-orm   spring-aop  spring-context  Spring Boot
  DataSource    Jpa/         @Transactional AOP 事件           事务自动配置
  Transaction   Hibernate    通过 AOP 织入  @Transactional   单数据源全自动
  Manager       事务管理器     TransactionInterceptor EventListener  Seata 集成
```

| 联动点 | 机制 | 说明 |
|--------|------|------|
| tx ↔ aop | TransactionInterceptor 是环绕通知 | 声明式事务 = AOP 代理 + 拦截器（见 [Spring-AOP 系列](../Spring‑AOP/00-Spring AOP组件总览.md)） |
| tx ↔ jdbc | DataSourceTransactionManager + DataSourceUtils | 连接绑定线程（[Spring-JDBC-07](../Spring‑JDBC/07-与事务ORM集成速查.md)） |
| tx ↔ orm | JpaTransactionManager + 持久化上下文 | JPA 事务与 JDBC 事务共享同步机制 |
| tx ↔ context | `@TransactionalEventListener`（AFTER_COMMIT） | 事务提交后才发事件/消息（[Spring-Context-05](../Spring‑Context/05-事件驱动机制速查.md)） |
| tx ↔ 异步 | @Async 线程丢失事务绑定 | 跨线程事务需显式传播（见第 2 节） |
| tx ↔ 分布式 | Seata / JTA / 本地消息表 | 跨库强一致 vs 最终一致（[Spring全家桶-14](../../../Spring全家桶/14-分布式事务-Seata.md)） |

> 🎯 **核心要点**：事务是"横切能力"——它不独立存在，必须寄生在 AOP（声明式）或模板（编程式）之上，落地在资源层（连接/会话）；理解事务 = 理解"契约层 + 织入层 + 资源层"三层的接缝。

### 1.1 集成接缝的常见故障

| 接缝 | 故障表现 | 根因 | 解法 |
|------|---------|------|------|
| tx ↔ aop | 注解不生效 | 无 spring-aop / 代理配置问题 | 确认 aop 依赖与代理类型（[03-@Transactional 速查](03-@Transactional速查.md)） |
| tx ↔ jdbc | `IllegalStateException: No transaction...` | 管理器未配 / 连接未绑定 | 检查 DataSourceTransactionManager Bean |
| tx ↔ orm | 懒加载报错 | 事务结束后访问持久化上下文 | 事务边界内取数（或按需配置） |
| tx ↔ context | 事件不触发 | AFTER_COMMIT 但事务被标记回滚 | 检查 rollbackOnly 标记（[07-回滚机制与测试速查](07-回滚机制与测试速查.md)） |
| tx ↔ 异步 | 子线程无事务 | ThreadLocal 隔离 | 子线程自开事务（[02-事务管理器速查](02-事务管理器速查.md) 4.1） |
| tx ↔ 分布式 | 数据不一致 | 本地事务各自提交 | 评估最终一致方案 |

> 🎯 **接缝排查顺序**：先确认"事务有没有开"（日志），再确认"资源在不在事务里"（连接绑定），最后确认"边界对不对"（异常与传播）——三层接缝逐层收窄。

### 1.2 集成点选型速查

| 需求 | 首选机制 | 备选 | 禁用 |
|------|---------|------|------|
| 提交后发通知 | `@TransactionalEventListener(AFTER_COMMIT)` | outbox 表 | 事务内直接发 MQ |
| 提交后更新缓存 | afterCommit 回调 | 事件监听 | 事务内写缓存 |
| 跨线程事务 | 子线程自开事务 | 事务上下文传播（不推荐） | 手动搬 ThreadLocal |
| 跨库强一致 | Seata AT / JTA | 本地消息表（最终一致） | 单管理器多 DataSource |
| 只读报表 | NOT_SUPPORTED 挂起 | 无事务直接查 | 长事务内跑大查询 |

> 💡 **选型心法**：能异步不阻塞、能最终一致不强一致、能事件不手动回调——三个"能...不..."覆盖 80% 集成决策。

### 1.3 事务与其他 Spring 组件的协作要点

| 组件 | 协作要点 | 常见坑 |
|------|---------|--------|
| Spring Validation | 校验应在事务方法入口完成 | 校验失败在事务内抛异常 → 回滚整段（浪费） |
| 消息监听（Kafka/RabbitMQ） | 监听方法内开事务，手动 ack 与提交联动 | ack 早于事务提交 → 消息丢失窗口 |
| 批处理（Spring Batch） | Chunk 级事务，`skip` 策略与回滚规则配合 | skip 计数与保存点混用时行为差异 |
| 缓存（@Cacheable） | 缓存写入时机与事务提交错位 | 提交后清理缓存用 afterCommit |
| 定时任务（@Scheduled） | 单线程执行器内自调用陷阱 | 任务方法自己开事务或注入自身代理 |

> 🎯 **协作总原则**：事务是"最后一道一致性屏障"——把校验、远程调用、缓存写入都放到事务边界之外，事务内只留"必须原子"的本地写；边界的每一寸收缩都是性能与可靠性的双赢。

## 2. 事务 + 事件 + 异步的组合姿势

```java
// 正确姿势：事务提交后发事件 → 事件内做异步副作用
@Service
public class OrderService {
    @Transactional
    public void create(OrderCmd cmd) {
        orderDao.insert(cmd);                       // ① 事务内写库
        publisher.publishEvent(new OrderCreatedEvent(cmd.id()));  // ② 事务内发布
    }
}

@Component
public class OrderEventHandlers {
    @TransactionalEventListener(phase = AFTER_COMMIT)   // ③ 提交后才触发
    @Async                                            // ④ 异步执行（提交已发生）
    public void onCreated(OrderCreatedEvent e) {
        mq.send(e.orderId());   // ⑤ 不会出现"回滚了还发了消息"
    }
}
```

| 组合 | 语义 | 坑 |
|------|------|----|
| 事务内发布 + AFTER_COMMIT 监听 | 提交成功才触发副作用 | 监听器内 `REQUIRES_NEW` 会真提交 |
| @Async 内开事务 | 新线程新事务（独立） | 拿不到主线程事务资源 |
| 事务内直接发 MQ | 回滚后消息已发（**脏消息**） | 必须用事务事件/本地消息表 |
| 自调用 + 事务 | 代理绕过 | 注入自身/模板/拆类 |

> 💡 面试加分组合："本地事务 + 事务事件 + MQ"是**最终一致性的最小实现**（outbox 模式的简化版）——答"事务提交后如何可靠发消息"用这个链。

### 2.1 事务后可靠发消息的三种方案对比

| 方案 | 机制 | 可靠性 | 复杂度 | 适用 |
|------|------|--------|--------|------|
| 事务事件（AFTER_COMMIT） | 提交成功后回调发 MQ | 中（回调失败消息丢失） | 低 | 通知类、非关键 |
| 本地消息表（outbox） | 同事务写 outbox 表 + 定时任务投递 | 高（有表可对账） | 中 | 订单/支付等关键链路 |
| 分布式事务消息（RocketMQ 事务消息） | 半消息 + 回查 | 高 | 高 | 已有 MQ 事务消息能力 |

```java
// 本地消息表的最小实现（outbox 模式）
@Transactional
public void createOrder(OrderCmd cmd) {
    orderDao.insert(cmd);                                   // ① 业务数据
    outboxDao.insert(new OutboxMsg("ORDER_CREATED", cmd));  // ② 同事务写消息表
    // ③ 定时任务扫描 outbox → 投递 MQ → 标记已发送
}

// 事务事件是"轻量版"：提交后回调，失败靠日志/补偿
@TransactionalEventListener(phase = AFTER_COMMIT)
public void onCreated(OrderCreatedEvent e) { mq.send(...); }
```

> 🎯 **选型一句话**：消息丢了可接受 → AFTER_COMMIT 事件；丢消息不可接受 → outbox（本地消息表）；跨系统强一致 → 事务消息 / Seata（成本最高，慎选）。

### 2.2 事务 + 异步的更多姿势

| 姿势 | 语义 | 坑 |
|------|------|----|
| 事务方法内 `@Async` 调用 | 异步任务独立线程、独立事务 | 拿不到主线程事务（预期行为） |
| 异步方法内 `@Transactional` | 新线程新事务（独立提交） | 提交时机与调用方无关 |
| 事务提交后手动 `executor.submit` | afterCommit 后提交任务 | 提交失败任务丢失（outbox 兜底） |
| `@Async` + `@TransactionalEventListener` | 提交后异步处理（最优雅） | 事件失败不影响事务结果 |

```java
// 事务提交后异步处理的"黄金组合"
@TransactionalEventListener(phase = AFTER_COMMIT)
@Async("taskExecutor")
public void onCreated(OrderCreatedEvent e) {
    // 提交已发生，这里可安全做任何副作用（发消息/通知/缓存预热）
    cacheManager.evict("order", e.orderId());
}
```

> ⚠️ **顺序细节**：`@Async` 与事件监听的顺序——事件监听先触发（提交回调线程），异步在事件方法内切换线程；两者叠加 = "提交后 + 新线程 + 失败隔离"，是副作用处理的最优解。

## 3. 高频问题与排查速查

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| 事务没生效 | 自调用/private/final/类未入容器 | 代理问题三查：调用方是否容器代理、方法是否 public、类是否 final（7.0 CGLIB 默认后 final 失效） |
| 受检异常没回滚 | 默认不回滚受检异常 | `rollbackFor = Exception.class` 显式声明 |
| 异常被吞仍提交 | catch 后未标记回滚 | catch 内 `setRollbackOnly()` 或重新抛出 |
| UnexpectedRollbackException | REQUIRED 内圈失败标记了回滚 | 内圈异常别吞——冒泡或内圈改 REQUIRES_NEW |
| 事务内查询性能差 | 长事务 + 锁 | 缩小事务边界；大查询用 NOT_SUPPORTED 挂起 |
| 连接池耗尽 | REQUIRES_NEW 滥用/长事务 | 检查嵌套层数与池大小；审计日志改批量 |
| 死锁/锁超时（1205/1213） | 多事务加锁顺序不一致 | 统一加锁顺序 + `@Retryable(include = DeadlockLoserDataAccessException)` |
| 异步线程事务失效 | ThreadLocal 绑定 | 事务逻辑在调用线程；异步任务内自己开事务 |
| 测试数据"消失" | 测试事务自动回滚 | 预期行为；调试用 `@Rollback(false)` |
| 多数据源事务错库 | 未指定 transactionManager | `transactionManager` 属性指定（[02-事务管理器速查](02-事务管理器速查.md)） |
| 7.0 升级后代理行为变化 | 默认 CGLIB | `@Proxyable(INTERFACES)` 按 Bean 恢复（[Spring-Context-03](../Spring‑Context/03-配置类与扫描机制速查.md)） |
| 事务内发了 MQ 但回滚了 | 脏消息 | AFTER_COMMIT 事件/本地消息表 |

> ⚠️ **排查三板斧**：① 事务没生效 → 先查"代理链"（自调用/public/final/容器）；② 回滚不对 → 查"异常类型与规则"（rollbackFor/noRollbackFor）；③ 资源问题（池/锁）→ 查"事务边界与嵌套"（时长/层数/连接数）。

### 3.1 排查路径图与补充问题

```text
事务问题排查决策树：
  ① 事务没生效？
      ├─ 日志有没有 "Getting transaction for"？
      │    ├─ 没有 → 代理问题：自调用 / public / final / 容器 / 依赖
      │    └─ 有 → 进入 ②
  ② 该回滚没回滚？
      ├─ 异常类型匹配 rollbackFor？noRollbackFor 命中？
      ├─ 异常被 catch 吞了？（setRollbackOnly）
      └─ 内圈 REQUIRED 标记后外层继续？（UnexpectedRollbackException）
  ③ 回滚了但资源异常？
      ├─ 连接池耗尽 → 嵌套 / 长事务 / REQUIRES_NEW 滥用
      ├─ 锁超时 / 死锁 → 加锁顺序 / 锁范围 / 锁内长逻辑
      └─ 数据不一致 → 边界外操作 / 异步 / 分布式
```

**补充高频问题：**

| 现象 | 根因 | 解法 |
|------|------|------|
| 事务内自增 ID 不连续 | 回滚不回收 AUTO_INCREMENT | 正常现象，勿按 ID 连续性设计业务 |
| 批量插入半成功 | 单条失败整体回滚 | NESTED 逐条保存点 / 分批提交 |
| 事务方法调用存储过程 | 存储过程内部提交无法回滚 | 存储过程不 commit；或改应用层 |
| `TransactionTimedOutException` | 事务超时（timeout 属性） | 短 SQL 拆出 / 调大超时 |
| 事务内远程调用慢 | 连接被占、锁被持 | 远程调用移到事务外 |

> ⚠️ **生产巡检清单**（每月）：长事务 TOP 榜（> 1s 事务）、连接池活跃数、死锁日志、事务超时报警——事务问题 90% 是"边界太大"而非"框架错了"。

### 3.2 集群与多实例环境下的事务注意点

| 场景 | 问题 | 对策 |
|------|------|------|
| 多实例定时任务 | 多个实例同时跑事务任务 | 分布式锁（Redis/DB 锁表）串行化 |
| 分布式锁 + 事务顺序 | 先锁后事务 / 先事务后锁语义不同 | 锁内开事务（锁覆盖事务）或先事务后锁（锁外）按需选择 |
| 事务内调用远程服务 | 多实例负载均衡下锁等待放大 | 远程调用移出事务（见 4.1） |
| 数据库迁移/灰度 | 新旧版本事务行为差异 | 事务测试回归 + 灰度流量验证 |

```java
// 定时任务 + 分布式锁 + 事务的正确顺序：锁在外、事务在内
public void scheduledJob() {
    if (distLock.tryLock("job:settle", 60)) {   // ① 先拿分布式锁
        try {
            settleService.settle();             // ② 事务方法（锁覆盖事务）
        } finally {
            distLock.unlock("job:settle");
        }
    }
}
```

> 🎯 **集群事务第一原则**：**锁覆盖事务**（锁先于事务、释放晚于事务结束）——否则两个实例可同时进入事务，分布式锁形同虚设；事务里再拿锁则可能死锁（两个事务互相等对方的锁）。

### 4.1 面试追问深水区

**追问与回答锚点：**

1. "@Transactional 在接口上还是实现类上？"——都可（7.0 CGLIB 下接口注解仍解析）；团队规范建议实现类，规避接口语义歧义；
2. "事务里调了第三方接口超时，怎么优化？"——先拆：第三方调用移出事务（事件/异步），事务只包本地写；
3. "一个大事务里有 100 个更新，如何最小化锁时长？"——拆小事务 + 批量 SQL + 索引优化 + 锁内无 IO；
4. "主从读写分离下事务怎么办？"——写走主库（事务内）；读走从库（无事务 / SUPPORTS）；强制走主库用 `@Transactional(readOnly = false)` 或 Hint；
5. "Seata AT 模式与本地事务的关系？"——AT 模式在本地事务之上做全局锁与补偿；spring-tx 本地事务仍是基础单元（见 [Spring全家桶-14](../../../Spring全家桶/14-分布式事务-Seata.md)）；
6. "如何给事务加监控？"——`label` 属性 + Micrometer 事务指标（commit/rollback 计数、时长分布）+ TransactionSynchronization 打点；
7. "事务日志量大会影响性能吗？"——事务 DEBUG 日志量小（每个事务几行），可长期开启；SQL 层日志（show_sql）才需要按需开启。

> 💡 **终局认知**：事务问题 90% 是"边界设计"问题（边界太大 / 嵌套太深 / 异常语义不清），10% 是机制问题（代理 / 传播 / 隔离）——把 08 篇的排查树走完，剩下的问题基本都指向"把事务边界画小"。
