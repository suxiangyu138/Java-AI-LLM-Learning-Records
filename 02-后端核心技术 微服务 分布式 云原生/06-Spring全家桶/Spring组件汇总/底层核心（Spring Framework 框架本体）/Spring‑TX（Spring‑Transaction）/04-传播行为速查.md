## 1. 七种传播一览

| 传播行为 | 无外层事务时 | 有外层事务时 | 典型场景 |
|---------|-------------|-------------|---------|
| `REQUIRED` | 新建 | **加入**（同一物理事务） | ✅ 默认；常规业务 |
| `REQUIRES_NEW` | 新建 | **挂起外层、另建新事务**（第二条连接） | 日志/审计/补偿（必须独立提交） |
| `NESTED` | 新建 | 保存点嵌套（可部分回滚） | 复杂流程的部分成功 |
| `SUPPORTS` | 无事务执行 | 加入 | 可事务可不事务的工具方法 |
| `MANDATORY` | **抛异常** | 加入 | 强制调用方开事务 |
| `NOT_SUPPORTED` | 无事务 | 挂起外层、无事务执行 | 慢查询/长任务脱离事务 |
| `NEVER` | 无事务 | **抛异常** | 禁止事务内调用 |

> 🎯 **核心要点（面试必背）**：REQUIRED 是"加入"不是"嵌套"——内圈异常**不实际回滚**，只标记 rollbackOnly，最终外圈提交时整体回滚（抛 `UnexpectedRollbackException`）；REQUIRES_NEW 才是真独立事务；NESTED 用数据库保存点做真部分回滚。

## 2. REQUIRED：默认与 90% 场景

```java
@Service
public class OrderService {
    @Transactional
    public void createOrder(OrderCmd cmd) {
        orderDao.insert(cmd);                 // ① 事务 A
        inventoryService.deduct(cmd);         // ② 同一事务（加入）
        payService.charge(cmd);               // ③ 同一事务（加入）
    }
}

// 三个 DAO 操作同一条物理连接、同一事务 —— 要么全成要么全败
```

| 特性 | 说明 |
|------|------|
| 连接 | 一条物理连接贯穿 |
| 内圈异常 | 标记 rollbackOnly → 外圈最终回滚（整体原子） |
| 内圈异常被捕获 | **事务已被标记回滚**——外圈继续执行也会在提交时炸（UnexpectedRollbackException） |
| 成本 | 最低（无额外连接/保存点） |

> ⚠️ **经典陷阱**：内圈异常被 catch 后，外圈以为还能提交——实际整个事务已判死缓；"捕获异常继续处理"在 REQUIRED 里**不可行**，只能让异常冒泡或改 REQUIRES_NEW。

### 2.1 REQUIRED 内圈外圈完整交互

```java
@Service
public class OuterService {
    @Transactional
    public void outer() {
        try {
            innerService.inner();            // REQUIRED：加入同一事务
        } catch (Exception e) {
            log.warn("内圈失败已捕获");        // ❌ 致命：事务已被标记回滚
        }
        // 提交时抛 UnexpectedRollbackException —— 数据全部回滚
    }
}
```

| 场景 | 内圈行为 | 外圈结果 |
|------|---------|---------|
| 内圈正常返回 | 什么都不做 | 提交 ✅ |
| 内圈抛异常且冒泡 | 标记 rollbackOnly → 异常传到外圈 → 外圈回滚 | 整体回滚 ✅ |
| 内圈抛异常被外圈捕获 | 标记 rollbackOnly（异常已被吞） | 外圈提交时 **UnexpectedRollbackException**，整体回滚 ✅（但失败暴露滞后） |
| 外圈捕获后继续写库 | 同上 | 写库全部回滚（白写） |

> ⚠️ **最佳实践**：REQUIRED 内圈的业务异常**应当冒泡**——靠外圈统一处理；"捕获后继续"在 REQUIRED 语义下必然拿到 UnexpectedRollbackException，不如让异常走正常链路（或按需改 REQUIRES_NEW）。

### 2.2 REQUIRED 的边界与适用性检查

| 检查项 | 结论 |
|--------|------|
| 内圈异常要"部分成功"？ | 不适合——REQUIRED 无保存点，改 NESTED |
| 内圈必须独立提交？ | 不适合——改 REQUIRES_NEW |
| 内圈参与同一物理事务即可？ | ✅ 适合——REQUIRED 是默认答案 |
| 内圈失败后外圈还要继续写？ | 不适合——标记已生效，改 NESTED 或重新设计 |

**生产经验**：REQUIRED 内圈失败的经典改法不是"catch 住继续"，而是**内圈先做校验、把可能失败的部分前置**——校验通过后进入事务主体，减少运行时异常概率；必要时用 NESTED 提供"逐段后悔"能力。

> 🎯 **一句话**：REQUIRED 的代价是"失败无边界"——内圈任何运行时异常都是全局性的；业务上"可失败但可继续"的需求必须显式换传播，REQUIRED 不是万能默认。

## 3. REQUIRES_NEW：独立事务

```java
@Service
public class OrderService {
    @Transactional
    public void createOrder(OrderCmd cmd) {
        try {
            orderDao.insert(cmd);                 // 事务 A
        } catch (Exception e) {
            auditService.logFailure(cmd, e);      // REQUIRES_NEW：事务 B（独立提交）
        }
    }
}

@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logFailure(OrderCmd cmd, Exception e) { ... }
}
```

| 特性 | 说明 |
|------|------|
| 物理连接 | **第二条连接**（池需有富余） |
| 提交时机 | 方法返回即提交——不随外圈成败 |
| 适用 | 日志/审计/通知/补偿——"无论主流程成败都必须落库" |
| 代价 | 多一条连接、多一次提交；并发下增加锁竞争 |
| 与外圈交互 | 外圈回滚**不影响**已提交的内圈（需业务补偿） |

> 🎯 **核心要点**：REQUIRES_NEW = "事务内开小灶"——审计日志在业务失败时也能保存；代价是**多连接**，循环里滥用会打爆连接池（每循环一次开一个新事务+连接）。

### 3.1 REQUIRES_NEW 与连接池

**每条 REQUIRES_NEW = 一条独立物理连接**——嵌套 N 层就同时占用 N+1 条连接：

```java
// ❌ 反例：循环 1000 条 × REQUIRES_NEW = 1000 次连接获取/释放
@Transactional
public void batch() {
    for (Row row : rows) {
        auditService.log(row);     // REQUIRES_NEW：每轮新连接
    }
}

// ✅ 正例：批量审计先攒后写（单条 SQL 批量插入）
@Transactional
public void batch() {
    List<AuditRow> buffer = new ArrayList<>();
    for (Row row : rows) {
        buffer.add(toAudit(row));
        if (buffer.size() == 500) {
            auditService.batchInsert(buffer);
            buffer.clear();
        }
    }
    if (!buffer.isEmpty()) auditService.batchInsert(buffer);
}
```

| 连接池风险 | 表现 | 应对 |
|-----------|------|------|
| 连接池耗尽 | `HikariPool-1 - Connection is not available, request timed out` | 压缩嵌套层数；增大池；审计改批量 |
| 死锁 | REQUIRES_NEW 内锁与主事务锁交叉 | 审计表不参与业务锁；统一加锁顺序 |
| 主事务回滚、审计已提交 | 业务数据与审计数据不一致 | 审计先行记录"意图"，对账任务兜底 |

> 💡 **选型铁律**：REQUIRES_NEW 用于"必须独立存活"的少数场景（审计/通知），不是默认工具——能用 REQUIRED 就不用 REQUIRES_NEW，能用批量就不用循环。

### 3.2 REQUIRES_NEW 的三问自检

| 自检问题 | 通过标准 |
|---------|---------|
| 内圈必须不受外圈成败影响？ | 是才用 REQUIRES_NEW |
| 内圈数据能容忍"外圈回滚后仍存在"？ | 是才用（否则会造成不一致） |
| 调用频率与连接池大小匹配？ | 并发 × 嵌套层数 < 池最大连接数 |

**一个典型的"不需要 REQUIRES_NEW"的反例：**

```java
// ❌ 想"内圈失败不影响外圈"——其实 NESTED 就够，且省一条连接
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void rowTask(Row row) { ... }

// ✅ 同连接保存点，失败只回滚本行，外圈继续
@Transactional(propagation = Propagation.NESTED)
public void rowTask(Row row) { ... }
```

> 🎯 **区分口诀**：**"失败后还要继续"用 NESTED（同连接）；"成功与否都要独立提交"用 REQUIRES_NEW（新连接）**——一个管回滚边界，一个管提交边界，混用前先对号入座。

## 4. NESTED：保存点嵌套

```java
@Transactional
public void batchImport(List<Row> rows) {
    for (Row row : rows) {
        try {
            rowService.saveRow(row);        // NESTED：每条一个保存点
        } catch (BadRowException e) {
            // 本行回滚，其余继续 —— 部分成功导入
        }
    }
}

@Transactional(propagation = Propagation.NESTED)
public void saveRow(Row row) { ... }
```

| 特性 | 说明 |
|------|------|
| 机制 | **数据库保存点（SAVEPOINT）**——内圈回滚只回滚到保存点 |
| 提交 | 内圈不独立提交，随外圈一起 |
| 差异 | NESTED 内圈异常**不影响外圈继续**（不同于 REQUIRED） |
| 限制 | 依赖数据库保存点支持（MySQL 支持；JPA 部分实现回退 join 语义） |
| 与 REQUIRES_NEW 对比 | 同物理连接 vs 新连接；最终一起提交 vs 独立提交 |

> 💡 面试辨析：**REQUIRED 内圈失败 = 全盘皆输；NESTED 内圈失败 = 只回滚自己；REQUIRES_NEW 内圈失败 = 只影响自己且可独立存活**——按"失败隔离度"从低到高记忆。

### 4.1 NESTED vs REQUIRED vs REQUIRES_NEW 八维对比

| 维度 | REQUIRED | NESTED | REQUIRES_NEW |
|------|----------|--------|--------------|
| 物理连接 | 同一连接 | 同一连接 | 新连接 |
| 内圈失败 | 标记 rollbackOnly | 回滚到保存点 | 独立回滚 |
| 外圈能否继续 | 不能（已被标记） | 能 | 能 |
| 内圈提交时机 | 随外圈 | 随外圈 | 方法返回即提交 |
| 外圈回滚影响内圈 | 一起回滚 | 一起回滚 | **不影响**（已提交） |
| 失败隔离度 | 无 | 中 | 高 |
| 额外成本 | 无 | 保存点（连接级少量开销） | 新连接 + 一次提交 |
| 典型场景 | 常规编排 | 批量逐条容错 | 审计/日志/补偿 |

> 🎯 **记忆锚点**：REQUIRED 内圈异常 = 全盘皆输；NESTED = 部分后悔（回滚到书签）；REQUIRES_NEW = 互不连坐（各管各的提交）——三者差异只在"失败隔离度"一条线上，面试把这张表默出来即满分。

### 4.2 NESTED 的工程陷阱

| 陷阱 | 说明 | 规避 |
|------|------|------|
| 保存点数量 | 循环内逐行 NESTED，保存点随行数增长 | 限制单事务行数（如每 500 行分批） |
| JPA 回退 | 无保存点支持时退化为 REQUIRED——"部分回滚"静默失效 | 生产前验证：MySQL + Hibernate 通常支持 |
| 锁不回退 | 保存点回滚不释放事务级锁 | 保存点只能救数据，救不了锁 |
| 外层标记残留 | 内圈 NESTED 抛异常未被捕获时，异常冒泡仍标记外层 | 捕获边界与传播声明保持一致 |

> ⚠️ **验证建议**：NESTED 上线前必须写"内圈失败、外圈继续提交"的集成测试——一旦底层 ORM 回退为 REQUIRED，测试会立刻暴露（断言外圈数据仍在，但内圈已回滚）。

## 5. 四种边缘传播

| 传播 | 行为 | 使用 |
|------|------|------|
| `SUPPORTS` | 有则加入、无则裸跑 | 通用工具/可选事务的查询 |
| `MANDATORY` | 无外层直接抛 `IllegalTransactionException` | 强制"必须由调用方开事务"的服务（防裸跑写库） |
| `NOT_SUPPORTED` | 挂起外层、无事务执行 | 长查询/大报表（避免占着事务连接）；JPA 混用注意持久化上下文 |
| `NEVER` | 有外层抛异常 | 禁止在事务内调用（如异步补偿入口） |

```java
@Transactional(propagation = Propagation.NOT_SUPPORTED)
public List<Order> heavyReport(Date from, Date to) {
    return jdbc.query(...);   // 挂起外层事务执行——不占事务、不锁表太久
}
```

> ⚠️ **挂起的代价**：NOT_SUPPORTED/REQUIRES_NEW 挂起外层时，外层连接仍**持有**（不释放）——池占用不变，只是不参与执行；挂起期间外层资源保持，注意总连接数上限。

### 5.1 边缘传播的实战组合

| 组合 | 场景 | 说明 |
|------|------|------|
| SUPPORTS + 非事务工具类 | 日志格式化、缓存读取 | 有事务则参与，无事务也不报错 |
| MANDATORY + 写服务 | 强制在事务内执行的写入口 | 防"裸跑"：无事务直接抛 `IllegalTransactionStateException` |
| NOT_SUPPORTED + 大报表 | 挂起事务跑长查询 | 不占事务连接、不长期持锁 |
| NEVER + 定时补偿入口 | 禁止在事务内触发的任务 | 防死锁 / 防连接嵌套 |

```java
// MANDATORY 的典型姿势：内部写服务强制事务上下文
@Transactional(propagation = Propagation.MANDATORY)
public void innerWrite(Data d) {
    // 被无事务的调用方调 → 抛异常（防裸跑）
    // 被事务调用方调 → 正常加入
}
```

> ⚠️ **NOT_SUPPORTED 陷阱**：挂起外层事务时**外层连接仍被持有**（只是不参与执行）——大报表场景若主事务还持着行锁，挂起并不能释放锁；真正的长查询优化是缩小外层事务边界（把大查询移出事务方法）。

## 6. 传播选型速查

| 业务形态 | 传播选择 |
|---------|---------|
| 常规 CRUD/服务编排 | REQUIRED（默认） |
| 审计/日志（主流程成败都要） | REQUIRES_NEW |
| 批量导入逐行容错 | NESTED |
| 只读查询工具方法 | SUPPORTS |
| 禁止裸跑的写服务 | MANDATORY |
| 大报表/长任务 | NOT_SUPPORTED |
| 防死锁的只读调用方 | NEVER |

> 🎯 **核心要点**：传播选择的本质是回答三个问题——**失败要隔离吗？（REQUIRED vs NESTED）要独立存活吗？（REQUIRES_NEW）允许无事务吗？（SUPPORTS/MANDATORY）**——先把"失败语义"想清楚，再选传播，顺序反了必踩坑。

### 6.1 传播行为面试追问

**高频追问与回答锚点：**

1. "REQUIRED 内圈异常被吞掉，外圈会发生什么？"——提交时 UnexpectedRollbackException，整体回滚（rollbackOnly 机制见 [02-事务管理器速查](02-事务管理器速查.md)）；
2. "NESTED 需要数据库什么能力？"——SAVEPOINT（MySQL/PG 支持）；JPA 部分实现无保存点时会**回退为 REQUIRED 语义**（源码锚点：`handleExistingTransaction` 中保存点管理为空的 fallback 分支）；
3. "REQUIRES_NEW 的挂起是怎么实现的？"——suspend：解绑资源 + 记录挂起状态，新事务完成后 resume 恢复（`AbstractPlatformTransactionManager` 模板统一处理）；
4. "什么时候绝对不能用 REQUIRES_NEW？"——循环内高频调用（连接池耗尽）、需要与主事务同生死的业务数据；
5. "SUPPORTS 和 NOT_SUPPORTED 无事务时的区别？"——两者无外层时都是"无事务执行"；只在"有外层事务"时有差异（加入 vs 挂起）；
6. "MANDATORY 与 NEVER 的区别？"——MANDATORY 是"必须要有事务"（无则抛异常），NEVER 是"必须没有事务"（有则抛异常）——一对相反的强制约束。

> 🎯 **答题框架**：任何传播题都按"无外层 / 有外层 + 失败时谁负责回滚 + 提交时机"三段式回答——覆盖 7 种传播全部考点；再补一句"传播语义全部由 AbstractPlatformTransactionManager 的 handleExistingTransaction 分派"即达源码层。

### 6.2 传播速记口诀与自测

**七种传播的速记口诀：**

```text
REQUIRED      有则加入无则建         —— 默认，90% 场景
REQUIRES_NEW  挂起外层另开炉灶       —— 独立存活
NESTED        保存点小后悔           —— 部分回滚
SUPPORTS      随遇而安               —— 可有可无
MANDATORY     没事务就翻脸           —— 强制要有
NOT_SUPPORTED 挂起外层裸奔           —— 脱事务跑
NEVER         有事务就翻脸           —— 强制没有
```

**自测题（快速检验理解）：**

| 自测题 | 答案 |
|--------|------|
| 外圈 REQUIRED 调内圈 REQUIRES_NEW，内圈成功外圈回滚，内圈数据？ | 已提交，存活（独立事务） |
| 外圈 REQUIRED 调内圈 NESTED，内圈失败被捕获，外圈继续？ | 可以继续，内圈只回滚到保存点 |
| 外圈无事务调内圈 MANDATORY？ | 抛 `IllegalTransactionStateException` |
| 外圈 REQUIRED 调内圈 NOT_SUPPORTED，内圈抛异常？ | 内圈无事务直接失败，外圈不受标记影响（但异常冒泡会触发外圈回滚） |

> 💡 最后一个自测是隐藏考点：NOT_SUPPORTED 内圈异常**不会标记外层**（因为根本没参与外层事务），但异常本身冒泡出去，外圈 catch 后仍可提交——与 REQUIRED 内圈"必然标记"形成鲜明对比。
