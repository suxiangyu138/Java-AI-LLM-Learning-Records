## 1. PlatformTransactionManager：三方法契约

```java
public interface PlatformTransactionManager {
    TransactionStatus getTransaction(TransactionDefinition definition);
    void commit(TransactionStatus status);
    void rollback(TransactionStatus status);
}
```

| 方法 | 行为 |
|------|------|
| `getTransaction(def)` | 按传播行为：开启新事务 / 加入已有 / 挂起外层（返回 TransactionStatus） |
| `commit(status)` | 已标记回滚则实际回滚；否则提交 |
| `rollback(status)` | 强制回滚（含仅标记） |

```text
事务生命周期（AbstractPlatformTransactionManager 编排）：
  getTransaction → doBegin（实现类：连接.setAutoCommit(false) / EntityManager 开启）
    → 业务执行（拦截器/模板）
    → commit / rollback → doCommit / doRollback → doCleanupAfterCompletion
```

> 🎯 **核心要点**：事务管理器只有三个方法——**所有复杂语义（传播/保存点/回滚规则）都在 AbstractPlatformTransactionManager 的模板里编排**，实现类只关心"我的资源怎么开启/提交/回滚"。

### 1.1 TransactionStatus：事务的"运行病历"

```java
public interface TransactionStatus extends SavepointManager, Flushable {
    boolean isNewTransaction();          // 本次调用是否新建了事务（REQUIRED 加入则 false）
    boolean hasSavepoint();              // 是否处于保存点状态（NESTED 内圈为 true）
    void setRollbackOnly();              // 标记回滚（不立即回滚，提交时生效）
    boolean isRollbackOnly();            // 是否已被标记回滚
    void flush();                        // 强制刷新（JPA 场景）
}
```

| 状态位 | 典型使用 |
|--------|---------|
| `isNewTransaction` | 判断"提交责任"在谁——内圈 REQUIRED 返回的 status 该位为 false，**不参与最终提交** |
| `setRollbackOnly` | 捕获异常后主动标记回滚（见 [07-回滚机制与测试速查](07-回滚机制与测试速查.md)） |
| `hasSavepoint` | NESTED 内圈为 true——回滚只到保存点 |

> 💡 面试细节：`isNewTransaction()==false` 的事务在 `commit(status)` 时不会真正提交——由最外层负责；这也是"内圈 commit 是空操作"说法的来源。

### 1.2 三方法契约的完整语义

```java
// 契约三方法在"加入已有事务"时的真实行为（面试必背）
PlatformTransactionManager ptm;

// ① REQUIRED 加入时：不开启新事务，返回"非新事务" status
TransactionStatus st = ptm.getTransaction(def);   // 可能复用，也可能新建

// ② 内圈（非新事务）commit：实际不提交，只做收尾
ptm.commit(st);       // isNewTransaction()==false → 空操作（提交责任在外层）

// ③ 内圈 rollback：只标记，不真回滚（REQUIRED 场景）
ptm.rollback(st);     // setRollbackOnly → 外圈提交时 UnexpectedRollbackException
```

| 调用方 | commit 的实际效果 | rollback 的实际效果 |
|--------|------------------|-------------------|
| 外层（新事务） | 真提交（或发现标记后回滚） | 真回滚 |
| 内圈（加入的） | 空操作 | 仅标记 rollbackOnly |

> 🎯 **一句话总结**：契约的三个方法"行为随事务层级变化"——**只有"新建事务"的那一层拥有提交/回滚的决定权**；理解这一点，传播行为的所有面试题都有了统一答案。

## 2. 管理器实现全家

| 实现 | 模块 | 资源 | 场景 |
|------|------|------|------|
| `DataSourceTransactionManager` | spring-jdbc | JDBC Connection | ✅ 默认（JDBC/MyBatis/Spring Data JDBC） |
| `JpaTransactionManager` | spring-orm | EntityManager | JPA（Hibernate） |
| `HibernateTransactionManager` | spring-orm（7.0 迁 `orm.jpa.hibernate`） | Session/EntityManager | Hibernate 6/7 原生 API |
| `JtaTransactionManager` | spring-tx（jta 包） | JTA（XA） | 多资源分布式事务（需事务中间件） |
| `ReactiveTransactionManager` | spring-tx（reactive 包） | 响应式连接 | R2DBC/MongoDB reactive |

```java
// 多数据源场景显式装配（Boot 自动配置仅单数据源时生效）
@Configuration
public class TxConfig {
    @Bean
    @Primary
    public PlatformTransactionManager orderTxManager(@Qualifier("orderDs") DataSource ds) {
        return new DataSourceTransactionManager(ds);
    }

    @Bean
    public PlatformTransactionManager reportTxManager(@Qualifier("reportDs") DataSource ds) {
        return new DataSourceTransactionManager(ds);
    }
}
```

> ⚠️ **多管理器陷阱**：容器有多个 `PlatformTransactionManager` 时，`@Transactional` 默认用 `@Primary` 那个——**不同库的事务要靠 `transactionManager` 属性显式指定**（见 [03-@Transactional 速查](03-@Transactional速查.md)）。

### 2.1 DataSourceTransactionManager 的关键行为

```text
doBegin 做了四件事（对应 TransactionDefinition 的四个属性）：
  ① 从 DataSourceUtils 获取连接（优先线程已绑定的，否则池取新连接）
  ② connection.setAutoCommit(false)              ← 事务开启的本质
  ③ 按 definition 设置隔离级别 / 只读 / 超时（下推给 JDBC Connection）
  ④ 连接绑定到线程（TransactionSynchronizationManager.bindResource）

doCommit / doRollback：
  connection.commit() / connection.rollback()

doCleanupAfterCompletion：
  resetConnectionAfterCompletion（恢复 autoCommit / 隔离 / 超时）→ 归还连接
```

| 细节 | 说明 |
|------|------|
| 连接获取 | `DataSourceUtils.getConnection`——**先查线程绑定，命中即复用**（REQUIRED 加入的核心） |
| 超时下推 | 设 `setNetworkTimeout` / 语句超时，超时抛 `TransactionTimedOutException` |
| 只读下推 | 部分驱动跳过写锁获取（MySQL 5.7 后基本无差别） |
| 连接归还 | 事务结束后**必归池**——异常路径由 finally 保证 |

> 🎯 **面试抓手**：问"REQUIRED 怎么做到同一连接"→ 答 `DataSourceUtils.getConnection` 的线程绑定查询；问"事务开启的本质"→ 答 `setAutoCommit(false)` + 提交/回滚 + 恢复，三句话闭环。

### 2.2 各管理器实现的差异点

| 差异维度 | DataSourceTransactionManager | JpaTransactionManager | JtaTransactionManager |
|---------|-----------------------------|----------------------|----------------------|
| 资源对象 | Connection | EntityManager / 持久化上下文 | 多个资源（XA） |
| 开启事务 | `setAutoCommit(false)` | `joinTransaction` / 创建事务 EntityManager | `UserTransaction.begin()` |
| 回滚 | `connection.rollback()` | 持久化上下文回滚 + 清缓存 | `UserTransaction.rollback()` |
| 保存点 | 支持（JDBC SAVEPOINT） | 视 JPA 实现（Hibernate 支持） | 一般不支持 |
| 只读提示 | 下推驱动（弱） | 关闭 dirty checking（强优化） | 部分支持 |
| 使用场景 | JDBC/MyBatis/Spring Data JDBC | JPA/Hibernate | 多资源分布式 |

**JpaTransactionManager 的额外职责**：事务提交前自动 flush 持久化上下文（保证变更先落库再提交）；回滚时清理一级缓存（避免脏实体残留）——这是 ORM 管理器独有的"上下文管理"负担。

> 💡 **选型细节**：Hibernate 6/7 原生 API 项目用 `HibernateTransactionManager`（spring-orm，7.0 迁至 `orm.jpa.hibernate` 包）；用 JPA 标准接口则统一 `JpaTransactionManager`——两者语义一致，只是对 Session/EntityManager 的接触面不同。

## 3. AbstractPlatformTransactionManager：模板骨架

| 能力 | 说明 |
|------|------|
| 传播编排 | 已有事务 → 挂起/加入/嵌套（模板统一处理，实现类不管） |
| 保存点 | NESTED 用保存点（JPA 不支持时回退 join） |
| 回滚标记 | `setRollbackOnly` 延迟回滚（外圈感知内圈失败） |
| 同步回调 | 提交前/后钩子（afterCommit、afterCompletion） |
| 超时 | 事务超时（setTransactionTimeout → 驱动层超时） |

```text
内圈失败外圈回滚的机制（面试必问）：
  REQUIRED 内圈抛异常 → 内圈只"标记 rollbackOnly"（不实际回滚）
  → 外圈提交时发现标记 → 抛 UnexpectedRollbackException 并整体回滚
```

> 🎯 **核心要点**：**"内圈异常、外圈事务必须整体回滚"**由 AbstractPlatformTransactionManager 的 rollbackOnly 标记实现——REQUIRED 嵌套不是真正的嵌套事务，只是参与同一物理事务；这是面试"REQUIRED 内圈异常外圈会怎样"的标准答案。

### 3.1 模板方法的完整调用链（源码级）

```text
AbstractPlatformTransactionManager.getTransaction(def)
  ├── 无活跃事务 → doGetTransaction() → 校验超时 → doBegin()
  ├── 有活跃事务 → handleExistingTransaction(def)    ← 传播行为分岔点
  │       ├── REQUIRED/SUPPORTS/MANDATORY → 复用，返回"非新事务"status
  │       ├── REQUIRES_NEW → suspend() 挂起外层 → doBegin() 新事务
  │       ├── NESTED → 有保存点支持 → 创建保存点（JPA 无保存点则退化为 REQUIRED 语义）
  │       ├── NOT_SUPPORTED → suspend() 无事务执行
  │       └── NEVER → 抛 IllegalTransactionStateException
  └── 注册同步回调

commit(status)  → processCommit
  ├── 标记了 rollbackOnly → 走 processRollback（抛 UnexpectedRollbackException）
  ├── 非新事务 → 不提交（提交责任在外层）
  └── 新事务 → triggerBeforeCommit → doCommit → triggerAfterCommit

rollback(status) → processRollback
  ├── 新事务 → doRollback（真正回滚）
  └── 非新事务 → 仅 setRollbackOnly（内圈 REQUIRED 场景，外圈最终感知）
```

> 🎯 **核心理解**：模板方法把"传不传播、挂不挂起、是否真提交"全部收拢，实现类只需实现 doGetTransaction / doBegin / doCommit / doRollback / doCleanupAfterCompletion 五个钩子——**"模板方法模式"是 spring-tx 的骨架设计**；面试被问"Spring 事务源码结构"直接画这棵调用树。

### 3.2 骨架能力的边界细节

| 骨架能力 | 细节 | 边界/坑 |
|---------|------|---------|
| 超时管理 | 事务开始计时，`getTimeout()` 递减；超时后执行抛 `TransactionTimedOutException` | 超时只作用于"后续 SQL 语句"，已执行的锁不受影响 |
| 挂起 | `suspend()`：解绑资源 + 保存挂起状态；`resume()`：恢复 | 挂起期间外层连接仍被持有（池占用不减） |
| rollbackOnly | 内圈标记 → 外圈 processCommit 抛 `UnexpectedRollbackException` | 标记后外圈继续写库是白写（最终全回滚） |
| 保存点 | `createSavepoint` / `rollbackToSavepoint` / `releaseSavepoint` | 连接级能力；临时表、锁不随保存点回滚 |
| 同步回调 | 注册列表按顺序触发 afterCommit / afterCompletion | afterCommit 中抛异常不影响提交结果 |

```java
// 超时与回滚标记的联动示例：批量任务每批限时
txTemplate.execute(status -> {
    status.setRollbackOnly();          // 主动标记：即使不抛异常也回滚
    return null;                        // 常见于"校验失败但不想抛异常"的场景
});
```

> ⚠️ **易错点**：`TransactionTimedOutException` 只保证"数据库语句不再执行"，不保证锁立即释放——超时后的清理（连接回滚归还）由 doCleanupAfterCompletion 兜底，但锁的释放仍以"事务真正回滚"为准。

## 4. TransactionSynchronizationManager：资源绑定

```text
TransactionSynchronizationManager（线程局部静态工具）：
  ┌── Map<DataSource, ConnectionHolder>   资源 → 连接持有者（绑定）
  ├── Map<Object, TransactionSynchronization> 同步回调列表
  ├── ThreadLocal<TransactionStatus>      当前事务状态
  └── ThreadLocal<Boolean>                事务激活标记

  JdbcTemplate/MyBatis 取连接时先查它 → 命中 = 加入当前事务
```

| 能力 | 说明 |
|------|------|
| 资源绑定 | 线程 → 事务资源（连接/EntityManager） |
| 同步回调 | `registerSynchronization`（afterCommit/afterRollback） |
| 隔离 | **线程级 ThreadLocal**——异步线程不带事务（@Async 内事务失效的根因） |
| 多资源 | JTA 下可绑定多资源（XA 事务） |

> ⚠️ **异步失效原理**：事务绑定是线程局部的——`@Async` 新线程里 `TransactionSynchronizationManager` 为空，新开事务或直接无事务；跨线程传事务要用 `TransactionTemplate` 显式包裹或传播上下文。

### 4.1 资源绑定的两个关键推论

**推论一：同一线程 = 同一事务。** 线程内所有 DAO 调用经 `DataSourceUtils.getConnection` 拿到同一连接，天然处于同一事务——与调用方是 JdbcTemplate、MyBatis 还是 Spring Data JDBC 无关。这也解释了"为什么换了 ORM 事务语义不变"。

**推论二：线程一变 = 事务消失。** 新线程的 ThreadLocal 全空——`@Async`、手动 `new Thread` 都不带事务。跨线程传事务的三种正规姿势：

| 姿势 | 做法 | 适用 |
|------|------|------|
| 任务内自开事务 | 异步方法自身 `@Transactional` / TransactionTemplate | 绝大多数场景 ✅ |
| 事务资源手动转移 | `unbindResource` + `bindResource` 手工搬运 | 极少数，易泄漏，不推荐 |
| 事务上下文传播 | 响应式 `TransactionalOperator`（订阅线程传播） | 响应式栈 |

> ⚠️ **生产铁律**：永远不要尝试"把主线程事务带到子线程"——绑定的连接线程不安全且提交时机不可控；正确做法是子线程自己开事务（详见 [06-编程式事务速查](06-编程式事务速查.md)）。

### 4.2 同步回调：afterCommit 钩子的正确姿势

`TransactionSynchronization` 是"事务生命周期监听器"——注册后按阶段回调：

| 回调方法 | 触发时机 | 典型用途 |
|---------|---------|---------|
| `beforeCommit` | 提交前（变更未落库） | 最后校验、补写审计字段 |
| `afterCommit` | 提交成功后 | 发事件/消息（失败只记日志） |
| `afterCompletion` | 提交/回滚都触发（终态） | 清理资源、统计打点 |

```java
// 事务提交后发事件的经典写法（声明式同样适用）
@Transactional
public void create(OrderCmd cmd) {
    orderDao.insert(cmd);
    TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    eventPublisher.publishEvent(new OrderCreated(cmd.id()));
                }
            });
}
```

> ⚠️ **afterCommit 的边界**：① 回调里抛异常不影响事务结果（已提交）；② 回调内再开事务（REQUIRES_NEW）会真提交；③ afterCommit 里拿不到事务内数据访问（连接已归还）——只做"提交成功后的通知"，不做"再写库"。

## 5. 管理器装配与选型

| 技术栈 | 管理器 | 装配 |
|--------|--------|------|
| JDBC/MyBatis/Spring Data JDBC | DataSourceTransactionManager | Boot 自动（starter-jdbc） |
| JPA | JpaTransactionManager | Boot 自动（starter-data-jpa） |
| 双数据源 | 各配一个 + @Primary | 手动 |
| 分布式（多库强一致） | JtaTransactionManager / Seata | 手动 + 中间件 |
| 响应式 | ReactiveTransactionManager | Boot 自动（R2DBC starter） |

> 💡 **选型一句话**：单资源 → 对应资源管理器；多资源分布式 → 先问业务"是否需要强一致"——多数场景最终一致 + 本地事务 + 补偿即可，避免 XA 复杂度（见 [Spring全家桶-14-分布式事务-Seata](../../../Spring全家桶/14-分布式事务-Seata.md)）。

### 5.1 多管理器实战与面试追问

**多数据源 + 事务的三种正解：**

| 场景 | 方案 |
|------|------|
| 一写一读，读库无事务 | 读库操作不标注事务；写库事务用默认管理器 |
| 两库各自独立事务 | 每个管理器配 `@Primary` + 方法上 `transactionManager` 显式指定 |
| 两库必须同事务 | **单管理器做不到**——JTA / Seata 或改最终一致（见 [08-集成地图与常见问题](08-集成地图与常见问题.md)） |

```java
// 跨两个管理器的典型错误与修正
@Transactional                              // ❌ 默认管理器只管 orderDs
public void crossDb() {
    orderDao.update(...);                   // orderDs 事务
    reportDao.insert(...);                  // reportDs：独立连接，不在事务内！
}

@Transactional(transactionManager = "orderTxManager")
public void crossDb() { ... }               // ✅ 指定管理器后语义才明确
```

**面试追问清单：**

1. "`getTransaction` 抛 `CannotCreateTransactionException` 什么时候？"——连接获取失败（池空 / 数据库宕机）；
2. "`commit` 抛 `UnexpectedRollbackException` 的完整链？"——内圈 setRollbackOnly → 外圈 processCommit 检查 isRollbackOnly → 整体回滚；
3. "为什么实现类只写五个钩子？"——模板方法模式：传播/挂起/保存点/回滚标记全部在模板里编排，实现类只负责"资源怎么开、怎么提交、怎么回滚"；
4. "`JtaTransactionManager` 与 `DataSourceTransactionManager` 的本质区别？"——前者管多个资源（XA 两阶段提交），后者管单资源；JTA 需要事务中间件（如 Narayana）支撑。

> 🎯 **管理器专题总结**：管理器 = 契约（三方法）+ 模板（编排）+ 钩子（资源操作）；面试把这三层讲清楚，事务管理器题就是送分题。

### 5.2 管理器与连接池的联动检查

| 检查项 | 命令/指标 | 异常含义 |
|--------|----------|---------|
| 连接活跃数 | HikariCP `active` 指标 | 持续高位 = 长事务/嵌套事务 |
| 连接等待数 | `pending` 指标 | REQUIRES_NEW 滥用或池太小 |
| 事务时长 | 事务 begin→commit 间隔 | > 1s 的写事务要警惕锁竞争 |
| 回滚率 | 回滚次数 / 提交次数 | 突增 = 异常语义或数据问题 |
| 死锁计数 | 数据库 `show engine innodb status` | 加锁顺序问题 |

**三个高频联动故障：**

| 故障 | 链路 | 解法 |
|------|------|------|
| 池耗尽 | REQUIRES_NEW 循环 × 池大小 | 压缩嵌套/批量（见 [04-传播行为速查](04-传播行为速查.md) 3.1） |
| 锁超时 | 长事务 × 行锁 | 缩边界、统一加锁顺序（见 [05-隔离级别与锁速查](05-隔离级别与锁速查.md)） |
| 连接泄漏 | 事务清理异常 | 升级版本 + 检查自定义拦截器 finally 处理 |

> 💡 经验值：连接池最大连接数建议 ≥ 预估并发事务数 ×（1 + 平均嵌套层数）；监控事务时长比监控连接数更能提前暴露问题——连接数是结果，事务时长是原因。
