## 1. 默认回滚规则

```text
@Transactional 默认回滚语义（面试必背）：
  回滚：RuntimeException（非受检）及其子类、Error
  不回滚：受检异常（Exception 的子类，非 RuntimeException）
    原因：设计上认为"受检异常是可预期的业务失败"（如余额不足），
         事务应该提交已做的部分；RuntimeException 是"程序缺陷"，必须回滚。
```

| 异常类型 | 默认行为 | 举例 |
|---------|---------|------|
| RuntimeException | ✅ 回滚 | NPE、IllegalArgumentException、DataAccessException |
| Error | ✅ 回滚 | OOM、AssertionError |
| 受检 Exception | ❌ 不回滚 | IOException、SQLException（被翻译后是 Runtime，不受影响） |

> ⚠️ **头号误解**："受检异常不回滚"导致**数据半提交**——抛 IOException 时前面的 INSERT 已提交；想统一回滚就 `rollbackFor = Exception.class`（团队规范常约定此配置）。

## 2. rollbackFor / noRollbackFor 精配

```java
@Service
public class OrderService {
    @Transactional(rollbackFor = Exception.class)          // 受检也回滚
    public void create(OrderCmd cmd) throws IOException { ... }

    @Transactional(noRollbackFor = BusinessRetryableException.class)
    public void sync() { ... }                              // 业务可重试异常：提交而非回滚

    @Transactional(rollbackFor = Exception.class,
                   noRollbackFor = {NoRetryException.class, AuditFailureException.class})
    public void process() { ... }                           // 组合：全回滚但这两类除外

    // 与传播、隔离组合
    @Transactional(rollbackFor = Exception.class,
                   propagation = Propagation.REQUIRES_NEW,
                   timeout = 30)
    public void audit() { ... }
}
```

| 属性 | 语义 | 优先级 |
|------|------|--------|
| `rollbackFor` | 指定异常（含子类）触发回滚 | 最高 |
| `rollbackForClassName` | 字符串形式（避免编译期依赖） | 同上 |
| `noRollbackFor` | 指定异常（含子类）**不回滚** | 覆盖 rollbackFor |
| 匹配规则 | 按**异常类型及子类**（isAssignableFrom） | - |

> 💡 细节：匹配是按异常**类型层次**（非实例相等）——`rollbackFor = Exception.class` 涵盖全部子类；`noRollbackFor` 优先级高于 `rollbackFor`（先查 no 表再查 yes 表）。

## 3. 回滚判定源码路径

```text
异常抛出 → TransactionInterceptor → TransactionAspectSupport.completeTransactionAfterThrowing
  1. txInfo.transactionAttribute.rollbackOn(ex)      ← 查 rollbackFor/noRollbackFor
  2. 命中 → txManager.rollback(status)
        → AbstractPlatformTransactionManager.processRollback
            全局回滚：doRollback（实现类：connection.rollback()）
            或标记回滚：只 setRollbackOnly（REQUIRED 内圈场景）
  3. 未命中（不回滚）→ txManager.commit(status)
        → 仍会提交（受检异常下前面操作落库！）
```

> 🎯 **核心要点**：回滚决策在 **TransactionAttribute.rollbackOn(Throwable)** 一处——`rollbackFor`/`noRollbackFor` 编译成规则集合（`RuleBasedTransactionAttribute`）；面试答"回滚规则怎么生效"指到 `RuleBasedTransactionAttribute.rollbackOn` 即可。

## 4. 事务测试：@Transactional 测试回滚

```java
@SpringBootTest
@Transactional                            // ★ 测试方法级事务：结束自动回滚
class OrderDaoTest {

    @Autowired OrderDao orderDao;

    @Test
    void insert_and_query() {
        orderDao.insert(sample());         // 插入（在测试事务中）
        Optional<Order> found = orderDao.findById(1L);
        assertTrue(found.isPresent());
        // 测试结束：自动回滚，无数据残留
    }
}
```

| 机制 | 说明 |
|------|------|
| 测试事务 | 每个测试方法一个事务，方法结束 `rollback`（不 commit） |
| 数据隔离 | 测试数据不落库——**可重复执行** |
| 例外 | 测试内 `REQUIRES_NEW` 的代码会**真实提交**（独立事务）——审计日志类测试要注意 |
| 配合 | `@Rollback(false)` 显式提交（调试时看数据）；`@Commit` 同义 |
| 局限 | 测不到"提交后的异步行为"（afterCommit/发 MQ）——需要单独用真实提交测试 |

> ⚠️ **测试事务两大坑**：① 测 `REQUIRES_NEW`/`REQUIRES_NEW` 内操作会**真提交**——断言前先清数据；② 测试事务内查不到"未提交的并发写入"（隔离级别），并发类测试用真实数据库 + 多线程。

## 5. 保存点与部分回滚

```java
// 编程式使用保存点（NESTED 的内部机制）
// 实现：Spring 的 JdbcTransactionObjectSupport.savepoint 走 connection.setSavepoint()

txTemplate.execute(status -> {
    Object savepoint = status.createSavepoint();      // 保存点
    try {
        doDangerousPart();
    } catch (BusinessException e) {
        status.rollbackToSavepoint(savepoint);        // 只回滚这一段
    }
    status.releaseSavepoint(savepoint);               // 释放（可选）
    return continueNormalFlow();                      // 其余逻辑继续
});
```

| 保存点能力 | 说明 |
|-----------|------|
| 支持 | 数据库支持 SAVEPOINT（MySQL/PG 支持；部分老库不支持） |
| 语义 | 回滚到保存点 = 撤销该点之后的变更（事务仍存活） |
| 限制 | 连接级资源（临时表/锁）不能完全回滚 |
| 常见实现 | NESTED 传播（[04-传播行为速查](04-传播行为速查.md) 第 4 节）、批量逐条容错 |

> 🎯 **核心要点**：保存点是"事务内的书签"——回滚到书签而不是整个事务；面试答"NESTED 怎么实现部分回滚"→ 保存点；答"保存点回滚不了什么"→ 锁与临时表等连接级副作用。
