## 1. 默认回滚规则

```text
@Transactional 默认回滚语义（面试必背）：
  回滚：RuntimeException（非受检）及其子类、Error
  不回滚：受检异常（Exception 的子类，非 RuntimeException）
    原因：设计上认为"受检异常是可预期的业务失败"（如余额不足），
         事务应该提交已做的部分；RuntimeException 是"程序缺陷"，必须回滚。
```

| 异常类型 | 默认行为 | 举例 |
|---------|---------|------|
| RuntimeException | ✅ 回滚 | NPE、IllegalArgumentException、DataAccessException |
| Error | ✅ 回滚 | OOM、AssertionError |
| 受检 Exception | ❌ 不回滚 | IOException、SQLException（被翻译后是 Runtime，不受影响） |

> ⚠️ **头号误解**："受检异常不回滚"导致**数据半提交**——抛 IOException 时前面的 INSERT 已提交；想统一回滚就 `rollbackFor = Exception.class`（团队规范常约定此配置）。

### 1.1 默认规则的设计权衡

**为什么受检异常默认不回滚？** Spring 沿袭 EJB 时代的语义判断：

| 异常类别 | 语义假设 | 处理 |
|---------|---------|------|
| RuntimeException | 程序缺陷 / 不可预期 | 回滚——"代码写错了，部分数据不能留" |
| Error | JVM 级灾难 | 回滚 |
| 受检 Exception | 可预期的业务失败 | 提交——"业务说失败也正常，已完成部分保留" |

这个默认值在真实业务里的争议点：

- 支持方：余额不足（业务异常）时，前面的积分赠送、流水记录应该保留（可对账）；
- 反对方：大多数团队"要么全成要么全败"的心智更简单，受检异常也被期望回滚。

**落地建议**：团队规范统一 `rollbackFor = Exception.class`（全回滚语义），再把"确实要提交"的异常用 `noRollbackFor` 显式豁免——显式优于隐式，语义在代码里看得见。

> ⚠️ **半提交事故示例**：`createOrder()` 中 insert 订单成功 → 调外部接口抛 IOException（受检）→ 默认提交 → 订单已入库但外部没处理——这就是"受检异常不回滚"的真实代价；用 rollbackFor=Exception 后该场景自动回滚。

### 1.2 回滚规则速记

| 声明 | 回滚范围 | 记忆 |
|------|---------|------|
| （不写） | RuntimeException + Error | 默认行为 |
| `rollbackFor = Exception.class` | 全部 Exception + Error（Error 本就回滚） | 团队标配 |
| `rollbackFor = {A.class, B.class}` | A/B 及其子类 | 并集匹配 |
| `noRollbackFor = X.class` | 默认回滚中排除 X | 显式豁免 |
| `rollbackFor = Exception.class, noRollbackFor = X.class` | 全回滚但 X 提交 | 全量 + 白名单 |

```java
// 幂等重试异常豁免示例：重试型业务异常不回滚（由上层重试）
@Transactional(rollbackFor = Exception.class,
               noRollbackFor = RetryableBusinessException.class)
public void syncPayment() { ... }
```

> 🎯 **记忆口诀**："默认滚运行时，全滚靠 Exception，豁免靠 noRollbackFor"——配置顺序永远"先声明全滚，再豁免特例"，语义最清晰。

## 2. rollbackFor / noRollbackFor 精配

```java
@Service
public class OrderService {
    @Transactional(rollbackFor = Exception.class)          // 受检也回滚
    public void create(OrderCmd cmd) throws IOException { ... }

    @Transactional(noRollbackFor = BusinessRetryableException.class)
    public void sync() { ... }                              // 业务可重试异常：提交而非回滚

    @Transactional(rollbackFor = Exception.class,
                   noRollbackFor = {NoRetryException.class, AuditFailureException.class})
    public void process() { ... }                           // 组合：全回滚但这两类除外

    // 与传播、隔离组合
    @Transactional(rollbackFor = Exception.class,
                   propagation = Propagation.REQUIRES_NEW,
                   timeout = 30)
    public void audit() { ... }
}
```

| 属性 | 语义 | 优先级 |
|------|------|--------|
| `rollbackFor` | 指定异常（含子类）触发回滚 | 最高 |
| `rollbackForClassName` | 字符串形式（避免编译期依赖） | 同上 |
| `noRollbackFor` | 指定异常（含子类）**不回滚** | 覆盖 rollbackFor |
| 匹配规则 | 按**异常类型及子类**（isAssignableFrom） | - |

> 💡 细节：匹配是按异常**类型层次**（非实例相等）——`rollbackFor = Exception.class` 涵盖全部子类；`noRollbackFor` 优先级高于 `rollbackFor`（先查 no 表再查 yes 表）。

### 2.1 匹配规则源码细节

```text
RuleBasedTransactionAttribute.rollbackOn(Throwable ex) 的判定逻辑：
  ① 遍历 noRollbackRules（noRollbackFor 编译产物）
      命中（ex 是其子类/实现）→ 返回 false（不回滚）    ← no 表优先
  ② 遍历 rollbackRules（rollbackFor 编译产物）
      命中 → 返回 true（回滚）
  ③ 都未命中 → 回退默认：RuntimeException/Error 回滚，否则提交
```

| 边界情况 | 行为 |
|---------|------|
| `rollbackFor = Exception.class` | 匹配所有 Exception 子类；**不含 Error**（Error 非 Exception 子类，但 Error 本就默认回滚） |
| `noRollbackFor = RuntimeException.class` | 所有运行时异常都不回滚——极端配置，慎用 |
| 多个 rollbackFor | 并集匹配（任一命中即回滚） |
| 接口/父类方法继承 | 注解属性不继承，各方法独立配置 |
| 异常的 cause 链 | 只按**抛出的最外层异常**匹配（不看 cause）——包装异常时注意 |

> 🎯 **面试得分点**：答"rollbackFor 匹配是 `isAssignableFrom` 类型层次判断，no 表先于 yes 表"——比"按异常实例判断"高一个层次；源码锚点 `RuleBasedTransactionAttribute.rollbackOn`。

### 2.2 回滚规则与传播的交互

| 传播 × 回滚规则 | 行为 | 注意 |
|----------------|------|------|
| REQUIRED + rollbackFor=Exception | 内圈受检异常也标记外层 | 标记后外圈无法挽救 |
| REQUIRES_NEW + rollbackFor=Exception | 内圈独立回滚，外圈无感 | 审计失败不影响主流程 ✅ |
| NESTED + noRollbackFor=X | X 异常不回滚到保存点（随外层提交） | 豁免异常会"带病提交"到外层 |
| MANDATORY + 默认规则 | 加入者规则由外层统一 | 内层属性只影响自己的判定 |

```java
// 经典组合：审计必须独立且全回滚；主流程宽松
@Transactional(propagation = Propagation.REQUIRES_NEW,
               rollbackFor = Exception.class)
public void audit(String op, String detail) { ... }

@Transactional
public void business() { ... }   // 默认规则：运行时异常回滚
```

> 💡 **组合思路**：回滚规则是"异常 → 动作"的映射，传播是"动作作用于哪个事务"——两者正交组合；先定传播（谁负责），再定规则（什么异常触发），顺序别反。

## 3. 回滚判定源码路径

```text
异常抛出 → TransactionInterceptor → TransactionAspectSupport.completeTransactionAfterThrowing
  1. txInfo.transactionAttribute.rollbackOn(ex)      ← 查 rollbackFor/noRollbackFor
  2. 命中 → txManager.rollback(status)
        → AbstractPlatformTransactionManager.processRollback
            全局回滚：doRollback（实现类：connection.rollback()）
            或标记回滚：只 setRollbackOnly（REQUIRED 内圈场景）
  3. 未命中（不回滚）→ txManager.commit(status)
        → 仍会提交（受检异常下前面操作落库！）
```

> 🎯 **核心要点**：回滚决策在 **TransactionAttribute.rollbackOn(Throwable)** 一处——`rollbackFor`/`noRollbackFor` 编译成规则集合（`RuleBasedTransactionAttribute`）；面试答"回滚规则怎么生效"指到 `RuleBasedTransactionAttribute.rollbackOn` 即可。

### 3.1 rollbackOnly 机制深入

```text
rollbackOnly 的完整链路（REQUIRED 嵌套场景）：
  内圈抛异常 → 内圈 TransactionAspectSupport 调 txManager.rollback(status)
    → AbstractPlatformTransactionManager.processRollback
        → 非新事务 → 不实际回滚，仅 status.setRollbackOnly()   ← 关键
  外圈正常返回 → completeTransactionAfterReturning → commit
    → processCommit 检查 isRollbackOnly → 抛 UnexpectedRollbackException
    → 整体回滚（事务最终一致）
```

| 传播 | 内圈失败时 | 外圈可见性 |
|------|-----------|-----------|
| REQUIRED | 标记 rollbackOnly | 提交时炸（UnexpectedRollbackException） |
| NESTED | 回滚到保存点（不标记外层） | 外圈正常提交 |
| REQUIRES_NEW | 独立回滚 | 外圈无感知 |

> 💡 **为什么设计成"延迟炸"**：内圈只标记、不立即回滚，是为了保留外圈"继续写"的机会（虽然最终仍回滚）——框架无法预知外圈是否还有补救逻辑；UnexpectedRollbackException 就是"判决书"：事务结局已定，通知调用方（如需捕获需在**最外层** catch）。

### 3.2 回滚路径的两个分支：全局回滚 vs 标记回滚

| 分支 | 触发条件 | 动作 | 典型场景 |
|------|---------|------|---------|
| 全局回滚 | 新事务 + 回滚判定命中 | `doRollback` 真正回滚 | 最外层失败 |
| 标记回滚 | 非新事务 + 回滚判定命中 | 仅 setRollbackOnly | REQUIRED 内圈失败 |
| 保存点回滚 | NESTED + 内圈失败 | `rollbackToSavepoint` | 批量逐条容错 |
| 提交路径 | 回滚判定未命中 | 正常 commit | 受检异常被豁免 |

```java
// 捕获 UnexpectedRollbackException 的正确位置：最外层调用方
try {
    outerService.outer();                    // 内圈失败被吞 → 提交时炸
} catch (UnexpectedRollbackException e) {
    // 事务已整体回滚：按业务语义处理（补偿 / 重试 / 告警）
    compensate(e);
}
```

> 🎯 **面试必答**："回滚有几条路径？"——**全局回滚、标记回滚、保存点回滚**三条 + 提交豁免一条；把每条路径的触发条件讲清，回滚机制题即满分。

## 4. 事务测试：@Transactional 测试回滚

```java
@SpringBootTest
@Transactional                            // ★ 测试方法级事务：结束自动回滚
class OrderDaoTest {

    @Autowired OrderDao orderDao;

    @Test
    void insert_and_query() {
        orderDao.insert(sample());         // 插入（在测试事务中）
        Optional<Order> found = orderDao.findById(1L);
        assertTrue(found.isPresent());
        // 测试结束：自动回滚，无数据残留
    }
}
```

| 机制 | 说明 |
|------|------|
| 测试事务 | 每个测试方法一个事务，方法结束 `rollback`（不 commit） |
| 数据隔离 | 测试数据不落库——**可重复执行** |
| 例外 | 测试内 `REQUIRES_NEW` 的代码会**真实提交**（独立事务）——审计日志类测试要注意 |
| 配合 | `@Rollback(false)` 显式提交（调试时看数据）；`@Commit` 同义 |
| 局限 | 测不到"提交后的异步行为"（afterCommit/发 MQ）——需要单独用真实提交测试 |

> ⚠️ **测试事务两大坑**：① 测 `REQUIRES_NEW`/`REQUIRES_NEW` 内操作会**真提交**——断言前先清数据；② 测试事务内查不到"未提交的并发写入"（隔离级别），并发类测试用真实数据库 + 多线程。

### 4.1 事务测试进阶

```java
// 进阶一：数据准备 + 事务回滚 + 提交后行为分离
@SpringBootTest
class OrderTxTest {

    @Autowired OrderService orderService;
    @Autowired OrderDao orderDao;

    @Test
    @Sql(statements = "INSERT INTO t_order(id, status) VALUES (100, 'NEW')")  // 同事务内准备
    void create_should_persist() {
        orderService.create(orderCmd(100));
        Order found = orderDao.findById(100).orElseThrow();
        assertEquals("PAID", found.status());
        // 方法结束自动回滚——@Sql 准备的数据也不残留
    }

    @Test
    @Rollback(false)   // 调试用：真实提交，跑完自行清理
    void debug_persist() { ... }
}

// 进阶二：验证 REQUIRES_NEW 真实提交的行为
@SpringBootTest
class AuditTxTest {
    @Test
    void audit_should_survive_outer_rollback() {
        assertThrows(RuntimeException.class, () -> orderService.createFail());
        // 外圈回滚了，但 REQUIRES_NEW 审计已落库 → 断言后手动清理
        assertEquals(1, auditDao.count(cmd.id()));
        auditDao.deleteByCmd(cmd.id());   // 手动清理
    }
}
```

| 测试要点 | 做法 |
|---------|------|
| 准备数据 | `@Sql`（同事务）/ `@BeforeEach` 手插 |
| 断言回滚 | 事务测试内查不到其他连接未提交的数据 |
| REQUIRES_NEW 残留 | 断言后手动清理（或 `@Sql` 清理脚本） |
| 并发类测试 | 脱离测试事务：真实数据库 + CountDownLatch + 多线程 |
| 提交后钩子验证 | 单独 `@Rollback(false)` 测试 + 消息断言（EmbeddedBroker / MockMvc） |

> ⚠️ **测试事务三原则**：① 断言只读数据；② REQUIRES_NEW 内容主动清理；③ 异步/并发行为另起真实测试——把"测试事务自动回滚"当默认但别当万能。

### 4.2 测试事务的边界情形

| 边界情形 | 行为 | 处理 |
|---------|------|------|
| 测试方法内调用 `@Async` | 异步线程不在测试事务内 | 异步任务自开事务/等待完成再断言 |
| 测试内查 H2 内存库 | 同事务内可见 | H2 模拟 MySQL 模式（MODE=MySQL） |
| 测试类级 `@Transactional` + 方法级 `@Rollback(false)` | 方法级真实提交 | 提交数据需在 `@AfterEach` 清理 |
| `@Sql` 与测试事务关系 | `@Sql` 在同一事务内执行（默认） | 回滚同样覆盖 |
| Mock 的 Service 调用 | Mock 不走代理 | 事务测试别 mock 目标服务本身 |

```java
// @Sql 与 REQUIRES_NEW 残留的清理组合
@SpringBootTest
class AuditTxTest {
    @Test
    @Sql(statements = "DELETE FROM t_audit WHERE cmd_id = 100")   // 前置清理
    void audit_should_survive() {
        assertThrows(RuntimeException.class, () -> orderService.createFail(100));
        assertEquals(1, auditDao.countByCmd(100));    // REQUIRES_NEW 已真提交
    }
}
```

> 💡 **测试设计建议**：事务测试专注于"回滚语义"验证；提交后行为（消息/事件）单独用 `@Rollback(false)` + 观察者断言——两类测试职责分离，互不干扰。

## 5. 保存点与部分回滚

```java
// 编程式使用保存点（NESTED 的内部机制）
// 实现：Spring 的 JdbcTransactionObjectSupport.savepoint 走 connection.setSavepoint()

txTemplate.execute(status -> {
    Object savepoint = status.createSavepoint();      // 保存点
    try {
        doDangerousPart();
    } catch (BusinessException e) {
        status.rollbackToSavepoint(savepoint);        // 只回滚这一段
    }
    status.releaseSavepoint(savepoint);               // 释放（可选）
    return continueNormalFlow();                      // 其余逻辑继续
});
```

| 保存点能力 | 说明 |
|-----------|------|
| 支持 | 数据库支持 SAVEPOINT（MySQL/PG 支持；部分老库不支持） |
| 语义 | 回滚到保存点 = 撤销该点之后的变更（事务仍存活） |
| 限制 | 连接级资源（临时表/锁）不能完全回滚 |
| 常见实现 | NESTED 传播（[04-传播行为速查](04-传播行为速查.md) 第 4 节）、批量逐条容错 |

> 🎯 **核心要点**：保存点是"事务内的书签"——回滚到书签而不是整个事务；面试答"NESTED 怎么实现部分回滚"→ 保存点；答"保存点回滚不了什么"→ 锁与临时表等连接级副作用。

### 5.1 保存点边界与面试追问

**保存点回滚不了什么：**

| 副作用 | 说明 |
|--------|------|
| 锁 | 事务级锁不因保存点释放（锁归事务管） |
| 临时表 / 临时资源 | 连接级资源不受保存点控制 |
| 已提交的 REQUIRES_NEW | 保存点管不到其他事务 |
| 自增 ID 消耗 | 回滚不回收 AUTO_INCREMENT |

**面试追问：**

1. "NESTED 与保存点的源码关系？"——`handleExistingTransaction` 中 NESTED 分支调 `createSavepoint`；JPA 无保存点能力时回退 REQUIRED 参与语义；
2. "保存点能跨连接吗？"——不能，保存点是连接级能力（一个连接一个保存点序列）；
3. "保存点数量有限制吗？"——数据库有（MySQL 未明确上限，但每保存点有开销），批量逐行保存点注意数量级；
4. "REQUIRED 内圈能不能用保存点做部分回滚？"——不能，REQUIRED 不创建保存点；要部分回滚必须声明 NESTED；
5. "保存点与 REQUIRES_NEW 在测试里怎么区分？"——NESTED 随外圈一起回滚（测试事务内不残留），REQUIRES_NEW 真提交（测试断言后需清理）。

> 🎯 **总结一句**：保存点 = "事务内的书签"，回滚到书签而非终点；锁、临时表等连接级副作用回滚不掉——面试答到这一层即为满分。

### 5.2 回滚机制生产实践清单

| 实践 | 做法 |
|------|------|
| 统一回滚策略 | 写方法 `rollbackFor = Exception.class`，豁免用 `noRollbackFor` |
| 异常不吞 | 事务方法内 catch 必须"重新抛出 或 setRollbackOnly" |
| 保存点容量 | NESTED 循环内控制单事务行数（如每 500 行分批） |
| 测试兜底 | 每个事务方法配"抛异常断言回滚"的测试 |
| 监控 | 回滚率指标 + UnexpectedRollbackException 告警 |
| 日志 | 回滚时打印异常与业务上下文（方便对账） |

> 💡 **回滚率是健康指标**：正常情况下回滚率 < 1%；突增通常意味着：① 异常语义错乱（该回滚没回滚的镜像问题）；② 校验前置不足（事务内频繁失败）；③ 并发冲突上升（锁/版本问题）——按这三类排查即可。

### 5.3 回滚相关面试一问一答

1. "默认回滚规则为什么是运行时异常？"——设计假设：受检异常是可预期的业务失败（可提交），运行时异常是程序缺陷（必回滚）——答完默认规则再答这个"为什么"，层次立即拉开；
2. "catch 住异常后如何保证回滚？"——重新抛出（推荐）或 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`；
3. "UnexpectedRollbackException 在哪一层捕获？"——最外层调用方（内层捕获无意义，事务结局已定）；
4. "测试里断言回滚的三种写法？"——查库断言无数据、`assertThrows` 配合回滚日志、`@Rollback(false)` 反向验证；
5. "保存点与 rollbackOnly 标记能混用吗？"——能：NESTED 内圈先回滚到保存点（若内圈回滚判定命中且是保存点事务），冒泡的异常才标记外层——理解顺序："先保存点自救，后外层标记"。

> 🎯 **回滚机制收尾**：默认规则（是什么）→ 精配规则（怎么配）→ 判定源码（怎么判）→ rollbackOnly（怎么传）→ 测试（怎么验）——五步闭环，07 篇即为"回滚"专题的完整答案。
