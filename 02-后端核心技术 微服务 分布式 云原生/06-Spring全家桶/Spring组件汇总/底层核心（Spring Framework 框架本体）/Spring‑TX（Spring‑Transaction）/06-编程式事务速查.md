## 1. 编程式 vs 声明式

| 维度 | @Transactional（声明式） | TransactionTemplate（编程式） |
|------|------------------------|------------------------------|
| 声明位置 | 方法级（AOP 织入） | 代码块内显式调用 |
| 粒度 | 整个方法 | **任意代码段**（可事务可非事务混合） |
| 自调用 | ❌ 失效 | ✅ 无代理依赖，直接可用 |
| 动态传播 | 编译期固定 | 运行时变量/循环内可控 |
| 事务内决策 | 被动（异常冒泡） | 主动（setRollbackOnly/返回值控制） |
| 可读性 | 高（一行注解） | 中（模板包裹） |
| 适用 | 90% 场景 | 自调用、循环、工具类、复杂流程 |

> 🎯 **核心要点**：声明式是"方法级事务"的语法糖；编程式是"任意代码块级事务"的底层能力——**自调用失效问题的最稳解法不是注入代理，而是 TransactionTemplate**（工具类/监听器场景尤甚）。

## 2. TransactionTemplate 基础用法

```java
@Component
public class AuditService {
    private final TransactionTemplate txTemplate;

    public AuditService(PlatformTransactionManager txManager) {
        this.txTemplate = new TransactionTemplate(txManager);   // 注入管理器构建
        // 可预置默认属性
        this.txTemplate.setPropagationBehavior(
                TransactionDefinition.PROPAGATION_REQUIRES_NEW);
        this.txTemplate.setTimeout(10);
    }

    // 有返回值
    public AuditLog saveAndReturn(AuditCmd cmd) {
        return txTemplate.execute(status -> {
            auditDao.insert(cmd);
            return auditDao.findById(cmd.id());        // 事务内查询返回
        });
    }

    // 无返回值
    public void saveOnly(AuditCmd cmd) {
        txTemplate.executeWithoutResult(status -> {
            auditDao.insert(cmd);                       // 异常自动回滚
        });
    }
}
```

| 方法 | 语义 |
|------|------|
| `execute(TransactionCallback<T>)` | 返回结果；回调抛异常 → 回滚并向外抛 |
| `executeWithoutResult(Consumer<TransactionStatus>)` | 无返回；lambda 抛异常 → 回滚 |
| 回调内 `status.setRollbackOnly()` | 主动标记回滚（不抛异常也回滚） |

> ⚠️ **模板是线程安全的**：`TransactionTemplate` 本身可共享（属性不可变后再暴露）；不要在回调里改模板属性——每线程用局部配置时新建模板。

### 2.1 TransactionTemplate 内部执行流程

```text
TransactionTemplate.execute(callback)
  ├── 1. 复制属性 → 构造 DefaultTransactionDefinition（每次执行独立）
  ├── 2. txManager.getTransaction(definition)         → 开启/加入（同声明式）
  ├── 3. try { 回调执行 }
  │        ├── 正常 → txManager.commit(status)
  │        └── 抛运行时异常 → txManager.rollback(status) 后重新抛出
  │        └── 抛受检异常 → 提交并向外抛（与 @Transactional 默认一致）
  └── 4. finally：清理（管理器内部完成连接归还）
```

| 细节 | 说明 |
|------|------|
| 与声明式同源 | 内部走同一个 `AbstractPlatformTransactionManager` 模板——语义完全一致 |
| 受检异常 | 回调抛受检异常 → **提交**并向外抛（要回滚需包成 RuntimeException） |
| 每次 execute | 属性从模板复制——并发下各执行互不影响（线程安全的基础） |

> 🎯 **核心结论**：TransactionTemplate 与 @Transactional 是**同一个引擎的两个方向盘**——模板默认也是"受检异常提交、运行时异常回滚"，别以为编程式天然全回滚（回滚规则见 [07-回滚机制与测试速查](07-回滚机制与测试速查.md)）。

### 2.2 TransactionTemplate 的配置细节

| 配置方法 | 语义 | 对应 @Transactional 属性 |
|---------|------|------------------------|
| `setPropagationBehavior` | 传播行为（默认 REQUIRED） | `propagation` |
| `setIsolationLevel` | 隔离级别（默认数据库默认） | `isolation` |
| `setTimeout` | 超时秒数（默认 -1） | `timeout` |
| `setReadOnly` | 只读提示 | `readOnly` |
| `setName` | 事务名称（日志/监控用） | 无（label 可近似） |

```java
// 自定义回滚规则：模板 + 规则（等价 rollbackFor）
@Bean
public TransactionTemplate auditTemplate(PlatformTransactionManager tm) {
    TransactionTemplate tt = new TransactionTemplate(tm);
    tt.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRES_NEW);
    tt.setTimeout(10);
    // 回滚规则：所有 Exception 都回滚（等价 rollbackFor = Exception.class）
    tt.setRollbackOn(ex -> ex instanceof RuntimeException || ex instanceof IOException);
    return tt;
}
```

> 💡 **模板与注解的属性差异**：模板的 `setRollbackOn` 是函数式规则（`TransactionTemplate#setRollbackOn(Predicate<Throwable>)`），比注解更灵活——支持按异常内容/类型任意判定；其余属性与注解一一对应。

## 3. TransactionOperations：接口化编程式事务

```java
// 面向接口编程：容器注入 TransactionOperations（默认实现即 TransactionTemplate）
@Service
public class BatchService {
    private final TransactionOperations txOps;      // 注入接口，测试时好替换

    public BatchService(TransactionOperations txOps) { this.txOps = txOps; }

    public void importAll(List<Row> rows) {
        for (Row row : rows) {
            txOps.executeWithoutResult(status -> importOne(row));  // 逐行事务
        }
    }
}
```

> 💡 `TransactionOperations` 是 6.x 引入的接口抽象（默认 Bean 由 Boot 提供）——好处是测试可 mock、实现可替换；Spring 官方推荐"编程式事务面向 TransactionOperations 编程"。

### 3.1 接口化与测试替换

```java
// 生产实现注入的是接口，测试可换假实现
@Service
public class PayoutService {
    private final TransactionOperations txOps;

    public PayoutService(TransactionOperations txOps) { this.txOps = txOps; }

    public void pay(PayCmd cmd) {
        txOps.executeWithoutResult(status -> {
            payoutDao.insert(cmd);
            notifyClient(cmd);           // 事务内副作用——测试时可观察
        });
    }
}

// 测试：替换为"假事务"验证回调逻辑（不碰数据库）
@Test
void pay_should_insert() {
    TransactionOperations fake = new TransactionTemplate(noopManager);
    PayoutService svc = new PayoutService(fake);
    svc.pay(cmd);
    verify(payoutDao).insert(cmd);       // 验证回调内逻辑
}
```

| 收益 | 说明 |
|------|------|
| 测试友好 | 事务边界逻辑可单测（回调内容与事务机制解耦） |
| 实现可换 | 缓存型事务 / 自研实现可无缝替换 |
| 语义稳定 | 接口语义 6.x 起冻结，升级零迁移 |

> 💡 **官方立场**：Spring 文档推荐"编程式事务优先注入 `TransactionOperations`"——接口抽象是 6.x 的编程式最佳实践（Boot 自动装配默认提供 TransactionTemplate 实例）。

### 3.2 编程式与声明式的混用规则

| 混用组合 | 行为 | 注意 |
|---------|------|------|
| 声明式方法内用模板 | 模板默认 REQUIRED → **加入外层事务** | 想要独立需显式 REQUIRES_NEW |
| 模板回调内调声明式方法 | 方法走代理 → 按传播加入/新开 | 自调用陷阱依然存在（回调内 this 调用） |
| 模板内用同步钩子 | afterCommit 等照常生效 | 与声明式事件行为一致 |
| 工具类 + 容器服务 | 模板自己开事务，服务方法无代理 | 工具类场景唯一正解 |

```java
// 混用示例：声明式外层 + 编程式内层独立提交
@Service
public class OrderService {
    private final TransactionOperations txOps;   // 默认 REQUIRED

    @Transactional
    public void createWithAudit(OrderCmd cmd) {
        orderDao.insert(cmd);                    // 外层事务
        txOps.executeWithoutResult(status -> {   // REQUIRED → 加入外层
            auditDao.insert(cmd.audit());
        });                                      // 提交点仍是外层
    }
}
```

> 🎯 **混用核心规则**：**两者共享同一线程的事务上下文**——模板的默认传播（REQUIRED）会加入声明式已开的事务；"独立"必须显式声明，这是混用时唯一的规则。

### 3.3 TransactionOperations 接口速览

```java
public interface TransactionOperations {
    <T> T execute(TransactionCallback<T> action);                        // 有返回
    void executeWithoutResult(Consumer<TransactionStatus> action);       // 无返回
}
```

| 方法 | 特点 | 适用 |
|------|------|------|
| `execute` | 返回业务结果；回调内可 setRollbackOnly | 需要返回值的事务块 |
| `executeWithoutResult` | 无返回值；lambda 内操作 | 纯写操作事务块 |
| 受检异常 | 回调内需自行包装（模板不吞异常） | 异常策略同声明式默认 |

> 💡 **接口与实现的关系**：`TransactionTemplate` 是唯一官方实现；接口化的价值不在多实现，而在**测试替身与语义隔离**——注入接口 = 声明"我只依赖事务能力，不依赖具体实现"。

## 4. 事务回调与状态控制

```java
txTemplate.execute(status -> {
    // ① 主动回滚：不抛异常
    if (!validate(cmd)) {
        status.setRollbackOnly();
        return null;
    }
    // ② 事务内条件分支：REQUIRES_NEW 动态决定
    if (cmd.forceAudit()) {
        txTemplate.executeWithoutResult(s -> auditDao.insert(cmd));  // 内层新事务
    }
    // ③ 事务同步钩子：提交后发事件
    TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    eventPublisher.publishEvent(new OrderCreated(cmd.id()));
                }
            });
    return doBusiness(cmd);
});
```

> 🎯 **核心要点**：编程式事务的"状态控制"是声明式做不到的——`setRollbackOnly` 精确回滚、`registerSynchronization` 的 afterCommit 钩子（"事务提交成功才发 MQ/事件"的经典实现，见 [Spring-Context-05](../Spring‑Context/05-事件驱动机制速查.md) 事务事件原理）。

### 4.1 回调边界与嵌套事务

```java
// 嵌套模板：内层 REQUIRES_NEW 与外层模板混用
txTemplate.executeWithoutResult(outer -> {
    orderDao.insert(cmd);                        // 外层事务
    if (cmd.needAudit()) {
        auditTemplate.executeWithoutResult(inner -> {   // 内层独立事务
            auditDao.insert(cmd.audit());
        });                                      // 内层立即提交
    }
    // 外层回滚不影响已提交的审计记录
});
```

| 边界 | 行为 |
|------|------|
| 回调内抛异常 | 回滚当前事务（模板感知的运行时异常） |
| 回调内捕获异常不抛 | 事务照常提交——"想回滚必须让异常冒泡或 setRollbackOnly" |
| 嵌套模板 | 内层独立传播（默认 REQUIRED 则加入外层！要独立需设 REQUIRES_NEW） |
| 事务内发事件 | 配合 afterCommit 钩子（见第 4 节示例） |

> ⚠️ **易错点**：内层模板若忘了设传播行为，默认 REQUIRED **加入外层**——"我以为开了新事务"是模板嵌套最常见的认知偏差；显式 `new TransactionTemplate(txManager, TransactionDefinition.PROPAGATION_REQUIRES_NEW)` 更清晰。

### 4.2 状态控制的完整边界

| 控制动作 | 效果 | 注意 |
|---------|------|------|
| `status.setRollbackOnly()` | 当前事务标记回滚（提交时生效） | 内圈标记 → 外圈 UnexpectedRollbackException |
| 抛异常（不捕获） | 模板自动回滚并重抛 | 最常用 |
| 捕获异常 + setRollbackOnly | 不抛异常但回滚 | "校验失败不打扰调用方"场景 |
| 返回 null | 正常提交（默认语义） | 别拿 null 当"回滚信号"——要回滚必须显式标记 |

```java
// 边界示例：校验失败 → 回滚但不抛异常
public boolean tryImport(ImportCmd cmd) {
    return txTemplate.execute(status -> {
        if (!validate(cmd)) {
            status.setRollbackOnly();      // 回滚已执行的 SQL
            return false;                  // 调用方拿到 false，不抛异常
        }
        importDao.insert(cmd);
        return true;
    });
}
```

> 🎯 **状态控制三问**：回滚吗？（setRollbackOnly / 抛异常）提交吗？（正常返回）通知谁？（返回值 / 异常）——编程式把这三个决定权全部交到代码手里，这就是它比声明式"主动"的原因。

### 4.3 回调内异常处理的三种姿势

| 姿势 | 代码 | 事务结果 |
|------|------|---------|
| 直接抛出 | `throw new BizException(...)` | 自动回滚 + 异常外抛 ✅ |
| 捕获后标记 | `catch (e) { status.setRollbackOnly(); log.warn(...); }` | 回滚但不外抛 |
| 捕获后忽略 | `catch (e) { log.warn(...); }` | **提交**（最危险） |

```java
// 姿势二实战：降级场景——失败回滚但返回降级结果
public boolean createWithDegrade(OrderCmd cmd) {
    return txTemplate.execute(status -> {
        try {
            orderDao.insert(cmd);
            return true;
        } catch (DataAccessException e) {
            status.setRollbackOnly();        // 回滚
            degradeRecorder.record(cmd);     // 降级记录（在事务内，会一起回滚！）
            return false;                    // 或把降级记录放到事务外
        }
    });
}
```

> ⚠️ **降级陷阱**：事务内写的"降级记录"会随 setRollbackOnly 一起回滚——要持久化降级信息必须用 REQUIRES_NEW 或移出事务块；"我想回滚业务但保留日志"是编程式里最常见的需求，解法只有独立事务。

## 5. TransactionalOperator：响应式事务

```java
// 响应式事务（R2DBC / Reactive Mongo 场景）
@Service
public class ReactiveOrderService {
    private final TransactionalOperator txOperator;   // Boot 自动装配

    public Mono<Void> create(OrderCmd cmd) {
        Mono<Void> work = orderRepository.insert(cmd)
                .then(accountRepository.debit(cmd.userId(), cmd.amount()));
        return txOperator.transactional(work);        // 订阅执行包进事务
    }
}
```

| 要点 | 说明 |
|------|------|
| 实现 | `TransactionalOperator`（reactive 包）+ `ReactiveTransactionManager` |
| 执行时机 | **订阅时**才开事务（不是构建时） |
| 错误处理 | Mono/Flux error → 自动回滚 |
| 混用禁止 | 阻塞式与响应式事务资源不能混在同一事务 |
| 管理器 | `R2dbcTransactionManager`（spring-r2dbc）/ `ReactiveMongoTransactionManager` |

> ⚠️ **响应式大坑**：响应式事务依赖**订阅线程传播上下文**——`block()` 混用或跨线程切换订阅器会丢事务；7.x 下响应式事务保持稳定语义（REQUIRED 等传播同样支持）。

### 5.1 响应式事务边界

| 边界 | 说明 |
|------|------|
| 传播支持 | REQUIRED / REQUIRES_NEW 等语义同样可用（`TransactionalOperator` 构造时配置） |
| 隔离级别 | 由响应式驱动支持（R2DBC 部分能力） |
| 超时 | `operator.transactional(work, timeout)` 可配 |
| 挂起 | 响应式无"挂起"概念——嵌套靠操作符组合 |

```java
// 传播配置：operator 每次事务的默认属性
TransactionalOperator operator =
        TransactionalOperator.create(txManager,
                new DefaultTransactionDefinition(
                        TransactionDefinition.PROPAGATION_REQUIRES_NEW));

Flux<Order> result = operator.transactional(orderRepository.findAll());  // 元素级事务
```

> ⚠️ **响应式 + 阻塞混用的红线**：`Mono.block()` 或 `Thread.sleep` 混入响应式事务——线程上下文丢失 + 阻塞事件循环；要么全响应式，要么全阻塞，**桥接层单独开事务**。

### 5.2 响应式事务适用场景与陷阱

| 场景 | 推荐 | 说明 |
|------|------|------|
| 全响应式服务（R2DBC） | `TransactionalOperator` | 订阅时开事务，语义与阻塞版一致 |
| 响应式入口 + 阻塞 DAO | ❌ 禁止混用 | 桥接层拆开，各自事务 |
| WebFlux + Mongo Reactive | `ReactiveMongoTransactionManager` | 无 SQL 锁概念，冲突靠重试 |
| 与事务事件配合 | 支持（响应式同步器） | `TransactionalEventListener` 同样可用 |

**常见陷阱：**

| 陷阱 | 表现 | 解法 |
|------|------|------|
| block() 混用 | 事务上下文丢失 | 全链路响应式 |
| 订阅器切换线程 | 连接跨线程 | `publishOn` 在事务操作符之外 |
| 长流逐元素事务 | 每元素一个事务（开销大） | 批量聚合后再 transactional |
| 错误类型 | 非事务错误也回滚 | 区分业务错误与事务错误处理链 |

> 🎯 **一句话**：响应式事务 = 同一套传播语义 + 订阅时开启 + 线程上下文敏感——"订阅即边界"，理解这条就抓住了与阻塞版的全部差异。

## 6. 编程式事务适用场景

| 场景 | 为什么用编程式 |
|------|--------------|
| 同类自调用需要事务 | @Transactional 失效，模板直接可用 |
| 循环内逐条事务 | 方法级注解做不到"每条一事务" |
| 监听器/定时任务 | 方法常被内部调用，代理不可靠 |
| 动态传播决策 | 传播行为由运行时条件决定 |
| 测试工具/脚本 | 快速包裹任意代码段 |
| 大流程局部事务 | 只有中间一段需要事务 |

> 🎯 **核心要点**：编程式与声明式是**同一套管理器 + 同步机制**的两个入口——混用安全（模板内外同事务）；选型标准：**方法级固定语义 → 声明式；代码块级/动态/自调用 → 编程式**。

### 6.1 编程式场景扩展与面试追问

| 场景 | 代码形态 |
|------|---------|
| 工具类（static 方法内） | 注入管理器后 `new TransactionTemplate(tx)` 局部使用 |
| 监听器内回调 | 模板包裹 `onMessage` 全段 |
| 批量任务逐条 | 循环内 `executeWithoutResult` |
| 动态传播 | 按条件 `template.setPropagationBehavior(...)`（每次 execute 前设置，线程安全） |
| 测试脚本 | 临时包裹任意代码段验证 SQL 行为 |

**面试追问：**

1. "编程式和声明式性能有差别吗？"——无本质差别（同引擎）；声明式多一层代理调用，可忽略；
2. "模板回调里能拿到事务状态吗？"——能，回调参数 TransactionStatus 可直接 setRollbackOnly；
3. "模板能脱离 Spring 容器用吗？"——能，new 出来 + 传入管理器即可（管理器本身通常需要容器）；
4. "声明式和编程式混用同一线程？"——安全，共享同一线程绑定资源——模板内调用 @Transactional 方法 = 加入同一事务（传播按默认 REQUIRED）；
5. "为什么自调用场景编程式是唯一正解？"——声明式依赖代理，自调用绕过代理；模板无代理依赖，直接包代码块——原理即"谁在开事务"（模板自己开）。

> 🎯 **选型总结**：90% 用声明式（可读性）；自调用/循环/动态传播/测试 10% 用编程式；两者是同一引擎的两个入口，理解引擎（[02-事务管理器速查](02-事务管理器速查.md)）即可无痛切换。
