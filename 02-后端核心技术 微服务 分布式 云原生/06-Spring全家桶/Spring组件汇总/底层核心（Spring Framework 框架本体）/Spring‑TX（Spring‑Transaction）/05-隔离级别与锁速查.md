## 1. 隔离级别全表

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | Spring 常量 |
|---------|:---:|:---:|:---:|------------|
| READ_UNCOMMITTED | 可能 | 可能 | 可能 | `Isolation.READ_UNCOMMITTED` |
| READ_COMMITTED | 避免 | 可能 | 可能 | `Isolation.READ_COMMITTED` |
| REPEATABLE_READ | 避免 | 避免 | 可能* | `Isolation.REPEATABLE_READ` |
| SERIALIZABLE | 避免 | 避免 | 避免 | `Isolation.SERIALIZABLE` |
| DEFAULT | 跟随数据库默认 | - | - | `Isolation.DEFAULT` |

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public void checkAndUpdate(...) { ... }

// 注意：isolation 只对"本事务新开启"生效；加入已有事务时忽略（以已开启事务为准）
```

> ⚠️ **加锁语义说明**：隔离级别是"并发正确性承诺"——级别越高隔离越严、并发越差；`SERIALIZABLE` 在 MySQL 下将普通读升级为读锁，吞吐骤降，非强一致场景慎用。

## 2. 三种并发问题

| 问题 | 现象 | 发生的隔离级别 |
|------|------|--------------|
| 脏读 | 读到**未提交**事务的数据（可能被回滚） | READ_UNCOMMITTED |
| 不可重复读 | 同一事务两次读**同一条**记录值不同（别事务已提交修改） | READ_COMMITTED 以下 |
| 幻读 | 同一事务两次查询**行数**不同（别事务插入了新行） | REPEATABLE_READ 以下 |

```text
场景速记：
  脏读：A 转账未提交，B 看到余额已变 → A 回滚 → B 用了假数据
  不可重复读：A 两次读订单金额，中间 B 改了它 → 两次结果不一致
  幻读：A 统计订单数，B 插入新订单 → 统计结果跳变

  MySQL InnoDB REPEATABLE_READ 用 MVCC + 间隙锁解决幻读（当前读场景），
  普通快照读下 REPEATABLE_READ 已避免幻读 —— 面试答"MySQL 可重复读防幻读"加分。
```

> 🎯 **核心要点**：Spring 的隔离级别是**翻译给数据库的请求**——数据库是否兑现承诺看引擎实现（InnoDB 的 RR 用 MVCC 做到了快照读防幻读）；Spring 层无法"补课"数据库做不到的隔离。

## 3. 数据库默认隔离对照

| 数据库 | 默认隔离 | 说明 |
|--------|---------|------|
| MySQL InnoDB | REPEATABLE_READ | MVCC 快照读 + 当前读间隙锁 |
| PostgreSQL | READ_COMMITTED | 多数业务默认已足够 |
| Oracle | READ_COMMITTED | 不支持 READ_UNCOMMITTED |
| SQL Server | READ_COMMITTED（可配置） | - |

> 💡 **面试高频**：MySQL 默认 RR 但业务常用 RC——因为 MVCC 下两者快照读表现接近，RC 可避免 RR 的间隙锁范围过大（死锁更少、并发更好）；主从复制下 RC 更安全（binlog 日志格式要求）。

## 4. 悲观锁：SELECT FOR UPDATE

```java
@Transactional
public void deductWithPessimisticLock(Long userId, BigDecimal amount) {
    // 当前读 + 行锁：其他事务 UPDATE 此行为阻塞
    AccountRow row = jdbc.sql(
            "SELECT balance FROM t_account WHERE user_id = ? FOR UPDATE")
            .param(userId).query(AccountRow.class).single();

    if (row.balance().compareTo(amount) < 0) {
        throw new InsufficientBalanceException();
    }
    jdbc.sql("UPDATE t_account SET balance = balance - ? WHERE user_id = ?")
            .params(amount, userId).update();
}
```

| 要点 | 说明 |
|------|------|
| 锁生效前提 | **必须在事务内**（commit 才释放）；Spring 中即 @Transactional 包裹 |
| 锁定范围 | 命中的行（配合索引！无索引锁全表） |
| 等待 | 默认等待锁超时（MySQL innodb_lock_wait_timeout）→ 翻译为 CannotAcquireLockException |
| 死锁 | 多事务按不同顺序锁多行 → 死锁，牺牲者抛 DeadlockLoserDataAccessException |
| 释放 | 事务提交/回滚即释放（不是手动 unlock） |

> ⚠️ **加锁口诀**：① 必须事务内；② **必须走索引**（无索引 = 全表锁，性能灾难）；③ 多行加锁顺序要一致（防死锁）；④ 锁内逻辑要短（锁等待超时 1205/55P03 是生产最常见报错之一）。

## 5. 乐观锁：版本号方案

```java
// 表结构：t_account(id, user_id, balance, version)

@Transactional
public boolean deductWithOptimisticLock(Long userId, BigDecimal amount) {
    int updated = jdbc.sql(
            "UPDATE t_account SET balance = balance - :amount, version = version + 1 " +
            "WHERE user_id = :userId AND balance >= :amount AND version = :expectVersion")
            .params("amount", amount, "userId", userId, "expectVersion", currentVersion)
            .update();

    if (updated == 0) {
        // 版本被改或余额不足 → 冲突，交给调用方重试/提示
        throw new OptimisticLockingFailureException("balance conflict");
    }
    return true;
}
```

| 对比 | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 时机 | 读时锁（FOR UPDATE） | 写时校验（version） |
| 冲突处理 | 等待 | **立即失败/重试** |
| 适用 | 写多读少、高冲突 | 读多写少、低冲突 |
| 代价 | 锁等待/死锁风险 | 更新失败需重试（配合 @Retryable） |
| Spring 翻译 | CannotAcquireLockException | OptimisticLockingFailureException |

> 🎯 **核心要点**：Spring 对乐观锁的翻译是 `OptimisticLockingFailureException`（Transient 族）——配合 [Spring-Core-07](../Spring‑Core/07-重试与弹性速查.md) 的 `@Retryable(include = OptimisticLockingFailureException.class)` 是"乐观锁 + 重试"的标准组合拳；JPA 用 `@Version` 字段自动生成版本校验。

## 6. 隔离级别选型

| 业务形态 | 推荐隔离 | 理由 |
|---------|---------|------|
| 常规业务（订单/用户） | READ_COMMITTED 或数据库默认 | 平衡一致性与并发 |
| 财务对账/强一致 | REPEATABLE_READ / SERIALIZABLE | 需要可重复读取一致快照 |
| 汇总统计 | REPEATABLE_READ | 防统计中数据跳变 |
| 高并发扣减 | READ_COMMITTED + 乐观锁/悲观锁 | 别指望隔离级别解决扣减竞态——用锁 |
| 兜底规则 | 靠锁不靠隔离 | 隔离级别防"读"问题，锁防"写"竞态 |

> ⚠️ **终极认知**：隔离级别解决"读的一致性问题"（脏读/不可重复读/幻读）；**写竞态（超卖/重复扣款）必须靠锁**（悲观/乐观）——用 SERIALIZABLE 防超卖是"用错工具"（性能崩了问题还在），正确姿势是锁 + 唯一约束。
