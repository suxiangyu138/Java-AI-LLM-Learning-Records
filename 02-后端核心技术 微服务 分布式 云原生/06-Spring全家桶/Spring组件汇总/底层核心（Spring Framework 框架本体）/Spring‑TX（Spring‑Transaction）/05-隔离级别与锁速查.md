## 1. 隔离级别全表

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | Spring 常量 |
|---------|:---:|:---:|:---:|------------|
| READ_UNCOMMITTED | 可能 | 可能 | 可能 | `Isolation.READ_UNCOMMITTED` |
| READ_COMMITTED | 避免 | 可能 | 可能 | `Isolation.READ_COMMITTED` |
| REPEATABLE_READ | 避免 | 避免 | 可能* | `Isolation.REPEATABLE_READ` |
| SERIALIZABLE | 避免 | 避免 | 避免 | `Isolation.SERIALIZABLE` |
| DEFAULT | 跟随数据库默认 | - | - | `Isolation.DEFAULT` |

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public void checkAndUpdate(...) { ... }

// 注意：isolation 只对"本事务新开启"生效；加入已有事务时忽略（以已开启事务为准）
```

> ⚠️ **加锁语义说明**：隔离级别是"并发正确性承诺"——级别越高隔离越严、并发越差；`SERIALIZABLE` 在 MySQL 下将普通读升级为读锁，吞吐骤降，非强一致场景慎用。

### 1.1 隔离级别的实现机制对照

| 隔离级别 | 主要实现机制 | 成本 |
|---------|-------------|------|
| READ_UNCOMMITTED | 读不加锁、读最新版本 | 最低 |
| READ_COMMITTED | 快照读（MVCC 每语句新快照）/ 行锁 | 低 |
| REPEATABLE_READ | 快照读（事务级快照）+ 当前读行锁/间隙锁 | 中 |
| SERIALIZABLE | 读加共享锁 / 范围锁（MySQL） | 高 |

```text
MySQL InnoDB 的两种读：
  快照读（普通 SELECT）：走 MVCC，不加锁——RR 下整个事务共享一个快照
  当前读（SELECT ... FOR UPDATE / UPDATE / DELETE）：读最新版本 + 加锁
```

> 🎯 **关键认知**：**隔离级别与锁是两套机制**——MVCC 解决"读不阻塞写"，锁解决"写不互相踩踏"；Spring 只负责把隔离级别翻译给数据库，锁的语义完全由 SQL 与数据库引擎决定（Spring 侧唯一相关的是把数据库锁异常翻译成 `CannotAcquireLockException` / `DeadlockLoserDataAccessException`）。

### 1.2 隔离级别速记表

| 速记 | 隔离级别 | 一句话 |
|------|---------|--------|
| 0 级 | READ_UNCOMMITTED | 什么都能读到（包括没提交的） |
| 1 级 | READ_COMMITTED | 只读已提交（PG/Oracle 默认） |
| 2 级 | REPEATABLE_READ | 同一事务内读到的行不变（MySQL 默认） |
| 3 级 | SERIALIZABLE | 串行化，谁也别想打扰 |
| 默认 | DEFAULT | 交给数据库说了算 |

> 💡 记忆锚点：**级别数 = 防护等级**——0 裸奔、1 防脏读、2 防不可重复读、3 防幻读；Spring 常量与 JDBC 常量一一对应（`TRANSACTION_*`），面试直接背这条递增链即可。

## 2. 三种并发问题

| 问题 | 现象 | 发生的隔离级别 |
|------|------|--------------|
| 脏读 | 读到**未提交**事务的数据（可能被回滚） | READ_UNCOMMITTED |
| 不可重复读 | 同一事务两次读**同一条**记录值不同（别事务已提交修改） | READ_COMMITTED 以下 |
| 幻读 | 同一事务两次查询**行数**不同（别事务插入了新行） | REPEATABLE_READ 以下 |

```text
场景速记：
  脏读：A 转账未提交，B 看到余额已变 → A 回滚 → B 用了假数据
  不可重复读：A 两次读订单金额，中间 B 改了它 → 两次结果不一致
  幻读：A 统计订单数，B 插入新订单 → 统计结果跳变

  MySQL InnoDB REPEATABLE_READ 用 MVCC + 间隙锁解决幻读（当前读场景），
  普通快照读下 REPEATABLE_READ 已避免幻读 —— 面试答"MySQL 可重复读防幻读"加分。
```

> 🎯 **核心要点**：Spring 的隔离级别是**翻译给数据库的请求**——数据库是否兑现承诺看引擎实现（InnoDB 的 RR 用 MVCC 做到了快照读防幻读）；Spring 层无法"补课"数据库做不到的隔离。

### 2.1 并发问题的生产定位

| 问题 | 生产表现 | 定位手段 |
|------|---------|---------|
| 脏读 | 报表读到回滚前的数据 | 查隔离级别配置（MySQL 默认不会发生） |
| 不可重复读 | 对账两次金额不一致 | 单事务内多次查询对比快照 |
| 幻读 | 统计条数跳变 | 事务内两次 COUNT 对比 |
| 写覆盖 | 余额/库存被覆盖（超卖） | **这是写竞态不是隔离问题**——用锁/乐观锁 |

**排查顺序建议：**

```text
先判断是"读不一致"还是"写丢失"：
  读不一致 → 隔离级别配置问题（调 RC / RR）
  写丢失   → 锁问题（悲观锁 / 乐观锁 / 唯一约束）
```

> ⚠️ **常见误区**：把"扣款被覆盖"归因于隔离级别——升级到 SERIALIZABLE 也无法根治写竞态（性能先崩）；正确工具是行锁或版本号，隔离级别只管读一致性。

## 3. 数据库默认隔离对照

| 数据库 | 默认隔离 | 说明 |
|--------|---------|------|
| MySQL InnoDB | REPEATABLE_READ | MVCC 快照读 + 当前读间隙锁 |
| PostgreSQL | READ_COMMITTED | 多数业务默认已足够 |
| Oracle | READ_COMMITTED | 不支持 READ_UNCOMMITTED |
| SQL Server | READ_COMMITTED（可配置） | - |

> 💡 **面试高频**：MySQL 默认 RR 但业务常用 RC——因为 MVCC 下两者快照读表现接近，RC 可避免 RR 的间隙锁范围过大（死锁更少、并发更好）；主从复制下 RC 更安全（binlog 日志格式要求）。

### 3.1 默认隔离的生产建议

| 数据库 | 建议策略 | 理由 |
|--------|---------|------|
| MySQL InnoDB | 保持 RR（默认），统计类显式 RR，常规写 RC 亦可 | MVCC 快照读让 RR 代价可控 |
| PostgreSQL | 保持 RC（默认） | RC + 应用层锁已覆盖绝大多数业务 |
| Oracle | 保持 RC（不可升级为 RU） | 数据库不支持 READ_UNCOMMITTED |
| 跨库迁移 | 用 DEFAULT 跟随数据库 | 避免硬编码隔离级别导致迁移差异 |

```java
// 统计类查询显式 RR（防统计中数据跳变）
@Transactional(isolation = Isolation.REPEATABLE_READ, readOnly = true)
public Report dailyReport(Date day) { ... }

// 常规写操作保持默认（跟随数据库）
@Transactional
public void updateStatus(Long id, String status) { ... }
```

> ⚠️ **硬编码隔离的风险**：`isolation = SERIALIZABLE` 硬编码进代码后，压测/上线环境隔离配置不一致时行为难复现——**优先 DEFAULT，特殊场景才显式**，且显式级别要在代码评审中说明理由。

## 4. 悲观锁：SELECT FOR UPDATE

```java
@Transactional
public void deductWithPessimisticLock(Long userId, BigDecimal amount) {
    // 当前读 + 行锁：其他事务 UPDATE 此行为阻塞
    AccountRow row = jdbc.sql(
            "SELECT balance FROM t_account WHERE user_id = ? FOR UPDATE")
            .param(userId).query(AccountRow.class).single();

    if (row.balance().compareTo(amount) < 0) {
        throw new InsufficientBalanceException();
    }
    jdbc.sql("UPDATE t_account SET balance = balance - ? WHERE user_id = ?")
            .params(amount, userId).update();
}
```

| 要点 | 说明 |
|------|------|
| 锁生效前提 | **必须在事务内**（commit 才释放）；Spring 中即 @Transactional 包裹 |
| 锁定范围 | 命中的行（配合索引！无索引锁全表） |
| 等待 | 默认等待锁超时（MySQL innodb_lock_wait_timeout）→ 翻译为 CannotAcquireLockException |
| 死锁 | 多事务按不同顺序锁多行 → 死锁，牺牲者抛 DeadlockLoserDataAccessException |
| 释放 | 事务提交/回滚即释放（不是手动 unlock） |

> ⚠️ **加锁口诀**：① 必须事务内；② **必须走索引**（无索引 = 全表锁，性能灾难）；③ 多行加锁顺序要一致（防死锁）；④ 锁内逻辑要短（锁等待超时 1205/55P03 是生产最常见报错之一）。

### 4.1 锁等待与死锁实战

```java
// 死锁场景：两个事务以相反顺序锁两行
@Transactional
public void t1() {
    lockRow(1);          // 锁 A 行
    sleep(100);
    lockRow(2);          // 等 B 行 → 与 t2 交叉 → 死锁
}

@Transactional
public void t2() {
    lockRow(2);          // 先锁 B 行
    sleep(100);
    lockRow(1);          // 等 A 行
}
```

**统一加锁顺序修正**：所有事务按"行 ID 升序"加锁，交叉必然消失。

| 报错 | 含义 | 处理 |
|------|------|------|
| `Lock wait timeout exceeded`（1205 / 55P03） | 锁等待超时（默认 50s） | 缩短事务、统一加锁顺序、缩小锁范围 |
| `Deadlock found`（1213 / 40P01） | 死锁，本事务被牺牲 | `@Retryable(include = DeadlockLoserDataAccessException.class)` 重试 |
| 锁等待期间连接占用 | 池连接被占 | 锁内逻辑必须短（只做读写，不做远程调用） |

> ⚠️ **锁内禁远程调用**：FOR UPDATE 持锁期间调用外部 API / 发 MQ——锁等待放大成连锁超时，是生产事故高发点；先算账后锁行，锁内只做本地计算 + 单条 SQL。

### 4.2 悲观锁的生产清单

| 清单项 | 检查内容 |
|--------|---------|
| 索引 | `EXPLAIN` 确认命中索引（type 为 ref/range 而非 ALL） |
| 事务边界 | FOR UPDATE 前后只包必要的读写，远程调用移出 |
| 加锁顺序 | 多行加锁按统一规则（如 ID 升序） |
| 等待超时 | `innodb_lock_wait_timeout` 按业务调整（默认 50s 偏长） |
| 异常处理 | 1205/1213 落到统一异常处理器 + 可重试策略 |

```java
// 悲观锁 + 可重试的完整姿势（与乐观锁的差异在"读时锁"）
@Transactional
@Retryable(include = {CannotAcquireLockException.class,
                       DeadlockLoserDataAccessException.class},
           maxAttempts = 3)
public void deductWithLock(Long userId, BigDecimal amount) {
    AccountRow row = jdbc.sql("SELECT balance FROM t_account WHERE user_id = ? FOR UPDATE")
            .param(userId).query(AccountRow.class).single();
    if (row.balance().compareTo(amount) < 0) throw new InsufficientBalanceException();
    jdbc.sql("UPDATE t_account SET balance = balance - ? WHERE user_id = ?")
            .params(amount, userId).update();
}
```

> 🎯 **悲观锁与乐观锁的 Spring 侧差异**：悲观锁靠"读时 FOR UPDATE + 锁异常重试"；乐观锁靠"写时版本校验 + 冲突异常重试"——两者最终都落在 `@Retryable` 上，只是重试触发条件不同（锁异常 vs 版本冲突）。

## 5. 乐观锁：版本号方案

```java
// 表结构：t_account(id, user_id, balance, version)

@Transactional
public boolean deductWithOptimisticLock(Long userId, BigDecimal amount) {
    int updated = jdbc.sql(
            "UPDATE t_account SET balance = balance - :amount, version = version + 1 " +
            "WHERE user_id = :userId AND balance >= :amount AND version = :expectVersion")
            .params("amount", amount, "userId", userId, "expectVersion", currentVersion)
            .update();

    if (updated == 0) {
        // 版本被改或余额不足 → 冲突，交给调用方重试/提示
        throw new OptimisticLockingFailureException("balance conflict");
    }
    return true;
}
```

| 对比 | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 时机 | 读时锁（FOR UPDATE） | 写时校验（version） |
| 冲突处理 | 等待 | **立即失败/重试** |
| 适用 | 写多读少、高冲突 | 读多写少、低冲突 |
| 代价 | 锁等待/死锁风险 | 更新失败需重试（配合 @Retryable） |
| Spring 翻译 | CannotAcquireLockException | OptimisticLockingFailureException |

> 🎯 **核心要点**：Spring 对乐观锁的翻译是 `OptimisticLockingFailureException`（Transient 族）——配合 [Spring-Core-07](../Spring‑Core/07-重试与弹性速查.md) 的 `@Retryable(include = OptimisticLockingFailureException.class)` 是"乐观锁 + 重试"的标准组合拳；JPA 用 `@Version` 字段自动生成版本校验。

### 5.1 乐观锁 + 重试完整代码

```java
@Service
public class InventoryService {
    // 扣减库存：版本校验 + 自动重试
    @Transactional
    @Retryable(retryFor = OptimisticLockingFailureException.class,
               maxAttempts = 3, backoff = @Backoff(delay = 50))
    public boolean deduct(Long skuId, int count) {
        int updated = jdbc.sql(
                "UPDATE t_inventory SET stock = stock - :c, version = version + 1 " +
                "WHERE sku_id = :id AND stock >= :c AND version = :v")
                .params("c", count, "id", skuId, "v", getVersion(skuId)).update();
        if (updated == 0) throw new OptimisticLockingFailureException("库存不足或版本冲突");
        return true;
    }

    @Recover
    public boolean deductFallback(OptimisticLockingFailureException e, Long skuId, int count) {
        log.warn("重试 3 次仍失败: sku={}", skuId);
        return false;   // 兜底：通知人工 / 转失败队列
    }
}
```

| 要点 | 说明 |
|------|------|
| 重试窗口 | 高并发下重试间隔要带随机退避（delay + multiplier） |
| 幂等 | UPDATE 条件含 `stock >= count`——重试安全，不会超扣 |
| 兜底 | `@Recover` 收尾（3 次失败转人工 / 对账） |
| 适用上限 | 冲突率 < 5% 时乐观锁体验最好；冲突率高改悲观锁或队列化 |

> 🎯 **组合拳总结**：`@Version`（JPA）或 version 字段（JDBC）+ 条件 UPDATE + `OptimisticLockingFailureException` + `@Retryable`——四件套即"乐观锁标准实现"，面试可直接背这一条链。

### 5.2 乐观锁的边界情况

| 边界 | 说明 | 处理 |
|------|------|------|
| 首次插入无版本 | 新行没有可校验的 version | 插入即写 version=0，后续更新走校验 |
| 批量更新 | 多行版本各自校验 | SQL 按行 `version = vX` 或逐行更新 |
| 版本回绕 | 版本号达到上限 | 用 long 类型（Java 8 无符号溢出几乎不可达） |
| 与唯一约束叠加 | 版本冲突 + 唯一键冲突 | 分别捕获两个异常，幂等场景优先判定 DuplicateKey |
| 悲观锁转换 | 冲突率飙升 | 加锁策略开关：低冲突乐观、高冲突悲观（配置切换） |

```java
// 幂等 + 乐观锁叠加的典型处理：重复回调幂等返回成功
@Transactional
public boolean markPaid(String orderNo, long expectVersion) {
    try {
        int updated = jdbc.sql(
                "UPDATE t_order SET status = 'PAID', version = version + 1 " +
                "WHERE order_no = :o AND version = :v")
                .params("o", orderNo, "v", expectVersion).update();
        return updated > 0;
    } catch (DuplicateKeyException e) {
        return true;   // 已处理过（幂等）：不视为失败
    }
}
```

> 💡 生产经验：**幂等 + 乐观锁是扣款/支付类接口的标准组合**——条件 UPDATE 天然防重放，唯一索引兜底重复插入，两个机制叠加后接口可以安全重试。

## 6. 隔离级别选型

| 业务形态 | 推荐隔离 | 理由 |
|---------|---------|------|
| 常规业务（订单/用户） | READ_COMMITTED 或数据库默认 | 平衡一致性与并发 |
| 财务对账/强一致 | REPEATABLE_READ / SERIALIZABLE | 需要可重复读取一致快照 |
| 汇总统计 | REPEATABLE_READ | 防统计中数据跳变 |
| 高并发扣减 | READ_COMMITTED + 乐观锁/悲观锁 | 别指望隔离级别解决扣减竞态——用锁 |
| 兜底规则 | 靠锁不靠隔离 | 隔离级别防"读"问题，锁防"写"竞态 |

> ⚠️ **终极认知**：隔离级别解决"读的一致性问题"（脏读/不可重复读/幻读）；**写竞态（超卖/重复扣款）必须靠锁**（悲观/乐观）——用 SERIALIZABLE 防超卖是"用错工具"（性能崩了问题还在），正确姿势是锁 + 唯一约束。

### 6.1 隔离级别与锁的权衡取舍

| 取舍维度 | 倾向 | 反面代价 |
|---------|------|---------|
| 隔离级别 | 尽量数据库默认（MySQL RR / PG RC） | 手动升级 SERIALIZABLE → 吞吐崩 |
| 读一致性 | RR 快照读（事务级一致） | 快照过期——长事务读到旧数据 |
| 写竞态 | 锁（悲观/乐观）而非隔离 | 锁 = 等待/重试成本 |
| 锁粒度 | 行锁优先（走索引） | 全表锁 = 灾难 |
| 锁时长 | 越短越好 | 事务边界无法再缩时用 NOT_SUPPORTED 拆分 |

**决策顺序建议：**

```text
① 是否有写竞态？ → 有 → 悲观/乐观锁 + 唯一约束（别靠隔离级别）
② 是否有读一致性要求？ → 有 → RR（统计/对账）或 RC（常规业务）
③ 是否有长事务？ → 有 → 拆分边界 / NOT_SUPPORTED / 异步化
```

> 🎯 **一句话选型**：隔离级别管"读得稳不稳"，锁管"写得对不对"——两者搭配：常规业务 RC/RR + 关键写路径加锁；面试答"隔离级别能防超卖吗"→ 不能，锁 + 约束才行。

### 6.2 隔离级别与锁的面试追问

1. "MySQL RR 下还能幻读吗？"——普通快照读不能（MVCC 快照）；当前读（FOR UPDATE）下有间隙锁兜底；**两事务分别快照读 + 插入**的"写偏斜"仍可能——答到"写偏斜"即超预期；
2. "SELECT FOR UPDATE 不生效的常见原因？"——没走索引（全表锁或锁错行）、事务外执行（自动提交立即释放）、主从库（读从库锁不到主库数据）；
3. "乐观锁与悲观锁怎么选？"——冲突率 < 5% 乐观锁（无锁开销），冲突率高悲观锁（避免重试风暴）；写多读少悲观锁、读多写少乐观锁；
4. "隔离级别可以加到保存点/内圈吗？"——不能，隔离级别是"事务级"属性，REQUIRED 加入后沿用外层已开启事务的隔离级别（`isolation` 只对新建事务生效）；
5. "锁等待超时和死锁怎么区分？"——超时是"等不到"（1205），死锁是"互相等，数据库选牺牲者"（1213）；死锁可重试，超时重试大概率仍超时（先缩事务）。

> 🎯 **答题收尾**：把"MVCC 两读（快照读/当前读）+ 隔离级别管读 + 锁管写 + 异常翻译（1205→CannotAcquireLock、1213→DeadlockLoser）"串成一条链，隔离与锁的面试题全覆盖。
