| 项 | 值 |

> 💡 独立使用场景：只想要"事务抽象 + 异常体系"而不引入 jdbc——spring-tx 是**最小事务依赖**（如纯 ORM 项目）。

### 1.1 引入方式速查

| 方式 | 写法 | 说明 |
|------|------|------|
| Maven（显式） | `org.springframework:spring-tx:7.0.x` | 只拿合同层，最小依赖 |
| Boot starter | `spring-boot-starter-jdbc` / `spring-boot-starter-data-jpa` | 传递引入 tx + 对应实现模块 |
| Gradle | `implementation 'org.springframework:spring-tx:7.0.x'` | 同 Maven 语义 |
| Boot 4 BOM | 不写版本号 | 由 `spring-boot-dependencies` 统一管理 |

**纯抽象场景**：自定义资源（如内存缓存、分布式锁客户端）要接入事务语义时，只需依赖 tx 并自己实现 `PlatformTransactionManager`——这是 tx 最小化设计的主要用途（`TestTransactionManager` 之于测试也是同类思路）：

```java
// 极简自定义管理器示例（仅供理解契约，生产用现成实现）
public class SimpleTransactionManager implements PlatformTransactionManager {
    @Override
    public TransactionStatus getTransaction(TransactionDefinition definition) {
        return new SimpleTransactionStatus();          // "开启"一个事务
    }

    @Override
    public void commit(TransactionStatus status) { /* 提交回调 */ }

    @Override
    public void rollback(TransactionStatus status) { /* 回滚回调 */ }
}
```

> 🎯 **面试锚点**："spring-tx 需要什么依赖才能编译？"——**零依赖即可**（接口 + 异常族是纯 Java）；要真正管 JDBC 事务才需要 spring-jdbc 的实现——这就是"合同与履约分离"的直接证据。

### 2.1 数据访问异常族速查（org.springframework.dao）

```text
DataAccessException（RuntimeException 根）
├── NonTransientDataAccessException（重试无用，必失败）
│   ├── DataIntegrityViolationException（约束违反：唯一键/外键）
│   │   └── DuplicateKeyException（唯一键冲突——幂等判定的依据）
│   ├── EmptyResultDataAccessException（queryForObject 无结果）
│   └── InvalidDataAccessApiUsageException（API 误用）
├── TransientDataAccessException（瞬时故障，重试可能成功）
│   ├── CannotAcquireLockException（锁等待超时：MySQL 1205 / PG 55P03）
│   ├── DeadlockLoserDataAccessException（死锁牺牲者：MySQL 1213 / PG 40P01）
│   └── QueryTimeoutException（查询超时）
└── ConcurrencyFailureException
    └── OptimisticLockingFailureException（乐观锁版本冲突）
```

| 异常 | 触发场景 | 应对 |
|------|---------|------|
| `DuplicateKeyException` | 唯一索引冲突（重复下单/重复回调） | 幂等判定：转业务提示而非 500 |
| `CannotAcquireLockException` | 行锁等待超时 | 短事务 + 统一加锁顺序 + 重试 |
| `DeadlockLoserDataAccessException` | 死锁被选为牺牲者 | `@Retryable(include = DeadlockLoserDataAccessException.class)` |
| `OptimisticLockingFailureException` | 版本号不一致 | 重试或提示用户刷新（详见 [05-隔离级别与锁速查](05-隔离级别与锁速查.md)） |

> 🎯 **记忆线索**：`Transient`（瞬时）= 可重试；`NonTransient`（非瞬时）= 必失败——异常族的设计本身就在告诉你"该不该重试"，这也是 `@Retryable` 选 include 异常的依据（配合 [Spring-Core-07](../Spring‑Core/07-重试与弹性速查.md)）。

### 2.2 三个关键包的职责分工

包结构里最值得先记的是 annotation / interceptor / support 三个包的"接力关系"：

| 包 | 代表类 | 职责 | 一句话记忆 |
|----|--------|------|-----------|
| `transaction.annotation` | `@Transactional`、`SpringTransactionAnnotationParser` | 声明事务语义（是什么） | 需求说明书 |
| `transaction.interceptor` | `TransactionInterceptor`、`TransactionAspectSupport` | 拦截方法、编排提交/回滚（怎么做） | 施工队 |
| `transaction.support` | `AbstractPlatformTransactionManager`、`TransactionTemplate` | 模板骨架与编程式入口 | 工具箱 |

**三者的数据流：**

```text
注解（annotation）→ 解析成 TransactionAttribute（含回滚规则）
  → 拦截器（interceptor）按属性开事务、调用业务、决定提交/回滚
  → 模板骨架（support）编排传播/挂起/保存点，钩子交给具体实现
```

> 💡 面试说"@Transactional 怎么生效"的完整链条就藏在这三个包里——注解 → 属性 → 拦截 → 模板 → 实现，五个环节缺一不可；每问一层就深一层，这就是从"会用"到"懂源码"的爬升路径。

| 类 | 包 | 职责 | 面试出镜率 |
|----|----|------|:---:|

## 3. 依赖边界

| 依赖 | 方向 | 说明 |
|------|------|------|
| `spring-core` / `spring-beans` | 依赖 | 工具、AOP 通知接入（advice）、Bean 属性 |
| `spring-aop` | 可选 | 声明式事务需 AOP 代理（@EnableTransactionManagement 时） |
| `spring-context` | 可选 | 事件、`TransactionalEventListener` |
| `spring-jdbc` / `spring-orm` | **被依赖** | 事务管理器**实现**所在——tx 只出合同 |
| `reactor` | 可选 | `TransactionalOperator`（响应式） |
| 反向依赖 | - | jdbc、orm、Boot 全依赖 tx（**公共事务契约**） |

> 🎯 **核心要点**：**spring-tx 不包含任何资源事务实现**——`DataSourceTransactionManager` 在 spring-jdbc，`JpaTransactionManager` 在 spring-orm；tx 是"接口 + 拦截器 + 异常族"，实现全部由资源模块提供（接口分离的教科书案例）。

### 3.1 依赖边界常见疑问

**Q1：为什么声明式事务需要 spring-aop？**
`@Transactional` 本身只是元数据，真正织入靠 `TransactionInterceptor`（AOP 环绕通知）。若项目只引入 tx 不加 aop，注解会被解析但不会产生代理——这是"注解不生效"的一类隐蔽根因。

**Q2：JDK 接口代理 vs CGLIB 与依赖的关系？**
接口代理模式只依赖 JDK 动态代理（`java.lang.reflect.Proxy`），零额外依赖；CGLIB 依赖 spring-core 内置的字节码库——7.0 默认 CGLIB 后无需额外引入，但 **final 类/方法不可代理**（详见 [03-@Transactional 速查](03-@Transactional速查.md)）。

**Q3：`<tx:annotation-driven>` 与 `@EnableTransactionManagement` 什么关系？**
两者解析到同一个 `AnnotationDrivenBeanDefinitionParser` 配置路径——XML 是注解的等价形态；同时使用会重复注册拦截器（Boot 中不要混用）。

**Q4：为什么说"jdbc、orm、Boot 全依赖 tx"？**
因为事务契约必须单一来源——所有数据访问模块共享同一套 `PlatformTransactionManager` 语义与 `DataAccessException` 翻译，业务代码才能"换实现不换代码"。

> ⚠️ **依赖瘦身提醒**：生产排查"事务不生效"时，第一步用 `mvn dependency:tree` 确认 tx 和 aop 都在 classpath——比查代码更快定位一类"依赖缺失"型故障。

### 3.2 依赖树排查实战

```text
mvn dependency:tree -Dincludes=org.springframework

org.springframework:spring-context:jar:7.0.6:compile
  ├─ org.springframework:spring-aop:jar:7.0.6:compile        ← 必须有（拦截器织入）
  ├─ org.springframework:spring-beans:jar:7.0.6:compile
  ├─ org.springframework:spring-core:jar:7.0.6:compile
  └─ org.springframework:spring-expression:jar:7.0.6:compile
org.springframework:spring-jdbc:jar:7.0.6:compile
  └─ org.springframework:spring-tx:jar:7.0.6:compile          ← 事务契约层
```

**依赖问题的三种典型形态：**

| 形态 | 现象 | 处理 |
|------|------|------|
| 缺 spring-tx | 编译期找不到 `PlatformTransactionManager` | 加 tx 依赖或换 starter |
| 缺 spring-aop | 编译通过，`@Transactional` 静默不生效 | 加 aop 依赖（starter 通常已带） |
| 版本冲突 | 两个版本共存，行为诡异 | `mvn dependency:tree -Dverbose` 定位，排除旧版 |

> 💡 **版本仲裁提醒**：Boot 项目永远用 `spring-boot-dependencies` BOM 统一版本，手写版本号是冲突的第一来源——除非有明确理由，不要在 starter 之外单独声明 spring-* 版本。

### 3.3 边界自查：我的项目需要哪些依赖

| 技术栈 | 需要的最小依赖 | 事务能力来源 |
|--------|--------------|-------------|
| 纯 JDBC（JdbcTemplate） | starter-jdbc（含 tx + jdbc） | DataSourceTransactionManager |
| MyBatis | mybatis-spring-boot-starter（含 jdbc + tx） | DataSourceTransactionManager |
| JPA/Hibernate | starter-data-jpa（含 orm + tx） | JpaTransactionManager |
| R2DBC | starter-data-r2dbc（含 r2dbc + tx） | R2dbcTransactionManager |
| 只有事务契约 | spring-tx（显式） | 自定义/测试管理器 |

> 🎯 **自查一句话**：凡是"数据访问 + 事务"的场景，starter 都替你装好了 tx；只有"裸写自定义资源事务"才需要显式依赖 spring-tx——别在 starter 项目里手写 tx 依赖（重复且容易版本漂移）。

### 3.4 依赖方向速记

```text
依赖方向只有两种：
  实现 → 契约：jdbc / orm / r2dbc 依赖 tx（履约方依赖合同）
  使用 → 契约：业务代码依赖 tx（甲方只认合同）
  契约 → 实现：永远不存在（tx 不认识任何资源实现——否则就循环依赖了）
```

> 💡 面试防坑：有人会答"spring-tx 依赖 spring-jdbc"——**方向反了**；正确是 spring-jdbc 依赖 spring-tx。记住"合同不依赖履约方"这一条，依赖方向题全对；再补一句"Boot 自动配置同时引入两者，但依赖方向从未变过"即可满分。

## 4. 职责切割：tx vs jdbc vs orm

| 维度 | spring-tx | spring-jdbc | spring-orm |
|------|-----------|-------------|------------|
| 定位 | 事务合同 | JDBC 模板 | ORM 集成 |
| 提供 | 管理器接口/@Transactional/异常族 | DataSourceTransactionManager | Jpa/HibernateTransactionManager |
| 执行 | 不执行 SQL | 模板执行 | EntityManager 管理 |
| 资源绑定 | TransactionSynchronizationManager | DataSourceUtils | EntityManagerFactoryUtils |
| 代表 | 契约与拦截 | 连接与模板 | 实体与映射 |

> 💡 面试画图题："Spring 事务体系分几层？"——**契约层（tx）→ 实现层（jdbc/orm）→ 使用层（@Transactional/TransactionTemplate）**，三句话讲清。

### 4.1 一次调用的事务接力

```text
业务代码 @Transactional 方法
  → tx 层：TransactionInterceptor 拦截、解析属性、选管理器
  → jdbc 层：DataSourceTransactionManager.doBegin 取连接、setAutoCommit(false)
  → 业务 SQL：JdbcTemplate/MyBatis 经 DataSourceUtils 拿"线程绑定"的连接
  → tx 层：commit/rollback 编排 → doCleanupAfterCompletion 归还连接
```

各模块各管一段，任何一环缺失，事务都"名存实亡"——这解释了三个经典症状：

| 症状 | 断裂位置 |
|------|---------|
| 方法不报错但事务没生效 | 拦截器没挂上（aop 缺失 / 自调用） |
| 抛 `IllegalStateException: No transaction...` | 管理器没配（jdbc/orm 模块缺失） |
| 连接没归还（池耗尽） | 清理阶段异常（嵌套挂起未释放） |

> 🎯 **抽象记忆**：tx 是"指挥"，jdbc/orm 是"士兵"——指挥错了（边界、规则），士兵再强也白搭；士兵没了（实现缺失），指挥只能干瞪眼。

### 4.2 职责切割的面试话术

**画图题标准答法（30 秒版）：**

| 层 | 代表 | 一句话 |
|----|------|--------|
| 契约层 | PlatformTransactionManager / TransactionDefinition / DataAccessException | 定义"事务是什么、规则怎么写、失败抛什么" |
| 实现层 | DataSourceTransactionManager / JpaTransactionManager | 把契约翻译成"连接关闭自动提交、回滚" |
| 使用层 | @Transactional / TransactionTemplate | 两种入口，同一引擎 |

**追问应对：**

1. "为什么要分两层，合并行不行？"——不行：合并后换 ORM 就要改业务代码；分层让"资源适配"与"业务语义"解耦（依赖倒置）；
2. "DataAccessException 为什么是运行时异常？"——让 SQL 异常无需强制 try-catch，且统一翻译为可重试/不可重试两类，配合 `@Retryable` 精准重试；
3. "MyBatis 和 JPA 的事务为什么是同一套？"——两者都通过 `DataSourceUtils` 拿线程绑定连接，事务语义在 tx 层统一，资源层只负责"连接归属"。

> 🎯 **一句话收尾**：职责切割的本质是"变化隔离"——资源实现可以变（JDBC→JPA→R2DBC），事务语义不能变；这份稳定就是 tx 作为独立模块存在的全部理由。

## 5. 版本兼容速查

| Spring Framework | Spring Boot | 备注 |
|------------------|-------------|------|
| 7.0.x（2025-11 起） | Boot 4.0.x | 当前主线；CGLIB 代理默认；JPA 3.2/Hibernate 7 |
| 7.1.x（2026-05 起） | Boot 4.1.x | 最新维护线 |
| 6.2.x | Boot 3.4/3.5 | 存量主流；JDK 接口代理行为可配置 |

> ⚠️ **升级提示（6.x → 7.x）**：① `@Transactional` 语义不变，无需改造；② 依赖"JDK 接口代理"（`proxyTargetClass=false` + 接口事务方法）的代码，7.0 默认 CGLIB 下需 `@Proxyable(INTERFACES)` 或显式配置恢复；③ 引用 `org.springframework.orm.hibernate5` 的代码迁到 `orm.jpa.hibernate`（spring-orm）。

### 5.1 版本兼容补充与升级顺序

**升级路径建议（6.x → 7.x）：**

```text
① Boot 3.5 + Framework 6.2 → 先升 Boot 4.0（Framework 7.0）
② 验证事务行为：全量回归"回滚 / 传播"用例（测试事务回滚天然适合做回归）
③ 处理代理差异：final 类 / 接口代理代码按升级提示逐项排查
④ 迁移 ORM 包：hibernate5 → orm.jpa.hibernate（IDE 全局替换 + 编译验证）
```

| 检查项 | 6.x 表现 | 7.x 表现 |
|--------|---------|---------|
| 代理默认 | 按接口（proxyTargetClass 可配） | 全局 CGLIB |
| final 类 + @Transactional | 接口代理下可用 | **静默失效** |
| Hibernate 包路径 | `orm.hibernate5` | `orm.jpa.hibernate` |
| 事务语义 | — | 完全不变 |

> 💡 **兼容策略一句话**：事务行为本身零迁移成本，升级工作量集中在"代理默认值"与"包路径"两项——提前用 `@Proxyable(INTERFACES)` 标注存量接口代理 Bean，可把风险降到最低；异常族（`org.springframework.dao`）包路径 5.x 至今未变，无需处理。

### 5.2 异常族与 ORM 的翻译链路

**为什么 ORM 的异常也归 DataAccessException？** Spring 的持久层翻译体系（PersistenceExceptionTranslator）把各资源异常统一翻译：

```text
SQLException（JDBC）
  → SQLExceptionTranslator：DataAccessException 族（按 SQLState / 错误码映射）
HibernateException / PersistenceException（ORM）
  → PersistenceExceptionTranslator（JpaTransactionManager 内建）
    → DataAccessException 族
```

| 原始异常 | 翻译结果 | 业务影响 |
|---------|---------|---------|
| SQLState 23000（唯一键冲突） | `DuplicateKeyException` | 幂等判定依据 |
| MySQL 1205（锁等待超时） | `CannotAcquireLockException` | 可重试 |
| MySQL 1213（死锁） | `DeadlockLoserDataAccessException` | 可重试 |
| 乐观锁版本不符（JPA） | `OptimisticLockingFailureException` | 可重试/提示 |

> 🎯 **设计意图**：业务代码**只依赖 `org.springframework.dao` 异常族**，不感知底层是 JDBC、MyBatis 还是 Hibernate——换数据访问技术，catch 的异常类型不变；这也是"异常体系是合同一部分"的体现（回滚规则正是按这个异常族匹配，见 [07-回滚机制与测试速查](07-回滚机制与测试速查.md)）。

### 5.3 维护线与升级节奏

| 场景 | 建议版本 | 理由 |
|------|---------|------|
| 新项目（2026 年） | Framework 7.1.x + Boot 4.1.x | 最新维护线，含后续修复 |
| 存量 Boot 3 项目 | 6.2.x（跟随 Boot 3.4/3.5） | 存量稳定，规划迁移窗口 |
| 只依赖 tx 的纯库项目 | 7.0.x 起步 | 契约稳定，升级成本极低 |

**何时升级？** 三个触发信号：

```text
① Boot 主版本升级（3→4）——随大版本一起升，减少迁移次数
② 安全/缺陷修复影响 tx 路径（发布说明里点名 transaction）
③ 新能力需求（响应式事务、新异常类型）——按需升级
```

> 💡 **务实建议**：事务模块是"稳定型依赖"——没有安全漏洞时，不追小版本；升级永远跟着 Boot 大版本走，一次迁移、全面回归（事务测试篇的自动回滚机制正好当回归工具）。
