## 1. Artifact 坐标与版本线

| 项 | 值 |
|----|----|
| GroupId | `org.springframework` |
| ArtifactId | `spring-context` |
| 最新版本 | 7.0.x（2026-08 时点，随 Framework 7.0 主线） |
| 维护线 | 7.0.x / 7.1.x（最新）、6.2.x（Boot 3.x） |
| Java 基线 | 7.x 要求 Java 17+（官方推荐 JDK 25 LTS） |
| 配套可选依赖 | `jakarta.inject`、`aspectjweaver`、Groovy（已边缘） |

> 💡 spring-context 是**日常项目唯一需要显式声明的 Spring Framework 模块**（其余如 aop/tx/web 按需声明）——Boot 应用中由 `spring-boot-starter` 传递引入。

### 1.1 可选依赖各自在什么时候"不得不加"

| 可选依赖 | 触发场景 | 不加的表现 |
|---------|---------|-----------|
| `jakarta.inject`（`jakarta.inject-api`） | 代码使用 `@Inject` / `@Named` | 编译期缺类，**编译就失败**（与 javax 时代"运行期才失效"不同） |
| `aspectjweaver` | `@EnableAspectJAutoProxy` 全量切点表达式、AspectJ LTW | 仅注解式切点（`@Around` 等）其实够用；全量表达式语法抛 `UnsupportedOperationException` |
| Groovy / BeanShell | `<lang:groovy>` 动态语言 Bean | 7.0 起该机制已废弃，**不要在新代码引入** |
| `spring-web` | 需要 `WebApplicationContext` / Servlet 环境 | 只声明 context 时拿不到 Servlet 相关类 |

> ⚠️ 常见误解：**`spring-context` 并不传递依赖 `spring-web`**——写了 `@Controller` 却只引入 context 的"轻量项目"会在部署期才炸。判断依赖是否齐备的唯一可靠手段是跑 `mvn dependency:tree` 核对，而不是靠猜。

### 1.2 JPMS 视角：spring-context 的模块化（Java 9+）

spring-context 是**多模块 jar**（Automatic-Module-Name），在 `module-info.java` 中可以显式依赖：

```java
module com.example.app {
    requires spring.context;          // 自动模块名：org.springframework.context
    requires spring.beans;           // 类型来自 beans（BeanFactory 等）
    requires spring.core;            // 类型来自 core（Environment/Resource 等）
    // 注意：不要 requires 未列出的模块——如需要 jakarta.inject 注解
    requires jakarta.inject;
}
```

| 关注点 | 说明 |
|--------|------|
| 模块名 | `org.springframework.context`（jar 内 MANIFEST 的 Automatic-Module-Name） |
| 传递模块 | `requires transitive` spring.beans / spring.core——用 context 的类型自动可见 |
| 反射访问 | 配置类/@Bean 方法用反射调用，**运行期需 `--add-opens`**（尤其 CGLIB 生成子类访问包私有成员时） |
| 与 classpath 混用 | 模块路径 + classpath 混用有坑（包拆分冲突）——生产上 Boot 项目仍以 classpath 为主 |

> 💡 **实操结论**：JPMS 在 Spring 生态中仍是"**可选增强**"而非默认——7.x 官方支持模块化构建，但绝大多数 Boot 工程跑在 classpath。只有需要 `jlink` 定制运行时（原生镜像/瘦身分发）时才值得全面模块化；此时 `--add-opens` 清单要按启动日志逐条补齐。

### 1.3 版本号语义与发布节奏

| 版本形态 | 示例 | 含义 |
|---------|------|------|
| 主线快照 | 7.0.0-SNAPSHOT / 7.1.0-RC1 | 开发中/候选版，**禁止生产使用** |
| GA 正式版 | 7.0.0 | 首个正式版（2025-11） |
| 补丁版 | 7.0.6（当前示例值） | bug 修复 + 安全补丁，**生产应跟进最新补丁** |
| 维护线 | 6.2.x | 上一代主线，只修不增 |

> 💡 **版本锁定实践**：生产工程**不写 SNAPSHOT、不写 `latest`**——固定补丁版本（如 7.1.2）+ Dependabot/Renovate 定期升级扫描；Spring Framework 的补丁版几乎每个都含安全修复（如 CORS、反序列化类漏洞），**落后补丁 = 已知 CVE 暴露**。

## 2. 包结构地图

```text
org.springframework.context
├── ApplicationContext / ConfigurableApplicationContext   # ★ 顶级接口
├── ApplicationEvent / ApplicationEventPublisher / ApplicationListener  # 事件三件套
├── MessageSource / MessageSourceAware / LocaleResolver    # 国际化
├── ResourceLoaderAware / Lifecycle / EnvironmentAware
├── annotation        # ★ 配置类注解与处理器
│   ├── @Configuration / @Bean / @ComponentScan / @Import / @ImportSelector
│   ├── @Profile / @Conditional / @Lazy / @DependsOn / @Scope / @Primary
│   ├── @PropertySource / @PropertySources
│   ├── ConfigurationClassPostProcessor（★ 配置类处理引擎）
│   ├── ConfigurationClassParser / ConfigurationClassBeanDefinitionReader
│   ├── @EnableResilientMethods / @Retryable / @ConcurrencyLimit（7.0 弹性）
│   └── @EventListener / @TransactionalEventListener（事件注解）
├── support          # 实现层
│   ├── AbstractApplicationContext（★ refresh() 模板方法所在地）
│   ├── GenericApplicationContext / AnnotationConfigApplicationContext
│   ├── ClassPathXmlApplicationContext（存量）
│   ├── ResourceBundleMessageSource / ReloadableResourceBundleMessageSource
│   ├── PropertySourcesPlaceholderConfigurer（${} 占位符解析）
│   └── ApplicationListenerMethodAdapter（@EventListener 适配器）
├── event             # 事件监听器注册/多播
│   └── SimpleApplicationEventMulticaster（★ 事件分发器）
├── i18n              # 国际化支持（LocaleContextHolder 等）
├── index             # 候选组件索引（@Indexed 产物 CANDIDATE_COMPONENTS）
├── weaver            # Load-time weaving（AspectJ LTW，少用）
└── ui               # ApplicationContext 的 Swing 适配（历史遗留）
```

**高频面试点名类**：`AbstractApplicationContext`（refresh 模板）、`ConfigurationClassPostProcessor`（配置类处理）、`SimpleApplicationEventMulticaster`（事件分发）、`AnnotationConfigApplicationContext`（注解入口）。

### 2.1 源码级重点类职责速查（面试背书版）

| 类 | 所在包 | 一句话职责 | 关键成员/方法 |
|----|--------|-----------|--------------|
| `AbstractApplicationContext` | `support` | refresh() 十二步模板 + 事件/资源/消息统一委派 | `refresh()` / `close()` / `getBeanFactory()` |
| `ConfigurationClassPostProcessor` | `annotation` | **最高优先级** `BeanDefinitionRegistryPostProcessor`，处理一切注解配置 | `postProcessBeanDefinitionRegistry()` |
| `ConfigurationClassParser` | `annotation` | 递归解析配置类：@ComponentScan/@Import/@Bean/@PropertySource | `doProcessConfigurationClass()` |
| `ConfigurationClassBeanDefinitionReader` | `annotation` | 把解析结果翻译成 BeanDefinition 注册进工厂 | `loadBeanDefinitions()` |
| `SimpleApplicationEventMulticaster` | `event` | 事件分发（同步/异步），监听器匹配基于 ResolvableType | `multicastEvent()` / `getApplicationListeners()` |
| `ApplicationListenerMethodAdapter` | `support` | 把 `@EventListener` 方法包装成监听器适配器 | `onApplicationEvent()` 反射调用 |
| `PropertySourcesPlaceholderConfigurer` | `support` | `${...}` 占位符解析的 BeanFactoryPostProcessor（7.0 前名字带 Environment） | `postProcessBeanFactory()` |
| `AnnotatedBeanDefinitionReader` | `annotation` | 注册单个注解类（@Bean 方法所在配置类由此读入） | `register()` |
| `ClassPathBeanDefinitionScanner` | `annotation` | 扫描 basePackages 下的候选组件 | `scan()` / `findCandidateComponents()` |

> 💡 **执行时序锚点**：`ConfigurationClassPostProcessor` 在 refresh 第 5 步**最先执行**（它实现了 `PriorityOrdered`）；`PropertySourcesPlaceholderConfigurer` 也在第 5 步但靠后；`SimpleApplicationEventMulticaster` 第 8 步创建；`ApplicationListenerMethodAdapter` 由 `EventListenerMethodProcessor`（BeanFactoryPostProcessor 之一）在第 5 步注册监听器、第 11 步前实例化。

### 2.2 常见误区：包名与 artifact 的对应

| 误区 | 真相 |
|------|------|
| "Environment 在 context 模块" | 接口在 **spring-core** 的 `org.springframework.core.env`；context 只做装配与注入支持 |
| "@Configuration 在 context 的 annotation 包" | 对，但 **@Component/@Service/@Repository 在 spring-beans**（`org.springframework.stereotype`） |
| "Resource 抽象属于 context" | 接口在 **spring-core** 的 `org.springframework.core.io`；context 提供 `ResourcePatternResolver` 实现 |
| "Spring 事件注解在 spring-core" | `@EventListener` 在 context（`org.springframework.context.event`） |

> 🎯 面试答模块归属题的关键话术：**"接口往 core/beans 放，处理器与装配往 context 放"**——core 管"是什么"（接口、工具），context 管"怎么跑起来"（解析、装配、生命周期）。

### 2.3 为什么配置类注解在 context 而不是 beans

| 疑问 | 解答 |
|------|------|
| "@Configuration 为什么不在 spring-beans？" | beans 只提供**工厂运行时**（BeanDefinition/实例化），配置类需要**解析器 + 后置处理器**（ConfigurationClassPostProcessor）——这是"企业编排"职责，归 context |
| "@Component 为什么在 beans？" | 组件注解是**纯标记**（无处理逻辑），由扫描器读取；扫描器在 context（ClassPathBeanDefinitionScanner），但标记语义属于工厂层 |
| "@Bean 方法声明在哪一层？" | 注解在 context 的 `org.springframework.context.annotation`；若只依赖 beans 而不引入 context，则无法用注解式配置（可用编程式 `registerBean`） |
| "为什么 XML 时代的解析器也在这层？" | XML 解析（XmlBeanDefinitionReader）历史归属 beans，注解解析归 context——两者最终都产出 BeanDefinition，**汇合点在 DefaultListableBeanFactory** |

> 💡 **记忆锚点**：**"标记在 beans、解析在 context、汇合在工厂"**——@Component/@Service 是标记（beans），@Configuration/@Bean/@ComponentScan 的解析引擎在 context（annotation 子包），所有解析结果最终都变成 BeanDefinition 注册进 `DefaultListableBeanFactory`。

### 2.4 包结构演进速记（理解设计意图）

| 包 | 演进故事 | 设计意图 |
|----|---------|---------|
| `annotation` | 3.0 起注解配置兴起，解析器集中于此 | 注解配置是"context 层能力"，独立成包便于演进 |
| `event` | 早期在 support，后独立 | 事件是"容器级关注点"，独立包强化语义 |
| `index` | 5.0 引入 @Indexed | 扫描性能优化（编译期索引） |
| `weaver` | 历史包袱 | AspectJ LTW 支持（现代少用） |
| `ui` | 历史包袱 | Swing 适配（1.x 遗留，勿用） |
| `i18n` | 国际化线程绑定 | LocaleContextHolder 的家 |

> 💡 **识别技巧**：看到 `org.springframework.context.*` 下的包名——**带"处理语义"的（annotation/event/support）是核心，带"历史痕迹"的（ui/weaver）基本不碰**；面试被问"context 里有什么包"时，先答核心三包（annotation/event/support），再提 index（性能）、i18n（国际化），最后一句带过历史包即可。

## 3. 依赖边界

| 依赖 | 方向 | 说明 |
|------|------|------|
| `spring-core` / `spring-beans` | 依赖 | context 建立在二者之上（工厂 + 工具 + 注解） |
| `spring-aop` | 依赖（核心） | 7.x 起 context 直接依赖 aop 模块（历史上为可选） |
| `jakarta.inject` | 可选 | `@Inject` 支持（7.0 起仅 jakarta 包） |
| `aspectjweaver` | 可选 | LTW 织入、切点表达式全量支持 |
| `spring-web` / `spring-jdbc` 等 | 可选扩展 | WebApplicationContext / 数据源集成 |
| 反向依赖 | - | context 被 aop/tx/webmvc/boot 全部依赖——**容器之枢纽** |

> ⚠️ **7.0 注意**：`javax.inject` / `javax.annotation` 不再受支持——`@Resource`、`@PostConstruct`、`@Inject` 必须换 jakarta 包（见 [07-集成地图与常见问题](07-集成地图与常见问题.md)）。

### 3.1 依赖故障速查（NoClassDefFoundError 家族）

| 故障现象 | 根因 | 排查手段 |
|---------|------|---------|
| `NoClassDefFoundError: javax/inject/Inject` | 老 jar 仍引 javax.inject-api | 依赖树 grep `javax.inject`，替换为 jakarta 或降级方案 |
| `ClassNotFoundException: org/springframework/web/...` | 缺 spring-web 声明 | 确认只声明了 context；按需补 web 依赖 |
| `NoClassDefFoundError: org/aspectj/lang/annotation/Around` | 用了 @Aspect 但无 aspectjweaver | 补 aspectjweaver；或改用 `AopInfrastructureBean` 之外的纯注解方案 |
| `AbstractMethodError`（运行时诡异） | 多个版本 Spring jar 混在 classpath（如 5.x + 7.x 并存） | `mvn dependency:tree -Dincludes=org.springframework` 全量核对，统一 BOM |
| `IllegalStateException: BeanFactory not initialized` | GenericApplicationContext 未 refresh 就 getBean | 检查构造器是否漏调 refresh() |

> ⚠️ Spring 的 jar 彼此版本强耦合——**core/beans/context 必须同版本**（transitive 引入可保证）。任何"手动指定 spring-core 旧版本"的操作都会导致 AbstractMethodError 这类难排查的运行时故障，禁止手动锁定部分模块版本。

### 3.2 为什么 7.x 的 context 直接依赖 aop（历史上是可选）

| 版本 | 依赖形态 | 影响 |
|------|---------|------|
| 6.x 及更早 | `spring-aop` 为可选依赖（需要时手动加） | 只用 context 的普通应用可以不带 aop |
| 7.0 起 | `spring-aop` 成为**直接依赖** | ① 任何 context 应用都有完整 AOP 能力（@EnableAspectJAutoProxy 直接可用）；② 传递依赖更简单，少一个"忘了加 aop 导致代理不生效"的坑 |

**为什么这样演进**：

```text
1. context 的多个能力其实依赖 aop 基础设施：
   @EnableAspectJAutoProxy（代理装配）、@Async（代理处理器）、
   @TransactionalEventListener（事务同步）、@Retryable（弹性代理）
2. 7.0 弹性能力内建（@EnableResilientMethods）后，代理成为 context 的
   "默认基础设施"而非可选附件
3. 结果：声明 spring-context 即获得完整代理能力，依赖面更可预期
```

> 💡 **实际影响**：存量项目升级 7.0 后若之前依赖"context 不含 aop"的瘦身依赖（极少见），依赖树会变大；正常项目无感知。面试若被问"context 与 aop 的依赖关系"，答"7.0 起直接依赖，因为代理成为容器级基础设施"即可。

## 4. 职责切割：context vs beans vs core

| 维度 | spring-core | spring-beans | spring-context |
|------|-------------|--------------|----------------|
| 定位 | 地基工具 | 工厂容器 | 企业容器 |
| 代表物 | 注解/工具/ResolvableType/SpEL/Resource | BeanFactory/BeanDefinition | ApplicationContext |
| Bean 管理 | 不参与 | 工厂 + 生命周期 | 预加载 + 配置类处理 + 扩展点 |
| 配置处理 | - | XML 解析 | @Configuration/@ComponentScan 全流程 |
| 事件/国际化/Environment | 只提供接口（env） | 不参与 | ★ 全部实现于此 |
| 谁依赖谁 | 无依赖（地基） | 依赖 core | 依赖 core + beans + aop |

> 🎯 **核心要点**：`Environment` 接口定义在 **spring-core 的 `org.springframework.core.env`**，`ApplicationContext` 在 **spring-context**——面试问"Environment 在哪个模块"答 core 不算错、更准确。

### 4.1 职责边界判断题（自测）

| 说法 | 判断 | 解析 |
|------|:----:|------|
| "BeanFactory 是 context 的一部分" | ❌ | BeanFactory 接口在 spring-beans；context **持有**它并扩展 |
| "事件发布能力定义在 context" | ❌ | `ApplicationEventPublisher` 接口在 **spring-context**（`org.springframework.context`）——这题对，注意与 Environment 区分 |
| "MessageSource 接口在 spring-core" | ❌ | 在 spring-context（`org.springframework.context.MessageSource`） |
| "Resource 抽象在 spring-core" | ✅ | `org.springframework.core.io.Resource`（core 的 io 包） |
| "占位符解析器 PropertySourcesPlaceholderConfigurer 在 context" | ✅ | `org.springframework.context.support` |
| "SpEL 表达式引擎在 context" | ❌ | 在 spring-core（`org.springframework.expression`） |
| "@EventListener 注解在 context" | ✅ | `org.springframework.context.event` |
| "DefaultListableBeanFactory 在 context" | ❌ | 在 spring-beans（`org.springframework.beans.factory.support`） |

> 🎯 **自测结论**：8 题里最容易混的是三组——**Resource vs MessageSource（core vs context）**、**BeanFactory vs ApplicationContext（beans vs context）**、**Environment 接口 vs 占位符解析器（core vs context）**。记法：**"纯工具与接口在 core，容器专属在 context，工厂实现全在 beans"**。

## 5. 版本兼容速查

| Spring Framework | Spring Boot | 备注 |
|------------------|-------------|------|
| 7.0.x（2025-11 起） | Boot 4.0.x | 当前主线；jakarta 注解强制、弹性注解可用 |
| 7.1.x（2026-05 起） | Boot 4.1.x | 最新维护线 |
| 6.2.x | Boot 3.4/3.5 | 存量主流；javax 注解仍可用 |

> 💡 **升级提示（6.x → 7.x）**：① 全局替换 `javax.annotation.*` → `jakarta.annotation.*`、`javax.inject.*` → `jakarta.inject.*`；② 确认日志依赖（spring-jcl 已移除，见 [Spring-Core-01](../Spring‑Core/01-模块清单.md)）；③ 测试上下文缓存行为微调（`spring.test.context.cache.pause`）。

### 5.1 升级 6.x → 7.x 实操清单

| 步骤 | 动作 | 验证方式 |
|------|------|---------|
| ① 摸清依赖 | `mvn dependency:tree -Dincludes=javax.*` 定位 javax 来源 | 确认替换面 |
| ② 全局替换 import | `javax.annotation` → `jakarta.annotation`、`javax.inject` → `jakarta.inject`（IDEA 全局替换 + 正则） | 编译通过 |
| ③ 核对日志依赖 | spring-jcl 已移除，确认有 slf4j 绑定 | 启动日志可见 |
| ④ 回归代理行为 | 有 `@Async`/事务代理且依赖接口类型的代码，检查是否需 `@Proxyable(INTERFACES)` | 类型转换/注入点测试 |
| ⑤ 测试上下文策略 | 按需设 `spring.test.context.cache.pause` | 测试套件运行时间对比 |
| ⑥ 清理废弃项 | `<lang:*`、BeanShell、Kotlin 脚本 Bean | 启动日志无 deprecation 警告 |

> 🎯 **核心要点**：升级最大的隐蔽风险是"编译通过、运行静默失效"——javax 注解不报错但不生效（`@Resource` 注入 null、`@PostConstruct` 不执行）。**替换 import 只是第一步，必须用测试验证注入与生命周期回调确实执行**，这是 7.0 迁移与普通升级的本质区别。

### 5.2 运行时与工具链兼容矩阵

| 组件 | 6.2.x（Boot 3.x） | 7.0.x / 7.1.x（Boot 4.x） |
|------|------------------|---------------------------|
| Java 基线 | 17+ | 17+（官方推荐 25 LTS） |
| 注解命名空间 | javax + jakarta 均可 | **仅 jakarta** |
| 日志 | spring-jcl（可切换） | 移除 spring-jcl，走 core 适配 |
| 测试上下文 | 常规缓存 | 新增 `spring.test.context.cache.pause` 暂停策略 |
| 代理默认 | JDK 接口代理 | **CGLIB**（可 @Proxyable 回退） |
| 弹性能力 | 无 | @EnableResilientMethods（内建重试/限流） |
| 已废弃机制 | `<lang:*` 等仍工作 | 废弃（7.0 起不再推荐） |

> 💡 **选型决策**：新工程直接 7.1.x + Boot 4.1.x + JDK 25；存量 Boot 3 工程评估迁移成本时，**先扫 javax 依赖面**（最耗时项），再评估代理行为变化（影响面最广），最后才是新特性接入——顺序决定排期，别反过来。

### 5.3 依赖裁剪与瘦身实践

| 场景 | 做法 | 收益 |
|------|------|------|
| 仅用容器无需 Web | 只声明 spring-context（+ logging） | jar 体积小、无 Servlet 依赖 |
| 排除不必要的传递依赖 | `exclusions`（如不用 JMX 可排除 `spring-context-support` 场景下无此问题） | 减小攻击面 |
| 模块化分发 | jlink + spring-context 模块（见 1.2） | 定制运行时，体积最小化 |
| 排查冗余 | `mvn dependency:analyze` 找出未使用依赖 | 清理 + 维护成本下降 |

```xml
<!-- 纯 context 应用的最小依赖（容器 + 日志），不含任何 Web 能力 -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context</artifactId>
    <version>7.1.2</version>
</dependency>
<dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-slf4j2-impl</artifactId>
</dependency>
```

> ⚠️ **裁剪边界**：别为瘦身排除"看着没用"的核心依赖——`spring-context` 的传递依赖（core/beans/aop）必须完整；裁剪只针对**可选依赖**（jakarta.inject、aspectjweaver、Groovy）和**你不使用的扩展模块**。裁剪后必须跑启动测试验证，避免"依赖被剪掉、运行期才炸"。

### 5.4 模块清单自测题

| 自测题 | 答案 |
|--------|------|
| "spring-context 传递依赖哪些模块？" | spring-core、spring-beans、spring-aop（7.x 直接依赖） |
| "哪些能力在 context 而接口不在？" | MessageSource 接口在 context；Environment 接口在 core |
| "context 的 annotation 包核心类是什么？" | ConfigurationClassPostProcessor（配置处理引擎） |
| "事件多播器在哪个包？" | `org.springframework.context.event` |
| "占位符解析器在哪个包？" | `org.springframework.context.support` |
| "7.0 后 context 与 aop 的关系？" | 直接依赖（代理成为容器级基础设施） |

> 🎯 **收尾**：模块清单的意义不是背包名，而是建立"**能力 → 包 → 类 → 时机**"的定位链——遇到任何 context 问题，先答"它属于哪个包、在 refresh 哪一步被驱动"，再展开细节。定位链越清晰，面试与排障越从容。本页的包结构地图、依赖边界、职责切割三张表建议打印对照复习——它们是"容器体系"面试题的目录页。
