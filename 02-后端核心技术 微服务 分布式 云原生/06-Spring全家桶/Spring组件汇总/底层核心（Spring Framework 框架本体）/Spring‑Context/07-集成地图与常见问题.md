## 1. 与其他模块的集成地图

```text
                    spring-context（企业容器枢纽）
        ┌──────────┬──────────┬──────────┬──────────┐
        ↓          ↓          ↓          ↓          ↓
  spring-core   spring-beans  spring-aop  spring-web  Spring Boot
  注解/环境接口   工厂能力      代理织入      Web 容器     自动配置
  Environment    BeanFactory   (依赖 aop)  WebApplication  挂载在
  接口定义       容器地基       模块已并入    Context       refresh 内
```

| 联动点 | 机制 | 说明 |
|--------|------|------|
| context ↔ beans | refresh 第 2-6 步操作 BeanFactory | 配置类处理 = 注册 BeanDefinition 的批量操作 |
| context ↔ core | `org.springframework.core.env` 接口 + SpEL | Environment/ResolvableType/SpEL 定义在 core，context 组装 |
| context ↔ aop | 7.x 起 context **直接依赖** aop | `@EnableAspectJAutoProxy` 由 context 的 @Import 装配 |
| context ↔ tx | `@EnableTransactionManagement` | 事务开关即 context 的组合注解（见 Spring-TX 系列） |
| context ↔ web | `WebApplicationContext` | request/session 作用域、DispatcherServlet 挂载 |
| context ↔ Boot | `@EnableAutoConfiguration` = 元注解 + DeferredImportSelector | Boot 的自动配置在 refresh 第 5 步参与（见第 2 节） |

> 🎯 **核心要点**：context 是"能力枢纽"——上游吃 core/beans/aop，下游被 web/tx/boot 全部依赖；面试答"容器体系"时按 core（地基）→ beans（工厂）→ context（企业容器）→ Boot（自动装配）四层递进。

## 2. Boot 自动配置在 refresh 里的位置

```text
SpringApplication.run → 创建 AnnotationConfigServletWebServerApplicationContext
  → refresh() 十二步
      第 5 步 invokeBeanFactoryPostProcessors
        → 处理主启动类上的 @SpringBootApplication = 元注解组合：
            @SpringBootConfiguration（= @Configuration）
            @EnableAutoConfiguration（= @Import(AutoConfigurationImportSelector)）
            @ComponentScan
        → AutoConfigurationImportSelector（DeferredImportSelector，最后阶段）
            读取 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
            → 按 @ConditionalOnXxx 逐个裁决 → 注册自动配置类
      第 11 步 实例化全部单例（含自动配置产生的 Bean）
      第 12 步 发布 ContextRefreshedEvent → Boot 启动完成
```

> 💡 与 context 的关系：Boot 没有另起炉灶——**自动配置就是"@Import + @Conditional 的规模化应用"**；`AutoConfigurationImportSelector` 是 `DeferredImportSelector` 子类，走 context 的配置处理管线。深挖见 [Spring生态深度剖析-02](../../../Spring生态深度剖析/02-SpringBoot启动流程与自动配置内核.md)。

## 3. 高频问题与排查速查

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| 升级 7.0 后 @Resource/@PostConstruct 失效 | javax 注解不再支持 | 全部替换为 `jakarta.annotation.*`/`jakarta.inject.*`（必改项） |
| @Bean 方法互调产生两个实例 | 配置类是 Lite 模式（@Component 上的 @Bean） | 改回 `@Configuration`；或接受并显式注入 |
| @ComponentScan 扫不到类 | basePackages 起点不对/过滤器误伤 | 扫描以配置类所在包为根；打印 `getBeanDefinitionNames()` 核对 |
| @Profile Bean 不存在 | 激活 profile 写错/设置太晚 | `setActiveProfiles` 须在 refresh 前；检查 `spring.profiles.active` |
| 事件没触发 | 监听器未注册/类型不匹配/事务监听无事务 | ① 监听器是否 @Component；② `@TransactionalEventListener` 默认无事务不触发（`fallbackExecution=true`） |
| 事件顺序乱/被异常截断 | 默认同步顺序分发 | `@Order` 排序；监听器内部 try-catch；全局 ErrorHandler |
| 异步事件异常"消失" | 线程池吞异常 | 配置 TaskExecutor 的 ErrorHandler + 日志监控 |
| @Value 解析失败 | 属性缺失/PropertySource 链没有 | 默认值 `${k:default}`；`PropertySources` 遍历排查（见 [04-Environment 与属性管理速查](04-Environment与属性管理速查.md)） |
| 中文消息乱码 | 属性文件非 UTF-8 | `setDefaultEncoding("UTF-8")` + 文件本身存成 UTF-8 |
| jar 内 getResource().getFile() 抛错 | 类路径资源不是文件 | 统一 `getInputStream()` |
| ContextRefreshedEvent 触发多次 | 父子多上下文 | 按 `event.getApplicationContext()` 过滤 |
| 测试上下文被频繁暂停重启 | 7.0 测试缓存暂停策略 | `spring.test.context.cache.pause=never`（默认 7.0.3+ 已放宽为"切换才暂停"） |

> ⚠️ **排查三板斧**：① 启动日志从"Bean 创建顺序"定位失败在第几步；② `getBeanDefinitionNames()` / `getBeansOfType` 看"注册了没"；③ 区分"没注册"（扫描/条件）与"注册了没生效"（代理/事件/作用域）。
