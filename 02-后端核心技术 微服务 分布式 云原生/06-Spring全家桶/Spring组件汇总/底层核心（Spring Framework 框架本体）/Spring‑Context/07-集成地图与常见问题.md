## 1. 与其他模块的集成地图

```text
                    spring-context（企业容器枢纽）
        ┌──────────┬──────────┬──────────┬──────────┐
        ↓          ↓          ↓          ↓          ↓
  spring-core   spring-beans  spring-aop  spring-web  Spring Boot
  注解/环境接口   工厂能力      代理织入      Web 容器     自动配置
  Environment    BeanFactory   (依赖 aop)  WebApplication  挂载在
  接口定义       容器地基       模块已并入    Context       refresh 内
```

| 联动点 | 机制 | 说明 |
|--------|------|------|
| context ↔ beans | refresh 第 2-6 步操作 BeanFactory | 配置类处理 = 注册 BeanDefinition 的批量操作 |
| context ↔ core | `org.springframework.core.env` 接口 + SpEL | Environment/ResolvableType/SpEL 定义在 core，context 组装 |
| context ↔ aop | 7.x 起 context **直接依赖** aop | `@EnableAspectJAutoProxy` 由 context 的 @Import 装配 |
| context ↔ tx | `@EnableTransactionManagement` | 事务开关即 context 的组合注解（见 Spring-TX 系列） |
| context ↔ web | `WebApplicationContext` | request/session 作用域、DispatcherServlet 挂载 |
| context ↔ Boot | `@EnableAutoConfiguration` = 元注解 + DeferredImportSelector | Boot 的自动配置在 refresh 第 5 步参与（见第 2 节） |

> 🎯 **核心要点**：context 是"能力枢纽"——上游吃 core/beans/aop，下游被 web/tx/boot 全部依赖；面试答"容器体系"时按 core（地基）→ beans（工厂）→ context（企业容器）→ Boot（自动装配）四层递进。

### 1.1 父子容器实战：场景、配置与坑

| 场景 | 典型结构 | 说明 |
|------|---------|------|
| 传统 Servlet war | `DispatcherServlet` 容器 ← 根容器（业务 Bean） | webmvc 经典双容器；7.x 时代已不推荐（Boot 单容器） |
| 插件/模块隔离 | 主容器 ← 子容器（模块私有 Bean） | 少见但存在（OSGi 风格遗留） |
| 测试隔离 | 测试容器 ← 父容器（共享基础设施） | Spring Test 内部使用 |

**父子容器的关键语义**：

```text
① getBean(name)：先查本级 → 未命中上溯父容器（单向，父不查子）
② getBeansOfType()：只查本级（Listable 语义，不跨级）
③ 同名 Bean：子容器覆盖父容器（子级优先）
④ 事件：父子容器各自维护监听器集合；子容器 publish 的事件不会广播给父容器
⑤ 作用域：request/session 作用域依赖 WebApplicationContext，父子需各自具备
```

| 高频坑 | 表现 | 解法 |
|--------|------|------|
| 子容器注入父容器 Bean 失败 | `NoSuchBeanDefinitionException`（类型查找不跨级） | 按名字 getBean 或把公共 Bean 放到父容器 |
| 双容器各起一套 AOP/事务 | 代理各管各的，事务注解偶发失效 | 统一容器策略：Boot 下禁止手动双容器 |
| ContextRefreshedEvent 触发多次 | 每个容器各发一次（见 [05-事件驱动机制速查](05-事件驱动机制速查.md) 第 6 节） | 事件内判断 `event.getApplicationContext()` |
| 关闭顺序错乱 | 父关子在先 → 子容器 Bean 引用失效 | `registerShutdownHook` 统一托管，按创建逆序关闭 |

> ⚠️ **现代结论**：Boot 是**单容器**（`AnnotationConfigServletWebServerApplicationContext`）——父子容器是遗留 webmvc 架构的产物；新代码遇到"多容器"需求先反思是否能用模块化/多上下文替代，别为隔离制造双容器复杂度。

### 1.2 集成链路自测（闭环复习）

| 自测题 | 考察点 | 答案锚点 |
|--------|--------|---------|
| "Spring Boot 的自动配置类什么时候被解析？" | context ↔ Boot 集成 | refresh 第 5 步，DeferredImportSelector 阶段（用户配置之后） |
| "@EnableTransactionManagement 谁提供？" | context ↔ tx | 注解与 @Import 在 context，事务管理器在 spring-tx |
| "request 作用域是谁注册的？" | context ↔ web | Web 容器子类第 4 步 `postProcessBeanFactory` 注册作用域 |
| "@Async 的代理是谁建的？" | context ↔ aop | `AsyncAnnotationBeanPostProcessor`（context 装配，aop 提供代理基建） |
| "Environment 接口在哪个 jar？" | context ↔ core | spring-core（`org.springframework.core.env`） |
| "@Value 占位符谁解析？" | context ↔ beans | `PropertySourcesPlaceholderConfigurer`（context 包）操作 BeanDefinition（beans 层） |

> 🎯 **一句话闭环**：**"接口在 core、工厂在 beans、编排在 context、专项在各自模块、Boot 只是规模化"**——这条线串起全部集成关系；自测能对答 6 题，容器体系面试的广度题基本无忧。

## 2. Boot 自动配置在 refresh 里的位置

```text
SpringApplication.run → 创建 AnnotationConfigServletWebServerApplicationContext
  → refresh() 十二步
      第 5 步 invokeBeanFactoryPostProcessors
        → 处理主启动类上的 @SpringBootApplication = 元注解组合：
            @SpringBootConfiguration（= @Configuration）
            @EnableAutoConfiguration（= @Import(AutoConfigurationImportSelector)）
            @ComponentScan
        → AutoConfigurationImportSelector（DeferredImportSelector，最后阶段）
            读取 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
            → 按 @ConditionalOnXxx 逐个裁决 → 注册自动配置类
      第 11 步 实例化全部单例（含自动配置产生的 Bean）
      第 12 步 发布 ContextRefreshedEvent → Boot 启动完成
```

> 💡 与 context 的关系：Boot 没有另起炉灶——**自动配置就是"@Import + @Conditional 的规模化应用"**；`AutoConfigurationImportSelector` 是 `DeferredImportSelector` 子类，走 context 的配置处理管线。深挖见 [Spring生态深度剖析-02](../../../Spring生态深度剖析/02-SpringBoot启动流程与自动配置内核.md)。

### 2.1 自动配置未生效的排查路径（生产必会）

```text
现象：预期的自动配置 Bean 没注册
  → ① 启动日志看 "Negative matches" / "Unconditional classes"
       （Boot 4 的自动配置报告，见 3.1 节）
  → ② 条件不满足的常见原因：
       - @ConditionalOnClass：类缺失（依赖没引入）
       - @ConditionalOnProperty：配置值不符（前缀/值大小写）
       - @ConditionalOnMissingBean：**被自己手写 Bean 顶掉**（最常见！）
       - @ConditionalOnWebApplication：环境不符（如非 Web 上下文）
  → ③ 确认自动配置类确实被加载：
       - META-INF/spring/...AutoConfiguration.imports 里有没有该项
       - 是否被 exclude / excludeNames 排除
       - 是否被条件类直接拦截
```

| 常见场景 | 根因 | 解法 |
|---------|------|------|
| 手写配置类与自动配置重名 | 自定义优先，自动配置被 `@ConditionalOnMissingBean` 跳过 | 确认这是预期（多数情况是**好事**） |
| 条件类在**自动配置之后**才生效 | 自动配置的 @ConditionalOnBean 依赖自定义 Bean → 评估顺序导致不匹配 | 用 `@AutoConfigurationAfter` / `@AutoConfigurationBefore` 声明顺序 |
| 引入 starter 但功能没开 | 属性开关未设置（如 `spring.xxx.enabled=false`） | 查文档对应开关属性 |
| 多自动配置相互覆盖 | 条件相同、注册同名 Bean | `exclude` 其中一个，或调整顺序 |

> 🎯 **排查三板斧（Boot 专用）**：① `debug=true` 或 Actuator 的 `conditions` 端点看正/负匹配；② `beans` 端点核对 Bean 是否存在及来源（`beanDefinition` 的 `resource` 字段）；③ `configprops` 端点核对属性绑定值。**先看匹配报告再动代码**，避免盲改。

## 3. 高频问题与排查速查

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| 升级 7.0 后 @Resource/@PostConstruct 失效 | javax 注解不再支持 | 全部替换为 `jakarta.annotation.*`/`jakarta.inject.*`（必改项） |
| @Bean 方法互调产生两个实例 | 配置类是 Lite 模式（@Component 上的 @Bean） | 改回 `@Configuration`；或接受并显式注入 |
| @ComponentScan 扫不到类 | basePackages 起点不对/过滤器误伤 | 扫描以配置类所在包为根；打印 `getBeanDefinitionNames()` 核对 |
| @Profile Bean 不存在 | 激活 profile 写错/设置太晚 | `setActiveProfiles` 须在 refresh 前；检查 `spring.profiles.active` |
| 事件没触发 | 监听器未注册/类型不匹配/事务监听无事务 | ① 监听器是否 @Component；② `@TransactionalEventListener` 默认无事务不触发（`fallbackExecution=true`） |
| 事件顺序乱/被异常截断 | 默认同步顺序分发 | `@Order` 排序；监听器内部 try-catch；全局 ErrorHandler |
| 异步事件异常"消失" | 线程池吞异常 | 配置 TaskExecutor 的 ErrorHandler + 日志监控 |
| @Value 解析失败 | 属性缺失/PropertySource 链没有 | 默认值 `${k:default}`；`PropertySources` 遍历排查（见 [04-Environment 与属性管理速查](04-Environment与属性管理速查.md)） |
| 中文消息乱码 | 属性文件非 UTF-8 | `setDefaultEncoding("UTF-8")` + 文件本身存成 UTF-8 |
| jar 内 getResource().getFile() 抛错 | 类路径资源不是文件 | 统一 `getInputStream()` |
| ContextRefreshedEvent 触发多次 | 父子多上下文 | 按 `event.getApplicationContext()` 过滤 |
| 测试上下文被频繁暂停重启 | 7.0 测试缓存暂停策略 | `spring.test.context.cache.pause=never`（默认 7.0.3+ 已放宽为"切换才暂停"） |

> ⚠️ **排查三板斧**：① 启动日志从"Bean 创建顺序"定位失败在第几步；② `getBeanDefinitionNames()` / `getBeansOfType` 看"注册了没"；③ 区分"没注册"（扫描/条件）与"注册了没生效"（代理/事件/作用域）。

### 3.1 排查工具与日志定位速查

| 工具/手段 | 用途 | 使用方式 |
|----------|------|---------|
| 启动 debug 日志 | 查看配置类处理/Bean 创建全过程 | `-Dlogging.level.org.springframework=debug`（慎用全量，量大） |
| `getBeanDefinitionNames()` | 核对"注册了没" | 启动后打印一遍，与预期清单比对 |
| `getBeansOfType(Class)` | 核对"类型解析对不对" | 接口 vs 实现类维度都查 |
| 条件评估日志 | 查看 @Conditional 匹配结果 | `logging.level.org.springframework.boot.autoconfigure=debug` |
| Actuator `conditions` | Boot 自动配置正/负匹配报告 | `/actuator/conditions` |
| Actuator `beans` | Bean 清单 + 依赖 + 来源 | `/actuator/beans` |
| 失败堆栈读取 | 定位失败步骤 | 异常栈顶找 `AbstractApplicationContext.refresh` 的调用栈帧对应步骤号 |
| 单元测试快速验证 | 上下文可启动性回归 | `@SpringBootTest` + 失败即红 |

```text
启动失败堆栈阅读模板：
  BeanCreationException: Error creating bean with name 'orderService'   ← 谁挂了
  Caused by: BeanCreationException: ... 'dataSource'                    ← 依赖谁
  Caused by: ... Failed to bind properties under 'spring.datasource'    ← 最终根因
  → 根因永远在 Caused by 链的**最底层**，逐层剥到根再动手
```

> 💡 **日志级别建议**：生产环境 `info`，开发环境 `debug`（仅限 Spring 包）；告警类 `BeanCreationException` 必须带完整堆栈（`log.error("...", e)` 而非 `e.getMessage()`），否则线上只能看到半句话。

### 4.1 源码级追问深水区（高级面试）

| 追问 | 源码锚点 | 关键结论 |
|------|---------|---------|
| "refresh() 的模板方法在哪、钩子有几个？" | `AbstractApplicationContext.refresh()`（约 200 行） | 3 个子类钩子：`postProcessBeanFactory` / `onRefresh` / `initPropertySources`；模板模式典型 |
| "配置类处理为什么是 PostProcessor 而非监听器？" | `ConfigurationClassPostProcessor` 实现 `BeanDefinitionRegistryPostProcessor` | 必须在**任何 Bean 实例化前**注册定义——监听器阶段太晚（实例化后） |
| "BeanDefinitionRegistryPostProcessor 与 BeanFactoryPostProcessor 谁先？" | `PostProcessorRegistrationDelegate` | 先所有 registry 型（按 PriorityOrdered → Ordered → 无序），后 factory 型——配置类处理因此最早 |
| "早期事件机制怎么实现？" | `AbstractApplicationContext.earlyApplicationEvents` | 第 10 步前发布的事件进 List 暂存，registerListeners 后逐个补发 |
| "@TransactionalEventListener 底层？" | `TransactionalEventListenerFactory` + `TransactionSynchronization` | 监听器被包装成事务同步回调，在 commit/rollback 回调点触发 |
| "占位符解析为什么 7.0 改属性名？" | `PropertySourcesPlaceholderConfigurer`（原 `PropertyPlaceholderConfigurer`） | 新版以 Environment 为唯一属性来源，旧类路径属性文件模式废弃 |
| "Boot 自动配置为什么用 DeferredImportSelector？" | `AutoConfigurationImportSelector` | 延迟到所有普通配置类处理完后执行 → 保证用户配置优先、自动配置可被条件覆盖 |

**答题结构建议（源码题通用公式）**：`何时执行（refresh 第几步）→ 由谁触发（哪个接口/钩子）→ 数据结构与缓存（Map/List 等）→ 失败行为（抛什么异常、状态如何）`——把答案组织成四段，比记代码行数更有说服力。

> 🎯 **最终闭环**：本系列 8 篇（00-07）覆盖了 spring-context 的**模块边界 → 容器骨架 → 配置处理 → 属性环境 → 事件总线 → 国际化/资源 → 集成排障**完整链路；面试与排障都能从"refresh 十二步"这一根主线展开——**一切 context 问题的第一反应都是"它在十二步中的哪一步"**。

### 4.2 30 秒口述冲刺（面试前速背）

| 口述题 | 30 秒答案 |
|--------|----------|
| "介绍一下 Spring 容器" | ApplicationContext 在 beans 工厂之上补五件事：预加载单例、配置类处理、事件、国际化、属性环境；启动走 refresh 十二步模板；Boot 挂载在自动配置处 |
| "refresh 最关键的三步" | 第 5 步改图纸（PostProcessor 处理配置类）、第 11 步开工（实例化单例）、第 12 步剪彩（ContextRefreshedEvent） |
| "配置类怎么处理" | ConfigurationClassPostProcessor 在第 5 步最先执行：解析 @Configuration → 扫描 → @Import → 注册 @Bean 定义，全程在实例化之前 |
| "事件机制一句话" | 进程内发布-订阅：publishEvent → 多播器按类型匹配监听器 → 默认同步逐个调用；事务事件挂在事务提交回调上 |
| "属性优先级" | PropertySource 链从前往后第一个命中生效：命令行 > 系统属性 > 环境变量 > 配置文件 > @PropertySource |
| "7.0 最大变化" | javax 注解强制迁 jakarta（静默失效风险）、代理默认 CGLIB、弹性注解内建 |

> 💡 **考前清单**：① refresh 十二步能默写；② Full/Lite 区别能举例；③ @Import 家族四个成员；④ 事件 vs MQ 三条差异；⑤ 配置优先级能说出 5 个来源；⑥ 7.0 迁移三项注意。六条过一遍，context 面试关即过。

### 4.3 面试追问补充：三个反直觉点

| 反直觉点 | 真相 | 陷阱 |
|---------|------|------|
| "配置类处理时类还没加载" | ConfigurationClassParser 基于字节码元数据，**目标类未进 JVM**——所以条件评估期间 `Class.forName` 的副作用不存在 | 误以为"解析 = 加载" |
| "refresh 失败后还能用吗" | **不能**——抛异常后容器状态不可恢复，只能 close 重建；但部分单例已创建（资源泄漏风险） | 误以为 catch 后继续 getBean 可用 |
| "事件同步是默认不是保证" | 默认同步**只是多播器的默认配置**；任何异步监听/ErrorHandler 改动都会改变语义——面试说"Spring 事件一定同步"不严谨 | 把默认当契约 |
| "父子容器事件不互通" | 子容器 publish 的事件**不会**广播给父容器监听器；但子容器能收到父容器发布的事件（父向子可见） | 方向记反 |

> 🎯 **最终建议**：context 是"**配置处理 + 生命周期 + 事件 + 属性**"四位一体的容器层——面试题无论从哪问起，最终都落到"**它在 refresh 十二步的哪一步、由哪个 PostProcessor 驱动、数据存在哪**"三问上。把三问作为答题骨架，context 相关面试无死角。
