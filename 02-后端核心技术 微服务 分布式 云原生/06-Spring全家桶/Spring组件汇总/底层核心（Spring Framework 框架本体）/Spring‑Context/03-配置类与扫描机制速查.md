## 1. 配置类处理引擎

```text
refresh() 第 5 步 invokeBeanFactoryPostProcessors
  → ConfigurationClassPostProcessor（BeanDefinitionRegistryPostProcessor ★）
      → ConfigurationClassParser
          1. 递归解析 @Configuration 类 → 形成 ConfigurationClass 集合
          2. 处理 @ComponentScan（扫描出的 @Component 也并入）
          3. 处理 @Import（导入类/Selector/Registrar/BeanRegistrar）
          4. 收集 @Bean 方法与 @PropertySource
      → ConfigurationClassBeanDefinitionReader
          把每个配置类成员翻译成 BeanDefinition 注册进容器
```

> 🎯 **核心要点**：一切注解配置（@Configuration、@Bean、@ComponentScan、@Import）都在 **refresh 第 5 步、实例化任何业务单例之前**被解析——所以 @Profile 等条件在"注册图纸"阶段就裁决完毕，不满足条件的 Bean 连 BeanDefinition 都不会存在。

### 1.1 哪些类会被当作"配置类"处理（判定边界）

`ConfigurationClassPostProcessor` 的判定规则（`ConfigurationClassUtils.checkConfigurationClassCandidate`）：

| 判定条件 | 是否 Full | 说明 |
|---------|:--------:|------|
| 标注 `@Configuration` | ✅ | 标准 Full 模式 |
| 标注 `@Component`/`@ComponentScan`/`@Import`/`@ImportResource` | Lite | 元注解触发，`proxyBeanMethods` 语义不同 |
| 标注 `@Bean` 方法的普通类 | Lite | 类上没有上述注解但方法有 @Bean |
| 注解类（`@interface` 自身） | ❌ | 只读取元数据，不实例化 |
| 匿名类 / Lambda | ❌ | 无法被 CGLIB 代理，直接忽略 |
| `final` 类 | Lite 兜底 | CGLIB 无法继承 final 类，Spring 退化为不代理（7.x 会打日志） |

```java
// 边界示例：@Import 一个非配置类 → 该类的 @Bean 方法仍生效（Lite 处理）
public class PlainHolder {                       // 无任何注解
    @Bean
    public DataSource ds() { return new HikariDataSource(); }
}
@Configuration
@Import(PlainHolder.class)                       // 导入后 ds() 仍被注册
public class AppConfig { }
```

> ⚠️ **边界坑**：`@Import` 一个**普通 POJO**（无 @Bean、无 @Configuration）会被直接注册为 Bean 实例——这常用于"引入无注解的第三方单例类"；但若该 POJO 依赖构造器参数，Spring 会尝试按构造器注入解析，参数不满足时启动报错而非降级。

### 1.2 配置类处理的元数据访问细节

配置类处理全程基于**字节码元数据**（`AnnotationMetadata` / `MethodMetadata`）——目标类在解析阶段**不会被加载进 JVM**：

| 元数据能力 | 说明 | 使用场景 |
|-----------|------|---------|
| `AnnotationMetadata.getAnnotationAttributes(...)` | 读取注解属性（含默认值） | ImportSelector 读开关参数（见 4.2） |
| `MethodMetadata` | @Bean 方法的返回类型、参数、注解 | BeanDefinition 的工厂方法元数据 |
| `isAnnotated(...)` / `hasAnnotation(...)` | 直接/元注解判定 | 条件评估（ProfileCondition 的判定路径） |
| `getMemberClassNames()` | 嵌套类列表 | 配置类内部类解析 |

```java
// 典型用法：自定义 Condition 中读取注解属性做决策
public class OnFeature implements Condition {
    @Override
    public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata meta) {
        Map<String, Object> attrs =
                meta.getAnnotationAttributes(Feature.class.getName());
        return attrs != null && "on".equals(attrs.get("state"));
    }
}
```

> 💡 **边界**：元数据是**编译期快照**——运行期通过反射修改的注解/字段不会反映到元数据中；同时字节码级解析**不触发类加载**，这是"扫描/条件评估对 JVM 类加载器无副作用"的保证（也解释了为什么 @Profile 判断不初始化任何 Bean）。

## 2. @Configuration：Full 与 Lite 模式

| 模式 | 判定 | 行为 | 影响 |
|------|------|------|------|
| Full | 类标注 `@Configuration`（非 final） | CGLIB 子类代理 `@Bean` 方法互调 → 单例保证 | `@Bean` 方法之间互相调用安全 |
| Lite | `@Component`/普通类上的 `@Bean` | 不代理，互调即 new 新对象 | 同类型 Bean 可能被创建多次 |

```java
@Configuration(proxyBeanMethods = true)   // Full（默认）——方法互调走代理
public class AppConfig {
    @Bean
    public A a() { return new A(); }
    @Bean
    public B b() { return new B(a()); }   // 取容器中的单例 A
}
```

> ⚠️ **高频坑**：Lite 模式下 `b()` 内部 `new a()` 会创建第二个 A——表现是"同一个 Bean 被实例化两次"；排查时先确认配置类是否为 `@Configuration`（Full）而非 `@Component`（Lite）。
> 💡 性能取向：`proxyBeanMethods = false` 可跳过 CGLIB 代理提速（适合纯返回 Bean 无互调的配置），代价是失去方法互调单例保证。

### 2.1 Full 模式 CGLIB 代理的边界与限制

| 限制 | 表现 | 规避 |
|------|------|------|
| 配置类不能是 `final` | CGLIB 无法生成子类，自动降级 Lite 并打 WARN 日志 | 类声明去掉 final |
| `@Bean` 方法不能是 `private`/`static`/`final` | 代理拦截不到，互调退化为直接 new | 改为 public/protected 实例方法 |
| 返回类型必须是可见类 | CGLIB 需要能生成目标子类（接口可，但生成的是代理类） | 用具体类或接口 + 实现类 |
| 跨配置类的 `@Bean` 互调 | Full 代理**只对同一实例内的方法互调生效**——配置类 A 调用配置类 B 的 @Bean 方法不走代理 | 用参数注入代替跨类互调 |

```java
@Configuration
public class ConfigA {
    @Bean
    public A a() { return new A(); }
}

@Configuration
public class ConfigB {
    @Bean
    public B b() { return new B(configA.a()); }   // ❌ 跨类调用：new 出第二个 A
    // ✅ 正确：@Bean public B b(A a) { return new B(a); }  —— 参数注入走容器
}
```

> 🎯 **面试追问**："Full 模式怎么保证单例？"——`@Configuration` 类被 `ConfigurationClassEnhancer` 用 CGLIB 生成子类，`@Bean` 方法被改写为：**先查容器（`BeanFactory` 的 `getBean`），命中直接返回，未命中才执行原方法体**——这就是"方法互调单例"的底层实现。

## 3. @ComponentScan：扫描与过滤

```java
@ComponentScan(
    basePackages = "com.example",
    includeFilters = @Filter(type = FilterType.ASSIGNABLE_TYPE, classes = Api.class),
    excludeFilters = {
        @Filter(type = FilterType.REGEX, pattern = ".*Mock.*"),
        @Filter(type = FilterType.ANNOTATION, classes = Deprecated.class)
    },
    lazyInit = true,                     // 扫描出的 Bean 统一懒加载
    nameGenerator = FullyQualifiedBeanNameGenerator.class  // 全限定名生成器
)
```

| FilterType | 匹配方式 |
|-----------|---------|
| `ANNOTATION` | 类上的注解（如 @Service） |
| `ASSIGNABLE_TYPE` | 类型可赋值（接口/父类） |
| `REGEX` | 类名正则 |
| `ASPECTJ` | AspectJ 表达式（需 aspectjweaver） |
| `CUSTOM` | 自定义 `TypeFilter` |

> 💡 细节：① 扫描基于 ASM 读字节码（**不加载类**），`@Indexed` 索引可跳过扫描加速启动（spring-context-indexer 生成 `META-INF/spring.components`）；② `@ComponentScan` 未指定 basePackages 时以**配置类所在包**为根；③ 7.0 起 `MetadataReader` 底层在 Java 24+ 使用 `ClassFileMetadataReader`（JEP 484，见 [Spring-Core-01](../Spring‑Core/01-模块清单.md)）。

### 3.1 扫描的边界、性能与 @Indexed 实战

**扫描的边界（扫不到/扫错的表现）**：

| 边界场景 | 表现 | 解法 |
|---------|------|------|
| basePackages 指向接口/抽象类包 | 注册了但无法实例化（接口无实现） | 扫实现类所在包 |
| 扫描到重复 Bean 名 | `BeanDefinitionStoreException: duplicate` | 检查同名类（常见于分包同名 DTO）；用 `nameGenerator` 或统一包名 |
| `@Component` 类在 jar 内 | 默认**扫不到**（扫描只针对 classpath 目录，不遍历 jar 内类） | 用 `@Indexed` 或 `@Import` 显式导入 |
| 嵌套类（内部类） | 能扫到（`$` 分隔名） | Bean 名含 `$`，谨慎依赖名字注入 |
| excludeFilters 误伤 | Bean 静默缺失，启动不报错 | 打印 `getBeanDefinitionNames()` 核对 |

**@Indexed 索引机制**：

```xml
<!-- 库项目：让引用方免扫描直接发现你的组件 -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context-indexer</artifactId>
    <optional>true</optional>   <!-- 仅编译期生成索引，不进入运行 classpath -->
</dependency>
```

```text
生成物：META-INF/spring.components（key=类名, value=注解名列表）
  com.example.MyService=org.springframework.stereotype.Component
机制：CandidateComponentsIndexLoader 在 classpath 读取所有 spring.components
      → ClassPathBeanDefinitionScanner 发现索引存在时跳过目录扫描（7.0 起默认使用）
代价：修改组件后需重新编译（索引是编译期产物）；不适合频繁增删类的开发期
```

> ⚠️ **权衡**：@Indexed 把"运行期扫描"换成"编译期索引"——启动提速明显（千级组件可省数百毫秒），但**开发期增删类必须重新编译**，否则新组件不生效。大型多模块工程启用，单体小工程收益不大。

## 4. @Import 家族：类/Selector/Registrar

| @Import 目标 | 机制 | 适用 |
|-------------|------|------|
| 普通类 | 直接注册为 Bean | 无注解的第三方类 |
| `@Configuration` 类 | 并入配置处理 | 模块化配置组合 |
| `ImportSelector` | 返回类名数组，**不加载自己** | 按条件/枚举批量导入（Boot 自动配置用它） |
| `DeferredImportSelector` | 最后阶段执行 | 依赖顺序的批量导入（Boot `AutoConfigurationImportSelector`） |
| `ImportBeanDefinitionRegistrar` | 直接操作 Registry 注册 | 旧式细粒度注册 |
| `BeanRegistrar`（7.0） | 注册 API 化、AOT 友好 | ✅ 新代码推荐 |

```java
// 条件化批量导入（自动配置核心模式）
class MySelector implements ImportSelector {
    @Override
    public String[] selectImports(AnnotationMetadata importingClassMetadata) {
        return new String[] {"com.example.CacheConfig", "com.example.MqConfig"};
    }
}
```

> ⚠️ **经典面试题**：`ImportSelector` 与 `@ComponentScan` 的差异——Selector 在**字节码层面**返回类名（不实例化自己、不加载目标类），适合"启动早期按条件决定导入谁"；扫描则是对已存在类的全量发现。

### 4.2 面试追问：@Import 的执行顺序与重复导入

| 追问 | 答案要点 |
|------|---------|
| "@Import 的处理顺序是什么？" | ① 普通类/配置类（直接注册）→ ② ImportSelector 返回值 → ③ ImportBeanDefinitionRegistrar → ④ **DeferredImportSelector 最后**（保证用户配置优先） |
| "同一个类被 @Import 两次会怎样？" | **幂等**——配置解析器按全限定名去重（`ConfigurationClassParser` 维护已处理集合），不会重复注册 |
| "@Import 与 @ComponentScan 扫到同一个类？" | 同一 BeanDefinition 来源去重：扫描与导入都落在工厂注册，**同名同类型**时后者覆盖前者（一般是导入覆盖扫描） |
| "为什么 Boot 自动配置必须用 DeferredImportSelector？" | 用户自定义配置类与 @Bean 需要先注册，自动配置的 `@ConditionalOnMissingBean` 才有得判断——延迟执行让"用户优先"成为可兑现的语义 |
| "Selector 里能读开关注解参数吗？" | 能——`selectImports(AnnotationMetadata)` 的入参就是**当前配置类上的注解元数据**（含 @EnableXxx 的属性） |

```java
// Selector 读取开关注解参数的完整姿势
public class CacheSelector implements ImportSelector {
    @Override
    public String[] selectImports(AnnotationMetadata meta) {
        Map<String, Object> attrs =
                meta.getAnnotationAttributes(EnableCache.class.getName());
        String type = (String) attrs.get("type");       // "redis" / "caffeine"
        return new String[] {
            "redis".equals(type) ? RedisCacheConfig.class.getName()
                                 : CaffeineCacheConfig.class.getName()
        };
    }
}
```

> 💡 **记忆锚点**：@Import 的处理优先级口诀——**"先类、再 Selector、后 Registrar、Deferred 殿后"**；去重与覆盖语义让"同一配置被多处导入"天然安全，这也是 Boot 多 starter 叠加不出乱子的底层保障。

## 5. @EnableXxx：组合式开关

`@EnableXxx` = **一个元注解 + 一个 @Import** 的组合注解，语义为"一键开启某能力"：

| 开关 | 组合内容 | 开启能力 |
|------|---------|---------|
| `@EnableAsync` | @Import(AsyncConfigurationSelector) | 异步执行（@Async） |
| `@EnableScheduling` | @Import(SchedulingConfiguration) | 定时任务（@Scheduled） |
| `@EnableCaching` | @Import(CachingConfigurationSelector) | 缓存（@Cacheable） |
| `@EnableTransactionManagement` | @Import(TransactionManagementConfigurationSelector) | 声明式事务 |
| `@EnableAspectJAutoProxy` | @Import(AspectJAutoProxyRegistrar) | AOP 注解切面 |
| `@EnableResilientMethods`（7.0） | @Import(ResilientMethodsConfiguration) | 重试/限流（@Retryable/@ConcurrencyLimit） |

> 🎯 **核心要点**：Spring Boot 的"自动配置开关"本质上就是这一模式的规模化——`@EnableAutoConfiguration` = 元注解 + `@Import(AutoConfigurationImportSelector.class)`。

### 5.1 自定义 @EnableXxx：完整实现（模块化配件的标准姿势）

```java
// ① 定义开关注解：元注解 + @Import(Registrar 或配置类)
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Import(RetrySupportRegistrar.class)
public @interface EnableRetrySupport {
    int maxAttempts() default 3;       // 开关上暴露可配置项
}

// ② Registrar 读取开关注解上的属性 → 注册 Bean
class RetrySupportRegistrar implements ImportBeanDefinitionRegistrar {
    @Override
    public void registerBeanDefinitions(AnnotationMetadata meta,
                                        BeanDefinitionRegistry registry) {
        Map<String, Object> attrs = meta.getAnnotationAttributes(EnableRetrySupport.class.getName());
        int max = (int) attrs.get("maxAttempts");
        GenericBeanDefinition bd = new GenericBeanDefinition();
        bd.setBeanClass(RetrySupport.class);
        bd.getConstructorArgumentValues().addGenericArgumentValue(max);
        registry.registerBeanDefinition("retrySupport", bd);
    }
}

// ③ 使用方：一个注解开箱即用（与 Boot 的 @EnableAutoConfiguration 同构）
@Configuration
@EnableRetrySupport(maxAttempts = 5)
public class AppConfig { }
```

| 实现路径 | 适用 | 取舍 |
|---------|------|------|
| `ImportSelector` | 按条件批量选配置类 | 无法直接读开关注解参数注册 Bean（需 `DeferredImportSelector` 组合） |
| `ImportBeanDefinitionRegistrar` | 细粒度注册 + 读注解属性 | 代码量最大，7.0 起推荐迁移到 `BeanRegistrar` |
| `BeanRegistrar`（7.0） | 声明式、AOT 友好 | 新代码首选（见 [Spring-Core-01](../Spring‑Core/01-模块清单.md)） |
| 直接 `@Import(Config.class)` | 最简单的固定装配 | 无参数化能力，无法按开关条件变化 |

> 💡 判断标准：**"开关是否携带参数"**——不带参数直接用 `@Import(配置类)`；带参数且要注册定制 Bean 用 Registrar；要按外部条件（类存在/属性存在）批量决定导入谁用 Selector。三者可以组合使用，Boot 的自动配置就是 Selector + 条件注解的叠加。

## 6. 条件评估时机与 @Profile

```text
条件评估分两个阶段（ConfigurationClassParser 处理时）：
  ① 配置类级条件（@Profile/@Conditional 标在配置类上）
     → 不满足则整个配置类跳过，其 @Bean/@Import 全部不生效
  ② 成员级条件（标在 @Bean 方法/组件类上）
     → 逐个裁决，只跳过不满足的单个定义
```

| 机制 | 声明位置 | 说明 |
|------|---------|------|
| `@Profile("dev")` | 配置类或 @Bean 方法 | 基于激活 profile 的派生条件（`ProfileCondition`） |
| `@Conditional(Condition.class)` | 类/方法 | 自定义：`matches(context, metadata)` 返回 true 才注册 |
| `@Profile("!test")` | 同上 | 支持 `!`/`&`/`|` 表达式：`@Profile("dev & !ci")` |

```java
@Configuration
@Profile("prod")                       // 配置类级：整个类只在 prod 生效
@Conditional(HasDatabase.class)        // 自定义条件叠加
public class ProdDataConfig {
    @Bean
    @Profile("!legacy")                // 成员级：prod 且非 legacy 才注册
    public DataSource ds() { ... }
}
```

> ⚠️ 注意：条件裁决发生在**BeanDefinition 注册阶段**（refresh 第 5 步），而非实例化阶段——所以 `ApplicationContext.getBeansOfType(DataSource.class)` 根本看不到未满足条件的类型。

### 6.1 条件评估的边界与 ConfigurationCondition

| 边界场景 | 行为 | 说明 |
|---------|------|------|
| 条件标在 `BeanDefinitionRegistryPostProcessor` 上 | **不生效**（该类自身注册先于条件评估） | 属于先有鸡还是先有蛋的死结，官方明确不支持 |
| 条件依赖其他 Bean 是否存在 | 评估时 Bean 尚未注册完 | 用 `ConfigurationCondition` 的 `Phase` 或 `@ConditionalOnBean` 的 `search` 语义 |
| `@Profile` 表达式写错 | 静默不注册（无任何警告） | `@Profile("dev & !ci")` 中 `&` 与 `|` 是**与/或**，不是 Java 位运算 |
| profile 名大小写 | 区分大小写（`Dev` ≠ `dev`） | 统一小写约定 |
| 多个 `@Conditional` | 全部 `matches` 返回 true 才注册（**与**关系） | 无法表达"任一满足"——需自定义组合 Condition |

```java
// ConfigurationCondition：在配置类解析阶段（PARSE_CONFIGURATION）就评估
public class OnClassPresent implements ConfigurationCondition {
    @Override
    public ConfigurationPhase getConfigurationPhase() {
        return ConfigurationPhase.PARSE_CONFIGURATION;   // 尽早：解析配置类之前
    }
    @Override
    public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata meta) {
        return ClassUtils.isPresent("com.thirdparty.Sdk", ctx.getClassLoader());
    }
}
```

> 💡 **记忆**：普通 `@Conditional` 默认 `REGISTER_BEAN` 阶段（注册 BeanDefinition 前）；`PARSE_CONFIGURATION` 阶段更早（整个配置类解析前）——需要"条件决定是否解析这个配置类"时用 `ConfigurationCondition`。Boot 的 `@ConditionalOnClass` 就是按 `PARSE_CONFIGURATION` 语义实现的。

## 7. @Proxyable 与全局代理默认（7.0）

7.0 起上下文级代理默认**统一为 CGLIB**（与 Boot 一致，@Async/@Retryable 等全部代理处理器一致生效）：

| 机制 | 用法 | 效果 |
|------|------|------|
| 全局默认 | 上下文内 `ProxyConfig` Bean（名 `AutoProxyUtils.DEFAULT_PROXY_CONFIG_BEAN_NAME`） | 上下文级代理类型默认 |
| `@Proxyable(TARGET_CLASS)` | `@Bean` 方法或 `@Component` 类上 | 该 Bean 强制 CGLIB（默认下可省略） |
| `@Proxyable(INTERFACES)` | 同上 | 该 Bean 强制 JDK 接口代理（退出 CGLIB） |
| `@Proxyable(interfaces = {...})` | 指定接口集合 | 覆盖上下文级默认 |

```java
@Configuration
public class AppConfig {
    @Bean
    @Proxyable(INTERFACES)          // 此 Bean 走 JDK 接口代理（其余仍 CGLIB）
    public PaymentClient paymentClient() { return new PaymentClientImpl(); }
}
```

> 💡 迁移提示：6.x 依赖"JDK 接口代理"的存量代码在 7.0 下默认行为改变——若强依赖接口代理，用 `@Proxyable(INTERFACES)` 按 Bean 恢复；详见 [Spring-AOP-00](../Spring‑AOP/00-Spring AOP组件总览.md) 与 [Spring-Core-06](../../../Spring Core/06-@Configuration与AOP代理机制.md)。

### 7.1 面试追问：代理类型在实际生产中的影响

| 追问场景 | CGLIB（默认） | JDK 接口代理（@Proxyable(INTERFACES)） |
|---------|--------------|----------------------------------------|
| 无接口的类能否被代理 | ✅ 能 | ❌ 不能（必须实现接口） |
| 注入类型用实现类 | ✅ 可直接注入 | ⚠️ 注入实现类类型会失败（代理只实现接口）——**这是 6.x 时代最常见的注入坑** |
| final 方法/类 | ⚠️ 无法代理（final 方法不拦截） | 与接口方法无关，可代理 |
| 性能 | 字节码增强，启动稍慢 | 原生动态代理，但仅限接口方法 |
| 自调用（this 调方法） | 两种情况都无法拦截——**代理只拦外部调用** | 同左 |

```java
// 7.0 排查"代理类型不符"的标准姿势
if (AopUtils.isCglibProxy(bean)) {
    // CGLIB 子类代理：可强转实现类类型
} else if (AopUtils.isJdkDynamicProxy(bean)) {
    // JDK 代理：只能强转接口类型，强转实现类抛 ClassCastException
}
```

> 🎯 **面试结论话术**：7.0 默认 CGLIB 是"消灭 JDK 代理的两个经典坑"（注入实现类类型失败、接口新增方法导致代理失效）——代价是生成子类有少量启动开销、final 方法失去拦截能力。理解"**代理 = 一个看起来是目标类型的增强子类/兄弟**"，就能推演出所有相关问题的答案。
