## 1. 配置类处理引擎

```text
refresh() 第 5 步 invokeBeanFactoryPostProcessors
  → ConfigurationClassPostProcessor（BeanDefinitionRegistryPostProcessor ★）
      → ConfigurationClassParser
          1. 递归解析 @Configuration 类 → 形成 ConfigurationClass 集合
          2. 处理 @ComponentScan（扫描出的 @Component 也并入）
          3. 处理 @Import（导入类/Selector/Registrar/BeanRegistrar）
          4. 收集 @Bean 方法与 @PropertySource
      → ConfigurationClassBeanDefinitionReader
          把每个配置类成员翻译成 BeanDefinition 注册进容器
```

> 🎯 **核心要点**：一切注解配置（@Configuration、@Bean、@ComponentScan、@Import）都在 **refresh 第 5 步、实例化任何业务单例之前**被解析——所以 @Profile 等条件在"注册图纸"阶段就裁决完毕，不满足条件的 Bean 连 BeanDefinition 都不会存在。

## 2. @Configuration：Full 与 Lite 模式

| 模式 | 判定 | 行为 | 影响 |
|------|------|------|------|
| Full | 类标注 `@Configuration`（非 final） | CGLIB 子类代理 `@Bean` 方法互调 → 单例保证 | `@Bean` 方法之间互相调用安全 |
| Lite | `@Component`/普通类上的 `@Bean` | 不代理，互调即 new 新对象 | 同类型 Bean 可能被创建多次 |

```java
@Configuration(proxyBeanMethods = true)   // Full（默认）——方法互调走代理
public class AppConfig {
    @Bean
    public A a() { return new A(); }
    @Bean
    public B b() { return new B(a()); }   // 取容器中的单例 A
}
```

> ⚠️ **高频坑**：Lite 模式下 `b()` 内部 `new a()` 会创建第二个 A——表现是"同一个 Bean 被实例化两次"；排查时先确认配置类是否为 `@Configuration`（Full）而非 `@Component`（Lite）。
> 💡 性能取向：`proxyBeanMethods = false` 可跳过 CGLIB 代理提速（适合纯返回 Bean 无互调的配置），代价是失去方法互调单例保证。

## 3. @ComponentScan：扫描与过滤

```java
@ComponentScan(
    basePackages = "com.example",
    includeFilters = @Filter(type = FilterType.ASSIGNABLE_TYPE, classes = Api.class),
    excludeFilters = {
        @Filter(type = FilterType.REGEX, pattern = ".*Mock.*"),
        @Filter(type = FilterType.ANNOTATION, classes = Deprecated.class)
    },
    lazyInit = true,                     // 扫描出的 Bean 统一懒加载
    nameGenerator = FullyQualifiedBeanNameGenerator.class  // 全限定名生成器
)
```

| FilterType | 匹配方式 |
|-----------|---------|
| `ANNOTATION` | 类上的注解（如 @Service） |
| `ASSIGNABLE_TYPE` | 类型可赋值（接口/父类） |
| `REGEX` | 类名正则 |
| `ASPECTJ` | AspectJ 表达式（需 aspectjweaver） |
| `CUSTOM` | 自定义 `TypeFilter` |

> 💡 细节：① 扫描基于 ASM 读字节码（**不加载类**），`@Indexed` 索引可跳过扫描加速启动（spring-context-indexer 生成 `META-INF/spring.components`）；② `@ComponentScan` 未指定 basePackages 时以**配置类所在包**为根；③ 7.0 起 `MetadataReader` 底层在 Java 24+ 使用 `ClassFileMetadataReader`（JEP 484，见 [Spring-Core-01](../Spring‑Core/01-模块清单.md)）。

## 4. @Import 家族：类/Selector/Registrar

| @Import 目标 | 机制 | 适用 |
|-------------|------|------|
| 普通类 | 直接注册为 Bean | 无注解的第三方类 |
| `@Configuration` 类 | 并入配置处理 | 模块化配置组合 |
| `ImportSelector` | 返回类名数组，**不加载自己** | 按条件/枚举批量导入（Boot 自动配置用它） |
| `DeferredImportSelector` | 最后阶段执行 | 依赖顺序的批量导入（Boot `AutoConfigurationImportSelector`） |
| `ImportBeanDefinitionRegistrar` | 直接操作 Registry 注册 | 旧式细粒度注册 |
| `BeanRegistrar`（7.0） | 注册 API 化、AOT 友好 | ✅ 新代码推荐 |

```java
// 条件化批量导入（自动配置核心模式）
class MySelector implements ImportSelector {
    @Override
    public String[] selectImports(AnnotationMetadata importingClassMetadata) {
        return new String[] {"com.example.CacheConfig", "com.example.MqConfig"};
    }
}
```

> ⚠️ **经典面试题**：`ImportSelector` 与 `@ComponentScan` 的差异——Selector 在**字节码层面**返回类名（不实例化自己、不加载目标类），适合"启动早期按条件决定导入谁"；扫描则是对已存在类的全量发现。

## 5. @EnableXxx：组合式开关

`@EnableXxx` = **一个元注解 + 一个 @Import** 的组合注解，语义为"一键开启某能力"：

| 开关 | 组合内容 | 开启能力 |
|------|---------|---------|
| `@EnableAsync` | @Import(AsyncConfigurationSelector) | 异步执行（@Async） |
| `@EnableScheduling` | @Import(SchedulingConfiguration) | 定时任务（@Scheduled） |
| `@EnableCaching` | @Import(CachingConfigurationSelector) | 缓存（@Cacheable） |
| `@EnableTransactionManagement` | @Import(TransactionManagementConfigurationSelector) | 声明式事务 |
| `@EnableAspectJAutoProxy` | @Import(AspectJAutoProxyRegistrar) | AOP 注解切面 |
| `@EnableResilientMethods`（7.0） | @Import(ResilientMethodsConfiguration) | 重试/限流（@Retryable/@ConcurrencyLimit） |

> 🎯 **核心要点**：Spring Boot 的"自动配置开关"本质上就是这一模式的规模化——`@EnableAutoConfiguration` = 元注解 + `@Import(AutoConfigurationImportSelector.class)`。

## 6. 条件评估时机与 @Profile

```text
条件评估分两个阶段（ConfigurationClassParser 处理时）：
  ① 配置类级条件（@Profile/@Conditional 标在配置类上）
     → 不满足则整个配置类跳过，其 @Bean/@Import 全部不生效
  ② 成员级条件（标在 @Bean 方法/组件类上）
     → 逐个裁决，只跳过不满足的单个定义
```

| 机制 | 声明位置 | 说明 |
|------|---------|------|
| `@Profile("dev")` | 配置类或 @Bean 方法 | 基于激活 profile 的派生条件（`ProfileCondition`） |
| `@Conditional(Condition.class)` | 类/方法 | 自定义：`matches(context, metadata)` 返回 true 才注册 |
| `@Profile("!test")` | 同上 | 支持 `!`/`&`/`|` 表达式：`@Profile("dev & !ci")` |

```java
@Configuration
@Profile("prod")                       // 配置类级：整个类只在 prod 生效
@Conditional(HasDatabase.class)        // 自定义条件叠加
public class ProdDataConfig {
    @Bean
    @Profile("!legacy")                // 成员级：prod 且非 legacy 才注册
    public DataSource ds() { ... }
}
```

> ⚠️ 注意：条件裁决发生在**BeanDefinition 注册阶段**（refresh 第 5 步），而非实例化阶段——所以 `ApplicationContext.getBeansOfType(DataSource.class)` 根本看不到未满足条件的类型。

## 7. @Proxyable 与全局代理默认（7.0）

7.0 起上下文级代理默认**统一为 CGLIB**（与 Boot 一致，@Async/@Retryable 等全部代理处理器一致生效）：

| 机制 | 用法 | 效果 |
|------|------|------|
| 全局默认 | 上下文内 `ProxyConfig` Bean（名 `AutoProxyUtils.DEFAULT_PROXY_CONFIG_BEAN_NAME`） | 上下文级代理类型默认 |
| `@Proxyable(TARGET_CLASS)` | `@Bean` 方法或 `@Component` 类上 | 该 Bean 强制 CGLIB（默认下可省略） |
| `@Proxyable(INTERFACES)` | 同上 | 该 Bean 强制 JDK 接口代理（退出 CGLIB） |
| `@Proxyable(interfaces = {...})` | 指定接口集合 | 覆盖上下文级默认 |

```java
@Configuration
public class AppConfig {
    @Bean
    @Proxyable(INTERFACES)          // 此 Bean 走 JDK 接口代理（其余仍 CGLIB）
    public PaymentClient paymentClient() { return new PaymentClientImpl(); }
}
```

> 💡 迁移提示：6.x 依赖"JDK 接口代理"的存量代码在 7.0 下默认行为改变——若强依赖接口代理，用 `@Proxyable(INTERFACES)` 按 Bean 恢复；详见 [Spring-AOP-00](../Spring‑AOP/00-Spring AOP组件总览.md) 与 [Spring-Core-06](../../../Spring Core/06-@Configuration与AOP代理机制.md)。
