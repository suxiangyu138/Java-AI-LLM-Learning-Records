## 1. MessageSource 体系

| 组件 | 职责 |
|------|------|
| `MessageSource` | `getMessage(code, args, defaultMessage, locale)` |
| `ResourceBundleMessageSource` | ✅ 标准实现：基于 JDK ResourceBundle |
| `ReloadableResourceBundleMessageSource` | 支持热重载（开发期友好，cacheSeconds） |
| `StaticMessageSource` | 编程式注册消息（测试用） |
| `DelegatingMessageSource` | 默认空实现（未配置时返回 code 本身） |

```text
getMessage 解析流程：
  ① 按 code 查找 messages.properties（basename 默认 "messages"）
  ② 无默认 MessageSource → DelegatingMessageSource 返回 code 原样
  ③ {0} {1} 参数占位 → getMessage("order.created", new Object[]{id}, locale)
```

```java
@Service
public class I18nService {
    private final MessageSource ms;

    public String msg(String code, Object... args) {
        return ms.getMessage(code, args, LocaleContextHolder.getLocale());
    }
}
```

> 🎯 **核心要点**：MessageSource 是**纯进程内**消息解析——不含翻译服务、不含持久化；业务上"提示文案国际化"用它，"界面多语言资源"常交给前端。刷新时机：refresh 第 7 步 `initMessageSource`，Bean 名为 `messageSource`。

### 1.1 MessageSource 边界：异常与实现选择

| 边界场景 | 行为 | 应对 |
|---------|------|------|
| code 不存在且未传默认值 | 抛 `NoSuchMessageException`（unchecked） | 业务侧统一传默认值：`getMessage(code, args, "未知错误", locale)` |
| 未配置任何 MessageSource Bean | 兜底 `DelegatingMessageSource`，返回 code 原样 | 想全局兜底文案就显式配置；想"找不到就报错"用 ResourceBundleMessageSource |
| 参数个数与占位不符 | 多余参数忽略；缺少参数按 `MessageFormat` 规则原样输出 `{0}` | 参数用数组顺序对应 |
| code 为 null / locale 为 null | NPE 风险 | `getMessage(code, args, locale)` 三个参数均校验 |
| 多实现并存 | **只有一个生效**（Bean 名固定 `messageSource`，同名覆盖） | 命名冲突时以名称为准，别注册两个 |

```java
// 安全调用封装：永远有兜底文案
public String msg(String code, Object... args) {
    try {
        return ms.getMessage(code, args, LocaleContextHolder.getLocale());
    } catch (NoSuchMessageException e) {
        return code;   // 或统一"文案待完善"
    }
}
```

| 实现 | 适用 | 取舍 |
|------|------|------|
| `ResourceBundleMessageSource` | 生产标准 | 基于 JDK ResourceBundle，**不支持运行时改文件** |
| `ReloadableResourceBundleMessageSource` | 开发/文案频繁调整 | 支持热重载（cacheSeconds），生产建议关闭（设 0 或大值） |
| `StaticMessageSource` | 单元测试 | 编程式 `addMessage`，无需文件 |

> ⚠️ **面试细节**：`MessageSource` 的 `getMessage(String code, Object[] args, String defaultMessage, Locale)` 有默认值版本——**传了默认值就永不抛异常**（找不到返回默认值）；不带默认值的版本才可能抛 `NoSuchMessageException`。

### 1.2 面试追问：MessageSource 关键点

| 追问 | 答案要点 |
|------|---------|
| "不配置 MessageSource 会怎样？" | refresh 第 7 步找不到 Bean 时注册 `DelegatingMessageSource`——`getMessage` 返回 code 原样，**应用不报错但全部文案变 key**（这是"没配国际化却静默"的坑） |
| "MessageSource 与 ResourceBundle 的关系？" | `ResourceBundleMessageSource` 底层就是 JDK 的 `ResourceBundle`（Locale 回退链 zh_CN → zh → 默认）；Spring 包了一层缓存与参数格式化 |
| "messageSource 这个 Bean 名有特殊意义吗？" | 有——refresh 第 7 步按**固定名 `messageSource`** 查找；改名则兜底实现接管，你的配置失效 |
| "热重载怎么做到的？" | `ReloadableResourceBundleMessageSource` 每次 getMessage 检查文件时间戳（受 cacheSeconds 节流），重读 properties——生产慎用（性能与一致性问题） |
| "父子容器的 MessageSource 会怎样？" | 子容器可配置 `setParentMessageSource` 委托父容器（默认无）——多容器场景需显式装配 |

> 💡 **记忆锚点**：MessageSource 的四个关键字——**固定 Bean 名（messageSource）、默认兜底（Delegating）、回退链（zh_CN→zh→默认→code）、格式化（MessageFormat）**。面试把这条线串起来，国际化题基本通关。

## 2. 资源文件与消息解析规则

```properties
# messages.properties（默认）
order.created=订单 {0} 已创建，金额 {1}
error.not.found=记录不存在

# messages_zh_CN.properties（中文）
order.created=订单 {0} 已创建，金额 {1}

# messages_en.properties（英文）
order.created=Order {0} created, amount {1}
```

| 特性 | 说明 |
|------|------|
| basename | 默认 `messages`，可 `setBasename("i18n/messages")` 分包 |
| 回退链 | `zh_CN` → `zh` → 默认 → code 原样 |
| 占位符 | `{0}` `{1}` 位置参数 |
| 编码 | **必须 UTF-8**（7.x 默认 UTF-8；旧版需 setDefaultEncoding） |
| 热重载 | `ReloadableResourceBundleMessageSource` + `cacheSeconds` |

```java
@Bean
public MessageSource messageSource() {
    ReloadableResourceBundleMessageSource ms = new ReloadableResourceBundleMessageSource();
    ms.setBasename("classpath:i18n/messages");
    ms.setDefaultEncoding("UTF-8");
    ms.setCacheSeconds(60);   // 开发期可设 1 秒
    return ms;
}
```

> ⚠️ 常见坑：属性文件保存为 GBK 时中文乱码——确认编辑器/CI 以 UTF-8 写入；`locale=zh_CN` 文件名格式是 `messages_zh_CN`（下划线）。

### 2.1 消息格式化高级用法（MessageFormat 能力）

```properties
# 占位符带格式化类型（底层走 java.text.MessageFormat）
order.created=订单 {0} 创建于 {1,date,short}，金额 {2,number,currency}
order.count=共 {0,number,integer} 条记录
```

```java
// 参数类型：字符串/数字/日期均可，格式化类型可选
ms.getMessage("order.created",
        new Object[]{ orderId, LocalDate.now(), amount },
        locale);
// 输出示例（zh_CN）：订单 1001 创建于 26-8-7，金额 ¥1,200.00
```

| 占位语法 | 含义 | 示例 |
|---------|------|------|
| `{0}` | 原样输出 | `订单 {0}` |
| `{0,number}` | 数字格式化（千分位） | `{0,number,#.##}` 保留两位 |
| `{0,number,currency}` | 货币（按 locale 符号） | `¥1,200.00` / `$1,200.00` |
| `{0,date,short}` / `{0,date,long}` | 日期格式（按 locale） | `26-8-7` / `2026年8月7日` |
| `{0,time}` | 时间格式 | `14:30:00` |
| `{0,choice,1#one|1<many}` | 单复数选择 | 英文单复数场景 |

> 💡 **细节**：① 格式化类型是**可选的**——不带类型则 `toString()` 输出；② 单引号是 MessageFormat 的转义字符，文案里要输出 `'` 需写 `''`；③ 中文无单复数变化，但数字格式化（千分位/货币）按 locale 自动切换符号，**这是纯翻译文件做不到的**——格式化必须放在模板里而非翻译里。

### 2.2 消息键命名与文件组织规范

**命名规范（推荐）**：`模块.场景.动作` 三级命名，全小写点分：

```properties
# 示例：order 模块
order.created=订单 {0} 已创建
order.paid=订单 {0} 已支付，金额 {1}
order.error.not_found=订单不存在
order.error.status_illegal=订单状态不允许该操作
user.login.fail=用户名或密码错误
```

| 组织维度 | 推荐 | 反例 |
|---------|------|------|
| 按模块分包 | `i18n/messages-order.properties`、`i18n/messages-user.properties`（setBasenames 多基名） | 单文件 500+ 条 |
| 错误码 vs 文案分离 | 错误码走错误码表，文案走 messages | 文案里硬编码错误码语义 |
| 文案评审 | 文案变更走 PR + 校对流程 | 开发直接改（翻译质量失控） |
| 前后端共用 | 前端需要时导出 messages 给前端（构建期） | 前端重复维护一套 |

> ⚠️ **生产建议**：① messages 文件**只放文案不放配置**（别把 URL/阈值混进来）；② 缺少翻译的 key 用 CI 检查（扫描 `getMessage` 的 code 与 properties 键比对）——**翻译缺失在测试环境就该暴露**，而不是用户上线后看到 code 原样。

## 3. Locale 解析与切换

| 组件 | 用途 | 归属 |
|------|------|------|
| `LocaleContextHolder` | 线程绑定当前 Locale（`setLocale`/`getLocale`） | context |
| `RequestContext` / `RequestContextHolder` | Web 请求上下文（内含 Locale） | web 模块 |
| `LocaleResolver` | 请求 → Locale 解析策略 | web 模块 |
| `AcceptHeaderLocaleResolver`（默认） | 从 Accept-Language 头取 | web 模块 |
| `CookieLocaleResolver` | Cookie 记忆用户语言 | web 模块 |
| `SessionLocaleResolver` | 会话级语言 | web 模块 |

```java
// 请求级切换（Web 场景）：URL 参数 ?lang=en → 写入 SessionLocaleResolver 后刷新
@PostMapping("/locale")
public void changeLocale(@RequestParam String lang, HttpSession session) {
    session.setAttribute(SessionLocaleResolver.LOCALE_SESSION_ATTRIBUTE_NAME,
                         Locale.forLanguageTag(lang));
}
```

> 💡 归属边界：`LocaleContextHolder` 在 spring-context；`LocaleResolver` 族在 spring-web——纯 context 应用（无 Web）直接用 `LocaleContextHolder.setLocale()` 绑定。

### 3.1 非 Web 场景 Locale 实战（CLI/批处理/测试）

```java
// CLI 工具：按参数绑定当前线程 Locale
public static void main(String[] args) {
    LocaleContextHolder.setLocale(Locale.forLanguageTag(args[0]));   // 线程绑定
    try (AnnotationConfigApplicationContext ctx =
                 new AnnotationConfigApplicationContext(AppConfig.class)) {
        I18nService svc = ctx.getBean(I18nService.class);
        System.out.println(svc.msg("order.created", 1001));          // 读线程绑定的 Locale
    } finally {
        LocaleContextHolder.resetLocaleContext();                    // 必须清理！防线程泄漏
    }
}
```

| 场景 | 绑定方式 | 清理 |
|------|---------|------|
| 单线程 CLI | `setLocale` + 用后 `resetLocaleContext` | 进程退出无碍，但规范上仍清理 |
| 线程池任务 | 每个任务内设置（**勿用 InheritableThreadLocal 传播过期值**） | 任务 finally 中 reset |
| Web 请求 | 由 `DispatcherServlet` 自动管理（LocaleResolver） | 框架自动清理 |
| 测试 | `LocaleContextHolder.setLocale` + @After 清理 | JUnit 每用例独立 |

> ⚠️ **线程池泄漏坑**：`LocaleContextHolder` 基于 `ThreadLocal`——**线程池复用的线程不清理会串语言**（线程 A 设置了 zh_CN，池中复用它处理 en_US 请求直接错乱）。Web 场景框架兜底，但**手写任务/异步监听器必须显式 reset**。

### 3.2 Web 端 Locale 全链路（请求 → 响应）

```text
请求到达（Accept-Language: zh-CN,zh;q=0.9,en;q=0.8）
  → LocaleResolver.resolveLocale(request)      （默认 AcceptHeaderLocaleResolver）
  → DispatcherServlet 将 Locale 写入 LocaleContextHolder（线程绑定）
  → 业务代码 LocaleContextHolder.getLocale() 取当前语言
  → MessageSource.getMessage(code, args, locale) 按 locale 查文件
  → 响应（渲染时按 Accept-Language 内容协商）
```

| 切换策略 | 实现 | 适用 |
|---------|------|------|
| 请求头（默认） | `AcceptHeaderLocaleResolver` | 浏览器语言跟随，无需用户设置 |
| Cookie 记忆 | `CookieLocaleResolver` | 用户手动选语言，持久记忆 |
| Session | `SessionLocaleResolver` | 登录会话内统一语言 |
| 参数指定 | 自定义或 `?lang=` + 手动设置 | 语言切换入口（见第 3 节代码） |

> 💡 **细节**：① `LocaleResolver` 决定"请求用什么语言"；`MessageSource` 决定"语言怎么映射到文案"——两者职责分离；② 切换语言后**重定向**（Post/Redirect/Get）避免刷新丢设置；③ 静态资源（图片/文档）的语言化不属于 MessageSource 范畴，走 CDN 或前端路由。

### 3.3 Locale 相关面试追问速答

| 追问 | 答案要点 |
|------|---------|
| "LocaleContextHolder 为什么是 ThreadLocal？" | Web 请求处理是线程绑定的——同请求内任意深度调用都能取到同一 Locale，无需层层传参；代价是线程池复用需清理 |
| "Accept-Language 带 q 权重怎么解析？" | `AcceptHeaderLocaleResolver` 按 q 值排序取最优先支持的；q=0 表示明确不接受 |
| "默认语言是什么？" | 无任何解析结果时 `Locale.getDefault()`（JVM 默认，注意与服务器地区一致性问题） |
| "语言切换接口怎么设计？" | 返回新语言的文案包 + 重定向；服务端记住偏好（Cookie/Session），不依赖客户端头 |
| "多语言文案测试怎么覆盖？" | 参数化测试遍历主要 Locale 断言 key 齐全 + 无乱码（GBK 文件是常见漏网） |

> 💡 **记忆锚点**：Locale 体系 = **解析（Resolver）→ 绑定（Holder）→ 查词（MessageSource）→ 格式化（MessageFormat）**——四环节两个在 web 模块（Resolver/Holder 的 Web 部分）、两个在 context 模块（Holder 基础 + MessageSource），回答归属问题时按此分层。

## 4. Resource 抽象速查

`Resource` 是 Spring 对"可读取资源"的统一抽象（**接口定义在 spring-core 的 `org.springframework.core.io`**）：

```text
Resource（getInputStream / getFilename / exists / getURI ...）
├── ClassPathResource       classpath:xxx       类路径资源
├── FileSystemResource      file:/path/xxx      文件系统
├── UrlResource             http:// / https:// / ftp://  URL 资源
├── ByteArrayResource       -                    字节数组内存资源
├── InputStreamResource     -                    一次性输入流
└── WritableResource        FileSystemResource 实现（可写）

加载器：
  ResourceLoader.getResource("classpath:...")       按前缀解析（前缀缺省取决于实现）
  ResourcePatternResolver.getResources("classpath*:**/*.xml")  模式解析 ★
  PathMatchingPatternResourceResolver：ant 风格通配 ? * ** {var}
```

| 前缀 | 语义 |
|------|------|
| `classpath:` | 类路径单资源 |
| `classpath*:` | **全类路径扫描**（多 jar 内同名资源全收集） |
| `file:` | 文件系统 |
| `http(s):` / `url:` | 远程 URL |
| 无前缀 | 依加载器实现而定（Web 下为 ServletContext 路径） |

> 🎯 **核心要点**：`classpath*:` 与 `classpath:` 的差异是高频考点——前者扫描**所有**类路径（多 jar 同名资源全部返回），后者只取**第一个**；扫描配置类、自动配置文件（`spring.factories`、`META-INF/spring.components`）都用前者。

### 4.1 Resource 常用方法速查与陷阱

| 方法 | 语义 | 陷阱 |
|------|------|------|
| `getInputStream()` | ✅ 通用读取入口 | **唯一跨实现安全**的方法 |
| `getFile()` | 仅文件系统资源有效 | jar 内抛 `FileNotFoundException`（见第 5 节） |
| `exists()` | 是否存在 | classpath 资源在 jar 内也可判断（读索引） |
| `isReadable()` | 可读性（含压缩包内） | 与 exists 语义不同 |
| `contentLength()` | 长度 | 流式资源（InputStreamResource）未知返回 -1 |
| `lastModified()` | 修改时间 | 某些远程资源不支持 |
| `getURI()` / `getURL()` | 定位 | jar 内是 `jar:file:...` 形式 |
| `getDescription()` | 调试描述 | **日志展示用**，跨实现稳定 |
| `createRelative(relative)` | 相对资源 | 路径基准按资源自身位置 |
| `WritableResource.getOutputStream()` | 写入（FileSystemResource） | 只读资源抛异常 |

```java
// 资源存在性判断与读取（安全姿势）
Resource r = new ClassPathResource("config/app.properties");
if (r.exists()) {
    try (InputStream in = r.getInputStream()) {
        Properties props = new Properties();
        props.load(in);                       // 或 StreamUtils.copyToString
    }
} else {
    log.warn("配置资源缺失: {}", r.getDescription());
}
```

> 💡 **实现选择**：读"打包后仍存在"的资源统一 `getInputStream()`；本地开发临时写文件用 `FileSystemResource`；要按"根目录 + 相对路径"多次定位用 `PathResource`（NIO，7.x 推荐）。

### 4.2 Resource 与各模块的配合实战

| 场景 | 用法 | 说明 |
|------|------|------|
| 读取 SQL 脚本初始化 | `new ClassPathResource("db/schema.sql")` + ScriptUtils | 测试库建表标准姿势 |
| 读取模板内容 | @Value 注入 Resource → getInputStream → 模板引擎渲染 | 见第 5 节 |
| 加载证书/密钥 | `classpath:cert/*.pem` 或 file: 外部路径 | 注意密钥不入制品（见 5.1） |
| 读取配置文件组 | `classpath*:config/*.properties` 批量 | 多 jar 合并 |
| 访问外部目录 | `file:/opt/app/conf/` + `FileSystemResource` | 运维挂载目录 |
| 测试资源 | Spring Test 的 `@Value("classpath:test-data.json")` | 测试内注入 |

```java
// 实战：批量加载 SQL 脚本并按序执行（初始化种子数据）
Resource[] scripts = new PathMatchingPatternResourceResolver()
        .getResources("classpath*:db/migration/*.sql");
Arrays.sort(scripts, Comparator.comparing(Resource::getFilename));
for (Resource script : scripts) {
    try (InputStream in = script.getInputStream()) {
        String sql = StreamUtils.copyToString(in, StandardCharsets.UTF_8);
        jdbcTemplate.execute(sql);   // 注意：生产用 Flyway/Liquibase，别手写
    }
}
```

> 💡 **边界提醒**：资源加载是**只读定位**——写文件场景（日志、临时目录）不要用 classpath 前缀（打包后目录只读），统一走 `file:` 外部路径或 `PathResource`（`java.nio.file`）指向明确目录。

## 5. 模式加载与 @Value 注入资源

```java
// ① @Value 注入 Resource（最常用，Spring 自动用 ResourceEditor 转换）
@Service
public class TemplateService {
    @Value("classpath:templates/email.html")
    private Resource emailTemplate;

    public String read() throws IOException {
        return Files.readString(emailTemplate.getFile().toPath());   // 或 getInputStream()
    }
}

// ② 注入 ResourceLoader 按需加载
@Service
public class FileService {
    private final ResourcePatternResolver resolver = new PathMatchingPatternResourceResolver();

    public List<String> loadMappers() throws IOException {
        Resource[] rs = resolver.getResources("classpath*:mapper/*.xml");
        return Arrays.stream(rs).map(Resource::getDescription).toList();
    }
}

// ③ 读取文件内容的安全姿势：getInputStream + StreamUtils（不依赖 getFile 存在性）
String content = StreamUtils.copyToString(res.getInputStream(), StandardCharsets.UTF_8);
```

> ⚠️ **典型坑**：打包成 jar 后 `resource.getFile()` 抛 `FileNotFoundException`（类路径资源在 jar 内不是文件）——**统一用 `getInputStream()`** 读取；`getDescription()` 用于日志展示。

### 5.1 资源加载生产实践与面试追问

**生产实践清单**：

| 实践 | 说明 |
|------|------|
| 资源路径统一前缀化 | `classpath:` 显式声明，避免依赖加载器默认行为（Web 下默认为 ServletContext 路径，纯 context 下为 classpath——行为不一致） |
| 模板文件放 `src/main/resources/templates` | 与代码分离，打包进 jar 后可读 |
| 敏感资源禁止进 classpath | 数据库口令、密钥走环境变量/密钥管理（classpath 资源随制品分发） |
| 多 jar 同名资源合并 | 用 `classpath*:` + 业务前缀命名空间（`META-INF/services/` 风格） |
| 资源读取一律 try-with-resources | InputStream 泄漏是资源类代码最常见的 bug |

**面试追问速答**：

| 追问 | 答题锚点 |
|------|---------|
| "@Value 注入 Resource 怎么实现的？" | 属性编辑器 `ResourceEditor`（PropertyEditor）把字符串按前缀转成对应 Resource 实现 |
| "classpath*: 的实现原理？" | `PathMatchingPatternResourceResolver` 遍历 classloader 全部 URL（`getResources`）再逐个匹配 ant 模式 |
| "jar 内资源还能用 getFile 吗？" | 能但只在 `file:` 协议下（spring-boot 打包的 BOOT-INF 结构下**不行**）——统一 getInputStream |
| "为什么推荐 @Value 注入而非自己 new Resource？" | 前者由容器统一解析（相对路径、前缀、编码都由容器决定），后者要自己处理加载器差异 |
| "Resource 与 Path/File 的关系？" | Resource 是**定位器**（可延迟解析），File/Path 是**具体文件**；Resource 可通过 getInputStream 统一转流 |

> 🎯 **一句话总结**：资源层的核心心法 = **"先定位（Resource 抽象）、后读取（getInputStream）、再关闭（try-with-resources）"**——前缀决定定位方式，方法决定跨环境安全性。

### 5.2 资源读取与编码实战（文本资源统一姿势）

```java
// 读文本资源的统一安全姿势：显式编码 + try-with-resources
public static String readText(Resource res) throws IOException {
    try (InputStream in = res.getInputStream()) {
        return new String(in.readAllBytes(), StandardCharsets.UTF_8);
    }
}

// @Value 注入 + 懒读取（避免启动期 IO 阻塞）
@Component
public class SqlLoader {
    @Value("classpath:sql/init.sql")
    private Resource initSql;          // 注入的是定位器，不触发读取

    public void load(JdbcTemplate jdbc) {
        String sql = readText(initSql);   // 用时才打开流
    }
}
```

| 坑 | 表现 | 对策 |
|----|------|------|
| 编码未指定 | 中文乱码（随平台默认编码漂移） | **永远显式 StandardCharsets.UTF_8** |
| 启动期读大资源 | 启动变慢 | @Value 注入定位器，运行时懒读 |
| 资源不存在不检查 | IO 异常运行时才炸 | 启动校验 `exists()`（测试环境尽早暴露） |
| 重复读取 | 流已消费 | 每次 `getInputStream()` 重新打开（资源本身可重开，勿缓存流） |

> 💡 **边界认知**：`@Value("classpath:...")` 注入的是**Resource 定位器**（不读内容）——需要启动期校验时，可在 `@PostConstruct` 里调 `exists()`；文本读取务必显式编码，这是资源代码里最高频的隐性 bug。
