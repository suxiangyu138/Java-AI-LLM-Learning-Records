## 1. 事件体系四件套

| 组件 | 职责 |
|------|------|
| `ApplicationEvent` | 事件对象（携带业务数据） |
| `ApplicationEventPublisher` | 发布器：`publishEvent(Object)`（ApplicationContext 即发布器） |
| `ApplicationListener<E>` | 经典监听接口：`onApplicationEvent(E)` |
| `SimpleApplicationEventMulticaster` | 多播器：把事件分发给所有匹配监听器（线程模型在此） |

```text
publishEvent(event)
  → AbstractApplicationContext.getApplicationEventMulticaster()
  → SimpleApplicationEventMulticaster.multicastEvent
  → 按事件类型过滤监听器（ResolvableType 精确匹配，含泛型）
  → 逐个 invokeListener（默认同步，可配 TaskExecutor 异步）
```

> 🎯 **核心要点**：事件机制 = **发布-订阅解耦**（事件源不知监听者存在）；事件分发的核心 `SimpleApplicationEventMulticaster` 在 refresh 第 8 步创建——**注册监听器前发布的事件会被暂存，刷新完成时补发**（早期事件机制）。

### 1.1 多播器内部机制源码级细节

```text
multicastEvent(event, eventType) 的执行链：
  1. 若设置了 taskExecutor → 每个监听器提交异步任务（线程池执行）
  2. 否则当前线程同步逐个调用
  3. 取监听器集合：getApplicationListeners(event, type)
     → 按 ResolvableType 匹配（泛型精确匹配：Listener<OrderCreatedEvent> 只收 OrderCreatedEvent）
     → 结果存入 ConcurrencyHashMap 缓存（listenerCache，按事件类型为 key）
  4. 逐个 invokeListener → 包装成 ErrorHandler 执行（默认无 ErrorHandler 则原样抛出）
```

**监听器匹配的边界细节**：

| 场景 | 是否触发 |
|------|---------|
| 监听器类型 = 事件类型 | ✅ |
| 监听器类型 = 事件**父类**（如 `ApplicationEvent`） | ✅ 通配（监听 ApplicationEvent = 收所有事件） |
| 监听器类型 = 事件**子类**（如监听 OrderCreatedEvent，发布 PayloadApplicationEvent 包装） | ⚠️ 需注意 POJO 包装后的类型匹配（见 1.1 节） |
| 泛型参数不同的同类（`GenericEvent<String>` vs `GenericEvent<Integer>`） | ✅ ResolvableType 区分（不会误触发） |
| 事件是 null | 发布空事件直接 NPE 前校验——`publishEvent(null)` 抛 `IllegalArgumentException` |

> 💡 **性能提示**：监听器匹配有缓存——首次发布某类型事件后，该类型的匹配结果被缓存（`listenerCache`），后续发布 O(1) 查缓存；所以"运行时动态增删监听器"（`addApplicationListener` 在 refresh 后调用）可能命中旧缓存，需手动 `multicaster.clearCache()` 或避免运行期注册。**常规应用感知不到，但这是"动态监听为什么有时不生效"的根因**。

### 1.2 事件对象设计最佳实践

| 设计要点 | 推荐 | 反例 |
|---------|------|------|
| 继承 `ApplicationEvent` 还是 POJO | 4.2+ 直接 POJO（record） | 老代码习惯继承——`ApplicationEvent` 的子类在序列化/日志上无额外收益 |
| 字段 | **不可变**（record/final） | 可变字段在异步监听下产生竞态 |
| 命名 | 语义化过去式：`OrderCreatedEvent` | `OrderEvent`（含义模糊） |
| 内容 | 只带**业务标识与必要载荷**（ID、金额） | 携带整个实体（大对象 + 序列化成本） |
| 时间戳 | 需要时显式加 `Instant createdAt` | 依赖监听侧自己取时间（不一致） |
| 继承体系 | 按领域建事件族：`OrderEvent` ← `OrderCreatedEvent` | 平铺无层次（监听父类型能力缺失） |

```java
// 推荐：record + 领域父接口（监听通配）
public sealed interface OrderEvent permits OrderCreatedEvent, OrderShippedEvent {
    Long orderId();
}
public record OrderCreatedEvent(Long orderId, BigDecimal amount,
                                Instant createdAt) implements OrderEvent { }

// 监听父接口 = 监听一族事件
@EventListener
public void onOrderChanged(OrderEvent e) { ... }   // 收创建 + 发货
```

> 🎯 **设计心法**：事件是**领域语言的一部分**（DDD 术语叫领域事件）——事件命名来自"已经发生的事实"（过去式），载荷只放"下游需要的"；把事件设计成"快照 + 标识"而不是"对象引用"，异步与持久化场景（outbox）才能安全复用。

## 2. 发布与监听的三种写法

```java
// 事件对象（继承 ApplicationEvent，或 4.2+ 直接发布任意 POJO）
public record OrderCreatedEvent(Long orderId, BigDecimal amount) { }

// 发布：注入发布器（ApplicationContext 本身也是发布器）
@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;   // 注入接口而非上下文！

    public void create(Order order) {
        // ...业务逻辑
        publisher.publishEvent(new OrderCreatedEvent(order.getId(), order.getAmount()));
    }
}
```

| 监听写法 | 示例 | 说明 |
|---------|------|------|
| 接口 | `class L implements ApplicationListener<OrderCreatedEvent>` | 经典，必须注册为 Bean |
| 注解 | `@EventListener public void on(OrderCreatedEvent e)` | ✅ 现代首选，零接口 |
| 泛型 | `@EventListener public void onGeneric(GenericEvent<String> e)` | 泛型事件精确匹配 |

```java
// 注解监听（推荐）：监听器与事件源完全解耦
@Component
public class OrderEventHandlers {
    @EventListener
    public void onCreated(OrderCreatedEvent e) {
        log.info("订单 {} 创建，金额 {}", e.orderId(), e.amount());
        // 通知、积分、审计等横切业务
    }
}
```

> ⚠️ **解耦边界**：监听器里**不要再回发消息**给事件源（易成环）；跨服务同步等待用命令模式 + 返回值，事件只做"单向通知"。监听器异常默认由多播器抛出——见第 5 节。

### 2.1 监听器注册的两条路径与实战要点

```text
路径一（接口监听器）：ApplicationListener<X> 实现类注册为 Bean
  → refresh 第 10 步 registerListeners() 从 BeanFactory 里按类型拉取，静态注册

路径二（注解监听器）：@EventListener 方法所在 Bean
  → EventListenerMethodProcessor（BeanFactoryPostProcessor）收集方法
  → 每个方法包装成 ApplicationListenerMethodAdapter 注册
  → 该 Processor 在 refresh 第 5 步注册、**第 11 步实例化监听器 Bean 后生效**
```

| 实战要点 | 说明 |
|---------|------|
| 监听器 Bean 是懒加载 | 事件永远不触发（懒加载 Bean 不被实例化，监听器不注册） |
| 监听器 Bean 依赖事件源 Bean | 相互注入需注意循环依赖（用 @Lazy 打破） |
| 同一方法监听多事件 | `@EventListener({A.class, B.class})` 参数须为公共父类型 |
| 条件监听 | `@EventListener(condition = "#e.amount > 100")` SpEL 过滤 |
| 返回值即新事件 | 监听方法返回值非 void → 自动作为新事件再发布（链式事件） |

```java
// 条件监听 + 返回值转发（事件链）
@EventListener(condition = "#e.amount().compareTo(BigDecimal.valueOf(100)) >= 0")
public OrderShippedEvent onBigOrder(OrderCreatedEvent e) {
    return new OrderShippedEvent(e.orderId());   // 返回非 void → 自动发布新事件
}
```

> ⚠️ **返回值事件链的坑**：返回值只支持**一个对象**（多事件用集合/数组）；转发的新事件同样走完整匹配与缓存流程；若返回值类型与监听器参数类型相同会造成死循环（无限转发）——生产上事件链要控制深度，最好显式 `publishEvent` 而非依赖隐式返回。

## 3. 事务事件：@TransactionalEventListener

| 阶段 | 触发时机 |
|------|---------|
| `AFTER_COMMIT`（默认） | 事务成功提交后 |
| `AFTER_ROLLBACK` | 事务回滚后 |
| `AFTER_COMPLETION` | 提交或回滚后（不区分） |
| `BEFORE_COMMIT` | 提交前（在事务内） |

```java
@Component
public class OrderEventHandlers {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onCommitted(OrderCreatedEvent e) {
        // 事务已提交才执行：发消息、通知下游——避免"事务回滚了但副作用已发出"
        mq.send(...);
    }
}
```

> 🎯 **核心要点**：`AFTER_COMMIT` 监听 = "事务成功才做副作用"的**事务边界解耦**——分布式一致性的本地兜底（配合 outbox 模式更稳）；注意：**无事务执行时默认不触发**（`fallbackExecution = true` 可回退为普通监听）。

### 3.1 事务事件的边界与组合坑

| 边界场景 | 行为 | 应对 |
|---------|------|------|
| 监听方法所在 Bean 无事务 | **默认不触发**（静默，无日志） | `fallbackExecution = true` 降级为普通监听；或确认发布方在事务内 |
| 与 `@Async` 组合 | 事务已提交但异步线程执行——提交时机可能错位 | 先提交事务（AFTER_COMMIT）再异步发送消息，**不要**在监听方法上叠 @Async 做"事务内异步" |
| 事务监听器内再开新事务 | 新事务独立提交（REQUIRED 传播下加入原事务须在提交前） | 监听器里的事务与主事务已分离，注意隔离语义 |
| 发布事件在事务回滚路径上 | 事件已发布但 AFTER_COMMIT 不触发 | 业务结果以事务为准；回滚补偿逻辑放 AFTER_ROLLBACK |
| 多数据源/多事务管理器 | 事件绑定的是**当前线程事务** | 明确事务管理器；XA/分库场景慎用 |

```java
// 生产推荐组合：事务提交 → 事件 → outbox 落库 → 异步投递（可靠事件）
@Transactional
public void createOrder(Order order) {
    orderRepo.save(order);
    outboxRepo.save(new Outbox(OrderCreatedEvent.class, serialize(event)));  // 同事务落 outbox
}
@EventListener(condition = "#e instanceof T(com.example.OrderCreatedEvent)")
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void publishOutbox(OrderCreatedEvent e) {
    outboxSender.sendPending();   // 提交后才投递，失败可重试
}
```

> 💡 **面试总结**：事务事件解决的是"**副作用与事务同生共死**"问题——核心机制是 `TransactionSynchronization`（事务同步管理器）在提交/回滚点触发回调；这也是 Outbox、发消息、写缓存等"事务后动作"的标准实现底座。

## 4. 异步事件与执行器

```java
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean
    public Executor eventTaskExecutor() {
        return new ThreadPoolTaskExecutor();   // 配置核心/最大线程、队列、拒绝策略
    }
}

// 方式一：@EventListener + @Async（方法级，需 @EnableAsync）
@Component
public class Handlers {
    @EventListener
    @Async
    public void onCreated(OrderCreatedEvent e) { ... }   // 异步执行
}

// 方式二：多播器全局配执行器（所有事件异步）
@Component
public class MulticasterConfig {
    @Bean
    public ApplicationEventMulticaster applicationEventMulticaster(
            Executor taskExecutor) {
        SimpleApplicationEventMulticaster mc = new SimpleApplicationEventMulticaster();
        mc.setTaskExecutor(taskExecutor);
        return mc;
    }
}
```

> ⚠️ **异步代价**：① 异常默认吞掉（异步线程抛出，主线程感知不到）——需要 `ErrorHandler`；② 线程切换丢失事务上下文（`@TransactionalEventListener` 与 `@Async` 组合时提交时机错位）；③ 事件顺序不再保证。**默认同步是正确选择**，仅对"可延迟、可失败"的事件开异步。

### 4.1 异步事件线程池生产参数

| 参数 | 建议值 | 理由 |
|------|--------|------|
| `corePoolSize` | 2-4 | 事件处理多为轻量任务，核心线程无需多 |
| `maxPoolSize` | 8-16 | 突发事件批量到来时的弹性上限 |
| `queueCapacity` | 500-2000 | 队列过大 → 积压延迟；过小 → 触发拒绝 |
| `keepAliveSeconds` | 60 | 闲时回收弹性线程 |
| 拒绝策略 | `CallerRunsPolicy` | **事件不能丢**——由发布线程兜底执行（同步退化） |
| 线程名前缀 | `event-` | 日志/监控可辨识 |
| 监视器 | 队列深度/拒绝计数告警 | 积压 = 监听器慢，先查业务再扩池 |

```java
@Bean("eventExecutor")
public Executor eventExecutor() {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.setCorePoolSize(4);
    ex.setMaxPoolSize(16);
    ex.setQueueCapacity(1000);
    ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    ex.setThreadNamePrefix("event-");
    ex.initialize();
    return ex;
}
```

> ⚠️ **决策建议**：先问三个问题再决定是否异步——① 事件失败能容忍吗？（不能 → 同步或 outbox 重试）② 事件必须有序吗？（必须 → 同步或单线程队列）③ 响应时间敏感吗？（不敏感 → 异步）。**默认同步、按需异步**，异步事件必须有监控兜底（线程池指标 + 错误日志），否则等于把故障藏起来。

## 5. 监听器顺序与异常处理

```java
@Component
public class Handlers {
    @EventListener
    @Order(1)                    // 数值小先执行；接口监听器实现 Ordered 同理
    public void first(OrderCreatedEvent e) { ... }

    @EventListener
    @Order(2)
    public void second(OrderCreatedEvent e) { ... }
}
```

| 问题 | 行为 | 对策 |
|------|------|------|
| 监听器抛异常 | 默认向发布线程抛出，**后续监听器中断** | 监听器内 try-catch；或 `ErrorHandler` 兜底 |
| 异步监听异常 | 线程池吞掉 | 配置 `TaskExecutor` 的 `ErrorHandler` 并监控 |
| 监听顺序不明确 | 不保证 | `@Order` / `Ordered` |
| 重复消费 | 无去重（非消息队列语义） | 业务幂等 |

> 💡 面试辨析：Spring 事件 ≠ 消息队列——事件**进程内同步/异步分发**，无持久化、无重试、无多节点；跨服务用 MQ（见消息队列系列）。事件用于"同进程内模块解耦"，MQ 用于"跨进程可靠投递"。

### 5.1 全局 ErrorHandler 完整示例（异步事件异常兜底）

```java
@Component
public class EventErrorHandler implements ErrorHandler {
    private final MeterRegistry registry;        // 或直接 Logger

    @Override
    public void handleError(Throwable t) {
        // 异步事件异常的唯一落点：必须记录 + 告警，否则事件"静默丢失"
        log.error("事件处理失败: {}", t.getMessage(), t);
        registry.counter("event.error", "class", t.getClass().getSimpleName())
                .increment();
    }
}

// 接入：多播器配置 ErrorHandler（见第 4 节方式二）
@Bean
public ApplicationEventMulticaster applicationEventMulticaster(
        @Qualifier("eventExecutor") Executor executor,
        ErrorHandler errorHandler) {
    SimpleApplicationEventMulticaster mc = new SimpleApplicationEventMulticaster();
    mc.setTaskExecutor(executor);
    mc.setErrorHandler(errorHandler);      // 同步模式同样生效
    return mc;
}
```

| 模式 | 异常去向 | 后续监听器 |
|------|---------|-----------|
| 同步 + 无 ErrorHandler | 抛回发布线程（业务可 catch） | 中断 |
| 同步 + ErrorHandler | 交给 handler，发布线程无感 | 继续执行 |
| 异步 + 无 ErrorHandler | **静默丢失**（线程池吞掉） | 各自独立 |
| 异步 + ErrorHandler | 交给 handler + 告警 | 各自独立 |

> 🎯 **生产铁律**：异步事件的错误处理**必须有显式落点**——ErrorHandler 里记日志 + 打指标 + 可选告警；否则故障排查时事件处理失败将完全不可见，表现为"功能偶发缺失"的疑难杂症。

### 5.2 测试中的事件验证（不依赖异步时序）

```java
@SpringBootTest
class EventTests {
    @Autowired private ApplicationEventPublisher publisher;

    @Test
    void listenerShouldFireOnPublish() {
        // 方式一：真实监听（同步事件，直接可断言）
        publisher.publishEvent(new OrderCreatedEvent(1L, BigDecimal.TEN));
        // 断言业务副作用（如积分记录）

        // 方式二：收集器（验证是否收到某类型事件）
        AtomicReference<OrderCreatedEvent> captured = new AtomicReference<>();
        TestApplicationListener listener = new TestApplicationListener(captured);
        // 注入收集器实现并发布后断言 captured 值
    }
}
```

| 测试关注点 | 建议 |
|-----------|------|
| 同步事件链路 | 直接发布 + 断言副作用（同步无时序问题） |
| 异步事件 | 用 `CountDownLatch`/Awaitility 等待，避免 `Thread.sleep` |
| 事务事件 | `@Transactional` 测试方法内发布 → 提交后断言；回滚场景单独用例 |
| 监听器未注册 | 断言"发布后无效果"（验证注册路径） |
| 事件顺序 | `@Order` 场景用记录型监听器按序收集断言 |

> 💡 **测试边界**：Spring 事件是进程内同步/异步分发——测试中**不需要 mock 发布器**（直接用真实多播器即可）；要 mock 的是事件里的外部副作用（发消息、调外部 API），即"监听器内部依赖"。这个边界想清楚，事件测试就简单了。

## 6. 内建事件（生命周期事件）

| 事件 | 触发时机 | 常见用途 |
|------|---------|---------|
| `ContextRefreshedEvent` | refresh() 完成（含多次刷新） | 启动后一次性初始化（预热缓存/注册表） |
| `ContextStartedEvent` / `ContextStoppedEvent` | start() / stop() | Lifecycle 协同 |
| `ContextClosedEvent` | close() | 优雅停机收尾 |
| `RequestHandledEvent` | Web 请求完成（web 模块） | 审计 |

```java
@Component
public class StartupTasks {
    @EventListener(ContextRefreshedEvent.class)
    public void onReady() {
        // 全部单例就绪后执行（比 @PostConstruct 晚，可安全使用任意 Bean）
        cache.preload();
    }
}
```

> 💡 监听 `ContextRefreshedEvent` 是"启动后收尾任务"的标准姿势——此时 refresh 十二步全部完成、单例全部实例化、代理全部就位；注意多上下文（父子）场景可能触发多次，用 `ApplicationContext` 判断或 `@Order` 规避。

### 6.1 生命周期事件边界与多上下文场景

| 场景 | 事件行为 | 注意点 |
|------|---------|--------|
| 单上下文 | 各事件各触发一次 | 标准场景无坑 |
| 父子容器 | **父 refresh 时子容器事件也补发**——子容器的事件监听器可能收到父的 ContextRefreshedEvent | 用 `event.getApplicationContext()` 判断来源 |
| refresh 二次执行（少见） | ContextRefreshedEvent 再次触发 | 监听器做幂等（预热逻辑可重复执行） |
| close 后重新 start | ContextStoppedEvent → ContextClosedEvent 顺序 | Lifecycle 协同场景 |
| 测试框架多上下文缓存 | 每个缓存上下文都发布一次事件 | 测试断言注意上下文隔离 |

```java
// 多上下文下过滤：只处理本容器的刷新
@Component
public class StartupTasks {
    private final ApplicationContext self;    // 注入自身上下文

    @EventListener(ContextRefreshedEvent.class)
    public void onReady(ContextRefreshedEvent e) {
        if (e.getApplicationContext() != self) {
            return;   // 子容器收到父容器事件 → 忽略
        }
        cache.preload();                      // 幂等设计仍然推荐
    }
}
```

> 🎯 **面试追问三连**（事件专题收尾）：
> ① "事件发布是同步还是异步？"——默认同步（当前线程、按序），异步需显式配置多播器 TaskExecutor 或 @Async；
> ② "同步事件中监听器抛异常会怎样？"——异常上抛、后续监听器中断（有 ErrorHandler 则吞并继续）；
> ③ "事件能跨 JVM 吗？"——不能，进程内机制；跨进程是 MQ 的领域。
> 答题公式：**发布-订阅 → 多播器分发 → 事务/异步边界 → 与 MQ 的边界**。
