## 1. BeanFactory 接口家族

```text
BeanFactory（最高抽象：getBean/containsBean/isSingleton/获取类型）
  ├── HierarchicalBeanFactory（父子容器：getParentBeanFactory）
  │     └── ConfigurableBeanFactory（别名、作用域注册、类加载器）→ 实现于 AbstractBeanFactory
  ├── ListableBeanFactory（批量：getBeansOfType / getBeanNamesForType）
  │     └── ConfigurableListableBeanFactory → 实现于 DefaultListableBeanFactory ★
  └── AutowireCapableBeanFactory（程序化装配：autowireBean / initializeBean / applyBeanPostProcessors）

DefaultListableBeanFactory  = Listable + Configurable + AutowireCapable（全家桶 ★）
```

| 接口/类 | 职责 | 面试频率 |
|--------|------|:---:|
| `BeanFactory` | 顶层工厂：`getBean(String)` 等 10 个方法 | ★★★ |
| `ListableBeanFactory` | 枚举能力：`getBeansOfType(T)` 拿全部类型 Bean | ★★★ |
| `HierarchicalBeanFactory` | 父子容器委派（子找不到问父） | ★★ |
| `AutowireCapableBeanFactory` | 给"非容器对象"做注入：`autowireBean(obj)` | ★★ |
| `DefaultListableBeanFactory` | **唯一主流实现**：一切注册表/工厂能力集大成 | ★★★ |
| `StaticListableBeanFactory` | 测试用静态清单工厂 | ★ |

**经典代码路径**（面试默写）：`getBean(name)` → `AbstractBeanFactory.doGetBean` → 单例缓存查找 → 创建 → `AbstractAutowireCapableBeanFactory.createBeanInstance` → `populateBean` → `initializeBean`。

### 1.1 getBean 完整调用链（源码级）

```text
getBean(name)
 └─ AbstractBeanFactory.doGetBean
     ├─ 转换别名 → 解析 & 前缀（FactoryBean 请求）
     ├─ ① 单例缓存查：getSingleton(name)（三级缓存，见第 3 节）
     ├─ ② 父容器委派：getParentBeanFactory().getBean（Hierarchical 语义）
     ├─ ③ 依赖优先创建：dependsOn 的 Bean 先 getBean
     ├─ ④ 按 scope 创建：
     │    singleton → getSingleton(name, ObjectFactory)   ← 创建后入 1 级缓存
     │    prototype → createBean 直接返回（不缓存）
     ├─ ⑤ createBean → AbstractAutowireCapableBeanFactory
     │    → resolveBeforeInstantiation（后处理器短路？）
     │    → createBeanInstance（推断构造器 / 工厂方法）
     │    → populateBean（属性填充 + @Autowired 注入）
     │    → initializeBean（Aware → 初始化三写法 → 代理）
     └─ ⑥ 类型转换：按目标类型匹配后返回
```

> 🎯 背诵锚点：**doGetBean 的"先查缓存、再问父容器、再创建"** 是面试手写 getBean 流程的黄金开头；后半段"实例化 → 填充 → 初始化"与 [05-生命周期](05-Bean生命周期与作用域速查.md) 的时序表完全对应。

### 1.2 面试追问：为什么主流实现只有 DefaultListableBeanFactory？

- 它同时实现 `ListableBeanFactory`（枚举）、`ConfigurableListableBeanFactory`（可配置）、`BeanDefinitionRegistry`（注册表）、`AutowireCapableBeanFactory`（程序化装配）——**一个对象覆盖全部角色**；
- `ApplicationContext` 内部持有的就是它（如 `AnnotationConfigApplicationContext` 内嵌一个 `DefaultListableBeanFactory`）；
- 支持定义覆盖开关、`getBeanNamesForType` 的解析缓存（内部用 lambda 延迟解析类型），批量查找性能好。

> ⚠️ 使用注意：直接 new 一个 `DefaultListableBeanFactory` 时没有 `refresh()` 流程——`@Autowired` 解析器、`@Value` 占位符等都不会自动注册；裸工厂只有"手动注册 + 手动 getBean"的原始能力。

### 1.3 接口家族的选型速查

| 我的需求 | 用哪个接口 |
|---------|-----------|
| 只拿 Bean（最简依赖） | `BeanFactory` |
| 枚举全部类型 Bean | `ListableBeanFactory` |
| 父子容器委派 | `HierarchicalBeanFactory` |
| 给非容器对象做注入 | `AutowireCapableBeanFactory.autowireBean(obj)` |
| 程序化创建并走完整生命周期 | `AutowireCapableBeanFactory.createBean` / `initializeBean` |

```java
// 经典程序化装配：把现有对象接入容器生命周期
AutowireCapableBeanFactory acf = ctx.getAutowireCapableBeanFactory();
SomeService service = new SomeService();        // 容器外创建
acf.autowireBean(service);                       // 注入依赖
acf.initializeBean(service, "someService");      // 执行 Aware/初始化回调
```

> 💡 面试加分：`autowireBean` 是"第三方对象借用容器能力"的官方入口——AOP 手动织入、遗留代码改造常靠它；但注意它**不注册**进容器，生命周期只到初始化为止。

## 2. BeanDefinition 体系

| 类/接口 | 职责 |
|--------|------|
| `BeanDefinition` | 接口：class/scope/lazyInit/initMethod/destroyMethod/属性集合/`isSingleton` 等 |
| `GenericBeanDefinition` | 通用实现（现代默认使用） |
| `RootBeanDefinition` | 完整合并后的定义（合并后实际使用的形态） |
| `ChildBeanDefinition` | 父子继承定义（parent/child，旧式） |
| `AnnotatedGenericBeanDefinition` | 从注解类生成的定义（`AnnotationConfigApplicationContext.register` 内部） |
| `ScannedGenericBeanDefinition` | 组件扫描产物（来自 `ClassPathScanningCandidateComponentProvider`） |
| `ConfigurationClassBeanDefinitionReader` | 由 `@Bean` 方法生成的定义 |

> 🎯 **核心要点**：BeanDefinition = Bean 的"图纸"，**配置文件/注解/扫描最终都翻译成 BeanDefinition**；`getBean` 时按图纸合并（`RootBeanDefinition`）→ 实例化 → 填充 → 初始化。

**关键属性速查**：

```text
scope（singleton/prototype）、abstract、lazyInit、autowireMode、initMethodName、
destroyMethodName、primary、fallback（7.0 新增）、dependsOn、role（infrastructure）、
description、factoryMethodName / factoryBeanName（@Bean 落点）
```

### 2.1 BeanDefinition 的合并（getMergedLocalBeanDefinition）

```text
父定义（parent）  ──┐
子定义（child）   ──┼─→ 合并 → RootBeanDefinition（最终执行图纸）
GenericBeanDefinition ──┘
```

- 合并时机：首次 `getBean` 时经 `getMergedBeanDefinition` 合并并缓存，后续直接复用；
- 合并内容：class / scope / 属性集合 / 初始化方法等**全量拷贝覆盖**，子定义的同名属性胜出；
- 面试考点：`@Bean` 方法定义由 `ConfigurationClassBeanDefinitionReader` 生成时**直接是 `RootBeanDefinition`**——"生而为根"，无需再合并；`@Component` 扫描产物（`ScannedGenericBeanDefinition`）则在 getBean 时才合并。

### 2.2 手工构建 BeanDefinition（旧式程序化注册）

```java
GenericBeanDefinition bd = new GenericBeanDefinition();
bd.setBeanClass(UserService.class);
bd.setScope(ConfigurableBeanFactory.SCOPE_PROTOTYPE);
bd.setInitMethodName("init");
bd.setPropertyValues(new MutablePropertyValues().add("maxRetry", 3));

DefaultListableBeanFactory factory = new DefaultListableBeanFactory();
factory.registerBeanDefinition("userService", bd);   // 图纸入库
UserService us = factory.getBean(UserService.class);
```

> ⚠️ 7.0 起此写法被 `BeanRegistrar` 取代（见第 6 节）：手工定义容易漏属性（如漏 `factoryMethodName` 导致 `@Bean` 语义丢失），且无法参与 AOT 优化——新代码请走 `registerBean` 高 API。

### 2.3 面试追问：GenericBeanDefinition 与 RootBeanDefinition 的区别？

| 维度 | GenericBeanDefinition | RootBeanDefinition |
|------|----------------------|-------------------|
| 定位 | 通用容器，可作父可作子 | 合并后的"最终形态" |
| 来源 | 扫描 / 手工注册 | 合并产物 / @Bean 方法 |
| 属性语义 | 未合并（含 parent 指针） | 已合并（可执行） |
| 缓存 | 不缓存合并结果 | 合并后按名称缓存 |

> 🎯 一句话：**Generic 是"待合并的图纸"，Root 是"可执行的图纸"**——容器运行时只认 Root。

## 3. Registry：注册表

| 接口/类 | 职责 |
|--------|------|
| `BeanDefinitionRegistry` | `registerBeanDefinition(name, bd)` / `removeBeanDefinition` / `containsBeanDefinition` |
| `SimpleBeanDefinitionRegistry` | 仅注册表的最小实现（不创建 Bean） |
| `DefaultListableBeanFactory` | 同时实现 Registry + Factory（同一对象两副面孔） |
| `SingletonBeanRegistry` | 单例注册：`registerSingleton(name, obj)` / `getSingleton`（三级缓存所在） |
| `DefaultSingletonBeanRegistry` | 三级缓存实现（`singletonObjects` / `earlySingletonObjects` / `singletonFactories`）★ |

> ⚠️ 三级缓存的三张 Map 都在 `DefaultSingletonBeanRegistry`——面试问"三级缓存在哪"答此类；其中第三级 `singletonFactories` 只存 `ObjectFactory`（lambda），是为了循环依赖时返回代理前的半成品。

### 3.1 三级缓存 getSingleton 流程（源码级）

```text
getSingleton(beanName, true)
 ├─ singletonObjects.get(name)             → 命中即返回（第 1 级）
 ├─ isSingletonCurrentlyInCreation(name)?
 │   ├─ earlySingletonObjects.get(name)    → 命中即返回（第 2 级）
 │   └─ singletonFactories.get(name)
 │       └─ factory.getObject()            → 生成早期引用（第 3 级）
 │           → 放入 earlySingletonObjects（提升到第 2 级，加速下次）
 └─ 都未命中 → 返回 null → 走完整创建流程
```

| 级别 | Map 名 | 存什么 |
|------|--------|--------|
| 1 | `singletonObjects` | 完整创建的单例 |
| 2 | `earlySingletonObjects` | 已生成过的早期引用（半成品） |
| 3 | `singletonFactories` | `ObjectFactory` lambda（延迟生成） |

> 🎯 面试深一层：第 3 级存 lambda 而非对象，是**延迟 + AOP 一致性**两个理由——绝大多数 Bean 无需提前暴露，不必为每个 Bean 提前判定/创建代理；只有当真正被循环引用时，才在工厂里生成早期引用（此时可能已应用 AOP 代理），保证"早期引用 == 最终 Bean"。

### 3.2 注册表的程序化操作示例

```java
DefaultListableBeanFactory factory = new DefaultListableBeanFactory();

// 注册（定义级）
factory.registerBeanDefinition("ds", new GenericBeanDefinition());
System.out.println(factory.containsBeanDefinition("ds"));   // true

// 注册（实例级）——直接放一个现成对象进单例缓存
factory.registerSingleton("cache", new ConcurrentHashMap<>());
Object cache = factory.getSingleton("cache");               // 命中 1 级缓存

// 移除与清空
factory.removeBeanDefinition("ds");
```

> ⚠️ 区分 `registerBeanDefinition` 与 `registerSingleton`：前者存"图纸"（后续走完整生命周期），后者直接存"成品"（**不再执行生命周期回调**）——测试里常用后者快速塞替身。

## 4. 后处理器家族

| 接口 | 触发时机 | 典型应用 |
|------|---------|---------|
| `BeanFactoryPostProcessor` | 容器启动早期，**所有 BeanDefinition 已注册但未实例化** | 修改/追加 BeanDefinition（`@Profile` 解析器就是它） |
| `BeanDefinitionRegistryPostProcessor` | 继承前者，先触发；还能往 Registry 注册新定义 | 旧式程序化注册（7.0 起被 BeanRegistrar 取代） |
| `BeanPostProcessor` | 每个 Bean **初始化前后**（`postProcessBeforeInitialization` / `After`） | @Autowired 注入、@PostConstruct、AOP 代理创建 |
| `InstantiationAwareBeanPostProcessor` | **实例化前/后 + 属性填充前**（更早插手） | 返回代理替换目标、短路创建 |
| `SmartInstantiationAwareBeanPostProcessor` | 实例化前预判、推测构造器 | 延迟代理、构造器选择（AOP 用它） |
| `SmartInitializingSingleton` | 全部单例创建完成后统一回调 | 一次性初始化聚合逻辑 |

**顺序速记**：

```text
refresh() → BeanFactoryPostProcessor（改图纸）
          → BeanDefinitionRegistryPostProcessor（加图纸，先于 BPP）
          → 逐个实例化单例：
              InstantiationAwareBPP（短路？）→ 构造 → 属性填充 → 各种 Aware
              → postProcessBeforeInitialization（BPP）
              → @PostConstruct / InitializingBean / initMethod
              → postProcessAfterInitialization（BPP，AOP 代理在此）★
          → SmartInitializingSingleton（全量后）
```

> 🎯 **核心要点**：AOP 代理在 `postProcessAfterInitialization` 创建（`AbstractAutoProxyCreator`）——这就是"先有 Bean 后有代理"、"Bean 自调用不走代理"的根因。

### 4.1 后处理器的注册与排序

- **注册时机**：容器启动早期 `registerBeanPostProcessors`（refresh 的第 5 步）——此时 BeanDefinition 已就绪但还没有任何业务 Bean 实例化；
- **排序规则**：实现 `PriorityOrdered` 的 > 实现 `Ordered` 的 > 其余；同类之间按 `getOrder()` 升序（数值小先执行）；
- **同序回退**：同为默认序的后处理器按注册顺序执行——这是"不稳定行为"，业务代码不要依赖。

```java
@Component
public class MyBpp implements BeanPostProcessor, Ordered {
    @Override
    public int getOrder() { return 0; }   // 数值小 → 先执行
    // postProcessBeforeInitialization / postProcessAfterInitialization 实现省略
}
```

> 💡 面试追问"多个 BPP 的执行顺序怎么控制"：实现 `Ordered` 或标注 `@Order`，数值越小越先执行；与 AOP 的 `AbstractAutoProxyCreator` 比较顺序时要清楚——它在初始化**之后**阶段，所以代理总会"包住"初始化完成的 Bean。

### 4.2 为什么 BPP 本身也是 Bean？

容器创建 Bean 需要 BPP 参与，但 BPP 自己也是 Bean——"鸡生蛋"问题。Spring 的解法：

```text
refresh() → registerBeanPostProcessors：
  先用"框架内置、已注册"的一批 BPP（如 AutowiredAnnotationBeanPostProcessor
  由 AnnotationConfigUtils 提前注册）来创建"用户自定义的 BPP"
```

> ⚠️ 推论：自定义 `BeanPostProcessor` 若依赖其他**自定义** BPP 的注入效果，很可能不生效——依赖只能由内置 BPP 提供；因此 BPP 内部尽量别依赖注入，需要什么自己从 `BeanFactory` 拿或延迟解析。

## 5. FactoryBean 与 ObjectProvider

| 类型 | 用途 | 与普通 Bean 的区别 |
|------|------|-------------------|
| `FactoryBean<T>` | 工厂 Bean：`getObject()` 产出目标对象，自身注册名为 `&name` | 容器拿到的是 `getObject()` 结果；`getBean("&name")` 拿工厂本身 |
| `ObjectFactory<T>` | 延迟获取（每次调用现取） | 注入的是"取 Bean 的能力"而非 Bean |
| `ObjectProvider<T>` | ObjectFactory 增强版：`getIfAvailable` / `getIfUnique` / `stream` | 可空注入、多候选选择、集合流式处理 |

**ObjectProvider 实战**（可空依赖/延迟注入首选）：

```java
@Service
public class ReportService {
    private final ObjectProvider<DataSource> dsProvider;   // 可能不存在

    public ReportService(ObjectProvider<DataSource> dsProvider) {
        this.dsProvider = dsProvider;
    }

    public void run() {
        DataSource ds = dsProvider.getIfAvailable(() -> new HikariDataSource());
    }
}
```

> 💡 **选型**：可空/可选依赖 → `ObjectProvider`；原型 Bean 注入单例 → `ObjectProvider.getObject()` 或 `@Lookup`；运行时动态选实现 → `ObjectProvider.stream()` + 条件。

### 5.1 FactoryBean 的解析调用链

```text
getBean("myBean")
 ├─ 检查名称前缀："&myBean" → 直接返回 FactoryBean 本身
 └─ 否则：先取得 FactoryBean 实例
     └─ getObjectForBeanInstance：
         ├─ 单例 → getObject() 结果缓存进 singletonObjects（缓存的是产品）
         └─ 原型 → 每次调用 getObject() 现取
```

### 5.2 FactoryBean 常见坑速查

| 常见坑 | 现象 | 解法 |
|--------|------|------|
| 想取工厂本身 | 拿到的是产品对象 | `getBean("&myBean")` |
| 产品类型是代理 | 按产品接口注入不匹配 | 正确实现 `getObjectType()`，容器按它注册类型 |
| 工厂内依赖注入 | 工厂本身没被装配 | 工厂实现 `BeanFactoryAware` 或在工厂里注入（工厂本身也是 Bean） |
| 单例产品缓存 | 多次 getBean 同一产品 | 单例产品缓存于 1 级缓存——按需 `prototype` 化 |

```java
@Component
public class MyFactoryBean implements FactoryBean<Cache> {
    @Override
    public Cache getObject() { return new LocalCache(); }   // 产品

    @Override
    public Class<?> getObjectType() { return Cache.class; } // 容器按此注册类型

    @Override
    public boolean isSingleton() { return true; }           // 单例产品
}
// 注入：@Autowired Cache cache（产品）；getBean("&myFactoryBean") 取工厂
```

### 5.3 ObjectProvider 的完整方法清单

| 方法 | 语义 | 空时行为 |
|------|------|---------|
| `getObject()` | 取一个实例 | 抛 `NoSuchBeanDefinitionException` |
| `getIfAvailable()` | 有则取 | 返回 null |
| `getIfAvailable(Supplier)` | 有则取 | 用默认值兜底 |
| `getIfUnique()` | 唯一则取 | 多候选返回 null（不报错） |
| `stream()` | 全部候选流 | 空流 |
| `orderedStream()` | 按 Order 排序流 | 空流 |

> 🎯 记忆：**getIfAvailable（可空）、getIfUnique（防多候选）、stream（全量）**——三件套覆盖"可选依赖"的绝大多数场景；面试答"可空注入怎么做"时首选 ObjectProvider 而非 `@Autowired(required=false)`。

## 6. BeanRegistrar（Spring 7 新成员）

**签名**：函数式接口，唯一方法：

```java
@FunctionalInterface
public interface BeanRegistrar {
    void register(BeanRegistry registry, Environment environment);
}
```

**使用要点**：

- 通过 `@Import(MyRegistrar.class)` 装配在 `@Configuration` 类上（不可用 `@Bean` 返回，需在配置处理期发现）；
- `BeanRegistry.registerBean(...)` 提供多重重载：按 Class、按 name + Class、带规格 lambda；
- 支持 `if` / `for` / `Environment.matchesProfiles` 动态注册 → **比 @Conditional/@Profile 更强的运行期判断**；
- AOT / GraalVM 原生镜像友好（实例化由供应商 lambda 捕获）；
- Kotlin 一等公民：`BeanRegistrarDsl`（`registerBean<Foo>()`、`profile("baz") {...}`）。

```java
class MyRegistrar implements BeanRegistrar {
    @Override
    public void register(BeanRegistry registry, Environment env) {
        registry.registerBean("orderService", OrderService.class);     // 最简
        registry.registerBean("cache", CacheManager.class, spec -> spec
            .prototype()                                               // 作用域
            .lazyInit()                                                // 懒加载
            .fallback()                                                // @Fallback 语义（7.0）
            .backgroundInit()                                          // 后台初始化
            .supplier(ctx -> new CacheManager(ctx.bean(Config.class))));
        if (env.matchesProfiles("preview")) {
            registry.registerBean(MockClient.class);
        }
    }
}
```

> ⚠️ **与旧方式的取舍**：`BeanDefinitionRegistryPostProcessor` 依然存在但不再推荐——BeanRegistrar 免去了手工 `GenericBeanDefinition`、语义更清晰、可测试、可 AOT；存量代码无需急迁，新代码直接用。

### 6.1 BeanRegistrar vs 旧式程序化注册

| 维度 | BeanRegistrar（7.0） | BeanDefinitionRegistryPostProcessor（旧） |
|------|---------------------|------------------------------------------|
| 注册时机 | 配置类处理期（ConfigurationClassParser 内） | refresh 早期，先于 BPP |
| 能否改已有定义 | 否（只新增） | 能（覆盖 registerBeanDefinition） |
| 条件注册 | if / for / Environment 原生支持 | 需手写条件逻辑 |
| AOT / GraalVM | ✅ 一等支持 | 部分（需额外配置） |
| 复杂度 | 低（函数式接口） | 高（模板方法 + 手工 BeanDefinition） |

> ⚠️ **边界**：BeanRegistrar 无法**修改或移除**已存在的 BeanDefinition——"改图纸"场景仍要用 `BeanFactoryPostProcessor`；且 `@Import` 中 BeanRegistrar 与 ImportSelector 按声明顺序解析，别依赖隐藏顺序。

### 6.2 面试追问：BeanRegistrar 与 @Bean 怎么取舍？

| 场景 | 选择 | 理由 |
|------|------|------|
| 固定数量、静态声明 | `@Bean` | 可读性最好，声明式可检查 |
| 数量 / 依赖环境动态决定 | `BeanRegistrar` | if / for / Environment 原生 |
| 集成第三方库的启动逻辑 | `BeanRegistrar` | 函数式、可注入、可测试 |
| 需要改已有定义 | `BeanFactoryPostProcessor` | 唯一能"改图纸"的扩展点 |

> 🎯 取舍本质：**@Bean 是"声明式"（可读、可查、可 AOT），BeanRegistrar 是"编程式"（运行期灵活、可分支可循环）**——声明式够用就声明式，动态场景再上编程式；两者混用完全合法。

### 6.3 BeanRegistrar 组合实战：循环注册 + 条件

```java
public class ClientRegistrar implements BeanRegistrar {
    @Override
    public void register(BeanRegistry registry, Environment env) {
        // for 循环批量注册：每个租户一个客户端
        for (String tenant : env.getProperty("tenants", "default").split(",")) {
            if (tenant.isBlank()) continue;                  // 运行时条件
            registry.registerBean("client-" + tenant, ApiClient.class, spec -> spec
                    .supplier(ctx -> new ApiClient(ctx.bean(ApiConfig.class).endpoint(tenant)))
                    .backgroundInit());                      // 后台初始化，不阻塞启动
        }
    }
}
```

> 💡 该模式替代了旧代码里"PostProcessor + 循环构造 BeanDefinition + 手写注册"约 40 行样板，语义一眼可读——这是 7.0 引入它的核心动机。

### 6.4 本系列核心类速查总表

| 类 | 一句话职责 | 面试问法 |
|----|-----------|---------|
| `DefaultListableBeanFactory` | 一切能力的集大成工厂 | "默认容器是谁？" |
| `DefaultSingletonBeanRegistry` | 三级缓存所在地 | "三级缓存在哪？" |
| `AbstractAutowireCapableBeanFactory` | 实例化/填充/初始化主逻辑 | "Bean 创建流程在哪个类？" |
| `AutowiredAnnotationBeanPostProcessor` | @Autowired 执行器 | "@Autowired 谁实现的？" |
| `AbstractAutoProxyCreator` | AOP 代理创建（aop 模块） | "代理在哪一步创建？" |
| `BeanRegistrar` | 7.0 程序化注册标准接口 | "7.x 新特性？" |

> 🎯 记忆线：**工厂（DefaultListable）→ 缓存（DefaultSingleton）→ 创建（AbstractAutowire）→ 注入（AutowiredBPP）→ 代理（AutoProxy）**——一条线串完容器源码主干。

### 6.5 排查指引：拿到异常怎么定位到类

| 异常信息片段 | 指向的类 | 下一步 |
|-------------|---------|--------|
| `No bean named 'x' available` | 工厂查找失败 | 检查注册/扫描/条件 |
| `Error creating bean with name 'x'` | 创建链某环节 | 看 caused by 是构造/填充/初始化 |
| `BeanCurrentlyInCreationException` | 单例缓存创建中判定 | 循环依赖，见 06 篇 |
| `BeanDefinitionStoreException` | 注册阶段 | 图纸本身非法（XML 语法/重复注册） |
| `BeanCreationNotAllowedException` | 容器关闭后 getBean | 生命周期误用（如销毁后还在用） |

> 💡 面试与排错共用技巧：**异常类名的前缀就是阶段**——`BeanDefinition`（注册期）、`BeanCreation`（创建期）、`BeanCurrentlyInCreation`（缓存判定期），先按前缀分段再深挖。
