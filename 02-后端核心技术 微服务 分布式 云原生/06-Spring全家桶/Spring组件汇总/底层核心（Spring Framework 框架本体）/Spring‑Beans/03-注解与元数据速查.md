## 1. 注解总表

| 分类 | 注解 | 所在包 |
|------|------|--------|
| 注册 | `@Component` / `@Service` / `@Repository` / `@Controller` | spring-core `org.springframework.stereotype` |
| 注册 | `@Configuration` / `@Bean` / `@ComponentScan` | spring-context |
| 注入 | `@Autowired` / `@Qualifier` / `@Value` | spring-beans `org.springframework.beans.factory.annotation` |
| 注入 | `@Resource` / `@PostConstruct` / `@PreDestroy` | `javax` / `jakarta.annotation` |
| 裁决 | `@Primary` / `@Fallback`（7.0） | spring-beans |
| 作用域 | `@Scope` / `@Lazy` / `@DependsOn` | spring-context / beans |
| 条件 | `@Conditional` / `@Profile` | spring-context |

> 💡 注意知识边界：`@Component` 在 **spring-core**，注入与裁决注解在 **spring-beans**，条件/扫描/配置注解在 **spring-context**——与 [01-模块清单](01-模块清单.md) 的依赖边界互相印证。

### 1.1 注解家族记忆法

- **三个包三句话**：`stereotype`（core）管身份、`factory.annotation`（beans）管注入与裁决、`context`（context）管扫描/条件/配置；
- **派生关系**：`@Component` 是根，`@Service` / `@Repository` / `@Controller` 都**携带** `@Component` 元注解，靠它被扫描识别——"派生"不是 Java 继承，而是元注解传递；
- **面试常考三分法**：`@Resource`（名字优先，JSR-250）、`@Autowired`（类型优先，Spring）、`@Inject`（类型优先，JSR-330）——三者语义差异见第 3 节与 06 篇第 5 节。

### 1.2 注解归属速查表（面试归类题）

| 注解 | 模块 | 记忆锚点 |
|------|------|---------|
| `@Component` / `@Service` / `@Repository` / `@Controller` | spring-core | "身份标记" |
| `@Autowired` / `@Qualifier` / `@Value` / `@Lookup` | spring-beans | "注入与裁决" |
| `@Configuration` / `@Bean` / `@ComponentScan` / `@Import` | spring-context | "配置与扫描" |
| `@Conditional` / `@Profile` | spring-context | "条件装配" |
| `@Resource` / `@PostConstruct` / `@PreDestroy` | jakarta.annotation | "JSR-250 标准" |
| `@ConditionalOnXxx` | spring-boot-autoconfigure | "Boot 专属" |

> ⚠️ 常见面试陷阱：`@ConditionalOnXxx` 不属于 Spring Framework——它是 Boot 自动配置模块的注解；纯 Spring 项目里只有 `@Conditional` 可用。

## 2. 注册类注解

| 注解 | 语义 | 细节 |
|------|------|------|
| `@Component` | 通用组件 | 扫描的底层语义，其余三个都是它的派生（`@Service` 等仅语义区分） |
| `@Service` | 业务服务 | 语义化别名（无行为差异） |
| `@Repository` | 数据访问 | 额外：`DataAccessException` 转换器识别它 |
| `@Controller` / `@RestController` | Web 控制器 | Spring MVC 识别（见 Spring-WebMVC 系列） |
| `@Configuration` | 配置类（Full 模式） | 类内 `@Bean` 方法会被 CGLIB 代理以保单例；`proxyBeanMethods` 可关 |
| `@Bean` | 工厂方法注册 | `name` / `initMethod` / `destroyMethod` / `autowireCandidate` / `value`（别名） |
| `@ComponentScan` | 扫描范围 | `basePackages` / `includeFilters` / `excludeFilters` / `lazyInit` |
| `@Import` | 导入配置/类 | 可导入普通类（变 Bean）、`@Configuration`、`ImportSelector`、`BeanRegistrar`（7.0） |

**@Bean 全部属性速查**：

| 属性 | 默认 | 语义 |
|------|------|------|
| `name` / `value` | 方法名 | Bean 名与别名（数组可多个） |
| `initMethod` / `destroyMethod` | 空 / 自动推断 | 初始化/销毁回调方法名 |
| `autowireCandidate` | true | 是否参与自动装配（false 只能显式引用） |
| `autowire` | NO | 注解风格自动装配模式（现代不用） |

**@Configuration 的 proxyBeanMethods 权衡**：

| proxyBeanMethods | 行为 | 代价 |
|:---:|------|------|
| true（默认） | @Bean 方法互调走 CGLIB 代理，保证单例 | 启动多一层代理（慢一点点） |
| false | 互调直接 new，方法间调用失去单例保证 | 更快，适合无方法间调用的配置 |

> 💡 工程建议：配置类内**不互相调用** `@Bean` 方法时，`proxyBeanMethods = false` 是免费优化（Boot 2.2+ 已对内部配置默认如此）；有互调必须保持 true——这是 Full/Lite 陷阱的配置侧开关。

**@Bean 常用写法**：

```java
@Configuration
public class DataConfig {
    @Bean(initMethod = "start", destroyMethod = "close")
    @Scope("singleton")
    public ConnectionPool pool(@Value("${pool.size}") int size) {
        return new ConnectionPool(size);   // 参数自动注入 = 工厂方法注入
    }
}
```

> ⚠️ **Full vs Lite 模式**：`@Configuration` + `@Bean`（Full）内部 `@Bean` 方法间调用会走代理（保证单例）；普通类（含 `@Component`）上的 `@Bean`（Lite）方法互调会直接 new——这是"重复创建"类坑的根源。

### 2.1 @ComponentScan 实战与 FilterType

```java
@Configuration
@ComponentScan(
    basePackages = "com.example",
    includeFilters = @ComponentScan.Filter(type = FilterType.ASSIGNABLE_TYPE,
                                           classes = HealthCheck.class),
    excludeFilters = {
        @ComponentScan.Filter(type = FilterType.REGEX, pattern = ".*Test"),
        @ComponentScan.Filter(type = FilterType.ANNOTATION,
                              classes = Deprecated.class)
    })
public class AppConfig { }
```

| FilterType | 匹配方式 | 典型用法 |
|-----------|---------|---------|
| ANNOTATION | 注解匹配 | 排除/收录带某注解的类 |
| ASSIGNABLE_TYPE | 类型/接口匹配 | 收录某接口的全部实现 |
| REGEX | 类名正则 | 排除 `*Test` / `*Mock` |
| ASPECTJ | AspectJ 表达式 | 复杂切面式匹配 |
| CUSTOM | 自定义 `TypeFilter` | 运行时逻辑过滤 |

> ⚠️ **includeFilters 不生效陷阱**：默认 `useDefaultFilters=true`，默认规则（@Component 家族）始终叠加——includeFilters 是"加"不是"换"；想完全自定义收录规则必须显式 `useDefaultFilters = false`。

### 2.2 @Import 的四种用法

| 用法 | 效果 | 场景 |
|------|------|------|
| `@Import(SomeClass.class)` | 普通类直接注册为 Bean | 无注解的三方类 |
| `@Import(SomeConfig.class)` | 导入另一个 @Configuration | 配置模块化 |
| `@Import(MyImportSelector.class)` | 动态挑选一批配置类 | 条件化导入（Boot 自动配置用它） |
| `@Import(MyRegistrar.class)`（7.0） | 程序化注册 | 动态/循环注册 |

```java
public class MyImportSelector implements ImportSelector {
    @Override
    public String[] selectImports(AnnotationMetadata metadata) {
        // 返回的是配置类的全限定名数组
        return new String[] { "com.example.FeatureConfig", "com.example.ToolsConfig" };
    }
}
```

> 💡 `ImportSelector` 与 `BeanRegistrar` 的分工：前者"选配置类"，后者"直接注册 Bean"——需要循环/条件注册时用后者，需要复用已有配置类时用前者。

## 3. 注入与装配注解

| 注解 | 规则 | 要点 |
|------|------|------|
| `@Autowired` | 类型优先：字段/构造器/setter 三用；候选唯一即中 | 构造器注入在 4.x 起可省略注解（单构造器自动注入） |
| `@Qualifier` | 名字兜底匹配 | 配合 `@Autowired`；也可配合构造器参数 |
| `@Value` | 注入外部配置/SpEL | `${prop}` 占位符、`#{spel}` 表达式 |
| `@Resource` | JSR-250，**名字优先**，后按类型 | 仅字段/setter（不支持构造器）；多 Bean 同类型时行为与 @Autowired 相反 |
| `@Lazy` | 懒加载注入 | 注入代理而非真实 Bean，首次调用才创建；**解决循环依赖的第三方案** |
| `@Lookup` | 方法级取原型 | 每次调用返回新实例（方法返回类型须为 Bean 类型） |
| `@DependsOn` | 显式依赖顺序 | 不依赖注入关系的启动先后控制 |

**构造器注入（首选）与现代写法**：

```java
@Service
public class OrderService {
    private final OrderRepo repo;      // final + 构造器 = 不可变、可测

    public OrderService(OrderRepo repo) {   // 单构造器可省 @Autowired
        this.repo = repo;
    }
}
```

### 3.1 @Autowired 不生效的场景（高频坑）

| 场景 | 失败表现 | 原因 / 解法 |
|------|---------|------------|
| 静态字段 | 注入为 null | 容器不管静态字段；改非静态 + `@PostConstruct` 转存，或构造器注入 |
| `new` 出来的对象 | 注入为 null | 容器只管理自己创建的 Bean；改用容器获取或工厂 |
| 线程池 / lambda 内匿名类 | null | 对象非容器创建；需要容器参与创建或传参 |
| 接口多实现无裁决 | `NoUniqueBeanDefinitionException` | `@Primary` / `@Qualifier` 解决 |
| 泛型实参不匹配 | `NoSuchBeanDefinitionException` | 泛型匹配按实参过滤（见 06 篇第 4 节） |

### 3.2 @Value 的边界与写法

```java
@Value("${pool.size:8}")        private int size;          // 属性 + 默认值
@Value("${server.timeout:3s}")  private Duration timeout;  // 自动转换 Duration
@Value("#{systemProperties['user.home']}") private String home;  // SpEL
@Value("#{'${gateway.ips}'.split(',')}")    private List<String> ips; // SpEL + 属性
```

> ⚠️ 两个易错点：① `${}` 与 `#{}` 混用时先解析占位符再执行表达式（嵌套写法少见，别依赖顺序）；② `@Value` 注入的是**字符串**，类型转换走 ConversionService——写错格式（如 `Duration` 写成 `"3"`）在启动期报错而非运行期。

### 3.3 @Lookup 的限制

- 方法必须可被 CGLIB 重写——**final 方法 / final 类上不生效**（直接返回 null 或调用原方法）；
- 返回类型必须是容器中的 Bean 类型，且方法不能有业务逻辑（容器用生成子类覆盖它）；
- 场景：单例注入原型、方法级每次取新实例；现代实现多用 `ObjectProvider` 替代。

### 3.4 注入注解使用决策表

| 依赖特征 | 推荐写法 |
|---------|---------|
| 必需、固定 | 构造器注入（final） |
| 可选、可给默认 | `ObjectProvider.getIfAvailable(Supplier)` |
| 多个同类型实现 | `@Qualifier` 点名或 `List<T>` 全量 |
| 运行时动态选择 | `ObjectProvider.stream()` + 条件过滤 |
| 外部配置值 | `@Value` |
| 需要名字语义（JSR 兼容） | `@Resource(name = "...")` |

> 🎯 一句话：**构造器兜底一切必需依赖，Provider 兜底一切可选/动态依赖**——其余写法都有更明确的替代。

## 4. 装配裁决：@Primary / @Fallback / @Qualifier

| 注解 | 语义 | 优先级 |
|------|------|--------|
| `@Primary` | 多个候选时的首选 | 最高（名字精确匹配除外） |
| `@Fallback`（7.0 新增） | 兜底候选：**仅当没有其他候选时**才被选中 | 最低 |
| `@Qualifier` | 显式名字/限定符匹配 | 命中即赢（压倒 @Primary） |

```java
@Configuration
public class ClientConfig {
    @Bean @Primary
    public PaymentClient alipay() { return new AlipayClient(); }

    @Bean @Fallback
    public PaymentClient defaultClient() { return new MockClient(); }  // 无其他候选时才用

    @Bean @Qualifier("wechat")
    public PaymentClient wechat() { return new WechatClient(); }
}

// 注入方
@Autowired @Qualifier("wechat")
private PaymentClient client;   // 精确命中，无视 @Primary
```

> 🎯 **核心要点**：裁决链 = `@Qualifier` 精确匹配 ＞ `@Primary` 首选 ＞ 名字回退 ＞ 类型唯一 ＞ 报 `NoUniqueBeanDefinitionException`；`@Fallback` 补齐了"声明一个永不打架的默认实现"场景（测试替身、降级实现）。

### 4.1 @Primary / @Fallback 在集合注入中的行为

> ⚠️ 集合注入（`List<T>` / `Map<String,T>`）时 **@Primary 与 @Fallback 不参与筛选**——容器注入全部候选；裁决注解只在"单值注入"时起作用。若 `@Fallback` 的兜底实现不想出现在集合里，注入方要显式用 `@Qualifier` 点名。

### 4.2 自定义限定符注解（组合 @Qualifier）

```java
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Qualifier                       // 以 @Qualifier 为元注解 → 组合限定符
public @interface Region {
    String value() default "cn"; // 可携带额外属性
}
```

| 方式 | 优点 | 缺点 |
|------|------|------|
| `@Qualifier("wechat")` | 简单直接 | 字符串魔法值，易拼错、无编译期检查 |
| 组合限定符 `@Region("cn")` | 类型安全、可带属性 | 定义成本略高 |

> 💡 面试加分：组合限定符是"注解即类型安全"的典型应用——大型项目多实现场景推荐用它替代字符串限定符。

### 4.3 面试追问：@Fallback 与 @Primary 能同时标一个 Bean 吗？

能标注但无意义——`@Fallback` 的语义是"仅当没有其他候选时"，而 `@Primary` 的语义是"有多个候选时优先"；二者同时存在时，`@Primary` 标记的 Bean 在"有多个候选"时直接胜出，`@Fallback` 标记的另一个 Bean 只在"除它之外无候选"时被选，两者不会同时命中。实际开发中一个 Bean 只标一个裁决注解。

### 4.4 裁决链完整流程图

```text
注入点需要 PaymentClient
 ├─ 候选收集：类型匹配（含父接口/泛型实参）
 ├─ 候选数 = 0 → NoSuchBeanDefinitionException（或 required=false 注入 null）
 ├─ 候选数 = 1 → 直接注入
 └─ 候选数 > 1：
     ├─ @Qualifier 精确命中 → 胜出
     ├─ @Primary 标记者 → 胜出
     ├─ 参数名/字段名与 Bean 名一致 → 回退胜出
     ├─ 除 @Fallback 标注者外只剩 1 个 → 该候选胜出
     └─ 仍 > 1 → NoUniqueBeanDefinitionException
```

> 🎯 面试默写这张图即可覆盖"多实现注入怎么裁决"的完整答案；注意 @Fallback 参与时机在名字回退**之后**——它只在"没有其他能胜出的候选"时才登场。

## 5. 条件与配置注解

| 注解 | 机制 | 典型场景 |
|------|------|---------|
| `@Conditional(Condition.class)` | 实现 `Condition.matches(...)` 判定 | 自定义开关 |
| `@Profile("dev")` | 基于激活 profile 的 `@Conditional` 派生 | 环境差异化 Bean（dev/test/prod） |
| `@ConditionalOnClass` 等 | **Spring Boot 专属**（spring-boot-autoconfigure） | 自动配置；不在 spring-beans |

```java
@Configuration
public class MockConfig {
    @Bean
    @Profile({"dev", "test"})            // 仅开发/测试环境存在
    @Conditional(OnFeatureEnabled.class) // 叠加自定义条件
    public PaymentClient mockClient() { return new MockClient(); }
}
```

> ⚠️ 注意归属：`@Conditional` 在 spring-context；`@ConditionalOnXxx` 系列属于 **spring-boot-autoconfigure**（Boot 自动配置），不属于 beans/context 模块——面试归类时别答错。

### 5.1 自定义 @Conditional 完整示例

```java
public class OnWindowsCondition implements Condition {
    @Override
    public boolean matches(ConditionContext ctx, AnnotatedTypeMetadata metadata) {
        String os = ctx.getEnvironment().getProperty("os.name", "").toLowerCase();
        return os.contains("win");
    }
}

@Configuration
public class OsConfig {
    @Bean
    @Conditional(OnWindowsCondition.class)
    public PathService pathService() { return new WindowsPathService(); }
}
```

> 💡 **排查技巧**：条件不满足时容器**不报错，只是不注册**——"Bean 神秘消失"先查条件；Boot 里开 `debug=true` 或看 `ConditionEvaluationReport`，能逐条列出每个条件判定的原因。`Condition` 与 `ConfigurationCondition` 的区别：后者可指定在配置类解析的哪个阶段判定（注册 vs 实例化）。

### 5.2 @Profile 与 @Conditional 的关系

- `@Profile` 底层就是 `@Conditional(ProfileCondition.class)`——封装了"从 Environment 读激活 profile"的判定；
- 因此 `@Profile` 可与自定义 `@Conditional` 叠加在同一个 `@Bean` 上，多个条件为 **AND** 语义（全部满足才注册）；
- 边界：profile 判定依赖 `spring.profiles.active`，该属性必须已进入 Environment——在 `@PropertySource` 加载**之前**的早期阶段判定可能拿到空值。

### 5.3 面试追问：为什么条件不满足不报错？

因为条件装配是"声明式过滤"——`matches` 返回 false 时，对应 BeanDefinition 直接不注册，容器无从知道"你本来想要它"。这是设计选择：**让条件决定存在性，而不是报错**。想要"缺 Bean 即失败"的效果，用 `ObjectProvider.getIfAvailable(() -> { throw ... })` 或 Boot 的 `@ConditionalOnMissingBean` + 后续显式校验。

## 6. 元注解与组合注解

- **元注解（meta-annotation）**：标注在注解上的注解——`@Component` 是 `@Service`/`@Repository`/`@Controller` 的元注解；
- **组合注解（composed annotation）**：一个注解叠多个注解并开放属性别名，如 `@RestController = @Controller + @ResponseBody`；
- **注解可发现性**：Spring 用 `@ComponentScan` + `ClassPathScanningCandidateComponentProvider` 扫描，组合注解通过 `@AliasFor` 传递属性（spring-core 的 `AnnotatedElementUtils` 解析）。

```java
// 自定义组合注解示例：@Service + @Scope 合并成一个
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Service
@Scope("prototype")
public @interface PrototypeService { }
```

> 💡 面试加分点：`@Component` 派生注解能被识别，依赖 spring-core 的 `@Indexed`（候选组件索引，加速启动扫描）与 `AnnotatedElementUtils` 的注解属性解析机制。

### 6.1 @AliasFor 的两种用途

| 用途 | 示例 | 效果 |
|------|------|------|
| 属性别名（同一注解内） | `@Bean(name = ..., value = ...)` 内部映射 | 两个属性互相等价 |
| 属性覆盖（跨注解） | 组合注解覆盖 `@ComponentScan.basePackages` | 组合注解开放属性给使用者 |

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@ComponentScan
public @interface MyScan {
    @AliasFor(annotation = ComponentScan.class, attribute = "basePackages")
    String[] value() default {};     // 用 value 代替 basePackages
}
```

> 💡 解析机制：`AnnotatedElementUtils.getMergedAnnotationAttributes` 按 `@AliasFor` 展开属性映射——这是"组合注解的 `value` 能直接当 `basePackages` 用"的原因；理解它就能读懂 Boot 大量组合注解（`@SpringBootApplication`）的传参行为。

> ⚠️ @AliasFor 的常见错误：① 别名属性类型必须一致（`String[]` 不能别名 `String`）；② 跨注解覆盖时，被覆盖注解必须出现在元注解链上；③ 组合注解没标 `@Retention(RUNTIME)` 时运行期读不到——报 `AnnotationConfigurationException` 先查这三条。

### 6.2 @Indexed 与扫描加速

- `@Indexed`（spring-core）：标注在 `@Component` 等 stereotype 注解上，编译期在 `META-INF/spring.components` 生成候选索引；
- 运行时 `ClassPathScanningCandidateComponentProvider` 优先读索引，**跳过目录扫描**——大项目启动加速明显；
- 代价：新增类需重新编译才进索引，热部署场景要小心索引过期（devtools 已处理）。

### 6.3 注解族高频面试题汇总

| 问题 | 一句话答案 |
|------|-----------|
| @Service 与 @Component 区别？ | 无行为差异，纯语义标记 |
| @Configuration 上的 @Bean 为什么单例？ | Full 模式 CGLIB 代理拦截方法间调用 |
| @Autowired 可以标注在方法上吗？ | 可以——方法参数自动装配 |
| 注解定义在哪个模块？ | 按包归属，见 1.2 表 |
| 注解为什么"即能力"？ | 元数据 + 后处理器消费（见 07 篇第 2 节） |

### 6.4 生产实践：注解选用的三条铁律

| # | 铁律 | 为什么 |
|---|------|--------|
| 1 | 业务 Bean 统一 `@Component` 家族，不混用 `@Bean` | 扫描路径清晰、依赖可见 |
| 2 | 三方库类与复杂初始化用 `@Bean`（工厂方法） | 创建逻辑显式、可传参 |
| 3 | 动态/批量注册用 `BeanRegistrar`（7.0） | 声明式覆盖不了的场景才上编程式 |

> 🎯 统一原则：**能声明式就声明式，能组件扫描就不写工厂方法**——注释与代码一样是债务，注解使用越收敛，项目越易维护。
