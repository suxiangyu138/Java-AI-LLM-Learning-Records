## 1. 配置入口总览

```text
Bean 定义来源（殊途同归 → BeanDefinition）
├── XML：<beans>/<bean>/<context:component-scan>      → XmlBeanDefinitionReader
├── 注解：@Component 扫描 / @Bean                      → ConfigurationClassPostProcessor
├── 程序化：BeanRegistrar（7.0 推荐） / Registry API    → 直接注册
└── Groovy：BeanBuilder（7.x 已边缘化，不展开）
```

> 💡 现代项目 99% 用"注解 + Java Config"，XML 仅存量系统；但 Spring Boot 自动配置的"条件装配"逻辑本质仍是 `@Conditional` + 配置属性联动，故属性速查必须会。

### 1.1 四套入口的取舍

| 入口 | 适用 | 优势 | 代价 |
|------|------|------|------|
| XML | 存量系统 / 非 Java 团队维护 | 配置与代码分离、可热改 | 冗长、无编译期检查 |
| 注解 + Java Config | 一切新项目 | 类型安全、IDE 友好 | 配置散落在代码里 |
| BeanRegistrar（7.0） | 动态/批量注册、框架集成 | 程序化、AOT 友好 | 可读性弱于注解 |
| Groovy（7.x） | 边缘化 | — | 不建议新用 |

> 🎯 一条原则：**能声明式就声明式（注解），必须动态才编程式（BeanRegistrar）**——声明式可读、可查、可 AOT；动态灵活性用 BeanRegistrar 的 if / for 补足。

### 1.2 配置流程时序（与容器启动对齐）

```text
容器 refresh()
 ├─ ① 配置类解析：@Configuration 类 → ConfigurationClassParser
 │     （@Bean 方法、@Import、@ComponentScan 在此展开）
 ├─ ② BeanFactoryPostProcessor：@PropertySource 加载、占位符解析器注册
 ├─ ③ 单例预加载：@Value 注入时解析 ${} 占位符
 └─ ④ 属性变更生效点：全部在启动期——运行期改配置不生效（需 refresh 或 @RefreshScope）
```

> ⚠️ 关键认知：**beans 的配置是"启动期快照"**——`@Value` 注入后属性再变也不更新；动态刷新是 Spring Cloud Config / Nacos 的 `@RefreshScope` 能力（context 层），不属于 beans 职责。

### 1.3 三种定义来源最终翻译成什么

| 来源 | 中间产物 | 最终形态 |
|------|---------|---------|
| XML `<bean>` | `GenericBeanDefinition`（XmlBeanDefinitionReader） | 合并为 `RootBeanDefinition` |
| `@Bean` 方法 | `ConfigurationClassBeanDefinitionReader` 产物 | 直接是 `RootBeanDefinition` |
| `@Component` 扫描 | `ScannedGenericBeanDefinition` | getBean 时合并 |

> 💡 面试加分：**无论从哪个入口定义，容器运行时只认合并后的 `RootBeanDefinition`**——这就是"殊途同归"的源码级含义；四种入口差异只在前半段（解析），后半段（实例化）完全一致。

### 1.4 配置写法演进简史

| 时代 | 主流写法 | 对应版本 |
|------|---------|---------|
| 2004-2009 | XML `<beans>` | 1.x - 2.x |
| 2009-2014 | XML + 注解混用 | 3.x |
| 2014 至今 | 全注解 + Java Config | 4.x+ |
| 2025 起 | 注解为主 + BeanRegistrar 程序化补充 | 7.x |

> 🎯 演进主线：**声明式配置的"语法"从 XML 收敛到注解，本质不变（都是 BeanDefinition）**——答"为什么还要学 XML"时用这条主线：学的是图纸模型，换的只是描述语言。

## 2. XML 命名空间速查

```xml
<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xmlns:context="http://www.springframework.org/schema/context"
       xsi:schemaLocation="
           http://www.springframework.org/schema/beans
           https://www.springframework.org/schema/beans/spring-beans.xsd
           http://www.springframework.org/schema/context
           https://www.springframework.org/schema/context/spring-context.xsd">

    <context:component-scan base-package="com.example"/>   <!-- 注解扫描入口 -->

    <bean id="orderService" class="com.example.OrderService"
          scope="singleton" lazy-init="false" primary="true"
          init-method="init" destroy-method="close" depends-on="dataSource">
        <property name="repo" ref="orderRepo"/>
        <property name="pageSize" value="20"/>
    </bean>

    <!-- 构造器注入 + 集合 -->
    <bean id="orderRepo" class="com.example.OrderRepo">
        <constructor-arg index="0" value="mysql"/>
        <property name="handlers">
            <list><ref bean="h1"/><ref bean="h2"/></list>
        </property>
    </bean>
</beans>
```

| 属性/元素 | 含义 |
|-----------|------|
| `id` / `name` | Bean 名 / 别名（逗号分隔） |
| `class` | 全限定类名 |
| `scope` | 作用域（singleton/prototype/custom） |
| `lazy-init` | 是否懒加载（对 singleton 生效） |
| `primary` | 首选候选 |
| `init-method` / `destroy-method` | 初始化/销毁回调 |
| `depends-on` | 显式依赖（逗号分隔多个） |
| `autowire` | byName/byType/constructor（现代不推荐，用注解） |
| `<property name="x" ref="beanId"/>` | setter 注入 |
| `<constructor-arg index/name value/ref/>` | 构造器注入 |
| `<context:property-placeholder location="classpath:db.properties"/>` | 属性占位符解析器 |

### 2.1 XML 高级特性：p/c 命名空间、父子 Bean、工厂方法

```xml
<beans xmlns:p="http://www.springframework.org/schema/p"
       xmlns:c="http://www.springframework.org/schema/c">
    <!-- p: 属性注入缩写，c: 构造器注入缩写 -->
    <bean id="orderRepo" class="com.example.OrderRepo"
          p:pageSize="20" c:driver="mysql"/>

    <!-- 父子 Bean：子继承父的属性，父 abstract 不实例化（模板） -->
    <bean id="baseDs" class="com.example.DataSource" abstract="true" p:poolSize="8"/>
    <bean id="slaveDs" parent="baseDs" p:readOnly="true"/>

    <!-- 静态工厂方法 -->
    <bean id="clock" class="java.time.Clock" factory-method="systemDefaultZone"/>
</beans>
```

| 特性 | 说明 |
|------|------|
| 父子 Bean | 子继承父的 class/属性；`abstract="true"` 的父只当模板 |
| 工厂方法 | `factory-method`（静态）或 `factory-bean` + `factory-method`（实例） |
| 内部 Bean | `<bean>` 嵌在属性内，无 id，随外部 Bean 生命周期 |
| `lookup-method` | XML 版原型注入（等价 @Lookup） |

> ⚠️ **XML 与注解混用陷阱**：只写 `<context:component-scan/>` 时 `@Autowired` 自动启用；但若只手动注册 `<bean>` 且没有扫描，必须显式加 `<context:annotation-config/>`，否则 `@Autowired` / `@Value` 全部静默失效。

### 2.2 面试追问：现在还需要学 XML 吗？

- **面试角度**：会读即可——存量系统（银行、国企、老框架）仍大量使用，且 XML `<bean>` 的属性全集就是 BeanDefinition 的属性全集，读懂 XML 等于读懂图纸模型；
- **工程角度**：新代码用注解；但"配置外置给非 Java 工程师维护"的场景，XML 依然是合理选择——不存在"过时"的配置方式，只有不匹配的场景。

### 2.3 XML 常见解析问题

| 现象 | 原因 | 解法 |
|------|------|------|
| 启动报 `BeanDefinitionStoreException` | schema 位置错 / XML 语法错 | 核对 `schemaLocation` 与 DTD 版本 |
| `ClassNotFoundException` | `<bean class>` 全限定名拼错 | 用 IDE 的类名补全生成 |
| 属性注入失败 | 属性名与 setter 不匹配 | setter 命名规范 `setPageSize` ↔ `pageSize` |
| 循环引用报错 | XML 属性注入也可能成环 | 构造器环无法解决；setter 环可三级缓存（旧版默认允许） |

> 💡 排错要点：XML 配置错误的报错**全部发生在启动早期**（BeanDefinitionStoreException 系）——比注解时代更早、更明显，这是 XML 的"配置即图纸"特性带来的可排查性优势。

## 3. Java Config 速查

```java
@Configuration                              // Full 模式配置类
@PropertySource("classpath:app.properties") // 加载属性文件
@ComponentScan(basePackages = "com.example",
               excludeFilters = @ComponentScan.Filter(type = FilterType.REGEX, pattern = ".*Mock"))
public class AppConfig {

    @Bean(name = {"pool", "connectionPool"}, destroyMethod = "close")
    @Lazy(value = false)
    @Primary
    public ConnectionPool pool(@Value("${pool.size:8}") int size) {
        return new ConnectionPool(size);
    }
}
```

| 注解属性 | 说明 |
|---------|------|
| `@Bean.name` / `value` | 名称（默认方法名；可多别名） |
| `@Bean.autowireCandidate` | 是否参与自动装配（false = 只能显式引用） |
| `@Bean.initMethod` / `destroyMethod` | 字符串方式指定（`destroyMethod = ""` 可关掉默认推断） |
| `@Configuration.proxyBeanMethods` | true（默认）@Bean 互调走代理保单例；false 提速（Lite 语义） |
| `@ComponentScan.lazyInit` | 扫描出的 Bean 统一懒加载 |
| `@ComponentScan.FilterType` | ANNOTATION / ASSIGNABLE_TYPE / REGEX / ASPECTJ / CUSTOM |

> ⚠️ **destroyMethod 默认推断陷阱**：`@Bean` 默认会查找 public `close()`/`shutdown()` 等约定方法作为销毁回调——若你的类恰好有同名方法但语义不是释放资源，需显式 `destroyMethod = ""` 关闭。

### 3.1 Java Config 进阶写法

```java
@Configuration
public class AdvancedConfig {
    // 集合属性注入：SpEL 拆分字符串
    @Value("#{'${gateway.ips}'.split(',')}")
    private List<String> gatewayIps;

    // @Bean 返回接口：容器按返回类型注册
    @Bean
    public PaymentClient paymentClient(@Value("${pay.mode:alipay}") String mode) {
        return "wechat".equals(mode) ? new WechatClient() : new AlipayClient();
    }

    // 导入外部配置类，避免巨型配置类
    @Import({DataConfig.class, CacheConfig.class})
    // 类体省略...
}
```

> ⚠️ **@Bean 返回类型陷阱**：返回接口时 BeanDefinition 的 `beanClass` 是**返回类型**——按接口类型 `getBean(PaymentClient.class)` 可命中，按实现类 `getBean(AlipayClient.class)` 反而找不到；需要精确类型注入时，返回具体类。

### 3.2 Java Config vs XML 对照表

| 能力 | XML 写法 | Java Config 写法 |
|------|---------|-----------------|
| 定义 Bean | `<bean class="...">` | `@Bean` 方法 |
| 属性注入 | `<property name="x" value="1"/>` | 方法参数 + `@Value` |
| 依赖引用 | `<property name="x" ref="beanId"/>` | 方法参数（类型自动） |
| 条件注册 | `profile="dev"` 属性 | `@Profile` / `@Conditional` |
| 导入其他配置 | `<import resource="..."/>` | `@Import` |
| 扫描 | `<context:component-scan/>` | `@ComponentScan` |

> 💡 理解对照即可双向翻译——存量 XML 迁移到注解时按此表逐行替换，语义一一对应。

## 4. Spring Boot 属性速查

| 属性 | 默认 | 说明 |
|------|------|------|
| `spring.main.lazy-initialization` | false | 全局懒加载（开发期提速利器） |
| `spring.main.allow-bean-definition-overriding` | false | 同名 BeanDefinition 覆盖开关 |
| `spring.main.allow-circular-references` | false（7.0/Boot 4） | 循环依赖开关（Boot 2.6 起默认禁止，见 06 篇） |
| `spring.beaninfo.ignore` | true | 忽略 `BeanInfo` 类（JDK BeanInfo 元数据） |
| `spring.aop.proxy-target-class` | true（Boot 4） | CGLIB vs JDK 代理全局开关 |
| `spring.config.import` | - | 引入额外配置文件（`optional:` 前缀可容错） |
| `spring.profiles.active` | - | 激活 profile |
| `spring.messages.*` | - | MessageSource（context 层，Bean 相关少用） |

```yaml
spring:
  main:
    lazy-initialization: true        # 开发期全局懒加载
    allow-circular-references: false # 保持关闭，改代码而不是开开关
  beaninfo:
    ignore: true
  profiles:
    active: dev
```

> 💡 **与 beans 直接相关的其实很少**——Boot 属性主要在 autoconfigure 层；beans 层的"配置"更多由 `@Value` + `@ConfigurationProperties`（见 Spring Boot 系列）消费。

### 4.1 关键属性的坑与生产建议

| 属性 | 坑点 | 生产建议 |
|------|------|---------|
| `spring.main.lazy-initialization` | 对 `@Configuration` 类无效（配置类始终预加载）；与 `@Lazy(false)` 冲突时注解优先 | 仅开发期开；生产全局懒加载慎用 |
| `allow-bean-definition-overriding` | 开启后同名定义**静默覆盖**（后者胜） | 保持 false；撞名是设计问题 |
| `allow-circular-references` | 只是"允许"不是"修复" | 保持 false，重构消除 |
| `spring.beaninfo.ignore` | 关闭后 JDK BeanInfo 干扰属性填充 | 保持 true（默认） |
| `spring.aop.proxy-target-class` | false 时无接口实现类无法代理 | 保持 true（Boot 4 默认） |

### 4.2 属性优先级（同 key 谁生效）

```text
命令行参数 ＞ Java System 属性 ＞ OS 环境变量 ＞ application-{profile}.yaml
＞ application.yaml ＞ @PropertySource 文件 ＞ @Value 默认值（:default）
```

> 💡 面试题"同一个 key 多处配置谁生效"按此顺序答；`spring.config.import` 引入的文件**优先级低于**主配置——`optional:` 前缀可让文件缺失不报错（本地开发常用）。

### 4.3 环境差异化的标准姿势

| 环境 | 做法 |
|------|------|
| dev / test / prod 差异 | `application-{profile}.yml` + `spring.profiles.active` |
| 仅本机生效 | `application-local.yml` + 本地 `-Dspring.profiles.active=local` |
| 敏感信息 | 环境变量 / 密钥管理（勿入库） |
| 开关切换实现 | `@Profile` / `@Conditional` 控制 Bean 有无 |

### 4.4 面试追问：Boot 属性与 beans 层有什么关系？

- Boot 属性（`spring.*`）由 autoconfigure 消费，**最终动作仍是"注册/不注册某个 Bean"**——落在 beans 的 BeanDefinition 上；
- 例：`spring.datasource.url` → `DataSourceAutoConfiguration` 条件满足 → 注册 `DataSource` Bean → 走 beans 的标准生命周期；
- 所以排查"配置了但 Bean 没有"时：先查条件（ConditionEvaluationReport），再查 BeanDefinition 是否注册，最后看生命周期——三段式排查与 beans 层完全同构。

> 🎯 一句话：**Boot 属性是"输入"，beans 容器是"执行器"**——理解 beans 就能读懂任何 Boot 自动配置的落地过程。

## 5. BeanRegistrar 注册规格速查（7.0）

`BeanRegistry.registerBean` 的规格 lambda 完整选项：

| 选项 | 默认 | 语义 |
|------|------|------|
| `prototype()` | false（单例） | 原型作用域 |
| `lazyInit()` | false | 懒加载 |
| `primary()` | false | 首选候选（= @Primary） |
| `fallback()` | false | 兜底候选（= @Fallback，7.0） |
| `backgroundInit()` | false | 后台异步初始化（不阻塞启动） |
| `autowirable(boolean)` | true | 是否自动装配候选 |
| `infrastructure()` | false | 标记为基础设施 Bean（框架级） |
| `order(Integer)` | null | 排序 |
| `description(String)` | null | 描述 |
| `supplier(Function<BeanRegistry, Object>)` | - | 实例化供应商（AOT 友好，可用 `ctx.bean(Clazz)` 取依赖） |

```java
registry.registerBean("ds", DataSource.class, spec -> spec
    .prototype()
    .backgroundInit()
    .supplier(ctx -> new HikariDataSource(ctx.bean(DataSourceConfig.class).url()));
```

### 5.1 registerBean 完整实战（动态 + 依赖 + 条件）

```java
@Configuration
@Import(DataSourceRegistrar.class)
public class AppConfig { }

public class DataSourceRegistrar implements BeanRegistrar {
    @Override
    public void register(BeanRegistry registry, Environment env) {
        // for 循环动态注册：按配置的租户清单逐个注册数据源
        for (String tenant : env.getProperty("datasources", "default").split(",")) {
            if (tenant.isBlank()) continue;                       // 运行时条件
            registry.registerBean("ds-" + tenant, DataSource.class, spec -> spec
                .supplier(ctx -> {
                    DataSourceConfig cfg = ctx.bean(DataSourceConfig.class); // 取依赖
                    return new HikariDataSource(cfg.poolUrl(tenant));
                })
                .backgroundInit());                               // 后台初始化
        }
    }
}
```

> ⚠️ **backgroundInit 注意**：后台初始化的 Bean 可能**尚未就绪就被注入**——消费方应经 `ObjectProvider` 延迟取或等待就绪钩子；它只适合"迟到也能用"的增强型 Bean（缓存预热等），不适合必须立即可用的核心依赖。

### 5.2 BeanRegistrar 的能力边界

| 能做 | 不能做 |
|------|--------|
| 新增 Bean（动态/批量/条件） | 修改已注册的 BeanDefinition |
| 指定作用域/懒加载/兜底/排序 | 移除已有 Bean |
| 声明供应商与依赖（AOT 友好） | 替代 `@ConditionalOnXxx` 的"缺 Bean 才注册"（需自行判定） |
| Kotlin DSL 一等支持 | 在配置类实例化之后才介入（注册时机固定） |

> 💡 边界总结：**BeanRegistrar 是"加法"扩展点，不是"修改"扩展点**——需要改图纸用 `BeanFactoryPostProcessor`，需要删定义用 Registry API，两者职责不重叠。

### 5.3 面试追问：registerBean 规格与 @Bean 属性如何对应？

| registerBean 规格 | 对应注解写法 |
|-------------------|-------------|
| `primary()` | `@Primary` |
| `fallback()` | `@Fallback`（7.0） |
| `prototype()` | `@Scope("prototype")` |
| `lazyInit()` | `@Lazy` |
| `autowirable(false)` | `@Bean(autowireCandidate = false)` |
| `order(n)` | `@Order(n)` |
| `backgroundInit()` | 无注解等价（7.0 独有） |

> 🎯 对照意义：程序化注册与注解声明是**同一套语义的两种语法**——写 BeanRegistrar 时按注解直觉选规格项即可，不用记两套模型。

## 6. 属性文件与占位符

```properties
# db.properties
pool.size=8
pool.timeout=3s
```

| 机制 | 写法 | 说明 |
|------|------|------|
| 占位符 | `${pool.size:8}` | `:` 后为默认值；解析器 `PropertySourcesPlaceholderConfigurer` 是 `BeanFactoryPostProcessor` |
| SpEL | `#{systemProperties['user.dir']}` | `@Value` 中 `#{}` 为表达式 |
| 组合 | `${pool.size:#{...}}` | 可嵌套（少用） |
| 宽松绑定 | `spring.datasource-url` vs `spring.datasource.url` | Boot 属性可大小写/连字符互换（autoconfigure 层） |

**占位符解析的源码时序**：

```text
refresh() → invokeBeanFactoryPostProcessors
 → PropertySourcesPlaceholderConfigurer.postProcessBeanFactory
     ├─ 扫描所有 BeanDefinition 的属性值
     ├─ 逐条匹配 ${...} → 从 PropertySources 取值（找不到且无默认值 → 抛异常）
     └─ 替换后写回 BeanDefinition → 实例化时直接用真实值
```

> 💡 因此"占位符不生效"先查三件事：① 解析器有没有注册（纯 beans 场景常见）；② 属性源有没有加载（@PropertySource 顺序）；③ key 是否拼错——按此顺序排查最快。

> 🎯 **核心要点**：占位符 `${}` 解析发生在容器启动早期（BeanFactoryPostProcessor 阶段）——因此属性缺失会在启动即失败，不会等到 getBean。

### 6.1 占位符解析失败的表现与原因

| 现象 | 原因 | 解法 |
|------|------|------|
| 启动报 `Could not resolve placeholder` | key 不存在且无默认值 | 加默认值 `${k:default}` 或补配置 |
| `@Value` 拿到字符串 `"${k}"` 原样 | 占位符解析器未注册（纯 beans 场景缺 context） | 注册 `PropertySourcesPlaceholderConfigurer` 或引入 context |
| 同 key 多属性源但取到旧值 | 加载顺序问题 | 按 4.2 优先级核对 |
| SpEL 抛 `SpelEvaluationException` | 表达式写错 / 属性类型不符 | 单测表达式；`${}` 与 `#{}` 勿混用 |

> 💡 机制补充：`PropertySourcesPlaceholderConfigurer` 是 `BeanFactoryPostProcessor`——它在 BeanDefinition 注册后、实例化前扫描所有属性值中的 `${}` 文本并替换。**替换发生在实例化之前**，所以失败必然启动即失败（fail-fast），不会拖到运行期才炸。

### 6.2 属性文件与占位符的生产实践

| 实践 | 说明 |
|------|------|
| 所有外置参数给默认值 | `${k:default}` 防缺失启动失败 |
| 敏感配置不进属性文件 | 环境变量 + 密钥管理 |
| 一个配置文件一组职责 | 拆 `db.properties` / `mq.properties` 更清晰 |
| 校验配置合法性 | 启动期 `@PostConstruct` 校验或 `ConfigurationProperties` 校验注解 |
| 统一命名前缀 | `pool.size` / `db.url` 风格，避免魔法值散落 |

> 🎯 生产铁律：**配置默认值 + 启动期校验**双保险——默认值保证"缺配置也能起"，校验保证"配置错了必报错"，两者结合才能避免"配置缺失静默降级"的事故。

### 6.4 配置排查三板斧

| # | 动作 | 目的 |
|---|------|------|
| 1 | 启动打印最终配置值（`@PostConstruct` 或 ConfigurationProperties 绑定后日志） | 确认"读到的值"与预期一致 |
| 2 | `debug=true` 或开启 `ConditionEvaluationReport` 日志 | 确认自动配置条件命中与否 |
| 3 | `getEnvironment().getProperty("key")` 临时打点 | 确认属性源里实际存在什么 |

> ⚠️ 注意顺序：先查"值对不对"，再查"条件满不满足"，最后查"Bean 有没有注册"——从数据到机制逐层逼近，避免在错误层次空转。
