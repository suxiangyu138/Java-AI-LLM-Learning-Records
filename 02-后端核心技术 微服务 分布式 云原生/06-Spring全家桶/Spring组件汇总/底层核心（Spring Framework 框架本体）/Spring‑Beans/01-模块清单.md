## 1. Artifact 坐标与版本线

| 项 | 值 |
|----|----|
| GroupId | `org.springframework` |
| ArtifactId | `spring-beans` |
| 最新版本 | 7.0.6（2026-08 时点，随 Framework 7.0 主线） |
| 维护线 | 7.0.x / 7.1.x（最新）、6.2.x（Boot 3.x）、6.1.x（EOL 临近） |
| 模块名 | `org.springframework.beans` |
| Java 基线 | 7.x 要求 Java 17+ |

> 💡 实际项目几乎不直接声明 `spring-beans`——`spring-context` 会传递引入；只有做"无上下文的手写 IoC"或写扩展插件（如自定义 Starter 内嵌注册逻辑）时才需要显式坐标。

### 1.1 何时需要显式声明 spring-beans

```xml
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-beans</artifactId>
    <version>7.0.6</version>   <!-- 版本随框架主线，避免与 spring-context 混用不同大版本 -->
</dependency>
```

| 场景 | 需要显式声明？ | 说明 |
|------|:---:|------|
| 普通 Boot / Spring 应用 | 否 | spring-context 传递引入 |
| 纯 beans 手写 IoC 工具 | 是 | 只需 Factory + 后处理器 |
| 自定义 Starter / 插件 | 视情况 | 要操作 BeanDefinition 时直接依赖更明确 |
| 编译期注解处理器 | 否（一般） | 只用注解定义时 spring-core 就够 |

> ⚠️ **版本一致性铁律**：spring-beans 与 spring-core / spring-context 必须同大版本（如全 7.0.x）——混用 6.2 的 beans + 7.0 的 core，会因二进制签名不兼容直接抛 `NoSuchMethodError` / `AbstractMethodError`，且这类报错栈信息往往指向 Spring 内部，极难定位。

### 1.2 版本号与发布节奏

| 版本号段 | 含义 | 何时出现 |
|---------|------|---------|
| `7.0.0-M3` | Milestone 里程碑版 | 功能开发期（2025-03） |
| `7.0.0-RC1` | Release Candidate 候选版 | 功能冻结后（2025-09 前后） |
| `7.0.0` / `7.0.6` | GA 正式版 / 补丁版 | 2025-11 起，按月打补丁 |
| `7.1.0` | 次版本（新特性） | 2026-05 起 |

> 💡 生产选版原则：**用 GA 线的偶数补丁版（如 7.0.6）**，不追 M/R C 预览版；次版本（7.1）发布后观察一两个补丁周期再切，给生态组件（Boot、MyBatis、Cloud）留兼容窗口。

### 1.3 面试追问：为什么 beans 要单独成模块？

- **分层职责**：容器核心（beans）与周边能力（context 的事件/国际化、aop 的代理）解耦，各模块可独立演进、独立测试、独立发布；
- **嵌入式场景**：工具类项目只需"最简 IoC"——引入 context 相当于连事件、国际化一起背进来，是重量级负担；
- **依赖方向可控**：beans → core（单向）、context → beans（单向），形成**无环依赖图**，从根上杜绝模块间循环引用——这是多模块工程设计的教科书范例。

## 2. 包结构地图

```text
org.springframework.beans
├── BeanFactory / BeanNameAware / PropertyValues ...   # 顶层接口与模型
├── factory                     # ★ 容器工厂核心
│   ├── BeanFactory（顶级接口）、HierarchicalBeanFactory、ListableBeanFactory
│   ├── ConfigurableBeanFactory、AutowireCapableBeanFactory
│   ├── FactoryBean<T>、ObjectFactory<T>、ObjectProvider<T>
│   ├── InitializingBean、DisposableBean、SmartInitializingSingleton
│   ├── NamedBean、BeanNameGenerator、BeanClassLoaderAware
│   ├── annotation            # @Autowired/@Qualifier/@Value/@Required 定义与解析
│   │   └── AutowiredAnnotationBeanPostProcessor（@Autowired 注入执行器）
│   ├── config               # SingletonBeanRegistry、BeanFactoryPostProcessor 等
│   ├── support              # ★ 实现层
│   │   ├── DefaultListableBeanFactory（最常用工厂实现）
│   │   ├── AbstractAutowireCapableBeanFactory（实例化/属性填充核心逻辑）
│   │   ├── AbstractBeanFactory（getBean 模板方法）
│   │   ├── BeanDefinitionRegistry / SimpleBeanDefinitionRegistry
│   │   ├── GenericBeanDefinition / RootBeanDefinition / ChildBeanDefinition
│   │   ├── BeanDefinitionBuilder / BeanDefinitionReader
│   │   ├── BeanPostProcessor（接口在此）、InstantiationAwareBeanPostProcessor
│   │   ├── BeanRegistrar（7.0 新增）＋ BeanRegistry
│   │   └── DefaultSingletonBeanRegistry（单例缓存与三级缓存所在地）
│   └── xml                  # XML 解析（XmlBeanDefinitionReader、DefaultBeanDefinitionDocumentReader）
├── propertyeditors          # 属性编辑器（String→任意类型的转换入口）
├── type                    # TypeConverter / ConversionService 适配
└── support（beans 顶层）    # BeanUtils、MutablePropertyValues、PropertiesEditor 等工具
```

**高频面试点名类**：`BeanFactory`、`DefaultListableBeanFactory`、`DefaultSingletonBeanRegistry`（三级缓存）、`AbstractAutowireCapableBeanFactory`（属性填充）、`AutowiredAnnotationBeanPostProcessor`。

### 2.1 包职责速查

| 包 | 职责 | 必知类 |
|----|------|--------|
| `beans` 顶层 | 核心模型与接口 | `BeanFactory`、`PropertyValues`、`BeanWrapper` |
| `factory` | 容器核心接口 | `FactoryBean<T>`、`ObjectProvider<T>`、`InitializingBean` |
| `factory.annotation` | 注入注解及其解析器 | `@Autowired`、`AutowiredAnnotationBeanPostProcessor` |
| `factory.config` | 配置期扩展 | `BeanFactoryPostProcessor`、`SingletonBeanRegistry` |
| `factory.support` | ★ 实现层 | `DefaultListableBeanFactory`、`GenericBeanDefinition` |
| `factory.xml` | XML 定义解析 | `XmlBeanDefinitionReader` |
| `propertyeditors` | 字符串→任意类型转换 | `CustomDateEditor` 等 PropertyEditor |
| `type` | 类型转换适配 | `TypeConverterDelegate`、`ConversionService` 桥接 |
| `support`（顶层） | 工具 | `BeanUtils`、`BeanWrapperImpl`、`MutablePropertyValues` |

> 💡 **读源码建议入口**：`DefaultListableBeanFactory` 是"一切能力集大成"（同时实现 4 个工厂接口 + Registry）；从它的方法列表出发追调用链，比从接口往下看快得多——`doGetBean` → `createBean` → `doCreateBean` 是黄金主线。

### 2.2 面试追问：BeanFactory 与 FactoryBean 的区别

- `BeanFactory`：**容器本身**，管理"Bean 的工厂"；
- `FactoryBean<T>`：**一个特殊 Bean**，`getObject()` 产出目标对象，自身以 `&name` 注册。

> 🎯 一句话背诵：**BeanFactory 是容器，FactoryBean 是容器里的工厂对象**——面试被问"& 前缀是什么"时，答"取 FactoryBean 本身而非其产品"即满分（详见 02 篇第 5 节）。

### 2.3 包结构使用建议与常见坑

| 场景 | 该用哪个包 | 常见坑 |
|------|-----------|--------|
| 自定义注入逻辑 | `factory.annotation` + `factory.support` | 直接继承 `InstantiationAwareBeanPostProcessorAdapter` 而非裸实现接口（省样板代码） |
| 手写属性转换 | `propertyeditors` / `type` | PropertyEditor 是**线程不安全**的单线程模型，自定义时别存状态 |
| XML 存量迁移 | `factory.xml` | `XmlBeanDefinitionReader` 不负责 `context:` 命名空间——那在 context 模块 |
| 写工具类 | `support`（顶层） | `BeanUtils.copyProperties` 是浅拷贝，且忽略 null 需手动处理 |

> ⚠️ **类加载器陷阱**：`BeanClassLoaderAware` 注入的是**定义 Bean 的类加载器**——在 Boot 打包（fat jar）或热部署（devtools 双类加载器）场景下与 `Thread.currentThread().getContextClassLoader()` 不一定相同；框架类加载请始终走 Aware 给的引用，别自己猜。

### 2.4 jar 包内容速查（`jar tf` 可见）

```text
org/springframework/beans/           # 模型接口 + 工具
org/springframework/beans/factory/   # ★ 容器核心（约占包体积一半）
org/springframework/beans/propertyeditors/
org/springframework/beans/type/
META-INF/spring/                    # 7.x 的 AOT 处理单元清单等
```

> 💡 观察法：面试问"beans 模块多大"，可答"工厂实现占大头"——`factory/support` 下有 200+ 个类，这是容器机制的全部复杂度所在；模型与注解只占小头。

## 3. 依赖边界

| spring-beans 依赖 | 方向 | 说明 |
|------------------|------|------|
| `spring-core` | 依赖 | 工具类、`ConversionService`、`SpringJclLog`——beans 是"在 core 之上的容器层" |
| `spring-core` 的注解 | 依赖 | `@Component`/`@Service`/`@Configuration` 等注解定义在 core 的 `org.springframework.stereotype`，beans 消费 |
| `spring-context` | 被依赖 | context 建立在 beans 之上：`ApplicationContext` 继承 `ListableBeanFactory` |
| `spring-beans` 反向 | 无 | beans **不依赖** context/aop/web——这是分层设计的根基 |

**beans 依赖 core 的具体内容**：

| core 的哪部分 | 被 beans 怎么用 |
|--------------|----------------|
| `ConversionService` | 属性值类型转换（string → int/Date/枚举） |
| `ResolvableType` | 泛型注入匹配（`List<Repository<Order>>` 判定） |
| `Environment` / `PropertyResolver` | 占位符 `${}` 解析 |
| `@Component` 等 stereotype 注解 | 组件扫描候选判定 |
| 日志桥接 / 工具类 | 全模块基础设施 |

> 🎯 **核心要点**：`@Component` 在 spring-core，`BeanFactory` 在 spring-beans，`ApplicationContext` 在 spring-context——面试问"注解与容器各在哪个模块"时按此回答。

### 3.1 依赖方向的源码证据

```text
spring-beans 的 pom 只依赖 spring-core：
  spring-beans → spring-core（utils / asm / objenesis / log 桥接）

spring-context 反向依赖 beans：
  spring-context → spring-beans → spring-core
```

用 Maven 验证传递链：

```bash
mvn dependency:tree -Dincludes=org.springframework:*
```

```text
org.springframework:spring-context:jar:7.0.6
└─ org.springframework:spring-beans:jar:7.0.6
   └─ org.springframework:spring-core:jar:7.0.6
```

### 3.2 为什么"@Component 在 core、容器在 beans"？

- 注解定义只是"标记 + 元数据"，本身不含容器逻辑——放 core 供**所有模块**消费（aop、tx、web 都要识别组件语义）；
- beans 负责"消费这些标记"（扫描、候选判定、解析注册），职责单一；
- 若把注解定义搬进 beans，则 core 层想用注解语义就得反向依赖 beans，破坏无环依赖图。

> 🎯 面试完整链路：`@Component` 定义在 core → beans 的 `ClassPathScanningCandidateComponentProvider` 扫描 → 产出 `ScannedGenericBeanDefinition` → 注册进 Registry → context 触发整条扫描流程。

### 3.3 依赖冲突排查速查

| 现象 | 可能原因 | 排查/解法 |
|------|---------|----------|
| `NoSuchMethodError`（Spring 内部类） | 多版本 beans/core 混入 classpath | `mvn dependency:tree` 查重复；`dependencyManagement` 统一版本 |
| 同 class 两个加载器各一份 | Boot 打包 / 插件 classloader | 检查 `spring.factories` 或 SPI 文件是否打进两个 jar |
| 注解类双份（core 重复） | 传递依赖绕过 BOM | 全局版本 BOM（`spring-boot-dependencies`）统一管理 |
| `ClassNotFoundException: jakarta.*` | 6.x 之后仍用 javax 坐标 | 升级 jakarta 坐标，或确认容器支持 |

> 💡 排查第一招：`mvn dependency:tree -Dverbose` 找重复坐标；第二招：日志开启 `logging.level.org.springframework=DEBUG` 看类是从哪个 jar 加载的。

### 3.4 分层设计给我们的启示

- **依赖只能向下**：beans 可以安全地假定 core 存在，但 core 不能假定 beans——写扩展时同样遵循"高层依赖低层"；
- **能力组合而非能力堆叠**：context 不强写事件逻辑到 beans，而是复用工厂再叠加——模块设计里"复用 + 叠加"优于"修改 + 内聚"；
- **可替换性**：正因为 beans 不依赖具体容器形态，测试时可以只起一个裸工厂，毫秒级启动，不必背起整个 context。

> 💡 这个"单向依赖、接口组合"的架构思路，同样是自研多模块项目值得抄的作业——把"核心机制"与"外围能力"拆开，各自演进。

## 4. 职责切割：spring-beans vs spring-context

| 维度 | spring-beans | spring-context |
|------|-------------|----------------|
| 容器形态 | BeanFactory（懒加载、最简能力） | ApplicationContext（启动即预加载全部单例） |
| 核心接口 | BeanFactory | ApplicationContext |
| 扩展机制 | BeanPostProcessor / BeanFactoryPostProcessor | 事件监听、国际化 MessageSource、ResourceLoader |
| 扫描注解 | 不负责（注解处理器在 beans 的 annotation 包） | 负责 @ComponentScan 触发与配置类处理 |
| AOP 联动 | 只提供代理钩子（AutoProxyCreator 注册点） | 集成 ProxyFactory（spring-aop） |
| 使用场景 | 嵌入式/工具型轻量 IoC | 一切业务应用 |

> ⚠️ 写扩展点时注意：如果只依赖 beans 而不引入 context，`@ComponentScan`、事件、AOP 全都不存在——只有 Factory + PostProcessor 的原始能力。

### 4.1 何时可以只用 beans（不用 context）？

| 场景 | 只用 beans 是否可行 | 说明 |
|------|:---:|------|
| 手写 IoC 工具 / 嵌入式框架 | ✅ | `registerBean` 直连，无需任何注解 |
| 注解驱动扫描（`@ComponentScan`） | ❌ | 配置类解析在 context 的 `ConfigurationClassPostProcessor` |
| 事件 / 国际化 / 属性源 | ❌ | 全部属于 context 能力 |
| 单元测试替身容器 | ✅ | `StaticListableBeanFactory` 足够 |

### 4.2 懒加载 vs 预加载的可观测差异

```java
// 只依赖 spring-beans 的最小容器：懒加载，getBean 时才创建
DefaultListableBeanFactory factory = new DefaultListableBeanFactory();
factory.registerBean("heavy", HeavyService.class);            // 此刻不创建
System.out.println("注册完成，尚未实例化");
HeavyService heavy = factory.getBean(HeavyService.class);     // 此刻才构造

// 而 ApplicationContext（context 模块）refresh() 时即预创建全部单例
```

> ⚠️ 生产观察：Boot 应用启动慢，一部分来自"预加载全部单例"；`spring.main.lazy-initialization=true` 可换启动速度，代价是**第一个请求变慢、错误后置到首次使用**——取舍要结合业务评估。

### 4.3 职责切割的源码级验证

| 能力 | 接口/类 | 模块 | 判据 |
|------|---------|------|------|
| 单例缓存 | `DefaultSingletonBeanRegistry` | beans | 属于 beans 的 `factory.support` |
| 事件发布 | `ApplicationEventPublisher` | context | 接口在 context 的 `context.event` 包 |
| 国际化 | `MessageSource` | context | 接口在 context 顶层 |
| 属性源 | `Environment` / `PropertySources` | core | 接口在 core 的 `core.env` 包 |
| 代理工厂 | `ProxyFactory` | aop | 属于 spring-aop |

> 🎯 面试归类题万能答法：**先报接口所在的包路径，再报模块**——如"`Environment` 在 `org.springframework.core.env`，所以属性源是 core 能力"。包路径就是最可靠的归属证据。

### 4.4 面试追问：BeanFactory 与 ApplicationContext 怎么选？

| 维度 | 选 BeanFactory | 选 ApplicationContext |
|------|---------------|---------------------|
| 场景 | 嵌入式、工具型、测试 | 一切业务应用 |
| 启动 | 懒（getBean 才创建） | 预加载全部单例 |
| 能力 | 仅 IoC | + 事件/国际化/资源/扫描/AOP 集成 |
| 内部实现 | 裸工厂 | 内部仍持有一个 `DefaultListableBeanFactory` |

> 💡 深层认知：ApplicationContext **不是** BeanFactory 的替代品，而是"在工厂之上包一层企业能力"——`AbstractApplicationContext` 内嵌 `DefaultListableBeanFactory` 并代为执行 refresh 流程；所以面试说"context 是工厂 + 更多"时，可以补一句"它内部就是持有一个工厂实例"。

### 4.5 面试追问：只用 beans 能跑出什么样的应用？

| 能力 | 裸 beans 表现 | 加上 context 后 |
|------|--------------|----------------|
| 依赖注入 | ✅ 构造器/setter 均可 | 同左 + 注解驱动 |
| 生命周期回调 | ✅ 全部支持 | 同左 |
| 注解扫描 | 手动调用扫描器可以 | `@ComponentScan` 一行开启 |
| 事件 | ❌ | ✅ 同步/异步监听 |
| AOP 事务 | ❌ | ✅ 自动代理集成 |

> 🎯 结论：**beans 是"引擎"，context 是"整车"**——引擎单独能转，但上路需要整车；扩展开发时按"引擎能力 vs 整车能力"划分预期，就不会疑惑"为什么我这套代码没有事件"。

## 5. 版本兼容速查

| Spring Framework | Spring Boot | 备注 |
|------------------|-------------|------|
| 7.0.x（2025-11 起） | Boot 4.0.x | 当前主线；BeanRegistrar/@Fallback 全量可用 |
| 7.1.x（2026-05 起） | Boot 4.1.x | 最新维护线，含 PreFlightRequestFilter 等 Web 侧更新 |
| 6.2.x | Boot 3.4/3.5 | 存量主流；6.1 及以下建议升级（安全与支持） |

> 💡 **升级提示**：6.x → 7.x 时 beans 层无需代码改造的场景占绝大多数（注解、生命周期、作用域语义不变）；唯一注意点是把"手工 new BeanDefinition + 注册进 Registry"的代码迁到 `BeanRegistrar`，以及确认没有依赖被移除的 6.x 废弃 API（如 `@Lookup` 语义、`scope` 属性写法均不变）。

### 5.1 6.x → 7.x 迁移检查清单

| # | 检查项 | 动作 |
|---|--------|------|
| 1 | 手写 BeanDefinition + 手工注册 | 迁到 `BeanRegistrar`（7.0 推荐） |
| 2 | 使用了 6.x `@Deprecated` API | 按 IDE 编译警告清单逐个替换 |
| 3 | 自定义 `BeanPostProcessor` 依赖隐式顺序 | 显式实现 `Ordered` / 标注 `@Order` |
| 4 | 第三方扩展依赖 `@Fallback` | 需框架 7.x 才识别，确认扩展版本 |
| 5 | Java 版本低于 17 | 7.x 基线 Java 17+，先升 JDK 再升框架 |

### 5.2 各版本线的选择建议

| 你的基线 | 建议 |
|---------|------|
| 全新项目（2026） | 7.0.x / 7.1.x + Boot 4.x，直接用 BeanRegistrar |
| Boot 3.4/3.5 存量 | 6.2.x 维护线，机制稳定，暂不迁移 |
| 6.1 及以下 | 尽快升级：已近 EOL，安全与 bug 修复停止 |
| 需要 GraalVM 原生镜像 | 7.x 优先——BeanRegistrar 对 AOT 一等支持 |

> 💡 升级不是竞赛：6.2.x 的容器机制与 7.x 一致（注册方式除外），稳定存量优先；但新模块开发一律按 7.x 写法。

### 5.4 版本对照记忆卡

| 记忆点 | 内容 |
|--------|------|
| 6.2 ↔ Boot 3.x | 存量主流，机制稳定，javax 已迁移为 jakarta |
| 7.0 ↔ Boot 4.0 | 当前主线，BeanRegistrar / @Fallback 全量可用 |
| 7.1 ↔ Boot 4.1 | 最新维护线 |
| Java 基线 | 6.2 为 Java 17+；7.x 为 Java 17+（无额外提升） |

> 🎯 面试答版本题的金句："Spring 的版本管理是**框架与 Boot 双轨**——框架升 7.0 时 Boot 同步升 4.0，业务代码的升级成本主要在依赖坐标与废弃 API，而非容器语义。"

### 5.3 版本兼容性测试清单

| # | 验证项 | 方法 |
|---|--------|------|
| 1 | 升级后全部 Bean 注册数不变 | 启动后打印 `getBeanDefinitionNames().length` 对比 |
| 2 | 后处理器顺序稳定 | 有 `@Order` 的 BPP 打日志验证执行序 |
| 3 | 循环依赖仍被禁止 | 保持 `allow-circular-references=false` 跑全量用例 |
| 4 | AOT 构建通过 | 执行 GraalVM 原生镜像构建 job |
| 5 | 销毁回调正常 | 容器关闭日志核对 destroy 顺序 |

> ⚠️ 若升级后出现"Bean 数量变少/多"：优先排查 `@ConditionalOnXxx` 依赖的版本变化与 `spring.factories` / `.imports` 文件差异，而不是怀疑容器机制——7.x 容器语义与 6.2 完全一致。

> 💡 再给一条定位建议：升级类问题先在**最小复现工程**里做，别在生产仓库直接切版本——beans 层报错往往伴随依赖冲突，小工程能最快二分出是"框架问题"还是"项目问题"；定位清楚后再回主仓库按清单执行迁移。
