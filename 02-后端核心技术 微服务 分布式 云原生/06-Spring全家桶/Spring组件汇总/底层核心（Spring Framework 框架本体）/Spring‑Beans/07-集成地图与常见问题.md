## 1. 与其他模块的集成地图

```text
                        spring-beans（容器地基）
        ┌───────────┬──────────┬───────────┬────────────┐
        ↓           ↓          ↓           ↓            ↓
   spring-core  spring-context  spring-aop  spring-tx   spring-web(MVC)
   注解定义        Application    代理织入    事务管理器    请求作用域
   @Component     Context 事件     在 BPP     依赖容器      Web 容器集成
   工具/转换       扫描/国际化      AfterInit   托管事务     DispatcherServlet
```

| 联动点 | 机制 | 说明 |
|--------|------|------|
| core ↔ beans | `@Component` 定义于 core，beans 的扫描器消费 | 组件扫描入口 `ClassPathScanningCandidateComponentProvider` 在 beans |
| context ↔ beans | `ApplicationContext` 继承 `ListableBeanFactory` | context 把"工厂"升级为"企业容器" |
| aop ↔ beans | `AbstractAutoProxyCreator` 是 `SmartInstantiationAwareBeanPostProcessor` | AOP 代理借 beans 的初始化后阶段织入（见 [Spring-AOP-00](../Spring‑AOP/00-Spring AOP组件总览.md)） |
| tx ↔ beans | `@Transactional` 由 `BeanFactoryTransactionAttributeSourceAdvisor` 挂上代理 | 事务本质 = 容器级代理 + 通知 |
| web ↔ beans | `WebApplicationContext` 注册 request/session 作用域 | 作用域注册表 `ConfigurableBeanFactory.registerScope` |
| Boot ↔ beans | 自动配置在 refresh 中触发；`@ConditionalOnXxx` 控制 Bean 有无 | Boot 的"起步即用"= beans 容器 + 条件装配（见 Spring Boot 系列） |

**集成失败时的定位顺序**：

```text
Bean 没生效
 ├─ 模块在不在 classpath？（依赖缺失最常被忽略）
 ├─ 自动配置条件满不满足？（ConditionEvaluationReport）
 ├─ BeanDefinition 注册了没有？（getBeanDefinitionNames）
 ├─ 生命周期哪一步挂了？（BeanCreationException 的 caused by）
 └─ 代理链是否生效？（AOP 场景：getBean 拿到的是否代理）
```

> ⚠️ 模块化集成的第一课：**先确认模块在 classpath 上**——"@Transactional 不生效"的第一嫌疑不是代码，而是 spring-tx 依赖缺失或代理配置；按上面顺序查，一分钟定位。

**各模块对 beans 的依赖方向**：

```text
web / tx / aop / context   →  spring-beans（全部单向依赖）
spring-beans               →  spring-core（唯一向下依赖）
spring-beans               →  （不依赖任何上层模块）
```

> 💡 面试常考：把模块关系画成"漏斗"——core 在最底、beans 一层、context/aop/tx/web 在上层各自插拔——**beans 是所有上层能力的公共地基**，这就是"为什么 Beans 系列值得深读"的答案。

> 🎯 **核心要点**：一切"注解即能力"（@Transactional/@Cacheable/@Async/@PreAuthorize）最终都落在 **BeanPostProcessor + 代理** 这条 beans 提供的机制上——beans 是 Spring 能力的第一性原理。

### 1.1 联动点的源码类速查

| 联动 | 关键类 | 所在模块 |
|------|--------|---------|
| core ↔ beans 扫描 | `ClassPathScanningCandidateComponentProvider` | beans |
| context ↔ beans 容器 | `AnnotationConfigApplicationContext`（内嵌 DefaultListableBeanFactory） | context |
| aop ↔ beans 代理 | `AbstractAutoProxyCreator`（BeanPostProcessor） | aop |
| tx ↔ beans 事务 | `BeanFactoryTransactionAttributeSourceAdvisor` + `TransactionInterceptor` | tx |
| web ↔ beans 作用域 | `RequestScope` / `SessionScope` + `WebApplicationContextUtils` | web / context |
| Boot ↔ beans 自动配置 | `AutoConfigurationImportSelector` + `ConditionEvaluator` | boot |

> 🎯 记忆锚点：所有联动都发生在 **refresh() 的固定阶段**——后处理器注册（第 5 步）、单例预加载（第 12 步）、Web 上下文初始化（第 13 步）；知道"发生在哪个阶段"，就能预判某 Bean 此刻是否已就绪。

### 1.2 Boot 自动配置的注册链

```text
启动 → AutoConfigurationImportSelector 读取 META-INF/spring/...AutoConfiguration.imports
 → 每个自动配置类本质上就是 @Configuration（可带 @ConditionalOnXxx）
 → 走 beans 的标准流程：解析 → BeanDefinition → 实例化 → 生命周期
```

> 💡 所以"Boot 为什么注解即能力"的答案 = **自动配置类只是更多 @Configuration + 条件注解**——落地机制与手写配置完全一致，没有魔法，只有约定。

### 1.3 集成时序速查（refresh 的 Beans 关键步骤）

| 步骤 | 事件 | beans 相关动作 |
|------|------|---------------|
| 4 | `invokeBeanFactoryPostProcessors` | BFPP 执行（含自动配置导入） |
| 5 | `registerBeanPostProcessors` | 全部 BPP 注册并排序 |
| 9 | `onRefresh` | Web 容器初始化（web 模块钩子） |
| 12 | `finishBeanFactoryInitialization` | 预加载全部非懒加载单例 |
| 13 | `finishRefresh` | 发布 `ContextRefreshedEvent`（此时 Bean 全就绪） |

> 🎯 面试题"什么时候所有 Bean 都创建完了"：**第 12 步完成后、第 13 步事件发布时**——所以监听 `ContextRefreshedEvent` 或在 `SmartInitializingSingleton` 里做全量收尾最安全。

## 2. 注解能力的传递链

以 `@Transactional` 为例（面试加分逻辑链）：

```text
@Configuration 被解析（ConfigurationClassPostProcessor，BeanFactoryPostProcessor）
  → 生成 BeanDefinition（spring-beans）
  → 实例化 + 初始化（AbstractAutowireCapableBeanFactory）
  → postProcessAfterInitialization（spring-aop 的 AbstractAutoProxyCreator）
  → 检查切点命中 @Transactional → 创建 CGLIB/JDK 代理
  → 容器暴露代理对象 → 调用走事务通知（spring-tx）
```

> 💡 同一链条可套用 `@Cacheable`（spring-context 缓存）、`@Async`（spring-context 异步）、`@Retryable`（spring-retry）——面试答"Spring 为什么能注解即能力"时按此链条展开。

### 2.1 自定义"注解即能力"完整示例

以 `@Timed` 为例（BeanPostProcessor + JDK 代理实现耗时统计）：

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
public @interface Timed { }

public class TimedAnnotationBeanPostProcessor implements BeanPostProcessor {
    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if (bean.getClass().isAnnotationPresent(Timed.class)) {
            return Proxy.newProxyInstance(bean.getClass().getClassLoader(),
                    bean.getClass().getInterfaces(), (proxy, method, args) -> {
                        long start = System.nanoTime();
                        Object result = method.invoke(bean, args);
                        log.info("{} 耗时 {}ms", method.getName(),
                                (System.nanoTime() - start) / 1_000_000);
                        return result;
                    });
        }
        return bean;
    }
}

@Configuration
public class AopConfig {
    @Bean
    public TimedAnnotationBeanPostProcessor timedBpp() { return new TimedAnnotationBeanPostProcessor(); }
}
```

> ⚠️ 该示例演示的是**机制而非工程方案**——JDK 代理要求接口；生产用 spring-aop 的 `AbstractAutoProxyCreator` + Advisor 更完善（可排序、可组合）。示例的价值在于证明"注解即能力 = BPP + 代理"这句话。

### 2.2 各能力注解的处理器对照

| 注解 | 处理器 | 所在模块 |
|------|--------|---------|
| `@Transactional` | `BeanFactoryTransactionAttributeSourceAdvisor` | tx |
| `@Cacheable` | `BeanFactoryCacheOperationSourceAdvisor` | context |
| `@Async` | `AsyncAnnotationBeanPostProcessor` | context |
| `@Scheduled` | `ScheduledAnnotationBeanPostProcessor` | context |
| `@PreAuthorize` | Spring Security 的 Advisor | security |
| `@Retryable` | `RetryAnnotationPostProcessor` | spring-retry |

> 🎯 面试金句：**"Spring 的注解能力 = 一个后处理器 + 一个代理工厂"**——任何注解能力都能用这个公式拆解，面试答"注解为什么即能力"时先抛公式再展开。

### 2.3 注解能力链的通用五步（背诵版）

```text
① 元数据：注解标注在类/方法上（core 定义）
② 解析：配置类处理期转成 BeanDefinition（beans）
③ 创建：实例化 + 初始化（beans 生命周期）
④ 代理：后处理器在 AfterInitialization 检查注解并织入（aop）
⑤ 生效：容器暴露代理对象，调用走拦截器（对应能力模块）
```

> 💡 任何注解能力（事务/缓存/异步/安全/重试）都可以按这五步作答——**背会五步，胜过背十个注解的处理类**；面试官追问哪一步，再展开对应模块细节。

## 3. 高频问题与排查速查

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| `NoSuchBeanDefinitionException` | 未扫描到/类型不对/条件不满足 | ① `@ComponentScan` 覆盖？② 类上有 `@Profile`/`@Conditional`？③ 用 `ApplicationContext.getBeanNamesForType(Clazz)` 列全名 |
| `NoUniqueBeanDefinitionException` | 多实现无裁决 | `@Primary` / `@Qualifier` / `@Fallback`（7.0） |
| `BeanCurrentlyInCreationException` | 构造器循环依赖（或开关关闭） | 重构拆循环；`@Lazy` 注入；不要开 `allow-circular-references` |
| 注入的 List/Map 为空 | 实现类没进容器 | 检查实现类注解/扫描路径；接口多态是否被 `autowireCandidate=false` |
| 原型 Bean 永远是同一实例 | 单例快照注入 | `ObjectProvider` / `@Lookup` / ScopedProxy（见 05 篇） |
| 自调用 `this.method()` 能力不生效 | 绕过代理 | 注入自身代理（`ObjectProvider<Self>`）或拆类 |
| `@Bean` 对象被创建两次 | Full/Lite 模式混用 | `@Configuration` 类必须为 Full（proxyBeanMethods 默认 true）；见 [03-注解与元数据速查](03-注解与元数据速查.md) |
| `@Value` 注入 null/启动报占位符错 | 属性源缺失 | 检查 `@PropertySource`/Boot 配置；用默认值 `${k:default}`；确认解析器已注册 |
| destroyMethod 意外被调用 | 默认推断 `close()` 等 | 显式 `destroyMethod = ""` |
| Bean 名字冲突覆盖 | 同名定义 | `spring.main.allow-bean-definition-overriding` 仅开发期开；生产改名/拆包 |
| 升级 6.x→7.x 后注册类不生效 | 仍用手写 BeanDefinition 旧 API | 迁移到 `BeanRegistrar`（7.0） |
| `@Value` 注入 null（不报错） | 属性存在但类型转换失败被吞？ | 实为 key 缺失且无默认值 → null；用 `${k:default}` 并启动期校验 |
| 同类型 Bean 注入到错误实例 | 多个 Bean 同名/同类型交错 | 打印 `getBeanNamesForType` 清单 + `@Qualifier` 点名 |
| 代理后 instanceof 判断失败 | 对象是 CGLIB/JDK 代理类 | 用 `AopUtils.getTargetClass` 或按接口判断 |

> ⚠️ **排查三板斧**：① `ContextRefreshedEvent` 后打印 `getBeanDefinitionNames()` 看注册全量；② 看启动日志的"Bean 创建"顺序与失败栈（哪个阶段抛的）；③ 区分"没注册"（扫描/条件问题）与"注册了没注入"（裁决/快照问题）。

### 3.1 扩展高频问题表

| 现象 | 根因 | 解法 |
|------|------|------|
| 两个配置类定义同名 Bean，注入总取后者 | 定义覆盖（Boot 默认禁止→直接报错） | 改名去重；确认覆盖语义后再开开关 |
| `@ConfigurationProperties` 类没被注册 | 缺 `@EnableConfigurationProperties` 或不在扫描路径 | 用前者显式注册 |
| Bean 初始化顺序不符合预期 | 隐式依赖顺序 | 显式 `@DependsOn`；或重构消除隐式依赖 |
| 父子容器中 `getBean` 找到父容器的 Bean | Hierarchical 向上委派 | 子容器注册同名定义或 `setAllowBeanDefinitionOverriding` |
| 自定义 BPP 未生效 | 未注册为 Bean / 注册时机不对 | 确认 `@Component` / `@Bean` 声明且实现正确接口 |
| 自调用 `this.method()` 事务不生效 | 绕过代理（this 是裸对象） | 注入自身代理（`ObjectProvider<Self>`）或拆类 |

> 💡 自调用问题的本质：**代理是容器暴露的 Bean，`this` 不是**——任何"注解即能力"在自调用时都会失效（事务/缓存/异步/重试全部适用），这是 beans 机制的第一性推论。

### 3.2 排查工具清单

| 工具 | 用途 |
|------|------|
| Actuator `/beans` 端点 | 生产环境看 Bean 全量 + 依赖关系（JSON） |
| `logging.level.org.springframework.beans=DEBUG` | 看 BeanDefinition 注册过程 |
| `ConditionEvaluationReport`（Boot debug=true） | 条件装配逐条判定结果 |
| `getBeanDefinitionNames()` + `getBeanNamesForType` | 快速区分"没注册"与"没注入" |
| 断点调试 | `AbstractAutowireCapableBeanFactory.doCreateBean` 主干 |

> 🎯 排查口诀：**先问"注册了吗"，再问"注入对了吗"，最后问"代理到了吗"**——三个问题对应三个工具组，按序走完基本定位 90% 的 Bean 问题。

### 3.3 完整排查案例：注入总是 null

| 步骤 | 动作 | 结论 |
|------|------|------|
| ① | 确认类被容器管理（`getBeanNamesForType`） | 无 → 扫描/条件问题（查 2 与 3 节） |
| ② | 确认注入点类型匹配（`getBeanNamesForType(T.class)` 清单） | 空 → 类型/泛型问题 |
| ③ | 确认裁决唯一（多候选？） | 多 → @Primary/@Qualifier |
| ④ | 确认字段非静态、非 new 创建 | 是 → 容器不管理（见 03 篇 3.1） |
| ⑤ | 确认代理链路（AOP 后引用是否被替换） | 替换 → 按接口/目标类判断 |

> 💡 该案例是"三板斧"的落地示范——多数"注入 null"都能在 ①② 两步定位，剩下的是代理或创建方式问题。
