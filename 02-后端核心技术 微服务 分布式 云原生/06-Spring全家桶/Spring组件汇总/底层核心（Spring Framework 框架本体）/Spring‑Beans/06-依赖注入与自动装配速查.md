## 1. 三种注入方式对比

| 方式 | 写法 | 优点 | 缺点 | 推荐 |
|------|------|------|------|:---:|
| 构造器 | `ctor(Repo r)` | 不可变(final)、显式依赖、易测试、可防循环依赖 | 参数多时啰嗦（可用 @RequiredArgsConstructor 缓解） | ✅ 首选 |
| Setter | `setRepo(Repo r)` | 可选依赖友好、可重配 | 可变对象、可注入半成品 | 可选依赖时 |
| 字段 | `@Autowired Repo r;` | 最简 | 难测试、隐藏依赖、不可变违规 | ❌ 仅快速原型 |

```java
// 首选：构造器注入（Spring 4.3+ 单构造器可省略 @Autowired）
@Service
@RequiredArgsConstructor                      // Lombok：final 字段自动生成构造器
public class OrderService {
    private final OrderRepo orderRepo;
    private final PaymentClient paymentClient;
}
```

> 🎯 **核心要点**：构造器注入 = 依赖即构造函数签名，容器发现不了的依赖在编译期就失败；字段注入的 `NPE 运行时才炸`。

## 2. @Autowired 装配规则

| 步骤 | 规则 | 失败行为 |
|------|------|---------|
| ① | 按类型匹配候选（含父接口/超类） | 0 个 → `NoSuchBeanDefinitionException` |
| ② | 唯一 → 直接注入 | 多个 → 进入裁决 |
| ③ | 多候选裁决（@Primary → 名字回退 → @Qualifier） | 仍不唯一 → `NoUniqueBeanDefinitionException` |
| ④ | 泛型擦除后的类型匹配（`List<T>`、`Map<String,T>` 特殊处理） | - |
| ⑤ | `required=false` 时可选注入 null | 默认 `required=true` |

**可选注入三种写法**：

```java
@Autowired(required = false)                       // ① 注解开关（字段/setter）
private DataSource optionalDs;

// ② 现代推荐：ObjectProvider（无 null 语义，可给默认值）
public ReportService(ObjectProvider<DataSource> dsProvider) {
    this.ds = dsProvider.getIfAvailable(() -> new HikariDataSource());
}

// ③ JDK 9+：Optional 参数
public ReportService(Optional<DataSource> ds) { ... }
```

## 3. 冲突解决与裁决链

```text
候选多个时裁决顺序：
  1. @Qualifier 精确匹配（名字/限定符）      → 命中即赢
  2. @Primary 标记的候选                    → 首选
  3. 参数名/字段名与 Bean 名回退匹配         → 命名回退
  4. 仍然多个                              → NoUniqueBeanDefinitionException
  ※ @Fallback（7.0）标注的候选只在"除它之外没有其他候选"时参与
```

```java
@Configuration
class PaymentConfig {
    @Bean @Primary  public PaymentClient alipay()   { ... }
    @Bean @Fallback public PaymentClient mock()     { ... }   // 7.0：仅无其他候选时兜底
    @Bean           public PaymentClient wechat()   { ... }
}

// 注入 wechat：@Qualifier 直接命中；注入默认：alipay（@Primary）；测试环境只注册 mock：自动选中
```

> 💡 `@Primary` vs `@Fallback`：前者"有多个时我优先"，后者"只有我一个时才用我"——兜底实现（降级/测试替身）场景用 `@Fallback` 更安全，不会意外盖掉业务实现。

## 4. 泛型注入与集合注入

| 注入形态 | 行为 |
|---------|------|
| `List<T>` | 注入**全部** T 类型 Bean（按 `@Order`/Ordered 排序） |
| `Map<String, T>` | key=Bean 名，value=Bean 实例 |
| `Optional<T>` | 有则装、无则空 |
| `ObjectProvider<T>` | 延迟/可选/流式 |
| 泛型限定 | `@Autowired Map<String, Repository<Order>>` 按**泛型实参**匹配候选 |

```java
// 策略模式：容器自动收集所有策略实现
@Service
public class OrderHandler {
    private final List<OrderValidator> validators;      // 自动注入全部实现

    public OrderHandler(List<OrderValidator> validators) {
        this.validators = validators;
    }
}

@Bean
public OrderValidator a() { ... }

@Bean
@Order(1)                        // 控制集合顺序
public OrderValidator b() { ... }
```

> 🎯 **核心要点**：集合注入 = 容器内建策略注册表——新增实现类无需改装配代码，是"开闭原则"在 Spring 中的天然体现（面试高频"如何实现策略模式"答案）。

## 5. @Resource vs @Autowired

| 维度 | `@Autowired`（Spring） | `@Resource`（JSR-250） |
|------|------------------------|------------------------|
| 匹配顺序 | 类型优先 | **名字优先**，找不到再按类型 |
| 可用位置 | 字段/构造器/setter/参数 | 字段/setter（**不支持构造器**） |
| 多候选时 | @Primary/@Qualifier 裁决 | `name` 属性精确匹配 |
| 依赖归属 | spring-beans | `jakarta.annotation`（JDK 移出后由 Jakarta EE 提供） |
| 推荐 | ✅ 团队标准（构造器注入） | 兼容 JSR 规范或需要名字语义时 |

> ⚠️ 常见误解：二者混用时同名 Bean 行为不同——同一接口多个实现时，`@Resource` 按字段名找，`@Autowired` 按类型找并可能抛唯一性异常。

## 6. 循环依赖：成因、处理与规避

**成因**：A 需要 B、B 需要 A（构造器或字段注入引发）。

| 场景 | 能否解决 | 说明 |
|------|:---:|------|
| 字段/setter 注入（单例） | ✅ | 三级缓存：提前暴露半成品对象引用（`ObjectFactory`） |
| 构造器注入 | ❌ | 构造参数必须完整对象，无法提前暴露 → 启动即失败 |
| 原型 Bean 循环 | ❌ | 原型不缓存、每次新实例 → 无限递归 |
| @Async/@Lazy 代理 Bean | 部分 | 依赖代理初始化时机，`@Lazy` 注入代理可解 |

**三级缓存（面试必背）**：

```text
1 级 singletonObjects         完成的单例
2 级 earlySingletonObjects   提前暴露的半成品（代理前）
3 级 singletonFactories      ObjectFactory 工厂（延迟到"确实需要提前暴露"才生成）

流程：A 创建 → 填 B → B 创建 → 填 A（发现 A 未完成）→ 从 3 级取 ObjectFactory
     → 生成早期引用 → 完成 B → A 继续填充完成 → 放入 1 级
```

> ⚠️ **Boot 4 / Framework 7 默认禁止循环依赖**：`spring.main.allow-circular-references=false`——启动直接报 `BeanCurrentlyInCreationException`。规范姿势：**重构消除**（拆类/接口抽象/事件解耦/`@Lazy` 注入），而不是开开关。

**规避三板斧**：

```java
// ① 重构：把 A↔B 的调用拆成单向依赖（接口 + 回调/事件）
// ② @Lazy：延迟注入代理，真正调用时才解析
public A(B b) { this.b = b; }   // A 依赖 B

// ③ 事件解耦：A 发事件，B 监听——消除编译期强依赖
```
