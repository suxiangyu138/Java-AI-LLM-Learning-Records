## 1. 三种注入方式对比

| 方式 | 写法 | 优点 | 缺点 | 推荐 |
|------|------|------|------|:---:|
| 构造器 | `ctor(Repo r)` | 不可变(final)、显式依赖、易测试、可防循环依赖 | 参数多时啰嗦（可用 @RequiredArgsConstructor 缓解） | ✅ 首选 |
| Setter | `setRepo(Repo r)` | 可选依赖友好、可重配 | 可变对象、可注入半成品 | 可选依赖时 |
| 字段 | `@Autowired Repo r;` | 最简 | 难测试、隐藏依赖、不可变违规 | ❌ 仅快速原型 |

```java
// 首选：构造器注入（Spring 4.3+ 单构造器可省略 @Autowired）
@Service
@RequiredArgsConstructor                      // Lombok：final 字段自动生成构造器
public class OrderService {
    private final OrderRepo orderRepo;
    private final PaymentClient paymentClient;
}
```

> 🎯 **核心要点**：构造器注入 = 依赖即构造函数签名，容器发现不了的依赖在编译期就失败；字段注入的 `NPE 运行时才炸`。

### 1.1 三种注入的深层对比

| 维度 | 构造器 | Setter | 字段 |
|------|--------|--------|------|
| 依赖可见性 | 显式（签名即契约） | 中（setter 名） | 隐藏 |
| 不可变性 | ✅ final | ❌ | ❌ |
| 循环依赖支持 | ❌ | ✅ | ✅ |
| 单元测试 | `new` 传参即可 | set 方法 | 反射/容器 |
| 框架侵入 | 无 | 无 | 反射注入 |
| 官方推荐 | ✅ 首选 | 可选依赖 | 不推荐 |

> 🎯 面试完整回答框架：**构造器注入三大理由 = 不可变性 + 显式契约 + 防循环依赖**；Setter 唯一合法场景是"可选依赖"（可空、可重配）；字段注入仅限快速原型。

### 1.2 面试追问：为什么说构造器注入能"防"循环依赖？

字段/setter 注入绕开循环依赖靠三级缓存"提前暴露半成品"；而构造器注入时**构造参数必须是完整对象**——A 构造需要 B 完成、B 构造需要 A 完成，死锁无法提前暴露，启动即 `BeanCurrentlyInCreationException`。所以"防"不是魔法，是**把问题从运行期提前到启动期暴露**——看似更严格，实则是更安全的失败模式。

### 1.3 多构造器时的注入规则

| 构造器情况 | 容器行为 |
|-----------|---------|
| 只有一个构造器 | 直接用它（无需注解） |
| 多个构造器 + 一个标 `@Autowired` | 用标注的那个 |
| 多个构造器 + 都未标注 | 用无参构造（没有则报错） |

> ⚠️ Lombok `@RequiredArgsConstructor` 生成"全部 final 字段"构造器——**与多个非 final 字段并存时注意**：生成的是全参构造器，容器可能按"唯一构造器"直接注入而忽略普通字段，行为与直觉不同；需要时补 `@Autowired` 或拆分设计。

## 2. @Autowired 装配规则

| 步骤 | 规则 | 失败行为 |
|------|------|---------|
| ① | 按类型匹配候选（含父接口/超类） | 0 个 → `NoSuchBeanDefinitionException` |
| ② | 唯一 → 直接注入 | 多个 → 进入裁决 |
| ③ | 多候选裁决（@Primary → 名字回退 → @Qualifier） | 仍不唯一 → `NoUniqueBeanDefinitionException` |
| ④ | 泛型擦除后的类型匹配（`List<T>`、`Map<String,T>` 特殊处理） | - |
| ⑤ | `required=false` 时可选注入 null | 默认 `required=true` |

**可选注入三种写法**：

```java
@Autowired(required = false)                       // ① 注解开关（字段/setter）
private DataSource optionalDs;

// ② 现代推荐：ObjectProvider（无 null 语义，可给默认值）
public ReportService(ObjectProvider<DataSource> dsProvider) {
    this.ds = dsProvider.getIfAvailable(() -> new HikariDataSource());
}

// ③ JDK 9+：Optional 参数
public ReportService(Optional<DataSource> ds) { ... }
```

**可选依赖选型总结**：

| 需求 | 首选 |
|------|------|
| 可选 + 需要默认值 | `ObjectProvider.getIfAvailable(Supplier)` |
| 可选 + 只想要"有/无"判断 | `Optional<T>` 参数 |
| 老代码兼容 | `@Autowired(required = false)` |
| 多个可选实现按条件选 | `ObjectProvider.stream()` |

### 2.1 @Autowired 的执行器源码链路

```text
AutowiredAnnotationBeanPostProcessor
 └─ postProcessProperties（在 populateBean 中触发）
     ├─ InjectionMetadata（注解解析缓存：字段 + setter + 方法）
     ├─ 逐个执行注入（AutowiredFieldElement / AutowiredMethodElement）
     └─ resolveDependency 依赖查找：
         ├─ ObjectFactory / ObjectProvider 包装
         ├─ Optional 包装
         ├─ @Value 占位符解析
         ├─ Map / List 集合展开
         └─ 普通类型 → 类型匹配 + 裁决链（见第 3 节）
```

> 💡 面试加分：`InjectionMetadata` 对每个 Bean **只解析一次注解**并缓存——`@Autowired` 的开销在"依赖查找"而非"注解解析"；这也是为什么字段多时性能影响可忽略。

### 2.2 required=false / Optional / ObjectProvider 三者差异

| 写法 | 缺 Bean 时 | 多候选时 | 延迟性 |
|------|-----------|---------|--------|
| `@Autowired(required = false)` | 注入 null | 正常裁决 | 无 |
| `Optional<T>` 参数 | 空 Optional | 正常裁决 | 无 |
| `ObjectProvider<T>` | `getIfAvailable` 返回 null/默认 | `getIfUnique` / `stream()` 可选 | ✅ 每次现取 |

> ⚠️ 细节：`Optional` 与 `ObjectProvider` 只能在**方法参数/构造器参数**中注入；字段上只有 `@Autowired(required=false)` 或直接注入 Provider 类型字段。三者混用时行为差异是高频面试题。

## 3. 冲突解决与裁决链

```text
候选多个时裁决顺序：
  1. @Qualifier 精确匹配（名字/限定符）      → 命中即赢
  2. @Primary 标记的候选                    → 首选
  3. 参数名/字段名与 Bean 名回退匹配         → 命名回退
  4. 仍然多个                              → NoUniqueBeanDefinitionException
  ※ @Fallback（7.0）标注的候选只在"除它之外没有其他候选"时参与
```

```java
@Configuration
class PaymentConfig {
    @Bean @Primary  public PaymentClient alipay()   { ... }
    @Bean @Fallback public PaymentClient mock()     { ... }   // 7.0：仅无其他候选时兜底
    @Bean           public PaymentClient wechat()   { ... }
}

// 注入 wechat：@Qualifier 直接命中；注入默认：alipay（@Primary）；测试环境只注册 mock：自动选中
```

> 💡 `@Primary` vs `@Fallback`：前者"有多个时我优先"，后者"只有我一个时才用我"——兜底实现（降级/测试替身）场景用 `@Fallback` 更安全，不会意外盖掉业务实现。

### 3.1 裁决链的源码级依据

```text
DefaultListableBeanFactory.resolveDependency
 ├─ 候选收集：getBeanNamesForType(type)（含父接口、泛型实参展开）
 ├─ 过滤：autowireCandidate = false 的候选排除
 ├─ 多候选时：
 │   ├─ @Primary 标记者 → 命中
 │   ├─ @Fallback（7.0）：除它外无候选才命中
 │   └─ 参数名/字段名与 Bean 名一致 → 回退命中
 └─ 仍多 → NoUniqueBeanDefinitionException（异常信息含候选清单）
```

> 🎯 命名回退的前提：编译期保留参数名（`-parameters`）——Maven 默认不保留、IDE 运行通常保留；**"本地好好的、线上报多候选"**先查编译参数，再查裁决注解。

### 3.2 生产实践：多实现注入的正确姿势

| 场景 | 推荐 |
|------|------|
| 明确要某一个实现 | `@Qualifier("name")` 或组合限定符 |
| 默认 + 兜底 | `@Primary` + `@Fallback`（7.0） |
| 全部实现都要 | `List<T>` 注入（策略模式） |
| 按运行条件选 | `ObjectProvider.stream()` + 过滤 |
| 接口本身可选 | `@Autowired(required=false)` 慎用（隐藏问题） |

> ⚠️ 反模式：接口多实现时大量使用 `@Autowired(required=false)`——掩盖配置错误，运行期才 NPE；正确做法是让"没有默认实现"尽早暴露。

## 4. 泛型注入与集合注入

| 注入形态 | 行为 |
|---------|------|
| `List<T>` | 注入**全部** T 类型 Bean（按 `@Order`/Ordered 排序） |
| `Map<String, T>` | key=Bean 名，value=Bean 实例 |
| `Optional<T>` | 有则装、无则空 |
| `ObjectProvider<T>` | 延迟/可选/流式 |
| 泛型限定 | `@Autowired Map<String, Repository<Order>>` 按**泛型实参**匹配候选 |

```java
// 策略模式：容器自动收集所有策略实现
@Service
public class OrderHandler {
    private final List<OrderValidator> validators;      // 自动注入全部实现

    public OrderHandler(List<OrderValidator> validators) {
        this.validators = validators;
    }
}

@Bean
public OrderValidator a() { ... }

@Bean
@Order(1)                        // 控制集合顺序
public OrderValidator b() { ... }
```

> 🎯 **核心要点**：集合注入 = 容器内建策略注册表——新增实现类无需改装配代码，是"开闭原则"在 Spring 中的天然体现（面试高频"如何实现策略模式"答案）。

### 4.1 集合注入的排序细节

| 机制 | 说明 |
|------|------|
| `@Order(n)` / `Ordered` | 升序排列（数值小在前） |
| `@Priority`（JSR-250） | 优先级高的在前（与 @Order 相反语义） |
| 无排序标注 | 注册顺序（不稳定，勿依赖） |
| Map 注入 | key = Bean 名，value = 实例（LinkedHashMap，同样排序） |

```java
// 泛型匹配的底层：ResolvableType
@Autowired
private Map<String, Repository<Order>> orderRepos;
// 只匹配 Repository<Order>，不会误收 Repository<User>
```

> 💡 泛型匹配机制：Spring 用 `ResolvableType` 解析字段的泛型签名，`getBeanNamesForType` 按"泛型实参一致"过滤——这就是 `Repository<Order>` 与 `Repository<User>` 互不误配的根源；面试问"泛型注入怎么实现的"答 `ResolvableType` 即加分。

### 4.2 集合注入的常见坑

| 坑 | 现象 | 解法 |
|----|------|------|
| 空集合 | 没注册任何实现 | 查扫描路径 / 条件 / autowireCandidate |
| 顺序乱 | 依赖注册顺序 | 全部加 `@Order` |
| 混入不想要的实现 | @Fallback 兜底也进集合 | 显式 `@Qualifier` 点名注入 |
| 类型擦除误收 | `List<Object>` 收全部 | 用泛型实参限定（ResolvableType） |

## 5. @Resource vs @Autowired

| 维度 | `@Autowired`（Spring） | `@Resource`（JSR-250） |
|------|------------------------|------------------------|
| 匹配顺序 | 类型优先 | **名字优先**，找不到再按类型 |
| 可用位置 | 字段/构造器/setter/参数 | 字段/setter（**不支持构造器**） |
| 多候选时 | @Primary/@Qualifier 裁决 | `name` 属性精确匹配 |
| 依赖归属 | spring-beans | `jakarta.annotation`（JDK 移出后由 Jakarta EE 提供） |
| 推荐 | ✅ 团队标准（构造器注入） | 兼容 JSR 规范或需要名字语义时 |

> ⚠️ 常见误解：二者混用时同名 Bean 行为不同——同一接口多个实现时，`@Resource` 按字段名找，`@Autowired` 按类型找并可能抛唯一性异常。

> 🎯 记忆口诀：**@Resource 看"叫什么名字"，@Autowired 看"是什么类型"**——一个对名、一个对型，混用时先想清楚依赖的唯一标识。

### 5.0 逐条规则对照：@Autowired 与 @Resource 行为差异

| 场景 | @Autowired | @Resource |
|------|-----------|-----------|
| 单实现注入 | 类型命中 | 名字命中（字段名=Bean 名时也成功） |
| 多实现、字段名恰好匹配 | 先类型后回退名字 | 名字直接命中 |
| 多实现、字段名不匹配 | 报唯一性异常 | 名字找不到 → 按类型找（仍多则报错） |
| 构造器参数 | ✅ | ❌（不支持） |
| 指定名称 | `@Qualifier("x")` | `name = "x"` |
| 指定首选 | `@Primary` 候选 | 无（只能 name 点名） |

> ⚠️ 最阴的坑：**接口多实现 + 字段名恰好等于某个实现 Bean 名**——`@Resource` 静默选中它，`@Autowired` 可能报唯一性异常或按名字回退选中同样的实现；同一段代码换注解后行为可能不一致，评审时别混用。

### 5.1 混用与迁移建议

| 现状 | 建议 |
|------|------|
| 新代码 | 统一构造器注入 + final（团队标准） |
| 老代码字段注入 | 按模块渐进迁移，新类不再用 |
| 与 @Resource 混用 | 同一文件内统一一种；`@Resource` 不支持构造器 |
| 框架内部代码 | 尊重框架自身选择（如 Boot 自动配置常用字段注入） |

> ⚠️ 混用最大风险：同一 Bean 的依赖一部分 `@Autowired`（类型）一部分 `@Resource`（名字），同名不同类时行为不一致——Code Review 时统一风格，别让两种语义并存。

### 5.2 面试追问：@Inject（JSR-330）与 @Autowired 什么关系？

- `@Inject` 语义与 `@Autowired` 基本等价（类型优先），但**没有 `required` 属性**——缺 Bean 直接报错，无法标记可选；
- `@Qualifier` 注解是两个体系共用的（JSR-330 也定义了它）；
- 选型：团队用 Spring 就 `@Autowired`；追求 JSR 标准兼容（换容器不换代码）才用 `@Inject`。

## 6. 循环依赖：成因、处理与规避

**成因**：A 需要 B、B 需要 A（构造器或字段注入引发）。

| 场景 | 能否解决 | 说明 |
|------|:---:|------|
| 字段/setter 注入（单例） | ✅ | 三级缓存：提前暴露半成品对象引用（`ObjectFactory`） |
| 构造器注入 | ❌ | 构造参数必须完整对象，无法提前暴露 → 启动即失败 |
| 原型 Bean 循环 | ❌ | 原型不缓存、每次新实例 → 无限递归 |
| @Async/@Lazy 代理 Bean | 部分 | 依赖代理初始化时机，`@Lazy` 注入代理可解 |

**三级缓存（面试必背）**：

```text
1 级 singletonObjects         完成的单例
2 级 earlySingletonObjects   提前暴露的半成品（代理前）
3 级 singletonFactories      ObjectFactory 工厂（延迟到"确实需要提前暴露"才生成）

流程：A 创建 → 填 B → B 创建 → 填 A（发现 A 未完成）→ 从 3 级取 ObjectFactory
     → 生成早期引用 → 完成 B → A 继续填充完成 → 放入 1 级
```

> ⚠️ **Boot 4 / Framework 7 默认禁止循环依赖**：`spring.main.allow-circular-references=false`——启动直接报 `BeanCurrentlyInCreationException`。规范姿势：**重构消除**（拆类/接口抽象/事件解耦/`@Lazy` 注入），而不是开开关。

**规避三板斧**：

```java
// ① 重构：把 A↔B 的调用拆成单向依赖（接口 + 回调/事件）
// ② @Lazy：延迟注入代理，真正调用时才解析
public A(B b) { this.b = b; }   // A 依赖 B

// ③ 事件解耦：A 发事件，B 监听——消除编译期强依赖
```

### 6.1 三级缓存为什么是"三级"而不是"两级"？

| 级别 | 存什么 | 为什么需要 |
|------|--------|-----------|
| 1 `singletonObjects` | 完整单例 | 正常读取 |
| 2 `earlySingletonObjects` | 已生成的早期引用 | 生成过就缓存，避免重复走工厂 |
| 3 `singletonFactories` | `ObjectFactory` lambda | **延迟生成早期引用** |

> 🎯 面试必答：第三级存 lambda 而非直接存对象，原因有二——① **延迟**：绝大多数 Bean 不需要提前暴露，不必为每个 Bean 生成早期引用（含 AOP 判定），只有真正被循环引用时才调用工厂；② **AOP 一致性**：工厂里可能提前应用代理（`AbstractAutoProxyCreator` 的早期引用逻辑），保证"早期引用 == 最终 Bean"——若二级直接存原始对象，代理后引用就错位了。

### 6.2 循环依赖的排查清单

| 步骤 | 做法 |
|------|------|
| 1 确认报错阶段 | `BeanCurrentlyInCreationException` 栈里看哪个 Bean 创建链 |
| 2 看依赖链 | 日志打印"currently in creation"的 Bean 清单 |
| 3 分类定性 | 构造器环 → 重构；字段环 → 已默认禁止，同样重构 |
| 4 选择解法 | `@Lazy` 注入（简单）、拆类、事件化、`ObjectProvider` 延迟 |

> ⚠️ 生产铁律：**循环依赖 = 设计信号，不是配置问题**——出现即意味着职责边界模糊；`allow-circular-references=true` 只用于兼容存量，新代码一律重构消除。

### 6.3 面试追问：@Async / @Lazy 场景为什么循环依赖仍能过？

- `@Lazy` 注入的是**代理**，构造时不需要真实对象——环在"构造期"被代理切断；
- `@Async` 同理：代理对象提前创建，依赖它的 Bean 拿到代理即可完成构造；
- 结论：**循环依赖的"解法"本质都是"让一方不再直接需要完整对象"**——代理、Provider、事件都是这个思路的变体。
