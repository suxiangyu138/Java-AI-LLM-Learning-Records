## 1. Resource：资源统一抽象

`Resource`（`org.springframework.core.io`）把"类路径文件、磁盘文件、URL、字节数组、流"统一成同一接口：

```java
public interface Resource extends InputStreamSource {
    boolean exists();
    InputStream getInputStream() throws IOException;      // ★ 唯一必须可用的能力
    String getFilename();
    String getDescription();                               // 日志友好描述
    URL getURL() / URI getURI() / File getFile();          // 视实现可用
    default boolean isFile() / isReadable() / contentLength() ...
}
```

| 能力 | 说明 |
|------|------|
| 读流 | `getInputStream()` ——**唯一跨实现安全**的读取方式 |
| 元数据 | exists / isReadable / contentLength / lastModified |
| 定位 | getURL / getFile（**仅特定实现可用**，jar 内抛错） |
| 写 | `WritableResource.getOutputStream()`（FileSystemResource 等） |

> 🎯 **核心要点**：读资源**只用 `getInputStream()`**——`getFile()` 在 jar 打包后必然失败（类路径资源不存在"文件"）；描述/日志用 `getDescription()`。

**Resource 接口方法全解析（源码级）**：

| 方法 | 语义 | 何时不可用 |
|------|------|-----------|
| `exists()` | 资源是否存在 | - |
| `isReadable()` | 是否可读（存在且非目录） | 目录资源返回 false |
| `isOpen()` | 是否为一次性流（InputStreamResource） | 返回 true 时不可重复读 |
| `isFile()` | 是否映射为真实文件 | jar 内类路径资源返回 false |
| `getURL()` / `getURI()` | 统一资源定位符/标识符 | 内存资源（ByteArray）不可用 |
| `getFile()` | 文件系统句柄 | **jar 内/内存资源抛 IOException** |
| `contentLength()` / `lastModified()` | 元数据 | 网络资源可能抛异常 |
| `createRelative(relativePath)` | 相对路径创建新资源 | 少数实现不支持 |
| `getDescription()` | 日志友好描述（**唯一保证可用**） | - |

```java
// 万能读取姿势：防御性判断 + 流读取
public String readAsString(Resource res, Charset charset) {
    Assert.notNull(res, "resource must not be null");
    Assert.state(res.exists(), () -> "resource not found: " + res.getDescription());
    try (InputStream in = res.getInputStream()) {      // 唯一跨实现安全的入口
        return new String(in.readAllBytes(), charset);
    } catch (IOException e) {
        throw new IllegalStateException("read failed: " + res.getDescription(), e);
    }
}
```

**Resource 与 InputStreamSource 的契约关系**：`Resource extends InputStreamSource`——父接口只声明 `getInputStream()`，子接口叠加元数据与定位能力。这个继承设计有深意：**任何想要"能被读取"但不需要文件语义的组件，只需依赖 InputStreamSource**；而需要元数据/相对路径/可写能力的场景依赖 Resource。写库时按"最小依赖"原则选择接口层级，能让组件在测试中轻松替换（如测试用 ByteArrayResource 喂数据）。

| 接口 | 能力 | 最小依赖场景 |
|------|------|-------------|
| `InputStreamSource` | 仅读流 | 模板引擎、解析器 |
| `Resource` | 读 + 元数据 + 定位 | 配置加载、文件服务 |
| `WritableResource` | 读 + 写 | 导出、上传落盘 |
| `ContextResource` | 相对于上下文根 | web 场景 |

> 💡 依赖方向上的启示：**消费方永远面向最窄接口**——模板引擎依赖 `InputStreamSource`、配置加载依赖 `Resource`、只有"需要写"的组件才依赖 `WritableResource`；反向设计（都依赖最宽接口）会让测试替换成本飙升。这也是所有抽象接口设计的通用准则。

> ⚠️ **编码与关闭**：`getInputStream()` 返回的流**必须关闭**（try-with-resources）；`FileCopyUtils.copyToString(res.getInputStream(), charset)` 是官方封装（内部自动关闭）；读取后 `exists()` 仍可能返回 false 的竞态（文件被删除）——读之前用 exists 做快速失败，读之后靠异常兜底。

## 2. 五种常用实现

| 实现 | 前缀 | 说明 |
|------|------|------|
| `ClassPathResource` | `classpath:` | 类路径资源（jar 内/IDE 类目录） |
| `FileSystemResource` | `file:` | 文件系统（实现 WritableResource 可写） |
| `UrlResource` | `http(s):` / `ftp:` | 任意 URL 资源 |
| `ByteArrayResource` | - | 内存字节数组 |
| `InputStreamResource` | - | 包装一次性输入流（**不可重复读**） |

```java
new ClassPathResource("templates/email.html");
new FileSystemResource("/data/app.conf");
new UrlResource("https://example.com/api.json");
```

**五种实现对比维度**：

| 维度 | ClassPath | FileSystem | Url | ByteArray | InputStream |
|------|:---:|:---:|:---:|:---:|:---:|
| 可重复读 | ✅ | ✅ | ✅ | ✅ | ❌（一次性） |
| getFile 可用 | ❌（jar 内） | ✅ | 仅 file: | ❌ | ❌ |
| 可写（WritableResource） | ❌ | ✅ | 部分 | ❌ | ❌ |
| 元数据（contentLength） | ✅ | ✅ | ✅ | ✅ | ❌ |
| 内存占用 | 流式 | 流式 | 流式 | 全量在内存 | 流式 |
| 典型用途 | 打包资源 | 外部配置 | 远程内容 | 测试/导出 | 上传流 |

> ⚠️ `InputStreamResource` 每次 `getInputStream()` 后流即耗尽——**避免复用**；读文件流首选 `FileCopyUtils.copyToString(res.getInputStream(), charset)` 一次性取完。

**实现选型与更多实现**：

| 场景 | 首选实现 | 理由 |
|------|---------|------|
| 打好的 jar 内资源 | `ClassPathResource` | 走 classloader 流读取，jar 内可用 |
| 运行时动态文件（配置热更新） | `FileSystemResource` | 支持 `getFile()`/写入 |
| 远程配置/静态资源 | `UrlResource` | http/https 协议 |
| 内存生成内容（导出、测试） | `ByteArrayResource` | 可重复读、可测 |
| 一次性流（事件流、上传流） | `InputStreamResource` | 不可复用，用完即弃 |

**其他实现**（web 与上下文环境）：`ServletContextResource`（Web 应用根路径）、`PathResource`（NIO 路径，7.x 推荐 FileSystem 场景）、`FileUrlResource`（file: URL 与文件系统桥接）、`InputStreamSource` 组合（仅提供流的轻量源）。创建资源的统一入口是 `ResourceLoader`（见第 3 节），**业务代码不应 new 具体实现**，应注入 loader 或按前缀解析——实现选择交给框架，代码只依赖抽象。

```java
// 对比：两个"看起来一样"但语义不同的读取
Resource jarResource = new ClassPathResource("data.json");
jarResource.isFile();    // false（jar 内）
jarResource.getFile();   // IOException —— 不要调用

Resource fileResource = new FileSystemResource("data.json");
fileResource.isFile();   // true
fileResource.getFile();  // 正常
```

> 💡 **判定口诀**："先 `isFile()` 再 `getFile()`"是安全姿势；只读内容则完全不需要 getFile——`getInputStream()` 一统天下。

## 3. ResourceLoader 与资源解析

| 组件 | 接口方法 | 说明 |
|------|---------|------|
| `ResourceLoader` | `getResource(String location)` | 按位置解析（前缀决定类型，无前缀依实现而定） |
| `ResourcePatternResolver` | `getResources(String pattern)` | 模式解析（ant 通配） |
| `PathMatchingPatternResourceResolver` | - | 默认实现：classpath*: 扫描 + ant 匹配 |

```text
ResourceLoader 解析规则：
  "classpath:x.txt"     → ClassPathResource
  "file:/data/x.txt"    → FileSystemResource
  "https://..."         → UrlResource
  "x.txt"（无前缀）       → 依加载器：ClassPathXmlApplicationContext 下是类路径

ApplicationContext 本身实现 ResourcePatternResolver —— 注入它即可加载资源
```

```java
// 注入 ResourceLoader（ApplicationContext 即 ResourceLoader）
@Service
public class ResourceService {
    private final ResourcePatternResolver resolver;

    public ResourceService(ResourcePatternResolver resolver) {  // 可注入接口
        this.resolver = resolver;
    }

    public Resource single() {
        return resolver.getResource("classpath:config/app.properties");
    }
}
```

**无前缀的解析行为**（最易踩的坑）：

| 加载器 | `getResource("x.txt")` 解析为 | 原因 |
|--------|------------------------------|------|
| ApplicationContext（非 web） | 类路径 `ClassPathResource` | 默认 classloader 语义 |
| Servlet WebApplicationContext | `ServletContextResource`（web 根） | 优先 web 根目录 |
| 裸 `DefaultResourceLoader` | 类路径 `ClassPathResource` | 前缀优先，缺省 classpath |
| 自定义 ResourceLoader | 实现决定 | 需读实现文档 |

> ⚠️ **规则记忆**：`getResource` 的解析优先级是"**前缀 > 加载器语义 > 类路径兜底**"——代码里永远写前缀（`classpath:`/`file:`/`https:`），不依赖加载器默认行为；无前缀 + web 环境的"我以为是类路径"是高频事故。

**自定义资源加载器**（框架集成场景）：实现 `ResourceLoader.getResource` 返回自定义 Resource（如数据库存配置、ZooKeeper 节点），即可让 `@Value`/`PropertySource` 等"资源感知"能力透明支持新来源——这是"资源抽象"最值钱的扩展点；注意实现 `getProtocol` 返回唯一协议名（供 `@Value("myproto:xxx")` 前缀命中）。

**ResourceLoader 解析顺序（DefaultResourceLoader 内部）**：

```text
getResource("classpath:x")     → 前缀命中 ClassPathResource
getResource("file:/x")         → 前缀命中 FileSystemResource（UrlResource 子类）
getResource("https://x")       → 前缀命中 UrlResource
getResource("x")               → 无前缀：协议探测（存在 "x" 的协议处理器？）→ 否 → 类路径兜底
```

| 前缀 | 目标实现 | 注意 |
|------|---------|------|
| `classpath:` | ClassPathResource | 相对 classloader 根 |
| `file:` | FileSystemResource | 绝对/相对路径均可 |
| `http(s):`/`ftp:` | UrlResource | 网络读取 |
| 无前缀 | 加载器默认 | 见上表（web 环境不同） |

> 💡 **协议扩展**：实现 `java.net.URLStreamHandler` + 注册协议可让 `UrlResource` 原生支持自定义协议（如 `zookeeper://`）——但更简单的是自定义 ResourceLoader 返回自定义实现；两者都使上层无感知。

## 4. PatternResolver：模式加载与 classpath*

| 写法 | 语义 |
|------|------|
| `classpath:x.xml` | 类路径**单个**资源（第一个命中） |
| `classpath*:x.xml` | **所有**类路径上的 x.xml（多 jar 收集）★ |
| `classpath*:**/mapper/*.xml` | 全类路径递归 + ant 匹配 |
| `file:/data/**/*.conf` | 文件系统模式 |
| `?` / `*` / `**` / `{var}` | ant 通配：单字符 / 路径段内任意 / 跨目录 / 占位变量 |

```java
// 多 jar 配置收集（Spring 自身大量使用：spring.factories、imports 文件）
Resource[] rs = resolver.getResources("classpath*:META-INF/spring/imports/*.imports");
```

> 🎯 **核心要点**：`classpath:` 取第一个命中；`classpath*:` 扫描全部类路径——多模块/多 jar 场景（自动配置、SPI 文件、多模块 mybatis mapper）必须用 `classpath*:`，否则只加载第一个 jar 的。

**PatternResolver 细节与性能**：

| 细节 | 说明 |
|------|------|
| 实现 | `PathMatchingPatternResourceResolver`（7.0 前为 `PathMatchingResourcePatternResolver`） |
| 扫描方式 | `classpath*:` 前缀下遍历 classloader 的 jar 清单 + 目录，ant 匹配在内存完成 |
| 性能 | jar 数量多时扫描有开销——**启动期一次性使用**，避免热路径调用 |
| 缓存 | 结果可缓存（多模块配置加载后缓存 Resource[] 或内容） |
| ant 通配 | `*` 不跨 `/`、`**` 跨目录、`?` 单字符、`{a,b}` 备选组 |
| 大小写 | 文件系统区分大小写（Linux），Windows 不区分——跨平台需注意 |

```java
// 缓存模式扫描结果：避免每次启动解析重复扫描 jar
@Component
public class SchemaLoader {
    private final Map<String, List<Resource>> cache = new ConcurrentHashMap<>();

    public List<Resource> load(String pattern) {
        return cache.computeIfAbsent(pattern, p -> {
            try {
                return Arrays.asList(resolver.getResources(p));
            } catch (IOException e) {
                throw new IllegalStateException("scan failed: " + p, e);
            }
        });
    }
}
```

> ⚠️ **classpath* 的坑**：① `classpath*:` 与 `classpath:` 混用导致"有时加载一个有时全部"——代码评审直接红线；② 目录为 `classpath*:` 时若根本无匹配 jar 会返回空数组（不抛异常），调用方需判空；③ 模式中含有 `**` 时性能下降明显（全路径枚举），尽量精确到前缀目录。

**ant 通配模式速查**（附带匹配结果）：

| 模式 | 匹配 | 不匹配 |
|------|------|--------|
| `config/*.properties` | `config/app.properties` | `config/dev/app.properties`（`*` 不跨目录） |
| `config/**/*.properties` | 上述两者 | - |
| `config/app?.properties` | `config/app1.properties` | `config/app12.properties`（`?` 单字符） |
| `**/mapper/*.xml` | 任意层 `mapper/` 下 | 无 |
| `{a,b}/config.yml` | `a/config.yml` 与 `b/config.yml` | - |

```java
// 生产样例：加载所有 sql 目录下的 DDL 并按文件名排序
Resource[] ddl = resolver.getResources("classpath*:db/migration/**/*.sql");
Arrays.sort(ddl, Comparator.comparing(Resource::getFilename));  // 保证执行顺序
```

> 💡 **语义对照**：`*` = 一层内的任意段、`**` = 任意层、`?` = 任意单字符、`{x,y}` = 枚举备选——与 Maven `**/*.java` 与 Jenkinsfile 的 glob 一致，但注意 Spring 的 `classpath*:` 前缀是**资源定位**概念，与 ant 通配是两个独立维度（一个管"去哪找"，一个管"怎么匹配"）。

## 5. Spring 内建使用场景

| 场景 | 使用方式 |
|------|---------|
| @Value 注入资源 | `@Value("classpath:templates/email.html") Resource tpl`（ResourceEditor 自动转换，context 模块） |
| XML 配置 | `<import resource="classpath*:config/spring-*.xml"/>` |
| Boot 配置文件 | `spring.config.location` / `spring.config.import`（Boot 内部全走 Resource 抽象） |
| MyBatis mapper | `classpath*:mapper/*.xml`（MyBatis 扫描器走 ResourcePatternResolver） |
| 自动配置候选 | `AutoConfigurationImportSelector` 读 `classpath*:META-INF/spring/...AutoConfiguration.imports` |
| 模板/静态资源 | ClassLoader 路径模板（Thymeleaf 等模板引擎内部） |

**内建场景的代码形态**：

```java
// ① @Value 注入资源（ResourceEditor 自动转换，context 提供）
@Value("classpath:license/License.txt")
private Resource licenseText;

// ② XML import 多模块配置（ant 模式 + classpath* 收集）
// <import resource="classpath*:config/spring-*.xml"/>

// ③ Boot 外部化配置：spring.config.import=optional:classpath:extra-config/
//    内部全部走 ResourcePatternResolver 加载
```

```text
Boot 配置加载顺序（全走 Resource 抽象）：
  spring.config.location（显式指定，file:/config/ 优先）
  → classpath:/config/ → classpath:/  → 环境变量 → 默认值
  每个位置尝试 application.{yml,yaml,properties} 前缀解析
```

> 💡 **资源抽象的最大受益者**：Boot 的配置系统——同一套 `application.yml` 可以来自 classpath、外部目录、URL、甚至 `spring.config.import` 的多个来源，全靠 Resource 统一后按序合并；理解"配置即资源"后，排查"为什么这个配置没生效"就有了起点：先确认该来源被加载（`ConfigDataLocation` 日志），再看优先级覆盖。

> 💡 **7.0 AOT 相关**：原生镜像下类路径资源需要显式 `RuntimeHints` 提示（`resourceHint`）——格式已从正则改 **glob**（`"/files/**/*.ext"`，`"/files/*.ext"` 不再匹配嵌套），见 [08-集成地图与常见问题](08-集成地图与常见问题.md)。

### 5.1 常见坑速查

| 坑 | 症状 | 解法 |
|----|------|------|
| jar 内 getFile 抛 IOException | 打包后读取失败、本地正常 | 一律 getInputStream（第 1 节） |
| classpath 只加载一个 jar | 多模块配置缺失 | 改 `classpath*:`（第 4 节） |
| 无前缀在 web 环境解析错 | 拿到的路径不是预期的类路径 | 显式写 `classpath:` 前缀 |
| InputStreamResource 复用 | 第二次读返回空/流已关闭 | 换 ByteArrayResource 或重新获取 |
| 相对路径 `createRelative` 语义 | 与文件系统相对路径混淆 | 确认文档：基于资源所在目录而非 cwd |
| 编码乱码 | 资源读取未指定 charset | 统一 `FileCopyUtils.copyToString(in, UTF_8)` |
| 文件被并发删除 | exists 后读取仍 IO 异常 | 异常兜底处理，不依赖竞态检查 |

**生产实践清单**：

| 实践 | 做法 |
|------|------|
| 统一读取入口 | 团队封装 `ResourceReader`（内部 getInputStream + UTF-8 + 异常包装），禁止散落裸读 |
| 显式前缀 | 所有 location 字符串必须带协议前缀，CI 正则检查 `(classpath\|file\|https):` |
| 多 jar 用 classpath* | 规则：只要"可能来自多个 jar"就 classpath*，否则 classpath: |
| 缓存热点资源 | 配置文件/模板缓存到内存（内容不变时），避免重复 IO |
| 资源日志可读 | 日志统一 `res.getDescription()`（而非路径字符串，便于区分来源） |
| AOT 提示登记 | 原生镜像项目：所有资源模式登记 RuntimeHints（glob 写法） |

> 💡 **团队规范样例**：接口层禁止出现 `new FileInputStream(...)` 读取业务数据——统一走 `ResourceService.load("classpath:...")`；这既是抽象约束，也让测试能注入内存资源。

### 5.2 面试追问点

- **"Resource 与 JDK URL/File 的关系"**：Resource 是**统一抽象**——把 URL/File/classpath/流/内存/自定义来源归一为同一接口，上层（@Value/PropertySource/模板引擎）只依赖 Resource，换来源不改业务代码；
- **"getFile 为什么在 jar 里失败"**：jar 内的类路径资源没有真实文件系统句柄（在 zip 条目里），getFile 抛 IOException 是**约定行为**而非缺陷——契约要求"仅 isFile() 为 true 时才调用"；
- **"classpath: 与 classpath*: 的性能差异"**：classpath: 直接按名称加载（快）；classpath*: 需遍历所有 jar 枚举匹配（慢）——**能用 classpath: 不用 classpath*:**，只有多 jar 收集才用后者；
- **"@Value 注入 Resource 的原理"**：`ResourceEditor`（PropertyEditor）按前缀解析字符串——`@Value("classpath:...")` 时环境注入 `ResourceLoader` 即 ApplicationContext，把字符串转 Resource；这也是"旧机制仍然有价值"的典型；
- **"AOT 下资源为什么会丢"**：原生镜像没有类路径 jar 扫描，资源必须在编译期静态登记（RuntimeHints）——7.0 用 glob 描述模式，比正则直观且实现可靠。

**资源问题排查工具箱**：

| 症状 | 排查动作 |
|------|---------|
| 找不到资源 | debug 日志查 `PathMatchingResourcePatternResolver` 的扫描路径；`jar tf` 验证打包内容 |
| 加载到错误资源 | 打印 `res.getDescription()` + `res.getURL()` 确认来源与顺序 |
| 内容乱码 | 确认读取 charset；`file` 命令查看文件真实编码 |
| classpath* 结果为空 | 确认 pattern 前缀目录存在；多模块时检查依赖是否打包 |
| 启动慢（大量资源扫描） | 火焰图定位 `PathMatchingResourcePatternResolver` 耗时，改精确模式 |

**一句话速记**：读用流、看用描述、前缀必写、classpath* 收多源、AOT 用 glob——五条规则覆盖 90% 资源问题；遇到"资源行为诡异"时按这五条逐项核对，通常一击命中。剩余 10% 多为编码与平台差异（大小写、换行符），按第 5.1 节表格逐项排除即可。

> 🎯 **全篇收束**：资源抽象的思维模型是"**协议化读取**"——把"来源"从代码中剥离，只留 `getInputStream` 这一个协议；遇到"读文件"需求先问"来源会变吗"，会变就用 Resource，不变才考虑裸 JDK。一句话总结全篇要点：**前缀定来源、流读保安全、classpath* 收多源、glob 备 AOT**——四个短语分别对应第 3、1、4、5 节的核心结论。
