## 1. 7.0 弹性体系总览

```text
Spring Framework 7.0 弹性能力（原独立项目 Spring Retry 并入并重设计）
├── spring-core  org.springframework.core.retry
│   ├── RetryTemplate（入口：同步执行 + 重试编排）
│   ├── RetryPolicy（何时重试：次数/异常分类）
│   ├── BackOffPolicy（重试间隔：固定/指数）
│   ├── RetryContext（本次执行上下文：尝试计数、异常记录）
│   └── RecoveryCallback（耗尽后的兜底）
└── spring-context  声明式注解
    ├── @EnableResilientMethods（开关：@Configuration 类上）
    ├── @Retryable（方法级重试，响应式自动适配）
    └── @ConcurrencyLimit（并发限流）
```

> 🎯 **核心要点**：7.0 把"重试"从第三方库升级为 Framework 一等能力——core 提供执行引擎，context 提供注解；响应式返回类型（Mono/Flux）自动用 Reactor 重试管道，命令式用 RetryTemplate。

**弹性能力定位**（7.0 内建重试 vs 专业弹性组件）：

| 能力 | core.retry（7.0 内建） | Sentinel / Resilience4j |
|------|----------------------|------------------------|
| 重试 | ✅ 完整（策略/退避/兜底） | ✅（Resilience4j Retry） |
| 熔断 | ❌ | ✅（核心能力） |
| 限流 | 仅方法级 @ConcurrencyLimit | ✅（QPS/线程池/信号量） |
| 降级 | 仅 RecoveryCallback | ✅（Fallback 体系） |
| 指标/控制台 | 基础日志 | ✅（指标 + 控制台） |
| 定位 | "框架内轻量容错" | "微服务治理平台" |

> 💡 **选型结论**：单体/少量外部调用用内建重试足够；微服务网关、依赖大量下游、需要熔断限流大盘的场景用专业组件——两者可共存（内建处理"方法级瞬时失败"，Sentinel 处理"服务级治理"）。

**术语对照表**（老 spring-retry 用户迁移必看）：

| 7.0 core.retry | 原 spring-retry | 变化 |
|----------------|----------------|------|
| `maxRetries` | `maxAttempts` | 语义改为"重试次数"（不含首次） |
| `RetryTemplate.builder()` | `RetryTemplate.builder()` | 保留，内部语义更新 |
| `org.springframework.core.retry` | `org.springframework.retry` | 包名迁移 |
| `RetrySynchronizationManager` | 同名 | 位置变化 |

## 2. RetryTemplate：编程式重试

```java
// ① Builder 快速构建（推荐）
RetryTemplate template = RetryTemplate.builder()
        .maxRetries(3)                                  // ★ 7.0 语义：最大重试次数（原 maxAttempts）
        .fixedBackoff(500)                              // 固定 500ms 间隔
        .exponentialBackoff(200, 2, 5_000)              // 或指数退避 200ms 起、×2、上限 5s
        .build();

// ② 执行：成功返回 / 失败重试 / 耗尽回调
String result = template.execute(
        ctx -> remoteCall(),                            // RetryCallback：可重试业务
        ctx -> fallbackValue(ctx.getLastThrowable()));  // RecoveryCallback：重试耗尽兜底
```

| 组件 | 职责 |
|------|------|
| `RetryCallback<T>` | 重试主体：`T doWithRetry(RetryContext ctx)` |
| `RecoveryCallback<T>` | 耗尽兜底：`recover(RetryContext)`（拿到最后异常） |
| `RetryContext` | `getRetryCount()` / `getLastThrowable()` / 属性传递 |
| `RetrySynchronizationManager` | 上下文在线程间传递（嵌套重试） |

**Builder 完整配置项**（`RetryTemplate.builder()`）：

| 方法 | 语义 | 默认 |
|------|------|------|
| `maxRetries(int)` | 最大重试次数（不含首次） | 3 |
| `fixedBackoff(long)` | 固定退避毫秒 | - |
| `exponentialBackoff(initial, multiplier, max)` | 指数退避 | - |
| `customPolicy(RetryPolicy)` | 自定义策略（异常分类等） | - |
| `customBackoff(BackOffPolicy)` | 自定义退避（含抖动） | - |
| `infiniteRetry()` | 无限重试（**生产禁用**，配合超时用） | - |
| `build()` | 构建（线程安全可复用） | - |

> 💡 **Builder 是推荐入口**：相比 `new RetryTemplate()` + setter 装配，Builder 参数自解释且防呆（如 `infiniteRetry` 显式命名提醒危险）；**构建后实例可全局共享**（无状态编排），每条业务线一个模板即可。若一条业务线需要"分类不同、退避不同"的多种重试，建两个模板实例并在代码路径中按需选择，比在单个模板上堆策略更清晰。注意模板共享不等于上下文共享——每次 execute 都是独立 RetryContext，模板复用不影响并发安全。

> ⚠️ **失败判定默认**：任何 `Exception` 都重试——业务上"不可重试错误"（参数错误/4xx 类）要显式配置 `RetryPolicy` 排除（见第 3 节）。

**RetryTemplate 执行流程（源码级）**：

```text
execute(callback, recovery):
  1. 创建 RetryContext（含 attempt 计数=0、属性 map）——从 RetrySynchronizationManager 取或新建
  2. 循环开始：
     a. attempt++；调用 RetryCallback.doWithRetry(ctx)
     b. 成功 → 返回结果（context 关闭，清理 ThreadLocal）
     c. 抛出异常 → 进入 RetryPolicy.canRetry(ctx)
        · false（策略判定不可重试/超限）→ 若有 RecoveryCallback 执行兜底
        · true → 进入 BackOffPolicy.backOff(ctx) 休眠间隔（可被中断）
        · 再次循环（总尝试次数受 policy 约束）
  3. 无 RecoveryCallback 且耗尽 → 抛出最后一次异常（原样，不包装）
```

| 环节 | 关键行为 | 面试点 |
|------|---------|--------|
| 上下文传递 | `RetrySynchronizationManager`（ThreadLocal）支持嵌套重试（外层 context 属性透传） | "嵌套重试上下文如何共享" |
| 异常记录 | context 记录最后异常（`getLastThrowable`），供 recovery 使用 | "兜底怎么拿到失败原因" |
| 中断处理 | backOff 期间线程中断 → 立即放弃并抛异常 | "优雅停机期间重试行为" |
| 耗尽行为 | 无 recovery 时抛**最后一次**异常（非包装） | "重试后异常类型保持" |

```java
// 编程式完整示例：带异常分类 + 抖动退避 + 兜底 + 结果校验
RetryTemplate template = RetryTemplate.builder()
        .maxRetries(3)
        .exponentialBackoff(100, 2, 3_000)        // 100ms 起 ×2，上限 3s
        .build();

boolean ok = template.execute(
        ctx -> {
            boolean success = remoteCall();
            if (!success) {
                throw new RetryableException("remote returned false");  // 业务自定义可重试异常
            }
            return true;
        },
        ctx -> {                                    // 耗尽兜底：告警 + 降级返回
            log.error("call failed after {} attempts", ctx.getRetryCount(), ctx.getLastThrowable());
            return false;
        });
```

> 💡 **业务重试建模**：对"返回 false 但没抛异常"的远程调用，推荐**包装为可重试异常**（如上），让重试判定走统一异常通道——比在 callback 内自己写循环清晰得多；`RetryableException` 是 core.retry 提供的通用可重试异常（也可自定义）。

## 3. RetryPolicy 与 BackOff 策略

| 策略 | 类 | 说明 |
|------|----|------|
| 次数 | `MaxAttemptsRetryPolicy`（builder 内建） | 最多尝试 N 次（含首次） |
| 异常分类 | `ExceptionClassifierRetryPolicy` | 按异常类型决定是否重试/是否退避 |
| 时间 | `TimeoutRetryPolicy` | 窗口期内重试 |
| 永不 | `NeverRetryPolicy` | 不重试（默认兜底） |
| 固定间隔 | `FixedBackOffPolicy` | 固定毫秒 |
| 指数退避 | `ExponentialBackOffPolicy` | 初始 × 倍数，可设上限与随机抖动 |
| 无退避 | `NoBackOffPolicy` | 立即重试 |

```java
// 异常分类：只对网络类异常重试，参数异常直接失败
RetryTemplate template = new RetryTemplate();
template.setRetryPolicy(new ExceptionClassifierRetryPolicy() {
    @Override
    protected boolean canRetry(RetryContext context) {
        Throwable t = context.getLastThrowable();
        return t instanceof IOException || t instanceof TimeoutException;
    }
});
template.setBackOffPolicy(new ExponentialBackOffPolicy());
```

> 💡 **最佳实践**：① 只重试"瞬时错误"（网络/限流/超时），不重试"确定错误"（参数/权限）；② 重试必须带退避（防打爆下游）；③ 调用方加**总超时**（重试总窗口），避免无限阻塞；④ 重试幂等——重试的副作用（已提交的订单）必须可幂等。

**策略选择决策表**：

| 场景 | RetryPolicy | BackOffPolicy | 理由 |
|------|-------------|---------------|------|
| 网络抖动（RPC/HTTP） | 异常分类 + 次数 | 指数退避 + 抖动 | 抖动集中在前 1-2s，指数增长避免打爆 |
| 数据库连接池打满 | 异常分类 | 固定 1-3s | 池恢复需要稳定间隔 |
| 外部限流（429） | 异常分类（限流异常） | 指数退避尊重 Retry-After | 限流重试过快会雪崩 |
| 批量任务 | 时间窗口（Timeout） | 固定短间隔 | 任务有整体 deadline |
| 绝不重试的场景 | NeverRetryPolicy | - | 参数错误/鉴权失败 |

**抖动（jitter）的作用**：多实例同时失败时，无抖动退避会让所有实例在同一时刻重试（惊群效应）——`ExponentialBackOffPolicy` 的抖动参数把间隔随机化（`setJitterFactor(0.25)` 表示 ±25% 随机浮动），重试请求均匀散开；**生产环境多实例部署必须开抖动**。

```java
// 抖动配置（builder 或直接设置）
ExponentialBackOffPolicy policy = new ExponentialBackOffPolicy();
policy.setInitialInterval(200);
policy.setMultiplier(2);
policy.setMaxInterval(5_000);
policy.setJitterFactor(0.25);          // ★ 多实例场景必开
```

> ⚠️ **时间策略注意**：`TimeoutRetryPolicy` 的时间窗口从**第一次尝试开始**计时，超时后立即停止（含退避等待时间）；它与"总超时"是两层概念——policy 管重试窗口，调用方超时管整体调用，两者都设时以更小者生效。

## 4. @Retryable 与 @ConcurrencyLimit（声明式）

```java
@Configuration
@EnableResilientMethods                       // ★ 总开关（context 7.0）
public class ResilientConfig { }

@Service
public class PaymentClient {
    @Retryable(maxRetries = 3,                 // ★ 7.0：maxAttempts → maxRetries
               backoff = @Backoff(delay = 200, multiplier = 2),
               include = {IOException.class},  // 只对指定异常重试
               exclude = {IllegalArgumentException.class})
    public PaymentResult charge(PaymentReq req) {
        return restTemplate.postForObject(...);   // 命令式：内部走 RetryTemplate
    }

    @Retryable(maxRetries = 2)
    public Mono<PaymentResult> chargeReactive(PaymentReq req) {
        return webClient.post().body(...).retrieve()...;   // 响应式：自动适配 Reactor retry
    }

    @ConcurrencyLimit(limit = 20)                // 并发限流：同方法同时执行 ≤ 20
    public void bulkSync() { ... }
}
```

| 注解属性 | 语义 |
|---------|------|
| `maxRetries`（7.0） | 最大重试次数（原 maxAttempts 已更名） |
| `backoff` / `@Backoff(delay, multiplier, maxDelay)` | 退避参数 |
| `include` / `exclude` | 异常白/黑名单 |
| `recover` | 兜底方法名（返回类型须兼容） |
| `label` / `listen` | 观测/日志（可扩展） |
| `@ConcurrencyLimit(limit)` | 并发上限（基于信号量式节流） |

> ⚠️ **注意**：① `@Retryable` 是代理注解——**同类自调用不生效**（见 [Spring-AOP-00](../Spring‑AOP/00-Spring AOP组件总览.md) 自调用坑）；② 7.0.0 曾有 `@ConcurrencyLimit` + `@Async`/`@Transactional` 组合异常（已修复）；③ 兜底 `recover` 方法默认按异常类型匹配。

**@Retryable 细节规则**：

| 规则 | 说明 |
|------|------|
| include/exclude 默认 | **默认全部异常可重试**（同编程式）；显式 include 后只重试白名单；exclude 优先于 include |
| include 继承 | include 指定的异常**子类也命中**（`IOException.class` 命中 `SocketTimeoutException`） |
| recover 方法签名 | `recover(异常类型, 方法参数...)`——异常类型参数 + 原方法参数列表，返回类型与原方法兼容 |
| 无 recover 时耗尽 | 抛出最后一次异常（保持原类型） |
| 幂等要求 | 重试执行的是**同一方法**，方法副作用必须幂等 |
| 与 @Async 组合 | 重试在异步线程内执行（代理链顺序由注册顺序决定） |
| 类级别 | 可标注在类上（所有公共方法生效），方法级覆盖 |

```java
// recover 方法完整示例：异常分类兜底
@Service
public class PaymentClient {
    @Retryable(maxRetries = 3, include = {IOException.class},
               recover = "chargeRecover")
    public PaymentResult charge(PaymentReq req) throws IOException { ... }

    // 兜底签名：第一个参数为异常类型（须与 include 匹配），后接原方法参数
    public PaymentResult chargeRecover(IOException e, PaymentReq req) {
        log.error("charge failed, fallback: {}", req.id(), e);
        return PaymentResult.fallback("CIRCUIT_OPEN");
    }
}
```

> 💡 **@ConcurrencyLimit 实现语义**：基于信号量式节流——同方法同时执行数超过 limit 的调用**立即失败**（抛异常/返回降级），而非排队等待；适合保护"昂贵且并发敏感"的操作（批量同步、报表导出），不适合"希望排队"的场景（用队列线程池）。

## 5. 迁移与选型

| 场景 | 选型 |
|------|------|
| 新项目（Framework 7 / Boot 4） | ✅ 直接用内建 `core.retry` + `@Retryable` |
| 存量 spring-retry 独立项目 | 迁移：移除 `spring-retry` 依赖，`maxAttempts` → `maxRetries`，包名 `org.springframework.core.retry` |
| 简单单次重试 | 甚至不必引入——`RestClient` 等自带重试或循环 + sleep |
| 复杂重试编排 | 内建 RetryTemplate 足够；更重场景上 Spring Batch 的 Retry 或消息队列重投递 |
| 消息消费重试 | 优先 MQ 死信/延迟队列，而非方法重试（见消息队列系列） |

```xml
<!-- 迁移：移除独立 spring-retry -->
<!-- 旧：org.springframework.retry:spring-retry -->
<!-- 新：随 spring-core 7.0 内建，无需额外坐标 -->
```

> 🎯 **核心要点**：重试是"最后手段"——先做**超时 + 熔断 + 降级**（Sentinel/Resilience4j 见分布式系列），重试只对瞬时故障负责；内建重试的定位是"轻量、框架内一致"，复杂链路治理仍交给专业组件。

### 5.1 生产实践与常见坑

| 坑 | 症状 | 解法 |
|----|------|------|
| 重试放大故障 | 下游故障时所有实例同时重试 | 指数退避 + 抖动 + 重试上限小（2-3 次） |
| 重试导致重复扣款 | 第一次成功但响应超时，重试再次成功 | **幂等键**（请求唯一 ID）+ 下游幂等校验 |
| 自调用不生效 | @Retryable 方法内调用同方法无重试 | 注入自身代理 / 拆到独立 Bean |
| 忘开总开关 | @Retryable 静默不生效 | 检查 `@EnableResilientMethods` 是否在配置类上 |
| 重试吞掉业务异常 | 耗尽后抛最后一次异常但被上层误判 | 无 recovery 时异常类型不变；recovery 内明确降级语义 |
| 退避时间过长 | 重试总窗口超出调用方超时 | 总超时 = 首次 + 各次退避之和 + 余量，先算后配 |
| 线程池内重试 | 重试在池线程执行，上下文丢失 | 确认 RetrySynchronizationManager 在池线程中的初始化（通常框架已处理） |

**配置参数计算模板**：

```text
maxRetries = 3、退避 200ms×2（上限 3s）→ 最坏耗时 = 200 + 400 + 800 = 1.4s（第 3 次退避 800ms）
调用方超时建议 = 业务单次耗时上限 + 1.4s + 余量 1s
```

> 💡 **验收方法**：写单测断言"第 N 次调用抛出特定异常时恰好重试 M 次"（Mockito 计数 verify），并断言退避间隔（注入 MockBackOffPolicy 或时钟）；生产通过 debug 日志（`RetryTemplate` 会打印 attempt 信息）观察实际重试轨迹。

### 5.2 面试追问点

- **"重试与熔断的顺序"**：先熔断后重试（失败率高时熔断打开直接短路，重试不再触发）；重试只适合"熔断未开、瞬时抖动"的窗口——组合顺序是 **超时 → 重试 → 熔断 → 降级**；
- **"为什么默认重试所有异常是危险的"**：参数错误重试 100 次也是失败（浪费 + 放大日志）；必须按异常分类收敛——白名单制（include）比黑名单制（exclude）更安全；
- **"重试为什么必须幂等"**：重试 = 同一操作执行多次；非幂等操作（扣款/发消息/下单）重试会造成业务重复——幂等键/唯一约束是重试的前置条件，不是可选优化；
- **"响应式重试与命令式差异"**：命令式在同步调用栈内循环（阻塞退避）；响应式（Mono/Flux）用 Reactor 的 `retryWhen` 管道（非阻塞调度退避）——7.0 自动适配，但**副作用回调时机**（doOnError 等）语义需注意；
- **"@ConcurrencyLimit 与限流组件区别"**：它是**方法级并发数**限制（信号量），不是 QPS 限流——针对"同方法并发执行数"，Sentinel 的 QPS 限流针对"每秒请求数"，维度不同；
- **"7.0 为什么把 Spring Retry 并进来"**：重试是基础能力而非业务库——并入后版本跟随 Framework 升级（消除版本漂移）、注解与核心 API 同源（@Retryable 直接消费 core.retry），Boot 场景开箱即用。

> 🎯 **全篇收束**：重试体系的本质是"**把'失败后怎么办'变成可配置策略**"——RetryPolicy 定"是否重试"、BackOffPolicy 定"何时重试"、RecoveryCallback 定"何时放弃"；三个正交维度组合出完整容错语义。面试讲重试先讲三策略，再讲幂等与代理限制，最后讲与熔断降级的分工。落地时从"最小配置"起步：`maxRetries(2) + exponentialBackoff(100, 2, 2000)` 已覆盖多数瞬时故障场景，按监控数据再逐步细化异常分类。至此 07 篇完毕，下一篇 08 是收尾篇——把 core 全部能力串成"集成地图 + 排障手册"。
