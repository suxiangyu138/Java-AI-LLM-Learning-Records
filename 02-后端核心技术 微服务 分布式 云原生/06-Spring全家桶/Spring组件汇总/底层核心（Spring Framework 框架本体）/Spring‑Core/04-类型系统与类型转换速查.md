## 1. ResolvableType：运行时泛型解析

**痛点**：Java 泛型在运行时被擦除——`List<String>` 反射只能拿到 `List`。

```java
// 直接擦除：拿不到泛型参数
Field field = Foo.class.getDeclaredField("list");
System.out.println(field.getGenericType());   // java.util.List<java.lang.String>（源码可用）
// 但运行时 new ArrayList<String>() 传参后，对象层面已不可知

// ResolvableType：从字段/方法/类声明还原泛型
ResolvableType rt = ResolvableType.forField(Foo.class.getDeclaredField("list"));
rt.getGeneric(0).getType();                    // class java.lang.String

// 类层次泛型：class MyRepo implements Repository<Order>
ResolvableType.forClass(MyRepo.class).as(Repository.class).getGeneric(0).resolve();  // Order
```

| 场景 | 用法 |
|------|------|
| 字段泛型 | `ResolvableType.forField(field)` |
| 方法返回/参数 | `forMethodParameter(method, 0)` |
| 类层次 | `forClass(impl).as(iface).getGeneric(0)` |
| 集合/Map 嵌套 | `getGeneric(0)`、`getGeneric(1)`、`as(Collection.class)` |

> 🎯 **核心要点**：Spring 能"泛型注入"（`Repository<Order>` 按类型参数匹配候选）靠的正是 ResolvableType——它是 `@Autowired` 泛型匹配（见 [Spring-Beans-06](../Spring‑Beans/06-依赖注入与自动装配速查.md)）的底层引擎。

**ResolvableType 解析原理（源码级）**：`forField`/`forMethodParameter` 拿到的是**声明处**的 `java.lang.reflect.Type`（字段声明 `List<String>` 时泛型信息完整保留在字节码 Signature 属性中）；ResolvableType 内部用 `ResolvableTypeCacheKey`（type + 变量映射）做缓存，核心算法是：

```text
解析三步：
  1. 取声明 Type：Field.getGenericType()（含 Signature 属性，擦除只发生在对象创建后）
  2. 类型变量替换：泛型基类/接口上的 T → 子类声明的实际类型（如 Repository<T> → Repository<Order>）
  3. 递归展开：getGeneric(n) 逐层展开嵌套泛型（如 Map<String, List<Integer>> 展开到 2 层）
```

**更多场景**：

| 场景 | 代码 |
|------|------|
| 方法返回泛型 | `ResolvableType.forMethodReturnType(method)` |
| 构造器参数 | `forConstructorParameter(ctor, 0)` |
| 泛型数组 | `getComponentType()` |
| 通配符解析 | `getGeneric(0).resolve()`（`? extends Order` → 上界 Order） |
| 运行时实例推断 | `ResolvableType.forClassWithGenerics(...)`（如 00 篇示例） |

```java
// 生产实战：泛型 DAO 基类拿子类实体类型
public abstract class BaseDao<T> {
    private final Class<T> entityClass;

    protected BaseDao() {
        ResolvableType rt = ResolvableType.forClass(getClass())
                .as(BaseDao.class);                    // 沿类层次定位泛型定义处
        this.entityClass = (Class<T>) rt.getGeneric(0).resolve();
        // new OrderDao() → entityClass = Order.class（无需子类显式传类型）
    }
}
```

> ⚠️ **边界**：① ResolvableType 只能解析**声明处**的泛型——`new ArrayList<String>()` 这种对象创建后传入方法，擦除信息已不可恢复（除非方法参数声明带泛型）；② 匿名内部类可以保留泛型（`new Repository<Order>(){}`），工具类常用此技巧（TypeToken 原理同源）；③ `resolve()` 返回 null 表示无法解析（如泛型变量无界）——调用前判空。

**ResolvableType 常见坑**：

| 坑 | 表现 | 解法 |
|----|------|------|
| `as(接口)` 误用 | 目标接口不在类型层次链上返回空描述符 | 先 `isAssignableFrom` 判断再取泛型 |
| 数组泛型 | `List<String>[]` 的 `getGeneric(0)` 指向数组 | 用 `getComponentType()` 先解数组层 |
| 变量未绑定 | 直接对 `Repository<T>` 取泛型拿到 `T` | `resolve()` 返回 null → 需要子类实例（`forClass(getClass())`） |
| 泛型通配符 | `List<? extends Order>` 解析为上界 | `getGeneric(0).resolve()` 取上界，`getGeneric(0).getGenerics()` 取通配符约束 |
| 性能误用 | 热路径反复构造 ResolvableType | 实例可缓存（内部有缓存但构造仍有开销） |

> 💡 **记忆口诀**："`as` 定位、`getGeneric` 取参、`resolve` 落类"——三层调用各司其职；`ResolvableType.forClassWithGenerics` 是"组装"（描述未实现的泛型），`forClass(...).as(...)` 是"拆解"（还原已声明的泛型），方向相反不要记混。

## 2. TypeDescriptor 与类型元数据

| 类型 | 职责 |
|------|------|
| `TypeDescriptor` | 类型描述（class + 泛型 + 注解），转换与校验用 |
| `GenericTypeResolver` | `resolveReturnType(method, clazz)` 等泛型解析工具 |
| `MethodParameter` | 方法参数描述（含注解），注入点解析基础 |
| `ParameterNameDiscoverer` | 方法参数名发现（字节码参数名，`-parameters` 编译选项） |

```java
TypeDescriptor source = TypeDescriptor.valueOf(String.class);
TypeDescriptor target = TypeDescriptor.valueOf(Integer.class);
boolean supported = conversionService.canConvert(source, target);
```

> 💡 `MethodParameter` + `ParameterNameDiscoverer` 是构造器注入"按参数名回退匹配"（见 Beans-06 裁决链）的基础设施。

**TypeDescriptor 源码级认知**：它是"类型信息 + 注解信息"的不可变聚合（`{Class, ResolvableType, 注解数组}`），转换服务用它做精确匹配——同一 `List` 类型，`List<String>` 与 `List<Integer>` 是两个不同描述符，这正是泛型转换（`String[] → List<Money>`）能工作的基础。`nested(n)` 可取出嵌套类型描述符（数组元素/泛型参数），`upcast`/`fromResolvableType` 等用于构建。

```java
// MethodParameter 实战：从注入点拿"类型 + 注解"（模拟 @Value 解析器）
MethodParameter mp = new MethodParameter(method, 0);        // 第 0 个参数
TypeDescriptor td = new TypeDescriptor(mp);
td.getType();                                // 参数类型（含泛型）
td.getAnnotation(Value.class);               // 参数上的注解
td.isCollection();                           // 是否集合
```

| 类型元数据 API | 用途 | 边界 |
|---------------|------|------|
| `TypeDescriptor` | 转换匹配的精确类型描述 | 不可变、可缓存 |
| `GenericTypeResolver` | 快速泛型解析（返回/参数/字段） | 无注解维度 |
| `MethodParameter` | 方法级类型 + 注解 + 嵌套索引 | 需要先拿到 Method |
| `ParameterNameDiscoverer` | 字节码参数名（`-parameters` 或 debug 表） | 未编译参数名时返回 null |

> ⚠️ **编译期参数名**：`ParameterNameDiscoverer` 依赖编译选项——Maven 需 `<parameters>true</parameters>`（Boot 默认开启）；缺失时构造器注入回退"类型唯一匹配"，多构造器场景可能报歧义——排查"参数名注入失败"先查编译配置。

**TypeDescriptor 的另类用途**：除了转换匹配，它还承担"类型契约校验"——`@ConfigurationProperties` 绑定器用描述符判断"宽松绑定"是否适用（`isBindable` 校验）、校验框架（spring-context `Validator`）用注解描述符触发分组校验。因此**只要涉及"按类型 + 注解做决定"的框架代码，最终都会落到 TypeDescriptor 上**——它是 core 类型域的"通用身份证"。

> 💡 关联记忆：`TypeDescriptor` ≈ `ResolvableType`（类型）+ `Annotation[]`（注解）+ 不可变性；看到"类型 + 注解"双参数的方法签名（如 `canConvert(TypeDescriptor, TypeDescriptor)`），背后一定是类型描述符在做精确匹配。

## 3. 类型转换三时代：PropertyEditor → ConversionService

| 时代 | 机制 | 现状 |
|------|------|------|
| 1.0 | `PropertyEditor`（java.beans，JDK 1.0 设计） | 仍兼容（XML/占位符兜底），新代码不写 |
| 3.0+ | `ConversionService` + `Converter`（类型安全、泛型友好） | ✅ 标准（Spring MVC/占位符/绑定默认走它） |
| 3.2+ | `Formatter`（转换 + 解析 + 显示三合一，i18n 友好） | MVC 展示层首选（spring-context 提供） |

```text
转换请求（如 @Value("${pool.size}") 注入 int）：
  String → Integer：ConversionService 找 Converter<String,Integer>（内建）
  失败 → PropertyEditor 兜底 → 异常
```

**@Value 注入自定义类型的完整链路**（以 `@Value("${max.amount}") Money amount` 为例）：

```text
1. 占位符解析器（context）把 ${max.amount} 替换为配置值 "12.50"
2. TypeConverterDelegate 拿到注入点 TypeDescriptor（Money + 泛型/注解）
3. 查 ConversionService：找到 Converter<String, Money>（我们注册的）→ 转换成功
4. 找不到 → 回退 PropertyEditor（注册的 setAsText）→ 再失败抛 ConversionFailedException
```

| 环节 | 归属模块 | 失败表现 |
|------|---------|---------|
| 占位符解析 | spring-context（PropertyPlaceholderConfigurer） | 未解析：注入原样 `${max.amount}` |
| 类型匹配 | spring-core（TypeConverterDelegate） | 未注册转换器：ConversionFailedException |
| 值绑定 | spring-beans（BeanWrapper） | 绑定阶段异常（启动期即暴露） |

> 💡 排查顺序：先看**值**（占位符是否解析）再看**类型**（转换器是否命中）——"值对但类型错"才需要动转换器；两个环节的异常信息会明确区分（未解析 vs 转换失败）。

| API | 语义 |
|-----|------|
| `ConversionService` | 门面：`convert(source, targetType)` / `canConvert` |
| `Converter<S,T>` | 简单转换：`convert(S) → T` |
| `ConverterFactory<S,R>` | 一族目标类型（如 String → Number 家族） |
| `GenericConverter` | 复杂转换（带类型上下文，如集合/Map） |
| `ConditionalConverter` | 条件激活：`matches(sourceType, targetType)` |
| `DefaultConversionService` | 内建 60+ 转换器（Number/日期/集合/枚举/字符串） |

> ⚠️ 边界：`Formatter` 在 **spring-context**（`format` 包）；`Converter` 族与 `ConversionService` 在 **spring-core**——归属不同模块，面试归类别混。

**三时代为什么并存**（面试高频题"为什么还保留 PropertyEditor"）：

| 维度 | PropertyEditor（1.0） | ConversionService（3.0+） | Formatter（3.2+） |
|------|----------------------|--------------------------|-------------------|
| 线程安全 | ❌ 有状态（值缓存在实例上） | ✅ 无状态可共享 | ✅ 无状态 |
| 泛型支持 | ❌ 无 | ✅ 完整 | 通过 Converter 桥接 |
| 显示/解析 | 仅 setAsText/getAsText | 仅转换 | 转换 + 显示双方向 |
| 现状 | XML 属性注入兜底、MVC 老代码 | 标准路径 | MVC 展示层首选 |

**兼容策略**：`PropertyEditorRegistry` 与 `ConversionService` 是**并列的两套注册表**——`TypeConverterDelegate`（beans 属性填充）的查找顺序是"先 ConversionService、后 PropertyEditor、再内建默认"；因此老项目自定义 PropertyEditor 依旧生效，但**新功能一律写 Converter/Formatter**，PropertyEditor 只是"遗留资产兼容层"。

> 💡 **一句话讲清演进**：1.0 时代"每类型一个编辑器且线程不安全"；3.0 升级为"无状态转换器 + 泛型感知"；3.2 再补"展示层 i18n"——三代的本质是**状态管理、类型安全、显示语义**的三次补课。

## 4. Converter 一族

```java
// 简单转换器：注册进容器后，@Value/绑定/MVC 自动使用
@Component
public class MoneyConverter implements Converter<String, Money> {
    @Override
    public Money convert(String source) {
        return Money.parse(source);        // "12.50" → Money(12.50)
    }
}

// 一族转换：String → 任意 Number 子类
public class StringToNumberConverterFactory
        implements ConverterFactory<String, Number> {
    @Override
    public <T extends Number> Converter<String, T> getConverter(Class<T> targetType) {
        return source -> (T) NumberUtils.parseNumber(source, targetType);
    }
}

// 带源类型判断的条件转换器
@Component
public class ConditionMoneyConverter implements Converter<String, Money>, ConditionalConverter {
    @Override
    public boolean matches(TypeDescriptor sourceType, TypeDescriptor targetType) {
        return Money.class.isAssignableFrom(targetType.getType());
    }
    // ...
}
```

> 💡 注册方式：① `@Component` + Boot 自动注册到 Web 层 ConversionService；② 纯 Spring：实现 `WebMvcConfigurer.addFormatters`（web）或 `ConversionServiceFactoryBean`/`DefaultFormattingConversionService` 装配。

**内建转换器清单**（`DefaultConversionService` 默认注册，60+ 个）——按域分类速记：

| 域 | 代表转换器 | 常见于 |
|----|-----------|--------|
| 数值 | String↔Integer/Long/BigDecimal、Number 家族互转 | @Value、占位符 |
| 日期时间 | String↔LocalDate/Instant/Date、时区感知 | 配置与绑定 |
| 集合 | String[]↔List/Set、Map 转换 | MVC 参数 |
| 枚举 | String↔Enum（忽略大小写回退） | 状态字段 |
| 字符编码 | String↔byte[]（Charset 参数） | HTTP |
| 对象 | 同类型恒等转换、Object↔String | 通用兜底 |

**自定义转换器注册优先级**（同源同目标多个转换器时）：

| 规则 | 说明 |
|------|------|
| 精确类型优先 | `Converter<String, Money>` 精确匹配优先于泛化 `Converter<Object, ?>` |
| 条件转换器先行 | `ConditionalConverter.matches` 返回 false 直接跳过 |
| 后注册覆盖前注册 | 同签名转换器后者生效（GenericConversionService 按注册序） |
| 链式组合 | 无直接转换器时尝试中间类型桥接（如 String → Number → Integer） |

> ⚠️ **调试技巧**：`GenericConversionService` 的 debug 日志会打印"从 X 转换到 Y 找到转换器 Z"——转换不生效时开 `org.springframework.core.convert` 的 debug 日志，直接看**命中/未命中**与**匹配到的转换器**。

## 5. 转换链与自定义转换器

```text
自定义转换器生效链路（@Value / 绑定 / MVC 参数）：
  1. 容器创建 ConversionService（Boot：webConversionService，含全部 Converter Bean）
  2. 转换请求到达 → 类型匹配查找（含 GenericConverter 条件）
  3. 命中 Converter → 转换；未命中 → 抛 ConversionFailedException
```

| 场景 | 做法 |
|------|------|
| @Value 注入自定义类型 | Converter<String, T> 注册进容器（Boot 自动收集） |
| MVC 请求参数绑定 | `Converter<String,T>`（web 层 `addFormatters`）或 `Formatter<T>` |
| 属性文件 → 对象 | Boot `@ConfigurationProperties`（内建宽松绑定转换） |
| 集合嵌套转换 | `GenericConverter`（`String[] → List<Money>`） |

**GenericConversionService 查找流程（源码级）**：

```text
convert(source, sourceType, targetType):
  1. 缓存查询：ConvertersForPair（同源同目标）是否已解析 → 命中直接复用
  2. 精确匹配：遍历该对注册的转换器（含 ConditionalConverter.matches 判断）
  3. 元素/嵌套转换：目标为集合/Map 时，递归转换元素类型（元素走同一流程）
  4. 无匹配 → 查找"转换链"（源→中间→目标，如 String→Number→Integer）
  5. 全部失败 → 抛 ConversionFailedException（消息含源值、源/目标类型、可用的转换器数）
```

| 环节 | 关键实现 | 面试点 |
|------|---------|--------|
| 缓存 | `GenericConversionService` 的 `converters` 映射 + 转换链缓存 | "转换查找带缓存，避免重复匹配" |
| 条件 | `ConditionalConverter.matches(TypeDescriptor, TypeDescriptor)` | "条件转换器先于精确匹配过滤" |
| 嵌套 | `CollectionToCollectionConverter` 等集合转换器递归元素 | "集合转换是元素转换的组合" |
| 兜底 | `ObjectToStringConverter` 等通用转换器 | "Object 级转换器最后兜底" |

> ⚠️ **排查提示**：`ConversionFailedException` = 目标类型无法从源转换——先确认 Converter 是否注册、类型是否匹配；`canConvert` 返回 false 时检查 `ConditionalConverter.matches` 条件。

### 5.1 常见坑与生产实践

| 坑 | 症状 | 解法 |
|----|------|------|
| 转换器没生效 | @Value 自定义类型注入报转换失败 | 确认注册到"正在使用的那个 ConversionService"（Boot 有 web 与 application 两套） |
| 泛型转换误匹配 | `List<A>` 转成了 `List<B>` | 检查 GenericConverter 的 targetType 条件；确认源描述符带泛型 |
| 枚举转换区分大小写 | "pending" 转枚举失败 | 内建转换器忽略大小写回退（但精确匹配优先）；自定义时明确策略 |
| 空串转数值 | `""` → Integer 报错 | 内建转换器对空串返回 null（安全）；自定义转换器要处理空输入 |
| 循环转换 | A→B→A 死循环 | `GenericConversionService` 有转换链缓存与深度保护；自定义避免成环 |
| @ConfigurationProperties 类型不符 | 绑定报 `ConversionFailedException` | 检查目标字段类型与配置值；宽松绑定只转字符串源 |

**生产最佳实践**：

```java
// 转换器编写规范：null 安全 + 空串语义 + 不可变结果
@Component
public class MoneyConverter implements Converter<String, Money> {
    @Override
    public Money convert(String source) {
        if (!StringUtils.hasText(source)) {     // null/空白 → null（与内建语义一致）
            return null;
        }
        try {
            return Money.parse(source.trim());  // 容忍前后空白
        } catch (NumberFormatException e) {
            throw new ConversionFailedException(
                    TypeDescriptor.valueOf(String.class), TypeDescriptor.valueOf(Money.class),
                    source, e);                  // 包装为框架异常，错误信息统一
        }
    }
}
```

> 💡 **规范要点**：① 转换器必须是**无状态单例**（Boot 容器管理，可注入依赖）；② 异常抛 `ConversionFailedException`（携带源值信息）而非裸 NumberFormatException；③ 输入空值返回 null（内建语义）还是抛异常，要在团队内统一。

### 5.2 面试追问点

- **"泛型为什么能被还原"**：擦除发生在**对象创建之后**（堆上只有原始类型），但**声明处的字节码 Signature 属性保留完整泛型**——ResolvableType 读声明而非读对象；
- **"@Autowired List<Mapper> 怎么注入多个"**：ResolvableType 解析出 `List<Mapper>` 后，容器按元素类型收集所有 Mapper 候选并装配（`forClassWithGenerics(Collection.class, Mapper.class)` 是收集器的核心判断）；
- **"ConversionService 与 PropertyEditor 谁先谁后"**：`TypeConverterDelegate` 先查 ConversionService（3.0 起优先），无匹配再回退 PropertyEditor——所以新旧并存时新转换器天然优先；
- **"为什么转换器要无状态"**：ConversionService 是全局单例、并发共享，有状态的转换器（如缓存上一次值）会造成线程间串数据——PropertyEditor 的教训；
- **"TypeDescriptor 与 ResolvableType 关系"**：TypeDescriptor 是"ResolvableType + 注解"的组合封装，面向转换匹配；ResolvableType 纯类型解析，面向泛型还原——一个偏"转换域"、一个偏"类型域"；
- **"转换器与校验器是什么关系"**：转换解决"形态"（字符串→对象），校验解决"合法性"（对象内部规则）——先转换后校验是 @ConfigurationProperties 与 MVC 参数处理的固定顺序，两者分别属于 core 与 context。

> 🎯 **全篇收束**：类型系统的本质是"**把编译期信息在运行时用起来**"——泛型注入、泛型转换、泛型绑定全部依赖 Signature 属性 + 类型描述符；理解"声明处信息完整、运行处信息擦除"这一对矛盾，类型系统就不再有黑盒。面试答题时用"声明与运行"二分法组织语言：先说声明处能拿到什么（泛型、注解、参数名），再说运行处丢失什么、由哪一层补回来（ResolvableType 补类型、ParameterNameDiscoverer 补参数名、ConversionService 补形态）。
