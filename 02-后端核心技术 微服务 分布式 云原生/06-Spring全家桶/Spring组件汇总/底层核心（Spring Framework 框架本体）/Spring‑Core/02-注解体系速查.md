## 1. 组件注解族（stereotype）

| 注解 | 语义 | 派生关系 | 被谁消费 |
|------|------|---------|---------|
| `@Component` | 通用组件（扫描的底层语义） | - | 组件扫描 |
| `@Service` | 业务服务 | `@Component` 派生 | 语义标记（无行为差异） |
| `@Repository` | 数据访问 | `@Component` 派生 | + `DataAccessException` 翻译识别 |
| `@Controller` | Web 控制器 | `@Component` 派生 | Spring MVC |
| `@RestController` | 控制器 + JSON | `@Controller` 派生（web 模块） | Spring MVC |
| `@Indexed` | 候选索引标记 | 类型级 | 编译期生成索引（见第 4 节） |

> 💡 注解定义在 `org.springframework.stereotype`（**spring-core**），但"扫描并注册"发生在 beans/context——注解是数据，容器是消费者；这是 [Spring-Beans-03](../Spring‑Beans/03-注解与元数据速查.md) 的注解总表之外的"归属补充"。

**各注解的消费时机与行为差异**：

| 注解 | 消费方 | 消费时机 | 行为差异 |
|------|--------|---------|---------|
| `@Component` | 组件扫描器 | 容器 refresh 启动期 | 注册为 BeanDefinition |
| `@Service` | 扫描器（语义等价） | 同上 | 无差异（仅标记分层） |
| `@Repository` | 扫描器 + `PersistenceExceptionTranslationPostProcessor` | 启动期 + **每次数据访问异常时** | 异常翻译：`DataAccessException` 转换（见下） |
| `@Controller` | RequestMappingHandlerMapping | 启动期收集映射 | 额外支持 `@ExceptionHandler` 等 |
| `@RestController` | 同上 | 同上 | `@ResponseBody` 语义并入 |

**@Repository 的隐藏能力——异常翻译**：仅标注 `@Repository` 的 Bean 会被 `PersistenceExceptionTranslationPostProcessor` 代理，把持久层原生异常（如 `SQLException`）翻译为 Spring 统一的 `DataAccessException` 体系——这就是"为什么 DAO 层必须标 @Repository 而不是 @Service"的底层理由；翻译基于 `PersistenceExceptionTranslator` SPI，由具体持久化框架（JDBC/MyBatis/JPA）提供实现。

**常见误用边界**：

| 场景 | 是否用 stereotype | 说明 |
|------|:---:|------|
| 工具类（静态方法） | 否 | 不是 Bean 语义，直接 new 或 static |
| 配置类 | 否（用 `@Configuration`，非 stereotype） | @Configuration 在 context 包，语义完全不同 |
| 切面类 | 否（用 `@Aspect`） | 由 AOP 基础设施消费，非组件扫描语义 |
| 事件监听器 | 是（@Component + @EventListener） | 组合使用 |

**定义注解的三要素**（写自定义注解前自查）：

| 元注解 | 作用 | 踩坑点 |
|--------|------|--------|
| `@Target` | 允许标注的位置（TYPE/METHOD/FIELD/PARAMETER...） | 漏写 PARAMETER 导致方法参数注解不生效 |
| `@Retention` | 生命周期（SOURCE/CLASS/RUNTIME） | **Spring 消费的注解必须 RUNTIME**——CLASS 级注解反射读不到 |
| `@Documented` / `@Inherited` | javadoc 收录 / 类继承传递 | @Inherited 只对类上直接标注的注解生效，Spring 语义合并不受它控制 |

```java
// 生产级自定义注解示例：标记"需要审计"的方法
@Target({ElementType.TYPE, ElementType.METHOD})   // 类或方法
@Retention(RetentionPolicy.RUNTIME)               // ★ 必须 RUNTIME 才能被容器/切面读取
@Documented
public @interface Audited {
    String action() default "";
    boolean logArgs() default true;               // 默认值属性
}
```

> 💡 自定义注解被"谁"读取决定了写法的差异：被 AOP 切面读取（Pointcut 匹配注解）需 RUNTIME；仅编译期检查（如 Lombok）用 CLASS/SOURCE 即可——**先确定消费者，再定三要素**。

## 2. 元注解、组合注解与 @AliasFor

```java
// 元注解：注解上的注解
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Component                        // 元注解：被派生注解继承语义
public @interface Service { }

// 组合注解：多个注解 + 属性别名
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Controller
@ResponseBody
public @interface RestController {
    @AliasFor(annotation = Controller.class, attribute = "value")   // ★ 属性传递
    String value() default "";
}
```

| 机制 | 类/API | 作用 |
|------|--------|------|
| 属性别名 | `@AliasFor` | 组合注解属性 → 元注解属性传递（如 `@RestController("api")` 设 `@Controller("api")`） |
| 解析引擎 | `AnnotatedElementUtils` | 查找含元注解/组合注解的完整注解信息 |
| 合并读取 | `MergedAnnotations`（5.2+） | 高效合并多个注解源（类+方法+接口），7.x 标准读取 API |
| 注解过滤 | `AnnotationFilter` | 跳过 Java 内置注解等 |

```java
// MergedAnnotations 实战：读取"类上及其元注解上的 @Component 派生注解"
MergedAnnotations merged = MergedAnnotations.from(OrderService.class,
        MergedAnnotations.SearchStrategy.TYPE_HIERARCHY);       // 含接口/父类
boolean isComponent = merged.isPresent(Component.class);        // true（@Service 派生也算）
```

> 🎯 **核心要点**：`@Service` 能被识别为组件，靠的是**元注解语义传递**（`MergedAnnotations`/`AnnotatedElementUtils` 按策略向上合并）——面试答"为什么注解派生能生效"时指到 `MergedAnnotations` 与 `SearchStrategy`（TYPE_HIERARCHY 含父类接口）。

**@AliasFor 的完整规则**（面试深挖点）：

| 规则 | 说明 |
|------|------|
| 显式别名 | 同注解内两属性互标 `@AliasFor("other")`，值必须一致，否则运行时抛 `AnnotationConfigurationException` |
| 跨注解传递 | `@AliasFor(annotation = X.class, attribute = "v")` 把值传给元注解属性（如 RestController → Controller.value） |
| 传递链 | 支持多层（组合注解的元注解还能再组合），运行时按链合并 |
| 隐式别名 | 两个属性都别名到同一元注解属性时互为隐式别名，值也必须一致 |
| 只读规则 | 不允许"一个属性别名到多个不同注解属性"的菱形传递 |

```java
// 显式别名：同注解内相互别名
public @interface MyPath {
    @AliasFor("path") String value() default "";
    @AliasFor("value") String path() default "";
}
// 用法冲突：@MyPath(value = "/a", path = "/b") → 启动报 AnnotationConfigurationException
```

**失败表现**：别名值不一致时异常在**注解元数据首次合并**时抛出（通常在容器启动期），而非使用期——所以"配置冲突"要等到启动才暴露；排查时看异常信息里的属性名对照即可定位。

> ⚠️ **易错点**：`@AliasFor` 是 **Spring 自己的注解**，别与 JDK 的 `@Deprecated`/`@SuppressWarnings` 的"别名属性"概念混淆；且只有 `@Retention(RUNTIME)` 且被 `MergedAnnotations` 读取的注解才生效——用反射 `getAnnotation` 直接读组合注解拿不到别名传递值。

## 3. MergedAnnotations：注解读取 API

| API | 特点 |
|-----|------|
| `MergedAnnotations.from(source)` | 从类/方法/注解读取，默认 DIRECT 策略 |
| `SearchStrategy.DIRECT` | 仅直接标注 |
| `SearchStrategy.INHERITED_ANNOTATIONS` | 含继承注解（@Inherited） |
| `SearchStrategy.TYPE_HIERARCHY` | 含父类与接口上的（最常用） |
| `searchStrategies...` | `TypeMappedAnnotations` 等底层实现 |

> ⚠️ 注意区别：`MergedAnnotations`（Spring 5.2+ 推荐）与旧 `AnnotationUtils` 并存——新代码一律用 MergedAnnotations；`AnnotationUtils` 仍可用但不再演进。

**MergedAnnotations 源码级解析**：调用 `MergedAnnotations.from(clazz, strategy)` 时，实际创建 `TypeMappedAnnotations` 实例——它按策略构建**注解源链**（直接标注 → 元注解 → 父类/接口），读取时惰性遍历整条链并逐层做 `AnnotationTypeMapping`（类型映射，处理 @AliasFor 传递）。因此：

- **合并顺序**：直接标注的注解属性优先级最高，链上后层的值仅做"未显式声明时填充"；
- **缓存**：`MergedAnnotations` 可复用实例（线程安全），高频读取场景（如容器反复问"是否组件"）应缓存而非每次重建；
- **与 AnnotatedElementUtils 分工**：`AnnotatedElementUtils` 面向"找某个注解的完整合并属性"（`findMergedAnnotation`），`MergedAnnotations` 面向"批量判断/遍历"——前者在 Beans 系列用的多，后者在 core 内部是主力。

```java
// 缓存复用：容器内"是否组件"判断会高频调用，缓存解析结果
private static final ConcurrentHashMap<Class<?>, Boolean> COMPONENT_CACHE = new ConcurrentHashMap<>();

static boolean isComponent(Class<?> type) {
    return COMPONENT_CACHE.computeIfAbsent(type, t ->
            MergedAnnotations.from(t, MergedAnnotations.SearchStrategy.TYPE_HIERARCHY)
                    .isPresent(Component.class));
}
```

**MergedAnnotations 常见坑**：

| 坑 | 表现 | 解法 |
|----|------|------|
| 策略用错 | 接口方法上的注解读不到（默认 DIRECT） | 方法场景用 `TYPE_HIERARCHY` 或 `TYPE_HIERARCHY_AND_METHODS` |
| 泛型擦除 | 注解在泛型基类上，子类读不到 | 策略含父类并确认泛型类注解确实可继承标注 |
| 性能误用 | 每次调用都 `MergedAnnotations.from` | 复用实例或缓存结果（见上） |
| 混淆 JDK 反射 | 用 `clazz.getAnnotation()` 读组合注解值 | 组合/别名语义必须走 MergedAnnotations |
| 处理 @Inherited | 以为继承策略只认 @Inherited | Spring 的层级搜索不依赖 @Inherited 标注 |

## 4. @Indexed 与候选组件索引

| 项 | 说明 |
|----|------|
| 问题 | 组件扫描在启动时遍历所有类字节码（`ClassPathScanningCandidateComponentProvider`），大项目慢 |
| 方案 | `@Indexed` 标记 → 编译期 `spring-context-indexer` 生成 `META-INF/spring.components`（类名→注解清单） |
| 效果 | 启动跳过扫描，直接读索引（可快 2-10 倍，视项目规模） |
| 注意 | 索引缺失时自动回退扫描——**语义不变，只是速度**；动态新增类路径需重新生成 |

```xml
<!-- 编译期生成索引 -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context-indexer</artifactId>
    <optional>true</optional>
</dependency>
```

```java
@Component
@Indexed      // 或标在派生注解上：@Indexed 元注解在 @Service 上已存在
public class OrderService { }
```

> 💡 细节：`@Indexed` 本身标注在 `@Component` 上——**标注 @Component 派生的类天然带索引候选**；7.0 的 `ClassFileMetadataReader`（Java 24+）已大幅加速扫描，索引对超大项目仍有效。

**索引文件长什么样**（理解后更容易排查"为什么没生效"）：

```text
# META-INF/spring.components（spring-context-indexer 编译期生成）
com.example.OrderService=org.springframework.stereotype.Component
com.example.PaymentRepository=org.springframework.stereotype.Repository
```

| 场景 | 行为 | 注意 |
|------|------|------|
| 索引存在 | 扫描器读索引，跳过字节码遍历 | 类路径新增 jar 需重新编译生成 |
| 索引缺失 | 自动回退完整扫描 | 语义不变，仅速度下降——**不会报错** |
| 索引过时（新增了 @Component 类未重编译） | 该 Bean 不被注册 | 这是索引唯一"静默丢 Bean"风险，CI 需保证 indexer 参与编译 |
| 多模块 | 每模块独立生成，扫描器合并读取 | 依赖模块需 `optional` 引入 indexer |

> ⚠️ **索引与 AOT 的区别**：`@Indexed` 索引是**启动期加速**（JVM 模式）；AOT 提示（`RuntimeHints`）是**原生镜像信息**（编译期注册）。两者不冲突也不替代——面试别混为一谈。

**什么时候值得引入 @Indexed**（成本收益权衡）：

| 项目规模 | 建议 | 理由 |
|---------|------|------|
| 组件 < 500 个 | 不引入 | 收益可忽略，多一个编译依赖 |
| 组件数千、启动要求 < 5s | 引入 | 扫描时间可砍 50-90% |
| 启动即性能指标（Serverless/FaaS） | 引入 + 关闭扫描回退 | 冷启动收益显著 |
| 类路径动态变化（插件体系） | 慎用 | 索引静态生成，动态类路径需重编译 |

> 💡 判断依据：先量一次启动日志中的 `ClassPathScanningCandidateComponentProvider` 耗时（debug 日志可见扫描耗时统计），扫描 < 200ms 就不值得引入；7.0 + JDK 24+ 的 Class-File API 扫描加速会让这个临界点更高。

## 5. 空安全注解与 JSpecify 迁移（7.0）

| 版本 | 注解 | 语义 |
|------|------|------|
| ≤ 6.2 | `org.springframework.lang.Nullable` / `NonNull` / `NonNullApi` / `NonNullFields` | JSR 305 语义（可被 Spring 识别） |
| 7.0+ | **迁移到 `org.jspecify.annotations.Nullable`/`NonNull`** | JSpecify 标准；Spring 自身源码已迁移 |

| 变化 | 影响 |
|------|------|
| Spring 内部代码 | 全部换 JSpecify 注解（含数组/泛型元素级空性） |
| 第三方用户代码 | 旧 `org.springframework.lang.*` 注解**仍可用但已废弃**（编译警告） |
| Kotlin 空性 | JSpecify 与 Kotlin 空安全映射更精确；个别 API 空性语义微调 |
| 工具链 | IDE/静态检查（Checker Framework、IntelliJ）对 JSpecify 支持完善 |

```java
// 7.0 新代码推荐（依赖 org.jspecify:jspecify）
import org.jspecify.annotations.Nullable;

public record Config(@Nullable String endpoint, int timeout) { }

// 存量代码：spring.lang 注解照常工作，只是标记 deprecated
```

> ⚠️ **升级提示**：① 不要大规模重写现有 `@Nullable`——废弃不破坏功能；② 新代码优先 JSpecify；③ 若被 `@NonNullApi` 包级默认覆盖逻辑影响，检查包级 `package-info.java` 的迁移状态。

**JSpecify 注解全景**（`org.jspecify.annotations` 包）：

| 注解 | 语义 | 对应旧注解 |
|------|------|-----------|
| `@Nullable` | 值可能为 null | `org.springframework.lang.Nullable` |
| `@NonNull` | 值不可为 null（默认隐式） | `org.springframework.lang.NonNull` |
| `@NullMarked` | 包/类级：内部默认全部非空，个别 `@Nullable` 例外 | `NonNullApi` + `NonNullFields` |
| `@NullUnmarked` | 取消外层 NullMarked 默认 | 无直接对应 |

```java
// 包级声明（package-info.java）：整包默认非空，单个参数例外
@NullMarked
package com.example.api;

import org.jspecify.annotations.NullMarked;
```

**迁移策略建议**：

| 项目状态 | 建议 |
|---------|------|
| 业务代码用了 spring.lang 注解 | 保留不动（废弃警告可忽略或加 `@SuppressWarnings`） |
| 新写的库/API | 直接用 JSpecify，声明 `org.jspecify:jspecify` 依赖 |
| 被 Kotlin 消费的 API | 优先迁移——JSpecify 与 Kotlin 空性映射更准确 |
| 依赖 Checker Framework | 确认版本支持 JSpecify（2.x+） |

**空安全注解如何被工具链使用**：这些注解**只影响静态分析，不影响运行期行为**——IDE 自动补全与编译器告警、Checker Framework 静态检查、Kotlin 空安全映射都以它们为输入；运行时它们被忽略（Retention 仅为 CLASS，反射不可见）。因此：

- 误标 `@Nullable` 不会造成运行期 NPE 保护（它只是"声明"，不是检查）；
- 真正防 NPE 靠代码习惯 + 静态检查 + 测试，注解是"契约文档"；
- Kotlin 调用 Java API 时，`@Nullable` 参数类型映射为 `String?`（可空），无标注映射为非空——**标注错误会误导 Kotlin 调用方产生运行时 NPE**，这是迁移 JSpecify 最实际的收益场景。

```kotlin
// Kotlin 视角：Java API 的空性注解决定可空类型
// Java: @Nullable String endpoint   →  Kotlin: String?
// Java: String name（无注解）        →  Kotlin: String（编译器视为非空）
val name: String = api.getName()      // 若实际返回 null → NPE（Kotlin 侧）
```

> 💡 **工程建议**：对外暴露的库/API 认真标注空性（收益是调用方 IDE 提示与 Kotlin 互操作）；纯内部代码标注优先级低——注解是成本（维护）与收益（契约清晰）的权衡，不是"标得越多越好"。

### 5.1 面试追问点

- **"@Component 与 @Service 有什么区别"**：语义上无行为差异，@Service 只是 @Component 的派生标记——区别在于可读性与工具支持；而 @Repository 有额外异常翻译行为、@Controller 有 MVC 映射行为，这是"派生但不完全等价"的证据；
- **"注解继承为什么默认不生效"**：Java 的 `@Inherited` 只对**类继承**生效且只针对**类上直接标注**的注解；Spring 的"继承"是**元注解语义合并**（MergedAnnotations 沿注解链向上找），两者机制完全不同——所以接口上的注解也能"生效"；
- **"自定义注解怎么让 Spring 识别为组件"**：把 `@Component` 作为元注解标在自己的注解上，并保证 `@Retention(RUNTIME)`；或用 `@Indexed` 标记后注册自定义扫描器；
- **"@AliasFor 与继承的区别"**：@AliasFor 是**同一注解语义的属性透传**（编译期字节码 + 运行期合并），不是 Java 继承——被别名注解无需知道别名的存在；
- **"为什么需要 @Indexed"**：组件扫描默认按字节码逐类检查，类路径大时启动慢；索引把"谁是组件"提前到编译期确定，运行期读索引表即可。

### 5.2 生产自查清单

| 检查项 | 方法 |
|--------|------|
| 自定义注解是否 RUNTIME | `javap -v 注解类` 查看 Retention |
| 组件扫描是否生效 | debug 日志看 `Using candidate component class` 行 |
| 派生注解是否被识别 | 写单测断言 `MergedAnnotations...isPresent(Component.class)` |
| 别名冲突 | 启动期异常即暴露；别名属性保持单一赋值习惯 |
| 索引是否参与编译 | 检查 target 目录存在 `META-INF/spring.components` |

> 🎯 **全篇收束**：注解体系的本质是"**字节码元数据 + 合并语义引擎**"——注解本身是数据，MergedAnnotations 是解析引擎，容器是消费者；写自定义注解时永远先问"谁读它、读什么策略、失败表现是什么"。
