## 1. Artifact 坐标与版本线

| 项 | 值 |
|----|----|
| GroupId | `org.springframework` |
| ArtifactId | `spring-core` |
| 最新版本 | 7.0.x（2026-08 时点，随 Framework 7.0 主线） |
| 维护线 | 7.0.x / 7.1.x（最新）、6.2.x（Boot 3.x） |
| Java 基线 | 17+（官方推荐 JDK 25 LTS；7.0 起 Java 24+ 自动用 Class-File API 扫描） |
| 可选伴侣 | Kotlin 2.2（core 提供 Kotlin 扩展）、GraalVM 25（AOT 运行时提示） |

> 💡 项目几乎从不显式声明 spring-core——`spring-beans` 传递依赖它；但**移除过时依赖排查**时要知道它是"万物之根"。

**坐标使用场景**：

| 场景 | 是否显式声明 | 说明 |
|------|:---:|------|
| Spring Boot 项目 | 否 | Boot 依赖管理统一提供，版本由 BOM 锁定 |
| 纯 Framework 项目 | 否 | 声明 spring-context 即可传递引入 |
| 只想用工具类 | 是 | 如"只想要 StringUtils/ResolvableType"的独立库，单独引入 core |
| 排查依赖冲突 | 否 | 用 `mvn dependency:tree` 观察，而非手动加版本 |

**版本线演进背景**：6.2 系列（2024-11 发布）服务 Boot 3.x 存量市场；7.0（2025-11）与 Boot 4.0 同步，是首个完整支持 JDK 24/25 的主线；7.1（2026-05）作为特性线持续维护。三者并存期较长，选型核心看 Boot 版本而非 Framework 版本——Boot 3.x 项目强行升 core 7.0 会导致 beans/context 版本不匹配。

**Gradle 写法**（非 Maven 项目对照）：

```kotlin
// build.gradle.kts：仅工具类场景可单独声明
implementation("org.springframework:spring-core:7.0.6")
// 全量项目仍建议 platform() 统一版本：
implementation(platform("org.springframework:spring-framework-bom:7.0.6"))
```

> 💡 **版本锁定建议**：无论 Maven 还是 Gradle，核心原则一致——**版本号只写一处**（BOM/platform），业务代码永不写 Spring 版本；CI 增加"依赖树检查"脚本（校验 core 唯一版本）可提前拦截混用事故。

│   ├── Assert / StringUtils / ObjectUtils / CollectionUtils / NumberUtils
│   ├── ReflectionUtils / ClassUtils / MethodInvoker / AttributeAccessor
│   ├── ResolvableType / TypeDescriptor / GenericTypeResolver / ParameterNameDiscoverer
│   ├── NamedThreadLocal / StopWatch / ConcurrentReferenceHashMap

│   ├── OrderComparator / PriorityOrdered / Ordered / AnnotationAwareOrderComparator

├── core.annotation
│   ├── @AliasFor / @Indexed / @Order / @NonNull / @Nullable / @NonNullApi / @NonNullFields
│   ├── MergedAnnotations / AnnotatedElementUtils / AnnotationUtils / AnnotationFilter

│   └── SpelCompilerMode / ExpressionValue
├── core.convert
│   ├── ConversionService / Converter / ConverterFactory / GenericConverter / ConditionalConverter
│   ├── support：DefaultConversionService / GenericConversionService ★ / 内建 60+ 转换器
├── core.retry（★ 7.0 新增，Spring Retry 并入）

**高频面试点名类**：`ResolvableType`、`StringUtils`、`ReflectionUtils`、`ConversionService`、`Resource`、`SpelExpressionParser`、`RetryTemplate`（7.0）。

**包结构设计原则**：core 的包划分遵循"能力域 + 依赖不上升"两条规则——同一能力域（转换、表达式、序列化）的接口、实现、工具收拢在同包；包之间几乎不互相依赖（io 不依赖 convert、convert 不依赖 expression），保证任一小包可独立抽取。历史上 Spring 曾尝试把 core 拆成多个更小的模块，最终因依赖复杂度放弃——理解这点就明白为何 core 是个"大而内聚"的包而非多个小模块。

**核心类归属速查**（面试问"这个类在哪个包"直接查表）：

| 类 | 包 | 一句话职责 |
|----|----|-----------|
| `@Component` / `@Service` | `org.springframework.stereotype` | 组件注解定义 |
| `@AliasFor` / `@Indexed` | `org.springframework.core.annotation` | 元注解机制 |
| `Assert` / `StringUtils` | `org.springframework.core` | 基础工具 |
| `ResolvableType` | `org.springframework.core` | 泛型解析引擎 |
| `ConversionService` | `org.springframework.core.convert` | 转换门面 |
| `Resource` | `org.springframework.core.io` | 资源抽象 |
| `SpelExpressionParser` | `org.springframework.core.expression` | SpEL 解析器 |
| `Environment` 接口 | `org.springframework.core.env` | 属性契约 |
| `StandardEnvironment` | `org.springframework.core.env`（**实现也在 core**） | 默认环境实现 |
| `RetryTemplate` | `org.springframework.core.retry`（7.0） | 重试引擎 |
| `RuntimeHints` | `org.springframework.aot.hints` | 原生镜像提示 |

> 💡 **包设计规律**：core 的包名即职责后缀（`annotation`/`env`/`io`/`convert`/`expression`/`retry`），记忆方式是"`org.springframework.core.` + 能力名"——比记类名更快；`stereotype` 与 `aot` 是仅有的两个例外包名。

**7.0 包内容变化清单**（升级时对照检查）：

| 包 | 变化 | 影响 |
|----|------|------|
| `core.retry` | ★ 新增（原 spring-retry 项目并入） | 新 API 落地，旧坐标失效 |
| `core`（顶层） | `ListenableFuture` 删除（util.concurrent） | 改用 CompletableFuture |
| `core`（顶层） | `Codec`/`Encoder`/`Decoder` 增强 | web 层编解码消费 |
| `core.expression` | `ExpressionParserConfiguration` 新增（操作上限） | SpEL 防炸弹配置入口 |
| `core.annotation` | `@NonNull` 等语义空注解标记废弃 | 迁移 JSpecify |
| `core.io.support` | `PathMatchingPatternResourceResolver` 重构（glob） | AOT 提示写法变化 |
| `core.aot.hints` | 资源提示正则改 glob | 原生镜像构建提示更新 |

> ⚠️ **升级检索技巧**：升级后先全库搜索 `ListenableFuture`、`spring-jcl`、`maxAttempts`、`org.springframework.retry` 四个关键词——命中即 7.0 破坏性变更点，逐一替换即可（替换映射见 [00-总览](00-Spring Core组件总览.md) 第 2 节迁移清单）。

## 3. spring-jcl 移除与日志体系（7.0）

| 版本线 | 日志机制 |
|--------|---------|
| ≤ 6.2 | spring-jcl 模块：`SpringJclLog` 自动桥接（Log4j2/Logback/JDK 内置，无依赖） |
| 7.0+ | **spring-jcl 移除**，直接依赖 Apache Commons Logging 1.3.0（`org.apache.commons.logging`） |

**spring-jcl 是什么、为何被移除**：6.2 及以前，Spring 为避免直接依赖 commons-logging（其 classpath 探测定序曾被诟病），自造了 `spring-jcl` 小模块——运行时探测应用已存在的日志实现并桥接。7.0 评估后认为"自造门面"的维护成本高于收益（现代应用几乎都经 SLF4J 桥接），回归 commons-logging 官方门面。**对应用层的影响几乎为零**，因为业务代码不直接调用 Spring 日志 API；唯一感知点是依赖树里少了一个 `org.springframework:spring-jcl`。

```xml
<!-- 7.0 传递依赖即满足 -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-core</artifactId>
    <version>7.0.6</version>
</dependency>
<!-- 无需再显式声明 org.springframework:spring-jcl -->
```

> ⚠️ **升级注意**：① 移除项目中显式声明的 `spring-jcl` 坐标；② 项目依赖 commons-logging 冲突时需检查传递版本（Commons Logging 1.3.0+）；③ 自定义日志桥接（如 SLF4J 的 `slf4j-jcl`）不受影响——应用层日志仍是 SLF4J/Logback 正常运作。

**日志体系工作原理**：Spring 框架内部日志从不直接绑定具体实现，而是通过 commons-logging 门面 API（`LogFactory`）输出；应用层选择实现方（Logback/SLF4J）后，门面在运行期自动路由。

| 日志方案 | 桥接方式 | 适用场景 |
|---------|---------|---------|
| Logback（Spring Boot 默认） | `logback-classic` 实现 SLF4J，`slf4j-jcl` 桥接 commons-logging | 绝大多数应用 |
| Log4j2 | `log4j-jcl` 或 SLF4J 桥接 | 对异步/性能有强需求 |
| JDK 内置 | 无桥接时 commons-logging 自动回退 JUL | 零依赖最小环境 |
| 无任何实现 | 输出被丢弃（仅有简单日志警告） | 工具类项目可接受 |

```xml
<!-- 最常见的应用层组合：SLF4J + Logback（Spring 日志经桥接进入统一管道） -->
<dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>2.0.x</version>
</dependency>
<dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>1.5.x</version>
</dependency>
```

> 💡 **排障口诀**："应用日志正常但 Spring 日志看不到"= 缺桥接依赖；"Spring 日志重复输出"= 多个实现同时在场（常见于同时引入 Logback 与 Log4j 依赖）；Spring 自身日志级别由 `org.springframework` 的 logger 级别控制，与业务包分开配置。

```yaml
# application.yml：Spring 框架日志级别（与业务日志分开治理）
logging:
  level:
    org.springframework: info          # 框架整体
    org.springframework.core: warn     # core 包细化（可精确到子包）
    org.springframework.core.retry: debug   # 排查重试行为时打开
```

> 💡 **实战技巧**：排查 core 行为（如转换失败、资源解析、SpEL 求值）时，把对应包日志调到 debug——core 的日志点虽少但信息密度高（`PathMatchingResourcePatternResolver`、`GenericConversionService`、`SpelExpressionParser` 均有关键 debug 输出），比加断点快得多。

**日志相关常见问题案例**：

| 现象 | 根因 | 修复 |
|------|------|------|
| 启动时"Logging system failed to initialize" | Boot 日志初始化顺序冲突（自定义日志配置路径错误） | 检查 `logging.config` 指向存在的文件 |
| Spring 内部日志全部消失 | 应用只引了 SLF4J API 无实现 | 加 logback-classic |
| 日志重复打印同一条 | 多实现（Logback + Log4j2）同时在 classpath | 排除其一，保留单一实现 |
| 升级 7.0 后找不到 `SpringJclLog` 类 | 代码直接引用了 spring-jcl 内部类（罕见但存在） | 改为 commons-logging `LogFactory` 或 SLF4J |
| 控制台日志乱码 | 编码配置缺失 | `logging.charset` 明确 UTF-8 |

> 🎯 记忆点：Spring 日志策略 30 年没变过——**门面 + 桥接 + 单一实现**三件套；7.0 只是换了门面实现（spring-jcl → commons-logging），应用层桥接方式完全不变。

## 4. 依赖边界

```text
spring-core（零核心依赖）
  ├── 编译必需：无（纯 JDK）
  ├── 可选：kotlin-stdlib（Kotlin 扩展）、commons-logging 1.3（日志）
  └── 被依赖：spring-beans / spring-context / spring-aop / spring-web / Boot 全家
```

| 关系 | 说明 |
|------|------|
| core → 其他模块 | **零依赖**（地基特性） |
| beans → core | 注解（@Component 定义在 core）、工具、ConversionService |
| context → core | Environment 接口、SpEL、Resource 抽象、retry |
| aop/tx/web → core | 通用能力全部下沉 |

> 🎯 **核心要点**：`@Component`/`@Service` 定义在 **core 的 `org.springframework.stereotype`**；`Environment`/`PropertyResolver` 在 **core 的 `org.springframework.core.env`**——"注解与接口在 core、容器在 beans、企业容器在 context"是模块地图的三根支柱。

**为什么 core 必须零依赖**——三个工程理由：

| 理由 | 解释 |
|------|------|
| 依赖方向唯一 | 若 core 依赖 beans，则 core 无法被 beans 依赖，形成环；所有模块都依赖 core 才能形成无环图 |
| 下沉原则 | 通用能力（字符串/反射/泛型/转换）放最底层，各模块免重复实现 |
| 独立可用 | 纯 JDK 的 core 可脱离 Spring 单独发布与测试（工具类库场景） |

**被依赖面**：spring-beans、spring-context、spring-aop、spring-web、spring-tx、spring-orm 以及 Boot 全家——凡声明任意 Spring 模块，依赖树必然出现 spring-core；因此**core 的版本就是整个 Spring 栈的"公共锚点"**，升级时优先保证它唯一。

```text
验证依赖树（Windows PowerShell）：
  mvn dependency:tree -Dincludes=org.springframework:spring-core
  输出应只有一个版本号；出现两个不同版本 = 需要 BOM 对齐
```

> ⚠️ **依赖冲突典型症状**：`NoClassDefFoundError: org/springframework/core/...`（类缺失）或 `NoSuchMethodError`（类存在但方法签名不匹配）——两者都优先怀疑 core 版本混用，而非代码问题。

**依赖边界自测题**（检验是否理解"零依赖"含义）：

| 问题 | 答案 |
|------|------|
| 只引入 spring-core 能跑起容器吗 | 不能——core 无容器实现，需 beans（BeanFactory）与 context（ApplicationContext） |
| 只引入 spring-core 能用 StringUtils 吗 | 能——纯 JDK 工具，编译运行零外部依赖 |
| core 能直接读取 application.yml 吗 | 不能——属性文件加载由 context/Boot 提供（`YamlPropertySourceLoader` 在 Boot） |
| core 的注解能被 JDK 原生扫描到吗 | 能——注解是字节码数据，与容器无关 |
| 日志必须配 Logback 吗 | 不必——无实现时 commons-logging 回退 JDK 内置日志，只是级别控制弱 |

> 💡 **自测结论**：core 是"能力零件库"——单件可用、整套需要上层组装；面试答"Spring 依赖关系"时用这句收尾，比罗列模块名更有深度。

**core 能力在上层模块的消费样例**（证明"谁依赖谁"的实锤）：

| 上层模块 | 消费的 core API | 典型调用点 |
|---------|----------------|-----------|
| spring-beans | `ResolvableType`、`TypeDescriptor` | `AutowiredAnnotationBeanPostProcessor` 注入点解析 |
| spring-context | `Environment`、`ResourcePatternResolver` | `AbstractApplicationContext.refresh()` 阶段 |
| spring-aop | `AnnotationAwareOrderComparator` | 通知排序 |
| spring-web | `Codec`/`Encoder`/`Decoder` | HTTP 消息编解码 |
| spring-tx | `TransactionSynchronization` 无关——用 `Assert`/`ReflectionUtils` | 事务属性解析 |
| Boot | `AotContext`、`RuntimeHints` | 原生镜像 AOT 处理 |

```java
// 手写示例：模拟 beans 层如何用 core 能力判断"这个类是不是组件"
import org.springframework.core.annotation.MergedAnnotations;
import org.springframework.stereotype.Component;

boolean isComponent(Class<?> clazz) {
    return MergedAnnotations.from(clazz, MergedAnnotations.SearchStrategy.TYPE_HIERARCHY)
            .isPresent(Component.class);
    // @Service / @Repository / @Controller 均命中——元注解合并语义
}
```

> 💡 面试拓展：说出"core 提供 `MergedAnnotations`，`ClassPathScanningCandidateComponentProvider`（beans/context）消费它完成候选判定"——比干背"注解在 core"深一层；消费方源码见 [Spring Core-02-BeanDefinition注册与解析机制](../../../Spring Core/02-BeanDefinition注册与解析机制.md)。

## 5. 版本兼容速查

| Spring Framework | Spring Boot | 备注 |
|------------------|-------------|------|
| 7.0.x（2025-11 起） | Boot 4.0.x | 当前主线；core.retry / JSpecify / glob AOT 提示 |
| 7.1.x（2026-05 起） | Boot 4.1.x | 最新维护线 |
| 6.2.x | Boot 3.4/3.5 | 存量主流；spring-jcl 仍存在、Spring Retry 独立项目 |

> 💡 **升级提示（6.x → 7.x）**：① 移除 spring-jcl 显式依赖；② `ListenableFuture` 相关代码改 `CompletableFuture`；③ 若用独立 spring-retry 项目：API 已在 7.0 内建（`core.retry`），移除外部依赖并迁移注解（`maxAttempts` → `maxRetries`）；④ AOT 资源提示改 glob 写法（[00-总览](00-Spring Core组件总览.md) 第 2 节）。

### 5.1 版本选型决策表

| 项目状态 | 推荐版本 | 理由 |
|---------|---------|------|
| 新项目（2026-08 起） | 7.1.x（Boot 4.1） | 最新特性线，维护期最长 |
| 存量 Boot 3.x 项目 | 6.2.x 保持 | 无强需求不升级，升级成本集中在业务代码 |
| 依赖 ListenableFuture / javax 注解 | 6.2.x | 7.0 已移除，迁移需改造代码 |
| 需要 Java 24+ 扫描加速 | 7.0.x+（JDK 25 LTS） | ClassFileMetadataReader 生效 |
| 纯工具库消费者 | 任意（建议最新） | 只依赖 core 单模块，升级风险极低 |

**升级演练（6.2 → 7.0 最小步骤）**：

```text
1. 备份分支 → 2. 统一 BOM 到 7.0.x → 3. 编译（修 ListenableFuture/spring-retry 引用）
4. 全局搜索四个破坏性关键词 → 5. 跑单元测试（重点 SpEL/转换/资源用例）
6. 跑集成测试（重点重试与日志配置） → 7. 灰度发布观察日志 → 8. 验证 AOT 构建（如有）
```

| 阶段 | 主要失败信号 | 应对 |
|------|-------------|------|
| 编译 | 找不到类/方法 | 按 7.0 变更清单替换（本文件第 2 节） |
| 单测 | SpEL 超限、转换异常 | 调配置或修表达式（06/04 篇） |
| 集成 | 日志缺失、重试行为变化 | 检查桥接依赖与 core.retry 配置（03/07 篇） |
| 灰度 | 启动变慢 | 确认 JDK 24+ 使用 Class-File API 扫描加速 |

> 🎯 **收尾要点**：模块清单的意义不在背包名，而在于建立"归属直觉"——看到类名能立刻判断它在 core 的哪个包、属于哪个能力域、被谁消费；这套直觉是排查依赖问题的第一工具。

### 5.2 面试追问点

- **"为什么 spring-core 版本必须全局唯一"**：所有模块传递依赖它，多版本共存时类加载按 classpath 顺序取其一，出现"编译期对、运行期错"的经典事故；
- **"core 里哪些类在业务代码中值得直接使用"**：Assert（契约校验）、StringUtils（字符串）、ResolvableType（泛型工具）、StopWatch（性能观测）——其余大多为框架内部消费；
- **"core.env 的接口与实现为何同包"**：`Environment` 接口在 core 定义契约，`StandardEnvironment` 实现也在 core（因为它是纯属性解析，无需容器），而**容器内的环境装配**（propertySources 注册）在 context——接口、实现、装配三层分离。

### 5.3 生产检查清单（依赖治理）

| 检查项 | 工具/命令 | 合格标准 |
|--------|----------|---------|
| core 版本唯一 | `mvn dependency:tree -Dincludes=org.springframework:spring-core` | 仅一个版本 |
| 无 spring-jcl 残留 | 全库搜索坐标 | 0 处（7.0 项目） |
| 无独立 spring-retry | 全库搜索坐标 | 0 处（7.0 项目） |
| 无 ListenableFuture 引用 | 全库搜索类名 | 0 处（7.0 项目） |
| BOM 版本统一 | 检查 pom 的 dependencyManagement | 仅一处声明 |
| 日志实现唯一 | `mvn dependency:tree -Dincludes=ch.qos.logback,org.apache.logging.log4j` | 单一实现族 |

> 💡 建议把这张表做成 CI 脚本（搜索关键词 + 依赖树断言），每次构建自动校验——依赖治理的投入产出比在 Spring 项目里是最高的。

> 🎯 **全篇收束**：01 篇回答三个问题——core 坐标是什么（1 节）、core 里有什么（2 节）、core 和别的关系（3-5 节）；后续各篇分别展开能力细节，遇到"某能力属于谁"的归属疑问时回到本页包地图定位。同时记住一句话：**core 是 Spring 唯一"没有自己的运行时"的模块，它的全部价值在于被上层调用**——这也是它与 beans/context 最本质的区别。
