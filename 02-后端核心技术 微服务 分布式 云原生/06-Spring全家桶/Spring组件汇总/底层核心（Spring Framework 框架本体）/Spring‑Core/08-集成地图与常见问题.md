## 1. 与其他模块的集成地图

```text
                     spring-core（零依赖地基）
        ┌──────┬────────┬────────┬─────────┬────────┐
        ↓      ↓        ↓        ↓         ↓        ↓
  spring-beans spring-context spring-aop spring-tx spring-web  GraalVM/AOT
  @Component   容器/事件/环境   切点/代理   事务      MVC/WebFlux  运行时提示
  工具/转换    SpEL/Resource  表达式     通知      codec        org.springframework.aot
```

| 消费点 | core 提供 | 消费者 |
|--------|----------|--------|
| 组件扫描 | `@Component` 族注解 | beans 的扫描器 |
| 容器属性 | `Environment`/`PropertyResolver` 接口 | context 的 StandardEnvironment 装配 |
| 注入解析 | `ResolvableType`（泛型匹配） | beans 的 @Autowired 解析器 |
| 类型转换 | `ConversionService`/`Converter` | beans 属性填充、MVC 参数绑定、@Value |
| 配置加载 | `Resource`/`ResourcePatternResolver` | context 的 XML/属性加载、Boot 配置 |
| 表达式 | SpEL | @Value/缓存键/安全表达式 |
| 弹性 | `core.retry`（7.0） | context 的 @Retryable 注解层 |
| AOT | `org.springframework.aot.hints`（glob 格式，7.0） | Boot 原生镜像编译期处理 |

**集成方向的三个"单向"铁律**（理解集成地图的骨架）：

| 铁律 | 说明 | 违背后果 |
|------|------|---------|
| 依赖单向 | 只有上层依赖 core，core 永不依赖上层 | 循环依赖 → 编译失败（模块化红线） |
| 时机单向 | core 的能力永远"被调用"，从不主动运行 | 概念错位 → 排查方向错误 |
| 语义单向 | 注解/接口在 core 定契约，实现/装配在上层 | 契约与实现混淆 → API 归属判断错误 |

> 💡 这三个单向是"为什么 core 改动少、升级稳"的根因——上层怎么变，契约（core）不动；面试讲"Spring 模块化为什么成功"时引用这三条，比背模块清单有说服力。

> 🎯 **核心要点**：core 是"能力库"而非"运行时"——它从不启动任何东西，一切能力都被上层模块在合适的时机（refresh、绑定、请求处理）调用；**没有 core，Spring 只剩一堆无法互通的类**。

**六条核心消费链路的完整路径**（面试"core 能力如何落地"的标准答案素材）：

| 链路 | 完整路径 | 失败时的排查入口 |
|------|---------|----------------|
| 组件扫描 | stereotype 注解 → MergedAnnotations（core）→ ClassPathScanningCandidateComponentProvider（context）→ BeanDefinition（beans） | 扫描器 debug 日志 |
| 泛型注入 | 注入点声明 → ResolvableType（core）→ DefaultListableBeanFactory 候选匹配（beans） | 注入点泛型是否完整声明 |
| 属性绑定 | ${} 占位符 → PropertyResolver（core.env）→ TypeConverter 转换（core.convert）→ BeanWrapper 填充（beans） | 占位符未解析 vs 转换失败 |
| 表达式求值 | 注解属性 → SpelExpressionParser（core.expression）→ 拦截器求值（context 缓存/AOP） | 表达式缓存与上下文配置 |
| 资源加载 | location 字符串 → ResourceLoader（core.io）→ 具体 Resource → 消费方（context/Boot） | 前缀与 classpath* 用法 |
| 弹性容错 | @Retryable（context）→ 代理 → RetryTemplate（core.retry）→ 策略执行 | 代理是否生效、策略是否匹配 |

> 💡 **规律**：每条链路都是"**core 提供零件 → context/beans 负责装配与时机 → 业务无感消费**"三段式；排查时先定位"在哪一段断的"（编译期/启动期/运行期），再进对应模块查——这是框架排查的通用方法，不只适用于 core。

## 2. 底层核心四系列串联

```text
底层核心（Spring Framework 框架本体）四兄弟：
  Spring-Core     地基：注解/工具/类型/资源/SpEL/重试     ← 本系列
  Spring-Beans    工厂：BeanFactory/BeanDefinition/生命周期 ← 8 篇
  Spring-Context  容器：ApplicationContext/事件/国际化/环境  ← 8 篇
  Spring-AOP      织入：切点/通知/代理                      ← 5 篇

学习顺序：Core（能力）→ Beans（工厂）→ Context（容器）→ AOP（织入）
面试答"容器体系"时按此递进，体现体系感。
```

**典型面试叙事（按四系列递进的一分钟回答）**：

> "Spring 的分层是**能力 → 对象 → 环境 → 横切**：core 提供基础能力（注解契约、泛型解析、类型转换、资源抽象、表达式、重试），它零依赖、只有被调用才运行；beans 层基于这些能力实现 BeanFactory 与生命周期，回答'对象怎么建'；context 层叠加环境、事件、国际化，回答'应用怎么跑'；aop 层用代理织入横切逻辑，回答'功能怎么扩展'。任何一个问题都可以落到这四个层面之一。"

| 面试问题 | 落到哪层 | 示例 |
|---------|---------|------|
| "@Autowired 怎么解析的？" | Beans（用 core 的 ResolvableType） | 注入点 → 类型匹配 → 候选裁决 |
| "配置怎么加载的？" | Context（用 core 的 Resource） | 多来源 → 优先级合并 |
| "注解事务怎么生效的？" | AOP（core 的注解 + beans 的代理） | 切面 → 通知 → 事务管理器 |
| "字符串怎么转对象的？" | Core | ConversionService 链路 |

> 💡 **叙事心法**：答任何 Spring 机制题都用"**core 提供 X → beans/context 消费 X → 业务无感**"句式收尾——既展示体系感，又顺带把能力归属讲清楚，这是面试官最想听到的"地图式回答"。

| 系列 | 篇数 | 一句话 |
|------|:---:|--------|
| [Spring‑Core](../Spring‑Core/00-Spring Core组件总览.md) | 9 | 一切模块的地基能力库 |
| [Spring‑Beans](../Spring‑Beans/00-Spring Beans组件总览.md) | 8 | Bean 定义、工厂与生命周期 |
| [Spring‑Context](../Spring‑Context/00-Spring Context组件总览.md) | 8 | 企业级容器与上下文服务 |
| [Spring‑AOP](../Spring‑AOP/00-Spring AOP组件总览.md) | 5 | 声明式横切织入 |

**四系列的"能力-时机-位置"对照**（理解分工的一句话版）：

| 系列 | 管什么 | 何时运行 | 典型类 |
|------|--------|---------|--------|
| Core | 能力（怎么算/怎么转/怎么读） | 被调用时 | StringUtils/ResolvableType/Resource |
| Beans | 对象（怎么建/怎么注入/怎么销毁） | 容器 refresh | BeanFactory/BeanDefinition |
| Context | 环境（容器/事件/国际化/配置） | 应用生命周期 | ApplicationContext/Environment |
| AOP | 横切（切点/通知/代理） | 方法调用时 | ProxyFactory/Advisor |

> 💡 **学习路线对照**：Core 提供"零件"，Beans 提供"工厂"，Context 提供"整机"（企业级容器），AOP 提供"改造车间"——面试讲容器体系按这个递进讲，从零件讲到整机，体现体系感；对应阅读路径见 [Spring Core-00-源码专题总览](../../../Spring Core/00-SpringCore专题总览.md)。

## 3. 高频问题与排查速查

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| 升级 7.0 后日志依赖异常 | spring-jcl 移除、commons-logging 1.3 变化 | 移除显式 spring-jcl 坐标；检查传递冲突（[01-模块清单](01-模块清单.md)） |
| `ListenableFuture` 编译错误（7.0） | 已移除 | 改 `CompletableFuture`（`CompletableFuture.completedFuture` 等） |
| @Value("#{...}") 表达式不生效 | SpEL 语法/上下文错误 | 解析错误信息定位；模板表达式用 `#{}` 而非 `${}` |
| SpEL 求值抛"操作数超限"（7.0.8+） | 单次 >10,000 操作 | 合法场景调大 `spring.expression.maxOperations`（[06-SpEL 表达式速查](06-SpEL表达式速查.md)） |
| 泛型注入匹配错乱 | 泛型信息在运行时丢失 | 用 `ResolvableType.forField` 验证；确认注入点字段/参数带泛型声明 |
| 类型转换失败 ConversionFailedException | 无匹配 Converter 或条件不满足 | `canConvert` 检查；注册自定义 Converter（[04-类型系统与类型转换速查](04-类型系统与类型转换速查.md)） |
| jar 内 getFile() 抛 IOException | 类路径资源非文件 | 一律 `getInputStream()`（[05-资源抽象速查](05-资源抽象速查.md)） |
| classpath* 只加载一个文件 | 用成 classpath: | 多 jar 场景改 `classpath*:` |
| 重试不生效/自调用失效 | @Retryable 是代理注解 | 注入自身代理或拆类；确认 `@EnableResilientMethods` 已开启 |
| 旧 spring-retry 代码编译失败（7.0） | 包名/参数名变更 | `maxAttempts`→`maxRetries`；`org.springframework.core.retry`（[07-重试与弹性速查](07-重试与弹性速查.md)） |
| AOT 原生构建资源缺失 | 资源提示写旧正则 | 改 glob：`"/files/**/*.ext"`（`/*.ext` 不再匹配嵌套） |

> ⚠️ **排查三板斧**：① 编译失败先看"删除/移动"清单（spring-jcl、ListenableFuture、javax 注解）——7.0 破坏性变化集中在移除项；② 运行时问题先确认"能力归属"（core 只提供类，是否被正确装配由 context/beans 决定）；③ SpEL/转换类问题用最小表达式在测试中复现。

**高频问题补充**（第二梯队，按出现频率排序）：

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| 注解在接口上不生效 | 搜索策略不含接口层级 | MergedAnnotations 用 TYPE_HIERARCHY（[02](02-注解体系速查.md)） |
| @AliasFor 值冲突启动报错 | 同注解两属性别名值不一致 | 属性名对照检查（[02](02-注解体系速查.md) 第 2 节） |
| 自定义转换器对 @Value 不生效 | 注册到了 web 层而非 application 层 ConversionService | 确认注册入口（[04](04-类型系统与类型转换速查.md) 第 4 节） |
| 参数名注入失败 | 编译未开 `-parameters` | Maven 配 `<parameters>true</parameters>` |
| 资源每次启动加载慢 | classpath*: 大范围模式 | 精确前缀 + 缓存结果（[05](05-资源抽象速查.md) 第 4 节） |
| SpEL 表达式缓存无效果 | 每次 parseExpression | 缓存 Expression 实例（[06](06-SpEL表达式速查.md) 第 1 节） |
| 重试日志看不到 | 日志级别未开 | `org.springframework.core.retry` debug（[07](07-重试与弹性速查.md)） |
| AOT 构建报反射缺失 | 类型未注册反射提示 | 7.0 注册类型反射提示自动覆盖方法/构造器/字段 |

**排查定位四步法**（把上面的坑串成流程）：

```text
1. 定阶段：编译期 / 启动期 / 运行期（异常抛出位置即阶段）
2. 定归属：core 能力 / beans 装配 / context 时机（见第 1 节六条链路）
3. 定环节：值 / 类型 / 时机（值错查解析，类型错查转换，时机错查装配）
4. 定证据：开对应包 debug 日志 → 最小复现测试 → 对照本表
```
