## 1. Artifact 坐标与版本线

| 项 | 值 |
|----|----|
| GroupId | `org.springframework` |
| ArtifactId | `spring-web` |
| 最新版本 | 7.0.x（2026-08 时点，随 Framework 7.0 主线） |
| 维护线 | 7.0.x / 7.1.x（最新）、6.2.x（Boot 3.x） |
| Java 基线 | 17+；Servlet 6.x（Jakarta EE 11）可选支持 |
| 配套 | spring-webmvc（Servlet 栈）、spring-webflux（响应式栈） |

> 💡 纯 HTTP 客户端项目（不搭服务器）只依赖 spring-web（Boot 4 的 `spring-boot-starter-restclient`）；服务端项目由 `starter-web` / `starter-webflux` 传递引入。

### 1.1 版本演进简史

| 版本 | 时间 | 关键变化 |
|------|------|---------|
| 4.x | 2013-2018 | http/converter/client 基本成型；RestTemplate 为主 |
| 5.0 | 2017 | 引入响应式（codec 包、WebClient 雏形） |
| 5.3 | 2020 | WebClient 稳定为推荐 |
| 6.0 | 2022 | Jakarta EE 9 命名空间切换（javax → jakarta） |
| 6.1 | 2023 | RestClient 正式推出（同步客户端现代化） |
| 6.2 | 2023 | RestClient 完善；HttpServiceProxyFactory 增强 |
| 7.0 | 2025-11 | 转换器改名、HttpMessageConverters、ApiVersionInserter、RestTemplate 弃用 |
| 7.1 | 2026-05 | PreFlightRequestFilter、HttpHeaders 互操作修复 |

> 💡 演进主线：**客户端从"模板类"走向"声明式"**（RestTemplate → RestClient → @HttpExchange 接口）——面试讲"Spring HTTP 客户端演进"按这条线讲最有体系。

### 1.2 版本确认与获取

| 方式 | 命令/位置 | 说明 |
|------|----------|------|
| 查看当前版本 | `mvn dependency:tree -Dincludes=org.springframework` | 实际生效版本 |
| 查看最新发布 | [Spring 官网 Releases](https://spring.io/projects/spring-framework#support) | 版本线对照 |
| 版本管理 | Boot BOM 统一管理 | 项目内勿手工覆盖 Framework 版本 |
| 仓库 | Maven Central（GA）、repo.spring.io（里程碑/快照） | 正式项目只用 Central |

> ⚠️ 生产项目禁用里程碑/快照版本（`-M`、`-SNAPSHOT`）——除非在评估新特性；依赖锁定用 `mvn versions:lock-snapshots` 或 Boot BOM 的版本属性。

| 包 | 高频类 | 一句话职责 |

### 2.2 包结构演进（6.x → 7.x）

| 位置 | 6.x | 7.x | 变化 |
|------|-----|-----|------|
| converter 包 | `MappingJackson2HttpMessageConverter` | `JacksonJsonHttpMessageConverter` | 改名（Jackson 2 → 3 命名） |
| client 包 | RestTemplate 为主 | RestClient 主推 + `HttpMessageConverters` | 新增统一配置 API |
| client 包 | 无版本注入 | `ApiVersionInserter` 族 | 新增 |

## 3. 双栈架构：Servlet 与响应式

```text
spring-web 之上两条技术栈（共用 HTTP 模型/转换器/客户端）：
  Servlet 栈（阻塞）                     响应式栈（非阻塞）
  spring-webmvc                         spring-webflux
  DispatcherServlet                     DispatcherHandler
  @Controller + Tomcat/Jetty             @Controller + Netty/Undertow
  虚拟线程（7.x/Boot 4 默认）              Reactor 全链路
  spring-boot-starter-web               spring-boot-starter-webflux

  共同底座（都在 spring-web）：
  HttpMessage/Headers、HttpMessageConverter、MediaType、
  UriComponentsBuilder、CORS、多部分解析、WebApplicationContext
```

> 🎯 **核心要点**：MVC 与 WebFlux "共享模型、分栈执行"——HTTP 语义（消息/转换/客户端）在 spring-web 统一；面试答"MVC 与 WebFlux 的异同"先说**共同底座**再讲**执行模型**（线程模型 vs 事件循环）。

### 3.1 双栈执行模型对比（面试细节）

| 维度 | Servlet 栈（MVC） | 响应式栈（WebFlux） |
|------|------------------|--------------------|
| 入口 | DispatcherServlet（Servlet） | DispatcherHandler（Reactor 链路） |
| 线程模型 | 每请求一线程（7.x 虚拟线程） | 少量事件循环线程 + 工作线程 |
| 并发载体 | 虚拟线程（KB 级栈，JDK 21+） | Netty EventLoop（非阻塞 IO） |
| 背压 | 无（靠线程数上限） | Reactor 原生背压 |
| 数据源 | JDBC 阻塞直连 | 需响应式驱动（R2DBC） |
| 阻塞操作 | 允许（虚拟线程消化） | 禁止（会阻塞事件循环） |
| 依赖 | jakarta.servlet + Tomcat/Jetty | spring-webflux + Netty/Undertow |
| 适用 | 常规 Web 应用、团队同步栈 | 网关、流式、高扇出 |

**双栈混用注意**（同一应用两个 Dispatcher 共存时）：

| 事项 | 说明 |
|------|------|
| 路径隔离 | 两个 Dispatcher 各管各的路径映射（如 `/api/**` 走 MVC，`/stream/**` 走 WebFlux） |
| 过滤器链 | Servlet 过滤器对两栈都生效（都在 Servlet 容器内） |
| 事务/作用域 | 各容器独立——跨栈调用不共享 request 作用域 |
| 性能真相 | 混用不叠加收益——每栈按自己的模型跑，复杂度翻倍 |

> ⚠️ **选栈不是选代码风格**：WebFlux 的收益前提是"全链路响应式"（DB/Redis/第三方全换响应式客户端）——混用 JDBC 的 WebFlux 只会得到"更复杂的同步代码"；7.x 虚拟线程让 MVC 重新成为默认，WebFlux 是专长场景选项。

### 3.2 选型决策速查（按项目特征）

| 项目特征 | 推荐栈 | 理由 |
|----------|--------|------|
| 常规 CRUD + JDBC + 外部 REST 调用 | MVC + 虚拟线程 | 同步代码 + 高并发，成本最低 |
| 大并发网关/聚合层 | WebFlux | 连接复用、背压、流式聚合 |
| AI 流式输出（LLM token） | MVC + SSE（或 WebFlux） | 两者都支持；MVC 更易维护 |
| 团队无响应式经验 | MVC | 响应式排障成本高，勿为"时髦"引入 |
| 已有 WebFlux 存量 | 继续 WebFlux | 迁移 MVC 无收益，除非阻塞库成为瓶颈 |
| 混合阻塞库（JDBC + 流式） | MVC + 虚拟线程 + SSE | 伪响应式（JDBC 混 WebFlux）最差 |

> 🎯 决策一句话：**瓶颈在"线程数"→ 虚拟线程解决；瓶颈在"连接数与背压"→ 响应式解决**——先诊断瓶颈再选栈。

### 3.3 codec 包：响应式侧的秘密武器

```text
org.springframework.http.codec（7.0 命名）
├── Encoder/Decoder SPI（对应 converter，但面向 Flux/Mono）
├── JacksonJsonEncoder / JacksonJsonDecoder      ★ JSON（改名对齐）
├── JacksonCborEncoder / JacksonCborDecoder      ★ CBOR（7.0 默认装配）
├── ServerSentEventHttpMessageReader/Writer      ★ SSE 编解码
├── FormHttpMessageReader/Writer / Multipart 族   ★ 表单/多部分
└── StringEncoder/Decoder / ByteArray 族          ★ 基础类型
```

| 对比 | converter（同步侧） | codec（响应式侧） |
|------|--------------------|------------------|
| 服务对象 | HttpMessageConverter | Encoder/Decoder |
| 数据形态 | 对象 ↔ 字节 | Publisher 流 ↔ 字节 |
| 消费方 | RestClient/RestTemplate/MVC | WebClient/WebFlux |
| 配置 | `HttpMessageConverters`（7.0） | `CodecConfigurer`（早已统一） |

> 💡 7.0 的 `HttpMessageConverters` 配置 API 就是**对齐 codec 侧的 CodecConfigurer** 设计——两侧配置心智统一是 7.0 转换器重构的目标之一。

## 4. 依赖边界

| 依赖 | 方向 | 说明 |
|------|------|------|
| `spring-core` / `spring-beans` | 依赖 | 工具、ResolvableType（转换器泛型）、属性绑定 |
| `spring-context` | 可选 | WebApplicationContext 集成需要 |
| Servlet API（jakarta.servlet） | 可选（provided） | Servlet 栈时提供 |
| Reactor（io.projectreactor） | 可选 | codec/WebClient 需要 |
| Jackson / Gson / kotlinx-serialization | 可选 | 对应转换器才引入 |
| 反向依赖 | - | webmvc、webflux、security、Boot 全依赖 spring-web |

> 💡 spring-web 的"可选哲学"：**核心是纯协议层**——不强制 Servlet、不强制 Jackson、不强制 Reactor；缺什么引什么，缺了也能跑（只是对应能力不装配）。

### 4.1 依赖引入方式与冲突排查

| 场景 | 推荐依赖 | 说明 |
|------|---------|------|
| 纯客户端（无服务器） | `spring-boot-starter-restclient`（Boot 4） | 只带 spring-web + 客户端基础设施 |
| MVC 服务端 | `spring-boot-starter-web` | 传递引入 spring-web + webmvc |
| 响应式服务端 | `spring-boot-starter-webflux` | 传递引入 spring-web + webflux |
| 需要 JSON 转换 | 类路径探测自动装配 | 引 Jackson 3（`tools.jackson` 系列）即生效 |
| 需要 XML | Jackson XML 扩展或 JAXB | 对应转换器按类路径装配 |

**依赖冲突排查路径**（面试题"NoClassDefFoundError 怎么办"）：

```text
1. mvn dependency:tree 定位传递依赖来源
2. 同名不同版本 → 排除低版本（exclusions）或统一版本
3. Servlet API 冲突 → 确认只用 Jakarta 命名空间（javax.* 为旧版残留）
4. Jackson 大版本冲突 → 以 Boot BOM 为准（7.x 用 Jackson 3），勿混引 2.x
5. Reactor 版本冲突 → 以 Boot BOM 为准，勿单独覆盖
```

> ⚠️ **javax.* vs jakarta.* 是 7.x 时代最常见依赖坑**：Servlet 6.x / Jakarta EE 11 只认 `jakarta.servlet.*`；代码里出现 `javax.servlet` 说明引了旧 Servlet API（5.x 时代产物）——升级报 ClassNotFound 先查它。

### 4.2 反向依赖矩阵（谁在依赖 spring-web）

| 模块 | 依赖方式 | 用 spring-web 的什么 |
|------|---------|---------------------|
| spring-webmvc | 强依赖 | 转换器、WebApplicationContext、过滤器、消息模型 |
| spring-webflux | 强依赖 | 消息模型、codec、CORS 配置 |
| spring-websocket | 强依赖 | HttpHeaders/WebSocketHttpHeaders 互操作 |
| spring-security | 强依赖 | HttpMessage、过滤器链集成 |
| Spring Boot | 强依赖 | 自动配置的基础（starter-web 传递） |
| 第三方框架（如 MyBatis-Plus Web 支持） | 可选 | 转换器/工具类 |

> 🎯 **依赖方向的面试结论**：spring-web 是"被依赖方"——一切 Web 上层都建立在它之上；所以它的稳定性要求最高（协议语义不能随意变动，7.0 改名也因此需要官方专门说明）。

### 4.3 依赖瘦身实战：纯客户端最小集

```xml
<!-- 纯 HTTP 客户端服务（调度服务/批处理）最小依赖： -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-restclient</artifactId>   <!-- web + 客户端 -->
</dependency>
<!-- + 具体转换依赖（按需） -->
<dependency>
    <groupId>tools.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>                <!-- JSON 转换 -->
</dependency>
```

| 做法 | 效果 |
|------|------|
| 用 starter-restclient 而非 starter-web | 省掉 Tomcat、webmvc、模板引擎等 30+ 传递依赖 |
| 按需引转换库 | 不用 JSON 就不引 Jackson——减少 CVE 暴露面 |
| 关闭多余自动配置 | `spring.autoconfigure.exclude` 排除 web 相关配置 |
| 定期 dependency:analyze | 找出未使用/多余依赖 |

> 💡 **依赖瘦身的面试话术**：依赖即"攻击面 + 启动成本 + 升级成本"——纯客户端服务用 starter-restclient 是 Boot 4 的官方答案，面试提这一点显实操深度。

## 5. 版本兼容速查

| Spring Framework | Spring Boot | 备注 |
|------------------|-------------|------|
| 7.0.x（2025-11 起） | Boot 4.0.x | 当前主线；HttpMessageConverters/JacksonJson 改名/RestClient 主推 |
| 7.1.x（2026-05 起） | Boot 4.1.x | 最新维护线；PreFlightRequestFilter；RestTemplate 标记 @Deprecated 计划 |
| 6.2.x | Boot 3.4/3.5 | 存量主流；RestClient 可用（6.1+）但无 HttpMessageConverters API |

### 5.1 面试追问与生产实践

| 追问 | 回答要点 |
|------|---------|
| spring-web 与 spring-webmvc 什么关系 | web 是协议/传输底座；webmvc 是控制器层，依赖 web |
| 为什么 spring-web 不强制依赖 Jackson | 可选哲学——核心纯协议层，转换器按类路径探测 |
| Servlet API 为什么是 provided | 容器（Tomcat）自带实现，应用只需编译期 API |
| WebFlux 能复用 MVC 的代码吗 | 控制器注解通用；依赖 Servlet API 的代码（部分 RequestContextHolder API）不可用 |
| 双 Dispatcher 共存注意什么 | 路径映射隔离；过滤器链共享；作用域/事务各按容器管理 |
| 纯客户端项目引了 starter-web 会怎样 | 白带 Tomcat 与 webmvc——用 starter-restclient 瘦身 |
| spring-web 与 spring-core 什么关系 | core 提供 ResolvableType/工具等能力；web 在其上实现 HTTP 语义 |
| 为什么 Boot 能"缺什么引什么" | 转换器/编解码器按类路径探测（ClassUtils.isPresent）——可选哲学的实现机制 |

**生产实践三注意**：

| 实践 | 要点 |
|------|------|
| 模块边界 | 业务代码只依赖接口包（`http.client` 等），不依赖 Servlet API（保持可测试性） |
| 版本管理 | 用 Boot BOM（Boot 4 → Framework 7.x），不手工指定 Framework 版本 |
| 依赖瘦身 | 纯客户端项目别引 starter-web——会带上 Tomcat 与 webmvc 全家桶 |

### 5.2 版本兼容对照与迁移检查清单

| 检查项 | 6.x 现状 | 7.x 目标 | 优先级 |
|--------|---------|---------|--------|
| 转换器类名 | MappingJackson2 等旧名 | 新名（编译错误直接暴露） | P0（必改） |
| 转换器配置 | extendMessageConverters | configureMessageConverters | P0（必改） |
| 客户端 | RestTemplate 存量 | 新代码 RestClient | P1（渐进） |
| 编码器 | Jackson2Encoder 等 | JacksonJsonEncoder 等 | P0（必改） |
| CORS | CorsFilter | + PreFlightRequestFilter（可选） | P2（可选） |

**模块加载与调试技巧**：

| 技巧 | 命令/方式 |
|------|----------|
| 看实际加载的类 | `mvn dependency:tree -Dincludes=org.springframework:spring-web` |
| 确认转换器装配 | 启动日志 `MappingJackson2HttpMessageConverter` → 搜新类名 |
| 看自动配置来源 | `--debug` 启动打印 Auto-configuration Report |
| 检查 ClassLoader 冲突 | `jar tf` 定位重复类（同名两个 jar） |

> 🎯 **本模块一句话**：spring-web 的包结构 = "协议（http）+ 容器（web）+ 工具（util）"三段——升级 7.x 的实质是"类名与配置 API 的迁移"，包结构骨架没变。

### 5.3 生产常见错误速查

| 报错 | 根因 | 解法 |
|------|------|------|
| `NoClassDefFoundError: jakarta/servlet/...` | 引了旧 javax Servlet API | 换 jakarta 坐标，排查传递依赖 |
| `ClassCastException: ...Jackson2...` | 新旧转换器类混引 | 统一到 7.0 新类名 |
| 启动报转换器重复 | 自定义 @Bean 与 Boot 自动装配重复 | 走 `configureMessageConverters` 统一管理 |
| WebFlux 与 MVC 类冲突 | 两栈 starter 同时引入 | 按需去掉一个 starter |
| 404 且无日志 | DispatcherServlet 路径未匹配 | 检查 servlet 映射路径与 @RequestMapping 前缀 |
| 转换器未装配但依赖已引 | 类路径探测失败（依赖 scope 错误） | 检查 runtime scope 与 optional 依赖 |
| `ClassNotFoundError: jakarta.annotation` | Jakarta 注解库缺失 | 补 `jakarta.annotation-api` 依赖 |

> ⚠️ **双 starter 警告**：`spring-boot-starter-web` 与 `spring-boot-starter-webflux` 同时存在时 Boot 会告警（MVC 优先）——同时用两栈的代价是依赖冗余与配置歧义，除非明确双 Dispatcher 需求，否则别共存。

### 5.4 一分钟记忆卡

```text
坐标：org.springframework:spring-web（7.x 主线，Java 17+）
三句话：
  1. HTTP 语义模型 + 转换器 + 客户端都在 http 包
  2. Web 容器/作用域/过滤器在 web 包
  3. Servlet 与响应式双栈共用底座，分栈执行

升级 7.x 三件事：改类名（JacksonJson）、改配置 API（HttpMessageConverters）、
新代码用 RestClient（RestTemplate 弃用）
```

> 🎯 一句话总结：**spring-web 是 Spring 的"HTTP 语言"**——http 包说协议，web 包说容器，util 包说工具；理解三段包结构，就理解了 MVC/WebFlux/Security 一切 Web 组件的公共底座。
