## 1. 与其他模块的集成地图

```text
                  spring-web（HTTP 基础设施）
        ┌──────────┬──────────┬──────────┬──────────┐
        ↓          ↓          ↓          ↓          ↓
  spring-core  spring-beans  spring-context spring-webmvc  Spring Boot
  Resolvable   转换器/客户端   Web 上下文    控制器层       starter-web
  Type 泛型     作为 Bean     父子容器       （建立在     Web 自动配置
  转换器 SPI    装配          request 作用域  web 之上）
```

| 联动点 | 机制 | 说明 |
|--------|------|------|
| web ↔ core | `ResolvableType` 泛型 + `ConversionService` | 转换器泛型解析、参数类型转换 |
| web ↔ context | `WebApplicationContext` 继承 ApplicationContext | 根/子父子容器（[05-Web 上下文与作用域速查](05-Web上下文与作用域速查.md)） |
| web ↔ beans | 转换器/客户端/RestClient 都是普通 Bean | Boot 自动装配注入 |
| web ↔ webmvc | MVC 的一切建立在 spring-web 之上 | DispatcherServlet 消费 HandlerMapping 等（MVC 系列） |
| web ↔ webflux | 共用 HTTP 模型 + codec | 响应式栈的编解码器在 spring-web（[07-异步与流式速查](07-异步与流式速查.md)） |
| web ↔ security | FilterChainProxy 在过滤器链中 | CORS/认证过滤器协作（[06-过滤链与 CORS 速查](06-过滤链与CORS速查.md)） |
| web ↔ Boot | 内嵌 Tomcat/Netty + 自动配置 | `spring-boot-starter-web` 全自动（Boot 系列） |

> 🎯 **核心要点**：spring-web 是"协议与传输层"——**上不碰控制器（webmvc）、下不碰容器（context）**，却在两者之间提供全部 HTTP 语义；答"一次 HTTP 请求经过谁"时按 Filter 链 → DispatcherServlet → HandlerMapping → 控制器 → 转换器 讲，前两层就在 spring-web。

### 1.1 与更多模块的联动细节

| 模块 | 联动机制 | 典型场景 |
|------|---------|---------|
| spring-jdbc | JdbcClient 与 RestClient 同为"模板族" | 服务端查询 → 响应转换，同构代码 |
| spring-tx | 事务代理与请求生命周期 | 请求内事务边界（[Spring-TX 系列](../Spring‑TX（Spring‑Transaction）/00-Spring TX组件总览.md)） |
| spring-aop | 拦截器/代理与转换器共存 | 日志/审计横切 |
| spring-security | FilterChainProxy + SecurityContextHolder | 认证信息跨层传递 |
| spring-session | SessionRepository 替换 HttpSession | 分布式会话（Redis） |
| spring-validation | @Valid 校验注解 | 请求体校验（[SpringMVC-03](../../../SpringMVC/03-参数绑定与数据校验.md)） |
| spring-retry | 重试模板组合 RestClient | 幂等重试（[Spring-Core-07](../Spring‑Core/07-重试与弹性速查.md)） |
| spring-webflux | 共用 codec 包 | 响应式栈编解码 |

> 💡 **联动主线**：**认证（security）→ 请求绑定（web）→ 事务（tx）→ 数据（jdbc）→ 响应转换（web）**——一次请求的完整依赖链，每一环都是独立模块，这正是"模块化"的面试答案。

### 1.2 集成问题的分层排查路径

```text
按"症状所在层"定位（每层都有专属排查入口）：
  症状 → 层
  405/415/406         → 协议层（web：转换器/协商）
  404/路由不匹配      → 控制器层（webmvc：HandlerMapping）
  401/403             → 安全层（security：过滤器链）
  500 事务回滚        → 事务层（tx：传播/异常回滚）
  慢查询/连接池耗尽   → 数据层（jdbc：连接池/SQL）
  客户端超时/重试     → 传输层（web：请求工厂/拦截器）

  原则：先分层、再定位——别在业务代码里找协议问题
```

| 层 | 代表症状 | 排查入口 |
|----|---------|---------|
| 传输层 | 连接超时/池耗尽 | 请求工厂配置、连接监控 |
| 协议层 | 415/406/乱码/头缺失 | 转换器、过滤器链、头检查 |
| 安全层 | 401/403/预检被拦 | Security 日志（DEBUG） |
| 控制器层 | 404/参数绑定失败 | HandlerMapping 日志 |
| 事务层 | 部分成功/回滚异常 | 事务日志 + 传播行为检查 |
| 数据层 | 慢/锁/连接耗尽 | SQL 慢日志、连接池指标 |

> 🎯 **面试答排查题的结构**：先"分层定位"（哪一层）→ 再"机制解释"（为什么）→ 最后"解法验证"（怎么修）——三步结构比直接给答案得分高。

## 2. 底层核心六系列串联

```text
底层核心（Spring Framework 框架本体）六兄弟全景：
  Spring-Core     地基能力库（注解/工具/类型/SpEL/retry）          9 篇
  Spring-Beans    工厂容器（BeanFactory/生命周期/DI）              8 篇
  Spring-Context  企业容器（ApplicationContext/事件/国际化）        8 篇
  Spring-AOP      织入（切点/通知/代理）                           5 篇
  Spring-JDBC     数据访问模板（JdbcTemplate/JdbcClient/DataSource）8 篇
  Spring-TX       事务契约（@Transactional/传播/隔离）             8 篇
  Spring-Web      HTTP 基础设施（客户端/转换器/Web 上下文）         8 篇 ★ 本系列

  请求全景链路（面试串联）：
  Filter 链（web）→ DispatcherServlet → 事务代理（tx+aop）
  → 控制器 → JdbcClient（jdbc）→ 事务提交（tx）→ 响应转换（web）
  全程跑在 Context 容器里（context），能力来自 Core（core）
```

### 2.1 一次请求的组件清单（面试串联）

| 阶段 | 组件 | 归属模块 |
|------|------|---------|
| 1 连接接入 | Tomcat/Netty 协议处理器 | Boot 内嵌容器 |
| 2 过滤器链 | CharacterEncoding → Cors → Security | spring-web / security |
| 3 请求绑定 | RequestContextHolder（线程绑定） | spring-web |
| 4 路由 | DispatcherServlet → HandlerMapping | spring-webmvc |
| 5 参数绑定 | HandlerMethodArgumentResolver | spring-webmvc |
| 6 事务 | 事务代理切面（@Transactional） | spring-tx + spring-aop |
| 7 业务 | Service/Repository | 业务代码 |
| 8 数据 | JdbcClient / JPA | spring-jdbc 等 |
| 9 响应转换 | HttpMessageConverter（JSON） | spring-web |
| 10 响应写回 | HttpMessage → 容器输出流 | spring-web + 容器 |

> 🎯 **面试答"一次请求"的层次感**：协议层（web）→ 控制器层（webmvc）→ 业务层（beans/context）→ 数据层（jdbc/tx）——**每一层说出归属模块**，就是面试官要的"体系化"。

### 2.2 六系列学习地图（按面试优先级）

| 系列 | 面试权重 | 核心掌握点 |
|------|---------|-----------|
| Spring-Core | ★★★★★ | ResolvableType、类型转换、SpEL |
| Spring-Beans | ★★★★★ | BeanFactory、生命周期、循环依赖 |
| Spring-Context | ★★★★ | 事件、国际化、资源 |
| Spring-AOP | ★★★★ | 代理机制、事务切面原理 |
| Spring-JDBC | ★★★★ | JdbcClient、连接池、异常体系 |
| Spring-TX | ★★★★★ | 传播/隔离、回滚语义 |
| Spring-Web | ★★★★ | HTTP 客户端、转换器、上下文（本篇） |

```text
学习顺序建议：
  第一轮：Beans → Context → AOP（容器三件套）
  第二轮：Web（本篇）→ JDBC → TX（请求与数据）
  第三轮：Core 补细节（类型系统/SpEL）
  面试串联：一次请求 = Web（协议）→ AOP+TX（事务）→ JDBC（数据）
```

> 💡 面试官最爱"横向串联"：问 RestClient 会扯到拦截器（AOP 思想）、转换器（类型系统）、事务（链路）——**六系列要能互相引用**。

## 3. 高频问题与排查速查

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| 415 Unsupported Media Type | 请求 Content-Type 无转换器 | 检查 Content-Type 与转换器支持（[03-消息转换与内容协商速查](03-消息转换与内容协商速查.md)） |
| 406 Not Acceptable | 响应类型无转换器可写 | 检查 Accept 头与 produces 声明 |
| 乱码 | 编码过滤器缺失/连接器配置 | 确认 CharacterEncodingFilter + UTF-8（[06-过滤链与 CORS 速查](06-过滤链与CORS速查.md)） |
| CORS 报错 | 过滤器顺序/未配置 Security 侧 | OPTIONS 请求被拦 = Security 未放行（[06](06-过滤链与CORS速查.md) 第 5 节） |
| 客户端调用超时/连接耗尽 | 请求工厂无池/超时未配 | RestClient 配 `HttpComponentsClientHttpRequestFactory` + 超时/连接池 |
| RestClient 无响应体时读不到头 | 转换器链只在有 body 时触发 | 用 `.exchange()` 手动处理（[02-HTTP 客户端速查](02-HTTP客户端速查.md) 第 3 节） |
| @Async 线程里请求上下文为 null | ThreadLocal 不跨线程 | TaskDecorator 传递或显式传参（[05-Web 上下文与作用域速查](05-Web上下文与作用域速查.md)） |
| request/session Bean 拿到旧实例 | 缺作用域代理 | `proxyMode = TARGET_CLASS`（[05](05-Web上下文与作用域速查.md) 第 3 节） |
| 升级 7.0 后旧转换器类名编译失败 | Jackson2 命名替换 | 改 `JacksonJsonHttpMessageConverter`（[03](03-消息转换与内容协商速查.md) 第 2 节） |
| 虚拟线程下 ThreadLocal 暴涨 | 每虚拟线程一份 | 用请求作用域/显式传递替代 ThreadLocal |
| SSE 断连 | 无心跳/超时 | 配置心跳（`SseEmitter` timeout + 定时 ping） |

> ⚠️ **排查三板斧**：① 协议类问题（415/406/乱码/CORS）先看"头"（Content-Type/Accept/Origin）与过滤器链；② 客户端问题先看"请求工厂"（超时/池/代理）；③ 7.0 升级问题先看"改名清单"（转换器/客户端 API）。

### 3.1 更多高频坑（生产向）

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| 大 JSON 响应慢 | 未开压缩/对象整驻内存 | Gzip（`server.compression.enabled=true`）+ 流式解析 |
| 上传大文件 413 | 容器限制未调整 | `spring.servlet.multipart.max-file-size` + 连接器 maxPostSize |
| 响应头被代理改写 | 网关/反代配置 | 检查 Nginx/网关透传头配置 |
| HTTP/2 下客户端报错 | 请求工厂不支持 H2 | 换 H2 兼容请求工厂（HttpComponents 5.4+ 或 JDK HttpClient） |
| 故障后客户端不恢复 | JVM DNS 缓存（默认永久） | `networkaddress.cache.ttl` 调小 |
| 读超大响应 OOM | 无限制读入内存 | 流式读取（exchange 或 WebClient bodyToFlux） |
| 代理后拿不到真实 IP | 未解析 X-Forwarded-For | `server.forward-headers-strategy=framework` |
| 老 JDK 虚拟线程 pinning | synchronized 长临界区 | 升 JDK 24+（JEP 491）或缩短临界区 |
| 接口偶发超时但监控正常 | 线程池/连接池争抢 | 查线程转储 + 连接池等待指标 |
| 重启后首个请求极慢 | 懒加载/连接建立 | 预热（@PostConstruct 探测）或懒加载关闭 |
| 序列化性能瓶颈 | 反射/默认配置 | Jackson 启用后处理（records/构造函数）或改用流式 |

> ⚠️ **故障排查顺序建议**：现象 → 判断层次（协议/容器/业务）→ 看头（Content-Type/Accept/Origin）→ 看配置（超时/池/限制）→ 看日志（异常栈的类名能直接定位模块）。

### 4.2 面试追问深挖（源码级）

| 追问 | 深挖点 |
|------|--------|
| 转换器匹配的完整链路是什么 | `AbstractMessageConverterMethodProcessor` 遍历转换器 → `canWrite` → `write`；泛型走 `GenericHttpMessageConverter` 的 ResolvableType 分支 |
| RestClient 的请求工厂有哪些实现 | `JdkClientHttpRequestFactory`（JDK 11+）/ `HttpComponentsClientHttpRequestFactory`（Apache）/ `SimpleClientHttpRequestFactory`（默认兜底） |
| 虚拟线程在 Tomcat 里怎么生效 | Tomcat 协议处理器换 `VirtualThreadExecutor`——请求处理线程池变虚拟线程（Boot 4 自动） |
| CORS 预检为什么必须用过滤器 | OPTIONS 请求也要过过滤链——拦截器在 DispatcherServlet 之后，预检未映射控制器时到不了 |
| request 作用域的注册机制 | `RequestScope` 在容器启动时注册（`registerScope`）——作用域失效报错即未注册 |
| 7.0 转换器配置如何对齐响应式 | `HttpMessageConverters` 对标 `CodecConfigurer`——两侧 API 结构（默认/替换/追加）一致 |

| 高级考点 | 一句话答案 |
|----------|-----------|
| HttpMessageConverters 与 Boot 自动配置的关系 | 7.0 框架级 API 取代 Boot 类型；Boot 自动配置转为调用框架 API |
| 为什么要先 registerDefaults 再替换 | 替换是"同媒体类型换实现"，依赖默认基线——顺序反了覆盖失效 |
| RestClient 无内建重试怎么办 | 拦截器/RetryTemplate 组合；幂等键设计比重试更重要 |
| SseEmitter 与 ResponseBodyEmitter 什么关系 | SseEmitter 继承 ResponseBodyEmitter——SSE 是"带格式的流式响应" |
| WebAsyncManager 在 7.x 还是核心吗 | 是——SseEmitter/DeferredResult 底层仍是它；虚拟线程改变了"要不要用"，没改变"机制" |
| 客户端测试用 RestTestClient 还是 MockRestServiceServer | 新代码用 RestTestClient（7.0 统一 API）；旧 mock 库维护存量即可 |
| 升级 7.0 后还能用 Jackson 2 吗 | 能——显式依赖 Jackson 2 并装配旧转换器；但 Boot 4 默认 Jackson 3，混用需自控 |
| 内容协商与版本化怎么共存 | ApiVersionInserter 注入版本，协商管格式——两个正交维度，可叠加使用 |

> 💡 **面试收尾话术**：把 spring-web 讲成"HTTP 协议的对象化层"——模型（HttpMessage）、转换（converter）、传输（client）、容器（context）、并发（virtual threads）五块能力，任何 Web 框架问题都能落到这五块之一。
