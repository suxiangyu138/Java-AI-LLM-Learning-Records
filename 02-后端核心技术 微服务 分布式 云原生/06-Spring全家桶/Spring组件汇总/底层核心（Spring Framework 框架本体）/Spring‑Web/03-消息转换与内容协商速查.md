## 1. HttpMessageConverter 架构

```java
public interface HttpMessageConverter<T> {
    boolean canRead(Class<?> clazz, MediaType mediaType);   // 能否读（类型 + 媒体类型）
    boolean canWrite(Class<?> clazz, MediaType mediaType);
    T read(Class<? extends T> clazz, HttpInputMessage input);
    void write(T t, MediaType contentType, HttpOutputMessage output);
}

// 泛型感知版（7.x 默认用）：支持 List<T>/DTO 泛型
public interface GenericHttpMessageConverter<T> extends HttpMessageConverter<T> {
    boolean canRead(ResolvableType type, MediaType mediaType);   // ResolvableType
    T read(ResolvableType type, HttpInputMessage input);
}
```

```text
转换链（服务端/客户端通用）：
  Java 对象 →（GenericHttpMessageConverter 匹配）→ 序列化为字节
  ← MediaType 匹配（application/json、text/plain...）
  ← 泛型解析（ResolvableType：List<Order> 也能对）
```

> 🎯 **核心要点**：转换器 = **类型 + 媒体类型**双匹配——对象能否转换取决于 `canRead/canWrite`；泛型支持（Generic 版）是 7.x 标准，`List<Order>` 不再丢失类型信息（底层 ResolvableType，见 [Spring-Core-04](../Spring‑Core/04-类型系统与类型转换速查.md)）。

### 1.1 转换器匹配链与装配顺序

```text
服务端写回（响应序列化）的匹配过程：
  1. 确定目标媒体类型（produces / Accept 协商结果）
  2. 按注册顺序遍历转换器，找第一个 canWrite(类型, 媒体类型) 为 true 的
  3. 泛型场景先走 GenericHttpMessageConverter.canWrite(ResolvableType,...)
  4. 命中后调用 write(...)；全部未命中 → 406 Not Acceptable

客户端读取（响应反序列化）对称：
  1. 按响应 Content-Type 找 canRead 的转换器
  2. 目标类型带泛型（List<Order>）时走 ResolvableType 分支
  3. 未命中 → 抛 HttpMessageNotReadableException
```

**Boot 4 默认装配顺序（前先后后，MVC 侧；XML/CBOR 等视依赖而定）**：

| 顺序 | 转换器 | 媒体类型 |
|------|--------|---------|
| 1 | `ByteArrayHttpMessageConverter` | `application/octet-stream` |
| 2 | `StringHttpMessageConverter` | `text/*` |
| 3 | `ResourceHttpMessageConverter` | `*/*`（资源） |
| 4 | `JacksonJsonHttpMessageConverter` | `application/json` |
| 5 | `JacksonCborHttpMessageConverter` | `application/cbor`（7.0 默认装配） |
| 6 | `JacksonXmlHttpMessageConverter` | `application/xml`（有 Jackson XML 依赖时） |
| 7 | `FormHttpMessageConverter` | `application/x-www-form-urlencoded` |
| 8 | `MultipartHttpMessageConverter` | `multipart/form-data` |

> ⚠️ **顺序即优先级**：`StringHttpMessageConverter` 在 JSON 之前——若某响应 Content-Type 同时命中多个转换器，先注册的赢；自定义转换器用 `addCustomConverter` 追加在末尾，或直接替换对应媒体类型转换器；**不要想当然"我注册了就是我的"**。

**客户端与服务端的差异**（面试细节）：

| 维度 | 服务端（MVC） | 客户端（RestClient） |
|------|--------------|---------------------|
| 读方向 | 按 Content-Type 绑定 @RequestBody | 按响应 Content-Type 反序列化 |
| 写方向 | 按 Accept + produces 协商 | 按你设置的 contentType |
| 默认顺序 | Boot 自动装配（上表） | 同款但略简（无 MVC 专属转换器） |
| 错误 | 415/406 走异常处理器 | HttpMessageNotReadableException / RestClientResponseException |

## 2. 转换器全家（7.0 命名）

| 转换器（7.0 名称） | 媒体类型 | 依赖 | 说明 |
|-------------------|---------|------|------|
| `JacksonJsonHttpMessageConverter` | `application/json` | Jackson 3（`jackson-core/json`） | ★ 取代旧 Jackson2 命名；可注入 JsonMapper |
| `JacksonXmlHttpMessageConverter` | `application/xml` | Jackson XML 扩展 | 独立于 JSON 配置 |
| `JacksonCborHttpMessageConverter` | `application/cbor` | Jackson CBOR | 7.0 起默认装配（CBOR 二进制） |
| `StringHttpMessageConverter` | `text/*` | 无 | 默认 UTF-8（`setDefaultCharset`） |
| `ByteArrayHttpMessageConverter` | `application/octet-stream` | 无 | 字节直传 |
| `FormHttpMessageConverter` | `application/x-www-form-urlencoded` | 无 | MultiValueMap 表单 |
| `MultipartHttpMessageConverter` | `multipart/form-data` | 无 | 文件上传 |
| `GsonHttpMessageConverter` / `JsonbHttpMessageConverter` | `application/json` | Gson / JSON-B | 替代 Jackson 时 |
| `MarshallingHttpMessageConverter` | `application/xml` | JAXB 等 | 旧式 XML |
| `KotlinSerializationJsonHttpMessageConverter` | `application/json` | kotlinx-serialization | **7.0：仅编解码 @Serializable 类型**（可 Predicate 定制） |
| `SourceHttpMessageConverter` / `ResourceHttpMessageConverter` | `application/xml` / 资源 | 无 | 特殊类型 |

> ⚠️ **升级注意**：旧类名 `MappingJackson2HttpMessageConverter` / `Jackson2ObjectMapperBuilder`（6.x）在 7.0 已被新类取代——代码引用旧类需改名迁移；Boot 4 默认装配**新命名转换器**。

### 2.1 转换器选型与依赖关系

| 场景 | 推荐 | 不推荐 |
|------|------|--------|
| 默认 JSON | `JacksonJsonHttpMessageConverter`（Jackson 3） | Gson（生态与性能弱于 Jackson 3） |
| 大型 JSON 文档 | Jackson 流式 API（JsonParser） | 对象绑定（整驻内存） |
| XML | JacksonXml 或 JAXB | 手写解析 |
| 二进制紧凑协议 | `JacksonCborHttpMessageConverter`（7.0 默认装配） | 自定义二进制 |
| Kotlin 服务端 | KotlinSerializationJson（仅 @Serializable） | 对非 @Serializable 类型无效 |
| 只传字符串/字节 | String/ByteArray（内建，零依赖） | 引 JSON 库（没必要） |

**Jackson 3 与 Jackson 2 的差异**（7.0 迁移重点）：

| 维度 | Jackson 2（6.x） | Jackson 3（7.x） |
|------|-----------------|-----------------|
| 依赖坐标 | `com.fasterxml.jackson.core:*` | `tools.jackson.core:*` |
| ObjectMapper | `com.fasterxml.jackson.databind.ObjectMapper` | `tools.jackson.databind.JsonMapper` |
| 注解包 | `com.fasterxml.jackson.annotation.*` | `tools.jackson.annotation.*` |
| 转换器类 | `MappingJackson2HttpMessageConverter` | `JacksonJsonHttpMessageConverter` |
| 兼容 | 6.x 默认 | Boot 4 默认（7.0 支持双版本共存配置） |

> ⚠️ **7.0 升级最常见的编译错误**：代码 import 的是 Jackson 2 的 `ObjectMapper`/注解——Boot 4 传递的是 Jackson 3；要么改包名到 `tools.jackson`，要么继续显式依赖 Jackson 2 并自行装配旧转换器（不推荐，双重维护）。

### 2.2 转换器的性能与安全

| 关注点 | 说明 | 实践 |
|--------|------|------|
| 大 JSON 整驻内存 | 对象绑定一次性读入 | 大文档用流式 API 或分页接口 |
| 深度嵌套/循环引用 | 序列化死循环或栈溢出 | Jackson 配置 `@JsonIdentityInfo` / 忽略循环字段 |
| 反序列化攻击 | 多态类型注入（`@class` 字段） | 默认禁用多态；`setDefaultTyping` 谨慎使用 |
| 字符串大小无上限 | 恶意超大 body 拖垮内存 | 容器/网关限制 body 大小（`server.tomcat.max-http-form-post-size` 等） |
| 敏感字段泄露 | DTO 直接暴露内部字段 | 响应用独立 DTO（@JsonIgnore 兜底） |
| 日期格式不一致 | 时区/格式错乱 | 统一 `JsonMapper` 配置（ISO-8601 + UTC） |
| 未知字段报错 | 服务端新增字段客户端崩溃 | 关闭 FAIL_ON_UNKNOWN_PROPERTIES（前向兼容） |
| 空值字段冗余 | 响应体膨胀 | 按场景配置 NON_NULL 序列化（注意契约一致性） |

```java
// 安全基线配置示例（JsonMapper）
JsonMapper mapper = JsonMapper.builder()
        .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
        .disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)  // 前向兼容
        .build();
```

> ⚠️ **多态反序列化是最高危点**：`@JsonTypeInfo` 让 JSON 携带类名——一旦接口可被外部调用者控制，就是反序列化攻击面；生产默认不开，开了也要白名单校验。

## 3. HttpMessageConverters：7.0 统一配置 API

```java
// 服务端（MVC）：WebMvcConfigurer（7.0 同款 API）
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void configureMessageConverters(HttpMessageConverters converters) {
        converters.registerDefaults()                                   // 保留默认
                .jsonMessageConverter(new JacksonJsonHttpMessageConverter(
                        customMapper()));                               // 替换 JSON
        // converters.addCustomConverter(new MyConverter());             // 追加
    }
}

// 客户端（RestClient / RestTemplate）
RestClient client = RestClient.builder()
        .configureMessageConverters(c -> c
                .registerDefaults()
                .xmlMessageConverter(new JacksonXmlHttpMessageConverter(xmlMapper)))
        .build();
```

| 方法 | 语义 |
|------|------|
| `registerDefaults()` | 注册类路径探测到的默认转换器（框架自动检测） |
| `jsonMessageConverter(...)` / `xmlMessageConverter(...)` | 替换对应媒体类型转换器 |
| `addCustomConverter(...)` | 追加自定义转换器 |
| 目的 | 取代 Boot 自身 `HttpMessageConverters` 类型，框架级统一 |

> 🎯 **核心要点**：7.0 把转换器配置从"Boot 专属"升级为"框架级 API"（对齐响应式侧 CodecConfigurer）——**服务端与客户端用同一套配置心智**；配置覆盖默认转换器时注意顺序（先 registerDefaults 再替换）。

### 3.1 配置覆盖的顺序与陷阱

| 操作 | 效果 | 陷阱 |
|------|------|------|
| `registerDefaults()` | 注册类路径探测到的默认转换器 | 漏调则默认转换器全无——新配置从零开始 |
| `jsonMessageConverter(...)` | 替换 JSON 转换器 | 参数是转换器实例——`JsonMapper` 需自己构造 |
| `addCustomConverter(...)` | 追加到末尾 | 与默认转换器撞车时匹配优先级低 |
| 不调 registerDefaults 直接 add | 只保留自定义 | 可能丢掉 String/ByteArray 等基础转换能力 |

```java
// 完整姿势：保留默认 → 替换 JSON → 追加自定义
RestClient client = RestClient.builder()
        .configureMessageConverters(c -> c
                .registerDefaults()                                     // 1 先默认
                .jsonMessageConverter(new JacksonJsonHttpMessageConverter(
                        JsonMapper.builder().build()))                  // 2 再替换
                .addCustomConverter(new CsvHttpMessageConverter()))     // 3 最后追加
        .build();
```

> ⚠️ **两步式记忆**：先 `registerDefaults` 建立基线，再逐类替换——顺序反了（先替换后默认）会导致你的替换被默认覆盖；替换是"同媒体类型换实现"，追加是"加媒体类型"。

### 3.2 registerDefaults 的探测机制

```text
registerDefaults() 内部做的事（类路径探测）：
  1. String/ByteArray/Resource —— 永远注册（零依赖）
  2. Jackson 3 在类路径？ → 注册 JacksonJsonHttpMessageConverter
  3. Jackson CBOR 扩展在？ → 注册 JacksonCborHttpMessageConverter
  4. Jackson XML 扩展在？   → 注册 JacksonXmlHttpMessageConverter
  5. kotlinx-serialization 在？ → 注册 KotlinSerializationJson（仅 @Serializable）
  6. Gson/JSON-B/JAXB 在？   → 对应转换器（旧栈兼容）
  探测工具：ClassUtils.isPresent —— 与 Boot 自动配置同机制
```

| 特性 | 说明 |
|------|------|
| 探测时机 | 配置生效时（启动期） |
| 缺失依赖的表现 | 静默跳过——不报错，只是该媒体类型不可用 |
| 与 Boot 自动配置关系 | 7.0 起框架级 API 接管；Boot 自身类型逐步退场 |
| 自定义优先级 | 显式注册（jsonMessageConverter 等）> 探测默认 |

> 💡 面试问"缺了 Jackson 会怎样"——答：**不会启动失败**，只是 JSON 能力不装配（415/406 报错）；这正是 spring-web 可选哲学的运行时体现。

**配置 API 与 6.x 写法对照**：

| 6.x 写法 | 7.x 写法 |
|----------|---------|
| `extendMessageConverters(List<HttpMessageConverter<?>>)` | `configureMessageConverters(HttpMessageConverters)` |
| Boot 的 `HttpMessageConverters` Bean 操作 | 框架级 `HttpMessageConverters` 参数 |
| 手动 `new MappingJackson2HttpMessageConverter(mapper)` | `new JacksonJsonHttpMessageConverter(JsonMapper)` |
| `Jackson2ObjectMapperBuilder` | `JsonMapper.builder()`（Jackson 3） |

## 4. 内容协商：Accept 与 produces

```text
服务端响应内容协商流程（MVC）：
  1. 控制器方法标注 produces = "application/json"
  2. 请求 Accept 头：application/json;q=0.9, application/xml;q=0.5
  3. 按 q 值排序 + produces 交集 → 选最高优先级媒体类型
  4. 找不到可匹配转换器 → 406 Not Acceptable
```

| 位置 | 机制 | 说明 |
|------|------|------|
| 服务端方法 | `@GetMapping(produces = "...")` | 限定响应媒体类型 |
| 服务端方法 | `@GetMapping(consumes = "...")` | 限定请求媒体类型（415 兜底） |
| 客户端 | `.accept(MediaType.APPLICATION_JSON)` | RestClient/WebClient 声明期望 |
| 客户端 | `Content-Type` | 请求体格式（转换器选择依据） |
| 优先级 | q 值协商（HTTP 标准） | `Accept: application/json;q=1, text/*;q=0.5` |

> ⚠️ **高频 415/406**：`415 Unsupported Media Type` = 请求 Content-Type 无转换器可读（如传了 text/plain 想绑定 JSON 对象）；`406 Not Acceptable` = 响应类型无转换器可写——排查先看两端媒体类型声明。

### 4.1 协商细节与排查流程

**q 值协商完整规则**：

```text
Accept: application/json;q=0.9, application/xml;q=0.5, text/*;q=0.1
1. 按 q 值降序（缺省 q=1）
2. 与控制器 produces 求交集
3. 交集内按"特异度"排序（application/json 优于 application/*）
4. 同分 → 先注册的转换器胜出
5. 空交集 → 406
```

**406/415 排查流程图**：

```text
响应 406？ ──否──► 正常
  │是
  ├─ Accept 与 produces 有交集吗？ ──无──► 改 produces 或 Accept
  ├─ 目标类型有 canWrite 的转换器吗？ ──无──► 装配对应转换器（如 XML 依赖）
  └─ 顺序对吗？ ──错──► 检查装配顺序（见 1.1）

请求 415？ ──否──► 正常
  ├─ Content-Type 与 consumes 匹配吗？ ──无──► 加 consumes 或改 Content-Type
  ├─ 目标类型有 canRead 的转换器吗？ ──无──► 引依赖（如缺 Jackson）
  └─ 媒体类型拼写对吗？ ──错──► 检查 charset/参数（如 application/json;charset=UTF-8）
```

> 💡 **调试技巧**：`curl -i -H "Accept: application/xml" URL` 直测服务端协商；客户端问题用 `-H "Content-Type: text/plain"` 复现 415——先定位是"服务端没有"还是"客户端声明错"。

### 4.2 服务端协商的进阶策略

| 策略 | 机制 | 注意 |
|------|------|------|
| produces 限定 | 方法级声明响应类型 | 与 Accept 求交集 |
| consumes 限定 | 方法级声明请求类型 | 不匹配直接 415（比转换器更早） |
| 文件后缀（`.json`/`.xml`） | 路径后缀参与协商 | 已弱化（7.x 默认关闭后缀协商） |
| 请求参数（`?format=json`） | 参数参与协商 | 调试方便，生产慎开 |
| Header 优先 | Accept 头 > 后缀 > 参数 | 默认策略链 |
| 固定媒体类型 | `produces = "text/event-stream"` | SSE 等特殊响应（协商被绕过） |
| 忽略协商 | `produces = "*/*"` + 单转换器 | 极少用——协商语义是 HTTP 基础 |

```text
协商策略链（默认）：
  1. Accept 头（优先）
  2. 固定媒体类型（produces 显式声明）
  3. 可配置：文件后缀 / format 参数（7.x 默认关闭）
  
  注意：produces = "application/json" 时 Accept 其他类型 → 406
  produces 不写时 → 按 Accept 协商，缺省按第一个可写转换器
```

> 💡 面试考点：**produces 不写也能返回 JSON**——因为默认协商会"取第一个能写的转换器"（顺序里 Jackson 在 String 之后但在表单之前）；写 produces 的意义是**精确限定 + 更早报 406**，而不是"让 JSON 生效"。

## 5. 自定义转换器

```java
// 场景：自定义协议格式（如 csv 行 → 对象）
@Component
public class CsvHttpMessageConverter implements HttpMessageConverter<Report> {
    @Override
    public boolean canRead(Class<?> clazz, MediaType mt) {
        return Report.class.isAssignableFrom(clazz) && mt.includes(MediaType.parseMediaType("text/csv"));
    }
    @Override
    public boolean canWrite(Class<?> clazz, MediaType mt) {
        return Report.class.isAssignableFrom(clazz);
    }
    @Override
    public Report read(Class<? extends Report> clazz, HttpInputMessage input) throws IOException {
        String csv = StreamUtils.copyToString(input.getBody(), UTF_8);
        return Report.parse(csv);                       // 自定义解析
    }
    @Override
    public void write(Report report, MediaType contentType, HttpOutputMessage output) throws IOException {
        output.getHeaders().setContentType(MediaType.parseMediaType("text/csv"));
        StreamUtils.copy(report.toCsv(), UTF_8, output.getBody());
    }
}

// 注册：MVC configureMessageConverters / 客户端 configureMessageConverters
```

> 💡 自定义转换器要点：① 实现 `canRead/canWrite` 精确匹配（类型 + 媒体类型）；② 泛型场景实现 `GenericHttpMessageConverter`；③ 注册顺序影响匹配优先级（先注册先匹配）。

### 5.1 自定义转换器注册与面试追问

| 注册位置 | 生效范围 | 写法 |
|----------|---------|------|
| MVC `configureMessageConverters` | 服务端请求/响应 | `addCustomConverter(...)` |
| RestClient `configureMessageConverters` | 客户端收发 | 同款 API |
| `@Bean HttpMessageConverter` | Boot 自动追加 | 7.x 建议走配置 API 更可控 |

**自定义转换器的常见坑**：

| 坑 | 现象 | 解法 |
|----|------|------|
| canWrite 判定太宽 | 劫持了其他类型（如 `*/*`） | 精确匹配类型 + 媒体类型 |
| 未实现 Generic 版 | 泛型目标（List<Report>）匹配失败 | 实现 `GenericHttpMessageConverter` |
| 顺序靠后 | 与默认转换器撞车时永远输 | 替换对应媒体类型或调整顺序 |
| 读流不关闭 | 连接泄漏 | try-with-resources 消费输入流 |
| write 顺序写反 | 响应体空但 Content-Type 已设 | 先 setContentType 再写流 |
| 转换器里抛异常无兜底 | 500 而不是 4xx | 解析失败应抛 `HttpMessageNotReadableException`（映射 400） |
| 只实现 HttpMessageConverter | 泛型目标全部匹配失败 | 泛型场景实现 Generic 版（7.x 标准） |
| 返回类型是 `Object`/接口 | canWrite 匹配失真 | 尽量返回具体类型（ResolvableType 才精确） |
| charset 与编码不一致 | 中文乱码/内容损坏 | String 转换器显式 `setDefaultCharset(UTF_8)`；响应头 charset 与实际编码一致 |

| 面试追问 | 回答要点 |
|----------|---------|
| 转换器与 JSON 库的 ObjectMapper 什么关系 | 转换器是 Spring 的 HTTP 边界 SPI，JSON 库是内部实现——@RequestBody 绑定实际是"转换器 → JSON 库"两级 |
| 为什么需要 GenericHttpMessageConverter | 泛型擦除后 List<Order> 只剩 List——ResolvableType 携带完整泛型信息 |
| 转换器是单例吗 | 是——无状态设计；自定义转换器不要存请求级状态 |
| 内容协商能关掉吗 | 能（策略替换），但 99% 场景不该关 |
| 同一种媒体类型两个转换器会怎样 | 先注册的优先（列表顺序）；canWrite 也会影响命中 |
| 转换器与参数绑定（WebDataBinder）什么关系 | 转换器管"HTTP 字节 ↔ 对象"，绑定管"请求参数 → 方法参数"——两条链路 |
| 为什么 String 转换器要在 JSON 之前 | 字符串/文本是兜底能力——顺序体现"基础优先、专用随后"的默认设计 |
| 406 错误响应体长什么样 | Spring 默认空体 + 状态码；可自定义 406 的响应内容（异常处理器） |
| 怎么让一个方法同时输出 JSON 和 XML | 不写死 produces，由 Accept 协商（两个转换器都装配即可） |

> 🎯 **本模块一句话**：转换器是"类型 × 媒体类型"双匹配的 SPI——配置走 7.0 统一 API（先默认后替换），协商看 Accept/produces，出问题先按 406/415 流程走一遍。

### 5.2 生产实践与快速记忆卡

| 生产实践 | 要点 |
|----------|------|
| 统一 JsonMapper | 全局一个 `JsonMapper` Bean 注入各转换器——日期/忽略规则只配一处 |
| 响应 DTO 与请求 DTO 分离 | 避免内部字段外泄；字段增删不影响契约 |
| 大响应开压缩 | `server.compression.enabled=true`（转换器输出前压缩） |
| 转换器变更走灰度 | 配置 API 是全局的——先小流量验证再全量 |
| 版本兼容 | 字段只加不减（FAIL_ON_UNKNOWN_PROPERTIES 关闭兜底） |
