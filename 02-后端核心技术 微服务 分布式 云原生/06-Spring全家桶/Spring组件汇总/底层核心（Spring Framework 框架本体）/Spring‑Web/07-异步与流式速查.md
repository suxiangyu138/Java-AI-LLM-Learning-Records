## 1. 三套并发模型

| 模型 | 机制 | 适用 | 7.x 状态 |
|------|------|------|---------|
| 平台线程（阻塞） | 每请求一线程（~1MB 栈） | 传统 | 已过时 |
| **虚拟线程**（阻塞但轻量） | 每请求一虚拟线程（KB 级） | ✅ **主流** | **Boot 4 默认**（Tomcat/WebFlux 均支持） |
| 响应式（非阻塞） | 事件循环 + Reactor | 流式/网关/极端并发 | 保留专长场景 |

```text
Boot 4 默认配置：spring.threads.virtual.enabled=true
  Tomcat 协议处理器虚拟线程化：请求处理线程 = 虚拟线程
  → 阻塞式代码（JDBC/Redis/外部调用）不再拖死平台线程
  → RestClient + 虚拟线程 = "同步代码 + 高并发"（官方主推姿势）
```

> 🎯 **核心要点**：7.x 的答案不是"全都改响应式"——**虚拟线程让阻塞式同步代码重新成为默认选择**；响应式保留给"真流式/背压/网关"场景；面试答"Spring 7 并发模型"按此三模型演进讲。

### 1.1 并发模型决策清单

| 项目特征 | 模型 | 理由 |
|----------|------|------|
| 常规 Web + JDBC + 外部调用 | 虚拟线程 + 同步 | 代码简单、并发足够（Boot 4 默认） |
| 长连接/SSE/AI 流式 | 同步 + 流式响应（SseEmitter） | 虚拟线程扛连接数，流式由容器支持 |
| 高扇出网关/聚合 | 响应式 | 背压与连接复用 |
| 计算密集型服务 | 平台线程/虚拟线程均无收益 | 用并行流/任务分片 |
| 混合（阻塞库 + 流式需求） | 虚拟线程 + SSE | 伪响应式（JDBC 混 WebFlux）最差 |

> 💡 决策原则：**先量化瓶颈再选模型**——压测看线程数/连接数/CPU 哪个先到顶；虚拟线程解决"线程不够"，响应式解决"连接与背压"。

## 2. 虚拟线程：7.x/Boot 4 默认

```yaml
# Boot 4（默认已开；可显式确认）
spring:
  threads:
    virtual:
      enabled: true
```

| 要点 | 说明 |
|------|------|
| 开启方式 | Boot 4 默认；纯 Framework 需 `SimpleAsyncTaskExecutor` 定制/容器协议处理器配置 |
| 生效范围 | 请求处理线程、@Async、@Scheduled、RestClient 阻塞调用 |
| 线程池注意 | **虚拟线程无需池**（创建便宜）；慎用"限流线程池"思维 |
| 兼容注意 | 线程局部变量/ThreadLocal 仍是每线程一份（虚拟线程也适用） |
| 与响应式 | 二者并存：虚拟线程管阻塞 IO，Reactor 管流式管道 |

> ⚠️ 常见误解：虚拟线程不是"免费无限并发"——**CPU 密集操作仍占核**；数据库连接池/外部连接池依然是瓶颈（虚拟线程等连接照样排队）；ThreadLocal 滥用会放大内存占用。

### 2.1 虚拟线程执行模型细节

```text
Tomcat 虚拟线程化（Boot 4）：
  Tomcat 协议处理器使用 VirtualThreadExecutor：
  Java 17+ 每请求 = 一个虚拟线程（挂载到平台线程上执行）
  阻塞点（JDBC/IO）→ 虚拟线程卸载（unmount）→ 平台线程继续跑其他任务
  → 线程数从"并发上限"变成"受内存与连接池约束"

  JDK 演进：JEP 444（21 落地）→ JEP 491（24）解决 synchronized pinning
  → 7.x/Boot 4 配套 JDK 24+ 时无需再规避 synchronized
```

| 维度 | 平台线程 | 虚拟线程 |
|------|---------|---------|
| 创建成本 | 高（1MB 栈，系统线程） | 低（KB 级栈，堆内对象） |
| 数量 | 数百-数千 | 数万-数十万 |
| 调度 | OS 调度器 | JVM 调度器（FIFO + 工作线程） |
| 阻塞语义 | 阻塞占线程 | 阻塞释放载体线程 |
| 适用 | 计算密集 | IO 密集（请求处理/外部调用） |

| 生产注意 | 说明 |
|----------|------|
| 数据库连接池 | 虚拟线程不解决连接上限——池满照样排队 |
| CPU 密集 | 虚拟线程无收益，甚至略差（调度开销） |
| ThreadLocal | 每虚拟线程一份——大量请求 × 大量 ThreadLocal = 内存放大 |
| synchronized | JDK 24（JEP 491）已消除 pinning；旧 JDK 避免长 synchronized |
| 转储 | `jcmd Thread.dump_to_file` 可转储全部虚拟线程 |

> 💡 **面试叙事**：虚拟线程的收益来自"阻塞不占平台线程"——所以"同步代码 + 虚拟线程"成为 7.x 默认；但要讲清边界（CPU/连接池/ThreadLocal），面试官才认可你真懂。

### 2.2 虚拟线程的配置与线程池改造

```yaml
# Boot 4 配置（默认已开，显式确认）
spring:
  threads:
    virtual:
      enabled: true
  task:
    execution:
      thread-name-prefix: "vt-"          # 便于转储识别（可选）
```

| 改造点 | 做法 | 注意 |
|--------|------|------|
| 请求处理 | Boot 4 默认虚拟线程化 | 无需改动 |
| @Async | Boot 自动切虚拟线程执行器 | 自定义池需 TaskDecorator（见 [05](05-Web上下文与作用域速查.md) 4.1） |
| @Scheduled | 默认虚拟线程 | 定时任务别用长阻塞 |
| 自定义线程池 | 评估是否必要 | 虚拟线程无需池——池思维要改 |
| 信号量限流 | 替代"线程池限流" | 虚拟线程下用 Semaphore 控并发 |

> ⚠️ **迁移红线**：**ThreadLocal 值传递**与 **synchronized 长临界区**是虚拟线程下仅存的两个老问题——前者用作用域 Bean/显式传递，后者升 JDK 24+（JEP 491）或重构加锁范围。

## 3. SSE：服务端推送基础

```text
SSE（Server-Sent Events）：HTTP 长连接服务端单向推送（text/event-stream）
  场景：AI 流式输出（LLM token 流）、实时进度、通知推送
  与 WebSocket 对比：单向、基于 HTTP、自动重连、更轻（见 WebSocket 系列）
```

| 技术 | 归属 | 说明 |
|------|------|------|
| `SseEmitter` | Spring MVC（webmvc） | 控制器返回流式事件 |
| `ServerSentEvent` | spring-web（`org.springframework.http.codec`） | 事件模型（data/id/event/retry） |
| `ResponseBodyEmitter` | webmvc | 通用流式响应基类 |
| `StreamingResponseBody` | webmvc | 原始流式输出 |

```java
// WebFlux 侧 SSE（响应式）：Flux<ServerSentEvent> 直出流
@GetMapping(path = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<String>> stream() {
    return Flux.interval(Duration.ofSeconds(1))
            .map(i -> ServerSentEvent.<String>builder()
                    .id(String.valueOf(i))
                    .data("tick-" + i)
                    .build());
}
```

> 💡 AI 应用高频：LLM 流式响应的标准形态就是 SSE（`text/event-stream`）——服务端逐 token 推送，前端 EventSource 接收；Spring 6.1+ 的 RestClient 同步调用 + SSE 消费在 WebFlux 侧更顺（见 AI 大模型应用开发系列）。

### 3.1 SSE 断连、心跳与消费

```java
// SseEmitter 心跳与超时（MVC 侧）
@GetMapping("/events")
public SseEmitter events() {
    SseEmitter emitter = new SseEmitter(60_000L);        // 总超时 60s
    ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
    scheduler.scheduleAtFixedRate(() -> {
        try {
            emitter.send(SseEmitter.event().comment("ping"));   // 心跳注释行
        } catch (IOException e) {
            emitter.completeWithError(e);                       // 断连 → 结束
            scheduler.shutdown();
        }
    }, 15, 15, TimeUnit.SECONDS);
    emitter.onCompletion(scheduler::shutdown);                 // 完成清理
    emitter.onTimeout(() -> { emitter.complete(); scheduler.shutdown(); });
    return emitter;
}
```

| SSE 断连要点 | 说明 |
|--------------|------|
| 断连检测 | 客户端断开时 send 抛 IOException → completeWithError |
| 心跳 | 定时 `comment("ping")`（注释行不触发回调但保活） |
| 超时 | SseEmitter 构造参数（默认 30s）——长流要调大 |
| 代理/网关 | Nginx 等需关缓冲（`X-Accel-Buffering: no`）否则 token 不实时 |
| 客户端重连 | EventSource 自动重连 + `retry:` 字段控制间隔 |

> ⚠️ **AI 流式输出生产三坑**：① 网关缓冲导致"一次性吐出"（关缓冲）；② 无心跳被负载均衡器掐断（加注释心跳）；③ 超时小于模型生成时间（调大或按事件重置）。

### 3.2 SSE 事件格式与客户端消费

```text
SSE 线上格式（text/event-stream）：
  id: 42                      ← 事件 id（断线重连时用于续传）
  event: token                ← 事件类型（前端 addEventListener("token")）
  data: {"text":"你好"}        ← 数据（可多行 data: 拼接）
  retry: 3000                 ← 客户端重连间隔（ms）

  : ping                      ← 注释行（心跳，不触发事件）
  （空行分隔事件）
```

| 字段 | 用途 | 客户端行为 |
|------|------|-----------|
| `id` | 断线续传标记 | 重连时带 `Last-Event-ID` 头 |
| `event` | 事件类型 | 按类型分发监听器 |
| `data` | 载荷（JSON 等） | 多行 data 按换行拼接 |
| `retry` | 重连间隔 | EventSource 自动应用 |

```java
// WebClient 消费 SSE 并自动重连
webClient.get().uri("/llm/stream")
        .accept(MediaType.TEXT_EVENT_STREAM)
        .retrieve()
        .bodyToFlux(ServerSentEvent.class)
        .retryWhen(Retry.backoff(5, Duration.ofSeconds(1)))  // 断线重连
        .subscribe(evt -> System.out.println(evt.data()));
```

> 💡 前端 EventSource 只支持 GET——SSE 的"方法限制"是设计特性；需要 POST/自定义头的流式走 fetch + ReadableStream 解析（或 WebSocket）。

## 4. 响应式栈基础：WebClient 与流式

```java
// 流式消费（WebClient 强项）
Flux<ServerSentEvent<Order>> events = webClient.get()
        .uri("/orders/stream")
        .retrieve()
        .bodyToFlux(new ParameterizedTypeReference<ServerSentEvent<Order>>() {});

events.filter(e -> "CREATED".equals(e.event()))
        .doOnNext(e -> notify(e.data()))
        .subscribe();          // 订阅即消费（背压由 Reactor 管理）

// 大数据流：db 游标 → 管道 → 客户端（不整驻内存）
Flux.from(streamAllRows())     // 每行一个事件
        .map(this::toJson)
        .subscribe(subscriber);
```

| 特性 | 说明 |
|------|------|
| 背压 | 消费者慢则上游减速（Reactor 原生） |
| 错误 | Flux error 信号可恢复/重试（配合 [Spring-Core-07](../Spring‑Core/07-重试与弹性速查.md) 响应式重试） |
| 线程 | 事件循环（Netty），勿在回调里做阻塞 IO |
| 深度 | 见响应式编程组件系列（WebFlux/Project Reactor） |

> ⚠️ 响应式边界：**一条链路全响应式才收益**——DB/Redis/第三方全是响应式客户端时才选 WebFlux；混用阻塞（JDBC）的"伪响应式"只换来复杂。

### 4.1 响应式管道的时间控制

```java
// 超时、重试与兜底
Mono<PaymentResult> call = webClient.post()
        .uri("/v1/charge")
        .bodyValue(req)
        .retrieve().bodyToMono(PaymentResult.class)
        .timeout(Duration.ofSeconds(5))                      // 超时 → TimeoutException
        .retryWhen(Retry.backoff(2, Duration.ofMillis(500)));  // 退避重试（有上限）

// 超时后的优雅降级
Mono<String> cached = cacheService.get(key)
        .timeout(Duration.ofMillis(200))
        .onErrorReturn("default-value");                     // 兜底

// 手动取消：订阅者 dispose —— 上游停止生产
Disposable d = flux.subscribe(...);
d.dispose();
```

| 操作符 | 语义 | 坑 |
|--------|------|-----|
| `timeout` | 发射超时 | 超时后管道错误终止，需配合 onError* |
| `retryWhen` | 按策略重试 | 无限重试 = 无限请求——必须配上限 |
| `onErrorReturn/Resume` | 错误兜底 | 掩盖错误要谨慎（可加日志） |
| `doOnNext` | 副作用观察 | 不应做阻塞/昂贵操作 |
| `block` | 同步桥 | 仅限非事件循环线程 |

> 🎯 **响应式自检清单**：管道里有没有阻塞调用？错误有没有兜底？重试有没有上限？超时有没有设置？——四个"有没有"过一遍，响应式代码才敢上线。

### 4.2 流式消费的常见坑

| 坑 | 现象 | 解法 |
|----|------|------|
| 忘记 subscribe | 代码"没反应" | 响应式两段式：声明 + 订阅 |
| 异常未处理 | 流静默中断 | doOnError 记录 + onErrorResume 降级 |
| 无限重试 | 下游故障时请求风暴 | Retry.backoff 配上限 |
| 背压被绕过 | 缓冲无界 OOM | 限制预取（limitRate）或按需订阅 |
| 事件循环里阻塞 | 全链路卡顿 | 阻塞操作换线程（publishOn）或改响应式客户端 |
| 连接泄漏 | 流未取消 | try-with-resources 订阅 / 显式 dispose |

> ⚠️ **内存大坑**：`Flux` 无限流 + 无限缓冲 = OOM——生产必须给"生产速率"或"缓冲上限"加约束（limitRate/onBackpressureBuffer 上限）。

## 5. 异步请求抽象：WebAsyncManager

```text
异步请求处理（Servlet 3.1 AsyncContext 的 Spring 抽象，spring-web 提供）：
  WebAsyncManager / AsyncWebRequest / WebAsyncTask
  → 请求线程立即返回，业务线程完成后写回响应
  → MVC 的 DeferredResult / Callable / SseEmitter 底层都走它

  Spring 6.1+/7.x 主流：
  虚拟线程使"异步请求处理"多数场景被"同步 + 虚拟线程"替代——
  只有真正需要"长任务与请求解耦"时才用异步 API。
```

```java
// MVC：DeferredResult（webmvc，底层走 WebAsyncManager）
@GetMapping("/async-order")
public DeferredResult<Order> asyncOrder() {
    DeferredResult<Order> result = new DeferredResult<>(30_000);  // 超时 30s
    CompletableFuture.supplyAsync(() -> orderService.slowBuild())
            .whenComplete((order, err) -> {
                if (err != null) result.setErrorResult(err);
                else result.setResult(order);
            });
    return result;
}
```

> 🎯 **核心要点**：异步请求处理的本质是"**请求线程与业务线程解耦**"——7.x 时代虚拟线程已让同步代码天然高并发，DeferredResult 类异步仅用于"长任务防占线程"或"需要超时/取消控制"的窄场景；面试答"Spring 异步请求"提 WebAsyncManager 是加分项。

### 5.1 异步抽象对比与面试追问

| 抽象 | 返回类型 | 用途 | 底层 |
|------|---------|------|------|
| `Callable` | 方法返回值 | 最简单的异步（丢给任务执行器） | WebAsyncManager |
| `WebAsyncTask` | Callable + 超时/回调 | 需要超时控制的 Callable | WebAsyncManager |
| `DeferredResult` | 手动 setResult | 长任务与请求解耦、事件驱动 | WebAsyncManager |
| `CompletableFuture`（7.x 直接支持） | 异步结果 | 与虚拟线程/响应式衔接 | WebAsyncManager 适配 |
| `SseEmitter` / `ResponseBodyEmitter` | 流式事件 | SSE/流式推送 | WebAsyncManager |
| `StreamingResponseBody` | 原始流 | 大文件下载 | WebAsyncManager |

```text
WebAsyncManager 生命周期：
  1. 请求线程进入（AsyncWebRequest.startAsync）
  2. 控制器返回异步结果 → 请求线程释放
  3. 业务线程完成 → setResult/complete → 回调写回响应
  4. 超时/错误/取消 → 对应回调链（onTimeout/onError/onCompletion）

  7.x 主流姿势：虚拟线程 + 同步控制器已覆盖 90% 异步需求；
  WebAsyncManager 系保留给"推送/流式/长任务解耦"
```

| 面试追问 | 回答要点 |
|----------|---------|
| 虚拟线程还需要异步 API 吗 | 多数不需要——异步 API 的价值从"省线程"变成"解耦与推送" |
| DeferredResult 与 CompletableFuture 区别 | 前者是 Servlet 异步容器抽象；后者是 JDK 任务编排——7.x 可直接返回 CompletableFuture |
| SSE 与轮询/WebSocket 选型 | 单向实时用 SSE；双向交互用 WebSocket；简单轮询兜底 |
| 异步请求的线程安全 | 回调线程与请求线程不同——共享状态要同步/不可变 |
| 长任务超时了会怎样 | onTimeout 回调触发——默认返回 503/断开，可自定义降级 |
| 大文件下载用哪个 | StreamingResponseBody（原始流）——避免整文件驻内存 |
| 虚拟线程与响应式能混用吗 | 能——虚拟线程处理阻塞入口，Reactor 管道做流式；混用边界在"线程切换点"要明确 |
| SSE 支持断点续传吗 | 支持——id + Last-Event-ID 头（服务端按 id 续推） |
| 为什么 AI 流式用 SSE 而不是 WebSocket | SSE 单向够用、HTTP 原生、自动重连、文本友好——WebSocket 留给双向交互 |
| 压测 SSE 长连接要注意什么 | 连接数指标（非 QPS）——连接上限与心跳频率是关键 |
| 虚拟线程转储怎么分析 | jcmd dump 后按虚拟线程分组看阻塞点（io/锁/池等待） |

> 💡 **本模块一句话**：并发三模型（平台线程 → 虚拟线程 → 响应式）按瓶颈选——虚拟线程管"阻塞 IO 并发"，SSE 管"服务端推送"，WebAsyncManager 管"请求解耦"；7.x 默认答案 = 虚拟线程 + 同步。

### 5.2 常见问题速查与记忆卡

| 问题 | 答案 |
|------|------|
| 虚拟线程下压测上不去 | 查连接池/CPU/ThreadLocal——不是线程数 |
| SSE 断了没有重连 | 检查 retry 字段/代理缓冲/心跳 |
| 流式输出"卡住不动" | 网关缓冲未关（X-Accel-Buffering） |
| 响应式链偶尔超时 | 事件循环被阻塞（找阻塞调用） |
| 异步任务完成但响应没写回 | 回调里异常未处理（onError 缺失） |
| 大文件下载内存爆 | StreamingResponseBody 流式写，别整读 |

```text
一分钟记忆卡：
  模型：平台线程（旧）→ 虚拟线程（Boot 4 默认）→ 响应式（专长）
  虚拟线程：阻塞不占线程；边界 = CPU/连接池/ThreadLocal
  SSE：text/event-stream、心跳注释、retry 重连、关网关缓冲
  异步抽象：Callable → DeferredResult → SseEmitter（底层 WebAsyncManager）
  响应式四问：阻塞？兜底？重试上限？超时？
```
