## 1. 模块总览

```text
spring-aop        ← Spring AOP 本体（代理工厂/切点/通知/织入，被一切代理依赖）
spring-aspects    ← @AspectJ 注解支持（@Aspect/@Around 等）
aspectjweaver     ← AspectJ 织入器（第三方，spring-aspects 的运行时依赖）
spring-context     ← 含 AOP 基础设施（AopConfig、@EnableAspectJAutoProxy）
```

> 🎯 **要点**：Spring AOP 是**运行时代理织入**（动态代理），不是 AspectJ 的编译期/类加载期织入——`spring-aspects` 只是借用了 AspectJ 的注解语法，织入仍是代理。

### 1.1 依赖传导链速览

```text
spring-boot-starter-aop
  ├── spring-aop            ← 代理工厂/切点/通知（一切代理的地基）
  ├── spring-aspects        ← @AspectJ 注解模型（@Aspect/@Around/@Pointcut）
  │     └── aspectjweaver   ← AspectJ 表达式解析与织入器（运行时依赖）
  └── spring-context        ← AutoProxyCreator 等基础设施（传递）
```

> 💡 排查依赖问题的第一直觉：看这条链缺了谁——"有 spring-aop 但 @Aspect 不识别"通常是缺 spring-aspects 或 aspectjweaver。

### 1.2 spring-aop 内部包结构

```text
org.springframework.aop
├── Pointcut / Advisor / TargetSource        # 核心抽象接口
├── aspectj                                  # AspectJ 表达式切点（AspectJExpressionPointcut）
├── framework                                # 代理工厂（ProxyFactory / AopProxy / 调用链）
├── framework.autoproxy                      # 自动代理（AbstractAutoProxyCreator）
├── interceptor                              # 方法拦截器（MethodInterceptor）
├── support                                  # 通用实现（DefaultPointcutAdvisor 等）
└── target                                   # 目标源（SingletonTargetSource 等）
```

### 1.3 Spring AOP 与 AspectJ 术语对照

两者共享同一套切点语法（Spring 直接复用 AspectJ 表达式解析器），但织入机制完全不同，面试常被追问：

| 概念 | Spring AOP | AspectJ |
|------|-----------|---------|
| 切点语法 | AspectJ 表达式（execution/within） | 同左（同源） |
| 织入时机 | 运行时创建代理 | 编译期（AJC）/类加载期（LTW）/运行时 |
| 切面定义 | @Aspect 注解类 | .aj 源文件或注解类 |
| 代理对象 | 有（目标被包裹） | 无（直接修改目标字节码） |
| 目标限制 | public 非 final 方法 | 几乎无限制 |
| 运行时开销 | 通知链调用开销 | 织入后无额外开销 |

> 🎯 一句话记忆：**Spring AOP = AspectJ 的"语法 + 表达式" + Spring 自己的"代理织入"**——依赖里的 aspectjweaver 只负责解析表达式，不负责织入。

### 1.4 模块一句话全景

| 模块 | 一句话 |
|------|--------|
| spring-aop | 代理与织入的核心（切点/通知/工厂全在这） |
| spring-aspects | 让 @Aspect 注解可被 Spring 解析（胶水层） |
| aspectjweaver | AspectJ 本体：提供注解定义与表达式解析器 |
| spring-context | 容器基建：AutoProxyCreator 的注册与触发 |
| spring-beans | 生命周期钩子：BeanPostProcessor 扩展点 |
| spring-boot-starter-aop | 一站打包：上述核心 + 注解模型 + 版本锁定 |

> 🎯 依赖心智模型：**spring-aspects 是"翻译官"（把 AspectJ 注解翻成 Spring Advisor），aspectjweaver 是"字典"（提供注解与语法），spring-aop 是"执行者"（代理织入）**——三者各司其职，缺一不可。

### 1.5 常见误读澄清

| 误读 | 澄清 |
|------|------|
| "Spring AOP 就是 AspectJ" | 只借语法与表达式，织入是动态代理 |
| "没有 spring-aspects 也能用 @Aspect" | 注解本体在 aspectjweaver，但**解析器在 spring-aspects**，缺了不生效 |
| "starter-web 已含完整 AOP" | 只含 spring-aop 基础，不含 @Aspect 注解模型 |
| "aspectjweaver 版本越新越好" | 与 Spring 配套即可，跨代升级可能有行为差异 |

> ⚠️ 这些误读对应生产中最常见的三种"切面不生效"——先对照此表排除依赖层问题，再往下查代码。

## 2. 核心模块

| Artifact | 职责 | 关键类 |
|---------|------|--------|
| `spring-aop` | AOP 核心抽象与代理工厂 | `ProxyFactory`、`Advisor`、`Pointcut`、`Advice`、`AspectJExpressionPointcut` |
| `spring-context`（内含） | AOP 基础设施自动装配 | `@EnableAspectJAutoProxy`、`AnnotationAwareAspectJAutoProxyCreator` |
| `spring-beans`（内含） | Bean 后置处理器链路 | `AbstractAutoProxyCreator`（代理创建入口） |

> ⚠️ **注意**：几乎所有 Spring 项目都间接依赖 spring-aop（事务/缓存/异步都基于它）——**无需单独引入**，除非用纯 Spring 手动装配。

### 2.1 关键类归属包对照

| 类 | 所在包 | 作用层级 |
|----|--------|---------|
| `ProxyFactory` | org.springframework.aop.framework | 编程式入口（最底层） |
| `AbstractAutoProxyCreator` | org.springframework.aop.framework.autoproxy | 自动代理入口（容器级） |
| `AnnotationAwareAspectJAutoProxyCreator` | org.springframework.aop.aspectj.annotation | 注解切面解析入口 |
| `AspectJExpressionPointcut` | org.springframework.aop.aspectj | 表达式切点实现 |
| `DefaultPointcutAdvisor` | org.springframework.aop.support | 切点+通知组装单元 |

> 💡 记忆法：`aop.framework` 管"怎么造代理"，`aop.aspectj` 管"怎么解析注解与表达式"，`aop.support` 管"通用实现"——报错堆栈里看到这些包名即可定位环节。

### 2.2 spring-context 内含的 AOP 基础设施

spring-context 不带切面注解，但携带让 AOP"跑起来"的装配件——这也是"有 spring-aop 却没有自动代理"时该查的地方：

| 类/注解 | 职责 |
|---------|------|
| `@EnableAspectJAutoProxy` | 注解开关：向容器注册 AutoProxyCreator |
| `AnnotationAwareAspectJAutoProxyCreator` | 扫描 @Aspect Bean 并创建代理（注解驱动） |
| `AspectJAwareAdvisorAutoProxyCreator` | XML `<aop:config>` 场景的自动代理（声明驱动） |
| `AopConfigUtils` | 注册 AutoProxyCreator 的静态工具（内部） |

> 💡 判断"自动代理有没有装上"：启动日志或断点看 `AnnotationAwareAspectJAutoProxyCreator` 是否作为 BeanPostProcessor 注册——没注册则一切切面静默失效。

### 2.3 spring-beans 的参与方式

spring-beans 不含任何 AOP 类，但提供了两个被 AOP 深度复用的机制：

| spring-beans 机制 | AOP 如何复用 |
|------------------|-------------|
| BeanPostProcessor | AbstractAutoProxyCreator 实现它，混入 Bean 生命周期后置处理 |
| BeanDefinition | 记录代理配置（如 @Proxyable 写入 Bean 级属性） |
| FactoryBean | ProxyFactoryBean 基于它实现 XML 时代的声明式代理 |
| BeanFactory | 代理工厂取目标 Bean 的入口（依赖解析的源头） |

> 💡 由此解释一个现象：**AOP 能代理"任何容器 Bean"而不侵入业务代码**——本质是借了 BeanPostProcessor 这个"生命周期钩子"，在 Bean 出厂前偷换成了代理。

### 2.4 spring-aop 版本线对照

| Spring 版本 | spring-aop 版本线 | 备注 |
|-------------|------------------|------|
| 7.1 | 7.1.x | 最新维护线（Boot 4.1 配套） |
| 7.0 | 7.0.x | 首个 7.x（Boot 4.0 配套） |
| 6.2 | 6.2.x | 存量主流（Boot 3.x 配套） |

> ⚠️ **禁止混搭**：spring-aop 6.x 与 spring-aspects 7.x 混用时，注解解析与代理机制可能出现不兼容（NoSuchMethodError 高发）——版本线必须整体一致。

### 2.5 编译期 vs 运行期的选择

| 维度 | 编译期织入（AJC） | 运行时代理（Spring AOP） |
|------|:---:|:---:|
| 配置成本 | 高（专用编译流程） | 低（加依赖即用） |
| 灵活性 | 低（改切面需重编译） | 高（配置驱动） |
| 生态配合 | 弱（与 Spring 容器解耦） | 强（自动代理/注解联动） |
| 适用 | 性能极致/无接口场景 | **绝大多数项目** |
| 排障可观测性 | 弱（需断点/专用流程） | 强（AopUtils 等工具即查） |

> 🎯 结论：除非性能敏感且对织入时机有硬性要求，**运行时代理是唯一理性选择**——AJC 的收益在现代 JVM 面前并不划算。

## 3. AspectJ 相关模块

| Artifact | 职责 | 引入时机 |
|---------|------|---------|
| `spring-aspects` | @AspectJ 注解模型支持（@Aspect、五类通知注解、@Pointcut） | 使用注解式 AOP 时（starter 已带） |
| `aspectjweaver` | AspectJ 织入器（表达式解析、LTW 能力） | 注解式 AOP 的运行时依赖；**需要 load-time weaving 时显式引入** |
| `aspectjrt` | AspectJ 运行时库 | 仅在真正使用 AspectJ 语言/编译时 |

```xml
<!-- 显式引入（纯 Spring 项目） -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-aop</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-aspects</artifactId>
</dependency>
```

> 💡 **AspectJ 三种织入方式对比**：

| 织入方式 | 时机 | Spring AOP 用的是？ |
|---------|:---:|:---:|
| 编译期织入（AJC） | 编译时 | ❌ |
| 类加载期织入（LTW） | JVM 加载类时 | 可选（需显式开启） |
| **运行时代理织入** | 运行时创建代理 | ✅ **默认方式** |

### 3.1 load-time weaving 开启步骤

LTW（类加载期织入）与运行时代理织入是两套机制：LTW 直接修改目标类字节码（**没有代理对象**），Spring AOP 生成代理对象。两者不可混用理解，绝大多数项目不需要 LTW。

| 步骤 | 操作 | 说明 |
|:---:|------|------|
| ① | 引入 aspectjweaver | 依赖层面准备 |
| ② | `-javaagent:path/to/aspectjweaver.jar` | JVM 启动参数 |
| ③ | 编写 `META-INF/aop.xml` | 声明要织入的切面 |
| ④ | `@EnableLoadTimeWeaving` | Spring 侧开启（或用 XML 命名空间） |

```xml
<!-- META-INF/aop.xml 示例：声明 LTW 切面 -->
<aspectj>
    <aspects>
        <aspect name="com.demo.aspect.LtwAuditAspect"/>
        <weaver options="-verbose"/>
    </aspects>
</aspectj>
```

> ⚠️ LTW 适合"目标类无接口、又不想引入代理语义"的存量系统迁移，但配置成本高、与容器代理体系割裂——**新项目一律用 Spring AOP 运行时代理**。

### 3.2 aspectjweaver 版本配套

aspectjweaver 由 spring-aspects 传递引入，正常情况下**不需要手工管版本**；只有手工覆盖时才需对照：

| Spring 版本 | 配套 AspectJ 线 | 说明 |
|-------------|----------------|------|
| Spring 7.x | 1.9.22+ | 支持较新 Java 语法特性 |
| Spring 6.x | 1.9.19+ | 存量 Boot 3.x 配套 |

> ⚠️ 手工降级 aspectjweaver 风险更高：切点表达式解析依赖新语法支持（如 Java 17+ 的记录类、模式匹配），版本过旧会直接抛解析异常。

### 3.3 注解与实现的三层归属

| 东西 | 所在模块/包 |
|------|-----------|
| `@Aspect`/`@Before` 等注解本体 | aspectjweaver：org.aspectj.lang.annotation |
| 注解解析器（把 @Aspect 解析成 Advisor） | spring-aspects：org.springframework.aop.aspectj.annotation |
| 表达式切点实现 | spring-aop：org.springframework.aop.aspectj |
| 代理工厂 | spring-aop：org.springframework.aop.framework |

> 💡 回答"@Aspect 是哪来的"：**注解本身来自 AspectJ（aspectjweaver），解析与织入全是 Spring 自己的**——这就是"借用语法"的完整含义，也是面试官最爱拆的细节。

### 3.4 aspectjweaver 的四个职责

| 职责 | 说明 |
|------|------|
| 注解定义 | org.aspectj.lang.annotation 下的 @Aspect/@Before/@Around 等 |
| 表达式解析 | PointcutExpression 解析 execution/within/@annotation |
| 字节码工具 | LTW/编译期织入时使用的 AspectJ 织入器 |
| 运行时支撑 | JoinPoint/ProceedingJoinPoint 等运行时类型 |

> 💡 注意区分：**运行时 JoinPoint 类型来自 aspectjweaver，但 Spring 的代理执行并不依赖 AspectJ 织入器**——只在解析表达式与提供类型时用到它。

## 4. 依赖什么场景引入什么

| 场景 | 需要的依赖 |
|------|-----------|
| Spring Boot 注解式 AOP（@Aspect） | `spring-boot-starter-aop`（一行搞定） |
| 纯 Spring + 注解式 AOP | spring-aop + spring-aspects |
| 纯 Spring + XML 式 AOP | spring-aop（`<aop:config>` 命名空间） |
| 编程式 AOP（ProxyFactory） | spring-aop |
| load-time weaving | + aspectjweaver + 启动参数 `-javaagent` |
| 只依赖事务/缓存（不写切面） | 无需单独引入（starter 传递依赖） |

### 4.1 依赖冲突与版本锁定

| 报错现象 | 根因 | 处理 |
|---------|------|------|
| `NoSuchMethodError`（AspectJ 相关类） | spring-aspects 与 aspectjweaver 版本不一致 | 统一交给 Boot dependency management 锁版本 |
| `ClassNotFoundException: org.aspectj.lang.annotation.Aspect` | 缺 aspectjweaver | 引入 spring-boot-starter-aop |
| 切点表达式解析抛错 | aspectjweaver 版本过旧 | 升级 aspectjweaver 至与 Spring 版本配套 |

> 🎯 经验法则：**AOP 相关依赖一律用 Boot 的依赖管理锁定**，手工单独引 aspectjweaver 是版本冲突的头号来源；只有 LTW 等特殊场景才需要显式管理版本。

### 4.2 三种使用形态选型

| 形态 | 配置位置 | 适用 | 维护性 |
|------|---------|------|--------|
| 注解式 `@Aspect` | 切面类内 | 业务横切（日志/审计/监控） | 最好（推荐） |
| XML `<aop:config>` | xml 文件 | 存量系统迁移 | 差（表达式与代码分离） |
| 编程式 `ProxyFactory` | Java 代码 | 动态织入/框架开发 | 中（样板多） |

> 💡 新代码一律注解式：切面与业务同在代码库、IDE 可跳转、编译期可发现错误；XML 只存在于历史系统。

### 4.3 依赖引入决策树

```text
项目要用 AOP 吗？
├─ 否（只依赖事务/缓存等能力）→ 不加任何 AOP 依赖（starter 传递已带）
├─ 是，注解式（@Aspect）→ Boot：spring-boot-starter-aop
│                         纯 Spring：spring-aop + spring-aspects
├─ 是，XML 式（<aop:config>）→ spring-aop 即可
├─ 是，编程式（ProxyFactory）→ spring-aop 即可
└─ 特殊：需要 LTW → + aspectjweaver + -javaagent + aop.xml
```

> 🎯 决策核心只有一条：**要不要写 @Aspect？**——要，就上 starter-aop（Boot 下）；不要，依赖早就在传递链里了，什么都不用加。

### 4.4 常见误区对照

| 误区 | 真相 |
|------|------|
| "我加了 starter-web，AOP 就能用" | web starter 只带 spring-aop，@Aspect 需要 starter-aop |
| "LTW 是 Spring AOP 的高级模式" | LTW 是 AspectJ 的机制，与代理织入两套体系 |
| "切面不生效就升级 aspectjweaver" | 90% 是依赖缺失或注册问题，先查依赖链 |
| "手写 aspectjweaver 版本更可控" | 与 Spring 配套即可，手工管版本反而引入冲突 |
| "重试注解与 AOP 无关" | @Retryable 由 spring-retry 提供拦截器，织入载体仍是 AOP 代理 |
| "aspectjweaver 是 Spring 的模块" | 第三方（AspectJ 项目）产物，Spring 只是消费方 |

> ⚠️ 对照排障：**切面不生效先走"依赖层 → 注册层 → 表达式层"三层排查**——依赖层问题用本表排除最快。

## 5. Starter 对照

| Starter | 包含 | 适用 |
|---------|------|------|
| `spring-boot-starter-aop` | spring-aop + spring-aspects + aspectjweaver | **注解式 AOP 标准入口** |
| `spring-boot-starter-web`（传递） | spring-aop（事务等基础设施） | 不写切面时无需加 AOP starter |
| `spring-boot-starter`（传递） | 同上 | 同上 |

> ⚠️ **经验**：Boot 项目里"@Aspect 不生效"十有八九是**忘了加 `spring-boot-starter-aop`**（stater-web 只带基础 spring-aop，不带 aspects 注解模型）。

### 5.1 Starter 与 Framework 版本对应

| Boot 版本 | 配套 Framework | AOP 关键行为 |
|-----------|---------------|-------------|
| Boot 4.1 | Spring 7.1 | CGLIB 一致默认 + @Proxyable（最新维护线） |
| Boot 4.0 | Spring 7.0 | CGLIB 一致默认 + @Proxyable（首个 7.x 线） |
| Boot 3.x | Spring 6.x | 存在 JDK/CGLIB 混差，依赖全局配置 |

> ⚠️ 跨主版本升级时重点核对：`spring.aop.proxy-target-class` 语义、所有"依赖 JDK 代理"的存量代码、以及 @Async/@Retryable 代理行为是否变化。

### 5.2 验证依赖是否就绪

| 方法 | 操作 | 判断依据 |
|------|------|---------|
| 依赖树 | `mvn dependency:tree -Dincludes=org.aspectj,org.springframework:spring-aop` | 确认 spring-aop / aspectjweaver 存在且版本一致 |
| 启动日志 | 观察启动期 bean 注册日志 | 出现 AutoProxyCreator 相关注册 |
| 断点 | 打断点于 `AnnotationAwareAspectJAutoProxyCreator` 构造器 | 命中即自动代理已装配 |
| 代码判断 | `AopUtils.isAopProxy(bean)` | 返回 true 说明代理已生成 |

```bash
# 快速验证：Maven 依赖树（确认版本一致）
mvn dependency:tree -Dincludes=org.aspectj,org.springframework:spring-aop
```

> 🎯 三条验证路径覆盖"依赖有没有 → 代理机制装没装 → 代理生没生成"三个层次——对应排查任何 AOP 失效问题的第一站。

### 5.3 Gradle 与版本核对补充

```gradle
// Gradle 等价引入
implementation 'org.springframework.boot:spring-boot-starter-aop'
```

| 工具 | 核对版本命令 |
|------|-------------|
| Maven | `mvn dependency:tree -Dincludes=org.aspectj,org.springframework:spring-aop` |
| Gradle | `./gradlew dependencies --configuration runtimeClasspath`（grep aspectj） |
| 冲突仲裁 | 以 Boot BOM 锁定的版本为准，`-Dverbose` 看仲裁过程 |

> ⚠️ 提醒：Gradle 下若手动覆盖 aspectjweaver 版本，注意与 spring-aspects 的 **runtime scope 传递关系**——显式声明时保持与 Spring 主版本配套。

### 5.4 纯 Spring 最小可运行 pom 片段

```xml
<!-- 纯 Spring + 注解式 AOP 的最小依赖（不写版本则交给 BOM 管理） -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context</artifactId>
    <version>7.0.x</version>
</dependency>
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-aspects</artifactId>
    <version>7.0.x</version>
</dependency>
```

```text
配合代码侧的最小启动条件：
  ① 配置类标注 @EnableAspectJAutoProxy
  ② @Aspect 切面类注册为 Bean
  ③ 目标 Bean 从容器取用
```

> 🎯 这份最小组合 = "容器 + 注解模型"双齐备——任何缺项都对应一类典型启动报错，可作为纯 Spring 项目的 AOP 基线模板。

### 5.5 一句话选型总结

| 你的情况 | 结论 |
|---------|------|
| Boot 项目，写 @Aspect | spring-boot-starter-aop |
| Boot 项目，只用事务/缓存 | 什么都不加（传递依赖已带） |
| 纯 Spring，注解式 | spring-context + spring-aspects |
| 纯 Spring，XML/编程式 | spring-aop |
| 任何项目要 LTW | 再加 aspectjweaver + javaagent |
| 只想在 XML 里配 `<aop:config>` | spring-aop 即可（无需 aspects） |
| 只想验证代理是否生成 | 代码里 `AopUtils.isAopProxy(bean)` 判断 |

> 🎯 全表浓缩：**Boot 用 starter，纯 Spring 用 aspects，特殊场景才手动碰 aspectjweaver**——选依赖只需这一行。
