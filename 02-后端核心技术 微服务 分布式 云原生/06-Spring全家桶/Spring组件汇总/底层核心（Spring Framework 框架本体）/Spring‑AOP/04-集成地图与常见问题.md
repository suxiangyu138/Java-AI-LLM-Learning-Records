## 1. 集成地图

```text
调用链：
  外部 Bean → Spring 代理（CGLIB 默认）→ 通知链 → 目标方法

同一代理上叠加的横切能力（执行顺序）：
  @Transactional（事务）→ @Cacheable（缓存）→ @PreAuthorize（安全）→ @Async（异步）→ 业务
  顺序由 @Order 与切面声明共同决定

地基关系：
  一切代理注解 → AbstractAutoProxyCreator → ProxyFactory → CGLIB
  （@Transactional/@Cacheable/@Async/@PreAuthorize/@Retryable 共用同一织入机制）
```

### 1.1 多能力叠加时的代理链（洋葱模型）

事务、缓存、安全、异步同时命中一个方法时，代理链呈"洋葱"结构——外层切面先 before、后 after：

```text
外部调用
  → 安全切面（鉴权，最外优先）          before 顺序
  → 缓存切面（查缓存/写缓存）
  → 事务切面（开启/提交/回滚）
  → 目标业务方法
  返回时逆序：业务 → 事务提交 → 缓存写入 → 安全后置
```

| 组合 | 典型坑 |
|------|--------|
| @Transactional + @Cacheable | 缓存写入先于事务提交 → 事务回滚后缓存残留未提交数据 |
| @Async + @Transactional | 异步方法在新线程执行，事务边界与调用方无关 |
| @PreAuthorize + 事务 | 鉴权失败在事务开启前抛出，不会产生空事务 |

> 💡 实际顺序由各切面 Advisor 的排序决定（@Order 可调），上图是典型默认姿态——需要自定义顺序时用 `@EnableTransactionManagement(order=...)` 或自定义切面的 @Order 干预。

### 1.2 代理链 vs 调用链 vs 事务传播链

三个"链"容易混，划清边界是面试加分点：

| 概念 | 含义 | 关注点 |
|------|------|--------|
| 代理链（Advisor 链） | 同一代理上挂载的所有通知的有序集合 | 顺序、嵌套 |
| 调用链（ReflectiveMethodInvocation） | 一次方法调用实际执行的拦截器序列 | 参数传递、异常传播 |
| 事务传播链 | 跨 Bean 调用时事务上下文的传递 | REQUIRED/NESTED 等传播行为 |

> 💡 一句话区分：**AOP 解决"方法级"横切，事务传播解决"跨方法"状态传递**——先走代理链进入事务，再在业务方法间按传播规则延续。

## 2. 与声明式能力的集成

| 能力 | 代理注解 | 与 AOP 的关系 | 联动文档 |
|------|---------|-------------|---------|
| 事务 | `@Transactional` | 事务管理器 + 事务切面（最经典 AOP 应用） | [Spring框架核心-06](../../../Spring框架核心/06-声明式事务管理.md) |
| 缓存 | `@Cacheable` 等 | 缓存切面（AnnotationCacheAspect） | Spring Data Redis 06 篇 |
| 异步 | `@Async` | 异步执行器切面（AnnotationAsyncExecutionInterceptor） | [Spring Task-04](../../../Spring Task/04-异步任务：@Async与线程池.md) |
| 安全 | `@PreAuthorize` | 方法安全切面（AuthorizationManagerBeforeMethodInterceptor） | [Spring Security-04](../../../Spring Security与Spring Security OAuth2/04-方法级安全：@EnableMethodSecurity与表达式.md) |
| 重试 | `@Retryable` | 重试切面（7.0 起 CGLIB 一致） | — |
| 事件 | `@EventListener` | 不依赖 AOP（观察者模式） | [Spring框架核心-07](../../../Spring框架核心/07-事件驱动机制.md) |

> 🎯 **要点**：AOP 是这些能力的"织入器"——它们的**失效原因 90% 相同**（自调用/代理未开），一份排障经验全通用。

### 2.1 声明式注解 → 底层拦截器对照

| 注解 | 底层拦截器/切面 | 代理装配方式 |
|------|----------------|-------------|
| @Transactional | TransactionInterceptor | 全局自动代理链路（InfrastructureAdvisorAutoProxyCreator） |
| @Cacheable 等 | CacheInterceptor | 注册缓存 Advisor，自动代理拾取 |
| @Async | AnnotationAsyncExecutionInterceptor | 专用后置处理器（AsyncAnnotationBeanPostProcessor） |
| @Retryable | RetryOperationsInterceptor | @EnableRetry 注册 Advisor |
| @PreAuthorize | AuthorizationManagerBeforeMethodInterceptor | 方法安全拦截器注册 |

> 💡 启示：事务、缓存、重试走**全局自动代理链路**（与 @Aspect 同源）；异步、安全走**专用装配**——失效表现与排查入口因此不同：前者查 AutoProxyCreator 与切点，后者查对应后置处理器/拦截器是否注册。

### 2.2 事务事件：AOP 与事件的交汇

`@TransactionalEventListener` 依赖事务切面把监听器注册进"事务同步"（TransactionSynchronization），是 AOP 事务能力的下游扩展：

```text
@Transactional 方法提交成功
  → TransactionSynchronization 同步回调
  → @TransactionalEventListener(phase = AFTER_COMMIT) 收到事件
```

| 阶段常量 | 触发时机 | 典型用途 |
|---------|---------|---------|
| BEFORE_COMMIT | 事务提交前 | 少见 |
| AFTER_COMMIT | 提交成功后 | **"事务内发消息"经典问题的解法** |
| AFTER_ROLLBACK | 回滚后 | 失败补偿 |
| AFTER_COMPLETION | 无论成败 | 兜底清理 |

> 💡 "事务内发 MQ 消息、提交前消费者已读到脏数据"的经典问题，就用 `@TransactionalEventListener(phase = AFTER_COMMIT)` 解决——消息只在事务真正提交后才发出。

## 3. 代理失效五大坑

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 1 | **同类自调用** | `this.method()` 绕过代理，注解静默失效 | 注入自身代理 / 拆类 / `AopContext.currentProxy()` |
| 2 | private / final 方法 | CGLIB 无法增强 | 方法改 public 非 final |
| 3 | 代理未开启 | `spring.aop.auto=false` 或未加 starter-aop | 检查配置与依赖 |
| 4 | 静态方法 | 代理不拦截静态方法 | 改为实例方法 |
| 5 | 新对象绕过容器 | `new Xxx()` 直接调用 | 一律从容器取 Bean |

```java
// 坑 1 的正确解法（三种）
@Service
public class OrderService {

    @Resource
    private OrderService self;                    // ① 注入自身代理

    public void create() {
        self.update();                            // 走代理 → @Transactional 生效
    }

    @Transactional
    public void update() { ... }
}

// ② 拆类：事务逻辑放独立 Bean
// ③ AopContext.currentProxy()（需 exposeProxy=true，最后手段）
```

> ⚠️ **坑 1 是生产头号事故**：代码看起来对、注解也写了、就是不生效——**"调自己"是最隐蔽的代理绕过**。排查第一问："这个方法是不是从外部 Bean 进来的？"

### 3.1 深水区失效场景

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 6 | 构造器/@PostConstruct 内自调用 | 初始化阶段调本类代理方法不生效 | 拆独立 Bean；或 ApplicationRunner 事后调用 |
| 7 | 泛型桥方法 | 泛型接口实现出现桥方法，execution 签名匹配混乱 | 优先注解驱动切点 |
| 8 | 内部类方法 | 内部类不属于代理范围 | 内部类提升为独立 Bean |
| 9 | 依赖 JDK 代理时强转具体类 | ClassCastException | 用接口类型接收，或统一 CGLIB |
| 10 | @Around 吞异常 | catch 后不抛出 → 事务不回滚、安全后置失效 | catch 后 rethrow（或按需标记回滚） |
| 11 | 循环依赖 + 代理 | 三级缓存提前暴露原始对象，代理后置 | 重构依赖；@Lazy 延迟注入 |

### 3.2 CGLIB 为何不能代理 private/final/static（原理级）

CGLIB 的增强手段是**生成目标类子类并覆写方法**——凡子类无法覆写的方法都天然在代理范围之外：

| 方法形态 | 子类可覆写？ | 原因 |
|---------|:---:|------|
| public | ✅ | 标准覆写 |
| protected | ✅ | 子类可见（同包/子类） |
| private | ❌ | 子类不可见 |
| static | ❌ | 不参与实例方法分派 |
| final | ❌ | Java 语法禁止覆写 |

> 🎯 推论：private/static/final 方法被切点表达式"匹配"也不会织入——**不是报错，是静默跳过**；因此"写了切面没效果"时，先查方法修饰符再查表达式。

### 3.3 自调用三种解法的取舍

| 解法 | 优点 | 缺点 |
|------|------|------|
| 注入自身代理（self） | 简单直观、无需配置 | 引入自我依赖（Spring 6 保留自注入，但需团队约定） |
| 拆类（独立 Bean） | 最干净、无任何魔法 | 类结构调整成本 |
| `AopContext.currentProxy()` | 不改结构、一处配置全局生效 | 需 exposeProxy；异步线程拿不到 |

> 💡 推荐序：**拆类 > 注入自身代理 > AopContext**——前两者没有隐藏状态，第三种是"最后一招"；代码评审时看到 AopContext 应追问"为什么不用拆类"。

### 3.4 标准面试答案：自调用为什么失效

```text
调用流程对比：
  外部调用：调用方 → 容器中的代理（事务通知开启事务）→ 目标方法   ✅ 生效
  自调用：  this.update() 直接命中原始对象的方法实现            ❌ 绕过代理

本质：this 关键字绑定的是"当前对象"，而 Bean 初始化后容器把引用
换成了代理——this 仍是原始对象，通知链根本没有入口。
```

| 层次 | 解释 |
|------|------|
| 表现层 | 注解写了、代码对了、就是不生效 |
| 机制层 | `this` 指向原始对象，代理的通知链未进入 |
| 原理层 | Bean 后置处理替换容器中的引用，但 `this` 引用不会跟着换 |

> 🎯 面试答到这"三层递进"即满分：先现象、再机制、后原理——背答案只能到第二层，能讲清"this 不随容器替换"才说明真懂代理。

## 4. 高频问题速查

| 现象 | 根因 | 处理 |
|------|------|------|
| @Aspect 切面不执行 | 未加 spring-boot-starter-aop / 未注册 Bean | 加依赖；@Aspect 类标注 @Component |
| @Transactional 不生效 | 自调用 / 方法非 public | 见 3.1 坑 |
| 切点表达式没匹配上 | 包名/方法签名写错 | 用 `execution(* com.demo..*(..))` 调试到最小集 |
| 代理对象类型不对 | JDK 代理 vs CGLIB 混用（6.x） | 7.x 已统一 CGLIB；存量用 @Proxyable 显式控制 |
| 两个切面顺序不对 | 未定义 @Order | @Order 数字小的先执行 |
| @Around 里没调 proceed | 目标方法不执行 | 环绕通知必须 proceed() |
| 切面里拿不到注解参数 | 绑定方式错误 | `@Around("@annotation(xxx)")` + 同名参数绑定 |
| 异常被 @Around 吞掉 | catch 后不 rethrow | 事务/安全感知的异常必须继续抛出 |
| 代理对象序列化/类型判断异常 | CGLIB 子类 | 用接口类型/`AopUtils.isAopProxy` 判断 |

### 4.1 面试追问点

| 追问 | 参考回答 |
|------|---------|
| 自调用为何是头号事故？ | 编译期无提示、运行期静默失效、现象像"注解没写" |
| @Transactional + @Cacheable 同用注意什么？ | 缓存写入先于事务提交（默认姿态），回滚后缓存残留脏数据 |
| 如何确认 Bean 确实被代理？ | `AopUtils.isAopProxy(bean)`；断点 wrapIfNecessary |
| 代理失效排查第一问？ | "这个方法是不是从容器外部、经代理对象调进来的？" |
| Spring AOP 与 AspectJ 什么关系？ | 借 AspectJ 注解语法与表达式解析，织入仍是动态代理 |

### 4.2 与测试的交互

| 场景 | 注意点 |
|------|--------|
| @SpringBootTest 集成测试 | 代理照常生效，无需特殊处理 |
| Mockito 单测（mock 对象） | mock 不是代理，切面不执行——测切面逻辑单独写测试 |
| @MockBean 注入容器 | 替换的是容器 Bean，代理链路仍可用 |
| 代理类型断言 | 用 `AopUtils.isAopProxy` / `AopUtils.getTargetClass`，别用 getClass() |
| 异步方法内断言 | @Async 线程内无 AopContext——需要代理语义用 self 注入 |
| 集成测试验证切面 | 用 @SpringBootTest 断言通知副作用（日志/计数/缓存行为） |

> ⚠️ 常见误判：单测里"切面没生效"以为代码有 bug——**单测 mock 绕过了容器，本来就该不生效**；验证切面请用集成测试或对切面类直接单测。

## 5. 排障流程

```text
① 确认代理存在：启动日志或断点 AbstractAutoProxyCreator
   （或 AopUtils.isAopProxy(bean) == true）
② 确认调用路径：是否从容器 Bean 外部进入（自调用检查）
③ 确认切点命中：切点表达式逐步放宽（execution → within → bean）定位
④ 确认通知顺序：多切面时检查 @Order 与同类通知顺序
⑤ 回归验证：@Aspect 切面加日志，观察织入前后行为
```

> 🎯 **速查结论**：AOP 集成地图一句话——**所有声明式能力共用一套代理织入机制**，失效原因高度同源（自调用、private/final、代理未开）。排障先答三问：代理存在吗？从外部调的吗？切点命中了吗？

### 5.1 调试工具清单

| 工具 | 用法 | 目的 |
|------|------|------|
| `AopUtils.isAopProxy(bean)` | 代码内判断 | 确认代理是否存在 |
| `AopUtils.getTargetClass(bean)` | 取真实目标类 | 确认代理链目标 |
| 断点 `wrapIfNecessary` | 观察匹配到的 Advisor | 代理创建全过程 |
| 断点 `ReflectiveMethodInvocation.proceed` | 观察通知链 | 切面顺序与参数 |
| `logging.level.org.springframework.aop=DEBUG` | 启动日志 | 观察 Advisor 装配 |

### 5.2 生产实战经验

- **先加日志再排查**：线上"AOP 不生效"，先给切面加 before/after 日志确认织入与否，比逐行读代码快；
- **最小复现**：把切点放宽到 `execution(* com.demo..*(..))` 验证框架链路，再逐步收紧，快速定位表达式错误；
- **升级台账**：6.x → 7.x 前审计"依赖 JDK 代理语义"的代码（类型强转、Proxy.isProxyClass、序列化）；
- **监控兜底**：关键切面加 metrics 埋点——切面失效时监控曲线（耗时、事务数）会先暴露异常，比用户报障更早。

### 5.3 排障实战案例

| 案例 | 现象 | 排查过程 | 根因 |
|------|------|---------|------|
| A | 订单状态更新无事务 | 断点 wrapIfNecessary 确认代理存在 → 检查调用路径 → 发现内部方法 `this` 调用 | 同类自调用 |
| B | 切面只对部分方法生效 | 表达式 `execution(* com.demo.service.*.*(..))` 只匹配一层 → 子包方法全部未命中 | 缺 `..` |
| C | 升级 7.x 后启动抛 ClassCastException | 启动日志显示 JDK 代理 → 审计代码发现 `(UserServiceImpl) service` 强转 | 强转具体类 |
| D | 事务回滚了但缓存未清 | 同方法 @Transactional + @Cacheable → 缓存写入先于提交 | 组合顺序问题 |

> 🎯 共性规律：**四个案例中三个的根因不在框架，而在"调用路径/表达式/类型使用"**——排障时先怀疑自己的代码，再怀疑框架。

### 5.4 排障口诀

```text
一查代理存不存在（AopUtils.isAopProxy）
二查入口是不是外部 Bean（自调用检查）
三查方法是不是 public 非 final（修饰符检查）
四查切点有没有命中（放宽表达式定位）
五查顺序对不对（@Order 与同类通知顺序）
```

> 🎯 口诀配合 5 步流程使用：**先"三问"（代理、入口、切点），再"两查"（修饰符、顺序）**——90% 的 AOP 失效问题落在前三个环节。
