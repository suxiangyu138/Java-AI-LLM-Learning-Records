## 1. spring.aop.* 属性表

```yaml
spring:
  aop:
    auto: true                  # 是否启用自动代理（默认 true）
    proxy-target-class: true    # 是否强制 CGLIB 代理（7.x 默认一致）
```

| 属性 | 默认 | 说明 |
|------|:---:|------|
| `spring.aop.auto` | true | 关闭后所有代理注解失效（@Transactional/@Async 等） |
| `spring.aop.proxy-target-class` | true（7.x 一致默认） | false = 有接口时优先 JDK 动态代理 |

> ⚠️ **注意**：`proxy-target-class=false` 在 7.x 与 CGLIB 一致默认冲突时，以更细粒度的 `@Proxyable` 为准——**全局属性用于兼容存量，细粒度用注解**。

### 1.1 属性来源与生效链路

`spring.aop.*` 由 Boot 的 `AopAutoConfiguration` 读取并装配到 `AnnotationAwareAspectJAutoProxyCreator`：

```text
application.yml
  → AopAutoConfiguration（条件装配：类路径存在 spring-aop 且 spring.aop.auto=true）
  → 创建 AnnotationAwareAspectJAutoProxyCreator
  → 写入 exposeProxy / proxyTargetClass
  → 注册为 BeanPostProcessor
  → 容器启动后参与每个 Bean 的代理决策
```

| 属性 | 生效时机 | 运行时可改？ |
|------|---------|:---:|
| spring.aop.auto | 启动期 | ❌ 需重启 |
| spring.aop.proxy-target-class | 启动期 | ❌ 需重启 |

> 💡 两个属性都是**启动时一次性读取**——运行时改 Environment 不生效；排查"改了配置没效果"先想到这一点，其次检查是否有更细粒度的配置（@Proxyable / 编程式）覆盖。

### 1.2 多环境写法对照

同一配置在不同环境载体中的写法（优先级从低到高，高者覆盖低者）：

| 载体 | 写法 | 优先级 |
|------|------|:---:|
| application.yml | `spring.aop.proxy-target-class: true` | 低 |
| application.properties | `spring.aop.proxy-target-class=true` | 低 |
| 环境变量 | `SPRING_AOP_PROXY_TARGET_CLASS=true` | 中 |
| 命令行参数 | `--spring.aop.proxy-target-class=true` | 高 |
| 配置中心（Nacos 等） | 覆盖本地同名 key | 视实现而定 |

> 💡 生产环境建议：**代理方式这种"全链路一致性"配置放配置中心统一管理**——测试与生产代理方式不一致，是"测试过、生产挂"的常见来源。

### 1.3 常见错误配置速查

| 错误写法 | 后果 | 正确做法 |
|---------|------|---------|
| `proxy-target-class=false` 且存在 final 类 | 启动报错或静默不代理 | 去掉 final 或保持 CGLIB |
| 手误关闭 `spring.aop.auto=false` | 所有代理注解失效（事务/缓存全挂） | 保持默认 true |
| 依赖运行时动态改属性 | 无效（启动期读取） | 重启，或用 @Proxyable/编程式 |
| 全局 false + @Proxyable(true) 混用 | 以 @Proxyable 为准（易误解） | 先读优先级表再配置 |

### 1.4 属性命名与松弛绑定

Boot 的 Relaxed Binding 让同一属性有多种等价写法，**一切以 `spring.aop.*` 前缀 + 驼峰/中划线/下划线等价**为准：

| 写法 | 是否等价 |
|------|:---:|
| `spring.aop.proxy-target-class` | 基准写法 |
| `spring.aop.proxyTargetClass` | ✅ 等价 |
| `SPRING_AOP_PROXYTARGETCLASS`（环境变量） | ✅ 等价 |
| `spring.aop.proxy_target_class` | ✅ 等价 |

> 💡 知道这一点可以避免"照着文档写却读不到"的困惑；也解释了为什么环境变量注入 Spring 配置如此省事（前缀大写 + 去分隔符即可）。

### 1.5 配置最终落到 ProxyFactory 的开关

```java
// 编程式等价（仅供理解，业务不这么写）
ProxyFactory factory = new ProxyFactory();
factory.setProxyTargetClass(true);   // = spring.aop.proxy-target-class=true
factory.setExposeProxy(true);        // = @EnableAspectJAutoProxy(exposeProxy=true)
```

| 配置形态 | 落到哪 | 粒度 |
|---------|--------|:---:|
| spring.aop.auto | 是否注册 AutoProxyCreator | 全局 |
| spring.aop.proxy-target-class | setProxyTargetClass | 全局 |
| @Proxyable | BeanDefinition 属性 | Bean |
| 编程式 ProxyFactory | 直接调用 | 对象 |

> 🎯 对照结论：**所有配置最终都落到 ProxyFactory 的几个开关上**——配置文件与注解只是这些开关的"声明式入口"，理解了这一点，配置优先级（编程式 > Bean 级 > 全局）就不需要背。

## 2. 代理类型决策

```text
Spring 7.x 默认：CGLIB（所有代理注解一致）

选择代理方式的层级（从宽到细）：
  ① 全局：spring.aop.proxy-target-class
  ② Bean 级：@Proxyable(proxyTargetClass = ...)（7.0 新）
  ③ 编程式：ProxyFactory.setProxyTargetClass(...)

何时需要 JDK 接口代理？
  - 依赖 JDK Proxy 语义的存量代码（Proxy.isProxyClass 判断）
  - 目标类 final / 私有构造（CGLIB 无法继承）
  - 特殊字节码增强工具兼容
```

| 代理方式 | 原理 | 限制 |
|---------|------|------|
| CGLIB（默认） | 生成目标类子类 | 目标类不能 final；方法不能 final/private |
| JDK 动态代理 | 实现接口 | 目标类必须实现接口；只代理接口方法 |

> 💡 **记忆**：CGLIB 管"类"，JDK 代理管"接口"——7.x 默认 CGLIB 后，**final 类/方法是唯一的代理禁忌**。

### 2.1 JDK 动态代理与 CGLIB 深层差异

| 维度 | JDK 动态代理 | CGLIB |
|------|-------------|-------|
| 原理 | 生成接口实现类（Proxy 子类） | 生成目标类子类并覆写方法 |
| 代理范围 | 仅接口方法 | 类方法（public/protected） |
| 目标类要求 | 必须实现接口 | 不能 final、不能私有构造 |
| 方法限制 | — | 不能 final / private / static |
| 类型识别 | `Proxy.isProxyClass` 可识别 | 代理类是目标类的子类 |
| 创建/调用性能 | 创建快、调用略慢（反射分发） | 创建慢、调用快（FastClass 索引） |
| 强转语义 | 只能转接口类型 | 可转具体类（子类） |

> 🎯 一句话：**JDK 是"照着接口造一个实现"，CGLIB 是"复制一个子类再改"**——前者管接口、后者管类；这也是"强转具体类"只在 JDK 代理下报 ClassCastException 的原因。

### 2.2 生产环境代理方式选型建议

| 场景 | 建议 |
|------|------|
| 新项目（Boot 4.x） | 零配置：CGLIB 默认即正确 |
| 存量项目升 7.x | 先全局 CGLIB 跑测试，再按报错逐个 @Proxyable 微调 |
| 强依赖接口契约的组件 | `@Proxyable(proxyTargetClass = false)` 显式 JDK |
| final 类无法代理 | 调整设计去掉 final，或改用 AspectJ LTW（不推荐） |
| 测试环境 | 显式配置与生产一致，避免"测试过、生产挂" |

### 2.3 CGLIB 代理对象的语义差异

Bean 被代理后，业务代码拿到的对象与原始对象在部分语义上有差异，容易踩坑：

| 行为 | 原始对象 | CGLIB 代理对象 |
|------|---------|---------------|
| equals/hashCode | 默认（比较引用） | 代理覆写后委托目标 |
| toString | 自定义实现 | 委托目标（含代理信息） |
| `instanceof 目标类` | true | true（代理是子类） |
| `getClass()` | 目标类 | 代理子类（`UserService$$EnhancerByCGLIB`） |
| 字段直接访问 | 可直接访问 | 代理不复制字段值，需走方法 |

> ⚠️ 注意：**代理对象的 `getClass()` 不等于目标类**——序列化框架按 `getClass()` 反射（部分 JSON 库、JPA 实体懒加载）时需适配；判断类型一律用 `instanceof` 或接口类型，不要用 `getClass()`。

### 2.4 必须 JDK 代理的少数场景

| 场景 | 说明 |
|------|------|
| 第三方框架要求接口类型 | 部分 RPC/序列化框架按接口反射 |
| 依赖 `Proxy.isProxyClass` 的存量代码 | 判断逻辑按 JDK 代理编写 |
| 目标类 final 但已有接口 | 唯一还能代理的路：走接口（JDK 代理不继承目标类） |
| 动态字节码工具冲突 | 个别 CGLIB 增强链冲突场景 |

> ⚠️ 澄清常见误区：**final 类 + 有接口 = 可以 JDK 代理**（JDK 代理不生成目标类的子类，只实现接口）——这不是"完全无法代理"，只是 7.x 全局 CGLIB 下需显式 `@Proxyable(false)` 才生效。

### 2.5 代理方式性能参考

| 指标 | JDK 动态代理 | CGLIB |
|------|:---:|:---:|
| 代理创建耗时 | 快 | 慢（生成子类字节码） |
| 单次调用耗时 | 略慢（反射 InvocationHandler） | 快（FastClass 直接索引） |
| 内存占用 | 小 | 大（额外子类与 FastClass） |
| 缓存友好度 | 中 | 高 |

> 💡 结论：**热路径上 CGLIB 略优，冷启动上 JDK 略优**——差异在微秒级以下，业务上基本无感；选型以"语义正确"为准，别为性能选代理方式。

### 2.6 代理方式决策速记

| 场景 | 结论 |
|------|------|
| 默认（99% 的 Bean） | CGLIB，什么都不配 |
| 有接口 + 需兼容存量 JDK 语义 | `@Proxyable(proxyTargetClass = false)` |
| final 类 | 去 final 或改设计（无法代理） |
| 有性能焦虑 | 差异在微秒级以下，别为此选型 |
| 测试/生产不一致 | 必须统一，先改测试环境 |
| 多环境切换 | 用配置中心统一管理代理方式，禁止各环境各自为政 |

> 🎯 一句话：**决策顺序 = 默认 CGLIB → 例外 @Proxyable → 特殊编程式**——99% 的代码走第一行。

## 3. @EnableAspectJAutoProxy 配置

```java
// 显式开启（Boot 自动，无需写）
@Configuration
@EnableAspectJAutoProxy(
    proxyTargetClass = true,     // 同 spring.aop.proxy-target-class
    exposeProxy = true)          // 暴露代理到 AopContext（解自调用）
public class AopConfig { }
```

| 属性 | 说明 | 场景 |
|------|------|------|
| `proxyTargetClass` | CGLIB 开关 | 全局默认 |
| `exposeProxy` | 暴露 `AopContext.currentProxy()` | **解同类自调用**（生产建议开启） |

```java
// exposeProxy 解自调用
@Service
public class OrderService {
    public void create() {
        // this.update() 不生效 → 用 AopContext.currentProxy()
        ((OrderService) AopContext.currentProxy()).update();
    }
    @Transactional
    public void update() { ... }
}
```

> ⚠️ **AopContext 注意**：必须 `exposeProxy=true` 且调用发生在代理执行链内；更干净的解法是**注入自身代理**或拆类——AopContext 是"最后一招"。

### 3.1 exposeProxy 的线程边界

| 调用场景 | 能拿到 currentProxy()？ |
|---------|:---:|
| 代理调用链内（同线程同步调用） | ✅ |
| @Async 异步方法内部 | ❌（新线程，ThreadLocal 隔离） |
| 手动 new Thread 内 | ❌ |
| 代理调用链外（普通 Bean 方法） | ❌ 抛 IllegalStateException |

> ⚠️ 常见误用：在 @Async 方法里调 `AopContext.currentProxy()` 必然失败——代理调用发生在调用方线程，异步执行在线程池新线程中。异步方法内部需要代理语义时，应注入自身代理（self 注入），而不是依赖 AopContext。

### 3.2 Boot 自动配置 vs 手动 @EnableAspectJAutoProxy

| 维度 | Boot 自动配置 | 手动注解 |
|------|-------------|---------|
| 触发方式 | `AopAutoConfiguration` 条件装配 | 显式标注在 @Configuration 上 |
| 属性来源 | `spring.aop.*` 配置文件 | 注解属性（proxyTargetClass/exposeProxy） |
| 共存规则 | 检测到已注册的 AutoProxyCreator 时自动放弃（条件不满足） | 手动标注优先 |
| 适用 | Boot 项目（默认，无需写） | 纯 Spring 项目 / 需要差异化配置 |

> 💡 纯 Spring 项目没有 AopAutoConfiguration，**必须手动 @EnableAspectJAutoProxy**——这也是"切面在 Boot 正常、在纯 Spring 项目不生效"的常见根因。

### 3.3 纯 Spring 项目最小可运行配置

```java
@Configuration
@EnableAspectJAutoProxy(proxyTargetClass = true, exposeProxy = true)
@EnableTransactionManagement
public class AppConfig { }
```

```text
纯 Spring 项目 AOP 生效三要件：
  ① @EnableAspectJAutoProxy（核心开关，不可缺）
  ② 切面 Bean 必须被容器管理（@Component 或 @Bean 注册）
  ③ 目标 Bean 必须从容器取用（不能 new 出来再调）
```

> ⚠️ 三要件缺一即静默失效——纯 Spring 项目排障先对着这三条逐项核对，比翻日志快。

### 3.4 完整组合示例：exposeProxy + 事务自调用

```java
// 配置侧：开启 exposeProxy
@Configuration
@EnableAspectJAutoProxy(exposeProxy = true)
public class AopConfig { }

// 业务侧：自调用场景用 AopContext 解围
@Service
public class OrderService {
    public void create() {
        ((OrderService) AopContext.currentProxy()).update();   // 走代理 → 事务生效
    }
    @Transactional
    public void update() { }
}
```

> 🎯 这是"配置 + 代码"的组合拳：一处 `exposeProxy=true`，换来所有自调用场景的逃生通道——代价是代码里出现强转与魔法调用，**能拆类就不要用它**。

### 3.5 生产中 exposeProxy 的开与关

| 决策 | 建议 |
|------|------|
| 新项目 | 直接开启（成本极低，自调用兜底） |
| 存量项目 | 按需开启；先修复已知自调用代码 |
| 安全敏感环境 | 评估 ThreadLocal 内容暴露面（存的是代理引用，7.x 已完善清理逻辑） |
| 纯查询服务（无事务/无切面） | 不需要开启，保持默认 |

> 💡 建议把 `exposeProxy` 视为"默认开启的保险丝"而非"危险开关"——真正需要警惕的是业务代码依赖它而不做结构治理。

## 4. 与 7.x @Proxyable 的配合

```java
// 全局 CGLIB 默认 + 个别 Bean 需要接口代理
@Proxyable(proxyTargetClass = false)
@Service
public class LegacyService implements LegacyApi { ... }

// 显式声明 CGLIB（防 final 类意外无法代理）
@Proxyable(proxyTargetClass = true)
@Service
public class ConcreteService { ... }
```

| 层级 | 优先级 |
|------|:---:|
| 编程式 ProxyFactory | 最高 |
| @Proxyable（Bean 级） | 中 |
| spring.aop.proxy-target-class（全局） | 低 |

> 🎯 **速查结论**：Boot 项目**通常零 AOP 配置**（auto=true + CGLIB 默认即正确）；要动的只有两处——`exposeProxy`（解自调用）与个别 Bean 的 `@Proxyable`（7.0 细粒度代理控制）。

### 4.1 @Proxyable 使用边界

| 场景 | 推荐写法 | 说明 |
|------|---------|------|
| 绝大多数 Bean | 不写 | 默认 CGLIB，最简 |
| 有接口且需 JDK 语义 | `@Proxyable(proxyTargetClass = false)` | 兼容存量 JDK 代理代码 |
| final 类 | 无法代理 | CGLIB 与 JDK 都不行，需调整设计 |
| 第三方类（无法加注解） | 全局属性或编程式 | @Proxyable 只能标注自己的 Bean |
| 配置类 | 一般无需标注 | 配置类默认已 CGLIB 增强 |

> 💡 @Proxyable 与全局属性是"互补"而非"二选一"：全局属性管默认基线，@Proxyable 管个别例外——升级 7.x 时按"全局 CGLIB + 例外 Bean 显式 JDK"的姿势推进，改动面最小。

### 4.2 面试追问点

| 追问 | 参考回答 |
|------|---------|
| proxy-target-class=false 影响什么？ | 有接口的 Bean 改用 JDK 代理，非接口方法不生效 |
| 全局属性与 @Proxyable 冲突听谁的？ | @Proxyable（Bean 级粒度更细，优先级更高） |
| 为什么 7.x 统一 CGLIB？ | 消除同 Bean 不同注解代理方式混差，行为可预测、问题可排查 |
| exposeProxy 有性能损失吗？ | 可忽略（调用链内一次 ThreadLocal set/remove） |

### 4.3 @Proxyable 的处理流程（源码级）

```text
@Proxyable 标注的 Bean
  → 配置解析阶段读取注解（与 @Service 等同期处理）
  → 把 proxyTargetClass 等属性记录到 BeanDefinition
  → AbstractAutoProxyCreator 创建代理时读取 BeanDefinition 属性
  → Bean 级代理方式生效（覆盖全局 spring.aop.proxy-target-class）
```

| 层级 | 读取位置 | 优先级 |
|------|---------|:---:|
| @Proxyable | BeanDefinition 属性 | 高 |
| spring.aop.proxy-target-class | 全局配置 | 低 |
| ProxyFactory.setProxyTargetClass | 编程式代码 | 最高（代码内直接决定） |

> 🎯 理解这个流程就明白：**@Proxyable 是"BeanDefinition 级"的配置**——它随 Bean 定义走，天然支持"同一种 Bean 不同实例不同代理方式"（如原型作用域），这是全局属性做不到的。

### 4.4 升级 7.x 配置迁移速查

| 6.x 存量写法 | 7.x 推荐做法 |
|-------------|-------------|
| 全局 `spring.aop.proxy-target-class=false` | 拆到个别 Bean 的 `@Proxyable(false)` |
| 依赖"某些注解是 JDK 代理"的行为 | 审计后统一 CGLIB，例外用注解 |
| 强转具体类的存量代码 | 改接口类型 / 统一 CGLIB 后验证 |
| 无细粒度控制手段 | 用 @Proxyable 表达意图 |

### 4.5 常见疑问

| 疑问 | 解答 |
|------|------|
| @Proxyable 能标在方法上吗？ | 不能，是类级注解 |
| 全局属性改了，@Proxyable 会自动同步吗？ | 不会，两者独立生效 |
| @Proxyable 在 6.x 存在吗？ | 不存在，7.0 引入 |
| 编程式 ProxyFactory 与 @Proxyable 冲突？ | 编程式优先（代码内直接决定） |

> 🎯 配置速查最终结论：**默认值全对，别乱动**——真正要动的只有两处：`exposeProxy`（解自调用）与个别 Bean 的 `@Proxyable`（例外代理方式）；配置越少，事故越少。
