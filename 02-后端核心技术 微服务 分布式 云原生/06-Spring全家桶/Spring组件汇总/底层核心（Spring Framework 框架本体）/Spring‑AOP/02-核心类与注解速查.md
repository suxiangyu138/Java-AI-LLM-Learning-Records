## 1. 代理体系

| 类/接口 | 职责 | 说明 |
|---------|------|------|
| `ProxyFactory` | 编程式代理工厂（最底层） | `addAdvice/addAdvisor` + `getProxy()` |
| `ProxyFactoryBean` | XML 时代的代理工厂 Bean | 被注解驱动取代 |
| `AspectJProxyFactory` | @Aspect 风格的编程式代理 | 测试/动态织入场景 |
| `AbstractAutoProxyCreator` | Bean 后置处理器：自动代理入口 | @Transactional/@Aspect 的织入者 |
| `AopProxy` / `CglibAopProxy` / `JdkDynamicAopProxy` | 代理实现 | CGLIB（7.x 默认一致） |
| `AopContext` | 代理上下文（暴露当前代理） | `AopContext.currentProxy()` 解自调用 |

```java
// 编程式代理（理解原理用）
ProxyFactory factory = new ProxyFactory(new UserService());
factory.addAdvice((MethodInterceptor) invocation -> {
    System.out.println("before " + invocation.getMethod().getName());
    return invocation.proceed();
});
UserService proxy = (UserService) factory.getProxy();
```

> 🎯 **要点**：一切声明式注解（事务/缓存/异步/安全）最终都是"某个 AutoProxyCreator 给 Bean 套上代理"——**理解 ProxyFactory 就理解了所有注解式能力的地基**。

### 1.1 AbstractAutoProxyCreator 织入时机（源码级）

自动代理的检查点在 `AbstractAutoProxyCreator#postProcessAfterInitialization`——Bean 初始化（属性填充、Aware 回调、init-method）**完成之后**：

```text
Bean 实例化 → 属性填充 → Aware 回调 → init-method
  → postProcessAfterInitialization(bean, beanName)   ← 织入检查点
      └─ wrapIfNecessary(bean, beanName, cacheKey)
           ├─ 收集所有匹配该 Bean 的 Advisor（逐个切点匹配）
           ├─ 无匹配 → 返回原 Bean（不创建代理）
           └─ 有匹配 → createProxy(...)
                ├─ 组装 ProxyFactory（设置目标/接口/代理方式）
                ├─ 决定 CGLIB 或 JDK 代理（proxyTargetClass 判断）
                └─ 生成代理对象，替换容器中的 Bean
```

> 🎯 三个推论：① 代理在**初始化之后**创建，构造器里自调用天然绕过代理；② `@PostConstruct` 中调用本类方法同样不生效；③ 代理创建失败（如 final 类）在启动期即报错而不是运行时——**启动报错比运行时静默失效好**。

### 1.2 AopContext 底层机制

`AopContext` 本质是一个 `ThreadLocal<Object>`，`exposeProxy=true` 时代理调用入口写入、调用链退出时清理：

| 机制点 | 说明 |
|--------|------|
| 存储 | ThreadLocal，线程内可见 |
| 写入时机 | 代理方法调用入口（要求 exposeProxy=true） |
| 清理时机 | 调用链 finally 中 remove |
| 获取方式 | `AopContext.currentProxy()` 返回当前代理 |
| 陷阱 | 新线程（@Async）内拿不到；调用链外调用抛 IllegalStateException |

```java
// 解自调用的"逃生门"写法
public void create() {
    // this.update() 无效 → 通过代理调用
    ((OrderService) AopContext.currentProxy()).update();
}

@Transactional
public void update() { ... }
```

> 💡 生产建议：`exposeProxy=true` 全局开启成本极低（一个 boolean 属性）；但**首选仍是注入自身代理或拆类**——AopContext 是"最后一招"，且异步场景（@Async 新线程）根本拿不到。

### 1.3 ProxyFactory 内部组装过程（源码级）

`ProxyFactory.getProxy()` 的内部步骤——理解后可以解释"代理的代理"（嵌套代理）现象：

```text
ProxyFactory.getProxy()
  ├─ createAopProxy()                 ← 按 proxyTargetClass 选择实现
  │    ├─ proxyTargetClass=true  → ObjenesisCglibAopProxy（CGLIB）
  │    └─ 否则且有接口            → JdkDynamicAopProxy（JDK 代理）
  └─ aopProxy.getProxy()              ← 生成代理实例（此时不执行通知）
       代理对象持有一条 Advisor 链 → 调用时由 ReflectiveMethodInvocation 按序调度
```

| 组装要素 | 设置方式 |
|---------|---------|
| 目标对象 | `setTarget(target)` / 构造器传入 |
| 代理接口 | `setInterfaces(...)`（JDK 代理必需） |
| 代理方式 | `setProxyTargetClass(true/false)` |
| 通知/切面 | `addAdvice()` / `addAdvisor()` |

> 🎯 关键推论：**代理创建时通知并不执行，只在方法调用时按序调度**——所以"切面日志在启动时看不到"是正常的，运行时才打印。

### 1.4 嵌套代理（代理的代理）

当多个 AutoProxyCreator 依次处理同一 Bean（如事务与自定义切面都命中），会发生**嵌套代理**——代理外面再包代理：

```text
容器中该 Bean 的实际形态：
  外层代理（事务切面）→ 内层代理（自定义切面）→ 原始对象
调用顺序：外层通知 → 内层通知 → 目标方法
```

| 现象 | 原因 | 处理 |
|------|------|------|
| 强转"一层代理"类型失败 | 实际是多层代理叠加 | 用接口类型接收 |
| 断点看对象"包了好几层" | 多个 AutoProxyCreator 都命中 | 正常现象，不要试图消除 |
| 序列化异常 | 嵌套 CGLIB 子类 | 序列化前用 `AopUtils.getTargetClass` 取真实类 |

> 💡 面试加分：能说出"同一 Bean 可能有多个代理层，每层对应一类切面"的人，说明真正理解了 AutoProxyCreator 的叠加机制。

### 1.5 判断 Bean 是否被代理的工具

```java
// 运行时快速判断（排障第一招）
boolean proxied = AopUtils.isAopProxy(bean);       // 是否 AOP 代理
Class<?> target  = AopUtils.getTargetClass(bean);  // 真实目标类（穿透代理）
Object proxy     = AopContext.currentProxy();      // 当前代理（需 exposeProxy=true）
```

| 场景 | 推荐 API |
|------|---------|
| 判断是否代理 | `AopUtils.isAopProxy(bean)` |
| 取真实目标类 | `AopUtils.getTargetClass(bean)` |
| 取当前代理（解自调用） | `AopContext.currentProxy()` |
| 类型判断 | 一律 `instanceof` 接口/目标类，不要用 `getClass()` |

## 2. 切点 Pointcut

| 类/接口 | 用途 |
|---------|------|
| `Pointcut` | 切点抽象（类过滤器 + 方法匹配器） |
| `AspectJExpressionPointcut` | 表达式切点（`execution(...)` 等） |
| `AnnotationMatchingPointcut` | 注解匹配切点 |
| `ComposablePointcut` | 可组合切点（并/交） |
| `PointcutParser` | AspectJ 表达式解析器 |

### 2.1 切点匹配机制对比

| 机制 | 代表实现 | 匹配方式 | 性能 | 适用 |
|------|---------|---------|:---:|------|
| 表达式匹配 | `AspectJExpressionPointcut` | 解析 AspectJ 表达式（execution/within 等） | 中（首次解析后缓存） | 注解切面（默认） |
| 注解匹配 | `AnnotationMatchingPointcut` | 扫描类/方法注解 | 快 | 注解驱动切面 |
| 静态匹配 | `StaticMethodMatcherPointcut` | 类级预过滤 + 方法级匹配 | 最快 | 框架内部（事务切面） |

> 💡 事务切面内部用的是静态方法匹配器（`TransactionAttributeSourcePointcut`），不走表达式解析——这也是事务代理的运行时开销远小于自定义 @Aspect 的原因之一。

### 2.2 命名切点最佳实践

| 实践 | 说明 |
|------|------|
| 集中管理 | 切点方法集中在统一类（如 `Pointcuts`），切面按 `Pointcuts.serviceLayer()` 引用 |
| 命名规范 | `xxxLayer` / `xxxAnnotation` 后缀，一眼看出匹配对象 |
| 组合复用 | 切点可互相组合：`@Pointcut("serviceLayer() && !@annotation(SysLog)")` |
| 访问控制 | 切点方法通常 public 空方法（private 时只能本切面引用） |

> 💡 大型项目把切点集中定义、切面只引用——调整匹配范围时只改一处，避免"表达式散落各切面"的维护灾难。

## 3. 通知 Advice 与五类注解

| 通知类型 | 注解 | 语义 | 典型用途 |
|---------|------|------|---------|
| 前置通知 | `@Before` | 目标方法**执行前** | 校验、记录入参 |
| 返回通知 | `@AfterReturning` | 目标方法**正常返回后** | 记录结果、审计 |
| 异常通知 | `@AfterThrowing` | 目标方法**抛异常后** | 异常上报、回滚辅助 |
| 最终通知 | `@After` | 无论成败**都执行**（finally） | 清理资源 |
| 环绕通知 | `@Around` | **完全包裹**（可控制 proceed） | 计时、限流、重试、事务 |

```java
@Around("@annotation(sysLog)")
public Object around(ProceedingJoinPoint pjp, SysLog sysLog) throws Throwable {
    // 前置逻辑
    Object result = pjp.proceed();      // 执行目标（可传参/可不执行）
    // 后置逻辑
    return result;
}
```

| 通知注解 | 注意点 |
|---------|--------|
| `@Before` | 异常阻止目标执行 |
| `@AfterReturning` | `returning` 属性绑定返回值；方法抛异常则不执行 |
| `@AfterThrowing` | `throwing` 属性绑定异常 |
| `@After` | 类似 finally |
| `@Around` | 必须调用 `proceed()`，否则目标不执行 |

> ⚠️ **执行顺序（重要）**：同一切点多个通知时——`@Around` 包裹 `@Before` → 目标 → `@AfterReturning/@AfterThrowing` → `@After` → 环绕后置。Spring 5.2.7+ 通知执行顺序有变化：**同类内 @Around 先于 @Before**；跨切面按 @Order 排序。

### 3.1 通知方法参数绑定规则

| 想拿什么 | 绑定方式 | 示例 |
|---------|---------|------|
| 方法签名/参数数组 | 直接声明 `JoinPoint` | `@Before(JoinPoint jp)` |
| 目标方法返回值 | `returning` 同名绑定 | `@AfterReturning(returning = "result")` |
| 抛出的异常 | `throwing` 同名绑定 | `@AfterThrowing(throwing = "ex")` |
| 方法入参 | 切点 `args(...)` 绑定 | `args(orderId, ..)` |
| 注解实例 | 切点 `@annotation(...)` 绑定 | `@annotation(sysLog)` |

```java
// 参数绑定完整示例
@Around("@annotation(sysLog) && args(orderId, ..)")
public Object around(ProceedingJoinPoint pjp, SysLog sysLog, Long orderId) throws Throwable {
    System.out.println("注解属性: " + sysLog.value() + ", 业务参数: " + orderId);
    return pjp.proceed();
}
```

> ⚠️ 绑定失败最高频原因：**切点表达式中的绑定名与通知方法参数名不一致**。编译时建议开启 `-parameters`，确保反射拿得到参数名；绑定不上时切点直接判定不匹配（静默，不报错）。

### 3.2 通知执行顺序的验证实验

不背文档也能确认顺序——写一个全通知切面，打印调用轨迹：

```java
@Aspect
@Component
public class OrderTraceAspect {

    @Pointcut("execution(* com.demo.OrderService.create(..))")
    public void pc() { }

    @Before("pc()")         public void b()  { System.out.println("1-before"); }
    @Around("pc()")         public Object a(ProceedingJoinPoint pjp) throws Throwable {
        System.out.println("2-around-before");
        Object r = pjp.proceed();
        System.out.println("6-around-after");
        return r;
    }
    @AfterReturning("pc()") public void ar() { System.out.println("4-returning"); }
    @After("pc()")          public void a2() { System.out.println("5-after"); }
}
// 调用 create() 的输出顺序：1 → 2 → 目标方法 → 4 → 5 → 6
```

> 🎯 实验结果与文档互相印证：**同类内 @Around 先于 @Before 进入（Spring 5.2.7+）**，@AfterReturning 先于 @After 退出——需要精确顺序时跑一遍实验比背文档可靠。

### 3.3 @AfterReturning 的返回值边界

```java
@AfterReturning(pointcut = "pc()", returning = "result")
public void after(JoinPoint jp, Object result) {
    result = null;   // ❌ 无效：只改局部变量，不影响返回值
}
```

| 通知 | 能否改写返回值 |
|------|:---:|
| @AfterReturning | ❌ 只读（返回值已取出） |
| @Around | ✅ 返回什么就是什么 |

> 🎯 需要"改写返回值"（脱敏、包装、兜底默认值）**必须用 @Around**——@AfterReturning 修改局部变量是无效操作，这是高频面试小坑。

## 4. 切面 @Aspect 与 Advisor

| 类/注解 | 职责 |
|---------|------|
| `@Aspect` | 声明切面类 |
| `@Pointcut` | 声明可复用切点方法 |
| `Advisor` / `DefaultPointcutAdvisor` | 切点 + 通知的组装单元（内部结构） |
| `@Order` | 多切面的执行顺序（小值先执行） |
| `@EnableAspectJAutoProxy` | 激活注解切面（Boot 自动开启） |

```java
@Aspect
@Component
@Order(1)                    // 多个切面时的顺序
public class FirstAspect {

    @Pointcut("execution(* com.demo.service..*(..))")
    public void serviceLayer() { }          // 可复用切点

    @Before("serviceLayer()")
    public void before() { }
}
```

> 🎯 **要点**：@Aspect 是"切面定义语法"，Advisor 是"运行时组装单元"——框架把 @Aspect 解析成多个 Advisor 再织入，理解这个映射就能解释切面执行顺序。

### 4.1 多切面执行顺序详解

```text
切面 A（@Order(1)）与切面 B（@Order(2)）同一切点命中时：

  进入顺序（@Before 视角）：      A → B
  目标方法执行
  退出顺序（@AfterReturning 视角）： B → A（逆序，类似栈）

  @Around 视角（洋葱模型）：
  A.around 前置 → B.around 前置 → 目标 → B.around 后置 → A.around 后置
```

| 场景 | 排序依据 |
|------|---------|
| 跨切面 | `@Order` 数字小的先执行（未标注按解析顺序） |
| 同类内多通知 | Spring 5.2.7+：`@Around` 先于 `@Before`；`@AfterReturning` 先于 `@After` |
| 同方法多切面命中 | 合并为有序 Advisor 链，规则同上 |

> 🎯 记忆：**@Before 像排队进门（正序），@AfterReturning 像逆序出门（反序），@Around 是完整包裹层**——需要"最先做前置、最后做清理"的切面给最小 @Order。

### 4.2 切面拆分原则

| 原则 | 说明 |
|------|------|
| 单一职责 | 一个切面只做一件事（日志归日志、监控归监控、安全归安全） |
| 顺序显式 | 有先后依赖的切面必须写 @Order，别依赖默认解析顺序 |
| 共享切点 | 相关切面引用同一命名切点，保证匹配口径一致 |

> 💡 反例警示：把日志、耗时、幂等全塞进一个切面，排查问题时要同时看三类逻辑——拆分是长期维护性的胜负手。

## 5. 切点表达式速查

| 表达式 | 匹配 | 示例 |
|--------|------|------|
| `execution(修饰符? 返回类型 类名.方法名(参数) 异常?)` | 方法签名 | `execution(* com.demo.service.*.*(..))` |
| `within(类型)` | 类型内所有方法 | `within(com.demo.service..*)` |
| `this(类型)` / `target(类型)` | 代理对象/目标对象 | `this(UserService)` |
| `args(类型)` | 参数类型 | `args(String, ..)` |
| `@annotation(注解)` | 方法带注解 | `@annotation(com.demo.annotation.SysLog)` |
| `@within(注解)` | 类带注解 | `@within(org.springframework.stereotype.Service)` |
| `bean(名字)` | Bean 名 | `bean(orderService)` |
| 逻辑组合 | 与或非 | `&&`、`\|\|`、`!` |

```text
常用组合模板：
  execution 公开方法 + @annotation 自定义注解 → 注解驱动切面（最常用）
  execution 于 service 包 + @within Service → 服务层统一切面
  bean(orderService) → 单 Bean 定向切面（性能最好）
```

### 5.1 切点表达式选型指南

| 需求 | 首选表达式 | 理由 |
|------|-----------|------|
| 拦截带指定注解的方法 | `@annotation(...)` | 与包结构解耦，重构不影响 |
| 整层统一处理 | `within(com.demo.service..*)` | 一条表达式覆盖整层 |
| 精确到单个方法签名 | `execution(...)` | 可控制修饰符、返回类型、参数 |
| 只拦指定 Bean | `bean(orderService)` | 匹配最快、意图最清晰 |
| 多条件组合 | `&&` / `\|\|` / `!` | 建议拆分子表达式提高可读性 |

> ⚠️ 选型教训：**优先注解驱动，其次包级**——用 execution 精确到具体类名，重构改名后切面会"悄悄失效"；注解驱动则类怎么改都不影响。

### 5.2 表达式调试三板斧

| 板斧 | 做法 | 效果 |
|------|------|------|
| 放宽法 | 从 `execution(* com.demo..*(..))` 开始逐步收紧 | 区分"框架没织入"与"表达式没匹配" |
| 隔离法 | 临时把表达式换成 `bean(具体Bean名)` | 排除表达式语法问题 |
| 日志法 | 切面内打印命中的方法签名 | 确认实际命中的方法集合 |

> ⚠️ 高频坑：`within(com.demo.service.*)` 只匹配一层，`within(com.demo.service..*)` 才匹配子包——"少个点就少一片"，`..` 表示任意多层，`*` 只代表一层。

## 6. 7.x 变化对照

| 变化 | 说明 |
|------|------|
| `@Proxyable`（新注解） | 按 Bean 指定代理类型：`@Proxyable(proxyTargetClass = true)` |
| 接口代理 Bean 属性（新） | BeanDefinition 属性强制接口代理 |
| CGLIB 一致默认 | Boot 下 @Retryable/@Async 等全部注解代理统一 CGLIB（原 JDK 代理的注解行为对齐） |
| `proxyTargetClass` 全局属性 | 仍可用（`spring.aop.proxy-target-class`），但 7.x 更推荐 @Proxyable 细粒度控制 |

```java
// 7.0：按 Bean 指定代理方式
@Proxyable(proxyTargetClass = false)   // 该 Bean 用 JDK 接口代理
@Service
public class UserService implements UserApi { ... }
```

> ⚠️ **升级注意**：7.0 全面 CGLIB 后，"依赖 JDK 动态代理语义"的代码（如强转接口类型、`Proxy.isProxyClass` 判断）行为会变化——升级前审计。

### 6.1 面试追问点

| 追问 | 参考回答要点 |
|------|-------------|
| 同类自调用为什么失效？ | `this` 指向原始对象而非代理，通知链没机会执行 |
| JDK 代理与 CGLIB 怎么选？ | 7.x 统一 CGLIB；JDK 只能代理接口方法且要求实现接口 |
| @Transactional 是怎么织入的？ | Bean 后置处理 → 匹配事务切点 → 创建代理 → 调用链中开启事务 |
| 两个切面顺序如何确定？ | @Order 小值优先；@Before 正序、@After* 逆序、@Around 嵌套 |
| AopContext 原理？ | ThreadLocal 存当前代理；exposeProxy=true 时调用链内可取 |
| CGLIB 有哪些限制？ | 目标类与方法不能 final；private/static 方法不可代理 |

### 6.2 一句话总结

- **织入** = Bean 后置处理时创建代理，调用时按序执行通知链；
- **失效** = 调用没经过代理（自调用/new/静态方法），或方法不可覆写（private/final）；
- **顺序** = @Order 定切面顺序，@Around 是洋葱外壳；
- **7.x** = 全部代理注解统一 CGLIB + @Proxyable 细粒度微调。
