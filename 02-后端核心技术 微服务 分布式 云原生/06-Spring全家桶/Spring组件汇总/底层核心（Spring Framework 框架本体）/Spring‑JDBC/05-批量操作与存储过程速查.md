## 1. 批量插入的三种姿势

| 方式 | 写法 | 适用 |
|------|------|------|
| 循环单条 update | for 循环 `update(sql, args)` | ❌ 最慢（N 次网络往返） |
| 批量参数 | `batchUpdate(sql, List<Object[]>, batchSize)` | ✅ 简单场景 |
| 自定义批处理 | `batchUpdate(sql, new BatchPreparedStatementSetter(){...})` | ✅ 复杂类型转换 |
| 多语句（7.x） | JdbcClient `.batchUpdate(...)` | 新代码优先 |

```java
// 姿势二：参数列表批量（内部按 batchSize 分批执行）
int[] results = jdbcTemplate.batchUpdate(
        "INSERT INTO t_order(user_id, amount) VALUES (?, ?)",
        orders.stream().map(o -> new Object[]{o.userId(), o.amount()}).toList(),
        500);                                    // 每批 500 条（批次大小）
```

> 🎯 **核心要点**：`batchUpdate` 内部是 **PreparedStatement 复用 + 分批 addBatch/executeBatch**——比循环单条快一个数量级；`int[]` 返回每批受影响行数。

### 1.1 三种姿势的性能对比与选型

| 方式 | 网络往返 | 内存 | 适用 |
|------|---------|------|------|
| 循环单条 update | N 次 | 低 | 条数极少（<20）或每条 SQL 不同 |
| 参数列表 batchUpdate | 约 N/batchSize 次 | 中（全部参数驻留） | 简单类型参数、数据量中等 |
| Setter 批处理 | 约 N/batchSize 次 | 低（逐行绑定） | 大表导入、类型转换复杂 |
| JdbcClient batchUpdate | 同 batchUpdate | 同 | 命名参数场景、新代码 |

```java
// 循环单条的代价：每次 update 都是一次完整"取连接-预编译-执行-归还"
for (Order o : orders) {
    jdbcTemplate.update("INSERT INTO t_order(user_id, amount) VALUES (?, ?)",
            o.userId(), o.amount());   // 10 万条 = 10 万次网络往返 ≈ 分钟级
}
```

> 🎯 经验值：单条循环 10 万条约 60-120 秒；batchUpdate 分批后约 2-5 秒（加 `rewriteBatchedStatements` 更快）——"批量还是慢"的第一怀疑对象永远是循环里发 SQL。

### 1.2 批量操作的面试追问

| 追问 | 回答锚点 |
|------|---------|
| batchUpdate 为什么比循环快 | 预编译一次 + 网络往返从 N 次降到 N/batchSize 次 |
| int[] 返回值含义 | 每批（或每条）受影响行数；驱动可能返回 -2（批量结果未知） |
| 批量失败怎么处理 | 无事务时前批已生效——要么包事务，要么设计可重入 |
| 批大小怎么定 | 500-1000 基准；过大内存膨胀、过小失去批量意义 |
| 批量与流式读结合 | 读一批 → 写一批，总内存恒定（生产者-消费者模式） |

> 💡 面试深挖点：`executeBatch` 失败时驱动可能抛出 `BatchUpdateException`（部分批次已执行）——Spring 的 `batchUpdate` 默认把它包装为 `DataIntegrityViolationException` 等；所以"批量失败自动整体回滚"只在事务包裹下成立，这是设计要点而非框架保证。

补充：批处理与"多值插入"的关系——`rewriteBatchedStatements` 生效时，驱动把一批 INSERT 重写成一条多值 INSERT（受 `max_allowed_packet` 限制），所以批大小不是越大越好：超过包上限会被驱动拆回逐条，反而退化。实践上 500-1000 兼顾了包大小与往返次数；单行字段特别宽（大文本）时批大小要相应调小。这个细节能把"为什么批量还有上限"讲透。

## 2. BatchPreparedStatementSetter 详解

```java
// 姿势三：Setter 自定义绑定（类型控制、复杂转换）
int[] results = jdbcTemplate.batchUpdate(
        "INSERT INTO t_log(user_id, msg, created_at) VALUES (?, ?, ?)",
        new BatchPreparedStatementSetter() {
            @Override
            public void setValues(PreparedStatement ps, int i) throws SQLException {
                LogEntry log = logs.get(i);
                ps.setLong(1, log.userId());
                ps.setString(2, log.msg());
                ps.setTimestamp(3, Timestamp.valueOf(log.createdAt()));   // 显式类型
            }
            @Override
            public int getBatchSize() {
                return logs.size();
            }
        });
```

| 要点 | 说明 |
|------|------|
| 回调粒度 | 每行一次 `setValues`；`getBatchSize` 告诉驱动批量大小 |
| 分页保护 | 超大集合（>10 万）应外层分片，避免单批撑爆内存 |
| 事务包装 | 批量放 `@Transactional` 内，失败整体回滚（否则半批已落库） |
| 替代 | JdbcClient `batchUpdate(sql, List<Map>)`（键名=命名参数） |

> ⚠️ **半批落库陷阱**：无事务时 executeBatch 分批提交——中途失败，前几批已生效（不可回滚）；大数据量导入务必包事务或可重入设计。

### 2.1 批量更新与分片处理（大集合防内存爆炸）

```java
// 分片导入：100 万条分 20 片，每片 5 万
private static final int SLICE = 50_000;
private static final int BATCH = 500;

public void importAll(List<Order> all) {
    for (int from = 0; from < all.size(); from += SLICE) {
        int to = Math.min(from + SLICE, all.size());
        int[] r = jdbcTemplate.batchUpdate(
                "INSERT INTO t_order(user_id, amount, status) VALUES (?, ?, 'CREATED')",
                all.subList(from, to).stream()
                        .map(o -> new Object[]{o.userId(), o.amount()})
                        .toList(),
                BATCH);                       // 每片内部再按 500 条一批执行
        log.info("imported {}-{}, rows={}", from, to, r.length);
    }
}
```

| 分片要点 | 说明 |
|---------|------|
| 外层分片 | 控制单次内存驻留（避免全量 `List<Object[]>` 常驻） |
| 内层 batchSize | 控制网络往返与数据库端批量大小 |
| 断点续传 | 记录已导入的 id 范围 / 状态位，失败后从断点继续 |
| 幂等设计 | 业务唯一键 + `ON DUPLICATE KEY UPDATE` 或先查重 |

> ⚠️ **断点续传的必要性**：10 万+ 数据的导入永远假设"会中途失败"（连接断开 / 唯一键冲突 / 内存溢出）——没有断点设计，每次重跑都是全量重复劳动。

### 2.2 BatchPreparedStatementSetter 常见误用

| 误用 | 后果 | 正确做法 |
|------|------|---------|
| setValues 里访问外部集合越界 | IndexOutOfBounds 或静默漏数据 | getBatchSize 必须与集合大小一致 |
| 每次 setValues 重新创建对象 | 垃圾回收压力 | 复用预创建的对象列表 |
| 忘记显式 setTimestamp | 时间字段错乱 | 日期统一显式 java.sql 类型 |
| getBatchSize 返回 0 | 批处理不执行 | 提前判空集合再进批处理 |

```java
// 防御式写法：空集合直接返回，避免无谓批处理
public int[] batchInsertLogs(List<LogEntry> logs) {
    if (logs == null || logs.isEmpty()) {
        return new int[0];
    }
    return jdbcTemplate.batchUpdate(SQL, new BatchPreparedStatementSetter() {
        @Override public void setValues(PreparedStatement ps, int i) throws SQLException {
            LogEntry log = logs.get(i);        // i 由 Spring 按 0..getBatchSize-1 递增
            ps.setLong(1, log.userId());
            ps.setString(2, log.msg());
        }
        @Override public int getBatchSize() { return logs.size(); }
    });
}
```

> 🎯 关键认知：`setValues` 的回调索引 i 从 0 到 `getBatchSize()-1` 顺序递增——实现时必须保证"索引能对应到数据源"，这是 Setter 姿势唯一的正确性契约；集合为空时提前返回是防御式编程的标准动作。

补充：Setter 姿势与参数列表姿势的底层差异——参数列表姿势会把整个 `List<Object[]>` 先转为内部数组再逐批执行，Setter 姿势则按 `getBatchSize` 分批回调；两者最终都走 `PreparedStatement.addBatch/executeBatch`。面试被问"两个姿势性能有差吗"——理论差异极小，选择标准是"类型转换复杂程度"而非性能。

## 3. 批量性能要点

| 优化 | 做法 | 收益 |
|------|------|------|
| 批大小 | `batchSize` 500-1000 | 平衡网络往返与内存 |
| 连接参数 | MySQL URL 加 `rewriteBatchedStatements=true` | 真正的多值批量（**数倍提升**） |
| 事务 | 包一层事务 | 减少自动提交次数 |
| 驱动 | 使用驱动专用批量 API（如 pgJDBC Copy） | 极致导入 |
| 会话设置 | 关闭外键检查/唯一索引（仅离线导入） | 索引维护开销 |

```yaml
# MySQL 批量关键参数（否则 batchUpdate 是"假批量"）
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/app?rewriteBatchedStatements=true&useServerPrepStmts=true
```

> 💡 **面试点**：MySQL 默认批处理是"逐条执行"的伪批量——`rewriteBatchedStatements=true` 让驱动重写为 `INSERT ... VALUES (...),(...)` 多值语句，性能提升 5-20 倍；这是"批量还是慢"排查的第一站。

### 3.1 批量性能排查清单（按顺序检查）

| 序号 | 检查项 | 症状 | 解法 |
|------|--------|------|------|
| 1 | URL 是否带 `rewriteBatchedStatements=true` | 万级数据仍十几秒 | URL 追加；确认驱动 ≥ 8.0 |
| 2 | 是否包了事务 | 每批后自动提交 | 外层 `@Transactional` 或 TransactionTemplate |
| 3 | batchSize 过大 / 过小 | 内存飙升 或 往返过多 | 500-1000 基准，压测调 |
| 4 | 事务内混入查询 | 长事务锁累积 | 先批量写后查询，或分开事务 |
| 5 | 索引过多 | 插入慢于预期 | 离线导入临时删非必要索引 |
| 6 | 驱动版本过老 | 不支持多值重写 | 升级 mysql-connector-j 8.0.33+ |

> 💡 判断是否"真批量"：开 MySQL 通用日志或查 `performance_schema`——看语句是一条条 `INSERT`，还是合并成多值 `INSERT ... VALUES (...),(...)`；后者才是 `rewriteBatchedStatements` 生效。

### 3.2 批量与事务的交互

| 组合 | 行为 |
|------|------|
| 无事务批量 | 每批自动提交——中途失败，前批已落库 |
| 事务内批量 | 全部回滚或全部提交（同一条连接） |
| 超大事务批量 | 长事务锁多行、undo 膨胀——按业务切分事务粒度 |
| 批量 + 查询混用 | 事务内查询会看到未提交的批量数据（同连接） |

```java
// 批量 + 事务的标准姿势（失败整体回滚）
@Transactional
public void importBatch(List<Order> orders) {
    jdbcTemplate.batchUpdate(
            "INSERT INTO t_order(user_id, amount) VALUES (?, ?)",
            orders.stream().map(o -> new Object[]{o.userId(), o.amount()}).toList(),
            500);
}
```

> ⚠️ 权衡提示：10 万行包一个事务，回滚代价与锁持有时间都很大；实践上"每 1-2 万行一个事务 + 断点续传"更稳——事务太大与完全无事务是两个极端，中间态（分片事务）才是生产常态。

补充事务粒度的量化参考：单条 INSERT 在 MySQL 下的事务开销（redo/undo）在微秒级，但锁的累积效应与回滚段膨胀才是主要问题——1 万行一个事务与 100 行一个事务在"锁等待峰值"上差异明显；生产上以"单事务锁行数可控 + 失败重跑代价可接受"为准则，通常 1-5 万行是常见分界。

## 4. SimpleJdbcInsert：声明式插入

```java
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("t_order")
        .usingGeneratedKeyColumns("id");              // 自增主键回填

// 按命名参数插入（自动生成 INSERT 语句）
Number key = insert.executeAndReturnKey(
        new MapSqlParameterSource()
                .addValue("user_id", 1001L)
                .addValue("amount", BigDecimal.valueOf(99.5)));

// 批量插入
int[] n = insert.executeBatch(rows);                  // List<MapSqlParameterSource>
```

| 能力 | 说明 |
|------|------|
| 语句自动生成 | 按表结构 + 参数生成 INSERT（少写 SQL） |
| 主键回填 | `usingGeneratedKeyColumns` |
| 列白名单 | `usingColumns(...)` 精确控制 |
| 批量 | `executeBatch` |

> ⚠️ 注意：SimpleJdbcInsert 生成的列名来自 `DatabaseMetaData` 或显式列集合——**列名大小写/下划线**在不同库行为有差异，生产建议显式 `usingColumns`。

### 4.1 SimpleJdbcInsert 完整示例与列名处理

```java
// 显式列白名单：避免依赖元数据猜测（生产推荐）
SimpleJdbcInsert insert = new SimpleJdbcInsert(dataSource)
        .withTableName("t_order")
        .usingColumns("user_id", "amount", "status")   // ★ 白名单，杜绝列错位
        .usingGeneratedKeyColumns("id");

// 批量插入：一次给多行
List<MapSqlParameterSource> batch = orders.stream()
        .map(o -> new MapSqlParameterSource()
                .addValue("user_id", o.userId())
                .addValue("amount", o.amount())
                .addValue("status", "CREATED"))
        .toList();
insert.executeBatch(batch);
```

| 列名问题 | 表现 | 解法 |
|---------|------|------|
| 大小写敏感（Oracle） | 找不到列 | `usingColumns` 显式写列名 |
| 下划线 / 驼峰 | 生成 SQL 与库不符 | 显式列名 |
| 同名列（JOIN 视图） | 歧义 | 不用 SimpleJdbcInsert，写显式 SQL |
| 默认值列 | 未提供时报错 | 从参数集合去掉，让库端填充 |

> 🎯 决策：表列 ≤ 10、且 90% 列都要插入 → SimpleJdbcInsert 省事；列多 / 有默认值 / 有表达式 → 手写 INSERT 更透明。生产团队常"手写 SQL 为主、SimpleJdbcInsert 处理高频小表"。

### 4.2 SimpleJdbcInsert 与 JdbcClient 的对比

| 维度 | SimpleJdbcInsert | JdbcClient 手写 INSERT |
|------|-----------------|----------------------|
| SQL 编写 | 自动生成 | 手写 |
| 主键回填 | 声明式 `usingGeneratedKeyColumns` | `update(KeyHolder)` |
| 列控制 | `usingColumns` 白名单 | SQL 天然显式 |
| 批量 | `executeBatch` | `.batchUpdate` |
| 可读性 | 生成逻辑藏在类配置里 | SQL 在眼前 |

选型逻辑：SimpleJdbcInsert 的优势是"表结构变了少改 SQL"（列来自元数据）；劣势是"SQL 不透明、依赖元数据"。面试答法：简单稳定表用 SimpleJdbcInsert 图省事，但涉及多表 / 复杂默认值一律手写 SQL——可维护性优先于省事，这也是生产团队的主流选择。

还有一个通用原则：批量插入的目的地如果带唯一索引，先对数据做去重（应用层 Set 或 SQL DISTINCT）能显著减少冲突与重试；配合 `ON DUPLICATE KEY UPDATE` 做幂等写入，是"导入任务可重跑"的标准组合——重试成本从"全量重来"降到"增量补齐"。

## 5. SimpleJdbcCall：存储过程调用

```java
SimpleJdbcCall call = new SimpleJdbcCall(dataSource)
        .withProcedureName("sp_create_order");          // 或 withFunctionName(...)
// 7.x：可用 withCatalogName/schema 限定

Map<String, Object> result = call.execute(
        new MapSqlParameterSource()
                .addValue("user_id", 1001L)
                .addValue("amount", BigDecimal.valueOf(99.5)));

// 出参（OUT/INOUT）
Object newId = result.get("new_id");                   // 按出参名取
```

| 场景 | 说明 |
|------|------|
| 存储过程 | `withProcedureName` |
| 函数 | `withFunctionName`（返回单值） |
| 出参 | 执行结果 Map 按键取（名称来自元数据） |
| 时间/游标 | 需 `declareParameters` 显式注册（元数据不可靠时） |
| 替代方案 | `JdbcTemplate` 原生 `{call sp(?)}` + CallableStatement |

> 🎯 **核心要点**：SimpleJdbcCall 的卖点是**元数据驱动**——自动从数据库读取参数名/方向/类型，免写 CallableStatement 样板；但元数据读取本身有开销，低频调用无所谓、高频过程调用建议缓存或显式参数声明。

### 5.1 存储过程出参 / 游标处理

```java
// 显式声明参数（元数据不可靠时的正规做法）
SimpleJdbcCall call = new SimpleJdbcCall(dataSource)
        .withProcedureName("sp_get_user_orders")
        .declareParameters(
                new SqlParameter("p_user_id", Types.BIGINT),     // IN
                new SqlOutParameter("p_total", Types.DECIMAL),   // OUT
                new SqlOutParameter("p_orders", Types.OTHER, new ResultSetExtractor<List<Order>>() {
                    @Override
                    public List<Order> extractData(ResultSet rs) throws SQLException {
                        List<Order> list = new ArrayList<>();
                        while (rs.next()) {
                            list.add(new Order(rs.getLong("id"), rs.getBigDecimal("amount")));
                        }
                        return list;
                    }
                }));                                          // 游标出参

Map<String, Object> out = call.execute(new MapSqlParameterSource("p_user_id", 1001L));
BigDecimal total = (BigDecimal) out.get("p_total");
List<Order> orders = (List<Order>) out.get("p_orders");
```

| 面试追问 | 回答锚点 |
|---------|---------|
| 为什么 SimpleJdbcCall 首次调用慢 | 启动时读 `DatabaseMetaData` 元数据；可用 `withoutProcedureColumnMetaDataAccess()` 关闭 |
| 游标出参怎么接 | `SqlOutParameter(name, Types.OTHER, ResultSetExtractor)` 直接映射 |
| 存储过程事务与应用事务 | 过程内部事务与应用事务互不知晓——跨进程边界，尽量少用过程承载事务 |
| 什么时候不用存储过程 | 逻辑演进快、需测试覆盖、多数据库迁移——应用层 SQL 更可控 |

> ⚠️ 元数据访问的隐藏成本：SimpleJdbcCall 首次调用会连库查元数据——**高频调用必须复用同一个实例**（Bean 单例），每次 new 等于每次查元数据。

### 5.2 存储过程的现代实践讨论

| 立场 | 观点 |
|------|------|
| 支持使用 | 复杂报表逻辑复用、安全边界（应用无表权限）、老系统遗产 |
| 反对使用 | 测试困难、版本管理缺失、多库迁移成本高、应用层事务难参与 |

```text
折中实践：
  1. 过程只做"事务性较强的单点操作"（如防并发扣减）
  2. 报表 / 复杂查询尽量应用层拼 SQL（可测、可优化）
  3. 用 SimpleJdbcCall 调用必须配显式 declareParameters
  4. 过程变更走发布流程与版本号（sp_name_v2），避免热改
```

> 💡 面试立场："存储过程是数据库能力的封装边界——合理用于强事务单点与安全边界，避免用于业务逻辑载体；调用必须显式声明参数、复用实例（元数据开销），并纳入版本管理。"——先给出立场再给依据，比罗列优缺点更有说服力。

最后补充：如果是新项目、没有存储过程遗产，默认答案就是"不用存储过程"——SQL 放在应用层配合 Mapper/模板，可测试、可版本控制、可跨库；只有业务强约束（安全隔离、并发原子扣减）或遗留系统才考虑过程。这个立场比"能用就用"更符合 2026 年的工程主流。
