## 1. Artifact 坐标与版本线

| 项 | 值 |
|----|----|
| GroupId | `org.springframework` |
| ArtifactId | `spring-jdbc` |
| 最新版本 | 7.0.x（2026-08 时点，随 Framework 7.0 主线） |
| 维护线 | 7.0.x / 7.1.x（最新）、6.2.x（Boot 3.x） |
| Java 基线 | 17+；Jakarta EE 11 基线（7.0） |
| 常用配套 | spring-tx（事务）、HikariCP/Druid（连接池）、spring-boot-starter-jdbc（Boot） |

> 💡 Boot 4 中 `spring-boot-starter-jdbc` 自动装配 `DataSource`、`JdbcTemplate`、`JdbcClient`、`DataSourceTransactionManager`——业务代码无需任何配置即可注入。

### 1.1 引入方式速查

```xml
<!-- Maven：框架维护者/非 Boot 项目场景 -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-jdbc</artifactId>
    <version>7.0.x</version>
</dependency>

<!-- Boot 4：starter 全自动装配（推荐，版本随 Boot BOM 管理，无需写 version） -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-jdbc</artifactId>
</dependency>
```

| 引入方式 | 自带内容 | 适用 |
|---------|---------|------|
| `spring-jdbc` 裸依赖 | 仅模板 / 数据源 / 翻译器 | 非 Boot 项目或自组框架 |
| `spring-boot-starter-jdbc` | 上述 + HikariCP + 自动装配 | Boot 项目（99% 场景） |
| `spring-jdbc` + `druid-spring-boot-starter` | 连接池换成 Druid | 需要监控 / SQL 防火墙 |

> 💡 starter 中默认连接池是 **HikariCP 且只有它一个**——换 Druid 就是排除 HikariCP 再加 Druid starter（配置见 [04-DataSource 与连接池速查](04-DataSource与连接池速查.md) 第 3 节）。

版本选择上还有一个工程细节：Spring Framework 7.x 的里程碑版（M 版）与 RC 版只用于尝鲜，生产项目应只用正式版（7.0.0 之后）；锁定补丁版本（如 7.1.x 的最新补丁）比锁定主版本更稳，补丁只修 bug 不引入行为变化。

### 1.2 spring-jdbc 与 spring-boot-starter-jdbc 的职责划分

很多同学分不清"spring-jdbc"和"spring-boot-starter-jdbc"的区别，面试被问"starter 到底做了什么"容易卡壳。核心区别只有一句话：**spring-jdbc 是能力提供者，starter 是装配组织者**。

| 层 | 代表 | 职责 |
|----|------|------|
| 框架模块 | spring-jdbc | 提供 JdbcTemplate、DataSource 抽象、翻译器、事务管理器实现 |
| Boot 自动装配 | spring-boot-starter-jdbc | 读配置（spring.datasource.*）→ 建 DataSource → 建模板 → 建事务管理器 |
| 应用代码 | 业务 DAO | 只注入成品 Bean，不关心装配过程 |

starter 的自动装配逻辑全部基于 `@ConditionalOnClass` 与 `@ConditionalOnMissingBean`：classpath 有 HikariCP 就装配 Hikari 数据源，有 Druid 就装配 Druid；应用自己定义了 `DataSource` Bean，自动装配就退出让位。理解这个机制，面试答"Boot 怎么知道用哪个连接池"就有了解答框架：先看 classpath 有什么，再看有没有用户自定义覆盖。

### 1.3 面试官追问什么

| 追问 | 回答锚点 |
|------|---------|
| spring-jdbc 和 starter 的区别 | 能力提供者 vs 装配组织者；starter 依赖 spring-jdbc |
| 为什么 spring-jdbc 不内置连接池 | 连接池是"实现选择"而非"框架职责"；DataSource SPI 已解耦 |
| 编译期需要驱动吗 | 不需要——驱动是运行时依赖，JDBC 通过 SPI 加载 |
| 7.0 最小升级改动是什么 | Kotlin 扩展 vararg 修正（编译错误）+ 废弃标记（告警） |
| spring-tx 和 spring-jdbc 谁依赖谁 | spring-jdbc 依赖 spring-tx（异常族与事务管理器接口在 tx） |

> 💡 面试细节：`DataSourceTransactionManager` 的全称是 `org.springframework.jdbc.datasource.DataSourceTransactionManager`——它在 spring-jdbc 包内、实现 spring-tx 定义的 `PlatformTransactionManager` 接口；答出这个归属关系，事务相关追问就稳了一半。

再补一个面试细节：spring-jdbc 的 Javadoc 首页会列出它依赖的模块（spring-core、spring-beans、spring-tx），其中 spring-tx 是唯一非 core/beans 的功能性依赖——因为 DataAccessException 家族与事务抽象定义在 tx。这也是为什么"异常翻译"与"事务管理"常被归为 spring-jdbc 的隐性能力：实现在这、契约在别处。

## 2. 包结构地图

```text
org.springframework.jdbc
├── core                   ★ 模板层
│   ├── JdbcTemplate / NamedParameterJdbcTemplate / JdbcClient（★ 7.0 主推）
│   ├── JdbcOperations / NamedParameterJdbcOperations（接口，模板的抽象）
│   ├── RowMapper / ResultSetExtractor / RowCallbackHandler / PreparedStatementSetter
│   ├── StatementCreatorUtils / ArgumentPreparedStatementSetter
│   └── ColumnMapRowMapper / SingleColumnRowMapper
├── core.support
│   ├── JdbcDaoSupport（★ 7.0 废弃 #35145）/ SqlUpdate / StoredProcedure（旧对象映射）
│   └── KeyHolder / GeneratedKeyHolder（自增主键回填）
├── datasource             ★ 数据源
│   ├── DriverManagerDataSource / SingleConnectionDataSource / SimpleDriverDataSource
│   ├── DataSourceUtils（连接获取/释放/事务绑定）★
│   ├── TransactionAwareDataSourceProxy / LazyConnectionDataSourceProxy
│   ├── init：DatabasePopulator / ResourceDatabasePopulator / DataSourceInitializer
│   └── embedded：EmbeddedDatabaseBuilder（H2/H2 内存库测试）
├── object                # 旧式对象映射（SqlQuery 等，已边缘）
├── support               # SQLErrorCodeSQLExceptionTranslator 等异常翻译 ★
└── config?（无独立 config 包；XML 命名空间在 spring-tx/context）
```

**高频面试点名类**：`JdbcTemplate`、`JdbcClient`、`RowMapper`、`DataSourceUtils`（连接与事务绑定）、`SQLErrorCodeSQLExceptionTranslator`。

### 2.1 核心类职责速查（按包分类记忆）

| 包 | 核心类 | 一句话职责 |
|----|--------|-----------|
| `core` | `JdbcTemplate` | 全部 SQL 执行入口（查询 / 更新 / 批量） |
| `core` | `JdbcClient` | Fluent 流式入口（7.0 主推） |
| `core` | `RowMapper` | 结果集单行 → 对象（每行回调一次） |
| `core` | `ResultSetExtractor` | 整个结果集 → 对象（聚合统计场景） |
| `core` | `StatementCreatorUtils` | 参数值 → `ps.setXxx` 的类型推断 |
| `core.support` | `KeyHolder` | 自增主键回填 |
| `datasource` | `DataSourceUtils` | 连接获取 / 释放 + 事务线程绑定 ★ |
| `datasource` | `DriverManagerDataSource` | 教学用无池数据源 |
| `datasource.embedded` | `EmbeddedDatabaseBuilder` | 内存库（H2）测试 |
| `support` | `SQLErrorCodeSQLExceptionTranslator` | 错误码 → DataAccessException ★ |

记忆口诀：**core 管执行、datasource 管连接、support 管翻译**——三个包各司其职，被问"spring-jdbc 有哪些包"按这个答。

### 2.2 包结构的设计思想：分层职责与依赖方向

```text
依赖方向（只允许单向向下）：
  core（模板执行）→ datasource（连接管理）→ support（异常翻译）
```

spring-jdbc 的包结构不是随意划分的，它体现了三层职责边界：

| 层 | 关注点 | 为什么独立成包 |
|----|--------|---------------|
| core | 执行 SQL、参数绑定、结果映射 | 与"连接从哪来"解耦——模板只认 DataSource 接口 |
| datasource | 连接获取/释放、事务绑定、脚本初始化 | 连接管理策略可替换（池/单连接/代理） |
| support | SQLException → DataAccessException | 翻译逻辑与执行逻辑分离，可独立测试 |

理解这个分层的实际收益是：**排查问题时能快速定位包**——SQL 行为问题查 core，连接行为问题查 datasource，异常行为问题查 support。面试被问"JdbcTemplate 的 getConnection 是哪一层的事"——答案是 datasource 层（DataSourceUtils），模板只是委托方；这种"模板只管执行、连接另有其主"的职责分离，是整个设计最值得讲的一点。

从演进角度看，包结构在 7.0 几乎没有变化——废弃的是类（NamedParameterJdbcTemplate、DaoSupport）而不是包；core 包继续收编新能力（JdbcClient 也在 core 包）。面试如果被问"7.0 包结构有什么变化"，正确回答是"包结构稳定，收口发生在类与 API 层面"，能答出这个区别，说明对版本演进有真实追踪。

> 🎯 面试升级点：`StatementCreatorUtils` 负责把 `Object` 参数映射为合适的 `setXxx`——`null` 值默认按 `Types.NULL` 设置、`java.util.Date` 自动转 `Timestamp`；这就是 JdbcTemplate 传参比裸 JDBC 少很多样板代码的底层原因（细节见 [02-JdbcTemplate 速查](02-JdbcTemplate速查.md) 第 4 节）。

## 3. 7.0 废弃与移除清单

| 项 | 状态 | 替代 |
|----|------|------|
| `NamedParameterJdbcTemplate` | 废弃（待移除） | `JdbcClient`（命名参数内建）或 `JdbcTemplate` |
| `JdbcDaoSupport` 等 `DaoSupport` 类 | 废弃（#35145） | 组合注入 `JdbcTemplate`/`JdbcClient` |
| `queryForObject(sql, Array)` Kotlin 扩展 | 替换（#35846） | vararg 版本（`sql, vararg args`） |
| `org.springframework.orm.hibernate5` | 迁移（spring-orm） | `org.springframework.orm.jpa.hibernate`（JPA 3.2/Hibernate 7） |
| `DataSourceUtils` 等核心 API | 稳定 | - |

> ⚠️ **升级提示**：① 新代码不写 NamedParameterJdbcTemplate；② 存量迁移示例：`namedTpl.queryForObject(sql, params, Type)` → `jdbcClient.sql(sql).params(map).query(Type).single()`；③ Kotlin 调用处改 vararg。

### 3.1 废弃 API 迁移实例（DaoSupport → 组合注入）

```java
// 旧：继承 JdbcDaoSupport（7.0 废弃 #35145）
// public class UserDao extends JdbcDaoSupport {
//     public int updateAge(long id, int age) {
//         return getJdbcTemplate().update("UPDATE t_user SET age = ? WHERE id = ?", age, id);
//     }
// }

// 新：组合注入 JdbcClient（推荐）
@Repository
public class UserDao {
    private final JdbcClient jdbc;

    public UserDao(JdbcClient jdbc) { this.jdbc = jdbc; }

    public int updateAge(long id, int age) {
        return jdbc.sql("UPDATE t_user SET age = :age WHERE id = :id")
                .param("age", age).param("id", id)
                .update();
    }
}
```

| 废弃项 | 迁移收益 |
|--------|---------|
| `extends JdbcDaoSupport` → 组合注入 | 解除基类耦合，单元测试可 mock |
| `getJdbcTemplate()` 调用 → 直接字段 | 依赖显式化，重构友好 |
| 多 DAO 共享模板 → 构造器注入同一 Bean | 配置集中、可统一替换 |

> 💡 迁移不必一次性完成：`JdbcDaoSupport` 在 7.0 只是 `@Deprecated` 标记、仍可运行——但新代码（尤其 Boot 4 项目）一律不写；存量代码建议随模块重构顺带迁移，避免"改一行牵连一片"。

### 3.2 理解 Spring 的废弃（deprecation）策略

| 阶段 | 行为 | 时间跨度 |
|------|------|---------|
| @Deprecated 标记 | 仍可用、编译告警 | 通常 ≥ 2 个主版本 |
| 移除 | 编译报错，必须迁移 | 下一个主版本或更晚 |

Spring 的废弃策略是"先标记、再移除"的两段式：7.0 标记的 NamedParameterJdbcTemplate 和 JdbcDaoSupport，至少要等到 8.x 才可能真正删除。这个策略意味着两点：一是存量代码不会被"突然删掉"打措手不及；二是新代码如果还在用废弃 API，会被代码评审和 IDE 告警持续提醒，属于"明知故犯"。

面试口径："Spring 的废弃分两阶段，7.0 只是第一阶段的标记，移除要等 8.x；但团队规范要求新代码立即切换，存量代码制定迁移计划。"——既展示了知识深度，又体现了工程态度；再补一句"迁移是语法级改动、事务与异常行为不变"，风险认知也到位了。

实际迁移时还有一类容易漏的点：测试代码。存量项目的测试里往往大量使用 NamedParameterJdbcTemplate 与 JdbcDaoSupport 相关的辅助类，编译告警会同时出现在 src 与 test 两套代码里；迁移计划要把测试代码一并纳入，并顺手把测试里的 SQL 参数从 Map 改成链式写法——测试先行迁移，反而能先暴露语义变化点。

## 4. 依赖边界

| 依赖 | 方向 | 说明 |
|------|------|------|
| `spring-core` / `spring-beans` | 依赖 | 工具、资源（SQL 脚本）、Bean 属性填充 |
| `spring-tx` | 依赖 | `DataSourceTransactionManager` 定义在 spring-tx，jdbc 提供实现 |
| JDBC 驱动（mysql-connector-j 等） | 运行时 | 编译期不需要 |
| 连接池（HikariCP/Druid） | 运行时 | 提供 `javax.sql.DataSource` 实现 |
| 反向依赖 | - | spring-orm（JPA）、spring-boot-starter-jdbc 依赖它 |

> 🎯 **核心要点**：spring-jdbc **不内置连接池**——`DriverManagerDataSource` 只是教学实现，生产必须配 HikariCP/Druid；连接池通过 `javax.sql.DataSource` SPI 接入，Spring 对此零侵入。

### 4.1 依赖瘦身与传递依赖

| 场景 | 需要的依赖 | 说明 |
|------|-----------|------|
| 只做模板查询 | spring-jdbc + 驱动 | 最小集 |
| 使用事务 | spring-tx（spring-jdbc 已传递引入） | 事务管理器开箱可用 |
| 脚本初始化 | 无需额外依赖 | `ResourceDatabasePopulator` 内建于 jdbc |
| 内存测试库 | `com.h2database:h2`（test scope） | 集成测试零外部依赖 |
| 连接池 | HikariCP / Druid | 运行时依赖（Boot starter 已含 Hikari） |

```xml
<!-- 非 Boot 项目的最小生产依赖 -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-jdbc</artifactId>
</dependency>
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>
<dependency>
    <groupId>com.zaxxer</groupId>
    <artifactId>HikariCP</artifactId>
</dependency>
```

> ⚠️ 驱动放 `runtime` scope：编译期不需要驱动类（模板通过 JDBC SPI 加载驱动），放 compile 会把驱动版本锁死进传递依赖、引发依赖冲突；连接池同理。

### 4.2 依赖冲突排查实战

| 冲突症状 | 原因 | 排查命令 |
|---------|------|---------|
| 找不到 `org.springframework.jdbc.core.JdbcTemplate` | 未引入 spring-jdbc 或版本太旧 | `mvn dependency:tree -Dincludes=org.springframework` |
| `NoClassDefFoundError: DataAccessException` | spring-tx 缺失或版本错 | 检查 spring-jdbc 的传递依赖是否被排除 |
| 驱动类重复 / 版本冲突 | 多个驱动坐标同时存在 | `mvn dependency:tree -Dincludes=mysql` |
| 编译期找不到 JDBC 接口 | JDK 模块化配置问题 | 确认 JDK 17+ 与模块声明 |

> ⚠️ 版本冲突的通用解法：非 Boot 项目引入 `spring-boot-dependencies` BOM 统一版本管理；Boot 项目不要手写 Spring 版本号，全部交给 Boot BOM——这是 Spring 版本混乱的第一防线，也是面试官爱问的工程实践题。

### 4.3 传递依赖的正确姿势

```text
要不要显式声明 spring-tx？
  spring-jdbc 已传递引入 spring-tx —— 业务代码直接用 @Transactional 即可；
  但"显式声明依赖"仍是团队规范推荐：用了哪个模块的类，就显式声明哪个模块，
  不依赖传递（transitive）偶然性 —— 未来父模块调整依赖时不会突然编译失败。
```

| 做法 | 说明 |
|------|------|
| 只用 JdbcTemplate | spring-jdbc 一个坐标足够 |
| 用 @Transactional / TransactionTemplate | 显式加 spring-tx（版本随 BOM） |
| 用事务事件（@TransactionalEventListener） | 需要 spring-context（通常已传递） |

> 💡 团队规范："显式依赖原则"——直接 import 了哪个包的类，就在 pom 里显式声明对应坐标；Spring 官方也推荐这种做法，它是依赖管理混乱的第一道防线。

## 5. 版本兼容速查

| Spring Framework | Spring Boot | 备注 |
|------------------|-------------|------|
| 7.0.x（2025-11 起） | Boot 4.0.x | 当前主线；JdbcClient 语句级配置；NamedParameterJdbcTemplate 废弃 |
| 7.1.x（2026-05 起） | Boot 4.1.x | 最新维护线 |
| 6.2.x | Boot 3.4/3.5 | 存量主流；JdbcClient 可用（6.1+）但无语句级配置 |

> 💡 JdbcClient 的演进速记：6.1 诞生（fluent API）→ 7.0 增强（fetchSize/maxRows/queryTimeout 语句级配置 + 命名参数收编）——面试答"JdbcClient 什么时候出的、7.0 加了什么"按此。

### 5.1 版本特性时间线（速记）

| 版本 | 时间 | jdbc 关键特性 |
|------|------|--------------|
| 6.1 | 2023-11 | `JdbcClient` 诞生（基础 fluent 链） |
| 6.2 | 2024-05 | 稳定维护线（Boot 3.x 配套） |
| 7.0 | 2025-11 | JdbcClient 语句级配置；NamedParameterJdbcTemplate / DaoSupport 废弃；Kotlin vararg 修正 |
| 7.1 | 2026-05 | 最新维护线（Boot 4.1 配套） |

面试口径："JdbcClient 是 **6.1 出生、7.0 成年**"——6.1 只有基础 fluent 链，7.0 补上 `fetchSize`/`maxRows`/`queryTimeout` 语句级配置并收编命名参数能力，成为官方主推入口；面试被问版本演进按这个时间线答，不要凭记忆报错版本号。

### 5.2 升级到 7.x 的检查清单

| 检查项 | 风险 | 说明 |
|--------|------|------|
| NamedParameterJdbcTemplate 使用点 | 废弃告警 | 逐个迁移到 JdbcClient（对照表见 [03-JdbcClient 速查](03-JdbcClient速查.md) 第 6 节） |
| JdbcDaoSupport 继承 | 废弃告警 | 改为组合注入，见 3.1 示例 |
| Kotlin 调用处 | 编译错误 | `queryForObject(sql, Array)` → vararg 版本 |
| Hibernate 集成 | 包迁移 | `orm.hibernate5` → `orm.jpa.hibernate` |
| 自定义 SQLExceptionTranslator | 兼容 | 翻译器 API 未变，无需改动 |

> 🎯 升级核心认知：7.x 的 jdbc 变化是"收口与标记"而非"重写"——JdbcTemplate 核心 API 完全没动，真正的破坏性变更只有 Kotlin 扩展一处（编译期报错）。把升级风险讲成"一处编译错误 + 若干废弃告警"，面试官就知道你是真升级过而不是背文档。

补充对比：6.2 与 7.0 的 jdbc 能力差异其实很小——JdbcClient 在 6.1 就有，Boot 3.x 项目完全可以用它写新代码；7.0 的关键增量是语句级配置（fetchSize/maxRows/queryTimeout）与废弃标记。因此选型时不必为"用上 JdbcClient"而升级框架：**6.2 + JdbcClient 与 7.0 + JdbcClient 的日常写法几乎一样**，区别只在于细粒度控制与长期维护线。真正驱动升级的因素是 Boot 版本、JDK 版本与安全补丁，而不是 jdbc 语法本身。

最后提醒一点版本习惯：7.1.x 是 7.x 的维护线，补丁只修 bug 不引入新特性；线上生产建议锁定 7.1.x 的最新补丁版本而非 7.0.x——维护线的 bug 修复是白嫖的稳定性。同样地，6.2.x 存量项目升级补丁时也要先读 Release Notes，确认补丁不含依赖行为变化，再走灰度发布。
