## 1. 与其他模块的集成地图

```text
                  spring-jdbc（数据访问模板层）
        ┌──────────┬──────────┬──────────┬──────────┐
        ↓          ↓          ↓          ↓          ↓
  spring-core  spring-beans  spring-tx  spring-orm   Spring Boot
  Resource     配置/注入     DataAccess   JPA/        starter-jdbc
  (SQL 脚本)    JdbcTemplate  Exception  Hibernate   自动装配
                Bean 装配     族定义      (JPA 3.2)   DataSource/模板
```

| 联动点 | 机制 | 说明 |
|--------|------|------|
| jdbc ↔ tx | `DataSourceTransactionManager` + `org.springframework.dao` 异常族 | 事务与异常契约都在 tx，jdbc 是实现者 |
| jdbc ↔ core | `Resource`/`EncodedResource` 加载 SQL 脚本、编码处理 | `ResourceDatabasePopulator` 执行 DDL |
| jdbc ↔ beans | `JdbcTemplate` 作为 Bean 注入、属性填充 | 模板本身是普通 Bean |
| jdbc ↔ orm | `DataSource` 共享 + `PersistenceExceptionTranslator` 统一翻译 | JPA/MyBatis 同一连接事务 |
| jdbc ↔ Boot | `DataSourceAutoConfiguration` / `JdbcTemplateAutoConfiguration` / `JdbcClientAutoConfiguration` | Boot 4 全自动装配（见第 2 节） |

> 🎯 **核心要点**：spring-jdbc 是"模板层"不是"框架层"——它不做连接池、不做 ORM、不做分布式事务，但**一切数据访问的接缝都在它这里**（DataSource 管理 + 连接事务绑定 + 异常翻译）。

### 1.1 数据访问全栈的层次关系（从下到上）

```text
应用代码（Controller → Service → DAO / Repository）
        ↓
  JdbcTemplate / JdbcClient / MyBatis Mapper / JPA Repository   ← 访问 API 层
        ↓
  spring-jdbc（DataSource 管理 + 连接事务绑定 + 异常翻译）      ← 公共底座
        ↓
  连接池（HikariCP / Druid）→ 驱动（mysql-connector-j）→ 数据库
```

| 层次 | 职责 | 谁提供 |
|------|------|--------|
| API 层 | SQL 书写与映射 | 各框架（MyBatis / JPA / JdbcClient） |
| 公共底座 | 连接 / 事务 / 异常契约 | spring-jdbc（本系列） |
| 连接与驱动 | 物理连接 | 连接池 + 驱动 |
| 数据库 | 存储 / 索引 / 锁 | MySQL / PG / Oracle |

> 🎯 理解层次后排查就有方向：SQL 层问题（映射/语法）看 API 层；连接事务问题（泄漏/不回滚）看底座层；性能问题（慢 SQL/锁）看数据库层——不要用数据库层的药治底座层的病。

### 1.2 各数据访问 starter 与 spring-jdbc 的关系

| starter | 是否依赖 spring-jdbc | 说明 |
|---------|---------------------|------|
| spring-boot-starter-jdbc | 直接依赖 | 纯 JDBC 模板 |
| spring-boot-starter-data-jpa | 传递依赖 | JPA 需要数据源与事务管理 |
| mybatis-spring-boot-starter | 传递依赖 | MyBatis 复用 DataSource 与事务 |
| spring-boot-starter-data-jdbc | 直接依赖 | 仓储层基于 JdbcTemplate |

```text
依赖方向：JPA / MyBatis / Spring Data JDBC → spring-jdbc → 连接池 + 驱动
```

> 💡 认知要点：无论用哪个 ORM，**DataSource 的创建与事务协调都落在 spring-jdbc 及其自动配置上**——所以"数据源配置在哪配"的答案永远在 `spring.datasource.*`；ORM 只负责自己的映射与执行层，这是"全家桶共用一份数据源配置"的根本原因。

延伸：既然 ORM 都依赖 spring-jdbc，那么"排查数据访问问题从哪开始"的答案也统一了——无论 MyBatis 还是 JPA 的诡异问题，先确认数据源与连接池健康（池日志、慢 SQL），再进入各自框架层排查；底层问题不会因为换了 ORM 而消失，只是换了症状。

## 2. Boot 数据访问的自动装配链

```text
spring-boot-starter-jdbc
  → DataSourceAutoConfiguration
      → 根据 classpath 选 HikariCP/Druid/Tomcat JDBC
      → 解析 spring.datasource.* → 创建 DataSource
  → DataSourceTransactionManagerAutoConfiguration
      → DataSourceTransactionManager Bean
  → JdbcTemplateAutoConfiguration
      → JdbcTemplate + NamedParameterJdbcTemplate（7.0 起废弃标记）
  → JdbcClientAutoConfiguration（Boot 4）
      → JdbcClient Bean ★
  → SQL 初始化：DataSourceInitializationConfiguration
      → schema.sql / data.sql（spring.sql.init.mode）
```

> 💡 一个依赖搞定全部：`spring-boot-starter-jdbc` = 数据源 + 连接池 + 事务管理器 + 三种模板 + SQL 脚本初始化；MyBatis/JPA 另加对应 starter 替换模板层。

### 2.1 自动装配的覆盖与定制点

| 想改什么 | 做法 |
|---------|------|
| 换连接池（HikariCP → Druid） | 排除 starter 内 HikariCP，加 `druid-spring-boot-starter` |
| 自定义 JdbcTemplate 配置 | 定义 `JdbcTemplate` Bean（Boot 条件装配自动让位） |
| 多数据源 | 自定义多个 DataSource Bean + 各自事务管理器（[07-与事务ORM集成速查](07-与事务ORM集成速查.md) 第 5 节） |
| 禁止数据源自动装配 | `spring.autoconfigure.exclude: ...DataSourceAutoConfiguration` |
| SQL 脚本初始化 | `spring.sql.init.mode: always` + schema.sql / data.sql（默认仅嵌入式库执行） |

```java
// 自定义 JdbcTemplate（追加全局查询超时）
@Bean
public JdbcTemplate jdbcTemplate(DataSource dataSource) {
    JdbcTemplate tpl = new JdbcTemplate(dataSource);
    tpl.setQueryTimeout(10);          // 全局兜底 10 秒
    return tpl;                       // Boot 检测到已有 Bean 则不再自建
}
```

> 💡 自动装配的核心机制是 `@ConditionalOnMissingBean`——**只要你自己定义了同名 Bean，Boot 就不会覆盖**；这是"既要自动装配又要定制"的官方扩展点。

### 2.2 SQL 脚本初始化的细节

| 配置 | 说明 |
|------|------|
| `spring.sql.init.mode` | `always` / `embedded`（默认）/ `never` |
| `schema.sql` | DDL，优先执行 |
| `data.sql` | DML，随后执行 |
| `spring.sql.init.continue-on-error` | 失败是否继续（默认 false） |
| 多环境 | 生产建议 `never` 或只用迁移工具（Flyway） |

> ⚠️ 生产环境禁用 schema.sql 自动执行：生产建表应由 Flyway / Liquibase 管理（带版本、可回滚审计），`spring.sql.init` 只适合本地 / 测试 / 演示——"DDL 自动执行"配置失误在真实事故里发生过多次；另外，`@Sql` 注解（spring-test）可在测试方法上执行脚本，与 spring.sql.init 互补——排查"数据为什么和预期不符"时，先确认是初始化脚本、测试脚本还是业务代码写的，三条路径混在一起是测试数据混乱的最大来源。

补充：如果确实需要在生产执行一次性 DDL，正确姿势是手动执行 + 变更记录（或走 Flyway 的 migrate 流程），而不是依赖启动时脚本；多实例部署时启动脚本还会出现"多实例同时执行"的竞争问题——同一原因，永远别在生产开 always。

## 3. 高频问题与排查速查

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| `CannotGetJdbcConnectionException` | 池耗尽/库不可达/密码错 | 先 ping 数据库；查 `HikariPool-1 - Connection is not available` 日志；看池参数与并发 |
| 连接池耗尽（request timed out） | 连接泄漏/事务未提交/池太小 | 找 `leakDetectionThreshold` 日志；检查 try-with-resources、流未关闭、事务包裹过宽 |
| 中文乱码 | 连接 URL 字符集/表字符集 | URL 加 `characterEncoding=utf8`；确认表 utf8mb4；列类型 VARCHAR/utf8mb4 |
| `queryForObject` 抛 EmptyResult | 无结果行 | 业务上"可能无"用 `optional()`/`list()` 形态 |
| 死锁/锁超时异常（1205/1213） | 并发事务交叉锁 | 索引优化 + `@Retryable(include = DeadlockLoserDataAccessException)`（[Spring-Core-07](../Spring‑Core/07-重试与弹性速查.md)） |
| 批量插入还是很慢 | MySQL 伪批量 | URL 加 `rewriteBatchedStatements=true`（[05-批量操作与存储过程速查](05-批量操作与存储过程速查.md)） |
| 事务没生效 | 自调用/类没进容器/方法非 public | `this.method()` 自调用 → 注入自身代理；检查 @Transactional 在 public 方法 |
| 事务内查不到刚插入的数据 | 隔离级别/缓存（JPA 一级缓存） | 同事务同连接应可见；JPA 混用注意 EntityManager 缓存 |
| 多数据源切换失效 | 事务已绑定第一个连接 | 事务内禁止切库；设计独立事务或分布式方案 |
| 升级 7.0 后 NamedParameterJdbcTemplate 告警 | 7.0 废弃 | 迁移 JdbcClient（[03-JdbcClient 速查](03-JdbcClient速查.md) 第 6 节） |
| 测试库数据被污染 | 测试事务未回滚 | `@Transactional` 测试默认回滚；确认测试类继承/配置 |
| SQL 脚本没执行 | `spring.sql.init.mode` 默认值 | 显式 `spring.sql.init.mode: always`（embed 时默认 always） |

> ⚠️ **排查三板斧**：① 连接类问题先看池日志与 SQL 监控；② 事务类问题先确认"代理与自调用"；③ 数据类问题（乱码/时区）先看 URL 参数与驱动版本。

### 3.1 排查方法论：一个问题三句话定位

| 步骤 | 动作 | 产出 |
|------|------|------|
| ① 复现并分层 | 错误发生在"取连接 / 执行 SQL / 映射结果 / 提交事务"哪一段 | 确定排查层 |
| ② 看日志 | `logging.level.org.springframework.jdbc=DEBUG`（打印 SQL 与参数） | 确定 SQL 与参数是否正确 |
| ③ 看池与库 | 池日志（HikariPool）、数据库慢日志 / 锁等待 | 确定是资源问题还是 SQL 问题 |

```text
示例：接口偶发超时
  ① 复现：超时发生在 update 阶段（日志显示执行时长异常）
  ② 定位：慢日志显示该 SQL 锁等待 20s → 是锁问题，不是 SQL 本身慢
  ③ 根因：事务 A 持有写锁未提交（长事务/泄漏式事务）→ 修事务边界
```

| 常见根因归类 | 症状指纹 |
|-------------|---------|
| 连接泄漏 | 池空闲连接稳定缩小 → 最终 request timed out；leakDetection 日志点名代码位置 |
| 长事务 | 锁等待堆积、undo 膨胀、从库延迟 |
| 慢 SQL | 单条执行时间长、explain 缺索引 |
| 参数问题 | SQL 正确但结果错 / 空（时区、类型转换） |
| 事务失效 | 该回滚没回滚、数据部分落库 |

> 💡 **经验**：生产事故 80% 落在"连接泄漏、长事务、慢 SQL"三个桶里——排查先按桶归类，比漫无目的翻日志高效得多。

补充一个工具位：慢日志与连接池日志是两套体系——慢日志回答"SQL 为什么慢"，池日志回答"连接为什么不够"；排查时先看池日志确认资源层正常，再看慢日志定位语句，顺序反了容易在 SQL 优化上白费功夫。

### 3.2 更多高频坑速查（补充表）

| 现象 | 根因 | 排查 / 解法 |
|------|------|------------|
| 时区差 8 小时 | 连接 URL 未设 serverTimezone | URL 加 `serverTimezone=Asia/Shanghai`；统一 UTC 存储 |
| 枚举 / 布尔映射错乱 | 驱动返回类型与字段类型不符 | 显式转换或用注解对齐（ORM 侧） |
| 大结果集内存溢出 | fetchSize 未生效 | MySQL 需 `useCursorFetch=true` 才真正流式 |
| 启动慢 | 启动即连库 | 需要时用 `LazyConnectionDataSourceProxy` |
| 测试连到生产库 | 测试配置未隔离 | `application-test.yml` + profile 强制 |

> ⚠️ MySQL 流式读取的隐藏条件：仅设 `fetchSize` 不生效——需要 URL 带 `useCursorFetch=true`（且不允许 LIMIT 优化），否则驱动仍一次拉全；这是"明明设了 fetchSize 内存还是爆"的经典原因。

延伸排查思路："大结果集内存溢出"还有个前置判断——先看是 OOM 还是 GC 压力：OOM 多半是全量 List 驻留，GC 频繁多半是批量处理中的对象创建（如 RowMapper 内 new 大对象）；前者改流式/分页，后者优化映射逻辑，别一上来就调 JVM 参数。

### 4.2 数据层面试的综合答题框架

面试官问任何数据层问题时，可以套用"三层两问"框架组织回答：

| 层 | 问题 | 示例 |
|----|------|------|
| API 层 | 用什么 API 访问 | JdbcClient / MyBatis / JPA 的选型与写法 |
| 底座层 | 连接、事务、异常怎么管理 | DataSourceUtils 绑定、翻译链 |
| 数据库层 | 数据、锁、索引层面发生了什么 | 死锁根因、慢 SQL、隔离级别 |

```text
示例（问"死锁怎么办"）：
  API 层：什么语句在抢锁（事务内更新顺序不一致）
  底座层：异常翻译成 DeadlockLoserDataAccessException（Transient）
  数据库层：索引缺失导致锁范围扩大；统一更新顺序 + 重试
```

> 🎯 这个框架的价值：**任何数据层问题都能归到三层之一**——回答时先定位层再展开，比"背答案"更能应对追问；面试官追问的本质就是"你到底理解到哪一层"，框架化的回答方式天然展示了分层认知。

最后给一个自测方法：用"三问法"检验理解——这个问题属于哪一层？这一层的核心机制是什么？如果层之间出现矛盾（如底座层说连接正常、数据库层说锁超时），以哪个为准？能连续答对三层，数据层面试基本就是"细节问答"而不是"知识拷问"了。

补充：自测清单的使用节奏——建议按"先 08 的考点清单 → 再 02/03 的追问小节 → 最后回到 08 的三层框架"循环两轮；第一轮查漏、第二轮巩固，两轮后能脱稿讲完 JdbcTemplate 链路与事务失效五场景，就达到面试要求了。
