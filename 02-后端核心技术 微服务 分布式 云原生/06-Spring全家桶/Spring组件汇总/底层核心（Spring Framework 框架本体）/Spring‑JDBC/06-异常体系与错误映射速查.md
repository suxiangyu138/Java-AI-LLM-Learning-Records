## 1. 异常翻译的价值

```text
裸 JDBC：SQLException（受检异常）——只能 catch(Exception) 笼统处理，
         无法区分"连接断了""主键冲突""锁超时"——业务代码无法精准应对。

Spring：SQLExceptionTranslator 把 SQLException 翻译为 DataAccessException（非受检）
        → 按数据库厂商错误码分类 → 业务代码可针对性处理：
          catch (DuplicateKeyException e) → 提示"重复"
          catch (CannotAcquireLockException e) → 重试
          catch (DeadlockLoserDataAccessException e) → 退避重试
```

> 🎯 **核心要点**：翻译让"数据库错误"变成**可编程应对的异常类型**——这是 JdbcTemplate 最大的隐性价值；ORM（JPA/MyBatis）也复用同一套翻译体系（MyBatis 在 Spring 集成中同样翻译）。

### 1.1 没有翻译层的业务代码长什么样（对比阅读）

```java
// 裸 JDBC：一个方法要处理多种异常，且 SQLException 只能笼统 catch
try {
    stmt.executeUpdate("INSERT INTO t_user(email) VALUES (?)", email);
} catch (SQLIntegrityConstraintViolationException e) {   // 驱动较新才有细分
    // 唯一键冲突 → 业务提示
} catch (SQLException e) {
    if (e.getErrorCode() == 1062) {          // 老驱动：查错误码，还依赖厂商
        // MySQL 唯一键冲突
    } else if (e.getErrorCode() == 1213) {   // 死锁
        // 重试
    }
    throw new RuntimeException(e);           // 最终只能这样处理
}

// Spring：翻译后按类型编程
try {
    jdbcTemplate.update("INSERT INTO t_user(email) VALUES (?)", email);
} catch (DuplicateKeyException e) {
    throw new BusinessException("邮箱已注册");
} catch (DeadlockLoserDataAccessException e) {
    return retry();                          // 死锁自动重试
}
```

| 裸 JDBC 痛点 | Spring 解决 |
|-------------|------------|
| SQLException 受检异常被迫到处声明/包装 | 非受检，可选择性捕获 |
| 错误码厂商私有、硬编码魔法数 | 错误码表统一映射为语义化类型 |
| 异常无法按"是否可重试"分类 | Transient / NonTransient 二分法 |

### 1.2 翻译的适用范围与例外

| 情形 | 是否翻译 | 说明 |
|------|---------|------|
| JdbcTemplate / JdbcClient 执行 SQL | ✅ | 走翻译链 |
| 模板内部参数绑定错误 | ✅ | 翻译为 InvalidDataAccessApiUsageException（编码错误） |
| 手工裸 JDBC（不走模板） | ❌ | SQLException 原样抛出 |
| MyBatis（Spring 集成） | ✅ | PersistenceExceptionTranslator 桥接 |
| JPA / Hibernate | ✅ | 同一桥接机制 |

值得注意的例外：**翻译只发生在模板执行路径上**——业务代码里绕过模板直接 `dataSource.getConnection()` 抛出的 SQLException 不会被翻译；这也是"统一走模板"的又一个理由。另外，翻译器只处理 SQLException，连接池自身的异常（如 HikariPool 借出超时）由池抛出，Spring 会包装为 `CannotGetJdbcConnectionException`——两类异常的来源不同，排查时先分清"池的错"还是"SQL 的错"。

补充一个边界：`SQLWarning` 不算 SQLException——驱动通过 `Statement.getWarnings()` 返回警告（如数据截断），Spring 默认忽略（`ignoreWarnings=true`）；诊断数据问题时临时关掉忽略、打印警告，往往能发现"值被截断 / 精度丢失"这类隐蔽问题。

## 2. DataAccessException 家族

```text
DataAccessException（org.springframework.dao，spring-tx 模块）
├── NonTransientDataAccessException（重试无意义）
│   ├── DataIntegrityViolationException
│   │   └── DuplicateKeyException          ★ 主键/唯一键冲突
│   ├── DataRetrievalFailureException
│   │   ├── EmptyResultDataAccessException ★ queryForObject 空结果
│   │   └── IncorrectResultSizeDataAccessException ★ 多行结果
│   ├── InvalidDataAccessResourceUsageException
│   │   └── BadSqlGrammarException         ★ SQL 语法错误
│   └── CannotGetJdbcConnectionException   ★ 拿不到连接（池耗尽/库挂了）
├── TransientDataAccessException（重试可缓解）
│   ├── ConcurrencyFailureException
│   │   ├── CannotAcquireLockException     ★ 锁等待超时
│   │   ├── DeadlockLoserDataAccessException ★ 死锁牺牲者
│   │   └── OptimisticLockingFailureException ★ 乐观锁版本冲突
│   └── QueryTimeoutException              ★ 查询超时
└── (RecoverableDataAccessException 等边缘类型)
```

> 💡 归属提示：`org.springframework.dao` 在 **spring-tx** 模块（不是 jdbc）——jdbc 的翻译器产出 tx 定义的异常族，再次印证"tx 是数据访问的公共契约层"。

### 2.1 按异常类型制定处理策略（生产实践）

| 异常 | 分类 | 推荐处理 |
|------|------|---------|
| `DuplicateKeyException` | NonTransient | 提示冲突 / 幂等返回旧数据，**不重试** |
| `DataIntegrityViolationException` | NonTransient | 参数校验问题，记日志 + 提示 |
| `BadSqlGrammarException` | NonTransient | 发布前 SQL 评审 / 测试兜底，运行时属 Bug |
| `CannotGetJdbcConnectionException` | NonTransient | 熔断 / 告警，快速失败比排队好 |
| `DeadlockLoserDataAccessException` | Transient | 退避重试 3 次（加 jitter） |
| `CannotAcquireLockException` | Transient | 检查锁等待超时配置（`innodb_lock_wait_timeout`） |
| `QueryTimeoutException` | Transient | 慢 SQL 优化 + 降级 |
| `EmptyResultDataAccessException` | 业务语义 | 业务层转 Optional 语义处理 |

```java
// 标准重试姿势（Spring Retry 2.x 写法；1.x 用 include）
@Retryable(retryFor = { DeadlockLoserDataAccessException.class,
                         CannotAcquireLockException.class },
           backoff = @Backoff(delay = 50, multiplier = 2, maxDelay = 2000))
public void transfer(long from, long to, BigDecimal amount) { ... }
```

> 🎯 关键认知：**重试只对 Transient 有效**——把 DuplicateKey 放进重试逻辑不仅无效，还可能放大冲突；错误码表（见第 4 节）就是判断"可重试 / 不可重试"的依据。

### 2.2 如何测试异常场景（数据层测试技巧）

| 场景 | 测试方式 |
|------|---------|
| 唯一键冲突 | 先插入一条，再插同键——断言 DuplicateKeyException |
| 语法错误 | 构造错误 SQL——断言 BadSqlGrammarException |
| 空结果 | 查不存在数据——断言 EmptyResultDataAccessException（或 optional 断言 empty） |
| 死锁 | 双线程交叉锁（H2 / MySQL 均可复现）——断言 DeadlockLoserDataAccessException |
| 连接失败 | 指向不存在的库 / 端口——断言 CannotGetJdbcConnectionException |

```java
@Test
@Transactional                       // 测试事务自动回滚，不污染数据
void duplicateKey_shouldThrow() {
    jdbc.sql("INSERT INTO t_user(email) VALUES (:e)").param("e", "a@b.com").update();
    assertThatThrownBy(() ->
            jdbc.sql("INSERT INTO t_user(email) VALUES (:e)").param("e", "a@b.com").update())
            .isInstanceOf(DuplicateKeyException.class);
}
```

> 💡 注意 `@Transactional` 测试的局限：它回滚的是"已提交语义"——死锁 / 锁等待这类并发异常很难在单事务测试里复现，需要独立线程 + 计数闩（CountDownLatch）编排；复杂度高时用真实数据库 + 集成测试环境，别在内存库上死磕并发语义。

补充：断言异常时不要只断言类型——用 `assertThatThrownBy(...).isInstanceOf(...).hasMessageContaining(...)` 断言关键信息（如约束名），避免"类型对但场景错"的假阳性；数据层测试的断言质量直接决定回归保护的有效性。

### 2.3 DataAccessException 的使用规范（团队实践）

| 规范 | 说明 |
|------|------|
| 不 catch 基类 | 只捕获具体子类（DuplicateKey 等），避免误吞重试类异常 |
| 不吞异常 | 捕获后必须记录或转换，禁止空 catch |
| 统一转换 | 业务层把 DataAccessException 转成业务异常（如 BizException）时保留 cause |
| 日志级别 | 非瞬态异常 WARN，瞬态异常（死锁）INFO + 重试 |
| 幂等设计 | 唯一键冲突不一定是错误——业务幂等可用 DuplicateKey 判"已处理" |

```java
try {
    createUser(u);
} catch (DuplicateKeyException e) {
    // 幂等语义：已存在则视为成功
    log.info("user {} already exists, skip", u.email());
    return existingUser(u.email());
}
```

> 🎯 面试加分：把 DuplicateKeyException 用于幂等不是投机——它是数据库唯一约束提供的原子性保证，比"先查后插"的检查-插入（check-then-act）更可靠；答出"约束即保证"这个点，数据一致性理解的深度就体现出来了。

延伸：数据访问层的异常设计规范——DAO 层不吞异常、Service 层按业务语义捕获（DuplicateKey → 提示冲突，Transient → 重试），Controller 层统一转错误码；异常类型的"翻译"从数据库到 API 边界应保持可追溯（cause 链完整），这样线上日志能一眼定位到数据库错误码，这是可观测性设计的一部分。

## 3. SQLExceptionTranslator：翻译机制

| 翻译器 | 机制 | 适用 |
|--------|------|------|
| `SQLErrorCodeSQLExceptionTranslator`（默认） | 按**数据库厂商错误码**映射 | ✅ 主流（内置 15+ 厂商错误码表） |
| `SQLStateSQLExceptionTranslator` | 按 SQLState（SQL 标准五类前缀） | 兜底/未知厂商 |
| `SQLExceptionSubclassTranslator` | 按 JDBC 4 异常子类（如 SQLIntegrityConstraintViolationException） | 驱动现代时优先 |
| 组合 | 翻译链：Subclass → ErrorCode → SQLState | 默认即此链 |

```text
翻译链（JdbcTemplate 默认）：
  SQLExceptionSubclassTranslator（子类直判）
    → SQLErrorCodeSQLExceptionTranslator（查错误码表）★
    → SQLStateSQLExceptionTranslator（SQLState 兜底）

错误码表：org.springframework.jdbc.support.sql-error-codes.xml
  （MySQL 1062 → DuplicateKeyException；MySQL 1213 → DeadlockLoser...）
```

> ⚠️ **厂商差异**：错误码是数据库私有的——同样"唯一键冲突"，MySQL 是 1062、PostgreSQL 是 23505、Oracle 是 00001——所以必须用 `DatabaseMetaData.getDatabaseProductName()` 选对厂商表；自定义错误码用 `setSqlErrorCodes` 追加。

### 3.1 翻译链源码级细节

```text
JdbcTemplate 默认装配的翻译器链：
  SQLErrorCodeSQLExceptionTranslator(dataSource)
    ├── delegate = SQLExceptionSubclassTranslator      ← 链头：JDBC 4 子类直判
    │     （SQLIntegrityConstraintViolationException → DataIntegrityViolationException）
    └── fallback = SQLStateSQLExceptionTranslator      ← 链尾：SQLState 兜底
        （类名前缀：23 → 完整性违规；40 → 事务回滚；08 → 连接异常）

SQLErrorCodeSQLExceptionTranslator 工作流程：
  1. dataSource.getConnection() → DatabaseMetaData.getDatabaseProductName()
     → 匹配 sql-error-codes.xml 中的厂商条目（MySQL/PG/Oracle/...）
  2. 按错误码查表：1062 → DuplicateKeyException
  3. 查不到 → 交给 SQLState 翻译器兜底
```

| 细节 | 说明 |
|------|------|
| 错误码表位置 | `org.springframework.jdbc.support.sql-error-codes.xml`（jar 内） |
| 厂商识别 | `DatabaseMetaData.getDatabaseProductName()`，经数据源连接获取 |
| 自定义追加 | `translator.setSqlErrorCodes(new SqlErrorCodes(){...})` 合并进表 |
| 业务级翻译 | `CustomSQLErrorCodesTranslation`：指定错误码 → 指定异常类 |
| 多数据源 | 各 DataSource 厂商不同——翻译器需按数据源分别装配 |

> 💡 面试深挖："翻译器怎么知道当前是 MySQL？"——它真的会拿一条连接查 `DatabaseMetaData`，所以翻译器一般按 DataSource 单例创建；这就是 JdbcTemplate 构造时传入 DataSource 比事后 setter 更稳妥的原因。

### 3.2 翻译与事务回滚的关系

| 问题 | 答案 |
|------|------|
| 翻译后的异常会触发回滚吗 | 会——DataAccessException 是 RuntimeException，@Transactional 默认回滚 |
| 翻译发生在提交前还是提交后 | 执行阶段翻译；提交阶段的异常（如死锁检测）同样翻译 |
| 回滚后还能继续用连接吗 | 连接被标记为坏连接，池会废弃重建——无需手动处理 |
| 自定义异常不继承 DataAccessException 会怎样 | 不会自动回滚（除非 rollbackFor 指定）——自定义 DAO 异常最好继承它 |

```text
时间线：SQL 执行 → SQLException → 翻译为 DataAccessException → 传播出代理
        → 事务管理器捕获 → 判定回滚 → rollback + 释放连接
```

> 💡 一个隐蔽点：`@Transactional` 的回滚判断发生在异常传播出代理边界时——如果 DAO 层捕获了 DataAccessException 自己处理（如重试），事务并不知道异常发生过，也就不会回滚；重试逻辑必须在事务边界内完成且不吞异常，或把重试放在事务外。

再补一个事务与翻译的联动细节：`@Transactional` 的超时（timeout 属性）在 JDBC 事务管理器下是通过"事务开始时间 + 超时秒数"判断的，超时抛 `TransactionTimedOutException`——它与 `QueryTimeoutException`（语句级超时）是两个不同机制；面试被问"事务超时和查询超时区别"，答"前者是事务生命期、后者是单条语句"即可。

## 4. 数据库错误码速查

| 场景 | MySQL | PostgreSQL | Oracle |
|------|-------|-----------|--------|
| 唯一键冲突 | 1062 | 23505 | 00001 |
| 外键违反 | 1452 | 23503 | 02291 |
| 语法错误 | 1064 | 42601 | 00900 |
| 锁等待超时 | 1205 | 55P03 | 00054 |
| 死锁牺牲者 | 1213 | 40P01 | 00060 |
| 连接拒绝 | - | - | 12541 |
| 表不存在 | 1146 | 42P01 | 00942 |

> 💡 面试加分：死锁与锁超时翻译为 **Transient 族**——配合重试（[Spring-Core-07](../Spring‑Core/07-重试与弹性速查.md) 的 @Retryable 只配 `include = DeadlockLoserDataAccessException`）是数据库并发斗争的标准姿势。

### 4.1 SQLState 五类前缀速查（SQLState 翻译器依据）

| 前缀 | 含义 | 典型代码 |
|------|------|---------|
| `08` | 连接异常 | 08001 无法连接、08006 连接断开 |
| `23` | 完整性约束违规 | 23505 唯一冲突（PG） |
| `40` | 事务回滚 | 40001 序列化失败、40P01 死锁 |
| `42` | 语法 / 访问错误 | 42601 语法错误、42P01 表不存在 |
| `HY` | 一般错误 / 驱动错误 | HY000 通用错误 |

> 💡 SQLState 是 SQL 标准定义——**跨厂商一致**，所以作为兜底翻译器；但它比厂商错误码粗（细分度不足），因此只是链尾兜底而非首选。

### 4.2 MySQL 高频错误码扩展速查

| 错误码 | 含义 | 对应异常 |
|--------|------|---------|
| 1040 | 连接数超上限（too many connections） | CannotGetJdbcConnectionException |
| 1044 / 1045 | 权限拒绝 / 密码错误 | 权限类 |
| 1064 | SQL 语法错误 | BadSqlGrammarException |
| 1146 | 表不存在 | BadSqlGrammarException |
| 1205 | 锁等待超时 | CannotAcquireLockException |
| 1213 | 死锁 | DeadlockLoserDataAccessException |
| 1364 | 非空字段未给默认值 | DataIntegrityViolationException |
| 1452 | 外键约束失败 | DataIntegrityViolationException |
| 2002 / 2003 | 无法连接服务器 | CannotGetJdbcConnectionException |
| 2013 | 连接中断（Lost connection） | 通信类（可重试） |

> 🎯 面试加分：把 2002（网络不通）、2013（连接被服务端关闭）与 1040（连接数满）区分开——三者都是"拿不到连接"，但根因分别是网络、闲置超时、资源上限，排查路径完全不同；能分清楚说明有真实排障经验。

### 4.3 错误码表使用注意事项

| 注意点 | 说明 |
|--------|------|
| 错误码随版本变化 | MySQL 8.x 与 5.7 的个别错误码有差异——以线上版本为准 |
| 驱动可能不填错误码 | 个别场景 `getErrorCode()` 返回 0——交给 SQLState 兜底 |
| 自定义错误码表要追加而非替换 | `setSqlErrorCodes` 是追加语义，不要清空内置表 |
| 同厂商多实例 | 相同错误码含义一致，可共享翻译器 |

> ⚠️ 常见误区：以为错误码表要自己维护——实际上 Spring 内置 15+ 厂商的错误码表已覆盖主流场景，绝大多数项目**不需要任何自定义**；只有用到罕见错误码或厂商方言扩展（如存储过程特定错误）时才需要追加。

最后提醒：错误码表是"映射规则"而非"文档"——排查未知错误码时直接查 `sql-error-codes.xml` 里对应厂商的 `<errorCodes>` 条目，比搜索引擎查错误码更快更准；这也是 Spring 文档推荐的第一手来源。

## 5. 翻译器的接入点

| 接入点 | 方式 |
|--------|------|
| JdbcTemplate | `tpl.setExceptionTranslator(custom)` |
| Boot 全局 | 无需配置（默认翻译链已生效） |
| 自定义错误码 | 继承翻译器 `setSqlErrorCodes(new SqlErrorCodes(){...})` |
| ORM | JPA/MyBatis-Spring 复用同一 `PersistenceExceptionTranslator`（ORM 异常 → DataAccessException） |

```java
// 自定义翻译器：追加业务错误码
SQLErrorCodeSQLExceptionTranslator translator = new SQLErrorCodeSQLExceptionTranslator();
translator.setSqlErrorCodes(new SqlErrorCodes() {{
    setProductName("MySQL");
    setBadSqlGrammarCodes(new String[]{"1064"});
    setDataIntegrityViolationCodes(new String[]{"1062", "1452"});
}});
jdbcTemplate.setExceptionTranslator(translator);
```

> 🎯 **核心要点**：翻译链是**分层兜底**设计（子类 → 错误码 → SQLState）——任何厂商任何错误都有归属；业务上"重试型异常"只认 Transient 族，"冲突型异常"认 DataIntegrityViolation 族，实现精准防御。

### 5.1 自定义翻译完整示例与面试官追问

```java
// 场景：把 MySQL 特定错误码映射为业务可识别的异常类型
public class BizSQLExceptionTranslator extends SQLErrorCodeSQLExceptionTranslator {
    @Override
    protected DataAccessException customTranslate(String task, String sql, SQLException sqlEx) {
        if (sqlEx.getErrorCode() == 3819) {               // MySQL CHECK 约束违反
            return new DataIntegrityViolationException(
                    "CHECK constraint violated: " + task, sqlEx);
        }
        if (sqlEx.getErrorCode() == 1364) {               // 非空字段未给值
            return new DataIntegrityViolationException("NOT NULL violation", sqlEx);
        }
        return null;                                      // 返回 null 继续走默认链
    }
}

// 装配到模板
JdbcTemplate tpl = new JdbcTemplate(dataSource);
tpl.setExceptionTranslator(new BizSQLExceptionTranslator(dataSource));
```

| 面试追问 | 回答锚点 |
|---------|---------|
| 翻译器是线程安全的吗 | 是（无状态，错误码表构造时固定）——可单例共享 |
| 自定义翻译与默认链的关系 | `customTranslate` 先于错误码表执行；返回 null 回落到默认链 |
| 所有异常都翻译成 DataAccessException 吗 | JdbcTemplate 内部参数错误是 `InvalidDataAccessApiUsageException`（编码错误类） |
| 为什么翻译器需要 DataSource | 需要连库查 `DatabaseMetaData` 识别厂商 |

> 🎯 面试回答模板："翻译链是三层兜底：JDBC 4 子类 → 厂商错误码表 → SQLState——分层设计保证任何数据库任何错误都有归属类型，业务只需按 Transient / NonTransient 制定策略。"
