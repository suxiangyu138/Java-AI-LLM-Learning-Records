## 1. HandlerInterceptor 三方法

```java
@Component
public class AuthInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp,
                             Object handler) throws Exception {
        // ① 处理器执行前（返回 false 短路）
        if (req.getHeader("X-Token") == null) {
            resp.sendError(HttpServletResponse.SC_UNAUTHORIZED);
            return false;
        }
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest req, HttpServletResponse resp,
                           Object handler, ModelAndView mav) {
        // ② 处理器执行后、渲染前（可改 ModelAndView）
        if (mav != null) mav.addObject("handledAt", Instant.now());
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse resp,
                                Object handler, Exception ex) {
        // ③ 渲染完成后（无论成败，finally 语义）
        log.info("request completed: {} {}", req.getMethod(), req.getRequestURI());
    }
}
```

| 方法 | 时机 | 典型用途 |
|------|------|---------|
| `preHandle` | 处理器前 | 鉴权（false 短路）、限流、日志开始 |
| `postHandle` | 执行后/渲染前 | 修改模型、性能计时（不含渲染） |
| `afterCompletion` | 渲染后 | 清理、耗时统计（含渲染） |

### 拦截器的能力边界

| 能做的事 | 做不到的事 |
|---------|-----------|
| 请求前检查（鉴权/限流/黑名单） | 拿不到控制器返回值（返回值处理在其后） |
| 请求属性传值（request.setAttribute） | 修改已写出的响应体（可包装 response 间接实现） |
| postHandle 改 ModelAndView（页面场景） | 拦截 @ResponseBody 的 JSON 输出内容 |
| 按注解/方法精细拦截（HandlerMethod） | 拦截静态资源（默认不走拦截器） |
| afterCompletion 记录完整耗时与结果 | 拦截其他 HandlerMapping 之外的处理 |

> 💡 需要"改响应体"时选型：**响应包装 Filter（HttpServletResponseWrapper）**或 **@ControllerAdvice 响应体增强**——拦截器不是干这个的；需要"拿返回值做审计"时用 AOP 或 ResponseBodyAdvice。

> 🎯 **核心要点**：`preHandle` 返回 false = **终止整个请求链**（不执行控制器、不渲染，但已通过的 afterCompletion 仍执行）；`handler` 参数通常是 `HandlerMethod`——可用 `((HandlerMethod) handler).getMethod()` 拿到注解做精细化拦截。

### 综合拦截器示例：鉴权 + 审计

```java
@Component
public class AuditInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response,
                             Object handler) throws Exception {
        if (!(handler instanceof HandlerMethod handlerMethod)) {
            return true;                                  // 非控制器请求放行
        }
        // 注解驱动：只拦带 @Audit 的接口
        Audit audit = handlerMethod.getMethodAnnotation(Audit.class);
        if (audit == null) return true;

        String token = request.getHeader("X-Token");
        if (token == null) {
            response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            return false;                                 // 短路
        }
        // 把用户信息放进请求属性，供控制器/后续拦截器读取
        request.setAttribute("currentUser", userService.resolve(token));
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        // 审计落库：谁在何时调了什么接口、结果如何
        long cost = System.currentTimeMillis() - startTime(request);
        auditLogger.log(request.getRequestURI(),
                request.getAttribute("currentUser"), response.getStatus(), cost);
    }
}
```

| 拦截器能力 | 实现方式 |
|-----------|---------|
| 按注解拦截 | `HandlerMethod.getMethodAnnotation` / `getMethod().isAnnotationPresent` |
| 跨层传值 | request.setAttribute（请求生命周期内共享） |
| 鉴权短路 | preHandle false + 写状态码 |
| 性能统计 | 开始时间放 request 属性，afterCompletion 差值 |

> 💡 `handler instanceof HandlerMethod` 判断是标准动作——HandlerExecutionChain 也可能包非注解处理器（静态资源处理器等），强转前必须判断；**拦截器里拿不到 @ResponseBody 的结果值**（返回值处理在其后），需要响应内容时用响应包装或 AOP。补充实践：拦截器按注解拦截时注意继承关系——`getMethodAnnotation` 只查方法注解，类级注解用 `HandlerMethod.getBeanType().getAnnotation(...)` 查找，接口默认方法场景需结合两者判断。

## 2. 拦截器注册与顺序

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new AuthInterceptor())
                .addPathPatterns("/api/**")            // 拦截路径
                .excludePathPatterns("/api/auth/**", "/api/public/**");  // 放行
        // 多个拦截器按注册顺序执行
    }
}
```

| 要点 | 说明 |
|------|------|
| 路径 | `addPathPatterns`/`excludePathPatterns`（PathPattern 语法，见 [03 篇第 6 节](03-控制器与请求映射速查.md)） |
| 顺序 | 注册顺序 = preHandle 执行顺序；post/after 逆序 |
| 放行 | exclude 优先级高于 include |
| 静态资源 | 默认不经过（除非 `/**` 显式） |

### 拦截器路径匹配细节

| 模式写法 | 匹配范围 | 说明 |
|---------|---------|------|
| `/api/**` | /api 下所有层级 | 最常用（含子路径） |
| `/api/*` | /api 下一级 | 不含多级子路径 |
| `/**` | 一切映射请求 | 含静态资源（慎用） |
| 无限制 | 所有控制器请求 | addInterceptors 默认 |

> ⚠️ 7.0 注意：拦截器路径同样走 PathPattern 语法——`/**` 中间段限制与控制器一致；`excludePathPatterns("/api/auth/**")` 放行优先级高于 include，**先匹配 exclude 再匹配 include**，两者都写时 exclude 生效。

> ⚠️ **注意**：拦截器只对**映射到控制器的请求**生效——静态资源/404 默认不触发；"全站都要"的横切用 Filter（[Spring-Web-06](../Spring‑Web/06-过滤链与CORS速查.md)）。

### 多拦截器执行顺序（A/B/C 推演）

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(logInterceptor);        // ① 最先注册
        registry.addInterceptor(authInterceptor);       // ②
        registry.addInterceptor(rateLimitInterceptor);  // ③ 最后注册
    }
}
```

```text
正常请求执行序列：
  log.pre → auth.pre → rate.pre → 控制器 → rate.post → auth.post → log.post
  → 渲染 → rate.after → auth.after → log.after

auth.pre 返回 false 时：
  log.pre → auth.pre(false) → auth.after → log.after（rate 完全不参与）
```

| 规则 | 记忆口诀 |
|------|---------|
| preHandle | 注册顺序执行（先进先出） |
| postHandle | 注册逆序执行（后进先出） |
| afterCompletion | 注册逆序执行（后进先出，finally 语义） |
| 短路 | 第 N 个 pre 返回 false → 仅前 N 个参与 afterCompletion |

| 常见坑 | 现象 | 根因 |
|--------|------|------|
| 拦截器不执行 | 路径未覆盖 / exclude 误写 / 静态资源 | 检查 addPathPatterns 与排除项 |
| postHandle 改模型无效 | mav 为 null | @ResponseBody 场景无视图（正常行为） |
| 拦截器执行两次 | 重复注册 | @Component + new 同时注册 |
| 拦截器里抛异常 | 后续拦截器 pre 不执行 | preHandle 内捕获处理，别靠异常传播 |

> ⚠️ 顺序陷阱：**日志拦截器要注册在第一位**（先记入）、**鉴权在业务拦截器之前**（先验证再用）；把限流放最外层可避免"无权限请求也计费限流"。

## 3. 拦截器 vs 过滤器 vs AOP

| 维度 | Filter | HandlerInterceptor | AOP |
|------|--------|--------------------|-----|
| 层面 | Servlet 容器 | Spring MVC | Spring 容器（Bean） |
| 位置 | DispatcherServlet 前 | 控制器前后 | 任意 Bean 方法 |
| 范围 | 一切请求 | 映射请求 | 切入点表达式 |
| 知道控制器吗 | 否 | ✅（HandlerMethod） | 否 |
| 典型 | 编码/CORS/安全链 | 鉴权/审计/限流 | 事务/缓存/日志 |

> 💡 选型一句话：**协议级 → Filter；请求级 → 拦截器；方法级 → AOP**；三层可以共存（Security 的过滤器链 + 业务拦截器 + @Transactional 事务 AOP 同台共舞）。

### Filter 与拦截器共存示例

```java
// Filter：协议级横切（字符编码、CORS、全站安全头）
@Configuration
public class FilterConfig {
    @Bean
    public FilterRegistrationBean<SecurityHeadersFilter> securityHeadersFilter() {
        FilterRegistrationBean<SecurityHeadersFilter> reg = new FilterRegistrationBean<>();
        reg.setFilter(new SecurityHeadersFilter());
        reg.addUrlPatterns("/*");                       // 一切请求
        reg.setOrder(Ordered.HIGHEST_PRECEDENCE);       // 最先执行
        return reg;
    }
}

// 拦截器：请求级横切（鉴权、审计、限流）——在 WebMvcConfigurer 注册
```

| 决策问题 | 选择 | 理由 |
|---------|------|------|
| 所有请求都要（含静态资源/错误页）？ | Filter | 容器层，先于 MVC |
| 只要控制器请求？ | 拦截器 | 能拿到 HandlerMethod |
| 要操作 ModelAndView？ | 拦截器 postHandle | Filter 无模型概念 |
| 按方法/注解粒度？ | AOP | 切入点表达式 |
| 要事务/缓存语义？ | AOP | 代理机制 |

> 💡 实际分层（推荐）：**Filter 管协议（编码/CORS/安全头）→ Security 管认证授权 → 拦截器管业务横切（鉴权后审计）→ AOP 管服务层（事务/缓存）**——各层职责不重叠，出现问题按层定位。

### AOP vs 拦截器深挖

| 维度 | HandlerInterceptor | Spring AOP |
|------|--------------------|-----------|
| 织入位置 | DispatcherServlet 内（请求级） | Bean 方法调用级（容器代理） |
| 能拿到什么 | HttpServletRequest/Response、HandlerMethod | 方法签名、参数、返回值、异常 |
| 时序 | 早（控制器前） | 控制器方法调用时（含内部调用链） |
| 事务共存 | 拦截器在事务代理外层 | @Transactional 本身是 AOP |
| 典型 | 鉴权、审计、限流 | 缓存、重试、幂等、日志切面 |

> 💡 判断口诀：**"跟 HTTP 请求走"的用拦截器，"跟方法调用走"的用 AOP**——登录检查是请求级的（拦截器），方法重试是调用级的（AOP）；两者可同时存在：拦截器先到（请求级），控制器方法执行时 AOP 再介入（方法级）。面试补充：控制器上的 @Transactional 之所以"失效"，正是因为事务是 AOP 代理挂在控制器 Bean 上，而拦截器在代理外层——事务边界应由服务层承担（[Spring-TX 系列](../Spring‑TX（Spring‑Transaction）/00-Spring TX组件总览.md)）。

## 4. ViewResolver 与视图渲染

```text
视图渲染链（页面场景，非 @ResponseBody）：
  控制器返回 "orders/list"
    → ViewResolverComposite（按 order 遍历）
        → ThymeleafViewResolver（Boot 4 默认模板）
        → InternalResourceViewResolver（JSP 历史）
    → 解析为 View → render(model, request, response)
```

| ViewResolver | 模板 | 7.x 状态 |
|-------------|------|---------|
| `ThymeleafViewResolver` | Thymeleaf | ✅ Boot 4 推荐（starter-thymeleaf） |
| `InternalResourceViewResolver` | JSP | 历史（Boot 内嵌容器不再默认支持 JSP） |
| `ContentNegotiatingViewResolver` | 多格式 | 少见 |
| `BeanNameViewResolver` | Bean 即视图 | 特殊 |

```java
// 控制器返回视图名（页面场景）
@Controller
public class PageController {
    @GetMapping("/orders")
    public String list(Model model) {
        model.addAttribute("orders", orderService.list());   // 模型数据
        return "orders/list";                                // → templates/orders/list.html
    }
}
```

```html
<!-- templates/orders/list.html（Thymeleaf） -->
<table>
  <tr th:each="o : ${orders}">
    <td th:text="${o.id}"></td>
    <td th:text="${o.amount}"></td>
  </tr>
</table>
```

> 🎯 **核心要点**：`@RestController`（JSON 直出）与 `@Controller`（视图渲染）的区别就在**返回值处理链**——前者走消息转换器、后者走 ViewResolver；现代后端 90% 是 JSON API，页面渲染多用于管理后台/SSR。

### ViewResolver 配置与自定义视图

```yaml
# Thymeleaf 常用配置（Boot 4）
spring:
  thymeleaf:
    prefix: classpath:/templates/     # 默认即此
    suffix: .html                     # 默认即此
    cache: true                       # 生产开缓存（开发可关）
    mode: HTML
```

```java
// 控制器返回视图名（页面场景）
@Controller
public class PageController {
    @GetMapping("/orders")
    public String list(Model model) {
        model.addAttribute("orders", orderService.list());   // 模型数据
        return "orders/list";                                // → templates/orders/list.html
    }
}
```

| 视图解析细节 | 说明 |
|------------|------|
| 视图名前缀 | 返回 `"redirect:/orders"` → 重定向；`"forward:/orders"` → 转发 |
| Model 传递 | 控制器 Model 属性 → 视图上下文（Thymeleaf `${...}`） |
| 视图不存在 | ViewResolver 解析失败 → 500（模板缺失先看 prefix/suffix） |
| 缓存 | 模板缓存生产必开（性能），开发关（热更新） |

| 场景 | 视图选型 |
|------|---------|
| 管理后台页面 | Thymeleaf（服务端渲染） |
| 前后端分离 | 无视图——JSON 直出 |
| 首屏 SEO 需求 | Thymeleaf SSR |
| 历史 JSP 系统 | JSP 兼容层（Boot 内嵌容器不支持，需外置容器） |

> ⚠️ 视图名错误形态：返回 `"orders/list"` 但 templates 下没有该文件 → `TemplateInputException`（500）；大小写敏感；先检查 prefix+suffix 拼出的完整路径；JSON 接口误返回视图名会出现"返回字符串但客户端拿到 HTML"的诡异现象——先确认方法上有没有 @ResponseBody。

### 视图渲染完整链路

```text
控制器返回 "orders/list"
  → 返回值处理器链：ViewNameMethodReturnValueHandler（无 @ResponseBody）
  → ModelAndViewContainer 收集模型 + 视图名
  → DispatcherServlet.render(mv)：
      → resolveViewName：ViewResolverComposite 按 order 遍历
          → ThymeleafViewResolver：拼 prefix+suffix 找模板
          → 找到 → 创建 ThymeleafView（携带模板名）
      → view.render(model, request, response)：
          → 模板引擎执行（解析 ${orders} 表达式）
          → 渲染结果写入 response（Content-Type: text/html）

关键点：模型（Model 属性）与视图（模板）在 render 阶段汇合
```

> 💡 面试串联：**"控制器返回字符串 → 页面"的全过程**就是"返回值处理链（13 号处理器接管）→ ViewResolverComposite（找到解析器）→ View.render（模型+模板合并）"三段——和 @ResponseBody 的"转换器直出"形成对照，一页一 JSON 两条路径都答全。

## 5. 静态资源与欢迎页

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/static/**")                    // URL 模式
                .addResourceLocations("classpath:/static/")          // 磁盘/类路径位置
                .setCachePeriod(3600);                               // 缓存秒
        // Boot 默认：/webjars/**、/static/、/public/、/resources/、/META-INF/resources/
    }
}
```

| 项 | 说明 |
|----|------|
| 默认位置 | `classpath:/static/`（Boot）等 5 个 |
| 欢迎页 | `index.html`（`WelcomePageHandlerMapping`，order=-1 优先） |
| 缓存 | `setCachePeriod`/`setCacheControl`（`Cache-Control`） |
| 版本化 | `addResourceHandler` + 内容哈希 URL（`/static-{hash}/`）防缓存陈旧 |

### 欢迎页与 webjars 细节

```text
欢迎页匹配顺序（WelcomePageHandlerMapping，order=-1）：
  / → 优先 index.html（静态欢迎页）
    → 否则 index 模板（Thymeleaf 欢迎页）
    → 否则 Spring Boot 内置错误页

webjars：/webjars/** → classpath:/META-INF/resources/webjars/
  前端库以 jar 依赖引入（如 bootstrap、jquery），Boot 自动映射
```

| 项 | 说明 |
|----|------|
| index.html 位置 | classpath:/static/index.html（Boot 默认） |
| 自定义欢迎页 | 静态目录放 index.html 即可，无需配置 |
| webjars 版本化 | URL 里带版本号（/webjars/bootstrap/5.x/css/...） |
| 生产兜底 | Nginx/CDN 接管静态资源后，MVC 资源映射可保留作为本地兜底 |

> 💡 生产要点：静态资源**由 CDN/Nginx 处理更优**——MVC 静态资源兜底本地；`Cache-Control` 用内容哈希做长期缓存（版本号 URL 方案）；webjars 前端依赖自动映射；开发期可关资源缓存（`spring.web.resources.cache.period=0`）免刷新即生效。安全提醒：静态目录里**不要放敏感文件**（配置、私钥、备份），Nginx/CDN 与 MVC 资源映射都可能被直接访问——敏感资源走接口鉴权而非静态目录。

### 静态资源缓存策略速查

| 资源类型 | 缓存策略 | 实现 |
|---------|---------|------|
| 版本化资源（hash 文件名） | 长期缓存（1 年） | `Cache-Control: max-age=31536000, immutable` |
| 非版本化静态文件 | 短缓存（5-10 分钟） | `Cache-Control: max-age=600` |
| 页面本身 | 不缓存/协商缓存 | `no-cache` + ETag/Last-Modified |
| 动态接口 | 不缓存（或业务层缓存） | - |

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        registry.addResourceHandler("/static/**")
                .addResourceLocations("classpath:/static/")
                .setCacheControl(CacheControl.maxAge(365, TimeUnit.DAYS).immutable());  // 版本化目录长期缓存
    }
}
```

> 💡 版本化实现：构建时给文件名加内容哈希（webpack output、Maven resource 插件）→ 文件名变 = 新资源 → 可放心长期缓存；用版本号 URL（`/static/v1/`）需每次发版改前缀，不如 hash 优雅。

### 资源处理常见问题

| 现象 | 根因 | 解法 |
|------|------|------|
| 静态资源 404 | 位置不在默认目录 / 自定义配置覆盖 | 检查 addResourceLocations 与默认 5 个位置 |
| 页面改了不生效 | 模板/资源缓存 | 开发期关缓存（thymeleaf.cache=false、resources.cache.period=0） |
| 资源跨域被拦 | CORS 未覆盖资源路径 | 配置 CorsRegistry 或网关统一处理 |
| webjars 404 | 依赖版本与 URL 不符 | 检查 /webjars/{lib}/{version}/ 路径 |
| 欢迎页不生效 | index.html 位置不对 | 必须 classpath:/static/index.html |

> 💡 排查口诀：**资源问题先确认"位置对没对"（默认目录/自定义 location），再查"缓存卡没卡"（开发期缓存），最后看"代理挡没挡"（Nginx/CDN 路径）**——三层顺一遍基本定位。

### 面试官追问

| 追问 | 回答锚点 |
|------|---------|
| preHandle false 后 afterCompletion 还执行吗？ | 已通过拦截器的执行（逆序），未通过的完全不参与 |
| 拦截器能拿到控制器方法注解吗？ | 能——handler 是 HandlerMethod |
| Filter 与拦截器顺序谁先？ | Filter（容器层）→ DispatcherServlet → 拦截器 |
| 页面接口和 JSON 接口怎么共存？ | @Controller + 方法级 @ResponseBody / produces 区分 |
| 静态资源为什么默认不走拦截器？ | ResourceHttpRequestHandler 由专门 HandlerMapping 处理 |
| 拦截器里能改响应体吗？ | 不能直接改——响应已在处理器链后写出；需包装 response 或用 AOP |
| 视图名"redirect:" 前缀什么含义？ | 重定向（302），配合 POST-Redirect-GET 防重复提交 |
| 拦截器注册顺序和执行顺序一致吗？ | pre 一致，post/after 相反（逆序） |
| 欢迎页和控制器 / 冲突吗？ | WelcomePageHandlerMapping order=-1 优先于注解路由 |
| 拦截器能调用数据库吗？ | 能（组件注入），但高并发路径慎用——拦截器每请求执行，慢查询会放大 |

> 🎯 本模块收官：拦截器（横切时机与顺序）+ 视图（渲染链路与选型）+ 静态资源（缓存与版本化）三段合起来就是"横切处理与页面渲染"的完整答案；自测：能否默写 pre/post/after 三方法的执行顺序与短路语义？能否讲清 Filter/拦截器/AOP 三层的选型边界？能否画出"控制器返回视图名到 HTML 输出"的完整链路？能否说清静态资源缓存策略（hash 长期缓存 / 页面 no-cache）的取舍？
