## 1. 校验体系总览

```text
三层校验（职责边界）：
  ① 协议层：Spring 框架异常（400/415/406）——DefaultHandlerExceptionResolver（见 05 篇）
  ② 参数层：Bean Validation（jakarta.validation）——@Valid/@Validated 触发
  ③ 业务层：自定义业务异常 + @ExceptionHandler

  参数校验失败 → MethodArgumentNotValidException（@RequestBody）
            或 BindException（表单/@ModelAttribute）→ 400
```

| 组件 | 说明 |
|------|------|
| Bean Validation（JSR 380） | `jakarta.validation` 标准：`@NotNull` 等注解 + Validator 执行 |
| Hibernate Validator | 默认实现（Boot 自动装配） |
| Spring 集成 | `LocalValidatorFactoryBean`（Validator 适配 + 国际化） |
| 触发 | `@Valid`（JSR）/ `@Validated`（Spring，支持分组） |

> 🎯 **核心要点**：校验是"标准注解 + 标准实现"——Spring 只负责**在参数解析时触发**（`MethodValidationInterceptor`/参数解析器内校验）；写 `@NotNull` 不写实现类，Hibernate Validator 自动生效（Boot 4 默认）。

### 校验触发时机（参数解析器内部）

```text
@RequestBody 场景：
  ① RequestResponseBodyMethodProcessor 用转换器反序列化 JSON → 对象
  ② validateIfApplicable：检测 @Valid/@Validated → 调用 Validator.validate
  ③ 校验失败 → MethodArgumentNotValidException（绑定结果含全部字段错误）
     → 异常解析链 → 全局 Advice 统一 400

@ModelAttribute 场景：
  ① WebDataBinder 绑定表单/查询参数 → 对象
  ② binder.validate()（@Valid 触发）→ 失败进 BindingResult
  ③ 方法签名带 BindingResult 参数 → 手动处理；不带 → BindException 冒泡

服务层方法级：
  @Validated 类上 + 参数注解 → MethodValidationInterceptor（AOP）→ ConstraintViolationException
```

| 触发点 | 失败异常 | 处理方 |
|--------|---------|--------|
| @RequestBody | MethodArgumentNotValidException | Advice（推荐） |
| @ModelAttribute 无 BindingResult | BindException | Advice |
| @ModelAttribute + BindingResult | 进 BindingResult | 方法内手动 |
| 服务层方法级 | ConstraintViolationException | Advice（需单独处理） |

> ⚠️ 校验时机都在**转换/绑定之后**——JSON 格式都解析不了时抛的是 HttpMessageNotReadableException（不是校验异常）；"校验不生效"排查顺序：注解位置（字段上）→ @Valid 是否带上 → 实现依赖是否引入（starter-validation）。

### 三层校验的职责边界

| 层 | 谁在做 | 校验什么 | 失败表现 |
|----|--------|---------|---------|
| 协议层 | Spring 框架 | 参数存在性/类型/媒体类型 | 400/415/406（DefaultHandlerExceptionResolver） |
| 参数层 | Bean Validation | 字段规则（非空/格式/范围） | 400（MethodArgumentNotValid 等） |
| 业务层 | 业务代码 | 状态机/余额/权限/依赖关系 | 4xx 业务错误（自定义异常 + Advice） |

> 💡 边界心法：**协议层管"能不能解析"，参数层管"值合不合规"，业务层管"业务允不允许"**——三层缺一不可：只做参数校验不做业务校验会漏掉"金额超余额"；只做业务校验不做参数校验会漏掉"类型错误 500"；先分层再写校验代码，职责不重叠。

## 2. @Valid 与 @Validated

| 注解 | 来源 | 能力 | 场景 |
|------|------|------|------|
| `@Valid` | jakarta.validation（JSR） | 级联校验（嵌套对象）、触发校验 | @RequestBody/@ModelAttribute/参数 |
| `@Validated` | Spring | **分组校验**、类级校验（方法参数） | @RequestBody 分组 / 方法级校验 |

```java
// @RequestBody + @Valid（最常用）
@PostMapping
public Order create(@Valid @RequestBody OrderCreateCmd cmd) { ... }

// 级联校验：cmd 里的嵌套对象也要校验
public class OrderCreateCmd {
    @NotBlank(message = "userId is required")
    private String userId;
    @NotNull @Positive
    private BigDecimal amount;
    @Valid                       // 级联：嵌套对象内部校验也执行
    private Address address;
}

// 分组校验（@Validated + groups）：不同操作不同规则
public interface CreateGroup {}
public interface UpdateGroup {}

public class OrderCmd {
    @Null(groups = CreateGroup.class)          // 创建时 id 必须为空
    @NotNull(groups = UpdateGroup.class)       // 更新时 id 必须存在
    private Long id;
}

@PostMapping
public Order create(@Validated(CreateGroup.class) @RequestBody OrderCmd cmd) { ... }
```

### 分组校验的使用细节

| 要点 | 说明 |
|------|------|
| 分组接口 | 纯标记接口（`interface CreateGroup {}`），无方法无字段 |
| 默认组 | 不指定 groups 的注解属于 Default 组 |
| 继承关系 | 分组接口可继承（CreateGroup extends BasicGroup） |
| 顺序控制 | @GroupSequence 强制按序校验（先基础后业务） |
| 级联分组 | 嵌套对象级联时可指定 `@Validated(子组)` 传递分组 |

> ⚠️ 常见误区：分组注解**不执行**时先查"是否指定了 groups"——`@NotNull(groups = CreateGroup.class)` 在 `@Valid`（无分组参数）下不会触发，必须 `@Validated(CreateGroup.class)`；分组与默认组混用时，默认注解（无 groups）在任意分组下都会执行。

> 💡 方法级校验（非 Web）：`@Validated` 标在类上，方法参数加校验注解，`MethodValidationPostProcessor` 生效——服务层 `@Validated` + 参数 `@NotNull` 是"防御式编程"标配。

### 服务层方法级校验（完整示例）

```java
@Service
@Validated                                    // 类级：开启方法参数校验（AOP 代理）
public class OrderService {

    public Order create(@Valid @NotNull OrderCreateCmd cmd) { ... }

    public Order getById(@NotNull(message = "id 不能为空") Long id) {
        // 参数校验失败 → ConstraintViolationException（注意与 Web 校验异常不同）
    }
}

// Advice 统一处理服务层校验异常
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(ConstraintViolationException.class)
    public ProblemDetail handleConstraint(ConstraintViolationException e) {
        String msg = e.getConstraintViolations().stream()
                .map(v -> v.getPropertyPath() + ": " + v.getMessage())
                .collect(Collectors.joining("; "));
        return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, msg);
    }
}
```

> 💡 三层校验异常的归口：Web 参数 `MethodArgumentNotValidException`、表单 `BindException`、服务层 `ConstraintViolationException`——Advice 里三个异常各写一个 @ExceptionHandler，前端永远收到统一结构（完整代码见 [05 篇第 3 节](05-异常处理速查.md)）。

## 3. 校验注解速查

| 注解 | 语义 | 常用 |
|------|------|------|
| `@NotNull` | 非 null | ★ |
| `@NotEmpty` | 非 null 且非空（集合/字符串） | ★ |
| `@NotBlank` | 非 null 且含非空白字符 | ★ 字符串 |
| `@Size(min, max)` | 长度/大小范围 | ★ |
| `@Min` / `@Max` | 数值下/上限 | ★ |
| `@Positive` / `@PositiveOrZero` | 正数 / 非负 | ★ |
| `@Email` | 邮箱格式 | ★ |
| `@Pattern(regexp)` | 正则 | 自定义格式 |
| `@Past` / `@Future` | 过去/未来时间 | 时间业务 |
| `@DecimalMin` / `@DecimalMax` | BigDecimal 边界 | 金额 |

```java
public record OrderCreateCmd(
        @NotBlank(message = "{order.userId.required}") String userId,   // 国际化消息键
        @NotNull @DecimalMin("0.01") BigDecimal amount,
        @Size(max = 200) String remark,
        @Pattern(regexp = "\\d{11}") @NotBlank String phone
) { }
```

> ⚠️ **消息国际化**：`message = "{order.userId.required}"` 花括号 = 从 MessageSource 取文案（配合 [Spring-Context-06](../Spring‑Context/06-国际化与资源访问速查.md)）；`@NotNull` 与 `@NotBlank` 对空字符串语义不同——字符串判空用 NotBlank。

### 进阶校验注解与常见坑

| 注解 | 语义 | 典型场景 |
|------|------|---------|
| `@Digits(integer, fraction)` | 整数位/小数位上限 | 金额、数量 |
| `@Range(min, max)` | 数值范围（Hibernate 扩展） | 页大小 1-100 |
| `@Length(min, max)` | 字符串长度（Hibernate 扩展） | 备注长度 |
| `@CreditCardNumber` | Luhn 校验 | 卡号 |
| `@URL` | URL 格式 | 跳转地址 |
| `@AssertTrue` / `@AssertFalse` | 布尔断言 | 协议条款勾选 |
| `@Null` | 必须为空 | 分组场景（创建时 id 为空） |

| 常见坑 | 现象 | 根因 | 解法 |
|--------|------|------|------|
| 校验不生效 | 接口不报 400 | 漏 @Valid / 注解在 getter 上 / 缺 starter-validation | 参数加 @Valid；注解放字段 |
| 空字符串通过 | @NotNull 对 "" 放行 | 语义不同 | 字符串用 @NotBlank |
| 嵌套对象不校验 | 内层字段无效 | 缺 @Valid 级联 | 嵌套字段加 @Valid |
| 分组不生效 | 分组注解未执行 | @Valid 不支持分组 | 换 @Validated(Group.class) |
| 金额精度 | 校验结果不准 | Double 字段 | BigDecimal + @Digits |

```java
public record PaymentCmd(
        @NotNull @Digits(integer = 10, fraction = 2) BigDecimal amount,  // 最多 10 位整数 2 位小数
        @Range(min = 1, max = 100) int pageSize,
        @Length(min = 2, max = 200) String remark
) { }
```

> 💡 选型：标准注解（jakarta.validation）优先，Hibernate 扩展（@Range/@Length）次之，自定义注解最后——标准注解可移植（换实现库不换代码）。

### 校验消息国际化配置

```properties
# ValidationMessages.properties（默认中文，类路径根目录）
order.userId.required=用户不能为空
order.amount.invalid=金额必须在 0.01 以上

# ValidationMessages_en.properties
order.userId.required=userId is required
order.amount.invalid=amount must be >= 0.01
```

```java
public record OrderCreateCmd(
        @NotBlank(message = "{order.userId.required}") String userId,  // {key} = MessageSource 查找
        @NotNull @DecimalMin(value = "0.01", message = "{order.amount.invalid}") BigDecimal amount
) { }
```

| 国际化要点 | 说明 |
|-----------|------|
| 文件位置 | `ValidationMessages*.properties`（classpath 根，Hibernate Validator 默认） |
| 花括号语法 | `{key}` 优先查 MessageSource，未命中用注解默认 message |
| 语言切换 | 依赖 LocaleResolver 解析的 Locale |
| 不推荐 | 直接硬编码中文在注解 message（改文案要改代码） |

> 💡 生产建议：**message 统一用消息键**（哪怕只有一个语言）——后续加语言或改文案都只动 properties，不动代码；校验消息与业务错误消息（[05 篇第 4 节](05-异常处理速查.md)）走同一套 MessageSource。

## 4. BindingResult 与错误处理

```java
// 方式一：@RequestBody —— 校验失败直接抛 MethodArgumentNotValidException（Advice 统一处理）

// 方式二：@ModelAttribute + BindingResult —— 手动处理错误
@PostMapping("/form")
public String submit(@Valid @ModelAttribute OrderForm form,
                     BindingResult bindingResult) {
    if (bindingResult.hasErrors()) {
        List<String> errors = bindingResult.getFieldErrors().stream()
                .map(f -> f.getField() + ":" + f.getDefaultMessage())
                .toList();
        return "form-error";                      // 回显错误页
    }
    return "ok";
}
```

| 要点 | 说明 |
|------|------|
| 规则 | `BindingResult` 必须紧跟被校验参数之后（否则 500） |
| 错误对象 | `FieldError`（字段）、`ObjectError`（对象级） |
| 全局处理 | @RequestBody 校验异常走 @ExceptionHandler（见 [05-异常处理速查](05-异常处理速查.md)） |
| 400 vs 手动 | 现代 API 全部走 Advice 统一 400 ProblemDetail |

### 表单回显完整示例（@ModelAttribute + BindingResult）

```java
@Controller
public class FormController {

    @PostMapping("/orders/form")
    public String submit(@Valid @ModelAttribute OrderForm form,
                         BindingResult bindingResult,
                         Model model) {
        if (bindingResult.hasErrors()) {
            // 回显：把错误与已填数据带回表单页
            model.addAttribute("errors", bindingResult.getAllErrors());
            model.addAttribute("form", form);
            return "order-form";                    // 回到表单页显示错误
        }
        orderService.create(form);
        return "redirect:/orders";                  // 成功 → 重定向（POST-Redirect-GET 模式）
    }
}
```

| 表单处理要点 | 说明 |
|------------|------|
| BindingResult 位置 | 必须紧跟被校验参数之后（否则 500） |
| 回显数据 | 表单对象放 model，模板里 `th:field` 自动回填 |
| 重定向模式 | 成功用 redirect 防止重复提交；临时数据用 FlashMapManager |
| 现代替代 | 前后端分离后表单场景已少，API 模式为主 |

> 🎯 **核心要点**：两种处理模式——**API（@RequestBody）让异常冒泡给全局 Advice**；**表单（@ModelAttribute）用 BindingResult 回显**；千万别在方法里 catch 校验异常自己吞。

### 全局统一校验错误（生产代码）

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // @RequestBody 校验失败
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleMethodArgumentNotValid(MethodArgumentNotValidException e) {
        List<FieldError> errors = e.getBindingResult().getFieldErrors();
        String msg = errors.stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining("; "));
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, msg);
        pd.setProperty("code", "VALIDATION_FAILED");
        pd.setProperty("fields", errors.stream().map(FieldError::getField).toList());
        return pd;
    }

    // 表单绑定失败（@ModelAttribute 未带 BindingResult 时冒泡至此）
    @ExceptionHandler(BindException.class)
    public ProblemDetail handleBind(BindException e) {
        String msg = e.getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, msg);
    }
}
```

| 要点 | 说明 |
|------|------|
| 字段错误列表 | FieldError 有 field / rejectedValue / defaultMessage |
| 国际化 | defaultMessage 可用 {key} 占位（MessageSource 解析） |
| 扩展字段 | code 固定 + fields 列表 → 前端可逐字段标红 |
| 别吞校验错误 | Advice 统一处理 = 结构一致 + 日志集中 |

> ⚠️ 注意：`BindException` 与 `MethodArgumentNotValidException` 是两个不同异常（前者是 DataBinder 绑定+校验、后者是 @RequestBody 参数解析）——Advice 里两个都要处理，否则表单场景 500。

## 5. DataBinder 绑定机制（7.1 变化）

```text
WebDataBinder 绑定流程（@ModelAttribute 表单/查询参数 → 对象）：
  1. 创建目标对象（构造器/无参 + setter）
  2. 遍历请求参数 → 属性路径匹配（user.address.city 级联）
  3. 类型转换（ConversionService）
  4. 数据绑定安全：allowedFields/disallowedFields 白/黑名单（★ 安全边界）

  7.1 变化（#36802）：disallowedFields 废弃（黑名单容易漏）
    → 推荐：不可变对象构造器绑定（record/主构造器）或 allowedFields 白名单
```

```java
// 7.1 推荐一：record 构造器绑定（不可变 + 天然白名单）
public record OrderQuery(String status, int page, int size) { }

// 7.1 推荐二：显式白名单（安全收紧）
@InitBinder
public void initBinder(WebDataBinder binder) {
    binder.setAllowedFields("status", "page", "size");   // 只允许这些字段
}

// 7.x 已支持：构造器绑定（6.1+，用于不可变 DTO）
@ModelAttribute
public OrderQuery bind(OrderQuery query) { return query; }
```

> ⚠️ **绑定安全**：无白名单时请求参数可注入 POJO 任意字段（**批量赋值漏洞**经典场景：`admin=true` 注入权限字段）——对外绑定对象必须用 record/白名单；7.1 废弃 disallowedFields 正是因为它"漏一个就破防"。

### DataBinder 绑定细节与常见坑

| 绑定行为 | 说明 |
|---------|------|
| 属性路径 | 点号级联：`user.address.city=xxx` 逐级 set |
| 类型转换 | ConversionService（String→int/Date/enum 等），失败 → TypeMismatchException（400） |
| 数组/集合 | `ids=1&ids=2` → List<Integer> |
| record 绑定 | 主构造器参数按名匹配（7.x 推荐） |
| 字段大小写 | 首字母小写匹配（`userId` ↔ 请求 `userId`）；`UserID` 不匹配 |
| 日期格式 | 默认 ISO/容器 Locale；自定义需 @DateTimeFormat |

```java
// 全局日期格式绑定（@InitBinder 放 @ControllerAdvice 即全局）
@ControllerAdvice
public class GlobalBinderAdvice {
    @InitBinder
    public void initBinder(WebDataBinder binder) {
        binder.addCustomFormatter(new DateFormatter("yyyy-MM-dd"));
    }
}

// 字段级格式（更精确）
public record QueryCmd(
        @DateTimeFormat(pattern = "yyyy-MM-dd HH:mm") LocalDateTime from
) { }
```

> 💡 绑定 vs 校验边界：绑定负责"参数 → 对象的类型转换"，校验负责"对象值的业务规则"——类型都转不过去时抛绑定异常（400），转过去但不合规则才走校验注解；排查 400 时先分清是"转不了"还是"不合规"。

### 构造器绑定的迁移示例（7.1 推荐）

```java
// 6.x 风格：无参构造 + setter + disallowedFields 黑名单（7.1 废弃）
// 7.x 风格一：record 构造器绑定（不可变 + 天然白名单）
public record OrderQuery(String status, int page, int size) { }

// 7.x 风格二：主构造器绑定（普通类同样适用）
public class OrderQuery {
    private final String status;
    private final int page;
    private final int size;

    public OrderQuery(String status, int page, int size) {
        this.status = status;
        this.page = page;
        this.size = size;
    }
    // getter 略
}
```

> 🎯 迁移要点：**构造器绑定天然只接收构造参数**——请求参数里多传的任何字段（如 admin=true）都没有对应构造参数，自动被忽略，从根上消灭批量赋值漏洞。若存量代码依赖 setter 绑定无法立即改造，过渡期用 `binder.setAllowedFields(...)` 显式白名单，但注意**白名单也要随 DTO 演进维护**——新增字段忘记加白名单会静默绑定失败（字段值丢失），这是白名单方案的主要维护成本。

## 6. 自定义校验器

```java
// 方式一：自定义注解（跨字段校验，如金额必须为正且<余额）
@Target({FIELD, PARAMETER})
@Retention(RUNTIME)
@Constraint(validatedBy = AmountValidator.class)
public @interface ValidAmount {
    String message() default "amount invalid";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class AmountValidator implements ConstraintValidator<ValidAmount, BigDecimal> {
    @Override
    public boolean isValid(BigDecimal value, ConstraintValidatorContext ctx) {
        return value != null && value.signum() > 0 && value.scale() <= 2;
    }
}

// 方式二：类级 Validator（跨字段：开始<结束）
public class DateRangeValidator implements ConstraintValidator<ValidRange, RangeCmd> {
    public boolean isValid(RangeCmd v, ConstraintValidatorContext ctx) {
        return v.start().isBefore(v.end());
    }
}
```

### 类级跨字段校验完整示例

```java
// 注解：标在类上（跨字段校验的固定姿势）
@Target(TYPE)
@Retention(RUNTIME)
@Constraint(validatedBy = OrderPeriodValidator.class)
public @interface ValidOrderPeriod {
    String message() default "结束时间必须晚于开始时间";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

// 校验器：泛型参数是整个对象，可访问所有字段
public class OrderPeriodValidator implements ConstraintValidator<ValidOrderPeriod, OrderTimeCmd> {

    @Override
    public boolean isValid(OrderTimeCmd cmd, ConstraintValidatorContext ctx) {
        if (cmd.start() == null || cmd.end() == null) {
            return true;                       // 空值交给 @NotNull 管（校验器只做业务规则）
        }
        return cmd.start().isBefore(cmd.end());
    }
}

// 使用：注解放类上
@ValidOrderPeriod
public record OrderTimeCmd(
        @NotNull LocalDateTime start,
        @NotNull LocalDateTime end
) { }
```

> 💡 设计要点：**跨字段校验三原则**——注解放类上（字段注解拿不到兄弟字段）、空值放行交给 @NotNull（职责单一）、失败时可用 `ctx.disableDefaultConstraintViolation()` 自定义错误消息指向具体字段。生产补充：跨字段校验器的空值放行不是偷懒——`@NotNull` 负责"没传"，你的校验器负责"传了但不合理"，两个职责拼起来才完整；顺序上先声明式注解后自定义校验器，避免校验器里重复判空代码。

> 💡 扩展点：`ConstraintValidator` 实现自动被 Hibernate Validator 发现（SPI）；跨字段校验把注解放**类**上（非字段）；消息默认值 + groups 与标准注解一致。

### 自定义校验器进阶：依赖注入与组合

```java
// ConstraintValidator 支持注入 Spring Bean（查库校验唯一性）
@Component
public class UniquePhoneValidator implements ConstraintValidator<UniquePhone, String> {
    private final UserRepository userRepository;

    public UniquePhoneValidator(UserRepository userRepository) {   // 构造器注入
        this.userRepository = userRepository;
    }

    @Override
    public boolean isValid(String phone, ConstraintValidatorContext ctx) {
        return !userRepository.existsByPhone(phone);               // 查库校验唯一
    }
}
```

| 进阶用法 | 说明 |
|---------|------|
| 注入依赖 | Validator 由 Spring 管理时 ConstraintValidator 可注入 Bean |
| 自定义消息 | `ctx.disableDefaultConstraintViolation()` + `buildConstraintViolationWithTemplate` |
| 组合注解 | 注解上叠注解（@NotBlank + @Pattern 合成一个 @ValidPhone） |
| 校验顺序 | 默认按注解顺序；`@GroupSequence` 控制分组顺序 |

### 面试官追问

| 追问 | 回答锚点 |
|------|---------|
| @Valid 与 @Validated 区别？ | JSR 触发 vs Spring 分组/方法级 |
| 校验失败返回什么异常？ | @RequestBody → MethodArgumentNotValidException；表单 → BindException |
| 批量赋值漏洞怎么防？ | record 构造器绑定 / allowedFields 白名单（7.1 disallowedFields 废弃） |
| 国际化校验消息怎么配？ | message 用 {key} + MessageSource + ValidationMessages.properties |
| 跨字段校验怎么写？ | 注解放类上 + ConstraintValidator 泛型取整个对象 |
| 校验和绑定谁先谁后？ | 先绑定（类型转换）后校验（值规则） |
| 校验性能要注意什么？ | 校验是反射执行注解，数量可控（几十个以内）无感知；避免校验器里查库（高并发场景） |
| record 类校验支持吗？ | 支持——注解标在构造参数（record 组件）上即可 |
