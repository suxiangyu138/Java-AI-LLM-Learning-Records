## 1. 异常解析链

```text
控制器/参数解析/转换器抛异常 → DispatcherServlet.processDispatchResult
  → HandlerExceptionResolver 链（按 order）：
      1. ExceptionHandlerExceptionResolver ★（@ExceptionHandler 方法）
      2. ResponseStatusExceptionResolver（@ResponseStatus/ResponseStatusException）
      3. DefaultHandlerExceptionResolver（框架标准异常 → 状态码，如 400/404/405）

  链上解析器"能吃"就返回 ModelAndView/错误体；全不处理 → 500 或 Boot 错误页
```

| 解析器 | 处理对象 | 优先级 |
|--------|---------|:---:|
| `ExceptionHandlerExceptionResolver` | `@ExceptionHandler` 方法（含 @ControllerAdvice） | 最高 |
| `ResponseStatusExceptionResolver` | `@ResponseStatus` 注解 / `ResponseStatusException` | 中 |
| `DefaultHandlerExceptionResolver` | MVC 框架标准异常（HttpMessageNotReadable → 400 等） | 兜底 |

> 🎯 **核心要点**：异常处理是**链式解析**——你的 @ExceptionHandler 优先，框架标准异常兜底；`ResponseStatusException` 是"快速改状态码"的轻量异常（`throw new ResponseStatusException(HttpStatus.NOT_FOUND, "not found")`）。

### 异常链源码级细节

```text
doDispatch 捕获异常 → processDispatchResult → processHandlerException：
  ① 若 response 已提交（流已写出一部分）→ 直接 rethrow（无法再改响应）
  ② 遍历 HandlerExceptionResolver 链：
     ExceptionHandlerExceptionResolver：找 @ExceptionHandler（方法级 → Advice 级）
     ResponseStatusExceptionResolver：@ResponseStatus / ResponseStatusException
     DefaultHandlerExceptionResolver：框架标准异常 → 状态码
  ③ 第一个返回非 null ModelAndView 的解析器终止链
  ④ 全不处理 → 交给容器错误页（Boot 4 → ErrorController / ProblemDetail）
```

| 解析器返回 | 含义 |
|-----------|------|
| ModelAndView 非空 | 已处理（错误视图或 ProblemDetail） |
| 响应已被转换器写出 | 已处理（@ResponseBody 场景，状态码由 @ResponseStatus 决定） |
| null | 未处理，交给下一个解析器 |

| 场景 | 异常 | 状态码 | 谁处理 |
|------|------|:---:|--------|
| 无路由 | NoHandlerFoundException | 404 | Default |
| JSON 解析失败 | HttpMessageNotReadableException | 400 | Default |
| 校验失败 | MethodArgumentNotValidException | 400 | Advice（业务化） |
| 业务不存在 | 自定义 NotFoundException | 404 | Advice |
| 未知异常 | Exception | 500 | Advice 兜底 |

> 💡 面试细节：`@ExceptionHandler` 方法上的 `@ResponseStatus` 决定状态码；若方法返回 `ResponseEntity` 则状态码来自它；`ProblemDetail` 自带 status——三者优先级以实际响应对象为准。

### ResponseStatusException vs 自定义异常

| 维度 | ResponseStatusException | 自定义业务异常 |
|------|------------------------|----------------|
| 用法 | `throw new ResponseStatusException(404, "not found")` | 预定义异常类 + 字段 |
| 适用 | 临时/一次性状态码 | 长期复用的业务错误 |
| 扩展字段 | 有限（detail/cause/ProblemDetail） | 任意（错误码/参数/上下文） |
| 国际化 | 不便 | 消息键可国际化 |
| 维护成本 | 低（随手一抛） | 中（需定义体系） |

> 💡 选型建议：**原型/胶水代码用 ResponseStatusException，核心业务建自定义异常体系**——自定义异常统一携带错误码与上下文，Advice 集中翻译，可维护性远好于散落的 status 抛出。

## 2. @ExceptionHandler 速查

```java
@RestController
public class OrderController {
    @ExceptionHandler(IllegalArgumentException.class)      // 方法内异常处理
    public ProblemDetail handleBadArg(IllegalArgumentException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, e.getMessage());
    }
}
```

| 要点 | 说明 |
|------|------|
| 作用域 | 所在控制器的方法异常 |
| 匹配 | 按异常类型（含子类）；多参数可带 `WebRequest`/`HttpServletRequest` |
| 返回 | ModelAndView / ProblemDetail / ResponseEntity / String（视图） |
| 组合 | `@ExceptionHandler({A.class, B.class})` 多异常一个方法 |
| 限制 | 只管本控制器（全局用 @ControllerAdvice） |

> 💡 方法内 `@ExceptionHandler` 适合"单控制器特殊错误"；业务统一错误模型放全局（下一节）。

### @ExceptionHandler 完整用法示例

```java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    // 多异常一个方法 + 附加 WebRequest 参数
    @ExceptionHandler({IllegalArgumentException.class, IllegalStateException.class})
    public ResponseEntity<ProblemDetail> handleBadState(Exception e, WebRequest request) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST, e.getMessage());
        pd.setProperty("path", request.getDescription(false));   // 附加请求信息
        return ResponseEntity.badRequest().body(pd);
    }

    // 精确优先：子类异常有单独处理器时不会被父类抢
    @ExceptionHandler(OrderNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ProblemDetail handleNotFound(OrderNotFoundException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    }
}
```

| 用法要点 | 说明 |
|---------|------|
| 异常匹配 | 按类型 + 子类；多个候选取**最精确**（不是注册顺序） |
| 方法参数 | 异常、`WebRequest`、`HttpServletRequest/Response`、`HandlerMethod` |
| 返回类型 | `ResponseEntity` / `ProblemDetail` / `ModelAndView` / `void`（写原生响应） |
| 继承注意 | 子类处理器存在时父类处理器不接管——别在父类兜底里漏了子类场景 |

### 自定义异常体系设计（生产模板）

```java
// 基础业务异常：携带 HTTP 状态 + 业务错误码 + 扩展字段
public class BizException extends RuntimeException {
    private final HttpStatus status;
    private final String code;
    private final Map<String, Object> properties = new HashMap<>();

    public BizException(HttpStatus status, String code, String message) {
        super(message);
        this.status = status;
        this.code = code;
    }

    public BizException withProperty(String key, Object value) {
        this.properties.put(key, value);
        return this;
    }

    // getter 略...
}

// 具体业务异常
public class OrderNotFoundException extends BizException {
    public OrderNotFoundException(Long orderId) {
        super(HttpStatus.NOT_FOUND, "ORDER_NOT_FOUND",
                "订单 " + orderId + " 不存在");
        withProperty("orderId", orderId);
    }
}

// Advice 统一翻译
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    public ProblemDetail handleBiz(BizException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(e.getStatus(), e.getMessage());
        pd.setProperty("code", e.getCode());
        e.getProperties().forEach(pd::setProperty);
        return pd;
    }
}
```

> 🎯 这套模板解决三个痛点：**状态码与业务码分离**（网关看 status、前端看 code）、**扩展字段天然携带**（订单号/库存）、**Advice 只有一个方法**（新异常只需建类，不用改 Advice）。

> ⚠️ 常见误解：`@ExceptionHandler(Exception.class)` 会拦截一切——包括 MVC 框架自己抛的异常；兜底方法里**必须记录日志**（否则线上问题不可见），且不要返回堆栈细节给客户端。

## 3. @ControllerAdvice 全局异常

```java
@RestControllerAdvice                                // = @ControllerAdvice + @ResponseBody
public class GlobalExceptionHandler {

    // 业务异常 → 404 问题体
    @ExceptionHandler(OrderNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ProblemDetail handleNotFound(OrderNotFoundException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
                HttpStatus.NOT_FOUND, e.getMessage());
        pd.setTitle("Order Not Found");
        pd.setProperty("orderId", e.getOrderId());     // 附加字段
        return pd;
    }

    // 参数校验失败 → 400（@Valid 触发）
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, msg);
    }

    // 兜底：未处理异常 → 500（不泄漏堆栈）
    @ExceptionHandler(Exception.class)
    public ProblemDetail handleOther(Exception e) {
        log.error("unhandled", e);
        return ProblemDetail.forStatusAndDetail(
                HttpStatus.INTERNAL_SERVER_ERROR, "server error");
    }
}
```

| 能力 | 说明 |
|------|------|
| 全局范围 | 所有控制器异常 |
| 附加注解 | `@InitBinder`（全局绑定器）、`@ModelAttribute`（全局模型）可同放 |
| 优先级 | 具体异常类型 > 父类；`Exception.class` 兜底 |
| 顺序控制 | `@Order` 多个 Advice 排序 |

> ⚠️ **404 还是 500 的检查清单**：`NoHandlerFoundException`（无路由）→ 404 需 `spring.mvc.throw-exception-if-no-handler-found`（Boot）；`MethodArgumentNotValidException`（校验）→ 400；`HttpMessageNotReadableException`（JSON 解析失败）→ 400；兜底 Exception → 500。

### 多个 Advice 的协作与排序

```java
// Advice A：业务异常（先执行）
@RestControllerAdvice
@Order(1)
public class BusinessExceptionAdvice {
    @ExceptionHandler(BizException.class)
    public ProblemDetail handleBiz(BizException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, e.getMessage());
    }
}

// Advice B：兜底（后执行）——只有 A 不处理的异常才会到 B
@RestControllerAdvice
@Order(2)
public class FallbackAdvice {
    @ExceptionHandler(Exception.class)
    public ProblemDetail handleOther(Exception e) {
        log.error("unhandled exception", e);
        return ProblemDetail.forStatusAndDetail(
                HttpStatus.INTERNAL_SERVER_ERROR, "internal server error");
    }
}
```

| 能力 | @ControllerAdvice 还能放什么 |
|------|------------------------------|
| @ExceptionHandler | 全局异常（本职） |
| @InitBinder | 全局绑定器（日期格式、allowedFields 白名单） |
| @ModelAttribute | 全局模型属性（每个控制器方法执行前放入模型） |

| 顺序规则 | 说明 |
|---------|------|
| Advice 之间 | @Order 数值小的优先；命中即止（后序 Advice 不执行） |
| 方法内 vs Advice | 控制器内的 @ExceptionHandler 优先于 Advice |
| 异常精确度 | 具体异常类型 > 父类（如 OrderNotFound 优先于 Exception） |

> 💡 生产建议：**一个兜底 Advice（Exception.class + 日志）+ 一个业务 Advice（自定义异常）+ 校验 Advice（MethodArgumentNotValid 等）**三段式最清晰；别把兜底写进业务 Advice 里让日志淹没。

### 校验异常统一处理（生产代码）

```java
@RestControllerAdvice
public class ValidationAdvice {

    // @RequestBody 校验失败
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleMethodArgumentNotValid(MethodArgumentNotValidException e) {
        List<FieldError> errors = e.getBindingResult().getFieldErrors();
        String msg = errors.stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining("; "));
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, msg);
        pd.setProperty("code", "VALIDATION_FAILED");
        pd.setProperty("fields", errors.stream().map(FieldError::getField).toList());
        return pd;
    }

    // 表单绑定失败（@ModelAttribute 未带 BindingResult 时冒泡至此）
    @ExceptionHandler(BindException.class)
    public ProblemDetail handleBind(BindException e) {
        String msg = e.getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining("; "));
        return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, msg);
    }

    // 服务层方法级校验失败
    @ExceptionHandler(ConstraintViolationException.class)
    public ProblemDetail handleConstraint(ConstraintViolationException e) {
        String msg = e.getConstraintViolations().stream()
                .map(v -> v.getPropertyPath() + ": " + v.getMessage())
                .collect(Collectors.joining("; "));
        return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, msg);
    }
}
```

> ⚠️ 注意：`BindException` 与 `MethodArgumentNotValidException` 是两个不同异常（前者是 DataBinder 绑定+校验、后者是 @RequestBody 参数解析）——Advice 里两个都要处理，否则表单场景 500（详见 [06 篇第 4 节](06-数据校验与绑定速查.md)）。

### Advice 常见陷阱

| 陷阱 | 后果 | 规避 |
|------|------|------|
| 兜底返回 e.getMessage() | 泄漏内部细节（类名/路径） | 兜底输出统一文案 |
| 兜底不记日志 | 线上故障无法排查 | 兜底必 log.error |
| Advice 上没加 @ResponseBody | 返回 ProblemDetail 变视图解析 | 用 @RestControllerAdvice |
| 多个 Advice 未排 @Order | 处理顺序不确定 | 显式 @Order |
| 异步场景用普通 @ExceptionHandler | 异步异常不进解析链 | DeferredResult 回调内处理/setErrorResult |
| 把业务逻辑写进 Advice | Advice 无法单元测试 | Advice 只做翻译，逻辑放服务 |
| 兜底里 catch 后不重抛 | 调用方拿到 200 空体 | catch 后必须转换为错误响应 |
| 校验异常只在方法内处理 | 全局结构不统一 | 校验异常统一冒泡给 Advice |

> 💡 自检方法：写一个故意抛异常的测试接口，用 curl 验证**状态码、Content-Type、错误体结构**三项——三者都符合契约才算异常处理达标；再检查日志侧：未处理异常有完整堆栈且带 traceId 可关联。

## 4. ProblemDetail：RFC 7807 错误体

```java
// 标准错误体：RFC 7807（application/problem+json）
ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, "order 1001 missing");
pd.setTitle("Order Not Found");              // 人类可读标题
pd.setType(URI.create("https://api.example.com/errors/order-not-found"));
pd.setProperty("orderId", 1001L);            // 扩展字段
pd.setInstance(URI.create("/api/orders/1001"));  // 出错实例

// 或直接抛 ResponseStatusException（快速）
throw new ResponseStatusException(HttpStatus.NOT_FOUND, "order missing",
        null, ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, "order missing"));
```

```json
{
  "type": "https://api.example.com/errors/order-not-found",
  "title": "Order Not Found",
  "status": 404,
  "detail": "order 1001 missing",
  "instance": "/api/orders/1001",
  "orderId": 1001
}
```

| 字段 | 含义 |
|------|------|
| `type` / `title` | 错误类型 URI / 标题 |
| `status` / `detail` | HTTP 状态码 / 详细描述 |
| `instance` | 出错资源 URI |
| 扩展 | `setProperty` 任意业务字段 |

### ProblemDetail 生产规范

| 规范 | 说明 |
|------|------|
| type 指向文档 | 每个错误类型一个稳定 URI，文档页说明含义与处理方式 |
| title 用标准短语 | Not Found / Conflict 等，别放动态内容 |
| detail 给人看 | 明确、可操作（"订单 1001 不存在"），不放堆栈 |
| instance 定位 | 放请求资源路径，方便日志关联 |
| 扩展字段业务化 | code + 业务参数（缺货量/冲突版本等） |

> ⚠️ 安全红线：**detail 里绝不输出堆栈/内部路径/SQL 片段**——异常消息默认可能含类名与内部信息，兜底处理器要输出统一文案而不是 `e.getMessage()`（业务异常例外，其消息已人工编写）。

> 🎯 **核心要点**：ProblemDetail（6.1+，Boot 3.2+/4 默认错误格式）是**行业标准错误体**——前端/网关可按 `status`+`type` 统一处理；7.x 下 API 错误响应**默认 application/problem+json**（配置 `spring.mvc.problemdetails.enabled` 控制）。

### 错误码设计：HTTP 状态码 × 业务错误码

| 设计点 | 推荐做法 | 反例 |
|--------|---------|------|
| 状态码 | 只映射 4xx/5xx 大类（400/403/404/409/500） | 用 499、599 等非标准码 |
| 业务错误码 | `setProperty("code", "ORDER_OUT_OF_STOCK")` | 拿状态码当业务码 |
| 前端契约 | 前端只认 `status` + `code` 两个字段分支 | 前端解析 detail 字符串 |
| 文档 | type URI 指向错误码文档页 | type 随意填 |

```java
@ExceptionHandler(OrderOutOfStockException.class)
public ProblemDetail handleStock(OrderOutOfStockException e) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(
            HttpStatus.CONFLICT, "stock insufficient");
    pd.setType(URI.create("https://api.example.com/errors/order-out-of-stock"));
    pd.setProperty("code", "ORDER_OUT_OF_STOCK");
    pd.setProperty("stock", e.getAvailableStock());
    return pd;
}
```

```json
{
  "type": "https://api.example.com/errors/order-out-of-stock",
  "title": "Conflict",
  "status": 409,
  "detail": "stock insufficient",
  "code": "ORDER_OUT_OF_STOCK",
  "stock": 0
}
```

> 🎯 一句话原则：**状态码管"协议层语义"，业务码管"业务层语义"**——网关/监控看 status，前端业务分支看 code，人看 detail；三个消费者各取所需，互不干扰。

### 错误消息国际化

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 注入 MessageSource，按客户端语言返回错误文案
    @ExceptionHandler(BizException.class)
    public ProblemDetail handleBiz(BizException e, Locale locale) {
        String message = messageSource.getMessage(e.getMessageKey(), e.getArgs(), locale);
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(e.getStatus(), message);
        pd.setProperty("code", e.getCode());
        return pd;
    }
}
```

```properties
# messages.properties（默认中文）
order.not.found=订单 {0} 不存在

# messages_en.properties
order.not.found=Order {0} does not exist
```

| 国际化要点 | 说明 |
|-----------|------|
| 触发 | Locale 由 LocaleResolver 解析（Accept-Language / Cookie 等） |
| 消息键 | 异常类持有 key + args，detail 按语言渲染 |
| code 不翻译 | 业务错误码是契约，任何语言一致 |
| 兜底不翻译 | 未知异常输出固定文案（无需多语言） |

> 💡 取舍：错误文案国际化是"体验项"不是"必须项"——内部系统可先统一中文/英文单语言，对外产品再补国际化；错误码结构一旦发布就**不能改**（契约），文案随时可改（非契约）。

## 5. 解析优先级与常见错误码

```text
异常解析优先级（面试必答）：
  @ExceptionHandler（局部/全局 Advice）> @ResponseStatus/ResponseStatusException
  > DefaultHandlerExceptionResolver（框架标准）> 500 兜底
```

| 框架标准异常 | 状态码 | 触发场景 |
|-------------|--------|---------|
| `HttpMessageNotReadableException` | 400 | 请求体 JSON 解析失败 |
| `MethodArgumentNotValidException` | 400 | @Valid 校验失败 |
| `MissingServletRequestParameterException` | 400 | 必填参数缺失 |
| `TypeMismatchException` | 400 | 参数类型不匹配 |
| `NoHandlerFoundException` | 404 | 无路由 |
| `NoResourceFoundException` | 404 | 静态资源缺失 |
| `HttpRequestMethodNotSupportedException` | 405 | 方法不允许 |
| `HttpMediaTypeNotSupportedException` | 415 | Content-Type 不支持 |
| `HttpMediaTypeNotAcceptableException` | 406 | Accept 不支持 |
| `AsyncRequestTimeoutException` | 503 | 异步超时 |

> 💡 面试加分：**415/406 不是业务异常是协议异常**——由 DefaultHandlerExceptionResolver 兜底翻译，无需自己 @ExceptionHandler；业务统一用自定义异常 + Advice 处理（错误码/国际化/扩展字段）。

### 常见错误码归因决策表

| 状态码 | 触发异常 | 归因 | 处理建议 |
|:---:|---------|------|---------|
| 400 | MissingServletRequestParameterException | 必填参数缺失 | 客户端补参/required=false |
| 400 | TypeMismatchException | 参数类型不匹配 | 检查类型与格式 |
| 400 | HttpMessageNotReadableException | 请求体解析失败 | 检查 JSON 语法/字段类型 |
| 400 | MethodArgumentNotValidException | 校验失败 | Advice 返回字段错误列表 |
| 404 | NoHandlerFoundException | 无路由 | 检查映射/通配写法 |
| 404 | NoResourceFoundException | 静态资源缺失 | 检查资源位置 |
| 405 | HttpRequestMethodNotSupportedException | 方法不允许 | 检查 method 条件 |
| 415 | HttpMediaTypeNotSupportedException | Content-Type 无转换器 | 检查依赖/头 |
| 406 | HttpMediaTypeNotAcceptableException | Accept 无转换器 | 检查 produces/依赖 |
| 503 | AsyncRequestTimeoutException | 异步超时 | 调超时/换同步 |

> 💡 记忆技巧：**4xx 全家族里只有 404/405 是"路由层"的，400/415/406 是"数据与媒体层"的**——排查时先分清是"找不到"还是"处理不了"。

### 404 与错误页配置

```yaml
# Boot 4：无路由时抛异常（默认直接返回错误页）
spring:
  mvc:
    throw-exception-if-no-handler-found: true   # 无路由抛 NoHandlerFoundException
  web:
    resources:
      add-mappings: false                       # 关闭静态资源兜底（配合上一条）
```

> 💡 两种 404 策略：**默认"错误页"策略**（无路由 → Whitelabel 错误页/Boot 默认 JSON）适合简单应用；**"抛异常"策略**（`throw-exception-if-no-handler-found=true`）让 404 进入异常解析链，@ExceptionHandler(NoHandlerFoundException.class) 可统一返回 ProblemDetail——对外 API 推荐后者，保证错误体结构一致。

### 异常处理生产实践清单

| 实践 | 说明 |
|------|------|
| 兜底必须打日志 | 未处理异常 `log.error`（带请求路径），响应不泄漏堆栈 |
| 自定义业务异常 | 继承 RuntimeException + 自带错误码/字段 |
| 校验异常统一处理 | MethodArgumentNotValidException → 400 + 字段错误列表 |
| 异步异常 | DeferredResult 超时 → AsyncRequestTimeoutException（503） |
| 响应体一致性 | 所有错误统一 ProblemDetail 结构 |
| 别吞异常 | catch 后 return null 会让调用方拿到 200 空体——语义错乱 |

### 异常日志规范

| 日志内容 | 建议 |
|---------|------|
| 谁调用了 | 请求路径 + 方法 + 用户/租户标识 |
| 哪个环节 | 异常类型 + 控制器类名 + 方法名 |
| 上下文 | 关键参数（订单号等，脱敏） |
| 堆栈 | 兜底异常必须打全堆栈（error 级别） |
| 关联 | traceId/messageId 贯穿（见 [Spring-Web-05](../Spring‑Web/05-Web上下文与作用域速查.md)） |

> 💡 日志与响应分离原则：**日志记全（堆栈/参数/上下文），响应给少（统一文案/错误码）**——日志给排查人员看，响应给调用方看，两边各取所需；错误码体系建好后，日志检索直接用错误码过滤即可。

### 面试官追问

| 追问 | 回答锚点 |
|------|---------|
| 异常解析链顺序？ | @ExceptionHandler（含 Advice）> ResponseStatus > Default > 500 兜底 |
| 同异常多个 Advice 谁处理？ | @Order 小的优先，命中即止 |
| 如何返回 404 的业务体？ | @ExceptionHandler(NoHandlerFoundException) 或错误页配置 |
| ProblemDetail 和旧 Map 错误体区别？ | 标准字段 + 可扩展 + Content-Type 固定 problem+json |
| 全局兜底要不要返回堆栈？ | 绝不——日志里记，响应给统一文案 |
| @ResponseStatus 注解和异常类关系？ | @ResponseStatus 标在异常类上，抛出即带状态码 |
| 错误码与状态码会重复吗？ | 状态码是协议大类，错误码是业务细分（同 400 可多个 code） |

> 🎯 本模块收官：异常链（谁处理）+ ProblemDetail（长什么样）+ 错误码设计（怎么约定）三段合起来就是"异常怎么变成友好响应"的完整答案；自测：能否默写异常解析优先级？能否背出 400/404/405/415/406 的触发异常与归因？能否讲清自定义异常体系（状态码/错误码/扩展字段）的设计思路？能否说清日志与响应"记全给少"的分离原则？
