## 1. @Controller 与 @RestController

| 注解 | 语义 | 响应 |
|------|------|------|
| `@Controller` | 控制器（可返回视图名） | 默认走 ViewResolver（页面） |
| `@RestController` | = `@Controller` + `@ResponseBody`（组合注解） | 默认 JSON 直出 |

```java
@Controller                                    // 返回视图名
public class PageController {
    @GetMapping("/index")
    public String index() { return "index"; }   // → ViewResolver 解析 index 模板
}

@RestController                                 // JSON API
public class OrderApi {
    @GetMapping("/api/orders")
    public List<Order> list() { ... }           // → 转换器直出 JSON
}
```

> 🎯 **核心要点**：`@RestController` 是组合注解（元注解机制见 [Spring-Core-02](../Spring‑Core/02-注解体系速查.md)）——`@ResponseBody` 让返回值走**消息转换器**而非视图解析器；混用页面与 API 时用 `@Controller` + 方法级 `@ResponseBody`。

### 控制器常见 404/405 归因

| 现象 | 归因 | 排查 |
|------|------|------|
| 控制器存在但 404 | 未扫描（包路径外）/ 类无 @Controller | 检查 @ComponentScan 范围与注解 |
| 路径一致但 405 | 方法不匹配 | GET 打到了 POST 映射（或反之） |
| 路径一致但 404 | 通配写法 7.0 不兼容 | 检查中间 `**` / 尾部斜杠 / 后缀匹配 |
| 接口能通但匹配错方法 | 条件（params/headers）设计重叠 | /actuator/mappings 核对条件 |
| 生产能通测试环境 404 | 环境差异（Context-path/端口） | 检查 server.servlet.context-path 配置 |

> ⚠️ 排查口诀：**404 先问"路径对不对"，405 先问"方法对不对"**——这两个状态码是路由层最直接的诊断信号，配合 /actuator/mappings 全量路由清单十分钟定位；若确认路由无误仍 404，再查静态资源映射是否把路径吞掉（ResourceHandlerMapping 兜底优先级最低，理论上不会抢注解路由，但 `/static/**` 等自定义资源映射要复核范围）。

### 权衡取舍：@Controller vs @RestController

| 维度 | @Controller | @RestController |
|------|-------------|----------------|
| 返回值默认走向 | 视图解析器（ViewResolver） | 消息转换器（JSON 直出） |
| 适用场景 | 页面渲染（SSR/管理后台） | JSON API |
| 返回 String 语义 | 视图名（"index" → index.html） | JSON 字符串（`"\"index\""`） |
| 组合方式 | 方法级可加 @ResponseBody 混用 | 组合注解（@Controller + @ResponseBody） |
| 异常响应 | 错误视图/ModelAndView | ProblemDetail / JSON |

```java
// 混用场景：一个控制器同时出页面与 JSON
@Controller
public class MixedController {
    @GetMapping("/page/orders")                  // 页面
    public String page(Model model) { return "orders/list"; }

    @GetMapping(value = "/api/orders/{id}", produces = "application/json")
    @ResponseBody                                // 方法级 → JSON 直出
    public Order api(@PathVariable Long id) { return orderService.get(id); }
}
```

| 生产场景 | 选型建议 |
|---------|---------|
| 纯 API（90% 场景） | @RestController |
| 管理后台/SSR | @Controller + Thymeleaf |
| 页面与接口同域混合 | @Controller + 方法级 @ResponseBody |
| 需要动态状态码 | ResponseEntity（替代 @ResponseStatus 固定注解） |

> ⚠️ 经典坑：`@RestController` 方法返回 `String` 时响应是 `"xxx"`（带引号的 JSON 字符串），不是纯文本——要纯文本用 `produces = "text/plain"` 或写 `HttpServletResponse`；反之 `@Controller` 返回 String 会被当视图名，模板缺失时 500。

## 2. @RequestMapping 属性全表

```java
@RequestMapping(
    value = "/api/orders",            // 路径（可数组多路径）
    method = {GET, POST},              // HTTP 方法（可数组）
    params = "status=PAID",            // 参数条件（必须含/不含）
    headers = "X-Api-Version=1",       // 头条件
    consumes = "application/json",     // 请求 Content-Type
    produces = "application/json",     // 响应 Accept
    name = "orderList",                // 路由名（测试/链接生成用）
    version = "1.2"                    // ★ 7.0：API 版本
)
```

| 条件 | 语义 | 不满足时 |
|------|------|---------|
| `params` | 请求参数必须匹配（`!` 前缀 = 不含） | 405/其他映射 |
| `headers` | 请求头必须匹配 | 同上 |
| `consumes` | Content-Type 匹配 | 415 |
| `produces` | Accept 匹配 | 406 |
| `version`（7.0） | API 版本匹配 | 404/版本不匹配 |

> ⚠️ 多条件同时满足才命中——`params`/`headers` 是**路由过滤**不是校验（不满足时继续找其他映射，而不是报 400）。

### 映射歧义与冲突处理

| 情形 | 行为 |
|------|------|
| 两个映射条件完全等价 | 启动期抛 `IllegalStateException`（重复映射，直接启动失败） |
| 路径相同、方法/条件不同 | 按条件精确度选择（见 [02 篇第 3 节](02-DispatcherServlet与请求全链路速查.md)） |
| 同一 URL 多版本（7.0） | 固定版本优先于基线版本 |
| 404 vs 405 判定 | 路径无命中 → 404；路径命中但方法不符 → 405 |

```java
// 同路径按请求头分流（多客户端协议场景）
@GetMapping(value = "/orders", headers = "X-Client-Type=web")
public List<Order> listWeb() { ... }

@GetMapping(value = "/orders", headers = "X-Client-Type=app")
public List<Order> listApp() { ... }

// 按参数条件分流（?source=admin 走管理逻辑）
@GetMapping(value = "/orders", params = "source=admin")
public List<Order> listAdmin() { ... }
```

> 💡 最佳实践：**一个 URL + 一个方法条件组合只对应一个业务动作**；别用 params/headers 做"校验"（它们不是校验器，不满足时只是换映射或 404），做"路由分流"才是正解——分流场景过多时优先考虑 7.0 的 API 版本化或独立路径。

### 映射设计规范（生产约定）

| 规范 | 示例 | 理由 |
|------|------|------|
| 资源用复数名词 | `/api/orders` 而非 `/api/order` | REST 约定一致 |
| 动词不入路径 | `/api/orders/cancel` → `POST /api/orders/{id}/cancel` | 动作语义化 |
| 分层路径 | `/api/orders/{id}/items` | 子资源表达 |
| 版本显式化 | `/api/v2/orders` 或 `@ApiVersion("v2")` | 兼容演进 |
| 查询参数做筛选 | `/api/orders?status=PAID` | 不做 `/api/paid-orders` |

> ⚠️ 路径设计失控的代价：映射越来越多 → 路由歧义、文档混乱、Security 匹配复杂——**先设计好资源树再写控制器**，别边写边加路径。

## 3. 组合映射注解

| 注解 | 等价 | 用途 |
|------|------|------|
| `@GetMapping` | `@RequestMapping(method = GET)` | 查询 |
| `@PostMapping` | POST | 创建 |
| `@PutMapping` | PUT | 整体更新 |
| `@PatchMapping` | PATCH | 部分更新 |
| `@DeleteMapping` | DELETE | 删除 |

```java
@PutMapping("/{id}")
public Order update(@PathVariable Long id, @Valid @RequestBody UpdateCmd cmd) {
    return orderService.update(id, cmd);   // 幂等整体更新
}

@PatchMapping("/{id}/status")
public Order changeStatus(@PathVariable Long id, @RequestBody StatusCmd cmd) { ... }
```

> 💡 REST 语义速记：GET 读、POST 建、PUT 全量改、PATCH 增量改、DELETE 删；组合注解 = 方法限定 + 路径（`@GetMapping("/x")` 相当于 `@RequestMapping(value="/x", method=GET)`）。

### HTTP 方法的幂等与安全语义

| 方法 | 安全（不改状态） | 幂等（重复执行结果一致） | 典型语义 |
|------|:---:|:---:|---------|
| GET | ✅ | ✅ | 查询（可缓存） |
| HEAD | ✅ | ✅ | 只取响应头 |
| POST | ❌ | ❌ | 创建（重复提交产生多条） |
| PUT | ❌ | ✅ | 整体替换（同参数重复提交结果一致） |
| PATCH | ❌ | ❌ | 增量修改（需结合版本/乐观锁防重复） |
| DELETE | ❌ | ✅ | 删除（重复删除返回 404 或幂等成功） |

> 💡 面试延伸：**幂等性靠什么保证**——PUT/DELETE 天然幂等（操作对象固定），POST 的幂等需要幂等键（Idempotency-Key 请求头或唯一业务号）；网关/支付场景幂等是必考题，见 [Spring-Web-02](../Spring‑Web/02-HTTP客户端速查.md) 客户端重试与幂等配合。

## 4. 方法参数解析速查

| 注解/类型 | 解析内容 | 常见错误 |
|----------|---------|---------|
| `@PathVariable` | URL 路径变量 `{id}` | 缺变量 → 500/404 |
| `@RequestParam` | 查询参数/表单字段 | 缺参 → 400（`required=false` 可空） |
| `@RequestHeader` | 请求头 | 缺头 → 400 |
| `@CookieValue` | Cookie | 缺 Cookie → 400 |
| `@RequestBody` | 请求体（转换器反序列化） | JSON 格式错 → 400 |
| `@ModelAttribute` | 表单/查询 → 对象绑定 | 绑定错误 → BindingResult |
| `@Validated` / `@Valid` | 校验注解 | 校验失败 → 400（MethodArgumentNotValidException） |
| `HttpServletRequest/Response` | Servlet 原生 | - |
| `Principal` / `@AuthenticationPrincipal` | 认证主体（Security） | - |

### @PathVariable vs @RequestParam 选型

| 维度 | @PathVariable | @RequestParam |
|------|--------------|---------------|
| 数据位置 | URL 路径 | 查询字符串/表单 |
| 典型场景 | 资源定位（/orders/1001） | 筛选/分页（?page=1&size=20） |
| 语义 | 层级资源标识 | 扁平查询条件 |
| 可选性 | 通常必填（路径即身份） | 常用 defaultValue / required=false |
| 长度限制 | 受容器 URL 限制 | 通常更宽松（受参数限制） |

> 💡 选型原则：**标识资源的用 PathVariable，筛选排序分页的用 RequestParam**——把订单 id 放查询参数、把筛选条件放路径，都会让路由表和文档混乱。

```java
@GetMapping("/orders")
public Page<Order> page(
        @RequestParam(defaultValue = "0") int page,        // 缺省值
        @RequestParam(required = false) String status,     // 可空
        @RequestHeader("X-Trace-Id") String traceId) {     // 必带头
    ...
}
```

> 🎯 **核心要点**：参数解析由 `HandlerMethodArgumentResolver` 链完成（[02 篇第 4 节](02-DispatcherServlet与请求全链路速查.md)）——**400 报错先看参数注解**（required 语义/格式）；`@RequestBody` 失败是转换器问题（[Spring-Web-03](../Spring‑Web/03-消息转换与内容协商速查.md)）。

### 参数解析顺序与常见 400 归因

| 400 报错信息 | 归因 | 解法 |
|-------------|------|------|
| `MissingServletRequestParameterException` | 必填参数缺失 | required=false 或客户端补参 |
| `MethodArgumentTypeMismatchException` | 参数类型转换失败（"abc" → Long） | 检查类型 + 格式（日期等） |
| `HttpMessageNotReadableException` | 请求体 JSON 解析失败 | 检查 JSON 语法/字段类型 |
| `MethodArgumentNotValidException` | 校验注解失败 | 看字段错误列表（[06 篇](06-数据校验与绑定速查.md)） |
| `BindException` | 表单绑定失败 | 同上 |

> 💡 排查顺序：**400 先看异常类型名**——异常类名直接告诉你"缺参、类型错、解析错、校验错"中的哪一种，然后对应查注解/转换器/校验器，三步定位（完整决策树见 [08 篇第 3 节](08-集成地图与常见问题.md)）。

### 自定义参数解析器（完整示例）

```java
// 场景：把 X-User-Id 请求头解析成 CurrentUser 参数
public class CurrentUserArgumentResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.getParameterType() == CurrentUser.class;
    }

    @Override
    public Object resolveArgument(MethodParameter parameter,
                                  ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest,
                                  WebDataBinderFactory binderFactory) throws Exception {
        String userId = webRequest.getHeader("X-User-Id");
        if (userId == null) {
            throw new UnauthorizedException("missing X-User-Id");
        }
        return new CurrentUser(userId);
    }
}

@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) {
        resolvers.add(new CurrentUserArgumentResolver());   // 追加到链尾
    }
}

@GetMapping("/me")
public CurrentUser me(@CurrentUser CurrentUser user) { return user; }
```

| 扩展点 | 要点 |
|--------|------|
| supportsParameter | 按类型或自定义注解判断归属 |
| resolveArgument | 解析值或抛异常（异常走 @ControllerAdvice） |
| 注册 | `addArgumentResolvers` 追加在默认链之后 |
| 常用场景 | 登录用户注入、租户上下文、链路追踪 |

> ⚠️ 自定义解析器抛出的异常同样进入异常解析链（@ControllerAdvice 可处理）；解析器每次请求每个参数都可能执行——别做重量级 IO 或数据库查询。

## 5. API 版本化（7.0）

```java
// 方式一：@RequestMapping(version)
@GetMapping(value = "/orders", version = "1.2")        // 固定版本
public List<Order> v12() { ... }

@GetMapping(value = "/orders", version = "1.2+")       // 基线版本：1.2 及以上
public List<Order> v12Plus() { ... }

// 方式二：类级 @ApiVersion
@RestController
@ApiVersion("v2")                                       // 类级版本（defaultVersion 可指定默认）
@RequestMapping("/api/orders")
public class OrderV2Controller { ... }

// Boot 属性
// spring.mvc.apiversion.use.path-segment=true  （版本走路径段）
// spring.mvc.apiversion.supported=v1,v2
```

| 版本语义 | 写法 | 说明 |
|---------|------|------|
| 任意版本 | 无 version | 匹配所有 |
| 固定版本 | `"1.2"` | 仅该版本命中 |
| 基线版本 | `"1.2+"` | 该版本及以上命中 |
| 客户端配合 | `ApiVersionInserter` | 请求自动带版本（[Spring-Web-02](../Spring‑Web/02-HTTP客户端速查.md) 第 6 节） |

> 💡 面试新题：Spring 7 API 版本化的三种策略——**头（HeaderApiVersionInserter）/ 媒体类型 / 路径段（PathApiVersionInserter）**——服务端 `@RequestMapping(version)` 与客户端 `ApiVersionInserter` 成对使用。

### 版本化启用与异常语义（7.0 细节）

```yaml
# Boot 4 属性启用版本化（等效于 WebMvcConfigurer 里的 ApiVersionConfigurer）
spring:
  mvc:
    apiversion:
      use:
        path-segment: 1          # 从路径段解析版本（也支持 request-header / parameter / media-type）
      supported: v1,v2           # 支持的版本集合（默认从映射声明的版本自动发现）
```

```java
// 路径段策略要求：版本变量必须声明为路径变量 {version}（名字不限）
@RestController
@RequestMapping("/api/{version}/orders")
public class OrderApi { ... }
// 或全局加前缀：configurePathMatch → addPathPrefix("/api/{version}", ...)
```

| 版本异常 | 含义 | 默认状态码 |
|---------|------|:---:|
| `MissingApiVersionException` | 启用版本化后请求未带版本 | 400 |
| `InvalidApiVersionException` | 版本格式非法 / 路径段缺 {version} 变量 | 400 |
| `NotAcceptableApiVersionException` | 版本不在支持集合（基线被更高固定版本封顶） | 400 |

> ⚠️ 常见翻车点：路径段策略下映射里**没有 `{version}` 变量** → 全部 400；客户端请求 `1.0.1` 但支持集合只有 `1.0` → 400（版本需逐段匹配）；版本缺失默认 400，可配置为"取最高支持版本"。**版本化默认关闭**——需要显式启用（Boot 属性或 ApiVersionConfigurer）。

### 版本策略选型

| 策略 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| 路径段 | `/api/v2/orders` | 直观、网关/日志友好 | URL 变长、需要 {version} 变量 |
| 请求头 | `API-Version: 2` | URL 干净 | 缓存/CDN 不友好 |
| 媒体类型 | `Accept: application/vnd.api+json;version=2` | RESTful 风格 | 客户端配置复杂 |

> 💡 选型建议：对外 API（可能被缓存/CDN 加速）用**路径段**；内部服务间调用用**请求头**最省事；媒体类型策略适合有强版本化规范的大型平台（如 Shopify/Stripe 风格）。

## 6. 路径匹配规则（7.0 PathPattern）

```text
7.0 起 PathPatternParser 是唯一默认（AntPathMatcher 废弃，#34018）：
  /api/{id}          路径变量（单段）
  /api/**            尾随任意段（跨级）
  /api/{*path}       捕获剩余路径（变量）
  /**/pages/index.html   ★ 7.0 新增：开头多段通配

  Security 7.0 收紧：** 不得出现在模式中间（如 /api/**/x 被拒）
  回退：spring.mvc.pathmatch.matching-strategy=ant_path_matcher（不推荐）
```

| 通配 | 语义 |
|------|------|
| `?` | 单字符（少用） |
| `*` | 段内任意（`/api/*` 匹配 /api/a 不匹配 /api/a/b） |
| `**` | 跨段任意（`/api/**` 匹配全部子路径） |
| `{var}` | 命名变量（`@PathVariable` 获取） |
| `{*var}` | 捕获剩余段 |

> ⚠️ **7.0 升级注意**：`/api/**/detail` 这类"中间 **"写法在 PathPattern 下不再支持（AntPathMatcher 可以）——升级后路由 404 先查模式写法；匹配性能：PathPattern 基于解析树，比 Ant 字符串正则快。

### PathPattern 性能与实现原理

PathPattern 快的两个原因：

- **解析树预编译**：映射注册时（启动期）把每个模式解析成一棵"段节点树"（每段可以是字面量/变量/单段通配/多段通配），请求匹配时按路径段逐级走树，是确定性算法；
- **无正则回溯**：AntPathMatcher 对候选模式逐个做正则式匹配，模式越多耗时线性叠加且存在回溯风险；PathPattern 的段树匹配与模式数量解耦，配合 MappingRegistry 的哈希索引，命中更快。

> 💡 面试对比题：**"PathPattern 和 AntPathMatcher 谁快？为什么？"**——快在预编译解析树 + 哈希索引，而不是运行时逐个正则比；路由数量大时差距更明显（数百路由场景可差一个数量级）。

### PathPattern 写法对照（升级必查）

| 需求 | AntPathMatcher 写法 | PathPattern 写法 | 备注 |
|------|-------------------|-----------------|------|
| 开头多段通配 | `/**/pages/index.html` | `/**/pages/index.html` | 7.0（M8 起）PathPattern 也支持 |
| 捕获剩余路径 | `/api/**` | `/api/{*path}` | 变量化更明确 |
| 中间通配 | `/api/**/detail` | ✗ 不支持 | 拆分为多个映射或精确段 |
| 单段通配 | `/api/*` | `/api/*` | 一致 |
| 正则变量 | `/api/{id:[0-9]+}` | `/api/{id:[0-9]+}` | 一致 |
| 尾部斜杠 | `/api/orders/` | 不匹配（trailingSlashMatch 已移除） | 7.0 严格区分 |

| 常见匹配 | 匹配 `/api/a/b`？ | 匹配 `/api/a`？ |
|---------|:---:|:---:|
| `/api/*` | ✅ | ✅ |
| `/api/{*path}` | ✅（path=a/b） | ✅（path=a） |
| `/api/**/x` | ✗（7.0 中间通配非法） | ✗ |
| `/api/{id}/b` | ✅（id=a） | ✗ |
| `/**/index.html` | ✗（最后一段必须是 index.html） | ✗ |

> 💡 7.0 路径移除项提醒：`suffixPatternMatch`（后缀匹配）、`trailingSlashMatch`（尾部斜杠）、`favorPathExtension`（后缀协商）**全部移除**——`/api/orders.json`、`/api/orders/` 这类历史写法在 7.0 下 404，客户端需按规范路径访问。

### 面试官追问

| 追问 | 回答锚点 |
|------|---------|
| @RestController 返回 String 是什么？ | JSON 字符串（带引号），不是视图名 |
| 一个 URL 两个方法（GET+POST）合法吗？ | 合法，方法条件不同；完全等价才报重复映射 |
| 参数解析链怎么排序？ | 第一个 supportsParameter 命中的接管；无注解兜底解析器在链尾 |
| 7.0 版本化默认开启吗？ | 默认关闭，需 ApiVersionConfigurer 或 Boot 属性启用 |
| PathPattern 与 Ant 性能差异？ | 解析树预编译 + 哈希索引，无正则回溯 |
| 版本不匹配返回什么？ | InvalidApiVersionException / NotAcceptableApiVersionException → 400 |
| 同路径按什么分流？ | headers / params / produces / version 四类条件 |
| 路径变量和查询参数谁优先级高？ | 两者可共存（/orders/{id}?fields=xx）；变量定位资源、参数做筛选 |

> 🎯 本模块收官：映射条件（路径/方法/参数/头/媒体类型/版本）+ 参数解析链是"路由与入参"的全部答案；自测：能否默写 @RequestMapping 的六类条件与各自失败状态码？能否解释 404/405/415/406 的产生时机？能否讲清 @PathVariable 与 @RequestParam 的选型边界？
