## 1. 与其他模块的集成地图

```text
                  spring-webmvc（Web 框架层，八系列之顶）
        ┌──────────┬──────────┬──────────┬──────────┐
        ↓          ↓          ↓          ↓          ↓
  spring-web    spring-context spring-aop/tx  Spring Security  Spring Boot
  HTTP 模型/     父子容器/       @Transactional  FilterChainProxy  starter-web
  转换器/Filter   事件（MVC 在   在服务层代理    在 Filter 链      自动配置
  （基础设施）    子容器中运行）   （与 MVC 正交）  （比 MVC 更早）  内嵌 Tomcat
```

| 联动点 | 机制 | 说明 |
|--------|------|------|
| mvc ↔ web | DispatcherServlet 消费 web 的转换器/过滤器/CORS | 见 [Spring-Web 系列](../Spring‑Web/00-Spring Web组件总览.md) |
| mvc ↔ context | 控制器在子上下文（Servlet WebApplicationContext） | 父子容器（[Spring-Web-05](../Spring‑Web/05-Web上下文与作用域速查.md)） |
| mvc ↔ tx/aop | @Transactional 在服务层，与 MVC 无耦合 | 事务代理先于控制器（[Spring-TX 系列](../Spring‑TX（Spring‑Transaction）/00-Spring TX组件总览.md)） |
| mvc ↔ security | Security 过滤器链在 DispatcherServlet **之前** | 认证失败不会进入控制器（[Spring-Web-06](../Spring‑Web/06-过滤链与CORS速查.md)） |
| mvc ↔ Boot | WebMvcAutoConfiguration 自动装配全套 | `spring.mvc.*` 属性控制（见第 2 节） |
| mvc ↔ webflux | 互斥技术栈 | 一个应用选一个 |

> 🎯 **核心要点**：一次请求的完整横切顺序 = **Security 过滤器链 → MVC 拦截器 → 事务代理 → 控制器**——"为什么 @Transactional 在 @Controller 上无效"（控制器是最后一层，事务应在服务层）；"为什么 Security 拦住了 401 而拦截器没机会"（过滤器更早）。

### 集成配置速查（Boot 4 yaml）

```yaml
spring:
  mvc:
    problemdetails:
      enabled: true            # 错误响应默认 ProblemDetail
    static-path-pattern: /static/**
    apiversion:                # 7.0 版本化（可选启用）
      use:
        request-header: API-Version
      supported: v1,v2
  servlet:
    multipart:
      max-file-size: 10MB      # 上传大小限制
      max-request-size: 10MB
  security:
    filter:
      order: -100              # 过滤器链位置（默认在 DispatcherServlet 前）
  thymeleaf:
    cache: true                # 生产模板缓存
```

| 联动点 | 关键配置/类 | 故障信号 |
|--------|-----------|---------|
| MVC ↔ Security | spring.security.filter.order | 401 但控制器未执行（正常，被过滤器拦） |
| MVC ↔ Boot | spring.mvc.* 全部属性 | 配置不生效 → 检查是否自定义配置覆盖 |
| MVC ↔ 容器 | server.port / tomcat.* | 端口/线程参数问题 |
| MVC ↔ 上传 | spring.servlet.multipart.* | 413 / 500（超限） |

> ⚠️ 隐藏故障：自定义 `WebMvcConfigurer` 不会关闭自动配置，但**自定义类继承 `WebMvcConfigurationSupport` 会**——若有人把配置类改成继承它，Boot 的 MVC 自动配置整体失效（静态资源 404、JSON 转换失效连锁故障），排查"配置明明写了不生效"先查这个。

### 集成故障典型案例

| 现象 | 根因 | 定位方法 |
|------|------|---------|
| Security 401 但日志无 MVC 痕迹 | 过滤器链先于 DispatcherServlet | 过滤器日志/断点定位 |
| 控制器拿到 null 用户 | SecurityContext 未透传 | 检查 SecurityContextHolder 策略与虚拟线程 |
| 拦截器里事务失效 | 拦截器在事务代理外层 | 事务放服务层 |
| 上传 500 而非 413 | 容器 swallow 限制 | server.tomcat.max-swallow-size |
| 重定向后参数丢失 | FlashMap 未用 | RedirectAttributes 传递 |

### 父子容器与跨层注入

| 层 | 容器 | 能注入什么 |
|----|------|-----------|
| 根容器 | Root WebApplicationContext | 服务层/数据层 Bean（DataSource、Service、Repository） |
| 子容器 | Servlet WebApplicationContext | 控制器/拦截器/转换器等 Web 组件 |
| 跨层规则 | 子容器可见父容器 Bean（向上查找） | 父容器看不到子容器 Bean（向下不可见） |

> ⚠️ 常见问题：**在 Filter 里注入不了控制器的 Bean**（Filter 在子容器之外，由容器提供者管理）；**控制器里注入 Service 一切正常**（向上查找）；若自定义配置把 Service 注册进了子容器，根容器（如调度器/监听器）里就拿不到——Bean 注册位置与容器层级必须一致。

## 3. 高频问题与排查速查

| 现象 | 根因 | 排查/解法 |
|------|------|----------|
| 404 | 无路由/PathPattern 写法不符/控制器未扫描 | 检查映射注解 + 通配写法（7.0 `/**` 中间段限制）+ 扫描路径 |
| 404（有路由） | 7.0 升级后 ant 模式失效 | `spring.mvc.pathmatch.matching-strategy` 回退或改 PathPattern |
| 400 | 参数缺失/类型不匹配/校验失败 | 看异常类型：MissingServletRequestParameter / MethodArgumentNotValid |
| 415 / 406 | 媒体类型协商失败 | Content-Type/Accept 与转换器（[04-响应与消息转换速查](04-响应与消息转换速查.md)） |
| JSON 循环引用（StackOverflow） | 双向关联实体序列化 | `@JsonIgnore`/`@JsonManagedReference`/DTO 投影 |
| LocalDateTime 序列化格式怪 | 未配 JavaTimeModule | Boot 4 默认已配；自定义 JsonMapper 时补模块 |
| 校验不生效 | 漏 @Valid/校验注解错误 | @RequestBody 必须 @Valid；注解在字段/参数上 |
| 拦截器不执行 | 路径未匹配/静态资源请求 | `addPathPatterns` 覆盖；静态资源不走拦截器 |
| preHandle false 后仍执行 | afterCompletion 语义 | 已通过拦截器的 afterCompletion 必执行（正确行为） |
| 返回 null 变 `"null"` | @ResponseBody null 序列化 | `ResponseEntity.noContent()` / 全局 Advice 处理 |
| 自调用 @Transactional 失效 | 代理绕过 | 服务层注入自身/模板（[Spring-TX-03](../Spring‑TX（Spring‑Transaction）/03-@Transactional速查.md)） |
| 上传文件过大 | multipart 限制 | `spring.servlet.multipart.max-file-size` |
| 虚拟线程下 ThreadLocal 暴涨 | 每请求一线程 | 请求作用域/显式传参（[Spring-Web-05](../Spring‑Web/05-Web上下文与作用域速查.md)） |

> ⚠️ **排查三板斧**：① 404/405 先查"路由与通配"（7.0 升级高发区）；② 4xx 先看"异常类型"（400/415/406 各有对应解析器）；③ 序列化问题先确认"转换器与 DTO 边界"（别把实体直接吐出去）。

### 4xx 排查决策树

```text
响应 4xx → 先看状态码：
  404 → 路由问题（映射注解/PathPattern 写法/控制器扫描）还是资源缺失
  400 → 参数问题：缺参（MissingServletRequestParameter）/
        类型错（TypeMismatch）/
        校验失败（MethodArgumentNotValid）/
        JSON 解析失败（HttpMessageNotReadable）
  405 → 路径命中但方法不匹配（GET 打 POST 映射）
  415 → 请求 Content-Type 无转换器可读（缺依赖/头写错）
  406 → 响应 Accept 无转换器可写（缺依赖/produces 不匹配）
  401 → Security 过滤器链拒绝（未认证）
  403 → 已认证但授权不足
  409 → 业务冲突（幂等/并发，业务异常映射）
```

### 高频坑补充表

| 坑 | 根因 | 解法 |
|-----------|------|------|
| CORS 跨域失败 | 未配 CORS 或配置在错误层 | MVC CorsRegistry / 网关统一（[Spring-Web-06](../Spring‑Web/06-过滤链与CORS速查.md)） |
| 时区偏差 8 小时 | Jackson 默认 UTC | spring.jackson.time-zone 或 JsonMapper 配置 |
| 懒加载序列化炸 | 实体带代理、事务已关闭 | DTO 组装 / @JsonIgnore 懒字段 |
| 虚拟线程 + ThreadLocal 泄漏 | 每请求一线程不回收 | 请求作用域 / 显式传参 |
| 上传 413 | 容器/multipart 限制 | server.tomcat.max-swallow-size + spring.servlet.multipart |
| 分页接口数据重复 | 排序不稳定（无 order by 唯一键） | SQL 加 id 兜底排序 |
| 接口幂等失败 | 重复提交无防重 | 幂等键/唯一索引 |
| 响应大对象 OOM | 一次性加载列表 | 分页 + StreamingResponseBody |
| 404 但接口文档有 | 网关路由/context-path 前缀不一致 | 核对网关转发规则与 server.servlet.context-path |

> 💡 排查方法论：**"异常类型 → 状态码 → 链路层"三层定位**——先看异常类名确定类型，再看状态码缩小范围（路由层/数据层/媒体层），最后按层查配置与代码；三分定位比翻日志快一个数量级。工具链：`/actuator/mappings`（路由）、`/actuator/conditions`（自动配置生效项）、`/actuator/beans`（Bean 装配）三个端点覆盖 80% 的配置类排查场景。

### 面试追问清单（八系列收官版）

| 追问 | 回答锚点 |
|------|---------|
| 一次请求从 Tomcat 到数据库经过哪些层？ | 八系列全景链路（第 2 节） |
| 控制器里能开事务吗？为什么不好？ | 能但事务在服务层更合理（代理粒度/传播） |
| Security 认证失败时 MVC 异常处理参与吗？ | 不参与——过滤器层已拦截 |
| 为什么 404 有时是 JSON 有时是页面？ | 错误处理路径不同（ErrorController vs ProblemDetail 配置） |
| 7.0 升级最大的三个坑？ | 通配写法 / 转换器类名 / HttpHeaders 类型 |
| 虚拟线程对 MVC 的影响？ | 每请求一线程 → ThreadLocal 语义变化（Boot 4 默认） |
| 上传与下载的边界怎么设？ | multipart 上限 + 流式写出 + 超时控制 |
| 怎么验证异常处理达标？ | curl 验三件：状态码 / Content-Type / 错误体结构 |
| 过滤器里的异常 MVC 能处理吗？ | 不能——容器层异常走容器错误处理，不进 HandlerExceptionResolver |
| 多环境路由不一致怎么办？ | context-path/网关前缀差异 → 用相对路径或配置中心统一 |

### 生产上线 Checklist（MVC 侧）

- [ ] 全局异常兜底 + 统一 ProblemDetail 结构（不泄漏堆栈）
- [ ] 校验注解覆盖所有对外入参（record/白名单防批量赋值）
- [ ] 拦截器：鉴权 + 审计 + 限流注册顺序正确
- [ ] 序列化：时间格式 / 时区 / 循环引用 / NULL 策略确认
- [ ] 上传/下载大小限制（multipart + Tomcat）
- [ ] CORS 配置（前后端分离场景）
- [ ] 7.0 通配写法审计（/actuator/mappings 全量核对）
- [ ] 压测：虚拟线程/线程池参数（server.tomcat.threads.*）
- [ ] 日志：traceId 贯穿 + 错误日志分级

> 🎯 **收官结论**：MVC 是整个八系列中最"薄"也最"重"的一层——薄在它只是调度与转换，重在它把所有下层能力串成一次完整请求；吃透本系列 + 深度体系 10 篇，Web 侧面试基本无死角；复习收尾按第 4 节考点清单逐条过，再用上方 Checklist 对照生产习惯自检一遍即可。本系列 8 篇的阅读顺序本身就是一条请求的完整生命周期（02 入口 → 08 收尾），重读时按"路由 → 执行 → 响应 → 横切"四条主线串行复述，每线两分钟能讲完，说明框架已经内化。
