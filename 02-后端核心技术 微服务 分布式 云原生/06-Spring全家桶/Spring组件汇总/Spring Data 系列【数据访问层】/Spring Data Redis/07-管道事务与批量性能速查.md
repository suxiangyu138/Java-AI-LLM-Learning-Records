## 1. 为什么批量：RTT 是 Redis 性能瓶颈

**通俗**：Redis 单命令极快（微秒级），但**每条命令一次网络往返（RTT）**——本地 0.1ms、跨机房 1-5ms；1000 条命令 = 1000 次 RTT，网络时间碾压执行时间。

```text
逐条执行：SET a →（RTT）→ SET b →（RTT）→ SET c →（RTT）  = 3 × RTT + 3 × 执行
管道执行：SET a; SET b; SET c 一次发出 → 一次 RTT = 1 × RTT + 3 × 执行

RTT 0.5ms 时：3 条命令逐条 ≈ 1.5ms+，管道 ≈ 0.5ms+ → 3 倍差距；100 条时差距 100 倍
```

> 🎯 面试必答：**"Redis 批量操作为什么快？"**——快在**减少 RTT**（网络往返），不是减少执行时间——Redis 执行命令本身微秒级，瓶颈在网络；Pipeline/事务/Lua 三种批量手段都是"一次 RTT 干 N 件事"，区别在原子性与编程能力（第 5 节对比）。

## 2. Pipeline：批量命令无原子

```java
// executePipelined：批量发送，一次 RTT，无原子性（中途失败不影响其他）
List<Object> results = redisTemplate.executePipelined((RedisCallback<Object>) conn -> {
    for (String key : keys) {
        conn.stringCommands().get(key.getBytes());     // 批量 GET
    }
    return null;                                       // 返回 null = 只管执行
});
// results：按命令顺序对应的结果列表

// 批量写（缓存预热/批量回填）
redisTemplate.executePipelined((RedisCallback<Object>) conn -> {
    for (Product p : products) {
        byte[] key = ("product:" + p.getId()).getBytes();
        conn.stringCommands().set(key, serialize(p));
    }
    return null;
});
```

| 要点 | 说明 |
|------|------|
| 语义 | **批量发送 + 批量收结果**（减少 RTT） |
| 原子性 | ❌ 无（各命令独立执行，中途失败不影响其他） |
| 回调 | `RedisCallback`（命令级 API，byte[] 操作——**序列化需自行处理**） |
| 4.x 注意 | 管道与事务**互斥**（不能管道内开事务；Lettuce 下 4.x 有约束，[10 篇](10-集成地图与常见问题.md)） |
| 适用 | 批量读（缓存预热）、批量写（导入）、无关命令打包 |

> ⚠️ 管道三大坑：① **大管道内存**（几万条一次发 = 客户端/服务端缓冲压力，分批 1000-5000 条）；② **无原子性**（需要原子用事务/Lua）；③ 回调里 byte[] 裸操作（序列化要自己管——推荐把序列化抽工具）。

## 3. 事务：multi/exec 与 @Transactional 绑定

### 3.1 原生 multi/exec（编程式）

```java
// RedisTemplate 原生事务（session 内命令入队，exec 一起执行）
SessionCallback<List<Object>> tx = new SessionCallback<>() {
    @Override
    @SuppressWarnings({"unchecked", "rawtypes"})
    public List<Object> execute(RedisOperations ops) throws DataAccessException {
        ops.multi();                                     // MULTI 开始入队
        ops.opsForValue().set("a", "1");
        ops.opsForValue().set("b", "2");
        ops.opsForValue().increment("counter");          // 入队命令（不立即执行）
        return ops.exec();                               // EXEC 一起执行
    }
};
List<Object> results = redisTemplate.execute(tx);        // 结果按命令顺序
```

### 3.2 @Transactional 绑定（Spring 事务同步）

```java
// ① 开启事务支持（连接工厂）
@Bean
RedisConnectionFactory redisConnectionFactory() {
    LettuceConnectionFactory factory = new LettuceConnectionFactory();
    factory.setShareNativeConnection(false);             // 事务需要独立连接（不共享）
    return factory;
}
// 或 spring.data.redis 下：LettuceConnectionFactory.setValidateConnection...

// ② 声明式：方法内所有 Redis 操作进入同一事务（multi/exec 包装）
@Transactional
public void transferWithRedis(String from, String to, int amt) {
    redisTemplate.opsForValue().decrement(from, amt);    // 入队
    redisTemplate.opsForValue().increment(to, amt);      // 入队
}                                                        // 方法结束 exec 提交
```

| 要点 | 说明 |
|------|------|
| 语义 | **原子执行**（exec 一起执行，成功全成、失败全不执行） |
| 回滚真相 | **Redis 事务没有回滚**——执行阶段某命令出错，其他命令照常执行（Lua 才真"回滚"= 不执行） |
| 与 DB 事务 | **两回事**：@Transactional 同时管 DB 事务 + Redis 事务（Redis 是独立事务，不参与 DB 回滚） |
| 连接要求 | 事务需要**独立连接**（shareNativeConnection=false 或池化） |
| 集群限制 | multi-key 事务必须同 slot（[02 篇](02-快速开始与连接配置速查.md) 4.2 hash tag） |

> ⚠️ **@Transactional + Redis 的常见误区**：以为 Redis 操作会随 DB 回滚——**不会**！@Transactional 只是"把 Redis 操作也包进 multi/exec"，DB 回滚时 Redis 已提交（除非手动补偿）；**跨 DB+Redis 的原子性必须靠补偿/对账，不是靠注解**。

## 4. watch 乐观锁与事务回滚真相

### 4.1 watch（CAS 式乐观锁）

```java
// WATCH：监视 key，执行前被改动 → EXEC 返回 null（放弃执行）
SessionCallback<List<Object>> cas = new SessionCallback<>() {
    @Override
    public List<Object> execute(RedisOperations ops) {
        ops.watch("stock:1");                            // 监视
        Object stock = ops.opsForValue().get("stock:1"); // 读当前值
        if (Integer.parseInt((String) stock) < 1) {
            ops.unwatch();
            return null;                                 // 业务判断失败
        }
        ops.multi();                                     // 入队
        ops.opsForValue().decrement("stock:1");
        return ops.exec();                               // 执行中被改 → 返回 null（冲突）
    }
};
List<Object> result = redisTemplate.execute(cas);
if (result == null) { /* 冲突：重试或失败 */ }
```

| 概念 | 说明 |
|------|------|
| WATCH | 监视 key 版本（类似乐观锁 @Version 的 Redis 版） |
| 冲突 | EXEC 时发现监视的 key 被改 → **放弃执行返回 null**（不执行任何入队命令） |
| 重试 | 冲突后重新读-判-写（循环，同乐观锁重试） |
| 与 Lua 对比 | WATCH+事务能实现 CAS 但**多轮 RTT 且重试复杂**——Lua 一条脚本更优（[06 篇](06-分布式锁与Lua脚本速查.md)） |

### 4.2 "回滚"真相表（面试必答）

| 手段 | 原子性 | 失败行为 | 是否可编程 |
|------|:---:|---------|:---:|
| Pipeline | ❌ | 各命令独立，失败不影响其他 | 部分 |
| multi/exec | ✅ 原子执行 | **无回滚**：执行阶段单命令错，其他照常 | ❌（预写命令） |
| WATCH+multi | ✅ 带条件 | 条件不满足**整批不执行**（返回 null） | ❌ |
| **Lua** | ✅ 原子 | 脚本内可判断，**可完全控制**（类似回滚） | ✅ |

> 🎯 面试必答：**"Redis 事务能回滚吗？"**——**不能**（与 SQL 事务的本质差异）：multi/exec 是"命令打包原子执行"，执行阶段某条出错时**其他命令照样执行**（错误被标记，不中断）——Redis 事务没有 undo；要"出错全不做"的语义用 **Lua**（脚本内判断与条件返回）——"Redis 事务无回滚"是高频考点，答完再补 Lua 方案直接满分。

## 5. 管道 vs 事务 vs Lua 对比（面试必考）

| 维度 | Pipeline | multi/exec 事务 | Lua |
|------|:---:|:---:|:---:|
| RTT | 1 | 1 | 1 |
| 原子性 | ❌ | ✅ | ✅ |
| 可编程（读-判-写） | ❌ | ⚠️（watch 勉强） | ✅ **最强** |
| 失败处理 | 各自为战 | 无回滚 | 脚本内完全控制 |
| 复杂度 | 低 | 中 | 中 |
| 适用 | 批量无关命令 | 简单原子批 | **复杂原子逻辑（锁/限流/扣减）** |
| 一句话 | 省 RTT | 打包原子 | 原子 + 可编程 |

> 🎯 面试必答：**"管道、事务、Lua 怎么选？"**——先答三者的本质：管道省 RTT 无原子、事务原子但无回滚、Lua 原子且可编程；再答选型：**无关命令批量 → 管道；简单原子批 → 事务；读-判-写组合（锁/限流/扣库存）→ Lua**——最后补一句：**能用原子单命令（INCR/条件 SET）解决的连 Lua 都不用**（分层选型，面试加分）。

## 6. 批量写入实战

### 6.1 缓存预热/批量回填

```java
// 批量回填（管道）：10000 条商品预热
public void warmup(List<Product> products) {
    byte[][] keys = new byte[products.size()][];
    byte[][] vals = new byte[products.size()][];
    for (int i = 0; i < products.size(); i++) {
        keys[i] = ("product:" + products.get(i).getId()).getBytes(StandardCharsets.UTF_8);
        vals[i] = objectMapper.writeValueAsBytes(products.get(i));   // 序列化统一
    }
    redisTemplate.executePipelined((RedisCallback<Object>) conn -> {
        for (int i = 0; i < keys.length; i++) {
            conn.stringCommands().set(keys[i], vals[i]);
        }
        return null;
    });
}
```

### 6.2 分批与内存控制

| 批量规模 | 建议 | 原因 |
|---------|------|------|
| < 1000 条 | 一次管道 | 无压力 |
| 1000 - 5000 | 每批 1000-2000 | 缓冲与响应时间平衡 |
| > 5 万 | 分批 + 异步/背压 | 内存与连接保护（[08 篇](08-响应式与ReactiveRedisTemplate速查.md) 响应式批量更优雅） |

> 💡 **批量与 8.4 MSETEX**：批量写"各自带 TTL"的 key 用 MSETEX 一条命令（[04 篇](04-操作API与Redis-8-4新命令速查.md) 5.2）——比管道更省（命令数少）；但 MSETEX 是单命令（受参数数量限制），超大批量仍用管道分批。

### 6.3 性能自查清单

| # | 检查 | 说明 |
|---|------|------|
| ① | 循环里逐条 set/get | 改管道/Lua/MSETEX（最常见性能病） |
| ② | 管道无分批 | 大管道内存风险 → 分批 1000-2000 |
| ③ | 管道里开事务 | 4.x 互斥约束（[10 篇](10-集成地图与常见问题.md)） |
| ④ | 需要原子却用了管道 | 改事务/Lua（原子性检查） |
| ⑤ | 集群下多 key 跨 slot | hash tag（[02 篇](02-快速开始与连接配置速查.md) 4.2） |
| ⑥ | 慢命令（KEYS/大集合全量） | 改 SCAN/分批（[Redis-06](../../../../02-非关系型数据库/Redis/06-Redis缓存实战与常见问题.md)） |

> 🎯 性能口诀：**"循环命令必批量、批量必分批、原子组合用 Lua"**——三条守住，Redis 侧性能问题减掉八成。
