## 1. 序列化为什么是头号事故源

**通俗**：Redis 只存字节（RESP 协议传字节），"存进去什么格式、读出来什么格式"完全由序列化器决定——**写入方和读取方序列化器不一致 = 乱码/反序列化失败**，这是 Spring Data Redis 90% 生产事故的根源。

```text
写入方：RedisTemplate(key=String, value=Jackson) ──► Redis 字节
读取方：RedisTemplate(key=String, value=JDK)    ──► 解析失败/乱码 ❌

同一套 Redis，不同服务/不同版本序列化器必须一致！
```

| 事故 | 症状 | 根源 |
|------|------|------|
| key 乱码 | `\xAC\xED\x00\x05t\x00\x0Bproduct:1` | 默认 JDK 序列化 |
| value 反序列化失败 | `ClassCastException`/`JSON parse error` | 类型信息丢失（@class 缺失） |
| 跨服务读不到 | 服务 A 写的服务 B 读不了 | 两侧序列化器不一致 |
| 升级后老数据读不了 | 序列化配置变了 | 变更序列化器前**必须考虑存量数据** |

> 🎯 铁律：**序列化配置是团队级约定**——key 统一 String、value 统一 JSON（带类型信息）、跨服务一致；改序列化器 = 数据迁移，不是改配置。

## 2. RedisSerializer 家族速查

| 序列化器 | 输出 | 可读性 | 类型安全 | 适用 |
|---------|------|:---:|:---:|------|
| `JdkSerializationRedisSerializer`（默认） | 二进制 | ❌ | ✅（带类信息） | **仅内部缓存**（官方默认但生产慎用） |
| `StringRedisSerializer` | 原文字节 | ✅ | ❌（需自行转换） | **key 必用**；value 为纯字符串 |
| `GenericJackson2JsonRedisSerializer` | JSON | ✅ | ✅（@class 类型标记） | **value 主力**（通用对象） |
| `Jackson2JsonRedisSerializer<T>` | JSON | ✅ | ⚠️（需指定类型） | value 类型固定时 |
| `GenericJackson2JsonRedisSerializer`（4.x 新名） | JSON | ✅ | ✅ | Jackson 3 迁移目标（第 4 节） |
| `GenericToStringSerializer` | String | ✅ | ⚠️ | 简单类型（Long 等） |
| 自定义 `RedisSerializer` | 自定 | — | — | 特殊格式（protobuf 等） |

```java
// 标准配置模板（key=String，value=JSON 带类型）
RedisTemplate<String, Object> t = new RedisTemplate<>();
t.setKeySerializer(new StringRedisSerializer());
t.setHashKeySerializer(new StringRedisSerializer());
t.setValueSerializer(new GenericJackson2JsonRedisSerializer());
t.setHashValueSerializer(new GenericJackson2JsonRedisSerializer());
```

> 🎯 选型一句话：**key 永远 String、value 通用对象用 GenericJackson2Json（带 @class）、纯字符串场景直接 StringRedisTemplate**——JDK 序列化只留给"绝不跨服务、绝不读码"的纯内部缓存。

## 3. JDK 序列化三大陷阱

| 陷阱 | 症状 | 说明 |
|------|------|------|
| **① 可读性** | redis-cli 里全是 `\xAC\xED` 乱码 | 运维无法用命令直接查看/修数据 |
| **② 兼容性** | 类改动（字段/包名）后老数据读不了 | JDK 序列化强绑定类结构（serialVersionUID） |
| **③ 性能与体积** | 体积大数倍（含类名+结构信息） | 网络与内存浪费；序列化 CPU 开销高 |

```text
JDK 序列化体积示例：
  "product:1" → 28 字节          # String 序列化
  Product 对象 → 300+ 字节       # JDK 序列化（含类名/字段描述）
  Product 对象 → 120 字节        # JSON
```

> ⚠️ 默认配置陷阱：**Boot 自动装配的 RedisTemplate 默认是 JDK 序列化**——不配置直接跑，生产一上 redis-cli 全乱码；**第一个 Bean 配置就是序列化器**（第 2 节模板）。

## 4. Jackson 2 → 3 迁移（4.x）

> Spring Data Redis 4.x 跟随全家族 **Jackson 3 迁移**：序列化器命名与包变化（Jackson 3 的坐标/包名改为 `tools.jackson`，注解仍在 `com.fasterxml.jackson`）。

| 维度 | 3.x（Jackson 2） | 4.x（Jackson 3） |
|------|------------------|------------------|
| 序列化器类 | `GenericJackson2JsonRedisSerializer` | **`GenericJackson2JsonRedisSerializer`（包路径/依赖变化，类名保留）** |
| Jackson 坐标 | `com.fasterxml.jackson.core:jackson-databind` | `tools.jackson.core:jackson-databind`（Jackson 3） |
| 类型标记 | `@class`（默认开启） | 默认行为保持（类型信息仍写入） |
| 迁移动作 | — | 依赖坐标更新 + 全量回归（老数据 @class 兼容） |

```xml
<!-- Jackson 3 依赖（4.x BOM 管理，通常无需手写） -->
<dependency>
    <groupId>tools.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
</dependency>
```

> ⚠️ 迁移注意：① **存量数据的 @class 标记与 Jackson 3 反序列化兼容**（类型引用格式不变），但全量回归不可省；② 自定义 `ObjectMapper` 配置（日期格式、忽略未知字段）要在新序列化器上重建；③ **序列化器改动 = 数据格式变更**——先测试环境全量读写验证再上生产（[10 篇](10-集成地图与常见问题.md) 迁移清单）。

## 5. key/value 双序列化与 StringRedisTemplate

### 5.1 key 与 value 分开设（双序列化）

```java
// key 用 String（业务可读、跨端一致）
// value 用 JSON（对象可读、类型安全）
t.setKeySerializer(new StringRedisSerializer());       // key: "product:1"
t.setValueSerializer(new GenericJackson2JsonRedisSerializer());  // value: {"@class":...,"name":...}

// 反例：key 也用 JDK → redis-cli 查不到、监控/运维全废
```

### 5.2 StringRedisTemplate（全 String 场景）

```java
// key 和 value 都是 String 的专用模板（Boot 自动装配）
StringRedisTemplate stringRedisTemplate;

stringRedisTemplate.opsForValue().set("counter", "100");
String v = stringRedisTemplate.opsForValue().get("counter");   // "100"（纯字符串，无需类型）

// 数值操作（Redis 原子自增）
Long n = stringRedisTemplate.opsForValue().increment("counter");  // 101
```

| 场景 | 用哪个 |
|------|--------|
| key 和 value 都是纯字符串（计数/会话 token/短链） | **StringRedisTemplate**（零配置心智） |
| value 是对象/复杂结构 | RedisTemplate + JSON 序列化器 |
| Hash 的 field 是字符串、value 是对象 | RedisTemplate（hashKey=String，hashValue=JSON） |

> 💡 **StringRedisTemplate 本质**：RedisTemplate 的 key/value/hashKey/hashValue 全 String 序列化——它是"最简单的正确配置"，新项目如果 90% 场景是字符串，直接用它起步。

## 6. @RedisHash 实体映射与二级索引

**通俗**：把 Java 对象直接存成 Redis Hash（字段 = Hash field），还能对指定字段建"二级索引"做条件查询——轻量"对象仓库"模式。

```java
@RedisHash("product")                        // key 前缀：product:{id}
public class Product {
    @Id private String id;                   // 生成 key：product:{id}
    @Indexed private String category;        // ★ 二级索引：可条件查询
    @Indexed private String status;
    private String name;
    private BigDecimal price;
    // getter/setter
}

public interface ProductRepository extends CrudRepository<Product, String> {
    List<Product> findByCategory(String category);    // 走二级索引（category:index 集合）
    List<Product> findByStatusAndCategory(String status, String category);
}
```

| 存储形态 | 说明 |
|---------|------|
| 主数据 | `product:{id}`（Hash：字段=属性） |
| 二级索引 | `product:category:手机`（Set：存匹配的 id）——**写入时自动维护** |
| TTL | 实体级无注解，手动 `expire` 或 `@TimeToLive`（`@TimeToLive` 字段动态 TTL） |
| 查询 | 仅**索引字段**可条件查询（非索引字段查不了） |
| 适用边界 | 轻量对象缓存；**复杂查询/大对象 → RedisTemplate 手动设计**（[04 篇](04-操作API与Redis-8-4新命令速查.md)） |

> 🎯 面试必答：**"@RedisHash 和 RedisTemplate 怎么选？"**——@RedisHash 适合"**对象级缓存 + 简单索引查询**"（如用户资料、会话数据：按 id 存取 + 按状态筛）；复杂结构/高性能/精确控制 TTL 与序列化 → RedisTemplate 手动设计——**Redis 本质是 KV 引擎，Repository 模式是"给 KV 套 ORM 壳"**，复杂查询需求一出现就该换回模板或换存储。

## 7. 乱码排查与选型总表

### 7.1 乱码排查五步

| 步骤 | 动作 | 结论 |
|------|------|------|
| ① | redis-cli `keys *` 看 key | `\xAC\xED` 开头 = key 用了 JDK 序列化 |
| ② | redis-cli `get product:1` 看 value | 二进制乱码 = value 用了 JDK；JSON 可读 = OK |
| ③ | 对比写入/读取的模板配置 | 两侧序列化器不一致（跨服务/跨版本） |
| ④ | 看反序列化异常 | 缺 @class / 类结构变了 |
| ⑤ | 检查自定义序列化器 | 自定义实现 bug（write/read 不对称） |

### 7.2 选型总表（团队约定模板）

| 数据形态 | key | value | 推荐模板 |
|---------|-----|-------|---------|
| 纯字符串（计数/token） | String | String | StringRedisTemplate |
| 通用对象（缓存业务数据） | String | JSON（GenericJackson2Json） | RedisTemplate + 标准序列化 |
| Hash 对象（@RedisHash） | String | — | RedisRepository |
| 跨语言/跨服务共享 | String | **协议明确**（JSON Schema/protobuf） | 自定义序列化器 |
| 敏感数据 | String | 加密序列化器 | 自定义（**慎用**，先评估 Redis 是否该放敏感数据） |

> 🎯 团队规范三句：**① key 全 String + 业务前缀（product:、session:）；② value 全 JSON 带类型；③ 改序列化器 = 数据迁移，走评审**——三条守住，乱码类事故绝迹。
