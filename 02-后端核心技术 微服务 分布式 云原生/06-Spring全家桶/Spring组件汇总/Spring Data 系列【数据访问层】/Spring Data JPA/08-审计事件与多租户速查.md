## 1. Spring Data 审计：自动填充创建/修改信息

### 1.1 三步开启

```java
// ① 启用审计（任意配置类）
@Configuration
@EnableJpaAuditing
public class JpaAuditingConfig { }

// ② 实体字段加注解
@Entity
public class Product {
    @Id private Long id;

    @CreatedDate          private LocalDateTime createdAt;    // 插入时自动填
    @LastModifiedDate     private LocalDateTime updatedAt;    // 每次更新自动改
    @CreatedBy            private String createdBy;           // 创建人
    @LastModifiedBy       private String updatedBy;           // 最后修改人
}

// ③ 审计人来源（获取当前登录用户）
@Bean
AuditorAware<String> auditorAware() {
    return () -> Optional.ofNullable(SecurityContextHolder.getContext().getAuthentication())
            .map(Authentication::getName)
            .or(() -> Optional.of("system"));       // 匿名/系统任务兜底
}
```

| 注解 | 语义 | 触发点 |
|------|------|--------|
| `@CreatedDate` | 创建时间 | 首次 persist |
| `@LastModifiedDate` | 最后修改时间 | 每次 flush 检测到变更 |
| `@CreatedBy` / `@LastModifiedBy` | 操作者 | 同上，取 `AuditorAware` |

> 💡 常见配套：① 共享字段抽到 `@MappedSuperclass`（[03 篇](03-实体映射与关联映射速查.md) 5.2）；② 用 `Auditable<T>` 接口 + `AbstractAuditable` 基类免写字段；③ **多数据源**：每个 EntityManagerFactory 各自的审计配置独立（`@EnableJpaAuditing` 只配一处即可，AuditorAware 全局生效）。

### 1.2 与 Hibernate 内置注解的对比

| 能力 | Spring Data 审计 | Hibernate `@CreationTimestamp`/`@UpdateTimestamp` |
|------|-----------------|--------------------------------------------------|
| 时间字段 | ✅ | ✅ |
| 操作者字段 | ✅ | ❌（需自己填） |
| 依赖 | spring-data-commons 审计模块 | Hibernate 内核 |
| 多源一致 | 各 Repository 统一 | 实体级 |
| 建议 | **团队统一用 Spring Data 审计** | 无 Spring Data 的纯 Hibernate 场景用 |

> ⚠️ 审计字段最佳实践：① **DB 侧也建默认值**（`DEFAULT CURRENT_TIMESTAMP`）兜底，防止绕过 JPA 的脚本插入缺列；② 时间列用 `insertable=false, updatable=false` 交给 DB 时，审计注解与 DB 默认值二选一，别重复；③ 大批量 @Modifying 更新（[04 篇](04-Repository速查.md) 第 4 节）**不触发**审计注解——批量改数据的审计靠显式列 + 日志，别依赖框架。

## 2. 实体生命周期回调

```java
@Entity
public class OrderEntity {
    @PrePersist void prePersist() { 
        this.orderNo = generateOrderNo();          // 插入前：生成业务编号
        this.status = OrderStatus.PENDING;         // 插入前：填默认状态
    }
    @PreUpdate  void preUpdate()  { this.updatedAt = LocalDateTime.now(); }   // 更新前
    @PostLoad   void postLoad()   { }              // 加载后：缓存派生字段（不落库）
    @PreRemove  void preRemove()  { }              // 删除前：校验/级联清理
    @PostPersist / @PostUpdate / @PostRemove / @PostLoad  // 对应后置钩子
}
```

| 钩子 | 时机 | 典型用途 |
|------|------|---------|
| `@PrePersist` | insert 前 | 业务编号、默认值、密码加密 |
| `@PostPersist` | insert 后 | 拿 id 后动作（注意：可能在 flush 时，不在方法返回时） |
| `@PreUpdate` | update 前 | 更新时间戳（用 @UpdateTimestamp 可省） |
| `@PostLoad` | 查询装载后 | 计算只读派生字段 |
| `@PreRemove` | delete 前 | 删除校验、级联清理 |

> ⚠️ 三大坑：① **回调在 flush 时触发**（批量场景延后、@Modifying 批量更新完全不触发）；② 回调里**不要再做查询/修改同实体**（可能递归/状态错乱），只做纯字段设置；③ `@PrePersist` 里调 `save` 会递归死循环——回调内用属性赋值，不调 Repository。

## 3. Spring Data 事件（与 JPA 回调的区别）

```java
// 监听器
@Component
public class ProductEventListener {
    @EventListener
    public void onSave(AfterSaveEvent<Product> event) {     // 保存后
        Product p = event.getEntity();
        searchIndexService.index(p);                         // 同步写 ES 索引（或发消息异步）
    }
}
```

| Spring Data 事件 | 时机 | 与 JPA 回调区别 |
|------------------|------|----------------|
| `BeforeSaveEvent` / `AfterSaveEvent` | save() 调用前后 | **由 Spring Data 触发**（save 方法），JPA 回调由 Hibernate 触发（flush 时） |
| `BeforeDeleteEvent` / `AfterDeleteEvent` | delete() 前后 | 逐条删除才触发；批量 @Modifying 不触发 |
| `AfterConvertEvent` | 查询结果装配后 | 读侧钩子 |

> 🎯 面试必答：**"JPA 回调和 Spring Data 事件有什么区别？"**——① 触发源不同：JPA 回调（@PrePersist 等）由 **Hibernate flush 时**触发，Spring Data 事件由 **Repository 的 save/delete 方法调用时**触发；② 参数不同：事件带整个实体上下文（BeforeSaveEvent 可改实体）；③ 批量操作都不触发——**"同步写索引/缓存"的挂载点用 Spring Data 事件（AfterSaveEvent），"实体字段默认值"用 JPA 回调**。
>
> ⚠️ 性能红线：事件监听器里做远程调用/重 IO 会拖慢主事务——**发消息异步化**（Spring 事件 `@Async` / `@TransactionalEventListener`），或事务提交后再触发：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)   // 事务提交后才执行
public void onSaved(AfterSaveEvent<Product> event) { ... }           // 失败不回滚主事务
```

## 4. Hibernate 7.4：@Audited 审计表与 @Temporal 时态表

> **7.4 新特性**（2026-05 发布）：把"每次变更留痕"内置进 ORM——以前只能靠 Envers 或自建双表，现在原生支持（本系列升级价值点之二）。

### 4.1 @Audited：审计表

```java
@Entity
@Audited                                   // 对该实体生成审计表：product_aud（含 REV/REVTYPE 列）
public class Product {
    @Id private Long id;
    private String name;
    private BigDecimal price;
}
```

| 概念 | 说明 |
|------|------|
| 生成 | 每次 insert/update/delete 在 `product_aud` 追加一行（修订号 REV + 修订类型 REVTYPE：0=新增/1=修改/2=删除） |
| 查询 | 按修订号回溯任意时间点的实体状态 |
| 定位 | 原 Envers 能力的原生替代（Envers 独立模块仍可用） |
| 成本 | 每次变更多写一张表——**只对需要审计的核心表启用** |

### 4.2 @Temporal：时态历史表（时态查询）

```java
@Entity
@Temporal(strategy = TemporalStrategy.HISTORY_TABLE)   // 生成 products_history 时态表
public class Product {
    @Id private Long id;
    private String name;
}
```

| 策略 | 行为 |
|------|------|
| `HISTORY_TABLE` | 独立历史表 `products_history`，带 `effective`/`superseded` 生效区间列 |
| `SINGLE_TABLE` | 主表加生效区间（每行带版本区间） |
| `NATIVE` | 依赖数据库原生时态支持（如 SQL Server Temporal Table） |

> 💡 定位：**业务需要"任意时间点快照查询"**（如"上周三这个商品价格是多少"）时，@Temporal 直接解决；普通"谁改了什么"用 @Audited；两者都可与 Spring Data 审计共存（各管一段：审计管操作记录，时态管状态快照）。

## 5. 软删除实战

> 业务上"删了要能恢复/留痕"的场景（订单、用户、文章）——不真删行，标记删除。JPA 无标准软删除注解，主流两种姿势：

### 5.1 姿势 A：@SQLDelete（Hibernate 拦截）

```java
@Entity
@SQLDelete(sql = "update product set deleted = true, deleted_at = now() where id = ?")
@SQLRestriction("deleted = false")                       // Hibernate 6.3+：全局过滤已删行
public class Product {
    @Id private Long id;
    @Column(nullable = false) private boolean deleted;
    private LocalDateTime deletedAt;
}
```

| 效果 | 说明 |
|------|------|
| delete() | 被翻译成 UPDATE 标记（所有删除入口统一拦截） |
| 查询 | @SQLRestriction 自动追加 `and deleted = false`（**所有查询含关联都过滤**） |
| 代价 | 需全局过滤：漏配的查询/原生 SQL 会读到已删数据；复杂 where 拼接注意过滤顺序 |

### 5.2 姿势 B：显式字段（团队控制）

```java
@Entity
public class Product {
    @Id private Long id;
    private LocalDateTime deletedAt;          // null = 未删除；非 null = 已删

    public void softDelete() { this.deletedAt = LocalDateTime.now(); }

    // 查询全用派生方法显式过滤：
    // findByDeletedAtIsNull() —— 所有查询都要带，漏一个就是线上事故
}
```

| 对比 | @SQLDelete 拦截式 | 显式字段式 |
|------|------------------|-----------|
| 防漏 | ✅ 自动过滤（关联查询也拦） | ❌ 靠自觉 |
| 可控性 | 全局生效难豁免（想查已删数据要额外技巧） | 灵活 |
| 推荐 | **新项目推荐**（Hibernate 7 下 @SQLRestriction 成熟） | 旧团队习惯沿用 |

> ⚠️ 软删除三提醒：① **唯一约束冲突**：软删后同名行再插入会撞唯一键（`user.phone` 唯一）——唯一索引里带 `deleted` 列或加 deleted_at 时间戳部分索引；② 批量 `@Modifying` 软删：直接手写 `update ... set deleted=true`（不走 @SQLDelete 拦截）；③ 关联过滤：`@SQLRestriction` 在集合上也生效（`@OneToMany ... @SQLRestriction("deleted = false")`），别漏。

## 6. 多租户方案

| 方案 | 原理 | 隔离度 | 成本 | 适用 |
|------|------|:---:|:---:|------|
| **共享表 + 租户列（Discriminator）** | 所有表加 tenant_id，查询自动过滤 | 低（逻辑隔离） | 低 | SaaS 中小租户（**最常用**） |
| 共享库 + 独立 Schema | 每租户一套 schema | 中 | 中 | 租户可迁移/备份 |
| 独立数据库 | 每租户一个库 | 高（物理隔离） | 高 | 大客户/合规要求 |
| 应用层约定（手动 where） | 每查询带 tenant_id | 低 | 最低 | 早期项目过渡 |

### 6.1 Hibernate 7 多租户（推荐：租户列 + 过滤器）

```java
// ① 实体加租户列（配合 Filter 自动过滤）
@Entity
@FilterDef(name = "tenantFilter", parameters = @ParamDef(name = "tenantId", type = Long.class))
@Filter(name = "tenantFilter", condition = "tenant_id = :tenantId")
public class OrderEntity {
    @Id private Long id;
    private Long tenantId;
}

// ② 请求上下文解析租户（Servlet Filter 从 Token/域名取）
public class TenantContext {
    private static final ThreadLocal<Long> CURRENT = new ThreadLocal<>();
    public static void set(Long tenantId) { CURRENT.set(tenantId); }
    public static Long get() { return CURRENT.get(); }
    public static void clear() { CURRENT.remove(); }
}

// ③ 每次会话开启时启用过滤器
@Component
public class TenantAwareHibernateListener {
    @EventListener
    public void onSessionOpen(SessionFactoryEvent.Type.SESSION_OPEN event) { }
    // 或：自定义 EntityManagerFactoryCustomizer 注册 SessionEventListener
    // 在每次 getCurrentSession 时：
    //   session.enableFilter("tenantFilter").setParameter("tenantId", TenantContext.get());
}
```

### 6.2 Hibernate 多租户原生接口（表/库级隔离）

```java
// 每租户独立 schema/库时实现（Hibernate 7 接口稳定）：
public class TenantConnectionProvider implements MultiTenantConnectionProvider {
    // selectConnection(String tenantId) → 按租户返回不同 DataSource/连接
}

// 配置（application.yml 或编程式）：
// hibernate.multi_tenant_connection_provider=com.example.TenantConnectionProvider
// hibernate.tenant_identifier_resolver=com.example.CurrentTenantResolver
```

| 实现点 | 接口 | 职责 |
|--------|------|------|
| 租户解析 | `CurrentTenantIdentifierResolver` | 从上下文取当前租户 |
| 连接提供 | `MultiTenantConnectionProvider` | 按租户给连接（schema/库级隔离的核心） |

> ⚠️ 多租户三红线：① **ThreadLocal 必清**（请求结束 clear，防串租户——用 `finally` 或 Servlet Filter 统一）；② **异步/线程池场景 ThreadLocal 不跨线程**（租户信息随任务传递，别踩 [06 篇](06-事务与并发控制速查.md) 多线程坑）；③ 租户列方案漏过滤 = 数据串租户（**生产级事故**）——用 @Filter 全局拦截，禁止手写 where 约定；需要更细的隔离与治理评估 [ShardingSphere](https://shardingsphere.apache.org/) 或云数据库多租户产品。
