## 1. 性能问题全景与排查法

| 问题 | 典型症状 | 根因 | 解法 |
|------|---------|------|------|
| N+1 查询 | 日志里"1 条列表查询 + N 条单查" | 懒加载集合逐条访问 | fetch join / @EntityGraph（第 3 节） |
| 列表查询慢 | 同一条 SQL 手工执行快 | EAGER 关联 join 膨胀 / 缺索引 | LAZY + 按需 fetch；加索引 |
| 批量插入慢 | 1000 条插了 1000 次 | 逐条 flush（IDENTITY 主键更糟） | batch_size + order_inserts（第 4 节） |
| 分页慢 | offset 大时指数级变慢 | 深分页全表扫描 | 游标分页（[04 篇](04-Repository速查.md) 5.3） |
| 内存爆 | 大结果集全量加载 | 无分页/无流式 | 分页 / Stream（[04 篇](04-Repository速查.md) 6.2） |
| 慢 SQL 偶发 | 时快时慢 | 缓存失效/统计信息过时 | 数据库侧分析（[SQL调优系列](../../../../01-关系型数据库/SQL调优/)） |

> 🎯 排查铁律：**show-sql 打开 → 看真实 SQL → EXPLAIN → 改查询/加索引**。JPA 生成 SQL 的怪异 90% 能一眼定位（N+1、无索引、EAGER join）；永远不要"凭感觉加二级缓存/改 fetch 策略"。

## 2. N+1 查询问题详解

### 2.1 什么是 N+1

```java
// 反模式：列表页展示订单 + 每个订单的用户名
@Transactional(readOnly = true)
public List<OrderEntity> listOrders() {
    List<OrderEntity> orders = orderRepository.findAll();        // SQL 1：select * from `order`
    return orders;                                              // 页面访问 o.getUser().getName()
}                                                               // 每行 → SQL 2..N：select * from user where id=?

// 共 1 + N 条 SQL —— N 是订单行数
```

| 阶段 | SQL 数 | 耗时（例） |
|------|:---:|---------|
| 列表查询 | 1 | 10ms |
| 懒加载访问 | N（每行一次） | 1000 行 × 5ms = 5s |
| 合计 | N+1 | 灾难 |

### 2.2 根治方案对比

| 方案 | SQL 数 | 适用 | 代价 |
|------|:---:|------|------|
| **fetch join**（JPQL） | 1 | 查询时确定要加载的关联 | 集合 join 会行膨胀（配合 distinct）；分页场景见 [7.4 分页下沉](#6-74-新特性分页--fetch-join-下沉-sql) |
| **@EntityGraph** | 1 | 派生方法/查询方法声明抓取路径 | 同上 |
| **@BatchSize** | 1 + (N/批量) | 懒加载兜底（不显式 fetch） | 批量 in 查询，仍比 1 条多 |
| 二级缓存 | 0 | 高频只读数据 | 一致性风险 |

> 🎯 面试必答：**"怎么根治 N+1？"**——三层答案：① 查询时 `fetch join`/`@EntityGraph` 显式抓取（首选）；② 无法显式抓取的场景用 `default_batch_fetch_size` 兜底（IN 批量）；③ 缓存热数据（二级缓存）。只答"懒加载改急加载"是错误答案（改 EAGER 是地图炮，全部查询全带 join）。

## 3. 加载策略：fetch join / EntityGraph / 批量抓取

### 3.1 fetch join（JPQL）

```java
// 单条关联：left join fetch 集合
@Query("select distinct o from OrderEntity o "
     + "left join fetch o.items i "
     + "where o.status = :status")
List<OrderEntity> findByStatusWithItems(@Param("status") OrderStatus status);
```

| 要点 | 说明 |
|------|------|
| distinct | 集合 join 行膨胀（1 订单 3 明细 = 3 行）→ distinct 去重（内存去重，小结果集可接受） |
| 多集合 | **一次只 fetch 一个集合**：多集合 join 笛卡尔积爆炸 → 分次查或 @BatchSize 兜底 |
| 分页 | 集合 fetch join + 分页在 6.x 是内存分页，**7.4 起已下沉 SQL**（第 6 节） |
| 替代 | 不需要 where 条件时可用 `@EntityGraph(attributePaths = "items")` 更简洁 |

### 3.2 @EntityGraph（声明式）

```java
public interface OrderRepository extends JpaRepository<OrderEntity, Long> {

    @EntityGraph(attributePaths = {"items", "items.product"})     // 嵌套路径
    List<OrderEntity> findByStatus(OrderStatus status);

    @EntityGraph(type = EntityGraph.EntityGraphType.FETCH)         // FETCH(默认，追加抓取) / LOAD(叠加关联映射)
    @Query("select o from OrderEntity o where o.customerId = :cid")
    List<OrderEntity> findByCustomer(@Param("cid") Long cid);
}
```

> 💡 区别一句话：**@EntityGraph 是"给查询附加抓取路径"，fetch join 是"查询里显式 join"**——EntityGraph 不改变 where 语义（fetch join 若把 join 写进 where 会过滤行），复杂条件用 fetch join，简单查询用 EntityGraph。

### 3.3 @BatchSize 兜底

```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100     # 全局兜底：集合懒加载变成 IN (100 ids)
```

```java
// 或实体级
@Entity
public class OrderEntity {
    @OneToMany(mappedBy = "order")
    @BatchSize(size = 50)                 // 仅此集合生效
    private List<OrderItem> items;
}
```

| 场景 | 效果 |
|------|------|
| 无法 fetch join 的查询路径 | N+1 → N/100 + 1（每 100 个 id 一次 IN 查询） |
| 深度懒加载（多层） | 每层各自批量，总 SQL 数可控 |
| 与 fetch join 关系 | fetch join 优先，BatchSize 是兜底不是替代 |

## 4. 批量写入优化

### 4.1 配置与代码

```yaml
spring:
  jpa:
    properties:
      hibernate:
        jdbc.batch_size: 50              # ★ 核心：批处理块大小
        order_inserts: true              # 按实体类型排序插入（批命中率关键）
        order_updates: true              # 更新同理
        jdbc.batch_versioned_data: true  # 带 @Version 也批处理
```

```java
// Repository 批量保存（内部仍逐条 flush，但 SQL 打包成多行 insert）
@Transactional
public void importProducts(List<Product> products) {
    productRepository.saveAll(products);
}

// 大量数据（万级）分块提交，防事务过大
@Transactional
public void importHuge(List<Product> products) {
    for (int i = 0; i < products.size(); i += 500) {
        productRepository.saveAll(products.subList(i, Math.min(i + 500, products.size())));
        productRepository.flush();
        entityManager.clear();            // 清一级缓存，防内存膨胀（注入 EntityManager）
    }
}
```

### 4.2 主键策略对批量的影响（面试必答）

| 主键策略 | 批量行为 | 结论 |
|---------|---------|------|
| SEQUENCE | 预取序列号（allocationSize），可整批 insert 多条 | ✅ **大批量导入选 SEQUENCE**（PostgreSQL/Oracle） |
| IDENTITY | 必须逐条 insert 才能拿到 id | ❌ 批量失效（逐条） |
| UUID | 应用生成，天然可批 | ✅ 分布式场景 |

> 🎯 面试必答：**"为什么 MySQL + IDENTITY 批量插入慢？"**——IDENTITY 的 id 由数据库生成，JPA 必须执行完一条 insert 拿到 id 才能继续 → 批处理退化为逐条；解法：① 数据导入换 SEQUENCE 策略（MySQL 8 无序列，可模拟）；② 用原生批量 insert（MyBatis/JDBC 直连）；③ 主键换 UUID/业务键。

## 5. 深分页与大数据量读取

| 场景 | 方案 | 出处 |
|------|------|------|
| 列表页（offset 小） | Page 分页 | [04 篇](04-Repository速查.md) 5.1 |
| 无限滚动/大表 | 游标分页（keyset） | [04 篇](04-Repository速查.md) 5.3 |
| 导出/报表百万行 | Stream 流式（事务内 + 关闭） | [04 篇](04-Repository速查.md) 6.2 |
| 只读大表扫描 | `@EntityGraph` 不参与 + 投影（第 8 节） | 本页 |

> ⚠️ 三件套记忆：**offset 深分页慢 → 游标；全量加载爆内存 → 流式；查询只带部分字段 → 投影**——性能优化三板斧，面试与实战通用。

## 6. 7.4 新特性：分页 + fetch join 下沉 SQL

> **Hibernate 7.4（2026-05）的重大性能修复**（本系列升级价值最大的一项，面试可讲"2026 新特性"）。

| 版本 | 行为 | 问题 |
|------|------|------|
| ≤7.2 | 集合 fetch join + 分页 → 先取全量结果到内存，再内存分页 | 大数据量内存爆炸；offset 分页失效 |
| **7.4** | **先取"受分页限制的父实体 ID"（嵌套查询），再按 ID 抓取集合** | 分页语义正确 + 内存可控 |

```java
// 7.4 之前：这行在内存里分页（可能 OOM）
@Query("select distinct o from OrderEntity o left join fetch o.items")
Page<OrderEntity> findAllWithItems(Pageable pageable);

// 7.4 起：LIMIT/OFFSET 下沉 SQL，只对有限的父 ID 加载集合 ✅
```

| 回退开关 | 说明 |
|---------|------|
| `org.hibernate.limitInMemory` 查询 hint | 恢复旧内存分页行为（如遇到 7.4 分页 SQL 生成 bug 时逃生） |

> 💡 升级 4.1/Hibernate 7.4 的核心收益之一：**带集合的分页查询可以直接放心写 fetch join 了**（旧版本这里全是内存分页坑）。

## 7. 二级缓存

### 7.1 缓存层级

```text
业务代码
  └─ 一级缓存（持久化上下文）     # Session 内，默认开启，事务结束即失效
       └─ 二级缓存（SessionFactory） # 跨事务/跨请求共享，需显式开启 + 配置
```

| 缓存 | 作用域 | 默认 | 配置 |
|------|--------|:---:|------|
| 一级缓存 | 当前 Session（事务） | ✅ | 无需配置；`clear()`/`detach()` 管理 |
| 查询缓存 | 二级缓存之上（结果集） | ❌ | `hibernate.cache.use_query_cache=true` |
| 二级缓存 | SessionFactory（全应用） | ❌ | `@Cacheable` + `hibernate.cache.region.factory_class` |

### 7.2 开启二级缓存

```yaml
spring:
  jpa:
    properties:
      hibernate:
        cache.use_second_level_cache: true
        cache.region.factory_class: org.hibernate.cache.jcache.JCacheRegionFactory   # 需 hibernate-jcache 依赖
        cache.use_query_cache: true        # 查询缓存（结果集；变更频繁的表反而慢，慎开）
```

```java
@Entity
@Cacheable                                      // 实体级：参与二级缓存
public class Category { ... }                   // 适用：低频变更的字典/类目数据
```

| 适用 | 不适用 |
|------|--------|
| 字典、类目、地区等**低频变更**数据 | 高频更新数据（缓存失效风暴） |
| 多请求共享的只读查询 | 按用户/时间过滤的结果集（失效成本高） |

> ⚠️ 二级缓存是**性能优化最后手段**：先修查询（fetch join/索引），再谈缓存；改数据（update）要同步失效缓存，JPA 自动维护，但**原生 SQL 更新会绕过缓存**——原生更新后一致性靠你的代码负责。缓存一致性优先用 [Redis](../../../Spring Data Redis/00-Spring Data Redis知识体系总览.md) 层方案（Cache-Aside），二级缓存留给"进程内高频只读"场景。

## 8. 投影（Projection）

> 只查需要的列：大实体列表页/报表场景，列越少，DB 扫描越少、网络传输越少、无需加载整个对象图。

```java
// ① 接口投影（封闭接口，只暴露 getter）
public interface ProductSummary {
    Long getId();
    String getName();
    BigDecimal getPrice();
}

// ② record 投影（4.0 推荐，简洁不可变）
public record ProductView(Long id, String name, BigDecimal price) {}

public interface ProductRepository extends JpaRepository<Product, Long> {

    List<ProductSummary> findAllByCategory(String category);        // 接口投影（Spring Data 自动生成）

    @Query("select new com.example.dto.ProductView(p.id, p.name, p.price) "
         + "from Product p where p.category = :category")           // JPQL 构造器投影
    List<ProductView> findViews(@Param("category") String category);
}
```

| 投影方式 | 说明 | 适用 |
|---------|------|------|
| 接口投影 | 动态代理生成实现，免写类 | 简单字段子集；多实体拼装麻烦 |
| record / DTO 构造器投影 | JPQL `new` 显式构造 | 复杂聚合/多实体；类型安全 |
| 类投影（@Projection） | 带 @Value 计算 | 旧写法，新代码用 record |

> 💡 投影 + 索引黄金组合：列表页"只查列表字段"的投影查询，建**覆盖索引**后走 index-only scan（[MySQL 索引原理](../../../../01-关系型数据库/MySQL/04-索引原理与设计.md)），比整行查询快一个量级。

## 9. 性能排查清单

| # | 动作 | 说明 |
|---|------|------|
| ① | `spring.jpa.show-sql=true` + `format_sql=true` | 拿到真实 SQL 与执行顺序（N+1 一眼可见） |
| ② | 数 SQL 条数 | 列表页 >10 条 SQL → N+1 确认 |
| ③ | 对热点 SQL 跑 EXPLAIN | 走没走索引、扫描行数（[SQL调优系列](../../../../01-关系型数据库/SQL调优/)） |
| ④ | 查 `default_batch_fetch_size` 是否配置 | 兜底 N+1 |
| ⑤ | 检查 EAGER 关联 | 全局搜 `FetchType.EAGER`（多对一默认），逐条评估 |
| ⑥ | 批量场景查主键策略 | IDENTITY + 批量 → 换方案（4.2 节） |
| ⑦ | 分页场景查 offset | 大 offset → 游标分页 |
| ⑧ | 大结果集场景查加载方式 | 全量 → 流式/投影 |
| ⑨ | 慢 SQL 日志 | `hibernate.session.events.log.LOG_QUERIES_SLOWER_THAN_MS` 阈值监控 |
| ⑩ | 升级评估 | Boot 4.1/Hibernate 7.4 的分页下沉特性（第 6 节） | 

> 🎯 口诀：**"先看 SQL、再修查询、最后上缓存"**——90% 的 JPA 性能问题在 ①-⑤ 步解决；⑥-⑧ 是结构性优化；二级缓存（第 7 节）永远最后考虑。
