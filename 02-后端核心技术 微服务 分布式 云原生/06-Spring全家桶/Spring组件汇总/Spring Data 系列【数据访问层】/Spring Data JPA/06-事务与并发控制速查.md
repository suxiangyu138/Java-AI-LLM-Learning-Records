## 1. 声明式事务基础

```java
@Service
public class OrderService {
    @Transactional                                   // 方法级事务
    public OrderEntity createOrder(OrderDto dto) {
        // ...调多个 Repository 方法——共用一个事务
    }

    @Transactional(readOnly = true)                  // 读事务（优化标记）
    public OrderEntity getOrder(Long id) { ... }
}
```

| 要点 | 说明 |
|------|------|
| 原理 | Spring AOP 代理：方法进入前开启/加入事务，异常时回滚，正常提交（[Spring 声明式事务管理](../../../Spring框架核心/06-声明式事务管理.md) 深度讲） |
| 默认行为 | 运行时异常（RuntimeException/Error）回滚；**受检异常（Exception）不回滚** |
| 生效条件 | ① 经 Spring 代理调用（外部调用）；② 方法所在类为 Spring Bean；③ 事务管理器存在 |
| 事务管理器 | `JpaTransactionManager`（Boot 自动配置，绑定 EntityManager） |
| 边界原则 | **事务边界在 Service 层**：一个业务用例 = 一个事务；Repository 方法自带的事务只是"单方法兜底"（[04 篇](04-Repository速查.md) 1.1） |

> 🎯 心智模型：`@Transactional` 不是"把方法包在 begin/commit 里"这么简单——它管理的是**持久化上下文的边界**：事务提交时 Hibernate 才 flush（脏检查 → UPDATE）、一级缓存才释放、锁才释放。事务越长，持锁越久、缓存越大。

## 2. 传播行为速查

| 传播行为 | 行为 | 典型场景 |
|----------|------|---------|
| `REQUIRED`（默认） | 有事务加入，无则新建 | **绝大多数业务** |
| `REQUIRES_NEW` | 挂起当前事务，新建独立事务 | 日志、审计、发消息（失败不影响主事务） |
| `NESTED` | 保存点：内层回滚不炸外层 | 批量处理逐条容忍失败（依赖 JDBC savepoint，MySQL 支持） |
| `SUPPORTS` | 有则加入，无则不开 | 查询辅助方法 |
| `NOT_SUPPORTED` | 挂起当前，无事务执行 | 大查询释放事务/锁（长连接场景） |
| `MANDATORY` | 必须已有事务，否则抛异常 | 内部专用方法（防漏事务） |
| `NEVER` | 必须无事务，否则抛异常 | 禁事务操作 |

```java
@Transactional
public void syncOrder(OrderEntity order) {
    orderRepository.save(order);                    // 主事务
    auditService.record(order);                     // @Transactional(propagation = REQUIRES_NEW)
}                                                   // audit 独立提交，主事务回滚不影响审计落库
```

> ⚠️ 高频误用：**REQUIRES_NEW 与自调用**——`this.audit()`（同类内部调用）走的是 this 引用，不经代理，REQUIRES_NEW 不生效（第 5 节坑 ⑤）。正确姿势：注入自身代理 / 拆独立 Bean。

## 3. 隔离级别速查

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---------|:---:|:---:|:---:|------|
| `READ_UNCOMMITTED` | ❌ 可能 | 可能 | 可能 | 几乎不用 |
| `READ_COMMITTED` | ✅ 防 | 可能 | 可能 | **MySQL 默认**（快照读机制下不可重复读部分缓解） |
| `REPEATABLE_READ` | ✅ | ✅ | ⚠️ 部分（InnoDB 间隙锁防幻读） | **MySQL InnoDB 默认** |
| `SERIALIZABLE` | ✅ | ✅ | ✅ | 全表范围锁，性能差，慎用 |

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public void transfer(Account from, Account to, BigDecimal amt) { ... }
```

| 注意 | 说明 |
|------|------|
| 级别是数据库侧实现的 | JPA 只是传话（`SET TRANSACTION ISOLATION LEVEL`），实现差异见 [MySQL 事务与锁机制](../../../../01-关系型数据库/MySQL/03-事务与锁机制.md) |
| **别依赖默认** | 各数据库默认不同（MySQL RR、PG/标准 RC），跨库项目必须显式声明 |
| 升级成本 | 隔离级别越高并发越差——"查一致"优先用读快照/读锁替代全局升级 |

> 🎯 面试必答：**"隔离级别从哪一层生效？"**——`Isolation` 枚举只是 Spring 把它翻译成 `SET TRANSACTION` 发给数据库；真正防脏读/幻读的是**数据库 MVCC 快照与锁**（InnoDB 的 undo log 版本链 + 间隙锁），框架层没有魔法（详见 [MySQL 03 篇](../../../../01-关系型数据库/MySQL/03-事务与锁机制.md)）。

## 4. 回滚规则与 readOnly

### 4.1 回滚规则

```java
@Transactional(rollbackFor = Exception.class)               // 受检异常也回滚（多数业务用这个）
@Transactional(noRollbackFor = BusinessIgnorableException.class)  // 指定异常不回滚
public void createOrder(OrderDto dto) throws Exception { ... }
```

| 写法 | 效果 | 建议 |
|------|------|------|
| 默认（不写） | 运行时异常回滚，受检异常不回滚 | 规范是"业务异常也回滚"→ 显式 rollbackFor |
| `rollbackFor = Exception.class` | 所有异常回滚 | **推荐**（省得每次想） |
| `rollbackFor = BizException.class` | 指定业务异常回滚 | 团队规范可选用 |
| `noRollbackFor` | 白名单豁免 | 如"已存在则忽略"的幂等场景 |

### 4.2 readOnly

```java
@Transactional(readOnly = true)      // 只读事务
public List<Product> search(...) { ... }
```

| 效果 | 说明 |
|------|------|
| 数据库侧 | 部分库（如 MySQL 无感知；PG 可减少锁）——**不是强制只读** |
| ORM 侧 | Hibernate 跳过脏检查（性能微优化）；写操作不会被拦 |
| 规范意义 | **代码自文档**：标注"此方法是读操作"；团队约定写方法不允许挂 readOnly |

> ⚠️ 常见误区：readOnly 能"防止误写"？——**不能**（不是只读约束）；要硬约束在数据库权限/触发器层做。readOnly 事务中调用写 Repository 方法仍然会写。

## 5. 事务失效八大坑（面试必考）

| # | 坑 | 场景 | 解法 |
|---|----|------|------|
| ① | **自调用** | 同类方法 A 调 B（`this.methodB()`），B 的 @Transactional 不生效 | 拆独立 Service / 注入自身代理（`@Lazy` 注入自己）/ TransactionTemplate |
| ② | **方法非 public** | protected/private 方法上的 @Transactional 不生效（JDK 代理限制） | 改 public |
| ③ | **类未被 Spring 管理** | new 出来的对象 / 非 Bean 类 | 交给 Spring 管理（@Service） |
| ④ | **异常被吞** | try-catch 住异常不抛出 → 不触发回滚 | 不吞异常；或 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`（慎用） |
| ⑤ | 异常类型不匹配 | 受检异常没配 rollbackFor | `rollbackFor = Exception.class` |
| ⑥ | 多线程 | `@Async`/新线程里的事务与主线程**各自独立**（线程不共享事务） | 新线程单独开事务；分布式场景换方案（[分布式事务](../../../../03-消息队列/消息队列理论与实战/07-分布式事务与消息队列.md)） |
| ⑦ | 多数据源没用对管理器 | 事务绑定了 A 库，操作了 B 库 | 显式 `@Transactional("secondaryTx")`（[02 篇](02-快速开始与连接配置速查.md) 多数据源） |
| ⑧ | 代理未生效（final/私有类） | final 类无法被 CGLIB 子类代理（Boot 默认 CGLIB） | 类与方法不要 final |

```java
// 坑 ① 自调用解法：注入自身代理
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository repo;
    private final OrderAuditService auditService;   // 拆成独立 Bean

    @Transactional
    public void create(OrderDto dto) {
        repo.save(dto.toEntity());
        auditService.log("create");                  // 独立 Bean → 代理生效，REQUIRES_NEW 正常
    }
}
```

> 🎯 **事务失效 = 代理失效**：所有失效场景都能归因到"方法没经过 Spring 代理"或"异常没传回代理"。排查铁律：先确认调用入口是 Bean 外部调用，再看异常是否上抛。

## 6. 乐观锁 @Version

```java
@Entity
public class Product {
    @Id private Long id;

    @Version private Long version;        // 版本列（int/short/long/时间戳均可）
    private BigDecimal price;
}

// 使用（业务层）：更新冲突处理
@Transactional
public void updatePrice(Long id, BigDecimal newPrice, int retry) {
    try {
        Product p = productRepository.findById(id).orElseThrow();
        p.setPrice(newPrice);            // flush 时执行：
                                         // UPDATE ... SET price=?, version=version+1
                                         // WHERE id=? AND version=旧版本
    } catch (ObjectOptimisticLockingFailureException e) {   // 或 OptimisticLockException
        if (retry > 0) {
            Thread.sleep(50);            // 简单退避后重试（读-改-写）
            updatePrice(id, newPrice, retry - 1);
        } else {
            throw new ConcurrentModificationException("商品价格已被他人修改，请刷新后重试");
        }
    }
}
```

| 要点 | 说明 |
|------|------|
| SQL 语义 | `UPDATE ... WHERE id=? AND version=?`——影响行数 0 即冲突 |
| 冲突时机 | **flush 时**（不是方法返回时）：commit 前统一校验，所以"方法没抛异常"≠"没冲突" |
| 异常 | Spring 包装 `ObjectOptimisticLockingFailureException`（根因 `OptimisticLockException`） |
| 重试 | 读-改-写循环可重试（有限次数 + 退避）；**条件更新**（`@Query("update ... where id=:id and price=:expect")`）更优雅 |
| 批量更新 | 批量 SQL 不走版本校验（版本列由手动 WHERE 条件替代） |

> 🎯 面试必答：**"乐观锁 vs 悲观锁怎么选？"**——读多写少、冲突概率低 → 乐观锁（无锁开销，靠版本重试）；写多冲突高、金额/库存等强一致 → 悲观锁（直接锁行，免重试风暴）。互联网"库存超卖"经典题两种都答得上才算过。

## 7. 悲观锁 @Lock

### 7.1 锁模式速查

| LockModeType | SQL 语义 | 场景 |
|--------------|---------|------|
| `PESSIMISTIC_WRITE` | `SELECT ... FOR UPDATE`（排他锁） | **改写同行的并发控制（主力）** |
| `PESSIMISTIC_READ` | `SELECT ... FOR SHARE`（共享锁） | 读防并发改（MySQL 8 的 FOR SHARE） |
| `PESSIMISTIC_FORCE_INCREMENT` | `FOR UPDATE` + 版本自增 | 锁 + 强制版本变化 |
| `OPTIMISTIC` / `OPTIMISTIC_FORCE_INCREMENT` | 无 SQL 锁（版本校验） | 编程式乐观锁 |

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select p from Product p where p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select p from Product p where p.sku = :sku")     // 非主键条件锁行
    Optional<Product> findBySkuForUpdate(@Param("sku") String sku);
}

// 使用：必须处于事务中
@Transactional
public void deductStock(Long productId, int qty) {
    Product p = productRepository.findByIdForUpdate(productId).orElseThrow();
    if (p.getStock() < qty) throw new StockInsufficientException();
    p.setStock(p.getStock() - qty);          // 锁释放 = 事务提交
}
```

> ⚠️ **悲观锁必须配事务**：锁在事务提交/回滚时才释放——`@Lock` 方法脱离 @Transactional 调用，锁秒开秒关，等于没锁（还多一次加锁开销）。锁住的也不仅是该方法，而是整个事务持有的所有行。

### 7.2 Hibernate 7 变化与 7.4 改进

| 版本 | 变化 |
|------|------|
| 7.0 | `Session.get(clazz, id, LockMode.PESSIMISTIC_WRITE)` **废弃** → `session.byId(clazz).with(LockOptions.PESSIMISTIC_WRITE).load(id)` |
| 7.2 | 悲观锁（Pessimistic Locking）专项改进（内部锁选项扩展，为 7.4 打底） |
| 7.4 | 锁相关增强合入（与 `@EmbeddedTable`、QuerySpecification 并列的 7.2-7.4 特性线） |

```java
// Hibernate 7 推荐的编程式加锁（Session 直取）
@Transactional
public void lockAndUpdate(Long id) {
    Product p = entityManager.unwrap(Session.class)
            .byId(Product.class)
            .with(LockOptions.PESSIMISTIC_WRITE)      // 替代已废弃的 Session.get(..., LockMode)
            .load(id);
    p.setPrice(newPrice);
}
```

## 8. 锁选型与并发设计

### 8.1 场景决策表

| 场景 | 方案 | 理由 |
|------|------|------|
| 商品库存扣减（高并发） | **悲观锁（FOR UPDATE）或条件 UPDATE**（`update stock = stock-? where stock>=?`） | 冲突率高；条件更新免读改循环最稳 |
| 用户资料编辑（低冲突） | 乐观锁 @Version | 无锁开销，冲突重试 |
| 订单状态流转（状态机） | 悲观锁 + 状态校验 | 防并发状态回跳 |
| 金额对账/累计 | 条件 UPDATE（CAS 式） | `update balance=balance+? where id=?` 原子自增 |
| 跨服务并发（分布式） | Redis 分布式锁 / Seata | 单库锁管不了多节点（见 [消息队列分布式事务](../../../../03-消息队列/消息队列理论与实战/07-分布式事务与消息队列.md)） |

### 8.2 大事务红线

| 红线 | 危害 | 解法 |
|------|------|------|
| 事务内调远程接口（HTTP/RPC） | 持锁等待网络，锁风暴/死锁风险 | **远程调用移出事务**（先落库改状态，再异步补发） |
| 事务内循环大量写 | 一级缓存膨胀 + 长持锁 | 分批 flush/clear；批量用 [07 篇](07-性能优化与批量操作速查.md) 批处理 |
| 事务跨多个业务动作 | 锁面扩大，死锁概率↑ | 事务只包"数据一致性最小集" |
| 读操作也开长事务 | 快照/undo 膨胀 | 读方法标 readOnly；纯读不走事务 |
| 事务内 await 异步任务 | 事务时间不可控 | 结果回填改事务提交后的事件（[08 篇](08-审计事件与多租户速查.md) 事件） |

> 🎯 并发设计口诀：**"事务越小越好、锁越短越好、远程调用不进事务、幂等靠唯一约束"**——JPA 侧你把锁和事务管对，剩下交给数据库（InnoDB 行锁/间隙锁细节见 [MySQL 03 篇](../../../../01-关系型数据库/MySQL/03-事务与锁机制.md)）。
