## 1. 与全家桶的集成地图

| 组件 | 联动点 | 要点 |
|------|--------|------|
| Spring MVC | 实体 → JSON 序列化 | ① 懒加载关联序列化会炸（[第 3 节](#3-lazyinitializationexception-全解)）；② **别直接返回实体**，返回 DTO/VO（实体结构泄露 + 序列化陷阱） |
| Spring Security | 审计取当前用户 | `AuditorAware` 里取 SecurityContext（[08 篇](08-审计事件与多租户速查.md) 1.1） |
| 数据库迁移 | Flyway / Liquibase | **生产 ddl-auto=none**，表结构由迁移脚本管理（[02 篇](02-快速开始与连接配置速查.md)） |
| Redis 缓存 | 读热数据 | Cache-Aside：`@Cacheable` 缓存 DTO，失效策略自理（[Spring Data Redis 系列](../../../Spring Data Redis/00-Spring Data Redis知识体系总览.md)） |
| Spring Data Elasticsearch | 搜索索引同步 | AfterSaveEvent → 同步/异步写 ES（[08 篇](08-审计事件与多租户速查.md) 第 3 节 + [ES 系列](../../Spring Data 系列【数据访问层】/Spring Data Elasticsearch/00-Spring Data Elasticsearch组件总览.md)） |
| 测试 | @DataJpaTest / H2 | 切片测试不启全应用（[第 7 节](#7-测试实践)） |
| 分布式事务 | Seata / 本地消息表 | @Transactional 只管单库（[06 篇](06-事务与并发控制速查.md) + [消息队列分布式事务](../../../../03-消息队列/消息队列理论与实战/07-分布式事务与消息队列.md)） |
| 监控 | Actuator + 慢查询日志 | `LOG_QUERIES_SLOWER_THAN_MS` + 连接池指标 |

> 🎯 集成总原则：**实体只在数据访问层流通，Service 转 DTO，Controller 只碰 DTO**——"实体不出 Service"能同时规避序列化、懒加载、接口泄露三大坑，是 JPA 项目最重要的工程约定。

## 2. open-in-view：生产必关的开关

```yaml
spring:
  jpa:
    open-in-view: false        # ★ 生产必设；Boot 默认 true
```

| 状态 | 行为 | 危害 |
|------|------|------|
| true（默认） | 每个请求从开始到返回都持有 EntityManager（OSIV：Open Session In View） | ① 连接被长占（空闲页面挂着连接）；② 事务边界形同虚设（视图层可触发懒加载 → 慢 SQL 藏到渲染阶段） |
| **false（生产推荐）** | 事务结束后关闭 EntityManager | 强制你在 Service/事务内把该加载的都加载好（配合 DTO 设计） |

> ⚠️ 关掉后的连锁反应：视图层访问懒加载属性 → `LazyInitializationException`（第 3 节）——这是"正确的痛"：逼你把数据准备放在事务内，而不是靠长连接掩盖。

## 3. LazyInitializationException 全解

### 3.1 症状与本质

```text
org.hibernate.LazyInitializationException: could not initialize proxy
  - no Session
```

**本质**：事务（Session）已关闭，你访问了未加载的懒加载属性——Session 都没了，Hibernate 无法再去查库。

### 3.2 四大解法

| 解法 | 做法 | 适用 |
|------|------|------|
| **① 事务内准备数据（正解）** | Service 内 @Transactional + fetch join/@EntityGraph 预加载（[07 篇](07-性能优化与批量操作速查.md) 第 3 节） | 列表/详情页 |
| ② 事务内访问 | 需要展示的数据在事务内完整读取后再返回 | 单条详情 |
| ③ DTO 组装在事务内 | Service 返回 DTO（实体不出层） | **推荐工程姿势**（第 1 节原则） |
| ④ ~~enable_lazy_load_no_trans~~ | Hibernate 7 **已移除**，别用 | 过去式 |

```java
// 正解示例
@Transactional(readOnly = true)
public OrderDetailDto getOrderDetail(Long id) {
    OrderEntity order = orderRepository.findWithItemsById(id);   // fetch join 预加载
    return OrderDetailDto.from(order);                           // 事务内完成所有访问
}
```

> 🎯 面试必答：**"怎么解决 LazyInitializationException？"**——① 框架层：事务内预加载（fetch join/@EntityGraph）；② 架构层：DTO 模式（实体不出 Service）；③ 兜底：批量抓取 @BatchSize；同时交代"osiv 是掩盖问题，不是解决问题"。**答案里出现 enable_lazy_load_no_trans 直接减分**（Hibernate 7 已删）。

## 4. save() 的语义陷阱

| 场景 | save() 实际行为 | 坑 |
|------|----------------|----|
| id 为 null（新实体） | `persist` → INSERT | ✅ 正常 |
| id 非 null 且**不在当前上下文** | 先 SELECT 检查存在，再 `merge`（存在→UPDATE，不存在→INSERT） | **多一次 SELECT**；循环 save 分离对象 = N+1 查询 |
| id 非 null 且在上下文中 | 脏检查统一 flush（无需 save） | 调 save 是多余的 |

```java
// 反模式：逐条 merge 分离对象（列表导入常见 N+1 来源）
for (ProductDto dto : dtos) {
    Product p = new Product();                    // 分离态（新对象但带 id？）
    p.setId(dto.getId());                          // 带 id → merge 先 select
    productRepository.save(p);
}

// 正解：批量导入用 upsert 风格
productRepository.saveAll(products);               // 仍是逐条判断，但省一层循环开销
// 或大表用 @Modifying 原生 upsert（INSERT ... ON DUPLICATE KEY UPDATE）
```

> 💡 记忆点：**save 的语义是"persist 或 merge"**——新实体 persist（纯 INSERT），分离实体 merge（先查后并）；同事务同 id 的实体其实是脏检查 flush，save 只是"唤醒"。批量场景优先 `saveAll` + 批处理参数（[07 篇](07-性能优化与批量操作速查.md) 第 4 节）。

## 5. 3.x → 4.x 迁移清单

> Boot 3.5（SDJ 3.5 + Hibernate 6.6）→ Boot 4.1（SDJ 4.1 + Hibernate 7.4）。**前置条件：Java 21**。逐项核对，改完全量回归。

### 5.1 必改项（不改编译失败/运行报错）

| # | 项目 | 3.x | 4.x | 说明 |
|---|------|-----|-----|------|
| ① | 注解处理器坐标 | `hibernate-jpamodelgen` | `hibernate-processor` | 不改 → 元模型类静默缺失（编译期看起来正常，运行期 `Product_` 找不到） |
| ② | 异步返回类型 | `ListenableFuture` | `CompletableFuture` | Spring Framework 7 移除前者，编译错误 |
| ③ | 持久化构造器注解 | `@PersistenceConstructor` | `@PersistenceCreator` | 多构造器实体改名 |
| ④ | dialect 显式配置 | `database-platform` / `hibernate.dialect` | **删除**（自动检测） | 旧类名（`*8Dialect`）在 7.x 已删除，不删直接启动失败 |
| ⑤ | 命名策略包路径 | `org.springframework.boot.orm.jpa.hibernate.SpringImplicitNamingStrategy` | `org.springframework.boot.hibernate.SpringImplicitNamingStrategy` | 自定义了该策略才受影响 |
| ⑥ | 原生查询增强属性 | `spring.data.jpa.query.native.parser` | 移除 → `QueryEnhancerSelector` | 用到了才迁移 |

### 5.2 行为变化（编译通过但行为不同，重点回归）

| # | 项目 | 变化 | 回归要点 |
|---|------|------|---------|
| ⑦ | 派生查询生成 | CriteriaQuery → **JPQL 生成 + 构建期验证** | ① 拼错属性名/方法名现在编译期报错；② SQL 文本不同——show-sql 断言类测试要重写；③ 复杂派生方法（多 join 隐式路径）逐条验证结果 |
| ⑧ | 懒加载逃逸 | `enable_lazy_load_no_trans` 移除 | 依赖它的代码运行期炸 LazyInitializationException，逐处改事务边界 |
| ⑨ | @JoinColumn nullable | 默认行为调整 | 外键可空性变化可能导致插入失败，审查 DDL 差异 |
| ⑩ | 空值注解 | JetBrains → JSpecify | Kotlin/静态检查工具可能报新警告 |
| ⑪ | Session.get(锁定) | — | 废弃 → `byId().with(LockOptions)`（[06 篇](06-事务与并发控制速查.md) 7.2） |

### 5.3 迁移动作清单

| 动作 | 说明 |
|------|------|
| 全量测试套件跑通 | 非协商项——派生查询/懒加载变化只能靠测试暴露 |
| `show-sql` 比对热点查询 | 找出 SQL 字面变化，EXPLAIN 复核执行计划 |
| 升级收益验收 | 7.4 分页下沉 SQL（[07 篇](07-性能优化与批量操作速查.md) 第 6 节）在有"集合 fetch join + 分页"的接口上直接见效 |
| 清理废弃配置 | `spring.jpa.hibernate.ddl-auto` 语义不变；删除所有已移除属性 |
| 灰度验证 | 先 4.0（Hibernate 7.2）再 4.1（7.4），分两步降低风险 |

> 🎯 迁移心法：**清单里 ①-⑥ 是"编译期硬约束"（机器帮你找），⑦-⑪ 是"行为软变化"（测试帮你找）**——先解编译错误，再跑全量测试，最后用 show-sql 复核热点查询；不要为了赶进度跳过 ⑦ 的回归，它是 4.x 最大行为差异。

## 6. 高频坑排错表

| 症状 | 根因 | 解法 |
|------|------|------|
| `LazyInitializationException: no Session` | 事务外访问懒加载 | 预加载/DTO（第 3 节）；别关 open-in-view 之前先查事务边界 |
| `EntityNotFoundException`（级联删除时报） | 删父级联到不存在的子（孤儿） | orphanRemoval 处理集合（[03 篇](03-实体映射与关联映射速查.md) 4.2） |
| `Detached entity passed to persist` | save 了带 id 的分离对象 | 用 merge 语义（save 会处理）；确认 id 生成策略与对象状态 |
| `OptimisticLockException` 频繁 | 乐观锁冲突率超预期 | 重试/退避；冲突高改悲观锁（[06 篇](06-事务与并发控制速查.md) 第 8 节） |
| `Deadlock found` | 多事务锁顺序不一致 | 统一加锁顺序（按 id 排序加锁）；缩小事务 |
| `MultipleBagFetchException` | 一个查询 fetch 两个集合 | 分次查 / @BatchSize（[07 篇](07-性能优化与批量操作速查.md) 3.1） |
| 中文乱码 | 连接串没 characterEncoding | url 加 `characterEncoding=utf8`（[02 篇](02-快速开始与连接配置速查.md)） |
| 启动报 `Could not determine recommended JdbcType` | 类型映射缺失（自定义类型没注册） | @JdbcTypeCode 指定（[03 篇](03-实体映射与关联映射速查.md) 2.2） |
| `Schema-validation: missing table` | validate 模式与迁移脚本不一致 | 跑 Flyway migrate；对齐实体与表 |
| 更新了不生效 | ① 一级缓存旧值；② @Modifying 没 clearAutomatically | ② 用 `clearAutomatically=true`（[04 篇](04-Repository速查.md) 第 4 节） |
| 查询走了全表扫描 | 缺索引/函数包裹索引列 | EXPLAIN + 联合索引（[MySQL 索引原理](../../../../01-关系型数据库/MySQL/04-索引原理与设计.md)） |
| `Page` 的 total 不对（join 后） | 集合 join 行膨胀 | distinct / 独立 count（[05 篇](05-复杂查询与Specification速查.md) 第 7 节） |
| Repository 方法名报了"构建期失败" | 4.0 派生查询验证（拼错属性） | 按报错修正属性路径（[04 篇](04-Repository速查.md) 第 7 节） |

## 7. 测试实践

### 7.1 @DataJpaTest 切片测试

```java
@SpringBootTest                                   // 场景 B：全上下文（含事务切面真实生效）
public class OrderServiceIT { ... }

@DataJpaTest                                      // 场景 A：只起 JPA 切片（Repository 层）
@AutoConfigureTestDatabase(replace = Replace.NONE) // 用真实 MySQL；默认替换为 H2
class ProductRepositoryTest {

    @Autowired ProductRepository productRepository;

    @Test
    void findByPriceBetween_shouldFilter() {
        productRepository.saveAll(List.of(p(100), p(5000), p(9000)));
        Page<Product> page = productRepository.findByPriceBetween(
                BigDecimal.ZERO, BigDecimal.valueOf(5000), PageRequest.of(0, 10));
        assertThat(page.getTotalElements()).isEqualTo(2);
    }
}
```

| 测试姿势 | 用途 | 要点 |
|---------|------|------|
| `@DataJpaTest` | Repository 派生方法/@Query 行为 | 默认 H2 + 每测试回滚；需要真库用 `Replace.NONE` |
| `@SpringBootTest` | 事务/Service 集成 | 含真实代理与事务切面（[06 篇](06-事务与并发控制速查.md) 失效场景测试） |
| 内嵌库 vs 真库 | 方言差异 | **关键 SQL 特性（JSON/窗口/间隙锁语义）必须在真库回归** |
| 测试数据 | 用测试基建（dbunit/脚本） | 别在测试里依赖生产数据 |

> ⚠️ 测试三坑：① **只测 H2 不测真库**——JSON 列、`FOR UPDATE`、分页方言差异在 H2 上行为不同（[03 篇](03-实体映射与关联映射速查.md) 2.2 的 JSON 映射就是典型）；② 派生查询 4.0 构建期已验证语法，但**语义（结果集）仍靠测试**；③ 断言顺序别断言 SQL 文本（第 5.2 节 ⑦）。
