## 1. 索引类型全览

| 索引类型 | 注解/API | 适用 | 说明 |
|---------|---------|------|------|
| 单字段 | `@Indexed` | 单条件查询 | 最基础 |
| 复合 | `@CompoundIndex` | 多条件/排序组合 | **查询优化的主力** |
| 唯一 | `@Indexed(unique = true)` | 业务唯一键（幂等） | 与 @Id 分开 |
| TTL | `@Indexed(expireAfterSeconds = N)` | 过期数据自动删除（会话/验证码） | **替代定时清理任务** |
| 文本 | `@TextIndexed` | 全文搜索（[05 篇](05-查询构造与模板速查.md) 6.1） | 中文分词弱 |
| 地理 | `@GeoSpatialIndexed` | 附近查询（[05 篇](05-查询构造与模板速查.md) 6.2） | 2dsphere |
| 哈希 | `@HashIndexed` | 分片键哈希 | 均匀分布 |
| 部分 | `@PartialIndexFilter` | 只索引满足条件的文档 | 减少索引体积 |
| 通配 | `@WildcardIndexed` | 动态字段全可查 | 8.x 能力 |
| 向量 | SearchIndexOperations + VectorIndex | 语义检索（[08 篇](08-向量检索与AI集成速查.md)） | **注意：不是普通索引，是 Search/Vector 索引** |

```java
@Document(collection = "user_session")
public class UserSession {
    @Id private String id;
    @Indexed(expireAfterSeconds = 86400) private LocalDateTime lastAccess;  // 24h 过期自动删
    @Indexed(unique = true) private String sessionToken;
}

@Document(collection = "product")
@CompoundIndex(def = "{'category': 1, 'price': -1}", name = "idx_cat_price")
public class Product { ... }
```

> ⚠️ **TTL 索引的正确认知**：MongoDB 每 60 秒扫一次 TTL 索引删过期文档——删除**有延迟**（最长 1 分钟），且 TTL 只删"主索引扫描到的文档"；依赖"删除后立即不存在"的业务（如验证码防重）要容忍窗口（[09 篇](09-集成地图与常见问题.md) 有坑）。

## 2. 索引设计原则（面试必考）

### 2.1 复合索引的黄金规则

```text
查询：find({category: '手机', price: {$gte: 1000}}).sort({price: -1})
最佳索引：{category: 1, price: -1}
规则：
  ① 等值字段放前面（category =）
  ② 范围/排序字段放后面（price 区间/排序）
  ③ 排序方向与索引方向一致（-1 对 -1）
```

| 原则 | 说明 |
|------|------|
| **ESR 规则** | Equal（等值）→ Sort（排序）→ Range（范围），字段顺序按此排 |
| 最左前缀 | 复合索引 {a, b, c} 可服务 {a}、{a,b}、{a,b,c} 查询 |
| 索引覆盖 | 查询只取索引内字段 → 不读文档（性能之王，配合投影） |
| 一查询一索引 | 每个查询模式配一个复合索引，别贪多（索引也占存储、拖写入） |
| 基数 | 高基数字段（唯一值多）优先做前缀 |

### 2.2 面试必答：ESR 规则举例

```java
// 查询模式：按类别等值 + 价格区间 + 按时间排序
// 查询：{"category": ?0, "price": {$gte: ?1, $lte: ?2}} sort createdAt desc
// 索引：@CompoundIndex(def = "{'category': 1, 'createdAt': -1, 'price': 1}",
//                     name = "idx_cat_time_price")
//       等值(category) → 排序(createdAt) → 范围(price)
```

> 🎯 面试必答：**"怎么给 MongoDB 设计索引？"**——答三层：① 先列出 Top 查询（QPS 最高/最慢的），用 ESR 规则（等值→排序→范围）排字段；② 用 explain 验证（IXSCAN + covered）；③ 控制索引数量（每集合 3-5 个复合索引够用，索引是写成本）。**加分句**：索引设计的前提是"按查询建模"的数据模型（第 4 节）。

### 2.3 索引管理 API

```java
// 查看/删除（IndexOperations）
IndexOperations ops = mongoTemplate.indexOps(Product.class);
List<IndexInfo> infos = ops.getIndexInfo();        // 查看现有索引
ops.dropIndex("idx_cat_price");                    // 删索引

// 自动创建：开发期 auto-index-creation: true；生产用脚本管理（02 篇）
```

## 3. explain 与慢查询诊断

### 3.1 explain（模板）

```java
// 查看查询执行计划
Query query = Query.query(Criteria.where("category").is("手机").and("price").gte(1000));
Document explain = mongoTemplate.explain(query, Product.class).getExecutionResults();
// → 看 winningPlan：IXSCAN（走索引）还是 COLLSCAN（全扫）
```

| explain 关键字段 | 含义 | 好/坏 |
|-----------------|------|-------|
| `winningPlan.stage` | IXSCAN（索引扫描）/ COLLSCAN（全集合扫描） | ✅ IXSCAN |
| `winningPlan.inputStage` | 覆盖查询显示 `FETCH` 缺失 = covered | ✅ 无 FETCH（覆盖） |
| `totalKeysExamined` | 扫描索引项数 | 越接近返回数越好 |
| `docsExamined` | 扫描文档数 | 远大于返回数 = 没走好索引 |
| `executionTimeMillis` | 执行耗时 | 与索引命中直接相关 |

### 3.2 慢查询日志

```json
// 配置（mongod 启动参数或运行时 setParameter）
db.adminCommand({setParameter: 1, slowms: 100})        // 100ms 以上记录
db.adminCommand({setParameter: 1, profile: 1})         // 开 profile（0=关 1=慢 2=全）
db.system.profile.find().sort({ts: -1}).limit(10)      // 查慢查询
```

> 💡 排查铁律（与 JPA/SQL 同思路）：**show 出真实查询 → explain 看走没走索引 → 修索引或修模型**。慢查询三因：没索引（补索引）、索引选错（调复合索引顺序）、模型设计差（内嵌/引用选择错，第 4 节）。

## 4. 文档建模：内嵌 vs 引用（面试必考）

### 4.1 完整决策表

| 判断维度 | 内嵌（Embed） | 引用（Reference/@DBRef） |
|---------|--------------|--------------------------|
| 读取模式 | **总是和父文档一起读** | 独立读取 |
| 生命周期 | **从属于父文档**（父删子亡） | 独立存活 |
| 数据量 | 子项少而稳定（< 数百条） | 子项海量/无限增长 |
| 更新频率 | 一起更新/不常变 | 独立高频更新 |
| 一致性要求 | 单文档原子（同读同写） | 各自更新（无事务关联） |
| 典型 | 订单明细、地址、标签、评论快照 | 用户↔角色、商品↔分类 |

### 4.2 三类建模误区（面试常考）

| 误区 | 症状 | 正解 |
|------|------|------|
| 全部内嵌 | 文档膨胀超 16MB / 子项更新要 $ 运算符 | 无限增长的子项拆集合引用 |
| 全部 @DBRef | N+1 查询、无级联、事务失效 | 90% 的场景内嵌足够 |
| 照搬 SQL 三范式 | 到处引用、处处 $lookup | **按查询建模**（冗余换取一次查询） |

> 🎯 面试必答：**"MongoDB 数据模型怎么设计？"**——四步：① **按查询建模**（先列出所有查询，模型为查询服务）；② 内嵌优先（同读同灭的数据内嵌）；③ 引用兜底（独立生命周期/海量子项）；④ 冗余权衡（跨集合频繁"一起读"的数据，宁可冗余一份，换一次查询）——最后对比：**关系库先定表再写查询，Mongo 先写查询再定文档**。

## 5. 设计模式速查

| 模式 | 场景 | 做法 |
|------|------|------|
| **文档版本化** | 每次修改留痕 | 内嵌历史数组 / 独立历史集合（可配 [JPA 审计思路](../../Spring%20Data%20系列【数据访问层】/Spring%20Data%20JPA/08-审计事件与多租户速查.md) 同款 @Version） |
| **预聚合计数** | 高频读计数（点赞/销量） | 写时维护计数字段（$inc），读时一次取 |
| **可扩展引用** | 双向引用（作者↔文章） | 只在一侧存引用数组 + 定期补偿 |
| **模式版本** | 结构演进 | 文档存 `schemaVersion` 字段，读时迁移 |
| **事务批量** | 批量导入 | bulkWrite + 分批（[06 篇](06-批量操作与写关注速查.md) 1 节） |
| **热数据分离** | 冷热数据混存 | 分集合/分片（按时间），TTL 自动归档 |

> 💡 模式与 [MongoDB 官方模式设计（Building with Patterns）](https://www.mongodb.com/docs/manual/data-modeling/design-patterns/) 对齐——生产模型设计时对照一遍，能避掉大部分后期改造。

## 6. 分片集群与查询优化

### 6.1 分片基础

| 要素 | 说明 |
|------|------|
| 分片键 | 决定数据分布（选择标准：**高频查询必带分片键**） |
| 分片方式 | 范围分片（区间）/ 哈希分片（均匀） |
| 集群组件 | mongos（路由）+ config server + shard 节点 |
| 与 SDM 关系 | **对应用透明**：连接 mongos 即可，代码零改动（连接串指向 mongos） |

### 6.2 分片键选择（与 SQL 分库分表同思路）

| 场景 | 推荐分片键 | 原因 |
|------|-----------|------|
| 订单/用户数据 | user_id（哈希） | 单用户查询命中单片 |
| 日志/事件 | 时间范围 | 天然归档、范围查询 |
| IoT 设备数据 | device_id + 时间复合 | 设备级查询单点 |
| 大集合 + 无高频查询键 | 可加冗余路由字段 | 否则查询全片广播 |

> ⚠️ **分片前的判断**（与 [SQL 分片](../../../../01-关系型数据库/SQL调优/) 同哲学）：**分片是最后手段**——先索引、再读写分离、再归档，单副本集撑到数据量/QPS 上限才分片；分片键**一旦选定不可变更**（需全量重分片），设计成本最高（深度见 [MongoDB-04 副本集与分片集群](../../../../02-非关系型数据库/MongoDB/04-MongoDB副本集与分片集群.md)）。

### 6.3 查询优化清单（分片后）

| 问题 | 解法 |
|------|------|
| 查询不带分片键 | 全片广播（慢）→ 查询强制带分片键 / 建二级索引 |
| 分片键基数低 | 热点倾斜 → 复合分片键（键 + 时间/ID） |
| 聚合跨片 | $group 分片内预聚合 → 合并（merge） |
| 排序跨片 | 分片键前缀排序才高效 → 调整查询模式 |

## 7. 性能排查清单

| # | 动作 | 说明 |
|---|------|------|
| ① | 打开慢查询日志 | `slowms=100` + profile，定位 Top 慢查询 |
| ② | explain 逐条分析 | IXSCAN vs COLLSCAN；docsExamined 远大于返回数 = 索引问题 |
| ③ | 检查复合索引顺序 | 是否满足 ESR（等值→排序→范围） |
| ④ | 检查查询是否带分片键 | 分片集群全片广播是大忌 |
| ⑤ | 检查文档大小 | > 1MB 的文档读写成本高（<16MB 只是硬上限，1MB 才是建议软限） |
| ⑥ | 检查 $lookup | 被连接集合有索引吗？能内嵌/冗余避免吗？ |
| ⑦ | 检查大结果集 | 无分页全量拉取 → 分页/游标/投影 |
| ⑧ | 检查索引数量 | 单集合索引 > 8 个 → 精简（每个索引都是写成本） |
| ⑨ | 检查连接池 | maxPoolSize 与并发是否匹配（[02 篇](02-快速开始与连接配置速查.md)） |
| ⑩ | 检查写关注 | 非关键集合误配 majority/journal 拖慢写入（[06 篇](06-批量操作与写关注速查.md)） |

> 🎯 性能口诀：**"索引对了，MongoDB 就快了；模型对了，索引才有意义"**——先模型（内嵌/引用）、再索引（ESR）、后优化（explain/慢日志），顺序不能反。
