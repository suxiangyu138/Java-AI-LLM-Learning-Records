## 1. 批量操作：bulkWrite 与 BulkOperations

**通俗**：一次请求发一批操作到数据库，少跑 N 次网络往返——吞吐翻倍的常用手段。

### 1.1 4.1 新版：MongoOperations.bulkWrite()

```java
// 4.1 新 API：多集合 + 混合操作一条调用
BulkWriteResult result = mongoTemplate.bulkWrite(List.of(
        new BulkWrite.Insert<>(collection1, doc1),        // 插入
        new BulkWrite.Insert<>(collection2, doc2),
        new BulkWrite.Update<>(collection2, query1, update1, UpdateOptions.upsert()),  // 更新
        new BulkWrite.Replace<>(collection1, query2, doc3),
        new BulkWrite.Delete<>(collection3, query3)       // 删除
));
int inserted = result.getInsertedCount();
```

| 能力 | 3.x（BulkOperations） | 4.1（bulkWrite） |
|------|----------------------|------------------|
| 多集合 | ❌ 单集合 | ✅ **多集合混合** |
| 操作混合 | insert/update/delete 可混（单集合） | ✅ 全类型混合 |
| 有序/无序 | 可配 | 可配（默认无序，性能更好） |
| 返回统计 | BulkWriteResult | ✅ 分类计数 |

### 1.2 经典场景：批量 upsert（幂等导入）

```java
// 批量导入：按业务键 upsert，重复跳过
public void batchImport(List<ProductDto> dtos) {
    BulkOperations bulk = mongoTemplate.bulkOps(BulkOperations.BulkMode.UNORDERED, Product.class);
    for (ProductDto dto : dtos) {
        Query q = Query.query(Criteria.where("sku").is(dto.sku()));    // 业务唯一键
        Update u = new Update()
                .set("name", dto.name())
                .set("price", dto.price())
                .setOnInsert("createdAt", LocalDateTime.now());        // 仅插入时填
        bulk.upsert(q, u);
    }
    bulk.execute();                                  // 一次网络往返
}
```

| 注意 | 说明 |
|------|------|
| 大分批 | 单批 1000~5000 条为佳（报文限制 16MB/批） |
| UNORDERED | 默认无序：一条失败不影响其他（记录错误继续） |
| ORDERED | 有序：遇错即停（事务语义更强但慢） |
| 错误处理 | `BulkWriteException` 里 `getWriteErrors()` 逐条分析 |

> ⚠️ 批量与 `saveAll` 的区别：`saveAll` 逐条执行（N 次网络往返，但能拿到每条结果）；`bulkWrite` 一次往返（更快，但错误粒度是批级）——**导入/同步场景用 bulk，业务交互场景用 saveAll**。

## 2. 写关注（Write Concern）

**通俗**：写操作"确认到什么程度才返回成功"——确认越严格越安全，但越慢。

### 2.1 级别速查

| 级别 | 语义 | 安全性 | 性能 |
|------|------|:---:|:---:|
| `w=0` | 不确认（fire-and-forget） | ❌ 最低 | 最快 |
| `w=1`（默认） | 主节点确认落盘 | ⚠️ 中 | 快 |
| `w=majority` | **多数节点确认**（副本集） | ✅ 高（防主节点故障丢数据） | 慢（要等复制） |
| `w=5` 等数字 | 指定 N 个节点确认 | 按需 | 更慢 |
| `journaled` | 落日志后才确认 | ✅ 最高（防宕机丢数据） | 最慢 |

```java
// 编程式
@Bean
WriteConcernResolver writeConcernResolver() {
    return action -> {
        if (action.getCollectionName().equals("payment_flow")) {
            return WriteConcern.MAJORITY;      // 资金流水：强确认
        }
        return WriteConcern.ACKNOWLEDGED;      // 常规集合：w=1
    };
}

// 实体级
@Document(collection = "payment_flow")
@WriteConcern(w = WriteConcern.MAJORITY.getWValue(), journal = true)
public class PaymentFlow { ... }
```

> 🎯 面试必答：**"w=majority 是什么？为什么资金数据要用？"**——主节点写完即返回（w=1）时，主节点若在复制前宕机，数据就丢了；`w=majority` 等多数副本确认后才返回，主节点故障时数据仍在新主上——**资金/订单等关键写入用 majority（甚至 +journal），日志/埋点用 w=1 甚至 w=0**。取舍核心：**安全 vs 延迟**。

### 2.2 与 SQL 的类比

| 概念 | SQL 对照 | 说明 |
|------|---------|------|
| w=1 | 普通 commit | 主库确认 |
| w=majority | 半同步复制确认 | 等多数从库 |
| journaled | fsync 落盘 | 等日志落盘 |

## 3. 读关注与读偏好

### 3.1 读关注（Read Concern）

| 级别 | 语义 | 场景 |
|------|------|------|
| `local`（默认） | 读主节点内存数据 | 常规读 |
| `majority` | 只读已被多数节点确认的数据 | 读刚写入的强一致数据 |
| `linearizable` | 线性一致读（配合 w=majority 写） | 关键读（余额查询） |

### 3.2 读偏好（Read Preference）

| 偏好 | 读谁 | 场景 |
|------|------|------|
| `primary`（默认） | 主节点 | 强一致读（默认） |
| `primaryPreferred` | 主优先，主不可用读从 | 高可用读 |
| `secondaryPreferred` | 从优先，从不可用读主 | **读写分离**（读多场景） |
| `secondary` / `nearest` | 只读从 / 就近读 | 分析查询/多机房 |

```yaml
spring:
  data:
    mongodb:
      uri: mongodb://host:27017,host2:27017/shop?replicaSet=rs0&readPreference=secondaryPreferred
```

> ⚠️ **读写分离的代价**：从节点有复制延迟（默认异步复制）——刚写完立刻从从节点读可能读不到（旧数据）；"写完马上读"的关键路径要读主（或 w=majority + readConcern=majority 组合）。

## 4. 多文档事务（副本集）

**通俗**：一个事务里改多个文档，要么全成、要么全不成——MongoDB 4.0+ 支持副本集内多文档事务。

### 4.1 开启与使用

```java
// ① 事务管理器（副本集环境自动配置；单节点会警告并禁用）
@Configuration
public class MongoTxConfig {
    @Bean
    MongoTransactionManager transactionManager(MongoDatabaseFactory dbFactory) {
        return new MongoTransactionManager(dbFactory);
    }
}

// ② 声明式事务（与 JPA @Transactional 同 API）
@Service
public class OrderService {
    @Transactional                                  // 进入事务：开启会话 + 启动事务
    public void createOrderWithPayment(OrderEntity order, PaymentEntity payment) {
        orderRepository.save(order);                // 文档 A
        paymentRepository.save(payment);            // 文档 B —— 同一事务，共提交/共回滚
    }
}
```

| 要点 | 说明 |
|------|------|
| 前提 | **副本集**（单节点不支持；开发测试起 `--replSet`） |
| 范围 | **单个副本集内**跨文档/跨集合（不支持跨副本集/跨集群） |
| 隔离 | 快照隔离（snapshot）——事务内读一致快照 |
| 时长 | 事务默认 60s 超时（长事务慎用） |
| 并发 | 写冲突返回 `WriteConflict`（重试语义，见 6.2） |

> 💡 与 JPA 事务的差异：**没有隔离级别枚举**（固定快照隔离）、没有传播行为复杂语义（REQUIRED 语义为主）；事务开销较大（**能用单文档原子就别开事务**——这是 MongoDB 设计哲学，与"事务越多越好"的关系型习惯相反）。

### 4.2 事务内操作模板

```java
// 编程式（模板内自定义会话）
mongoTemplate.executeInTransaction(session -> {
    OrderEntity o = mongoTemplate.findOne(
            Query.query(Criteria.where("id").is(orderId)), OrderEntity.class);
    mongoTemplate.update(OrderEntity.class)
            .matching(Query.query(Criteria.where("id").is(orderId)))
            .apply(new Update().set("status", "PAID"))
            .inSession(session);
    return o;
});
```

> 🎯 面试必答：**"MongoDB 什么时候需要事务？"**——先答"大多数场景不需要"：单文档更新天然原子（$set/$inc）；**需要"跨多个文档/集合的原子性"时才用事务**（订单 + 流水 + 库存三个文档一起变）；再补边界：限副本集内、快照隔离、有超时、写冲突要重试——最后加分句：**"能用文档内嵌 + 单文档原子解决的，绝不引入事务"**。

## 5. 事务与批量/乐观锁的边界

| 场景 | 边界 | 说明 |
|------|------|------|
| 批量 + 事务 | bulkWrite 可放入事务（4.1 bulkWrite 支持会话） | 事务会放大批量开销，批量导入一般不入事务 |
| @Version + 事务 | 版本冲突在事务内 flush 时暴露 | 同 JPA 语义（[03 篇](03-实体映射与文档注解速查.md) 5.1） |
| @Version + 批量 | **批量/原生驱动绕过版本校验** | 批量更新需手动条件（`{'version': ?}`） |
| 事务 + 读主 | 事务内读始终走主节点快照 | 无需担心读偏好 |
| 事务 + 分布式 | 跨副本集/跨服务不受支持 | 走最终一致 + 对账（[消息队列分布式事务](../../../../03-消息队列/消息队列理论与实战/07-分布式事务与消息队列.md)） |

> ⚠️ 与 JPA 事务失效八大坑对照（[JPA 06 篇](../../Spring%20Data%20系列【数据访问层】/Spring%20Data%20JPA/06-事务与并发控制速查.md)）：**自调用失效、异常被吞、异常类型不匹配**这三条在 MongoDB 事务下同样成立——@Transactional 本质都是 AOP 代理，规律通用。

## 6. 一致性权衡速查

### 6.1 权衡全景

```text
写入安全 ←──────────────────────────→ 写入性能
journaled < majority < w=1 < w=0
    └─ 资金/订单关键数据              └─ 日志/埋点/统计

读取一致 ←──────────────────────────→ 读取性能
linearizable < majority < local
    └─ 余额/状态强一致读              └─ 常规查询

事务原子性 ←─────────────────────────→ 吞吐
多文档事务（开销大） < 单文档原子（$inc/$set）
```

### 6.2 写冲突重试模式

```java
// 事务写冲突（WriteConflict）重试：与乐观锁重试同理
private static final int MAX_RETRY = 3;

public void createWithRetry(OrderEntity order, PaymentEntity payment) {
    for (int attempt = 0; attempt < MAX_RETRY; attempt++) {
        try {
            mongoTemplate.executeInTransaction(session -> {
                orderRepository.save(order);
                paymentRepository.save(payment);
                return null;
            });
            return;
        } catch (MongoWriteConflictException e) {
            if (attempt == MAX_RETRY - 1) throw new BizException("系统繁忙，请重试", e);
            Thread.sleep(50L * (attempt + 1));          // 简单退避
        }
    }
}
```

> 🎯 一致性总结三句：① **单文档原子是默认武器**（$inc/$set/upsert），能不用事务就不用；② **跨文档必须原子时用多文档事务**，记住快照隔离 + 写冲突重试；③ **写关注/读关注按数据等级分层**——资金 majority、常规 w=1、日志 w=0，与 [消息队列投递语义](../../../../03-消息队列/消息队列理论与实战/02-消息可靠性：三大投递语义.md) 的"按业务分级配置"是同一套思维。
