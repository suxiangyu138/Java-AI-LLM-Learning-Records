## 2. ObjectId 序列化三方案

**问题**：实体 `@Id String id` 反序列化后是 ObjectId，Jackson 序列化时默认输出 24 位 hex 字符串（可以工作）；但**原生 ObjectId 字段 / $ref 结构 / 数字形态**会炸或格式不对。

| 方案 | 做法 | 适用 |
|------|------|------|
| ① 统一 String（推荐） | 实体字段全用 `String id`（SDM 自动转换） | **90% 场景** |
| ② Jackson 模块 | 引入 `jackson-databind` + Mongo 专用序列化器（Boot 自动注册 `MongoJacksonModule`） | 原生 ObjectId 字段 |
| ③ 自定义序列化器 | 为 ObjectId/DBRef 写 JsonSerializer | 特殊格式需求 |

```java
// 方案 ②：Boot 自动注册 MongoJacksonModule（4.x 默认）
// 效果：ObjectId → "507f1f77bcf86cd799439011"（字符串）
// 方案 ① 的实际做法：id 字段声明为 String，无需任何配置
@Document
public class Product {
    @Id private String id;     // ← 用 String 就完了，JSON 天然是字符串
}
```

> ⚠️ 序列化红线：① **不要序列化整个实体到前端**（DTO 原则）；② 日期字段序列化格式统一（ISO 8601，别混时间戳）；③ 大字段（byte[]/GridFS 元数据）排除出 JSON。

## 3. 时区与日期：UTC 的真相

**通俗**：MongoDB 的 Date 类型**永远存 UTC 毫秒**——Java 读回时按 JVM 默认时区转换，显示"本地时间"；写进去的 LocalDateTime 也先转 UTC。**坑不在存储，在"你以为存的是本地时间"**。

| 场景 | 行为 | 坑 |
|------|------|-----|
| 存 `LocalDateTime.now()` | 转 UTC 落库 | 本意"北京时间 12:00"，库里是 04:00Z |
| 读回 | 按 JVM 时区转回 | JVM 时区不同，同一数据显示不同 |
| 日期区间查询 | `$gte/$lte` 用 Date | 边界要按"UTC 零点"算，不是本地零点 |
| 时区变更 | 服务器切时区 | 全量数据显示错位 |

| 解法 | 说明 |
|------|------|
| 统一约定 | **应用层统一用 UTC 存储与传输**（ISO 8601 + Z），展示层再转本地 |
| 日期字段显式化 | 用 `LocalDateTime` + 明确"这是 UTC"注释；避免裸 `java.util.Date` |
| 查询边界工具 | 区间查询用 `atStartOfDay().toInstant(ZoneOffset.UTC)` 类工具统一构造 |
| 时间戳备选 | 纯时间点（事件、日志）直接用 `Instant`（无时区歧义） |

> 🎯 面试必答：**"MongoDB 日期存进去为什么差 8 小时？"**——Date 类型以 UTC 毫秒存储（1970 纪元），**时区转换发生在客户端**（驱动按 JVM 默认时区）；显示差 8 小时 = 存储是 UTC、读取按东八区转回"本地时间"，实际数据没错——错的是"谁在哪个时区解释它"；解法：统一 UTC 语义 + 展示层转换。

## 4. 16MB 上限与 GridFS

**通俗**：单文档硬上限 16MB——大文件（图片/视频/大 JSON）不能直接塞文档，用 GridFS 分块存储。

```java
// 存文件
GridFsTemplate gridFs = mongoTemplate.getGridFsTemplate();   // 或注入 GridFsTemplate
ObjectId fileId = gridFs.store(inputStream, "photo.jpg", "image/jpeg");

// 读文件
GridFSFile file = gridFs.findOne(new Query(Criteria.where("_id").is(fileId)));
GridFsResource resource = gridFs.getResource(file);
InputStream in = resource.getInputStream();                   // 流式读
```

| 场景 | 存文档内 | GridFS |
|------|:---:|:---:|
| < 1MB 的小文件（头像缩略图） | ✅ | 不必 |
| 1MB ~ 16MB（中等文件） | ⚠️ 看频率 | ✅ 流式友好 |
| > 16MB（视频/大附件） | ❌ 超限 | ✅ 分块（默认 255KB/块） |
| 文件大量且要 CDN | — | 直接对象存储（OSS/S3）更优 |

> ⚠️ 2026 主流做法：**文件优先对象存储（OSS/S3）+ MongoDB 存元数据**（url/etag/大小）——GridFS 适合"不想引第三方、文件量可控"的场景；别把 GridFS 当对象存储的免费替代（无 CDN、无防盗链）。

## 5. 3.x → 4.1 迁移清单

> Boot 3.5（SDM 3.5）→ Boot 4.1（SDM 4.1 + MongoDB 8.x）。**前置条件：Java 21**（与 JPA 4.x 线相同的平台约束）。

### 5.1 必改项

| # | 项目 | 3.x | 4.x | 说明 |
|---|------|-----|-----|------|
| ① | Java/框架基线 | Java 17 + Framework 6.2 | **Java 21 + Framework 7.0** | 非协商项 |
| ② | 空值注解 | JetBrains | JSpecify | 静态检查工具适配 |
| ③ | 驱动版本 | 4.x/5.x 随 BOM | 5.6.x（BOM 锁定） | 跟随 BOM 即可 |
| ④ | 已移除 API | — | 3.x 中废弃项清理 | 编译期错误逐条解 |

### 5.2 行为变化（重点回归）

| # | 项目 | 变化 | 回归要点 |
|---|------|------|---------|
| ⑤ | 派生查询校验 | 坏 JSON 查询运行期才炸 | 4.x 启动期校验 → 升级后启动报错即旧问题，逐条修 |
| ⑥ | 日期/类型默认值 | 转换细节调整 | 重点测：LocalDateTime 参数 JSON 查询、BigDecimal、枚举 |
| ⑦ | null 处理 | 默认跳过 null 字段 | 确认老数据（有 null 字段）读取兼容 |
| ⑧ | 事务管理 | 4.x 需显式 MongoTransactionManager 场景检查 | 确认 Bean 配置与副本集 |
| ⑨ | 索引自动创建 | auto-index-creation 默认值/行为 | 生产配置显式化 |
| ⑩ | 响应式 API | 同族升级 | Reactive 仓库/模板回归 |

### 5.3 升级收益验收

| 新能力 | 出处 | 验收方式 |
|--------|------|---------|
| 类型安全属性路径 | [01 篇](01-模块清单.md) 4.1 | 重构一处字符串查询编译期校验 |
| bulkWrite 多集合 | [06 篇](06-批量操作与写关注速查.md) | 批量导入场景压测吞吐 |
| 向量检索全链路 | [08 篇](08-向量检索与AI集成速查.md) | 建索引 + 语义检索 demo |
| MongoDB 8.x 性能 | 官方 45% 读/35% 写 | 压测对比 |

> 🎯 迁移心法（同 JPA 系列）：**先解编译期硬约束（①-④），再跑全量测试暴露行为变化（⑤-⑩），最后按业务验收新能力**——不要为升级而升级，升级必须带走至少一个新能力。

## 6. 高频坑排错表

| 症状 | 根因 | 解法 |
|------|------|------|
| `Timed out after 30000 ms` | 集群不可达/uri 错 | mongosh 手动连；查连接串（[02 篇](02-快速开始与连接配置速查.md) 6 节） |
| 查询全集合扫描慢 | 没索引 / 索引顺序错 | explain 看 COLLSCAN；ESR 建复合索引（[07 篇](07-索引与性能优化速查.md)） |
| 字段名对不上 | Mongo 不做驼峰转换 | `@Field("snake_case")` 显式命名（[03 篇](03-实体映射与文档注解速查.md) 2.1） |
| JSON 序列化 ObjectId 报错 | 原生 ObjectId 字段 | id 用 String；或 MongoJacksonModule（第 2 节） |
| 日期差 8 小时 | UTC 存储语义 | 统一 UTC 约定（第 3 节） |
| `Insertion failed: Document exceeds maximum allowed BSON object size` | 超 16MB | 大字段拆集合/GridFS（第 4 节） |
| `OptimisticLockingFailureException` 频繁 | 版本冲突 | 重试/条件更新（[03 篇](03-实体映射与文档注解速查.md) 5.1） |
| 事务不生效 | 单节点无副本集 / 缺事务管理器 | 起 replSet + MongoTransactionManager（[06 篇](06-批量操作与写关注速查.md) 4 节） |
| $vectorSearch 报"index not found" | 索引没建/没 READY/组件缺失 | 查索引状态；确认 mongot（[08 篇](08-向量检索与AI集成速查.md) 2 节） |
| 查询结果 null 字段丢失 | 默认跳过 null 写入 | `@Field(nullValue = SET)` 显式写（[03 篇](03-实体映射与文档注解速查.md) 6.2） |
| `is(null)` 查不到"字段为 null 的文档"（反之） | null 语义：不存在也匹配 | 需要严格区分用 `exists`（[05 篇](05-查询构造与模板速查.md) 2.2） |
| 聚合 $lookup 巨慢 | 被连接集合无索引 | 加索引；或改内嵌（[07 篇](07-索引与性能优化速查.md) 4 节） |

## 7. 测试实践

### 7.1 @DataMongoTest 切片测试

```java
@DataMongoTest                                   // 只起 Mongo 切片（连接测试库）
@AutoConfigureMockMvc                           // 按需
class ProductRepositoryTest {

    @Autowired ProductRepository productRepository;

    @Test
    void findByPriceBetween_shouldFilter() {
        productRepository.saveAll(List.of(p(100), p(5000), p(9000)));
        Page<Product> page = productRepository.findByCategoryAndPriceBetween(
                "手机", BigDecimal.valueOf(100), BigDecimal.valueOf(5000),
                PageRequest.of(0, 10));
        assertThat(page.getTotalElements()).isEqualTo(2);
    }
}
```

| 测试姿势 | 用途 | 要点 |
|---------|------|------|
| `@DataMongoTest` | Repository/模板切片 | 默认连本地 MongoDB（`spring.data.mongodb.uri` 指向测试库/Testcontainers） |
| `@SpringBootTest` | 事务/Service 集成 | 副本集事务测试用 Testcontainers 起 replSet |
| Testcontainers | 版本一致的 Mongo | `new MongoDBContainer("mongo:8.0")` 可配副本集 |
| 内嵌 Mongo | 快速单测 | de.flapdoodle 内嵌版（与生产版本差异注意） |

> ⚠️ 测试三坑：① **别连生产库**（数据污染/慢）；② 事务测试必须副本集容器（单节点会静默失败——[06 篇](06-批量操作与写关注速查.md) 4 节）；③ 派生方法 4.x 启动期已校验语法，但**语义（结果集）仍靠测试**——日期边界、null 语义、正则转义是重点用例。
