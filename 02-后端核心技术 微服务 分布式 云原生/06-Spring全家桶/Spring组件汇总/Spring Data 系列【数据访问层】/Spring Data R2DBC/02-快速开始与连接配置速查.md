## 1. 三步启动最小工程

### 1.1 依赖

```xml
<!-- 核心 starter（含 SDR + r2dbc-pool + 自动配置，不含驱动） -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-r2dbc</artifactId>
</dependency>

<!-- 按库选驱动（三选一，版本由 BOM 管理） -->
<dependency>
    <groupId>io.asyncer</groupId>
    <artifactId>r2dbc-mysql</artifactId>
    <scope>runtime</scope>
</dependency>
<!-- PostgreSQL: io.r2dbc:r2dbc-postgresql -->
<!-- H2 开发测试: io.r2dbc:r2dbc-h2 -->
```

| 组合场景 | 依赖 |
|---------|------|
| MySQL 8 生产 | starter + `io.asyncer:r2dbc-mysql` |
| PostgreSQL 生产 | starter + `io.r2dbc:r2dbc-postgresql` |
| 本地联调/测试 | starter + `io.r2dbc:r2dbc-h2` |
| WebFlux 全栈 | starter + `spring-boot-starter-webflux` |

> 💡 依赖最小化原则：**不要**手动引入 r2dbc-spi/r2dbc-pool 写版本——starter + Boot BOM 已锁定兼容（[01 篇](01-模块清单.md) 版本协调三原则）。

### 1.2 配置文件（application.yml）

```yaml
spring:
  r2dbc:
    url: r2dbc:mysql://localhost:3306/shop?serverTimezone=Asia/Shanghai
    username: root
    password: root
    pool:
      enabled: true               # ★ 连接池开关（r2dbc-pool）
      max-size: 20                # 池上限（默认 10）
      initial-size: 5
      max-idle-time: 30m
```

> ⚠️ **URL 前缀是 `r2dbc:`，不是 `jdbc:`**——`r2dbc:mysql:` / `r2dbc:postgresql:` / `r2dbc:h2:`；写错前缀启动直接报 `Unknown driver`。MySQL 8 注意 `serverTimezone` 参数（与 JDBC 相同）。

### 1.3 实体扫描与仓库扫描

| 机制 | 默认行为 | 定制 |
|------|---------|------|
| 实体映射 | 主启动类所在包及子包 | 无需 @EntityScan（R2DBC 无独立扫描器，靠仓库与模板推断） |
| Repository 扫描 | 主启动类所在包及子包 | `@EnableR2dbcRepositories(basePackages = "...")` |
| 事务管理器 | 自动配置 `R2dbcTransactionManager` | 多数据源时显式（第 4 节） |

```java
@SpringBootApplication
@EnableR2dbcRepositories(basePackages = "com.example.shop.repository")
public class ShopApplication { ... }
```

> 💡 多模块工程最常见的坑：**仓库散落在主包之外但忘了声明扫描包** → 启动报"找不到 Repository 实现"（[09 篇](09-集成地图与常见问题.md) 排错表）。

### 1.4 最小实体 + 仓库跑通

```java
@Table("user_account")
public class UserAccount {
    @Id private Long id;              // 自增主键（save 后自动回填）
    private String username;
    // getter/setter + 无参构造
}

public interface UserAccountRepository extends R2dbcRepository<UserAccount, Long> {
    Mono<UserAccount> findByUsername(String username);
}

// 使用（响应式类型贯穿）
@RestController
public class UserController {
    @GetMapping("/users/{username}")
    public Mono<UserAccount> find(@PathVariable String username) {
        return userAccountRepository.findByUsername(username);
    }
}
```

> 🎯 跑通即及格：**save → findById → findByUsername 三者全通**（测试里用 `StepVerifier` 或临时 block），说明"映射 + 仓库 + 连接 + 事务管理器"整条链路 OK——注意：**控制器直接返回 Mono/Flux 是 WebFlux 正确姿势**，别在控制器里 `.block()`（[08 篇](08-WebFlux响应式集成速查.md) 阻塞陷阱）。

## 2. Boot 4 属性总表

### 2.1 spring.r2dbc.*

| 属性 | 默认 | 说明 |
|------|------|------|
| `spring.r2dbc.url` | — | R2DBC 连接串（`r2dbc:mysql://host:port/db`） |
| `spring.r2dbc.username` / `password` | — | 凭据（url 里可内嵌） |
| `spring.r2dbc.pool.enabled` | true（url 配置时） | 连接池开关 |
| `spring.r2dbc.pool.max-size` | 10 | 池上限 |
| `spring.r2dbc.pool.initial-size` | 与 max-size 相同 | 初始连接数 |
| `spring.r2dbc.pool.max-idle-time` | 30m | 连接最大空闲时间 |
| `spring.r2dbc.pool.max-life-time` | 30m | 连接最大存活 |
| `spring.r2dbc.pool.validation-depth` | LOCAL | 校验深度 |
| `spring.r2dbc.properties.*` | — | 透传驱动参数（如 `ssl`、`tlsVersion`） |

> 💡 与 JDBC 属性对照：`spring.r2dbc.*` 对应 `spring.datasource.*`；池参数对应 `hikari.*`——团队习惯可平移，但**获取连接的 API 是非阻塞的**（`Mono<Connection>`），没有 Hikari 的"阻塞等待超时"语义。

### 2.2 常见驱动参数

```yaml
spring:
  r2dbc:
    url: r2dbc:mysql://localhost:3306/shop
    properties:
      sslMode: REQUIRED                # MySQL TLS（VERIFY_CA/REQUIRED/DISABLED）
      allowPublicKeyRetrieval: true    # MySQL 8 caching_sha2_password 需要
      connectTimeout: 10s              # 连接超时
```

> ⚠️ MySQL 8 认证插件：caching_sha2_password 需要 `allowPublicKeyRetrieval=true` 或配置 RSA 公钥（与 JDBC 同坑）；TLS 生产必开（`sslMode=REQUIRED` 起步）。

## 3. 连接池：r2dbc-pool 调参

```java
// 编程式定制（ConnectionFactory 级）
@Configuration
public class R2dbcPoolConfig {
    @Bean
    ConnectionFactory connectionFactory() {
        ConnectionFactory base = ConnectionFactories.get(
                "r2dbc:mysql://localhost:3306/shop");
        return new ConnectionPool(base, ConnectionPoolConfiguration.builder(base)
                .maxSize(30)                 // 峰值并发事务 × (1 + 慢查询占比) 的思路
                .initialSize(5)
                .maxIdleTime(Duration.ofMinutes(20))
                .maxLifeTime(Duration.ofMinutes(60))
                .build());
    }
}
```

| 调参要点 | 说明 |
|---------|------|
| max-size | 与 Hikari 同思路：≈ 峰值并发 × (1 + 慢查询占比)；响应式下连接是"稀有资源"（线程不占，连接照占） |
| max-life-time | 应小于数据库 wait_timeout（MySQL 默认 8h） |
| validation-query | 可选探活 SQL（MySQL `SELECT 1`） |
| 监控 | Actuator 暴露 `r2dbc.pool` 指标（活跃/空闲/等待数） |

> ⚠️ 连接池误区：**响应式 ≠ 连接不要钱**——每条 SQL 仍占用池中一个连接；长事务/慢查询照样把池耗尽（表现为"获取连接超时"），优化路径仍是"缩事务、改 SQL"。

## 4. 事务管理器配置

```java
// Boot 自动配置（单数据源无需手写）
// 多数据源时显式：
@Configuration
public class R2dbcTxConfig {
    @Bean
    R2dbcTransactionManager transactionManager(ConnectionFactory cf) {
        return new R2dbcTransactionManager(cf);
    }
}
```

```java
// 使用（与 JPA 同 API，响应式方法上标注）
@Service
public class OrderService {
    @Transactional                        // 进入事务：上下文绑定到当前连接
    public Mono<Void> transfer(Long from, Long to, BigDecimal amt) {
        return accountRepo.deduct(from, amt)
                .then(accountRepo.add(to, amt));
    }
}
```

| 要点 | 说明 |
|------|------|
| 管理器 | `R2dbcTransactionManager`（ReactiveTransactionManager） |
| 声明 | `@Transactional` 同 JPA（传播/隔离/回滚规则语义一致） |
| **线程传播** | 响应式事务绑定在 **Publisher 订阅链**上，不是线程上——`block()`/`.subscribeOn(其他线程池)` 场景要小心（[06 篇](06-响应式事务与并发控制速查.md) 专节） |
| 隔离级别 | `@Transactional(isolation = ...)` 支持（随驱动能力） |

> 🎯 面试必答：**"响应式事务和 JPA 事务本质区别？"**——JPA 事务绑定"线程 + ThreadLocal"（阻塞模型天然成立）；R2DBC 事务绑定"**Publisher 订阅链**"（Reactor Context 传播）——所以**响应式事务的正确边界是"整条 reactive 管道不跨线程切换"**，一旦 `.block()` 或换线程池，事务上下文就断了；Spring Framework 7 的响应式事务传播已很成熟，但"管道完整性"这条铁律不变（[06 篇](06-响应式事务与并发控制速查.md) 有失效场景清单）。

## 5. 多数据源与多数据库

### 5.1 多数据源（两库两套）

```java
@Configuration
public class MultiR2dbcConfig {
    // ① 两个 ConnectionFactory
    @Bean @Primary
    ConnectionFactory primaryCf() {
        return ConnectionFactories.get("r2dbc:mysql://host1:3306/db1");
    }
    @Bean
    ConnectionFactory secondaryCf() {
        return ConnectionFactories.get("r2dbc:mysql://host2:3306/db2");
    }

    // ② 两个事务管理器（@Transactional("secondaryTx") 指名）
    @Bean @Primary
    R2dbcTransactionManager primaryTx(@Qualifier("primaryCf") ConnectionFactory cf) {
        return new R2dbcTransactionManager(cf);
    }
    @Bean
    R2dbcTransactionManager secondaryTx(@Qualifier("secondaryCf") ConnectionFactory cf) {
        return new R2dbcTransactionManager(cf);
    }
}

// ③ 仓库分两批扫描
@Configuration
@EnableR2dbcRepositories(basePackages = "com.example.repo.primary",
        connectionFactoryRef = "primaryCf")
class PrimaryRepoConfig {}

@Configuration
@EnableR2dbcRepositories(basePackages = "com.example.repo.secondary",
        connectionFactoryRef = "secondaryCf")
class SecondaryRepoConfig {}
```

### 5.2 双轨场景：JDBC + R2DBC 共存

| 场景 | 做法 | 注意 |
|------|------|------|
| 团队渐进迁移 | 同库同时配 `spring.datasource` + `spring.r2dbc` | **两套连接池两套驱动**，成本翻倍；只在新链路用 R2DBC |
| 阻塞组件（Flyway 迁移） | 迁移仍走 JDBC（Flyway 不支持 R2DBC） | **生产常规组合**：Flyway(JDBC) + 业务(R2DBC) |
| 完全切换 | 全量 R2DBC | 放弃 JPA 全部特性（[09 篇](09-集成地图与常见问题.md) 迁移对照） |

> 💡 **Flyway + R2DBC 组合是行业标配**：Flyway 只支持 JDBC——`spring.datasource.url`（jdbc:）+ `spring.r2dbc.url` 并存，Flyway 走 JDBC 建表，业务走 R2DBC（Boot 自动配置兼容双轨）。

## 6. 常见连接问题排错

| 症状 | 根因 | 排查动作 |
|------|------|---------|
| `Unknown driver` / `ConnectionFactory` Bean 缺失 | URL 前缀错（jdbc: 写成）/ 驱动依赖没加 | 确认 `r2dbc:mysql:` 前缀 + 驱动坐标（[01 篇](01-模块清单.md) 2 节） |
| `Connection refused` | 数据库没起/端口错/防火墙 | 客户端（mysql 命令）手动连确认 |
| `Public Key Retrieval is not allowed` | MySQL 8 认证插件 | properties 加 `allowPublicKeyRetrieval: true` |
| 连接被踢（`Connection is not available`） | max-life-time > 数据库 wait_timeout | 池参数 `max-life-time` 调小（< 8h） |
| 高并发下连接耗尽 | 池太小 / 长事务占连接 | 池 max-size 调大 + 缩事务（第 3 节） |
| `Authentication failed` | 账号/密码/authSource 错 | 用客户端验证凭据 |
| 响应式链路卡死（无响应不报错） | 阻塞调用混入非阻塞链路 | [08 篇](08-WebFlux响应式集成速查.md) 阻塞陷阱排查 |

> 🎯 排障顺序铁律（同 JPA/Mongo 系列）：**数据库层（客户端能连吗）→ 连接层（URL/驱动/池参数对吗）→ 映射层（表和实体对得上吗）→ 响应式链路（有没有 block/阻塞调用）**——从下往上，90% 的"启动失败/卡死"在数据库与连接层解决。
