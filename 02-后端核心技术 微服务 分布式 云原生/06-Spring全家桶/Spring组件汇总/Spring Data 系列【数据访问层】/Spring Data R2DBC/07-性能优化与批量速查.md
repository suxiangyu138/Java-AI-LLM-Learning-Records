## 1. 响应式性能观：并发模型是第一性能

**通俗**：R2DBC 的性能价值不在"单条 SQL 快"，而在"**同一个线程能同时等很多条 SQL**"——1000 并发下，JDBC 要 1000 个线程，R2DBC 可能 20 个线程就够。

| 模型 | 1000 并发查询 | 单查询耗时 | 线程占用 |
|------|-------------|-----------|---------|
| JDBC（阻塞） | 1000 线程各等各的 IO | 快 | **1000 线程**（内存 ~1GB+，切换开销大） |
| R2DBC（非阻塞） | 20 线程同时处理 1000 个等待 | 略慢（协议开销） | **20 线程**（内存 ~20MB） |

> 🎯 面试必答：**"R2DBC 凭什么在高并发下更好？"**——阻塞模型里线程 = 并发数（每个请求占一个线程等 IO）；非阻塞模型里**一个线程可以同时等待多个 IO**（事件驱动 + 回调/响应式），所以同等并发下线程需求降一个量级——**性能提升来自并发模型，不是单查询速度**；单查询 R2DBC 通常还略慢（协议编解码开销）。

### 1.1 前提：全链路非阻塞

| 链路环节 | 阻塞实现 | 响应式实现 |
|---------|---------|-----------|
| HTTP | MVC（Servlet 线程池） | **WebFlux**（Netty） |
| 数据库 | JDBC | **R2DBC** |
| Redis | Lettuce 同步 | **Lettuce 响应式 / ReactiveRedisTemplate** |
| 第三方 HTTP | RestTemplate/Feign | **WebClient** |
| 连接池 | Hikari | **r2dbc-pool** |

> ⚠️ **阻塞陷阱**：链路里任何一环是阻塞的（比如用了 JDBC 或 RestTemplate），线程照样被占满——**响应式的收益是全链路的**，只换数据层 = 只省了数据库那一环的线程（[08 篇](08-WebFlux响应式集成速查.md) 有完整排查）。

## 2. 批量写入优化

### 2.1 批量插入

```java
// Repository：insertAll（Flux 批量）
public interface ProductRepository extends R2dbcRepository<Product, Long> {
    // saveAll 会逐条执行（每条一个往返）；insertAll 是 SQL 批处理
}

// 实体模板：insertAll
Flux<Product> saved = r2dbcEntityTemplate.insertAll(List.of(p1, p2, p3, ...));

// DatabaseClient：批量拼接（一条 SQL 多组值，注意参数上限）
client.sql("""
    insert into product (name, price) values (:n1, :p1), (:n2, :p2), (:n3, :p3)
    """)
    .bind("n1", ...).bind("p1", ...)
    ...
    .fetch().rowsUpdated();
```

| 方式 | 网络往返 | 适用 |
|------|:---:|------|
| `saveAll`（逐条） | N | 小批量（< 100） |
| `insertAll`（模板） | 1（驱动批处理） | **中大批量（100-1000）** |
| 手拼多值 SQL | 1 | 超大批量（注意参数与包大小限制） |

> ⚠️ **响应式批量的注意**：① 事务内大批量 insertAll 仍会占连接（长事务红线，[06 篇](06-响应式事务与并发控制速查.md)）；② 单批上限参考：MySQL 包大小（max_allowed_packet 默认 64MB，安全单批 1000-5000 行）；③ **无 IDENTITY 批处理问题**——R2DBC 无 ORM 层"逐条拿 id"机制，自增 id 回填在 insert 后由驱动返回（大批量回填代价高，导入场景可不用回填）。

### 2.2 批量更新（条件更新/upsert）

```java
// 4.1 聚合根 upsert（一条 SQL）
@Modifying
@Query("""
    insert into product (id, name, price, version)
    values (:id, :name, :price, 1)
    on duplicate key update name = values(name), price = values(price)
    """)
Mono<Long> upsertProduct(@Param("id") Long id, @Param("name") String name,
                         @Param("price") BigDecimal price);
```

> 💡 upsert 是"幂等导入"正解（同 [JPA/MyBatis 的 ON DUPLICATE KEY](../../../../01-关系型数据库/MyBatisPlus/) 思路）：批量导入重复数据不报错、不重复插入——配合唯一索引使用（[03 篇](03-聚合根映射速查.md) 业务唯一键）。

## 3. 流式读取与大数据量

**通俗**：R2DBC 天生流式——查询结果**逐行**从数据库流过来，不一次性全部加载进内存（Flux + 背压）。

```java
// 全量导出：Flux 流式（百万行不 OOM）
public Flux<Product> exportAll() {
    return client.sql("select * from product")
            .map(Product.class)
            .all();                    // 逐行发射，背压控制拉取
}

// 分批消费：buffer 凑批处理
public Mono<Void> exportToFile() {
    return exportAll()
            .buffer(1000)              // 每 1000 行凑一批
            .concatMap(batch -> writeBatch(batch))   // 串行写（不积压）
            .then();
}
```

| 对比 | JDBC | R2DBC |
|------|------|-------|
| 大数据量 | 全量载入内存（List）或 fetchSize 流式（复杂） | **天然流式**（Flux 逐行） |
| 内存 | 百万行 = 大 List | 恒定（背压按需拉取） |
| 导出/报表 | 游标 + 手动分批 | `.buffer(n)` + `.concatMap` |

> 🎯 面试必答：**"R2DBC 怎么做大数据量导出？"**——Flux 天然流式：查询 → 逐行发射 → `buffer(1000)` 凑批 → `concatMap` 串行写文件（避免 flatMap 并发积压）；**全程内存恒定**——这是响应式模型相对 JDBC 的杀手锏场景（JDBC 要么全量 List、要么手写 fetchSize 流式）。

## 4. 无缓存下的优化策略

**通俗**：JPA 有"一级缓存"（同事务查过的实体不重查）；R2DBC 什么都没有——**每次查询都真实打库**，所以热点数据的缓存要自己建。

| 策略 | 做法 | 适用 |
|------|------|------|
| **应用层缓存** | Caffeine（本地）/ Redis（分布式）包住读方法 | 读多写少热数据（商品信息、字典） |
| 缓存失效 | 写路径主动失效（Cache-Aside，同 [JPA 05 篇](../../Spring%20Data%20系列【数据访问层】/Spring%20Data%20JPA/07-性能优化与批量操作速查.md) 一致性方案） | 更新后删缓存 |
| 响应式缓存 | `Mono.cache()` 对同一订阅复用结果 | 单个 Mono 结果复用（短窗口） |
| 查询优化 | 索引 + 投影 + 覆盖索引 | 数据库侧（[MySQL 索引原理](../../../../01-关系型数据库/MySQL/04-索引原理与设计.md)） |
| 连接优化 | 池大小 + 短事务 | 连接是稀缺资源（[02 篇](02-快速开始与连接配置速查.md) 3 节） |

```java
// 响应式缓存示例（本地 Caffeine）
@Service
public class ProductService {
    private final Cache<String, Mono<Product>> cache = Caffeine.newBuilder()
            .expireAfterWrite(Duration.ofMinutes(10)).maximumSize(10_000).build();

    public Mono<Product> getProduct(Long id) {
        return cache.get("product:" + id, k ->
                productRepository.findById(id).cache());    // cache()：单次订阅内复用
    }

    // 写路径失效
    @Transactional
    public Mono<Product> updatePrice(Long id, BigDecimal price) {
        return productRepository.findById(id)
                .flatMap(p -> { p.setPrice(price); return productRepository.save(p); })
                .doOnSuccess(p -> cache.invalidate("product:" + id));   // 更新后失效
    }
}
```

> ⚠️ **缓存一致性红线**（同 JPA 系列）：读多写少才缓存；更新后主动失效（Cache-Aside）；资金/库存强一致数据不缓存或慎缓存——响应式只是换了个 API，一致性坑一个不少。

## 5. 背压与查询控制

### 5.1 背压（Reactive Streams 内建）

```text
数据库 → 驱动（按需取行）→ Flux → 消费者
                    ↑
          消费者 request(n)：一次只要 n 行
          （背压：数据库不会一股脑推完整个结果集）
```

| 场景 | 背压控制 | 说明 |
|------|---------|------|
| 大结果集消费 | 天然背压（Flux 按 request 取行） | 无需配置，流式就是背压 |
| 消费端慢 | 驱动停止取行，等待 | 内存不增长 |
| 凑批处理 | `.buffer(n)` / `.window(n)` | 批量消费 |
| 限制并发 | `.concatMap`（串行）/ `.flatMap(..., concurrency)` | 防积压 |

### 5.2 查询侧控制

```java
// 限制结果数（防拉爆）
client.sql("select * from product where category = :c limit :limit")
        .bind("c", "手机").bind("limit", 100)
        .map(Product.class).all();

// 深分页（同 SQL 系列：游标式）
@Query("select * from product where id > :lastId order by id limit :size")
Flux<Product> findNextPage(@Param("lastId") Long lastId, @Param("size") int size);
```

> ⚠️ 查询控制三件事：**limit 防拉爆、游标防深分页、流式防内存**——与 [JPA 07 篇](../../Spring%20Data%20系列【数据访问层】/Spring%20Data%20JPA/07-性能优化与批量操作速查.md) 的三板斧同思路，响应式下"流式"是内建能力（更省事）。

## 6. 性能排查清单

| # | 动作 | 说明 |
|---|------|------|
| ① | **查阻塞陷阱** | 链路里有没有 block/同步调用/JDBC 混入（[08 篇](08-WebFlux响应式集成速查.md)）——**响应式性能的第一杀手** |
| ② | 看 SQL（@Query 直写） | R2DBC 无 ORM 生成层，SQL 即所见；EXPLAIN 逐条分析 |
| ③ | 检查索引 | 手写 SQL 也要索引（[MySQL 索引原理](../../../../01-关系型数据库/MySQL/04-索引原理与设计.md)） |
| ④ | 检查连接池 | max-size 与并发匹配；长事务占连接（[02 篇](02-快速开始与连接配置速查.md) 3 节） |
| ⑤ | 检查事务边界 | 大事务/事务内远程调用（[06 篇](06-响应式事务与并发控制速查.md) 6 节） |
| ⑥ | 检查重复查询 | 无缓存：同数据被反复查 → 上应用层缓存（第 4 节） |
| ⑦ | 检查大结果集 | 无 limit/流式 → 限流 + 流式（第 3/5 节） |
| ⑧ | 检查批量 | 逐条 saveAll → insertAll/批处理（第 2 节） |
| ⑨ | 监控 | Actuator `r2dbc.pool` 指标 + 慢 SQL 日志 |
| ⑩ | 压测验证 | **响应式收益必须压测证明**（并发场景对比），别凭感觉 |

> 🎯 性能口诀：**"先查阻塞（链路非阻塞了吗）→ 再查 SQL（走索引了吗）→ 后查缓存（重复查了吗）"**——响应式性能问题的 80% 在 ①②，别一上来就调连接池。
