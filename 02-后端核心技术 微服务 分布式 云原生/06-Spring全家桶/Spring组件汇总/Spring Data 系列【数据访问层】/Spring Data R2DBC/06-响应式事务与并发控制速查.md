## 1. 响应式事务的本质

**通俗**：JPA 事务绑"线程"（ThreadLocal），R2DBC 事务绑"**管道**"（Reactor Context）——同一个 Publisher 订阅链上的操作共用一个连接、一个事务。

```text
阻塞模型（JPA）：
  线程 T ── begin ── SQL1 ── SQL2 ── commit        # 事务 = 线程的局部状态

响应式模型（R2DBC）：
  Publisher 链 ── begin(订阅时) ── SQL1 ── SQL2 ── commit
       │  事务上下文随 Reactor Context 沿链传播，与线程无关
       └─ 线程池里任何线程执行都行，只要还在同一订阅链上
```

| 维度 | JPA 事务 | R2DBC 事务 |
|------|---------|-----------|
| 绑定对象 | 线程（ThreadLocal） | **Publisher 订阅链**（Reactor Context） |
| 连接获取 | 事务开始时同步拿连接 | 订阅时拿连接（`Mono<Connection>`） |
| 提交时机 | 方法返回时 | **Publisher 完成时**（链上最后一个操作完成） |
| 生效前提 | 方法经代理调用 | 方法经代理调用 + **管道完整传播** |

> 🎯 面试必答：**"响应式事务怎么实现回滚？"**——@Transactional 拦截器把事务上下文放入 Reactor Context（`TransactionalOperator` 包裹），管道执行中任何操作抛异常 → **异常沿管道向上传播** → 拦截器收到异常执行 rollback；所以**响应式事务的正确性 = 管道的完整性**：异常不能被"吞掉"，上下文不能被"切断"。

## 2. R2dbcTransactionManager 配置

```java
// Boot 单数据源自动配置（无需手写）；多数据源显式：
@Configuration
public class R2dbcTxConfig {
    @Bean
    R2dbcTransactionManager transactionManager(ConnectionFactory cf) {
        return new R2dbcTransactionManager(cf);
    }
}

// 声明式使用（与 JPA 同 API）
@Service
public class OrderService {
    @Transactional
    public Mono<Void> createOrder(OrderEntity order, PaymentEntity payment) {
        return orderRepository.save(order)
                .then(paymentRepository.save(payment))
                .then();
    }
}
```

| 要点 | 说明 |
|------|------|
| 管理器 | `R2dbcTransactionManager`（实现 `ReactiveTransactionManager`） |
| 声明 | `@Transactional` 注解（Spring Framework 7 响应式事务支持成熟） |
| 编程式 | `TransactionalOperator.execute(transaction -> ...)` |
| 默认回滚 | 运行时异常（同 JPA）；`rollbackFor = Exception.class` 同样适用 |
| 只读 | `@Transactional(readOnly = true)` 语义支持 |

> ⚠️ **事务未提交的常见表象**：方法返回了但数据没写进去——因为**提交发生在 Publisher 完成时**；调用方如果 `.block()` 在事务方法外或没订阅完整，提交就不发生（见第 4 节失效清单）。

## 3. 传播行为与隔离级别

### 3.1 传播行为（与 JPA 语义一致）

| 传播行为 | 行为 | 响应式注意 |
|----------|------|-----------|
| `REQUIRED`（默认） | 有事务加入，无则新建 | 主流 |
| `REQUIRES_NEW` | 挂起当前，新建独立 | 响应式下=独立管道（跨 Service 调用场景注意） |
| `NESTED` | 保存点 | 依赖数据库 savepoint，支持有限 |
| `MANDATORY` / `NEVER` / `SUPPORTS` / `NOT_SUPPORTED` | 同 JPA 语义 | — |

### 3.2 隔离级别（随驱动能力）

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public Mono<Void> transfer(...) { ... }
```

| 注意 | 说明 |
|------|------|
| 级别是数据库侧实现的 | 与 JPA 相同（`SET TRANSACTION ISOLATION LEVEL`，实现见 [MySQL 事务与锁](../../../../01-关系型数据库/MySQL/03-事务与锁机制.md)） |
| 驱动差异 | MySQL 驱动支持读已提交/可重复读；具体能力随驱动版本 |
| 别依赖默认 | 跨库项目显式声明（同 JPA 系列） |

> 💡 事务语义全部平移自 [JPA 06 篇](../../Spring%20Data%20系列【数据访问层】/Spring%20Data%20JPA/06-事务与并发控制速查.md)——**传播/隔离/回滚规则三张表直接复用**，响应式只多了"管道传播"这一条新铁律。

## 4. 失效场景清单（响应式专属）

> 与 JPA 的"事务失效八大坑"对照：**①-⑤ 通用**（自调用、非 public、非 Bean、异常被吞、异常类型），**⑥-⑧ 是响应式新增**：

| # | 失效场景 | 症状 | 解法 |
|---|---------|------|------|
| ① | **自调用** | 同类方法 A 调 B（this.B()），B 的 @Transactional 不生效 | 拆独立 Bean / 注入自身代理（同 JPA 坑） |
| ② | 方法非 public | 代理不拦截 | 改 public |
| ③ | 类未被 Spring 管理 | new 出来的对象 | @Service 等交给容器 |
| ④ | **异常被吞** | `.onErrorReturn()` 兜底把异常吃掉 → 不回滚 | 事务方法内不吞异常；兜底放事务外 |
| ⑤ | 异常类型不匹配 | 受检异常没配 rollbackFor | `rollbackFor = Exception.class` |
| ⑥ | **`.block()` 切断管道** | 事务方法内 `.block()` → 阻塞 + 上下文断 | **事务管道内禁止 block**；要同步结果在事务外 block |
| ⑦ | **换线程池** | `.subscribeOn(Schedulers.boundedElastic())` 切线程 | Reactor Context 默认会传播，但**非 Reactor 管理的线程/虚拟线程切换**可能丢上下文；尽量不切 |
| ⑧ | **热流/多订阅** | `.share()`/`.cache()` 让事务方法被订阅两次 | 事务方法返回冷流（每次订阅重新执行） |

```java
// 反模式（⑥）：事务内 block —— 管道被切断 + 线程阻塞
@Transactional
public OrderEntity createBlocking(OrderDto dto) {
    return orderRepository.save(dto.toEntity()).block();   // ❌ 管道断了，事务语义全丢
}

// 正解：响应式贯穿
@Transactional
public Mono<OrderEntity> create(OrderDto dto) {
    return orderRepository.save(dto.toEntity());           // ✅ 提交发生在调用方订阅完整时
}
```

> 🎯 面试必答：**"响应式事务最容易踩什么坑？"**——三条：① **事务内 block**（管道切断，事务上下文丢失，还占线程）；② **异常被 onErrorReturn 吞掉**（不回滚，数据半提交）；③ **自调用**（与 JPA 完全相同的代理失效）——记忆口诀："**管道不断、异常不吞、代理不走**"。

## 5. 乐观锁与重试

### 5.1 @Version 与响应式重试

```java
// 实体（同 JPA 语义，见 03 篇 5 节）
@Table("product")
public class Product {
    @Id private Long id;
    @Version private Long version;
}

// 响应式重试：冲突 → 重新读-改-写
@Service
public class PriceService {
    private static final int MAX_RETRY = 3;

    public Mono<Product> updatePrice(Long id, BigDecimal newPrice) {
        return Mono.defer(() -> productRepository.findById(id)     // defer：每次重试都重新执行
                .flatMap(p -> {
                    p.setPrice(newPrice);                          // 改属性（无脏检查，显式 save）
                    return productRepository.save(p);              // 版本 CAS 在这里
                }))
                .retryWhen(Retry.max(MAX_RETRY - 1)
                        .filter(OptimisticLockingFailureException.class::isInstance)
                        .onRetryExhaustedThrow((spec, sig) -> new BizException("操作冲突，请重试")));
    }
}
```

| 要点 | 说明 |
|------|------|
| 冲突异常 | `OptimisticLockingFailureException`（同 JPA） |
| **defer 必须** | 每次重试要**重新执行**读-改-写（`Mono.defer` 包裹，否则重试复用一个已完成的流） |
| retryWhen | Reactor 重试操作符（`Retry.max` + filter 指定异常） |
| 退避 | `Retry.backoff(3, Duration.ofMillis(50))` 指数退避更稳 |

> ⚠️ **响应式重试与同步重试的本质差异**：同步重试是"循环调用方法"；响应式是"**重新订阅管道**"——所以必须 `Mono.defer` 保证每次订阅都重新执行查询，这是响应式乐观锁重试最容易写错的地方（复用一个完成的流 = 重试无效）。

### 5.2 悲观锁（条件更新替代）

```java
// R2DBC 无 @Lock 注解；悲观锁语义用"条件更新/原子更新"替代：
@Modifying
@Query("update product set stock = stock - :qty where id = :id and stock >= :qty")
Mono<Long> deductStock(@Param("id") Long id, @Param("qty") int qty);   // 0 行 = 冲突

// 或 FOR UPDATE（需事务内）
@Transactional
public Mono<Void> lockAndUpdate(Long id) {
    return client.sql("select * from product where id = :id for update")  // 行锁
            .bind("id", id)
            .map(Product.class).one()
            .flatMap(p -> client.sql("update product set price = :price where id = :id")
                    .bind("price", newPrice).bind("id", id)
                    .fetch().rowsUpdated().then());
}
```

| 方案 | 适用 | 与 JPA 对照 |
|------|------|------------|
| 条件更新（CAS 式 SQL） | **首选**（免锁、免事务） | 等价 JPA @Modifying 条件更新 |
| @Version + 重试 | 读-改-写业务 | 等价 JPA 乐观锁 |
| SELECT ... FOR UPDATE | 强一致 + 已有事务 | 等价 JPA @Lock(PESSIMISTIC_WRITE)（需手写 SQL） |

## 6. 事务性能红线

| 红线 | 危害 | 解法 |
|------|------|------|
| 事务内调远程接口（HTTP/RPC） | 持连接等网络（响应式下连接被占） | 远程调用移出事务（同 JPA 红线） |
| 事务内大循环写 | 长事务占连接 | 分批提交 / 批量（[07 篇](07-性能优化与批量速查.md)） |
| 事务内 block | 线程阻塞 + 上下文断 | 全管道响应式 |
| 跨服务事务 | 单数据源管不了 | 最终一致 + 对账（[消息队列分布式事务](../../../../03-消息队列/消息队列理论与实战/07-分布式事务与消息队列.md)） |
| 长事务（> 秒级） | 连接池耗尽（连接是响应式下的稀缺资源） | 缩事务范围 / 优化 SQL |

> 🎯 总结三句：**① 事务边界放 Service、管道保持完整（不断 block 不吞异常）；② 并发控制优先"条件更新"（免锁免事务），其次 @Version 重试（记得 defer），最后才 FOR UPDATE；③ 连接是稀缺资源——事务越小越好**——与 [JPA 06 篇](../../Spring%20Data%20系列【数据访问层】/Spring%20Data%20JPA/06-事务与并发控制速查.md) 的心法完全一致，响应式只是把"线程"换成了"连接 + 管道"。
