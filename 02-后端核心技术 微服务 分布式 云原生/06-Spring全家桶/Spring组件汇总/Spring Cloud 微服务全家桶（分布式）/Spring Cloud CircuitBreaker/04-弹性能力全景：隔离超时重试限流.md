## 1. 能力全景：五件套职责

| 能力 | 英文 | 防什么 | 类比 |
|------|------|--------|------|
| **熔断** | CircuitBreaker | 下游已挂，防继续调用 + 防雪崩 | 保险丝 |
| **隔离** | Bulkhead | 一个下游耗尽线程，传染其他调用 | 船舱隔板（舱壁） |
| **超时** | TimeLimiter | 下游慢，请求无界等待 | 闹钟 |
| **限流** | RateLimiter | 瞬时流量打爆自己 | 水龙头 |
| **重试** | Retry | 瞬时故障（网络抖动），重试可成功 | 再试一次 |

> 🎯 心智模型：**熔断是"闸门"（开了全拒），隔离是"墙"（隔开互不传染），超时是"底线"（不能无限等），限流是"入口"（控制总量），重试是"容错"（一次不行再来）**——五件套可单独用，也可嵌套组合。

## 2. Bulkhead：舱壁隔离

### 2.1 两种实现

| 维度 | SemaphoreBulkhead（信号量） | ThreadPoolBulkhead（线程池） |
|------|---------------------------|------------------------------|
| 限制什么 | **并发执行数**（信号量计数） | **并发执行数**（线程池最大线程） |
| 超过限制 | 立即拒绝（抛 BulkheadFullException） | 任务进队列（排队等线程） |
| 线程模型 | 调用线程执行（零切换） | 独立线程池执行（调用线程不阻塞） |
| 超时协同 | 与 TimeLimiter 结合（Future 取消） | 自带 `keepAliveDuration`、队列满拒绝 |
| 默认 | **SCCB 默认 FixedThreadPoolBulkhead** | 同左 |
| 切换 | `enable-semaphore-default-bulkhead=true` | — |
| 适用 | 轻量、低并发 | 慢下游、需要超时中断的场景 |

> ⚠️ **SCCB 注意**：SCCB 的默认 Bulkhead 是 **FixedThreadPoolBulkhead**（官方文档默认值），要信号量版需显式开 `spring.cloud.circuitbreaker.resilience4j.enableSemaphoreDefaultBulkhead=true`；而 Resilience4J 独立库默认是信号量——**两套默认不一样，别记混**。

### 2.2 配置示例

```yaml
resilience4j:
  thread-pool-bulkhead:
    instances:
      orderService:
        max-thread-pool-size: 4        # 最大线程数
        core-thread-pool-size: 4       # 核心线程数
        queue-capacity: 10             # 排队容量（满则拒绝）
  bulkhead:                            # 信号量版（启用后走这里）
    instances:
      orderService:
        max-concurrent-calls: 10       # 最大并发数
        max-wait-duration: 10ms        # 获取信号量等待超时（超时抛 BulkheadFullException）
```

### 2.3 隔离解决的问题

```text
场景：order-service 同时调 payment-service 和 user-service
  ├── payment 挂了 → 50 个请求阻塞等 payment 超时
  ├── 无隔离：order-service 的 200 个线程全被占住 → user-service 的调用也排队 → 全链路雪崩
  └── 有隔离：payment 的 Bulkhead 只有 10 个槽 → 占满即拒（快速失败）
       → 其余 190 线程继续正常服务 user-service 调用 ← ★ 这就是"舱壁"的价值
```

> 🎯 面试必答：**"为什么需要隔离？"**——防止**故障蔓延**（single point of failure 传染）；信号量隔离省线程、线程池隔离断依赖（下游慢调用不占业务线程，且可优雅超时取消）。

## 3. TimeLimiter：超时控制

### 3.1 原理

```text
TimeLimiter 用 ScheduledExecutorService 定时：
  ├── 调用执行 > timeoutDuration（默认 1s）→ 触发超时
  ├── cancelRunningFuture=true（默认）：取消 Future → 中断正在执行的线程
  └── 抛 TimeoutException → 计为失败 → 走 fallback / 触发熔断统计
```

### 3.2 配置与注意

```yaml
resilience4j:
  timelimiter:
    instances:
      orderService:
        timeout-duration: 3s           # 超时上限（默认 1s！）
        cancel-running-future: true    # 超时后中断线程（默认 true）
```

| 要点 | 说明 |
|------|------|
| **默认 1s 太激进** | 业务接口普遍 >1s，**必配**，否则正常慢调用全被当失败 |
| 与熔断联动 | TimeoutException 计入失败率 → 大量超时 = 熔断 |
| 与 Bulkhead 关系 | 阻塞式下 TimeLimiter 的取消依赖 Future——**信号量隔离下是"中断调用线程"，线程池隔离下是"取消池内任务"** |
| 响应式 | 不适用（响应式靠订阅取消，无 Future 模型） |
| 调用链超时一致性 | **本层超时 > 上游超时 > 下游超时**（见 [08 篇](08-生产实践与选型避坑.md) 超时链） |

> ⚠️ **注意**：`cancelRunningFuture=true` 中断的是**调用方线程**——如果下游调用是阻塞式 IO（如 RestTemplate），中断只能取消"等待"，**已发出的 HTTP 请求无法收回**（连接会继续占着直到对端返回）；要彻底解决需要客户端连接池超时配合。

## 4. RateLimiter：限流

### 4.1 令牌桶模型

```text
RateLimiter 本质：令牌桶
  ├── 每 refresh-period 生成 limit-for-period 个令牌
  ├── 调用消耗 1 个令牌（可配置 permits，2.3.0 起注解支持指定）
  ├── 无令牌 → 阻塞等待（timeout-duration 内）或直接拒绝（抛 RequestNotPermitted）
  └── 2.3.0：executeSuspendFunction 尊重 drainPermissionsOnResult
```

### 4.2 配置示例

```yaml
resilience4j:
  ratelimiter:
    instances:
      orderService:
        limit-for-period: 100         # 每个周期最多 100 次
        limit-refresh-period: 1s      # 周期 1s（= QPS 100）
        timeout-duration: 0ms         # 拿不到令牌的等待上限（0 = 立即拒绝）
```

> 🎯 与熔断的区别（面试高频）：**熔断是下游坏了才触发（反应式），限流是流量超了随时触发（预防式）**——"削峰"靠限流，"防雪崩"靠熔断+隔离。

## 5. Retry：重试

### 5.1 配置示例

```yaml
resilience4j:
  retry:
    instances:
      orderService:
        max-attempts: 3               # 最多尝试 3 次（含首次）
        wait-duration: 500ms          # 间隔 500ms
        retry-exceptions:
          - org.springframework.web.client.ResourceAccessException   # 只重试这类异常
        ignore-exceptions:
          - org.springframework.web.client.HttpClientErrorException # 4xx 不重试
        enable-exponential-backoff: true
        exponential-backoff-multiplier: 2.0
        max-wait-duration: 5s
```

### 5.2 重试的正确打开方式

| 规则 | 说明 |
|------|------|
| **只重试瞬时故障** | 网络抖动/连接拒绝/超时（ResourceAccessException）→ 重试；**4xx/业务异常绝不重试**（幂等语义！） |
| 重试必须幂等 | 重试会重复请求：**写接口必须有幂等设计**，否则重复下单/重复扣款 |
| 与熔断组合 | 重试在外、熔断在内（见下节顺序）——**先熔断后重试顺序错了会雪上加霜** |
| 重试放大效应 | 100 请求 × 重试 3 次 = 300 次下游调用，**重试 + 限流/熔断一起配** |

## 6. 组合顺序：装饰器嵌套模型

### 6.1 官方推荐嵌套顺序

```text
Resilience4J 全部能力可以任意组合，官方推荐（从外到内）：
    Retry
      └── CircuitBreaker
            └── RateLimiter
                  └── TimeLimiter
                        └── Bulkhead
                              └── 实际调用

为什么？—— 外层做"策略决定"，内层做"资源保护"：
  ├── Retry 最外层：重试的是"整个被保护的调用"（包括熔断状态），先重试后熔断
  │     —— 若熔断在外：OPEN 抛 CallNotPermittedException 会被 Retry 重试 → 熔断形同虚设！
  ├── CircuitBreaker 次外：统计包含重试后的最终结果
  ├── RateLimiter 中层：限流在真正消耗资源前拦截
  ├── TimeLimiter 次内：给实际执行设超时
  └── Bulkhead 最内：限制并发执行，防资源耗尽
```

### 6.2 SCCB 里的组合现实

| 组合方式 | 说明 |
|---------|------|
| **SCCB 默认** | CircuitBreaker + TimeLimiter（starter 只带这两个模块） |
| 加 Bulkhead | 引 `resilience4j-bulkhead`，SCCB **自动包一层**（自动装配） |
| 加 RateLimiter/Retry | 引 `resilience4j-ratelimiter` / `resilience4j-retry`，用 Resilience4J 的 `Decorators.of(…)` 编程式组合 |
| 注解组合 | 引 `resilience4j-spring-boot3`，多注解叠加（@Retry 最外）——顺序见 [05 篇](05-注解开发与降级速查.md) |

```java
// 编程式五件套组合（引齐依赖后）
io.github.resilience4j.Decorators.ofSupplier(() -> downstream.call())
    .withRetry(retry)
    .withCircuitBreaker(circuitBreaker)
    .withRateLimiter(rateLimiter)
    .withTimeLimiter(timeLimiter, executorService)
    .withBulkhead(bulkhead)
    .get();
```

> ⚠️ **顺序反了的典型事故**：`Retry(CircuitBreaker())` 写成 `CircuitBreaker(Retry())`——熔断期间 Retry 还在疯狂重试被拒的调用（CallNotPermittedException 不计入失败统计但会反复触发），**下游没被打死，先把自己的重试队列打爆**。

## 7. 线程池隔离 vs 信号量隔离

### 7.1 原理对比

| 维度 | 线程池隔离（Hystrix 默认 / Bulkhead 线程池版） | 信号量隔离（Resilience4J 独立库默认） |
|------|----------------------------------------------|--------------------------------------|
| 核心思想 | 每依赖一个**独立线程池**，依赖之间线程完全隔离 | 每依赖一个**信号量计数**，共用业务线程 |
| 调用线程 | 提交任务后**线程切换**（业务线程不阻塞） | 业务线程**直接执行**（零切换） |
| 超时取消 | ✅ 能取消池内任务 | ⚠️ 只能中断业务线程（RestTemplate 场景受限于 IO 不可中断） |
| 上下文传递 | 需要手动传 ThreadLocal（traceId/用户态） | 天然同线程（**无上下文丢失**） |
| 资源开销 | 每依赖一个池（线程数 × 依赖数） | 无额外线程 |
| 适用 | 慢 IO、需要强超时取消、依赖间必须硬隔离 | 快速调用、轻量场景、性能敏感 |

### 7.2 面试结论

> 🎯 **"Hystrix 为什么默认线程池隔离，Resilience4J 为什么默认信号量？"**——Hystrix 诞生时 Java 线程池是唯一可靠隔离手段（且那时认为线程切换成本可接受）；Resilience4J 面向更现代的场景：**大多数内部 RPC 是毫秒级调用，线程切换是纯浪费**；且响应式时代"不阻塞线程"是基本要求，线程池隔离（阻塞模型）与响应式天然冲突——**信号量 + 超时 + 熔断的组合在绝大多数场景性价比更高**。

### 7.3 选择建议

| 场景 | 选 |
|------|-----|
| 内部 RPC（Feign 调微服务）、调用快 | 信号量隔离（默认） |
| 慢外部调用（第三方 API、支付网关） | 线程池隔离（可超时取消） |
| 响应式链路 | 无隔离概念（Reactor 本身非阻塞）——靠并发限制算子 |
| 需要 TraceId 传播 | 信号量（同线程）优先，线程池需手动传 |
