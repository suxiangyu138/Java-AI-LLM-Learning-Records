## 1. 重要澄清：@CircuitBreaker 到底是谁的

### 1.1 源码实证结论（2026-08，v5.0.2）

| 问题 | 结论 | 证据 |
|------|------|------|
| Spring Cloud 有官方 @CircuitBreaker 注解吗？ | **没有** | spring-cloud-commons 5.0.2 源码 grep：circuitbreaker 包下只有 Factory API + httpservice + observation，**无任何注解类**（[GitHub 源码](https://github.com/spring-cloud/spring-cloud-commons/tree/main/spring-cloud-commons/src/main/java/org/springframework/cloud/client/circuitbreaker)） |
| SCCB starter 带注解吗？ | **不带** | starter POM 实证：只依赖 resilience4j-circuitbreaker + resilience4j-timelimiter |
| 教程里的 @CircuitBreaker(fallbackMethod=…) 是什么？ | **Resilience4J 自己的注解** | `io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker`（resilience4j-spring-boot3） |
| 注解方案怎么引入？ | **单独引 resilience4j-spring-boot3** | 见 1.2 |

> ⚠️ 这个澄清很重要：**面试/写代码时区分清楚**——Spring Cloud 的官方编程方式是 `CircuitBreakerFactory.run()`（[02 篇](02-快速开始与编程式API速查.md)）；注解是 Resilience4J 的生态能力，SCCB 只是"恰好兼容"（Factory 与注解可共用同一份 yaml 实例配置）。

### 1.2 注解方案依赖

```xml
<!-- SCCB starter（Factory API 用） -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
</dependency>

<!-- 注解 + AOP + yaml 属性绑定（Resilience4J 官方 Boot 3 集成） -->
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot3</artifactId>
    <!-- 版本 2.3.0（与 SCCB 5.0.2 对齐）；独立最新 2.4.0 支持 Boot 4/Cloud 5 -->
</dependency>
```

> 💡 加完依赖**无需任何 @EnableXxx**——resilience4j-spring-boot3 自动装配注解切面（AspectJ + Spring AOP）；2.3.0 前的老文档要 `@EnableResilience4j`，那是 1.x 时代的写法。

## 2. Resilience4J 五注解速查

### 2.1 注解一览

| 注解 | 能力 | 对应 yaml 配置域 | 适用 |
|------|------|-----------------|------|
| `@CircuitBreaker` | 熔断 | resilience4j.circuitbreaker.instances | 下游故障保护 |
| `@Retry` | 重试 | resilience4j.retry.instances | 瞬时故障 |
| `@RateLimiter` | 限流 | resilience4j.ratelimiter.instances | 流量控制 |
| `@Bulkhead` | 隔离 | resilience4j.bulkhead / thread-pool-bulkhead.instances | 并发控制（`type` 可选手信号量/线程池） |
| `@TimeLimiter` | 超时 | resilience4j.timelimiter.instances | 超时控制（**需配合线程池/异步**） |

### 2.2 基础用法

```java
@Service
public class OrderService {
    @CircuitBreaker(name = "orderService", fallbackMethod = "fallback")
    public Order getOrder(Long id) {
        return restTemplate.getForObject("http://order-service/orders/" + id, Order.class);
    }

    public Order fallback(Long id, Throwable t) {   // ★ 签名 = 原方法参数 + Throwable
        return Order.empty("订单服务暂不可用");
    }
}
```

### 2.3 注解进阶属性

```java
@CircuitBreaker(
        name = "orderService",
        fallbackMethod = "fallback",
        group = "orderGroup",                    // 分组（对应 create(id, group)）
        ignoreExceptions = {ResourceNotFoundException.class},   // 这些异常不算失败
        recordExceptions = {IOException.class})                 // 只有这些异常算失败
public Order getOrder(Long id) { ... }

// 2.3.0 起：@RateLimiter 可指定所需令牌数
@RateLimiter(name = "orderService", fallbackMethod = "fallback", permits = 2)
```

## 3. fallbackMethod 规则详解

### 3.1 匹配规则

| 规则 | 说明 | 示例 |
|------|------|------|
| **同 Class** | fallback 方法必须在**同一个类**里（AOP 代理限制） | — |
| **签名匹配** | 参数 = 原方法参数 + 可选追加 `Throwable`（放最后） | `fallback(Long id, Throwable t)` |
| **最接近匹配** | 多个 fallback 时选与异常类型**最接近**的（catch 语义） | `fallback(Long, TimeoutException)` 优先于 `fallback(Long, Exception)` |
| **单参兜底** | 可只写一个 `Throwable` 参数（通用兜底） | `fallback(Throwable t)` |
| **返回值一致** | 返回类型必须与原方法一致 | — |
| 可见性 | 建议 public（非 public 可能受代理限制） | — |

### 3.2 行为语义（重要！）

```text
fallback 的触发时机 = "方法抛出异常"（任意时刻），不是"只有熔断时"！
  ├── CLOSED 状态：下游抛异常 → 也走 fallback ← ★ 最常见的认知误区
  ├── OPEN 状态：方法体不执行，直接走 fallback（抛 CallNotPermittedException）
  └── HALF_OPEN：试探请求成功则不触发，失败触发

fallback 里抛异常 → 调用方看到的是新异常（降级失败）——fallback 只做兜底，别抛错
```

> 🎯 面试必答：**"fallback 什么时候触发？"**——**任何被 record 的异常都触发**（含 CLOSED 状态的普通异常），不只是熔断期；熔断期的特殊点是"方法体不执行"（CallNotPermittedException 触发）。所以"熔断了才降级"是错误理解——**降级 = 失败兜底，熔断 = 失败更早发生**。

### 3.3 经典坑：自调用失效

```java
@Service
public class OrderService {
    public Order wrapper(Long id) {
        return getOrder(id);     // ❌ 自调用：this 调用不经过代理，注解 AOP 不生效！
    }

    @CircuitBreaker(name = "orderService", fallbackMethod = "fallback")
    public Order getOrder(Long id) { ... }   // 注解白写了
}
```

解决：注入自身代理（`@Lazy` 自注入）、拆到独立 Service、或用编程式 API。

## 4. 注解 AOP 与切面顺序

### 4.1 多注解叠加的默认顺序（官方 Aspect 顺序）

```text
Retry → CircuitBreaker → RateLimiter → TimeLimiter → Bulkhead → 方法体
  （外 → 内，与编程式组合推荐一致，见 04 篇）

例：
@Retry(name = "x", fallbackMethod = "fb")
@CircuitBreaker(name = "x", fallbackMethod = "fb")
@RateLimiter(name = "x", fallbackMethod = "fb")
public String call() { ... }
```

### 4.2 顺序调整

```yaml
resilience4j:
  retry:
    retry-aspect-order: 1          # 数值越小越靠外
  circuitbreaker:
    circuit-breaker-aspect-order: 2
  ratelimiter:
    rate-limiter-aspect-order: 3
```

> ⚠️ **混用警告**：同一个方法上**不要同时**用 SCCB 编程式 `run()` 包裹 + 注解——双重拦截双重统计，fallback 嵌套混乱；选一种。

## 5. OpenFeign 集成：feign.circuitbreaker

### 5.1 配置

```yaml
feign:
  circuitbreaker:
    enabled: true          # ★ 开启后所有 @FeignClient 自动包熔断器
  # 熔断器实例名 = FeignClient 的 name（serviceId）
```

```java
@FeignClient(name = "payment-service",
        fallback = PaymentClientFallback.class,          // 方式一：fallback 类
        fallbackFactory = PaymentClientFallbackFactory.class)  // 方式二（推荐）：可拿异常原因
public interface PaymentClient {
    @GetMapping("/payments/{id}")
    Payment getPayment(@PathVariable Long id);
}

// fallback 实现（必须注册为 Bean；错误场景可拿具体异常）
@Component
public class PaymentClientFallback implements PaymentClient {
    @Override
    public Payment getPayment(Long id) {
        return Payment.empty();     // 兜底空对象
    }
}

// fallbackFactory（推荐：保留异常上下文）
@Component
public class PaymentClientFallbackFactory implements FallbackFactory<PaymentClient> {
    @Override
    public PaymentClient create(Throwable cause) {
        log.warn("payment-service 调用失败", cause);
        return new PaymentClient() {
            @Override public Payment getPayment(Long id) {
                return Payment.empty();
            }
        };
    }
}
```

### 5.2 熔断器命名与配置

```yaml
resilience4j:
  circuitbreaker:
    instances:
      payment-service:              # ★ 就是 @FeignClient 的 name
        sliding-window-size: 20
        minimum-number-of-calls: 5
        failure-rate-threshold: 50
  timelimiter:
    instances:
      payment-service:
        timeout-duration: 3s
```

> 💡 fallback vs fallbackFactory：**fallback 简单但拿不到异常**；**fallbackFactory 能拿到 cause**（打日志/判断是否重试）——生产推荐 fallbackFactory。

## 6. Spring Cloud Gateway 集成

### 6.1 依赖与配置

```xml
<!-- Gateway 项目里加 reactor 版 starter -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-reactor-resilience4j</artifactId>
</dependency>
```

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-route
          uri: lb://order-service
          predicates: [Path=/orders/**]
          filters:
            - name: CircuitBreaker          # ★ 网关级熔断过滤器
              args:
                name: orderCircuitBreaker   # 熔断器实例名
                fallbackUri: forward:/fallback/order   # ★ 熔断/失败时转发到本地降级端点
            - name: Retry                   # 可与重试过滤器组合
              args:
                retries: 2
                statuses: [SERVICE_UNAVAILABLE]
```

```java
@RestController
public class FallbackController {
    @GetMapping("/fallback/order")
    public String orderFallback() {
        return "订单服务暂不可用，请稍后再试";
    }
}
```

### 6.2 网关熔断 vs 服务内熔断

| 维度 | 网关级（Gateway） | 服务内（Feign/Factory） |
|------|------------------|----------------------|
| 位置 | 入口统一保护 | 调用点就近保护 |
| 降级粒度 | 路由级（整个服务） | 方法级（精细） |
| 适用 | 统一兜底页面/全局入口限流 | 业务级差异化降级 |

> 🎯 架构原则：**网关熔断管"入口"，服务内熔断管"出口"**——两者不互斥，生产常同时配（网关兜底 UI，服务内兜底业务）。

## 7. HttpServiceFallback：声明式 HTTP 服务降级（5.x 新增）

### 7.1 背景

Spring Cloud 5.x 支持**声明式 HTTP 服务**（RestClient/WebClient 版 @HttpExchange），SCCB 5.x 为它提供自动熔断装饰（`spring-cloud-commons` 的 httpservice 模块，默认开启）。

### 7.2 用法

```java
// ① 定义 HTTP 服务（Spring Framework 7 声明式客户端）
public interface OrderServiceClient {
    @HttpExchange("/orders/{id}")
    Order getOrder(@PathVariable Long id);
}

// ② 声明降级配置类
@Configuration
@HttpServiceFallback(value = OrderServiceFallbacks.class, service = OrderServiceClient.class)
public class FallbackConfig { }

// ③ 降级实现（方法名/参数签名与原接口一致；可追加 Throwable 参数）
public class OrderServiceFallbacks {
    public Order getOrder(Long id) { return Order.empty(); }
    public Order getOrder(Long id, Throwable cause) { return Order.empty("cause=" + cause.getMessage()); }
}
```

### 7.3 匹配优先级

```text
① 同时匹配 service + group 的 fallback
② 只匹配 service（无 group）
③ 无 service/group 的全局兜底
关闭：spring.cloud.circuitbreaker.http-services.enabled=false
```

> 💡 与 @FeignClient 的关系：**都是声明式客户端**——@HttpExchange 是 Framework 7 原生（Spring AI/REST Client 生态），Feign 是 Netflix 遗产；新项目可以开始用 @HttpExchange + HttpServiceFallback，存量 Feign 项目保持 Feign fallback 即可（[08 篇](08-生产实践与选型避坑.md) 趋势）。
