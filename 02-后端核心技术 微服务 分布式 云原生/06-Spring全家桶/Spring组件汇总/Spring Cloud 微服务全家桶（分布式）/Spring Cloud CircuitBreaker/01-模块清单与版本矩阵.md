## 1. 模块组成

| 模块 | 类型 | 职责 | 引入方 |
|------|------|------|--------|
| **spring-cloud-commons** | 核心抽象层 | `CircuitBreakerFactory`/`CircuitBreaker`/`ReactiveCircuitBreakerFactory` 接口 + 自动装配（有 starter 时自动创建 Factory Bean） | 传递依赖（starter 内含） |
| **spring-cloud-starter-circuitbreaker-resilience4j** | starter | Resilience4J 实现（阻塞式）：熔断+超时+隔离+限流+重试 | **默认实现，推荐入口** |
| **spring-cloud-starter-circuitbreaker-reactor-resilience4j** | starter | Resilience4J 响应式实现（WebFlux/WebClient：Mono/Flux） | 响应式项目 |
| **spring-cloud-starter-circuitbreaker-spring-retry** | starter | Spring Retry 实现（RetryTemplate 状态机） | 维护模式，存量使用 |
| **spring-cloud-starter-circuitbreaker-framework-retry** | starter | **Framework Retry 实现（5.0 新增）**：Spring Framework 7 原生 retry 状态机，仅阻塞式 | Boot 4 新项目可选 |
| spring-cloud-circuitbreaker-* | 实现库 | 上面 starter 背后的实现模块（resilience4j / spring-retry / framework-retry） | starter 传递依赖 |
| resilience4j-spring-boot3 | 外部库 | Resilience4J 官方 Boot 集成：**注解 AOP（@CircuitBreaker 等）**、yaml 属性绑定 | **需单独引入**（SCCB starter 不含它！） |

> 💡 接入口诀：**阻塞式选 `starter-circuitbreaker-resilience4j`，响应式选 `starter-circuitbreaker-reactor-resilience4j`**；抽象层（commons）与实现库都是传递依赖，无需单独引。

> ⚠️ **最常见误解**：以为 SCCB starter 自带 `@CircuitBreaker` 注解——**SCCB 官方没有注解**（源码中只有 Factory API，见 [05 篇](05-注解开发与降级速查.md)）；要用注解必须**额外**引 `io.github.resilience4j:resilience4j-spring-boot3`（该注解是 Resilience4J 自己的）。

## 2. 核心包结构

### 2.1 抽象层（spring-cloud-commons，5.0.2 源码实证）

```text
org.springframework.cloud.client.circuitbreaker
├── CircuitBreaker                  # ★ 接口：run(Supplier) / run(Supplier, Function<Throwable,T>)
├── ReactiveCircuitBreaker          # 响应式接口：run(Mono/Flux, fallback)
├── CircuitBreakerFactory           # ★ 阻塞式工厂：create(id) / create(id, group)
├── ReactiveCircuitBreakerFactory   # 响应式工厂
├── AbstractCircuitBreakerFactory   # 基类：configureDefault / configure(builder, id...) / 全局 Customizer 管
├── ConfigBuilder                   # 配置构建器接口（各实现提供自己的 Builder）
├── Customizer                      # 配置回调接口（@Bean 注入即生效）
├── NoFallbackAvailableException    # 无 fallback 时 run() 抛出
├── httpservice/                    # 5.x 新增：RestClient/WebClient 声明式 HTTP 服务熔断装饰（@HttpServiceFallback）
└── observation/                    # Micrometer Observation 集成（可观测性）
```

> 🎯 关键认知：**抽象层不实现任何熔断逻辑，只定义"创建-运行"契约**；真正状态机在 Resilience4J（`io.github.resilience4j.circuitbreaker.CircuitBreaker`）里——SCCB 的 `Resilience4JCircuitBreaker` 只是薄封装（把 Resilience4J 的状态机包成统一的 `CircuitBreaker` 接口）。

### 2.2 Resilience4J 实现（spring-cloud-circuitbreaker-resilience4j）

```text
org.springframework.cloud.circuitbreaker.resilience4j
├── Resilience4JCircuitBreaker             # 阻塞式实现（内部包 resilience4j 的 CircuitBreaker + TimeLimiter）
├── ReactiveResilience4JCircuitBreaker     # 响应式实现（Mono/Flux）
├── Resilience4JCircuitBreakerFactory      # 阻塞式工厂（自动装配的主 Bean）
├── ReactiveResilience4JCircuitBreakerFactory
└── Resilience4JConfigBuilder              # configureDefault/configure 用的 Builder
    ├── circuitBreakerConfig(CircuitBreakerConfig)   # 熔断状态机参数
    └── timeLimiterConfig(TimeLimiterConfig)         # 超时参数
```

### 2.3 Resilience4J 核心库（io.github.resilience4j，2.3.0）

```text
io.github.resilience4j
├── circuitbreaker          # ★ 熔断器：状态机 + 滑动窗口 + EventPublisher
├── timelimiter             # 超时限制（TimeLimiter）
├── bulkhead                # 隔离：SemaphoreBulkhead / ThreadPoolBulkhead
├── ratelimiter             # 限流：令牌桶（RateLimiter）
├── retry                   # 重试（Retry）
├── spring-boot3            # Boot 3 集成：注解 AOP + 属性绑定（单独引）
├── micrometer              # 指标接入（与 actuator 搭配）
└── feign                   # Feign 装饰器（一般随 OpenFeign 集成走）
```

> 💡 依赖关系记忆：**starter（SCCB）→ spring-cloud-circuitbreaker-resilience4j → resilience4j-circuitbreaker + resilience4j-timelimiter**（POM 实证：5.0.2 starter 只带这两个模块）；Bulkhead/RateLimiter/Retry 需自行引入或用 `resilience4j-spring-boot3` 全家桶。

## 3. 依赖坐标与边界

### 3.1 官方坐标（Maven Central，5.0.2 实证）

```xml
<!-- ① 阻塞式默认实现（Boot 4 + Cloud 2025.1） -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
</dependency>

<!-- ② 响应式实现 -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-reactor-resilience4j</artifactId>
</dependency>

<!-- ③ 注解支持（需要才加，SCCB starter 不含！） -->
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot3</artifactId>
    <!-- 版本 2.3.0 与 SCCB 对齐；独立最新 2.4.0（支持 Boot 4/Cloud 5） -->
</dependency>

<!-- 版本管理：Spring Cloud BOM（不写 version，由 BOM 锁） -->
<dependencyManagement>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-dependencies</artifactId>
        <version>2025.1.2</version>       <!-- 与 Boot 4 对应的 Cloud 版本 -->
        <type>pom</type><scope>import</scope>
    </dependency>
</dependencyManagement>
```

### 3.2 依赖边界

| 边界 | 说明 |
|------|------|
| **SCCB 版本 ↔ Cloud release train** | 5.0.x↔2025.1.x（Boot 4）；3.3.x↔2025.0.x（Boot 3.5）——**错配启动即失败**（compatibility verifier） |
| 版本由 Spring Cloud BOM 管理 | 不手写 version，用 spring-cloud-dependencies BOM 对齐 |
| 阻塞/响应式二选一 | 同用 resilience4j 可共存（Factory 类型不同），但别同时引 spring-retry 与 resilience4j 两套实现（有多个 Factory 冲突） |
| Resilience4J 版本可覆盖 | SCCB 5.0.2 钉 2.3.0；独立库 2.4.0 已发布（Boot 4/Cloud 5 兼容、ignoreExceptions 优先级修复）——**覆盖需自行验证** |
| 无业务依赖 | 不引业务库（纯调用保护） |

> ⚠️ **最常见的坑**：Boot 3.5 项目引 SCCB `5.0.x`（或 Boot 4 项目引 3.3.x）——**启动直接失败**（版本不兼容校验）；版本永远跟着 Spring Cloud BOM 走，别单独钉 SCCB 版本。

## 4. 版本兼容矩阵（2026-08）

### 4.1 SCCB ↔ Spring Cloud ↔ Boot ↔ Resilience4J（权威组合）

| Spring Cloud | SCCB | Boot | Resilience4J | JDK | 备注 |
|--------------|------|------|--------------|-----|------|
| **2025.1.x（Oakwood）** | **5.0.x（5.0.2）** | **4.0.x/4.1.x** | **2.3.0**（2.4.0 可覆盖） | 17+ | **当前主线**；新增 Framework Retry；跳过 4.0.x |
| 2025.0.x（Northfields） | 3.3.x | 3.5.x | 2.2.x/2.3.x | 17 | OSS 已于 2026-06-30 EOL |
| 2024.0.x（Moorgate） | 3.2.x | 3.4.x | 2.1.x/2.2.x | 17 | EOL |
| 2023.0.x（Leyton） | 3.1.x | 3.2.x/3.3.x | 2.0.x/2.1.x | 17 | EOL |
| 2022.0.x（Kilburn） | 3.0.x | 3.0.x/3.1.x | 1.7.x | 8/11/17 | 老存量（Boot 3 首线） |
| 2021.0.x（Jubilee） | 2.1.x | 2.6.x/2.7.x | 1.7.x | 8/11 | 老存量（javax） |
| 2020.0.x（Ilford） | 2.0.x | 2.4.x/2.5.x | 1.5.x | 8 | 老存量（javax） |
| Hoxton | 1.0.x | 2.2.x/2.3.x | —（Hystrix 实现） | 8 | 废弃 |

> ⚠️ **为什么没有 4.0.x**：2025.1 发布列车全组件统一升 5.0.0，SCCB 官方明确"moved to 5.0.x to align with the rest of the release train, **skipping version 4.0.x**"——看到"4.x"的教程基本是误传，别信。

### 4.2 快速对齐口诀

| 场景 | 推荐组合 |
|------|---------|
| 新项目（Boot 4.0/4.1） | Spring Cloud 2025.1.x + SCCB 5.0.x + JDK 17+ |
| 存量 Boot 3.5（计划升级） | 现状 3.3.x → **尽快迁 2025.1.x**（Northfields OSS 已结束） |
| 存量 Boot 3.4 | SCCB 3.2.x（EOL，建议升级） |
| 老 Boot 2.7 项目 | SCCB 2.1.x（**别硬升 SCCB，先升 Boot 全家桶**） |

> ⚠️ **升级路径**：3.3.x → 5.0.x 是**大版本跳升**（Boot 3.5→4、javax→jakarta 已完成、Framework 7）——建议走 release train 整批升级（Boot + Cloud + SCCB 一起），单点升 SCCB 一定错配。升级注意：若用了 Spring Retry 实现，评估迁移到 Resilience4J 或 Framework Retry（[07 篇](07-Framework Retry与Spring Retry对比.md)）。

### 4.3 Resilience4J 版本演进（独立库）

| 版本 | 里程碑 |
|------|--------|
| 1.x（2019-2023） | Boot 2 时代（resilience4j-spring-boot2），随 SCCB 3.x 前身使用 |
| 2.0（2024 初） | 大版本：Java 17 基线、模块重组 |
| 2.2.x（2025） | 性能与稳定性迭代 |
| **2.3.0**（2025 末） | ★ SCCB 5.0.2 锁定版：**虚拟线程 pinning 修复**（synchronized→ReentrantLock）、**无锁滑动窗口**（高并发吞吐）、自定义 Clock（测试友好）、RxJava3 支持、Feign 12.5+ |
| **2.4.0**（2026 中） | 独立库最新：**Boot 4/Cloud 5 兼容支持**、SpEL 组件命名、`ignoreExceptions` 优先于 `recordExceptions`（修复）、HALF_OPEN→CLOSED 可配置、TimeLimiter 注册表 Builder、JDK 21 构建基线 |

> 🎯 面试考点：**2.3.0 的"虚拟线程 pinning 修复"**——虚拟线程下 synchronized 会导致 pinning（钉死载体线程），Resilience4J 把内部锁换成 ReentrantLock 规避；这提示**虚拟线程项目要留意第三方库的锁实现**（[04 篇](04-弹性能力全景：隔离超时重试限流.md)）。

## 5. 实现选型（三套实现怎么选）

| 维度 | Resilience4J（默认） | Spring Retry | Framework Retry（5.0 新增） |
|------|---------------------|--------------|---------------------------|
| 状态机 | 完整三态+滑动窗口统计 | 三态（RetryTemplate 状态机） | 三态（Framework 7 原生） |
| 超时 | TimeLimiter ✅ | 需配 TimeoutRetryPolicy | 无内建超时（Framework 7 RetryPolicy 只有重试语义） |
| 隔离 | Bulkhead（信号量/线程池）✅ | ❌ | ❌ |
| 限流 | RateLimiter ✅ | ❌ | ❌ |
| 重试 | Retry ✅ | ✅ 本职 | ✅ 本职（RetryPolicy） |
| 响应式 | ✅ reactor starter | ❌ | ❌（官方明确不支持） |
| 注解 | ✅（引 resilience4j-spring-boot3） | ✅（@Retryable 等 Spring Retry 注解） | @Retryable（Framework 7 原生） |
| 依赖 | resilience4j 全家桶（最重） | spring-retry（轻） | 零依赖（Framework 7 自带） |
| 维护状态 | ✅ 活跃 | ⚠️ **维护模式**（停产即移除） | ✅ 新秀（5.0 起） |
| 适用 | **通用默认**（能力最全） | 存量项目、只需"重试+熔断" | Boot 4 新项目、想要零依赖轻量熔断 |

> 🎯 选型原则：**新项目无脑 Resilience4J**（能力全覆盖、生态最成熟）；**Boot 4 且只需要"重试+熔断"的轻量场景**可以考虑 Framework Retry（零依赖）；Spring Retry 只在存量迁移完成前用（[07 篇](07-Framework Retry与Spring Retry对比.md) 详细对比）。

## 6. 模块选型建议

| 场景 | 推荐 | 理由 |
|------|------|------|
| 阻塞式微服务（Feign/RestTemplate） | `starter-circuitbreaker-resilience4j` | 默认实现，能力全 |
| 响应式（WebFlux/WebClient） | `starter-circuitbreaker-reactor-resilience4j` | Mono/Flux 原生 |
| 需要注解开发 | 上述任一 + `resilience4j-spring-boot3` | SCCB 无官方注解，注解来自 Resilience4J |
| Boot 4 轻量场景（只需重试+熔断） | `starter-circuitbreaker-framework-retry` | 零依赖、Framework 7 原生 |
| 存量 Spring Retry 用户 | `starter-circuitbreaker-spring-retry` | 维护模式，过渡期可留 |
| 国内 SCA 生态 | **Sentinel**（spring-cloud-starter-alibaba-sentinel） | 控制台/规则持久化更完善（[08 篇](08-生产实践与选型避坑.md)） |
| 需要限流+熔断+持久化规则 | Resilience4J（单机）+ 配置中心，或直接 Sentinel | SCCB 无控制台 |
