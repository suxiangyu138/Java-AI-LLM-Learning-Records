## 1. 接入清单：哪些调用必须包熔断器

| 调用类型 | 必接？ | 说明 |
|---------|:---:|------|
| 微服务间 RPC（Feign） | ✅ | 最核心：任意下游故障都影响本服务 |
| 外部第三方 API | ✅ | 不可控依赖（支付/短信/地图），超时+熔断是底线 |
| 数据库/Redis 访问 | ⚠️ | 通常不包（连接池自带保护）；但可对"慢查询兜底"用 TimeLimiter |
| 本地方法调用 | ❌ | 无网络边界，熔断无意义 |
| 消息消费者 | ⚠️ | 消费失败应进死信/重试队列，不是熔断（MQ 领域） |
| 网关路由 | ✅ | 网关级熔断兜底（[05 篇](05-注解开发与降级速查.md)） |

> 🎯 原则：**每个"网络边界"都是一个熔断器**——服务间调用、外部 API、网关路由各配一个独立实例（名字=服务名），独立统计独立熔断，别共用。

## 2. 参数调优节奏与基线

### 2.1 四步调优节奏

```text
① 先跑通：minimum-number-of-calls 调小（5-10），窗口 20，阈值 50 —— 验证链路
② 再对齐：TimeLimiter timeout-duration 与下游 P99 对齐（P99×1.5~2，见 2.2）
③ 后收紧：慢调用阈值 < 超时；窗口 100；半开 5；waitDuration 30s
④ 持续调：按监控数据（失败率/慢调用率）每月复盘，避免"拍脑袋参数"
```

### 2.2 超时链对齐（最关键的参数关系）

```text
下游接口 P99 = 800ms
  ├── 本层 TimeLimiter timeout-duration：1.5s（P99×2 留余量）
  ├── 上游（网关/调用方）超时：3s（大于本层，避免上游先断）
  └── 慢调用 slow-call-duration-threshold：1.5s（≤ 超时，才能提前统计慢）
违反后果：超时 1s 但慢调用阈值 60s → 慢调用永远统计不到 → 慢导致的熔断失效
```

### 2.3 参数速查基线

| 参数 | 基线 | 说明 |
|------|------|------|
| timeout-duration | P99×2 | 别用默认 1s |
| slow-call-duration-threshold | = timeout 或略小 | 慢调用先行统计 |
| sliding-window-size | 100（或 P99 流量×2） | 样本足够即可 |
| minimum-number-of-calls | 20（测试期 5） | 防小样本误判 |
| failure-rate-threshold | 50 | 业务敏感可 30 |
| wait-duration-in-open-state | 30s | 默认 60s 偏长 |
| permitted-number-of-calls-in-half-open-state | 3-5 | 试探数 |
| retry max-attempts | 3 | 只重试瞬时异常（[04 篇](04-弹性能力全景：隔离超时重试限流.md)） |

## 3. 监控与告警

### 3.1 监控三层

| 层 | 手段 | 内容 |
|----|------|------|
| 指标 | Micrometer + Grafana（[06 篇](06-配置属性速查.md) 6.2） | failure_rate、state、calls 分布 |
| 事件 | EventPublisher 监听（[03 篇](03-熔断原理：状态机与滑动窗口.md) 5.1） | 状态转换、失败率超阈值 |
| 日志 | `logging.level.io.github.resilience4j=INFO` | 状态转换日志 |

### 3.2 告警规则建议

| 告警 | 级别 | 条件 |
|------|------|------|
| 熔断开启 | P1（立即） | `state` 出现 OPEN / health 变 OUT_OF_SERVICE |
| 预熔断 | P2 | failure_rate > 30%（持续 5 分钟） |
| 半开振荡 | P2 | 半小时内 OPEN→HALF_OPEN 循环 > 3 次（下游恢复不稳） |
| 拒绝量突增 | P3 | CallNotPermitted 计数异常上升 |

### 3.3 复盘模板

```text
一次熔断事故复盘四问：
  ① 触发源：失败率还是慢调用率？（看 failure_rate / slow_call_rate）
  ② 触发根因：下游故障？超时配置过紧？（对齐 P99 重新算）
  ③ 熔断效果：恢复时间？（OPEN 到 CLOSED 的总时长 = 故障持续 + waitDuration）
  ④ 降级体验：fallback 返回是否可接受？（是否该用缓存数据而不是固定文案）
```

> ⚠️ **生产事故提醒**：`register-health-indicator: true` 时熔断器 OPEN 会让 **health 变 OUT_OF_SERVICE，注册中心探活会摘除实例**——如果不想"熔断=下线"，要么关掉 indicator，要么把 circuitBreakers 从探活排除（常见误配事故）。

## 4. 坑位表：10 大高频坑

| # | 坑 | 现象 | 解法 |
|---|-----|------|------|
| 1 | **create 名字与 yaml 实例名不一致** | 熔断"不生效"（全走默认配置） | 打印 cb.getName() 核对；Feign 场景 = @FeignClient name |
| 2 | **默认 minimum-number-of-calls=100** | 测试/低流量永远不熔断 | 测试期配 5；生产按流量算 |
| 3 | **默认 timeout-duration=1s** | 正常慢接口全超时降级 | 按 P99×2 显式配置 |
| 4 | **fallback 里抛异常** | 用户看到 500 不是兜底 | fallback 只返回兜底值，别抛 |
| 5 | **注解与 Factory 双重包裹** | 双重统计、fallback 嵌套 | 一个调用点选一种（[05 篇](05-注解开发与降级速查.md)） |
| 6 | **自调用导致注解失效** | 注解方法被同类方法调 → 不熔断 | @Lazy 自注入 / 拆独立 Service / 用 Factory API |
| 7 | **重试与熔断顺序反了** | 熔断期重试疯狂触发，下游雪上加霜 | Retry 在外、CircuitBreaker 在内（[04 篇](04-弹性能力全景：隔离超时重试限流.md) 6.1） |
| 8 | **重试了非幂等写接口** | 重复下单/重复扣款 | 写接口不重试或必须幂等设计 |
| 9 | **register-health-indicator 导致实例被摘除** | 熔断时实例下线，流量全部转移 | 评估探活口径（见 3.3） |
| 10 | **混淆 @CircuitBreaker 来源** | 以为 SCCB 自带注解，没引 resilience4j-spring-boot3 → 编译不过/不生效 | 引依赖；区分 Spring Cloud Factory API 与 Resilience4J 注解（[05 篇](05-注解开发与降级速查.md) 1.1） |

> 💡 排障口诀：**"名字对不对 → 参数够不够（样本数）→ 异常算不算（record/ignore）→ 有没有重复包裹"**——按这个顺序查，80% 的问题在前两步。

## 5. vs Sentinel：全维度选型

### 5.1 对比表

| 维度 | Resilience4J（SCCB 默认） | Sentinel（SCA） |
|------|--------------------------|-----------------|
| 出身 | Spring Cloud 官方默认实现 | 阿里开源（SBA） |
| 生态 | 官方 Cloud / Boot 全系 | Spring Cloud Alibaba |
| 熔断 | 状态机+滑动窗口（失败率/慢调用率） | 滑动窗口（慢调用比例/异常比例/异常数） |
| 限流 | RateLimiter 单机令牌桶 | 流量整形/预热/热点参数/集群流控（更强） |
| 隔离 | Bulkhead 信号量/线程池 | 线程池/信号量隔离（兼容模式） |
| 控制台 | ❌ | ✅ 可视化控制台（实时监控+规则管理） |
| 规则持久化 | 配置中心（自接） | ✅ 数据源（Nacos/Apollo） |
| 规则热更新 | 接配置中心可热更新 | ✅ 控制台实时下发 |
| 响应式 | ✅ reactor starter | ⚠️ 支持有限 |
| 运维成本 | 低（纯库） | 中（需部署控制台+依赖 SCA） |
| 适用 | 官方生态、代码级控制、轻量 | 阿里生态、要控制台、要规则治理 |

### 5.2 决策建议

```text
选 Resilience4J：
  ├── 用官方 Spring Cloud 全家桶（Gateway/OpenFeign/Config）
  ├── 团队代码能力强，规则交给 yaml/配置中心
  └── 只需单机熔断限流

选 Sentinel：
  ├── 已在 SCA 生态（Nacos 注册/配置）
  ├── 需要控制台可视化 + 规则热下发 + 集群流控
  └── 国内团队运维习惯（阿里系文档/社区）

不推荐：双轨混用（同项目同时引两套熔断）——规则心智负担翻倍
```

> 🎯 面试结论：**"Sentinel 和 Resilience4J 怎么选？"**——看生态：官方 Cloud 栈选 Resilience4J（更轻、代码级、响应式好）；阿里 SCA 栈选 Sentinel（控制台、规则持久化、集群流控更完善）；两者理念同源（都防雪崩），实现差异在**统计模型、控制台、规则下发**三大块。

## 6. 升级路径：3.3.x → 5.0.x

### 6.1 升级必要性判断

| 现状 | 判断 |
|------|------|
| Spring Cloud 2025.0.x（Boot 3.5）+ SCCB 3.3.x | **建议升级**：Northfields OSS 已于 2026-06-30 结束 |
| Spring Cloud 2024.0.x（Boot 3.4）+ SCCB 3.2.x | **建议升级**：Moorgate 已 EOL |
| Spring Cloud 2023.0.x（Boot 3.2/3.3）+ SCCB 3.1.x | 计划升级（Leyton EOL） |
| Boot 2.7 + SCCB 2.1.x | 大工程，先规划 Boot 升 4 |

### 6.2 升级 Checklist

```text
□ 1. 整批升级：Boot 3.5→4.x + Cloud 2025.0→2025.1（不要单点升 SCCB）
□ 2. 依赖核对：starter 坐标不变，版本由新 BOM 锁 5.0.x
□ 3. 代码兼容：
     - jakarta 命名空间（Boot 4 已是，确认无 javax import）
     - @HttpExchange/@HttpServiceFallback 新特性可选用
     - Resilience4J 2.3.0：无 API 破坏（Factory API 不变）
□ 4. 实现核对：
     - 用 Spring Retry 实现的 → 评估迁 Framework Retry / Resilience4J（07 篇）
     - 用 Resilience4J 的 → yaml 属性不变，直接跑
□ 5. 回归验证：熔断触发/恢复/fallback 全链路（02 篇验证清单）
□ 6. 新特性收益：Framework Retry 零依赖实现可试用（Boot 4 新项目）
```

### 6.3 升级风险提示

| 风险 | 说明 |
|------|------|
| 版本错配启动失败 | 2025.1 的 compatibility verifier 会直接拒启动（别用禁用开关硬跑） |
| Resilience4J 覆盖到 2.4.0 | 非必需（2.3.0 足够）；覆盖前读 release notes（HALF_OPEN 转换可配等新行为） |
| 行为变化 | 2.3.0 无锁滑动窗口在高并发下吞吐变化——压测回归 |
| 虚拟线程 | 2.3.0 已修 pinning（ReentrantLock），虚拟线程项目直接受益（[01 篇](01-模块清单与版本矩阵.md) 4.3） |
