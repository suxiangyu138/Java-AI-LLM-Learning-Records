## 1. 属性总览与命名规则

### 1.1 五大配置域

| 配置域 | 管理的能力 | 来源 |
|--------|-----------|------|
| `resilience4j.circuitbreaker.*` | 熔断状态机 | resilience4j-spring-boot3 属性绑定 |
| `resilience4j.timelimiter.*` | 超时 | 同上 |
| `resilience4j.thread-pool-bulkhead.*` | 线程池隔离 | 同上 |
| `resilience4j.bulkhead.*` | 信号量隔离 | 同上 |
| `resilience4j.ratelimiter.*` | 限流 | 同上 |
| `resilience4j.retry.*` | 重试 | 同上 |

### 1.2 结构规则

```yaml
resilience4j:
  <能力>:
    configs:            # ★ 命名配置（default 是兜底；其他名字 = 分组）
      default:          # 所有实例的默认值
        <属性>: <值>
      <组名>:           # 分组配置（create(id, group) 或注解 group 指定）
        <属性>: <值>
    instances:          # ★ 具体实例（熔断器名字）
      <实例名>:         # = create("名字") / @CircuitBreaker(name=) / FeignClient name
        <属性>: <值>     # 只写要覆盖的，其余从 configs 继承
```

> 🎯 记忆口诀：**configs 是"模板库"，instances 是"实例表"**——实例没有的属性按 分组 → default → 出厂默认 逐级找。

## 2. circuitbreaker 属性全表

| 属性（yaml 驼峰→短横线） | 默认值 | 语义 | 面试价值 |
|--------------------------|--------|------|:---:|
| `sliding-window-type` | COUNT_BASED | 窗口类型：COUNT_BASED / TIME_BASED | ★★★ |
| `sliding-window-size` | 100 | 窗口大小（次数或秒数） | ★★★ |
| `failure-rate-threshold` | 50 | 失败率阈值 %（≥ 即熔断） | ★★★ |
| `minimum-number-of-calls` | 100 | 判定最少调用数（样本不足不算） | ★★★ |
| `wait-duration-in-open-state` | 60s | OPEN 停留时长 → 转 HALF_OPEN | ★★★ |
| `permitted-number-of-calls-in-half-open-state` | 3 | 半开试探请求数 | ★★ |
| `max-wait-duration-in-half-open-state` | 0（无限） | 半开停留上限 | ★ |
| `slow-call-duration-threshold` | 60s | 慢调用判定阈值 | ★★ |
| `slow-call-rate-threshold` | 100 | 慢调用率阈值 %（≥ 即熔断） | ★★ |
| `record-exceptions` | 空（全部记录） | 白名单：只这些异常算失败 | ★★ |
| `ignore-exceptions` | 空 | 黑名单：这些异常不算失败（**但算调用数**） | ★★★ |
| `record-failure-predicate` | 空 | 自定义判定（类名，实现 Predicate<Throwable>） | ★ |
| `record-result-predicate` | 空 | 按返回结果判定失败（Java 类） | ★ |
| `automatic-transition-from-open-to-half-open` | false | OPEN 到点自动转 HALF_OPEN（true）或调用触发 | ★ |
| `register-health-indicator` | false | 暴露 /actuator/health 子状态 | ★★ |
| `event-consumer-buffer-size` | 100 | 事件缓冲（丢了说明消费慢） | ★ |
| `sliding-window-size` 与 LOCK_FREE | — | 2.3.0 无锁模式仅 COUNT_BASED（TIME_BASED 组合校验失败） | ★★ |

### 2.1 关键属性语义举例

```yaml
resilience4j:
  circuitbreaker:
    instances:
      payment-service:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 50            # 统计最近 50 次
        minimum-number-of-calls: 10        # 够 10 次才开始判定
        failure-rate-threshold: 50         # 50 次里失败 ≥ 25 次 → OPEN
        slow-call-duration-threshold: 5s   # 超过 5s 算慢
        slow-call-rate-threshold: 60       # 慢调用占 60% 也熔断（双通道触发）
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 3
        ignore-exceptions:
          - com.example.OrderNotFoundException   # 404 类业务异常不算失败
```

> ⚠️ **ignore vs record 陷阱**：`ignore-exceptions` 的异常**计入调用总数**（分母）但不计失败——调 100 次全 ignore，分母 100、失败 0，**不会熔断**，但半开/统计正常；`record-exceptions` 是白名单（只列出的算失败），与 ignore 冲突时 **2.4.0 起 ignore 优先**。

## 3. timelimiter / bulkhead / ratelimiter / retry 属性表

### 3.1 timelimiter

| 属性 | 默认值 | 语义 |
|------|--------|------|
| `timeout-duration` | **1s**（激进，必改） | 超时上限 |
| `cancel-running-future` | true | 超时后取消/中断 Future |

### 3.2 thread-pool-bulkhead（SCCB 默认隔离方式）

| 属性 | 默认值 | 语义 |
|------|--------|------|
| `max-thread-pool-size` | 10 | 最大线程数（到达即隔离点） |
| `core-thread-pool-size` | 10 | 核心线程数 |
| `queue-capacity` | 100 | 排队容量（满 → 拒绝 BulkheadFullException） |
| `keep-alive-duration` | 20ms | 非核心线程回收时间 |
| `max-wait-duration` | 0 | 排队等待上限（0 = 不等待直接拒） |
| `writable-stack-trace-enabled` | true | 线程栈可写 |

### 3.3 bulkhead（信号量，需开启 enableSemaphoreDefaultBulkhead）

| 属性 | 默认值 | 语义 |
|------|--------|------|
| `max-concurrent-calls` | 25 | 最大并发数 |
| `max-wait-duration` | 0 | 拿信号量等待上限（0 = 立即拒绝） |
| `fair-call-handling-strategy` | — | 公平/非公平获取策略 |

### 3.4 ratelimiter

| 属性 | 默认值 | 语义 |
|------|--------|------|
| `limit-for-period` | 50 | 每周期令牌数 |
| `limit-refresh-period` | 500ns（默认极短） | 令牌补充周期（务必配成业务 QPS 口径） |
| `timeout-duration` | 5s | 等令牌上限（超时抛 RequestNotPermitted） |
| `drain-permissions-on-result` | false | 按结果"归还"权限（2.3.0 起注解生效） |

### 3.5 retry

| 属性 | 默认值 | 语义 |
|------|--------|------|
| `max-attempts` | 3 | 最大尝试次数（含首次） |
| `wait-duration` | 500ms | 重试间隔 |
| `retry-exceptions` | 空（全重试） | 白名单异常 |
| `ignore-exceptions` | 空 | 黑名单异常（如 4xx） |
| `retry-on-result-predicate` | — | 按结果重试 |
| `retry-on-exception-predicate` | — | 自定义异常谓词 |
| `enable-exponential-backoff` | false | 指数退避 |
| `exponential-backoff-multiplier` | 2.0 | 退避倍数 |
| `max-wait-duration` | 0 | 退避上限（防止退避失控） |
| `enable-randomized-wait` | false | 随机化间隔（防惊群） |

## 4. 三级优先级与合并规则

### 4.1 查找顺序

```text
instances.<id>  >  configs.<group>（或注解 group）  >  configs.default  >  出厂默认
   最具体                                            最通用
```

### 4.2 合并语义

```yaml
resilience4j:
  circuitbreaker:
    configs:
      default:
        sliding-window-size: 100
        failure-rate-threshold: 50
      orderGroup:
        failure-rate-threshold: 40        # 组：只覆盖阈值
    instances:
      orderService-v1:
        sliding-window-size: 30           # 实例：只覆盖窗口
        # 最终：size=30（实例），threshold=40（组继承），其余 = default
      orderService-v2:                    # 无实例配置
        # 最终：全部走 configs.default
```

> ⚠️ **分组 vs 默认的坑**：`create(id, group)` 时，若 group 名字在 `configs` 里不存在 → 直接回落到 `configs.default`（不报错）——**拼错组名 = 静默走默认配置**，排查时先确认组名。

## 5. 属性 vs Customizer：谁说了算

| 配置源 | 优先级 | 特点 |
|--------|--------|------|
| yaml 属性（resilience4j.*） | **高** | 可被配置中心动态刷新（如果接了 Config/Nacos）；运维友好 |
| Customizer Bean（Java） | 低 | 复杂逻辑（谓词/动态计算）；代码可读 |
| 出厂默认 | 最低 | 兜底 |

> 💡 实践：**能 yaml 的用 yaml**（改规则不用动代码）；Customizer 只放 yaml 表达不了的（自定义谓词类、多实例工厂级定制）。注意：注解与 Factory 共用同一 yaml 实例配置——**同名的注解和 Factory 走同一份规则**。

## 6. Metrics 与 Health 开关

### 6.1 Health（健康检查）

```yaml
resilience4j:
  circuitbreaker:
    instances:
      payment-service:
        register-health-indicator: true   # ★ 熔断器状态接入 /actuator/health

# 效果：
# GET /actuator/health
#   circuitBreakers: { status: "UP", details: { payment-service: { status: "OUT_OF_SERVICE" } } }
#   OUT_OF_SERVICE = OPEN 熔断中；UP = 正常
```

> ⚠️ **注意**：熔断器 OPEN 会让整体 health 变 `OUT_OF_SERVICE`——**注册中心（Nacos/Eureka）探活会摘除该实例！** 网关/注册中心别把熔断当存活信号，要么不注册 health indicator，要么把 circuitBreakers 从探活里排除（生产常见事故，见 [08 篇](08-生产实践与选型避坑.md)）。

### 6.2 Metrics（指标）

```xml
<!-- 引 micrometer 桥接 -->
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-micrometer</artifactId>
</dependency>
<!-- spring-boot-starter-actuator 通常已引 micrometer-core -->
```

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health, metrics
```

| 关键指标 | 含义 |
|---------|------|
| `resilience4j.circuitbreaker.state` | 各状态计数（CLOSED/OPEN/HALF_OPEN） |
| `resilience4j.circuitbreaker.calls` | 调用结果分布（成功/失败/被拒/被忽略） |
| `resilience4j.circuitbreaker.failure_rate` / `slow_call_rate` | 失败率/慢调用率（告警源） |
| `resilience4j.bulkhead.available_concurrent_calls` | 隔离剩余容量 |
| `resilience4j.ratelimiter.available_permissions` | 令牌余量 |

> 🎯 告警基线：**`failure_rate` 持续升高（如 >30%）预熔断告警；`state` 出现 OPEN 立即告警**（[08 篇](08-生产实践与选型避坑.md) 监控章节）。

## 7. 生产基线模板

```yaml
resilience4j:
  circuitbreaker:
    configs:
      default:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 100
        minimum-number-of-calls: 20
        failure-rate-threshold: 50
        slow-call-duration-threshold: 3s
        slow-call-rate-threshold: 60
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 5
        automatic-transition-from-open-to-half-open: true
        ignore-exceptions:
          - org.springframework.web.client.HttpClientErrorException  # 4xx 不熔断（按业务调整）
  timelimiter:
    configs:
      default:
        timeout-duration: 3s
        cancel-running-future: true
  retry:
    configs:
      default:
        max-attempts: 3
        wait-duration: 300ms
        retry-exceptions:
          - org.springframework.web.client.ResourceAccessException    # 只重试瞬时故障
        enable-exponential-backoff: true
        exponential-backoff-multiplier: 2.0
        max-wait-duration: 3s
  bulkhead:
    configs:
      default:
        max-concurrent-calls: 50
        max-wait-duration: 10ms
```

> 💡 模板要点：**超时 3s > 慢调用阈值 3s 需一致（或慢调用 < 超时）**；重试只认瞬时异常；半开 5 次试探；`automatic-transition-from-open-to-half-open: true` 让恢复节奏可控。按业务量再逐实例覆盖（[08 篇](08-生产实践与选型避坑.md) 调优节奏）。
