## 1. 状态机：三态转换

### 1.1 状态图

```text
                   失败率 ≥ threshold 且调用数 ≥ minimumNumberOfCalls
   ┌────────────────────────────────────────────────────────────┐
   │                                                             ▼
 ┌──────────┐         熔断（OPEN）           ┌────────────────┐
 │  CLOSED  │ ────────────────────────────► │      OPEN      │
 │  正常放行  │                               │  快速失败（fallback）│
 └──────────┘ ◄──────────────────────────── └────────────────┘
   │        ▲        恢复（CLOSED）                │
   │        │            waitDurationInOpenState 之后
   │        │                                     ▼
   │        │                               ┌────────────────┐
   │        └─────────────────────────────── │   HALF_OPEN    │
   │            试探成功 → 转 CLOSED           │  放行 1 个试探请求 │
   │                                          │                │
   │        试探失败 → 重新 OPEN                └────────────────┘
   └──────────────────────────────────────────────────────────┘
```

### 1.2 三态语义

| 状态 | 行为 | 进入条件 | 离开条件 |
|------|------|---------|---------|
| **CLOSED（关闭）** | 请求正常放行，**所有结果都记录**（成功/失败/慢调用） | 初始状态 | 滑动窗口内失败率（或慢调用率）≥ 阈值 **且** 调用数 ≥ minimumNumberOfCalls |
| **OPEN（打开）** | **拒绝所有请求**（快速失败：抛 CallNotPermittedException → fallback），**不调用下游** | 从 CLOSED 判定成立 | 经过 waitDurationInOpenState 后自动转 HALF_OPEN |
| **HALF_OPEN（半开）** | 放行**限定数量**的试探请求（permittedNumberOfCallsInHalfOpenState，默认 3） | 从 OPEN 定时转来 | 试探成功 ≥ 阈值 → CLOSED；失败 → 回 OPEN（重新计时） |

> 🎯 核心心智：**CLOSED 是"统计模式"，OPEN 是"保护模式"，HALF_OPEN 是"探测模式"**——熔断器本质是一个带状态机的"流量闸门"，统计只在 CLOSED 和 HALF_OPEN 发生。

### 1.3 OPEN 期间发生了什么

```text
请求到达 → tryAcquirePermission()
    ├── OPEN 状态：拒绝（抛 CallNotPermittedException）→ 上层走 fallback（毫秒级）
    └── CLOSED/HALF_OPEN：放行 → 执行调用 → 记录结果 → 更新统计
```

| 关键点 | 说明 |
|--------|------|
| 熔断期间零下游调用 | 这是防雪崩的核心：**下游已经扛不住了，别再去打它** |
| 快速失败毫秒级 | 不需要等超时（TimeLimiter 1s/3s 都不等了，直接拒绝） |
| 异常类型 | 拒绝时抛 `CallNotPermittedException`（Resilience4J），**这个异常也走 fallback** |
| 注意 | 默认情况下**拒绝本身不计入统计**（没有调用发生） |

## 2. 滑动窗口：COUNT_BASED 与 TIME_BASED

### 2.1 两种窗口类型（sliding-window-type）

| 维度 | COUNT_BASED（次数窗口） | TIME_BASED（时间窗口） |
|------|------------------------|------------------------|
| 统计口径 | 最近 **N 次调用**（环形缓冲） | 最近 **N 秒内**的调用（分桶聚合） |
| 配置 | `sliding-window-size: 100`（N=100 次） | `sliding-window-size: 10`（N=10 秒） |
| 内存 | O(N) 每条调用一条记录 | O(N) 固定桶数组（按秒桶） |
| 特点 | 结果精确、大流量下内存大 | 时间对齐直观、流量不均时窗口内样本数不可控 |
| 适用 | 高频稳定调用 | 时间语义明确、低频/突发流量 |
| 高并发 | 2.3.0 起有 **LOCK_FREE 无锁环形缓冲**（吞吐更高） | 默认加锁；**LOCK_FREE 仅支持 COUNT_BASED**（组合校验） |

### 2.2 COUNT_BASED 环形缓冲实现

```text
sliding-window-size = 4（示意）
环形缓冲：[成功][成功][失败][成功] ← 新结果覆盖最旧
  ├── 统计窗口 = 固定 4 个槽位，永远统计"最近 4 次"
  ├── 满员前：调用数 < 4 时不做熔断判定（受 minimumNumberOfCalls 约束）
  └── 2.3.0 无锁化：原子替换槽位，避免全局锁竞争（高并发吞吐提升）
```

### 2.3 TIME_BASED 分桶实现

```text
sliding-window-size = 10（10 个秒桶）
time[0] time[1] ... time[8] time[9]
  └── 新调用写入当前秒桶；每秒滚动一个桶
  ├── 聚合 10 秒内的 成功数/失败数/慢调用数 → 算失败率
  └── 桶内样本数不固定：10 秒内可能只有 3 次调用
```

> ⚠️ **组合陷阱**：`TIME_BASED` 与 `LOCK_FREE` 不能组合（2.3.0 起非法组合直接校验失败）——要无锁只能用 COUNT_BASED。

## 3. 熔断判定：失败率/慢调用率/异常谓词

### 3.1 判定公式

```text
触发熔断（CLOSED → OPEN）需同时满足：
  ① 窗口内调用数 ≥ minimumNumberOfCalls（默认 100）   ← 样本不足不判定
  ② 失败率 ≥ failureRateThreshold（默认 50%）
     或 慢调用率 ≥ slowCallRateThreshold（默认 100%，可调小）

失败率 = 失败调用数 / 总调用数 × 100%
慢调用率 = 耗时 > slowCallDurationThreshold（默认 60s）的调用数 / 总调用数 × 100%
```

### 3.2 什么算"失败"（record 语义）

| 语义 | 默认 | 配置 |
|------|------|------|
| 抛出的异常算失败？ | ✅ 所有异常都算 | `record-exceptions` 白名单 / `ignore-exceptions` 黑名单 / `record-failure-predicate` 自定义 |
| 被 ignore 的异常 | 不算失败，**但算调用数**（计入分母） | 适用于"业务上可接受的异常"（如 404） |
| 超时算失败？ | ✅ TimeLimiter 超时 → 抛 TimeoutException → 算失败 | `cancel-running-future` 控制是否中断线程 |
| 熔断拒绝（CallNotPermittedException） | 不计入（OPEN 期间无调用） | 不可配置（设计如此） |
| 返回 null / 特定结果算失败？ | ❌ 默认不算 | `record-result-predicate`（Java API）自定义 |
| 慢调用（超时阈值内但很慢） | 另算慢调用率 | `slow-call-duration-threshold` / `slow-call-rate-threshold` |

> 🎯 面试必答：**"熔断器怎么知道下游挂了？"**——两层信号：**① 异常**（超时/连接拒绝/5xx 抛异常）；**② 慢调用**（没抛异常但耗时超过 slowCallDurationThreshold）——所以参数里 `slowCallDurationThreshold` 必须小于你的超时配置（见 [08 篇](08-生产实践与选型避坑.md) 参数链）。

### 3.3 异常谓词优先级（2.4.0 修复点）

```text
record-exceptions 与 ignore-exceptions 都配了同名异常时：
  ❌ 2.3.0：行为不确定（历史 bug，谁先注册谁生效）
  ✅ 2.4.0：ignore-exceptions 明确优先于 record-exceptions
```

## 4. 半开试探与恢复

### 4.1 半开的完整时序

```text
t0  CLOSED：失败率 80%（≥50%）→ OPEN
t1  OPEN：所有请求快速失败（fallback），持续 waitDurationInOpenState（默认 60s）
t2  OPEN → HALF_OPEN：开始放行 permittedNumberOfCallsInHalfOpenState 个试探（默认 3）
    ├── 试探成功：3 次全成功 → CLOSED（恢复正常流量）
    └── 试探失败：任意失败达到半开失败率阈值 → 回 OPEN（重新计时 60s）
t3  循环：OPEN ↔ HALF_OPEN 反复，直到下游恢复
```

### 4.2 半开参数

| 参数 | 默认 | 说明 |
|------|------|------|
| `permitted-number-of-calls-in-half-open-state` | 3 | 半开期放行的试探请求数 |
| 半开失败率阈值 | 沿用 `failure-rate-threshold` | 半开期内试探失败率 ≥ 该值 → 回 OPEN |
| `max-wait-duration-in-half-open-state` | 0（无限） | 半开停留上限（防止试探请求长期堆积） |
| 半开自动关闭 | 2.4.0 新增可配置项 | HALF_OPEN→CLOSED 转换参数化 |

> 💡 **恢复期的"惊群"问题**：下游刚恢复时半开只放 3 个试探，能防止恢复瞬间流量洪峰再次打垮下游——这是熔断器"温柔恢复"的设计。

### 4.3 手动干预

```java
// 运维手段：手动重置（下游确认恢复后立刻恢复流量，不等 waitDuration）
circuitBreaker.reset();                 // 强制回 CLOSED
circuitBreaker.transitionToOpenState(); // 强制熔断（如灰度发现下游异常）
circuitBreaker.transitionToClosedState();
```

## 5. 事件模型与状态观察

### 5.1 事件类型（EventPublisher）

| 事件 | 触发时机 | 典型用途 |
|------|---------|---------|
| `onStateTransition` | 任意状态转换 | 告警：OPEN 即告警（最关键） |
| `onFailureRateExceeded` | 失败率超阈值 | 预熔断预警 |
| `onCallNotPermitted` | 请求被熔断拒绝 | 统计熔断期间的拒绝量 |
| `onError` | 调用抛异常（记录失败） | 失败埋点 |
| `onSuccess` / `onSlowCallRateExceeded` / `onIgnoredError` | 对应语义 | 观测明细 |

### 5.2 三种观察方式

```java
// ① 编程式监听（Customizer，推荐生产用）
@Bean
public Customizer<Resilience4JCircuitBreakerFactory> alertCustomizer() {
    return factory -> factory.addCircuitBreakerCustomizer(cb ->
            cb.getEventPublisher().onStateTransition(event -> {
                if (event.getStateTransition().getToState() == CircuitBreaker.State.OPEN) {
                    alertService.send("熔断告警：" + event.getCircuitBreakerName());
                }
            }));
}

// ② Actuator 健康检查（health 端点，配了 registerHealthIndicator 后）
// GET /actuator/health → circuitBreakers: { status: "UP" | "OUT_OF_SERVICE", details: {orderService: {...} } }

// ③ Micrometer 指标（引 resilience4j-micrometer）
// GET /actuator/metrics/resilience4j.circuitbreaker.state 等
```

## 6. vs Hystrix / vs Sentinel 原理对比

### 6.1 vs Hystrix（原理层面）

| 维度 | Resilience4J | Hystrix（废弃） |
|------|--------------|----------------|
| 统计窗口 | 滑动窗口（环形缓冲/分桶） | 滚动桶（类似 TIME_BASED） |
| 判定维度 | 失败率 + 慢调用率（双阈值） | 失败率（单阈值） |
| 熔断期行为 | 快速失败 + fallback | 同 |
| 半开试探 | ✅ 默认 3 次 | ✅ 单次 |
| 隔离方式 | 默认信号量（可线程池） | 默认线程池（重） |
| 依赖 | 单库轻量、无外部依赖 | 引入 Netflix 全家桶 |
| 响应式 | ✅ 原生 | ❌ |
| 维护 | ✅ 活跃 | 2018 停止 |

> 🎯 面试加分点：**Hystrix 默认线程池隔离（每命令一个池）**，代价是线程切换开销 + 线程池数量爆炸；**Resilience4J 默认信号量隔离**（零线程开销），线程池隔离作为可选——这是"轻量替代 Hystrix"的核心卖点。

### 6.2 vs Sentinel（同层对照）

| 维度 | Resilience4J（SCCB 默认） | Sentinel（SCA） |
|------|--------------------------|-----------------|
| 统计窗口 | 滑动窗口（环形缓冲/秒桶） | 滑动窗口（毫秒级格子，更细） |
| 熔断判定 | 失败率/慢调用率 | 慢调用比例/异常比例/异常数（三种策略） |
| 半开 | ✅ | ✅（探测请求机制） |
| 限流 | RateLimiter（单机令牌桶） | 流量整形/预热/热点参数（更强） |
| 控制台 | ❌ 无 | ✅ 可视化控制台 + 规则下发 |
| 规则持久化 | 配置中心（自己接） | ✅ 内置数据源（Nacos/APOLLO） |
| 动态规则 | 重启生效（除非接 Config） | ✅ 控制台实时下发 |
| 生态 | 官方 Spring Cloud | 阿里 SCA 生态 |

> 🎯 选型一句话：**官方 Cloud 生态 / 想要代码级细粒度控制 → Resilience4J；阿里生态 / 要控制台运维 / 要规则热下发 → Sentinel**（[08 篇](08-生产实践与选型避坑.md) 全维度对比）。
