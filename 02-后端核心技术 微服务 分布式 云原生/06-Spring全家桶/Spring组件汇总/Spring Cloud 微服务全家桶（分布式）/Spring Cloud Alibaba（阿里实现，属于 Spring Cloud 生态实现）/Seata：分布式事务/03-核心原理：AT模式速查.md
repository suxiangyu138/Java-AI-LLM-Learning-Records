## 1. 三角色与 XID

| 角色 | 全称 | 位置 | 职责 |
|------|------|------|------|
| **TC** | Transaction Coordinator | 独立 Server | 维护全局/分支事务状态机，推进二阶段提交/回滚 |
| **TM** | Transaction Manager | 事务发起方（业务服务） | 开启全局事务、提交/回滚全局事务（`@GlobalTransactional`） |
| **RM** | Resource Manager | 每个参与方（数据库侧） | 注册分支事务、执行分支提交/回滚、上报状态 |

```text
流程全景（下单场景）：

    TM（订单服务）                 TC（Server）                RM（库存服务）
         │  begin 全局事务              │                          │
         │ ─────────────────► 生成 XID ─┼─────────────────────────►│
         │  XID 写入 RootContext        │                          │
         │      │                       │  分支事务注册（携带锁）      │
         │      └───────────────────────┼─────────────────────────►│
         │                              │     本地事务提交（快）       │
         │  全部完成：commit/rollback    │                          │
         │ ────────────────────────────►│ 二阶段：异步删 undo_log    │
         │                              │  或 通知 RM 反向回滚        │
```

### 1.1 XID：贯穿全程的全局事务 ID

```java
// 发起方开启全局事务后，XID 存在 ThreadLocal（RootContext）
String xid = RootContext.getXID();        // 形如 192.168.0.1:8091:2512345678901234567

// RPC 传递：Seata 拦截器自动注入请求头（OpenFeign/RestTemplate/Dubbo 都适配）
// 请求头字段：TX_XID —— 下游服务从 Header 取出，set 回 RootContext
```

> 🎯 **XID 传递断链是最隐蔽的故障**：只要中间有一跳没传（自定义 Filter/新 RPC 组件/异步线程池），下游就成了"游离本地事务"——**验证方法：各服务打印 `RootContext.getXID()`，同一全局事务下 XID 必须一致**（[09 篇](09-集成地图与常见问题.md)）。

## 2. 一阶段：业务执行与分支注册

AT 模式一阶段 = **业务 SQL + 全局锁 + undo_log 快照 + 本地提交**，全部发生在业务数据库本地：

```text
一阶段（RM 侧，数据源代理内完成）：
    UPDATE stock SET count = count - 1 WHERE sku_id = 'S001'
        │
        ├─ ① SQL 解析（Druid parser）：识别 UPDATE + 主键 + 影响行
        ├─ ② 前镜像：SELECT count FROM stock WHERE sku_id='S001'  → 100
        ├─ ③ 执行业务 SQL：count 100 → 99
        ├─ ④ 后镜像：SELECT count FROM stock WHERE sku_id='S001'  → 99
        ├─ ⑤ 写 undo_log（前镜像 100 + 后镜像 99，同库同事务）
        ├─ ⑥ 注册分支事务 → TC：申请全局锁（resource_id:table:pk）
        ├─ ⑦ 全局锁成功 → 提交本地事务（业务数据 + undo_log 原子落库）
        └─ ⑧ 释放本地连接（一阶段到此结束，不阻塞）
```

| 步骤 | 关键点 | 失败处理 |
|------|--------|---------|
| SQL 解析 | 只支持**单一主键表的 UPDATE/INSERT/DELETE**；无主键表不支持 | 抛异常提示加主键 |
| 前后镜像 | 一次额外 SELECT；数据量大时镜像查询有开销 | — |
| 全局锁申请 | 锁被其他全局事务持有 → **循环重试等待** | 超过重试次数回滚本地事务 |
| 本地提交 | 业务数据与 undo_log **同库同事务**原子写入 | 任何一步失败本地回滚 |

> 🎯 一阶段的关键设计：**本地事务提交后立即释放数据库连接**——这是 AT 比 XA 性能高的根本原因（XA 一阶段不提交、锁到二阶段才释放）。

## 3. 二阶段提交：异步收尾

```text
提交（Commit）路径：
    TM → TC 提交全局事务
        ├─ TC 校验所有分支状态均为成功 → 状态 Begin → Committing
        ├─ 全部为 AT 分支 → 转异步提交（AsyncCommitting）
        ├─ 定时线程池扫描存储介质 → 逐分支通知 RM
        └─ RM：删除 undo_log + 释放全局锁（两步都异步，毫秒级）
```

| 设计点 | 说明 |
|--------|------|
| **异步提交** | 不阻塞业务线程；TC 定时批处理 |
| 删 undo_log | 提交后快照无用，直接删（**失败也无妨，只是残留脏数据**） |
| 释放全局锁 | 从 lock_table 删除行锁记录 |

> ⚠️ 提交失败（TC 崩溃等）会转重试；**undo_log 残留不影响一致性**，可定期清理 `log_status=0 且 gmt_modified 超时` 的行。

## 4. 二阶段回滚：反向 SQL 与脏写检查

回滚路径是 AT 模式的精髓——**用前镜像生成反向 SQL 恢复数据**：

```text
回滚（Rollback）路径：
    TM → TC 回滚全局事务
        ├─ TC **不释放全局锁**（防止回滚期间他人改数据）
        ├─ 通知所有 RM 执行本地回滚
        ├─ RM 根据 undo_log 前镜像生成反向 SQL：
        │    前镜像 count=100，当前 99 → 反向 UPDATE SET count=100 WHERE sku_id='S001'
        ├─ 回滚前执行【脏写检查】（三段比较）
        ├─ 本地回滚成功 → 上报 → TC 删除事务日志 + 释放全局锁
        └─ 若脏写检查失败 → 抛异常，转人工处理
```

### 4.1 脏写检查（三段比较）

| 比较项 | 比较结果 | 含义 | 动作 |
|--------|---------|------|------|
| 后镜像 vs 当前数据 | 一致 | 期间无人修改，安全 | 执行反向 SQL 回滚 |
| 后镜像 vs 当前数据 | 不一致 | 数据被动过 | 继续下一步 |
| 前镜像 vs 当前数据 | 一致 | 已被手动回滚过 | 不执行回滚（幂等跳过） |
| 前镜像 vs 当前数据 | 不一致 | **脏写**（他人绕过 Seata 改了数据） | 抛异常，人工介入 |

```java
// 伪代码（io.seata.rm.datasource.undo.AbstractUndoExecutor）
if (currentData.equals(afterImage)) {
    buildUndoSQL();              // 安全：正常回滚
} else if (currentData.equals(beforeImage)) {
    skip;                        // 已回滚过：幂等跳过
} else {
    throw new DirtyDataException("脏写，需人工处理");   // 必须人工介入
}
```

> 🎯 面试必答：**"AT 模式能保证不脏写吗？"**——正常情况下全局锁保证写隔离，脏写**只会出现在有人绕过 Seata 直改数据库**的场景；出现脏写时 Seata 宁可抛异常也不覆盖，这是**安全优先**的设计。

### 4.2 回滚失败常见原因

| 原因 | 表现 | 处理 |
|------|------|------|
| 表结构变更（删列/改类型） | 反向 SQL 生成失败 | 事务期间禁止 DDL |
| 连接池耗尽 | 回滚拿不到连接 | 调大连接数（回滚需要额外连接） |
| 无主键表 | SQL 无法定位行 | 加主键 |
| 时间戳字段精度问题 | 前后镜像比较失败 | 2.6 已修（DmdbTimestamp UTC 统一比较） |

## 5. 全局锁与隔离性

### 5.1 写隔离（全局锁）

```text
两个全局事务同时改同一行：
    Tx-A：注册分支 → 申请全局锁(sku:S001) → 拿到 → 提交本地
    Tx-B：注册分支 → 申请全局锁(sku:S001) → 【冲突】→ 循环重试
           └─ 重试上限内 Tx-A 二阶段完成释放锁 → B 拿到锁继续
           └─ 超限 → 抛全局锁冲突异常，本地回滚
```

| 要点 | 说明 |
|------|------|
| 锁粒度 | 行级（`resource_id:table:pk` 组成 row_key） |
| 锁管理 | TC 统一维护（lock_table）——**所有 RM 的锁都在 Server 侧判定** |
| 重试 | 默认循环重试（可配 `client.rm.lock.retry-interval/retry-times`） |
| 释放时机 | **二阶段结束后**（提交删锁/回滚完删锁），不是一阶段后 |

### 5.2 读隔离（全局读已提交）

| 场景 | 默认隔离 | 说明 |
|------|---------|------|
| 普通 SELECT | **读未提交（脏读可能）** | 一阶段本地提交后数据可见，但全局事务可能回滚 |
| SELECT FOR UPDATE | 读已提交 | 代理会查全局锁：被持有则释放本地锁重试，**拿不到不返回** |

```sql
-- 需要读已提交的业务必须用 FOR UPDATE（Seata 自动加全局锁检查）
SELECT * FROM stock WHERE sku_id = 'S001' FOR UPDATE;
```

> ⚠️ 面试易错点：**"AT 模式默认隔离级别？"——读未提交（业务读），写已隔离（全局锁）**；要全局读已提交必须 `FOR UPDATE`（[06 篇](06-模式选型与对比.md) 与 TCC/XA 对比时反复考）。

## 6. AT 模式性能特征与边界

| 维度 | 表现 |
|------|------|
| 性能 | 高：一阶段提交后即释放本地连接，全局锁只在写热点时竞争 |
| 吞吐瓶颈 | 热点行高并发 → 全局锁冲突放大（重试风暴） |
| 侵入性 | 极低：数据源代理自动完成，业务零改动 |
| 一致性 | 最终一致（回滚窗口内可读到中间态） |
| 支持 SQL | UPDATE/INSERT/DELETE + 单一主键表（无主键/多主键表不支持） |
| 不支持场景 | 存储过程/触发器/复杂 JOIN 更新（镜像无法可靠生成） |

> 💡 热点行优化：库存扣减类高并发场景，AT 全局锁是瓶颈——**方案 A：换 TCC**（无全局锁，业务锁自管）；**方案 B：库存拆行**（多行预分配，缓解热点）。详见 [06 篇](06-模式选型与对比.md)。

## 7. 面试高频问题

| 问题 | 一句话答案 |
|------|-----------|
| AT 为什么比 XA 快？ | 一阶段本地提交后释放连接，二阶段异步；XA 全程持锁到二阶段 |
| undo_log 有什么用？ | 存前后镜像，二阶段回滚时生成反向 SQL |
| 全局锁在谁手里？ | TC（Server 侧统一管理，lock_table） |
| 回滚时脏写检查怎么做？ | 后镜像 vs 当前（正常）→ 前镜像 vs 当前（已回滚跳过）→ 都不一致（脏写抛异常） |
| AT 支持哪些 SQL？ | UPDATE/INSERT/DELETE + 单主键表 |
| 读隔离能到已提交吗？ | 能，必须 SELECT FOR UPDATE（触发全局锁检查） |
| 全局事务怎么结束？ | TM 调 commit/rollback → TC 推进二阶段 |
