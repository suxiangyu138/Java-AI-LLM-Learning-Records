## 1. 高可用架构总览

Seata Server 是**有状态服务**（会话 + 锁），高可用 = **多节点 + 会话共享（或复制）+ 自动发现**：

```text
两种主流形态：

形态 A：主从 + 共享存储（传统，db/redis）
    client ──► Nacos 发现 TC 集群（master/slave 分组）
                 ├── TC-1（master）──┐
                 ├── TC-2（master）──┼──► 共享 DB / Redis（会话全量在存储）
                 └── TC-3（slave）  ─┘    任一节点挂 → Nacos 摘除 → 请求切走

形态 B：Raft 原生集群（2.2+，自管一致性）
    client ──► TC-1 / TC-2 / TC-3（3 节点，Raft 选主）
                 ├── Leader 处理读写，Raft 日志复制到 Follower
                 └── 无需注册中心、无需 DB/Redis（会话存 Raft 日志）
```

| 方案 | 依赖 | 一致性 | 适用 |
|------|------|--------|------|
| 主从 + db | MySQL 等 | 存储即真相（弱一致窗口小） | 已有 DB 基建 |
| 主从 + redis | Redis | 同上（pipeline 高性能） | 高性能要求 |
| **Raft** | 无（自管） | **Raft 强一致** | 新生产环境推荐 |

## 2. 方案一：主从集群 + 注册中心 + 共享存储

### 2.1 部署要点（以 db 存储为例）

```text
① 4 节点：master 组 2 台 + slave 组 2 台（同机测试用 7091~7094 端口区分）
② 每节点改 conf/application.yml：store.mode=db + 相同 DB 连接
③ 每节点注册 Nacos（registry.type=nacos，不同节点名）
④ 事务分组 vgroupMapping 指向集群（客户端先拿组 → 再拉实例列表）
⑤ 启动顺序：Nacos → MySQL → Server → 业务服务
```

```yaml
# server conf/application.yml（db 存储集群关键项）
store:
  mode: db
  db:
    url: jdbc:mysql://mysql-host:3306/seata?rewriteBatchedStatements=true
    user: seata
    password: seata
registry:
  type: nacos
  nacos:
    application: seata-server      # 注册名（客户端靠它发现）
    server-addr: nacos-host:8848
    group: SEATA_GROUP
    namespace: public
```

> ⚠️ **共享存储要点**：所有节点连**同一个 DB/Redis**（会话全局可见）；任一台挂掉，Nacos 自动摘除，客户端切换到存活节点——**存储就是单点**，DB/Redis 自身要主从/哨兵兜底。

### 2.2 Redis 存储模式（主从集群性能版）

```yaml
store:
  mode: redis
  redis:
    mode: sentinel                # 生产用哨兵
    sentinel:
      master-name: mymaster
      sentinel-hosts: redis-s1:26379,redis-s2:26379,redis-s3:26379
    max-conn: 10
    min-conn: 1
    database: 0
    type: pipeline                # 批量写（默认 pipeline）
```

## 3. 方案二：Raft 原生集群

### 3.1 核心配置（3 节点）

```yaml
# server conf/application.yml（每节点相同）
seata:
  raft:
    group: default                # ★ 与客户端事务分组对应
    server-addr: 192.168.0.111:9091,192.168.0.112:9091,192.168.0.113:9091
    snapshot-interval: 600        # 600s 做快照，加速 raftlog 滚动
    apply-batch: 32
    election-timeout-ms: 1000
    sync: true
store:
  mode: raft                      # ★ 存储模式 = raft
  file:
    dir: sessionStore             # raftlog 落盘路径（必须持久化卷）
registry:
  type: file                      # ★ raft 模式不允许用非 file 注册中心
```

### 3.2 Raft 集群运维铁律

| 规则 | 说明 |
|------|------|
| **最少 3 节点** | 2 节点无容错意义（选主半数失败） |
| 扩缩容走 openapi | `/metadata/v1/changeCluster?raftClusterStr=new_cluster_list`，改配置重启不生效 |
| raft 端口偏移 | Raft 端口 = Netty 端口 + 1000（默认 9091），同机需 `-Dserver.raftPort` |
| 会话持久化 | `store.file.dir` 目录必须挂持久卷（K8s PVC） |
| 快照定期做 | `snapshot-interval` 控制，防止 raftlog 无限增长 |
| 性能参数 | `max-append-bufferSize`（默认 256K）、`max-replicator-inflight-msgs`（256）、`disruptor-buffer-size`（16384，写吞吐大调大） |

> 🎯 **什么时候选 Raft**：新环境、无 DB/Redis 运维负担、要强一致会话——3 台小机器即获"无需注册中心"的高可用；存量有 DB 基建则 db 模式更顺手。

## 4. 事务分组与集群路由

```text
客户端找 TC 的完整链路（08 篇有配置详解）：
    client tx-service-group: my_test_tx_group
        → 配置中心查 service.vgroupMapping.my_test_tx_group = default
        → 注册中心按集群名 default 拉 TC 实例列表（master/slave）
        → 随机/权重选一台建 Netty 连接
```

| 配置项 | 作用 |
|--------|------|
| `tx-service-group` | 客户端事务分组名（逻辑隔离单位：不同业务线可分组） |
| `service.vgroupMapping.<组>` | 组 → TC 集群名的映射（存配置中心） |
| TC 集群名 | Server 注册时的 `registry.*.cluster`（默认 default） |
| 多分组用途 | 核心业务 / 非核心业务分属不同 TC 集群，故障隔离 |

> ⚠️ **生产实践**：核心交易与辅助业务**分不同事务组 + 不同 TC 集群**——核心链路挂事务不影响辅助，反之亦然。

## 5. 性能调优清单

| 调优点 | 配置 | 效果 |
|--------|------|------|
| MySQL 批量写 | DB URL 加 `rewriteBatchedStatements=true` | 全局锁批量插入性能 **提升 10 倍+** |
| Server 连接池 | `store.db.max-conn` 调大（默认 20） | 大事务并发不排队 |
| 客户端锁重试 | `client.rm.lock.retry-interval`（默认 10ms）/`retry-times`（30） | 冲突放大时调小重试次数快速失败 |
| 客户端连接池 | `spring.datasource.hikari.maximum-pool-size` 调大 | 回滚阶段需额外连接，池小会回滚失败 |
| 全局事务超时 | `@GlobalTransactional(timeoutMills = 60000)` | 防长事务占会话 |
| undo_log 清理 | 定时删 `log_status=0 且超时` 的行 | 防表膨胀（提交删失败残留） |
| Raft 写吞吐 | `disruptor-buffer-size` 调大 | 高写入场景 |
| 分支合并 | 2.6：[#7509] 连接复用合并分支事务 | 减少连接开销 |

> 🎯 **Top 3 生产优化**：① `rewriteBatchedStatements=true`（10 倍）；② 客户端连接池充足（回滚保命）；③ 全局事务超时显式设置（防悬挂）。

## 6. 容量评估与监控

| 指标 | 评估/监控方式 |
|------|--------------|
| TPS 上限 | 一事务 ≈ 2 次分支注册 + 1 次提交/回滚；db 模式受 DB 写 QPS 限制 |
| 全局锁冲突率 | Server 日志/控制台（冲突高 → 换 TCC 或拆行） |
| 会话积压 | 控制台全局/分支事务数（2.6+ 集群信息展示） |
| undo_log 表大小 | 定期 `SELECT COUNT(*) FROM undo_log WHERE log_status=0` |
| Server 健康 | 端口探活 + 日志 `Server started` / 分支处理日志 |
| MCP 可观测 | 2.6+：MCP 工具查全局/分支会话与锁（AI 运维） |

## 7. 1.x → 2.x 迁移清单

| 迁移项 | 1.x | 2.x | 动作 |
|--------|-----|-----|------|
| 注解包名 | `com.alibaba.seata.*` | `io.seata.*` | 改 import |
| client 依赖 | seata-all/旧 starter | seata-spring-boot-starter / SCA starter | 换坐标 |
| Server 配置 | `conf/file.conf` + `registry.conf` | `conf/application.yml`（统一） | 迁移配置 |
| 存储 | file/db/redis | 增加 **raft** | 新环境直接 raft |
| 端口 | 8091（控制台同口） | 8091 Netty + **7091 控制台** | 开放 7091 |
| 事务组 | vgroupMapping 同 | 同（配置中心管理） | 核对一致性 |
| 升级顺序 | — | **先 Server 后 Client**，逐服务灰度 | 回滚预案 |

> ⚠️ **升级铁律**：Server 与 Client **同步升**（2.x 内小版本可 server 略新）；先升级测试环境跑全链路回归（下单/支付/回滚用例），再灰度生产。

## 8. 生产兜底与演练

| 场景 | 兜底方案 |
|------|---------|
| TC 全部不可用 | 客户端事务降级：`client.tm.degrade-check` 开启 → 全局事务降级为本地事务（数据局部一致，需业务容忍） |
| 回滚失败 | 告警 + 人工核对 undo_log 生成补偿脚本 |
| 存储（DB/Redis）故障 | 存储自身高可用（主从/哨兵）+ 恢复演练 |
| 二阶段提交丢失 | TC 重试机制（会话持久化后重启续跑） |
| 演练清单 | ① 杀一台 TC 看切换；② 杀 DB 看会话恢复；③ 注入分支失败看回滚；④ 双写灰度迁移 |

> 🎯 **生产红线**：**"全局事务超时 + 事务降级开关 + 人工补偿预案"三件套缺一不可**——Seata 保证协议内一致，协议外（TC 全挂/存储损坏）必须靠降级与人工预案兜底。
