## 1. 组件一句话定位

**Seata（Simple Extensible Autonomous Transaction Architecture，阿里开源）是分布式事务解决方案**——用「TC 协调者 + TM 发起者 + RM 资源管理者」三角色模型，以 AT（自动补偿，非侵入）、TCC（手工补偿）、SAGA（长事务编排）、XA（数据库原生 2PC）四种模式覆盖不同一致性需求；**2024 年进入 Apache 孵化器（incubator-seata），2.6.0 起向"云原生 + AI 可观测"演进（MCP 工具、事务分组管理、HTTP/2）**。

```text
核心心智模型：
    TM（事务发起方）──开启全局事务，拿到 XID──► TC（协调器，独立 Server）
        │                                              │
        ├── XID 随 RPC 传递到各 RM ◄──────────────────┘ 维护全局/分支事务状态
        │                   │
        └──► RM-A（数据库A）     RM-B（数据库B）     RM-C（数据库C）
             本地事务 + 分支注册     本地事务 + 分支注册     本地事务 + 分支注册
             （undo_log 或 TCC 三方法 或 状态机 或 XA 协议）
```

| 维度 | 说明 |
|------|------|
| 所属 | Apache 孵化项目（原阿里巴巴开源，SCA 生态核心件） |
| 版本线 | 2.6.0（2026-01-28 稳定线）；2.7.0（2026 特性线） |
| 配套 | Spring Cloud Alibaba 2025.1.0.0 内置 Seata 2.5.0（client） |
| Java 要求 | Server: 17+ / Client: 8+（Boot 4 需 17+） |
| 四模式 | AT（非侵入自动补偿）/ TCC（手工三方法）/ SAGA（状态机编排）/ XA（原生 2PC） |
| 定位 | 微服务跨库事务唯一正统解（SCA 体系），与 Nacos/Sentinel/RocketMQ 并列四件套 |

### 1.1 Seata 解决什么问题

**① 跨服务跨数据库的一致性问题**：下单要「订单库插入 + 库存库扣减 + 账户库扣款」三个库一起成功或一起失败——本地事务（`@Transactional`）只覆盖单库，分布式场景必须有**全局协调者**（TC）来统一提交/回滚（[03 篇](03-核心原理：AT模式速查.md)）。

**② 一致性成本可控问题**：强一致（2PC/XA）性能差、侵入性强；消息事务只能解决"发消息"环节。Seata 用 **AT 模式的非侵入 + 性能折中**成为默认选项，再按场景给出手工方案（TCC/SAGA）——**一句话：AT 满足 80% 场景，剩下 20% 选型看 [06 篇](06-模式选型与对比.md)**。

| 维度 | 没有 Seata | 有 Seata |
|------|-----------|---------|
| 跨库写入 | 各库本地事务，部分成功部分失败 | 全局提交/回滚，最终一致或强一致 |
| 回滚 | 无（要自己写补偿代码） | AT 自动反向 SQL / TCC 手工 Cancel |
| 事务边界 | 单服务内 | `@GlobalTransactional` 跨服务级联 |
| 性能 | — | AT 一阶段提交后释放本地锁，优于 XA 全程持锁 |

> 🎯 判断标准一句话：**"一次用户操作会写 2+ 个数据库（或 2+ 个服务且各自持库）？"**——是，需要 Seata；只是调远程接口不改库，不需要（那是补偿/SAGA 问题）。

### 1.2 适用与不适用场景

| 场景 | 适合？ | 说明 |
|------|:---:|------|
| 微服务跨库写入（SCA 生态） | ✅ | 主战场（AT 模式默认） |
| 电商下单/支付/库存联动 | ✅ | AT 或 TCC（高并发扣减用 TCC） |
| 金融强一致核心交易 | ✅ | XA 模式（性能换强一致） |
| 超长业务流程（>1 分钟、5+ 服务） | ✅ | SAGA 模式（[05 篇](05-SAGA与XA模式速查.md)） |
| 单库单服务应用 | ❌ | 本地事务就够了，引入 Seata 是过度设计 |
| 纯读多写少、无跨库操作 | ❌ | 无全局事务需求 |
| 高并发热点行扣减 | ⚠️ | AT 全局锁会冲突放大，考虑 TCC + 库存本地扣减 |

> ⚠️ **最大认知误区**：把 Seata 当"分布式事务万能解"——它是**数据库事务的分布式延伸**；消息解耦场景（发送后下游异步处理）该用 RocketMQ 事务消息，跨服务无强一致需求该用本地消息表——**别让 Seata 干所有活**（[06 篇](06-模式选型与对比.md) 有完整选型对比）。

### 1.3 与主流分布式事务方案对照

| 维度 | Seata AT | Seata TCC | Seata SAGA | Seata XA | RocketMQ 事务消息 | 本地消息表 |
|------|---------|-----------|-----------|----------|------------------|-----------|
| 一致性 | 最终一致（可读已提交） | 最终一致 | 最终一致 | **强一致** | 最终一致 | 最终一致 |
| 业务侵入 | 无（自动） | 高（三方法） | 高（补偿/状态机） | 无 | 低（半消息） | 低（写表+任务） |
| 性能 | 高 | 最高 | 高 | 低（全程持锁） | 高 | 高 |
| 回滚 | 自动反向 SQL | 手工 Cancel | 手工补偿 | 数据库自动 | 自动反查+回滚消息 | 任务补偿 |
| 典型场景 | 默认首选 | 高并发扣减 | 长流程 | 金融核心 | 发消息下游异步 | 消息型异步化 |

> 🎯 面试必答：**"Seata 和 RocketMQ 事务消息什么区别？"**——Seata 是**同步强/最终一致**的事务编排（调用方等着结果），事务消息是**异步最终一致**（发消息后立即返回，下游消费失败重试/死信）；**同库改+发消息用 RocketMQ 事务消息，跨库强一致用 Seata**（[09 篇](09-集成地图与常见问题.md) 有联动图）。

## 3. 能力地图

| 能力域 | 能力点 | 对应 API/机制 |
|--------|--------|-------------|
| 全局事务 | 开启/提交/回滚全局事务 | `@GlobalTransactional` + TM 客户端 |
| XID 传递 | 全局事务 ID 跨服务传播 | `RootContext.getXID()` + RPC 拦截器（Seata 自动注入请求头） |
| AT 模式 | 自动补偿回滚 | 数据源代理 + undo_log 表 + 反向 SQL |
| TCC 模式 | 手工三方法补偿 | `@LocalTCC` + `@TwoPhaseBusinessAction` |
| SAGA 模式 | 长事务状态机编排 | 状态机 JSON 定义 / `@SagaTransactional` + `@Compensable` |
| XA 模式 | 数据库原生 2PC | XA 数据源代理（`DataSourceProxyXA`） |
| 全局锁 | 写隔离（防脏写） | lock_table + TC 统一冲突判定 |
| 隔离性 | 读已提交（可选） | SELECT FOR UPDATE 代理 + 全局锁查询 |
| 高可用 | 集群/选举/存储 | file/db/redis/raft 四种存储模式（[07 篇](07-高可用与生产实践速查.md)） |
| 事务分组 | 资源逻辑隔离、集群路由 | `tx-service-group` + `service.vgroupMapping` |
| 配置/注册中心 | Server/Client 协同 | Nacos/Eureka/Consul/ZK/Redis/etcd3（[08 篇](08-配置与注册中心集成速查.md)） |
| 安全 | 反序列化防护 | 2.7 JSON 白名单；2.6 HTTP 请求过滤器 |
| AI 可观测（2.6 新） | MCP 会话/锁管理 | MCP 工具 + spring-ai console |

### 3.1 能力边界：Seata 不做什么

| 能力边界 | 谁来做 | 说明 |
|---------|--------|------|
| 消息解耦/异步化 | RocketMQ 事务消息 | 同库写 + 发消息用事务消息，不是 Seata |
| 本地事务 | Spring `@Transactional` | Seata 依赖本地事务承载分支事务 |
| 分布式锁 | Redisson/Redis | 全局锁 ≠ 业务锁：只护事务行，不护缓存/接口 |
| 服务注册发现 | Nacos | Seata 复用注册中心感知 TC 集群（[08 篇](08-配置与注册中心集成速查.md)） |
| 幂等/防重 | 业务代码/Redis 幂等表 | TCC 空回滚/悬挂防护（TCC-FENCE）仍需业务配合 |

> ⚠️ **常见归因错误**：回滚失败怪 Seata——排查路径："分支事务注册了吗（Server 日志）→ undo_log 有前镜像吗（DB 查表）→ 反向 SQL 生成对吗（表结构兼容性）→ 连接池够吗（回滚需要新连接）"——Seata 只保证协调，**业务 SQL 与表结构问题它兜不住**（[09 篇](09-集成地图与常见问题.md) 排错表）。

## 5. 快速上手 3 步

**① 启动 Seata Server**（单机 file 模式，开发够用）：

```bash
# 方式 A：Docker（推荐开发，2.6.0）
docker run -d --name seata-server -p 8091:8091 \
  seataio/seata-server:2.6.0

# 方式 B：下载解压启动（生产用 db/raft 模式，见 02 篇）
# bin/seata-server.sh -m file -p 8091
```

**② 引入客户端依赖 + 配置**（每个参与分布式事务的微服务）：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-seata</artifactId>
</dependency>
```

```yaml
seata:
  enabled: true                    # ★ 必须显式开启
  tx-service-group: my_test_tx_group
  service:
    vgroup-mapping.my_test_tx_group: default
    grouplist.default: "127.0.0.1:8091"
```

**③ 业务方法加注解**（事务发起方，如订单服务）：

```java
@GlobalTransactional(rollbackFor = Exception.class)   // ★ 全局事务入口
public void createOrder(OrderDTO dto) {
    orderMapper.insert(dto);                  // 本地事务 + 注册分支（RM-A）
    stockClient.deduct(dto.getSkuId(), 1);    // XID 随 RPC 传给库存服务（RM-B）
    accountClient.pay(dto.getUserId(), 100);  // RM-C
}
```

> 🎯 跑通即及格：**① Server 日志看到事务组注册；② 控制台/日志出现分支注册；③ 故意让最后一个服务抛异常，前面的库数据被级联回滚**——三件事都通，分布式事务打通（[03 篇](03-核心原理：AT模式速查.md) 深入原理）。

### 5.1 三步验证与排障起点

| 步骤 | 做法 | 预期 |
|------|------|------|
| ① Server 就绪 | 启动 seata-server → 日志 `Server started` | 8091 端口监听 |
| ② 客户端接入 | 启动服务 → 日志出现 `Register branch` / 分支注册 | Server 控制台看到全局/分支事务 |
| ③ 级联回滚 | 末位服务抛异常 → 查前面库数据 | 前库数据被自动回滚（undo_log 生效） |

> 💡 排障起点：**先看 XID 传没传（`RootContext.getXID()` 打印），再看 Server 日志（分支注册/提交/回滚）**；`@GlobalTransactional` 不生效先查 `seata.enabled` 与事务组名是否三端一致（[09 篇](09-集成地图与常见问题.md) 排错表）。

## 8. 核心概念速查

| 术语 | 一句话解释 |
|------|-----------|
| TC | 事务协调器（独立 Server），维护全局/分支事务状态并推进二阶段 |
| TM | 事务管理器（发起方），开启/提交/回滚全局事务 |
| RM | 资源管理器（每个参与库），注册/上报分支事务，执行分支提交/回滚 |
| XID | 全局事务唯一 ID，随 RPC 传递贯穿所有参与服务 |
| 全局事务 | 跨服务跨库的一次业务操作整体（一个大 XID） |
| 分支事务 | 单个数据库内的本地事务（全局事务的组成部分） |
| AT 模式 | 自动补偿：SQL 反向解析 + undo_log 快照，无业务侵入 |
| undo_log | AT 模式回滚日志表（前/后镜像），参与方每库必建 |
| 全局锁 | 写隔离机制：分支提交前先抢行级全局锁，防止脏写 |
| 反向 SQL | 回滚时由 undo_log 前镜像生成的恢复语句 |
| 脏写检查 | 回滚前比较后镜像/当前数据/前镜像三段，防覆盖他人修改 |
| TCC | Try/Confirm/Cancel 手工三阶段补偿（空回滚/悬挂/幂等三难题） |
| SAGA | 长事务拆短事务 + 补偿链（状态机引擎或注解式） |
| XA | 数据库原生 2PC（一阶段准备、二阶段提交/回滚，强一致） |
| 事务分组 | tx-service-group：客户端到 TC 集群的虚拟映射（路由/隔离单位） |
| vgroupMapping | 事务分组 → TC 集群名的映射配置 |
| 存储模式 | Server 会话存储：file（单机）/db（集群）/redis（集群）/raft（原生高可用） |
| TCC-FENCE | Seata 防悬挂/空回滚的增强（幂等 + 悬挂标记表） |
