## 1. SCA 全家桶联动地图

```text
Spring Cloud Alibaba 四件套协作（下单场景）：

    Gateway ──► 订单服务（TM：@GlobalTransactional）
        │             │
        │             ├── Nacos：注册 + 配置（Server 注册/事务组映射）
        │             ├── Seata TC（Server）：全局事务协调
        │             ├── OpenFeign ──► 库存服务（RM-AT）──► MySQL + undo_log
        │             └── OpenFeign ──► 账户服务（RM-AT）──► MySQL + undo_log
        │
        └── Sentinel：流量防护（事务接口限流，防热点击穿全局锁）
```

| 组件 | 在本体系中的角色 | 说明 |
|------|----------------|------|
| Nacos | 注册中心 + 配置中心 | Seata Server 注册、事务分组映射（[08 篇](08-配置与注册中心集成速查.md)） |
| Seata | 分布式事务协调 | 全局/分支事务、全局锁 |
| Sentinel | 流量治理 | 事务接口限流熔断（Seata 不负责流量） |
| OpenFeign | 服务调用 | **XID 传递的载体**（请求头 TX_XID） |
| RocketMQ | 消息解耦 | 与 Seata 分工（同步事务 vs 异步消息，[06 篇](06-模式选型与对比.md)） |

> 🎯 联动要点：**四件套里 Seata 只干事务**——注册找 Nacos、限流找 Sentinel、消息找 RocketMQ；集成错误通常是"让 Seata 干了别的事"。

## 2. 与本地事务/ORM 框架协作

### 2.1 @Transactional 与 @GlobalTransactional

| 组合 | 行为 |
|------|------|
| 只有 `@GlobalTransactional` | 每条 SQL 执行后注册分支事务（无本地事务包住时） |
| 两层都有 | 外层全局事务 + 内层本地事务（**推荐**：本地事务包业务 + 注册分支） |
| 只有 `@Transactional` | 普通本地事务，不参与全局（下游失败不回滚） |

```java
@GlobalTransactional(rollbackFor = Exception.class)   // 全局入口
public void createOrder(OrderDTO dto) {
    orderMapper.insert(dto);
    stockClient.deduct(...);                            // 跨服务
}

// 服务内多表操作建议再加 @Transactional 包住（单分支内原子）
```

> ⚠️ **传播行为注意**：全局事务内调用**同服务内另一个 @GlobalTransactional 方法**会参与同一全局事务（XID 已存在）——不会开新全局事务，是"同事务"语义。

### 2.2 与 MyBatis / Druid / 多数据源

| 集成点 | 说明 |
|--------|------|
| MyBatis | 无感：SQL 走 DataSourceProxy → MyBatis 正常执行 |
| Druid | starter 自动代理（Seata 基于 Druid parser 解析 SQL）；自定义 Druid 数据源时注意代理顺序 |
| 多数据源 | `@EnableAutoDataSourceProxy` 手动开启；每个数据源都要被代理 |
| ShardingSphere | Seata 代理在分片外层（Seata 先接管 → 分片执行）；有专门兼容组合 |
| 动态数据源（dynamic-datasource） | 需把 Seata 代理接入每个真实数据源（官方文档有配置） |

> 💡 **数据源自检**：打印 `dataSource.getClass()`——若是 `DataSourceProxy`（或 wrapped 形式）说明代理成功；是裸 `HikariDataSource` 说明没代理，`@GlobalTransactional` 必不生效。

## 3. XID 传递链路与断点

```text
XID 生命周期：
    发起方 @GlobalTransactional 拦截器：
        ① RootContext.bind(xid)（ThreadLocal）
        ② OpenFeign 拦截器读 xid → 写请求头 TX_XID
        ③ 下游服务 Filter/拦截器读请求头 → RootContext.bind(xid)
        ④ 下游执行 SQL → 分支事务注册（携带 xid）
    结束：拦截器 finally 里 RootContext.unbind()（防线程池复用串号）
```

| 断点类型 | 现象 | 修复 |
|---------|------|------|
| 异步线程（@Async/线程池） | 子线程 XID 为空（ThreadLocal 不跨线程） | 手动 `RootContext.bind(xid)` 传递 |
| 自定义 RPC（gRPC/自研协议） | 无 TX_XID 头 | 自定义拦截器手动透传 |
| MQ 消费 | 消费者拿不到生产者 XID | 事务语义不跨消息（该用事务消息） |
| 网关层 | Gateway 不参与事务（无 DB） | 正常：事务从下游服务起 |
| 线程池复用 | A 事务线程被 B 复用拿到旧 XID | 拦截器 finally unbind（Seata 已处理）；自定义线程注意 |

> 🎯 **排查 XID 三件套**：① 各服务打印 `RootContext.getXID()`；② 对比是否同一串；③ 从"哪一跳开始为空"定位断点。

## 4. 高频坑排错表

| # | 现象 | 根因 | 处理 |
|---|------|------|------|
| 1 | `@GlobalTransactional` 不生效 | `seata.enabled` 没配/版本错配/数据源没代理 | 显式 true；查版本矩阵（[01 篇](01-模块清单.md)）；自检数据源类型 |
| 2 | 下游成功上游失败，数据不回滚 | XID 没传到下游（下游成游离本地事务） | 按第 3 节断点排查 |
| 3 | 报 `no available service` | 事务分组映射/集群名错 | 核对 vgroupMapping + cluster + namespace |
| 4 | 全局锁冲突超时 | 热点行并发 / 事务太长 | 调重试；短事务；换 TCC |
| 5 | 回滚报连接超时 | 连接池耗尽（回滚需要新连接） | 调大 `maximum-pool-size` |
| 6 | 回滚失败：找不到 undo_log | 没建 undo_log 表 / 表被清理 | 建表（每库）；检查清理任务 |
| 7 | SQL 不被支持 | 无主键表 / 复杂 SQL | 加主键；换 TCC 或改写 SQL |
| 8 | 启动报 ClassNotFound | Seata 与 Boot/Cloud 版本错配 | 查 [01 篇](01-模块清单.md) 版本矩阵 |
| 9 | 双数据源代理 | 同时引 seata-all 与 SCA starter | 只留一条接入链 |
| 10 | 事务悬挂（卡在 Begin） | 全局事务超时没配 / 线程被杀 | 显式 timeoutMills；检查业务异常是否被吞 |
| 11 | TCC 重复扣减 | 二阶段重复回调无幂等 | 开 TCC-FENCE（[04 篇](04-TCC模式实战速查.md)） |
| 12 | 提交后 undo_log 残留 | 异步删除失败/积压 | 定时清理 `log_status=0` 超时行 |

## 5. 回滚失败专项排查

```text
回滚失败 = 全局事务已回滚，但某个库数据没恢复。排查顺序：

    ① Server 日志：该分支回滚调用了吗？报什么错？
    ② undo_log 表：rollback_info 有内容吗？（没内容 = 一阶段就没写）
    ③ 反向 SQL：表结构变过吗？字段类型/精度兼容吗？
    ④ 连接：回滚执行时连接池有可用连接吗？
    ⑤ 脏写：脏写检查抛异常了吗？（后镜像 vs 当前数据）
    ⑥ 确认状态：log_status=1 说明回滚已执行；查业务数据为何没变
```

| 检查项 | 关键文件/命令 |
|--------|--------------|
| Server 分支日志 | seata-server 日志（`Rollback branch` / 异常堆栈） |
| undo_log 内容 | `SELECT * FROM undo_log ORDER BY id DESC LIMIT 5` |
| 镜像序列化 | `context` 字段看 serializer（2.7 统一 json-common） |
| 数据源代理 | 客户端启动日志 `Data source proxy mode` |

## 6. 上线验证清单

| 阶段 | 检查项 | 通过标准 |
|------|--------|---------|
| 部署 | Server 启动成功、注册 Nacos、存储模式正确 | 控制台/日志确认 |
| 接入 | 各服务数据源代理成功、事务组映射加载 | 日志无 warning |
| 功能 | 正常下单成功（全提交） | 数据一致、undo_log 清空 |
| 回滚 | 注入下游失败 → 上游数据回滚 | 订单表无残留 |
| 并发 | 同订单号并发下单（全局锁冲突） | 一成一败或串行成功 |
| 边界 | TC 停止 → 降级开关生效 | `degrade-check=true` 时本地事务可用 |
| 监控 | Server 指标接入、undo_log 清理任务运行 | 告警规则就绪 |
| 演练 | 杀 TC/杀存储/双写迁移 | 恢复预案可执行 |

> 🎯 上线总原则：**"先跑通回滚，再谈性能"**——回滚是分布式事务的命门，回滚验证不过，一切优化免谈。
