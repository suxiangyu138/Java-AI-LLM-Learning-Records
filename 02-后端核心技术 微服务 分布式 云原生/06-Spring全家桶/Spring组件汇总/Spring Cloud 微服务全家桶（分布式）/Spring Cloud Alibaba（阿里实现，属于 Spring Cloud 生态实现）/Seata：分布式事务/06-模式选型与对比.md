## 1. 四模式全景对比

| 维度 | **AT** | **TCC** | **SAGA** | **XA** |
|------|--------|---------|----------|--------|
| 一致性 | 最终一致（默认读未提交） | 最终一致（业务可控趋近强一致） | 最终一致 | **强一致（严格 ACID）** |
| 业务侵入 | **无**（数据源代理自动） | 高（Try/Confirm/Cancel 三方法） | 中高（补偿链/状态机） | **无**（协议标准） |
| 开发成本 | 极低 | 极高（含三难题处理） | 高 | 低 |
| 性能 | 高（一阶段提交释放锁） | **最高**（无全局锁） | 高（无锁） | **低**（Prepare 后持锁到二阶段） |
| 数据库依赖 | 需事务 + undo_log 表 | **不依赖**（支持异构存储） | 不依赖 | 必须支持 XA 协议 |
| 事务长度 | 短（秒级） | 短 | **长（分钟/小时级）** | 短 |
| 隔离性 | 写隔离（全局锁）；读需 FOR UPDATE | 业务自管（无全局锁） | **无隔离**（中间状态可见） | 库级隔离 |
| 回滚实现 | 自动反向 SQL | 手工 Cancel | 手工补偿链 | 数据库自动 ROLLBACK |
| 失败兜底 | 自动 | 自动（FENCE 表） | **补偿失败需人工** | 自动 |
| 典型场景 | **默认首选**（下单/跨库写入） | 高并发扣减/异构存储/精细控制 | 履约流程/预订/跨机构 | 金融核心/强一致小并发 |

> 🎯 记忆锚点：**AT = 自动（省心）、TCC = 手工（可控）、SAGA = 编排（长流程）、XA = 协议（强一致）**。

### 1.1 一致性视角再分组

| 分组 | 模式 | 一致性实现 |
|------|------|-----------|
| 补偿型（AP） | AT/TCC/SAGA | 先提交后补偿，中间状态可见，最终一致 |
| 协议型（CP） | XA | 二阶段协议保证原子，强一致 |

> ⚠️ 面试常考：**"Seata 是 CP 还是 AP？"**——Seata 的协调器（Server 侧存储可选 CP 的 raft）；但四种模式本身：**XA 是 CP（强一致），AT/TCC/SAGA 是 AP（最终一致）**——先回答模式再回答 Server，别混。

## 2. 选型决策流程

```text
开始：有跨库/跨服务的写一致需求？
  │
  ├─ 需求是"发消息给下游异步处理"？ ──► RocketMQ 事务消息（不是 Seata 的事）
  │
  ├─ 事务运行时间 > 1 分钟 或 服务数 > 5？ ──► SAGA（长流程唯一解）
  │
  ├─ 必须强一致（金融/账务）？
  │      ├─ 并发低（核心系统）──► XA
  │      └─ 并发高 ──► TCC（Try 冻结 + Confirm 划转，业务控隔离）
  │
  ├─ 热点行高并发扣减（秒杀/库存）？ ──► TCC（无全局锁）
  │
  ├─ 跨异构存储（Redis/Mongo 参与）？ ──► TCC（不依赖 DB 事务）
  │
  └─ 其余（80% 场景）──► AT（默认首选）
```

| 决策问题 | 回答"是"选 | 回答"否"落 |
|---------|-----------|-----------|
| 发消息异步化？ | RocketMQ 事务消息 | 继续 |
| 超长流程（>1 分钟/5+ 服务）？ | SAGA | 继续 |
| 强一致 + 低并发？ | XA | 继续 |
| 强一致 + 高并发？ | TCC | 继续 |
| 热点行扣减/异构存储/精细隔离？ | TCC | AT（默认） |

> 🎯 面试加分话术：**"我默认 AT 起步（无侵入、性能可），监测到全局锁冲突率 > X% 或需要强一致时，局部替换 TCC/XA——四种模式可以共存于一个系统，按业务线选"**（见第 4 节混合策略）。

## 3. 与 Seata 外方案对比（2PC/消息事务/本地消息表）

### 3.1 经典 XA/2PC（数据库层，无协调器框架）

| 对比项 | 经典 2PC | Seata（AT） |
|--------|---------|-------------|
| 协调 | 中间件（JTA 等） | Seata TC |
| 一阶段 | Prepare（持锁） | 提交（释放锁） |
| 二阶段 | Commit/Rollback | 异步删 undo_log / 反向 SQL |
| 性能 | 低 | 高 |
| 一致性 | 强一致 | 最终一致 |
| 失败恢复 | 需事务中间件 | 重试 + 人工兜底 |

### 3.2 RocketMQ 事务消息（异步解耦）

| 对比项 | 事务消息 | Seata |
|--------|---------|-------|
| 场景 | **同库写 + 发消息**（本地事务 + 消息原子） | 跨库/跨服务同步事务 |
| 返回方式 | 立即返回（异步消费） | 同步等待全局结果 |
| 一致性 | 最终一致（消费失败重试/死信） | 同步提交/回滚 |
| 适用 | 下单发消息通知、异步化削峰 | 要求调用方知道成败 |

### 3.3 本地消息表（经典国产方案）

| 对比项 | 本地消息表 | Seata AT |
|--------|-----------|---------|
| 实现 | 业务表 + 消息表同事务 + 定时任务投递 | 数据源代理自动 |
| 侵入 | 中（建消息表 + 写重试任务） | 无 |
| 实时性 | 依赖定时任务轮询 | 实时二阶段 |
| 适用 | 无额外中间件的轻量场景 | SCA 生态标配 |

> 🎯 结论：**Seata 解决"同步跨库一致"，事务消息/消息表解决"异步消息一致"**——两者不是竞争而是分工；混合系统里常见"下单事务用 Seata，下单后发消息用事务消息"。

## 4. 混合使用策略

一个系统内四种模式可共存（Seata 按分支类型分发）：

| 业务线 | 推荐模式 | 理由 |
|--------|---------|------|
| 常规订单（写 3 个库） | AT | 无侵入，够用 |
| 秒杀/库存扣减 | TCC | 无全局锁，扛热点 |
| 用户注册→初始化多服务 | AT 或 TCC | 短流程 |
| 订单履约全流程（含物流回调） | SAGA | 长流程 + 外部回调 |
| 核心账户/对账 | XA | 强一致要求 |

> ⚠️ 混合注意事项：**同一全局事务内混用 AT + TCC 可以**（分支类型不同，TC 分别处理），但全局锁/补偿语义要清楚；**TCC 分支的 Confirm/Cancel 与 AT 分支的回滚都会走各自的机制**——复杂度上升，非必要不混。

## 5. 典型业务场景选型卡

| 业务 | 推荐 | 一句话理由 |
|------|------|-----------|
| 电商下单（订单+库存+账户） | AT | 默认首选，非侵入 |
| 秒杀扣库存 | TCC | 无全局锁，并发最高 |
| 支付退款（第三方接口不可回滚） | TCC/SAGA | Cancel=调退款接口 |
| 旅游预订（酒店+机票+保险） | SAGA | 多服务长流程 |
| 银行转账核心 | XA | 强一致 |
| 分布式订单号发号 | 不用 Seata | 那是雪花算法/发号器的事 |
| 下单后发消息通知仓库 | RocketMQ 事务消息 | 异步解耦 |

## 6. 面试高频问题

| 问题 | 一句话答案 |
|------|-----------|
| 四种模式怎么选？ | 默认 AT；长流程 SAGA；强一致 XA；热点/异构 TCC |
| AT 和 TCC 怎么权衡？ | AT 自动省心但全局锁限并发；TCC 无锁并发高但要写三方法 + 防三难题 |
| XA 为什么不用在互联网高并发？ | Prepare 持锁到二阶段，连接占用久、吞吐低 |
| SAGA 能保证隔离吗？ | 不能（中间状态可见），需业务接受 |
| Seata 能替代消息事务吗？ | 不能——异步消息一致性是消息事务的领域 |
| 你们项目用的哪种？ | 主体 AT + 秒杀 TCC（混合策略，面试加分点） |
