## 1. 熔断 vs 限流：两种防护定位

| 维度 | 限流（FlowRule） | 熔断（DegradeRule） |
|------|-----------------|-------------------|
| 时机 | **事前**：流量超阈值主动拦截 | **事后**：异常累积到阈值被动切断 |
| 对象 | 正常流量 | 异常资源（慢/错） |
| 触发 | 计数超阈值 | 异常指标超阈值（RT/比例/数） |
| 恢复 | 规则持续生效 | 时间窗后**半开试探**自动恢复 |
| 类比 | 限速闸门 | 保险丝（烧断→冷却→恢复） |

```text
一句话：限流是"防患于未然"，熔断是"亡羊补牢"——两者叠加使用（限流挡突刺、熔断挡故障）。
```

> 🎯 面试必答：**"限流和熔断什么区别？"**——限流在**请求到达前**按阈值拒绝（保护自身容量）；熔断在**故障发生后**按异常指标切断（保护下游与自身线程）——前者防"流量超载"，后者防"故障扩散"。

## 2. 熔断状态机与半开恢复

```text
熔断三态：
    CLOSED（关闭）──异常指标超阈值──► OPEN（开启/熔断）
        ▲                                │
        │         半开探测成功（放行1个请求成功）│ timeWindow 时间窗到期
        │                                ▼
        └────────── HALF_OPEN（半开）◄──┘
                    半开探测失败 → 回到 OPEN（重置时间窗）
```

| 状态 | 行为 | 进入条件 |
|------|------|---------|
| **CLOSED** | 正常放行，统计异常指标 | 初始态 |
| **OPEN** | **快速失败**：所有请求直接拒绝（走降级） | 异常指标连续达到阈值 |
| **HALF_OPEN** | **放行 1 个探测请求**，成功 → CLOSED；失败 → 回 OPEN | OPEN 状态持续 timeWindow 后 |

> 🎯 面试必答：**"熔断怎么恢复？"**——OPEN 状态持续 `timeWindow`（秒）后转 HALF_OPEN，**放行 1 个探测请求**：成功说明下游恢复了 → 回 CLOSED 全量放行；失败 → 重新 OPEN 并重置时间窗——**避免"恢复抖动"（下游没好透就全量放流量再打爆）**。

## 3. 策略一：慢调用比例（RT）

| 参数 | 含义 | 示例 |
|------|------|------|
| `grade=0` | 慢调用比例 | — |
| `count` | 慢调用阈值 RT（ms） | 200ms |
| `timeWindow` | 熔断时间窗（s） | 10s |
| `minRequestAmount` | 触发统计的最小请求量 | 5 |
| `slowRatioThreshold` | 慢调用比例阈值（0~1） | 0.5 |

```java
DegradeRule rule = new DegradeRule("order:pay");
rule.setGrade(RuleConstant.DEGRADE_GRADE_RT);        // 慢调用比例
rule.setCount(200);                                   // RT > 200ms 记为慢调用
rule.setTimeWindow(10);                               // 熔断 10s
rule.setMinRequestAmount(5);                          // 1s 内至少 5 个请求才统计
rule.setSlowRatioThreshold(0.5);                      // 慢调用占比 ≥ 50% 触发
```

**触发逻辑**：单位统计时长内，请求量 ≥ `minRequestAmount` **且** 慢调用比例 ≥ `slowRatioThreshold` → 熔断。

> ⚠️ **RT 统计上限坑**：`-Dcsp.sentinel.statistic.max.rt` 默认 **4900ms**——超过 4900ms 的调用按 4900ms 计（超出部分不计入），RT 阈值设置若高于 4900 需调大该参数。

## 4. 策略二：异常比例

| 参数 | 含义 | 示例 |
|------|------|------|
| `grade=1` | 异常比例 | — |
| `count` | 异常比例阈值（0~1） | 0.3 |
| `timeWindow` | 熔断时间窗（s） | 10s |
| `minRequestAmount` | 最小请求量 | 5 |

```java
DegradeRule rule = new DegradeRule("order:create");
rule.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_RATIO);
rule.setCount(0.3);                                   // 异常占比 ≥ 30%
rule.setTimeWindow(10);
rule.setMinRequestAmount(5);
```

**触发逻辑**：请求量 ≥ 5 **且** 异常数 / 通过量 ≥ 0.3 → 熔断。

## 5. 策略三：异常数

| 参数 | 含义 | 示例 |
|------|------|------|
| `grade=2` | 异常数 | — |
| `count` | 异常数阈值（近 1 分钟） | 20 |
| `timeWindow` | 熔断时间窗（s） | 10s |

```java
DegradeRule rule = new DegradeRule("order:create");
rule.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_COUNT);
rule.setCount(20);                                    // 近 1 分钟异常 ≥ 20 次熔断
rule.setTimeWindow(10);
```

> ⚠️ **异常数的统计窗口是分钟级**：若 `timeWindow < 60s`，熔断结束后可能**再次立刻熔断**（历史异常仍累积在分钟窗口内）——异常数策略建议 timeWindow ≥ 60s 或配合异常比例使用。

### 5.1 三种策略选型速查

| 策略 | 统计窗口 | 适合 | 注意 |
|------|---------|------|------|
| 慢调用比例 | 秒级 | 下游变慢但不报错 | 调 RT 上限参数 |
| 异常比例 | 秒级 | 下游报错集中 | 最常用 |
| 异常数 | 分钟级 | 错误总量控制 | 时间窗别小于 60s |

## 6. 降级兜底写法（blockHandler/fallback）

熔断触发后请求快速失败——**必须给用户一个兜底结果**，否则熔断只是把异常换了个形式抛出去：

```java
@SentinelResource(value = "order:create",
        blockHandler = "createBlock",       // 熔断/限流/授权触发 → 走这里
        fallback = "createFallback")        // 业务异常（非 Block）→ 走这里
public Order create(OrderDTO dto) {
    return orderService.create(dto);
}

/** blockHandler：处理 BlockException（熔断、限流、授权） */
public Order createBlock(OrderDTO dto, BlockException e) {
    return Order.degraded(dto, "系统繁忙，请稍后重试");   // 友好降级
}

/** fallback：处理业务异常（NPE 等） */
public Order createFallback(OrderDTO dto, Throwable t) {
    return Order.degraded(dto, "服务异常");
}
```

| 兜底方式 | 适用 | 写法要求 |
|---------|------|---------|
| `blockHandler` | 熔断/限流/授权（BlockException） | 同参同返回 + 可加 BlockException |
| `fallback` | 业务异常（Throwable） | 同参同返回 + 可加 Throwable |
| `defaultFallback` | 通用兜底（无参数版） | 无需原方法参数（可加 Throwable） |
| `fallbackClass`/`blockHandlerClass` | 兜底方法外置 | 对应方法必须 static |
| Feign fallback | 远程调用降级 | 实现 FallbackFactory（[08 篇](08-与SpringCloudAlibaba集成速查.md)） |

> ⚠️ **默认无兜底**：只加规则不加 blockHandler/fallback → 被拦截时抛 `BlockException`（控制台返回 `Blocked by Sentinel` 默认页）——**线上必须有兜底**，否则用户看到的是 500 不是友好提示。

## 7. 生产建议与面试高频题

| 生产建议 | 说明 |
|---------|------|
| 熔断必须配降级兜底 | 没兜底的熔断 = 把故障换皮抛给用户 |
| 慢调用熔断优先 | 下游变慢（非报错）是雪崩主因，RT 策略最能护线程 |
| timeWindow 别太短 | 3~10s 起步，防止恢复抖动打爆下游 |
| 与限流叠加 | 限流挡突刺 + 熔断挡故障，双闸门 |
| 监控熔断事件 | 熔断是"事故信号"，要有告警（否则默默降级=业务静默受损） |

| 面试题 | 一句话答案 |
|--------|-----------|
| Sentinel 三种熔断策略？ | 慢调用比例（RT）/ 异常比例 / 异常数（统计窗口不同） |
| 熔断恢复机制？ | timeWindow 后 HALF_OPEN 放 1 个探测请求，成 → 关闭，败 → 再熔断 |
| 限流和熔断区别？ | 限流事前按阈值拒流量；熔断事后按异常指标切断（保险丝） |
| Sentinel vs Hystrix 熔断？ | Sentinel 秒级滑动窗口 + 半开恢复；Hystrix 线程池隔离 + 已停更 |
| 慢调用 RT 阈值上限？ | 默认 4900ms，超了需调 `csp.sentinel.statistic.max.rt` |
