## 1. 为什么必须持久化

| 痛点 | 说明 |
|------|------|
| **重启丢规则** | 默认规则在客户端内存，服务重启全部消失 |
| **多实例不同步** | 控制台推到一台客户端，其他实例没有 |
| **运维不可审计** | 规则变更无版本、无记录（Nacos 配置有历史） |
| **无法动态调整** | 线上改阈值要改代码发版 |

> ⚠️ **生产红线**：**不加数据源的 Sentinel 只能当"测试工具"**——线上必须把规则放进 Nacos（或 ZK/Apollo），实现"一次修改，全网生效，重启不丢"。

## 2. 三种推送模式对比

| 模式 | 链路 | 实时性 | 一致性 | 适用 |
|------|------|--------|--------|------|
| **原生模式** | 控制台 API → 客户端内存 | 即时 | 各实例独立 | 仅测试 |
| **拉模式（Pull）** | 客户端**定时轮询**规则源（文件/DB） | 延迟（分钟级） | 弱 | 轻量场景 |
| **推模式（Push）★** | 规则中心（Nacos）**监听推送** → 客户端数据源 | 秒级 | 强 | **生产标准** |

```text
推模式完整链路（生产标准）：
    Dashboard 修改规则
        → 写入 Nacos 配置中心（dataId: 应用名-flow-rules）
        → Nacos 长轮询/推送 → 客户端 sentinel-datasource-nacos 监听
        → 规则热更新（本地内存规则刷新）→ 生效
```

> 🎯 关键认知：**规则的正确流转是"配置中心 → 数据源 → Sentinel"**（单向拉/推送）；不是客户端写回 Nacos——只有 Dashboard 改造后由 Dashboard 写 Nacos（第 4 节）。

## 3. Nacos 数据源接入（客户端）

### 3.1 依赖 + 配置

```xml
<dependency>
    <groupId>com.alibaba.csp</groupId>
    <artifactId>sentinel-datasource-nacos</artifactId>
    <version>1.8.9</version>
</dependency>
```

```yaml
spring:
  cloud:
    sentinel:
      datasource:
        ds-flow:                       # 数据源名（自定义）
          nacos:
            server-addr: localhost:8848
            dataId: ${spring.application.name}-flow-rules    # 规则配置 ID
            groupId: SENTINEL_GROUP
            rule-type: flow            # flow/degrade/param-flow/system/authority
        ds-degrade:
          nacos:
            server-addr: localhost:8848
            dataId: ${spring.application.name}-degrade-rules
            groupId: SENTINEL_GROUP
            rule-type: degrade
        ds-param-flow:
          nacos:
            server-addr: localhost:8848
            dataId: ${spring.application.name}-param-flow-rules
            groupId: SENTINEL_GROUP
            rule-type: param-flow
```

| 配置项 | 说明 |
|--------|------|
| `rule-type` | 规则类型：flow / degrade / param-flow / system / authority（每个数据源对应一种规则） |
| `dataId` 规范 | 建议 `应用名-规则类型-rules`（如 `order-service-flow-rules`） |
| 一个数据源只能管一种规则 | 多类型规则需配多个数据源（如上） |

### 3.2 Nacos 中创建规则配置（JSON）

```json
// dataId: order-service-flow-rules（限流规则）
[
  {
    "resource": "order:create",
    "limitApp": "default",
    "grade": 1,
    "count": 100,
    "strategy": 0,
    "controlBehavior": 0,
    "clusterMode": false
  }
]
```

```json
// dataId: order-service-degrade-rules（熔断规则）
[
  {
    "resource": "order:create",
    "grade": 1,
    "count": 0.3,
    "timeWindow": 10,
    "minRequestAmount": 5
  }
]
```

| 规则字段速查 | flow | degrade | 说明 |
|-------------|:---:|:---:|------|
| `resource` | ✅ | ✅ | 资源名（与注解 value 一致） |
| `grade` | ✅（1=QPS/0=线程） | ✅（0=RT/1=异常比例/2=异常数） | 阈值类型 |
| `count` | ✅ | ✅ | 阈值 |
| `strategy` | ✅（0直接/1关联/2链路） | — | 流控模式 |
| `controlBehavior` | ✅（0快速失败/1排队/2预热） | — | 流控效果 |
| `timeWindow` | — | ✅ | 熔断时间窗（s） |
| `minRequestAmount` | — | ✅ | 最小请求量 |

> 💡 **Nacos 配置变更即热更新**：控制台改 Nacos 配置 → 客户端秒级刷新规则（无需重启）——这就是推模式的价值。

## 4. Dashboard 双向同步改造

默认 Dashboard 只把规则推到客户端内存（原生模式）——**生产要"控制台改 → 落 Nacos → 全网生效"必须改造 Dashboard**，官方预留了两个 SPI 扩展点：

| 扩展点 | 作用 | 改造目标 |
|--------|------|---------|
| `DynamicRuleProvider` | 规则查询（控制台显示用） | 从 Nacos 读（替换默认 `flowRuleDefaultProvider`） |
| `DynamicRulePublisher` | 规则发布（控制台保存用） | 写 Nacos（替换默认 `flowRuleDefaultPublisher`） |

```java
// 改造示例：FlowRule 的 Nacos 发布器（官方 test 目录有完整实现可复制）
@Component("flowRuleNacosPublisher")
public class FlowRuleNacosPublisher implements DynamicRulePublisher<List<FlowRule>> {
    @Autowired
    private ConfigService configService;
    private static final String DATA_ID = "order-service-flow-rules";
    private static final String GROUP = "SENTINEL_GROUP";

    @Override
    public void publish(String app, List<FlowRule> rules) throws Exception {
        configService.publishConfig(DATA_ID, GROUP, JSON.toJSONString(rules));
    }
}
```

```text
改造步骤：
    ① 引入 nacos-client 到 Dashboard
    ② 实现 DynamicRuleProvider（Nacos 读）+ DynamicRulePublisher（Nacos 写）
    ③ 配置 ConfigService（serverAddr/namespace）
    ④ 前端接口从 FlowControllerV1 改为 FlowControllerV2（走 Nacos 实现）
    ⑤ 其他规则类型（熔断/热点/系统/授权）同样替换
```

| 改造收益 | 说明 |
|---------|------|
| 控制台改规则 → Nacos | 配置可审计、可回滚（Nacos 历史版本） |
| 客户端从 Nacos 读 | 重启不丢、多实例一致 |
| 集群流控规则 | 可解决"Dashboard 建的集群规则不到 Token Server"的坑（[07 篇](07-集群流控速查.md)） |

> ⚠️ **改造风险**：Dashboard 是社区维护的参考实现，改造成本与升级成本并存——**也可选择"控制台只读 + 直接在 Nacos 改配置"**的轻量方案（规则以 Nacos 为准），免改造。

## 5. 其他数据源（ZK/Apollo/Redis）

| 数据源 | 坐标 | 场景 |
|--------|------|------|
| Nacos | `sentinel-datasource-nacos` | **首选**（SCA 生态天然配套） |
| ZooKeeper | `sentinel-datasource-zookeeper` | 已有 ZK 基建 |
| Apollo | `sentinel-datasource-apollo` | 携程配置中心体系 |
| Redis | `sentinel-datasource-redis` | 轻量规则存储（简单场景） |

```yaml
# ZK 数据源示例（结构一致，换类型）
spring:
  cloud:
    sentinel:
      datasource:
        ds-flow:
          zookeeper:
            server-addr: localhost:2181
            path: /sentinel-rules/flow
            rule-type: flow
```

> 💡 选型原则：**跟已有配置中心走**——有 Nacos 用 Nacos（SCA 标配）、有 Apollo 用 Apollo，别为规则持久化新引入一套配置中心。

## 6. 生产持久化方案选型

| 方案 | 成本 | 一致性 | 适用 |
|------|------|--------|------|
| Nacos 数据源（客户端接入） | 低（配置即用） | 秒级推送 | 绝大多数生产 |
| Nacos + Dashboard 改造 | 高（改前端后端） | 强（双向同步） | 规则运维频繁的大团队 |
| ZK/Apollo 数据源 | 低 | 秒级 | 已有对应基建 |
| Redis 数据源 | 低 | 弱（无监听推送语义强） | 简单场景 |

> 🎯 落地建议：**起步用"Nacos 数据源 + 直接在 Nacos 改配置"**（零改造）；团队大了再考虑 Dashboard 双向改造——**规则以 Nacos 为唯一事实源**（Single Source of Truth）是原则。

## 7. 常见问题

| 现象 | 原因 | 处理 |
|------|------|------|
| 重启后规则不生效 | 数据源没配/配置错误 | 检查依赖 + dataId/groupId/rule-type |
| 改 Nacos 不热更新 | 数据源未监听（版本问题） | 确认 sentinel-datasource-nacos 版本与 1.8.x 匹配 |
| Dashboard 改的规则没进 Nacos | 没改造 Publisher | 走"Nacos 直接改"方案或改造 Dashboard |
| 规则 JSON 格式错 | 字段名/类型不对 | 按官方 rule 字段（见 3.2 速查表） |
| 多应用共用 dataId | 规则串扰 | dataId 带应用名（`${spring.application.name}-...`） |
