## 1. 组件一句话定位

**Sentinel（阿里开源，分布式系统的流量防卫兵）是流量控制 + 熔断降级 + 系统保护三合一的轻量组件**——以**资源**为粒度（URL/方法/接口），用滑动窗口统计实时流量，支持 QPS/并发线程数限流、慢调用比例/异常比例/异常数熔断、热点参数限流、BBR 系统自适应保护与集群流控；**2026 年 2.0 方向升级为"流量治理"，成为 OpenSergo 流量治理标准实现，并同步 Go/C/Rust 多语言版本向云原生演进**。

```text
核心心智模型：
    流量 ──► 资源（URL / 方法 / Feign 接口）
              │
              ├─ ① 限流规则（QPS/线程数）──► 超阈值 → Blocked
              ├─ ② 熔断规则（RT/异常比例/异常数）─► 异常累积 → 熔断 → 半开试探
              ├─ ③ 热点参数规则（参数级限流）──► 热点参数 → 拒绝
              └─ ④ 系统保护规则（Load/CPU/入口QPS）─► 超阈值 → 全局拦流量
                    全部通过 → 执行业务 → 统计面板上报 Dashboard
```

| 维度 | 说明 |
|------|------|
| 所属 | Spring Cloud Alibaba 生态（阿里开源，SCA 四件套之一） |
| 版本线 | **1.8.9（SCA 2025.x 内置稳定线）**；2.0 方向 = 流量治理/OpenSergo |
| 配套 | Spring Cloud Alibaba 2025.1.0.0（Boot 4.0.x）/ 2025.0.0.0（Boot 3.5.x） |
| Java 要求 | 1.8+（客户端）；控制台 1.8.x 需 JDK 8+/17+ |
| 三能力 | 流量控制（限流）/ 熔断降级 / 系统自适应保护 |
| 定位 | 微服务入口 + 链路防护，防"雪崩"的第一道闸门 |

### 1.1 Sentinel 解决什么问题

**① 流量突增打垮服务**：大促/热点事件流量瞬时暴涨，数据库/下游被压垮——Sentinel 按 QPS/线程数**先拦后放**，把流量挡在业务之外（[03 篇](03-核心原理：流量控制速查.md)）。

**② 下游故障雪崩**：一个服务变慢/报错，调用方线程全被拖死，级联放大——Sentinel 熔断降级：**检测到异常就快速失败（走兜底），不再打爆故障服务**（[04 篇](04-熔断降级速查.md)）。

| 维度 | 没有 Sentinel | 有 Sentinel |
|------|--------------|-------------|
| 突增流量 | 服务直接被打崩（DB 连接耗尽） | 超阈值请求被拒（Blocked by Sentinel） |
| 下游故障 | 线程阻塞堆积 → 雪崩 | 熔断快速失败 + 降级兜底 |
| 慢接口拖累 | 无法感知 | RT 指标统计 + 限流/熔断 |
| 规则调整 | 改代码发版 | 控制台动态调整，秒级生效 |

> 🎯 判断标准一句话：**"你的服务会接外部流量、依赖下游（DB/其他服务），且出现过或怕出现被打崩？"**——是，上 Sentinel；纯内网批处理无并发压力则不需要。

### 1.2 适用与不适用场景

| 场景 | 适合？ | 说明 |
|------|:---:|------|
| Web 接口限流（QPS/并发） | ✅ | 主战场（URL 自动埋点） |
| 服务调用熔断降级（Feign） | ✅ | 下游故障快速失败 + 兜底 |
| 热点参数限流（秒杀商品） | ✅ | 参数级（商品 ID）精准拦截 |
| 系统级保护（入口总流量） | ✅ | BBR 自适应，防全站雪崩 |
| 集群精确限流 | ✅ | Token Server 模式（[07 篇](07-集群流控速查.md)） |
| 网关流量治理（Gateway/WebFlux） | ✅ | 1.6+ 网关适配器 |
| 单机无依赖服务 | ⚠️ | 能限流但收益有限（无下游依赖） |
| 消息消费幂等/重试 | ❌ | 那是 MQ 与业务的事 |

> ⚠️ **最大认知误区**：把 Sentinel 当"万能治理"——它是**流量/故障防护**专家；**依赖治理（降级预案编排）、熔断后的恢复编排、多活切换**是架构层面的事，Sentinel 只提供规则闸门（[09 篇](09-集成地图与常见问题.md) 分工图）。

### 1.3 与主流防护组件对照

| 维度 | Sentinel | Hystrix | Resilience4j | 网关限流（Nginx/网关） |
|------|----------|---------|--------------|----------------------|
| 限流能力 | ✅ QPS/线程/热点/系统 | ❌（仅隔离） | ✅ 部分 | ✅（QPS 级） |
| 熔断策略 | RT/异常比例/异常数 | 失败率 | 失败率/慢调用 | ❌ |
| 隔离方式 | **信号量/线程数控制** | 线程池隔离 | 信号量/线程池 | — |
| 统计维度 | 秒级滑动窗口 | 滚动窗口 | 滑动窗口 | 请求计数 |
| 动态规则 | 控制台/数据源热更新 | 静态 | 编程式 | 配置重载 |
| 维护状态 | **活跃（1.8.x 稳定）** | 已停更 | 活跃 | 各自生态 |
| 集群流控 | ✅ Token Server | ❌ | ❌ | Nginx 集群（分布式） |

> 🎯 面试必答：**"Sentinel 和 Hystrix 什么区别？"**——Hystrix 已停更、只做熔断+线程池隔离（线程切换开销大）；Sentinel **限流+熔断+系统保护一体**、信号量级无线程开销、秒级滑动窗口统计、控制台动态规则、支持集群流控——**Sentinel 是 Hystrix 的现代替代**（[09 篇](09-集成地图与常见问题.md) 有迁移清单）。

## 3. 能力地图

| 能力域 | 能力点 | 对应规则/机制 |
|--------|--------|-------------|
| 流量控制 | QPS/并发线程数限流 | FlowRule（grade: QPS/THREAD） |
| 流控模式 | 直接/关联/链路 | FlowRule.strategy（0/1/2） |
| 流控效果 | 快速失败/预热/匀速排队 | FlowRule.controlBehavior（0/1/2） |
| 热点参数限流 | 参数级 QPS + 例外项 | ParamFlowRule（LRU + 令牌桶） |
| 熔断降级 | RT/异常比例/异常数 | DegradeRule（grade: RT/RATIO/COUNT） |
| 熔断恢复 | 半开试探（timeWindow 后） | 内置状态机 CLOSED/OPEN/HALF_OPEN |
| 系统保护 | Load/CPU/RT/线程数/入口 QPS | SystemRule（BBR 自适应） |
| 授权规则 | 黑/白名单（来源限流） | AuthorityRule（limitApp） |
| 集群流控 | Token Server/Client | 独立/嵌入两种部署（[07 篇](07-集群流控速查.md)） |
| 规则持久化 | Nacos/ZK/Apollo 推模式 | DataSource SPI（[06 篇](06-规则持久化与动态数据源速查.md)） |
| 监控 | 秒级指标 + Dashboard | 心跳上报 + 控制台实时曲线 |
| 生态适配 | Spring MVC/Feign/Gateway/WebFlux/Dubbo | 适配器自动埋点 |

### 3.1 能力边界：Sentinel 不做什么

| 能力边界 | 谁来做 | 说明 |
|---------|--------|------|
| 服务注册发现 | Nacos | Sentinel 不负责实例管理 |
| 分布式事务 | Seata | SCA 兄弟组件（[Seata 目录](../Seata：分布式事务/00-Seata知识体系总览.md)） |
| 消息削峰 | MQ | 限流是"挡"，削峰是"蓄"（MQ 缓冲） |
| 降级预案编排 | 业务/架构 | Sentinel 触发降级入口，预案内容业务自定 |
| 幂等/防重 | 业务/Redis | 与流量防护无关 |

> ⚠️ **常见归因错误**：限流后用户收到 `Blocked by Sentinel` 怪"系统崩了"——**限流是主动防御，不是故障**；排查规则阈值是否合理（误杀正常流量）而不是删规则（[09 篇](09-集成地图与常见问题.md)）。

## 5. 快速上手 3 步

**① 启动 Dashboard 控制台**（本地开发）：

```bash
# 下载 sentinel-dashboard-1.8.9.jar，启动（默认 8080）
java -Dserver.port=8080 -Dcsp.sentinel.dashboard.server=localhost:8080 \
     -Dproject.name=sentinel-dashboard -jar sentinel-dashboard-1.8.9.jar
# 控制台：http://localhost:8080（默认账号 sentinel/sentinel）
```

**② 客户端接入依赖 + 配置**：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-sentinel</artifactId>
</dependency>
```

```yaml
spring:
  cloud:
    sentinel:
      transport:
        dashboard: localhost:8080     # 控制台地址
        port: 8719                    # 客户端心跳/上报端口
      eager: true                     # ★ 启动即连控制台（否则首次访问才注册）
```

**③ 控制台加规则 + 业务兜底**：

```java
@SentinelResource(value = "order:create",
        blockHandler = "createBlock",          // 限流/熔断触发 → 走这里
        fallback = "createFallback")           // 业务异常 → 走这里
public Order createOrder(OrderDTO dto) { ... }

public Order createBlock(OrderDTO dto, BlockException e) {
    return Order.retryLater(dto);              // 返回友好降级结果
}
```

> 🎯 跑通即及格：**① 控制台出现客户端应用与实时曲线；② 加一条 QPS=1 的限流规则；③ 连点两次接口，第二次被 Blocked 且走了 blockHandler**——三件事都通，Sentinel 主链路打通（[03 篇](03-核心原理：流量控制速查.md)）。

### 5.1 三步验证与排障起点

| 步骤 | 做法 | 预期 |
|------|------|------|
| ① 控制台注册 | 启动应用 → 控制台应用列表 | 出现应用名（eager=true 启动即注册） |
| ② 规则生效 | 控制台加 QPS=1 规则 → 连点接口 | 第二次响应被拒/走 blockHandler |
| ③ 指标上报 | 控制台实时监控 | 曲线可见（秒级统计） |

> 💡 排障起点：**先看控制台有没有应用（没出现 = 心跳问题，查 8719 端口与 Dashboard 地址），再看规则有没有生效（没生效 = 规则没推送/资源名不匹配）**——`Blocked by Sentinel` 字样出现说明拦截链路已通（[09 篇](09-集成地图与常见问题.md) 排错表）。

## 8. 核心概念速查

| 术语 | 一句话解释 |
|------|-----------|
| 资源（Resource） | 被保护对象：URL、方法、Feign 接口名（一切皆资源） |
| 规则（Rule） | 对资源施加的防护策略（限流/熔断/授权/系统） |
| 滑动窗口 | 秒级统计容器：当前秒的请求量/RT/异常计数 |
| 限流 | 超阈值请求直接拒绝（防患于未然） |
| 熔断 | 异常累积到阈值后快速失败（亡羊补牢）+ 半开恢复 |
| 降级 | 熔断/限流后的兜底返回（blockHandler/fallback） |
| 热点参数限流 | 按参数值（商品 ID）做令牌桶限流 |
| 系统保护 | 系统整体 Load/CPU 超标时全局拦截（BBR 自适应） |
| 授权规则 | 按调用来源黑白名单放行/拒绝 |
| BlockException | Sentinel 拦截后抛的异常族（限流/熔断/授权） |
| Token Server | 集群流控的令牌发放方 |
| 规则持久化 | 规则存入 Nacos/ZK，重启不丢（推模式） |
| Dashboard | 控制台：规则管理 + 实时监控 |
