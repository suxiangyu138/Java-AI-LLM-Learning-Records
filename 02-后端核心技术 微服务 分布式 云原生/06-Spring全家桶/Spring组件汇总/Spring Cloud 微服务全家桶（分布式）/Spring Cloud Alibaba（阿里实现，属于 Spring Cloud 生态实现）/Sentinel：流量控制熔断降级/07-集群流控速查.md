## 1. 为什么需要集群流控

```text
单机限流的局限（10 台实例，目标：集群总量 100 QPS）：
    每台设 10 QPS → 总量上限 100
    但流量分布不均（一台 30、一台 2）：
        ├─ 30 的机器被误限（其实集群总量才 60）
        └─ 总量可能冲到 120（部分机器没到 10）
    → 单机限流只能"近似"，无法精确控制集群总量
```

| 场景 | 说明 |
|------|------|
| 总量硬约束 | 下游/第三方 API 有总量配额（如调用外部接口 100 QPS） |
| 流量不均 | 多实例负载不均衡时单机阈值失真 |
| 秒杀总控 | 全集群限 N 单，超出返回失败 |

> 🎯 一句话：**单机限流是"每台自己的闸门"，集群流控是"集群共享一个总闸门"**——总闸门由 Token Server 统一发放令牌。

## 2. 架构：Token Server / Token Client

```text
集群流控架构：
    Token Client（各业务实例）
        │ 请求令牌（携带资源+计数）
        ▼
    Token Server（发放令牌）
        ├─ 按集群规则判断：集群总量未超 → 发令牌 → Client 放行
        ├─ 超限 → 拒绝 → Client 触发限流（Blocked）
        └─ 规则源：从 Nacos 动态拉取（按 namespace）

    兜底：Token Server 不可达时，Client 按【本机规则】兜底（fail-open/fail-close 可配）
```

| 角色 | 职责 | 部署 |
|------|------|------|
| **Token Client** | 向 Server 申请令牌，按结果放行/拒绝 | 每个业务实例内嵌 |
| **Token Server** | 统一判定集群规则，发放/拒绝令牌 | 独立进程或嵌入某实例 |

> 💡 关键机制：**Token Server 挂了的兜底**——Client 的 `failOpen` 语义：Server 不可达时**降级为本机限流**（不阻塞业务），保证"精确性损失但可用性不丢"。

## 3. 两种部署模式：独立 vs 嵌入

| 模式 | 部署 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **独立模式（Alone）** | Token Server 单独进程 | 隔离性好、不干扰业务 | 多一套部署 | **全局精确限流（推荐）** |
| **嵌入模式（Embedded）** | Token Server 与某业务实例同进程 | 免额外部署、角色可切换 | 占用业务资源；需限 QPS | 应用内集群流控 |

> ⚠️ **嵌入模式风险**：Token Server 承担集群全部判定请求，**QPS 必须限制**（1.4.1+ 支持 `maxAllowedQps`）——否则判定请求本身会压垮宿主应用；生产大流量场景优先独立模式。

## 4. Token Server 启动与配置

### 4.1 依赖

```xml
<!-- Token Server 侧 -->
<dependency>
    <groupId>com.alibaba.csp</groupId>
    <artifactId>sentinel-cluster-server-default</artifactId>
    <version>1.8.9</version>
</dependency>
```

### 4.2 独立模式启动代码

```java
// 独立进程：初始化 Token Server
ClusterTokenServer tokenServer = new SentinelDefaultTokenServer();
ClusterServerConfigManager.loadGlobalConfig(new ServerGlobalConfig()
        .setMaxAllowedQps(50000));                    // 兜底：Server 自身 QPS 上限

// namespace（多应用隔离）：注册应用 A 与 B 的 namespace
Set<String> namespaces = new HashSet<>(Arrays.asList("appA", "appB"));
ClusterServerConfigManager.loadServerNamespaceSet(namespaces);

// 传输配置（客户端连这里）
ServerTransportConfig transport = new ServerTransportConfig()
        .setPort(11111)                                // Token Server 端口
        .setIdleSeconds(600);
ClusterServerConfigManager.loadServerTransportConfig(transport);

tokenServer.start();
```

| 配置项 | 说明 |
|--------|------|
| `loadServerNamespaceSet` | 服务哪些应用（namespace 隔离） |
| `ServerTransportConfig.port` | Token Server 端口（客户端连它） |
| `maxAllowedQps` | Server 自身处理上限（防被打满） |
| 动态化 | 通过 `NacosDataSource` + `SentinelProperty` 监听热更新 namespace/transport（生产推荐） |

### 4.3 集群流控规则源（按 namespace 动态加载）

```java
// 为 namespace 注册规则源（Nacos 推模式）
ClusterFlowRuleManager.registerPropertySupplier(namespace, () -> {
    // 从 Nacos 拉取该 namespace 的集群流控规则
    ReadableDataSource<String, List<FlowRule>> ds =
        new NacosDataSource<>(NACOS_ADDR, "SENTINEL_GROUP",
                              namespace + "-cluster-flow-rules", new FlowRuleJsonParser());
    return ds.getProperty();
});
```

> 🎯 设计要点：**集群规则与 namespace 绑定**——不同应用（namespace）各自从 Nacos 拉自己的集群规则，互不串扰（与 [06 篇](06-规则持久化与动态数据源速查.md) 的推模式同一套思路）。

## 5. Token Client 接入

### 5.1 依赖与配置

```xml
<!-- 业务服务加 Client 依赖（独立模式只需 client） -->
<dependency>
    <groupId>com.alibaba.csp</groupId>
    <artifactId>sentinel-cluster-client-default</artifactId>
    <version>1.8.9</version>
</dependency>
```

```java
// Client 启动配置：连接哪个 Token Server
ClusterClientConfig config = new ClusterClientConfig()
        .setRequestTimeout(200);                      // 请求超时（ms）
ClusterClientConfigManager.applyNewConfig(config);

// 注册 Token Server 地址（独立模式直连；嵌入模式指向自己）
ClusterClientConfigManager.applyServerList(
        new ServerList(new ServerTransportConfig().setHost("token-server-host")
                                                  .setPort(11111))
);

// 集群规则（Nacos 推模式，与单机规则同 dataId 可加 clusterMode: true）
ClusterFlowRuleManager.loadRules(namespace, flowRules);
```

```json
// Nacos 中集群限流规则（flow 规则加 clusterMode）
[
  {
    "resource": "order:create",
    "grade": 1,
    "count": 100,
    "strategy": 0,
    "controlBehavior": 0,
    "clusterMode": true,             // ★ 开启集群模式
    "clusterConfig": {
      "thresholdType": 1             // 1=集群总量 / 0=每实例均摊
    }
  }
]
```

| clusterConfig.thresholdType | 含义 |
|----------------------------|------|
| 0 | 每实例均摊（阈值 × 实例数） |
| 1 | **集群总量（推荐）**：全局 100 QPS |

## 6. 规则下发与生产实践

```text
生产推荐拓扑：
    Nacos（规则唯一事实源）
      │ 推模式
      ├─► Token Server（独立进程，按 namespace 拉规则）
      └─► Token Client（业务实例，集群规则也走 Nacos）
    业务流量：Client ──请求令牌──► Server ──判定──► 放行/拒绝
```

| 实践项 | 建议 |
|--------|------|
| Server 部署 | **独立模式** + 多实例（Server 自身也要 HA：多 Server 前挂 LB/直连列表） |
| 规则管理 | 全部走 Nacos 推模式（Dashboard 集群规则创建有坑，见下） |
| 兜底策略 | Server 不可达 → Client 降级本机规则（fail-open），保证可用性 |
| 超时控制 | Client 请求 Server 设超时（如 200ms），超时走兜底不阻塞 |
| namespace | 一个应用一个 namespace，规则隔离 |
| 容量评估 | Server 单机可支撑的 token 请求量有限，超了水平扩展 |

> ⚠️ **已知坑：Dashboard 创建的集群规则不自动下发 Token Server**——Dashboard 的 `/cluster/server/flowRules` 常为空，需手动 `/cluster/server/modifyFlowRules` 导入，或改造 Dashboard 接入 Nacos（[06 篇](06-规则持久化与动态数据源速查.md) 方案同样适用于集群规则）。

## 7. 常见问题

| 现象 | 原因 | 处理 |
|------|------|------|
| 集群规则不生效 | 规则没下发到 Token Server | 手动导入或 Dashboard 改造（见上） |
| Client 全部被拒 | thresholdType=1 阈值设太低 / Server 拒绝 | 核对集群总量配置 |
| Server 成为瓶颈 | 判定 QPS 打满 | 独立模式 + 水平扩展 + maxAllowedQps |
| Server 挂后业务全挂 | fail-close 语义 | 改 fail-open（本机规则兜底） |
| namespace 不匹配 | Client/Server namespace 不一致 | 核对 loadServerNamespaceSet |
