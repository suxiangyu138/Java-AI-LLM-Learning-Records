## 1. 系统保护定位

| 防护层 | 粒度 | 作用 |
|--------|------|------|
| 限流（FlowRule） | 单个资源 | 接口级防护 |
| 熔断（DegradeRule） | 单个资源 | 接口级故障切断 |
| **系统保护（SystemRule）** | **全局** | **整个应用**的兜底闸门：CPU/Load 超标时所有入口限流 |

```text
典型场景：数据库连接池快耗尽了、CPU 打满 95%、GC 疯狂
    → 单接口限流已来不及（流量分散在几十个接口）
    → SystemRule：入口总 QPS 自动下调 / 全局拦截 → 保住进程不死
```

> 🎯 一句话定位：**系统保护是"全站最后一根保险丝"**——平时不动，系统濒危时自动全局拦流量，防整体雪崩。

## 2. SystemRule 五项指标

| 指标 | 含义 | 说明 |
|------|------|------|
| **Load** | 系统 1 分钟平均负载（`load.1m`） | 超过阈值时系统过载，触发全局保护 |
| **CPU 使用率** | 系统 CPU 使用率（%） | 超过阈值触发（1.5.0+） |
| **平均 RT** | 入口平均响应时间 | 所有入口请求的平均 RT 超阈值触发 |
| **并发线程数** | 入口并发线程数 | 全局并发超阈值触发 |
| **入口 QPS** | 总入口 QPS | 全局 QPS 超阈值触发 |

```java
SystemRule rule = new SystemRule();
rule.setHighestSystemLoad(3.0);          // Load > 3 时全局限流（阈值类型：load）
rule.setHighestCpuUsage(0.8);            // CPU > 80% 触发
rule.setAvgRt(2000);                     // 平均 RT > 2000ms 触发
rule.setMaxThread(1000);                 // 并发线程 > 1000 触发
rule.setQps(10000);                      // 入口 QPS > 10000 触发
SystemRuleManager.loadRules(Collections.singletonList(rule));
```

| 字段 | 默认 | 说明 |
|------|------|------|
| `highestSystemLoad` | -1（不生效） | Load 阈值（Unix 系统才采集） |
| `highestCpuUsage` | -1 | CPU 使用率阈值（0~1） |
| `avgRt` | -1 | 入口平均 RT 阈值 |
| `maxThread` | -1 | 入口并发线程阈值 |
| `qps` | -1 | 入口 QPS 阈值 |

> ⚠️ **Load 指标平台限制**：`highestSystemLoad` 依赖 Unix 系统指标（Windows 下无效）；**CPU 使用率是最通用的一项**（跨平台），生产优先配 CPU + 入口 QPS。

## 3. BBR 自适应原理

Sentinel 系统保护不是简单"超阈值就全拒"，而是用 **BBR（Bottleneck Bandwidth and Round-trip propagation，瓶颈带宽与往返传播时间）** 思路**自适应调节**：

```text
BBR 核心思想：
    系统有个"临界点"（拐点）：RT 开始暴涨的入口 QPS 拐点
    在拐点之前：RT 平稳 → 可继续放流量
    过了拐点：RT 急剧上升 → 说明系统瓶颈已到 → 按当前 RT 反推合理 QPS

Sentinel 落地：
    监控入口 RT 与 QPS
    当系统指标（Load/CPU）超阈值时，用当前平均 RT 推算一个安全 QPS：
        安全 QPS ≈ min(系统允许的 QPS, 由 RT 反推的值)
    规则设置的最高阈值被动态压低 → 达到"自适应限流"
```

| 对比 | 固定阈值限流 | BBR 自适应 |
|------|------------|-----------|
| 阈值来源 | 人工拍脑袋 | 根据系统实时 RT/Load 动态推算 |
| 流量高峰 | 阈值低了误杀、高了打死 | 逼近系统真实瓶颈自动调节 |
| 维护 | 压测 + 人工调参 | 设上限即可，机器自适应 |
| 场景 | 接口级（规则精确） | **系统级兜底（大促自动降）** |

> 🎯 面试必答：**"Sentinel 系统保护怎么自适应？"**——监测系统 Load/CPU 等指标，超阈值后用 **BBR 思路**：以当前入口平均 RT 反推系统瓶颈 QPS，把全局限流阈值**动态调低到安全值**，系统恢复后阈值回升——**不靠人工设死阈值，机器自己找平衡点**。

## 4. 授权规则（黑白名单）

控制"谁"能访问资源——按调用来源（应用名/来源标识）放行或拒绝：

| 类型 | 含义 | 配置 |
|------|------|------|
| **白名单** | 只允许指定来源 | `limitApp` = 来源列表，`strategy=WHITE` |
| **黑名单** | 拒绝指定来源 | `limitApp` = 来源列表，`strategy=BLACK` |

```java
// 只允许 gateway 与 admin 调用（白名单）
AuthorityRule rule = new AuthorityRule();
rule.setResource("order:create");
rule.setStrategy(RuleConstant.AUTHORITY_WHITE);      // 白名单
rule.setLimitApp("gateway,admin");                    // 允许的来源（逗号分隔）

// 调用来源由 RequestOriginParser 解析（自定义从 Header/参数取来源）
public class HeaderOriginParser implements RequestOriginParser {
    @Override
    public String parseOrigin(HttpServletRequest request) {
        return request.getHeader("X-Origin");         // 网关注入的来源标识
    }
}
```

| 要点 | 说明 |
|------|------|
| 来源获取 | 需实现 `RequestOriginParser` 自定义解析（默认空） |
| 常见来源 | 网关转发的 Header（如 `X-Origin: gateway`） |
| 拦截行为 | 白名单外/黑名单内 → 抛 `AuthorityException`（BlockException 子类） |
| 场景 | 内部接口禁外部直连、管理接口限来源调用 |

> ⚠️ **授权规则前提**：不实现 `RequestOriginParser` 时来源恒为空——**白名单会全拒、黑名单会全放**，规则形同虚设或误杀；接入时先确认来源解析链路（[09 篇](09-集成地图与常见问题.md)）。

## 5. 与限流/熔断的配合

```text
完整防护体系（按触发位置）：
    入口层：Gateway 限流（网关适配器）
    接口层：FlowRule 限流（QPS/线程）＋ ParamFlowRule 热点限流
    故障层：DegradeRule 熔断（RT/异常比例/异常数）
    全局层：SystemRule 系统保护（Load/CPU/入口 QPS）
    访问层：AuthorityRule 授权（黑白名单）

配置顺序建议：先接口限流（保容量）→ 再熔断（保故障）→ 后系统保护（保进程）
```

| 场景 | 推荐组合 |
|------|---------|
| 普通接口 | 限流（QPS）+ 熔断（异常比例） |
| 慢接口 | 限流（线程数）+ 熔断（慢调用比例） |
| 大促全站 | 系统保护（CPU/QPS）+ 热点限流 |
| 内部接口 | 授权白名单 |
| 秒杀 | 热点限流 + 匀速排队 + 系统保护 |

## 6. 面试高频题

| 面试题 | 一句话答案 |
|--------|-----------|
| Sentinel 系统保护是什么？ | 全局兜底闸门：Load/CPU/RT/线程/QPS 五项指标超限全局限流 |
| BBR 是什么？ | 自适应限流算法：按当前 RT 反推系统瓶颈 QPS，动态调节全局阈值 |
| 授权规则怎么用？ | 实现 RequestOriginParser 取来源 → 黑白名单放行/拒绝 |
| 系统保护和限流区别？ | 限流单资源；系统保护全局（濒危兜底） |
| 大促怎么防全站雪崩？ | 系统保护（CPU/入口 QPS）+ 热点限流 + 网关限流三层 |
