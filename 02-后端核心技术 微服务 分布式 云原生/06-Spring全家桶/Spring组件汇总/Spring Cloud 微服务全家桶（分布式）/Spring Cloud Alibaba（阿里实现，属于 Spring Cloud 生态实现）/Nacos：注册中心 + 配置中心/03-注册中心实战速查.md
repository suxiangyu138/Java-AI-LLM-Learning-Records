## 1. 注册与发现的机制

**通俗**：实例启动 → 告诉 Nacos"我在这（IP:port）"→ Nacos 存进服务列表 → 消费者订阅服务名 → 有实例变化（上线/下线/故障）实时通知消费者——**地址信息永不硬编码**。

```text
Provider（user-service 实例 A/B）
  │ ① 注册（gRPC）
  ▼
Nacos Server（naming 模块）
  │ ② 存储 + 心跳维护（5s 心跳，15s 未到标记不健康，30s 移除）
  ▼
Consumer（order-service）── ③ 订阅 user-service（gRPC 长连接）
  │ ④ 实例变化（A 下线/B 新增）→ 推送通知 → 更新本地缓存
  ▼
OpenFeign 按服务名调用（LoadBalancer 从缓存列表选实例）
```

| 环节 | 机制 | 关键参数 |
|------|------|---------|
| 注册 | 启动时 gRPC 上报实例 | `spring.cloud.nacos.discovery.*` |
| 心跳 | 客户端 5s 一次（3.x gRPC 保活） | `heart-beat-interval` |
| 不健康判定 | 15s 未心跳标记不健康 | `ip-delete-timeout`（30s 移除） |
| 订阅 | 消费者 gRPC 长连接（增量推送） | 自动 |
| 下线 | 优雅停机自动注销（Spring 监听） | 默认开启 |

> 🎯 面试必答：**"Nacos 服务发现和 Eureka 的机制区别？"**——相同：都是"注册 + 心跳 + 客户端缓存 + 变更通知"模式；不同：① Nacos 2.x 起用 **gRPC 长连接**（Eureka 是 HTTP 轮询拉取，延迟高）；② Nacos 支持**权重/保护阈值/命名空间**；③ Eureka 纯 AP 停更，Nacos 有 AP/CP 双模式——**机制同源、能力更全**。

## 2. 配置项全表

```yaml
spring:
  cloud:
    nacos:
      server-addr: localhost:8848      # 服务端地址（IP:port，不带 http://）
      username: nacos                  # 3.x 鉴权必配（客户端身份）
      password: nacos
      discovery:
        enabled: true                  # 注册开关
        service: user-service          # 注册名（默认 spring.application.name）
        group: DEFAULT_GROUP           # 分组
        namespace: public              # ★ 命名空间 ID（不是名称）
        ip: 10.0.0.5                   # 自定义注册 IP（容器/多网卡场景）
        port: 8080                     # 自定义注册端口
        weight: 1.0                    # 权重（负载均衡比例）
        ephemeral: true                # 临时实例（默认；false=持久实例，3.x 简化）
        cluster-name: DEFAULT          # 集群名（同机房实例归组）
        heart-beat-interval: 5000      # 心跳间隔 ms
        ip-delete-timeout: 30000       # 无心跳移除时间 ms
        register-enabled: true         # 是否注册（只消费不注册设 false）
```

> ⚠️ **namespace 配 ID 不是名字**（[02 篇](02-快速开始与部署速查.md) 5 节）；`register-enabled: false` 用于"纯消费者"（不提供服务的网关/任务，减少无用注册）。

## 3. 命名空间与分组隔离

### 3.1 两级隔离模型

```text
Namespace（环境级：prod/test/dev 或租户）
  └── Group（业务级：DEFAULT_GROUP / ORDER_GROUP / USER_GROUP）
        └── Service（服务名）
```

| 维度 | 用途 | 例子 |
|------|------|------|
| **Namespace** | 环境/租户隔离 | prod 命名空间、test 命名空间——**服务与配置都不互通** |
| **Group** | 同环境内业务分组 | 订单域 ORDER_GROUP、用户域 USER_GROUP |
| Service | 单个服务 | user-service（服务名唯一） |

```yaml
# 测试环境消费者：只发现测试环境的 user-service
spring:
  cloud:
    nacos:
      server-addr: localhost:8848
      discovery:
        namespace: 7d9f2c8e-xxxx-xxxx  # 测试环境命名空间 ID
        group: DEFAULT_GROUP
```

> 🎯 面试必答：**"namespace 和 group 怎么用？"**——namespace 管**环境/租户隔离**（prod 的 user-service 与 test 的 user-service 互不可见，配置也隔离）；group 管**同环境内的逻辑分组**（灰度组/业务域）；**默认全部 public + DEFAULT_GROUP**——生产按"环境 → 命名空间、域 → 分组"规划，别裸奔默认。

### 3.2 常见隔离方案

| 方案 | 做法 | 适用 |
|------|------|------|
| 环境隔离 | 每环境一个 namespace | **标准做法** |
| 业务域隔离 | 每域一个 group | 多域共环境 |
| 灰度隔离 | 灰度环境 namespace + 灰度服务 group | 发布灰度 |

## 4. 权重、保护阈值与健康检查

### 4.1 权重（Weight）

```text
weight=1.0：正常参与负载均衡
weight=0：不参与流量（灰度观察/下线前摘流量）
weight=0.2：少分流量（机器差/压测中）
```

```yaml
spring:
  cloud:
    nacos:
      discovery:
        weight: 0.2          # 客户端注册时指定
# 或控制台动态调整（不重启）
```

> 💡 权重应用：① **发布摘流量**（先 weight=0 等存量请求结束再下线）；② **灰度放量**（新版本 weight=0.1 → 0.5 → 1）；③ 控制台操作即时生效（配合 LoadBalancer 的权重支持，[05 篇](#5-与-loadbalancer--openfeign-联动)）。

### 4.2 保护阈值（Protect Threshold）

**通俗**：健康实例比例太低时，**宁可把请求发给不健康实例，也不让大部分流量集中在少数健康实例上**——防"健康实例被压垮 → 全挂"的雪崩。

```text
服务 user-service：10 个实例，8 个不健康
保护阈值 = 0.8（80%）
健康比例 = 2/10 = 0.2 < 0.8 → 触发保护：向全部 10 个（含不健康）分发
（否则 8 个实例的流量全压到 2 个健康实例上 → 这 2 个也被压垮 → 全服务不可用）
```

| 要点 | 说明 |
|------|------|
| 设置 | 控制台服务详情 → 保护阈值（0-1） |
| 语义 | 健康比例 < 阈值 → 容忍不健康实例参与分发 |
| 代价 | 请求可能打到不健康实例（调用失败率上升）——**两害相权** |
| 适用 | 实例数多的服务（实例少时保护意义有限） |

### 4.3 健康检查

| 检查方式 | 机制 | 3.x 状态 |
|---------|------|---------|
| 客户端心跳（临时实例） | gRPC 保活 + 心跳（默认） | ✅ 默认 |
| 服务端主动探活 | TCP/HTTP 探测（持久实例） | 3.x 简化（[00 篇](00-Nacos知识体系总览.md) 2.1） |

> ⚠️ **健康状态 ≠ 业务可用**：Nacos 的"健康"是"网络可达 + 心跳正常"——**业务自检（数据库连接、依赖健康）要用自定义健康检查**（Spring Actuator /health 与注册心跳分离认知）。

## 5. 与 LoadBalancer / OpenFeign 联动

### 5.1 联动链路

```text
OpenFeign @FeignClient("user-service")
  → Spring Cloud LoadBalancer（服务名 → 实例列表）
      → NacosServiceDiscovery.getInstances（本地缓存，订阅增量）
      → 按策略选实例（轮询/随机/权重——NacosLoadBalancer 支持权重）
  → 发起 HTTP 调用
```

### 5.2 落地配置

```yaml
# 依赖：LoadBalancer（2020 后 Ribbon 移除，必须显式引）
# spring-cloud-starter-loadbalancer

# Nacos 权重感知（NacosLoadBalancer）
spring:
  cloud:
    loadbalancer:
      nacos:
        enabled: true        # 启用 Nacos 权重负载均衡（按 discovery.weight 分配）
```

```java
// 编程式取实例（排障/灰度定制）
@Autowired
NacosServiceManager nacosServiceManager;

List<Instance> instances = nacosServiceManager.getNamingService()
        .selectInstances("user-service", "DEFAULT_GROUP", true);   // healthy=true
// selectInstances 带负载均衡语义（按权重选一个）：selectOneHealthyInstance(...)
```

> ⚠️ 联动三大坑：① **缺 loadbalancer 依赖** → 服务名调用报 `No instances available`；② 权重生效需 `loadbalancer.nacos.enabled=true`（默认可能只轮询）；③ 自定义 LoadBalancer 规则时注意与 Nacos 权重的取舍（[09 篇](09-集成地图与常见问题.md)）。

## 6. 编程式 NamingService

> 非 Spring 场景（原生 Java/工具类）直接使用 nacos-client API：

```java
// 原生客户端注册与发现
Properties props = new Properties();
props.put("serverAddr", "localhost:8848");
props.put("username", "nacos"); props.put("password", "nacos");
NamingService naming = NamingFactory.createNamingService(props);

// 注册
naming.registerInstance("user-service", "10.0.0.5", 8080);

// 发现（拉取 + 订阅）
List<Instance> instances = naming.selectInstances("user-service", true);
naming.subscribe("user-service", event -> {
    NamingEvent e = (NamingEvent) event;
    // 实例变化通知（上线/下线/权重变更）
});
```

> 💡 编程式场景：**非 Spring 服务**（Python/Go 侧通过 HTTP API；Java 工具类）注册发现；Spring 项目一律用 starter（自动装配，别重复造轮子）。

## 7. 注册中心实战红线

| # | 红线 | 说明 |
|---|------|------|
| 1 | 服务名统一 | `spring.application.name` 全公司规范（别大小写/前后缀混乱） |
| 2 | 环境必须 namespace 隔离 | 测试环境连到生产注册中心 = 生产事故 |
| 3 | 9848 端口必须开 | gRPC 主链路（[02 篇](02-快速开始与部署速查.md)） |
| 4 | 纯消费者 register-enabled=false | 网关/定时任务别做无用注册 |
| 5 | 下线前先摘流量 | weight=0 → 等存量 → 优雅停机（发布规范） |
| 6 | 保护阈值合理设 | 默认 0（不保护）在实例批量挂时等于雪崩助推器 |
| 7 | 客户端鉴权必配 | 3.x 服务端鉴权开，客户端不配 = 静默失败（[07 篇](07-安全与权限速查.md)） |
| 8 | 别把 Nacos 当配置字典 | 大配置/密钥管理用专业方案（配置中心红线见 [04 篇](04-配置中心实战速查.md)） |

> 🎯 注册中心自检五问：① 服务名规范吗？② 环境隔离了吗（namespace）？③ 9848 通吗？④ 纯消费者不注册了吗？⑤ 发布有"摘流量→下线"流程吗？——五问过了再上生产。
