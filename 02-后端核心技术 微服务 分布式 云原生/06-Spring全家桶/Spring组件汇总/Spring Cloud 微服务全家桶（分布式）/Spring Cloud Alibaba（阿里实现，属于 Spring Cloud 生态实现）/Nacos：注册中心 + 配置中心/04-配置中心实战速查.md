## 1. dataId 规则与配置定位

**通俗**：dataId 是 Nacos 里配置文件的名字，命名规则 `服务名-环境.后缀`——客户端按这个名字去拉自己的配置。

```text
dataId = ${spring.application.name}[-${spring.profiles.active}].${file-extension}

例子：
  user-service.yaml              # 默认配置（所有环境都加载）
  user-service-dev.yaml          # dev 环境专属
  user-service-prod.yaml         # prod 环境专属
  user-service-prod-grayscale.yaml  # 灰度环境
```

```yaml
spring:
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        file-extension: yaml        # ★ dataId 后缀（yaml/properties）
        prefix: user-service        # dataId 前缀（默认 = spring.application.name）
        # group: DEFAULT_GROUP      # 配置分组
        # namespace: prod-id        # 配置命名空间（与注册中心同一套隔离）
```

| 要素 | 说明 |
|------|------|
| prefix | 默认 = `spring.application.name`（通常不配） |
| profile | `spring.profiles.active` 自动拼进 dataId（dev/prod） |
| file-extension | **必须配置**（yaml/properties），不配默认 properties |
| namespace | 配置的命名空间（多环境隔离，**配 ID**） |
| group | 配置分组（默认 DEFAULT_GROUP） |

> ⚠️ **环境映射不是自动的**：`spring.profiles.active=dev` 只会让客户端去拉 `user-service-dev.yaml`——**前提是 Nacos 控制台里建了这个 dataId**；建配置时命名不按规则 = 客户端拉不到（[09 篇](09-集成地图与常见问题.md) 高频坑）。

## 2. 配置加载顺序与优先级

```text
优先级从高到低：
① Nacos 远程配置（dataId 匹配的）
   ├─ user-service-prod.yaml（带 profile 的）
   └─ user-service.yaml（通用）
② 本地 bootstrap.yml（Nacos 连接/早期配置）
③ 本地 application.yml（本地兜底）

同名 key：远程 > 本地——远程一改，本地覆盖失效
```

| 场景 | 配置放哪 |
|------|---------|
| 数据库/Redis 连接、业务开关 | **Nacos 远程**（动态调整） |
| Nacos 连接地址、启动早期参数 | bootstrap.yml（需 `spring-cloud-starter-bootstrap`） |
| 本地兜底/不走 Nacos 的环境 | application.yml |

> 💡 **bootstrap vs application**：用 bootstrap.yml 加载 Nacos 配置需要显式引入 `spring-cloud-starter-bootstrap`（2020 后默认移除）——**否则配置在 application 阶段才加载，部分早期初始化（数据源等）用不到远程配置**；新版也可用 `spring.config.import` 方式（`spring.config.import: nacos:user-service.yaml`，[09 篇](09-集成地图与常见问题.md) 两种姿势）。

## 3. 动态刷新：@RefreshScope 全解

### 3.1 使用姿势

```java
// 姿势一：@Value（简单字段）
@RefreshScope                      // ★ 必须加，否则配置变更不更新
@Component
public class OrderConfig {
    @Value("${order.timeout:3000}") private int timeout;
}

// 姿势二：@ConfigurationProperties（推荐，类型安全）
@RefreshScope                      // ★ 也要加
@ConfigurationProperties(prefix = "order")
@Component
public class OrderProperties {
    private int timeout;
    private boolean retryEnabled;
    // getter/setter
}
```

```text
刷新链路：
控制台改配置发布
  → Nacos 服务端长轮询感知变更 → 推送
  → 客户端 ConfigService 收到变更 → 发布 RefreshEvent
  → @RefreshScope Bean 销毁重建 → 新配置生效（毫秒~秒级）
```

| 要点 | 说明 |
|------|------|
| @RefreshScope 作用 | 标记的 Bean 在配置变更时**重建**（新值注入） |
| 生效范围 | 只有 @RefreshScope 的 Bean 刷新；普通 Bean 保持旧值 |
| 推荐姿势 | **@ConfigurationProperties + @RefreshScope**（类型安全、嵌套支持） |
| 不刷新的数据源 | 数据源等启动期 Bean 通常不刷新（重建连接代价大）——**动态切库用专门方案** |

### 3.2 刷新失效排查（面试必答）

| # | 症状 | 根因 | 解法 |
|---|------|------|------|
| ① | 配置改了不生效 | 缺 `nacos-config` starter（只有 discovery） | 引 config starter |
| ② | @Value 不更新 | 类没加 @RefreshScope | 加 @RefreshScope |
| ③ | @ConfigurationProperties 不更新 | 没加 @RefreshScope / 类没被扫描 | 加注解 + @Component |
| ④ | 静默不刷新（无报错） | 服务端开了鉴权但客户端没配账号 | 客户端配 username/password（[07 篇](07-安全与权限速查.md)） |
| ⑤ | 版本跨大版本 | client 3.x ↔ server 2.x | 版本对齐（[01 篇](01-模块清单.md) 矩阵） |
| ⑥ | 拉不到配置 | dataId/namespace 不匹配 | 控制台核对 dataId 规则 + namespace ID（[09 篇](09-集成地图与常见问题.md)） |

> 🎯 面试必答：**"配置怎么做到动态刷新？"**——答机制四步：① 客户端启动拉取配置（NacosPropertySourceLocator）；② **长轮询**挂起等待（服务端 30s 无变更则返回，客户端再发起——变更时立即返回）；③ 服务端配置变更 → 长轮询响应 → 客户端发 RefreshEvent；④ **@RefreshScope Bean 重建**注入新值——**加分句**："@Value 与 @ConfigurationProperties 都行，但推荐后者（类型安全）；数据源类 Bean 不刷新（连接重建代价大）"。

## 4. 多环境管理

| 环境 | 做法 | 说明 |
|------|------|------|
| dev/test/prod | **命名空间隔离**（每环境一个 namespace ID） | 配置与服务同时隔离（[03 篇](03-注册中心实战速查.md) 3 节） |
| 环境内 profile | dataId 带 profile（user-service-dev.yaml） | 同命名空间内细分 |
| 灰度 | 灰度命名空间 + 灰度 dataId | 发布灰度配套 |
| 本地开发 | 本地 application.yml（不连 Nacos 或连 dev） | 联调自由 |

```yaml
# dev 环境客户端
spring:
  profiles:
    active: dev
  cloud:
    nacos:
      server-addr: nacos-dev.example.com:8848
      config:
        namespace: <dev-命名空间-ID>
        file-extension: yaml
```

> 💡 环境治理口诀：**"环境 = 命名空间，环境内细分 = profile（dataId）"**——改环境只改 `namespace` + `profiles.active`，代码零改动。

## 5. 扩展配置与共享配置

**通俗**：多个服务要共用一份配置（Redis 地址、公共开关）——用"共享/扩展配置"抽公共部分。

```yaml
spring:
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        file-extension: yaml
        # 扩展配置（本服务专属，可多份）
        ext-config:
          - dataId: user-service-ext.yaml
            group: DEFAULT_GROUP
            refresh: true               # ★ 显式指定（不配默认 false？——按版本，显式最稳）
        # 共享配置（多服务共用）
        shared-configs:
          - dataId: common-redis.yaml
            group: COMMON_GROUP
            refresh: true
```

| 要点 | 说明 |
|------|------|
| shared-configs | 跨服务共享（公共组件配置） |
| ext-config | 本服务额外配置（拆分多文件） |
| **refresh 必须显式** | 官方坑：某组 refresh 不显式配，整组不监听变更（[09 篇](09-集成地图与常见问题.md)） |
| 优先级 | 主 dataId > ext-config > shared-configs（后者被前者覆盖） |

> ⚠️ **共享配置的坑**：① refresh 必须显式 true（否则共享配置改了不生效）；② 共享配置变更影响所有引用服务（**发布前评估影响面**，用灰度/低峰期）；③ 敏感配置（密钥）别放共享配置（权限粒度在命名空间级）。

## 6. 配置回滚、灰度与审计

### 6.1 回滚（控制台）

```text
控制台 → 配置管理 → 配置列表 → 详情 → 历史版本
  → 选择版本 → 回滚（一键恢复历史配置）
```

| 要点 | 说明 |
|------|------|
| 历史版本 | Nacos 保留配置变更历史（默认 10 条？按版本） |
| 回滚时机 | 配置改错/发布事故 |
| 回滚即发布 | 回滚 = 发布历史版本（客户端同样走推送链路） |

### 6.2 灰度与审计

| 能力 | 说明 |
|------|------|
| 灰度发布 | 控制台 beta 发布（指定 IP 灰度生效，其余仍旧值）——**配置灰度发布**（3.x 支持 beta 发布） |
| 审计 | 配置变更记录（谁、何时、改成什么——控制台历史 + 日志） |
| 权限 | 配置读写按命名空间/分组授权（[07 篇](07-安全与权限速查.md) RBAC） |

> 💡 生产规范：**关键配置（数据源、开关）变更走"灰度 → 观察 → 全量"**——与代码发布同等对待，别把配置当"随手改的文本"。

## 7. 配置中心实战红线

| # | 红线 | 理由 |
|---|------|------|
| 1 | **敏感信息放 Nacos 明文** | 密钥/证书建议配置中心 + 加密插件（Nacos 支持加密插件）或引专业密钥管理 |
| 2 | 大配置（> 1MB）塞 Nacos | 长轮询/推送压力大；大文件用对象存储 |
| 3 | 配置变更无灰度直接全量 | 改错 = 全服务事故（用 beta 灰度 + 历史回滚） |
| 4 | @Value 滥用 | 全局搜 @Value 换 @ConfigurationProperties（类型安全） |
| 5 | 不配 file-extension | 默认 properties，yaml 内容拉不到 |
| 6 | 共享配置 refresh 不显式 | 改了不生效的隐形坑 |
| 7 | 配置与代码不同步管理 | 配置变更要有审计/文档（重要配置变更记录） |
| 8 | 本地配置覆盖远程依赖 | 别在 application.yml 里写同 key（远程优先级被本地覆盖——注意方向：远程 > 本地） |

> 🎯 配置中心自检五问：① dataId 命名规范吗？② 环境 namespace 隔离了吗？③ 动态字段都 @RefreshScope 了吗？④ 共享配置 refresh 显式了吗？⑤ 关键配置有灰度与回滚预案吗？——五问过了再上生产。
