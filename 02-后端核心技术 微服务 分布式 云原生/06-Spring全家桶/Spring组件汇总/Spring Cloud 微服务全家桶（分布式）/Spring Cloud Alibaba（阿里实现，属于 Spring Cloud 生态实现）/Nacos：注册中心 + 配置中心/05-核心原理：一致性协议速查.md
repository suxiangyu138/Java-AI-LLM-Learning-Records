## 1. CAP 视角：注册中心为什么默认 AP

**通俗**：注册中心面对的场景是"实例地址列表"——**短暂的不一致（刚下线的实例还被调用一次）可接受，注册中心不可用不可接受**——所以默认 AP。

| CAP 取舍 | AP（默认） | CP（可选） |
|---------|-----------|-----------|
| 可用性（A） | ✅ 节点挂了照常服务（可能读到旧列表） | ⚠️ 多数派不可达则拒绝写 |
| 一致性（C） | ⚠️ 短暂不一致（下线感知有延迟） | ✅ 强一致（写多数派成功才返回） |
| 分区容忍（P） | ✅ | ✅ |
| 典型实现 | Distro（Nacos AP） | JRaft（Nacos 3.x CP）、ZK、etcd |
| 适用 | **服务注册默认（业务可容忍短暂旧列表）** | 强一致场景（选主/分布式锁类元数据） |

> 🎯 面试必答：**"为什么注册中心默认 AP 而不是 CP？"**——注册数据的语义是"**读到旧列表可用、读不到不可用**"：服务下线后，消费者多调用旧地址一次（重试/负载均衡会绕开）问题不大；但注册中心因选举不可用（CP 多数派故障）时**所有服务无法注册/发现 = 全系统不可用**——**可用性优先更符合注册场景**；ZK 当年选 CP 是历史设计，Nacos 用 AP/CP 双模式覆盖两种需求。

## 2. AP 模式：Distro 协议

```text
Nacos-1 ──► 写入实例 A（本节点内存 + 同步副本）
Nacos-2 ──► 写入实例 B（本节点 + 同步 Nacos-1/3）
Nacos-3 ──► 写入实例 C

写：任意节点可写（不要求多数派确认）→ 高可用
同步：异步复制到其他节点（Distro 协议）
读：客户端从任意节点拉（本地缓存）
一致性窗口：节点间复制延迟（秒级）——下线感知有延迟
```

| Distro 特征 | 说明 |
|------------|------|
| 写模型 | **任意节点可写**（无主）→ 单点故障不影响写 |
| 数据同步 | 节点间异步复制（增量 + 快照） |
| 一致性 | 最终一致（窗口秒级） |
| 故障 | 单节点挂：其上的实例数据由其他节点副本兜底 |
| 适用 | 默认注册模式（实例列表语义容忍窗口） |

## 3. CP 模式：JRaft（3.0 引入）

```text
Nacos-1（Leader）── 写请求 ──► 复制到 Nacos-2/Nacos-3（Follower）
        │  多数派确认（2/3）→ 返回成功
        ▼
Leader 故障 → Follower 选举新 Leader（多数派投票）
```

| JRaft 特征 | 说明 |
|-----------|------|
| 协议 | Raft 类（Leader 选举 + 日志复制 + 多数派确认） |
| 写 | **只走 Leader**，多数派（2/3）确认才成功 |
| 读 | Leader 读（可线性一致） |
| 故障 | Leader 挂 → 秒级选举新 Leader |
| 3.0 意义 | 注册数据可强一致（选主/状态类场景） |
| 端口 | 7848（JRaft 通信，集群内） |
| 适用 | 强一致元数据（**默认仍 AP，按需切 CP**） |

> 💡 3.x 的 CP 模式定位：**不是替代 AP**，而是"按数据场景选模式"——普通服务注册用 AP（可用性优先），强一致需求（如集群内选主/特殊元数据）用 CP；官方默认与推荐仍是 AP（注册场景）——**面试答"双模式"而不是"CP 更好"**。

## 4. 客户端通信：长轮询与 gRPC

### 4.1 配置中心：长轮询

```text
客户端 ──► 发起长轮询（30s 服务端挂起）
服务端 ──► 配置无变更：30s 后返回"无变更"→ 客户端立即再发起
服务端 ──► 配置有变更：立即返回 → 客户端拉取新配置
          （客户端监听 @RefreshScope 刷新）
```

| 长轮询特征 | 说明 |
|-----------|------|
| 本质 | HTTP 请求挂起（服务端 hold 住请求，有变更立即响应） |
| 延迟 | 变更 → 客户端感知：**毫秒级**（30s 是"无变更时的心跳周期"） |
| 压力 | 每客户端一个挂起连接（万级服务 OK） |
| 对比 | 轮询（每 30s 无脑拉）vs 长轮询（挂起等变更）——**省流量省延迟** |

### 4.2 注册中心：gRPC 长连接（2.x 起）

```text
客户端 ── gRPC 长连接（9848）──► 服务端
   ├─ 注册/心跳（连接保活，替代 1.x 的 HTTP 心跳）
   ├─ 订阅（服务端有变更 → 连接上推送）
   └─ 双向流（客户端上报 + 服务端下发）
```

| gRPC 特征 | 说明 |
|-----------|------|
| 端口 | 9848（= 8848 + 1000），**必须放行**（[02 篇](02-快速开始与部署速查.md)） |
| 心跳 | gRPC 保活（替代 1.x HTTP 心跳轮询） |
| 推送 | 服务端主动推送实例变更（1.x 是客户端轮询） |
| 1.x 兼容 | 老客户端仍走 HTTP（服务端兼容） |

> 🎯 面试必答：**"Nacos 客户端怎么感知变更？"**——分职责答：**配置中心**用 HTTP **长轮询**（请求挂起 30s，变更立即响应——毫秒级感知）；**注册中心** 2.x 起用 **gRPC 长连接**（订阅 + 服务端推送，替代 1.x 轮询）——**共同点**：都是"长连接/长请求代替短轮询"，变更感知延迟毫秒级、服务端压力可控。

## 5. 集群选主与数据同步

### 5.1 两种模式的集群行为

| 环节 | AP（Distro） | CP（JRaft） |
|------|-------------|-------------|
| 主节点 | **无主**（人人可写） | **有 Leader**（选举产生） |
| 节点挂 | 副本数据兜底，服务不中断 | Leader 挂 → 秒级选举 |
| 脑裂 | 无主天然免疫 | 多数派机制免疫（少数派拒绝写） |
| 数据同步 | 异步复制 | 日志复制 + 多数派确认 |
| 集群最小规模 | 2+（越多越稳） | **3（多数派=2）** |

### 5.2 选举与同步要点（JRaft）

```text
选举：Follower 超时未收到 Leader 心跳 → 变 Candidate → 拉票 → 多数派同意 → 新 Leader
复制：写请求 → Leader 本地落盘 → 复制到 Follower → 多数派 ACK → 提交 → 响应客户端
快照：数据量大时定期打快照（压缩日志）
```

> 💡 JRaft 与 ZooKeeper 的 Zab、etcd 的 Raft 是同类协议——**概念通用**（Leader 选举/日志复制/多数派），学一个通三个（[ZooKeeper 深度](../../../../../09-Web开发全流程/ZooKeeper/00-ZooKeeper知识体系总览.md) 对照理解）。

## 6. 与 ZK / Eureka 一致性对照（面试必考）

| 维度 | Nacos（AP 默认） | Eureka（AP） | ZooKeeper（CP） |
|------|-----------------|-------------|----------------|
| 协议 | Distro（AP）/ JRaft（CP） | 无协议（纯最终一致） | Zab（CP） |
| 写模型 | 任意节点可写 | 任意节点可写 | 只走 Leader |
| 读一致性 | 最终一致（秒级窗口） | 最终一致（更长窗口） | **强一致**（Leader 读） |
| 节点故障 | 副本兜底 | 副本兜底 | 选举期间不可写 |
| 健康检查 | 心跳 + 可扩展 | 心跳 | Session（临时节点） |
| 配置中心 | ✅ 内建 | ❌ | ⚠️ znode 可模拟 |
| 适合 | 服务注册（默认 AP） | 服务注册（历史） | 协调/选主（强一致） |
| 维护 | **活跃（2026 AI 转型）** | 停更 | 活跃 |

> 🎯 面试必答：**"Nacos、Eureka、ZooKeeper 怎么选？"**——答三层：① 服务注册（默认场景）：**Nacos**（注册+配置一体、AP 双模式、活跃维护）——Eureka 停更；② 强一致协调（选主/分布式锁/元数据）：**ZK/etcd**（CP 强一致，专业协调器）；③ 结论：**"注册用 Nacos（AP），协调用 ZK（CP），别混用"**——加分句：Nacos 3.x 的 CP 模式（JRaft）也能覆盖部分强一致场景，但专业协调器生态（watcher/临时节点语义）仍更成熟。
