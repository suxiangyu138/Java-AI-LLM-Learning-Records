## 1. 高可用架构全景

```text
                    ┌── 客户端（服务/消费者）──┐
                    │  server-addr: nacos.example.com │
                    └───────────┬──────────┘
                        Nginx（负载 + 健康检查）
              ┌────────────┬───┴────┬────────────┐
        ┌─────▼────┐ ┌─────▼────┐ ┌─▼──────┐
        │ Nacos-1  │ │ Nacos-2  │ │ Nacos-3 │   ← 3 节点（JRaft/Distro 同步）
        └─────┬────┘ └─────┬────┘ └────┬────┘
              └───── MySQL 主从（数据持久化）──┐
                    ┌─────▼────┐
                    │ MySQL-M │ ← 主
                    └─────┬────┘
                    ┌─────▼────┐
                    │ MySQL-S │ ← 从（备份/容灾）
                    └─────────┘
```

| 层级 | 高可用手段 | 说明 |
|------|-----------|------|
| 客户端入口 | Nginx 负载 + 健康检查 | 单节点挂自动切换（[02 篇](02-快速开始与部署速查.md) 4 节） |
| Nacos 节点 | 3 节点集群 | AP 容错 N-1；CP 容错 1 |
| 数据持久化 | **MySQL 主从** | 单实例 MySQL = 单点（配置/注册数据全丢风险） |
| 应用侧 | 客户端多地址 + 容灾目录 | nacos-client 自带本地容灾（`nacos` 容灾目录） |

> 🎯 高可用口诀：**"Nacos 3 节点、MySQL 主从、Nginx 前置、客户端多地址"**——四件事做到，单点风险清零（单 Nacos + 单 MySQL = 伪高可用）。

## 2. 集群规划与容量评估

### 2.1 节点规划

| 规模 | 节点数 | 说明 |
|------|:---:|------|
| 开发/测试 | 1（standalone） | 够用 |
| 小生产（< 100 服务） | 3 | JRaft 多数派（2/3） |
| 中生产（100-500 服务） | 3-5 | 按 QPS 与容错 |
| 大生产（500+ 服务） | 5+ | 分机房部署 |

### 2.2 容量评估维度

| 维度 | 参考指标 | 说明 |
|------|---------|------|
| 服务数 | 单集群建议 < 2000 服务 | 超限分集群（按域拆） |
| 实例数 | 万级 OK（gRPC 长连接高效） | 2.x 起容量大幅提升 |
| 配置数 | 十万级 OK | 配置按需加载（不全部拉取） |
| 心跳/连接 | 每节点长连接数监控 | gRPC 连接是主要开销 |
| 内存 | 实例数据 + 配置缓存 | 8G 起步（3.x） |
| 磁盘 | MySQL 数据增长 | 配置历史版本会增长（定期清理） |

> 💡 **拆集群的判断**：服务数 > 2000 或跨大域（订单域/用户域）——拆多套 Nacos 集群（按域/环境），**别让一个集群承载一切**（故障半径控制）。

## 3. MySQL 主从与数据安全

```sql
-- ① 主库初始化（02 篇 3 节）+ 建账号
-- ② 从库：主从复制配置（binlog 开启）
CHANGE MASTER TO MASTER_HOST='mysql-m', MASTER_USER='repl', MASTER_PASSWORD='xxx';
START SLAVE;

-- ③ 验证
SHOW SLAVE STATUS\G   -- Slave_IO_Running: Yes / Slave_SQL_Running: Yes
```

| 数据安全要点 | 说明 |
|-------------|------|
| 主从复制 | 从库 = 备份 + 读分担（Nacos 主写从读可配） |
| 定时备份 | 每日 mysqldump（配置/注册数据都是资产） |
| 恢复演练 | 季度演练（主库挂 → 从库提升） |
| 配置历史 | config_info 历史版本定期清理（保留 N 天） |
| 幂等恢复 | 实例数据可重注册（AP 模式），配置数据必须备份 |

> ⚠️ **数据优先级认知**：**配置数据 > 注册数据**——注册实例丢了会自己重注册（客户端心跳），配置丢了是永久丢失（只能从备份恢复）——**MySQL 备份是配置数据的第一道保险**。

## 4. 容灾：多机房与异地双活

| 方案 | 做法 | 适用 |
|------|------|------|
| 同机房多节点 | 3 节点同机房（标准） | 常规生产 |
| 跨机房（主备） | 主集群 + 备集群（数据定期同步，故障切换 DNS） | 中大型 |
| 异地双活 | 双集群各自服务 + 数据双向同步 | 大型（成本高） |
| 客户端容灾 | nacos-client 本地容灾目录（服务端全挂时用本地快照） | **兜底方案（免费）** |

```text
客户端本地容灾（nacos-client 内建）：
  ${user.home}/nacos/naming/xxx 和 ${user.home}/nacos/config/xxx
  服务端全挂 → 客户端读本地快照（注册列表/最后配置）→ 服务不中断（旧数据）
```

> 💡 **容灾认知**：注册中心的容灾核心是"**客户端本地快照**"（nacos-client 内建）——服务端全挂时服务仍用最后已知列表工作；配置容灾同样有本地缓存——**别忘了测试"服务端全挂"场景**（故障演练，[09 篇](09-集成地图与常见问题.md)）。

## 5. 2.x → 3.x 升级迁移清单

> **升级核心约束**：客户端与服务端**同大版本**（SCA 2025.0.x + client 3.0.3 必须配服务端 3.x，[01 篇](01-模块清单.md) 矩阵）。

### 5.1 迁移清单

| # | 动作 | 说明 |
|---|------|------|
| ① | 备份 | MySQL 全量备份 + 配置导出（控制台） |
| ② | 先升服务端（新集群） | 部署 3.2.x 新集群（不直接升生产旧集群） |
| ③ | 灰度验证 | 测试环境全量 → 生产灰度服务切新集群 |
| ④ | 客户端同步升级 | SCA 2025.0.x（client 3.0.3）与 3.x 服务端配套 |
| ⑤ | 行为差异回归 | 3.0 默认鉴权（客户端配账号）、namespace public、UDP PUSH 移除（3.2） |
| ⑥ | 全量切换 | 双注册过渡 → 切流 → 旧集群下线 |

### 5.2 3.x 行为差异（重点回归）

| 差异 | 3.x | 回归要点 |
|------|-----|---------|
| 默认鉴权 | 控制台/API 默认开 | 客户端必须配 username/password（[07 篇](07-安全与权限速查.md)） |
| namespace 默认 | public | 老配置在 public 下可读；自定义 namespace 核对 ID |
| UDP PUSH | 3.2 移除 | 依赖 UDP 推送的老客户端升级 |
| 临时/持久节点 | 模型简化 | 老 ephemeral 语义迁移 |
| CP 模式 | JRaft（新） | 需要强一致时启用（[05 篇](05-核心原理：一致性协议速查.md)） |

> 🎯 迁移心法：**"先备后升、新集群灰度、客户端同步、行为回归"**——升级 Nacos 最大的坑不是服务端，是**客户端版本不配套**（配置静默失效）——迁移第一步永远是对齐版本矩阵。

## 6. 监控与告警

| 监控项 | 手段 | 告警阈值建议 |
|--------|------|-------------|
| 节点存活 | 进程监控 + 控制台集群状态 | 节点数 < 3 告警 |
| 服务注册量 | 控制台服务列表 / API | 异常骤降告警（大量服务掉线） |
| 配置变更 | 控制台历史 + 审计 | 敏感配置变更告警 |
| 客户端连接数 | 服务端指标（gRPC 连接数） | 超容量阈值告警 |
| MySQL | 主从状态（Slave_IO/SQL_Running） | 复制中断立即告警 |
| 磁盘/内存 | 节点资源监控 | 磁盘 > 80% 告警 |
| 客户端侧 | 注册/拉取失败日志告警 | `init nacos ok` 缺失 / Connection refused |

> 🎯 生产监控三件套：**节点（3 节点存活）、MySQL（主从状态）、客户端（注册/拉取失败率）**——三件套告警配齐，Nacos 事故 90% 提前发现。
