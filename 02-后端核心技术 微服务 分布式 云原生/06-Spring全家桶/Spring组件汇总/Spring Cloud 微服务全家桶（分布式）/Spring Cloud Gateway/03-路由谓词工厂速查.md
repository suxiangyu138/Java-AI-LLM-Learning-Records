## 1. 谓词模型：AND 组合与匹配语义

```text
路由匹配 = 该路由所有谓词 AND（全部为 true 才命中）
  └── 多条路由：按定义顺序，第一个全命中者生效（RoutePredicateHandlerMapping 顺序遍历）

示例：
predicates:
  - Path=/orders/**
  - Method=GET        ← 只有 GET /orders/** 命中；POST /orders/** 不命中（换下一条路由）
  - Header=X-Env, prod ← 再加环境头要求
```

| 语义 | 说明 |
|------|------|
| 同路由内 | **AND**：所有谓词都 true 才命中 |
| 路由之间 | 顺序优先：第一条全命中的路由生效 |
| 不命中 | 404（网关不转发，也无兜底） |
| 谓词数量 | 无上限（但越多匹配越慢，按需） |

> 🎯 面试必答：**"多个谓词和多个路由怎么匹配？"**——**谓词之间 AND**（都满足才过），**路由之间顺序优先**（先定义先匹配）；所以"精确路由放前面、兜底路由放后面"是标准写法。

## 2. 请求特征类：Path / Host / Method

### 2.1 Path：路径匹配（最常用）

```yaml
predicates:
  - Path=/red/{segment},/blue/{segment}   # 逗号 = OR 匹配多个模式
  # 参数：matchTrailingSlash（默认 true：/red/1/ 也算匹配；false 则不算）
```

```text
/red/1  → ✅ 命中（{segment}=1，存入 ServerWebExchange 属性供过滤器用）
/red/1/ → ✅（matchTrailingSlash=true 默认）
/blue/green → ✅
/other  → ❌
```

| 特性 | 说明 |
|------|------|
| 模式语法 | Spring PathMatcher（`**` 任意层、`*` 单层、`{var}` 变量） |
| 变量提取 | `{segment}` 提取到 `URI_TEMPLATE_VARIABLES_ATTRIBUTE`（自定义过滤器可取用） |
| 注意 | **Path 谓词不改变转发路径**（剥前缀是 StripPrefix 过滤器的事） |

### 2.2 Host：域名匹配

```yaml
predicates:
  - Host=**.somehost.org,**.anotherhost.org   # Ant 风格，. 分隔
  - Host={sub}.myhost.org                     # {sub} 模板变量
```

```text
www.somehost.org → ✅（**.somehost.org）
beta.somehost.org → ✅
other.org → ❌
```

> 💡 典型用途：**多域名网关**（api.example.com → 一套路由，admin.example.com → 另一套）。

### 2.3 Method：方法匹配

```yaml
predicates:
  - Method=GET,POST     # 逗号 = 匹配任一方法
```

```text
GET /orders/** → ✅（配合 Path 时）
DELETE /orders/1 → ❌（只允许 GET/POST）
```

> 💡 典型用途：**写接口与读接口分流**（GET 走缓存路由，POST 走主路由）。

## 3. 参数类：Header / Query / Cookie

### 3.1 Header：请求头匹配（正则）

```yaml
predicates:
  - Header=X-Request-Id, \d+            # 头名 + Java 正则
```

```text
X-Request-Id: 12345 → ✅（\d+ 命中）
无 X-Request-Id 头 → ❌
X-Request-Id: abc → ❌
```

> 💡 典型用途：**版本头路由、灰度头路由、内部调用标识路由**（X-Env: internal → 内部路由）。

### 3.2 Query：查询参数匹配

```yaml
predicates:
  - Query=green              # 只要求参数存在
  - Query=red, gree.         # 参数 + 值正则（gree. = green/greet...）
```

```text
/goods?green=1 → ✅（第一个）
/goods?red=green → ✅（第二个）
/goods?blue=1 → ❌
```

> 💡 典型用途：**特殊参数路由**（?version=v2 → 新版服务）、**AB 测试参数路由**。

### 3.3 Cookie：Cookie 匹配（正则）

```yaml
predicates:
  - Cookie=chocolate, ch.p    # Cookie 名 + 值正则
```

```text
Cookie: chocolate=chip → ✅
Cookie: chocolate=xxx → ❌（值不匹配）
```

> 💡 典型用途：**登录态路由**（有会话 Cookie → 走认证后的路由）。

## 4. 灰度与流量类：Weight

### 4.1 加权分流

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: weighthigh
              uri: https://weighthigh.org
              predicates:
                - Weight=group1, 8        # 组 + 权重 8
            - id: weightlow
              uri: https://weightlow.org
              predicates:
                - Weight=group1, 2        # 组 + 权重 2
```

```text
group1 内总权重 10：约 80% 流量 → weighthigh，20% → weightlow
```

### 4.2 灰度实践

| 场景 | 组合 |
|------|------|
| 金丝雀发布 | Weight 90/10 新旧版本服务 |
| 分阶段放量 | 5% → 20% → 50% → 100% 调整权重 |
| 版本隔离 | Weight + Header（新版本只接测试头流量） |

> ⚠️ **注意**：Weight 是**随机加权**（非确定性），测试/联调别依赖它；权重路由应配在**最后**（Weight 谓词会干扰其他谓词匹配的确定性）。

## 5. 时间类：After / Before / Between

```yaml
predicates:
  - After=2026-01-01T00:00:00.000+08:00[Asia/Shanghai]    # 该时刻之后
  - Before=2026-12-31T23:59:59.999+08:00[Asia/Shanghai]   # 该时刻之前
  - Between=2026-01-01T00:00:00.000+08:00[Asia/Shanghai], 2026-02-01T00:00:00.000+08:00[Asia/Shanghai]
```

| 谓词 | 语义 | 典型用途 |
|------|------|---------|
| After | 请求时间 ≥ 指定时刻 | 活动上线自动开启路由 |
| Before | 请求时间 < 指定时刻 | 活动下线自动关闭 |
| Between | 指定时间窗口内 | **维护窗口**（期间流量切到维护页） |

> 💡 时间谓词用 **ZonedDateTime 格式**（带时区），服务器时区不一致时务必带时区后缀；时间窗口路由适合"预告定档"场景（0 点自动开售）。

## 6. 地址与内容类：RemoteAddr / XForwardedRemoteAddr / ReadBody

### 6.1 RemoteAddr：客户端 IP（CIDR）

```yaml
predicates:
  - RemoteAddr=192.168.1.1/24      # IP 或 CIDR
```

```text
来源 192.168.1.55 → ✅（/24 网段内）
来源 10.0.0.1 → ❌
```

> 💡 典型用途：**内网/IP 白名单路由**（内部系统只允许办公网访问）。

### 6.2 XForwardedRemoteAddr

```yaml
predicates:
  - XForwardedRemoteAddr=10.0.0.0/24    # 基于 X-Forwarded-For 的远端地址
```

> ⚠️ **安全注意**：X-Forwarded-For 可伪造——用 XForwardedRemoteAddr 时确保前面有可信代理设置该头（[10 篇](10-生产实践与选型避坑.md) 安全坑）。

### 6.3 ReadBody（BETA）

```yaml
predicates:
  - name: ReadBody
    args:
      data-class: com.example.BodyDTO    # 反序列化类型
      predicate: "#{@bodyPredicate}"     # SpEL 引用 Bean 判断
```

```text
流程：读取请求体 → 反序列化为 data-class → 用 predicate Bean 判断
注意：读取后请求体需缓存（配合 CacheRequestBody 过滤器），否则下游读不到体
```

> ⚠️ **BETA 状态**：ReadBody 官方标记 BETA（行为可能变化）；用它必须配 **CacheRequestBody 过滤器**（否则体被读走后下游拿不到）。

## 7. 版本路由类：API Versioning（5.0 新增）

### 7.1 背景

5.0（Oakwood）新增 **API Versioning Predicate**（issue #3864，Server WebFlux）——把"接口版本"从 Path/Header 手写正则，升级为**内置版本匹配谓词**。

### 7.2 用法

```yaml
predicates:
  - ApiVersion=1.0,1.1        # 匹配请求的 API 版本
```

```text
请求带 API 版本信息（版本头/路径版本段）→ 路由到对应版本的服务
  /v1/** → version 1.0 路由
  /v2/** → version 2.0 路由（新旧版本共存）
```

| 版本路由方式对比 | 说明 |
|----------------|------|
| Path 前缀（/v1/** /v2/**） | 传统做法，直观但路径被版本污染 |
| Header 版本头 | 干净但客户端要维护头 |
| **API Versioning 谓词（5.0）** | **内置版本语义**，与谓词体系统一 |

> 💡 版本治理实践：**API 版本路由 + Weight 灰度组合**——版本谓词决定"能不能进"，Weight 决定"进多少"，完整支撑"多版本共存 + 灰度放量"（[10 篇](10-生产实践与选型避坑.md) 灰度方案）。

## 8. 谓词速查总表

| 谓词 | 参数 | 匹配对象 | 典型场景 | 面试价值 |
|------|------|---------|---------|:---:|
| **Path** | 模式列表 + matchTrailingSlash | 请求路径 | 核心路由 | ★★★ |
| **Host** | 域名模式列表 | Host 头 | 多域名网关 | ★★ |
| **Method** | HTTP 方法列表 | 请求方法 | 读写分流 | ★★★ |
| **Header** | 头名 + 正则 | 请求头 | 灰度/版本/认证头 | ★★★ |
| **Query** | 参数名 + 正则 | 查询参数 | 特殊参数路由 | ★★ |
| **Cookie** | Cookie 名 + 正则 | Cookie | 登录态路由 | ★★ |
| **Weight** | 组 + 权重 | 按权重随机 | 灰度分流 | ★★★ |
| **After/Before/Between** | ZonedDateTime | 请求时间 | 活动/维护窗口 | ★★ |
| **RemoteAddr** | IP/CIDR | 客户端 IP | IP 白名单 | ★★ |
| XForwardedRemoteAddr | IP/CIDR | XFF 头 | 代理场景 | ★ |
| ReadBody（BETA） | data-class + SpEL | 请求体 | 内容路由 | ★ |
| **API Versioning** | 版本列表 | 版本信息 | 多版本共存（5.0 新） | ★★（新特性） |
| CloudFoundryRouteService | 无 | — | CF 生态 | ★ |

> 🎯 面试组合拳：**"网关怎么做灰度？"**——**Weight 谓词按权重分流 + Header 谓词按灰度头定向 + 多版本路由共存（API Versioning）**，三层组合：先版本谓词隔离新旧，再 Header 定向测试用户，最后 Weight 逐步放量。
