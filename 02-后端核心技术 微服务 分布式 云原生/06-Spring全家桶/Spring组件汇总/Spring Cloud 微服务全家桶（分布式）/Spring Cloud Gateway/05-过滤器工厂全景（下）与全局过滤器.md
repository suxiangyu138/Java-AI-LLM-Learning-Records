## 1. 防护类：CircuitBreaker 过滤器

### 1.1 用法

```xml
<!-- 网关需引 SCCB 响应式实现（与网关同栈） -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-reactor-resilience4j</artifactId>
</dependency>
```

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: order-service
              uri: lb://order-service
              predicates:
                - Path=/orders/**
              filters:
                - name: CircuitBreaker
                  args:
                    name: orderServiceCB          # ★ 熔断器实例名
                    fallbackUri: forward:/fallback/order   # ★ 熔断/失败时转发到本地兜底端点
```

```java
@RestController
public class FallbackController {
    @GetMapping("/fallback/order")
    public String orderFallback() {
        return "订单服务暂不可用，请稍后再试";
    }
}
```

### 1.2 工作原理

```text
CircuitBreaker 过滤器 → 调用 SCCB ReactiveCircuitBreakerFactory
  ├── 正常：转发到下游
  ├── 下游失败/超时/熔断 OPEN：执行 fallbackUri（本地兜底端点）
  └── 熔断状态由 SCCB 状态机管理（配置见下）

熔断参数（resilience4j.* yaml，与 SCCB 系列共用同一套）：
resilience4j:
  circuitbreaker:
    instances:
      orderServiceCB:
        sliding-window-size: 50
        minimum-number-of-calls: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
```

> 🎯 面试必答：**"网关熔断和服务内熔断什么关系？"**——**同一个 SCCB 底座**：网关用 CircuitBreaker 过滤器（ReactiveCircuitBreakerFactory），服务内用 Factory/注解（阻塞或响应式）——**网关管"入口保护"（fallbackUri 兜底页面），服务内管"调用点保护"（业务级降级）**，两者不冲突，生产常同时配。

### 1.3 fallbackUri 支持

| fallbackUri | 说明 |
|-------------|------|
| `forward:/fallback/xxx` | 转发到网关本地端点（常用，Java 处理） |
| `forward:/fallback` | 静态兜底（可配静态资源） |
| 不配 | 熔断时返回 500/网关错误响应 |

> ⚠️ **注意**：fallbackUri 只能用 `forward:`（本地转发），**不能是外部 URL**——兜底必须在网关自身。

## 2. 防护类：RequestRateLimiter 与 Bucket4j

### 2.1 RequestRateLimiter（Redis 令牌桶，默认实现）

```xml
<!-- 需要 Redis -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis-reactive</artifactId>
</dependency>
```

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: order-service
              uri: lb://order-service
              predicates:
                - Path=/orders/**
              filters:
                - name: RequestRateLimiter
                  args:
                    redis-rate-limiter.replenishRate: 10      # ★ 每秒补充令牌（速率）
                    redis-rate-limiter.burstCapacity: 20      # ★ 桶容量（突发上限）
                    redis-rate-limiter.requestedTokens: 1     # 每请求消耗令牌
                    key-resolver: "#{@userKeyResolver}"       # ★ 限流 key 解析器（按谁限）
```

```java
// 限流 key：按用户/按 IP/按接口
@Bean
public KeyResolver userKeyResolver() {
    return exchange -> Mono.just(
        exchange.getRequest().getRemoteAddress().getAddress().getHostAddress()); // 按 IP
}
```

### 2.2 令牌桶语义

```text
Redis 令牌桶（Lua 脚本原子操作）：
  ├── replenishRate=10：每秒往桶里放 10 个令牌
  ├── burstCapacity=20：桶最大 20 个（突发可打 20）
  └── 请求消耗 requestedTokens 个令牌，桶空 → 429 Too Many Requests

参数关系：
  ├── replenishRate ≤ burstCapacity（桶不能小于补给）
  ├── 稳定 QPS = replenishRate；突发上限 = burstCapacity
  └── 业务换算：接口 P99 流量 × 1.5 余量
```

> ⚠️ **key-resolver 必配**：不配 key-resolver 时**所有请求共用一把锁**（按 IP/用户/接口区分才有意义）——最常见的限流失效/误伤原因。

### 2.3 Bucket4jRateLimiter（5.0 支持，本地桶）

```yaml
filters:
  - name: Bucket4jRateLimiter
    args:
      # 基于 Bucket4j 库的本地令牌桶（不依赖 Redis，单实例限流）
      rate-limiter: "#{@myRateLimiter}"   # Bean 提供限流配置
```

| 实现 | 依赖 | 集群支持 | 适用 |
|------|------|---------|------|
| RedisRateLimiter | Redis | ✅（共享桶） | **多实例网关（默认推荐）** |
| Bucket4jRateLimiter | 无 | ❌（单实例） | 单实例/轻量场景 |

## 3. 会话类：SaveSession / TokenRelay

### 3.1 SaveSession（会话保存）

```yaml
filters:
  - SaveSession        # 转发前持久化会话（配合 Spring Session 使用）
```

> 💡 场景：**网关 + Spring Session（Redis 会话）**——转发前先保存会话状态，下游（走同一会话）才能读取；不配则在某些转发路径下会话丢失。

### 3.2 TokenRelay（OAuth2 token 透传）

```yaml
filters:
  - TokenRelay         # 把 Authorization 头里的 token 传给下游
```

```text
流程（配合 Spring Security OAuth2 客户端）：
  客户端 → 网关（带 Bearer token）→ TokenRelay 透传 → 下游资源服务校验
  ← 网关负责：token 转发 + 可选的重定向登录/刷新
```

> 💡 典型架构：**网关做 SSO 入口**（登录后网关持有 token，TokenRelay 把 token 带给下游资源服务），下游只校验不登录。

## 4. 安全类：SecureHeaders / LocalResponseCache

### 4.1 SecureHeaders（安全响应头一键加）

```yaml
filters:
  - SecureHeaders        # 默认加 11 个安全头
```

| 安全头 | 默认值 | 防什么 |
|--------|--------|--------|
| X-XSS-Protection | 1; mode=block | XSS |
| X-Frame-Options | DENY | 点击劫持 |
| Strict-Transport-Security | max-age=631138519 | HTTPS 降级 |
| X-Content-Type-Options | nosniff | MIME 嗅探 |
| Content-Security-Policy | default-src 'self' | 内容注入 |
| ...（共 11 个） | 可自定义 | 综合 |

> 🎯 面试加分：**"网关安全怎么做？"——SecureHeaders 一键安全响应头 + RemoveRequestHeader 剥离内部头 + RequestSize 防大包 + 限流防刷 + TLS 加密传输**——五件套是网关安全的完整答案。

### 4.2 LocalResponseCache（本地响应缓存）

```yaml
filters:
  - name: LocalResponseCache
    args:
      size: 1024          # 缓存条目上限
      ttl: 60s            # 缓存有效期
```

> 💡 场景：**下游热接口的网关级缓存**（如配置接口、字典接口）——减少下游压力；注意缓存一致性（TTL 内可能过期数据）。

## 5. GlobalFilter：全局过滤器

### 5.1 概念

```text
GlobalFilter = 作用于所有路由的过滤器（与 GatewayFilter 并列的接口）
  ├── 执行时机：与路由过滤器一起进入过滤链（按 order 排序）
  ├── 典型内置全局过滤器：
  │   ├── NettyRoutingFilter          # 转发到下游（最后执行）
  │   ├── LoadBalancerClientFilter    # lb:// 服务解析
  │   ├── ForwardRoutingFilter        # forward: 本地转发
  │   ├── RouteToRequestUrlFilter     # 拼转发 URL
  │   ├── GatewayMetricsFilter        # 指标
  │   └── WebsocketRoutingFilter      # WebSocket 转发
  └── 自定义：实现 GlobalFilter + Ordered 接口
```

### 5.2 自定义全局过滤器（认证/日志）

```java
@Component
public class AuthGlobalFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        // 认证逻辑：校验 token，不过直接返回 401
        String token = exchange.getRequest().getHeaders().getFirst("X-Token");
        if (token == null || !token.equals("expected")) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();   // 短路，不转发
        }
        // 放行：往 exchange 塞业务上下文
        exchange.getAttributes().put("userId", "123");
        return chain.filter(exchange);                     // 继续过滤链
    }

    @Override
    public int getOrder() {
        return -100;    // 负数 = 靠前执行（先认证后转发）
    }
}
```

> 💡 全局过滤器 vs 路由过滤器分工：**全局 = 横切所有路由的**（认证/日志/鉴权/链路 ID）；**路由级 = 只影响特定路由的**（限流/改写）。

## 6. 自定义过滤器（两种方式）

### 6.1 方式一：自定义 GatewayFilter（路由级）

```java
@Configuration
public class CustomFilters {
    @Bean
    public RouteLocator customFilterRoutes(RouteLocatorBuilder builder) {
        return builder.routes()
                .route("custom", r -> r
                        .path("/custom/**")
                        .filters(f -> f.filter(new CustomGatewayFilter()))  // ★ 直接加过滤器实例
                        .uri("lb://order-service"))
                .build();
    }

    static class CustomGatewayFilter implements GatewayFilter, Ordered {
        @Override
        public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
            // 处理逻辑
            return chain.filter(exchange);
        }
        @Override
        public int getOrder() { return 0; }
    }
}
```

### 6.2 方式二：自定义过滤器工厂（yaml 可配）

```java
@Component
public class MyFilterGatewayFilterFactory extends AbstractGatewayFilterFactory<MyFilterGatewayFilterFactory.Config> {
    public MyFilterGatewayFilterFactory() { super(Config.class); }

    @Override
    public GatewayFilter apply(Config config) {
        return (exchange, chain) -> { /* 用 config 处理 */ return chain.filter(exchange); };
    }

    public static class Config {
        private String name;      // 过滤器参数
        // getter/setter
    }
}
```

```yaml
filters:
  - MyFilter=hello        # ★ 工厂名自动匹配：MyFilter + GatewayFilterFactory
```

> 🎯 两条路线怎么选：**只在此路由用 → 直接加实例；想 yaml 可配置复用 → 工厂**（工厂名规则 = 类名去掉 `GatewayFilterFactory` 后缀）。

## 7. 过滤器顺序控制

### 7.1 顺序规则

```text
执行顺序 = Order 值升序（小的先执行）
  ├── 路由过滤器的默认顺序：按配置顺序（0, 1, 2...）
  ├── 全局过滤器：自定义实现 Ordered 指定（负数 = 在路由过滤器前）
  └── 关键链路顺序（默认）：
      AuthGlobalFilter(-100) → 路由过滤器链 → LoadBalancerClientFilter → NettyRoutingFilter
      认证最前、转发最后
```

### 7.2 顺序错乱的典型问题

| 问题 | 原因 | 修正 |
|------|------|------|
| 认证后加的头下游收不到 | 认证过滤器在转发过滤器后执行 | order 调负（认证先） |
| 限流不生效 | 限流过滤器顺序靠后，其他过滤器已放行 | 限流放最前 |
| 日志漏请求 | 日志过滤器被短路（前面过滤器 return 了） | 日志 order 最小 |

> 💡 顺序心智：**"先横切（认证/日志/限流）→ 再路由级处理（改写）→ 最后转发"**——顺序错误是网关过滤器最常见的隐性 bug。

## 8. 过滤器速查总表（下）

| 过滤器 | 作用 | 依赖 | 面试价值 |
|--------|------|------|:---:|
| **CircuitBreaker** | 网关熔断 + fallbackUri 兜底 | reactor SCCB starter | ★★★ |
| **RequestRateLimiter** | Redis 令牌桶限流 | Redis reactive | ★★★ |
| Bucket4jRateLimiter | 本地桶限流（5.0） | Bucket4j | ★ |
| SaveSession | 会话持久化 | Spring Session | ★★ |
| TokenRelay | OAuth2 token 透传 | Spring Security OAuth2 | ★★★ |
| **SecureHeaders** | 11 个安全响应头 | 无 | ★★ |
| LocalResponseCache | 本地响应缓存 | 无 | ★★ |
| **GlobalFilter** | 全局横切（认证/日志） | 自定义实现 | ★★★ |
| 自定义 GatewayFilter/工厂 | 扩展 | 自定义 | ★★★ |

> 🎯 网关防护完整答案：**认证（GlobalFilter/TokenRelay）→ 限流（RequestRateLimiter）→ 熔断（CircuitBreaker + fallbackUri）→ 重试（Retry，[04 篇](04-过滤器工厂全景（上）.md)）→ 安全头（SecureHeaders）**——五层过滤链就是生产网关的标配骨架。
