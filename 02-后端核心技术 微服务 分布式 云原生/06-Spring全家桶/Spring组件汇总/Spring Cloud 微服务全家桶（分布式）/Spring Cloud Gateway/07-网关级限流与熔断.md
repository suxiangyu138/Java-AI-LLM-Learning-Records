## 1. 为什么需要网关级防护

```text
防护分层心智：
  ├── 第一层：网关（入口）——限流（防刷/防爆）+ 熔断（下游挂了不拖垮网关）
  ├── 第二层：服务内（调用点）——熔断/隔离/降级（防雪崩传染）
  └── 第三层：数据层——连接池/超时（兜底）

网关防护的价值：
  ├── 全部流量必经网关 → 在入口统一"挡"（比每个服务各挡一遍高效）
  ├── 客户端不可控（爬虫/刷单/突发）→ 网关是第一道闸
  └── 下游故障时网关先熔断 → 上游/客户端快速失败，不堆积
```

> 🎯 一句话：**网关防护是"入口闸门"，服务内防护是"内部防火墙"**——缺网关层，恶意/突发流量直接打到每个服务；缺服务内层，单个服务故障仍会传染。

## 2. RequestRateLimiter：Redis 令牌桶限流

### 2.1 完整配置（多路由示例）

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis-reactive</artifactId>
</dependency>
```

```yaml
spring:
  data:
    redis:
      host: localhost            # 网关限流依赖 Redis
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: order-service
              uri: lb://order-service
              predicates:
                - Path=/orders/**
              filters:
                - name: RequestRateLimiter
                  args:
                    redis-rate-limiter.replenishRate: 100     # 每秒 100 令牌
                    redis-rate-limiter.burstCapacity: 200     # 突发 200
                    redis-rate-limiter.requestedTokens: 1
                    key-resolver: "#{@ipKeyResolver}"         # ★ 按 IP 限
```

### 2.2 令牌桶三参数语义（面试必问）

```text
replenishRate  = 每秒补充令牌数 = 稳定 QPS 上限
burstCapacity  = 桶容量 = 允许的突发上限（瞬时流量峰值）
requestedTokens = 每请求消耗令牌数

行为：
  ├── 正常流量：消耗 < 补充 → 全部放行
  ├── 突发流量：打空桶里攒的令牌 → 超出的请求 429
  ├── 持续超限：429 持续（桶始终空）
  └── 限流响应：HTTP 429 Too Many Requests

参数关系（官方校验）：
  ├── replenishRate ≤ burstCapacity（否则启动报错/行为异常）
  ├── burstCapacity ≈ replenishRate × 突发时长（如 2s 突发 → ×2）
  └── 换算法：按业务 QPS 预估 ×1.5 余量起步，压测校准
```

> 🎯 面试必答：**"Redis 令牌桶怎么实现？"**——**Lua 脚本原子操作**（GET/SET + 时间戳计算令牌）：每次请求读桶状态 → 按时间差补充令牌（replenishRate × 秒数）→ 消耗 requestedTokens → 剩余不足则拒绝——**Lua 保证多实例网关共享同一把桶且无并发竞争**（这是选 Redis 而非本地实现的原因）。

### 2.3 多实例网关为什么必须 Redis

| 实现 | 多实例效果 |
|------|-----------|
| 本地计数（无外部存储） | 每实例独立桶 → N 实例 = N 倍上限（限流失效） |
| **Redis 共享桶** | 全局一把桶 → 总 QPS 精确可控 ✅ |
| Bucket4j（本地） | 单实例语义（多实例需分布式扩展） |

> ⚠️ **多实例网关 + 本地限流 = 伪限流**：3 实例每实例 100/s → 实际 300/s——生产多实例必须 Redis（或分布式 Bucket4j）。

## 3. KeyResolver：按谁限流

### 3.1 三种常用维度

```java
// 按 IP（最常用）
@Bean
public KeyResolver ipKeyResolver() {
    return exchange -> Mono.just(
            exchange.getRequest().getRemoteAddress().getAddress().getHostAddress());
}

// 按用户（需认证后才有用户标识）
@Bean
public KeyResolver userKeyResolver() {
    return exchange -> Mono.just(
            exchange.getRequest().getHeaders().getFirst("X-User-Id"));
}

// 按接口（全局限流：不分用户）
@Bean
public KeyResolver apiKeyResolver() {
    return exchange -> Mono.just(exchange.getRequest().getPath().value());
}
```

### 3.2 组合限流（多维度多把桶）

```yaml
# 同一路由两把桶：总 QPS 100 + 每用户 10
filters:
  - name: RequestRateLimiter
    args:
      redis-rate-limiter.replenishRate: 100
      redis-rate-limiter.burstCapacity: 200
      key-resolver: "#{@apiKeyResolver}"
  - name: RequestRateLimiter
    args:
      redis-rate-limiter.replenishRate: 10
      redis-rate-limiter.burstCapacity: 20
      key-resolver: "#{@userKeyResolver}"
```

> 🎯 限流维度设计：**"全局总量 + 单用户额度"双桶组合**是生产标配——防总流量打爆 + 防单用户刷接口（[10 篇](10-生产实践与选型避坑.md) 限流基线）。

## 4. Bucket4j：本地限流

### 4.1 配置

```yaml
filters:
  - name: Bucket4jRateLimiter
    args:
      rate-limiter: "#{@myRateLimiter}"      # Bucket4j 限流器 Bean
```

```java
@Bean
public Supplier<RateLimiter> myRateLimiter() {
    return () -> Bucket4j.builder()
            .addLimit(Bandwidth.classic(100, Refill.greedy(100, Duration.ofSeconds(1))))
            .build();
}
```

### 4.2 对比与选型

| 维度 | RedisRateLimiter | Bucket4j |
|------|-----------------|----------|
| 存储 | Redis（Lua） | 本地内存 |
| 多实例一致 | ✅ | ❌（需分布式扩展） |
| 额外依赖 | Redis | 无 |
| 延迟 | +1 次 Redis 往返 | 零额外 IO |
| 适用 | **多实例生产（默认推荐）** | 单实例、延迟敏感 |

> 💡 判断标准：**多实例网关用 RedisRateLimiter（一致性优先），单实例或极端延迟敏感用 Bucket4j**。

## 5. CircuitBreaker 过滤器：网关熔断

### 5.1 完整配置（熔断 + fallback + 超时）

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: order-service
              uri: lb://order-service
              predicates:
                - Path=/orders/**
              filters:
                - name: CircuitBreaker
                  args:
                    name: orderServiceCB
                    fallbackUri: forward:/fallback/order
                - name: Retry                    # 重试在外
                  args:
                    retries: 2
                    statuses: SERVICE_UNAVAILABLE
                    methods: GET
resilience4j:
  circuitbreaker:
    instances:
      orderServiceCB:
        sliding-window-size: 50
        minimum-number-of-calls: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
  timelimiter:
    instances:
      orderServiceCB:
        timeout-duration: 3s        # 网关转发超时（防下游慢拖垮网关）
```

### 5.2 过滤链顺序（网关场景）

```text
推荐顺序（yaml 配置顺序）：
  RequestRateLimiter（先限流：进都进不来）
  → CircuitBreaker（再熔断：下游挂了快速失败）
  → Retry（后重试：熔断保护下重试瞬时故障）
  → 转发

为什么限流最前：
  ├── 限流 = 保护网关/下游总量（防刷）
  ├── 熔断 = 保护下游质量（防雪崩）
  └── 重试 = 容错瞬时故障（下游已挂时熔断拦截，重试不会打下游）
```

> 🎯 网关防护组合拳（面试完整答案）：**"网关层防护 = 限流（入口总量控制）+ 熔断（下游故障快速失败+兜底）+ 重试（瞬时容错）+ 超时（防慢拖累）"**——四件套按"限流→熔断→重试→转发"排列，缺一不可。

### 5.3 与 Sentinel 网关限流对照

| 维度 | Gateway 内置（RedisRateLimiter） | Sentinel（SCA） |
|------|--------------------------------|-----------------|
| 实现 | Redis 令牌桶 | 滑动窗口/令牌桶/漏桶 |
| 控制台 | ❌ | ✅ 可视化 |
| 规则动态下发 | ❌（改配置重启/刷新） | ✅ 控制台实时 |
| 集群流控 | ❌（Redis 共享桶近似） | ✅ 独立集群流控 |
| 维度 | KeyResolver 自定义 | 参数/热点/链路（更丰富） |
| 生态 | 官方 Gateway | SCA 网关集成 |

> 🎯 选型一句话：**"只要简单限流 → Gateway 内置够用；要控制台/热点限流/规则治理 → 上 Sentinel 与 SCA 网关整合"**（[10 篇](10-生产实践与选型避坑.md) 选型）。

## 6. 三层防护架构设计

### 6.1 全链路防护图

```text
客户端（App/Web/第三方）
  │
  ▼
① 网关层：限流（总量+单用户）→ 熔断（fallbackUri 兜底）→ 重试 → 超时
  │            │ 429/兜底响应
  ▼
② 服务内层：CircuitBreaker（调用点熔断）→ Bulkhead（隔离）→ TimeLimiter（超时）
  │            │ 业务级降级（缓存/默认值）
  ▼
③ 数据层：连接池限制 → 超时配置 → 降级到只读/缓存
```

### 6.2 各层防护职责划分

| 层 | 防什么 | 手段 | 兜底表现 |
|----|--------|------|---------|
| 网关 | 外部流量总量/刷单 | RequestRateLimiter | 429 |
| 网关 | 下游整体故障 | CircuitBreaker + fallbackUri | 兜底页/静态响应 |
| 服务内 | 单调用点故障传染 | SCCB 熔断+隔离 | 业务降级（缓存） |
| 数据层 | 存储故障 | 连接池/超时/降级开关 | 只读模式 |

> ⚠️ **别把防护都堆在网关**：网关熔断是"入口兜底"（粗粒度），服务内熔断是"业务级降级"（细粒度）——**网关挂了兜底页，服务内挂了兜底业务数据**，两者缺一不可。

## 7. 参数调优与验证

### 7.1 限流参数基线

| 场景 | replenishRate | burstCapacity | 说明 |
|------|--------------|---------------|------|
| 一般接口 | 业务 QPS × 1.5 | × 2 | 留突发余量 |
| 大促接口 | 峰值 QPS × 1.2 | × 1.5 | 压测校准 |
| 登录/验证码 | 低（如 5/秒/用户） | 10 | 防刷重点 |
| 全局限流 | 总容量 × 0.8 | 同 | 留冗余 |

### 7.2 熔断参数基线（对照 SCCB 系列）

```yaml
sliding-window-size: 50           # 最近 50 次
minimum-number-of-calls: 10       # 10 次才开始判定
failure-rate-threshold: 50        # 50% 熔断
wait-duration-in-open-state: 30s  # 30s 后半开
timelimiter.timeout-duration: 3s  # 网关转发超时（≤ 上游超时）
```

### 7.3 验证方法

| 验证 | 做法 | 预期 |
|------|------|------|
| 限流生效 | 压测超限流量 | 429 + Redis 桶计数正常 |
| 熔断生效 | 停下游连续调用 | 状态机 OPEN → fallbackUri 响应 |
| 多实例一致 | 两个网关实例同时压 | 总 QPS 被限（共享桶） |
| 兜底可用 | 熔断期间访问 | 返回兜底页（200/503 按设计） |

> 💡 压测红线：**网关防护参数全部要压测验证**——尤其是限流（多实例一致性）与熔断（半开恢复），"配了但没验证"等于没配（[10 篇](10-生产实践与选型避坑.md) 验证清单）。
