## 1. TLS 与 SSL 终结

### 1.1 网关 HTTPS 终结

```yaml
server:
  port: 8443
  ssl:
    enabled: true
    key-store: classpath:gateway.p12
    key-store-password: ${TLS_PASSWORD}
    key-store-type: PKCS12
```

```text
架构语义：
  客户端 ──HTTPS──► 网关（证书终结，解密）──HTTP/HTTPS──► 下游
  ├── 网关 = 证书保管处（一个证书管所有流量）
  ├── 证书轮换只在网关（下游无证书负担）
  └── 内网转发用 HTTP 或另配 mTLS
```

### 1.2 下游 TLS 配置（网关 → 下游 https）

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          httpclient:
            ssl:
              use-insecure-trust-manager: false      # 生产必须 false
              # trust-store: classpath:truststore.p12
              # trust-store-password: ${TRUST_PASSWORD}
            # mTLS（双向）：客户端证书
            ssl:
              key-store: classpath:client.p12
              key-store-password: ${CLIENT_KEY_PASSWORD}
```

> ⚠️ **生产红线**：`use-insecure-trust-manager: true` = 网关不校验下游证书（可被中间人攻击）——只准测试环境用；生产配 trust-store 或 mTLS。

### 1.3 常用 TLS 实践

| 场景 | 配置 |
|------|------|
| 证书轮换 | 提前生成新证书 → 平滑替换（网关重启） |
| 多域名 | 标准证书（SAN）或多证书按 Host 路由 |
| 安全扫描 | 关 TLS 1.0/1.1、弱加密套件（Boot 默认已安全） |

## 2. CORS 跨域配置

### 2.1 网关级 CORS（推荐：统一处理跨域）

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          globalcors:
            cors-configurations:
              '[/**]':
                allowedOrigins: "https://app.example.com"   # 白名单域名
                allowedMethods: GET,POST,PUT,DELETE
                allowedHeaders: "*"
                allowCredentials: true
                maxAge: 3600
```

### 2.2 路由级 CORS

```yaml
routes:
  - id: open-api
    uri: lb://open-service
    predicates: [Path=/open/**]
    metadata:
      cors:
        allowedOrigins: "https://partner.example.com"
        allowedMethods: GET
```

### 2.3 CORS 常见坑

| 坑 | 现象 | 解决 |
|----|------|------|
| 重复 CORS 头 | 网关和下游都处理跨域 → 响应头重复 | 网关统一处理，下游关 CORS（DedupeResponseHeader 可兜底） |
| allowCredentials + * | 带凭证的请求不能配 * 源 | 显式列域名 |
| 预检不过 | OPTIONS 预检被路由谓词挡住 | 全局 CORS 在路由前处理（globalcors 语义） |

> 🎯 实践：**跨域统一在网关做（一处配置全服务生效），下游服务全部关 CORS**——"网关收口"是 CORS 治理的标准姿势。

## 3. Actuator：路由管理端点

### 3.1 暴露与端点清单

```yaml
management:
  endpoints:
    web:
      exposure:
        include: gateway, health
```

| 端点 | 方法 | 用途 |
|------|------|------|
| /actuator/gateway/routes | GET | 路由列表（含谓词/过滤器 JSON） |
| /actuator/gateway/routes/{id} | GET | 单条路由详情 |
| /actuator/gateway/routes/{id} | DELETE | **删除路由（动态移除）** |
| /actuator/gateway/refresh | POST | **刷新路由缓存（路由变更生效）** |
| /actuator/gateway/globalfilters | GET | 全局过滤器清单 |
| /actuator/gateway/routefilters | GET | 过滤器工厂清单 |
| /actuator/health | GET | 健康检查 |

### 3.2 动态路由管理实践

```text
场景：路由变更不想重启网关
  ├── 方案一：路由存 Config（Git）→ 改配置 → /actuator/gateway/refresh 刷新
  ├── 方案二：/actuator/gateway/routes/{id} DELETE 动态下线（临时故障路由）
  └── 方案三：自定义路由数据源（动态增删，见 6.2）
```

> 💡 生产标配：**路由配置进 Config/Nacos（版本化）+ 变更后 refresh 端点生效**——网关路由和业务配置一样治理。

## 4. 多实例共享路由（Redis）

### 4.1 问题

```text
多网关实例时：路由定义在各自内存
  ├── 一台改了路由，其他实例不知道 → 路由不一致
  └── 动态路由（Actuator 删除/新增）只影响单实例
```

### 4.2 解决方案（Redis 共享路由）

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          redis:
            routes:
              enabled: true        # ★ 路由存储到 Redis（多实例共享）
              # 前缀/序列化等可配
```

```text
效果：
  ├── 路由定义存 Redis（Key: 路由 id，Value: 路由 JSON）
  ├── 任一实例增删路由 → 全实例同步可见
  └── 多实例路由一致性（与限流共享桶同一思路）
```

> 🎯 选型：**实例数 > 1 且有动态路由需求 → Redis 共享路由**；静态 yaml 路由多实例无需（配置相同即可）。

## 5. Fluent Java Routes API 进阶

### 5.1 谓词 DSL

```java
@Bean
public RouteLocator advancedRoutes(RouteLocatorBuilder builder) {
    return builder.routes()
            .route("advanced", r -> r
                    .path("/api/**").and()               // 谓词组合：and / or / negate
                    .header("X-Env", "prod").or()        // 或：X-Env=prod 也可以
                    .readBody(String.class, body -> body.contains("keyword"))
                    .filters(f -> f
                            .setPath("/internal/**")
                            .retry(config -> config.setRetries(2)
                                    .setStatuses(HttpStatus.SERVICE_UNAVAILABLE)))
                    .uri("lb://backend-service"))
            .build();
}
```

| DSL | 语义 |
|-----|------|
| `.path().and().header()` | AND 组合 |
| `.or()` | OR 组合 |
| `.negate()` | 取反 |
| `.readBody()` | 体内容谓词 |
| `.metadata(key, value)` | 元数据 |

> 💡 面试加分：**"yaml 表达不了的复杂匹配用 Java DSL"**——如"路径 A 或（路径 B 且头 X）"这种组合，yaml 难写、DSL 一行。

## 6. 路由元数据

### 6.1 用途

```yaml
routes:
  - id: order-service
    uri: lb://order-service
    predicates: [Path=/orders/**]
    metadata:
      owner: order-team            # 业务元数据（自定义任意键值）
      timeout: 3s
      region: cn-east
```

```java
// 自定义过滤器里读取元数据
Route route = exchange.getAttribute(ServerWebExchangeUtils.GATEWAY_ROUTE_ATTR);
String owner = route.getMetadata().get("owner");   // "order-team"
```

| 用途 | 说明 |
|------|------|
| 路由归属/负责人 | 运维审计 |
| 自定义过滤器参数 | 按路由传参（不写死在代码） |
| 监控标签 | 路由级指标 |

## 7. AOT 与原生镜像

### 7.1 支持现状

| 能力 | 原生镜像（AOT） |
|------|:---:|
| 路由定义（静态 yaml） | ✅（构建期解析） |
| 内置过滤器/谓词 | ✅ |
| **动态路由（Actuator/Redis）** | ❌（运行期反射/动态类加载不支持） |
| **自定义过滤器（反射创建）** | ⚠️ 需要 @RegisterReflectionForBinding |
| 配置刷新 | ❌（原生镜像无刷新） |

### 7.2 实践要点

```text
网关原生镜像约束：
  ├── 只支持静态路由（构建期烘焙）
  ├── 自定义过滤器类要注册反射提示
  └── 动态路由/动态配置场景别用原生镜像
```

> 🎯 选型：**网关追求极致启动速度（秒级）且路由静态 → 原生镜像可行**；需要动态路由管理的生产网关 → 常规 JVM 更省心。

## 8. 性能调优方向

### 8.1 关键配置

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          httpclient:
            connect-timeout: 2000          # 连接超时
            response-timeout: 5s           # ★ 响应超时（防下游慢拖）
            pool:
              type: fixed                  # 连接池类型（fixed=固定连接数）
              max-connections: 500         # 最大连接数（高并发调大）
              max-idle-time: 30s
              max-life-time: 60s
          # 线程模型
          thread-pool:                      # 事件循环线程数（默认 CPU×2）
            # 一般不动，压测看瓶颈再调
```

### 8.2 调优检查清单

| 检查项 | 手段 |
|--------|------|
| 过滤器阻塞 | 压测观察事件循环线程占用（阻塞 = 持续高占用） |
| 下游慢 | response-timeout 收紧 + 下游熔断 |
| 连接池打满 | max-connections 调大 + 下游扩容 |
| 路由过多 | 谓词数量与路由数量权衡（匹配 O(n)） |
| 日志开销 | 访问日志采样/关闭 |
| Redis 限流延迟 | 限流 key 数量与 Redis 性能（共享桶有 1 次往返） |

> 💡 调优哲学：**先压测找瓶颈（线程/连接/延迟），再动参数**——网关默认配置对大多数场景够用，参数堆砌不如消除阻塞（[10 篇](10-生产实践与选型避坑.md) 调优节奏）。
