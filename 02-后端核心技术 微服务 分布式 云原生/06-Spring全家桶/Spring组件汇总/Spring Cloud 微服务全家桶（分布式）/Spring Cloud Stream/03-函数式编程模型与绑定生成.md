## 1. 模型总览：三类函数角色

| 函数类型 | 角色 | 绑定方向 | 触发方式 | 等价旧注解模型 |
|----------|------|---------|---------|----------------|
| `Supplier<T>` | Source 数据源 | 仅 output（`-out-0`） | 轮询/定时/外部事件（响应式） | `@InboundChannelAdapter` |
| `Function<I, O>` | Processor 处理器 | input + output | 事件驱动 | `@StreamListener` + `@SendTo` |
| `Consumer<I>` | Sink 数据汇 | 仅 input（`-in-0`） | 事件驱动 | `@StreamListener` |

```java
@Configuration
public class OrderFunctions {

    // Source：每 5 秒生产一条订单事件
    @Bean
    public Supplier<OrderEvent> orderSupplier() {
        return () -> new OrderEvent(UUID.randomUUID().toString(), "CREATED");
    }

    // Processor：订单事件 → 支付事件
    @Bean
    public Function<OrderEvent, PaymentEvent> orderToPayment() {
        return order -> new PaymentEvent(order.orderId(), "PAID");
    }

    // Sink：消费支付事件
    @Bean
    public Consumer<PaymentEvent> paymentLogger() {
        return event -> log.info("Payment: {}", event);
    }
}
```

> 🎯 **核心要点**：函数即消息端点。业务逻辑写成普通 `java.util.function.*`，框架负责"绑定→消费/生产→类型转换→重试"，业务代码对中间件零感知。

## 2. 绑定命名规则

每个函数 bean 自动生成绑定名，规则：

```text
<函数名>-<in|out>-<索引>
```

| 函数 | 生成绑定 | 说明 |
|------|---------|------|
| `Supplier<OrderEvent> orderSupplier()` | `orderSupplier-out-0` | 只有一个输出 |
| `Function<OrderEvent, PaymentEvent> orderToPayment()` | `orderToPayment-in-0` / `orderToPayment-out-0` | 一入一出 |
| `Consumer<PaymentEvent> paymentLogger()` | `paymentLogger-in-0` | 只有一个输入 |
| 多输入/多输出函数 | `fn-in-0`/`fn-in-1`、`fn-out-0`/`fn-out-1` | 索引区分通道 |

配置时用绑定名引用：

```yaml
spring:
  cloud:
    stream:
      bindings:
        orderSupplier-out-0:
          destination: order-events
          producer:
            partition-key-expression: payload.orderId
        paymentLogger-in-0:
          destination: payment-events
          group: payment-service
```

## 3. 函数选择与组合

### 3.1 函数选择（definition）

| 场景 | 配置 | 说明 |
|------|------|------|
| 只有一个函数 bean | 可不配（自动发现），但建议显式声明 | `spring.cloud.function.definition=paymentLogger` |
| 多个函数 bean | **必须配** | 分号分隔：`orderSupplier;orderToPayment;paymentLogger` |
| 需要禁用自动发现 | `spring.cloud.stream.function.autodetect=false` | 函数 bean 用于其他目的（如被普通代码调用）时避免误绑定 |

```yaml
spring:
  cloud:
    function:
      definition: orderSupplier;orderToPayment;paymentLogger
```

> ⚠️ **易错点**：definition 属性是 `spring.cloud.function.definition`（Spring Cloud Function 的），不是 `spring.cloud.stream.*`；多函数时漏配会因绑定歧义启动失败。

### 3.2 函数组合（`|` 管道）

同一条链路可组合多个函数，中间结果不进中间件：

```yaml
spring:
  cloud:
    function:
      definition: orderSupplier|enrichHeader|orderToPayment
```

组合后：`orderSupplier` 的输出直接喂给 `enrichHeader`，再传给 `orderToPayment`，最终绑定只出现在首尾两端（`orderSupplier-out-0` → 输入侧自动成为 `orderSupplier|enrichHeader|orderToPayment-in-0`）。

| 组合能力 | 用法 |
|----------|------|
| 处理链 | `a\|b\|c` 顺序执行，类型依次流转 |
| 绑定名简化 | `spring.cloud.stream.function.bindings."orderSupplier\|enrichHeader\|orderToPayment"-in-0=input` |
| 横切关注点 | 用独立函数做 header 增强、校验、幂等过滤后再进入主业务函数 |

### 3.3 多输入 / 多输出（响应式 Tuple）

```java
// 两个输入流 + 一个输出流
@Bean
public Function<Tuple2<Flux<String>, Flux<Integer>>, Flux<String>> merge() {
    return tuple -> tuple.getT1().mergeWith(tuple.getT2().map(String::valueOf));
}
```

Tuple 的元数决定绑定数量（`merge-in-0`、`merge-in-1`、`merge-out-0`），类型由泛型推断。

## 4. Supplier 数据源详解

### 4.1 轮询模式（默认）

框架默认每秒调用一次 Supplier 并发送返回值：

| 配置 | 默认 | 说明 |
|------|------|------|
| `spring.cloud.stream.poller.fixed-delay` | 1000ms | 轮询间隔 |
| `spring.cloud.stream.poller.max-messages-per-poll` | - | 每次轮询最大消息数 |
| `spring.cloud.stream.poller.initial-delay` | 0 | 首次延迟 |

```yaml
spring:
  cloud:
    stream:
      poller:
        fixed-delay: 2000
        max-messages-per-poll: 10
```

> ⚠️ **轮询陷阱**：轮询模式下 Supplier 每次调用**必须返回新对象**（或 null 跳过本次），不能返回固定单例（会被重复发送）。发送间隔受执行时间影响，吞吐受限场景改用响应式或 StreamBridge。

### 4.2 响应式模式

```java
@Bean
public Supplier<Flux<OrderEvent>> orderReactiveSupplier() {
    EmitterProcessor<OrderEvent> processor = EmitterProcessor.create();
    // 外部事件源（WebSocket、DB CDC 回调等）调用 processor.onNext(...)
    return () -> processor;
}
```

`Supplier<Flux<...>>` 返回事件流而非单值，适配高频/背压场景。

### 4.3 无源输出：StreamBridge

消息来自 REST 接口等"流之外"的入口时，用 StreamBridge 编程式发送（详见 [09-StreamBridge与事件路由](09-StreamBridge与事件路由.md)）：

```java
@RestController
public class OrderController {
    private final StreamBridge streamBridge;

    @PostMapping("/orders")
    public void create(@RequestBody OrderEvent order) {
        streamBridge.send("order-out-0", order);   // 目标绑定名
    }
}
```

## 5. Consumer / Function 消费详解

### 5.1 消费触发

`Function` 与 `Consumer` 由到达 `-in-0` 目的地的消息驱动，返回值自动发送到 `-out-0`（Function）。

### 5.2 消费并发与确认

| 属性（`bindings.<b>.consumer.*`） | 默认 | 说明 |
|------|------|------|
| `concurrency` | 1 | 消费并发数（Kafka: 并发容器数；Rabbit: concurrent consumers） |
| `max-attempts` | 3 | 最大尝试次数（重试次数 = max-attempts - 1） |
| `auto-commit-offset`（Kafka） | true | 是否自动提交 offset |
| `start-offset`（Kafka） | latest | earliest/latest（群组无 offset 时的起点） |
| `partitioned` | false | 输入绑定感知分区 |

### 5.3 响应式消费者注意事项

`Consumer<Flux<?>>` 返回 void，框架无法感知订阅完成，**推荐写法**是 `Function<Flux<?>, Mono<Void>>` + `.then()` 显式表达完成，或内部显式 subscribe。

## 6. 批量消费（Batch Mode）

```yaml
spring:
  cloud:
    stream:
      bindings:
        order-in-0:
          destination: order-events
          group: order-service
          consumer:
            batch-mode: true
```

```java
// 整批消息作为 List 传入
@Bean
public Function<List<OrderEvent>, List<OrderEvent>> batchProcessor() {
    return batch -> batch.stream().map(...).toList();
}
```

| 维度 | 单条模式 | 批量模式 |
|------|---------|---------|
| 函数签名 | `Function<OrderEvent, OrderEvent>` | `Function<List<OrderEvent>, List<OrderEvent>>` |
| 吞吐 | 逐条处理 | 一批一次调用，减少框架开销 |
| 批量头 | - | Kafka: `kafka_batchConvertedHeaders`；Rabbit: `amqp_batchedHeaders`（按消息粒度嵌套） |
| 与 DLQ 兼容 | 支持重试 | **Kafka 批量模式下 DLQ 不支持重试**（直接进 DLQ），见 [08](08-消息可靠性与重试死信.md) |
| 转换失败 | 单条失败重试 | 部分转换失败会缩小批大小，头数量保持原批大小（易错） |

> ⚠️ **批量易错点**：转换失败时"批大小缩小但头数量不变"——遍历头做索引映射会越界，务必按消息粒度组织数据处理。

## 7. 自定义绑定名与函数注册

### 7.1 绑定名友好化

```yaml
spring:
  cloud:
    stream:
      function:
        bindings:
          orderSupplier-out-0: output        # 函数绑定名 → 自定义名
          paymentLogger-in-0: input
      bindings:
        input:
          destination: payment-events        # 之后用自定义名配置
          group: payment-service
```

典型用途：与 Spring Cloud Data Flow 约定兼容（期望 `input`/`output` 命名）。

### 7.2 函数的其他注册方式

| 方式 | 说明 |
|------|------|
| `@Bean` 方法 | 最常用，类型推断完整 |
| `spring.cloud.function.definition` + 配置 | 仅用于选择已有 bean，不能凭空创建 |
| 泛型类型擦除问题 | 无泛型的 `Supplier`/`Consumer`（如 `Consumer<Object>`）时需 `@Bean` + 具体类型方法签名保证泛型可推断 |

## 8. 与注解模型的差异对照

| 维度 | 注解模型（≤3.2） | 函数式模型（4.0+ 唯一） |
|------|------------------|--------------------------|
| 声明 | `@EnableBinding(Processor.class)` + `@StreamListener` | `Function`/`Consumer`/`Supplier` Bean |
| 绑定名 | 接口字段 `@Input("input")` | `<函数名>-in-0`（可自定义映射） |
| 条件过滤 | `@StreamListener(condition=...)` | 函数内自行判断（或组合函数） |
| 返回发送 | `@SendTo` | Function 返回值自动发送 |
| 错误处理 | `@ServiceActivator(inputChannel=errorChannel)` | binder 级重试/DLQ 属性 + 自定义 ErrorHandler |
| 响应式 | 支持但割裂 | `Flux` 原生融合 |

> ⚠️ **迁移提醒**：3.x 旧代码无法直接升级到 4.x——注解、接口、`Processor`/`Source`/`Sink` 常量全部删除，需按本模块范式重写为函数 + 配置。

## 9. 核心要点

> 🎯 **核心要点**：
> - 函数角色映射：`Supplier`=源、`Function`=处理器、`Consumer`=汇；绑定名 = `<函数名>-<in|out>-<索引>`；
> - 多函数必须配 `spring.cloud.function.definition`（`;` 并列多函数、`|` 管道组合）；
> - 定时源用 Poller（默认 1s），外部触发源用响应式 Supplier，REST 入口用 StreamBridge；
> - 高吞吐用批量模式（`consumer.batch-mode=true` + `List` 签名），但牺牲 DLQ 重试能力；
> - 4.0 起无注解模型，所有网上 `@StreamListener` 教程均已失效。
