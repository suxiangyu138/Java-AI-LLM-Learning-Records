## 1. 单元测试与集成测试

### 1.1 Test Binder：不连中间件的测试

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-stream-test-binder</artifactId>
    <scope>test</scope>
</dependency>
```

```java
@SpringBootTest
class OrderFunctionsTest {

    @Autowired
    private InputDestination input;      // 测试 Binder 提供的"输入"：断言发给消费端的数据
    @Autowired
    private OutputDestination output;    // 测试 Binder 提供的"输出"：捕获生产端发出的数据

    @Test
    void supplierProducesEvent() {
        Message<byte[]> received = output.receive(5000, "orderSupplier-out-0");
        assertThat(received).isNotNull();
        assertThat(new String(received.getPayload())).contains("CREATED");
    }

    @Test
    void consumerProcessesEvent() {
        // 手工投喂一条消息给 orderLogger-in-0
        input.send(MessageBuilder.withPayload("{\"orderId\":\"1\",\"status\":\"PAID\"}").build(), "orderLogger-in-0");
        // 断言日志/副作用
    }
}
```

| 能力 | 说明 |
|------|------|
| 不连真实中间件 | 测试快、稳定、无环境依赖 |
| `OutputDestination.receive(timeout, bindingName)` | 断言"发出去"的消息 |
| `InputDestination.send(message, bindingName)` | 模拟"收进来"的消息 |
| 限制 | 不覆盖 binder 专属行为（分区分配、offset 提交、DLQ 细节） |

> 💡 分层策略：函数逻辑 + 绑定断言用 Test Binder（快）；DLQ/重试/分区行为用 Testcontainers 跑真实 Kafka/Rabbit（慢但真实，CI 上跑）。

## 2. 监控与可观测性

| 维度 | 手段 |
|------|------|
| 消息指标 | binder 暴露 Micrometer 指标（`spring.cloud.stream` 前缀）：消息数、错误数、耗时 |
| 消费进度 | Kafka 消费组 lag（`kafka-consumer-groups --describe`）、Rabbit 队列堆积 |
| DLQ 监控 | 死信 Topic/Queue 积压 → 告警（**DLQ 有消息必须秒级告警**） |
| 应用指标 | actuator + Prometheus/Grafana：`spring.cloud.stream.binding` 指标 |
| 链路追踪 | 消息头透传 traceId（Micrometer Tracing 集成） |
| 日志 | 错误头 `x-exception-stacktrace` 落日志平台，与 DLQ 关联分析 |

> ⚠️ 可观测性三件套必须齐全：消费 lag 曲线（吞吐/积压）、DLQ 计数（错误）、处理耗时（性能）。只盯 lag 会漏掉"消息进 DLQ 不消费"的静默失败。

## 3. 性能调优基线

| 参数 | 位置 | 调优方向 |
|------|------|---------|
| `consumer.concurrency` | bindings | 消费并行度（Kafka 受分区数上限约束） |
| `producer.partition-count` | bindings | 吞吐上限（分区数 = 并行度天花板） |
| Kafka `max.poll.records` | kafka.bindings.consumer.configuration | 单次拉取条数（吞吐 vs 延迟） |
| `batch-mode: true` | bindings | 整批处理，吞吐最大化 |
| Rabbit `batching-enabled` | rabbit.bindings.producer | 批量发送 |
| `consumer.max-attempts` | bindings | 降低重试开销（结合 DLQ） |
| `poller.fixed-delay` | poller | 轮询源频率 |

**调优顺序**：先定分区数（并行度上限）→ 再调并发 → 再批量 → 最后压测验证重试/退避与 `max.poll.interval.ms` 的关系。

## 4. 与原生客户端对比

| 维度 | Spring Cloud Stream | 原生 kafka-clients / spring-kafka | 直接封装的 MQ 工具类 |
|------|---------------------|-----------------------------------|----------------------|
| 中间件解耦 | ✅ 切换只改配置 | ❌ 写死 Kafka API | ⚠️ 自己的抽象层 |
| 业务代码 | 纯函数，零 MQ 概念 | 回调/容器代码交织 | 工具类薄封装 |
| 重试/DLQ | 内置属性即用 | 手写 ErrorHandler/DLT | 自研，易踩坑 |
| 类型转换 | 内置 JSON 转换链 | 手写序列化 | 自研 |
| 响应式 | 响应式 Binder 可选 | 手写 Reactor Kafka | 自研 |
| 学习成本 | 绑定/函数概念 | 原生概念 + 容器机制 | 内部约定 |
| 调试深度 | 出问题要懂底层 | 直连底层，透明 | 看实现 |
| 适用 | **新项目、多中间件、快速迭代** | 极致控制、小众特性 | 遗留系统过渡 |

> 🎯 **选型结论**：中大型团队、消息是业务主干 → Stream；深度依赖 Kafka 独有特性（事务精确语义、Streams 计算、自定义分区分配器）且团队精通 → 原生 spring-kafka 更透明；小型项目一条队列 → 两者皆可，Stream 仍值得（重试/DLQ 开箱即用）。

## 5. 选型决策：Stream vs 直接封装 vs 其他框架

| 决策问题 | 结论 |
|----------|------|
| 中间件会不会换？（Kafka↔Rabbit↔云托管） | 会 → Stream；不会 → 可原生 |
| 需要多中间件并存（多 Binder）？ | Stream 天然支持 |
| 需要云托管消息（Kinesis/PubSub/Event Hubs）？ | 官方 Binder 即插即用 |
| 需要 Kafka 事务精确一次？ | Stream 支持但复杂度高，评估原生 |
| 需要流计算（聚合/join）？ | Kafka Streams Binder |
| 已有 Spring Boot 3 老项目迁移 | 先看 [4.0 Migration guide](https://github.com/spring-cloud/spring-cloud-stream/wiki/4.0-Migration-guide)，函数式改造工作量 |

## 6. 生产避坑清单

| # | 坑 | 现象 | 规避 |
|---|----|------|------|
| 1 | 多函数漏配 definition | 启动绑定歧义失败 | 显式 `spring.cloud.function.definition` |
| 2 | `max-attempts: 1` 以为禁重试 | 无 DLQ 时容器默认重试 10 次 | 自定义容器 ErrorHandler（FixedBackOff(0,0)） |
| 3 | 重试总时长超 `max.poll.interval.ms` | 频繁 rebalance、重复消费 | 收敛重试参数或用容器级重试 |
| 4 | 匿名组（无 group） | 无法 DLQ；重启重读消息 | 生产必配 group |
| 5 | 动态目的地高基数 | Topic/Exchange 资源爆炸 | 低基数白名单 + 规范化 |
| 6 | 批量模式期待重试 | 批量 + DLQ 无重试直接进 DLQ | 认识权衡，或单条模式 |
| 7 | 事务模式配 retryable-exceptions | 配置被忽略（AfterRollbackProcessor 接管） | 用 BackOff 控制回滚重试 |
| 8 | 生产者绑定级 configuration 不生效（4.x） | acks/retries 静默无效 | 提到 binder 级 `kafka.binder.configuration.*` |
| 9 | 多 binder 容器自定义器被覆盖 | DLQ 行为不符合预期 | `BinderCustomizer` 设置 |
| 10 | `requeue-rejected: true` 无 DLQ（Rabbit） | 无限重投风暴 | 保持 false + DLQ |
| 11 | 3.x 注解代码升 4.x | 编译失败 | 函数式重写 |
| 12 | 升级后消息不消费 | 3.2.4→4.0.1 通道订阅问题（#2662） | 清注解残留 + 核对 definition |
| 13 | StreamBridge 高频同步调用 | 线程阻塞、吞吐低 | 批量配置 + 异步化 |
| 14 | 自定义 converter 不生效 | 类型转换走默认 JSON | 实现 SmartMessageConverter 并注册 |

## 7. 面试高频题

| 问题 | 答题要点 |
|------|---------|
| Stream 解决了什么问题？ | 中间件无关的消息编程模型：Binder 抽象吸收 Kafka/Rabbit 差异，业务只写函数 + 配置 |
| 五大核心概念？ | Destination / Binding / Group / Partition / Binder，各自一句话职责 |
| 函数式模型 vs @EnableBinding？ | 4.0 起注解模型已删除；Supplier/Function/Consumer 对应源/处理器/汇；绑定名 `<fn>-in-0` |
| 消费组是什么？ | 组内竞争（负载均衡）、组间广播；Kafka group.id / Rabbit 组队列 |
| 怎么保证消息不丢？ | 至少一次语义下：acks=all + required-groups + 处理后提交 + DLQ 兜底 + 业务幂等 |
| max-attempts=1 就能禁重试吗？ | 不能（Kafka 无 DLQ 时归容器管，默认 10 次）；需自定义 ErrorHandler |
| 重试和 rebalance 的关系？ | binder 级重试总时长超 max.poll.interval.ms 触发 rebalance；长重试用容器级（SeekToCurrentErrorHandler） |
| DLQ 启用条件与命名？ | Kafka：显式 group + enable-dlq；默认 `error.<dest>.<group>`；错误头 x-exception-* |
| 分区键的作用？ | 同 key 有序 + 并行度上限；稳定字段做 key |
| StreamBridge 什么场景用？ | 流外入口（REST/定时）发消息；动态目的地；同步 send 注意性能 |
| 恰好一次怎么实现？ | Kafka 事务 + 幂等生产者（限定 Kafka 内）；Rabbit 不支持，业务幂等兜底 |
| Stream 与原生 spring-kafka 怎么选？ | 解耦/开箱重试 DLQ vs 极致控制/透明性 |

## 8. 升级路径建议

| 现状 | 目标 | 路径 |
|------|------|------|
| Boot 3.x + Stream 4.2 | Boot 4 + Stream 5.0 | 1) 按 4.0 Migration guide 确认无注解残留；2) 升 Boot 4.0.1+ 与 2025.1 列车（5.0.1 起兼容）；3) 核对 Kafka 事务管理器 API 变更（5.0 用 setKafkaAwareTransactionManager） |
| Boot 2.7 + Stream 3.2 | 任一新线 | 先函数式重写（definition/绑定名重命名），再逐列车升级；**禁止直接跳** |
| 云托管中间件 | - | 换官方 Binder 依赖 + 连接配置，业务代码不变 |

> ⚠️ 升级铁律：先读官方 Migration guide 与 Release Notes，再在小流量灰度验证重试/DLQ/事务行为——版本间错误处理语义变化最隐蔽（见避坑 #11/#12）。

## 9. 核心要点

> 🎯 **核心要点**：
> - 测试：Test Binder 快测绑定逻辑，Testcontainers 测真实行为；
> - 监控：lag 曲线 + DLQ 计数 + 处理耗时三件套，DLQ 有消息即告警；
> - 调优顺序：分区数 → 并发 → 批量 → 重试参数与 max.poll.interval.ms 对齐；
> - 避坑 14 条按清单自查（重试语义、事务交互、configuration 生效范围是重灾区）；
> - 升级先读 Migration guide，灰度验证错误处理语义。
