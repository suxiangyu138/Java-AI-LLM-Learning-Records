## 1. 可靠性语义总览

| 语义 | 含义 | Stream 实现方式 | 适用 |
|------|------|-----------------|------|
| 至多一次（at-most-once） | 可能丢，不重复 | 关重试 + 提前提交 offset + 无 DLQ | 日志/监控类可容忍丢失 |
| **至少一次（at-least-once）** | 不丢，可能重复 | 默认模型：处理后提交 offset + 重试 + DLQ；**业务必须幂等** | 绝大多数业务默认 |
| 恰好一次（exactly-once） | 不丢不重 | Kafka 事务 + 幂等生产者（读-写同事务）；Rabbit 下无此语义（靠业务幂等） | 支付、库存等强一致 |

> 🎯 **核心要点**：Stream 默认是**至少一次**。重复消费不是 bug，而是默认语义的代价——幂等设计（唯一键、状态机、DB 约束）是消息系统的第一工程纪律。

## 2. 投递链路与丢失风险点

```text
生产者应用 ──(1)──> Broker ──(2)──> 消费者应用
```

| 环节 | 风险 | 防护 |
|------|------|------|
| (1) 生产者→Broker | 发送失败/未确认 | `acks=all` + 重试；启动期用 `required-groups` 防组未就绪丢消息 |
| (2) Broker 存储 | 副本丢失 | Kafka: 副本数 ≥ 3 + `min.insync.replicas`；Rabbit: 持久化 Exchange/Queue + `delivery-mode: PERSISTENT` |
| (3) Broker→消费者 | offset 提前提交导致漏消费 | 处理后提交（默认）；幂等兜底重复 |
| 消费处理中 | 处理失败 | 重试 → 重试耗尽进 DLQ（可回放） |

## 3. Kafka Binder 重试体系

### 3.1 两条重试路径

| 路径 | 位置 | 机制 | 特点 |
|------|------|------|------|
| **无状态重试**（binder 级，默认） | `KafkaMessageChannelBinder` 内 | `RetryTemplate`，按 `max-attempts` + 退避重试，**不碰 offset** | 简单；重试总时长必须 < `max.poll.interval.ms`（默认 5 分钟），否则触发 rebalance |
| **有状态重试**（容器级） | listener 容器 `ErrorHandler` | `SeekToCurrentErrorHandler` + `BackOff`，seek 回滚未提交分区位置 | 单次退避可任意长（seek 后重新拉取）；总时长无上限；配合 `max-attempts: 1` 使用 |

### 3.2 max-attempts 的真实行为（高频面试点）

| 配置场景 | 实际行为 |
|----------|---------|
| DLQ 开启 + `max-attempts: 3` | 重试 2 次，耗尽后进 DLQ |
| DLQ 关闭 + `max-attempts: 1` | **依然重试**！落到容器默认 `DefaultErrorHandler`（spring-kafka 默认 10 次）——`max-attempts` 对容器级无效 |
| DLQ 关闭，想完全禁重试 | 自定义 `ListenerContainerCustomizer`：`DefaultErrorHandler(new FixedBackOff(0, 0))` |
| DLQ 开启 | binder 设置优先于容器级错误处理 |

> ⚠️ **最易踩的坑**：以为 `max-attempts: 1` 就禁了重试。DLQ 关闭时重试由 spring-kafka 容器接管（默认 10 次带退避），唯一可靠做法是容器自定义 ErrorHandler。

### 3.3 无状态重试的 rebalance 风险

```text
maxAttempts=5, backoffInitialInterval=10s, multiplier=2.0
总重试时长 ≈ 10 + 20 + 40 + 80 = 150s < 300s(max.poll.interval.ms)  ✅ 安全
maxAttempts=8  → 总时长 ≈ 10+20+40+80+160+320+640 = 1270s > 300s  ❌ 触发 rebalance
```

rebalance 后分区易主，重试上下文（未提交 offset 位置）被其他实例接管，造成**处理重叠或顺序错乱**。解法：

| 方案 | 做法 |
|------|------|
| 参数收敛 | 压缩重试次数/退避，让总时长 < `max.poll.interval.ms` |
| 有状态重试 | 重试移入容器（第 5 节） |
| 加大拉取间隔 | `configuration.max.poll.interval.ms` 调大（治标不治本） |

## 4. Kafka DLQ 死信主题全解

### 4.1 启用条件与命名

| 项 | 规则 |
|----|------|
| 前置条件 | **必须显式配置 group**（匿名组无法启用 DLQ） |
| 启用 | `spring.cloud.stream.kafka.bindings.<b>.consumer.enable-dlq: true` |
| 默认 DLQ 主题 | `error.<destination>.<group>`（如 `error.order-events.order-service`） |
| 自定义 | `dlq-name`（主题名）、`dlq-partitions`（分区数） |
| 时机 | 重试耗尽后进入 DLQ（重试优先于 DLQ） |

### 4.2 错误头协议

| 头 | 内容 |
|----|------|
| `x-original-topic` | 原主题 |
| `x-exception-message` | 异常消息文本 |
| `x-exception-stacktrace` | 异常堆栈（`byte[]`） |

### 4.3 DLQ 场景矩阵

| 场景 | 行为 |
|------|------|
| 无 DLQ + 失败 | 容器默认重试 10 次后**丢弃**（消息丢失！） |
| 有 DLQ + 重试耗尽 | 进 DLQ，附错误头 |
| 有 DLQ + 批量模式 | **无重试，直接进 DLQ**（batch 模式不支持重试，官方实证） |
| 有 DLQ + 事务开启 | 事务内失败进 DLQ 需 `AfterRollbackProcessor` 配合；`retryable-exceptions`/`default-retryable` 被忽略 |

## 5. 重试移入容器：ListenerContainerWithDlqAndRetryCustomizer

需要容器级重试/DLQ（跨集群 DLQ、重试监听、超长退避）时实现该接口：

```java
@Bean
public ListenerContainerWithDlqAndRetryCustomizer customizer() {
    return new ListenerContainerWithDlqAndRetryCustomizer() {
        @Override
        public void configure(AbstractMessageListenerContainer container,
                              String destinationName, String group,
                              DlqDestinationResolver dlqDestinationResolver,
                              BackOff backOff) {
            container.setCommonErrorHandler(new DefaultErrorHandler(
                    new DeadLetterPublishingRecoverer(kafkaTemplate),
                    new ExponentialBackOff(1_000, 2.0)));   // 容器级重试 + 发布到 DLQ
        }

        @Override
        public boolean retryAndDlqInBinding(String destinationName, String group) {
            return false;   // 关闭 binder 级重试/DLQ，交给容器
        }
    };
}
```

| 场景 | 必须用它的理由 |
|------|----------------|
| 重试总时长 > `max.poll.interval.ms` | binder 级重试会触发 rebalance |
| DLQ 发到其他集群 | 自定义 `DeadLetterPublishingRecoverer` 指向别的 Kafka |
| 需要重试监听器 | ErrorHandler 上挂 `RetryListener` 告警 |

> ⚠️ **多 Binder 限制**：存在多个 binder 时该 Bean 会被 `DefaultBinderFactory` 覆盖——改用 `BinderCustomizer` 在 `KafkaMessageChannelBinder` 上设置容器自定义器（官方实证，见参考来源）。

## 6. 批量模式与事务的可靠性交互

| 组合 | 行为 |
|------|------|
| 批量 + DLQ | 重试失效，失败直接进 DLQ；整批一起失败 |
| 批量 + 事务 | 整批原子提交；单条失败整批回滚 → `AfterRollbackProcessor` 重试批次 |
| 单条 + 事务 | 消费-处理-生产原子；提交才提交 offset |
| 事务 + 重试配置 | binder 级重试属性被忽略，回滚重试由 `AfterRollbackProcessor` 的 `BackOff` 控制 |

> 💡 取舍建议：正确性优先（支付/库存）→ 单条模式 + 幂等 + 可选事务；吞吐优先（日志/统计）→ 批量模式 + DLQ 兜底 + 幂等。

## 7. Rabbit 与 Kafka 可靠性对照

| 维度 | Kafka Binder | RabbitMQ Binder |
|------|--------------|-----------------|
| 重试默认 | 容器 10 次（无 DLQ 时） | binder RetryTemplate（max-attempts 控制） |
| 禁重试 | 自定义容器 ErrorHandler | `max-attempts: 1` 即可 |
| DLQ 资源 | Topic `error.<dest>.<group>` | 队列 `<queue>.dlq` + DLX |
| DLQ 头 | `x-original-topic`/`x-exception-*` | `x-death`/`x-original-exchange`/`x-exception-stacktrace`（republish 模式） |
| 重试退避 | RetryTemplate 或容器 BackOff | RetryTemplate 或 **DLQ + TTL 回退**（不占线程） |
| 无限重投风险 | rebalance 或丢弃 | `requeue-rejected: true` 无 DLQ → 无限重投 |
| 恰好一次 | Kafka 事务（限定 Kafka 内） | 不支持（业务幂等） |

## 8. 死信消息处理与回放

### 8.1 死信消费策略

| 策略 | 说明 |
|------|------|
| 告警 + 人工 | DLQ 出消息即告警（日志/监控平台），人工排查修复 |
| 自动回放 | 消费 DLQ → 重发原目的地（`x-retries` 头计数，防无限循环） |
| 停车场（parking lot） | 回放超过 N 次进第三主题，彻底隔离"毒丸消息" |
| 双阶段 | DLQ → 中间主题（修复/补数据）→ 回主主题 |

### 8.2 回放应用示例（Kafka）

```java
@Configuration
public class DlqReplay {

    @Bean
    public Consumer<Message<byte[]>> dlqConsumer(StreamBridge streamBridge) {
        return msg -> {
            String originalTopic = msg.getHeaders().get("x-original-topic", String.class);
            int retries = Optional.ofNullable(msg.getHeaders().get("x-retries", Integer.class)).orElse(0);
            if (retries >= 3) {
                streamBridge.send("parkingLot-out-0", msg);       // 转停车场
                return;
            }
            // 修复/重发
            streamBridge.send(originalTopic + "-out-0",
                    MessageBuilder.fromMessage(msg)
                            .setHeader("x-retries", retries + 1).build());
        };
    }
}
```

> ⚠️ **回放安全**：只有**瞬时故障**（依赖服务重启、网络抖动）才能自动回放；数据/逻辑错误（反序列化失败、校验不通过）回放只会无限循环——回放前先判断错误头，毒丸消息必须隔离。

## 9. 可靠性最佳实践清单

| # | 实践 | 说明 |
|---|------|------|
| 1 | 业务幂等 | 唯一业务键 + 去重表/状态机，兜底一切重复 |
| 2 | 生产配 `acks=all` | 服务端确认不丢 |
| 3 | 生产配 `required-groups` | 防启动期组未就绪丢消息 |
| 4 | 显式 group | 匿名组无法 DLQ 且重启重读 |
| 5 | 默认开 DLQ | `enable-dlq: true`（Kafka）/ `auto-bind-dlq: true`（Rabbit） |
| 6 | 重试时长预算 | binder 级重试总时长 < `max.poll.interval.ms` |
| 7 | 长重试用容器 | `ListenerContainerWithDlqAndRetryCustomizer` |
| 8 | DLQ 监控告警 | DLQ 有消息立即告警，别等积压 |
| 9 | 毒丸隔离 | 回放计数器 + 停车场队列 |
| 10 | 写者确认 | Kafka `acks`、Rabbit publisher confirms（`delivery-mode` + confirm） |

## 10. 核心要点

> 🎯 **核心要点**：
> - 默认语义 = 至少一次；幂等是底线，DLQ 是兜底，事务是上限；
> - `max-attempts: 1` 不生效的坑：Kafka 无 DLQ 时重试归容器管（默认 10 次），禁重试必须自定义 ErrorHandler；
> - 重试两策略：binder 级（快、短）、容器级（长、稳），超 `max.poll.interval.ms` 必须容器级；
> - DLQ 三要求（Kafka）：显式 group + `enable-dlq: true` + 重试耗尽才进；
> - 回放前判错因，毒丸进停车场；DLQ 消息即告警。
