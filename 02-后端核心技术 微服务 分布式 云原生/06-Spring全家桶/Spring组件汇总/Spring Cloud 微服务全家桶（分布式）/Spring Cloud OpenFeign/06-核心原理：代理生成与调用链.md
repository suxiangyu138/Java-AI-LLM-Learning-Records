## 1. 魔法拆解：接口如何变成可调用 Bean

```text
你写的：
    @FeignClient(name = "payment-service")
    public interface PaymentClient { ... }

Spring 做的事（启动时）：
  ├── @EnableFeignClients 扫描 → 找到 @FeignClient 接口
  ├── FeignClientFactoryBean 注册为 Bean（Bean 名 = 接口全限定名）
  ├── 容器实例化 FactoryBean → getObject() 触发代理构建
  └── 注入时拿到：JDK 动态代理（PaymentClient 接口的代理实例）
        ├── 代理内部持有：Target（服务名/URL）+ 方法映射（方法→RequestTemplate）
        ├── 调用 hello() → 代理 → 构建 HTTP 请求 → 走调用链 → 返回
        └── 代理实现所有接口方法（含默认方法），业务代码无感
```

> 🎯 一句话本质：**@FeignClient 接口 = 一份"调用说明书"**——FactoryBean 读说明书生成动态代理，代理把"方法调用"翻译成"HTTP 请求"——**接口本身永远没有实现类，只有代理**。

## 2. FeignClientFactoryBean：工厂与上下文

### 2.1 工厂职责

```text
FeignClientFactoryBean（实现 FactoryBean<Object>）：
  ├── 属性：name/url/contextId/configuration（从 @FeignClient 读取）
  ├── 构建流程：
  │     ① 创建该客户端的独立子上下文（NamedContextFactory，per-client 隔离）
  │     ② 从子上下文装配 Feign 组件（编码器/解码器/契约/Client/拦截器）
  │     ③ 用 Feign.builder() 组装 → target() 生成动态代理
  ├── 返回：代理对象（Bean）
  └── 关键：每个 FeignClient 一个子上下文（配置互不污染）
```

### 2.2 子上下文的意义

```text
per-client 上下文（NamedContextFactory）：
  ├── 每个 @FeignClient 有独立 Bean 空间（configuration 类只影响自己）
  ├── 同名客户端不同配置 → contextId 区分（[02 篇](02-快速开始与@FeignClient速查.md)）
  └── 对比 LoadBalancer 的 per-service 上下文——同一模式（Spring Cloud 的通用隔离手法）
```

> 💡 面试加分：**"为什么 Feign 每个客户端一个上下文？"**——**配置隔离**：不同客户端需要不同超时/拦截器/编解码器，独立上下文让 `configuration` 类只作用于自己的客户端（与 [LoadBalancer 的 per-service 上下文](../Spring Cloud LoadBalancer/04-核心原理：Supplier 链与响应式实现.md) 同款设计）。

## 3. SpringMvcContract：Spring MVC 契约

### 3.1 契约是什么

```text
Feign 原生契约：@RequestLine("GET /api") 注解（Netflix Feign 风格）
SpringMvcContract：把 Spring MVC 注解翻译成 Feign 请求定义
  ├── @GetMapping("/hello") → RequestTemplate(GET /hello)
  ├── @PathVariable("id") → URL 模板变量 {id}
  ├── @RequestParam → 查询参数
  ├── @RequestBody → 请求体（走编码器）
  └── @RequestHeader → 请求头
```

### 3.2 一次方法调用的翻译

```java
// 接口定义
@GetMapping("/payments/{id}")
Payment getPayment(@PathVariable("id") Long id);

// 调用 getPayment(1001L) → 代理内部：
//   RequestTemplate: GET http://payment-service/payments/1001
//   目标服务名: payment-service（LB 待解析）
//   ↓ 交给调用链
```

> 🎯 面试必答：**"Feign 为什么能用 Spring MVC 注解？"**——**SpringMvcContract**：Feign 的"契约解析器"把 Spring MVC 注解（@GetMapping/@PathVariable 等）翻译成 Feign 的请求模板（RequestTemplate）——**同一套注解在 Controller 和 Feign 接口复用，一套语义两处使用**；不用它（纯 Feign）就得写 @RequestLine 原生注解。

## 4. 调用链全景

### 4.1 完整调用链（从方法调用到 HTTP）

```text
paymentClient.hello()   （业务代码）
  │
  ▼
① JDK 动态代理（InvocationHandler）
  │    方法 → 方法元数据（从 SpringMvcContract 解析的 MethodMetadata）
  ▼
② 构建 RequestTemplate（URL 模板/参数绑定/头）
  │
  ▼
③ 编码器链：RequestInterceptor（拦截器）→ 编码器（请求体序列化）
  │
  ▼
④ Capability 链（可选）：
  │    MicrometerObservationCapability（指标/追踪）
  │    CachingCapability（缓存，@EnableCaching 时）
  │
  ▼
⑤ FeignCircuitBreaker（熔断，enabled 时）
  │    CLOSED 放行 / OPEN 走 fallback
  ▼
⑥ Retryer（重试，默认关闭）
  │
  ▼
⑦ Client（默认 FeignBlockingLoadBalancerClient）
  │    LB 选实例 → 替换 URL → 真实 HTTP 发送（内置 Client / HC5）
  ▼
⑧ 响应 → 解码器（反序列化）→ ErrorDecoder（异常解析）
  │
  ▼
业务代码拿到结果
```

### 4.2 各环节 Bean（默认自动装配）

| 环节 | 默认 Bean | 自定义覆盖 |
|------|----------|-----------|
| 契约 | SpringMvcContract | @Bean Contract |
| 编码/解码 | SpringEncoder / ResponseEntityDecoder | @Bean Encoder/Decoder |
| 拦截器 | 无（不创建） | @Bean RequestInterceptor 集合 |
| 日志 | Slf4jLogger | @Bean Logger |
| 重试 | Retryer.NEVER_RETRY | @Bean Retryer |
| 熔断 | FeignCircuitBreaker.Builder（CB 在场时） | — |
| Client | FeignBlockingLoadBalancerClient | @Bean Client（**必须 Singleton**） |

> ⚠️ **Client Singleton 红线**：自定义 Client Bean 非单例 → 连接池每请求新建 → 生产事故（[03 篇](03-超时重试与HTTP客户端.md)）。

## 5. 配置优先级：属性 vs Bean

### 5.1 优先级链

```text
① @FeignClient 注解（name/url/configuration）
② 属性（spring.cloud.openfeign.client.config.<name>.*）    ← 默认最高（default-to-properties=true）
③ configuration 类 Bean（超时/拦截器/编解码器）
④ 全局默认（FeignClientsConfiguration）

default-to-properties=false → ②③ 互换
```

### 5.2 决策表

| 想配什么 | 用哪层 |
|---------|--------|
| 超时/重试/日志级别 | 属性（yaml，可刷新） |
| 拦截器/编解码器/ErrorDecoder | configuration 类（Bean） |
| 只影响一个客户端 | config.<name> 或该客户端 configuration |
| 全局统一 | config.default 或全局配置类 |

> 💡 实践：**能用属性用属性**（yaml 可审计、可接配置中心动态刷新）；Bean 留给"属性表达不了"的（拦截器逻辑、自定义解码）。

## 6. vs 手写 RestTemplate：性能与取舍

### 6.1 对比

| 维度 | Feign | RestTemplate（@LoadBalanced） |
|------|-------|------------------------------|
| 声明式 | ✅ 接口即调用 | ❌ 手写 URL |
| 反射代理 | ✅（启动构建，运行期方法级分派） | ❌（无代理） |
| 调用开销 | 方法分派 + 模板构建（微秒级） | URL 拼接（略少） |
| 可读性 | 接口契约清晰 | 散落调用点 |
| 熔断降级 | ✅ fallback 声明式 | ❌ 手动 |
| 可测试 | ✅ Mock 接口 | ⚠️ 需 Mock RestTemplate |
| 性能差异 | **可忽略**（微秒级 vs 网络毫秒级） | 略快（无代理层） |

### 6.2 结论

```text
性能结论：Feign 的代理开销相对网络调用可忽略（微秒 vs 毫秒）
  └── 选 Feign 不是性能考虑，是"工程组织"考虑：
      接口契约、声明式降级、统一拦截器 → 团队一致性收益 >> 微秒级开销
```

> 🎯 面试必答：**"Feign 性能比 RestTemplate 差吗？"**——**理论上有微秒级代理开销，实际可忽略**（相对网络延迟毫秒级是 3-4 个数量级差距）；选型看工程收益：Feign 的**接口契约 + 声明式熔断降级 + 统一拦截器**让代码组织更规范——**性能不该是选型理由**（除非极端压测场景）。
