## 1. 开启熔断：feign.circuitbreaker.enabled

### 1.1 依赖与开关

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
</dependency>
```

```yaml
spring:
  cloud:
    openfeign:
      circuitbreaker:
        enabled: true              # ★ 开启后所有 @FeignClient 方法自动包熔断器
        group:
          enabled: false           # 分组模式（默认 false：每方法一个熔断器）
        alphanumeric-ids:
          enabled: true            # 熔断器名用字母数字（默认）
```

### 1.2 开启后的行为

```text
feign.circuitbreaker.enabled=true 之后：
  ├── 每个 Feign 方法 → 一个熔断器实例（默认命名：FeignClientClass#method(params)）
  ├── 方法异常（超时/连接失败/5xx）→ 计入熔断统计
  ├── 熔断 OPEN → 不再调用下游，直接走 fallback
  └── 未配 fallback → 抛异常（熔断拒绝异常）
```

> ⚠️ **默认命名含特殊字符**：`FooClient#bar()` 的 `#` `()` 在监控/配置里难用——`alphanumeric-ids.enabled=true`（默认）会转成字母数字形式；也可自定义 CircuitBreakerNameResolver（[3 节](#3-熔断器命名规则)）。

## 2. fallback vs fallbackFactory：怎么选

### 2.1 fallback（简单降级）

```java
@FeignClient(name = "payment-service", fallback = PaymentFallback.class)
public interface PaymentClient {
    @GetMapping("/api/hello")
    String hello();
}

@Component                                         // ★ fallback 必须是 Spring Bean
public class PaymentFallback implements PaymentClient {
    @Override
    public String hello() {
        return "支付服务暂不可用";                   // 兜底值
    }
}
```

### 2.2 fallbackFactory（推荐：可拿异常）

```java
@FeignClient(name = "payment-service", fallbackFactory = PaymentFallbackFactory.class)
public interface PaymentClient {
    @GetMapping("/api/hello")
    String hello();
}

@Component
public class PaymentFallbackFactory implements FallbackFactory<PaymentClient> {
    @Override
    public PaymentClient create(Throwable cause) {     // ★ 拿到触发异常
        log.warn("payment-service 调用失败", cause);     // 打日志/埋点
        return new PaymentClient() {
            @Override
            public String hello() {
                return "支付服务暂不可用（" + cause.getClass().getSimpleName() + "）";
            }
        };
    }
}
```

### 2.3 对比与选择

| 维度 | fallback | fallbackFactory |
|------|----------|-----------------|
| 拿到异常 | ❌ | ✅（create 的 Throwable 参数） |
| 日志埋点 | ❌（需额外手段） | ✅ |
| 按异常分支降级 | ❌ | ✅（超时 vs 熔断不同兜底） |
| 代码量 | 少 | 略多 |
| 生产推荐 | 简单场景 | **推荐**（可观测性） |

> 🎯 面试必答：**"fallback 和 fallbackFactory 什么区别？"**——**fallback 是纯兜底实现（拿不到异常）；fallbackFactory 能拿到触发异常的 Throwable**（打日志、按异常类型分支降级）——生产推荐 fallbackFactory，降级可观测。

### 2.4 primary 属性的配合

```java
// 多个 fallback 时可能产生 @Primary 冲突（注入歧义）
@FeignClient(name = "payment-service", fallback = PaymentFallback.class, primary = false)
public interface PaymentClient { ... }
```

> 💡 `primary=false` 用于：**需要精确选择 Bean 时关闭默认 @Primary 标记**（多客户端/多 fallback 场景）。

## 3. 熔断器命名规则

### 3.1 默认命名

```text
默认格式：<FeignClient类名>#<方法名>(<参数类型>)
  例：com.example.PaymentClient#hello()
      com.example.PaymentClient#createPayment(PaymentRequest)

alphanumeric-ids.enabled=true（默认）：
  └── 转成字母数字：com.example.PaymentClient#hello() → 可配置友好名
```

### 3.2 自定义命名（CircuitBreakerNameResolver）

```java
@Bean
public CircuitBreakerNameResolver customNameResolver() {
    return (feignClientName, target, method) -> feignClientName + "." + method.getName();
    // 例：payment-service.hello（好读、好配监控）
}
```

### 3.3 熔断器名对应配置

```yaml
resilience4j:
  circuitbreaker:
    instances:
      # 默认命名（开启 alphanumeric-ids 后）：看 /actuator/health 或日志实际名
      "com.example.PaymentClient#hello()":
        sliding-window-size: 20
        minimum-number-of-calls: 5
        failure-rate-threshold: 50
```

> ⚠️ **命名坑**：熔断器实例名 = 配置 key——**先查实际生成的名字（health 端点/日志）再配 resilience4j.instances**，写错名字 = 走默认配置（熔断"不生效"）（[08 篇](08-生产实践与选型避坑.md) 坑位表）。

## 4. 熔断规则配置（resilience4j）

### 4.1 完整配置示例

```yaml
resilience4j:
  circuitbreaker:
    instances:
      "com.example.PaymentClient#hello()":
        sliding-window-size: 50
        minimum-number-of-calls: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 3
  timelimiter:
    instances:
      "com.example.PaymentClient#hello()":
        timeout-duration: 3s        # ★ Feign 场景：与 readTimeout 对齐（见下）
        cancel-running-future: true
```

### 4.2 超时与熔断的联动（关键）

```text
Feign 调用链中的超时有两层：
  ├── Feign readTimeout（连接后等待响应）：超时抛异常 → 计入熔断失败
  ├── TimeLimiter timeout-duration（熔断层超时）：SCCB 的 TimeLimiter
  └── 关系：readTimeout ≤ TimeLimiter（否则 TimeLimiter 永远先触发/后触发混乱）
推荐：readTimeout 与 timeout-duration 配置一致（如都 3s）
```

> 🎯 面试组合拳：**"Feign 的熔断怎么配？"**——**三步**：① `feign.circuitbreaker.enabled=true`；② 配 fallbackFactory（降级）；③ resilience4j 配熔断参数（窗口/阈值/半开）+ TimeLimiter 与 readTimeout 对齐——**超时→熔断统计→OPEN→fallback** 一条链闭环。

## 5. 完整链路：LB + 熔断 + 重试

### 5.1 调用链全景

```text
调用 PaymentClient.hello()
  │
  ├── ① FeignCircuitBreaker（熔断层）
  │       ├── CLOSED：放行 → ②
  │       └── OPEN：直接走 fallback（不发起调用！）
  ├── ② Retryer（重试层，默认关闭）
  │       └── 失败按策略重试（默认 NEVER_RETRY）
  ├── ③ FeignBlockingLoadBalancerClient（LB 层）
  │       ├── 服务名 → LoadBalancer 选实例
  │       └── 替换 URL → ④
  └── ④ HTTP Client（HC5/内置）→ 真实发送
```

### 5.2 组合配置基线

```yaml
spring:
  cloud:
    openfeign:
      circuitbreaker:
        enabled: true
      client:
        config:
          default:
            connectTimeout: 3000
            readTimeout: 3000
            # retryer: com.example.SimpleRetryer   # 默认关闭，按需开
resilience4j:
  circuitbreaker:
    instances:
      "com.example.PaymentClient#hello()":
        sliding-window-size: 50
        minimum-number-of-calls: 10
        failure-rate-threshold: 50
        wait-duration-in-open-state: 30s
```

> ⚠️ **重试与熔断的顺序**：Feign 的重试在熔断内层——**熔断 OPEN 时重试不会执行**（熔断直接短路）；这符合"熔断保护 + 重试容错"的语义（对照 [CircuitBreaker 04 篇](../Spring Cloud CircuitBreaker/04-弹性能力全景：隔离超时重试限流.md) 的装饰器顺序）。

## 6. 降级设计最佳实践

### 6.1 降级值的设计

| 降级类型 | 返回什么 | 场景 |
|---------|---------|------|
| 静态兜底 | 固定文案/默认值 | 提示类接口 |
| 缓存降级 | 上次成功数据 | 读多写少（订单查询） |
| 空对象降级 | empty 对象/空列表 | 列表类接口 |
| 抛出业务异常 | 上层感知后统一处理 | 关键链路不允许静默失败 |

```java
// 缓存降级示例（fallbackFactory 里实现）
@Component
public class OrderFallbackFactory implements FallbackFactory<OrderClient> {
    @Autowired
    private OrderCacheService cacheService;      // 本地/Redis 缓存

    @Override
    public OrderClient create(Throwable cause) {
        return new OrderClient() {
            @Override
            public Order getOrder(Long id) {
                return cacheService.getLastSuccess(id);   // ★ 降级到缓存
            }
        };
    }
}
```

### 6.2 降级规范

| 规范 | 说明 |
|------|------|
| 降级可观测 | fallback 里打日志/指标（fallbackFactory 拿 cause） |
| 区分熔断 vs 异常 | 按 cause 类型分支（CallNotPermittedException = 熔断，其他 = 业务失败） |
| 静默失败禁区 | 关键链路（下单）别静默返回成功——降级 = 明确降级语义 |
| 降级不是兜底一切 | 缓存降级注意一致性（降级数据可能过期） |

> 💡 降级心智：**"降级是给用户体验保底，不是掩盖故障"**——每次降级都要可观测、可告警，故障恢复后降级自动解除（熔断半开恢复）。
