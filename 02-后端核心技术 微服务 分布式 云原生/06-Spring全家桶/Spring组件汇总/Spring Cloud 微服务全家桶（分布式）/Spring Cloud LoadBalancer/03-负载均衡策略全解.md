## 1. 策略模型：Supplier 组合与 configurations 开关

### 1.1 两种配置入口

```yaml
# 方式一：configurations 开关（内置组合，一键生效）
spring:
  cloud:
    loadbalancer:
      configurations: weighted        # weighted | zone-preference | health-check
                                     # | same-instance-preference | request-based-sticky-session
                                     # | subset | api-version
                                     # 可逗号多选（按序组合）

# 方式二：Builder 编程式（精细定制，见 2.2 和 6 节）
```

```java
// Builder 组合示例（发现→缓存→加权）
@ServiceInstanceListSupplier.builder()
        .withDiscoveryClient()                    // ① 注册中心发现
        .withCaching()                            // ② Caffeine 缓存
        .withWeighted()                           // ③ 权重过滤
        .build(context);
```

> 🎯 心智模型：**策略 = "发现 → 缓存 → 过滤/变换 → 选择" 的 supplier 链**——configurations 是官方配好的组合包，Builder 是自由组合——理解链就能理解所有策略。

### 1.2 组合叠加语义

```text
多个过滤 supplier 叠加 = 逐层过滤：
  [全部实例] → 缓存 → 健康检查（滤掉不健康） → 权重（按权重选） → 最终选择

示例：configurations: health-check,weighted
  = DiscoveryClient → Caching → HealthCheck（滤除不健康） → Weighted（加权）
```

> ⚠️ **组合顺序注意**：HealthCheck 与 Caching **二选一**（health-check 自带 replay 缓存，再包 Caching 是双缓存）；官方建议缓存/健康检查 supplier 紧跟发现 supplier 之后（[05 篇](05-缓存与健康检查.md)）。

## 2. 基础策略：轮询 / 随机

### 2.1 轮询（默认）

```yaml
# 默认行为，无需配置
spring:
  cloud:
    loadbalancer:
      configurations: ""        # 默认 = 轮询
```

```text
RoundRobinLoadBalancer：按顺序轮流选（A → B → C → A → ...）
  ├── 原子计数器维护当前序号
  └── 实例列表变化（上下线）自动适应（序号取模）
```

### 2.2 随机

```java
@Configuration
public class RandomLbConfig {
    @Bean
    ReactorLoadBalancer<ServiceInstance> randomLoadBalancer(
            Environment environment, LoadBalancerClientFactory factory) {
        String serviceId = environment.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        return new RandomLoadBalancer(
                factory.getLazyProvider(serviceId, ServiceInstanceListSupplier.class), serviceId);
    }
}

// 应用（不能标 @Configuration 的类，见 06 篇）
@LoadBalancerClient(name = "payment-service", configuration = RandomLbConfig.class)
```

| 策略 | 特点 | 适用 |
|------|------|------|
| 轮询 | 均匀、可预测 | **默认通用** |
| 随机 | 不可预测、实现简单 | 压测/混合负载场景 |

## 3. 权重策略：Weighted

### 3.1 用法

```yaml
spring:
  cloud:
    loadbalancer:
      configurations: weighted
```

```yaml
# 实例侧：注册时在 metadata 里写 weight（Nacos 控制台/注册元数据）
spring:
  cloud:
    nacos:
      discovery:
        metadata:
          weight: 3        # 该实例权重 3（默认 1）
```

### 3.2 语义

```text
WeightedServiceInstanceListSupplier：
  ├── 读取每个实例 metadata 的 weight（默认 1）
  ├── 按权重随机选择（权重 3 的实例被选中概率是权重 1 的 3 倍）
  └── 实例无 weight → 按 1 参与

Builder 自定义权重函数：
  .withWeighted(instance -> { /* 按实例特征计算权重 */ })
```

> 🎯 典型用途：**新购机器给高权重（多接流量）、老机器降权、按实例规格加权**——比轮询更贴近"容量差异"的现实。

## 4. 区域策略：ZonePreference

### 4.1 用法

```yaml
spring:
  cloud:
    loadbalancer:
      configurations: zone-preference
      zone: cn-east-1          # ★ 本实例所在区域（Eureka 自动设置，其他注册中心手动配）
```

```yaml
# 实例侧：metadata 写 zone
spring:
  cloud:
    nacos:
      discovery:
        metadata:
          zone: cn-east-1
```

### 4.2 语义

```text
ZonePreferenceServiceInstanceListSupplier：
  ├── 优先选同区域实例（本地 zone = 配置或 Eureka 提供）
  ├── 同区域无可用 → 回退全部实例
  └── 本实例 zone 为空 → 不过滤（全部候选）

典型场景：同机房调用（低延迟）+ 跨机房容灾（同区域挂掉自动回退）
```

> ⚠️ **Zone 来源注意**：只有 **Eureka** 会自动设置 zone；Nacos/Consul 需手动配 `spring.cloud.loadbalancer.zone` + 实例 metadata（[08 篇](08-生产实践与选型避坑.md) 坑位表）。

## 5. 健康策略：HealthCheck

### 5.1 用法

```yaml
spring:
  cloud:
    loadbalancer:
      configurations: health-check
      health-check:
        initial-delay: 1s         # 首次探测延迟
        interval: 5s              # 探测间隔
        path:
          default: /actuator/health   # ★ 默认探测路径
          payment-service: /health/custom   # 按服务定制
        refetch-instances: true   # 定期重拉实例列表
        refetch-instances-interval: 30s
        port: 8080                # 探测端口（默认实例端口）
```

### 5.2 语义

```text
HealthCheckServiceInstanceListSupplier：
  ├── 定期（interval）对实例列表发 HTTP 健康探测
  ├── 不健康的实例从候选列表剔除
  ├── 全部不健康 → 回退全部（避免空列表）
  └── 自带 replay 缓存（不要再包 Caching supplier）
```

> 🎯 与注册中心健康检查的关系：**注册中心健康检查 = 实例"活着吗"（粗，心跳）；LB 健康检查 = 业务接口"可用吗"（细，HTTP 探测）**——对"活着但处理不了请求"的实例，LB 健康检查是第二道防线。

## 6. 灰度策略：Hint / Subset

### 6.1 Hint：按提示定向

```yaml
spring:
  cloud:
    loadbalancer:
      hint:
        default: default          # 默认提示（无请求头时用）
        payment-service: gray     # 该服务默认提示 gray
      hint-header-name: X-SC-LB-Hint   # 请求头名（可自定义）
```

```yaml
# 实例侧：metadata 写 hint
metadata:
  hint: gray          # 灰度实例标 gray；生产实例标 default
```

```text
HintBasedServiceInstanceListSupplier：
  ├── 请求头 X-SC-LB-Hint（或属性 hint）→ 过滤出 metadata.hint 匹配的实例
  ├── 无头/无匹配 → 全部实例
  └── 实现"定向灰度"：灰度请求头 → 只打灰度实例
```

> 🎯 典型用途：**灰度发布**——网关配灰度头（X-SC-LB-Hint: gray）的流量打到灰度实例，其余打生产实例（与 [Gateway 系列](../Spring Cloud Gateway/00-Spring Cloud Gateway知识体系总览.md) 的灰度路由配合）。

### 6.2 Subset：实例子集

```yaml
spring:
  cloud:
    loadbalancer:
      configurations: subset
      subset:
        size: 10              # 子集大小（默认 100）
        instance-id: payment-service-${server.port}   # 标识（支持占位符）
```

```text
SubsetServiceInstanceListSupplier：
  ├── 大集群（如 100+ 实例）中确定性选出一个子集（如 10 个）
  ├── 子集内再做轮询/随机（减小候选集，降低连接发散）
  └── SRE 算法：确定性哈希 → 同一实例稳定在子集内（连接复用率高）
```

> 💡 典型场景：**超大集群 + 长连接**（gRPC/WebSocket）——子集让每个调用方只连固定几个实例，连接池复用率高、下游连接数可控。

## 7. 会话策略：SameInstance / StickySession

### 7.1 SameInstancePreference：同实例偏好

```yaml
spring:
  cloud:
    loadbalancer:
      configurations: same-instance-preference
```

```text
SameInstancePreferenceServiceInstanceListSupplier：
  ├── 记住上次选择的实例（请求带实例 id）
  ├── 下次优先选同一实例（仍在列表则复用）
  └── 实例下线 → 回退重新选择
用途：替代 Zookeeper 的 StickyRule（有状态会话场景）
```

### 7.2 RequestBasedStickySession：请求粘性会话

```yaml
spring:
  cloud:
    loadbalancer:
      configurations: request-based-sticky-session
      sticky-session:
        add-service-instance-cookie: true
        instance-id-cookie-name: sc-lb-instance-id    # Cookie 名（默认）
```

```text
RequestBasedStickySessionServiceInstanceListSupplier（WebClient 专用）：
  ├── 首次请求选实例 → 响应 Set-Cookie（sc-lb-instance-id=实例id）
  ├── 后续请求带该 Cookie → 优先打同一实例
  └── 实现"会话内固定实例"（本地会话场景）
```

> ⚠️ **无状态化警告**：粘性会话与"服务无状态"的微服务原则冲突——**只有无法改造的遗留会话才用**；新系统应把会话放 Redis/数据库（[08 篇](08-生产实践与选型避坑.md) 坑位表）。

## 8. 版本策略：API Versioning（5.0 新增）

### 8.1 用法

```yaml
spring:
  cloud:
    loadbalancer:
      configurations: api-version
      clients:
        payment-service:
          api-version:
            header: X-API-Version          # ★ 从请求头读版本
            default-version: 1.0           # 缺省版本
            required: false                # 版本必须匹配（true 无匹配拒绝；false 回退）
            fallback-to-available-instances: true   # 无匹配时回退全部
```

```yaml
# 实例侧：metadata 写 API 版本
metadata:
  api-version: 1.0       # 或 1.1（新版本实例）
```

### 8.2 语义

```text
ApiVersionServiceInstanceListSupplier（Blocking/Reactive 两版）：
  ├── 请求带版本（header/query/path/media type 参数，可配置）
  ├── 过滤出 metadata.api-version 匹配的实例
  ├── 无匹配：required=true → 拒绝；否则回退（fallback-to-available-instances）
  └── 基于 Spring Framework 7.0 的 API versioning 支持（默认语义解析器 SemanticApiVersionParser）
```

> 🎯 典型场景：**多版本实例共存**——旧版本实例（1.0）与新版本实例（1.1）同时在注册中心，按请求版本路由到对应实例，支撑"滚动升级/兼容期"（与 [Gateway 的 API Versioning 谓词](../Spring Cloud Gateway/03-路由谓词工厂速查.md) 互补：网关按版本路由到服务，LB 按版本选实例）。

## 9. 策略速查总表

| 策略 | configurations 值 | 依据 | 典型场景 | 面试价值 |
|------|------------------|------|---------|:---:|
| 轮询（默认） | （空） | 顺序计数 | 通用 | ★★★ |
| 随机 | 自定义 Bean | 随机数 | 压测 | ★ |
| **权重** | weighted | metadata.weight | 容量差异 | ★★★ |
| **区域** | zone-preference | zone metadata | 同机房优先 | ★★★ |
| **健康** | health-check | HTTP 探测 | 故障感知 | ★★★ |
| **提示（灰度）** | hint（builder） | hint metadata/头 | 定向灰度 | ★★★ |
| 子集 | subset | 哈希子集 | 超大集群长连接 | ★★ |
| 同实例偏好 | same-instance-preference | 上次选择 | 会话（遗留） | ★★ |
| 粘性会话 | request-based-sticky-session | Cookie | 会话（WebClient） | ★★ |
| **API 版本** | api-version | metadata.api-version | 多版本共存（5.0 新） | ★★（新） |

> 🎯 面试组合拳：**"怎么实现灰度 + 同机房 + 容量差异的综合调度？"**——**configurations: zone-preference,weighted + Hint** 三段式：**先区域过滤（同机房优先）→ 再权重（容量差异）→ 灰度流量用 Hint 定向**——supplier 链的组合就是完整答案。
