## 1. LB 重试：换实例重试

### 1.1 配置

```yaml
spring:
  cloud:
    loadbalancer:
      retry:
        enabled: true          # ★ 全局开关（默认 false）
```

### 1.2 语义与限制

```text
LB 重试 = 调用失败时换下一个实例重试（不同于 HTTP 层重试）：
  ├── 第一次：选实例 A → 调用失败（连接/超时）
  ├── 重试：换实例 B → 调用
  └── 失败策略：默认最多重试列表内所有实例？——不：默认只重试 1 次换实例

官方限制：
  ├── retry.enabled 只能全局开关（不能按服务单独启用）
  ├── 可按服务禁用：spring.cloud.loadbalancer.clients.<id>.retry.enabled=false
  └── 依赖 spring-retry 类库（starter 已带）
```

> ⚠️ **重试语义注意**：LB 重试是"换实例重试整个请求"——**写请求重试有重复提交风险**（与 HTTP 重试同样的幂等问题）；生产上"LB 重试 + 熔断"组合时注意重试风暴（[08 篇](08-生产实践与选型避坑.md)）。

### 1.3 与各层重试的关系

| 重试层 | 位置 | 语义 |
|--------|------|------|
| LB 重试 | 选实例失败 | **换实例重试** |
| Feign/HTTP 重试 | 同一实例 | 同实例重发 |
| 网关 Retry 过滤器 | 网关 | 转发层重试 |
| 熔断（SCCB） | 保护层 | 不重试，快速失败 |

> 💡 组合建议：**LB 重试（换实例） + 调用方超时（防挂死） + 熔断（下游整体故障快速失败）**——三层各管一段。

## 2. 自定义 LoadBalancer（替换选择算法）

### 2.1 实现自定义策略

```java
// 例：最近最少使用（LRU）策略——继承 RoundRobin 或实现接口
public class LeastConnectionsLoadBalancer extends RoundRobinLoadBalancer {
    // 扩展：按连接数选择（伪代码思路）
}
```

```java
@Configuration
public class CustomLbConfig {
    @Bean
    ReactorLoadBalancer<ServiceInstance> customLoadBalancer(
            Environment environment, LoadBalancerClientFactory factory) {
        String serviceId = environment.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        return new CustomLoadBalancer(
                factory.getLazyProvider(serviceId, ServiceInstanceListSupplier.class), serviceId);
    }
}
```

### 2.2 应用自定义策略

```java
// ★ 关键：configuration 类不能标 @Configuration（会全局生效），用 @LoadBalancerClient 按服务绑定
@LoadBalancerClient(name = "payment-service", configuration = CustomLbConfig.class)
public class PaymentClientConfig { }
// 或 @LoadBalancerClients({@LoadBalancerClient(...), ...}) 多服务
```

> ⚠️ **最常见扩展坑**：自定义配置类标了 `@Configuration` → 配置**污染所有服务的 LB 上下文**（子上下文会继承父上下文配置）——官方明确：**configuration 类不能标 @Configuration**（或放组件扫描外）。

## 3. 自定义 Supplier（定制候选列表）

### 3.1 场景

```text
默认候选列表来自注册中心（DiscoveryClient）——需要定制时：
  ├── 静态列表（无注册中心环境）
  ├── 按业务过滤（只选某标签实例）
  ├── 融合多数据源（注册中心 + 本地配置）
  └── 动态加权（按实时指标）
```

### 3.2 实现

```java
// 自定义 supplier：实现 ServiceInstanceListSupplier 接口
@Component
public class CustomServiceInstanceListSupplier implements ServiceInstanceListSupplier {
    private final ServiceInstanceListSupplier delegate;

    public CustomServiceInstanceListSupplier(ServiceInstanceListSupplier delegate) {
        this.delegate = delegate;     // 包装默认 supplier
    }

    @Override
    public Flux<ServiceInstance> get(Request request) {
        return delegate.get(request)
                .filter(instance -> filterByBusinessRule(instance));   // ★ 定制过滤
    }

    @Override
    public String getServiceId() { return delegate.getServiceId(); }
}

// 注册：用 @LoadBalancerClient 的配置类提供
@Configuration
public class SupplierConfig {
    @Bean
    ServiceInstanceListSupplier customSupplier(ConfigurableApplicationContext context) {
        return ServiceInstanceListSupplier.builder(context)
                .withDiscoveryClient()
                .withCaching()
                .build();            // 或完全自定义
    }
}
```

> 🎯 扩展心智：**想改"候选列表" → 自定义 Supplier；想改"选择算法" → 自定义 LoadBalancer**——职责清晰，改哪块动哪块。

## 4. LoadBalancerLifecycle：生命周期回调

### 4.1 接口方法

```java
public class MyLoadBalancerLifecycle implements LoadBalancerLifecycle {
    @Override
    public void onStart(Request<RC> request) { /* 选择开始前 */ }

    @Override
    public void onStartRequest(Request<RC> request, Response<T> lbResponse) {
        /* 选中实例、请求发出前 */
    }

    @Override
    public void onComplete(CompletionContext<RES, T, RC> completionContext) {
        /* 请求完成（成功/失败/丢弃）——打指标、日志 */
    }
}
// 注册：@Component 即可（Bean 自动被调用）
```

### 4.2 典型用途

| 用途 | 说明 |
|------|------|
| 监控指标 | 记录每次选择的实例、耗时、结果（配合 Micrometer） |
| 日志审计 | 每次调用的目标实例（排查"打到哪了"） |
| 业务扩展 | 选择前加权限/限制 |

> 💡 面试加分：**"怎么观测每次调用打到哪个实例？"**——**LoadBalancerLifecycle 的 onStartRequest/onComplete**——选中的实例、请求结果、耗时全在这里（或直接用官方 MicrometerStatsLoadBalancerLifecycle + actuator 指标，[08 篇](08-生产实践与选型避坑.md) 监控）。

## 5. @LoadBalancerClient 配置规则

### 5.1 用法汇总

```java
// 单服务
@LoadBalancerClient(name = "payment-service", configuration = PaymentLbConfig.class)
// 多服务
@LoadBalancerClients({
    @LoadBalancerClient(name = "payment-service", configuration = PaymentLbConfig.class),
    @LoadBalancerClient(name = "order-service", configuration = OrderLbConfig.class)
})
public class LbConfigurations { }
```

### 5.2 三条铁律

| 铁律 | 说明 |
|------|------|
| ① configuration 类**不能标 @Configuration** | 否则全局生效（子上下文继承父配置） |
| ② 配置文件要能被扫描到 | @LoadBalancerClient 的 configuration 由子上下文按类加载（类必须在组件扫描范围） |
| ③ 一个服务一个配置 | 不同服务不同策略互不干扰 |

> ⚠️ **矛盾点注意**：铁律①说不能标 @Configuration，铁律②说要在扫描范围——**类不标注解但放在扫描包下**（或放组件扫描外但被 @LoadBalancerClient 显式引用）——这是 LoadBalancer 配置最绕的地方，写错的表现 = 策略全局生效或完全不生效。

## 6. AOT 与原生镜像约束

### 6.1 官方约束

```text
AOT/原生镜像（4.0.0+ 支持，但有要求）：
  ├── 服务 ID 必须显式声明：
  │     @LoadBalancerClient(name=...) 或 spring.cloud.loadbalancer.eager-load.clients
  ├── 隐式服务 ID（运行期才知道的服务名）无法提前注册 → 原生镜像不支持
  └── 自定义 Supplier/LoadBalancer 类需反射提示（@RegisterReflectionForBinding）
```

### 6.2 实践

```yaml
spring:
  cloud:
    loadbalancer:
      eager-load:
        clients: payment-service,order-service    # ★ 原生镜像必配（显式服务清单）
```

> 💡 原生镜像网关/服务：**所有被调服务名都要在 eager-load.clients 里显式列出**——漏一个 = 运行期找不到该服务的 LB 上下文。
