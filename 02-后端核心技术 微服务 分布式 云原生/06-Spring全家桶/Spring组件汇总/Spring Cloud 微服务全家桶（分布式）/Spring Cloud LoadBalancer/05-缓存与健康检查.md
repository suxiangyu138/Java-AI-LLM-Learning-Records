## 1. 为什么需要缓存

```text
没有缓存的问题：
  ├── 每次调用都查注册中心 → 注册中心压力大（高 QPS 服务 × 多实例 = 请求风暴）
  ├── 注册中心挂掉 → 所有调用全挂（LB 完全依赖注册中心）
  └── 响应式查询有延迟（每次查询 = 1 次网络往返）

有缓存（CachingServiceInstanceListSupplier）：
  ├── 实例列表缓存 N 秒 → 注册中心请求量降为 1/N
  ├── 注册中心短暂故障 → 缓存兜底（调用仍可继续）
  └── 代价：实例变更最多延迟 TTL 感知（下线的实例 TTL 内仍可能被选）
```

> 🎯 权衡心智：**缓存 = 用"感知延迟"换"注册中心压力与可用性"**——TTL 就是故障感知的最坏延迟，35s 默认是官方权衡后的平衡点。

## 2. Caffeine 缓存配置

### 2.1 默认值与配置

```yaml
spring:
  cloud:
    loadbalancer:
      cache:
        enabled: true        # 默认 true（生产强烈建议开启）
        ttl: 35s             # ★ 缓存时长（默认 35s）
        capacity: 256        # 缓存容量（默认 256 个服务）
        # caffeine.spec: maximumSize=500,expireAfterWrite=35s   # 高级 Caffeine 规格
```

### 2.2 实现选择

```text
CachingServiceInstanceListSupplier 的缓存实现：
  ├── classpath 有 Caffeine → Caffeine 缓存（性能优，推荐）
  └── 无 Caffeine → DefaultLoadBalancerCache（内置兜底，功能等同）
```

> ⚠️ **Caffeine 依赖**：spring-cloud-starter-loadbalancer 默认带 caffeine（starter 内含）；如果自行排除了，会回退 DefaultLoadBalancerCache——功能无差别，性能略低。

## 3. 缓存失效与感知延迟

### 3.1 三类感知延迟

```text
实例状态变化的感知总延迟 = 注册中心感知 + LB 缓存 TTL：

  ① 实例下线（主动）：
     实例发注销 → 注册中心立即摘除 → LB 最多等 TTL 感知
     （Nacos 有健康检查补偿：实例失联 15s 心跳超时后摘除）

  ② 实例新增（上线）：
     注册成功 → LB 最多等 TTL 后才看到新实例（新实例 TTL 内接不到流量）

  ③ 实例失联（被动）：
     注册中心心跳超时才摘除（Nacos 默认 15s）→ + LB TTL → 感知更慢
```

### 3.2 业务影响与对策

| 场景 | 影响 | 对策 |
|------|------|------|
| 下线实例 TTL 内仍被选 | 少数请求打到已停实例（快速失败） | 接受（配合重试/熔断兜底）；或 TTL 调小 |
| 新实例 TTL 内无流量 | 扩容后 N 秒内不生效 | 接受（默认）；或 TTL 调小 |
| 关键故障场景 | 感知慢 = 恢复慢 | 配合 HealthCheck（秒级探测） |

> 🎯 面试必答：**"实例下线了为什么还有请求打过去？"**——**缓存 TTL（默认 35s）**：LB 的实例列表是缓存的，下线实例在 TTL 内仍可能在缓存里被选中；解法：**① 接受（调用方配重试/熔断兜底）② TTL 调小（注册中心压力增大）③ 配 HealthCheck（主动探测，秒级剔除）**——生产通常三选二。

## 4. HealthCheck：主动健康探测

### 4.1 配置

```yaml
spring:
  cloud:
    loadbalancer:
      configurations: health-check       # ★ 开启健康检查链
      health-check:
        initial-delay: 1s                # 首次探测延迟
        interval: 5s                     # ★ 探测间隔（感知粒度）
        path:
          default: /actuator/health      # 默认探测路径
          payment-service: /health/payment   # 按服务定制
        refetch-instances: true          # 定期重拉实例列表
        refetch-instances-interval: 30s
        port: 8080                       # 探测端口（默认实例端口）
        repeat-health-check: true        # 失败后继续探测（默认）
        update-results-list: true        # 更新探测结果列表（默认）
```

### 4.2 工作机制

```text
HealthCheckServiceInstanceListSupplier：
  ├── 周期任务（Flux.interval）：对每个实例发 HTTP GET /actuator/health
  ├── 正常（2xx）→ 保留在候选列表
  ├── 非正常/超时/连接失败 → 从候选列表剔除
  ├── 全部不健康 → 回退全部实例（避免空列表导致全挂）
  └── 自带 replay 缓存（不要再包 Caching supplier，双缓存重复）
```

### 4.3 与注册中心健康检查的分工

| 维度 | 注册中心健康检查 | LB HealthCheck |
|------|----------------|----------------|
| 检查方式 | 客户端心跳（Nacos 15s） | **LB 主动 HTTP 探测**（可秒级） |
| 检查内容 | 实例"活着"（进程在） | 业务健康端点（能处理请求） |
| 检查方 | 注册中心 | 调用方（LB） |
| 感知速度 | 秒级-分钟级 | 探测间隔级（如 5s） |
| 覆盖盲区 | 实例活着但业务挂（如 OOM/死锁） | ✅ 能发现（健康端点返回非 2xx） |

> 🎯 典型价值：**"进程活着但处理不了请求"的实例**（内存泄漏、依赖挂掉）——注册中心认为健康（心跳正常），LB 探测健康端点发现异常并剔除——**健康检查是缓存之外的第二道故障防线**。

## 5. 缓存与注册中心的协同

### 5.1 双重缓存问题

```text
Eureka 客户端自身也有缓存（EurekaClient 的本地缓存，默认 30s 更新）：
  ├── Eureka + LB 缓存 = 双重缓存（感知延迟叠加）
  └── 官方建议：Eureka 用户可禁用 LB 缓存（注册中心已缓存）

Nacos 客户端：
  ├── Nacos 的 UDS 订阅是推送式（变更即时通知）
  └── LB 缓存会削弱推送的即时性（TTL 内旧列表）
```

### 5.2 决策建议

| 场景 | 建议 |
|------|------|
| Eureka | 官方建议关 LB 缓存（`cache.enabled: false`）或至少理解双重延迟 |
| Nacos（推送式） | 保留 LB 缓存但 TTL 合理（推送是即时，LB 缓存是防压力） |
| 高实时要求 | TTL 调小 + HealthCheck（双管齐下） |
| 注册中心不稳定 | **必须保留缓存**（兜底可用性） |

> ⚠️ **常见事故**：Nacos 用户把 LB 缓存 TTL 调成 0 或关缓存——注册中心压力陡增 + 注册中心抖动时调用全挂——**缓存是可用性保险，别为了"即时性"轻易关**（[08 篇](08-生产实践与选型避坑.md) 坑位表）。

## 6. 调优建议

### 6.1 参数基线

| 参数 | 默认 | 建议 | 说明 |
|------|------|------|------|
| cache.ttl | 35s | 15-60s | 故障感知 vs 注册中心压力的平衡点 |
| cache.capacity | 256 | 服务数 × 1.5 | 缓存容量不够 = 频繁逐出 |
| health-check.interval | — | 5-15s | 探测越勤越快感知，成本是探测请求量 |
| health-check.path | /actuator/health | 业务健康端点 | 探测内容决定感知质量 |
| eager-load.clients | 空 | 核心服务 | 首调冷启动消除 |

### 6.2 调优组合场景

| 场景 | 推荐组合 |
|------|---------|
| 普通生产 | TTL 35s + 重试/熔断兜底（默认即可） |
| 秒级故障感知需求 | TTL 10s + HealthCheck 5s |
| 大促/高可用 | TTL 保留 + HealthCheck + 多注册中心 |
| 注册中心弱 | TTL 60s + 缓存必开（可用性优先） |

> 💡 调优哲学：**缓存与健康检查是"延迟 vs 成本"的旋钮**——别追求极端即时（注册中心扛不住），也别放任 35s（故障恢复慢）——结合业务 SLA 选平衡点，压测验证。
