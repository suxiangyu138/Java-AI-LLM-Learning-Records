## 1. 可靠性加固

Bus 默认 fire-and-forget，生产要加固到 at-least-once：

### 1.1 RabbitMQ 加固

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual            # ★ 手动 ack（消费成功才确认）
        default-requeue-rejected: false     # ★ 拒绝的消息不入队重试（防死循环）
    publisher-confirm-type: correlated       # 发布确认（可选，观察发布结果）
```

| 配置 | 效果 |
|------|------|
| `acknowledge-mode: manual` | 消费失败不 ack → 消息可重投 |
| `default-requeue-rejected: false` | 处理不了的消息直接丢弃（不进死循环） |
| `publisher-confirm-type` | 发布确认回调（可告警） |

> ⚠️ **默认配置的坑**：RabbitMQ 默认**自动 ack + 拒绝消息无限重入队**——一个坏事件会让队列反复投递，拖垮消费；手动 ack + 不重入是生产标配。

### 1.2 Kafka 加固

```yaml
spring:
  cloud:
    stream:
      kafka:
        binder:
          configuration:
            enable:
              auto:
                commit: false              # ★ 禁自动提交 offset
      bindings:
        springCloudBusInput:
          consumer:
            partitioned: true              # ★ 分区广播（每实例都消费）
```

| 配置 | 效果 |
|------|------|
| `enable.auto.commit=false` | 处理成功才提交（at-least-once） |
| `partitioned: true` | Bus 广播语义（否则同组竞争消费） |

### 1.3 终极兜底：轮询

```text
即使加固，广播仍是"尽力而为"：
    └─ 断线重连期间的事件会丢
    └─ 兜底：客户端启动/定时轮询 Config Server（spring.cloud.config 原生支持）
    └─ 原则：Bus 负责"即时性"，轮询保证"最终一致"
```

> 🎯 生产结论：**Bus 是"快"通道，轮询是"稳"兜底**——两者并存，配置最终一致；别指望 Bus 单通道覆盖可靠性。

## 2. 安全红线

| 风险 | 说明 | 防护 |
|------|------|------|
| 未授权触发刷新 | 任何人 POST bus-refresh 全网刷配置 | 端点鉴权（Spring Security）+ 内网 VPC |
| Webhook 暴露公网 | Git 回调被恶意触发 | Token 校验 + 内网回调 |
| 事件内容泄露 | 自定义事件载荷敏感 | 载荷不传敏感数据；MQ 网络隔离 |
| 管理端点全开 | actuator 全部暴露 | 只暴露必要端点（include 白名单） |

```yaml
# 端点鉴权示例（Spring Security 保护 bus 端点）
spring:
  security:
    user:
      name: busadmin
      password: ${BUS_ADMIN_PWD}
management:
  endpoints:
    web:
      exposure:
        include: bus-refresh, health       # ★ 只暴露必要的
```

> ⚠️ **安全红线一句话**：**`/actuator/bus-refresh` 是"全网控制开关"，必须鉴权 + 内网**——暴露出去等于把配置刷新权交给公网（[02 篇](02-快速开始与配置刷新速查.md) Webhook 场景同样）。

## 3. 生产架构建议

```text
生产推荐拓扑：
    Git 仓库（配置唯一事实源）
        │ Webhook（内网 + Token）
        ▼
    Config Server（固定刷新入口，鉴权）
        │ POST /actuator/bus-refresh
        ▼
    RabbitMQ（专用 vhost/topic，手动 ack）
        ▼
    各微服务实例（bus.id 唯一 + refresh.enabled + trace）
        └─ 兜底：定时轮询 Config Server
```

| 实践项 | 建议 |
|--------|------|
| 刷新入口固定 | 只向 Config Server 发刷新（业务服务不承担调度） |
| MQ 专用隔离 | RabbitMQ 单独 vhost / Kafka 单独 topic |
| bus.id 唯一 | `app:port:random`（Docker 必须） |
| 监控 | trace 开启 + MQ 消费指标监控 |
| 灰度 | 先定向刷新一台（`service:port`）验证，再全网 |

## 4. 选型决策：Bus vs Nacos 推送

| 维度 | Bus + Config | Nacos 配置中心 |
|------|-------------|---------------|
| 刷新机制 | **MQ 广播事件**（推） | **客户端长轮询拉取**（秒级） |
| 额外组件 | **需要 MQ** | **不需要**（Nacos 自带） |
| 可靠性 | fire-and-forget（可加固） | 拉模式（丢了下次拉回来） |
| 运维复杂度 | Config + MQ + Bus 三件 | Nacos 一组件 |
| 生态 | 传统 Spring Cloud | **SCA 生态（首选）** |
| 定向刷新 | destination 精确到实例 | namespace/group + 客户端策略 |
| 适用 | 存量 Config 体系 | 新项目 / SCA 体系 |

```text
决策流程：
    用 Nacos（SCA 生态）？ ──是──► 不需要 Bus（Nacos 推送够用）
    存量 Spring Cloud Config？──是──► 上 Bus（实例 > 3 才值得）
    实例 ≤ 3？ ──是──► 手动逐个 refresh 也行，Bus 收益小
```

> 🎯 面试必答：**"你项目用 Bus 还是 Nacos？"**——**SCA 生态用 Nacos**（长轮询拉取，免 MQ、更可靠）；**传统 Config 生态才用 Bus**（MQ 广播）。面试加分：能讲清"推送 vs 拉取"的可靠性差异——**拉模式天然防丢**（丢了下次拉回来），推模式依赖 MQ 可靠性。

## 5. 高频坑排错表

| # | 现象 | 根因 | 处理 |
|---|------|------|------|
| 1 | 404：/actuator/bus-refresh | 端点没暴露 | include 加 bus-refresh |
| 2 | 刷新不生效 | `refresh.enabled` 默认 false | 显式 true |
| 3 | 事件被单实例重复消费 | bus.id 重复（Docker 固定端口） | id 加 `${random.value}` |
| 4 | 定向刷新静默失败 | destination 大小写/格式错 | trace 验证；`app:**` 起步 |
| 5 | 事件发了没人收到 | 事件包没扫描 | @RemoteApplicationEventScan |
| 6 | 消费端反序列化失败 | 无无参构造/类型名重复 | 按 [04 篇](04-自定义事件与业务广播速查.md) 规范 |
| 7 | 坏事件死循环 | 默认 requeue | `default-requeue-rejected: false` |
| 8 | Kafka 只有一台刷新 | consumer group 竞争 | `partitioned: true` |
| 9 | 断线后事件丢失 | fire-and-forget 语义 | 轮询 Config Server 兜底 |
| 10 | @Value 不更新 | 没标 @RefreshScope | 标注 + 配置类注入 |
| 11 | 刷新后取旧值 | 单例注入时机 | ObjectFactory/ScopedProxy |
| 12 | 升级 Boot 3 编译失败 | javax → jakarta | 包迁移 + Bus 4.x |

## 6. 上线验证清单

| 阶段 | 检查项 | 通过标准 |
|------|--------|---------|
| 部署 | Bus 依赖、MQ 连通、端点暴露 | 各实例启动无异常 |
| 全网刷新 | 改配置 → bus-refresh | 所有实例 @RefreshScope 更新 |
| 定向刷新 | `service:port` 刷新 | 仅目标实例更新 |
| 可靠性 | 杀一个实例再广播 | 存活实例正常刷新；重启后轮询拉回新配置 |
| 安全 | 无鉴权访问 bus-refresh | 返回 401/403 |
| 监控 | trace 开启 + MQ 指标 | 广播链路可查 |
| 兜底 | 停 MQ → 轮询兜底 | 配置仍最终一致（延迟） |

> 🎯 上线总原则：**"先兜底（轮询），后 Bus（即时）"**——Bus 是锦上添花的即时通道，轮询是保底的最终一致；生产配置变更流程 = Webhook 自动 + 轮询兜底 + 监控告警。
