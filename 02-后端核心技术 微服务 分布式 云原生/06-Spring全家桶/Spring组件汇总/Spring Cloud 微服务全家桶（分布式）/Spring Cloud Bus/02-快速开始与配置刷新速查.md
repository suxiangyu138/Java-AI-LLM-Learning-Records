## 1. 配置刷新场景总览

```text
完整刷新链路：
    Git 仓库（配置源）改配置
        │ ① Config Server 拉取/通知
        ▼
    Config Server（配置中心）
        │ ② POST /actuator/bus-refresh（人工/Webhook）
        ▼
    Bus 发布 RefreshRemoteApplicationEvent → MQ 广播
        │ ③ 所有订阅实例消费
        ▼
    各实例：ContextRefresher 重建 @RefreshScope Bean → 新配置生效（无重启）
```

| 刷新方式 | 手动 | Webhook |
|---------|------|---------|
| 触发 | 人工 POST bus-refresh | Git 提交事件自动触发 |
| 场景 | 灰度/验证 | 日常配置变更 |
| 可靠性 | 人工确认 | 全自动（需保护端点） |

## 2. 依赖与配置

### 2.1 依赖

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bus-amqp</artifactId>
</dependency>
<!-- 若配置源是 Config Server，再加 -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-config</artifactId>
</dependency>
```

### 2.2 配置（每个微服务）

```yaml
spring:
  application:
    name: order-service
  rabbitmq:
    host: localhost
    port: 5672
    username: guest
    password: guest
  cloud:
    bus:
      id: ${spring.application.name}:${server.port}:${random.value}  # ★ 实例唯一 ID
      refresh:
        enabled: true          # ★ 2021.0+ 默认 false，必须显式开
      trace:
        enabled: true          # 开启事件跟踪（生产建议）
management:
  endpoints:
    web:
      exposure:
        include: bus-refresh, bus-env, health, info, httptrace   # ★ 端点暴露
```

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `spring.cloud.bus.id` | 空 | **必须唯一**：`app:port:random` 防 ID 冲突（去重/定向依赖） |
| `spring.cloud.bus.refresh.enabled` | **false** | 2021.0+ 默认关，不开则事件被丢弃 |
| `spring.cloud.bus.trace.enabled` | false | 事件跟踪（httptrace 看广播链路） |
| `spring.cloud.bus.destination` | springCloudBus | 默认 Topic 名 |
| `spring.cloud.bus.ack.enabled` | true | ack 事件（trace 用） |

> ⚠️ **Docker 部署的 bus.id 陷阱**：容器里 `server.port` 固定（如 8080），硬编码 `app:8080` 会让**所有实例 ID 相同** → 事件被单个消费者重复消费/定向失效——**必须加 `${random.value}` 保证唯一**。

## 3. @RefreshScope 正确用法

### 3.1 注解目标

| 用法 | 说明 | 推荐 |
|------|------|------|
| `@RestController + @RefreshScope` | 类上标注，整个 Bean 重建 | ✅ 配置直接注入 |
| `@ConfigurationProperties` 类 | 属性绑定 Bean 加 @RefreshScope | ✅ 推荐（集中配置类） |
| 普通 Service 上标 | 不推荐（重建有状态 Bean 有风险） | ⚠️ 尽量只标"配置 Bean" |
| 启动类上标 | 无意义 | ❌ |

```java
// 推荐：配置类集中管理
@RefreshScope
@ConfigurationProperties(prefix = "order")
public class OrderProperties {
    private int timeout = 5000;
    private boolean slowQueryLog = false;
    // getter/setter
}

// Controller 里注入（不标 @RefreshScope，注入的是代理）
@RestController
public class OrderController {
    private final OrderProperties props;      // ScopedProxy 注入
    public OrderController(OrderProperties props) { this.props = props; }
    @GetMapping("/timeout") public int timeout() { return props.getTimeout(); }
}
```

### 3.2 刷新时机的监听

```java
// 刷新完成后收到通知（做缓存预热等）
@Component
public class RefreshListener {
    @EventListener(RefreshScopeRefreshedEvent.class)
    public void onRefresh(RefreshScopeRefreshedEvent e) {
        // @RefreshScope Bean 已重建，这里做后置动作
    }
}
```

> ⚠️ **@RefreshScope 三坑**：① 被单例 Bean 构造时直接注入会**拿到旧值**（需 `ObjectFactory`/`ScopedProxyMode.TARGET_CLASS` 注入）；② 不标 @RefreshScope 的 @Value 不会更新；③ 静态字段/static 配置不参与刷新。

## 4. bus-refresh 三形态

### 4.1 全网刷新（广播所有实例）

```bash
curl -X POST http://localhost:8080/actuator/bus-refresh
```

| 发向哪里 | 效果 |
|---------|------|
| Config Server | 所有客户端刷新（**推荐**：职责单一，见下） |
| 任意客户端实例 | 所有实例（含发送方自身）刷新 |

> 💡 **推荐向 Config Server 发**：业务服务不应承担"配置刷新调度"职责，且服务地址会随迁移变化——**Config Server 是固定的刷新入口**（也方便 Webhook 指向唯一地址）。

### 4.2 定向刷新（destination）

```bash
# 按服务：刷新 order-service 所有实例
curl -X POST "http://localhost:8080/actuator/bus-refresh/order-service:**"

# 按实例：只刷指定实例（app:port）
curl -X POST "http://localhost:8080/actuator/bus-refresh/order-service:8081"

# 查询参数形式（等价）
curl -X POST "http://localhost:8080/actuator/bus-refresh?destination=order-service:**"
```

| destination 写法 | 匹配范围 | 示例 |
|-----------------|---------|------|
| `app:**` | 指定服务的所有实例 | `order-service:**` |
| `app:port` | 指定服务 + 指定端口 | `order-service:8081` |
| `app:index:id` | 精确实例 | `order-service:0:abc123` |
| `**` | 全部 | 等价全网刷新 |

> ⚠️ **destination 大小写敏感**：`order-service` 与 `Order-Service` 不互通（精确匹配）；匹配失败时事件被静默忽略（无报错，定向排查靠 trace）。

### 4.3 触发后的刷新动作（各实例内）

```text
收到 RefreshRemoteApplicationEvent → ContextRefresher 执行：
    ① 重新从 Config Server 拉配置（spring.cloud.config 的 refresh）
    ② 清除 RefreshScope 缓存 → 标记 @RefreshScope Bean 失效
    ③ 下次访问时重建 Bean（懒重建）→ 新配置生效
    ④ 发 RefreshScopeRefreshedEvent（可监听）
```

## 5. bus-env：环境属性定向更新

比"全量刷新"更精细——**只更新指定实例的指定属性**：

```bash
# 更新 order-service:8081 的 order.timeout 属性
curl -X POST "http://localhost:8080/actuator/bus-env?destination=order-service:8081&name=order.timeout&value=3000"
```

| 参数 | 说明 |
|------|------|
| `destination` | 定向目标（同 destination 语法） |
| `name` | 属性名（如 order.timeout） |
| `value` | 新值 |

> 💡 场景：**灰度验证单实例新参数**（不广播、不动配置仓库）——适合"临时调参数看效果"；正式变更仍走配置源 + 全量刷新。

## 6. Git Webhook 全自动刷新

```text
自动刷新链路：
    Git 提交（配置变更）
        │ Webhook（Gitee/GitHub/GitLab 配置中心）
        ▼
    回调 Config Server 的 webhook 端点
        │ （或直接 POST /actuator/bus-refresh）
        ▼
    MQ 广播 → 全网刷新 → 配置生效（零人工）
```

| 平台 | Webhook 配置 |
|------|-------------|
| GitHub | Settings → Webhooks → 填 Config Server 刷新 URL |
| Gitee | 仓库管理 → WebHooks |
| GitLab | Settings → Webhooks |

> ⚠️ **Webhook 安全红线**：暴露公网的回调端点**必须鉴权**（Token/内网）——否则任何人都能触发全网刷新（配置可能被刷成异常状态）——**生产：内网 VPC + 密钥校验**（[05 篇](05-生产实践与选型避坑速查.md) 安全清单）。

## 7. 常见问题

| 现象 | 原因 | 处理 |
|------|------|------|
| 404：bus-refresh 不存在 | 端点没暴露 | `management.endpoints.web.exposure.include` 加 bus-refresh |
| 刷新没生效 | `refresh.enabled` 默认 false | 显式 `spring.cloud.bus.refresh.enabled: true` |
| 事件被单实例重复消费 | bus.id 重复（Docker） | id 加 `${random.value}` |
| 定向刷新没效果 | destination 大小写/格式不符 | 用 `app:**` 验证；开 trace 看匹配 |
| @Value 不更新 | Bean 没标 @RefreshScope | 标注 + 用配置类注入 |
| 刷新后拿旧值 | 单例构造时注入 | ObjectFactory / ScopedProxy 注入 |
| MQ 连不上 | RabbitMQ 地址/账号错 | 查 spring.rabbitmq.* + MQ 健康 |
