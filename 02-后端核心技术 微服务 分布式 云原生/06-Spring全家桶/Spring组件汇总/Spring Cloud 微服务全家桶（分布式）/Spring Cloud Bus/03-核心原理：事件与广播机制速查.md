## 1. 整体架构：两层拼接

```text
Bus = Spring 事件机制（应用内） + MQ 广播（应用间）

    发送方实例：
    Actuator 端点 ──► BusAutoConfiguration
        │                │ 包装成 RemoteApplicationEvent
        ▼                ▼
    Spring 事件（本地 publish）──► BusBridge 桥接
                                       │ 写入 Stream channel
                                       ▼
    MQ（RabbitMQ Topic / Kafka）──► 广播

    接收方实例：
    MQ ──► Stream listener（BusConsumer）
            │ 反序列化 RemoteApplicationEvent
            ├─ ① 来源去重（自己的事件不处理）
            ├─ ② destination 匹配（不匹配则忽略）
            └─ ③ 发布本地 Spring 事件 → ContextRefresher 执行刷新
```

| 层 | 组件 | 职责 |
|----|------|------|
| 应用内 | Spring ApplicationEvent | 本地事件发布/监听 |
| 桥接层 | BusBridge / BusConsumer | 本地事件 ↔ MQ 消息互转 |
| 传输层 | Spring Cloud Stream | binder 抽象（RabbitMQ/Kafka 二选一） |
| 触发层 | RefreshBusEndpoint | `/actuator/bus-refresh` 端点 |

> 🎯 一句话理解：**"在一个实例里 publish 一个 Spring 事件，Bus 把它变成 MQ 消息广播出去，所有实例收到后重新 publish 成本地事件执行"**——两层事件 + 一层 MQ，就是 Bus 的全部。

## 2. 事件模型：RemoteApplicationEvent 家族

| 事件类 | 用途 | 触发端点 |
|--------|------|---------|
| `RefreshRemoteApplicationEvent` | 配置刷新广播 | `/actuator/bus-refresh` |
| `EnvironmentChangeRemoteApplicationEvent` | 环境属性更新 | `/actuator/bus-env` |
| `AckRemoteApplicationEvent` | ack 确认（trace 用） | 自动 |
| `SentRemoteApplicationEvent` | 发送记录（trace 用） | 自动 |
| 自定义子类 | 业务广播 | 自定义端点/事件 |

### 2.1 事件类核心结构

```java
// RemoteApplicationEvent 基类关键字段
public abstract class RemoteApplicationEvent extends ApplicationEvent {
    private String originService;      // 来源实例 ID（app:index:id）
    private String destinationService; // 目标（null=全网；或 app:** / app:port）
    private String id;                 // 事件唯一 ID（去重）
    // 序列化：JSON（@JsonTypeName 标识具体事件类型）
}
```

| 字段 | 作用 |
|------|------|
| `originService` | 发送方 ID（**来源去重依据**） |
| `destinationService` | 目标匹配串（**定向依据**） |
| `id` | 事件 ID（防重复消费） |

> 🎯 面试必答：**"事件怎么跨实例传？"**——事件以 **JSON 序列化**（@JsonTypeName 标注类型名）写入 MQ；消费方按类型反序列化还原为具体事件类，再转成本地 Spring 事件——**事件类要无参构造 + Jackson 可序列化**（[04 篇](04-自定义事件与业务广播速查.md) 有自定义规范）。

## 3. 广播链路：Stream 桥接

### 3.1 RabbitMQ 侧（默认总线形态）

```text
RabbitMQ 拓扑（BusAutoConfiguration 自动创建）：
    Exchange：springCloudBus（topic 类型，bus.destination 可改）
        │ bind
    Queue：springCloudBus.anonymous.xxx（每实例一个临时队列）
        │
    广播：事件 → Exchange → 所有绑定队列 → 各实例消费
    特点：无持久化语义（临时队列 + 自动删除），fire-and-forget
```

### 3.2 Kafka 侧

```text
Kafka 拓扑：
    Topic：springCloudBus（topic 名可配）
    ConsumerGroup：每实例独立 group（默认）→ 每个实例都收到广播
    注意：若多实例同 group，广播会变成"组内竞争消费"（只有一台处理）——Bus 场景每实例必须独立消费组
```

> ⚠️ **Kafka 广播的坑**：Bus 语义是"**每实例都处理**"——Kafka 下需保证各实例 **consumer group 不同**（Bus 默认按实例生成）；`partitioned=true` 可强制分区广播语义。

### 3.3 可靠性语义

| 语义 | 说明 | 加固手段 |
|------|------|---------|
| 默认 | **fire-and-forget**（发完不管） | — |
| 目标 | at-least-once（至少一次） | RabbitMQ 手动 ack + Kafka 禁自动提交 |
| 丢失场景 | 实例断线重连期间的事件 | 重启后轮询 Config Server 兜底 |

> 💡 生产加固配置（[05 篇](05-生产实践与选型避坑速查.md) 有完整清单）：RabbitMQ `acknowledge-mode=manual` + `default-requeue-rejected=false`；Kafka `enable.auto.commit=false`。

## 4. destination 定向匹配

### 4.1 匹配规则

```text
destination 由 PathMatcher（冒号分隔）匹配实例 ID：
    实例 ID 格式：app:index:id（如 order-service:8081:abc123）
    匹配模式：
        order-service:**    → app 前缀匹配（该服务全部实例）
        order-service:8081  → app + index（该实例）
        **                  → 全部
    destinationService = null → 表示全网（无过滤）
```

| 匹配项 | 例子 | 命中 |
|--------|------|------|
| `order-service:**` | 模式 | 所有 order-service 实例 |
| `order-service:8081` | 模式 | 端口 8081 实例 |
| `**` | 模式 | 所有 |
| 大小写 | `Order-Service` ≠ `order-service` | **精确匹配** |

### 4.2 不匹配的后果

```text
消费方收到事件 → 比对 destinationService：
    不匹配 → 静默丢弃（不打日志）→ 看起来"没刷新"
    匹配   → 转本地事件执行
```

> ⚠️ **定向排查技巧**：定向刷新没生效且无报错——**开 trace**（`spring.cloud.bus.trace.enabled: true`）看 httptrace 里事件是否被目标实例消费；destination 写法错误是最常见的"静默失败"。

## 5. 来源去重机制

```text
为什么需要去重：
    发送方自己也订阅了 MQ → 会收到自己发的事件
    → 若不处理：发送方自己触发自己的刷新（无害但多余）
    → 更危险：事件被再次转发？——Bus 设计上消费后不转发（非级联）

去重实现：
    BusConsumer 收到事件 → originService == 本地实例 ID？
        ├─ 是 → 丢弃（自己的事件不执行）
        └─ 否 → 按 destination 匹配执行
```

| 要点 | 说明 |
|------|------|
| 去重依据 | `originService`（发送方实例 ID） |
| 前提 | **bus.id 全局唯一**（否则误判"自己的事件"而丢弃） |
| 级联转发 | 不转发（收到的事件不再发回 MQ）——一次广播只跑一跳 |

> 🎯 面试必答：**"发送方会收到自己广播的事件吗？"**——会（自己也在订阅队列），但 Bus 按 **originService == 本地 ID 丢弃**；所以 **bus.id 唯一性不仅是定向的基础，也是去重的正确性前提**（[05 篇](05-生产实践与选型避坑速查.md) 坑位 #2）。

## 6. 事件跟踪（trace）

```yaml
spring:
  cloud:
    bus:
      trace:
        enabled: true          # 开启后产生 Sent/Ack 事件
management:
  endpoints:
    web:
      exposure:
        include: httptrace     # 查看跟踪
```

```text
trace 能看到的链路：
    SentRemoteApplicationEvent（事件被发往 MQ）
    AckRemoteApplicationEvent（各实例确认收到）
    → httptrace 端点列出：谁发了、谁收到了（含 originService/destinationService）
```

| 用途 | 说明 |
|------|------|
| 排错广播链路 | 看事件有没有到目标实例 |
| 验证定向匹配 | 看 destination 是否命中 |
| 监控广播风暴 | 事件量异常可感知 |

## 7. 面试高频问题

| 问题 | 一句话答案 |
|------|-----------|
| Bus 怎么实现全网刷新？ | 事件 → MQ 广播 → 各实例消费执行 @RefreshScope 重建 |
| Bus 基于什么构建？ | Spring Cloud Stream（binder 适配 RabbitMQ/Kafka） |
| 事件怎么去重？ | originService == 本地 ID 则丢弃（前提 bus.id 唯一） |
| 定向刷新怎么匹配？ | destination 用 PathMatcher 匹配 app:index:id |
| Bus 可靠吗？ | fire-and-forget（默认），可加固到 at-least-once，仍不保证强一致 |
| 为什么需要 MQ？ | 发布-订阅广播：一个 Topic 全实例订阅（Bus 无存储语义） |
