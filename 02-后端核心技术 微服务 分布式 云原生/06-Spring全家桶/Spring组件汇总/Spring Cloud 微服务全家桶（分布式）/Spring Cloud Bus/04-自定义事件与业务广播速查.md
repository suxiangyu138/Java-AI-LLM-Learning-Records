## 1. 为什么自定义事件

| 场景 | 说明 |
|------|------|
| 批量指令 | 通知所有实例"清空本地缓存"（缓存预热/失效广播） |
| 集群状态同步 | 广播"配置源已切换"等管理事件 |
| 分布式控制 | 全量实例执行某个动作（如刷新线程池参数） |
| 灰度切换 | 定向通知部分实例切换开关 |

> 🎯 原则：**"需要所有实例同时做一件事，且不要求可靠确认"**——适合 Bus 广播；**"要保证每个实例都收到并处理"**——别用 Bus（fire-and-forget），用 MQ 业务队列 + 确认。

## 2. 自定义事件三步走

### 2.1 定义事件类（继承 RemoteApplicationEvent）

```java
// ① 事件类：继承 RemoteApplicationEvent
@JsonTypeName("cacheRefreshEvent")                 // ★ JSON 类型名（序列化标识）
public class CacheRefreshRemoteEvent extends RemoteApplicationEvent {
    private String cacheName;                      // 业务载荷
    private String version;

    // ★ 必须有无参构造（Jackson 反序列化）
    public CacheRefreshRemoteEvent() {}

    // 发布用构造：originService 由 Bus 填充
    public CacheRefreshRemoteEvent(Object source, String originService,
                                   String destinationService, String cacheName) {
        super(source, originService, destinationService);
        this.cacheName = cacheName;
    }
    // getter/setter
}
```

### 2.2 发送（任意实例发布）

```java
// ② 发送：通过 ApplicationEventPublisher
@Service
public class CacheCommandService {
    @Autowired
    private ApplicationEventPublisher publisher;

    public void broadcastCacheRefresh(String cacheName) {
        publisher.publishEvent(new CacheRefreshRemoteEvent(
                this,                              // source
                BusProperties.getSelfId(),         // originService（Bus 自动）
                null,                              // destinationService = null → 全网
                cacheName));
    }
}
```

### 2.3 监听（各实例消费）

```java
// ③ 监听：@EventListener 本地事件（Bus 消费后转成本地事件）
@Component
public class CacheRefreshListener {

    @EventListener(CacheRefreshRemoteEvent.class)
    public void onCacheRefresh(CacheRefreshRemoteEvent event) {
        log.info("收到缓存刷新指令: cache={}", event.getCacheName());
        cacheManager.clearCache(event.getCacheName());   // 执行动作
    }
}

// 若事件类不在 org.springframework.cloud.bus.event 包下，需显式扫描：
@Configuration
@RemoteApplicationEventScan(basePackages = "com.example.events")  // ★ 扫描事件包
public class BusConfig { }
```

> 🎯 三步口诀：**① 继承 + @JsonTypeName + 无参构造；② publishEvent 发出去；③ @EventListener 收进来**——Bus 处理中间一切（序列化、广播、去重、匹配）。

## 3. 事件规范与序列化约束

| 约束 | 说明 | 违反后果 |
|------|------|---------|
| **无参构造必须** | Jackson 反序列化需要 | 消费端反序列化失败，事件被丢 |
| **@JsonTypeName 唯一** | 类型名标识具体事件 | 重名 → 反序列化成错误类型 |
| **字段可序列化** | 载荷用基础类型/String/简单对象 | 复杂对象序列化失败 |
| **包扫描** | 事件放 `org.springframework.cloud.bus.event` 子包，或 `@RemoteApplicationEventScan` 指定 | 找不到事件类型，消费失败 |
| **originService 正确** | 发布时用当前实例 ID | 去重失效/定向错乱 |
| getter/setter | Jackson 需要 | 字段丢失 |

```java
// 事件包推荐组织：
// 方式 A：org.springframework.cloud.bus.event 子包（默认扫描）
package org.springframework.cloud.bus.event.cache;
// 方式 B：业务包 + @RemoteApplicationEventScan(basePackages="com.example.events")
```

> ⚠️ **最隐蔽的坑：事件类没被扫描到**——启动不报错，事件发出去后**所有实例都收不到**（反序列化失败静默丢弃）；**先用 trace 验证事件被消费**，再排业务逻辑（[05 篇](05-生产实践与选型避坑速查.md) 坑位表）。

## 4. 业务广播场景设计

### 4.1 典型场景：本地缓存全局失效

```text
场景：订单服务各实例有本地缓存（Caffeine），后台改商品数据
    方案：管理端 → 广播 CacheRefreshRemoteEvent（destination=product-service:**）
         → 商品服务各实例清缓存 → 下次查询回源
    要点：destination 定向到受影响的服务，避免全网广播
```

### 4.2 定向 vs 全网设计

| 广播类型 | destination | 场景 |
|---------|-------------|------|
| 全网 | null / `**` | 全局配置刷新、全站缓存失效 |
| 按服务 | `service:**` | 只影响该服务的指令 |
| 按实例 | `service:port` | 灰度验证、单实例操作 |

### 4.3 幂等与去重设计

```java
// 消费端务必幂等（广播可能重复：网络重发/多路径）
public void onCacheRefresh(CacheRefreshRemoteEvent event) {
    String key = event.getVersion();                    // 事件版本号
    if (processedCache.add(key)) {                      // 已处理集合去重
        cacheManager.clearCache(event.getCacheName());
    }
}
```

| 设计要点 | 说明 |
|---------|------|
| 事件带版本号 | 消费端按版本去重（幂等） |
| 动作必须幂等 | 清缓存天然幂等；**扣库存等非幂等动作禁止走 Bus** |
| 不依赖顺序 | 广播无序，业务不能假设先后 |

> ⚠️ **红线：Bus 只发"指令/通知"，绝不承载"业务数据变更"**——清缓存、刷新参数可以；扣款、改库不行（那是 MQ 可靠消息 + 幂等消费的领域）。

## 5. 与 MQ 直连的边界

| 对比 | Bus 广播 | MQ 直连（业务队列） |
|------|---------|-------------------|
| 语义 | 广播指令（fire-and-forget） | 可靠投递（确认/重试/死信） |
| 可靠性 | 不强求 | at-least-once + 幂等 |
| 载荷 | 轻（指令参数） | 业务数据（订单等） |
| 积压 | 无（临时队列） | 有（队列/分区） |
| 消费确认 | 无 | 有 |
| 典型场景 | 配置刷新、缓存失效 | 下单通知、异步处理 |

> 🎯 选型一句话：**"通知所有实例做件事"→ Bus；"把业务数据可靠地发给一个消费者"→ MQ 直连**——两者可共存，但别互相替代。

## 6. 常见问题

| 现象 | 原因 | 处理 |
|------|------|------|
| 事件发出去没人收到 | 事件包没扫描（@RemoteApplicationEventScan 缺失） | 加扫描注解 |
| 反序列化报错 | 无无参构造 / 字段不兼容 | 补无参构造；简化载荷 |
| 事件类型串了 | @JsonTypeName 重复 | 类型名全局唯一 |
| 定向事件全量执行 | destinationService 拼错 | 用 trace 验证匹配 |
| 消费端重复执行 | 广播重复/网络重发 | 消费端幂等（版本号去重） |
| 业务数据走 Bus 丢了 | 用错了通道 | 换 MQ 可靠队列 |
