## 1. 加密模型：密文入库、解密下发

```text
核心原则：敏感值"at rest"（Git 仓库里）永远是密文
  ├── 加密：{cipher}xxxx 存入 Git
  ├── 存储：Git 仓库里只有密文（泄露仓库 ≠ 泄露密码）
  ├── 解密：Config Server 拉取配置时解密 → 只下发明文给客户端
  └── 明文只存在于：Config Server 内存 + 客户端运行时（不落盘配置）
```

| 环节 | 明文？ | 说明 |
|------|:---:|------|
| Git 仓库 | ❌ 密文 | {cipher} 前缀 + 密文 |
| Config Server 存储 | ❌ | 后端读到密文 |
| Server → 客户端 HTTP | ✅ 明文 | 解密后下发（内网/HTTPS） |
| 客户端运行时 | ✅ | 正常业务读取 |

> 🎯 面试必答：**"Config 怎么保证密码安全？"**——**密文入库 + 服务端解密**：Git 里只有 `{cipher}` 密文（仓库泄露也不泄密），Config Server 持有密钥（encrypt.key 或 keyStore），拉取时解密后下发客户端——密钥只存在于 Server，客户端/仓库都拿不到密钥。

## 2. /encrypt /decrypt 端点

### 2.1 用法

```bash
# 加密（Server 端，POST 明文）
curl -X POST http://localhost:8888/encrypt -s -d mysecret
682bc583f4641835fa2db009355293665d2647dade3375c0ee201de2a49f7bda

# 解密（验证用）
curl -X POST http://localhost:8888/decrypt -s \
     -d 682bc583f4641835fa2db009355293665d2647dade3375c0ee201de2a49f7bda
mysecret
```

### 2.2 curl 坑（官方文档原话警告）

| 坑 | 正确姿势 |
|----|---------|
| 特殊字符（`+` 尤其坑） | 用 `--data-urlencode` 且值前加 `=`：`--data-urlencode "=my+secret"` |
| 静默输出 | 加 `-s`（否则统计信息混入密文） |
| 密文落文件 | 输出到文件再复制，避免 shell 历史泄露 |

### 2.3 按应用/环境加密（多密钥场景）

```text
端点路径：/encrypt/{application}/{profiles} 和 /decrypt/{application}/{profiles}
  └── 需自定义 @Bean TextEncryptorLocator（按应用/环境返回不同加密器）
  └── 默认 TextEncryptorLocator 对所有请求用同一个密钥
```

## 3. 对称密钥：encrypt.key

### 3.1 配置

```properties
# Config Server 的 application.properties（或 bootstrap.properties）
encrypt.key=my-strong-secret-key
```

```bash
# 或用环境变量（推荐，不进配置文件）
export ENCRYPT_KEY=my-strong-secret-key
```

### 3.2 特点

| 维度 | 说明 |
|------|------|
| 算法 | AES 对称加密（同一密钥加解密） |
| 优点 | 配置最简单（一个属性） |
| 缺点 | 密钥泄 = 全部泄；密钥在 Server 配置里（仍需保护） |
| 适用 | 轻量场景、团队小、无严格合规 |

> ⚠️ **加密配置的生效位置**：用了 bootstrap 模式（starter-bootstrap 或 spring.cloud.bootstrap.enabled=true）时，`encrypt.key` 必须放 **bootstrap.properties** 而不是 application.properties——放错位置密钥读不到，解密静默失败（所有 {cipher} 变 invalid）。

## 4. 非对称密钥：encrypt.keyStore

### 4.1 生成密钥库（keytool）

```bash
# 生成 RSA 密钥对并存入 jks 密钥库
keytool -genkeypair -alias config-server-key \
        -keyalg RSA -keysize 2048 -storetype jks \
        -keystore config-server.jks -storepass changeit \
        -validity 3650
```

### 4.2 配置

```properties
# Config Server
encrypt.keyStore.location=classpath:/config-server.jks
encrypt.keyStore.password=changeit
encrypt.keyStore.alias=config-server-key
encrypt.keyStore.type=jks
```

### 4.3 特点与用法

| 维度 | 说明 |
|------|------|
| 算法 | RSA 非对称：**公钥加密（加密端点），私钥解密（下发时）** |
| 安全等级 | 高于对称（私钥只存 Server，公钥可分发） |
| 公钥分离 | 可只配公钥 → 团队本地用公钥加密，Server 只解密（密钥不集中） |
| 适用 | 生产、合规要求、密钥需要轮换 |

```bash
# 用公钥文件加密（Spring CLI）
spring encrypt mysecret --key @${HOME}/config-server-pub.pem
```

> 🎯 对称 vs 非对称一句话：**对称省事（一个 key 全搞定）、非对称安全（公钥加密私钥解密，私钥永不离开 Server）**——生产推荐非对称，尤其有合规要求时。

## 5. 加密值的写入与解析

### 5.1 两种格式的写法差异

```yaml
# YAML：必须加引号！
spring:
  datasource:
    password: '{cipher}682bc583f4641835fa2db009355293665d2647dade3375c0ee201de2a49f7bda'
```

```properties
# .properties：绝对不能加引号！（加了不解密）
spring.datasource.password={cipher}682bc583f4641835fa2db009355293665d2647dade3375c0ee201de2a49f7bda
```

> ⚠️ **格式坑（高频）**：YAML 不加引号 → YAML 解析异常/被当普通字符串；properties 加引号 → 解密不生效——**两种格式引号规则相反**，写错 80% 表现为"密码是密文/连接失败"。

### 5.2 解密时机与密钥前缀

```text
Config Server 返回响应前：
  扫描所有属性值 → 发现 {cipher} 前缀 → 用密钥解密 → 替换为明文
  ├── 客户端拿到的是明文（正常使用）
  ├── 无密钥/解密失败 → invalid 机制（下节）
  └── 密钥前缀 {cipher:key-id} → 用指定密钥解密（多密钥，见第 7 节）
```

## 6. invalid 前缀：解密失败兜底

### 6.1 机制

```text
解密失败时（密钥错误/缺失/密文损坏）：
  ├── 原属性被移除
  └── 新增 invalid.<key> = <n/a>（防止密文作为密码泄露给客户端）

示例响应：
  "source": {
    "invalid.SharedPassword": "<n/a>",        // 解密失败
    "SharedPassword": "Fill_me_in"             // 低优先级文件里的明文兜底
  }
客户端：读 SharedPassword → 命中低优先级文件的明文（安全降级）
```

### 6.2 关闭与风险

```properties
spring.cloud.config.server.encrypt.prefix-invalid-properties=false
```

> ⚠️ **别关**：关闭后解密失败的属性**原样返回密文**——客户端可能把密文当密码去连接数据库（更糟）；保持默认（invalid 前缀）让"解密失败"显式可见（/actuator/health 或响应排查）。

## 7. 多密钥与密钥轮换

### 7.1 {cipher:key-id} 机制

```yaml
# 指定密钥解密（key-id 对应 TextEncryptorLocator 的命名）
password: '{cipher:legacy-key}682bc583f4641835fa2db009355293665d2647dade3375c0ee201de2a49f7bda'
password2: '{cipher:new-key}AAABBB...'
```

```text
轮换流程（在线轮换）：
  ① 新密钥上线（TextEncryptorLocator 增加 new-key）
  ② 新配置用 {cipher:new-key} 加密
  ③ 旧配置保留 {cipher:legacy-key}（老密钥还能解密）
  ④ 全部迁移完 → 下线老密钥
  ⑤ 轮换期间两种密文并存，客户端无感
```

### 7.2 TextEncryptorLocator 自定义

```java
@Bean
public TextEncryptorLocator myEncryptorLocator() {
    return new TextEncryptorLocator() {
        @Override
        public TextEncryptor locate(String keyId) {
            if ("new-key".equals(keyId)) return new AesBytesEncryptor("new-secret", ...);
            return new AesBytesEncryptor("legacy-secret", ...);
        }
    };
}
```

### 7.3 轮换最佳实践

| 步骤 | 说明 |
|------|------|
| 1. 双密钥并存 | 新旧密钥同时在 locator 注册 |
| 2. 增量迁移 | 新值用新密钥，旧值 {cipher:旧id} 不变 |
| 3. 灰度验证 | 验证新密钥解密正常（/decrypt 端点） |
| 4. 全面切换 | 所有值切新密钥 |
| 5. 下线旧钥 | 确认无 {cipher:legacy} 引用后删除 |

> 💡 密钥管理总纲：**密钥只放 Server（或环境变量/秘钥服务），不进 Git**；定期轮换（合规 90 天/180 天）；Server 密钥泄 = 全部密文可解——Server 本身的安全防护见 [07 篇](07-安全认证与生产运维.md)。
