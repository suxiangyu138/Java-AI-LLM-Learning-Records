## 1. 安全威胁模型

```text
Config Server = 全网的"密码分发中心"（解密后下发明文）
  ├── 威胁 1：配置仓库泄露 → 密文在手（有密钥才能解）→ {cipher} 缓解
  ├── 威胁 2：Server 被非法访问 → 拿到所有明文配置 → 必须认证 + 内网隔离
  ├── 威胁 3：Webhook/monitor 被滥用 → 恶意触发全网刷新 → 必须鉴权
  ├── 威胁 4：密钥泄露 → 一切白搭 → 密钥不进 Git、环境变量/秘钥服务管理
  └── 威胁 5：传输被窃听 → 明文配置在 HTTP 上裸奔 → HTTPS/TLS
```

| 风险 | 缓解手段 |
|------|---------|
| 配置仓库泄露 | {cipher} 密文存储（[06 篇](06-加密解密与密钥管理速查.md)） |
| Server 未授权访问 | Basic Auth / 内网隔离 / TLS |
| monitor 滥用 | Webhook 鉴权（token 头） |
| 密钥泄露 | 密钥环境变量注入 / 秘钥服务（Vault/AWS SM） |
| 传输窃听 | HTTPS（生产强制） |

> 🎯 一句话安全观：**Config Server 是配置界的"根证书"——它的安全等级决定了全网的配置安全等级**，宁可多防不可裸奔。

## 2. 服务端认证：Basic Auth / TLS

### 2.1 Basic Auth（最简单）

```xml
<!-- Server 加 Spring Security -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
```

```yaml
# Server application.yml
spring:
  security:
    user:
      name: config-admin
      password: ${CONFIG_PASSWORD}
```

```text
效果：所有 /{app}/{profile} 与 /encrypt /decrypt 需要认证
客户端配凭证（见第 3 节）
```

### 2.2 TLS（HTTPS）

```yaml
# Server：标准 Boot TLS 配置
server:
  port: 8443
  ssl:
    enabled: true
    key-store: classpath:config-server.p12
    key-store-password: ${TLS_PASSWORD}
    key-store-type: PKCS12
```

```text
客户端配 trust-store（或跳过校验——生产别跳）
生产建议：HTTPS + Basic Auth 双保险（认证防未授权、TLS 防窃听）
```

### 2.3 monitor 端点保护

```yaml
# 方式一：路径级认证（Spring Security）
spring:
  security:
    filter:
      order: 10
# 方式二：自定义过滤器校验 Webhook token（Git 平台自定义 Header）
```

```text
Git 平台 Webhook 配一个 secret token → Config Server 校验该 Header
（GitHub: X-Hub-Signature；GitLab: X-Gitlab-Token）
```

> ⚠️ **常见事故**：Config Server 直挂公网或内网裸奔（无认证）——任何人都能拉全部配置、触发刷新；**至少 Basic Auth + 内网段限制**（防火墙/安全组）。

## 3. 客户端凭证配置

### 3.1 直连认证

```yaml
# 客户端
spring:
  cloud:
    config:
      uri: https://config-server:8443
      username: config-admin
      password: ${CONFIG_PASSWORD}      # 从环境变量/秘钥服务注入
```

### 3.2 discovery 模式凭证（元数据携带）

```yaml
# Config Server 注册到注册中心时带上凭证元数据
spring:
  cloud:
    config:
      server:
        discovery:
          metadata:
            user: config-admin
            password: ${CONFIG_PASSWORD}
```

### 3.3 自定义 Header

```yaml
spring:
  cloud:
    config:
      headers:
        X-Api-Key: ${CONFIG_API_KEY}    # 自定义认证头（网关/内部认证体系）
```

> 💡 客户端凭证**不要写死在配置文件里**（矛盾：保护配置的凭证放在配置里）——用环境变量/K8s Secret/秘钥服务注入。

## 4. 健康检查与监控

### 4.1 Server 健康指示器

```text
Config Server 自带健康检查：
  GET /actuator/health → configServer 子状态
  ├── 检查默认仓库可达性（clone/fetch 成功）
  └── 多仓库配置时：检查所有仓库（fail-fast=false 时可部分失败）

自定义健康检查：
  spring.cloud.config.server.health.repositories.<name>.uri=...  # 指定仓库探测
```

### 4.2 客户端健康信号

| 手段 | 说明 |
|------|------|
| 启动日志 | `Located property source` 出现 = 拉取成功 |
| refresh 返回 | /actuator/refresh 返回变更 key 列表 |
| Bus 消费日志 | RefreshRemoteApplicationEvent 消费日志 |
| 指标 | 拉取耗时/失败次数（Micrometer 自定义埋点） |

> 💡 生产监控组合：**Server 健康检查探活 + 客户端拉取成功埋点 + 刷新事件日志聚合**——配置中心的"三类健康信号"全链路可见。

## 5. 高可用部署形态

### 5.1 单点 vs 高可用

| 维度 | 单 Server | 多 Server 高可用 |
|------|----------|-----------------|
| 架构 | 1 实例 | N 实例（无状态）+ 共享 Git 仓库 |
| 客户端 | 单 URI | 多 URI / discovery |
| 故障影响 | 全挂（客户端启动失败） | 单点故障无感（多 URI 容错） |
| 状态 | Server 本身无状态（状态在 Git） | 每实例本地工作目录（需 force-pull） |

### 5.2 高可用配置清单

```yaml
# Server（每台相同配置）
spring:
  cloud:
    config:
      server:
        git:
          uri: https://github.com/you/config-repo
          force-pull: true            # ★ 本地工作目录强制同步（多实例共享仓库必配）
          clone-on-start: true

# 客户端
spring:
  config:
    import: optional:configserver:http://config-1:8888,http://config-2:8888
  cloud:
    config:
      multiple-uri-strategy: always
      fail-fast: true
      retry:
        max-attempts: 6
```

> ⚠️ **多 Server 的隐藏坑**：每个实例有**独立本地工作目录**——实例 A fetch 了最新、实例 B 还是旧目录 → 客户端请求打到 B 得到旧配置！**force-pull: true 或统一清 basedir**；更稳的方案是 `fetch-interval` 配置为合理缓存 + 定期同步。

### 5.3 部署形态选择

| 形态 | 适用 | 说明 |
|------|------|------|
| 单实例 | 测试/低可用要求 | 最简单 |
| 多实例 + 负载均衡 | 生产 | 无状态水平扩展 |
| discovery 注册 | 弹性伸缩 | 客户端自动发现 |
| K8s | 云原生 | Deployment + 多副本 + 共享 Git 凭证 |

## 6. 性能优化

| 优化点 | 手段 | 效果 |
|--------|------|------|
| fetch 缓存 | `spring.cloud.config.server.git.fetch-interval: 30` | 30s 内不重复 fetch（默认 0=每次 fetch，高并发下 Git 压力大） |
| 启动提速 | clone-on-start: true | 首次请求不阻塞（提前 clone） |
| 多仓库 | 通配符仓库会弱化本地缓存 | 减少仓库数 / 子目录 search-paths |
| 客户端重试 | 重试参数合理（避免启动风暴） | 多实例同时启动别全压 Server |
| 加密开销 | {cipher} 解密在 Server 每次请求都做 | 大量密文 + 高并发 → 关注 CPU；可提前解密预热（无官方缓存，自行评估） |

> ⚠️ 注意：**fetch-interval > 0 意味着配置变更最多延迟 fetch-interval 秒**——动态刷新链路也受它影响（改了配置但 Server 还在缓存期内）。

## 7. AOT 与原生镜像

### 7.1 官方限制（重点）

| 能力 | 原生镜像（AOT）支持 |
|------|:---:|
| Config Data 拉取 | ✅ 支持（4.0.0+） |
| bootstrap 模式 | ❌ 不支持（必须 Config Data） |
| **@RefreshScope 动态刷新** | ❌ **不支持**——官方原话："Refresh scope is not supported with native images... set spring.cloud.refresh.enabled to false" |
| 配置属性名发现 | ⚠️ 需要 AOT 提示（@ConfigurationProperties 自动注册） |

### 7.2 实践要点

```yaml
# 原生镜像客户端
spring:
  cloud:
    refresh:
      enabled: false      # ★ 原生镜像必须关 refresh（否则运行期出错）
  config:
    import: optional:configserver:http://config-server:8888
```

```text
原生镜像约束总结：
  ├── 配置必须在"构建时可解析"（构建期能连上 Config Server）
  ├── Bean 创建影响属性须与运行期一致（AOT 静态化）
  └── 接受"无动态刷新"（原生镜像 + 配置变更 = 重新部署）
```

> 🎯 选型提示：**追求原生镜像启动速度（秒级）的团队，要接受"配置刷新能力缺失"**——动态刷新与原生镜像二选一，或配置变更走"重新发布"流水线（[08 篇](08-生产实践与选型避坑.md) 也提）。
