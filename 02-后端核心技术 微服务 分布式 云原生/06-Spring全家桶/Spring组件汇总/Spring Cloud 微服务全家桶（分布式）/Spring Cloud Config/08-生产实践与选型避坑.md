## 1. 接入清单：哪些配置该进 Config

| 配置类型 | 进 Config？ | 说明 |
|---------|:---:|------|
| 数据源/Redis/MQ 连接配置 | ✅ | 环境差异最大，最该集中 |
| 业务开关/阈值/超时 | ✅ | 动态调整的价值所在（@RefreshScope） |
| 日志级别 | ✅ | 线上调日志不用重启 |
| 消息队列/限流参数 | ✅ | 集中管理 |
| **构建期常量** | ❌ | 编译期就定的别放 |
| **密钥** | ⚠️ | 用 {cipher} 或 Vault（[06 篇](06-加密解密与密钥管理速查.md)） |
| 超大静态数据（白名单表等） | ⚠️ | 数据量级大时考虑数据服务而非配置 |
| 本地开发私有配置 | ❌ | 个人 IDE 配置（.mvn 等）不进共享仓库 |

> 🎯 治理原则：**"环境相关、需要动态调、需要审计"的进 Config；"代码相关、私有、静态"的不进**——配置中心不是垃圾桶，过度集中反而难维护。

## 2. 配置治理规范

| 规范 | 说明 |
|------|------|
| 命名规范 | `{应用}-{环境}.yml`，应用名与 spring.application.name 严格一致 |
| 分组 | 全局共享放 application.yml；应用私有放应用文件 |
| 敏感项 | 一律 {cipher}（或 Vault），明文密码禁入 Git |
| 变更流程 | 走 MR/评审 + 分支管理（label 灰度） |
| 备份 | Git 仓库异地备份（配置 = 基础设施） |
| 文档 | 配置字典（每个 key 的含义/负责人）——团队越大越必要 |

## 3. 坑位表：10 大高频坑

| # | 坑 | 现象 | 解决 |
|---|-----|------|------|
| 1 | **文件名与应用名不匹配** | /order-service/dev 404 | `{spring.application.name}-{profile}.yml` 严格一致 |
| 2 | **Server 工作目录落后** | 改了 Git 拉不到新值 | force-pull: true / 清 basedir / 看响应 version |
| 3 | **bootstrap 模式 encrypt.key 放错** | {cipher} 全部解密失败 | bootstrap 模式下放 bootstrap.properties（[06 篇](06-加密解密与密钥管理速查.md)） |
| 4 | **yaml/properties 引号规则反了** | 密码是密文/连接失败 | yaml 加引号、properties 不加（[06 篇](06-加密解密与密钥管理速查.md) 5.1） |
| 5 | **@RefreshScope 漏标** | 刷了值不变 | 目标 Bean 标注 @RefreshScope |
| 6 | **bus.refresh.enabled 默认 false** | 全网刷新无效果 | 显式开启（[05 篇](05-动态刷新与Bus集成速查.md)） |
| 7 | **bus.id 重复** | 部分实例不刷新 | id = app:port:random |
| 8 | **远程配置里写 import configserver** | 递归拉取/启动异常 | 禁止远程配置再 import configserver |
| 9 | **refresh 未暴露** | 端点 404 | management.endpoints.web.exposure.include: refresh |
| 10 | **连接池等重量 Bean 标 @RefreshScope** | 刷新时连接中断/重建风暴 | 评估重建影响，连接池用动态刷新或重建策略 |

> 💡 排障口诀：**"文件在不在 → Server 新不新 → 信号到没到 → Bean 刷没刷"**——四步定位，每步都有响应/日志可验证。

## 4. 刷新链路五段排查法

| 段 | 验证 | 常用命令/日志 |
|----|------|--------------|
| ① 仓库 | Git push 了吗、分支对吗 | `git log` / `git status` |
| ② Server | 响应 version = 最新 commit？ | `curl /order-service/dev` 看 version 字段 |
| ③ 信号 | 刷新事件发出去了吗 | MQ 队列看 RefreshRemoteApplicationEvent |
| ④ 实例 | 实例收到事件了吗 | 实例日志 RefreshScopeRefreshedEvent / bus-refresh 消费 |
| ⑤ Bean | 重建了吗、值对了吗 | 日志 Refresh scope / 接口返回值 |

```bash
# 一条龙快速验证（示例）
curl http://config-server:8888/order-service/dev | jq '.version'          # ① ② Server 侧
curl -X POST http://order-1:8081/actuator/refresh                         # ③ 单实例验证
curl http://order-1:8081/timeout                                          # ⑤ 业务值验证
```

> 💡 五段排查的黄金法则：**每一段失败都有独立证据**（version 字段/MQ 日志/Bean 重建日志）——不要"猜"哪段坏了，用证据定位。

## 5. vs Nacos：全维度选型

### 5.1 对比表

| 维度 | Spring Cloud Config | Nacos 配置中心 |
|------|--------------------|---------------|
| 出身 | Spring Cloud 官方 | 阿里（SCA） |
| 存储 | **Git 仓库（默认）** | 内嵌存储（MySQL 持久化） |
| 配置变更模型 | 启动拉取 + refresh/Bus 事件 | **长轮询推送（秒级自动生效）** |
| 动态刷新 | 需 refresh 端点/Bus + @RefreshScope | **内置**（监听器 + 自动刷新） |
| 额外组件 | 需要 Bus（全网刷新）+ MQ | **不需要**（内置推送） |
| 版本化/回滚 | ✅ Git 天然版本化 | ✅ 历史版本 + 回滚 |
| 加密 | ✅ {cipher} 体系完善 | ⚠️ 基础（社区方案） |
| 敏感配置 | Vault/AWS SM 复合 | 需自行加密 |
| 命名空间/分组 | profile/label（文件模型） | ✅ 命名空间+分组+Data ID（更直观） |
| 灰度 | label（分支） | ✅ Beta 发布（按 IP/权重） |
| 控制台 | ❌ 无（Git 平台管理） | ✅ 可视化控制台 |
| 生态 | 官方 Cloud（Gateway/Feign 全家桶） | SCA 生态 |
| 监控 | Git/actuator | 控制台内置监控 |
| 学习成本 | 中（文件模型 + 刷新链路） | 低（控制台点几下） |
| 适用 | 官方生态、Git 工作流、强审计 | 阿里生态、要控制台、要秒级推送 |

### 5.2 决策建议

```text
选 Config：
  ├── 用官方 Spring Cloud 全家桶（Config 与 Gateway/Feign 一体）
  ├── 团队 Git 工作流成熟（配置走 MR/评审）
  ├── 需要 {cipher} 加密 + Vault 复合的强安全体系
  └── 能接受"刷新链路"（refresh/Bus）运维成本

选 Nacos：
  ├── 已在 SCA 生态（Nacos 注册中心/Seata 一起用）
  ├── 想要控制台可视化 + 秒级自动推送（省去 Bus/MQ）
  ├── 需要命名空间/分组/灰度发布等治理能力
  └── 国内团队（阿里系文档/社区）

不推荐：同时上两套配置中心（心智负担翻倍）
```

> 🎯 面试结论：**"Config 和 Nacos 怎么选？"**——官方 Cloud 生态选 Config（Git 版本化 + 加密体系是差异化优势），SCA 生态选 Nacos（内置推送 + 控制台 + 秒级生效）；**刷新模型差异是核心**：Config 是"拉 + 事件广播"，Nacos 是"长轮询推送"——想要"改完就生效、零运维"选 Nacos，想要"Git 工作流 + 强加密审计"选 Config。

### 5.3 混合使用的现实

```text
现实场景：很多团队注册中心用 Nacos、配置中心用 Config（或不混用）
  ├── 可行：两者职责独立（注册 vs 配置）
  └── 但配置中心一旦选型，全链路统一（别一半服务用 Nacos 一半用 Config）
```

## 6. 升级路径：4.3.x → 5.0.x

### 6.1 升级必要性判断

| 现状 | 判断 |
|------|------|
| Spring Cloud 2025.0.x（Boot 3.5）+ Config 4.3.x | **建议升级**：Northfields OSS 已于 2026-06-30 结束 |
| Spring Cloud 2024.0.x（Boot 3.4）+ Config 4.2.x | **建议升级**：Moorgate 已 EOL |
| Spring Cloud 2023.0.x（Boot 3.2/3.3）+ Config 4.1.x | 计划升级 |
| Boot 2.7 + Config 3.0.x | 大工程，先规划 Boot 升 4 |

### 6.2 升级 Checklist

```text
□ 1. 整批升级：Boot 3.5→4.x + Cloud 2025.0→2025.1（Server 和 Client 一起升）
□ 2. 依赖核对：starter-config 坐标不变，版本由新 BOM 锁 5.0.x
□ 3. 代码兼容：
     - Jackson 3 迁移（自定义 ObjectMapper 相关）
     - 移除的 deprecated API（升级前 grep @Deprecated）
     - jakarta 命名空间（Boot 4 已是）
□ 4. 配置核对：
     - spring.config.import / spring.cloud.config.* 属性不变（基本零改）
     - bootstrap 模式用户：评估迁 Config Data（原生镜像也依赖它）
□ 5. 回归验证：
     - Server：/order-service/dev JSON 结构、version、解密链路
     - Client：拉取日志、@RefreshScope 刷新、Bus 全网刷新
     - 加密：{cipher} 解密、invalid 机制
□ 6. 运维验证：健康检查、多 Server 容错、监控指标
```

### 6.3 升级风险提示

| 风险 | 说明 |
|------|------|
| 版本错配启动失败 | 2025.1 compatibility verifier 直接拒启动 |
| Jackson 3 影响面 | 主要在 Server 端 JSON 处理；自定义序列化代码需回归 |
| deprecated API 移除 | 老代码用了直接编译失败（可见可改） |
| 5.0.1 兼容修复 | 用 5.0.1+（5.0.4 最新），别停在 5.0.0 |
