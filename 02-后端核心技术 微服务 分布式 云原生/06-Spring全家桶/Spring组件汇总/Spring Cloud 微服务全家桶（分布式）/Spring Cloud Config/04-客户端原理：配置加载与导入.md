## 1. Config Data 加载模型（Boot 2.4+）

### 1.1 一句话本质

```text
Config Client = Spring Boot 配置加载流程里"多挂了一个配置源"
  ├── Spring Boot 启动 → ConfigDataEnvironmentPostProcessor（加载 spring.config.import）
  ├── import 里出现 configserver: → ConfigServerConfigDataLoader 接管
  ├── 发起 HTTP 请求 /{app}/{profile}/{label} → 拿到 propertySources
  └── 远程 propertySources 追加进 Environment 属性源链 → 后续 @Value/@ConfigurationProperties 正常读到
```

### 1.2 与 bootstrap 模式的关键差异

| 维度 | Config Data（Boot 2.4+，默认） | bootstrap（遗留） |
|------|-------------------------------|-------------------|
| 触发方式 | `spring.config.import=configserver:` | `spring.cloud.bootstrap.enabled=true` 或 starter-bootstrap |
| 加载时机 | 与本地配置一起进 ConfigData 流程 | 在**整个应用启动之前**（bootstrap context 先行） |
| 能激活 profile | ✅（两步加载，见下） | ❌（拉完才知 profile，无法反向激活） |
| 属性优先级 | 与本地配置统一按加载顺序排 | bootstrap 属性源特殊置顶 |
| 官方态度 | **推荐** | 遗留，仅迁移期用 |
| AOT/原生镜像 | ✅ 支持 | ❌ 不支持 |

> 🎯 面试必答：**"Config Data 和 bootstrap 什么区别？"**——bootstrap 模式在应用上下文创建**之前**拉配置（能影响 Bean 创建早期行为，但无法根据远程配置激活 profile、不支持原生镜像）；Config Data 把远程配置**纳入标准配置加载流程**（支持两步加载反向激活 profile、支持 AOT），是 Boot 2.4+ 的官方推荐，bootstrap 只留作迁移。

## 2. 两步加载：为什么要请求两次

### 2.1 流程

```text
启动阶段（ConfigData 处理）：
  ① 第一步：用 default profile 请求一次 /{app}/default/{label}
       ├── 目的：拿到"可能激活其他 profile"的属性（如 spring.profiles.active）
       └── 拿到后：本地/远程属性决定激活 profile 集合
  ② 第二步：用激活后的 profile 集合再请求 /{app}/{profiles}/{label}
       └── 结果作为最终远程配置
  → 所以客户端启动时日志里会有"多次请求 Config Server"——正常现象！
```

### 2.2 为什么必须两步

```text
老问题：配置里写了 spring.profiles.active=prd（在远程仓库里）
  ├── 单次拉取：先拉 default → 不知道要激活 prd → 拉错配置
  └── 两步加载：先拉 default 发现 active=prd → 用 prd 再拉一次 → 拉对配置
```

| 能力 | 单次拉取（bootstrap） | 两步加载（Config Data） |
|------|:---:|:---:|
| 远程配置里激活 profile | ❌ | ✅ |
| 请求次数 | 1 | 2（或多 profile 时更多） |
| 排查困惑点 | 无 | "为什么请求两次"（正常） |

> 💡 优化提示：两步加载在 **profile 较多时请求次数翻倍**（每 profile 一次）；4.2.0+ 的 `send-all-labels` 与多 profile 场景配合时注意请求量（[07 篇](07-安全认证与生产运维.md) 性能）。

## 3. spring.config.import 全语法

### 3.1 基本形态

```yaml
spring:
  config:
    import: optional:configserver:http://localhost:8888
```

| 形态 | 含义 |
|------|------|
| `configserver:` | 必须拉取（拉不到 = 启动失败） |
| `optional:configserver:` | 可选（拉不到也能启动，默认 Server 地址 localhost:8888） |
| `configserver:http://host:port` | 内联地址（优先级高于 spring.cloud.config.uri） |
| `optional:configserver:http://host:port` | 组合 |
| 多行（list 形式） | 按顺序导入多个源 |

### 3.2 多配置源导入

```yaml
spring:
  config:
    import:
      - configserver:http://config-1:8888
      - configserver:http://config-2:8888
      - file:./local-extra.yml          # 可混入本地文件源
```

> ⚠️ 注意：**同一个 import 下的多个 configserver 源按顺序处理，后面的覆盖前面**（后加载的 propertySource 优先级更高）；`multiple-uri-strategy` 属性对这种形式**不生效**（那是 spring.cloud.config.uri 多地址的场景）。

### 3.3 import 位置的坑

```text
spring.config.import 的解析顺序与文件位置有关：
  ├── application.yml 里的 import → 常规顺序
  ├── 必须写在"能被 ConfigData 处理"的位置（application.yml 根级，不能放进自定义 profile 文件里才被 import 发现——鸡生蛋问题）
  └── 常见错误：把 import 写进 order-service-dev.yml（远程文件）→ 递归拉取！配置里再 import configserver = 递归
```

> ⚠️ **禁止在远程配置里写 spring.config.import=configserver:**——会形成递归拉取；远程配置里需要"再导入别的源"的场景用 property source 顺序替代。

## 4. 遗留 bootstrap 模式：对比与迁移

### 4.1 开启方式

```xml
<!-- 方式一：加 starter -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bootstrap</artifactId>
</dependency>
<!-- 方式二：属性开启（系统属性/环境变量） -->
<!-- SPRING_CLOUD_BOOTSTRAP_ENABLED=true -->
```

```yaml
# bootstrap.yml（bootstrap 模式的配置入口）
spring:
  application:
    name: order-service
  cloud:
    config:
      uri: http://localhost:8888
      fail-fast: true
```

### 4.2 迁移到 Config Data 的清单

```text
□ 1. bootstrap.yml 里的 spring.cloud.config.* → 移到 application.yml（import + 同键属性）
□ 2. 删掉 spring-cloud-starter-bootstrap 依赖
□ 3. 检查依赖 bootstrap 加载顺序的代码（早期 Bean 初始化依赖配置的）
□ 4. 验证 profile 激活逻辑（两步加载会改变激活时机）
□ 5. 回归：配置拉取、刷新、AOT（如需）
```

> 🎯 何时不迁移：**有代码依赖 bootstrap 先行语义**（如注册中心地址也必须从配置中心来、早期 Filter 需要配置）——这类场景保留 bootstrap 或显式处理，别为了新而新。

## 5. 失败语义：fail-fast / 重试 / 容错

### 5.1 三档失败策略

| 策略 | 配置 | 行为 |
|------|------|------|
| 容错启动（默认） | `optional:configserver:` | 拉不到 → 警告日志，本地配置继续启动 |
| 快速失败 | 去掉 optional | 拉不到 → **启动失败**（生产推荐，防止"无配置裸奔"） |
| 重试后失败 | + spring-retry 依赖 | 按重试策略多次尝试后才失败 |

### 5.2 重试配置

```yaml
# 依赖：spring-retry + spring-boot-starter-aop
spring:
  cloud:
    config:
      retry:
        max-attempts: 6          # 最多 6 次（默认）
        initial-interval: 1000   # 初始间隔 1s
        multiplier: 1.1          # 指数倍率
        max-interval: 2000
        use-random-policy: true  # 随机退避（防多个实例同时重试惊群）
```

> 💡 生产组合拳：**去掉 optional（必拉）+ 配重试（网络抖动可恢复）+ 健康检查（拉取失败暴露到监控）**——启动即有配置，且不因瞬断直接挂掉。

## 6. 发现配置服务器：discovery 模式

### 6.1 通过注册中心找 Config Server

```yaml
spring:
  cloud:
    config:
      discovery:
        enabled: true                 # ★ 从注册中心发现 Server（默认 false）
        service-id: configserver     # Server 在注册中心的服务名
```

```text
流程：客户端启动 → 连注册中心（Eureka/Nacos）→ 找 configserver 实例 → 拉配置
Server 端配合：注册到中心 + metadata 里放凭证：
  spring.cloud.config.server.discovery.metadata = {user: xxx, password: xxx, configPath: /config}
```

### 6.2 直连 vs discovery

| 维度 | 直连（uri） | discovery |
|------|------------|-----------|
| 配置 | spring.cloud.config.uri | discovery.enabled=true |
| 依赖 | 无 | 注册中心可用 |
| 故障转移 | 手动多地址 | 注册中心负载均衡 |
| 适用 | 简单、少实例 | 多 Server 高可用、弹性伸缩 |

> ⚠️ 坑：**discovery 模式下 Server 必须注册到中心且健康检查正常**；Client 启动时若注册中心不可用则拉取失败（此时配了 retry 有用武之地）。

## 7. 多 label 与多 URI

### 7.1 多 label（4.2.0+）

```yaml
spring:
  cloud:
    config:
      label: myfeature,develop        # 逗号分隔多个分支
      send-all-labels: true           # ★ 4.2.0+：一次请求返回所有 label 的配置（要求 Server 4.2.0+）
      # false（默认）：逐个尝试 label，第一个有配置的生效（遗留行为）
```

| 场景 | 用法 |
|------|------|
| 灰度分支 | label: feature-xxx（只有灰度实例配） |
| 蓝绿/回滚 | 切 label 即回滚（不动内容） |
| 多分支合并 | send-all-labels: true（按序合并） |

### 7.2 多 URI（Server 集群）

```yaml
spring:
  cloud:
    config:
      uri: http://config-1:8888,http://config-2:8888
      multiple-uri-strategy: always       # always=全部尝试；connection-timeout-only=仅连接失败才换
```

> 💡 生产高可用标配：**多 Config Server（共享 Git 仓库）+ 客户端多 URI（或 discovery）+ fail-fast + retry**——四件套齐了，配置中心单点故障才真正消除（[07 篇](07-安全认证与生产运维.md) 高可用）。

## 8. 属性源优先级全景

### 8.1 完整优先级（Spring Boot 外部化配置）

```text
高 ←──────────────────────────────────────────────────────────→ 低
命令行参数
Java System Properties / OS 环境变量
JAR 包外 application-{profile}.yml
JAR 包内 application-{profile}.yml
JAR 包外 application.yml
JAR 包内 application.yml
Config Data 导入源（spring.config.import 追加的，含 configserver:）   ← ★ Config 配置在这层
配置文件外的 @PropertySource（如果配置了）
```

### 8.2 关键结论

| 结论 | 说明 |
|------|------|
| 远程覆盖本地 | Config 拉取的配置优先级高于本地 application.yml（同键） |
| 更具体覆盖更通用 | 远程内部：order-service-dev 覆盖 order-service；dev 覆盖 default |
| 命令行仍最高 | `--server.port=9000` 可以覆盖远程配置（排障常用） |
| 环境变量高于文件 | OS env 覆盖 application.yml（生产常用来注入凭证） |

> 🎯 面试必答：**"配置优先级怎么排？"**——背口诀"**命令 > 系统属性/环境变量 > 外置文件 > 内置文件 > Config 远程**"；再补一句：Config 远程配置内部按"应用+环境最具体者优先"，所以**"远程 > 本地"是默认，但不是绝对**（被环境变量覆盖时远程不生效）。
