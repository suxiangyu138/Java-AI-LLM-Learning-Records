## 1. 集成地图

```text
        HTTP / SSE / WebSocket 请求
                │
        ┌───────▼────────┐
        │   Netty 服务器  │（少量线程，event loop）
        └───────┬────────┘
                ▼
        ┌──────────────────────────────┐
        │   Spring WebFlux（SF 7.0.x） │
        │   注解式 / RouterFunction    │
        │   WebFilter → Controller →  │
        │   @ControllerAdvice 异常     │
        └───────┬──────────┬──────────┘
                │          │
        R2DBC / Mongo-reactive  WebClient（下游服务）
        （响应式数据库）        （网关扇出 / 聚合）
                │
        Micrometer 指标 + Tracing + WebTestClient 测试
```

## 2. WebFlux vs MVC 选型（2026 版）

| 维度 | WebFlux（响应式） | MVC + 虚拟线程（SF 7 推荐组合） |
|------|------------------|-------------------------------|
| 线程模型 | 少量 event loop 线程非阻塞 | 每请求一个虚拟线程（阻塞便宜） |
| 高并发能力 | 强（背压 + 少量线程） | 强（虚拟线程海量） |
| 代码风格 | 操作符链（学习成本高） | 传统命令式（熟悉） |
| 全链路 | 必须全响应式（R2DBC…） | 阻塞栈任意（JDBC 随便用） |
| 流式场景（SSE/大流） | ✅ 原生背压 | 一般（可做但不优） |
| 网关场景（扇出聚合） | ✅ 并发扇出 | 可做（虚拟线程并发） |
| 调试/排障 | 栈追踪复杂 | 传统 |
| 适合 | 全响应式技术栈、流式、网关 | **大多数业务系统** |

> 🎯 **2026 定论**：**默认选 MVC + 虚拟线程；只有"全栈已响应式"或"流式长连接"才选 WebFlux**——"WebFlux 更快"是过时认知，两者并发能力相当，差异在技术栈适配。

## 3. 与生态的集成

| 集成对象 | 方式 | 要点 |
|---------|------|------|
| R2DBC | 响应式 DAO 返回 Mono/Flux | 端到端非阻塞（JDBC 在 WebFlux 是反模式） |
| 响应式 MongoDB/Redis | starter 响应式变体 | 全响应式链路 |
| Spring Cloud Gateway | 基于 WebFlux 构建 | 路由/过滤器全是响应式 |
| RSocket | 响应式通信协议 | req-stream 天然背压 |
| Kotlin 协程 | suspend 函数 / coRouter | SF 7 结构化并发增强 |
| Spring Security reactive | WebFilter 式安全链 | 认证/授权响应式版本 |
| 消息（Kafka reactive） | reactor-kafka 消费 | 事件驱动 WebFlux 服务 |
| Micrometer / Tracing | 自动观测 | 响应式链路可观测 |
| 虚拟线程 | ReactiveAdapterRegistry（SF 7） | 响应式/命令式混合边界 |

> 🎯 集成铁律：**WebFlux 项目"要么全响应式，要么明确边界"**——混入 JDBC/同步 Redis 的链必须用 `subscribeOn(boundedElastic)` 隔离；端到端响应式才是 WebFlux 的价值所在。

## 4. 高频问题速查

| 问题 | 根因 | 处理 |
|------|------|------|
| 接口不响应/卡死 | 链内阻塞调用（JDBC、block()）占住 event loop | 换 R2DBC 或 subscribeOn(boundedElastic) |
| `block()` 抛异常 | 在非阻塞线程上阻塞 | 去掉 block；用响应式组合（zip/switchIfEmpty） |
| `DataBufferLimitException` | 超过 codec 内存上限 | 调 spring.codec.max-in-memory-size |
| 返回 Flux 但响应一次性 JSON 数组 | 忘记 produces 流式类型 | 加 `produces = APPLICATION_NDJSON_VALUE` 或 SSE |
| 异常被吞 | 链内异常没走 error 通道 | doOnError / @ControllerAdvice 接 WebExchangeBindException |
| Context 丢失 | 跨线程/WebFilter 未传递 | 用 ReactiveContext 传播 / WebFilter 内 ctx 传递 |
| 上传超过 1MB 报错 | multipart 默认上限 | 调 spring.webflux.multipart.* |
| WebSocket 报错 | SF 7 移除非响应式 handler | 改用响应式 WebSocketHandler |
| 与 MVC 并存启动异常 | 同时引了两个 starter | 二选一 |
| 背压溢出 | 下游消费慢 | onBackpressureBuffer/Drop + limitRate |
| 响应式 DB 报"阻塞"错误 | R2DBC 驱动里跑阻塞代码 | 检查 DAO 实现与事务边界 |

## 5. 排障流程

```text
① 线程层：接口卡死？看线程名（Reactor-http-* 上做阻塞 = 反模式）
② 数据层：数据到了吗？（Flux.log() / doOnNext 打点，确认链在执行）
③ 响应层：返回类型对吗？（Mono 空 → 404 需 defaultIfEmpty；Flux 需流式 produces）
④ 异常层：错误去哪了？（@ControllerAdvice / WebExceptionHandler 是否覆盖）
⑤ 观测层：线上看指标与 Tracing（耗时分布、背压丢弃计数）
```

> 💡 排障三利器：**线程名（Reactor-http-*）、Flux.log()（信号明细）、WebTestClient（本地复现）**——与 Reactor 卡片同套方法论，WebFlux 侧多查"返回类型与 produces"。

> 🎯 **核心要点**：集成地图一句话 = "Netty 少量线程 + 全响应式链路 + 背压"；2026 选型定论 = "MVC+虚拟线程是默认，WebFlux 留给全响应式与流式"；排障先看线程再查数据最后看异常。深挖见 [官方参考文档](https://docs.spring.io/spring-framework/reference/web/webflux.html)。
