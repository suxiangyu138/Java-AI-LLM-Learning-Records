## 1. 三种注入方式与选择

### 1.1 三种方式对比

| 方式 | 写法 | 时机 | 优劣 |
|------|------|------|------|
| 构造器 | `public UserService(OrderService os)` | 实例化时 | **推荐**：不可变、必填、无循环依赖隐患 |
| Setter | `@Autowired setOrderService(...)` | 属性填充时 | 可选依赖、可变 |
| 字段 | `@Autowired OrderService os` | 属性填充时 | 简洁但难测试、不推荐生产 |

```java
// Spring 官方推荐：构造器注入（必填依赖）
@Service
public class UserService {
    private final OrderService orderService;   // final 保证不可变

    public UserService(OrderService orderService) {
        this.orderService = orderService;
    }
}

// 老代码常见：字段注入（测试时需反射/构造器辅助）
@Service
public class UserService {
    @Autowired
    private OrderService orderService;         // 不便测试、final 不可用
}
```

> 🎯 选型结论：**必填依赖 → 构造器（final + 不可变）；可选依赖 → Setter；字段注入仅限快速原型**。Spring 官方文档推荐构造器注入，Spring Boot 4 的构造函数参数不再需要 @Autowired（自动推断）。

### 1.2 构造器自动推断（Spring 4.3+）

```java
// 4.3+ 单构造器自动推断：无需 @Autowired
@Service
public class UserService {
    public UserService(OrderService os) { ... }   // 容器自动用该构造器
}
// 多构造器时必须显式标注一个 @Autowired
```

## 2. @Autowired 处理核心：AutowiredAnnotationBeanPostProcessor

### 2.1 处理时机（BeanPostProcessor 链）

```text
doCreateBean → populateBean（属性填充）
    ↓
applyMergedBeanDefinitionPostProcessors → AutowiredAnnotationBeanPostProcessor
    ↓
① postProcessProperties 收集注入点（字段/方法/构造器）
② 逐个解析依赖并注入（resolveDependency → doResolveDependency）
```

### 2.2 注入点收集（postProcessProperties）

```java
// AutowiredAnnotationBeanPostProcessor 核心逻辑（6.x/7.x 一致）
public PropertyValues postProcessProperties(PropertyValues pvs, Object bean, String beanName) {
    InjectionMetadata metadata = findAutowiringMetadata(beanName, bean.getClass(), pvs);
    metadata.inject(bean, beanName, pvs);        // 执行注入
    return pvs;
}
// 收集哪些？@Autowired / @Value / 带 @Autowired 的构造器与方法
// 缓存：InjectionMetadata 按类缓存（每个类只解析一次）
```

### 2.3 注入方式选择（resolveDependency）

```text
doResolveDependency 的决策顺序：
  ① 先处理 @Value（占位符解析 + 类型转换）
  ② 处理类型匹配（requiredType）
     - 单实例 → getBean
     - 集合（List/Map）→ 收集全部该类型
     - Optional → 存在性包装
     - ObjectProvider → 延迟获取
  ③ 多候选时的选择：
     - @Primary 优先
     - @Qualifier / @Qualifiers 限定
     - 泛型参数精确匹配（7.0 增强）
     - 名称回退：字段名/参数名匹配 bean 名
     - 仍未命中 → NoUniqueBeanDefinitionException
```

## 3. 自动装配的查找与解析

### 3.1 类型查找底层

```java
// 类型 → bean 候选（ListableBeanFactory.getBeansOfType）
// DefaultListableBeanFactory 内部：
//   · 遍历 beanDefinitionNames
//   · 按类型匹配 BeanDefinition 或工厂方法返回类型
//   · 缓存：getType 结果按 name 缓存，冻结配置后可提速
```

### 3.2 候选选择优先级（面试必答）

```text
多候选解析顺序：
  ① 依赖上标注 @Primary 的 bean → 直接命中
  ② 依赖上标注 @Qualifier("xxx") → 按限定名命中
  ③ 泛型匹配：如 List<Payment> 注入 payment 接口多实现
     → 7.0 起按泛型参数精确匹配（无需 @Qualifier）
  ④ 名称回退：字段名（userService）== bean 名 → 命中
  ⑤ 都不满足 → NoUniqueBeanDefinitionException 报错
```

```java
// @Primary 示例：默认支付实现
@Component
@Primary
public class WechatPay implements Payment { }

// @Qualifier 示例：指定实现
@Service
public class OrderService {
    @Autowired
    @Qualifier("alipay")
    private Payment payment;
}

// Spring 7.0 泛型精确匹配：无需 @Qualifier
@Autowired
private Payment<AliPay> payment;   // 7.0 起按泛型参数精确匹配
```

## 4. 泛型注入与 @Qualifier

### 4.1 泛型注入（6.x 基础 + 7.0 增强）

```java
// 6.x：接口泛型化，多实现时默认按泛型匹配（ResolvableType）
public interface Converter<T> { T convert(String s); }

@Component public class UserConverter implements Converter<User> { }
@Component public class OrderConverter implements Converter<Order> { }

// 6.x 已支持按泛型注入：
@Autowired
private Converter<User> userConverter;      // 匹配 UserConverter

// 7.0 增强：同一泛型类型多个 bean 时按参数精确匹配，
// 减少 @Qualifier 依赖（修复 6.x 泛型歧义）
```

### 4.2 ResolvableType（泛型解析的底层）

```java
// 泛型信息的运行时获取依赖 ResolvableType（Spring 泛型抽象）
ResolvableType type = ResolvableType.forField(field);
Class<?> generic = type.getGeneric(0).resolve();   // 拿到 T 的实际类型
// AutowiredAnnotationBeanPostProcessor 用它做泛型匹配
```

## 5. 构造器注入的循环依赖问题

### 5.1 为什么构造器注入不能解决循环依赖

```text
循环依赖解决的前提：三级缓存提前暴露【原始实例】
字段/Setter 注入：先创建原始实例（可提前暴露）→ 再填充
构造器注入：创建实例本身就需要依赖 → 无法提前暴露
  → A 的构造需要 B、B 的构造需要 A → 死锁 → BeanCurrentlyInCreationException

结论：
  · 字段/Setter 循环依赖：容器可解决（三级缓存）
  · 构造器循环依赖：容器解决不了（报错）
  · 最佳实践：设计上避免循环依赖（拆服务/事件解耦）
```

> 🎯 面试必答：**「为什么推荐构造器注入但循环依赖又解决不了？」**——推荐构造器是因为「必填 + 不可变 + 无隐藏依赖」；若出现构造器循环依赖，正确的做法是**重构代码消除环**（提取依赖/事件驱动），而不是退回字段注入掩盖问题。

## 6. @Value 与类型转换

### 6.1 @Value 的处理链

```text
@Value("${app.name:default}") String name;
处理（AutowiredAnnotationBeanPostProcessor 内）：
  ① 占位符解析：PropertySourcesPlaceholderConfigurer
     （${} 从 Environment/PropertySource 取，含默认值语法 :default）
  ② SpEL 求值（#{} 表达式）
  ③ 类型转换：ConversionService（String → 目标类型）
```

### 6.2 常见写法

```java
@Value("${server.port:8080}")          // 配置 + 默认值
@Value("#{systemProperties['os.name']}")  // SpEL
@Value("classpath:app.yml")            // 资源路径
@Value("${app.list:1,2,3}")            // 逗号分隔（需 converter）
```

> ⚠️ 注意：@Value 的解析依赖 PropertySourcesPlaceholderConfigurer（XML 时代）或 Spring Boot 自动注册的配置处理器；纯注解容器中 Boot 场景无需手动配置。

## 7. 注入失效的经典场景

| 场景 | 为什么失效 | 修正 |
|------|------|------|
| `new UserService()` | 脱离容器：注入点是容器后置处理器处理的 | 交给容器管理（@Service/@Bean） |
| static 字段 @Autowired | 静态字段不属于实例，后置处理器不处理 | 用构造器/非静态 + 静态访问器 |
| 工具类直接 @Autowired | 同上 | 静态方法拿容器：实现 ApplicationContextAware 或 @PostConstruct 赋值 |
| 过滤器/拦截器里注入 | 生命周期早于 Spring 容器 | 走 WebApplicationContext 或 Bean 注册 |
| 泛型多实现注入报歧义 | 多候选无 Primary/Qualifier | 加 @Primary 或 @Qualifier（7.0 泛型精确匹配） |
| @Async 方法内 self 调用 | 自调用不走代理 | 注入自身/拆 bean（见 05 篇 6.2） |

```java
// 静态工具类拿 bean 的标准姿势（避免 @Autowired static 失效）
@Component
public class SpringContextHolder implements ApplicationContextAware {
    private static ApplicationContext ctx;

    @Override
    public void setApplicationContext(ApplicationContext applicationContext) {
        ctx = applicationContext;
    }

    public static <T> T getBean(Class<T> clazz) {
        return ctx.getBean(clazz);
    }
}
```

> 🎯 **核心要点**：DI 底层 = **AutowiredAnnotationBeanPostProcessor 在 populateBean 阶段收集注入点 → doResolveDependency 按「Primary → Qualifier → 泛型（7.0 精确）→ 名称」解析候选 → 注入**。面试三连问：为什么推荐构造器注入（必填+不可变）、构造器循环依赖为什么死（无法提前暴露）、@Autowired 为什么失效（脱离容器/静态字段）。Spring 7.0 的泛型注入改进是 2026 新考点：同泛型多 bean 精确匹配，减少 @Qualifier。
