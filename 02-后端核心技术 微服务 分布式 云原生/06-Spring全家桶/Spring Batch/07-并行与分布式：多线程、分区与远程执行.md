## 1. 扩展阶梯：从单线程到远程执行

| 层级 | 手段 | 重启能力 | 复杂度 | 适用量级 |
|------|------|---------|--------|---------|
| 0 | 单线程 Step | ✅ 完整 | 最低 | 默认起点 |
| 1 | 多线程 Step（taskExecutor） | ❌ 丢失（并发提交无法精确断点） | 低 | 单 JVM 内提速 |
| 2 | 本地分区（PartitionStep） | ✅ 按分区粒度 | 中 | 单 JVM 多线程 + 分区续跑 |
| 3 | 远程分区（Remote Partitioning） | ✅ 共享 JobRepository | 高 | 千万~亿级，IO 瓶颈 |
| 4 | 远程 Chunking（Remote Chunking） | ✅ 共享 JobRepository | 高 | 亿级，处理（CPU）瓶颈 |

> 💡 官方反复强调的顺序：**先确认单线程 + commit-interval + 批量写已经榨干**，再上多线程，最后才考虑跨 JVM 方案——分布式带来的基础设施成本（消息中间件、共享元数据库）不是为十万级数据准备的。

## 2. 多线程 Step（Thread-Safe 陷阱）

```java
return new StepBuilder("import", jobRepository)
        .<Order, Order>chunk(500)
        .transactionManager(txManager)
        .reader(reader)                       // ⚠️ 必须线程安全
        .processor(processor)                 // 需无状态
        .writer(writer)                       // 每次 write 独立事务
        .taskExecutor(threadPoolTaskExecutor) // 并行度 = 池大小
        .build();
```

**三大陷阱**：

1. **Reader 线程安全**：JdbcCursorItemReader 等持有连接/游标的 reader 无法安全共享——官方方案：
   - 使用线程安全的 reader（JdbcPagingItemReader 每线程独立查页）；
   - 或 `SynchronizedItemStreamReader` 包装（串行化 read，仅并发处理/写入）；
   - 或每个线程独立 reader 实例（配合 ExecutionContext 各算各的）。
2. **重启能力丢失**：多个线程的 chunk 提交顺序不定，元数据无法还原"全局断点"——**多线程 Step 失败后只能整步重跑**（生产上常配合"业务侧幂等"）。
3. **事务与步进状态**：多线程共享一个 StepExecution，计数器并发更新在 6.0 已修复线程安全问题（StepContribution 计数器），但 `@StepScope` 组件的代理仍按线程切换上下文。

> ⚠️ 6.0 变化：旧 API 的 `throttleLimit` 已被移除——6.0 以**有界队列 + 生产者-消费者模型**控制吞吐（见第 6 节），不需要再调 throttle。

## 3. 本地分区 Partitioning

分区的核心思想：**把数据集切成 N 个分片，每个分片由一个独立 Step（子执行）处理**，子执行各自有完整的事务与重启记录。

### 3.1 三个角色

| 角色 | 接口/类 | 职责 |
|------|---------|------|
| Partitioner | `Partitioner.partition(int gridSize)` | 把数据集描述为 `Map<String, ExecutionContext>`（分区名 → 分片参数，如 id 区间） |
| PartitionHandler | `TaskExecutorPartitionHandler` | 用线程池执行各分片子 Step |
| StepExecutionAggregator | `DefaultStepExecutionAggregator` | 汇总各分片结果到父 StepExecution |

### 3.2 示例：按 ID 区间分区

```java
@Bean
Partitioner orderRangePartitioner() {
    return gridSize -> {
        Map<String, ExecutionContext> partitions = new HashMap<>();
        for (int i = 0; i < gridSize; i++) {
            ExecutionContext ctx = new ExecutionContext();
            ctx.putLong("min.id", i * 1_000_000L + 1);   // 每个分片传自己的区间
            ctx.putLong("max.id", (i + 1) * 1_000_000L);
            partitions.put("partition" + i, ctx);
        }
        return partitions;
    };
}

@Bean
Step masterStep(JobRepository jobRepository, TaskExecutorPartitionHandler handler,
                Step workerStep) {
    return new StepBuilder("master", jobRepository)
            .partitioner("worker", orderRangePartitioner())  // 分区名 + 分区器
            .partitionHandler(handler)
            .build();
}

@Bean
TaskExecutorPartitionHandler partitionHandler(Step workerStep,
                                              TaskExecutor taskExecutor) {
    TaskExecutorPartitionHandler handler = new TaskExecutorPartitionHandler();
    handler.setStep(workerStep);
    handler.setTaskExecutor(taskExecutor);
    handler.setGridSize(8);                    // 分区数
    return handler;
}

// 子 Step：读分片参数（@StepScope + jobParameters 之外的 ExecutionContext 用 stepExecution 注入）
@Bean
@StepScope
JdbcPagingItemReader<Order> workerReader(
        @Value("#{stepExecution.executionContext.getLong('min.id')}") Long minId,
        @Value("#{stepExecution.executionContext.getLong('max.id')}") Long maxId) {
    return new JdbcPagingItemReaderBuilder<Order>()
            .name("workerReader")
            .dataSource(dataSource)
            .selectClause("SELECT * FROM t_order")
            .fromClause("FROM t_order")
            .whereClause("WHERE id BETWEEN :minId AND :maxId")
            .parameterValues(Map.of("minId", minId, "maxId", maxId))
            .sortKeys(Map.of("id", Order.ASCENDING))
            .pageSize(1000)
            .build();
}
```

**本地分区的价值**：父 Step 的元数据记录每个分区子执行的成败——**失败时只需重跑失败的分片**（重启能力按分区保留），这是它优于"裸多线程 Step"的决定性理由。

## 4. 远程分区 Remote Partitioning

把分区子执行**跨 JVM 分发**到 worker 节点：master 只把"分片范围"（轻量 ExecutionContext）发到消息通道，worker 各自完整执行一个 Step。

### 4.1 架构与组件

```text
Manager（master JVM）                          Worker（worker JVM）
Partitioner → MessageChannelPartitionHandler   StepExecutionRequestHandler（@MessageEndpoint）
    │                │                                │
    │        发送 StepExecutionRequest              接收请求
    │        （仅分片参数，数据不过网）          通过 StepLocator 找到 Step
    │                │                        （BeanFactoryStepLocator）执行
    └── 汇总：reply-channel 或 JobRepository 轮询      │
                      共享 JobRepository（状态/结果/重启）
```

### 4.2 关键配置

```java
// Manager 侧
@Bean
MessageChannelPartitionHandler partitionHandler(JobExplorer jobExplorer,
                                                MessageChannel replyChannel) {
    MessageChannelPartitionHandler handler = new MessageChannelPartitionHandler();
    handler.setStepName("worker");
    handler.setGridSize(8);
    handler.setJobExplorer(jobExplorer);      // 轮询模式需要 JobExplorer 查完成状态
    handler.setMessagingTemplate(new MessagingTemplate(replyChannel));
    return handler;
}
// 两种完成判定模式：
//   1) reply-channel 模式：worker 回执聚合（receiveTimeout 可配）
//   2) JobRepository 轮询模式：轮询元数据判定分区完成（6.0 起 MessageChannelPartitionHandler
//      可与任意 JobRepository 实现配合——此前要求 JDBC）

// Worker 侧
@Bean
StepExecutionRequestHandler stepExecutionRequestHandler(JobExplorer jobExplorer,
                                                        StepLocator stepLocator) {
    StepExecutionRequestHandler handler = new StepExecutionRequestHandler();
    handler.setJobExplorer(jobExplorer);
    handler.setStepLocator(stepLocator);      // BeanFactoryStepLocator：按名称找 Step Bean
    return handler;
}
```

### 4.3 硬性约束

- **Manager 与 Worker 必须共享同一个 JobRepository**（通常为关系库）——状态协调、重启、监控都靠它；**ResourcelessJobRepository 不能用于远程执行**；
- 传输通道用 Spring Integration：内存 QueueChannel（同 JVM 演练）、JMS、AMQP（RabbitMQ）、Kafka 均可；
- 网络负载低（只传分片范围），适合 **IO 瓶颈**（读/写慢）的场景。

## 5. 远程 Chunking Remote Chunking

反过来：**master 负责读数据，把每个 chunk 的 item 数据整体发给 worker**，worker 处理（+可选写）。

```java
// Manager 侧：6.0 提供新构建器简化配置
RemoteChunkingManagerStepBuilderFactory managerStepFactory; // 6.0 新增
Step managerStep = managerStepFactory.get("managerStep")
        .<Order, Order>chunk(100)
        .reader(reader)                    // master 读
        .outputChannel(requestsChannel)    // chunk 数据发往 workers
        .inputChannel(repliesChannel)
        .build();

// Worker 侧
RemoteChunkingWorkerBuilder workerBuilder; // 6.0 新增
Step workerStep = workerBuilder.get("workerStep")
        .inputChannel(requestsChannel)
        .outputChannel(repliesChannel)
        .<Order, Order>chunk(100)
        .processor(processor)              // worker 处理
        .writer(writer)                    // 可在 worker 写库
        .build();
```

对比结论（面试高频）：

| 维度 | 远程分区 | 远程 Chunking |
|------|---------|--------------|
| 过网数据 | 只有分片范围（极小） | **全部 item 数据**（大） |
| 谁读数据 | worker 各自读 | 只有 master 读 |
| 瓶颈适配 | IO 瓶颈（读写慢） | 处理瓶颈（processor 重） |
| 网络成本 | 低 | 高 |
| 6.0 组件 | MessageChannelPartitionHandler / StepExecutionRequestHandler | RemoteChunkingManagerStepBuilderFactory / RemoteChunkingWorkerBuilder（替代旧 ChunkHandler → 已改名 ChunkRequestHandler） |

## 6. 6.0 新并发模型：生产者-消费者与背压

6.0 把 Chunk 步的并发从"并行迭代"改为**生产者-消费者模型**：

- 生产者线程执行 read/process，消费者线程执行 write，中间隔一个**有界队列**；
- 队列有界 = 天然**背压**：消费者慢时生产者自动阻塞，不会无限堆积内存；
- 这正是 `BlockingQueueItemReader` / `BlockingQueueItemWriter`（5.2 引入）的用武之地——手工搭建"流水线"时用它们对接；
- 支持 **SEDA 风格**：用 Spring Integration MessageChannel 连接多个处理阶段，每个阶段独立线程池，阶段间有界队列削峰。

```java
// 手工生产者-消费者骨架（5.2+/6.0）
BlockingQueueItemReader<Order> queueReader = new BlockingQueueItemReader<>(queue, 10_000);
// 生产者线程往 queue 填数据，chunk 步从 queueReader 消费
```

## 7. 虚拟线程与选型总结

- **虚拟线程（JDK 21+）**：Boot 4 / Batch 6 可把 `TaskExecutor` 配成虚拟线程执行器；对 **IO 密集**（网络调用、慢 SQL 等待）有效，对 CPU 密集无帮助（虚拟线程不增加计算核心）；
- 与多线程 Step 一样，虚拟线程并行同样**丢失重启粒度**——追求可重启的并行优先分区模型；
- 远程执行 + 虚拟线程可组合：worker 内部用虚拟线程池。

**选型检查清单**：

```text
数据量 < 百万 & 单次运行分钟级     → 单线程 + commit-interval 调优
单 JVM 多核 & 可接受整步重跑        → 多线程 Step（reader 线程安全！）
单 JVM & 需要按分区续跑             → 本地分区
多 JVM & IO 瓶颈 & 已有消息中间件    → 远程分区
多 JVM & 处理瓶颈 & 网络带宽充足     → 远程 Chunking
```

---

> 🎯 **核心要点**：扩展按阶梯爬——多线程 Step 快但丢重启能力；分区（本地/远程）保留按分片的重启能力，本地分区把子执行记录在元数据；远程分区只传范围（IO 型），远程 Chunking 传数据（处理型），两者必须共享 JobRepository；6.0 的并发内核改为"有界队列 + 生产者-消费者"实现背压，`throttleLimit` 已成历史。
