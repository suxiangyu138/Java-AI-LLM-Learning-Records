## 1. 批处理的定义与适用场景

Spring Batch 面向**离线、大数据量、可重启**的批处理作业，其设计目标（也是它与"for 循环 + 事务"自研方案的差异）可以归纳为：

| 设计支柱 | 具体体现 |
|---------|---------|
| 可重启 | JobInstance 用参数定位业务身份，执行中断后可"续跑"而非"重跑" |
| 事务边界 | Chunk 模型将读写封装为"读一批 → 处理 → 一次提交"，失败只回滚当前块 |
| 声明式容错 | Skip / Retry / 忽略错误码，无需在业务代码中写 try-catch 控制流 |
| 元数据审计 | JobRepository 记录每次运行的完整轨迹，可监控、可对账 |
| 标准抽象 | ItemReader / ItemProcessor / ItemWriter 三接口，读写实现与业务解耦 |

**适用边界**（与消息队列、Spring Task 的选型）：

| 场景 | 工具 | 理由 |
|------|------|------|
| 千万级历史数据迁移 / 日终结算 / 报表汇总 | Spring Batch | 大数据量 + 可重跑 + 审计要求 |
| 在线异步削峰 / 即时消费 | 消息队列（Kafka/RabbitMQ） | 低延迟、事件驱动 |
| 轻量定时任务（清理、缓存刷新） | Spring Task | 数据量小、无需元数据 |
| 大数据离线计算（ETL 重型转换） | Spark / Flink | 超出单 JVM 内存，需分布式计算引擎 |
| 实时流式处理 | Flink / Kafka Streams | 毫秒级窗口计算 |

> 💡 大厂面试高频结论：**Spring Batch 不是分布式计算框架**，它解决的是"单 JVM 内的健壮批处理"，跨 JVM 扩展靠的是分区/远程执行（见模块 07），而不是像 Spark 那样的数据分片计算模型。

## 2. 领域对象全景

```text
Job 定义（配置类，构建期）
 │  由 JobBuilder 构建：name + 若干 Step + 流程控制
 │
 ├── Step 定义（最小执行单元）
 │   ├── TaskletStep：执行一段 Tasklet 逻辑
 │   ├── Chunk 步：ItemReader → ItemProcessor → ItemWriter 循环
 │   ├── PartitionStep：分片并行执行子步骤
 │   ├── FlowStep / JobStep：组合其他 Flow / Job
 │   └── （6.0 新增 StoppableStep 语义：任意 Step 可响应外部停止）
 │
 └── 运行时对象（运行期，持久化到 JobRepository）
     ├── JobInstance：业务身份（Job 名 + JobParameters 的哈希 JOB_KEY）
     ├── JobExecution：一次运行（1 个 Instance 可有 N 次 Execution）
     └── StepExecution：每次运行中每个 Step 的一次执行（1:1 与 JobExecution 关联）
```

### 2.1 三者关系：身份 vs 运行

| 对象 | 一句话定位 | 何时创建 | 数量关系 |
|------|-----------|---------|---------|
| JobInstance | "同一次业务任务" | 首次以某组参数启动时创建；参数不同则新建 | 1 : N JobExecution |
| JobExecution | "一次实际运行" | 每次启动（含重启）都新建 | N : M StepExecution |
| StepExecution | "一次运行中的一个 Step" | 每次 JobExecution 中每 Step 创建 | 1 : 1（按 Step 名） |

关键规则：**JobInstance 由 `(JOB_NAME, JOB_KEY)` 唯一确定**，`JOB_KEY` 是 JobParameters 的序列化哈希。所以：

- 同参数重启 → 属于同一 Instance，框架知道"这次是续跑"；
- 换参数（如换日期）启动 → 新 Instance，独立运行；
- `JOB_EXECUTION` 表记录了每个 Instance 的所有运行历史（首次、失败、重启…）。

> ⚠️ **6.0 数据兼容警告**：JobParameters 的序列化格式在 6.0 中发生了变化（JobParameter 变为 record），**5.x 中 FAILED 状态且未重启完成的实例无法用 6.0 续跑**——迁移前必须把失败的 v5 实例重启到成功或 abandon 掉，否则启动会报参数不兼容。

### 2.2 StepExecution 的计数器

StepExecution 上记录了批处理最重要的审计字段（也一一对应 `BATCH_STEP_EXECUTION` 表的列）：

| 计数器 | 含义 | 典型用途 |
|--------|------|---------|
| READ_COUNT / WRITE_COUNT | 成功读 / 写条数 | 对账、进度 |
| COMMIT_COUNT | 已提交的事务块数 | 进度估算 |
| FILTER_COUNT | 被 Processor 返回 null 过滤的条数 | 数据质量 |
| READ_SKIP_COUNT / PROCESS_SKIP_COUNT / WRITE_SKIP_COUNT | 三类跳过计数 | 容错审计（模块 06） |
| ROLLBACK_COUNT | 回滚次数 | 故障定位 |

## 3. JobParameters 与 ExecutionContext：参数与状态

### 3.1 JobParameters（6.0 变为 record）

JobParameters 是启动 Job 时传入的参数集合，**它的作用是定义 JobInstance 的身份**，而不是跨步骤传递状态（那是 ExecutionContext 的职责）。

6.0 重构（对应 5.x 对比）：

| 维度 | 5.x | 6.0 |
|------|-----|-----|
| JobParameter | 普通类，含 `getValue()` 类型判断 | **record**，封装参数名 + 类型化值（STRING/LONG/DOUBLE/DATE，6.0.2 新增 ZonedDateTime/OffsetDateTime 支持） |
| JobParameters 容器 | `Map<String, JobParameter>` | **`Set<JobParameter>`** |
| 参数不可变性 | 可变 | 构造后不可变（配合领域对象整体不可变） |

```java
// 6.0 构建 JobParameters 的典型方式（JobParametersBuilder 仍可用）
JobParameters params = new JobParametersBuilder()
        .addString("input.file", "s3://bucket/20260807/orders.csv")
        .addLocalDateTime("run.date", LocalDateTime.now())
        .toJobParameters();
```

> ⚠️ **6.0 行为变更**：`JobParametersIncrementer` 与 Job 绑定后，**用户显式传入的参数会被忽略（仅打印 warning）**——框架按 incrementer 计算下一组参数，避免参数与实例身份冲突。

### 3.2 ExecutionContext：真正的状态传递

ExecutionContext 是 key-value 存储，用于在**同一 Step 的多次 chunk 间**、**Step 之间**、**重启前后**传递状态。它是"续跑"能力的技术载体：

| 场景 | 用法 |
|------|------|
| 断点续跑 | 把"已处理到第 N 行 / 游标位置 / 分批页码"存入 ExecutionContext，重启时读出继续 |
| Step 间传递 | `StepExecution.getJobExecution().getExecutionContext()` 写入，下游 Step 读取 |
| 失败现场 | 记录最后成功处理的业务键，用于幂等兜底 |

```java
// 在 StepExecutionListener.afterStep 中记录进度
context.putInt("last.row", lastRow);
// 重启时在 beforeStep 中读取
Integer lastRow = context.getInt("last.row", 0);
```

> ⚠️ **6.0.4 修复**：`ExecutionContext` 的 dirty 标志此前存在"从不复位"的缺陷，导致冗余持久化调用与重启时的状态跟踪错误，6.0.4（及 5.2.6）已修复。

### 3.3 StepContribution

StepExecution 内部还有一个 StepContribution：它聚合"本次 Step 执行改变了多少状态"（读了几条、写了几条、跳过几条…），在**每次 chunk 提交后**由 Step 框架合并回 StepExecution。6.0 中还修复了 StepContribution 计数器在多线程下的线程安全问题。

## 4. 状态机：BatchStatus / ExitStatus / FlowExecutionStatus

Spring Batch 有三套并存的"状态"概念，这是最容易混淆的地方：

### 4.1 BatchStatus：Step 内部执行状态（持久化到数据库）

| 枚举 | 含义 |
|------|------|
| STARTED | 正在执行 |
| COMPLETED | 成功完成 |
| FAILED | 失败（**可重启**） |
| STOPPED | 被外部停止（**可重启**） |
| ABANDONED | 放弃（**不可重启**，用于"失败实例已不需要再跑"） |
| UNKNOWN | 状态未知（异常发生在持久化前） |

流转规则（核心）：

```text
STARTED ──正常完成──▶ COMPLETED
   │
   ├──业务异常─────▶ FAILED ──允许重启──▶ STARTED（同一 Instance 新 Execution）
   ├──外部停止─────▶ STOPPED ──允许重启──▶ STARTED
   ├──人为放弃─────▶ ABANDONED（终止状态，不再重启）
   └──更新失败─────▶ UNKNOWN（需人工介入查库）
```

### 4.2 ExitStatus：Step/Job 的退出码（驱动流程分支）

ExitStatus = **ExitCode（字符串）+ ExitDescription（细节信息）**。它决定 Flow 如何分支：

- 默认 ExitCode 与 BatchStatus 同名（COMPLETED / FAILED / STOPPED）；
- 可以用 `ExitStatus("CUSTOM_CODE")` 自定义，再配合 `on("CUSTOM_CODE")` 走专属分支；
- 6.0 修复了 `ExitStatus#setExitException` 破坏不可变契约的问题——ExitStatus 在 6.0 中不可变，异常上下文通过 ExitDescription 传递。

### 4.3 三者的对照关系

| 维度 | BatchStatus | ExitStatus | FlowExecutionStatus |
|------|------------|-----------|--------------------|
| 粒度 | Step 内部状态 | Step/Job 的对外退出码 | Flow 分支决策状态 |
| 持久化 | 是（BATCH_* 表 STATUS 列） | 是（EXIT_CODE / EXIT_MESSAGE 列） | 否（运行时） |
| 用途 | 决定"能否重启" | 决定"流程怎么走" | 匹配 `on("...")` 模式 |
| 数量 | 7 个枚举 | 任意自定义字符串 | 与 ExitStatus 一一对应 |

> 🎯 **核心辨析**：判断"作业失败能不能重启"看 **BatchStatus**；判断"失败后走哪个分支"看 **ExitStatus**。把两者混为一谈是面试和实战的第一大坑。

## 5. 一次 Job 的完整执行时序

以 Chunk 模型为例（含 2 个 Step 的简单 Job），一次成功运行的时序：

```text
JobLauncher.start(job, parameters)
  1. JobRepository 创建/定位 JobInstance（同参数 → 复用；新参数 → 新建）
  2. 创建 JobExecution（状态 STARTED），持久化
  3. 执行 Step1：
       a. 创建 StepExecution（STARTED）
       b. 循环执行 chunk：读 N 条 → 处理 → 写 → 提交事务
          （每轮提交前先持久化 StepExecution 状态：commit 前写盘是重启的保证）
       c. 结束：StepExecution COMPLETED，写回元数据
  4. 执行 Step2（同 3）
  5. JobExecution 置 COMPLETED
  6. 返回 JobExecution
```

两个容易被问到的实现细节：

- **"提交前先持久化"**：每次 chunk 提交前，框架先把 StepExecution（含 ExecutionContext 与计数器）写入元数据表，保证"数据库事务提交"与"批处理元数据"的一致性——这是重启续跑正确性的来源；
- **元数据事务与业务事务分离**：JobRepository 用自己的事务管理器（或配置的事务），与业务 chunk 事务相互独立，业务回滚不会把运行状态也回滚掉。

## 6. 6.0 领域模型不可变重构

6.0 对领域模型做了"不可变化"重构，理解它才能看懂 6.0 API 为什么变了：

| 变化 | 5.x | 6.0 | 影响 |
|------|-----|-----|------|
| 主键类型 | `Long`（可 null、可 set） | **primitive `long`**，禁止重新赋值 | 实体一旦创建不可改 ID |
| 实体构造 | 可构造"孤儿实体"（无兄弟对象） | **不允许孤儿实体**，查询返回带完整关联的实体 | DAO/仓库层重构 |
| 工件装配 | 默认构造 + setter + `afterPropertiesSet` | **构造时注入必需依赖** | 所有 reader/writer 改为构造器注入 |
| JobParameter | 可变类 | **record**（不可变） | 序列化格式变化 → v5 失败实例无法用 v6 重启 |
| ExitStatus | 可变（setExitException） | **不可变**（6.0.4 修复） | 异常信息走 ExitDescription |
| 包结构 | 分散在 `core.explore` / `core.listener` 等 | 归拢：`core.repository.explore` / `core.listener` / `core.job.parameters` / `core.repository.dao.jdbc|mongo` | 迁移需改 import |

> ⚠️ 编码影响：**6.0 中自定义 reader/writer 必须用构造器注入依赖**，不能再写"无参构造 + setter"旧风格——这是 6.0 与 5.x 代码迁移中最高频的报错点。

---

> 🎯 **核心要点**：领域模型是三层"身份-运行-步骤"结构：JobInstance 由参数哈希唯一标识（重启的锚点），JobExecution 记录每次运行，StepExecution 记录每次运行的每个步骤。状态判定要看准三套枚举的分工——BatchStatus 管重启资格、ExitStatus 管流程分支。6.0 的不可变重构（record、primitive long、构造注入）是理解所有 API 变更的总纲。
