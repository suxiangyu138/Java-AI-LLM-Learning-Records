## 1. 基础层面试题（8 题）

### Q1：Spring Batch 是什么？适合什么场景，不适合什么场景？

- 离线、大数据量、可重启的批处理框架：**可重启、事务化 chunk、声明式容错、元数据审计**是四大核心能力；
- 适合：日终结算、数据迁移、报表汇总、对账；
- 不适合：低延迟在线处理（用 MQ）、流式计算（用 Flink/Kafka Streams）、大数据分布式计算（用 Spark）、轻量定时（Spring Task）。

### Q2：Job / JobInstance / JobExecution / StepExecution 四者的关系？

- JobInstance = 业务身份，由（Job 名 + JobParameters 哈希 JOB_KEY）唯一确定；
- JobExecution = 一次实际运行，同实例可多次执行（首次/失败/重启）；
- StepExecution = 每次运行中每个 Step 的一次执行，承载全部计数器；
- 一句话：**实例定义"这是哪次业务"，执行定义"这次跑得怎么样"**。

### Q3：JobParameters 与 ExecutionContext 的区别？

- JobParameters：启动参数，**决定实例身份**（同参数=同实例），不可变，6.0 为 record；
- ExecutionContext：运行期键值状态，**决定续跑断点**，存于元数据表，可跨 chunk/step 传递；
- 反例：把进度放进 JobParameters 是错的——它会改变实例身份。

### Q4：Chunk 模型的事务边界？commit-interval 怎么定？

- 一个 chunk（读 N 条 → 处理 → 写）一个事务；失败只回滚当前块，已提交块不重放；
- 提交前先持久化 StepExecution 与上下文 → 重启续跑正确性来源；
- 经验值：JDBC 批写 500~2000、文件 1000~5000、重处理 100~500，实测调优。

### Q5：ItemReader 返回 null 与 ItemProcessor 返回 null 分别意味着什么？

- Reader 返回 null：**数据耗尽**，Step 结束；
- Processor 返回 null：**过滤本条**（不写、FILTER_COUNT+1），Step 继续。

### Q6：BatchStatus 与 ExitStatus 的区别？

- BatchStatus：Step 内部执行状态（STARTED/COMPLETED/FAILED/STOPPED/ABANDONED），**决定能否重启**；
- ExitStatus：退出码字符串，**决定流程分支**（`.on("FAILED")` 匹配它），可自定义；
- 混淆两者 = 分支判断错误的头号原因。

### Q7：重启（restart）的机制？

- 同参数再次启动 = 同一实例续跑：跳过已提交 chunk，从 ExecutionContext 断点继续；
- 控制：startLimit、allowStartIfComplete、preventRestart、JobOperator.restart；
- 前提：**写入必须幂等**（已提交块不重放，重放靠去重）。

### Q8：6.0 相比 5.x 有哪些"入口级"变化？

- 默认 Resourceless 仓库（无需数据库）；JobBuilder/StepBuilder 构造注入；`@EnableJdbcJobRepository` 拆分；JobParameters 变 record；retry 内核换 Spring Framework 7；JobOperator extends JobLauncher；CommandLineJobOperator 替代 CommandLineJobRunner。

## 2. 进阶层面试题（8 题）

### Q9：Skip 与 Retry 分别解决什么问题？读/写/处理三类 skip 的差异？

- Skip：永久性坏数据；Retry：瞬时故障——"数据问题 skip、资源问题 retry、进程问题 restart"；
- 读 skip：该行丢弃；处理 skip：该条过滤（chunk 其余正常）；**写 skip：整块回滚 + 逐条重放定位坏数据，代价最大**。

### Q10：skipLimit 超了会怎样？为什么生产必须配 SkipListener？

- 超限 → Step 失败 → 走重启流程；
- SkipListener 落审计表：数据质量报告、坏数据归档、"为什么跳"的证据链。

### Q11：多线程 Step 为什么会失去重启能力？怎么解决？

- 并发提交顺序不定 → 元数据无法还原全局断点；失败只能整步重跑；
- 解决：本地分区（按分片粒度保留重启记录）或"业务侧幂等 + 接受整步重跑"。

### Q12：本地分区与远程分区的区别？远程 Chunking 呢？

- 本地：TaskExecutorPartitionHandler 同 JVM 跑分片，元数据记录每分片成败；
- 远程分区：只传分片范围给 worker（数据不过网），共享 JobRepository，适合 IO 瓶颈；
- 远程 Chunking：master 读 + 数据过网 + worker 处理，适合处理瓶颈，网络成本高。

### Q13：远程执行为什么必须共享 JobRepository？

- 状态协调、分区结果聚合、重启、监控全部依赖元数据；Resourceless 仓库无法跨 JVM 共享状态。

### Q14：6.0 的并发模型改成什么了？背压怎么实现？

- 生产者-消费者 + **有界队列**：read/process 与 write 解耦，队列满即阻塞生产者 → 天然背压；
- `throttleLimit` 已移除；BlockingQueueItemReader/Writer + Spring Integration 通道支撑 SEDA 流水线。

### Q15：怎么保证批处理幂等？

- 三原则：写前可查重、写时唯一键（ItemKeyGenerator / ON DUPLICATE KEY）、重跑可覆盖（先删后插）；
- 非事务写入（文件/Kafka）无法回滚 → 消费端/落盘端幂等兜底。

### Q16：6.0 的 JobRepository 有哪三种实现？怎么选？

- Resourceless（默认，无持久化，一次性/测试）、Jdbc（生产标准，6 表 + 序列 + 乐观锁）、Mongo（5.2 引入，已有 Mongo 基建）；重启/监控/远程执行必须 JDBC 或 Mongo。

## 3. 架构与生产面试题（6 题）

### Q17：Job 状态与执行的运维操作？stop 是同步的吗？

- JobOperator：start/stop/restart/recover（6.0 新增）/abandon；
- **stop 异步**：当前 chunk 跑完才停；进程级优雅停机走 SIGTERM + StoppableStep（6.0）。

### Q18：多实例部署批处理怎么防止重复执行？

- 调度单点触发（ShedLock/外部调度）+ JOB_KEY 唯一约束兜底 + 启动前 JobExplorer 查运行中状态；
- 失败的实例要 restart 而非换参数重跑（换参数 = 新实例，旧失败实例残留）。

### Q19：怎么监控批处理作业？

- 指标（Micrometer spring.batch.job/step + 显式 ObservationRegistry）+ JFR 事件（6.0）+ 元数据 SQL 巡检（超时/失败率/skip 激增）+ 对账（COMPLETED vs 业务产出）。

### Q20：v5 到 v6 迁移最需要注意什么？

- v5 FAILED 实例无法在 v6 重启（参数序列化变化，先 restart 或 abandon）；
- 序列改名 + 迁移脚本；构造注入 API；包改名（core.repository.explore 等）；ObservationRegistry；Jackson 3。

### Q21：你们项目为什么用 Spring Batch 而不是自研 for 循环？

- 自研循环 = 手写事务边界、重试、断点、审计——Spring Batch 把这些做成声明式；
- 元数据表是可监控、可对账、可重启的系统资产；分区/远程执行是标准化扩展路径。

### Q22：一个千万级数据导入 Job 你会怎么设计？

- 分步：校验 Step（快失败）→ 转换 Step（可 skip 坏数据）→ 写入 Step（批量+幂等）；
- 参数化（input.file/业务日期）→ 重启续跑；游标 reader + 合理 commit-interval；数据量大再上本地分区；
- 监控：skip 计数、进度（COMMIT_COUNT）、超时告警。

## 4. 避坑清单 20 条

```text
【模型与配置】
01 别把进度/运行期状态放进 JobParameters（改变实例身份）→ 用 ExecutionContext
02 分支判断看 ExitStatus，不是 BatchStatus
03 6.0 必须用 new JobBuilder(name, jobRepository) 构造注入（工厂已移除）
04 5.x 的 .chunk(n, tx) 双参在 6.0 已废弃 → .chunk(n).transactionManager(tx)
05 @EnableBatchProcessing(dataSourceRef=...) 已拆分 → @EnableJdbcJobRepository(dataSourceRef=...)
06 生产别用默认 Resourceless 仓库（无重启/监控/审计）
07 v5 失败实例必须先在旧版本重启/放弃，再升级 v6

【数据与容错】
08 把瞬时故障配成 skip 会静默丢数据 → 数据 skip、资源 retry
09 写 skip 是重操作（整块回滚 + 逐条重放），尽量用唯一键在写入层消除
10 非事务写入（文件/Kafka）没有回滚 → 幂等设计兜底
11 skip 必须配监听器落审计表
12 restart 重放已提交块 → 写入必须幂等（ON DUPLICATE KEY / 先删后插）
13 事务内长退避重试会拉长事务 → backoff 上限 < 事务超时

【性能与并行】
14 游标 reader 不设 fetchSize，Oracle/PostgreSQL 会慢到离谱
15 分页 reader 必须唯一排序键，深翻页用游标分页（WHERE id > ? LIMIT n）
16 多线程 Step 的 reader 必须线程安全；不可共享连接类 reader
17 别一上来就分布式 → 按阶梯：多线程 → 本地分区 → 远程
18 JpaItemWriter 纯插入用 usePersist(true)，merge 逐条查询慢到爆

【运维与版本】
19 6.0 指标不输出？先检查有没有显式 ObservationRegistry Bean
20 JsonFileItemWriter + append 有历史缺陷 → 升级 6.0.4+ 或临时文件合并
```

## 5. 一句话知识卡片

| 话题 | 一句话 |
|------|--------|
| 重启锚点 | JOB_KEY = JobParameters 哈希 → 实例身份 |
| 断点载体 | ExecutionContext 持久化于元数据表 |
| 事务单元 | 一个 chunk = 一个事务 |
| 续跑保证 | 提交前先写元数据 |
| 跳过语义 | 读跳行、处理跳条、写跳块回滚重放 |
| 扩展阶梯 | 单线程 → 多线程（失重启）→ 本地分区 → 远程 |
| 远程铁律 | 共享 JobRepository；Resourceless 不可用 |
| 6.0 内核 | Retry 换 SF7、并发换有界队列、观测加 JFR |
| 默认行为 | 无库可跑（Resourceless + ResourcelessTransactionManager） |
| 迁移头号坑 | v5 FAILED 实例不能 v6 续跑 |
