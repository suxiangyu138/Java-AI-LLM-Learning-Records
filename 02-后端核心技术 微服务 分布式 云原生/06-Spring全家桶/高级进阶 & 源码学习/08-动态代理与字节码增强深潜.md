## 1. 两类代理的源码级对比

| 维度 | JDK 动态代理 | CGLIB |
|------|-------------|-------|
| 原理 | 实现接口 + `InvocationHandler` | 生成目标类**子类** + `MethodInterceptor` |
| 目标要求 | **必须有接口** | 无接口即可（不能 final） |
| 生成时机 | 运行时（Proxy.newProxyInstance） | 运行时（Enhancer 生成字节码） |
| 性能 | 生成快、调用慢（反射分发） | 生成慢、调用快（FastClass 直调） |
| 包名 | `jdk.proxy` 动态类 | 目标类子类（包内） |
| Spring 选择 | 目标有接口且可用（默认） | 无接口 / 显式 `proxyTargetClass=true` |

> 🎯 **核心要点**：JDK 代理 = "同接口的替身"；CGLIB = "目标类的私生子"。两者都是**方法调用拦截**——在调用前后织入逻辑。

## 2. JDK 动态代理源码

### 2.1 生成过程

```text
Proxy.newProxyInstance(classLoader, interfaces, handler)
 ├─ 生成代理类字节码（ProxyGenerator.generateProxyClass）
 │     └─ 代理类 extends Proxy implements 目标接口
 ├─ 定义类并加载（Unsafe/ClassLoader 定义）
 └─ 实例化：构造器注入 InvocationHandler
```

### 2.2 调用过程

```text
proxy.method(args)            // 代理类的方法（所有方法转发）
 └─ Proxy.h.invoke(...)       // 内部持有 InvocationHandler
      └─ InvocationHandler.invoke(proxy, method, args)
           └─ 反射 method.invoke(target, args)（或被拦截逻辑包装）
```

| 关键点 | 源码事实 |
|--------|---------|
| 代理类生成 | `ProxyGenerator`（JDK 内部，可 `-Dsun.misc.ProxyGenerator.saveGeneratedFiles` 存盘查看） |
| 方法转发 | 代理类所有接口方法体都是 `h.invoke(this, m, args)` 一行 |
| 局限 | 只代理**接口方法**；`Object.equals/hashCode/toString` 也转发 |

## 3. CGLIB 增强源码

### 3.1 生成过程

```text
Enhancer.create()
 ├─ 选择父类（目标类）+ 接口
 ├─ 生成子类字节码（ASM 生成）
 │     └─ 重写可继承方法：方法体变为 callback 调度
 └─ 创建子类实例（构造器调用 + 初始化）
```

### 3.2 调用过程

```text
sub.method(args)                              // 生成子类方法
 └─ MethodInterceptor.intercept(obj, method, args, methodProxy)
      └─ methodProxy.invokeSuper(obj, args)   // FastClass 直调父类方法（非反射）
```

| 关键点 | 源码事实 |
|--------|---------|
| FastClass | 为每个方法生成索引，`invoke(index)` 直接调用（省反射） |
| `methodProxy.invokeSuper` vs `invoke` | invokeSuper 调父类实现（**不被再次拦截**）；invoke 会再次进入拦截器 |
| final 限制 | final 方法/类无法重写 → 无法代理（Spring 7 在 `Objenesis` 基础上仍受此限） |

> ⚠️ **CGLIB 调用性能优势的来源就是 FastClass**：索引直调代替反射。这也是"Spring 默认在目标有接口时也常选 CGLIB"（Boot 时代 `proxyTargetClass=true` 成为默认）的原因之一。

## 4. Spring ProxyFactory 决策逻辑

```text
ProxyFactory / AbstractAutoProxyCreator.wrapIfNecessary
 → 判断是否需要代理（有 Advisor 且匹配切点）
 → DefaultAopProxyFactory.createAopProxy
      ├─ config.isProxyTargetClass() == true → CGLIB（Objenesis 无参实例化）
      └─ false（默认）→ 目标有接口 → JDK 代理；无接口 → CGLIB
```

| 场景 | 代理选择 |
|------|---------|
| Boot 4 默认 | `spring.aop.proxy-target-class=true` → **一律 CGLIB** |
| 显式 JDK | `proxyTargetClass=false` 且目标有接口 |
| 无接口类 | 无论配置如何都 CGLIB |
| 接口 + JDK 模式 | 只代理接口方法（实现类的额外方法不拦截） |

> 💡 **Boot 默认 CGLIB 的意义**：实现类自有方法也能被 AOP 拦截（JDK 模式做不到）——"Spring 4+ 默认 CGLIB"是 Boot 时代的事实，7.x 延续。

## 5. 代理失效场景根因

| 场景 | 根因（源码级） |
|------|----------------|
| 同类自调用（`this.xxx()`） | `this` 是代理内部的目标实例，**不是代理**——方法调用在 `MethodProxy.invokeSuper` 里发生，不经过拦截器 |
| private/final 方法 | CGLIB 无法重写 → 不织入；JDK 代理不涉及非接口方法 |
| 非 Spring 管理的对象 | 无代理（`new` 出来的对象无增强） |
| `@Transactional` 自调用 | 同上：`this.save()` 绕过事务拦截器（经典坑） |
| 泛型擦除的切点误配 | 切点表达式匹配不到目标方法 → 不创建代理 |

```java
// 自调用失效示意
@Service
public class OrderService {
    @Transactional
    public void create() { ... }

    public void batch() {
        this.create();          // ❌ 不走事务代理（this 是目标对象）
        create();               // ❌ 等价于 this.create()
    }
}

// 正确解法：注入自身代理 或 拆到另一个 Bean
@Autowired
private OrderService self;      // 注进来的才是代理
```

> 🎯 **核心要点**：一切"注解没生效"先问两个问题——① 调用方拿到的对象是不是代理（断点看类名，`$$EnhancerBySpringCGLIB`/`$Proxy` 后缀）？② 调用是否经过代理（`this.` 直调必然绕过）？

## 6. ASM 与字节码操作简介

| 层 | 工具 | 用途 |
|----|------|------|
| 直接操作字节码 | ASM | CGLIB/ByteBuddy 的底层 |
| CGLIB | Enhancer + FastClass | Spring AOP 默认增强 |
| 现代替代 | ByteBuddy | Mockito 等使用 |
| 查看字节码 | `javap -c` / IDEA 字节码视图 | 阅读代理类 |

```bash
# 看代理类字节码（JDK 代理示例）
javap -c -p 'jdk.proxy.$Proxy0.class'
# 或启动参数保存代理类
-Djdk.proxy.ProxyGenerator.saveGeneratedFiles=true
-Dcglib.debugLocation=./cglib-classes
```

> 💡 面试加分项：能说出"Spring 7 的 CGLIB 依赖 Objenesis 绕过构造器实例化 + FastClass 索引直调"，比"用了 CGLIB"高一个档次。

## 7. 核心要点

> 🎯 **核心要点**：
> - JDK 代理：接口替身 + InvocationHandler；CGLIB：子类 + MethodInterceptor + FastClass；
> - Boot 默认 `proxyTargetClass=true` → CGLIB 优先（能拦实现类自有方法）；
> - 失效根因三问：对象是代理吗？调用过代理吗？方法可重写吗？
> - FastClass 与 Objenesis 是 CGLIB 的两个内部要点，也是面试深挖点。
