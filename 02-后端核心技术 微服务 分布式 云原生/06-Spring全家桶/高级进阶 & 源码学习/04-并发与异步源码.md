## 1. TaskExecutor 体系：Spring 的线程池抽象

```text
TaskExecutor（接口：execute(Runnable)）
 └─ 继承树
     ├─ AsyncTaskExecutor（submit 带 Future）
     ├─ SchedulingTaskExecutor（可延期/定期）
     ├─ ThreadPoolTaskExecutor  ★ 最常用（包装 java.util.concurrent.ThreadPoolExecutor）
     └─ SimpleAsyncTaskExecutor（每次新建线程，仅测试用）
```

| 实现 | 底层 | 场景 |
|------|------|------|
| `ThreadPoolTaskExecutor` | `ThreadPoolExecutor` 包装 | 生产默认 |
| `ThreadPoolTaskScheduler` | `ScheduledThreadPoolExecutor` 包装 | 定时任务 |
| `SimpleAsyncTaskExecutor` | 新线程 | 禁用（无池化） |
| `ConcurrentTaskExecutor` | 直接包装原生执行器 | 兼容场景 |

> 💡 Spring 的线程池 = JDK `ThreadPoolExecutor` 的**配置化封装**：核心参数（core/max/queue/拒绝策略）在 `ThreadPoolTaskExecutor` 属性中暴露，`initialize()` 时创建底层池。面试问"Spring 线程池参数"，答 JDK 参数 + Spring 配置映射。

## 2. @Async 源码链路

### 2.1 完整调用链

```text
@EnableAsync
 ├─ 注册 AsyncAnnotationBeanPostProcessor（Advisor 注入器）
 │     └─ 为 @Async 方法所在 Bean 创建代理（ProxyFactory）
 │           └─ AsyncAnnotationInterceptor（MethodInterceptor）
 │                 └─ 提交 TaskExecutor.execute
 │                       └─ 实际线程执行（Future 回填）
```

| 环节 | 关键类 | 关注点 |
|------|--------|--------|
| 开启 | `@EnableAsync` → `AsyncConfigurationSelector` | 选择 proxy 模式 |
| 代理 | `AsyncAnnotationBeanPostProcessor` | 为含 `@Async` 的 Bean 加 Advisor |
| 拦截 | `AsyncExecutionInterceptor` | 方法级调度、异常处理 |
| 执行 | `AsyncExecutionAspectSupport.determineAsyncExecutor` | **Executor 选择逻辑** |
| 回执 | `Future`/`CompletableFuture` 回填 | 返回值语义 |

### 2.2 三个高频源码点

| 考点 | 源码事实 |
|------|---------|
| 执行器选择 | `determineAsyncExecutor`：优先 `@Async("executorName")` 指定 → `AsyncConfigurer` 自定义 → 默认 `SimpleAsyncTaskExecutor`（**Boot 4 默认提供 `applicationTaskExecutor`**） |
| 自调用失效 | 代理拦截只对**代理外调用**生效；同类内 `this.xxx()` 不走代理（与 AOP 失效同因，见 [08](08-动态代理与字节码增强深潜.md)） |
| 返回类型 | void/Future/CompletableFuture；返回对象会被包装丢弃 |

```java
@Bean
public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(16);
    executor.setQueueCapacity(1000);
    executor.setThreadNamePrefix("biz-");
    executor.initialize();
    return executor;
}

@Async("taskExecutor")        // 指定执行器
public CompletableFuture<String> doAsync() { ... }
```

> ⚠️ **生产陷阱**：默认执行器在 Boot 4 是 `applicationTaskExecutor`（无界队列），高并发下任务堆积不排队阻塞——**业务异步必须显式配队列与拒绝策略**。

## 3. @Scheduled 源码链路

```text
@EnableScheduling
 ├─ 注册 ScheduledAnnotationBeanPostProcessor
 │     ├─ 扫描 @Scheduled 方法 → ScheduledTaskRegistrar 收集
 │     └─ 按 cron/fixedRate/fixedDelay 注册到 ThreadPoolTaskScheduler
 │           └─ ScheduledExecutorService（JDK）执行
```

| 环节 | 关键类 | 关注点 |
|------|--------|--------|
| 扫描 | `ScheduledAnnotationBeanPostProcessor` | `postProcessAfterInitialization` 扫描 |
| 注册 | `ScheduledTaskRegistrar` | 任务注册表 |
| 调度 | `TaskScheduler`/`ReschedulingRunnable` | cron 表达式解析（CronExpression） |
| 线程 | 默认单线程池 | **多任务相互阻塞**是高频坑 |

> ⚠️ 默认 `@Scheduled` 只有 1 个调度线程：一个任务卡住，其余全部停摆。生产必须自定义 `TaskScheduler` 线程池。

## 4. WebFlux 线程模型

```text
WebFlux（Reactor Netty）
 ├─ 事件循环线程（Netty EventLoop，少量固定）
 ├─ 业务处理：默认与 IO 线程同一事件循环（非阻塞代码）
 └─ 阻塞转义：publishOn/subscribeOn 显式切线程（受管线程池）
```

| 模型 | 线程数 | 适用 |
|------|--------|------|
| WebMVC（Tomcat） | 200 默认线程池，每请求一线程 | 阻塞 IO 业务 |
| WebFlux（Netty） | 事件循环（核数级），请求异步化 | 高并发非阻塞 |
| 混合 | `blocking` 隔离线程池 | 渐进改造 |

> 💡 **源码读法**：`HttpWebHandlerAdapter`（WebFlux 入口）→ `WebFilterChain`（过滤器链）→ `DispatcherHandler`（分发器，类似 DispatcherServlet）。线程模型差异的根源在**容器**（Netty vs Tomcat），不在业务代码。

## 5. Spring 源码中的并发工具

| 工具 | 源码用途 |
|------|---------|
| `LinkedHashMap` 同步（synchronized 块） | 单例注册表（早期）→ 7.x 优化 |
| `ConcurrentHashMap` | BeanDefinition 注册表、事件监听器注册表 |
| `CopyOnWriteArrayList` | 监听器列表（读多写少） |
| `ReentrantLock` | `SingletonBeanRegistry` 锁、线程池初始化 |
| `CountDownLatch` | 容器启动同步 |
| `CompletableFuture` | `@Async` 返回值、WebFlux 桥接 |

> 🎯 **核心要点**：Spring 并发源码 = JDK 并发工具的**工程化示范**——读"注册表用什么集合、锁粒度在哪"比背工具更有收获。

## 6. 核心要点

> 🎯 **核心要点**：
> - TaskExecutor 体系 = JDK 线程池的配置化封装；`ThreadPoolTaskExecutor` 是生产默认；
> - @Async 链路：@EnableAsync → BPP 代理 → AsyncExecutionInterceptor → 执行器选择 → 线程执行；
> - 两大高频坑：默认执行器无界队列（任务堆积）、@Scheduled 默认单线程（互相阻塞）；
> - 自调用不生效与 AOP 同源：代理只拦截外部调用；
> - WebFlux 线程模型差异在容器（Netty 事件循环），不在业务代码。
