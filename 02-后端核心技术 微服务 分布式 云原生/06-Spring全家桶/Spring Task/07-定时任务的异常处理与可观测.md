# 07 定时任务的异常处理与可观测

> 定时任务"静默死亡"是生产最阴险的事故：任务抛异常后日志被吞、任务不再执行却无人知晓、监控图上看不到任何痕迹——本模块讲透异常路径、errorHandler、指标与告警的完整方案

## 1. 默认行为的真相：异常去哪了

```java
@Scheduled(fixedDelay = 5000)
public void syncData() {
    // 第 100 次执行时抛异常
    throw new RuntimeException("db connection failed");
}
```

**默认行为：**

```text
任务异常 → 调度器捕获并输出日志（ERROR 级别，stacktrace）
        → 不影响下次调度（fixedDelay/cron 仍会继续执行）
        → 没有告警、没有指标、没有失败记录
```

| 事实 | 说明 |
|------|------|
| 任务异常不会终止任务 | 下次照常执行（与 Quartz 的 misfire 策略不同） |
| 默认有日志 | 但日志可能被淹（海量任务 × 高频率） |
| 无失败语义 | 成功/失败无差别——**可观测性为零** |

> 🎯 **核心要点**："任务会重试吗？"——Spring 默认**不重试**，只是"下次照常"。失败感知完全要靠自己建设：执行记录 + 指标 + 告警。

## 2. errorHandler：任务异常的集中处理

```java
@Bean
public TaskScheduler taskScheduler() {
    ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
    scheduler.setPoolSize(5);
    scheduler.setErrorHandler(new TaskErrorHandler());   // 统一异常处理
    return scheduler;
}

// 集中处理：日志 + 指标 + 告警（替代散落的 try-catch）
public class TaskErrorHandler implements ErrorHandler {

    @Resource
    private MeterRegistry meterRegistry;

    @Override
    public void handleError(Throwable t) {
        // ① 完整日志（含任务上下文）
        log.error("scheduled task failed: {}", t.getMessage(), t);
        // ② 指标（失败计数 → 告警）
        meterRegistry.counter("task.failure", "source", "scheduler").increment();
        // ③ 告警（钉钉/企业微信/邮件——按失败频率限流）
        alertService.sendIfNeeded("scheduled task failed", t);
    }
}
```

> 💡 **注意**：errorHandler 只能拿到 Throwable，**拿不到"是哪个任务"**——想定位任务身份，需要在任务内 try-catch 或使用包装 Runnable（带任务名）。

```java
// 带任务名的包装（推荐：错误可定位）
public Runnable namedTask(String taskName, Runnable body) {
    return () -> {
        try {
            body.run();
        } catch (Exception e) {
            log.error("task [{}] failed", taskName, e);
            metricRegistry.counter("task.failure", "task", taskName).increment();
            throw e;   // 或吞掉（按策略）
        }
    };
}
```

## 3. 任务失败检测：执行记录与告警

### 3.1 执行记录表（任务"健康档案"）

```sql
CREATE TABLE task_execution_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    task_name VARCHAR(64) NOT NULL,
    expected_cron VARCHAR(32),
    start_time DATETIME NOT NULL,
    end_time DATETIME,
    status VARCHAR(16) NOT NULL,      -- SUCCESS / FAILED / TIMEOUT
    error_msg TEXT,
    duration_ms BIGINT,
    KEY idx_task_time (task_name, start_time)
);
```

```java
// 任务执行包装：每次执行写一条记录
public void executeWithLog(String taskName, Runnable body) {
    long start = System.currentTimeMillis();
    try {
        body.run();
        logExecution(taskName, "SUCCESS", null, System.currentTimeMillis() - start);
    } catch (Exception e) {
        logExecution(taskName, "FAILED", e.getMessage(), System.currentTimeMillis() - start);
        throw e;
    }
}
```

### 3.2 告警策略

| 场景 | 告警规则 |
|------|---------|
| 单次失败 | 连续失败 ≥ 3 次才告警（防抖动） |
| 任务未执行（静默死亡） | **对比期望执行次数**：`now - max(start_time) > 期望间隔 × 2` → 告警 |
| 执行时长异常 | duration_ms 超过 P95×3 → 告警 |
| 失败率 | 每小时失败率 > 阈值 → 告警 |

> ⚠️ **"任务没跑"是最难发现的故障**：没有异常、没有日志——只有"该发生的事没发生"。**期望执行监控（heartbeat 缺失检测）是定时任务监控的第一优先**。

## 4. 重叠执行与超时的监控

### 4.1 重叠检测

```java
@Component
public class MonitoredTask {
    private final AtomicBoolean running = new AtomicBoolean(false);

    @Scheduled(fixedDelay = 5000)
    public void run() {
        if (!running.compareAndSet(false, true)) {
            metricRegistry.counter("task.overlap", "task", "sync").increment();  // 重叠计数
            log.warn("task overlap detected");
            return;
        }
        try { doWork(); } finally { running.set(false); }
    }
}
```

### 4.2 超时监控

```java
// 任务内包超时控制（或依赖执行记录表的 duration 对比）
try {
    Future<?> future = executor.submit(body);
    future.get(30, TimeUnit.SECONDS);        // 超时抛 TimeoutException
} catch (TimeoutException e) {
    log.error("task timeout, mark and alert");
    metricRegistry.counter("task.timeout", "task", "sync").increment();
}
```

> 💡 **注意**：`future.get(timeout)` 只停止"等待"，**不停止任务线程**——真正中断需要 `future.cancel(true)` 配合任务可中断设计（检查中断位）。

## 5. Micrometer 指标与日志规范

### 5.1 指标清单

```text
task.execution.success    成功次数（按任务名打标签）
task.execution.failure    失败次数
task.execution.duration   执行耗时直方图（P50/P95/P99）
task.execution.overlap    重叠次数
task.heartbeat            最后执行时间戳（告警用）
```

```java
// 封装一个统一的任务执行器，自动打点
@Component
public class TaskRunner {

    @Resource
    private MeterRegistry registry;

    public void run(String taskName, Runnable body) {
        Timer.Sample sample = Timer.start(registry);
        try {
            body.run();
            registry.counter("task.execution.success", "task", taskName).increment();
        } catch (Exception e) {
            registry.counter("task.execution.failure", "task", taskName).increment();
            throw e;
        } finally {
            sample.stop(Timer.builder("task.execution.duration")
                    .tag("task", taskName).register(registry));
        }
    }
}
```

### 5.2 日志规范

```text
✅ 任务开始：task=[sync] start cron=0 */5 * * * ? instance=pod-1
✅ 任务结束：task=[sync] end status=SUCCESS duration=1200ms rows=35210
✅ 任务失败：task=[sync] fail error=db timeout retry=1/3
❌ 无任务名、无实例标识、异常堆栈裸打
```

> 🎯 **要点**：每条日志必须能回答三个问题——**哪个任务、哪个实例、成功还是失败**。堆栈要有（排障），任务名与实例要有（聚合）。

## 6. 幂等与重试策略

### 6.1 幂等是任务的第一原则

```text
为什么必须幂等：
  ① 失败重试 → 任务跑两次
  ② 多实例部署 → 任务跑多次（08 篇）
  ③ 手动补跑 → 业务补偿

幂等设计：
  业务主键去重（如订单号）           ← 最可靠
  状态机校验（只处理特定状态）
  分布式锁保护（同 key 只执行一次）
```

### 6.2 重试策略模板

```java
@Component
public class RetryableTask {

    @Scheduled(fixedDelay = 60_000)
    public void syncOrders() {
        int maxRetries = 3;
        for (int attempt = 1; attempt <= maxRetries; attempt++) {
            try {
                doSync();
                return;
            } catch (Exception e) {
                log.warn("sync failed, attempt {}/{}: {}", attempt, maxRetries, e.getMessage());
                if (attempt == maxRetries) {
                    log.error("sync failed after {} attempts, alerting", maxRetries);
                    alertService.alert("syncOrders 连续失败，需人工介入");
                }
                sleepBackoff(attempt);   // 1s, 2s, 4s...
            }
        }
    }
}
```

| 重试要素 | 建议 |
|---------|------|
| 重试次数 | 3-5 次内（避免无限重试拖垮依赖） |
| 退避策略 | 指数退避 + 抖动（1s→2s→4s...） |
| 最终失败 | 告警 + 补偿机制（死信表/人工补跑） |
| 重试粒度 | 任务内重试 vs 调度频率重试（60s 间隔本身就是天然重试） |

> 🎯 **核心要点**：定时任务的可靠性 = 幂等（重跑安全）× 失败可见（日志+指标+告警）× 可补跑（执行记录+手动触发）。**监控优先级排序：心跳缺失检测 > 失败告警 > 耗时异常**——"任务根本没跑"远比"任务跑慢了"危险。
