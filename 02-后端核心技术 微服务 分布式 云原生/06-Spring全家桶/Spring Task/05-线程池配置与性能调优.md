## 1. 配置属性全解：scheduling 与 execution 两套命名空间

Spring Boot 用两套独立命名空间分别管理调度器与执行器：

```yaml
spring:
  task:
    scheduling:                      # 定时任务调度器（TaskScheduler）
      pool:
        size: 10                     # 调度线程数（默认 1！）
      thread-name-prefix: task-sched-
      shutdown:
        await-termination: true      # 停机等待任务完成
        await-termination-period: 30s
    execution:                       # 异步执行器（@Async 线程池）
      pool:
        core-size: 8                 # 核心线程
        max-size: 16                 # 最大线程
        queue-capacity: 200          # 队列容量
        keep-alive: 60s              # 非核心线程空闲回收
      thread-name-prefix: async-
      shutdown:
        await-termination: true
        await-termination-period: 30s
```

| 命名空间 | 控制对象 | 关键属性 |
|---------|---------|---------|
| `spring.task.scheduling.*` | 定时任务调度器 | pool.size、thread-name-prefix、shutdown |
| `spring.task.execution.*` | @Async 执行器 | pool 三件套、thread-name-prefix、shutdown |

> ⚠️ **Boot 4 重要提醒**：Java 21+ 默认虚拟线程场景下，`pool.size`/`pool.core-size` 等池参数**被忽略**（SimpleAsyncTaskScheduler/虚拟线程执行器无池化）——这是官方明确文档化的行为（06 篇）。

## 2. 容量设计：核心/最大/队列怎么定

### 2.1 ThreadPoolExecutor 的运行逻辑（复习）

```text
提交任务 →
  ① 线程 < coreSize → 新建线程执行
  ② 线程 >= coreSize 且队列未满 → 进队列等待
  ③ 队列已满 且 线程 < maxSize → 扩线程到 maxSize
  ④ 队列满 + 线程已达 maxSize → 触发拒绝策略
```

### 2.2 设计公式与经验值

| 参数 | 设计依据 | 经验值 |
|------|---------|--------|
| coreSize | 平均并发任务数（QPS × 任务耗时） | CPU 密集：CPU 核数+1；IO 密集：核数×2 起 |
| maxSize | 峰值并发（含积压） | core 的 1.5-2 倍 |
| queueCapacity | 可容忍的积压深度（峰值时长 × 平均任务量） | 200-1000 量级 |
| keepAlive | 非核心线程空闲回收时间 | 60s 起 |

**容量估算示例：**

```text
业务：异步通知，平均 QPS=50，单任务平均耗时 200ms
平均并发 = 50 × 0.2 = 10
→ coreSize = 12（10 × 1.2 余量）
→ maxSize = 24
→ queue = 500（可缓冲峰值 10 秒的积压）
```

> 💡 **原则**：线程池参数没有"抄作业"标准——**由平均并发与峰值时长推导**；上线后按监控回调（第 5 节）。

### 2.3 线程池命名（排查必备）

```java
executor.setThreadNamePrefix("async-order-");   // 线程名带业务，jstack 一眼定位
scheduler.setThreadNamePrefix("sched-clean-");
```

> ⚠️ **生产事故**：线程池全部叫 `pool-1-thread-N`，线程 dump 里无法区分——**每个池必须唯一前缀**（业务名 + 池类型）。

## 3. 拒绝策略与过载保护

| 策略 | 行为 | 生产建议 |
|------|------|---------|
| AbortPolicy（默认） | 抛异常 | 配合降级/告警 |
| **CallerRunsPolicy** | 提交者线程执行 | **推荐**：天然背压 |
| DiscardPolicy | 静默丢弃 | ❌ |
| DiscardOldestPolicy | 丢最老 | 特殊场景 |

```java
// 过载保护三板斧：拒绝策略 + 计数告警 + 降级
executor.setRejectedExecutionHandler((r, pool) -> {
    if (overloadCounter.incrementAndGet() % 100 == 1) {
        log.error("async pool overloaded: queue={}, active={}, rejected={}",
                pool.getQueue().size(), pool.getActiveCount(), rejectedCount);
    }
    // 降级：走本地线程执行（CallerRuns 语义）或丢弃并记补偿
    r.run();
});
```

> 🎯 **要点**：过载不是"错误"，是系统给的重压信号——**必须可观测**（拒绝计数 + 告警）且**有兜底**（降级/补偿）。

## 4. 优雅关闭：停机不丢任务

### 4.1 两种关闭行为的对比

```java
// 属性配置（推荐）
spring.task.execution.shutdown.await-termination: true
spring.task.execution.shutdown.await-termination-period: 30s

// 或编程式
executor.setWaitForTasksToCompleteOnShutdown(true);
executor.setAwaitTerminationSeconds(30);
```

| 关闭模式 | 行为 | 风险 |
|---------|------|------|
| 默认（false） | 立即中断线程池 | **正在执行的任务被打断**，可能数据不一致 |
| await-termination | 等任务完成后关闭（超时兜底） | 等待期内新任务被拒 |

> ⚠️ **生产事故**：K8s 滚动发布时线程池被立即打断——报表任务写到一半，数据缺块。**优雅关闭 + 30s 超时是标配**；任务本身要幂等（重跑安全）。

### 4.2 优雅关闭的完整时序

```text
停机信号 → Spring 容器关闭 →
  ① 停止接收新任务（调度器取消未来任务）
  ② 等待在途任务完成（await-termination）
  ③ 超时仍未完成 → 强杀（await-termination-period 兜底）
  ④ 任务方校验"正在关闭"标识，自行安全退出
```

## 5. 线程池监控与动态调参

### 5.1 Micrometer 指标（Spring Boot Actuator）

```text
executor.active.count        活跃线程数
executor.queue.depth         队列深度
executor.completed.count     完成任务总数
executor.pool.core/max.size  池容量
executor.rejected.count      拒绝数（过载信号）
```

```java
// 手动上报业务级指标
MeterRegistry registry;   // 注入
registry.counter("task.rejected", "pool", "async-order").increment();
```

| 指标 | 健康信号 | 异常信号 |
|------|---------|---------|
| queue.depth | 趋近 0 | 持续上涨 = 积压 |
| active.count | 远小于 core | 长期等于 max = 过载 |
| rejected.count | 0 | >0 = 需要扩容或降级 |

### 5.2 动态调参（生产）

```java
// 用可调线程池（如 Nacos 配置驱动）
@ConfigurationProperties(prefix = "task.pool")
public class PoolProperties { int core; int max; int queue; }

// 变更时重建/调整：ThreadPoolTaskExecutor 支持 setCorePoolSize/setMaxPoolSize 运行期调整
```

> 💡 **调参纪律**：参数变更要配套"压测 → 观察指标 → 调整"循环；**一次只动一个参数**，留记录。

## 6. 调优实战流程

```text
① 基线：压测场景下采集指标（active/queue/rejected/latency）
② 定位瓶颈：
   队列积压 + active 满 → 容量不足（扩 max/queue）
   响应慢 + 线程空闲 → 任务本身慢（优化业务，不是扩池）
   rejected > 0 → 峰值超容（CallerRuns 背压 or 削峰）
③ 调整参数（一次一个）+ 复测
④ 沉淀：记录"场景 → 参数 → 结果"到团队知识库
```

**常见误区：**

| 误区 | 真相 |
|------|------|
| 线程池越大越快 | 线程切换开销 + 资源争抢；CPU 密集池 > 核数无益 |
| 队列越大越安全 | 积压 = 延迟恶化 + 内存占用；任务可能早已过期 |
| 抄同事配置 | 场景不同（IO/CPU、QPS、峰值时长）参数必然不同 |
| 只有线程池是性能因素 | 任务自身逻辑、DB 连接池、外部依赖同样关键 |

> 🎯 **核心要点**：线程池调优 = 容量设计（由并发量推导）+ 过载保护（拒绝策略可观测）+ 优雅关闭（停机不丢任务）+ 监控回调（指标驱动调整）。纪律三则：池子必须有唯一命名、拒绝必须告警、参数变更必须配套监控验证。
