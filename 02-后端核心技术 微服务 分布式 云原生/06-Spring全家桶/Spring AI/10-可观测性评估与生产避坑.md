## 1. 可观测性：追踪与指标

### 1.1 Micrometer Tracing 集成

| 观测点 | 说明 |
|--------|------|
| ChatClient 调用 | 每次对话自动生成 span（模型、token 用量、耗时） |
| Advisor 链 | 每个 Advisor 的执行时机可观测（递归轮次可见） |
| 工具调用 | 每次工具执行独立 span（参数、结果、耗时） |
| 输出到 | 兼容 Zipkin/Jaeger/OpenTelemetry（Spring Boot 4 观测栈） |

### 1.2 核心指标

| 指标 | 关注点 |
|------|--------|
| 请求量/成功率 | 模型调用次数、错误率 |
| 延迟（p50/p95/p99） | 模型响应耗时（流式首 token 延迟更关键） |
| Token 用量 | 输入/输出 token 趋势（成本曲线） |
| 工具调用次数/失败率 | Agent 行为健康度 |
| 校验重试次数 | 结构化输出失败率（模型质量信号） |

```yaml
spring:
  ai:
    chat:
      client:
        observability:
          enabled: true       # 2.0 观测默认开启
```

> 💡 生产必备：把"token 用量"与"结构化校验失败率"接到告警——前者是成本失控信号，后者是模型/提示词劣化信号。

## 2. 模型评估

| 评估维度 | 内容 | 手段 |
|----------|------|------|
| 输出正确性 | 结构化字段准确率 | 自动化断言 + schema 校验 |
| 检索质量（RAG） | 召回率/相关度 | 真实查询集 + 人工标注（或 LLM 打分） |
| 提示词回归 | 同一输入多次输出稳定性 | 固定 seed/低温度 + 回归用例 |
| 成本基线 | 每任务 token 消耗 | 用量统计 |
| 安全 | 拒答率、越狱成功率 | 红队用例集 |

```text
评估闭环：测试集（真实问题） → 批量调用 → 指标汇总 → 提示词/分块调优 → 再评估
```

> ⚠️ **上线前必答三问**：测试集覆盖典型场景了吗？劣化阈值（结构化失败率/相关度）定义了吗？模型升级（厂商滚动更新）后有回归机制吗？——三者缺一，模型哪天变了都不知道。

## 3. 安全：提示注入与数据泄露

| 风险 | 场景 | 防护 |
|------|------|------|
| 提示注入 | 用户输入诱导模型执行越权工具 | `SafeGuardAdvisor` 敏感词拦截；工具最小权限；系统提示词边界声明 |
| 数据泄露 | 内部文档被检索/输出外泄 | 元数据权限标签 + 检索后过滤；输出脱敏 |
| 工具滥用 | 模型误调写操作工具 | 读写工具分离、确认机制（写操作二次确认） |
| MCP 外部工具 | 第三方服务器不可信 | `McpToolFilter` 白名单 + OAuth 鉴权 |

```java
// 输出侧护栏
@Bean
SafeGuardAdvisor safeGuardAdvisor() {
    return new SafeGuardAdvisor(List.of("密码", "密钥", "token"), List.of());  // 拦截词
}
```

## 4. 成本与性能控制

| 手段 | 说明 |
|------|------|
| 模型分层 | 简单任务小模型（`gpt-4o-mini`/`deepseek-chat`），复杂任务大模型 |
| 缓存 | 相同问题命中缓存（语义缓存：向量相似度判同） |
| 上下文预算 | 记忆窗口裁剪 + 检索 Top-K 控制 token 总量 |
| 超时与重试 | 配置调用超时 + 限流（防模型故障拖垮服务） |
| 流式优先 | 长输出走 stream（首 token 延迟体验） |
| 预算告警 | 每日 token 用量告警阈值 |

## 5. 与 LangChain4j 等框架对比选型

| 维度 | Spring AI 2.0 | LangChain4j | 原生 SDK（OpenAI 等） |
|------|---------------|-------------|------------------------|
| 生态归属 | Spring 官方（Boot 4 原生） | 社区框架（Java） | 厂商 SDK |
| 编程风格 | ChatClient + Advisor 链 | AiServices + 接口代理 | 直接调用 |
| 工具/MCP | 统一 ToolCallback + MCP 原生 | 工具绑定 + MCP 支持 | 手写闭环 |
| 向量库 | 20+ 官方 starter | 多实现 | 无 |
| 与 Spring 全家桶 | 自动配置/观测/测试无缝 | 需手动集成 | 需手动集成 |
| 稳定性 | 官方路线（2.0 重构期注意破坏性） | 社区驱动 | 厂商迭代快 |
| 适用 | **Boot 4 新项目首选** | 存量 Boot 3 项目 | 最小依赖/深度定制 |

> 🎯 **选型结论**：Boot 4 新项目 → Spring AI 2.0；Boot 3.5 存量项目 → LangChain4j（或 Spring AI 1.1.x）；仅单模型简单调用 → 原生 SDK。

## 6. 生产避坑清单

| # | 坑 | 现象 | 规避 |
|---|----|------|------|
| 1 | 2.0 用在 Boot 3 | 启动失败/编译错误 | 先升 Boot 4（硬性要求） |
| 2 | 旧 `toolNames()` 写法 | 编译失败（已删除） | 显式 ToolCallback + `.tools()` |
| 3 | 依赖 provider 默认值 | 输出忽高忽低（temperature 随厂商默认） | 显式配置 Options |
| 4 | 模型 ID 写死 | 厂商下线/改名后全线报错 | 配置外置 + 模型列表页核对 |
| 5 | 记忆进工具循环 | prompt 膨胀、工具判定漂移 | 记忆 Advisor 保持在循环外 |
| 6 | 不设上下文预算 | token 成本失控 | 记忆窗口 + Top-K + 超时 |
| 7 | 结构化输出不校验 | 解析 NPE/脏数据入库 | `StructuredOutputValidationAdvisor` 兜底 |
| 8 | 工具无权限收敛 | 模型误调写操作 | 读写分离 + SafeGuard + 二次确认 |
| 9 | MCP 不设过滤 | 外部服务器全部工具可见 | `McpToolFilter` 白名单 |
| 10 | 无评估集上线 | 模型升级后行为劣化无感知 | 测试集 + 阈值告警 |
| 11 | SSE 端点配置 | 2.0 MCP 连接失败 | 切 Streamable HTTP |
| 12 | 无重试/降级 | 模型故障 = 服务故障 | 多模型降级 + 超时重试 |

## 7. 面试高频题

| 问题 | 答题要点 |
|------|---------|
| Spring AI 2.0 与 1.x 最大区别？ | ChatClient 主 API、工具调用统一进 ToolCallingAdvisor、MCP 原生、Boot 4 基线 |
| ChatClient 和 ChatModel 的关系？ | 主 API vs 底层构建块；ChatClient 通过 Advisor 链挂载工具/记忆/校验 |
| 工具调用闭环怎么实现的？ | 注入 schema → 模型请求 → 执行 ToolCallback → 结果回传 → 递归重入（copy 子链） |
| Advisor 链有什么用？ | 横切 AI 模式：记忆/工具/安全/校验/观测；支持递归与排序 |
| RAG 在 Spring AI 怎么落地？ | VectorStore + QuestionAnswerAdvisor / RetrievalAugmentationAdvisor + ChatClient |
| 记忆如何实现？ | ChatMemoryRepository + 记忆 Advisor + 窗口裁剪（2.0 对齐 USER 边界） |
| MCP 是什么？Spring AI 怎么用？ | 协议三要素；@McpTool 发布、Client 接入；Streamable HTTP |
| 结构化输出怎么保证可靠？ | entity() + Schema 校验 Advisor（失败重试 3 次）+ provider 原生模式 |
| 2.0 升级注意什么？ | Boot 4 前置、工具 API 破坏、Jackson 3、Options 不可变、SSE→Streamable HTTP |
| 怎么控制 AI 应用成本？ | 模型分层、缓存、上下文预算、token 告警 |

## 8. 核心要点

> 🎯 **核心要点**：
> - 观测三件套：调用 span、token 指标、校验失败率告警；
> - 评估闭环是 AI 工程的"测试"，上线前必有测试集与阈值；
> - 安全三防线：SafeGuard 输入拦截、权限标签防越权检索、工具最小权限；
> - 成本四杠杆：模型分层、语义缓存、上下文预算、流式；
> - 12 条避坑按清单自查，2.0 迁移类问题优先。
