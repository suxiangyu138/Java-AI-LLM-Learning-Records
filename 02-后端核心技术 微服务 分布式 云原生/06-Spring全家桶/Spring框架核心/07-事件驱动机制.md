## 1. 观察者模式在 Spring 的实现

**事件驱动 = 观察者模式**（见 `Java面向对象/09` 模式速览）的 Spring 实现——发布者不关心谁在听，监听者不关心谁在发：

```text
传统直接调用：
OrderService → 发短信 → 发邮件 → 记账本 → 清缓存        （发布者认识所有下游，改一个全改）

事件驱动：
OrderService → publishEvent(OrderCreatedEvent)          （只认识事件总线）
                ↓ 事件总线（ApplicationEventMulticaster）
    → 短信监听器 → 邮件监听器 → 记账监听器 → 缓存监听器   （每个监听器独立，可增可减）
```

**三个角色**：

| 角色 | 职责 | Spring 对应 |
|------|------|------------|
| 事件（Event） | 携带数据的载体 | `ApplicationEvent` 或任意对象（Spring 4.2+ 无需继承） |
| 发布者（Publisher） | 发布事件，不关心结果 | `ApplicationEventPublisher.publishEvent()` |
| 监听者（Listener） | 订阅并响应 | `@EventListener` / `ApplicationListener` |

> 🎯 **核心要点**：事件的价值 = **发布者与监听者完全解耦**——新增"下单后要做的第 5 件事"只加一个监听器，OrderService 零改动。这是"开闭原则"的教科书实现。

## 2. 事件定义与发布

```java
// 事件定义（Spring 4.2+ 推荐：继承 ApplicationEvent 不是必须的，POJO 即可）
public record OrderCreatedEvent(Long orderId, String userId) { }

// 发布：注入 ApplicationEventPublisher（或 ApplicationContext）
@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public OrderService(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void createOrder(...) {
        Order order = save(...);
        publisher.publishEvent(new OrderCreatedEvent(order.getId(), order.getUserId()));
        // 发布后立即返回 —— 监听器同步执行完才回到这里（默认同步）
    }
}
```

**三种发布对象**（`publishEvent` 的重载行为）：

| 传入 | 行为 |
|------|------|
| 自定义事件对象 | 直接作为事件分发 |
| `ApplicationEvent` 子类 | 同上 |
| **普通对象**（Spring 4.2+） | 自动包装为 `PayloadApplicationEvent` |

> 💡 经典误区：事件对象**尽量不可变**（record 最合适）——多个监听器共享同一事件实例，可变事件会让监听器间"互相看到修改"。

## 3. @EventListener 注解驱动与异步事件

```java
@Component
public class OrderEventListeners {

    // 基础用法：方法参数即事件类型
    @EventListener
    public void onOrderCreated(OrderCreatedEvent event) {
        smsService.send(event.userId(), "订单已创建: " + event.orderId());
    }

    // 多事件：一个监听器处理多种事件
    @EventListener({OrderCreatedEvent.class, OrderPaidEvent.class})
    public void onOrderChanged(Object event) { ... }

    // 条件过滤：SpEL 表达式
    @EventListener(condition = "#event.amount > 1000")
    public void onBigOrder(OrderCreatedEvent event) { ... }

    // 返回新事件：自动重新发布（事件转换链）
    @EventListener
    public OrderPaidEvent onOrderCreated(OrderCreatedEvent event) {
        return new OrderPaidEvent(event.orderId());    // 自动再发布 OrderPaidEvent
    }
}
```

**异步事件**（关键细节：**代理与事务的坑**）：

```java
// ① 开启异步支持（缺一不可）
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean
    public ThreadPoolTaskExecutor appExecutor() {     // 自定义线程池（默认 SimpleAsyncTaskExecutor 不推荐）
        ThreadPoolTaskExecutor pool = new ThreadPoolTaskExecutor();
        pool.setCorePoolSize(4);
        pool.setMaxPoolSize(16);
        pool.setQueueCapacity(1000);
        pool.setThreadNamePrefix("event-");
        pool.initialize();
        return pool;
    }
}

// ② 监听方法加 @Async —— 走线程池异步执行
@Async("appExecutor")
@EventListener
public void onOrderCreated(OrderCreatedEvent event) {
    // 异步：发布方法立即返回，此处在线程池执行
}
```

> ⚠️ **异步事件的三连坑**：① `@Async` 与 `@EventListener` 在同一类 = **自调用失效**（@Async 也是 AOP 代理——拆两个类）；② 异步后**异常不再传播给发布者**（要自己记录）；③ 异步监听器**不保证顺序**（多监听器时）。

## 4. 事务事件：@TransactionalEventListener

**业务痛点**：事件监听器在事务**提交前**执行——如果监听器里有数据库操作，会参与还没提交的事务；更糟的是**事务回滚了，监听器的工作却已做**（如已发短信但订单其实没建成）。

```java
@Service
public class OrderService {
    @Transactional
    public void createOrder(...) {
        Order order = save(...);
        publisher.publishEvent(new OrderCreatedEvent(order.getId(), order.getUserId()));
        // 此刻事务还未提交 —— 事件已被同步监听器处理
    }
}
```

**@TransactionalEventListener 解决"事务完成后才响应"**：

```java
@Component
public class OrderEventListeners {

    // 默认：事务提交后执行（phase = AFTER_COMMIT）
    @TransactionalEventListener
    public void onOrderCreated(OrderCreatedEvent event) {
        // 事务已提交 —— 这里再发短信/发 MQ，不会因回滚误发
    }

    // 可选阶段
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)     // 提交后（默认）
    @TransactionalEventListener(phase = TransactionPhase.ROLLBACK)         // 回滚后
    @TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)    // 提交前
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMPLETION) // 无论成败
}
```

**关键行为**：

| 场景 | 行为 |
|------|------|
| 有事务且提交成功 | 提交后触发监听器 |
| 事务回滚 | **不触发**（AFTER_COMMIT 阶段）→ 避免"误发短信" |
| 无事务调用 | **默认不触发**（fallbackExecution=false）；要触发需 `fallbackExecution = true` |

> 🎯 **核心要点**：**发短信、发 MQ、写审计等"事务外动作"必须用 @TransactionalEventListener**——否则事务回滚后监听器已执行，造成"订单没了但短信发了"的经典事故。

## 5. 事件异常处理与传播

```java
// 同步事件：监听器抛异常会传播给发布者！
@Service
public class OrderService {
    public void createOrder(...) {
        // ...
        publisher.publishEvent(event);      // 若某同步监听器抛异常 → 这里抛出来 → 业务中断
    }
}
```

**同步事件的异常策略**：

| 策略 | 做法 | 适用 |
|------|------|------|
| 监听器内部 try-catch | 每个监听器自己兜住 | 监听器之间互不影响的默认姿势 |
| 发布者捕获 | 包住 publishEvent | 容忍"监听器失败不影响主流程" |
| 不处理 | 异常打断主流程 | 监听器失败 = 业务失败（如审计必须成功） |

```java
@Component
public class OrderEventListeners {
    @EventListener
    public void sendSms(OrderCreatedEvent event) {
        try {
            smsService.send(...);
        } catch (Exception e) {
            log.error("短信发送失败，不影响主流程", e);     // 监听器自治：失败不影响业务
        }
    }
}
```

**异步事件异常**：异常发生在线程池——**发布者永远看不到**；必须监听器内自行记录 + 告警，或线程池配 `UncaughtExceptionHandler`（见 `Java异常体系/07`）。

> 🎯 **核心要点**：事件监听的异常原则 = **"主流程不能因监听器失败而失败"**——默认监听器内自治（try-catch + 日志 + 告警/重试），只有"审计强一致"等极少数场景才让异常上抛。

## 6. 事件 vs 消息队列 vs 直接调用

| 维度 | 直接调用 | Spring 事件 | 消息队列（MQ） |
|------|:--------:|:-----------:|:--------------:|
| 解耦 | ❌ 强耦合 | ✅ 进程内解耦 | ✅ 跨进程解耦 |
| 同步/异步 | 同步 | 默认同步，可 @Async | 天然异步 |
| 可靠性 | — | 无持久化、无重试 | **持久化 + 重试 + 死信** |
| 跨服务 | ❌ | ❌ 仅同进程 | ✅ |
| 顺序保证 | ✅ | ✅（同步时） | 需配置 |
| 复杂度 | 最低 | 低 | 高（依赖中间件） |
| 适用 | 强事务绑定 | **同进程内的解耦响应** | 跨服务、削峰、可靠性要求高 |

**选型判断**：

```text
同一进程内、不需要可靠投递 → Spring 事件 ✅
需要事务提交后才响应       → @TransactionalEventListener ✅
跨服务 / 需要重试与持久化   → MQ（RabbitMQ/Kafka，见 02 层中间件系统）
```

> 🎯 **核心要点**：**Spring 事件是"进程内的轻量 MQ"**——同服务模块间解耦（订单 → 短信/邮件/缓存）用它，跨服务可靠通信才上 MQ。用错场景（拿事件做跨服务）是常见架构错误。
