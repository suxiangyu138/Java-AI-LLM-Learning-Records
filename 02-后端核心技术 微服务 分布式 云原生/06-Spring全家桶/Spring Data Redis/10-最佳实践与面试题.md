## 2. 缓存与数据库一致性方案

### 2.1 四类经典方案对比

| 方案 | 做法 | 一致性 | 并发风险 | 适用 |
|------|------|:---:|---------|------|
| Cache Aside（旁路） | 读：先缓存后 DB；写：先 DB 后删缓存 | 弱（最终一致） | 删缓存与写库竞态 | **默认首选** |
| 先更库后更缓存 | 写：DB + 缓存同时更新 | 弱 | 双写不一致 | 低并发 |
| Read/Write Through | 缓存层代理 DB 读写 | 中 | 实现复杂 | 框架集成场景 |
| Write Behind（异步） | 只写缓存，异步落库 | 最终 | 宕机丢数据 | 高写低读场景 |

### 2.2 Cache Aside 的删缓存姿势（重点）

```text
更新流程（标准 Cache Aside）：
  1. 更新 DB
  2. 删除缓存（延迟双删或订阅 binlog）
```

**为什么"更新后删缓存"而不是"更新后写缓存"：** 写缓存无法保证与 DB 完全同步（并发写序），删缓存让下次读回源，天然收敛到最终一致。

**经典竞态与解法：**

```text
竞态：线程A 读缓存未命中 → 查库旧值 → 写缓存
      线程B 更新 DB → 删缓存
      结果：缓存里残留旧值（脏读）
解法①（延迟双删）：B 删缓存后 sleep(100ms) 再删一次
解法②（binlog 订阅）：Canal 订阅 binlog → 异步删缓存（可靠且解耦）
解法③（版本号）：缓存带 DB 版本，读时校验
```

> 🎯 **面试标准答法**：主推 Cache Aside + 删除缓存；高要求场景上延迟双删或 Canal 订阅；再往上就是"缓存版本号/时间戳"语义——**删比写可靠**是核心结论。

### 2.3 三大难题注解层应对（承接 06 篇）

| 难题 | 注解/配置手段 | 代码层补充 |
|------|--------------|-----------|
| 穿透 | `unless="#result==null"` + 短 TTL 空缓存 | 布隆过滤器 |
| 击穿 | `sync=true` | 单飞锁/本地缓存 |
| 雪崩 | TTL 差异化 + 抖动 | 多级缓存（Caffeine） |

## 3. key 设计与命名规范

### 3.1 命名模板

```text
业务域:对象:标识[:子标识]
例：user:profile:1001        order:detail:20260807001
    counter:visit:20260807   stock:sku:10086
```

| 规范 | 说明 |
|------|------|
| 冒号分层 | `:` 分隔，天然形成层级，SCAN 可分段 |
| 业务前缀 | 第一段是业务域，多业务隔离 |
| 有界长度 | key 总长控制（几百字节内），避免大 key |
| 可过期后缀 | 日期型 key 带日期（`counter:visit:20260807`），自然过期可清 |
| 禁止无意义前缀 | `cache:` 全局共用 → 无法按业务排查 |

### 3.2 与 Spring 侧的对应

```text
@Cacheable(cacheNames="user") + key="#id"   →  cache:user::1001   （06 篇）
StringRedisTemplate 手动 key               →  user:profile:1001
@RedisHash("user") + @Id=1001              →  user:1001（+ 索引 user:name:*）
```

> 💡 三个体系（Cache 前缀 `cache:`、手动 key、Repository hash key）**命名空间互不冲突但要统一规划**——同语义数据避免多套 key 并存（例如"用户信息"既有 `cache:user::` 又有 `user:profile:` 两套，就是设计债）。

## 4. 生产故障排查手册

### 4.1 故障分类速查

| 故障现象 | 优先排查链 |
|---------|-----------|
| 缓存全是乱码 | 序列化器检查（02 篇第 8 节流程） |
| 接口偶尔超时 | 命令级观测 → 慢命令 → bigkeys → 阻塞命令 |
| 连接数飙升 | 手写 getConnection 泄漏 / 池配置 |
| 内存持续增长 | TTL 未设 / key 泄漏 / 大 value |
| 数据不一致 | 双写方案竞态 / 延迟双删失效 |
| 切换后大面积报错 | 拓扑刷新未开 / 重定向超限（09 篇） |
| 消息丢失 | Pub/Sub 误用（08 篇可靠性边界） |
| @Cacheable 不生效 | @EnableCaching 未开 / 自调用绕过代理 |

### 4.2 排查工具链

```bash
redis-cli INFO keyspace              # 各库 key 数与过期情况
redis-cli --scan --pattern 'user:*'  # 分段扫描（禁 KEYS）
redis-cli SLOWLOG GET 10             # 慢命令
redis-cli --bigkeys                  # 大 key（负载低时执行）
redis-cli MEMORY USAGE user:1001     # 单 key 内存
redis-cli XINFO STREAM stream:orders # 消息积压
```

**标准排查流程五步：**

```text
① 看指标：命令耗时/错误率/连接数（可观测先行）
② 看慢日志：定位最慢命令与 key
③ 看大 key：bigkeys + MEMORY USAGE
④ 复现与实验：本地压测 / 灰度开关对比
⑤ 修与验证：改配置/代码 → 指标回落 → 复盘
```

## 5. 面试高频 15 问

**基础层：**

**Q1：RedisTemplate 为什么线程安全？**
模板无共享可变状态，通过回调模型在每次执行时"借连接→执行→归还"（ThreadLocal 绑定），连接生命周期由 ConnectionFactory 管理。（01 篇）

**Q2：为什么默认序列化是坑？怎么配？**
默认 JDK：乱码不可读、字段变更即反序列化失败、体积 2-4 倍。生产 key 用 String、value 用 JSON（Generic 系列带 @class 多态安全）。（02 篇）

**Q3：StringRedisTemplate 与 RedisTemplate 区别？**
前者固定 String 序列化，专用于字符串/计数/锁；后者可自定义四槽位序列化，存对象。两者同 key 混写会互相覆盖。（04 篇）

**Q4：setIfAbsent 与"setnx + expire"区别？**
setIfAbsent（SET NX PX）是单条原子命令；分两步存在崩溃窗口（锁永不过期）。分布式锁三件套：原子加锁、原子续期（脚本）、原子释放（脚本比对 owner）。（03/04 篇）

**Q5：管道与事务的区别？**
管道=传输层合并减少 RTT，无原子性；事务=MULTI/EXEC 执行层原子；Lua 兼具两者。Redis 4.x 起 Lettuce 下管道与事务互斥。（05 篇）

**Q6：MULTI 里 get 为什么返回 null？如何事务内判断？**
MULTI 队列期命令不执行；判断用 WATCH 乐观锁（EXEC 返回 null 表示冲突需重试）。（05 篇）

**缓存层：**

**Q7：@Cacheable 的 unless 与 condition 区别？**
condition 方法调用前评估（决定走不走缓存），unless 返回后评估（引用 #result 决定缓存否）。防穿透用 unless=null。（06 篇）

**Q8：缓存穿透/击穿/雪崩的注解层与代码层方案？**
穿透=unless+空值短缓存+布隆；击穿=sync 单飞；雪崩=TTL 抖动+多级缓存。（06/10 篇）

**Q9：缓存与 DB 一致性方案？为什么删缓存不更新缓存？**
Cache Aside + 删缓存；"删"让下次读回源收敛，更新缓存有写序竞态。进阶：延迟双删、Canal binlog 订阅。（10 篇）

**Q10：RedisCache 4.x 的 evict/clear 有什么变化？**
4.0 起非阻塞：单 key 走 DEL、清空改 SCAN 分批（旧版 KEYS 全扫阻塞）；4.1 resetCaches() 对专用缓存实例一次 FLUSHDB。（06 篇）

**消息层：**

**Q11：Pub/Sub 与 Stream 怎么选？**
广播+可丢→Pub/Sub；持久+消费组+确认+回放→Stream。可靠投递、离线消费、ACK 是 Stream 的分水岭能力。（08 篇）

**Q12：@RedisListener 是什么？**
Spring Data 2026.0.0 注解式 Pub/Sub 监听：@EnableRedisListeners 激活，@RedisListener(topic, consumes="application/json") 按 MIME 自动选转换器（Jackson/Kotlin/Gson 自动注册）。（08 篇）

**Q13：Stream 消费可靠性怎么保证？**
消费成功才 XACK；失败不 ACK 留 pending 可重投；重试 3 次进死信 stream + 告警；消费逻辑幂等（业务唯一 ID）。（08 篇）

**进阶层：**

**Q14：集群模式下什么会报错？拓扑刷新怎么配？**
多 key 命令（MGET/事务/Lua）要求同 slot，否则拒绝——用 {tag} 哈希标签。集群扩容/切换后需拓扑刷新（Lettuce 自适应刷新），否则大量 MOVED 与超时。（09 篇）

**Q15：Redis 8.x 的新命令在 Spring Data Redis 里怎么用？**
Redis 8.0：HGETDEL/HGETEX/HSETEX（4.0 引入，hashOps.getAndDelete/getAndExpire/set+ttl）；Redis 8.4：条件 SET/DEL（2026.0.0 引入，valueOps.set(key, v, spec -> spec.ifEquals().value(expected))），一次往返消除竞态。（03 篇）

## 6. 版本特性速查（2026）

| 版本线 | 关键能力 | 本体系章节 |
|--------|---------|:---:|
| Spring Data Redis 4.0.x（Spring Boot 4.0） | JSpecify 空值注解、Redis 8.0 新 hash 命令、Jackson 3 序列化器新命名、RedisCache 非阻塞 evict | 02/03/06 |
| Spring Data Redis 4.1.x / 2026.0.0（Spring Boot 4.1） | @RedisListener 注解监听、Redis 8.4 条件 SET/DEL、RedisMessageSendingTemplate、RedisCache.resetCaches() FLUSHDB 优化 | 03/06/08 |
| Redis 8.0 | HGETDEL / HGETEX / HSETEX | 03 |
| Redis 8.4 | 值级条件 SET / DEL | 03 |

> 💡 **迁移提醒**：Spring Boot 3.x → 4.x 时，Jackson 2 序列化器类（GenericJackson2JsonRedisSerializer）deprecated，新代码用 GenericJacksonJsonRedisSerializer（Jackson 3）；若保留 Jackson 2 依赖仍可用旧类，但不可混传 ObjectMapper。

> 🎯 **核心要点**：最佳实践=前面九篇的公约数（原子性、序列化、TTL、可观测、可靠性）；面试=理解机制而非背 API——能讲出"为什么删缓存比写缓存可靠""为什么事务里读不到值""为什么集群要同 slot"，比背 20 个 API 更能证明水平。
