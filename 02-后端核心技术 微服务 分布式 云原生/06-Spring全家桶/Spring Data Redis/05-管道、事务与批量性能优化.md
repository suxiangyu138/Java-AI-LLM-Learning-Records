# 05 管道、事务与批量性能优化

> 一次网络往返能做多少事？管道（Pipeline）把 N 条命令压进一次 RTT；事务（multi/exec）给命令套上原子语义；watch 则提供乐观锁——本模块讲透三者的语义、实现、约束与性能实测对比

## 1. 三者的语义与适用边界

| 维度 | 管道 Pipeline | 事务 MULTI/EXEC | Lua 脚本 |
|------|:---:|:---:|:---:|
| 减少 RTT | ✅ 一条网络往返 | ✅ 批量 EXEC 一次提交 | ✅ 一条 EVAL |
| 原子性 | ❌ 命令间可插入其它客户端命令 | ✅ EXEC 内整体原子 | ✅ 脚本内整体原子 |
| 命令间可见性 | 互相不可见（立即发出） | 队列内不执行，EXEC 时统一执行 | 脚本内顺序可见 |
| 中途失败处理 | 其余命令照常执行 | 运行时错误不回滚（入队错误则整体拒绝） | call 出错终止脚本 |
| 典型用途 | 批量写入/预热/批量删除 | 强一致批量 + 条件校验 | 复杂原子业务逻辑 |
| 实现依赖 | 客户端侧（驱动聚合发送） | 服务端队列（watch 参与） | 服务端脚本引擎 |

**一句话选型：**
- 只要"少几次往返、不在乎原子" → **管道**；
- 要"一批命令要么全成功要么都不执行 + 并发校验" → **事务 + watch**；
- 要"读-判断-写"的复杂原子逻辑 → **Lua 脚本**（04 篇）。

> 🎯 **最容易混淆的点**：管道 ≠ 事务。管道只做"传输层合并"，命令间没有原子性；事务才是"执行层原子"。管道里塞命令、事务里排队命令，语义完全不同。

## 2. 管道：executePipelined 全解

### 2.1 基础用法

```java
@Resource
private RedisTemplate<String, Object> redisTemplate;

public void batchInit() {
    // 回调内所有写操作被聚合，一次 RTT 发送给 Redis
    List<Object> results = redisTemplate.executePipelined((RedisCallback<Object>) connection -> {
        for (int i = 0; i < 1000; i++) {
            connection.set(("cache:item:" + i).getBytes(), ("v" + i).getBytes());
        }
        return null;
    });
}
```

**要点：**
- 回调内必须使用 `connection` 的原生命令（底层字节级 API），不能嵌套 `redisTemplate.opsForXxx()`（会死锁/破坏管道聚合）；
- 返回的 `List<Object>` 与命令一一对应（自动按 RedisTemplate 序列化器解码结果）；
- 回调内的命令**不会立即返回结果**，全部执行完统一返回。

### 2.2 与序列化协同

```java
// 回调里手动序列化（推荐：字节 API 与模板序列化器一致）
StringRedisSerializer str = StringRedisSerializer.UTF_8;

List<Object> results = stringRedisTemplate.executePipelined((RedisCallback<Object>) conn -> {
    for (String sku : skuList) {
        byte[] key = str.serialize("stock:" + sku);
        byte[] qty = str.serialize(queryStock(sku));
        conn.set(key, qty);
    }
    return null;
});
```

### 2.3 管道能做什么

| 场景 | 管道收益 |
|------|---------|
| 缓存预热 / 批量初始化 | 1000 条写入 = 1 次往返 |
| 批量删除（删除前按模式查 key） | SCAN + DEL 合并 |
| 批量查询（mget 不够灵活时） | N 次读 = 1 次往返 |
| 批量写日志/埋点（可容忍部分失败） | 大量小命令聚合 |

## 3. 事务：@Transactional 与 RedisTemplate 绑定

### 3.1 开启事务支持

```java
@Bean
public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory factory) {
    RedisTemplate<String, Object> template = new RedisTemplate<>();
    template.setConnectionFactory(factory);
    template.setEnableTransactionSupport(true);   // 关键：绑定 Spring 事务
    // ...序列化配置
    return template;
}
```

### 3.2 事务语义：MULTI 排队

开启 `setEnableTransactionSupport(true)` 后，Spring 会做两件事：

1. 在 `@Transactional` 方法执行前，把当前连接绑定到线程（ThreadLocal），并发送 `MULTI`；
2. 方法内所有 Redis 命令**进入队列不立即执行**（返回 null 或排队标记），方法提交时统一 `EXEC`。

```java
@Transactional
public void transfer(String from, String to, long amount) {
    ValueOperations<String, Object> ops = redisTemplate.opsForValue();
    // 命令进 MULTI 队列，此处 get 返回 null（未执行）
    Object fromBal = ops.get("account:" + from);
    Object toBal = ops.get("account:" + to);
    ops.increment("account:" + from, -amount);
    ops.increment("account:" + to, amount);
    // 方法返回时 EXEC 一次性执行
}
```

> ⚠️ **最大陷阱**：事务内 `get` 读到的是 null——命令在排队期不执行，**不能"先读再判断"**。事务内读取必须用 `watch`（乐观锁）配合重试，或把读逻辑放事务外。

### 3.3 事务与 Spring 数据事务的区别

| 维度 | Spring 数据事务（@Transactional + JDBC/JPA） | Redis 事务（同上注解 + RedisTemplate） |
|------|:---:|:---:|
| 回滚 | 失败回滚全部变更 | **EXEC 执行后不回滚**（运行时错误仅跳过该命令） |
| 隔离 | 数据库隔离级别 | 无隔离级别，MULTI 期间其它客户端照常读写 |
| 用途 | 数据库一致 | 批量原子提交 |

> 💡 **重要认知**：Redis 事务没有"回滚"概念——EXEC 后部分命令出错，已成功的命令生效（原子性 ≠ 回滚）。需要整体回滚语义必须用 Lua 脚本在业务侧实现"补偿逻辑"。

## 4. watch 乐观锁：CAS 语义

`watch` 让事务具备"先比较后提交"的乐观锁能力：

```java
public boolean updateIfUnchanged(String key, String expected, String newValue) {
    return redisTemplate.execute((RedisCallback<Boolean>) conn -> {
        conn.watch(key.getBytes());                    // 1. 监视 key
        byte[] current = conn.get(key.getBytes());     // 2. 读当前值
        if (!Arrays.equals(current, expected.getBytes())) {
            conn.unwatch();
            return false;                              // 3a. 值已变，放弃
        }
        conn.multi();                                  // 3b. 值未变，开启事务
        conn.set(key.getBytes(), newValue.getBytes());
        List<Object> results = conn.exec();            // 4. 提交；若期间 key 被改，exec 返回 null
        return results != null;                        // null = 冲突，调用方重试
    });
}
```

**执行语义：**

```text
WATCH key → GET 校验 → MULTI → QUEUE 命令 → EXEC
              │                          │
              └ 期间 key 被其它客户端改了 ─┘
                         EXEC 返回 null（事务整体放弃）
```

| 特点 | 说明 |
|------|------|
| 乐观锁 | 不阻塞写者，冲突靠"放弃重试" |
| 冲突检测 | EXEC 返回 null 表示期间有 key 被修改 |
| 竞态窗口 | 从 WATCH 到 EXEC 之间的窗口被监控 |
| 适用 | 低冲突率的"读-改-写"（如库存扣减） |
| 不适用 | 高冲突率（频繁失败重试）→ 换 Lua 脚本 |

## 5. 性能对比实测

**典型基准（本地 Redis，1000 条 SET）：**

| 方案 | 往返次数 | 相对耗时 | 原子性 |
|------|:---:|:---:|:---:|
| 逐条 SET | 1000 | 1x（基准） | - |
| 管道 | 1 | **约 0.05x（节省 90%+ 时间）** | ❌ |
| 事务 MULTI/EXEC | 1 + 排队开销 | 略高于管道 | ✅ |
| Lua 脚本 | 1 | 与管道相近 | ✅ |

> 💡 **实测结论**：网络往返（RTT）是 Redis 客户端性能的第一瓶颈。本地机器逐条 1000 次约 50ms 级，管道压缩到 1-2ms。远程/跨机房场景差距更悬殊（每加一次往返就加一次网络延迟）。**批量写一律管道或脚本，逐条写是性能浪费。**

**写入量更大时（10 万+）：** 分片批量（每管道 1000-2000 条），避免单次管道过大导致服务端输出缓冲积压；并关注 Redis 输出缓冲区限制（client-output-buffer-limit）。

## 6. 4.x 约束与常见坑

### 6.1 4.x 已知约束（3.x 升级带来的语义收紧）

| 约束 | 说明 | 影响 |
|------|------|------|
| **管道与事务互斥** | 同一连接上不能既开管道又开事务（驱动层拒绝） | 先想清楚语义再选 API |
| 服务端/连接级命令禁用 | `CLIENT SETNAME`、`PING` 等连接命令不可进管道/事务 | 连接命令走普通 execute |
| 事务内读为空 | MULTI 排队期 get 返回 null | 读放事务外或用 watch |

### 6.2 常见坑速查

| 坑 | 现象 | 处理 |
|----|------|------|
| 回调内用 `redisTemplate.opsForXxx()` | 嵌套调用取连接，死锁或管道失效 | 回调内一律用 `connection` 原生 API |
| 事务方法内 get 判断 | 恒为 null，逻辑错乱 | watch + 重试 / 读放事务外 |
| 忘记 `setEnableTransactionSupport(true)` | @Transactional 不生效，命令立即执行 | 检查模板配置 |
| 事务内捕获异常继续执行 | 出错命令被跳过，其余生效（无回滚） | 校验前置；需要回滚语义用 Lua |
| 管道结果顺序错位 | 回调内条件分支导致命令数不确定 | 保持回调命令数与结果一一对应 |
| exec 返回 null 却当成功 | 冲突被吞 | 判空并重试（循环最多 N 次） |

> 🎯 **核心要点**：性能优化的第一要义是减少往返——管道用于"量大不要求原子"的写入，事务用于"原子 + 校验"，Lua 用于"复杂原子逻辑"；三者不可混用（尤其管道与事务互斥）。事务内读不到值是最大的语义陷阱，`watch` 是唯一的事务内条件判断正道。判空 exec 结果、判空管道回调——空指针皆因语义没吃透。
