## 1. 三种部署形态与连接工厂对应

| 部署形态 | 连接工厂配置 | 路由/高可用能力 | Spring 侧行为 |
|---------|------------|----------------|--------------|
| 单机 Standalone | `RedisStandaloneConfiguration` | 无 | 直连 |
| 哨兵 Sentinel | `RedisSentinelConfiguration` | 主从自动切换，客户端拿到新 master | 断线重连 + 拓扑感知 |
| 集群 Cluster | `RedisClusterConfiguration` | 分片路由 + 槽位重定向 + 从节点读 | 节点自动发现 |

```text
RedisClusterConfiguration / RedisSentinelConfiguration / RedisStandaloneConfiguration
                        │  都实现 RedisConfiguration
                        ▼
        LettuceConnectionFactory / JedisConnectionFactory（分别实例化）
```

**Spring Boot 4.x 三态配置：**

```yaml
# 单机
spring.data.redis.host: localhost
spring.data.redis.port: 6379

# 哨兵
spring.data.redis.sentinel.master: mymaster
spring.data.redis.sentinel.nodes: 10.0.0.1:26379,10.0.0.2:26379,10.0.0.3:26379

# 集群
spring.data.redis.cluster.nodes: 10.0.0.1:6379,10.0.0.2:6379,10.0.0.3:6379
spring.data.redis.cluster.max-redirects: 3
```

> ⚠️ **注意**：哨兵与集群配置二选一（`RedisSentinelConfiguration` 与 `RedisClusterConfiguration` 互斥），同时配置会按优先级只生效其一（Boot 中集群优先）。

## 2. 哨兵模式：高可用接入

**哨兵职责**：监控主节点、故障时自动把从节点提升为新 master、通知客户端。

```java
// 编程式配置
RedisSentinelConfiguration sentinelConfig = new RedisSentinelConfiguration()
        .master("mymaster")                                    // 监控的主节点逻辑名
        .sentinel("10.0.0.1", 26379)
        .sentinel("10.0.0.2", 26379)
        .sentinel("10.0.0.3", 26379);
LettuceConnectionFactory factory = new LettuceConnectionFactory(sentinelConfig);
```

**Spring Data Redis 在哨兵态的关键行为：**

| 行为 | 说明 |
|------|------|
| master 发现 | 连接时向哨兵查询当前 master，只连 master 读写 |
| 主从切换 | 哨兵通知新 master 后，客户端**自动重连**新主 |
| 只读从节点 | 手动配置 `setReadFrom(ReadFrom.REPLICA)` 才把读分流到从 |
| 故障窗口 | 切换期间（数秒）写入可能失败/超时 |

> 💡 **默认策略**：读写都走 master（`ReadFrom.MASTER`）。生产主从架构若想读从库降载，用 Lettuce `setReadFrom(ReadFrom.REPLICA_PREFERRED)` 并接受读延迟与可能读到旧值。

## 3. 集群模式：路由与拓扑刷新

### 3.1 槽位路由

```text
Redis Cluster = 16384 个 hash slot，按 CRC16(key) % 16384 分配到节点

Spring Data Redis 集群工厂：
  1. 启动时从任一节点拉取集群拓扑（nodes + slots 分布）
  2. 命令发出前按 key 计算 slot → 路由到对应节点
  3. 节点返回 -MOVED/-ASK 重定向错误时：
       - 若在客户端拓扑中：更新拓扑缓存，重发命令
       - 超过 max-redirects 次：抛 RedisSystemException
```

```java
RedisClusterConfiguration clusterConfig = new RedisClusterConfiguration()
        .clusterNode("10.0.0.1", 6379)
        .clusterNode("10.0.0.2", 6379)
        .clusterNode("10.0.0.3", 6379);
clusterConfig.setMaxRedirects(3);       // 重定向上限
LettuceConnectionFactory factory = new LettuceConnectionFactory(clusterConfig);
```

### 3.2 拓扑刷新（集群节点的"动态成员"）

集群扩容/缩容/故障后，客户端本地拓扑会过期。Lettuce 支持自动刷新：

| 刷新方式 | 配置 | 时机 |
|---------|------|------|
| 手动刷新 | `clusterConnection.refreshClusterView()` | 运维脚本/定时 |
| 自适应刷新（推荐） | `ClusterTopologyRefreshOptions` | 命令失败/重定向时按需刷新 |
| 周期性刷新 | `refreshPeriod(Duration)` | 固定间隔 |

```java
LettuceClientConfiguration clientConfig = LettuceClientConfiguration.builder()
        .clientOptions(ClusterClientOptions.builder()
                .topologyRefreshOptions(ClusterTopologyRefreshOptions.builder()
                        .enablePeriodicRefresh(Duration.ofSeconds(60))     // 周期刷新
                        .enableAllAdaptiveRefreshTriggers()                // 失败时自适应刷新
                        .build())
                .build())
        .build();
```

> ⚠️ **生产事故源**：集群扩容/故障切换后**未开拓扑刷新** → 客户端仍按旧拓扑路由 → 大量 `MOVED` 重定向与超时。开启自适应刷新后，切换期间的偶发错误会自动自愈。

### 3.3 集群下的 key 设计纪律

- 多 key 操作（MGET、事务、Lua）的 key 必须**同 slot**：`{user:1001}:cart` 花括号内部分参与 CRC16；
- `opsForXxx` 单 key 命令不受影响；
- 跨 slot 的管道/事务直接失败（服务端拒绝）——**这是集群与单机最大的行为差异**。

## 4. 两种驱动在集群下的差异

| 维度 | Lettuce（默认） | Jedis |
|------|----------------|-------|
| 拓扑感知 | 原生 ClusterTopologyRefreshOptions | 需自行轮询/手动刷新 |
| 重定向处理 | 内置 -MOVED/-ASK 自动重试（max-redirects 内） | 支持，但重试逻辑较弱 |
| 从节点读 | `ReadFrom.REPLICA_PREFERRED` 等策略完整 | 需自定义 |
| 自适应刷新 | ✅ | ❌（手动） |
| 主从切换感知 | 哨兵通知 + 自动重连 | 依赖 pool 重建 |

> 🎯 **结论**：集群/哨兵场景**优先 Lettuce**——拓扑刷新、重定向重试、从节点读策略是生产刚需，Lettuce 原生完备，Jedis 需要大量手工补丁。

## 5. Micrometer 可观测：命令级指标与追踪

### 5.1 开启观测（Spring Boot 4.x 内置集成）

```yaml
management:
  tracing:
    sampling:
      probability: 1.0        # 全量采样（压测环境可 0.1）
  observations:
    key-values:
      application: demo-app
```

```java
// 手动给工厂挂观测回调（Boot 自动配置时已挂好）
RedisConnectionFactory observed = new ObservableRedisConnectionFactory(factory);
```

**观测到的内容（命令级）：**

| 观测项 | 示例指标 | 用途 |
|--------|---------|------|
| 命令耗时 | `redis.command.duration` | 慢命令定位 |
| 命令错误 | `redis.command.error` | 异常率监控 |
| 连接状态 | `redis.connection.*` | 连接池/共享连接健康 |
| 命令名称 | `redis.command`（command=GET/SET/...） | 命令分布统计 |

### 5.2 追踪链路（Micrometer Tracing）

开启后 Redis 命令自动进入 OpenTelemetry/Jaeger 链路：**每条命令带 span（`redis.command`），span 含 connection 与远程地址**——从"接口慢"一键下钻到"哪条 Redis 命令慢"。

```text
HTTP 接口 span
└── redis.command span（command=GET key=cache:user:1001 duration=120ms）
```

> 💡 **生产价值**：没有命令级观测时，Redis 慢只能猜；挂上观测后，慢查询、热点 key、连接异常全部有数据说话。2026 年面试问"Redis 性能怎么排查"，答"命令级指标 + 追踪下钻 + bigkeys/慢日志对比"。

### 5.3 配套：慢日志与 bigkeys

```bash
redis-cli CONFIG SET slowlog-log-slower-than 10000   # >10ms 记录
redis-cli SLOWLOG GET 10                              # 看慢命令
redis-cli --bigkeys                                   # 大 key 扫描（注意负载）
```

## 6. 故障切换下的应用行为与重试策略

### 6.1 切换瞬间会发生什么

```text
哨兵故障切换（failover）期间：
  ├── 旧 master 失联：客户端命令超时/连接拒绝
  ├── 新 master 产生（数秒）：客户端重连新主
  └── 恢复后：命令正常（读从库可能短暂读到旧数据）
```

**应用侧现象**：超时异常（`RedisConnectionFailureException`）、短暂 5xx、重试后自愈。

### 6.2 重试策略设计

| 层级 | 策略 | 实现 |
|------|------|------|
| 命令级重试 | 超时/连接失败重试 2-3 次，退避 50-200ms | Lettuce `SocketOptions`/自定义 `RetryPolicy` |
| 业务级重试 | 幂等接口 + 重试队列 | 失败进 MQ/延迟任务 |
| 兜底降级 | 缓存不可用 → 直连 DB 或降级响应 | 开关/熔断（Sentinel） |

> ⚠️ **重试的原子性警告**：**写命令重试要谨慎**——"SET 成功但响应丢失"时重发会导致重复写；写操作重试前提是**幂等**（带业务 ID 或条件写）。读命令重试安全。

## 7. 生产检查清单

- [ ] 集群已开启拓扑自适应刷新（或确认扩容流程含刷新步骤）；
- [ ] max-redirects 配置合理（默认 3，重定向频繁则调大）；
- [ ] 多 key 操作全部同 slot（`{tag}` 哈希标签）验证过；
- [ ] 哨兵切换时间窗口有监控告警（切换=秒级不可用）；
- [ ] 读写分离（若启用 REPLICA 读）已确认可接受读延迟；
- [ ] 命令级观测（Micrometer）已开启，慢命令有阈值告警；
- [ ] 写命令重试均为幂等场景；
- [ ] 集群故障演练（kill master / 缩容）已跑过，客户端能自愈。

> 🎯 **核心要点**：三种形态的差异全在"路由与拓扑"——哨兵管"谁是 master"、集群管"key 在哪个节点"、观测管"命令到底发生了什么"。生产接入的三大纪律：**集群必开拓扑刷新、跨 slot 操作严格禁止（除非同 tag）、故障切换靠可观测兜底**。
