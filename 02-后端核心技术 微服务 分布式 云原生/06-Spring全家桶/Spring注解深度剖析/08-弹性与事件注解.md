# 08 弹性与事件注解

> Spring Framework 7 把重试与并发限制收编进核心：@Retryable/@ConcurrencyLimit/@Timeout/@Recover 构成 Resilience 注解家族，@EnableResilientMethods 取代外部依赖 spring-retry。事件侧 @EventListener/@TransactionalEventListener 是解耦业务的标准姿势。本篇覆盖新注解的完整语义、与旧 spring-retry 的行为差异、以及事件注解的事务边界细节

## 1. Resilience 入核：动机与激活方式

Spring 7 将重试/并发限制能力从独立项目 spring-retry 收编进 spring-core/context 的 Resilience 模块，激活注解从 `@EnableRetry` 更名为 **`@EnableResilientMethods`**（@Import 模式，02 篇机制）。动机两条：虚拟线程让"无池上限的并发失控"成为普遍风险（@ConcurrencyLimit 应运而生）；重试已成为微服务时代的基础设施而非可选依赖，框架应收编。

与 spring-retry 的关系：spring-retry 项目仍独立演进（提供 RetryTemplate 编程式 API 与批量重试等高级能力），Spring 7 的注解层实现是其语义子集 + 增强——**响应式返回类型支持**（@Retryable 标注返回 Mono/Flux 的方法时经 Reactor 的 retryWhen 装饰，spring-retry 注解不支持）。混合使用时注意别同时引入两套 @Retryable 注解（包不同、行为不同，import 混乱是升级期事故源）。

## 2. @Retryable / @Backoff / @Recover

```java
@Retryable(maxAttempts = 3, backoff = @Backoff(delay = 2000, multiplier = 2, maxDelay = 30000),
           include = RemoteAccessException.class)
public String callRemote() { ... }

@Recover
public String remoteFallback(RemoteAccessException e) { return "降级结果"; }
```

属性语义：`maxAttempts`（总尝试次数含首次）；`include/exclude`（按异常类型白名单/黑名单，子类异常默认匹配）；`backoff = @Backoff(delay/multiplier/maxDelay/random)`（指数退避，乘数 2 时 2s→4s→8s 封顶 maxDelay——**退避是防雪崩的关键**，重试风暴会放大下游故障）；`maxAttemptsExpression`（SpEL 动态次数）。

**@Recover** 是耗尽重试后的兜底方法：签名必须与原方法兼容（同返回类型 + 首个参数为异常类型），重试全部失败后调用。注意它是**同一类内**的兜底声明（代理机制要求经容器调用），且兜底方法自身执行失败会直接抛出。响应式场景的语义差异：@Retryable 标注返回 Mono/Flux 的方法时经 Reactor 的 `retryWhen(Retry.backoff(...))` 装饰——**退避发生在响应式流内部**（信号重订阅），而非阻塞线程 sleep；此时 @Recover 的降级语义不适用（流内异常走 onErrorResume 才是响应式惯用姿势）。同一个注解、两套执行模型——阻塞返回类型走 RetryTemplate、响应式返回类型走 Reactor，混用工程要按方法签名区分行为预期。

### 2.1 @Backoff 的退避细节

`@Backoff(delay = 1000, multiplier = 2, maxDelay = 10000)` 的退避序列是 1s → 2s → 4s → 8s → 10s（封顶）；`random = true` 在退避基础上加随机抖动（**分布式防雷群**的关键——多实例同时重试且退避完全相同时，重试风暴会二次打爆下游，抖动打散时间点）。两个工程认知：重试次数与退避时长是**爆炸式增长**（maxAttempts 3 + 指数退避 30s 封顶 = 最长阻塞分钟级），方法调用方的超时预算必须覆盖；`maxAttemptsExpression` 支持 SpEL 动态次数（配置中心调节重试策略的热开关）。

行为差异要点（7.0.2 起）：接口上标注 @Retryable **不再对实现类生效**（issue #36233）——注解必须落在实现类方法上，升级 spring-retry 老项目时这是最先撞到的变化。同类失效模型依旧：自调用失效（代理拦截）。

## 3. @ConcurrencyLimit 与 @Timeout

**@ConcurrencyLimit(value = 20, policy = ThrottlePolicy.BLOCK)** 限制方法同时执行数——虚拟线程时代"池子不再挡并发"之后，这是保护下游的唯一闸门。两种策略的语义：`BLOCK` 超额调用**排队等待**（背压式，适合"慢点没关系但要成功"的场景）；`REJECT` 超额调用**立即拒绝**（快速失败，抛错或走 @Recover 兜底，适合"宁快勿堵"的接口）。属性还有 `timeout`（BLOCK 排队上限）与 SpEL 版 valueExpression。选型对照：下游有明确承载上限（数据库连接池、第三方 QPS 配额）时按限额配置 REJECT 快速失败；下游弹性大但瞬时洪峰会造成抖动时用 BLOCK 平滑削峰——限流的本质是"把超过承受能力的请求挡在门外或排队缓行"，两种策略只是缓行的耐心不同。

**@Timeout("2s")** 声明式切断超时调用：方法执行超过时长即中断（响应式返回类型走 timeout 操作符，阻塞返回类型走线程中断语义）。与 @Transactional 的 timeout 分工：@Transactional.timeout 管**事务**超时（连接资源保护），@Timeout 管**方法整体**超时（含非事务逻辑）。三注解可叠加：@Retryable + @Timeout + @ConcurrencyLimit 组合出"限并发 + 超时切断 + 退避重试"的完整弹性配置。

## 4. @EventListener 与 @TransactionalEventListener

**@EventListener** 让任意 @Bean 方法成为事件监听器（无需实现 ApplicationListener 接口，Spring 4.2 起）：泛型方法签名即事件类型声明（`@EventListener public void on(OrderCreatedEvent e)`），`condition` 属性 SpEL 过滤（`condition = "#event.total > 100"`），`classes` 声明监听类型，方法返回新对象时自动**发布为新事件**（事件链式流转）。@Order 控制同事件多监听器顺序，@Async 叠加让监听器异步执行（注意：@Async 在监听器上需代理生效，与 07 篇同模型）。

事件发布的入口是 `ApplicationEventPublisher`（注入即可用，`publishEvent(new OrderCreatedEvent(order))`）——Spring 4.2 起事件对象可以是**任意 POJO**（不强制继承 ApplicationEvent，框架自动包装为 PayloadApplicationEvent）。异步监听器的异常语义：监听器抛异常默认**传播回发布线程**（同步监听器会中断发布链）——`@Async` 异步化后异常不再回流发布方，必须给 @Async 配 AsyncUncaughtExceptionHandler（07 篇）或监听器内部自吞 + 告警，否则"监听失败"静默消失。泛型事件（`EntityCreatedEvent<User>`）Spring 也能按泛型精确分发（ResolvableType 支持），条件过滤优先用 `condition` SpEL 而非方法内 if——声明式语义让"哪些事件被处理"在方法签名与注解上一目了然。

**@TransactionalEventListener** 是事务边界的事件版本：监听器**在事务提交后才执行**（默认 phase = AFTER_COMMIT），另有 AFTER_ROLLBACK（失败补偿）、BEFORE_COMMIT（提交前最后检查）、AFTER_COMPLETION（无论成败）。这是"发消息/刷缓存/发通知"的正确时机——事务内监听器发消息可能"消息已发但事务回滚"（双写不一致），提交后监听则"提交成功才发"（配合 outbox 模式兜底消息丢失窗口）。`fallbackExecution = true` 让无事务上下文时监听器也执行（默认 false，无事务时不执行——测试环境踩坑点）。实现机制上它依赖 TransactionSynchronizationManager 的事务同步回调（06 篇 4.1 已述），所以它的"提交后执行"发生在**事务提交完成的瞬间、同一线程内**——不是异步消息，调用链仍同步阻塞；真异步需要监听器上再叠 @Async。

## 5. 迁移注意与面试题

1. **spring-retry → Resilience 迁移三件事**：换 import 包、@EnableRetry 改 @EnableResilientMethods、检查接口标注（#36233 行为变化，注解挪到实现类）；
2. **重试必须幂等**：@Retryable 标注的方法可能被执行多次，下游写操作必须幂等（幂等键/唯一约束）——重试注解与幂等设计是一对；同样的推理适用于 @ConcurrencyLimit 的 BLOCK 策略（排队后重复执行同一调用，调用方超时重试会叠加请求，服务端幂等兜底）。
3. **面试必答框架**：「@Retryable 与 spring-retry 的 RetryTemplate 什么关系？」——Spring 7 的注解实现内部仍委托 RetryTemplate 执行（阻塞场景），响应式场景经 Reactor retryWhen——框架收编的是注解与集成层，重试引擎复用既有成熟实现；「@TransactionalEventListener 为什么默认提交后执行？」——事务内发布有"回滚后消息已发"的不一致风险，提交后执行是事务一致性的安全默认；
4. **「@Recover 与 @TransactionalEventListener(AFTER_ROLLBACK) 怎么选？」**——作用域不同：@Recover 是"当前方法的失败降级"（重试耗尽后的替代路径，返回降级结果）；AFTER_ROLLBACK 监听是"事务回滚后的补偿"（跨方法的清理/告警，无返回语义）——方法级降级用 Recover，事务级补偿用事件监听；
5. **「@ConcurrencyLimit 与线程池 maxPoolSize 的区别？」**——线程池上限是**执行资源**约束（超过排队/拒绝），@ConcurrencyLimit 是**业务并发**约束（同一方法的语义并发上限，与执行线程无关）——虚拟线程时代线程池不再限制并发，业务级闸门必须由 @ConcurrencyLimit（或信号量）承担，这是它入核的根本原因。
