# 04 配置与属性注解

> 配置注解回答"Bean 怎么被创建、属性从哪来"：@Configuration 决定配置类是被代理还是纯工厂、@Bean 的七个属性控制创建细节、@Value 与 @ConfigurationProperties 是属性注入的两条路线（散点 vs 结构化）。理解 @Configuration 的 proxyBeanMethods 开关，就理解了配置类一切"诡异行为"的根源

## 1. @Configuration：full 与 lite 模式

`proxyBeanMethods` 属性是理解一切配置类行为的总开关：

- **true（full 模式，默认）**：配置类被 CGLIB 增强为子类代理。@Bean 方法间的调用会被拦截——方法体不再执行，而是**从容器返回已注册的单例**。于是 `@Bean A a() { return new A(b()); }` 里 `b()` 返回容器单例而非新建对象，依赖关系被 Spring 接管（A 依赖 B 可被容器感知、注入代理增强）；
- **false（lite 模式）**：无代理，@Bean 方法就是普通工厂方法，方法间调用每次新建对象。启动更快、无 CGLIB 开销，但"方法调用即依赖声明"失效。

选择规则：配置类内 @Bean 方法**互不调用**时用 lite（绝大多数据配置类如此，Spring 官方建议 `proxyBeanMethods = false` 为默认习惯）；需要"跨 @Bean 方法共享单例/声明依赖"时保留 full。full 模式的三个限制要记：配置类不能是 final、@Bean 方法不能是 private/final、静态 @Bean 方法不参与代理语义（静态方法无实例可代理，被调用即新对象）——违反前两条时 Spring 静默降级为 lite 语义或报错，行为差异即从此而来。

@Configuration 也是 @Component 派生链一员（会被扫描），且 full 模式类上标 @Lazy 时其 @Bean 方法全部惰性化——这些组合语义是排查"Bean 行为与预期不符"时的第二检查点。

## 2. @Bean 全属性

- `value/name`（别名）：Bean 名，默认方法名；
- `initMethod/destroyMethod`：生命周期回调（等价 XML 的 init-method/destroy-method；destroyMethod 默认推断 close/shutdown——**不想自动推断时显式设空串**）；
- `autowireCandidate`（默认 true）：false 时该 Bean 不参与按类型装配的候选（排除多候选歧义，@Qualifier 点名不受影响）；
- `@Primary/@DependsOn/@Scope/@Lazy/@Description` 等组合注解直接叠加在 @Bean 方法上（@Bean 方法上的注解经 ConfigurationClassPostProcessor 转译为 BeanDefinition 属性）。

一个机制要点：@Bean 方法在 lite 模式（或非 @Configuration 类中）产出的 Bean **不参与 CGLIB 增强**，@Scope 的 proxyMode、@Lazy 注入代理等增强行为受限——"@Bean 方法写在哪"决定了产物的增强能力，不只是代码组织问题。静态 @Bean 方法（static factory）在 full 模式配置类中**不会**被代理拦截，跨方法依赖需显式参数注入。

## 3. 作用域与装配期注解：@Scope / @Lazy / @Primary / @DependsOn

- **@Scope("singleton"/"prototype"/自定义)**：singleton 是默认；prototype 每次装配新建；`proxyMode = ScopedProxyMode.TARGET_CLASS` 生成作用域代理——**singleton Bean 注入 prototype Bean 的经典问题**（单例持有固定的原型实例）靠代理解决，每次方法调用走代理重新获取；
- **@Lazy**：单例 Bean 推迟到首次使用才实例化（解决启动慢/循环依赖/非必需组件延迟初始化）；Boot 4 有全局属性 `spring.main.lazy-initialization=true` 一键全惰性，但生产要警惕"错误推迟到运行时爆发"；
- **@Primary**：按类型装配多候选时的默认胜者（@Qualifier 点名优先级更高——05 篇详解）；
- **@DependsOn("beanB")**：显式声明初始化顺序，兜底"无依赖声明但有初始化时序要求"的场景（如先建连接池再建缓存管理器）。

作用域体系的外延：自定义作用域（`@Scope("tenant")` + 实现 Scope 接口 + 注册 `CustomScopeConfigurer`）是租户级/会话级 Bean 的扩展点——多租户场景"每租户一个连接池"即自定义作用域的典型用例；`@Scope(proxyMode = ScopedProxyMode.INTERFACES)`（接口代理）与 TARGET_CLASS（类代理）的选择取决于 Bean 是否基于接口注入。@Lazy 的组合语义：@Configuration 类级 @Lazy 传染其全部 @Bean 方法；@Lazy 标注注入点（构造器参数）则**该依赖**延迟注入——两者的作用对象不同，排查"Bean 没按预期初始化"时先确认 @Lazy 的落点。

## 4. 属性注入两条路线：@Value 与 @ConfigurationProperties

**@Value 双语法**：占位符 `${server.port:8080}`（Environment 解析，冒号后默认值）与 SpEL `#{...}`（表达式求值）。定位是**散点注入**：一两个值直接注字段/构造器参数。坑位：URL 含冒号要写 `${url:}` 空默认再拼接；SpEL 每次求值有成本，高频路径慎用；@Value 拿不到的类型转换错误在启动期报出（好事）。优先级链：@Value 解析走 Environment 的 PropertySource 链（命令行参数 > 系统属性 > 环境变量 > 配置文件 > 默认值），同一键多处定义时**越靠前的源胜出**——排查"配置没生效"时按这条链从前往后查覆盖关系，而不是只看 application.yml。

**@ConfigurationProperties(prefix = "app.pay")** 定位是**结构化绑定**：整块配置绑定到类（record 天然适配——构造器绑定即 record 规范构造器），配合 @Validated 做配置校验、`@ConfigurationPropertiesScan` 或 @EnableConfigurationProperties 注册（二选一：Scan 按包自动发现、Enable 显式点名——多个配置类时显式点名可读性更好）。关键语义：`value` 与 `prefix` 是 @AliasFor 别名；`ignoreUnknownFields`（默认 true，环境里多出的键忽略——收紧为 false 能在启动期暴露配置名拼错）；**@DefaultValue 注解标注的默认值不进 Environment**——用 `${}` 占位符读不到它，读取必须走绑定。路线选型：结构化配置（连接池/线程池/业务参数组）用 @ConfigurationProperties + record，散点开关用 @Value——两条路线混用不冲突，纪律在"一组配置只在一个地方声明"。

**@PropertySource("classpath:custom.properties")** 补充外部属性文件进 Environment（`factory` 属性支持自定义 PropertySourceFactory，如 YAML 文件加载）。

### 4.1 宽松绑定与构造绑定

@ConfigurationProperties 的绑定引擎有两个机制值得深挖：**宽松绑定（relaxed binding）**——`app.pay-timeout`（kebab）、`app.payTimeout`（camel）、`APP_PAYTIMEOUT`（环境变量）等价命中 `payTimeout` 字段，属性名风格不敏感；**构造绑定**——record 或 `@ConstructorBinding` 类走构造器绑定（不可变优先）。组合姿势：

```java
@ConfigurationProperties(prefix = "app.pay")
public record PayConfig(@NotBlank String channel, @Min(1) int timeoutSeconds) {}
```

record + @Validated 让配置**启动期校验**（非法配置直接启动失败而非运行期爆发）——这是 @ConfigurationProperties 相对 @Value 的核心优势之一（@Value 也能校验但无结构语义）。注意 `@DefaultValue`（注解上的默认值）**不进 Environment**：占位符 `${app.pay.timeout:0}` 读不到它，默认值只在绑定路径生效——两套默认值机制（@DefaultValue vs 占位符冒号）并存是配置体系的经典迷惑点，团队规范应二选一。环境变量映射规则同样要记：环境变量通过 `SystemEnvironmentPropertySource` 参与绑定，点号/中划线在环境变量里不可用，靠大小写与下划线表达层级（宽松绑定兜住大部分映射）。

## 5. 高频坑与面试题

1. **proxyBeanMethods 的行为分叉**：同一配置类 full/lite 下"方法调用返回单例还是新实例"完全不同——排查配置类诡异行为第一眼看这个属性；对比实验是排查手段：同一配置类改开关跑一次断言，行为差异立现；
2. **singleton 注入 prototype 失效**：不配 proxyMode 时 prototype 形同 singleton——面试经典，答案即作用域代理；
3. **@Value 默认值陷阱**：URL/带冒号值必须 `${x:}` 空默认写法；SpEL 注入的表达式错误在启动期暴露，占位符缺键（无默认值）抛 IllegalArgumentException；
4. **面试必答框架**：「@Configuration 为什么需要代理？」——full 模式拦截 @Bean 方法间调用保证容器单例语义与依赖关系声明；lite 模式放弃代理换启动性能，代价是方法调用即新建；追问「static @Bean 方法为什么不受代理影响？」——CGLIB 子类代理只能拦截实例方法，静态方法无 this 可拦截；
5. **「@Value 与 @ConfigurationProperties 的边界再确认？」**——数量维度：一两个散点值用 @Value，一组结构化配置用 @ConfigurationProperties；能力维度：后者才有宽松绑定、构造绑定、配置校验、元数据生成（IDE 提示）——配置项超过三个建议整体走 @ConfigurationProperties + record；
6. **「@Scope 自定义作用域怎么落地？」**——三步：实现 Scope 接口（get/remove/registerDestructionCallback 操作自定义存储，如租户上下文 Map）→ 注册 CustomScopeConfigurer 把名字绑定到实现 → @Scope("tenant") 使用——多租户连接池、请求外会话级 Bean 都走这个扩展点。
