## 1. @Autowired 的注入点语义

@Autowired 默认 `required = true`（候选缺失抛 `NoSuchBeanDefinitionException`；可选依赖 `required = false` 或 `@Nullable`、Java 8 `Optional<T>` 参数）。四类注入点的语义差异：

- **构造器注入（标准姿势）**：Spring 4.3+ 起单构造器时 @Autowired 可省略；字段 final 可声明，依赖不可变；测试无需容器即可 new 出对象——2026 年的行业共识是构造器为默认，字段注入只存在于存量代码与测试便利场景。多个构造器时 @Autowired 必须显式标注到目标构造器上（Spring 无法猜测用哪个），且其中一个构造器可在参数上标 `@Autowired(required = false)` 表达"可选依赖构造器"——这是构造器注入表达可选依赖的另一种姿势（对比 @ObjectProvider 的方案）；
- **字段注入**：反射直接赋值（Field.set），无 setter 也能注入；代价是字段可变、隐式依赖、循环依赖只能靠字段注入打破（构造器循环依赖直接抛 BeanCurrentlyInCreationException——三级缓存机制只对字段/setter 注入路径生效）；
- **setter/方法注入**：任意方法签名（多参数）都可标 @Autowired，容器装配时调用；多参数方法注入可一次装配整组协作依赖，但可读性弱于构造器——定位是"构造器不宜改造的存量类"的过渡姿势；
- **集合注入**：`@Autowired List<Validator>` 注入**该类型全部 Bean** 的有序集合（按 @Order/@Priority 排序）；`Map<String, Xxx>` 注入 Bean 名 → 实例映射——策略模式/插件架构的装配基础；集合注入对空集合天然容忍（无候选时注入空集合而非报错，required 语义在此失效）——这个特性本身是双刃剑：策略链场景空集合=功能静默缺失（应该 fail-fast 还是容忍，取决于业务语义，团队规范需明确）。

解析核心在 `AutowireCandidateResolver`：按类型筛候选 → 多个候选按注入点名称（字段名/参数名，依赖 `-parameters` 编译参数）二次匹配 → 仍未决走 @Primary/@Qualifier。泛型注入：Spring 能解析注入点的泛型签名（`Dao<User>` vs `Dao<Order>` 可精确匹配），但**类型擦除边界**（原型/通配符）处仍需 @Qualifier 兜底。

## 2. 歧义解决链：@Qualifier / @Primary / 名称匹配

多候选时的完整裁决链：**@Qualifier 点名 > 注入点名称匹配 > @Primary > 报错**。

- **@Qualifier("smsSender")**：按 Bean 名或限定符值点名。推荐姿势是把 @Qualifier 做成**语义限定符**——`@Qualifier("primary")` 这种与 Bean 名耦合的写法脆弱，更好的做法是自定义限定符注解（元注解叠 @Qualifier 的派生注解，如 @PaymentChannel("wechat")），重命名 Bean 不受影响；
- **@Primary**：声明"此类型默认胜者"，仅在无 @Qualifier 点名时生效——优先级低于 @Qualifier，这是常见面试陷阱（"我加了 @Primary 为什么还报歧义"——因为别处用了 @Qualifier 点名另一个）；
- 名称匹配：候选集中 Bean 名与注入点名（字段名/参数名）一致者胜出——依赖参数名保留（-parameters），这就是"@Autowired 字段叫 smsSender 就能自动选中同名 Bean"的机制。

> ⚠️ **陷阱**：@Qualifier 的值同时参与"限定符值匹配"与"Bean 名匹配"两个阶段，@Qualifier("x") 且不存在名为 x 的 Bean 但存在限定符值为 x 的 Bean 时也能命中——排查歧义时先明确候选集与各阶段命中情况。

## 3. @Resource 与 @Inject：Jakarta 标准对照

| 注解 | 来源 | 匹配顺序 | required 语义 |
|------|------|---------|------|
| @Autowired | Spring | 类型 → 名称 → @Primary/@Qualifier | required 属性 |
| @Resource | Jakarta | **名称 → 类型** | 无 required，缺失抛异常 |
| @Inject | Jakarta（JSR-330） | 类型（同 @Autowired 模型） | 经 Provider 表达可选 |

@Inject 配套的两个注解：`@Named`（JSR-330 限定符，与 @Qualifier 语义对应——Spring 对二者互认，@Inject + @Qualifier 混用也合法）与 `jakarta.inject.Provider<T>`（延迟获取）。JSR-330 体系的定位：跨容器标准（Guice/Spring 共用一套注解），适合"框架中立"的库代码；应用代码层面它与 @Autowired 能力等价，团队统一用 Spring 体系即可，@Inject 出现在要兼容非 Spring 容器的 SDK/库模块。

@Resource 的**先名称后类型**是它区别于 @Autowired 的本质：`@Resource(name = "smsSender")` 直接点名；不写 name 时用**字段名**做默认名称查找，失败再退化为类型匹配。历史定位是 Java EE 标准注解（Spring 兼容支持），新项目统一 @Autowired + 构造器注入即可，@Resource 只在"按名称优先"的存量代码里出现。@Inject 的现代价值是 JSR-330 标准兼容（与 Guice 同模型），Provider<T> 注入延迟获取实例——Spring 中可直接用 @ObjectProvider 替代。

## 4. @Lookup 与 @ObjectProvider

**@Lookup** 解决"singleton 持有 prototype"的另一条路（对比 04 篇的作用域代理）：标注抽象方法，Spring 用 CGLIB 生成**方法级代理**——每次调用返回容器里新取的原型实例。相比 proxyMode 全局代理，@Lookup 只作用于调用点，更精准但要求类可被 CGLIB 增强（非 final、方法非 static/private）。

**@ObjectProvider<T>** 是构造器注入时代的"可选/延迟/流式"利器：`getObject()`（缺失时抛异常，`getIfAvailable()` 安全获取）、`getIfUnique()`（唯一候选才返回）、`stream()`（流式消费全部候选）、`orderedStream()`（按序）。核心场景：构造器注入 + 可选依赖（替代 `required = false` 的字段注入）、多候选延迟挑选、循环依赖缓解（Provider 延迟解析）。纪律：ObjectProvider 应只在构造器参数中出现一次且尽快消费——注入后随意保存 Provider 再延迟调用，会把"启动期失败"变成"运行期爆发"，削弱了构造器注入的快速失败优势。

### 4.1 集合注入的策略模式落地

集合注入是策略模式的天然装配基础：

```java
@Component
public class PaymentRouter {
    private final Map<String, PaymentService> services;   // Bean 名 → 实例

    public PaymentRouter(Map<String, PaymentService> services) {
        this.services = services;
    }

    public void pay(String channel, Order order) {
        services.get(channel).pay(order);                 // 按渠道路由
    }
}
```

`Map<String, X>` 的 key 是 Bean 名（@Bean("wechatPay") 或类名首字母小写），`List<X>` 按 @Order/@Priority 排序——两个变体的选择：需要"按 key 路由"用 Map（策略分派），需要"链式处理"用 List（校验链/过滤器链，每个元素依次执行）。泛型解析的深水区：`PaymentService<Order>` 与 `PaymentService<Refund>` 的泛型注入由 `ResolvableType` 解析（Spring 的泛型解析工具，比 JDK 反射的 TypeVariable 更完整）——但**类型擦除边界**（原始类型、通配符 `PaymentService<?>`）处解析失效，多候选场景会报歧义，需 @Qualifier 兜底。这是"泛型注入大多数情况能用、边界处必须点名"的诚实边界。

## 5. 高频坑与面试题

1. **@Primary 压不住 @Qualifier**：裁决链优先级是 @Qualifier > @Primary，两个注解同时存在时 @Qualifier 胜——面试高频陷阱题；生产事故形态："加了 @Primary 还是报歧义"——必然是别处 @Qualifier 点名了另一个候选，全局搜 @Qualifier 引用即可定位；
2. **参数名保留**：构造器参数名参与名称匹配，未开 `-parameters` 编译时名称匹配失效（本机好、CI 挂类问题）；
3. **集合注入的排序**：依赖 @Order/@Priority，未标注时顺序不稳定——策略链场景必须显式排序；
4. **面试必答框架**：「@Autowired 装配过程？」——按类型筛候选 → 多候选按注入点名称匹配 → 仍未决看 @Qualifier/@Primary → 按构造器/setter/字段策略实例化并反射赋值——完整链路是"类型优先、名称次之、注解裁决"；追问「构造器注入为什么推荐？」——final 字段不可变、依赖显式、循环依赖编译期即暴露（字段注入会把循环依赖藏到运行期）；
5. **「循环依赖三种解法怎么选？」**——构造器循环依赖直接报 BeanCurrentlyInCreationException（**最优解**：重构拆出第三类）；字段注入 + 三级缓存（Spring 的 earlySingletonObjects 机制，字段注入能跑但掩盖设计问题）；@Lazy 打破一侧初始化链（延迟注入打破时序，属设计妥协）——按"重构 → @Lazy → 容忍字段注入"排序回答；
6. **「@Resource 与 @Autowired 混用的风险？」**——两者匹配顺序相反（名称优先 vs 类型优先），同一代码库混用会让"哪个注解选哪个 Bean"变得不可预期——团队规范应统一一个注解（新项目统一 @Autowired + 构造器），@Resource 只出现在存量代码。
