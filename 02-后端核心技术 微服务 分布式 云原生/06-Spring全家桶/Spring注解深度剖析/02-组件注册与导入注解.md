# 02 组件注册与导入注解

> Bean 定义的来源只有两条路：扫描（@ComponentScan 在类路径上"发现"组件）与导入（@Import 显式"引入"配置）。本篇拆解两条路的全部注解属性与机制——@ComponentScan 的扫描器怎样工作、@Indexed 如何省掉扫描成本、@Import 三种形态各自解决什么问题

## 1. @ComponentScan 扫描器全属性

@ComponentScan 的消费者是 `ClassPathBeanDefinitionScanner`，属性即扫描参数：

- **basePackages/value**（别名）：扫描根包；**basePackageClasses**（类型安全替代——扫该类的包，重构免改字符串，框架配置类惯用）；
- **includeFilters/excludeFilters**：类型过滤器（`@Filter(type = FilterType.ANNOTATION, classes = ...)`），五类过滤：ANNOTATION/ASSIGNABLE_TYPE/ASPECTJ/REGEX/CUSTOM；
- **useDefaultFilters**（默认 true）：扫描器默认只认 @Component 及其派生链；关掉后仅按 includeFilters 扫描；
- **lazyInit**：扫出的 Bean 全部 @Lazy；
- **nameGenerator/scopedProxy**：Bean 命名与作用域代理策略。

一个关键心智：**扫描基于 ASM 字节码，不加载类**。扫描器用 MetadataReader 读取类结构 + 注解属性，确认候选后才构造 BeanDefinition——类加载推迟到实例化阶段。这意味着"扫描到的类"与"能加载的类"是两个集合：@Conditional 在配置类级别再过滤一轮（03 篇）。路径上两个默认行为要注意：扫描器**默认扫描当前配置类所在包**（@SpringBootApplication 无参时的包即应用主类包），且默认**不扫接口、不扫内部类**（除非带 @Component）。

重复标注 @ComponentScan 靠 @Repeatable（Scans 容器）展开，多个配置类各自声明扫描范围的合并语义是"并集"——这是分包扫描的惯用姿势。

## 2. @Component 派生链与 @Indexed 候选索引

@Component → @Service/@Repository/@Controller → @Configuration → @RestController 构成派生链：每一层都是元注解组合（@RestController = @Controller + @ResponseBody）。扫描器用 `isCandidateComponent` 走 MergedAnnotations 递归判断（01 篇机制），所以**任何自定义注解只要元注解链上出现 @Component 即成为组件注解**——派生注解的零成本扩展正是 Spring 注解模型的设计红利。

**@Indexed 候选索引**解决启动性能：默认扫描要遍历类路径上全部 class 文件逐个读取判定，包越大越慢。编译期注解处理器（spring-context-indexer）把组件候选类写入 `META-INF/spring.components` 索引文件，运行时 `CandidateComponentsIndex` 直接读索引跳过全量扫描。适用边界：应用包（稳定、可重新编译）收益大；框架包、动态生成类不适用。注意 @Indexed 是 javax.lang 语义（标注任何"索引候选"），@Component 体系内已隐式包含，自定义派生注解需显式 @Indexed 才能进索引。接入方式：引入 spring-context-indexer 注解处理器（Maven annotationProcessorPaths 或 Gradle annotationProcessor），编译产物即自动生成索引——**注意**：索引只在"应用类 + 注解处理器"齐备时生效，缺失时静默回退全量扫描（功能不受影响、性能回到基线），排查"索引为什么没生效"先看构建配置。

### 2.1 扫描的性能账单与 lazyInit

扫描的成本构成：遍历 jar 内全部 class 条目 + 逐个 ASM 读取判定。两个工程注意：**范围纪律**——basePackages 精确到应用包（扫第三方 jar 的组件注解是误注册与启动变慢的双料事故）；**@Indexed 是加速项而非正确性项**——索引里没有的类不会被注册（索引与代码不同步时出现"Bean 神秘消失"，重建索引即修复，这是索引方案的已知脆弱点）。`lazyInit = true` 让扫出的 Bean 全部延迟实例化：收益是启动加速，代价是"实例化错误推迟到首次使用爆发"——生产环境谨慎开启，且全局 `spring.main.lazy-initialization=true` 会覆盖局部配置。

## 3. @Import 三种形态

@Import 是**程序化注册**的总入口，三种形态对应三个扩展点：

**形态一：直接导入配置类**。`@Import(OtherConfig.class)` 等价于把该类纳入容器处理（@Configuration 类会被增强）。用途：显式聚合分模块配置、导入第三方未标 @Configuration 的类。

**形态二：ImportSelector**。接口 `selectImports()` 返回要导入的类名数组，**运行时决策**导什么：经典案例是 @EnableTransactionManagement 的 TransactionManagementConfigurationSelector——按代理模式（JDK/CGLIB）选不同配置类。进阶是 DeferredImportSelector：在**所有**常规配置处理后执行（@EnableAutoConfiguration 就是 DeferredImportSelector，保证自动配置最后注册、用户 Bean 优先）。

**形态三：ImportBeanDefinitionRegistrar**。拿到注册器 + 元数据，可编程构造任意 BeanDefinition：MyBatis 的 @MapperScan（MapperScannerRegistrar 扫描接口注册 MapperFactoryBean）、Feign 的 @EnableFeignClients（FeignClientsRegistrar）都是这个形态的产物。三形态的选型：静态导入用形态一；"根据环境/其他 Bean 决定导什么"用形态二；"要造特殊的 BeanDefinition/工厂 Bean"用形态三。

### 3.1 @Import 与 @Conditional 的协同案例

以 MyBatis starter 为例拆解完整链路：`@MapperScan("com.x.mapper")` → @Import(MapperScannerRegistrar) → Registrar 注册扫描器 + MapperFactoryBean 的 BeanDefinition → 扫描器按注解找 Mapper 接口 → 每个接口注册为一个 MapperFactoryBean（工厂 Bean 在 getObject 时生成 JDK 动态代理）——用户拿到的 Mapper 实例就是 Proxy。这条链路上 @Conditional 的落点：自动配置类级 @ConditionalOnClass(name = "org.apache.ibatis.session.SqlSessionFactory")（字符串形式，03 篇详述）+ @ConditionalOnMissingBean(SqlSessionFactory.class)（用户自定义优先）——导入负责"怎么注册"、条件负责"注册不注册"，两者分工就是自动配置的两段式结构。读懂这个案例，任何一个第三方 starter 的注册链路都能按同样框架拆解。

> 🎯 **核心要点**：@Import 是 Spring 生态的"元开关"——@EnableXxx 注解几乎都 = @Import(配置类或 Selector/Registrar)。理解三形态，就理解了 MyBatis/Feign/Security 一切 @Enable 注解的注册机制。

## 4. @ImportResource 与遗留体系桥接

@ImportResource("classpath:spring-legacy.xml") 把 XML 配置并入注解容器——两条 Bean 定义通道并存，`locations` 支持多个资源。用途收窄为：存量 XML 系统渐进迁移（新 Bean 走注解、旧 Bean 走 XML）、需要 XML 独有能力（`<util:>` 命名空间、XSD 校验的声明式配置）的场景。方向性结论：新项目不再需要它，但它标注了 Spring"新旧体系长期共存"的设计哲学——BeanDefinition 是统一货币，XML/注解/程序化只是三种造币方式。

注册时序的全局观：一切组件注册由 `ConfigurationClassPostProcessor` 统一驱动——先解析 @ComponentScan（发现配置类与组件）→ 逐个解析配置类（@Import/@Bean/@Conditional 在此裁决）→ @ImportResource 的 XML 混入 → 常规 Bean 按条件注册。理解这个时序就能解释两个常见现象：**自动配置总是最后处理**（DeferredImportSelector 排队到常规配置之后，用户 Bean 优先）；**同名 Bean 的胜负由注册顺序决定**（后注册覆盖先注册，Boot 3+ 收紧为报错）。

## 5. 高频坑与面试题

1. **扫描包过大/过小**：扫到第三方包（启动变慢 + 误注册）或漏扫子包（@SpringBootApplication 不放业务包父级）——排查"Bean 找不到"先看扫描范围，@SpringBootApplication 默认扫主类所在包；
2. **excludeFilters 与 @Conditional 的边界**：过滤器在扫描期裁决（类不进候选集），@Conditional 在注册期裁决（BeanDefinition 跳过注册）——两者时机不同，性能敏感场景优先用过滤器（省掉构造 BeanDefinition 成本）；
3. **Bean 名冲突**：两个不同配置源注册同名 Bean 时，Spring Boot 默认**后注册者覆盖先注册者**（allowBeanDefinitionOverriding 语义，Boot 3+ 默认收紧为 false 抛异常）——升级 Boot 3+ 后"同名 Bean 静默覆盖"变为启动失败，排查冲突用 `spring.main.allow-bean-definition-overriding=true` 临时恢复旧行为但应在代码层面消除重名；
4. **@Indexed 与增量构建的脆弱性**：索引文件与源码不同步（IDE 增量编译漏生成）时出现"Bean 神秘消失"——排查顺序：先确认 META-INF/spring.components 里有没有这个类，再删索引强制重建。
3. **面试必答框架**：「@EnableXxx 是怎么工作的？」——注解上 @Import 配置类/ImportSelector/ImportBeanDefinitionRegistrar，注册器在容器刷新期编程化注册 Bean——MyBatis 的 @MapperScan 用第三种形态把接口扫成 MapperFactoryBean；追问「@MapperScan 为什么不扫 @Component？」——Mapper 接口没有实现类，不能走组件扫描 + 反射实例化路线，必须注册为工厂 Bean 由代理生成实现；追问「为什么扫描不加载类？」——ASM 字节码读取（MetadataReader）拿注解与类结构，类加载推迟到实例化——扫描成本与类路径规模线性相关，与类自身复杂度无关。
