# 07 异步任务与缓存注解

> @Async 把方法调用切到线程池、@Scheduled 把方法变成定时任务、@Cacheable 家族把方法结果放进缓存——三者同属"方法级行为增强"，共享 AOP 代理失效模型（自调用失效）。但各自有专属坑位：@Async 的异常感知、@Scheduled 的默认单线程调度器、@Cacheable 的 key 生成与一致性

## 1. @Async：线程池、返回值与异常

@Async 标注的方法在**调用线程之外的线程池**执行。三个核心决策：

**线程池选择**：`@Async("beanName")` 指定执行器 Bean；不指定时找容器里唯一的 TaskExecutor（或名为 taskExecutor 的 Bean）——**都找不到时用 SimpleAsyncTaskExecutor，它每次调用新建线程**（Spring 6.1+ 支持虚拟线程版），生产不配线程池等于线程无上限，必须在 @EnableAsync 或 Bean 层面显式配置 ThreadPoolTaskExecutor。

**返回值三种形态**：void（真正 fire-and-forget）；`Future<T>`（可 get 阻塞等待，注意超时）；`CompletableFuture<T>`（2026 年标准——链式组合、异常传递、可超时）。方法内部再抛异常时：void 型异常**调用方感知不到**，必须配 AsyncUncaughtExceptionHandler（日志兜底）；Future/CompletableFuture 型异常包装进 get()/join() 抛出，感知路径完整。生产级线程池配置的标准形态：

```java
@Bean("bizExecutor")
public ThreadPoolTaskExecutor bizExecutor() {
    var executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(8);          // 核数 × 2 起步
    executor.setMaxPoolSize(16);
    executor.setQueueCapacity(1000);      // 有界队列防 OOM
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.setThreadNamePrefix("biz-"); // 线程名可观测
    executor.initialize();
    return executor;
}
```

三个参数纪律：**队列必须有界**（无界队列 = 慢请求堆积 OOM）；拒绝策略显式化（CallerRuns 让调用线程兜底执行，牺牲延迟换不丢任务）；`setWaitForTasksToCompleteOnShutdown` 配置优雅停机时未完成任务的处理。

**失效与语义边界**：自调用失效（与 @Transactional 同源的代理模型，06 篇推导式记忆同样适用）；事务上下文**不跨线程**（@Async 方法里的事务是独立新事务，ThreadLocal 绑定的事务资源不传递）；标注在 private 方法无效。@EnableAsync 的 `mode` 属性可选 ASPECTJ 模式（编译期织入绕过代理限制，代价是构建复杂度，团队级决策）。

## 2. @Scheduled：三种调度模式

- **cron**：6 位表达式（秒 分 时 日 月 周），`zone` 指定时区（**容器 UTC 时区时 cron 会整体偏移**，中国时区必须显式 zone = "Asia/Shanghai"）；周域 0-7（**0 与 7 均表示周日，1=周一…6=周六**）——注意与 Quartz（1=周日）的编号不同，迁移时周域值需整体核对；
- **fixedDelay / fixedDelayString**：上次**执行结束**后间隔 N 毫秒再执行——任务耗时漂移但永不重叠；
- **fixedRate / fixedRateString**：上次**执行开始**后间隔 N 毫秒——重叠执行由 `@Scheduled` 所在调度器的单线程模型自然排队（默认调度器单线程，多个任务互相阻塞，`spring.task.scheduling.pool.size` 配置并行度）；`initialDelay` 控制首轮延迟。

`@Schedules` 容器注解支持同一方法多个调度声明。调度器的正确姿势：@EnableScheduling + 显式 pool size + 任务方法各自短小（长任务占住单线程会饿死其他任务——重活丢给 @Async 线程池）。@EnableScheduling 内部 @Import(SchedulingConfiguration) 注册 ScheduledAnnotationBeanPostProcessor——它扫描所有 Bean 上的 @Scheduled 方法注册为 ScheduledTask，任务的执行器与注册器分离（TaskScheduler 与调度线程池可独立配置），这是排查"任务不触发"的两层入口：注解没扫到（Bean 未注册/代理问题）或调度器没启动。调度任务是"进程内多实例重复执行"的重灾区（多副本同 cron 全跑），集群场景要么分布式锁、要么调度中心（XXL-Job 类）——这是注解体系的能力边界。

## 3. @Cacheable 家族

五件套：`@Cacheable`（查缓存，命中直接返回——**方法体不执行**）；`@CacheEvict`（清缓存，`beforeInvocation` 控制先清后执行还是先执行后清）；`@CachePut`（执行后更新缓存，返回值必须正确）；`@Caching`（组合多操作）；`@CacheConfig`（类级共享 cacheNames/keyGenerator）。开关 `@EnableCaching`（同样 @Import 模式）。

**key 的 SpEL 生成**是使用核心：默认 SimpleKeyGenerator 按"全部参数 equals"生成 key；`key = "#userId"`（参数取属性）、`key = "#user.id"`（对象属性）、`key = "T(com.x.KeyGen).gen(#user)"`（静态方法自定义）；`condition = "#total > 100"`（满足才缓存）、`unless = "#result == null"`（结果为空不缓存）。坑位：**@CacheEvict 的 key 表达式必须与 @Cacheable 完全一致**否则清不掉（默认 allEntries = true 兜底但粗粒度）；SpEL 可调用静态方法但不可调用 Spring Bean 方法（需要时用自定义 KeyGenerator Bean）；缓存 null 会击穿到 DB（除非 unless 排除或缓存层支持 null 值）。

**一致性定位**：注解缓存是**本地性能优化**而非一致性方案——读多写少（字典、配置、热点商品详情）是甜区；强一致数据（余额、库存）不该走注解缓存。更新侧用 @CacheEvict（删而非改，防并发写脏）+ 双删策略属缓存体系范畴，注解层记住"改删缓存、键一致"六字纪律。

缓存三大问题的注解层应对：**击穿**（热点 key 过期瞬间并发打 DB）——注解层无内置互斥，靠 `sync = true`（ConcurrentMapCache 有限支持）或缓存层锁方案；**穿透**（查不存在的 key 反复打 DB）——`unless = "#result != null"` 不缓存 null 是防穿透前提，配合缓存空值占位；**雪崩**（批量过期同时失效）——`@Cacheable` 无 TTL 属性，TTL 由缓存管理器/Redis 层配置，过期时间**随机化**是标准解法。注解缓存的定位总结：它解决"方法结果复用"，不解决"缓存治理"——TTL、淘汰、集群一致性都下沉到缓存基础设施层。

cron 表达式六域（秒 分 时 日 月 周）的易错点补充：日域与周域**互斥**（一个写具体值另一个必须写 `?`，Spring 支持 `?` 语义）；`0 0/30 * * * ?` 每半小时、`0 0 2 * * ?` 每天凌晨 2 点；周域 `1-5` 是**周一到周五**（Spring 语义 1=周一、0 或 7=周日）——与 Quartz（1=周日）的编号不同，迁移时周域表达式必须整体核对而非照抄。调试技巧：`spring.task.scheduling` 的日志打开后能看任务触发记录，cron 写错的最快发现方式是小步进时间（如每分钟）验证后再改回目标时间。

## 4. 虚拟线程时代的执行器选择

Spring 6.1+/7 的虚拟线程支持改变了两类执行器的选型：

- **@Async 任务池**：IO 密集任务（HTTP 调用、DB 等待）改用虚拟线程执行器（`TaskExecutor` 的 virtualThreadPerTask 实现或 `@Async("virtualTaskExecutor")`）——无限并发、无池调优负担；CPU 密集任务仍应回落到平台线程池（虚拟线程不增加算力，且避免 pinning 拖垮平台线程）；
- **@Scheduled 调度器**：调度线程保持平台线程（定时触发是轻量操作），任务体内部的 IO 等待再交给虚拟线程池——"调度用平台、执行可虚拟"的分层。

Spring 7 的 @ConditionalOnThreading 条件装配让"虚拟线程可用才启用某配置"成为标准姿势，自研组件可复用该条件实现双配置自动切换。

## 5. 高频坑与面试题

1. **SimpleAsyncTaskExecutor 默认兜底**：没配执行器时每任务一线程——生产必须显式线程池或虚拟线程执行器；
2. **cron 时区漂移**：容器 UTC 下任务整体偏移 8 小时——zone 属性必须显式；
3. **默认调度器单线程**：多个 @Scheduled 任务互相阻塞——pool size 配置是启动项而非调优项；
4. **面试必答框架**：「@Async 与 @Transactional 失效为什么同源？」——都是 AOP 代理拦截方法，自调用/非 public/新线程三者都绕过代理；追问「@Async 方法里的事务与调用方事务什么关系？」——无关系，事务上下文线程绑定，新线程开启全新事务，调用方回滚不影响异步方法已提交的结果；
5. **「@Cacheable 的缓存穿透怎么防？」**——注解层 `unless = "#result != null"` 不缓存 null + 缓存层空值占位（短 TTL 的空对象）双层防护；追问「@CacheEvict 为什么清了没用？」——key 表达式与 @Cacheable 不一致（默认生成器按全参数，显式 key 必须两边一字不差），或缓存管理器不一致（两个缓存实例各存各的）；
6. **「@Scheduled 集群多实例怎么办？」**——注解调度是进程内行为，多副本同时触发——方案按复杂度递进：单实例部署（简单业务）、分布式锁（ShedLock 类，注解无侵入）、调度中心统一调度（XXL-Job 类，重任务标准解）。
