# 06 事务注解

## 1. @Transactional 全属性

完整属性表按使用频率分层：

- **rollbackFor/rollbackForClassName**：声明回滚异常类型。默认只回滚 RuntimeException 与 Error，**受检异常默认提交**——吞掉"异常已发生但事务提交"事故的最常见来源；生产规范是显式 `rollbackFor = Exception.class`（或团队约定的业务异常基类）；
- **noRollbackFor/noRollbackForClassName**：例外清单（如补偿已完成的异常不回滚）；
- **propagation**（七值，见下节）与 **isolation**（READ_UNCOMMITTED/READ_COMMITTED/REPEATABLE_READ/SERIALIZABLE，默认走数据库默认级别；调级要给出并发语义理由）；
- **readOnly = true**：优化提示（连接标记只读、脏检查关闭），**不是强制约束**——写操作照样执行，只当查询优化的声明；
- **timeout/timeoutString**：秒级超时（基于事务开始时间），超时抛 TransactionTimedOutException 回滚；
- **transactionManager/transactionManagerQualifier/value**：指定事务管理器（多数据源场景按 Bean 名或限定符点名）；
- **label**（JTA 事务的标签，普通场景不用）。

属性经 `AnnotationTransactionAttributeSource` 解析为 TransactionAttribute 并**按方法缓存**（ConcurrentHashMap，01 篇的性能纪律在此落地）——同一方法的重复调用不再做注解合并解析。

## 2. 传播行为七值的业务含义

传播行为的本质是"方法进入时对现有事务的态度"，按业务场景归三类：

**加入类**：REQUIRED（默认，有则加入无则新建——业务主路径）；SUPPORTS（有则加入无则裸跑——查询方法可选事务）；MANDATORY（必须有，否则抛 IllegalTransactionStateException——强一致写操作的自检）。

**挂起类**：REQUIRES_NEW（挂起当前、新开独立事务——**独立提交独立回滚**，日志落库/审计写失败不影响主流程）；NOT_SUPPORTED（挂起并以无事务运行——报表查询免锁）；NEVER（有事务直接抛异常——强制非事务的检查）。

**嵌套类**：NESTED（保存点 savepoint 机制，子事务回滚到保存点而不伤外层——JPA 不完整支持，数据库需支持保存点）。

两个心智模型：REQUIRES_NEW 与 NESTED 的差别在**失败影响面**（REQUIRES_NEW 子事务已提交即无法回滚、NESTED 外层回滚会带走内层）；REQUIRES_NEW 通过代理调用才生效——**自调用时它退化为 REQUIRED**，这是隐性 bug 高发点（见下节）。

## 3. 失效场景的机制推导

一切失效都源于一个事实：@Transactional 由 **TransactionInterceptor（AOP 代理）**执行，注解只是切点标记。失效清单 = "绕过代理的方式"全集：

1. **自调用**：`this.inner()` 不过代理，inner 上的 @Transactional 静默失效——解法：注入自身代理（@Autowired 自己的接口）、抽独立 Bean、或 TransactionTemplate；
2. **非 public 方法**：Spring AOP 只拦截 public（CGLIB 时代同源）；private 方法标注注解编译通过、运行无效；
3. **异常被吞**：try-catch 内吞掉异常后事务管理器感知不到异常信号，事务正常提交——"事务没回滚"排查第一方向；
4. **受检异常默认不回滚**：见第 1 节 rollbackFor；
5. **传播语义错误**：REQUIRES_NEW/NESTED 自调用退化、事务管理器指向错误（多数据源）；
6. **非 Spring 管理的调用边界**：new 出来的对象、静态方法、@Async 新线程（事务上下文不跨线程——传播只在同一线程的 ThreadLocal 事务上下文内有效）。

推导式记忆：**代理没拦到、异常没看到、传播没配对**三句话覆盖全部失效场景，比背清单可靠。

失效排查的实操路径：先确认方法是否被代理拦截（断点看 this 是否为代理类，类名带 `$$` 后缀即代理）；再确认异常路径（日志里事务提交/回滚语句、吞异常点）；最后核对传播与事务管理器配置（REQUIRES_NEW 调用路径、多数据源点名）。三步走完仍不生效的案例极少——绝大多数"事务没回滚"事故都能在这三步内定位，比逐条背失效清单效率高得多。

## 4. @EnableTransactionManagement 与编程式对照

@EnableTransactionManagement 是总开关：@Import(TransactionManagementConfigurationSelector)（02 篇形态二）按代理模式选择配置——proxyTargetClass 决定 JDK 代理还是 CGLIB（接口类默认 JDK，Boot 自动配置已默认开启事务管理，纯框架场景才手动开启）。拦截器链：事务元数据解析 → 开启事务（传播决策）→ 执行业务 → 提交/回滚（异常判定 + rollbackFor 过滤）→ 连接释放回池。

编程式 TransactionTemplate 的适用边界要诚实：**声明式覆盖 95% 场景**，编程式只在"事务边界无法用方法边界表达"时使用（部分提交、循环内分批事务、动态传播决策）。对照语义：template.execute 的默认传播就是 REQUIRED、异常默认回滚——与注解语义对齐，混用时不会分裂心智。

### 4.1 事务同步机制：提交后做什么

@Transactional 方法里注册 `TransactionSynchronizationManager.registerSynchronization()` 可以在提交/回滚后执行回调（发消息、刷新本地缓存的正确时机）——@TransactionalEventListener（08 篇）就是这套机制的注解封装。关键认知：事务上下文是 **ThreadLocal 绑定**的（事务资源、连接、同步列表都在当前线程），所以"事务内注册的回调"只对当前线程有效，跨线程（@Async）调用天然脱离事务上下文——这解释了 06 篇第 5 条失效场景与 07 篇异步事务隔离的同源机制。

隔离级别的实战案例：高并发扣库存场景默认 REPEATABLE_READ 下大量间隙锁引发死锁，显式 `isolation = Isolation.READ_COMMITTED` 消除间隙锁（配合乐观锁 @Version 保证正确性）是常见组合——**隔离级别不是越强越好，是"锁代价"与"一致性要求"的权衡**，调级必须能说出并发语义理由。`readOnly = true` 再提醒一次：它只是优化提示（连接只读标记 + Hibernate 脏检查关闭），**不会阻止写操作**——把它当"只读约束"用是事故隐患。

## 5. 高频坑与面试题

1. **REQUIRES_NEW 自调用退化**：注解在内层方法上但外层 this 调用——传播语义从"新事务"静默变"加入事务"，审计日志与主事务绑死；
2. **rollbackFor 缺失 + 受检异常**：下单扣库存抛库存异常（受检）→ 订单照常提交——数据不一致的经典形态；
3. **@Transactional 加在 Controller/私有无意义**：事务边界应在 Service 公共入口（聚合业务单元），Controller 层标注虽能生效（代理存在）但边界错误；
4. **面试必答框架**：「@Transactional 原理」——BeanPostProcessor 创建代理 → TransactionInterceptor 拦方法 → 解析 TransactionAttribute（注解合并 + 缓存）→ 事务管理器按传播开启 → try/catch 按 rollbackFor 裁决 → 提交/回滚；「为什么失效」按三句话框架答：代理没拦到（自调用/非 public/新线程）、异常没看到（吞掉/受检不默认回滚）、传播没配对（REQUIRES_NEW 退化/管理器错）；
5. **「类级与方法级 @Transactional 的关系？」**——方法级注解**覆盖**类级（属性继承只发生在"方法无注解"时，且继承规则要求方法为 public）；类级标注 + 方法级只覆盖个别属性（如仅改 readOnly）时其余属性继承类级——"覆盖是整注解替换还是属性级合并"是常见追问，答案是整注解替换（方法注解完全覆盖类注解）；
6. **「多数据源怎么指定事务管理器？」**——`transactionManager`/`transactionManagerQualifier` 属性点名（Bean 名或限定符），配 @EnableTransactionManagement 注册多个 DataSourceTransactionManager——不指定时框架按类型取唯一，多个管理器存在且未点名直接报歧义。
