# 03 条件装配注解

> 自动配置的本质是"按环境条件决定注册哪些 Bean"，@Conditional 家族就是这个决策系统。2026 年最大的坑在 @ConditionalOnClass：Java 24+ 下 Spring 7 的元数据读取器会急切解析注解中的类字面量，可选依赖缺失时条件评估前就爆炸——字符串形式 name 是官方解法。本篇覆盖条件契约、家族全解、评估顺序与调试手段

## 1. @Conditional 契约与评估模型

@Conditional 的契约极简：value 指定一个或多个 `Condition` 实现，`matches(ConditionContext, AnnotatedTypeMetadata)` 返回 true 才注册。真正的复杂度在评估语义：

- **注册期裁决**：条件是 ConfigurationClassParser 处理 @Bean 方法/配置类时的决策——条件不满足时 Bean 定义根本不会进入容器，而不是"注册了但被停用"；
- **评估时点**：@Bean 方法上的 @Conditional 在解析配置类时评估（此时其他 Bean 未必已注册），所以 @ConditionalOnBean/@ConditionalOnMissingBean 的判定基于**当时容器里已有的 BeanDefinition**——这就是"依赖的 Bean 在另一个自动配置里注册，但条件顺序不对导致误判"类问题的根源，@AutoConfigureAfter 由此而来；
- **元数据入参**：AnnotatedTypeMetadata 让条件能读到注解属性（如 @ConditionalOnProperty 的 name/havingValue）与类元数据（不含类加载）。

条件三要素的工程实践：`ConditionContext` 提供 BeanDefinitionRegistry（查已注册 Bean）、ConfigurableListableBeanFactory（查环境与类加载器）、Environment（读属性）；自定义条件实现必须**无状态**（可能被缓存复用）。

自定义条件的完整两文件姿势：

```java
// 注解侧
@Target({ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
@Conditional(OnFeatureEnabledCondition.class)
public @interface ConditionalOnFeatureEnabled {
    String value();     // 功能开关的配置键
}

// 条件侧
public class OnFeatureEnabledCondition implements Condition {
    @Override
    public boolean matches(ConditionContext context, AnnotatedTypeMetadata metadata) {
        Map<String, Object> attrs = metadata.getAnnotationAttributes(
                ConditionalOnFeatureEnabled.class.getName());
        String key = (String) attrs.get("value");
        return Boolean.parseBoolean(context.getEnvironment().getProperty(key, "false"));
    }
}
```

`metadata.getAnnotationAttributes()` 是条件实现的标准取参姿势——它走的是合并语义（元注解链上的 @Conditional 同样可读），与 01 篇的消费端纪律一致。评估时机分两个阶段：**PARSE_CONFIGURATION**（解析配置类时，@Bean 方法级条件在此评估）与 **REGISTER_BEAN**（注册常规 Bean 时）——@Conditional 可用 `ConfigurationCondition` 接口显式声明 phase，这是"条件要在其他配置类处理完再评估"类问题的正规解法。

## 2. @ConditionalOnXxx 家族全解

按评估对象分类：

- **类路径**：@ConditionalOnClass / @ConditionalOnMissingClass——value 传 Class 字面量或 name 传全限定名（见第 3 节）；
- **Bean 存在性**：@ConditionalOnBean / @ConditionalOnMissingBean——按类型或名字判断"容器里是否已有"；@ConditionalOnMissingBean 是"用户自定义优先于自动配置默认值"的标准实现（**自动配置的每个 Bean 都有这个保护，这是 @Bean 方法级最常用条件**）；
- **属性**：@ConditionalOnProperty(prefix/name/havingValue/matchIfMissing)——属性名拼错时条件永远 false、组件**静默消失**，排查第一方向永远是条件报告；`matchIfMissing = true` 控制"属性不存在时算不算通过"（默认不通过，显式声明默认启用语义）；`@ConditionalOnBooleanProperty`（Boot 3.4+）是布尔属性的专用简化（匹配 true/false 值，Boot 4 自动配置新惯用法）；
- **Web 环境**：@ConditionalOnWebApplication(type = SERVLET/REACTIVE/ANY)、@ConditionalOnNotWebApplication；
- **其他**：@ConditionalOnExpression（SpEL 表达式条件，如 `@ConditionalOnExpression("${app.mode:standard} == 'multi'")`——复杂属性组合条件用表达式而非嵌套多个 @ConditionalOnProperty）、@ConditionalOnResource（资源存在性）、@ConditionalOnWarDeployment/@ConditionalOnWarDeployed（传统 WAR 部署检测）、@ConditionalOnThreading（虚拟线程/平台线程选择，07 篇执行器选型的条件化开关）、@ConditionalOnJndi（JNDI 存在性）。

组合使用是自动配置类的标准形态：类级 @ConditionalOnClass（依赖存在才解析）+ @Bean 方法级 @ConditionalOnMissingBean（用户优先）+ 方法级 @ConditionalOnProperty（开关控制）——三个条件各司其职：**类路径门槛、覆盖保护、业务开关**。误用形态要警惕：@Bean 方法级 @ConditionalOnClass 挡不住方法返回类型的类加载（03 篇架构规则已述）；@ConditionalOnBean 依赖"评估时已注册"的时序，必须 @AutoConfigureAfter 配合。

评估顺序固定为**类路径 → Bean → 属性**：先查类是否存在，再查依赖 Bean，最后读配置。这个顺序的设计理由很实在——@ConditionalOnClass 不通过时后续条件没有评估意义，且避免"条件自身引用了不存在的类"。

## 3. @ConditionalOnClass 的 2026 新坑

Spring Framework 7 的 spring-core 是多版本 JAR：Java 24+ 上用 `ClassFileMetadataReader`（基于 java.lang.classfile API）替代 ASM 版 SimpleMetadataReader。它解析注解时会**急切执行 `ClassUtils.resolveClassName()`**——@ConditionalOnClass 属性里的类字面量在条件评估之前就被加载，可选依赖不在类路径时直接抛 `ClassNotFoundException`，自动配置**连评估的机会都没有**（Camunda PR #47466 记录了该问题的完整修复过程）。

两个层面的应对：

1. **写法层面**：可选依赖一律用字符串形式 `@ConditionalOnClass(name = "io.micrometer.core.instrument.MeterRegistry")`——name 形式只做类路径存在性检查、不触发加载，还能免掉对可选依赖的编译期引入（Class 字面量要求依赖在编译类路径上）；
2. **架构层面**：构建检查规则禁止 **@Bean 方法上**标 @ConditionalOnClass——即使条件通过与否，方法的返回类型在解析时就已被加载，条件保护不住返回类型本身。

判断标准一句话：**@ConditionalOnClass 保护的是"引用该类的代码"，不是"该类的加载"**——String 形式把保护范围精确到类路径检查本身。

## 4. @Profile、自动配置清单与排序

**@Profile("prod")** 是 @Conditional(ProfileCondition) 的派生注解，语义等价于"Environment 的活跃 profile 匹配"：`@Profile("a & !b")` 支持与/非/或表达式（或写作 `{"a", "!b"}`）。与 @ConditionalOnProperty 的分工：@Profile 表达**环境身份**（dev/test/prod），@ConditionalOnProperty 表达**配置开关**（feature.enabled）——身份用 Profile、开关用 Property 是团队约定俗成的边界。

**自动配置的登记与排序**（Boot 2.7+ 新惯例，4.x 的标准形态）：

- 配置类登记在 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（每行一个类名，spring.factories 的 EnableAutoConfiguration 键已退场）；
- 类上标 `@AutoConfiguration`（携带 before/after/afterNames/beforeNames 元数据）或单独标 `@AutoConfigureBefore/@AutoConfigureAfter/@AutoConfigureOrder`——排序解决"我的条件依赖你的 Bean 先注册"；
- 编译期 `spring-boot-autoconfigure-processor` 生成条件元数据（`META-INF/spring-autoconfigure-metadata.properties`），启动期**预过滤**——不满足条件的配置类在读取 imports 清单阶段就被剔除，这是自动配置"读几十个配置类但启动不慢"的核心优化。

自定义 starter 的完整注解姿势：@AutoConfiguration + @ConditionalOnClass(name=...) + @AutoConfigureOrder + 属性类（@EnableConfigurationProperties）。starter 的验收标准：引入依赖即可用（自动装配）、条件不满足时启动零痕迹（不进条件报告负面清单）、@EnableXxx 可显式开关（手动模式兜底）——三条全过才叫合格的自动配置。

## 5. 调试手段与面试题

1. **条件评估报告是第一排查工具**：`--debug` 启动（或 logging.level.org.springframework.boot.autoconfigure=DEBUG）输出 Positive/Negative matches 完整清单，**每个 Bean 的每个条件、哪个条件失败**一目了然——"Bean 没注册"类问题先看报告再猜原因；
2. **@ConditionalOnMissingBean 的评估时点**：它看的是"评估时刻"的容器状态，先注册的配置类会让后注册方的条件误判——自动配置间依赖必须显式 @AutoConfigureAfter 声明顺序；
3. **面试必答框架**：「自动配置怎么知道条件不满足？」——编译期 autoconfigure-processor 生成条件元数据 → 启动期按元数据预过滤 imports 清单 → 剩余配置类逐条件评估（类路径 → Bean → 属性）→ 失败项进 ConditionEvaluationReport；追问「@ConditionalOnClass 为什么改用 name 字符串？」——Java 24+ 的 ClassFileMetadataReader 急切解析类字面量，可选依赖缺失时评估前抛 ClassNotFoundException，name 形式只做类路径检查；
4. **「@ConditionalOnProperty 与 @Profile 怎么选？」**——按语义边界答：@Profile 表达环境身份（dev/test/prod 的整包 Bean 集合），@ConditionalOnProperty 表达功能开关（feature.enabled 的细粒度 Bean）；身份用 Profile、开关用 Property，混用会让"哪个开关控制哪批 Bean"失控；
5. **「自定义条件什么时候需要 ConfigurationCondition？」**——默认 phase 是 PARSE_CONFIGURATION（解析配置类时评估），当条件依赖"其他配置类已注册的 Bean"时（如"存在某 Bean 才注册我的 Bean"且对方在另一个配置类），必须实现 ConfigurationCondition 并返回 REGISTER_BEAN phase——推迟评估时机，否则顺序导致的误判无法靠 @AutoConfigureOrder 修复；
6. **「条件元数据与运行期评估的关系？」**——autoconfigure-processor 编译期生成 `META-INF/spring-autoconfigure-metadata.properties`（条件类名 + 属性），启动期按元数据**预过滤**：条件失败概率高的配置类连解析都不做——所以"改了条件但没重新构建元数据"会导致启动行为与代码不一致（IDE 增量编译漏跑处理器时的疑难杂症），排查手段是删掉元数据全量重建。
