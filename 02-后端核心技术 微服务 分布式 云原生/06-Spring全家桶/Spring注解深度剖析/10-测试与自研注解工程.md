## 1. @SpringBootTest 与上下文定制注解

@SpringBootTest 的完整属性：`webEnvironment`（MOCK 默认/RANDOM_PORT/DEFINED_PORT/NONE——RANDOM_PORT 走真实端口测完整 HTTP 链路，端口经 @LocalServerPort 注入，配 TestRestTemplate 测真实序列化与过滤器链）、`classes`（指定配置类替代自动扫描）、`properties`（内联属性覆盖，如 `properties = "app.cache.enabled=false"`）、`useMainMethod`（按主类 main 方法启动，测试与生产启动路径一致——排查"测试与生产行为不一致"时的对照手段）。

上下文定制五注解：`@TestConfiguration`（测试专用配置类——内嵌静态类 + 类内定义的 @Bean 仅对该测试生效，**优先级高于主配置**，是"测试里微调 Bean"的首选）；`@ContextConfiguration`（指定上下文加载来源）；`@ActiveProfiles("test")`（激活测试 profile）；`@TestPropertySource`（属性源覆盖）；`@Sql`（脚本初始化数据）。`@DynamicPropertySource` 是 Testcontainers 时代的标配——静态方法内注册容器地址到 Environment（`registry.add("spring.datasource.url", () -> container.getJdbcUrl())`），解决"容器随机端口先于上下文启动"的时序问题。@DirtiesContext 最后手段化：它使上下文缓存失效，高频使用是测试设计出问题的信号。

## 2. @MockitoBean：Bean 替换的官方姿势

Boot 4 移除了 @MockBean/@SpyBean，Spring Test 的 bean-override 体系正式接管：**@MockitoBean**（org.springframework.test.context.bean.override.mockito，按类型或 name 属性点名）与 **@MockitoSpyBean**。旧注解的问题：运行时替换容器 Bean 会**破坏测试上下文缓存**（缓存键含替换列表，不同测试类替换不同 Bean 时各自冷启动，套件慢数倍）；且替换语义不透明。新注解显式化"替换哪个 Bean"，配合 `@MockitoBean(types = ..., name = ...)` 精确点名。

工程纪律三条：优先 @Profile + 测试配置 Bean（如 `@Profile("test")` 的内存版支付客户端）而非运行时替换——mock 是最后手段；确需 mock 时把替换集合**标准化**（相同测试切片用相同替换列表，缓存键一致）；被替换的是容器 Bean，`@MockitoBean` 不影响手动 new 的对象（构造器注入场景直接 new + 传 mock，比容器替换更轻）。测试双保险：MockitoExtension 的 strict stubs 会拒绝未使用的打桩（UnnecessaryStubbingException），打桩即契约。

### 2.1 上下文缓存的机制细节

TestContext 框架按**缓存键**复用 ApplicationContext：配置类集合 + @ActiveProfiles + @TestPropertySource + webEnvironment + @MockitoBean 替换列表等组成键，键相同直接复用已启动上下文（毫秒级），键不同冷启动（秒级）。三条派生纪律：**profile 与属性标准化**（全部测试类用同一组 @ActiveProfiles 与属性文件，减少键分叉）；**替换列表收敛**（@MockitoBean 只出现在真正的集成测试里，切片测试用 @WebMvcTest 自带的轻量上下文）；**@DirtiesContext 最后手段化**——它主动失效缓存，套件里出现十个 @DirtiesContext 基本等于每次冷启动。压测发现测试慢，第一步永远是查缓存键分叉（打印 TestContext 缓存命中日志），而不是加机器。

## 3. 切片测试注解族

切片注解 = "只装配某一层"的预裁剪上下文：`@WebMvcTest(controllers = UserController.class)`（Web 层，默认注入 MockMvc，依赖的 Service 需 @MockitoBean 补）；`@DataJpaTest`（持久层 + 内嵌数据库，事务自动回滚）；`@DataRedisTest`/`@DataMongoTest` 等数据切片；`@RestClientTest`（RestClient 调用层）；`@AutoConfigureMockMvc`（@SpringBootTest 下补 MockMvc）。切片的价值公式：**上下文越小 → 启动越快 → 缓存共享率越高 → 套件越快**。选型规则：测 Controller 用 @WebMvcTest、测 Repository 用 @DataJpaTest、测完整链路（安全/序列化/异常）才上 @SpringBootTest(RANDOM_PORT)。

切片注解的机制本质：每个切片 = 一组**预裁剪的自动配置集合**（@WebMvcTest 只开 Web 相关自动配置、@DataJpaTest 只开数据访问自动配置）——理解这点后自定义切片 = 自定义自动配置裁剪集合，`includeFilters/excludeFilters` 属性可再微调。常见踩坑：@WebMvcTest 下**安全配置默认生效**（Security 过滤链还在，测试被 401 挡住——@AutoConfigureMockMvc(addFilters = false) 关闭或注入安全测试配置）；@DataJpaTest 默认内嵌 H2/HSQL，方言差异导致生产 SQL 不兼容时换 @AutoConfigureTestDatabase(replace = NONE) + @Testcontainers 真库。

## 4. 自研注解：元注解组合与 @AliasFor 透传

Spring 集成式自研注解的标准姿势是**元注解组合**——把框架注解叠在自己的注解上，配合 @AliasFor 透传属性：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
@Cacheable(cacheNames = "order")                 // 元注解：框架能力
public @interface OrderCached {
    @AliasFor(annotation = Cacheable.class, attribute = "key")
    String key();                                 // 透传 key 表达式
    @AliasFor(annotation = Cacheable.class, attribute = "condition")
    String condition() default "";
}
```

机制闭环：@Cacheable 在元注解链上 → MergedAnnotations 合并时 @AliasFor 把 OrderCached.key 覆写进 Cacheable.key → 缓存基础设施（AnnotationCacheOperationSource）读到的就是合并后的完整 @Cacheable——**框架升级新增属性自动可用**（不拷属性即免维护）。工程纪律：属性透传是"按需暴露"而非全量拷贝（团队只该暴露自己的语义）；@AliasFor 双向成对声明；注解必须 @Retention(RUNTIME) + @Documented。同模式的实战家族：@MyLog（叠 @Around 切点标记）、@RateLimit（叠 @ConcurrencyLimit 或自定义拦截）、@ApiVersion 风格的多版本声明。验收环节补一条：用 `AnnotatedElementUtils.findMergedAnnotation` 在单元测试里断言合并结果——透传属性名写错时框架静默拿到默认值，测试断言是唯一可靠的回归防线。

## 5. 自定义 @Conditional 与 @EnableXxx starter 模式

**自定义条件注解**的三层结构：`@Conditional(OnXxxCondition.class)` 元注解 → Condition 实现（读 AnnotatedTypeMetadata 拿注解属性 + ConditionContext 查环境/Bean 注册表）→ 业务注解消费。典型场景："配置中心某个开关开启才装配"（@ConditionalOnProperty 的定制版）、"某个中间件探活成功才装配"。条件实现必须无状态（可能缓存复用，03 篇已述）。自定义条件与配置属性类通常是同一组件的三件套：条件注解 + Condition 实现 + @ConfigurationProperties 属性类——三者共同构成"带开关的自动配置组件"。

**@EnableXxx starter 模式**是自研组件的对外接口规范，五步走：定义 @EnableMyFeature 注解（@Import 自己的配置类或 ImportSelector）→ 配置类上 @AutoConfiguration + @ConditionalOnClass(name = "...")（**字符串形式，03 篇的 2026 最佳实践**）→ 属性类 @ConfigurationProperties(prefix = "my.feature") + record → 登记进 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` → autoconfigure-processor 生成条件元数据。验收标准：引入依赖即可用（自动装配）、@EnableMyFeature 可显式开关（手动模式）、条件不满足时启动零痕迹。

## 6. 高频坑与面试题

1. **@MockitoBean 打碎上下文缓存**：每类不同替换列表 → 每次冷启动——标准化替换集合或改用 @Profile 测试 Bean；替换列表进入缓存键是 Boot 4 升级后测试变慢的头号原因；
2. **自研注解忘记 @Retention(RUNTIME)**：默认 CLASS 导致 Spring 合并层读不到——自研注解的第一个事故；
3. **@AliasFor 透传属性名写错**：框架静默拿到默认值（属性没透传成功），消费端必须验证合并结果（AnnotatedElementUtils 读取断言）；
4. **面试必答框架**：「怎么做一个 @EnableXxx 的 starter？」——@Import 模式 + @AutoConfiguration + 条件装配（@ConditionalOnClass 字符串形式）+ imports 清单登记 + 元数据生成，五步闭环；追问「元注解组合为什么比拷贝属性好？」——合并层自动继承框架注解的完整语义与后续演进（框架新增属性零成本可用），拷贝属性则随框架升级漂移；
5. **「@TestConfiguration 与 @Import(Config.class) 的差别？」**——@TestConfiguration 的 Bean 优先级更高（先于主配置注册，可覆盖自动配置 Bean）且**不参与组件扫描**（只在测试上下文显式生效，无污染生产的风险）——测试微调用 @TestConfiguration，复用生产配置用 @Import；
6. **「自研注解的验收清单？」**——五条：Retention(RUNTIME) 显式声明、@AliasFor 双向成对、消费端走 MergedAnnotations（裸反射读不到合并语义）、属性新增带 default（向后兼容）、注解处理器/切面缓存解析结果（性能纪律）——五条全过才允许进团队规范。
