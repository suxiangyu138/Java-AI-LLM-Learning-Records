## 1. 故障一：消息堆积

### 1.1 现象与定位

```text
现象：消费延迟越来越大 / 积压消息数持续增长
```

```bash
# Kafka：消费组延迟
kafka-consumer-groups --bootstrap-server localhost:9092 \
  --describe --group order-group
# LAG 列：积压量（持续增长 = 生产 > 消费）

# RocketMQ：堆积
mqadmin consumerProgress -n localhost:9876 -g order-group

# RabbitMQ：队列积压
rabbitmqctl list_queues name messages consumers

# 通用公式：堆积量 = 生产速率 - 消费速率
```

### 1.2 根因矩阵

| 根因 | 特征 | 解决 |
|------|------|------|
| **消费变慢** | 消费速率下降（DB/下游慢） | 优化消费逻辑/下游 |
| **消费者减少** | 实例挂/缩容 | 扩容消费者 |
| **生产激增** | 堆积从某时间点开始（大促/异常） | 限流/扩容 |
| **消费失败重试** | 失败重试占满消费线程 | 修失败原因（见故障二） |
| 分区/队列不均 | 热点分区 | 分区键优化 |

```text
堆积处理（紧急 → 根治）：
  ① 扩容消费者（Kafka 加分区才有效——消费并行度 = 分区数）
  ② 临时跳过（跳过阻塞消息，先消化存量）
  ③ 根治：消费逻辑/下游性能/失败原因
```

> 🎯 **Kafka 堆积的扩容铁律**：**消费者扩容上限 = 分区数**——分区 3 个，加 10 个消费者也没用；堆积严重先确认"分区数是否够"。

## 2. 故障二：消费失败与重试风暴

### 2.1 现象

```text
现象：消费失败率升高 + 重试风暴（同一消息反复重试）+ 堆积
```

```bash
# Kafka：查看消费组状态（重试风暴看消费速率与错误日志）
kafka-consumer-groups --describe --group order-group
# 消费者日志：同一消息反复处理（重试）

# RocketMQ：重试队列堆积
# RabbitMQ：死信队列增长
```

### 2.2 重试风暴的元凶

| 元凶 | 特征 | 解决 |
|------|------|------|
| **下游故障**（DB/HTTP） | 全部消息失败 | 修下游（熔断降级） |
| 代码 Bug | 特定消息必失败（反序列化） | 修代码 + 死信隔离 |
| 重试参数不当 | 重试间隔太短/次数太多 | 退避 + 上限 |
| 幂等缺失 | 重试导致副作用放大 | 幂等处理（见故障三） |

```text
重试策略建议：
  退避重试（指数退避）+ 次数上限（3-5 次）
  超限进死信（见 08）——防止毒丸消息无限重试
```

> ⚠️ **重试风暴的本质**：重试是"给瞬时故障的机会"，不是"给永久故障的机会"——**永久失败（数据/反序列化）应立即进死信**，否则重试 = 自残。

## 3. 故障三：重复消费

### 3.1 为什么会重复

```text
重复消费是"至少一次"语义的必然结果：
  Kafka：处理成功后提交 offset 前崩溃 → 重启重读
  RocketMQ：消费成功后 ACK 丢失 → 重投
  RabbitMQ：NACK 后重投

不是 Bug，是语义代价——业务必须幂等！
```

### 3.2 幂等方案

| 方案 | 说明 |
|------|------|
| **唯一业务键** | 消息带业务 ID（orderId），DB 唯一约束/去重表 |
| 状态机 | 处理前检查状态（已处理则跳过） |
| Redis 去重 | `SETNX` 消息 ID（带 TTL） |
| 数据库幂等表 | 消息 ID + 处理结果落库（唯一索引） |

```text
幂等设计三步：
  ① 消息必须携带业务唯一键（orderId/messageId）
  ② 消费前检查（DB 唯一约束最可靠）
  ③ 处理结果幂等（重复执行结果一致）
```

> 🎯 **幂等是消息系统的第一工程纪律**：**"至少一次"语义下，不幂等 = 迟早出事故**（重复下单/重复扣款）——唯一业务键 + DB 唯一约束是标准解。

## 4. 故障四：顺序错乱

### 4.1 顺序保证的边界

```text
各 MQ 的顺序能力：
  Kafka：分区内有序（同 key 同分区）
  RocketMQ：队列内有序（顺序消息）
  RabbitMQ：单队列有序（并发消费破序）

关键：顺序只对"同 key"有意义（订单的创建→支付→取消）
```

### 4.2 顺序错乱的原因

| 原因 | 场景 | 解决 |
|------|------|------|
| 分区键变化 | 订单 ID 作 key 但偶尔变化 | 稳定 key |
| 多消费者 | 同 key 被不同消费者并行 | 分区内单消费者 |
| 重试乱序 | 消息 A 失败重试，B 先处理 | 顺序消息 + 重试策略 |
| 本地缓存 key 不一致 | 分片逻辑不一致 | 统一分区逻辑 |

> 🎯 **顺序与性能的权衡**：顺序消息牺牲并行度（同 key 串行）——**只对真正需要顺序的业务用**（订单流转），其余并行。

## 5. MQ 通用排查路径

```text
MQ 故障排查五步：
  ① 堆积量：LAG/队列积压（开始时间 = 故障时间）
  ② 消费速率：消费速率曲线（变慢了？）
  ③ 失败日志：消费错误（失败原因分类）
  ④ 下游状态：DB/HTTP/Redis（下游是否故障）
  ⑤ 幂等检查：重复是否在造成副作用
```

| 步骤 | 工具 | 结论 |
|------|------|------|
| ① 堆积 | kafka-consumer-groups / rabbitmqctl | 故障时间点 |
| ② 速率 | 消费监控 | 消费变慢 vs 生产激增 |
| ③ 错误 | 消费者日志 | 失败原因 |
| ④ 下游 | 下游监控 | 下游故障传导 |
| ⑤ 幂等 | 业务日志 | 重复副作用 |

> 💡 与[日志监控指标](../日志监控指标/00-日志监控指标总览.md)联动：堆积量/消费速率/失败率都是核心监控项——**堆积告警要在"开始堆积"就触发**，不是堆满了才响。

## 6. 核心要点

> 🎯 **核心要点**：
> - 堆积 = 生产速率 - 消费速率：先看拐点（故障时间）再分"消费慢"还是"生产快"；
> - Kafka 扩容上限 = 分区数（堆积先看分区够不够）；
> - 重试风暴：退避 + 上限 + **永久失败立即进死信**；
> - 重复消费是"至少一次"的语义代价——**幂等是铁律**（唯一键 + DB 唯一约束）；
> - 顺序只对同 key 有意义：稳定分区键 + 单消费者，牺牲并行度换顺序；
> - 排查五步：堆积 → 速率 → 错误 → 下游 → 幂等。
