## 1. 灰度落地四方案对比

| 方案 | 原理 | 精确度 | 复杂度 | 适用 |
|------|------|--------|--------|------|
| **Argo Rollouts** | K8s 原生渐进交付（副本/权重 + 分析自动回滚） | 高 | 中 | **K8s 团队首选** |
| **Istio** | Service Mesh 权重路由（VirtualService） | 最高（可到 1% 级） | 高（需 Mesh） | 已上 Mesh 的团队 |
| **Nacos 配置灰度** | 配置中心按服务/标签灰度发布配置 | 中（配置级） | 低 | 配置变更灰度 |
| **网关灰度** | 网关按 Header/权重路由 | 中高 | 低 | 无 Mesh 的微服务团队 |

> 🎯 **选型主线**：有 Istio → 权重路由；无 Mesh 的 K8s → Argo Rollouts；只改配置 → Nacos 灰度；非 K8s → 网关灰度。

## 2. Argo Rollouts：K8s 原生渐进交付

### 2.1 为什么用 Rollouts

```text
原生 Deployment 滚动更新的局限：
  无法控制流量比例（只能按实例数）
  无法基于指标自动回滚
  无发布过程的灰度视图

Argo Rollouts 提供：
  金丝雀/蓝绿策略（渐进放量）
  AnalysisTemplate（指标分析自动决策）
  可视化发布进度（Rollout UI）
```

### 2.2 金丝雀配置

```yaml
# rollout.yaml（替代 Deployment）
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: order-service
spec:
  replicas: 5
  strategy:
    canary:
      steps:
        - setWeight: 10          # ① 10% 流量
        - pause: { duration: 5m }  # 观察 5 分钟
        - setWeight: 30          # ② 30%
        - pause: { duration: 5m }
        - setWeight: 60          # ③ 60%
        - pause: { duration: 5m }
        - setWeight: 100         # ④ 全量
      analysis:
        templates:
          - templateName: success-rate   # 指标分析模板
  selector:
    matchLabels: { app: order-service }
  template:
    metadata:
      labels: { app: order-service }
    spec:
      containers:
      - name: order-service
        image: harbor.example.com/prod/order-service:1.0.4
```

### 2.3 自动分析回滚（AnalysisTemplate）

```yaml
# analysis-template.yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
  - name: success-rate
    interval: 1m
    successCondition: result[0] >= 0.99        # 成功率 ≥ 99%
    failureLimit: 3
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{job="order-service",code=~"5.."}[1m]))
          / sum(rate(http_requests_total{job="order-service"}[1m]))
```

```bash
# 发布与回滚
kubectl -n production set image rollout/order-service \
  order-service=harbor.example.com/prod/order-service:1.0.4
kubectl -n production rollout status rollout/order-service
kubectl -n production rollout undo rollout/order-service    # 手动回滚
# 指标分析失败 → 自动回滚（无需人工）
```

> 🎯 **Rollouts 的核心价值**：**放量节奏（steps）+ 指标分析（AnalysisTemplate）+ 自动回滚**三位一体——"灰度三件套"的平台化实现。

## 3. Istio：权重路由灰度

### 3.1 配置

```yaml
# 两个版本（同 Service）
apiVersion: apps/v1
kind: Deployment
metadata: { name: order-v1 }
spec:
  template:
    metadata: { labels: { app: order, version: v1 } }
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: order-v2 }
spec:
  template:
    metadata: { labels: { app: order, version: v2 } }

# 权重路由
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: order-vs
spec:
  hosts: [order-service]
  http:
  - route:
    - destination: { host: order-service, subset: v1 }
      weight: 90
    - destination: { host: order-service, subset: v2 }
      weight: 10
---
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: order-dr
spec:
  host: order-service
  subsets:
  - name: v1
    labels: { version: v1 }
  - name: v2
    labels: { version: v2 }
```

```bash
# 渐进调整权重（10% → 30% → 60% → 100%）
kubectl apply -f vs-10.yaml    # 修改 weight 后重新 apply
```

### 3.2 Istio 灰度优势

| 能力 | 说明 |
|------|------|
| 精确权重 | 可到 1% 级（比副本比例更细） |
| 按 Header 路由 | 深红发布（`headers: {x-user-group: {exact: vip}}`） |
| 流量镜像 | 影子流量（新版本只收拷贝流量不响应） |
| 与可观测集成 | 指标/链路天然支持 |

```yaml
# 按请求头路由（深红/VIP 先试）
http:
- match:
  - headers:
      x-user-group: { exact: "internal" }
  route:
  - destination: { host: order-service, subset: v2 }
- route:
  - destination: { host: order-service, subset: v1 }
```

## 4. Nacos 配置灰度

```text
场景：只改配置（开关/阈值/比例）也想灰度——Nacos 配置中心原生支持
```

```bash
# Nacos 控制台发布配置时：
# 选择"灰度发布" → 配置灰度规则：
#   按服务名/分组/IP/标签 选择灰度目标
# 灰度配置只对命中规则的实例生效
```

```yaml
# 灰度规则示例（Nacos 控制台配置）
# 灰度目标：IP 为 10.0.0.5 的实例
# 配置内容：feature.flag=true（灰度实例开启新功能）
```

| 场景 | 说明 |
|------|------|
| 功能开关灰度 | 灰度实例开启新逻辑 |
| 阈值调整灰度 | 部分实例先调 |
| 配置回滚 | Nacos 配置历史版本一键回滚 |
| 与发布联动 | 新版本 + 新配置同时灰度 |

> 💡 **配置灰度 vs 版本灰度**：版本灰度用 Rollouts/Istio；**配置灰度用 Nacos**——先切配置后切代码（或反之）的精细组合是成熟团队的常规操作。

## 5. 网关灰度（Spring Cloud Gateway）

```text
无 Service Mesh 的微服务团队的灰度方案：
  网关按 Header/Cookie 路由到不同版本服务
```

```yaml
# Spring Cloud Gateway 灰度路由（按版本分组）
spring:
  cloud:
    gateway:
      routes:
        - id: order-v1
          uri: lb://order-service-v1        # 灰度组
          predicates:
            - Path=/api/orders/**
          filters:
            - name: Weight
              args: { group: order, weight: 90 }    # 90% 权重
        - id: order-v2
          uri: lb://order-service-v2
          predicates:
            - Path=/api/orders/**
          filters:
            - name: Weight
              args: { group: order, weight: 10 }    # 10% 权重
```

```text
网关灰度要点：
  ① 服务注册时打版本标签（Nacos metadata: version=v2）
  ② 网关按版本路由（权重/Header）
  ③ 灰度实例组独立部署（order-service-v2 注册名）
  ④ 放量节奏改网关配置（动态刷新）
```

> ⚠️ **网关灰度的局限**：只控制"入口流量"——**服务间调用（A 调 B）不走网关**，内部调用灰度需注册中心标签路由或 Mesh。

## 6. 灰度可观测与自动回滚

### 6.1 灰度观察指标

| 指标 | 观察内容 |
|------|---------|
| 错误率 | 灰度组 vs 稳定组对比 |
| p99 延迟 | 性能劣化信号 |
| 资源占用 | CPU/内存（新版本膨胀） |
| 业务指标 | 下单成功率/转化率（深红/A-B 场景） |
| 日志异常 | ERROR 数量对比 |

```text
对比方法（灰度组 vs 稳定组）：
  Grafana 面板按 version 标签分组对比
  或 Rollouts AnalysisTemplate 自动对比（见 2.3）
```

### 6.2 自动回滚阈值（参考）

| 指标 | 自动回滚阈值 |
|------|-------------|
| 错误率 | 灰度组错误率 > 稳定组 2 倍 或 > 1% |
| p99 延迟 | 超过稳定组 1.5 倍持续 5 分钟 |
| 资源 | CPU > 80% 持续 5 分钟 |

> 🎯 **自动回滚的前提**：指标对比必须"灰度组 vs 稳定组"（绝对值判断会误伤大促等正常波动）。

## 7. 灰度落地检查清单

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | 灰度目标明确 | 新版本？配置？哪个服务？ |
| 2 | 放量节奏定义 | 10-30-60-100（每步观察时长） |
| 3 | 指标对比面板 | 灰度 vs 稳定（version 标签） |
| 4 | 自动回滚阈值 | 错误率/延迟阈值定义 |
| 5 | 回滚演练 | 灰度异常时能否秒级切回 |
| 6 | 数据库兼容 | 新旧版本共用 DB 的兼容性 |
| 7 | 日志/链路 | 灰度实例可识别（version 标签入日志） |
| 8 | 通知机制 | 灰度各阶段通知团队 |

## 8. 核心要点

> 🎯 **核心要点**：
> - 四方案：Rollouts（K8s 首选）、Istio（最精确）、Nacos（配置级）、网关（无 Mesh 兜底）；
> - Rollouts 三位一体：steps 放量 + AnalysisTemplate 分析 + 自动回滚；
> - Istio：权重到 1% 级、Header 路由做深红、流量镜像做影子发布；
> - Nacos 配置灰度：配置变更的"轻量灰度"，与版本灰度组合使用；
> - 网关灰度局限：只管入口流量，服务间调用需注册中心标签路由；
> - 自动回滚前提：灰度 vs 稳定组对比（不是绝对值）；
> - 8 项检查清单：节奏、指标、回滚、DB 兼容、可识别（version 入日志）缺一不可。
