## 1. upstream 基本配置

```nginx
upstream backend_pool {
    server 192.168.1.100:8080 weight=3;
    server 192.168.1.101:8080;
    server 192.168.1.102:8080 backup;
}

server {
    listen 80;
    location / {
        proxy_pass http://backend_pool;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

| 要素 | 说明 |
|------|------|
| `upstream` | 后端服务器组定义 |
| `server` | 组内成员（IP:端口 + 参数） |
| `proxy_pass http://backend_pool` | 转发到组（按策略分发） |

## 2. 四种负载均衡策略（面试必问）

| 策略 | 配置 | 原理 | 适用 |
|------|------|------|------|
| **轮询（默认）** | 无参数 | 请求依次分发 | 后端配置均衡 |
| **加权轮询** | `weight=3` | 按权重比例分发 | 机器配置不均 |
| **最少连接** | `least_conn;` | 发给活动连接最少者 | 请求耗时差异大 |
| **IP 哈希** | `ip_hash;` | 同 IP 固定同后端 | 会话亲和（sticky） |

```nginx
# 最少连接
upstream backend {
    least_conn;
    server 192.168.1.100:8080;
    server 192.168.1.101:8080;
}

# IP 哈希（会话保持）
upstream backend {
    ip_hash;
    server 192.168.1.100:8080;
    server 192.168.1.101:8080;
}
```

> 🎯 **策略选择**：无状态服务 → 轮询/least_conn；有状态（无独立 Session 存储）→ ip_hash；**微服务推荐无状态 + 轮询/least_conn**（Session 外置到 Redis）。

## 3. 关键参数详解

| 参数 | 默认 | 说明 |
|------|------|------|
| `weight` | 1 | 权重（weight=3 分 3 倍流量） |
| `max_fails` | 1 | 连续失败 N 次判为不可用 |
| `fail_timeout` | 10s | 失败后暂停时长 |
| `backup` | - | 备用节点（主节点全挂才启用） |
| `down` | - | 手动下线（不参与调度） |

```nginx
upstream backend {
    server 192.168.1.100:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 192.168.1.101:8080 max_fails=3 fail_timeout=30s;
    server 192.168.1.102:8080 backup;        # 备用：前两台挂才启用
    server 192.168.1.103:8080 down;          # 手动下线（维护中）
}
```

> 💡 **backup 的运维价值**：主节点全挂自动启用备用（容量兜底）；`down` 用于维护时优雅下线（不删配置）。

## 4. 健康检查与故障转移

### 4.1 被动健康检查（默认）

```text
被动检查：请求失败（max_fails）→ 标记不可用（fail_timeout）→ 恢复后自动回归
  无需额外配置（内置）
  局限：不发主动探活（坏节点在无人访问时不被发现）
```

### 4.2 主动健康检查（商业版/第三方）

```text
主动检查：定时探测（如每 5s 请求 /health）
  商业版 nginx plus 内置 health_check
  开源替代：第三方模块 nginx_upstream_check_module
```

### 4.3 故障转移（proxy_next_upstream）

```nginx
# 上游失败时自动切换到下一个后端
proxy_next_upstream error timeout invalid_header http_500 http_502 http_503;

# 注意：不转移 4xx（客户端错误不是上游问题）
# 生产配置参考
proxy_next_upstream error timeout http_500 http_502 http_503 http_504;
proxy_next_upstream_tries 2;     # 最多尝试 2 个后端
```

| 转移条件 | 说明 |
|----------|------|
| `error` / `timeout` | 连接错误/超时 |
| `http_500/502/503/504` | 服务端错误（转移） |
| **不转移 4xx** | 客户端错误与上游无关 |
| `proxy_next_upstream_tries` | 尝试次数上限 |

> ⚠️ **转移与幂等**：自动转移 = 请求会打到第二个后端——**非幂等请求（下单）重放风险**：业务侧幂等键兜底（见 [05-HTTP层问题排查](../网络问题排查/05-HTTP层问题排查.md)）。

## 5. keepalive 连接复用

```nginx
upstream backend {
    server 192.168.1.100:8080;
    server 192.168.1.101:8080;
    keepalive 32;                    # Nginx 与后端保持的空闲连接数
}

server {
    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;      # keepalive 需要 HTTP/1.1
        proxy_set_header Connection "";   # 清空 Connection（复用）
    }
}
```

```text
keepalive 的价值：
  减少 Nginx ↔ 后端 的 TCP 握手开销
  高并发下显著降低连接建立成本

三件套：
  upstream 内 keepalive N
  proxy_http_version 1.1
  proxy_set_header Connection "";
```

> 🎯 **keepalive 是性能加分项**：面试问"Nginx 怎么优化与后端的连接"——答 keepalive 三件套（复用连接减少握手）。

## 6. 典型应用场景

| 场景 | 配置要点 |
|------|---------|
| 多实例水平扩展 | upstream + 轮询/least_conn |
| 蓝绿部署 | 两个 upstream（蓝/绿）+ 切换 proxy_pass |
| 灰度发布 | 加权轮询调整权重（见 CI/CD 体系） |
| 会话保持 | ip_hash（有状态场景） |
| 高可用 | backup 备用节点 + 故障转移 |

```nginx
# 蓝绿部署的 Nginx 视角
upstream blue  { server 192.168.1.100:8080; }
upstream green { server 192.168.1.101:8080; }
# 切换：proxy_pass http://green;（或加权调整）
```

> 💡 与 [CI/CD 灰度发布](../CI%20CD灰度发布/00-CI-CD与灰度发布总览.md) 联动：Nginx 权重调整是"无 Mesh 团队"的灰度手段之一；K8s 场景用 Argo Rollouts/Istio。

## 7. 核心要点

> 🎯 **核心要点**：
> - 四策略：轮询（默认）/加权（weight）/最少连接（least_conn）/IP 哈希（ip_hash）——面试必问；
> - 参数四件套：weight/max_fails/fail_timeout/backup；
> - 故障转移：`proxy_next_upstream`（error/timeout/5xx）+ 不转移 4xx；注意幂等重放；
> - keepalive 三件套：upstream keepalive + HTTP/1.1 + Connection ""（性能加分项）；
> - 被动健康检查内置（max_fails），主动检查需商业版/第三方模块；
> - 微服务推荐无状态 + 轮询/least_conn；有状态用 ip_hash。
