## 1. 落地路线图

```text
第一阶段：应用侧地基（1 周）
  SLF4J + Logback 规范（MDC/滚动/异步/JSON）
  Actuator 暴露指标 + 业务埋点（Micrometer）
  → 产出：每个服务"日志可查、指标可看"

第二阶段：平台侧建设（2 周）
  Prometheus（指标采集）+ Grafana（面板）
  Loki + Alloy（日志采集）
  → 产出：统一查询入口（LGTM）

第三阶段：告警与 SLO（1 周）
  核心服务 SLO 定义 → 燃烧率告警 → 分级通知
  → 产出：告警"响得值得"

第四阶段：链路与融合（2 周）
  OTel Java Agent 接入 → Tempo 链路 → 三支柱关联
  → 产出：指标→日志→链路一键跳转

第五阶段：治理与 AI（持续）
  告警准确率治理 → 成本优化 → 容量预测
```

| 阶段 | 关键度量 |
|------|---------|
| 应用侧 | 服务接入率 100% |
| 平台侧 | 查询耗时 p50 < 3s |
| 告警 | 告警准确率 > 80% |
| 链路 | 核心服务链路覆盖率 |
| 治理 | MTTA/MTTR 趋势 |

## 2. 落地检查清单

### 2.1 应用侧（开发自查）

| # | 检查项 | 说明 |
|---|--------|------|
| 1 | 日志走 SLF4J | 无 System.out/printStackTrace |
| 2 | 参数化占位符 | 无字符串拼接 |
| 3 | MDC 注入 traceId/userId | 入口 put、finally remove、线程池传递 |
| 4 | Pattern 含 %X{traceId} | 链路可关联 |
| 5 | 滚动策略 + 总量上限 | 磁盘安全 |
| 6 | 敏感信息脱敏 | 手机号/密码打码 |
| 7 | Actuator 暴露 prometheus | curl 可拉指标 |
| 8 | 业务埋点 | 核心操作 Counter/Timer |
| 9 | 标签低基数 | 无用户 ID/订单 ID 进标签 |
| 10 | JSON 日志 | 采集平台直接解析 |

| # | 检查项 | 说明 |

| 1 | 采集器 DaemonSet | 每节点 Alloy/Fluent Bit |
| 2 | 日志保留策略 | dev 7 天 / prod 180 天 |
| 3 | 磁盘监控 | LokiDiskUsageHigh > 85% 告警 |
| 4 | OTel 采样已配置 | 第一天就配（防成本爆炸） |

## 3. 成本规划

### 3.1 自托管 vs 托管

```text
自托管（Prometheus + Loki + Tempo + Grafana）：
  约为同等规模 Datadog 费用的 1/4 ~ 1/10，全开源

托管（Grafana Cloud 等）：
  团队 < 10 人且流量 < 500 req/s 时消除运维负担
  代价：厂商锁定 + 更高成本
```

### 3.2 成本参考（某生产案例，AWS EKS，31 天保留）

| 流量规模 | 月成本（自托管） |
|----------|-----------------|
| < 500 req/s | 约 $600 |
| 500-2K req/s | 约 $2,400 |
| 2K-10K req/s | 约 $8,500 |
| > 10K req/s | $22,000+ |

### 3.3 成本控制杠杆

| 杠杆 | 手段 |
|------|------|
| 采样 | OTel 概率/尾部采样（第一天就配） |
| 保留期 | 分层保留（dev 7 天 / prod 180 天） |
| 标签基数 | 控制 Prometheus/Loki 标签（基数爆炸 = 存储爆炸） |
| 日志量 | 采集端过滤噪声、级别策略、JSON 压缩 |
| 面板优化 | recording rules 替代复杂 PromQL 子查询 |

> ⚠️ **成本三大黑洞**：不采样（追踪爆炸）、标签基数失控（序列爆炸）、日志全量保留（存储爆炸）——第一天就要防。

## 4. 高频避坑清单

| # | 坑 | 现象 | 规避 |
|---|----|------|------|
| 1 | 日志框架冲突 | 双 SLF4J 绑定/栈溢出 | 单一绑定 + 桥接包单向 |
| 2 | MDC 不清理 | 线程池复用串号（A 请求日志带 B 的 userId） | finally remove / TaskDecorator |
| 3 | Pattern 带 %caller | 高并发性能劣化 | 生产禁 %caller/%L |
| 4 | 异步日志丢数据 | 队列满/宕机丢审计日志 | 核心日志同步 + neverBlock 权衡 |
| 5 | 标签基数爆炸 | Prometheus/Loki 查询变慢/存储暴涨 | 低基数标签纪律 |
| 6 | 不采样 | 追踪成本失控被迫关闭 | 第一天配采样 |
| 7 | OTel Collector OOM | memory_limiter 过低或 batch 过大 | memory_limiter 第一、batch 最后 |
| 8 | 告警疲劳 | 告警太多没人看 | 分级 + 燃烧率 + 准确率治理 |
| 9 | 只建指标不建日志链路 | 告警响了查不到根因 | 三支柱同步建设 |
| 10 | 忽略磁盘监控 | Loki/ES 磁盘写满停摆 | LokiDiskUsageHigh 告警 |

## 5. 面试题

| 题目 | 答题要点 |
|------|---------|
| SLF4J 是什么？为什么用它？ | 日志门面：业务代码与实现解耦；换实现不改代码；参数化占位符 |
| Logback 与 Log4j2 怎么选？ | Logback：Spring Boot 默认、稳妥；Log4j2：Disruptor 异步吞吐高，但安全历史需 2.20.0+ 管控 |
| MDC 是什么？异步场景怎么处理？ | 线程上下文（traceId/userId）；ThreadLocal 本质，线程池需 TaskDecorator/TTL 传递 + finally 清理 |
| 异步日志的坑？ | 队列满丢弃（neverBlock）、宕机丢日志；审计日志不同步 |
| 日志滚动策略怎么配？ | 按天 + 单文件大小 + 总量上限；charset UTF-8；pattern 含 %d 占位符 |
| EFK 和 Loki 的区别？ | 全文索引 vs 标签索引；查询能力 vs 成本；K8s 大多数场景 Loki 更优 |
| JVM 监控看哪些指标？ | 内存（used/max/live data）、GC（停顿/次数）、线程（live/blocked）、类加载 |
| 内存泄漏的指标信号？ | GC 后 live data 持续增长、Metaspace 持续增长、used 持续高位 |
| SLO 是什么？怎么设计？ | SLI（可测量指标）→ SLO（目标值）→ 错误预算（1-SLO）；业务与成本平衡 |
| 燃烧率告警是什么？ | 实际错误率/允许错误率；14x/30min Page + 2x/6h Warning（Google SRE） |
| 三支柱怎么关联？ | traceId 贯穿：MDC 注入日志、OTel 生成链路；Grafana 一键跳转 |
| OpenTelemetry 解决什么？ | 统一三支柱 API/SDK：一次埋点任意导出、避免厂商锁定、Java Agent 零代码 |
| 采样为什么必须配？ | 不采样追踪成本爆炸被迫关闭；概率（便宜）vs 尾部（错误可查） |
| 标签基数为什么危险？ | 标签是笛卡尔积：3 个标签各 10 值 = 1000 条序列；无界值（用户 ID）进标签 = 爆炸 |

## 6. 核心要点

> 🎯 **核心要点**：
> - 落地五阶段：应用侧（日志+指标）→ 平台侧（LGTM）→ 告警 SLO → 链路融合 → 治理；
> - 应用侧 10 项自查：SLF4J/参数化/MDC/滚动/脱敏/Actuator/埋点/标签/JSON；
> - 成本三黑洞：不采样、标签基数、全量保留——第一天防；
> - 避坑 Top3：MDC 串号、标签爆炸、不采样；
> - 面试主线：门面 → 选型 → MDC → 滚动/异步 → JVM 指标 → SLO 燃烧率 → 三支柱 → OTel；
> - 与同级 Prometheus 体系（10 篇）联动阅读：采集细节在那边，指标语义与 SLO 在本体系。
