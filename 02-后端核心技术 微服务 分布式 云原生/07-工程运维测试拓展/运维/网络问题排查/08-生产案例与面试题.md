## 1. 案例一：偶发 Connection reset（连接池坑）

```text
现象：生产偶发 "Connection reset by peer"，重启后短暂恢复，又复发
```

```text
排查过程：
① 抓包：连接建立后空闲一段时间 → 服务端发 RST
② 服务端确认：Nginx keepalive_timeout = 60s（空闲 60s 回收）
③ 客户端确认：连接池空闲连接未验证，复用被回收的连接
④ 根因：池的"空闲超时 > 服务端 keepalive" + 无复用验证

解决：
  池 max-idle-time < 服务端 keepalive_timeout（60s）
  或复用前验证（testOnBorrow）
```

| 教训 | 说明 |
|------|------|
| 偶发 reset 先抓包看时机 | RST 发生在"空闲后"= 超时回收 |
| 两端参数要对齐 | 池空闲超时 < 对端 keepalive |
| 复用必须验证 | 连接池验证查询（SELECT 1） |

## 2. 案例二：迁移后全部超时（防火墙）

```text
现象：服务从机房 A 迁移到云上后，客户端访问全部 Connection timed out
```

```text
排查过程：
① ping 通（网络层 OK）
② telnet 8080 超时（传输层被拦）
③ 本地访问服务正常（服务端应用 OK）
④ 确认：云安全组/防火墙未放行 8080

解决：安全组放行端口 → 恢复
```

| 教训 | 说明 |
|------|------|
| ping 通 ≠ 端口通 | 网络层与传输层分开验证 |
| 迁移必查安全组 | 云环境防火墙是迁移后第一嫌疑 |
| telnet 区分两种失败 | timeout（drop）vs refused（未监听） |

## 3. 案例三：域名变更后 Java 连旧 IP

```text
现象：CDN IP 切换后，部分 Java 应用仍连旧 IP（旧 IP 已下线）
```

```text
排查过程：
① 浏览器访问正常（新 IP）
② Java 应用日志：连接旧 IP 失败
③ 检查 JVM 参数：networkaddress.cache.ttl=-1（永久缓存！）
④ 根因：JVM DNS 缓存永久化，重启才刷新

解决：
  启动参数 -Dnetworkaddress.cache.ttl=30
  或 java.security 配置统一
  变更流程：先降 TTL 再切换
```

| 教训 | 说明 |
|------|------|
| Java DNS 缓存是隐蔽层 | 解析失败先查 JVM 缓存参数 |
| IP 变更规范 | 先降 TTL → 切换 → 等缓存过期 |
| 浏览器正常不代表应用正常 | 各层缓存独立 |

## 4. 案例四：CLOSE_WAIT 堆积（泄漏）

```text
现象：服务响应越来越慢，最终无法接受新连接；ss 显示 CLOSE_WAIT 数千
```

```text
排查过程：
① ss -tn state close-wait | wc -l：持续增长
② jstack：大量线程阻塞在响应读取
③ 代码审查：HTTP 客户端响应体未关闭（缺 try-with-resources）
④ 根因：连接泄漏 → 句柄耗尽 → 无法建连

解决：
  修复泄漏（关闭响应体/归还连接池）
  临时：重启 + 句柄上限监控
```

| 教训 | 说明 |
|------|------|
| CLOSE_WAIT 是代码问题 | 不是网络问题，重启只缓解 |
| 监控句柄 | 文件描述符使用率告警 |
| try-with-resources | 流/响应体必须自动关闭 |

## 5. 案例五：K8s Service 偶发不通

```text
现象：集群内调用 Service 偶发失败，时好时坏
```

```text
排查过程：
① kubectl get endpoints：部分实例缺失
② kubectl get pods：某副本 CrashLoopBackOff（不健康）
③ 根因：坏副本被轮询到 → 请求失败；健康副本正常 → 时好时坏

解决：
  修复坏副本（资源/代码问题）
  readinessProbe 配置（不健康自动摘除）
```

| 教训 | 说明 |
|------|------|
| 偶发失败先看 endpoints | 部分实例缺失 = 有坏副本 |
| readinessProbe 必配 | 不健康自动摘流 |
| 时好时坏 = 概率问题 | 通常是一个坏实例在轮询中 |

## 6. 案例六：微服务调用"请求没到"

```text
现象：A 服务调 B 服务超时，A 报 ConnectException 或 timeout
```

```text
排查过程：
① A 日志：调 B 报错（哪个阶段？connect/read）
② B 日志：请求到没到？（关键分水岭）
③ 没到：检查服务发现（Nacos 注册的 IP 对不对）+ 网络连通
④ 到了：B 处理慢（DB/线程池/GC）→ 看 B 指标
⑤ 根因示例：B 的线程池满（默认 200），A 的并发超 200 排队

解决：
  B 扩容/线程池调优/限流
```

| 教训 | 说明 |
|------|------|
| "请求到没到"是分水岭 | 网络问题 vs 处理问题 |
| 服务发现 IP 核对 | 容器化场景注册 IP 易错 |
| 超时链检查 | A 的 readTimeout vs B 的处理时间 |

## 8. 高频避坑清单

| # | 坑 | 规避 |
|---|----|------|
| 1 | ping 不通就判断网络故障 | ICMP 可能被拦；用 telnet 确认端口 |
| 2 | 只看客户端不看服务端 | 先 `ss -tlnp` 确认监听 |
| 3 | 超时重试非幂等接口 | 写操作必须幂等键 |
| 4 | 忽略 JVM DNS 缓存 | networkaddress.cache.ttl 显式配置 |
| 5 | 池参数不对齐 | max-lifetime/keepalive vs 对端超时 |
| 6 | 禁用证书校验"解决"SSL | 正确姿势是导入 truststore |
| 7 | CLOSE_WAIT 当网络问题 | 是代码泄漏，查归还逻辑 |
| 8 | K8s 不看 endpoints | selector 不匹配是第一嫌疑 |
| 9 | 微服务不确认"请求到没到" | B 的日志是分水岭 |
| 10 | 改配置不验证 | 改完必须复测 + 观察指标 |

## 9. 面试题

| 题目 | 答题要点 |
|------|---------|
| 连接超时和连接拒绝的区别？ | 超时=包被丢（网络/防火墙 drop/队列满）；拒绝=收到 RST（端口未监听/防火墙 reject）——telnet 输出区分 |
| TIME_WAIT 是什么？为什么多？ | 主动关闭方等 2MSL（约 60s）；高并发短连接多；解决：连接池复用优先，tcp_tw_recycle 禁用 |
| CLOSE_WAIT 堆积说明什么？ | 对端已关应用未关 = 连接泄漏（代码问题）；jstack + 代码审查；try-with-resources |
| 域名 IP 变更后 Java 不生效？ | JVM DNS 缓存（networkaddress.cache.ttl 默认可能永久）；显式配置 + 变更前降 TTL |
| 连接池偶发 Connection reset？ | 空闲连接被服务端超时回收后复用；池空闲超时 < 对端 keepalive + 复用验证 |
| 如何定位"请求慢"？ | curl -w 耗时分解：DNS/连接/TLS/首字节；服务端 jstack + 指标 |
| 超时重试的幂等问题？ | readTimeout 超时 ≠ 未执行；写操作必须幂等键或禁止自动重试 |
| K8s Service 不通先看什么？ | kubectl get endpoints（空 = selector 不匹配） |
| 微服务 A 调 B 失败怎么排查？ | 分水岭：B 日志请求到没到——没到查发现/网络，到了查 B 处理 |
| 抓包怎么看握手问题？ | 只有 SYN 无 SYN-ACK（丢包/队列满）；立即 RST（未监听/reject） |
| 容器内 localhost 为什么连不上宿主机？ | 容器 localhost = 容器自身；宿主机用 172.17.0.1 / host.docker.internal |

## 10. 核心要点

> 🎯 **核心要点**：
> - 六案例沉淀六教训：池参数对齐、防火墙迁移必查、JVM DNS 缓存、CLOSE_WAIT=泄漏、K8s 看 endpoints、请求到没到；
> - 排查八习惯：分层、五连、两端、记录、抓包、查配置、单点验证、复盘；
> - 避坑 Top3：ping 误判、超时重试非幂等、CLOSE_WAIT 当网络问题；
> - 面试主线：超时 vs 拒绝 → TIME_WAIT → CLOSE_WAIT → JVM DNS → 池 reset → 耗时分解 → 幂等 → K8s endpoints → 调用链分水岭；
> - 方法论回顾：**分层定位 + 两端视角 + 抓包定论**是本体系不变的骨架。
