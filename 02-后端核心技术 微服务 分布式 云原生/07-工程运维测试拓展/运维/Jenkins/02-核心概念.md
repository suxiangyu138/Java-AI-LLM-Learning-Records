## 1. 总体架构：调度与执行分离

```text
Jenkins 主从架构（Master-Agent）：
  Master（控制器）
  ├─ Web UI / API
  ├─ 调度器（队列）
  ├─ 凭证/配置存储
  └─ 默认也执行构建（可禁用）

  Agent（节点/代理）
  ├─ 实际执行构建的机器（Executor 槽位）
  ├─ 通过 SSH / JNLP / Docker 接入
  └─ 可多台、可标签分组

  构建流程：Job 入队 → Master 调度 → 匹配 Agent → Agent 执行 → 回传结果
```

| 组件 | 职责 | 说明 |
|------|------|------|
| **Master** | 调度 + 管理 | 别让它干重活（大构建交给 Agent） |
| **Agent** | 执行构建 | 可多台、可动态（[06](06-Agent与分布式构建.md)） |
| **Executor** | Agent 上的执行槽位 | 1 个 Executor = 同时跑 1 个构建 |
| **Queue** | 等待队列 | Executor 占满时排队 |
| **Workspace** | 构建工作目录 | 代码检出 + 构建产物存放 |

> 🎯 架构本质：**"调度（Master）与执行（Agent）分离"**——这就是 Jenkins 能横向扩展的原因：Master 管队列，Agent 加机器 = 构建能力翻倍（[06](06-Agent与分布式构建.md) 展开）。

## 2. Job 类型：四种任务形态

| Job 类型 | 配置方式 | 适用 | 2026 定位 |
|---------|---------|------|:---:|
| **Freestyle**（自由风格） | UI 图形化配置 | 简单任务/遗留 | 遗留为主 |
| **Pipeline** | 代码化（Jenkinsfile） | **一切新任务** | ⭐ 推荐 |
| **Multi-branch Pipeline** | Jenkinsfile + 分支扫描 | 分支级流水线 | 推荐 |
| **Multijob** | 子 Job 编排 | 复杂编排（少用） | 边缘 |
| Folder | 组织 Job 的目录 | 项目分组 | 常用 |

```text
选择原则：
  · 新 Job 一律 Pipeline（代码化：可版本控制、可复用、可审计）
  · Freestyle 只留存量（UI 点出来的配置无法进 Git）
  · 多分支项目用 Multi-branch（每分支自动建流水线）
```

> 🎯 面试点：**"为什么新任务必须用 Pipeline 而不是 Freestyle？"**——代码化（Jenkinsfile 进 Git）、可复用（共享库）、可审计（diff 即配置变更）、可测试。Freestyle 的配置在数据库里，无法版本管理。

## 3. Freestyle vs Pipeline

| 维度 | Freestyle | Pipeline |
|------|:---:|:---:|
| 配置位置 | UI（Jenkins 数据） | **代码（Jenkinsfile）** |
| 版本管理 | ❌ | ✅ |
| 复用 | ❌ | ✅（共享库） |
| 复杂逻辑 | 有限 | **完整 Groovy** |
| 并行/条件 | 有限 | ✅ stage/parallel/when |
| 审计 | 差 | ✅ 代码审查 |
| 新人学习 | 简单 | 有 Groovy 门槛 |

```groovy
// Pipeline 最小示例（Jenkinsfile，见 03 完整语法）
pipeline {
    agent any
    stages {
        stage('Build') {
            steps { sh 'mvn -B clean package' }
        }
        stage('Test') {
            steps { sh 'mvn -B test' }
        }
    }
}
```

> 💡 从 Freestyle 迁移：官方支持"从 Freestyle 生成 Pipeline 骨架"（UI 里 Convert to Pipeline），但**建议直接手写**——迁移是重新设计流水线的机会，不是机械转换。

## 4. Workspace 与构建记录

```text
Workspace（工作目录）：
  Master 默认：JENKINS_HOME/workspace/{job-name}/
  Agent：按 Agent 配置的根目录
  每个构建在同一个 workspace 顺序执行（默认不隔离！）

构建记录（Build Record）：
  · 构建号（#123）+ 时间 + 结果（成功/失败/不稳定）
  · 控制台输出（Console Output）——排障第一现场
  · 制品（Artifacts）：构建产物归档
  · 测试报告/覆盖率报告/代码检查报告
```

| 构建结果 | 含义 |
|---------|------|
| SUCCESS | 全部步骤通过 |
| FAILURE | 关键步骤失败（构建红） |
| UNSTABLE | 测试失败/质量门禁不过（黄色，构建"不稳定"） |
| ABORTED | 手动终止/超时 |
| NOT_BUILT | 未执行（条件不满足跳过） |

> ⚠️ **Workspace 并发陷阱**：默认同 Job 的两个构建不能并行跑在**同一 Agent**（会争抢 workspace）——并行要么配多个 Executor 不同 Agent，要么用 `parallel` 阶段（Pipeline 内部并行是同一 workspace 安全的多线程）。**并发构建的脏 workspace 是"偶发构建失败"的头号原因**（[08](08-生产运维与故障排查.md) 故障篇）。

## 5. 触发器：构建怎么开始

| 触发器 | 场景 | 说明 |
|--------|------|------|
| **SCM Polling** | Git 变更轮询 | 每隔 N 分钟检查远端（简单但延迟） |
| **Webhook** | 推送即构建 | Git 平台 push 时通知（**推荐**） |
| 定时（Cron） | 周期构建 | `H 2 * * *`（哈希分钟防同时挤爆） |
| 上游构建 | Job 依赖 | 下游在上游成功后自动跑 |
| 手动 | 按需 | 带参数手动触发（最常用） |

```groovy
// 触发器声明（Pipeline 内）
pipeline {
    triggers {
        cron('H 2 * * *')                       // 每天 2 点（哈希分钟）
        pollSCM('H/5 * * * *')                  // 每 5 分钟查 Git
    }
}
```

```text
Webhook 配置（GitHub/GitLab 推送触发）：
  · 安装插件：GitHub Integration / GitLab
  · Git 平台 → Webhooks → URL: http://jenkins:8080/github-webhook/
  · Jenkins Job → 勾选 "GitHub hook trigger for GITScm polling"
  · 注意：Jenkins 需对 Git 平台可达（内网/公网地址）
```

> 🎯 触发器选型：**Webhook 优先**（零延迟、不浪费轮询）；cron 用于"固定时间构建"（如每日回归）；`H` 前缀（哈希）避免多个 Job 同时触发打爆资源。

## 6. 参数化构建

```groovy
// 参数化 Pipeline：手动触发时填参
pipeline {
    parameters {
        string(name: 'BRANCH', defaultValue: 'main', description: '构建分支')
        choice(name: 'ENV', choices: ['dev', 'staging', 'prod'], description: '部署环境')
        booleanParam(name: 'RUN_TESTS', defaultValue: true)
        password(name: 'DEPLOY_TOKEN', defaultValue: '')   // 密码参数（隐藏显示）
    }
    stages {
        stage('Checkout') {
            steps { checkout scm }   // BRANCH 参数在分支选择里用
        }
        stage('Deploy') {
            when { expression { params.ENV == 'prod' } }
            steps { sh "deploy.sh ${params.ENV}" }
        }
    }
}
```

| 参数类型 | 用途 |
|---------|------|
| string | 分支名/版本号 |
| choice | 环境选择（枚举） |
| booleanParam | 开关（是否跑测试） |
| password | 敏感值（**用 Credentials 更好**，见 04） |
| file | 上传文件参数 |

> 🎯 参数化 = **"一个流水线多场景复用"**——构建分支、目标环境、是否测试全部参数化，运维/QA 手动触发时只需选参数，不用改流水线代码。
