## 1. 项目协作模型

| 角色 | 权限 | 典型职责 |
|------|------|---------|
| 项目所有者 | 全部 | 项目管理、成员管理、分支合并 |
| 维护者 | 编辑 + 合并 | 接口定义维护、测试维护 |
| 开发者 | 编辑 | 接口调试、用例编写 |
| 只读成员 | 查看 | 文档阅读、测试查看 |

```text
协作模式：
后端团队定义接口 → 前端查看文档/Mock → QA 维护测试套件
→ 变更通知全员 → 分支合入 → 版本记录
```

> 🎯 **协作核心**：接口定义是团队的"单一事实源"——后端改定义、前端看文档、QA 跑测试，三方围绕同一份数据工作。

## 2. 分支管理

```text
分支模型（类似 Git）：
main（主分支，稳定可发布）
  └─ feature/xxx（功能分支：接口批量调整、测试重构）
       └─ 确认差异 → 合入 main
```

| 分支能力 | 说明 |
|----------|------|
| 创建分支 | 从主分支复制当前状态 |
| 独立修改 | 分支内自由调整（接口/测试/Mock） |
| 差异对比 | 合入前可视化差异（新增/修改/删除） |
| 合入/放弃 | 确认后合入 main，或放弃分支 |
| 冲突处理 | 与主分支冲突提示 |

> 💡 **场景**：接口大版本升级（v1 → v2）在分支中重构，验证无误后合入——避免直接改动影响正在联调的团队。

## 3. AI 分支

AI 分支（2026 新增）是**面向 AI Agent 的协作安全机制**：

```text
AI Agent 修改项目资源
  → 自动在独立分支完成修改（不直接碰主分支）
  → 生成差异预览（改了什么/影响哪些接口）
  → 人工确认 → 合入目标分支
```

| 价值 | 说明 |
|------|------|
| 防污染 | AI 自动化修改不影响主分支/协作分支 |
| 可审查 | 合入前差异确认（AI 改错了可以放弃） |
| 可追溯 | 分支记录 AI 的每次修改 |
| 与 CLI 联动 | Agent 通过 CLI 在分支内操作（见 [05](05-CLI与CI-CD集成.md)） |

> ⚠️ AI 分支是"AI 写代码也要走 Code Review"理念在 API 协作层的体现——**AI 的修改必须可审查、可回滚**。

## 4. 导入：Postman / OpenAPI / Hoppscotch

### 4.1 Postman 导入

```text
Postman Collection JSON → APIFox 项目
```

| 2026 导入优化 | 说明 |
|---------------|------|
| 变量名空格处理 | 自动处理 Postman 变量名中的空格 |
| Workspace 重命名 | 支持重命名 Postman Workspace |
| Base URL 自动映射 | 导入时自动映射为 APIFox 环境变量 |

```text
映射关系：
  Postman Collection → APIFox 项目
  Postman Folder → APIFox 目录
  Postman Environment → APIFox 环境
  Postman Pre-request/Test Scripts → APIFox 前后置脚本（兼容层转换）
```

### 4.2 OpenAPI / Swagger 导入

```text
OpenAPI 3.0 / Swagger 2.0 YAML/JSON → APIFox 项目
```

| 导入能力 | 说明 |
|----------|------|
| 接口定义 | 路径/方法/参数完整导入 |
| Schema | 请求/响应 Schema 导入（含引用类型） |
| 引用类型兼容 | 2026 优化 object 与引用类型参数 |
| 服务器地址 | `servers` 映射为环境变量 |

### 4.3 Hoppscotch 导入（2026-01）

```text
Hoppscotch Collection → APIFox
（Hoppscotch 是开源 API 调试工具，导入其 Collection 格式）
```

## 5. 导出与数据互通

| 导出格式 | 用途 |
|----------|------|
| OpenAPI 3.0 | 生成代码（OpenAPI Generator）、与其他工具互通 |
| Markdown | 文档归档 |
| HTML | 离线文档 |
| JSON | 项目备份/迁移 |

```bash
# CLI 导出
apifox export --project <项目ID> --format openapi --output ./api.yaml
```

> 💡 **双向互通**：APIFox 不是封闭工具——OpenAPI 进出自由，可对接代码生成、契约测试、API 网关等生态。

## 6. 数据模型与公共资源复用

```yaml
# 公共数据模型（如 User、Order）
data-models:
  User:
    id: string
    name: string
    email: string
  Order:
    id: string
    userId: string
    items: array<OrderItem>
    totalAmount: number
```

| 复用方式 | 说明 |
|----------|------|
| 接口响应引用 | 响应定义引用公共模型（`User`） |
| 嵌套模型 | Order 引用 OrderItem |
| 修改联动 | 模型修改 → 引用它的接口全部联动 |
| Mock 联动 | 模型 Schema 驱动 Mock 数据 |

> 🎯 公共模型的本质 = **API 世界的"类型定义"**——消除重复定义，一处修改处处生效（与 Java 后端定义 DTO 同理）。

## 7. 从 Postman 迁移实战

```text
五步迁移：
① 导出 Postman Collection（JSON）+ 环境文件
② APIFox 创建项目 → 导入 Collection
③ 检查环境变量映射（baseUrl 等）
④ 检查脚本（pm.* 兼容性）→ 改写不兼容部分
⑤ 重建 Mock 规则与自动化测试（原 Runner 用例）
```

| 迁移项 | 处理 |
|--------|------|
| 接口/目录 | ✅ 自动导入 |
| 环境变量 | ✅ 自动映射（2026 优化） |
| 前置/后置脚本 | ⚠️ `pm.*` API 有兼容层，复杂脚本需人工检查 |
| 断言 | ⚠️ 需在 APIFox 重写（断言库不同） |
| Runner 用例 | ⚠️ 需在测试套件中重建 |
| Mock | ⚠️ 需重新配置期望 |

> ⚠️ 迁移不是一键完成：**脚本与测试是主要人工工作**——先迁移接口与文档（零成本），再逐步迁移测试。

## 8. 变更管理与审计

| 能力 | 说明 |
|------|------|
| 变更记录 | 每个接口的修改历史（谁/何时/改了什么） |
| 评论 | 接口级讨论（参数疑问/返回结构） |
| 通知 | 接口变更通知团队成员（订阅制） |
| 分支审计 | 分支合入记录（含 AI 分支） |
| 权限审计 | 成员操作记录 |

> 💡 变更管理对前后端协作的意义：**后端改了接口，前端不再"莫名联调失败"**——变更通知 + 评论闭环让契约变更显性化。

## 9. 核心要点

> 🎯 **核心要点**：
> - 协作四角色：所有者/维护者/开发者/只读，接口定义是单一事实源；
> - 分支管理：功能分支改 → 差异确认 → 合入（类似 Git 流程）；
> - AI 分支：AI 修改先落分支、可审查、可回滚（防污染主分支）；
> - 导入三源：Postman（脚本需人工检查）、OpenAPI（Schema 完整）、Hoppscotch；
> - 公共模型 = API 世界的"类型定义"，一处修改处处联动；
> - 迁移节奏：先接口文档（零成本）→ 再测试脚本（人工重点）。
