## 1. 验收测试概述

### 1.1 验收测试在测试流程中的位置

```
单元测试 → 集成测试 → 系统测试 → 验收测试 → 上线
  ↑                              ↑
开发者保证"做对了"            用户/业务确认"做的东西是对的"
```

| 对比维度 | 系统测试 | 验收测试 |
|----------|----------|----------|
| **执行者** | 测试工程师 | 业务用户/产品/客户 |
| **视角** | 技术正确性 | 业务可用性 |
| **数据** | 模拟数据 | 真实/近真实数据 |
| **环境** | 测试环境 | 预发布/生产级环境 |
| **关注点** | 功能/Bug | 业务流程/用户体验 |

## 2. UAT用户验收测试

### 2.1 UAT核心要素

```text
UAT (User Acceptance Testing) = 真实用户在真实场景下验证系统

UAT通过标准（DoD — Definition of Done）：
□ 所有核心业务流程可完整走通
□ 业务方签字确认
□ 0个P0/P1问题遗留
□ 用户操作手册已交付
□ 培训完成（如有必要）
```

### 2.2 UAT测试用例编写

```text
UAT用例 ≠ 技术测试用例

技术测试用例："输入用户名'张三'，点击查询，验证返回数据包含'张三'"
UAT用例："作为客服人员，我能通过姓名查到客户，以便快速处理投诉"

UAT用例模板：
  场景：XXX业务场景
  前置条件：以XXX角色登录、有XXX权限
  操作步骤：
    1. 进入XXX页面
    2. 输入XXX → 点击提交
    3. 查看结果
  预期结果：XXX（从业务角度描述）
  实际结果：（用户填写）
  通过/失败：（用户勾选）
```

### 2.3 UAT常见问题

| 问题 | 说明 | 对策 |
|------|------|------|
| 用户不知道测什么 | 没培训过系统 | 先做Demo演示+提供操作手册 |
| 测得太浅 | 只走了一遍Happy Path | 给用户异常场景的任务（如"你余额不足时下单"） |
| 反馈不及时 | 测试后用户不理了 | 安排固定的UAT窗口期+每日站会 |
| 数据和线上不一致 | 测试环境的脏数据 | 准备和线上结构一致的脱敏数据集 |

## 3. Alpha测试 vs Beta测试

| 维度 | Alpha测试 | Beta测试 |
|------|-----------|----------|
| **执行地点** | 开发方内部 | 用户实际环境 |
| **执行者** | 内部员工（非测试人员） | 真实用户/客户 |
| **环境** | 内部预发布环境 | 用户真实环境 |
| **开发者参与** | 开发者在场观察 | 开发者通常不在场 |
| **目标** | 发现严重Bug | 收集真实场景反馈 |
| **典型场景** | 内部试用新版后台管理系统 | 外部用户试用新App的公测版 |

```text
流程对比：
  Alpha：发布到内部环境 → 邀请内部非开发团队试用 → 记录反馈 → 修复 → 再测
  Beta：发布Beta版 → 邀请种子用户 → 收集Crash报告+问卷反馈 → 迭代 → GA正式发布
```

## 4. 契约测试

### 4.1 为什么需要契约测试

```text
微服务场景：
  订单服务(Consumer) 调用 用户服务(Provider)
  
问题：用户服务改了接口 → 订单服务不知道 → 上线后炸了
  
传统方案：集成测试、E2E测试（需要完整环境，慢且贵）
契约测试：Consumer定义"我需要这样的接口" → Provider验证"我满足这个契约"
```

### 4.2 契约测试流程

```text
Consumer端：
  1. 定义期望的API请求和响应（契约）
  2. 发布契约到Pact Broker
  3. Consumer本地Mock Provider，根据契约测试自己

Provider端：
  1. 从Pact Broker拉取契约
  2. 验证Provider的接口是否满足所有Consumer的契约
  3. 如果满足 → 通过；不满足 → 提前发现不兼容
```

### 4.3 Spring Cloud Contract示例

```groovy
// contracts/shouldReturnUserById.groovy
Contract.make {
    request {
        method 'GET'
        url '/api/users/1'
        headers { header('Accept', 'application/json') }
    }
    response {
        status 200
        body([
            id: 1,
            name: '张三',
            email: 'zhangsan@example.com'
        ])
        headers { header('Content-Type', 'application/json;charset=UTF-8') }
    }
}
```

## 5. 验收标准编写

### 5.1 INVEST原则

| 字母 | 含义 | 说明 |
|:---:|------|------|
| **I** | Independent | 每个验收标准独立可测 |
| **N** | Negotiable | 可讨论、可调整 |
| **V** | Valuable | 对用户/业务有价值 |
| **E** | Estimable | 可估算复杂度 |
| **S** | Small | 粒度适中 |
| **T** | Testable | 可验证 |

### 5.2 验收标准模板

```markdown
## Story: 用户登录

**验收标准**:
- [ ] ✅ 正确用户名+密码 → 登录成功，跳转到首页
- [ ] ✅ 错误密码 → 提示"用户名或密码错误"，3次后锁定账号
- [ ] ✅ 未输入用户名 → 按钮置灰不可点击
- [ ] ✅ 已登录状态 → 直接跳转首页（跳过登录页）
- [ ] ✅ "记住我"勾选 → Token有效期延长到7天
- [ ] ✅ 不支持IE浏览器 → 显示"请使用Chrome/Firefox/Edge"
```

> 🎯 **验收测试的核心价值**：确认"我们做了对的东西"，而不只是"我们把东西做对了"。
