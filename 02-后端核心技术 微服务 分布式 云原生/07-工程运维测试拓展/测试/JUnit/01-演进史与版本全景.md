## 1. 三大时代演进

### 1.1 JUnit 3/4：框架时代（1997-2017）

| 维度 | JUnit 3 | JUnit 4 |
|------|---------|---------|
| 约定 | 继承 `TestCase`，方法名以 `test` 开头 | POJO + `@Test` 注解 |
| 断言 | `assertXxx` 静态方法 | `assertXxx` + `@Test(expected=...)` |
| 扩展 | `TestSuite` 硬编码 | `@RunWith` + `Rule`（1998-2007 年的最优解，但非组合式） |
| 问题 | 命名约定驱动，无元数据 | 单一 Runner 限制、Rule 顺序不可控、无嵌套/参数化原生支持、无并行 |

JUnit 4 的痛点：一套测试只能有一个 `@RunWith`（想用 Spring 的 Runner 就无法用 Mockito 的 Runner）；`Rule` 之间无法表达依赖；测试发现与执行完全绑定 JVM 类加载。**这些问题直接催生了平台化架构**。

### 1.2 JUnit 5：平台时代（2017-2025）

JUnit 5 = Platform + Jupiter + Vintage 三件套，将「测试引擎」从「测试 API」中彻底解耦：

- **JUnit Platform**：独立于引擎的 Launcher 层，负责测试发现（Discovery）、过滤、执行与报告，暴露 `TestEngine` SPI；
- **Jupiter**：新测试引擎与 API 模型（`org.junit.jupiter`），支持嵌套、参数化、扩展机制、函数式断言；
- **Vintage**：在 Platform 上运行 JUnit 3/4 旧测试的兼容引擎。

> 💡 平台化的直接收益：任何引擎（Jupiter、TestNG、Selenium 自定义引擎）可共存在一次构建中；IDE 与构建工具只对接 Platform，不再绑定具体框架。

### 1.3 JUnit 6：现代化时代（2025.09-）

JUnit 6.0.0 于 **2025-09-30 GA**，是建立在 Jupiter 模型上的**演进式**大版本（非重写）。官方定位：只移除弃用超过两年的 API，大部分 5.x 测试**零改动运行**。但它做了一组强硬的「现代化」决定：Java 17 基线、统一版本号、Vintage 弃用、JSpecify 空安全注解。这标志着 JUnit 5 进入维护期（5.x 继续以 5.14.x 修补）。

## 2. 版本时间线（2026-08 现状）

### 2.1 JUnit 5.x 线（维护中）

| 版本 | 日期 | 要点 |
|------|------|------|
| 5.10.x | 2023-10 起 | Java 8 基线末期、`@CsvSource` 增强 |
| 5.11.x | 2024-07 起 | 类级 `@EnabledIf` 等条件注解改进 |
| 5.12.x | 2025-01 起 | `@ParametersAreNullableByDefault` 等空安全前奏 |
| 5.13.x | 2025-07 起 | 弃用期 API 标注（为 6.0 铺路） |
| 5.14.x | 2026-01 起 | **5.14.4（2026-04-26）为当前最新**，含 JDK 26 GA/27 EA 兼容性验证 |

### 2.2 JUnit 6.x 线（主推，统一版本号）

| 版本 | 日期 | 要点 |
|------|------|------|
| 6.0.0 | 2025-09-30 | GA：Java 17 基线、CancellationToken、Kotlin suspend、FastCSV、JFR 内置 |
| 6.0.1 | 2025-11 | 缺陷修复 |
| 6.0.2 | 2026-01-06 | 缺陷修复 |
| 6.1.0 | 2026-05-19 | `@DefaultLocale/@DefaultTimeZone`、`org.junit.start`、并行执行线程池可选、内存清理模式 |
| 6.1.1 | 2026-06-28 | **当前最新**：内存清理引擎排除参数、`SetSystemProperty` 参数化修复 |

> ⚠️ **版本代号**：JUnit 6 起 Platform/Jupiter/Vintage **共用一个版本号**（如 6.1.1），不再有 1.x/5.x 拆分，依赖管理大幅简化。JUnit 5 时代需区分 `junit-platform:1.14.x` 与 `junit-jupiter:5.14.x`。

## 3. JUnit 6 核心变化全景

### 3.1 基线提升

| 项目 | JUnit 5 | JUnit 6 |
|------|---------|---------|
| Java 最低版本 | Java 8 | **Java 17**（对应现代 LTS） |
| Kotlin 最低版本 | 1.8+ | **2.2**（官方迁移 Wiki 记为 2.1 起） |
| Surefire/Failsafe | 2.x 可用 | **必须 ≥ 3.0.0** |
| 目标 JDK | 老版本全面兼容 | 已测 JDK 17–26 GA / 27 EA |

### 3.2 功能变化

- **CancellationToken + `--fail-fast`**：`LauncherSession` 可将取消令牌传给引擎，首个失败即中止整次执行（CI 提速利器）；
- **JFR 内置**：JFR 事件从独立模块 `junit-platform-jfr` 移入 `junit-platform-launcher`（`org.junit.platform.launcher.jfr`），零额外依赖即可录制发现/执行事件；
- **Kotlin suspend 原生支持**：测试方法与生命周期方法可直接声明 `suspend`，不再需要 `runBlocking` 包装；
- **FastCSV 替换 univocity-parsers**：`@CsvSource/@CsvFileSource` 性能显著提升、RFC 4180 合规、错误报告更精确；`lineSeparator` 属性移除（自动识别 `\r`/`\n`/`\r\n`），闭合引号后的多余字符视为格式错误；
- **JSpecify 空安全**：全模块标注 `@Nullable/@NonNull`，IDE 与 Kotlin 互操作类型区分更准确；
- **`org.junit.start` 模块（6.1）**：Java 25 起可用，单文件源码程序直接跑测试，`import module org.junit.start;` + `JUnit.run()`。

### 3.3 移除与弃用（迁移必看）

| 项目 | 状态 | 说明 |
|------|------|------|
| `junit-platform-runner` | **移除** | JUnit 4 风格的 Platform Runner |
| `junit-platform-jfr` | **移除** | 并入 launcher 模块 |
| `junit-platform-suite-commons` | **移除** | 并入 suite 模块 |
| **JUnit Vintage** | **弃用** | 运行 JUnit 3/4 的临时迁移桥，只发 INFO 警告；Spring Boot 4 已从 starter-test 移除 |
| `junit-jupiter-migrationsupport` | 弃用 | JUnit 4 注解迁移支持模块 |
| `MethodOrderer.Alphanumeric` | 移除 | 由 `MethodOrderer.Default` 取代（仍确定性但故意"不明显"的顺序） |
| `ExtensionContext.Store.getOrComputeIfAbsent` | 移除 | 改为空安全的 `computeIfAbsent` |
| JRE 条件注解（`@EnabledOnJre` 等） | 调整 | Java 8–16 的 `JRE` 常量弃用；17 以下条件恒为假 |
| `@CsvSource lineSeparator` | 移除 | 自动检测行尾 |

## 4. JUnit 5 vs JUnit 6 对比

| 维度 | JUnit 5（5.14.4） | JUnit 6（6.1.1） |
|------|-------------------|-------------------|
| 版本体系 | Platform 1.14.x / Jupiter 5.14.x 分离 | **统一 6.x** |
| Java 基线 | 8 | 17 |
| Vintage | 完整支持 | 弃用（迁移桥） |
| CSV 解析 | univocity-parsers | FastCSV |
| 空安全 | 无 | JSpecify 注解全模块覆盖 |
| 失败即停 | 无官方机制 | CancellationToken + `--fail-fast` |
| JFR | 独立模块 | 内置 launcher |
| Kotlin | 需包装协程 | suspend 原生支持 |
| 并行执行 | ForkJoin 池固定 | **6.1 可选 ForkJoin/WorkerThreadPool** |
| 单文件测试 | 不支持 | 6.1 `org.junit.start`（Java 25+） |

## 5. Spring Boot 4 生态集成

- **Spring Boot 4（2025-11 发布）将 JUnit 6 设为默认测试框架**：`spring-boot-starter-test` 内含 Jupiter 6.x、AssertJ 3.26+、Mockito 5.x、Hamcrest 2.2、JSONassert、JsonPath；
- **Vintage 从 starter-test 完全移除**：JUnit 4 测试不再自动执行。仍依赖 JUnit 4 的框架（如 Vaadin TestBench）需**显式**添加 `org.junit.vintage:junit-vintage-engine`；
- JUnit 4 的 `@RunWith(SpringRunner.class)` → `@ExtendWith(SpringExtension.class)`；`@Category` → `@Tag`；`ExpectedException` Rule → `assertThrows`；
- Testcontainers 通过 `@ServiceConnection` 成为一等公民（详见 07 模块）。

## 6. 快速上手配置示例

### 6.1 Maven（JUnit 6.1.1）

```xml
<properties>
    <junit.version>6.1.1</junit.version>
    <maven.compiler.release>17</maven.compiler.release>
</properties>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.junit</groupId>
            <artifactId>junit-bom</artifactId>
            <version>${junit.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>          <!-- api + engine + params 全家桶 -->
        <scope>test</scope>
    </dependency>
    <dependency>
        <groupId>org.mockito</groupId>
        <artifactId>mockito-junit-jupiter</artifactId>  <!-- MockitoExtension 集成 -->
        <scope>test</scope>
    </dependency>
</dependencies>
```

> 💡 BOM 管理版本后无需再写各模块版本号；JUnit 6 单一版本号同时管住 platform/jupiter/vintage。

### 6.2 Gradle

```groovy
dependencies {
    testImplementation(platform("org.junit:junit-bom:6.1.1"))
    testImplementation("org.junit.jupiter:junit-jupiter")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.test {
    useJUnitPlatform()
}
```

### 6.3 第一组测试

```java
class CalculatorTest {

    @Test
    void add_returns_sum() {
        assertEquals(5, Calculator.add(2, 3), "2 + 3 应等于 5");
    }
}
```

```bash
mvn test            # 输出：Tests run: 1, Failures: 0
```

## 7. 选型决策与升级成本

**新项目**：直接 JUnit 6.1.x（Java 17+ 前提下），这是 2026 年的默认选项。

**存量 5.x 项目**：升级收益大于成本——
- 成本：Java 基线 17、构建插件 ≥ 3.0、删掉两年以上弃用 API 的使用、CSV 用例复核（FastCSV 更严格）；
- 收益：统一版本号、JFR 免依赖、失败即停、Kotlin 协程原生、空安全标注；
- 纯 Jupiter 测试绝大多数**零改动**；官方给出了顺滑迁移路径（详见 09 模块迁移清单）。

**仍在 JUnit 4 的项目**：是时候规划迁移了——Vintage 在 JUnit 6 已弃用，Spring Boot 4 不再兜底，JUnit 4 事实上的支持已终结。

> 🎯 **核心要点**：JUnit 6 不是新框架，而是 Jupiter 的"现代化发布"——它用低迁移成本换取了 Java 17 基线、统一版本号与平台能力（失败即停、JFR、suspend）的确定性。判断一个版本是否"当前"只需记住两个数字：**JUnit 6.1.1（2026-06）** 与 **JUnit 5.14.4（2026-04，维护线最新）**。
