## 1. 测试金字塔与策略

### 1.1 金字塔 vs 冰淇淋

```text
        /╲            投入分布（正确）                投入分布（反例：冰淇淋圣代）
       /  ╲           UI/E2E 少而精 ──────────────→   UI/E2E 多且慢（冒烟栈）
      /────╲          ┌─────────┐                    ┌─────────┐
     /      ╲         │ UI/E2E  │ 5%                 │ UI/E2E  │ 60% ← 又慢又脆
    /────────╲        └─────────┘                    └─────────┘
   /          ╲       │ 服务/集成│ 25%               │ 服务/集成 │ 20%
  /────────────╲      └─────────┘                    └─────────┘
 / 单元测试      ╲    │ 单元测试  │ 70%              │ 单元测试  │ 20% ← 上层的假绿灯
/________________╲   └─────────┘                    └─────────┘
```

**分层定位（JUnit 语境）**：

| 层 | 工具组合 | 运行时机 | 典型耗时 |
|----|---------|---------|---------|
| 单元 | Jupiter + Mockito/Fake，零外部依赖 | `mvn test`（每次提交） | 秒级 |
| 服务/集成 | `@SpringBootTest` + 切片 + Testcontainers | PR / merge | 分钟级 |
| E2E | 切片 + Playwright/Selenium 等 | 发布前冒烟 | 10+ 分钟 |

> ⚠️ 冰淇淋反例的典型症状：大量 E2E 用例互相依赖、套件跑 40 分钟、失败排查需要看三个系统日志——这是把「测试工作量」错当成「测试质量」。

### 1.2 测试粒度决策

| 被测对象 | 首选层 | 理由 |
|---------|--------|------|
| 纯函数/工具类 | 单元 | 快、穷举边界 |
| Service 业务规则 | 单元 + Mock 外部 | 规则穷举 |
| Repository | 集成（容器/嵌入式 DB） | SQL 方言真实性 |
| Controller 契约 | 切片（MockMvc） | 序列化 + 状态码 |
| 跨系统流程 | E2E 冒烟 | 只覆盖主链路 |

## 2. FIRST 原则

| 原则 | 含义 | 违反信号 |
|------|------|---------|
| **F**ast | 单测毫秒级，套件分钟级 | `Thread.sleep`、真实网络、每次建上下文 |
| **I**solated | 测试互相独立，可单独运行 | 依赖测试顺序、共享可变静态状态 |
| **R**epeatable | 任意次数运行结果一致 | 依赖时钟/随机数/本机时区 |
| **S**elf-verifying | 无人工检查，红绿一目了然 | 测试里 println、依赖日志人工看 |
| **T**imely | 与被测代码同步写 | 上线后补测试、覆盖率 0 的模块 |

**Repeatable 的三个具体解法**：

```java
@Test
void time_dependent() {
    try (MockedStatic<Instant> mocked = mockStatic(Instant.class)) {
        mocked.when(Instant::now).thenReturn(Instant.parse("2026-08-06T00:00:00Z"));
        // 断言基于固定时间的行为
    }
}

@Test
void locale_dependent() {
    Locale.setDefault(Locale.US);          // 或用 JUnit 6.1 @DefaultLocale("en-US")
    // ...
}

@Test
void random_dependent() {
    when(random.nextInt(anyInt())).thenReturn(42);   // 或注入固定种子
}
```

## 3. 命名与结构规范

### 3.1 命名三件套

```java
// 方法名：被测方法_条件_期望（英文，下划线分隔，机器可读）
@Test
void pay_insufficientBalance_throwsInsufficientBalanceException() { }

// @DisplayName：业务中文叙事（报告/IDE 可读）
@Test
@DisplayName("余额不足时支付失败并抛出业务异常")
void pay_fail_when_insufficient() { }

// 类名：被测类 + Test
class OrderServiceTest { }
class OrderControllerTest { }
class OrderRepositoryIT { }          // 集成测试用 *IT 区分
```

### 3.2 AAA 结构与单断言倾向

```java
@Test
void refund_restores_balance() {
    // Arrange —— 准备输入与前置状态
    Order order = new Order(100);
    order.pay();

    // Act —— 执行被测行为（只一行）
    order.refund();

    // Assert —— 断言结果（行为结果，而非实现细节）
    assertEquals(100, order.getBalance());
}
```

**单断言原则的边界**：一个测试断言**一个行为维度**——同一行为的多个结果用 `assertAll` 聚合，不同行为拆多个测试。

### 3.3 测试数据构造

```java
// 工厂方法（避免测试中散落构造器调用）
class OrderFactory {
    static Order paidOrder(int amount) {
        return Order.builder().amount(amount).status(PAID).build();
    }
    static Order draftOrder() { ... }
}
```

| 模式 | 适用 |
|------|------|
| 工厂方法 | 测试内少量变体 |
| Builder | 参数多、需覆盖组合 |
| Test Fixture 类 | 跨类复用的领域对象 |
| `@Nested` 分组长公共 Setup | 同主题不同前置 |

## 4. JUnit 5 → 6 迁移清单

官方定位：5→6 迁移远比 4→5 平滑，**大多数纯 Jupiter 测试零改动**。按顺序核对：

- [ ] **Java 基线**：JDK 17+（Kotlin 测试需 2.1+/2.2+）
- [ ] **构建插件**：Surefire/Failsafe ≥ 3.0.0
- [ ] **版本统一**：`org.junit:junit-bom` 单版本管理（替代 Platform/Jupiter 双版本）
- [ ] **Vintage 处理**：无 JUnit 3/4 测试可移除；有则显式添加 `junit-vintage-engine` 作为临时迁移桥（注意其已弃用）
- [ ] **移除项检查**：`junit-platform-runner`、`junit-platform-jfr`（功能已内置 launcher）、`junit-platform-suite-commons`、`MethodOrderer.Alphanumeric`
- [ ] **Store API**：`getOrComputeIfAbsent` → `computeIfAbsent`
- [ ] **CSV 用例复核**：`lineSeparator` 属性删除；闭合引号后多余字符会报格式错误
- [ ] **JRE 条件**：`@EnabledOnJre(JAVA_8..16)` 清理（恒跳过）
- [ ] **参数化显示**：字符串参数默认带引号，`quoteTextArguments=false` 可还原旧观感
- [ ] **全量回归**：`mvn verify` + 并行模式各跑一遍，对比结果集

**Spring Boot 3 → 4 联动项**：`@MockBean` → `@MockitoBean`（OpenRewrite 自动迁移）、starter-test 中的 Vintage 移除、切片注解包迁移。

## 5. Flaky 治理与变异测试

### 5.1 Flaky 测试（偶发失败）根因分类

| 根因 | 典型场景 | 治理手段 |
|------|---------|---------|
| 时间竞态 | 异步回调未完成、超时边界 | Awaitility 轮询断言；消除 sleep；超时只测「限时完成」语义 |
| 共享状态 | 静态字段、系统属性、固定端口 | PER_METHOD 隔离、`@ResourceLock`、每次重置 |
| 环境依赖 | 本机时区/编码/网络外呼 | mockStatic 固定时钟；`@DefaultLocale`（6.1）；禁外呼 |
| 并行污染 | 并行开启后偶发 | 先随机顺序单线程验证隔离，再开并行逐步排查 |
| 数据残留 | DB/缓存未清理 | `@Transactional` 回滚；`@TempDir` 自动清理；每测重建 |
| 外部服务 | 容器/依赖接口抖动 | Testcontainers 固定版本；外部 HTTP 一律 mock |

**治理纪律**：Flaky 不靠「重试掩盖」解决——CI 重试开关只在**已知第三方抖动**场景允许（`@RetryingTest` 类扩展明确标注原因）；新发现的 flaky 必须建档根因后再处置。

### 5.2 变异测试（Pitest）：检验测试有效性

覆盖率只回答「哪些行被执行」，变异测试回答「断言真的有效吗」——把生产代码做小变异（`==` → `!=`、去掉一行），测试若未失败说明该断言是无效的：

```xml
<!-- pitest-maven：mvn org.pitest:pitest-maven:mutationCoverage -->
<plugin>
    <groupId>org.pitest</groupId>
    <artifactId>pitest-maven</artifactId>
    <version>1.17.2</version>
    <configuration>
        <targetClasses><param>com.example.*Service</param></targetClasses>
        <targetTests><param>com.example.*Test</param></targetTests>
        <mutationThreshold>80</mutationThreshold>   <!-- 变异存活率门禁 -->
    </configuration>
</plugin>
```

**适用边界**：变异测试有真实算力成本（每个变异一次全量运行），适合**核心业务模块**（支付、库存、订单状态机）做季度强化，不适合全仓库常驻。

> 💡 变异测试发现的典型「假阳性测试」：只测 happy path 的测试、`assertTrue(flag)` 无消息断言、mock 返回值恒真时的单分支测试——修复方式是把断言收窄到行为结果。

## 6. 常见故障排查速查表

| 症状 | 常见原因 | 解法 |
|------|---------|------|
| `No tests found` | 命名不匹配（`*Test`/`Test*`/`*Tests`）| 检查 includes 约定；Surefire 3.x 确认引擎依赖 |
| `NoSuchMethodError: getOrComputeIfAbsent` | 5.x/6.x 依赖混用 | BOM 统一版本；清掉旧 `junit-jupiter-engine` |
| `Engine ID not registered` | 缺 `junit-jupiter-engine` 运行时依赖 | test scope 加 `junit-jupiter`（含引擎） |
| 测试顺序执行报错 | 隐式顺序依赖 + 默认顺序"不明显" | 消除依赖；临时 `MethodOrderer.MethodName` 复现 |
| 并行下偶发失败 | 共享状态/静态字段/固定端口 | 定位并隔离；`@ResourceLock` 声明资源 |
| `UnnecessaryStubbingException` | 严格模式下僵尸 stub | 删除未用 stub；确需宽松用 `LENIENT` |
| CSV 数据报解析错误 | JUnit 6 FastCSV 更严格 | 复核引号闭合、多余字符 |
| `MockedStatic` 泄漏 | 未 try-with-resources | 作用域限定在测试方法内 |
| 上下文启动慢 | 每个类不同配置组合 | 统一配置组合提升缓存命中；切片化 |
| 测试通过但 `mvn verify` 失败 | Failsafe 阶段统计 IT | 检查 `*IT` 失败报告 |
| `java --module-path` 跑单文件报模块错误 | org.junit.start 需 Java 25+ | 检查 JDK 版本与 lib 目录完整性 |

> 🎯 **核心要点**：测试策略的终局形态是「**快反馈 + 真覆盖**」——金字塔保证投入比例，FIRST 保证单测可信，命名与 AAA 保证可持续维护；JUnit 6 迁移是低风险高收益动作，按清单执行并在最后做并行模式回归即可安全上线。
