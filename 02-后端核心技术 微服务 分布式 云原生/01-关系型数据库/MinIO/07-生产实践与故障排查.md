## 1. 容量规划：小文件陷阱与纠删集计算

```text
纠删码空间公式（对象存储容量规划的核心）：
  实际可用 = 总磁盘 × (数据块 / (数据块 + 校验块))

  例：16 盘 8+8 配置 → 可用 50%（8/16）
      14 盘 10+4 配置 → 可用 71.4%（10/14）
      12 盘 8+4 配置 → 可用 66.7%（8/12）

规划三步：
  ① 预估对象总量与平均大小
  ② 计算纠删集开销（含小文件放大，见 §2）
  ③ 留 20-30% 余量（版本控制 + 重建空间 + 增长缓冲）
```

| 配置 | 可用率 | 容错 | 适用 |
|------|:---:|:---:|------|
| 8+8（16 盘） | 50% | 8 盘 | 高可靠（默认） |
| 10+4（14 盘） | 71% | 4 盘 | 性价比平衡 |
| 12+4（16 盘） | 75% | 4 盘 | 容量优先 |
| 2+2（4 盘） | 50% | 2 盘 | 最小生产 |

> ⚠️ 常见规划错误：**按"总容量"规划，没算纠删码开销**——16 盘 8+8 的实际可用只有一半。这是"容量规划拍脑袋 → 半年告警"的头号原因。

## 2. 小文件问题与对策

```text
小文件陷阱（2026 生产事故高发区）：
  每对象在每个纠删集磁盘上写一个 xl.meta（元数据文件）
  15 盘宽的纠删集 → 每个小对象 = 15 份元数据开销

  例：100 万个小文件（各 10KB）
    直觉：100 万 × 10KB = 10GB
    实际：元数据放大 15 倍 → 150GB+（含分片开销）

  真实案例（pepitedata 2026 报告）：
    "容量规划两年够用 → 几天内崩溃"（海量小对象场景）
```

| 对策 | 说明 |
|------|------|
| 打包 | 小文件合并成大对象（如 1000 个 10KB 合成 10MB 一个） |
| 换方案 | 海量小对象（<500KiB）+ 高频 KV 访问 → **别用对象存储**（用 Cassandra/数据库） |
| 控制宽纠删集 | 小文件场景用窄纠删集（如 4+2 而非 8+8）降低放大倍数 |
| 监控 | 对象数/平均对象大小纳入容量监控（不只盯字节数） |

> 🎯 选型红线：**"对象存储适合'大文件、少而大'，不适合'海量小文件'"**——这是对象存储与数据库/键值存储的分界线（[08-选型对比与面试题](08-选型对比与面试题.md) 有完整决策）。

## 3. 升级与版本管理

```text
升级策略（MinIO 发布频繁，2026 已修复多个 CVE）：
  · 小版本（bugfix）：定期升级（月度）
  · 安全 CVE：立即升级（如 2026-03/04 的复制头注入、认证绕过）
  · 大版本（RELEASE 主版本）：先测试环境验证再滚动升级

滚动升级流程：
  ① 备份配置 + 记录当前版本
  ② 测试环境升级 → 验证读写/复制
  ③ 生产逐个节点滚动升级（同一二进制，逐个重启）
  ④ 升级后验证 mc admin info 健康 + 数据访问
```

```bash
# 版本管理
mc admin update local                          # 在线升级（生产慎用，先测试）
mc admin info local | grep -i version          # 查看版本
mc admin prometheus generate local             # 升级后确认指标正常
```

> ⚠️ 升级铁律：**MinIO 支持滚动升级但"只向前不向后"**——升级前记录版本，发现问题及时回滚（用旧二进制重启即可）；别跨太多版本一次升（先小步验证）。

## 4. 常见故障速查表

| 故障现象 | 根因 | 排查/解法 |
|---------|------|----------|
| `AccessDenied` | 凭证错/策略不足 | `mc admin accesskey diagnose`（2026 新工具）；检查 AK/SK、策略 Action/Resource |
| `SignatureDoesNotMatch` | 客户端时钟偏差 | 检查 NTP 同步（±15min 内） |
| 连接超时 | 网络/防火墙/端口 | `telnet minio:9000`；检查安全组 |
| `Region` 错误 | 区域配置不一致 | 客户端指定正确 Region |
| `NoSuchBucket` | 桶不存在/不同账号 | 检查桶名（全局唯一）与端点 |
| 写失败 `InsufficientStorage` | 容量满/quorum 不足 | `mc admin info` 看容量与盘状态 |
| **HTTP 507** | 磁盘满（集群级） | 2026 起满盘按离线处理（quorum 仍在则继续写）——清理或扩容 |
| 读报 "file is corrupted" | 位衰减/分片损坏 | 触发 healing（`mc admin heal`）；2026 修复了 O_DIRECT 未对齐读 bug（升级） |
| 性能下降 | 盘不均衡/小文件/网络 | 看各盘用量均衡、对象大小分布、节点延迟 |
| 版本残留容量不减 | 删除标记/旧版本 | 生命周期规则清理 + `mc rm --purge-deleted` |

```bash
# 故障定位三板斧
mc admin info local              # ① 集群健康（盘/容量/版本）
mc admin heal local              # ② 修复（重建分片）
mc admin trace local             # ③ 实时追踪请求（定位慢/错）
```

> 🎯 定位方法论：**先 `admin info` 看盘与容量 → 再 `trace` 看请求行为 → 最后看应用侧日志**——90% 的 MinIO 故障在第一步就定位了（盘 offline/容量满/版本不一致）。

## 5. 性能优化

| 优化项 | 做法 | 收益 |
|--------|------|------|
| 网络 | 万兆网卡/同机房部署 | 吞吐瓶颈通常在网络 |
| 磁盘 | NVMe（热数据）/ HDD（冷归档） | 延迟 10 倍差 |
| 分片上传 | 大文件显式分片 + 并发 | 速度提升 |
| 对象大小 | 避免小对象（§2） | 元数据开销大降 |
| 客户端 | 连接池/复用（SDK 默认） | 避免连接重建 |
| 读缓存 | CDN 前置（[06 §7](06-后端架构配合.md)） | 回源大减 |
| 监控基线 | 记录正常延迟/吞吐 | 异常对比定位 |

> 💡 MinIO 单二进制 + 无依赖的设计让性能基线很高（可跑满 100GbE）；**生产性能问题 80% 出在网络与磁盘选择**，而不是 MinIO 本身。

## 6. 备份与恢复演练

```text
三层备份体系（[03 §7](03-部署与运维.md) 已讲机制，本处讲落地）：
  ① 纠删码：防硬件故障（集群内）
  ② 版本控制 + 生命周期：防逻辑误删
  ③ 异地复制/备份：防站点级灾难（机房挂/勒索）

落地建议：
  · 同机房：站点复制到独立集群（或 rclone 定期镜像）
  · 异地：rclone 加密同步到云 OSS（跨云备份）
  · 恢复演练：每季度测试环境完整恢复 + 校验数据可读
```

```bash
# 定期备份（cron 示例：每日增量同步）
0 2 * * * rclone sync minio:bucket1 backup:bucket1 --transfers 16 --checkers 32 2>>/var/log/rclone.log

# 恢复验证（演练）
rclone copy backup:bucket1 restore:restore-bucket --transfers 16
mc find restore/restore-bucket --name "*.pdf" | head    # 抽样校验
```

> ⚠️ 备份三大谎言：**"我们有备份"（没验证）、"每天全量"（其实增量坏了）、"异地了"（没演练过恢复）**——恢复演练的频率 = 数据重要度，金融数据季度演练，普通业务半年一次。

## 7. 生产 Checklist

```text
MinIO 生产上线 Checklist（照着打勾）：
  □ 分布式部署（≥4 节点 × 4 盘）
  □ 纠删码配置明确（8+8 或 10+4 等，已算可用容量）
  □ 容量规划含纠删码开销 + 20% 余量 + 版本控制放大
  □ 时钟同步（NTP）
  □ 监控接入（Prometheus：容量/盘离线/健康）告警
  □ 备份：站点复制或 rclone 异地 + 恢复演练记录
  □ 版本控制 + 生命周期规则（防误删 + 容量治理）
  □ 权限：服务账号最小权限 + 根凭证收管
  □ TLS 证书（内网 CA 或正式证书）
  □ 升级计划（月度常规 + CVE 立即）
  □ 健康探针接入（K8s/lb：live/ready/cluster）
  □ 小文件场景评估（对象数量与大小分布）
```
