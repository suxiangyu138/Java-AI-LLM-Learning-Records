## 1. 架构总览：文件放哪的现代答案

```text
传统架构（要淘汰）：
  文件 → 应用服务器磁盘 → 负载均衡后文件分裂 → 备份噩梦

现代架构（标准答案）：
  文件 → MinIO/云 OSS（对象存储）
  → 数据库只存"路径 + 元数据"（不存文件字节）
  → 应用只出 API（不碰文件流）

        ┌────────────────────────────────────────┐
 前端 ──┤ ① 上传：应用签发预签名 URL → 前端直传 MinIO│
        │ ② 访问：应用返回对象地址 → 前端直读        │
        │ ③ 元数据：文件名/大小/URL 存数据库          │
        └────────────────────────────────────────┘
```

| 组件 | 职责 | 存什么 |
|------|------|--------|
| **MinIO/云 OSS** | 文件字节 + 元数据 | 对象（数据本体） |
| **数据库** | 业务元数据 | 对象键、文件名、大小、业务关联 |
| **应用** | 签发凭证、校验权限 | 不存文件！ |

> 🎯 一句话架构：**"文件放对象存储，路径放数据库，应用只管签发与校验"**——三个组件各司其职，这是 2026 年后端文件管理的标准形态（告别"应用服务器磁盘存文件"）。

## 2. 方案一：应用转发上传（中小文件）

```text
流程：
  前端 → POST /api/files（multipart）→ 应用 → MinIO putObject
  应用全程经手：接收字节 → 转存 MinIO → 返回对象键

适用：小文件（<10MB）、需要服务端处理（校验/改名/异步任务）的场景
```

```java
@RestController
@RequestMapping("/api/files")
public class FileController {
    private final MinioService minioService;
    private final FileMetaRepository metaRepo;   // DB 元数据

    @PostMapping
    public Result<FileVO> upload(@RequestParam("file") MultipartFile file) {
        // 1. 服务端校验（大小/类型魔数——参考 Servlet 上传安全）
        if (file.getSize() > 10 * 1024 * 1024) {
            return Result.error(400, "文件不能超过 10MB");
        }
        // 2. 生成安全对象键（UUID 重命名 + 业务前缀）
        String objectKey = "files/" + UUID.randomUUID() + "_" + sanitize(file.getOriginalFilename());
        // 3. 转存 MinIO
        try (InputStream in = file.getInputStream()) {
            minioService.uploadFile("app-files", objectKey, in,
                    file.getSize(), file.getContentType());
        }
        // 4. 元数据入库（DB 存键，不存字节）
        FileMeta meta = metaRepo.save(FileMeta.builder()
                .objectKey(objectKey)
                .fileName(file.getOriginalFilename())
                .size(file.getSize())
                .contentType(file.getContentType())
                .build());
        return Result.ok(FileVO.from(meta));
    }
}
```

> ⚠️ 方案一的局限：**应用服务器是带宽/内存瓶颈**——大文件（视频/安装包）与高并发场景，应用转发 = 应用扛流量。这时上方案二。

## 3. 方案二：预签名直传（大文件/高并发）

```text
流程（前端直传，应用只签发）：
  ① 前端请求 POST /api/presigned/upload（带文件名/大小）
  ② 应用校验权限 → 生成预签名 PUT URL（15min 有效）→ 返回
  ③ 前端用 URL 直接 PUT 到 MinIO（不经应用！）
  ④ 上传完成后前端调 POST /api/files/complete 通知应用
  ⑤ 应用校验对象存在 → 元数据入库

收益：
  · 应用零字节转发（带宽/内存压力清零）
  · MinIO 直连前端（水平扩展由对象存储扛）
  · 下载同理：预签名 GET URL 直读
```

```java
// ① 签发预签名 PUT
@PostMapping("/presigned/upload")
public Result<PresignVO> presignUpload(@RequestBody UploadRequest req) {
    String objectKey = "files/" + UUID.randomUUID() + "_" + sanitize(req.getFileName());
    String url = minioService.presignedPut("app-files", objectKey, 900);
    return Result.ok(new PresignVO(url, objectKey));
}

// ⑤ 完成回调：校验 + 元数据入库
@PostMapping("/complete")
public Result<FileVO> complete(@RequestBody CompleteRequest req) {
    // 校验对象确实存在（statObject）
    if (!minioService.objectExists("app-files", req.getObjectKey())) {
        return Result.error(400, "文件未上传成功");
    }
    FileMeta meta = metaRepo.save(FileMeta.builder()
            .objectKey(req.getObjectKey())
            .fileName(req.getFileName())
            .size(req.getSize())
            .build());
    return Result.ok(FileVO.from(meta));
}
```

| 对比 | 应用转发（方案一） | 预签名直传（方案二） |
|------|:---:|:---:|
| 应用带宽 | 全量经手 | **零字节** |
| 大文件 | 吃力 | ✅ 推荐 |
| 服务端校验 | 灵活 | 有限（上传前/后校验） |
| 实现复杂度 | 简单 | 中（两段式流程） |
| 适用 | <10MB 小文件 | 大文件/高并发 |

> 🎯 生产组合：**小文件走方案一（简单可控），大文件走方案二（性能）**——一个上传接口按大小分流，兼顾简单与性能。前端直传的完整示例见 [前端直传架构参考](https://min.io/docs/minio/developer/)。

## 4. 元数据分离：DB 与对象存储的分工

```sql
-- 数据库只存元数据（文件字节在 MinIO）
CREATE TABLE file_meta (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT,
    object_key   VARCHAR(512) NOT NULL,      -- MinIO 对象键（唯一地址）
    bucket       VARCHAR(64)  NOT NULL,
    file_name    VARCHAR(255) NOT NULL,       -- 原始文件名（展示用）
    size         BIGINT       NOT NULL,
    content_type VARCHAR(128),
    biz_type     VARCHAR(32),                 -- 业务类型（头像/附件/证据）
    biz_id       BIGINT,                      -- 业务关联 ID
    created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_object (bucket, object_key)
);
```

| 数据 | 放哪 | 原因 |
|------|------|------|
| 文件字节 | MinIO | 对象存储的职责 |
| 对象键/桶 | DB + MinIO | DB 是索引，MinIO 是本体 |
| 业务关联（biz_id/type） | **只放 DB** | MinIO 无查询能力 |
| 自定义元数据 | 两边可选 | 简单场景放 MinIO `userMetadata`，查询场景放 DB |

> 🎯 设计原则：**"DB 是唯一业务索引，MinIO 是文件仓库"**——所有"按业务查文件"的查询都走 DB；MinIO 的键由 DB 持有，不会出现"文件在但找不到对应业务"的孤儿状态。

## 5. 文件访问与下载链路

```text
访问设计三形态：
  ① 私有文件（订单附件/隐私）：
     应用校验权限 → 签发预签名 GET（15min）→ 前端直读
     ✅ 权限可控（无 URL 即无文件）
  ② 公开文件（头像/公开图片）：
     MinIO 桶策略只读公开 + 直接 URL（或 CDN 前缀）
     ⚠️ 公开桶 = 任何人可读（只放可公开的数据！）
  ③ 半公开（防刷）：
     应用层加防盗链/限频（Referer/签名）

安全红线：
  · 隐私文件绝不进公开桶
  · 私有文件的"URL 直读"必须预签名（禁桶策略公开）
```

```java
// 私有文件下载（权限校验 + 预签名）
@GetMapping("/api/files/{id}/download")
public Result<String> downloadUrl(@PathVariable Long id) {
    FileMeta meta = metaRepo.findById(id).orElseThrow();
    // ① 权限校验（属主/角色——见 Web 安全越权篇）
    checkPermission(currentUser(), meta);
    // ② 签发限时 URL
    String url = minioService.presignedGet(meta.getBucket(), meta.getObjectKey(), 900);
    return Result.ok(url);
}
```

> ⚠️ 常见事故：**把私有桶设成公开**（图省事）→ 数据裸奔。规则：**默认私有，公开是显式决定**（[04 §7](04-权限与安全.md) 安全基线）。

## 6. 图片处理与静态资源托管

| 场景 | 方案 |
|------|------|
| 图片缩略图/水印 | 上传后异步处理（ImageMagick/thumbor）+ 存多尺寸对象 |
| 前端静态资源（JS/CSS） | MinIO 托管 + CDN（或继续用 Nginx/对象存储桶） |
| 头像/图片直读 | 预签名 GET 或公开桶 + 缓存头 |
| 视频/音频 | 直传 + 范围读取（支持拖拽）+ CDN 分发 |

```text
图片处理异步链路：
  上传原图 → MinIO（原图）
  异步任务 → 缩略图生成 → MinIO（thumb 规格）
  DB 存多尺寸键 → 前端按场景取尺寸
  命名：files/xxx/original.jpg + files/xxx/thumb_200.jpg
```

> 💡 与 [SpringBoot Web 上传体系](../../09-Web开发全流程/SpringBoot%20Web/08-生产实践与面试题.md) 的关系：Boot 负责接收与校验（multipart 配置、大小限制、异常处理），MinIO 负责存储——**上传链路 = Boot 的 API 能力 + MinIO 的存储能力**，两者配合而非竞争。

## 7. CDN 与缓存配合

```text
公开文件的 CDN 链路：
  前端 → CDN（缓存）→ 回源 MinIO
  · 首次访问：CDN 回源拉取 → 缓存（TTL 按文件类型）
  · 后续访问：CDN 命中（全球就近，0 回源）

缓存头设计（与 HTTP 缓存体系一致）：
  · 版本化对象（app-{hash}.js）：长缓存（1 年）
  · 可变对象（头像）：短缓存（10min）或 no-cache
  · 图片：30 天 + 版本化（[Web 高阶缓存篇](../../09-Web开发全流程/Web%20高阶知识/02-HTTP缓存体系.md)）

MinIO 侧配合：
  · 对象 key 用版本/哈希（改内容换键，CDN 缓存自然失效）
  · 公开桶可直接接 CDN 源站
```

> 🎯 架构总结：**对象存储 + CDN = 现代文件分发的标准形态**——应用只做"签发与校验"，字节流的存储（MinIO）、分发（CDN）、索引（DB）各归其位。整套链路与 [Web 服务器动静分离](../../09-Web开发全流程/Web%20服务器/05-Web服务器与应用服务器分工.md) 的理念完全一致：让最便宜的基础设施干最重的活。
