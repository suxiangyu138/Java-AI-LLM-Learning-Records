## 1. 数据模型：桶与对象

```text
对象存储 = 两层命名空间：
  桶（Bucket）   ：顶层容器（全局唯一命名）
  对象（Object） ：桶内的文件（键唯一）

  bucket "avatars"
    └── user-42.png      （对象：键 = user-42.png）
    └── 2026/08/photo.jpg（键可含 /，但只是名字，不是目录！）

访问路径（HTTP 语义）：
  GET /avatars/user-42.png
  └── bucket ┘└── 对象键 ┘
```

| 概念 | 说明 | 类比 |
|------|------|------|
| Bucket | 命名空间容器（桶名全局唯一、小写） | 顶层目录/数据库名 |
| Object | 数据 + 元数据 + 键 | 文件 |
| Object Key | 对象唯一标识（可含 `/`） | 文件路径（但无目录树） |
| Object Metadata | 自定义元数据（`X-Amz-Meta-*`） | 文件属性 |
| ETag | 对象内容指纹（MD5/校验和） | 文件哈希 |

> 🎯 核心思维转变：**对象存储没有"目录"**——`a/b/c.png` 里的 `/` 只是键的一部分，不是层级结构。"列出 `a/` 下的对象"是前缀扫描（S3 ListObjects 的 `prefix` 参数），不是目录遍历。这个区别决定了[性能模型](../MinIO/02-架构原理纠删码与数据保护.md)。

## 2. 对象键：扁平命名空间

```text
键命名设计（影响性能与组织方式）：
  ❌ 无规律平铺：img1.png, img2.png ... （无法按业务组织）
  ✅ 前缀分区：  users/42/avatar.png, orders/2026/08/invoice.pdf
  ✅ 时间分区：  logs/2026/08/08/app.log （日志按天归档）

前缀与"目录"的差别：
  · ListObjects(prefix="users/42/") → 列出该前缀下所有对象
  · 不是遍历目录，是键前缀匹配（亿级对象也是前缀扫描）

热分区建议（高并发场景）：
  避免所有请求打同一前缀（如单桶单前缀热点）——用随机前缀/ID 前缀分散
```

| 键设计模式 | 场景 | 示例 |
|-----------|------|------|
| 业务前缀 | 按业务隔离 | `users/{id}/`、`orders/{id}/` |
| 时间前缀 | 日志/归档 | `logs/2026/08/` |
| ID 前缀 | 大流量去热点 | `{hash(id)[0:2]}/{id}/file` |
| 版本后缀 | 静态资源 | `assets/app-{version}.js` |

> 💡 经验：**键就是对象的"地址"**——设计好键前缀，等于设计好数据组织（类似数据库的分区键）。别把对象当文件树用，把它当"可搜索的键空间"用。

## 3. 访问凭证与端点

```text
访问三要素：
  Endpoint     ：服务地址（http://minio:9000）
  Access Key   ：凭证 ID（类似用户名）
  Secret Key   ：凭证密钥（类似密码）

凭证管理：
  · 根凭证：首次启动生成（minio 控制台可查）
  · 服务账号（Service Account）：为每个应用/服务单独签发（最小权限）
  · 访问密钥轮换：mc admin accesskey / 控制台
```

```bash
# mc 配置（MinIO 客户端）
mc alias set local http://localhost:9000 ACCESS_KEY SECRET_KEY
# 验证
mc admin info local
```

| 凭证类型 | 用途 | 权限 |
|---------|------|------|
| 根凭证 | 初始管理 | 全权（**别给应用用**） |
| 服务账号 | 应用接入 | 按需（[04-权限与安全](04-权限与安全.md)） |
| STS 临时凭证 | 短时授权 | 过期自动失效 |

> ⚠️ 安全基线：**应用永远不用根凭证**——为每个服务建独立服务账号 + 最小权限策略（只给需要的桶/操作）。密钥泄漏是对象存储第一事故源（[04 §1](04-权限与安全.md) 展开）。

## 4. 版本控制

```text
版本控制开启后：
  每次覆盖/删除 → 生成新版本（保留旧版本）
  GET 默认拿最新版本；可回滚到任意版本
  删除 = 打"删除标记"（对象仍在，可恢复）

场景价值：
  · 防误覆盖/误删（开发期神器）
  · 数据合规（审计/恢复）
  · 与复制/备份配合（增量）
```

```bash
# mc 版本控制操作
mc version enable local/bucket          # 开启版本控制
mc ls --versions local/bucket           # 查看所有版本
mc rm --versions local/bucket/obj       # 彻底删除（含所有版本）
mc rm --purge-deleted local/bucket --versions --recursive   # 清理删除标记对象（2026 新特性）
```

| 版本控制注意 | 说明 |
|-------------|------|
| 成本 | 每版本全量存储（大文件高频覆盖 = 容量翻倍） |
| 删除标记 | 只打标记不删数据（需定期清理） |
| 生命周期 | 可配"保留 N 个版本/到期删除"自动治理 |
| 2026 新命令 | `mc rm --purge-deleted` 清理版本感知应用的残留标记 |

> 🎯 版本控制是**防误删的第一道保险**：生产桶建议开启 + 生命周期限制版本数（如保留最近 10 版），兼顾安全与容量。

## 5. 生命周期管理

```text
生命周期规则（按对象前缀/标签 + 时间自动执行）：
  转换（Transition）：标准 → 低频 → 归档（按访问频率降成本）
  过期（Expiration）：到期自动删除（日志/临时文件治理）
  版本处理：旧版本过期策略（配合版本控制）

规则示例：
  · 日志桶：7 天后删除（expiration）
  · 图片桶：30 天未访问转低频（transition）
  · 备份桶：保留 90 天 + 最多 5 个版本
```

```bash
# mc 生命周期配置（JSON 规则）
mc ilm rule add local/logs --expire-days 7
mc ilm rule list local/logs
```

| 规则类型 | 动作 | 场景 |
|---------|------|------|
| Expiration | 到期删除 | 日志/临时文件/验证码图片 |
| Transition | 转存储类 | 冷数据降本（云 OSS 场景更常用） |
| 版本过期 | 只清旧版本 | 配合版本控制防容量膨胀 |

> 💡 生产桶标配：**日志/临时桶配过期规则**，防"只进不出"的容量慢性死亡——这是对象存储最常被忽略的治理项（[07-生产实践与故障排查](07-生产实践与故障排查.md) 容量篇）。

## 6. S3 API 全景

```text
S3 API 核心命令族（MinIO 100% 兼容）：
  桶操作：CreateBucket / ListBuckets / DeleteBucket
  对象操作：PutObject / GetObject / DeleteObject / CopyObject
  列表：ListObjectsV2（prefix + pagination）
  分片：CreateMultipartUpload / UploadPart / CompleteMultipartUpload
  版本：PutObjectVersion / ListObjectVersions / DeleteObjectVersion
  预签名：PresignedGetObject / PresignedPutObject
  复制：PutBucketReplication / GetBucketReplication
```

| API 族 | 后端对应场景 |
|--------|-------------|
| PutObject | 文件上传（小文件） |
| 分片上传 | **大文件上传**（>100MB 必用，见 [05](05-Java集成.md)） |
| PresignedURL | **预签名直传/直读**（浏览器直传不经过应用，见 [06](06-后端架构配合.md)） |
| ListObjectsV2 | 文件列表/分页 |
| CopyObject | 服务端复制（改存储类/复制） |

> 🎯 面试点：**S3 API 兼容 = 生态通用**——MinIO、AWS S3、阿里云 OSS、腾讯云 COS 都是同一套 API 的不同实现；会一套 SDK 全部会用。

## 7. 对象存储 vs 传统文件系统（思维转换）

| 习惯（文件系统） | 转变（对象存储） |
|-----------------|-----------------|
| 目录层级 = 组织方式 | **键前缀** = 组织方式 |
| 修改文件（原地写） | **覆盖 = 新对象**（版本控制下是写新版本） |
| 挂载访问（NFS） | **HTTP 访问**（REST API） |
| 文件锁 | 无锁（最终一致/版本控制） |
| 移动/重命名 | 没有"移动"——**Copy + Delete** |
| 权限靠文件系统 | **策略（Policy）**（[04](04-权限与安全.md)） |

> ⚠️ 最大思维坑：**"改文件"的直觉**——对象存储没有原地修改，小改动 = 整个对象重传（所以大文件用分片、频繁改的对象要评估存储模型）。理解这个模型，MinIO 的很多"反直觉"设计（如性能、成本）就都通了。
