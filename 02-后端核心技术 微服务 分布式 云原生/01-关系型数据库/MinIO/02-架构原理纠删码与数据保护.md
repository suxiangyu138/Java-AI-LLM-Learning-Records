## 1. 数据保护的两种路线：副本 vs 纠删码

```text
三副本方案（传统/部分云厂商）：
  数据 → 3 份拷贝 → 任意 2 份损坏可恢复
  成本：3 倍空间

纠删码方案（MinIO）：
  数据 → 切成数据块 + 校验块 → 分到不同磁盘
  任意 N 块存活即可重建（N = 数据块数）
  成本：1.5~2 倍空间（16 盘 8+8 = 2 倍；10+4 = 1.4 倍）
```

| 方案 | 空间开销 | 容错 | 重建成本 | 代表 |
|------|:---:|------|---------|------|
| 三副本 | 3 倍 | 2 盘 | 复制即可 | 传统 HDFS/部分云 |
| **纠删码** | 1.4-2 倍 | 按分片设计 | 需计算重建 | MinIO / Ceph / 云厂商底层 |

> 🎯 面试金句：**"纠删码用 1.4~2 倍空间达到三副本的可靠性，省 30-50% 存储成本——代价是重建需要计算"**。这是对象存储相对"文件系统多副本"的核心优势。

## 2. 纠删码原理：数学之美

```text
纠删码 = 分块 + 冗余（Reed-Solomon 类算法）：
  原数据 → 切成 k 个数据块
         → 计算 m 个校验块（线性代数）
         → 共 k+m 块，分到 k+m 块磁盘

重建能力：任意 ≤ m 块磁盘损坏，都能用剩余 k 块恢复全部数据
  例：k=10, m=4（10+4 配置）
      · 14 块盘里任意坏 4 块 → 数据完整
      · 空间开销 = 14/10 = 1.4 倍

与 RAID 的关系：
  RAID-5/6 是"单机版"纠删码（1-2 块盘容错）
  MinIO 是"分布式版"——跨服务器、跨磁盘
```

> 🎯 类比：**纠删码 ≈ 把 RAID 的冗余思想扩展到整个分布式集群**——这就是为什么 MinIO 不用 RAID 也能防盘损（MinIO 官方甚至建议**不用 RAID**，让纠删码直管裸盘）。

## 3. MinIO 的纠删码实现

| 配置参数 | 说明 |
|---------|------|
| 纠删集（Erasure Set） | 数据布局单位，**每组最多 16 块盘** |
| 默认分片 | 16 盘 = 8 数据块 + 8 校验块（8+8，容错 8 盘） |
| 推荐配置 | 12+4 / 10+4 / 8+4（空间与容错平衡） |
| 最少要求 | 4 盘起（2+2） |
| 数据放置 | 每对象 × 每盘写一个分片 + xl.meta 元数据 |

```text
典型生产布局（4 节点 × 4 盘 = 16 盘）：
  对象 A → 16 个分片 → 每盘 1 片（8 数据 + 8 校验）
  任意 8 块盘同时坏 → 数据可重建

实例化选择：启动参数 --data-dir 多个路径 = 多盘
  minio server http://node{1..4}/data{1..4}
  → 16 块盘 → 自动按 16 盘纠删集组织
```

> ⚠️ 关键认知：**容错上限是"盘数"不是"节点数"**——8+8 配置下，若 2 个节点共 8 盘全坏，数据仍完整；但**节点级冗余设计**（每节点至少留 1 盘存活）是生产铁律（[03-部署与运维](03-部署与运维.md)）。

## 4. Bit Rot：静默损坏的威胁

```text
Bit Rot（位衰减）：磁盘"悄悄"损坏数据（读不出错但内容变了）
  · 硬件级静默错误（固件 bug、信号干扰、老化）
  · 普通文件系统/备份无法发现（读时无报错）
  · 静默累积 → 数据最终不可用

MinIO 的防护：
  · 每对象存校验和（哈希）
  · 读取时校验 → 发现不一致 → 用纠删码从其他分片重建
  · 后台扫描（healing）：定期全量校验 + 自动修复
```

| 防护手段 | 说明 |
|---------|------|
| 读时校验 | GET 时比对校验和，不一致触发重建 |
| 后台 Healing | `mc admin heal` 手动 / 自动后台扫描 |
| 健康检查 | `mc admin info` 看盘状态 |

> 🎯 面试差异化：**"MinIO 能防 bit rot——文件系统做不到的事"**——纠删码 + 校验和让"静默损坏"变为"可检测可修复"，这是对象存储比传统文件系统可靠性高一个维度的原因。

## 5. 分布式架构与数据布局

```text
MinIO 分布式架构：
  N 台服务器，每台 M 块盘 → 集群（无主从，对等节点）
  ┌─────────────┐
  │ Node1 盘1盘2 │ ← 纠删集（≤16 盘）
  │ Node2 盘1盘2 │
  │ Node3 盘1盘2 │  ← 对象分片分散在这些盘
  │ Node4 盘1盘2 │
  └─────────────┘
  特性：
  · 无中心节点（去中心化）
  · 任意节点可服务任意请求（对等）
  · 水平扩展：加节点 → 自动重新平衡
  · 数据写入：多数派确认（quorum）
```

| 架构特性 | 说明 |
|---------|------|
| 对等架构 | 无主从，任意节点可访问全部数据 |
| Quorum | 写需多数派成功（与纠删码容错联动） |
| 扩容 | 加节点/加盘（新纠删集；旧数据不自动重分布） |
| 故障域 | 节点/机架设计（别让一个机架断电带走全部校验块） |

> ⚠️ 扩容认知：**MinIO 扩容是"加新池"不是"重新打散"**——旧数据留在旧纠删集，新数据进新池。容量规划要一次到位或预留扩展节点（[07](07-生产实践与故障排查.md) 容量篇）。

## 6. 一致性模型与站点复制

```text
集群内（单站点）：
  · 强一致读写（写入多数派成功后，任何节点读到的都是新数据）
  · 分布式的"单机"体验

站点复制（Site Replication，跨数据中心）：
  · 异步镜像复制（类似持续 rsync）
  · ⚠️ 不是多主共识（无仲裁、无一致性级别选择）
  · 网络分区时可能静默丢弃"正确"写入（2026 生产经验报告）

适用：灾备（异地镜像）、跨云同步
不适用：需要强一致的多活写入
```

| 复制类型 | 一致性 | 场景 |
|---------|--------|------|
| 集群内 | 强一致 | 单站点读写 |
| 站点复制 | **异步最终一致** | 灾备/镜像 |
| 桶复制（Bucket Replication） | 异步 | 单桶级跨站同步 |

> ⚠️ 2026 生产教训（pepitedata 报告）：**别把站点复制当多活共识**——跨站点没有仲裁，分区时可能丢写。灾备场景可接受异步镜像，多活场景要选带共识的方案（如 Ceph RGW 多站点/云厂商）。

## 7. 纠删码的边界与陷阱

| 陷阱 | 说明 |
|------|------|
| **小文件放大** | 每对象在每个纠删集磁盘写一个 xl.meta——15 宽纠删集下小对象 = **15 倍元数据开销**（真实事故：容量规划"两年够用几天崩溃"） |
| 逻辑错误不防 | 误删/攻击/程序 bug——纠删码只防硬件故障，版本控制 + 备份才是逻辑防线 |
| 重建有成本 | 大文件重建耗 CPU/带宽（故障后自动重建期间注意负载） |
| 不是 NoSQL | 海量小对象（<500KiB）+ 高并发键值访问 → 选 Cassandra/Ceph/数据库（[08](08-选型对比与面试题.md)） |

> 🎯 收尾认知：**纠删码是"硬件容错"不是"数据保险箱"**——三层防线缺一不可：纠删码（硬件故障）+ 版本控制（逻辑误删）+ 站点复制/备份（灾难恢复）。详见 [07-生产实践与故障排查](07-生产实践与故障排查.md)。
