## 1. JDBC 事务模型：一连接一事务

**核心模型**：**一个 Connection 同时只能有一个事务**——事务边界 = 连接的生命周期段：

```text
Connection 默认 autoCommit=true：
  每条 SQL 独立提交（无事务）

手动事务流程：
  conn.setAutoCommit(false)      ← 开启事务（从此刻起 SQL 不自动提交）
  ... 多条 SQL ...
  conn.commit()                  ← 全部提交
  或 conn.rollback()             ← 全部回滚
  conn.setAutoCommit(true)       ← 恢复自动提交（连接归还池前必须！）
```

**这个模型的推论**（理解 Spring 事务的钥匙）：

```text
① 一个事务必须"同一个连接"执行（不同连接 = 不同事务）
② 事务跨越多个方法 → 必须共享连接（线程绑定连接）
③ 连接池归还前必须复位（autoCommit=true + 回滚未提交）
④ Spring 事务 = "一个线程一个连接 + 事务边界管理"（见第 5 节）
```

> 🎯 **核心要点**：事务模型 = "**一连接一事务（autoCommit 开关）**"——**"跨方法事务必须共享连接"是 Spring 事务管理器的根本任务**；连接池的复位（autoCommit=true）是防"事务污染"的关键。

## 2. 手动事务：setAutoCommit / commit / rollback

```java
public void transfer(long fromId, long toId, BigDecimal amount) {
    try (Connection conn = ds.getConnection()) {
        // ① 开启事务
        conn.setAutoCommit(false);

        try {
            // ② 业务 SQL（同一连接）
            try (PreparedStatement ps1 = conn.prepareStatement(
                    "UPDATE account SET balance = balance - ? WHERE id = ?")) {
                ps1.setBigDecimal(1, amount);
                ps1.setLong(2, fromId);
                ps1.executeUpdate();
            }
            try (PreparedStatement ps2 = conn.prepareStatement(
                    "UPDATE account SET balance = balance + ? WHERE id = ?")) {
                ps2.setBigDecimal(1, amount);
                ps2.setLong(2, toId);
                ps2.executeUpdate();
            }

            // ③ 提交
            conn.commit();
        } catch (SQLException e) {
            // ④ 异常回滚
            conn.rollback();
            throw new RuntimeException("转账失败，已回滚", e);
        } finally {
            // ⑤ 复位（归还连接前）
            conn.setAutoCommit(true);
        }
    } catch (SQLException e) {
        throw new RuntimeException("数据库操作失败", e);
    }
}
```

**手动事务的五步规范**（面试手写题标准）：

```text
① setAutoCommit(false)：开启
② 业务 SQL（同一连接！）
③ commit()：正常提交
④ rollback()：异常回滚
⑤ finally 中 setAutoCommit(true)：复位（防污染连接池）
```

> 🎯 **核心要点**：手动事务 = "**五步（开/做/交/滚/复位）**"——**"finally 复位 autoCommit"是最容易被忽略的一步**（连接池复用时的污染源）；手写转账是 JDBC 面试的经典场景题。

## 3. savepoint：部分回滚

**savepoint（保存点）**：事务内设置标记，回滚到标记处（部分回滚）：

```java
conn.setAutoCommit(false);

try {
    // SQL 1
    updateA();
    Savepoint sp = conn.setSavepoint("afterA");    // ① 设置保存点

    try {
        updateB();          // SQL 2
        conn.commit();      // 全部提交
    } catch (SQLException e) {
        // ② 只回滚 B，保留 A
        conn.rollback(sp);          // 回滚到保存点（B 撤销，A 保留）
        conn.commit();              // 提交 A
    }
} catch (SQLException e) {
    conn.rollback();        // 整体回滚
}
```

**savepoint 的要点**：

```text
① 语义：事务内的"书签"——rollback(sp) 只撤销 sp 之后的 SQL
② 前提：需要 JDBC 3.0+ 与数据库支持（MySQL InnoDB 支持）
③ 对应 Spring：@Transactional 的 REQUIRES_NEW/NESTED 底层之一
   → NESTED 用保存点实现（部分回滚）
④ 用完释放：conn.releaseSavepoint(sp)（可选）

与事务传播的关系（见 Spring 框架核心/06）：
  REQUIRES_NEW = 新连接新事务（完全独立）
  NESTED = 同连接保存点（可部分回滚）
```

> 🎯 **核心要点**：savepoint = "**事务内书签（部分回滚）**"——**"Spring 的 NESTED 传播底层就是保存点"是进阶考点**（连接 06 模块联动）；MySQL InnoDB 支持。

## 4. 隔离级别与并发问题

**JDBC 设置隔离级别**：

```java
// 设置隔离级别（必须在事务开始前）
conn.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);
// 或 setObject/isolation 配置

// 常量速查：
Connection.TRANSACTION_READ_UNCOMMITTED;   // 读未提交（脏读）
Connection.TRANSACTION_READ_COMMITTED;     // 读已提交（防脏读）✅ 多数默认
Connection.TRANSACTION_REPEATABLE_READ;    // 可重复读（防不可重复读）MySQL 默认
Connection.TRANSACTION_SERIALIZABLE;       // 串行化（防幻读，性能差）
```

**并发问题与隔离的对应**（与 `MySQL/` 与 `Java多线程/03` 联动）：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|:----:|:---------:|:----:|
| READ_UNCOMMITTED | ❌ 可能 | 可能 | 可能 |
| READ_COMMITTED | ✅ 防 | 可能 | 可能 |
| REPEATABLE_READ | ✅ | ✅ 防 | MySQL 可防（MVCC） |
| SERIALIZABLE | ✅ | ✅ | ✅ |

**JDBC 层的注意**：

```text
① 隔离级别是"连接级"设置（一连接一设置）
② 连接池：复位时恢复默认（防上次事务的级别残留）
③ 与数据库默认的关系：不设 = 用数据库默认
   → MySQL 默认 REPEATABLE_READ；PG/Oracle 默认 READ_COMMITTED
④ 锁：SELECT ... FOR UPDATE（悲观锁）也是 JDBC SQL 层操作
```

> 🎯 **核心要点**：隔离级别 = "**连接级设置 + 并发问题映射表**"——**"MySQL 默认 RR、PG 默认 RC"是细节考点**；连接池的复位（含隔离级别）与 Spring 的 @Transactional(isolation) 联动。

## 5. 与 Spring 事务的联动

**Spring 事务的 JDBC 真相**（面试必答——`Spring框架核心/06` 联动）：

```text
Spring 事务 = JDBC 事务的"托管化"：
  ① AOP 拦截 @Transactional 方法
  ② 获取线程绑定的连接（DataSourceUtils.getConnection —— 同线程同连接）
  ③ 调 conn.setAutoCommit(false)（等价 JDBC 手动事务）
  ④ 方法成功 → conn.commit()；异常 → conn.rollback()
  ⑤ 归还连接前复位（autoCommit=true + 隔离级别默认）

关键机制（为什么"自调用失效"）：
  AOP 代理拦截 → 绑定连接 → 事务
  同类 this.method() 不经过代理 → 无连接绑定 → 无事务

DataSourceTransactionManager：
  = "连接绑定（线程） + 事务边界（提交/回滚）"的管理器
```

```java
// 手动事务 vs Spring 声明式（对应关系）：
// @Transactional 方法：
@Transactional(rollbackFor = Exception.class)
public void transfer(...) {
    // Spring 代理：setAutoCommit(false) → 执行 → commit/rollback → 复位
    // 等价 JDBC 五步（见第 2 节）——框架替你做
}
```

**排查联动**（事务"不生效"的 JDBC 视角）：

```text
① 自调用 → 无代理 → 无连接绑定 → 无事务
② 连接池耗尽 → 拿不到连接 → 事务无法开始（超时）
③ 连接被提前归还 → 事务中断（setAutoCommit 复位时机）
④ 多数据源 → 每个数据源独立事务（需分布式方案）
```

> 🎯 **核心要点**：Spring 事务 = "**JDBC 手动事务的代理化（连接绑定 + 提交回滚管理）**"——**"@Transactional 底层就是 setAutoCommit(false)/commit/rollback"是面试深度题的答案**；自调用失效的机制也源于此（详见 `Spring框架核心/06`）。
