## 1. 性能调优 PRAGMA 清单

### 1.1 核心 PRAGMA 总表

| PRAGMA | 默认 | 推荐（生产） | 作用 |
|--------|:---:|:---:|------|
| journal_mode | delete | **WAL** | 读写并发 |
| synchronous | FULL | **NORMAL**（WAL 下） | 安全/性能平衡 |
| busy_timeout | 0 | **5000+** | 锁等待 |
| cache_size | -2000 | -16000 或按需 | 页缓存 |
| mmap_size | 0 | 按需（大读场景） | mmap 读 |
| foreign_keys | OFF | **ON** | 外键约束 |
| temp_store | default | MEMORY（小场景） | 临时表内存 |
| wal_autocheckpoint | 1000 | 1000-4000 | WAL 合并阈值 |

```sql
-- 生产初始化模板（每次连接）
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
PRAGMA busy_timeout=5000;
PRAGMA foreign_keys=ON;
PRAGMA cache_size=-16000;      -- 16MB 缓存
```

### 1.2 缓存与内存

```text
cache_size 权衡：
  大缓存 → 读快（热数据驻留）
  大缓存 → 内存占用（-16000 = 16MB）

mmap_size：
  开启后读走内存映射（省用户态拷贝）
  适用：大表扫描/只读场景
  注意：WAL 模式下 mmap 限制（不能映射 wal？——只读安全）

temp_store：
  临时表/排序内存 or 磁盘
  MEMORY 快但占内存；FILE 稳但慢
  大排序场景评估

内存数据库（:memory:）：
  极快（无磁盘 IO）
  数据丢失风险（进程退出即失）
  适用：缓存层、测试、临时计算
```

## 2. 读写性能优化

### 2.1 读优化

| 手段 | 说明 |
|------|------|
| 索引 | 覆盖/部分/表达式（03 模块） |
| 缓存 | cache_size 匹配热数据集 |
| 只读打开 | 只读连接（省锁开销） |
| 避免 SELECT * | 只取所需列 |
| 游标分页 | 替代深 OFFSET |
| ANALYZE | 优化器统计（大表变更后） |

```text
读吞吐参考（单机）：
  页缓存命中：10 万+ 行/秒（内存级）
  磁盘冷读：1-5 万行/秒（SSD）
  索引点查：微秒级
```

### 2.2 写优化

| 手段 | 提升 | 说明 |
|------|:---:|------|
| 事务批量 | 10-100× | 默认每语句一事务 |
| WAL + NORMAL | 2-5× | 顺序写 + 少 fsync |
| 预编译复用 | 明显 | 参数绑定复用 |
| 减少索引 | 写越快 | 每索引一次更新 |
| 同步关闭（OFF） | 更大 | 仅可容忍丢失场景 |

```java
// JDBC 批量写入（事务 + 预编译）
conn.setAutoCommit(false);
try (PreparedStatement ps = conn.prepareStatement(
        "INSERT INTO t (a, b) VALUES (?, ?)")) {
    for (int i = 0; i < 100000; i++) {
        ps.setInt(1, i);
        ps.setString(2, "value" + i);
        ps.addBatch();
        if (i % 5000 == 0) ps.executeBatch();  // 分批提交
    }
    ps.executeBatch();
    conn.commit();
}
// 实测：比逐条自动提交快 10-100 倍
```

### 2.3 写入吞吐参考

```text
单写者下的吞吐（实测量级）：
  逐条自动提交：几十-几百写/秒
  事务批量（WAL+NORMAL）：1-10 万写/秒（SSD）
  内存库：10 万+ 写/秒

瓶颈分析：
  磁盘 fsync 频率（synchronous）
  WAL 文件增长/checkpoint
  索引数量（写放大）
```

## 3. 备份与恢复

### 3.1 备份方式对比

| 方式 | 原理 | 适用 |
|------|------|------|
| VACUUM INTO | 在线一致性快照（3.27+） | 手动备份（推荐） |
| backup API | 增量备份（sqlite3_backup） | 程序化备份 |
| 文件拷贝 | 复制 .db（需先 checkpoint） | 简单但易错 |
| Litestream | 持续流式复制（见下） | 生产自动备份 |

```sql
-- VACUUM INTO：在线一致性备份（不打断读写）
VACUUM INTO 'backup-20260806.db';

-- 注意：WAL 模式下直接拷文件会漏 wal 数据
-- → 先 checkpoint 再拷：
PRAGMA wal_checkpoint(TRUNCATE);
-- 然后拷贝 .db（此时 wal 已合并）
```

### 3.2 备份最佳实践

```text
生产备份方案：
  ① 定时 VACUUM INTO（每日）
  ② Litestream 流式（持续，RPO 秒级）
  ③ 快照 + 恢复演练（定期验证）

恢复验证：
  备份必须"能恢复"才算备份
  定期演练恢复流程（目标时间：分钟级）

一致性要求：
  VACUUM INTO / backup API 保证一致性快照
  文件拷贝（无 checkpoint）可能不一致
```

## 4. 复制与分布式（Turso/Litestream）

### 4.1 Litestream：流式复制

```text
Litestream：SQLite 的持续复制工具
  原理：监听 WAL → 流式复制到对象存储/S3
  RPO：秒级（wal 帧实时上传）
  恢复：拉取 wal 重放 → 完整数据库

适用：单写多读 + 异地备份
  生产常用组合：主节点写 + Litestream 备份 + 灾难恢复
```

### 4.2 Turso / libSQL：多区域

```text
Turso（libSQL fork）：SQLite 的分布式化
  ① 嵌入式副本：多区域只读副本（边缘分发）
  ② 主从架构：单主写 + 多副本读
  ③ BEGIN CONCURRENT：实验性多写者（fork 内）
  ④ Cloudflare D1：SQLite 边缘部署（HTTP API）

架构模式：
  写入集中主节点（单写者限制）
  读取分布边缘（副本就近）
  同步：WAL 流式复制（主 → 副本）

定位：SQLite 的"云原生形态"
  适用：边缘应用、全球读分布、Serverless
```

### 4.3 分布式方案的边界

```text
不要期待：
  多写者强一致（非 Raft 数据库）
  跨区域强一致写（延迟物理约束）

适合：
  读多写少 + 边缘读（Turso 模式）
  单主 + 异地备份（Litestream 模式）
  单机 + 对象存储归档

对比：真分布式数据库（TiDB/CockroachDB）→ 不同量级需求
```

## 5. 监控与运维

### 5.1 监控指标

| 指标 | 获取 | 告警 |
|------|------|------|
| 数据库大小 | 文件大小/PRAGMA page_count | 增长异常 |
| WAL 大小 | -wal 文件 | 过大（checkpoint 异常） |
| 繁忙（BUSY） | 应用日志/统计 | 频繁 → 锁竞争 |
| 查询慢 | EXPLAIN/应用埋点 | P99 超阈值 |
| 缓存命中 | PRAGMA cache_spill/统计 | 低 → 调 cache_size |
| 完整性 | PRAGMA integrity_check | 定期跑 |

```sql
-- 快速体检
PRAGMA integrity_check;       -- 完整性（损坏检测）
PRAGMA page_count;            -- 总页数
PRAGMA freelist_count;        -- 空闲页（碎片）
PRAGMA wal_checkpoint;        -- WAL 状态
PRAGMA query_only;            -- 只读保护
```

### 5.2 运维实践

```text
日常运维清单：
  ① 定期 integrity_check（周）
  ② WAL 大小监控（checkpoint 健康）
  ③ 备份 + 恢复演练（月）
  ④ 碎片整理：VACUUM（删除大量数据后）
  ⑤ 版本升级（3.51.3 修复 WAL 损坏 bug——关注补丁）

常见运维动作：
  VACUUM：重建数据库文件（去碎片、缩小）
  REINDEX：重建索引（碎化后）
  ANALYZE：更新统计（优化器）
```

## 6. 常见坑与反模式

### 6.1 高频坑

| 坑 | 表现 | 对策 |
|------|------|------|
| 忘设 WAL/busy_timeout | 读写互斥/BUSY 错误 | 连接初始化模板 |
| 逐条自动提交写 | 吞吐惨淡 | 事务批量 |
| 网络文件系统跑 SQLite | 损坏/锁失效（NFS/SMB） | 本地盘/禁用 |
| 拷贝文件备份（WAL 漏数据） | 备份不一致 | VACUUM INTO/checkpoint |
| 长读事务拖住 checkpoint | WAL 无限增长 | 短事务/监控 |
| 忘开外键 | 外键约束失效（静默） | foreign_keys=ON |
| 多线程共享连接 | 并发异常/损坏 | 每线程独立连接 |
| 用 LIKE '%x%' 大表搜索 | 全表扫描慢 | FTS5/trigram |

### 6.2 反模式清单

```text
① 把 SQLite 当 MySQL 用（网络/并发写）
② 一个库塞所有数据（单文件过大 >10GB 拆库）
③ 忽略版本升级（3.51.3 修复损坏 bug）
④ 生产无备份/无恢复演练
⑤ 连接不设 PRAGMA（默认配置低效）
⑥ 大 JSON 频繁全量更新（用 JSONB）
⑦ 不用事务包批量写
⑧ 移动端不关 journal（文件系统脆弱场景）

规模警戒线（经验）：
  >10GB：考虑拆库/换库
  >1000 写/秒：写合并/分库
  >100 并发连接：连接池管理
```

### 6.3 生产配置速查（最终模板）

```sql
-- 每个生产连接的标准初始化：
PRAGMA journal_mode=WAL;       -- 读写并发
PRAGMA synchronous=NORMAL;     -- 安全/性能平衡
PRAGMA busy_timeout=5000;      -- 锁等待
PRAGMA foreign_keys=ON;        -- 外键生效
PRAGMA cache_size=-16000;      -- 16MB 缓存
-- 可选：
PRAGMA wal_autocheckpoint=2000;
PRAGMA temp_store=MEMORY;      -- 小临时数据
```

> 🎯 **核心要点**：SQLite 生产化 = "配置模板（WAL/NORMAL/busy/缓存）+ 写模式（事务批量）+ 备份纪律（VACUUM INTO/Litestream）+ 监控（完整性/WAL/慢查询）"四件套。它的性能上限很高（批量写 10 万+/秒），但依赖正确使用；它的坑集中在"默认配置"（无 WAL、无 busy 超时、无外键）与"错误定位"（当服务型数据库用）。2025-2026 的分布式化（Turso/Litestream/D1）让"单文件"也能走向生产与边缘。
