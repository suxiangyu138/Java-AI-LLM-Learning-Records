## 1. 多线程架构

### 1.1 线程模型

```text
Memcached 的线程结构：
  ① 主线程：监听/接受连接（accept）
  ② 工作线程 N：处理请求（默认 = CPU 核数）
  ③ 辅助线程：LRU 维护、过期清理等

工作方式：
  主线程 accept → 连接分发给工作线程
  每个连接绑定一个工作线程（后续请求由同一线程处理）
  工作线程各自独立处理（无共享锁争用）

对比 Redis（7.x 前）：
  Redis 单线程执行命令（IO 多线程化 7.0+）
  Memcached 从设计之初就是多线程
  → 多核机器的吞吐优势（Memcached 的招牌）
```

### 1.2 为什么 Memcached 可以多线程

```text
多线程的难点：共享状态（内存分配、LRU）→ 锁竞争

Memcached 的解法：
  ① 内存分配：slab 分配器 + 每线程局部缓存（线程本地 chunk 池）
  ② LRU：分段锁（per-class 锁，非全局）
  ③ 无共享数据结构：连接/请求状态线程私有

设计结论：
  锁粒度小（class 级）→ 多核扩展性接近线性
  对比 Redis 的全局单线程 → 多核利用率高
```

> 🎯 核心认知：**Memcached 的多线程 = 从诞生就有的设计**（2009 年 1.4 起默认），通过 slab 的细粒度锁与无共享状态实现接近线性的多核扩展——这是它在多核机器上吞吐领先 Redis 的根本原因。

## 2. libevent 事件循环

### 2.1 事件驱动模型

```text
libevent：异步事件库（网络 IO 的基础）

每个工作线程的事件循环：
  ① epoll/kqueue 监听 fd 事件（读就绪/写就绪）
  ② 事件触发 → 回调处理（解析命令/执行/响应）
  ③ 回到事件循环（非阻塞）

特点：
  单线程内异步（高并发连接）
  多线程 × 事件循环 = 横向扩展

对比阻塞 IO 模型：
  每连接一线程（阻塞）→ 线程数爆炸
  事件驱动 → 少量线程处理海量连接
```

### 2.2 连接处理流程

```text
连接生命周期（工作线程内）：
  ① accept（主线程）→ 连接加入某工作线程
  ② 读就绪 → 读取请求（缓冲区）
  ③ 解析命令（ASCII/二进制）
  ④ 执行（内存操作）
  ⑤ 写就绪 → 发送响应
  ⑥ 循环

关键优化：
  多请求合并读取（批处理）
  响应合并发送（writev 聚合）
  连接复用（keep-alive）

工程含义：
  长连接 + 批量请求 = 吞吐最大化
  （客户端连接池的协议层理由）
```

## 3. 性能基准

### 3.1 实测数据（2025-2026 检索）

| 场景 | Memcached 1.6.x | Redis 7.x |
|------|:---:|:---:|
| 单线程 GET/SET | ~30 万 ops/s | ~25 万 ops/s |
| 8 线程 | ~150 万 ops/s | ~80 万 ops/s |
| p99 延迟 | ~0.2ms | ~0.3ms |
| 管道化 | 百万级+ | 120 万 ops/s |

```text
数据解读（测试差异大，看趋势）：
  单线程：两者接近（Redis 7 IO 多线程后差距缩小）
  多核：Memcached 优势明显（线性扩展 vs Redis 命令仍单线程）
  延迟：同量级（内存操作，微秒-亚毫秒）

结论（稳定共识）：
  高核数 + 纯缓存负载 → Memcached 吞吐更优
  功能需求 → Redis（吞吐差距可被功能抵消）
```

### 3.2 影响性能的因素

| 因素 | 影响 |
|------|------|
| 值大小 | 大值 → 网络/拷贝开销（内存操作占比下降） |
| 连接数 | 事件驱动可承载万级连接 |
| 批量 | 批处理显著提升（网络往返减少） |
| 网络 | 千兆/万兆（局域网内 Memcached 常见） |
| CPU 核数 | 多核扩展（Memcached 线性） |
| 内存命中 | 命中率影响平均延迟（miss → 应用回源） |

## 4. 性能调优参数

### 4.1 启动参数

| 参数 | 默认 | 说明 |
|------|:---:|------|
| -t | 核数 | 工作线程数 |
| -m | 64MB | 内存上限 |
| -c | 1024 | 最大连接数 |
| -l | 本机 | 监听地址 |
| -p | 11211 | 端口 |
| -n | 48 | 最小 item 分配 |
| -f | 1.25 | 增长因子 |
| -I | 1m | 最大值大小 |
| -o | — | 现代选项（LRU 等） |

### 4.2 线程与连接调优

```text
线程数（-t）：
  经验：= CPU 核数（或核数-1）
  过多 → 上下文切换开销
  过少 → 核闲置

连接数（-c）：
  客户端连接池的总连接数上限
  事件驱动 → 可设较大（万级）
  注意 fd 限制（ulimit）

确认方法：
  stats 命令 → threads/curr_connections
  → 线程利用率/连接水位
```

### 4.3 现代选项（-o）

```text
-o modern：启用现代特性组合
  （lru_maintainer、slab_automove 等）

关键选项：
  slab_automove：自动均衡 slab 分配（内存压力时移动 slab）
  slab_reassign：手动/自动 slab 重分配
  lru_maintainer：后台 LRU 维护线程
  maxconns_fast：连接满时快速拒绝（防排队）

工程建议：
  默认 -o modern（现代部署标配）
  老配置（无 modern）→ 升级启用
```

## 5. 瓶颈分析与优化

### 5.1 瓶颈定位

```text
瓶颈排查顺序：
  ① CPU：线程利用率（多核是否吃满）
  ② 网络：带宽/连接数
  ③ 内存：命中率/淘汰率
  ④ 应用：客户端侧（连接池/序列化）

工具：
  stats：命中率、连接、命令计数
  top/pidstat：CPU 使用
  netstat：连接状态
  客户端指标：延迟分布
```

### 5.2 常见优化

| 问题 | 优化 |
|------|------|
| CPU 打满 | 加节点（水平）/调线程数 |
| 命中率低 | 加大 -m / TTL 调整 / 值大小贴合 chunk |
| 网络瓶颈 | 批量/管道/压缩值 |
| 大值拖慢 | 拆分/压缩/存引用 |
| 连接堆积 | 客户端连接池上限/超时 |
| 淘汰频繁 | 检查内存压力（slab 分配） |

### 5.3 与 Redis 的性能对比视角

```text
为什么 Memcached 多核更强：
  ① 多线程命令执行（vs Redis 命令单线程）
  ② 更少的功能路径（无数据结构解析）
  ③ slab 局部性（内存访问模式简单）

为什么差距"没那么大"：
  Redis 7 IO 多线程（网络层并行）
  实际瓶颈常在网络而非 CPU
  → 大多数场景两者吞吐都够用

选型结论：性能不是唯一维度
  （功能、运维、生态综合判断，见 08 模块）
```

## 6. 压测方法

### 6.1 压测工具

| 工具 | 用途 |
|------|------|
| memtier_benchmark | 官方推荐（Redis 出品，支持 memcached） |
| mcperf（libmemcached） | Memcached 专用压测 |
| 自研压测 | 真实业务负载（更准确） |

```text
memtier 示例：
  memtier_benchmark -s localhost -p 11211 \
    --protocol=memcache_text \
    --threads=4 --clients=50 \
    --test-time=60 --ratio=1:9
  # 4 线程 50 连接，读写比 1:9，60 秒
```

### 6.2 压测要点

```text
① 负载模型：贴近真实（读写比、值大小、键分布）
② 预热：先填充缓存（测稳态）
③ 多轮：取稳定值（排除冷启动）
④ 监控：服务端 CPU/网络 + 客户端延迟
⑤ 对比：基线 vs 调优后

报告指标：
  吞吐（ops/s）、P99/P999 延迟、命中率、错误率
```

> 🎯 **核心要点**：Memcached 性能 = 多线程（核数线性扩展）+ 事件驱动（万级连接）+ slab 局部性（内存高效）。调优三件事：**-t 匹配核数、-m 匹配命中率、-o modern 启用现代特性**；瓶颈排查按 CPU→网络→内存→应用顺序。性能基准的共识：多核纯缓存场景 Memcached 吞吐领先，但大多数应用瓶颈在网络而非 CPU——选型要综合功能与运维（08 模块）。
