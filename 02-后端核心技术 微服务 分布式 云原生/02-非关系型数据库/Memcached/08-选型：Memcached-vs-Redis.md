## 1. 全面对比

### 1.1 功能对比（2026）

| 维度 | Memcached 1.6 | Redis 7.x/8.x |
|------|:---:|:---:|
| 数据结构 | 字符串 | 字符串/哈希/列表/集合/有序集合/流 |
| 最大值大小 | 1MB（可调） | 512MB |
| 持久化 | 无 | RDB + AOF |
| 复制/高可用 | 无内置 | 主从 + Sentinel + Cluster |
| 集群 | 客户端分片 | 内置（16384 槽） |
| 脚本 | 无 | Lua / Functions |
| 发布订阅 | 无 | Pub/Sub + Streams |
| 事务 | 单命令原子 | MULTI/EXEC、Lua |
| 模块 | 无 | 模块系统（JSON/搜索等） |
| 许可 | **BSD** | RSALv2/SSPL（Valkey 为 BSD） |

### 1.2 性能对比

| 场景 | Memcached | Redis |
|------|:---:|:---:|
| 多核吞吐 | 领先（多线程） | 命令单线程（IO 多线程） |
| 单线程 | 接近 | 接近 |
| 延迟 p99 | ~0.2ms | ~0.3ms |
| 内存效率 | 更优（slab，每键 60-70B） | 良好（jemalloc，100-120B） |
| 大值处理 | 1MB 上限 | 512MB |

```text
性能结论（2025-2026 检索共识）：
  纯 KV 高吞吐 → Memcached 占优（多核）
  功能驱动 → Redis（性能差距可接受）
  实际瓶颈常在网络 → 差距被稀释
```

## 2. 2026 生态变化

### 2.1 Redis 许可变更与 Valkey

```text
2024 年重大事件：
  Redis Ltd 将 Redis 从 BSD 改为 RSALv2/SSPL 双许可
  → 云厂商不能免费商用 Redis 源码

Linux 基金会推出 Valkey：
  Redis 7.2 的 BSD 分支（AWS/Google 等支持）
  功能基本等价（社区继续演进）
  → 2026 年 Valkey 成为无许可顾虑的 Redis 替代

对选型的影响：
  Redis 用户需关注许可（商业/合规）
  Valkey 提供"BSD 的 Redis 体验"
  Memcached 始终 BSD（无此问题）
```

### 2.2 生态对比（2026）

| 维度 | Memcached | Redis/Valkey |
|------|:---:|:---:|
| 社区活跃度 | 维护稳定（慢） | 非常活跃 |
| 客户端生态 | 各语言主流 | 极丰富 |
| 云服务 | 各大云提供 | 各大云提供（托管） |
| 工具链 | 基础（stats） | 丰富（redis-cli、insight） |
| 文档/资料 | 较少 | 极多 |
| 许可 | BSD | RSALv2/SSPL（Valkey BSD） |

```text
生态结论：
  Redis 生态全面领先（资料/工具/社区）
  Memcached 的优势在"简单稳定"本身
  → 生态差距是选型的重要考量（学习/招聘/排障）
```

## 3. 选型决策框架

### 3.1 需求驱动

```text
第一问：只需要 KV 缓存吗？
  是 → 继续（Memcached 候选）
  否（结构/持久化/队列）→ Redis

第二问：需要持久化吗？
  是 → Redis（RDB/AOF）
  否 → 继续

第三问：需要内置高可用/集群吗？
  是 → Redis（Sentinel/Cluster）
  否（客户端分片可接受）→ 继续

第四问：吞吐/内存效率是首要吗？
  是 → Memcached（多核吞吐/内存省）
  否 → Redis（功能全面）
```

### 3.2 场景对照表

| 场景 | 推荐 | 理由 |
|------|:---:|------|
| HTML/API 片段缓存 | **Memcached** | 纯缓存、高吞吐 |
| 会话存储（可持久） | Redis | AOF 持久化 |
| 排行榜/计数器 | Redis | Sorted Set/INCR |
| 分布式锁 | Redis | SETNX/Redisson |
| 消息队列 | Redis | Streams/Pub-Sub |
| 亿级键纯缓存 | **Memcached** | 每键内存省 |
| 限流 | Redis | Lua 原子脚本 |
| 缓存+数据库混合 | Redis | 多功能 |

### 3.3 决策矩阵

| 权重 | Memcached | Redis |
|------|:---:|:---:|
| 功能需求 | 低 | **高** |
| 吞吐（多核） | **高** | 中 |
| 内存效率 | **高** | 中 |
| 持久化 | 无 | **有** |
| 高可用 | 客户端/代理 | **内置** |
| 生态/资料 | 中 | **高** |
| 许可自由 | **BSD** | RSALv2（Valkey BSD） |
| 运维复杂度 | **低** | 中 |

```text
一句话选型：
  只要缓存 → 两者都行（Memcached 更简更快）
  缓存 + 其他需求 → Redis（功能覆盖）
  极致吞吐 + 极简运维 → Memcached
  许可敏感 → Memcached 或 Valkey
```

## 4. 双用架构

### 4.1 为什么双用

```text
真实生产（2025-2026 常见）：
  Redis：会话、实时特性（排行榜/锁/队列）、持久化需求
  Memcached：高吞吐页面/API 缓存（纯缓存负载）

原因：
  Memcached 的多核吞吐与内存效率适合"纯缓存洪峰"
  Redis 的功能密度适合"状态与实时"
  → 各取所长（不互斥）

Facebook 级实践：
  大规模 Memcached 集群（数十 TB）
  Redis 承担特定功能（计数/队列等）
```

### 4.2 双用架构模式

```text
典型部署：
  应用 → Memcached（页面/查询缓存，高速层）
        → Redis（会话/锁/计数，功能层）
        → 数据库

数据划分原则：
  按"数据特性"划分（不是按团队偏好）：
    可丢、读多、大流量 → Memcached
    需持久/原子/结构 → Redis

注意：
  两套系统 = 两套运维（监控/容量/排障）
  → 中小团队慎重（单一系统更省）
```

### 4.3 简化建议

```text
何时只需一个：
  中小规模 → Redis 一个就够（功能覆盖）
  纯缓存场景 → Memcached 一个就够（简单高效）
  复杂混合 → 双用（各取所长）

演进路径：
  起步：Redis（功能全）
  规模大 + 缓存洪峰 → 增加 Memcached 缓存层
  或：起步 Memcached（简单）→ 需要功能加 Redis
```

## 5. 迁移场景

### 5.1 Memcached → Redis

```text
何时迁移：
  需要持久化/结构/集群
  需要原子复合操作（Lua）
  生态/工具需求（监控/客户端）

迁移方式：
  ① 双写过渡（同时写两者 → 逐步切读）
  ② 一次性迁移（低峰期导出导入）
  ③ 协议层：Redis 6.2+ 无 memcached 协议兼容
    → 需应用改造（客户端替换）

改造点：
  客户端：Xmemcached → Jedis/Lettuce
  命令：get/set → 对应（+ 新功能）
  序列化：复用（JSON 等）
  TTL/过期：语义相同
```

### 5.2 Redis → Memcached

```text
何时迁移（罕见）：
  纯缓存场景 + 吞吐瓶颈（多核）
  许可/合规考虑（BSD）

迁移注意：
  失去：持久化/结构/原子操作
  → 迁移前确认"确实只用缓存能力"

现实：Redis → Memcached 迁移很少
  更多是"新增 Memcached 层"而非替换
```

### 5.3 迁移检查清单

```text
① 功能盘点：用了 Redis 哪些能力？
   （仅 KV → 可迁；结构/持久化 → 不可）
② 数据量：缓存数据可重建？（缓存可丢前提）
③ 客户端改造：命令映射/序列化兼容
④ 双写验证：一致性对比（过渡期）
⑤ 回滚预案：保留旧系统（灰度切换）
⑥ 性能验证：新架构吞吐/延迟达标
```

> 🎯 **核心要点**：选型的本质是"需求 vs 能力"的匹配——Memcached 赢在"纯缓存极致"（多核吞吐、内存效率、BSD、极简运维），Redis 赢在"功能密度"（结构/持久化/集群/生态）。2026 年的新变量是 Redis 双许可与 Valkey；主流架构是**双用**（Memcached 管高速缓存、Redis 管状态与实时）。迁移前必答：你的需求真的只有 KV 缓存吗？

## 6. 结论与建议

### 6.1 最终建议（2026 视角）

| 场景 | 建议 |
|------|------|
| 新项目（不确定需求） | Redis/Valkey（功能覆盖） |
| 纯缓存 + 高吞吐 | Memcached（简单高效） |
| 大厂规模（缓存洪峰） | 双用（Memcached + Redis） |
| 许可敏感 | Memcached 或 Valkey |
| 云上 | 云托管（按需选型） |

### 6.2 学习建议

```text
① 先掌握缓存通用理论（本目录 02/06 模块：内存/三问题）
② 再对比掌握两者（08 模块：选型框架）
③ 实践：一个真实缓存场景跑通（页面/查询缓存）
④ 关注：Valkey 生态、Redis 8.x 演进、Memcached 1.6 更新

配套阅读：
  Redis/ 兄弟目录（功能与命令深入）
  分布式系统与架构/（一致性哈希/缓存模式）
  MySQL/（缓存回源与一致性）
```

> 🎯 **核心要点**：Memcached vs Redis 不是"谁更好"，而是"需求匹配谁"——纯缓存极致选 Memcached、多功能存储选 Redis、大规模双用。2025-2026 的生态现实：**Memcached 依然在"高吞吐纯缓存"领域不可替代**（多线程 + slab + BSD），Redis/Valkey 统治多功能场景。选型四问（纯缓存？持久化？集群？吞吐？）能覆盖 90% 的决策场景。
