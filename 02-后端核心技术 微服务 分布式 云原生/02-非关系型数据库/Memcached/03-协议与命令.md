## 1. 两种协议

### 1.1 ASCII vs 二进制

| 维度 | ASCII | 二进制 |
|------|:---:|:---:|
| 可读性 | ✅（telnet 直接调试） | ❌ |
| 效率 | 文本解析开销 | 更紧凑 |
| 功能 | 完整 | 完整 + 扩展 |
| 适用 | 调试/简单客户端 | 生产（效率） |

```text
协议选择：
  Java 客户端（Xmemcached）默认二进制（可配）
  telnet/nc 调试用 ASCII
  两者可混用（同一服务器同时支持）

telnet 调试：
  telnet localhost 11211
  set foo 0 60 5
  hello
  STORED
  get foo
  VALUE foo 0 5
  hello
```

### 1.2 协议基础

```text
传输：TCP（默认端口 11211）
命令格式（ASCII）：
  <command> <key> <flags> <exptime> <bytes> [noreply]\r\n
  <data block>\r\n

响应：
  STORED（成功）/ NOT_STORED（条件不满足）
  DELETED / NOT_FOUND
  END（get 结束标记）
  ERROR / CLIENT_ERROR / SERVER_ERROR

key 规则：
  长度 ≤ 250 字节
  不含空格与控制字符
  （二进制协议无此限制）
```

## 2. 核心命令集

### 2.1 存储命令

| 命令 | 语义 | 行为 |
|------|------|------|
| set | 无条件存储 | 覆盖（存在则更新） |
| add | 仅当键不存在 | 已存在 → NOT_STORED |
| replace | 仅当键存在 | 不存在 → NOT_STORED |
| append | 值尾部追加 | 键必须存在 |
| prepend | 值头部追加 | 键必须存在 |
| cas | 条件存储（版本校验） | 版本不符 → EXISTS |

```text
存储命令参数：
  set <key> <flags> <exptime> <bytes> [noreply]
  flags：客户端自定义元数据（如序列化类型）
  exptime：过期（0=永不过期，秒数）
  bytes：值长度（字节）

选型：
  初始化缓存 → add（防覆盖）
  更新缓存 → set（无条件）
  条件更新 → cas（并发安全）
```

### 2.2 读取命令

```text
get <key> [<key>...]        单/多键读取
gets <key> [<key>...]       读取 + CAS 版本号

响应：
  VALUE <key> <flags> <bytes> [<cas-id>]
  <data>
  END

批量 get 的意义：
  一次请求多个键（网络往返合并）
  → Java 客户端 getBulk 的协议基础
```

### 2.3 删除命令

```text
delete <key> [<time>] [noreply]
  默认立即删除
  <time>：延迟删除（键在指定秒内不可用）
    → 用于"延迟双删"策略的协议支持

响应：DELETED / NOT_FOUND

flush_all [<delay>]
  清空全部（可延迟）
  实现：置全局过期时间（不真正释放内存）
  → 新写入正常，旧数据全部失效
```

## 3. 过期机制

### 3.1 exptime 的两种形式

```text
exptime 语义：
  0：永不过期（默认）
  < 30 天：相对过期（从现在起 N 秒）
  ≥ 30 天：绝对过期（Unix 时间戳）

注意：30 天分界线（避免歧义）
  设 30 天以上 → 解释为时间戳
  例：exptime=2592000（30 天）→ 相对
      exptime=2592001 → 时间戳（1970+30天）

工程陷阱：误用时间戳导致立即过期/长期不过期
  → 客户端库通常封装（传相对秒数）
```

### 3.2 过期的实现

```text
两级清理：
  ① 惰性：get 时检查 → 过期返回 miss
  ② 定期：后台线程扫描（lru_crawler）

过期 item 的处理：
  不立即释放（惰性）
  定期 crawler 回收 → 空闲 chunk
  内存压力 → LRU 淘汰（含未过期）

工程观察：
  stats items → expired_unfetched
  → 大量过期未读 = TTL 偏长/垃圾键多
```

### 3.3 TTL 设计

| 场景 | TTL 建议 |
|------|---------|
| 热点查询结果 | 30s-5min（按数据变化频率） |
| 页面片段 | 1-10min |
| 配置类 | 5-30min |
| 会话（可丢） | 30min-24h |
| 永不失效数据 | 0（但会占内存） |

```text
TTL 设计原则：
  ① 短于数据变化周期（避免脏数据）
  ② 不长于内存可承受时间（垃圾堆积）
  ③ 热点数据 TTL 内多次命中才有价值
  ④ 与"缓存三问题"配合（06 模块）
```

## 4. CAS：并发控制

### 4.1 为什么需要 CAS

```text
问题（并发覆盖）：
  两个请求同时 get 同一键 → 都修改 → 后写覆盖先写
  例：计数器/缓存更新的"丢失更新"

CAS（Compare-And-Swap）流程：
  ① gets 读取（拿到 cas-id 版本号）
  ② 应用处理
  ③ cas 写入（带 cas-id）
  ④ 版本匹配 → 成功；不匹配 → EXISTS（重试）
```

### 4.2 CAS 语义

```text
cas <key> <flags> <exptime> <bytes> <cas-id> [noreply]

响应：
  STORED：成功（版本匹配）
  EXISTS：版本不匹配（已被其他客户端修改）
  NOT_FOUND：键不存在（已被删除）

Java（Xmemcached）：
  GetsResponse resp = client.gets(key);
  long cas = resp.getCas();
  client.cas(key, newValue, cas);

适用场景：
  需要"读-改-写"原子的业务
  缓存回填的并发保护
```

### 4.3 CAS 与淘汰的交互

```text
注意：CAS 不保护"被 LRU 淘汰"的键
  键被淘汰 → NOT_FOUND（而非 EXISTS）
  → 应用需处理（重新初始化）

CAS 的限制：
  粒度：整个值（无字段级）
  重试：冲突需应用层重试
  适用：低频冲突场景（高频用 Redis INCR）

替代方案：
  计数场景 → Redis INCR（原子）
  缓存更新 → 删除而非 CAS（更简单）
```

## 5. 计数器与特殊命令

### 5.1 计数器

```text
incr <key> <delta>     # 值自增
decr <key> <delta>     # 值自减

规则：
  值必须是数字字符串（10 进制，无符号 64 位）
  键不存在 → NOT_FOUND（可用 add 初始化）
  自减到 0 以下 → 归 0（不出现负数）

适用：简单计数（PV/UV 近似、限流窗口内计数）

限制：无原子"读-改-写复合"（仅自增/自减）
  复杂计数 → Redis（INCRBY + 数据结构）
```

### 5.2 其他命令

```text
touch <key> <exptime>     # 更新过期时间（不读值）
  适用：滑动过期（活跃会话续期）

stats [subcommand]        # 统计信息
  stats / stats slabs / stats items / stats sizes
  （运维监控的基础，06 模块）

version                   # 版本信息
verbosity <level>         # 日志级别
quit                      # 断开
```

### 5.3 批量与管道

```text
批量读取：
  get key1 key2 key3（多键一次往返）
  → Java getBulk（网络优化关键）

管道（pipelining）：
  连续发送多条命令（不等响应）
  → 减少往返（吞吐大幅提升）
  → Java 客户端自动/手动支持

工程收益：
  批量 + 管道：吞吐提升 2-10 倍（网络往返主导时）
  实测参考：管道化可达百万级 ops/s
```

## 6. 协议工程实践

### 6.1 常见错误

| 错误 | 后果 |
|------|------|
| 大 key（>1MB） | 存储失败/性能差 |
| key 含空格/超长 | 协议错误 |
| exptime 误用时间戳 | 立即过期/永久有效 |
| 忽略 NOT_FOUND | 逻辑错误（键不存在） |
| 无 noreply 的批量写 | 每命令等响应（慢） |
| CAS 无重试 | 更新丢失 |

### 6.2 协议层优化

```text
① 批量 get（getBulk）：合并网络往返
② 管道写：连续 set（noreply）
③ 压缩值：大文本压缩（CPU 换带宽）
④ 序列化选择：紧凑格式（protobuf > JSON > Java 序列化）
⑤ 连接池：复用长连接（避免建连开销）

Java 侧（Xmemcached）：
  getBulk(keys) 批量读
  setWithNoReply 异步写
  连接池配置（min/max conn）

（完整 Java 实践见 07 模块）
```

> 🎯 **核心要点**：Memcached 协议 ≈ 15 个命令，但每个都有精确语义——set/add/replace/cas 的差别（无条件/不存在/存在/版本）、exptime 的 30 天分界、gets+cas 的并发控制、incr/decr 的计数器。工程要点：**批量 get 与管道是吞吐关键、exptime 语义要清楚、CAS 用于低频冲突**。协议简单 = 易调试 = 少出错。
