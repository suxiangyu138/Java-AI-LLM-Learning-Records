## 1. Memcached 是什么

### 1.1 定义

**Memcached**：高性能的分布式内存对象缓存系统（BSD 许可）。

```text
核心定位一句话：
  "用内存缓存减轻数据库负载"——把热点数据放在内存里，
  让查询走内存而不是数据库。

起源：2003 年 Brad Fitzpatrick（LiveJournal）
  解决：动态网站的数据库压力（每请求多次查询）
  方案：热点数据（用户信息、会话、页面片段）缓存到内存

事实：Facebook 的缓存系统（数十 TB 内存、百万级 QPS）基于 Memcached
```

### 1.2 缓存的位置

```text
典型架构位置：
  应用层 → Memcached（内存缓存）→ 数据库

数据流（Cache-Aside 模式）：
  读：查缓存 → 命中返回；未命中 → 查库 → 回填缓存
  写：写库 → 失效缓存（或更新）

Memcached 是"旁路缓存"：
  应用主动管理缓存（读写路径）
  数据库是唯一真相源（缓存可随时丢弃）
```

> 🎯 核心认知：**Memcached 是缓存，不是数据库**——它的数据随时可丢（重启即失）、由应用管理生命周期。这个定位决定了它的设计（无持久化、无复制）与价值（极简单、极快）。

## 2. 设计哲学：刻意简单

### 2.1 只做一件事

```text
Memcached 的能力边界（刻意保留）：
  做：KV 存储（字符串值）、过期、LRU 淘汰、CAS
  不做：持久化、复制、集群、数据结构、脚本、发布订阅

设计原则（官方口径）：
  ① 简单 = 可靠（功能越少 bug 越少）
  ② 简单 = 快（无多余路径）
  ③ 简单 = 可预测（行为透明）

Facebook 经验：大规模缓存系统不需要复杂功能
  → 复杂性放在客户端/代理层（mcrouter）
```

### 2.2 简单带来的工程收益

| 收益 | 说明 |
|------|------|
| 吞吐 | 多线程 + 极简路径 → 数百万 ops/s |
| 内存效率 | slab 分配器（每键 60-70 字节） |
| 运维简单 | 约 15 个命令、无配置文件地狱 |
| 可预测 | 行为透明（无后台魔法） |
| 许可自由 | BSD（2026 年 Redis 双许可对比下更显宽松） |

```text
对比 Redis 的复杂化（2024+）：
  Redis 7.x/8.x：模块、函数、集群、许可变化（RSALv2/SSPL）
  Memcached 1.6.x：保持稳定（功能冻结是特性）

工程意义：
  需要"极简高吞吐缓存" → Memcached 无可替代
  需要"多功能存储" → Redis
```

## 3. 适用场景与边界

### 3.1 适用场景

| 场景 | 说明 |
|------|------|
| HTML 页面片段缓存 | 大对象（可配置 slab） |
| API 响应缓存 | 高频查询结果 |
| 数据库查询结果缓存 | 热点查询（Cache-Aside） |
| 会话缓存（可丢失） | 非关键会话 |
| 高吞吐缓存层 | 多核机器上的极致吞吐 |
| 亿级键缓存 | 低每键开销（内存效率） |

### 3.2 不适用场景

| 场景 | 原因 | 替代 |
|------|------|------|
| 需持久化 | 无持久化 | Redis（RDB/AOF） |
| 需复制/高可用 | 无内置复制 | Redis Sentinel/Cluster |
| 复杂数据结构 | 仅字符串 | Redis |
| 排行榜/计数器 | 无原子复合操作 | Redis（Sorted Set/INCR） |
| 消息队列 | 无 pub/sub/streams | Redis/Kafka |
| 分布式锁 | 无内置锁原语 | Redis（SETNX） |

> ⚠️ 工程铁律：**Memcached 是"纯缓存"，不要指望它承担数据库/队列/锁的职责**——需要这些功能时用 Redis 或其他中间件，Memcached 只做它擅长的（高吞吐 KV 缓存）。

## 4. 系统架构与数据流

### 4.1 整体架构

```text
┌────────────┐      ┌─────────────┐      ┌────────────┐
│  应用进程    │ ───→ │  Memcached   │ ───→ │   数据库     │
│（客户端库）  │ ←─── │  （内存缓存）  │ ←─── │（真相源）    │
└────────────┘      └─────────────┘      └────────────┘
      │                    │
      │  一致性哈希路由      │  多节点（客户端分片）
      └────────────────────┘
```

```text
组件构成：
  ① 客户端库：路由（一致性哈希）、序列化、连接池
  ② 服务端：内存存储 + 协议处理（多线程）
  ③ 代理层（可选）：mcrouter/Twemproxy（路由/故障转移）

关键：无中心协调（无集群元数据服务）
  → 客户端自己知道"哪个键在哪个节点"
  → 节点增删 → 客户端哈希环更新
```

### 4.2 读/写数据流

```text
读路径（Cache-Aside）：
  ① get(key) → 命中？返回（内存，微秒级）
  ② 未命中 → 查询数据库
  ③ 回填：set(key, value, ttl)
  ④ 后续读命中（直到过期/淘汰）

写路径：
  ① 写数据库（事务）
  ② 删除缓存键（或更新——删除更简单可靠）
  ③ 一致性：下次读重新回填

缓存一致性策略：
  删除（推荐）vs 更新（复杂）
  延迟双删（并发场景）
  —— 详见 06 模块缓存三问题
```

### 4.3 客户端-服务端通信

```text
协议：ASCII（调试友好）/ 二进制（效率）
  传输：TCP（默认）/ UDP（丢弃场景）
  连接：长连接 + 连接池（客户端管理）

命令示例（ASCII）：
  set key 0 60 5\r\nhello\r\n    # 存（TTL 60s）
  get key\r\n                   # 取
  delete key\r\n                # 删
  incr key 1\r\n                # 自增

（完整命令见 03 模块）
```

## 5. 与 Redis 的定位差异

### 5.1 一句话定位

| 维度 | Memcached | Redis |
|------|-----------|-------|
| 定位 | 纯 KV 缓存 | 多功能数据结构服务器 |
| 核心能力 | 快、简单、内存省 | 数据结构 + 持久化 + 集群 |
| 哲学 | 刻意简单 | 功能丰富 |
| 数据可丢 | ✅（缓存） | ❌（可持久） |

```text
定位差异的根源：
  Memcached：把"缓存"做到极致（简单可靠）
  Redis：从缓存演变为"数据结构存储"（多功能）

选型直觉：
  只要缓存 → Memcached 或 Redis 都行（看其他需求）
  需要持久化/结构/集群 → Redis
  极致吞吐 + 简单 → Memcached

（完整对比见 08 模块）
```

## 6. 历史与生态

### 6.1 发展简史

```text
2003：Brad Fitzpatrick 创建（LiveJournal）
2007-2010：Facebook 大规模采用（带动性能优化）
2011+：多线程改进、二进制协议、slab 改进
2016+：1.5.x（分段 LRU）、1.6.x（扩展、改进）
2020s：稳定维护（1.6.x 系列）

2025-2026 状态：
  版本：1.6.x（1.6.24 等小版本迭代）
  定位：保持"简单缓存"路线（功能冻结）
  社区：维护活跃度低于 Redis，但稳定可靠
```

### 6.2 生态组件

| 组件 | 作用 |
|------|------|
| mcrouter（Facebook） | 代理层：路由/故障转移/批量 |
| Twemproxy（Twitter） | 轻量代理：分片/连接复用 |
| repcached（第三方） | 复制扩展（非官方） |
| Xmemcached | Java 客户端（主流） |
| Memcached-java-client | 老牌 Java 客户端 |
| Danga 系列 | Perl/各语言客户端 |

> 🎯 **核心要点**：Memcached 的定位 = "刻意简单的分布式内存缓存"——它用"功能冻结"换取极简可靠与极致吞吐，20 多年在 Facebook/大规模生产验证。理解它的哲学（简单=可靠）、边界（纯缓存）与架构（客户端分片无中心），是使用与选型的前提。2025-2026 它在"纯缓存"领域依然无可替代（尤其多核高吞吐场景）。
