## 1. 无集群：分布式在客户端

### 1.1 设计决策

```text
Memcached 的分布式选择：
  服务端：无集群、无元数据、无协调（每个节点独立）
  客户端：负责路由（一致性哈希）与故障处理

为什么这样设计：
  ① 简单可靠（服务端无状态协调）
  ② 水平扩展容易（加节点 = 客户端配置更新）
  ③ 无中心（无单点故障）

对比 Redis Cluster：
  服务端管理槽位（16384 个哈希槽）
  客户端只做重定向（MOVED）
  → 两种"分布式"哲学：客户端分片 vs 服务端集群
```

### 1.2 客户端路由

```text
路由流程（客户端）：
  ① 计算 key 的哈希
  ② 哈希环定位 → 选择节点
  ③ 发送请求到该节点

客户端配置：
  节点列表（server list）
  一致性哈希环（启动时构建）

工程含义：
  客户端版本一致（哈希算法一致）→ 所有客户端路由一致
  客户端升级 → 可能改变路由 → 缓存短暂失效（可接受）
```

> 🎯 核心认知：**Memcached 的"分布式"是客户端特性，不是服务端特性**——服务端只是"各自独立的内存仓库"，客户端负责"哪个键去哪台机器"。这个设计让 Memcached 服务端保持极简，分布式复杂度全部收敛到客户端/代理层。

## 2. 一致性哈希

### 2.1 朴素取模的问题

```text
朴素路由：node = hash(key) % N

问题：节点数变化（增/减）→ 几乎所有键重新映射
  N=4 → N=5：80% 的键换节点 → 缓存全部失效（雪崩）

一致性哈希的解法：
  把节点与键都映射到哈希环（0 ~ 2³²-1）
  键归属：顺时针第一个节点
  → 节点增减只影响相邻区间（少量键迁移）
```

### 2.2 一致性哈希环

```text
哈希环结构：
  ① 节点哈希：hash(server_ip:port) → 环上位置
  ② 键哈希：hash(key) → 环上位置
  ③ 路由：顺时针找最近的节点

节点减少的影响：
  只影响"该节点负责的环区间"的键
  → 迁移比例 ≈ 1/N（N=4 时 25%，而非 80%）

特性：
  单调性：节点增减只影响相邻区间
  平衡性：节点均匀分布时键均匀分布（虚拟节点保证）
```

### 2.3 最小化失效的原则

```text
缓存失效的可控性：
  加节点：1/N 的键迁移（其余命中不变）
  减节点：1/N 的键失效（其余命中不变）
  → 对比取模的"全部失效"，一致性哈希是生产必需

工程注意：
  一致性哈希只保证"路由稳定"，不保证"数据迁移"
  → 迁移的键 = 未命中 → 回源数据库 → 回填
  → 大规模增删节点时仍会有"缓存雪崩窗口"（可用预热缓解）
```

## 3. 虚拟节点

### 3.1 为什么需要虚拟节点

```text
朴素环的问题（节点少时）：
  节点哈希位置随机 → 环区间不均匀
  → 少量节点承担大量键（负载不均）

例：3 个节点，哈希位置扎堆 → 一个节点负责 70% 区间

虚拟节点（Virtual Nodes）：
  每个物理节点在环上放置多个虚拟点（如 160 个）
  物理节点的区间 = 其所有虚拟点区间的总和
  → 分布更均匀（大数定律）

实现：hash(server:port#0)、hash(server:port#1)...
```

### 3.2 虚拟节点的效果

| 节点数 | 无虚拟节点偏差 | 160 虚拟节点偏差 |
|:---:|:---:|:---:|
| 3 | 可达 40%+ | <5% |
| 10 | 可达 15% | <2% |
| 50 | 可达 5% | <1% |

```text
工程结论：
  虚拟节点 = 用"哈希多点"换"负载均衡"
  客户端（Xmemcached）默认启用（权重可配）
  节点权重：weight 参数（大节点多虚拟点）

注意：虚拟节点数影响内存与构建时间
  160/节点是主流默认（Ketama 算法）
```

### 2.4 Ketama 算法

```text
Ketama：Memcached 生态的事实标准哈希算法
  特性：
    ① 虚拟节点：每物理节点 160 个虚拟点
    ② 一致性：节点增删影响最小
    ③ 兼容：所有主流客户端实现一致

支持：
  Xmemcached、Spymemcached、libmemcached 等
  → 多客户端共存时路由一致（关键！）

工程意义：
  客户端混用（不同语言）时路由必须一致
  → 统一用 Ketama（避免双写不一致）
```

## 4. 节点增删与缓存失效

### 4.1 增删节点的流程

```text
加节点：
  ① 部署新节点
  ② 客户端配置加入（重启/热更新）
  ③ 哈希环重建 → 约 1/N 键路由到新节点
  ④ 这些键未命中 → 回源回填（缓存预热）

删节点（计划内）：
  ① 客户端配置移除（先）
  ② 环重建 → 受影响键路由到邻居
  ③ 停机节点（后）

故障删节点：
  ① 客户端检测失败 → 临时移除（或降级）
  ② 环重建 → 受影响键失效
  ③ 恢复后重新加入（键重新分布）
```

### 4.2 缓存失效的治理

```text
节点增删的"缓存雪崩窗口"：
  1/N 键同时失效 → 数据库瞬时压力
  → 大规模变更需预热/限流

治理手段：
  ① 分批迁移（逐个节点，非同时）
  ② 预热：预先回填新节点区间（脚本/工具）
  ③ 限流：数据库侧保护（降级）
  ④ 双读：新旧环并行（复杂，少用）

经验：生产节点变更选低峰期 + 预热
```

## 5. 故障处理

### 5.1 客户端侧故障处理

```text
节点故障的检测：
  连接失败/超时（客户端探活）

处理策略：
  ① 临时移除（从环中剔除 → 键路由到邻居）
  ② 重试（短超时 + 有限重试）
  ③ 降级（缓存 miss → 直接查库）

故障恢复：
  节点恢复 → 客户端重新加入
  → 该节点区间键重新分布（缓存重建）

工程权衡：
  快速剔除（保护请求延迟）vs 保留重试（避免抖动）
  → 配置：failover 阈值/重试次数
```

### 5.2 雪崩风险

```text
故障导致的雪崩链：
  节点故障 → 1/N 键失效 → 数据库压力 ↑
  → 数据库变慢 → 更多超时 → 更多节点被剔除 → 雪崩

防护：
  ① 客户端熔断（超时快速失败，不无限重试）
  ② 数据库限流/降级（缓存失效时的兜底）
  ③ 故障转移（代理层 mcrouter 自动切换）
  ④ 单节点故障不扩散（隔离）

（缓存三问题的完整治理见 06 模块）
```

### 5.3 无状态服务的优势

```text
Memcached 故障处理的独特优势：
  数据可丢（缓存）→ 无需数据恢复
  节点无状态 → 故障节点直接替换（新节点空缓存）
  无集群协调 → 无"脑裂/选主"问题

对比 Redis：
  主从切换（Sentinel/Cluster）有复杂度
  Memcached：客户端剔除 + 重建 = 完成

代价：故障窗口内缓存 miss（数据库承压）
  → 设计上接受（缓存本来就是"可丢的加速层"）
```

## 6. 代理层方案

### 6.1 mcrouter（Facebook）

```text
mcrouter：Memcached 代理层（Facebook 开源）
  能力：
    ① 路由（一致性哈希在代理层）
    ② 故障转移（节点失败自动切换）
    ③ 批量/管道（合并客户端请求）
    ④ 影子请求/预热（流量复制）
    ⑤ 运维友好（客户端无状态）

架构：
  应用 → mcrouter（代理）→ Memcached 集群
  → 客户端只需连代理（路由变化对客户端透明）
```

### 6.2 Twemproxy（Twitter）

```text
Twemproxy（nutcracker）：轻量代理
  能力：
    ① 分片（一致性哈希/取模）
    ② 连接复用（客户端连接合并）
    ③ 故障剔除（自动）

特点：
  更轻量（相比 mcrouter）
  维护活跃度较低（mcrouter 更活跃）

选型：
  Facebook 规模 → mcrouter（功能全）
  简单分片 → Twemproxy 或客户端直连
```

### 6.3 代理层的取舍

| 维度 | 客户端直连 | 代理层 |
|------|:---:|:---:|
| 延迟 | 低（直连） | +1 跳 |
| 路由管理 | 客户端配置 | 代理集中 |
| 故障转移 | 客户端处理 | 代理处理 |
| 运维 | 客户端升级 | 代理部署 |
| 适用 | 中小规模 | 大规模/多客户端 |

```text
工程建议：
  中小规模：客户端直连（简单）
  大规模/多语言客户端：代理层（集中管理）
  超大规模（Facebook）：代理 + 客户端双层
```

> 🎯 **核心要点**：Memcached 分布式 = **客户端一致性哈希（Ketama）+ 虚拟节点 + 故障剔除**——服务端零集群，复杂度全在客户端/代理层。核心收益：节点增删只影响 1/N 键（对比取模的全量失效）；核心风险：故障时的缓存失效窗口（数据库承压，需熔断/限流兜底）。大规模场景用 mcrouter 把路由收敛到代理层。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 分布式在哪实现？ | 客户端（服务端无集群） |
| 为什么一致性哈希？ | 节点变化只影响 1/N（vs 取模全失效） |
| 虚拟节点？ | 每节点多点哈希 → 负载均衡（Ketama 160 点） |
| 节点增删影响？ | 相邻区间键失效 → 回源回填（需预热） |
| 故障怎么处理？ | 客户端剔除 + 缓存重建（无数据恢复） |
| 代理层？ | mcrouter/Twemproxy（集中路由/故障转移） |
