## 1. 为什么需要 slab 分配器

### 1.1 朴素分配的问题

```text
直接 malloc/free 每个键值的问题：
  ① 内存碎片：频繁分配释放 → 碎片化 → 有效内存下降
  ② 每键开销大：分配头（元数据）占空间
  ③ 性能波动：malloc 在高碎片时变慢

slab 分配器的解法：
  预分配固定大小的内存单元（chunk）
  按大小分桶（slab class）
  → 无碎片、开销固定、分配 O(1)
```

### 1.2 内存效率的量化

| 指标 | Memcached（slab） | Redis（jemalloc） |
|------|:---:|:---:|
| 每键开销 | 60-70 字节 | 100-120 字节 |
| 内存碎片 | 极低（固定 chunk） | 低（jemalloc 优化） |
| 分配复杂度 | O(1) | O(1) |

```text
每键开销差异的意义：
  亿级键场景：Memcached 省 30-40% 内存
  → 同等内存下可缓存更多键
  → "内存效率"是 Memcached 的核心卖点之一
```

> 🎯 核心认知：**slab 分配器 = "用固定单元换零碎片"**——牺牲少量内部浪费（chunk 内未用空间），换来无碎片、O(1) 分配、可预测内存。这是 Memcached 内存效率的物理基础。

## 2. slab class 与 chunk

### 2.1 基本结构

```text
内存按 slab class 分桶（默认 64 个 class）：
  class 1：chunk 96 字节（默认最小）
  class 2：chunk 120 字节（增长因子 1.25）
  class N：chunk 大小按增长因子递增
  每 class 分配多个 slab（每个 slab 1MB）

chunk 结构：
  [item 元数据（键长/过期/标志等）| 键 | 值]

取值规则：值大小 → 落在最小能装下的 chunk 类
  → 小于 96 字节的值用 class 1
  → 96-120 字节用 class 2
```

### 2.2 增长因子（growth factor）

```text
增长因子（-f 参数，默认 1.25）：
  决定 chunk 大小增长速率：
    1.25：96 → 120 → 150 → 187 → ...（精细，碎片少）
    2.0：96 → 192 → 384 → ...（粗糙，省内存但浪费）

选择权衡：
  增长因子小 → chunk 贴合值大小（浪费少）但 class 多
  增长因子大 → class 少但 chunk 可能远大于值（浪费多）

调优经验：
  默认 1.25 适合大多数场景
  值大小分布集中 → 可调大（减少 class）
  值大小分布散 → 默认或调小
```

### 2.3 chunk 内部浪费

```text
内部碎片（slab 分配器的代价）：
  值 100 字节 → class 2（120 字节）→ 浪费 20 字节
  值 500 字节 → class 7（约 512）→ 浪费 12 字节

控制方式：
  ① 增长因子（匹配值分布）
  ② 应用层统一值大小（padding 对齐）
  ③ slab_chunk_max 调整

统计查看：
  stats slabs 命令 → 各 class 的 used_chunks/free_chunks
  → 分析哪类浪费多
```

## 3. 内存分配流程

### 3.1 写入流程

```text
set(key, value) 的内存路径：
  ① 计算值大小 → 定位 slab class（最小能装下）
  ② 从该 class 空闲链表取 chunk
  ③ 无空闲 chunk → 该 class 分配新 slab（预分配 1MB）
  ④ 全部 slab 用尽 → LRU 淘汰该 class 最旧 item
  ⑤ 写入 item（元数据 + 键 + 值）

关键特性：
  每个 class 独立分配/淘汰（互不影响）
  内存按需分配（-m 限制总量）
  淘汰只发生在"该 class 内存不足"时
```

### 3.2 内存上限（-m）

```text
-m 参数：最大内存（MB，默认 64MB）
  达到上限 → 不再分配新 slab
  → 写入触发 LRU 淘汰

内存分配的特点：
  惰性分配（slab 按需创建）
  总内存 = 已分配 slab 之和 ≤ -m
  淘汰 = 内存压力下的自我保护

调优注意：
  -m 过小 → 频繁淘汰（命中率低）
  -m 过大 → 内存浪费（OS 层面）
  用 stats 观察内存利用率调整
```

## 4. LRU 淘汰机制

### 4.1 分段 LRU（1.5+）

```text
分段 LRU（Segmented LRU）：
  每条 item 有"热/冷"属性（标志位）
  热链（Hot LRU）：新写入/被访问的 item
  冷链（Cold LRU）：降级的 item

淘汰流程：
  新 item → 热链尾部
  热链满 → 尾部 item 降级到冷链
  冷链满 → 淘汰冷链尾部（真正的驱逐）

目的：保护热数据（避免刚写入就被淘汰）
  → 提升命中率（对比简单 LRU）

（-o lru_maintainer 相关参数控制）
```

### 4.2 过期与淘汰

| 机制 | 时机 | 说明 |
|------|------|------|
| 惰性过期 | 读取时 | 读时检查 TTL，过期即删（返回 miss） |
| 定期清理 | 后台线程 | 定期扫描过期 item |
| LRU 淘汰 | 内存压力 | 冷链尾部驱逐（内存不足时） |

```text
关键理解：
  过期 item 不立即释放内存（惰性）
  → 大量过期键占内存直到被扫描/淘汰
  → TTL 设置过长的"垃圾键"影响命中率

统计：
  stats items → expired_unfetched（过期未被读）
  → 过期垃圾多 → 检查 TTL 设计
```

### 4.3 淘汰与命中率的权衡

```text
命中率 = 缓存有效性的核心指标
  影响因素：内存大小（-m）、TTL、淘汰策略、键分布

提升命中率的路径：
  ① 加大 -m（内存换命中）
  ② 合理 TTL（不短不过长）
  ③ 值大小分布贴合 chunk（减少内部浪费 = 更多 item）
  ④ 分段 LRU 参数调优（热数据保护）

生产目标：核心缓存命中率 > 95%（视场景）
```

## 5. 内存碎片与 1MB 限制

### 5.1 为什么 slab 无碎片

```text
外部碎片（传统 malloc 的问题）：
  频繁分配释放不同大小 → 内存空洞 → 有效容量下降

slab 的碎片控制：
  固定 chunk 大小 → 无外部碎片（空洞不可能）
  代价：内部碎片（chunk 大于值）
  → 总量可控、可预测（stats 可查）

对比 jemalloc（Redis）：
  两者都优秀（现代分配器）
  Memcached 的 slab 更"可预测"（每 class 独立）
```

### 5.2 1MB 值大小限制

```text
默认限制：单值 ≤ 1MB（-I 参数可调）

为什么限制：
  ① 大值破坏内存效率（占多个 slab、淘汰粒度粗）
  ② 大值拖慢网络传输（缓存应存小对象）
  ③ 大值增加复制成本（memcached 内部）

调整：
  -I 2m / -I 10m（调大，谨慎）
  或应用层拆分（大对象分片/存引用）

工程经验：
  缓存的值应"小而热"（页面片段、查询结果）
  大文件/大对象 → 存对象存储/文件系统，缓存只存元数据
```

## 6. 内存调优

### 6.1 关键参数

| 参数 | 默认 | 作用 |
|------|:---:|------|
| -m | 64MB | 最大内存 |
| -f | 1.25 | 增长因子 |
| -I | 1m | 最大值大小 |
| -o modern | — | 现代特性（LRU 维护器等） |
| slab_chunk_max | — | chunk 上限 |

### 6.2 调优流程

```text
① 观察 stats slabs/stats items（各 class 使用率）
② 分析值大小分布（应用层统计）
③ 调整增长因子（贴合分布）
④ 调整 -m（命中率目标）
⑤ 观察命中率（get_hits/get_misses）
⑥ 迭代

常用诊断命令：
  stats                    总体统计（命中率）
  stats slabs              各 class 分配/使用
  stats items              item 统计（过期/淘汰）
  stats sizes              值大小分布（调试模式）

性能基准参考（2025-2026 检索）：
  8 线程：~150 万 ops/s、p99 ~0.2ms
  （多核吞吐是 Memcached 相对 Redis 的优势场景）
```

> 🎯 **核心要点**：slab 分配器是 Memcached 内存效率的灵魂——固定 chunk 无碎片、O(1) 分配、每键 60-70 字节开销。调优三参数（-m/-f/-I）+ 分段 LRU 保护热数据；工程纪律：**值小而热（<1MB）、TTL 合理、按 class 观察**。理解"每个 class 独立淘汰"就能解释"为什么某些键总是被驱逐"。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 为什么 slab？ | 无碎片、O(1) 分配、开销固定 |
| chunk 怎么选？ | 最小能装下值的 class（增长因子控制粒度） |
| 每键开销？ | 60-70 字节（vs Redis 100-120） |
| LRU 怎么淘汰？ | 分段 LRU（热/冷链，保护热数据） |
| 1MB 限制？ | 单值默认 ≤1MB（-I 可调） |
| 调优三参数？ | -m（内存）、-f（增长因子）、-I（值上限） |
