## 1. 可用性模型：可丢缓存

### 1.1 缓存的可用性定位

```text
Memcached 的可用性模型：
  数据可丢（无持久化）→ 可用性目标 = "服务可用"，非"数据不丢"
  节点可替换（空缓存启动）→ 无数据恢复流程

与数据库的区别：
  数据库：数据是资产（必须不丢）
  缓存：数据是加速（丢了可重建）

高可用设计的核心：
  ① 缓存不可用 → 应用降级（直连数据库）
  ② 节点故障 → 客户端剔除 + 重建
  ③ 大规模失效 → 防雪崩（保护数据库）
```

### 1.2 可用性量化

```text
Memcached 可用性指标：
  服务可用性：节点存活（进程/网络）
  缓存有效性：命中率（数据是否还有价值）
  降级能力：缓存挂时应用能否正常工作

关键认知：缓存挂了 ≠ 系统挂了
  → 应用必须设计"缓存不可用时的降级路径"
  → 这是缓存架构的第一原则
```

> 🎯 核心认知：**Memcached 的高可用 = 应用的降级能力**——因为缓存可丢，可用性重点不在"缓存本身不挂"，而在"缓存挂了系统没事"。设计缓存架构时先回答：缓存全挂，系统还能跑吗？

## 2. 缓存雪崩

### 2.1 定义与成因

```text
雪崩：大量缓存同时失效 → 请求全部打到数据库 → 数据库崩溃

成因：
  ① 大量键同一 TTL（同时过期）
  ② 节点大规模故障（一致性哈希迁移）
  ③ 缓存服务重启（全量清空）

特征：数据库流量瞬时 N 倍 → 响应变慢 → 连接堆积 → 雪崩
```

### 2.2 防雪崩手段

| 手段 | 原理 | 适用 |
|------|------|------|
| TTL 随机化 | 过期时间加随机偏移（分散失效） | 批量设置场景 |
| 多级缓存 | 本地缓存 + 分布式缓存（缓冲） | 读多场景 |
| 熔断降级 | 数据库保护（限流/排队） | 高并发 |
| 预热 | 提前回填（重启/扩容后） | 计划内变更 |
| 互斥重建 | 单请求回源（其他等待） | 击穿场景（见下） |

```java
// TTL 随机化（防同时过期）
int ttl = baseTtl + random.nextInt(60);   // 基础 TTL + 0-60s 抖动
client.set(key, value, ttl);
```

### 2.3 多级缓存架构

```text
两级/三级缓存：
  本地缓存（Caffeine，进程内）→ Memcached → 数据库

链路：
  ① 本地命中（微秒级）→ 返回
  ② 本地 miss → Memcached（亚毫秒）→ 回填本地
  ③ Memcached miss → 数据库 → 回填两级

收益：
  本地缓存挡住大部分读（数据库压力骤降）
  雪崩窗口被本地缓存缓冲（重建风暴缓解）

代价：
  本地缓存一致性（更新需失效/短 TTL）
  内存占用（每节点一份）
```

## 3. 缓存击穿与穿透

### 3.1 缓存击穿

```text
击穿：单个热点 key 过期瞬间，大量并发请求同时回源

与雪崩的区别：
  雪崩：大量键同时失效（广度）
  击穿：单个热点键失效（深度）

典型场景：
  热点商品详情、热搜数据（单键高并发）

解法：
  ① 互斥锁（重建）：单请求回源，其余等待/返回旧值
  ② 逻辑过期：值内带过期时间，异步重建（不真删）
  ③ 永不过期 + 后台更新
```

```java
// 互斥重建（防击穿的核心模式）
Value v = client.get(key);
if (v == null) {
    if (tryLock(key)) {          // 分布式锁（抢到重建权）
        try {
            v = loadFromDb(key); // 单请求回源
            client.set(key, v, ttl);
        } finally { unlock(key); }
    } else {
        v = client.get(key);     // 其他请求：重试/返回旧值
    }
}
```

### 3.2 缓存穿透

```text
穿透：查询不存在的数据 → 缓存永远 miss → 每次打数据库

场景：
  恶意请求（随机 ID）、查询不存在的记录

后果：
  无效请求绕过缓存直达数据库（可能拖垮）

解法：
  ① 空值缓存：不存在也缓存（短 TTL）
  ② 布隆过滤器：请求前过滤（不存在直接拒绝）
  ③ 参数校验：非法参数拦截（应用层）
```

```java
// 空值缓存（防穿透）
Value v = client.get(key);
if (v == null) {
    v = loadFromDb(key);
    if (v == null) {
        client.set(key, EMPTY_PLACEHOLDER, 60);  // 空值也缓存（短 TTL）
        return null;
    }
    client.set(key, v, ttl);
}
return v;
```

### 3.3 三问题治理总表

| 问题 | 本质 | 核心解法 |
|------|------|---------|
| 雪崩 | 大量键同时失效 | TTL 随机化、多级缓存、预热 |
| 击穿 | 热点键失效瞬间 | 互斥重建、逻辑过期 |
| 穿透 | 不存在数据反复查询 | 空值缓存、布隆过滤器 |

```text
通用防线（自底向上）：
  ① 应用层：参数校验（拦截无效请求）
  ② 缓存层：空值缓存（穿透）、互斥（击穿）、随机 TTL（雪崩）
  ③ 数据库层：限流/熔断（最后防线）
```

## 4. 代理层高可用

### 4.1 mcrouter 的高可用能力

```text
mcrouter（Facebook）的高可用特性：
  ① 故障转移：节点失败 → 自动切换（路由到健康节点）
  ② 池化路由：多个池（主池/备池）切换
  ③ 降级策略：配置化（failover 阈值）
  ④ 影子流量：故障演练（复制请求观察）

架构：
  应用 → mcrouter（HA 逻辑）→ Memcached 集群
  → 客户端只需连代理（无状态）
```

### 4.2 故障转移的语义

```text
mcrouter 的故障转移语义：
  键路由到故障节点 → 重路由到备用节点
  备用节点无数据 → miss → 回源重建

注意：
  转移 ≠ 数据迁移（备用节点空缓存）
  转移的粒度：池级别（整个池故障）
  转移的代价：额外延迟（多一跳）

工程配置：
  主池 + 备池（或跨机房池）
  故障阈值（连续失败 N 次触发）
  恢复检测（周期探活）
```

### 4.3 代理层本身的可用性

```text
代理层的单点问题：
  mcrouter 挂 → 全部客户端不可用

解法：
  ① 多代理 + 客户端负载均衡（L4/L7）
  ② 代理无状态（可水平扩展）
  ③ 客户端直连兜底（代理故障时降级）

架构演进：
  简单：客户端直连（无代理）
  标准：多代理 + 客户端 LB
  复杂：分层代理（区域级）
```

## 5. 监控体系

### 5.1 核心指标

| 指标 | 命令/来源 | 告警阈值 |
|------|-----------|---------|
| 命中率 | stats（get_hits/get_misses） | <90% 关注、<80% 告警 |
| 内存使用 | stats（bytes/limit_maxbytes） | >80% 关注 |
| 淘汰率 | stats（evictions） | 持续增长告警 |
| 连接数 | stats（curr_connections） | 接近 -c 上限 |
| CPU | 系统监控 | >80% 关注 |
| 过期垃圾 | stats items（expired_unfetched） | 大量 → TTL 检查 |

### 5.2 监控命令详解

```text
stats 关键字段：
  get_hits / get_misses → 命中率
  cmd_get / cmd_set → 读写量
  curr_items / total_items → 键数量
  bytes / limit_maxbytes → 内存
  evictions → 淘汰数
  curr_connections → 当前连接
  threads → 线程数

stats slabs：
  各 class 的 used_chunks / free_chunks
  → 内存分布是否合理（内部碎片）

stats items：
  expired_unfetched（过期未读）
  evicted_unfetched（淘汰未读）
  → 缓存有效性诊断
```

### 5.3 监控集成

```text
采集方式：
  ① memcached_exporter（Prometheus 生态）
  ② 自研采集（stats 命令轮询）
  ③ 云服务自带监控（云托管场景）

告警设计：
  命中率骤降（雪崩信号）
  淘汰率飙升（内存压力）
  连接数激增（客户端异常）
  节点不可达（进程/网络）

日志：
  访问日志（-v 级别）
  错误日志（连接/协议错误）
```

## 6. 应急预案

### 6.1 场景与响应

| 场景 | 响应 |
|------|------|
| 单节点故障 | 客户端自动剔除（设计内）→ 观察命中率 |
| 缓存雪崩 | 熔断降级（数据库保护）→ 限流 → 预热 |
| 命中率骤降 | 检查内存（淘汰）/节点（剔除）/TTL |
| 节点扩容 | 低峰期 + 预热 |
| 版本升级 | 滚动升级（逐节点） |

### 6.2 降级方案设计

```text
缓存故障的降级阶梯：
  ① 本地缓存（Caffeine）→ 仍可服务
  ② 直连数据库（限流）→ 可用但慢
  ③ 服务降级（返回旧数据/缓存快照）→ 保命

设计原则：
  降级路径必须"预演过"（故障演练）
  降级阈值要明确（什么条件触发）
  恢复路径要自动（探测恢复自动切回）

演练建议：
  定期杀节点（混沌测试）
  观察应用降级是否正常
  记录恢复时间（目标：分钟级）
```

### 6.3 与 Redis 运维的对比

| 维度 | Memcached | Redis |
|------|:---:|:---:|
| 持久化 | 无（重启即失） | RDB/AOF |
| 复制 | 无内置（代理/第三方） | 主从内置 |
| 故障恢复 | 客户端剔除+重建 | Sentinel 自动切换 |
| 数据安全 | 可丢（缓存） | 可持久（需配置） |
| 运维复杂度 | 低（简单） | 中（持久化/复制） |

```text
Memcached 运维的独特优势：
  无持久化 → 无备份/恢复流程
  无主从 → 无切换/脑裂处理
  无集群 → 无槽位/迁移管理
  → "最少的运维负担"是它被选择的原因之一
```

> 🎯 **核心要点**：Memcached 高可用 = "可丢缓存 + 降级能力"模型——无持久化反而简化运维（无备份/无切换）。工程重心在三问题治理（雪崩/击穿/穿透：TTL 随机化/互斥重建/空值缓存）+ 代理层故障转移（mcrouter）+ 监控（命中率/淘汰率/连接）+ 降级演练。铁律：**缓存架构必须回答"缓存全挂系统还能跑吗"，答案要经过演练验证**。
