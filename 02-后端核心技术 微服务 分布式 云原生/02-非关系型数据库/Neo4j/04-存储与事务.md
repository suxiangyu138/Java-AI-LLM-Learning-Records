## 1. 原生图存储

### 1.1 什么是原生图存储

```text
原生图存储（Native Graph Storage）：
  节点、关系、属性以图结构物理存储
  节点直接持有指向邻居的指针（免索引邻接）

对比非原生图数据库：
  非原生（基于关系型/文档存储上层建模）：
    → 遍历依赖底层存储的索引/JOIN
  原生（Neo4j）：
    → 遍历 = 指针跳转（O(1)/跳）

核心文件（Neo4j 的存储布局）：
  neostore.nodestore.db：节点记录
  neostore.relationshipstore.db：关系记录
  neostore.propertystore.db：属性记录
  → 节点/关系/属性分离存储
```

### 1.2 存储的物理布局

```text
节点记录：
  [Label 引用 | 第一个关系指针 | 第一个属性指针]

关系记录：
  [起点节点 | 终点节点 | 关系类型 | 上一个/下一个关系指针]

属性记录：
  [键 | 值 | 下一个属性指针]（链式）

遍历路径：
  节点 → 关系指针 → 关系记录 → 邻居节点指针 → ...
  → 全程指针跳转（免索引）

设计意义：
  ① 多跳遍历高效（指针 vs 索引）
  ② 存储紧凑（固定大小记录）
  ③ 局部性好（相关数据邻近）
```

> 🎯 核心认知：**原生图存储 = "节点记住邻居"**——每个节点物理存储其关系的指针链，遍历就是沿指针走。这是图数据库与"在 SQL 上模拟图"的根本区别，也是多跳查询性能的物理基础。

## 2. 存储文件结构

### 2.1 存储文件与页缓存

```text
存储文件家族（数据库目录）：
  neostore.*（节点/关系/属性/Label/索引记录）
  index/（索引文件）
  schema/（约束/索引定义）
  transactions/（事务日志）

页缓存（Page Cache）：
  数据文件的内存映射（mmap）
  作用：热数据驻留内存（读性能核心）
  配置：dbms.memory.pagecache.size（建议 ≥ 数据大小）

写路径：
  事务 → 事务日志（WAL）→ 页缓存 → 后台刷盘
  → 与数据库的 WAL 模式同构
```

### 2.2 存储特性

```text
存储的特性：
  ① 事务性（ACID）
  ② 崩溃恢复（WAL 重放）
  ③ 在线备份（事务日志）
  ④ 高扇出优化（关系链式存储）

容量规划：
  存储大小 ≈ 节点数 × 记录大小 + 关系数 × 关系大小
  关系记录比节点记录更小（固定结构）

监控：
  db.storage 指标（页缓存命中率/存储增长）
  → 命中率低 = pagecache 不足
```

## 3. Bolt 协议与驱动

### 3.1 Bolt 协议

```text
Bolt：Neo4j 的二进制协议（驱动与服务器通信）

特点：
  ① 二进制（紧凑高效）
  ② 类型系统（图类型原生编码：Node/Relationship/Path）
  ③ 管线化（请求/响应流水）
  ④ 加密（TLS 支持）

对比 HTTP API：
  HTTP：REST 风格（简单、调试友好）
  Bolt：高性能（生产驱动默认）

驱动生态：
  官方驱动：Java/.NET/Python/JS/Go 等
  社区驱动：各语言
  → 生产用 Bolt + 官方驱动
```

### 3.2 驱动使用模式

```java
// Java 驱动（官方 neo4j-java-driver）
Driver driver = GraphDatabase.driver(
    "bolt://localhost:7687",
    AuthTokens.basic("neo4j", "password"));

try (Session session = driver.session()) {
    Result result = session.run(
        "MATCH (p:Person {name: $name}) RETURN p.age",
        Map.of("name", "张三"));
    while (result.hasNext()) {
        Record record = result.next();
        System.out.println(record.get("p.age").asInt());
    }
}
driver.close();
```

```text
驱动要点：
  连接池（自动管理）
  会话模式（READ/WRITE 路由——集群）
  参数化查询（$name——防注入）
  事务 API（自动/手动）
  → 详见 07 模块（Spring Data Neo4j）
```

## 4. 事务与并发控制

### 4.1 事务特性

```text
Neo4j 事务：
  ACID（与关系型数据库同级）
  读已提交 + 快照隔离（默认）

事务 API（Java）：
  自动事务：session.run（单条自动提交）
  显式事务：session.beginTransaction()
  函数事务：session.executeWrite(tx -> {...})（推荐）

隔离级别：
  默认 READ COMMITTED + 快照
  可配置（dbms.transaction 设置）
```

### 4.2 并发控制

```text
锁机制：
  写锁：节点/关系/属性级（细粒度）
  锁等待：冲突时等待（可超时配置）

冲突处理：
  并发写同一节点 → 锁竞争（串行化）
  死锁：Neo4j 自动检测/回滚（重试）

高并发写策略：
  ① 减少热点节点（避免超级节点并发写）
  ② 事务尽量小（短事务）
  ③ 冲突重试（应用层）
  ④ 批次写入（IN TRANSACTIONS）
```

### 4.3 事务与批处理

```cypher
// 大批量写入分批事务（推荐模式）
CALL {
    MATCH (n:Node) WHERE n.status = 'PENDING'
    SET n.status = 'DONE'
    RETURN count(*) AS batch
} IN TRANSACTIONS OF 1000 ROWS;
// 每批独立事务（失败不影响已提交批次）

// 并发子查询（2026.06：DISJOINT BY 防死锁）
CALL {
    MATCH (a:Account)
    SET a.balance = a.balance * 1.01
} IN CONCURRENT TRANSACTIONS DISJOINT BY a.id;
```

## 5. 集群架构

### 5.1 集群角色

```text
Neo4j 集群（因果集群，Causal Clustering）：
  核心服务器（Core）：数据读写（RAFT 复制）
  只读副本（Read Replica）：水平扩展读

核心服务器（3-7 台）：
  写事务在核心执行（RAFT 达成一致）
  全部核心持有数据（复制）
  故障自动选举（RAFT）

只读副本：
  从核心同步数据（异步）
  承载读流量（水平扩展）
  故障无影响（读降级）

架构演进：多数据库（每个库独立集群可选）
```

### 5.2 集群配置

| 配置 | 说明 | 建议 |
|------|------|------|
| 核心服务器数 | RAFT 成员 | 3（容 1 故障）/5（容 2） |
| 只读副本数 | 读扩展 | 按读负载 |
| 发现机制 | 初始成员列表 | 固定配置 |
| 网络分区 | 核心多数派 | 少数派降级只读 |

```text
部署形态：
  单机：开发/小规模（社区版）
  集群：生产（企业版功能：集群/热备）
  AuraDB：云托管（自动集群）

注意：
  社区版无集群（单实例）
  企业版提供：集群、热备、多数据库、安全
```

### 5.3 高可用设计

```text
写可用性：
  核心多数派存活 → 可写
  少数派隔离 → 降级（不可写，可读本地）

读扩展：
  只读副本就近（地域分布）
  读一致性：因果一致性（见下）

故障转移：
  核心故障 → RAFT 选举新首领（秒级）
  副本故障 → 读流量重路由（无感）

容灾：
  备份（在线/离线）
  跨地域复制（企业版/云）
```

## 6. 因果一致性

### 6.1 为什么需要

```text
集群中的一致性挑战：
  写 → 核心（RAFT 一致）
  读 → 核心/副本（可能不同步）
  → "写后读"可能读到旧数据（副本延迟）

因果一致性（Causal Consistency）：
  保证"因果关系"的操作顺序可见：
    写 A → 读 A（同一会话必见）
    写 A → 写 B（B 依赖 A）→ 读 B 时 A 必可见

实现：书签（Bookmark）
  写事务返回书签
  后续读携带书签 → 路由到"已包含该写"的服务器
```

### 6.2 书签机制

```java
// 写后读的因果保证（书签）
BookmarkManager bookmarkManager = new BookmarkManager();

try (Session writeSession = driver.session(
        SessionConfig.forDatabase("neo4j")
            .withBookmarkManager(bookmarkManager)
            .build())) {
    writeSession.executeWrite(tx ->
        tx.run("CREATE (p:Person {name: $name})", Map.of("name", "张三")));
}

// 同一 BookmarkManager 的读会话 → 保证看到上面的写
try (Session readSession = driver.session(
        SessionConfig.forDatabase("neo4j")
            .withBookmarkManager(bookmarkManager)
            .build())) {
    readSession.executeRead(tx -> tx.run(
        "MATCH (p:Person {name: $name}) RETURN p", Map.of("name", "张三")));
}
```

### 6.3 一致性模型的选择

```text
Neo4j 的一致性选项：
  ① 因果一致性（默认，书签）——写后读保证
  ② 最终一致性（无书签）——允许短暂滞后
  ③ 强一致读（读核心）——最严格但性能受限

工程选择：
  需要"写后立刻读到自己写的"（用户会话）→ 书签
  可容忍滞后（分析/报表）→ 读副本（无书签）
  强一致场景（账务）→ 读核心（核心负担）

单机部署：无此问题（天然一致）
  集群部署：按会话/查询选择
```

> 🎯 **核心要点**：Neo4j 存储 = 原生图记录（指针链）+ 页缓存 + WAL 事务；集群 = RAFT 核心 + 只读副本 + 因果一致性（书签）。工程要点：**pagecache 是性能核心、事务要短小、批处理用 IN TRANSACTIONS、写后读用书签保证**。社区版单机 vs 企业版集群的选择在 08 模块详述。
