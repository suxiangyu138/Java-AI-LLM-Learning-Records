## 1. 索引类型

### 1.1 三类索引

| 索引 | 用途 | 语法 |
|------|------|------|
| 范围索引 | 等值/范围/排序（属性查找） | CREATE RANGE INDEX |
| 全文索引 | 文本搜索（模糊/分词） | CREATE FULLTEXT INDEX |
| 向量索引 | 相似度搜索（embedding） | CREATE VECTOR INDEX |

```cypher
-- 范围索引（默认）
CREATE INDEX person_name FOR (p:Person) ON (p.name);
CREATE RANGE INDEX person_age FOR (p:Person) ON (p.age);

-- 全文索引
CREATE FULLTEXT INDEX person_search
FOR (p:Person) ON EACH [p.name, p.bio];

-- 向量索引（Lucene HNSW 实现）
CREATE VECTOR INDEX movie_vec
FOR (m:Movie) ON (m.embedding)
OPTIONS {indexConfig: {
    `vector.dimensions`: 1024,
    `vector.similarity_function`: 'cosine'
}};
```

### 1.2 索引选择

| 查询模式 | 推荐索引 |
|---------|---------|
| 精确匹配（=） | 范围索引 |
| 范围（>/<） | 范围索引 |
| 排序（ORDER BY） | 范围索引 |
| 文本包含（CONTAINS） | 全文索引 |
| 模糊匹配 | 全文索引 |
| 向量相似度 | 向量索引 |
| 复合条件 | 复合索引（多属性） |

```text
索引生效条件：
  锚点属性必须命中索引（查询起点）
  复合索引按"最左前缀"（同关系型）
  全文索引只能用于 db.index.fulltext.queryNodes（过程/函数）

注意：Cypher 25 的 SEARCH 语法
  → 向量查询用原生语法（替代过程调用）
  → 详见 06 模块
```

### 1.3 索引的代价

```text
索引维护：
  写入时更新（写放大）
  存储占用（索引文件）

权衡：
  读多写少 → 大胆建索引
  写密集 → 克制（高吞吐写入场景）
  查询模式分析 → 只为"锚点"建索引

检查索引使用：
  EXPLAIN 计划中的 NodeIndexSeek/IndexScan
  → 未用索引 = 全表扫描（慢）
```

## 2. 约束

### 2.1 约束类型

| 约束 | 语法 | 作用 |
|------|------|------|
| 唯一 | CREATE CONSTRAINT ... IS UNIQUE | 唯一性 |
| 存在 | ... IS NOT NULL | 属性必填 |
| 属性类型 | ... IS :: TYPE | 类型检查 |
| 键 | ... IS KEY | 唯一 + 存在（复合） |
| 关系类型 | ... IS RELATIONSHIP TYPE | 关系类型限制 |

```cypher
-- 唯一约束（也创建索引）
CREATE CONSTRAINT person_name_unique
FOR (p:Person) REQUIRE p.id IS UNIQUE;

-- 属性类型约束（2025.10 原生 Vector 类型）
CREATE CONSTRAINT chunk_vec
FOR (c:Chunk) REQUIRE c.vector_embedding IS :: VECTOR<FLOAT32>(1024);

-- 复合键
CREATE CONSTRAINT person_key
FOR (p:Person) REQUIRE (p.type, p.externalId) IS KEY;
```

### 2.2 约束与数据质量

```text
约束的价值：
  ① 数据完整性（唯一/必填）
  ② 查询性能（约束自带索引）
  ③ 类型安全（属性类型约束）

工程建议：
  实体唯一标识 → 唯一约束（id/业务键）
  必填字段 → 存在约束
  Embedding 字段 → VECTOR 类型约束（2025.10+）

注意：
  约束建立前需数据清洗（违反约束的数据会失败）
  大规模数据加约束 → 先验证后启用
```

## 3. 执行计划：EXPLAIN 与 PROFILE

### 3.1 查看执行计划

```cypher
-- EXPLAIN：预估计划（不执行）
EXPLAIN MATCH (p:Person {name:'张三'})-[:FRIEND]->(f) RETURN f.name;

-- PROFILE：实际执行 + 行数/耗时
PROFILE MATCH (p:Person {name:'张三'})-[:FRIEND]->(f) RETURN f.name;
```

```text
计划中的关键操作符：
  NodeIndexSeek：索引查找（高效）✅
  NodeByLabelScan：Label 全扫描（慢）⚠️
  AllNodesScan：全节点扫描（最慢）❌
  Expand(All)：关系展开
  Filter：过滤（可下推更好）
  Sort：排序（无索引时内存排序）

判断标准：
  锚点命中索引（NodeIndexSeek）
  过滤尽早执行（下推）
  无全扫描（大图）
```

### 3.2 计划解读示例

```text
查询：MATCH (p:Person {name:'张三'})-[:FRIEND]->(f)

好计划：
  NodeIndexSeek（person_name 索引定位张三）→ Expand(All) → 返回
  → 索引锚点 + 直接遍历

差计划：
  NodeByLabelScan（扫全部 Person）→ Filter（name=张三）→ Expand
  → 全表扫描后再过滤（大图灾难）

修复：
  ① 确认 person_name 索引存在
  ② 确认查询语法与索引匹配（属性名一致）
```

### 3.3 计划调优技巧

| 技巧 | 说明 |
|------|------|
| 锚点最小化 | 起点用选择性最高的条件 |
| 尽早过滤 | WHERE 下推（计划器自动，但书写有影响） |
| 避免笛卡尔积 | 多个 MATCH 无连接条件（危险） |
| 限制返回 | LIMIT 提前（计划器支持） |
| 索引匹配 | 属性/Label 与索引定义一致 |
| 避免大范围变长路径 | 设跳数上限 |

## 4. 查询性能调优

### 4.1 常见性能问题

| 问题 | 原因 | 修复 |
|------|------|------|
| 全表扫描 | 锚点无索引 | 建索引 |
| 笛卡尔积 | 多 MATCH 无连接 | 连接条件/模式合并 |
| 大跳数爆炸 | 变长路径无上限 | 限制跳数 |
| 属性过滤慢 | 非锚点属性过滤 | 复合索引/调整锚点 |
| 排序慢 | ORDER BY 无索引 | 范围索引 |
| 大量 collect | 内存聚合 | 分批/限制 |

### 4.2 查询重写示例

```cypher
-- 差：全扫描过滤
MATCH (p:Person) WHERE p.name = '张三' AND p.age > 30

-- 好：锚点索引 + 模式过滤
MATCH (p:Person {name:'张三'}) WHERE p.age > 30
-- 或：复合索引 (name, age)

-- 差：无上限多跳
MATCH path = (a)-[:X*]->(b)

-- 好：限制跳数 + 方向
MATCH path = (a)-[:X*1..4]->(b)
```

### 4.3 批处理与分页

```cypher
-- 大批量操作分批（事务大小控制）
CALL {
    MATCH (n:Node) WHERE n.processed IS NULL
    SET n.processed = true
    RETURN count(*) AS cnt
} IN TRANSACTIONS OF 1000 ROWS;
-- 每批 1000 行（避免大事务内存问题）
```

## 5. 数据模型与性能

### 5.1 模型对性能的影响

```text
建模决策影响查询性能：
  ① 锚点设计：哪个 Label/属性做起点（索引）
  ② 关系方向：查询方向的匹配（可双向查但建模更优）
  ③ 属性冗余：需要过滤的属性是否可索引
  ④ 节点规模：高扇出节点的遍历成本

反模式（性能杀手）：
  无 Label 的节点（全扫描）
  属性在查询时才过滤（无索引）
  超级节点（百万关系，遍历爆炸）
```

### 5.2 超级节点问题

```text
超级节点：单个节点拥有海量关系（如"所有人"节点）
  遍历该节点 = 遍历其全部关系（爆炸）

对策：
  ① 避免超级节点建模（分解/时间分片）
  ② 查询时限制（跳数/方向/类型）
  ③ 属性过滤前置（减少遍历量）
  ④ 关系类型拆分（不同类型分关系）

识别：DB 统计（节点度分布）
```

### 5.3 建模与查询的迭代

```text
性能优化流程：
  ① PROFILE 定位瓶颈（全扫描/笛卡尔积/大跳数）
  ② 检查索引（锚点命中？）
  ③ 调整查询（锚点/过滤/跳数）
  ④ 调整模型（超级节点/属性冗余）
  ⑤ 复测（PROFILE 对比）

原则：查询先行（先写查询再定模型）
  → 模型为高频查询服务
```

## 6. 性能监控

### 6.1 监控指标

| 指标 | 含义 | 工具 |
|------|------|------|
| 查询延迟 | P50/P99 | 慢查询日志/APM |
| 命中率 | 页缓存命中（数据/索引） | Neo4j Browser 指标 |
| 事务冲突 | 并发写冲突率 | 指标监控 |
| 堆内存 | JVM 使用 | 监控系统 |
| 存储增长 | 数据库大小 | 容量规划 |

### 6.2 慢查询治理

```text
慢查询治理流程：
  ① 开启慢查询日志（query.log 配置）
  ② 定期分析 TOP 慢查询
  ③ EXPLAIN/PROFILE 定位
  ④ 索引/查询/模型优化
  ⑤ 复测验证

内存配置关键：
  pagecache（数据页缓存）——核心性能参数
    经验：≥ 数据库大小（热数据驻留内存）
  heap（JVM 堆）——查询执行内存
  （详见 08 模块部署配置）
```

> 🎯 **核心要点**：Neo4j 性能 = 索引（锚点命中）+ 计划（EXPLAIN 验证）+ 模型（超级节点/扇出控制）。三个高频坑：**全表扫描（无索引锚点）、笛卡尔积（多 MATCH 无连接）、大跳数爆炸（无上限路径）**。优化方法论：PROFILE 定位 → 索引/查询/模型三线修复 → 复测。内存配置的核心是 pagecache（数据驻留内存）。
