## 2. 部署与配置

### 2.1 部署方式

```text
自建部署：
  ① 传统安装（tar/包管理器）
  ② Docker（neo4j 官方镜像）
  ③ K8s（Helm chart）

Docker 快速开始：
  docker run -d --name neo4j \
    -p 7474:7474 -p 7687:7687 \
    -e NEO4J_AUTH=neo4j/password \
    -v $PWD/data:/data \
    neo4j:2025.10

云市场（2026）：
  AWS/Azure/GCP 市场一键部署
  AuraDB（官方托管）
```

### 2.2 关键配置

| 配置 | 说明 |
|------|------|
| NEO4J_AUTH | 认证（首次密码） |
| dbms.memory.pagecache.size | 页缓存（数据内存） |
| dbms.memory.heap.initial_size | JVM 堆初始 |
| dbms.memory.heap.max_size | JVM 堆上限 |
| dbms.default_listen_address | 监听地址 |
| dbms.security.auth_enabled | 认证开关 |

```yaml
# Docker 环境变量示例
NEO4J_dbms_memory_pagecache_size: 4g
NEO4J_dbms_memory_heap_initial__size: 1g
NEO4J_dbms_memory_heap_max__size: 4g
NEO4J_server_bolt_listen__address: 0.0.0.0:7687
```

## 3. 内存与性能配置

### 3.1 内存架构

```text
Neo4j 的两块内存：
  ① 页缓存（Page Cache）：数据/索引文件缓存
     → 读性能核心（热数据驻留）
     → 建议：≥ 数据库文件大小（或可用内存的 50-70%）
  ② JVM 堆（Heap）：查询执行/事务内存
     → 建议：可用内存的 25% 左右（页缓存之外）

分配示例（32GB 机器）：
  页缓存：16-20GB（数据大时）
  JVM 堆：4-8GB
  系统/其他：剩余

经验法则：
  数据 10GB、内存 32GB → 页缓存 16GB + 堆 4GB
  命中率监控调整（db.storage 指标）
```

### 3.2 性能调优清单

| 方向 | 手段 |
|------|------|
| 读性能 | 页缓存充足、索引命中、查询优化 |
| 写性能 | 批量事务、避免热点、索引适度 |
| 内存 | 页缓存优先（读多）、堆按查询复杂度 |
| 并发 | 连接池、事务短小、冲突重试 |
| 图规模 | 超级节点治理、跳数限制 |

```text
压测验证：
  读多场景：页缓存命中率 > 95%
  写场景：事务冲突率低、批处理吞吐达标
  查询：PROFILE 验证计划（03 模块）
```

## 4. 备份与监控

### 4.1 备份

| 方式 | 说明 | 适用 |
|------|------|------|
| 在线备份（dump） | neo4j-admin database dump | 定期备份 |
| 离线备份 | 停止后拷贝数据目录 | 简单 |
| 事务日志 | WAL 持续 | 增量 |
| 集群复制 | 核心复制（自动） | 高可用 |
| AuraDB | 自动备份 | 托管 |

```bash
# 在线备份（企业版/社区 dump）
neo4j-admin database dump neo4j --to-backup=/backup/neo4j.dump

# 恢复
neo4j-admin database load neo4j --from-path=/backup/
```

### 4.2 监控指标

| 指标 | 来源 | 告警 |
|------|------|------|
| 页缓存命中率 | db.storage.pageCache | <90% 关注 |
| 查询延迟 | 慢查询日志 | P99 超标 |
| 事务冲突 | 指标 | 突增告警 |
| 连接数 | 指标 | 接近上限 |
| 存储增长 | 指标 | 容量规划 |
| 集群状态 | 集群指标 | 核心健康 |

| 特性 | 版本 | 说明 |
|------|------|------|
| 原生 Vector 类型 | 2025.10 | VECTOR\<FLOAT32\>(n) |
| Cypher 25 | 2025 | SEARCH/WHEN/GQL 对齐 |

| GRAPH TYPE | 2026.06 GA | 数据模型蓝图（Schema） |
| HFQ 向量搜索 | 2026.06 预览 | 量化 + 全精度重排 |
| DISJOINT BY | 2026.06 | 并发写防死锁 |
| Community 向量 | 2025 | 社区版免费向量搜索 |
| GenAI Plugin | 2025-2026 | embed/search/generate |
| Aura Agent | 2026 | GraphRAG Agent 产品 |

### 5.2 特性解读

```text
GRAPH TYPE（2026 GA）：
  声明统一的数据模型蓝图
  SHOW CURRENT GRAPH TYPE AS GRAPH（虚拟节点/关系）
  → 图数据的"Schema 化"（数据治理）

HFQ 量化向量搜索（预览）：
  量化搜索 + 全精度重排
  → 更快查询、更低内存、更高召回
  → 预期下个版本 GA

DISJOINT BY（并发写）：
  IN CONCURRENT TRANSACTIONS 防死锁
  → 并行写入的工程化支持

趋势总结：
  AI 能力（向量/GraphRAG）成为主线
  图数据治理（GRAPH TYPE）成熟
  性能（HFQ/并发）持续优化
```

## 6. 图数据库选型

### 6.1 主流图数据库对比

| 数据库 | 架构 | 协议 | 特点 |
|--------|------|------|------|
| Neo4j | 原生图（单机/集群） | Cypher | 生态最成熟、GraphRAG 集成 |
| TigerGraph | 分布式 | GSQL/Cypher | 大规模分析 |
| JanusGraph | 分布式（外部存储） | Gremlin | 弹性存储 |
| Neptune | 云托管 | Cypher/Gremlin | AWS 生态 |
| NebulaGraph | 分布式 | nGQL | 国内活跃 |
| ArangoDB | 多模型 | AQL | 文档+图 |

### 6.2 选型框架

```text
选型四问：
  ① 规模：单机可承载（亿级内）→ Neo4j
           超大规模（十亿+）→ 分布式（TigerGraph 等）
  ② 生态：GraphRAG/AI 集成 → Neo4j（最成熟）
  ③ 云：AWS → Neptune；自建 → Neo4j
  ④ 团队：Cypher 技能 → Neo4j（资料丰富）

2026 判断：
  AI 场景（GraphRAG）→ Neo4j 事实标准
  超大规模分析 → 分布式图平台
  云托管 → AuraDB/Neptune
```

### 6.3 Neo4j vs 其他（选型要点）

```text
Neo4j 的优势：
  ① 图模型与 Cypher 成熟（20 年积累）
  ② GraphRAG 生态（向量 + GenAI + Agent）
  ③ 文档/社区最丰富
  ④ 免费社区版可用（含向量）

Neo4j 的边界：
  单机写吞吐（对比分布式）
  集群需企业版
  超大规模（十亿关系+）需评估

结论：
  90% 的图应用场景（社交/风控/知识图谱/GraphRAG）
  → Neo4j 是默认选择
  → 超大规模/特殊需求再评估分布式
```

> 🎯 **核心要点**：Neo4j 生产化 = 三形态选择（社区/企业/AuraDB）+ 内存配置（页缓存优先）+ 备份监控纪律。2025-2026 主线是 AI 化：向量搜索进社区版、SEARCH 语法、索引内过滤、GRAPH TYPE、HFQ——图数据库正在成为 GraphRAG 的标准基础设施。选型结论：**图场景默认 Neo4j**（生态/GraphRAG 成熟度无可替代），超大规模再考虑分布式平台。
