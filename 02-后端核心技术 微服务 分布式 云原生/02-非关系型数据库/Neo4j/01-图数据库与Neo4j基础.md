## 1. 图数据库是什么

### 1.1 定义

**图数据库**：以图结构（节点 + 关系）为存储与查询核心的数据库。

```text
图数据库的回答：
  关系型数据库：数据是"表"（关系靠 JOIN 推导）
  图数据库：数据是"图"（关系是存储的一等公民）

核心差异：
  关系的存储方式（显式存储 vs 查询时推导）
  关系的查询效率（直接遍历 vs 多表 JOIN）

Neo4j：最流行的原生图数据库（2007 年发布）
  属性图模型 + Cypher 查询语言 + 原生图存储
```

### 1.2 关系密集的数据

```text
什么数据"关系密集"：
  社交网络：用户-好友-关注（多跳关系）
  风控：账户-交易-设备-IP（关联图谱）
  供应链：供应商-零件-产品-订单
  知识图谱：实体-关系-实体
  权限：用户-角色-资源

特征：查询核心是"多跳关系"而非"单表过滤"
  → 图的建模与查询效率决定系统能力
```

> 🎯 核心认知：**图数据库为"关系遍历"而生**——当业务的核心操作是"A 到 B 经过哪些路径"时，图数据库的建模与性能都优于关系型（避免 N 表 JOIN 与递归查询）。

## 2. 属性图模型

### 2.1 三个基本要素

| 要素 | 说明 | 示例 |
|------|------|------|
| 节点（Node） | 实体（带 Label 与属性） | (:Person {name:'张三'}) |
| 关系（Relationship） | 有向连接（带类型与属性） | [:FRIEND_OF {since:2020}] |
| 属性（Property） | 键值对（节点/关系均可） | {age: 30} |

```text
关键概念：
  Label（标签）：节点的类型（Person/Movie）
    一个节点可有多个 Label（多类型）
  Relationship Type：关系的类型（FRIEND_OF/ACTED_IN）
    关系必须有方向（建模时定义语义）
    关系可有属性（since、weight、role）

Cypher 示例（属性图）：
  (张三)-[:FRIEND_OF {since:2020}]->(李四)
  (李四)-[:ACTED_IN {role:'主角'}]->(电影A)
```

### 2.2 图模型的表达能力

```text
关系作为一等公民的价值：
  ① 多对多关系天然表达（不需要中间表）
  ② 关系可带属性（关系的"数据"）
  ③ 多跳查询直接遍历（不需要 JOIN）
  ④ 图模式匹配（pattern matching）声明式查询

对比关系型建模：
  多对多 → 中间关联表（3 表 JOIN）
  关系属性 → 关联表加列
  → 图模型更直接、查询更简洁
```

### 2.3 建模原则

```text
建模决策（节点 vs 属性 vs 关系）：
  实体 → 节点（有独立身份/被查询）
  关联 → 关系（有方向/属性/被遍历）
  描述性数据 → 属性（不参与图遍历）

常见建模错误：
  把关系建模成节点（过度建模）
  把实体建模成属性（丢失关联能力）
  忽略关系的方向与类型语义

经验法则：
  "会参与多跳查询的关联 → 关系"
  "只是描述性的数据 → 属性"
```

## 3. 免索引邻接：原生图存储

### 3.1 什么是免索引邻接

```text
免索引邻接（Index-free Adjacency）：
  每个节点直接存储指向其邻居的指针
  遍历关系 = 跟随指针（无需全局索引查找）

对比关系型：
  JOIN 需要索引查找（O(log n) 每跳）
  图遍历 = 指针跳转（接近 O(1) 每跳）

效果：
  3 跳查询：图 ≈ 3 次指针操作
           关系型 ≈ 3 次索引 + JOIN（指数级代价）
  → 跳数越多，图数据库优势越大
```

### 3.2 性能特征

| 跳数 | 关系型（JOIN 估算） | Neo4j（遍历） |
|:---:|:---:|:---:|
| 1 | 1 次 JOIN | 1 次指针 |
| 2 | 2 次 JOIN | 2 次指针 |
| 3 | 3 次 JOIN（指数退化风险） | 3 次指针 |
| 5+ | 通常不可行 | 仍可（毫秒级） |

```text
性能结论：
  单跳查询：两者接近（关系型索引也快）
  多跳查询（3+）：图数据库数量级优势
  → "跳数"是选型的关键指标（业务是否需要多跳）

数据规模影响：
  关系型 JOIN 代价随表大小增长
  图遍历代价与"路径长度"相关（与总规模弱相关）
  → 大规模关系数据 → 图数据库更稳
```

## 4. 与关系型数据库对比

### 4.1 模型对比

| 维度 | 关系型（MySQL/PG） | 图数据库（Neo4j） |
|------|:---:|:---:|
| 数据模型 | 表/行/列 | 节点/关系/属性 |
| 关系表达 | 外键 + JOIN | 显式关系（存储） |
| 多对多 | 中间关联表 | 直接关系 |
| 关系属性 | 关联表加列 | 关系自带属性 |
| Schema | 严格（表结构） | 灵活（Label/属性） |
| 查询语言 | SQL | Cypher |
| 多跳查询 | 递归 JOIN（复杂） | 模式匹配（自然） |
| 事务 | ACID | ACID |

### 4.2 适用边界

```text
关系型更优：
  报表/聚合（GROUP BY 成熟）
  大量单表查询（索引高效）
  严格 Schema 的业务（订单/财务）
  团队 SQL 技能（生态成熟）

图数据库更优：
  多跳关系查询（社交/风控/供应链）
  关系密度高（每个实体大量关联）
  模式灵活演进（知识图谱）
  图算法需求（中心性/社区）

工程判断：
  查询模式以"单实体过滤+聚合"为主 → 关系型
  查询模式以"多跳关系遍历"为主 → 图数据库
  混合 → 互补（图库 + 关系库并存）
```

## 5. 与文档/键值数据库对比

| 维度 | 文档（MongoDB） | 键值（Redis） | 图（Neo4j） |
|------|:---:|:---:|:---:|
| 模型 | JSON 文档 | KV | 图 |
| 关系 | 嵌入/引用（弱） | 无 | 一等公民 |
| 查询 | 字段/聚合 | 按键 | 模式匹配 |
| 适用 | 灵活文档 | 高速缓存 | 关系遍历 |
| 多跳 | 需应用层 | 不支持 | 原生 |

```text
NoSQL 家族的分工：
  文档：聚合导向（订单+明细嵌入）
  键值：速度导向（缓存/会话）
  图：关系导向（连接查询）
  列族：分析导向（宽表）

选型口诀：
  实体+聚合 → 文档
  键+值 → KV
  实体+关系 → 图
```

## 6. 适用场景与边界

### 6.1 适用场景

| 场景 | 图的价值 |
|------|---------|
| 社交网络 | 好友推荐（多跳）、影响力分析 |
| 金融风控 | 关联图谱（欺诈团伙识别） |
| 供应链 | 依赖链、瓶颈分析 |
| 知识图谱 | 实体关系检索（GraphRAG 基础） |
| 权限系统 | 角色-资源继承（可达性） |
| 推荐系统 | 图路径推荐（协同过滤的图版） |
| 网络运维 | 依赖拓扑、故障影响分析 |

### 6.2 不适用场景

| 场景 | 原因 | 替代 |
|------|------|------|
| 大量聚合报表 | 图模型不适合 | 关系型/OLAP |
| 纯 KV 高速访问 | 图遍历开销 | Redis |
| 大规模全文检索 | 图不擅长 | Elasticsearch |
| 简单 CRUD | 杀鸡用牛刀 | 关系型 |

### 6.3 图数据库家族

```text
Neo4j：原生图（属性图，最流行）
TigerGraph：分布式图（大规模）
JanusGraph：分布式（HBase/Cassandra 后端）
Amazon Neptune：云托管（兼容 Cypher/Gremlin）
ArangoDB：多模型（文档+图）
NebulaGraph：分布式（国内活跃）

选型因素：
  规模（单机 vs 分布式）
  生态（Cypher vs Gremlin）
  云服务（托管 vs 自建）
  —— 详见 08 模块
```

> 🎯 **核心要点**：Neo4j = 属性图模型 + Cypher + 免索引邻接——三位一体构成"关系遍历"的极致体验。选型的核心判断：**业务查询是否需要"多跳关系遍历"**（是 → 图库；否 → 关系型即可）。图模型让"关系"成为一等公民，代价是聚合/报表能力弱于关系型——两者互补而非替代。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 图数据库解决什么？ | 多跳关系遍历（关系密集数据） |
| 属性图三要素？ | 节点、关系、属性（关系有一等公民地位） |
| 免索引邻接？ | 指针直连邻居（遍历 O(1)/跳） |
| vs 关系型？ | JOIN 推导 vs 显式存储；多跳是分水岭 |
| vs 文档/KV？ | 文档聚合/KV 速度/图关系 |
| 适用判断？ | 查询模式是"多跳遍历"就用图库 |
