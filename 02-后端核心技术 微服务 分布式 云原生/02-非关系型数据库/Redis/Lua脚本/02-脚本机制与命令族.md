## 1. EVAL：执行脚本

```bash
# 语法：EVAL script numkeys [key...] [arg...]
EVAL "return redis.call('GET', KEYS[1])" 1 user:42
#                                                  ↑ numkeys=1，接下来 1 个 key

# 无键的脚本：numkeys 传 0
EVAL "return redis.call('TIME')[1]" 0

# 多个键与参数
EVAL "redis.call('SET', KEYS[1], ARGV[1]); return redis.call('GET', KEYS[1])" 1 "stock:1001" "50"
```

| 参数 | 说明 |
|------|------|
| script | 脚本源码（每次 EVAL 都完整传输） |
| numkeys | 键的数量（声明键有几个） |
| key... | 键名（占 KEYS[1]、KEYS[2]...） |
| arg... | 值参数（占 ARGV[1]、ARGV[2]...） |

> ⚠️ **不要用 EVAL 执行同一个脚本 N 次**：脚本源码每次都全量传输 + 重新编译。生产必须走 SCRIPT LOAD + EVALSHA（见 §4）。

## 2. KEYS 与 ARGV：传参铁律

```lua
-- ✅ 正确：键通过 KEYS 传
EVAL "return redis.call('GET', KEYS[1])" 1 user:42

-- ❌ 错误：键名拼进脚本（集群模式下直接报错）
EVAL "return redis.call('GET', 'user:42')" 0
```

| 铁律 | 原因 |
|------|------|
| **键必须走 KEYS[i]** | Redis Cluster 用脚本里的 KEYS 计算槽位——拼进脚本的键无法做集群路由（`CROSSSLOT`/`MOVED` 错误） |
| 键不能写死 | 脚本缓存后换键名就废（缓存按脚本原文算 SHA1） |
| 值走 ARGV[i] | 键与值分离，可缓存脚本、只换参数 |
| 多键多槽 | 脚本内多个 KEYS 必须同槽（同哈希标签），否则集群拒绝 |

```lua
-- 集群安全写法：同槽多键（用 {tag} 哈希标签）
EVAL "redis.call('MGET', KEYS[1], KEYS[2])" 2 "user:{42}:profile" "user:{42}:orders"
```

> 🎯 面试必答：**"Redis Cluster 为什么要求脚本用 KEYS 传键？"** ——脚本执行前，集群需要把 KEYS 映射到槽位做路由；键拼死在脚本里就无法路由（且脚本缓存后也无法复用不同键）。

## 3. redis.call vs redis.pcall

```lua
-- redis.call：命令出错 → 脚本立即抛错终止（错误传播给客户端）
return redis.call('GET', KEYS[1])
-- 若 KEYS[1] 是 List：WRONGTYPE 错误，脚本终止

-- redis.pcall：命令出错 → 返回错误 table（脚本可以自己处理）
local result = redis.pcall('GET', KEYS[1])
if type(result) == 'table' and result.err then
    return { err = "key type mismatch: " .. result.err }   -- 降级处理
end
return result
```

| 函数 | 出错行为 | 适用 |
|------|---------|------|
| `redis.call()` | 抛错终止脚本 | 预期不会错 / 出错就该失败 |
| `redis.pcall()` | 返回错误表（`{err=...}`） | 需要容错分支（如探测键类型） |

```lua
-- 错误表形态（pcall 返回值）：
-- { err = "WRONGTYPE Operation against a key holding the wrong kind of value" }
-- 判断：type(result) == 'table' and result.err ~= nil
```

> 💡 典型用法：**先 pcall 探测再决定**——比如"如果是 List 就 LPOP，是 String 就 GET"的类型自适应脚本（Redis 6.2+ 更推荐 OBJECT ENCODING 判断，但 pcall 容错依然是基本功）。

## 4. 脚本缓存：SCRIPT 命令族

```bash
# ① 缓存脚本，返回 SHA1 摘要（不执行）
> SCRIPT LOAD "return redis.call('GET', KEYS[1])"
"b8059ba43af6a2d9c9e0a4f9d4f4c0b7f6e8a1d2"

# ② 检查脚本是否在缓存
> SCRIPT EXISTS b8059ba43af6a2d9c9e0a4f9d4f4c0b7f6e8a1d2
1) (integer) 1

# ③ 清空脚本缓存
> SCRIPT FLUSH

# ④ 终止正在执行的脚本
> SCRIPT KILL
```

| 命令 | 用途 |
|------|------|
| `SCRIPT LOAD` | 缓存脚本 → 返回 SHA1（不执行） |
| `SCRIPT EXISTS` | 批量检查缓存（返回 0/1 数组） |
| `SCRIPT FLUSH` | 清空缓存（**重启后缓存也没了**） |
| `SCRIPT KILL` | 终止卡住的脚本（未写数据时才能杀，见 03 §5） |

> ⚠️ **脚本缓存是"易失的"**：重启 / SCRIPT FLUSH / 故障转移后缓存清空 → EVALSHA 报 NOSCRIPT——客户端必须缓存 SHA1 并做好 NOSCRIPT 回退（见 §5、[07 Spring 集成](07-Spring-Data-Redis集成.md)）。

## 5. EVALSHA 与 NOSCRIPT 处理

```text
生产调用链：
  SCRIPT LOAD "..." → SHA1（启动时一次性）
  后续请求 → EVALSHA SHA1 1 key arg（只传摘要，不传源码）
  缓存丢失 → NOSCRIPT 错误 → 重新 SCRIPT LOAD → 重试一次
```

```java
// 客户端视角的 NOSCRIPT 处理（伪代码）
String sha = loadScript(script);          // 启动时 SCRIPT LOAD
try {
    return evalSha(sha, keys, args);      // 正常走 EVALSHA
} catch (NoscriptException e) {
    sha = loadScript(script);             // 缓存丢了 → 重新加载
    return evalSha(sha, keys, args);      // 重试一次（最多一次）
}
```

| 收益 | 说明 |
|------|------|
| 带宽 | 脚本内容不再每次传输（可省 ~95%） |
| 性能 | 避免重复编译 |
| 风险 | NOSCRIPT 必须处理（重启/FLUSH/故障转移） |

> 🎯 生产规范：**Script 走 SCRIPT LOAD + EVALSHA + NOSCRIPT 回退**；更省心的替代是直接用 Redis 7+ 的 [Function](05-Redis-Function机制.md)（持久化，天然无 NOSCRIPT 问题）。

## 6. 返回类型转换

```lua
-- Lua 类型 → Redis 返回类型的转换规则
return 42               -- integer
return "ok"             -- bulk string
return nil              -- nil（客户端得到 nil）
return false            -- 也是 nil（false 被转成 nil！）
return true             -- integer 1
return {1, 2, 3}        -- array
return {err = "msg"}    -- error reply（客户端收到错误）
return {ok = "msg"}     -- status reply
return redis.status_reply("OK")   -- 等价 {ok=...}
return redis.error_reply("custom error")  -- 等价 {err=...}
```

| 陷阱 | 说明 |
|------|------|
| **false → nil** | Lua 的 false 返回给客户端变成 nil（判空注意） |
| 空 table | `{}` 返回空数组（Redis 6.0+ 区分空数组与 nil） |
| 浮点 | Redis 返回整数；需要精度用字符串返回 |
| 错误返回 | `return redis.error_reply("msg")` 客户端得到异常 |

## 7. 与客户端交互的错误约定

```text
脚本内主动报错的两条路径：
  ① redis.call 命令出错 → 错误自动传播
  ② return redis.error_reply("业务错误信息") → 业务判定错误

客户端区分：
  · 命令错误（WRONGTYPE 等）→ 客户端异常
  · 业务错误（自定义 message）→ 客户端按业务处理（可自定义异常映射）
```

```lua
-- 业务错误约定：错误信息前缀化，客户端可解析
-- 例：限流脚本
local remaining = redis.call('DECR', KEYS[1])
if remaining < 0 then
    redis.call('INCR', KEYS[1])          -- 回滚
    return redis.error_reply("RATE_LIMIT_EXCEEDED")
end
return remaining
```

> 💡 进阶：脚本内可使用 `redis.log(redis.LOG_WARNING, ...)` 记录日志（**替代已移除的 lua print**，见 [03 §5](03-原子性与执行语义.md)）——生产脚本必须留痕，错误排查靠它。
