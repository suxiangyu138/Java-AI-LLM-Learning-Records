## 1. 脚本实战总纲

```text
四个经典场景的共同点：
  都是"检查 + 修改"两步 —— 单条命令做不到，脚本天生适合

场景矩阵：
  分布式锁   → SETNX + 过期时间 + 校验持有者（原子）
  限流      → 计数 + 过期 + 窗口判断（原子）
  扣库存    → 读库存 + 条件扣减（原子）
  防重      → 键存在性 + 写入（原子）
```

> 🎯 共同心法：**先 GET/EXISTS 判断 → 条件满足才写 → 一步脚本返回结果**——把竞态窗口压缩到零。

## 2. 分布式锁（Redisson 同款思路）

```lua
-- ═══ 加锁脚本（Redisson 实现的核心，流程同款）═══
-- KEYS[1] = lock key
-- ARGV[1] = 唯一标识（UUID:threadId，用于安全释放）
-- ARGV[2] = 过期时间（毫秒）

-- 1. 原子判断：键不存在才设置（SET NX + EX 原子）
if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then
    return 1            -- 加锁成功
end
-- 2. 可重入：同线程再次加锁（Redisson 的 hash 可重入结构简化版）
return 0                -- 加锁失败

-- ═══ 解锁脚本（校验持有者，防止误删别人的锁）═══
-- KEYS[1] = lock key，ARGV[1] = 唯一标识
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])   -- 是自己的锁才删
end
return 0                -- 不是自己的锁（已过期/被别人持有），不删
```

```java
// 使用范式（配合 try-finally）：
String token = UUID.randomUUID().toString();
Boolean locked = (Boolean) redisTemplate.execute(
        lockScript, List.of(lockKey), token, "30000");
try {
    if (Boolean.TRUE.equals(locked)) {
        // ... 临界区业务
    }
} finally {
    redisTemplate.execute(unlockScript, List.of(lockKey), token);
}
```

| 设计要点 | 说明 |
|---------|------|
| **SET NX PX 原子** | 设值与过期时间一条命令（防"设值后宕机 → 永久锁"） |
| **唯一标识校验** | 解锁前比对持有者（防"A 的锁被 B 误删"） |
| 可重入 | 同线程多次加锁需计数（生产直接用 Redisson 现成实现，见 [Redis 主体系](../../Redis/08-Spring%20Boot集成Redis与Lua.md) 相关章节） |
| 看门狗续期 | Redisson 自动续期（防业务超时锁过期）——脚本只提供原子原语 |

> 🎯 面试必考：**"为什么 Redis 分布式锁要 Lua 脚本？"** ——`SET NX PX` 解决加锁原子，但**解锁的"先判断后删除"必须脚本**（GET+DEL 两步非原子会误删新锁）。两个脚本 = 加锁原子 + 解锁原子，分布式锁才成立。

## 3. 限流：固定窗口

```lua
-- ═══ 固定窗口限流 ═══
-- KEYS[1] = 限流键（如 rate:user:42:20260808-18:00）
-- ARGV[1] = 窗口内最大次数
-- ARGV[2] = 窗口时长（秒）

local key = KEYS[1]
local limit = tonumber(ARGV[1])

local current = tonumber(redis.call('GET', key) or '0')
if current >= limit then
    return 0                    -- 拒绝（窗口内已满）
end
redis.call('INCR', key)
redis.call('EXPIRE', key, ARGV[2])   -- 每次刷新过期 = 固定窗口
return limit - current          -- 返回剩余额度
```

| 特点 | 说明 |
|------|------|
| 优点 | 实现极简（1 个键） |
| 缺点 | **窗口边界突刺**（窗口末与下窗口初可双倍放行） |
| 适用 | 简单防刷（IP/用户维度），对突刺不敏感 |
| 窗口键 | 用时间戳取整生成窗口键（`now - now % window`） |

## 4. 限流：滑动窗口

```lua
-- ═══ 滑动窗口限流（ZSET 实现：窗口内请求时间戳集合）═══
-- KEYS[1] = zset 键
-- ARGV[1] = 窗口长度（毫秒）
-- ARGV[2] = 窗口内最大次数

local now = redis.call('TIME')[1] * 1000   -- 服务器时间（毫秒）
local windowStart = now - tonumber(ARGV[1])

-- 1. 移除窗口外旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, windowStart)

-- 2. 统计窗口内请求数
local count = redis.call('ZCARD', KEYS[1])
if count >= tonumber(ARGV[2]) then
    return 0                     -- 拒绝
end

-- 3. 记录本次请求（时间戳为 score）
redis.call('ZADD', KEYS[1], now, now .. ":" .. ARGV[3])   -- member 需唯一
redis.call('PEXPIRE', KEYS[1], ARGV[1])                    -- 滑动过期

return tonumber(ARGV[2]) - count   -- 剩余额度
```

| 特点 | 说明 |
|------|------|
| 优点 | 精确（任意时刻窗口内都严格 ≤ 上限，无突刺） |
| 代价 | ZSET 内存（每请求一条记录，需定期清理） |
| member 唯一 | `时间戳:随机数`（同毫秒多条不覆盖） |
| 适用 | 对突刺敏感的业务限流（支付/短信等） |

> 💡 面试对比：**固定窗口 vs 滑动窗口**——固定窗口简单但有边界双倍放行；滑动窗口精确但 ZSET 内存成本高。生产常见组合：滑动窗口用于敏感操作（短信/支付），固定窗口用于常规防刷。

## 5. 限流：令牌桶

```lua
-- ═══ 令牌桶限流（HASH 存桶状态）═══
-- KEYS[1] = bucket key
-- ARGV[1] = 桶容量
-- ARGV[2] = 每秒补充速率
-- ARGV[3] = 当前时间戳（毫秒）

local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- 1. 读取桶状态（不存在则初始化满桶）
local tokens, lastRefill
local bucket = redis.call('HMGET', KEYS[1], 'tokens', 'lastRefill')
if bucket[1] == false then
    tokens, lastRefill = capacity, now
else
    tokens, lastRefill = tonumber(bucket[1]), tonumber(bucket[2])
end

-- 2. 按流逝时间补充令牌
local elapsed = (now - lastRefill) / 1000
tokens = math.min(capacity, tokens + elapsed * rate)

-- 3. 判断是否放行
if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', KEYS[1], 'tokens', tokens, 'lastRefill', now)
    return 1                    -- 放行
end
-- 不足：仍然更新时间戳（避免空转不补）
redis.call('HSET', KEYS[1], 'lastRefill', now)
return 0                        -- 拒绝
```

| 特点 | 说明 |
|------|------|
| 优点 | **允许突发**（满桶可一次性爆发 capacity 个请求）——最贴近真实流量模型 |
| 状态 | 每桶 2 字段（tokens + lastRefill） |
| 补充 | 惰性计算（按时间差补，无需定时任务） |
| 适用 | 平滑突发流量的接口限流 |

> 🎯 三种限流选型：**固定窗口（简单防刷）/ 滑动窗口（精确严格）/ 令牌桶（允许突发）**——面试答出"为什么令牌桶允许突发"即理解核心。完整限流理论见 [Sentinel 体系](../../../06-Spring全家桶/Spring组件汇总/Spring%20Cloud%20微服务全家桶（分布式）/Spring%20Cloud%20Alibaba（阿里实现，属于%20Spring%20Cloud%20生态实现）/Sentinel：流量控制熔断降级/00-Sentinel知识体系总览.md)。

## 6. 扣库存：秒杀场景

```lua
-- ═══ 秒杀扣库存（条件扣减 + 防超卖 + 限购）═══
-- KEYS[1] = 库存键（stock:1001）
-- KEYS[2] = 已购用户集合（buyers:1001）
-- ARGV[1] = 用户 ID
-- ARGV[2] = 购买数量

-- 1. 限购：每人最多 1 件
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2                   -- 已购买过
end

-- 2. 库存检查
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock < tonumber(ARGV[2]) then
    return -1                   -- 库存不足
end

-- 3. 扣减 + 记录（原子，超卖不可能发生）
redis.call('DECRBY', KEYS[1], ARGV[2])
redis.call('SADD', KEYS[2], ARGV[1])
return 1                        -- 成功
```

| 场景 | 要点 |
|------|------|
| 防超卖 | 条件扣减在脚本内原子完成（无并发窗口） |
| 防重复购买 | SET 集合天然去重（SADD 返回 0 即已买过） |
| 返回值约定 | 1 成功 / -1 无货 / -2 重复 |
| 兜底 | 库存预热（Redis 存库存）+ 最终 DB 落库 |

> ⚠️ 脚本无回滚（[03 §4](03-原子性与执行语义.md)）：扣库存脚本内部必须**先全量校验再执行写操作**——上面脚本的顺序（先检查用户/库存，最后 DECRBY+SADD）保证出错时无副作用。

## 7. 防重与幂等

```lua
-- ═══ 幂等键防重（SET NX 原子占位 + 状态流转）═══
-- KEYS[1] = 幂等键（idem:order:20260808-001）
-- ARGV[1] = 过期时间（秒）
-- ARGV[2] = 初始状态

-- 1. 尝试占位（首次请求成功，重复请求失败）
local result = redis.call('SET', KEYS[1], ARGV[2], 'NX', 'EX', ARGV[1])
if not result then
    return 0                    -- 重复请求（已有处理中/已处理）
end
return 1                        -- 首次请求（客户端继续执行业务）

-- ═══ 状态流转升级版（防止"处理中"被当"已完成"）═══
-- 状态机：PROCESSING → SUCCESS / FAILED
if redis.call('SET', KEYS[1], 'PROCESSING', 'NX', 'EX', ARGV[1]) then
    return 1                    -- 首次
end
local state = redis.call('GET', KEYS[1])
if state == 'SUCCESS' then
    return 2                    -- 已完成（幂等返回结果）
end
return 0                        -- 处理中（重试稍后）
```

| 设计 | 说明 |
|------|------|
| SET NX EX 原子 | 占位与过期一条命令（防占位后宕机死键） |
| 状态机 | 区分"处理中/成功"（比纯占位更健壮） |
| 过期兜底 | 幂等键过期后允许重试（业务窗口内有效） |
| 与业务联动 | 业务完成后需把状态置为 SUCCESS（另一脚本） |
