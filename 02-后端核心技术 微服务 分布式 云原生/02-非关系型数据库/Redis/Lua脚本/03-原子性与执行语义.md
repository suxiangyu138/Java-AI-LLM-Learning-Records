## 1. 原子性：单线程的承诺

```text
Redis 是单线程执行模型（命令处理线程）：
  所有命令（含脚本）在同一个事件循环里排队执行

  EVAL 脚本执行期间：
  ┌────────────────────────────────────────────┐
  │ 脚本开始 ──→ 脚本内所有 redis.call 依次执行 ──→ 脚本结束 │
  │             （期间其他任何命令排队等待）              │
  └────────────────────────────────────────────┘
  从其他客户端视角：脚本要么没发生，要么全部发生——原子
```

| 原子性保证 | 说明 |
|-----------|------|
| 隔离性 | 脚本执行期间其他命令不插入 |
| 一致性 | 要么全部命令执行，要么一个不执行（出错即中止） |
| 持久性 | 脚本内所有写操作随 RDB/AOF 持久化 |
| 并发安全 | 无需加锁（单线程天然串行） |

> 🎯 面试金句：**"Redis 脚本的原子性来自单线程执行模型——脚本一旦开始执行，其他客户端的所有命令都进队列等待，直到脚本返回"**。这正是分布式锁/限流/防重的理论基础。

## 2. 脚本 vs 事务 MULTI/EXEC

| 维度 | MULTI/EXEC 事务 | Lua 脚本 |
|------|:---:|:---:|
| 执行方式 | 命令排队后**批量执行**（无逻辑） | 脚本内**可编程**（if/循环） |
| 原子性 | ✅ 整体执行 | ✅ 整体执行 |
| 条件逻辑 | ❌ 不支持（排队时无法判断） | ✅ 完整语言能力 |
| 错误处理 | 执行期错误继续执行（2.6.5+） | 出错即终止 |
| 回滚 | ❌ 不支持 | ❌ 不支持（见 §4） |
| WATCH | 需要配合 WATCH 做乐观锁 | **天然免锁**（无竞态） |
| 典型场景 | 简单批量 | 复杂多步逻辑 |

```text
核心差异一句话：
  MULTI/EXEC = "把这堆命令原子地执行"
  Lua 脚本   = "这段逻辑（可判断可循环）原子地执行"
  脚本是事务的超集——事务做不了的判断/循环，脚本都能做
```

> 🎯 结论：**能写进脚本的复杂逻辑就别用 MULTI**——WATCH + 重试的乐观锁心智负担远大于直接脚本。但注意：**脚本内不能使用 WATCH/MULTI/EXEC**（命令受限）。

## 3. 执行期间的副作用

```text
副作用清单（脚本运行期间）：
  · 所有其他客户端命令阻塞等待（含读命令！）
  · 持久化（RDB 快照/AOF 写入）不受影响（后台线程）
  · 过期键删除、复制等后台任务不受影响（后台线程）
  · 慢日志：脚本总耗时计入（SLOWLOG 可查）
```

| 影响面 | 结论 |
|--------|------|
| 其他请求 | **全部排队**（最长 = 脚本执行时间） |
| 集群其他节点 | 不受影响（每节点独立） |
| 从节点 | 复制脚本命令/效果（见 §8） |
| 风险 | **慢脚本 = 全局停顿**（业务雪崩起点） |

> ⚠️ 生产铁律：**脚本执行时间必须毫秒级**。一个 1 秒的脚本 = 整个 Redis 停 1 秒 = 所有依赖它的请求超时。性能红线见 [08-性能调试与生产实践](08-性能调试与生产实践.md)。

## 4. 错误与回滚：脚本没有回滚

```lua
-- 脚本内命令出错（redis.call 抛错）→ 脚本立即终止
-- 已执行的命令【不会回滚】！
local a = redis.call('SET', KEYS[1], 'x')   -- ① 已执行
local b = redis.call('LPOP', KEYS[2])       -- ② 报错（WRONGTYPE）
-- 脚本终止：① 的 SET 已生效，不撤销！

-- 事务同样无回滚（对比关系型数据库的 ACID 回滚）
```

| 机制 | 回滚 |
|------|:---:|
| 关系型事务（MySQL） | ✅ 支持 |
| Redis MULTI/EXEC | ❌ 不回滚 |
| Redis Lua 脚本 | ❌ 不回滚 |

> ⚠️ **脚本无回滚是最大的语义坑**：业务上需要"要么全成功要么全失败"时，必须**脚本内手动补偿**（先检查再操作 / 出错前已做的操作自己撤销，如 §7 限流的 DECR 后 INCR 回滚）。依赖"出错自动回滚"是错误认知。

## 5. 沙箱与限制

```text
Lua 沙箱边界（脚本内可用什么）：
  ✅ 可用：redis（call/pcall/log）、cjson、cmsgpack、string、table、math
  ❌ 不可用：io（文件）、os（系统）、socket（网络）、package（加载 C 库）、debug
  ❌ 全局变量/函数（7.0+ 起禁止）
```

| 限制 | 说明 |
|------|------|
| 无网络 | 脚本不能发起 HTTP/外部请求（安全设计） |
| 无文件 | 不能读写文件系统 |
| 无 C 库 | 不能加载外部模块（package 受限） |
| 内存 | 脚本执行有内存限制（防 OOM 绕过） |
| 时间 | `lua-time-limit` 默认 5 秒（见 §7） |

> 🎯 理解沙箱的价值：**脚本只能"操作 Redis 数据"**——不能作为后门执行系统命令，这是 Redis 脚本能开放给业务线的安全前提。

## 6. 2026 沙箱加固：Redis 7.0+ 的变化

Redis 7.0（Valkey 8.0 同步）对 Lua 沙箱做了**安全加固**，影响所有 EVAL 与 Function：

| 变化 | 说明 | 影响 |
|------|------|------|
| **禁止全局函数/变量** | 沙箱使用只读表保护（CVE 修复）——`local` 是强制要求 | 老脚本直接报 `Attempt to modify a readonly table` |
| **lua print 移除** | 不再可用 | 用 `redis.log(redis.LOG_NOTICE, ...)` 替代 |
| **EVAL 脚本 LRU 淘汰** | 500 条 LRU 缓存只淘汰 **EVAL 生成的脚本**（SCRIPT LOAD 的不淘汰） | 事务中 EVALSHA 超过 500 脚本会 NOSCRIPT |
| **Lua 内存限制** | 执行期间强制内存上限 | 防"脚本绕过 maxmemory 写爆内存" |

```lua
-- 老脚本（7.0 前写法 → 报错）：
function myFunc() return 1 end        -- 全局函数 ❌
-- 新写法（强制）：
local function myFunc() return 1 end  -- 局部函数 ✅

-- print 替代：
print("debug")                        -- ❌ 已移除
redis.log(redis.LOG_DEBUG, "debug")   -- ✅ 正确姿势
```

> ⚠️ 迁移提示：**存量脚本上 Redis 7.0+ 前必须自查**——① 全部 local 化；② print 改 redis.log；③ 确认不在 EVAL 里塞超量脚本（500 LRU 上限）。

## 7. 执行超时与 SCRIPT KILL

```text
超时机制：
  · lua-time-limit 默认 5000ms（5 秒）
  · 超时后脚本【不会立即停止】——Redis 继续执行，但：
      ├─ 其他客户端收到 BUSY 错误（"script is running"）
      └─ 管理员可干预：SCRIPT KILL / SHUTDOWN NOSAVE
```

| 场景 | 手段 | 能否成功 |
|------|------|:---:|
| 脚本超时但**未写数据** | `SCRIPT KILL` | ✅ 终止 |
| 脚本超时且**已写数据** | SCRIPT KILL | ❌ 拒绝（防不一致） |
| 已写数据的卡死脚本 | `SHUTDOWN NOSAVE` | ✅ 重启解决（丢数据） |

```bash
# 处理流程（慢脚本故障实战）
> EVAL "while true do end" 0        # 死循环脚本
(error) ... busy script              # 其他客户端开始报 BUSY
> SCRIPT KILL                        # 未写数据 → 成功终止
```

> 🎯 面试加分：**"超时后 Redis 不是自动杀掉脚本，而是继续跑 + 报 BUSY，等管理员 SCRIPT KILL（未写数据时）或 SHUTDOWN NOSAVE（已写数据时）"**——这解释了为什么慢脚本是生产事故。

## 8. 复制与确定性

```text
脚本在从库的执行方式（Redis 5.0 起：effects replication）：
  主库执行脚本 → 记录【写命令的效果】→ 把效果（SET/DEL 等结果）发给从库
  从库执行同样的写命令（不重新执行脚本）

为什么：
  · 脚本里若有随机/时间相关操作（TIME、SRANDMEMBER、随机数）
  · 从库重放脚本会得到不同结果 → 主从数据不一致
  · effects replication 让从库与主库逐命令一致
```

| 要点 | 说明 |
|------|------|
| 复制模式 | Redis 5.0+：传播**写效果**而非脚本本身 |
| 随机命令 | TIME/SRANDMEMBER/RANDOMKEY 可用（效果一致即可） |
| 只读脚本 | 无写操作 → 从库可本地执行（`EVAL_RO`/`FCALL_RO`） |
| 集群 | 脚本多键必须同槽（见 [02 §2](02-脚本机制与命令族.md)） |
| 从库读 | 只读脚本可在从库执行（读写分离友好） |

> 💡 `EVAL_RO`/`EVALSHA_RO`（7.0+）：只读脚本专用入口——只含读命令的脚本用 RO 变体，可放心在从库/副本执行，主库也不做写复制开销。Function 对应 `FCALL_RO`（[05](05-Redis-Function机制.md)）。
