## 1. 性能：脚本为什么快，快在哪

```text
对比两种实现（原子扣库存）：
  无脚本：GET → 判断 → DECRBY（客户端三连）
    · 3 次网络往返（每次 ~0.1ms 本地 / 更高跨机房）
    · 3 步之间不原子（并发漏洞）

  有脚本：EVALSHA 1 次
    · 1 次网络往返（省 ~2/3 延迟）
    · 全程服务器内执行（无中间通信开销）
    · 原子（无竞态）
```

| 性能维度 | 无脚本 | 有脚本 |
|---------|:---:|:---:|
| 网络往返 | N 次 | **1 次** |
| 原子性 | 无 | ✅ |
| 服务器 CPU | 相同命令数 | 相同 + 解释执行开销（微秒级） |
| 适用 | 简单单命令 | 多步/逻辑 |

> 🎯 结论：**脚本的收益来自"往返次数"与"原子性"，不是"执行更快"**——脚本内命令还是要逐个执行（单线程），多出的 Lua 解释开销微秒级可忽略。面试答"脚本快"要答对原因。

## 2. 性能红线与优化手段

```text
红线：脚本执行时间毫秒级（lua-time-limit 默认 5s 是保命线，不是目标线）
目标：P99 脚本 < 5ms；一旦脚本耗时超过 10ms 就要优化
```

| 优化手段 | 说明 |
|---------|------|
| **KEYS 参数最小化** | 每次调用传必要的键（别一次遍历全量数据） |
| 避免遍历大集合 | `LRANGE 0 -1` 大列表 / HGETALL 大哈希——脚本内遍历 = 阻塞 |
| 用 ZSET 裁剪代替全量 | 滑动窗口先 ZREMRANGEBYSCORE 再统计（[06 §4](06-经典脚本实战.md)） |
| HASH 批量读写 | HMSET/HMGET 代替多次 HSET/GET |
| 减少命令数 | 能一条搞定的别拆三条（命令数 = 执行时间） |
| 警惕随机数/时间 | TIME 等命令开销高于常量（且影响确定性） |
| 监控 | SLOWLOG + 脚本耗时埋点（`redis.log` 打印耗时） |

```lua
-- ❌ 反例：脚本内全量遍历（100 万成员的集合 → 全局阻塞）
local all = redis.call('SMEMBERS', KEYS[1])       -- 大数据集全量拉取！
for _, m in ipairs(all) do ... end

-- ✅ 正例：增量处理 + 边界控制
local cursor = '0'
repeat
    local result = redis.call('SSCAN', KEYS[1], cursor, 'COUNT', 100)
    cursor = result[1]
    -- 每批 100 处理（单次执行有限量）
until cursor == '0'
```

> ⚠️ **大数据集操作是脚本性能头号杀手**：SMEMBERS/LRANGE 0 -1/HKEYS 全量在脚本里等于"Redis 停 N 毫秒"。必须 SCAN/增量/裁剪。

## 3. 调试三板斧

### 3.1 板斧一：redis-cli 直接验证

```bash
# 用 redis-cli 独立验证脚本逻辑（脱离应用，最快定位）
redis-cli EVAL "local n = tonumber(ARGV[1]); return n * 2" 0 21
(integer) 42

# 加载测试（检查语法错误）
redis-cli SCRIPT LOAD "local function x() return 1 end; return x()"
"<sha1>"        # 语法错误会直接报错

# 真实键测试（先造数据再跑脚本）
redis-cli SET stock:1001 10
redis-cli EVAL "return redis.call('DECRBY', KEYS[1], ARGV[1])" 1 stock:1001 3
(integer) 7
```

### 3.2 板斧二：SCRIPT DEBUG + --ldb（交互式调试器）

```bash
# 开启调试模式后，用 --ldb 进入交互式 Lua 调试器
redis-cli --ldb --eval script.lua key1 key2 , arg1 arg2
# 调试器内可用命令：s(step) n(next) c(continue) b(break) p(print) w(watch) l(list)

# 或按需开启/关闭（生产慎用：SYNC 模式会阻塞）
redis-cli SCRIPT DEBUG YES   # 开启（异步模式，生产会拖慢）
redis-cli SCRIPT DEBUG NO    # 关闭（生产必须关！）
```

> ⚠️ 生产铁律：**SCRIPT DEBUG 必须关闭**（调试模式有性能与安全影响）；调试只在本机/预发环境开。

### 3.3 板斧三：redis.log 留痕

```lua
-- 脚本内打日志（替代已移除的 print，见 03 §6）
redis.log(redis.LOG_DEBUG, "rate_limit key=" .. KEYS[1] .. " current=" .. current)
redis.log(redis.LOG_WARNING, "rate limit exceeded: " .. KEYS[1])
-- 日志出现在 Redis 日志文件（按 loglevel 过滤）
```

| 日志级别 | 用途 |
|---------|------|
| LOG_DEBUG | 开发期详细追踪（生产关） |
| LOG_VERBOSE | 一般调试 |
| LOG_NOTICE | 业务关键节点 |
| LOG_WARNING | 异常/拒绝分支（生产必留） |

> 🎯 综合调试流程：**① redis-cli 独立验证逻辑 → ② 造数据跑真实键 → ③ 加 redis.log 观察分支 → ④ 必要时 --ldb 单步**——90% 的脚本 bug 在第一步就能暴露。

## 4. 慢脚本治理

| 发现手段 | 说明 |
|---------|------|
| SLOWLOG | `SLOWLOG GET` 查慢命令（脚本记录总耗时） |
| MONITOR | 观察脚本调用频率与键（生产慎开） |
| 应用埋点 | 脚本调用耗时打点（分钟级 P99 监控） |
| BUSY 错误 | 已经超时卡住了（事故，见 [03 §7](03-原子性与执行语义.md)） |

```bash
# 慢脚本定位
> SLOWLOG GET 10
1) 1) (integer) 101           # 日志 ID
   2) (integer) 1782350000    # 时间戳
   3) (integer) 1200000       # 耗时（微秒）= 1.2 秒！严重
   4) 1) "evalsha"            # 命令
      2) "b8f1..."            # 脚本 sha1
```

| 治理动作 | 说明 |
|---------|------|
| 定位慢脚本 | SLOWLOG → 拿 sha1 → 对照脚本代码 |
| 优化逻辑 | 减命令数/避免全量遍历（§2） |
| 分片 | 大集合按业务键拆分（避免单脚本扫全量） |
| 兜底 | 设置合理 `lua-time-limit`（保命线别乱调大） |
| 熔断 | 调用侧超时 + 降级（别让慢脚本拖垮调用链） |

> 🎯 治本思维：**慢脚本 = 设计问题**（遍历/全量/过度集中）——优化脚本本身，而不是调大超时。

## 5. 12 大避坑清单

| # | 坑 | 现象 | 解法 |
|:---:|----|------|------|
| 1 | 键名拼进脚本（不走 KEYS） | 集群 CROSSSLOT/无法路由 | 键全部走 KEYS[i]（[02 §2](02-脚本机制与命令族.md)） |
| 2 | 全局变量/函数 | 7.0+ 报 readonly table | 全部 local（[03 §6](03-原子性与执行语义.md)） |
| 3 | 用 print 调试 | 报错/无输出 | redis.log（[03 §6](03-原子性与执行语义.md)） |
| 4 | 脚本内全量遍历 | 全局阻塞秒级 | SCAN/增量/裁剪（§2） |
| 5 | 以为出错会回滚 | 部分命令已生效 | 先校验后写 + 手动补偿（[03 §4](03-原子性与执行语义.md)） |
| 6 | 不设 ResultType | 反序列化异常 | ResultType 对齐返回值（[07 §2](07-Spring-Data-Redis集成.md)） |
| 7 | JDK 序列化传参数 | Lua tonumber 拿 nil | StringRedisTemplate + 字符串参数（[07 §4](07-Spring-Data-Redis集成.md)） |
| 8 | 事务内 EVALSHA 遇 NOSCRIPT | 事务整体失败 | 启动预热脚本（[07 §5](07-Spring-Data-Redis集成.md)） |
| 9 | 解锁不校验持有者 | 误删他人锁 | GET 比对唯一标识再 DEL（[06 §2](06-经典脚本实战.md)） |
| 10 | 新代码还用 EVAL | 生产维护成本高 | 新代码用 Function（[05](05-Redis-Function机制.md)） |
| 11 | 临时脚本注册 Function | 永久持久化+复制 | 临时用 EVAL（[05 §8](05-Redis-Function机制.md)） |
| 12 | 生产开 SCRIPT DEBUG | 性能拖慢 | 生产必须 DEBUG NO（§3） |

## 6. 高频面试题

### Q1：为什么 Redis 脚本是原子的？
> Redis 单线程执行模型：脚本一旦开始执行，其他客户端命令全部排队等待，脚本内所有操作要么全部执行要么一个不执行（出错即止）。原子性来自单线程，不是加锁。

### Q2：Lua 脚本和 MULTI/EXEC 事务的区别？
> 事务只保证命令排队后整体执行，**没有逻辑能力**（不能判断/循环），且需要 WATCH 乐观锁配合；脚本有完整编程能力（if/循环/函数/cjson），天然无竞态。脚本是事务的超集——复杂逻辑用脚本。

### Q3：脚本出错会回滚吗？
> **不会**。脚本内已执行的命令不回滚（Redis 事务也一样）。业务需要"全成功或全失败"时，脚本内部先校验后写、出错手动补偿。这与关系型数据库的 ACID 回滚是本质区别。

### Q4：Redis Cluster 为什么要求脚本用 KEYS 传键？
> 集群按键计算槽位路由；脚本里的键通过 KEYS 参数声明，集群才能把脚本路由到正确节点并校验多键同槽。键拼死在脚本里无法路由（CROSSSLOT 错误），且脚本缓存后无法复用。

### Q5：NOSCRIPT 错误怎么来的？怎么处理？
> EVALSHA 依赖脚本缓存，缓存是易失的（重启/SCRIPT FLUSH/故障转移清空）→ EVALSHA 报 NOSCRIPT。处理：客户端捕获 NOSCRIPT 后重新 SCRIPT LOAD 再重试一次（Spring Data Redis 已内置）。Function 方案天然免疫（持久化）。

### Q6：Redis 7.0 的沙箱加固改了什么？
> ① 禁止全局函数/变量（只读表保护，CVE 修复）——全部 local；② lua print 移除——用 redis.log；③ EVAL 脚本 500 条 LRU 缓存只淘汰 EVAL 生成的（SCRIPT LOAD 不淘汰）；④ Lua 执行内存限制。老脚本上 7.0+ 必须自查。

### Q7：Function 和 EVAL 怎么选（2026）？
> 官方建议：新生产代码用 Function（Redis 7.0+）——命名库、RDB 持久化、自动复制、版本化热更新（FUNCTION LOAD REPLACE 免发版）；EVAL 保留给一次性/调试/老版本环境。核心差异：脚本是"客户端递给服务器的代码"，Function 是"服务器管理的软件组件"。

### Q8：分布式锁为什么要脚本？
> 加锁：SET NX PX 本身原子（一条命令）；**解锁必须脚本**——"先判断持有者再删除"是两步，非原子会误删新锁（A 的锁过期后 B 加锁，A 的 DEL 把 B 的锁删了）。脚本把判断+删除合成原子操作。同理 Redisson 的可重入、看门狗续期都基于脚本。

### Q9：固定窗口、滑动窗口、令牌桶限流怎么选？
> 固定窗口：简单防刷，边界有双倍放行突刺；滑动窗口（ZSET）：精确无突刺，内存成本高（敏感操作）；令牌桶（HASH 惰性补充）：允许突发，最贴近真实流量模型。三者都用脚本实现"判断+计数+过期"的原子性。

### Q10：脚本慢怎么排查？
> SLOWLOG 拿耗时与 sha1 → 对照脚本 → 常见根因：全量遍历大集合（SMEMBERS/LRANGE 0 -1）、命令过多、大数据 HGETALL。优化：SCAN/增量/裁剪、HASH 批量、减命令数。红线：脚本毫秒级，慢脚本=设计问题。卡死场景：未写数据 SCRIPT KILL，已写数据 SHUTDOWN NOSAVE。
