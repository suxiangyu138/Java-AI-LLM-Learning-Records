## 1. 连接为什么会死

**"连上就能一直用"是错觉**——连接死亡的原因五花八门：**网络切换**（WiFi → 蜂窝，TCP 断）、**空闲超时**（服务端/中间代理回收"静默连接"——Nginx 的 proxy_read_timeout 默认 60s，客户端 60s 没说话就被断开）、**服务器重启/发布**（连接全部断）、**移动网络 NAT 表过期**（运营商 5-30 分钟回收空闲映射）。**关键认知**：**"连接死"往往双方都不知道**——TCP 断连要等超时才被发现——**心跳就是"主动探测：你还活着吗"**，重连就是"死了就再连"——"**没有心跳的 WS 连接，是双方都不知道它已死的僵尸连接**"。

## 2. 心跳机制：协议级与应用级

**协议级心跳（PING/PONG 帧）**：RFC 6455 的 0x9/0xA 帧——**服务端发 PING，客户端必须回 PONG**（浏览器自动应答，无需业务代码）——Spring 的 `WebSocketHandler` 支持 setSendTimeLimit/setIdleTimeout，STOMP 配置 `heartbeatIncoming/Outgoing`（03/02 篇）——"**协议级心跳是保活的标准件**"。

**应用级心跳（业务 ping/pong 消息）**：`{type:"ping"}`/`{type:"pong"}` 业务消息（02 篇封装）——**能探测"协议活着但业务死了"**（如连接在但消息队列堵了）。**双层心跳的实践**：**协议级保活（服务端配置）+ 应用级探测（前端定时器）**——前端"发 ping 后 2 个周期没收到 pong → 判定死连接 → 主动 close → 触发重连"（02 篇封装代码）。

## 3. 服务端超时管理

**服务端是心跳的管理者**（客户端浏览器会自动回 PONG，服务端负责"多久没消息就断开"）：

```java
// Spring 原生 Handler：空闲超时
registry.addHandler(handler, "/ws").setIdleTimeout(60_000);   // 60s 无消息断开
// STOMP 配置心跳
registry.enableSimpleBroker("/topic", "/queue")
        .setHeartbeatValue(new long[]{10000, 10000});         // 服务端 10s 发心跳
```

**服务端超时策略**：**空闲超时要比"心跳周期 × 2-3"大**（如心跳 10s、超时 30-60s）——**太短误杀正常连接，太长留僵尸连接**；**心跳与业务消息的关系**：任何消息（不只 PING）都算"活跃"——"**有来有往就不算死**"；**僵尸连接的代价**：占内存 + 占线程/文件描述符——**服务端定时扫描 + 超时断开是容量管理的底线**（08 篇）。

## 4. 断线重连策略

**重连不是"断了就重连"三个字，是策略**：

**指数退避（exponential backoff）**——延迟 1s → 2s → 4s → 8s…封顶（如 30s）——"**第一次断线 1s 重连、第十次断线 30s 重连**"；**加抖动（jitter）**——每次延迟加 ±20% 随机量——**防止"所有客户端同时退避到同一时刻，服务端恢复瞬间被重连风暴打崩"**（08 篇重连风暴）。**重连上限**——连续失败 N 次（如 5-10 次）停止自动重连，提示用户手动刷新——"**无限重连 = 无限请求 + 用户看到永远转圈**"。**在线/离线状态提示**——状态进 UI（"连接中/已断开，正在重连…"），**别让用户面对无声的失败**。

## 5. 重连后的状态恢复

**重连成功 ≠ 一切恢复**——客户端要"重新进入状态"：

**订阅恢复**：STOMP 客户端重连后**订阅全部失效，要重新 subscribe**（@stomp/stompjs 的 onConnect 里重订阅）；**会话状态恢复**：重新发送"我上线了"（用户 ID）、**拉取错过的消息**（离线期间的消息：前端记录 lastMessageId，重连后向服务端要增量）——"**重连只是恢复了管道，业务状态要自己补齐**"；**服务端侧**：握手鉴权（07 篇）在每次重连都会重走——**token 过期会导致重连失败**——"**重连失败查 token：令牌续期 + 重连要一起设计**"（Token 体系交叉：`../Token/00-Token总览.md`）。

## 6. 消息可靠性：序号与去重

**WebSocket 没有内置"消息确认与重放"**（TCP 保证传输顺序但不保证应用层语义）——**消息可靠性要应用自己设计**：

**服务端**：消息带**单调递增序号**（`seq`），客户端记录已处理的最大序号；**客户端**：重连后**从最后确认的序号继续**——**"去重 + 补拉"是消息可靠性的两个动作**——去重（重复收到的序号跳过，TCP 重连可能重放）、补拉（gap 的序号向服务端要）。**落库兜底**：**关键消息（订单通知/支付结果）服务端落库**，客户端重连后按 `lastSeq` 拉取——"**实时通道只管送达，可靠性靠'序号 + 落库 + 补拉'三层**"；**实时性 vs 可靠性的取舍**：聊天消息丢一条可容忍（补拉可选），**交易通知丢一条是事故**（必须落库补拉）。

## 7. SockJS 回退

**SockJS** 是"WebSocket 不可用时的回退方案"：**优先 WebSocket，连不上自动降级为 HTTP 长轮询/流式**——浏览器老版本、**剥掉 Upgrade 头的企业代理**、受限网络都能连（05 篇长轮询的"最后防线"场景）。**用法**：Spring 侧 `.withSockJS()`（03 篇 STOMP 配置），前端 `sockjs-client` + @stomp/stompjs。**2026 的认知**：**浏览器支持 99.84%，SockJS 的价值只剩"企业代理环境"**——新项目可以不用（直连 WebSocket），**但要部署在代理严格的政企/银行环境则保留回退**——"**SockJS 是保险丝：平时不触发，触发时救场**"。

## 8. 五个常见坑

- **坑一**：没配服务端空闲超时——**僵尸连接越积越多，内存与连接数暴涨；setIdleTimeout 必配**（第 3 节）；
- **坑二**：心跳周期与超时时间不匹配——**心跳 10s 超时 10s：正常连接被误杀；超时 ≥ 心跳 × 2-3**；
- **坑三**：重连固定间隔——**重连风暴；指数退避 + 抖动**（第 4 节）；
- **坑四**：重连后不恢复订阅/不补消息——**"连接好了但业务没恢复"；onConnect 里重订阅 + 按 seq 补拉**（第 5 节）；
- **坑五**：token 过期不处理——**重连永远失败；token 刷新与重连联动**（第 5 节）。
