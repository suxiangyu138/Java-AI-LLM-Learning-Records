## 1. 四方案全景

| 方案 | 方向 | 协议 | 自动重连 | 连接数成本 | 适用 |
|------|:---:|------|:---:|------|------|
| 短轮询 | 双向（模拟） | HTTP | ❌ | 每次请求新建 | 极简需求/频率低 |
| 长轮询 | 双向（模拟） | HTTP | ❌ | 挂起连接 | 代理剥 Upgrade 的兜底 |
| SSE | 单向推送 | HTTP | ✅ 内置 | 常驻连接（轻） | 通知/日志/**LLM 流式** |
| WebSocket | ⭐ 双向 | WS | ❌ 手写 | 常驻连接（重） | ⭐ 聊天/协作/游戏 |

**横向比较的四个维度**：**方向**（单向推送 vs 双向通信——**第一步就定死一半**）；**自动重连**（SSE 内置 EventSource 重连、WS 手写——**"SSE 省的重连代码，WS 要自己写"**）；**连接形态**（HTTP 短连接 vs 常驻长连接——**服务器连接数是容量关键**，08 篇）；**代理兼容**（HTTP 全兼容、WS 依赖 Upgrade——**企业代理剥头时 WS 连不上**，04 篇 SockJS）。**一句话选型**：**"双向且频繁 → WS；单向且服务端主动 → SSE；什么都绕不过 → 长轮询；简单查询 → 轮询"**。

## 2. SSE 深潜：2026 的 AI 主场

**SSE（Server-Sent Events）**：基于 HTTP 的**单向服务端推送**——浏览器 `EventSource` 原生支持、**内置自动重连（Last-Event-ID 续传）**、消息格式极简（`data: ...` 多行）。

```javascript
const source = new EventSource('/api/events');
source.onmessage = (e) => console.log(e.data);
source.onerror = () => console.log('断线（EventSource 会自动重连）');
```

**为什么说它是 2026 的 AI 主场**：**LLM 的 token 流式输出全用 SSE**——OpenAI/Anthropic/Gemini 的流式 API 底层就是 SSE（每 token 一条 `data:` 事件）——"**模型说话是单向流，SSE 是它的天然协议**"；**SSE 的三个工程优势**：**自动重连省心**、**基于 HTTP 代理全兼容**（穿过企业代理无压力）、**轻量**（无子协议/无帧格式学习成本）。**局限**：**单向**（客户端想发消息得另走 HTTP POST——"SSE + POST 组合"是常见架构）、连接数限制（浏览器对同域 HTTP/1.1 连接数 ~6 的限制，SSE 常驻会占配额——**HTTP/2 多路复用解决**）。

## 3. 轮询的两个变体

**短轮询**：客户端每 N 秒发请求，"有新消息吗？"——**实现最简单但 99% 请求空转**——适合"频率低 + 状态变化不重要"的极简场景（如每隔 30s 查一次在线状态）。

**长轮询**：客户端发请求后**服务端挂起**（hold），有消息立即响应、没消息等超时（如 30s）再响应——客户端收到后立刻再发——**模拟出"推送"效果**。**代价**：**每个挂起请求占一个连接/线程**（HTTP/1.1 下连接复用有限）、实现复杂（超时/重发/顺序）。**2026 的位置**：**WebSocket 连不上时的兜底**——剥掉 Upgrade 头的企业代理环境（04 篇 SockJS 的回退就是长轮询）——"**长轮询是方案的最后防线，不是默认选择**"。

## 4. WebTransport：未来协议

**WebTransport（QUIC 原生）** 是 WebSocket 的**未来继任者**：**多路复用流 + 不可靠 datagram**（游戏状态/语音/遥测——"**旧数据不如没有**"的场景）、**连接迁移**（WiFi → 蜂窝不断线）、**无队头阻塞**。**2026 的现实**：浏览器支持 ~75%（**仅 Chrome/Edge，Firefox 在 flag 后、Safari 无**——直接排除 25%+ 用户）、**服务器实现极少、CDN/代理支持实验性**、API 仍在演进——**采纳时间线**：2026 实验、**2027 早期采用、2028 主流**。

**给工程者的判断**：**2026 年新项目不选 WebTransport**——"**WebSocket 是 2026 的默认答案，WebTransport 是 2027+ 的升级项**"；**关注点**：Socket.IO 的 Engine.IO 已把 WebTransport 作为第三种传输（与 WebSocket/长轮询并列，**基础设施在悄悄布局**）——"**将来 WebTransport 成熟时，升级路径是替换传输层，不是重写业务**"。

## 5. 选型决策树

```text
需要服务端主动推消息吗？
├── 不需要 → 普通 HTTP 轮询/定时刷新（别用实时方案）
└── 需要 →
    ├── 只需要"服务端 → 客户端"单向？
    │   ├── 是 → SSE（通知/日志/LLM 流式——自动重连白拿）
    │   └── 否（要双向）→
    │       ├── 浏览器/网络环境支持 WS？→ WebSocket（⭐ 默认）
    │       └── 企业代理剥 Upgrade？→ SockJS 回退（长轮询兜底）
    └── 特殊需求：不可靠传输/多流/网络切换 → 关注 WebTransport（2027+）
```

**决策主线**：**先问方向（单向/双向），再问环境（代理兼容），最后问未来（WebTransport 关注不迁移）**——**"SSE 能解决的就别上 WS，WS 能解决的就别上 WebTransport"**是 2026 的保守原则——**方案越简单，运维越省心**。

## 6. 组合姿势

**生产系统很少只用一种方案**，三个真实组合：

**组合一（AI 应用）**：**SSE 流式输出 LLM token + WebSocket 双向协作**——模型说话走 SSE（流式顺滑）、人机同编辑/工具确认走 WS（双向）——"**2026 AI 应用的实时双通道**"（00 篇分工）。

**组合二（IM 系统）**：**WebSocket 主通道 + HTTP 兜底**——WS 聊天、断线时客户端降级长轮询/HTTP 拉取离线消息——"**实时走 WS，可靠走 HTTP**"（04 篇补拉）。

**组合三（监控/大盘）**：**SSE 推送指标 + WS 推送操作**——数据流单向用 SSE（省心）、控制操作双向用 WS——"**按消息方向分协议，不按模块分**"。

**组合心法**：**"每个消息方向选择最简协议"**——不是"全站 WebSocket"，而是"该单向的单向、该双向的双向"。

**还有一个维度：延迟需求**——**"实时"的度量是需求定的，不是技术定的**：秒级可接受（状态轮询/定时刷新）用轮询就够，百毫秒级（聊天/协作）才需要 WS——**"先量化延迟需求，再选方案，别为不需要的实时性买单"**。

## 7. 五个常见坑

- **坑一**：单向推送也用 WebSocket——**重连手写、代理不兼容、连接更重；SSE 白拿自动重连**（第 2 节）；
- **坑二**：选型不看浏览器/代理环境——**政企内网先验证 Upgrade 是否被剥；SockJS 回退备好**（第 3 节）；
- **坑三**：被 WebTransport 的宣传带节奏——**2026 年 Firefox/Safari 不支持 = 25%+ 用户进不来**（第 4 节）；
- **坑四**：全站一个方案——**单向双向混用的应用一套 WS 全扛；按消息方向分协议**（第 6 节）；
- **坑五**：SSE 在 HTTP/1.1 下开多条——**同域连接数上限 ~6，SSE 常驻占配额；HTTP/2 或减少并发**（第 2 节）。
