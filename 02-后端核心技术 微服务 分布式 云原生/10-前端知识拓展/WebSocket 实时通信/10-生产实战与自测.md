## 1. 实战：实时通知系统三合一

```java
// ① STOMP 配置（03 篇）：/app 进、/topic /queue 出
@Configuration
@EnableWebSocketMessageBroker
public class StompConfig implements WebSocketMessageBrokerConfigurer {
    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.enableSimpleBroker("/topic", "/queue");
        registry.setApplicationDestinationPrefixes("/app");
    }
    @Override
    public void registerStompEndpoints(StompEndpointRegistry registry) {
        registry.addEndpoint("/ws").setAllowedOrigins("https://app.example.com"); // 07 篇白名单
    }
}

// ② 握手鉴权 + 用户注入（07 篇）：token 从 query 验，用户进会话
@Component
public class TokenHandshakeInterceptor implements HandshakeInterceptor {
    @Override
    public boolean beforeHandshake(ServerHttpRequest req, ServerHttpResponse res,
                                   WebSocketHandler h, Map<String, Object> attrs) {
        String token = UriComponentsBuilder.fromUri(req.getURI())
            .build().getQueryParams().getFirst("token");
        User user = jwtService.verify(token);            // 验不过返回 false = 拒握手
        if (user == null) return false;
        attrs.put("user", user);                          // 注入连接上下文（09 篇）
        return true;
    }
}

// ③ 广播 + 点对点 + 跨实例同步（06 篇）：本地推 + Redis 广播
@Service
public class NotifyService {
    private final SimpMessagingTemplate template;
    private final StringRedisTemplate redis;

    public void notifyOrder(Long userId, String orderId, String status) {
        // 本地推（用户在本实例的连接）
        template.convertAndSendToUser(userId.toString(), "/queue/orders",
            Map.of("orderId", orderId, "status", status));
        // 跨实例广播（其他实例收到后查自己的连接推，06 篇监听器）
        redis.convertAndSend("notify.channel",
            JsonUtil.toJson(Map.of("userId", userId, "orderId", orderId, "status", status)));
    }
}

// ④ 前端订阅（02 篇）
// client.subscribe('/user/queue/orders', m => renderOrder(JSON.parse(m.body)));
// client.subscribe('/topic/announce', m => renderBanner(m.body));
```

**验收三问**：① 前端订阅 `/user/queue/orders` 后，`notifyOrder` 触发立即收到通知；② 双实例部署 + Redis Pub/Sub，**用户连实例 A 也能收到实例 B 触发的通知**（跨实例验证）；③ 未登录/假 token 握手被拒（鉴权生效）、非白名单 Origin 连不上。

## 2. 生产纪律清单

- **wss 必用**：证书与 HTTPS 同源，本地开发才允许 ws；
- **Origin 白名单**：setAllowedOrigins 具体域名，**禁止 "*" 上生产**；
- **握手必鉴权**：token 验证失败拒握手，用户注入连接上下文；
- **心跳 + 超时**：服务端空闲超时 ≥ 心跳 × 2-3，僵尸连接必清；
- **重连策略**：前端指数退避 + 抖动 + 上限，重连后重订阅 + 补拉；
- **分布式三件套**：Redis Pub/Sub 广播 + 连接注册表 + TTL 兜底；
- **监控五指标**：连接数/消息速率/延迟 P99/重连率/错误分布；
- **发布优雅关闭**：滚动发布 + shutdown 通知消息，避免重连风暴；
- **消息类型化**：统一信封 + Bean Validation，消息入口即校验；
- **连接限额**：单用户连接上限 + 全局上限，ulimit 提前调。

## 3. 报错速查十条

| 报错/现象 | 原因 | 修复 |
|------|------|------|
| 握手成功但立即断开（秒断） | 反代超时（Nginx 默认 60s）或 Upgrade 头没转发 | 三要素检查：Upgrade/Connection/read_timeout（06 篇） |
| 浏览器拦截连接（混合内容） | https 页面用 ws:// | 改 wss://（07 篇） |
| 握手 403 | Origin 白名单拒绝 | 白名单加域名（07 篇） |
| 握手失败/401 | token 无效或过期 | 刷新 token 重连（04/07 篇） |
| 连上了但收不到广播 | 没订阅 / 订阅失效（重连后） | onConnect 里重订阅（04 篇） |
| 点对点收不到（多实例） | 用户连在别的实例 | Redis 广播 + 本地推（06 篇） |
| 连接数涨到上限报错 | 僵尸连接堆积 / 限额太小 | 空闲超时清理 + 限额评估（08 篇） |
| 大量 1006 异常关闭 | 中间代理/服务端异常掐断 | 查代理超时与发布日志（08 篇） |
| 内存持续上涨 | 僵尸连接 + 消息缓冲堆积 | 超时清理 + 缓冲上限（08 篇） |
| Boot 4 启动失败（WS 相关） | Jackson 配置缺失（4.0.5 前） | 升级 4.0.5+ 或配 ObjectMapper（03 篇） |

## 4. 面试三范式

**范式一：价值式**——"我负责的实时通知系统支撑 5 万在线连接：心跳保活 + 指数退避重连把重连率从 15% 压到 3%，消息 P99 延迟 200ms 内，双实例 Redis Pub/Sub 跨实例推送 100% 到达"——**用连接数/延迟/到达率讲价值**。

**范式二：原理式**——"WebSocket 是 HTTP Upgrade 出的全双工通道，帧格式 2-14 字节、客户端强制掩码；STOMP 在裸协议上加订阅语义（/app 进 /topic 出 /user 个性化）；连接是常驻资源，每连接占 fd 与内存，容量要按账本算"——**展示协议深度与资源意识**。

**范式三：生产式**——"生产三件套：wss + Origin 白名单 + 握手 token 鉴权；分布式用 Redis Pub/Sub + 连接注册表；监控五指标 + 秒断先查代理；发布用滚动 + shutdown 消息避免重连风暴"——**展示系统思维**。

**追问四连防身**：①"WS 和 HTTP 长连接区别？"——WS 是全双工协议帧，HTTP 长连接是复用请求-响应；②"心跳为什么用 PING/PONG 不用业务消息？"——协议级零业务耦合、浏览器自动应答；③"100 万连接怎么设计？"——Redis 注册表 + 广播 + 多实例，单实例上限压测定，必要时专业件（06/08 篇）；④"SSE 和 WS 怎么选？"——单向推送 SSE（自动重连/代理友好），双向 WS；AI 场景 token 流走 SSE、事件走 WS（05 篇）。

## 5. 简历呈现

**项目写法示例**："基于 Spring Boot 4 + STOMP 构建实时通知系统（5 万在线连接）：握手 token 鉴权 + Origin 白名单双防线，Redis Pub/Sub + 连接注册表实现双实例跨节点推送（到达率 100%），指数退避重连 + 协议级心跳把重连率降至 3%，Prometheus 监控连接数/消息延迟 P99（200ms）；滚动发布 + 优雅关闭消息避免重连风暴"——**要点：数字量化（连接数/延迟/重连率）、技术纵深（鉴权/分布式/监控）、运维意识（发布）**。
