## 1. 连接的资源账本

**每个 WebSocket 连接都是常驻资源，账要算清**：**内存**（会话对象 + 收发缓冲区 + 编解码器，**单连接约 1-10KB 起步**，含业务上下文更多）；**文件描述符**（每连接一个 fd——**Linux 单进程默认 1024 个 ulimit，生产必须调大**）；**线程/IO**（每连接收发占事件循环/线程池资源——**连接数与吞吐是两本账**）。**账本算术**：**1 万连接 ≈ 几十 MB 内存 + 1 万 fd**；**100 万连接 ≈ 10GB 级内存 + 百万 fd + 专用架构**——"**万级连接是配置问题，百万级连接是架构问题**"——**2026 的现实**：IM/推送类应用 10 万级连接是常见规模，**先做容量预算再谈功能**（第 5 节公式）。

## 2. 连接管理

**连接的四个管理动作**：**限额**——**全局连接上限 + 单用户连接上限**（同一用户多端登录：限制 3-5 条，防滥用与资源耗尽——"**连接数限制既是安全手段也是容量手段**"，07 篇）；**超时**——空闲超时断开僵尸连接（04 篇第 3 节：心跳 × 2-3）；**登记**——连接注册表（用户 → 实例 → 会话，06 篇）；**清理**——断开事件里删注册表记录 + 通知业务（03 篇事件监听）——"**连接的生命周期管理：进有登记、闲有超时、死有清理**"。

## 3. 消息格式与协议治理

**消息格式与协议治理是实时系统的"代码质量"**：**统一信封**（`{type, data, seq}`，02 篇协议设计）——**type 字典集中维护**（前后端各一份、文档化——"**消息类型是实时系统的 API 面，比 REST 接口更需要治理**"）；**JSON Schema 校验**（服务端反序列化时校验字段——"**消息体是攻击面，反序列化即校验**"，07 篇内容防护）；**版本演进**（消息加字段向后兼容——**客户端版本多样，老客户端收到新字段要能忽略**）；**心跳与业务消息分离**（ping/pong 走专用 type，不进业务处理链）。**治理三件套**：**信封统一 + 类型文档化 + 校验在入口**——"**实时系统的消息格式野了，比接口文档过期更可怕**"。

## 4. 监控指标

**实时系统的五个核心指标**：**连接数**（当前值 + 趋势——**连接数突降 = 服务端重启/网络故障；突增 = 异常流量**）；**消息速率**（每秒收发消息数——吞吐水位）；**消息延迟**（**服务端收到 → 推送完成的耗时，P95/P99**——实时系统的核心质量指标）；**重连率**（断线重连占比——**重连率飙升 = 网络问题/服务不稳定/代理超时**）；**错误/异常**（握手失败率、关闭码分布——**大量 1006（异常关闭）= 中间层掐断，查代理超时**）。**采集**：Prometheus 指标（连接数/消息速率/延迟直方图）+ 日志（握手日志/异常关闭日志）——与日志监控指标体系（`../../07-工程运维基础/运维/日志监控指标/`）交叉——"**连接数报警是最粗的网，延迟与重连率才是实时系统的真实脉搏**"。

## 5. 容量规划

**容量规划公式（先算后跑）**：**内存预算 = 连接数 × 单连接内存 + 消息缓冲**；**fd 预算 = 连接数 × 1 + 预留**（ulimit 与 fd 监控）；**带宽预算 = 消息速率 × 平均消息大小 × 8**（每秒 bit）；**实例数 = max(连接数 ÷ 单实例上限, 吞吐 ÷ 单实例吞吐)**。**实测方法论**：**压测先行**——单实例连 1 万/5 万/10 万连接，测内存与吞吐拐点（**连接数与消息吞吐是两个独立拐点**）；**预留水位**——**生产容量用到 60-70% 就该扩容**（连接突增是常态，100% 水位 = 事故边缘）。**2026 的经验值**：**单实例（8C16G）裸 WebSocket 扛 5-10 万连接是常见量级**（带业务逻辑打折），**再往上走 Redis 注册表 + 多实例 + 可能上专业件**（06 篇升级路径）。

## 6. 故障排查

**实时系统故障排查五板斧**：

**板斧一：连接秒断/频繁重连**——**先查反代三要素**（Upgrade 头/Connection 改写/超时——Nginx proxy_read_timeout 默认 60s 是最常见元凶，06 篇）——"**秒断先查代理，别查业务**"；**板斧二：连不上**——握手失败：查 Origin 白名单（07 篇）、token 失效（07/04 篇）、证书（wss 配置）；**板斧三：消息收不到**——**查"消息是否到了用户连接的实例"**：连接注册表（06 篇）+ 广播通道（Redis Pub/Sub 是否订阅）——"**分布式场景消息丢失，先画'消息路径图'，逐跳排查**"；**板斧四：延迟高**——查服务端队列积压（消息速率 vs 消费速率）、网络链路（跨机房）、消息大小（大消息序列化慢）；**板斧五：内存涨**——**僵尸连接**（空闲超时没配/配太长，04 篇）+ 消息缓冲堆积——"**内存涨先数连接，连接涨先查心跳**"。

## 7. 发布与优雅关闭

**实时系统的发布比 REST 更痛**：**重启 = 所有连接断开 = 全体客户端重连风暴**。**三个实践**：其一，**滚动发布**——实例逐个重启，**每次只断一批连接**（客户端指数退避重连，04 篇——"**重连风暴与发布节奏强相关**"）；其二，**优雅关闭**——**关闭前先停止接收新连接，再通知已连接客户端"即将断开，请重连"**（发一条 `{type:"shutdown"}` 消息），**等几秒让客户端主动重连到别的实例**，最后才关——"**优雅关闭是把'全体突然断'变成'分批有序断'**"；其三，**发布窗口**——大版本发布选低峰期 + 观察重连率指标（第 4 节）——"**实时系统的发布是运维事件，不是开发动作**"。

## 8. 五个常见坑

- **坑一**：ulimit 不调——**万级连接直接"too many open files"；ulimit 与 fd 监控上线前配好**（第 1 节）；
- **坑二**：连接数上限不设——**单用户开 100 条连接打爆资源；限额必设**（第 2 节）；
- **坑三**：监控只看连接数——**延迟 P99 与重连率才是质量指标；五指标全上**（第 4 节）；
- **坑四**：容量不压测——**生产 10 万连接才发现单实例扛不住；压测找拐点，60-70% 水位扩**（第 5 节）；
- **坑五**：发布直接重启——**全体断连 + 重连风暴；滚动 + 优雅关闭消息**（第 7 节）。
