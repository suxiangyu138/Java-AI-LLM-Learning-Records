## 1. 问题：连接是"本机私有的"

**单机一切正常，多实例问题浮现**：用户 A 连上 Server-1、用户 B 连上 Server-2——A 给 B 发消息时，**Server-1 的会话集合里根本没有 B**（03 篇的 sessions 集合只是本机视图）——"**连接在哪个实例上，消息只有那个实例能推**"。**核心矛盾**：**连接是实例私有的，但业务是全局的**。**解法两条路**：**要么让用户永远连同一台机器**（粘滞会话——把问题绕开），**要么让消息到达所有机器**（广播同步——把消息复制过去）——**"粘滞是回避，广播是解决"**，生产系统以广播为主、粘滞为辅助。

## 2. 方案一：Redis Pub/Sub（⭐ 最简单）

**机制**：**Server-1 收到消息 → 发布到 Redis Channel → 所有订阅了该 Channel 的实例收到 → 各自查自己的连接注册表推给目标用户**——"**消息经 Redis 广播到所有实例，每个实例只推自己手上的连接**"。

```java
// 发布端：任何实例收到消息都发布（03 篇 ChatController 里加一行）
stringRedisTemplate.convertAndSend("chat.channel", json);

// 订阅端：每个实例都订阅（应用启动时注册）
@Component
public class RedisMessageListener implements MessageListener {
    private final SimpMessagingTemplate template;

    @Override
    public void onMessage(Message message, byte[] pattern) {
        ChatMessage msg = JsonUtil.parse(message, ChatMessage.class);
        template.convertAndSendToUser(msg.getTo(), "/queue/private", msg);
        // 本实例没有该用户连接？convertAndSendToUser 无感跳过（09 篇行为）
    }
}
```

**为什么"⭐ 最简单"**：**Redis 已是 Java 后端标配**（缓存/分布式锁都在用）、Pub/Sub 两条命令搞定、无新增基础设施。**三个注意**：其一，**Pub/Sub 不持久化**——**消息发布时没有订阅者就丢了**（与 Redis Stream 的区别：Stream 可持久化可回放，08 篇可靠性场景用 Stream）；其二，**订阅端要幂等**——同一消息被多个实例收到，**推送目标只在自己连接上执行**，天然无重复推送（每实例只推自己有的连接）；其三，**消息要序列化**——统一 JSON，别用 Java 原生序列化（跨实例反序列化脆弱）。

## 3. 方案二：MQ 广播（Kafka/RocketMQ）

**机制**：消息 → MQ Topic → **所有实例作为消费者组/独立消费者**收到 → 查本地连接推送——与 Redis Pub/Sub 同构，但多三个能力：**持久化**（消费者没在线也能补拉）、**回溯**（从指定 offset 重放）、**削峰**（消费速率控制）。**适用**：**已有 MQ 基础设施的团队**（不新增组件）、**消息量大且要持久化**（事件溯源/审计）、**跨系统广播**（实时模块与其他微服务解耦）。

**与 Redis Pub/Sub 的选型**：**简单实时场景用 Redis**（秒级延迟、零成本）；**要持久化/削峰/审计用 MQ**——"**Redis 管'现在的消息'，MQ 管'不能丢的消息'**"；**2026 的增量认知**：Redis 7+ 的 **Stream** 填补了"轻量持久化"空档——**中等可靠性场景（订单通知）用 Stream，重度可靠性（交易事件）用 MQ**。

## 4. 方案三：粘滞会话（IP Hash）

**机制**：Nginx 按 userId/IP Hash 路由——**同一用户永远连同一台实例**——用户消息在实例内就能找到目标（无需广播）——"**把分布式问题变成单机问题**"（Nginx 配置 `ip_hash` 或按自定义 key 一致性哈希）。

**三个致命缺陷**：其一，**单点故障**——**某实例挂了，Hash 到它的所有用户重连后 Hash 到别的机器，但"机器 A 上的会话"没了**（粘滞只解决"平时找得到"，不解决"挂了怎么办"）；其二，**负载不均**——热点用户全 Hash 到一台；其三，**扩容/缩容要重 Hash**（一致性哈希缓解）。**2026 定位**：**粘滞是"减少广播压力"的辅助手段，不是分布式方案**——"**粘滞 + 广播组合**"：默认广播保正确，粘滞保性能（热点用户少跨机）。

## 5. 连接注册表

**广播同步之外，分布式实时通信的第二根柱子：连接注册表**——"**用户 → 在哪个实例的哪条连接**"的全局视图。**实现**：

```text
Redis：  user:{userId} → {serverId, sessionId}
        （连接建立时写入、断开时删除——TTL 防残留）

用途一：定向推送 —— 消息只发给"有该用户连接的实例"（省广播流量）
用途二：用户在线状态 —— 全局"在线/离线"判断（事件监听写状态，03 篇）
用途三：踢人下线 —— 找到实例 → 通知该实例关闭指定连接（07 篇安全）
```

**连接注册表的三个纪律**：**写时机**（连接建立/断开事件里同步写——03 篇 SessionConnectEvent/DisconnectEvent）、**TTL 兜底**（**异常断连可能没触发清理事件，TTL 防幽灵记录**，04 篇僵尸连接的服务端版）、**一致性**（注册表是"尽力一致"——**以实际推送结果为准，注册表只做路由优化不做事实依据**）。**规模升级路径**：小规模（几十实例）Redis 注册表 + Pub/Sub 够用；**超大规模（百万连接）上专业方案**（Pusher/Ably 等实时基础设施或自研网关层）——"**先 Redis 三件套（Pub/Sub + 注册表 + Stream），打不住了再上专业件**"。

## 6. 网关层的 WebSocket 转发

**网关（Nginx/Spring Cloud Gateway）必须支持 WebSocket 转发**，三个要素：

**Nginx**（`../../07-工程运维基础/运维/Nginx 基础/03-反向代理配置.md` 交叉）：

```nginx
location /ws/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;       # 要素一：转发 Upgrade 头
    proxy_set_header Connection "upgrade";        # 要素二：改写 Connection
    proxy_read_timeout 3600s;                     # 要素三：长超时（默认 60s 会掐断）
}
```

**Spring Cloud Gateway**：`spring.cloud.gateway.routes[].uri: ws://backend` 或 lb:// 前缀——**网关支持 WebSocket 路由**（转发 Upgrade），注意**网关实例也要配 WS 超时**。**三要素本质**：**Upgrade 头转发 + Connection 头改写 + 超时放宽**——**任何反代层漏一个，WebSocket 就"握手上、秒断开"**（08 篇排障第一条）。**WebSocket 与负载均衡**：**WS 长连接不参与"轮询均衡"**——连接建立后固定在某实例（粘滞天然发生），**实例扩容/缩容时已建立的连接不受影响**（新连接才重新分配）。

## 7. 方案对比与选型

| 方案 | 持久化 | 复杂度 | 适用 |
|------|:---:|------|------|
| Redis Pub/Sub | ❌ | ⭐ 最低 | 实时广播/默认选择 |
| Redis Stream | ✅ | 低 | 中等可靠性（订单通知） |
| MQ（Kafka/RocketMQ） | ✅ | 中 | 大流量 + 持久化 + 审计 |
| 粘滞会话 | — | 低 | 辅助手段（减广播压力） |
| 专业实时基础设施 | ✅ | 高 | 百万连接级 |

**选型主线**：**"默认 Redis Pub/Sub + 连接注册表；要持久化升 Stream；重可靠性/大流量上 MQ；粘滞只做辅助；百万级上专业件"**——与消息队列体系（`../../03-消息队列/消息队列理论与实战/`）的分工：**MQ 体系讲消息中间件本身，本体系讲'实时连接如何跨实例路由'**。

## 8. 五个常见坑

- **坑一**：只配粘滞不配广播——**实例挂了用户全断；粘滞是辅助，广播是底线**（第 4 节）；
- **坑二**：Redis Pub/Sub 当可靠消息用——**无持久化，发布时无订阅者就丢；要可靠用 Stream/MQ**（第 3 节）；
- **坑三**：Java 原生序列化跨实例——**脆弱；统一 JSON**（第 2 节）；
- **坑四**：注册表不设 TTL——**异常断连留幽灵记录；TTL 兜底**（第 5 节）；
- **坑五**：Nginx 转发漏 Upgrade/Connection 头——**握手成功即断；三要素检查清单**（第 6 节）。
