## 1. 攻击面地图

Token 方案的四条主要攻击线，各自对应防线：

| 攻击 | 手法 | 防线 |
|------|------|------|
| XSS 偷凭证 | 注入脚本读 localStorage/内存 | 不存 localStorage、HttpOnly、前端转义 |
| CSRF 借凭证 | 跨站请求自动带 Cookie | SameSite、Token 头、CSRF Token |
| 泄露面 | URL/日志/错误上报带 Token | 不走 URL、日志脱敏、错误信息净化 |
| 越权 | 拿自己令牌访问他人资源 | 授权模型（BOLA 治理），不是令牌问题 |

**核心认知：Token 防不了「登录后的滥用」**——认证只证明「你是你」，越权是授权层的事；而凭证本身的失守（偷/借/漏）才是 Token 方案的主战场。四线都要防，任何一线失守都有对应方案补救——纵深防御。

## 2. XSS：偷凭证

XSS 是「前端凭证泄露」的头号来源——脚本一旦执行，同源内的一切都暴露：

**攻击路径**：反射型（URL 参数注入）、存储型（评论/昵称存恶意脚本）、DOM 型（前端拼接 innerHTML）——执行后 `localStorage.getItem('accessToken')`、`document.cookie`（HttpOnly 读不到，非 HttpOnly 全裸）直接偷走。

**防线三层**：**存储层**——Token 不落 localStorage（04 篇），HttpOnly Cookie 让 XSS 读不到；**渲染层**——用户输入一律转义（Vue 默认转义 `{{ }}`、React 默认转义 JSX——**别用 `v-html`/`dangerouslySetInnerHTML` 渲染用户内容**）、`innerHTML` 拼串是禁区；**检测层**——CSP（内容安全策略）限制脚本来源（`script-src` 白名单）是 XSS 的浏览器侧保险丝——XSS 是 2026 年 Web 第一大漏洞，前端安全的第一优先级。

## 3. CSRF：借凭证

CSRF（跨站请求伪造）针对「自动携带凭证」的 Cookie 方案：用户登录着银行，访问恶意站点，恶意站点的表单 POST 自动带上银行域的 Cookie——银行以为是用户操作。

**攻击成立的三个条件**：凭证走 Cookie 自动携带 + 无 SameSite 防护 + 目标接口无额外校验。

**防线（按层叠加）**：**SameSite=Lax/Strict**——2026 主防线（浏览器侧，跨站 POST 不带 Cookie）；**Bearer 头方案天然免疫**——header 不会自动携带（这是 SPA 用 header 的安全红利）；**同步 Token（CSRF Token）**——服务端签发随机串，表单携带，服务端校验（Cookie 方案的深度防线）；**双提交 Cookie**——请求头带与 Cookie 相同的随机值，服务端比对；**敏感操作二次验证**——改密/转账要密码或验证码（最后防线）。**要点：SameSite 是默认防线不是唯一防线**——高敏感系统多层叠加。

## 4. 泄露面治理：URL/日志/内存

凭证的「合法路径」也是泄露路径——三条最常被忽略的泄露面：

**URL**——Token 进 URL（`?token=xxx`）即进入浏览器历史、Referer 头（跳转外站时带出）、网关与代理日志、监控系统。**红线：凭证绝不进 URL**（OAuth 2.1 明文禁止，07 篇）。

**日志**——前端 console.log 打 token、错误上报（Sentry 等）默认捕获全部上下文（包括请求头）——**一旦上报，Token 进了第三方服务器**。防线：**日志与上报统一脱敏**（拦截器层对 Authorization 头做 redact，上报前清洗），开发环境也别养成打 token 的习惯。

**内存与调试**——devtools 的 Network 面板、浏览器插件（extensions 有权限读请求）——**没法完全防，所以 access 要短**（05 篇 TTL 设计的理由）。**第三方脚本**（统计、AB 测试、监控）——有权限读 DOM 与部分请求——鉴权页面少引第三方脚本，或隔离执行域。

## 5. 越权：认证之外的授权

**越权（BOLA/BFLA）连续多年是 OWASP API Top10 榜首**——比认证漏洞更常见：用户 A 用自己合法的 Token，访问 `/api/orders/12345`——如果后端只验「登录了」没验「订单 12345 属于你」，A 就能看别人的订单。

**防线在授权层，不在令牌层**：**对象级授权**——每个资源访问都要校验「当前用户是否拥有该资源」（订单属于谁、文件属于谁）；**方法级授权**——角色/权限判定（管理员接口用户不能调）；**框架支撑**——Spring Security 的授权模型（[[../../06-Spring全家桶/Spring%20Security与Spring%20Security%20OAuth2/00-Spring%20Security与OAuth2知识体系总览|Spring Security 体系]] 03 篇）；**测试纪律**——越权用例（A 的 token 访问 B 的资源必须 403）是 API 测试的必选项。**「我们有 JWT 认证」≠「我们有授权」**——这是 2026 年最常被误解的安全声明。

## 6. 令牌绑定：DPoP 与 mTLS

「令牌被盗」的终极解法——**让令牌离开持有者就失效**：把令牌绑定到客户端持有的密钥（证明持有，Proof of Possession）：

**DPoP（RFC 9449）**——客户端生成密钥对，把公钥放进请求的 `DPoP` 头（JWT 形态，含时间戳与请求指纹）；授权服务器把令牌与公钥绑定；**后续每个请求都要带新的 DPoP 证明**（私钥签名）——攻击者偷走令牌没有私钥，请求证明签不出来。**适用**：高敏感 API（金融）、令牌会经过不可信网络的场景。

**mTLS（RFC 8705）**——客户端证书绑定令牌：授权服务器记录客户端证书指纹，令牌只对「持有该证书的客户端」有效——移动端/企业内网场景的强绑定。

**对比**：mTLS 更强但部署重（证书管理）；DPoP 轻量（纯应用层，无证书基础设施）——2026 新项目从 DPoP 起步，金融级上 mTLS。**DPoP 的成本**：每个请求一次签名 + 服务端验签——性能开销小但实现复杂度增加，非高敏感场景不必上。

## 7. 运维护栏：限流与审计

认证端点是攻击者的正面战场——**登录/刷新/重置是限流与审计的重点**：

**限流**：`/login`、`/refresh`、`/reset` 按「身份 + IP」双重限流（同账号 5 次/分钟、同 IP 20 次/分钟），指数退避 + 连续失败锁定（5-10 次）；**响应形状恒定**——「用户不存在」与「密码错误」返回同样的文案与耗时（防账号枚举——时间差也是信息）；**验证码兜底**（高频失败触发图形/滑动验证）。

**审计**：每个认证事件落日志——登录成功/失败、令牌签发/刷新/撤销、重用检测触发、密码修改——带 user_id、jti、IP、设备、关联 ID（[[../../09-Web开发全流程/Filter%20过滤器/00-Filter过滤器总览|Filter 体系]] 的登录拦截与此配合）；**异常检测**——不可能旅行（北京登录后 10 分钟上海登录）、新设备登录、重用模式——触发升级验证或告警。**审计日志是「事件发生后能还原」的唯一依据**——不可缺失，不可写进业务库（独立存储 + 只追加）。

## 8. 安全红线清单

- [ ] Token 不落 localStorage；Cookie 全属性（HttpOnly/Secure/SameSite）
- [ ] 凭证不进 URL；日志/上报脱敏；不 console.log token
- [ ] XSS 防线：转义 + 禁 v-html/dangerouslySetInnerHTML + CSP
- [ ] CSRF 防线：SameSite + 头携带（Bearer）或 CSRF Token
- [ ] 授权独立设计：对象级校验 + 越权测试用例
- [ ] 认证端点限流 + 恒定响应 + 验证码兜底
- [ ] 认证事件全量审计（独立存储）
- [ ] 密钥管理：环境变量 + 定期轮换 + 不用默认密钥
- [ ] 高敏感场景：DPoP/mTLS 绑定
