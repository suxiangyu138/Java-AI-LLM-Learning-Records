## 1. 拦截器体系总设计

前端 Token 工程的完整骨架是「三层拦截 + 一个状态」：

```text
请求层（axios 拦截器）
  请求拦截：注入 Authorization
  响应拦截：401 → 静默刷新 → 重放原请求（03 篇）
路由层（导航守卫）
  进入受保护页面 → 检查登录态 → 无态跳登录
  登录态过期 → 刷新失败 → 跳登录并记录原目标
状态层（认证状态管理）
  isAuthenticated / userInfo / token 生命周期
  登录 → 置状态；登出 → 清状态；刷新 → 保持
```

设计原则：**请求层管「凭证怎么带」、路由层管「页面能不能进」、状态层管「登录态是什么」**——三层各司其职，互不渗透；业务组件只感知 `useAuth()`（读状态）与 `login()/logout()`（改状态），不直接碰 Token 细节。**单页应用里「请求 401」与「路由守卫」是两条独立防线**：请求 401 由拦截器静默处理（用户无感知），路由守卫处理「明确未登录的进入」（直接拦截跳转）——两者都做，缺一层就有体验或安全漏洞。

## 2. 请求拦截：携带与重试

```javascript
// api.js — 完整请求拦截（携带 + 幂等重试）
import axios from 'axios';
import { getAccessToken } from './tokenStore';

const api = axios.create({ baseURL: import.meta.env.VITE_API_BASE || '/api', timeout: 15000 });

api.interceptors.request.use((config) => {
  const token = getAccessToken();
  if (token) config.headers.Authorization = `Bearer ${token}`;
  if (!config.headers['X-Request-Id'])                       // 幂等键：重试可识别
    config.headers['X-Request-Id'] = crypto.randomUUID();
  return config;
});
```

两个细节：**Token 为空时不加头**（登录接口、公开接口自然不带——无需特殊处理）；**请求幂等键**（X-Request-Id）是「拦截器层」的重试安全网——网络超时重试时，服务端按键去重，写操作不重复执行（配合 [[../Axios%20异步请求、Promise%20基础/01-Axios核心用法与后端对标|Axios 体系]] 的请求规范）。

## 3. 响应拦截：401 刷新链

完整版 401 处理链（03 篇基础版 + 细节补全）：

```javascript
api.interceptors.response.use(
  (resp) => resp,
  async (error) => {
    const { response, config } = error;
    const status = response?.status;

    if (status === 401 && !config._retry && !config._isAuth) {
      if (!refreshing) {
        refreshing = api.post('/auth/refresh', { refreshToken: getRefreshToken() })
          .then(({ data }) => saveTokens(data.accessToken, data.refreshToken))
          .catch((e) => { clearTokens(); throw e; })
          .finally(() => { refreshing = null; });
      }
      try {
        await refreshing;
        config._retry = true;
        return api(config);                     // 重放（带新 token）
      } catch {
        authState.forceLogout();                // 通知状态层 → 路由跳登录
        return Promise.reject(error);
      }
    }
    if (status === 401 && config._isAuth) {     // 刷新接口本身 401
      authState.forceLogout();
      return Promise.reject(error);
    }
    return Promise.reject(error);
  });
```

要点：**`_isAuth` 标记区分「业务请求」与「刷新请求」**——刷新接口自己 401 时不能再触发刷新（死循环）；**刷新成功只换 token 不重登**（用户无感知）；**forceLogout 走状态层**（清状态 + 跳登录 + 提示「登录已过期」），而不是拦截器里直接 `window.location`（组件与路由才能优雅处理）。

## 4. 路由守卫：页面级访问控制

路由层控制「哪些页面必须登录」——Vue Router 与 React Router 各一套，思路一致：

```javascript
// Vue Router 导航守卫
router.beforeEach(async (to) => {
  const auth = useAuthStore();
  if (to.meta.requiresAuth && !auth.isAuthenticated) {
    auth.trySilentRefresh();                    // 尝试静默恢复（内存方案）
    if (!auth.isAuthenticated) {
      return { path: '/login', query: { redirect: to.fullPath } };  // 记录原目标
    }
  }
  if (to.path === '/login' && auth.isAuthenticated) {
    return { path: '/' };                       // 已登录访问登录页 → 回首页
  }
});
```

```javascript
// React Router（v6+ 的组件式守卫）
function RequireAuth({ children }) {
  const { isAuthenticated } = useAuth();
  const location = useLocation();
  if (!isAuthenticated) return <Navigate to="/login" state={{ from: location }} replace />;
  return children;
}
// 用法：<Route path="/orders" element={<RequireAuth><Orders/></RequireAuth>} />
```

设计要点：**`requiresAuth` 元信息声明式控制**（页面声明「我要登录」，守卫统一执行）；**登录后回跳原目标**（`redirect`/`state.from`——「登录后回到刚才的页面」的标准体验）；**登录页对已登录用户重定向**（防反复登录）；**守卫不做数据请求**（只做页面级开关，数据级校验在后端——前端守卫只是体验层，不是安全层）。

## 5. 多 Tab 同步

「一个 tab 登出，其他 tab 应该跟着登出」——localStorage 与 Cookie 方案各有同步手段：

```javascript
// 方案一：storage 事件（localStorage 方案——注意这是存储的锅之一）
window.addEventListener('storage', (e) => {
  if (e.key === 'auth_state') handleAuthChanged(JSON.parse(e.newValue));
});

// 方案二：BroadcastChannel（内存/Cookie 方案，现代推荐）
const bc = new BroadcastChannel('auth_channel');
bc.onmessage = (e) => {                          // 收到登出/登录广播
  if (e.data.type === 'logout') forceLogout();
  if (e.data.type === 'login') refreshUser();
};
// 登出时广播：bc.postMessage({ type: 'logout' });
```

设计要点：**所有 tab 共享「一个登录态」**——登录在一个 tab 发生，其他 tab 感知（刷新用户信息）；登出在一个 tab 发生，其他 tab 立即清理（否则还能继续调 API 直到 401）；**BroadcastChannel 是 2026 推荐**（storage 事件只对 localStorage 方案有效，且事件携带旧值兼容问题多）；**tab 关闭不触发同步**（新 tab 打开时重新检查登录态即可）。

## 6. 框架集成：Vue/React

框架差异只在「状态怎么存」，设计模式通用：

**Vue（Pinia 推荐）**——`useAuthStore`：state（user/token 状态）+ actions（login/logout/fetchUser）+ 持久化插件（Pinia persist 存 refresh 而非 access——安全分层）；`setup` 里初始化时调 `trySilentRefresh`。**React（Zustand/Context）**——`useAuth` hook 包 Zustand store；`Provider` 在根部包裹；`useEffect` 里监听认证事件（token 过期通知）。**共同纪律**：**状态与存储分离**（store 管状态，tokenStore 管凭证读写——04 篇）；**认证状态不存组件内**（刷新页面就丢——必须提升到全局 store）；**框架无关的拦截器与守卫逻辑抽成独立模块**（换框架只换壳）。

**登录态与请求态的竞态治理**：前端最隐蔽的 bug 是「登录动作与并发请求的竞态」——页面加载时多个组件同时发请求（未登录），同时用户点了登录——请求 401 → 触发刷新（refresh 还没有！）→ 刷新失败 → 跳登录页把刚登录的用户踢出去。治理三招：**刷新失败先查 refresh 是否存在**（没有 refresh 的 401 直接视为未登录，不触发刷新链）；**登录成功广播事件**（authEvents.emit('login') 让挂起的请求重试）；**请求队列**（登录进行中的请求先排队，登录完成统一放行——BFF 层或前端 store 都可实现，复杂场景用队列，简单场景广播够用）。**「请求层与状态层的握手」是前端认证工程的经验分水岭**——面试追问「登录和请求同时发生怎么办」就在这里。

## 7. 常见坑

**坑一：拦截器里直接 window.location**。跳转绕过路由与状态层——组件/路由才能优雅处理，走 forceLogout。

**坑二：路由守卫只防跳转不防请求**。守卫过了但请求 401——两条防线都要（守卫是体验层，后端才是安全层）。

**坑三：刷新接口的 401 也走刷新链**。死循环——`_isAuth` 标记区分。

**坑四：多 tab 不同步**。一个 tab 登出其他 tab 还在用——BroadcastChannel 广播。

**坑五：登录状态存组件里**。刷新页面就丢——全局 store。

**坑六：守卫里做数据请求**。守卫发 API 查权限——页面级守卫只查状态，数据级校验交给请求层。
