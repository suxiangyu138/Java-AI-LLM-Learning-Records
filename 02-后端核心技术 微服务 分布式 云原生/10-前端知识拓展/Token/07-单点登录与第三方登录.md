## 1. 单点登录 SSO 全景

SSO 解决「一次登录，多应用免登」——所有应用的认证委托给统一认证中心：

```text
SSO 核心流程（JWT 方案）：
1. 用户访问 app1.example.com → 无凭证 → 302 到 sso.example.com/login
2. 用户在 SSO 登录 → SSO 签发凭证 → 302 回 app1（带凭证）
3. 用户访问 app2.example.com → 无凭证 → 302 到 sso.example.com
4. SSO 已有登录态（SSO 域 Cookie）→ 直接签发 → 302 回 app2
关键：SSO 的登录态以 Cookie 形式存在认证中心域下，各应用只认签发的 Token
```

**SSO 与普通登录的本质区别**：登录状态存在**认证中心域**（sso.example.com 的 Cookie），各应用拿到的是「认证中心签发的凭证」——应用自己不存密码、不做认证，只做验证（JWT 验签）或会话映射（CAS）。**SSO 的会话是两级**：认证中心的全局会话 + 各应用的本地会话——全局会话在，访问新应用免登；全局会话过期，各应用登录态陆续失效。

## 2. Token 传递三方案

SSO 中心签发的凭证怎么安全地传给各应用——三个方案按安全性排序：

**方案一：重定向 URL 参数（不安全）**——`app1.example.com?token=xxx`。Token 暴露在 URL——进历史记录、进 Referer、进网关日志。**仅限低敏感演示，生产禁用**。

**方案二：SSO 域 Cookie（同域名）**——`Set-Cookie: token=xxx; Domain=.example.com`——子域名共享 Cookie，app1/app2 都能读。**同域名场景推荐**——但注意 Domain 属性扩大了 Cookie 作用域（任何子域 XSS 都能读它）、且受 SameSite 跨站限制约束。

**方案三：OAuth 授权码（跨域名标准）**——应用跳转 SSO → 登录 → SSO 302 回应用带**一次性授权码**（URL 里是 code 不是 token）→ 应用后端拿 code 换 token（服务端到服务端的换码请求，token 全程不进浏览器 URL）。**跨域名、生产标准**——token 不出现在 URL，安全性最高。

## 3. OAuth 2.1 授权码流程

授权码是 OAuth 的核心流程，也是 SSO 跨域的标准实现（2026 版 = OAuth 2.0 + 2.1 收紧项）：

```text
OAuth 授权码流程（授权码 + PKCE）：
前端（SPA）              后端（应用）          授权服务器（微信/Google/SSO）
  │                         │                       │
  │──跳转授权页（含 client_id、redirect_uri、scope、code_challenge）──→│
  │                         │                       │ 用户登录+授权
  │←──302 回 redirect_uri?code=一次性授权码────│
  │──把 code 发给后端──→│                       │
  │                         │──POST /token（code+client_secret+verifier）──→│
  │                         │←──{access_token, id_token, refresh_token}───│
  │←──{应用令牌}─────│                       │
```

**前端在流程中的角色只有两个**：跳转授权页（发起授权）+ 收下回跳的 code 转交后端——**前端永远碰不到 OAuth 的 token 交换**（那是后端与授权服务器的服务端通信）。这是 OAuth 的安全根基：token 从授权服务器直达后端，不经过浏览器。**2026 收紧项（OAuth 2.1）**：PKCE 全客户端必选；redirect_uri 精确匹配（禁通配符）；Implicit 授权移除；密码模式移除；Bearer 令牌禁 URL。

## 4. PKCE：移动端与 SPA 的必选项

PKCE（RFC 7636）解决「授权码被截获」的问题——SPA 与移动端没有 client_secret 可保密的场景尤其关键：

```javascript
// 前端生成 code_verifier 与 code_challenge（授权跳转前）
import { randomBytes, createHash } from 'crypto';

const verifier = randomBytes(32).toString('base64url');        // 随机串
const challenge = createHash('sha256').update(verifier).digest('base64url');
// 跳转授权页带 code_challenge；回跳后把 verifier 交给后端
// 后端用 code + verifier 换 token——授权服务器校验 challenge 匹配
```

**攻击场景**：攻击者截获授权码（比如通过恶意 App 注册同样的 redirect_uri）——没有 PKCE 时，拿着 code 就能换 token；有 PKCE 时，换 token 需要 code_verifier（在合法客户端手里），截获 code 无用。**为什么 2.1 全客户端必选**：移动端/SPA 的 client_secret 存不住（反编译即得），PKCE 用「动态挑战」替代「静态密钥」——同样的防护、无需密钥。**前端要点**：verifier 存内存/会话存储（刷新丢则重新授权）；challenge 用 S256（比 plain 强）。

## 5. OIDC 与 ID Token

OAuth 管「授权」（能不能调 API），OIDC（OpenID Connect）在 OAuth 之上加「认证」（用户是谁）——多出的产物就是 **ID Token**（JWT 形态）：

```javascript
// ID Token 的解码内容（JWT 三段结构，02 篇）：
{
  "iss": "https://auth.example.com",    // 签发者
  "sub": "user-123",                    // 用户唯一标识（跨应用稳定）
  "aud": "my-app",                      // 受众 = 你的 client_id
  "exp": ..., "iat": ...,
  "email": "user@example.com",          // 身份声明
  "email_verified": true
}
```

**ID Token 与 Access Token 的分工**：ID Token 是给「应用」看的身份证明（登录后显示用户信息），Access Token 是给「资源服务器」看的权限凭证——**两者别混用**（拿 ID Token 调 API 是经典错误，反之亦然）。**前端消费**：登录回跳后，后端验 ID Token（iss/aud/exp + 签名，02 篇五要点），把用户信息返回前端——前端不自己解 ID Token（除非纯前端校验场景）。

## 6. 社交登录实战（微信/Google）

社交登录 = 对接第三方的 OAuth 授权服务器（微信、Google、GitHub 各有实现）：

**微信登录（网页授权）**：跳转 `open.weixin.qq.com/connect/oauth2/authorize?appid=...&redirect_uri=...&scope=snsapi_userinfo&state=...` → 回跳 `code` → 后端拿 `appid + secret + code` 换 `access_token + openid` → 用 openid 关联自家用户表。**要点**：微信的 `secret` 是机密（后端持）；`openid` 是用户在本应用的唯一标识（跨应用用 unionid）；`state` 参数防 CSRF（回跳校验）。

**Google 登录**：标准 OIDC——跳转 Google 授权页 → 回跳 code → 后端换 `id_token + access_token` → 验 ID Token 拿 `sub`（用户 ID）关联自家用户。**Google 是「标准 OIDC 教科书实现」**——学会了 Google，其他 OIDC 提供商（GitHub、Microsoft）都是同一套流程换参数。

**通用要点**：**回调地址必须在提供商后台注册且精确匹配**（2.1 无通配符）；**第三方账号与本地账号的绑定表**（openid/sub → user_id）；**首次登录建本地账号、再次登录直接关联**；**第三方停用/改绑的兜底**（邮箱验证）。

## 7. JWT SSO vs CAS SSO

两代 SSO 实现方案对比：

| 维度 | JWT SSO | CAS SSO |
|------|---------|---------|
| 凭证形态 | JWT（自包含，验签即用） | TGT/ST（票据，需查 CAS 服务器） |
| 应用侧 | 验签即可（无网络依赖） | 每次校验调 CAS 服务器（验证接口） |
| 状态 | 应用无状态 | CAS 服务器集中会话 |
| 撤销 | 靠 TTL/黑名单 | 撤销票据即全局生效 |
| 适用 | 微服务/多客户端 | 传统 Web 应用集群 |
| 成熟度 | 2026 新项目主流 | 传统企业（Apereo CAS 仍在维护） |

**选型**：新项目、API 型应用 → JWT SSO（验签轻量、无集中依赖）；存量企业、Web 为主 → CAS（集中管控成熟、撤销即时）。两者混合也常见：CAS 做认证中心，签 JWT 给应用验签——认证集中、验证分散。

## 8. 常见坑

**坑一：Token 走 URL 参数**。SSO 回跳带 token 进历史与 Referer——生产用授权码（code 换 token）。

**坑二：前端自己换 token**。SPA 拿 code 自己调 /token——client_secret 暴露在浏览器——换码必须是后端到授权服务器。

**坑三：redirect_uri 通配符**。`*.example.com` 开放回跳——攻击者注册子域截获 code——精确匹配。

**坑四：PKCE 只做一半**。生成了 challenge 忘了验 verifier——两步都要。

**坑五：ID Token 当 Access Token 用**。拿身份证明调资源 API——权限校验失败——各司其职。

**坑六：`state` 参数不校验**。OAuth 回跳的 CSRF——授权发起时生成 state、回跳时校验一致。
