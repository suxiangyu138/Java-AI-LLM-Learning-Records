## 1. 决策框架

2026 年的选型共识已经收敛（多方来源一致），按应用形态对号入座：

| 应用形态 | 推荐方案 | 理由 |
|---------|---------|------|
| 服务端渲染的 Web 应用 | 服务端会话（HttpOnly Cookie） | 即时登出、集中管控、撤销简单 |
| SPA / 移动端 / 纯 API | 短时 access + refresh 轮换 | 无状态验证、跨客户端、体验好 |
| 社交登录 / 企业 SSO | OAuth 2.0/2.1 + OIDC | 协议标准、免自研 |
| 鉴权非核心业务的绿地项目 | 托管身份提供商 | 安全基础设施不自己造 |

**「不要用 JWT 做 Web 应用的会话」是 2026 年的明确共识**——Web 应用要登出生效、要会话审计、要防篡改权限，会话方案全占；JWT 的「无状态」优势在 Web 应用场景用不上，反而背上撤销难的包袱。JWT 的舞台是 **API**：多客户端（Web/移动/第三方）、微服务独立验签、无共享存储的分布式——这些场景会话方案要共享 Redis 才能撑住。

## 2. 两种方案的完整对比

| 维度 | 服务端会话 | JWT |
|------|-----------|-----|
| 状态位置 | 服务端（Redis/DB） | 客户端（令牌内） |
| 撤销 | 删记录，秒级生效 | 难——等过期/拉黑名单 |
| 登出 | 立即生效 | 需要配套（refresh 撤销） |
| 扩展性 | 需要共享存储 | 各服务独立验签 |
| 服务端资源 | 每会话一条存储 | 仅验签 CPU |
| 敏感数据 | 服务端存，客户端无感 | payload 明文可见 |
| 调试 | 查一个存储 | 跨服务翻日志 |
| 典型故障 | 存储故障全掉线 | 验证不一致/时钟偏差 |

关键认知：**「会话不安全、JWT 安全」与「JWT 高性能、会话慢」都是片面结论**——会话把风险集中在基础设施（集中管控、集中杀），JWT 把风险分散到治理（每个服务都要验对）；JWT 省的是「查存储」不是「算签名」。真实泄漏多数来自生命周期治理问题（密钥管理、TTL 不当、日志泄露），不是方案本身。

## 3. 会话方案的正确姿势

选了会话不是躺平——正确姿势清单：**存储用 Redis 不用内存**（多实例共享、重启不丢、TTL 天然）；**会话 ID 登录时轮换**（防会话固定攻击——登录前一个 ID、登录后换新的）；**HttpOnly + Secure + SameSite 全配**（04 篇）；**空闲超时 + 绝对超时双 TTL**（15 分钟空闲踢出、8 小时强制过期是常用基线）；**CSRF 防护**（SameSite 是浏览器侧防线，服务端配同步 Token/双提交 Cookie）；**会话审计**（登录/登出/异常事件留痕）。细节见 [[../../09-Web开发全流程/Cookie%20&%20Session（会话技术）/00-会话技术总览|Cookie & Session 体系]] 的服务端完整实现。

## 4. JWT 方案的正确姿势

选了 JWT 也不轻松——完整姿势清单：**短 access + refresh 轮换**（05 篇）；**RS256 + JWKS**（密钥不分发、可轮换）；**验证五要点**（02 篇：验签 + iss + aud + exp + jti）；**敏感信息不进 payload**；**存储不用 localStorage**（04 篇）；**登出要撤销 refresh**（服务端有状态——JWT 的「无状态」只对 access 成立，refresh 必须有状态管理）。**「JWT 无状态」的正确理解**：access 验证无状态，但整套方案（refresh 存储、黑名单、审计）是有状态的——纯无状态的 JWT 方案在现实中不存在。

## 5. 混合方案

真实系统常常混合——按接口敏感度分层：

**形态一：会话为主 + JWT 子集**——Web 应用用会话登录，对外开放的 API（第三方接入）用独立 JWT（短 TTL + 独立密钥）——两种凭证互不干扰，安全域隔离。

**形态二：JWT 为主 + 会话兜底**——SPA 用双 Token，但敏感操作（改密、转账）要求「最近重新认证」——服务端记录最近认证时间，超时拒绝（step-up auth）。

**形态三：会话 + 内部 API 令牌**——用户态走会话，服务间调用走服务账号 JWT/API Key——两套凭证体系按角色区分，不混用。

**混合的红线**：**同一接口不要同时接受会话与 JWT 两套凭证的「宽松等价」**——要么严格分层（/api/ 只认 JWT、/web/ 只认会话），要么统一到一种——「两套都认」的接口是最容易被绕过的边界。

## 6. 迁移与演进

从会话迁 JWT（或反向）的工程路径：**双写期**——登录同时发会话与 JWT，灰度切换接口；**验证期**——新方案监控：登录成功率、401 率、刷新成功率、重登频次（刷新失败的表现）；**切换期**——按接口/用户灰度，出问题秒回滚；**清理期**——下线旧凭证体系。**迁移的常见翻车点**：旧会话未清理（双写期存储膨胀）；JWT 的时钟偏差（签发与验证服务器时间不一致导致全员 401）；refresh 轮换与多设备冲突（05 篇）；**灰度期间两套凭证的边界漏洞**（混合红线）。

## 7. 常见坑

**坑一：抄流行方案**。「大家都在用 JWT」不是选型理由——按应用形态对号入座。

**坑二：会话方案用内存存储**。重启全掉线、多实例不一致——Redis。

**坑三：JWT 全无状态**。refresh 无状态 = 无法登出/撤销——refresh 必须有状态。

**坑四：混合方案两套都认**。同一接口双凭证宽松等价——被绕过的边界。

**坑五：迁移无灰度**。一次切完翻车无回滚——双写 + 灰度 + 监控。

**坑六：会话固定攻击不防**。登录后会话 ID 不轮换——攻击者可预置会话。

**坑七：忽略「退出登录」的产品语义**。「登出」在会话方案是删记录（秒生效），在 JWT 方案是撤销 refresh + 等 access 过期（分钟级生效）——如果产品要求「登出立即不可用」，JWT 方案要配 access 黑名单或缩短 TTL——选型时把登出语义写进需求，别上线后才发现对不上。
