# 05-双Token模式

## 1. 为什么需要双 Token

单 Token 方案的死结：**TTL 短了体验差**（每 10 分钟重新登录）、**TTL 长了风险高**（令牌泄漏后有效窗口以天计）。双 Token 拆开两个矛盾诉求：

**Access Token（访问令牌）**——短命（5-15 分钟），承载业务请求。泄漏代价可控：就算被偷，有效窗口只有几分钟——「妥协窗口 = access 的 TTL」。

**Refresh Token（刷新令牌）**——长命（7-30 天），唯一职责是换新的 access。平时躺在存储里不出现在业务请求中，攻击面小；配合轮换（每次使用即换新），泄漏能被发现（重用检测）。

分工一句话：**access 保安全（短窗口），refresh 保体验（免重登）**——两者互为缓冲，任何一环失守都有限度。

## 2. TTL 设计

TTL 是安全与体验的旋钮，设计依据场景：

| 场景 | Access TTL | Refresh TTL |
|------|-----------|-------------|
| 金融/支付 | 5 分钟 | 1-7 天 |
| 通用业务 | 15-30 分钟 | 7-14 天 |
| 低敏感内部 | 1 小时 | 30 天 |
| 「记住我」 | 同上 | 30 天 + 会话独立 |

三条纪律：**access 短是安全底线**——敏感 API 5-15 分钟起步（妥协窗口等于 access TTL）；**refresh 长要配轮换**——不轮换的长 refresh 等于单 Token 的长 TTL，泄漏不可发现；**TTL 进配置不进代码**——按业务域差异化（支付接口 5 分钟、查询接口 30 分钟），配置中心统一管理。**「记住我」的实现**：登录时勾选记住 → refresh TTL 30 天；不勾 → refresh 仅当天（或会话 Cookie）——同一套双 Token，按登录选项换 TTL。

## 3. 轮换机制

轮换（Rotation）是双 Token 模式的安全核心——**每次使用 refresh 换新时，旧 refresh 立即作废**：

```javascript
// 刷新请求（客户端视角与 03 篇一致）
// POST /auth/refresh { "refreshToken": "旧" }
// 响应：{ "accessToken": "新", "refreshToken": "新" }  ← 每次都是新对
```

```java
// 服务端视角：轮换的核心逻辑
@PostMapping("/auth/refresh")
public Result<?> refresh(@RequestBody RefreshDTO dto) {
    var record = refreshStore.findByToken(dto.getRefreshToken());
    if (record == null)
        throw new AuthException("无效或已轮换");       // 查不到 = 已作废
    if (record.getStatus() == REUSED) {               // 重用检测（下节）
        refreshStore.revokeFamily(record.getFamilyId());  // 撤销整族
        throw new AuthException("检测到重用，已全部撤销");
    }
    refreshStore.rotate(record);                       // 旧记录标记 REUSED，签发新 token
    return Result.ok(issueNewPair(record.getUserId()));
}
```

轮换的效果：**任何一次 refresh 泄漏，只影响「泄漏后到被使用前」的窗口**——攻击者用一次，新 refresh 到手，但合法用户下一次刷新会撞上「已轮换」错误；**配合重用检测，攻击者的存在本身会被发现**。

## 4. 重用检测

重用检测是轮换的配套——**「已被轮换作废的旧 refresh 再次出现」= 令牌被盗的强信号**：

**检测逻辑**：refresh 每次换新时，旧 token 进入「已使用」状态（Redis/DB 标记）；若「已使用」的 token 再次被提交——重用事件。**处置策略**：不只看这一次——**撤销该令牌的整个「家族」**（Family：同一登录会话签发的一串 refresh，用 family_id 关联），让攻击者与合法用户都重新登录；**记录告警**（用户 ID、IP、设备——审计与异常检测的素材）；**要求重新认证**（重登 + 可选二次验证）。**不做无差别封号**——重用可能是攻击也可能是用户多设备/客户端 bug（如并发刷新未单飞），先撤销家族再观察，误杀重灾区是并发刷新（03 篇单飞是防线之一）。

**撤销的工程实现**：refresh 存储按 family_id 组织——撤销 = 该 family 全部记录标记作废；Redis 存储天然支持（`family_id → 成员列表`，撤销即批量删）。

## 5. 并发与多设备

双 Token 的两个工程难题：

**并发刷新（多 tab/多请求同时过期）**——多个请求同时触发刷新，若不单飞，两个刷新请求带着**同一个旧 refresh** 先后到达：第一个轮换成功，第二个触发「已使用」——**误报重用**！防线：前端单飞（03 篇 refreshing 单例，同窗口只发一次刷新，其余等待）；服务端宽容窗口（同一 refresh 在 1-2 秒内的重复提交视为并发而非重用）；两者都做，双保险。

**多设备登录**——同一账号多设备各自持有 refresh：**轮换互不影响**（各自家族独立）；「踢人」功能 = 按 user_id 撤销该设备的家族（而不是全部设备）；「全部下线」= 撤销该用户所有家族。**会话管理页面**（「在别处登录的设备」列表）就是 refresh 记录的展示——设备名、登录时间、撤销按钮。

## 6. 服务端状态设计

双 Token 模式里 **access 无状态（验签即用），refresh 必须有状态**——refresh 的服务端存储是整套安全机制的地基：

```java
// refresh 记录的最小结构
class RefreshRecord {
    String tokenHash;      // 不存明文（防库泄露直接可用）
    String familyId;       // 家族标识（轮换与撤销的单位）
    String userId;
    String deviceId;       // 多设备管理
    Instant expiresAt;     // 过期时间
    int status;            // ACTIVE / ROTATED / REVOKED
}
```

存储选型：**Redis 首选**——TTL 天然支持（`expiresAt` 即 Redis 过期）、读写快、按 family/user 索引方便；MySQL 可做但查询与过期清理成本高。**三条纪律**：**存哈希不存明文**（库泄露时 refresh 不可直接使用）；**刷新/撤销/重用检测都走同一存储**（状态一致性的唯一来源）；**审计日志另记**（谁、何时、哪台设备刷新了——不放进业务存储）。

## 7. 常见坑

**坑一：refresh 不轮换**。固定 refresh 泄漏不可发现——长 TTL + 不轮换 = 单 Token 的慢性自杀。

**坑二：重用检测误杀并发**。多 tab 同时刷新触发误报——前端单飞 + 服务端宽容窗口双防线。

**坑三：refresh 明文存库**。库泄露 = 全部会话可冒充——存哈希。

**坑四：撤销只撤销单个 token**。攻击者已经轮换拿到新 token——撤销按家族（family_id）。

**坑五：access 太长**。1 小时 access = 1 小时妥协窗口——敏感场景 5-15 分钟。

**坑六：刷新失败静默吞掉**。用户一直拿到 401 却不知道——刷新失败要跳登录 + 提示重新登录。

**坑七：轮换与「记住我」冲突**。「记住我」的 refresh 30 天，轮换后每 15 分钟换新——30 天的「记住」实际靠链条续命，用户两周后回来 refresh 链已断——要么接受（安全优先），要么刷新时检测「接近原签发时间」续期（体验优先），产品决策别默认。
