## 1. 流程全景

一次完整登录的六个环节，前后端协作的边界一目了然：

```text
前端                                      后端
─────────────────────────────────────────────────
登录页 ──POST /auth/login {用户名,密码}──→ 验证 → 签发
  ←──{accessToken, refreshToken}───────
存储（Cookie/内存）                       （存储 refresh 或写库）
  │
API 请求 ──GET /api/orders──→         校验 access（验签+过期）
  │  Authorization: Bearer xxx          ↓
  ←──200 {data}──────────────────── 业务处理
  │
access 过期 ──GET /api/orders──→        返回 401
  │
POST /auth/refresh {refreshToken}──→  验 refresh → 签发新对
  ←──{accessToken, refreshToken}───
重试原请求 ──GET /api/orders──→          200
  │
登出 ──POST /auth/logout──→            撤销 refresh
  清理本地凭证
```

六个环节的职责划分：**登录与刷新是后端认证服务的入口**；**携带是前端请求层的统一职责**（拦截器）；**过期处理是前端请求层与路由层协作**（静默刷新 vs 跳登录）；**登出是双方配合**（前端清本地、后端撤销长时凭证）。

## 2. 登录：换取 Token

前端登录的核心是「表单提交 → 拿到令牌 → 交给存储模块」，业务代码不直接碰存储细节：

```javascript
// auth.js — 认证模块
import api from './api';
import { saveTokens, clearTokens } from './tokenStore';

export async function login(username, password) {
  const { data } = await api.post('/auth/login', { username, password });
  saveTokens(data.accessToken, data.refreshToken);   // 存储细节封装在 tokenStore
  return data.user;
}

export async function logout() {
  try { await api.post('/auth/logout'); } catch { /* 网络失败也要清本地 */ }
  clearTokens();
  window.location.href = '/login';
}
```

三个要点：**存储细节封装**——login 只管换令牌，存 Cookie 还是内存由 tokenStore 决定（04 篇），换存储方案不动业务代码；**登出先清本地**——后端撤销失败（网络断了）也要清本地凭证，否则「登出了还能调 API」；**密码只在登录请求里出现一次**——之后全程令牌，绝不再传密码。

## 3. 携带：每次请求带凭证

「每个请求都带 Token」不能靠手写——用 axios 请求拦截器统一注入：

```javascript
// api.js — axios 实例 + 拦截器
import axios from 'axios';

const api = axios.create({ baseURL: '/api', timeout: 10000 });

api.interceptors.request.use((config) => {
  const token = getAccessToken();          // 从存储取（Cookie 方案则无需手动加）
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});
```

两种携带方式的差异：**Authorization 头**（`Bearer xxx`）——显式、跨域无碍、不自动发送（防 CSRF 天然优势），SPA 推荐；**HttpOnly Cookie**——浏览器自动携带，JS 拿不到（防 XSS），但要处理 CORS 的 `withCredentials` 与 CSRF 防护（04 篇详述）。**拦截器是「一次写好、处处生效」**——新增 API 调用零成本带凭证。

## 4. 过期：401 与刷新

Access Token 过期是常态而非异常——正确处理是「静默刷新 + 重试原请求」，刷新失败才跳登录：

```javascript
// api.js — 响应拦截器：401 统一处理
let refreshing = null;                     // 刷新中标记（防并发重复刷新）

api.interceptors.response.use(
  (resp) => resp,
  async (error) => {
    const { response, config } = error;
    if (response?.status === 401 && !config._retry) {
      if (!refreshing) {
        refreshing = refreshAccessToken()   // 单飞：并发 401 只发一次刷新
          .finally(() => { refreshing = null; });
      }
      try {
        await refreshing;
        config._retry = true;               // 重试标记（防死循环）
        return api(config);                 // 重放原请求
      } catch {
        clearTokens();
        window.location.href = '/login';    // 刷新失败才跳登录
        return Promise.reject(error);
      }
    }
    return Promise.reject(error);
  });
```

设计要点：**并发 401 只刷新一次**（多请求同时过期时，`refreshing` 单例让后续请求等同一个刷新 Promise）；**`_retry` 标记防死循环**（刷新后仍 401 说明令牌真失效，不再重试）；**刷新失败统一跳登录**（业务代码零感知——这是「401 不裸跳登录页」的工程化实现）。

## 5. 登出：清理凭证

登出的完整动作清单：**后端撤销 refresh**（服务端把 refresh 令牌加入黑名单/删除记录——否则「登出后 refresh 还能换新 access」）；**前端清所有本地凭证**（Cookie 要清同名 Cookie——注意 Cookie 的 Domain/Path 必须与设置时一致才能删除）；**清理应用状态**（用户信息、路由守卫的登录态）；**跳登录页**。前端框架里还要处理「登出后其他 tab 的同步」（08 篇多 tab 同步）。

## 6. 后端对照

后端认证服务的最小实现（Java + Spring 视角，完整框架见 [[../../06-Spring全家桶/Spring%20Security与Spring%20Security%20OAuth2/00-Spring%20Security与OAuth2知识体系总览|Spring Security 体系]]）：

```java
@PostMapping("/auth/login")
public Result<?> login(@RequestBody LoginDTO dto) {
    User user = userService.verify(dto.getUsername(), dto.getPassword());
    String access = jwtService.signAccess(user);        // 5-15 分钟
    String refresh = jwtService.signRefresh(user);      // 7-30 天，jti 入库
    return Result.ok(Map.of("accessToken", access, "refreshToken", refresh));
}

@PostMapping("/auth/refresh")
public Result<?> refresh(@RequestBody RefreshDTO dto) {
    if (!refreshService.isValid(dto.getRefreshToken()))  // 校验+轮换检查
        throw new AuthException("refresh 无效或已重用");
    User user = refreshService.consumeAndRotate(dto.getRefreshToken());
    return Result.ok(Map.of("accessToken", jwtService.signAccess(user),
                            "refreshToken", refreshService.issueNew(user)));
}
```

要点：**access 无状态签发（验签即用）**；**refresh 必须有状态管理**（入库/Redis：记录 jti、用户、过期时间——轮换与撤销都靠它）；**登录接口限流**（防爆破）；**密码错误不区分「用户不存在」与「密码错误」**（防账号枚举，09 篇）。

**前端登录页面的工程细节**（常被忽略但体验与安全都相关）：**登录按钮防重复提交**——请求中禁用按钮，避免连点触发两次登录（后端可能生成两个 refresh，旧的一个失效引发困惑）；**错误信息分级**——「密码错误」给用户，「网络异常」给重试，「账号锁定」给等待指引——别把后端错误码原文怼到页面；**记住我选项**——勾选决定 refresh 的 TTL（05 篇）；**回车提交**——form 的 submit 事件而非按钮 click，移动端键盘行为正确；**密码框**——`type="password"` + 自动填充属性正确（`autocomplete="current-password"`），浏览器密码管理器的配合是真实用户习惯。**登录接口的三重防护**：HTTPS 必须（密码明文传输的前提）、限流必须有（09 篇）、错误响应恒定（防枚举）。

## 7. 常见坑

**坑一：401 直接跳登录页**。access 过期是常态——静默刷新重试优先，刷新失败才跳。

**坑二：并发 401 触发 N 次刷新**。无单飞保护——多个请求同时 401 会并发刷新，refresh 轮换后旧 refresh 失效，其他刷新请求 401 连环失败。

**坑三：刷新后不重放原请求**。用户操作丢失——`config._retry` + `api(config)` 重放。

**坑四：登出不清 Cookie**。Cookie 的 Domain/Path 不一致删不掉——与设置时完全一致才可删。

**坑五：密码在请求体明文传输**。登录必须 HTTPS——明文密码走 HTTP 等于裸奔。

**坑六：tokenStore 与业务耦合**。login 里直接 localStorage——换存储方案改业务代码——封装层隔离。

**坑七：刷新接口与业务接口共用实例**。刷新请求也走带 Authorization 的拦截器——access 过期时刷新请求带着旧 token 触发服务端校验失败——刷新请求标记跳过注入或走独立实例（08 篇 `_isAuth` 的分工）。

**坑八：401 与 403 混为一谈**。401 是未认证（去刷新/重登），403 是已认证但无权限（提示无权限，重试无用）——拦截器对 403 直接抛错，别触发刷新链。
