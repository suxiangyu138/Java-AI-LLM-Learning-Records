## 1. Token 家族

「Token」在鉴权语境下是一个家族，四个成员各司其职：

**会话 ID（Session ID）**——服务端状态的无菌凭证：一个随机字符串（约 32 字节），指向服务端会话存储（Redis 等）里的用户状态。它本身不含任何信息，纯粹是「查房的钥匙」。撤销即删记录，秒级生效。

**访问令牌（Access Token）**——自包含的短期凭证（JWT 形态居多）：签发时把用户信息与权限写进令牌，任何服务验签即可信任，无需查存储。TTL 设计 5-15 分钟，过期后凭刷新令牌换新。

**刷新令牌（Refresh Token）**——长时凭证（7-30 天），唯一职责是换新的访问令牌。它不出现在业务请求里，只在 `/auth/refresh` 端点使用，配合轮换机制（每次使用即换新）控制泄漏面。

**ID Token**——OIDC 协议的身份声明凭证（JWT 形态）：证明「用户是谁」，包含姓名、邮箱、头像等身份信息，由授权服务器签发，第三方应用直接信任。

家族分工一句话：**会话 ID 是「状态在服务端」的钥匙，Access/Refresh 是「状态在客户端」的凭证对，ID Token 是「第三方身份」的证明**。

## 2. 本质区别：状态在谁手里

2026 年最重要的认知升级：**session 与 JWT 之争的本质是「认证状态存放在哪」，而不是「用什么传输」**。会话状态在服务端（客户端只有一个不透明 ID），JWT 状态在客户端（服务端不存任何会话，每次从令牌解析）。Cookie 与 Authorization 头只是「怎么送」，与「存哪」是两个正交维度——会话 ID 可以走 Cookie 也可以走 header，JWT 同理。

这个区别派生出一串工程后果：**撤销**——会话秒撤（删存储），JWT 难撤（令牌自证，只能等过期或拉黑）；**扩展**——JWT 让任何服务独立验签（适合微服务与多客户端 API），会话要共享存储（Redis 集中）；**安全**——会话把风险集中在基础设施（集中管控、集中杀），JWT 把风险分散到治理（每个服务都要验对）；**调试**——会话查一个存储即可，JWT 要跨服务翻日志（验证不一致、时钟偏差、JWKS 缓存陈旧）。

**「JWT 更安全」是伪命题**：两者的泄漏都主要来自生命周期与治理问题而非加密强度——选型看场景，不看流行度。

## 3. 2026 基线

**选型共识**（多方来源一致的决策框架）：服务端渲染的传统 Web 应用 → 服务端会话（HttpOnly Cookie）；SPA/移动端/纯 API → 短时 Access Token + Refresh Token 轮换（HttpOnly Cookie 存储）；社交登录/企业 SSO → OAuth 2.0/2.1 + OIDC；鉴权不是核心业务的绿地项目 → 托管身份提供商（Auth0/Clerk/Supabase Auth 等）——「别自己造安全最敏感的基础设施」。

**协议演进**：OAuth 2.1 仍是 IETF 草案（draft-15，2026-03），但方向已定且主流提供商实际执行——PKCE 全客户端必选、重定向 URI 精确匹配、Implicit 授权移除、密码模式移除、刷新令牌轮换强制、Bearer 令牌禁止进 URL 查询串。**RFC 9700（OAuth 2.0 Security BCP）是最可操作的 IETF 文档**——把「我们踩过的坑」浓缩成了规范。

**技术趋势**：Passkeys（WebAuthn）作为抗钓鱼因子全面普及；DPoP（RFC 9449）把令牌绑定到客户端密钥，盗走也没用；**「认证是容易的一半，授权是难的一半」**——越权（BOLA）连续多年占据 OWASP API Top10 榜首，鉴权做完只是开始。

## 4. 解决什么问题

Token 机制解决的核心问题是 HTTP 的无状态性：HTTP 每次请求独立，服务器不记得你——Token 就是「跨请求的记忆」的载体。具体到前后端协作，Token 解决三件事：

**认证闭环**——登录一次，之后的请求都携带凭证，服务器验证凭证即认人；**状态隔离**——前端不需要知道后端会话存储细节（JWT 场景后端也不需要存会话），双方只约定「Token 怎么传、怎么验」；**跨域协作**——前后端分离部署（不同域名），Cookie 受同源限制，Authorization 头无此问题——Token 是分布式前后端的天然选择。

**托管身份提供商的现实**：2026 年绿地项目（鉴权不是核心业务的）越来越多直接选托管方案——Auth0、Clerk、Supabase Auth、WorkOS 等——理由很直白：登录、令牌轮换、MFA、Passkeys、会话管理这些「安全敏感基础设施」自研成本高且容易出错，托管商把成熟的加固方案打包好。本体系的价值在于：**用了托管方案你也要懂底层机制**（对接 OAuth 流程、理解 token 生命周期、排查 401）；而自研方案（本体系核心）的每一层都是面试与架构设计的硬通货。**选型的判断标准**：安全是产品核心卖点 → 自研/深度定制；安全只是成本项 → 托管。

## 5. Token 与 Cookie/Session 的关系

两者不是对立而是搭配：**Cookie 是传输载体，Session 是状态方案，Token 是凭证形态**——「用 Cookie 传会话 ID」「用 Cookie 传 JWT」「用 header 传 JWT」是三种正交组合。细节见 [[../../09-Web开发全流程/Cookie%20&%20Session（会话技术）/00-会话技术总览|Cookie & Session 体系]]（那边讲 Session 机制与 JWT 双 Token 模式的服务端视角），本体系聚焦前端视角的完整闭环。传输出错（CORS、Cookie 属性）的排查见 [[../HTTP%20规范、跨域、状态码、Chrome%20调试工具/04-跨域CORS原理与解决方案|CORS 体系]]。

## 6. 五条边界

**不是加密协议**——JWT 是签名不是加密，payload 人人可读；机密信息不进令牌。

**不做授权**——Token 只证明「你是谁」，权限判定（能不能删这个订单）是授权层的事，BOLA 是 API 安全第一大漏洞。

**不解决 CSRF**——header 传 Token 天然免疫 CSRF，但 Cookie 传 Token 仍需 SameSite 等 CSRF 防护。

**不是唯一凭证**——API Key（机器对机器）、Passkeys（无密码）、短信验证码（短时多因子）各有场景。

**不承担会话全部职责**——登出、踢人、会话审计需要配套机制（轮换、拉黑、审计日志），Token 只是其中一环。
