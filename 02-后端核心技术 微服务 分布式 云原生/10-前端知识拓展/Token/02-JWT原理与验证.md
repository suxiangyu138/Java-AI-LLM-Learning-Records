## 1. 三段结构

JWT 是三个 base64url 编码的 JSON 段用点号连接：`头部.载荷.签名`。随手解一段（jwt.io 在线工具或本地脚本）比背定义有用：

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   ← header（算法声明）
.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6...   ← payload（声明）
.aB3cDeFgHiJkLmNoPqRsTuVwXyZ0123456789   ← signature（签名）
```

**Header**：`{"alg": "HS256", "typ": "JWT"}`——声明签名算法与类型。**Payload**：标准声明（Registered Claims）——`sub`（主体，用户 ID）、`iss`（签发者）、`aud`（受众，目标应用）、`exp`（过期时间）、`nbf`（生效时间）、`iat`（签发时间）、`jti`（令牌唯一 ID）；自定义声明——业务字段（角色、部门）。**Signature**：`HMACSHA256(base64url(header) + "." + base64url(payload), 密钥)`——防篡改的指纹。

理解三段结构的关键：**header 和 payload 只是 base64 编码，不是加密**——任何人拿到令牌都能解码读出全部内容；签名才是安全核心——没有密钥就无法伪造/篡改。

## 2. 签名与验签

两类签名算法，场景分明：

**HS256（对称）**——签发与验证用同一个密钥，快但密钥必须在签发方与验证方共享。适合「单服务自签自验」（单体应用）。

**RS256/ES256（非对称）**——私钥签发、公钥验证。私钥只在授权服务器，公钥通过 JWKS 端点（`/.well-known/jwks.json`）公开分发，任意服务都能验签。适合「一个签发方、多个验证方」（微服务、第三方登录——OIDC 的 ID Token 就是 RS256 家族）。**2026 生产推荐 RS256**：密钥不分发、支持密钥轮换（换公钥即全体生效）、第三方可独立验证。

**验签的工程细节**：公钥从 JWKS 拉取后要缓存（带 TTL）；密钥轮换时新旧公钥并存（JWKS 列表多条目），过期公钥条目的令牌要能过渡验证；**时钟偏差**——签发服务器与验证服务器时间不同步会导致 exp 误判，验证库一般允许几十秒偏差。

## 3. 验证五要点

后端验证 JWT 的完整清单——**签名只是第一关，五要点缺一不可**：

```java
// 以 jjwt 库为例（思路通用）
Jwts.parser()
    .verifyWith(secretKey)          // 1. 验签（密钥来自配置，不是令牌头）
    .requireIssuer("auth-server")   // 2. iss 签发者必须匹配
    .requireAudience("my-app")      // 3. aud 受众必须匹配（防令牌跨应用使用）
    .build()
    .parseSignedClaims(token);      // 4. exp/nbf 过期与生效时间自动校验
// 5. jti 去重：短窗口内同一 jti 出现两次 = 重放，拒绝
```

要点展开：**验签密钥永远来自配置，绝不用令牌 header 里声明的信息**（算法混淆攻击的根源，见下节）；**iss/aud 防「拿 A 应用的令牌调 B 应用」**——签发者与受众不匹配直接拒绝；**exp 校验是安全底线**——过期令牌任何场景不得放行；**jti 是重放检测的载体**——配合 Redis 短窗口去重，防止抓包重放。

## 4. 经典攻击面

JWT 的四个经典攻击，面试与渗透必问：

**`alg:none` 攻击**——攻击者把 header 的 alg 改成 `none` 并去掉签名，部分实现会放行。**防御：算法白名单**——验证库显式指定 `algorithms: ["RS256"]`，绝不信任令牌声明的算法。

**算法混淆攻击（RS256→HS256）**——服务器配的是 RS256（公钥验签），攻击者声明 HS256 并用公钥内容当 HMAC 密钥自签——如果验证库按令牌声明选算法，公钥（公开的！）就成了攻击者的签名密钥。**防御同样是算法白名单**——这解释了为什么「显式固定算法」是 JWT 安全第一铁律。

**`kid` 注入**——header 的 `kid`（密钥 ID）若被当作路径/查询去取密钥，攻击者可注入 `../../etc/passwd` 之类路径。**防御：kid 只作为 JWKS 映射表的键**，绝不当文件路径或数据库查询输入。

**Payload 篡改**——base64 解码改 payload 后重签？没有密钥签不出来——签名挡住篡改，但要先验签再信任内容。

**XSS 窃取**——payload 里的内容在前端渲染时若未转义（`<script>` 注入），JWT 自带的 user 信息就成 XSS 载体——前端渲染令牌里的用户数据同样要转义。

## 5. Payload 纪律

写进 payload 的内容三问：**必要吗**——只放「每次请求都要用的身份信息」（用户 ID、角色），不放可查的数据；**敏感吗**——手机号、身份证、邮箱是 base64 明文，任何人可解码——敏感信息绝不放（要放就换会话方案，或做加密 JWT 但那是另一个协议）；**会过期吗**——角色、权限这类会变的信息放短 TTL 令牌里，别放长 TTL——「用户被降权但令牌里还是管理员角色」是最经典的越权事故。

**最佳实践**：payload 只放 `sub`（用户 ID）+ `role`（或干脆不放角色，每次查库）——身份最小化，权限实时化。会话方案（服务端存状态）天然规避这些问题——这也是「敏感场景用会话」的理由之一。

**验证库的选型与现实**：JWT 验证别手写（签名算法、时钟处理、base64url 细节太多）——用成熟库：Java 用 jjwt 0.12+（2026 主流）、Nimbus JOSE；Node 用 jsonwebtoken / jose（jose 更现代，支持 JWKS 自动拉取）；Python 用 PyJWT。**库的选择要点**：是否内置 JWKS 客户端（RS256 场景必需——自动拉取与缓存公钥）；是否默认校验 exp（部分库需要显式开）；是否允许算法白名单配置（02 篇安全铁律的实现载体）。**「用库」不等于「不用懂」**——库只做验签与解析，iss/aud 校验、jti 去重、密钥轮换这些工程决策仍然是你的事——面试问「验证 JWT 要注意什么」，答案在本文不在库文档。

## 6. 常见坑

**坑一：验签后不验 iss/aud**。签验过了但令牌是别的应用签发的——受众校验缺失，跨应用令牌乱用。

**坑二：算法从令牌头读取**。`alg:none` 与算法混淆的根源——固定白名单。

**坑三：exp 不校验**。库默认可能不验过期——显式开；过期令牌是重放攻击的免费午餐。

**坑四：payload 存手机号**。base64 不是加密——解码即明文。

**坑五：密钥写死在代码/仓库**。HS256 密钥泄露 = 任意令牌可造——密钥走环境变量/密钥管理，定期轮换。

**坑六：长 TTL 装会变的信息**。角色/权限随令牌走 7 天——降权不生效，越权隐患。
