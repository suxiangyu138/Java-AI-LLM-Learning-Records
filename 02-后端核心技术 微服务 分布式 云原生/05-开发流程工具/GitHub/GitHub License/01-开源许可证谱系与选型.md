## 1. 许可证谱系图

```text
更宽松 ←──────────────────────────────→ 更强约束
│                                          │
Public Domain      宽松         弱著佐权      强著佐权       非 OSI
Unlicense        MIT          MPL-2.0      GPL-3.0        SSPL
CC0             BSD-3        LGPL-2.1     AGPL-3.0       Elastic
Apache-2.0
```

| 谱系 | 特征 | 商业影响 |
|------|------|---------|
| 公有领域 | 放弃一切权利 | 完全自由 |
| 宽松（Permissive） | 仅要求保留版权声明 | 可闭源商用，最常见 |
| 弱著佐权 | 修改文件需开源，整体可闭源（文件级） | 库类适用 |
| 强著佐权 | 衍生作品整体必须同许可开源 | 传染全项目 |
| 网络著佐权 | AGPL：**网络服务调用**也视为"分发" | 云服务避雷 |
| 非 OSI | 自定义条款（常针对云厂商） | 商用需单独评估 |

> 🎯 **核心要点**：选型坐标 = "**是否允许别人闭源商用我的代码**"。宽松（MIT/Apache）= 允许；强著佐权（GPL/AGPL）= 要求衍生品开源。没有"既允许闭源又要求开源"的中间态。

## 2. 主流许可证全景对比

| 许可证 | 谱系 | 允许商用 | 允许闭源分发 | 专利授权 | 传染性 | 最适用 |
|--------|------|:---:|:---:|:---:|:---:|--------|
| MIT | 宽松 | ✅ | ✅ | 无 | 无 | **库/小项目/教学，默认首选** |
| Apache-2.0 | 宽松 | ✅ | ✅ | ✅ 显式 | 无 | 中大型项目、企业开源 |
| BSD-3 | 宽松 | ✅ | ✅ | 无 | 无 | 学术/系统软件 |
| MPL-2.0 | 弱著佐权 | ✅ | ⚠️ 文件级 | 隐性 | 文件级 | 浏览器/混合项目（Firefox 系） |
| LGPL-2.1/3.0 | 弱著佐权 | ✅ | ⚠️ 动态链接可 | 3.0 有 | 文件/链接级 | 库（Linux 的 libc 系） |
| GPL-3.0 | 强著佐权 | ✅ | ❌ 必须开源 | ✅ | 全项目 | 强开源理念项目 |
| AGPL-3.0 | 网络著佐权 | ✅ | ❌ 必须开源 | ✅ | 全项目 + 网络 | 服务器软件（防 SaaS 白嫖） |
| Unlicense/CC0 | 公有领域 | ✅ | ✅ | - | 无 | 彻底放弃权利 |

> ⚠️ **LGPL 动态/静态链接的差异**：LGPL 允许**动态链接**下闭源商用（库文件独立分发）；**静态链接**则要求提供重链接手段或开源。这是"Linux 上用 LGPL 库能闭源"的原因。

## 3. 选型流程：choosealicense 三问

| 问题 | 选项 | 推荐 |
|------|------|------|
| ① 希望别人使用你的代码时做什么？ | 只想被使用/贡献 → 宽松；要求改后开源 → 著佐权 | MIT/Apache vs GPL/AGPL |
| ② 社区是否强烈要求特定许可？ | 生态规范（如某些社区默认 MIT） | 跟随社区 |
| ③ 是否希望显式专利授权？ | 项目含专利 → Apache-2.0 | Apache-2.0（显式专利条款） |

```text
决策树（简化版）：
是教学/库/API 客户端？ → MIT
是企业级/含专利？     → Apache-2.0
是服务器软件怕 SaaS 白嫖？ → AGPL-3.0
是强开源理念的全栈项目？ → GPL-3.0
想彻底放弃权利？       → Unlicense / CC0
默认没想法？           → MIT（生态最广，兼容性最好）
```

| 决策陷阱 | 说明 |
|----------|------|
| "没写许可证 = 允许用" | ❌ 默认**保留所有权利**，商业使用有法律风险 |
| "CC BY-NC 用于代码" | CC 系列**不适合代码**（非 OSI），且 NC 限制商用 |
| "引用 MIT 库的项目必须开源" | ✅ 只有**分发衍生代码**才受约束；内部使用不受影响 |
| "GitHub 检测到 MIT 就安全" | 检测 ≠ 法律确认；文件内容被改动时 Licensee 只给"相似度" |

## 4. SPDX 标识符

SPDX（Software Package Data Exchange）是许可证的标准标识体系：

| 示例 | 含义 |
|------|------|
| `MIT` | MIT 许可证 |
| `Apache-2.0` | Apache 2.0 |
| `GPL-3.0-only` | GPL 3.0（仅本版本） |
| `GPL-3.0-or-later` | GPL 3.0 或更高版本 |
| `MIT OR Apache-2.0` | 二选一（双许可） |
| `NOASSERTION` | 无法确认（GitHub API 用） |

> 💡 **Licensee 的已知限制**：检测引擎**不解析 SPDX 表达式**（`GPL-3.0-only` vs `or-later` 无法区分）——需要精确语义时以 LICENSE 文件文本与 SPDX 列表为准。

## 5. 非 OSI 许可证（云厂商条款）

| 许可证 | 背景 | 关键条款 | 风险 |
|--------|------|---------|------|
| SSPL（MongoDB） | 防云厂商白嫖 | 提供 SaaS 需开源**管理平台代码** | 非 OSI；与 GPL 不兼容 |
| Elastic License | Elasticsearch 改许可 | 禁止提供托管服务（部分条款） | 非 OSI |
| BUSL（Business Source） | 商业源码过渡 | 变更许可时间后开放 | 非 OSI |
| 自定义 EULA | 商业软件 | 按合同 | 无法用标准工具扫描 |

> ⚠️ 依赖里出现非 OSI 许可证时：CI 的 `deny-licenses` 列表要显式加黑名单（如 SSPL-1.0），因为 Licensee/API 可能返回 `OTHER`，漏过默认白名单。

## 6. 核心要点

> 🎯 **核心要点**：
> - 谱系坐标：宽松（允许闭源）↔ 强著佐权（要求开源）↔ 网络著佐权（SaaS 也传染）↔ 非 OSI（自定义条款）；
> - 默认选择：无特殊需求选 MIT；企业含专利选 Apache-2.0；防 SaaS 白嫖选 AGPL；
> - 没有 LICENSE = 保留所有权利，不是免费；
> - SPDX 是标准标识，`only`/`or-later`/`OR` 表达式 Licensee 不解析；
> - 非 OSI 许可证（SSPL/Elastic）要在合规白名单外显式黑名单。
