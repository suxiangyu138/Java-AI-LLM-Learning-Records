## 1. 兼容性矩阵

"兼容" = 两个许可证的代码能否合并分发（组合作品的许可条件可同时满足）：

| 新代码许可 | 可合并 MIT | 可合并 Apache | 可合并 GPL-3 | 可合并 AGPL | 可合并 SSPL |
|-----------|:---:|:---:|:---:|:---:|:---:|
| MIT 项目 | ✅ | ✅ | ⚠️ 合并后整体 GPL | ⚠️ 合并后整体 AGPL | ❌ |
| Apache 项目 | ✅ | ✅ | ⚠️ 合并后整体 GPL | ⚠️ 合并后整体 AGPL | ❌ |
| GPL 项目 | ✅ | ✅ | ✅ | ❌ | ❌ |
| 闭源项目 | ✅ | ✅ | ❌ | ❌ | ❌ |

| 规则 | 说明 |
|------|------|
| 宽松兼容一切 | MIT/Apache 代码可并入任何项目（保留版权声明） |
| 强著佐权向下兼容 | GPL 项目可并入 MIT/Apache 代码，合并品整体 GPL |
| 传染方向 | **强著佐权传染宽松**，反之不传染 |
| 不兼容对 | GPL ↔ AGPL（合并有争议，一般避免）、SSPL 与一切 OSI 许可 |
| 双许可 | `MIT OR Apache-2.0` 同时满足任一即可 |

> 🎯 **核心要点**：兼容性判断 = "合并后的整体许可证能否同时满足所有组成部分的义务"。宽松代码进 GPL 项目没问题；GPL 代码进宽松项目是违规。

## 2. GPL 传染的精确边界

### 2.1 触发条件：分发（distribution）

```text
传染触发 = 修改/链接 GPL 代码 + 向第三方分发
不触发 = 内部使用（含内部 SaaS）/ 个人使用
```

| 场景 | 传染？ | 说明 |
|------|:---:|------|
| 内部系统用 GPL 库 | ❌ | 未分发 |
| 给客户交付含 GPL 代码的软件 | ✅ | 需整体开源 |
| 开源软件里链接 GPL 库 | ✅ | 整体转 GPL |
| 进程间通信（独立进程） | ❌（通常） | 视为独立作品 |
| 插件体系（明确 API 边界） | ⚠️ 争议 | 按司法实践与分发方式定 |

### 2.2 链接形式与传染

| 形式 | 判定 |
|------|------|
| 静态链接 | 视为衍生作品，传染 |
| 动态链接 | 通常视为衍生作品，传染（GPL 下与 LGPL 不同） |
| 复制源码到项目 | 明确传染 |
| 命令行工具调用 | 通常不算衍生 |

> ⚠️ **动态链接的 GPL vs LGPL 差异**：GPL 库动态链接**也传染**；只有 LGPL 才允许"动态链接闭源"。

## 3. 商用场景四问

| 问题 | 判定 | 动作 |
|------|------|------|
| ① 依赖树里有没有 GPL/AGPL/SSPL？ | SCA 扫描 | 有 → 评估传染路径 |
| ② 我们的分发形态是什么？（交付二进制/源码/SaaS） | 分发 vs 内部 | SaaS 关注 AGPL |
| ③ 强著佐权依赖能否替换/隔离？ | 依赖治理 | 换许可/进程隔离/商购双许可 |
| ④ 谁拍板？ | 法务 + 工程 | 自动扫描给事实，法务给结论 |

```text
商用合规决策流：
依赖扫描 → 有强著佐权？
  ├─ 无 → 常规署名义务即可
  ├─ 有且分发 → ① 替换依赖 ② 整体开源该项目 ③ 购买商业双许可
  └─ 有且仅内部使用 → 记录备案（无需动作）
```

## 4. 高频场景裁决表

| 场景 | 结论 |
|------|------|
| 闭源项目引用 MIT/Apache 库 | ✅ 合法（保留版权声明即可） |
| 闭源项目引用 GPL 库（静态链接）并分发 | ❌ 违规，必须开源 |
| 闭源 SaaS 引用 AGPL 库 | ❌ 违规（网络分发也算） |
| 闭源 SaaS 引用 GPL 库（非 AGPL） | ✅ 内部使用不传染 |
| 引用 SSPL（MongoDB）提供 SaaS | ⚠️ 需开源管理平台代码或商用许可 |
| 修改了 MIT 库但不公开 | ✅ 允许（MIT 无公开义务） |
| 修改了 GPL 库但不公开 | ❌ 分发时必须开源修改 |
| 项目是 MIT，有人 Fork 后转 GPL | ✅ 允许（fork 者选择自己的许可） |
| 用 MIT 代码做了付费闭源产品 | ✅ 允许（MIT 最核心的意义） |

> 🎯 **核心要点**：记住三组对立——**MIT=随便用**、**GPL=分发必须开源**、**AGPL=网络服务也必须开源**。所有裁决都从这三条推导。

## 5. NOTICE 与署名义务

| 许可证 | 署名要求 | 说明 |
|--------|---------|------|
| MIT/BSD | 版权声明保留 | 分发时带 LICENSE 文件或版权段 |
| Apache-2.0 | 版权 + **NOTICE 文件**（如有） | 修改需显著声明（第 4b 条） |
| MPL | 文件头 | 修改文件保留 MPL 头 |
| GPL 系 | 版权 + 提供对应源码 | 分发时附源码或书面要约 |

```text
NOTICE 文件（Apache 项目规范）：
Apache License 2.0 要求：若上游提供 NOTICE，衍生分发必须保留其内容
（NOTICE 不是版权声明替代品，是额外署名）
```

> ⚠️ **署名坑**：去掉上游 NOTICE 文件 = 违反 Apache-2.0 条件（虽然很少被起诉，但合规审计会亮红）。

## 6. 核心要点

> 🎯 **核心要点**：
> - 兼容方向：宽松可并入一切；强著佐权只进更强/同级；SSPL 与 OSI 全不兼容；
> - GPL 触发 = 修改/链接 + 分发；AGPL 触发 = 网络服务；内部使用永远不触发；
> - 商用四问：扫描 → 分发形态 → 隔离/替换 → 法务裁决；
> - 高频裁决背三句：MIT 随便用、GPL 分发开源、AGPL 网络开源；
> - NOTICE/署名是"条件"不是"建议"，审计会查。
