## 1. 合规问题的本质

消费开源依赖的风险矩阵：

| 风险 | 场景 | 后果 |
|------|------|------|
| 许可证冲突 | 引入 GPL 库到闭源项目 | 衍生代码被迫开源 |
| 许可证未知 | 依赖无 LICENSE 或无标准文本 | 法律灰色地带 |
| 条款变化 | 依赖升版换了许可证（AGPL 化） | 沉默违规 |
| 传染性传递 | 传递依赖（transitive）含强著佐权 | 间接传染 |

> 🎯 **核心要点**：合规不是"看主依赖"，是**看整棵依赖树**——传递依赖的许可证同样传染。工程上必须把合规做成 **PR 门禁**，而不是发布前人工检查。

## 2. Dependency Review Action：PR 门禁

```yaml
# .github/workflows/dependency-review.yml（示例）
name: 'Dependency Review'
on:
  pull_request:
    paths: ['**/pom.xml', '**/package-lock.json', '**/requirements.txt']  # 依赖变更才触发

permissions:
  contents: read
  pull-requests: write

jobs:
  dependency-review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/dependency-review-action@v4
        with:
          deny-licenses: AGPL-1.0, AGPL-3.0, GPL-2.0-only, GPL-3.0-only, SSPL-1.0
          fail-on-severity: high          # 同时拦高危漏洞
          comment-summary-in-pr: on-failure
```

| 配置项 | 作用 |
|--------|------|
| `deny-licenses` | 黑名单：引入即拦截（强著佐权/非 OSI） |
| `allow-licenses` | 白名单：仅允许列出的许可证 |
| `allow-dependencies-licenses` | 指定依赖的例外（CI 工具类依赖） |
| `fail-on-severity` | 联动漏洞等级拦截 |
| 数据源 | GitHub Advisory Database + Open Source Insights API 解析许可证 |

> 💡 **落地要点**：设为 main 分支的 **required status check**；加 `paths` 过滤避免无关 PR 排队；新增黑名单许可证时先评估再启用。

## 3. GitHub 许可证合规产品（2026）

GitHub OSPO（开源项目办公室）2026-07 公开其内部策略并产品化：

| 能力 | 说明 |
|------|------|
| 与 Dependency Graph + Dependabot 集成 | 依赖清单直接驱动扫描 |
| 500+ SPDX 标识符 | 覆盖主流与长尾许可证 |
| 自定义/模糊许可证识别 | 启发式 + ML（配合 ScanCode 工具链） |
| 策略即代码 | `approved`/`restricted` 分类、双许可处理、传染性继承检测 |
| PR 差异内展示 | 合并前在 PR diff 直接标许可证警告 |
| SBOM 生成 | CycloneDX 格式机器可读 |

> ⚠️ 该产品定位是**辅助治理**：自动扫描解决"发现"，策略分类解决"决策"，人工法务保留"争议裁决"。别把自动判定当法律结论。

## 4. Dependabot 的边界

| 能力 | Dependabot 是否提供 |
|------|:---:|
| 漏洞扫描与自动 PR | ✅ |
| 依赖版本更新 | ✅ |
| **许可证合规检查** | ❌（原生不支持） |
| SBOM 生成 | ❌（需其他工具） |
| 传递依赖完整覆盖 | ⚠️ 部分（版本更新为主） |

> ⚠️ **常见误解**：Dependabot 管"安全和版本"，不管"许可证"——后者用 Dependency Review Action 或 [04](#3-github-许可证合规产品2026) 的合规产品补位。

## 5. 第三方 SCA 工具对比

| 工具 | 许可证扫描 | 漏洞扫描 | SBOM | 定位 |
|------|:---:|:---:|:---:|------|
| Dependabot | ❌ | ✅ | ❌ | GitHub 原生、免费 |
| Dependency Review Action | ✅ | ✅（联动） | ❌ | PR 门禁 |
| GitHub 合规产品 | ✅ | ✅ | ✅ | 企业治理 |
| Snyk | ✅ | ✅ | ✅ | 开发者友好、订阅制 |
| Mend（WhiteSource） | ✅ | ✅ | ✅ | 企业级策略 |
| Trivy | ✅ | ✅ | ✅ | 开源、容器优先 |

| 选型建议 | 场景 |
|----------|------|
| 小团队/个人 | Dependabot + Dependency Review Action（免费够用） |
| 中大型团队 | 加 Snyk 或 GitHub 合规产品（策略与审计） |
| 强监管行业 | SCA + SBOM 导出 + 定期人工审计 |

## 6. SBOM 与审计

```text
SBOM（软件物料清单）: 描述"软件由哪些组件构成"的标准清单
格式：CycloneDX（最流行）/ SPDX
用途：合规审计、漏洞追溯、供应链透明度
```

| 生成方式 | 工具 |
|----------|------|
| GitHub 合规产品 | 自动生成（CycloneDX） |
| 开源 | `syft`、`trivy sbom`、`cyclonedx-maven-plugin` |
| 企业 | Snyk/Mend 导出 |

```bash
# 例：trivy 生成 SBOM
trivy fs --format cyclonedx --output sbom.json .

# 例：trivy 扫描许可证
trivy fs --scanners license . --license-full
```

## 7. 合规流程落地清单

| # | 步骤 | 工具 |
|---|------|------|
| 1 | 建立许可证策略（白名单/黑名单/特批流程） | 团队文档 + 代码仓库 |
| 2 | PR 门禁接入 | Dependency Review Action + required check |
| 3 | 定期全量扫描存量依赖 | trivy / Snyk / 合规产品 |
| 4 | 传递依赖专项核查 | SCA 工具的 transitive 报告 |
| 5 | SBOM 生成与归档 | CI 内生成、制品库归档 |
| 6 | 双许可/无许可依赖人工裁决 | 法务 + OSPO 流程 |
| 7 | 依赖升级触发重新评估 | Dependabot PR 联动合规检查 |

## 8. 核心要点

> 🎯 **核心要点**：
> - 合规看**整棵依赖树**，传递依赖同样传染；
> - 免费标准组合 = Dependabot（版本/漏洞）+ Dependency Review Action（许可证门禁）；
> - Dependabot 本身**不做许可证合规**——这是最高频的误解；
> - 2026 GitHub 合规产品提供策略即代码 + SBOM（CycloneDX）+ PR 内警告；
> - 落地顺序：策略 → 门禁 → 存量扫描 → SBOM 归档 → 人工裁决兜底。
