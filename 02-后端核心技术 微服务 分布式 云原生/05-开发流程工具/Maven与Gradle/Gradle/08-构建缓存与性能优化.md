## 1. 三大复用层次与配置缓存

Gradle 通过四个层次避免重复构建工作：

```text
① 增量构建：任务 inputs/outputs 未变 → UP-TO-DATE 跳过
② 本地缓存：跨工作区/分支复用任务输出（无需网络）
③ 远程缓存：跨团队/CI 复用任务输出（如 Develocity）
④ 配置缓存：复用配置阶段输出，跳过配置执行（独立于①②③）
```

四层分工：①②③ 复用"任务执行结果"，④ 复用"配置阶段结果"——大型项目配置占 50%+ 时间，④ 的收益常被低估。**四层全开的项目 vs 全关的项目，构建时间差一个数量级**。

## 2. 配置缓存：跳过配置阶段

```properties
org.gradle.configuration-cache=true
```

配置缓存把配置阶段的输出（任务图、脚本编译结果）缓存为二进制，下次构建直接加载——**配置阶段从"执行脚本"变成"读缓存"**。

9.6 的重大改进：**属性精确追踪**——即使通过 `-D` 系统属性、`ORG_GRADLE_PROJECT_*` 环境变量或 gradle.properties 传入不同值，只要配置阶段没读取该属性，缓存条目即可复用（9.1 支持 `-P`、9.4 支持 properties 文件、9.6 全覆盖）。CI 场景收益最大：不同参数构建共享配置缓存。

**配置缓存的纪律**：配置阶段不读外部状态（文件、环境变量、时间）；读的话要声明为输入（`providers` 或 `inputs`）；任务配置保持惰性（07 篇 Provider 是前提）。排查：`--configuration-cache` 报告问题条目，日志明确提示"哪个属性读取破坏了可缓存性"。

## 3. 本地缓存与远程缓存

```properties
org.gradle.caching=true                    # 本地缓存
# 远程缓存（org.gradle.caching.http 或 Develocity 插件）
```

- **本地缓存**：`~/.gradle/caches/build-cache-1` 存任务输出，跨工作区/分支复用（切分支后未变模块直接 FROM-CACHE）
- **远程缓存**：CI 与开发者共享——CI 构建的产物，开发者本地直接复用（反之亦然），团队"永远不重复构建同一件事"

启用与验证：`--build-cache` 命令行或 gradle.properties；执行日志看 `FROM-CACHE` 状态。**远程缓存的安全**：制品在缓存服务传输，企业内用 Develocity/私有缓存服务，公网场景注意访问控制。

## 4. 缓存失效的根因分析

缓存命中率上不去，先查根因：

| 失效原因 | 典型场景 | 修复 |
|----------|----------|------|
| 易变输入 | 时间戳、构建号、随机数进 inputs | 去掉或声明为无关输入 |
| 绝对路径 | 本机路径进 inputs | 用相对路径/布局 API |
| 重叠输出 | 多任务写同一文件 | 输出隔离 |
| 配置阶段读外部 | 读文件/环境变量 | Provider 化 + 声明输入 |
| 任务依赖漂移 | dependsOn 动态计算 | 固定依赖图 |

**诊断工具**：Build Scan 的 Cacheability 过滤器区分可缓存/不可缓存任务；FROM-CACHE 过滤器看成功命中；`--info` 日志显示未命中原因（`CACHED_INPUTS_CHANGED` 等）。Develocity 的 Build Caching Optimizer（2026.2 GA）用 AI 代理自动做根因分析 + 最小修复 + PR 提交——基于 Build Scan 数据解决 4/4 场景（纯日志 AI 只能 0/4）。

## 5. 增量编译与 kapt → KSP

- **Java 增量编译**：9.x 下源码或 classpath 变化只重编译受影响类——大项目全量编译时间降到增量级别
- **Kotlin 增量编译**：Kotlin 插件自带增量（受编译选项影响，关闭 flag 会退化为全量）
- **kapt → KSP**：kapt（Kotlin 注解处理）不兼容增量且慢，KSP 快 2 倍以上且支持增量——新注解处理项目直接用 KSP（Room、Dagger、DataBinding 等都有 KSP 处理器）

```kotlin
plugins {
    id("com.google.devtools.ksp") version "2.1.0-1.0.29"   // 替代 kapt
}
dependencies {
    implementation("androidx.room:room-runtime:2.7.0")
    ksp("androidx.room:room-compiler:2.7.0")               // 而非 kapt
}
```

## 6. Ephemeral CI 优化实战

临时 CI 环境（每次构建全新容器）的官方基准（Spring Boot 项目，基线 31.5 秒）：

| 优化 | 做法 | 效果 |
|------|------|------|
| 缓存 modules-2 | 持久化 `~/.gradle/caches/modules-2` | 22.7s（省 28%），最大单项收益 |
| 共享只读依赖缓存 | `GRADLE_RO_DEP_CACHE` 挂只读共享 | 与可写性能一致，免锁竞争 |
| 缓存 jars-9 | 处理/插桩 JAR 缓存 | 无单独收益，随 GRADLE_USER_HOME 免费获得 |
| 配置缓存 | 见第 2 节 | CI 参数多变场景收益最大 |

核心：**CI 里持久化 GRADLE_USER_HOME**（依赖缓存 + 构建缓存 + 配置缓存一次搞定）；Ephemeral 环境用 `GRADLE_RO_DEP_CACHE` 共享只读依赖缓存免锁竞争。

## 7. 性能诊断：Build Scan 与报告

```bash
./gradlew build --scan        # 生成 Build Scan（gradle.com 可观测性）
./gradlew build --profile     # 本地 HTML 阶段报告
./gradlew build --info        # 详细日志（缓存命中状态）
```

Build Scan 看什么：**配置 vs 执行耗时占比**（配置 >50% → 配置缓存/惰性优化）；**任务耗时 Top**（哪个任务最贵）；**缓存命中/未命中**（未命中看原因）；**每个配置步骤成本**（脚本编译/插件构建/模型配置）。性能优化的正确顺序：**先扫描定位，再针对性优化**——不要凭感觉调参数。

## 8. Develocity：企业级加速体系

Develocity（2026.1/2026.2）的 Universal Cache 覆盖构建全生命周期：

| 组件 | 缓存对象 | 典型收益 |
|------|----------|----------|
| Setup Cache | 配置阶段输出（脚本编译/依赖访问器/共享逻辑） | 配置时间缩短约 50% |
| Artifact Cache | 依赖构件下载 | AndroidX 案例 44m20s → 2m49s |
| Build Cache | 任务与转换输出 | 跨团队复用 |
| Test Distribution | 远程代理并行测试 | 测试时间大幅下降 |
| Predictive Test Selection | 只跑受影响测试 | 回归成本骤降 |

其他能力：Build Scan 可观测性、Analytics 跨团队指标（缓存命中率/构建时间趋势）、Develocity MCP Server 自然语言查询（"哪些模块拖慢构建"）、Build Caching Optimizer AI 代理（2026.2 GA）。**注意**：Build Cache Node 组件支持 2026-12-31 结束，官方建议迁移到 Develocity Edge。
