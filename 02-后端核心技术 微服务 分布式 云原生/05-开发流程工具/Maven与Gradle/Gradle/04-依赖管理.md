## 1. 仓库与坐标：兼容 Maven 体系

依赖坐标沿用 Maven 约定：`group:artifact:version`，仓库也兼容 Maven 中央仓库与私有仓库（Nexus/Artifactory）。

```kotlin
repositories {
    mavenCentral()                          // Maven 中央仓库
    maven { url = uri("https://repo.example.com/maven") }  // 私有仓库
    google()                                // Android 场景
}

dependencies {
    implementation("com.google.guava:guava:33.4.0-jre")
}
```

**与 Maven 的兼容意味着**：依赖坐标、仓库格式、制品结构完全互通——Maven 项目引 Gradle 制品、Gradle 项目引 Maven 制品都没问题。差异在解析策略（Gradle 默认按"最新版本"仲裁，Maven 按"最先声明"）与动态版本支持（Gradle 支持 `+`、`latest.release` 但生产不推荐）。

## 2. 配置（Configuration）：依赖的作用域

配置（configuration）是 Gradle 的依赖作用域概念，理解它是依赖管理的钥匙：

| 配置 | 语义 | 对应 Maven |
|------|------|-----------|
| implementation | 编译与运行都需要，不暴露给消费者 | compile |
| api | 暴露给消费者（library 模块） | compile（旧） |
| compileOnly | 仅编译（注解处理器） | provided |
| runtimeOnly | 仅运行 | runtime |
| testImplementation | 测试编译与运行 | test |
| annotationProcessor | 注解处理器 | — |

```kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web:3.4.0")
    compileOnly("org.projectlombok:lombok:1.18.36")
    annotationProcessor("org.projectlombok:lombok:1.18.36")
    testImplementation("org.junit.jupiter:junit-jupiter:5.11.4")
}
```

**api vs implementation 的工程意义**：library 模块用 api 把依赖暴露给使用者，用 implementation 则隐藏——隐藏可减少消费者的编译类路径与传递依赖爆炸（"依赖隔离"是 Gradle 优于 Maven 的工程点之一）。**配置名拼错是最常见的报错**：`dependencies` 块里的配置必须在插件声明的配置集合内（java 插件提供上述配置，`implementation` 写成 `implemntation` 直接报错）。

## 3. 传递依赖与冲突仲裁

传递依赖（传递性依赖）由 Gradle 自动解析，冲突仲裁规则：

- **默认策略：版本最高者胜（newest）**——Maven 是"最先声明者胜"，这是两者解析差异的核心
- 仲裁后可通过 `dependencyConstraints`/`resolutionStrategy` 覆盖

```kotlin
configurations.all {
    resolutionStrategy {
        failOnVersionConflict()               // 冲突直接失败（严格模式）
        force("org.slf4j:slf4j-api:2.0.16")    // 强制版本（最后手段）
    }
}
```

**冲突排查三连**：`./gradlew dependencies --configuration compileClasspath` 看树；`dependencyInsight --dependency <name>` 看某个依赖为何是这个版本；找到冲突源后**优先升级自己声明的版本或加依赖约束**，`exclude` 是最后手段（会连带排除传递功能）。

## 4. 依赖约束与 BOM 平台

- **依赖约束（constraints）**：不直接引入依赖，只约束"如果出现则用这个版本"——适合统一管理传递依赖版本

```kotlin
dependencies {
    constraints {
        implementation("org.slf4j:slf4j-api:2.0.16")  // 传递依赖出现 slf4j 时强制此版本
    }
}
```

- **平台（platform）**：Maven BOM 的 Gradle 对应物，`implementation(platform("org.junit:junit-bom:5.11.0"))` 引入 BOM 批量管理版本；Spring Boot 的 `spring-boot-dependencies` BOM 同样适用。声明"作为平台导入"与"作为依赖导入"语义不同，生产库用 `platform` 引入 BOM 而不是直接依赖。

## 5. 版本目录：libs.versions.toml

版本目录（Version Catalog）是 9.x 推荐的依赖管理方式——把版本集中到 `gradle/libs.versions.toml`：

```toml
[versions]
guava = "33.4.0-jre"
junit = "5.11.4"

[libraries]
guava = { group = "com.google.guava", name = "guava", version.ref = "guava" }
junit-jupiter = { module = "org.junit.jupiter:junit-jupiter", version.ref = "junit" }

[bundles]
test = ["junit-jupiter", "mockito-core"]

[plugins]
spring-boot = { id = "org.springframework.boot", version = "3.4.0" }
```

```kotlin
dependencies {
    implementation(libs.guava)
    testImplementation(libs.bundles.test)
}
```

价值：**版本单一来源**（升级只改一处）、**类型安全访问器**（libs.xxx 自动补全）、**跨模块共享**（settings 里声明，多模块统一消费）。9.0 的 init 支持 Maven 项目转换时自动生成版本目录。

## 6. 依赖锁定与版本一致性

- **依赖锁定（dependency locking）**：把解析结果固定到 lockfile，保证"今天构建的依赖 = 明天构建的依赖"

```bash
./gradlew dependencies --write-locks    # 生成/更新锁定文件
# gradle.lockfile 提交到 Git
```

- **动态版本的风险**：`latest.release`/`1.+` 每次解析可能不同——CI 缓存与本地不一致是"构建漂移"的根源；生产项目要么锁定、要么固定版本
- **reproducible 意识**：9.0 起可复现归档默认（字节级一致），配合锁定实现完全可复现构建

## 7. 依赖分析排查

| 命令 | 用途 |
|------|------|
| `./gradlew dependencies` | 完整依赖树（按配置） |
| `./gradlew dependencyInsight --dependency guava` | 单依赖的来源与版本决策 |
| `./gradlew dependencyUpdates`（插件） | 检测可升级版本 |
| `./gradlew dependencies --write-locks` | 生成锁定文件 |

排查流程：先看树（谁引入了问题依赖）→ dependencyInsight（为什么是这个版本）→ 决策（升级自己声明 / constraints / 最后 exclude）。**不要盲删依赖**——删除前确认没有代码引用，删除后跑全量测试。

## 8. 依赖安全与供应链

2026 年依赖管理的重要维度是供应链安全：

- **漏洞扫描**：OWASP Dependency-Check / Snyk / 平台扫描集成到 CI——依赖版本升级前先扫漏洞
- **锁文件 + SBOM**：依赖锁定（第 6 节）是供应链可审计的基础；SBOM（软件物料清单）导出依赖清单供审计（CycloneDX 插件）
- **私有仓库治理**：企业依赖统一走私有 Nexus/Artifactory（代理公共仓库 + 制品管控），禁止直连公共仓库的随意拉取
- **传递依赖信任链**：`dependencies` 树里的每个传递依赖都在信任范围内——**减少依赖数量本身是安全策略**，一个 100 行工具库依赖链上可能有 20 个包

```kotlin
// 供应链防护示例：CycloneDX SBOM 生成
plugins {
    id("org.cyclonedx.bom") version "2.0.0"
}
// ./gradlew cyclonedxBom → bom.xml（SBOM 审计用）
```

依赖治理三问：这个依赖真的需要吗？它传递了什么？它的版本是否在漏洞库覆盖范围内？——三问过后再写 dependencies。记住一个原则：**依赖是负债不是资产**——每个依赖都带来版本仲裁成本、漏洞暴露面与升级维护负担，能用 JDK/标准库解决的场景优先少引依赖，这是大型项目依赖膨胀失控的第一道防线。

依赖管理的执行顺序建议：**先锁定策略后写依赖**——仓库配置（私有代理优先）、版本目录建立、锁定开关确认，然后再逐条写 dependencies。很多团队依赖混乱的根源不是不会写，而是"先写了再说"，冲突与漏洞靠事后排查——把依赖策略前置到模板仓库（05 篇约定插件里固化仓库与锁定配置），新模块零成本继承正确策略。
