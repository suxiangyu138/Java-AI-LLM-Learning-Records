## 1. 安装三选：直接装 / Wrapper / IDE 内置

```text
方式一：直接安装（本机开发）
  ├── SDKMAN（推荐，Linux/macOS/WSL）：sdk install gradle
  ├── 包管理器：brew install gradle / scoop install gradle
  └── 手动解压：下载 zip → 配置 GRADLE_HOME + PATH

方式二：Wrapper（项目内，核心方式）
  任意有 gradlew 的项目：./gradlew build
  首次运行自动下载对应版本 Gradle 到用户目录

方式三：IDE 内置
  IDEA/VS Code 自动识别 build.gradle.kts 并下载 Gradle
```

推荐组合：**本机装一个 Gradle 用于 `gradle init` 生成项目，项目内一律用 Wrapper**。团队成员的机器不需要装 Gradle——git clone 后直接 `./gradlew` 即可。验证安装：`gradle -v` 显示版本与 JVM 信息。

## 2. Wrapper：Gradle 工程的基石

Wrapper 是 Gradle 的版本固定启动器，工程里包含四个文件：

```text
gradlew / gradlew.bat      # 启动脚本（Unix/Windows）
gradle/wrapper/gradle-wrapper.jar     # 下载器
gradle/wrapper/gradle-wrapper.properties  # 版本声明
```

```properties
# gradle-wrapper.properties
distributionUrl=https\://services.gradle.org/distributions/gradle-9.6.0-bin.zip
```

**Wrapper 的价值**：团队成员与 CI 用同一版本构建（消除"我本地能过"的版本差异）；升级版本只改 properties 一处（`./gradlew wrapper --gradle-version 9.6.0`）；9.5 起支持下载重试（`retries` / `retryBackOffMs` 属性），解决 CI 不稳定网络的下载失败。

**工程纪律**：gradlew、gradle-wrapper.jar、gradle-wrapper.properties 必须提交到 Git（.jar 是二进制也要提交，否则 CI 无法下载）；distributionUrl 指定确切的 -bin/-all 版本，不要用动态版本。

## 3. 第一个 Kotlin DSL 构建

```kotlin
// build.gradle.kts
plugins {
    java
    application
}

group = "com.example"
version = "1.0.0"

repositories {
    mavenCentral()
}

dependencies {
    testImplementation(platform("org.junit:junit-bom:5.11.0"))
    testImplementation("org.junit.jupiter:junit-jupiter")
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

application {
    mainClass = "com.example.MainKt"
}

tasks.test {
    useJUnitPlatform()
}
```

```bash
gradle init          # 交互生成项目（选择 Kotlin DSL + Java）
./gradlew build      # 完整构建（编译+测试+打包）
./gradlew run        # 运行应用（application 插件）
./gradlew test       # 只跑测试（DAG 按需执行）
```

第一个构建就体现两个 Gradle 特征：**插件即能力**（java/application 插件带来编译、测试、打包全套任务）与**声明即配置**（repositories/dependencies 是标准声明式块）。

## 4. Java 工具链管理

Java 工具链（toolchain）解决"项目需要 JDK 21，本机只有 JDK 17"的痛点：

```kotlin
java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)   // 声明项目目标 JDK
        vendor = JvmVendorSpec.ADOPTIUM                 // 可选：指定发行版
    }
}
```

机制：Gradle 自动检测已安装 JDK；找不到时**自动下载**（需要配置 toolchain 仓库）或报错提示安装。工具链的价值：**构建不依赖本机 JDK**——CI 和本地环境差异不影响构建结果；多版本项目（不同模块不同 JDK）各模块独立声明。

工具链位置（9.x）：`org.gradle.java.installations.auto-download` 控制自动下载；已装 JDK 的发现路径可用 `org.gradle.java.installations.paths` 指定。

## 5. Gradle Daemon 与构建进程

Gradle 默认以 **守护进程（Daemon）** 方式运行：首次构建启动一个常驻 JVM，后续构建复用——省去 JVM 启动与类加载开销，这是 Gradle 快的另一个原因。

```text
Daemon 机制：
├── 首次构建：启动 daemon（几秒成本）
├── 后续构建：复用 daemon（快）
├── 闲置超时：默认 3 小时回收
└── 管理：./gradlew --stop 停止所有 daemon
```

注意：**daemon 缓存的是 JVM 与类加载，不缓存构建结果**——构建缓存（08 篇）才负责任务输出复用。CI 场景建议关闭 daemon（`--no-daemon`）或设置短超时，避免容器里残留守护进程；`GRADLE_OPTS` 可调 daemon 内存（大项目 `-Xmx4g` 起）。

**首次构建 vs 后续构建的体验差异**是初学者最常见的困惑：首次构建（下载 Gradle + 依赖 + 启动 daemon）可能几分钟，第二次构建秒级——这是"下载与预热"成本，不是 Gradle 慢。判断一个构建"是否正常快"的标准：依赖与 Wrapper 已缓存的前提下，纯增量构建时间应远小于首次。CI 里第一次构建慢是常态，所以 CI 缓存持久化（09 篇）才是关键，而不是怀疑工具。

**国内网络场景**：Gradle 发行版与依赖下载走 services.gradle.org 与 Maven Central，国内可能慢或超时——解法：发行版用阿里云镜像（`distributionUrl` 换成 mirrors.aliyun.com 的 gradle 分发地址）、依赖仓库加阿里云 maven 镜像（`maven { url = uri("https://maven.aliyun.com/repository/public") }`）、GRADLE_USER_HOME 缓存持久化。镜像配置写进模板仓库，团队一致受益。

## 6. 环境变量与配置优先级

Gradle 配置来源的优先级（高 → 低）：

```text
命令行（-P 属性 / --option） > gradle.properties（项目根） 
> ~/.gradle/gradle.properties（用户级） > 系统环境变量 > 默认值
```

常用设置（gradle.properties）：

```properties
org.gradle.jvmargs=-Xmx4g -XX:MaxMetaspaceSize=1g   # daemon 内存
org.gradle.caching=true                              # 开启构建缓存
org.gradle.configuration-cache=true                  # 开启配置缓存
org.gradle.parallel=true                             # 并行构建
```

环境变量里最常用：`GRADLE_USER_HOME`（缓存与 Wrapper 下载位置，CI 里持久化它即缓存依赖）、`ORG_GRADLE_PROJECT_xxx`（注入项目属性）。9.6 起配置缓存对 `-D`/环境变量/`gradle.properties` 属性的读取精确追踪——只要配置阶段没读该属性，不同值也可复用缓存（08 篇展开）。

## 7. 常见报错速查

| 错误 | 原因 | 解法 |
|------|------|------|
| Could not find or load main class | application 插件 mainClass 未配 | 设置 mainClass 或按 Kotlin 类名规范 |
| Could not resolve dependencies | 仓库缺依赖/网络不通 | 检查 repositories、换国内镜像（阿里云 maven 镜像） |
| Gradle version X required | Wrapper 版本与插件不兼容 | 升级 Wrapper 或插件版本 |
| Unable to start daemon | 内存不足/端口占用 | 调 org.gradle.jvmargs、--stop 后重试 |
| Configuration cache problems | 配置阶段读外部状态 | 见 08 篇惰性纪律 |

排错顺序固定：**先环境（JDK/网络/内存）后代码（脚本语法/插件版本）**——Gradle 报错信息通常精确到任务与行号，读日志比猜快。`--stacktrace` 展开完整栈，`--info` 看细节，`--debug` 是最后手段。若报错信息指向"依赖下载失败"，八成是网络问题而非配置问题——先用 curl 试仓库地址，再查镜像配置。入门阶段把"读报错、查环境、跑通一次真实构建"三件事做完，比刷十篇教程都有用。
