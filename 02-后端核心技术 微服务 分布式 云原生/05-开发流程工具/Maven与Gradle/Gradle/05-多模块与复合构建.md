## 1. settings.gradle.kts：多模块的入口

```kotlin
// settings.gradle.kts
rootProject.name = "my-platform"

include("app", "common:core", "common:utils", "services:order", "services:user")
```

```text
项目结构：
├── settings.gradle.kts      # 根设置（模块声明、插件管理、版本目录）
├── build.gradle.kts         # 根构建（公共配置）
├── gradle/libs.versions.toml
├── app/                     # 可执行模块
├── common/core/             # 公共库模块
└── services/order/          # 业务模块
```

settings 文件职责：声明模块（include）、插件管理（pluginManagement）、版本目录声明、复合构建（includeBuild）。**settings 在初始化阶段最先执行**——模块结构在配置阶段之前确定，运行时增删模块不支持（除非重新构建）。

## 2. 多模块结构设计

两种主流结构：

```text
按层拆：app（入口）+ common（通用）+ services（业务）+ storage（存储）
按域拆：order-service + user-service + product-service（每个域自治）
```

设计原则：**模块粒度适中**（太细 → 构建图开销大，太粗 → 复用差）；**依赖单向**（业务层 → 服务层 → 存储层，禁止循环）；**入口最小**（app 模块只做装配，业务逻辑在库模块）。微服务场景的模块化 + 独立部署需求，用复合构建更合适（第 5 节）。

**模块间依赖**：

```kotlin
// app/build.gradle.kts
dependencies {
    implementation(project(":services:order"))   // 模块依赖
    implementation(project(":common:core"))
}
```

模块依赖 `project(...)` 在本地构建时直接编译依赖模块（增量 + 缓存友好），发布后自动转为坐标依赖——这就是"开发期用源码、发布期用制品"的 Gradle 默认行为。

## 3. 约定插件：共享构建逻辑

约定插件（convention plugins）是多模块工程化的核心实践：把"每个模块都要配置的东西"抽成插件。

```kotlin
// build-logic/conventions/src/main/kotlin/java-conventions.gradle.kts
plugins {
    java
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}

tasks.withType<Test>().configureEach {
    useJUnitPlatform()
    maxHeapSize = "1g"
}
```

```kotlin
// 各模块只写一行
plugins {
    id("java-conventions")
}
```

```text
约定插件 vs 根 build.gradle.kts 公共配置：
├── 根配置（allprojects/subprojects）：全局生效，隐式依赖，难排查
└── 约定插件：显式声明（每个模块自己 apply），可组合可传参，类型安全
```

**9.5 新增**：预编译 Settings 约定插件获得类型安全 Kotlin 访问器——settings 级约定（插件仓库、版本目录默认值）也能享受 IDE 补全与编译检查。约定插件是"团队规范代码化"的载体：java 约定、测试约定、发布约定各一个插件，按模块组合。

## 4. buildSrc vs 约定插件 vs 复合构建

三者都用于共享构建逻辑，适用场景不同：

| 方案 | 机制 | 适用 |
|------|------|------|
| buildSrc | 根目录的隐藏构建，编译共享类与脚本 | 单仓库内共享（构建逻辑规模小） |
| 约定插件（build-logic） | includeBuild 引入的插件构建 | 单仓库内共享（推荐，可演进） |
| 复合构建（includeBuild） | 引入独立构建（插件或其他项目） | 跨仓库共享、依赖未发布的本地项目 |

**推荐路线**：约定插件（build-logic 目录 + includeBuild）是当前主流——buildSrc 会强制重建全部模块（改动一次全量重编译），约定插件按需加载；跨仓库场景再用复合构建引入。规模再大（多团队多仓库共享插件）→ 发布插件到私有仓库（06 篇）。

## 5. 复合构建：组合独立构建

复合构建（composite builds）让多个**独立构建**组合为一个，执行时统一调度：

```kotlin
// settings.gradle.kts
includeBuild("../shared-libs")          // 引入独立构建
includeBuild("../deployment-tools")     // 引入工具构建
```

价值场景：**本地开发依赖未发布的库**（用源码构建替代坐标，改完即生效）；**微服务本地联调**（多个服务 + 公共库一起构建）；**插件开发测试**（用 includeBuild 引入插件构建做集成验证）。复合构建之间通过项目路径依赖引用，构建缓存跨构建共享（命中即复用）。

## 6. 模块间版本共享

- **版本目录全局共享**：settings 里声明版本目录（默认 gradle/libs.versions.toml），所有模块 `libs.xxx` 引用——多模块版本统一的核心手段
- **统一 group/version**：根 build.gradle.kts 或约定插件统一设置 group 与 version，避免各模块漂移
- **平台 BOM 共享**：library 模块用 `api(platform(...))` 暴露 BOM，消费者模块自动继承版本管理

```kotlin
// 根 build.gradle.kts
allprojects {
    group = "com.example"
    version = "1.0.0"
}
```

版本统一的目标：**一处改版本、全模块生效、无版本漂移**——版本目录 + 统一 group/version + BOM 三层配合实现。

## 7. Isolated Projects 方向

Isolated Projects（隔离项目）是 Gradle 的架构方向：**每个项目的配置相互隔离**——当前多模块构建中，所有模块的构建脚本在同一进程配置（改动一个模块的配置会影响整体，配置缓存也受全局影响）。

- 现状：未进入 9.0（优先产品化配置缓存，即其前置条件），计划在后续 9.x 推进
- 目标：模块配置独立执行 → 配置阶段并行化 + 缓存更细粒度 + 平台兼容性
- 对开发者的意义：理解方向即可——9.x 内继续用约定插件 + 配置缓存，Isolated Projects 生效后配置性能再上一个台阶

多模块工程的演进路径建议：**单体 → 多模块 → 多仓库 → 复合构建**按需演进，不要一步到位。判断信号：构建时间超 5 分钟（考虑约定插件与缓存优化而非拆仓）、单仓库内业务模块互不相关（考虑拆独立仓库）、多个独立仓库频繁联调（考虑复合构建）。**结构演进跟着痛点走**——过度设计的多模块比单模块更痛苦。

一个实际的多模块坑：**模块间隐式依赖**——A 模块代码直接用了 B 模块的类但没在 dependencies 里声明 project(":B")，本地构建靠 IDEA 的模块依赖能过，CI 干净构建直接编译失败。排查姿势：干净 clone 后 `./gradlew clean build` 全量验证；预防姿势：CI 每次在干净工作区构建 + 开启 `--strict-dependencies`（严格模式检查未声明依赖）。这是"本机能过 CI 挂"的典型来源之一，与 Wrapper 版本问题并列多模块工程两大首坑。
