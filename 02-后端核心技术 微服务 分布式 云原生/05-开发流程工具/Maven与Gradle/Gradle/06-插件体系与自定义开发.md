## 1. 插件分类与生命周期

Gradle 插件按来源分三类：

- **核心插件**：随 Gradle 发布（java、application、base、maven-publish 等），无需版本号
- **社区/生态插件**：独立发布（Spring Boot、Shadow、KSP），`plugins {}` 块声明版本
- **本地/自定义插件**：buildSrc、约定插件、includeBuild 引入

```kotlin
plugins {
    java                      // 核心插件：无版本
    id("org.springframework.boot") version "3.4.0"   // 生态插件：带版本
}
```

插件生命周期：**应用（apply）时注册任务与扩展（extension）**——插件的 `apply()` 在配置阶段执行，创建任务、扩展与默认配置。插件的幂等性：同一插件重复 apply 会报错（除非显式声明）。

## 2. pluginManagement：插件版本管理

settings.gradle.kts 的 pluginManagement 统一管理插件仓库与版本：

```kotlin
pluginManagement {
    repositories {
        gradlePluginPortal()                        // 官方插件门户
        maven { url = uri("https://repo.example.com/plugins") }  // 私有插件仓库
    }
    resolutionStrategy {
        eachPlugin {
            if (requested.id.id == "org.springframework.boot") {
                useVersion("3.4.0")                  // 统一版本
            }
        }
    }
}
```

工程价值：**插件版本单一来源**（各模块 plugins 块不再写版本，settings 统一）；**私有插件仓库**（企业内部分发）；**版本目录的 plugins 块**（libs.versions.toml 里声明插件版本，模块 `alias(libs.plugins.spring.boot)`）。9.x 惯例：插件版本写在 settings（pluginManagement）或版本目录，模块里只写 id。

## 3. 核心插件速查

| 插件 | 提供 | 适用 |
|------|------|------|
| java | compile/test/jar + 配置集合 | 所有 JVM 项目 |
| java-library | api/implementation + 元数据 | 库模块 |
| application | run + 启动脚本 + 可执行分发 | 可执行程序 |
| base | build/clean/assemble/check 生命周期 | 通用 |
| maven-publish | 发布到 Maven 仓库 | 库/制品发布 |
| signing | 制品签名 | 发布到中央仓库 |

组合使用：java-library + maven-publish（库项目标准组合）、application + distribution（可执行项目）。核心插件不依赖 Gradle 版本号——能力随 Gradle 升级，这就是"9.x 新特性直接可用"的原因。

## 4. 生态插件：Spring Boot / Shadow / KSP

| 插件 | 场景 | 关键能力 |
|------|------|----------|
| org.springframework.boot | Spring Boot 项目 | bootJar 可执行 fat jar、依赖管理 BOM |
| com.github.johnrengelman.shadow | 通用 fat jar | 合并依赖为单一可执行 jar（非 Spring 场景） |
| com.google.devtools.ksp | Kotlin 注解处理 | kapt 的替代（快 2 倍+、增量支持） |
| com.diffplug.spotless | 代码格式化 | 统一格式 + 检查门禁 |
| com.github.ben-manes.versions | 依赖升级 | dependencyUpdates 检测可升级版本 |
| io.gitlab.arturbosch.detekt | Kotlin 静态分析 | 质量门禁 |

生态插件选择原则：**优先官方/大厂维护**（Spring Boot 官方、Google KSP）；**版本与 Gradle 兼容**（插件市场的 Gradle 兼容列——插件版本与 Gradle 版本有对应关系，9.x 下用旧插件可能报错）；**KSP 已替代 kapt**（新 Kotlin 注解处理项目直接用 KSP）。

## 5. 自定义插件开发

```kotlin
// build-logic/conventions/build.gradle.kts
plugins {
    `java-gradle-plugin`
    kotlin("jvm")
}

gradlePlugin {
    plugins {
        create("my-conventions") {
            id = "com.example.my-conventions"
            implementationClass = "com.example.MyConventionsPlugin"
        }
    }
}
```

```kotlin
// MyConventionsPlugin.kt
class MyConventionsPlugin : Plugin<Project> {
    override fun apply(project: Project) {
        project.plugins.apply("java")
        project.extensions.create("myConfig", MyConfigExtension::class.java)

        project.tasks.register("greeting") {
            doLast { println("Hello from my conventions!") }
        }
    }
}
```

插件开发三件套：**java-gradle-plugin 插件**（提供插件 DSL 与自动测试支持）、**Plugin<Project> 接口**（apply 入口）、**扩展（extension）**（`extensions.create` 暴露配置，用户 `myConfig {}` 块配置）。自定义插件的两种形态：约定插件（本仓库工程化，05 篇）与独立插件（发布分发）。

## 6. 插件发布与消费

```kotlin
// 插件构建的发布配置
plugins {
    `maven-publish`
}

gradlePlugin {
    website = "https://github.com/example/my-plugin"
    vcsUrl = "https://github.com/example/my-plugin.git"
}

publishing {
    repositories {
        maven { url = uri("https://repo.example.com/plugins") }
    }
}
```

发布三步：`publish` 任务发到私有仓库 → 消费者在 pluginManagement 配置该仓库 → 消费者 `plugins { id("...") version "x" }` 使用。**发布到 Gradle Plugin Portal**（全球分发）需要申请与审核；企业内部用私有仓库即可。插件的发布与消费链路与 Maven 制品一致（maven-publish + 仓库），只是多了 pluginManagement 声明。

## 7. 插件开发的最佳实践

1. **懒配置**：任务用 `register`，扩展用 `Property`/`Provider`（07 篇），避免配置阶段做实际工作
2. **命名规范**：插件 id 用反向域名（com.example.xxx），避免与 Gradle 内部前缀冲突
3. **功能测试**：`java-gradle-plugin` 提供 GradleRunner（TestKit）做集成测试——插件改动要有测试兜底
4. **版本兼容矩阵**：声明最低 Gradle 版本（`gradlePlugin {}` 或文档），9.x 破坏性变更（Kotlin 2/Groovy 4）可能要求插件适配
5. **文档与迁移说明**：插件升级要写 changelog，特别是破坏性变更

## 8. 插件与 Gradle 版本兼容

插件与 Gradle 版本存在兼容矩阵，9.x 时代尤其需要注意：

- **9.0 破坏性变更**：最低 Java 版本提升、移除废弃 API、升级 Kotlin 2/Groovy 4、采用 JSpecify——旧插件可能无法在 9.x 运行
- **检查姿势**：Gradle Plugin Portal 的插件详情页标有"Gradle compatibility"列；升级 Gradle 前先跑 `./gradlew plugins` 与 `./gradlew validatePlugins` 检查
- **升级顺序**：先升级插件到支持 9.x 的版本，再升级 Gradle——顺序反了会得到"插件不兼容"的报错
- **约定插件同理**：仓库内约定插件升级 Kotlin 版本要与 Gradle 内置 Kotlin 兼容（9.x 内置 Kotlin 2.x）

一句话纪律：**Gradle 大版本升级 = 插件兼容性审计先行**。遇到不兼容插件，查其 changelog 的 9.x 适配版本，无维护的插件考虑替代品或自研（第 5 节）。

插件生态选型的另一个维度：**插件即构建规范**——团队用 spotless（格式）+ detekt（静态分析）+ cyclonedx（SBOM）把质量与供应链要求插件化，比"每人自觉遵守"可靠。插件化的规范随构建脚本进版本库、进 CI 门禁，评审从"口头提醒"变成"构建失败"——这是 Gradle 生态对工程治理的最大贡献，也是面试里"为什么团队要自研约定插件"的答案。

自研插件前先问三个问题：**现成插件能满足吗**（生态里大概率有）；**逻辑会被多模块复用吗**（单模块用脚本块就够了）；**维护成本谁承担**（插件是长期资产，要有负责人与测试）。判断标准：同一个逻辑写第三遍的时候，才是抽插件的时机——过早抽象与永不抽象同样有害，这个分寸感是插件开发的成熟标志。

补一个实战细节：约定插件里给任务挂接 `doLast` 钩子**不会被执行阶段的 `--dry-run` 尊重**——dry-run 只模拟任务图不执行任务体，所以"验证插件逻辑"要用真实构建 + `--rerun-tasks` 强制重跑（否则 up-to-date 跳过看不到效果）。插件开发的测试闭环：TestKit 功能测试（真实构建）+ 单元测试（扩展逻辑）+ 真实项目冒烟——三层都过才算插件可发布。
