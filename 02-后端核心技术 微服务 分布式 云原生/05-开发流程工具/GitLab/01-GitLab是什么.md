## 1. DevOps 平台：不是代码托管

**GitLab（2011 年诞生）的定位一句话：一体化 DevOps 平台**——**"从写代码到上线的所有工具，一个产品全包"**。它诞生于"工具链割裂"的痛点：代码在 GitHub、CI 在 Jenkins、扫描在 SonarQube、制品在 Nexus——**每个环节换一个工具 = 权限、数据、上下文全断**。GitLab 的答案：**SCM（代码托管）+ CI/CD（流水线）+ DevSecOps（安全）+ 制品库 + 监控 + AI 助手全部内置**——"**GitHub 是仓库，Jenkins 是流水线，SonarQube 是质量——GitLab 是'一个平台全包'**"。**它的核心哲学**：**单一数据源（single source of truth）**——**代码、流水线、MR、安全报告的上下文在同一处**——MR 里能看到"这条代码的测试结果 + 安全扫描 + 覆盖率"，不用跳五个系统。**诞生背景**：2011 年 Dmitriy Zaporozhets 起步时只有代码托管，2013 年加入 CI 后走向一体化——"**一体化的方向在 2013 年就定了**"。

## 2. 五大能力域

**GitLab 的能力分五域**：**① 代码托管（SCM）**——Git 仓库、分支保护、MR 评审（02/06 篇）；**② CI/CD**——.gitlab-ci.yml 声明式流水线、Runner 调度、制品与缓存（03-05 篇）——**核心价值域**；**③ DevSecOps**——SAST/DAST/依赖扫描/容器扫描内置（07 篇）；**④ 制品库**——Container Registry/Package Registry/CI/CD Catalog（08 篇）；**⑤ AI 助手（Duo）**——代码生成、CI Expert 生成流水线、Data Analyst 查指标（2026 主线）。**学习 GitLab 的顺序就是这五域的展开**——"**先会托管与 CI/CD，再谈安全与制品，最后用 AI 提效**"。**五域的协同价值**：一个 MR 从"代码提交"到"合并上线"走过的路——**SCM 提供仓库与 MR、CI/CD 提供流水线、DevSecOps 提供扫描、制品库提供镜像、Duo 提供 AI 辅助**——五域在 MR 页面汇合（06/07 篇）——"**五域不是五个功能，是一条链的五段**"。

## 3. 2026 现状与版本基线

**2026-08 基线：GitLab 19.2（2026-07-16 发布）**。2026 的关键版本：

| 版本 | 时间 | 主线 |
|------|------|------|
| 19.2 | 2026-07-16 | **受治理的智能体自动化**：依赖扫描自动修复（beta）、Security Review Flow（beta）、Duo CLI（GA）、Custom Flows（GA） |
| 19.1 | 2026-06 | 开发者摩擦降低：Duo 密钥误报常开、Code Owner 自动分配 |
| 19.0 | 2026-05-21 | **Secrets Manager**（beta）、Developer Flow、CI/CD Catalog 分析、SBOM 供应链可见性 |
| 18.11 | 2026-04 | **CI Expert Agent**（beta 自动生成流水线）、Data Analyst Agent（GA） |

**2026 主线一句话**："**平台 + AI 双轮：CI/CD 从'手写 YAML'走向'智能体生成 + 自动修复'，但 YAML 语法与流水线概念仍是地基**"——**AI 生成的流水线也要人 review，学会语法才能 review AI**（03-04 篇）——**19.x 是 2026 年度主线，18.x 仍是存量常见版本——学习资料注意版本标注**。

## 4. 三种形态

**GitLab 的三种交付形态**：**GitLab.com（SaaS）**——官方托管，**小团队/个人最省事**（免费额度够用，托管 Runner 开箱即用）；**Self-Managed（自托管）**——**企业内网部署**（Omnibus 包/Docker/K8s，09 篇运维）——**数据合规 + 完全掌控**——"**GitLab 的立身之本就是私有化**"；**GitLab Dedicated**——**单租户托管**（云厂商隔离实例）——大企业合规要求。**选型主线**：**"小团队 SaaS 起步，合规/内网自托管，超严合规 Dedicated"**——"**SaaS 省运维，自托管省合规焦虑，Dedicated 是两者的折中**"；**自托管的前提**：有运维人力与内网基础设施——"**没有运维团队，别选自托管**"（09 篇运维成本）。

## 5. GitLab vs GitHub vs Gitee

| 维度 | GitLab | GitHub | Gitee |
|------|--------|--------|-------|
| 定位 | 一体化 DevOps 平台 | 开源协作 + 代码托管 | 国内合规托管 |
| CI/CD | ⭐ 内置（强） | Actions（生态广） | 弱 |
| 安全扫描 | ⭐ 内置（SAST/DAST） | 需 marketplace 集成 | 弱 |
| 私有化 | ⭐ 成熟（Self-Managed） | 仅 Enterprise 服务端 | 支持 |
| 开源生态 | 中 | ⭐ 全球最大 | 国内镜像/社区 |
| AI | Duo（平台内置） | Copilot（生态） | 少 |
| 适用 | 企业内网/一体化 | 开源项目/公网 | 国内合规/中文 |

**选型主线**：**开源项目 GitHub（生态最大）、企业内网 GitLab（一体化 + 私有化）、国内合规 Gitee（中文 + 备案友好）**——"**GitLab 与 GitHub 不是竞争关系，是两种哲学：一体化的企业平台 vs 生态化的开源社区**"（GitHub 专精体系交叉：`../GitHub/01-GitHub平台完全指南.md`）。

## 6. 版本节奏与升级策略

**GitLab 的版本节奏**：**月度发布**（每月 22 号，大版本每年 2-3 个：17.x → 18.x → 19.x）——**版本号 X.Y，X 是年度主线，Y 是月度**。**版本号语义**：**19.2 的 19 是年度主线（2026 年）、2 是月度**——"**大版本每年 +1（17→18→19），小版本每月 +1**"。**升级策略三个要点**：其一，**别跳大版本**（升级路径有要求：如 18 → 19 直接升级可能失败，**按官方升级路径逐版本走**——09 篇）；其二，**小版本（Y）升级低风险**（月度修复/特性，**测试环境先升**）；其三，**大版本升级前读升级说明**（破坏性变更清单——如 19.0 的权限/行为变更）——"**月度节奏 = 频繁小升 + 年度大考**"。**安全补丁**：严重 CVE 出 **patch 版本**（如 19.2.1），**安全团队关注 security releases 邮件**。

## 7. 生态位置与五条边界

**生态位置**：GitLab 是**企业级 DevOps 平台的事实标准**——尤其"**代码与流水线同仓库**"的哲学被广泛认可（GitHub Actions 也效仿）；**MR-First 工作流**（06 篇）是它的协作名片。**一句话定位**："**Git 是引擎，GitLab 是整车——从提交到上线的每一站都在一个平台里**"。

**五条边界**：其一，**GitLab 不替代 Git**——底层还是 Git，`git push/clone/rebase` 照旧（Git 体系交叉）；其二，**GitLab CI 不替代 Jenkins 的一切**——**存量 Jenkins 插件生态（特定构建工具/私有协议）仍有价值**，"迁移是渐进不是推倒"（CI/CD 体系交叉）；其三，**GitLab 不是云平台**——部署到 K8s 靠 GitOps/CI（05 篇），**不负责运行你的应用**；其四，**免费版（Free）有功能边界**——安全扫描/Secrets Manager 部分要 Premium/Ultimate（07 篇）——"**功能表先看版本，再看文档**"；其五，**AI 能力是辅助不是权威**——Duo 生成的代码/流水线**要人 review**（AI 治理是 2026 主题，19.2 的 AI 审计事件）；其六，**GitLab 不替代团队规范**——分支策略/评审规则/门禁阈值是团队定的，GitLab 只是执行器——"**平台提供机制，规范靠团队**"（06 篇）。
