## 1. DevSecOps：安全左移

**DevSecOps 的哲学一句话：安全是流水线的一部分，不是上线前的一道检查**——"**扫描在合并前，不在上线后**"。**传统流程的痛点**：安全团队在发布前做渗透测试——**发现漏洞 → 打回 → 修 → 重测——发布延期 + 修复成本高（上线后修 bug 的成本是开发时的 10 倍）**。**DevSecOps 的答案**：**每次 MR 自动跑安全扫描**——**开发者在合并前看到"我的代码引入了漏洞"**——**安全责任从安全团队下沉到开发者**（安全左移 = shift left）。**GitLab 的内置安全能力**（Ultimate 版）让"安全工具链割裂"消失：**扫描结果直接进 MR**（不用跳 SonarQube/独立扫描平台）——"**GitLab 的安全卖点不是扫描器多强，是'扫描结果与代码评审同处一屏'**"。

## 2. 扫描家族：SAST / DAST / 依赖 / 容器

**GitLab 的四类内置扫描**：**SAST（静态应用安全测试）**——**不运行代码**，扫描源码找漏洞模式（SQL 注入/不安全反序列化）——**合并前必跑**（快，每 MR 都扫）；**DAST（动态应用安全测试）**——**运行应用后扫描**（真实请求打接口找漏洞）——**部署后跑**（慢，发布前/定期）；**依赖扫描（Dependency Scanning）**——**扫描依赖库的已知 CVE**（SBOM 清单比对漏洞库——**19.0 的供应链可见性**）；**容器扫描（Container Scanning）**——**扫描镜像基础层漏洞**（镜像 push 时扫）。**2026 的增强**（19.2）：**依赖扫描自动修复（beta）**——**发现漏洞包自动开 MR 升级修复，升级坏了构建自动迭代修复方案**——"**扫描从'报告问题'走向'自动修复'——2026 安全智能化的代表**"。

## 3. 安全门禁：不安全的代码进不了 main

**扫描的落地靠"门禁"**——**GitLab 的 Security Approval Policies**：**扫描发现 critical 级漏洞 → MR 自动被阻止合并**（或要求安全角色批准才能合并）：

```yaml
# .gitlab/security-policies/policy.yml
approval_policy:
  rules:
    - type: scan_finding
      scanners: [sast, dependency_scanning]
      severity_levels: [critical, high]     # 高危以上
      vulnerability_states: [newly_detected]  # 新引入的漏洞
  actions:
    - type: require_approval                # 必须安全批准
```

**门禁的三条纪律**：其一，**只卡"新引入"的漏洞**（`newly_detected`——**存量漏洞另排期修，别让历史债阻塞所有 MR**）；其二，**扫描结果进 MR 页面**（开发者看到"哪行代码引入什么漏洞"——**修复有上下文**）；其三，**误报处理**（`vulnerability management` 里标记误报/豁免——**别为了消灭红点把门禁关了**）——"**门禁是'安全政策的执行器'：政策写在 YAML 里，执行在合并前**"。

## 4. 变量安全：Masked / Protected / 文件变量

**CI 变量的安全三件套**：**Masked（打码）**——**变量值在流水线日志中自动打码**（`***`——防密钥泄露进日志——**任何密钥变量必开**）；**Protected（保护）**——**变量只在保护分支的流水线中可用**（main/release 流水线能用，**feature 分支的 MR 流水线拿不到**——**防"恶意 MR 打印密钥"攻击**）；**File 变量**——**以文件形式注入**（`$CI_PROJECT_DIR/.env` 挂载——**工具要读文件路径的场景**）。**攻击场景**（为什么要 Protected）：**攻击者开一个 MR，在 script 里 echo $DEPLOY_KEY——如果不 Protected，密钥直接打出来**——"**Masked 防'不小心打印'，Protected 防'恶意打印'——两层都要**"。

## 5. Secrets Manager（19.0）

**GitLab Secrets Manager（19.0 引入，beta，Premium/Ultimate）**——**把凭证管理收进平台**：**在 GitLab 里存密钥**（`gitlab-secrets:create` 等），**job 按需获取**（`secrets: - name: DEPLOY_KEY`），**带审计日志**（谁在哪个 job 用了哪个密钥——**合规要求**）。**与外部 KMS 集成**：**HashiCorp Vault / AWS Secrets Manager / Azure Key Vault / GCP Secret Manager**——**已有 KMS 的组织直接集成**（GitLab 只做"作用域 + 审计"层）。**与 CI 变量的对比**：**CI 变量是"静态注入"**（配置时就定），**Secrets Manager 是"运行时获取 + 审计"**（谁用了有记录）——"**2026 的凭证治理：小团队 CI 变量（Masked + Protected）够用，合规组织上 Secrets Manager/KMS 集成**"。

## 6. 权限与审计

**安全运维的权限与审计**：**权限最小化**（02 篇五级角色 + **组权限继承**——"**一个人能给的最小权限就是最合适的权限**"）；**管理员账号单独管理**（root 账号不开 2FA 是事故——**强制 2FA 政策**）；**审计事件**（Admin → Audit Events：谁改了权限/删了项目/动了设置——**合规留痕**）；**19.2 的 AI Audit Event**（**AI 辅助操作也记审计事件**——"AI 时代合规的新维度"）；**安全仪表盘**（安全团队的漏洞看板：按项目/严重度聚合——**安全治理的数据基础**）。**零信任实践**：**Personal Access Token 短时效 + 最小 scope**（02 篇）、**部署密钥与个人密钥分离**（部署用专用 deploy key）——"**权限与审计是安全的'制度层'：扫描防技术漏洞，权限防人的漏洞**"。

## 7. 2026 新能力：自动修复与 AI 审计

**2026 的安全主线是"智能化"**：**19.2 依赖扫描自动修复（beta）**——发现漏洞包 → **自动开 MR**（升级到修复版本）→ 升级导致构建失败 → **自动迭代修复方案**（再开 MR）——"**扫描 → 修复 → 验证的闭环自动化**"；**Security Review Flow（beta）**——**AI 查"模式扫描器查不出的逻辑漏洞"**（授权缺陷/业务逻辑/竞态条件——**模式扫描的盲区**）；**19.1 的 Duo 密钥误报常开检测**（AI 实时识别"看起来像密钥其实不是"——**减少误报噪音**）；**AI 审计事件**（AI 辅助的代码/流水线操作记录在案）。**给团队的落地建议**：**AI 安全能力先小范围试用**（beta 特性别直接上生产门禁），**核心门禁（SAST/依赖扫描）用成熟能力**——"**2026 的安全：机器在'发现问题 - 修复问题'上越来越能干，人的角色转向'政策与评审'**"。

## 8. 五个常见坑

- **坑一**：门禁卡存量漏洞——**历史债阻塞所有 MR；只卡 newly_detected**（第 3 节）；
- **坑二**：密钥变量不 Protected——**恶意 MR 能打印；Protected + Masked 双开**（第 4 节）；
- **坑三**：扫描结果不进 MR——**开发者看不到上下文；扫描与 MR 绑定是 GitLab 的卖点**（第 2 节）；
- **坑四**：误报靠关扫描解决——**门禁关了 = 漏洞自由；标记误报/豁免**（第 3 节）；
- **坑五**：密钥放代码/仓库——**泄露即事故；Secrets Manager/CI 变量/KMS**（第 5 节）。
