## 1. 三种分支模型的取舍

**Git 世界有三种主流分支模型**（Git 体系 03 篇深潜：`../Git/03-Git分支模型与团队工作流.md`）：**GitFlow**——main/develop/feature/release/hotfix 五分支——**复杂但严谨**（适合版本发布节奏严格的产品）；**GitHub Flow**——main + feature 两分支，PR 即评审——**简单**（适合持续部署的 SaaS）；**GitLab Flow**——**main + feature + 环境分支（pre-production/production）**——**GitHub Flow 的务实增强**。

**2026 的选型主线**：**持续部署的现代团队 → GitHub Flow/GitLab Flow**（**GitFlow 的 develop 分支在"每天上线"的团队是多余的一层**）；**版本发布型产品（固定发版节奏）→ GitFlow 仍有价值**——"**GitLab 官方推荐 GitLab Flow：简单 + 环境映射，是'部署型团队'的最优解**"；**落地顺序**：先定合并策略（第 6 节）再定分支模型——"策略先行，模型后定"。

## 2. GitLab Flow：环境分支

**GitLab Flow 的核心思想：环境即分支**——**main（集成）→ pre-production（预发布）→ production（生产）**——**代码从 main 合入环境分支发布**：

```text
feature/login ──→ main ──→ pre-production ──→ production
   (MR 评审)     (集成)      (预发布验证)       (生产发布)
```

**环境分支的三个要点**：其一，**环境分支是"发布流水线"不是"开发线"**——**开发只往 main 合**，环境分支只做"挑选要发布的内容"（main → 环境分支的 merge 就是发布动作）；其二，**环境分支的合并节奏 = 发布节奏**（pre-production 每次发版合一次、production 灰度合一次）；其三，**环境分支要保护**（02 篇分支保护：只有发布权限的人能合）——"**GitLab Flow 是'持续部署 + 环境控制'的平衡：main 是流水的源头，环境分支是闸门**"。**轻量替代**：小团队用 `environment` 标记（03 篇 environment 关键字）代替物理环境分支——"环境分支是显式流程，environment 标记是轻量记录——规模小用标记，规模大用分支"；**命名对应**：环境分支名与环境关键字一致（pre-production/production）——"**分支名与环境名一致，发布记录才可读**"。

## 3. 分支命名与保护规范

**分支命名规范**（团队约定，Git 体系交叉）：**feature/xxx**（功能）、**fix/xxx**（缺陷）、**release/x.y.z**（版本分支）、**hotfix/xxx**（紧急修复）——**命名即上下文**：MR 标题/流水线/回滚都靠分支名定位；**MR 标题建议 `feat/fix/docs: 描述`**（Conventional Commits 风格）——"**提交规范与分支规范同源**"。**分支保护矩阵**（02 篇第 5 节实操版）：

| 分支 | 谁可推 | 谁可合并 | 说明 |
|------|--------|---------|------|
| main | Maintainer（或禁止直推） | Maintainer | 强制 MR + 评审 |
| pre-production/production | 禁止直推 | 发布责任人 | 发布闸门 |
| release/* | Maintainer | Maintainer | 版本分支 |
| feature/* | Developer | — | 自由推，MR 进 main |

（**保护分支与密钥安全联动**：Protected 变量只在保护分支的流水线生效——"保护分支即安全边界"，07 篇。）

——"**保护的粒度按'这条分支能不能影响生产'定：越接近生产，保护越严**"。

## 4. MR 生命周期

**MR（Merge Request）是代码进 main 的唯一通道**，生命周期八个状态：**Draft（草稿）→ 提交评审（Reviewer 被指派）→ 评审意见（Inline comments）→ 修改（继续 push，MR 自动更新）→ 批准（Approval）→ CI 通过 → 合并（Merge）→ 删除源分支**。**三个工程细节**：其一，**MR 描述模板**（项目根目录 `.gitlab/merge_request_templates/` 放模板——**"这个 MR 改了什么/为什么/怎么测"变成必填结构**）；其二，**Draft 标记防误合并**（没写完标 Draft，GitLab 禁止合并 Draft）；其三，**MR 与 Issue 关联**（`Closes #123` 自动关 Issue——**追踪闭环**）。**19.0 的 Developer Flow**：**一键 rebase-and-merge**（冲突就地解决）、**Resolve with Duo**（AI 生成修复）——"**MR 流程 2026 年被 AI 提速，但'评审把关'的关卡不变**"。

## 5. Approval 规则

**Approval 规则是"谁批准才能合并"的强制要求**：**规则一：最少批准人数**（`Approvals required: 2`——**关键项目双人评审**）；**规则二：Code Owners**（**按路径指定负责人**：`/src/payment/** @payment-team` 用 CODEOWNERS 文件——**改支付代码必须支付组的人批准**）；**规则三：按角色**（仅 Maintainer 批准可合并）。**2026 增强**（19.1）：**Code Owner 自动指派评审人**（改到谁的代码自动分配 Reviewer）——"**Approval 规则把'评审靠自觉'变成'评审靠规则'**"——**与安全门禁联动**（安全扫描不通过不能合并，07 篇）。**落地路径**：Settings → Merge requests → Approval rules——"**规则配置一次，强制生效永久**"。

## 6. 合并策略

**GitLab 的三种合并策略**：**Merge Commit**（默认——保留合并提交，**历史有"合并痕迹"**）；**Squash**（**把 MR 的所有提交压成一个**——**历史干净**，适合"一个 MR 一个功能"的团队）；**Fast-forward**（**禁止合并提交**，历史线性——**强制 rebase 风格**）。**选型主线**：**"要历史干净用 Squash/Fast-forward，要保留合并上下文用 Merge Commit"**——**多数现代团队 Squash**（MR 是一件事，一个提交表达一件事）；**Squash 的代价**：中间提交细节丢失（调试历史变薄）——**提交信息要写好（一个提交 = 完整描述）**；**rebase 的纪律**（Git 体系 04 篇交叉）：**rebase 后 force push 只对 feature 分支做**（共享分支禁用）——"**合并策略是历史风格的选择：现代团队倾向'一个 MR 一个提交'**"。

## 7. MR 与 CI 的关卡联动

**MR 是 GitLab 的质量关卡总成**——**CI 结果、安全扫描、覆盖率、审批全部挂在 MR 上**：**合并前必过**（Merge checks）完整清单：**Pipeline must succeed**（流水线全绿才能合并——**红线**）；**Approvals 满足**（第 5 节）；**无冲突**（rebase 可解）；**（可选）安全门禁**（SAST 无 critical 才能合并，07 篇）——"**合并是'全绿才放行'的关卡，不是顺手点一下**"。**MR 页面的信息聚合**：**测试报告内嵌**（JUnit）、**覆盖率变化**（Cobertura）、**安全扫描结果**——"**MR 页面 = 代码评审的全部上下文：看代码、看测试、看扫描、点批准、点合并——五件事一处完成**"（03 篇第 7 节呼应）。

## 8. 五个常见坑

- **坑一**：GitFlow 的 develop 分支照搬——**持续部署团队多一层无意义分支；GitLab Flow 环境分支更务实**（第 2 节）；
- **坑二**：Approval 规则不配——**评审靠自觉；关键路径/关键人强制 Approval**（第 5 节）；
- **坑三**：合并策略不统一——**历史风格混乱；团队定一种（多数 Squash）**（第 6 节）；
- **坑四**：Pipeline must succeed 不设——**红流水线也能合并；合并检查必开**（第 7 节）；
- **坑五**：MR 不关联 Issue——**追踪断裂；Closes #123 关闭环**（第 4 节）。
