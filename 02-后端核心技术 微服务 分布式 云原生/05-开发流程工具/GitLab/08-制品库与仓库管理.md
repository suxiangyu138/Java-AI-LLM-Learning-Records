## 1. 制品库家族：三类仓库

**GitLab 内置三类"仓库"**，对应构建链路的三个产物：**Container Registry**——**Docker 镜像仓库**（构建的最终产物）；**Package Registry**——**依赖包仓库**（Maven/npm/PyPI 等——构建的中间依赖与发布包）；**CI/CD Catalog**——**流水线组件仓库**（04 篇 Components 的发布地）。**它们的共同价值**：**与项目/组绑定**（权限模型复用）、**与 CI 闭环**（流水线自动推拉）、**一个平台管理**（不用 Nexus + Harbor + 模板库三个系统）——"**制品库家族是'构建产物的一条龙仓库'：镜像、包、组件各就各位**"。

## 2. Container Registry：镜像仓库

**Container Registry 是 GitLab 内置的 Docker 镜像仓库**——**镜像地址 = GitLab 域名 + 项目路径**：`registry.gitlab.com/group/project/image:tag`。**CI 里的典型闭环**：

```yaml
build-image:
  stage: build
  image: docker:27
  services: [docker:dind]              # Docker-in-Docker（05 篇）
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA   # 推镜像（预定义变量自动配）
deploy:
  stage: deploy
  script:
    - docker pull $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA   # 部署拉取
```

**三个要点**：其一，**预定义变量**（`$CI_REGISTRY_IMAGE`/`$CI_REGISTRY_USER`/`$CI_REGISTRY_PASSWORD`）——**CI 自动注入 registry 凭据**（不用手配密钥）；其二，**镜像 tag 策略**（`$CI_COMMIT_SHA` 精确 tag + `latest` 别名——**部署用精确 tag 可回滚**）；其三，**清理策略**（第 7 节）——"**镜像 tag 是部署的版本号：用 SHA 精确 tag，别裸用 latest**"。

## 3. Package Registry：依赖包仓库

**Package Registry 支持 Maven/npm/PyPI/Go 等主流格式**——**私有依赖包的发布与消费**：**发布**——CI 里 `mvn deploy`（仓库地址指向 GitLab Package Registry）；**消费**——项目配置里加 GitLab 仓库源（**私有包供内部项目用**）——"**内部公共组件（工具库/公共 SDK）的发布地**"。**与 CI 的协同**：**CI job token 自动认证**（同项目/同组拉私有包不用单独配凭据）——"**GitLab 的包管理是'代码 + 包 + 流水线'同源的最后一环**"。**注意**：**Package Registry 的容量与保留策略要治理**（每个版本都 push = 仓库膨胀，第 6 节）。

## 4. CI/CD Catalog：流水线组件仓库

**CI/CD Catalog 是 04 篇 Components 的发布地**——**把可复用的流水线逻辑（构建模板/部署脚本）发布成"组件"**，组织内项目一行 include 引用：

```yaml
include:
  - component: gitlab.com/group/ci-components/java-build@1.2
```

**Catalog 的三个角色**：**发布方**（把团队的公共流水线逻辑组件化、版本化、写文档）；**消费方**（一行 include，锁版本）；**组织方**（19.0 的 Components Analytics：**看板看组件使用与版本分布**——"**哪些组件在用、哪些版本落后**"）。**价值**：**消灭复制粘贴的流水线**（团队 30 个服务的构建逻辑一处维护）——"**CI/CD Catalog 是'流水线的中央仓库'：组件即依赖，版本即纪律**"（04 篇第 6 节）。

## 5. CI 与制品库的闭环

**制品库的完整闭环**：**代码 push → CI 构建 → 产物入制品库（镜像/包）→ 部署拉取 → 运行**——"**制品库是 CI 与部署之间的'交接站'**"。**闭环的三个设计原则**：**产物唯一性**（每个构建的产物带唯一标识——SHA tag——**部署可回滚**）；**拉取与推送分离**（CI push 用 CI 凭据、部署 pull 用部署凭据——**权限分离**）；**镜像内容可追溯**（镜像带 commit SHA/构建号 label——**生产镜像能查到源码版本**，GitOps 审计链，05 篇）——"**制品库不是'存东西的地方'，是'部署链路的事实来源'**"。

## 6. 仓库治理：大小与历史

**仓库治理是长期运维的隐形战场**——三个问题与对策：**仓库膨胀**（大文件/二进制进 Git 仓库——**Git 历史只进代码；大文件用 LFS/制品库**，Git 体系交叉）；**历史无限增长**（每个 MR 的中间提交——**定期清理已合并分支 + 压缩历史（慎用，会破坏协作）**）；**磁盘占用**（**制品库与镜像的保留策略**——第 7 节）。**仓库治理的三件套**：**仓库大小监控**（项目设置看仓库大小——**超限告警**）；**LFS 政策**（大文件必须 LFS）；**分支清理**（**合并后自动删除源分支**（02 篇 MR 流程）+ 定期清理 stale 分支）——"**仓库治理不是'上线前的事'，是'每月看一眼'的日常**"。

## 7. 镜像策略与清理

**镜像/包的清理策略（Cleanup Policies）是制品库的"垃圾回收"**——**按规则自动删除旧产物**：

```yaml
# 项目设置 → Container Registry cleanup policy
# 保留最近 5 个镜像 / 保留 30 天 / 只清理无标签镜像
# 规则组合：按 tag 匹配 + 保留数量 + 保留时长
```

**清理策略的三个要点**：**先设保留规则再开启自动清理**（**别把生产要回滚的镜像清了**——保留最近 N 个是底线）；**按 tag 模式分桶**（`stable-*` 长期保留、`dev-*` 短保留——**不同环境不同策略**）；**清理有延迟**（策略定期执行，不是实时）——"**镜像策略是'存储成本 vs 回滚能力'的平衡：保留的粒度 = 你敢回滚的粒度**"。

## 8. 与 Nexus/Harbor 对比

| 维度 | GitLab Registry | Harbor | Nexus |
|------|----------------|--------|-------|
| 定位 | 平台内置（一体） | 专业镜像仓库 | 专业依赖包仓库 |
| 镜像 | ✅ | ⭐ 更强（复制/漏洞扫描） | 弱 |
| 依赖包 | ✅（Maven/npm 等） | ❌ | ⭐ 更强 |
| 与 CI 闭环 | ⭐ 原生（凭据自动） | 需集成 | 需集成 |
| 适用 | GitLab 一体化团队 | 独立镜像治理强需求 | 独立包治理强需求 |

**选型主线**：**GitLab 一体化团队 → 内置 Registry 够用**（闭环省事）；**独立治理/多平台异构 → Harbor（镜像）+ Nexus（包）**——"**内置够用就用内置（少一个系统），专业需求再引专业件**"（CI/CD 灰度发布体系的制品管理章节交叉：`../../07-工程运维基础/运维/CI CD灰度发布/`）。

## 9. 五个常见坑

- **坑一**：镜像 tag 裸用 latest——**部署不可回滚；SHA 精确 tag**（第 2 节）；
- **坑二**：大文件进 Git 历史——**仓库永久膨胀；LFS/制品库**（第 6 节）；
- **坑三**：清理策略不设——**镜像越积越多，磁盘爆；先保留规则后自动清理**（第 7 节）；
- **坑四**：清理策略把生产镜像清了——**回滚无镜像可用；保留最近 N 个底线**（第 7 节）；
- **坑五**：复制粘贴流水线不用 Catalog——**配置漂移；组件化 + 锁版本**（第 4 节）。
