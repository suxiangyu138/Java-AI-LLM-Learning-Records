## 1. 三种启动方式

**个人学习/小团队三个选择**：**GitLab.com**——注册即用，托管 Runner 开箱（**最快**，01 篇形态一）；**Docker 单机**——本地/内网验证（**学习与实验最佳**）：

```bash
docker run --detach --hostname gitlab.example.com \
  --publish 443:443 --publish 80:80 --publish 22:22 \
  --name gitlab --restart always \
  --volume $GITLAB_HOME/config:/etc/gitlab \
  --volume $GITLAB_HOME/logs:/var/log/gitlab \
  --volume $GITLAB_HOME/data:/var/opt/gitlab \
  gitlab/gitlab-ee:19.2.0-ee.0
```

**Omnibus 包**——生产单机部署（CentOS/Ubuntu，`curl -sS https://packages.gitlab.com/install/repositories/gitlab/gitlab-ee/script.rpm.sh | bash` + `gitlab-ctl reconfigure`）——"**Docker 实验、Omnibus 生产、K8s 集群（09 篇）**"。**Omnibus 的硬件前提**：**4GB 内存起步、20GB 磁盘**（仓库会涨）——"**先算资源再部署，别拿 2G 小机器跑 GitLab**"（09 篇容量）。**注意**：GitLab 启动慢（首次 3-5 分钟），**耐心等日志出现 "GitLab is ready"**——"**起不来先看日志，别反复重启容器**"（09 篇排障）；**Docker 升级姿势**：改 image tag 重建容器——**数据卷在宿主机不丢**——"**容器可换，数据在外**"。

## 2. 项目与组：组织结构

**GitLab 的组织结构三层**：**Group（组）→ Subgroup（子组）→ Project（项目）**——**组是权限与命名的容器**：组的成员权限继承到子组与项目（在组里加一个人 = 所有项目生效）——"**先建组再建项目：权限按组管，项目按业务分**"。**项目（Project）的四个要素**：**仓库**（代码 + 历史）；**议题（Issue）**（任务/缺陷跟踪）；**MR**（代码评审入口）；**CI/CD 配置**（.gitlab-ci.yml 在仓库根目录）。**2026 认知**：**项目即微服务的边界**——一个服务一个项目（monorepo 用子目录 + 多个 .gitlab-ci 配置，08 篇仓库管理）。**项目设置的关键项**：**可见性**（私有/内部/公开——**内网默认私有**）、CI/CD 开关（首次用 CI 要启用）、集成（Webhook/邮箱通知）。**Issue 的工程用法**：Issue 模板（缺陷/需求两种模板）+ 标签（bug/feature）——"**Issue 是任务的入口，MR 是任务的出口**"。

## 3. 权限模型：五级角色

**GitLab 的五级角色（权限从低到高）**：

| 角色 | 权限要点 |
|------|---------|
| Guest（访客） | 看项目/提 Issue，不能看代码（内网合规场景常用） |
| Reporter（报告者） | 看代码/看 CI 结果，不能推送 |
| Developer（开发者） | ⭐ 推送分支/开 MR/触发流水线——**日常开发角色** |
| Maintainer（维护者） | 合并 MR/改设置/管分支保护——**项目管理员** |
| Owner（所有者） | 删项目/转让/管理组成员——**最高权限** |

**三个实践**：其一，**Developer 是日常**（能推能开 MR 不能合并——**强制评审的权限设计**）；其二，**Maintainer 管合并与分支保护**（合并权限与开发分离 = 评审闭环）；其三，**权限最小化**——**组成员按需给角色，密钥/管理员账号单独管理**（07 篇安全）——"**五级角色是 GitLab 协作规范的第一道闸**"。**角色继承与覆盖**：组角色继承到项目，项目可覆盖（组 Developer 在项目里给 Maintainer）——"**继承是默认，覆盖是例外，例外要记录**"。**角色分配的最佳实践**：外部协作者给 Reporter/Guest（只读）、核心成员 Developer、组长 Maintainer——"**角色按职责分，不按关系分**"。

## 4. SSH 与 HTTPS 访问

**两种访问方式的选型**：**SSH**——`git clone git@gitlab.example.com:group/project.git`——**推荐**（免密码、密钥对管理）；**HTTPS**——`https://gitlab.example.com/group/project.git`——**防火墙友好**（443 端口，SSH 22 被挡的环境），**配 Personal Access Token 代替密码**（2021 起 GitLab 禁密码推送）。**SSH 配置三件事**：**生成密钥**（`ssh-keygen -t ed25519`）、**添加到 GitLab**（用户设置 → SSH Keys）、**验证**（`ssh -T git@gitlab.example.com`）——"**SSH 免密是开发体验第一件小事**"（Git 体系远程章节交叉：`../Git/`）。**SSH key 命名纪律**：一个账号多 key 按设备命名（home-laptop/work-desktop）——**吊销时知道是哪个设备**；**deploy key**（部署专用只读 key）与个人 key 分离——"**个人 key 管开发，deploy key 管部署**"。**Token 纪律**：**Personal Access Token 按权限最小化生成**（只勾需要的 scope）、**过期时间设短**、**泄露立即吊销**（07 篇）。**访问与 CI 的关系**：Runner 拉代码走 HTTP/HTTPS 内网地址——**内网部署注意 Runner 能访问 GitLab**（05 篇）。

## 5. 分支保护

**分支保护（Protected Branches）是 GitLab 协作的默认安全网**：**保护 main/master**——**只有 Maintainer 能直接推送/合并**，Developer 必须走 MR（评审强制）；**保护规则的可配项**：**谁可以推**（Maintainer/Developer/不允许直接推）、**谁可以合并**（Maintainer 或具体组）、**允许强制推送**（默认禁止——**rebase 场景单独开给特定角色**）。**生产纪律**：**main 与发布分支（release/*）必保护**（**保护规则支持通配：release/* 一键保护所有版本分支**）；**开发分支（feature/*）不保护**（自由推）——"**保护的是'能上线的分支'，不是所有分支**"（06 篇分支策略）。

## 6. 第一个 MR：完整闭环

```bash
# ① 建分支（Git 体系：功能分支模型）
git checkout -b feature/login
# ② 开发提交推送
git add . && git commit -m "feat: 登录接口" && git push -u origin feature/login
# ③ 打开 MR（GitLab 界面：Create Merge Request）
#    源分支 feature/login → 目标分支 main
#    Reviewer 评审 → CI 流水线跑（03 篇）→ Approval 通过（06 篇）
# ④ 合并（Merge）→ 删除源分支（可选）
```

**MR 的生命周期**：**Draft（草稿，未完成标记）→ 评审（Reviewer 评论/提意见）→ 修改（提交到同一分支，MR 自动更新）→ Approval（批准）→ CI 通过 → 合并**——"**MR 是代码从'写出来'到'进主线'的全部关卡**"：**评审、测试、安全扫描都在 MR 上完成**（03/06/07 篇）。**19.0 的 Developer Flow**：一键 rebase-and-merge（冲突就地解决再合并）、Resolve with Duo（AI 修复评审意见）——"**MR 体验在 2026 被 AI 重塑，但流程关卡不变**"。**MR 合并后的收尾三件事**：**删除源分支**（防分支堆积）、**关联 Issue 自动关闭**（`Closes #123`）、**发布时打 tag**——"MR 不是合并完就结束"。**评审职责分工**：Reviewer 看代码逻辑、Approver 把关合并（权限分离）——"**看得懂的人评审，有权限的人合并**"；**MR 是 CI 的触发器**：开 MR 即跑流水线——"MR 一开，验证自动开始"（03 篇第 7 节）。

## 7. 五个常见坑

- **坑一**：权限给最大（全员 Maintainer）——**评审闭环失效；Developer 日常 + Maintainer 管合并**（第 3 节）；
- **坑二**：main 分支不保护——**直接推送绕过评审；保护 main + 强制 MR**（第 5 节）；
- **坑三**：HTTPS 用密码推送——**2021 起被禁；Personal Access Token**（第 4 节）；
- **坑四**：Docker 起不来反复重启——**首次启动 3-5 分钟；看 /var/log/gitlab 日志**（第 1 节）；
- **坑五**：组不建直接建项目——**权限失控；先组后项目**（第 2 节）；
- **坑六**：镜像/包不设清理策略——**仓库膨胀磁盘爆；清理策略先保留规则后自动清理**（08 篇）。
