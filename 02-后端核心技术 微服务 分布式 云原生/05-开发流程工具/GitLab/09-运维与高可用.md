## 1. 部署形态选型

**自托管 GitLab 的四种部署形态**（01 篇三形态的运维细化）：**Omnibus 单机**——**小团队默认**（一台 8C16G 扛几百人够用）；**Omnibus 多机**（应用 + 数据库分离——**中规模**）；**K8s 部署**（官方 Helm chart——**规模化 + 云原生团队**）；**GitLab.com/Dedicated**（**不自己运维**——"**能 SaaS 就 SaaS，自托管是'合规/内网'的不得已**"）。**选型主线**：**"< 500 人单机 Omnibus；500+ 或高可用要求上多机/K8s；不想运维用 SaaS"**——"**自托管的每一分省下的年费，都花在运维时间上**"——**部署形态是容量与人力投入的权衡**（CI/CD 体系部署章节交叉：`../../07-工程运维基础/运维/CI CD灰度发布/`）。

## 2. Omnibus 与 Docker 部署

**Omnibus 包部署三步**：**① 装包**（RPM/DEB 仓库安装）；**② 配置**（`/etc/gitlab/gitlab.rb`——`external_url` 必配，其他按需）；**③ 生效**（`gitlab-ctl reconfigure`——**生成配置 + 启动服务**）。**常用命令**：`gitlab-ctl status`（服务状态）、`gitlab-ctl tail`（看日志）、`gitlab-ctl reconfigure`（改配置后执行）、`gitlab-ctl stop/start`。**Docker 部署**（02 篇）**注意三卷**（config/logs/data）+ **external_url 与端口映射一致**。**排障三板斧**（02 篇坑四细化）：**先 tail 日志**（reconfigure/异常看 `/var/log/gitlab`）、**再查端口与 DNS**（external_url 访问不通先查域名解析）、**最后看资源**（内存不足 GitLab 各种诡异——**4GB 是底线，8GB 舒适**）——"**GitLab 排障：日志第一、资源第二、配置第三**"。

## 3. 升级策略与节奏

**GitLab 升级是"有节奏的必修课"**（01 篇版本节奏的运维面）：**升级三原则**：**先备份再升级**（升级失败回滚靠备份——**铁律**）；**不跳大版本**（**升级路径限制：18.x → 19.x 直接升可能失败，官方要求按路径**——"**GitLab 升级不支持跳级，路径就是版本号逐个走**"）；**先测试环境**（**生产升级前，测试实例先升一遍**——版本兼容性先验证）。**升级节奏建议**：**跟随月度小版本（Y）**（修复 + 安全补丁及时）；**大版本（X）升级前读升级文档**（破坏性变更清单）——"**GitLab 的升级哲学：小步快跑（月度）+ 绝不跳级（路径）**"。**安全补丁**：**security releases 邮件订阅**，严重 CVE 的 patch 版本**尽快升**（GitLab 是内网单点，被攻破 = 源码 + 密钥全泄露）。

## 4. 备份与恢复

**备份是自托管的生命线**——**GitLab 备份的命令**：

```bash
gitlab-backup create            # 全量备份（数据库 + 仓库 + 上传文件）
# 恢复：gitlab-backup restore BACKUP=1234567_2026_08_10_19.0
# 配置备份：/etc/gitlab/gitlab.rb + gitlab-secrets.json 单独备份！
```

**备份的三个关键认知**：其一，**备份分两块**——**数据备份**（gitlab-backup create）+ **配置文件备份**（`/etc/gitlab/` 与 **`gitlab-secrets.json`——不含它恢复后密钥全失效**，凭据解密不了）；其二，**备份要异地/异机**（**同机备份 = 没备份**——机器挂了备份一起没）；其三，**恢复要演练**（**备份的价值在恢复，恢复没演练过 = 备份可能不可用**——季度演练是纪律）。**备份内容**：**数据库（PostgreSQL）+ 仓库（Git 数据）+ 上传文件（LFS/附件）**——"**备份两件套（数据 + 配置/密钥）+ 异地存放 + 定期演练**"。

## 5. Geo：高可用与异地容灾

**GitLab Geo 是官方的高可用/容灾方案**——**主站点 + 从站点（Geo secondary）**：**数据持续复制**（PostgreSQL 流复制 + 仓库/制品异步同步）；**从站点可读**（**就近读加速**——跨地域团队的读操作走本地从站）；**故障切换**（主站挂 → 提升从站（promote）——**容灾 RTO 分钟级**）。**Geo 的三个认知**：**Geo 是"读扩展 + 容灾"不是"双活"**（写操作仍走主站——**GitLab 不是多主架构**）；**配置复杂度高**（需要专用拓扑，**小团队别上**——单机扛不住再说）；**Geo 是 Premium/Ultimate 功能**（版本边界，01 篇边界四）。**替代**：**中小团队的高可用 = 备份 + 恢复演练**（**先备份，再谈 Geo**）——"**Geo 是锦上添花，备份是雪中送炭——容灾的起点永远是备份**"。

## 6. 监控与告警

**GitLab 自带的监控**：**GitLab Exporter**（Prometheus 兼容指标——**进程/HTTP/数据库指标**）；**健康检查端点**（`/-/health` 与 `/-/readiness`——**K8s 探针/负载均衡健康检查用**）；**管理仪表盘**（`/admin` 的 overview：**队列、延迟、后台任务**）。**关键监控指标**：**Sidekiq 队列长度**（**后台任务积压 = GitLab 变慢的常见根因**）；**磁盘空间**（仓库/数据库/日志三块磁盘的容量——**磁盘满 = GitLab 只读/挂掉**）；**内存/CPU**（Puma + Sidekiq + PostgreSQL 三大进程的资源）。**告警配置**：**Prometheus + Alertmanager**（或云监控）——"**监控三看：Sidekiq 队列、磁盘水位、三大进程资源——GitLab 的故障 80% 在这三处露头**"（日志监控指标体系交叉：`../../07-工程运维基础/运维/日志监控指标/`）。

## 7. 容量规划

**GitLab 容量规划的经验值**（官方参考，按实际验证）：**存储**：**仓库 1GB/开发者/年 + 数据库 0.5GB/开发者/年 + 制品/镜像按使用**（**镜像清理策略是容量治理第一手段**，08 篇）；**内存**：**4GB 起步**（小团队）、**500 用户 ~16GB、2000 用户 ~64GB**（Puma + Sidekiq 占大头）；**CPU**：**2 核起步**，CI 负载重时**Runner 与 GitLab 分机部署**（**Runner 是 CPU 大户，别和 GitLab 抢资源**，05 篇）。**规划纪律**：**磁盘监控 + 80% 水位告警**；**制品库清理定期执行**；**仓库大小治理**（08 篇第 6 节）——"**容量规划不是'买多大机器'，是'监控 + 治理的循环'**"。

## 8. 五个常见坑

- **坑一**：只备份数据不备份 gitlab-secrets.json——**恢复后密钥全失效；两件套一起备**（第 4 节）；
- **坑二**：升级跳大版本——**升级失败；按官方路径逐版本走**（第 3 节）；
- **坑三**：备份同机存放——**机器挂备份一起没；异地/异机**（第 4 节）；
- **坑四**：磁盘不监控——**磁盘满 = 服务挂；80% 水位告警**（第 6 节）；
- **坑五**：小团队直接上 Geo——**复杂度大于收益；先备份演练，规模到了再 Geo**（第 5 节）。
