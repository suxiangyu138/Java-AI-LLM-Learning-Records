## 1. 协作模型：与 GitHub Flow 同构

Gitee 的协作流程与 GitHub 完全同构，这是它"低迁移成本"的核心——在 GitHub 上练过的团队到 Gitee 零学习成本：

```text
开发流程（GitHub Flow 风格）：
创建功能分支 → 提交推送 → 开 PR → 审查讨论 → 合并 → 删除分支
          ↖ 关联 Issue ← 任务来源 ↙
```

与 Git 知识体系的分支模型篇衔接：主干保护 + 功能分支 + PR 审查 = GitHub Flow 的最小闭环；需要发布节奏时升级 GitFlow（develop 分支 + release 分支）。**平台提供机制，团队规范决定质量**——PR 是机制，审查清单是规范。

## 2. Pull Request 完整流程

```text
① 创建分支：git checkout -b feature/order-export
② 提交推送：git push origin feature/order-export
③ 开 PR：Gitee 仓库 → Pull Requests → 新建
   ├── 源分支 → 目标分支（通常 main）
   ├── 标题与描述（关联 Issue：#123）
   └── 模板（团队预置）
④ 审查：评论/代码行内评论/请求修改
⑤ 合并：合并提交 / 压缩合并 / 变基合并
⑥ 删除源分支
```

PR 三个关键设置：

- **关联 Issue**：描述里写 `#123` 自动关联，合并后 Issue 自动关闭——任务追踪闭环
- **审查者（Reviewers）**：指派 1-2 名审查者，Gitee 有"请求审查"机制，可设多人
- **合并方式**：压缩合并（squash）保持主干历史干净，变基合并（rebase）保线性，合并提交（merge）保真实历史——按团队偏好选，**定了就统一**

## 3. Issue：任务与讨论的载体

Issue 在 Gitee 里承担任务管理（不只是缺陷跟踪）：

- **模板化**：新建 Issue 支持模板（bug/feature/问题），引导提交者写清背景、复现步骤、期望行为
- **状态流转**：打开 → 处理中 → 已解决 → 已关闭，与 Gitee Go 流水线联动（PR 合并自动关 Issue）
- **标签体系**：优先级（P0-P3）、类型（bug/feature/refactor）、模块标签
- **里程碑**：按版本聚合 Issue，规划发布范围

团队实践：**Issue 是需求与缺陷的唯一入口**，PR 必须关联 Issue——这样"为什么改"有迹可循，发布说明可以自动生成（合并的 PR 关联的 Issue 汇总）。

## 4. 保护分支：主干守门员

保护分支是"没人能直接往 main 提交"的机制：

```text
分支保护规则（推荐基线）：
├── 禁止直接推送（必须走 PR）
├── 合并前要求审查通过（≥1 人）
├── 合并前要求 CI 通过（Gitee Go 集成）
└── 管理员也要走流程（或保留管理员豁免）
```

保护分支与 Gitee Go 的配合是质量闭环的关键：**PR 合并门禁 = 审查通过 + 流水线通过**——GiteeScan 扫描、GiteeTest 测试跑完且全绿才能合并。这个门禁把"代码质量"从口头要求变成硬性机制。

## 5. Fork 协作 vs 直接分支

| 场景 | 方式 | 适用 |
|------|------|------|
| 项目协作者 | 直接分支 + PR | 团队成员、长期合作 |
| 开源贡献者 | Fork + PR | 外部贡献者（无写权限） |
| 教学演示 | Fork | 学生练习 |

Fork 协作流程：Fork 到自己名下 → clone 本地 → 加 upstream 远程（原仓库）→ 同步上游 → 分支开发 → PR 回原仓库。Fork 模式的核心是 **upstream 同步**：`git remote add upstream <原仓库>`，开发前 `git fetch upstream && git merge upstream/main`，否则 PR 会因分支落后产生冲突。

## 6. 审查的最佳实践

代码审查的质量取决于流程设计，四条高频经验：

1. **小 PR 原则**：单 PR 改动量控制在可审查范围（经验值 < 400 行或 < 10 个文件），大改动拆分为逻辑独立的多个 PR——审查者注意力有限，大 PR 的审查质量必然下降
2. **描述即文档**：PR 描述写清"为什么改 + 怎么改 + 怎么测"，审查者不用猜意图；空白 PR（只改格式无说明）直接打回
3. **行内评论聚焦代码**：评论落在具体代码行（Gitee 支持行内评论），讨论可追溯；有争议的设计问题提到 Issue 讨论，避免 PR 评论区变成辩论场
4. **审查轮次上限**：超过 3 轮往返的 PR，要么设计有问题（回到设计评审），要么沟通成本失控（当面讨论）——审查不是无限循环

## 7. 团队规范模板

一套可落地的 Gitee 团队规范：

```text
分支命名：feature/xxx、fix/xxx、release/x.y.z、docs/xxx
PR 模板字段：背景 | 改动 | 测试 | 关联 Issue | 影响面
审查清单：逻辑正确 / 命名清晰 / 无重复代码 / 测试覆盖 / 无敏感信息
合并规则：squash 合并 + 删除源分支 + 门禁（审查 1 人 + CI 全绿）
Issue 规则：标签必选 + 里程碑归属 + PR 必关联
```

规范的价值：**把协作摩擦前置到模板与规则**——新成员看模板就知道怎么提 PR，审查者看清单就知道查什么，Issue 闭环让每个改动都可追溯。

规范落地的一条经验：**规范不是文档，是模板与配置**——写 10 页《协作规范.pdf》没人读，但把 PR 模板、分支保护、门禁配置、Issue 标签做进平台，新成员第一次提 PR 就被模板引导。Gitee 的模板仓库 + 组织级设置（如果有企业版）可以把这套配置固化，新仓库一键继承。规范演进也要"配置化"：团队复盘发现的协作问题，转化成模板字段或门禁规则，而不是再开一次会。

审查文化的两个反向陷阱：**形式化审查**（只看格式不问逻辑，门禁全过但质量没把关）与**过度审查**（每行都要改，拖垮节奏）。健康节奏：核心逻辑（安全、数据、架构）严审，样板代码（配置、测试夹具）快速放行；审查者先看整体再看细节——顺序错了就会陷入"改格式"的无效循环。审查质量指标：发现率（多少 bug 在审查阶段被拦下）比"通过率"更有意义。
