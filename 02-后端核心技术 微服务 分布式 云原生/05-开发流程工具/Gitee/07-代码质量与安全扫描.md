## 1. 质量体系全景：Scan/Test/AI 三件套

Gitee 的质量能力是三层结构：

- **GiteeScan**：静态代码扫描——安全漏洞（注入/XSS/弱加密）、规范违规（命名/复杂度）、依赖风险
- **GiteeTest**：自动化测试平台——单元测试/接口测试/UI 测试的执行与报告
- **AI 检测**：模力方舟的漏洞检测——结合上下文语义理解与静态分析，识别模式规则难以覆盖的逻辑漏洞

三者与 Gitee Go 的集成是闭环关键：**扫描与测试在流水线里跑，结果进 PR 门禁**——代码质量从"人盯人"变成"机制守门"。

## 2. GiteeScan：代码扫描能力

GiteeScan 覆盖的检查维度：

| 维度 | 检查内容 | 典型发现 |
|------|----------|----------|
| 安全漏洞 | OWASP 类漏洞模式 | SQL 注入、XSS、硬编码密钥 |
| 规范合规 | 编码规范/复杂度 | 命名违规、圈复杂度超标 |
| 依赖风险 | 依赖库已知漏洞 | CVE 告警、高危版本 |
| 许可合规 | 开源许可检查 | GPL 传染、许可冲突 |

使用方式：仓库 → 服务 → GiteeScan 开启；与 Gitee Go 集成后每次 push/PR 自动扫描，结果按严重级别（致命/严重/一般/提示）分级展示。**扫描规则可配置**：按语言选规则集、按项目豁免误报——扫描工具都会误报，豁免机制是可用性的关键。

## 3. GiteeTest：自动化测试

GiteeTest 提供自动化测试执行能力：

- **测试类型**：单元测试（JUnit/Pytest）、接口测试、UI 测试（浏览器自动化）
- **执行方式**：与 Gitee Go 流水线集成，测试作为阶段任务执行；支持定时/触发执行
- **报告**：测试结果报告、失败详情、覆盖率

工程实践：**测试分层**（单元 > 接口 > UI，成本递增收益递减）、**覆盖率红线**（如核心模块 80%）、**失败即阻塞合并**（门禁配置）。测试的价值在回归——CI 里跑测试的意义是"每次提交都验证一遍老功能没坏"。

## 4. AI 漏洞检测：静态分析的智能化

Gitee 的 AI 检测与传统静态分析（SAST）的差异：

- **上下文语义理解**：传统规则引擎按模式匹配（`= "SELECT ..." +` 拼接即报警），AI 结合代码上下文理解数据流与调用链，判断漏洞是否真实可达
- **测试路径推荐**：AI 不仅报漏洞，还推荐测试路径/测试用例，指导修复验证
- **本土化模型**：基于海量开源项目数据训练的专用模型，更懂中国开发者常见写法

**定位**：AI 检测是人工审查的辅助，不是替代——静态分析的三类输出（确定漏洞/疑似漏洞/误报）仍需人工分级。工程上把 AI 检测作为扫描流水线的一档，输出"建议人工确认"级别的报告。

## 5. 质量门禁的落地姿势

质量工具的价值在"门禁绑定"，推荐基线：

```text
合并门禁配置（保护分支）：
├── 审查通过（≥1 人）
├── GiteeScan 扫描通过（无致命/严重漏洞）
├── GiteeTest 测试通过（全绿 + 覆盖率达标）
└── AI 检测高风险项已确认
```

两条经验：**门禁从严到宽分阶段**——先禁致命漏洞，再禁严重，逐步收紧，避免第一天就全量阻塞导致团队绕过流程；**误报豁免要有流程**——豁免需理由与人工确认，不是静默关闭。

## 6. 敏感信息防护

扫描里最容易踩雷的一类问题：**密钥与凭证入库**。

```text
高危模式：.env 提交、API Key 硬编码、数据库密码写配置、.gitignore 漏配
平台能力：GiteeScan 检测硬编码密钥（AK/SK、token、密码）
防泄漏基线：
├── .gitignore 必配（.env、*.pem、application-local.yml）
├── 密钥只进环境变量/密钥管理服务（K8s Secret、Vault）
├── 已泄露密钥立即轮换（提交历史里删文件不够，历史仍在）
└── 扫描结果里的密钥按紧急处理
```

**已泄露的密钥必须轮换**——删除文件不解决问题，git 历史里永远能找到。扫描工具发现密钥后：立即轮换 → 清理历史（filter-repo，见 Git 知识体系）→ 补 .gitignore 防再犯。

## 7. 扫描结果治理

扫描的最终敌人是"告警疲劳"——问题太多导致没人看：

1. **分级处置**：致命/严重（阻塞门禁）、一般/提示（周报跟进）
2. **存量清零**：项目接入扫描第一天先清存量问题，再守新增（增量门禁）
3. **趋势看板**：问题数/修复率/平均修复时长——用数据驱动改进
4. **规则持续优化**：误报多的规则调整或豁免，漏报场景补规则
5. **责任到人**：扫描结果按模块归属到负责人，修复计入迭代

治理闭环：**扫描（发现问题）→ 门禁（阻止新问题）→ 看板（度量趋势）→ 优化（规则与流程）**。

一个常见疑问：为什么不用现成的 SonarQube/开源扫描器？——可以，而且很多团队这么做。但平台内置扫描的价值在**零部署与流程集成**：不用维护扫描服务器、结果直接进 PR 门禁、成员在 Gitee 内查看与豁免，省的是"工具运维 + 流程对接"的成本。已有 SonarQube 基础架构的大团队继续用开源栈没问题；中小团队从 GiteeScan 起步更务实。
