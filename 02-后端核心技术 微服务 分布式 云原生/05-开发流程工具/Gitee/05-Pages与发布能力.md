## 1. Gitee Pages：静态站点托管

Gitee Pages 是内置的静态站点托管服务，支持从仓库分支直接部署：

- **能力**：HTML/CSS/JS 静态资源托管，支持自定义域名、HTTPS 证书
- **用途**：项目文档站、个人主页、前端 Demo、VuePress/Hugo/Jekyll 构建产物
- **部署方式**：仓库 → 服务 → Gitee Pages，选择分支与目录，点击部署

与 GitHub Pages 的定位一致，但有国内网络优势：国内访问 Gitee Pages 速度快且稳定，不需要加速手段。**适用边界**：只支持静态资源，不支持服务端逻辑（动态 API 需要后端，见 09 篇的 API 集成）。

## 2. Pages 的实名与审核约束

这是 Gitee Pages 与 GitHub Pages 最大的体验差异：

- **免费版强制实名认证**：未实名用户无法使用 Pages 服务
- **内容审核**：发布站点有内容审核流程，违规内容（侵权/违法/涉政）会被拒绝或下线
- **域名要求**：自定义域名需 ICP 备案（国内托管平台的统一要求）

约束的解读：这是国内网络内容管理政策的平台化落地，不是 Gitee 独有的限制（GitHub Pages 在中国访问本身不稳定）。**规划 Pages 使用时要预留审核时间**——发布流程从"点击即上线"变成"提交 → 审核 → 上线"，文档更新频率高的站点要考虑这个延迟。

## 3. Pages 部署工作流

```text
静态站常规部署：
本地构建（VuePress/Hugo）→ 推送到 Pages 分支（如 gh-pages 同构的 pages 分支）
  → Gitee Pages 选择该分支 → 部署

自动化（推荐）：
代码 push main → Gitee Go 流水线构建静态站 → 部署产物到 Pages 分支
  → 调用 Pages 部署接口刷新
```

工程建议：**构建产物与源码分离**——源码在 main，构建产物在独立分支（或独立仓库），避免 main 被构建产物污染。Gitee Go 里配置"构建后自动部署 Pages"即可实现"push 即发布"。

一个容易忽略的细节：**Pages 的部署结果有缓存**——更新内容后立即访问可能看到旧版本，发布后等 1-2 分钟或强制刷新再验收；频繁更新的站点建议在页面里标注构建时间戳，排查"为什么没更新"时先看时间戳再怀疑部署链路。多站点管理：一个账号可部署多个仓库的 Pages（每个仓库独立站点），个人主页与项目文档互不干扰——规划好"哪个仓库对应哪个站点"避免误部署。

## 4. Releases：版本发布体系

Releases 是"tag + 发布包 + 变更说明"的版本发布体系：

```text
发布流程：
① 打 tag：git tag v1.2.0（语义化版本）
② 推送 tag：git push origin v1.2.0
③ 创建 Release：Releases → 新建 → 选择 tag
   ├── 标题与变更说明（可自动汇总关联 Issue/PR）
   ├── 附件（安装包、二进制、源包）
   └── 标记预发布（Pre-release）
```

Releases 与镜像的配合：tag 会随镜像同步（03 篇），发布到 GitHub 的 Release 需在 GitHub 侧单独创建。**语义化版本（SemVer）**是发布规范的核心：主版本.次版本.补丁版本，破坏性变更升主版本、新特性升次版本、修复升补丁。

## 5. Wiki：项目文档协作

Gitee Wiki 提供仓库级文档协作：

- 每个仓库独立 Wiki，支持 Markdown 编辑
- 与 README 的分工：**README 是门面**（项目是什么、怎么用），**Wiki 是深度文档**（架构说明、贡献指南、FAQ）
- 权限随仓库：私有仓库 Wiki 仅协作者可见

实践建议：文档在代码库维护（docs/ 目录 + README）优于 Wiki——文档随代码走，PR 审查文档改动，发布时同步。Wiki 适合非开发者参与维护的场景（产品文档、运营手册）。

一个务实的混合方案：**README 放快速开始（给使用者），docs/ 放架构与贡献指南（给开发者），Wiki 放团队约定与 FAQ（给内部）**——三者按"受众"分流而不是按"习惯"堆一起。这也是多数成熟开源项目的标准布局，直接照抄即可。文档质量检查可以进流水线：链接失效检查（markdown-link-check）、代码块可执行性抽查（docs 里的命令实际跑一遍）——文档也是代码，值得门禁。

## 6. Pages 的调试与故障排查

Pages 站点出问题时的排查顺序：

| 现象 | 原因 | 解法 |
|------|------|------|
| 访问 404 | 分支/目录选错 | 检查 Pages 配置的分支与目录 |
| 样式全丢 | 相对路径问题 | 静态站 base path 配置（VuePress base、Hugo baseURL） |
| 内容陈旧 | 部署未触发 | 检查构建产物分支是否更新 |
| 审核被拒 | 内容违规 | 查看拒绝原因，整改后重新提交 |
| 域名不可用 | 备案未通过 | ICP 备案完成后重试绑定 |

高频坑是**相对路径**：静态站构建时默认按根路径生成资源链接（`/assets/...`），部署在子路径（`https://gitee.io/用户名/仓库/`）时全部 404——构建时显式配置 base 为仓库路径，或在 Pages 设置中核对访问路径。

## 7. 发布场景选型

| 场景 | 方案 | 理由 |
|------|------|------|
| 项目文档站 | Pages + 构建产物分支 | 静态站快、免服务器 |
| 个人主页/简历 | Pages | 实名后一键部署 |
| 软件版本发布 | Releases + tag | 包管理 + 变更说明 |
| 前端 Demo | Pages | 演示环境 |
| 动态网站 | 外接服务器/云函数 | Pages 不支持服务端 |
| 多版本文档 | Pages 分版本目录 | /v1/、/v2/ 目录隔离 |

**核心判断**：静态 → Pages（成本最低）；动态 → 服务器/云函数（Pages 之外）；版本 → Releases（规范发布）。发布链路与 06 篇 Gitee Go 配合可实现"提交即发布"的完整自动化。
