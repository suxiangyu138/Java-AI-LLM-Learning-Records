## 1. 注册与安全基线

注册流程与常规平台一致（手机号/邮箱均可），但有一个强制项：**二次验证（2FA）**。

- Gitee 强制要求账号开启 2FA（两步验证），登录与敏感操作需要动态口令
- 推荐绑定**验证器 App**（Google Authenticator/微软验证器），备份恢复码
- 个人令牌（Personal Access Token）：用于命令行与 CI 场景鉴权，替代密码——token 只显示一次，丢失重建

安全基线三条：2FA 必开（平台强制，别嫌麻烦）、token 按最小权限创建（只勾所需 scope）、密码不与其他平台复用。开源账号一旦被劫持，恶意提交会污染你的项目历史——Gitee 曾因社工攻击导致过账号安全事件，2FA 是防线。

## 2. 创建仓库：完整参数解读

新建仓库时五个关键参数：

| 参数 | 选项 | 影响 |
|------|------|------|
| 仓库名称 | 英文/数字/连字符 | 克隆地址的一部分，避免大写与空格 |
| 路径 | 可自定义 | 影响 URL，改名后旧链接失效（提供跳转） |
| 可见性 | 私有/公开 | 公开即开源，私有限协作成员 |
| 初始化 | README/.gitignore/许可 | 建议初始化 README + 匹配语言的 .gitignore |
| 模板 | 自定义模板仓库 | 团队统一脚手架：CI 配置、分支规范、PR 模板 |

两个实用技巧：**模板仓库**让新项目零配置起步（把 GiteeGo 配置、CONTRIBUTING、PR 模板放进模板仓库）；**分支模型**在仓库设置里默认保护 main，与团队规范（Git 知识体系的分支模型篇）配合。

## 3. 克隆与推送：SSH 配置

```bash
# ① 生成密钥（Git Bash / 终端）
ssh-keygen -t ed25519 -C "your@email.com"

# ② 添加公钥：Gitee → 设置 → SSH 公钥 → 粘贴 ~/.ssh/id_ed25519.pub
# ③ 验证连接
ssh -T git@gitee.com
# → Hi 用户名! You've successfully authenticated...

# ④ 克隆与推送（Gitee 支持 HTTPS 与 SSH 两种地址）
git clone git@gitee.com:用户名/仓库名.git
cd 仓库名
git remote -v            # 查看远程
# 修改远程地址（GitHub 迁移场景常用）
git remote set-url origin git@gitee.com:用户名/仓库名.git
```

SSH 优先于 HTTPS 的理由：免输密码、支持 2FA 场景（HTTPS 用 token）、更稳定的连接。多账号场景（GitHub + Gitee 并存）用 `~/.ssh/config` 按 host 分配不同密钥：

```text
Host gitee.com
    HostName gitee.com
    User git
    IdentityFile ~/.ssh/id_ed25519_gitee
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github
```

## 4. 导入已有仓库：从 GitHub/GitLab 迁移

Gitee 支持一键导入，两条路径：

- **新建仓库 → 勾选"导入已有仓库"**：粘贴 GitHub/GitLab 仓库 HTTPS 地址直接导入，保留提交历史（含全部 commit）
- **手动迁移**：本地 `git clone --mirror` 拉全量镜像 → 添加 Gitee 远程 → `git push --mirror`——适合大仓库与离线场景

导入限制（2026-08）：单仓库大小不超过 **2GB**；**不支持 Git-LFS 同步**（大文件需单独处理）；导入后如需持续同步用镜像功能（03 篇）。

一个实用的迁移组合拳：**"镜像 + 本地双远程"双保险**——高频同步用镜像（03 篇），低频大文件/特殊场景用本地 `git push --all` 手动同步。迁移期间用 GitHub Actions 自动同步到 Gitee 也可行（push 后脚本推一份），适合"主阵地在 GitHub、Gitee 只是展示"的场景。方案按"谁在提交"定，见 03 篇主从策略。

常见迁移坑：导入后检查 `.gitmodules`（子模块地址要改）、CI 配置的仓库地址（GiteeGo 用新地址）、issue/PR 历史不迁移（GitHub 的 PR/issue 是平台数据，无法随仓库搬走）。

## 5. 免费版与付费版边界

| 能力 | 免费版 | 企业版 |
|------|--------|--------|
| 私有仓库 | 有（数量/协作者受限） | 不限 |
| Gitee Go | 200 分钟赠送 + 每月额度 | 8000 核分/年起 |
| Pages | 需实名 + 内容审核 | 免实名 |
| 镜像仓库 | 基础方向 | 高级选项（Issue/PR 同步） |
| 安全审计/留痕 | 无 | 有（DevSecOps 核心） |
| 私有化部署 | 无 | 有（信创场景） |

免费版够个人学习与小型开源项目用；团队协作、审计要求、信创合规必须企业版。**选型的判断标准不是价格，是合规需求**——政企场景企业版私有化是唯一选项。

## 6. 仓库管理日常操作

- **Webhook**：仓库 → 管理 → Webhooks，push 后通知外部系统（CI/IM/自建服务）——镜像同步与自动化通知的基础
- **标签与 Releases**：语义化版本打 tag，Releases 发布包与说明（05 篇展开）
- **仓库标签（Topic）**：给仓库打主题标签，帮助社区发现
- **Fork**：参与他人项目先 Fork 再提 PR（04 篇）
- **仓库设置**：删除/转移/改名（改名提供旧链接跳转）、分支保护、协作者管理

日常操作的三个纪律：**命名即文档**——仓库名/分支名/标签名一旦公开就难改，命名规范（kebab-case、语义化版本）从第一天执行；**权限定期盘点**——协作者与成员按季度清理，离职人员立即移除（GitHub/Gitee 都有安全告警机制提醒失活成员）；**README 是门面**——README 决定仓库被发现的转化率（标题、一句话定位、截图、快速开始、License 五项缺一不可），模板仓库里固化这份规范，新仓库零成本继承。

再补充一个仓库规模管理认知：**仓库不是越大越好**——单仓库体积影响 clone 速度、CI 时长与代码审查范围（超大 PR 无法有效审查）。常规工程按"一个服务一个仓库"（多仓库）或"一个平台一个仓库"（monorepo）二选一，混合型（大仓库 + 子模块）最痛苦。Gitee 对仓库大小有限制（导入 2GB），大仓库要拆分或走 Git-LFS（注意 Gitee 镜像不支持 LFS）——仓库结构在创建时定，比事后迁移便宜得多。
