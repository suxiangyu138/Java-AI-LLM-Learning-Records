## 1. 镜像是什么：三个同步对象

镜像仓库把 Gitee 与 GitHub 的仓库做**自动同步**，同步对象是三个：

- **分支（Branches）**：全部分支的最新状态
- **标签（Tags）**：版本标签
- **提交记录（Commits）**：提交历史

注意边界：**不包含** Issue、Pull Request、Wiki、Star 等平台数据——这些是平台生态，镜像只同步 Git 数据。Issue/PR 同步是企业版高级选项。

典型使用场景：项目在 Gitee 开发（国内团队 + 国内 CI），同步到 GitHub 扩大开源影响力；或反向：GitHub 开源项目自动同步到 Gitee，国内用户免梯子访问。

## 2. 三种镜像方向与配置

配置入口：仓库 → 管理 → 仓库镜像管理 → 添加镜像（需先绑定 GitHub 账号）。

| 方向 | 含义 | 触发方式 |
|------|------|----------|
| Push 方向 | Gitee → GitHub | 向 Gitee 提交后自动同步到 GitHub |
| Pull 方向 | GitHub → Gitee | 自动（webhook）或手动（点击更新） |
| 双向镜像 | 两端互相同步 | 两端提交都触发对端同步 |

配置要点：GitHub 私人令牌（Personal Token）**必须包含 `repo` 授权**；勾选"自动从 GitHub 同步"还需 `admin:repo_hook` 授权（webhook 创建需要），否则自动同步配置失败。权限不足的表现是同步不触发或 401。

```text
绑定 GitHub → 仓库镜像管理 → 添加镜像
  ├── 方向：Push / Pull / 双向
  ├── 目标仓库：GitHub 仓库选择
  └── Token：repo（+ admin:repo_hook 用于自动同步）
```

## 3. Webhook 实时同步原理

Pull 方向的"自动镜像"通过 **webhook** 实现：GitHub 仓库配置 webhook，push 事件触发 → Gitee API 拉取更新。

```text
GitHub push → webhook POST https://gitee.com/api/v5/repos/{user}/{repo}/hooks
              （Secret 填 Gitee 个人令牌，事件选 push）
  → Gitee 收到通知 → 执行镜像同步 → Gitee 仓库更新
```

等效的手工配置：GitHub 仓库 → Settings → Webhooks → 新建 webhook，Payload URL 指向 Gitee API hooks 端点，Secret 填令牌。**webhook 是"事件驱动"的**——相比定时轮询（每小时/每天同步频率），webhook 在提交后立即触发，延迟从"小时级"降到"分钟级"（受 5 分钟最小间隔约束）。

## 4. 硬性限制清单

| 限制 | 数值 | 影响 |
|------|------|------|
| 最小触发间隔 | 5 分钟 | 短时间内多次提交只同步一次 |
| 同步超时 | 30 分钟 | 超时失败，大仓库不适合镜像 |
| 手动导入大小 | 2GB | 超大仓库需本地镜像迁移 |
| LFS | 不支持 | Git-LFS 大文件不同步 |
| 覆盖行为 | 覆盖目标分支/标签/提交 | 目标仓库被完全覆盖，先备份 |
| 中断性 | 发起后无法中断 | 只能等完成或强制停止 |
| 双向风险 | 两端同时提交可能丢码 | 官方明确警告 |

两条红线：**双向镜像不要在两端同时提交**（冲突时一方提交被覆盖，代码丢失），两端提交间隔尽量大于 30 分钟；**镜像操作会覆盖目标仓库**——目标端有独有分支时先备份。**强制推送与历史重写同样危险**：镜像按分支/标签/提交全量对齐，一端 rebase 重写历史后，另一端会被同步成"新历史"，旧提交看似消失——团队协作中 rebase 的纪律（见 Git 知识体系）在镜像场景被放大，建议镜像两端都禁止强推。

## 5. 主从策略：怎么用才安全

安全的镜像不是"两端都写"，而是**明确主从**：

```text
方案一：Gitee 主 + GitHub 从（Push 方向）
  国内团队在 Gitee 开发提交 → 自动同步 GitHub 发布
  适用：团队在国内、开源影响力在国内

方案二：GitHub 主 + Gitee 从（Pull 方向 + webhook）
  在 GitHub 开发 → 自动同步 Gitee 供国内访问
  适用：开源项目主阵地在 GitHub，国内用户免梯子

方案三：单向 + 手动（最稳）
  一端开发，另一端手动触发同步，避免自动覆盖风险
  适用：低频发布、对一致性要求高的项目
```

判断依据：**谁在提交，谁就是主**。开发提交只发生在主端，从端永远被动接收。镜像期间不要手动改从端仓库，否则下次同步覆盖你的改动。

## 6. 镜像失败排查

| 现象 | 原因 | 解法 |
|------|------|------|
| 同步不触发 | Token 缺 repo 权限 | 重新生成含 repo 的 token |
| 自动同步失败 | 缺 admin:repo_hook | 补授权后重配 |
| webhook 401 | Secret 与令牌不一致 | 核对 Gitee 个人令牌 |
| 同步超时 | 仓库过大 | 换手动镜像或本地迁移 |
| LFS 文件缺失 | 不支持 LFS | 单独走对象存储 |
| 目标被覆盖 | 从端有独有提交 | 先备份；明确主从 |

排查顺序：先看 Gitee 镜像管理页的最近同步状态（成功/失败/耗时），再检查 Token 权限与 webhook 配置，最后确认仓库大小与 LFS 情况。

镜像的替代方案对比：需要"同步"但不想用镜像时，可选 **GitHub Actions 同步脚本**（push 后触发脚本 push 到 Gitee，灵活可控但多一份维护）、**手动导入**（低频场景，一次性）、**纯本地双远程**（`git remote add github ...` + `git push --all github`，全手动最可控）。镜像适合"自动且省心"，脚本适合"要定制逻辑"，双远程适合"偶尔同步"——按频率与定制需求选择，不要为了自动化而自动化。

镜像的适用判断还可以从"受众"出发：**谁读谁写**——代码被国内团队读写（含 CI 拉取），Gitee 为主；代码面向全球开源社区，GitHub 为主；国内用户只是"看"（下载/issue），用 Pull 方向镜像即可。镜像不能解决的两类需求：**开源项目的贡献者管理**（PR 与 Issue 不镜像，社区治理还在 GitHub 侧）与**下载流量**（Release 附件也不随镜像走，国内分发要靠 Gitee 侧单独上传）——这些场景要把"镜像 + 手动维护"结合。
