UML类图核心知识点
UML（统一建模语言）类图是Java后端开发中核心的建模工具，用于描述系统中类的结构、属性、方法及类与类之间的关系，是需求分析、架构设计、代码落地及团队协作的重要载体。核心围绕“类的定义”和“类间关系”展开，以下是后端开发必备的核心知识点，适配实战与面试场景。
一、UML类图核心基础（后端开发高频）
1.1 类的UML表示
UML类图中，类用矩形表示，分为3层（自上而下），与Java类的结构完全对应，无需多余修饰，简洁明了：
第一层：类名（居中），普通类直接写类名；抽象类斜体表示；接口用「I+类名」或斜体，部分场景会添加「<<interface>>」标识。
第二层：属性（成员变量），格式：可见性 属性名 : 数据类型 [= 默认值]。
第三层：方法（成员方法），格式：可见性 方法名(参数列表) : 返回值类型。
核心注意（后端重点）：可见性对应Java的访问修饰符，必须规范：+（public，公开）、#（protected，保护）、-（private，私有）、~（package-private，包访问权限，后端较少用）；抽象方法斜体表示，与Java抽象方法一致。
示例（Java实体类对应UML）：
// Java实体类
public class User {
    private Long id;
    public String username;
    protected Integer age;
    public void login(String password) {}
    private String getUsername() { return username; }
}
// 对应UML类表示（矩形3层）
User
-id : Long
+username : String

# ge : Integer
+login(password: String) : void
-login() : String
1.2 接口的UML表示（后端高频）
Java后端中接口（如DAO接口、Service接口）是核心，UML中有两种常用表示方式，均适配后端场景：
方式1：矩形表示（与类一致），类名斜体，或添加「<<interface>>」标识，仅包含方法（无属性，除非是常量）。
方式2：棒棒糖表示（简洁），圆形+接口名，通过直线连接实现该接口的类，适合类图元素较多、追求简洁的场景。
示例（Java接口对应UML）：
// Java接口
public interface UserService {
    void addUser(User user);
    User getUserById(Long id);
}
// 对应UML表示（方式1）
<<interface>>
UserService
+addUser(user: User) : void
+getUserById(id: Long) : User
二、Java后端高频UML类间关系（核心重点）
类间关系是UML类图的核心，后端开发中重点关注6种关系，需区分清楚含义、表示方式及Java中的对应实现，避免混淆（面试高频考点）。
2.1 继承关系（Generalization）
含义：子类继承父类（或实现类实现接口），子类拥有父类的属性和方法，可重写父类方法（类继承）或实现接口方法（接口实现）。
UML表示：空心三角形+实线，三角形指向父类（或接口），实线连接子类（或实现类）。
Java对应：类继承用extends关键字；接口实现用implements关键字。
后端场景：实体类继承BaseEntity（公共属性：id、createTime）、Service实现类继承Service接口（如UserServiceImpl implements UserService）。
2.2 实现关系（Realization）
含义：类实现接口，是“继承关系”的特殊形式，仅适用于接口与实现类之间。
UML表示：空心三角形+虚线，三角形指向接口，虚线连接实现类；也可使用“棒棒糖”表示（接口圆形+直线连接实现类）。
Java对应：implements关键字，如UserDaoImpl implements UserDao。
注意：Java中类可实现多个接口，UML中表现为多个“空心三角形+虚线”指向不同接口。
2.3 关联关系（Association）
含义：两个类之间存在固定的依赖关系（非临时），分为单向关联和双向关联，后端中以单向关联为主。
UML表示：实线，单向关联（最常用）：实线带箭头，箭头指向被关联的类；双向关联：无箭头实线。
Java对应：一个类中包含另一个类的对象作为成员变量，如Order类包含User对象（订单属于某个用户）。
后端场景：Order类关联User类（private User user;）、Service类关联Dao类（private UserDao userDao;）。
补充：关联关系可标注“多重度”（后端常用），表示类之间的数量对应关系，如1对多（1:*）、多对多（*:*），示例：Order（1）-->（*）OrderItem（一个订单包含多个订单项）。
2.4 聚合关系（Aggregation）
含义：“整体-部分”关系，部分可脱离整体独立存在（弱关联），是关联关系的特殊形式。
UML表示：空心菱形+实线，菱形指向整体，实线连接部分，可标注多重度。
Java对应：整体类包含部分类的对象，部分类可独立创建，如Department（整体）包含Employee（部分），员工可脱离部门存在。
后端场景：团队（Team）聚合成员（Member）、订单（Order）聚合商品（Product）。
2.5 组合关系（Composition）
含义：“整体-部分”关系，部分无法脱离整体独立存在（强关联），整体销毁时部分也会销毁，是比聚合更强的关联。
UML表示：实心菱形+实线，菱形指向整体，实线连接部分。
Java对应：整体类的构造方法中创建部分类的对象，部分类无法独立创建，如User（整体）包含Address（部分），地址无法脱离用户存在。
后端场景：用户（User）组合地址（Address）、订单（Order）组合支付信息（PaymentInfo）。
后端高频区分：聚合vs组合（面试常考）——聚合是“弱依赖”（部分可独立），组合是“强依赖”（部分不可独立）；如“班级-学生”是聚合（学生可转班），“人-心脏”是组合（心脏无法脱离人存在）。
2.6 依赖关系（Dependency）
含义：两个类之间临时的依赖关系（非固定），一个类的方法执行需要另一个类的对象作为参数或局部变量，依赖关系是最弱的类间关系。
UML表示：虚线+箭头，箭头指向被依赖的类（即“谁被用，箭头指向谁”）。
Java对应：方法参数、局部变量、静态方法调用，如UserService的login方法依赖UserDao的selectByUsername方法（参数或局部变量）。
后端场景：Service方法依赖Dao方法、工具类（如StringUtils）被其他类临时调用。
三、Java后端UML类图实战规范（避坑重点）
命名规范：类名、接口名、属性名、方法名与Java代码完全一致，避免缩写（除非是通用缩写，如Dao、Service）；接口名统一前缀为I（如IUserService），或不前缀但斜体标注，保持团队统一。
可见性规范：必须标注属性和方法的可见性（+/-/#），对应Java的public/private/protected，禁止省略；包访问权限（~）后端几乎不用，避免使用。
关系规范：优先使用单向关联（避免双向关联，降低耦合）；聚合与组合区分清晰，不混淆使用；依赖关系仅用于临时调用，不用于固定成员变量（固定成员变量用关联关系）。
实战简化：后端类图以“清晰易懂”为核心，无需标注所有属性和方法，仅标注核心属性（如实体类的主键、核心字段）和核心方法（如Service的核心业务方法），避免类图过于臃肿。
与设计模式结合：设计模式的类图需清晰呈现核心角色的关系，如访问者模式中，对象结构与元素是关联关系，元素与访问者是依赖关系，严格对应代码实现。
工具适配：后端常用工具（IDEA插件、StarUML、DrawIO）绘制类图，确保图形规范（如箭头方向、菱形/三角形样式），可直接导出用于文档或面试展示。
四、后端面试高频考点（UML类图）
1. 区分6种类间关系（重点：聚合vs组合、依赖vs关联），并说明Java中的实现方式。
2. 绘制指定设计模式的UML类图（如访问者模式、策略模式），标注核心角色和关系。
3. 说明UML类图中抽象类、接口的表示方式，与Java代码的对应关系。
4. 后端开发中，类图的核心作用（需求落地、架构设计、团队协作、代码映射）。
    核心总结：Java后端UML类图的核心是“映射Java代码结构”，重点掌握「类的表示」「6种类间关系」「实战规范」，无需追求复杂，只需确保类图与代码一致、关系清晰，既能满足日常开发协作，也能应对面试考察。
