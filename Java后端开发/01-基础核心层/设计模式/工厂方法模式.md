# 工厂方法模式
在掌握简单工厂模式后，我们完成了对象创建逻辑与业务逻辑的初步解耦，依靠统一工厂类封装实例化流程，简化客户端调用。但简单工厂存在无法根治的架构缺陷：新增产品时必须修改工厂内部分支判断代码，直接违反**开闭原则**；同时唯一工厂包揽全部产品的创建工作，职责臃肿、代码冗余，难以支撑产品持续迭代的复杂业务。

工厂方法模式（Factory Method Pattern）属于GoF 23种创建型设计模式，是简单工厂的标准化重构与进阶方案。它从架构层面解决开闭原则冲突，细化各模块职责、降低代码耦合，是企业级开发中对象创建场景的主流方案。下文从定义、角色、代码实现、执行流程、优劣、场景、工程规范、横向对比完整梳理。

## 一、模式核心定义
工厂方法模式又称工厂模式，归属创建型设计模式。核心思想：**定义抽象工厂接口，规范创建对象的标准工厂方法，将各类产品的实例化逻辑下沉到独立具体工厂；客户端仅依赖抽象层编码，实现对扩展开放、对修改关闭**。

与简单工厂集中式单一工厂不同，工厂方法把工厂层拆分为「抽象工厂+多个具体工厂」两层结构，一个具体工厂只负责生产一类产品，严格遵守单一职责、开闭原则、依赖倒置三大面向对象核心准则，彻底分离对象创建与业务执行代码，适配业务持续新增产品的扩展需求。

## 二、模式四大核心角色
整体分为产品体系、工厂体系两层，共四类角色，边界清晰、高内聚低耦合：
1. **抽象产品 Abstract Product**
    顶层抽象接口/抽象类，定义所有产品统一的业务行为规范，是全部具体产品的父类型。客户端直接依赖该抽象层，是落地依赖倒置原则的关键。
2. **具体产品 Concrete Product**
    实现抽象产品接口，完成专属业务逻辑，是工厂最终产出的实例对象；每一类产品对应独立实现类。
3. **抽象工厂 Abstract Factory**
    工厂层顶层抽象，仅声明统一的产品创建工厂方法，不包含任何实例化代码，约束所有具体工厂必须实现创建逻辑。
4. **具体工厂 Concrete Factory**
    实现抽象工厂接口，重写工厂方法，内部仅负责创建对应单一产品；一个工厂只生产一类产品，严格遵循单一职责。

## 三、标准代码实现
以IM即时通讯系统消息处理器为业务场景，基于简单工厂重构为工厂方法模式，保持场景连贯：
### 1. 抽象产品：统一消息处理接口
```java
public interface MessageHandler {
    void handleMessage(String content);
}
```

### 2. 具体产品：各类消息处理器
```java
public class TextMessageHandler implements MessageHandler {
    @Override
    public void handleMessage(String content) {
        System.out.println("文本消息处理：" + content);
    }
}

public class ImageMessageHandler implements MessageHandler {
    @Override
    public void handleMessage(String content) {
        System.out.println("图片消息处理：" + content);
    }
}

public class VoiceMessageHandler implements MessageHandler {
    @Override
    public void handleMessage(String content) {
        System.out.println("语音消息处理：" + content);
    }
}
```

### 3. 抽象工厂：创建处理器规范
```java
public interface MessageHandlerFactory {
    MessageHandler createHandler();
}
```

### 4. 具体工厂：对应产品专属工厂
```java
public class TextMessageHandlerFactory implements MessageHandlerFactory {
    @Override
    public MessageHandler createHandler() {
        return new TextMessageHandler();
    }
}

public class ImageMessageHandlerFactory implements MessageHandlerFactory {
    @Override
    public MessageHandler createHandler() {
        return new ImageMessageHandler();
    }
}

public class VoiceMessageHandlerFactory implements MessageHandlerFactory {
    @Override
    public MessageHandler createHandler() {
        return new VoiceMessageHandler();
    }
}
```

### 5. 客户端调用层
客户端仅依赖抽象工厂、抽象产品，无任何具体实现硬耦合：
```java
public class ImClient {
    public static void main(String[] args) {
        MessageHandlerFactory textFactory = new TextMessageHandlerFactory();
        MessageHandler textHandler = textFactory.createHandler();
        textHandler.handleMessage("工厂方法模式实战");

        MessageHandlerFactory imageFactory = new ImageMessageHandlerFactory();
        MessageHandler imageHandler = imageFactory.createHandler();
        imageHandler.handleMessage("im_img_001.jpg");
    }
}
```

## 四、模式完整执行流程
1. 客户端实例化目标对应的具体工厂，代码仅面向抽象工厂接口声明，不绑定具体工厂实现；
2. 调用抽象工厂定义的`createHandler`工厂方法，实际执行逻辑由子类具体工厂实现；
3. 具体工厂内部完成对应产品实例化，向上返回抽象产品类型对象；
4. 客户端调用抽象产品的业务方法，完全隔离产品实现细节；
5. 新增消息类型时，只需新增「具体产品类+配套具体工厂类」，原有所有代码无需改动，无侵入扩展。

## 五、核心优缺点
### 优点
1. **完全符合开闭原则**
    新增产品仅新增两个类，无需修改现有工厂与业务代码，解决简单工厂修改分支逻辑的致命问题，适配频繁迭代业务。
2. **单一职责落地彻底**
    每个工厂只生产一种产品，创建逻辑分散独立，不会出现单一工厂代码臃肿、职责过载问题。
3. **极致解耦，遵循依赖倒置**
    客户端全程依赖抽象层，不感知具体产品、具体工厂实现，系统可维护性、灵活度大幅提升。
4. **扩展无侵入**
    新增功能不会改动存量代码，不会影响线上原有业务逻辑，适配中大型、分布式系统迭代。
5. **架构标准化**
    分层结构统一，团队协作编码规范一致，便于调试、维护、迭代。

### 缺点
1. **类文件数量成倍增加**
    每新增一款产品，就要配套新增产品类、工厂类，产品品类庞大时，类文件管理成本显著上升。
2. **学习与落地门槛更高**
    相比简单工厂单层结构，新增抽象工厂分层，初学者理解成本更高。
3. **客户端需感知具体工厂**
    原生实现下客户端必须手动new对应工厂，无法通过参数统一分发；工程中通常搭配配置文件、Spring IOC容器优化。

## 六、适用业务场景
1. 产品品类丰富、持续新增类型，且项目强制要求遵循开闭原则、需要高扩展性；
2. 需要屏蔽对象创建细节，业务层只面向抽象接口开发，彻底分离创建与业务逻辑的中大型项目；
3. 单个产品实例化流程复杂，需要独立封装维护，避免创建逻辑污染业务代码；
4. 微服务、分布式系统中标准化组件、工具Bean、业务处理器统一创建管理；
5. 原有系统使用简单工厂，因频繁扩展需要重构，解决开闭原则违规问题。

## 七、工程落地规范与优化方案
1. **控制产品规模，避免类爆炸**
    若产品数量极多，可升级为抽象工厂模式，按产品分组管理，减少工厂类数量。
2. **结合IOC容器消除硬编码**
    Spring等企业框架中，将所有具体工厂注册为Bean，客户端通过容器获取工厂，不再手动new具体工厂，进一步降低耦合。
3. **抽象工厂改用抽象类抽取公共逻辑**
    若多个工厂存在重复创建逻辑，把抽象工厂从接口改为抽象类，封装通用代码，子类仅实现差异化逻辑，减少冗余。
4. **统一标准化异常处理**
    产品实例化失败时，在具体工厂抛出统一业务异常，方便全局异常捕获、问题定位。
5. **无状态产品做单例优化**
    对于无状态产品，在工厂内部实现单例，避免频繁创建销毁对象，提升系统性能。
6. **按需选型，拒绝过度设计**
    小型项目、产品固定几乎不迭代，优先简单工厂；中大型、需求持续扩展项目，选用工厂方法模式。

## 八、简单工厂 vs 工厂方法模式对比
|对比维度|简单工厂模式|工厂方法模式|
| ---- | ---- | ---- |
|设计原则|违反开闭原则|严格遵守开闭、单一职责、依赖倒置|
|工厂职责|一个工厂创建全部产品，职责过载|一个工厂仅生产一类产品，分工清晰|
|扩展方式|新增产品必须修改工厂分支代码|新增产品仅新增类，存量代码无改动|
|代码结构|单层结构，类数量少，简单易上手|双层抽象架构，分层清晰，类文件更多|
|适用场景|小型项目、产品固定、迭代极少|中大型项目、产品持续迭代、高扩展需求|

## 九、章节总结
工厂方法模式是简单工厂模式的进阶优化方案，依靠抽象工厂分层架构，彻底解决简单工厂违背开闭原则的核心缺陷，将三大核心面向对象设计原则贯穿对象创建全流程。

该模式核心价值是实现创建逻辑与业务逻辑完全解耦，支持无侵入横向扩展，是工业级项目对象创建场景的标准方案。实际开发中不能盲目套用，需要结合项目体量、产品迭代频率合理选型：既要规避简单工厂无法扩展的短板，也要防止工厂方法模式类数量过多造成过度设计。

熟练掌握工厂方法模式，不仅能规范对象创建代码，更能建立抽象分层的设计思维，为后续学习抽象工厂模式、框架源码阅读、分布式架构设计打下基础。
