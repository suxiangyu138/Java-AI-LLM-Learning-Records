## 1. 认证与授权基础

### 1.1 概念区分

```
认证（Authentication = AuthN）：你是谁？
  验证用户身份的过程
  手段：用户名密码、短信验证码、指纹/人脸、二维码扫码

授权（Authorization = AuthZ）：你能干什么？
  验证用户是否有权限访问某个资源
  手段：角色（ROLE_ADMIN）、权限（user:delete）

凭证（Credentials）：你如何证明你是谁？
  认证成功后获得的凭证，用于后续请求的身份证明
  形式：SessionId（Cookie）、JWT Token（Header）

身份提供商（IdP = Identity Provider）：
  专门负责认证的三方服务
  如：微信登录、Google 登录、企业 SSO
```

### 1.2 主流认证方案对比

| 方案 | 存储位置 | 跨域 | 移动端 | 可伸缩性 | 主动失效 | 适用场景 |
|------|---------|------|--------|---------|---------|---------|
| Cookie-Session | 服务端 | ❌ | ❌ | ⚠️(需 Redis) | ✅ | SSR 传统 Web |
| JWT | 客户端 | ✅ | ✅ | ✅ | ❌(需黑名单) | SPA/App/API |
| OAuth 2.0 | Token 服务 | ✅ | ✅ | ✅ | ✅ | 第三方登录/开放平台 |

## 2. JWT 深度解析

### 2.1 JWT 结构

```
JWT = Header.Payload.Signature

Header:  Base64Url({
    "alg": "RS256",    // 签名算法
    "typ": "JWT"       // 类型
})

Payload:  Base64Url({
    "iss": "api.example.com",        // 签发者 Issuer
    "sub": "12345",                  // 主题 Subject（通常为用户 ID）
    "aud": "mobile-app",             // 受众 Audience（接收方）
    "exp": 1718254200,               // 过期时间 Expiration Time
    "nbf": 1718167800,               // 生效时间 Not Before
    "iat": 1718167800,               // 签发时间 Issued At
    "jti": "unique-token-id",        // JWT ID（防重放）
    // 自定义声明：
    "name": "张三",
    "roles": ["user", "admin"],
    "deptId": 5
})
// ⚠️ Payload 只是 Base64Url 编码，不是加密！不要放敏感信息（密码、手机号）

Signature:
  HMAC-SHA256(
      Base64Url(Header) + "." + Base64Url(Payload),
      Secret       // HMAC 对称密钥 或 RSA 私钥
  )

// 最终：eyJhbGci...（Header）+ .eyJzdWIi...（Payload）+ .SflKxwR...（Signature）
```

### 2.2 签名算法选择

```
对称算法（共享密钥，如 HS256）：
  签名和验证用同一把密钥
  优点：快
  缺点：密钥共享有安全风险（所有需要验证 JWT 的服务都要有密钥）
  适用：单体应用、小规模

非对称算法（公私钥，如 RS256 / ES256）：
  签发用私钥，验证用公钥
  优点：公钥可以安全分发（放网关、Nginx、配置中心）
  微服务中推荐！
  签发服务（Auth-Service）持有私钥
  其他服务持有公钥即可验证

算法	        类型	    密钥长度	摘要长度	性能
HS256	      HMAC      256-bit	   256-bit	   快
RS256	      RSA	     2048-bit   256-bit	   中
ES256	      ECDSA	 256-bit	   256-bit	   快(小密钥)
EdDSA	      Ed25519	 256-bit	   256-bit	   最快
```

### 2.3 双 Token 机制

```
Access Token（访问令牌）：
  - 短期（15min - 2h）
  - 用于 API 请求鉴权
  - 放在 Header: Authorization: Bearer <access_token>
  - 过期了用 Refresh Token 换新

Refresh Token（刷新令牌）：
  - 长期（7d - 30d）
  - 只用于换新的 Access Token（不参与业务请求）
  - 存储在安全的 HTTP-only Cookie 或安全存储
  - 暴露风险更小（不发到业务接口）

流程：
  1. 登录 → 返回 Access Token + Refresh Token
  2. 请求 API → 带 Access Token
  3. Access Token 过期返回 401
  4. 客户端用 Refresh Token 换新的 Access Token
  5. Refresh Token 过期 → 重新登录

Refresh Token 轮换（Rotation）：
  每次刷新 → 旧的 Refresh Token 失效 → 返回新的 Refresh Token
  防止 Refresh Token 被盗 → 定期复用
```

### 2.4 JWT 安全实践

```
安全使用 JWT 的 10 条建议：

1. Token 放 Header，不放 URL
   ❌ GET /api/users?token=xxx（Token 出现在日志、浏览器历史）
   ✅ Authorization: Bearer xxx

2. 设置合理的过期时间
   Access Token: 15 分钟
   Refresh Token: 7 天

3. 使用非对称加密（RS256/ES256）
   公钥分发无风险，私钥集中保管

4. Payload 不存储敏感数据
   密码、手机号、身份证等不要放 Payload

5. Token 黑名单（登出/封禁时用）
   Redis 维护黑名单，key = jti，过期时间 = Token 剩余有效期

6. 签名算法白名单
   校验时只接受预先配置的算法
   防止 alg:none 攻击！

7. HTTPS 全链路
   JWT 在网络传输中需要 TLS 保护

8. 验证所有标准声明
   exp（过期）、nbf（生效）、iss（签发者）、aud（受众）

9. 使用 jti 防重放
   对关键操作（支付、转账），检查 jti 是否已被使用

10. 限制 Payload 大小
    不要让 JWT 变得太大（影响每次请求的 Header 大小）
```

## 3. OAuth 2.0 与 OIDC

### 3.1 授权码模式（最安全最常用）

```
授权码模式 + PKCE（当前推荐的安全标准）：

角色：
  Resource Owner（资源所有者）  = 用户
  Client（客户端）              = Web 应用 / App
  Authorization Server（授权服务器） = 认证中心
  Resource Server（资源服务器）   = API 服务

流程（SPA/移动 App 带 PKCE）：
  Step 1: 客户端生成 code_verifier（随机字符串）
          计算 code_challenge = SHA256(code_verifier)

  Step 2: 浏览器重定向到授权服务器
          GET /authorize?
              response_type=code
              &client_id=my-app
              &redirect_uri=https://app.example.com/callback
              &code_challenge=<challenge>
              &code_challenge_method=S256
              &scope=openid profile email
              &state=random-string（防 CSRF）

  Step 3: 用户在授权服务器登录 + 授权

  Step 4: 授权服务器重定向回客户端
          https://app.example.com/callback?code=xxx&state=random-string
          （state 需要验证匹配！）

  Step 5: 客户端后端（或前端 BFF）用 code + code_verifier 换 Token
          POST /token
            grant_type=authorization_code
            &code=xxx
            &code_verifier=<verifier>
            &client_id=my-app
            &redirect_uri=https://app.example.com/callback

  Step 6: 获得 access_token + refresh_token + id_token(如果是 OIDC)

PKCE 的作用：
  防止授权码拦截攻击（恶意 App 截获回调 URL 中的 code）
  没有 code_verifier → 无法用 code 换 token
```

### 3.2 四种授权模式对比

| 模式 | 客户端类型 | 是否需要后端 | 安全性 | 状态 |
|------|-----------|------------|--------|------|
| **授权码 + PKCE** | 所有类型 | 不强制（PKCE 增强） | ⭐⭐⭐⭐⭐ | ✅ 推荐 |
| **客户端凭证** | 机对机（M2M） | N/A | ⭐⭐⭐⭐ | ✅ 推荐 |
| 隐式模式 | SPA | 否 | ⭐⭐ | ❌ 废弃 |
| 密码模式 | 自家 App | 是 | ⭐⭐⭐ | ❌ 废弃 |

### 3.3 OIDC（OpenID Connect）

```
OAuth 2.0 = 授权协议（给权限，但不知道你是谁）
OIDC = 基于 OAuth 2.0 的身份认证层（知道你是谁）

OIDC 在 OAuth 2.0 基础上增加了：
  id_token（JWT 格式，包含用户的身份信息）
  /userinfo 端点（获取用户资料的 REST API）
  标准 Claims（sub 用户 ID, name, email, picture...）

id_token vs access_token：
  id_token     → 给客户端看的（证明用户身份）→ 不是用来调 API！
  access_token → 给 API 用的（证明有权限访问资源）

Token 验证时机：
  客户端 → 验证 id_token（确认用户身份）
  API    → 验证 access_token（确认有权限）
```

## 4. Spring Security 完全指南

### 4.1 过滤器链

```
Spring Security 过滤器链（部分）：

┌────────────────────────────────────────────────┐
│ DisableEncodeUrlFilter                          │
│ WebAsyncManagerIntegrationFilter               │
│ SecurityContextHolderFilter（管理 SecurityContext） │
│ HeaderWriterFilter（安全 Headers）              │
│ CorsFilter（跨域）                              │
│ CsrfFilter（CSRF 防护）                         │
│ LogoutFilter（登出处理）                        │
│ OAuth2AuthorizationRequestRedirectFilter        │
│ BearerTokenAuthenticationFilter（JWT Bearer 解析）│
│ UsernamePasswordAuthenticationFilter（表单登录） │
│ DefaultLoginPageGeneratingFilter（默认登录页）   │
│ DefaultLogoutPageGeneratingFilter（默认登出页）  │
│ BasicAuthenticationFilter（HTTP Basic Auth）    │
│ RequestCacheAwareFilter                         │
│ SecurityContextHolderAwareRequestFilter         │
│ ExceptionTranslationFilter（异常转 403/401）     │
│ AuthorizationFilter（最终授权）                 │
│ FilterSecurityInterceptor                       │
└────────────────────────────────────────────────┘

核心过滤器详解：

SecurityContextHolderFilter：
  把 SecurityContext 放到 SecurityContextHolder 中（请求结束时清除）
  SecurityContextHolder 默认用 ThreadLocal 存储

BearerTokenAuthenticationFilter：
  从 Authorization: Bearer xxx 中提取 Token
  → 交给 AuthenticationManager 认证
  → 认证成功 → 设置 SecurityContext

AuthorizationFilter / FilterSecurityInterceptor：
  检查当前用户是否有权限访问该 URL
  基于 AccessDecisionManager（投票器）
```

### 4.2 JWT + Spring Security 完整实现

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity  // 开启方法级安全（@PreAuthorize）
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            // 无状态
            .sessionManagement(session ->
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))

            // CSRF 关闭（前后端分离，Token 不在 Cookie 中）
            .csrf(AbstractHttpConfigurer::disable)

            // 异常处理
            .exceptionHandling(ex -> ex
                .authenticationEntryPoint((req, res, e) -> {
                    res.setContentType("application/json;charset=utf-8");
                    res.getWriter().write("{\"code\":401,\"message\":\"未登录或 Token 已过期\"}");
                })
                .accessDeniedHandler((req, res, e) -> {
                    res.setContentType("application/json;charset=utf-8");
                    res.getWriter().write("{\"code\":403,\"message\":\"无权限访问\"}");
                }))

            // 权限配置
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()     // 登录注册
                .requestMatchers("/api/public/**").permitAll()   // 公开接口
                .requestMatchers("/actuator/health").permitAll() // 健康检查
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())

            // JWT 过滤器
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)

            // OAuth2 资源服务器模式（可替代 JWT 过滤器）
            // .oauth2ResourceServer(oauth2 ->
            //     oauth2.jwt(jwt -> jwt.jwtDecoder(jwtDecoder())));

        return http.build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
        // 默认使用 BCrypt（自适应哈希）
        // 支持多种编码格式：{bcrypt}$2a$10$...  {noop}plaintext
    }

    @Bean
    public AuthenticationManager authenticationManager(AuthenticationConfiguration config)
        throws Exception {
        return config.getAuthenticationManager();
    }
}
```

### 4.3 方法级安全

```java
// 开启：@EnableMethodSecurity

@RestController
public class UserController {

    // 基于角色的访问控制
    @PreAuthorize("hasRole('ADMIN')")
    @GetMapping("/admin/users")
    public Result<?> listAllUsers() { ... }

    // 基于权限的访问控制
    @PreAuthorize("hasAuthority('user:delete')")
    @DeleteMapping("/users/{id}")
    public Result<?> deleteUser(@PathVariable Long id) { ... }

    // 组合条件
    @PreAuthorize("hasRole('ADMIN') or #id == authentication.principal.id")
    @GetMapping("/users/{id}")
    public Result<?> getUser(@PathVariable Long id) { ... }

    // 方法返回后的过滤
    @PostAuthorize("returnObject.data.status != 'DELETED'")
    @GetMapping("/orders/{id}")
    public Result<Order> getOrder(@PathVariable Long id) { ... }

    // 参数过滤
    @PreFilter("filterObject.ownerId == authentication.principal.id")
    @PostMapping("/batch/delete")
    public Result<?> batchDelete(@RequestBody List<Order> orders) { ... }

    // 返回结果过滤
    @PostFilter("filterObject.ownerId == authentication.principal.id")
    @GetMapping("/orders")
    public List<Order> listOrders() { ... }
}
```

## 5. RBAC 与权限模型

### 5.1 RBAC 核心模型

```
RBAC（Role-Based Access Control）：

基础模型（RBAC0）：
  User -m:n- Role -m:n- Permission
  张三    →      管理员    →    用户:删除
  李四    →      编辑者    →    用户:编辑

扩展模型：
  RBAC1（角色继承）：
    管理员 → 编辑者 → 读者
    （管理员拥有编辑者和读者的所有权限）

  RBAC2（职责分离）：
    限制互斥角色（同一用户不能同时是"下单人"和"审核人"）
    基数限制（最多 N 个超级管理员）

  RBAC3：RBAC1 + RBAC2

数据库设计：
  sys_user          (id, username, password, ...)
  sys_role          (id, name, code, ...)
  sys_permission    (id, name, code, url, method, ...)
  sys_user_role     (user_id, role_id)
  sys_role_permission (role_id, permission_id)
```

### 5.2 动态权限控制

```java
// 动态权限（从数据库加载权限规则）
@Component
public class DynamicAuthorizationManager implements AuthorizationManager<RequestAuthorizationContext> {

    private final PermissionService permissionService;

    @Override
    public AuthorizationDecision check(Supplier<Authentication> authentication,
                                       RequestAuthorizationContext context) {
        // 1. 获取当前用户权限列表
        Collection<? extends GrantedAuthority> authorities =
            authentication.get().getAuthorities();

        // 2. 获取当前请求所需的权限（URL + Method 匹配）
        String path = context.getRequest().getRequestURI();
        String method = context.getRequest().getMethod();
        Set<String> requiredPermissions =
            permissionService.getRequiredPermissions(path, method);

        // 3. 判断用户是否有所需权限
        boolean granted = authorities.stream()
            .map(GrantedAuthority::getAuthority)
            .anyMatch(requiredPermissions::contains);

        return new AuthorizationDecision(granted);
    }
}

// 应用动态权限管理器
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth ->
        auth.anyRequest().access(dynamicAuthorizationManager));
    return http.build();
}
```

## 6. 常见安全漏洞与防护

### 6.1 OWASP Top 10 防护

```
1. 注入（Injection）
  SQL 注入：用 PreparedStatement / MyBatis #{}
  XSS：CSP Header + 输出编码

2. 失效的身份认证
  密码强度要求、多因素认证、登录频率限制、失败锁账户

3. 敏感数据泄露
  密码哈希存储（BCrypt）、HTTPS 全链路、敏感字段脱敏

4. XML 外部实体（XXE）
  禁用外部实体解析

5. 失效的访问控制
  服务端校验（不依赖前端隐藏按钮）
  @PreAuthorize 方法级控制

6. 安全配置错误
  关闭 Debug 模式、不要暴露错误堆栈

7. 跨站脚本（XSS）
  反射型/存储型/DOM 型
  CSP Header + 输出编码 + HttpOnly Cookie

8. 不安全的反序列化
  不信任输入的反序列化
  Jackson 的 enableDefaultTyping 谨慎使用

9. 使用含有已知漏洞的组件
  定期依赖扫描（OWASP Dependency-Check、Snyk）

10. 日志和监控不足
    记录登录/敏感操作日志、异常行为告警
```

### 6.2 CSRF 与 XSS 防护详解

```
CSRF（跨站请求伪造）：
  攻击：用户登录了 bank.com → 访问恶意网站
       → 恶意网站自动向 bank.com 发转账请求（带上 Cookie）
  防护：
    - SameSite Cookie: SameSite=Strict/Lax（最有效）
    - 前后端分离 + JWT in Header（不在 Cookie 中 → 自动免疫）
    - CSRF Token（表单中嵌入）
    - 检查 Origin/Referer Header

XSS（跨站脚本）：
  存储型：恶意脚本存在数据库，用户浏览时执行
  反射型：恶意脚本在 URL 参数中，服务端直接反射回页面
  DOM 型：前端 JS 不安全操作导致

  防护：
    输入校验：
      白名单校验（允许什么，只允许什么）
    输出编码：
      HTML 实体编码、JavaScript 编码、CSS 编码
    CSP（Content Security Policy）：
      Content-Security-Policy: default-src 'self'; script-src 'self'
    HttpOnly Cookie：
      Set-Cookie: session=xxx; HttpOnly（JS 无法读取）
```

## 7. API 安全最佳实践

```
1. 始终使用 HTTPS
   生产环境 HTTP → 301 重定向到 HTTPS
   HSTS（HTTP Strict Transport Security）

2. API 网关统一鉴权
   不在每个微服务重复实现认证逻辑
   Gateway 解析 Token → Header 传递给下游

3. 签名验证（防篡改）
   重要操作（支付/转账）加签名
   请求参数 + 时间戳 + Nonce + Secret → HMAC 签名
   → 防篡改 + 防重放

4. 频率限制（防暴力破解）
   登录接口限流：5 次/分钟/IP
   发送验证码限流：1 次/分钟/手机号

5. 敏感接口双重确认
   支付、修改手机号 → 短信验证码 + 支付密码

6. 最小权限原则
   Token 中只给当前应用所需的权限
   服务间调用用独立的 Client Credential

7. 请求日志审计
   记录：谁（userId）+ 什么时候（time）+ 做了什么（operation）
   敏感操作要有不可篡改的审计日志

8. 输入校验（永远不信任前端）
   即使前端校验了，后端也要再做一次
   @Valid + 自定义 Validator
```

## 8. 密码学基础

### 8.1 哈希与加密

```
哈希（不可逆）：
  MD5：128 bit，已不安全（碰撞攻击）
  SHA-256：256 bit，安全但适合完整性校验
  BCrypt：自适应哈希，迭代次数可调，防暴力破解
  Argon2：最新推荐，抗 GPU 并行破解

加密（可逆）：
  AES（对称加密）：加解密同一密钥
    模式：CBC（需 IV）、GCM（带认证）
    场景：数据库敏感字段加密

  RSA（非对称加密）：
    公钥加密，私钥解密；或私钥签名，公钥验签
    场景：JWT RS256 签名、HTTPS TLS 握手

Base64：
  不是加密，是编码！
  把二进制数据编码为可打印的 ASCII 字符
  场景：JWT 的 Base64Url 编码、图片 Data URI
```

### 8.2 BCrypt 原理

```
BCrypt 哈希 = 算法 + 迭代次数 + Salt + 密码

$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
 │   │  │                                                 │
 │   │  └────────── 22 位 Salt ──────────┘
 │   │
 │   └── Cost Factor（迭代次数 = 2^10 = 1024 次）
 │       每次迭代都重新生成子密钥的 S-Box
 │
 └────── 算法版本标识

特点：
  1. 每次生成不同的哈希值（随机 Salt）
  2. 天然防彩虹表攻击（Salt 不同）
  3. 慢哈希（故意慢，防暴力破解）
  4. Cost 越高越安全（也越慢，一般 10~12）

验证流程：
  1. 存储哈希值（包含 Salt + Cost）
  2. 用户登录 → 输入密码
  3. 取出哈希值 → 提取 Cost + Salt
  4. 用同样的 Cost + Salt 哈希输入的密码
  5. 比较两个哈希值 → 相同则密码正确
```

## 9. 常见面试题

### Q1: Token 过期了怎么办？

```
Access Token 过期 → 返回 401
客户端用 Refresh Token 换新的 Access Token
  1. 发送 POST /auth/refresh 带 Refresh Token
  2. 服务端验证 Refresh Token
     - 是否有效（签名正确）
     - 是否过期
     - 是否在黑名单中（被撤销）
  3. 验证通过 → 返回新的 Access Token（和新的 Refresh Token）
  4. Refresh Token 也过期 → 返回 401 → 跳转登录页

Refresh Token 冲突检测（防复用）：
  同一用户的 Refresh Token 同时并发刷 → 只接受第一个
  使用版本号或"已使用的 Refresh Token 集合"
```

### Q2: 单点登录（SSO）的实现原理？

```
SSO = Single Sign-On（一次登录，多个系统共享）

实现方案：

1. 同域 SSO（基于 Cookie）
   各系统同域名（a.example.com, b.example.com）
   Cookie 设 domain=.example.com
   共享 SessionId → Nginx 反向代理 + Redis 共享 Session

2. 跨域 SSO（基于 CAS 或 OAuth 2.0）
   认证中心 + Ticket 机制：
   1. 用户访问系统 A → 重定向到认证中心
   2. 用户登录 → 认证中心返回 Ticket（给系统 A）
   3. 系统 A 用 Ticket 去认证中心验证 → 获取用户信息
   4. 用户访问系统 B → 重定向到认证中心
   5. 认证中心已有登录状态 → 直接返回 Ticket

3. OIDC / OAuth 2.0 SSO（现代方案）
   认证中心是 OAuth 2.0 Authorization Server
   各系统是 OAuth 2.0 Client
   一次授权 → 各系统各自获得 Access Token
```

### Q3: 如何设计权限系统？

```
核心：RBAC（用户-角色-权限）

表设计：
  sys_user        (id, username, password, status, dept_id, ...)
  sys_role        (id, name, code, status, ...)
  sys_menu        (id, name, parent_id, path, component, icon, order, ...)
  sys_permission  (id, name, code, ...)
  sys_user_role       (user_id, role_id)
  sys_role_menu       (role_id, menu_id)
  sys_role_permission (role_id, permission_id)

权限粒度演进：
  Level 1: 菜单权限（能看到什么页面）
  Level 2: 按钮权限（能点什么按钮 → 增删改查）
  Level 3: 数据权限（能看到哪些数据 → 只能看自己部门的数据）

数据权限实现：
  - 部门隔离：WHERE dept_id IN (...)
  - MyBatis 插件：自动追加数据权限条件到 SQL
  - @DataScope(deptAlias = "d", userAlias = "u") 自定义注解
```
