# 单元测试与集成测试实战

## 前言

在软件工程领域，测试不是可选项，而是保障代码质量的核心手段。尤其在 Java 后端开发中，随着微服务架构的普及和 CI/CD 流水线的成熟，缺乏有效测试的项目几乎不可能保持高质量交付。本文从工程实战角度出发，系统性地讲解单元测试与集成测试的核心概念、主流框架（JUnit 5、Mockito、Spring Boot Testing、Testcontainers）的使用方法，以及业界最佳实践，帮助读者构建一套可落地、可维护的测试体系。

---

## 一、测试基础

### 1.1 测试金字塔

测试金字塔是 Mike Cohn 在其著作《Succeeding with Agile》中提出的经典模型，它将测试按粒度分为三层：

```
         /\
        /  \         E2E 端到端测试（约 10%）
       /    \
      /----------\
     /            \    集成测试（约 20%）
    /---------------\
   /                  \
  /---------------------\  单元测试（约 70%）
 /                       \
```

- **单元测试（Unit Test）**：测试最小的可测试单元（通常是单个方法或类），不依赖外部资源（数据库、网络、文件系统），速度极快（毫秒级），占总测试量的 70% 左右。
- **集成测试（Integration Test）**：验证多个模块之间的协作是否正确，通常涉及数据库、消息队列或远程服务，速度适中（秒级），约占总量的 20%。
- **端到端测试（End-to-End Test）**：模拟用户操作，验证整个系统链路是否正常工作，启动成本高、执行速度慢（分钟级），占总量的 10% 左右。

在实际项目中，**金字塔形状比绝对比例更重要**——保证底层有足够多的快速反馈测试，上层有少量高价值覆盖。如果项目中出现"倒金字塔"（大量 E2E 测试、少量单元测试），CI 流水线将异常缓慢，开发者的等待时间会急剧增加。

### 1.2 测试的价值

**回归防护（Regression Protection）**：代码重构或新增功能时，已有测试可快速捕获意外破坏。没有测试的项目，每次改动都像在走钢丝。

**文档作用（Living Documentation）**：好的测试是可运行的文档。阅读 `givenX_whenY_thenZ` 格式的测试，比翻阅几十页需求文档更快理解一个类的行为。

**驱动设计（TDD）**：测试驱动开发倡导"红-绿-重构"循环——先写失败测试，再写最小实现让测试通过，最后重构代码。这不仅提升了代码质量，更迫使开发者在编码前思考接口设计。

**重构信心（Refactoring Confidence）**：有充分测试覆盖的代码，开发者可以大胆进行重构。没有测试的"遗留代码"往往陷入"不敢改、越改越烂"的恶性循环。

### 1.3 FIRST 原则

优秀的单元测试应当遵循 FIRST 原则：

| 原则 | 含义 | 实践要点 |
|------|------|----------|
| **F**ast | 快速 | 单个测试应在毫秒级完成，避免网络 IO 和数据库操作 |
| **I**ndependent | 独立 | 测试之间不应有依赖，每个测试可单独运行，顺序无关 |
| **R**epeatable | 可重复 | 在任何环境下运行结果一致，不依赖外部状态 |
| **S**elf-Validating | 自验证 | 测试应自动判断通过/失败，无需人工检查 |
| **T**imely | 及时 | 测试应在生产代码之前或与之同步编写 |

违反 FIRST 原则最常见的例子是：测试 A 向数据库插入了一条记录，测试 B 依赖这条记录才能通过——当测试单独运行时就会失败。解决方案是让每个测试自己准备好所需数据，并在测试后清理。

## 二、JUnit 5 深度实践

JUnit 5 是 Java 生态中单元测试的事实标准，由三个子项目组成：**JUnit Platform**（测试引擎启动基础）、**JUnit Jupiter**（新编程模型和扩展 API）、**JUnit Vintage**（兼容 JUnit 4 的老测试运行器）。

### 2.1 核心注解

```java
import org.junit.jupiter.api.*;

class CalculatorTest {

    @BeforeAll
    static void setupClass() {
        // 在所有测试方法之前执行一次，必须为 static
        System.out.println("=== 初始化测试类资源 ===");
    }

    @AfterAll
    static void teardownClass() {
        // 在所有测试方法之后执行一次，必须为 static
        System.out.println("=== 清理测试类资源 ===");
    }

    @BeforeEach
    void setup() {
        // 每个测试方法之前执行，用于初始化测试对象
        System.out.println("准备测试用例");
    }

    @AfterEach
    void teardown() {
        // 每个测试方法之后执行，用于清理
        System.out.println("清理测试用例");
    }

    @Test
    @DisplayName("两数相加应返回正确和")
    void shouldReturnSumWhenAddTwoNumbers() {
        Calculator calc = new Calculator();
        int result = calc.add(3, 5);
        Assertions.assertEquals(8, result);
    }
}
```

关键注意事项：
- `@BeforeAll` / `@AfterAll` 方法**必须声明为 `static`**，除非修改了测试实例生命周期（见 2.7）。
- `@DisplayName` 支持中文和空格，在 IDE 和测试报告中的可读性远超方法名。

### 2.2 断言详解

JUnit 5 的 `Assertions` 类提供了丰富的断言方法，掌握它们是写好测试的基础。

```java
import static org.junit.jupiter.api.Assertions.*;

class AssertionDemoTest {

    private final Calculator calc = new Calculator();

    @Test
    @DisplayName("assertEquals: 期望值在前，实际值在后")
    void testAssertEquals() {
        assertEquals(4, calc.add(2, 2), "加法结果不正确");
        // 注意参数顺序: (expected, actual, message)
        // 期望值写前面是约定俗成，因为错误信息输出为 "expected: X but was: Y"
    }

    @Test
    @DisplayName("assertTrue / assertFalse")
    void testAssertBoolean() {
        assertTrue(calc.isPositive(5));
        assertFalse(calc.isPositive(-1));
    }

    @Test
    @DisplayName("assertThrows: 断言抛出特定异常")
    void testAssertThrows() {
        // 当 calc.divide(1, 0) 执行时，必须抛出 ArithmeticException 才通过
        ArithmeticException exception = assertThrows(
            ArithmeticException.class,
            () -> calc.divide(1, 0)
        );
        assertEquals("/ by zero", exception.getMessage());
    }

    @Test
    @DisplayName("assertAll: 批量断言，即使前面的失败也继续执行后续断言")
    void testAssertAll() {
        User user = new User("Alice", 25, "alice@example.com");

        // assertAll 会执行所有 lambda，收集所有失败信息一并报告
        assertAll("用户属性验证",
            () -> assertEquals("Alice", user.getName()),
            () -> assertTrue(user.getAge() >= 18),
            () -> assertTrue(user.getEmail().contains("@"))
        );
        // 如果三个断言中有多个失败，JUnit 会全部列出来，而不是停在第一个
    }

    @Test
    @DisplayName("assertTimeout: 超时断言")
    void testAssertTimeout() {
        // 如果方法执行超过 1 秒则失败
        assertTimeout(Duration.ofSeconds(1), () -> calc.heavyComputation());
    }
}
```

`assertAll` 是实际项目中非常有用的工具。在验证对象状态的场景中，如果第一个 `assertEquals` 失败后中止测试，你就无法知道后面还有多少失败——采用 `assertAll` 可以一次性获取全部失败信息，极大提升调试效率。

### 2.3 参数化测试

参数化测试允许用一组数据运行同一个测试方法，显著减少重复代码。

```java
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.*;

class ParameterizedTestDemo {

    @ParameterizedTest
    @ValueSource(ints = {1, 2, 3, 4, 5})
    @DisplayName("@ValueSource: 基本类型参数")
    void testWithValueSource(int number) {
        assertTrue(number > 0);
    }

    @ParameterizedTest
    @CsvSource({
        "1,    1,    2",
        "2,    3,    5",
        "10,  20,   30",
        "-1,   1,    0"
    })
    @DisplayName("@CsvSource: 多参数 CSV")
    void testWithCsvSource(int a, int b, int expected) {
        assertEquals(expected, calc.add(a, b));
    }

    @ParameterizedTest
    @CsvFileSource(resources = "/test-data.csv", numLinesToSkip = 1)
    @DisplayName("@CsvFileSource: 从CSV文件读取测试数据")
    void testWithCsvFileSource(int a, int b, int expected) {
        assertEquals(expected, calc.add(a, b));
    }

    @ParameterizedTest
    @MethodSource("provideUserData")
    @DisplayName("@MethodSource: 方法提供参数")
    void testWithMethodSource(String name, int age, boolean expectedAdult) {
        User user = new User(name, age);
        assertEquals(expectedAdult, user.isAdult());
    }

    static Stream<Arguments> provideUserData() {
        return Stream.of(
            Arguments.of("Alice", 20, true),
            Arguments.of("Bob", 17, false),
            Arguments.of("Charlie", 18, true)
        );
    }

    @ParameterizedTest
    @EnumSource(OrderStatus.class)
    @DisplayName("@EnumSource: 枚举参数")
    void testWithEnumSource(OrderStatus status) {
        assertNotNull(status.getDescription());
    }
}
```

**`@MethodSource` 的引用方法必须是 `static`**（除非使用了 `@TestInstance(Lifecycle.PER_CLASS)`）。对于复杂的测试数据构造，`@MethodSource` 是最灵活的选择，它甚至可以返回 `Stream<Arguments>`，允许程序化生成测试数据。

### 2.4 嵌套测试

`@Nested` 允许在内层类中对测试进行分组，为每个分组设置独立的 `@BeforeEach` / `@AfterEach`。

```java
import org.junit.jupiter.api.Nested;

class StackTest {

    private Stack<String> stack;

    @Test
    @DisplayName("新建栈应为空")
    void testNewStackIsEmpty() {
        stack = new Stack<>();
        assertTrue(stack.isEmpty());
    }

    @Nested
    @DisplayName("当栈不为空时")
    class WhenStackIsNotEmpty {

        @BeforeEach
        void pushElements() {
            stack = new Stack<>();
            stack.push("Element1");
            stack.push("Element2");
        }

        @Test
        @DisplayName("pop 应返回栈顶元素")
        void shouldReturnTopElementWhenPop() {
            assertEquals("Element2", stack.pop());
            assertFalse(stack.isEmpty());
        }

        @Nested
        @DisplayName("当栈满时")
        class WhenStackIsFull {

            @BeforeEach
            void fillStack() {
                for (int i = 0; i < Stack.MAX_SIZE - 2; i++) {
                    stack.push("Extra" + i);
                }
            }

            @Test
            @DisplayName("push 应抛出 StackOverflowException")
            void shouldThrowWhenPushOnFullStack() {
                assertThrows(StackOverflowException.class,
                    () -> stack.push("Overflow"));
            }
        }
    }
}
```

嵌套测试的结构天然对应 Arrange-Act-Assert 模式——外层类或 `@Nested` 的 `@BeforeEach` 执行 Arrange，具体 `@Test` 方法执行 Act 和 Assert。当测试的业务逻辑有多个分支状态时，`@Nested` 可以极为清晰地组织测试用例。

### 2.5 条件执行

JUnit 5 内置了基于操作系统、环境变量、系统属性等条件来决定是否执行测试的注解。

```java
import org.junit.jupiter.api.condition.*;

class ConditionalTestDemo {

    @Test
    @EnabledOnOs(OS.WINDOWS)
    @DisplayName("仅在 Windows 上运行")
    void onlyOnWindows() {
        // 测试 Windows 专属功能
    }

    @Test
    @DisabledOnOs(OS.LINUX)
    @DisplayName("在 Linux 上跳过")
    void notOnLinux() {
        // Linux 环境不支持的特性
    }

    @Test
    @EnabledOnJre(JRE.JAVA_17)
    @DisplayName("仅在 JDK 17 运行")
    void onlyOnJdk17() {
        // 使用 JDK 17 新特性的测试
    }

    @Test
    @EnabledIfEnvironmentVariable(named = "ENV", matches = "CI")
    @DisplayName("仅在 CI 环境运行")
    void onlyInCIContext() {
        // 需要 CI 环境配置的测试
    }
}
```

### 2.6 标签过滤

`@Tag` 允许为测试打上标签，在构建时选择性地运行。

```java
import org.junit.jupiter.api.Tag;
import org.junit.jupiter.api.Test;

class TaggedTestDemo {

    @Test
    @Tag("slow")
    @Tag("integration")
    @DisplayName("慢速集成测试")
    void slowIntegrationTest() {
        // 需要较长时间执行的测试
    }

    @Test
    @Tag("fast")
    @DisplayName("快速单元测试")
    void fastUnitTest() {
        // 毫秒级完成的测试
    }
}
```

在 Maven 中通过 `-Dgroups` 选择运行特定标签的测试：

```xml
<!-- 快速验证：只跑 fast 标签 -->
mvn test -Dgroups="fast"

<!-- 跳过低速测试 -->
mvn test -DexcludedGroups="slow"
```

### 2.7 测试实例生命周期

JUnit 5 默认每个测试方法都会创建一个新的测试类实例（`PER_METHOD`），这保证了测试之间的完全隔离。可以通过 `@TestInstance` 修改为 `PER_CLASS`。

```java
import org.junit.jupiter.api.TestInstance;
import org.junit.jupiter.api.TestInstance.Lifecycle;

@TestInstance(Lifecycle.PER_CLASS)
class SharedStateTest {

    private int sharedCounter = 0;

    @Test
    @DisplayName("测试 A：修改共享状态")
    void testA() {
        sharedCounter++;
        assertEquals(1, sharedCounter);
    }

    @Test
    @DisplayName("测试 B：共享状态已被 testA 修改")
    void testB() {
        sharedCounter++;
        // 如果按默认 PER_METHOD，sharedCounter 在这里是 1
        // 如果按 PER_CLASS，sharedCounter 在这里是 2
        System.out.println("sharedCounter = " + sharedCounter);
    }
}
```

**什么时候用 `PER_CLASS`？**
- 当需要在所有测试方法之间共享一个重量级对象（如一个连接池、一个 Spring 容器）时。
- `@BeforeAll` / `@AfterAll` 不再需要 `static` 修饰。

**什么时候避免？**
- 当你需要测试之间完全隔离时——大多数单元测试都应使用默认的 `PER_METHOD`。
- 共享可变状态容易被测试顺序影响，导致偶发失败。

## 三、Mock 技术

### 3.1 为什么需要 Mock

单元测试的核心要求是**隔离**。一个典型的业务服务类通常依赖外部组件：

```java
@Service
public class OrderService {

    @Autowired
    private PaymentClient paymentClient;  // 外部 HTTP 服务

    @Autowired
    private OrderRepository orderRepository;  // 数据库

    @Autowired
    private MessageQueueProducer mqProducer;  // 消息队列
}
```

如果不 Mock，测试这个 `OrderService` 就需要：
1. 启动一个真实的支付服务
2. 配置好数据库连接
3. 运行消息队列

这会导致测试速度极慢（违反 **F**ast）、依赖外部环境（违反 **I**ndependent 和 **R**epeatable）。Mock 的作用就是**用轻量级的替身对象替换真实的依赖**，让测试专注于被测类自身的逻辑。

此外，Mock 在模拟异常场景方面具有不可替代的优势——你很难让真正的数据库连接在需要的时候恰好抛出 `ConnectionTimeoutException`，但 Mock 可以精确地做到这一点。

### 3.2 Mockito 核心用法

Mockito 是 Java 生态中最流行的 Mock 框架，下面的代码展示了最常见的用法。

```java
import org.mockito.*;
import org.mockito.junit.jupiter.MockitoExtension;
import org.junit.jupiter.api.extension.ExtendWith;

@ExtendWith(MockitoExtension.class)  // 自动初始化 @Mock 和 @InjectMocks
class OrderServiceTest {

    @Mock
    private PaymentClient paymentClient;

    @Mock
    private OrderRepository orderRepository;

    @InjectMocks  // 自动将上面的 @Mock 注入到 OrderService 中
    private OrderService orderService;

    @Test
    @DisplayName("下单成功时应保存订单并调用支付")
    void shouldSaveOrderAndCallPaymentWhenPlaceOrderSuccess() {
        // Given: 准备测试数据和模拟行为
        OrderRequest request = new OrderRequest("item-1", 2, 100.0);
        Order savedOrder = Order.builder()
            .id("order-123")
            .itemId("item-1")
            .totalAmount(200.0)
            .status(OrderStatus.PENDING)
            .build();

        when(orderRepository.save(any(Order.class))).thenReturn(savedOrder);
        when(paymentClient.pay(anyString(), anyDouble()))
            .thenReturn(new PaymentResponse(true, "txn-001"));

        // When: 执行被测方法
        Order result = orderService.placeOrder(request);

        // Then: 验证结果和行为
        assertNotNull(result);
        assertEquals(OrderStatus.PENDING, result.getStatus());
        verify(orderRepository, times(1)).save(any(Order.class));
        verify(paymentClient, times(1)).pay(eq("order-123"), eq(200.0));
    }
}
```

**`@ExtendWith(MockitoExtension.class)`** 是 Mockito 与 JUnit 5 的桥梁，它自动处理 `@Mock`、`@InjectMocks` 等注解的初始化。如果不加这个注解，你需要手动调用 `MockitoAnnotations.openMocks(this)`。

**`@InjectMocks`** 尝试将 `@Mock` 或 `@Spy` 标记的对象通过**构造函数注入、Setter 注入或字段注入**的方式注入到被测类中。如果被测类有多个构造函数，Mockito 会选择参数最多的那个。

### 3.3 Stubbing（桩代码）

Stubbing 就是定义 Mock 对象在调用特定方法时的行为。

```java
public class StubbingDemoTest {

    @Mock
    private UserRepository userRepository;

    @Test
    @DisplayName("when...thenReturn: 定义返回值")
    void testThenReturn() {
        User mockUser = new User("Alice", "alice@test.com");
        when(userRepository.findById("1")).thenReturn(mockUser);

        // 调用时返回 mockUser
        assertEquals(mockUser, userRepository.findById("1"));

        // 未 stub 的调用返回默认值（null, 0, false 等）
        assertNull(userRepository.findById("non-existent"));
    }

    @Test
    @DisplayName("thenThrow: 模拟异常")
    void testThenThrow() {
        when(userRepository.findById(anyString()))
            .thenThrow(new DataAccessException("数据库连接失败"));

        assertThrows(DataAccessException.class,
            () -> userRepository.findById("1"));
    }

    @Test
    @DisplayName("doThrow: 模拟 void 方法抛异常")
    void testDoThrow() {
        // void 方法不能用 when().thenThrow()，需用 doThrow
        doThrow(new RuntimeException("发送失败"))
            .when(userRepository).deleteById(anyString());

        assertThrows(RuntimeException.class,
            () -> userRepository.deleteById("1"));
    }

    @Test
    @DisplayName("doAnswer: 根据参数动态返回结果")
    void testDoAnswer() {
        when(userRepository.findById(anyString()))
            .thenAnswer(invocation -> {
                String id = invocation.getArgument(0);
                return "admin".equals(id)
                    ? new User("Admin", "admin@system.com")
                    : new User("Guest", "guest@test.com");
            });

        assertEquals("Admin", userRepository.findById("admin").getName());
        assertEquals("Guest", userRepository.findById("anyone").getName());
    }

    @Test
    @DisplayName("链式 Stub: 连续调用返回不同值")
    void testChainedStub() {
        when(userRepository.findById(anyString()))
            .thenReturn(new User("First", "first@test.com"))
            .thenReturn(new User("Second", "second@test.com"))
            .thenThrow(new RuntimeException("超出调用次数"));

        assertEquals("First", userRepository.findById("1").getName());
        assertEquals("Second", userRepository.findById("1").getName());
        assertThrows(RuntimeException.class,
            () -> userRepository.findById("1"));
    }
}
```

### 3.4 参数匹配器

参数匹配器让 Stubbing 和验证更加灵活。

```java
import static org.mockito.ArgumentMatchers.*;

public class ArgumentMatcherDemoTest {

    @Mock
    private InventoryService inventoryService;

    @Test
    @DisplayName("常用参数匹配器")
    void testArgumentMatchers() {
        when(inventoryService.checkStock(anyString(), anyInt()))
            .thenReturn(true);

        // anyString() 匹配任意字符串
        // anyInt() 匹配任意 int
        // any() 匹配任意类型（包括 null）
        // eq() 精确匹配特定值

        assertTrue(inventoryService.checkStock("A", 10));
        assertTrue(inventoryService.checkStock("B", 999));
    }

    @Test
    @DisplayName("argThat: 自定义匹配器")
    void testCustomMatcher() {
        // 只接受数量在 1~100 之间的库存查询
        when(inventoryService.checkStock(anyString(), argThat(quantity ->
            quantity >= 1 && quantity <= 100)))
            .thenReturn(true);

        assertTrue(inventoryService.checkStock("A", 50));
        assertFalse(inventoryService.checkStock("B", 200));  // 未被 stub
    }
}
```

**重要提示**：当你在一个方法中使用参数匹配器时，**该方法的所有参数都必须使用匹配器**，不能混用原始值和匹配器。例如：

```java
// 错误写法：混用原始值和匹配器
when(inventoryService.checkStock("A", anyInt())).thenReturn(true);

// 正确写法：所有参数都用匹配器
when(inventoryService.checkStock(eq("A"), anyInt())).thenReturn(true);
```

### 3.5 行为验证

行为验证检查 Mock 对象上是否发生了预期的交互。

```java
import static org.mockito.Mockito.*;

public class VerificationDemoTest {

    @Mock
    private EmailService emailService;

    @Test
    @DisplayName("验证方法调用次数和顺序")
    void testVerification() {
        // 执行一些操作
        emailService.send("welcome@test.com", "Welcome!");
        emailService.send("admin@test.com", "New user registered");
        emailService.send("welcome@test.com", "Welcome!");

        // 验证调用次数
        verify(emailService, times(2))
            .send(eq("welcome@test.com"), anyString());
        verify(emailService, atLeastOnce())
            .send(anyString(), eq("Welcome!"));
        verify(emailService, never())
            .send(anyString(), eq("Spam"));

        // 验证调用顺序
        InOrder inOrder = inOrder(emailService);
        inOrder.verify(emailService).send("welcome@test.com", "Welcome!");
        inOrder.verify(emailService).send("admin@test.com", "New user registered");
        inOrder.verify(emailService).send("welcome@test.com", "Welcome!");
    }

    @Test
    @DisplayName("验证零交互")
    void testNoInteractions() {
        // 验证 emailService 没有被调用过
        verifyNoInteractions(emailService);
    }

    @Test
    @DisplayName("验证除指定调用外无其他交互")
    void testVerifyNoMoreInteractions() {
        // 只允许 send 方法被调用
        emailService.send("test@test.com", "Test");
        verify(emailService).send("test@test.com", "Test");
        verifyNoMoreInteractions(emailService);
    }
}
```

### 3.6 高级技巧：@Spy、@Captor

**@Spy（部分 Mock）**：Spy 是一个"部分 Mock"——默认情况下，它会调用对象的真实方法，只有被 stub 的方法才返回 Mock 行为。

```java
public class SpyDemoTest {

    @Spy
    private List<String> spyList = new ArrayList<>();

    @Test
    @DisplayName("@Spy: 保留真实行为，但可选择性 Stub")
    void testSpy() {
        // 真实方法：向列表添加元素
        spyList.add("A");
        spyList.add("B");
        assertEquals(2, spyList.size());

        // Stub size() 方法，覆盖真实行为
        when(spyList.size()).thenReturn(100);
        assertEquals(100, spyList.size());

        // 未 stub 的 get() 仍执行真实逻辑
        assertEquals("A", spyList.get(0));
    }
}
```

**@Captor + ArgumentCaptor（捕获参数）**：当需要验证传递给 Mock 方法的参数的具体细节时，`ArgumentCaptor` 比通配匹配器更精确。

```java
public class ArgumentCaptorDemoTest {

    @Mock
    private MessageQueueProducer mqProducer;

    @Captor
    private ArgumentCaptor<OrderEvent> eventCaptor;

    @Test
    @DisplayName("ArgumentCaptor: 捕获并验证复杂参数")
    void testArgumentCaptor() {
        // 执行操作，该方法内部会调用 mqProducer.send(event)
        orderService.completeOrder("order-123");

        // 捕获 send 方法收到的 OrderEvent 参数
        verify(mqProducer).send(eventCaptor.capture());
        OrderEvent captured = eventCaptor.getValue();

        // 验证事件内容的详细信息
        assertEquals("order-123", captured.getOrderId());
        assertEquals(OrderEventType.COMPLETED, captured.getEventType());
        assertNotNull(captured.getTimestamp());
        assertTrue(captured.getRetryCount() >= 0);
    }
}
```

`ArgumentCaptor` 尤其适合验证传递给依赖对象的参数是否包含正确的字段值——这在事件驱动架构和消息推送场景中极为常见。

### 3.7 Mock 静态方法与构造方法

从 Mockito 3.4.0 开始，支持 Mock 静态方法和构造方法。

```java
public class StaticMethodMockDemoTest {

    @Test
    @DisplayName("Mock 静态方法（try-with-resources 方式）")
    void testMockStatic() {
        // try-with-resources 确保 Mock 在测试后自动释放
        try (MockedStatic<IdGenerator> mockedStatic =
                 mockStatic(IdGenerator.class)) {

            mockedStatic.when(IdGenerator::nextId)
                .thenReturn("mocked-id-001");

            String id = IdGenerator.nextId();
            assertEquals("mocked-id-001", id);

            // 验证静态方法被调用
            mockedStatic.verify(IdGenerator::nextId);
        }
        // 退出 try 块后静态方法 Mock 自动失效
    }

    @Test
    @DisplayName("Mock 构造方法")
    void testMockConstruction() {
        try (MockedConstruction<ExternalService> mocked =
                 mockConstruction(ExternalService.class)) {

            // 当调用 new ExternalService() 时，返回 Mock 对象
            ExternalService service = new ExternalService();
            when(service.call()).thenReturn("mocked response");

            // 被测类在内部 new ExternalService() 会得到 Mock 对象
            String result = service.call();
            assertEquals("mocked response", result);
        }
    }
}
```

**重要提醒**：Mock 静态方法是有副作用的（影响同一个类加载器范围内的所有代码），务必使用 `try-with-resources` 确保作用域受到严格管控，不要将它用于无状态工具类的单元测试之外。

### 3.8 Mock vs Stub vs Fake vs Spy

Martin Fowler 在《Mocks Aren't Stubs》一文中系统性地区分了这些概念：

| 概念 | 说明 | 典型实现 |
|------|------|----------|
| **Dummy** | 传递但不使用的对象，仅用于填充参数列表 | `null` 或 `new DummyObject()` |
| **Fake** | 有真实工作实现但简化了的对象（如内存数据库替代 PostgreSQL） | H2 内存数据库 |
| **Stub** | 提供预设的返回值，不验证行为 | Mockito `when().thenReturn()` |
| **Spy** | 对真实对象的包装，部分行为可被覆写 | Mockito `@Spy` |
| **Mock** | 既有预设行为，也验证交互是否符合预期 | Mockito `@Mock` + `verify()` |

在实践中，"Mock"一词经常被当作泛指各种替身的总称，但理解上述的分类有助于在与团队成员讨论测试策略时保持术语的精确性。

## 四、Spring Boot 测试

Spring Boot 为不同层次的测试提供了一组注解，允许开发者精确控制启动 Spring 容器的范围。

### 4.1 @SpringBootTest：完整容器测试

`@SpringBootTest` 启动完整的 Spring ApplicationContext，是集成测试的入口。

```java
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.context.SpringBootTest.WebEnvironment;
import org.springframework.test.context.ActiveProfiles;

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
@ActiveProfiles("test")
class OrderServiceIntegrationTest {

    @Autowired
    private OrderService orderService;

    @Autowired
    private OrderRepository orderRepository;

    @Test
    @DisplayName("完整容器测试：下单后数据库中应有记录")
    void shouldPersistOrderWhenPlaceOrder() {
        OrderRequest request = new OrderRequest("item-1", 1, 99.0);

        Order order = orderService.placeOrder(request);

        assertNotNull(order.getId());
        assertTrue(orderRepository.findById(order.getId()).isPresent());
    }
}
```

`webEnvironment` 参数控制 Web 容器的行为：

| 值 | 含义 |
|----|------|
| `MOCK`（默认） | 加载 WebApplicationContext，但不启动嵌入式服务器，配合 MockMvc 使用 |
| `RANDOM_PORT` | 启动嵌入式服务器（Tomcat、Netty 等），端口随机 |
| `DEFINED_PORT` | 启动嵌入式服务器，使用配置中的端口 |
| `NONE` | 不加载 WebApplicationContext |

### 4.2 @WebMvcTest：Controller 层测试

`@WebMvcTest` 只加载 Controller 层相关的 Bean（Controller、ControllerAdvice、Jackson 配置等），不加载 Service 和 Repository，因此需要配合 `@MockBean` 使用。

```java
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.boot.test.mock.mockito.MockBean;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;
import static org.springframework.test.web.servlet.result.MockMvcResultHandlers.*;

@WebMvcTest(UserController.class)  // 只加载 UserController
class UserControllerTest {

    @Autowired
    private MockMvc mockMvc;  // MockMvc 由 @WebMvcTest 自动配置

    @MockBean  // 替换容器中的 UserService 为 Mock
    private UserService userService;

    @Test
    @DisplayName("GET /api/users/{id} 应返回用户信息")
    void shouldReturnUserWhenGetById() throws Exception {
        // Given: 准备 Mock 数据
        User mockUser = new User("1", "Alice", "alice@test.com");
        when(userService.findById("1")).thenReturn(mockUser);

        // When & Then: 发起 HTTP 请求并验证响应
        mockMvc.perform(get("/api/users/{id}", "1")
                .accept(MediaType.APPLICATION_JSON))
            .andDo(print())                    // 打印请求和响应详情
            .andExpect(status().isOk())         // 验证状态码 200
            .andExpect(jsonPath("$.name").value("Alice"))
            .andExpect(jsonPath("$.email").value("alice@test.com"));
    }

    @Test
    @DisplayName("GET /api/users/{id} 用户不存在应返回 404")
    void shouldReturn404WhenUserNotFound() throws Exception {
        when(userService.findById("999")).thenThrow(
            new UserNotFoundException("用户不存在"));

        mockMvc.perform(get("/api/users/{id}", "999"))
            .andExpect(status().isNotFound())
            .andExpect(jsonPath("$.error").value("用户不存在"));
    }

    @Test
    @DisplayName("POST /api/users 应创建新用户")
    void shouldCreateUserWhenPostValidRequest() throws Exception {
        UserCreateRequest request = new UserCreateRequest("Bob", "bob@test.com");
        User createdUser = new User("2", "Bob", "bob@test.com");

        when(userService.createUser(any(UserCreateRequest.class)))
            .thenReturn(createdUser);

        mockMvc.perform(post("/api/users")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"name\":\"Bob\",\"email\":\"bob@test.com\"}"))
            .andExpect(status().isCreated())
            .andExpect(jsonPath("$.id").value("2"))
            .andExpect(jsonPath("$.name").value("Bob"));
    }
}
```

**MockMvc 的核心方法链**：
- `perform(...)`：执行 HTTP 请求（`get`、`post`、`put`、`delete`、`patch`）
- `andExpect(...)`：验证响应（状态码、Header、响应体）
- `andDo(print())`：打印请求和响应的全部细节到控制台
- `andReturn()`：获取完整的 `MvcResult` 对象

**jsonPath 常用表达式**：

| 表达式 | 含义 | 示例值 |
|--------|------|--------|
| `$.name` | 根对象的 name 字段 | `"Alice"` |
| `$.data.items[0].id` | data.items 数组的第一个元素的 id | `"1"` |
| `$.data.items.length()` | data.items 数组的长度 | `3` |
| `$.data.items.size()` | 同上 | `3` |
| `$..price` | 深度搜索所有 price 字段 | 所有 price 值 |
| `$.store.book[?(@.price < 10)]` | 条件过滤 | 小于 10 的书 |

### 4.3 @DataJpaTest：数据层测试

`@DataJpaTest` 只加载 JPA 相关的 Bean（EntityManager、DataSource、Repository 等），默认使用内嵌数据库（如 H2）替换生产数据库。

```java
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;
import org.springframework.test.context.jdbc.Sql;

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.ANY)
class UserRepositoryTest {

    @Autowired
    private TestEntityManager entityManager;  // JPA 测试辅助类

    @Autowired
    private UserRepository userRepository;

    @Test
    @DisplayName("根据邮箱查询用户")
    void shouldFindUserByEmail() {
        // Given: 通过 TestEntityManager 直接操作数据库
        User user = new User("Alice", "alice@test.com");
        entityManager.persistAndFlush(user);

        // When: 调用 Repository 方法
        var found = userRepository.findByEmail("alice@test.com");

        // Then
        assertTrue(found.isPresent());
        assertEquals("Alice", found.get().getName());
    }

    @Test
    @Sql(statements = "INSERT INTO users (id, name, email) " +
                      "VALUES ('u1', 'Bob', 'bob@test.com')",
         executionPhase = Sql.ExecutionPhase.BEFORE_TEST_METHOD)
    @DisplayName("@Sql 初始化数据并查询")
    void testWithSqlAnnotation() {
        var found = userRepository.findByEmail("bob@test.com");
        assertTrue(found.isPresent());
    }
}
```

**`TestEntityManager`** 是 `@DataJpaTest` 自动提供的，它封装了 `EntityManager` 的常用操作（`persist`、`flush`、`find`、`clear` 等），比直接注入 `EntityManager` 更方便安全。

**`@AutoConfigureTestDatabase`** 控制是否使用内嵌数据库替换生产数据库：
- `Replace.ANY`（默认）：使用内嵌数据库
- `Replace.NONE`：使用生产配置的数据源

### 4.4 @MockBean vs @SpyBean

`@MockBean` 和 `@SpyBean` 是 Spring Boot 提供的，用于在 Spring 容器层面替换或包装 Bean。

```java
@SpringBootTest
class OrderServiceMockBeanTest {

    @MockBean   // 完全替换容器中的 PaymentClient
    private PaymentClient paymentClient;

    @SpyBean    // 包装容器中的 OrderRepository，保留真实行为
    private OrderRepository orderRepository;

    @Autowired
    private OrderService orderService;

    @Test
    @DisplayName("@MockBean: Mock 外部支付客户端")
    void testWithMockBean() {
        // PaymentClient 被完全 Mock
        when(paymentClient.pay(anyString(), anyDouble()))
            .thenReturn(new PaymentResponse(true, "txn-mock"));

        Order order = orderService.placeOrder(
            new OrderRequest("item-1", 1, 50.0));

        // OrderRepository 是 @SpyBean，实际会写入数据库
        assertNotNull(order.getId());
        verify(paymentClient).pay(anyString(), anyDouble());
    }
}
```

**`@MockBean` 与 `@Mock` 的核心区别**：

| 对比维度 | `@Mock` (Mockito) | `@MockBean` (Spring Boot) |
|----------|-------------------|---------------------------|
| 作用范围 | 当前测试类的字段 | Spring ApplicationContext 中的 Bean 定义 |
| 影响范围 | 仅当前测试 | 影响容器内的所有注入点 |
| 适用场景 | 纯单元测试 | 集成测试（需要 Spring 容器的场景） |

### 4.5 TestRestTemplate

当使用 `@SpringBootTest(webEnvironment = RANDOM_PORT)` 时，Spring Boot 自动配置了 `TestRestTemplate`，用于向真实的嵌入式服务器发送 HTTP 请求。

```java
@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
class UserControllerRestTemplateTest {

    @Autowired
    private TestRestTemplate restTemplate;

    @Test
    @DisplayName("TestRestTemplate: 完整 HTTP 调用")
    void testGetUser() {
        // 使用 TestRestTemplate 发起真实 HTTP 请求
        ResponseEntity<User> response = restTemplate
            .getForEntity("/api/users/{id}", User.class, "1");

        assertEquals(HttpStatus.OK, response.getStatusCode());
        assertNotNull(response.getBody());
        assertEquals("1", response.getBody().getId());
    }

    @Test
    @DisplayName("POST 请求创建资源")
    void testCreateUser() {
        UserCreateRequest request = new UserCreateRequest("Charlie", "c@test.com");

        ResponseEntity<User> response = restTemplate
            .postForEntity("/api/users", request, User.class);

        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.CREATED);
        assertThat(response.getBody().getName()).isEqualTo("Charlie");
    }
}
```

**`TestRestTemplate` vs `MockMvc`**：

| 对比维度 | MockMvc | TestRestTemplate |
|----------|---------|------------------|
| 是否启动真实服务器 | 否（模拟 Servlet 容器） | 是（随机端口 Tomcat） |
| 执行速度 | 快 | 较慢 |
| 测试真实性 | 较低（无真实网络栈） | 高（完整 HTTP 调用） |
| 适用场景 | Controller 层单元测试 | 完整集成测试 |

## 五、集成测试

### 5.1 Testcontainers：用 Docker 模拟真实依赖

Testcontainers 允许在测试时通过 Docker 启动真实的服务实例（MySQL、Redis、Kafka 等），测试结束后自动销毁。它解决了"内嵌 H2 与真实 MySQL 行为不一致"这一经典问题。

```java
import org.testcontainers.containers.MySQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;

@Testcontainers
@SpringBootTest
class UserRepositoryTestcontainersTest {

    // 声明一个 MySQL Docker 容器
    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0")
        .withDatabaseName("testdb")
        .withUsername("test")
        .withPassword("test");

    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        // 将 Spring 数据源配置动态指向 Testcontainers 的 MySQL 容器
        registry.add("spring.datasource.url", mysql::getJdbcUrl);
        registry.add("spring.datasource.username", mysql::getUsername);
        registry.add("spring.datasource.password", mysql::getPassword);
        registry.add("spring.datasource.driver-class-name", mysql::getDriverClassName);
    }

    @Autowired
    private UserRepository userRepository;

    @Test
    @DisplayName("Testcontainers: 操作真实的 MySQL 数据库")
    void testWithRealMySQL() {
        User user = new User("Alice", "alice@test.com");
        userRepository.save(user);

        var found = userRepository.findByEmail("alice@test.com");
        assertTrue(found.isPresent());
    }
}
```

**常见问题与最佳实践**：

1. **容器声明为 `static`**：这样同一个容器可以被整个测试类复用，避免每个测试方法都启动一个新容器。
2. **`@DynamicPropertySource` 必须为 `static` 方法**：它将容器属性动态注入 Spring Environment。
3. **容器镜像选择**：尽量选择与生产环境一致的版本，如果使用 MySQL 请留意 `mysql:8.0` 的时区设置。
4. **资源清理**：Testcontainers 会在容器关闭后自动删除，但如果使用了 `withReuse(true)`，容器会被保留以加速本地开发。

Testcontainers 支持的服务还包括：

```java
// Redis
static GenericContainer<?> redis =
    new GenericContainer<>("redis:7-alpine").withExposedPorts(6379);

// Kafka
static KafkaContainer kafka = new KafkaContainer(
    DockerImageName.parse("confluentinc/cp-kafka:latest"));

// Elasticsearch
static ElasticsearchContainer es =
    new ElasticsearchContainer("docker.elastic.co/elasticsearch/elasticsearch:8.10.0");
```

### 5.3 @Transactional + @Rollback

在集成测试中，最常用的数据隔离策略是让每个测试运行在事务中，并在测试结束后回滚。

```java
import org.springframework.test.annotation.Rollback;
import org.springframework.transaction.annotation.Transactional;

@SpringBootTest
@Transactional  // 每个测试方法运行在事务中
class TransactionalTestDemo {

    @Autowired
    private UserRepository userRepository;

    @Test
    @DisplayName("事务自动回滚：测试后数据不残留")
    void testTransactionalRollback() {
        // 这个 save 操作在事务中执行
        userRepository.save(new User("Alice", "alice@test.com"));

        // 测试中可以查询到
        assertEquals(1,
            userRepository.findByEmail("alice@test.com").isPresent() ? 1 : 0);

        // 方法结束后事务自动回滚，数据不会真正写入数据库
    }

    @Test
    @Rollback(false)  // 覆盖类级别配置，允许提交
    @DisplayName("@Rollback(false): 允许事务提交")
    void testWithoutRollback() {
        // 这个 save 操作将会真正提交到数据库
        userRepository.save(new User("Bob", "bob@test.com"));
        // 注意：这会污染数据库，通常只用于特定的数据准备场景
    }
}
```

**注意**：`@Transactional` 在测试中的行为与生产代码中有所不同——测试中的事务默认在方法结束后回滚（无论方法是否抛异常）。但如果测试的 Controller 层开启了新的事务（即 `REQUIRES_NEW` 传播级别），或者使用了异步处理，事务回滚可能无法覆盖所有的数据变更。

### 5.4 WireMock：HTTP 服务模拟

当被测服务需要调用外部 HTTP 接口时，WireMock 可以模拟外部服务的 HTTP 响应。

```java
import com.github.tomakehurst.wiremock.client.WireMock;
import com.github.tomakehurst.wiremock.junit5.WireMockTest;

@WireMockTest(httpPort = 8089)  // WireMock 监听 8089 端口
class PaymentClientWireMockTest {

    @Autowired
    private PaymentClient paymentClient;  // 配置指向 localhost:8089

    @Test
    @DisplayName("WireMock: 模拟支付成功响应")
    void testPaymentSuccess() {
        // 定义 WireMock stub
        WireMock.stubFor(WireMock.post(WireMock.urlEqualTo("/api/payments"))
            .willReturn(WireMock.aResponse()
                .withStatus(200)
                .withHeader("Content-Type", "application/json")
                .withBody("{\"transactionId\": \"txn-wiremock-001\", " +
                          "\"status\": \"SUCCESS\"}")));

        // 执行被测方法
        PaymentResponse response = paymentClient.pay("order-001", 100.0);

        // 验证结果
        assertTrue(response.isSuccess());
        assertEquals("txn-wiremock-001", response.getTransactionId());

        // 验证请求已被正确接收
        WireMock.verify(WireMock.postRequestedFor(
            WireMock.urlEqualTo("/api/payments"))
            .withRequestBody(WireMock.matchingJsonPath("$.orderId")));
    }

    @Test
    @DisplayName("WireMock: 模拟超时异常")
    void testPaymentTimeout() {
        WireMock.stubFor(WireMock.post("/api/payments")
            .willReturn(WireMock.aResponse()
                .withFixedDelay(5000)));  // 延迟 5 秒

        assertThrows(PaymentTimeoutException.class,
            () -> paymentClient.pay("order-001", 100.0));
    }

    @Test
    @DisplayName("WireMock: 模拟服务端错误")
    void testPaymentServerError() {
        WireMock.stubFor(WireMock.post("/api/payments")
            .willReturn(WireMock.aResponse()
                .withStatus(500)
                .withBody("{\"error\": \"Internal Server Error\"}")));

        assertThrows(PaymentServiceException.class,
            () -> paymentClient.pay("order-001", 100.0));
    }
}
```

### 5.5 契约测试

在微服务架构中，服务之间的接口契约是系统稳定性的基石。消费者驱动的契约测试确保服务的提供方在不破坏消费者的情况下进行变更。

**Spring Cloud Contract** 的工作流程：

1. **提供方**在 JAR 中发布契约（Groovy/YAML 文件定义请求和响应）
2. **消费者**拉取契约并验证自己的 HTTP 客户端是否符合契约
3. 提供方修改接口时运行契约测试，如果消费者无法满足则拒绝变更

```groovy
// contracts/shouldReturnUser.groovy - Spring Cloud Contract 契约示例
Contract.make {
    description "应该返回用户信息"
    request {
        method GET()
        url "/api/users/1"
        headers {
            accept(applicationJson())
        }
    }
    response {
        status OK()
        headers {
            contentType(applicationJson())
        }
        body([
            id  : "1",
            name: "Alice",
            email: "alice@test.com"
        ])
    }
}
```

**Pact** 是另一个流行的契约测试框架，特别适合消费者端驱动：

```java
// 消费者端定义 Pact
@Pact(consumer = "OrderService", provider = "UserService")
public V4Pact createPact(PactDslWithProvider builder) {
    return builder
        .given("用户 Alice 存在")
        .uponReceiving("获取用户信息")
            .path("/api/users/1")
            .method("GET")
        .willRespondWith()
            .status(200)
            .body(new PactDslJsonBody()
                .stringType("id", "1")
                .stringType("name", "Alice"))
        .toPact(V4Pact.class);
}

@PactTestFor(pactMethod = "createPact")
@Test
void testGetUser() {
    ResponseEntity<User> response = restTemplate
        .getForEntity("/api/users/1", User.class);
    assertEquals(200, response.getStatusCodeValue());
    assertEquals("Alice", response.getBody().getName());
}
```

契约测试的价值在于：**服务提供方在修改接口时不需要手动通知所有消费者，CI 中的契约测试会自动判断改动是否兼容**。

## 六、测试最佳实践

### 6.1 命名规范

测试命名应传达三个信息：**方法名 + 测试状态 + 期望行为**。

```java
// 推荐命名格式：methodName_StateUnderTest_ExpectedBehavior
@Test
void findById_WhenUserExists_ShouldReturnUser() { }

@Test
void findById_WhenUserNotExists_ShouldThrowNotFoundException() { }

@Test
void placeOrder_WhenInventoryInsufficient_ShouldThrowInsufficientStockException() { }

@Test
void cancelOrder_WhenOrderAlreadyShipped_ShouldThrowCannotCancelException() { }
```

如果团队觉得方法名过长，也可以用 `@DisplayName` 配合简短的方法名：

```java
@Test
@DisplayName("用户存在时返回用户信息")
void case1() { }

@Test
@DisplayName("用户不存在时抛出异常")
void case2() { }
```

### 6.2 Given-When-Then 模式

每个测试方法应当遵循 Arrange-Act-Assert（AAA）模式，用空行清晰分隔三个部分：

```java
@Test
@DisplayName("退货时，如果订单已超过退货期限，应拒绝退货")
void shouldRejectReturnWhenExceedReturnPeriod() {
    // Given - 准备测试数据
    Order order = Order.builder()
        .id("order-001")
        .status(OrderStatus.DELIVERED)
        .deliveredAt(LocalDateTime.now().minusDays(40))
        .build();
    when(orderRepository.findById("order-001"))
        .thenReturn(Optional.of(order));

    // When - 执行被测操作
    ReturnResult result = returnService.requestReturn("order-001");

    // Then - 验证结果
    assertFalse(result.isApproved());
    assertEquals("已超过退货期限（30天）", result.getRejectReason());
    verify(notificationService).notify(
        eq("order-001"),
        argThat(msg -> msg.contains("退货期限"))
    );
}
```

### 6.3 一个测试只测一个逻辑

如果测试方法中有多个 verify 或多个断言且它们验证的是不同的行为，考虑将其拆分为多个测试方法：

```java
// 不好的做法：一个方法测试多个场景
@Test
void testOrderLifecycle() {
    // 创建订单
    Order order = orderService.createOrder(...);
    assertNotNull(order);

    // 支付订单（和前一步是不同的行为）
    orderService.pay(order.getId());
    assertEquals(OrderStatus.PAID, order.getStatus());

    // 取消订单（又是另一个行为）
    orderService.cancel(order.getId());
    assertEquals(OrderStatus.CANCELLED, order.getStatus());
}
```

```java
// 好的做法：每个测试方法测试一个行为
@Test
void shouldCreateOrderWhenRequestIsValid() { }

@Test
void shouldMarkOrderAsPaidWhenPaymentSuccess() { }

@Test
void shouldCancelOrderWhenUserRequestCancellation() { }
```

当测试失败时，一个测试只测一个逻辑能让你立即定位到具体是哪个行为出了问题，而不需要在长长的测试方法中 Debug。

### 6.4 不要测试私有方法

这是最常见的争论点之一。**测试应该关注公共接口的行为**，而不是内部实现的细节。

```java
public class OrderService {

    public double calculateTotal(String itemId, int quantity, String couponCode) {
        double basePrice = getBasePrice(itemId);            // 私有方法
        double discountedPrice = applyDiscount(basePrice);  // 私有方法
        double couponDeduction = applyCoupon(couponCode);   // 私有方法
        return (discountedPrice * quantity) - couponDeduction;
    }

    private double applyDiscount(double price) { ... }
    private double applyCoupon(String code) { ... }
    private double getBasePrice(String itemId) { ... }
}
```

不要直接测试 `applyDiscount`、`applyCoupon`、`getBasePrice` 这三个私有方法，而应该通过 `calculateTotal` 测试不同的输入组合：

```java
@Test
void shouldCalculateTotalWithDiscountAndCoupon() {
    // 测试公共方法
    double total = orderService.calculateTotal("item-1", 2, "SAVE50");
    assertEquals(150.0, total);
}

@Test
void shouldCalculateTotalWithoutCoupon() {
    double total = orderService.calculateTotal("item-1", 1, null);
    assertEquals(100.0, total);
}
```

**例外情况**：如果私有方法足够复杂且包含核心业务逻辑，一个更好的做法是**将其提取到一个独立的类中**，变成公开方法再进行测试——这通常也意味着你的设计需要改进。

### 6.5 JaCoCo 代码覆盖率

JaCoCo（Java Code Coverage）是 Java 项目中最常用的覆盖率工具，它可以集成到 Maven 或 Gradle 的构建生命周期中。

```xml
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.11</version>
    <executions>
        <execution>
            <goals>
                <goal>prepare-agent</goal>  <!-- 在测试前注入代理 -->
            </goals>
        </execution>
        <execution>
            <id>report</id>
            <phase>verify</phase>           <!-- 在 verify 阶段生成报告 -->
            <goals>
                <goal>report</goal>
            </goals>
        </execution>
        <execution>
            <id>check</id>
            <phase>verify</phase>
            <goals>
                <goal>check</goal>
            </goals>
            <configuration>
                <rules>
                    <rule>
                        <element>BUNDLE</element>
                        <limits>
                            <limit>
                                <counter>LINE</counter>
                                <value>COVEREDRATIO</value>
                                <minimum>0.80</minimum>  <!-- 行覆盖率要求 80% -->
                            </limit>
                        </limits>
                    </rule>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

运行 `mvn verify` 后，在 `target/site/jacoco/index.html` 可以查看完整的覆盖率报告，包括：

- **行覆盖率（Line Coverage）**：代码中有多少行被执行了。
- **分支覆盖率（Branch Coverage）**：if/else、switch 等分支中有多少分支被执行了。
- **方法覆盖率（Method Coverage）**：类中有多少方法被调用了。
- **类覆盖率（Class Coverage）**：有多少类被加载测试了。

### 6.6 不要追求 100% 覆盖率

100% 的覆盖率是一个危险的目标，原因如下：

1. **边际效益递减**：为了覆盖最后 10% 的代码（往往是简单的 getter/setter、日志记录、配置加载等），投入的精力远高于收益。
2. **导致测试质量下降**：为了凑覆盖率而写的"形式主义测试"往往只调用了方法却没有验证任何行为。
3. **阻碍重构**：测试绑定到实现细节而非行为时，重构的成本会急剧增加。

```java
// 这类测试对覆盖率有贡献，但对产品质量没有帮助
@Test
void testGetterAndSetter() {
    User user = new User();
    user.setName("Alice");
    assertEquals("Alice", user.getName());
}
```

**正确的做法**：关注核心业务逻辑的覆盖，在 CI 中设定一个合理的覆盖率阈值（如 80%），但允许部分模块豁免。覆盖率是发现**未被测试覆盖的区域**的工具，而不是目标本身。

## 总结与清单

下面是一份测试实践的快速检查清单，可作为团队测试规范的参考：

### 测试设计
- [ ] 测试金字塔结构合理：单测居多，E2E 精而少
- [ ] 每个测试遵循 Given-When-Then 结构
- [ ] 一个测试只验证一个逻辑场景
- [ ] 测试命名清晰传达意图：`methodName_State_ExpectedBehavior`
- [ ] 遵循 FIRST 原则（Fast, Independent, Repeatable, Self-Validating, Timely）

### JUnit 5
- [ ] 使用 `@DisplayName` 提供中文/可读性强的测试名称
- [ ] `assertAll` 批量断言避免第一个失败就停止
- [ ] `assertThrows` 精确验证异常类型和消息
- [ ] 参数化测试消除重复的测试方法
- [ ] `@Nested` 分组组织复杂的测试场景
- [ ] `@Tag` 区分慢速测试和快速测试

### Mock 与隔离
- [ ] 用 Mock 隔离外部依赖（数据库、外部 API、消息队列）
- [ ] `@ExtendWith(MockitoExtension.class)` 与 `@Mock` / `@InjectMocks` 配合使用
- [ ] `when().thenReturn()` / `doThrow()` 规范 Stubbing
- [ ] `verify()` 验证关键交互
- [ ] `ArgumentCaptor` 捕获并验证复杂参数
- [ ] 静态方法 Mock 使用 `try-with-resources` 确保作用域受控

### Spring Boot 测试
- [ ] `@WebMvcTest` + `MockMvc` 测试 Controller 层
- [ ] `@DataJpaTest` + `TestEntityManager` 测试数据层
- [ ] `@SpringBootTest` + `TestRestTemplate` 测试完整集成
- [ ] `@MockBean` / `@SpyBean` 替换容器中的 Bean
- [ ] 使用 `jsonPath` 验证 JSON 响应结构

### 集成测试
- [ ] Testcontainers 用 Docker 模拟真实中间件
- [ ] `@Sql` / `@SqlGroup` 管理测试数据
- [ ] `@Transactional` + 默认回滚保证测试隔离
- [ ] WireMock 模拟外部 HTTP 服务
- [ ] 契约测试确保微服务间接口兼容性

### 持续改进
- [ ] 使用 JaCoCo 生成覆盖率报告，关注核心业务逻辑覆盖
- [ ] 不盲目追求 100%，设定合理的覆盖率阈值（如 80%）
- [ ] 将测试纳入 CI 流水线，失败立即告警
- [ ] 定期审视测试质量，删除/重构无效的"形式主义测试"

---

测试不是开发工作的附属品，而是代码设计的一面镜子——**难以测试的设计往往意味着设计的耦合度过高**。当你发现某个类难以编写单元测试时，不妨把这看作一个信号：也许这个类需要拆分，也许依赖关系需要反转。从这个角度来说，写好测试的过程，本身就是在锤炼架构设计能力。
