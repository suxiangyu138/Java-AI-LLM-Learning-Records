## 一、代码质量意识（★★★★★）

### 1.1 《Clean Code》核心原则

```
命名规范：
- 变量名 = 意图清晰：elapsedTimeInDays > et
- 函数名 = 动词：getUserById()、calculateTotalPrice()
- 类名 = 名词：OrderService、UserRepository
- 避免魔法数字：MAX_RETRY_COUNT > 3
- 避免缩写：customer > cust（除非领域通用如 DTO/VO）

函数设计：
- 一个函数只做一件事
- 函数参数 ≤ 3 个（多了封装为参数对象）
- 无副作用：函数要么做事，要么回答，不要两样都做
- 函数长度 ≤ 20 行（非强制，但可作为自检标准）

注释原则：
- 好代码 + 好命名 > 烂代码 + 好注释
- 注释 WHY 而不是 WHAT（WHAT 看代码）
- 删除被注释掉的代码（Git 保留历史，不需要留在文件中）
```

### 1.2 代码坏味道（Code Smell）

| 坏味道 | 症状 | 重构手段 |
|--------|------|---------|
| 过长函数 | 一个方法 > 50 行 | 提取方法（Extract Method） |
| 过大类 | 一个类 > 500 行 / > 10 个字段 | 提取类（Extract Class） |
| 重复代码 | 同样的逻辑出现 ≥ 3 次 | 提取公共方法 |
| 过长参数列表 | 方法参数 > 3 个 | 引入参数对象 |
| Switch 滥用 | 多处 switch/if-else 判断类型 | 多态替代（策略模式） |
| 发散式变化 | 一个类因为不同原因被修改 | 按职责拆分 |
| 霰弹式修改 | 一个变化需要改很多类 | 内聚到同一个类 |
| 依恋情节 | A 类频繁访问 B 类数据 | 把方法移到 B 类 |
| 基本类型偏执 | 用 int/String 表达业务概念 | 封装为值对象（Money/PhoneNumber） |
| 注释过多 | 靠注释解释烂代码 | 重构代码使其自解释 |

### 1.3 单元测试编写

```java
// JUnit 5 + Mockito 标准模板

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;

    @Mock
    private PaymentGateway paymentGateway;

    @InjectMocks
    private OrderService orderService;

    @Test
    @DisplayName("正常创建订单：库存充足时应成功")
    void shouldCreateOrderWhenStockSufficient() {
        // Given（准备数据）
        CreateOrderRequest request = new CreateOrderRequest(1L, 1001L, 2);
        when(orderRepository.countStock(1001L)).thenReturn(10);

        // When（执行被测方法）
        Order order = orderService.createOrder(request);

        // Then（验证结果）
        assertThat(order.getStatus()).isEqualTo(OrderStatus.CREATED);
        verify(orderRepository).decreaseStock(1001L, 2);
    }

    @Test
    @DisplayName("库存不足时应抛异常")
    void shouldThrowExceptionWhenStockInsufficient() {
        CreateOrderRequest request = new CreateOrderRequest(1L, 1001L, 20);
        when(orderRepository.countStock(1001L)).thenReturn(10);

        assertThrows(InsufficientStockException.class,
            () -> orderService.createOrder(request));
    }
}
```

### 1.4 Code Review 指南

```
Review 关注点（按优先级）：
1. 逻辑正确性：边界条件、空指针、并发安全
2. 设计合理性：是否符合现有架构，是否过度设计
3. 性能影响：数据库查询次数、循环复杂度
4. 安全性：SQL 注入、XSS、越权
5. 可读性：命名、函数拆分（最后关注）

Review 沟通技巧：
✅ "这里如果 user 为 null 会怎样？考虑加 @NonNull 注解？"
❌ "这里可能空指针，你怎么连这个都想不到"
✅ "这个循环可以用 Stream API 简化，但我看你用了并行流，是测过性能更好？"
❌ "为什么不用 Stream？"

每轮 Review 的合理粒度：< 400 行代码变更
超过 400 行 → 拆分为多个小 PR
```

## 二、沟通协作能力（★★★★☆）

### 2.1 技术文档写作

```
文档分层：
- 方案文档（Design Doc）：大功能、大改动前写，回答 WHY + WHAT + HOW
- 接口文档（API Doc）：Swagger/OpenAPI 自动生成，手写 Markdown 补充
- 操作手册（Runbook）：线上常见问题和处理步骤
- 复盘文档（Postmortem）：事故复盘，重点是改进措施

Markdown 排版规范：
- 标题层级不跳级（## 下面不能直接 ####）
- 表格用 | 对齐，表头加分隔线
- 代码块标注语言 ```java
- 示意图用 ASCII art 或拖图片（不要大段文字描述架构）
```

### 2.2 技术分享

```
一个好的技术分享的结构：
1. 问题引入（1 分钟）：我们遇到了什么问题？
2. 方案探索（2 分钟）：试了哪几种方案，各有什么问题？
3. 方案详解（5 分钟）：最终方案是什么，核心原理？
4. 效果数据（1 分钟）：方案上线后的数据对比
5. 踩坑总结（1 分钟）：过程中遇到的坑，怎么解决的？
6. Q&A

黄金法则：
- 讲给 3 年前的自己听（把复杂原理降维到入门水平）
- 用 Demo 代替 PPT（现场写代码比放截图更有说服力）
- 准备 3 倍内容，现场根据听众反应选择讲哪部分
```

### 2.3 跨部门沟通

```
与产品经理沟通：
- 用"技术成本"代替"不能做"
  ✅ "这个功能需要 5 天开发，我们可以分两步：先把核心功能上线要 2 天，优化功能后续迭代"
  ❌ "这个做不了"

与前端沟通：
- 提前定义接口格式（RESTful 规范 + JSON Schema）
- 接口变更时同步更新文档，@前端在 PR 中

与测试沟通：
- 提供测试用例建议（边界值 + 异常场景）
- 复杂逻辑提供代码走读，帮助测试设计用例
```

### 3.2 开源贡献策略

```

1. 先修 Issue：找 good first issue 标签
2. 修文档：改错别字/补充示例（熟悉 PR 流程）
3. 修 Bug：找 confirmed bug，自己定位并修复
4. 加 Feature：提交 Proposal → 讨论 → 实现 → 合并
5. 成为 Maintainer：长期贡献后自然获得邀请

你的目标项目：
- Spring / MyBatis Plus（国内认可度高）
- Arthas / Nacos（阿里开源，社区活跃）
- 自己写一个工具类库（从 0 到 500 Star）
```
