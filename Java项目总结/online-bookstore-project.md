# 在线图书商城项目设计说明

## 项目概述

在线图书商城是一个典型的电商交易类项目，核心链路通常包括商品展示、购物车、订单创建、物流状态跟踪以及后台商品和订单管理，因此非常适合用于展示 Java 后端在业务建模、事务控制和系统设计方面的能力。[cite:1][cite:6] 相关资料普遍将图书商城视为包含前台用户操作与后台管理操作的综合系统，既覆盖基础 CRUD，也覆盖交易流程与状态流转。[cite:6][cite:12]

对于求职导向的项目实践，这个题目的价值不在页面数量，而在于是否完整实现了“加购—下单—扣库存—生成订单—发货—签收”的闭环业务链路。[cite:1][cite:9] 该链路涉及订单状态管理、库存一致性和物流信息展示，是面试中经常被追问的重点部分。[cite:10][cite:15]

## 核心模块

### 商品管理

商品管理模块负责图书信息维护与前台展示，通常包含图书分类、图书详情、价格、库存、上架状态以及关键字搜索等能力。[cite:1][cite:6] 该模块既服务于用户浏览与检索，也服务于后台对图书数据的维护与上下架控制。[cite:6][cite:9]

### 购物车

购物车模块负责暂存用户意向商品，常见功能包括加入购物车、修改数量、删除商品、清空购物车以及价格汇总。[cite:1][cite:8] 在业务上，购物车是订单提交前的数据缓冲区，因此它与库存校验、价格快照和用户会话管理存在直接联系。[cite:1][cite:6]

### 订单管理

订单模块是整套系统的交易中心，通常包括提交订单、查询订单详情、取消订单、查看历史订单和订单状态流转等功能。[cite:1][cite:12] 相关项目资料显示，订单表与订单明细表的拆分设计是常见做法，因为它能清晰表达“订单主信息”和“商品购买快照”两类数据。[cite:1][cite:15]

### 物流状态

物流模块一般用于记录物流单号、承运商、运输进度和签收结果，帮助用户在下单后持续追踪配送过程。[cite:6][cite:10] 一些订单状态设计资料明确区分了“支付/交易状态”和“发货/配送状态”，说明物流状态最好独立建模，而不是直接混入订单状态字段中。[cite:10][cite:15]

## 数据库设计

为了兼顾开发效率和项目完整度，数据库设计应围绕交易主链路展开，优先保证用户、图书、购物车、订单、订单项和物流等核心实体完整可用。[cite:1][cite:6] 对于本科求职项目而言，表数量不需要过多，但主干表之间的关系必须清晰、可解释、能支撑事务流程。[cite:6][cite:9]

| 表名 | 作用 |
|---|---|
| `user` | 存储用户账号、登录信息与基本资料。[cite:6] |
| `category` | 存储图书分类信息。[cite:6] |
| `book` | 存储图书名称、作者、价格、库存、状态等核心商品数据。[cite:1][cite:9] |
| `cart_item` | 存储用户购物车中的图书、数量和价格信息。[cite:1][cite:8] |
| `orders` | 存储订单号、用户、金额、状态、地址等主订单信息。[cite:1][cite:15] |
| `order_item` | 存储订单明细和商品购买快照。[cite:1][cite:15] |
| `shipping_address` | 存储用户收货地址信息。[cite:1] |
| `logistics` | 存储物流单号、物流公司、物流状态和更新时间。[cite:6][cite:10] |
| `inventory_log` | 记录库存变化日志，便于审计和问题排查。[cite:6] |

其中，`orders` 与 `order_item` 的拆分是订单系统设计中的关键，因为下单后商品价格、名称、数量等信息需要作为订单快照保留，不能简单依赖图书表实时数据。[cite:1][cite:15] 同时，物流表独立设计更有利于表达配送阶段的多次状态更新。[cite:10]

## 状态建模

订单状态建议至少包含待支付、已支付、已发货、已完成和已取消等阶段，这类分层方式能较好覆盖电商交易流程中的主要节点。[cite:7][cite:10] 一些资料还会进一步细分为待拣货、已出库、已关闭等状态，这说明系统应具备状态机思想，而不应仅使用简单字符串随意更新。[cite:10]

物流状态则更适合独立表示为待发货、待揽收、运输中、已送达、已退回等过程型状态，因为它反映的是包裹履约进度，而不是交易是否成立。[cite:10][cite:15] 将订单状态与物流状态拆开后，系统建模会更符合真实电商业务，也更便于后续扩展退款、退货和售后流程。[cite:10]

## 事务设计

在线图书商城最重要的技术点之一是下单事务控制，因为订单创建往往同时涉及购物车校验、库存扣减、订单主表写入、订单明细落库和购物车清理等多个步骤。[cite:1][cite:6] 如果这些步骤不在统一事务边界中执行，就可能出现“库存已扣但订单未创建”或“订单已生成但购物车未清理”的数据不一致问题。[cite:1][cite:6]

一个典型的下单事务流程可以设计为：读取购物车勾选项、校验商品状态与库存、创建订单主记录、批量写入订单明细、扣减库存、删除购物车对应记录，最后统一提交事务。[cite:1][cite:6] 一旦中间任意步骤失败，应整体回滚，以保证订单数据与库存数据的一致性。[cite:1]

在库存扣减上，采用“条件更新”通常比“先查库存再更新”更稳妥，例如通过 `stock >= ?` 作为更新条件来控制超卖风险，这也是很多交易系统处理中低并发库存问题的基础思路。[cite:6] 这种方案虽然不是完整的高并发秒杀架构，但作为本科简历项目已经足够体现事务意识和并发安全意识。[cite:6][cite:9]

## 技术栈建议

如果项目目标是服务 Java 后端求职，常见而合理的技术组合可以是 Spring Boot、MyBatis 或 MyBatis-Plus、MySQL、Redis、JWT 或 Sa-Token，以及 Vue 前端页面。[cite:6][cite:13] 这类组合既符合当前主流教学和求职项目实现路径，也便于后续扩展缓存、权限控制、接口文档和容器部署能力。[cite:6]

购物车和热门图书列表适合考虑缓存优化，而订单、库存、订单明细等关键交易数据则应优先保证数据库事务一致性，这种冷热分层思路也符合电商系统中“弱一致高频读”与“强一致核心写”的常见划分方式。[cite:6] 在项目汇报时，若能清晰说明哪些数据放缓存、哪些数据必须落 MySQL，将比单纯罗列技术栈更有说服力。[cite:6][cite:9]

## 简历亮点写法

该项目在简历中应突出交易链路完整性、事务一致性和状态建模能力，而不是仅描述为“实现了图书增删改查”。[cite:1][cite:6] 更有价值的表述通常会强调商品管理、购物车、订单中心、物流跟踪、库存扣减和事务回滚等关键后端能力。[cite:6][cite:10]

可以参考以下表达方式：

- 基于 Spring Boot + MySQL + Redis 实现在线图书商城，完成图书管理、购物车、订单结算、物流状态追踪等核心交易功能。[cite:6]
- 设计订单与物流双状态模型，支持待支付、待发货、运输中、已签收、已取消等状态流转。[cite:10][cite:15]
- 在下单链路中通过数据库事务统一控制订单创建、订单明细写入、库存扣减与购物车清理，保障数据一致性。[cite:1][cite:6]
- 采用条件更新方式进行库存扣减，降低并发场景下的超卖风险。[cite:6]

## 开发顺序建议

为了降低开发复杂度，推荐先完成数据库建模和基础商品管理，再逐步推进购物车、订单事务主链路和后台发货管理。[cite:1][cite:6] 这种顺序符合大多数在线书城项目的自然依赖关系，也有利于尽早打通一个可演示的闭环版本。[cite:6][cite:12]

建议开发顺序如下：

1. 设计数据库表结构和实体关系。[cite:1][cite:6]
2. 完成商品分类、图书管理、图书展示与搜索。[cite:6]
3. 完成购物车功能。[cite:1][cite:8]
4. 完成订单提交事务和订单详情查询。[cite:1][cite:6]
5. 完成后台发货与物流状态维护。[cite:6][cite:10]
6. 最后补充 Redis 优化、权限控制、Docker 部署等增强能力。[cite:6]
