# 高阶架构项目实现方案

适用目标：冲击大厂后端开发、高薪 Java 岗、简历项目升级、八股与项目拷打联动。

## 项目定位

这 4 个项目不是普通 CRUD 项目，而是面向“高并发、分布式、可观测、可扩展”的高阶架构型项目。它们的共同价值在于：

- 能体现 Java 后端核心能力：并发、缓存、消息、分布式协调、性能优化。
- 能覆盖面试高频问题：缓存一致性、限流、削峰、幂等、容灾、监控。
- 能直接写进简历，并支撑你在面试中展开系统设计与故障分析。

## 1. 分布式短链接系统

### 1.1 项目目标

实现一个类似 Bitly 的短链接平台，支持长链接转短链、短链跳转、访问统计、过期控制、风控校验和后台管理。

### 1.2 核心技术栈

- Java 17
- Spring Boot
- MySQL
- Redis
- Redisson
- Bloom Filter
- Kafka
- Nginx
- Docker
- Prometheus + Grafana

### 1.3 核心功能

- 长链接转短链接
- 自定义短码生成
- 短链跳转与 302 重定向
- UV、PV、IP 访问统计
- 链接过期时间控制
- 黑名单与恶意链接过滤
- 后台分页查询与数据分析

### 1.4 架构设计

```text
用户请求
   ↓
Nginx 网关
   ↓
短链接服务
   ├─ 短码生成器
   ├─ 布隆过滤器
   ├─ Redis 缓存
   ├─ MySQL 持久化
   └─ Kafka 统计消息
                ↓
           统计消费服务
                ↓
         MySQL / ClickHouse
```

### 1.5 关键实现

#### 1）短码生成策略

可选方案：

- 自增 ID + Base62 编码
- Snowflake ID + Base62 编码
- MurmurHash + 冲突校验

推荐：`号段/雪花ID + Base62`。

原因：

- 生成快，适合高并发。
- 长度短，可控性强。
- 易于分库分表扩展。

#### 2）缓存设计

Redis Key 设计：

```text
short:url:{code} -> longUrl
short:meta:{code} -> json(meta)
short:stats:{code} -> pv/uv/ip
```

缓存策略：

- 热点短链优先走 Redis。
- 未命中时回源 MySQL。
- 查询成功后回填缓存。
- 空值缓存防止缓存穿透。

#### 3）布隆过滤器

作用：

- 快速判断短码是否可能存在。
- 减少恶意请求直接打到数据库。

使用场景：

- 跳转前校验短码。
- 自定义短码判重前预检查。

#### 4）访问统计

统计维度：

- PV：总访问次数
- UV：独立用户数
- IP：独立 IP 数
- 地域、设备、浏览器、来源页

实现方式：

- 请求链路中仅做轻量采集。
- 统计消息异步写入 Kafka。
- 消费端聚合后批量入库。

### 1.6 面试亮点

- 如何解决短码冲突？
- 如何处理缓存穿透、击穿、雪崩？
- 如何保证统计链路不拖慢跳转主流程？
- 如何设计高可用跳转服务？

### 1.7 简历写法

- 设计并实现分布式短链接系统，采用 Base62 + Redis + 布隆过滤器实现高性能短链生成与跳转。
- 基于 Kafka 构建异步访问统计链路，支持 PV/UV/IP 多维度数据采集与聚合。
- 针对缓存穿透、热点访问与高并发场景设计多级缓存与空值保护机制，提升系统吞吐与稳定性。

## 2. 高并发直播弹幕系统

### 2.1 项目目标

实现一个支持海量用户实时发送、接收直播弹幕的系统，要求低延迟、高吞吐、可扩展，并具备限流、敏感词过滤、消息持久化能力。

### 2.2 核心技术栈

- Java 17
- Spring Boot
- Netty
- WebSocket
- Redis
- Kafka / RocketMQ
- MySQL
- Elasticsearch
- Docker
- Prometheus + Grafana

### 2.3 核心功能

- 用户连接直播间
- 实时发送弹幕
- 异步广播推送
- 敏感词过滤
- 用户禁言与封禁
- 限流与防刷
- 历史弹幕查询

### 2.4 架构设计

```text
客户端
   ↓ WebSocket
Netty 接入层
   ├─ 连接管理
   ├─ 心跳检测
   ├─ 鉴权校验
   ├─ 房间路由
   └─ 限流过滤
          ↓
      MQ 消息队列
          ↓
   弹幕消费服务
   ├─ 广播推送
   ├─ 持久化存储
   └─ 敏感词审查
```

### 2.5 关键实现

#### 1）为什么用 Netty

Netty 适合高并发长连接场景，原因：

- 基于 NIO，多路复用，连接成本低。
- EventLoop 线程模型性能高。
- 对 WebSocket 支持成熟。
- 可灵活定制编解码、心跳、连接生命周期。

#### 2）连接与房间管理

核心映射：

```text
userId -> channel
roomId -> channelGroup
channel -> userSession
```

设计重点：

- 每个直播间维护独立 ChannelGroup。
- 用户进入房间时绑定房间路由。
- 用户断线时自动移除连接。

#### 3）异步推送

发送流程：

1. 用户发送弹幕。
2. Netty 服务完成鉴权、限流、格式校验。
3. 合法消息写入 MQ。
4. 消费者从 MQ 拉取后广播至直播间。
5. 持久化服务异步落库。

这样做的好处：

- 接入层轻，避免同步广播阻塞。
- 便于削峰填谷。
- 支持后续接入审核、推荐、热词分析。

#### 4）限流设计

可组合使用：

- 单用户滑动窗口限流
- 单房间 QPS 限流
- IP 级限流
- 敏感用户加强限制

Redis 方案：

- `INCR + EXPIRE`
- Lua 保证原子性

#### 5）可靠性设计

- 心跳保活，定期清理失效连接。
- 广播失败重试。
- 消息序列号防止乱序分析困难。
- MQ 堆积监控与消费告警。

### 2.6 面试亮点

- Netty 线程模型怎么讲？
- 为什么 WebSocket 比 HTTP 轮询更适合弹幕？
- 如何避免单个直播间热点爆炸？
- 如何平衡实时性与持久化一致性？

### 2.7 简历写法

- 基于 Netty + WebSocket 实现高并发直播弹幕系统，支持海量长连接接入与低延迟实时推送。
- 引入 Redis + Lua 实现多维度限流与防刷机制，保障热点直播间服务稳定性。
- 使用 MQ 解耦消息接入与广播链路，完成弹幕异步推送、持久化存储与敏感词过滤。

## 3. 多级缓存商品详情页

### 3.1 项目目标

实现电商商品详情页高性能访问系统，支撑高并发读场景，降低数据库压力，并解决缓存一致性与热点数据问题。

### 3.2 核心技术栈

- Java 17
- Spring Boot
- Caffeine
- Redis
- MySQL
- Canal
- Nginx
- CDN
- OpenFeign
- Prometheus + Grafana

### 3.3 核心功能

- 商品详情聚合展示
- 多级缓存加速查询
- 热点商品缓存预热
- 商品库存与价格更新
- 缓存失效与一致性保障
- 限流降级与兜底页面

### 3.4 多级缓存结构

```text
浏览器缓存
   ↓
CDN
   ↓
Nginx/OpenResty
   ↓
应用本地缓存 Caffeine
   ↓
Redis 分布式缓存
   ↓
MySQL
```

### 3.5 关键实现

#### 1）为什么要多级缓存

单 Redis 缓存不够，原因：

- 网络访问 Redis 仍有开销。
- 超热点 Key 会把压力集中到 Redis。
- 大促场景需要更近一层缓存保护。

所以典型做法是：

- 浏览器/CDN 抗静态流量。
- Nginx/OpenResty 抗边缘热点。
- Caffeine 抗应用层热点。
- Redis 做共享缓存。

#### 2）商品详情聚合

详情页数据一般来自多个维度：

- 商品基础信息
- 价格
- 库存
- 营销活动
- 评论摘要
- 店铺信息

实践建议：

- 聚合服务统一对外。
- 内部通过 RPC/Feign 拉取多源数据。
- 非核心字段允许异步加载或降级。

#### 3）缓存一致性策略

常见更新方案：

- 先更新数据库，再删除缓存
- 延迟双删
- Canal 订阅 binlog 异步删缓存
- MQ 通知缓存失效

推荐组合：

- 读多写少场景：`更新 DB + 删除 Redis + 本地缓存失效`
- 高一致性场景：`binlog 监听 + 异步失效广播`

#### 4）热点 Key 问题

解决手段：

- 热点商品预热
- 互斥锁防止击穿
- 逻辑过期 + 后台异步刷新
- 热点 Key 永不过期 + 主动更新

#### 5）降级兜底

- Redis 故障时可读取本地缓存。
- 非核心字段查询失败时返回默认值。
- 极端流量下返回静态详情页快照。

### 3.6 面试亮点

- 本地缓存和 Redis 如何配合？
- 如何保证多个节点本地缓存一致？
- 为什么详情页适合多级缓存？
- 大促场景如何防止 Redis 被打挂？

### 3.7 简历写法

- 设计电商商品详情页多级缓存架构，基于 Caffeine + Redis + CDN 提升高并发读性能并显著降低数据库压力。
- 针对热点商品场景引入缓存预热、互斥锁、逻辑过期等策略，提升系统抗峰值能力。
- 结合 binlog 订阅与缓存失效广播机制优化缓存一致性，支持商品价格、库存等核心字段动态更新。

## 4. 分布式定时任务平台

### 4.1 项目目标

基于 XXL-Job 搭建企业级任务调度平台，实现任务统一注册、动态配置、失败重试、日志监控、告警通知和分片执行。

### 4.2 核心技术栈

- Java 17
- Spring Boot
- XXL-Job
- MySQL
- Redis
- Docker
- Prometheus + Grafana
- 企业微信 / 邮件告警

### 4.3 核心功能

- 任务创建与管理
- Cron 动态调度
- 任务参数配置
- 失败重试
- 执行日志查看
- 告警通知
- 分片广播任务
- 执行器集群扩展

### 4.4 架构设计

```text
运维/开发人员
   ↓
XXL-Job Admin 调度中心
   ├─ 任务配置
   ├─ 调度触发
   ├─ 执行日志
   └─ 失败告警
          ↓
   XXL-Job Executor 集群
   ├─ 定时任务A
   ├─ 定时任务B
   ├─ 分片任务
   └─ 重试补偿逻辑
```

### 4.5 关键实现

#### 1）典型任务场景

- 订单超时取消
- 优惠券过期处理
- 每日经营报表生成
- 用户积分结算
- 数据同步与补偿

#### 2）动态配置

调度平台应支持：

- 在线修改 Cron 表达式
- 在线启停任务
- 在线传递任务参数
- 路由策略选择

这样可以避免频繁发版，提升运维效率。

#### 3）失败重试

常见失败原因：

- 下游接口超时
- 数据库锁冲突
- 网络抖动
- 短时服务不可用

处理策略：

- 设置重试次数与退避策略。
- 区分可重试异常与不可重试异常。
- 关键任务增加幂等校验。
- 超过阈值时发送告警。

#### 4）日志监控

重点监控指标：

- 任务成功率
- 平均执行耗时
- 超时次数
- 重试次数
- 堆积任务数

日志体系建议：

- 任务执行链路统一 traceId。
- 关键参数和结果状态结构化记录。
- 调度中心与执行器日志分离存储。

#### 5）分片任务

适合场景：

- 大批量数据扫描
- 分库分表数据处理
- 批量消息补发

实现思想：

- 将任务切分为多个分片。
- 不同执行器节点并行处理。
- 通过分片参数控制处理范围。

### 4.6 面试亮点

- XXL-Job 调度中心和执行器如何协作？
- 为什么定时任务必须做幂等？
- 重试机制如何避免重复执行问题？
- 分片广播适合什么业务？

### 4.7 简历写法

- 基于 XXL-Job 搭建分布式定时任务平台，支持任务动态配置、失败重试、执行日志监控与告警通知。
- 设计任务幂等校验、重试补偿和分片执行机制，提升批处理任务稳定性与扩展性。
- 将订单关闭、报表生成、数据同步等场景统一纳入调度平台，降低人工运维成本。

## 项目落地建议

### 第一阶段：先做 MVP

建议你先把每个项目都做出最小可运行版本：

- 分布式短链接系统：先实现短链生成、跳转、统计。
- 直播弹幕系统：先实现 WebSocket 连接、弹幕发送、房间广播。
- 多级缓存商品详情页：先实现商品查询、Redis 缓存、本地缓存。
- 定时任务平台：先接入 XXL-Job，完成 2 到 3 个真实任务。

### 第二阶段：补高阶特性

把简历拉开差距的不是“能跑”，而是这些增强点：

- 限流
- 熔断降级
- 监控告警
- 链路追踪
- 灰度发布
- 容器化部署
- 压测数据

### 第三阶段：准备面试材料

每个项目至少准备以下内容：

- 系统架构图
- 核心流程图
- 表结构设计
- Redis Key 设计
- 面试亮点问题
- 性能优化前后对比
- 项目难点与取舍

## 推荐你优先做的顺序

如果你的目标是“校招/实习简历快速提升 + Java 后端高阶能力展示”，推荐顺序如下：

1. 多级缓存商品详情页
2. 分布式短链接系统
3. 分布式定时任务平台
4. 高并发直播弹幕系统

原因：

- 商品详情页最贴近大厂电商面试场景。
- 短链接系统容易讲缓存、布隆过滤器、统计异步化。
- 定时任务平台容易落地，也容易与真实业务结合。
- 直播弹幕系统技术亮点强，但实现复杂度最高。
