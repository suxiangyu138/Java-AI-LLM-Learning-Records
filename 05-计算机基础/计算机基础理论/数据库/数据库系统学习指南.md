## 1. SQL 语法基础

### 1.1 数据定义（DDL）

```sql
CREATE TABLE users (
    id         BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键',
    username   VARCHAR(50)  NOT NULL UNIQUE COMMENT '用户名',
    email      VARCHAR(100) NOT NULL COMMENT '邮箱',
    age        TINYINT      DEFAULT 0 COMMENT '年龄',
    created_at DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_username (username),
    INDEX idx_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

### 1.2 增删改查（DML）

```sql
-- 插入
INSERT INTO users (username, email, age) VALUES ('zhangsan', 'zhangsan@example.com', 25);
INSERT INTO users (username, email, age) VALUES
    ('lisi', 'lisi@example.com', 30),
    ('wangwu', 'wangwu@example.com', 28);

-- 更新
UPDATE users SET age = 26 WHERE username = 'zhangsan';
-- ⚠️ 生产环境 UPDATE/DELETE 必须加 WHERE，先 SELECT 确认再执行

-- 删除
DELETE FROM users WHERE id = 1;      -- 逐行删除，可回滚
TRUNCATE TABLE users;                -- 删除全表，不可回滚，重置自增ID

-- 查询
SELECT id, username, email FROM users
WHERE age > 20 AND email LIKE '%@example.com'
ORDER BY created_at DESC
LIMIT 10 OFFSET 0;
```

### 1.3 多表联查（JOIN）

```sql
-- INNER JOIN: 两表匹配的行
SELECT u.username, o.order_no, o.amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

-- LEFT JOIN: 左表全部 + 右表匹配的行（最常用）
SELECT u.username, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id;

-- 区别记忆：
-- INNER JOIN = 取交集  LEFT JOIN = 左表全保留   RIGHT JOIN = 右表全保留
```

### 1.4 聚合与分组

```sql
SELECT
    user_id,
    COUNT(*)     AS order_count,       -- 订单数
    SUM(amount)  AS total_amount,      -- 总金额
    AVG(amount)  AS avg_amount,        -- 平均金额
    MAX(amount)  AS max_amount,        -- 最高金额
    MIN(amount)  AS min_amount         -- 最低金额
FROM orders
WHERE status = 'completed'             -- 分组前过滤
GROUP BY user_id
HAVING total_amount > 1000             -- 分组后过滤（聚合函数结果）
ORDER BY total_amount DESC;
```

**SQL 执行顺序：**
```
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

### 1.5 子查询

```sql
-- 标量子查询（子查询返回单个值）
SELECT * FROM users WHERE age > (SELECT AVG(age) FROM users);

-- IN 子查询
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE amount > 1000);

-- EXISTS 子查询（大数据量时 EXISTS 通常优于 IN）
SELECT * FROM users u WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 1000
);

-- 派生表（子查询作为临时表）
SELECT t.username, t.order_count
FROM (SELECT u.username, COUNT(o.id) AS order_count
      FROM users u LEFT JOIN orders o ON u.id = o.user_id
      GROUP BY u.id) t
WHERE t.order_count > 5;
```

## 2. 索引原理

### 2.1 B+ 树索引结构

```
                   [30 | 60]                    ← 非叶子节点（存索引键 + 子节点指针）
                  /    |    \
         [10|20]     [40|50]    [70|80|90]     ← 非叶子节点
         /  |  \     /  |  \    /  |  |  \
        [1] [10] [20] ...  ...  ... ... ...     ← 叶子节点（存完整数据 + 前后叶子指针）
         ↕   ↕   ↕                              ← 叶子节点形成有序双向链表
```

**B+ 树特点（与 B 树对比）：**

| 特征 | B 树 | B+ 树 |
|------|------|-------|
| 数据存储 | 所有节点都存数据 | **仅叶子节点存数据** |
| 非叶子节点 | 存 key + data + 指针 | 仅存 key + 指针（更"瘦"，可放更多索引） |
| 叶子节点 | 无链表 | **双向链表**，支持范围查询 |
| 范围查询 | 需要中序遍历 | 叶子链表直接扫描 |

**MySQL InnoDB 选择 B+ 树的原因：**
1. 非叶子节点不存 data，高度更低，I/O 次数更少
2. 叶子节点有链表，范围查询效率高
3. 查询稳定（所有查询最终到叶子层）

### 2.2 聚簇索引 vs 非聚簇索引（二级索引）

| 类型 | 叶子节点存储 | InnoDB 中 |
|------|-------------|-----------|
| 聚簇索引 | **完整行数据** | 主键索引（每表仅一个） |
| 二级索引 | **主键值** + 索引列 | 普通索引、唯一索引 |

**回表查询流程：**
```
二级索引查找 → 获得主键 id → 聚簇索引查找 → 获得完整行数据
```

**覆盖索引（避免回表）：**
```sql
-- 假设有联合索引 idx_user_status(user_id, status)
-- ✅ 覆盖索引：查询列均在索引中，无需回表
SELECT user_id, status FROM orders WHERE user_id = 100;

-- ❌ 需要回表：SELECT 包含非索引列
SELECT user_id, status, amount FROM orders WHERE user_id = 100;
```

### 2.3 联合索引与最左匹配原则

```sql
-- 创建联合索引
CREATE INDEX idx_a_b_c ON table_name (a, b, c);

-- ✅ 走索引（匹配最左列）
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3
WHERE a = 1 AND c = 3        -- a 匹配，c 未匹配但索引下推可优化

-- ❌ 不走索引
WHERE b = 2                  -- 跳过 a，不满足最左匹配
WHERE c = 3                  -- 跳过 a、b
WHERE b = 2 AND c = 3        -- 跳过 a

-- ⚠️ 范围查询后失效
WHERE a = 1 AND b > 2 AND c = 3  -- a、b 走索引，c 不走（范围列之后失效）
```

### 2.4 索引失效场景

```sql
-- 1. 函数操作（索引列参与计算）
WHERE YEAR(created_at) = 2024       -- ❌
WHERE created_at >= '2024-01-01'    -- ✅ 改写为范围查询

-- 2. 隐式类型转换
WHERE phone = 13800138000           -- ❌ phone 是 VARCHAR，会隐式转换
WHERE phone = '13800138000'         -- ✅

-- 3. LIKE 前缀模糊
WHERE username LIKE '%zhang'         -- ❌ 前缀 % 导致索引失效
WHERE username LIKE 'zhang%'         -- ✅

-- 4. OR 连接非索引列
WHERE id = 1 OR name = 'test'       -- ❌ name 无索引
WHERE id = 1 UNION SELECT ...       -- ✅ 改写

-- 5. != / NOT IN / IS NULL / IS NOT NULL
-- 视情况而定，MySQL 优化器可能选择全表扫描
```

### 2.5 索引下推（ICP）

```sql
-- 联合索引 idx(name, age)
SELECT * FROM users WHERE name LIKE '张%' AND age = 25;

-- 无 ICP：存储引擎按 name 过滤 → Server 层再按 age 过滤
-- 有 ICP：存储引擎按 name 过滤同时按 age 过滤 → 减少回表次数
```

## 3. 事务机制

### 3.1 ACID 特性

| 特性 | 定义 | MySQL 实现 |
|------|------|-----------|
| **A**tomicity（原子性） | 事务是一个不可分割的单位 | undo log（回滚日志） |
| **C**onsistency（一致性） | 事务前后数据满足所有约束 | 其他三个特性共同保证 |
| **I**solation（隔离性） | 并发事务互不干扰 | MVCC + 锁 |
| **D**urability（持久性） | 提交后数据永久保存 | redo log（重做日志） |

### 3.2 隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现 |
|----------|------|-----------|------|------|
| READ UNCOMMITTED | ✓ | ✓ | ✓ | 无锁，几乎不用 |
| READ COMMITTED | ✗ | ✓ | ✓ | 每次读生成 ReadView |
| REPEATABLE READ（默认） | ✗ | ✗ | 部分解决 | 事务开始时生成 ReadView |
| SERIALIZABLE | ✗ | ✗ | ✗ | 读写均加锁 |

**脏读 / 不可重复读 / 幻读 的区别：**
- **脏读**：读到另一个事务未提交的数据
- **不可重复读**：同一事务两次读取同一行，数据不同（被其他事务 UPDATE 了）
- **幻读**：同一事务两次查询同一条件，行数不同（被其他事务 INSERT/DELETE 了）

**Oracle 默认 RC，MySQL 默认 RR——为什么？**
- MySQL 早期 binlog 只支持 STATEMENT 格式，RC 下会导致主从不一致
- 现在支持 ROW 格式 binlog 后，RC 也可安全使用

### 3.3 MVCC 多版本并发控制

**核心组成：**
- **隐藏字段：** `DB_TRX_ID`（事务 ID）、`DB_ROLL_PTR`（回滚指针）、`DB_ROW_ID`（行 ID）
- **undo log：** 记录数据的历史版本，形成版本链
- **ReadView：** 快照，记录活跃事务列表，用于判断版本可见性

**快照读 vs 当前读：**
```sql
-- 快照读（基于 MVCC，不加锁）
SELECT * FROM users WHERE id = 1;

-- 当前读（加锁，读取最新版本）
SELECT * FROM users WHERE id = 1 FOR UPDATE;    -- 排他锁
SELECT * FROM users WHERE id = 1 LOCK IN SHARE MODE; -- 共享锁
UPDATE users SET age = 26 WHERE id = 1;         -- 当前读
```

**ReadView 可见性判断：**
```
trx_id < min_trx_id  → 可见（事务在快照创建前已提交）
trx_id > max_trx_id  → 不可见（事务在快照创建后启动）
min ≤ trx_id ≤ max   → trx_id 在活跃列表中 → 不可见
                    → trx_id 不在活跃列表中 → 可见
```

### 3.4 Redo Log 与 Undo Log

| | Redo Log | Undo Log |
|------|----------|----------|
| 用途 | 崩溃恢复（crash recovery） | 事务回滚 + MVCC |
| 记录内容 | 物理日志：页的物理修改 | 逻辑日志：修改前的数据 |
| 写入时机 | 事务执行中持续写入 | 事务执行中持续写入 |
| 存储位置 | ib_logfile | undo 表空间 |
| 刷盘策略 | `innodb_flush_log_at_trx_commit` | — |

**WAL（Write-Ahead Logging）：**
- 先写 redo log，再修改数据页
- 保证持久性：即使数据页未刷盘，崩溃后可通过 redo log 恢复

### 3.5 Binlog（归档日志）vs Redo Log

| | Redo Log | Binlog |
|------|----------|--------|
| 所属层 | InnoDB 引擎层 | MySQL Server 层 |
| 记录内容 | 物理日志（页修改） | 逻辑日志（SQL 语句或行变更） |
| 写入方式 | 循环写（固定大小） | 追加写（文件切换） |
| 用途 | 崩溃恢复 | 主从复制、数据恢复 |

**两阶段提交：**
```
① Prepare 阶段：写 redo log，状态为 prepare
② Commit 阶段：写 binlog
③ 写 redo log，状态为 commit
```
保证了 redo log 和 binlog 的一致性。

## 4. 锁机制

### 4.1 全局锁 / 表锁 / 行锁

```sql
-- 全局锁（整个数据库只读，用于全库备份）
FLUSH TABLES WITH READ LOCK;

-- 表锁（手动）
LOCK TABLES users READ;   -- 读锁（共享锁）
LOCK TABLES users WRITE;  -- 写锁（排他锁）
UNLOCK TABLES;

-- 行锁（InnoDB，自动加锁）
SELECT ... FOR UPDATE;  -- 排他锁（X 锁）
SELECT ... LOCK IN SHARE MODE; -- 共享锁（S 锁）
```

### 4.2 共享锁 vs 排他锁（兼容矩阵）

| | S 锁 | X 锁 |
|------|------|------|
| S 锁 | ✓ | ✗ |
| X 锁 | ✗ | ✗ |

### 4.3 乐观锁 vs 悲观锁

| | 悲观锁 | 乐观锁 |
|------|--------|--------|
| 思想 | 每次读写都认为会冲突 | 读写时不加锁，更新时检查版本 |
| 实现 | `SELECT ... FOR UPDATE` | 版本号 + `CAS` 更新 |
| 适用场景 | 冲突概率高（短事务、高并发写） | 冲突概率低（读多写少） |
| 缺点 | 可能死锁 | 自旋 CAS 消耗 CPU |

**乐观锁实现（版本号方式）：**
```sql
-- 读取时获取版本号
SELECT id, stock, version FROM product WHERE id = 1;
-- 更新时检查版本号
UPDATE product
SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = #{oldVersion};
-- 影响行数为 0 → 版本冲突 → 重试
```

**MyBatis-Plus 中的乐观锁：**
```java
@Version
private Integer version;  // 只需加注解，MyBatis-Plus 自动处理
```

### 4.4 死锁

**原因：** 两个事务相互等待对方持有的锁。

**示例：**
```sql
-- 事务 A：先锁 id=1，再锁 id=2
-- 事务 B：先锁 id=2，再锁 id=1
-- 结果：A 等 B 释放 id=2，B 等 A 释放 id=1 → 死锁
```

**排查：**
```sql
SHOW ENGINE INNODB STATUS;          -- 查看最近一次死锁信息
SELECT * FROM information_schema.INNODB_TRX;  -- 当前事务
SELECT * FROM information_schema.INNODB_LOCKS; -- 当前锁
```

**预防：**
- 所有事务按相同顺序加锁
- 尽量使用索引，避免行锁升级为表锁
- 事务尽量短小，减少持锁时间

### 4.5 间隙锁（Gap Lock）

**Next-Key Lock = 行锁 + 间隙锁**

**作用：** 防止幻读（REPEATABLE READ 下使用）

```
表数据（id）：1, 5, 10, 15
间隙锁范围：(-∞, 1], (1, 5], (5, 10], (10, 15], (15, +∞)

SELECT * FROM t WHERE id = 5 FOR UPDATE;
-- 锁住：id=5 的行锁 + (1,5] 和 (5,10] 的间隙锁
-- 其他事务无法在 1~10 范围内插入数据
```

## 5. 查询优化

### 5.1 EXPLAIN 分析

```sql
EXPLAIN SELECT * FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.age > 20 AND o.status = 'completed';
```

**关键字段解读：**

| 字段 | 含义 | 关注值 |
|------|------|--------|
| type | 访问类型（性能从好到差） | system > const > eq_ref > ref > range > index > **ALL** |
| key | 实际使用的索引 | NULL = 未使用索引 |
| rows | 预估扫描行数 | 越小越好 |
| Extra | 额外信息 | Using index（覆盖索引，最优）/ Using filesort（需排序优化）/ Using temporary（需临时表优化） |

**type 等级详解：**
```
system  >  const  >  eq_ref  >  ref  >  range  >  index  >  ALL
 │          │         │         │        │         │        │
系统表   主键/唯一  关联表主键  普通索引  索引范围  全索引扫  全表扫
```

### 5.2 慢查询优化

```sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;  -- 超过 0.5 秒记录

-- 查看慢查询
SHOW VARIABLES LIKE 'slow_query%';
```

**优化步骤：**
1. 用 EXPLAIN 分析执行计划
2. 检查是否走索引（`type` 是否为 ALL）
3. 检查是否覆盖索引（`Extra` 是否有 Using index）
4. 优化 SQL 写法（避免 SELECT *、避免函数索引、大偏移量优化）
5. 考虑分库分表或读写分离

**大偏移量优化：**
```sql
-- ❌ 慢（offset 很大时需扫描并丢弃前 100000 行）
SELECT * FROM users ORDER BY id LIMIT 100000, 20;

-- ✅ 优化方案一：基于主键的延迟关联
SELECT * FROM users
WHERE id >= (SELECT id FROM users ORDER BY id LIMIT 100000, 1)
ORDER BY id LIMIT 20;

-- ✅ 优化方案二：记录上次查询的最大 id（适用于分页连续翻页）
SELECT * FROM users WHERE id > #{lastId} ORDER BY id LIMIT 20;
```

### 5.3 SQL 优化规范

1. **禁止 SELECT ***：只查需要的列，尽量利用覆盖索引
2. **WHERE 条件尽量用索引列**，避免函数、计算、类型转换
3. **OR 改写为 UNION**（OR 两边都有索引时才高效）
4. **大表 JOIN 先过滤再关联**：WHERE 条件下推到子查询
5. **批量操作分批执行**：
   ```sql
   -- ❌ 一次性删除大量数据，可能锁全表
   DELETE FROM logs WHERE created_at < '2025-01-01';
   -- ✅ 分批删除
   DELETE FROM logs WHERE created_at < '2025-01-01' LIMIT 1000;
   ```

## 6. 数据库设计

### 6.1 ER 模型向关系模型转换

**实体集 → 表，联系集 → 外键或关联表**

```
1:1 联系：任一方添加外键
1:N 联系：在 N 方添加外键
M:N 联系：创建关联表（两个外键作为联合主键）
```

### 6.2 范式

| 范式 | 规则 | 反例 |
|------|------|------|
| 1NF | 列不可再分（原子性） | 地址列存"北京市朝阳区"一整串 |
| 2NF | 非主键列完全依赖于主键（消除部分依赖） | 联合主键(a,b)，c 只依赖 a |
| 3NF | 非主键列不依赖于其他非主键列（消除传递依赖） | 学生表存"系名 + 系主任"（系主任依赖系名） |
| BCNF | 主键列之间无依赖 | 极少违反 |

**反范式化：** 实际生产通常到 3NF 为主，适当冗余以提高查询性能（如订单表冗余商品名，避免 JOIN）。

### 6.3 分库分表

**水平拆分 vs 垂直拆分：**

| | 水平拆分 | 垂直拆分 |
|------|----------|----------|
| 方式 | 按行拆分（多个表结构相同） | 按列拆分（热点列和非热点列） |
| 举例 | 按用户 ID 取模分 16 个库 | 商品主信息 + 商品详情分表 |
| 中间件 | ShardingSphere、MyCat | ShardingSphere |

**分库分表后的挑战：**
- 跨库 JOIN（改用应用层聚合）
- 分布式 ID 生成（雪花算法）
- 分布式事务（Seata、XA）
- 数据迁移（双写 + 灰度）

## 7. 后端开发关联

### 7.1 MyBatis 动态 SQL

```xml
<select id="findUsers" resultType="User">
    SELECT id, username, email, age
    FROM users
    <where>
        <if test="username != null and username != ''">
            AND username = #{username}
        </if>
        <if test="minAge != null">
            AND age &gt;= #{minAge}
        </if>
    </where>
    ORDER BY id
</select>
```

**关键注意：`#{}`（预编译，防注入）vs `${}`（直接拼接，危险）**

### 7.2 连接池配置（HikariCP）

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20         # 最大连接数
      minimum-idle: 10              # 最小空闲连接
      idle-timeout: 600000          # 空闲超时（10分钟）
      connection-timeout: 30000     # 连接等待超时
      max-lifetime: 1800000         # 连接最大存活时间（30分钟）
```

**连接数公式：** `pool_size = T_n × (C_m - 1) + 1`
> T_n = 最大线程数，C_m = 单个线程持有连接数

### 7.3 秒杀库存超卖解决方案

**方案一：数据库行锁 + 乐观锁**
```sql
UPDATE product
SET stock = stock - 1
WHERE id = #{id} AND stock > 0;  -- stock > 0 防止超卖
```

**方案二：Redis 预减库存 + 异步下单**
```java
// 1. Redis 预减库存（原子操作）
Long stock = redisTemplate.opsForValue().decrement("stock:" + productId);
if (stock < 0) throw new SoldOutException();
// 2. 消息队列异步创建订单
orderQueue.send(new OrderMessage(userId, productId));
// 3. 数据库最终扣减
```
