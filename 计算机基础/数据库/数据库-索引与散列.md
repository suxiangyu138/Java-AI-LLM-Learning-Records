## 索引与散列核心内容（原书框架）

### 一、基本概念

- **索引**：加速数据查询的数据结构，避免全表扫描
- **散列**：通过哈希函数将键映射到存储位置，实现等值快速查询

### 二、有序索引

| 索引类型 | 说明 |
|----------|------|
| **主索引（聚簇索引）** | 数据与索引同存储，叶子节点即数据行 |
| **辅助索引（非聚簇索引）** | 叶子节点存主键值，需回表查询 |
| **稠密索引** | 每个键对应索引项，查询快，空间大 |
| **稀疏索引** | 仅部分键建索引，空间小，查询稍慢 |

### 三、B+树索引

- **结构特点**：平衡多路搜索树，叶子节点有序链表
- **操作**：插入、删除、查找，支持范围查询
- **优势**：查询稳定 O(log n)，减少磁盘 I/O

### 四、散列索引

| 类型 | 说明 |
|------|------|
| 静态散列 | 固定桶数量，简单但扩展性差 |
| 动态散列（可扩展散列、线性散列） | 动态调整桶数量，适应数据增长 |
| 哈希函数 + 冲突解决 | 链地址法、开放寻址 |

### 五、位图索引

- 适用于低基数列（性别、状态）
- 位运算高效，适合多条件统计

### 六、索引设计原则

- 索引选择性
- 维护成本
- 查询频率权衡

## Java 后端开发视角深度剖析

### （一）有序索引：Java 后端查询优化基础

#### 1. 聚簇索引（InnoDB 主键）

- 数据与索引同存储，叶子节点即数据行
- **Java 实践**：主键必选自增 ID / 雪花 ID，避免 UUID 随机插入
- 范围查询（时间、ID 区间）性能最优

```sql
-- 聚簇索引范围查询（高效）
SELECT * FROM orders WHERE id BETWEEN 1000 AND 2000;
```

#### 2. 非聚簇索引（二级索引）

- 叶子节点存主键值，需回表查询
- **Java 优化**：覆盖索引（查询字段全在索引中）避免回表

```sql
-- 覆盖索引示例：name 在索引中，无需回表
SELECT id, name FROM user WHERE age = 18;
```

#### 3. 稠密/稀疏索引

| 索引类型 | 空间占用 | 查询性能 | Java 应用 |
|----------|----------|----------|-----------|
| 稠密索引 | 大 | 快（每个键都有索引） | 高频字段 |
| 稀疏索引 | 小 | 稍慢（部分键有索引） | 低频字段 |

### （二）B+ 树索引：MySQL 核心索引，Java 后端必备

#### 1. 结构优势适配 Java 业务

- **平衡树**：查询稳定 O(log n)，无最坏情况
- **有序链表**：支持范围查询、排序（`ORDER BY`）
- **多路存储**：减少磁盘 I/O，适配磁盘页特性

#### 2. 复合索引与 Java 查询规范

> **最左前缀原则：** 索引 `(a, b, c)` 支持 `a`、`a+b`、`a+b+c` 查询，不支持 `b`、`c`、`b+c` 查询。

```sql
-- 创建复合索引
CREATE INDEX idx_user_status_time ON orders (user_id, status, create_time);

-- 有效查询（满足最左前缀）
SELECT * FROM orders WHERE user_id = 101;
SELECT * FROM orders WHERE user_id = 101 AND status = 1;
SELECT * FROM orders WHERE user_id = 101 AND status = 1 AND create_time > '2024-01-01';

-- 失效查询（不满足最左前缀）
SELECT * FROM orders WHERE status = 1;           -- 索引失效
SELECT * FROM orders WHERE create_time > '2024-01-01'; -- 索引失效
```

**设计顺序建议：** 区分度高 → 常用条件 → 范围条件

#### 3. 索引失效场景（Java 高频坑点）

| 场景 | 反例 | 正确做法 |
|------|------|----------|
| 索引列运算 | `WHERE age + 1 = 20` | `WHERE age = 19` |
| 隐式类型转换 | `WHERE id = '123'`（id 为数字） | 保持类型一致 |
| 使用 OR | `WHERE status = 1 OR status = 2` | 改为 `IN (1,2)` |
| NOT IN / != | `WHERE status != 1` | 改写为范围查询 |
| LIKE 前缀模糊 | `WHERE name LIKE '%张三'` | 使用全文索引或搜索引擎 |

```xml
<!-- MyBatis 动态 SQL 需规避以上写法 -->
<select id="findActiveUsers" resultType="User">
    SELECT * FROM user
    WHERE status IN
    <foreach collection="statusList" item="s" open="(" separator="," close=")">
        #{s}
    </foreach>
    AND create_time >= #{startTime}
</select>
```

### （三）散列索引：等值查询极致优化

#### 1. 散列索引特性

- 等值查询 **O(1)**，不支持范围查询、排序
- 冲突影响性能，需合理设计哈希函数

#### 2. Java 技术栈适配

- **数据库**：Memory 存储引擎、Redis 哈希结构
- **应用场景**：用户 Token 校验、订单号精确查询

```java
// Redis 哈希实现等值查询 O(1)
@Service
public class TokenService {
    @Autowired
    private StringRedisTemplate redisTemplate;

    public boolean validateToken(String userId, String token) {
        String key = "user:token:" + userId;
        String stored = redisTemplate.opsForValue().get(key);
        return token.equals(stored);
    }
}
```

#### 3. 与 B+树选型对比

| 查询类型 | 推荐索引 | 说明 |
|----------|----------|------|
| 仅等值查询 | 散列索引 | O(1) 极致速度 |
| 范围/排序 | B+树索引 | 支持范围扫描与排序 |
| 混合查询 | B+树索引 | 兼顾等值与范围 |

> **Java 实践：** 热点等值数据用 Redis 哈希，数据库用 B+ 树。

### （四）位图索引：Java 统计类业务适配

#### 1. 适用场景

- 低基数列（性别、订单状态、是否删除）
- 多条件统计：`WHERE gender = 1 AND status = 2`

```sql
-- 位图索引示例（MySQL 不直接支持，InnoDB 用索引合并替代）
SELECT COUNT(*) FROM user WHERE gender = 1 AND status = 0;
```

#### 2. Java 后端应用

- 报表统计、后台筛选（商品类型、用户标签）
- > **注意：** 高基数列（手机号、ID）禁用，空间爆炸

### （五）索引设计：Java 后端表结构核心

#### 1. 选择性原则

> 选择性 = 不同值数 / 总行数，越高越适合建索引。

```sql
-- 低选择性反例：给 is_deleted (0/1) 单独建索引，几乎无效
CREATE INDEX idx_deleted ON user (is_deleted);  -- 不推荐
```

#### 2. 维护成本权衡

- 索引加速查询，但增删改需同步更新
- **Java 实践**：写多读少表（日志表）少建索引

#### 3. 工具支持

```java
// MyBatis-Plus：@TableIndex 自动建索引
@TableName("orders")
@TableIndex(name = "idx_user_id", columns = "user_id")
public class Order { ... }
```

```sql
-- 数据库：EXPLAIN 分析索引使用情况
EXPLAIN SELECT * FROM orders WHERE user_id = 101;
```

### （六）散列技术在 Java 后端扩展应用

#### 1. 分库分表哈希

```java
// Sharding-JDBC：哈希(user_id)路由表，均匀分布数据
// 解决单表数据量过大问题
ShardingStrategy strategy = new InlineShardingStrategy("user_id", "user_$->{user_id % 16}");
```

#### 2. 分布式缓存哈希

- Redis Cluster：虚拟槽哈希，实现数据分片
- 保证缓存高可用与负载均衡

#### 3. 一致性哈希

- 微服务节点路由、缓存扩缩容
- 避免数据全量迁移

## 索引与散列对 Java 后端核心价值

1. **解决查询性能瓶颈**：避免全表扫描，提升接口响应速度
2. **支撑高并发业务**：优化热点数据查询，降低数据库压力
3. **指导数据结构设计**：主键、索引、分表策略基于索引/散列原理
4. **适配复杂查询场景**：覆盖索引、位图索引满足统计、筛选需求

## Java 后端索引设计常见误区

| 误区 | 后果 |
|------|------|
| 索引越多越好 | 增删改性能下降，存储空间浪费 |
| 忽视最左前缀原则 | 复合索引使用不当，导致索引失效 |
| 低基数列建索引 | 选择性差，查询优化效果不明显 |
| 过度依赖散列 | 不支持范围查询，业务受限 |
| 未用覆盖索引 | 频繁回表查询，性能低下 |
