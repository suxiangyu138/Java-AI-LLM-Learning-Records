## 1. 数据库系统的产生背景

### 1.1 文件系统的缺陷

早期文件系统存在以下核心问题，催生了数据库系统的诞生：

| 问题 | 描述 | 影响 |
|------|------|------|
| **数据冗余与不一致** | 多应用重复存储相同数据，修改不同步 | 数据冲突、业务异常 |
| **数据孤立** | 数据分散在不同文件中，难以跨文件查询 | 无法支撑复杂业务关联 |
| **完整性约束缺失** | 无统一约束规则，易存储非法数据 | 数据质量无法保证 |
| **并发访问问题** | 并发读写易冲突，无事务保障 | 数据错乱、超卖 |
| **安全性差** | 权限控制弱，数据易泄露 | 安全风险 |
| **应用程序与数据强耦合** | 数据结构变更需修改大量代码 | 维护成本高 |

### 1.2 数据库系统的目标

解决文件系统弊端，实现数据的**统一管理、共享、安全、可靠**，降低应用开发与维护成本。

## 2. 数据库系统的核心定义

| 概念 | 定义 |
|------|------|
| **数据库 (DB)** | 长期存储、有组织、可共享的数据集合 |
| **数据库管理系统 (DBMS)** | 管理数据库的系统软件，是数据库系统的核心 |
| **数据库系统 (DBS)** | DB + DBMS + 应用程序 + 用户 + DBA 组成的完整系统 |

## 3. 数据视图与数据抽象

数据库系统通过**三层抽象**实现数据独立性：

```
┌─────────────────────────────────────┐
│           视图层 (View Level)        │  ← 面向用户的局部数据
│         应用可见的数据子集            │
├─────────────────────────────────────┤
│          逻辑层 (Logical Level)       │  ← 表结构、字段、约束
│        描述数据结构与关系              │
├─────────────────────────────────────┤
│          物理层 (Physical Level)      │  ← 磁盘存储、文件格式
│        描述数据存储细节                │
└─────────────────────────────────────┘
```

| 层次 | 关注点 | 说明 |
|------|--------|------|
| **物理层** | 数据存储细节 | 磁盘结构、文件格式、存储引擎 |
| **逻辑层** | 数据结构与关系 | 表定义、字段类型、约束（主键/外键） |
| **视图层** | 用户视角的局部数据 | 应用可见的数据子集，屏蔽敏感字段 |

## 4. 数据库语言

### 4.1 语言分类

| 语言 | 全称 | 功能 | 典型命令 |
|------|------|------|----------|
| **DDL** | Data Definition Language | 定义数据结构 | `CREATE`, `ALTER`, `DROP` |
| **DML** | Data Manipulation Language | 操作数据 | `SELECT`, `INSERT`, `UPDATE`, `DELETE` |
| **DCL** | Data Control Language | 权限控制 | `GRANT`, `REVOKE` |
| **TCL** | Transaction Control Language | 事务控制 | `BEGIN`, `COMMIT`, `ROLLBACK` |

### 4.2 DDL vs DML

```sql
-- DDL: 定义结构
CREATE TABLE users (
    id   INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50) NOT NULL,
    age  INT CHECK (age > 0)
);

-- DML: 操作数据
INSERT INTO users (name, age) VALUES ('张三', 25);
SELECT * FROM users WHERE age > 18;
UPDATE users SET age = 26 WHERE name = '张三';
DELETE FROM users WHERE id = 1;
```

## 5. 数据库架构

| 架构类型 | 特点 | 适用场景 |
|----------|------|----------|
| **集中式** | 单节点部署，简单直接 | 小型项目、单体应用 |
| **客户端/服务器 (C/S)** | 应用与数据分离，独立部署 | 传统企业应用 |
| **分布式** | 多节点协同，数据分片 | 微服务、高并发大流量 |

## 6. 数据库用户与 DBA 职责

### 6.1 用户分类

| 用户类型 | 角色描述 |
|----------|----------|
| **普通用户** | 通过应用程序访问数据，执行日常业务操作 |
| **应用程序员** | 编写数据库应用程序，设计表结构和 SQL |
| **DBA (数据库管理员)** | 负责数据库的规划、维护、优化和安全管理 |

### 6.2 DBA 核心职责

| 职责 | 说明 |
|------|------|
| **模式定义** | 设计数据库逻辑结构、表结构 |
| **存储结构定义** | 确定物理存储方案、索引策略 |
| **权限管理** | 用户创建、权限分配 (GRANT/REVOKE) |
| **备份恢复** | 制定备份策略，故障时恢复数据 |
| **性能优化** | SQL 调优、参数配置、资源监控 |

## 7. Java 后端视角深度解读

### 7.1 文件系统缺陷 ↔ Java 后端痛点

| 文件系统缺陷 | Java 后端对应场景 | 数据库解决方案 |
|-------------|-------------------|---------------|
| 数据冗余不一致 | 微服务各服务本地文件存储用户信息 | 统一数据库，单一数据源 |
| 数据孤立 | 订单/用户/商品分散在不同文件 | 关系型数据库关联查询 |
| 完整性约束缺失 | Java 代码中重复校验（年龄非负、手机号格式） | 数据库约束 (CHECK, UNIQUE) |
| 并发访问问题 | 高并发下库存扣减超卖/少卖 | 事务 + 锁机制 |
| 安全性差 | 敏感数据明文存储在文件中 | 加密存储 + 权限隔离 |

### 7.2 三层抽象 ↔ Java 分层架构

```
数据库三层抽象              Java 后端分层
─────────────────────────────────────────────
视图层 (View)        →     DTO/VO (数据传输对象)
                            │
逻辑层 (Logical)     →     Entity/Mapper (实体/数据访问层)
                            │
物理层 (Physical)    →     ORM 底层 (MyBatis/Hibernate)
```

| 数据库层次 | Java 后端对应 | 说明 |
|-----------|-------------|------|
| **物理层** | MyBatis/JPA/Hibernate 底层 | 屏蔽存储细节（InnoDB、索引结构） |
| **逻辑层** | Entity 实体类 + Mapper 接口 | 定义表结构、字段关系、约束 |
| **视图层** | DTO/VO + Service 层 | 按需筛选数据，屏蔽敏感字段 |

### 7.3 数据库语言 ↔ Java 技术栈

| 数据库语言 | Java 技术栈对应 |
|-----------|---------------|
| **DDL** | Flyway/Liquibase 版本控制、`schema.sql` 初始化脚本 |
| **DML** | MyBatis XML/注解 SQL、JPA JPQL、Spring Data JPA |
| **DCL** | Spring Security 权限控制 + 数据库 GRANT/REVOKE |
| **TCL** | `@Transactional` 声明式事务 |

### 7.4 数据库架构 ↔ Java 部署架构

| 数据库架构 | Java 部署架构 | 技术选型 |
|-----------|-------------|---------|
| **集中式** | 单体应用 + 单节点 DB | Spring Boot + MySQL |
| **C/S** | 应用服务器 + 独立数据库 | Tomcat + MySQL/PostgreSQL |
| **分布式** | 微服务 + 分库分表 | Spring Cloud + Sharding-JDBC + 主从复制 |

## 8. 常见误区与总结

### 8.1 Java 后端开发常见误区

| 误区 | 问题 | 正确做法 |
|------|------|----------|
| **忽视数据抽象** | 直接写原生 SQL 硬编码，切换 DBMS 困难 | 使用 ORM + 合理抽象 |
| **轻视约束规则** | 仅靠 Java 代码校验，高并发下数据不一致 | 数据库约束 + 代码校验双保险 |
| **盲目架构选型** | 小项目用分布式、大项目用单节点 | 根据实际流量和数据量选型 |
| **忽略 DBA 协作** | 表结构设计不合理、索引缺失 | 遵循范式、合理设计索引 |

### 8.2 总结

> **核心认知：** 数据库引言是数据库知识的总纲。从 Java 后端角度看，核心是理解"数据管理的演进逻辑"与"系统分层设计思想"。

掌握引言内容能够帮助开发者：

- ✅ **建立全局认知** — 理解数据库系统本质，从根源解决数据问题
- ✅ **指导技术选型** — 明确不同架构和 DBMS 的适用场景
- ✅ **规范开发行为** — 遵循数据抽象与约束规则，写出高质量代码
- ✅ **衔接进阶学习** — 为事务、并发控制、索引、分布式数据库等内容奠定基础
