## 核心内容（原书框架）

### 一、存储介质与文件组织

| 组件 | 说明 |
|------|------|
| 磁盘结构 | 磁盘页（块）为最小读写单位 |
| 顺序文件 | 按某字段顺序存储，适合范围查询 |
| 哈希文件 | 通过哈希函数定位，适合等值查询 |
| B+树索引文件 | 平衡多路搜索树，支持高效范围查询 |

### 二、索引结构

- **有序索引**：主索引（聚簇索引）、辅助索引（非聚簇索引）、稠密索引、稀疏索引
- **B+树**：MySQL 主流索引结构，支持范围查询
- **哈希索引**：等值查询 O(1)，不支持范围查询
- **位图索引**：适用于低基数列，位运算高效
- **聚簇索引**：数据与索引同存储，叶子节点即数据行

## Java 后端开发视角深度剖析

### （一）存储结构：Java后端性能的物理根基

#### 1. 磁盘页（Page）与Java数据交互

> **核心要点：** 数据库最小读写单位通常为 16KB（InnoDB），Java 批量操作应适配页大小以减少 I/O。

```sql
-- 示例：合理批量插入，适配页大小
INSERT INTO orders (id, user_id, amount) VALUES
(1, 101, 99.9),
(2, 102, 29.9),
...;  -- 每批建议控制在页大小适配范围内
```

- **Java 实践：** MyBatis `foreach` 批量操作应适配页大小，避免单行频繁更新导致页分裂
- **反例：** 单次批量过大，超过页大小，导致多次磁盘 I/O

#### 2. 文件组织对查询的影响

| 文件类型 | 适用场景 | Java 后端建议 |
|----------|----------|---------------|
| 顺序文件 | 范围查询（订单时间、用户ID） | 按时间/ID排序的分页查询 |
| 哈希文件 | 等值查询（用户ID、订单号） | 精确匹配的热点查询 |
| B+树文件 | 范围+等值混合查询 | 大多数业务场景首选 |

> **Java 实践：** 根据查询模式选择索引类型，避免全表扫描。

#### 3. 聚簇索引（InnoDB主键）

- 数据按主键顺序存储，范围查询极快
- **Java 实践：** 设计自增 ID / 雪花 ID 主键，避免随机插入导致页分裂

```java
// 推荐：雪花 ID 生成器
public class SnowflakeIdGenerator {
    private long workerId;
    private long sequence = 0L;
    // ...
    public synchronized long nextId() {
        // 生成趋势递增的分布式唯一 ID
    }
}
```

### （二）索引结构：Java后端查询优化核心

#### 1. B+树索引（MySQL主流）

- 所有数据存叶子节点，范围查询高效
- 复合索引遵循 **最左前缀原则**（Java 高频考点）

```sql
-- 复合索引 (user_id, status, create_time)
-- 有效查询（满足最左前缀）
SELECT * FROM orders WHERE user_id = 101 AND status = 1;
SELECT * FROM orders WHERE user_id = 101;

-- 失效查询（不满足最左前缀）
SELECT * FROM orders WHERE status = 1;  -- 索引失效
```

#### 2. 哈希索引

- 等值查询 O(1)，不支持范围查询
- 适用场景：Redis 缓存、用户 Token 校验
- **Java 实践：** 热点等值查询用 Redis 哈希，数据库用 B+树

#### 3. 索引设计与Java实践

| 原则 | 说明 |
|------|------|
| 高频查询字段建索引 | `user_id`、`order_no`、`status` |
| 避免过度索引 | 增删改性能下降 |
| 联合索引顺序 | 区分度高 → 常用条件 → 范围条件 |

```java
// MyBatis-Plus：@TableIndex 注解自动建索引
@TableName("orders")
@TableIndex(name = "idx_user_status", columns = {"user_id", "status"})
public class Order {
    private Long id;
    private Long userId;
    private Integer status;
}
```

### （三）查询处理流程：Java后端SQL执行本质

#### 1. 解析与预处理

- 校验 SQL 语法、表/字段存在性
- **Java 实践：** 避免 SQL 语法错误，使用预编译防止注入攻击

```java
// 推荐：使用 MyBatis 参数绑定，防止 SQL 注入
@Select("SELECT * FROM user WHERE id = #{id}")
User findById(@Param("id") Long id);
```

#### 2. 查询优化器（核心）

- 自动选择最优执行计划（索引、连接顺序）
- **Java 影响因素：** SQL 写法、索引设计、数据分布

```sql
-- 示例：子查询转 JOIN，优化器选择更优计划
-- 不推荐：
SELECT * FROM orders WHERE user_id IN (SELECT id FROM user WHERE status = 1);

-- 推荐：
SELECT o.* FROM orders o JOIN user u ON o.user_id = u.id WHERE u.status = 1;
```

#### 3. 执行引擎

- 调用存储接口获取数据
- **Java 实践：** 减少网络交互，批量获取数据，避免 N+1 查询

### （四）查询优化：Java后端性能调优关键

#### 1. 关系代数等价变换

| 策略 | 说明 | Java 实践 |
|------|------|-----------|
| 选择下推 | 先过滤后连接，减少中间结果 | WHERE 条件尽早过滤 |
| 投影下推 | 只查需要字段，减少数据传输 | 避免 `SELECT *` |

```sql
-- 不推荐
SELECT * FROM orders o JOIN users u ON o.user_id = u.id;

-- 推荐：明确查询列，减少数据传输
SELECT o.id, o.amount, u.name FROM orders o JOIN users u ON o.user_id = u.id;
```

#### 2. 连接顺序优化

- 小表驱动大表，减少循环次数
- **MyBatis 实践：** 关联查询时控制主表数据量

#### 3. 避免索引失效

| 场景 | 反例 | 正确做法 |
|------|------|----------|
| 函数操作 | `WHERE DATE(create_time) = '2024-01-01'` | `WHERE create_time >= ? AND create_time < ?` |
| 隐式类型转换 | `WHERE id = '123'`（id 为数字类型） | 保持类型一致 |
| 使用 OR/NOT IN | `WHERE status != 1` | 改写为范围查询或使用覆盖索引 |

### （五）缓冲区管理：Java后端并发性能保障

#### 1. 数据库缓冲区（Buffer Pool）

- 缓存热点数据页，减少磁盘 I/O
- InnoDB Buffer Pool：建议设为物理内存 50%~70%
- **Java 实践：** 高并发下依赖缓冲区提升响应速度

#### 2. 替换策略（LRU）

- 淘汰最少使用页
- **Java 实践：** 避免全表扫描（`SELECT *`）污染缓冲区

```java
// Java 本地缓存同样采用 LRU 策略
Cache<String, Object> cache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(10, TimeUnit.MINUTES)
    .build();
```

#### 3. 预读机制

- 顺序查询时预读相邻页
- 适用场景：分页查询、范围查询（订单列表）

### （六）事务存储与日志：Java后端一致性保障

#### 1. redo log（重做日志）

- 保证事务持久性，崩溃恢复
- **Java 实践：** 事务提交依赖 redo log 落盘

#### 2. undo log（回滚日志）

- 实现事务原子性与 MVCC
- 支持读已提交、可重复读隔离级别
- **Java 实践：** 长事务导致 undo log 膨胀，应避免大事务

```java
// 避免长事务：缩小事务边界
@Service
public class OrderService {
    @Transactional
    public void processOrder(Order order) {
        // 只包含必要的数据库操作
        orderDao.insert(order);
        inventoryDao.update(order.getProductId(), -1);
        // 耗时操作移出事务
    }
}
```

#### 3. MVCC（多版本并发控制）

- 读写不阻塞，提升并发性能
- **Java 实践：** MySQL 默认隔离级别（可重复读）依赖 MVCC 实现

## Java后端存储与查询常见误区

| 误区 | 说明 |
|------|------|
| 主键设计不合理 | UUID 随机插入导致页分裂，性能低下 |
| 索引滥用或缺失 | 单表索引过多，增删改缓慢；高频查询无索引，全表扫描 |
| 忽视SQL对存储的影响 | 大事务、全表查询污染 Buffer Pool，拖垮数据库 |
| 不理解MVCC机制 | 长事务导致幻读、数据膨胀，并发性能下降 |
| 批量操作不当 | 单次批量过大，超过页大小，导致多次磁盘 I/O |
