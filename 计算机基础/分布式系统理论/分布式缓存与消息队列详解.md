# 分布式缓存与消息队列详解

> 分布式缓存解决"快"的问题——用空间换时间，降低数据库压力；消息队列解决"稳"的问题——削峰填谷、解耦异步，保证系统可靠性。两者是分布式系统的左右护法。

## 一、分布式缓存

### 1.1 缓存分层架构

```
                    命中率       延迟
浏览器缓存 (HTTP Cache)    →    ~0ms
CDN 边缘缓存              →    10~50ms
Nginx 本地缓存            →    <1ms
应用本地缓存 (Caffeine)    →    <1ms     (JVM 内)
分布式缓存 (Redis)         →    1~5ms    (网络+内存)
数据库 (MySQL)            →    10~100ms  (磁盘)
```

### 1.2 缓存三大问题及解决方案

| 问题 | 场景 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 查不存在的数据 → 每次穿透到 DB | ① 布隆过滤器过滤不存在的 key ② 缓存空值（短 TTL） |
| **缓存击穿** | 热点 key 过期 → 大量并发打到 DB | ① 互斥锁：一个线程查 DB 重建，其他等待 ② 逻辑过期 + 异步更新 |
| **缓存雪崩** | 大量 key 同时过期 → DB 崩溃 | ① TTL 加随机值 ② 多级缓存 ③ 限流熔断兜底 |

### 1.3 缓存更新策略

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **Cache Aside** | 读：先缓存，miss 则查 DB 写：先更新 DB，再删缓存 | 最常用，简单 | 可能出现短暂不一致 |
| **Read/Write Through** | 缓存层代理 DB，读写都走缓存 | 缓存与 DB 强一致 | 实现复杂 |
| **Write Behind** | 异步批量写回 DB | 写入性能极高 | 缓存挂了丢数据 |

### 1.4 Cache Aside 的"先删缓存还是先更 DB"问题

```
先删缓存 + 后更 DB：
  A 删缓存 → B 读（缓存 miss，读 DB 旧值）→ B 写缓存（旧值）→ A 更 DB（新值）
  → 缓存中是旧值！不一致！

先更 DB + 后删缓存（推荐）：
  A 读缓存 miss → 读 DB 旧值 → B 更 DB 新值 → B 删缓存 → A 写缓存旧值
  → 概率极低（A 写缓存必须在 B 删缓存之后），99.9% 场景够用

兜底方案：设置合理过期时间 + 延迟双删（更 DB 后延迟几百 ms 再删一次）
```

### 1.5 Redis 集群模式

| 模式 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **主从复制** | 一主多从，读写分离 | 简单、读扩展 | 手动故障转移 | 小型项目 |
| **哨兵（Sentinel）** | 监控主从，自动故障转移 | 自动 HA | 不能水平扩展写 | 中型项目 |
| **Cluster** | 16384 个槽，多主多从 | 水平扩展，自动故障转移 | 跨槽操作受限 | 大型项目 |

### 1.6 淘汰策略

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| `noeviction` | 内存满拒绝写入 | 严格不能丢 |
| `allkeys-lru` | 所有 key 中淘汰最久未用的 | 通用（推荐） |
| `volatile-lru` | 有过期时间的 key 中淘汰 LRU | 部分 key 永久 |
| `allkeys-lfu` | 所有 key 中淘汰最少使用的 | 热点明显 |
| `volatile-ttl` | 淘汰即将过期的 | 对 TTL 敏感 |

## 二、消息队列

### 2.1 为什么需要 MQ？

| 作用 | 说明 | 无 MQ 的问题 |
|------|------|-------------|
| **异步** | 非核心流程异步处理，快速返回 | 用户等所有步骤完成，体验差 |
| **解耦** | 上下游通过 MQ 通信，互不依赖 | 直接 RPC，下游挂了上游也挂 |
| **削峰** | 突发流量暂存 MQ，下游平滑消费 | 流量高峰打垮下游 |
| **日志/数据分发** | 一个消息多方消费 | 需要维护多个推送通道 |

### 2.2 主流 MQ 对比

| 对比维度 | Kafka | RocketMQ | RabbitMQ | Pulsar |
|---------|-------|----------|----------|--------|
| **语言** | Java/Scala | Java | Erlang | Java |
| **吞吐量** | ⭐⭐⭐⭐⭐ 百万级 | ⭐⭐⭐⭐⭐ 十万~百万 | ⭐⭐⭐ 万级 | ⭐⭐⭐⭐⭐ |
| **延迟** | ms 级 | ms 级 | μs 级 | ms 级 |
| **事务消息** | ❌（需自己实现） | ✅ 原生支持 | ❌（需自己实现） | ❌ |
| **顺序消息** | 分区内有序 | ✅ 全局/分区有序 | 队列内有序 | 分区内有序 |
| **延时消息** | ❌ | ✅ 18 个级别 | 插件支持 | ✅ |
| **集群模式** | 分布式 | 分布式（NameServer 轻量） | 主从 | 分布式（存算分离） |
| **适用场景** | 大数据/日志/流处理 | 电商/金融业务消息 | 企业级/RPC 低延迟 | 多租户/云原生 |

### 2.3 Kafka 核心概念

```
Producer ─→ [Broker-1] [Broker-2] [Broker-3]
              │  Topic: order
              │  Partition-0 (Leader)──→ Replica (Follower)
              │  Partition-1 (Leader)──→ Replica (Follower)
              │  Partition-2 (Leader)──→ Replica (Follower)
              │
Consumer ─→  Consumer Group
              ├─ Consumer-1 → 消费 Partition-0,1
              └─ Consumer-2 → 消费 Partition-2
```

| 概念 | 说明 |
|------|------|
| **Topic** | 消息的逻辑分类 |
| **Partition** | 物理分片，一个 Topic 多个 Partition → 并行读写 |
| **Offset** | 消息在 Partition 中的唯一序号 |
| **Consumer Group** | 消费者组，组内每个消费者独占不同 Partition |
| **ISR** | In-Sync Replicas，与 Leader 保持同步的副本集合 |
| **HW/LEO** | High Watermark（已提交的最高 offset）/ Log End Offset |

### 2.4 消息可靠性保证

| 维度 | 配置 | 说明 |
|------|------|------|
| **生产端** | `acks=all`（Kafka）| 所有 ISR 确认才返回成功 |
| **Broker 端** | 多副本 + ISR + `unclean.leader.election.enable=false` | 不在 ISR 中的副本不能选为 Leader |
| **消费端** | 手动提交 offset，处理完再提交 | 防止自动提交导致丢消息 |

### 2.5 消息幂等性

| 方案 | 做法 |
|------|------|
| **数据库唯一键** | 用消息 ID 做唯一索引，`INSERT IGNORE` |
| **Redis SETNX** | 消息 ID 做 key，只有第一次设置成功 |
| **业务状态机** | 订单状态"已支付"不能重复扣款 |

### 2.6 消息顺序性

| 场景 | Kafka 方案 | RocketMQ 方案 |
|------|-----------|--------------|
| 全局有序 | 1 Topic 1 Partition（牺牲并行度） | 1 Topic 1 Queue |
| 局部有序 | 相同 key 发到同一 Partition | 相同 ShardingKey 发到同一 Queue |

## 三、面试高频问题

**Q1：Redis 和 Memcached 的区别？**
> Redis 支持多种数据结构（String/Hash/List/Set/ZSet）、持久化、集群、发布订阅；Memcached 只有 String、纯内存（重启丢数据）、多线程。现代项目无脑选 Redis。

**Q2：Kafka 为什么快？**
> ① 顺序写磁盘（比随机写快几个数量级）② Page Cache（OS 缓存读写）③ 零拷贝（sendfile，数据不经过用户态）④ 批量压缩 + 批量传输。

**Q3：怎么保证消息不丢？**
> 生产端 ack=all → Broker 多副本 + min.insync.replicas ≥ 2 → 消费端手动提交 offset。三者都做好，消息 0 丢失。

**Q4：怎么处理消息积压？**
> ① 临时扩容消费者 ② 增加 Partition → 增加并行度 ③ 消费逻辑优化（批量处理）④ 积压过大时跳过非关键消息，事后补偿。

**Q5：Kafka、RocketMQ、RabbitMQ 怎么选？**
> 大数据/日志 → Kafka；电商/金融业务 → RocketMQ（事务消息+延时消息）；低延迟/RPC → RabbitMQ。

## 📖 核心要点速记

1. **缓存三大问题**：穿透（布隆/空值）→ 击穿（互斥锁/永不过期）→ 雪崩（TTL 随机/多级/限流）
2. **缓存更新**：先更 DB，后删缓存（Cache Aside）
3. **Redis 集群**：主从 → 哨兵 → Cluster（按规模升级）
4. **MQ 选型**：大数据→Kafka，业务→RocketMQ，低延迟→RabbitMQ
5. **消息可靠三要素**：生产端 ack + Broker 持久 + 消费端手动提交
6. **幂等**：唯一键/状态机/SETNX
