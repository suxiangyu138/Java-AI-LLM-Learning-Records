# 分布式一致性协议详解

> 分布式一致性协议解决的核心问题是：在不可靠的网络环境下，如何让多个节点对某个值达成共识。Paxos 是理论奠基，Raft 是工程实现的事实标准。

## 一、一致性问题本质

### 1.1 什么是共识（Consensus）？

多节点对**同一个值**达成一致。
- 例如：谁是 Leader？这笔交易的顺序是什么？这个配置的值应该是什么？

### 1.2 为什么需要共识算法？

| 场景 | 如果没有共识算法 |
|------|----------------|
| 选主 | 可能出现脑裂（两个节点都认为自己是 Leader） |
| 日志复制 | 不同节点的日志顺序不一致，数据错乱 |
| 配置变更 | 各节点配置不同，行为不一致 |
| 分布式锁 | 同一把锁被多个客户端获取 |

### 1.3 FLP 不可能定理

> 在异步通信的分布式系统中，即使只有一个节点可能故障，也不存在一个确定性算法能在有限时间内达成共识。

**工程应对**：用超时机制打破纯异步假设 → 实际系统中可以实现共识（只是可能超时）。

## 二、Paxos 协议

> 1990年 Leslie Lamport 提出，是第一个被证明正确的共识算法。被誉为"分布式系统的珠穆朗玛峰"——难理解，更难实现。

### 2.1 三种角色

| 角色 | 职责 |
|------|------|
| **Proposer（提议者）** | 提出提案（值），推动共识 |
| **Acceptor（接受者）** | 投票表决是否接受提案 |
| **Learner（学习者）** | 学习最终被选定的值，不参与投票 |

> 一个节点可以同时担任多种角色。

### 2.2 Basic Paxos 两阶段流程

```
阶段一：Prepare（准备）
  Proposer → 所有 Acceptor：Prepare(N)  // N 为提案编号
  Acceptor → Proposer：Promise(N, 已有最高编号提案的值)
    条件：N > 之前承诺过的任何编号
    如果接受了过某个提案，一并返回该提案的值和编号

阶段二：Accept（接受）
  Proposer 收到多数派 Promise 后：
    如果所有 Promise 都没有返回值 → 用自己的值发起 Accept(N, V)
    如果某个 Promise 返回了值 → 用返回的最高编号的值发起 Accept(N, V_max)
  Proposer → 所有 Acceptor：Accept(N, V)
  Acceptor → Proposer：Accepted(N, V)
    条件：N >= 自己承诺过的最大编号

共识达成：多数派 Accepted → 值被选定
```

### 2.3 Multi-Paxos

Basic Paxos 每次选一个值就要两轮 RPC，太慢。Multi-Paxos 的优化：

| 优化 | 做法 |
|------|------|
| **选 Leader** | 长期只有一个 Proposer，减少 Prepare 阶段 |
| **日志复制** | 一次 Prepare 后连续多次 Accept（Raft 的核心思想来源） |

### 2.4 为什么 Paxos 难以工程化？

- 论文晦涩难懂（Paxos Made Simple 也不简单）
- 没有给出完整的工程细节（日志压缩、成员变更等）
- 多 Paxos 变体之间差异大，选型困难

## 三、Raft 协议

> 2013年提出，设计目标就是**易于理解**。通过分解问题（选主 + 日志复制 + 安全），让每个子问题独立求解。

### 3.1 Raft 三大子问题

| 子问题 | 解决内容 |
|--------|---------|
| **Leader 选举** | 选出一个 Leader 管理日志 |
| **日志复制** | Leader 将日志复制到所有 Follower |
| **安全性** | 保证最终一致（选举限制、提交限制） |

### 3.2 三种角色与状态

```
        选举超时
    ┌─────────────┐
    │   Follower  │ ←── 收到 Leader 心跳
    └──────┬──────┘
           │
    收到多数票
    ┌──────▼──────┐         发现更高 Term
    │   Leader    │ ──────────────────→ Follower
    └─────────────┘
           │
    发现更高 Term
    ┌──────▼──────┐
    │  Candidate  │
    └─────────────┘
```

### 3.3 Leader 选举

| 概念 | 说明 |
|------|------|
| **Term（任期）** | 逻辑时钟，每次选举递增，单调递增 |
| **选举超时** | Follower 一段时间没收到心跳 → 变为 Candidate，Term+1，投票给自己 |
| **投票规则** | 每个节点每个 Term 只能投一票，Candidate 日志不能比自己旧 |
| **胜选条件** | 获得多数派（≥ N/2+1）投票 |

### 3.4 日志复制

```
Client ─→ Leader
            │
            ├─ 1. 将命令追加到本地日志
            ├─ 2. 并行发送 AppendEntries RPC 给所有 Follower
            ├─ 3. 多数派确认后 → 提交（committed）
            └─ 4. 返回结果给 Client
                    │
                    └─ 5. 后续心跳中通知 Follower 提交
```

### 3.5 Raft 安全性保证

| 规则 | 目的 |
|------|------|
| **选举限制** | Candidate 的日志必须至少和多数派一样新 → 保证新 Leader 包含所有已提交日志 |
| **提交限制** | Leader 只能提交当前 Term 的日志 → 防止已提交日志被覆盖 |
| **日志匹配** | 相同 index + term → 之前所有日志相同 → 保证一致性 |

## 四、ZAB 协议（ZooKeeper）

> ZooKeeper Atomic Broadcast，ZooKeeper 使用的共识协议，类似 Raft 但不同。

| 对比 | ZAB | Raft |
|------|-----|------|
| 状态 | 4 种（LOOKING/LEADING/FOLLOWING/OBSERVING） | 3 种（Leader/Follower/Candidate） |
| 日志提交 | 支持乱序提交（TCP 保证有序） | 严格按 index 顺序提交 |
| 快速选举 | 有快速选举机制 | 选举超时触发 |
| 成员变更 | 支持动态配置变更 | 单节点变更（joint consensus） |

## 五、共识算法的工程对比

| 对比维度 | Paxos | Raft | ZAB |
|---------|-------|------|-----|
| 可理解性 | ⭐ 极难 | ⭐⭐⭐⭐⭐ 极易 | ⭐⭐⭐ 中等 |
| 工程实现 | Google Chubby 等少数 | etcd、TiKV、Consul | ZooKeeper |
| 性能 | 理论最优 | 接近 Paxos | 略低于 Raft |
| Leader 选举 | 不强制单 Leader | 强 Leader 模型 | 强 Leader 模型 |
| 成员变更 | 未明确定义 | 单节点变更 | 动态配置 |
| 适用场景 | 理论研究 | 大规模生产 | ZooKeeper 生态 |

## 六、面试高频问题

**Q1：Paxos 和 Raft 的核心区别？**
> Paxos 是理论模型，Raft 是工程实现。Raft 通过强 Leader、日志匹配规则、成员变更协议等工程细节让共识算法真正可落地。核心思想一致：多数派投票。

**Q2：为什么必须是多数派（> N/2）？**
> 两个多数派必然有交集 → 保证至少一个节点知道之前选定的值 → 新 Leader 不会覆盖旧数据。如果用全部节点（N），任意一个故障系统就不可用。

**Q3：Raft 怎么保证不会选出日志落后的 Leader？**
> 选举限制：Candidate 发 RequestVote 时带上自己的最新日志的 term + index；投票者只投票给日志不比自己旧的 Candidate。

**Q4：Raft 的"脑裂"问题如何解决？**
> 旧 Leader 被网络隔离后，新 Leader 被选出。旧 Leader 在旧 Term 中尝试提交时，因得不到多数派确认而失败。收到新 Term 的心跳后自动降级为 Follower——通过 Term 机制天然防脑裂。

## 📖 核心要点速记

1. **Paxos**：理论奠基，两阶段（Prepare + Accept），多数派共识
2. **Raft**：工程标准，三子问题（选主 + 日志复制 + 安全），易于理解
3. **共同点**：都是多数派投票，都保证最终一致
4. **关键数**：N = 2F+1，容忍 F 个节点故障，5 节点集群最多挂 2 个
5. **一句话**：Paxos 难懂难写 → Raft 易懂易写 → 选 Raft
