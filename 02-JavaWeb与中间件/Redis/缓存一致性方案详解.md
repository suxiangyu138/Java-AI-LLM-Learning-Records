# 缓存一致性方案详解

## 问题背景

缓存（Redis）和数据库（MySQL）是两套存储系统，更新时无法天然保证一致性。常见场景如：更新了用户信息，但缓存里还是旧数据。

## Cache Aside 模式（最常用）

**读：** 先读缓存 → 缓存有直接返回 → 缓存无则读 DB，回写缓存
**写：** 先更新 DB → 再删除缓存

```java
public User getUser(Long userId) {
    String cacheKey = "user:" + userId;
    User user = redisTemplate.opsForValue().get(cacheKey);
    if (user != null) return user;

    user = userMapper.selectById(userId);
    if (user != null) {
        redisTemplate.opsForValue().set(cacheKey, user, 30, TimeUnit.MINUTES);
    }
    return user;
}

@Transactional
public void updateUser(User user) {
    userMapper.updateById(user);           // 1. 先更新 DB
    redisTemplate.delete("user:" + user.getId());  // 2. 再删除缓存
}
```

**为什么不是更新缓存而是删除？**
更新缓存可能做无用的序列化计算（尤其是更新后很长时间没人读）。直接删除，等下次读再懒加载，更简单安全。

## 不一致的极端场景

**场景：缓存刚过期，读请求和写请求并发**

```
写请求：                 读请求：
1. 更新 DB              2. 查缓存（miss）
3. 删除缓存             4. 读 DB（读到旧数据，因为 3 还没执行）
                        5. 写缓存（旧数据！）
```

概率极低（写 DB 通常比读 DB 慢），但理论上存在。解决：**延迟双删**

```java
@Transactional
public void updateUser(User user) {
    redisTemplate.delete("user:" + user.getId());  // 1. 先删
    userMapper.updateById(user);                   // 2. 更新 DB
    // 3. 延迟再删
    CompletableFuture.runAsync(() -> {
        try { Thread.sleep(500); } catch (InterruptedException e) { }
        redisTemplate.delete("user:" + user.getId());
    });
}
```

## Read/Write Through 模式

缓存层作为数据访问的统一入口，业务代码只和缓存交互，缓存层负责同步 DB。适合有成熟缓存中间件的场景。

## Write Behind 模式

先写缓存，异步批量写 DB。写入延迟最低但一致性最弱，丢缓存可能丢数据。适合日志、计数等允许少量丢失的场景。

## 模式对比

| 模式 | 一致性 | 性能 | 复杂度 | 适用 |
|------|--------|------|--------|------|
| Cache Aside | 最终一致 | 高 | 低 | 绝大多数场景 |
| Read/Write Through | 较强 | 中 | 中 | 缓存中间件成熟 |
| Write Behind | 弱 | 极高 | 高 | 日志/计数 |
| 延迟双删 | 较强 | 高 | 中 | 对一致性要求高时 |

## 最终一致性兜底

**Canal + MQ**：监听 MySQL binlog → Canal 解析 → 发 MQ → 更新 Redis

```
MySQL 更新 → binlog → Canal 监听 → MQ → 消费端更新 Redis
```

适合对缓存一致性要求较高的核心业务。

## 生产实践

- **设过期时间兜底**：所有缓存都设过期时间（建议 5-30 分钟），即使删除失败也会自动过期
- **先更新 DB 再删除缓存**：不要反过来，先删缓存再更新 DB 会放大不一致窗口
- **缓存 NULL 值防穿透**：查不到数据也缓存空值（设短过期时间），防止大量请求打穿 DB
- **不要追求强一致性**：缓存的设计目标就是最终一致性，真有强一致性需求就直读 DB
