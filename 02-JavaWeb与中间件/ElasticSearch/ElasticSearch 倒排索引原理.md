# ElasticSearch 倒排索引原理（Java 后端企业级实战版）

> **文档定位**：Java 后端企业级技术文档 | ES 底层原理深度解析
> **版本**：Elasticsearch 7.x/8.x
> **核心问题**：ES 为什么比 MySQL 快？倒排索引如何工作？

---

## 一、正排索引 vs 倒排索引

### 1.1 MySQL 正排索引（B+Tree）

```
文档ID → 内容
  doc1 → "计算机专业学生"
  doc2 → "计算机科学与技术"
  doc3 → "软件工程专业"

查询"计算机"：全表扫描 / 模糊LIKE，慢
```

- **结构**：行 → 字段值的映射
- **问题**：模糊搜索必须全表扫描每个字段

### 1.2 ES 倒排索引

```
词项(Term) → 文档ID列表[ ]
  "计算机"   → [doc1, doc2]
  "专业"     → [doc1, doc3]
  "科学"     → [doc2]
  "技术"     → [doc2]
  "软件"     → [doc3]
  "工程"     → [doc3]
  "学生"     → [doc1]
```

查询"计算机"：直接查 Term Dictionary，O(1)找到文档列表

## 二、倒排索引三大核心结构

```
┌─────────────────────────────────────┐
│          Term Dictionary（词项词典）   │  <- FST 压缩存储，内存常驻
│  "计算" → offset                    │
│  "计算机" → offset                   │
│  "专业" → offset                    │
└────────────┬────────────────────────┘
             ↓
┌─────────────────────────────────────┐
│        Posting List（倒排列表）       │  <- Skip List 加速跳转
│  "计算机": [doc1(boost), doc2]       │
│  "专业":   [doc1(boost), doc3]       │
└────────────┬────────────────────────┘
             ↓
┌─────────────────────────────────────┐
│        Payload / Position           │  <- 位置信息（高亮、短语匹配）
│  词位置、词偏移、词频(TF)              │
└─────────────────────────────────────┘
```

### 2.1 Term Dictionary（词项词典）

存储所有不重复的词项，使用 **FST（Finite State Transducer）** 压缩：
- 共享前缀压缩，内存占用极小
- 支持 O(len) 查找，字符越多越精确
- 全部常驻内存（Lucene 的秘技）

### 2.2 Posting List（倒排列表）

每个 Term 对应一个 Posting List，记录包含该 Term 的所有文档 ID：

```
"计算机": [1, 3, 5, 7, 9, 11, 13, 15]
         → Delta 编码 → [1, 2, 2, 2, 2, 2, 2, 2]
         → 压缩后仅占几个字节
```

采用 **FOR（Frame Of Reference）+ Roaring Bitmap** 压缩：
- Delta 编码：存差值而非绝对值
- 对于大量文档 ID，使用 Bitmap 压缩

### 2.3 Skip List（跳表）

在 Posting List 上建跳表，实现 O(log n) 的多词项交集：

```
多词查询 "计算机 AND 专业" ：
  "计算机": [1, 3, 5, 7, 9, 11, 13]  ← Skip List 跳
  "专业":   [1, 4, 7, 10, 13]        ← Skip List 跳
  → 交集:  [1, 7, 13]
```

## 三、段（Segment）机制

### 3.1 什么是 Segment

ES 中的一个 Shard 由多个 **Segment** 组成，每个 Segment 是一个完整的**倒排索引**：

```
Shard = Segment1 + Segment2 + Segment3 + ...
```

- Segment 是**不可变**的（写入后不修改），类似 LSM Tree 的 SSTable
- 删除文档：标记删除（`.del` 文件），而非物理删除
- 更新文档：标记旧文档为删除 + 写入新文档

### 3.2 Segment 合并

```
写入: Seg1(100条) → Seg2(100条) → Seg3(100条)
                    ↓ 合并
         Seg4(300条) ← 查询加速，删除真正释放空间
```

- 后台自动合并小 Segment 为大 Segment
- 减少查询时需要扫描的 Segment 数量
- 真正回收被标记删除的文档空间

## 四、列式存储（Doc Values）

### 4.1 为什么需要 Doc Values

倒排索引擅长**搜索**，但不擅长**排序和聚合**：

```json
// 需求：查询 desc 包含"计算机"，按 age 排序
// 倒排索引：只能找到"计算机"对应哪些 doc
// 还需要：快速获取这些 doc 的 age 字段值进行排序
```

### 4.2 Doc Values 原理

```
倒排索引：
  Term → DocIDs（用于搜索）

Doc Values（正排索引）：
  DocID → Field Value（用于排序、聚合、过滤）
```

- 列式存储，每个字段单独存储
- 可以快速的通过 DocID 拿到字段值
- 存储在磁盘，OS Page Cache 加速

### 4.3 对比

| 结构 | 方向 | 用途 |
|---|---|---|
| 倒排索引 | Term → [DocID] | 全文搜索 |
| Doc Values | DocID → Value | 排序、聚合、精确过滤 |
| fielddata (内存) | DocID → Value | 同上但纯内存，text 字段用（谨慎） |

## 五、与 MySQL B+Tree 对比

| 维度 | MySQL B+Tree | ES 倒排索引 |
|---|---|---|
| **数据结构** | 平衡多路搜索树 | FST + Skip List + Posting List |
| **搜索方式** | 前缀匹配、区间扫描 | 全文分词匹配 |
| **模糊搜索** | `LIKE %keyword%` 全表扫描 | Term 直接命中，O(1) |
| **最左前缀** | 强依赖索引顺序 | 不依赖，独立匹配 |
| **排序** | 叶子链表，天然有序 | 需 Doc Values |
| **更新** | 原地更新 | 标记删除 + 新增（不可变） |
| **适用场景** | 事务、精确查询、JOIN | 全文搜索、分词、海量文本 |

## 六、为什么 ES 这么快

1. **倒排索引**：查询直接命中词项，不需要遍历
2. **FST 全内存**：Term Dictionary 在内存中，查找速度极快
3. **分片并行**：查询分发到所有分片并行执行
4. **Segment 不可变**：无锁读，不需要事务开销
5. **Doc Values**：列式存储加速排序和聚合
6. **缓存分层**：Query Cache、Fielddata Cache、OS Page Cache

---

## 七、面试核心要点

1. **倒排索引是什么？** Term → [DocID] 的映射，用 FST + Posting List 实现
2. **为什么 ES 不能替代 MySQL？** ES 不支持事务、不支持 JOIN、写入后不是立即可见
3. **Segment 为什么不可变？** 不可变 = 无锁读 = 高并发；更新通过标记删除实现
4. **删除文档空间何时释放？** Segment 合并时
5. **路由公式是什么？** `hash(routing) % num_primary_shards`

---

## 八、极简总结

```
MySQL B+Tree：顺序好，模糊慢
ES 倒排索引：模糊快，事务无

倒排 = 把"文档→词"反过来存成"词→文档"
查词 = 直接命中，不用扫全表
```
