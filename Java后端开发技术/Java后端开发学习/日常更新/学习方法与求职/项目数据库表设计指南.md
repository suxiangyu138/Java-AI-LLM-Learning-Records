项目数据库与表数量设计指南
一、先搞懂两个核心概念
1. 数据库：MySQL 里一个  database  / Schema，对应一套独立的账号、权限、隔离规则；
2. 表：数据库里的  table ，存储实体数据（用户、订单、商品等）。
 
二、不同规模项目：数据库数量参考
1. 小型项目（个人/小团队、单体应用）
- 场景：个人博客、小型工具、简单管理后台、学生毕设
- 数据库数量：1 个数据库
- 设计：所有业务表都放在同一个库，最简单、维护成本最低
2. 中型项目（企业内部系统、中小型SaaS、垂直业务平台）
- 场景：电商小店、CRM、OA、教务系统、中小型后台服务
- 数据库数量：1～3 个数据库
- 常见拆分方式：
- 业务库 + 日志库
- 核心业务库 + 配置库 + 统计库
3. 大型项目（互联网平台、高并发系统、微服务架构）
- 场景：电商平台、支付系统、内容平台、多租户SaaS、金融系统
- 数据库数量：按业务模块拆分，N 个数据库
- 典型拆分逻辑：
- 用户库、订单库、商品库、支付库、日志库、统计库、配置库、风控库等
- 微服务架构：一个微服务对应一个独立数据库，彻底解耦
 
三、不同规模项目：数据表数量参考
1. 小型项目
- 表数量：5～30 张
- 常见表：用户表、角色权限表、1～2 张业务主表、少量关联表、字典表
2. 中型项目
- 表数量：30～100 张
- 特点：模块变多、权限体系完善、有流程审批、有统计、有日志、有历史记录表
3. 大型项目
- 表数量：100 张以上，几百～上千张都很正常
- 特点：分库分表、冷热数据分离、多维度冗余表、历史归档表、分租户表、分业务线表
 
四、核心设计原则（决定你该用多少库/表）
1. 什么时候要「分库」？
- 业务模块高度独立，团队拆分开发维护；
- 单库 IO 压力过大、连接数不够、读写瓶颈；
- 数据安全隔离（比如支付数据和普通业务数据不能放一起）；
- 多租户SaaS，需要物理隔离不同客户数据；
- 不同模块更新频率、备份策略、权限完全不同。
2. 什么时候要「分表」？
- 单表数据量过大（MySQL 建议单表控制在 千万级以内，最优百万级）；
- 冷热数据分离（订单历史、日志单独分表/分库）；
- 按时间、用户ID、地区做水平分表；
- 大字段拆分（比如商品详情、富文本单独一张表）。
3. 新手最容易踩的坑
1. 一上来就搞多库多表，过度设计，维护爆炸；
2. 所有东西塞一张大表，后期扩展、查询、改表全是坑；
3. 权限、字典、系统配置表不抽离，到处冗余字段。
 
五、给你一个「通用标准模板」（直接套用）
单体中小型项目（最常用）
- 数据库：1 个
- 表结构建议：
- 系统模块：用户、角色、权限、菜单、字典、配置
- 业务模块：主业务表、关联表、明细表、状态表
- 辅助模块：操作日志、登录日志、定时任务、文件记录
微服务项目标准拆分
- 用户服务 → user_db
- 订单服务 → order_db
- 商品服务 → goods_db
- 支付服务 → pay_db
- 日志/监控 → log_db
- 统计分析 → stat_db
 
六、一句话总结
- 小项目：1 库，几十张表足够；
- 中项目：1～3 库，30～100 张表；
- 大项目：按服务分库，表数量无上限，按需拆分。
