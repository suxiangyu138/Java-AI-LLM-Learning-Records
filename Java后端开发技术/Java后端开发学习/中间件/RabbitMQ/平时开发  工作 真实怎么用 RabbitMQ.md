平时开发 / 工作 真实怎么用 RabbitMQ
一、你平时什么时候会用 MQ？（真实业务场景）
只要遇到下面这些情况，必加 RabbitMQ：
1. 接口响应太慢（发短信、发邮件、日志记录、推送消息）
→ 异步处理，接口立马返回，后台慢慢跑
2. 秒杀、高并发抢购、短时间流量爆炸
→ 流量削峰，请求放进队列，慢慢消费
3. 系统解耦
下单成功 ≠ 必须立刻扣库存、发短信、物流创建
→ 下单只发消息，其他服务监听队列自己处理
4. 定时/延迟任务
比如：订单30分钟未支付自动取消（死信队列）
5. 最终一致性、可靠消息补偿
简单记：慢的、量大的、没必要同步做的、需要解耦的，全扔 MQ
 
二、日常最标准使用流程（90% 项目都这么写）
1. 整体流程
1. 生产者（业务服务）
做完核心业务，发一条消息到 RabbitMQ 交换机
2. 交换机
根据路由规则，转发消息到指定队列
3. 队列
消息落地存储，等待消费
4. 消费者（独立/同服务）
监听队列，后台慢慢执行业务
 
三、日常开发只用这三种交换机
1. Direct 直连（最常用）
- 一对一
- 精准匹配  routingKey 
- 用途：单服务点对点发送、简单异步任务
2. Topic 主题（企业级最常用）
- 模糊匹配  * # 
- 用途：日志、多模块订阅、复杂业务事件
3. Fanout 广播
- 无视路由 key，全部队列都收到
- 用途：全局通知、缓存刷新、多服务同步事件
 
四、你写代码时固定套路（SpringBoot 日常写法）
1. 引入依赖
xml
spring-boot-starter-amqp
 
2. 配置yml
yaml
spring:
  rabbitmq:
    host: localhost
    port: 5672
    username: admin
    password: 123456
 
3. 配置类：声明交换机、队列、绑定
项目启动只初始化一次
4. 生产者发消息
java
rabbitTemplate.convertAndSend("交换机","路由key",消息体);
 
5. 消费者监听
java
@RabbitListener(queues = "队列名")
public void handleMsg(String msg){
    // 执行业务
}
 
 
五、线上/本地开发 必开的 4 个保障（工作硬性要求）
1. 消息持久化
重启 MQ 消息不丢
2. 生产者确认 Confirm
保证消息一定到达 MQ
3. 消费者手动 ACK
业务处理成功才签收，失败自动重试
4. 死信队列
失败多次的消息不卡死，进入死信人工处理
 
六、你本地学习怎么最简单用？
1. Docker 一键启动 RabbitMQ
2. 打开后台管理页面： 15672  控制台
3. 代码里：
- 先创建队列、交换机
- 写一个生产者发消息
- 写一个消费者收消息
4. 控制台可以：
看队列、看消息、手动删除、排查积压
 
七、极简人话总结（背下来就够用）
1. 复杂耗时操作异步就用 RabbitMQ
2. 架构解耦、高并发削峰全靠 MQ
3. 日常开发固定三件套：
- 生产者发消息
- 交换机路由
- 消费者监听消费
4. 本地 Docker 部署，开发最舒服，不污染本机
5. 正式项目必须加：持久化、ACK、死信、消息确认
