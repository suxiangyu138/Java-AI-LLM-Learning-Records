## 1. 基础概念与核心原理

### Q1：高并发场景下，Redis 预减库存和 MySQL 直接扣库存有什么区别？为什么秒杀必须用 Redis？

**面试官意图：** 考察对高并发场景下缓存与数据库协同工作的理解。

**完美解答：**

**MySQL 直接扣库存的问题：**
- MySQL 单行写入 QPS 约 500-1000，秒杀场景瞬间 10 万请求时完全扛不住
- 行级锁导致排队：大量请求阻塞在 `UPDATE ... WHERE stock > 0` 这行 SQL 上
- 连接池被打满：数据库连接被占满后，其他业务也无法正常使用

**Redis 预减库存的优势：**
- Redis 单机写入 QPS 约 8-10 万，是 MySQL 的 100 倍以上
- Lua 脚本保证"判断库存 + 扣减"原子操作，不需要锁

```lua
-- Redis Lua 预减库存脚本
local key = KEYS[1]          -- 库存 key
local quantity = tonumber(ARGV[1])  -- 购买数量

local stock = redis.call('GET', key)
if not stock then
    return -1  -- key 不存在
end

if tonumber(stock) < quantity then
    return 0   -- 库存不足
end

redis.call('DECRBY', key, quantity)
return 1       -- 扣减成功
```

**完整流程：**
```
用户请求 → Nginx 负载均衡
              ↓
         Redis Lua 预减库存（原子操作，QPS 8-10w）
              ↓
         判断 stock > 0？
         ├─ 否 → 直接返回"已售罄"（毫秒级快速失败）
         └─ 是 → 发消息到 RabbitMQ
                       ↓
                  消费者异步创建订单（削峰填谷）
                       ↓
                  MySQL 最终扣减库存
```

**延伸追问应对：** 如果面试官问"Redis 预减库存了，MySQL 那边扣减失败怎么办？"回答：需要最终一致性补偿机制，比如加一个"回补库存"的定时任务，比对 Redis 和 MySQL 中的库存差异。

### Q2：什么是 RAG？为什么大模型需要 RAG 而不是只靠训练数据？

**面试官意图：** 考察对 AI 大模型应用落地的核心理解。

**完美解答：**

RAG（Retrieval-Augmented Generation，检索增强生成）是一种让大模型在回答问题时先检索相关知识，再基于检索结果生成答案的技术范式。

**为什么需要 RAG：**

| 能力维度 | 纯大模型（无 RAG） | 大模型 + RAG |
|----------|-------------------|--------------|
| 知识时效性 | 训练数据截止日之后的知识不知道 | 实时检索最新文档，知识不过时 |
| 内部知识 | 不知道企业私有数据 | 检索企业知识库，回答内部问题 |
| 幻觉控制 | 可能胡编乱造 | 基于检索结果生成，事实更准确 |
| 可溯源 | 说不清信息来自哪 | 每句话可引用来源文档 |
| 成本 | 微调更新知识成本高 | 更新文档库即可，无需重新训练 |

**核心流程：**
```
文档上传 → 文本提取 → 分块（Chunk）→ Embedding → 存入向量库
                                        
用户提问 → 问题 Embedding → 向量检索 Top-K → 拼接 Prompt → 调用 LLM
                                                                  ↓
                                                            返回答案 + 引用来源
```

**延伸追问应对：** 如果问"RAG 和微调的区别"，回答：RAG 是"给模型配了一本可以随时翻阅的参考书"，微调是"让模型把知识背下来"。RAG 适合高频更新的知识，微调适合让模型学会某种风格或格式。

### Q3：什么是 Agent？ReAct 模式是怎么工作的？

**面试官意图：** 考察对 AI Agent 核心范式的理解。

**完美解答：**

Agent（智能体）是一个能自主感知环境、做出决策、执行行动的 AI 系统。它不止是"对话"，而是能调用工具、执行任务、完成复杂工作流的自主程序。

**ReAct（Reasoning + Acting）模式** 是目前最主流的 Agent 范式，核心思想是"边想边做"：

```
用户：我的订单 ORD-001 什么时候发货？
              ↓
    Agent（大模型驱动推理）
              ↓
   Thought: 用户想知道订单状态，我需要查询订单信息
   Action: 调用 OrderQueryTool(order_id="ORD-001")
   Observation: 订单状态="已发货"，快递单号=SF123456
              ↓
   Thought: 用户还想知道快递走到哪了，我需要查物流信息
   Action: 调用 LogisticsQueryTool(tracking_no="SF123456")
   Observation: 快递到达"北京分拣中心"，预计明天送达
              ↓
   Final Answer: 您的订单 ORD-001 已发货（快递 SF123456），
                 目前已到达北京分拣中心，预计明天送达。
```

**ReAct 的循环过程：**
1. **Thought（思考）**：分析当前状态，决定下一步行动
2. **Action（行动）**：调用一个工具执行具体操作
3. **Observation（观察）**：获取工具返回的结果
4. 重复 1-3 直到获得足够信息 → 输出 Final Answer

> 🎯 **面试核心**：Agent 和普通 API 调用的最大区别是"Agent 能自主决策该调用哪个工具、怎么处理工具返回的结果"——这需要大模型有推理能力，不只是生成。

## 2. 项目实战深度问答

> 💡 面试官会深挖你的项目细节，验证你"真的做过"而不是"背过"

### Q4：秒杀系统的超卖问题你是怎么解决的？请从数据层面讲清楚。

**面试官意图：** 考察对数据一致性和并发安全的理解深度。

**完美解答：**

超卖问题是秒杀系统最核心的技术难点。我用的是"三层防线"方案：

**第一层防线：Redis Lua 脚本（原子操作）**
```lua
-- 在 Redis 这边就把超卖拦住，Lua 保证原子性
if tonumber(redis.call('GET', KEYS[1])) >= tonumber(ARGV[1]) then
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 1
end
return 0
```
Redis 是单线程模型，Lua 脚本在 Redis 中执行时不会被其他命令打断，天然原子。

**第二层防线：MySQL 行级锁**
```sql
-- 扣库存时加库存数量条件，CAS 思想
UPDATE product 
SET stock = stock - 1 
WHERE id = ? AND stock > 0;
-- 返回影响行数，如果为 0 则说明库存不足
```

**第三层防线：唯一索引防止重复下单**
```sql
-- 每个用户 + 每场秒杀活动只能下一单
ALTER TABLE seckill_order 
ADD UNIQUE INDEX uk_user_session (user_id, session_id);
```

**这三种方式怎么配合？**
```
Redis Lua（第一道，抵挡 99.9% 的流量）
    ↓ 通过后
发送 MQ 消息 -> 消费者异步处理
    ↓
MySQL CAS 扣库存（第二道，防 Redis 异常）
    ↓ 成功后
插入订单 -> 唯一索引（第三道，防重复）
```

**延伸追问应对：** 如果面试官问"那 Redis 和 MySQL 库存数据不一致怎么办？"回答：设计一个"对账补偿"任务，定时扫描比对 Redis 和 MySQL 中的库存数据，发现差异按 MySQL 为准修正。

### Q5：你在 RAG 项目中是怎么做检索优化的？混合检索比纯向量检索好在哪里？

**面试官意图：** 考察 RAG 系统的深度理解，不是只调 API 的表面功夫。

**完美解答：**

纯向量检索有一个核心缺陷：**语义接近不等于精准匹配**。比如搜"Java 8 新特性"，向量检索可能返回"Java 11 新特性"，因为语义很像，但其实不是用户要的。

**混合检索（Hybrid Search）的解决方案：**

```
用户查询 "Java 8 Lambda 表达式"
          ↓
    ┌─────┴─────┐
    ↓           ↓
向量检索     BM25 关键词检索
(语义匹配)   (精确匹配)
    ↓           ↓
  Top 20      Top 20
    └─────┬─────┘
          ↓
    结果融合（RRF 算法）
          ↓
      Rerank 重排序
          ↓
    Top 5 最终结果
```

**为什么有效：**
| 场景 | 向量检索 | BM25 | 混合检索 |
|------|----------|------|----------|
| "Java 8 Lambda" | 可能找到"Java 11 Lambda" | 精准包含"Java 8"的文档 | 两者都找到 |
| "那本1999年的小说" | 很难匹配 | "1999"精确命中 | 效果好 |
| 同义替换检索 | 好（"电脑"→"计算机"） | 不好 | 互补 |

**Reciprocal Rank Fusion（RRF）融合算法：**
```java
// RRF: 将向量和 BM25 的排名融合
double rrfScore(int rank1, int rank2, int k) {
    return 1.0 / (k + rank1) + 1.0 / (k + rank2);
}
// k 通常取 60
```

**Rerank 进一步提纯：**
```python
# 对融合后的 Top 20 逐个计算与问题的相关度分数
# BGE-Reranker 会在 10ms 内给出精准的相关度打分
# 最终只取 Top 5 作为 LLM 的上下文
```

> 🎯 **关键数据**：在我的项目中，纯向量检索 Top-5 准确率约 72%，混合检索提升到 83%，加上 Rerank 后达到 87%。

### Q6：Agent 系统中，如果某个 Tool 调用失败了，你是怎么处理的？

**面试官意图：** 考察 Agent 工程化的容错设计和异常处理能力。

**完美解答：**

Agent 调用第三方工具（数据库、外部 API 等）必然会遇到失败。我的处理策略分为三个层次：

**第一层：Tool 本身做容错**
```java
@Tool("查询订单信息")
public String queryOrder(@P("订单ID") String orderId) {
    try {
        Order order = orderMapper.selectById(orderId);
        if (order == null) {
            return "未找到订单: " + orderId;
        }
        return String.format("订单 %s 状态: %s, 金额: %.2f", 
            orderId, order.getStatus(), order.getAmount());
    } catch (Exception e) {
        log.error("查询订单异常: ", e);
        // 返回友好的错误信息，Agent 可以据此决定下一步
        return "系统繁忙，查询订单失败，请稍后重试";
    }
}
```

**第二层：Agent Prompt 中注入错误处理指令**
```
当工具调用返回错误时：
1. 重试 1 次（可能是网络抖动）
2. 如果还是失败，换一个工具试试（比如 FAQ 搜索代替订单查询）
3. 所有工具都失败，转人工客服
4. 永远不要编造答案
```

**第三层：人机协同（Human-in-the-Loop）**
```java
@Tool("转人工客服")
public String transferToHuman(@P("问题描述") String issue) {
    // 1. 创建工单
    Long ticketId = ticketService.create(issue);
    
    // 2. 将对话历史同步给人工客服
    ticketService.syncConversation(ticketId, chatHistory);
    
    // 3. 通知坐席
    notificationService.notifyAgent(ticketId);
    
    return String.format("已为您转接人工客服，工单编号: %s，请稍候", ticketId);
}
```

**实际案例：** 物流查询 API 偶尔超时，Agent 第一次调用失败后会自动重试。如果还是失败，Agent 会回复"暂时查不到物流信息，我帮您关注一下，建议您稍后再查"，而不是让用户干等或报错。

> 💡 **面试亮点**：能主动聊到"Tool 异常时 Agent 怎么 fallback"，说明你真的写过 Agent，而不只是看了概念。

## 3. 进阶与系统设计

> 💡 这是拉开差距的环节，考察架构思维

### Q7：如果让你设计一个支持百万 QPS 的秒杀系统，架构怎么设计？

**面试官意图：** 考察系统架构设计能力，从"能跑"到"能扛"的思考过程。

**完美解答：**

百万 QPS 的秒杀系统，核心设计理念是"层层削峰、快速失败、异步处理"。

**架构设计：**

```
用户端
  ↓
CDN（静态资源加速）
  ↓
DNS 轮询 + SLB（负载均衡）
  ↓
Nginx 集群（限流 + 黑白名单）
  ↓
API 网关层（Sentinel 限流 + 热点参数限流）
  ↓
业务校验层（Token + 风控 + 频率限制）
  ↓
Redis 集群（预减库存，Lua 原子操作）
  ↓ 库存充足
消息队列（RabbitMQ/Kafka 削峰填谷，异步落单）
  ↓
消费者集群（异步下单 + MySQL 最终扣减）
```

**关键设计策略：**

**1. 分层限流**
| 层级 | 限流方式 | 目的 |
|------|----------|------|
| 前端 | 按钮置灰 + 随机等待 | 减少无效请求 |
| Nginx | 单 IP QPS 限流 | 拦截脚本刷单 |
| 网关 | Sentinel 热点参数限流 | 保护后端服务 |
| 业务层 | 用户维度频率限制 | 每人每秒只能请求一次 |

**2. 快速失败（Fail Fast）**
```
用户请求 → 商品校验（不合规则秒拒）
            → Token 校验（未获取资格则拒）
            → Redis 预扣（库存不足则拒）
            → 进入 MQ 排队
```
前面三步都在毫秒级完成，99%的请求在几毫秒内就知道结果，不占用系统资源。

**3. 异步化**
```
同步：请求 → 扣库存 → 生成订单 → 返回结果（TPS 低，耗时长）
异步：请求 → 返回排队中 → MQ 缓冲 → 消费者处理（TPS 高，体验好）
```

**4. 兜底方案**
- **Redis 宕机降级**：降级为数据库直接操作（限流到系统能承受的 QPS）
- **MQ 消息积压**：动态扩容消费者，从 10 个扩展到 100 个
- **库存回滚**：订单 30 分钟未支付自动取消，库存回补

### Q8：一个生产级的 RAG 系统，光有检索还不够，还需要哪些工程化组件？

**面试官意图：** 考察 RAG 系统从 Demo 到生产级的完整落地方案。

**完美解答：**

生产级 RAG 系统需要 7 个核心组件：

```text
                    ┌──────────────────────────────────────┐
                    │         RAG 生产级架构                  │
                    │                                        │
  文档处理层 ──────  │  格式解析(Tika) → 智能分块 → Embedding  │
                    │                                        │
  存储层 ──────────  │  Milvus(向量) + ES(BM25) + Redis(缓存) │
                    │                                        │
  检索引擎层 ──────  │  查询重写 → 混合检索 → Rerank → 上下文压缩 │
                    │                                        │
  生成层 ──────────  │  Prompt 模板 → LLM 调用 → 流式输出      │
                    │                                        │
  工程保障层 ──────  │  鉴权/限流/缓存/监控/日志/反馈收集       │
                    └──────────────────────────────────────┘
```

**每个组件的关键考虑：**

**1. 文档处理层**
```java
// 智能分块策略（不只是一个固定 size）
DocumentChunkingStrategy strategy = new SemanticChunkingStrategy(
    500,    // 基准块大小（字符）
    50,     // 重叠窗口
    true    // 按语义边界（段落/句子）分割
);

// 多模态文档支持
// PDF + Word + Markdown + HTML + 图片OCR
```

**2. 检索引擎优化**

| 优化手段 | 解决的问题 | 效果 |
|----------|-----------|------|
| **查询重写** | 短查询（"价格"）找不到匹配 | LLM 扩展为"商品价格是多少？" |
| **HyDE** | 问题与文档表述方式不同 | 先生成假设答案再检索 |
| **Rerank** | 向量检索 Top-K 精度不够 | 从 Top 20 精排到 Top 5 |
| **上下文压缩** | 检索结果太长，Token 浪费 | 保留最相关片段，减少 50% Token |

**3. 反馈闭环**
```sql
-- 收集用户正反馈 / 负反馈，用于优化检索质量
CREATE TABLE retrieval_feedback (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    query TEXT NOT NULL,           -- 用户问题
    retrieved_docs JSON,           -- 检索到的文档
    top1_doc_id VARCHAR(64),       -- 最终使用的文档
    rating TINYINT,               -- 1-5 分
    feedback_type ENUM('thumbs_up', 'thumbs_down'),
    created_at DATETIME
);
```

> 🎯 **面试关键**：讲出"反馈闭环"，说明你有系统化思维——系统不只是"能回答问题"，还能"越用越好"。

### Q9：多租户模式下，不同客户的 RAG 知识库如何做到数据隔离？

**面试官意图：** 考察 SaaS 架构设计能力和 AI 系统的工程化理解。

**完美解答：**

多租户数据隔离有三种方案，各有优劣：

**方案一：Collections 隔离（Milvus 原生支持）**
```java
// 每个租户一个独立的 collection
// 优点：物理隔离，查询互不影响
// 缺点：collection 过多时管理复杂（每个有独立的索引）
String collectionName = "knowledge_" + tenantId;
milvusClient.createCollection(
    CreateCollectionReq.builder()
        .collectionName(collectionName)
        .build()
);
```

**方案二：Metadata 过滤（推荐）**
```java
// 所有租户共用一个 collection，通过 metadata 字段过滤
// 优点：管理简单，资源利用率高
// 缺点：数据量大时过滤条件可能影响性能

// 插入时带租户标记
InsertReq insertReq = InsertReq.builder()
    .collectionName("knowledge_base")
    .data(splitDocs)
    .metadata("tenant_id", tenantId)  // 关键：过滤字段
    .build();

// 查询时按租户过滤
SearchReq searchReq = SearchReq.builder()
    .collectionName("knowledge_base")
    .filter("tenant_id == '" + tenantId + "'")  // 必带租户过滤
    .build();
```

**方案三：独立部署（适合高安全性场景）**
- 每个重要客户部署独立的 RAG 服务实例
- 物理隔离，数据不出客户 VPC
- 成本高，适合金融、医疗等强合规场景

**我的选型建议：**
| 场景 | 方案 | 原因 |
|------|------|------|
| 初创 MVP | Metadata 过滤 | 快速上线，资源复用 |
| 企业版 | Collections 隔离 | 性能和安全性更好 |
| 金融/医疗 | 独立部署 | 合规要求 |

> 💡 实际项目我用的是方案二 + 方案一的混合：小客户用 metadata 过滤共享 collection，大客户给独立 collection，按资源使用量计费。

### Q10：秒杀活动中 Redis 宕机了怎么办？你的降级方案是什么？

**面试官意图：** 考察系统容灾设计能力和高可用的工程思维。

**完美解答：**

Redis 是秒杀的核心组件，宕机时必须有一套完整的降级方案。

**降级策略分三级：**

**一级降级（Redis 部分 key 失效）：**
```java
// 用本地缓存兜底（Guava Cache / Caffeine）
LoadingCache<String, Integer> stockCache = Caffeine.newBuilder()
    .expireAfterWrite(1, TimeUnit.SECONDS)  // 极短过期时间
    .maximumSize(10000)
    .build(key -> {
        // 从 Redis 读取，如果 Redis 也连不上则查数据库
        Integer stock = redisTemplate.opsForValue().get(key);
        if (stock == null) {
            stock = loadStockFromDB(key);
        }
        return stock;
    });
```

**二级降级（Redis 完全不可用）：**
```java
// 直接降级到 MySQL，但需要大幅限制 QPS
// 方案：将秒杀活动改为"抽签模式"
// 用户点击秒杀 → 进入一个等待队列 → 系统分批处理
// 不再要求"毫秒级反馈"，改为"30 秒内出结果"

@PostMapping("/seckill/downgrade")
public Result seckillDowngrade(Long productId, Long userId) {
    // 1. 检查是否在降级模式
    if (!isDegradeMode()) {
        return normalSeckill(productId, userId);
    }
    
    // 2. 降级模式：限速 + 排队
    if (!rateLimiter.tryAcquire()) {
        return Result.fail("系统繁忙，请稍后重试");
    }
    
    synchronized (productId.intern()) {  // 粗粒度但有效的锁
        Product product = productMapper.selectById(productId);
        if (product.getStock() <= 0) {
            return Result.fail("已售罄");
        }
        // 先下单再扣库存
        orderService.createOrder(userId, productId);
        productMapper.reduceStock(productId);
        return Result.success("抢购成功");
    }
}
```

**三级降级（整场秒杀熔断）：**
```java
// Sentinel 熔断：当错误率超过 50%，直接熔断秒杀功能
// 返回活动太火爆，请稍后重试
@SentinelResource(value = "seckill", 
    fallback = "seckillFallback", 
    blockHandler = "seckillBlockHandler")
```

> 🎯 **核心思想**：降级不是"系统挂了"，而是"系统以降低体验为代价继续服务"。讲清楚不同降级级别的触发条件和恢复机制，才是面试官想看到的。

### Q11：RAG 系统中，如果检索到的文档和问题不相关怎么办？

**面试官意图：** 考察 RAG 系统的鲁棒性和生产级兜底方案。

**完美解答：**

即使做了混合检索和 Rerank，仍然可能检索到不相关的内容。我会做以下 4 层保障：

**第一层：相关性阈值过滤**
```java
public class RelevanceFilter {
    static final double MIN_RELEVANCE_SCORE = 0.5;
    
    public List<Document> filterDocuments(List<Document> docs) {
        return docs.stream()
            .filter(d -> d.getRelevanceScore() >= MIN_RELEVANCE_SCORE)
            .collect(Collectors.toList());
    }
}
// 如果过滤后没有文档达到阈值，直接告诉用户"知识库中没有相关信息"
```

**第二层：Prompt 中加入"拒绝回答"指令**
```text
系统指令：
1. 基于以下上下文回答问题。如果上下文中没有足够信息回答，明确说"知识库中没有相关信息"。
2. 不要基于自己的知识编造答案。
3. 如果用户问的问题与知识库主题无关，礼貌地引导到知识库覆盖的话题。
```

**第三层：输出内容审核**
```java
@Tool("输出内容审核")
public String auditResponse(String question, String response, List<Document> contexts) {
    // 检查 LLM 的回答是否在检索到的文档中有依据
    for (String sentence : extractKeyClaims(response)) {
        boolean hasEvidence = contexts.stream()
            .anyMatch(doc -> doc.contains(sentence));
        if (!hasEvidence && isFactualClaim(sentence)) {
            // 标记为"低可信度"，降低展示优先级
        }
    }
    return response;
}
```

**第四层：用户反馈闭环**
```java
// 用户反馈 → 标记该检索结果为负样本
// 定期分析负样本 → 优化分块策略 / Embedding 模型 / Rerank 模型
// 形成"检索质量持续优化"的数据飞轮
```

> 💡 **面试亮点**：提到"相关性阈值"和"拒绝回答"机制，说明你考虑到了 AI 系统的安全性，不只是"答出来就行"。

### Q12：Agent 的多轮对话中，ChatMemory 是怎么管理的？上下文太长怎么办？

**面试官意图：** 考察 Agent 工程化中的 Token 管理和状态管理能力。

**完美解答：**

Agent 中 ChatMemory 的管理核心是"用有限的窗口记住最有价值的信息"。

**1. 滑动窗口策略**
```java
// 保留最近的 N 轮对话，丢弃最早的内容
SlidingWindowChatMemory chatMemory = ChatMemory.builder()
    .maxMessages(20)       // 最多保留 20 条消息
    .build();

// 优点：简单有效
// 缺点：如果前面的关键信息被丢弃，Agent 可能"失忆"
```

**2. Token 预算策略（推荐）**
```java
public class TokenBudgetMemory {
    private static final int MAX_TOKENS = 4000;  // 上下文预算
    private final LinkedList<Message> messages = new LinkedList<>();
    
    public void addMessage(Message msg) {
        messages.add(msg);
        trimToBudget();
    }
    
    private void trimToBudget() {
        int totalTokens = countTokens(messages);
        while (totalTokens > MAX_TOKENS && messages.size() > 2) {
            // 优先丢弃中间的轮次，保留第一轮（系统指令）和最后一轮（当前问题）
            messages.remove(1);  // 删除最早的对话轮次
            totalTokens = countTokens(messages);
        }
    }
    
    // 智能压缩：对过长的消息做摘要
    private void compressMessages() {
        for (int i = 0; i < messages.size(); i++) {
            if (messages.get(i).getTokens() > 1000) {
                // 调用 LLM 对过长消息做摘要压缩
                messages.set(i, compress(messages.get(i)));
            }
        }
    }
}
```

**3. 关键信息持久化**
```java
// 将对话中提取的关键信息存入 Redis，Agent 需要时可以查询
// 比如：用户之前提到"订单 ORD-001"，Agent 可以记住

public class ConversationMemory {
    @Autowired
    private RedisTemplate<String, String> redis;
    
    public void remember(String sessionId, String key, String value) {
        // 每个 session 的关键信息哈希表
        redis.opsForHash().put("memory:" + sessionId, key, value);
        // 设置过期时间（24 小时后自动遗忘）
        redis.expire("memory:" + sessionId, 24, TimeUnit.HOURS);
    }
    
    public String recall(String sessionId, String key) {
        return (String) redis.opsForHash().get("memory:" + sessionId, key);
    }
}
```

> 🎯 **面试关键**：ChatMemory 管理体现了"有限资源下的工程取舍"。面试官想听的不是一个完美的方案，而是一个"在约束下做最优决策"的思考过程。

### Q13：秒杀系统的消息队列积压了怎么办？

**面试官意图：** 考察消息队列压力场景下的应急处理能力。

**完美解答：**

**应急处理四步法：**

**第一步：确认积压情况**
```bash
# RabbitMQ 查看队列积压
rabbitmqctl list_queues name messages consumers

# 或者通过管理 API
curl http://localhost:15672/api/queues | jq '.[] | {name: .name, messages: .messages_ready}
```

**第二步：紧急扩容消费者**
```yaml
# 方案 A：docker-compose 原地扩容（最快速）
docker-compose up -d --scale consumer=10 consumer

# 方案 B：修改代码，提高消费速率
spring.rabbitmq.listener.simple.concurrency=5    # 初始并发
spring.rabbitmq.listener.simple.max-concurrency=20  # 最大并发
spring.rabbitmq.listener.simple.prefetch=100     # 每次预取 100 条
```

**第三步：如果积压超过消费者处理能力 → 临时启用"快速消费模式"**
```java
// 先保证不丢消息，降低处理精度
@Component
@ConditionalOnExpression("${emergency.fast-mode:false}")
public class FastModeConsumer {
    
    @RabbitListener(queues = "seckill.order.queue")
    public void fastConsume(SeckillMessage message) {
        // 快速模式：只做核心操作
        // 1. 直接插入订单表（不做校验）
        // 2. 发送"下单成功"通知
        // 3. 库存扣减后置处理（优惠券等）延后执行
        
        orderMapper.insert(message.toOrder());
        sendNotification(message.getUserId(), "下单成功");
        // 等积压缓解后再后台补齐优惠券等。。
    }
}
```

**第四步：事后改进**
```yaml
# 永久性方案：
# 1. 消费者预配置足够的并发数
# 2. 设置死信队列 + 重试机制
# 3. 监控告警：队列长度超过阈值自动告警
# 4. 提前压测，确定队列的消费能力上限
```
