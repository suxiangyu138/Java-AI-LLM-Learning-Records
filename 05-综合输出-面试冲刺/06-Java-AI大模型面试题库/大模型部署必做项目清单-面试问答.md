### Q1：大模型部署有哪些主流方案？各自适合什么场景？请做一个全面的对比。
**面试官意图：** 考察你对大模型部署生态的整体认知，以及场景判断能力。

**完美解答：**
目前主流的部署方案可以分为四类：

| 方案 | 代表 | 部署复杂度 | 推理速度 | 并发能力 | 适合场景 |
|------|------|-----------|---------|---------|----------|
| **Ollama** | Ollama | 最低（一键安装） | 中等 | 低 | 个人开发、原型验证 |
| **vLLM** | vLLM | 中等 | 最高（5-10x 加速） | 高 | 生产环境、高并发 |
| **TGI** | HuggingFace TGI | 高 | 高 | 高 | 企业级生产部署 |
| **llama.cpp** | llama.cpp | 中 | 中 | 低 | 边缘设备、CPU 推理 |
| **云 API** | OpenAI/通义 | 无 | 最快 | 无限 | 无数据隐私需求 |

**选择决策树**：
```yaml
Q: 数据是否需要私有化？
├─ 否 → 用云 API（最快、最省事）
└─ 是 → Q: 并发量需求？
    ├─ 低 (< 10 QPS) → Ollama（最简单）
    ├─ 中 (10-100 QPS) → vLLM（性价比最高）
    └─ 高 (> 100 QPS) → vLLM + 集群（分布式）
```

**Java 后端的部署推荐**：
- **原型阶段**：Ollama（1 天部署）
- **生产阶段**：vLLM + SpringBoot 网关（4 天部署）
- **大规模生产**：vLLM 集群 + K8s + SpringCloud Gateway（1 周部署）

### Q2：模型量化的原理是什么？INT4、INT8、FP16 有什么区别？量化一定会损失精度吗？
**面试官意图：** 考察对模型量化技术的深度理解，这是部署优化的核心技能。

**完美解答：**
**量化原理**：模型量化是将模型权重从高精度浮点数（FP32）映射到低精度表示（INT8/INT4）的过程，核心目的是减少显存占用和加速推理。

**精度对比**：

| 格式 | 每个权重位数 | 显存节省 (vs FP32) | 精度损失 | 适用场景 |
|------|------------|-------------------|----------|----------|
| FP32 | 32 位 | 基准 | 无 | 训练、科学研究 |
| FP16 | 16 位 | 50% | 几乎无 (<0.1%) | 训练、生产推理 |
| INT8 | 8 位 | 75% | 轻微 (1-2%) | 生产推理（推荐） |
| INT4 | 4 位 | 87.5% | 中等 (3-5%) | 边缘设备、低显存场景 |
| NF4 | 4 位 | 87.5% | 优于 INT4 | QLoRA 微调场景 |

**量化是否会损失精度？**
会，但**在实际应用中通常可以接受**。关键发现：

```
7B 模型：
- FP16: 准确率 85.2%
- INT8: 准确率 84.8% (仅下降 0.4%)
- INT4: 准确率 82.1% (下降 3.1%)

13B INT4: 准确率 86.5% (比 7B FP16 还高！)
```

核心洞察：**用更大量化模型的 INT4 版本，比用小模型的高精度版本效果更好**。这就是为什么 13B INT4 在部署中的性价比超过 7B FP16。

**量化方法分类**：
```yaml
训练后量化 (PTQ):
  - 最常用，不需要重新训练
  - 直接对权重做映射
  - 速度快，效果好

量化感知训练 (QAT):
  - 训练时模拟量化误差
  - 精度更好但需要训练
  - 一般用于 INT4 以下极端量化

GGUF 量化:
  - llama.cpp 的量化格式
  - 支持混合精度（不同层用不同精度）
  - 兼容 CPU 推理
```

### Q3：vLLM 是如何实现 5-10 倍推理加速的？它的核心原理是什么？
**面试官意图：** 考察对高性能推理引擎原理的理解，这是大模型生产部署的关键。

**完美解答：**
vLLM 的加速来自于**三大核心创新**的协同作用：

**1. PagedAttention（分页注意力管理）—— 最大创新**

传统推理引擎的最大痛点是 KV Cache 的内存管理。KV Cache 的大小取决于序列长度，而序列长度是动态变化的。传统方案需要预分配一块连续的大内存，利用率通常只有 20-40%。

PagedAttention 借鉴操作系统的分页机制：
```yaml
传统方案:
  - 预分配最大可能长度的连续内存
  - 问题：内存碎片化严重，利用率低
  - 类比：连续内存分配

PagedAttention:
  - 将 KV Cache 分成固定大小的块（Block），每块约 16 个 token
  - 按需分配，用页表管理物理块和逻辑块的映射
  - 物理块可以不连续，消除碎片
  - 内存利用率从 20-40% 提升到 90%+
  - 类比：虚拟内存分页
```

**2. Continuous Batching（连续批处理）**

传统批处理是**静态的**——等一个 batch 全部处理完才处理下一个。如果 batch 中有请求提前结束（序列生成了 EOS），后续计算就被浪费了。

vLLM 的 Continuous Batching 是**动态的**——在每个 step 都可以动态调整 batch 内容：
```
时间 →
Batch 1: [A, B, C, D]  → A 提前结束
Batch 1: [B, C, D, E]  → 加入新请求 E
Batch 1: [B, D, E, F]  → C 结束，加入 F
...
```
效果：GPU 利用率从 50% 提升到 95%+。

**3. 异步调度**

- 请求解码和内存管理异步执行
- 调度器在 GPU 计算的同时准备下一个 step 的输入
- 消除 CPU/GPU 之间的等待时间

**实际效果数据**（以单张 A100-80G 部署 Llama2-13B 为例）：
```yaml
HuggingFace Transformers:
  - 吞吐量: 20 requests/s
  - 内存利用率: 35%
  - P50 延迟: 500ms

vLLM:
  - 吞吐量: 150 requests/s (7.5x 提升)
  - 内存利用率: 92%
  - P50 延迟: 200ms (2.5x 降低)
```

### Q4：你在用 Docker 部署 Ollama 时，Dockerfile 怎么写的？多阶段构建和分层优化怎么做？
**面试官意图：** 考察容器化部署的具体实现能力，以及镜像优化的工程经验。

**完美解答：**
**Dockerfile 示例（多阶段构建）**：
```dockerfile
# 第一阶段：模型下载
FROM ollama/ollama AS model-downloader
# 下载模型到临时目录
RUN ollama pull qwen2.5:7b-q4_0
RUN ollama pull bge-m3:latest

# 第二阶段：运行服务
FROM ollama/ollama AS runtime
# 从第一阶段复制模型权重
COPY --from=model-downloader /root/.ollama /root/.ollama
# 复制自定义配置
COPY ollama.env /etc/ollama.env
# 暴露 API 端口
EXPOSE 11434
# 健康检查
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost:11434/api/tags || exit 1
# 启动命令
ENTRYPOINT ["ollama", "serve"]
```

**分层优化策略**：
```yaml
1. 模型权重分层:
   Layer 1: 基础镜像 (ollama/ollama) → 很少变化
   Layer 2: 模型权重 → 只在模型升级时变化
   Layer 3: 配置文件 → 经常变化
   
   优化：把经常变化的内容放在后面，充分利用缓存

2. 小模型 + 构建时下载:
   不在 Dockerfile 中下载大模型（会导致镜像过大）
   而是在启动时按需拉取，或使用数据卷挂载

3. 镜像瘦身:
   - 使用 alpine 基础镜像
   - 清理 apt-get 缓存
   - 只保留必要文件
```

**启动脚本**：
```bash
#!/bin/bash
# docker-run-ollama.sh

# 数据卷挂载（模型权重持久化）
docker run -d \
  --name ollama \
  --gpus all \
  -p 11434:11434 \
  -v ./models:/root/.ollama \
  -v ./config:/etc/ollama \
  -e OLLAMA_NUM_PARALLEL=4 \
  -e OLLAMA_KEEP_ALIVE=5m \
  --restart unless-stopped \
  ollama/ollama
```

### Q5：你在实现 OpenAI 兼容 API 网关时，怎么把 Ollama 的 API 封装成和 OpenAI 一致的格式？
**面试官意图：** 考察 API 网关的设计能力和协议兼容性意识。

**完美解答：**
OpenAI API 是事实上的行业标准，封装成兼容格式意味着任何 OpenAI SDK 可以无缝切换到私有部署。

**核心实现**：
```java
@RestController
@RequestMapping("/v1")
public class OpenAIApiGateway {
    
    @Autowired
    private ModelRouter modelRouter;
    
    // OpenAI 兼容的 Chat API
    @PostMapping("/chat/completions")
    public ResponseEntity<?> chatCompletion(@RequestBody OpenAIRequest request) {
        // 1. 转换请求格式
        OllamaRequest ollamaReq = convertRequest(request);
        
        // 2. 根据模型名路由到对应后端
        ModelEndpoint endpoint = modelRouter.route(request.getModel());
        
        // 3. 如果是流式请求
        if (request.isStream()) {
            return ResponseEntity.ok()
                .contentType(MediaType.TEXT_EVENT_STREAM)
                .body(streamResponse(endpoint, ollamaReq));
        }
        
        // 4. 非流式响应
        OllamaResponse ollamaResp = invokeModel(endpoint, ollamaReq);
        OpenAIResponse response = convertResponse(ollamaResp);
        return ResponseEntity.ok(response);
    }
    
    // 流式处理：SSE → OpenAI 格式
    private Flux<String> streamResponse(ModelEndpoint endpoint, OllamaRequest req) {
        return webClient.post()
            .uri(endpoint.getUrl() + "/api/chat")
            .bodyValue(req)
            .retrieve()
            .bodyToFlux(String.class)
            .map(this::toOpenAIStreamFormat);
    }
    
    // 格式转换：Ollama → OpenAI
    private String toOpenAIStreamFormat(String ollamaChunk) {
        // Ollama 返回: {"model":"qwen2.5","message":{"role":"assistant","content":"你好"}}
        // OpenAI 返回: {"id":"...","object":"chat.completion.chunk","choices":[{"delta":{"content":"你好"}}]}
        OllamaStreamChunk chunk = JsonUtils.parse(ollamaChunk, OllamaStreamChunk.class);
        OpenAIStreamChunk openAIChunk = OpenAIStreamChunk.builder()
            .id(UUID.randomUUID().toString())
            .object("chat.completion.chunk")
            .choices(List.of(Choice.builder()
                .delta(new Delta(chunk.getMessage().getContent()))
                .index(0)
                .build()))
            .build();
        return "data: " + JsonUtils.toJson(openAIChunk) + "\n\n";
    }
}
```

**请求格式转换映射**：
```yaml
OpenAI → Ollama:
  model → model (模型名映射)
  messages → messages (消息数组)
  stream → stream (流式标志)
  temperature → options.temperature
  max_tokens → options.num_predict
  top_p → options.top_p
  frequency_penalty → options.repeat_penalty
  stop → options.stop
```

### Q6：集群负载均衡部署中，你是用 Nginx 还是 SpringCloud Gateway？负载均衡策略怎么配置？
**面试官意图：** 考察负载均衡方案选型和配置的实战经验。

**完美解答：**
两者我都用过，选择取决于场景：

**方案对比**：

| 维度 | Nginx | SpringCloud Gateway |
|------|-------|---------------------|
| 层数 | L4/L7 | L7（应用层） |
| 配置复杂度 | 低 | 中 |
| 动态调整 | 需 reload | 支持动态 |
| 集成度 | 独立的网关 | 与 SpringBoot 深度集成 |
| AI 场景 | 流量转发 | 智能路由、鉴权、限流 |

**如果只是做流量分发** → Nginx（简单高效）

```nginx
# nginx.conf - Ollama 集群负载均衡
upstream ollama_cluster {
    # 负载均衡策略：最少连接
    least_conn;
    
    # 多个 Ollama 实例
    server 192.168.1.10:11434 weight=3;
    server 192.168.1.11:11434 weight=2;
    server 192.168.1.12:11434 weight=2;
    
    # 健康检查
    keepalive 32;
}

server {
    listen 80;
    
    location /api/ {
        proxy_pass http://ollama_cluster;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        
        # SSE 流式支持
        proxy_buffering off;
        proxy_cache off;
        
        # 超时配置（大模型推理可能很久）
        proxy_read_timeout 300s;
        proxy_connect_timeout 10s;
    }
    
    location /health {
        # 健康检查端点
        return 200 "OK";
    }
}
```

**如果需要智能路由（按模型、按用户、按场景）** → SpringCloud Gateway

```java
@Bean
public RouteLocator aiRoutes(RouteLocatorBuilder builder) {
    return builder.routes()
        // 按模型路由
        .route("qwen-route", r -> r
            .path("/v1/chat/completions")
            .and().header("X-Model", "qwen2.5")
            .uri("http://ollama-node1:11434"))
        
        .route("llama-route", r -> r
            .path("/v1/chat/completions")
            .and().header("X-Model", "llama3")
            .uri("http://ollama-node2:11434"))
        
        // 负载均衡
        .route("load-balance", r -> r
            .path("/api/**")
            .filters(f -> f
                .circuitBreaker(c -> c.setName("ollamaCB"))
                .requestRateLimiter(c -> c.setRateLimiter(redisRateLimiter())))
            .uri("lb://ollama-cluster"))
        .build();
}
```

**关键配置经验**：
```yaml
1. 超时设置:
   - 大模型推理时间长，read_timeout 建议 300s+
   - connect_timeout 可以短（10s），超时说明节点可能挂了

2. 流式支持:
   - Nginx: 关闭 proxy_buffering
   - Gateway: 不要压缩 response

3. 健康检查:
   - 定期检查 /api/tags 端点
   - 连续 3 次失败自动剔除
   - 恢复后自动加入

4. 权重调整:
   - GPU 强的节点 weight 设大
   - 新上线的节点先设小权重，观察稳定后再调大
```

### Q8：你的 vLLM 服务上线后，高并发场景下频繁报 OOM，怎么优化？
**面试官意图：** 考察生产环境中 vLLM 的调优经验和 OOM 问题排查能力。

**完美解答：**
OOM 是 vLLM 生产环境中最常见的问题。排查和优化路径如下：

**Step 1：确定 OOM 类型**
```yaml
GPU OOM（显存溢出）:
  - 特征: nvidia-smi 显示显存 100%
  - 常见原因: 
    - 模型太大（7B 模型需要 14GB+ 显存）
    - 并发请求太多，KV Cache 占满显存
    - 上下文太长

CPU OOM（系统内存溢出）:
  - 特征: free -h 显示内存接近满载
  - 常见原因:
    - vLLM 的 CPU 内存分配过大
    - 同时加载了太多模型
```

**Step 2：针对性优化措施**

```yaml
显存优化:
  1. 模型量化: 7B FP16(14GB) → 7B INT8(7GB) → 7B INT4(4GB)
  2. 限制 max-model-len: 
     --max-model-len 4096  (从 8192 降为 4096，显存减半)
  3. 限制并发请求数:
     --max-num-seqs 8  (默认 256，限制到 8)
  4. 启用 gpu-memory-utilization:
     --gpu-memory-utilization 0.85  (保留 15% 留给其他进程)

内存优化:
  1. 减少 CPU 交换: --swap-space 0
  2. 启用 CPU offloading 但不要过度

系统层面:
  1. 给容器设内存上限
  2. 使用 K8s 的 resource limits
  3. 监控显存使用，接近 90% 时告警
```

**Step 3：长期方案**
```yaml
1. 增加节点: 横向扩容，分散请求
2. 模型分片: tensor-parallel-size=2（两张卡）
3. 请求排队: 队列大小限制，超出直接返回 429
4. 动态降级: 显存 > 85% 时自动降级为小模型
```

### Q9：你的多模型管理平台上，某个模型突然"挂了"（不响应），你怎么实现自动检测和恢复？
**面试官意图：** 考察运维自动化和高可用设计能力。

**完美解答：**
我会设计一个**健康检查 + 自动恢复**的闭环系统：

**健康检查模块**：
```java
@Component
public class ModelHealthChecker {
    
    @Scheduled(fixedRate = 30000) // 每 30 秒检查一次
    public void checkAllModels() {
        for (ModelInstance instance : modelRegistry.getAllInstances()) {
            HealthStatus status = checkInstance(instance);
            if (status == HealthStatus.DOWN) {
                handleDownInstance(instance);
            } else if (status == HealthStatus.DEGRADED) {
                handleDegradedInstance(instance);
            }
        }
    }
    
    private HealthStatus checkInstance(ModelInstance instance) {
        try {
            // 1. 简单心跳检查
            HttpResponse resp = httpClient
                .timeout(Duration.ofSeconds(5))
                .get(instance.getHealthEndpoint());
            
            if (resp.statusCode() != 200) {
                return HealthStatus.DOWN;
            }
            
            // 2. 功能检查（发送一个简单请求）
            String testResult = llmClient.chat(instance, "ping");
            if (testResult == null || testResult.isEmpty()) {
                return HealthStatus.DEGRADED;
            }
            
            return HealthStatus.UP;
        } catch (Exception e) {
            return HealthStatus.DOWN;
        }
    }
    
    private void handleDownInstance(ModelInstance instance) {
        // 1. 从负载均衡中移除
        loadBalancer.removeInstance(instance);
        
        // 2. 尝试重启
        boolean restarted = restartInstance(instance);
        
        if (restarted) {
            // 3. 验证恢复
            HealthStatus status = checkInstance(instance);
            if (status == HealthStatus.UP) {
                loadBalancer.addInstance(instance);
                notifyAdmin("模型恢复: " + instance.getName());
            }
        } else {
            // 4. 自动切换备用节点
            autoFailover(instance);
            notifyAdmin("模型故障: " + instance.getName() + "，已切换备用");
        }
    }
}
```

**自动恢复流程**：
```yaml
故障检测 → 从集群移除 → 自动重启 → 健康验证 → 重新加入集群
    ↑                                             |
    └────────── 失败 → 通知管理员 ────────────────┘
```

**监控告警**：
```yaml
对接 Prometheus + Grafana:
  指标:
    - model_up: 模型是否在线（0/1）
    - model_response_time: 响应时间
    - model_error_rate: 错误率
    - gpu_memory_used: 显存使用

告警规则:
  - model_up == 0 for 1m → P0 告警
  - error_rate > 10% for 5m → P1 告警
  - response_time > 10s for 5m → P1 告警
```

### Q10：在企业级 RAG 部署方案中，如何保证文档数据的安全性和多用户隔离？
**面试官意图：** 考察数据安全设计和多租户隔离的工程能力。

**完美解答：**
在企业内部知识库场景，数据安全和权限隔离是必须解决的问题。

**多层次隔离方案**：

**第一层：用户权限管理**
```java
// 数据 + 行级权限控制
public class DocumentPermissionManager {

    public List<Document> getAccessibleDocs(String userId) {
        User user = userService.getUser(userId);
        String dept = user.getDepartment();
        String role = user.getRole();

        return documentRepository.findByPermission(dept, role);
    }
    
    // 文档权限模型
    @Entity
    public class Document {
        private Long id;
        private String content;
        private String department; // 所属部门
        private String permissionLevel; // PUBLIC/DEPT_ONLY/CONFIDENTIAL
        private String createdBy;
    }
}
```

**第二层：检索隔离**
```java
public List<Document> search(String userId, String query) {
    User user = userService.getUser(userId);
    
    // 构建带权限过滤的检索条件
    SearchRequest request = SearchRequest.builder()
        .query(query)
        .filter("department IN " + user.getAccessibleDepartments())
        .filter("permission_level <= " + user.getMaxPermissionLevel())

}
```

**第三层：数据加密**

```yaml
  - 密钥由独立 KMS 管理
```

### Q11：使用 K8s 部署大模型时，GPU 调度和自动扩缩容（HPA）是怎么配置的？
**面试官意图：** 考察云原生大模型部署的进阶能力。

**完美解答：**
**GPU 资源调度配置**：
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: vllm
  template:
    metadata:
      labels:
        app: vllm
    spec:
      containers:
      - name: vllm
        image: vllm/vllm-openai:latest
        args: [
          "--model", "/models/qwen2.5-7b",
          "--tensor-parallel-size", "1",
          "--gpu-memory-utilization", "0.9",
          "--max-model-len", "8192",
        ]
        resources:
          limits:
            nvidia.com/gpu: 1  # 申请 1 张 GPU
            memory: "32Gi"
            cpu: "8"
          requests:
            nvidia.com/gpu: 1
            memory: "24Gi"
            cpu: "4"
        volumeMounts:
        - name: model-storage
          mountPath: /models
      volumes:
      - name: model-storage
        persistentVolumeClaim:
          claimName: model-pvc
---
# 确保 GPU 节点有对应的 taint/toleration
apiVersion: v1
kind: Node
metadata:
  labels:
    gpu-type: nvidia-tesla-t4
---
# 调度到有 GPU 的节点
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: nvidia.com/gpu.present
            operator: In
            values:
            - "true"
```

**自动扩缩容（HPA - 基于自定义指标）**：
```yaml
# 基于请求量的自动扩缩容
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: vllm-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: vllm-deployment
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Pods
    pods:
      metric:
        name: request_count_per_second
      target:
        type: AverageValue
        averageValue: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # 缩容冷却 5 分钟
    scaleUp:
      stabilizationWindowSeconds: 60   # 扩容冷却 1 分钟
      policies:
      - type: Pods
        value: 2                       # 每次最多加 2 个
        periodSeconds: 60
```

**关键配置经验**：
```yaml
GPU 调度:
  - nvidia.com/gpu 是整数，不支持小数（不能用半张卡）
  - 每个容器只能申请 1+ 整张 GPU
  - 需要安装 nvidia-device-plugin

自动扩缩容:
  - 大模型服务启动慢（模型加载 2-5 分钟）
  - HPA 需要预留缓冲，避免频繁扩缩
  - 扩缩容冷却时间要比模型加载时间长

存储:
  - 模型权重用 PVC 持久化
  - 多个 Pod 可以共享 ReadOnlyMany 模式
  - 避免每次扩容都重新下载模型
```

### Q12：私有化大模型部署中，如果训练数据或用户查询中包含敏感信息，怎么做到"数据不出域"的同时保证服务质量？
**面试官意图：** 考察私有化部署中数据安全和隐私保护的综合设计能力。

**完美解答：**
"数据不出域"是金融、医疗、政务场景的硬性要求。我的方案是**"物理隔离 + 逻辑隔离 + 可审计"**三层架构：

**物理隔离方案**：
```yaml
部署架构:
  ┌──────────────────────────┐
  │       外部网络            │
  └──────────┬───────────────┘
             │ HTTPS (TLS 1.3)
  ┌──────────▼───────────────┐
  │    DMZ 层 (反向代理/Nginx) │
  └──────────┬───────────────┘
             │ 内网通信
  ┌──────────▼───────────────┐
  │    应用服务层 (SpringBoot) │
  └──────────┬───────────────┘
             │ 
  ┌──────────▼───────────────┐
  │     AI 服务层 (Ollama)    │ ← 完全内网，不连外网
  └──────────────────────────┘

核心原则:
  - 模型服务完全不连外网（物理断网）
  - 所有日志不出域
  - 加密存储 + 定期清理
```

**数据安全策略**：
```yaml
1. 传输安全:
   - 所有请求 HTTPS
   - 内部服务间使用 mTLS 双向认证
   - API 调用必须携带 Token

2. 存储安全:
   - 用户查询日志 AES-256 加密
   - 文档内容加密存储
   - 向量数据不包含原文
   - 密钥由独立 KMS 管理

3. 查询脱敏:
   - 在写入日志前自动脱敏（手机号、身份证、银行卡）
   - 脱敏后的数据只保留 30 天
   - 审计日志只能由管理员查看

4. 模型隔离:
   - 每个租户独立模型实例或独立上下文
   - 一个租户的数据不会出现在另一个租户的回答中
```

**保证服务质量**：
```yaml
离线部署不影响质量的措施:

1. 定期模型更新:
   - 通过离线介质（U盘/光盘）更新模型版本
   - 对比更新前后的 benchmark 分数
   - 每次更新做好版本控制和回滚预案

2. 知识库持续更新:
   - 内部知识库定期导入（文档上传）
   - 自动索引和向量化
   - RAG 确保知识始终最新

3. 质量评估闭环:
   - 定期抽样评估回答质量
   - 收集用户反馈（点赞/点踩）
   - 基于反馈优化 Prompt 和检索策略
   - 全部在内部闭环完成，不需要外网
```
