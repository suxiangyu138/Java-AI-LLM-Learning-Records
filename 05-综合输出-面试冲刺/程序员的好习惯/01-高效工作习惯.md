## 1. 效率的本质：消除摩擦力

> 🎯 **核心认知**：效率提升的本质不是塞进更多工作量，而是**消除工作流程中一切不必要的内部摩擦力**——注意力切换、重复操作、工具不顺、流程冗余，都是摩擦。

```text
效率 = 产出 / (投入 × 摩擦系数)
├── 提高产出的手段有限（人不能无限加速）
├── 降低摩擦系数的手段无限：
│   ├── 自动化（消灭重复操作）
│   ├── 批量（消灭切换成本）
│   ├── 隔离（消灭打断）
│   └── 模板化（消灭重新思考）
└── 结论：程序员的效率之战 = 摩擦力削减战
```

| ❌ 高摩擦工作方式 | ✅ 低摩擦工作方式 |
|-----------------|-----------------|
| 每次 git status 敲全名 | 终端别名 `gs` |
| 反复切窗口找文件 | 全局文件秒开（Ctrl+P） |
| 一会写代码一会回消息 | 消息定点批量回复 |
| 每件事从头想一遍 | 模板 + 清单复用 |

## 2. 自动化铁律

### 2.1 铁律内容

> ⚠️ **自动化铁律**：**重复两次以上就自动化**——别让大脑反复处理机器能做的事。

### 2.2 自动化三件套

```text
自动化层级
├── ① 终端别名：高频命令缩写
│   ├── gs = git status
│   ├── ga = git add
│   ├── gcm = git commit -m
│   └── dev = docker compose up -d
├── ② Shell 函数：多步骤工作流打包
│   ├── deploy() = build + test + push + ssh deploy
│   └── newpage() = 创建模板文件 + 注册路由
└── ③ 工程脚本：项目固定操作统一入口
    └── scripts/ 目录（build.sh / test.sh / lint.sh）
```

```bash
# 终端别名配置示例（~/.bashrc 或 ~/.zshrc）
alias gs='git status'
alias ga='git add'
alias gcm='git commit -m'
alias gp='git push'
alias gl='git log --oneline --graph'

# Shell 函数：多步骤打包
deploy() {
    echo "→ 构建"
    ./scripts/build.sh
    echo "→ 测试"
    ./scripts/test.sh
    echo "→ 部署"
    ssh prod "cd /app && ./deploy.sh"
}
```

> 💡 **自动化的判断标准**：一个操作如果「你记得要怎么做 + 做它超过 30 秒 + 每月超过 2 次」——就值得自动化。

## 3. 双终端与工作区

### 3.1 双终端原则

> 🎯 **双终端**：桌面永远只留两个终端窗口——**工作终端**（固定大本营：开发服务器、测试）与**探索终端**（允许凌乱的实验场）。

```text
双终端分工
├── 工作终端（左屏固定）：
│   ├── 开发服务器 / 测试运行
│   ├── Git 操作
│   └── 生产排查（只读）
├── 探索终端（右屏随意）：
│   ├── 临时实验 / curl 测试
│   ├── 查日志 / 看文档
│   └── 允许乱来（大不了关掉）
└── 价值：把「业务执行」与「临时排查」空间切割，减少微观上下文切换
```

### 3.2 编辑器效率（告别鼠标）

```text
编辑器快捷键四件套（2026 必备）
├── ① 全局文件秒开：Ctrl+P / Cmd+P（不翻目录树）
├── ② 精准定位符号：Ctrl+Shift+O（跳方法/类）
├── ③ 追踪逻辑链路：F12 跳定义 / Alt+F12 速览
├── ④ 多行协同编辑：Ctrl+D 多光标（批量改同名变量）
└── 进阶：Snippets 代码片段——把高频模板封装成快捷键
```

## 4. 批量处理相似工作

### 4.1 核心思路

> 🎯 **批处理原则**：把性质类似的工作收拢到固定时间段成批处理——切换成本是最隐形的效率杀手，一次切换约损失 5-10 分钟注意力。

```text
批处理分组（示例日程）
├── 上午（精力最饱满）：深度闭门创作区
│   └── 啃硬业务：核心逻辑/复杂问题/设计
├── 下午（协作时间）：琐事打包区
│   ├── 会议集中安排
│   ├── 代码评审集中处理
│   └── 周报/文档/回复消息
└── 原则：创作与协作分离，专注与琐事分离
```

### 4.2 三类批处理实践

| 类型 | 做法 | 收益 |
|------|------|------|
| **消息批处理** | 关高频弹窗，定点检查（如每小时 10 分钟） | 保护深度工作 |
| **评审批处理** | 小型 PR 立即处理（两分钟原则）；大型评审独立安排 | 不打断节奏 |
| **沟通批处理** | 提问/咨询集中在固定时段（如下午 4-5 点） | 双方效率 |

### 4.3 两分钟原则

> 💡 **两分钟原则**：预计两分钟内能处理完的小事（小型 PR 评审、简单回复、小修小补）**立即处理**——记下来的成本可能比做它更高；超过两分钟的事，**单独安排**而不是顺手做（顺手做会打断当前深度工作）。

## 5. 保护深度工作

### 5.1 为什么深度工作稀缺

> 📊 **关键数据**：开发者从深度编码状态被打断后，平均需要 **15-20 分钟**才能重新进入状态——一次打断的实际代价是 20+ 分钟。**上下文切换是效率的最大杀手。**

### 5.2 深度工作保护方案

```text
深度工作保护四件套
├── ① 日历屏蔽：主动在日历上屏蔽专注时段（如 9:00-11:30）
├── ② 通知管理：专注时段关闭 IM 弹窗/邮件提醒
├── ③ 状态信号：IM 状态设为「专注中，紧急电话」（团队约定）
├── ④ 批量回应：专注结束后统一回复（并说明「刚在专注」）
└── 团队协作约定：紧急才打断；非紧急等专注结束
```

### 5.3 深度工作的最佳时段

```text
精力曲线与任务匹配
├── 上午 9-11 点：精力巅峰 → 最难的开发任务
├── 下午 2-4 点：次佳 → 设计/重构/评审
├── 下午 4-6 点：下降 → 琐事/回复/文档
└── 晚上：不安排重脑力（加班不宜超 22 点，脑子糊时写全是 bug）
```

## 6. 15 分钟法则

### 6.1 法则内容

> 🎯 **15 分钟法则**：面对不想干的脏活，先承诺做 15 分钟；钻技术兔子洞前，先定 15 分钟倒计时。

```text
15 分钟法则的两个应用
├── 应用一：对抗拖延
│   ├── 不想干的事 → 承诺 15 分钟
│   ├── 15 分钟后：通常已进入状态（继续干）
│   └── 实在不行：停下来换别的（至少消灭了拖延的焦虑）
├── 应用二：对抗兔子洞
│   ├── 查一个"有趣但不关键"的技术问题 → 定 15 分钟
│   ├── 15 分钟没解决 → 记录下来，标记为后续任务
│   └── 回到主线工作（防止一上午消失）
```

> 💡 **法则的本质**：给「开始」一个低门槛，给「沉溺」一个硬截止——拖延与钻洞是同一个问题的两面：缺乏边界。

## 7. 调试与排查习惯

### 7.1 调试三原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | **二分法定位** | 一次改一个变量，用日志/断点缩小范围 |
| 2 | **先复现再修** | 记录复现步骤——修不了的 bug 先问「能不能稳定复现」 |
| 3 | **读日志读全** | 看异常要看完整堆栈 + 上下文日志，不只看最后一行 |

### 7.2 排查流程化

```text
bug 排查标准流程
├── ① 复现：记录复现步骤（输入/环境/操作序列）
├── ② 定位：二分法 + 日志 + 断点（一次只改一个变量）
├── ③ 修复：最小改动 + 补测试（防止回归）
├── ④ 复盘：为什么没被测试发现？→ 补测试盲区
└── ⑤ 沉淀：复现步骤写进测试用例（bug 变资产）
```

> 🎯 **bug 是资产**：每一个修好的 bug 都该变成一条测试用例、一条知识库记录——「每次事故都是一次免费的评估集扩充」（AI 时代的说法）。

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 效率的本质是消除摩擦力：自动化铁律（重复两次就自动化）+ 批量处理（消灭切换成本）
> 2. 双终端 + 编辑器快捷键四件套：空间切割专注与实验，操作路径最短化
> 3. 深度工作最稀缺：被打断需 15-20 分钟重回状态——日历屏蔽 + 通知管理 + 团队约定
> 4. 15 分钟法则（对抗拖延与兔子洞）+ 调试三原则（复现/二分/全日志）+ bug 变资产
