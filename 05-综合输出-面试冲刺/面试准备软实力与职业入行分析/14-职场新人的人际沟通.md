## 1. 加了mentor/leader微信第一句说什么

### 实习入职前加微信

```text
场景：HR把你的微信推给了mentor，或者你自己加上了

✅ 正确示范：
"XX哥/姐你好，我是新来的实习生XX，下周一开始入职，
提前加一下你，请多关照！[抱拳]"

要点：
  - 说清楚你是谁（mentor可能同时带好几个新人）
  - 说明入职时间
  - 简短客气，不用发小作文
```

### 实习结束后保持联系

```text
场景：实习结束，想和mentor保持长期联系

✅ 正确示范：
"XX哥/姐，我的实习今天结束了。
 这段时间真的从你身上学到了很多，
 特别是XX方面（提到一个具体的事）。
 希望以后还有机会合作。保持联系！[抱拳]"

要点：
  - 具体提到对方对你的帮助（说明你不是群发的）
  - 表达感激但要真诚，不要肉麻
  - 不要立刻求帮忙（显得功利）
```

## 2. 怎么在群里说话不尴尬

### 实习生群聊生存指南

| 场景 | ❌ 不要 | ✅ 要做 |
|------|--------|--------|
| 刚被拉进群 | 沉默什么都不说 | "大家好，我是新来的实习生XX，以后请多关照" |
| 被@了 | 当作没看见 / 只回一个"收到" | 及时回应，说清楚你收到并理解 |
| 有问题要问 | 群里发一个很模糊的问题 | 先私聊mentor或找到合适的人 |
| 别人在讨论 | 强行插话发表不成熟的看法 | 先听、先学、有把握了再说 |
| 同事分享成果/喜讯 | 沉默 | 点个赞或发个"厉害/恭喜" |
| 有人帮你解决了问题 | 不吭声 | 在群里说一声"解决了，谢谢XX" |

### 群聊中的"存在感"管理

```text
实习生不需要在群里"刷存在感"，但需要"有存在感"：

刷存在感（❌）：
  - 每个话题都要说两句
  - 发一些没有信息量的"哈哈""+1"
  - 转发和工作无关的内容

有存在感（✅）：
  - 提问题时表达清晰
  - 被cue时及时响应
  - 完成一个任务后在群里同步一下结果
  - 遇到自己解决不了的问题，把求助信息写清楚
```

## 3. 被批评了怎么回应

### 实习生一定会被批评——这不可怕

```text
可能被批评的场景：
  - 代码CR被mentor打回来一大堆comment
  - 需求理解错了，做出来的东西完全不对
  - 不小心把测试环境的数据库删了（真的发生过）
  - 说了不合适的话 / 做了不合时宜的事
```

### 被批评时的正确回应流程

```text
第1步：先听，不要立刻辩解
  "你说得对，这个确实是我的问题。"
  → 不要"但是..."、"因为..."——不管原因是什么，先承认结果

第2步：说清楚你理解的问题在哪里
  "我理解了，问题是我没有考虑XX的情况就写了这段代码。"
  → 表明你不是在敷衍，真的理解了错误

第3步：说清楚你接下来怎么做
  "我马上改，大概XX时间能改完。以后我会在提交之前先自己跑一遍所有case。"
  → 给出解决方案 + 避免再犯的方法

第4步：做完了通知对方
  "XX哥，那个问题我已经修复了，你看一下。"
  → 形成闭环，证明你说到做到
```

### 常见批评场景的应对

| 场景 | ❌ 错误回应 | ✅ 正确回应 |
|------|-----------|-----------|
| CR被提了很多意见 | "我觉得这样写也没问题啊" | "好的，我改一下。有几个地方我想确认一下再改" |
| 需求做错了 | "需求文档没写清楚啊" | "是我没确认清楚，我重新做，以后做完设计先给你看一眼" |
| 犯了低级错误 | "我忘了"（太敷衍） | "这个确实不该犯，我下次注意。要不要我加一个检查清单？" |
| 被说"效率太低" | "因为XX原因才慢的" | "确实花了比预期多的时间，主要卡在XX，我在想怎么提高..." |

## 4. 如何委婉拒绝不合理的要求

实习生在职场中有时会遇到一些不太合理的请求，学会委婉拒绝是必要的自我保护。

### 拒绝的通用公式

```
拒绝 = 表示理解 + 说明客观限制 + 提供替代方案（如果有）

不要只说"不行"，也不要编假理由。
```

### 场景举例

**场景一：同事让你帮忙做和他的项目无关的事**

```text
❌ "这不是我的活，我不做。"（太生硬）

✅ "我理解你这个比较急，
   但我手上有mentor安排的XX需求，deadline是周五。
   如果这件事优先级更高的话，要不要和mentor沟通一下排期？
   或者等我周五忙完了可以帮你看一下。"
```

**场景二：快下班时被要求做一件不紧急的事**

```text
❌ "我要下班了，明天再说吧。"（可能会有人说你"

✅ "这个今天就要吗？如果不太急的话我明天一早就弄，
   今晚我先想一下大概方案，明天效率会更高。"
```

**场景三：被要求做超出你能力范围的事**

```text
❌ 硬着头皮答应然后做不出来（更糟糕）

✅ "这个方向我之前没接触过，如果让我独立做的话可能需要比较长的时间。
   能不能这样——XX（有经验的人）先带我搭个框架，然后我再完善细节？"
```

### 什么情况不该拒绝

| 该接的 | 为什么 |
|--------|--------|
| 领导/mentor直接安排的任务 | 这是你的本职工作 |
| 虽然是杂活但能让你快速了解业务流程 | 新人对业务的了解往往从杂活开始 |
| 同事确实忙不过来，你能帮上忙 | 建立互帮互助的关系，以后你需要时人家也会帮你 |
| 和你的技术发展方向相关 | 即使是额外任务，能学到东西就值得做 |

## 5. 周报怎么写让leader看到你的成长

### 周报不是形式，是你的"存在证明"

Leader可能不知道你每天在做什么——这就是周报的价值。

### 实习生周报模板

```markdown
本周工作
  1. [需求/任务名称] - 进度：已完成/80%/进行中
     - 做了什么：具体描述
     - 遇到什么问题：XX（如果解决了，写怎么解决的）
  2. ...

下周计划
  1. [下一步要做什么]
  2. ...

学习与思考（实习生特有板块——展示你的成长）
  1. 这周学到了什么新东西？
  2. 有什么踩坑经验分享？
  3. 对团队有什么建议？（如果有的话，语气温和地说）

需要帮助
  - 有什么需要mentor/leader帮忙协调的事情？
```

### 好周报 vs 坏周报

```text
❌ 坏周报：
"本周继续开发XX功能，修了几个Bug，看了一些代码。"
→ 信息量为零，leader看完不知道你做了什么

✅ 好周报：
"本周工作：
 1. 完成订单查询接口开发（已完成+已提测）
    - 使用Redis缓存热点查询，QPS从500提升到3000
    - 遇到一个问题：缓存与数据库一致性，和mentor讨论后采用先更新DB再删缓存方案
 2. 修复了3个线上Bug：#1234 #1235 #1236
    - #1234的根因是并发场景下没有加锁，学习到了乐观锁vs悲观锁的选型

下周计划：
 1. 开发退款流程模块
 2. 给订单模块补充单元测试（覆盖率目前60%→目标80%）

学习与思考：
 - 这周深入学习了一下Redis的缓存策略，写了个笔记，分享给大家：[链接]
 - 发现我们项目里缓存key的命名不太统一，建议可以定一个命名规范"
```

> 💡 **周报的数据思维：** 能写数字的地方一定写数字。完成了几个需求、修了几个Bug、性能提升了多少、覆盖率达到多少——数字让你的工作"可视化"。

## 6. 技术讨论中怎么表达不同意见

### 技术分歧是常态

技术方案的讨论中，你和同事可能有不同意见。这很正常——不正常的是不会表达。

### 表达不同意见的框架

```text
认可对方 → 提出你的观点（用数据或逻辑支撑）→ 寻求共识

不要：直接说"你这个方案不行"
要：   "你的方案在XX方面考虑得很好。不过我在想YY场景下会不会有ZZ问题？
      我的想法是...你觉得呢？"
```

### 场景举例

```text
场景：Code Review时你觉得mentor的建议不是最好的

❌ "这样改性能会更差吧？"（挑战性语气）

✅ "这个建议我理解是为了解决XX问题。
    不过我看了一下，如果这样改的话，每次请求会多一次数据库查询。
    有没有可能用缓存来解决，同时不会影响性能？
    或者你觉得这个场景下性能的影响可以忽略？"
    
    → 你提出了技术事实（多了查询）+ 给出了替代方案（缓存）
    + 最后把判断权交回给对方（尊重）
```

### 技术讨论中不要做的事

| ❌ 不要 | 为什么 |
|--------|--------|
| 在公开群里说别人的方案不好 | 私下说或者小范围讨论 |
| 用"你这明显不行"这种话 | 否定对方，引发防御心理 |
| 为了赢而争论 | 技术讨论的目标是更好的方案，不是你赢 |
| 拿大厂/大V的话当绝对真理 | "XXX公司就是这么做的"不是充分的论据 |
| 争论到对方认输为止 | 如果没达成共识，可以说"要不我们都再想想？" |

## 7. 与产品/测试/运营等非技术角色的沟通

### 核心原则：说人话

和产品经理、测试、运营沟通时，最大的问题是——你说的术语他们听不懂，他们说的业务你听不懂。

| 原则 | 说明 |
|------|------|
| **翻译** | 把技术语言翻译成业务语言。不是"Redis挂了"，是"用户数据加载会慢几秒" |
| **共情** | 理解对方的诉求。产品要的是"用户体验好"，测试要的是"质量有保障" |
| **说影响不说原因** | 不是"数据库死锁了"，是"刚才下单会失败，大概影响10分钟" |

### 和产品经理沟通

```text
场景：产品经理提了一个技术上很难实现的需求

❌ "这个做不了，技术上不可能。"（阻断式沟通）

✅ "这个需求我理解了，用户确实需要这个功能。
    不过如果完全按照这个方案来做，开发量会很大（大概2周），
    我有一个替代方案：把XX简化一下，能达到80%的效果，开发只用3天。
    你觉得这个折中方案可以吗？"
    
    → 你提出了事实（开发量），给出了替代方案，把决定权交给了产品。
```

### 和测试沟通

```text
场景：测试提了一个你觉得不是Bug的Bug

❌ "这不是Bug，这是特性/设计如此。"（推卸式）

✅ "这个行为确实是代码逻辑导致的——我们在设计的时候是这样考虑的...（解释为什么）。
    不过从用户角度看，确实不太合理。
    要不这样，这次先记录为一个优化项，下个迭代我们重新设计一下这个交互？"
```

### 和运营/客服沟通

```text
场景：运营反馈说"系统又挂了"

❌ "不可能，我看监控都是正常的。"（否定了对方的反馈）

✅ "能说一下具体是什么操作、什么时间出现的吗？
    我看一下监控数据，如果是系统问题我马上修，
    可能是某个场景下有Bug，我排查一下。"
```

## 8. 书面沟通：消息与邮件的规范

### 企业微信/飞书/钉钉消息规范

```text
1. 不要发"在吗？"然后等回复
   → 直接说事："XX哥，有一个问题想请教你：[具体问题]"

2. 一个问题一条消息（不要分很多段发）
   → 对方打开手机一口气看完，比你一句一句发体验好得多

3. 重要的事情用文字，不要用语音
   → 语音没法搜索、没法复制、不方便回看

4. 收到长消息及时回复
   → 如果不能立刻处理，回一个"收到，我看完回复你"
   → 让对方知道你看到了，不是已读不回

5. 代码/报错信息用代码块
   → ``` 代码块包裹，不要直接粘贴
```

### 工作邮件规范

实习生发邮件的机会不多，但一旦要发，注意这些：

```text
邮件标题：清晰概括内容
  ✅ "【实习生-XX】订单模块Redis缓存方案设计 - 请审阅"
  ❌ "问个问题"

邮件正文结构：
  1. 收件人称呼："XX哥/XX姐/XX总，你好"
  2. 背景（一句话）：为什么写这封邮件
  3. 核心内容：清晰分段，重点加粗
  4. 行动项（如果有）：你需要对方做什么、什么时间前
  5. 礼貌结束语

抄送规则：
  - 主管/mentor：和你工作直接相关的抄送
  - 大Leader：除非特别重要或mentor让你抄，不要随便抄送大Leader
  - 跨部门：只抄送真正需要知情的人
```

---

> 🎯 **最后的话：** 沟通能力不是天生的，是练出来的。你不需要变成社交达人，只需要做到——说话有重点、回应不拖延、批评不辩解、不同意见好好说。做到这四点，你在任何一个团队里都不会因为沟通问题吃亏。
