## 1. 09:00-09:30 晨间准备

### 1.1 开机三件套

每天早上坐到工位后，有经验的开发会在3分钟内完成"开机三件套"的启动：

```bash
# 三件套依次启动
1. IntelliJ IDEA（已经打开昨天的项目，索引加载中）
2. 数据库客户端（Navicat / DataGrip / DBeaver）
3. 终端（iTerm2 / Windows Terminal / Tabby）
```

> 💡 **效率技巧**：IntelliJ IDEA 可以在 Preferences → Appearance & Behavior → System Settings 中开启"Reopen last project on startup"。这样每天一打开IDEA，自动加载昨天的项目，节省至少2分钟。

除了三件套，资深开发还会额外启动：

```text
辅助工具清单（按优先级排列）：
├── 必开：企业微信/钉钉/飞书 (消息保持在线)
├── 必开：浏览器 (常用标签页：Grafana、Kibana、Jenkins、Wiki)
├── 推荐：ApiFox / Postman (接口调试)
├── 推荐：Navicat / DataGrip (数据库可视化)
├── 进阶：Kibana (看日志)、Prometheus + Grafana (看监控)
├── 进阶：Termius / XShell (SSH连接服务器)
└── 进阶：VS Code (看文档、改配置文件等轻量操作)
```

### 1.2 消息检查清单

打开消息工具后，不要焦虑地逐条回复。按**优先级**快速扫描：

| 优先级 | 消息类型 | 处理方式 |
|:------:|---------|---------|
| P0 | 线上报警 @所有人 | 立刻看，确认是否真挂 |
| P1 | 直接@你的消息 | 看内容，紧急的立即回，不紧急的先标记 |
| P2 | 项目群聊消息 | 快速划一遍，和自己有关的回一下 |
| P3 | 邮件 | 扫标题，非紧急的集中处理 |
| P4 | GitHub/GitLab通知 | Review邀请、CI失败提醒需要关注 |

**实战场景：消息检查的两种典型风格**

```text
风格A——"一次性处理型"（推荐）
07:50 到工位 -> 开机 -> 打水 -> 坐下
07:55 打开消息工具，逐条处理
       ① 线上报警？没有，安全
       ② 产品@我确认一个字段长度，回"ok，一会儿看"
       ③ 测试标记了一个Bug，瞄一眼，确认是自己模块的
       ④ 邮件：全是周报汇总，不紧急
08:05 处理完毕，开始梳理想办

风格B——"被动响应型"（不推荐）
09:00 到工位，打开消息工具
09:05 看到群里@我，回复
09:10 又弹出消息，回复
09:15 又来一条，回复……
09:30 站会了，啥也没准备，被问到进度支支吾吾
```

### 1.3 待办梳理法：紧急-重要矩阵

打开自己的待办工具（Jira / TAPD / Trello / 甚至一个 `.md` 文件），用**艾森豪威尔矩阵**排序：

```text
                    紧急                  不紧急
              ┌──────────────┬──────────────┐
    重要      │  马上做      │  计划做      │
              │ · 线上Bug    │ · 技术优化    │
              │ · 今天截止   │ · 重构方案    │
              │ · 阻塞别人   │ · 学习新技    │
              ├──────────────┼──────────────┤
    不重要    │  授权/快做   │  别做         │
              │ · 抄送邮件   │ · 无意义报    │
              │ · 琐碎问    │ · 不紧急    │
              │ · 非核心修   │ · 刷手机     │
              └──────────────┴──────────────┘
```

> 💡 **推荐做法**：每天早上花5分钟在笔记里写下当天的Top 3任务。不是把所有事都列出来，而是筛选出**今天必须完成的3件事**。做完这三件，今天就是成功的。

**示例：早上列出的待办清单**

```markdown
## 2026-07-28 待办 (Top 3)

### P0 - 今天必须完成
1. [ ] 开发"用户提现"接口 - 估时4h，下午前端要联调
2. [ ] 修复生产环境"订单超时未取消"Bug - 估时1h，昨天已有用户反馈

### P1 - 最好今天做
3. [ ] 退款模块的技术方案评审文档 - 估时1.5h，明天过会

### P2 - 有空再做
4. [ ] 升级Guava版本（安全漏洞扫描提醒）
5. [ ] 阅读新来的实习生的代码，给反馈
```

### 1.4 值班日特殊动作：先看监控大盘

如果今天是你的 **On-Call值班日**，清晨的第一件事不是看消息，而是**登录监控大盘做健康检查**：

```bash
# 值班检查清单
□ Prometheus + Grafana 大盘检查
   □ CPU使用率（正常 < 80%，异常 > 90%）
   □ 内存使用率（看GC频率，Full GC是否有异常）
   □ 接口QPS（和昨日同时段对比，大幅下跌=可能挂了）
   □ 接口响应时间P99（超过500ms需要关注）
   □ 错误率（4xx/5xx比例，超过1%需要排查）

□ Kibana日志检查
   □ ERROR级别日志有没有突然增多
   □ 业务异常日志（如支付失败、超时等）

□ 定时任务检查（XXL-Job / Elastic-Job）
   □ 昨晚的批量任务是否运行正常
   □ 有没有重试队列积压

□ 消息队列积压检查（RocketMQ / RabbitMQ / Kafka）
   □ Consumer Lag 是否在合理范围
   □ 超过阈值需要排查消费端问题
```

> ⚠️ **值班守则**：如果你是大厂值班开发，通常还有SLA要求——比如"P0告警5分钟内响应，15分钟内定位"。所以值班日早上7:50就到工位看大盘是常态，不是夸张。

```text
【值班场景模拟】

09:00 打开Grafana大盘，发现订单服务的错误率从0.1%飙到了5%
09:01 查看Kibana日志，发现大量 Connection refused 错误
09:03 确认是新发布的版本调用了已下线的Redis集群地址
09:05 联系值班负责人，决定回滚
09:10 执行回滚操作（jenkins点击"回滚到上一版本"）
09:15 确认大盘恢复，在值班群同步

🎯 核心要点：值班日的早晨，"先看大盘"比"看消息"重要100倍。
   用户已经在抱怨了，企业的监控系统往往比用户更早知道问题。
```

## 2. 09:30-09:50 每日站会

### 2.1 站会三段式汇报模板

每日站会（Daily Stand-up）是Scrum的核心仪式，但也可能是**最容易被新人坑进去的陷阱**。标准格式：**20分钟，站着开，每人说三件事**：

```text
✅ 标准站会回答模板

"我昨天做了：
  - 完成了订单列表接口开发（TAPD-1234）
  - 和前端同学联调了登录模块

 我今天计划做：
  - 开发退款接口（TAPD-1235），预计下午提测
  - 如果有富余时间，修一下测试提的Bug-7890

 我的阻塞是：
  - 退款接口依赖第三方支付网关的文档还没给到，已经催了，如果今天上午还拿不到需要产品帮忙推动"
```

> 💡 **站会公式**：昨天做了什么 + 今天做什么 + 阻塞项 = 完美站会。每个部分控制在30秒内，总共不超过90秒。

### 2.2 好的站会 vs 差的站会

| 维度 | 好的站会 ✅ | 差的站会 ❌ |
|------|-----------|-----------|
| **时长控制** | 每人1分钟，全场15分钟搞定 | 一个人讲5分钟，全场拖到40分钟 |
| **内容颗粒度** | "完成了订单列表分页查询" | "我昨天一直在看代码……"（说不出具体产出） |
| **阻塞表达** | 明确说出需要什么帮助 | "额……目前还好"（实际上卡了一整天） |
| **听众意识** | 捡和团队相关的说 | 把站会当述职，从头到尾讲细节 |
| **同步态度** | 主动同步进度 | 低头看手机，轮到自己的时候"和昨天一样" |
| **后续行动** | 站会后自动找相关人员私聊 | 站会上聊细节，其他人干等 |

**反面案例（不推荐的站会回答）：**

```text
❌ 错误示范1：过度细节型

"我昨天在写那个订单接口，就是那个查询订单的，用的是MyBatis-Plus，
然后我写了一个分页，但是分页的时候发现total不对，
我查了一下是count查询的问题，然后我改成了……
（2分钟后还在讲分页查询的SQL怎么写）"

💡 分析：技术细节应该站会后私聊，站会上只说"完成了订单接口开发，遇到分页total不准的问题已解决"。

❌ 错误示范2：报流水账型

"我昨天开了两个会，然后下午看了一些文档，
然后改了一些Bug……"

💡 分析：说了等于没说。给出具体的任务编号或功能名称。

❌ 错误示范3：事不关己型

"我昨天没什么，今天继续做XX模块"

💡 分析：团队协作中，即使你的任务和当前迭代无关，也要说清楚规划和进度。要培养"信息透明"的工程文化意识。
```

### 2.3 站会中如何优雅地说"我被卡住了"

这是很多新人最怕的场景——站会上所有人看着你，你要说"我搞不定"。但恰恰相反，**敢于暴露问题是优秀工程师的标志**。关键是表达方式：

```text
✅ 得体的表达方式

"退款接口的幂等方案我遇到了一个问题——
  考虑用Redis分布式锁实现，但和现有事务可能冲突，
  我现在有A、B两个方案：
    A方案：在事务外层加锁（并发控制好，但长事务风险）
    B方案：乐观锁+重试（性能好，但需要在代码里做更多补偿）
  我想站会后找您（看向技术Leader）帮我评估一下选哪个方案。"

❌ 不合适的表达方式

"退款接口做不出来，卡住了。"

💡 关键差异：优秀的表达是"我做了什么分析 + 我有哪些方案 + 我需要什么帮助"。
   而不是单纯地说"我卡住了"——这叫甩锅，不叫求助。

💡 更进一步：站会结束后，主动找相关同事去聊阻塞项。
   不要在站会上展开讨论——站会的目的是"同步"，不是"解决问题"。
```

### 2.4 分布式团队站会

如果团队在多个城市或远程办公，站会通过飞书、Teams、Zoom等工具进行：

```text
分布式站会的注意事项

1. 确保网络稳定（开摄像头，关掉不必要的视频/直播）
2. 用"虚拟举手"代替抢话（Teams有raise hand功能）
3. 分享屏幕比口述更高效（如果有代码/设计要展示）
4. 说慢一点，给网络延迟留缓冲
5. 用文档同步代替口头汇报：
   提前在共享文档写好"昨日/今日/阻塞"，站会直接过

🎯 工具配置推荐：
   - 飞书：视频会议 + 飞书文档共享
   - Teams：频道 + Planner任务同步
   - Zoom：Breakout Rooms处理分组讨论
   - 同步文档：Confluence / 飞书文档 / Google Docs
```

## 3. 09:50-10:30 需求拆解与任务评估

### 3.1 接到需求后的标准流程

产品经理（PM）在群里发了一个需求文档（PRD），或者Jira/TAPD上给你分配了一个任务。这时候不要急着开干，按照以下5步走：

```text
Step 1: 读PRD
  → 理解业务场景和用户故事
  → 标记不懂的地方
  
Step 2: 画流程图
  → 泳道图（用户 → 前端 → 后端 → 第三方系统）
  → 时序图（请求的完整生命周期）
  
Step 3: 拆任务
  → 把需求拆成可独立开发的子任务
  → 每个子任务估时不超过1天

Step 4: 估工时
  → 三点估算法（乐观/可能/悲观）
  → 给评估范围而不是精确数字

Step 5: 对齐
  → 和PM确认自己理解是否正确
  → 和前端/测试确认接口约定
```

### 3.2 需求拆解完整案例：「用户提现功能」

**原始需求（一句话）**：

```
用户可以将账户余额提现到绑定的银行卡，单日提现限额5000元。
```

**拆解后的完整任务树**：

```text
用户提现功能
│
├── 后端开发任务（6个子任务，共4人日）
│   ├── [1h] 建表脚本 + 数据模型（withdraw_record 表）
│   ├── [4h] 提现接口开发
│   │   ├── 参数校验（金额>0、绑定银行卡、每日限额校验）
│   │   ├── 业务逻辑（冻结金额 -> 落单 -> 异步处理）
│   │   └── 幂等处理（防止重复提交）
│   ├── [2h] 提现记录查询接口（前后端联调用）
│   ├── [3h] 对接三方支付（调用银行接口 / 微信支付商户）
│   ├── [2h] 定时任务（处理"提现中"状态的订单，查银行结果）
│   └── [2h] 回调通知（提现成功/失败通知用户，短信/站内信）
│
├── 前端开发任务（3个子任务）
│   ├── 提现页面开发
│   ├── 提现记录列表页面
│   └── 提现结果展示（成功/失败/处理中）
│
└── 测试任务（4个子任务）
    ├── 正常提现流程测试
    ├── 边界测试（超限额、余额不足、银行卡已解绑）
    ├── 异常测试（三方支付超时、重复提交）
    └── 并发测试（同一时间发起多笔提现）
```

**详细的任务拆解**（以"提现接口"为例）：

```markdown
### 任务：提现接口开发 (4h)

#### 技术方案

1. API设计
   - POST /api/v1/withdrawal/apply
   - 请求体：{ amount: BigDecimal, bankCardId: Long }
   - 响应体：{ code: 0, data: { withdrawId: Long, status: "PROCESSING" } }

2. 流程设计

   用户提交提现
     │
     ▼
   参数校验 ──❌--> 返回错误信息
     │
     ✔
   每日限额检查（Redis计数器）──❌--> "已超今日限额"
     │
     ✔
   余额检查 ──❌--> "余额不足"
     │
     ✔
   幂等校验（Redis+数据库唯一索引）──❌--> "请勿重复提交"
     │
     ✔
   冻结余额（update user_balance with 乐观锁）
     │
     ✔
   插入提现记录（status = PROCESSING）
     │
     ✔
   发送MQ消息（异步处理 → 调用三方支付）
     │
     ✔
   返回结果

3. 边界条件
   - 最小提现金额：1元（需配置）
   - 单日限额：5000元（需可配置）
   - 提现后余额不能低于0
   - 业务时间支持防重放

4. 异常场景
   - 三方支付超时 → 定时任务兜底查状态
   - 银行返回失败 → 自动回滚冻结金额 + 通知用户
   - 并发提现 → 数据库行锁 + 乐观锁双重保障
```

### 3.3 工时估算方法：三点估算法

新人的常见痛点是"估不准"——要么估少了拼命加班，要么估多了被PM质疑。三点估算法可以解决这个问题：

```text
三点估算法公式：

    E = (O + 4M + P) / 6

其中：
  O = Optimistic (最乐观) —— 一切顺利，没Bug，没阻塞
  M = Most Likely (最可能) —— 正常情况，有测试和联调时间
  P = Pessimistic (最悲观) —— 遇到坑，需要改方案，第三方不配合

示例：提现接口开发

  乐观估计(O)：3小时（代码已经写过类似的，直接改）
  最可能(M)： 5小时（需要写单元测试，和前端联调）
  悲观估计(P)：10小时（第三方支付文档不全，踩坑重来）

  E = (3 + 4×5 + 10) / 6 = (3 + 20 + 10) / 6 = 33/6 = 5.5小时

✅ 给PM的答复： "这个接口大约需要5-6小时，今天下午可以完成。"

💡 面试话术：
  "我一般不直接告诉PM我估了多少小时，而是给一个范围。
  比如这个任务，按正常情况今天下午能交付，但如果第三方接口有问题可能需要明天上午。
  这样PM心里有数，万一延期也有预期。"
```

### 3.4 如何识别需求中的坑

**经验丰富的开发在看到需求的第一时间，脑子里会自动跑一个"风险扫描器"**：

```text
隐藏需求检查清单

□ 权限相关
   → 这个接口需要什么角色才能调用？
   → 用户是否有权限查看/操作？

□ 数据一致性
   → 涉及多个表的修改，需要事务吗？
   → 涉及跨系统调用，数据一致性怎么保证？

□ 并发场景
   → 同一个用户同时操作怎么办？
   → 库存/余额这类数据要防超卖/超提吗？

□ 历史数据兼容
   → 现有数据里有空值/异常值怎么办？
   → 新逻辑向下兼容吗？

□ 性能影响
   → 这个接口的QPS预估是多少？
   → 涉及大表查询吗？走了索引吗？

□ 第三方依赖
   → 调用了外部系统吗？对方SLA怎么保证？
   → 第三方挂了怎么办？（熔断降级）

□ 配置化需求
   → 金额限制是硬编码还是动态配置？
   → 是否要考虑多环境（dev/test/prod）差异？

□ 日志和监控
   → 关键节点有没有打日志？
   → 异常有没有告警？
```

> 🎯 **实战案例**：信用卡还款业务中"单日还款上限"的需求
>
> 表面需求：用户每天最多还款50000元
>
> 隐含坑：
> 1. 跨时区问题 —— 按哪个时区的0点算"一天"？（UTC+8还是用户所在地）
> 2. 动态调整 —— 重大活动期间能不能临时提高额度？（需要配置中心支持）
> 3. 累加维度 —— 是按持卡人维度累加还是卡维度累加？
> 4. 币种一致 —— 多币种卡还款怎么换算？
> 5. 对账影响 —— 限额影响的是用户实际还款能力，那征信报送的还款金额怎么算？
>
> 有经验的开发会在评审会上直接抛出这些问题，而不是在开发了三天后才发现。

#### 4.3.1 设计API

// ============ 请求参数 ============

#### 4.3.2 写Controller层（参数校验 + 统一响应）

@RestController

#### 4.3.3 写Service层（业务逻辑 + 事务）

```java
@Service
@Slf4j
public class OrderServiceImpl implements OrderService {

    @Autowired
    private OrderMapper orderMapper;

    @Override
    public PageResult<OrderVO> queryOrders(OrderQueryRequest request) {
        // 1. 构造查询条件
        LambdaQueryWrapper<Order> wrapper = new LambdaQueryWrapper<>();
        
        // 按状态筛选
        if (StringUtils.hasText(request.getStatus())) {
            wrapper.eq(Order::getStatus, request.getStatus());
        }
        
        // 按时间范围筛选
        if (request.getStartTime() != null) {
            wrapper.ge(Order::getCreateTime, request.getStartTime());
        }
        if (request.getEndTime() != null) {
            wrapper.le(Order::getCreateTime, request.getEndTime());
        }
        
        // 按创建时间倒序
        wrapper.orderByDesc(Order::getCreateTime);

        // 2. 分页查询
        Page<Order> page = new Page<>(request.getPage(), request.getSize());
        Page<Order> result = orderMapper.selectPage(page, wrapper);

        // 3. 实体转VO（使用MapStruct或手动转换）
        List<OrderVO> records = result.getRecords().stream()
                .map(this::toVO)
                .collect(Collectors.toList());

        // 4. 构建分页结果
        return PageResult.<OrderVO>builder()
                .records(records)
                .total(result.getTotal())
                .page((int) result.getCurrent())
                .size((int) result.getSize())
                .build();
    }

    private OrderVO toVO(Order order) {
        // 简单的属性拷贝，实际项目推荐用 MapStruct
        OrderVO vo = new OrderVO();
        BeanUtils.copyProperties(order, vo);
        // 金额分转元
        vo.setAmount(new BigDecimal(order.getAmount()).divide(new BigDecimal(100), 2, RoundingMode.HALF_UP));
        return vo;
    }
}
```

```java
// 分页结果封装
@Data
@Builder
public class PageResult<T> {
    private List<T> records;
    private long total;
    private int page;
    private int size;
}
```

#### 4.3.4 写DAO层（MyBatis-Plus + SQL优化）

```java
@Mapper
public interface OrderMapper extends BaseMapper<Order> {

    // MyBatis-Plus 自带 CRUD 方法
    // selectPage() 已经自动处理了分页
    // 不需要写 XML

    // 但如果需要复杂统计查询，可以自己写SQL：
    @Select("SELECT status, COUNT(*) as cnt " +
            "FROM `order` " +
            "WHERE create_time BETWEEN #{startTime} AND #{endTime} " +
            "GROUP BY status")
    List<OrderStatVO> countByStatus(@Param("startTime") LocalDateTime startTime,
                                     @Param("endTime") LocalDateTime endTime);
}
```

> ⚠️ **SQL优化提醒**：订单表通常是大表（百万/千万级），写SQL时注意：
> - `create_time` 必须建索引（对于时间范围查询）
> - `status` 如果区分度不高（只有几个值），索引效果可能不好
> - 查询条件顺序：把区分度高的字段放在前面
> - 避免 `SELECT *`，只查需要的字段

  "那要不这样，在 Service 层加一个判断，

  我上次写过一个类似的，可以参考一下。"

💡 CR沟通黄金法则：
  - 先肯定，再提出异议
  - 用"我发现"代替"你错了"
  - 用"你看是不是"代替"你应该"
  - 如果发现问题，附上解决问题的建议
