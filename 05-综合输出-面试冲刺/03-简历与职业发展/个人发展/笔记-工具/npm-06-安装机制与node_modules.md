# npm 安装机制与 node_modules 原理

> 了解 `node_modules` 的内部结构，才能真正理解"幽灵依赖"、"依赖提升"这些概念。

---

## 一、npm 安装演化史

### 1.1 npm 1/2：嵌套地狱

```
node_modules/
├── package-a/
│   └── node_modules/
│       ├── lodash@4.0.0/
│       └── axios/
│           └── node_modules/
│               └── lodash@3.0.0/    ← 与上面的不同版本
└── package-b/
    └── node_modules/
        └── lodash@4.0.0/            ← 重复安装！
```

**问题**：
- 路径过长（Windows 260 字符路径限制）
- 重复安装相同的包，磁盘占用巨大
- `rm -rf node_modules` 可能因为路径太长而失败

### 1.2 npm 3+：扁平化

```
node_modules/
├── package-a/
├── package-b/
├── lodash@4.0.0/          ← 提到顶层！多个包共享
├── axios/
│   └── node_modules/
│       └── lodash@3.0.0/  ← 版本冲突时仍然嵌套
└── ...
```

**变化**：尽量把依赖"提升"（hoist）到顶层，减少嵌套。版本冲突时才保留嵌套。

### 1.3 pnpm：硬链接 + 软链接（更激进的优化）

```
node_modules/
├── .pnpm/                         ← 所有包的真正存储（硬链接到全局仓库）
│   ├── vue@3.4.0/node_modules/vue/
│   ├── axios@1.6.0/node_modules/axios/
│   └── ...
├── vue        → .pnpm/vue@3.4.0/node_modules/vue/     ← 软链接
└── axios      → .pnpm/axios@1.6.0/node_modules/axios/  ← 软链接
```

**优势**：
- 全局仓库（store），所有项目共享同一份包文件，通过硬链接共用
- 只暴露 `package.json` 中声明的依赖，**杜绝幽灵依赖**
- 安装速度最快

## 二、node_modules 结构详解

### 2.1 扁平化安装过程

```
假设项目依赖：A@1.0, B@1.0
A 依赖：C@1.0
B 依赖：C@2.0

npm 安装过程：

Step 1：安装项目依赖
  node_modules/
  ├── A@1.0/
  └── B@1.0/

Step 2：安装 A 的依赖 C@1.0
  提升到顶层
  node_modules/
  ├── A@1.0/
  ├── B@1.0/
  └── C@1.0/

Step 3：安装 B 的依赖 C@2.0
  顶层已有 C@1.0，版本冲突！
  → 嵌套到 B 下
  node_modules/
  ├── A@1.0/
  ├── B@1.0/
  │   └── node_modules/
  │       └── C@2.0/    ← 版本冲突，保留嵌套
  └── C@1.0/
```

### 2.2 依赖提升（Hoisting）规则

```
提升优先级：
1. 被更多包依赖的 → 提得更高
2. 安装顺序也影响结果（最先安装的先占据顶层）
3. 顶层已有不冲突的版本 → 直接用顶层的
4. 顶层有冲突的版本 → 嵌套到包内部

结果：node_modules 结构不是唯一确定的！
    安装顺序不同可能导致不同的目录结构
```

### 2.3 幽灵依赖（Phantom Dependencies）

```json
// package.json：只声明了 express
{
  "dependencies": {
    "express": "^4.18.0"
  }
}
```

```javascript
// 你的代码：
const lodash = require('lodash');   // ✅ 能跑！
// express 依赖了 lodash，lodash 被提升到了顶层 node_modules
// → 你的代码可以引用未声明的 lodash
```

**幽灵依赖的危害**：
- Express 某天不再依赖 lodash → `lodash` 从顶层消失 → 💥 你的代码直接报错
- 本地开发正常，CI 环境炸了（依赖版本不同）
- 在其他包管理器（pnpm）下直接跑不起来

**解决方案**：
```bash
# 使用 pnpm（严格模式默认禁止幽灵依赖）
# 或安装 eslint-plugin-import 检查
npm i -D eslint-plugin-import
```

```js
// .eslintrc.js 中配置
rules: {
  'import/no-extraneous-dependencies': 'error'
}
```

## 三、npm install 完整流程

```
npm install
     │
     ▼
┌─────────────────┐
│ 1. 读取配置      │
│ .npmrc + config  │  
└────────┬────────┘
         ▼
┌─────────────────┐
│ 2. 解析依赖树     │
│ 读取 package.json │
│ 计算需要的所有包   │
│ 版本范围 → 具体版本│
└────────┬────────┘
         ▼
┌─────────────────┐
│ 3. 检查缓存      │
│ ~/.npm/_cacache  │
│ 有 → 直接解压     │
│ 没有 → 下载       │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 4. 下载包        │
│ 从 Registry 拉取  │
│ .tgz 压缩包      │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 5. 解压到        │
│ node_modules     │
│ 并执行扁平化      │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 6. 执行 install  │
│ 生命周期脚本      │
│ (preinstall等)   │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 7. 写入 lock     │
│ package-lock.json │
└─────────────────┘
```

### npm ci 的不同

`npm ci` 跳过步骤 2（不解析版本范围）和步骤 7（不写 lock），直接从 lock 文件读取精确版本。

## 四、缓存机制

### 4.1 缓存目录

```bash
npm config get cache
# Windows: %AppData%/npm-cache
# macOS: ~/.npm
# Linux: ~/.npm

# 缓存目录结构
~/.npm/_cacache/
├── content-v2/sha512/    # 包体文件（按内容哈希存储）
├── index-v5/             # 索引：包名 → 版本 → 哈希 → 文件位置
└── tmp/                  # 临时数据
```

### 4.2 缓存策略

```
npm install axios
    │
    ▼
1. 计算 axios@1.6.0 对应的完整性哈希
2. 查找 index-v5：这个哈希对应的包在 content-v2 的哪个位置
3. 找到了 → 直接从缓存解压到 node_modules（不下载）
4. 没找到 → 从 Registry 下载 → 存到缓存 → 解压
```

### 4.3 缓存命令

```bash
npm cache verify         # 验证缓存完整性，清理无效文件（推荐）
npm cache clean --force  # 强制清空整个缓存（谨慎使用）
npm cache ls             # 列出缓存内容

# 离线安装（前提：包已经在缓存中）
npm install --prefer-offline
npm install --offline    # 完全离线，缓存没有就失败
```

## 五、生命周期脚本（Lifecycle Scripts）

### 5.1 完整的执行顺序

```
npm install 时触发的生命周期：

preinstall        ← 安装开始前
  ↓
install           ← 包安装期间
  ↓
postinstall       ← 安装完成后
  ↓
prepublish        ← （仅本地，非 npm install 触发）
  ↓
preprepare        ← （npm 8+）
  ↓
prepare           ← 安装完成后（最常用：husky install）
  ↓
postprepare       ← （npm 8+）
```

### 5.2 各生命周期常用场景

```json
{
  "scripts": {
    "preinstall": "npx only-allow pnpm",
    "postinstall": "patch-package",
    "prepare": "husky install",
    "prebuild": "npm run lint",
    "build": "vite build",
    "postbuild": "node scripts/after-build.js"
  }
}
```

| 钩子 | 常用场景 |
|------|----------|
| `preinstall` | 强制使用特定包管理器（如 `npx only-allow pnpm`）|
| `postinstall` | 打补丁（patch-package）、自动生成类型/代码 |
| `prepare` | 初始化 Git hooks（husky）、编译为 JS |
| `prebuild` | 构建前的检查（lint、类型检查）|
| `postbuild` | 构建后的处理（拷贝资源、生成 Stats）|

## 六、package-lock.json 字段解释

```json
{
  "name": "my-project",
  "version": "1.0.0",
  "lockfileVersion": 3,
  "packages": {
    "node_modules/axios": {
      "version": "1.6.2",
      "resolved": "https://registry.npmjs.org/axios/-/axios-1.6.2.tgz",
      "integrity": "sha512-xxxxx...",
      "dependencies": {
        "follow-redirects": "^1.15.0"
      }
    }
  }
}
```

| 字段 | 说明 |
|------|------|
| `version` | 实际安装的精确版本 |
| `resolved` | 包的下载地址（记录了从哪个源下载的）|
| `integrity` | SHA-512 哈希（用于校验包完整性，防篡改）|
| `dependencies` | 此包自身的依赖（来自其 package.json 的声明）|

## 七、node_modules 问题排查

### 7.1 常见报错

| 报错 | 原因 | 解决 |
|------|------|------|
| `Cannot find module 'xxx'` | 依赖未安装/幽灵依赖/路径错误 | `npm install`，检查代码引用 |
| `ERESOLVE unable to resolve` | 依赖版本冲突 | `npm install --legacy-peer-deps` 或修复版本 |
| `Maximum call stack` | 循环依赖 | 检查包的依赖链 |
| `Integrity check failed` | 包被篡改或缓存损坏 | `npm cache verify` 后重新安装 |
| Windows 路径过长 | 嵌套过深 | 删除重装 + 用较新 Node 版本（已支持长路径）|

### 7.2 清理重装

```bash
# 彻底清理
rm -rf node_modules package-lock.json
npm cache verify
npm install
```

### 7.3 依赖体积分析

```bash
# 查看哪些包占空间最大
npx cost-of-modules

# 可视化分析
npx npm-why axios   # 为什么 axios 是间接依赖

# 查看是否有重复包
npm ls lodash       # 查看 lodash 被安装了几份
npm dedupe          # 尽量消除重复依赖
```

---

> **核心记忆**：npm 3+ 扁平化安装，版本冲突时嵌套保留。幽灵依赖是扁平化的副产物（pnpm 解决了它）。install 生命周期有严格的执行顺序。出问题就 `rm -rf node_modules && npm install`。
