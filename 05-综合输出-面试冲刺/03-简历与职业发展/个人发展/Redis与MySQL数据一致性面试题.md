# Redis 与 MySQL 数据一致性

## 概述

Redis 作为缓存层，本质是 MySQL 的数据副本，用于提升查询性能。由于缓存和数据库是两个独立存储系统，数据更新无法做到原子性同步，加上并发读写、操作失败、网络延迟等因素，必然面临数据一致性问题。本文系统梳理面试中该话题的核心考点与回答框架。

---

## 一、基础概念

### 1.1 为什么会出现不一致？

```
Redis（缓存副本） ←→ MySQL（数据源头）
       ↑                    ↑
   两个独立存储，更新操作非原子性
   + 并发读写 + 网络延迟 + 操作失败
         ↓
       数据不一致
```

### 1.2 读写核心流程

| 操作类型 | 流程 |
|---------|------|
| **查询** | 查 Redis → 命中则直接返回 → 未命中则查 MySQL → 数据写入 Redis → 返回 |
| **更新** | 需同时操作数据库和缓存，**操作时序**是决定一致性的关键因素 |

### 1.3 一致性级别与选型

| 级别 | 定义 | 性能影响 | 适用场景 |
|------|------|:---:|---------|
| **强一致性** | 任意时刻缓存与数据库数据完全一致 | 性能较低 | 金融、支付、账户余额等 |
| **最终一致性** | 允许短暂不一致，最终达到一致状态 | 性能最优 | 绝大多数互联网业务（商品信息、用户资料等） |
| **弱一致性** | 不保证同步时效，只保证数据最终落地 | 性能最高 | 日志、统计、非核心展示类业务 |

## 二、缓存更新策略

### 2.1 三种主流策略对比

| 策略 | 流程 | 优点 | 缺点 | 推荐程度 |
|------|------|------|------|:---:|
| **先更新 DB，再删除缓存** | 更新 MySQL → 删除 Redis 缓存 | 实现简单、并发问题最少 | 极端并发下短暂脏数据（可兜底） | ⭐⭐⭐ **业界首选** |
| **先删除缓存，再更新 DB** | 删除 Redis 缓存 → 更新 MySQL | 无明显优势 | 高并发下产生永久脏数据，**生产环境禁止使用** | ⭐ 不推荐 |
| **先更新 DB，再更新缓存** | 更新 MySQL → 更新 Redis 缓存 | 缓存始终是最新数据 | 并发更新数据覆盖、写多场景浪费性能 | ⭐⭐ 仅写少读多场景 |

### 2.2 策略一详解：先更新 DB，再删除缓存（推荐）

```
正常流程：
  更新 MySQL ✓ → 删除 Redis 缓存 ✓ → 下次查询时重新加载最新数据

极端并发问题：
  线程 A 更新 MySQL（写入新数据）
  线程 B 查询 Redis（缓存已过期）→ 查 MySQL（此时 A 尚未删除缓存？）
  → B 将查到的数据写入 Redis
  
  但 Redis 已被 A 删除，B 写入时查到的是 MySQL 最新数据，所以实际上没有问题。
  
真正的风险场景（概率极低）：
  线程 A 查询 Redis（未命中）→ 查 MySQL（读到旧数据）
  线程 B 更新 MySQL（写入新数据）→ 删除 Redis 缓存
  线程 A 将旧数据写入 Redis
  
  → 解决：延时双删 + 缓存 TTL 兜底
```

### 2.3 策略二风险分析：先删除缓存，再更新 DB（禁用的原因）

```
线程 A：删除 Redis 缓存 → 准备更新 MySQL（尚未执行）
线程 B：查询 Redis（未命中）→ 查 MySQL（读到旧数据）→ 将旧数据写入 Redis
线程 A：更新 MySQL（写入新数据）

结果：MySQL 是新数据，Redis 是旧数据 → 永久脏数据（直到缓存过期）
```

### 2.4 为什么不推荐更新缓存而是删除缓存？

| 原因 | 说明 |
|------|------|
| 性能更优 | 删除比写入开销小，避免无效的缓存写入操作 |
| 避免并发覆盖 | 更新缓存会出现并发写覆盖问题（后写的旧数据覆盖先写的新数据） |
| 避免浪费 | 写多场景下，缓存频繁更新但可能从未被读取，纯浪费资源 |
| 懒加载思想 | 删除后等下次查询时按需加载，保证缓存中都是热数据 |

## 三、高并发场景下的一致性保障方案

### 3.1 延时双删

**执行流程**：

```
更新 MySQL → 删除 Redis → 休眠（业务查询耗时）→ 再次删除 Redis
                ↑                                    ↑
            第一次删除                          第二次删除（兜底）
```

| 维度 | 说明 |
|------|------|
| 解决问题 | "先更库后删缓存"极端并发下，旧数据回写到缓存的低概率事件 |
| 休眠时间 | 根据业务查询耗时调整，一般设置 **200~500ms** |
| 注意事项 | 第二次删除建议异步执行，避免阻塞主流程影响接口响应时间 |

### 3.2 分布式锁方案（强一致性）

使用 Redisson 分布式锁，将缓存 + 数据库操作串行化：

| 步骤 | 操作 |
|:--:|------|
| 1 | 对操作的业务 Key 加分布式锁 |
| 2 | 加锁成功后，依次执行：MySQL 更新 → Redis 缓存删除/更新 |
| 3 | 操作完成后释放锁 |
| 4 | 同一时刻只有**一个线程**操作该数据，彻底避免并发不一致 |

> **适用场景**：核心业务数据（如账户余额、库存扣减），对一致性要求极高。

### 3.3 Canal + Binlog 异步同步方案（最终一致性）

| 步骤 | 说明 |
|:--:|------|
| 1 | Canal 伪装成 MySQL 从节点，订阅主库 Binlog 日志 |
| 2 | 监听到数据库增删改操作后，解析 Binlog 获取数据变更内容 |
| 3 | 异步执行 Redis 缓存删除/更新操作 |

| 优势 | 说明 |
|------|------|
| 业务无侵入 | 代码中不需要写缓存同步逻辑，完全由中间件处理 |
| 不影响性能 | 异步执行，不阻塞业务主流程 |
| 保证最终一致性 | 基于 Binlog 的可靠数据源，变更不会遗漏 |

### 3.4 方案对比总览

| 方案 | 一致性级别 | 性能影响 | 复杂度 | 适用场景 |
|------|:---:|:---:|:---:|---------|
| 先更 DB + 删缓存 + TTL | 最终一致性 | 低 | 低 | 绝大多数业务（默认首选） |
| + 延时双删 | 最终一致性（更可靠） | 低 | 中 | 高并发读写场景 |
| + 分布式锁 | 强一致性 | 中高 | 中 | 核心业务数据（支付/库存） |
| Canal + Binlog | 最终一致性 | 极低 | 高 | 大规模微服务架构 |

## 四、场景化选型指南

### 4.1 按读写比例选型

| 场景特征 | 推荐方案 | 原因 |
|---------|---------|------|
| **读多写少** | 先更新 DB + 删除缓存 + 缓存 TTL | 性价比最高，缓存命中率高 |
| **写多读少** | 直接禁用缓存，查询走数据库 | 避免缓存频繁更新，写入成本大于收益 |
| **读写均衡 + 高并发** | 先更 DB + 延时双删 + TTL | 覆盖极端并发下的旧数据回写 |
| **强一致性要求** | 分布式锁串行化 | 牺牲并发性能换取数据绝对一致 |

### 4.2 缓存异常与一致性的关联

| 缓存问题 | 与一致性的关系 | 解决方案 |
|---------|--------------|---------|
| **缓存击穿** | 热点 Key 过期，大量请求直达 DB，并发查库写缓存可能引发不一致 | 热点 Key 永不过期 / 加互斥锁 |
| **缓存穿透** | 查询不存在的数据，每次穿透到 DB，一般不直接影响一致性 | 布隆过滤器 / 空值缓存 |
| **缓存雪崩** | 大量 Key 同时过期，DB 压力骤增，可能间接影响数据同步时效 | 过期时间加随机值 / 多级缓存 / 熔断降级 |

## 五、生产环境最佳实践总结

### 分层设计

```
┌──────────────────────────────────────────┐
│  第一层：基础策略                          │
│  先更新 MySQL → 删除 Redis → 设置 TTL     │
├──────────────────────────────────────────┤
│  第二层：并发兜底（高并发场景）              │
│  延时双删 + 异步执行第二次删除              │
├──────────────────────────────────────────┤
│  第三层：强一致保障（核心数据）              │
│  分布式锁 串行化 DB + 缓存操作              │
├──────────────────────────────────────────┤
│  第四层：架构级保障（大规模微服务）           │
│  Canal + Binlog 异步同步，业务零侵入        │
├──────────────────────────────────────────┤
│  兜底层：最终防线                          │
│  所有缓存必有 TTL + 定时任务校验热点数据     │
└──────────────────────────────────────────┘
```

### 核心原则

1. **默认首选**：先更新 DB，再删除缓存，设置 TTL——覆盖 90% 的场景
2. **高并发加兜底**：延时双删 + 异步执行
3. **核心数据加锁**：分布式锁实现强一致性
4. **大规模用中间件**：Canal 监听 Binlog，业务代码零侵入
5. **永远有 TTL**：所有缓存必须设过期时间，这是最后的兜底防线
