# Redis与MySQL数据一致性面试题

## 一、基础面试题
1. 为什么会出现Redis和MySQL数据不一致的问题？
    Redis作为缓存，是MySQL的数据副本，用于提升查询性能，避免直接查询数据库。由于缓存和数据库是两个独立存储，数据更新无法做到原子性同步，再加上并发读写、操作失败、网络延迟等问题，就会出现两者数据不一致的情况。
2. 缓存和数据库的读写核心流程是什么？
    - 查询流程：先查Redis→缓存命中直接返回→未命中则查MySQL，再将数据写入Redis，最后返回
    - 更新流程：需要同时操作数据库和缓存，操作时序不当就会引发数据不一致
3. 数据一致性分为哪几种级别？业务中该如何选择？
    1. 强一致性：任意时刻缓存和数据库数据完全一致，牺牲性能换一致性，适用于金融、支付等场景
    2. 最终一致性：允许短暂数据不一致，最终能达到一致，性能最优，适用于绝大多数互联网业务
    3. 弱一致性：不保证数据同步时效，只保证数据最终落地，适用于日志、统计等非核心业务

## 二、核心策略面试题
1. 缓存更新有哪几种主流策略？各自优缺点是什么？
    （1）先更新MySQL，再删除Redis缓存（业界首选）
    - 优点：实现简单、性能开销小、并发场景下问题最少
    - 缺点：极端并发下会出现短暂脏数据，可通过兜底方案解决
    - 适用场景：绝大多数互联网业务、读多写少场景
    （2）先删除Redis缓存，再更新MySQL
    - 优点：无明显优势
    - 缺点：高并发下会产生永久脏数据，生产环境严禁使用
    - 问题场景：线程A删缓存→线程B查缓存未命中→查MySQL旧数据→写入缓存→线程A更新数据库，缓存留存旧数据
    （3）先更新MySQL，再更新Redis缓存
    - 优点：缓存始终是最新数据
    - 缺点：并发更新会出现数据覆盖、写多场景下缓存无效更新浪费性能
    - 适用场景：写少读多、数据更新频率极低的场景
2. 什么是延时双删？解决什么问题？
    - 执行流程：更新MySQL→删除Redis缓存→休眠几百毫秒→再次删除Redis缓存
    - 解决问题：解决「先更库后删缓存」极端并发下，旧数据回写到缓存的问题
    - 注意事项：休眠时间根据业务查询耗时调整，一般设置200-500ms，避免影响业务性能
3. 如何彻底解决缓存和数据库的不一致问题？
    1. 基础兜底：所有缓存必须设置TTL过期时间，即使出现脏数据也会自动淘汰
    2. 并发优化：高并发场景使用延时双删策略
    3. 强一致方案：使用分布式锁，串行化缓存+数据库操作
    4. 无侵入方案：通过Canal监听MySQL Binlog日志，异步同步数据到Redis

## 三、进阶&场景面试题
1. Canal实现Redis和MySQL最终一致性的原理是什么？
1. Canal伪装成MySQL从节点，订阅主库Binlog日志
2. 监听到数据库增删改操作后，解析Binlog获取数据变更
3. 异步执行Redis缓存删除/更新操作
4. 优势：业务代码无侵入、不影响业务性能、保证最终一致性
2. 分布式锁如何保证缓存数据库强一致性？
    针对核心数据操作，使用Redisson分布式锁：
    1. 对操作的业务key加分布式锁
    2. 加锁成功后，依次执行MySQL更新、Redis缓存删除/更新
    3. 操作完成后释放锁
    4. 保证同一时刻只有一个线程操作数据，彻底避免并发不一致问题
3. 读多写少和写多读少场景，分别该选择什么一致性方案？
    - 读多写少：先更新数据库+后删除缓存+缓存TTL，性价比最高
    - 写多读少：直接禁用缓存，直接查询数据库，避免缓存频繁更新
4. 缓存穿透、缓存击穿、缓存雪崩和数据一致性有什么关联？
    - 缓存击穿：热点key过期，大量请求直击数据库，可能引发旧数据回写缓存导致不一致
    - 解决方案：热点key永不过期、加互斥锁，避免并发查库写缓存

## 四、面试总结题
1. 生产环境中，你如何设计Redis和MySQL数据一致性方案？
1. 核心业务：采用先更新MySQL，再删除Redis缓存+延时双删+缓存TTL，保证最终一致性
2. 高并发核心数据：新增分布式锁，实现强一致性
3. 大规模微服务：接入Canal中间件，异步同步数据，业务无侵入
4. 兜底保障：所有缓存必设过期时间，定时任务校验热点数据
2. 为什么不推荐使用更新缓存，而是删除缓存？
    1. 删除缓存性能更高，避免无效的缓存写入操作
    2. 更新缓存会出现并发覆盖问题，旧数据覆盖新数据
    3. 写多场景下，缓存更新频繁，无实际意义，浪费资源
