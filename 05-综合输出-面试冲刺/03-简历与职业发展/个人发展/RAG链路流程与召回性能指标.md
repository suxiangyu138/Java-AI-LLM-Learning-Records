# RAG 链路、Skill/MCP、对话管理与消息队列选型

> 本文整理 AI 应用开发面试中的 5 个高频技术问答，涵盖 RAG 召回链路、Skill 封装与 MCP 协议、多轮对话管理、Prompt 工程、消息队列选型。

## 一、RAG 链路流程与召回性能指标

### 1.1 完整 RAG 链路

RAG（Retrieval-Augmented Generation）链路分为 6 个阶段：

| 阶段 | 名称 | 操作说明 |
|:--:|------|---------|
| 1 | 数据预处理 | 非结构化文档清洗、分段，按业务逻辑设置**重叠窗口**（Overlap），避免上下文在切分边界处断裂 |
| 2 | 向量化与存储 | 调用 Embedding 模型将文本片段转为向量，存入向量数据库（Milvus / Chroma 等），建立索引 |
| 3 | 用户 Query 处理 | 对用户输入进行意图识别、关键词提取和 **Query 改写**，解决歧义和口语化问题 |
| 4 | 向量召回 | 根据用户 Query 向量，在向量库中进行 Top-K 相似性检索，得到候选相关片段 |
| 5 | 重排序（Rerank） | 使用交叉编码器（Cross-Encoder）模型对召回结果进行二次相关性排序，过滤低质量结果 |
| 6 | Prompt 组装与生成 | 将重排序后的上下文与用户问题注入 Prompt 模板，调用 LLM 生成最终答案 |

### 1.2 召回性能指标体系

| 指标类别 | 指标名称 | 说明 |
|---------|---------|------|
| **核心指标** | Recall@K | Top-K 召回结果中，相关文档占全部相关文档的比例 |
| | Precision@K | Top-K 召回结果中，相关文档占召回结果的比例 |
| | MRR（Mean Reciprocal Rank） | 第一个相关文档排名的倒数均值，衡量排名质量 |
| **业务指标** | 答案相关性 | 生成答案与用户意图的匹配程度 |
| | 幻觉率 | 生成内容中存在事实错误的占比 |

### 1.3 性能调优手段

| 调优维度 | 具体手段 | 效果目标 |
|---------|---------|---------|
| Chunk 大小 | 调整文本切分粒度（如 256 / 512 / 1024 tokens） | 平衡语义完整与检索精度 |
| 重叠窗口 | 设置相邻 Chunk 之间的重叠长度 | 减少上下文断裂 |
| Embedding 模型 | 对比不同模型（如 text-embedding-3、bge-large 等）的向量表达能力 | 提升语义匹配准确率 |
| Rerank 模型 | 引入 Cross-Encoder 模型（如 bge-reranker）做二次排序 | 提升 Top 结果的相关性 |

> **调优成果参考**：通过上述组合手段，Recall@5 可提升至 90% 以上。

## 二、Skill 封装与 MCP 协议交互

### 2.1 核心区别

Skill 技能封装和 MCP 协议交互的核心区别在于**抽象层级**和**交互方式**。

| 对比维度 | Skill 技能封装 | MCP 协议交互 |
|---------|---------------|-------------|
| **定位** | 面向开发者的本地/服务端函数封装 | 标准化的远程交互协议 |
| **本质** | 将具体能力包装为可被大模型调用的**可执行单元** | 定义大模型与外部工具/服务之间的**通信格式** |
| **包含内容** | 输入输出参数定义、参数校验、异常处理 | 请求头、请求体、错误码、流式响应格式 |
| **运行位置** | 应用服务内 | 定义跨服务、跨语言的标准化通信规范 |
| **解决的问题** | "Agent 能调用什么功能" | "Agent 怎么与外部工具通信" |

### 2.2 项目中的实践方案

```
设计原则：业务逻辑与协议交互解耦

┌──────────────────────────────────────┐
│          MCP 协议交互层               │
│  解析请求 → 路由 → 格式化响应          │
├──────────────────────────────────────┤
│       Skill 技能封装层                │
│  订单查询 │ 天气查询 │ 数据库操作 │ ... │
└──────────────────────────────────────┘
```

**实现步骤**：

1. 将业务逻辑封装为独立的 Skill（如订单查询、天气查询），每个 Skill 有明确的 Schema 定义（输入参数、输出格式、异常类型）
2. 基于 MCP 协议规范，开发通用的工具调用客户端
3. 当大模型通过 Function Call 返回工具调用请求时，客户端**解析请求 → 路由到对应 Skill → 执行 → 按 MCP 协议格式返回结果**
4. 新增 Skill 时无需修改协议层代码，只需注册新的 Skill 即可

## 三、多轮对话管理与上下文优化

### 3.1 三层架构总览

会话记忆和上下文管理采用三层架构：

```
┌─────────────────────────────────┐
│       Prompt 组装层              │  最终 Prompt 拼装 + Token 计数
├─────────────────────────────────┤
│       上下文优化层               │  滑动窗口 / 摘要压缩 / 关键信息提取
├─────────────────────────────────┤
│       会话存储层                 │  Redis 缓存 + MySQL 持久化
└─────────────────────────────────┘
```

### 3.2 各层详解

| 层级 | 组件 | 实现方式 |
|------|------|---------|
| **会话存储层** | Redis 缓存 | 以 `sessionId` 为 Key 存储对话历史，设置过期时间（TTL） |
| | MySQL 持久化 | 持久化会话记录，用于审计追溯和模型微调数据积累 |
| **上下文优化层** | 滑动窗口 | 仅保留最近 N 轮对话，防止上下文超出模型限制 |
| | 摘要压缩 | 对话超过阈值轮数时，调用 LLM 对历史对话生成摘要，用摘要替代原始历史 |
| | 关键信息提取 | 从对话中提取实体（订单号、用户 ID）和意图，结构化存储，减少后续轮次的重复提问 |
| **Prompt 组装层** | 模板拼装 | 将优化后的对话历史、当前用户问题、System Prompt 按固定格式组装 |
| | Token 计数 | 实时计算组装后 Prompt 的 Token 数量，确保不超过模型最大上下文窗口限制 |

## 四、Prompt 工程理解与实践

### 4.1 核心理解

Prompt 工程不是玄学，而是一套有方法论的工程实践——通过设计**清晰、明确、可被大模型理解的输入指令**，引导模型输出符合预期的结果。

### 4.2 Cursor 辅助 Prompt 开发的实践

| 场景 | 做法 |
|------|------|
| 快速迭代 Prompt 模板 | 使用 Cursor 的 AI 对话功能，快速生成和修改不同场景下的 Prompt 模板（RAG 场景、多轮对话、工具调用等） |
| 调试 Few-shot 示例 | 借助 AI 辅助设计和验证 Few-shot 示例，确保覆盖主要业务场景和边界情况 |
| Prompt 性能分析 | 对比不同 Prompt 模板的输出效果，定位模型容易产生幻觉或答非所问的点，针对性优化 |

### 4.3 Prompt 工程四项核心原则

| # | 原则 | 说明 | 示例 |
|:--:|------|------|------|
| 1 | **指令明确** | 清晰告诉模型：任务目标、角色身份、输出格式、行为约束 | "你是一个医疗问诊助手，请根据用户描述的症状..." |
| 2 | **提供上下文** | 给模型足够的背景信息，减少歧义和猜测空间 | 注入相关文档片段、用户历史记录、业务规则 |
| 3 | **设置边界** | 明确定义模型**不能**做什么，建立安全护栏 | "如果用户询问用药剂量，请引导其咨询医生，不要给出具体建议" |
| 4 | **结构化输出** | 指定输出格式（JSON / Markdown 等），方便下游程序解析 | 要求返回 `{"symptoms":[], "suggestions":[], "urgency":"low|medium|high"}` |

## 五、消息队列选型：为什么选择 RabbitMQ

### 5.1 选型理由

| 考量维度 | RabbitMQ 优势 |
|---------|--------------|
| **可靠性** | 支持消息持久化、生产者确认（Publisher Confirm）、消费者确认（Consumer Ack），保证消息不丢失，满足业务最终一致性要求 |
| **路由灵活性** | 支持 Direct / Topic / Fanout / Headers 四种 Exchange 类型，灵活实现消息路由与广播 |
| **生态成熟度** | Java 生态支持良好（Spring AMQP 开箱即用），社区活跃，文档和问题解决方案丰富 |

### 5.2 主流消息队列对比

| 对比维度 | RabbitMQ | Kafka | RocketMQ |
|---------|:---:|:---:|:---:|
| **吞吐量** | 中等（万级 TPS） | 极高（百万级 TPS） | 高（十万级 TPS） |
| **消息可靠性** | 高（持久化 + 确认机制） | 可配置（允许丢失换取性能） | 高（同步刷盘 + 事务消息） |
| **路由能力** | 强（多种 Exchange） | 弱（仅 Topic 分区） | 中等 |
| **适用场景** | 业务解耦、异步处理、可靠消息 | 日志采集、流处理、大数据管道 | 电商交易、金融场景 |
| **Java 集成** | Spring AMQP（极简） | Spring Kafka | RocketMQ Spring |
| **学习成本** | 低 | 中高 | 中 |

### 5.3 决策总结

```
业务场景要求：高可靠性 + 灵活路由 + 开发维护成本可控
        ↓
推荐选择：RabbitMQ（而非 Kafka 的高吞吐低可靠，或 RocketMQ 的高维护成本）
```
