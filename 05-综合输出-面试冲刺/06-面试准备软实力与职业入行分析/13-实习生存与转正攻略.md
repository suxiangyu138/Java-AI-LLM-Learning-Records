## 1. 入职前一周的准备清单

### 技术准备

```
□ 了解公司的技术栈
  → 看JD描述、面经中提到、或直接问HR/mentor
  → 提前熟悉：如果公司用Dubbo但你只会Spring Cloud，至少了解一下Dubbo基础

□ 搭建开发环境
  → JDK版本、IDE、Maven/Gradle、Git
  → 公司一般用企业微信/飞书/钉钉+内网VPN，提前下载好

□ 复习核心知识
  → Java集合、多线程、MySQL、Redis——你面试时说的"熟悉"，马上要兑现了
```

### 心态准备

```
□ 调整预期
  → 实习第一个月大概率在"看代码"和"配环境"中度过——这是正常的
  → 你的代码会被CR（Code Review）找出大量问题——这也是正常的，不要玻璃心
  → 你可能发现自己啥都不会——几乎每个人都这样

□ 明确目标
  → 如果目标是转正：一切行动围绕"证明你能独立干活"
  → 如果目标是学习：一切行动围绕"深度参与而非浅尝辄止"
  → 如果目标是简历加分：一切行动围绕"留下可写的项目成果"
```

### 物资准备

```
□ 笔记本电脑（如果公司不配）
□ 水杯、纸巾等日常用品
□ 小本子和笔（记重要的信息——比手机记更有仪式感，也显得认真）
□ 提前确认：着装要求（互联网公司多数无要求，但第一天稍微正式一点不会错）
```

## 2. 第一周：建立人脉与上手环境

### 第一天的核心任务

| 任务 | 怎么做 |
|------|--------|
| **认识团队** | mentor介绍每个人时，记下名字+负责方向。主动说"你好，我是新来的实习生XX" |
| **加联系方式** | 加mentor、leader、组内同事的企业微信/飞书 |
| **搞定环境** | 开发环境、代码仓库权限、数据库权限、各种内部平台账号 |
| **了解项目** | 看项目文档、架构图、核心业务流程介绍 |
| **搞清楚规则** | 上下班时间、例会时间、请假流程、报销流程、WiFi密码 |

### 第一周的沟通清单

```text
一定要找mentor聊清楚的几件事：
  1. "我接下来主要跟哪个项目/模块？"
  2. "团队对实习生的期望是什么？大概什么时候开始独立做需求？"
  3. "代码规范和开发流程大概是怎样的？（分支策略/CR流程/发布流程）"
  4. "日常沟通是用什么方式？遇到问题优先找谁？"
  5. "有没有新人文档或者 onboarding 文档？"
```

### 第一周的观察清单

```text
暗中观察（帮你更快融入）：
  - 团队的工作节奏：是9点到9点还是10点到7点？
  - 同事间的沟通风格：是直接还是委婉？开玩笑的边界在哪？
  - 谁会主动帮你？谁比较热情？——这些人是你遇到问题时优先找的
  - leader的管理风格：是放养型还是细节型？这决定了你该怎么汇报
```

## 3. 第一个月：拿下第一个需求

### 从"看代码"到"写代码"的过渡

```
第1-3天：搭环境、看文档、了解业务流程
第4-7天：看代码（先看结构，再看具体模块），尝试本地跑起来并debug
第2周：  mentor会给你一个小需求（改个Bug/加个小功能）
         这是你证明自己的第一个机会！

第3-4周：完成1-2个需求后，mentor会逐步给你更复杂的事情
         你的目标：让mentor觉得"这个实习生可以独立干活了"
```

### 如何快速读懂一个陌生的代码库

| 步骤 | 做什么 | 为什么 |
|:--:|------|--------|
| 1 | 先看项目结构（包名/模块划分） | 建立全局地图，知道什么代码在哪 |
| 2 | 看配置文件（application.yml、pom.xml） | 了解用了什么中间件、什么版本 |
| 3 | 找一个接口，从Controller追到DAO | 理解完整的请求链路 |
| 4 | 看数据库表结构（ER图如果有的话） | 理解数据模型是最快理解业务的方式 |
| 5 | 看单元测试（如果有） | 测试是最好的使用文档 |
| 6 | 遇到不懂的类/方法→不要立刻读源码→先搞清楚它的职责和对外的接口 | 先黑盒理解，再白盒深入 |

> 💡 **看代码时的心态：** 你不需要理解每一行代码。你需要的是——当一个需求过来时，你能大概知道"改哪个包、改哪个类、可能影响哪些地方"。

### 做第一个需求时的注意事项

```
1. 理解需求再动手
   先用自己的话复述给mentor确认——确保你没理解错

2. 设计方案再写代码
   哪怕是改一个小功能，也先说"我打算这样做：...你看合适吗？"

3. 写完后自己先测
   在提交CR之前，至少把你的修改跑一遍，把基本的Case测了
   不要把一个"明显跑不通"的代码提交给mentor审核

4. CR时的心态
   mentor在你的代码上标了一堆comment → 这是好事！说明他在认真带你
   不要防御性回复（"但是..."），而是"好的，我改一下"
   把mentor提的每个点记下来，下次不再犯同样的
```

## 4. 问问题的正确姿势：实习生最重要的技能

### 问问题的黄金法则

> 🎯 **"先自己尝试15分钟 → 整理好问题 → 带上你的尝试结果去问"**

这不是客气，是效率。你带着"我试了XX、YY都不行"去问，mentor可以快速定位问题。你直接说"这个怎么做"，mentor还得从头给你讲起。

### 好问题 vs 坏问题

| ❌ 坏问题 | ✅ 好问题 |
|---------|---------|
| "这个报错了怎么办？" | "我跑XX接口时报了NPE，看了日志是第42行，我怀疑是XX对象没注入，但我检查了配置好像没问题——能帮我看一下吗？" |
| "Redis怎么用？" | "我在做XX功能需要缓存，我看了项目里其他地方用了RedisTemplate，我可以参考那个实现吗？还是团队有别的推荐方式？" |
| "这个项目是干什么的？" | "我看了项目文档了解了大概，想问一下我们团队主要负责的是那一层？和其他团队的边界在哪里？" |
| "这个代码什么意思？" | "我看了XX方法，大概理解是做了XX，但YY那部分逻辑不太明白为什么这样处理——能简单讲一下背景吗？" |

### 提问的时机

| 什么时候该立刻问 | 什么时候该自己先研究 |
|----------------|-------------------|
| 涉及权限/账号的问题（你没法自己解决） | 代码逻辑不理解的（先看注释+debug） |
| 环境/配置问题卡了30分钟以上 | 报错信息可以在Google/内部Wiki里搜到的 |
| 业务逻辑不清楚（需求文档没写） | 技术实现方式的选择（先尝试自己写一版） |
| 涉及安全/线上操作的问题 | 框架/中间件的基本用法（先看文档） |

> ⚠️ **两个极端都要避免：** ①遇到问题立刻张嘴问（不思考）②卡了两天还死扛（不问人）。掌握了"15分钟原则"，你就能在这两个极端之间找到平衡。

## 5. 实习生最常见的坑

| 坑 | 表现 | 怎么避免 |
|----|------|---------|
| **不敢问问题** | 怕显得菜，一个人闷头搞了好几天没进展 | 记住第4节的"好问题"法则——问问题本身是能力的体现 |
| **问太多太碎** | 每个小问题都去问，mentor不胜其烦 | 攒3-5个问题一次性问，或者先在文档/Wiki里搜 |
| **过度表现** | 第一周就想重构代码、推翻现有设计 | 先理解为什么它是这样设计的，大概率有历史原因 |
| **划水摸鱼** | 没人管就刷手机、看视频 | 主动找mentor要活。没事干比活多更可怕 |
| **擅自做决定** | 觉得"这点小事不用问"，上线后出问题 | 不确定的事一定要确认。实习生最大的特权就是"可以问" |
| **只关注自己的模块** | 不看全局，不理解业务 | 主动了解你在做的东西在整体系统中的位置 |
| **代码Review玻璃心** | 被提了comment就不高兴/沮丧 | CR被批是日常，这是你在快速成长 |
| **只做被安排的事** | 做完分配的活就等着 | 主动说"我这边做完了，还有什么我可以帮忙的吗？" |

> 🎯 **实习生评价的核心标准：** mentor能不能放心地把一个需求交给你，不需要他时刻盯着。你的所有行为都该围绕"建立信任"这个目标。

## 6. 如何让mentor愿意教你

### 带实习生对mentor来说意味着什么

> mentor带你不会多拿工资。对他来说，带你 = 额外工作量。所以你要做的是——**让带你这件事，从负担变成价值。**

### 让mentor觉得"带你不亏"的行为

| 行为 | mentor的感受 |
|------|------------|
| 你问问题之前先自己查过、尝试过 | "这个实习生省心" |
| 同一个问题不问第二遍（记下来了） | "他学得很快" |
| CR提的问题一次改到位 | "他认真听了" |
| 你的代码写得规范、测试充分 | "可以放心交给他了" |
| 你主动写了个踩坑文档/onboarding笔记 | "他在帮团队沉淀知识，有价值" |
| 你做完了分配的活，主动要新的 | "他有自驱力" |
| 你在周会上分享了学到的东西 | "他在给团队做贡献" |

### 和mentor的相处分寸

```text
应该的：
  - 主动汇报进度（不用他问"做完了吗"）
  - 遇到困难及时反馈（不用他主动来发现你卡住了）
  - 接受批评，不辩解
  - 在合适的时机表达感谢（不用天天拍马屁，但偶尔一句"谢谢你的建议"很有用）

不应该的：
  - 过度打扰（mentor也有自己的工作）
  - 下班后频繁发消息（除非是紧急的线上问题）
  - 在公开场合和mentor争论（即便你对，私聊说）
  - 越级汇报（有问题先找mentor，除非mentor真的不管）
```

## 7. 转正的标准、节奏与策略

### 转正考核什么

| 维度 | 考核标准 | 你怎么做 |
|------|---------|---------|
| **技术能力** | 能独立完成中等复杂度的需求 | 主动争取有挑战的任务，别只做简单Bug |
| **代码质量** | CR时问题少、边界考虑全、有测试 | 提交前自己先测，写好单元测试 |
| **学习能力** | 遇到新东西能快速上手 | 主动学新工具/新技术，展示学习过程 |
| **沟通协作** | 能和产品/测试/其他开发顺畅沟通 | 主动参与讨论，不只闷头写代码 |
| **主动性** | 不只完成分配任务，能有更多贡献 | 主动做技术分享、写文档、做工具改进 |
| **可靠性** | 承诺的事情能做到，出问题不甩锅 | 凡事有响应，遇到问题第一时间说 |

### 转正的时间节奏

```
6月入职（暑期实习）
    ↓
7月-8月：正常工作，积累表现
    ↓
8月底-9月初：通常开始转正答辩/评估
    ↓
9月中：转正结果 + Offer发放
    ↓
（如果转正成功）9-11月秋招季，你已经有保底了
```

### 转正答辩准备

```text
如果你的实习有转正答辩，通常会让你做一个总结汇报，内容包括：

1. 实习期间做了什么事（项目/需求列表）
2. 最有挑战的一件事是什么，你怎么解决的（技术深度）
3. 你学到了什么（成长总结）
4. 你对团队有什么贡献（不只是代码，可以是文档/工具/分享）
5. 你觉得自己还有什么不足（诚实+改进计划）

准备技巧：
  - 用数据说话（完成了X个需求、修复了Y个Bug、优化了Z%的性能）
  - 不止讲"做了什么"，更要讲"为什么这么做"和"学到了什么"
  - 提到感谢mentor和团队（得体且真诚）
```

### 如果没转正怎么办

```text
不要慌。转正失败≠你不行，可能的原因：
  - 部门HC被砍了（和你的表现无关）
  - 公司战略调整（和你的表现无关）
  - 组里高手太多（你在别的地方可能是最好的）

你需要做的：
  1. 问mentor/leader对你的反馈——"我有哪些地方可以改进？"
  2. 把实习项目写成简历亮点
  3. 请mentor/leader做你的背调联系人
  4. 拿着这份含金量更高的简历，秋招/春招再战
```

## 8. 实习结束后要做的事

### 技术收尾

```
□ 把你负责的代码做好注释和文档
□ 把交接文档写好（你的代码怎么跑、有哪些注意事项）
□ 确保你的分支已经合并/你的代码有人接手
□ 把实习期间学到的技术点整理成笔记（别丢了）
```

### 人际关系收尾

```
□ 在团队群里发一个简短的感谢消息
□ 单独给mentor和leader发感谢（具体提到他们对你的帮助）
□ 加mentor和合得来的同事的私人微信（别只留在企业微信里）
□ 如果有转正，确认Offer细节（薪资、入职时间、部门）

离职消息示例：
  "各位好，我的实习今天结束了。
   感谢大家这段时间的照顾，特别是XX（mentor）教了我很多。
   实习这段时间学到了很多，希望以后还有机会和大家一起工作。
   大家有需要我的地方随时联系我，我的微信是XX"
```

### 个人收尾

```
□ 更新简历（把你实习做的项目写上去，用STAR法则）
□ 请mentor/leader写一封推荐信（LinkedIn或背调用）
□ 把实习经历写成一篇技术复盘博客
□ 整理实习期间的技术笔记，归档到你的知识库
```

---

> 🎯 **最后的话：** 决定实习价值的，不完全是你在哪家公司，而是你在这2-3个月里做了什么、学到了什么、留下了什么。一个在中小厂核心项目里独当一面的实习生，简历含金量远远超过一个在大厂边缘部门打杂的实习生。记住一句话：**无论在什么环境里，主动的人总能找到成长的机会。**
