## 1. 分层模型与协议全景

OSI 七层与 TCP/IP 四层对应关系必背：**应用层（HTTP/DNS/FTP）→ 传输层（TCP/UDP）→ 网络层（IP/ICMP）→ 链路层（ARP/以太网）**。面试以四层为主，OSI 七层能说出"应用/表示/会话/传输/网络/数据链路/物理"即可，重点在**各层职责与协议归属**。经典例题：HTTP 是应用层、TCP 是传输层、IP 是网络层、ARP 是链路层——选错一个全错。

分层的好处一句话：**每层只解决自己的问题，改动互不影响**（比如传输层从 TCP 换 UDP 不用动应用层代码）。**数据封装**：发送方逐层加头（应用数据 → TCP 头 → IP 头 → 帧头尾），接收方逐层解封装——"路由器看 IP 头、交换机看 MAC 头、防火墙看传输层端口"这句实操认知加分。

## 2. TCP 三次握手与四次挥手

**三次握手**（建立连接，四报文）：客户端发 **SYN=1, seq=x** → 服务端回 **SYN=1, ACK=1, seq=y, ack=x+1** → 客户端发 **ACK=1, seq=x+1, ack=y+1**。为什么不是两次：**两次无法确认双方收发能力**——第二次后服务端知道客户端能发、自己能收，但不知道客户端能否收到自己的响应（丢包则服务端白等）；三次后双方确认"对方能收自己的包"。为什么不是四次：第三次已足够，第四次冗余。

**四次挥手**（关闭连接）：客户端 FIN → 服务端 ACK（半关闭，服务端还能发数据）→ 服务端数据发完 FIN → 客户端 ACK。为什么是四次不是三次：**TCP 全双工，两个方向的关闭独立**——ACK 与 FIN 被服务端的发送数据隔开，无法合并。

两个必背机制：**TIME_WAIT（主动关闭方进入，等 2MSL）**——为什么 2MSL：一是保证最后一个 ACK 能到达（丢了还能重发），二是让旧连接报文在网络中消亡（防止串扰新连接）；**SYN 洪泛攻击**（半连接队列被占满）——半连接/全连接队列（backlog）是深挖点。生产视角：高并发服务 TIME_WAIT 过多是常见问题（端口耗尽），调优用 `net.ipv4.tcp_tw_reuse` 与长连接池。

## 3. TCP 可靠性：滑动窗口与拥塞控制

TCP 可靠性五件套：**校验和、序列号与确认应答（ACK）、超时重传、滑动窗口（流量控制）、拥塞控制**。

**滑动窗口（流量控制）**：接收方通过窗口大小通告剩余缓冲区，发送方窗口内数据不用等确认连续发送——解决"发太快接收方缓存溢出"；窗口大小由接收方动态通告。

**拥塞控制（网络层视角）**四算法必背：**慢启动**（cwnd 从 1 指数增长到慢启动阈值 ssthresh）、**拥塞避免**（线性增长）、**快重传**（收到 3 个重复 ACK 立即重传，不等超时）、**快恢复**（ssthresh 减半，cwnd 从 ssthresh 线性增长）。**TCP 粘包/拆包**是面试爱问的工程题：TCP 是字节流无消息边界——解决靠**应用层协议定界**（长度前缀、分隔符、固定长度），Netty 的 LengthFieldBasedFrameDecoder 就是长度前缀方案。

## 4. TCP vs UDP

对比记忆：TCP **面向连接、可靠、有序、流量控制、拥塞控制、全双工字节流**；UDP **无连接、尽力而为、不可靠、无流量控制、数据报**。应用场景对应：TCP——HTTP/HTTPS、MySQL、Redis（默认）、文件传输；UDP——**DNS 查询（小报文一次往返）、音视频直播（可丢帧不可卡）、游戏实时对战、QUIC/HTTP3**。

选型思路（工程题）：**需要可靠交付与顺序用 TCP，实时性优先且可容忍少量丢失用 UDP**。追问"为什么直播用 UDP 不用 TCP"——TCP 的拥塞控制与重传在弱网下导致延迟不可控，丢一帧重传不如直接丢帧；再追问"那直播怎么保证质量"——**QUIC 的独立流 + 前向纠错 FEC + 自适应码率**。

## 5. HTTP 演进：1.1 到 3

**HTTP/1.1**：默认长连接（Connection: keep-alive）、管道化（pipelining，但队头阻塞严重，实际几乎不用）、Host 头支持虚拟主机。痛点：**队头阻塞**（一个请求慢全队等）、每次请求带冗余头（无压缩）。

**HTTP/2**：**二进制分帧**（替代文本协议）、**多路复用**（一个 TCP 连接并行多个流，逻辑层解决队头阻塞）、**头部压缩 HPACK**（静态表+动态表+哈夫曼）、**服务器推送**（Server Push——已废弃，Chrome 停用）。注意：**HTTP/2 仍存在 TCP 层的队头阻塞**（一个包丢失影响整条连接所有流）。

**HTTP/3**：基于 **QUIC（UDP 之上实现可靠传输）**——独立流（一个流丢包不影响其他流，彻底解决队头阻塞）、**0-RTT 握手**（首次 1-RTT、复用连接 0-RTT 建立）、连接迁移（网络切换不断连）。2026 采用数据：**HTTP/3 站点占比约 40%、流量约 21-34%**，HTTP/2 流量约 51-55%——答"目前主流是 HTTP/2，3 正在爬坡"即准确。

## 6. HTTPS 与 TLS 握手

HTTPS = HTTP + TLS（TCP 443）。**TLS 1.2 握手**（四次消息背熟）：① 客户端发 ClientHello（支持的加密套件、随机数 A）→ ② 服务端回 ServerHello（选定套件、随机数 B）+ 证书 → ③ 客户端验证证书（信任链 + 有效期 + 域名），生成**预主密钥**用证书公钥加密发回（RSA 密钥交换）→ 双方用 A + B + 预主密钥推导出会话密钥 → ④ 双方发 Finished 确认。

**TLS 1.3 的优化**（2026 加密流量中 TLS 1.3 占比约 70-73%）：握手从 2-RTT 降到 **1-RTT**（证书与密钥交换合并）、**0-RTT 恢复会话**（PSK）、移除 RSA 密钥交换（仅前向保密的 ECDHE，握手密钥即便被截获也无法解密历史流量）、仅保留 AEAD 加密套件（AES-GCM/ChaCha20）。**前向保密**概念必背：会话密钥由临时私钥参与推导，服务端长期私钥泄露不影响已记录流量。

## 7. 输入 URL 到页面展示全链路

全链路题是综合大题，按八步串讲：**① DNS 解析**（浏览器缓存 → 系统缓存 → 本地 hosts → 递归 DNS 服务器，A/CNAME 记录）→ **② 建立 TCP 连接**（三次握手）→ **③ TLS 握手**（HTTPS）→ **④ 发送 HTTP 请求**（方法、头、Cookie）→ **⑤ 服务端处理**（反向代理 → 应用 → 数据库/缓存）→ **⑥ 响应返回**（状态码、响应头）→ **⑦ 浏览器解析渲染**（HTML → CSSOM/DOM → 布局绘制，关键渲染路径）→ **⑧ 断开连接**（四次挥手或长连接复用）。

加分细节：DNS 缓存与 CDN 就近解析（CNAME 到 CDN 边缘节点）、TCP 连接复用（keep-alive）、HTTP 缓存（强缓存 Cache-Control/协商缓存 ETag）、渲染阻塞（CSS 阻塞渲染、JS 阻塞解析）。能把缓存与渲染细节说进去，本题从"会背"升到"真懂"。

### 追问速查

SYN 洪泛怎么防（半连接队列 + SYN Cookie）；HTTPS 为什么慢（握手 RTT + 加密开销，TLS1.3 缓解）；DNS 用 TCP 还是 UDP（通常 UDP 53，大响应切 TCP）；浏览器同域名并发连接数限制（HTTP/1.1 约 6 个，HTTP/2 多路复用无需）。
