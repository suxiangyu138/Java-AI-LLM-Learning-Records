## 1. 索引原理：为什么是 B+ 树

为什么用 B+ 树不用其他结构，是索引第一问，按对比链回答：**哈希索引**只支持等值查询（O(1)），不支持范围与排序——场景受限；**二叉树**退化成链 O(n)，且树高随数据增长；**B 树**每节点多路，矮胖，但叶子节点不形成有序链表，范围查询仍需中序遍历；**B+ 树**叶子节点全数据 + 有序链表，非叶子只存索引（一个 16KB 页能存上千个 key，树高 3-4 层即可支撑千万级数据），范围查询走叶子链表。**InnoDB 默认页大小 16KB，树高 3 层约 2000 万数据**——这个数字要背。

MySQL 8.4 现状：InnoDB 是唯一存储引擎（MyISAM 已退出舞台），支持降序索引与函数索引（8.0 起），8.4 默认 `mysql_native_password` 禁用、复制命令统一 SOURCE/REPLICA——答索引题不用再纠结 MyISAM 对比。

## 2. 聚簇索引与回表

**聚簇索引（主键索引）**：叶子节点存整行数据，一张表只有一个；**二级索引（普通索引）**：叶子节点存主键值。**回表**：走二级索引查到主键，再回聚簇索引查整行——多一次 IO。**覆盖索引**：查询列全部在索引里，无需回表——优化查询的头号手段（`SELECT id, name FROM t WHERE name = 'x'` 若 (name, id) 建了联合索引即覆盖）。

联合索引的最左前缀原理必背：**(a, b, c) 索引实际是 (a)、(a,b)、(a,b,c) 三个索引**——B+ 树按 a 排序，a 相同按 b，b 相同按 c，所以跳过 a 直接用 b 会失效。引申：**索引下推（ICP）**——5.6 起，二级索引过滤条件下推到引擎层，减少回表次数；**索引合并**——多个单列索引的 AND/OR 可能走 Intersection/Union 合并，但生产上更推荐联合索引。

## 3. 事务 ACID 与隔离级别

ACID 四性：**原子性**（undo log 回滚）、**一致性**（约束与业务规则，ACID 的核心目标）、**隔离性**（锁 + MVCC）、**持久性**（redo log 崩溃恢复）。事务四种隔离级别按"问题从有到无"记忆：**读未提交**（脏读）→ **读已提交**（脏读消除，不可重复读还在——同事务两次读不一致）→ **可重复读**（MySQL 默认，不可重复读消除，幻读部分解决——快照读无幻读，当前读靠间隙锁）→ **串行化**（全部加锁，性能最差）。

默认隔离级别是必考点：MySQL 默认**可重复读（REPEATABLE READ）**，而 Oracle 默认读已提交——为什么 MySQL 选可重复读：一是历史原因（binlog 复制模式下，读已提交 + 主从复制可能不一致，需要间隙锁保护）；二是配合 MVCC 快照读几乎无额外开销。

## 4. MVCC 与快照读

MVCC（多版本并发控制）是事务隔离的实现核心，答题链：**undo log 版本链 + ReadView 判断可见性**。每个行记录有隐藏列 trx_id（最近修改事务）与 roll_pointer（指向 undo log 版本链）；读操作时生成 ReadView（活跃事务列表 + 最大最小事务号），判断版本可见性：**版本事务小于最小活跃事务号 → 可见；大于最大事务号 → 不可见；在两者之间 → 看是否在活跃列表**。

快照读 vs 当前读是关键辨析：**快照读**（普通 SELECT）走 MVCC 不加锁，读历史版本；**当前读**（`SELECT ... FOR UPDATE` / UPDATE / DELETE / INSERT）读最新版本并加锁。可重复读下快照读无幻读，当前读用**间隙锁 + 记录锁组成的临键锁（Next-Key Lock）**挡住区间插入——这就是"可重复读下幻读被解决"的完整解释。

## 5. 锁机制与死锁

InnoDB 锁体系按粒度与模式记忆：**行锁**（记录锁 Record Lock、间隙锁 Gap Lock、临键锁 Next-Key Lock——左开右闭区间）、**表锁**（意向锁 IS/IX，用于表与行锁兼容性判断）、**自增锁**（插入自增时的特殊锁）。锁的兼容性速记：共享锁共享、排他锁全排斥。

**死锁四条件**（互斥/持有并等待/不可剥夺/循环等待）与处理：InnoDB 检测到死锁自动回滚一个事务（报 Deadlock found 错误），**innodb_deadlock_detect 默认开启**。生产防死锁六招：**固定加锁顺序、尽量小事务、走索引避免全表锁、控制并发度、拆分大事务、死锁重试机制**。加锁顺序不一致是最高频死锁根因——两个事务分别持有 A 锁请求 B 锁、持有 B 锁请求 A 锁，经典场景是转账 A→B 与 B→A 并发。

## 6. SQL 优化与索引失效

优化流程四步：**慢查询日志定位 → EXPLAIN 分析 → 针对性改写 → 回归验证**。EXPLAIN 关键列：**type**（性能从好到差：system > const > eq_ref > ref > range > index > ALL——ALL 即全表扫描，必优化）、**key**（实际用到的索引）、**rows**（扫描行数）、**Extra**（Using filesort 文件排序、Using temporary 临时表、Using index 覆盖索引、Using where 回表过滤）。

索引失效六大场景必背：**违反最左前缀**（跳列）、**对索引列使用函数或运算**（`WHERE YEAR(create_time)` 失效，函数索引可解）、**隐式类型转换**（字符串列传数字）、**LIKE 前置通配符**（`'%xxx'`）、**OR 连接非索引列**（需两侧都索引）、**not in / != 走索引条件苛刻**。优化实战套路：**深分页优化**（`LIMIT 100000, 20` 用延迟关联——先查主键再关联）、**JOIN 小表驱动大表**、**避免 SELECT \***（覆盖索引前提）、**EXPLAIN 看 type 到 range 以上**。

## 7. 主从复制与高可用

主从复制原理三线程必背：**主库 binlog 线程（写 binlog）→ 从库 IO 线程（拉取写 relay log）→ 从库 SQL 线程（重放）**。两种复制模式：**异步复制**（默认，主库不确认从库收到，丢数据窗口存在）、**半同步复制**（至少一个从库确认才提交，保丢窗口但降性能）。8.0 的并行复制（MTS，基于库或基于事务的并行）解决了传统主从延迟大头。

主从延迟四大来源与对策：**大事务**（拆分）、**DDL 慢**（pt-osc 在线变更）、**单线程 SQL 重放**（并行复制）、**从库查询压力大**（读写分离 + 分流）。延迟监控看 `Seconds_Behind_Master`（秒级口径，多线程复制下不完全准确）。高可用方案演进：MHA（已停维护）→ **MySQL InnoDB Cluster（Group Replication 组复制）**是 2026 主流方向；Keepalived + 主主虚拟 IP 是经典兜底。

## 8. 分库分表与生产选型

什么时候必须分：**单表数据量 > 2000 万或单表容量大、写入并发高、单库连接数吃紧**——但先做这三件事：索引优化、归档冷数据、读写分离，都顶不住再分。**分库**解决并发与连接压力，**分表**解决单表数据量；**垂直拆分**按业务域拆表/库，**水平拆分**按分片键（取模/范围/一致性哈希）拆表。**分片键选择是分库分表成败关键**——必须选查询最频繁的等值字段（用户 id、订单 id），否则跨片查询回天无力。

拆分后的三座大山：**跨片 JOIN**（冗余字段/应用层组装/全局表）、**分布式事务**（本地消息表/最终一致性）、**全局唯一 ID**（雪花算法/号段模式）。中间件选型 2026 口径：**ShardingSphere-JDBC**（客户端模式，性能好、侵入代码轻）与 **ShardingSphere-Proxy**（代理模式，对应用透明），MyCat 市场份额已萎缩。**先量级后拆分，没有万级数据不要分库分表**——这是面试最爱的"工程判断"题。
