## 1. 消息队列核心价值与选型

MQ 三大价值必背：**解耦**（上下游不互相依赖，A 发消息即可，B/C/D 按需订阅——新增消费者零改动）、**异步**（同步链路变异步，缩短响应时间——订单创建后发消息通知各系统）、**削峰填谷**（秒杀高峰流量先进队列，下游按处理能力消费，保护数据库）。代价也要答出来：**系统复杂度上升**（重复消费、消息丢失、顺序问题）、**最终一致性取代强一致**、**运维成本**。

四大 MQ 选型对比（2026 口径）：

| 中间件 | 定位 | 核心优势 | 弱项 |
|--------|------|----------|------|
| Kafka | 大数据/日志/事件流 | 吞吐最高（百万级）、分区并行、生态完善 | 吞吐强但功能弱（无延迟队列/死信弱） |
| RocketMQ | 业务消息 | 事务消息、延迟消息、死信队列完整，功能最全 | 吞吐低于 Kafka，文档一般 |
| RabbitMQ | 中小业务 | 功能丰富、路由灵活、社区成熟 | 吞吐瓶颈（万级） |
| Pulsar | 云原生新贵 | 计算存储分离、多租户、无 rebalance 痛点 | 生态与运维复杂度 |

选型思路一句话：**日志/流处理用 Kafka，业务消息（事务/延迟/死信刚需）用 RocketMQ，中小项目求稳用 RabbitMQ，云原生多租户考虑 Pulsar**。追问"为什么不用 RabbitMQ 做秒杀"——吞吐量级差一个数量级。

## 2. 消息可靠性：三段保障

消息可靠性按**生产 → 存储 → 消费**三段背：**生产端**：发送确认机制（Kafka 的 acks=all 等 ISR 全部确认、RocketMQ 的同步发送 + 重试）、失败重试 + 兜底落库（本地消息表定时扫描重发）；**存储端**：Kafka 多副本（副本数 3）+ 日志落盘（可配置）、RocketMQ 同步刷盘；**消费端**：**先消费后提交 offset（处理成功才 ack）**——但这也带来重复消费风险，所以消费端必须幂等。

经典框架"本地消息表"（最终一致性兜底）必背：业务操作与消息写入**同一个本地事务** → 定时任务扫描未发送消息重发 → 消费者幂等处理。追问"发消息失败了怎么办"——本地表 + 定时重发 + 失败告警；追问"重复发了怎么办"——消费幂等（见第 3 节）。

## 3. 消息顺序与幂等消费

**顺序消息**三场景必背：**全局顺序**（单分区 + 单消费者——吞吐牺牲，极少用）、**分区顺序**（Kafka 按 key 哈希到同一分区——订单维度顺序，主流方案）、**事务消息顺序保证**。追问"为什么 Kafka 只能分区级顺序"——分区内有序由 offset 保证，跨分区无法全局有序；RabbitMQ 单队列有序但多消费者失序。

**幂等消费**四方案：**唯一键 + 去重表**（消息带业务唯一键，消费前查库，已处理则跳过——数据库唯一索引兜底）、**状态机校验**（订单状态流转判断是否已处理）、**Redis SETNX**（短窗口去重）、**业务天然幂等**（update 语句本身幂等，扣库存要条件更新）。核心认知：**消息系统只能保证 at-least-once（至少一次），幂等是消费者的责任**——这句是面试官最想听到的总结。

## 4. 分布式事务方案全景

分布式事务四个层次由强到弱记忆：

**2PC/XA（强一致）**：准备阶段（prepare 锁定资源）+ 提交阶段（commit/rollback）——协调者单点、同步阻塞、性能差，工程上几乎不用裸 XA。**TCC（Try-Confirm-Cancel）**：业务级补偿——Try 预留资源（冻结库存）、Confirm 确认、Cancel 回滚（解冻）；优点：不锁资源、性能好；代价：**每个操作要写三个方法，侵入大**。**本地消息表/事务消息（最终一致）**：本地表定时补偿，或 RocketMQ 事务消息（半消息 + 本地事务确认 + 回查）；工程性价比最高，主流选择。**SAGA**：长事务按步骤执行 + 逆向补偿——适合流程长、链路明确的场景（订单全链路）。

2026 选型口径：**强一致场景用 Seata 的 AT 模式（自动补偿，基于 undo_log）或 XA；最终一致业务场景用事务消息/本地消息表**。追问"AT 模式和 TCC 区别"——AT 自动生成反向 SQL 无侵入，TCC 手写三方法灵活但侵入大。

## 5. CAP 定理与 BASE 理论

CAP 必背：**一致性 C（Consistency，所有节点同一时间看到同一数据）、可用性 A（Availability，每个请求都能收到响应）、分区容错性 P（Partition tolerance，网络分区下系统继续工作）**——**三者不可兼得，网络分区不可避免，所以实际是 CP 与 AP 二选一**。

分布式的本质：**在 P 前提下，网络分区发生时，你选择保证一致（拒绝部分请求，牺牲可用）还是保证可用（接受不一致，后续收敛）**。案例对照：ZooKeeper/etcd 是 CP（选举期间不可写），Eureka 是 AP（注册表最终一致），MySQL 主从复制是 AP（异步复制有延迟），Redis Cluster 主从故障切换窗口内 CP、平时 AP——答出这些实例立即拉满。

BASE：**Basically Available（基本可用）+ Soft state（软状态）+ Eventually consistent（最终一致）**——是 AP 路线的落地理论，最终一致性的实践（消息队列 + 幂等 + 补偿）。一句话总结：**CAP 告诉你选什么，BASE 告诉你怎么落地**。

## 6. 分布式 ID 方案

四大方案对比必背：**UUID**（本地生成零依赖，但无序、长、影响 MySQL 索引性能——B+ 树随机插入页分裂）、**数据库自增**（简单但单点、并发瓶颈）、**雪花算法 Snowflake**（**41 位时间戳 + 10 位机器 ID + 12 位序列号 = 64 位 long**，每秒单机 409.6 万 ID，趋势递增——主流方案）、**号段模式**（数据库批量取号段，应用内存分配——Leaf 的 segment 模式）。

雪花算法的坑必背：**时钟回拨**（时间回拨导致 ID 重复——解法：等待时钟追上/备用时钟/号段模式）、**机器 ID 分配**（手工配置 vs 注册中心）、**序列号溢出**（同毫秒超过 4095 等待下一毫秒）。追问"趋势递增对数据库友好吗"——比 UUID 好，long 有序插入 B+ 树更少页分裂；"为什么不用 Redis 生成"——可做，但引入新依赖且要处理持久化。

## 7. 接口幂等设计

幂等（Idempotent）定义必背：**同一个请求执行一次和执行多次，结果一致**。GET 天然幂等（查询），危险的是 POST（创建）与部分 PUT（扣款/转账）。**方案三件套**：① **唯一请求号 + 服务端去重**（前端/调用方生成 requestId，服务端查重表，重复直接返回首次结果）；② **数据库唯一约束**（订单号、流水号建唯一索引，重复插入报错转成功处理）；③ **状态机前置校验**（订单状态未支付才能支付，支付后状态变更，重复请求校验状态直接返回）。

设计要点：**幂等键要覆盖重试场景**（客户端重试、MQ 重复消费、支付回调重复通知）；**去重表与业务表同事务**（防去重成功但业务失败）；**Token 预生成**（下单前先取 token，提交时校验消费）。追问"幂等和防重有什么区别"——幂等是"结果一致"，防重是"只处理一次"，防重是幂等的实现手段之一。

## 8. 高频面试题与追问预案

### 基础概念档

| # | 题目 | 答题要点 |
|---|------|----------|
| 1 | 为什么用 MQ？ | 解耦/异步/削峰 + 代价（复杂度/最终一致） |
| 2 | CAP 定理？ | C/A/P 定义 / P 不可避免 / 实际是 CP vs AP |
| 3 | Kafka 为什么吞吐高？ | 顺序写磁盘 / 零拷贝 / 分区并行 / 批量 |
| 4 | 消息丢失怎么防？ | 生产 ack + 存储副本 + 消费先处理再提交 |

### 工程实践档

| # | 题目 | 答题要点 |
|---|------|----------|
| 5 | 重复消费遇到过？ | at-least-once 必然 / 幂等四方案 / 唯一键去重表 |
| 6 | 消息积压怎么办？ | 扩容消费者 / 临时紧急消费 / 积压分析定位消费慢原因 |
| 7 | 接口重复提交？ | 唯一请求号 / 数据库唯一约束 / 状态机前置校验 |

### 架构设计档

| # | 题目 | 答题要点 + 追问点 |
|---|------|------------------|
| 8 | 订单扣库存怎么保证一致性？ | 事务消息 + 幂等消费 / 状态机；追问"先扣库存还是先创建订单" |
| 9 | 秒杀系统怎么设计？ | 页面静态化 → 网关限流 → MQ 削峰 → 库存预扣；追问"超卖怎么防" |
| 10 | 分布式事务方案怎么选？ | 强一致 2PC/AT vs 最终一致事务消息 / 按业务容忍度 |

### 追问速查

RocketMQ 事务消息流程（半消息 → 本地事务 → 提交/回滚 → 回查）；雪花算法时钟回拨怎么解（等待/备用时钟）；Kafka 分区与消费者组关系（分区数 = 最大并行度）；CAP 里 P 可不可以选"不分区"（不能，分区是客观存在）。

> 🎯 **核心要点**：分布式题的通吃公式 = **为什么（价值与代价）→ 方案全景（从强到弱的谱系）→ 选型（业务容忍度）→ 兜底（幂等+补偿）**。面试官最看重"权衡意识"——能说出"强一致还是最终一致取决于业务"，比背出所有方案名字更值钱。
