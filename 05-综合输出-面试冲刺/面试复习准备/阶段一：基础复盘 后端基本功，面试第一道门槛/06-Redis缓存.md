## 1. 数据结构与底层编码

五大基本结构一句话用法：**String**（计数、缓存、分布式锁载体）、**List**（消息队列、最新列表）、**Hash**（对象存储——用户信息，节省内存且字段级操作）、**Set**（去重、交集并集——共同关注）、**ZSet**（排行榜、延迟队列——score 排序）。进阶结构：**HyperLogLog**（去重计数，12KB 存亿级基数）、**Bitmap**（签到、在线状态，位运算）、**Geo**（地理位置）、**Stream**（Redis 5+ 的可靠消息队列，消费组机制，8.x 已完善）。

底层编码是深挖考点：String 底层 SDS（简单动态字符串——O(1) 获取长度、二进制安全、预分配防频繁扩容）；ZSet 底层**跳表 + 哈希表**（跳表支持范围查询，哈希表 O(1) 查 score）——追问"为什么不用红黑树"（实现简单、区间遍历友好、平衡成本低）；List 3.2 后用 quicklist（ziplist 分段 + 双向链表）；Hash 小数据用 listpack，大数据转哈希表。

## 2. 持久化：RDB 与 AOF

**RDB**（快照）：fork 子进程全量生成二进制快照文件（写时复制 COW，父进程改动复制页）。优点：文件紧凑、恢复快、适合备份；缺点：**两次快照间数据丢失**、fork 大内存实例有停顿。**AOF**（追加日志）：记录每条写命令，fsync 策略三种（always 每命令刷盘最安全最慢、everysec 每秒默认、no 交给 OS）。优点：**最多丢 1 秒数据**；缺点：文件大、恢复慢（AOF rewrite 可压缩）。

选型口径 2026：**生产默认混合——RDB 做冷备与快速恢复 + AOF 做崩溃恢复兜底**；AOF 重写用 BGREWRITEAOF 子进程；数据可丢一点就 RDB 优先（缓存场景甚至可不持久化）。Redis 8.x 对 AOF 可靠性继续强化——面试答"默认 everysec + 混合持久化"即满分。

## 3. 过期删除与内存淘汰

过期删除策略三选一：**惰性删除**（访问时检查过期才删——不占资源但过期 key 残留）、**定期删除**（每秒抽查一批删——折中方案）、**Redis 用惰性 + 定期组合**（每次访问检查 + 主循环抽查，保证过期 key 不长期滞留又不过度消耗 CPU）。

内存淘汰八策略按"保底"记忆：`noeviction`（默认，写失败返回错误）、`allkeys-lru / volatile-lru`（LRU 最近最少使用）、`allkeys-lfu / volatile-lfu`（LFU 最不经常使用——8.x 生产首选）、`volatile-ttl`（淘汰快过期的）、`volatile-random / allkeys-random`（随机）。**面试口径：先区分 allkeys 与 volatile（全部 vs 只限带过期时间的），再对比 LRU/LFU 适用场景**（LFU 防"热点瞬时访问污染"）。

## 4. 缓存三大问题：穿透击穿雪崩

**缓存穿透**：查询**不存在的数据**，每次都打到 DB。解法三层：**缓存空值（设置短 TTL）→ 布隆过滤器拦截（8.x 集成模块化）→ 参数校验**。追问"布隆过滤器误判怎么办"——误判只放行不误拦，配合空值缓存兜底。

**缓存击穿**：**单个热点 key 过期瞬间**，大量请求直击 DB。解法：**互斥锁重建**（同一 key 只有一个线程查库回填，其余等待重试）、**逻辑过期**（不设物理 TTL，后台异步刷新）、**热点 key 永不过期 + 主动更新**。追问"互斥锁加在哪"——查 DB 前后加 SETNX 锁，注意锁粒度按 key。

**缓存雪崩**：**大量 key 同一时间过期**或 Redis 宕机，流量全压 DB。解法：**过期时间加随机抖动**（基础 TTL ± 随机数）、**多级缓存**（本地缓存 Caffeine + Redis 兜底）、**Redis 高可用**（集群 + 哨兵）、**限流降级**（DB 侧保护）。三大问题必须能对号入座——**穿透查不存在、击穿单个热点、雪崩批量过期**，一个词记错就是基础不牢。

## 5. 分布式锁的完整实现

Redis 分布式锁演进史必背：**SETNX + 手动 DEL**（简单但无法解决锁过期与误删——自己持有别人的锁）→ **SET key value NX EX 30 + Lua 校验释放**（正确姿势：加锁带唯一标识 value + 原子释放判断——`if get(key)==value then del(key)` 用 Lua 保证原子）→ **看门狗自动续期**（锁快过期时业务没跑完，定时续期——Redisson 的实现，默认 30s 锁自动续期）→ **RedLock 红锁**（多节点过半加锁，解决单点故障——但 2026 大厂口径：**工程上单 Redis + 看门狗已够用，RedLock 有争议且运维复杂**）。

必考题"锁过期了业务没执行完怎么办"：**续期机制 + 业务幂等 + 释放时校验唯一标识**三件套。追问"释放锁为什么用 Lua 脚本"——GET 与 DEL 非原子，中间插进别的线程释放。追问"Redis 锁与数据库乐观锁怎么选"——分布式多实例场景 Redis 锁，单库并发更新用乐观锁版本号。

## 6. 高可用：主从哨兵与集群

三层架构演进必背：**主从复制**（一主多从，读写分离，主写从读——解决读压力，不解决自动切换）→ **哨兵 Sentinel**（监控 + 自动故障转移 + 通知——主观下线/客观下线/选举新主，解决 HA，3 个哨兵起步）→ **Cluster 集群**（16384 个槽位，节点按槽分片，客户端用 CRC16(key) % 16384 定位；每个节点主从配对——解决容量与写入扩展）。

必考细节：**Cluster 的 16384 为什么不是更大**（心跳包槽位 bitmap 2KB，节点数上限 1000 量级，16384 在容量与性能间平衡）；**key 分散问题**（hash tag `{user:1}` 让相关 key 落同一节点支持事务与管道）；**集群模式不支持多 key 操作跨节点**（除非 hash tag）；**缓存场景 8.x 多线程 I/O 显著提升吞吐**。主从复制的新方向：Redis 8.4 支持**原子化 Slot 迁移**（CLUSTER MIGRATION，集群扩容缩容零停机，迁移提速最高 30 倍）——2026 面试提出来是明显加分项。

## 7. 缓存与数据库一致性

一致性问题是综合大题，答题框架：**先更新 DB 再删缓存（Cache Aside，主流）**——为什么不是先更缓存或先删缓存：先更缓存容易写失败或脏读；先删缓存 + 更库会因删除后立刻有人读旧值回填导致缓存长期脏。**Cache Aside 的并发竞态**：读请求读 DB 旧值 + 写请求先更库后删缓存，若删缓存发生在读回填之前，缓存被写回旧值——经典解决方案：**延迟双删**（删除 → 更新 → 延迟 500ms 再删一次）、**Binlog 订阅（Canal）异步删除**、**带版本号写缓存**（写缓存带上时间戳/版本，回填时校验）。

面试口径核心：**缓存一致性没有银弹，取决于业务容忍度**——强一致场景直接不用缓存；容忍最终一致用"DB 更新 + 缓存删除 + 消息补偿"；极端并发用双删 + 版本校验。能讲出"权衡"比背方案更重要。

### 追问速查
