## 1. 协议层：OpenAI 兼容与 Responses API

2026 年的事实标准：**OpenAI 兼容协议**（`/v1/chat/completions` 的 messages 格式）——DeepSeek、Qwen、vLLM、Ollama 全兼容，一套客户端代码跑遍各家。2026 年的新变量是 **Responses API**：OpenAI 2025 年推出、DeepSeek V4-Flash 原生支持，把"模型回复 + 推理状态 + 工具调用"统一到一个顶层结构中，简化多轮工具调用逻辑。面试答题姿势：先说兼容协议是事实标准（切换成本最低），再说 Responses API 是生态演进方向（工具循环更干净），最后补一句工程判断——**协议认 OpenAI、能力看需求，生产环境自己封装一层统一抽象**，换模型只改配置不改代码。

## 2. 流式响应：SSE 与增量拼接

大模型 API 的非流式调用等待全量生成，动辄数十秒；流式（SSE）按 token 逐块返回，首字延迟（TTFT）大幅下降，是对话应用的标配。必背的工程细节：**流式返回的是增量不是全量**——每条 `data:` 块带一个 `delta`，客户端要自己按角色拼接（多轮对话还要把完整回复存下来回传给下一轮）；**工具调用要跨块组装**——工具参数是 JSON 字符串，被切成多个 chunk，要等 `finish_reason=tool_calls` 或 `arguments` 结束标记才能解析，中途解析必然报错；**要处理三条流**——内容流、工具调用流、推理模型（如 DeepSeek V4 系列）的思考流（reasoning_content 要回传，否则下次请求 400）。追问"流式为什么快"——不是生成快了，是把等待拆碎，用户体感首字快；后端吞吐一样，流式是体验优化不是性能优化。

## 3. 超时重试与幂等

大模型 API 是外部依赖，必配三层重试：**连接超时**（短，3-5s，服务不可达快速失败）、**读超时**（长，按任务估——流式请求读超时要比非流式更长，因为首字可能慢）、**总超时**（兜底防挂死）。重试策略：指数退避 + 抖动（base × 2^n + random），配合 **429 重试**（服务端限流，尊重 Retry-After）、**5xx 重试**、**4xx 不重试**（参数错误重试也没用）。幂等的正确姿势：**把重试与幂等分开**——HTTP 层重试只用于"请求没被处理"的不确定场景；业务幂等靠请求 ID 或业务键去重，因为模型调用可能"生成了但响应丢了"，直接重试会重复扣费与重复副作用。2026 加分点：工具调用场景（见 04 篇）的错误处理——工具执行失败要转成错误消息回传给模型继续决策，而不是简单重试整个调用链。

## 4. 并发与限流

并发控制三件事：**并发上限**（semaphore 限住并发请求数，防打爆供应商配额与本地资源）；**流控**（令牌桶限 QPS——OpenAI/DeepSeek 按 RPM/TPM 计限，超出 429）；**队列与背压**（请求排队 + 超时丢弃，而不是无限积压）。工程落点：Java 用 Semaphore/Guava RateLimiter、Python 用 asyncio.Semaphore；批量场景（知识库向量化）用并发池 + 分批提交 + 失败重试队列。面试常问"并发 1000 怎么办"——答：客户端限流是底线，真正扩容靠供应商配额与多 key 轮换，或自建网关层统一治理（LiteLLM Proxy 这类网关做统一限流、虚拟 key、成本统计，2026 年已是中大型团队的标配）。

## 5. 成本治理：Token 计量与模型分层

成本 = 单价 × token 数，治理三板斧：**计量**（每次调用记录 input/output/cache token 数，按会话与用户累计，超标告警）；**模型分层**（简单任务走便宜小模型——摘要用 Flash、复杂推理用 Pro，7B 能完成的别上 70B，模型选型本身就是最大降本项目）；**缓存**（Prompt Caching 见下节 + 工具结果缓存：幂等查询类工具按参数做 TTL 缓存，非幂等写操作绝不缓存）。2026 数据：调优良好的缓存组合在高流量 Agent 上可降 **50-90% 成本**；缓存命中 input token 约 50% 折扣，Anthropic 读缓存再降 90%。面试表达：先给公式再给手段，最后给治理闭环——成本是工程指标，要监控、要告警、要复盘。

## 6. Prompt Caching：稳定前缀工程

2026 年最值钱的 API 工程知识。原理：**供应商按请求前缀复用 KV Cache，前缀字节完全不变才命中**。工程化纪律五条：**稳定前缀**（system 指令、工具列表放在最前，会话中绝不改写）；**易变内容隔离**（每次变化的知识库内容、环境上下文追加到消息末尾，用明确的标记包裹，不污染前缀）；**工具列表稳定排序**（在注册处统一按名字排序，工具集合相同但顺序变了就会全 miss——这是最隐蔽的缓存杀手）；**配置变更只追加**（权限升级、参数调整渲染成新消息追加，绝不改历史）；**压缩历史显式触发**（历史摘要重写前缀必然破缓存，触发阈值设在输入占用约 70% 时，并视为新前缀起点）。配套监控：用 `cache_read_input_tokens / (cache_read + cache_creation + prompt_tokens)` 算命中率，低于 50% 排查提示词或工具是否在变。自托管侧同理：vLLM Automatic Prefix Caching 按内容哈希共享块，共享 system prompt 可降 TTFT 60-80%。

## 7. 多模型适配与切换

多模型时代三个痛点：**切换成本**（各厂商协议与字段略不同）、**Key 管理**（多供应商密钥散落）、**成本不可见**（各家计费口径不一）。解法：统一适配层（自己封装 ChatClient 抽象）或现成网关（**LiteLLM Proxy** 是 2026 事实标准：一个 OpenAI 兼容端点管理 100+ 供应商，虚拟 key 做权限与预算、路由做 fallback、成本统计内建）。面试加分点：**fallback 策略**（主模型 429/5xx 自动切备用供应商，生产双供应商是标准配置）、**能力探测**（国产兼容 ≠ 同能力，上线前用探针验证工具调用与推理行为）、**灰度切换**（新模型先小流量，靠评估门禁（09 篇）决定全量）。回答"为什么要多模型"——供应商限流与故障、成本分层、能力互补（推理 vs 快速）、合规（数据出境）。
