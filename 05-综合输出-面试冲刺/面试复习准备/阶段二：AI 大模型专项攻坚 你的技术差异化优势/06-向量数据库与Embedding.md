## 1. Embedding：把语义变成坐标

Embedding（嵌入）一句话：**把文本映射成固定维度的向量，让语义相近的文本在向量空间里距离更近**。关键心智：这不是哈希，是深度学习学出来的语义空间——"苹果"与"水果"的向量距离远小于"苹果"与"榴莲炸弹"，同一 Embedding 模型下"F=ma"与"牛顿第二定律"可以落在相邻位置，这是 RAG 能理解语义等价的基础。三个常问点：**维度**（384/768/1024/1536/3072，维度越高信息量越大但存储与计算成本越高，2026 年实用甜点区是 1024 附近，多数应用不需要追最高维）；**相似度度量**（余弦相似度最常用，向量归一化后余弦等价于点积；L2 距离、内积各有用武之地，索引时要选对度量并保持查询一致）；**与词向量（Word2Vec）的区别**（词向量是静态词级，Embedding 是上下文相关的句级——同一词在不同句子中向量不同）。

## 2. Embedding 模型选型与使用铁律

2026 年主流模型一句话速览：**bge-m3**（BAAI，1024 维，多语言 + 同时支持稠密与稀疏向量，开源首选）；**text-embedding-3 系列**（OpenAI，API 托管，1536 维起）；**GTE/Qwen-Embedding**（国产开源，中文强）；**all-MiniLM**（384 维，轻量，原型验证用）。选型逻辑：**语言覆盖（中文场景优先国产模型）→ 维度与成本 → 领域微调空间**（垂直领域（代码、医疗、法律）可以微调 Embedding 模型，2026 年在线教育等行业已有微调提升检索命中率的实践）。

两条铁律背熟：**① 入库与查询必须用同一个 Embedding 模型**——不同模型的向量在不同空间，相似度分数无意义，这是生产事故第一来源；**② 模型升级要做全量重索引**——换了新模型旧向量全部失效，要设计离线重算任务。工程细节：文本长度裁剪（超长先分块再嵌入）、批量嵌入限流（向量化是 API 密集操作）、向量与原文同库存储（原文、向量、元数据一条记录，查出来直接用）。

## 3. 向量检索原理：从暴力扫描到 ANN

面试必问"向量检索为什么快"——答案分层：**暴力扫描（FLAT）** 逐一比对全库向量，百万级 1536 维下延迟数百毫秒级，不可接受；**ANN 近似最近邻**牺牲可控的召回率换数量级性能提升，2026 年三大族：**HNSW**（图索引，查询最快、召回率最高 95-99.5%，但图驻留内存、内存占用高）；**IVF**（倒排分桶，先聚类粗筛再桶内精扫，内存友好但召回略降，IVF_PQ 量化后内存再降 90%）；**DiskANN**（磁盘索引，十亿级冷数据场景）。面试答题公式：**暴力扫描基准 → ANN 三族各一句话 → 给一个实测数据**——"HNSW 配置 ef=64 时千万级向量 Top-10 检索 P99 约 15-35ms、召回率 94-98%"这类数据会显著加分。

## 4. HNSW：生产默认的图索引

HNSW（分层可导航小世界图）是 2026 年生产默认索引，原理一句话：**构建多层图，高层稀疏快速导航接近目标区域，底层稠密精确收敛到最近邻**——像地图先到城市再到街道。三个参数背熟：**M**（每个节点的连接数，32/64 常见，越大图越稠密、召回越高、内存越大）；**efConstruction**（建图质量，200 左右常见，影响召回上限）；**ef**（查询深度，**查询时动态调**——ef 越大越准越慢，生产用 ef=64 附近换毫秒级 98% 召回）。内存账本要会算：**1000 万条 1024 维向量 HNSW 约需 40GB 内存**——面试问"亿级向量怎么部署"答"内存不够上 DiskANN 或 IVF_PQ 量化，或分片"。注意 HNSW 是"建了图就记住"的结构，**海量增删场景要预留重构空间或换索引策略**。

## 5. 主流向量数据库横向对比

| 产品 | 语言/定位 | 强项 | 短板 | 适用 |
|------|----------|------|------|------|
| Milvus | Go/分布式 | 亿级规模、存算分离、10+ 索引、GPU 索引、混合检索、多租户 | 依赖 etcd/MinIO/Pulsar 多组件，运维重 | 中大型团队、亿级生产 |
| Qdrant | Rust/单二进制 | 过滤在图中直接生效、P99 8ms、部署轻 | 生态与规模验证弱于 Milvus | 中小团队、高过滤场景 |
| Chroma | Python/SQLite | 零配置上手、原型最快 | 百万级后瓶颈 | 10 万级以下原型 |
| FAISS | 库非数据库 | 极致性能、灵活 | 无分布式无高可用，自己造轮子 | 离线/单机检索 |

面试答题姿势：先给"向量库本质 = 检索引擎 + 存储 + 高可用"，再说选型看三点——**规模**（十万级 Chroma 够了，亿级必须 Milvus）、**运维能力**（Milvus 分布式组件多，没有专职运维选 Qdrant）、**业务特性**（高过滤场景 Qdrant 的图内过滤占优）。2026 加分：Milvus 2.4 起支持 GPU 索引构建（十亿级索引小时级→分钟级）、3.0 探索流式向量计算；向量库与 PostgreSQL（pgvector）、ES（向量检索）的竞争关系也要能聊——**专业向量库胜在高性能与混合检索，数据库内置胜在运维简单**。

## 6. 混合检索：稠密-稀疏-标量三位一体

2026 年生产标配，一句话定义：**稠密向量（语义）+ 稀疏向量/BM25（关键词）+ 标量过滤（元数据）** 三者组合，各自解决对方的盲区：稠密向量语义强但精确词匹配弱（"F=ma"能查到"牛顿第二定律"但精确 ID 查不准）；BM25 精确匹配强但不懂语义；标量过滤做硬条件（时间范围、部门、价格区间）精准剪枝。实现形态：Milvus 内置 BM25Function 自动生成稀疏向量 + 原生 Reranker 合并两路结果重排；或用 Elasticsearch 的混合查询。工程姿势：**先过滤后检索**（元数据硬过滤收窄候选集再向量检索，电商推荐场景过滤效率提升数倍）；**两路结果合并策略**（RRF 倒数排名融合或加权，Reranker 精排收尾）。面试一句话总结：**"语义召回 + 精确召回互补，元数据硬约束，Reranker 统一精排"**——这 18 个字背熟，混合检索题必过。

## 7. 选型决策树

按问题形态选：**精确 ID/关键词查询多 → 传统数据库或 ES 就够，别上向量库**；**十万级原型 → Chroma/pgvector**；**百万-千万级生产 → Qdrant（轻）或 Milvus（全）**；**亿级 + 多租户 + GPU 索引 → Milvus 分布式**；**离线批处理 → FAISS**。配套决策：**Embedding 模型选语言覆盖最强的开源模型（bge-m3），维度选 1024 甜点**；**索引默认 HNSW，内存不够换 IVF_PQ/DiskANN**；**必须上混合检索**（2026 年不再是可选项）；**冷数据分层**（热数据内存索引、冷数据 DiskANN 磁盘索引）。追问预案："向量库和 Redis 向量搜索比呢"——Redis 胜在简单与低延迟场景（万级），专业库胜在索引质量与混合检索。
