## 1. 为什么需要 RAG

RAG（检索增强生成）的动机一句话：**把外部知识在生成前塞进上下文，让模型"有据可依"地回答**。它解决四个问题：**知识时效**（模型知识有训练截止，RAG 注入最新数据）；**私有数据**（企业内部数据不在训练集）；**幻觉**（回答有检索来源兜底，忠实度大幅提升）；**成本与可控**（相比重新训练，更新知识只换索引，改一条数据实时生效）。定位辨析：RAG 不改变模型能力，只改变模型的"输入"——所以"模型不会的东西"（新语言、新格式能力）RAG 解决不了，那是微调的事。2026 加分视角：RAG 的演进方向是"检索即能力"——不只喂文本，还通过 MCP 触发工作流、操作业务系统，从"回答问题"升级为"参与流程"（Agentic RAG，见第 5 节）。

## 2. 五步架构：从文档到答案

标准管线五步背熟：**① 加载**（源文档：PDF/网页/数据库/API）；**② 分块**（长文档切 chunk，策略见下节）；**③ 嵌入**（每个 chunk 用 Embedding 模型转成向量，入库时同时存原文、向量与元数据）；**④ 检索**（用户查询转向量，在向量库做近似最近邻召回 TopK）；**⑤ 生成**（把"问题 + 召回片段"拼进提示词，让模型基于片段回答并标注来源）。两个常被问的细节：**检索要带上元数据过滤**（时间、部门、文档类型做硬过滤，比纯向量精准——混合检索见 06 篇）；**生成时的引用溯源**（答案标注来自哪个片段，是忠实度可验证的前提，也是降幻觉的工程手段）。整条链路的延迟预算：检索毫秒级、生成秒级，瓶颈永远是生成段。

## 3. 分块策略：质量的第一道关口

分块是 RAG 最容易被忽视但影响最大的环节，三个问题必答：**多大**——256-512 token 是 2026 年多数文档与问答场景的甜点区：太大则块内噪音多、检索精度降；太小则上下文断裂、语义不完整；**怎么切**——按结构切（标题、段落、代码块）优于纯长度切，保留块间少量重叠（15% 左右）防边界截断；**块要带上下文**——把标题/章节路径作为元数据随块存储，检索后拼回给模型（"第 2 章 3.1 节"让模型理解块在文档中的位置）。进阶策略（答加分）：**语义分块**（按语义边界切，2026 年主流）、**父子块**（检索小块、生成拼父块上下文）、**问题导向分块**（把段落改写成"问答对"格式存储，检索命中率更高）。追问"分块怎么评估好坏"——不单独评，看端到端检索命中率与答案忠实度（07 节评估）。

## 4. 检索与重排序

检索两阶段：**召回**（粗筛，向量 TopK——召回要"多取"保证不漏，TopK 常见 20-50）；**重排**（精排，用 Cross-Encoder 对召回的 20-50 条逐条算"与问题的相关度"，取 TopK 5-8 条进上下文）。为什么召回后必须重排：向量检索（Bi-Encoder）把问题和文档各自编码再算相似度，快但粗；Cross-Encoder 把"问题+文档"拼在一起深度交互编码，准但慢——所以两级配合，用召回的数量换重排的质量。重排的工程注意：**重排模型要单独选**（bge-reranker 等，与 Embedding 模型不同）；**重排结果不进向量库，只影响当前请求**；重排的延迟要压（20 条 ≈ 几十毫秒）。2026 加分：混合检索（稠密向量 + BM25 稀疏 + 元数据过滤）已是生产标配，Milvus 原生集成稀疏向量与 Reranker（详见 06 篇）。

## 5. RAG 演进谱系：经典-高级-Graph-Agentic

按演进顺序答，展示"知道 RAG 不是一成不变"：**经典 RAG**（朴素五步，单轮检索，简单但召回差）；**高级 RAG**（查询改写、混合检索、重排、上下文压缩——生产主流形态）；**GraphRAG**（把文档构建成知识图谱再检索——擅长多跳关系问题（"A 和 B 有什么间接关系"），2026 年与向量检索配合使用，构建成本高是主要代价）；**Agentic RAG**（2026 年主导范式：把检索变成 Agent 的工具——多轮追问、自动选择知识库、检索后触发业务动作，检索通过 MCP 暴露为可复用能力）。答题姿势：先给谱系，再说生产选型——"单轮知识问答用高级 RAG 就够了，多跳关系用 GraphRAG，需要多轮决策与动作执行才上 Agentic RAG"，**别一上来就 Agent 化，简单场景固定管线更便宜更稳**。

## 6. 失效模式与排查三板斧

"RAG 效果差"的排查顺序是最有价值的工程题：**三板斧从链路末端往回查**——① 生成段：检索到的片段明明正确但答案错（提示词问题、片段拼接不当、模型不强）；② 检索段：答案不对先看 TopK 召回里有没有正确答案（没有→分块与向量问题；有但排在后面→重排与阈值问题）；③ 入库段：知识库质量（脏数据、重复文档、embedding 模型不一致——**入库与查询用了不同 Embedding 模型是最常见的低级事故**）。三大高频病根：**分块把答案切断了**（答案跨块，加重叠与父子块）；**问题与文档说法不一致**（"F=ma"查"牛顿第二定律"，靠查询改写与同义扩展）；**检索噪声淹没信号**（TopK 太大、无关片段进上下文，压缩上下文或调低阈值）。2026 新病根：**评估裸奔**——没有忠实度指标，自信的错误答案最危险（见下节）。

## 7. RAG 评估与长上下文之辩

评估两段拆：**检索段用 IR 指标**（Recall@k、MRR、Hit Rate——需要人工标注"正确文档是哪个"）；**生成段用 RAGAS 四指标**（Faithfulness 忠实度——答案声明是否被检索片段支持、Answer Relevancy 相关性、Context Precision 精准率、Context Recall 召回率；其中忠实度最关键，抓"基于错误上下文自信编造"）。典型阈值：忠实度 ≥ 0.85-0.95、相关性 ≥ 0.85。评估必须拆两段定位问题：答案差可能是检索拖后腿而不是提示词问题（详见 09 篇）。

**长上下文之辩**（2026 年最高频争议）：1M 上下文都出来了，RAG 是不是要死？正确答案：**不会**。三个理由——**装不下**：企业知识库亿级 token，任何窗口都放不下；**找不准**：窗口只保证"能看到"，不保证"看到对的"，百万 token 里找一条关键信息正是向量检索的活；**付不起**：全量送上下文成本与延迟线性涨，检索只送 TopK 片段是数量级的省钱。补充一个反方视角显示思辨：单文档超长场景（一本书、一份完整年报）确实直接喂长上下文更简单，RAG 与长上下文是互补不是替代——**检索解决"哪里找"，窗口解决"装不装得下"**。

### 追问速查

挑 3 条背熟：TopK 取多少（召回 20-50、重排后进上下文 5-8，随业务调）；GraphRAG 什么时候用（多跳关系查询，构建成本高）；Agentic RAG 与普通 RAG 区别（检索变工具、多轮决策、可触发动作）。

> 🎯 **核心要点**：RAG 题满分答案 = 五步架构 + 一个排查案例 + 一个评估数据。如"五步管线（架构）→ 线上答案差，先从生成段查到检索段，发现是 Embedding 模型入库查询不一致（案例）→ 之后加忠实度门禁 0.9 才放行（评估）"。排查三板斧与长上下文之辩是本篇背诵重点。
