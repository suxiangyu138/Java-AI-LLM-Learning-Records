# 02 - 提示词工程与模型能力边界

## 1. 提示词工程还有没有用

2026 年模型变强了，提示词工程的价值也变了，但没消失：**它从"教会模型做复杂任务"降级为"说清任务边界与输出格式"**。面试官问"提示词工程是不是快被淘汰了"，高分答案是承认变化再给出新的落点：强模型自己会写思维链，人肉 CoT 收益下降；但结构化输出约束、角色与上下文隔离、few-shot 示例校准格式，仍然是大模型应用上线前必须做的工程动作。2026 年的新趋势是把提示词交给"系统提示词版本管理"——提示词是代码的一部分，走 CI/CD、有版本、有灰度、有回滚，这正是 09 篇评估门禁的输入。

## 2. 结构化提示词四要素

一套能背的骨架：**角色 + 任务 + 约束 + 输出格式**。角色（"你是资深的数据库运维工程师"）设定领域知识与回答口吻；任务一句话说清目标（"根据给定的慢查询日志，给出索引优化建议"）；约束写死边界（"只基于给定的日志回答，不要编造执行计划""不确定时明确说不知道"）；输出格式锁定解析（"按 JSON 输出：{suggestion, reason, risk}"）。加分细节：**复杂任务拆步骤**（"先分析表结构与查询模式，再给建议"）；**给正反例**（"正确示例：... 错误示例：..."）；**关键内容放开头结尾**（长提示词中模型对中间内容注意力弱）。

工程提示：提示词里不要放会变化的大块内容（如每次不同的知识库文本）——那部分应该走 RAG 动态注入，静态提示词保持稳定还能吃到 Prompt Caching 的缓存红利（见 03 篇），这是 2026 年"提示词设计"与"成本设计"耦合的新考点。

## 3. Few-shot 与思维链 CoT

**Few-shot（少样本）**：给 2-5 个"输入-输出"示例让模型模仿格式与推理路径。示例的选择讲究：覆盖边界情况、与真实输入同分布、示例本身必须正确（模型会模仿错误）。2026 年的变化：强模型对 few-shot 的依赖下降，但**输出格式校准仍靠它**——示例比文字描述更有效地锁死 JSON 结构。

**CoT（思维链）**：让模型"先推理后给答案"，复杂任务准确率显著提升。2026 年的正确说法是分层：**普通模型要提示词引导 CoT**（"请一步步思考"或给推理示例），**推理模型（DeepSeek V4 系列、Claude 5 等）自带思考过程**，不需要提示引导——反而要提示它"直接给结论"来省 token。追问"CoT 的原理"——多步推理把问题分解成中间步骤，每步的计算在上下文里显式可见，减少了"一步到位"的注意力偏差；代价是 token 成本上升、延迟变长。

## 4. 幻觉：成因与缓解

幻觉是 AI 面试必问题。成因三层：**训练层面**（模型学的是统计规律，知识有截断日期且记忆不可靠）；**生成层面**（自回归逐 token 采样，高置信但错误的内容也会被顺滑地生成出来）；**场景层面**（提示词诱导编造、检索不到还硬答）。缓解按代价从小到大排序：**提示词约束**（"只基于给定材料回答，不确定说不知道"——治标）、**RAG 接地**（把事实来源塞进上下文，回答有据可依——治本）、**评估兜底**（RAGAS 忠实度指标 + 引用溯源，让幻觉在门禁处被拦下——工程闭环，见 09 篇）。2026 新视角：架构级降幻觉——DeepSeek V4 的 Engram 条件记忆模块把静态知识存储与动态神经计算分离，通过外部记忆库显著降低幻觉率，这是"记忆外置"路线（与 RAG 同源）进入模型架构的信号。

## 5. 模型能力边界清单

面试官问"模型的局限是什么"，按三层答：**知识边界**（训练数据有截止时间、私有数据与实时数据不知道——用 RAG 与工具调用补）；**能力边界**（精确数学与多步逻辑仍会错、长文本中间的细节会丢、格式稳定性不够——用代码与工具算、用结构化输出约束）；**成本边界**（token 计费、延迟、幻觉风险——用模型分层与小模型兜底）。加分表达：**每个边界都要给出工程对策**，这直接展示"工程视角"——"知识有时效→接搜索工具；算数不准→接计算器；格式不稳→上 JSON Schema 校验"。

## 6. 长上下文的陷阱

2026 年上下文已到百万级，"长上下文是不是不需要 RAG"成了高频题。必背三个陷阱：**lost in the middle**——模型对长文本中间位置的信息记忆最差，关键内容要放开头与结尾；**成本与延迟线性涨**——每次请求全量送上下文，1M 上下文请求的价格与首字延迟都远超短请求；**无关信息的干扰**——塞入大量无关内容会稀释注意力、降低答案质量。由此得出面试结论：**上下文窗口是"能力上限"而不是"推荐用量"**，长上下文适合"完整文档问答"与"多轮 Agent 会话"，但知识库检索仍然要 RAG——检索精度与成本是窗口解决不了的。

## 7. 提示词 vs RAG vs 微调：选型决策树

这是 2026 年最高频的架构选择题，决策树一句话背熟：**改行为方式用提示词（快、零成本）→ 改知识来源用 RAG（动态、可更新）→ 改模型本身用微调（风格、格式、专业能力）**。展开说：提示词适合约束输出格式、设定角色、给规则；RAG 适合私有知识、实时知识、大知识库（知识变了不用重新训练，改索引即可）；微调适合固定输出风格（客服口吻、报告格式）、领域术语与专业格式、用少量高质量数据提升特定任务准确率。边界与陷阱：提示词无法注入大知识量（上下文放不下、也贵）；RAG 解决不了"模型不会的东西"（新能力要微调或换模型）；微调改不了知识（微调是学行为，知识仍靠训练数据与 RAG）。三者可组合——最标准的 2026 生产组合是"微调格式 + RAG 知识 + 提示词串联"。

## 8. 高频面试题与追问预案

### 基础概念档（30-60 秒作答）

| # | 题目 | 答题要点 |
|---|------|----------|
| 1 | 提示词工程核心要素？ | 角色-任务-约束-输出格式 / 拆步骤 / 正反例 / 关键内容首尾 |
| 2 | Few-shot 怎么选示例？ | 与真实输入同分布 / 覆盖边界 / 示例必须正确 / 2-5 个足够 |
| 3 | CoT 是什么？ | 先推理后作答 / 普通模型提示引导 / 推理模型自带 / 成本上升 |
| 4 | 幻觉的成因与缓解？ | 三层成因（训练-生成-场景）/ 缓解：约束→RAG→评估兜底 |

### 工程实践档（"我遇到过 → 怎么定位 → 怎么修"）

| # | 题目 | 答题要点 |
|---|------|----------|
| 5 | 模型总答非所问怎么办？ | 查提示词是否够具体 / 加 few-shot 校准 / 拆任务步骤 / 换成结构化输出 |
| 6 | 回答格式不稳定无法解析？ | JSON Schema 约束 / 示例校准 / 解析失败重试一次 / 不行就走兜底流程 |
| 7 | 知识库问答答错？ | 先测检索（TopK 有没有对）再测生成 / 补 RAG 上下文 / 忠实度评估 |

### 架构设计档

| # | 题目 | 答题要点 + 追问点 |
|---|------|------------------|
| 8 | 提示词、RAG、微调怎么选？ | 行为→提示词 / 知识→RAG / 能力与风格→微调 / 可组合；追问"微调能补知识吗"（不能，行为工具） |
| 9 | 长上下文了还要 RAG 吗？ | 要——窗口解决装得下，不解决找得准与付得起；追问"什么场景直接用长上下文"（整文档问答） |

### 追问速查

挑 3 条背熟：推理模型要不要提示词引导思考（不要，它自带 CoT，反而要提示"直接给结论"省 token）；提示词与成本怎么耦合（静态稳定前缀吃 Prompt Caching 缓存红利）；模型怎么"知道自己不知道"（它不会——所以靠 RAG 接地 + 评估门禁，不靠模型自觉）。

> 🎯 **核心要点**：提示词题满分答案 = 骨架 + 一个调优案例 + 一个边界。如"结构化提示词四要素（骨架）→ 生产里给 JSON 输出加 few-shot 校准后解析成功率从 70% 到 98%（案例）→ 但提示词救不了幻觉，要 RAG 接地（边界）"。本模块的选型决策树是 9 篇里最值得背的一张图。
