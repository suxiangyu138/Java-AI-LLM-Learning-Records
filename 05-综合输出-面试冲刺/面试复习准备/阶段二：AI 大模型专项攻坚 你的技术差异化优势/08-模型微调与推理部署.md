## 1. 微调 vs RAG vs 提示词：决策树

面试官问"什么时候需要微调"，决策树背熟：**知识问题 → RAG**（私有知识、实时知识，更新只换索引）；**行为与风格问题 → 微调**（固定输出格式、领域口吻、专业术语、特定任务准确率）；**规则与格式问题 → 提示词**（约束输出、角色设定，零成本）。微调的正确使用姿势要强调：**微调是学行为不是学知识**——知识仍靠训练数据与 RAG，微调把"怎么答、什么风格、什么格式"固化进模型；**微调前先问三个问题**——RAG 能解决吗？提示词能解决吗？训练数据质量够吗？三个都不行才微调。2026 年务实视角：小模型微调是"省钱路线"——用 QLoRA 把 7B 小模型微调到专精任务，替代每次调贵 API 的通用大模型，是 2026 年成本治理的主流手段之一。

## 2. LoRA 原理与参数

LoRA（低秩适配）一句话原理：**冻结原模型全部参数，只训练注入的低秩矩阵补丁**——权重更新 ΔW 被分解成两个小矩阵 A×B（低秩分解），训练时只更新 A/B，推理时 W + A×B 合并。收益三个数据背熟：**可训练参数减少到原来的 0.1% 量级（几十 MB 适配器）**；单卡就能训大模型；适配器即产品（不同任务训不同适配器，推理时热切换，不用存多份模型）。关键参数：**rank（r）**——容量调节旋钮，8-32 常见，太小欠拟合、太大浪费且易过拟合；**alpha**——缩放系数，常见是 r 的 2 倍；**target_modules**——作用在哪些层，实践建议覆盖所有线性层（不只注意力 Q/V），持续缩小与全量微调的差距，这个选择比优化器更影响质量。追问"LoRA 为什么有效"——微调的权重变化通常分布在低秩子空间，低秩分解足以表达任务更新。

## 3. QLoRA 与数据准备

QLoRA = LoRA + 4bit 量化底座：**冻结的基座模型量化到 4bit（NF4），训练适配器保持高精度**——单张 RTX 3090 微调 70B、4bit QLoRA 微调 7B 仅需约 6GB 显存。核心细节：**量化只作用于被冻结的底座，可训练的 A/B 矩阵与梯度必须高精度**——量化适配器会破坏训练信号；paged optimizer 把优化器状态溢出到 CPU 应对显存尖峰。2026 年标准流水线：**QLoRA 4bit + SFT → DPO 两阶段**（先教行为后对齐偏好），工具链 LLaMA-Factory 零代码 CLI/Web UI 覆盖 100+ 模型、ms-swift 全流程、Unsloth 加速 2 倍省 50% 内存。**数据质量是微调的天花板**：数量不是越多越好（几千-几万条高质量样本常见），必须"messages 三件套"格式（system/user/assistant）、覆盖边界情况与错误示例（错误-纠正对教模型避坑）、清洗与去重、留出验证集（微调评估见下节）。追问"数据太少怎么办"——宁缺毋滥，几百条精准样本也可能优于几万条噪声数据；合成数据（用强模型生成再人工校验）是 2026 年主流扩数手段。

## 4. 微调的评估与避坑

微调评估三件事：**任务指标**（领域任务的准确率/格式通过率——用独立验证集，不用训练集）；**通用能力回测**（微调会遗忘通用能力——灾难性遗忘，混入通用数据或单独回测代码/数学/安全）；**与基线对比**（微调后 vs 微调前 vs RAG 方案的端到端评测，证明微调真有用）。常见避坑清单：**过拟合**（训练损失降但验证集不涨——加正则/减 rank/加数据）；**数据泄漏**（验证集与训练集重叠，指标虚高——去重）；**格式崩坏**（输出不再遵守 JSON——target_modules 或数据格式问题）；**灾难性遗忘**（专用能力涨、通用能力掉——混通用数据）。上线前必须做的动作：**合并 LoRA 再量化（merge-then-quantize）**——先 `merge_and_unload` 合并适配器（CPU 上即可，8B 约一两分钟），再做 GPTQ/GGUF 量化，避免"量化误差 + LoRA 近似误差"叠加，也让单文件部署更简单——这是 2026 年最值钱的一条微调部署经验。

## 5. 推理引擎：vLLM 与 PagedAttention

面试问"为什么 vLLM 快"，答案链条背熟：**PagedAttention**（把 KV Cache 切成固定大小的块管理，像操作系统虚拟内存分页——显存碎片浪费减少 30% 以上、吞吐提升 2-3 倍）；**连续批处理**（动态批处理：请求随到随处理，不用等一批集齐，GPU 利用率翻倍）；**前缀缓存**（Automatic Prefix Caching 按内容哈希共享 KV 块，共享 system prompt 下 TTFT 降 60-80%、吞吐 1.5-2.5 倍，自托管版 Prompt Caching）。对比数据：vLLM 相比原生 Transformers 吞吐高 2-4 倍——"更换推理框架是最便宜的降本项目"。配套：OpenAI 兼容 API（一套代码无感切换）、多 LoRA serving（一个模型服务多任务适配器）、与 DeepSeek 的 DSpark 推测解码（小模型猜、大模型验，速度最高提升 85%）。2026 年自托管选型：vLLM（高吞吐默认）/ SGLang（RadixAttention，树状前缀场景强，LLM-as-Judge 评测类工作负载）。

## 6. 量化方案全景

量化把参数精度从 FP32/FP16 压到 INT8/INT4——体积缩小 4-8 倍、显存需求大幅下降。四大方案一句话各背一句：**GPTQ**（基于二阶 Hessian 逐层校准的权重量化，vLLM 原生支持 + Marlin INT4 kernel 推理极快，领域微调场景 4bit 精度损失可压到 1-3 个点——**生产部署首选**）；**AWQ**（activation-aware，低比特 3bit 场景比 GPTQ 略稳）；**FP8 W8A8**（无需校准集几分钟完成、精度几乎无损，但需 Ada Lovelace/Hopper 新 GPU——新硬件快速压缩首选）；**GGUF（llama.cpp 生态）**（端侧/本地/Ollama 场景唯一选择；级别选 Q4_K_M ≈ 4.5 bit/weight——性价比甜点，Q5_K_M 接近 fp16 质量，Q8_0 几乎无损）。**bitsandbytes NF4/INT8 只用于开发（加载即量化），vLLM 支持有限，生产不用**。面试补充：量化前必须**用微调数据同分布校准集**（通用数据集校准会让领域效果明显变差）；量化后必须用 holdout 集做回归测试（对比量化前后关键指标）。

## 7. 生产部署架构与成本优化

自托管部署链路：**模型服务**（vLLM OpenAI 兼容端点，--gpu-memory-utilization 0.9、max-model-len 按需）；**网关层**（LiteLLM 等统一管理自托管与云 API，路由/限流/成本统计——自托管与云 API 混合是 2026 标准：高峰弹云、低谷自托管）；**观测**（每请求 token/延迟/TTFT 指标 + Prometheus）；**弹性**（K8s 按流量扩缩容，GPU 按需）。成本优化优先级（答这个顺序最加分）：**先软件优化**（量化、换推理框架、连续批处理——投入小收益大）→ **资源治理**（混部、弹性、清理闲置）→ **架构优化**（模型分层路由：简单问题小模型、复杂问题大模型；缓存）→ **采购策略**（预留/竞价实例）——**模型选型本身是最重要的降本项目：7B 能完成的别上 70B**。面试数据点：70B Q4_K_M 量化后约 40GB 可单卡推理；8 卡 A100 可部署 70B 全精度；7B 量化后单张消费级卡即可。
