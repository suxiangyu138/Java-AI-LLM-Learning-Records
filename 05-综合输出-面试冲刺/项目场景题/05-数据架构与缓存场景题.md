## 1. 场景题 1：Redis缓存实战与三大经典问题

> **面试官意图**：考察你对缓存最核心的三个问题——穿透、击穿、雪崩的理解深度。不只是概念，要能给出实战方案和代码。

### 1.1 缓存三大问题全景对比

| 问题 | 现象 | 原因 | 后果 | 一句话识别 |
|------|------|------|------|-----------|
| **缓存穿透** | 缓存和DB都没有数据 | 查询不存在的数据 | 恶意攻击打穿DB | "查了个不存在的东西" |
| **缓存击穿** | 缓存有但某个key过期 | 热点key过期 | 高并发直击DB | "一个key过期把DB打挂" |
| **缓存雪崩** | 缓存大量key同时过期 | 同一时间大量key过期 | DB瞬间被打爆 | "一堆key同时过期" |

### 1.2 缓存穿透——布隆过滤器方案

**问题场景**：攻击者不断请求一个不存在的商品ID（如 `-1` 或随机字符串），每次请求都会穿过缓存直达DB。

**解决方案**：布隆过滤器（Bloom Filter）+ 缓存空值（Null Cache）双保险。

```java
// SuGuangMall - 布隆过滤器实现
@Component
public class BloomFilterService {

    private final RedisTemplate<String, Object> redisTemplate;
    private static final String BLOOM_KEY = "bloom:product_ids";
    private static final long EXPECTED_INSERTIONS = 100_000L;
    private static final double FPP = 0.01;  // 1%误判率

    @PostConstruct
    public void init() {
        // 启动时加载所有有效商品ID到布隆过滤器
        List<Long> allProductIds = productService.getAllProductIds();
        allProductIds.forEach(this::add);
    }

    public boolean mightContain(Long productId) {
        // 使用Redisson的RBloomFilter
        RBloomFilter<Long> bloomFilter = redissonClient
            .getBloomFilter("productIdBloomFilter");
        bloomFilter.tryInit(EXPECTED_INSERTIONS, FPP);
        return bloomFilter.contains(productId);
    }

    public void add(Long productId) {
        RBloomFilter<Long> bloomFilter = redissonClient
            .getBloomFilter("productIdBloomFilter");
        bloomFilter.tryInit(EXPECTED_INSERTIONS, FPP);
        bloomFilter.add(productId);
    }
}

// 在查询中应用
public Product getProduct(Long productId) {
    // 第一步：布隆过滤器拦截（快速失败）
    if (!bloomFilterService.mightContain(productId)) {
        log.warn("Invalid product ID requested: {}", productId);
        return null;  // 直接返回，不打DB
    }

    // 第二步：查缓存
    String cacheKey = "product:" + productId;
    Product cached = (Product) redisTemplate.opsForValue().get(cacheKey);
    if (cached != null) {
        return cached;
    }

    // 第三步：查DB
    Product product = productMapper.selectById(productId);
    if (product != null) {
        redisTemplate.opsForValue().set(cacheKey, product, 30, TimeUnit.MINUTES);
    } else {
        // 空值缓存，防止穿透（TTL较短）
        redisTemplate.opsForValue().set(cacheKey, new NullProduct(), 5, TimeUtil.MINUTES);
    }
    return product;
}
```

**布隆过滤器参数配置**：

| 预期数据量 | 误判率(FPP) | 位数组大小 | Hash函数个数 | 内存占用 |
|-----------|------------|-----------|------------|---------|
| 10万 | 1% | ~120万bit | 7 | ~150KB |
| 100万 | 1% | ~1200万bit | 7 | ~1.5MB |
| 1000万 | 1% | ~1.2亿bit | 7 | ~15MB |

> 💡 **提示**：空值缓存TTL建议5-10分钟，防止恶意key长期占用内存。

### 1.3 缓存击穿——分布式锁+双重检查

**问题场景**：某个热点商品（如iPhone首发）的缓存过期瞬间，大量并发请求打到DB。

**解决方案**：分布式锁 + 双重检查机制。

```java
// SuGuangMall - 缓存击穿防护
public Product getHotProduct(Long productId) {
    String cacheKey = "hot_product:" + productId;
    String lockKey = "lock:hot_product:" + productId;

    // 第一次检查（不加锁）
    Product product = (Product) redisTemplate.opsForValue().get(cacheKey);
    if (product != null) {
        return product;
    }

    // 获取分布式锁（Redisson）
    RLock lock = redissonClient.getLock(lockKey);
    try {
        // 尝试加锁，等待3秒，锁过期10秒
        boolean locked = lock.tryLock(3, 10, TimeUnit.SECONDS);
        if (!locked) {
            // 获取锁失败，返回降级数据
            return getDegradedProduct(productId);
        }

        // 第二次检查（双重检测）
        product = (Product) redisTemplate.opsForValue().get(cacheKey);
        if (product != null) {
            return product;
        }

        // 查询DB
        product = productMapper.selectById(productId);
        if (product != null) {
            // 加随机TTL，防止相同过期时间
            int ttl = 300 + ThreadLocalRandom.current().nextInt(100);
            redisTemplate.opsForValue().set(cacheKey, product, ttl, TimeUnit.SECONDS);
        }
        return product;

    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        return getDegradedProduct(productId);
    } finally {
        lock.unlock();
    }
}
```

**为什么双重检查？**

```
线程A: 检查缓存（miss）→ 获取锁 → 再次检查缓存（miss）→ 查DB → 回填缓存
线程B: 检查缓存（miss）→ 等待锁 → 获取锁 → 再次检查缓存（hit!）→ 直接返回
                                            ↑
                                    这就是双重检查的价值
```

### 1.4 缓存雪崩——随机TTL + 逻辑过期 + Caffeine L1

**问题场景**：大量缓存同时过期（如晚上12点统一过期），或Redis宕机。

**三层防护**：

```java
// 第一层：随机TTL（防止同时过期）
public void setWithRandomTtl(String key, Object value, int baseTtl) {
    int randomOffset = ThreadLocalRandom.current().nextInt(baseTtl / 5);  // 20%随机偏移
    redisTemplate.opsForValue().set(key, value, baseTtl + randomOffset, TimeUnit.SECONDS);
}

// 第二层：逻辑过期（避免物理过期后全部打到DB）
@Data
public class CacheValue<T> {
    private T data;
    private long expireTime;  // 逻辑过期时间戳

    public boolean isExpired() {
        return System.currentTimeMillis() > expireTime;
    }
}

public T getWithLogicalExpire(String key, Class<T> clazz,
        Function<String, T> dbLoader, int logicalTtlSec) {
    // 读取缓存
    CacheValue<T> cacheValue = (CacheValue<T>) redisTemplate.opsForValue().get(key);

    if (cacheValue == null) {
        // 缓存不存在 -> 同步加载
        return syncLoadCache(key, dbLoader, logicalTtlSec);
    }

    if (!cacheValue.isExpired()) {
        return cacheValue.getData();  // 逻辑未过期，直接返回
    }

    // 逻辑已过期：异步刷新 + 返回旧值（避免等待DB）
    asyncRefreshCache(key, dbLoader, logicalTtlSec);
    return cacheValue.getData();  // 返回旧数据，用户体验不受影响
}

// 第三层：Caffeine本地缓存（L1）
@Configuration
public class CaffeineCacheConfig {

    @Bean
    public Cache<String, Object> caffeineCache() {
        return Caffeine.newBuilder()
            .maximumSize(10_000)         // 最多1万个条目
            .expireAfterWrite(60, TimeUnit.SECONDS)  // 60秒过期
            .recordStats()               // 开启统计
            .build();
    }
}
```

## 2. 场景题 2：Caffeine + Redis多级缓存架构

> **面试官意图**：考察你对多级缓存的深度理解——不只是堆叠缓存层，而是理解每一层的职责、容量、一致性模型。

### 2.1 三层缓存架构

```
┌─────────────────────────────────────────────┐
│  客户端                                      │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│  L1: Caffeine 本地缓存                       │
│  ├─ 容量: 10,000条                           │
│  ├─ TTL: 60秒（短，保证时效性）               │
│  ├─ 特点: 毫秒级响应，无网络开销              │
│  └─ 适用: 热点数据（80%请求命中这里）         │
├─────────────────────────────────────────────┤
│  L2: Redis 分布式缓存                       │
│  ├─ 容量: 10GB+                             │
│  ├─ TTL: 30分钟（相对长）                    │
│  ├─ 特点: 微秒级响应，集群高可用             │
│  └─ 适用: 全量缓存数据                      │
├─────────────────────────────────────────────┤
│  L3: MySQL 数据库                           │
│  ├─ 容量: 无限制（持久化）                   │
│  ├─ 特点: 毫秒级响应，最终数据一致            │
│  └─ 适用: 数据最终存储                      │
└─────────────────────────────────────────────┘
```

### 2.2 读路径详解

```java
// SuGuangMall - 多级缓存读取
public Product getProductWithMultiLevelCache(Long productId) {
    String cacheKey = "product:" + productId;

    // ===== L1: Caffeine本地缓存 =====
    Product product = caffeineCache.getIfPresent(cacheKey);
    if (product != null) {
        metricsService.recordCacheHit("L1");
        return product;
    }
    metricsService.recordCacheMiss("L1");

    // ===== L2: Redis分布式缓存 =====
    product = (Product) redisTemplate.opsForValue().get(cacheKey);
    if (product != null) {
        metricsService.recordCacheHit("L2");
        // 回填L1（本地缓存同步）
        caffeineCache.put(cacheKey, product);
        return product;
    }
    metricsService.recordCacheMiss("L2");

    // ===== L3: MySQL数据库 =====
    product = productMapper.selectById(productId);
    if (product != null) {
        // 回填L2
        redisTemplate.opsForValue().set(
            cacheKey, product,
            300 + ThreadLocalRandom.current().nextInt(100),
            TimeUnit.SECONDS
        );
        // 回填L1
        caffeineCache.put(cacheKey, product);
    }

    return product;
}
```

### 2.3 写路径与一致性保证

```java
// SuGuangMall - 更新路径
@Transactional
public Product updateProduct(Product product) {
    String cacheKey = "product:" + product.getId();

    // 1. 更新DB（事务内）
    productMapper.updateById(product);

    // 2. 删除Redis缓存（延迟删除，配合Cache-Aside模式）
    redisTemplate.delete(cacheKey);

    // 3. 发送MQ消息通知其他服务删除Caffeine缓存
    mqTemplate.convertAndSend("cache.invalidation", new CacheInvalidationEvent(
        cacheKey, "product"
    ));

    return product;
}

// MQ消费者（所有实例都订阅）
@Component
@RabbitListener(queues = "cache.invalidation")
public class CacheInvalidationConsumer {

    @Autowired
    private Cache<String, Object> caffeineCache;

    @RabbitHandler
    public void handle(CacheInvalidationEvent event) {
        // 所有实例删除本地Caffeine缓存
        caffeineCache.invalidate(event.getCacheKey());
        log.debug("Invalidated local cache: {}", event.getCacheKey());
    }
}
```

### 2.4 Cache-Aside Pattern详解

```
读缓存:    读请求 → 查L1 → miss → 查L2 → miss → 查DB → 回填L2 → 回填L1 → 返回
写数据库:  更新DB → 删L2缓存 → MQ通知 → 删L1缓存

为什么是"删缓存"而不是"更新缓存"？
  - 更新缓存存在并发写的一致性问题（两个线程同时写）
  - 删除缓存后下次读取会重新加载，保证最终一致性
  - 删除比更新更简单、更可靠
```

### 2.5 三种一致性方案的对比

| 方案 | 一致性强度 | 复杂度 | 延迟影响 | 适用场景 |
|------|----------|-------|---------|---------|
| **Cache-Aside + MQ** | 最终一致 | 中等 | 低 | SuGuangMall通用场景 |
| **Canal + Binlog** | 最终一致（秒级） | 高 | 无（异步） | 对业务无侵入 |
| **延迟双删** | 最终一致 | 低 | 中（等待1秒） | 简单场景 |

```java
// Canal Binlog监听器
@Component
public class BinlogCacheSyncListener {

    @Autowired
    private Cache<String, Object> caffeineCache;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    @EventListener
    public void onBinlogEvent(CanalEntry.Entry entry) {
        if (entry.getEntryType() == CanalEntry.EntryType.ROWDATA) {
            CanalEntry.RowChange rowChange = CanalEntry.RowChange.parseFrom(entry.getStoreValue());

            String tableName = entry.getHeader().getTableName();
            for (CanalEntry.RowData rowData : rowChange.getRowDatasList()) {
                String cacheKey = buildCacheKey(tableName, rowData);
                // 删除L1缓存
                caffeineCache.invalidate(cacheKey);
                // 删除L2缓存
                redisTemplate.delete(cacheKey);
                log.info("Binlog sync invalidated cache: {}", cacheKey);
            }
        }
    }
}
```

**Canal方案的优势**：
- 对业务代码零侵入（无需在Service层写缓存删除代码）
- 不会漏掉任何数据变更（基于Binlog）
- 异步处理，不影响主流程

> 🎯 **核心要点**：多级缓存的关键是**读写路径分离**和**分层失效机制**。L1解决热点，L2解决容量，L3兜底。一致性不强求强一致，最终一致即可。

## 3. 场景题 3：ShardingSphere分库分表设计与基因法

> **面试官意图**：考察你对分库分表的实战理解——不只是会配，而是要理解为什么这么分。

### 3.1 为什么按user_id分而不是order_id？

```text
两种分片键的对比：

按 order_id 分片：
  → 优点：订单数据均匀分布
  → 缺点：用户查询自己的订单需要查询所有分片（因为同一用户的订单分散在各表中）
  → 结果：查询效率极低

按 user_id 分片：
  → 优点：同一用户的所有订单在同一个分片上
  → 缺点：user_id需要作为查询条件
  → 结果：用户维度的查询效率极高

结论：互联网应用90%的查询是用户维度（"我的订单"），所以按user_id分片。
```

```java
// ShardingSphere分片算法 - 自定义实现
public class UserIdShardingAlgorithm implements StandardShardingAlgorithm<Long> {

    private static final int DB_COUNT = 4;
    private static final int TABLE_COUNT = 4;
    private static final int TOTAL_TABLES = DB_COUNT * TABLE_COUNT;

    @Override
    public String doSharding(Collection<String> availableTargetNames,
                             PreciseShardingValue<Long> shardingValue) {
        Long userId = shardingValue.getValue();

        // user_id后4位取模（保证均匀分布）
        int tableIndex = (int) (userId % TOTAL_TABLES);
        int dbIndex = tableIndex / TABLE_COUNT;
        int actualTableIndex = tableIndex % TABLE_COUNT;

        String dbName = "ds" + dbIndex;
        String tableName = "t_order_" + actualTableIndex;

        return dbName + "." + tableName;
    }
}
```

### 3.3 基因法：将user_id注入order_id

**问题**：如果按user_id分片，但用户通过order_id查询订单怎么办？order_id不知道对应的user_id，需要广播到所有分片。

**解决方案：基因法（Gene Algorithm）**

```java
// SuGuangMall - 基因法生成order_id
public class OrderIdGenerator {

    // 总表数 = 16（4库*4表）
    private static final int TABLE_COUNT = 16;
    // 基因位数 = log2(16) = 4位
    private static final int GENE_BITS = 4;
    // 基因掩码 = 0b1111 = 15
    private static final long GENE_MASK = (1 << GENE_BITS) - 1;

    /**
     * 生成包含user_id基因的order_id
     * 结构：时间戳(42位) | 自增序列(18位) | 基因(4位)
     */
    public long generateOrderId(long userId) {
        long timestamp = System.currentTimeMillis();
        long sequence = sequenceGenerator.nextId();

        // 从user_id中提取基因（后4位）
        long gene = userId & GENE_MASK;

        // 将基因注入order_id的后4位
        return (timestamp << 22) | (sequence << 4) | gene;
    }

    /**
     * 从order_id中提取基因，计算目标分片
     */
    public int calculateTableIndex(long orderId) {
        long gene = orderId & GENE_MASK;
        return (int) (gene % TABLE_COUNT);
    }

    /**
     * 从order_id中提取user_id（可能不完全准确，但可以缩小范围）
     */
    public long extractUserIdHint(long orderId) {
        return orderId & GENE_MASK;
    }
}
```

**基因法原理**：

```
user_id = 1024（二进制: 10000000000）
user_id & 0xF = 1024 & 15 = 0（后4位是0000）
  → 数据在 t_order_0 表

order_id = 202607281234567890（最后4位=0000）
order_id & 0xF = 0
  → 从 order_id 就能确定它在 t_order_0 表！

无需user_id也能找到分片！
```

**实际效果**：

| 查询方式 | 无基因法 | 有基因法 |
|---------|---------|---------|
| 按user_id查 | 1次查询（精确路由） | 1次查询 |
| 按order_id查 | 16次查询（广播） | 1次查询（基因提取） |
| 按user_id+order_id查 | 1次查询 | 1次查询 |

### 3.4 扩容策略：一致性哈希

```java
// SuGuangMall - 一致性哈希扩容
public class ConsistentHashSharding {

    private final TreeMap<Long, String> ring = new TreeMap<>();
    private static final int VIRTUAL_NODES = 160;  // 每个物理节点160个虚拟节点

    public ConsistentHashSharding(List<String> nodes) {
        for (String node : nodes) {
            for (int i = 0; i < VIRTUAL_NODES; i++) {
                long hash = hash(node + "#VN" + i);
                ring.put(hash, node);
            }
        }
    }

    public String getNode(String key) {
        if (ring.isEmpty()) return null;
        long hash = hash(key);
        // 找到第一个大于等于hash的节点
        Map.Entry<Long, String> entry = ring.ceilingEntry(hash);
        if (entry == null) {
            entry = ring.firstEntry();  // 回到环起点
        }
        return entry.getValue();
    }

    // 扩容：只需迁移 1/N 的数据
    public void addNode(String newNode) {
        // 添加虚拟节点
        for (int i = 0; i < VIRTUAL_NODES; i++) {
            long hash = hash(newNode + "#VN" + i);
            ring.put(hash, newNode);
        }
        // 理论迁移量 = 1/(N+1) 的数据
    }
}
```

> 🎯 **核心要点**：分库分表的核心是**分片键选择**和**跨分片查询处理**。按user_id分片是最常见的策略，基因法可以优雅解决order_id查询的问题。

## 4. 场景题 4：MySQL索引优化与慢SQL排查

### 4.1 索引类型选择

| 索引类型 | 适用场景 | 不合适场景 |
|---------|---------|-----------|
| **联合索引** | 多条件查询 `WHERE a=1 AND b=2` | 单列查询 |
| **覆盖索引** | 查询字段都在索引中 | 查询大文本字段 |
| **唯一索引** | 业务上必须唯一的字段 | 非唯一字段 |
| **前缀索引** | 长字符串字段（如url） | 区分度低的字段 |
| **全文索引** | 大文本搜索 | 精确匹配 |

### 4.2 联合索引设计原则

```sql
-- 口诀：最左前缀原则

-- 创建联合索引
CREATE INDEX idx_user_status_time ON t_order (user_id, status, create_time);

-- 能用上索引的查询
SELECT * FROM t_order WHERE user_id = 1001;                              -- ✅ 最左列
SELECT * FROM t_order WHERE user_id = 1001 AND status = 'PAID';          -- ✅ 前两列
SELECT * FROM t_order WHERE user_id = 1001 AND status = 'PAID' 
    AND create_time > '2026-01-01';                                      -- ✅ 全列
SELECT * FROM t_order WHERE status = 'PAID';                             -- ❌ 跳过了user_id
SELECT * FROM t_order WHERE create_time > '2026-01-01';                  -- ❌ 跳过了前两列
SELECT * FROM t_order WHERE user_id = 1001 AND create_time > '2026-01-01'; -- ⚠️ 跳过status，只能用user_id
```

**联合索引列顺序原则**：

```text
① 区分度高的列放前面（user_id区分度 > status）
② 等值查询的列放前面（WHERE user_id = 1001）
③ 范围查询的列放最后（WHERE create_time > ?）
④ 最常用的列放前面
```

// SuGuangMall - 强制走主库（写后立即读场景）
@Service
public class OrderService {

    @Transactional
    public Order createOrder(OrderCreateRequest request) {
        // 1. 写操作（事务内自动走主库）
        Order order = orderMapper.insert(request.toOrder());

        // 2. 写完后，需要立即查到这个订单
        // 方法一：HintManager强制走主库
        try (HintManager hintManager = HintManager.getInstance()) {
            hintManager.setWriteRouteOnly();  // 强制走主库
            return orderMapper.selectById(order.getId());
        }

        // 方法二：直接从方法返回值返回（不需要再查DB）
        return order;
    }

    // 读操作（允许最终一致性的场景）
    public List<Order> getOrders(Long userId) {
        // 默认走从库，使用HintManager设置读库
        try (HintManager hintManager = HintManager.getInstance()) {
            hintManager.setReadwriteSplittingHint("order-ds", false);  // false=读从库
            return orderMapper.selectByUserId(userId);
        }
    }
}

// 注解方式（AOP实现）
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RouteTo {
    enum Target { MASTER, SLAVE }
    Target value() default Target.SLAVE;
}

@Aspect
@Component
public class RoutingAspect {

    @Around("@annotation(routeTo)")
    public Object route(ProceedingJoinPoint pjp, RouteTo routeTo) throws Throwable {
        try (HintManager hintManager = HintManager.getInstance()) {
            if (routeTo.value() == RouteTo.Target.MASTER) {
                hintManager.setWriteRouteOnly();
            } else {
                hintManager.setReadwriteSplittingHint("order-ds", false);
            }
            return pjp.proceed();
        }
    }
}

// 使用示例
@RouteTo(RouteTo.Target.MASTER)  // 强制走主库
public Order getOrderJustCreated(Long orderId) {
    return orderMapper.selectById(orderId);
}

### 5.4 延迟容忍策略

```text
根据业务场景决定一致性等级：

强一致（写后立即读）：
  - 场景：支付结果、订单创建、库存扣减
  - 策略：强制走主库
  - 代价：主库压力增大，分摊效果有限

最终一致（允许短时延迟）：
  - 场景：订单历史查询、商品浏览、用户信息
  - 策略：走从库 + 前端轮询/WebSocket推送最新状态
  - 代价：用户可能看到旧数据（1秒内恢复）
```

> 💡 **经验值**：实际项目中70%的查询可以接受最终一致，只有30%的关键操作需要强制走主库。不要一刀切全部走主库，失去了读写分离的意义。

## 6. 场景题 6：Redis与DB数据一致性保证

> **面试官意图**：考察你对缓存一致性的理解深度——强一致还是最终一致，怎么取舍。

### 6.1 Cache-Aside Pattern详解

```
读请求:
  读缓存 → 命中 → 返回
  读缓存 → 未命中 → 读DB → 写缓存 → 返回

写请求（先更新DB，后删缓存）:
  更新DB → 删除缓存

为什么不先删缓存再更新DB？
  线程A: 删缓存 → 线程B: 读缓存(miss) → 读DB(旧数据) → 写缓存(旧数据) → 线程A: 更新DB
  最终结果：缓存中是旧数据！
  
所以正确的顺序是：先更新DB，再删缓存
```

public class CanalDataSyncHandler {

    @Resource
    private RedisTemplate<String, Object> redisTemplate;
    @Resource
    private Cache<String, Object> caffeineCache;

    // 不同类型的数据处理器
    private final Map<String, DataSyncHandler> handlers = new HashMap<>();

    @PostConstruct
    public void init() {
        handlers.put("product", new ProductSyncHandler());
        handlers.put("order", new OrderSyncHandler());
        handlers.put("user", new UserSyncHandler());
    }

    public void handleDataChange(String tableName, CanalEntry.EventType eventType,
                                  CanalEntry.RowData rowData) {
        String businessType = parseBusinessType(tableName);

        DataSyncHandler handler = handlers.get(businessType);
        if (handler == null) {
            log.warn("No handler for table: {}", tableName);
            return;
        }

        // 构建缓存key并删除
        String cacheKey = handler.buildCacheKey(rowData);
        redisTemplate.delete(cacheKey);
        caffeineCache.invalidate(cacheKey);

        // 如果是强一致场景，同步刷新缓存
        if (handler.needSyncRefresh(eventType)) {
            Object freshData = handler.loadFromDB(rowData);
            redisTemplate.opsForValue().set(cacheKey, freshData, 30, TimeUnit.MINUTES);
            caffeineCache.put(cacheKey, freshData);
        }

        log.info("Canal synced: table={}, event={}, key={}", tableName, eventType, cacheKey);
    }
}

public class OrderRouter {

    private static final String HOT_DS = "order-hot";
    private static final String COLD_DS = "order-cold";

### 8.2 连接数计算公式

```text
最大连接数 = (CPU核心数 * 2) + 有效磁盘数

经验公式：
  纯CPU密集型（复杂计算）：maxPoolSize ≈ CPU核数 + 1
  IO密集型（数据库查询）：maxPoolSize ≈ CPU核数 * 2
  混合型：maxPoolSize ≈ CPU核数 * 2 + 1

实际案例（SuGuangMall）：
  CPU: 8核
  业务类型: IO密集型（大量数据库读写）
  计算: 8 * 2 = 16
  最终配置: maxPoolSize = 20（留一些余量）
```

### 8.5 连接不够用时的应急方案

```text
第一反应：先别加连接数！分析原因：

① 慢SQL占用了大量连接（最常见）
   现象：active连接数高，CPU正常
   解决：优化慢SQL，不是加连接数

② 突发流量导致连接不够
   现象：pending线程增长，连接数打到上限
   解决：限流（Sentinel）+ 排队等待

③ 连接泄露
   现象：active缓慢增长，idle持续下降
   解决：findBugs/Arthas排查未关闭的连接

④ 数据库性能瓶颈
   现象：active连接都在运行中，数据库CPU 100%
   解决：扩容数据库，不是加连接数

调优顺序：SQL优化 → 限流 → 扩容 → 加连接数
```

> 🎯 **核心要点**：连接池调优不是改一个数字那么简单。**先排查是不是慢SQL/泄露等问题，最后再动连接数**。

@Service
public class ProductSearchService {

    private final ElasticsearchRestTemplate esTemplate;

    public Page<ProductDocument> searchProducts(ProductSearchRequest request) {
        NativeQueryBuilder queryBuilder = NativeQuery.builder()
            .withSort(Sort.by(
                Sort.Order.desc("_score"),
                Sort.Order.desc("salesCount"),
                Sort.Order.desc("createTime")
            ))
            .withPageable(PageRequest.of(request.getPage(), request.getSize()));

        // Bool查询
        BoolQuery.Builder boolQuery = QueryBuilders.bool();

        // 关键字搜索（多字段匹配）
        if (StringUtils.hasText(request.getKeyword())) {
            boolQuery.must(QueryBuilders.multiMatch(q -> q
                .fields("productName^3", "categoryName^2", "brandName^2", "description")
                .query(request.getKeyword())
                .analyzer("ik_smart")
                .type(MultiMatchQueryType.BEST_FIELDS)
            ));
        }

        // 过滤条件
        if (request.getMinPrice() != null) {
            boolQuery.filter(QueryBuilders.range(q -> q
                .field("price").gte(request.getMinPrice())));
        }
        if (request.getMaxPrice() != null) {
            boolQuery.filter(QueryBuilders.range(q -> q
                .field("price").lte(request.getMaxPrice())));
        }
        if (request.getBrandName() != null) {
            boolQuery.filter(QueryBuilders.term(q -> q
                .field("brandName").value(request.getBrandName())));
        }

        queryBuilder.query(boolQuery.build()._toQuery());
        queryBuilder.withHighlight(hl -> hl
            .fields(Map.of("productName", HighlightField.hf(hf -> hf
                .preTags("<em>").postTags("</em>"))))
        );

        SearchHits<ProductDocument> hits = esTemplate.search(
            queryBuilder.build(), ProductDocument.class);

        return new PageImpl<>(
            hits.stream().map(SearchHit::getContent).collect(Collectors.toList()),
            PageRequest.of(request.getPage(), request.getSize()),
            hits.getTotalHits()
        );
    }
}

@Component
public class ProductCanalToESHandler {

    private final RabbitTemplate rabbitTemplate;

    @EventListener
    public void onProductChange(CanalEntry.Entry entry) {
        if (entry.getEntryType() != CanalEntry.EntryType.ROWDATA) return;

        CanalEntry.RowChange rowChange;
        try {
            rowChange = CanalEntry.RowChange.parseFrom(entry.getStoreValue());
        } catch (Exception e) {
            log.error("Parse canal entry failed", e);
            return;
        }

        for (CanalEntry.RowData rowData : rowChange.getRowDatasList()) {
            ProductSyncEvent event = ProductSyncEvent.builder()
                .productId(extractProductId(rowData))
                .eventType(convertEventType(rowChange.getEventType()))
                .timestamp(System.currentTimeMillis())
                .build();

            // 发MQ，由ES同步消费者处理
            rabbitTemplate.convertAndSend("es.sync.product", event);
        }
    }
}

// ES同步消费者
@Component
@RabbitListener(queues = "es.sync.product")
public class ProductESSyncConsumer {

    private final ElasticsearchRestTemplate esTemplate;
    private final ProductMapper productMapper;

    @RabbitHandler
    public void handle(ProductSyncEvent event) {
        switch (event.getEventType()) {
            case INSERT:
            case UPDATE:
                // 查询完整数据
                Product product = productMapper.selectById(event.getProductId());
                if (product != null) {
                    ProductDocument doc = convertToDocument(product);
                    esTemplate.save(doc);
                    log.info("ES synced product: {}", event.getProductId());
                }
                break;
            case DELETE:
                esTemplate.delete(event.getProductId().toString(), ProductDocument.class);
                log.info("ES deleted product: {}", event.getProductId());
                break;
        }
    }
}

### 9.4 全量同步策略

```java
// SuGuangMall - ES全量同步
@Component
public class ESFullSyncJob {

    @Scheduled(cron = "0 0 4 * * ?")  // 每天凌晨4点
    public void fullSync() {
        log.info("Starting ES full sync...");

        // 1. 创建临时索引
        String tempIndex = "products_" + LocalDate.now().format(DateTimeFormatter.BASIC_ISO_DATE);
        esTemplate.indexOps(IndexCoordinates.of(tempIndex)).create(createMapping());

        // 2. 分页全量读取MySQL数据
        int pageSize = 1000;
        int page = 0;
        int total = 0;

        while (true) {
            List<Product> products = productMapper.selectPage(page * pageSize, pageSize);
            if (products.isEmpty()) break;

            // 批量写入临时索引
            List<ProductDocument> docs = products.stream()
                .map(this::convertToDocument)
                .collect(Collectors.toList());

            esTemplate.save(docs, IndexCoordinates.of(tempIndex));

            total += products.size();
            page++;
            log.info("Synced {} products, total: {}", products.size(), total);
        }

        // 3. 切换别名（原子操作，零停机）
        boolean switched = switchAlias("products", tempIndex);
        if (switched) {
            log.info("ES full sync completed, switched to index: {}", tempIndex);
        } else {
            log.error("ES alias switch failed!");
        }
    }

    private boolean switchAlias(String alias, String newIndex) {
        // 原子切换别名
        IndicesAliasesRequest request = new IndicesAliasesRequest();
        // 移除旧的
        request.addAliasAction(
            IndicesAliasesRequest.AliasActions.remove()
                .index("products_*")
                .alias(alias)
        );
        // 添加新的
        request.addAliasAction(
            IndicesAliasesRequest.AliasActions.add()
                .index(newIndex)
                .alias(alias)
        );
        return esTemplate.indexOps(IndexCoordinates.of(alias)).alias(request);
    }
}
```

### 9.5 数据一致性保障策略

```text
ES与MySQL一致性保障矩阵：

增量同步（实时）：
  Canal监听Binlog → MQ → ES更新
  延迟：<1秒
  风险：MQ消息丢失 → 需要补偿机制

全量同步（每日）：
  凌晨低峰期全量重建索引
  别名切换实现零停机
  保证最终数据一致

补偿机制：
  对账：每日比对MySQL和ES的数据量
  补录：发现不一致时触发单条补录
  手动触发：运营后台提供"刷新ES"按钮

兜底方案：
  如果ES不可用 → 降级到MySQL搜索（性能差但可用）
```

> 🎯 **核心要点**：ES和MySQL同步的关键是**增量同步 + 全量同步 + 补偿机制**三合一。增量保证实时性，全量保证最终一致性，补偿兜底。
