#### 完整数据流

```
用户点击"立即秒杀"
  → 前端验证：按钮状态、验证码
    → CDN 静态资源加载
      → Nginx：IP 限流（10次/s）
        → Gateway：JWT 鉴权 + 总 QPS 限流
          → Seckill Service：用户维度限流
            → Redis Lua：预减库存
              ├── 成功 → 返回 "抢购成功" → 发送 MQ 消息
              │           → Order Consumer：创建订单（MySQL）
              │           → 支付成功 → 订单完成
              │           → 15min 未支付 → 死信队列触发 → 关单 + 回滚库存
              └── 失败 → 返回 "已售罄" / "操作太频繁"
```

#### 关键决策表

| 决策点 | 方案 | 为什么选这个 | 不这么选的后果 |
|--------|------|-------------|---------------|
| 库存扣减 | Redis Lua 原子脚本 | Redis 单线程 10W+ QPS，原子性保证 | MySQL 行锁 → 串行化 → 几百 QPS |
| 下单方式 | 异步 MQ | 削峰填谷，保护 DB | 同步 → DB 被打满 → 服务雪崩 |
| 关单方案 | 死信延迟队列 | 精准、无锁、低延迟 | 定时任务扫表 → 延迟高、DB 压力大 |
| 防刷策略 | Nginx + Sentinel 双层限流 | 多维度防护 | 仅单层限流 → 被穿透 |
| 分表策略 | user_id 分 16 表 | 用户级查询友好，数据均匀 | 不分表 → 单表千万级 → 慢查询 |

### 追问应对

> 追问1：如果 Redis 也扛不住怎么办？

**多级库存 + 本地预分摊**：
- 将 1W 库存预分到多个 Redis 节点（每个节点 1000 件）
- Nginx 根据 hash(user_id) 路由到不同节点
- 节点内库存耗尽 → 回源到中心库存
- 终极方案：**请求排队**，先到先得，队列内串行处理

> 追问2：订单分表后怎么跨页查询？

- 强制带 user_id 查询（走 ShardingSphere 路由到具体表）
- 后台管理查询 → 通过 ES 同步索引
- 避免不带分片键的全表扫描

> 追问3：Seata AT 模式会不会影响性能？

- Seata AT 在秒杀中只用于**最终一致性**场景（订单→库存→MQ 的最终一致）
- 秒杀主路径（Redis 预减）使用 Lua 保证强一致
- Seata 的 undo_log 和全局锁在低并发时性能可接受
- 高并发路径不要用 Seata（见场景题 3 分析）

### 🎯 核心要点

- **回答要有层次**：从端到端，7 层逐层展开
- **数据要具体**：QPS 2000+、100W 过滤到 10W、15min 关单
- **肯定要有取舍**：没有银弹，每个选择都有 trade-off
- **实战项目**：SuGuangMall 实测数据是加分项

## 3. 场景题 2：「为什么用Redis而不是数据库直接扣库存？Redis挂了怎么办？」

### 面试官意图

考察**技术选型能力**和**容灾意识**。不是背八股，要能说出 Redis vs MySQL 在并发场景的本质差异，以及 Redis 挂了之后的降级方案。

### 答题框架

**Redis vs DB 对比 → 为什么 Redis 适合 → Redis 挂了怎么办 → 多层降级**

### 标准答案（详细）

#### Redis vs 数据库直接扣库存对比

| 维度 | 数据库直接扣库存 | Redis 预减库存 |
|------|----------------|---------------|
| 并发能力 | 行锁 → 串行化，单表 ~1000 TPS | 单线程 + 内存操作，单节点 ~10W QPS |
| 响应时间 | 10~50ms（磁盘 IO + 锁竞争） | <1ms（纯内存） |
| 原子性 | `UPDATE stock=stock-1 WHERE stock>0` 行锁保证 | Lua 脚本保证复合操作原子性 |
| 超卖风险 | 行锁 + 事务可保证不超卖 | Lua 原子性保证不超卖 |
| 持久性 | ACID 事务，崩溃恢复后一致 | RDB/AOF 有丢数据窗口 |
| 扩展性 | 分库分表后查询复杂 | Redis Cluster 天然支持水平扩展 |
| 复杂度 | 简单直接 | 需要处理缓存与 DB 一致性 |
| 适用场景 | 低并发、强事务要求 | 高并发、允许最终一致性 |

**核心结论**：秒杀场景下，DB 的行锁机制是最大瓶颈。MySQL 的 `UPDATE stock=stock-1 WHERE stock>0` 虽然能保证不超卖，但**所有请求串行化等待行锁**，TPS 天花板极低。

#### Redis 挂了怎么办？—— 多级降级策略

```
┌─────────────────────────────────────────────────────────────┐
│               秒杀场景 Redis 故障多级降级                      │
│                                                             │
│  Level 0：正常状态                                           │
│    Redis Cluster 主从 + Sentinel 高可用                      │
│    ● 库存：Redis Lua 预减                                    │
│    ● 用户标记：Redis SET 防重复                              │
│                                                             │
│  Level 1：Redis 节点故障（主从切换）                          │
│    ● Sentinel 自动故障转移，30s 内恢复                        │
│    ● 期间请求走降级路径                                      │
│    ● 库存数据从最近的 RDB+AOF 恢复                           │
│                                                             │
│  Level 2：Redis 集群大部分不可用                              │
│    ● 降级为本地缓存 + 数据库模式                              │
│    ● 使用 Caffeine 本地缓存预加载部分库存                     │
│    ● 设置秒杀活动为"暂停"状态，前端显示"系统繁忙"              │
│    ● 数据库添加乐观锁：UPDATE stock=stock-1 WHERE             │
│      stock>0 AND version=#{version}                          │
│    ● QPS 降为 DB 能承受的量（~500 TPS）                      │
│                                                             │
│  Level 3：Redis 完全不可用 + DB 压力过大                      │
│    ● 直接熔断秒杀接口，返回"活动太火爆"                        │
│    ● 等待 Redis 恢复后，重新加载库存数据到缓存                 │
│    ● 对已经预占库存但未支付的用户保留资格                      │
│                                                             │
│  Level 4：灾难恢复                                            │
│    ● 从 AOF/RDB 恢复库存数据                                  │
│    ● 比对 MySQL 订单数据和 Redis 库存记录，人工对账            │
│    ● 发送补偿消息，处理不一致的订单                           │
└─────────────────────────────────────────────────────────────┘
```

#### Redis 持久化配置

| 场景 | 持久化策略 | 优点 | 缺点 |
|------|-----------|------|------|
| 秒杀库存 | RDB 每 60s + AOF everysec | 性能较好，最多丢 1s 数据 | 秒级数据丢失风险 |
| 用户标记 | RDB 每 300s | 可以接受少量丢失 | 丢失后用户可能重复抢 |
| 订单数据（不用 Redis 存） | 不用 Redis 持久化，直接写 MySQL | 保证数据安全 | N/A |

#### SuGuangMall 实战配置

```yaml
# Redis 高可用配置
spring:
  redis:
    cluster:
      nodes:
        - 192.168.1.101:6379
        - 192.168.1.102:6379
        - 192.168.1.103:6379
    # 持久化：混合 RDB + AOF
    # 实际由 redis.conf 控制
```

```bash
# redis.conf 关键配置
save 60 10000       # 60秒内至少有10000个key变化则RDB
appendonly yes      # 开启AOF
appendfsync everysec # 每秒刷盘
```

### 追问应对

> 追问1：Redis 恢复后库存和数据库不一致怎么办？

**对账机制**：
1. 定时任务扫描 MySQL 订单表和 Redis 库存记录
2. 对比实际售出数 vs Redis 库存减少数
3. 不一致时以 MySQL 订单为准，修正 Redis 库存
4. 回滚或补偿异常订单

> 追问2：主从切换时，库存数据会不会丢？

- 秒杀场景使用 `WAIT` 命令同步复制到至少 1 个从节点
- 主从切换后，Redis 新主库存可能比实际多 → 允许少量超卖，通过 DB 层兜底
- 关键：**宁可超卖 1%，不可少卖 1%**（超卖可以退款，少卖是收入损失）

### 🎯 核心要点

- Redis 胜在**内存 + 单线程 + Lua 原子性**，不是持久化能力
- 降级策略要**分层**：从正常到熔断，逐级降级
- 持久化不是银弹，**对账和补偿**才是最终保障
- 面试时要说出 **Level 0~4 的完整降级思路**

## 4. 场景题 3：「Lua脚本具体怎么写？为什么Lua比Redis事务好？」

### 面试官意图

考察**Lua 脚本的实战能力**。不只要知道 Lua 脚本怎么写，还要知道为什么它比 Redis 的 `MULTI/EXEC` 事务更适合秒杀场景。

### 答题框架

**Lua 脚本示例 → MULTI/EXEC vs Lua 对比 → 原子性保证原理**

### 标准答案（详细）

#### SuGuangMall 秒杀 Lua 脚本

```lua
-- kill.lua：秒杀预占库存 + 用户防重复
-- KEYS[1] = 库存 key (seckill:stock:{seckillId})
-- KEYS[2] = 用户标记 key (seckill:user:{seckillId}:{userId})
-- ARGV[1] = 用户 ID
-- ARGV[2] = 购买数量（通常为1）

-- 1. 检查用户是否已经抢购过（防重复标记）
local userKey = KEYS[2]
local userId = ARGV[1]
local hasBought = redis.call('sismember', userKey, userId)
if hasBought == 1 then
    return {err = "您已经参与过该秒杀活动"}
end

-- 2. 检查库存是否足够
local stockKey = KEYS[1]
local stock = redis.call('get', stockKey)
if not stock then
    return {err = "秒杀活动不存在"}
end
if tonumber(stock) <= 0 then
    return {err = "商品已售罄"}
end

-- 3. 预占库存（扣减）
local quantity = tonumber(ARGV[2]) or 1
if tonumber(stock) < quantity then
    return {err = "库存不足"}
end
redis.call('decrby', stockKey, quantity)

-- 4. 标记用户已抢购
redis.call('sadd', userKey, userId)

-- 5. 设置用户标记过期时间（活动结束后自动清理）
redis.call('expire', userKey, 86400)

-- 6. 返回成功，包含当前剩余库存
local remain = redis.call('get', stockKey)
return {success = "ok", remain = tonumber(remain)}
```

#### Redis MULTI/EXEC 事务 vs Lua 脚本对比

| 维度 | MULTI/EXEC 事务 | Lua 脚本 |
|------|----------------|---------|
| 执行方式 | 多条命令缓存后批量执行 | 一个脚本内包含所有逻辑 |
| 原子性 | 全部执行或全部不执行 | **整个脚本作为原子操作** |
| 回滚能力 | 语法错误回滚，运行时错不**不回滚** | 无回滚，但出错后后续不执行 |
| 业务逻辑 | 不支持 if-else 等分支判断 | 支持完整的编程逻辑 |
| 网络开销 | N 条命令 = N 次网络往返 | 1 次脚本发送，1 次执行 |
| 复用性 | 每次发多命令 | 脚本被缓存（SCRIPT LOAD），后续 EVALSHA 调用 |
| 可读性 | 简单操作可读 | 复杂逻辑在脚本内，不易调试 |
| 回滚能力 | 能在 EXEC 前 DISCARD 取消 | 执行前可保证原子性，执行后不可回滚 |

**为什么 Lua 更好？** 三个核心原因：

1. **原子性**：Lua 脚本执行期间，其他客户端命令不会插入（Redis 单线程执行整个脚本），天然等于一个原子操作
2. **业务逻辑**：MULTI/EXEC 只能做简单的 GET/SET 排队，而 Lua 可以在 Redis 内完成 if-else 判断、类型检查、多 key 操作
3. **网络效率**：1 次网络传输完成 N 次操作，秒杀场景下网络延迟是瓶颈之一

#### Lua 脚本原子性保证原理

```
Redis 单线程执行模型：

Client A: EVALSHA "kill.lua"  → → → → → Redis 主线程执行
                                    ↓
Client B: GET stock:123       → → → → 等待 → → 执行
                                    ↓
Client C: DECR stock:456      → → → → 等待 → → 执行

整个 Lua 脚本执行期间，不会处理任何其他命令！
```

#### 注意事项

```lua
-- ⚠️ 不要在 Lua 中做这些事：
-- 1. 长时间运算（阻塞其他请求）
-- 2. 调用 redis.call('time') 太频繁
-- 3. 操作大量 key（单次脚本建议 < 1000 个 key）
-- 4. 在 Lua 中打印日志（消耗性能）

-- ✅ 最佳实践：
-- 1. 脚本尽量短小精悍
-- 2. 用 KEYS 数组传 key，ARGV 数组传参数
-- 3. 控制脚本执行时间（< 5ms）
-- 4. 用 EVALSHA 减少网络传输
```

### 追问应对

> 追问1：Lua 脚本执行时间太长会怎样？

- Redis 是单线程，Lua 脚本执行期间会阻塞所有其他命令
- Redis 内置了 **lua-time-limit** 参数（默认 5000ms），超时会报错
- 但即便如此，超过 100ms 的脚本就已经是大问题了
- **方案**：拆分脚本、减少循环、把复杂逻辑移到 Java 层

> 追问2：可以用 Lua 做分布式锁吗？

可以，Redis 官方 RedLock 就是用 Lua 实现的。但秒杀场景下，Lua 脚本本身已经包含原子性和互斥逻辑，不需要额外加分布式锁。

> 追问3：多个 Lua 脚本之间的依赖怎么处理？

Lua 脚本之间没有依赖关系，每个脚本独立执行。如果需要跨脚本一致性，需要应用层保证（如使用 Seata）。

### 🎯 核心要点

- Lua 脚本 = **原子性 + 业务逻辑 + 网络效率** 三重优势
- MULTI/EXEC 只是命令批次执行，不支持分支判断
- 秒杀 Lua 脚本三步：检查库存 → 扣减 → 标记用户
- 用 **EVALSHA** 缓存脚本，减少网络传输

#### 消息丢失三大场景及解决方案

| 丢失场景 | 原因 | 解决方案 | SuGuangMall 实现 |
|---------|------|---------|-----------------|
| **生产者丢失** | 消息发到 Exchange 前，网络故障/应用宕机 | **Publisher Confirm 机制** | 异步 Confirm 回调，失败则重发 |
| **Broker 丢失** | RabbitMQ 宕机，消息未持久化 | **消息持久化** + **Mirrored Queue** | `delivery_mode: 2` 持久化消息 |
| **消费者丢失** | 消费者处理完但未 ACK 时宕机 | **手动 ACK**，处理完才确认 | `acknowledge-mode: manual` |

#### 生产者可靠性（Publisher Confirm）

```java
@Component
@Slf4j
public class SeckillOrderSender {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    @PostConstruct
    public void init() {
        // 确认回调
        rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
            if (ack) {
                log.info("消息确认成功: {}", correlationData.getId());
            } else {
                log.warn("消息确认失败: {}, cause: {}", correlationData.getId(), cause);
                // 失败重发逻辑（存入重试表，定时扫描重发）
                retrySend(correlationData.getId());
            }
        });

        // 回退回调（消息不可路由）
        rabbitTemplate.setReturnsCallback(returned -> {
            log.warn("消息不可路由: exchange={}, routingKey={}, msg={}",
                returned.getExchange(), returned.getRoutingKey(), returned.getMessage());
        });
    }

    public void sendOrderMessage(SeckillOrderMessage message) {
        CorrelationData correlationData = new CorrelationData(UUID.randomUUID().toString());
        rabbitTemplate.convertAndSend(
            "seckill.order.exchange",
            "seckill.order.routing",
            message,
            msg -> {
                msg.getMessageProperties().setDeliveryMode(MessageDeliveryMode.PERSISTENT);
                msg.getMessageProperties().setExpiration("900000"); // 15min TTL
                return msg;
            },
            correlationData
        );
        // 记录消息发送记录到数据库
        saveMessageRecord(correlationData.getId(), message);
    }
}
```

#### 消费者可靠性（手动 ACK + 幂等）

```java
@Component
@Slf4j
public class SeckillOrderConsumer {

    @Autowired
    private OrderService orderService;

    @RabbitListener(queues = "seckill.order.queue")
    public void handleOrder(SeckillOrderMessage message,
                            Channel channel,
                            @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag) throws IOException {
        try {
            // 1. 幂等性检查 - 消息去重
            String messageId = message.getMessageId();
            if (redisTemplate.opsForValue().setIfAbsent(
                    "seckill:msg:" + messageId, "1", 1, TimeUnit.HOURS)) {
                // 2. 业务处理：创建订单 + 扣减库存
                orderService.createOrder(message);
                // 3. 手动 ACK
                channel.basicAck(deliveryTag, false);
                log.info("订单创建成功: {}", messageId);
            } else {
                // 已处理过的消息，直接 ACK
                channel.basicAck(deliveryTag, false);
                log.info("重复消息已忽略: {}", messageId);
            }
        } catch (Exception e) {
            log.error("订单创建失败: {}", e.getMessage());
            // 重试判断
            if (message.getRetryCount() < 3) {
                channel.basicNack(deliveryTag, false, true); // 重新入队
            } else {
                // 超过重试次数 → 进入死信队列
                channel.basicNack(deliveryTag, false, false); // 不重新入队
                // 记录失败日志，人工介入
                saveFailLog(message, e);
            }
        }
    }
}
```

#### 幂等性保证方案对比

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **Redis SETNX** | 消息 ID 作为 key，第一次 set 成功则处理 | 高性能，支持分布式 | 需要 Redis 高可用 |
| **数据库唯一索引** | 订单表建立 message_id 唯一索引 | 数据库保证，绝对可靠 | 插入性能瓶颈 |
| **状态机** | 订单状态从 INIT→PROCESSING→DONE | 精确控制 | 实现复杂 |

SuGuangMall 使用 **Redis SETNX + 数据库唯一索引** 双重保障。

### 追问应对

> 追问1：MQ 积压了怎么办？

- **紧急扩容**：增加 Consumer 实例数量
- **临时队列**：创建新的临时队列，将积压消息路由到新队列
- **降级处理**：关闭非核心业务，优先处理秒杀订单
- 上线后**限流阈值调低**，从源头减少消息量

> 追问2：死信队列的消息也丢了怎么办？

- 死信队列同样启用 Publisher Confirm + 持久化
- 增加**定时任务兜底**：每 5 分钟扫描未支付订单（对比对账）
- 对账机制：每日凌晨比对 Redis 库存和 MySQL 订单数

### 🎯 核心要点

- 消息丢失三环节：**生产者 → Broker → 消费者**，每个环节都要保证
- 幂等性用 **Redis SETNX** 或 **数据库唯一索引**
- 死信队列 + TTL 实现精准关单，比定时任务更高效
- 重试 3 次 + 失败记录，避免消息无限重试

### 追问应对

> 追问1：验证码也有打码平台破解，怎么办？

- 升级为**无感验证**：行为验证（鼠标轨迹、点击区域分析）
- **二次验证**：第一次抢购成功 → 弹出验证码 → 验证通过才创建订单
- 叠加使用：验证码 + 用户维度限流 + 行为分析，单点突破无意义

> 追问2：Nginx 限流和 Sentinel 限流重复吗？

不重复，是互补关系：
- Nginx：**IP 维度**，粗粒度，拦截网络层流量
- Sentinel：**用户维度**，细粒度，拦截业务层异常
- 双层限流 = IP 不好使了用用户维度兜底，用户维度不好使了用 IP 兜底

### 🎯 核心要点

- 防刷是**多层防御**，没有单一方案能解决
- 核心思路：**量上限制 + 身份验证 + 行为分析**
- 用户体验和防护强度要平衡，不能为了防刷让正常用户抢不到
- 黑名单要有**自动释放机制**，防止误封

## 8. 场景题 7：「秒杀库存从1W扩到10W，架构需要改什么？」

### 面试官意图

考察**架构扩展能力**。10 倍库存不仅是数量变化，会影响整个系统的设计。

### 答题框架

**分层分析影响 → 逐个给出方案 → 弹性伸缩**

### 标准答案（详细）

#### 各层影响与调整

| 层次 | 1W 库存设计 | 10W 库存调整 | 原因 |
|------|-----------|------------|------|
| Redis 库存 Key | 单个 Key | **分片库存**：每个 Key 存 1000 件，100 个 Key | 单 Key 热点过高 |
| Redis 内存 | ~10KB | **~1MB**，无压力 | 10W 库存数据极小 |
| 预减逻辑 | 一次 Lua 操作 | **一致性哈希** 路由到不同的库存分片 | 分散热点 |
| 秒杀时长 | 默认 15min | **分时段秒杀**：每批 1W，分 10 批 | 降低瞬时压力 |
| DB 订单量 | 单秒 ~2000 订单 | 单秒可能 2W+ 订单 | 分库分表需要扩容 |
| MQ 消息量 | 瞬时 2000/s | 瞬时可能 2W/s | **Consumer 扩容** + 调整 prefetch |
| 监控指标 | 单维度库存 | **多维监控**：各分片库存、各时段数据 | 更精细的运营管理 |

#### 分片库存设计

```java
/**
 * 分片库存路由
 * 将 10W 库存均匀分配到 100 个 Redis Key
 * 每个 Key 持有 1000 件
 */
@Component
public class ShardedStockManager {

    private static final int SHARD_COUNT = 100;
    private static final int STOCK_PER_SHARD = 1000;

    // 用户取模分配到分片
    public String getShardKey(Long seckillId, Long userId) {
        int shardId = Math.abs(userId.hashCode()) % SHARD_COUNT;
        return "seckill:stock:" + seckillId + ":shard:" + shardId;
    }

    // 秒杀 Lua - 多分片版本
    public Map<String, Object> tryAcquireSharded(Long seckillId, Long userId) {
        String shardKey = getShardKey(seckillId, userId);
        // 只在一个分片上扣减
        return redisScriptExecutor.execute(seckillLua, shardKey, userId);
    }

    // 查询总剩余库存
    public int getTotalStock(Long seckillId) {
        int total = 0;
        for (int i = 0; i < SHARD_COUNT; i++) {
            String key = "seckill:stock:" + seckillId + ":shard:" + i;
            String val = redisTemplate.opsForValue().get(key);
            total += (val != null ? Integer.parseInt(val) : 0);
        }
        return total;
    }
}
```

- 预见问题：用户分配到空分片 → 给出重定向方案

#### 死信队列关单实现

```java
@Component
@Slf4j
public class SeckillDlxConsumer {

    @Autowired
    private OrderService orderService;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    @RabbitListener(queues = "seckill.dlx.queue")
    public void handleDlxMessage(SeckillOrderMessage message,
                                  Channel channel,
                                  @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag) throws IOException {
        try {
            // 1. 幂等检查（防止二次回滚）
            String rollbackKey = "seckill:rollback:" + message.getOrderId();
            Boolean already = redisTemplate.opsForValue().setIfAbsent(rollbackKey, "1", 1, TimeUnit.DAYS);
            if (Boolean.FALSE.equals(already)) {
                channel.basicAck(deliveryTag, false);
                return;
            }

            // 2. 查询订单状态
            Order order = orderService.getById(message.getOrderId());
            if (order == null || "CANCELLED".equals(order.getStatus())) {
                channel.basicAck(deliveryTag, false);
                return;
            }

            // 3. 只有未支付才关单
            if ("UNPAID".equals(order.getStatus())) {
                // 3.1 更新订单状态为 CANCELLED
                orderService.cancelOrder(message.getOrderId());
                // 3.2 Lua 脚本回滚库存
                String lua = "redis.call('incr', KEYS[1])";
                List<String> keys = Arrays.asList("seckill:stock:" + message.getSeckillId());
                redisTemplate.execute(new DefaultRedisScript<>(lua, Long.class), keys);
                // 3.3 发送通知（可选）
                notifyUser(message.getUserId(), "您的秒杀订单已超时取消");
                log.info("关单+回滚成功: orderId={}, seckillId={}", message.getOrderId(), message.getSeckillId());
            }

            channel.basicAck(deliveryTag, false);
        } catch (Exception e) {
            log.error("关单处理失败: {}", e.getMessage(), e);
            channel.basicNack(deliveryTag, false, true);
        }
    }
}
```

#### 定时任务兜底

```java
@Component
@Slf4j
public class SeckillTimeoutJob {

    @Autowired
    private OrderService orderService;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    /**
     * 每分钟执行一次，扫描超时未支付的秒杀订单
     */
    @Scheduled(cron = "0 */1 * * * ?")
    public void handleTimeoutOrders() {
        log.info("开始扫描超时未支付订单");
        // 查询所有超时未支付的秒杀订单
        List<Order> timeoutOrders = orderService.list(new QueryWrapper<Order>()
            .eq("type", "SECKILL")
            .eq("status", "UNPAID")
            .lt("create_time", LocalDateTime.now().minusMinutes(15)));

        for (Order order : timeoutOrders) {
            try {
                // 幂等检查
                String key = "seckill:rollback:job:" + order.getId();
                if (Boolean.TRUE.equals(redisTemplate.opsForValue().setIfAbsent(key, "1", 1, TimeUnit.HOURS))) {
                    orderService.cancelOrder(order.getId());
                    // Redis 回滚库存
                    String lua = "redis.call('incr', KEYS[1])";
                    List<String> keys = Arrays.asList("seckill:stock:" + order.getSeckillId());
                    redisTemplate.execute(new DefaultRedisScript<>(lua, Long.class), keys);
                    log.info("定时任务回滚: orderId={}", order.getId());
                }
            } catch (Exception e) {
                log.error("定时回滚失败: orderId={}", order.getId(), e);
            }
        }
    }
}
```

#### 对账机制

```java
@Component
@Slf4j
public class SeckillReconciliationJob {

    /**
     * 每日凌晨 2:00 对账
     */
    @Scheduled(cron = "0 0 2 * * ?")
    public void reconcile() {
        // 昨天的秒杀活动
        List<SeckillActivity> activities = getYesterdayActivities();

        for (SeckillActivity activity : activities) {
            // 1. 从 MySQL 统计售出数量
            int soldInDb = orderService.count(new QueryWrapper<Order>()
                .eq("seckill_id", activity.getId())
                .in("status", "PAID", "UNPAID"));

            // 2. 从 Redis 计算减少量
            int initialStock = activity.getStock();
            int currentStock = getRedisStock(activity.getId());
            int reducedInRedis = initialStock - currentStock;

            // 3. 比对
            if (soldInDb != reducedInRedis) {
                log.warn("库存对账不一致！活动={}, DB售出={}, Redis减少={}",
                    activity.getId(), soldInDb, reducedInRedis);
                // 发送告警
                sendAlert(activity.getId(), soldInDb, reducedInRedis);
                // 以 DB 为准修正 Redis
                fixRedisStock(activity.getId(), initialStock - soldInDb);
            } else {
                log.info("对账一致: 活动={}, 售出={}", activity.getId(), soldInDb);
            }
        }
    }
}
```

#### 三种回滚方式的对比

| 方式 | 时效性 | 可靠性 | 资源消耗 | 适用场景 |
|------|-------|--------|---------|---------|
| 死信队列 | 精准 15min | 高（持久化+ACK） | 低 | **主方案** |
| 定时任务 | 1min~5min 延迟 | 极高（扫表硬核对） | 中（每分钟扫表） | **兜底方案** |
| 每日对账 | T+1 | 极高（DB 为准） | 低（凌晨执行） | **最终保障** |

### 追问应对

> 追问1：回滚库存时 Redis 刚好又宕机了怎么办？

- 回滚失败记录到**失败日志表**（MySQL）
- 另一个定时任务专门处理回滚失败的记录
- 最终以 MySQL 订单数据为准，Redis 库存可以重建

> 追问2：用户 14min 支付成功，15min 时回滚了怎么办？

秒杀场景下，这种**边界情况**的真实概率极低。处理方案：
1. 回滚前查一次订单状态（双重检查）
2. 如果出现回滚了但用户支付成功 → 对账发现不一致 → **人工介入退款**
3. 用户侧补偿：优惠券 + 道歉

### 🎯 核心要点

- **三重保障**：死信队列（主力）→ 定时任务（兜底）→ 每日对账（最终）
- 回滚的关键是**幂等性**，防止重复回滚
- Redis 库存回滚用 **Lua incr**，保证原子性
- 最终一致性 = 以 MySQL 订单数据为准

## 10. 高并发场景通用答题框架

### 面试官意图

考察你在任何高并发场景下能否系统化思考，而不是只会背秒杀答案。

### 答题模板

```
高并发场景答题框架 —— 5 步法

STEP 1：确认需求（避免答非所问）
  - QPS 多少？数据量级？
  - 一致性要求（强一致 vs 最终一致）？
  - 可用性要求（99.9% vs 99.99%）？

STEP 2：全链路分层（7 层展开）
  ┌─ 前端/CDN：静态资源、防重复、CDN
  ├─ Nginx：限流、动静分离
  ├─ Gateway：鉴权、路由、限流
  ├─ Service：业务逻辑、缓存、线程池
  ├─ MQ：削峰填谷、异步解耦
  ├─ Data：缓存层 + 持久层 + 分库分表
  └─ Monitor：监控告警、链路追踪

STEP 3：关键技术决策（每个决策都要说清 trade-off）
  | 决策点 | 方案 | 为什么 | 不选方案的原因 |

STEP 4：异常场景（展示深度）
  - 缓存挂了怎么办？
  - MQ 积压怎么办？
  - 超卖怎么办？
  - 响应慢怎么办？

STEP 5：扩展性思考（展示格局）
  - 10 倍流量怎么扩？
  - 如何演进到下一个架构？
  - 有什么可以简化的地方？

🎯 三个面试加分项：
  1. 实战数据：QPS 2000+、零超卖、15min 关单（用项目说话）
  2. 自省弱点：Redis 挂了会降级到什么程度（展示思考深度）
  3. Trade-off：每个方案都有取舍，没有银弹（展示成熟度）
```

### 高并发核心口诀

> **前端拦截，Nginx 限流，网关过滤，服务异步，缓存加速，MQ 削峰，数据库兜底，监控保航**

### 常见高并发场景速查

| 场景 | 核心思路 | 关键组件 | 常见坑 |
|------|---------|---------|-------|
| 秒杀 | Redis Lua 预减 + MQ 异步 | Redis + RabbitMQ + Lua | Redis 宕机、超卖 |
| 热点数据 | 多级缓存 + 本地缓存 | Caffeine + Redis + CDN | 缓存雪崩、缓存击穿 |
| 分布式锁 | Redisson + Lua | Redisson | 锁超时、可重入 |
| 限流 | 漏桶/令牌桶 + 滑动窗口 | Sentinel | 限流阈值设置不当 |
| 异步处理 | MQ 削峰填谷 | RabbitMQ / RocketMQ | 消息堆积、丢失 |
| 读写分离 | 主从复制 + 分库分表 | ShardingSphere + MySQL | 延迟一致性问题 |
