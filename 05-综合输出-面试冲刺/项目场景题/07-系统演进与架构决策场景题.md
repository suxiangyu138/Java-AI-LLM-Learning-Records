## 1. 从单体到微服务的演进过程与策略

> **面试官意图**：考察架构演进思维 + 拆分经验 + 数据迁移方案。没有一步到位的架构，能说清楚演进过程才是真懂。

### 答题框架：演进全景图

```
单体应用 ──→ 垂直拆分 ──→ 微服务 ──→ 服务网格
  (Flavor Dash)    (过渡期)   (SuGuangMall)   (未来展望)
```

### 标准回答：三步演进策略

#### 阶段一：单体架构（Flavor Dash 初期）

Flavor Dash 初期是一个典型的 Spring Boot 单体：

```
flavor-dash/
├── controller/       # 控制层
├── service/          # 业务层（含 AI 服务）
├── repository/       # 数据层
├── llm/              # LLM 调用模块
├── config/           # 配置
└── resource/         # 静态资源
```

**单体痛点**：
- 团队从 2 人扩张到 8 人，代码冲突频繁
- AI 模块迭代快，频繁发布影响订单稳定性
- 数据库连接池争抢：AI 模块的 Embedding 计算占用大量连接
- LLM 调用延时高（5~10s），阻塞 Tomcat 线程池

#### 阶段二：垂直拆分（过渡期策略）

拆分原则：**先拆无依赖服务 → 再拆核心链路 → 最后拆数据层**

```
┌────────────────────────────────────────────────────┐
│ 拆分第一刀：垂直拆分（按业务能力）                     │
│                                                      │
│  ┌────────────┐  ┌──────────┐  ┌────────────────┐   │
│  │ Order       │  │ User      │  │ LLM Gateway    │   │
│  │ Service     │  │ Service   │  │ Service        │   │
│  │ (核心订单)   │  │ (用户)    │  │ (AI 能力)      │   │
│  └──────┬──────┘  └─────┬────┘  └───────┬────────┘   │
│         │               │               │            │
│         └───────────────┼───────────────┘            │
│                         ▼                           │
│               ┌──────────────────┐                   │
│               │   API Gateway    │                   │
│               └──────────────────┘                   │
└────────────────────────────────────────────────────┘
```

**关键决策**：
```yaml
# 为什么先拆 LLM Gateway？
# 1. 对订单系统无依赖（独立团队维护）
# 2. 变更最频繁（每周 3~5 次发布）
# 3. 性能影响最大（需要独立扩缩容）
# 4. 暴露问题最快（有利于积累微服务经验）
```

**数据迁移方案（最重要环节）**：

```java
// 策略：双写 + 对账 + 切流

// Step 1: 双写阶段（持续 1~2 周）
public class OrderService {
    
    @Transactional
    public Order createOrder(OrderRequest request) {
        // 写入老表（单体数据库）
        Order oldOrder = oldOrderRepo.save(request);
        
        // 写入新表（新服务数据库）
        try {
            newOrderRepo.save(request);
        } catch (Exception e) {
            // 新表写入失败不影响主流程
            // 记录到对账表，后续补偿
            reconciliationLogService.logFailed(request);
            log.warn("新表写入失败，已记录对账", e);
        }
        
        return oldOrder;
    }
}

// Step 2: 对账阶段
// 定时任务：比对老表和新表的数据，补全不一致的记录
// SQL: SELECT * FROM old_order WHERE id NOT IN (SELECT old_id FROM new_order)

// Step 3: 切流阶段（灰度）
// 5% → 25% → 50% → 75% → 100%
// 每个阶段观察 2~3 天

// Step 4: 下线老表（数据迁移完成）
// 老表只读保留 1 个月，无异常后删除
```

### 演进式架构的关键原则

| 原则 | 说明 | 实践 |
|------|------|------|
| **增量变更** | 每次只改一点，不要大规模重写 | 每两周拆一个模块 |
| **可逆决策** | 拆分后也保留合并的可能性 | 模块间接口抽象，预留合并路径 |
| **数据先行** | 数据拆分最难，先设计好再动手 | 双写 + 对账 + 灰度切流 |
| **监控跟上** | 每一步拆分都有对应的监控 | 调用链、依赖图、数据库连接数 |
| **团队匹配** | 2 pizza team，一个团队负责 2~3 个服务 | 按业务域划分团队 |

> 💡 **面试追问 1**：拆分过程中出现分布式事务问题怎么解决？
> 
> 答：优先避免分布式事务（通过业务设计），不可避免时：(1) 最终一致性 + 对账补偿（Flavor Dash 做法）；(2) Seata AT 模式（SuGuangMall 做法）；(3) 本地消息表 + 定时任务。

> 💡 **面试追问 2**：拆成微服务后，查询效率反而低了怎么办？
> 
> 答：这是常见问题。解决方案：(1) CQRS（命令查询职责分离）；(2) 数据冗余（订单服务存一份用户基本信息）；(3) API 聚合层（BFF）；(4) 大屏查询从 Elasticsearch 查。

> 🎯 **核心要点**：架构演进的精髓在于"拆的时机"和"怎么拆"。面试中要体现出：(1) 理解单体不是原罪，小团队单体最合适；(2) 拆分有轻重缓急，先拆独立模块；(3) 数据迁移是最大难点，双写 + 对账是最稳的方案。一句话总结：不要为了微服务而微服务。

## 2. RAG 从 3 步到 14 步的演进，如何抽象通用框架？

> **面试官意图**：考察 AI 系统设计能力 + 抽象和封装思维。RAG 是 2024~2026 最热门的 AI 应用模式，能否抽象出通用框架决定了你是"调 API"还是"做系统"。

### 标准回答：RAG 演进路线

#### 从 3 步到 14 步的演进

```
┌─── RAG V1 (Flavor Dash) ─── 3 步 ───┐
│                                      │
│  Query ──→ Embedding ──→ Search ──→ LLM Generate  │
│                                      │
│  问题：召回质量差，没有 rerank，没有多轮对话上下文    │
└──────────────────────────────────────┘

┌─── RAG V2 (SuGuangMall) ─── 8 步 ────┐
│                                        │
│ Query → Rewrite → Embedding → Search   │
│        → Rerank → Context → LLM → Eval │
│                                        │
│  新增：Query 改写、Rerank、上下文压缩、答案评估  │
└────────────────────────────────────────┘

┌─── RAG V3 (LingShu) ─── 14 步 ────────┐
│                                         │
│ Query → Classify → Route → Rewrite →    │
│ SubQuery → Multi-Retrieval → Merge →   │
│ Rerank → Context Compress → ShortTerm   │
│ Memory → LongTerm Memory → LLM →       │
│ Verify → Citation → Eval               │
│                                         │
│  新增：意图分类、多路召回、Memory、验证、引用溯源  │
└─────────────────────────────────────────┘
```

#### 抽象通用 RAG 框架

核心思路：**将 RAG 流程抽象为可插拔 Pipeline**

```java
// 通用 RAG Pipeline 接口设计

// 1. Pipeline 定义
public interface RagPipeline {
    RagResponse execute(RagRequest request);
}

// 2. 组件接口
public interface RagComponent<I, O> {
    String name();              // 组件名称，用于配置和监控
    O process(I input, RagContext context);
    boolean enabled(RagRequest request);  // 条件启用
}

// 3. Pipeline 编排
public class DefaultRagPipeline implements RagPipeline {
    
    private final List<RagComponent<?, ?>> components;
    private final MetricsRegistry metrics;
    
    @Override
    public RagResponse execute(RagRequest request) {
        RagContext context = new RagContext(request);
        
        for (RagComponent<?, ?> component : components) {
            if (!component.enabled(request)) {
                log.debug("Component {} skipped", component.name());
                continue;
            }
            
            long start = System.currentTimeMillis();
            try {
                component.process(context.getInput(), context);
                metrics.record(component.name(), System.currentTimeMillis() - start);
            } catch (Exception e) {
                metrics.recordError(component.name());
                // 非关键组件失败可降级
                if (component.isCritical()) {
                    throw new RagException("Critical component failed: " + component.name(), e);
                }
                log.warn("Non-critical component {} failed, degraded", component.name(), e);
            }
        }
        
        return context.buildResponse();
    }
}

// 4. 必选模块 vs 可选模块
// 必选：Embedding、LLM Generate
// 可选：Query Rewrite、Rerank、Memory、Verify、Citation
```

> 💡 **面试追问 1**：RAG 演进中，哪一步带来的质量提升最大？
> 
> 答：Rerank（重排序）。没有 Rerank 时 Top-5 准确率约 65%，加上后升到 90%+。原因是 Embedding 相似度最高的文档不一定最相关，Rerank 模型能更好地理解 query 和文档的语义匹配。

> 💡 **面试追问 2**：RAG 做 AI 客服，怎么处理上下文长度限制？
> 
> 答：(1) 滑动窗口 + 摘要压缩历史；(2) 分层 Memory：短期（最后 N 轮）→ 中期（当天会话摘要）→ 长期（用户画像摘要）；(3) 最长上下文屏蔽，超过限制时用 LLM 压缩。

> 🎯 **核心要点**：RAG 不是简单的"搜索+LLM"，而是一套精密的 Pipeline 系统。面试中展示可插拔 Pipeline 设计 + 配置化 + 组件降级策略，说明你有系统设计能力，而不仅是调 API。

## 3. RocketMQ vs RabbitMQ vs Kafka 技术选型

> **面试官意图**：考察对消息队列的理解深度 + 结合业务场景做决策的能力。

### 答题框架：三维对比 + 选型依据

#### 核心对比表

| 维度 | RabbitMQ | RocketMQ | Kafka |
|------|---------|---------|-------|
| **定位** | 通用消息代理 | 金融级分布式 MQ | 分布式流处理平台 |
| **吞吐量** | 1~2 万/秒 | 10~100 万/秒 | 100~1000 万/秒 |
| **延迟** | 微秒级 | 毫秒级 | 毫秒级 |
| **消息可靠性** | 高（Confirm + 持久化） | 极高（同步刷盘 + 主从同步） | 高（ISR 副本机制） |
| **消息顺序** | 单队列有序 | 分区有序（支持严格顺序） | 分区有序 |
| **延时消息** | 插件支持 | 原生支持（18 个级别） | 不支持 |
| **死信队列** | 原生支持 | 原生支持 | 需自建 |
| **事务消息** | 需插件 | 原生支持（半消息机制） | 0.11+ 支持 |
| **消息回溯** | 不支持 | 支持按时间回溯 | 支持 offset 回溯 |
| **语言生态** | 多语言（Java/Go/Python/...） | Java 为主 | 多语言 |
| **运维复杂度** | 低 | 中 | 高 |
| **监控** | 自带管理界面 | 支持 Prometheus + Grafana | 需要 JMX + 第三方 |
| **社区活跃度** | 极活跃 | 活跃（阿里主导） | 极活跃 |

#### 选型决策树

```
是否只需要消息推送/异步解耦？
├── 是 → 是否需要高吞吐（>5万/秒）？
│   ├── 是 → 是否需要事务消息？
│   │   ├── 是 → RocketMQ
│   │   └── 否 → Kafka
│   └── 否 → 运维能力如何？
│       ├── 强 → RocketMQ（功能丰富）
│       └── 弱 → RabbitMQ（运维简单）
├── 否 → 是否需要流处理（Kafka Streams/ksqlDB）？
│   ├── 是 → Kafka
│   └── 否 → 是否需要金融级事务？
│       ├── 是 → RocketMQ
│       └── 否 → RabbitMQ
└── 是否需要顺序消息 + 重试机制丰富？
    ├── 是 → RabbitMQ（推荐）/ RocketMQ
    └── 否 → Kafka
```

#### Flavor Dash 选 RabbitMQ 的原因

```yaml
选择 RabbitMQ 的决策依据：
  1. 规模匹配：Flavor Dash 初期 QPS < 1000，RabbitMQ 完全够用
  2. 运维简单：Erlang 安装配置简单，管理界面功能完善
  3. 灵活路由：Topic/Header/Fanout/Direct 四种 Exchange，满足各类业务场景
  4. 延迟消息：通过死信队列能实现 15min 关单等复杂策略
  5. 社区活跃：中文文档丰富，出现问题容易搜到解决方案
  6. 资源占用：比 RocketMQ 轻量，服务器成本低

不适合的点（但初期可以接受）：
  - 吞吐量上限低（不到 5 万/秒）
  - 消息堆积后性能下降严重
  - 不支持消息回溯
```

#### SuGuangMall 选 RocketMQ 的原因

```yaml
选择 RocketMQ 的决策依据：
  1. 吞吐需求：压测峰值 2000+ QPS，但预留 5 倍冗余，需要支撑万级吞吐
  2. 事务消息：订单系统需要分布式事务（Seata + 半消息），RocketMQ 原生支持
  3. 延时消息：秒杀场景 15min 关单，RocketMQ 原生支持 18 级延时
  4. 消息回溯：排查问题时可以按时间回溯消费
  5. 批量消费：更强大的批量拉取能力
  6. 阿里生态：与 Nacos/Sentinel/Seata 同属阿里系，集成无缝

不适合的点：
  - 客户端仅 Java（限制了多语言调用）
  - 运维比 RabbitMQ 复杂（需要 NameServer + Broker 分离部署）
  - 资源消耗更大
```

#### Kafka 不适合的场景

| 场景 | Kafka 的短板 |
|------|------------|
| 延时/定时消息 | 原生不支持，需要自建 |
| 死信队列 | 需要自己实现死信重试机制 |
| 消息精确投递 |Exactly Once 配置复杂，有性能损耗 |
| 小规模业务 | 运维成本高（需要 Zookeeper/KRaft） |
| 需要丰富路由规则 | 只支持 Topic 分区，没有 Exchange 灵活 |
| 在线业务场景 | 吞吐量溢出，过于"重" |

> 💡 **面试追问 1**：RabbitMQ 宕机了怎么办？
> 
> 答：RabbitMQ 集群用镜像队列模式（Mirrored Queue）实现主从同步。宕机一个节点后，其他节点仍有完整数据。备选方案：如果数据量不大，可以用 MQ + DB 双写，MQ 不可用时降级到数据库直连。

> 💡 **面试追问 2**：Kafka 为什么吞吐量最高？
>

## 5. Flavor Dash 要支撑日均 10W 单，架构怎么改？

> **面试官意图**：考察容量规划 + 分布式架构设计能力。这是系统设计题的变体，但更贴近真实项目。

### 标准回答：容量规划 + 架构升级方案

#### 第一步：容量规划

```
日均 10W 单的 QPS 估算：
  白天 8 小时（28800 秒）处理 90% 流量
  QPS = 100,000 * 0.9 / 28800 ≈ 3.1
  峰值（秒杀/促销）按 10 倍算 ≈ 30 QPS

虽然 30 QPS 不高，但需要考虑：
  - 查询 QPS（商品浏览）：通常是下单的 100 倍 ≈ 3000 QPS
  - 搜索 QPS：浏览的 20% ≈ 600 QPS
  - AI 服务 QPS（推荐/问答）：浏览的 10% ≈ 300 QPS
  - 秒杀峰值：瞬时可能是 100~200 QPS
```

**硬件规划**：

| 组件 | 当前（日均 1K 单） | 10W 单 | 选型建议 |
|------|:----------------:|:------:|---------|
| 应用服务器 | 2 台 4C8G | 6 台 8C16G | Docker/K8s 部署，方便弹性伸缩 |
| 数据库 | 1 台 4C16G MySQL | 2 主 4 从 | 分库分表（ShardingSphere） |
| Redis | 1 台 4G | Redis Cluster 12G（3 主 3 从） | 多级缓存 + 缓存 TTL 优化 |
| MQ | RabbitMQ 单机 | RabbitMQ 集群 3 节点 | 或升级 RocketMQ（如果事务需求复杂） |
| 对象存储 | 本地 | OSS（阿里云/MinIO） | 图片、文档等静态资源上云 |
| CDN | 无 | 配置 CDN | 静态资源加速 |
| ES | 无 | 3 节点集群 | 商品搜索 + 订单检索 |

#### 第二步：架构升级路线

```
Phase 1（当前→QPS 50）：    单体 + 读写分离
Phase 2（QPS 50→200）：        垂直拆分 + 缓存 + MQ
Phase 3（QPS 200→1000）：      微服务 + 分库分表 + ES
Phase 4（QPS 1000+）：         服务网格 + 单元化 + 异地多活
```

**Phase 1 具体方案（当前→10W 单最直接的改造）**：

```java
// 多级缓存实现
public class MultiLevelCacheService {
    
    private final Cache<String, Object> localCache;  // Caffeine
    private final StringRedisTemplate redisCache;     // Redis
    private final DatabaseService databaseService;    // DB
    
    public Object get(String key) {
        // 1. 查本地缓存
        Object local = localCache.getIfPresent(key);
        if (local != null) return local;
        
        // 2. 查 Redis
        String redisValue = redisCache.opsForValue().get(key);
        if (redisValue != null) {
            localCache.put(key, redisValue);  // 回填本地
            return redisValue;
        }
        
        // 3. 查数据库
        Object dbValue = databaseService.query(key);
        if (dbValue != null) {
            redisCache.opsForValue().set(key, serialize(dbValue), 1, TimeUnit.HOURS);
            localCache.put(key, dbValue);
        }
        return dbValue;
    }
}
```

## 6. 普通下单和秒杀的本质区别与架构差异

> **面试官意图**：考察对两类核心电商场景的深度理解，区分"做过项目"和"深入思考过"。

### 标准回答：本质区别对比

#### 核心区别表

| 维度 | 普通下单 | 秒杀 |
|------|---------|------|
| **流量特征** | 平稳，QPS 稳定 | 瞬时峰值，QPS 暴涨 100~1000 倍 |
| **并发冲突** | 低，很少争抢同一商品 | 极高，万人抢 1 件商品 |
| **一致性要求** | 强一致性（ACID 事务） | 最终一致性（允许短暂超卖再回滚） |
| **库存处理** | UPDATE stock SET stock = stock - 1 WHERE stock > 0 | Redis Lua 预占 → 异步扣减 |
| **响应时间** | 用户可以等 1~2s | 必须在 100ms 内响应"抢到了/没抢到" |
| **事务策略** | 数据库事务（@Transactional） | 补偿事务（TCC / 本地消息表） |
| **设计目标** | 数据准确 > 用户体验 | 用户体验 > 绝对准确（允许少卖，不能超卖） |

#### 架构差异对比

```
┌──── 普通下单架构 ────┐        ┌──── 秒杀下单架构 ────┐
│                       │        │                       │
│  用户点击 → 创建订单   │        │  用户点击 → 前端限流   │
│  → 校验库存(DB行锁)    │        │  → Nginx 限流         │
│  → 扣减库存(DB行锁)    │        │  → Gateway 限流       │
│  → 生成订单(DB事务)    │        │  → Redis 预占库存     │
│  → 返回订单号          │        │  → MQ 异步创建订单    │
│  → 支付流程            │        │  → DB 最终扣减        │
│                       │        │  → 返回"抢购成功"      │
│  QPS: 100~500         │        │  QPS: 10,000+         │
│  响应: ~200ms          │        │  响应: < 50ms          │
│  事务: 强一致          │        │  事务: 最终一致        │
└───────────────────────┘        └───────────────────────┘
```

#### 关键设计差异详解

**1. 库存扣减策略**

```java
// 普通下单：数据库行锁扣减
@Transactional
public Order createOrder(OrderRequest req) {
    // 行锁：SELECT ... FOR UPDATE
    Product product = productMapper.selectForUpdate(req.getProductId());
    if (product.getStock() < req.getQuantity()) {
        throw new StockException("库存不足");
    }
    // 扣减
    productMapper.deductStock(req.getProductId(), req.getQuantity());
    // 创建订单
    return orderMapper.insert(req);
}

// 秒杀：Redis Lua 预占 + MQ 异步扣减
// 预占阶段（Redis Lua）
public boolean trySeckill(Long userId, Long skuId) {
    String lua = """
        local stock = redis.call('get', KEYS[1])
        if not stock or tonumber(stock) <= 0 then
            return 0  -- 已售罄
        end
        local bought = redis.call('sismember', KEYS[2], ARGV[1])
        if bought == 1 then
            return -1  -- 已经抢过
        end
        redis.call('decr', KEYS[1])
        redis.call('sadd', KEYS[2], ARGV[1])
        return 1  -- 抢购成功
    """;
    Long result = redisTemplate.execute(
        new DefaultRedisScript<>(lua, Long.class),
        Arrays.asList("stock:" + skuId, "bought:" + skuId),
        userId.toString()
    );
    if (result == 1) {
        // 发 MQ 异步创建订单
        mqSender.send("order.create", new OrderMessage(userId, skuId));
    }
    return result == 1;
}

// 异步扣减阶段（MQ Consumer）
@RabbitListener(queues = "order.create")
public void handleOrderCreate(OrderMessage msg) {
    // 实际扣减库存（乐观锁）
    int rows = productMapper.deductStockByOptimisticLock(
        msg.getSkuId(), 
        1, 
        stockVersion  // 版本号
    );
    if (rows > 0) {
        orderMapper.insert(msg.toOrder());
    } else {
        // 库存已被抢完，回滚 Redis 预占库存
        redisTemplate.opsForValue().increment("stock:" + msg.getSkuId());
        log.warn("库存扣减失败，回滚 Redis 预占库存: {}", msg.getSkuId());
    }
}
```

**2. 事务策略差异**

| 策略 | 普通下单 | 秒杀 |
|------|---------|------|
| **事务模型** | 本地事务（@Transactional） | 分布式事务（TCC / SAGA） |
| **补偿机制** | 事务回滚 | 定时关单 + 库存回滚 |
| **一致性** | 强一致（ACID） | 最终一致（BASE） |
| **超时处理** | 数据库锁超时 | MQ 死信延迟队列（15min 关单） |
| **幂等方案** | 唯一索引 + 重试 | 唯一订单号 + Redis 防重复 |

**3. 限流策略差异**

```yaml
# 普通下单：相对简单的限流
spring:
  cloud:
    sentinel:
      flow-rules:
        - resource: "createOrder"
          grade: 2       # QPS
          count: 200     # 单机 200 QPS
          controlBehavior: 0  # 快速失败

# 秒杀：多层限流
# 1. 前端限流：按钮灰化 + 验证码 + 5 秒内只能点一次
# 2. Nginx 限流：单 IP 1 秒 1 次
# 3. Gateway 限流：接口级 QPS 1000
# 4. 服务层限流：Sentinel 热点限流，同一商品 1 秒 10 次
# 5. Redis 预占：原子脚本保证不超卖
```

> 💡 **面试追问 1**：秒杀场景下，Redis 预占库存 + MQ 异步扣减，最坏情况下会超卖吗？
> 
> 答：理论上有极小概率超卖（Redis 到 MQ 到 DB 扣减之间发生）。所以需要 DB 层做最后兜底——乐观锁或库存字段设为无符号整数（`stock >= 0` 约束）。SuGuangMall 实测零超卖就是用"Redis Lua + 数据库乐观锁"双保险。

> 💡 **面试追问 2**：秒杀库存的 Redis 预热怎么做？
> 
> 答：系统启动或秒杀开始前，将商品库存从 DB 加载到 Redis：`SET stock:skuId 100`。预热时注意 DB 和 Redis 的数据一致性，使用分布式锁保证预热过程中没有误扣减。

> 🎯 **核心要点**：普通下单和秒杀的本质区别是"流量确定 vs 流量峰值"和"数据强一致 vs 用户体验优先"。架构的核心差异在于：库存扣减从 DB 行锁变为 Redis Lua，事务从 ACID 变为 BASE，响应从同步变为异步。能说出这些本质差异，说明你理解了不是"加个缓存"那么简单。

#### 还债优先级矩阵

| 优先级 | 技术债类型 | 判断标准 | 案例 |
|:------:|-----------|---------|------|
| **P0** | 影响线上稳定性的 | 可能导致 P0 事故 | 连接泄露、未设置超时 |
| **P1** | 阻碍业务迭代的 | 每次加功能都要改这里 | 硬编码的 Tool Schema |
| **P2** | 影响开发效率的 | 上下文切换成本高 | 重复代码、缺乏单元测试 |
| **P3** | 影响代码可读性的 | 不影响功能，但难维护 | 命名不规范、缺注释 |

> 💡 **面试追问 1**：技术债要不要还？什么时机还？
> 
> 答：不是所有技术债都要还。判断标准：(1) 这个债是否影响当前开发效率；(2) 是否阻碍了新功能上线；(3) 还债的风险是否可控。建议在每次迭代中分配 20% 的容量做技术债清理。

> 💡 **面试追问 2**：怎么说服业务方同意还技术债？
> 
> 答：不要说"代码重构"，要说业务语言：(1) "现在加这个功能需要 5 天，还完债后只需要 1 天"；(2) "不修这个漏洞，双 11 可能宕机 30 分钟"；(3) 用"时间和成本"而不是"技术质量"来说服。

> 🎯 **核心要点**：面试中能主动说出"技术债务"，说明你有反思精神。但关键在于：(1) 能识别具体的技术债案例；(2) 有实际的还债方案；(3) 知道还债的优先级判断。不要说"我写过烂代码"，要说"我在什么场景下留了债，后来用什么方案还了，收益是什么"。

> 💡 **面试追问 1**：AI 中台和普通中台的区别是什么？
> 
> 答：(1) AI 中台的"计算资源"不是 CPU 而是 GPU，成本高得多；(2) 模型版本管理（模型 A/B 测试）；(3) Token 用量和成本分摊是所有 AI 中台都要解决的问题；(4) 内容安全（敏感词 + 隐私保护 + 内容审核）。

> 💡 **面试追问 2**：AI 中台如果宕机了，所有业务线都会受影响，怎么保证高可用？
> 
> 答：(1) 多模型降级——主模型超时自动切换备用模型；(2) 缓存相同 Query（缓存命中率约 30~50%）；(3) 本地备选方案（离线模型）；(4) 多活部署（至少 2 个 Region）；(5) 熔断 + 快速失败，避免连锁反应。

> 🎯 **核心要点**：AI 中台设计的关键是"多租户 + 配额管理 + 成本分摊"。面试中要体现出：(1) 你考虑到了不同业务线的不同需求（模型选择、配额不同）；(2) 你考虑到了成本控制（按量计费）；(3) 你考虑到了安全（内容审核 + 数据隔离）。

## 9. 架构决策通用框架

### ADR（Architecture Decision Record）模板

```markdown
# ADR-001：选择 RabbitMQ 作为消息中间件

## 状态
[√] 已接受
[ ] 已否决
[ ] 已废弃

## 背景
Flavor Dash 需要一个消息中间件来处理：
1. 订单创建的异步处理
2. 支付超时关单（延迟消息）
3. 服务间解耦

## 约束
- 团队 3 人，运维能力有限
- 初期 QPS < 1000
- 需要延迟消息功能
- 技术栈以 Java + Spring Boot 为主

## 方案对比

| 方案 | 优势 | 劣势 |
|------|------|------|
| RabbitMQ | 运维简单、延迟消息支持、灵活路由 | 吞吐上限低（5万/s） |
| RocketMQ | 高吞吐、事务消息、延迟消息 | 运维复杂，仅 Java |
| Kafka | 极高吞吐、流处理 | 无延迟消息、运维复杂 |

## 决策
选择 RabbitMQ

## 依据
1. 满足当前 QPS 需求（< 1000）
2. 运维成本最低
3. 延迟消息满足业务需求
4. 团队有 RabbitMQ 使用经验

## 后果
正面：
- 快速实现异步订单处理
- 延迟关单功能 1 天内上线

负面：
- 将来 QPS 超过 1 万时需要迁移到 RocketMQ
- RabbitMQ 消息堆积后性能下降明显

## 后续改进
- 在 Queue 上设置 x-max-length 限制积压
- 监控队列深度，配置告警
- 预留 RocketMQ 迁移路径（消息接口抽象）
```

### CAP 权衡决策矩阵

| 场景 | 对 C 的要求 | 对 A 的要求 | 对 P 的要求 | 倾向 |
|------|:---------:|:---------:|:---------:|------|
| 支付系统 | 高（钱不能错） | 中（可以等一下） | 高 | CP |
| 商品搜索 | 低（数据稍旧可接受） | 高（不能报错） | 高 | AP |
| 用户登录 | 高（密码不能错） | 高（快速响应） | 高 | CP + 缓存 |
| 订单状态 | 中（状态短暂不一致可接受） | 高（不能失败） | 高 | AP + 补偿 |
| 库存扣减 | 高（不能超卖） | 高（高并发也不能挂） | 高 | CP + 最终一致 |

### 演进式架构三大核心原则

在 Flavor Dash → SuGuangMall → LingShu 的演进过程中，我们逐步沉淀出三个核心原则：

#### 原则 1：最后责任时刻（Last Responsible Moment）

> 将决策推迟到"不做决策的代价 > 做错决策的代价"的那一刻。

```yaml
核心理念：
  - 过早决策 → 被错误的约束框死，后续改动成本巨大
  - 过晚决策 → 影响开发进度，技术债堆积
  - 最佳时机：当信息足够充分，且不决策开始阻碍进展时

Flavor Dash 案例：
  - 消息队列选型：前 3 个月用 DB + 定时任务临时替代
    - 做决策的代价：选错 MQ 迁移成本高
    - 不做决策的代价：DB 轮询越来越慢
    - 最后时刻点：QPS 超过 500，DB 轮询延迟超过 5s
    - 到这一刻，我们确认了 QPS 模式，选了 RabbitMQ

SuGuangMall 案例：
  - 分库分表策略：先不分表，用 MySQL 单表硬扛
    - 做决策的代价：分片键选错后续无法修改
    - 最后时刻点：单表超过 500W 行，查询延迟 > 200ms
    - 到这一刻，我们充分了解了查询模式，选了 user_id 作为分片键

LingShu 案例：
  - RAG 框架设计：先用最简单的 3 步，逐步增加组件
    - System 1 (3步): 解决"有没有"的问题
    - System 2 (8步): 解决"好不好"的问题
    - System 3 (14步): 解决"稳不稳"的问题
    - 每一步的决策都在"当前方案不够好"的时刻做出

判断方法：
  - [ ] 这个决策是否影响后续多个模块？
  - [ ] 是否有前置依赖需要先验证？
  - [ ] 不决策会阻碍其他人工作吗？
  - [ ] 反向决策的成本有多高？
  # 如果以上大部分回答"是"，就是最后责任时刻。
```

#### 原则 2：可逆决策（Reversible Decisions）

> 好的架构决策不一定是"正确的"，而是"容易逆转的"。

```yaml
第一层次（接口抽象）：
  - 所有服务间调用走接口，不要直接依赖实现
  - Spring Cloud Feign / OpenFeign 接口定义
  - 收益：即使以后合并不用改调用方代码
  
  案例：Flavor Dash 的 LLM Gateway 接口
  public interface LlmGateway {
      ChatResponse chat(ChatRequest request);
  }
  // 实现可以是 HTTP 调用 / gRPC / 本地进程调用
  // 可逆：如果合并回单体，只需换一个 LocalLlmGateway 实现

第二层次（数据抽象）：
  - 数据库表设计保留扩展字段
  - 用 MySQL JSON 类型存扩展属性
  - 收益：分表后跨表字段变化不用改 Schema
  
  案例：订单表的 extra 字段
  CREATE TABLE t_order (
      id BIGINT PRIMARY KEY,
      user_id BIGINT,
      -- 核心字段强类型
      status TINYINT,
      total_amount DECIMAL(10,2),
      -- 扩展字段用 JSON
      extra JSON COMMENT '扩展属性：渠道、标签、优惠信息等'
  );

第三层次（部署抽象）：
  - 容器化部署（Docker + K8s）
  - 收益：单体 / 微服务 / 服务网格都可以部署在同一套 K8s 上
  - 可逆：从微服务退化为单体只需要合并镜像，不改代码

可逆决策清单：
  [ ] 这个决策能否在 1 天内逆转？
  [ ] 逆转的影响范围是否受控？
  [ ] 是否有 feature flag 控制？
  [ ] 接口层面是否做了适配层？
```

#### 原则 3：适应度函数（Fitness Functions）

> 定义架构的"健康指标"，用自动化验证来保证架构演进不偏离目标。

```yaml
定义：一组可量化的架构度量指标，持续验证架构是否符合预期。

Flavor Dash 的适应度函数：
  - 性能维度：接口 P99 < 500ms
  - 可用性维度：系统可用性 > 99.9%（月度）
  - 耦合维度：模块间调用深度 < 3 层
  - 测试维度：核心链路测试覆盖率 > 80%

SuGuangMall 的适应度函数（升级）：
  - 新增：服务间调用延迟 P99 < 50ms（内网）
  - 新增：数据库连接数 < 80%
  - 新增：缓存命中率 > 90%
  - 新增：分库分表后的跨分片查询占比 < 5%
  - 新增：MQ 积压告警（队列深度 > 10000）

LingShu 的适应度函数（AI 专项）：
  - LLM 调用：P99 延迟 < 3s（含推理）
  - RAG 检索：Top-5 准确率 > 85%
  - Token 成本：单次问答成本 < ¥0.01
  - 护栏效果：敏感内容拦截率 > 99.9%

实现方式：
  # Prometheus + Grafana 采集和可视化
  # 持续集成流水线中定期运行
  # 偏离阈值自动告警
  
适应度函数的核心思想：
  - 不要等到架构"出问题"才改
  - 定义好"什么算好"的标准
  - 持续测量，发现偏离及时调整
  - 适应度函数本身也要随架构演进
```

#### 其他演进式原则

```yaml
原则 4：只做必要的抽象
  - 问题：过早抽象 → 过度设计
  - 判断：是否有 3 个以上的类似场景需要复用？
  - 案例：LLM 网关在 Flavor Dash 第 3 次 LLM 调用时抽出

原则 5：增量优于重写
  - 重写老系统 → 90% 的项目死在这步
  - 总是在现有系统上做增量改进
  - 案例：Flavor Dash 先拆 LLM Gateway（不影响订单），再拆订单（双写过渡）

原则 6：架构是对未来的预测，但别预测太远
  - 预测 3 个月够用："下个月双十一流量翻倍"
  - 预测 3 年不靠谱："五年后我们要服务一亿用户"

原则 7：监控先行
  - 架构变更前：先加上监控指标
  - 架构变更中：对比前后指标变化
  - 架构变更后：持续观察 1 周
```

```
[ ] 可观测性：变更后怎么确认效果？
[ ] 团队能力：团队能否掌握这个新技术？
[ ] 演进路径：这个决策是否为后续演进留了路？
```

> 💡 **面试追问 1**：面试官问"如果让你设计 XX 系统"的时候，你要怎么回答？
> 
> 答：不要一上来就画大架构！标准答题框架应该是：(1) 确认需求（QPS/数据量/一致性要求）；(2) 给出候选方案对比；(3) 结合约束做决策；(4) 设计粗略架构；(5) 指出可能的瓶颈和演进方向。

> 🎯 **核心要点**：架构决策的终极心法——没有最好，只有最合适。面试中展现出"权衡"思维比展示"大全套"架构更重要。ADR 是行业最佳实践，面试中提到它说明你有正规的架构设计流程。永远不要说"XX 技术一定比 YY 好"，要说"在 XX 约束下，选择 YY 更合适"。

## 10. 技术选型决策树（10 个常见场景的快速决策路径）

> **面试官意图**：考察对技术选型的全局把握能力。面试中遇到"为什么选 X 不选 Y"的问题，本质上都在考"你是否有自己的选型框架"。

### 统一决策框架

在做任何技术选型之前，先问自己四个问题：

```
① 我的场景是什么？     →  在线业务 / 离线计算 / AI 推理 / 数据存储
② 我的约束是什么？     →  团队能力 / 运维成本 / 预算 / 时间窗口
③ 我的规模是什么？     →  日均 QPS / 数据量 / 并发数
④ 我的未来是什么？     → 未来 6 个月的预期增长 / 可能的架构变化
```

### 场景 1：消息队列选型

```
输入条件：
  QPS < 5000                    → RabbitMQ
  QPS 5000~10万，需要事务消息   → RocketMQ
  QPS > 10万，需要流处理        → Kafka
  团队运维能力弱                → RabbitMQ（最省心）
  需要延迟消息                  → RabbitMQ（插件） / RocketMQ（原生）
  需要消息回溯                  → RocketMQ / Kafka

一句话决策：
  "初创期用 RabbitMQ（运维简单），成长期用 RocketMQ（功能全面），
   数据部门用 Kafka（流处理）"
```

### 场景 2：数据库选型

```
输入条件：
  关系型数据，事务要求高            → MySQL（默认选型）
  关系型数据，读写比 10:1 以上       → MySQL + 读写分离
  关系型数据，单表 > 500W 行        → MySQL + 分库分表（ShardingSphere）
  非关系型，缓存场景                → Redis
  非关系型，文档存储                → MongoDB
  非关系型，图关系                  → Neo4j
  搜索引擎                          → Elasticsearch
  时序数据（监控/指标）              → Prometheus + VictoriaMetrics / TDengine
  向量数据（AI Embedding）          → Milvus（推荐）/ Qdrant / pgvector

面试贴士：
  - 不要为了"新技术"而用 MongoDB/ES，MySQL 能解决 90% 的问题
  - 面试官问数据库选型，真正想听的是"你什么时候该用 NoSQL"
  - 推荐策略：MySQL 兜底 + Redis 缓存 + ES 搜索 + Milvus 向量
```

### 场景 3：缓存选型

```
输入条件：
  单机缓存，不需要共享            → Caffeine（内存级，性能王者）
  分布式缓存，需要共享            → Redis（标准答案）
  Redis 高可用                   → Redis Sentinel（主从切换）
  Redis 海量数据                 → Redis Cluster（分片）
  多级缓存                       → Caffeine（L1）+ Redis（L2）+ DB（L3）
  本地缓存需要 TTL 和淘汰策略    → Caffeine / Guava Cache
  需要持久化缓存                 → Redis RDB/AOF

性能数据：
  Caffeine 本地缓存：读 QPS 100万+（毫秒级）
  Redis 分布式缓存：单机 QPS 5~10万（毫秒级）
  数据库缓存：QPS 1000~5000（~10ms 级）
  
  策略：先扛 80% 读请求在本地缓存，15% 在 Redis，5% 落 DB
```

### 场景 4：微服务框架选型

```
输入条件：
  Spring 生态，Java 技术栈     → Spring Cloud Alibaba（国内推荐）
  Spring 生态，但团队小         → Spring Cloud Netflix（轻量）
  不需要完整微服务，仅需 RPC    → Dubbo / OpenFeign
  云原生，多语言               → Istio + gRPC（服务网格）
  需要全链路灰度               → Spring Cloud Alibaba + Nacos
  需要快速开发                 → Spring Boot 单体 + 预留微服务拆分

项目实践：
  Flavor Dash：Spring Boot 单体 → 拆 Feign 接口
  SuGuangMall：Spring Cloud Alibaba（Nacos + Sentinel + Seata）
  LingShu：Spring Cloud Alibaba + Dubbo（部分服务）
```

### 场景 5：AI 模型选型

```
输入条件：
  通用对话，中文为主               → DeepSeek（性价比之王）
  复杂推理，英文为主               → Claude（推理能力强）/ GPT-4o
  实时聊天（延时敏感）              → DeepSeek-V4 / GPT-4o-mini
  离线批量处理                     → DeepSeek / Llama（本地部署）
  垂直领域（代码/法律/医疗）        → 领域微调模型 / RAG + 通用模型
  图片理解                         → GPT-4o / Claude 3.5
  文档理解（长文本）                → DeepSeek（1M Token 上下文）
  嵌入 Embedding                  → BGE-M3（最优国产）/ text-embedding-3

成本参考（2026.07）：
  DeepSeek-V4：输入 ¥0.001/1K tokens，输出 ¥0.002/1K tokens
  GPT-4o：输入 $0.0025/1K tokens，输出 $0.01/1K tokens
  Claude 3.5 Sonnet：输入 $0.003/1K tokens，输出 $0.015/1K tokens
  
  策略：80% 请求走 DeepSeek，20% 复杂推理走 Claude/GPT
```

### 场景 6：RAG 方案选型

```
输入条件：
  简单问答（< 1000 文档）           → OpenAI/DeepSeek API + 简单向量库
  中型知识库（1万~10万文档）        → LangChain4j + Milvus + BGE-M3
  大型知识库（> 100万文档）         → 分库 + 多路召回 + 重排序
  需要高准确率                     → Query Rewrite + Rerank + 引用溯源
  实时性要求高                     → 缩短检索窗口 + 缓存命中
  多模态搜索                       → 多向量 + 跨模态检索
  需要多轮对话                     → 添加 Memory 模块（短期+长期）

Flavor Dash：3 步（Embedding + Search + Generate）
SuGuangMall：8 步（+ Rewrite + Rerank + Context + Eval）
LingShu：14 步（+ Classify + Route + Memory + Verify + Citation）
```

### 场景 7：容器化与部署选型

```
输入条件：
  单机部署，小团队           → Docker Compose（最简单）
  多机部署，自运维           → Docker Swarm / 手动部署
  多机部署，云原生           → Kubernetes（标准答案）
  需要 CI/CD                → GitHub Actions / GitLab CI / Jenkins
  需要自动化部署             → ArgoCD（GitOps）/ Spinnaker
  需要服务网格               → Istio / Linkerd
  需要 Serverless           → AWS Lambda / 阿里云函数计算
  监控（容器）               → Prometheus + Grafana + AlertManager
  日志                      → ELK（Elasticsearch + Logstash + Kibana）
  调用链                    → SkyWalking / Jaeger / Zipkin

演进路径：
  Docker Compose → K8s（需要专业 OPS）
  推荐：先容器化，再编排，最后服务网格
```

### 场景 8：API 网关选型

```
输入条件：
  Spring 生态，需要 Java 定制   → Spring Cloud Gateway（推荐）
  高性能，多语言               → Kong / APISIX
  云原生，K8s 原生             → Nginx Ingress / Traefik
  需要 API 管理全生命周期        → Apifox / Apigee / Kong
  需要限流熔断                  → Spring Cloud Gateway + Sentinel
  需要灰度发布                  → Nacos + Spring Cloud Gateway
  需要动态路由                  → Spring Cloud Gateway + Nacos

对比参考：
  Spring Cloud Gateway：Java 生态最佳，易扩展，性能中等
  Kong：基于 OpenResty，性能好，插件丰富
  APISIX：国产，性能优于 Kong，Apache 基金会
  Nginx Ingress：K8s 默认，功能简单但稳定
```

### 场景 9：注册中心与配置中心选型

```
输入条件：
  需要 AP（高可用优先）         → Nacos / Eureka
  需要 CP（强一致优先）         → Nacos / Consul / Zookeeper
  Spring Cloud 生态            → Nacos（推荐）/ Eureka（维护模式）
  多语言支持                   → Consul / Nacos
  需要配置中心                 → Nacos（推荐）/ Apollo（携程）/ Spring Cloud Config
  需要服务网格                 → Nacos + Istio / Consul + Istio

三项目实践：
  Flavor Dash：未使用（配置写 application.yml，缺点：改配置需重启）
  SuGuangMall：Nacos（注册中心 + 配置中心）
  LingShu：Nacos + Apollo（配置多环境管理）

为什么选 Nacos？
  - 同时支持注册中心和配置中心（减少组件）
  - 支持 CP + AP 切换
  - 与 Spring Cloud Alibaba 无缝集成
  - 国产，文档丰富
```

### 场景 10：监控与可观测性选型

```
输入条件：
  需要 Metrics                  → Prometheus + Grafana（标准答案）
  需要 Logging                  → ELK（推荐）/ Loki（轻量）
  需要 Tracing                  → SkyWalking（推荐）/ Jaeger / Zipkin
  需要 APM 全链路               → SkyWalking / Datadog / 阿里云 ARMS
  需要告警                      → AlertManager / 飞书/钉钉 Webhook
  需要健康检查                  → Spring Boot Actuator（基础）/ K8s Probe
  需要审计日志                  → 自建（切面注解 + 数据库）

推荐组合（性价比最高）：
  Prometheus + Grafana（指标）
  + ELK（日志）
  + SkyWalking（调用链）
  + AlertManager（告警）
  = 完整的可观测性体系

注意事项：
  - 监控要"先于"架构变更搭建，而不是之后补
  - 不要追求 100% 覆盖，核心链路先覆盖（订单、支付、AI 调用）
  - 告警要有分级：P0（立即处理）/ P1（15min）/ P2（1h）/ P3（日报）
```

### 技术选型通用避坑指南

```yaml
常见的选型错误：
  1. 为了新技术而选型
     - 错误："Kafka 很火，所以我们要用 Kafka"
     - 正确："我们的日志系统需要 50 万 QPS 吞吐，所以选 Kafka"
  
  2. 过早优化
     - 错误："将来可能到 10 万 QPS，先上 RocketMQ"
     - 正确："当前 1000 QPS 用 RabbitMQ，预留 RocketMQ 迁移路径"
  
  3. 忽略运维成本
     - 错误：选了一个需要专人维护的组件（如 ZooKeeper + Kafka）
     - 正确：评估团队运维能力，选择能力范围内的技术栈
  
  4. 忽略社区生态
     - 错误：选了一个没有中文文档的冷门框架
     - 正确：优先选社区活跃、中文文档丰富的方案
  
  5. 忽略迁移成本
     - 错误：选了个无法渐进式迁移的方案
     - 正确：选择支持双活/灰度迁移的方案
```

> 💡 **面试贴士 1**：面试中被问到技术选型时，不要只回答选了什么，要给出决策过程。使用"背景 → 约束 → 方案对比 → 决策 → 后果"的五步框架。

> 💡 **面试贴士 2**：如果面试官追问"你选的这个有什么缺点？"，不要回避。坦诚地说出缺点 + 后续改进计划，这比吹得天花乱坠更有说服力。

> 🎯 **核心要点**：技术选型没有银弹，但有一套可复用的决策框架。10 个场景覆盖了后端开发中最常见的选型需求。面试中重点展示：(1) 你了解多个候选方案的优缺点；(2) 你会结合场景和约束做决策；(3) 你知道选型不是终点，演进才是。

---

> 🎯 **核心要点总览**：系统演进和架构决策题考察的是"从项目中学到了什么"。10 个场景题覆盖了面试中常见的架构类问题：(1) 演进路径（单体→微服务）；(2) RAG 框架设计；(3) MQ 选型；(4) 复盘反思；(5) 容量规划；(6) 场景对比；(7) 技术债务管理；(8) 中台设计；(9) 决策方法论；(10) 技术选型决策树。这些题没有标准答案，但有"好的答题框架"——展示思考过程比展示技术名词更重要。
