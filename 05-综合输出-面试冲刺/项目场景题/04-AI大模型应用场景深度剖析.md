### 1.3 Flavor Dash：3步MVP RAG（"能用就行"）

Flavor Dash是一个餐饮推荐项目，RAG只做最基本的"搜索菜谱"功能。

**3步流程**：

```
用户提问 → ① Embedding检索 → ② Prompt拼接 → ③ LLM生成
```

**Step 1 - Embedding检索**：
```java
// FlavorDash RAG - 最简实现
List<Document> search(String query) {
    float[] queryVec = embeddingService.embed(query);
    // 直接在内存中计算cosine similarity（小规模数据）
    return documents.stream()
        .map(doc -> new ScoredDocument(doc, cosineSimilarity(queryVec, doc.getVector())))
        .sorted(Comparator.comparingDouble(ScoredDocument::score).reversed())
        .limit(3)
        .map(ScoredDocument::getDocument)
        .collect(Collectors.toList());
}
```

**Step 2 - Prompt拼接**：
```java
String buildPrompt(String question, List<Document> docs) {
    String context = docs.stream()
        .map(Document::getContent)
        .collect(Collectors.joining("\n---\n"));

    return String.format("""
        基于以下信息回答问题，如果信息不足，请说不知道。
        
        参考信息：
        %s
        
        问题：%s
        """, context, question);
}
```

**Step 3 - LLM生成**：直接调用LLM API返回结果。

> 💡 **MVP阶段不需要复杂Pipeline**。先跑通再优化，这是工程化的基本原则。

### 1.4 SuGuangMall：7步电商RAG（"通用搜索"）

SuGuangMall是一个电商项目，RAG需要处理商品搜索、客服问答等场景。

**7步流程**：

```
① 查询预处理 → ② Embedding检索 → ③ BM25检索 → ④ RRF融合 →
⑤ 上下文构建 → ⑥ Prompt组装 → ⑦ LLM生成
```

**复杂度递增原因**：
1. **电商数据量大**：需要分片存储，不能全量内存计算
2. **查询多样性**：用户可能搜商品名、品牌、功能描述，单路检索不够
3. **排序要求高**：搜索结果需要相关度排序

**Step 1 - 查询预处理**：去除停用词、拼音转中文、同义词替换
```java
String preprocessQuery(String rawQuery) {
    return rawQuery.toLowerCase()
        .replaceAll("[\\p{Punct}]+", " ")  // 去标点
        .replaceAll("\\s+", " ")
        .trim();
}
```

**Step 2/3 - 双路检索**：见场景题3详解。

**Step 4 - RRF融合**：见场景题3详解。

**Step 5 - 上下文构建**：控制token数，避免超长
```java
// SuGuangMall - 动态上下文截断
List<ScoredDocument> buildContext(List<ScoredDocument> results, int maxTokens) {
    List<ScoredDocument> context = new ArrayList<>();
    int totalTokens = 0;
    for (ScoredDocument doc : results) {
        int tokens = estimateTokens(doc.getContent());
        if (totalTokens + tokens > maxTokens) break;  // 截断
        context.add(doc);
        totalTokens += tokens;
    }
    return context;
}
```

### 1.5 LingShu：14步医疗级RAG（"合规为先"）

LingShu是医疗咨询系统，RAG的复杂度陡增——**不是因为技术炫技，而是因为医疗场景的特殊要求**：

- **PHI（受保护健康信息）必须脱敏**：患者姓名、电话、身份证号等不能暴露给LLM
- **意图必须精准**：医疗咨询vs预约挂号vs用药查询，路由到不同的处理流程
- **来源必须可追溯**：每一条回答都要标注知识来源
- **输出必须安全**：不能输出治疗方案（只能输出参考信息），不能出现错误引导

> 🎯 **核心要点**：14步不是"过度设计"，而是医疗场景的合规需求倒逼出来的架构。每多一步，都是为了解决一个真实问题。

### 2.2 逐步骤详解

#### Step 1 - PHI脱敏（必要性：⭐️⭐️⭐️⭐️⭐️ 医疗合规刚需）

将用户问题中的敏感信息进行掩码处理。

```java
// LingShu PHI脱敏器
public String deidentify(String text) {
    // 1. 姓名脱敏
    text = text.replaceAll("(姓)?([\\u4e00-\\u9fa5]{2,3})电话", "$1***电话");
    // 2. 手机号脱敏
    text = text.replaceAll("1[3-9]\\d{9}", maskPhone);
    // 3. 身份证脱敏
    text = text.replaceAll("\\d{17}[\\dXx]", maskIdCard);
    // 4. 地址脱敏
    text = text.replaceAll("(省|市|区|县)([\\u4e00-\\u9fa5]+路)", "$1***路");
    return text;
}
```

> ⚠️ **面试重点**：PHI脱敏必须在检索之前做——否则敏感信息会被写入向量数据库和日志，造成合规事故。

#### Step 2 - Intent Routing（必要性：⭐️⭐️⭐️⭐️ 不同意图不同处理）

#### Step 3 - Query Rewrite（必要性：⭐️⭐️⭐️ 提升检索召回率）

```java
// LingShu Query Rewriter - 用LLM改写查询
String rewriteQuery(String originalQuery) {
    String prompt = """
        请将以下医疗查询改写成更适合搜索的形式：
        
        原始查询：%s
        
        要求：
        - 补充医学专业术语
        - 去除口语化表达

// 示例： "我最近老是头疼" → "持续性头痛症状原因及治疗方案"
```

#### Step 4 - Multi-Retrieval（必要性：⭐️⭐️⭐️⭐️⭐️ 保证召回质量和覆盖率）

同时启动BM25关键词检索和向量语义检索（详细见场景题3）。

#### Step 5 - RRF k=60融合（必要性：⭐️⭐️⭐️⭐️ 多路排序合并）

RRF（Reciprocal Rank Fusion）公式详见场景题3。LingShu使用k=60，更平滑的融合权重。

#### Step 6 - Re-ranking（必要性：⭐️⭐️⭐️⭐️ 提升Top-K准确率）

LingShu使用**混合重排序策略**：

```
Re-rank Score = 0.7 × 向量相似度 + 0.3 × BM25关键词匹配度
```

之所以用70%向量+30%关键词，是因为**医疗场景中语义比关键词更重要**——患者描述症状时通常不包含精确医学术语。

#### Step 7 - Context Builder（必要性：⭐️⭐️⭐️⭐️ 控制token并保证信息完整性）

```java
// LingShu - Token感知的上下文构建
RagContext buildContext(List<ScoredDocument> docs, String query) {
    int totalTokens = 0;
    int maxTokens = 3800;  // 预留800token给回复
    List<String> contexts = new ArrayList<>();

    for (ScoredDocument doc : docs) {
        int docTokens = estimateTokens(doc.getContent());
        if (totalTokens + docTokens > maxTokens) {
            // 截断最长的文档，保留前50%
            String truncated = truncateToTokens(doc.getContent(), maxTokens - totalTokens);
            contexts.add(truncated);
            break;
        }
        contexts.add(doc.getContent());
        totalTokens += docTokens;
    }
    return new RagContext(contexts, calculateRelevance(docs));
}
```

## 3. 场景题 3：BM25与向量检索的双重召回与RRF融合

> **面试官意图**：考察你对信息检索的理解——是不是只知道embedding，却忽略了关键词检索的价值？

### 3.1 BM25 vs 向量检索对比表

| 维度 | BM25（关键词检索） | Vector Embedding（语义检索） |
|------|-------------------|---------------------------|
| **原理** | 词频+逆文档频率统计 | 深度神经网络语义编码 |
| **匹配方式** | 精确关键词匹配 | 语义相似度计算 |
| **同义词处理** | ❌ 不支持 | ✅ 支持（"开心"≈"快乐"） |
| **拼写容错** | ❌ 不支持 | ✅ 部分支持 |
| **稀有词** | ✅ 高权重（TF-IDF特性） | ❌ 容易被淹没 |
| **长文本** | ✅ 高效 | ⚠️ 需要截断 |
| **冷启动** | ✅ 无需训练 | ❌ 需要预训练模型 |
| **计算成本** | ✅ 极低 | ⚠️ 较高（GPU推理） |
| **典型得分** | 0~15之间 | 0~1之间 |

### 3.2 为什么两个都要用？

**互补性分析**：

```
搜索"发烧了吃什么药"

BM25命中：
  - 文档A: "发烧的治疗方案"  [高TF-IDF，因为"发烧"是稀有词]
  - 文档B: "小儿退烧药剂量"  ["发烧"+"药"都匹配]

向量检索命中：
  - 文档C: "发热患者的用药指南"  [语义上"发烧"≈"发热"]
  - 文档D: "体温升高的处理办法"  [语义相关但无关键词匹配]
```

在**实际测试**中：
- BM25单独：召回率约62%
- 向量单独：召回率约71%
- **BM25 + 向量（RRF融合）**：召回率约**94%** ——提升非常显著

> 🎯 **核心要点**：关键词检索和语义检索各有优缺点，组合使用才能达到工业化召回率。

### 3.3 RRF融合公式与实现

**RRF（Reciprocal Rank Fusion）公式**：

```
score(d) = Σ(1 / (k + rank_i(d)))
```

- `rank_i(d)`：文档d在第i路检索中的排名
- `k`：平滑参数（LingShu使用k=60）
- 求和：对所有检索路的排名进行求和

**例子**：

| 文档 | BM25排名 | 向量排名 | RRF得分（k=60） |
|------|---------|---------|-------------|
| A | 1 | 3 | 1/61 + 1/63 ≈ 0.0322 |
| B | 2 | 5 | 1/62 + 1/65 ≈ 0.0315 |
| C | 10 | 1 | 1/70 + 1/61 ≈ 0.0307 |
| D | 4 | 4 | 1/64 + 1/64 ≈ 0.0313 |

**最终排序**：A > B > D > C

### 3.4 为什么k=60？

k值影响融合效果：

| k值 | 特点 | 适用场景 |
|-----|------|---------|
| k=0 | 只看排名，不考虑具体位置差异 | 两路质量接近时 |
| k=30 | 适度平滑，对大排名差异敏感 | SuGuangMall通用搜索 |
| k=60 | 更平滑，给低排名文档更多机会 | LingShu医疗场景（避免遗漏） |
| k=100 | 过度平滑，区分度下降 | 不推荐 |

**LingShu选择k=60的原因**：医疗场景宁可多召回一些低相关文档（通过后续重排序过滤），也不能遗漏关键信息。

### 3.5 代码实现

```java
// LingShu RRF Fusion Engine
public List<ScoredDocument> fuse(
        List<ScoredDocument> bm25Results,
        List<ScoredDocument> vectorResults,
        int k) {

    // 1. 分别排名
    Map<String, Integer> bm25Ranks = rankByScore(bm25Results);
    Map<String, Integer> vectorRanks = rankByScore(vectorResults);

    // 2. 收集所有文档ID
    Set<String> allDocIds = new HashSet<>();
    allDocIds.addAll(bm25Ranks.keySet());
    allDocIds.addAll(vectorRanks.keySet());

    // 3. 计算RRF得分
    List<ScoredDocument> fused = allDocIds.stream()
        .map(docId -> {
            int bm25Rank = bm25Ranks.getOrDefault(docId, Integer.MAX_VALUE);
            int vecRank = vectorRanks.getOrDefault(docId, Integer.MAX_VALUE);
            double score = 0.0;
            if (bm25Rank != Integer.MAX_VALUE) {
                score += 1.0 / (k + bm25Rank);
            }
            if (vecRank != Integer.MAX_VALUE) {
                score += 1.0 / (k + vecRank);
            }
            return new ScoredDocument(docId, score);
        })
        .sorted(Comparator.comparingDouble(ScoredDocument::getScore).reversed())
        .collect(Collectors.toList());

    return fused;
}

private Map<String, Integer> rankByScore(List<ScoredDocument> docs) {
    Map<String, Integer> ranks = new HashMap<>();
    for (int i = 0; i < docs.size(); i++) {
        ranks.put(docs.get(i).getId(), i + 1);  // 排名从1开始
    }
    return ranks;
}
```

```java
        if (recentActions.size() >= 3 &&
            recentActions.stream().distinct().count() == 1) {

            return true;
        }
        return false;
```

### 4.3 死循环防护策略

```
┌─────────────────────────────────────────┐
│            死循环防护三件套                  │
├─────────────────────────────────────────┤
│ ① 最大步数限制：max_steps = 10           │
│    超过10步直接终止，返回已收集的信息       │

├─────────────────────────────────────────┤
│ ③ 重复Action检测：                        │
│    连续3轮都是同一个action → 判定死循环    │
│    策略：重新规划或返回部分结果            │
```

```java
// LingShu - 死循环防护实现
@Component
public class LoopDetector {
    private static final int MAX_STEPS = 10;
    private static final int TIMEOUT_SECONDS = 30;
    private static final int REPEAT_THRESHOLD = 3;

    public void guard(AgentSession session) {
        // 1. 步数检查
        if (session.getStepCount() >= MAX_STEPS) {
            throw new AgentException("Max steps exceeded");
        }
        // 2. 超时检查
        if (session.getElapsed() > TIMEOUT_SECONDS) {
            throw new AgentException("Agent timeout");
        }
        // 3. 重复检查
        List<String> recentActions = session.getRecentActions(REPEAT_THRESHOLD);
        if (recentActions.size() == REPEAT_THRESHOLD &&
            recentActions.stream().distinct().count() == 1) {
            throw new AgentException("Detected action loop: " + recentActions.get(0));
        }
    }
}
```

```java
public abstract class AbstractLLMClient implements LLMClient {

    protected final WebClient webClient;
    protected final LLMConfig config;

    public AbstractLLMClient(LLMConfig config) {
        this.config = config;

        // 统一构建WebClient，不同鉴权方式
        WebClient.Builder builder = WebClient.builder()
            .baseUrl(config.getBaseUrl())
            .defaultHeader("Content-Type", "application/json");

        switch (config.getAuthType()) {
            case API_KEY:
                builder.defaultHeader("Authorization", "Bearer " + config.getApiKey());
                break;
            case OAUTH2:
                builder.filter(oauthFilter(config));
                break;
            case CUSTOM:
                config.getExtraHeaders().forEach(builder::defaultHeader);
                break;
        }
        this.webClient = builder.build();
    }
}

// 5. 指数退避重试
@Component
public class RetryStrategy {

    public void executeWithRetry(Runnable action, int maxRetries) {
        for (int i = 0; i < maxRetries; i++) {
            try {
                action.run();
                return;
            } catch (Exception e) {
                if (i == maxRetries - 1) throw e;
                long waitMs = (long) (2000 * Math.pow(2, i));  // 2s → 4s → 8s
                if (waitMs > 10000) waitMs = 10000;             // 上限10s
                log.warn("Retry {} after {}ms due to: {}", i + 1, waitMs, e.getMessage());
                Thread.sleep(waitMs);
            }
        }
    }
}

// 6. Resilience4j熔断
@Component
public class ResilienceLLMClient implements LLMClient {

    private final LLMClient delegate;
    private final CircuitBreaker circuitBreaker;
    private final TimeLimiter timeLimiter;

    public ResilienceLLMClient(LLMClient delegate, LLMConfig config) {
        this.delegate = delegate;

        // CircuitBreaker配置
        CircuitBreakerConfig cbConfig = CircuitBreakerConfig.custom()
            .failureRateThreshold(50)
            .waitDurationInOpenState(Duration.ofSeconds(30))
            .slidingWindowSize(10)
            .build();
        this.circuitBreaker = CircuitBreaker.of("llm-client", cbConfig);

        // TimeLimiter配置
        this.timeLimiter = TimeLimiter.of(Duration.ofMillis(config.getTimeoutMs()));
    }

    @Override
    public ChatResponse chat(ChatRequest request) {
        return Try.ofSupplier(CircuitBreaker.decorateSupplier(circuitBreaker, () ->
            TimeLimiter.decorateSupplier(timeLimiter, () ->
                delegate.chat(request)
            ))).get();
    }
}
```

### 6.4 LLM JSON不稳定的处理方法

LLM输出JSON格式不稳定的问题非常常见，SuGuangMall使用了三重保障：

```java
// SuGuangMall - JSON不稳定处理策略
@Component
public class FunctionCallParser {

    private static final int MAX_RETRIES = 3;

    public FunctionCall parse(String llmOutput) {
        // 策略1：标准解析
        try {
            return parseJson(llmOutput);
        } catch (JsonParseException e) {
            log.warn("Standard JSON parsing failed, trying retry...");
        }

        // 策略2：带格式约束的重新生成
        for (int i = 0; i < MAX_RETRIES; i++) {
            try {
                String retryOutput = llmClient.generate(
                    "请严格按JSON格式输出：{\"function\":\"工具名\",\"arguments\":{...}}\n" +
                    "你的上一步输出格式不正确，请重新输出："
                );
                return parseJson(retryOutput);
            } catch (JsonParseException e) {
                continue;
            }
        }

        // 策略3：正则兜底
        FunctionCall fallback = extractByRegex(llmOutput);
        if (fallback != null) {
            log.info("Fallback regex extraction succeeded: {}", fallback);
            return fallback;
        }

        throw new FunctionCallException("Failed to parse function call after all strategies");
    }

    private FunctionCall extractByRegex(String text) {
        // 正则匹配 function call 模式
        Pattern pattern = Pattern.compile(
            "\\{\\s*\"function\"\\s*:\\s*\"(\\w+)\"\\s*,\\s*\"arguments\"\\s*:\\s*\\{(.+?)\\}\\s*\\}"
        );
        Matcher matcher = pattern.matcher(text.replaceAll("\\n", " "));
        if (matcher.find()) {
            String funcName = matcher.group(1);
            String argsStr = "{" + matcher.group(2) + "}";
            try {
                Map<String, Object> args = objectMapper.readValue(argsStr, Map.class);
                return new FunctionCall(funcName, args);
            } catch (Exception e) {
                return null;
            }
        }
        return null;
    }
}
```

```java
            return "订单%s：状态=%s, 金额=%.2f, 物流=%s".formatted(

        });
        handlers.put("cancelOrder", params -> {
            String orderId = (String) params.get("orderId");
            String reason = (String) params.get("reason");
            orderService.cancelOrder(orderId, reason);
            return "订单%s已取消，原因为：%s".formatted(orderId, reason);

    public ToolResult execute(FunctionCall call) {
        ToolHandler handler = handlers.get(call.getFunctionName());
        if (handler == null) {
            return ToolResult.failure("Unknown tool: " + call.getFunctionName());
        }
        try {
            String result = handler.handle(call.getArguments());
            return ToolResult.success(result);
        } catch (Exception e) {
            return ToolResult.failure("Tool execution error: " + e.getMessage());
```

## 7. 场景题 7：CLIP以图搜图实现

> **面试官意图**：考察你对多模态检索的理解——不只是文字搜索，图片搜索怎么做？

### 7.1 CLIP原理简述

CLIP（Contrastive Language-Image Pre-training）是OpenAI提出的多模态模型，核心思想：

```
图片分支：Image Encoder（ViT） → 512维向量
文字分支：Text Encoder（GPT）  → 512维向量
        ↓
两个向量映射到同一个语义空间
        ↓
计算cosine similarity，语义匹配的pair得分高
```

**为什么选512维？**

| 维度 | 模型 | 特点 | 适用场景 |
|------|------|------|---------|
| 256维 | CLIP ViT-B/16 | 速度快，精度略低 | 实时搜索 |
| **512维** | **CLIP ViT-B/32** | **精度和速度的最佳平衡** | **通用场景** |
| 768维 | CLIP ViT-L/14 | 精度高，速度慢 | 精度优先场景 |
| 1024维 | CLIP ViT-H/14 | 最高精度，最慢 | 科研场景 |

> 💡 **Flavor Dash选择512维的原因**：
> 1. 餐饮图片搜索不需要极高精度（区分汉堡和披萨，512维足够）
> 2. 512维向量占用内存较小，百万级图片只需要2GB内存
> 3. 检索速度在Milvus上能达到<10ms

- **IVF_FLAT**：倒排文件索引，速度快，适合中等规模（百万量级）
- **PQ（Product Quantization）**：乘积量化压缩，减少内存占用约4倍
- 精度损失<3%，但检索速度提升5倍

```java
@Component
public class InputSafetyChecker {

    // 一级：正则模式检测
    private static final List<Pattern> MALICIOUS_PATTERNS = List.of(
        Pattern.compile("(/\\*.*?\\*/|\\b(?:DROP|DELETE|INSERT|UPDATE)\\b.*?;)", Pattern.CASE_INSENSITIVE),
        Pattern.compile("<script[^>]*>.*?</script>", Pattern.CASE_INSENSITIVE),
        Pattern.compile("(\\.\\.(/|\\\\))+"),
        Pattern.compile("\\bexec\\s*\\(|\\beval\\s*\\(|\\bsystem\\s*\\(|\\brm\\s+-rf\\s+/")
    );

    private static final List<String> SENSITIVE_KEYWORDS = List.of(

    );

    // 三级：敏感词库（DFA算法）
    private final DFAFilter sensitiveWordFilter = new DFAFilter(
        loadSensitiveWordLibrary()
    );

    public SafetyResult check(String input) {
        // 一级检测
        for (Pattern pattern : MALICIOUS_PATTERNS) {
            if (pattern.matcher(input).find()) {
                return SafetyResult.REJECTED("Malicious pattern detected");
            }
        }

        // 二级检测
        for (String keyword : SENSITIVE_KEYWORDS) {
            if (input.contains(keyword)) {
                return SafetyResult.REJECTED("Sensitive keyword detected");
            }
        }

        // 三级检测
        if (sensitiveWordFilter.contains(input)) {
            return SafetyResult.FLAGGED("Contains sensitive words");
        }

        return SafetyResult.PASSED();
    }
```

```java
// 问题：多个请求同时推理，OLLAMA进程OOM
// 解决：信号量限制并发 + 队列缓冲

@Component
public class OllamaRateLimiter {

    // 控制最大2个并发请求
    private final Semaphore semaphore = new Semaphore(2);
    // 请求队列（缓冲最多10个等待请求）
    private final BlockingQueue<Runnable> queue = new LinkedBlockingQueue<>(10);

    public <T> CompletableFuture<T> executeWithLimit(Supplier<T> action) {
        return CompletableFuture.supplyAsync(() -> {
            if (!semaphore.tryAcquire()) {
                // 队列已满时直接拒绝
                if (!queue.offer(() -> {})) {
                    throw new ServiceException("Server busy, please try again later");
                }
                semaphore.acquire();
                queue.poll();
            }
            try {
                return action.get();
            } finally {
                queue.poll();
                semaphore.release();
            }
        });
    }
}
```

```java
        问题：{question}
        
        要求：
        1. 如果参考信息足够，给出准确回答
        2. 如果不够，说"基于提供的信息无法完全回答"
        3. 附上信息来源编号
        """,
        // 版本C：分步推理版（Chain-of-Thought）
        """
        请按以下步骤回答：
        1. 理解用户问题：{question}
        2. 从参考信息中找到相关内容：{context}
        3. 推理：结合信息回答问题
        4. 输出：清晰的回答
        
        注意：只基于参考信息回答。
        """
    );

    @GetMapping("/abtest")
    public ABTestResult runABTest(@RequestParam String question) {
        // 随机分成3组测试不同prompt
        int variantId = ThreadLocalRandom.current().nextInt(3);
        String answer = ragService.answer(question, PROMPT_TEMPLATES.get(variantId));
        return new ABTestResult(variantId, answer);
    }
}
```

### 10.6 反馈闭环

```text
用户反馈流程：

用户点击"没用" → 
  选择原因：回答不准确 / 信息不全 / 理解错误 / 其他 →
  后台记录 caseId + errorType →
  定期（每周）分析反馈数据 →
  发现Top问题类型 →
  针对性优化（补充知识/调整Prompt/修改检索） →
  新评估集验证效果 →
  部署上线
```

## 11. AI场景通用答题框架

### 11.1 面试答题模板

当面试官问到一个AI场景题时，按以下框架回答：

```
○ 背景说明（30秒）
  - 这个场景在什么业务中出现
  - 解决什么问题

○ 技术方案（2分钟）
  - 整体架构（画图或文字描述）
  - 核心实现细节
  - 代码或伪代码

○ 为什么这么设计（1分钟）
  - 权衡了什么（trade-off）
  - 为什么选A不选B
  - 有没有更好的方案

○ 踩过的坑（30秒）
  - 实际开发中遇到的问题
  - 怎么解决的

○ 效果量化（30秒）
  - 用了数据指标
  - 前后对比
```

### 11.2 常见追问准备

```text
任何AI场景题都可能被追问：

「你这个方案有什么缺陷？」
  → 主动说出当前方案的局限性
  → 给出后续优化方向
  → 展现架构思维

「数据量放大100倍还撑得住吗？」
  → 架构扩展性分析
  → 哪些组件需要扩容
  → 可能的瓶颈点

「这个和传统方案比有什么优势？」
  → 定量对比（准确率/延迟/成本）
  → 场景适用性分析
  → 不盲吹AI，承认局限性

「为什么不用别人现成的方案？」
  → 开源方案局限性
  → 自定义需求的必要性
  → 成本考虑
```
