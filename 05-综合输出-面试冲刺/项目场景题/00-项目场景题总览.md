### 🚀 速通版（3 天）—— 面试前冲刺

```

  └── 学会 STAR+3C 答题结构
Day 2: 02 秒杀 + 03 分布式（选一个核心模块）
  ├── 秒杀：Redis Lua + 限流 + 异步削峰
  └── / 分布式：事务 + 锁 + 分表
Day 3: 04 AI大模型 + 05 数据架构（选一个方向）
  ├── AI：RAG 管线 + Function Calling
  └── / 数据：缓存策略 + 混合检索
```

### 📖 标准版（1 周）—— 系统准备

```
Day 1-2: 01 项目全景 + 08 答题框架（打基础）
  ├── 准备 3/5/10 分钟三个版本自我介绍

  └── 准备 2-3 个线上真实案例
Day 5-6: 04+05 AI大模型 + 数据架构（差异化模块）
  ├── RAG 管线 14 步逐一理解

  └── 混合检索 BM25+向量+RRF 原理
Day 7: 06 故障排查 + 07 架构演进（加分模块）
```

```
Week 1: 全模块基础 + 代码级别理解
  ├── Mon-Wed: 01 + 08 框架 + 逐字稿打磨
  ├── Thu: 02 秒杀（看 Redis Lua 源码 + 限流算法实现）
  ├── Fri: 03 分布式（选1-2个组件看核心源码）
  ├── Sat: 04 AI（跑通 RAG 管线 + Function Calling Demo）
  └── Sun: 复习 + 面试模拟

Week 2: 深度追问 + 交叉场景 + 压力训练
  ├── Mon: 04+05 交叉场景（AI+缓存/RAG+向量检索）
  ├── Tue: 06 故障排查（模拟3个线上故障排查）
  ├── Wed: 07 架构演进（画架构演进时间线）
  ├── Thu: 深度追问应对（每个项目准备5个"再深挖"问题）
```

## 5. 项目场景题 vs 八股文 vs 系统设计

| 对比维度 | 八股文 | 项目场景题 | 系统设计 |
|:--------:|--------|:----------:|:--------:|
| **考察目标** | 知识广度 - 你是否知道 | 应用深度 - 你是否做过 | 架构能力 - 你能否设计 |
| **典型提问** | Redis 有哪些数据结构？ | 你们的秒杀怎么解决超卖的？ | 设计一个秒杀系统 |
| **答题结构** | 列举式（特性/分类/对比） | 叙事式（STAR + 3C） | 框架式（需求→架构→细节） |
| **技术深度** | 1 层：API / 概念 | 2-3 层：原理 + 落地细节 | 2 层：选型 + 权衡 |
| **面试轮次** | 一面 / 二面 | 二面 / 三面 | 三面 / 四面 |
| **加分项** | 对比分析 / 底层原理 | 数据 + 案例 + 反思 | 取舍 / 演进规划 |
| **扣分项** | 背错 / 概念混淆 | 只说操作不说为什么 | 只画大图不扣细节 |
| **准备方法** | 刷题 + 背诵 | 复盘项目 + 提炼模式 | 读架构书 + 画架构图 |
| **权重（大厂）** | 30% | 40% | 30% |
| **准备难度** | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **面试官角色** | 知识检验者 | 合作者（他帮你挖掘亮点） | 架构评审者 |

> 💡 **核心差异**：八股文回答是「T 型」—— 先定性（是什么），再展开；场景题是「倒 L 型」—— 先讲故事（经历过什么），再深挖技术细节；系统设计是「回型」—— 从外到内逐层细化。三者并不是独立的，面试中经常混用。

## 6. 面试中场景题的出题规律

### 6.1 考官到底想考察什么

场景题不是考你是否背过答案，而是通过你描述「真实经历」的过程，综合评估 7 个维度：

```
┌─────────────────────────────────────────────────────────┐
│              场景题 7 维评估模型                          │
├───────────────┬─────────────────────────────────────────┤
│ ① 真实性      │ 是否真的做过项目（细节、数据、决策过程）    │
│ ② 技术深度    │ 停留在 API 调用还是理解底层原理            │
│ ③ 问题拆解    │ 面对复杂问题能否分解成可解决的小问题        │
│ ④ 决策能力    │ 技术选型的理由，权衡取舍的依据             │
│ ⑤ 复盘能力    │ 遇到问题后的反思，改进方向                │
│ ⑥ 沟通表达    │ 能否把复杂技术讲清楚（3分钟讲透）          │
│ ⑦ 技术热情    │ 是否主动学习新技术，尝试改进               │
└───────────────┴─────────────────────────────────────────┘
```

### 6.2 常见出题套路

| 套路类型 | 典型问法 | 考察重点 | 应对策略 |
|----------|---------|:--------:|----------|
| **痛点追问** | 你们秒杀怎么解决超卖？ | 真实性 + 技术深度 | 先抛出问题，再展开方案，最后给数据 |
| **复盘追问** | 如果重来，你会怎么优化？ | 复盘能力 + 技术热情 | 指出当前不足 + 给出优化方向 + 说明为什么当时没做 |
| **对比追问** | 为什么用 Seata AT 不用 TCC？ | 决策能力 | 对比优劣 + 结合场景说明取舍 |
| **极限追问** | QPS 再高 10 倍怎么办？ | 架构视野 | 先分析瓶颈 → 给出扩容方案 → 说明代价 |
| **场景假设** | 如果消息丢了怎么恢复？ | 问题拆解 + 全链路理解 | 分阶段定位 → 各阶段恢复策略 |
| **跨界追问** | 秒杀系统怎么用 AI 优化？ | 创新思维 + 技术广度 | 结合项目特点给出 1-2 个可行方案 |

### 6.3 不同轮次面试官的心理画像

```
一面（技术面）：
  └─ 心理：确认简历真实性，判断编码和基本技术素养
  └─ 场景题：偏向基础场景（缓存、数据库、接口设计）
  └─ 关注：项目里的技术细节能不能说清楚

二面（Leader / 资深工程师）：
  └─ 心理：判断独立解决问题能力和技术深度
  └─ 场景题：偏向高并发、分布式、线上故障
  └─ 关注：遇到问题怎么拆解、怎么决策、复盘了什么

三面（跨部门 / 架构师）：
  └─ 心理：判断架构视野和技术格局
  └─ 场景题：偏向系统演进、技术选型、多系统协作
  └─ 关注：技术决策的逻辑、对未来演进的规划

四面（HR / 交叉面）：
  └─ 心理：判断沟通协作和项目真实参与度
  └─ 场景题：偏向项目中怎么跟人合作、遇到冲突怎么解决
  └─ 关注：团队角色、沟通方式、复盘态度
```

| **精读** | 3-7 天 | 掌握核心场景题的答案框架 | 每道题用 STAR+3C 写出逐字稿 |
| **演练** | 3-5 天 | 形成肌肉记忆 | 对着镜子 / 录音讲，控制时间 |
| **压力测试** | 1-2 天 | 应对随机追问 | 找朋友或模拟面试官随机提问 |

### 7.2 最佳实践

1. **先读完 08 答题框架**：这是所有场景题的方法论基础，掌握后再看具体题目事半功倍
2. **每个场景题都要用自己的话讲**：不要背答案，理解后再用自己的表述讲出来
3. **准备数据弹药**：所有回答中都要有数字（QPS、召回率、响应时间、成功率）
4. **敢于承认不知道**：面试官更看重你面对未知时的分析思路，而不是你碰巧背过答案
5. **关联三个项目**：同一个技术点如果在多个项目中有不同的实现，对比着讲效果更好

### 7.3 常见误区

| 误区 | 错误表现 | 正确做法 |
|:----:|----------|----------|
| **跳进方案** | 面试官刚问完就立刻列方案 | 先分析问题背景和约束条件 |
| **只讲结果** | "我们用了 Redis Lua 解决了" | 从为什么选 → 怎么实现 → 遇到什么坑 → 效果如何 |
| **回避不足** | 所有方案都说得完美无缺 | 主动指出妥协和待改进之处 |
| **忘记数据** | "效果挺好的" | "QPS 从 500 提升到 2000+，超卖率降为 0" |
| **脱离项目** | 讲通用方案跟项目没关系 | 一定要回到项目场景："在我们项目中..." |
| **背得过于流畅** | 像在背课文 | 适当停顿、思考，展示真实的思考过程 |

---

> 🎯 **核心要点**：项目场景题是面试中权重最高的部分（40%），它是你区分于「只会背八股文」的候选人的关键战场。不要把它当成考试，而是当成一次技术深度的展示机会。本讲义的目标是帮你把项目经历打磨成「技术故事」，让面试官听完后觉得：「这个人真的做过项目，而且会思考。」
