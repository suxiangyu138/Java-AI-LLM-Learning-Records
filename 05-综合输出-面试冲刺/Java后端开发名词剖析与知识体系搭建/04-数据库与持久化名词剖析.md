## 1. MySQL 架构概览

```text
MySQL 逻辑架构：

  ┌─────────────────────────┐
  │   连接层 (Connectors)     │  ← JDBC/ODBC/Native C API
  ├─────────────────────────┤
  │   服务层 (Server)         │
  │   ├── 连接池              │  ← 线程复用
  │   ├── SQL 接口 / Parser  │  ← 语法解析 + 语义分析
  │   ├── 优化器 (Optimizer)  │  ← CBO 代价优化

  │   存储引擎层 (Storage)    │  ← 可插拔：InnoDB/MyISAM/Memory
  │   数据按页存储，Buffer Pool 缓冲│
  └─────────────────────────┘
```

## 3. 索引

### 3.1 索引分类

```text
按数据结构：
  ├── B+Tree 索引（InnoDB 默认）
  ├── Hash 索引（Memory 引擎 / 自适应 Hash）
  ├── Full-Text 索引（全文搜索）
  └── R-Tree 索引（空间数据）

按物理存储：
  ├── 聚簇索引（Clustered）：数据与索引存储在一起，叶子节点 = 完整行数据
  │   └── InnoDB 的主键索引就是聚簇索引，一张表只有一个
  └── 非聚簇索引（Secondary）：叶子节点存储主键值
      └── 普通索引 / 唯一索引 / 联合索引 → 回表查主键索引

按逻辑功能：
  ├── 主键索引（PRIMARY KEY）：唯一 + 非空
  ├── 唯一索引（UNIQUE）：唯一 + 可空
  ├── 普通索引（INDEX）：加速查询
  ├── 联合索引（Composite）：多列组合
  ├── 前缀索引：只索引列的前 N 个字符
  └── 覆盖索引（Covering Index）：查询列都在索引中 → 不回表！
```

### 3.2 B+Tree 为什么适合数据库索引

```text
B+Tree vs B-Tree vs 二叉树：

  二叉树：
    → 深度大（100w数据深度~20），磁盘IO多
    → 不适合磁盘存储

  B-Tree：
    → 每个节点同时存数据+索引
    → 非叶子节点也存数据 → 浪费空间

  B+Tree（MySQL 采用）：
    ✅ 数据只存叶子节点 → 非叶子节点可存更多索引键
    ✅ 叶子节点用双向链表连接 → 范围查询高效！
    ✅ 树矮胖（1000w数据深度~3-4层）→ 磁盘IO少
    ✅ 每次磁盘IO读一页（16KB）→ 一次加载多个键

MySQL InnoDB 的 B+Tree：
  → 页大小 16KB
  → 每个页存约 1170 个键（bigint 主键）
  → 高度 3 = 1170³ ≈ 16 亿行数据
  → 也就是说 16 亿行数据只需 3 次磁盘 IO 就能定位！
```

### 3.3 最左前缀原则

```sql
-- 联合索引 (a, b, c)
CREATE INDEX idx_abc ON t(a, b, c);

-- 命中索引（按序使用最左前缀）
SELECT * FROM t WHERE a = 1;               -- ✅ 命中 a
SELECT * FROM t WHERE a = 1 AND b = 2;     -- ✅ 命中 a, b
SELECT * FROM t WHERE a = 1 AND b = 2 AND c = 3; -- ✅ 命中 a, b, c
SELECT * FROM t WHERE a = 1 AND c = 3;     -- ✅ 命中 a（b 断了，c 失配）
SELECT * FROM t WHERE a = 1 AND b > 2;     -- ✅ 命中 a, b（范围后失效）

-- 不命中索引
SELECT * FROM t WHERE b = 2;               -- ❌ 没有最左 a
SELECT * FROM t WHERE c = 3;               -- ❌ 没有最左 a
SELECT * FROM t WHERE a > 1 AND b = 2;     -- ❌ a 范围后 b 失效
SELECT * FROM t WHERE a LIKE '%abc';       -- ❌ 左侧模糊失配

-- 关键规则：最左列必须出现，遇到范围查询后失效
```

### 3.4 索引优化策略

| 策略 | 说明 |
|------|------|
| **覆盖索引** | SELECT 的列全部在索引中，不用回表，Using index |
| **索引下推** | MySQL 5.6+，在索引遍历时先过滤，减少回表次数 |
| **避免 SELECT *** | 只查需要的列，利于覆盖索引 |
| **联合索引列顺序** | 区分度高的列放前面 |
| **前缀索引** | 长字符串列（如 URL）只索引前 N 个字符 |
| **避免函数操作** | `WHERE DATE(create_time) = '2026-01-01'` 导致索引失效 |

## 4. 事务与隔离级别

### 4.1 ACID

| 特性 | 全称 | 说明 |
|------|------|------|
| **A** | Atomicity 原子性 | 要么全完成，要么全不完成（Undo Log） |
| **C** | Consistency 一致性 | 事务前后数据完整性约束不变 |
| **I** | Isolation 隔离性 | 并发事务互不干扰（MVCC + 锁） |
| **D** | Durability 持久性 | 提交后数据永久保存（Redo Log） |

### 4.2 四种隔离级别

```text
┌─────────────┬──────┬──────┬──────┬──────┐
│   隔离级别   │ 脏读 │ 不可重复读│ 幻读 │
├─────────────┼──────┼──────┼──────┼──────┤
│ READ UNCOMMITTED│ ✅ │  ✅  │  ✅  │ 废弃  │
│ READ COMMITTED  │ ❌ │  ✅  │  ✅  │ Oracle默认│
│ REPEATABLE READ │ ❌ │  ❌  │  ⚠️  │ MySQL默认│
│ SERIALIZABLE    │ ❌ │  ❌  │  ❌  │ 最安全但性能最差│
└─────────────┴──────┴──────┴──────┴──────┘

脏读：读到其他事务未提交的数据
不可重复读：同一事务两次读同一行，值不同
幻读：同一事务两次读，行数不同（多了几行）

MySQL RR 级别通过 Next-Key Lock（行锁+间隙锁）基本解决幻读，
但快照读时可能产生"当前读幻读"。
```

## 5. MVCC 多版本并发控制

```text
MVCC = Multi-Version Concurrency Control

核心组件（InnoDB）：
  ├── 隐藏列：
  │   ├── DB_TRX_ID  (6B)：最近修改此记录的事务 ID
  │   ├── DB_ROLL_PTR (7B)：指向 Undo Log 的回滚指针
  │   └── DB_ROW_ID   (6B)：隐含的自增 ID（无主键时使用）
  │
  ├── Undo Log（版本链）：所有历史版本串联
  │
  └── Read View（一致性视图）：
      ├── m_ids：当前活跃事务列表
      ├── min_trx_id：最小活跃事务 ID
      ├── max_trx_id：下一个即将分配的事务 ID
      └── creator_trx_id：创建此 ReadView 的事务 ID

可见性判断规则：
  1. trx_id < min_trx_id → 可见（事务在 ReadView 创建前提交）
  2. trx_id >= max_trx_id → 不可见（事务在 ReadView 创建后开始）
  3. trx_id 在 m_ids 中 → 不可见（事务活跃中、未提交）
  4. 否则 → 可见

  RC vs RR 级别的区别：
    → RC：每次 SELECT 都创建新的 ReadView
    → RR：事务第一次 SELECT 创建 ReadView，后续复用
       → 所以 RR 下同一事务多次读结果一样（可重复读）
```

## 6. SQL 优化

### 6.1 EXPLAIN 核心字段

```sql
EXPLAIN SELECT * FROM users WHERE age > 18 ORDER BY create_time DESC;

-- 关键字段解读：
-- type:      访问类型（ALL < index < range < ref < eq_ref < const < system）
--            → 至少要到 range 级别！
-- key:       实际使用的索引
-- rows:      预估扫描行数
-- Extra:     额外信息
--   Using index:     覆盖索引（最优）
--   Using where:     在 server 层过滤
--   Using filesort:  额外排序（需优化！）
--   Using temporary: 使用临时表（需优化！）
```

### 6.2 常见 SQL 优化技巧

```sql
-- ❌ 索引失效：OR 条件
SELECT * FROM t WHERE a = 1 OR b = 2;  -- a 和 b 各有索引时会失效

-- ✅ 改用 UNION
SELECT * FROM t WHERE a = 1
UNION ALL
SELECT * FROM t WHERE b = 2;

-- ❌ 索引失效：函数操作
SELECT * FROM t WHERE YEAR(create_time) = 2026;

-- ✅ 使用范围
SELECT * FROM t WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01';

-- ❌ 隐式类型转换
SELECT * FROM t WHERE phone = 13800138000;  -- phone 是 VARCHAR，索引失效！

-- ✅ 类型匹配
SELECT * FROM t WHERE phone = '13800138000';

-- ❌ 大分页
SELECT * FROM t ORDER BY id LIMIT 1000000, 20;  -- 扫描 100 万行+才取 20 行

-- ✅ 延迟关联
SELECT * FROM t
INNER JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000, 20) AS tmp
ON t.id = tmp.id;
```

## 7. 分库分表

### 7.1 策略对比

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **垂直分库** | 按业务拆分（订单库、用户库） | 业务解耦、独立扩展 | 跨库 JOIN 困难 |
| **垂直分表** | 按列拆分（热点列+冷数据列） | 减少IO、提升缓存命中 | 需要冗余主键 |
| **水平分表** | 按行拆分（按ID/时间） | 线性扩展、单表数据量可控 | 跨分片查询复杂 |
| **水平分库** | 水平分表 × 多库 | 存储+吞吐双扩展 | 分布式事务 + 跨库 JOIN |

### 7.2 分片算法

```java
// 1. 取模（Hash 分片）
shard = id % 4;  // → db_0, db_1, db_2, db_3
// 问题：扩容时数据迁移量大

// 2. 一致性 Hash
shard = consistentHash(id);  // 扩容仅影响相邻节点
// 优点：扩容数据迁移量小

// 3. 范围分片
shard = id / 10000000;  // → db_0: [0-1千万), db_1: [1千万-2千万)
// 优点：按范围查询高效

// 4. 时间分片
shard = yearMonth;  // → table_202601, table_202602
// 日志/订单按时间归档，天然适合
```

### 7.3 分库分表中间件

| 中间件 | 模式 | 特点 |
|--------|:--:|------|
| **ShardingSphere-JDBC** | 客户端 SDK | 增强版 JDBC 驱动，无网络开销 |
| **ShardingSphere-Proxy** | 代理 | 独立进程，跨语言支持 |
| **MyCat** | 代理 | 老牌，社区活跃度下降 |
| **Vitess** | 代理 | YouTube 开源，云原生 |

## 8. MyBatis / JPA

### 8.1 MyBatis vs JPA

| 维度 | MyBatis / MyBatis-Plus | JPA / Hibernate |
|------|:-------------------:|:-------------:|
| **定位** | SQL 映射框架 | ORM 框架 |
| **SQL 控制** | 完全手写（灵活） | 自动生成（HQL/JPQL） |
| **学习曲线** | 低 | 高 |
| **复杂查询** | 灵活手写 | 需要 JPQL/Criteria |
| **缓存** | 一级缓存（SqlSession），二级缓存 | 一级/二级/查询缓存完善 |
| **动态 SQL** | 原生支持 `<if> <foreach>` | Criteria/Specification |
| **中国市场** | 主流 ✅ | 较少 |

```xml
<!-- MyBatis 动态 SQL -->
<select id="findUsers" resultType="User">
    SELECT * FROM users
    <where>
        <if test="name != null">AND name LIKE CONCAT('%', #{name}, '%')</if>
        <if test="age != null">AND age = #{age}</if>
    </where>
    ORDER BY create_time DESC
</select>
```

### 8.2 MyBatis 核心组件

| 组件 | 说明 |
|------|------|
| **SqlSessionFactory** | 创建 SqlSession，全局唯一 |
| **SqlSession** | 一次数据库会话，非线程安全 |
| **Executor** | 执行器，负责 SQL 执行和缓存 |
| **MappedStatement** | 封装 SQL 的映射信息 |
| **TypeHandler** | Java 类型 ↔ JDBC 类型转换 |
| **Interceptor (Plugin)** | 插件拦截，分页插件就是它！ |
