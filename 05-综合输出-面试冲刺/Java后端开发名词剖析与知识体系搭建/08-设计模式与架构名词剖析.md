## 1. 设计模式六大原则

| 原则 | 全称 | 核心思想 |
|:--:|------|---------|
| **SRP** | 单一职责原则 | 一个类只做一件事 |
| **OCP** | 开闭原则 | 对扩展开放，对修改关闭 |
| **LSP** | 里氏替换原则 | 子类可以替换父类而不出错 |
| **ISP** | 接口隔离原则 | 接口要小、要专一 |
| **DIP** | 依赖倒置原则 | 依赖抽象而非具体实现 |
| **LoD** | 迪米特法则 | 最少知道原则（不和陌生人说话） |

## 2. 创建型模式

| 模式 | 说明 | 典型场景 |
|------|------|---------|
| **单例 Singleton** | 全局唯一实例 | Spring Bean（默认）、配置管理 |
| **工厂方法 Factory Method** | 子类决定创建哪个实例 | `BeanFactory` |
| **抽象工厂 Abstract Factory** | 创建相关对象家族 | UI 组件库跨平台 |
| **建造者 Builder** | 分步构建复杂对象 | `StringBuilder`, Lombok `@Builder` |
| **原型 Prototype** | 克隆对象 | Spring `@Scope("prototype")` |

```java
// 单例模式：枚举实现（防反射 + 防序列化）
public enum Singleton {
    INSTANCE;
    public void doSomething() { }
}

// 建造者模式
User user = User.builder()
    .name("John")
    .age(25)
    .email("john@example.com")
    .build();
```

### 单例模式实现对比

| 方式 | 线程安全 | 延迟加载 | 防反射 | 防序列化 |
|------|:------:|:------:|:----:|:-----:|
| 饿汉式 | ✅ | ❌ | ❌ | ❌ |
| 懒汉式 synchronized | ✅ | ✅ | ❌ | ❌ |
| 双重检查锁 DCL | ✅ | ✅ | ❌ | ❌ |
| 静态内部类 | ✅ | ✅ | ❌ | ❌ |
| **枚举** | ✅ | ❌ | ✅ | ✅ |

## 3. 结构型模式

| 模式 | 说明 | 典型场景 |
|------|------|---------|
| **适配器 Adapter** | 接口转换 | `InputStreamReader`（字节→字符） |
| **装饰器 Decorator** | 动态增强 | `BufferedInputStream`（包装增强） |
| **代理 Proxy** | 控制访问 | Spring AOP、MyBatis Mapper 代理 |
| **外观 Facade** | 统一入口 | Controller → Service Facade |
| **桥接 Bridge** | 抽象与实现分离 | JDBC（Driver 与 Connection） |
| **组合 Composite** | 树形结构 | 菜单/目录树 |
| **享元 Flyweight** | 共享减少创建 | Integer 缓存(-128到127)、连接池 |

### 代理模式 vs 装饰器模式

| 维度 | 代理模式 | 装饰器模式 |
|------|---------|-----------|
| **目的** | 控制访问（权限、延迟加载） | 增强功能（叠加多个功能） |
| **关系** | 代理与被代理对象在编译时确定 | 装饰器可运行时动态组合 |
| **创建** | 代理通常由框架生成 | 用户手动创建装饰链 |
| **例子** | Spring AOP（@Transactional 代理） | `new BufferedReader(new FileReader(f))` |

## 4. 行为型模式

| 模式 | 说明 | 典型场景 |
|------|------|---------|
| **策略 Strategy** | 算法族，可切换 | 支付方式选择、排序器 |
| **模板方法 Template** | 父类定义骨架，子类实现细节 | `AbstractList` → `ArrayList` |
| **观察者 Observer** | 一对多通知 | Spring Event、MQ 发布订阅 |
| **责任链 Chain** | 请求沿链传递 | 拦截器链、过滤器链 |
| **命令 Command** | 请求封装为对象 | 线程池 `Runnable`、撤销操作 |
| **状态 State** | 状态驱动行为 | 订单状态机（待支付→已支付→已发货） |
| **迭代器 Iterator** | 统一遍历接口 | `Iterator<T>` |

```java
// 策略模式 + 枚举（消除 if-else）
public enum PaymentStrategy {
    ALIPAY {
        @Override
        public void pay(BigDecimal amount) {
            // 支付宝支付逻辑
        }
    },
    WECHAT {
        @Override
        public void pay(BigDecimal amount) {
            // 微信支付逻辑
        }
    };

    public abstract void pay(BigDecimal amount);
}

// 使用
PaymentStrategy.ALIPAY.pay(new BigDecimal("100.00"));
```

## 5. Spring 中的设计模式

| 模式 | Spring 中的应用 |
|------|---------------|
| **单例** | Bean 默认 scope=singleton |
| **工厂方法** | `BeanFactory` / `ApplicationContext` |
| **代理** | AOP（JDK动态代理 / CGLIB） |
| **模板方法** | `JdbcTemplate`, `RestTemplate`, `RedisTemplate` |
| **观察者** | `ApplicationEvent` + `@EventListener` |
| **策略** | `ResourceLoader` 不同实现 |
| **适配器** | `HandlerAdapter`（适配不同 Controller） |
| **装饰器** | `ServerHttpRequestDecorator` |
| **责任链** | `FilterChain`, `InterceptorChain` |
| **建造者** | `SpringApplicationBuilder` |

## 6. 架构模式与分层

### 6.1 MVC / MVP / MVVM

| 模式 | Model | View | Controller/Presenter/ViewModel |
|------|-------|------|-------------------------------|
| **MVC** | 数据+逻辑 | 展示 | Controller 处理输入 |
| **MVP** | 数据+逻辑 | 被动展示 | Presenter 双向绑定 View |
| **MVVM** | 数据+逻辑 | XAML/布局 | ViewModel 数据绑定（Data Binding） |

### 6.2 常见分层架构

```text
传统分层架构（DDD 之前）：
┌─────────────────┐
│   Controller     │  ← 接收请求、参数校验
├─────────────────┤
│   Service        │  ← 业务逻辑
├─────────────────┤
│   Repository     │  ← 数据访问
├─────────────────┤
│   Domain (Entity)│  ← 数据库实体（贫血模型）
└─────────────────┘

整洁架构（Clean Architecture）：
┌──────────────────────────────┐
│       Frameworks & Drivers   │  ← Controller, DB, Web
│  ┌──────────────────────┐    │
│  │   Interface Adapters │    │  ← DTO, Presenter, Gateway
│  │  ┌──────────────┐    │    │
│  │  │   Use Cases  │    │    │  ← Application Service
│  │  │  ┌──────┐    │    │    │
│  │  │  │Entity│    │    │    │  ← Domain（核心！）
│  │  │  └──────┘    │    │    │
│  │  └──────────────┘    │    │
│  └──────────────────────┘    │
└──────────────────────────────┘

依赖方向：外层 → 内层（内层不知道外层的存在）
```

## 7. DDD 领域驱动设计

### 7.1 战略设计

```text
DDD 战略设计核心概念：

  限界上下文（Bounded Context）：
    → 一个领域模型的语义边界
    → 同一个"用户"在不同上下文中有不同含义：
      订单上下文：User = {userId, shippingAddress}
      认证上下文：User = {username, password, roles}

  上下文映射（Context Map）：
    → 限界上下文之间的关系
    ├── 共享内核（Shared Kernel）
    ├── 客户-供应商（Customer-Supplier）
    ├── 防腐层（Anti-Corruption Layer, ACL）
    │   → 在自己的边界内定义模型，不受外部模型污染
    ├── 开放主机服务（Open Host Service, OHS）
    └── 发布语言（Published Language）

  通用语言（Ubiquitous Language）：
    → 开发团队和业务专家使用相同的术语
    → 代码中直接体现业务语言
```

### 7.2 战术设计

| 概念 | 说明 | 代码示例 |
|------|------|---------|
| **Entity** | 有唯一标识，可变 | `Order(id, status)` |
| **Value Object** | 无标识，不可变 | `Money(amount, currency)` |
| **Aggregate** | 实体+值对象的聚合根 | `Order` 聚合根管理 `OrderItem` |
| **Repository** | 聚合的持久化接口 | `OrderRepository.save(order)` |
| **Domain Service** | 不属于任何实体的领域逻辑 | `TransferService.transfer(from, to, money)` |
| **Domain Event** | 领域中发生的事件 | `OrderPaidEvent(orderId, paidTime)` |
| **Factory** | 复杂聚合的创建 | `OrderFactory.createFrom(cart)` |

```java
// DDD 聚合示例
@Getter
public class Order extends AggregateRoot {  // 聚合根
    private OrderId id;           // 值对象
    private UserId userId;
    private Money totalAmount;    // 值对象
    private OrderStatus status;
    private List<OrderItem> items = new ArrayList<>();  // 只能通过聚合根操作

    // 领域行为（而非 setter）
    public void addItem(Product product, Quantity quantity) {
        if (status != OrderStatus.DRAFT) {
            throw new OrderNotEditableException();
        }
        items.add(new OrderItem(product.getId(), product.getPrice(), quantity));
        recalculateTotal();
    }

    public void pay() {
        if (status != OrderStatus.DRAFT) {
            throw new IllegalOrderStatusException();
        }
        if (items.isEmpty()) {
            throw new EmptyOrderException();
        }
        this.status = OrderStatus.PAID;
        addDomainEvent(new OrderPaidEvent(this.id));
    }
}
```

> 🎯 **一句话总结**：设计模式解决的是 **代码级别的复用与解耦**，架构模式解决的是 **系统级别的组织与分工**，DDD 则让代码直接反映业务领域，避免"翻译损耗"。
