## 1. 创业公司/小团队 (5-30人)

### 1.1 典型技术栈

| 维度 | 技术选型 | 说明 |
|------|---------|------|
| 后端框架 | Spring Boot 3.x + MyBatis-Plus | 单体应用为主，快速开发，易上手 |
| 数据库 | MySQL (阿里云RDS) + Redis (阿里云Redis) | 云托管，免运维，按量付费 |
| 消息队列 | RabbitMQ / 甚至不需要 | 流量小的时候线程池就能处理异步 |
| 注册中心/配置 | 不需要 / 简单Nacos | 服务数少，写死IP也行 |
| 网关 | Nginx反向代理 | 不需要Spring Cloud Gateway，Nginx足够 |
| 部署 | Docker Compose + 阿里云ECS | 一般不碰K8s，维护成本太高 |
| CI/CD | Jenkins简单流水线 / 手动部署 | 快速迭代优先，测试自动化程度低 |
| 监控 | 阿里云CloudMonitor / 简单Grafana | 云厂商自带即可，不搭ELK |
| 前端 | Vue3 / React + Element Plus | 全栈开发一人搞定 |
| 协作工具 | Git + GitHub/GitLab + 飞书/钉钉 | 敏捷沟通，文档偏少 |
| 对象存储 | 阿里云OSS / 腾讯云COS | 图片、文件上传直接走云服务 |

### 1.3 工具链

| 类别 | 工具 | 说明 |
|:----:|------|------|
| IDE | IntelliJ IDEA (社区版/付费版) | VS Code也常见，前端后端一把梭 |
| 版本控制 | Git + GitHub/Gitee | 简单分支策略（master + feature） |
| 接口调试 | Postman / Apifox | Apifox集成了接口管理和Mock |
| 云服务器 | 阿里云ECS / 腾讯云CVM | 2核4G起步，一年几百块 |
| 项目管理 | 飞书多维表格 / Notion | 轻量级，没有专门PM |
| 沟通 | 飞书 / 钉钉 / 企业微信 | 全天在线，随时响应 |

### 1.4 技术特点

| 特点 | 正面 | 反面 |
|:----:|------|------|
| **快速迭代** | 一周上线一个功能，验证速度快 | 技术债越积越多，后期重构成本高 |
| **一人多能** | 后端也要写前端、配运维、搭CI | 深度不够，没有时间钻研底层 |
| **选型保守** | 不踩新技术的坑，稳定成熟 | 错失技术红利，系统扩展性差 |
| **沟通高效** | 微信一句话就能决策 | 缺少文档沉淀，新人上手难 |
| **成本敏感** | 云服务按量付费，控制成本 | 高可用方案缺位，出问题只能重启 |

### 1.5 面试中如何评价创业公司经历

```
❌ 错误回答：
"我在小公司，技术栈比较浅，用的就是Spring Boot + MySQL，没什么可说的。"
(贬低自己的经历，面试官会觉得你没有总结能力)

✅ 优秀回答框架：

"我在创业公司虽然技术栈以Spring Boot单体为主，
但正因为团队小，我从需求分析到上线部署全流程都做过。
具体来说：

1️⃣ 从零搭建项目：我负责了整个后端的架构选型和初始化，
   选择了Spring Boot + MyBatis-Plus + MySQL + Redis这套方案。
   选型考虑是：团队成员都熟悉Java、业务场景以CRUD为主、
   短期没有微服务化的必要。

2️⃣ 经历过完整链路：对接过支付宝和微信支付、做过数据库设计
   和SQL优化、配置过Nginx和HTTPS证书、搭过Jenkins自动部署。

3️⃣ 有技术判断力：我知道单体架构在业务增长后需要拆成微服务，
   也规划好了分表方案（预留了分布式ID和分表键），
   不是只会CRUD不考虑未来。

4️⃣ 踩过坑才有深度：有一次线上OOM，我从堆转储分析到线程Dump，
   最终定位到是ThreadLocal没有清理导致的内存泄漏。
   这种实战排查经验，是大厂里分工细化的环境下不容易获得的。"

🎯 核心亮点：
1. 强调"全流程经验"——广度是你的核心优势
2. 承认"简单够用"的合理性——展示技术选型的判断力
3. 展示"知道怎么进化"——体现架构思维，不是只会CRUD
4. 穿插具体踩坑案例——证明你不仅有广度，也有深度思考
```

> 💡 **面试策略**：创业公司面试大厂，你的优势是**对抗未知的勇气**和**全栈视野**。面试官通常不介意你深度不够——深度可以培养，但视野和主动性很难。关键是你能不能说清楚**当时为什么那样选，以及如果重新来会怎么优化**。

> ⚠️ **避坑提醒**：不要过度渲染"我什么都会"——面试官会找你不熟的方向深挖。建议主攻2-3个核心技术（如Spring Boot自动配置原理、MySQL索引优化、Redis缓存设计），展示你在广度之上的深度。

## 2. 中型互联网公司 (50-300人)

### 2.1 典型技术栈

公司规模变大后，**规范化**和**扩展性**成为核心诉求。技术栈从单体演进为微服务架构：

| 维度 | 技术选型 | 说明 |
|:----:|---------|------|
| 后端框架 | Spring Cloud Alibaba 全家桶 | Nacos + Sentinel + Gateway + Seata + OpenFeign |
| 注册中心 | Nacos集群 (3节点) | AP/CP模式按场景选择，配置中心二合一 |
| 数据层 | MySQL主从 + ShardingSphere分库分表 | 数据量上来后必须分库，读写分离 |
| 缓存 | Redis Cluster (3主3从) | 哨兵模式不够用，集群方案支持水平扩展 |
| 消息队列 | RocketMQ 集群 (4主4从) | 事务消息、顺序消息、延迟消息全用上 |
| 搜索引擎 | Elasticsearch 集群 | 搜索业务 + 日志分析 + APM数据 |
| 网关 | Spring Cloud Gateway + 灰度发布 | 路由规则热更新到Nacos，灰度切流量 |
| 分布式事务 | Seata (AT/TCC模式) | 跨服务事务一致性的主流方案 |
| 部署 | K8s (3-5节点) | 容器化基本成熟，有专门的DevOps |
| CI/CD | Jenkins / GitLab CI | 自动化测试 + 自动部署 + 质量门禁 |
| 监控 | Prometheus + Grafana + ELK + SkyWalking | 可观测性三支柱齐备 |
| 任务调度 | XXL-JOB | 分布式定时任务，分片广播 |
| 对象存储 | MinIO / 阿里云OSS | 自建或云服务，文件服务独立部署 |
| 配置管理 | Nacos配置中心 | 配置热更新，多环境(dev/test/prod)管理 |

### 2.3 监控体系：Prometheus + Grafana + ELK + SkyWalking

中型公司的可观测性体系通常按**指标(Metrics)、日志(Logs)、链路(Traces)** 三支柱搭建：

| 支柱 | 工具 | 采集内容 | 告警规则示例 |
|:----:|------|---------|-------------|
| **指标** | Prometheus + Grafana | CPU/内存/JVM/接口QPS/P99延迟 | P99 > 3s → 钉钉告警 |
| **日志** | Filebeat + ELK (ES + Logstash + Kibana) | 业务日志、异常栈、请求日志 | ERROR日志5分钟内>100条 → 告警 |
| **链路** | SkyWalking + Agent探针 | 服务间调用拓扑、慢Trace、SQL耗时 | 单次调用 > 5s → 慢查询追踪 |
| **告警** | Alertmanager → 钉钉/企微/电话 | 聚合告警、告警静默、值班排班 | 核心接口错误率 > 1% → 电话告警 |

```
🔔 告警分级示例：

P0 (致命): 核心接口不可用 → 立即电话 + 钉钉@所有人
  例：登录/支付/下单接口500错误率>5%

P1 (严重): 功能受损 → 钉钉@值班人 + 企微通知
  例：P99延迟 > 5s、数据库连接池耗尽

P2 (一般): 需要关注 → 钉钉群通知
  例：磁盘使用率 > 80%、JVM FullGC频率升高

P3 (提示): 日常观察 → 日报/周报汇总
  例：慢SQL数量增加、缓存命中率下降
```

### 2.4 技术特点

| 维度 | 发展期特点 | 挑战 |
|:----:|-----------|------|
| **服务拆分** | 按业务域拆分为10-30个微服务 | 拆得太细导致治理成本 > 收益 |
| **容器化** | Docker + K8s 基本普及 | 学习曲线陡，初期运维靠人肉 |
| **DevOps** | CI/CD Pipeline + 自动化测试 | 流水线不稳定，测试覆盖率不足 |
| **中间件** | MQ/ES/Redis 集群化部署 | 中间件版本管理混乱，升级困难 |
| **监控** | 可观测性三支柱基本到位 | 告警太多变"狼来了"，有效告警率低 |
| **团队** | 后端/前端/测试/运维分工明确 | 跨部门协作成本上升，沟通效率下降 |

### 2.5 具体案例：SuGuangMall项目技术栈映射

以SuGuangMall电商项目为参考，展示中型互联网公司技术栈的完整落地：

| 模块 | 技术选型 | 说明 |
|:----:|---------|------|
| **用户服务** | Spring Boot + MyBatis-Plus + MySQL | 用户注册/登录/个人信息，集成Sa-Token权限 |
| **商品服务** | Spring Boot + ES + Redis | 商品搜索用ES，商品详情缓存到Redis |
| **订单服务** | Spring Boot + Seata + RocketMQ | 订单创建用Seata AT事务，下单成功发MQ通知 |
| **支付服务** | Spring Boot + 支付宝/微信SDK | 支付回调处理，幂等控制，对账 |
| **库存服务** | Spring Boot + Redis (库存预占) | Redis原子操作扣减库存，MQ异步落库 |
| **搜索服务** | Elasticsearch + Canal + Kibana | Canal同步MySQL binlog到ES，保持数据一致 |
| **网关** | Spring Cloud Gateway + JWT | 路由转发 + Token鉴权 + 接口限流 |
| **注册/配置** | Nacos (集群) | AP模式做注册中心，配置热更新 |
| **部署** | Docker + K8s + Jenkins | 微服务容器化部署，GitLab CI自动构建 |
| **监控** | Prometheus + Grafana + SkyWalking | 接口QPS/P99监控 + 全链路追踪 |

> 💡 **项目面试话术**："SuGuangMall是一个基于Spring Cloud Alibaba的微服务电商项目，服务数量8个左右。我主要负责订单和支付两个核心域。下单链路涉及Redis库存预占→Seata分布式事务→RocketMQ异步通知→ES数据同步→SkyWalking全链路追踪，基本覆盖了中型互联网公司典型的技术栈。"

### 2.6 面试中如何评价中型公司经历

```
✅ 优秀回答框架：

"我在上一家中型互联网公司（200人左右）担任后端开发，负责订单域。
技术栈是Spring Cloud Alibaba全套，服务数大概15个左右。

我最大的收获有三个方面：

第一是微服务治理的实战经验。
比如服务多了以后，Nacos频繁推送导致服务间调用超时，
后来排查发现是Nacos AP模式下健康检查过于敏感，
调整了心跳间隔（从5s调整为15s）解决了。
再比如Sentinel限流规则的动态配置，我们通过Nacos持久化实现，
避免了每次重启规则丢失的问题。

第二是稳定性建设。
我是我们组On-Call值班的负责人，经历过几次线上事故后，
搭建了完善的告警体系。核心接口P99 > 3s钉钉告警，
错误率 > 1%电话告警，每天自动出稳定性日报。

第三是性能优化的实践经验。
以MySQL为例，我们有一个慢查询导致接口超时的问题，
通过EXPLAIN分析发现是索引失效（隐式类型转换），
修复后查询时间从2.3s降到15ms。

当然现在回头看也有不足：
- 微服务拆得比较随意，没有严格按DDD划分边界
- 配置管理没有统一规范，各服务有自己的配置文件
- 发布流程太慢，从开发到上线要一周

如果让我重新规划，会更早引入配置规范，用统一的配置中心做配置管理。"

🎯 核心亮点：
1. 具体技术场景 + 解决方案（证明实战经验）
2. 稳定性建设和值班制度（证明运维意识）
3. MySQL索引优化的量化数据（证明深度）
4. 反思不足 + 改进方案（证明架构思维）
```

> ⚠️ **面试提醒**：中型公司的面试往往最侧重**实战经验**。面试官会问"你们用XX遇到过什么问题？怎么解决的？"提前准备2-3个你工作中的技术难题和解决过程，比背八股文有用得多。

## 3. 大厂 (BAT/字节/美团/京东)

### 3.1 技术栈特点：自研中间件为主 + 开源为辅

### 3.7 面试重点：不只问怎么用，更问原理和二次开发

大厂面试对技术栈的要求呈现明显的**深度分层**：

| 层级 | 要求 | 举例：Redis |
|:----:|------|------------|
| **使用层** (P5) | 能正确使用API和常见场景 | 会用RedisTemplate，知道5种基本数据类型 |
| **原理层** (P6) | 理解底层数据结构和算法 | 知道SDS/跳表/压缩列表/RedisObject结构 |
| **源码层** (P6+) | 读过核心源码，能说出关键流程 | 读过setCommand/getCommand、AOF/RDB重写机制 |
| **调优层** (P7) | 能根据场景做性能调优 | 调整hash-max-ziplist-entries、内存碎片优化、Pipeline |
| **二次开发层** (P7+) | 能基于开源做定制化 | 自定义数据类型、改通信协议、加监控埋点 |
| **自研层** (P8+) | 能实现替代方案 | 理解Raft选主、自己做分布式缓存 |

```
大厂面试官的核心关注点（按权重排序）：

1️⃣ 原理理解 (40%) —— 不只是API，是"为什么这么设计"
   例：为什么Redis用单线程？为什么Kafka吞吐高？
   为什么Sentinel用滑动窗口做统计？

2️⃣ 场景判断 (30%) —— 知道在什么场景下用什么技术
   例：什么时候用MQ解耦？什么时候用分布式锁？
   分库分表的策略怎么选？

3️⃣ 踩坑经验 (20%) —— 曾经踩过什么坑，怎么解决的
   例：缓存一致性怎么保证？分布式事务失败怎么处理？
   OOM怎么排查？

4️⃣ 原理广度 (10%) —— 有没有横向对比不同方案的差异
   例：RocketMQ vs Kafka vs RabbitMQ 的选型对比
   Seata AT vs TCC vs Saga 的选择
```

> ⚠️ **大厂面试真相**：千万别觉得"会用"就够了。大厂面试P6（高级工程师）时，对核心中间件的**原理层是基本要求**，源码层是加分项。P7+（资深工程师/架构师）要求到**调优层和二次开发层**。

### 6.2 面试中被问"为什么选这个技术栈"的四步回答法

这是面试中极高频率的问题，回答时按**场景 → 对比 → 决策 → 反思**四步：

```
📋 四步回答法：

Step 1: 场景 (Context) —— 讲清楚背景
"当时的情况是：团队5个人、创业初期、DAU 1万左右、
业务逻辑复杂度中等、要求在3个月内上线MVP。
我们面临的核心约束是：人少、时间紧、预算有限。"

Step 2: 对比 (Comparison) —— 展示你有做调查研究
"我们在以下几个方案中做了权衡：
- 单体 vs 微服务：选单体。DAU才1万，微服务的治理成本远大于收益。
  引入Nacos/Sentinel/Gateway/Seata这套，5个人光运维就忙不过来。
- MySQL还是MongoDB：选MySQL。业务关系复杂（订单/用户/商品/支付关联），
  MongoDB的多文档事务不如MySQL的ACID成熟。
- Docker Compose vs K8s：选Docker Compose。没人懂K8s，
  学了再上线黄花菜都凉了。直接ECS + Docker Compose先跑起来。"

Step 3: 决策 (Decision) —— 讲清楚最终选择和核心理由
"最终的选型是：Spring Boot 3 + MySQL 8 + Redis 7 + Docker Compose。
核心原则是：**用最成熟的技术解决当前问题，不为未来的不确定性买单**。
在满足需求的前提下，选团队最熟悉、社区最活跃、资料最丰富的方案。"

Step 4: 反思 (Retrospective) —— 展示成长性思维
"现在回头看，这个决策基本正确。但有一点遗憾：
当时MySQL没有预留分表的字段（用了自增主键，没用分布式ID），
导致后来数据量大时做分表比较痛苦。
如果能重来，我会一开始就设计好分表方案：
用雪花算法ID + 按时间分区，即使当时不需要分区，
但预留了扩展性，后续迁移成本会低很多。"

🎯 这套回答展示了什么？
- 你能基于实际场景做技术判断 (场景驱动的选型思维)
- 你考虑过多个方案并且能说清楚优劣 (权衡能力)
- 你能复盘并承认不足 (成长性思维)
- 你有架构前瞻性 (不是只解决眼前问题)
```

```
├─ MySQL主从 + ShardingSphere (用户/订单表分库)
├─ Redis Cluster (缓存 + 分布式锁 + Session共享)
├─ RocketMQ (交易消息 + 异步通知 + 死信重试)
├─ Elasticsearch (商品搜索 + 订单搜索)
├─ K8s (15个微服务容器化)
├─ Prometheus + Grafana + SkyWalking (可观测性)
└─ Jenkins + GitLab CI (CI/CD)

总成本：~3-5万/月 (云服务 + 自建K8s节点)
```

**案例3：大型互联网平台 (成熟阶段)**

```
场景：100+后端，上市/Pre-IPO，DAU 5000万+
选型：
├─ 自研RPC框架 (Kitex/HSF/JSF)
├─ 自研微服务治理体系 (Service Mesh + Sidecar)
├─ 自研分布式数据库 (OceanBase/PolarDB/veDB)
├─ 自研消息队列 (RocketMQ深度定制/BMQ/JMQ)
├─ 自研缓存系统 (Tair/Squirrel)
├─ 自研配置中心 (Lion/自研)
├─ 多活架构 + 单元化 (2-3个机房同时服务)
├─ 全链路压测 + 混沌工程
├─ 全链路可观测性 (自建APM + OpenTelemetry)
└─ AI for Ops (智能告警/根因定位/容量预测)

总成本：千万级/月 (基础设施 + 中间件团队)
```

> 🎯 **核心要点**：技术选型没有绝对的对错，只有合不合适。面试官问技术选型，看的不是"你选了什么"，而是"你**为什么这么选**"——你考虑了哪些因素，权衡了哪些取舍。这种决策能力是一个架构师的核心素养。

## 7. 面试标准话术

### 7.1 "你期望在什么样的技术栈下工作？"标准回答

这是面试中出现频率极高的问题。面试官想考察的是：
- 你是否有技术追求和学习意愿
- 你关注技术本身还是业务价值
- 你是否能适应目标公司的技术环境
- 你对新技术的态度（盲目追新 vs 实际有用）

```
✅ 标准回答模板（根据情况选择）：

📌 版本A：强调成长与挑战（适合面互联网公司）

"我期望的技术栈有以下几个特点：

第一，**有挑战的技术问题**。我希望工作中能接触到高并发、
分布式、数据一致性这类场景。比如用Redis解决缓存问题、
用MQ做异步解耦、用分布式事务保证一致性——
这些场景能让我持续成长，而不是天天写CRUD。

第二，**有规范的工程实践**。我希望团队有完善的Code Review、
CI/CD和自动化测试流程。代码质量上的追求，
最终会反映在系统的稳定性和自己的成长速度上。

第三，**不排斥但也不盲从新技术**。我不会因为一个技术"火"
就去追，而是会基于实际场景判断是否合适。
但同时我也保持学习和研究——比如最近我在学习
Virtual Threads和LangChain4j，虽然当前项目不一定用得上，
但保持对新技术的敏锐度是必要的。

对于贵司的技术栈，我了解主要是XX和XX（提前做了功课），
我认为与我的技术方向和成长预期是匹配的。"

📌 版本B：强调务实与价值（适合面传统企业/国企）

"比起具体用什么技术栈，我更关注**解决的问题是否有价值**。
我认为技术是为业务服务的，先进的技术如果不能解决实际问题
就没有意义。在上一家公司，我用Spring Boot搭建了一套
完整的订单系统，虽然没有微服务化，但很好地支撑了业务增长。

当然我也在不断学习新技术，保持自己的竞争力。
我理解贵司的技术栈以XX为主，虽然是成熟技术，
但稳定性和可靠性经过了长时间验证，这是对用户负责的表现。
我相信我的技术基础能快速适应贵司的环境。"

📌 版本C：强调能力可迁移（适合跨行业跳槽）

"我不会把技术栈当成选择公司的首要标准。
我的经验告诉我，**核心的工程能力是可迁移的**——
不管是Spring Boot还是ASP.NET Core，不管是MySQL还是Oracle，
背后的设计理念（事务、索引、缓存、异步）是相通的。

我更看重的是：团队的技术氛围、代码质量要求、和技术Leader的视野。
具体用什么框架和语言，给我2-4周时间我就能上手。"

⚠️ 不管哪个版本，一定要加上最后一句，展示你做了功课：
"我在来面试前已经了解过贵司的技术栈，主要是XX和XX，
和我的技术方向是匹配的/是我想要学习的方向。"
```

### 7.2 其他高频面试话术

**"你认为一个好的技术栈应该具备什么特征？"**

```
✅ 回答框架：

一个好的技术栈应该具备五个特征：

1️⃣ 社区活跃：有足够多的用户和贡献者，
   遇到问题能搜到答案，不担心项目突然消亡。
   （不看star数的绝对值，看增长趋势和Issue响应速度）

2️⃣ 团队匹配：团队里有人懂，或者学习成本可控。
   引入一个没人会的技术栈，风险远大于收益。

3️⃣ 场景适配：技术的设计哲学和业务场景匹配。
   就像你不会用Kafka处理延迟消息，不会用RabbitMQ做日志收集。

4️⃣ 生态兼容：能和现有技术栈良好集成。
   Spring Cloud Alibaba的好处就是和Spring Boot无缝衔接。

5️⃣ 可演进：技术本身有持续发展的动力，
   不会短时间内被替代。也要考虑升级路径是否平滑。
```

**"你用过哪些技术？都到什么程度？"**

```
✅ 回答框架（按领域组织，不要散装罗列）：

"按领域来说，我最深入的是三个方向：

1️⃣ Java生态：Spring Boot的自动配置原理、@Conditional机制、
   自定义Starter开发都理解得很清楚。
   Spring Cloud Alibaba的Nacos（AP/CP模式切换、健康检查机制）
   和Sentinel（滑动窗口限流、规则持久化）读过部分核心源码。

2️⃣ 数据存储：MySQL的索引优化、事务隔离级别和MVCC有实战经验。
   Redis的5种数据结构底层实现、持久化和主从复制原理理解较深。

3️⃣ 中间件：RocketMQ的事务消息和顺序消息在生产环境用过，
   了解其存储机制和刷盘策略。ES的倒排索引和DSL查询有一定实践。

其他技术像K8s、Docker、Prometheus能达到独立使用的水平，
但还在持续深入学习中。"
```

**"你为什么选择Java而不是Go/Python？"**

```
✅ 回答框架：

"选择Java主要是三个原因：

1️⃣ 生态成熟：Java在企业级应用中的生态是最完善的。
   Spring全家桶让复杂的微服务开发变得标准化，
   中间件（MQ/ES/Redis/NoSQL）对Java的集成支持最好。

2️⃣ 大厂背书：国内头部互联网公司（阿里/美团/京东）的核心系统
   仍然以Java为主，这意味着Java开发者的职业天花板很高。

3️⃣ 性能+规范性平衡：Java比Python/Ruby性能好，
   比Go的工具链成熟、框架统一。Virtual Threads出来后，
   并发编程的复杂度也大大降低了。

当然我也在学习Go——主要看中它在云原生和中间件开发领域的优势。
但我认为Java在未来5-10年依然是企业级后端的第一选择。"
```

### 7.3 面试中绝对不要说的话

```
❌ "我什么都会" —— 面试官会找你最弱的方向深挖，露馅扣分
❌ "这些技术都差不多" —— 说明你没有深入了解过差异
❌ "我只做业务，不管用啥" —— 说明你没有技术热情
❌ "大厂用的都是自研，我没用过所以不了解" —— 避重就轻，显得没有学习主动性
❌ "Spring Boot就是自动配置，具体原理我没看过" —— 面试官一秒判断水平
```

> 🎯 **面试话术核心原则**：不夸大、不贬低、展示思考过程、展示学习意愿、展示工程判断力。面试官选的是**能解决问题的人**，不是**知道最多技术名词的人**。

## 各规模公司面试策略总结

| 公司类型 | 面试重点 | 需要准备的内容 |
|:--------:|:--------:|:-------------:|
| **创业公司** | 动手能力 + 全栈视野 | 完整项目经验、快速学习能力、抗压能力 |
| **中型公司** | 实战经验 + 微服务治理 | 具体踩坑案例、技术选型理由、稳定性建设 |
| **大厂** | 原理深度 + 源码理解 + 架构思维 | 核心中间件源码、设计模式、高并发方案 |
| **国企/银行** | 工程规范 + 安全意识 + 文档能力 | 对稳定的理解、合规意识、长期规划 |
| **外企** | 系统设计 + 英语沟通 + 工程文化 | Design Doc风格回答、英文自我介绍、BQ准备 |
