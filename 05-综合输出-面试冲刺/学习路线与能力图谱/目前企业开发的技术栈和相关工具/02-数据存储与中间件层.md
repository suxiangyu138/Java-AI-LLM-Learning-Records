## 1. MySQL — 企业级数据库实践

> MySQL是Java后端最核心的持久化存储，面试中围绕InnoDB引擎、索引优化、SQL调优的考察密度极高。

### 1.1 企业中MySQL的真实用法

#### 1.1.1 部署架构选型

| 架构模式 | 适用场景 | 优点 | 缺点 |
|---------|---------|------|------|
| **单机部署** | 开发/测试环境、小型应用 | 简单、成本低 | 单点故障、性能瓶颈 |
| **主从复制 (Master-Slave)** | 读写分离、备份恢复 | 读扩展、数据备份 | 主节点仍是单点 |
| **主主复制 (Master-Master)** | 双活写入、高可用 | 任一节点可写 | 冲突处理复杂 |
| **MGR (MySQL Group Replication)** | 强一致性要求 | 自动选主、多节点写入 | 版本要求高、网络敏感 |
| **PXC (Percona XtraDB Cluster)** | 金融级数据一致性 | 同步复制、多节点强一致 | 写入性能下降 |

#### 1.1.2 读写分离架构

```
          +-----------+
          |  应用层    |
          +-----+-----+
                |
          +-----+-----+
          |  读写分离   |
          |  中间件     |  (ShardingSphere/MyCat/ProxySQL)
          +--+------+--+
             |      |
     +-------+--+  ++--------+
     |  Master  |  |  Slave   |
     | (写)     |  | (读)     |
     +----------+  +----------+
                    |  Slave   |
                    | (读)     |
                    +----------+
```

> 💡 **企业实践**：一主多从架构下，一般配置2~3个Slave节点。写请求路由到Master，读请求分发到Slave。从节点可以承担数据报表、ES数据同步等非核心业务查询。

### 1.2 InnoDB核心原理——面试必问深度

#### 1.2.1 B+Tree索引结构

| 对比维度 | B+Tree | B-Tree | Hash |
|---------|--------|--------|------|
| 非叶子节点 | 只存索引键 | 存索引键+数据 | - |
| 叶子节点 | 存数据+双向链表 | 存数据 | - |
| 范围查询 | 高效（链表遍历） | 低效（回溯） | 不支持 |
| 等值查询 | O(logN) | O(logN) | O(1) |
| 磁盘I/O次数 | 树高度决定（一般3~4层） | 树高度决定 | 1次 |

**聚簇索引 vs 辅助索引**：

```
聚簇索引 (Primary Key)
  [10|...] → [20|...] → [30|...] → ...
    ↓           ↓           ↓
  数据行      数据行      数据行

辅助索引 (Secondary Index)
  [name='Alice'|pk=10] → [name='Bob'|pk=20] → ...
          ↓                       ↓
      回表查询聚簇索引          回表查询聚簇索引
```

#### 1.2.2 MVCC (多版本并发控制)

> 💡 **核心机制**：MVCC通过"快照读"实现非阻塞读，写操作不影响读操作，大幅提升并发性能。

**三个关键隐藏字段**：

| 字段 | 含义 | 作用 |
|-----|------|------|
| `DB_TRX_ID` | 事务ID | 标识最后修改该行的事务 |
| `DB_ROLL_PTR` | 回滚指针 | 指向Undo Log中的上一个版本 |
| `DB_ROW_ID` | 行ID | 未定义主键时的隐藏主键 |

**Undo Log版本链**：

```
事务100: INSERT
  → 事务200: UPDATE name='Bob'
    → 事务300: UPDATE name='Charlie'
      → (最新版本)
```

**ReadView可见性判断**：

```text
ReadView结构:
  - m_ids:   活跃事务ID列表（启动时未提交的）
  - min_trx_id: 最小活跃事务ID
  - max_trx_id: 预分配的下一个事务ID
  - creator_trx_id: 创建该ReadView的事务ID

判断规则:
  1. DB_TRX_ID == creator_trx_id → 可见（自己修改的）
  2. DB_TRX_ID < min_trx_id  → 可见（已提交的）
  3. DB_TRX_ID >= max_trx_id → 不可见（未来事务）
  4. DB_TRX_ID ∈ m_ids      → 不可见（未提交）
```

#### 1.2.3 锁机制

| 锁类型 | 粒度 | 说明 | 加锁时机 |
|-------|------|------|---------|
| **表锁** | 整张表 | MyISAM使用，InnoDB不使用 | DDL语句 |
| **行锁** | 单行记录 | InnoDB最细粒度锁 | UPDATE/DELETE/FOR UPDATE |
| **间隙锁 (Gap Lock)** | 间隙范围 | 防止幻读，RR级别默认 | 范围条件查询 |
| **Next-Key Lock** | 行+间隙 | 行锁与间隙锁组合 | RR级别索引条件 |
| **意向锁** | 表级别 | 快速判断行锁存在 | 加行锁前自动加 |

> ⚠️ **面试高频题**：MySQL RR级别如何解决幻读？答案是 **Next-Key Lock**。在`SELECT ... FOR UPDATE`时，不仅锁住命中行，还锁住行之间的间隙，防止新记录插入。

### 1.3 索引设计与优化

#### 1.3.1 联合索引（最左前缀原则）

```sql
-- 创建联合索引
CREATE INDEX idx_org_status_time ON t_order (org_id, status, create_time);

-- 走索引的情况（最左前缀匹配）
WHERE org_id = 100;                                 -- 只使用org_id
WHERE org_id = 100 AND status = 1;                  -- 使用org_id + status
WHERE org_id = 100 AND status = 1 AND create_time > '2026-01-01'; -- 完全使用

-- 不走索引或部分走索引的情况
WHERE status = 1;                                   -- 无最左列，全表扫描
WHERE org_id = 100 AND create_time > '2026-01-01';  -- 只用到org_id，跳过status
```

> 🎯 **核心要点**：联合索引本质上是**有序的多维数组**，优先按第一列排序，同值下按第二列排序。跳过了中间列，后面的列无法使用索引。

#### 1.3.2 覆盖索引（Covering Index）

```sql
-- 表结构
CREATE TABLE t_user (
  id BIGINT PRIMARY KEY,
  name VARCHAR(50),
  age INT,
  email VARCHAR(100),
  INDEX idx_name_age (name, age)
);

-- 覆盖索引查询：SQL所需字段完全在索引中，无需回表
EXPLAIN SELECT name, age FROM t_user WHERE name = 'Alice';
-- Extra: Using index  ← 表示使用了覆盖索引

-- 非覆盖索引查询：需要回表
EXPLAIN SELECT name, email FROM t_user WHERE name = 'Alice';
-- Extra: Using index condition  ← 需要回表查询email
```

#### 1.3.3 索引下推 (Index Condition Pushdown, ICP)

```sql
-- MySQL 5.6+ 特性：将WHERE条件从Server层"下推"到存储引擎层过滤

-- 示例：联合索引 idx_age_name (age, name)
SELECT * FROM t_user WHERE age > 20 AND name LIKE '%Li%';

-- 无ICP时:
--   存储引擎扫描age>20的记录 → 回表 → Server层过滤name LIKE
-- 有ICP时:
--   存储引擎同时用age和name条件过滤 → 减少回表次数
```

#### 1.3.4 EXPLAIN实战解读

| 列名 | 关键值 | 含义 |
|-----|--------|------|
| `type` | `const` → `ref` → `range` → `index` → `ALL` | 访问类型（从好到差） |
| `key` | 实际使用的索引名 | 使用了哪个索引 |
| `rows` | 扫描行数估算 | 越少越好 |
| `Extra` | `Using index` | 覆盖索引，最佳 |
| `Extra` | `Using filesort` | 需要额外排序，需优化 |
| `Extra` | `Using temporary` | 使用了临时表，需优化 |
| `Extra` | `Using index condition` | 使用了ICP |

```sql
-- 优化前
EXPLAIN SELECT * FROM t_order WHERE status = 0 ORDER BY create_time DESC;
-- type: ALL, Extra: Using filesort  ← 全表扫描+额外排序，危险！

-- 优化后：创建联合索引
CREATE INDEX idx_status_create_time ON t_order (status, create_time);
EXPLAIN SELECT * FROM t_order WHERE status = 0 ORDER BY create_time DESC;
-- type: ref, Extra: NULL  ← 索引定位+索引有序，高效！
```

### 1.4 SQL编写规范（企业级代码规范）

```sql
-- =============================================
-- 企业SQL编写规范示例
-- =============================================

-- 1. 禁止使用SELECT *，必须指定字段列表
-- 错误: SELECT * FROM t_user;
-- 正确:
SELECT id, name, age FROM t_user;

-- 2. 大表查询必须带LIMIT
SELECT id, name FROM t_order WHERE status = 1 LIMIT 100;

-- 3. JOIN不宜超过3张表，必须确保关联字段有索引
SELECT o.id, u.name
FROM t_order o
INNER JOIN t_user u ON o.user_id = u.id   -- user_id和id都有索引
WHERE o.create_time > '2026-01-01';

-- 4. WHERE条件中禁止对索引列做函数操作
-- 错误: WHERE DATE(create_time) = '2026-01-01'
-- 正确: WHERE create_time >= '2026-01-01' AND create_time < '2026-01-02'

-- 5. 分页查询深翻页优化
-- 错误（深翻页）: SELECT * FROM t_order LIMIT 1000000, 20;
-- 正确（子查询优化）:
SELECT * FROM t_order
WHERE id > (SELECT id FROM t_order ORDER BY id LIMIT 1000000, 1)
ORDER BY id LIMIT 20;

-- 6. UNION代替OR（OR导致索引失效）
-- 错误: SELECT * FROM t_user WHERE name = 'Alice' OR age = 25;
-- 正确:
SELECT * FROM t_user WHERE name = 'Alice'
UNION
SELECT * FROM t_user WHERE age = 25;

-- 7. 批量INSERT使用一条语句
INSERT INTO t_order (id, user_id, amount) VALUES
(1, 101, 99.9),
(2, 102, 199.9),
(3, 103, 299.9);
```

### 2.2 Redis数据类型在企业中的真实用法

#### 2.2.1 String（字符串）—— 最基础，但最常用

```java
// Spring Data Redis 示例
@Service
public class UserCacheService {
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    // 缓存穿透保护：缓存空值
    public User getUserById(Long id) {
        String key = "user:" + id;

        // 1. 查缓存
        User user = (User) redisTemplate.opsForValue().get(key);
        if (user != null) {
            return user;
        }

        // 2. 缓存空值保护（缓存穿透）
        String nullFlag = (String) redisTemplate.opsForValue().get(key + ":null");
        if (nullFlag != null) {
            return null;  // 防止穿透到DB
        }

        // 3. 查数据库
        user = userMapper.selectById(id);
        if (user == null) {
            // 设置空值缓存，TTL 60秒
            redisTemplate.opsForValue().set(key + ":null", "1", 60, TimeUnit.SECONDS);
        } else {
            // 正常缓存，TTL 30分钟
            redisTemplate.opsForValue().set(key, user, 30, TimeUnit.MINUTES);
        }
        return user;
    }
}
```

#### 2.2.2 Hash（哈希）—— 对象存储优选

```java
// Hash适合存储结构化对象，比String + JSON更节省内存，支持字段单独操作
public void updateUserField(Long userId, String field, Object value) {
    String key = "user:" + userId;
    redisTemplate.opsForHash().put(key, field, value);
}
```

| 对比项 | String + JSON | Hash |
|-------|--------------|------|
| 内存占用 | 大（整个JSON序列化） | 小（独立字段存储） |
| 修改单个字段 | 需要全量读写 | 直接操作字段 |
| 序列化开销 | 高 | 低 |
| 适用场景 | 整体读写多的场景 | 频繁修改部分字段的场景 |

#### 2.2.3 List（列表）—— 简单消息队列

```java
// 生产者
public void sendTask(Long taskId) {
    redisTemplate.opsForList().rightPush("task:queue", taskId.toString());
}

// 消费者（阻塞读取）
public void consumeTask() {
    while (true) {
        String taskId = (String) redisTemplate.opsForList()
            .leftPop("task:queue", 5, TimeUnit.SECONDS);
        if (taskId != null) {
            processTask(Long.parseLong(taskId));
        }
    }
}
```

#### 2.2.4 ZSet（有序集合）—— 排行榜

### 2.3 缓存策略模式对比

| 模式 | 读操作 | 写操作 | 优点 | 缺点 |
|------|-------|--------|------|------|
| **Cache-Aside** | 先查缓存→未命中查DB→回写缓存 | 先写DB→删除缓存 | 实现简单、命中率高 | 存在短暂不一致 |
| **Read-Through** | 缓存层自动加载DB数据 | 同Cache-Aside | 对应用透明 | 实现复杂 |
| **Write-Through** | 同Read-Through | 先写缓存→缓存写DB | 一致性高 | 写入延迟增加 |
| **Write-Behind** | 同Read-Through | 先写缓存→异步写DB | 写入性能高 | 宕机可能丢数据 |

> 💡 **企业推荐**：**Cache-Aside** 是最广泛采用的模式。更新策略使用"先写DB，后删缓存"而不是"更新缓存"，因为后者在并发写入时会出现脏数据。

### 2.4 缓存穿透/击穿/雪崩的企业级解决方案

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 查询不存在的数据，每次穿透到DB | 1. 缓存空值<br>2. 布隆过滤器<br>3. 参数校验 |
| **缓存击穿** | 热点Key过期，高并发打到DB | 1. 互斥锁<br>2. 逻辑过期（异步刷新）<br>3. 永不过期+后台更新 |
| **缓存雪崩** | 大量Key同时过期，DB被打垮 | 1. TTL加随机值<br>2. 多级缓存（本地+Redis）<br>3. 限流降级 |

```java
// 布隆过滤器防止缓存穿透
@Component
public class BloomFilterService {
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    private static final String BLOOM_KEY = "bloom:users";
    private static final int EXPECTED_SIZE = 100_0000;
    private static final double FPP = 0.01;

    private BloomFilter<Long> bloomFilter;

    @PostConstruct
    public void init() {

            Funnels.longFunnel(), EXPECTED_SIZE, FPP);

// 互斥锁防止缓存击穿
public User queryWithMutex(Long id) {
    String key = "user:" + id;
    // 1. 查缓存
    User user = (User) redisTemplate.opsForValue().get(key);
    if (user != null) return user;

    // 2. 获取互斥锁
    String lockKey = "lock:user:" + id;
    Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);

    if (Boolean.TRUE.equals(locked)) {
        try {
            // 3. 查DB
            user = userMapper.selectById(id);
            redisTemplate.opsForValue().set(key, user, 30, TimeUnit.MINUTES);
            return user;
        } finally {
            redisTemplate.delete(lockKey);
        }
    } else {
        // 4. 没拿到锁，休眠后重试
        Thread.sleep(100);
        return queryWithMutex(id);
    }
}

// TTL加随机值防止雪崩
int baseTTL = 30 * 60;  // 30分钟
int randomTTL = baseTTL + new Random().nextInt(10 * 60);  // 增加0~10分钟随机值
redisTemplate.opsForValue().set(key, user, randomTTL, TimeUnit.SECONDS);
```

```java
@Configuration
public class RedissonConfig {
    @Bean
    public RedissonClient redissonClient() {
        Config config = new Config();
        config.useSingleServer()
            .setAddress("redis://localhost:6379")
            .setConnectionPoolSize(10);

@Service
public class OrderService {
    @Autowired
    private RedissonClient redissonClient;

    // 标准分布式锁
    public void createOrder(Long orderId) {
        RLock lock = redissonClient.getLock("order:" + orderId);
        try {
            // 尝试加锁，最多等3秒，锁有效30秒
            if (lock.tryLock(3, 30, TimeUnit.SECONDS)) {
                // 执行业务逻辑
                processOrder(orderId);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            lock.unlock();
        }
    }

    // 看门狗机制（自动续期）
    public void processWithWatchdog(Long orderId) {
        RLock lock = redissonClient.getLock("order:" + orderId);
        lock.lock(); // 默认30秒，看门狗每10秒续期一次
        try {
            // 执行业务逻辑（即使超过30秒也不用担心锁超时）
            longProcess(orderId);
        } finally {
            lock.unlock();
        }
    }

    // 可重入锁
    public void reentrantExample(Long userId) {
        RLock lock = redissonClient.getLock("user:" + userId);
        lock.lock();
        try {
            // 第一层
            innerMethod(userId);  // 内部再次加同一把锁，可重入
        } finally {
            lock.unlock();
        }
    }

    private void innerMethod(Long userId) {
        RLock lock = redissonClient.getLock("user:" + userId);
        lock.lock();  // 可重入：同一个线程可多次加锁
        try {
            // 内部逻辑
        } finally {
            lock.unlock();
        }
    }

    // 红锁（多节点分布式锁，RedLock算法）
    public void redLockExample(Long resourceId) {
        RLock lock1 = redissonClient.getLock("node1:resource:" + resourceId);
        RLock lock2 = redissonClient.getLock("node2:resource:" + resourceId);
        RLock lock3 = redissonClient.getLock("node3:resource:" + resourceId);
        RLock redLock = new RedissonRedLock(lock1, lock2, lock3);

        try {
            if (redLock.tryLock(5, 30, TimeUnit.SECONDS)) {
                // 获得多数节点锁，执行业务
                processResource(resourceId);
            }
        } finally {
            redLock.unlock();
        }
    }
}
```

> 💡 **看门狗机制**：Redisson的自动续期机制。锁默认30秒过期，看门狗每10秒检查一次，如果业务还在执行则自动续期到30秒。业务执行完毕主动释放，避免死锁。

```java
@Component
public class OrderTransactionListener implements TransactionListener {
    @Autowired
    private OrderService orderService;

    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            // 执行本地事务（创建订单）

            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;

        // 回查：检查本地事务是否成功

        return success ?

}
```

### 3.5 消息可靠性保证

> 💡 **端到端可靠性**：三端保障——Producer确认、Broker持久化、Consumer ACK。

```
┌─────────┐   Confirm    ┌─────────┐  持久化    ┌─────────┐
│Producer │ ───────────→ │ Broker  │ ────────→ │Consumer │
│         │              │         │           │         │
│ 重试机制 │              │ 同步刷盘 │           │ 手动ACK │
│ 事务消息 │              │ 主从复制 │           │ 幂等消费 │
│ 回调确认 │              │ OFFSET   │           │ 重试机制 │
└─────────┘              └─────────┘           └─────────┘
```

| 阶段 | 风险 | 解决方案 |
|------|------|---------|
| **生产者 → Broker** | 网络问题导致消息丢失 | Confirm回调 + 重试机制 |
| **Broker存储** | 宕机丢消息 | 同步刷盘 + 主从复制 / ISR |
| **Broker → 消费者** | 消费者崩溃 | 手动ACK + 死信队列 |

```java
public class IdempotentConsumer {
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    public boolean consume(String messageId, Consumer<Message> consumer) {
        String key = "msg:idempotent:" + messageId;
        // SETNX原子操作，保证只执行一次
        Boolean success = redisTemplate.opsForValue()

            return true;

        return false;
    }
}
```

```json
      "stock": {
        "type": "integer"
      },
      "status": {
        "type": "byte"
      },
      "createTime": {
        "type": "date",
```

#### 4.2.2 索引优化原则

| 优化项 | 建议 |
|--------|------|
| **分片数** | 单分片20~50GB；总分片数 = 节点数 × (1~2) |
| **副本数** | 生产环境至少1个副本；读写均衡场景2个 |
| **Refresh Interval** | 搜索场景 1-10s（默认1s对写入压力大） |
| **Translog** | 异步持久化（写入性能提升5倍） |
| **禁用Norms** | 不需要评分的字段禁用，节省内存 |
| **禁用Doc Values** | 不需要聚合排序的字段禁用 |
| **字段数量** | 单个索引不超过1000个字段 |

**ES消费程序**：

```java
@Component
public class ProductSyncConsumer {
    @Autowired
    private ElasticsearchRestTemplate esTemplate;

    @KafkaListener(topics = "es_product_topic", groupId = "es-sync-group")
    public void syncProduct(String message) {
        CanalMessage canalMsg = JSON.parseObject(message, CanalMessage.class);

        switch (canalMsg.getType()) {
            case "INSERT":
            case "UPDATE":
                Product product = JSON.parseObject(
                    canalMsg.getData().get(0).toString(), Product.class);
                esTemplate.save(product);
                break;
            case "DELETE":
                String productId = canalMsg.getData().get(0)
                    .getString("productId");
                esTemplate.delete(productId, Product.class);
                break;
        }
    }
}
```

#### Java RestClient代码

```java
@Service
public class ProductSearchService {
    @Autowired
    private ElasticsearchRestTemplate esTemplate;

    public SearchResponse<Product> searchProducts(
            String keyword, Long categoryId, Double priceMin,
            Double priceMax, int page, int size) {

        NativeSearchQueryBuilder queryBuilder = new NativeSearchQueryBuilder();
        BoolQueryBuilder boolQuery = QueryBuilders.boolQuery();

        // 全文检索
        if (StringUtils.hasText(keyword)) {
            boolQuery.must(QueryBuilders.matchQuery("productName", keyword));
        }

        // 类目过滤
        if (categoryId != null) {
            boolQuery.filter(QueryBuilders.termQuery("categoryId", categoryId));
        }

        // 价格范围过滤
        if (priceMin != null || priceMax != null) {
            RangeQueryBuilder range = QueryBuilders.rangeQuery("price");
            if (priceMin != null) range.gte(priceMin);
            if (priceMax != null) range.lte(priceMax);
            boolQuery.filter(range);
        }

        // 分页（from + size，避免深分页用search_after）
        queryBuilder.withQuery(boolQuery)
            .withPageable(PageRequest.of(page, size))
            .withSort(Sort.by("price").ascending());

        SearchHits<Product> hits = esTemplate.search(
            queryBuilder.build(), Product.class);
        return new SearchResponse<>(hits);
    }
}
```

**深分页问题**：

| 方案 | 原理 | 适用场景 |
|------|------|---------|
| `from + size` | 默认分页 | 前10000条 |
| `search_after` | 基于上一页最后一条的排序值 | 深度翻页（无跳页） |
| `scroll` | 快照游标 | 全量导出/批量处理 |
| `PIT (Point In Time)` | 7.x+ 替代Scroll | 稳定性更好的全量处理 |

### 5.2 Nginx（反向代理/负载均衡）

```nginx
# Nginx核心配置示例

upstream backend_servers {
    # 负载均衡策略
    # 默认: 轮询
    # ip_hash: 根据IP哈希（Session保持）
    # least_conn: 最小连接数
    # weight: 权重
    server 127.0.0.1:8080 weight=3;
    server 127.0.0.1:8081 weight=2;
    server 127.0.0.1:8082 weight=1 backup;  # 备用
}

server {
    listen 80;
    server_name api.example.com;

    # 动静分离
    location /api/ {
        proxy_pass http://backend_servers;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /static/ {
        root /var/www/html;
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # 限流
    location /api/order/ {
        limit_req zone=order_limit burst=20 nodelay;
        proxy_pass http://backend_servers;
    }
}

# 限流区域定义
limit_req_zone $binary_remote_addr zone=order_limit:10m rate=100r/s;
```
