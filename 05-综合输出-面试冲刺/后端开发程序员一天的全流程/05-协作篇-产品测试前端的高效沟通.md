## 1. 与产品经理的协作

> 后端开发不是执行者，而是技术参谋。需求评审时后端不发言，上线后就等着背锅

### 1.1 需求评审时后端应该关注什么

后端在需求评审阶段不能只被动接收信息，要从以下六大维度主动审视和分析：

**1. 技术可行性（Technical Feasibility）**

后端要评估当前系统架构是否能够支撑需求。关注点包括：

- 现有技术栈能否实现？是否需要引入新的中间件或框架？
- 依赖的外部系统是否具备对应能力？
- 需求中有没有隐含的技术债务积累？

**2. 边界条件（Edge Cases）**

需求文档通常只覆盖正常流程，后端要主动思考非正常场景：

- 数据为空时系统如何表现？
- 用户并发操作会出现什么情况？
- 极端输入（超大数据量、超长字符串、异常格式）如何处理？
- 上下游系统超时或不可用时如何降级？

**3. 性能影响（Performance Impact）**

每个需求上线后都会对系统产生性能影响，后端要提前预估：

- 新增接口的预估 QPS 是多少？对现有数据库的压力有多大？
- 是否需要引入缓存、异步队列、读写分离等优化策略？
- 数据量增长趋势如何？半年后还在这个设计下跑得动吗？

**4. 安全风险（Security Risk）**

后端是系统安全的第一道防线：

- 接口是否需要登录鉴权？权限粒度是否合理？
- 是否存在 SQL 注入、XSS、CSRF 等安全漏洞？
- 敏感数据（手机号、身份证、银行卡）是否脱敏处理？
- 是否存在越权漏洞（水平越权/垂直越权）？

**5. 扩展性（Extensibility）**

好的设计要为未来留余地：

- 这个需求未来可能的迭代方向有哪些？
- 当前的数据库设计和接口设计能否平滑扩展？
- 如果业务量增长 10 倍，当前方案还能支撑吗？

**6. 数据一致性（Data Consistency）**

涉及多步操作、多系统交互时一致性是核心关注点：

- 是否需要强事务保障（ACID）？还是可以接受最终一致性？
- 分布式场景下如何保证数据不丢失、不重复？
- 是否需要设计对账/补偿机制？

> 💡 **实战经验**：需求评审会上后端发言量应该占 30% 以上。如果你全程只说"好的""没问题"，说明你还没进入深度思考状态。第一次需求评审可以提前找产品拿到 PRD，先预审一遍再上会。

### 1.2 后端评审需求的标准 Checklist 表

需求评审前、评审中、评审后，建议使用以下标准 CheckList 逐项确认：

```markdown
## 后端需求评审 CheckList

### 业务理解
- [ ] 我是否完全理解了需求的业务背景和目标？
- [ ] 需求解决了用户的什么痛点？衡量指标是什么？
- [ ] 是否有参考竞品或同类功能的实现方式？

### 技术可行性
- [ ] 当前系统架构是否支持？是否需要架构变更？
- [ ] 是否存在技术难点或不确定的技术方案？
- [ ] 是否需要引入新的第三方依赖或中间件？

### 数据设计
- [ ] 是否需要新建或修改数据库表？
- [ ] 字段类型、长度、索引设计是否合理？
- [ ] 数据量预估是多少？未来 6 个月的增长趋势如何？
- [ ] 是否需要数据迁移？迁移方案是否已确认？

### 接口设计
- [ ] 需要新增/修改哪些接口？
- [ ] 接口的请求/响应格式是否与现有规范一致？
- [ ] 是否需要考虑接口版本管理（向下兼容）？

### 性能评估
- [ ] 接口预期的 QPS 和响应时间要求是多少？
- [ ] 是否需要缓存？缓存策略是怎样的？
- [ ] 是否需要异步处理或消息队列？
- [ ] 是否存在慢查询风险？SQL 执行计划是否已确认？

### 安全评估
- [ ] 接口是否存在未授权访问风险？
- [ ] 敏感数据是否已确认脱敏方案？
- [ ] 是否存在 SQL 注入、XSS 等安全风险？
- [ ] 第三方数据传输是否加密？

### 依赖管理
- [ ] 是否依赖其他团队或外部服务？
- [ ] 依赖服务是否已确认可接入？SLA 如何？
- [ ] 依赖服务不可用时的降级方案是什么？

### 可观测性
- [ ] 是否需要新增业务埋点/日志？
- [ ] 是否有关键指标的监控告警？
- [ ] 线上出问题时如何快速定位？

### 上线与回滚
- [ ] 上线方案是否已规划？灰度策略如何？
- [ ] 回滚方案是什么？回滚后数据是否一致？
```

> 🎯 **核心要点**：把这份 CheckList 打印出来贴在工位上，每次评审对着过一遍。三个月后你会发现，你已经能自动跳过那些不必要的检查项，只关注风险点——这就是经验。

### 1.3 如何优雅地拒绝不合理需求：用数据说话提供替代方案

后端经常遇到产品提出"技术上很难实现"或"实现成本极高"的需求。粗暴拒绝伤害合作关系，无原则接受伤害系统质量。正确的做法是**用数据说话，结构化呈现风险，并提供替代方案**。

**拒绝不合理需求的四步表达框架：**

```text
第一步：共情（承认需求价值）
"我理解这个需求是为了解决用户……的问题，确实很有价值。"

第二步：陈述约束（用数据/事实说话）
"但从技术角度来看，这个方案有几个挑战：
  1. 当前系统架构在 XX 方面不支持，改造需要 X 人天
  2. 上线后数据库 QPS 预计会达到 X，当前规格扛不住
  3. 依赖的 XX 系统目前没有这个能力，接入周期需要 X 周"

第三步：提供替代方案（至少 2 个选项）
"我建议几个替代方案供你评估：
  方案 A（推荐）：…… 优点是…… 缺点是……
  方案 B（可选）：…… 优点是…… 缺点是……"

第四步：把决策权交还给产品
"你评估一下哪个方案更符合当前的业务节奏？"
```

**效果对比：**

| 维度 | 坏的方式 | 好的方式 |
|------|---------|---------|
| 话术 | "做不了，技术上不行" | "我有几个方案，其中 A 方案成本最低且能达到 80% 的效果" |
| 数据支撑 | 无 | "改造需要 3 人天，数据库压力会增大 10 倍" |
| 态度 | 对立（你做不了我的需求） | 同盟（我们一起找到一个可行的方案） |
| 结果 | 产品投诉你态度差 | 产品觉得你专业、靠谱 |

**实战案例：**

```text
场景：产品要求在一个订单详情接口中，把用户过去 3 年的所有行为轨迹都返回。

错误回应：
"不行，数据量太大了，查不了。"
→ 产品内心：你就不能优化一下吗？

正确回应：
"这个需求我理解是为了让客服侧快速了解用户全貌。但有一个数据问题：
每个用户 3 年的行为轨迹平均有 5000 条记录，一次性查出来接口耗时
预计超过 10 秒，而且传输数据量很大。我建议两个方案：

方案 A：按类型和时间分段查询，默认只查最近 30 天，支持高级筛选。
  优点：性能好，接口响应 < 200ms
  缺点：需要二次查询才能查看更多

方案 B：走异步导出，生成 Excel/PDF 报告。
  优点：可以查看全部数据
  缺点：需要等待 1-2 分钟生成

你倾向哪个方案？"
```

> ⚠️ **重要提醒**：拒绝需求不是为了自己省事，而是为产品的长期健康负责。如果需求确实有价值，只是因为技术实现有难度被拒绝，产品一定不服。所以一定要给替代方案——让产品觉得"虽然没按我的想法来，但结果更好"。

### 1.4 需求不清晰时的 5W1H 提问框架

需求描述模糊是常态。与其"猜"着开发然后返工，不如用 5W1H 框架逐层澄清：

```text
5W1H 提问框架

What（做什么）
  问题："这个功能的最终交付物是什么？用户看到/操作的是什么？"
  示例："你说的'用户签到'，是指每天点一下获得积分，还是连续签到有额外奖励？"

Why（为什么做）
  问题："这个需求要解决的业务痛点是什么？我们怎么衡量它成功了？"
  示例："做签到功能的目的是拉升 DAU，还是提升用户的付费转化率？方向不同设计差异很大。"

Who（谁会用）
  问题："目标用户画像是什么？是 C 端普通用户、B 端运营人员、还是系统管理员？"
  示例："这个报表是给运营同学看，还是给老板看？展示方式和数据粒度不一样。"

When（什么时候用）
  问题："用户在什么时机/场景下触发这个功能？有没有时间要求？"
  示例："这个任务是在用户下单后立即触发，还是每天凌晨跑批处理？"

Where（在哪里展示）
  问题："功能部署在哪个端？App / 小程序 / H5 / PC 后台？"
  示例："需要同时支持 App 和 H5 吗？两个端的交互方式可能不同。"

How（怎么做）
  问题："用户的操作流程是怎样的？预期交互路径有多少步？"
  示例："用户从进入页面到完成签到，中间要经过几步？有没有弹窗环节？"
```

**5W1H 实战案例：**

```text
产品说："我想给用户加一个积分商城功能。"

用 5W1H 追问后，发现真实需求是：
  - 提升用户活跃度和留存（Why）
  - 用户可以浏览商品，用积分兑换（What）
  - 面向所有注册用户（Who）
  - 用户在小程序首页可以进入（Where）
  - 每天首次打开时推送消息提醒（When）
  - 需要对接仓储系统的库存接口来扣减库存（How 之依赖关系）

→ 一个"加个积分商城"的需求，经过 5W1H 澄清后变成了完整的系统设计：
  - 新增积分商品表、积分兑换记录表
  - 新增商品展示、兑换流程、库存扣减接口
  - 对接仓储系统库存接口
  - 设计每日推送提醒定时任务
  - 考虑积分过期策略和退换货场景
```

> 🎯 **核心要点**：5W1H 不是机械地提问，而是帮助你和产品一起把需求从"模糊概念"变成"可执行方案"。如果 5W1H 中有 3 个以上说不清楚，不要进入开发阶段——宁可在需求阶段多花 1 天，也不要在开发阶段返工 3 天。

### 1.5 对话示例：产品提技术上很难实现的需求，如何回应

**场景：** 产品要求在一个已上线 2 年的电商系统中，给所有订单接口加上"实时物流轨迹追踪"能力——用户打开订单详情就能看到快递小哥的实时位置。

```text
❌ 不专业的回应（水平差、态度差）：

后端：这个做不了。
产品：为什么？我看隔壁组某某系统就有这个功能。
后端：他们对接了快递鸟的付费 API，我们没买。
产品：那我们也买啊。
后端：买了也不一定能快速接上，物流数据格式不一样，要改造好久。
产品：那要多久？
后端：不一定，至少一个月吧。
产品：不能快点吗？
后端：快不了，就这么难。
→ 结果：产品投诉到技术总监那里，说后端不配合。


✅ 专业的回应（有数据、有方案、有选择）：

后端：我理解这个需求是为了提升用户的订单体验，尤其是在大促期间的物流焦虑问题。

首先我来评估一下：实现实时物流追踪，目前有两条技术路径——
  路径 A：对接快递鸟/菜鸟裹裹的物流轨迹 API，可以获取快递员的实时位置。
  路径 B：自建物流追踪系统，从各个快递公司拉数据。
  路径 A 相对成熟，我们重点看这个方案。

数据评估结果：
  - 快递鸟接入费用：约 X 万/年
  - 对接开发成本：后端 3 人天 + 前端 2 人天
  - 我们日均订单 5000 单，API 调用费用约 X 元/天
  - 全年总成本：约 X 万元

我的建议方案：
  方案 A（推荐）：先接入快递鸟的"物流轨迹查询"接口——只查节点轨迹
    （已揽收→运输中→派送中→已签收），不做实时位置展示。
    成本低，1 周上线。
  方案 B（进阶）：在方案 A 基础上，接入实时位置接口，展示快递员位置。
    需要快递鸟的高级版，费用翻倍，且需要客户端改造。
    预估周期：3 周。

建议第一阶段先做方案 A，上线后看用户反馈，如果确实有实时位置需求，
下个迭代再做方案 B。你看这样可以吗？

→ 结果：产品觉得你做事有条理，选了方案 A，第一周就上线了。
```

### 1.6 需求变更管理流程 + 影响评估模板

需求变更是软件开发中唯一不变的事。问题不在于"需求变了"，而在于"变了之后大家没对齐"。

**需求变更标准流程：**

```text
需求变更管理流程
═══════════════════════════════════════

触发变更
  └── 来源：产品/运营/客户反馈/技术自发现

Step 1: 记录变更请求
  ├── 谁提出的？什么时候？变更内容是什么？
  ├── 变更原因（需求变了 / 之前没想清楚 / 市场变化 / 技术约束）
  └── 记录到项目管理工具（Jira/Trello/飞书）

Step 2: 影响评估（后端执行）
  ├── 技术影响分析：改代码、改表、改接口的范围
  ├── 工时影响：增加多少開発工时？是否影响当前迭代截止时间？
  ├── 质量风险：改动的测试回归范围有多大？
  └── 兼容性影响：是否影响已上线功能？旧数据怎么处理？

Step 3: 同步与决策
  ├── 把影响评估结果同步给产品
  ├── 产品决定：变更是否纳入当前迭代
  └── 如果纳入：替换哪些低优先级需求？还是延期？

Step 4: 执行变更
  ├── 更新接口文档、测试用例
  ├── 开发、自测
  └── 同步变更到所有相关方

Step 5: 验收与复盘
  ├── 测试验证变更后的功能
  └── 复盘：为什么需求会变？下次如何提前规避？
```

**需求变更影响评估模板：**

```markdown
## 需求变更影响评估表

**变更编号：** CHG-2026-0728-001
**提出人：** [姓名]（产品/运营/技术）
**提出日期：** 2026-07-28
**关联需求：** [REQ-XXXXX]

### 一、变更描述
（简明扼要地描述变更内容）

原需求：订单列表按"下单时间"降序排列
变更为：订单列表按"支付时间"降序排列，未支付订单排在最后

### 二、变更原因
（为什么变？是业务策略调整还是之前没考虑到？）

运营策略调整，希望优先展示已支付订单，提高复购转化

### 三、技术影响分析

| 评估维度 | 详细说明 | 影响程度 |
|---------|---------|:-------:|
| 数据库 | 不需要改表结构，只需修改 SQL 排序条件 | 低 |
| 接口 | 订单列表接口排序逻辑修改，接口入参不变 | 中 |
| 前端 | 后端排序改了，前端不需改动 | 无 |
| 缓存 | 缓存 key 不变，需清除旧缓存 | 低 |
| 测试范围 | 需回归订单列表功能，重点关注排序 | 中 |
| 兼容性 | 兼容旧版本客户端（新增排序参数） | 无 |

### 四、工时估算

| 角色 | 工时 | 说明 |
|------|:---:|------|
| 后端 | 0.5 人天 | SQL 排序逻辑修改 + 测试 |
| 前端 | 0 人天 | 接口兼容，无需修改 |
| 测试 | 0.5 人天 | 回归排序功能 |
| 总工时 | 1 人天 | |

### 五、风险评估
- 风险 1：涉及订单列表核心功能，需充分回归
- 风险 2：缓存清除时序要精确，避免脏数据

### 六、决策

□ 纳入当前迭代（替换低优先级需求：________）
□ 纳入当前迭代（延期 1 天）
□ 排入下个迭代
□ 拒绝变更（理由：________________）

**决策人：** [产品经理签字] **日期：** ________
```

> ⚠️ **铁律**：永远不要接受口头需求变更。只要没写在文档里、没在 IM 上有留痕的变更，出问题后说不清楚责任。哪怕是个很小的字段修改，也要在群里说一句"我确认一下，这个字段从 A 改成 B，对吧？"——给自己留个保命符。

## 2. 与测试/QA 的协作

> 测试是你代码质量的守门人。和测试搞好关系，Bug 变少、发版安心、线上事故减少。提测质量的高低直接决定了你在团队中的靠谱印象

### 2.1 提测前自测 CheckList（正常流程/异常流程/边界值/并发/性能）

提测之前不自测，是后端开发的大忌。"我代码没问题，直接测吧"这种话一经说出，测试测出第一个 Bug 时你的信用就开始透支了。

```markdown
## 提测前自测 CheckList

### 一、正常流程（Happy Path）
- [ ] 主流程完整走通：从前端请求到数据库落盘，全链路无报错
- [ ] 成功时返回正确的 HTTP 状态码（200/201/204）
- [ ] 返回数据结构符合接口文档（字段名、类型、层级）
- [ ] 各可选参数组合都能正常返回预期结果
- [ ] 业务状态流转正确（如待支付→已支付→已发货→已完成）

### 二、异常流程（Sad Path）
- [ ] 必填参数缺失时返回正确的错误码和提示
- [ ] 参数类型错误（String 传成了 Integer）时友好提示
- [ ] 业务逻辑校验（重复提交、余额不足、状态冲突、库存不足）
- [ ] 依赖服务超时/不可用时有降级处理（不抛 500）
- [ ] 鉴权失败（未登录/Token过期/无权限）返回 401 或 403
- [ ] 操作不存在的数据（ID 不存在）返回 404

### 三、边界值（Boundary Value）
- [ ] 分页参数：page=0、page=1、page=-1、page=99999
- [ ] 分页参数：size=0、size=1、size=10000
- [ ] 字符串长度：空串""、超长（超过 DB 字段长度）、特殊字符、emoji
- [ ] 数值范围：最小值、最大值、负数、0、小数（精度问题）
- [ ] 时间范围：跨年、闰年 2/29、时区差异、夏令时、null
- [ ] 枚举值：不存在的枚举值、大小写敏感问题
- [ ] 数组/列表：空数组[]、单条记录、最大允许条数

### 四、并发场景（Concurrency）
- [ ] 同一用户重复提交相同请求（幂等性验证）
- [ ] 高并发扣减库存/余额（超卖、重复扣款）
- [ ] 数据库锁超时/死锁（是否设置合理的超时时间）
- [ ] 并发创建同名资源（唯一约束 vs 应用层校验）

### 五、性能（Performance）
- [ ] 接口响应时间在合理范围内（P99 < 500ms）
- [ ] 数据库查询无全表扫描（EXPLAIN 确认走了索引）
- [ ] 大数据量（如 10 万条）分页查询性能正常
- [ ] N+1 查询问题已排查（尤其是 MyBatis 关联查询）

### 六、安全（Security）
- [ ] 越权访问测试（A 用户能否通过修改 ID 访问 B 用户的数据）
- [ ] SQL 注入测试（字段传 ' OR 1=1 -- 等）
- [ ] 敏感字段脱敏（手机号、身份证、银行卡）
- [ ] 请求频率限制（敏感接口是否限流）
```

> 💡 **自测技巧**：不要只在"干净"的数据库上自测。在测试环境里构造一些"脏数据"（残缺数据、异常状态数据、超大文本数据），看看接口能不能正确处理。很多线上 Bug 就是死在"数据不干净"上。

### 2.3 Bug 单标准格式（标题/复现步骤/期望结果/实际结果/环境信息）

- 该订单未申请过退款
- 测试环境已部署 v2.3.0 版本

### 复现步骤
1. 登录用户 A（userId=12345）
2. 调用 POST /api/v1/orders/10086/refund

### 实际结果
- 订单 `refundStatus` 仍为 "REFUNDING"

- Kibana 日志链接：http://kibana.company.com/app/kibana#/xxx

### 2.4 测试提 Bug 后响应流程：复现 → 确认 → 排优先级 → 修复 → 验证

```text
测试提 Bug → 后端响应流程
═══════════════════════════════════════

Step 1: 确认收到（≤ 30 分钟）
  ├── 回复测试："收到，我先复现一下。"
  └── 让测试知道你没有无视他的 Bug，这是基本尊重

Step 2: 复现与确认（≤ 2 小时）
  ├── 如果能复现
  │   ├── 确认问题确实存在 → 标记为 "已确认"
  │   └── 进入 Step 3
  └── 如果不能复现
      ├── 联系测试确认：环境、数据、操作步骤的差异
      ├── 让测试提供更详细的日志/录屏
      └── 如果仍然无法复现 → 标记为 "CNR（Cannot Reproduce）"

Step 3: 定位根因
  ├── 看代码 → 看日志 → 看数据 → 确定问题代码位置
  ├── 评估影响范围（影响哪些场景？影响多少用户？）
  └── 评估修复风险（改动的会不会引入新 Bug）

Step 4: 排定优先级
  ├── P0：立即放下手头工作，优先修复
  ├── P1：当前任务完成后立即修复
  ├── P2：在当前迭代内修复
  └── P3：排入下个迭代

Step 5: 修复与自测
  ├── 修复代码并编写单元测试
  ├── 自测通过（正常流程 + 修复验证 + 回归测试受影响场景）
  └── 提交代码 + 在 Bug 单备注"已修复，等待验证" + 附修复说明

Step 6: 测试回归验证
  ├── 测试按原复现步骤验证
  ├── 验证通过 → 关闭 Bug 单
  └── 验证不通过 → Reopened → 回到 Step 3

Step 7: 复盘（可选）
  ├── 这个 Bug 是怎么产生的？代码审查漏了？
  ├── 是否能通过自动化测试提前发现？
  └── 是否需要在团队内同步经验？
```

**CNR（Cannot Reproduce）处理指南：**

```text
当你说"我这边复现不了"时，不要停留在这一句。试试这些：

1. 环境比对
   测试用的数据库和你的一样吗？数据量级一样吗？
   测试的配置中心开关和你的一样吗？

2. 日志深挖

3. 代码审计
   仔细读代码，看是否有"概率性触发"的逻辑
   如并发条件竞争、定时任务执行间隙、缓存过期瞬间

4. 数据克隆
   让测试把引发 Bug 的那条数据导出来给你
   在你的环境里复现那条数据的精确状态

5. 如果仍然无法复现
   在 Bug 单记录排查过程和结论
   挂起 Bug，等线上出现时再追踪（记录观察日志）
```

### 2.5 Bug 冲突处理对话示例：测试说是 Bug，后端说是 Feature

**场景：** 用户下单后立即查询订单列表，订单状态显示为"待支付"，但实际用户已经在支付页完成了支付流程。测试提交了 Bug："支付成功后订单状态未更新"。

后端经过分析后发现：支付流程走了异步回调机制，支付成功后 MQ 消息存在 1-3 秒的延迟，订单状态的更新需要等回调消息被消费。用户支付完成后立即刷新订单列表，此时消息尚未到达。

```text
❌ 不专业的处理方式：

测试：支付完成后订单状态没变，还是"待支付"，这个 Bug 你修一下。
后端：这个不是 Bug，支付是异步回调的，要等 MQ 消息过来才会更新状态。
测试：那用户付完款再看到"待支付"，用户体验很差啊，这不是 Bug？
后端：那是前端的问题，没有轮询。后端逻辑没问题。
测试：那用户不管，他就看到页面不对。
后端：行吧我看看……（不情不愿）

→ 结果：双方都不开心，问题没解决，用户体验依然差。


✅ 专业的处理方式：

测试：支付完成后订单状态没变，还是"待支付"，我提了个 P1 Bug。
后端：收到，我来排查一下。

（后端排查后）

后端：我分析了，这个问题的根因是这样的：
我们的支付流程是：

用户支付 → 支付网关回调 → 发 MQ 消息 → 订单服务消费 → 更新状态

MQ 从回调到消费更新有 1-3 秒的延迟。
所以用户支付完成后过快刷新页面时，状态还没更新。

这是个架构设计上的取舍——为了系统的解耦和稳定性，
我们选择了异步回调而不是同步阻塞。

不过你说的问题确实存在：用户感知不好。
我建议几个方案：

方案 A（短期，2 人天）：后端提供一个"等待支付结果"的长轮询接口。
前端在用户支付完成后调用这个接口，最长等 5 秒，
如果状态更新了就立即返回，超时再返回当前状态。

方案 B（中期，5 人天）：接入 WebSocket，支付成功后主动推送给前端。

方案 C（同步支付）：改为同步支付，等回调回来才返回成功。
但这样用户体验反而更差（要等 3-5 秒），而且支付网关抖动会影响整个下单流程。

你觉得方案 A 可以接受吗？我排到下个迭代开发，这个迭代先加一行提示文案：
"支付结果可能会有延迟，请稍后查看订单状态。"

测试：方案 A 可以，先把提示文案加上，下个迭代做长轮询。
后端：好的，这个 Bug 我确认是预期行为，但确实影响体验，我按优化项处理，
提测单里标注一下。

→ 结果：后端解释了技术原理，给了短期+中期方案，测试理解了也得到结果。
```

> 🎯 **核心要点**：Bug 与 Feature 之争的本质，不是"谁对谁错"，而是"用户感知到的体验是否够好"。从这个角度出发，后端和测试会从对立走向协作。

## 3. 与前端的协作

> 前后端分离的架构下，接口就是你们的契约。接口定义得越清晰，联调阶段的摩擦就越少

### 3.1 接口设计阶段：前后端联合定义 API

最佳实践：**接口定义先于代码开发**。在写第一行业务代码之前，前后端先联合输出接口文档。

#### RESTful 规范

```text
标准 RESTful 接口设计
═══════════════════════════════════════

查询列表：
  GET    /api/v1/resources                 → 参数放 Query String
  GET    /api/v1/resources?page=1&size=20  → 支持分页

查询单条：
  GET    /api/v1/resources/{id}            → 路径参数

创建：
  POST   /api/v1/resources                 → 参数放 Request Body
  Response: 201 + 创建的资源

全量更新：
  PUT    /api/v1/resources/{id}            → 传完整资源对象

部分更新：
  PATCH  /api/v1/resources/{id}            → 只传要更新的字段

删除：
  DELETE /api/v1/resources/{id}            → Response: 204
```

#### 字段命名规范

```json
// ✅ 统一小驼峰（camelCase）—— 前后端通用标准
{
  "userId": 10086,
  "nickName": "Alice",
  "avatarUrl": "https://cdn.xxx.com/avatar/10086.png",
  "createdAt": "2026-07-28T10:00:00Z",
  "orderList": []
}

// ❌ 混用命名风格——前端解析时还要做字段映射
{
  "user_id": 10086,
  "nick_name": "Alice",
  "avatar_url": "https://cdn.xxx.com/avatar/10086.png",
  "created_at": "2026-07-28T10:00:00Z",
  "order_list": []
}
```

> 💡 **Spring Boot 配置**：如果数据库字段是下划线命名（snake_case），后端可以用 `spring.jackson.property-naming-strategy = SNAKE_CASE` 或 MyBatis-Plus 的自动驼峰映射来做转换。业务代码中统一使用 camelCase，数据库字段用 snake_case。

#### 统一错误码设计

```json
{
  "code": 10001,
  "message": "用户不存在",
  "data": null,
  "requestId": "req-abc-123-def",
  "path": "/api/v1/users/999",
  "timestamp": 1690527600000
}
```

| 错误码范围 | 含义 | 示例 |
|-----------|------|------|
| 0 | 成功 | `{"code": 0, "message": "success"}` |
| 10000-10099 | 通用参数错误 | 10001 参数校验失败、10002 请求过于频繁 |
| 10100-10199 | 鉴权错误 | 10101 未登录、10102 Token 过期、10103 无权限 |
| 20000-29999 | 业务错误 | 20001 订单不存在、20002 余额不足、20003 订单状态冲突 |
| 30000-39999 | 系统错误 | 30001 数据库异常、30002 第三方服务超时、30003 内部错误 |

> 🎯 **核心要点**：前后端约定好统一的错误码体系后，前端可以根据 code 做统一的全局拦截器（如 10101 跳转登录页），而不用在每一个请求里硬编码错误提示。**前端只关心 code，不解析 message 文案中的业务逻辑。**

### 3.2 接口文档评审 CheckList（前端视角）

后端写完接口文档后，从前端的视角进行评审——因为接口文档最终是给前端用的。

```markdown
## 接口文档评审 CheckList（前端视角）

### 一、路径与命名
- [ ] 接口路径是否遵循 RESTful 规范？
- [ ] 路径中的参数是 Path Variable 还是 Query Param？是否合理？
- [ ] 接口版本号是否在路径中？(/api/v1/...)

### 二、请求参数
- [ ] 必填参数和可选参数是否有明确标识？
- [ ] 参数类型是否明确（String/Number/Boolean/Array/Object）？
- [ ] 数组参数是否可以传多值？格式是什么？
- [ ] 文件上传接口的 Content-Type 是否明确（multipart/form-data）？

### 三、响应格式
- [ ] 响应数据结构是否扁平化？避免多层嵌套增加前端取值复杂度
- [ ] 分页接口的响应格式是否统一？
- [ ] 数组字段始终是数组吗？（不要单条返回对象，多条返回数组）
- [ ] 时间格式是否统一？（建议 ISO 8601：yyyy-MM-dd'T'HH:mm:ss'Z'）
- [ ] 空值处理是否明确？（null / "" / [] 的约定）

### 四、错误处理
- [ ] 所有错误场景是否有对应的错误码？
- [ ] 错误信息是否包含前端可以直接展示的文案？
- [ ] 是否需要前端对错误码做特殊处理（如 401 跳登录）？

### 五、兼容性
- [ ] 新增字段是否会破坏现有前端的解析？(加字段不破坏，删字段破坏)
- [ ] 修改已有字段时是否有版本隔离？
- [ ] 旧版本客户端是否需要兼容？

### 六、性能与安全
- [ ] 接口是否有频率限制？超过限制后的响应格式是什么？
- [ ] 是否需要前端加密传输敏感信息？
- [ ] 响应数据量有多大？是否需要分页或懒加载？
```

> 💡 **实践建议**：写完接口文档后，直接发给前端同事说："帮我 Review 一下这个接口设计，看有没有前端不好处理的地方。"前端帮你审出问题，比联调时发现问题再改成本低 10 倍。

### 3.3 联调前后端各自责任表

联调阶段最容易出现扯皮问题："这个不是我的问题，是你的问题。"明确的责任划分可以减少 80% 的联调矛盾。

| 阶段 | 前端责任 | 后端责任 |
|------|---------|---------|
| **设计阶段** | 参与接口评审，确认接口满足前端需求 | 编写接口文档，提供 Mock 数据 |
| **开发阶段** | 基于 Mock 数据开发页面，不阻塞 | 开发接口，保持与文档一致 |
| **联调准备** | 确保开发环境可连通后端 | 确保测试/开发环境稳定，已部署最新代码 |
| **联调执行** | 发起请求，验证前端页面与后端接口的集成 | 修复联调中发现的接口问题 |
| **联调自测** | 覆盖所有前端页面的接口调用场景 | 覆盖所有接口的异常流程和边界值 |
| **问题定位** | 提供请求报文和浏览器 Network 截图 | 查看服务端日志，定位问题根因 |
| **问题修复** | 修复前端调用逻辑错误 | 修复后端接口返回错误 |
| **性能优化** | 控制请求数量（避免重复请求）、合理使用缓存 | 优化接口响应时间、SQL 查询、缓存策略 |
| **安全** | 前端参数校验（用户体验） | 后端参数校验（安全防线，前端绕过后端也能拦住） |
| **上线** | 前端资源发布 CDN | 后端服务发布，确保兼容性 |

**联调时的黄金原则：**

```text
遇到联调问题时，不指责，先排查。

1. 看请求：前端发送的参数对不对？
   → 打开浏览器 Network 面板，看 Request Payload
   → 如果参数不对 → 前端问题

2. 看响应：后端返回的数据对不对？
   → 看 Response Body 里的字段和接口文档是否一致
   → 如果数据不对 → 后端问题

3. 看日志：后端有没有报错？
   → 去 Kibana/Dashboard 查全链路日志
   → 如果有异常 → 后端问题

4. 如果是接口定义模糊导致的理解分歧
   → 双方确认后更新接口文档
   → 不要争论"我当时说的意思是这个"——以文档为准
```

### 3.4 常见前后端矛盾及解决

| 矛盾 | 后端常见说法 | 前端常见说法 | 解决方案 |
|------|------------|------------|---------|
| **字段类型不一致** | "我返回 long 类型没问题啊" | "JS 里长数字精度丢失，后几位全变 0 了" | 超过 `2^53-1`(9007199254740991) 的长整数用 String 返回。Java 用 `@JsonSerialize(using = ToStringSerializer.class)` 或全局配置 `Long` → `String` 序列化 |
| **分页格式不统一** | "page 从 0 开始有啥问题？" | "Element-UI 的表格组件 page 从 1 开始" | 团队统一：page 从 1 开始，或者后端兼容前端传入 0（自动转 1）。响应格式统一为 `{ page, size, total, totalPages, data }` |
| **时间格式不统一** | "时间戳多通用，前端自己转" | "每次都要 new Date(timestamp) 转，不同接口格式还不一样" | 统一使用 UTC 时间 `yyyy-MM-dd'T'HH:mm:ss'Z'`，前端在展示层根据用户时区做本地化。Java 配置：`spring.jackson.date-format=yyyy-MM-dd'T'HH:mm:ss'Z'` + `spring.jackson.time-zone=UTC` |
| **空值处理：null vs ""** | "null 表示没有值，语义明确" | "我取 user.name 直接报 Cannot read property of null" | 统一约定：String 类型空值返回 `null`（不返回 `""`），前端统一用 `?.` 可选链或 `?? ''` 兜底。对象类型空值返回 `null`，不返回该字段（可选）。数组类型空值返回 `[]`，不收返回 `null` |
| **错误提示太笼统** | "前端看 code 判断就好" | "用户要看中文提示，我难道每个 code 都要维护一套文案？" | 后端直接返回前端可以展示的 `message` 字段。**后端最清楚错误原因，不要把这个责任推给前端去猜** |
| **接口粒度问题** | "一个接口返回所有数据，省事" | "我要分步渲染，你给我一堆我用不到的数据，浪费性能" | 根据前端实际渲染需求设计接口粒度。可以同时保留"聚合接口"和"细分接口" |
| **冗余字段 vs 精确数据** | "前端自己算一下不就行了" | "后端多给一个字段我省很多事" | 适当冗余可以。如果数据量很小、计算逻辑不复杂（如总计），后端直接返回可以省去前端很多麻烦 |

**时间格式争议的终结方案：**

```text
团队规范：所有时间字段统一按 ISO 8601 格式返回
示例：2026-07-28T14:30:00Z

后端（Java）配置：
  spring.jackson.date-format = yyyy-MM-dd'T'HH:mm:ss'Z'
  spring.jackson.time-zone = UTC
  spring.jackson.serialization.write-dates-as-timestamps = false

前端（JavaScript）处理：
  const date = new Date('2026-07-28T14:30:00Z');
  // 展示时根据用户本地时区格式化
  date.toLocaleString('zh-CN', { timeZone: 'Asia/Shanghai' });
  // → "2026/7/28 22:30:00"

原理：
  服务端存储和传输统一用 UTC → 前端根据用户本地时区展示
  → 全球用户看到的时间都是自己的当地时间
```

### 3.5 对话示例：前端反馈接口慢，如何协作排查

**场景：** 前端反馈说用户收藏列表接口加载需要 8 秒，严重影响用户体验，要求后端优化。

```text
❌ 不专业的回应（推卸责任、拒绝协作）：

前端：收藏列表接口好慢啊，加载要 8 秒！
后端：我本地测了才 200ms，不是我们接口的问题。
前端：但 Network 里确实显示 8 秒。
后端：那可能是你网络不好吧，或者你电脑的问题。
前端：……（无语）

→ 结果：问题悬而未决，前端不开心，后端被鄙视。


✅ 专业的回应（协作排查、数据驱动）：

前端：收藏列表接口好慢，Chrome Network 显示接口加载用了 8 秒。
用户反馈列表页面经常白屏，影响体验。

后端：收到，我来查一下。你把请求的 Request ID 发我，
再看 Network 里接口的"Waiting (TTFB)"和"Content Download"
分别是多少？

（后端开始排查——第一步：确认是后端慢还是网络慢）

后端：我查了 ELK 日志，这个接口的服务端处理时间（P99）是 200ms，
很正常。你说的 8 秒和我这边的数据对不上。
你的 TTFB 是 7.5 秒 + Content Download 0.5 秒？
还是 TTFB 200ms + Download 7.8 秒？

前端：TTFB 7.5 秒，Download 0.5 秒。

后端：那说明服务端收到请求后处理很快（200ms），
但问题出在"前端到服务端"的网络链路上——TTFB 包括了网络传输时间。
我查了你的请求来源 IP，是测试环境（AWS 新加坡）。
你现在在国内，跨国请求延迟大。

前端：那能不能解决？

后端：有几个方案——

方案 A（立即见效）：用公司的 VPN 连到新加坡的专线，延迟能降到 200ms。
方案 B（开发环境优化）：在国内搭建一个预发布环境，测试阶段用国内服务器。
方案 C（线上方案）：上线后用户访问的是国内服务器，这个问题在线上应该不存在。

另外我还排查到一个问题：接口返回的 JSON 有 500KB，
主要是用户头像用了 base64 格式。如果改成 CDN URL 格式，
能降到 5KB 左右。这个我下个迭代优化。

你现在先试方案 A？看看效果？

前端：好，我切 VPN 试试。头像那个优化也留意一下，那个确实太占带宽了。
后端：没问题，我记录到技术债务里。

→ 结果：问题定位清晰，前端知道了根因是网络而非后端代码，
且后端主动提出了后续优化方案。
```

> 🎯 **核心要点**：排查问题要基于数据，不要猜测。**前端提供 Network 截图 + 后端查全链路日志**，两者结合才能准确定位问题。推卸责任是最愚蠢的做法——问题不解决，最终用户骂的是产品，产品骂的是整个技术团队。

## 4. 与技术负责人/Tech Lead 的协作

> Tech Lead 是你的技术导师和绩效评估者。和他协作的质量，直接影响你的成长速度和职业发展

### 4.1 如何汇报风险：不要只说问题，带解决方案

Tech Lead 的时间非常宝贵。向他汇报风险时，最关键的原则是：**不要只带问题，要带方案**。

**坏汇报 vs 好汇报：**

```text
❌ 坏的汇报（Tech Lead 听完想打人）：

"老大，订单导出功能可能要延期。"
"为什么？"
"那个大数据量导出超时了。"
"那怎么办？"
"我也不知道……"

→ Tech Lead 心里：所以你来告诉我这个有什么用？我还要帮你擦屁股。


✅ 好的汇报（STAR 汇报框架）：

"老大，关于订单导出功能，我有个风险需要同步一下。

Situation（背景）：订单导出功能需要在 10 万数据量下正常导出 Excel。
但测试时发现超过 5 万条就超时了。

Task（任务）：需要在本周五前解决这个问题，否则影响上线时间。

Action（我做了什么 & 建议方案）：
  我排查了根因是 POI 在内存中生成 Excel 时 OOM。
  我考虑了几个方案：
  方案 A：加内存 -Xmx 从 512m 提升到 2g（改动最小，治标不治本）
  方案 B：分批导出，后端分页查询 + 流式写入 Excel（SXSSFWorkbook）
           → 内存占用降到 50MB，推荐
  方案 C：改成异步导出，先生成文件再推送下载链接
           → 用户体验最好，但需要前端配合

Result（建议）：
  我倾向方案 B，今天下班前能改完。你看这个方向可以吗？
  如果没问题，我改完后明天上午给你 Review 代码。"

→ Tech Lead 心里：这家伙靠谱，方案想好了，只需要我确认方向和排期。
```

**STAR 汇报公式速记：**

```text
S（Situation）— 背景：什么事？什么影响？
T（Task）— 任务：需要什么时候解决？标准是什么？
A（Action）— 行动：你做了什么？建议什么方案（2-3个）？
R（Result/Recommendation）— 建议：你倾向哪个方案？需要他做什么？
```

### 4.2 技术方案评审的准备要点

技术方案评审是后端展示技术深度的关键时刻。做得好，Tech Lead 会觉得你靠谱，愿意给你更有挑战的工作。

**技术方案评审准备清单：**

```
□ 是否有 2 个以上的方案对比？（不要只带一个方案，那说明你没思考过其他可能）
□ 是否有明确的技术选型理由？（为什么选 A 不选 B，要有量化对比）
□ 是否分析了影响面？（涉及哪些模块、哪些团队、哪些服务）
□ 数据一致性方案是否清晰？（强一致？最终一致？补偿机制？）
□ 是否有考虑容错和降级？（依赖挂了怎么办？）
□ 是否评估了性能？（预估 QPS、RT、DB 连接数、缓存命中率）
□ 是否有灰度方案？（上线后如何逐步放量？）
□ 是否有回滚方案？（出问题如何快速回退？数据怎么恢复？）
□ 是否有可观测性设计？（日志、监控指标、告警规则）
□ 是否有排期和任务拆分？（不要只说"2 周"，要拆到天）
```

**技术方案文档模板：**

```markdown
# 技术方案：订单退款功能重构

## 1. 背景与目标
（为什么要做这次重构？解决什么问题？核心衡量指标是什么？）

- 当前退款流程不支持部分退款
- 退款处理超时率 5%，超过 SLO 标准
- 目标：支持部分退款 + 退款超时率降到 < 1%

## 2. 方案对比

| 维度 | 方案 A：优化现有流程 | 方案 B：引入异步退款 + MQ（推荐） |
|------|:-----------------:|:-------------------------------:|
| 实现复杂度 | 低 | 中 |
| 开发成本 | 2 人天 | 5 人天 |
| 扩展性 | 差，下次改还要大改 | 好，支持后续多渠道退款 |
| 一致性保证 | 强一致 | 最终一致（有补偿机制） |
| 用户体验 | 同步等待 3-5s | 异步通知，体验流畅 |
| 风险 | 改造范围大，影响现有逻辑 | 引入 MQ 增加运维复杂度 |

**推荐方案：** 方案 B，虽然开发成本高，但扩展性和用户体验更好。

## 3. 推荐方案详细设计

### 3.1 系统架构
（参与的系统、服务、MQ 拓扑）

### 3.2 数据库设计
（新增表、索引、数据量预估）

### 3.3 接口定义
（新增/修改接口列表）

### 3.4 关键流程
- 正常流程：申请退款 → 校验 → 发 MQ → 消费 → 回调 → 更新状态
- 异常流程：校验失败 → 返回错误码
- 补偿流程：回调超时 → 定时任务扫描 → 补偿重试（最多 3次）

### 3.5 一致性与幂等
- 幂等方案：refund_no 全局唯一，重复请求幂等处理
- 对账方案：每日凌晨对账脚本，标记不一致的退款单

## 4. 排期

| 阶段 | 时间 | 产出 |
|------|:----:|------|
| 数据库设计 | Day 1 | 建表 SQL、索引设计 |
| 核心接口开发 | Day 2-3 | 退款接口、查询接口 |
| 异步回调 + MQ | Day 3-4 | 消息消费者、回调处理 |
| 补偿机制 | Day 4 | 定时任务、对账脚本 |
| 自测 + 联调 | Day 5 | 测试用例、联调通过 |

## 5. 风险与应对

| 风险 | 概率 | 影响 | 应对方案 |
|------|:---:|:----:|---------|
| MQ 消息丢失 | 低 | 高 | 本地消息表 + 定时补偿 |
| 重复退款 | 中 | 高 | 幂等校验 + 乐观锁 |
| 第三方支付接口超时 | 中 | 中 | 设置超时时间 + 熔断 |
```

> 🎯 **核心要点**：技术方案评审不是为了走过场，而是为了让更多有经验的人帮你发现盲区。写方案时如果你觉得"这里可能有问题"，那多半真的有问题——标出来，在评审会上主动提。

### 4.3 如何争取做更有挑战的工作（话术模板）

Tech Lead 手上有很多工作：简单的 CRUD 业务开发，复杂的系统架构设计，没人愿意碰的历史遗留系统重构。他会把高价值的工作分配给谁？**分配给"靠谱的人"**。

**争取高价值工作的策略 + 话术：**

```text
策略一：把手头的事做到超出预期

→ 话术：
"我手头的退款功能已开发完成，我还把相关的压测报告和
异常场景测试用例写好了。接下来有没有其他可以帮忙的？"

关键点：先把当前任务完成得无可挑剔，这是争取下个高价值任务的基础。

---

策略二：主动表达兴趣，提供"试稿"

→ 话术：
"我看群里在讨论订单分库分表的方案，我对这块很感兴趣。
我之前研究过 ShardingSphere，也做过一些 Demo。
这个方案我可以先写一个初稿，你看完后觉得方向没问题我再深入做，
你看可以吗？"

关键点：不要直接说"我想做分库分表"，而是说"我可以先写方案给你看"。
先拿出产出再谈机会。

---

策略三：解决 Tech Lead 的痛点

→ 话术：
"老大，我最近发现我们支付模块的重试机制有个隐患——如果 MQ 挂了，
重试消息会丢。我周末调研了本地消息表的方案，可以彻底解决这个问题。
我整理了一个简版方案，你能帮我把把关吗？"

关键点：主动发现团队的技术债务，且已经调研好了方案。
Tech Lead 喜欢能替他分忧的人。

---

策略四：在绩效沟通中明确成长方向

→ 话术：
"老大，下个季度我希望能承担更多中台设计的工作。
我目前的规划是先把订单模块的稳定性做到 P99.99，
然后逐步参与交易中台的设计。
你觉得我目前还需要补什么能力才能达到这个目标？"

关键点：不是在跟 Tech Lead 要东西，而是在请求指导。
Tech Lead 很愿意指导一个有明确成长方向的后端同学。
```

> 💡 **一个现实的观察**：Tech Lead 分配任务时的心态是——"这个任务交给他，我能不能放心？"如果你频繁出低级 Bug、需要别人擦屁股、遇到问题不主动汇报，那你永远只能做边缘模块。**信任是一点一点积累的，但一次不靠谱就可能前功尽弃。**

## 5. 跨团队协作

> 在大公司的后端开发中，30% 以上的工作时间用于跨团队协作。对接其他团队是你的核心能力之一

### 5.1 依赖其他团队接口时的标准流程

```text
依赖其他团队接口的标准流程
═══════════════════════════════════════

Phase 1: 需求确认（开发前 2 周）
  □ 明确需要依赖哪个团队、哪个接口、什么数据
  □ 找到对方团队的接口负责人（不是随便找一个人）
  □ 确认接口是否存在
  □ 如果不存在 → 与对方团队协商排期

Phase 2: 接口对齐（开发前 1 周）
  □ 双方对齐接口定义：
    - 请求参数（必填/可选、类型、长度、格式）
    - 响应格式（字段名、类型、嵌套结构）
    - 错误码（对方返回的错误码含义）
  □ 确认 SLA：
    - 可用性（Service Level Agreement）：≥ 99.9%
    - 响应时间：P99 < 200ms
    - 吞吐量：QPS 上限是多少？
  □ 约定联调时间：
    - Mock 接口什么时候可用？
    - 联调窗口是什么时候？
    - 紧急情况下的联系方式是什么？

Phase 3: 降级方案设计（开发前完成）
  □ 对方不可用时的兜底方案
  □ 对方超时时的处理策略（超时时间、重试次数、熔断阈值）
  □ 对方返回异常数据时的处理逻辑
  □ 功能是否可降级？（有对方没对方都能用？还是说对方挂了功能就不可用？）

Phase 4: 开发与联调
  □ 并行开发：后端用 Mock 数据开发，不依赖对方真实接口
  □ 联调验证：两端环境连通，验证业务场景
  □ 联调问题处理：记录问题、逐条解决、更新文档

Phase 5: 上线与监控
  □ 双方同步上线计划（谁先上？谁后上？是否需要同时发布？）
  □ 配置告警规则（接口调用失败率、响应时间监控）
  □ 灰度发布，观察线上指标
  □ 确认稳定后关闭功能开关
```

### 5.2 遇到依赖方延期怎么办（5 种策略）

依赖方延期是跨团队协作中最常见也最头疼的问题。应对策略按优先级排列：

```text
策略一：主动推进对方（首选）
  → 亲自去对方工位/飞书沟通，了解真实卡点
  → 看能否帮对方解决卡点（"你的接口还差什么？我能不能帮忙？"）
  → 梳理对方还需要什么，把你的资源借给他
  适用：只是对方排期紧，不是技术障碍

策略二：Mock 先行，不阻塞自身
  → 自己 Mock 对方接口的响应，走通自己的全部流程
  → 等对方接口就绪后再替换 Mock
  → 核心思想：不让依赖方成为你的阻塞项
  适用：对方接口不涉及核心数据正确性验证

策略三：降级绕过
  → 设计降级策略：对方不可用时不展示该模块数据
  → 核心功能先上线："有数据展示，没数据不展示"
  → 等对方接口就绪后再开启完整功能
  适用：依赖功能不是核心流程的必要环节

策略四：找替代方案
  → 是否有另一个团队的同类接口可以替代？
  → 是否可以自己实现一个轻量版本？（先上，后续再替换）
  → 是否可以通过定时同步对方的数据，避免实时调用？
  适用：对方确实是无法交付且没有明确的交付时间

策略五：升级协调
  → 如果你的 Leader 和对方 Leader 关系好，请求 Leader 出面协调
  → 让产品经理去推动对方的产品经理（业务对业务，更有说服力）
  → 如果影响上线，上升到更高层决策
  适用：对方延期影响核心功能上线时间
```

**实战案例：**

```text
场景：你依赖支付团队的"对账文件下载"接口，但对方说开发排满了，要延期 2 周。

错误的处理：
后端：好吧，那我等你。—— 结果项目延期 2 周，问责时你说"是支付团队延期了"，
老板问"那你做了什么？"你答不出来。

正确的处理：

Step 1 - 主动推进：
"张哥（支付团队同学），我看你的对账接口排到下个迭代了。
我这边项目比较急，能不能把接口定义先给我？
我先 Mock 数据把流程跑通。
你的代码我可以帮忙一起写，我对这块业务也熟。"

→ 结果 1：对方给了接口定义 -> 你先 Mock，不阻塞
→ 结果 2：对方接受你帮忙 -> 你帮他写一部分，加快进度

Step 2 - 如果协商失败，降级方案：
"如果接口确实赶不上，那第一期我先不做自动对账，
改用手动上传对账文件 + 后台解析的方式，功能先上，
下个迭代再替换成自动对接。"

Step 3 - 如果影响上线，升级协调：
同步给你的 Leader 和产品：
"支付团队的对账接口要延期 2 周，我们的自动对账功能受影响。
对接情况：已沟通但对方排期满了。
我现在准备走手动对账方案兜底。
但如果你这边能推动对方 Leader 排期，自动对账可以按期上。
需要你帮忙协调一下吗？"
```

### 5.3 跨部门沟通注意事项

**跨部门沟通 vs 同部门沟通的差异：**

| 维度 | 同部门 | 跨部门 |
|------|--------|--------|
| 关系基础 | 有团队归属感，协作是天经地义 | 没有义务帮你，"帮你是情分" |
| 优先级 | 同一 Leader 可以统一协调优先级 | 对方 Leader 有自己的优先级，你的需求不一定排得高 |
| 信息透明度 | 日常站会、周会同步 | 你不问对方不会主动告诉你进度 |
| 责任划分 | 共同对产品负责 | 各管各的，出了问题可能扯皮 |
| 沟通频率 | 每天见面，随时沟通 | 可能两周才对齐一次 |

**跨部门沟通的 7 条核心原则：**

```text
原则 1：找到关键对接人
  不要在工作群里群发"找 XX 团队的对账接口负责人"。
  先问你的 Leader 或同事"支付团队的对账接口找谁"，
  然后直接私聊那个人。

原则 2：文档先行
  开会前先把接口文档、对接方案、时间节点整理成文档，
  发给对方提前看。不要直接拉会让人家"聊一下"。

原则 3：明确时间节点
  "这个接口下周五之前能出来吗？"
  而不是"尽快"——"尽快"在对方的 To-do List 里可能排到第 99 位。

原则 4：提前暴露风险
  发现可能延期时第一时间同步，不要憋到最后。
  Leader 不怕延期，怕的是"临上线了才知道延期"。

原则 5：沟通留痕
  重要约定（接口定义、时间节点、SLA）要有文字记录。
  飞书/企微聊天记录截个图，或者邮件确认一下。
  口头承诺——三天后对方可能不记得了。

原则 6：主动反馈
  对方帮你解决了问题后，发个消息："接口调通了，谢谢！"
  这不是客套——正向反馈会提高对方下次帮你的意愿。

原则 7：建立长期关系
  路过对方工位时打个招呼、团建时一起吃饭、
  对方有困难时主动帮忙——人脉是在日常中积累的。
  "关键时候有人帮你"的前提是"你平时就在积累好人缘"。
```

> 🎯 **核心要点**：跨团队协作的本质是**管理他人的优先级**。对方没有义务按时帮你，你需要让对方觉得"帮你是对双方都有利的事"。文档留痕、提前暴露风险、主动推进——这三个习惯能让你在跨团队协作中立于不败之地。

## 6. 实习生/新人沟通特别指南

> 每个大牛都是从小白起步的。前 3 个月的沟通策略，直接决定了你在团队中的"靠谱印象"和成长加速度

### 6.1 如何提问（先自己研究 15 分钟 → 带着方案提问）

新人最容易犯的错误是：**遇到问题不留思考时间，立马就问人**。问题还没到 30 秒就抛到工作群，不仅打断别人，也让你失去了独立解决问题的机会。

**15 分钟自检法则：**

```text
遇到问题时，不要急着问人。给自己 15 分钟：

0-5 分钟：自行搜索
  ├── 项目代码里有没有类似实现？Ctrl+Shift+F 搜关键词
  ├── 项目 Wiki / 内部博客有没有相关文档？
  ├── Google / Stack Overflow / ChatGPT 搜索报错信息
  └── 搜团队聊天记录历史（别人可能问过同样的问题）

5-10 分钟：自行排查
  ├── 看日志（重点是 Error 级别和 Stack Trace）
  ├── 本地 Debug 追一下调用链
  ├── IDEA 提示（Alt+Enter 有没有解决方案？）
  └── 写一个最小 Demo 验证猜想

10-15 分钟：准备提问
  ├── 整理问题上下文（是什么？在哪出现？做了什么尝试？）
  ├── 形成自己的猜想（我觉得可能是……但我不能确定）
  └── 找到合适的人（不要在工作群 @所有人）
```

**好的提问 vs 坏的提问（同一个问题）：**

```text
❌ 坏的提问（直接往群里甩）：

"这个接口报 500 了，谁来看看？"

→ 结果：没人愿意回。信息太少，别人没法定位。
  而且群里 @ 所有人，大家都会装作没看见。

✅ 好的提问（私聊 + 带着方案）：

"张哥好，忙吗？有个问题想请教一下，大概 3 分钟。

我在调 user-service 的 GET /api/v1/users/10086 时，
返回了 500 错误。报错信息是数据库连接超时。

我做了这些排查：
1. 确认了本地 MySQL 是启动的（进程在运行）
2. 试了用 Navicat 直连，能连上
3. 项目 application.yml 里数据库地址配的是 10.0.1.100
4. 我看其他同学配置的是 localhost

我猜想是不是因为我数据库地址配错了？
该改成 localhost？但不知道为什么用 IP 连不上，
本地 hosts 也没配这个 IP 的映射。

张哥能帮我看下这个问题可能出在哪吗？"

→ 结果：张哥只需要 10 秒就能回答"是的，改成 localhost"。
  张哥还会觉得"这新人不错，思路很清晰"。
```

**提问质量对照表：**

| 维度 | 差的提问 | 好的提问 |
|------|---------|---------|
| 时机 | 遇到问题立刻问 | 先自己研究 15 分钟 |
| 渠道 | 工作群 @所有人 | 私聊 + 先问"方便吗" |
| 信息量 | "报错了，帮我看看" | 问题背景 + 已经做的排查 + 我的猜想 |
| 问题范围 | 模糊不清（"这里有问题"） | 具体明确（"这个方法抛 NPE"） |
| 对方成本 | 需要从零开始排查 | 只需要确认/纠正你的思路 |

> 💡 **记住**：一个问题如果你问了两次，说明第一次你只是记住了答案，没理解原理。每次问完后把答案记到自己的笔记里——Notion / Obsidian / 语雀都可以。

### 6.2 如何让别人愿意帮你（提问的艺术）

在职场中，**别人帮你不是义务**。别人愿意花时间帮你，是因为你值得帮。

**让别人愿意帮你的 4 个原则：**

```text
原则 1：备足功课，降低对方的帮助成本

✅ "我查了项目文档、看了代码、试了 A 和 B 都没解决，
   现在卡在 C 上。能帮我看看 C 的思路吗？"
   → 对方只需要在 C 上指点你，成本极低

❌ "这个不会，教教我。"
   → 对方要从头开始教你，成本极高

---

原则 2：尊重对方的时间

✅ "张哥，现在方便吗？有个关于订单退款的问题想请教，大概 3 分钟。"
   → 让对方自己决定是否现在处理

❌ 直接发一个问号或"在吗？"
   → 对方心里：你谁啊？凭什么让我猜你要干嘛？

---

原则 3：记笔记，不重复犯

✅ 别人教了你之后：
   "明白了，原来是这个原理。我记到笔记里了，下次不会再犯了。谢谢！"

❌ 同样的问题问第二次
   "上次你说过的那个……我忘了，能再说一遍吗？"
   → 对方：上次白教了

---

原则 4：正向反馈，让帮助有价值感

✅ "按你教的方法解决了！原来忽略了这个细节，学到了。"
   → 帮助有价值感，下次还愿意帮你

❌ 问完就走，没有反馈
   → 对方不知道你解决了没，下次帮你的意愿降低
```

**新人沟通避坑清单：**

```text
🚫 绝对不要做的事：

1. 在群里问"在吗？"
   → 这是最令人讨厌的打招呼方式。有事直接说事。

2. 在群里 @ 所有人 问一个私聊就能解决的问题
   → 所有人的消息都被你打扰了，你的"不靠谱"标签又+1

3. 没有自己查就问
   → 别人一搜就搜到答案的问题，你还去问
   → 别人会想"这人不爱思考"

4. 问完不记笔记
   → 同样的问题问两遍，信用破产

5. 不懂装懂
   → 需求评审时一直点头，开发一半才发现方向错了
   → 不仅坑自己，还坑测试和前端

✅ 应该做的事：

1. 问之前先做 15 分钟研究
2. 私聊 + 先确认对方是否方便
3. 带着方案提问（我的理解是……这样对吗？）
4. 问完后记笔记，分享到团队文档
5. 问完后给对方反馈（"按你说的方法解决了，谢谢"）
```

### 6.3 入职前 3 个月沟通策略（第 1 月 / 第 2 月 / 第 3 月）

**第一个月：适应期——多听少说，建立信任**

```text
核心目标：
  ├── 了解团队组织架构、业务方向、技术栈
  ├── 本地开发环境跑通，项目能启动
  ├── 认识团队每个成员（记住名字和对应模块）
  └── 交付第一个任务（哪怕只是改一个文案）

沟通策略：
  1. 参加所有会议（站会、评审会、复盘会）
     - 听不懂的记下来，会后问 Mentor
     - 不要怕问"幼稚"的问题（但问之前先 15 分钟自检）

  2. 接到任务后先确认理解
     "我理解这个需求是要……这样做对吗？有没有什么要注意的？"
     → 避免方向性错误，这是新人最大的坑

  3. 每天同步进度
     "今天的进展是……明计划做……目前没有阻塞。"
     → 让 Mentor 知道你在做什么

  4. 踩坑记录
     "今天在搭环境时遇到的 XXX 问题，解决方案是……"
     → 形成自己的第一份知识文档
```

**第二个月：上手期——主动承担，建立产出**

```text
核心目标：
  ├── 独立完成一个中等难度的需求（开发→自测→提测→上线）
  ├── 理解项目的核心业务流程
  ├── 开始主动同步进度而非被动回答
  └── 和测试、前端同学建立基本的协作关系

沟通策略：
  1. 需求评审时开始发表技术意见
     "这个接口如果数据量大的话，建议加缓存。"
     → 让大家意识到你已经开始思考了

  2. 提测前主动找测试对齐
     "老张，退款功能明天提测。主要改动是……自测结果见文档……
      重点关注退款并发和超时场景。"
     → 测试会很喜欢这样的后端

  3. 联调时主动找前端确认
     "接口已经部署到测试环境了，你看看文档里的接口能不能调通？
      有问题随时找我。"
     → 前端感觉你在主动配合，合作会很愉快

  4. 遇到风险及时汇报
     "目前整体进度正常，但有一个风险——支付回调接口依赖第三方，
      还在等对方确认。如果本周五前没回复，可能影响提测。"
     → 不要等 deadline 才说"做不完"
```

**第三个月：贡献期——独立交付，提出改进**

```text
核心目标：
  ├── 独立负责一个完整的功能模块
  ├── 对不合理的代码或流程提出改进建议
  ├── 参与 Code Review，给他人提意见
  └── 在团队内做一次技术分享

沟通策略：
  1. 主动参与 Code Review
     "你这个订单查询的 SQL 我看了，用 EXISTS 替代 IN 会快一些。"
     → 展示技术判断力，让大家注意到你在成长

  2. 发现文档缺失主动补全
     "我发现在 README 里缺少本地环境搭建的步骤，
      我补充了一下，大家看看有没有问题。"
     → 团队喜欢能主动维护知识库的人

  3. 做一次技术分享（15-30 分钟）
     "我给大家分享一下这次重构支付的踩坑记录……"
     → 技术分享是新人的高光时刻，准备充分点

  4. 开始思考系统层面
     "我最近发现我们支付模块的重试机制有风险，
      当消息队列挂掉时重试消息会丢。要不要加个本地消息表？"
     → 从"执行者"到"思考者"的转变
```

**新人入职 3 个月的自检问题：**

```text
月底花 10 分钟问自己这几个问题：

第一个月：
  □ 我能独立把项目在本地跑起来了吗？
  □ 我知道团队里每个人负责什么模块吗？
  □ 我已经交付了一个任务并上线了吗？
  □ 我有自己的知识笔记了吗？

第二个月：
  □ 我能在不求助的情况下完成一个中等任务吗？
  □ 我和测试、前端有过直接协作了吗？
  □ 我遇到问题时知道该找谁了吗？
  □ 我在需求评审上说过话了吗？

第三个月：
  □ 我能独立完成一个完整功能上线了吗？
  □ 我给别人的代码提过 Review 建议了吗？
  □ 我在团队里做过分享了？
  □ 团队同事对我有"靠谱"的评价了吗？
```

> 🎯 **核心要点**：新人最大的资本是**学习态度**，最大的负债是**不主动**。主动汇报、主动提问（但先自己查）、主动帮忙、主动记录——这四个主动让你在团队中快速站稳脚跟。没有人有义务教你，让同事愿意教你，是你自己的本事。
