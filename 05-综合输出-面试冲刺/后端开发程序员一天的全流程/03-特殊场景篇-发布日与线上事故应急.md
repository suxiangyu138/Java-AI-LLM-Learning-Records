### 1.4 出了问题怎么办：回滚决策树

```text
                  发布后发现异常
                       │
                ┌──────┴──────┐
                ▼              ▼
             P0/P1 故障       P2/P3 问题
                │                │
        ┌───────┴───────┐       │
        ▼               ▼       ▼
   影响全部用户     影响部分用户   可接受
        │               │        │
        ▼               ▼        ▼
   立即回滚        评估严重程度     记录 Bug
        │               │        下版本修复
        │          ┌────┴────┐
        │          ▼         ▼
        │      有规避方案   无规避方案
        │          │         │
        │          ▼         ▼
        │      接受 + 修复  回滚
        │        下版本
        ▼
   git revert + 重新部署 + 验证
```

| 情况 | 决策 | 理由 |
|------|:----:|------|
| 核心接口 500、用户无法操作 | 立即回滚 | 用户体验优先，不能影响线上 |
| 接口 P99 响应从 100ms 升到 500ms | 视情况回滚 | 如果严重影响用户体验则回滚 |
| 新功能有个 Bug 但没触发 | 记录 Bug 下版本修复 | 不影响现有功能，不必冒险回滚 |
| 配置项写错了 | Hotfix | 改配置重新发布，无需回滚代码 |
| DB 变更导致慢查询 | 回滚 DDL | DDL 回滚 + 紧急索引优化 |

### 1.5 回滚操作实战

```bash
# Step 1: 立即停止灰度/全量发布
# Jenkins 中停止继续部署，或手动停止脚本

# Step 2: Git 回退版本
git checkout master
git pull origin master
git revert v1.2.0 --no-edit
git push origin master

# Step 3: 重新构建部署包
mvn clean package -DskipTests -Pproduction
scp target/app.jar user@prod-server:/opt/app/

# Step 4: 重启服务
ssh user@prod-server "systemctl restart app"

# Step 5: 验证回滚成功
# 检查接口是否恢复
curl -X GET "https://api.example.com/health" -w "%{http_code}"

# 检查日志无异常
kubectl logs --tail=100 -n production pod/app-xxx | grep "ERROR" | head

# Step 6: 数据兼容性验证
# 确保回滚后新产生的数据不会因为字段缺失而报错
```

> ⚠️ **回滚黄金法则**：
> 1. **回滚要快**：发现 P0 故障后 2 分钟内开始回滚
> 2. **数据兼容第一**：发布新字段时确保上游代码兼容旧版本
> 3. **回滚后立即通知**：通知产品/运维/QA 已经回滚
> 4. **复盘再发布**：回滚后分析根因，修复后再重新走发布流程

> 💡 **回滚 vs Hotfix 选择**：
> - **回滚**适合：代码本身有问题、数据不一致、核心功能异常
> - **Hotfix**适合：配置错误、非功能性 Bug、不影响核心逻辑的小问题

> 🎯 **核心要点**：发布不是终点，而是线上运维的起点。好的发布流程让 99% 的发布无感完成，好的回滚方案让那 1% 的异常 5 分钟恢复。

## 2. 线上事故应急全流程

### 2.1 P0 事故应急 SOP

```text
阶段1: 发现 (0-2min)
   告警触发 / 用户反馈 / 监控大盘异常
   ↓
   值班人员确认告警真实性
   ↓
阶段2: 拉群 (2-5min)
   建立应急响应群：@相关后端、@运维、@产品
   ↓
阶段3: 止血 (5-15min)
   回滚 / 降级 / 限流 / 重启 / DB 切换
   ↓
阶段4: 定位 (15-30min)
   日志 → 指标 → 链路 → 代码
   ↓
阶段5: 修复 (30-60min)
   代码修复 / 配置修改 / 数据订正
   ↓
阶段6: 复盘 (24h 内)
   5Why 分析 → 改进措施 → 责任人 → 跟进
```

### 2.2 事故响应角色

| 角色 | 职责 | 谁担任 |

### 2.3 真实事故场景模拟 4 个

#### 场景 1：「数据库连接池满了，用户支付失败」

**事故背景**：晚上 20:00，监控告警：支付接口错误率飙升至 30%，用户反馈无法支付。

**现象**：
- 错误日志：`Cannot acquire connection from HikariPool - Timeout`
- 支付接口响应时间从 50ms 飙升至 10s+
- QPS 正常，但错误率持续上升

**影响范围**：
- 所有用户无法支付
- 等级：P0

**应急步骤与止血方案**：

```bash
# Step 1: 确认告警（2min）
# 查看 HikariCP 连接池状态
jstat -gcutil <pid> 1000 5
# 发现活跃连接数满，连接池耗尽

# Step 2: 紧急止血（5min）
# 方案 A: 重启应用（快速恢复连接池）
kubectl rollout restart deployment/payment-service -n production

# 方案 B: 如果重启无效，排查是否有慢 SQL 占连接不放
# 查看 MySQL 当前连接状态
SHOW FULL PROCESSLIST;

# 发现大量处于 "Sending data" 状态的连接
# Step 3: Kill 异常连接
KILL CONNECTION <thread_id>;

# Step 4: 临时限制连接池大小并监控
# 在配置中心调整
spring.datasource.hikari.maximum-pool-size=50  # 从 100 降到 50
spring.datasource.hikari.connection-timeout=5000  # 超时时间降为 5s

# Step 5: 等待连接池恢复正常
# 观察活跃连接数曲线下降
```

**根因定位**：

```sql
-- 分析慢查询
SELECT * FROM information_schema.PROCESSLIST 
WHERE COMMAND != 'Sleep' 
ORDER BY TIME DESC LIMIT 20;

-- 发现一条 SQL 执行了 60s+
SELECT * FROM `order` WHERE user_id = ? AND status IN (?, ?, ?) ORDER BY created_at DESC;
-- 原因：user_id 字段没有索引，全表扫描 500 万行

-- 验证索引情况
SHOW INDEX FROM `order`;
-- user_id 确实没有索引
```

**永久修复**：

```sql
-- 1. 添加索引
ALTER TABLE `order` ADD INDEX `idx_user_id` (`user_id`);

-- 2. 代码层优化（限制查询范围）
SELECT * FROM `order` 
WHERE user_id = ? AND status IN (?, ?, ?) 
  AND created_at >= DATE_SUB(NOW(), INTERVAL 3 MONTH)  -- 限制查询范围
ORDER BY created_at DESC 
LIMIT 20;

-- 3. 增加慢查询监控告警
-- 在 MySQL 配置中设置慢查询阈值
SET GLOBAL long_query_time = 2;
SET GLOBAL slow_query_log = ON;
```

> 🎯 **核心要点**：连接池耗尽的核心原因往往不是并发过高，而是**慢 SQL 占着连接不释放**。先 Kill 慢查询止血，再添加索引根治。

#### 场景 2：「Redis 挂了，缓存全部穿透到 DB」

**事故背景**：下午 15:00，Redis 集群主节点宕机，所有缓存失效。

**现象**：
- DB 连接数从 50 飙升至 500+
- DB CPU 从 20% 飙升至 95%
- 大量业务接口响应超时

**影响范围**：
- 全部接口变慢（3s+ 响应时间）
- 部分接口超时报错
- 等级：P1

**分级应对**：

```text
Level 1: 缓存穿透（少量 Key 失效）
   → 方案：布隆过滤器 + 互斥锁
   
Level 2: Redis 部分不可用（当前场景）
   → 方案：本地缓存兜底 + 限流降级
   
Level 3: Redis 完全不可用
   → 方案：限流 + DB 保护 + 降级展示

Level 4: DB 也被打崩
   → 方案：限流 + 返回兜底数据 + 排队页
```

**应急步骤**：

```bash
# Step 1: 确认 Redis 状态（2min）
redis-cli -h redis-cluster.example.com -p 6379 ping
# (error) CLUSTERDOWN The cluster is down

# 检查 Redis 集群节点状态
redis-cli --cluster check redis-cluster.example.com:6379

# Step 2: 紧急止血 - 开启本地缓存兜底（5min）
```

```java
// 本地缓存兜底方案（Caffeine）
@Component
public class CacheFallbackManager {
    
    private final Cache<String, Object> localCache = Caffeine.newBuilder()
        .maximumSize(10000)
        .expireAfterWrite(30, TimeUnit.SECONDS)  // 本地缓存 30s 过期
        .build();
    
    public <T> T getWithFallback(String key, Class<T> type, Supplier<T> dbLoader) {
        // 1. 先查 Redis
        T value = redisTemplate.opsForValue().get(key);
        if (value != null) return value;
        
        // 2. Redis 挂了，查本地缓存
        value = (T) localCache.getIfPresent(key);
        if (value != null) return value;
        
        // 3. 本地也没有，查 DB（加互斥锁防止击穿）
        synchronized (key.intern()) {
            value = (T) localCache.getIfPresent(key);
            if (value != null) return value;
            
            value = dbLoader.get();
            if (value != null) {
                localCache.put(key, value);
            }
            return value;
        }
    }
}
```

```yaml
# 配置中心 - 开启降级开关
circuit-breaker:
  enabled: true
  redis:
    fallback: local-cache        # 降级策略：本地缓存兜底
    rate-limit: 100              # 限流：每秒最多 100 个查 DB 请求
    timeout-ms: 200              # 超时 200ms 直接降级
```

```bash
# Step 3: 限流保护 DB（10min）
# Nginx 层面限流
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=500r/s;

# Step 4: Redis 恢复
# 重启 Redis 节点
redis-server /etc/redis/redis.conf &

# 重建集群
redis-cli --cluster rebalance redis-cluster.example.com:6379

# Step 5: 恢复后验证
redis-cli ping
# PONG

# 确认缓存重新加载正常
curl -X GET "https://api.example.com/products/top" -w "%{time_total}s"
# 恢复至 20ms
```

**永久修复**：

```yaml
# 架构优化：多级缓存架构
cache:
  l1:                              # 一级缓存：本地
    type: caffeine
    max-size: 10000
    ttl: 30s
  
  l2:                              # 二级缓存：Redis
    type: redis-cluster
    nodes: 
      - redis-1:6379
      - redis-2:6379
      - redis-3:6379
  
  l3:                              # 三级缓存：DB
    type: mysql
    read-timeout: 500ms
    
  circuit-breaker:
    enabled: true
    redis-down-strategy: local-cache-only  # Redis 挂掉，只用本地缓存
    db-down-strategy: return-fallback      # DB 挂掉，返回兜底数据
```

> 🎯 **核心要点**：每一个 Redis 缓存必须回答"Redis 挂了怎么办"。**多级缓存 + 限流降级**是应对缓存故障的标准方案。

#### 场景 3：「新版本上线后接口 QPS 暴跌 70%」

**事故背景**：22:00 发布新版本 v1.2.0，22:10 监控显示核心接口 QPS 从 2000 暴跌至 600。

**现象**：
- QPS 曲线断崖式下跌
- 错误率正常（<0.1%）
- 响应时间正常
- 服务器资源正常

**影响范围**：
- 业务指标异常（订单量下降）
- 用户无感，但业务受损
- 等级：P1

**排查与回滚**：

```bash
# Step 1: 检查错误率（2min）
# 错误率正常 → 排除代码异常

# Step 2: 检查响应时间（3min）
# 响应时间正常 → 排除性能问题

# Step 3: 检查流量入口（5min）
# 查看 Nginx 日志
tail -n 1000 /var/log/nginx/access.log | awk '{print $7}' | sort | uniq -c | sort -rn

# 发现某几个接口完全没有请求？
# 检查：是否改动了路由配置

# Step 4: 排查 Gateway 路由（5min）
# 查看 Gateway 日志
kubectl logs -n production pod/gateway-xxx | grep "routing"

# 发现新版本改动了 Gateway 路由配置
# 原来的 /api/v1/orders -> order-service
# 变成了 /api/v2/orders -> order-service
# 前端调用的还是 /api/v1/orders！

# Step 5: 立即回滚（5min）
git revert v1.2.0
mvn clean package -DskipTests -Pproduction
kubectl rollout restart deployment/order-service -n production

# Step 6: 验证恢复
# QPS 曲线观察 5 分钟，恢复至 2000+
```

**根因分析**：
- 开发在重构时改了 API 路径前缀（`v1` → `v2`），但未通知前端更新
- QA 测试时用的测试环境配置不同，未发现路由问题
- 线上流量真实用户访问才暴露问题

**永久修复**：


#### 场景 4：「MQ 消息积压 500 万条，订单处理延迟」

**事故背景**：周五晚高峰，监控告警：订单处理 MQ 队列积压 500 万条，消费者处理延迟达 30 分钟。

**现象**：
- 消费者日志显示处理时间从 10ms 涨到 500ms/条
- 队列堆积量每分钟增加 1 万条
- 用户反馈下单后 30 分钟仍未收到确认通知

**影响范围**：
- 订单状态更新延迟
- 用户通知延迟
- 等级：P1

**紧急处理**：

```bash
# Step 1: 确认积压情况（2min）
# RocketMQ 控制台查看堆积
# 或使用 CLI
mqadmin consumerProgress -n namesrv:9876 -g order-consumer-group

# 输出：
# Topic: order_topic
# 总消息数: 5,000,000
# 消费者落后: 4,800,000
# 消费速度: 1,000 msg/s

# Step 2: 判断积压原因（5min）
# 检查消费者日志，发现处理每条消息都要查一次数据库
# DB 响应变慢导致消费速度下降

# Step 3: 紧急止血 - 扩容消费者（10min）
kubectl scale deployment/order-consumer --replicas=20 -n production
# 从 5 个消费者扩容到 20 个

# Step 4: 如果消费者是单线程处理，调整并发参数
# 配置中心调整
spring.cloud.stream.bindings.order-input:
  consumer:
    concurrency: 10          # 每个消费者线程数从 1 -> 10

# Step 5: 观察消费速度（5min）
# 消费速度从 1000 msg/s 提升到 5000 msg/s
# 预计 16 分钟消费完毕

# Step 6: 处理完积压后，逐步缩容回正常规模
kubectl scale deployment/order-consumer --replicas=5 -n production
```

**根因定位**：

```java
// 问题代码：每条消息都查 DB，且 SQL 慢
@Component
public class OrderConsumer {
    
    @StreamListener("order-input")
    public void handleOrder(OrderMessage message) {
        // 每条消息查一次 DB
        Order order = orderMapper.selectById(message.getOrderId());
        // ... 处理业务逻辑
        
        // 再查一次用户信息
        User user = userMapper.selectById(order.getUserId());
        // ... 发送通知
    }
}

// 解决方案：批量消费 + 缓存
@Component
public class ImprovedOrderConsumer {
    
    private static final int BATCH_SIZE = 100;
    private final List<OrderMessage> buffer = new ArrayList<>(BATCH_SIZE);
    
    @StreamListener("order-input")
    public void handleOrder(OrderMessage message) {
        buffer.add(message);
        if (buffer.size() >= BATCH_SIZE) {
            processBatch(new ArrayList<>(buffer));
            buffer.clear();
        }
    }
    
    private void processBatch(List<OrderMessage> messages) {
        // 批量查 DB，一次查询代替 N 次
        List<Long> orderIds = messages.stream()
            .map(OrderMessage::getOrderId)
            .collect(Collectors.toList());
        List<Order> orders = orderMapper.selectBatchIds(orderIds);
        
        // 批量处理
        Map<Long, Order> orderMap = orders.stream()
            .collect(Collectors.toMap(Order::getId, Function.identity()));
        
        for (OrderMessage msg : messages) {
            Order order = orderMap.get(msg.getOrderId());
            if (order != null) {
                processOrder(order);
            }
        }
    }
}
```

**永久修复**：

```yaml
# 1. 消费者改为批量消费
mq:
  consumer:
    batch-size: 100
    concurrency: 5
    max-retry: 3

# 2. 增加积压告警（提前发现）
monitor:
  alert-rules:
    - metric: mq_accumulation
      threshold: 100000    # 积压 10 万条告警
      severity: P1
      action: auto-scale   # 自动扩容

# 3. 消费者自动弹性伸缩
auto-scaling:
  consumer-group: order-consumer-group
  min-replicas: 3
  max-replicas: 20
  scale-up-threshold: 50000   # 积压 > 5 万自动扩容
  scale-down-threshold: 1000  # 积压 < 1000 自动缩容
```

> 🎯 **核心要点**：MQ 积压的核心原因是**消费速度 < 生产速度**。应急止血靠扩容 + 批量消费，根治靠优化消费逻辑减少外部依赖。

### 3.2 告警分级与响应 SLA

| 等级 | 定义 | 响应时间 | 恢复时间 | 通知方式 | 示例 |

## 4. 周末/凌晨被叫醒怎么办

### 4.1 心态调整

被叫醒的第一反应往往决定了处理效率：

```text
❌ 错误心态：
"为什么又是我？！烦死了！"
→ 带着情绪处理，容易犯错

✅ 正确心态：
"告警响了，肯定是哪里有问题，先确认一下"
→ 冷静处理，快速定位

✅ 进阶心态：
"又出这个告警了？看来上次的修复还不够彻底"
→ 思考根因，减少下次被叫醒的概率
```

**心理建设技巧：**

| 状态 | 技巧 | 说明 |
|------|------|------|
| 刚被叫醒大脑空白 | 深呼吸 3 次 → 喝口水 → 看消息 | 给大脑 30s 缓冲 |
| 看到告警很慌 | 告诉自己：先看日志，再看监控 | 按流程走，不慌乱 |
| 处理到一半不会了 | 升级！立即电话 Leader | 不丢人，比出大事强 |
| 处理完了 | 记录 + 睡回笼觉 | 第二天复盘即可 |

### 4.2 标准化应急流程（减少个人压力）

```text
被叫醒后的标准化流程（2 分钟内完成）：

Step 1: 看消息（30s）
   └─ 什么告警？什么服务？影响什么？

Step 2: 看一眼手机上的监控（30s）
   └─ 用手机打开 Grafana / 监控 App

Step 3: 判断级别（30s）
   └─ P0/P1 → 起床开电脑 → 开始处理
   └─ P2/P3 → 看一眼能否扛到明天
           └─ 能 → 记下来，明天处理
           └─ 不能 → 起床处理

Step 4: 通知（30s）
   └─ P0 → 在群里 @所有人 说一句 "已在排查"
   └─ P1 → 确认是否影响核心功能

Step 5: 开电脑处理（5-15min）
   └─ 按应急 SOP 走
```

### 4.3 事后复盘与改进（从根因上减少被叫醒）

**复盘 5Why 分析法：**

```text
问题：凌晨 3 点被叫醒，用户服务 CPU 飙到 100%

Why 1: 为什么 CPU 飙到 100%？
  因为 Full GC 频繁，GC 线程占大量 CPU

Why 2: 为什么 Full GC 频繁？
  因为堆内存被占满，大量对象无法回收

Why 3: 为什么堆内存被占满？
  因为缓存了 500MB 的用户 Session 数据没有过期

Why 4: 为什么 Session 缓存没有过期？
  因为 Session 的 TTL 配置成 7 天，且没有最大容量限制

Why 5: 为什么 TTL 配置这么长？
  因为上次为了修复"用户登录频繁过期"问题，把 TTL 调长了，但没有配套的容量限制

根因：Session 缓存配置不合理，TTL 过长且无容量限制
改进：设置最大容量 + 合理的 TTL + 告警
```

**减少被叫醒的改进清单：**

| 改进方向 | 具体措施 | 效果 |
|----------|----------|:----:|
| 增加自动恢复能力 | 连接池自动扩容、自动重启 | 很多问题自动恢复 |
| 增加弹性伸缩 | MQ 消费者自动扩容 | 积压问题自动消化 |
| 配置合理化 | 内存上限、超时时间、连接池大小 | 减少资源耗尽 |
| 增加预警 | CPU > 70% 就告警，别等到 100% | 提前处理 |
| 健全监控 | 更细粒度的监控指标 | 快速定位 |
| 前置发现 | 压测发现性能瓶颈，预调优 | 减少线上问题 |
| 加强测试 | 更多回归测试、灰度测试 | 减少发布问题 |

**个人改进记录模板：**

```markdown
# 被叫醒记录
```

> 🎯 **核心要点**：每一次被叫醒都应该是一次改进的机会。**不要只想"把它修好"，要想"怎么让它不再出同样的问题"**。好的工程师不只是解决问题，更是系统地减少问题。
