Live Templates 能让你用几个字母就生成一段代码模板，省去重复敲击的时间。

| 缩写 | 模板内容 | 使用频率 |
|:----:|---------|:-------:|

| `sout` | `System.out.println()` | 调试打印（建议换成 soutv） |
| `soutv` | `System.out.println("变量名 = " + 变量)` | 调试打印 |

| `foreach` / `iter` | `for (T item : items) {}` | 遍历集合 |
| `ifn` | `if (变量 == null) {}` | 空值判断 |

| `list.for` | `list.forEach(item -> {})` | Lambda 遍历 |
| `return` | 自动补全方法返回值 | 写 return 语句 |

**推荐自定义的模板：**

在 IDEA 中打开 `Settings → Editor → Live Templates → 新建 Template Group`，添加以下高频模板：

```java
// 1. log - 日志输出 (SLF4J)
// 缩写: log
private final Logger logger = LoggerFactory.getLogger($CLASS$.class);
// 适用: Java

// 2. logi - INFO 日志
// 缩写: logi
logger.info("$MESSAGE$", $PARAMS$);

// 3. loge - ERROR 日志
// 缩写: loge
logger.error("$MESSAGE$", $PARAMS$);

// 4. logw - WARN 日志
// 缩写: logw
logger.warn("$MESSAGE$", $PARAMS$);

// 5. api - 写一个完整的 Controller 接口
// 缩写: api
@$TYPE$Mapping("/$PATH$")
public CommonResult<$RESULT$> $METHOD$(@RequestBody $PARAMS$) {
    return CommonResult.success($SERVICE$.$METHOD$($PARAMS$));
}
```

### 1.4 Debug 高级技巧

普通断点大家都会用，真正拉开差距的是**高级断点技巧**。

#### 条件断点

在断点上右键，输入条件表达式。只在满足条件时停下，避免无休止的 F9。

```java
// 场景：10W 条数据处理，从第 50000 条开始出了问题
// 设置条件断点：index >= 50000
for (int i = 0; i < 100000; i++) {
    process(data[i]);  // 在这里打条件断点 i >= 50000
}
```

#### 异常断点

不用猜测异常在哪抛出，直接让 IDE 停在异常发生的那一行。

操作：`View → Breakpoints → + → Java Exception Breakpoint`，输入 `NullPointerException` 或自定义异常类。

```text
场景：线上日志看到 NullPointerException，但 try-catch 范围太大
方法：增加异常断点 NullPointerException，不勾选 Caught exception，只勾选 Uncaught exception
效果：程序在 NPE 发生的第一时间停下来，精确到行
```

#### 字段断点

监控某个字段值被修改的地方，不需要全项目搜索赋值语句。

```java
// 场景：订单状态 orderStatus 莫名其妙被改了
// 在 orderStatus 字段上打 Field Watchpoint
private Integer orderStatus;  // 右键 → Field Watchpoint → 勾上 Field modification
// 任何地方修改了这个字段，IDE 都会自动停在修改处
```

#### 远程调试

线上 Bug 难以复现时，用远程调试连到测试环境（注意不要在生产环境使用！）。

```bash
# JVM 启动参数，开启远程调试端口 5005
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=5005 \
     -jar my-app.jar
```

IDEA 中配置：`Run → Edit Configurations → + → Remote JVM Debug`，输入 Host 和端口。

> ⚠️ **安全性**：远程调试端口**不要暴露到公网**。只在办公网络/VPN 内使用，用完立即关闭。

#### Debug 常用快捷键

| 快捷键 | 作用 |
|--------|------|
| `F8` | 单步跳过（Step Over） |
| `F7` | 单步进入（Step Into） |
| `Shift + F8` | 跳出（Step Out） |
| `F9` | 继续运行至下一断点（Resume） |
| `Alt + F8` | 表达式求值（Evaluate Expression） |
| `Ctrl + Shift + F8` | 查看所有断点 |

### 2.2 日志查看三件套：grep + tail + less 组合技

排查线上问题，90% 的时间都在看日志。掌握这三个命令的组合是后端基本功。

**场景一：实时追踪日志，过滤关键字**

```bash
# 实时查看日志，过滤出包含 "ERROR" 的行
tail -f /app/logs/app.log | grep --color=always ERROR

# 带上上下文（查 NPE 时看前后 10 行）
tail -f /app/logs/app.log | grep -C 10 "NullPointerException"

# 过滤多个关键字（同时包含 ERROR 和 orderId=12345）
tail -f /app/logs/app.log | grep "ERROR" | grep "orderId=12345"
```

**场景二：搜索历史日志**

```bash
# 在日志文件中搜索关键字（忽略大小写）
grep -i "order_timeout" /app/logs/app.log.2026-07-28

# 递归搜索整个日志目录（-r 递归, -n 显示行号）
grep -rn "transactionId=abc123" /app/logs/

# 统计关键字出现次数
grep -c "OutOfMemoryError" /app/logs/app.log
```

**场景三：查看大日志文件**

```bash
# 用 less 打开 GB 级别的日志文件（瞬间打开）
less /app/logs/app.log

# 在 less 中常用操作
# /keyword  → 向下搜索关键字
# ?keyword  → 向上搜索关键字
# n         → 下一个匹配
# N         → 上一个匹配
# g         → 跳到文件开头
# G         → 跳到文件末尾
# F         → 进入尾随模式（相当于 tail -f）
# Ctrl+C    → 退出尾随模式

# 用 less 打开并实时跟踪
less +F /app/logs/app.log
```

### 2.3 服务器健康检查三板斧

接到告警或被反馈"服务器有问题"，第一件事就是跑这三个命令：

```bash
# 第一板斧：top - 看整体负载
top
# 关键看：
#   load average: 1.23, 1.45, 1.67  → 超过 CPU 核数就说明过载
#   %Cpu(s): us 用户态, sy 内核态, wa IO等待
#   RES: 进程占用物理内存

# 第二板斧：free -h - 看内存
free -h
# 关键看：
#   total / used / available
#   available 是真正可用的内存（比 free 更准确）
#   注意: Linux 会把空闲内存用作缓存，所以 used 高不一定内存不足

# 第三板斧：df -h - 看磁盘
df -h
# 关键看：
#   各分区使用率，如果超过 80% 就要关注
#   超过 90% 可能导致服务异常（日志写不进去）
```

> 💡 **排查口诀**：先看负载（top）再看内存（free）再看磁盘（df），哪里满了解决哪里。如果都正常，那就是应用本身的问题，去看日志。

### 2.4 SSH 连接与跳板机配置

公司网络架构通常有多层隔离，需要配置 SSH 跳板：

```bash
# 方式一：直接通过跳板机（ProxyJump）
ssh -J user@jump-server user@target-server

# 方式二：在 ~/.ssh/config 中配置（推荐，方便复用）
# 文件位置: ~/.ssh/config
Host jump
    HostName jump.company.com
    User yourname
    Port 22

Host target-dev
    HostName 10.0.1.100
    User root
    Port 22
    ProxyJump jump     # 通过 jump 跳板

# 连接: ssh target-dev
```

**SSH 免密登录**

```bash
# 生成密钥对
ssh-keygen -t ed25519 -C "your_email@company.com"

# 复制公钥到服务器（自动添加到 ~/.ssh/authorized_keys）
ssh-copy-id user@server-ip
```

### 2.5 alias 别名配置

把高频命令缩写成 2-3 个字母，能节省大量输入：

```bash
# 在 ~/.bashrc 或 ~/.zshrc 中添加
# 常用缩写
alias ll='ls -lah --color=auto'
alias gp='git pull'
alias gc='git commit -m'
alias gst='git status'
alias gco='git checkout'
alias gb='git branch'
alias gl='git log --oneline --graph --all'

# Java 相关
alias jps='jps -l'
alias jstat='jstat -gcutil'
alias jstack='jstack -l'

# Docker 相关
alias dc='docker compose'
alias dcu='docker compose up -d'
alias dcd='docker compose down'
alias dcl='docker compose logs -f'

# 系统检查
alias meminfo='free -h'
alias diskinfo='df -h'
alias cpuinfo='lscpu'
alias ports='netstat -tulpn | grep'

# 重启 Java 服务流程
alias restart-java='ps aux | grep java | grep -v grep | awk "{print \$2}" | xargs kill -9 && java -jar /app/app.jar > /dev/null 2>&1 &'
```

加载配置：`source ~/.bashrc`

### 2.6 tmux 保持会话

SSH 断开后，终端上的任务会终止。tmux 可以保持会话不中断：

```bash
# 安装 tmux
apt install tmux -y

# 新建会话
tmux new -s my-session

# 常用快捷键（在 tmux 会话内按）
# Ctrl+B → %    垂直分屏
# Ctrl+B → "    水平分屏
# Ctrl+B → 方向键   切换窗格
# Ctrl+B → d    分离会话（不退出程序）
# Ctrl+B → [    进入滚动模式（可以翻页看历史输出）

# 重新连接会话
tmux attach -t my-session

# 列出所有会话
tmux ls
```

> ⚠️ **生产操作安全**：在生产服务器上执行长时间任务（如数据迁移、日志归档）时，一定要在 tmux 中执行。否则 SSH 抖动一下，任务断了都不知道。

> 🎯 **核心要点**：终端操作的效率来自肌肉记忆。grep/tail/less 日志三件套 + top/free/df 健康检查三板斧 + SSH 配置，这三大块是后端每天都要用到的。每学会一个命令，就配置一个 alias，让常用操作变成肌肉记忆。

## 3. 版本控制篇 — Git 工作流实战

### 3.2 Git 分支策略详解

**Git Flow（经典但较重）**

```text
main                ← 生产版本
  ├── develop       ← 开发主分支
  │    ├── feature/a  ← 功能分支（从 develop 切出，合并回 develop）
  │    ├── feature/b
  │    └── release/1.0  ← 发布分支（从 develop 切出，合并到 main 和 develop）
  └── hotfix/urgent   ← 紧急修复分支（从 main 切出，合并到 main 和 develop）
```

| 优点 | 缺点 |
|------|------|
| 流程规范，适合大团队 | 分支多，管理成本高 |
| 每类分支职责清晰 | 对持续交付要求高的团队不友好 |
| 适合有固定发布周期的项目 | 新手容易在 merge 方向犯错 |

**GitHub Flow（轻量，适合持续部署）**

```text
main                                ← 随时可部署
  └── feature/a  → 提 PR → merge    ← 功能分支，提 PR 后 Code Review
```

| 优点 | 缺点 |
|------|------|
| 极简，只有 main 和 feature 分支 | 没有 release 隔离，对发布节奏有要求 |
| 配合 CI/CD，合并即部署 | 不适合多版本并行维护的场景 |
| PR + Code Review 是核心机制 | |

**Trunk-based（主干开发，适合 DevOps 成熟团队）**

```text
main (trunk)                              ← 所有人直接往主干提交
  └── short-lived branch (1-2天) → merge
```

| 优点 | 缺点 |
|------|------|
| 冲突最少，因为分支存活时间短 | 对 CI 质量门禁要求极高 |
| 适合 DevOps 成熟度和自动化测试高的团队 | 不适合功能开发周期长的团队 |
| 持续集成的最佳实践 | 需要强大的特性开关（Feature Flag）支持 |

> 💡 **面试常考**："你们团队用什么分支策略？为什么？" 回答不仅仅是背定义，要说清楚你们团队的情况（迭代节奏、发布频率、团队规模）和选择的理由。面试官在意的是你会不会根据场景做决策。

### 3.3 冲突解决实战

冲突是每个后端开发日常要面对的事情，关键在于**冷静分析**而不是慌。

**冲突场景一：两个人改了同一个文件的同一行**

```text
<<<<<<< HEAD
    private String userName;
=======
    private String nickName;
>>>>>>> feature/profile
```

解决步骤：
1. 和改这行代码的同事沟通，确认使用哪个字段名
2. 如果需要都保留：`private String userName; private String nickName;`
3. 删除 `<<<<<<<`、`=======`、`>>>>>>>` 标记

**冲突场景二：同时改了接口的入参**

```java
// 你改了接口参数
public CommonResult<UserDTO> getUser(Long userId, Boolean includeDeleted)

// 同事改了同一个接口
public CommonResult<UserVO> getUser(Long userId)

// 解决方案：去和同事确认接口定义达成一致，然后统一成一个版本
```

**IDEA 可视化解决冲突**

```text
VCS → Git → Resolve Conflicts
-----------------------------------
IDEA 会显示三栏对比：
  Left:     你的本地版本
  Center:   共同的祖先版本
  Right:    远程版本

操作：
  ↑↓ 箭头：选择应用哪个版本
  X: 不应用任何版本
  可以直接在下方结果区手动编辑
```

> ⚠️ **冲突解决原则**：宁可改完跑一遍测试，也不要觉得"我肯定改对了"。冲突时常见的 Bug 是误删了别人的代码逻辑。

### 3.4 git rebase vs merge 的选择

这是一个经典的工程决策问题。

**merge 的场景：**
- 合并到主分支（main/develop）—— 保留完整的合并记录，知道"哪批功能合进来了"
- 公共分支上有人也基于同一个分支开发 —— merge 不修改历史，比 rebase 安全
- 你希望保留真实的合并历史

**rebase 的场景：**
- 功能分支开发中，想拉取主分支的最新代码 —— rebase 让提交历史是一条直线
- 提交历史有多个"WIP"或"fix typo"这样的临时提交，想整理后再合并
- 希望提交历史看起来干净、线性

```bash
# rebase 的正确姿势
git checkout feature/order
git rebase main
# 如果有冲突，解决后
git add .
git rebase --continue
# 推到远程（可能需要 force push，⚠️ 仅在你自己开发的分支上）
git push --force-with-lease
```

> 💡 **黄金法则**：**不要对公共分支（main/develop）执行 rebase**。rebase 会改写提交历史，如果在多人共享的分支上做，会导致大家的本地仓库都乱了。这个原则在面试中也常考。

### 3.5 git stash 妙用

stash 是后端开发最实用的命令之一，常用场景：

```bash
# 场景一：写到一半，突然要切分支修 Bug
# 当前工作区有修改，但还没提交
git stash save "WIP: order refund logic"  # 保存当前改动
git checkout hotfix/payment                # 切换到 hotfix 分支
# ... 修完热修复 ...
git checkout feature/order                 # 切回原分支
git stash pop                              # 恢复保存的改动

# 场景二：保存多个暂存项
git stash list                              # 列出所有 stash
git stash apply stash@{0}                   # 应用某个 stash 但不删除
git stash drop stash@{0}                    # 删除某个 stash

# 场景三：stash 未跟踪的文件
git stash -u                               # 连 untracked 文件一起暂存
```

### 3.6 git log / blame 追踪代码变更

**用 git log 了解提交历史：**

```bash
# 美观的单行显示
git log --oneline --graph --all

# 查看某个文件的修改历史
git log --oneline -p src/main/java/com/example/OrderService.java

# 查看某段代码是谁写的（显示改动的行号和作者）
git log -L 100,120:src/main/java/com/example/OrderService.java
```

**用 git blame 找"谁写了这行代码"：**

```bash
git blame src/main/java/com/example/OrderService.java
# 输出：
# a1b2c3d4 (张三 2026-07-20) private Integer orderStatus;
# e5f6g7h8 (李四 2026-07-25) private LocalDateTime payTime;

# 看到有疑问的老代码，先去 blame 找到原作者，沟通确认逻辑再改
```

> 💡 **实用技巧**：IDEA 里直接在行号上右键 → Annotate with Git Blame，比命令行更直观。

### 3.7 常见 Git 事故急救

#### 事故一：git reset --hard 误操作

```bash
# 手贱了？别慌！reflog 是最后的救命稻草
git reflog
# 输出类似：
# a1b2c3d4 HEAD@{0}: reset: moving to a1b2c3d4
# e5f6g7h8 HEAD@{1}: commit: feat: add order refund logic
# 找到你回退之前的 HEAD 位置（HEAD@{1}）
git reset --hard HEAD@{1}
# 搞定！
```

#### 事故二：commit message 写错了

```bash
# 还没 push，可以修改最新 commit 的消息
git commit --amend -m "feat: add order refund logic (fixed typo)"

# 已经 push 了，修改消息后 force push（⚠️ 仅限单人分支）
git commit --amend -m "feat: add order refund logic"
git push --force-with-lease
```

#### 事故三：提交到了错误的分支

```bash
# 在 main 上误提交了 feature 的代码
# 1. 从当前 main 创建 feature 分支
git branch feature/order
# 2. 把 main 回退到提交前（用 reflog 找到前一个提交）
git reset --hard HEAD@{1}
# 3. 切到 feature 分支继续开发
git checkout feature/order
```

#### 事故四：忘记了 pull，push 被拒绝

```bash
git push
# 报错: ! [rejected] feature/order -> feature/order (non-fast-forward)

# 正确做法：rebase 而不是 merge
git pull --rebase origin feature/order
# 如果有冲突，解决冲突
git add .
git rebase --continue
git push
```

#### 事故五：想撤销某个远程 commit（但不想改历史）

```bash
# revert 会创建一个新的"撤销提交"，不会改历史，适合公共分支
git revert <commit-id>
git push
```

> 🎯 **核心要点**：Git 技能的核心不在于背命令，而在于理解 Git 的数据模型（commit 是快照链、HEAD 是游标、reflog 是操作日志）。理解了模型，遇到任何"事故"都能推导出解决方法。另外，记住 `git reflog` 是最终的救命命令。

## 4. 接口调试篇 — Postman/Apifox 实战

> 后端写完接口后第一件事就是自己调试。一个能管理接口、自动化测试的调试工具，能让联调效率提升 50%

### 4.1 环境变量管理

用环境变量来管理不同环境的 URL 和 Token，避免每次手动替换：

```text
Postman 环境变量设置
-------------------------------
Variable          Initial Value                       Current Value
baseUrl-dev       http://localhost:8080/api/v1
baseUrl-staging   http://staging.company.com/api/v1
baseUrl-prod      http://api.company.com/v1
token             从 Login 接口自动获取

用法：{{baseUrl-dev}}/orders/{{orderId}}
```

> 💡 **最佳实践**：把环境独立成文件，团队成员通过 Git 同步。不要在接口 URL 里硬编码 IP 和端口。

### 4.2 Pre-request Script（自动获取 Token）

每次调试需要登录态的接口时，手动去拷贝 token 非常低效。Pre-request Script 可以在发送请求前自动执行：

```javascript
// Pre-request Script 示例：自动获取 token
// 在 Collection 级别的 Pre-request Script 中编写
const loginRequest = {
    url: pm.variables.get("baseUrl") + "/auth/login",
    method: 'POST',
    header: {
        'Content-Type': 'application/json'
    },
    body: {
        mode: 'raw',
        raw: JSON.stringify({
            username: 'test_user',
            password: 'test_password'
        })
    }
};

pm.sendRequest(loginRequest, (err, response) => {
    if (!err) {
        const token = response.json().data.token;
        // 将 token 设为集合变量，集合内所有请求都可以使用
        pm.collectionVariables.set("authToken", token);
    }
});
```

```text
变量引用：在请求 Header 中添加
  Authorization: Bearer {{authToken}}
```

**Apifox 中的等效操作：**

Apifox 支持前后置操作，同样可以编写 JS 脚本来自动获取 Token。此外 Apifox 的"参数构造"功能可以通过 UI 配置而非写代码来实现大部分前置操作，对不熟悉 JS 的开发者更友好。

### 4.3 Tests 断言脚本

在 Postman Tests 标签中写断言，自动验证响应是否符合预期：

```javascript
// Tests Script（请求发送后自动执行）
// 1. 检查 HTTP 状态码
pm.test("Status code is 200", () => {
    pm.response.to.have.status(200);
});

// 2. 检查响应结构
pm.test("Response has data field", () => {
    const jsonData = pm.response.json();
    pm.expect(jsonData).to.have.property("code", 200);
    pm.expect(jsonData).to.have.property("data");
});

// 3. 检查数组长度
pm.test("Order list has items", () => {
    const jsonData = pm.response.json();
    pm.expect(jsonData.data.records).to.have.lengthOf.at.least(1);
});

// 4. 检查字段值
pm.test("Order status is valid", () => {
    const jsonData = pm.response.json();
    pm.expect(jsonData.data.status).to.be.oneOf([0, 1, 2, 3]);
});

// 5. 响应时间检查（性能回归）
pm.test("Response time is acceptable", () => {
    pm.expect(pm.response.responseTime).to.be.below(500);
});
```

### 5.2 日常 SQL 操作

#### EXPLAIN 分析执行计划

```sql
-- 在 SQL 前加上 EXPLAIN，看执行计划
EXPLAIN SELECT o.*, u.name
FROM orders o
LEFT JOIN user u ON o.user_id = u.id
WHERE o.status = 1 AND o.create_time > '2026-01-01';

-- 重点关注输出中的关键字段：
-- type:         ALL（全表扫描）→ 需要优化
--               index（全索引扫描）→ 较好
--               range（范围扫描）→ 好
--               ref（非唯一索引查找）→ 好
--               const/system（唯一索引查找）→ 最优
-- possible_keys: 可能使用的索引
-- key:          实际使用的索引
-- rows:         扫描行数（越小越好）
-- Extra:        Using filesort → 排序未用索引
--               Using temporary → 用了临时表（要避免）
```

#### 慢查询查看

```sql
-- MySQL 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;  -- 超过1秒的查询
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';

-- 查看慢查询
SELECT * FROM mysql.slow_log ORDER BY start_time DESC LIMIT 10;

-- 用 pt-query-digest 分析慢查询日志
pt-query-digest /var/log/mysql/slow.log
```

#### 索引管理

```sql
-- 查看表索引
SHOW INDEX FROM orders;

-- 创建索引（注意命名规范：idx_表名_字段名）
CREATE INDEX idx_orders_status ON orders(status);
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- 复合索引（最左前缀原则）
CREATE INDEX idx_orders_status_time ON orders(status, create_time);

-- 查看 SQL 是否使用了索引
EXPLAIN SELECT * FROM orders WHERE status = 1 AND create_time > '2026-01-01';
-- 如果使用了 idx_orders_status_time，Extra 会显示 "Using index condition"
```

> ⚠️ **索引优化原则**：
> 1. 选择性高的字段放前面（区分度大的字段先放）
> 2. 不要在一个表上建太多索引（影响写入性能）
> 3. 不要对频繁更新的字段建索引
> 4. 索引不是越多越好，权衡查询效率和写入成本

### 5.4 生产环境操作安全规范

> ⚠️ **以下规范是血的教训换来的，请务必遵守！**

**第一条：先 SELECT 确认，再 UPDATE/DELETE**

```sql
-- 错误做法
UPDATE orders SET status = 2 WHERE user_id = 12345;

-- 正确做法
-- 第一步：先 SELECT 确认
SELECT id, status, user_id FROM orders WHERE user_id = 12345;

-- 第二步：确认无误后，用主键执行 UPDATE
-- ❌ 不要用 DELETE 或 UPDATE 不带 WHERE（除非你确实要全表操作）
UPDATE orders SET status = 2 WHERE id IN (1001, 1002, 1003);
```

**第二条：UPDATE/DELETE 加 LIMIT**

```sql
-- 分批删除/更新，防止大量锁行导致主从延迟
DELETE FROM order_logs WHERE create_time < '2025-01-01' LIMIT 1000;
-- 循环执行，直到影响行数为 0
```

**第三条：重要操作开启事务**

```sql
-- 在终端中操作
START TRANSACTION;

-- 执行更新操作
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 先检查数据是否正确
SELECT * FROM accounts WHERE id IN (1, 2);

-- 确认无误后提交
COMMIT;
-- 如果发现不对，ROLLBACK;
```

**第四条：不在生产环境直接修改数据（除非是紧急事故）**

```text
生产数据变更流程：
1. 提交 SQL 脚本 → Code Review
2. DBA 审核（如有）
3. 在变更窗口执行
4. 执行前备份
5. 执行后验证
6. 回滚方案就绪
```

> 🎯 **核心要点**：数据库操作的底线是"**不丢数据、不影响线上**"。一切操作都要遵循"先查后改、分批执行、事务保护、有备份"的原则。出了生产数据事故，轻则背 C 绩效，重则开除。

## 6. CI/CD 篇 — 自动化构建与部署

> 持续集成/持续部署是现代工程团队的标配。理解 CI/CD Pipeline，是后端面试的加分项

### 6.1 主流 CI/CD 工具对比

| 特性 | Jenkins | GitHub Actions | GitLab CI |
|------|---------|---------------|-----------|
| **部署方式** | 自建服务器 | SaaS（GitHub 提供） | 内置在 GitLab |
| **配置语言** | Jenkinsfile（Groovy） | YAML | YAML |
| **插件生态** | 极其丰富（1000+） | 丰富（Marketplace） | 丰富 |
| **学习曲线** | 较陡 | 平缓 | 中等 |
| **UI 体验** | 传统、功能强大但界面老 | 现代化 | 良好 |
| **费用** | 免费（需自建服务器） | 公共仓库免费，私有有限配额 | 自托管免费，SaaS 收费 |
| **适合场景** | 传统企业、复杂 Pipeline | 开源项目、GitHub 用户 | GitLab 用户 |

### 6.2 Java 项目典型 CI/CD Pipeline

```yaml
# GitHub Actions 示例：Java Spring Boot 项目
# 文件位置：.github/workflows/ci-cd.yml

name: Java CI/CD Pipeline

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  # Stage 1: 编译与单元测试
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'

      - name: Cache Maven dependencies
        uses: actions/cache@v4
        with:
          path: ~/.m2/repository
          key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}

      - name: Compile
        run: mvn compile

      - name: Run Unit Tests
        run: mvn test

      - name: Generate Test Report
        run: mvn surefire-report:report

  # Stage 2: 代码质量检查
  code-quality:
    needs: build-and-test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: SonarQube Scan
        uses: sonarsource/sonarqube-scan-action@master
        with:
          args: >
            -Dsonar.projectKey=my-java-project
            -Dsonar.host.url=${{ secrets.SONAR_HOST_URL }}
            -Dsonar.login=${{ secrets.SONAR_TOKEN }}

      - name: Checkstyle
        run: mvn checkstyle:check

  # Stage 3: 构建 Docker 镜像并推送
  build-and-push-image:
    needs: code-quality
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Build JAR
        run: mvn package -DskipTests

      - name: Build Docker Image
        run: docker build -t my-app:${{ github.sha }} .

      - name: Push to Registry
        run: |
          docker tag my-app:${{ github.sha }} registry.company.com/my-app:latest
          docker push registry.company.com/my-app:latest

  # Stage 4: 部署到测试环境
  deploy-to-staging:
    needs: build-and-push-image
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy to K8s
        run: |
          kubectl set image deployment/my-app my-app=registry.company.com/my-app:${{ github.sha }}
          kubectl rollout status deployment/my-app
```

**Pipeline 各阶段说明：**

```text
Java 项目标准 Pipeline 流程
═══════════════════════════════════════════════
                          ┌─────────────────┐
                          │   代码 Push      │
                          └────────┬────────┘
                                   ▼
                   ┌─────────────────────────────┐
                   │  Stage 1: 编译 + 单元测试   │
                   │  mvn compile + mvn test     │
                   │  失败 → 通知开发者           │
                   └────────────┬────────────────┘
                                ▼
                   ┌─────────────────────────────┐
                   │  Stage 2: 代码质量检查       │
                   │  SonarQube + Checkstyle     │
                   │  不达标 → 禁止合并           │
                   └────────────┬────────────────┘
                                ▼
                   ┌─────────────────────────────┐
                   │  Stage 3: 构建 JAR + 镜像   │
                   │  mvn package + docker build │
                   │  推送镜像到容器仓库          │
                   └────────────┬────────────────┘
                                ▼
                   ┌─────────────────────────────┐
                   │  Stage 4: 部署到目标环境     │
                   │  生产环境需人工审批          │
                   │  灰度发布 → 全量发布         │
                   └─────────────────────────────┘
```

### 6.3 如何看懂 Pipeline 日志定位构建失败

Pipeline 构建失败时，不要直接截图扔群里问人，自己先定位：

```bash
# 1. 看 Stage 名称：哪个 Stage 失败了？
#   - "build-and-test" 失败 → 编译错误或单元测试失败
#   - "code-quality" 失败 → 代码规范不达标
#   - "build-and-push-image" 失败 → Docker 构建问题

# 2. 看具体 Job 的输出日志
# 在 Jenkins / GitHub Actions 界面中，展开失败的 Stage
# 搜索关键字：
#   - "ERROR"、"FAILURE"、"BUILD FAILURE"
#   - "Exception"、"NullPointerException"
#   - "Test failures: 1"

# 3. 常见失败原因快速定位

# 编译错误
[ERROR] Failed to execute goal compile on project ...
# → 本地先 mvn compile，修复编译错误后重新提交

# 测试失败
[INFO] Tests run: 100, Failures: 3, Errors: 0
# → 到 surefire-reports 目录看具体哪个测试用例失败
# → target/surefire-reports/xxxTest.txt

# 镜像构建失败
Step 1/10 : FROM openjdk:17-jdk-alpine
Get https://...: dial tcp: lookup
# → 网络问题，检查 Docker 镜像源或代理配置

# 部署失败
Error from server (InternalError): ...
# → K8s 配置问题，检查 yaml 格式、Secret 是否存在
```

> 💡 **面试加分项**：面试被问"你们 CI/CD 怎么做的"，不仅要能说 Pipeline 的流程，最好能讲一个"CI/CD 帮你抓住了什么 Bug"的具体例子。比如："有一次我在本地跑测试全过，但 CI 上发现了一个环境相关的测试失败，原来是 application-test.yml 里配置的数据库密码不对..." —— 这种细节能证明你真的在 CI/CD 环境下工作过。

> 🎯 **核心要点**：CI/CD 的核心价值是"把验证流程自动化"，让每行代码在合并之前都经过了编译、测试、质量检查。面试时重点展示对 Pipeline 各阶段的理解，以及遇到构建失败时的排查思路。

## 7. 监控告警篇 — Prometheus + Grafana

> 系统上线只是开始，确保系统持续健康运行才是后端工程师的日常。监控告警是你了解系统运行状态的"眼睛"

### 7.1 日常需要关注的监控指标

```text
后端服务核心监控指标体系
═══════════════════════════════════════

┌─ 业务指标 (Business)
│   QPS (每秒请求数)       → 当前流量大小 → 突增可能异常或营销活动
│   RT (响应时间)          → P50/P90/P99   → 接口性能是否劣化
│   错误率                  → 5xx / 业务异常 → 是否有 Bug 或依赖故障
│   调用量趋势              → 和周/日环比   → 同比变化是否正常
│
├─ 应用指标 (Application)
│   JVM 堆内存             → GC 频率/停顿  → 内存泄漏? 对象分配过快?
│   线程数 / 线程池状态    → 活跃线程/等待队列 → 线程池打满?
│   数据库连接池           → 活跃连接/等待  → 连接池不够?
│   接口超时率             → Feign/DB/Redis超时 → 下游依赖故障
│
├─ 基础设施指标 (Infrastructure)
│   CPU 使用率             → 是否达到上限  → 扩容评估
│   内存使用率             → 是否存在泄漏  → OOM 风险
│   磁盘使用率             → 日志是否撑满  → 磁盘告警
│   网络 IO / 磁盘 IO     → 是否成为瓶颈 → 限流/扩容
│
└─ 中间件指标 (Middleware)
    Redis: 内存使用 / 命中率 / 慢查询
    MySQL: QPS / 慢查询 / 连接数 / 主从延迟
    MQ:    堆积量 / 消费延迟 / 重试次数
```

### 7.2 Grafana 大盘解读

一个标准的后端 Grafana 大盘通常包含以下面板：

```text
Grafana 服务监控大盘布局
═══════════════════════════════════════

第一行：整体概览（红色/黄色/绿色状态）
  ├── 服务健康状态 | 错误率 | QPS 总量 | 平均 RT
  └── 本周和上周对比趋势图

第二行：业务指标
  ├── 各接口 QPS Top10（柱状图：哪些接口流量最大）
  ├── 各接口 RT P99（柱状图：哪些接口最慢）
  ├── HTTP 状态码分布（饼图：200/4xx/5xx 比例）
  └── 错误率趋势（折线图：随时间变化）

第三行：应用指标
  ├── JVM 堆内存使用（堆区/非堆区/元空间）
  ├── GC 次数与耗时（Young GC / Full GC）
  ├── 活跃线程数（Tomcat 线程池）
  └── 数据库连接池大小

第四行：中间件指标
  ├── MySQL 慢查询数量
  ├── Redis 命中率
  └── MQ 消息堆积量

底部：告警事件时间线
  └── 当天触发的告警列表
```

**检查大盘的日常节奏：**

```text
每天早上到工位后，花 3 分钟看监控：
1. ✅ 先看 "健康状态" 是不是绿色（红色立刻处理）
2. 📈 看 QPS 和 RT 曲线：昨晚到今早有没有异常波动
3. ⚠️ 看错误率：有没有突增的 5xx
4. 💾 看 GC 和内存：有没有内存泄漏迹象（GC 频率增加）
5. 📋 看告警时间线：晚上有没有 P2/P3 告警需要处理
```

### 7.3 收到告警后的排查路径

```text
收到告警 → 系统排查标准路径
═══════════════════════════════════════

Step 1: 确认告警级别
  ├── P0 (系统不可用) → 立即响应，放下手中一切工作
  ├── P1 (核心功能受损) → 30分钟内响应
  ├── P2 (非核心功能异常) → 当天处理
  └── P3 (告警通知) → 正常工作时间内处理

Step 2: 打开 Grafana 看大盘
  ├── 确认是整体故障还是单机故障
  ├── 看是哪个指标触发了告警（CPU? 内存? 错误率?）
  └── 看故障开始的时间点

Step 3: 查看日志（Kibana / ELK）
  ├── 以故障时间点为起点搜索 ERROR 日志
  ├── 搜索关联 TraceID
  └── 定位具体异常堆栈

Step 4: 查看 APM（链路追踪，如 SkyWalking / Zipkin）
  ├── 看慢调用链（哪个环节最慢）
  ├── 看调用关系（是自身 Bug 还是下游故障）
  └── 看 DB/Redis/MQ 的调用耗时

Step 5: 如果紧急 → 止血（回滚/重启/降级）
  ├── 先恢复服务（止血优先于定位根因）
  └── 再定位根因（发布变更回滚/代码修复）

Step 6: 复盘与改进
  ├── 写事故报告（What / Why / How / Action Items）
  └── 增加监控告警 + 增加自动化测试
```

> ⚠️ **止血第一原则**：线上事故的核心原则是"先止血，再排查"。只要影响了用户，第一时间回滚版本、重启服务、或者切流量到备用集群。不要一上来就分析代码，先把服务恢复了再说。

> 🎯 **核心要点**：面试时被问到"线上出了故障怎么排查"，展示的不仅仅是你对工具的了解，更重要的是**方法论和排查路径**——从告警到大盘到日志到 APM 再到止血，每一步都要有清晰的思路。

### 8.3 代码即文档的理念

优秀代码本身就是最好的文档。以下几点是"代码即文档"的实践：

```java
// ❌ 糟糕的代码 + 注释（注释说的是废话）
// 获取用户信息
public UserVO getInfo(Long id) {
    // 查用户
    User user = userMapper.selectById(id);
    // 转VO
    UserVO vo = new UserVO();
    vo.setName(user.getUsername());
    vo.setMail(user.getEmail());
    return vo;
}

// ✅ 自文档化的代码（方法名 + 变量名清晰地表达了逻辑）
public UserVO getUserProfile(Long userId) {
    User user = userRepository.findById(userId);
    return UserVOAssembler.toUserProfile(user);
}

// ✅ 复杂的业务逻辑用注释说明"为什么"，而不是"是什么"
/**
 * 使用分布式锁防止重复下单。
 * 
 * 原因：用户快速点击提交按钮时，前端可能连续发送两个请求。
 * 方案：Redis 分布式锁，key = "lock:order:create:" + userId，过期时间 5 秒。
 * 补充：不直接使用数据库唯一索引，因为订单号生成在 Service 层内。
 */
public Long createOrder(OrderCreateRequest request) {
    String lockKey = "lock:order:create:" + request.getUserId();
    RedisLock lock = redisLockManager.acquire(lockKey, 5, TimeUnit.SECONDS);
    // ...
}
```

```text
自文档化代码的核心原则：
1. 方法名要能准确描述做了什么（getUserById 而不是 getData）
2. 变量名要有含义（activeUsers 而不是 list）
3. 复杂分支逻辑要加注释说明原因
4. 不要给"显而易见"的代码加注释（纯属噪声）
5. README / Wiki 写清楚"如何跑起来"和"项目结构"
```

> 🎯 **核心要点**：文档的价值是"**让别人（包括未来的你）能快速理解**"。不管是个人笔记还是团队文档，都要考虑"如果半年后我回来看这个，能秒懂吗？" 坚持记笔记和写文档，一年后你会感谢自己。
