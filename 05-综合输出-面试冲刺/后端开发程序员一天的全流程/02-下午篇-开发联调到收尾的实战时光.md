## 1. 13:30-14:00 午后热身

### 1.1 午休后的状态恢复技巧

午休后的大脑处于"睡眠惯性"状态，直接进入高难度编码会效率极低。建议采用以下恢复策略：

| 阶段 | 时间 | 动作 | 目的 |
|------|:----:|------|------|
| 唤醒期 | 13:30-13:35 | 起身接水、洗把脸、做2次深呼吸 | 物理唤醒 |
| 信息期 | 13:35-13:45 | 浏览未读消息、邮件、Merge Request通知 | 信息同步 |
| 进入期 | 13:45-14:00 | 选择一个低认知负荷的任务启动 | 热脑启动 |

> 💡 **技巧**：下午开工不要直接写复杂逻辑。先做**代码Review**或**回复消息**这类轻量任务，让大脑逐步进入状态。

## 2. 14:00-15:30 前后端联调实战

### 2.1 联调前准备

联调失败的根因 80% 是准备不足。联调前必须确认以下事项：

**Checklist：**

| # | 检查项 | 验收标准 | 负责人 |
|---|--------|----------|--------|
| 1 | API 文档已更新 | Swagger/Apifox 文档与实际接口一致 | 后端 |
| 2 | Mock 数据就绪 | 前后端约定的 Mock 数据已配置 | 前后端 |
| 3 | 联调环境部署完成 | Dev/Test 环境已部署最新代码 | 运维/后端 |
| 4 | 接口参数确认 | Request/Response 字段与前端对齐 | 前后端 |
| 5 | 异常场景约定 | 约定错误码格式、异常响应结构 | 前后端 |
| 6 | 联调工具就绪 | Postman/Apifox 集合已准备好 | 后端 |

> 💡 **最佳实践**：在每日站会（或上午）就约好下午联调的时间窗口，给双方留出准备时间。

### 2.2 联调标准流程

```
单接口自测 → 联调环境部署 → 接口对接 → 异常场景覆盖 → 联调通过
```

**Step 1: 单接口自测（后端独立完成）**

后端在联调前，必须先用 Postman/Apifox 对每个接口完成自测：

```json
// Postman Tests 脚本示例
pm.test("状态码为 200", function () {
    pm.response.to.have.status(200);
});

pm.test("响应格式正确", function () {
    var jsonData = pm.response.json();
    pm.expect(jsonData).to.have.property("code", 0);
    pm.expect(jsonData).to.have.property("data");
    pm.expect(jsonData.data).to.have.property("items").that.is.an("array");
});

pm.test("分页参数正确", function () {
    var jsonData = pm.response.json();
    pm.expect(jsonData.data.total).to.be.at.least(0);
    pm.expect(jsonData.data.pageNum).to.equal(1);
});
```

**Step 2: 联调环境部署**

```bash
# 部署到 Dev 环境
mvn clean package -DskipTests
scp target/app.jar user@dev-server:/opt/app/
ssh user@dev-server "systemctl restart app"

# 或通过 Jenkins 触发部署
curl -X POST http://jenkins.example.com:8080/job/deploy-dev/build \
  --user "username:apitoken" \
  --data-urlencode "BRANCH_NAME=feature/order-list-api"
```

**Step 3: 接口对接**

前后端坐在联调环境前，逐个接口验证：

| 阶段 | 动作 | 工具 | 预期结果 |
|------|------|------|----------|
| 正向流程 | 前端调用接口，后端处理 | Chrome DevTools / ApiFox | 接口正常返回 200 |
| 参数校验 | 传递非法参数 | ApiFox | 后端返回参数校验错误 |
| 鉴权测试 | 不带 Token、过期 Token | ApiFox | 返回 401/403 |
| 数据边界 | 空数据、大数据量 | 构造极端数据 | 后端正常处理 |
| 并发场景 | 同一接口多次快速调用 | Postman Runner | 无数据竞争异常 |

**Step 4: 异常场景覆盖**

| 异常场景 | 模拟方式 | 预期表现 |
|----------|----------|----------|
| 数据库超时 | 在 SQL 中加入 `SLEEP(30)` | 接口超时、前端友好提示 |
| 第三方服务不可用 | 停掉下游 Mock 服务 | 熔断降级、返回兜底数据 |
| 参数缺失 | 前端不传必填字段 | 后端返回 400 + 明确错误信息 |
| 数据不存在 | 请求不存在的 ID | 返回 404 或业务错误码 |
| 并发请求 | Postman Runner 并发 50 次 | 接口无死锁、无数据异常 |

### 2.3 联调中的常见问题和解决方案

| 问题 | 现象 | 排查方向 | 解决方案 |
|------|------|----------|----------|
| 跨域问题 CORS | 浏览器提示 `No 'Access-Control-Allow-Origin'` | 后端 Nginx/Gateway 配置 | 添加 `Access-Control-Allow-Origin: *` 或指定域名 |
| 参数格式不一致 | 前端传 Snake Case，后端用 Camel Case | 前后端参数命名约定 | 统一 JSON 字段命名规范，使用 `@JsonProperty` |
| 数据类型不匹配 | 前端传 String 类型 ID，后端用 Long | 参数类型 | 后端做好类型兼容，或前端传正确类型 |
| 鉴权 Token 过期 | 接口返回 401 | Token 有效期配置 | 检查 Token 过期时间和刷新机制 |
| 数据库主键冲突 | Insert 时报 Duplicate Key | 分布式 ID 生成策略 | 使用雪花算法或 Redis 自增 ID |
| 时区不一致 | 时间字段差了 8 小时或 14 小时 | 前后端时区配置 | 统一用 UTC 传输，前端展示时转换本地时间 |

> ⚠️ **经验之谈**：联调中最坑的不是逻辑问题，而是约定不一致的问题。**提前约定好接口规范**，能省 80% 的联调时间。

### 2.4 联调对话示例

#### 反面示例（差的联调对话）

> **前端**：那个订单列表的接口返回 500 了，你看看吧。
>
> **后端**：我这边测试没问题啊，你是不是传错了参数？
>
> **前端**：我按你文档传的，文档里写的是 `orderId`，但接口返回说字段不存在。
>
> **后端**：哦那个，文档没更新，实际是 `order_no`。
>
> **前端**：……那你先把文档更新了再喊我联调。

> 🎯 **教训**：文档不同步、态度推诿、信息不透明——这是最差劲的联调协作。

#### 正面示例（好的联调对话）

> **后端**：@前端 订单列表接口（`GET /api/orders`）已部署到 dev 环境，请求参数和响应示例见 [Apifox 链接]，当前时间字段用 timestamp 毫秒值传。联调前我做了自测，正向流程和参数校验都过了。
>
> **前端**：收到，我刚调了 `GET /api/orders`，正向流程 OK。但发现时间字段返回的 `2026-07-28T10:30:00Z` 格式，前端展示需要本地时间，要不要统一用时间戳？
>
> **后端**：好的，我统一改成时间戳毫秒值，预计 5 分钟改完重新部署，改完后 @你。
>
> **前端**：好嘞，那同时我确认一下：**分页参数** 是 `pageNum/pageSize`，起始值是 1 对吗？
>
> **后端**：对，pageNum 从 1 开始，pageSize 最大 100，超了会限制为 100。

> 🎯 **核心要点**：好的联调是**信息透明、及时回应、主动同步**。后端要主动提供联调信息，前端要清楚确认每个参数。

### 2.5 如何写一份前端看了不骂人的接口文档

#### API 文档规范清单

| 必须项 | 示例 | 原因 |
|--------|------|------|
| 接口说明 | "获取用户订单列表，支持分页和状态筛选" | 让前端知道这是什么接口 |
| 请求方法 + URL | `GET /api/v1/orders` | 基础信息 |
| 请求参数描述 | 参数名、类型、是否必填、默认值、说明 | 减少沟通成本 |
| 请求参数示例 | `{"pageNum": 1, "pageSize": 20, ...}` | 清晰直观 |
| 响应结构示例 | `{"code": 0, "data": {...}, "msg": "success"}` | 便于解析 |
| 错误码说明 | `1001: 参数错误 / 1002: 无权限 / 1003: 订单不存在` | 前端展示错误 |
| 字段类型说明 | `orderId: Long / status: Integer(0-待支付,1-已支付)` | 减少类型歧义 |

#### Apifox/Swagger 配置示例

```yaml
# Swagger 注解示例
@Api(tags = "订单管理")
@RestController
@RequestMapping("/api/v1/orders")
public class OrderController {

    @ApiOperation("获取用户订单列表")
    @ApiImplicitParams({
        @ApiImplicitParam(name = "pageNum", value = "页码", required = true, dataType = "int", example = "1"),
        @ApiImplicitParam(name = "pageSize", value = "每页条数", required = true, dataType = "int", example = "20"),
        @ApiImplicitParam(name = "status", value = "订单状态: 0-待支付, 1-已支付, 2-已取消", dataType = "int", example = "0")
    })
    @GetMapping
    public Result<PageResult<OrderVO>> list(@Valid PageParam pageParam, @RequestParam(required = false) Integer status) {
        return Result.success(orderService.list(pageParam, status));
    }
}
```

// Pre-request Script (自动刷新 Token)
const tokenExpireTime = pm.environment.get("token_expire_time");
const now = Date.now();

if (!tokenExpireTime || now > parseInt(tokenExpireTime)) {
    pm.sendRequest({
        url: pm.environment.get("base_url") + "/auth/refresh",
        method: "POST",
        header: { "Authorization": "Bearer " + pm.environment.get("refresh_token") }
    }, function (err, res) {
        if (!err) {
            const jsonData = res.json();
            pm.environment.set("token", jsonData.data.token);
            pm.environment.set("token_expire_time", String(now + 7200000));
        }
    });
}
```

## 3. 15:30-16:30 Code Review 与 Bug 修复

### 3.1 Code Review (CR) 全流程

#### 3.1.1 提交 CR 前的自查清单

在提交 Merge Request / Pull Request 之前，开发者应当自查以下内容：

**代码规范自查：**

| 检查项 | 说明 | 检查方法 |
|--------|------|----------|
| 命名规范 | 类名/方法名/变量名符合项目规范 | 肉眼 + CheckStyle |
| 注释规范 | 关键逻辑有注释、API 有 JavaDoc | 肉眼 |
| 代码风格 | 缩进、空行、括号风格一致 | `mvn checkstyle:check` |
| 无用代码 | 没有 System.out / TODO / 注释掉的代码 | `grep -r "TODO\|System.out" src` |
| 日志规范 | 使用 SLF4J Logger，日志级别合理 | 肉眼 |
| 异常处理 | 不吞异常、异常信息有意义 | 肉眼 |

**测试覆盖：**

| 检查项 | 说明 |
|--------|------|
| 新增方法有单元测试 | Controller/Service/DAO 层覆盖 |
| 边界条件覆盖 | 空值、非法参数、大数据量 |
| 测试全部通过 | `mvn test` 或 CI 运行通过 |

**安全自查：**

```java
// ❌ 危险：SQL 拼接
String sql = "SELECT * FROM user WHERE id = " + id;

// ✅ 安全：参数化查询
String sql = "SELECT * FROM user WHERE id = ?";
jdbcTemplate.query(sql, id, userRowMapper);
```

```java
// ❌ 危险：用户输入直接返回
return userInput;

// ✅ 安全：XSS 过滤 / HTML 转义
return HtmlUtils.htmlEscape(userInput);
```

**性能自查：**

| 检查项 | 说明 |
|--------|------|
| N+1 查询问题 | 排查循环内查询数据库 |
| 大批量数据内存处理 | 使用分页或流式处理 |
| 无用对象创建 | 避免循环内 new 对象 |
| 缓存是否合理 | 热点数据是否加缓存 |

#### 3.1.2 如何写好的 PR 描述

**PR 模板：**

```markdown
## 背景
[为什么需要这个变更？关联的 Jira/Tapd 需求链接]

## 变更内容
- [功能1] 新增订单列表筛选接口
- [优化2] 重构订单状态机，去掉 if-else 链
- [修复3] 修复订单超时未取消的 Bug

## 技术方案
- 使用策略模式替代原有的 switch-case
- 缓存热点状态数据到 Redis，减少 DB 查询

## 影响范围
- 涉及表：order（新增 status_time 字段）
- 涉及接口：GET /api/v1/orders
- 涉及配置：新增 order.timeout.minutes=30

## 测试情况
- 单元测试覆盖 95%（新增 15 个测试用例）
- 手动测试场景：正向流程、异常参数、超时取消

## 部署注意
- 执行 SQL 脚本：V20260728_01_add_status_time.sql
- 无需重启即可热更新
```

**反例（差的 PR 描述）：**

```markdown
## 标题：修复Bug
## 描述：修了几个Bug，代码改了一些，你们review一下。
```

> 💡 **好 PR 的标准**：Reviewer 看完描述就能理解你做了什么、为什么做、影响范围，不需要再问你一遍。

#### 3.1.3 作为 Reviewer 的检查清单

**业务逻辑：**

| 检查项 | 说明 |
|--------|------|
| 是否覆盖所有业务场景 | 正常/异常/边界 |
| 有无遗漏校验 | 参数校验、权限校验、状态校验 |
| 业务规则是否正确 | 与产品文档/需求一致 |

**代码质量：**

| 检查项 | 说明 |
|--------|------|
| 可读性 | 代码是否自解释、是否需要过多注释 |
| 扩展性 | 是否硬编码、是否便于后续扩展 |
| 设计模式 | 是否有更好的设计模式方案 |
| 重复代码 | 是否抽取了公共方法/工具类 |

**安全：**

- 是否有 SQL 注入风险
- 是否有 XSS 风险
- 是否有越权问题（水平/垂直越权）
- 敏感数据是否脱敏

**性能：**

- 循环内查询数据库（N+1）
- 大批量数据一次性加载到内存
- 无索引字段查询
- 锁的粒度是否过粗

**测试：**

- 测试是否覆盖了核心逻辑
- 测试命名是否规范（`methodName_condition_expectedResult`）
- 是否用了 Mock 来隔离外部依赖

#### 3.1.4 CR 评论的礼仪规范

**核心原则：对代码不对人。**

| 差的评论 | 好的评论 |
|----------|----------|
| "这段代码写得有问题" | "这里用 `List.contains()` 做大量查询是 O(n^2)，建议改成 `Set` 来优化" |
| "你忘了处理异常" | "这里的 `findUser()` 可能抛 `UserNotFoundException`，建议加上异常处理" |
| "这命名什么鬼" | "`getData()` 太笼统了，建议改成 `getUserOrderList()` 更清晰" |
| "你这段代码重复了" | "这块逻辑和第 50 行重复了，建议抽成一个公共方法" |

> 💡 **CR 礼仪四步法**：
> 1. **先说优点**："整体逻辑清晰，测试覆盖全面"
> 2. **再说问题**："不过有一个小建议..."
> 3. **给解决方案**："我们可以改成...，理由是这样..."
> 4. **表达支持**："改完这部分我觉得就可以合了"

#### 3.1.5 CR 对话示例

**差的 CR 评论：**

> **Reviewer**：你这个 `UserServiceImpl` 写了 800 行，太臃肿了，拆一下。
>
> **Author**：哪里臃肿了？逻辑都在这里，拆了反而不好维护。
>
> **Reviewer**：你自己看看，这里面既有订单逻辑又有用户逻辑，职责不清。
>
> **Author**：那我拆成两个 Service？那还要改 Controller 引用。
>
> **Reviewer**：你自己决定吧，反正我觉得要拆。

> 🎯 **教训**：只抛出问题不给方案、态度生硬→引发无效争论。

**好的 CR 评论：**

> **Reviewer**：建议把 `UserServiceImpl` 拆一下，因为这里有订单统计的逻辑，放到 `OrderStatisticService` 会更合适，后续维护也方便。我可以一起改，或者我来协助你拆。
>
> **Author**：有道理，我这里确实混了订单逻辑和用户逻辑。我来拆吧，预计半小时改完。
>
> **Reviewer**：好的，辛苦。拆完后注意引入依赖的循环引用问题，可以考虑用接口隔离。

### 3.2 Bug 修复流程

#### 3.2.1 标准修复流程

```
收到 Bug 报告 → 复现 Bug → 定位根因 → 修复代码 → 验证修复 → 回归测试 → 关闭
```

**Step 1: 复现 Bug**

```bash
# 查看线上日志，找到错误上下文
kubectl logs --tail=500 -n production pod/app-xxx | grep "ERROR\|Exception" | head -20

# 使用 Arthas 线上诊断（如果环境允许）
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar

# 在 Arthas 中查看异常堆栈
stack com.example.service.OrderService createOrder
watch com.example.service.OrderService createOrder '{params, throwExp}' -x 2
```

**Step 2: 定位根因**

| 排查方向 | 工具 | 说明 |
|----------|------|------|
| 日志分析 | ELK / Loki / Graylog | 搜索关键 Error Message |
| 链路追踪 | SkyWalking / Zipkin / Jaeger | 查看调用链上的耗时和异常 |
| 数据库 | `SHOW ENGINE INNODB STATUS` | 查看死锁、锁等待 |
| JVM 监控 | Arthas / JVisualVM | 线程堆栈、内存快照 |
| 请求追踪 | 接口日志 TraceId | 串联一次请求的完整链路 |

**Step 3: 修复代码**

```java
// 修复前：空指针隐患
public OrderVO getOrder(Long orderId) {
    Order order = orderMapper.selectById(orderId);
    return OrderConverter.toVO(order);  // order 可能为 null
}

// 修复后：空值处理
public OrderVO getOrder(Long orderId) {
    if (orderId == null) {
        throw new IllegalArgumentException("orderId 不能为空");
    }
    Order order = orderMapper.selectById(orderId);
    if (order == null) {
        throw new OrderNotFoundException("订单不存在: " + orderId);
    }
    return OrderConverter.toVO(order);
}
```

**Step 4: 验证修复**

```bash
# 本地单元测试
mvn test -Dtest=OrderServiceTest

# 接口测试（使用 Postman 或 curl）
curl -X GET "http://localhost:8080/api/v1/orders/INVALID_ID" -H "Authorization: Bearer $TOKEN"

# 验证异常场景返回是否符合预期
```

#### 3.2.2 Bug 优先级分类

| 优先级 | 定义 | 响应时间 | 修复时限 | 示例 |
|--------|------|:--------:|:--------:|------|
| P0 | 核心功能不可用，影响全部用户 | 5分钟 | 立即修复 | 用户无法登录、支付接口500 |
| P1 | 核心功能受影响，影响部分用户 | 15分钟 | 2小时内 | 某个品类商品搜索不到 |
| P2 | 非核心功能异常，有临时规避方案 | 1小时 | 下个版本 | 导出报表格式不对 |
| P3 | 体验问题，不影响功能 | 次日 | 后续迭代 | 页面按钮没对齐 |

#### 3.2.3 常见 Bug 类型与排查方向

| Bug 类型 | 典型现象 | 排查方向 | 常见原因 |
|----------|----------|----------|----------|
| 空指针 NPE | `NullPointerException` | 检查链式调用、查库结果 | 未判空、远程调用失败返回 null |
| 数据错乱 | 金额不对、状态不对 | 检查事务、并发控制 | 并发无锁、事务未回滚 |
| 性能问题 | 接口响应 > 3s | 慢 SQL、死循环、锁等待 | SQL 没索引、代码 O(n^2)、锁冲突 |
| 数据丢失 | 记录没了、数据没入库 | 检查事务提交、消息消费 | 事务未 commit、MQ 消费失败丢消息 |
| 权限异常 | 不该看到的数据看到了 | 检查权限校验逻辑 | 水平越权、未做数据权限过滤 |
| 环境差异 | 本地正常，线上出问题 | 配置、依赖版本、JDK 版本 | 配置文件不同、MySQL/ES 版本差异 |

> 🎯 **核心要点**：Bug 修复的黄金法则是**先复现再修，先写测试再改代码**。没有复现步骤的 Bug 修复是盲人摸象。

```markdown
# 技术方案：订单超时自动取消

## 1. 背景与目标
- 当前问题：用户下单未支付，系统未自动取消，导致库存被占用
- 业务目标：下单后 30 分钟未支付自动取消订单，释放库存
- 技术目标：高可用、低延迟、不丢消息

## 2. 方案对比

| 方案 | 实现方式 | 优势 | 劣势 | 推荐 |
|------|----------|------|------|:----:|
| A-定时任务扫描 | `@Scheduled` 每30s扫一次 | 实现简单 | 扫描压力大、实时性差 | ❌ |
| B-DelayQueue | JVM 延迟队列 | 实时性好 | 应用重启丢数据 | ❌ |
| C-Redis ZSet | ZSet 按时间排序，轮询过期 Key | 实时性好、支持持久化 | 需额外开发 | ✅ |
| D-MQ 延时消息 | RocketMQ 延时消息 | 成熟可靠 | 需引入 MQ | 可选项 |

## 3. 详细设计（以方案 C 为例）

### 3.1 核心流程
```text
用户下单 → 写入订单表 + 写入 Redis ZSet → 定时任务扫描 ZSet →
发现过期订单 → 查询订单状态确认未支付 → 取消订单 → 
释放库存 → 发送通知消息
```

### 3.2 关键代码
// OrderTimeoutTask.java
@Component
@Slf4j
public class OrderTimeoutTask {
    
    @Autowired
    private RedisTemplate<String, String> redisTemplate;
    
    @Scheduled(fixedDelay = 5000)  // 每 5s 执行一次
    public void processTimeoutOrders() {
        long now = System.currentTimeMillis();
        // 获取 30 分钟前到现在所有过期的订单
        Set<String> orderIds = redisTemplate.opsForZSet()
            .rangeByScore(ORDER_TIMEOUT_KEY, 0, now);
        
        for (String orderId : orderIds) {
            handleTimeoutOrder(orderId);
        }
    }
}

## 4. 风险评估

| 风险 | 影响 | 应对方案 |
|------|------|----------|
| Redis 宕机 | 无法检测取消 | 兜底：重启后扫描所有未支付订单 |
| 重复取消 | 业务异常 | 数据库乐观锁 + 状态判断 |
| 并发取消 | 数据不一致 | 分布式锁保障同一个订单同时只有一个处理 |
