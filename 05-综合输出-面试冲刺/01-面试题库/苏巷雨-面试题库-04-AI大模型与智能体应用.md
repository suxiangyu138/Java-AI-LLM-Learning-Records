## 一、大模型基础原理

### 1. 大语言模型（LLM）的基本原理是什么？

**核心架构**：Transformer（"Attention Is All You Need"，2017）。

**关键组件**：
- **Self-Attention（自注意力）**：每个 token 关注序列中所有其他 token，计算关联权重
- **Multi-Head Attention（多头注意力）**：多组并行的注意力，每组关注不同的语义关系
- **Feed-Forward Network（前馈网络）**：对每个 token 做非线性变换
- **Layer Normalization + Residual Connection**：稳定训练，支持深层堆叠

**训练流程**：
1. **预训练（Pre-training）**：海量文本（TB 级），预测下一个 token（Next Token Prediction），学到通用语言能力
2. **监督微调（SFT）**：用高质量问答数据微调，让模型学会遵循指令
3. **RLHF（人类反馈强化学习）**：训练奖励模型 → PPO 算法优化模型输出，对齐人类偏好

**推理时的自回归生成**：
```
输入："今天天气"
→ 模型预测下一个 token："真"（概率最高）
→ 输入变为 "今天天气真"
→ 预测下一个："好"
→ ... 直到输出 <EOS> 结束标记
```

📌 **项目实践（Flavor Dash LLM Client Factory）**：在设计 SSE 流式输出和上下文窗口管理时，必须深刻理解自回归生成的 token 级别机制。流式输出利用逐 token 生成特性，通过 SSE 将每个 token 实时推送给前端，实现打字机效果。上下文窗口管理通过 token 预估算提前截断历史，避免超出模型限制。自回归的"下一个 token 预测"机制直接决定了流式输出的实现方式和上下文管理的策略选择。

### 2. Transformer 的 Self-Attention 是怎么计算的？

```
输入序列 X：[batch, seq_len, d_model]

1. 通过三个权重矩阵得到 Q、K、V：
   Q = X · W_Q    查询（Query）
   K = X · W_K    键（Key）
   V = X · W_V    值（Value）

2. 计算注意力分数：
   Score = Q · K^T / √d_k    ← 除以 √d_k 防止点积过大导致 softmax 梯度消失

3. 归一化为注意力权重：
   Attention_Weights = softmax(Score)

4. 加权求和：
   Output = Attention_Weights · V

最终公式：
Attention(Q,K,V) = softmax(Q·K^T / √d_k) · V
```

**直观理解**：
- Q（查询）："我在找什么？"
- K（键）："我有什么标签？"
- V（值）："我的内容是什么？"
- 注意力权重 = Q 和 K 的匹配程度 → 决定从每个 V 中取多少信息

**Masked Self-Attention（Decoder 中）**：用上三角掩码屏蔽未来位置的 token，保证生成时只能看到已生成的 token（自回归）。

📌 **项目实践（Flavor Dash RAG 管线）**：理解多头注意力机制帮助调试 RAG 上下文质量问题。当检索文档相关性低时，可追溯模型如何关注长上下文中的不同片段——通过分析注意力权重分布，发现模型是否忽略了关键文档或过度关注噪声内容。这一认知直接指导文档分块策略优化（如重叠分块、语义分块），确保检索到的文档块在注意力范围内保留完整语义。

### 3. Token 和 Tokenizer 是什么？Token 计数为什么重要？

**Token**：模型处理文本的最小单位。不是字也不是词，而是子词（subword）。

**Tokenizer**：文本 → Token 序列。
- **BPE**（Byte Pair Encoding）：常用的子词分词。英语中约 1 token ≈ 0.75 个单词，中文中约 1 个汉字 ≈ 1~2 token
- 例："ChatGPT is great" → ["Chat", "G", "PT", " is", " great"]，5 tokens

**为什么 Token 计数重要？**
- **上下文窗口有限**：gpt-4o-mini 128K tokens，deepseek-chat 128K。超出窗口 → 截断或报错
- **成本**：API 按 token 计费（input $0.15/1M，output $0.6/1M 左右）
- **你的项目实践（Flavor Dash 的 LLM Client Factory）**：`LLMGateway` 中有 `countTokens(text)` 方法，输入前估算 token 数，超出窗口则自动截断对话历史。主动截断策略使 API 拒绝错误减少约 30%，每次请求 token 浪费减少约 15%。

```java
// 粗略估算（不作为精确值，用于预判断）
public int estimateTokens(String text) {
    // 中文：约 1 字符 ≈ 1 token
    // 英文：约 4 字符 ≈ 1 token
    int chineseChars = countChinese(text);
    int otherChars = text.length() - chineseChars;
    return chineseChars + (otherChars / 4);
}
```

### 4. 模型的 Temperature 和 Top-P 是什么？

**Temperature（温度）**：控制输出的随机性。
- **低温度（0~0.3）**：输出更确定、保守，适合代码生成、事实问答
- **高温度（0.7~1.0）**：输出更多样、创新，适合创意写作、头脑风暴
- 原理：logits / temperature → softmax（温度越低概率分布越尖锐，高概率 token 被选中的概率更高）

**Top-P（Nucleus Sampling，核采样）**：
- 从累积概率达到 P 的最小 token 集合中随机采样
- Top-P=0.9：只从概率最高的、累积概率 ≥ 90% 的 token 中采样
- 裁剪掉长尾低概率 token，既保证多样性又避免胡言乱语

**Top-K**：只从概率最高的 K 个 token 中采样。

**你项目中的使用**：
- Flavor Dash AI 客服：Temperature=0.3（需要准确答案） + Top-P=0.8
- SuGuangMall 智能推荐描述生成：Temperature=0.7（需要多样性） + Top-P=0.9
- LingShu 医疗问诊：Temperature=0.1（极度保守，幻觉零容忍）

### 5. 什么是模型幻觉？为什么会产生？怎么缓解？

**幻觉（Hallucination）**：模型生成看似合理但事实错误的内容。

**原因**：
- 训练数据的噪声和错误
- 模型本质是统计模式匹配，不是知识库
- 缺乏实时/领域知识
- 解码策略（高温采样）引入随机性
- 长文本推理时信息衰减

**缓解方案**（你项目中的实践）：

| 方案 | 原理 | 你的项目应用 |
|------|------|------------|
| **RAG** | 检索外部知识库作为上下文 | 三个项目全部使用 RAG |
| **System Prompt 约束** | "只基于给定的文档回答，不知道就说不知道" | 医疗平台的核心安全护栏 |
| **低温度 + 低 Top-P** | 减少随机采样 | 医疗场景 temperature=0.1 |
| **Function Calling** | 用结构化数据回答，而非生成 | AI 客服查订单 |
| **来源溯源** | 答案附带引用来源 | 灵枢医疗的输出带文档引用 |
| **输出护栏** | 正则 + 规则检查输出 | 医疗平台 6 条安全正则 |
| **事实性校验** | 用另一个模型检查 | 医疗场景的二次复核 |

📌 **效果量化（Flavor Dash）**：RAG 结合 Function Calling 使 AI 客服幻觉相关的用户升级投诉减少约 70%。通过检索真实订单数据作为回答依据，模型不再需要"编造"订单状态，从根本上消除了该类幻觉。

## 二、Function Calling 深度解析

### 6. Function Calling 的底层实现原理？

**这并非模型真的"调用"函数，而是以下流程**：

```
1. 定义函数 Schema（JSON Schema 格式）传给模型
   {
     "name": "get_weather",
     "description": "获取指定城市的天气",
     "parameters": {
       "type": "object",
       "properties": {
         "city": {"type": "string", "description": "城市名称"},
         "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
       },
       "required": ["city"]
     }
   }

2. 用户输入 → 模型判断需要调用哪个函数 → 返回 tool_call 而非普通文本
   {
     "id": "call_xxx",
     "type": "function",
     "function": {
       "name": "get_weather",
       "arguments": "{\"city\": \"合肥\", \"unit\": \"celsius\"}"
     }
   }

3. 你的代码执行 get_weather("合肥", "celsius")

4. 将执行结果作为 tool 消息返回给模型：
   { "role": "tool", "content": "{\"temperature\": 25, \"condition\": \"晴\"}", "tool_call_id": "call_xxx" }

5. 模型基于工具返回的结构化数据，生成自然语言回复
   "合肥今天晴天，气温 25°C，适合出行！"
```

**关键**：模型做的事是**意图识别 + 参数提取** + **结果转自然语言**，实际执行完全是你的代码做的。

📌 **项目实践（Flavor Dash AI 客服）**：用户问"我的订单到哪了" → 模型提取 orderId → 调用 `queryOrder(orderId)` 后端接口 → 返回真实物流状态 → 模型生成自然语言回复"您的订单已出库，预计明天到达"。AI 客服自动处理约 70% 的咨询量，仅复杂纠纷转人工。

### 7. Function Calling 的常见坑和处理？

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| **参数幻觉** | 模型编造参数值（比如拿不到 orderId 就瞎编一个） | System Prompt 明确："如果没有足够信息，不要调用函数，向用户确认" |
| **不调用函数** | 应该调函数但模型直接胡编一个答案 | 降低 temperature、增加 Few-shot 示例 |
| **参数格式错误** | JSON 格式不对、缺少必填参数 | 代码层做参数校验 + 错误时让模型重试 |
| **多次调用** | 需要链式调用多个函数 | 支持连续 Function Calling（模型返回 → 代码执行 → 结果回传 → 模型可能再调用） |
| **幻觉函数名** | 模型调用了一个你没定义的函数 | 在 System Prompt 强调"只能调用提供的函数" |
| **参数注入** | 用户输入中注入恶意参数 | 参数校验 + 白名单 + SQL 注入防护 |

📌 **项目实践（Flavor Dash 实际踩坑）**：参数幻觉是最频繁遇到的问题——模型在用户未提供 orderId 时自行编造。通过 System Prompt 规则（"没有足够信息不要调用函数，向用户确认"）+ 服务端参数校验（必填字段缺失时返回错误并提示重试），失败案例减少约 60%。

## 三、Agent 智能体深度解析

### 8. Agent 和普通 LLM 调用的本质区别？

| | 普通 LLM 调用 | Agent |
|--|-------------|-------|
| 交互方式 | 单轮/多轮：用户→模型→回答 | 自主循环：思考→行动→观察→思考... |
| 工具使用 | 不支持或通过 Function Calling 单次 | 自主选择多工具、多轮调用 |
| 规划能力 | 无 | 分解任务、制定计划、执行后反思 |
| 状态管理 | 仅对话历史 | 对话历史 + 任务状态 + 工具调用历史 |
| 示例 | "1+1等于几？" | "帮我比价三家购物平台，推荐最便宜的 iPhone 15" |

**Agent 的核心循环（你项目中的实现）**：

```java
// Think → Act → Observe 循环
public String run(String userInput) {
    agentMemory.addMessage(Role.USER, userInput);
    
    for (int step = 0; step < maxSteps; step++) {
        // 1. Think：模型思考下一步做什么
        String thought = llm.think(agentMemory.getHistory(), availableTools);
        
        // 2. 判断是否结束
        if (thought.isFinalAnswer()) {
            return thought.getAnswer();
        }
        
        // 3. Act：调用工具
        ToolCall toolCall = thought.getToolCall();
        String result = toolRegistry.execute(toolCall);
        
        // 4. Observe：观察结果，加入记忆
        agentMemory.addToolResult(toolCall, result);
        
        // 5. 循环继续（Analyze result → Think again）
    }
    
    return "任务超过最大步骤数";
}
```

📌 **项目实践（Flavor Dash Agent 框架）**：Think→Act→Observe 循环应用于 AI 客服的复杂多步场景。例如用户投诉"我买的 iPhone 15 还没到，想退款"→思考需要查订单→查物流→查退款政策→综合回复。该框架使复杂多步客服请求的首次解决率（FCR）达到约 85%。

### 9. ReAct 编排为什么有效？和其他模式对比？

**ReAct = Reasoning + Acting（推理 + 行动交替）**

**为什么有效？**
- **思考链（CoT）**：只在推理阶段，不能获取外部信息，错误可能被放大
- **纯行动（Act-Only）**：没有推理过程，每个行动孤立
- **ReAct**：思考指导行动，行动反馈修正思考，形成闭环

**举例对比**：

纯 LLM 回答（有幻觉风险）：
> "您想买 iPhone 15？京东价格是 5999 元，拼多多是 5499 元。推荐在拼多多购买。" ← 可能编造价格

ReAct Agent：
```
Think: 需要查询京东和拼多多的 iPhone 15 价格
Act: search_product("iPhone 15", platform="京东") → {"price": 6999, "inStock": true}
Observe: 京东 6999 元，有货
Think: 还需要查拼多多
Act: search_product("iPhone 15", platform="拼多多") → {"price": 6599, "inStock": true}
Observe: 拼多多 6599 元，有货
Think: 拼多多便宜 400 元，两家都有货。推荐拼多多，但提醒注意售后差异
最终回复："京东 6999 元，拼多多 6599 元。推荐在拼多多购买可省 400 元，但京东售后更方便..."
```

**你项目的 AgentRouter 设计**（SuGuangMall）：
```
用户输入 → 意图路由（Router LLM）
    ↓
    ├── "找东西" → SearchAgent（工具：ES搜索、向量搜索、价格过滤）
    ├── "比较"   → CompareAgent（工具：多商品参数对比、评测查询）
    ├── "推荐"   → RecommendAgent（工具：用户画像、协同过滤、RAG推荐理由）
    ├── "问题"   → CustomerServiceAgent（工具：订单查询、退款申请、FAQ检索）
    ├── "写内容" → ContentAgent（工具：模板填充、风格调整、SEO优化）
    └── "分析"   → AnalysisAgent（工具：NL2SQL、数据可视化）
```

**效果量化**：AgentRouter 比单体 Agent 的任务完成时间减少约 40%。专业 Agent 专注各自领域，避免了大 Prompt 带来的推理效率下降。

### 10. Agent 记忆系统怎么设计？

**你的双层存储方案**（灵枢医疗）：

```
用户会话
    ↓
┌─ L1 缓存（Caffeine，JVM 堆内存）──┐
│  - 热数据：当前活跃会话           │
│  - 极快（纳秒级）                 │
│  - 容量有限（堆内存用完 GC）      │
└───────────────────────────────────┘
    ↓ 淘汰/L1 miss
┌─ L2 存储（Redis）───────────────┐
│  - 冷数据：历史会话               │
│  - 快（毫秒级）                   │
│  - 容量大，可设置过期时间         │
│  - 支持分布式（多实例共享记忆）   │
└───────────────────────────────────┘
```

**记忆类型**：
- **短期记忆**：当前对话的上下文窗口（对话历史，支持 20 轮 / 8000 字）
- **长期记忆**：跨对话的用户偏好、历史行为（存储在 Redis/DB 中，下次对话可恢复）
- **工作记忆**：当前 Agent 任务的中间状态（工具调用结果、中间推理）

**上下文窗口管理**：当对话历史接近模型上下文窗口上限时：
1. 保留最近的 N 轮对话
2. 对早期对话做摘要（Summarization）压缩
3. 保留关键信息（用户意图、已确认的事实）

**效果量化**：Caffeine L1 缓存实现热会话亚毫秒级读写，相比直读 Redis 减少延迟约 90%。摘要压缩策略使 50 轮长对话维持在 128K 上下文窗口内，避免了超长对话被截断导致的信息丢失。

### 11. Multi-Agent 和单 Agent 的优劣？

| | 单 Agent | Multi-Agent |
|--|---------|------------|
| 复杂度 | 低 | 高（需路由/编排） |
| 专业性 | 通用，每领域都不深 | 各 Agent 专注各自领域 |

```java
// 技能热加载器
@Component
public class SkillLoader {
    private Map<String, SkillConfig> skills = new ConcurrentHashMap<>();
    
    @Scheduled(fixedDelay = 5000)  // 每 5 秒扫描
    public void reload() {
        Resource[] resources = new PathMatchingResourcePatternResolver()
            .getResources("classpath:skills/*.yml");
        for (Resource r : resources) {
            SkillConfig config = yamlMapper.readValue(r.getInputStream(), SkillConfig.class);
            if (!config.equals(skills.get(config.getName()))) {
                skills.put(config.getName(), config);
                log.info("技能 {} 已更新/加载", config.getName());
            }
        }
    }
}
```

## 四、多模态与 CLIP

### 13. CLIP 模型的原理是什么？

**CLIP（Contrastive Language-Image Pre-training）**：OpenAI 的多模态模型，将图片和文本映射到同一向量空间。

**训练方式**：对比学习（Contrastive Learning）。
- 输入 N 个（图片, 描述）配对
- 图片通过 Image Encoder → 图片向量
- 文本通过 Text Encoder → 文本向量
- 目标：正确的（图片, 文本）配对的余弦相似度尽可能高，错误的尽可能低
- N×N 的相似度矩阵，对角线为正样本，其余为负样本

**结果**："一张猫的照片" 和 猫的图片 → 向量空间距离很近。

**你项目的应用**（SuGuangMall 以图搜图）：
1. 商品图片 → CLIP Image Encoder → 512 维向量 → 存入 Milvus
2. 用户搜索图片 → CLIP Image Encoder → 512 维向量
3. Milvus ANN 搜索 Top-30 相似向量 → 相似度匹配准确率 ~90%
4. 之后可选：文本属性过滤（颜色/材质）+ 风格识别 → 推荐 + 穿搭建议

### 14. 多模态 Embedding 和纯文本 Embedding 的区别？

| | 文本 Embedding（BGE） | 多模态 Embedding（CLIP） |
|--|---------------------|------------------------|
| 输入 | 文本 | 图片 + 文本 |
| 输出维度 | 768/1024 | 512/768 |
| 向量空间 | 仅文本语义空间 | 文本+图片共享空间 |
| 使用场景 | 文档检索、语义匹配 | 以图搜图、图文匹配 |
| 文本→图片 | 不能 | 能（"红色连衣裙"→ 找图片） |
| 图片→文本 | 不能 | 能（用户拍的衣服→找描述） |

**项目实践（SuGuangMall）**：CLIP 512 维向量用于以图搜图（用户上传衣服图片搜同款）和文字搜图片（"红色连衣裙"搜商品图）；BGE 文本 Embedding（768 维）用于商品描述语义搜索和 FAQ 匹配。两者互补，CLIP 处理视觉匹配，BGE 处理语义理解。

### 16. Resilience4j 在你的模型网关中怎么配置的？

```java
// 熔断配置
CircuitBreakerConfig cbConfig = CircuitBreakerConfig.custom()
    .failureRateThreshold(50)        // 失败率 50% 触发熔断
    .slowCallRateThreshold(50)       // 慢调用率 50% 触发熔断
    .slowCallDurationThreshold(Duration.ofSeconds(10))  // 超过 10s 算慢调用
    .slidingWindowType(SlidingWindowType.COUNT_BASED)
    .slidingWindowSize(10)           // 统计最近 10 次调用
    .minimumNumberOfCalls(5)         // 至少 5 次调用才开始统计
    .waitDurationInOpenState(Duration.ofSeconds(30))  // 熔断 30s 后半开
    .build();

// 重试配置
RetryConfig retryConfig = RetryConfig.custom()
    .maxAttempts(3)
    .waitDuration(Duration.ofMillis(2000))  // 初始等待 2s
    .intervalBiFunction((attempt, delay) -> 
        delay * (long) Math.pow(2, attempt - 1))  // 指数退避：2s→4s→8s
    .retryOnException(e -> e instanceof RetryableException)
    .build();

// 组合装饰
Supplier<String> decorated = Decorators.ofSupplier(() -> client.chat(request))
    .withCircuitBreaker(circuitBreaker)
    .withRetry(retryConfig)
    .decorate();
```

📌 **项目实践（Flavor Dash LLM Client Factory）**：线上真实故障转移故事——某日 DeepSeek 上游服务中断约 15 分钟，熔断器在 30 秒内（10 次调用滑动窗口，失败率超 50%）触发 OPEN 状态，网关自动将流量切换到 Qwen（备用 provider），整个过程零人工干预。30 秒后半开探针检测到 DeepSeek 恢复，自动关闭熔断。P95 延迟控制在 3 秒以内，用户无感知。

## 六、MCP 协议深度

### 17. MCP 协议的架构和工作原理？

**MCP（Model Context Protocol）**：标准化 AI 应用与外部工具/资源的交互协议。

**架构**：
```
┌──────────────┐          ┌──────────────┐
│  MCP Client  │◄────────►│  MCP Server  │
│ （AI 应用）   │  JSON-RPC │ （工具提供方）│
│ Claude Code  │  over     │  Filesystem  │
│ Cursor       │  stdio    │  Database    │
│ 你的 Java App│  / SSE    │  Web APIs    │
└──────────────┘          └──────────────┘
```

**核心概念**：
- **Tools（工具）**：可执行的函数，LLM 可以通过 Function Calling 调用
- **Resources（资源）**：可读取的数据（文件、数据库记录 → URI 标识）
- **Prompts（提示模板）**：可复用的提示词模板
- **Sampling（采样）**：Server 可以请求 Client 调用 LLM（反向）

**生命周期**：
1. **初始化**：Client→Server 发送 `initialize` 请求，协商协议版本和能力
2. **正常操作**：Client 通过 `tools/list` 获取工具列表，通过 `tools/call` 调用工具
3. **心跳**：`ping` 保持连接
4. **通知**：Server 可主动通知 Client（如文件变更）

**与 Function Calling 的关系**：
- Function Calling：在单次请求中定义工具 → LLM 判断是否调用
- MCP：工具定义的标准化协议，实现**工具的跨应用复用**
- 你可以在 Agent 中通过 MCP 协议引入任意 MCP Server 的工具

📌 **项目实践（SuGuangMall）**：6 Agent 系统的工具定义统一遵循 MCP 风格的 JSON Schema 约定。CompareAgent 和 CustomerServiceAgent 共用同一套商品查询 MCP 工具，无需各自重复集成。标准化工具定义使每工具集成成本降低约 60%，新增 Agent 时直接复用已有 MCP 工具即可。

### 18. MCP 协议在 Agent 开发中的价值？

**Before MCP（M×N 问题）**：
- 3 个 AI 应用 × 5 个数据库工具 → 15 个定制集成
- 每个工具集成都要写代码

**After MCP**：
- 数据库工具写一次 MCP Server → 3 个 AI 应用都能用
- 类比 USB：鼠标（MCP Server）→ 标准接口（MCP 协议）→ 任何电脑（MCP Client）

**你项目的 MCP 实践（SuGuangMall）**：
- SuGuangMall 中每个 Agent 的工具（商品搜索、订单查询、价格对比）均封装为 MCP 兼容的 Tool Service
- 工具按 MCP 规范定义了统一的 JSON Schema、input/output 格式和错误码，可以在不同 Agent 间直接复用
- 设计上支持跨应用复用——未来其他 AI 应用（如 Cursor IDE）可通过 MCP 协议直接调用 SuGuangMall 的商品搜索工具

## 八、安全与合规

### 21. AI 应用有哪些安全隐患？如何防护？

**OWASP Top 10 for LLM Applications**（核心风险）：

| 风险 | 说明 | 你的防护 |
|------|------|---------|
| **Prompt Injection** | 通过输入覆写 System Prompt | 3 层检测（关键词 → 语义 → 意图），拦截率 99.5%（LingShu） |
| **Insecure Output Handling** | 输出未校验直接执行/展示 | 输出护栏 + 6 条危险正则 + XSS 编码（LingShu） |
| **Training Data Poisoning** | 训练/微调数据被污染 | 使用 RAG 而非微调，不存储用户数据到训练集 |
| **Model Denial of Service** | 超长输入耗尽资源 | 输入长度限制 + 限流 + Token 预估算截断 |
| **Sensitive Information Disclosure** | LLM 泄露训练数据中的隐私 | PHI 脱敏正则（输入输出双向运行），100% 覆盖（LingShu） |
| **Excessive Agency** | Agent 执行了危险操作 | 每个 Agent 工具白名单操作（LingShu 5 个医疗 Skill 均有权限控制） |

### 22. 你医疗平台的安全护栏具体是怎么实现的？

**以"灵枢"为例的完整安全架构**：

```
┌─────────────────────────────────────────────┐
│                  输入安全层                    │
│  L1 关键词检测 → L2 Prompt注入检测 → L3 意图识别 │
├─────────────────────────────────────────────┤
│                  处理层                        │
│  PHI脱敏 → 意图分类 → 医疗专业Agent            │
├─────────────────────────────────────────────┤
│                  输出安全层                    │
│  6条危险正则 → 合规检查 → 来源溯源 → 免责追加   │
├─────────────────────────────────────────────┤
│                  审计层                        │
│  全量日志 → 异常行为告警 → 人工抽检            │
└─────────────────────────────────────────────┘
```

**6 条输出危险正则详解**（见题库 01 的第 11 题）。

**PHI（Protected Health Information）脱敏正则**：
```java
Map<Pattern, String> PHI_PATTERNS = Map.of(
    Pattern.compile("[一-龥]{2,4}(?=(先生|女士|患者|病人))"), "[姓名]",
    Pattern.compile("1[3-9]\\d{9}"), "[手机号]",
    Pattern.compile("\\d{17}[0-9Xx]"), "[身份证号]",
    Pattern.compile("(\\d{3,4}-)?\\d{7,8}"), "[电话]",
    Pattern.compile("[\\u4e00-龥]+(市|县|区|街道|路|号|栋|楼|室)"), "[地址]"
);
```

**效果量化**：内部安全审计表明，该 4 层架构实现 99.9% 的有害输出拦截率。200 条标注测试对话中，PHI 脱敏覆盖率达 100%（无任何姓名、手机号、身份证号泄露）。6 条危险正则零误报，所有被拦截的输出均确认为安全违规。
