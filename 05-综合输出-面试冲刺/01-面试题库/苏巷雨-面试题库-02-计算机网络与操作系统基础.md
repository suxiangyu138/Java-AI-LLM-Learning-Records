### 2. TCP 三次握手和四次挥手？为什么是三次和四次？

**三次握手**：
```
客户端                         服务端
  |    SYN=1, seq=x             |
  |--------------------------->|
  |   SYN=1, ACK=1, seq=y,     |
  |   ack=x+1                  |
  |<---------------------------|
  |   ACK=1, seq=x+1, ack=y+1  |
  |--------------------------->|
```

- **为什么不是两次？**：防止已失效的连接请求到达服务端。如果只有两次握手，客户端第一次 SYN 因网络延迟，超时后又发一次 SYN，两次都到达服务端 → 服务端建立两个连接，浪费资源
- **为什么不是四次？**：服务端 SYN + ACK 可以合并发送，不需要分开发

**四次挥手**：
```
客户端                         服务端
  |   FIN=1, seq=u              |
  |--------------------------->|  (1) 客户端：我没有数据要发了
  |   ACK=1, seq=v, ack=u+1    |
  |<---------------------------|  (2) 服务端：我知道了
  |   FIN=1, ACK=1, seq=w,     |  (服务端可能还有数据要发)
  |   ack=u+1                  |
  |<---------------------------|  (3) 服务端：我也没有数据要发了
  |   ACK=1, seq=u+1, ack=w+1  |
  |--------------------------->|  (4) 客户端：好的，再见
```

- **为什么四次？**：TCP 是全双工的，双方都可以主动关闭。服务端收到 FIN 后可能还有数据要发，ACK 和 FIN 必须分开
- **TIME_WAIT（2MSL）**：客户端发送最后 ACK 后等待 2MSL（Maximum Segment Lifetime，约 2 分钟）。原因：
  - 确保最后的 ACK 被服务端收到（丢了服务端会重发 FIN）
  - 让旧连接的所有报文在网络中消失

### 5. HTTP 1.0 / 1.1 / 2.0 / 3.0 的区别？

| 版本 | 特点 | 问题 |
|------|------|------|
| **HTTP 1.0** | 每次请求新建 TCP 连接 | 连接开销大 |
| **HTTP 1.1** | **持久连接**（Keep-Alive，默认不关）、**管道化**（Pipelining，请求可排队但响应必须同序）、Host 头（虚拟主机）、断点续传 | 队头阻塞（Head-of-Line Blocking） |
| **HTTP 2.0** | **二进制分帧**、**多路复用**（一个连接并发多个请求/响应）、头部压缩（HPACK）、服务端推送 | TCP 层仍有序，丢包重传阻塞所有流 |
| **HTTP 3.0** | 基于 **QUIC**（UDP），0-RTT 握手、无队头阻塞 | 普及度还在增长中 |

**你项目中的关联**：
- SSE 基于 HTTP 1.1 长连接
- OpenFeign 底层使用 HTTP/1.1 或 HTTP/2
- Nginx 反向代理可配置 HTTP/2

### 6. HTTPS 加密过程（SSL/TLS 握手）？

```
1. 客户端 → 服务端：ClientHello（支持的 TLS 版本 + 加密套件 + 随机数1）
2. 服务端 → 客户端：ServerHello（选定的 TLS 版本 + 加密套件 + 随机数2）+ 数字证书（含公钥）
3. 客户端验证证书链（CA 签名 → 根证书）
4. 客户端生成随机数3（Pre-Master Secret）→ 用公钥加密 → 发送给服务端
5. 服务端用私钥解密获得随机数3
6. 双方用随机数1 + 随机数2 + 随机数3 生成**会话密钥**（对称加密）
7. 之后的数据传输用会话密钥对称加密
```

**核心**：非对称加密（RSA/ECDHE）用于交换密钥，对称加密（AES）用于数据传输。

**HTTP vs HTTPS**：HTTPS = HTTP + TLS，端口 443；HTTP 端口 80，明文传输。

### 7. DNS 解析过程？

```
用户输入 www.example.com
    ↓
1. 浏览器 DNS 缓存 → 有则返回
    ↓ miss
2. 操作系统缓存（hosts 文件）→ 有则返回
    ↓ miss
3. 本地 DNS 服务器（ISP 提供）
    ↓ 递归查询
4. 根域名服务器 → 返回 .com 顶级域名服务器地址
5. .com 顶级域名服务器 → 返回 example.com 权威域名服务器地址
6. example.com 权威域名服务器 → 返回 www.example.com 的 IP
    ↓
7. 本地 DNS 缓存结果 → 返回给客户端
```

### 8. Cookie、Session、Token、JWT 的区别？

| | Cookie | Session | Token | JWT |
|--|--------|---------|-------|-----|
| 存储位置 | 浏览器 | 服务端 | 客户端（localStorage/cookie） | 客户端 |
| 安全性 | 低（明文） | 高（服务端） | 中 | 高（签名校验） |
| 状态 | 无状态 | 有状态（服务端存 session） | 无状态 | 无状态（自包含） |
| 跨域 | 受同源策略限制 | 默认不支持跨域 | 支持 | 支持 |
| 扩展性 | - | 差（分布式需共享 session） | 好 | 好 |

**JWT 结构**（你项目中使用）：
```
Header.Payload.Signature
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEyM30.xxx

Header：  { alg: "HS256", typ: "JWT" }
Payload： { userId: 123, role: "user", exp: 1234567890 }
Signature：HMAC-SHA256(base64(Header) + "." + base64(Payload), secret)
```

**JWT 如何防止伪造？**：Signature 用密钥签名，篡改 Payload 后签名不匹配 → 校验失败。

**JWT 的缺点**：无状态也意味着无法主动失效（除非加黑名单 Redis 检查）。

**你项目的实践**：Gateway + JWT 鉴权，用户登录后生成 JWT，请求携带在 Authorization: Bearer xxx 头中。

### 12. TCP 拥塞控制？

四种算法：
1. **慢启动**：拥塞窗口 cwnd 从 1 开始，指数增长（每收到 ACK → cwnd × 2），直到达到慢启动阈值 ssthresh
2. **拥塞避免**：cwnd ≥ ssthresh 后，线性增长（每 RTT → cwnd + 1）
3. **快重传**：收到 3 个重复 ACK → 判定丢包 → 立即重传（不等超时）
4. **快恢复**：快重传后，ssthresh = cwnd/2，cwnd = ssthresh，直接进入拥塞避免（不降到 1）

### 13. TCP 粘包/拆包怎么解决？

**原因**：TCP 是流式协议，无消息边界。发送方连续发送小包可能合并（粘包），大包可能被拆分（拆包）。

**解决方案**：
- **定长消息**：每个消息固定长度，不够则填充
- **分隔符**：如用 `\n` 分割消息（Netty DelimiterBasedFrameDecoder）
- **消息头 + 消息体**：头中声明消息长度（Netty LengthFieldBasedFrameDecoder）
- 使用应用层协议：HTTP（自带 Content-Length）

## 二、操作系统

### 14. 进程和线程的区别？协程又是什么？

| | 进程 | 线程 | 协程 |
|--|------|------|------|
| 资源 | 独立资源单位（独立地址空间） | 共享进程资源 | 共享线程资源 |
| 切换开销 | 大（切换页表、TLB 刷新） | 中等（内核态切换） | 小（用户态切换，无内核介入） |
| 通信 | IPC（管道/消息队列/共享内存） | 共享变量（需同步） | 共享变量 |
| 创建 | 慢 | 较快 | 极快 |
| 崩溃影响 | 不影响其他进程 | 影响同一进程的线程 | 影响同一线程的协程 |

**Java 中的协程**：JDK 19+ Virtual Thread（虚拟线程/Project Loom），类似 Go 的 Goroutine，轻量并发。

**你项目的实践**：
- Spring Boot 默认每请求一个线程（Tomcat 线程池）
- WebFlux/SSE 基于 NIO 非阻塞模型，减少线程开销

### 15. 线程间的通信方式？

**Java 中**：
1. **volatile**：保证共享变量可见性（轻量级）
2. **synchronized + wait/notify**：等待唤醒机制
3. **Lock + Condition**：比 wait/notify 更灵活，支持多条件
4. **JUC 工具**：CountDownLatch（倒计数）、CyclicBarrier（循环栅栏）、Semaphore（信号量）
5. **BlockingQueue**：生产者-消费者模式
6. **CompletableFuture**：异步回调
7. **ThreadLocal**：线程局部变量

### 16. 进程间的通信方式（IPC）？

1. **管道（Pipe）**：半双工，父子进程间。`ps aux | grep java`
2. **命名管道（FIFO）**：非父子进程也可用
3. **信号（Signal）**：如 `kill -9 PID`
4. **消息队列**：内核管理，异步
5. **共享内存**：最快，但需同步机制（信号量配合）
6. **信号量（Semaphore）**：同步互斥
7. **Socket**：网络通信，跨机器（最常用的 IPC，你的微服务间 RPC/HTTP 本质就是 Socket IPC）

### 17. 死锁的四个必要条件？如何排查和避免？

**四个必要条件**（缺一不可）：
1. **互斥**：资源一次只能被一个进程/线程使用
2. **请求保持**：持有资源的同时请求新资源
3. **不可剥夺**：已获得的资源不能被强制拿走
4. **循环等待**：形成资源等待环（P1→P2→P3→P1）

**排查死锁**：
```bash
jstack PID | grep -A 10 "deadlock"
# 或 jconsole / jvisualvm 可视化管理工具
```

**代码示例**（构造死锁）：
```java
// 线程 A：先拿 lock1 → 等 lock2
// 线程 B：先拿 lock2 → 等 lock1
synchronized(lock1) {
    Thread.sleep(100);
    synchronized(lock2) { ... }
}
```

**避免死锁**：
- 破坏循环等待：**固定加锁顺序**（所有线程按相同顺序获取锁）
- 破坏请求保持：一次获取所有资源
- 破坏不可剥夺：`tryLock(timeout)` 超时放弃
- 破坏互斥：使用无锁数据结构（CAS）

📌 **项目实践**：在Flavor Dash中曾遇到OSS文件上传锁与本地缓存刷新锁的相互等待导致超时，通过jstack导出线程dump分析死锁环，调整为统一锁获取顺序解决。SuGuangMall秒杀中用Redisson分布式锁+Lua脚本原子操作避免死锁，看门狗自动续期防锁超时释放。

### 18. 用户态和内核态的区别？切换场景？

| | 用户态 | 内核态 |
|--|--------|--------|
| 权限 | 低（不能访问硬件、不能执行特权指令） | 高（完全控制 CPU） |
| 地址空间 | 用户空间 | 内核空间 |
| 崩溃影响 | 只影响当前进程 | 系统崩溃（蓝屏/内核 panic） |

**切换场景**：
- **系统调用**：read/write、send/recv（主动切换）
- **中断**：硬件中断（磁盘 IO 完成、网卡收到数据）
- **异常**：缺页异常、除零异常

**Java 中的体现**：
- NIO 的 Selector 通过 `select()` 进行系统调用，从用户态切换到内核态等待 IO 事件
- `new Thread().start()` → 调用 clone() 系统调用创建内核线程

### 19. 虚拟内存和物理内存？分页机制？

**虚拟内存**：每个进程看到的连续地址空间（4GB on 32-bit），但实际物理内存可能不连续。

**分页机制**：
- 虚拟地址 → **页表**（Page Table）映射 → 物理地址
- 页面大小：通常 4KB
- 虚拟地址结构：`[页号] + [页内偏移]`
- 通过 **MMU**（Memory Management Unit）硬件转换

**好处**：
- 隔离：进程 A 不能访问进程 B 的内存
- 共享：不同进程的虚拟地址映射到同一物理页（共享库、mmap）
- 更大的地址空间：可以使用比物理内存大的地址空间（页面置换到磁盘 swap）

**缺页中断**：访问的页面不在物理内存中 → 触发中断 → OS 从磁盘加载

### 20. 内存管理中的分段 vs 分页？

| | 分段 | 分页 |
|--|------|------|
| 划分方式 | 逻辑单位（代码段、数据段、栈段） | 物理单位（固定大小页框） |
| 粒度 | 可变（每个段大小不同） | 固定（4KB） |
| 碎片 | 外部碎片 | 内部碎片（页内浪费） |
| 程序员可见 | 可见（段寄存器） | 不可见 |

**现代 OS 使用段页式**：先用段确定区域，再在段内分页。

📌 **项目实践**：在LingShu灵枢部署中，用tail -f追踪Spring Boot启动日志定位配置错误；netstat -anp查端口占用解决Nginx与Gateway的8080冲突；awk+sort统计Nginx access.log分析API调用分布和异常IP。

### 22. 零拷贝是什么？NIO 中怎么用？

**传统 IO（4 次拷贝 + 4 次上下文切换）**：
```
磁盘 → 内核缓冲区 → 用户缓冲区 → 内核 Socket 缓冲区 → 网卡
```

**零拷贝（sendfile/Linux 2.4+，2 次拷贝 + 2 次切换）**：
```
磁盘 → 内核缓冲区 → 网卡（DMA 直接）
```

**Java 中**：
- `FileChannel.transferTo()`：底层调用 sendfile，实现零拷贝
- Netty 的 `FileRegion` 包装了 `transferTo()`
- Kafka 大量使用零拷贝提升吞吐

### 23. 同步/异步、阻塞/非阻塞的区别？

这是一个常见的概念陷阱：

- **阻塞/非阻塞**：关注**调用者等待返回时的状态**
  - 阻塞：线程挂起等待结果
  - 非阻塞：立即返回，稍后再来问
- **同步/异步**：关注**被调用方如何通知结果**
  - 同步：调用方主动等待/轮询结果
  - 异步：被调用方通过回调/事件/Future 通知调用方

**组合**：
| | 同步 | 异步 |
|--|------|------|
| 阻塞 | BIO（read 阻塞等数据） | - |
| 非阻塞 | NIO（selector 轮询，数据就绪后才 read） | AIO（回调通知数据已准备好） |

**Java 中的体现**：
- `CompletableFuture.supplyAsync()`：异步非阻塞
- `Future.get()`：同步阻塞（等着拿结果）
- `Selector.select()`：同步非阻塞（轮询等待事件）

### 24. 什么是上下文切换？如何减少？

**上下文切换**：CPU 从一个线程/进程切换到另一个时，保存当前状态 → 加载下一个状态（寄存器、程序计数器、栈指针）。

**耗时原因**：
- 保存/恢复寄存器
- 切换页表（进程切换时）→ TLB 刷新
- Cache 失效（冷启动）

**减少上下文切换**：
- **无锁编程**：CAS 避免阻塞 → 减少线程挂起
- **合理线程数**：不是越多越好，CPU 核数 × 2 左右
- **协程**：用户态切换，不经过内核
- **批量处理**：减少系统调用次数
- **CPU 亲和性**：绑定线程到固定 CPU 核

📌 **项目实践**：SuGuangMall中JDK 21 Virtual Thread在处理IO密集型LLM API调用时大幅减少内核级上下文切换，与传统线程池(200线程)相比，虚拟线程(2000并发)上下文切换次数降低~90%。
