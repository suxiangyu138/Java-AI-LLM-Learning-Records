## 一、设计模式

### 1. 你用过哪些设计模式？项目中具体怎么用的？

**单例模式**：Spring Bean 默认 scope=singleton。我自己在项目中用枚举单例管理全局配置。

**工厂模式**：**LLM Client Factory**（Flavor Dash 核心设计）：
```java
// 工厂创建不同 provider 的客户端
public class LLMClientFactory {
    public LLMClient create(ProviderEnum provider) {
        return switch (provider) {
            case OPENAI -> new OpenAIClient(openAIConfig);
            case DEEPSEEK -> new DeepSeekClient(deepSeekConfig);
            case QWEN -> new QwenClient(qwenConfig);
            case GLM -> new GLMClient(glmConfig);
        };
    }
}
// 结合策略模式：运行时根据配置/负载选择 provider
```

**策略模式**：
- 不同的模型提供商有不同的调用策略（请求格式、响应解析、Token 计数方式）
- 二级缓存淘汰策略切换（LRU / LFU / TTL）

**代理模式**：
- Spring AOP（@Transactional、日志切面）本质是动态代理
- MyBatis Mapper 接口的 JDK 动态代理

**模板方法模式**：
- `LLMClient` 抽象类定义调用流程：`preProcess() → doChat() → postProcess() → handleError()`
- 子类只需实现 provider 特定的细节

**观察者模式**：
- Spring Event（`ApplicationEventPublisher`），在Flavor Dash中订单支付成功通过Spring Event(观察者模式)通知积分服务和推荐服务
- RabbitMQ 发布/订阅，在Flavor Dash中跨服务用RabbitMQ(发布-订阅模式)做异步通知，如订单状态变更推送给WebSocket服务

**责任链模式**：
- Gateway Filter Chain
- Sentinel Slot Chain（限流/熔断/降级按顺序执行）
- 医疗平台的安全护栏（多级检测串成链）

**建造者模式**：
- `ChatRequest.builder().model(...).messages(...).temperature(0.7).build()`
- Lombok @Builder

### 2. 单例模式的几种写法？双重校验锁为什么要用 volatile？

**5 种写法优缺点**：

```java
// 1. 饿汉式 - 类加载时创建，简单安全，但可能浪费内存
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}

// 2. 懒汉式 DCL - 最常用，volatile 必须
public class Singleton {
    private static volatile Singleton instance; // ★ volatile 防指令重排
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {                    // 第一重检查（提升性能）
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二重检查（保证单例）
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

// 3. 静态内部类 - 利用类加载机制，优雅
public class Singleton {
    private Singleton() {}
    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}

// 4. 枚举 - 最安全，防反射、防反序列化
public enum Singleton {
    INSTANCE;
    public void doSomething() { ... }
}

// 5. CAS 无锁 - 乐观，但多次 new 浪费（无伤大雅）
public class Singleton {
    private static final AtomicReference<Singleton> INSTANCE = new AtomicReference<>();
    public static Singleton getInstance() {
        for (;;) {
            Singleton current = INSTANCE.get();
            if (current != null) return current;
            current = new Singleton();
            if (INSTANCE.compareAndSet(null, current)) return current;
        }
    }
}
```

**DCL 为什么必须 volatile？**

`new Singleton()` 在 JVM 层面不是原子的，分为三步（可能被重排序）：
1. 分配内存空间
2. 初始化对象（调用构造器）
3. 将引用指向分配的内存

如果发生指令重排：1 → 3 → 2。此时 instance 不为 null 但**对象还没初始化完** → 另一个线程在第一个 if 判断时取到非 null instance → 使用半初始化对象 → **空指针异常或状态错误**。

volatile 通过内存屏障禁止指令重排，保证 `new Singleton()` 的完整执行顺序。

### 3. 工厂模式 vs 策略模式的区别？

| | 工厂模式 | 策略模式 |
|--|---------|---------|
| 关注点 | **创建**对象 | **使用**对象（行为选择） |
| 使用时机 | 需要决定 new 哪个实现类 | 需要运行时切换算法/行为 |
| 典型代码 | `if(type == A) new A() else new B()` | `strategy.execute(data)` |
| 组合使用 | 工厂创建策略对象，策略执行逻辑 | ← 两者经常一起用 |

**你项目中的组合**：
```java
// 工厂创建 → 策略执行
LLMClient client = factory.create(provider);   // 工厂模式
String reply = client.chat(request);            // 策略模式
```

### 4. 代理模式：JDK 动态代理 vs CGLIB 代理？

| | JDK 动态代理 | CGLIB 代理 |
|--|-------------|-----------|
| 原理 | 基于接口，生成实现接口的代理类 | 基于继承，生成目标类的子类 |
| 要求 | 目标类必须实现接口 | 不能代理 final 类/方法 |
| 创建方式 | `Proxy.newProxyInstance()` | `Enhancer` + `MethodInterceptor` |
| 性能 | 创建快，执行稍慢（反射） | 创建慢（ASM 字节码），执行快 |
| Spring 默认 | 有接口时用 JDK | 无接口时用 CGLIB |
| Spring Boot 2.x | 默认 CGLIB | 默认 CGLIB |

**MyBatis 为什么用 JDK 动态代理？**
Mapper 天然是接口，JDK 动态代理正好匹配。

**Spring AOP 为什么 Spring Boot 2.x 后默认 CGLIB？**
避免强依赖接口，更灵活；CGLIB 性能已优化到接近 JDK 代理。

### 5. 观察者模式和发布-订阅模式的区别？

| | 观察者模式 | 发布-订阅模式 |
|--|----------|------------|
| 耦合 | Subject 直接通知 Observer | 通过 Broker/EventBus 解耦 |
| 范围 | 同步、进程内 | 异步、可跨进程 |
| 实现 | `java.util.Observer`、Spring Event | RabbitMQ、Kafka |

**你项目的实践（Flavor Dash）**：
- 进程内（观察者模式）：订单支付成功，通过Spring Event通知积分服务和推荐服务
- 跨进程（发布-订阅模式）：订单状态变更推送到RabbitMQ，WebSocket服务订阅后主动推送前端

### 6. 设计模式的六大原则（SOLID）？

| 原则 | 说明 | 反例 |
|------|------|------|
| **SRP** 单一职责 | 一个类只负责一件事 | UserService 既管用户又管订单又管日志 |
| **OCP** 开闭原则 | 对扩展开放，对修改关闭 | 新增模型 provider 要改核心代码（应该用工厂/策略扩展） |
| **LSP** 里氏替换 | 子类可以替换父类 | 正方形继承长方形，setWidth 改了两个边（违反行为一致） |
| **ISP** 接口隔离 | 接口小而精，不要大而全 | 一个 Animal 接口有 fly() + swim() + run() |
| **DIP** 依赖倒置 | 依赖抽象不依赖具体 | Service 中直接 new 具体 Client（应该注接口） |
| **LoD** 迪米特法则 | 最少知识原则 | A → B → C → D 链式调用，A 不需要知道 C 和 D |

**你项目中的体现**：
- OCP：新增模型 provider 只需加一个实现类 + 配置，不改核心代码
- DIP：`LLMClient` 接口，Service 注入接口不关心具体实现
- SRP：每个微服务职责单一（用户服务只处理用户，订单服务只处理订单）

## 二、Git 版本控制

### 7. Git 常用工作流？分支管理策略？

**Git Flow**：
```
main（生产）
  ├── develop（开发主线）
  │   ├── feature/xxx（功能分支）
  │   ├── release/1.0（发布分支）
  │   └── hotfix/xxx（紧急修复）
```

**GitHub Flow**（更轻量，你用的）：
```
main（始终可部署）
  └── feature-branch → PR → Code Review → Merge to main → 自动部署
```

**常用命令**（面试可能手写）：
```bash
# 分支操作
git branch feature/ai-chat        # 创建分支
git checkout -b feature/ai-chat   # 创建并切换
git merge feature/ai-chat         # 合并到当前分支
git branch -d feature/ai-chat     # 删除分支

# 暂存与提交
git stash                     # 暂存改动
git stash pop                 # 恢复暂存
git add -p                    # 交互式选择提交内容
git commit --amend            # 修改最后一次提交信息

# 远程
git push origin main
git pull --rebase origin main  # 拉取并变基（保持历史线性）

# 历史查看
git log --oneline --graph --all  # 图形化历史
git diff HEAD~1                   # 上次提交的改动
git blame file.java               # 查看每行代码的作者

# 撤销
git reset --soft HEAD~1     # 撤销 commit，保留改动
git reset --hard HEAD~1     # 完全撤销 commit + 改动
git revert HEAD             # 生成一个反向 commit
git checkout -- file.java   # 丢弃工作区改动
```

### 8. Git merge 和 rebase 的区别？

| | merge | rebase |
|--|-------|--------|
| 结果 | 产生新的 merge commit | 将 commit 嫁接到目标分支末尾 |
| 历史 | 保留分支结构，"非线性但真实" | 线性历史，"干净但不真实" |
| 冲突解决 | 一次解决 | 每个 commit 逐个解决 |
| 适用 | 公共分支合并（保留历史） | 个人分支整理（保持整洁） |

**最佳实践**：
- `merge`：feature → main，保留分支痕迹
- `rebase`：main → feature（拉取最新代码），保持 feature 分支干净
- **永远不要 rebase 已推送的公共分支！**（会改写历史导致团队混乱）

### 9. Git 冲突怎么解决？

```bash
# 1. merge/rebase 时出现冲突
# <<<<<<< HEAD
# 你的改动
# =======
# 别人的改动
# >>>>>>> branch-name

# 2. 手动编辑文件，决定保留哪些内容

# 3. 标记解决
git add resolved_file.java

# 4. 继续
git merge --continue      # merge 场景
git rebase --continue     # rebase 场景

# 5. 冲突太复杂想放弃
git merge --abort
git rebase --abort
```

**减少冲突的方法**：
- 频繁拉取最新代码（至少每天一次）
- 小步提交（每个 PR 不要太大）
- 提前沟通：改公共模块前先和团队同步

## 三、Maven 构建工具

### 10. Maven 核心概念？生命周期？

**三大生命周期**（相互独立）：
```
clean 生命周期：
  pre-clean → clean → post-clean

default 生命周期（最常用）：
  validate → compile → test → package → verify → install → deploy

site 生命周期：
  pre-site → site → post-site → site-deploy
```

**坐标系**：`groupId:artifactId:version`（GAV），全网唯一标识一个 jar。

**依赖范围（scope）**：
| scope | 编译 | 测试 | 运行 | 举例 |
|-------|------|------|------|------|
| compile（默认） | ✓ | ✓ | ✓ | spring-boot-starter-web |
| provided | ✓ | ✓ | ✗ | servlet-api、lombok |
| runtime | ✗ | ✓ | ✓ | mysql-connector-j |
| test | ✗ | ✓ | ✗ | junit、mockito |

### 11. Maven 依赖传递和冲突解决？

**依赖传递**：A 依赖 B，B 依赖 C → A 间接依赖 C。

**冲突解决原则**：
1. **最短路径优先**：A → B → C(v1)，A → D → E → C(v2) → 选 v1
2. **第一声明优先**：路径长度相同时，谁在 pom.xml 中先声明选谁
3. **手动排除**：
```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>A</artifactId>
    <exclusions>
        <exclusion>
            <groupId>com.example</groupId>
            <artifactId>C</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```
4. **dependencyManagement**：父 POM 统一管理版本号，子模块不用写版本

**排查冲突**：
```bash
mvn dependency:tree           # 查看依赖树
mvn dependency:tree -Dincludes=com.google.guava  # 只看特定依赖
mvn dependency:analyze        # 分析未使用和未声明的依赖
```

## 四、Docker 与容器化

### 12. Docker 的核心概念？

- **镜像（Image）**：只读模板，类似 Java 的 Class
- **容器（Container）**：镜像的运行实例，类似 new 出来的对象
- **Dockerfile**：构建镜像的脚本
- **Docker Compose**：编排多容器应用
- **Registry**：镜像仓库（Docker Hub / 阿里云 / Harbor）

### 13. Docker 常用命令？

```bash
# 镜像
docker images                    # 查看本地镜像
docker pull openjdk:17-slim      # 拉取镜像
docker build -t my-app:1.0 .     # 构建镜像
docker rmi image_id              # 删除镜像

# 容器
docker run -d -p 8080:8080 --name my-app my-app:1.0
docker ps -a                     # 查看所有容器
docker stop/start/restart container_name
docker logs -f container_name    # 实时日志
docker exec -it container_name bash  # 进入容器
docker rm container_name         # 删除容器
docker rm -f container_name      # 强制删除（运行中）

# Compose
docker-compose up -d             # 后台启动所有服务
docker-compose down              # 停止并删除
docker-compose logs -f           # 查看所有服务日志
docker-compose restart service_name  # 重启单个服务
```

### 14. Dockerfile 常用指令？如何优化镜像大小？

```dockerfile
# 多阶段构建（LingShu灵枢：maven:3.9-eclipse-temurin-21构建JAR → eclipse-temurin:21-jre-alpine运行，镜像从800MB压缩至180MB）
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
COPY pom.xml .
COPY src ./src
RUN mvn clean package -DskipTests

FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**优化策略**：
- **多阶段构建**：构建和运行分离，最终镜像只含 JRE + jar
- **选轻量基础镜像**：alpine（~5MB）vs ubuntu（~70MB）
- **减少层数**：合并 RUN 命令（`RUN cmd1 && cmd2 && cmd3`）
- **.dockerignore**：排除 target、.git、IDE 文件
- **清理缓存**：`apt-get clean`、`rm -rf /var/lib/apt/lists/*`

### 17. 单元测试怎么写？JUnit 5 常用注解？

```java
// SuGuangMall 秒杀模块单元测试示例
@SpringBootTest
@AutoConfigureMockMvc
class OrderServiceTest {

    @MockBean
    private RedisTemplate<String, Object> redisTemplate;

    @Autowired
    private MockMvc mockMvc;

    @Test

        MvcResult result = mockMvc.perform(post("/api/seckill/123")
                .header("Authorization", "Bearer " + jwtToken))

```

**常用注解**：
| 注解 | 说明 |
|------|------|
| @Test | 标识测试方法 |
| @BeforeEach / @AfterEach | 每个测试前后 |
| @BeforeAll / @AfterAll | 所有测试前后（static） |
| @DisplayName | 测试描述 |
| @ParameterizedTest | 参数化测试 |
| @MockBean | Spring Boot Mock Bean |
| @SpyBean | 部分 Mock |
| @DataJpaTest | JPA 切片测试 |

### 18. Mockito 常用操作？

```java
// 打桩（Stub）
when(userService.findById(1L)).thenReturn(mockUser);
when(userService.findById(anyLong())).thenReturn(mockUser);
doThrow(new RuntimeException()).when(userService).delete(1L);

// 验证（Verify）
verify(userService, times(1)).findById(1L);
verify(userService, never()).delete(anyLong());

// 参数匹配
any()、anyString()、anyLong()、eq("value")、argThat(x -> x > 0)

// 捕获参数
ArgumentCaptor<User> captor = ArgumentCaptor.forClass(User.class);
verify(userService).save(captor.capture());
User saved = captor.getValue();
```

**原则**：Given-When-Then（安排→执行→断言），一个测试只测一种场景。

```java
public class OrderService {

        }
    }
}
```

### 20. 如何在项目中做监控（Prometheus + Grafana）？

**你项目中的实践**：

```
Spring Boot Actuator (暴露 metrics 端点)
    ↓
Micrometer (采集 JVM / HTTP / 自定义指标)
    ↓
Prometheus (拉取 metrics 数据)
    ↓
Grafana (可视化面板 + 告警)
```

**关键指标**：
- **QPS**：每秒请求数（`http_server_requests_seconds_count`）
- **RT**：响应时间百分位（P50/P90/P99）
- **错误率**：5xx / 4xx 比例
- **JVM**：堆内存使用、GC 频率/耗时、线程数
- **数据库**：慢查询、连接池使用率
- **Redis**：命中率、连接数
- **AI 模型**（自定义指标）：各 provider 调用量、成功率、延迟、Token 用量

```java
// 自定义指标
@Bean
public MeterRegistryCustomizer<MeterRegistry> metrics() {
    return registry -> {
        registry.gauge("ai.provider.status", 
            Tags.of("provider", "openai"), 
            circuitBreaker, 
            cb -> cb.getState() == State.CLOSED ? 1 : 0);
    };
}

// 或直接用 Timer/Counter
```

## 七、CI/CD

### 21. CI/CD 是什么？你了解哪些工具？

**CI（持续集成）**：代码提交 → 自动构建 → 自动测试 → 反馈结果。
**CD（持续交付/部署）**：通过 CI 的代码 → 自动部署到环境。

**工具链**：
- **代码托管**：GitHub / GitLab
- **CI**：GitHub Actions / Jenkins / GitLab CI
- **镜像构建**：Docker Build → push 到 Registry
- **部署**：Docker Compose / K8s / 云平台（阿里云 ACK）

**GitHub Actions 示例**：
```yaml
name: CI/CD Pipeline
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
      - name: Build & Test
        run: mvn clean test
      - name: SonarQube Scan
        run: mvn sonar:sonar
      - name: Build Docker Image
        run: docker build -t my-app:${{ github.sha }} .
      - name: Push to Registry
        run: docker push registry.example.com/my-app:${{ github.sha }}
```

## 八、技术选型与架构思维

### 22. 技术选型时的考虑因素？

- **业务需求**：是否满足功能？是否过度设计？
- **团队能力**：团队是否熟悉？学习成本？
- **生态成熟度**：社区活跃度、Star 数、Issue 响应速度、文档质量
- **性能**：吞吐量、延迟、资源消耗
- **可维护性**：API 是否稳定？升级兼容性？
- **运维成本**：部署难度、监控、高可用方案
- **许可证**：开源协议是否友好（Apache 2.0 / MIT 无忧，GPL 需谨慎）

**你项目中的决策举例**：
- Redis vs Memcached → Redis（更丰富的数据结构、持久化、集群）
- Consul vs Nacos vs Eureka → Nacos（功能最全：注册中心+配置中心；Eureka 已停维）
- LangChain4j vs Spring AI → LangChain4j（Agent 支持更成熟、社区案例更多）
- Milvus vs Faiss vs Pinecone → Milvus（开源 + Java SDK + 私有部署）
