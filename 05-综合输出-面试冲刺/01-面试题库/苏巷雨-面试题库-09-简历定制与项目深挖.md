## 二、Flavor Dash 深挖（7 题）

> 面试官关注点：Spring Boot 基础功、缓存实战、AI 网关设计

| # | 题目 | 难度 | 答题方向 |
|---|------|------|---------|
| 4 | **LLM Client Factory 多模型网关你是怎么设计的？** | ⭐⭐⭐ | 工厂模式 + 策略模式；OAuth/API Key 多鉴权抽象；SSE 流式 → Flux\<String\> 统一返回；指数退避 2s→4s→10s；Resilience4j CircuitBreaker + TimeLimiter；Token 计数用 JTokkit |
| 5 | **Resilience4j 熔断降级你是怎么配置的？什么场景触发？** | ⭐⭐⭐ | 滑动窗口 COUNT_BASED 10次→失败率>50%→OPEN 60s→HALF_OPEN 3次探测→决定 CLOSE 或重新 OPEN；触发场景：API Key 过期/额度耗尽/模型超时 |
| 6 | **Redis 缓存你是怎么用的？缓存穿透/击穿/雪崩分别怎么解决？** | ⭐⭐ | 穿透→布隆过滤器预判；击穿→分布式锁+双重检查；雪崩→随机TTL过期+X天逻辑过期+Caffeine L1；预热→启动时从DB加载热点数据 |
| 7 | **RAG 管线的 DocumentSplitter 你是怎么做的？** | ⭐⭐ | 按语义分段(标题/段落)而非固定字数；overlap 10~15%防止切断；结合项目知识库(菜品/商家/评价)定制分块策略 |
| 8 | **AI 智能客服的 Function Calling 是怎么实现的？** | ⭐⭐⭐ | 定义 Tool Schema(查订单/退款/催单等)；Prompt 引导 LLM 输出 JSON tool_call；ToolExecutor 解析→执行业务→结果回填→LLM 二次总结；SSE 流式输出给前端 |
| 9 | **Agent 框架的 Think→Act→Observe 循环，你是怎么处理死循环的？** | ⭐⭐⭐ | 最大步数限制(e.g. 10步)+超时控制+重复 action 检测；如果连续3轮相同tool_call则强制退出→LLM总结 |
| 10 | **日均 5000 单，MySQL 扛得住吗？你做了哪些优化？** | ⭐⭐ | 索引优化(联合索引+覆盖索引)；读写分离(主写从读)；慢SQL定时抓取explain分析；热点数据Redis缓存；归档历史订单 |

## 三、SuGuangMall 深挖（9 题）

> 面试官关注点：微服务架构能力、高并发设计、Multi-Agent 创新

| # | 题目 | 难度 | 答题方向 |
|---|------|------|---------|
| 11 | **12 个微服务你是怎么拆的？拆分原则是什么？** | ⭐⭐⭐ | 按业务域拆分：用户/商品/订单/支付/购物车/库存/秒杀/搜索/推荐/通知/管理后台 + 7个AI服务；遵循高内聚低耦合+DDD限界上下文；每个服务独立DB |
| 12 | **秒杀系统全链路怎么设计的？为什么能做到零超卖？** | ⭐⭐⭐⭐ | Nginx limit_conn限流→Sentinel QPS控制→Redis Lua原子操作 `DECR stock:123`→库存<0拒绝→RabbitMQ异步创建订单→死信队列15min关单回滚；预占库存机制：先扣Redis→支付成功确认→超时回滚（详见题库05 #1） |
| 13 | **Lua 脚本原子扣库存具体怎么写？为什么不用 Redis 事务？** | ⭐⭐⭐ | Lua 原子性：`EVAL "if redis.call('get',KEYS[1])>0 then redis.call('decr',KEYS[1]) return 1 else return 0 end" 1 stock:123`；MULTI/EXEC 无逻辑判断能力，Lua 可在服务端做 if 判断 |
| 14 | **JMeter 压测 QPS 2000+，你怎么确定瓶颈在哪？** | ⭐⭐⭐ | JVM: jstack 看线程状态+jstat看GC频率→CPU: top看利用率→DB: 慢查询日志+Druid连接池监控→Redis: redis-cli --latency→网络: ping/traceroute；然后逐个优化：加索引/加缓存/调连接池/异步化 |
| 15 | **Multi-Agent 购物管家的 AgentRouter 意图路由怎么设计？** | ⭐⭐⭐⭐ | 第一层：LLM 意图分类(搜索/比较/推荐/客服/内容/分析)→第二层：关键词规则兜底；如果 LLM 不确定→反问用户澄清；支持多 Agent 串联(搜索→比较→推荐) |
| 16 | **CLIP 以图搜图，为什么选 512 维？Milvus 用的什么索引？** | ⭐⭐ | CLIP ViT-B/32 输出 512 维；Milvus 用 IVF_FLAT(聚类)+PQ(乘积量化)压缩加速；TopK=30 粗排→属性标签精排→LLM 穿搭建议生成 |
| 17 | **Seata AT 模式是怎么回滚的？你遇到过什么坑？** | ⭐⭐⭐ | AT 自动生成 undo_log(前镜像+后镜像)→第二阶段TC通知TM→RM根据undo_log反向SQL回滚；坑：全局锁竞争+性能损耗(RM与TC通信2次/事务)→秒杀场景不用Seata，用最终一致性 |
| 18 | **ShardingSphere 分库分表，为什么按 user_id 分？扩容怎么办？** | ⭐⭐⭐ | user_id 均匀分布+查询以用户维度为主；一致性哈希避免数据迁移；或基因法注入 user_id 后几位到 order_id，关联查询无需跨库 |
| 19 | **Caffeine + Redis 多级缓存，数据一致性怎么保证？** | ⭐⭐ | 写：先更新DB→删Redis→发MQ通知各节点删Caffeine；读：Caffeine miss→Redis→DB→回填；最终一致性(秒级延迟可接受) |

## 四、LingShu 灵枢 深挖（8 题）

> 面试官关注点：系统设计能力、安全意识、工程化落地

| # | 题目 | 难度 | 答题方向 |
|---|------|------|---------|
| 20 | **14 步 RAG 管线，每一步做什么？为什么要这么复杂？** | ⭐⭐⭐⭐ | 列出完整14步：PHI脱敏→意图路由→查询改写→多路召回(BM25+向量)→RRF k=60融合→重排序(70%向量+30%关键词)→上下文构建→Prompt组装→LLM生成→输出护栏→来源溯源→结果缓存→日志记录→反馈收集；医疗场景精度要求高，每步都有意义 |
| 21 | **安全护栏具体怎么设计？输入端+输出端分别做什么？** | ⭐⭐⭐ | 输入：正则+关键词匹配+敏感词库，3级检测→拦截→提示；输出：6条危险模式正则(禁止诊断结论/禁止停药建议/禁止药物剂量)→命中则替换为"请咨询医生"；PHI 脱敏：姓名/电话/身份证号→掩码处理 |
| 22 | **四级异常分类是哪四级？每一级怎么处理？** | ⭐⭐⭐ | L1-参数校验(400)→直接返前端提示；L2-业务异常(自定义BizException)→友好提示；L3-第三方调用失败(模型超时/额度耗尽)→重试+降级(返回默认回复)；L4-未知异常(500)→全局兜底+告警通知 |
| 23 | **Ollama 本地部署踩过什么坑？单机 8GB 够吗？** | ⭐⭐ | 8GB 勉强跑 qwen2:1.5b/llama3.2:3b；坑：模型首次加载慢→预加载+keep_alive；并发请求OOM→限制并发数；量化模型精度损失→医疗场景仅做意图分类，核心生成走云端 |
| 24 | **为什么用 BM25 而不用全向量检索？RRF 融合 k=60 是什么意思？** | ⭐⭐ | BM25 对关键词/术语精准匹配好(如"布洛芬")；向量检索对语义相近好(如"头疼"→"偏头痛")；RRF: `score = Σ 1/(k+rank)`，k=60 起到平滑作用，避免排位极端影响 |
| 25 | **Docker Compose 编排 9 个服务，服务启动顺序怎么解决？** | ⭐⭐ | depends_on + healthcheck(如 MySQL: `mysqladmin ping`)；wait-for-it.sh 脚本；Spring Boot 自身重连机制兜底 |
| 26 | **Python 爬虫采集了哪些数据？怎么构建向量知识库？** | ⭐⭐ | 采集公开医学百科/药品说明书/义诊问答；BeautifulSoup/Scrapy 解析→清洗去重→按症状/科室/药品分类→BGE Embedding→Milvus 存储→定期增量更新 |
| 27 | **单元测试+集成测试全覆盖，你写了多少？怎么组织的？** | ⭐⭐ | JUnit5 + Mockito 单元测试(Service层) + SpringBootTest 集成测试(Controller层) + Testcontainers(MySQL/Redis)；覆盖率 80%+；CI 自动化跑 |

## 五、交叉技术追问（10 题）

> 面试官跨项目对比或深挖某个技术点

| # | 题目 | 难度 | 答题方向 |
|---|------|------|---------|
| 28 | **三个项目都用了 Agent，它们的 ReAct 实现有什么不同？** | ⭐⭐⭐⭐ | Flavor Dash：简单 Tool Registry + AgentMemory；SuGuangMall：LangChain4j + AgentRouter + 6 专业 Agent + YAML 热加载；LingShu：自定义 AgentPlanner + Function Calling JSON 解析 + 双层存储；三者复杂度递增 |
| 29 | **三个项目的 RAG 管线有什么区别？为什么越做越复杂？** | ⭐⭐⭐ | Flavor Dash：基础 DocumentSplitter+Embedding+Milvus 检索(3步)；SuGuangMall：增加 Query Rewrite+混合检索+RRF+MMR(7步)；LingShu：再增加脱敏+意图路由+输出护栏+溯源(14步)；场景从通用→电商搜索→医疗合规，精度要求递增 |
| 30 | **LLM 网关三个项目都有，为什么每个项目都要自己写？不能复用吗？** | ⭐⭐⭐ | 应该复用。实际演进：Flavor Dash 写的基础版→抽象成 common 模块→SuGuangMall 复用并加多模态→LingShu 加安全护栏；理想方案是抽出独立 starter |
| 31 | **Sentinel 三个项目都用了，配置有什么不同？** | ⭐⭐ | Flavor Dash：API 调用熔断(失败率50%→OPEN)；SuGuangMall：网关限流(每个微服务QPS上限)+秒杀专项限流；LingShu：模型调用降级(超时→返回默认回复) |
| 32 | **RabbitMQ 异步削峰，消息丢了怎么办？** | ⭐⭐ | 生产者确认(Publisher Confirm)+持久化(Queue/Message durable)+手动ACK(消费成功再确认)+死信队列兜底+消息补偿任务(定时扫描未处理订单) |
| 33 | **为什么 SuGuangMall 用 Dubbo 又用 OpenFeign？不重复吗？** | ⭐⭐ | Dubbo 用于高频RPC调用(如商品查询，性能好)；OpenFeign 用于声明式HTTP调用(如跨服务CRUD，易调试)；实际以 Feign 为主，Dubbo 补高性能场景 |
| 34 | **JWT + RBAC 权限是怎么设计的？token 过期了怎么办？** | ⭐⭐ | JWT 存 user_id+role→Gateway 解析校验→微服务 @PreAuthorize 注解；双 token：access_token 30min + refresh_token 7d；access 过期用 refresh 换新 |
| 35 | **Prometheus + Grafana 监控了哪些指标？告警规则怎么设的？** | ⭐⭐ | JVM: heap/GC/threads；接口: QPS/RT/错误率；DB: 连接数/慢SQL；Redis: 命中率/内存；告警：错误率>1%/RT>2s/内存>80%→企业微信通知 |
| 36 | **为什么 Seata AT 适合普通下单，但不适合秒杀？** | ⭐⭐ | AT 模式两阶段提交+undo_log 写入+全局锁，RT 增加 30~50%；秒杀追求极致吞吐→用异步+最终一致性+定时对账替代强一致性 |
| 37 | **MCP 协议你实际用过吗？在你的项目里有什么价值？** | ⭐⭐ | MCP 标准化 Agent-Tool 通信协议；如果重构，Agent 调用外部工具(搜索/数据库/API)统一走 MCP Server，不用每个项目单独集成 |
