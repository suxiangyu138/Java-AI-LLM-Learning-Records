一、Java基础与JVM类（必考题）
题目1：HashMap的底层实现原理？JDK1.7和JDK1.8有哪些区别？
解析：核心是“数组+链表/红黑树”的哈希表结构，核心目的是解决哈希冲突、提升查询效率。
1. 底层结构：JDK1.7 是数组+链表；JDK1.8 是数组+链表（链表长度≤8）+红黑树（链表长度>8，数组长度≥64），红黑树目的是将查询时间复杂度从O(n)优化为O(logn)。
2. 哈希冲突解决：采用“链地址法”（链表/红黑树挂载冲突元素），而非开放地址法。
3. 核心区别：① 结构差异（有无红黑树）；② JDK1.7扩容时会出现链表循环（线程不安全），JDK1.8优化了扩容机制，避免循环；③ JDK1.8的hash计算更简洁（减少位运算）；④ JDK1.7是头插法，JDK1.8是尾插法。
4. 补充：HashMap线程不安全，多线程场景用ConcurrentHashMap；初始容量16，负载因子0.75，扩容时容量翻倍。
    题目2：JVM的内存模型是什么？堆、栈、方法区的作用及区别？
    解析：JVM内存模型（JMM）核心是规范线程如何通过内存进行交互，解决多线程可见性、原子性、有序性问题；内存分区（运行时数据区）分为5部分，重点掌握堆、栈、方法区：
    1. 堆（Heap）：① 作用：存储对象实例和数组，是JVM中最大的内存区域；② 特点：线程共享，垃圾回收的主要区域（分年轻代、老年代，年轻代又分Eden区、Survivor区）；③ 异常：OOM（内存溢出）常见于堆内存不足（如对象无法回收、内存泄漏）。
    2. 虚拟机栈（VM Stack）：① 作用：存储栈帧（每个方法调用对应一个栈帧），包含局部变量表、操作数栈、返回地址等；② 特点：线程私有，生命周期与线程一致，栈深度有限；③ 异常：StackOverflowError（栈深度超出限制，如递归无终止条件）、OOM（栈内存扩容失败）。
    3. 方法区（Method Area）：① 作用：存储类信息（类加载器、类结构）、常量、静态变量、即时编译后的代码；② 特点：线程共享，JDK1.8后用“元空间”实现（替代永久代），元空间占用本地内存，而非JVM内存；③ 异常：OOM（如大量动态生成类，导致元空间不足）。
    题目3：Java的垃圾回收机制（GC）？常见的垃圾回收算法有哪些？CMS和G1收集器的区别？
    解析：GC核心是“自动回收不可达对象的内存”，无需手动释放，避免内存泄漏，核心步骤是“标记-清除”（简化）。
    1. 垃圾判断标准：通过“可达性分析”（以GC Roots为起点，遍历对象引用链，不可达对象标记为垃圾），GC Roots包括：虚拟机栈局部变量、方法区静态变量、常量、Native方法引用对象。
    2. 常见垃圾回收算法：
    - 标记-清除算法：先标记垃圾，再清除垃圾；优点：简单；缺点：产生内存碎片，效率低。
    - 复制算法：将内存分为两块，存活对象复制到另一块，清除原块；优点：无内存碎片，效率高；缺点：内存利用率低（仅用一半），适合年轻代（存活对象少）。
    - 标记-整理算法：标记垃圾后，将存活对象移动到一端，再清除垃圾；优点：无内存碎片，内存利用率高；缺点：效率低，适合老年代（存活对象多）。
    - 分代收集算法：结合以上三种，年轻代用复制算法，老年代用标记-整理/标记-清除算法（主流JVM默认）。
    3. CMS与G1收集器区别：
    - CMS（并发标记清除）：以“低延迟”为目标，并发执行（不暂停用户线程）；优点：响应快，适合对延迟敏感的场景；缺点：产生内存碎片、CPU占用高、无法处理浮动垃圾。
    - G1（区域化分代式）：将堆分为多个Region，兼顾延迟和吞吐量；优点：无内存碎片、可预测延迟、支持动态调整Region大小；缺点：复杂度高，适合大堆内存（如8G以上）。
    题目4：volatile关键字的作用？能保证原子性吗？为什么？
    解析：volatile是Java并发编程中的轻量级同步机制，核心作用是“保证可见性、禁止指令重排”，不能保证原子性。
    1. 核心作用：
    - 可见性：当一个线程修改了volatile修饰的变量，其他线程能立即看到修改后的值（强制变量修改后立即刷新到主内存，读取时从主内存读取，而非线程本地缓存）。
    - 禁止指令重排：JVM会对代码进行指令重排优化，volatile会禁止重排（通过内存屏障实现），避免多线程场景下的逻辑错乱（如单例模式双重检查锁中，volatile修饰实例变量）。
    2. 不能保证原子性的原因：原子性是指“一个操作要么全部执行，要么全部不执行”，volatile无法保证复合操作的原子性（如i++，本质是i = i + 1，分三步：读取i、计算i+1、赋值i），多线程下会出现线程安全问题；解决原子性需用synchronized、AtomicInteger等。
    题目5：Java线程池的核心参数？核心原理？如何合理配置线程池参数？
    解析：线程池核心是“复用线程、控制线程数量”，避免频繁创建/销毁线程带来的性能损耗，核心类是ThreadPoolExecutor。
    1. 核心参数（5个）：
    - corePoolSize：核心线程数（常驻线程，即使空闲也不销毁，除非设置allowCoreThreadTimeOut=true）。
    - maximumPoolSize：最大线程数（线程池能容纳的最大线程数，超出核心线程数的线程是临时线程）。
    - keepAliveTime：临时线程的空闲时间，超过该时间，临时线程会被销毁。
    - workQueue：任务队列，用于存放等待执行的任务（如ArrayBlockingQueue、LinkedBlockingQueue）。
    - handler：拒绝策略，当线程数达到最大且队列满时，处理新任务的方式（4种：AbortPolicy抛异常、CallerRunsPolicy由调用线程执行、DiscardPolicy丢弃任务、DiscardOldestPolicy丢弃队列最老任务）。
    2. 核心原理：提交任务时，先判断核心线程是否已满→未满则创建核心线程执行任务→已满则判断队列是否已满→未满则将任务放入队列→已满则判断是否达到最大线程数→未达到则创建临时线程执行→达到则执行拒绝策略。
    3. 合理配置：根据任务类型（CPU密集型、IO密集型）配置：
    - CPU密集型（如计算）：核心线程数 = CPU核心数 + 1（减少线程切换损耗）。
    - IO密集型（如数据库操作、网络请求）：核心线程数 = CPU核心数 × 2（IO操作时线程会空闲，多配置线程提高利用率）。

二、后端框架类（高频题）
题目1：Spring IOC的核心原理？Bean的生命周期？
解析：Spring IOC（控制反转）核心是“将对象的创建、依赖注入交给Spring容器管理”，减少代码耦合，核心接口是BeanFactory、ApplicationContext。
1. 核心原理：
    - 控制反转：原本由程序员手动创建对象（new），反转给Spring容器创建，程序员仅需配置（注解/XML），容器负责对象的实例化、依赖注入（DI）。
    - 实现流程：① 读取配置（注解如@Component、@Service，XML如<bean>）；② 解析配置，生成BeanDefinition（描述Bean的信息）；③ 容器根据BeanDefinition实例化Bean；④ 依赖注入（将依赖的Bean注入到当前Bean中）；⑤ Bean初始化，对外提供使用。
2. Bean的生命周期（核心步骤）：
    1. 实例化（创建Bean对象，调用无参构造器）；
    2. 依赖注入（设置Bean的属性、依赖的Bean）；
    3. 初始化前（调用BeanPostProcessor的postProcessBeforeInitialization方法，前置处理）；
    4. 初始化（调用@PostConstruct注解方法、InitializingBean接口的afterPropertiesSet方法）；
    5. 初始化后（调用BeanPostProcessor的postProcessAfterInitialization方法，后置处理，如AOP代理）；
    6. 销毁（容器关闭时，调用@PreDestroy注解方法、DisposableBean接口的destroy方法）。
    题目2：Spring AOP的实现原理？动态代理有哪两种方式？区别是什么？
    解析：Spring AOP（面向切面编程）核心是“在不修改原有代码的前提下，对方法进行增强”（如日志、事务、权限），底层基于动态代理实现。
    1. 核心概念：
    - 切面（Aspect）：封装增强逻辑的类（如日志切面）；
    - 通知（Advice）：增强的具体逻辑（如前置通知、后置通知、异常通知、环绕通知）；
    - 切入点（Pointcut）：指定哪些方法需要被增强（如所有Service层方法）；
    - 连接点（JoinPoint）：所有可能被增强的方法（切入点是连接点的子集）。
    2. 实现原理：Spring AOP底层用动态代理，有两种方式，根据目标类是否实现接口选择：
    - JDK动态代理：① 前提：目标类实现接口；② 原理：通过Proxy类的newProxyInstance方法，生成接口的代理对象，增强接口方法；③ 缺点：只能增强接口方法，不能增强类的普通方法。
    - CGLIB动态代理：① 前提：目标类不实现接口（或实现接口也可）；② 原理：通过字节码技术，生成目标类的子类，重写目标方法实现增强；③ 缺点：不能增强final修饰的方法（子类无法重写final方法）。
3. 区别：① 依赖：JDK动态代理依赖接口，CGLIB不依赖；② 底层：JDK是接口代理，CGLIB是子类代理；③ 限制：JDK不能增强非接口方法，CGLIB不能增强final方法。
    题目3：Spring Boot的自动配置原理？如何自定义一个自动配置类？
    解析：Spring Boot自动配置核心是“约定优于配置”，减少XML配置，自动配置符合条件的Bean，核心注解是@SpringBootApplication。
    1. 自动配置原理：
    - @SpringBootApplication是复合注解，包含3个核心注解：
    ① @SpringBootConfiguration：本质是@Configuration，标记当前类是配置类；
    ② @ComponentScan：扫描当前包及子包下的@Component、@Service、@Controller等注解，将其注册为Bean；
    ③ @EnableAutoConfiguration：核心注解，开启自动配置。
    - @EnableAutoConfiguration的实现：通过@Import(AutoConfigurationImportSelector.class)，加载META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports文件中的所有自动配置类（如DataSourceAutoConfiguration、WebMvcAutoConfiguration）；每个自动配置类通过@Conditional系列注解（如@ConditionalOnClass、@ConditionalOnMissingBean）判断是否需要生效，生效后自动注册对应的Bean。
    2. 自定义自动配置类步骤：
    1. 新建配置类，添加@Configuration注解；
    2. 添加@Conditional系列注解，指定生效条件（如@ConditionalOnClass(XXX.class)，表示存在XXX类时生效）；
    3. 用@Bean注解注册需要自动配置的Bean；
    4. 在resources/META-INF目录下，创建spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports文件，写入自定义自动配置类的全路径，让Spring Boot扫描到。
    题目4：MyBatis的一级缓存和二级缓存的区别？缓存失效的场景有哪些？
    解析：MyBatis缓存核心是“减少数据库查询次数，提升性能”，分为一级缓存（默认开启）和二级缓存（手动开启）。
    1. 一级缓存：
    - 作用范围：SqlSession级别（一个SqlSession内有效）；
    - 原理：SqlSession执行查询后，将结果缓存到本地，同一SqlSession再次查询相同SQL（参数一致），直接从缓存获取，不查询数据库；
    - 特点：默认开启，无需配置，关闭SqlSession后，缓存失效。
    2. 二级缓存：
    - 作用范围：Mapper接口级别（多个SqlSession共享同一个Mapper的缓存）；
    - 原理：SqlSession查询后，结果缓存到Mapper的二级缓存中，其他SqlSession查询相同Mapper的相同SQL，可复用缓存；
    - 特点：需手动开启（在MyBatis配置文件中设置<setting name="cacheEnabled" value="true"/>，或在Mapper接口上添加@CacheNamespace注解）；缓存的对象需实现Serializable接口（支持序列化）。
    3. 缓存失效场景：
    - 一级缓存失效：① 关闭SqlSession；② 同一SqlSession内执行update、delete、insert操作（会清空当前SqlSession的一级缓存）；③ 手动调用sqlSession.clearCache()。
    - 二级缓存失效：① 执行update、delete、insert操作（会清空当前Mapper的二级缓存）；② 未开启二级缓存；③ 缓存对象未实现Serializable接口。
    题目5：Spring Cloud的核心组件有哪些？Nacos、Feign、Sentinel的作用分别是什么？
    解析：Spring Cloud是微服务架构的一站式解决方案，核心解决微服务的“注册发现、远程调用、限流熔断、配置管理”等问题，常用组件如下：
    1. 核心组件及作用：
    - Nacos：注册中心 + 配置中心；① 注册中心：服务提供者注册服务，服务消费者获取服务列表，实现服务发现；② 配置中心：集中管理所有微服务的配置（开发/测试/生产环境），支持动态刷新配置，无需重启服务。
    - Feign：声明式远程调用组件；基于注解（@FeignClient），简化微服务间的远程调用（无需手动写HttpClient、RestTemplate），支持负载均衡（集成Ribbon）、熔断（集成Sentinel）。
    - Sentinel：限流、熔断、降级组件；① 限流：限制接口的并发请求数，避免服务被压垮；② 熔断：当服务调用失败率达到阈值，自动断开调用，避免级联故障；③ 降级：服务异常时，返回默认值，保证系统可用性。
    - 补充：Gateway（网关）：统一入口，实现路由转发、权限控制、限流等；Seata（分布式事务）：解决微服务间数据一致性问题。

三、中间件类（高频题）
题目1：Redis的核心数据结构有哪些？Redis的持久化机制（RDB和AOF）区别？
解析：Redis是高性能的键值对数据库（内存数据库），核心数据结构有5种，持久化机制用于解决“内存数据丢失”问题。
1. 核心数据结构（5种）：
    - String（字符串）：最基础，存储字符串、数字，常用场景：验证码、计数器、缓存简单数据。
    - Hash（哈希）：存储键值对的集合，适合存储对象（如用户信息），可单独修改对象的某个字段，节省内存。
    - List（列表）：有序、可重复，底层是双向链表，常用场景：消息队列、最新消息列表。
    - Set（集合）：无序、不可重复，支持交集、并集、差集，常用场景：去重、好友列表。
    - ZSet（有序集合）：有序、不可重复，每个元素有一个分数（score），按分数排序，常用场景：排行榜、优先级队列。
2. RDB与AOF持久化区别：
    - RDB（快照持久化）：① 原理：在指定时间间隔内，将内存中的数据生成快照（.rdb文件），写入磁盘；② 优点：体积小、恢复速度快；③ 缺点：数据一致性差（可能丢失最后一次快照后的修改）、备份时会阻塞Redis（大数据量下）。
    - AOF（Append Only File）：① 原理：将每一条写操作（set、del等）追加到AOF文件中，恢复时重新执行文件中的命令；② 优点：数据一致性高（可配置同步策略：每秒同步、每次写同步）、丢失数据少；③ 缺点：文件体积大、恢复速度慢。
3. 补充：Redis默认开启RDB，可同时开启RDB和AOF，恢复时优先加载AOF文件（数据更完整）。
    题目2：Redis缓存穿透、缓存击穿、缓存雪崩的解决方案？
    解析：三者都是Redis缓存使用中的常见问题，核心是“缓存未命中，导致大量请求直接打向数据库，压垮数据库”，解决方案针对性不同：
    1. 缓存穿透：
    - 定义：查询一个“不存在的数据”，缓存中没有，数据库中也没有，导致每次请求都打向数据库（如恶意查询不存在的用户ID）。
    - 解决方案：① 缓存空值：查询不到数据时，缓存一个空值（设置短期过期时间），避免重复查询数据库；② 布隆过滤器：提前将所有存在的key存入布隆过滤器，查询前先判断key是否存在，不存在则直接返回，不查询缓存和数据库。
    2. 缓存击穿：
    - 定义：一个“热点key”（高频查询）过期，此时大量请求同时查询该key，缓存未命中，全部打向数据库。
    - 解决方案：① 热点key永不过期：对于核心热点key，设置为永不过期（避免过期）；② 互斥锁：缓存未命中时，只有一个线程去查询数据库，其他线程等待，查询到数据后更新缓存，避免并发请求打向数据库；③ 预热缓存：提前将热点key加载到缓存中，并设置合理的过期时间。
    3. 缓存雪崩：
    - 定义：大量缓存key在同一时间过期，导致大量请求同时打向数据库，压垮数据库。
    - 解决方案：① 过期时间错开：给每个key的过期时间添加随机值（如10-20分钟），避免同一时间过期；② 集群部署：搭建Redis集群，避免单点故障，即使部分节点失效，其他节点仍能提供服务；③ 降级策略：缓存失效时，返回默认数据（如兜底接口），不直接打向数据库，保护数据库。
    题目3：如何保证MQ消息的可靠性？避免消息丢失、重复消费的方案？
    解析：MQ（如Kafka、RabbitMQ）消息可靠性核心是“消息不丢失、不重复、不重复消费”，分三个环节保障：生产者、MQ服务器、消费者。
    1. 避免消息丢失（三个环节）：
    - 生产者环节：① 开启生产者确认机制（如RabbitMQ的publisher-confirm-type=correlated，Kafka的acks=all），确保消息成功发送到MQ服务器；② 失败重试：消息发送失败时，进行重试（设置合理重试次数和间隔），避免网络波动导致的丢失。
    - MQ服务器环节：① 开启消息持久化（RabbitMQ的队列和消息都设置为持久化，Kafka的topic设置replica副本数≥2），避免MQ服务器宕机导致消息丢失；② 搭建MQ集群，避免单点故障。
    - 消费者环节：① 关闭自动确认（RabbitMQ的ack-mode=manual，Kafka手动提交offset），消费者处理完消息后，手动确认消息，避免消息未处理完就被确认，导致丢失；② 处理失败时，将消息放入死信队列，后续人工处理，不直接丢弃。
    2. 避免消息重复消费：
    - 原因：网络波动、消费者宕机、MQ重试机制，导致同一消息被多次消费。
    - 解决方案：① 消费者端实现幂等性（核心）：无论消费多少次，结果一致（如用数据库唯一索引、Redis分布式锁、消息唯一ID去重）；② 消息唯一标识：给每条消息设置唯一ID（如UUID），消费者消费前先判断该ID是否已消费，已消费则直接跳过。

四、数据库类（必考题）
题目1：MySQL的索引类型有哪些？聚簇索引和非聚簇索引的区别？
解析：MySQL索引核心是“提升查询效率”，本质是“排好序的数据结构”（如B+树），分为聚簇索引和非聚簇索引，常用索引类型如下：
1. 常用索引类型：
    - 主键索引（Primary Key）：唯一标识一条记录，不可为空，一个表只能有一个主键索引，默认是聚簇索引。
    - 唯一索引（Unique Key）：索引列的值唯一，但可以为空，一个表可以有多个唯一索引。
    - 普通索引（Index）：最基础的索引，无唯一性约束，仅用于提升查询效率。
    - 联合索引（Composite Index）：多个列组合而成的索引，遵循“最左前缀原则”（查询时需包含最左列，否则索引失效）。
    - 全文索引（Fulltext Index）：用于文本内容的模糊查询（如文章标题、内容），不适用于短文本、数字。
2. 聚簇索引与非聚簇索引区别：
    - 聚簇索引：① 索引结构与数据存储在一起，索引的叶子节点就是数据本身；② 优点：查询效率高（一次查询即可获取数据）；③ 缺点：插入、删除、更新效率低（需移动数据）；④ 数量：一个表只能有一个聚簇索引（主键索引默认是聚簇索引，无主键则选唯一索引，无唯一索引则自动生成隐藏聚簇索引）。
    - 非聚簇索引：① 索引结构与数据分离，索引的叶子节点存储的是数据的主键值（回表查询）；② 优点：插入、删除、更新效率高（仅需修改索引）；③ 缺点：查询效率低（需先查索引，再根据主键查数据，两次查询）；④ 数量：一个表可以有多个非聚簇索引。
3. 补充：回表查询：非聚簇索引查询时，先找到索引叶子节点的主键值，再通过主键索引（聚簇索引）查询到具体数据，这个过程就是回表。
    题目2：MySQL的事务隔离级别有哪些？默认隔离级别是什么？各隔离级别解决了什么问题？
    解析：事务的四大特性（ACID）：原子性、一致性、隔离性、持久性；隔离级别用于解决“事务并发带来的问题”（脏读、不可重复读、幻读）。
    1. 并发事务的三大问题：
    - 脏读：一个事务读取到另一个事务未提交的修改（该修改可能被回滚，导致读取的数据是无效的）。
    - 不可重复读：一个事务内，多次读取同一数据，结果不一致（被另一个事务修改并提交了）。
    - 幻读：一个事务内，多次查询同一条件的数据，结果行数不一致（被另一个事务插入/删除并提交了）。
    2. 四大隔离级别（从低到高）：
    - 读未提交（Read Uncommitted）：① 允许读取未提交的修改；② 问题：存在脏读、不可重复读、幻读；③ 几乎不用。
    - 读已提交（Read Committed）：① 只能读取已提交的修改；② 解决：脏读；③ 问题：存在不可重复读、幻读；④ 主流数据库默认隔离级别（如Oracle）。
    - 可重复读（Repeatable Read）：① 同一事务内，多次读取同一数据，结果一致（即使被其他事务修改并提交）；② 解决：脏读、不可重复读；③ 问题：存在幻读（MySQL通过MVCC机制解决了幻读）；④ MySQL默认隔离级别。
    - 串行化（Serializable）：① 事务串行执行（一个执行完再执行下一个），完全隔离；② 解决：所有并发问题；③ 缺点：性能极差，仅用于高一致性要求、低并发场景。
    3. 补充：MVCC（多版本并发控制）：MySQL可重复读隔离级别解决幻读的核心机制，通过保存数据的多个版本，让事务读取到指定版本的数据，避免幻读。
    题目3：SQL优化的常用方法有哪些？
    解析：SQL优化核心是“减少数据库查询时间，降低数据库压力”，从索引、SQL语句、表结构三个维度优化：
    1. 索引优化（最核心）：
    - 给查询频繁的列、WHERE条件列、JOIN关联列创建索引；
    - 避免索引失效：① 不使用SELECT *（避免回表，只查需要的列）；② 避免WHERE子句中使用函数、表达式（如where age+1=10，索引失效）；③ 避免WHERE子句中使用!=、<>、NOT IN、IS NULL、IS NOT NULL（索引失效）；④ 联合索引遵循最左前缀原则。
    2. SQL语句优化：
    - 避免子查询，用JOIN替代（子查询效率低，会创建临时表）；
    - 避免JOIN过多表（一般不超过3张表，JOIN越多，效率越低）；
    - 避免使用DISTINCT、ORDER BY（尽量让索引完成排序，减少数据库排序）；
    - 批量操作（批量插入、批量更新，减少数据库连接次数）；
    - 用EXPLAIN分析SQL执行计划，定位慢查询（重点看type、key、rows字段）。
    3. 表结构优化：
    - 选择合适的数据类型（如用INT替代VARCHAR存储数字，用TIMESTAMP替代DATETIME，节省内存）；
    - 分库分表（针对大数据量表，如订单表，按时间、用户ID分表，减少单表数据量）；
    - 读写分离（主库负责写操作，从库负责读操作，分担主库压力）；
    - 避免冗余字段，合理设计表关联（遵循三大范式）。

五、工程化与DevOps类（高频题）
题目1：CI/CD的核心概念？Java项目如何实现CI/CD流程？
解析：CI/CD是DevOps的核心，核心是“自动化编译、测试、部署”，提升交付效率，减少人为失误。
1. 核心概念：
    - CI（持续集成）：开发人员频繁（每天）将代码合并到主干，自动完成编译、单元测试、代码扫描，尽早发现代码问题（如语法错误、测试不通过）。
    - CD（持续交付）：CI通过后，自动将制品（Jar包、Docker镜像）部署到测试/预发环境，随时可手动发布到生产。
    - CD（持续部署）：在持续交付基础上，自动化将合格的制品发布到生产环境，无需人工干预。
2. Java项目CI/CD实现流程（以Jenkins为例）：
    1. 代码提交：开发人员将Java代码提交到Git仓库（GitLab/GitHub）；
    2. 触发CI：通过Webhook触发Jenkins CI流程（提交代码、合并MR时触发）；
    3. 自动化编译：用Maven/Gradle编译Java代码，打包成Jar包；
    4. 质量验证：① 单元测试（JUnit5+Mockito），检查测试覆盖率；② 代码扫描（SonarQube），检查代码规范、漏洞；
    5. 制品归档：将Jar包/Docker镜像推送到制品仓库（Nexus/Harbor）；
    6. CD部署：① 测试环境：自动部署到测试服务器（Docker/K8s），执行接口测试；② 预发环境：人工审批后，自动部署，执行性能测试；③ 生产环境：人工审批后，通过灰度发布部署到生产集群。

    题目2：Docker容器化部署Java应用的步骤？Docker与虚拟机的区别？
    解析：Docker是轻量级容器技术，核心是“打包应用及依赖，实现环境一致性”，Java应用容器化是后端开发必备技能。
    1. Java应用Docker容器化步骤：
    1. 编写Dockerfile（核心）：指定基础镜像（如openjdk:11）、复制Jar包、暴露端口、设置启动命令（如java -jar xxx.jar）；
    2. 构建Docker镜像：执行docker build -t 镜像名:版本 . （如docker build -t springboot-app:1.0 .）；
    3. 运行Docker容器：执行docker run -d -p 宿主机端口:容器端口 镜像名（如docker run -d -p 8080:8080 springboot-app:1.0）；
    4. 推送镜像：将镜像推送到Harbor/Nexus制品仓库，供部署使用。
    2. Docker与虚拟机的区别：
    - 底层架构：① Docker：基于宿主机内核，共享宿主机操作系统资源，容器之间隔离的是进程（轻量级隔离），无需模拟完整操作系统；② 虚拟机（VM）：基于Hypervisor虚拟化技术，每个虚拟机都有独立的操作系统（内核、系统文件），模拟完整硬件环境，隔离级别高。
    - 资源占用：① Docker：轻量级，占用资源少（仅占用应用运行所需资源，无系统开销），启动速度快（秒级启动）；② 虚拟机：重量级，占用资源多（需分配独立CPU、内存、磁盘，有系统运行开销），启动速度慢（分钟级启动）。
    - 部署效率：① Docker：打包应用及依赖为镜像，可快速在任意支持Docker的环境中部署，实现“一次构建、到处运行”，解决Java应用“环境不一致”痛点；② 虚拟机：需安装完整操作系统，再部署应用，部署繁琐，环境迁移成本高。
    - 隔离性：① Docker：进程级隔离，隔离性较弱，容器之间可能共享宿主机资源（如内核），一个容器故障可能影响其他容器；② 虚拟机：系统级隔离，隔离性强，每个虚拟机独立运行，互不影响，安全性更高。
    - 适用场景：① Docker：适合Java微服务部署、高频迭代的应用（如互联网项目），追求部署效率和资源利用率；② 虚拟机：适合对安全性、隔离性要求高的场景（如金融、政务系统），或需要运行不同操作系统的应用。
3. 补充：Java应用容器化核心优势——解决“开发环境能跑、测试/生产环境报错”的问题，通过Docker镜像统一运行环境，配合K8s可实现容器编排（扩容、滚动更新），适配微服务架构。
