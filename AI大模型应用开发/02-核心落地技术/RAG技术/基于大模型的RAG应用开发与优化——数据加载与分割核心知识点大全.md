## 一、核心定位

- **数据加载**：将原始数据转化为大模型可识别格式，是"知识入库"第一步
- **数据分割**：将完整数据拆解为大小合适、语义连贯的"知识片段"，解决上下文窗口限制，提升检索精度

## 二、数据加载

### 2.1 常见数据来源

| 类型 | 示例 |
|------|------|
| 文档类 | PDF、Word、Excel、PPT、TXT、Markdown |
| 数据库类 | MySQL、PostgreSQL、MongoDB、Redis |
| 网页/接口类 | 企业官网、内部知识库、API |
| 其他 | 语音转文字、图片 OCR、邮件、聊天记录 |

### 2.2 核心加载工具

| 工具 | 适配场景 | 实操要点 |
|------|----------|----------|
| **LangChain Document Loaders** | 多格式文档、数据库、网页 | PDF：PyPDFLoader（可编辑）、UnstructuredPDFLoader（扫描+OCR） |
| **LlamaIndex Loaders** | 复杂文档、多源数据融合 | 自动提取目录/标题层级，支持增量加载 |
| **自定义 Loader** | 企业私有格式、加密文件 | Python 实现"读取→解析→提取文本" |

### 2.3 加载后的处理步骤

- **内容提取**：剔除页眉、页脚、水印、空白页
- **编码统一**：全部转为 UTF-8
- **初步去重**：删除完全重复内容
- **元数据标注**：文档类型、上传时间、所属部门、关键词

### 2.4 常见问题

| 问题 | 解决方案 |
|------|----------|
| 扫描版 PDF 无法提取文本 | OCR 工具（Tesseract） |
| 大文件加载卡顿 | 分块加载、流式读取 |
| 数据库权限不足 | 最小权限账号，仅开放查询 |
| 多源格式不统一 | 统一转为文本格式 + 元数据 |

## 三、数据分割

### 3.1 核心原则

- **语义连贯**：不能拆分一句话或一个知识点
- **大小适配**：通常 128-512 tokens，复杂场景可达 512-2048 tokens
- **粒度合理**：产品手册按功能模块拆分，合同按条款拆分

### 3.2 分割策略

| 策略 | 说明 | 推荐场景 |
|------|------|----------|
| **语义分割**（首选） | 按段落、句子、标题层级递归拆分 | 大多数企业场景 |
| **固定长度分割**（兜底） | 按固定字符/tokens 数拆分 | 日志、聊天记录 |
| **自定义分割** | 按文档结构或业务规则拆分 | 合同、行业规范 |

### 3.3 关键参数

- **chunk_size**：128-512 tokens（常见），复杂场景放宽到 512-2048
- **chunk_overlap**：chunk_size 的 10%-20%

### 3.4 分割工具对比

| 工具 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| LangChain RecursiveCharacterTextSplitter | 语义连贯、可自定义 | 无结构文本效果一般 | 大多数企业场景 |
| LlamaIndex HierarchicalSplitter | 保留层级结构 | 集成复杂度高 | 结构化文档 |
| 固定长度分割 | 简单高效 | 易拆分语义 | 无结构文本兜底 |
| 自定义分割 | 贴合业务 | 开发成本高 | 合同、行业规范 |

### 3.5 优化技巧

- **粒度动态调整**：短文档不分割，中长按段落，超长按章节
- **保留元数据关联**：每个片段继承原文档元数据
- **重叠窗口优化**：避免长文本语义断裂
- **增量分割**：仅处理新增/修改文档
- **分割后清洗**：剔除无效片段（仅标点、空白）

---

## 核心要点回顾

- 加载：适配多源数据，格式解析 + 初步清洗 + 元数据标注
- 分割：优先语义分割，结合固定长度分割兜底
- 参数：chunk_size 128-1024 tokens，overlap 10%-20%
- 工程化：自动化流水线、容错机制、性能优化、安全性
