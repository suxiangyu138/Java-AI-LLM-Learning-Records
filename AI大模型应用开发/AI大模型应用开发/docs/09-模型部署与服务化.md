```

├────────────────┼──────────────┼──────────────┼──────────────┤

│ 定制能力        │ 有限          │ 完全          │ 中等          │
│ 弹性扩展        │ 无限          │ 受硬件限制    │ 灵活          │
└────────────────┴──────────────┴──────────────┴──────────────┘
```

### 1.2 部署决策树

```
需要 100% 数据不出内网？
├── 是 → 需要微调模型？
│         ├── 是 → 70B+ 模型微调 → 至少 A100×4
│         └── 否 → 仅推理 →
│               ├── 7B 模型满足需求？→ 单卡 RTX 4090 / A10
│               ├── 70B 模型满足需求？→ A100×2 / H100×1
│               └── 405B+ 模型满足需求？→ H100×8
└── 否 → 调用 API 即可
```

### 2.2 显存估算公式

```
模型推理显存 ≈ 参数量 × 精度字节数 × 1.2

精度字节数：
  FP32:  4 bytes
  FP16:  2 bytes
  INT8:  1 byte
  INT4:  0.5 bytes

示例：
  7B FP16:  7 × 2 × 1.2 = 16.8 GB → 24GB 显存 OK
  7B INT4:  7 × 0.5 × 1.2 = 4.2 GB → 6GB 显存就能跑
  70B FP16: 70 × 2 × 1.2 = 168 GB → 需要 A100×4
  70B INT4: 70 × 0.5 × 1.2 = 42 GB → A100×1 可跑

还要加 KV Cache：
  KV Cache ≈ 2 × num_layers × hidden_dim × num_kv_heads/num_heads
            × context_length × dtype_bytes

  7B 模型 4K context，GQA 下：额外 ~0.5-1 GB
  70B 模型 128K context：额外 ~20-40 GB

总显存 = 模型权重 + KV Cache + 框架开销 (~10%)
```

## 5. 模型网关

### 5.1 多模型路由网关

```java
@Component
public class ModelGateway {

    /**
     * 多模型路由策略：
     * 1. 简单问题 → 便宜的小模型
     * 2. 复杂问题 → 贵的大模型
     * 3. 特定领域 → 领域微调模型
     */
    public ModelRoute route(String userMessage, UserContext ctx) {
        // 策略 1：意图识别后路由
        String intent = classifyIntent(userMessage);

        return switch (intent) {
            case "GREETING", "SIMPLE_QA" ->
                new ModelRoute("qwen2.5-7b", "cheap", 0.001);
            case "CODE", "MATH", "LOGICAL" ->
                new ModelRoute("deepseek-v3", "powerful", 0.01);
            case "LEGAL" ->
                new ModelRoute("law-ft-model", "domain", 0.005);
            default ->
                new ModelRoute("gpt-4o", "default", 0.008);
        };
    }

    /**
     * Fallback 策略
     */
    public String callWithFallback(String message, ModelRoute primaryRoute) {
        try {
            return callModel(primaryRoute.model(), message);
        } catch (TimeoutException | RateLimitException e) {
            // 降级到备用模型
            log.warn("Primary model {} failed: {}", primaryRoute.model(), e.getMessage());
            return callModel(primaryRoute.fallbackModel(), message);
        }
    }
}
```

### 5.2 模型网关核心功能

```
企业模型网关功能清单：
├── 路由决策：意图 → 模型（规则/ML）
├── 负载均衡：轮询/最少连接/一致性哈希
├── 故障转移：主模型挂了 → 备用模型
├── 限流：按用户/API Key/模型限流
├── 缓存：相同问题缓存答案（语义缓存）
├── 日志审计：所有请求和响应记录
├── 成本追踪：按用户/部门/模型统计
├── A/B 测试：分流到不同 Prompt/模型
└── 内容过滤：输入输出安全审核
```

## 6. 性能优化

### 6.1 推理优化技术栈

```
推理优化金字塔：

         ┌─────────────┐
         │  量化 (INT4) │  ← 最大收益（4× 减内存，2× 加速）
         ├─────────────┤
         │  KV Cache   │  ← PagedAttention (vLLM)
         ├─────────────┤
         │ Flash Attn  │  ← IO-aware，加速+省显存
         ├─────────────┤
         │Cont. Batching│  ← 动态批处理，提高吞吐
         ├─────────────┤
         │Spec. Decode │  ← 推测解码，2-3× 加速
         └─────────────┘
```

### 6.2 持续批处理 (Continuous Batching)

```
传统静态批处理：
  [req1, req2, req3] → 等最长的 req3 完成 → [req4, req5, req6]
  缺点：短请求等长请求，GPU 空闲

持续批处理 (vLLM)：
  [req1, req2, req3, req4, req5]
   req1,req2 完成 → 立刻加入 req6,req7
  不用等待整批完成，GPU 利用率高

吞吐量提升：5-10×
```

### 6.3 语义缓存

```java
@Service
public class SemanticCache {

    private final VectorStore cacheStore;
    private final EmbeddingModel embeddingModel;
    private static final double SIMILARITY_THRESHOLD = 0.95;

    /**
     * 语义缓存：相似的问题返回缓存的答案
     */
    public Optional<String> get(String question) {
        List<Document> results = cacheStore.similaritySearch(
            SearchRequest.query(question)
                .withTopK(1)
                .withSimilarityThreshold(SIMILARITY_THRESHOLD)
        );

        if (!results.isEmpty()) {
            String answer = results.get(0).getMetadata().get("answer").toString();
            log.info("Cache hit! Saved tokens");
            return Optional.of(answer);
        }
        return Optional.empty();
    }

    public void put(String question, String answer) {
        float[] embedding = embeddingModel.embed(question);
        Document doc = new Document(question,
            Map.of("answer", answer, "cached_at", Instant.now().toString()));
        doc.setEmbedding(embedding);
        cacheStore.add(List.of(doc));
    }
}

// 在 ChatService 中使用
public String chat(String question) {
    // 1. 先查缓存
    return semanticCache.get(question)
        .orElseGet(() -> {
            // 2. 缓存未命中，调用 LLM
            String answer = callLLM(question);
            // 3. 存入缓存
            semanticCache.put(question, answer);
            return answer;
        });
}
```

## 7. 冷启动优化

### 7.1 模型加载优化

```
冷启动时间（7B 模型为例）：
  Ollama:         ~5-10s
  vLLM:           ~10-30s
  原生 Transformers: ~30-60s
  首次请求延迟：模型加载 + 预热

优化策略：
├── 1. 模型持久化到 SSD/NVMe（非网络存储）
├── 2. 预加载：启动时加载模型，就绪后再接流量
├── 3. 预热请求：就绪探针时发送 dummy 请求
├── 4. 模型副本：保持一定数量的 warm pod
└── 5. 共享内存：同一节点多个 Pod 共享模型文件
```

### 7.2 K8s 预热配置

```yaml
# 就绪探针 + 预热脚本
containers:
- name: vllm
  readinessProbe:
    httpGet:
      path: /health
      port: 8000
    initialDelaySeconds: 60         # 等待模型加载
    periodSeconds: 10
    failureThreshold: 10           # 失败 10 次才标记 NotReady

  lifecycle:
    postStart:
      exec:
        command:
        - /bin/sh
        - -c
        - |
          # 预热：发送 dummy 请求
          sleep 30
          curl -s http://localhost:8000/v1/chat/completions \
            -H "Content-Type: application/json" \
            -d '{"model":"qwen2.5-7b","messages":[{"role":"user","content":"test"}]}'
```
