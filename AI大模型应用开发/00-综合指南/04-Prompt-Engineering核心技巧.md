# ✍️ Prompt Engineering 核心技巧

> Prompt Engineering 是 AI 开发中门槛最低、回报最高的技术。一个好的 Prompt 能零成本地将模型输出质量提升 50% 以上。它不像微调那样需要数据和 GPU，也不像 RAG 那样需要搭建检索系统——只需要你掌握与 AI 有效沟通的语言艺术。本文从黄金公式出发，逐步深入到 Few-shot、CoT 和结构化输出等高级技巧。

## 1. Prompt 的黄金公式

### 1.1 四要素模型

一个高质量的 Prompt 必须包含以下四个要素：

```
Prompt = 角色 + 任务 + 约束 + 格式

角色：你是一个资深的 Java 后端架构师
任务：分析以下代码的性能瓶颈并给出优化方案
约束：每个瓶颈至少给出 2 种替代方案，包含时间复杂度分析
格式：用 Markdown 表格输出，按优化收益降序排列
```

### 1.2 对比演示

**❌ 低质量 Prompt：**
```
帮我优化这段代码
```

**✅ 高质量 Prompt：**
```
你是一名具有 10 年经验的 Java 性能优化专家。
请对以下代码进行全面分析：

1. 识别所有性能瓶颈（按严重程度排序）
2. 对每个瓶颈，提供至少 2 种优化方案
3. 标注每种方案的时间复杂度变化和预期提升
4. 如果涉及并发安全，特别标注

输出格式：
| 瓶颈 | 严重程度 | 优化方案 | 复杂度变化 | 预期提升 |
|------|---------|---------|-----------|---------|
```

> **重点**：差 Prompt 和好 Prompt 之间的差距，往往比不同模型之间的差距还要大。写好 Prompt，就是用最低成本激发模型的最好表现。

### 1.3 Prompt 长度——不是越短越好

```
研究数据（基于 GPT-4 测试）：
- Prompt < 50 字：输出质量不可控，模型自行脑补
- Prompt 100-300 字：最优区间，指令清晰但不过度约束
- Prompt > 500 字：回报递减，模型可能忽略部分指令
- Prompt > 2000 字：需要分段指令 + 结构化分隔符
```

## 2. 角色扮演：赋予模型专业身份

### 2.1 为什么角色扮演有效

大模型在预训练期间阅读了大量专业文档。当你指定一个角色时，实际上是在**激活模型参数中与该角色相关的知识子空间**——让模型用更专业的"口吻"和"知识体系"来回答问题。

### 2.2 角色设计模式

```markdown
# 模式 1：专业角色 + 背景信息
你是一位专注于微服务架构的 Java 技术顾问，经常为金融行业提供技术方案。
你熟悉 Spring Cloud、Kubernetes 和分布式事务处理。

# 模式 2：角色 + 思维框架
你是一位采用"第一性原理"思考的软件架构师。
在回答任何架构问题时，你遵循以下框架：
1. 先定义核心问题
2. 拆解为子问题
3. 评估每种方案的 trade-off
4. 给出推荐的决策路径

# 模式 3：角色 + 输出风格
你是一位善于用类比解释复杂概念的编程导师。
你的解释风格是：
- 用生活中熟悉的场景做类比
- 每个概念不超过 2 个类比
- 类比之后必须回到技术本身给出准确定义
```

### 2.3 角色扮演的效果对比

| 场景 | 无角色 Prompt | 带角色 Prompt | 效果提升 |
|------|-------------|-------------|---------|
| 代码审查 | "帮我 review 这段代码" | "你是一位亚马逊的 SDE III..." | +40% 发现更多隐患 |
| 技术写作 | "写一篇关于 Redis 的文章" | "你是 Redis 官方文档作者..." | +35% 更专业准确 |
| 面试模拟 | "模拟一场技术面试" | "你是一位严格的字节跳动面试官..." | +50% 更有针对性 |

## 3. Few-Shot：用示例教学

### 3.1 Few-Shot 的核心原理

模型从示例中**隐式学习**模式，而非从指令中**显式**遵循规则。几个高质量示例的效果往往超过长篇指令说明。

### 3.2 示例设计的四个原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **多样性** | 覆盖正例、反例、边界案例 | 正常输入、错误输入、极短/极长输入 |
| **完整性** | 示例必须包含完整的输入输出对 | 不要只给输出，不给输入 |
| **一致性** | 所有示例遵循相同的格式和风格 | 不要混用不同格式的输出 |
| **渐进性** | 从简单到复杂排列 | 先简单案例，后复杂案例 |

### 3.3 Few-Shot 代码示例

```python
prompt = """
你将扮演代码审查员，对代码片段进行分类和风险评估。

输入 → 输出格式：
{分类} | {风险等级} | {问题描述}

示例 1：
输入：sql = "SELECT * FROM users WHERE id = " + userId
输出：SQL注入 | 高危 | 使用字符串拼接构造SQL，应改用参数化查询

示例 2：
输入：for i in range(len(data)): print(data[i])
输出：代码风格 | 低危 | 应使用 for item in data 替代索引遍历

现在，分析以下代码：
输入：password = hashlib.md5(user_input.encode()).hexdigest()
"""
```

## 4. 思维链：让模型"展示工作"

### 4.1 CoT 的本质

**思维链（Chain-of-Thought, CoT）** 是通过要求模型**逐步推理**来提升复杂问题准确率的技巧。它不改变模型本身，只改变 Prompt 的写法。

```
无 CoT：
Q: 小明有 5 个苹果，给了小红 2 个，又买了 3 个，现在有几个？
A: 6 个

有 CoT（要求展示推理过程）：
Q: 小明有 5 个苹果，给了小红 2 个，又买了 3 个，现在有几个？
A: 让我们逐步思考：
   1. 小明最初有 5 个苹果
   2. 给了小红 2 个：5 - 2 = 3 个
   3. 又买了 3 个：3 + 3 = 6 个
   4. 最终答案：6 个
```

### 4.2 CoT 适用场景

| 适合用 CoT | 不适合用 CoT |
|-----------|------------|
| 数学计算 | 简单事实查询 |
| 逻辑推理 | 情感表达 |
| 代码调试 | 翻译任务 |
| 多步骤分析 | 创造性写作 |
| 方案设计 | 角色对话 |

### 4.3 Zero-Shot CoT：万能触发词

你甚至不需要提供示例，只需要在 Prompt 末尾加上一句魔法短语：

```
让我们一步一步思考。
Let's think step by step.
```

这简单的 8 个字，能将 GPT 在数学推理任务上的准确率从 **18% 提升到 79%**（论文数据）。

### 4.4 高级变体

| CoT 变体 | 核心思想 | 适用场景 |
|----------|---------|---------|
| **Self-Consistency** | 多次采样 + 投票 | 需要更高准确率时 |
| **Tree-of-Thought** | 多路径探索 + 回溯 | 复杂决策问题 |
| **Auto-CoT** | 自动生成推理链 | 批量任务自动化 |
| **ReAct** | 推理 + 行动交替 | Agent 场景 |

## 5. 结构化输出：强制格式控制

### 5.1 为什么需要结构化输出

当你需要将 LLM 的输出接入程序时（如解析 API 返回、存入数据库），自由文本格式就是一场灾难。**结构化输出**让模型返回可预测、可解析的数据格式。

### 5.2 JSON 输出约束

```markdown
请用以下 JSON 格式输出你的分析结果。严格遵守格式，不要添加任何 JSON 之外的文字。

```json
{
  "summary": "一句话总结",
  "issues": [
    {
      "severity": "high|medium|low",
      "category": "performance|security|style|logic",
      "file": "文件名",
      "line": 数字,
      "description": "问题描述",
      "suggestion": "改进建议"
    }
  ],
  "score": 1-10
}
```

要分析的代码：
[代码内容]
```

### 5.3 Markdown 表格输出

```markdown
请用 Markdown 表格输出。表格列：
| 方案 | 优点 | 缺点 | 适用场景 | 实施难度 |

如果某个方面不适用，填写 N/A。
不要省略任何列。
```

## 6. 实战模板集合

### 6.1 Java 代码审查模板

```markdown
## 角色
你是一位 Java 性能优化专家，曾在阿里巴巴中间件团队工作 8 年。

## 任务
审查以下代码，输出完整的审查报告。

## 审查维度（按优先级）
1. 线程安全：是否存在竞态条件、死锁风险、不当的锁粒度
2. 性能：是否存在 N+1 查询、不必要的对象创建、IO 阻塞
3. 异常处理：是否存在异常吞噬、过于宽泛的 catch
4. 代码规范：命名、注释、设计模式使用

## 输出格式
对每个问题，输出：
- 位置（行号）
- 严重程度（致命/严重/一般/建议）
- 问题描述
- 修复代码（完整可用的代码片段）

[被审查的代码]
```

### 6.2 技术方案选型模板

```markdown
## 角色
你是一位技术架构顾问，擅长为创业公司提供技术选型建议。

## 场景
[描述你的业务场景]

## 要求
请比较以下方案，从以下维度分析：
1. 学习成本（团队能否快速上手）
2. 生态成熟度（社区活跃度、第三方库、文档质量）
3. 性能特性（吞吐量、延迟、资源消耗）
4. 运维复杂度（部署、监控、扩展）
5. 长期维护成本

## 输出格式
| 维度 | 方案A | 方案B | 方案C |
|------|-------|-------|-------|

最后给出你的推荐排序和理由。
```

### 6.3 学习路径生成模板

```markdown
## 角色
你是一位有着 15 年经验的资深技术导师，擅长为不同背景的工程师定制学习路径。

## 学习者背景
- 当前水平：[描述]
- 目标：[描述]
- 可用时间：每周 [X] 小时
- 学习风格：[偏理论/偏实战/均衡]

## 要求
请设计一份 [N] 周的学习计划，结构如下：
1. 每周学习目标（可量化的）
2. 学习内容（具体到文章/视频/练习）
3. 实战项目（每周至少 1 个动手任务）
4. 检查点（学完的标准是什么）
5. 常见陷阱提醒

## 输出格式
使用 Markdown 表格，每周一行。
```

## 核心要点回顾

- **黄金公式**：角色 + 任务 + 约束 + 格式 = 高质量 Prompt
- **角色扮演**激活模型的专业知识子空间，效果提升 35-50%
- **Few-Shot** 用示例"教会"模型模式，优于长篇指令
- **思维链** 让复杂推理准确率翻倍，触发词是"让我们一步一步思考"
- **结构化输出** 是 AI 应用对接程序的桥梁，输出格式先行定义
- 写好 Prompt 不需要 GPU，不需要数据——它是 AI 开发中**投入产出比最高**的技能
