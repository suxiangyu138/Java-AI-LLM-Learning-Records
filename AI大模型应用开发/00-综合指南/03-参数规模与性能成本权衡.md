## 1. 参数规模的真实影响

### 1.1 参数与能力的关系（非线性）

```
模型能力提升曲线：

  能力
   ↑
   │                                    ┌── 100B+
   │                          ┌──── 70B
   │                   ┌── 30B
   │             ┌── 13B
   │        ┌─ 7B
   │   ┌─ 3B
   │── 1B
   └──────────────────────────→ 参数量

关键拐点在 7B 和 70B 附近。
从 1B 到 7B 是质的飞跃；从 70B 到 100B+ 提升递减。
```

### 1.2 参数的回报递减效应

| 参数规模 | 基准能力 | 增量收益 | 推理成本（相对1B） |
|----------|---------|---------|-------------------|
| 1B | 基础语言理解 | — | 1× |
| 7B | 流利对话 | +60% | 7× |
| 13B | 初步推理 | +20% | 13× |
| 70B | 复杂推理 | +15% | 70× |
| 405B | 专家级推理 | +5% | 405× |

> **重点**：从 7B 到 70B，能力提升约 35-40%，但成本增加 10 倍。从 70B 到 405B，能力提升不到 10%，但成本增加近 6 倍。**参数规模越大，性价比越低**。

## 2. 性能≠参数规模：多维度评估

### 2.1 影响模型实际表现的因素

```
模型最终表现 = f(参数规模, 训练数据质量, 训练方法, 微调质量, Prompt 质量, 推理设置)
```

| 因素 | 影响权重 | 说明 |
|------|---------|------|
| **数据质量** | ⭐⭐⭐⭐⭐ | 高质量数据的小模型 > 低质量数据的大模型 |
| **训练方法** | ⭐⭐⭐⭐ | RLHF/DPO 对齐显著提升可用性 |
| **Prompt 质量** | ⭐⭐⭐⭐ | 好 Prompt 能让 7B 模型输出超越裸 70B |
| **微调质量** | ⭐⭐⭐⭐⭐ | 精细化微调的 7B > 通用 70B（垂直领域） |
| **参数规模** | ⭐⭐⭐ | 重要但非决定性因素 |
| **推理参数** | ⭐⭐ | temperature、top_p 等调节输出风格 |

### 2.2 真实场景验证

```
案例：某电商客服场景

指标              通用 GPT-4     微调后 Qwen-7B
─────────────────────────────────────────────
回复准确率          91%            89%
回复相关性          88%            92%（垂直领域更懂行话）
单次延迟            800ms          200ms
日成本（10万次）    $200           $15
─────────────────────────────────────────────
结论：微调后的 7B 模型在垂直领域的性价比远超大模型
```

## 3. 推理成本的构成分析

### 3.1 API 调用成本模型

```python
# API 调用成本计算

class CostCalculator:
    """LLM API 调用成本估算器"""

    @staticmethod
    def estimate(
        model: str,
        input_tokens: int,
        output_tokens: int,
        calls_per_day: int
    ) -> dict:
        """估算每日/每月成本"""
        # 参考定价（2026年行情，单位：元/百万token）
        pricing = {
            "gpt-4o":           {"input": 35, "output": 105},
            "gpt-4o-mini":     {"input": 2,  "output": 8},
            "claude-sonnet":    {"input": 21, "output": 70},
            "deepseek-v3":     {"input": 1,  "output": 2},
            "qwen-max":        {"input": 5,  "output": 15},
            "local-7b":        {"input": 0,  "output": 0},  # 本地仅电费
        }

        p = pricing.get(model, {"input": 10, "output": 30})

        cost_per_call = (input_tokens * p["input"] + output_tokens * p["output"]) / 1_000_000
        daily_cost = cost_per_call * calls_per_day
        monthly_cost = daily_cost * 30

        return {
            "模型": model,
            "单次成本": f"¥{cost_per_call:.4f}",
            "日成本(万次)": f"¥{daily_cost:.2f}",
            "月成本(万次/日)": f"¥{monthly_cost:,.0f}"
        }


# 场景：每次对话 2000 input + 500 output tokens
calc = CostCalculator()
for model in ["gpt-4o", "claude-sonnet", "deepseek-v3"]:
    result = calc.estimate(model, 2000, 500, 10_000)
    print(result)
```

### 3.2 本地部署硬件成本

| 模型规模 | 最小显存 | 推荐 GPU | GPU 价格（参考） | 月电费（7×24） |
|----------|---------|---------|-----------------|---------------|
| 7B (INT4) | 4GB | RTX 3060 12GB | ¥2,000 | ¥150 |
| 7B (FP16) | 14GB | RTX 3090 24GB | ¥6,000 | ¥300 |
| 13B (INT4) | 7GB | RTX 3090 24GB | ¥6,000 | ¥300 |
| 70B (INT4) | 35GB | A100 80GB | ¥80,000 | ¥500 |
| 70B (FP16) | 140GB | 2×A100 | ¥160,000 | ¥1,000 |

### 3.3 API vs 本地部署的分界线

```
日调用量 < 1,000次    → API 更划算（零固定成本）
日调用量 1,000-10,000  → 两可地带（取决于 GPU 利用率）
日调用量 > 10,000次    → 本地部署边际成本优势明显
```

## 4. 量化：以小博大的核心技术

### 4.1 量化原理

**量化（Quantization）** 是将模型参数的精度从高比特位降低到低比特位，从而压缩模型体积、加速推理。

```
FP32：每个参数 32 位（4 字节）
FP16：每个参数 16 位（2 字节）  ← 体积减半，精度基本无损
INT8：每个参数 8 位（1 字节）   ← 体积为 1/4，精度轻微损失
INT4：每个参数 4 位（0.5 字节） ← 体积为 1/8，需接受一定质量下降
```

### 4.2 量化方法对比

| 方法 | 精度 | 压缩比 | 推理加速 | 适用场景 |
|------|------|--------|---------|---------|
| **GPTQ** | INT4/INT8 | 4-8× | 2-4× | GPU 推理（需校准数据） |
| **AWQ** | INT4 | 8× | 3-4× | GPU 推理（保护关键权重） |
| **GGUF** | Q2-Q8 | 2-8× | CPU 可用 | 消费级设备、CPU 推理 |
| **bitsandbytes** | INT4/INT8 | 4-8× | 2-3× | 训练时量化（QLoRA） |

### 4.3 量化效果实测

```python
# 使用 transformers + bitsandbytes 加载量化模型
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
import torch

# INT4 量化配置
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_compute_dtype=torch.float16,
    bnb_4bit_use_double_quant=True,   # 双重量化：进一步压缩
    bnb_4bit_quant_type="nf4"         # NF4：更适合正态分布的权重量化
)

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct",
    quantization_config=bnb_config,
    device_map="auto"
)

# 显存对比：
# FP16：~14GB
# INT4（单重量化）：~5GB
# INT4+Nested（双重量化）：~4GB
```

> **注意**：量化不是万能的。INT4 以下（Q2、Q3）的量化会导致明显的质量下降，不建议生产环境使用。**INT4 + AWQ/GPTQ 是当前性价比最优解**。

## 5. 模型路由：大小模型协同

### 5.1 分层路由策略

并非每个请求都需要最大模型来处理。**模型路由（Model Router）** 根据请求复杂度动态选择模型：

```
用户请求
    │
    ▼
┌─────────────┐
│ 意图分类器   │  ← 轻量级模型，极低成本
└─────────────┘
    │
    ├── 简单闲聊 ──→ 7B 本地模型（0 成本）
    ├── 常规问答 ──→ DeepSeek-V3（极低成本）
    ├── 复杂推理 ──→ Claude Sonnet（中等成本）
    └── 关键任务 ──→ GPT-4o / Claude Opus（最高质量）
```

### 5.2 路由实现框架

```python
class ModelRouter:
    """智能模型路由器"""

    def __init__(self):
        self.models = {
            "tiny":   {"name": "qwen2.5:1.5b", "cost": 0,     "priority": 1},
            "small":  {"name": "deepseek-chat", "cost": 0.001, "priority": 2},
            "medium": {"name": "claude-sonnet", "cost": 0.005, "priority": 3},
            "large":  {"name": "gpt-4o",        "cost": 0.015, "priority": 4},
        }

    def route(self, query: str, context: dict = None) -> str:
        """根据查询特征选择模型"""
        # 规则 1：超短问候 → tiny
        if len(query) < 15:
            return "tiny"

        # 规则 2：简单事实查询 → small
        if any(kw in query for kw in ["是什么", "怎么用", "解释"]):
            return "small"

        # 规则 3：需要深度推理 → medium
        if any(kw in query for kw in ["为什么", "如何设计", "架构", "源码"]):
            return "medium"

        # 规则 4：关键任务标识 → large
        if context and context.get("priority") == "critical":
            return "large"

        return "small"  # 默认使用便宜的

    def call(self, query: str, context: dict = None) -> str:
        model_key = self.route(query, context)
        model = self.models[model_key]
```

## 6. ROI 计算模型

### 6.1 综合 TCO（总拥有成本）公式

```
TCO/月 = 硬件折旧 + GPU 电费 + API 调用费 + 运维人力 + Prompt 缓存节省

其中：
- 硬件折旧 = GPU 价格 / 36（3年折旧）
- API 调用费 = 日调用量 × 单次 token × 单价 × 30
- 运维人力 = 工程师时薪 × 运维小时数/月
```

### 6.2 典型场景 ROI 速查

| 场景 | 日调用量 | 推荐方案 | 月成本 | 备注 |
|------|---------|---------|--------|------|
| 个人项目 | <100 | API（DeepSeek） | <¥10 | 零运维 |
| 创业验证 | 100-1000 | API + 缓存 | ¥100-500 | 快速迭代 |
| 中小企业 | 1000-10000 | 云 GPU + 开源 7B | ¥500-3000 | 可控成本 |
| 中大型企业 | 1万-10万 | 本地 70B 集群 | ¥5000-20000 | 数据安全 |
| 大规模服务 | 10万+ | 自建集群 + MoE | ¥20000+ | 极致优化 |

## 核心要点回顾

- **能力 ≠ 参数量**：数据质量、微调质量、Prompt 质量的影响往往大于参数规模
- 量化是性价比之王：**INT4 + AWQ** 可将模型压缩 8×，推理加速 3-4×，质量损失极小
- 模型路由是工程必选项：80% 的请求用低成本模型处理，仅 20% 需要大模型
- API vs 本地的分界线在**日调用量 1000-10000 次**之间
- **ROI 最优解 = 微调后的 7-30B 模型 + INT4 量化 + 模型路由**（绝大多数场景）
