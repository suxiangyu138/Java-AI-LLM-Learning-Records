# 源码阅读加速 —— AI 导读攻克 Spring/MyBatis 源码

## 传统方法的困境

打开 Spring 源码 → 点 `AnnotationConfigApplicationContext` → 跳 `AbstractApplicationContext` → 跳 `BeanFactory` → 跳 `BeanDefinitionReader` → 50 次跳转后迷失在调用链中。

**根本问题**：你不缺代码，缺的是"地图"。AI 就是你的源码导航仪。

---

## AI 源码导读 4 步法

### 步骤 1：让 AI 画架构全景图

```
我正在阅读 Spring IoC 容器初始化源码，请帮我：
1. 画出核心类图（用 ASCII art）
   - BeanFactory → ApplicationContext 继承链
   - BeanDefinitionReader / Scanner 的角色
2. 标注每个核心类的单一职责（一句话）
3. 标注关键设计模式（工厂/策略/模板方法）

用以下格式：
```
```
AbstractBeanFactory
│  职责：BeanFactory 的基础实现，定义 getBean() 的完整流程
│  模式：模板方法模式 —— 定义骨架，子类实现细节
├── AbstractAutowireCapableBeanFactory
│  职责：支持自动装配和 BeanPostProcessor
└── DefaultListableBeanFactory
   职责：BeanDefinition 注册表 + 完整 BeanFactory 实现
```

### 步骤 2：让 AI 分解核心流程

```
请把 refresh() 方法的 12 个步骤逐一拆解：

对每个步骤（如 obtainFreshBeanFactory()），输出：
1. 这一步做什么（1 句话）
2. 入参/出参是什么
3. 内部调用了哪几个关键方法
4. 如果这一步失败会发生什么
5. 对应的源码入口文件名 + 大致行号范围
```

### 步骤 3：让 AI 生成简化版代码

```
请基于 Spring IoC 初始化流程，写一个极简版的 DI 容器实现：
- 支持 @Component 扫描
- 支持 @Autowired 注入
- 支持 @PostConstruct 生命周期
- 总代码量 < 200 行
- 保留核心设计模式，去掉性能优化和异常处理
```

**价值**：200 行代码跑通 DI 核心流程，理解 Spring 20 万行代码的骨架。看完简化版再回看源码，不再迷失。

### 步骤 4：让 AI 回答"为什么这样设计"

```
在 AbstractApplicationContext.refresh() 中：
1. 为什么 BeanFactoryPostProcessor 要在 Bean 实例化之前执行？
2. 为什么 registerBeanPostProcessors() 和 invokeBeanFactoryPostProcessors() 
   要分成两个步骤？
3. 为什么 finishBeanFactoryInitialization() 放在最后而不是中间？
4. 如果让你重新设计，你会怎样调整这个流程？

请答出设计者当年的权衡（trade-off），不要只描述功能。
```

## 源码阅读分层策略

| 层级 | 目标 | AI 角色 | 耗时 |
|------|------|--------|------|
| L1：架构概览 | 理解模块划分和核心类 | 画类图/架构图 | 30 分钟 |
| L2：核心流程 | 理解关键方法的调用链 | 拆解步骤，标注关键类 | 1 小时 |
| L3：简化实现 | 手写迷你版理解本质 | 生成极简 Demo 代码 | 1.5 小时 |
| L4：设计哲学 | 理解设计权衡和历史背景 | 回答"为什么"，对比替代方案 | 30 分钟 |

总计：~3.5 小时理解一个框架的核心机制，而传统方法需要 3-7 天。

## Java 后端必读源码 AI 导读清单

| 框架 | 核心模块 | 传统耗时 | AI 加速 |

## 反模式

```
❌ AI 给了类图后就觉得自己懂了
❌ 不看源码只看 AI 总结
❌ 跳过简化实现环节直接看复杂源码

✅ 先看 AI 的架构图形成心智模型
✅ 对照 AI 的调用链说明走读源码（IDE 打断点）
✅ 手写简化版 Demo 跑通核心流程
✅ 追问 3 次"为什么"，触及设计原则
```
