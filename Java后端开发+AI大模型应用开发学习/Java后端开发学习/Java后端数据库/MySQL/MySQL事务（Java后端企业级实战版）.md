MySQL事务（Java后端企业级实战版）
第九章：MySQL事务（Java后端核心实战）
核心说明：Java后端开发中，多表操作、批量操作场景（如创建订单、分配权限），往往需要“多个SQL语句同时成功或同时失败”，否则会导致数据不一致（如订单创建成功但订单详情未插入、用户扣费成功但商品未出库）。MySQL事务（Transaction）正是解决这一问题的核心工具——它将一组SQL语句封装为一个“不可分割的操作单元”，要么全部执行成功，要么全部执行失败，保障数据一致性。本章衔接前文多表操作、视图、用户与权限知识点，重点讲解事务的ACID特性、事务操作、隔离级别及Java后端实战用法，全程贴合企业级开发场景（如订单创建、权限分配），规避冗余理论，确保与前文知识点连贯，同时覆盖事务的核心避坑点。
前置基础：已掌握多表关联操作、视图使用、用户与权限体系的多表结构，明确多表批量操作的痛点（如SQL执行部分成功导致数据混乱），理解“数据一致性”对后端系统的重要性（如电商订单、金融支付场景，数据错误会造成严重损失）。
9.1 核心认知：什么是事务（Java后端视角）
事务是MySQL中一组“不可分割的SQL执行单元”，核心目标是保证数据一致性。简单来说，事务就是“要么一起成，要么一起败”——当一组SQL语句（如新增订单+新增订单详情）中，有任意一条执行失败，所有已执行的SQL都会回滚（撤销），回到操作前的状态；只有所有SQL都执行成功，事务才会提交（确认操作），数据才会真正写入数据库。
Java后端实战场景（必须用事务的3种情况）：
多表关联操作：如创建订单（新增t_order + 新增t_order_detail），两个操作必须同时成功，否则会出现“有订单无详情”或“有详情无订单”的异常；
批量操作：如批量删除用户（删除t_user + 删除t_user_role关联数据），需确保所有用户及关联数据都删除，避免部分删除导致数据冗余；
敏感操作：如用户充值、商品出库（扣减余额 + 扣减库存），需确保扣款和库存扣减同时成功，避免“扣钱未出库”或“出库未扣钱”的财务异常。
关键提醒：事务仅对INNODB存储引擎有效（前文表设计均指定ENGINE=InnoDB），MyISAM存储引擎不支持事务，企业级开发中需严格使用INNODB引擎，避免事务失效。
9.2 事务核心特性：ACID（企业级必懂）
事务的四大特性（ACID）是事务可靠性的核心保障，也是Java后端面试高频考点，结合实战场景理解，无需死记硬背，重点掌握“为什么需要这个特性”。
9.2.1 原子性（Atomicity）—— 核心特性
定义：事务中的所有SQL操作，要么全部执行成功，要么全部执行失败，没有“部分成功”的情况，事务是一个不可分割的整体。
实战场景：创建订单时，执行“新增t_order”和“新增t_order_detail”两条SQL。若新增订单详情失败，原子性会保证“新增t_order”的操作回滚（撤销），不会出现“有订单无详情”的数据混乱。
9.2.2 一致性（Consistency）—— 最终目标
定义：事务执行前后，数据库中的数据始终保持“合法状态”，符合业务规则和约束（如主键唯一、非空约束、外键约束）。
实战场景：用户充值100元，执行“扣减用户余额100”和“增加商品库存”两条SQL。若事务执行失败，一致性会保证余额和库存回到操作前的状态，不会出现“余额减少但库存未增加”的非法状态。
9.2.3 隔离性（Isolation）—— 避免并发问题
定义：多个事务同时执行时，各个事务之间相互隔离，一个事务的执行不会影响其他事务的执行，避免并发操作导致的数据异常（如脏读、不可重复读）。
实战场景：两个用户同时给同一个商品下单（扣减库存），隔离性会保证两个事务相互独立，不会出现“库存扣减负数”的异常（后续9.4节详细讲解隔离级别）。
9.2.4 持久性（Durability）—— 数据安全保障
定义：事务一旦提交（COMMIT），数据就会永久写入数据库，即使数据库崩溃、重启，提交的数据也不会丢失。
实战场景：用户下单成功（事务提交），即使MySQL突然崩溃，重启后订单数据依然存在，不会丢失，保障业务数据安全。
9.3 事务核心操作（企业级实战）
MySQL事务的操作语法简洁，核心是“开启事务→执行SQL→提交/回滚事务”，结合Java后端实战场景（创建订单、分配权限），重点讲解实战用法，贴合企业级规范。以下操作均基于db_ecommerce数据库，复用前文订单、用户与权限相关表结构。
9.3.1 事务的基本操作（手动控制）
企业级开发中，手动控制事务（开启、提交、回滚）是核心，可精准控制事务的执行范围，避免不必要的性能开销。
-- 1. 开启事务（默认自动提交关闭，后续SQL纳入事务）
START TRANSACTION;  -- 或 BEGIN; 两种语法等价
-- 2. 执行一组SQL操作（如创建订单：新增订单主表+新增订单详情）
INSERT INTO t_order (order_no, user_id, total_price, order_status)
VALUES ('20241001003', 1, 6999.00, 0);  -- 新增订单主表
INSERT INTO t_order_detail (order_id, goods_id, goods_name, goods_price, buy_num)
VALUES (3, 2, '华为Mate60', 5999.00, 1);  -- 新增订单详情（关联订单id=3）
-- 3. 提交事务（所有SQL执行成功，数据永久写入）
COMMIT;
-- 4. 回滚事务（若任意一条SQL失败，执行回滚，撤销所有操作）
-- ROLLBACK;  -- 仅在SQL执行失败时使用
实战演示：事务回滚场景
START TRANSACTION;
-- 新增订单主表（成功）
INSERT INTO t_order (order_no, user_id, total_price, order_status)
VALUES ('20241001004', 1, 7999.00, 0);
-- 新增订单详情（失败，假设goods_id=100不存在，外键约束报错）
INSERT INTO t_order_detail (order_id, goods_id, goods_name, goods_price, buy_num)
VALUES (4, 100, '不存在的商品', 1000.00, 1);
-- 由于第二条SQL失败，执行回滚，第一条SQL的操作会被撤销
ROLLBACK;
执行后，t_order表中不会有order_no=20241001004的订单，确保数据一致性，避免“有订单无详情”的异常。
9.3.2 自动提交与关闭（Java后端适配）
MySQL默认开启“自动提交”（autocommit=1），即每条SQL语句都会自动作为一个独立事务，执行后立即提交。Java后端开发中，多表操作需关闭自动提交，手动控制事务，避免部分SQL提交、部分失败。
-- 查看自动提交状态（1=开启，0=关闭）
SELECT @@autocommit;
-- 关闭自动提交（仅当前会话有效，Java后端连接数据库时可配置）
SET autocommit = 0;
-- 开启自动提交（恢复默认）
SET autocommit = 1;
Java后端关联实战
后端通过MyBatis、Spring框架控制事务时，会自动关闭自动提交，手动开启事务，执行完业务逻辑后提交事务，出现异常时自动回滚。例如，Spring中通过@Transactional注解，可快速实现事务控制，无需手动编写START TRANSACTION、COMMIT等SQL。
9.3.3 事务的保存点（SAVEPOINT）—— 进阶用法
复杂事务中，可设置保存点，实现“部分回滚”——即回滚到保存点，而非回滚整个事务，适配多步骤复杂业务场景（如订单创建+库存扣减+日志记录，若日志记录失败，仅回滚日志，保留订单和库存操作）。
START TRANSACTION;
-- 步骤1：新增订单（成功）
INSERT INTO t_order (order_no, user_id, total_price, order_status)
VALUES ('20241001005', 1, 8999.00, 0);
-- 设置保存点（标记步骤1执行完毕）
SAVEPOINT order_save;
-- 步骤2：扣减商品库存（成功）
UPDATE t_goods SET stock = stock - 1 WHERE id = 2 AND is_delete = 0;
-- 设置保存点（标记步骤2执行完毕）
SAVEPOINT stock_save;
-- 步骤3：记录操作日志（失败）
INSERT INTO t_operation_log (user_id, operation, create_time)
VALUES (1, '创建订单', NOW());  -- 假设t_operation_log表不存在，执行失败
-- 回滚到stock_save保存点（仅撤销步骤3，保留步骤1、步骤2）
ROLLBACK TO stock_save;
-- 提交事务（确认步骤1、步骤2的操作）
COMMIT;
关键提醒：保存点仅在当前事务中有效，事务提交或回滚后，保存点自动失效；企业级开发中，仅复杂业务场景（多步骤、可部分回滚）使用，简单场景无需使用，避免增加复杂度。
9.4 事务隔离级别（解决并发问题）
Java后端高并发场景（如秒杀、多用户同时下单），多个事务同时执行会出现并发问题（脏读、不可重复读、幻读），MySQL通过“隔离级别”控制事务之间的隔离程度，解决这些并发问题。MySQL默认隔离级别为“可重复读”，适配大多数企业级场景。
9.4.1 常见并发问题（必懂）
脏读：一个事务读取到另一个事务“未提交”的数据，若该事务回滚，读取到的数据就是“无效数据”。例如：用户A充值100元（事务未提交），用户B查询A的余额，读取到100元，随后A的事务回滚，B读取到的就是脏数据。
不可重复读：一个事务内，多次读取同一数据，结果不一致（被另一个事务修改并提交）。例如：用户A查询余额为1000元，同时用户B扣减A的500元并提交，A再次查询余额为500元，两次读取结果不同。
幻读：一个事务内，多次查询同一条件的数据，结果行数不一致（被另一个事务新增/删除并提交）。例如：管理员查询未删除用户有10人，同时另一个事务新增1个用户并提交，管理员再次查询变为11人，出现“幻觉”。
9.4.2 MySQL四大隔离级别（企业级实战）
MySQL提供四种隔离级别，从低到高依次为：读未提交、读已提交、可重复读、串行化，隔离级别越高，并发问题越少，但性能越低，企业级开发需根据业务场景选择（默认可重复读）。

9.4.3 隔离级别的设置（Java后端适配）
可通过SQL设置全局隔离级别（所有会话生效）或当前会话隔离级别（仅当前连接生效），企业级开发中，通常在数据库配置文件中设置，或通过Spring框架配置，无需手动执行SQL。
-- 查看全局隔离级别
SELECT @@global.tx_isolation;
-- 查看当前会话隔离级别
SELECT @@tx_isolation;
-- 设置全局隔离级别为可重复读（默认）
SET GLOBAL tx_isolation = 'REPEATABLE-READ';
-- 设置当前会话隔离级别为串行化
SET SESSION tx_isolation = 'SERIALIZABLE';
Java后端实战适配
Spring框架中，可通过@Transactional注解的isolation属性设置隔离级别，例如：@Transactional(isolation = Isolation.REPEATABLE_READ)，无需手动操作MySQL隔离级别，适配业务场景需求。
9.5 事务的企业级避坑指南（Java后端必看）
事务使用不当会导致事务失效、数据不一致、性能隐患等问题，以下避坑点结合Java后端实战场景，避免后期返工和线上故障。
避坑1：使用MyISAM存储引擎
❌ 错误：表使用MyISAM引擎，事务操作无效（MyISAM不支持事务），导致数据不一致；
✅ 正确：所有核心业务表（t_user、t_order、t_role等）均使用INNODB引擎，与前文表设计规范保持一致。
避坑2：事务范围过大
❌ 错误：将无关操作（如日志记录、接口调用）纳入事务，导致事务执行时间过长，锁表时间久，降低并发性能；
✅ 正确：事务仅包含“必须保证一致性的SQL操作”，无关操作（日志、通知）放在事务提交后执行。
避坑3：忽略异常处理，导致事务无法回滚
❌ 错误：Java后端代码中，捕获异常后未抛出，导致Spring事务无法感知异常，无法触发回滚；
✅ 正确：捕获异常后，需重新抛出异常（如throw new RuntimeException()），或在@Transactional注解中指定rollbackFor属性，确保异常触发回滚。
避坑4：并发场景未设置合适的隔离级别
❌ 错误：高并发秒杀场景使用默认隔离级别（可重复读），导致幻读、库存超卖；
✅ 正确：高并发、数据一致性要求高的场景（如库存扣减），设置隔离级别为串行化，或结合乐观锁、悲观锁使用。
避坑5：手动事务忘记提交/回滚
❌ 错误：手动开启事务（START TRANSACTION）后，忘记执行COMMIT或ROLLBACK，导致事务长期未结束，锁表阻塞其他操作；
✅ 正确：手动控制事务时，必须在try-catch块中处理，确保异常时回滚，正常时提交。
避坑6：视图操作纳入事务
❌ 错误：将视图的修改操作（INSERT/UPDATE）纳入事务，视图是虚拟表，修改视图本质是修改底层表，易导致事务异常；
✅ 正确：事务仅操作底层表，视图仅用于查询，不参与事务中的修改操作。

9.7 本章小结（Java后端重点）
事务的核心价值是保证多SQL操作的数据一致性，核心特性是ACID（原子性、一致性、隔离性、持久性），原子性是基础，一致性是最终目标；
核心操作：开启（START TRANSACTION）、提交（COMMIT）、回滚（ROLLBACK），保存点用于复杂场景的部分回滚，简单场景无需使用；
隔离级别用于解决并发问题，MySQL默认可重复读，企业级开发需根据业务场景选择（高并发选读已提交，高一致性选串行化）；
避坑核心：使用INNODB引擎、控制事务范围、正确处理异常、设置合适的隔离级别，避免事务失效和数据不一致；
后续章节：讲解索引（提升事务执行效率）、存储过程与函数（封装复杂事务逻辑），进一步完善Java后端数据库操作体系，适配高并发、复杂业务场景。
