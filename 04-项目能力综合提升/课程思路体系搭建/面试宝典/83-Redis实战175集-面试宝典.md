## 一、基础概念速答

### 1. NoSQL 和关系型数据库的区别？
> 理解 NoSQL 的定位和适用场景是 Redis 面试的基础。

| 对比维度 | 关系型数据库（MySQL） | NoSQL（Redis） |
|---------|:------------------:|:-------------:|
| 数据模型 | 表结构、关系 | KV、文档、图、列族 |
| 查询方式 | SQL 标准查询 | API 操作 |
| ACID | 完整支持 | 有限支持 |
| 扩展方式 | 垂直扩展为主 | 水平扩展天然 |
| 适用场景 | 强事务、复杂查询 | 高并发、简单查询 |
| 一致性 | 强一致 | 最终一致 |

> 💡 NoSQL 和 RDBMS 是互补关系，实际项目通常是 RDBMS + NoSQL 混合使用。

### 2. Redis 安装启动的三种方式？
> 开发和生产环境可以选择不同的启动方式。

```bash
# 1. 前台启动（调试用）
redis-server

# 2. 后台启动（配置文件模式，生产推荐）
redis-server /etc/redis/6379.conf

# 3. Docker 启动
docker run -d --name redis -p 6379:6379 redis:7.0
```

**配置文件关键项**：
```text
daemonize yes                 # 后台运行
port 6379                     # 端口
logfile /var/log/redis.log    # 日志路径
dir /var/lib/redis            # 数据持久化目录
requirepass yourpassword      # 密码
```

### 3. Redis 通用命令都有哪些？
> 通用命令适用于所有数据类型，面试中按场景考查。

```bash
# 基础通用命令
KEYS pattern         # 查找所有匹配的 key（线上禁止使用，会阻塞）
SCAN cursor [MATCH pattern] [COUNT count]  # 分批遍历 key（推荐替代 KEYS）
EXISTS key           # 判断 key 是否存在
TYPE key             # 返回 key 的类型
DELETE key           # 删除 key
UNLINK key           # 异步删除（4.0+，后台线程删除，不阻塞）

# 过期相关
EXPIRE key seconds   # 设置过期时间（秒）
TTL key              # 查看剩余过期时间
PERSIST key          # 移除过期时间

# 其他
RANDOMKEY            # 随机返回一个 key
RENAME key newkey    # 重命名 key
SORT key             # 对 List/Set/ZSet 排序
DUMP key              # 序列化 key
RESTORE key ttl serialized-value  # 反序列化
```

> 🎯 大忌：不能在线上执行 `KEYS *`，如果 Redis 中有百万级 key，会直接阻塞。一律用 `SCAN` 代替。

### 4. Redis Key 的层级格式设计？
> 合理的 key 命名能提升可维护性和性能。

```text
# 推荐格式：业务名:对象名:ID[:属性]
shop:user:1001              # 用户
shop:product:2001           # 商品
shop:order:3001             # 订单
shop:product:2001:detail    # 商品详情

# Hash Tag 用法（集群模式下强制同槽）
shop:{user:1001}:profile
shop:{user:1001}:address
# 使用 {} 圈定的部分用于计算哈希槽，相同 hash tag 的 key 在同一槽位
```

**设计原则**：
1. **可读性**：见名知意，通过 key 就能知道数据含义
2. **防冲突**：不同业务用不同前缀
3. **方便管理**：按前缀分组管理，批量操作可按前缀扫描
4. **控制长度**：key 越长占用内存越多，保持适度

### 5. String 类型底层编码详解？
> Redis String 有三种编码方式：INT、EMBSTR、RAW。

**编码转换条件**：
```text
整数（可转为 long） -> INT       # 如 SET age 25
长度 <= 44 字节      -> EMBSTR   # Redis 3.2+ 为 44，之前是 39
长度 > 44 字节       -> RAW      # 堆内存分配
```

**EMBSTR vs RAW**：
| 比较 | EMBSTR | RAW |
|------|--------|-----|
| 内存分配 | 一次分配（Object + SDS 连续） | 两次分配（Object 和 SDS 分开） |
| 内存释放 | 一次 free | 两次 free |
| 修改操作 | 只读，修改会转为 RAW | 可读写 |
| 效率 | 更高（缓存友好） | 一般 |

> 💡 EMBSTR 的 44 字节限制是怎么来的？因为 Redis Object（16 字节）+ SDS 头 + 空终止符（1 字节）+ 数据，总大小 <= 64 字节（jemalloc 的最小分配单位）。

### 6. Hash 类型的底层实现？
> Hash 在元素较少时使用 ZipList，元素增多后升级为 HashTable。

**ZipList 条件**：
```bash
# 当满足以下两个条件时使用 ZipList：
hash-max-ziplist-entries 512    # 元素数量 < 512
hash-max-ziplist-value 64       # 单个 value 长度 < 64 字节
```

**Hash 常用命令**：
```bash
HSET user:1001 name "张三" age "25"
HGET user:1001 name        # 获取单个字段
HMGET user:1001 name age   # 获取多个字段
HGETALL user:1001          # 获取所有字段（慎用，大 Hash 会阻塞）
HINCRBY user:1001 age 1    # 字段自增
HEXISTS user:1001 name     # 判断字段是否存在
HDEL user:1001 age         # 删除字段
HLEN user:1001              # 获取字段数量
```

**适用场景**：适合存储对象结构（用户信息、商品详情、配置信息）——相比 String 存储整个 JSON，Hash 可以独立读写单个字段，节省带宽。

### 7. Set 类型的应用场景？
> Set 的"无序不重复"和"交并差"运算特性决定了它的应用场景。

**核心命令**：
```bash
SADD set member1            # 添加元素
SMEMBERS set                # 获取所有元素
SISMEMBER set member1       # 判断元素是否存在
SCARD set                   # 元素数量
SREM set member1            # 删除元素
SINTER set1 set2            # 交集（共同好友）
SUNION set1 set2            # 并集
SDIFF set1 set2             # 差集
SRANDMEMBER set 3           # 随机获取 3 个元素
SPOP set 1                  # 随机弹出一个元素
```

**典型场景**：
- **标签系统**：用户标签用 Set 存储，通过 SINTER 找到有相同标签的用户
- **共同关注**：两个用户的关注列表取交集
- **抽奖系统**：SPOP 随机抽取中奖用户
- **好友推荐**：用 SDIFF 找出"我的好友"和"好友的好友"之间的差异

### 8. SortedSet 底层实现详解？
> ZSet 的底层是 ZipList 或 SkipList + Dict 的组合。

**编码条件**：
```bash
# ZipList 条件（同时满足）
zset-max-ziplist-entries 128   # 元素 < 128
zset-max-ziplist-value 64      # 元素值 < 64 字节
# 超出任一条件即使用 SkipList + Dict
```

**SkipList + Dict 双结构**：
```
SkipList：按 score 排序，支持范围查询（O(logN)）
Dict：按 member 查询 score（O(1)）
```

```bash
# ZSet 核心命令
ZADD leaderboard 100 member1 200 member2
ZRANK leaderboard member1       # 按 score 升序排名
ZREVRANK leaderboard member1    # 按 score 降序排名
ZRANGE leaderboard 0 9          # Top 10（升序）
ZREVRANGE leaderboard 0 9       # Top 10（降序）
ZINCRBY leaderboard 10 member1  # 增加分数
ZSCORE leaderboard member1      # 获取分数
ZCOUNT leaderboard 100 200      # 统计分数区间内元素数
ZRANGEBYSCORE leaderboard 100 200  # 按分数范围获取
```

> 💡 ZSet 的实现非常巧妙：用 SkipList 处理排序操作，用 Dict 处理精确查询，两者共用 member 和 score 数据。

### 9. GEO 类型底层是什么？
> GEO 底层使用 ZSet 存储，score 是 GeoHash 的整数编码。

**基本原理**：
1. 将经纬度通过 GeoHash 算法编码为一个 52 位整数（作为 ZSet 的 score）
2. 使用 ZSet 的 ZRANGEBYSCORE 实现附近位置查询
3. GeoHash 编码越长精度越高，且编码前缀匹配表示位置接近

```bash
# GEO 命令
GEOADD cities 121.47 31.23 "上海"   # 添加地理位置
GEOPOS cities "上海"                # 获取位置坐标
GEODIST cities "上海" "北京" km     # 计算距离
GEORADIUS cities 121.47 31.23 100 km   # 查询附近
GEORADIUSBYMEMBER cities "上海" 100 km # 以成员为中心查询
GEOHASH cities "上海"               # 获取 GeoHash 字符串
```

> 🎯 面试常问：GeoHash 的编码原理。回答要点：将经纬度交替二分编码，将二维空间降维到一维字符串，且字符串越长精度越高。

### 10. BitMap 底层实现和性能？
> BitMap 不是新类型，而是 String 类型的位操作扩展。

**底层**：基于 String 的位数组，最大长度为 2^32 位（512MB 内存）。

```bash
# BitMap 命令
SETBIT key offset 1          # 设置指定位为 1（offset 从 0 开始）
GETBIT key offset            # 获取指定位的值
BITCOUNT key [start end]     # 统计 1 的数量
BITOP AND dest key1 key2     # 位运算（AND/OR/XOR/NOT）
BITPOS key 1                 # 查找第一个 1 出现的位置
```

**性能**：每个 BitMap 操作的时间复杂度为 O(1)或 O(N/8)，N 为字节数。

**典型场景**：
- 用户签到：365 天只需要 46 字节
- 布隆过滤器：配合多个 hash 函数实现
- 在线状态：每个用户对应一个 bit
- 权限控制：每位代表一个权限

### 11. HyperLogLog 的实现原理？
> HyperLogLog 基于概率算法实现极低内存的基数统计。

**原理简析**：
- 使用 16384 个寄存器（bucket），每个寄存器 6 位
- 总内存：16384 * 6 / 8 = 12KB（固定！）
- 对输入元素计算 hash，根据 hash 值的"前导零"数量估计算数
- 标准误差：1.04 / sqrt(16384) ≈ 0.81%

```bash
# HyperLogLog 命令
PFADD uv:page1 user1 user2 user3    # 添加元素
PFCOUNT uv:page1                     # 估算基数（UV）
PFMERGE uv:total uv:page1 uv:page2   # 合并多个
```

> ⚠️ 误差是 HyperLogLog 的固有特性，0.81% 的标准误差意味着 100 万 UV 约误差 ±8100。如果要求精确计数，使用 Set 或 String INCR。

### 12. Stream 消费者组如何工作？
> Stream 的消费者组实现了消息的分组消费和 ACK 机制。

**消费者组模型**：
```text
Stream
  |
消费者组 group1
  ├── consumer1（cursor: 已消费到消息 N）
  ├── consumer2（cursor: 已消费到消息 N+2）
  └── consumer3（cursor: 已消费到消息 N+5）

每一条消息只被消费者组内的一个消费者处理
```

**消息状态流转**：
```
消息到达 -> Pending（待处理） -> XACK（已确认） -> 移除
                            -> 消费后未 ACK -> 仍在 Pending 列表
```

```bash
# 完整操作
XADD mystream * name "John"                # 生产消息
XGROUP CREATE mystream mygroup 0           # 创建消费者组
XREADGROUP GROUP mygroup consumer1 STREAMS mystream >  # 消费消息
XACK mystream mygroup 1700000000000-0      # ACK 确认
XPENDING mystream mygroup                  # 查看待处理消息
XCLAIM mystream mygroup consumer2 10000 1700000000000-0  # 转移消息
```

## 二、深度原理剖析

### 1. Redis 7.0 新特性有哪些？
> 了解 Redis 最新版本特性体现技术深度。

| 特性 | 说明 |
|------|------|
| **Listpack 替代 ZipList** | 从根本上解决连锁更新问题 |
| **共享缓冲区** | replica 和 master 共享 replication buffer，减少内存占用 |
| **AOF 多目录支持** | AOF 文件和数据文件可放在不同路径 |
| **函数（Function）** | 比 Lua 更强大的脚本功能，支持库管理 |
| **Sharded Pub/Sub** | 在集群模式下支持分片发布订阅 |
| **自动 failover 优化** | 改进了集群故障转移的稳定性 |
| **更好的内存管理** | 更精确的内存统计和碎片整理优化 |

### 2. Redis 的用户态和内核态空间理解？
> 理解操作系统层面的 IO 模型需要了解用户态和内核态。

**用户空间（User Space）vs 内核空间（Kernel Space）**：
```
用户空间：应用程序运行的地方，访问受限
内核空间：操作系统核心运行的地方，可访问硬件和所有内存

用户态 -> 内核态切换（系统调用）：
  应用程序 -> read(socket, buffer) -> 系统调用 -> 
  内核等待数据 -> 数据从内核拷贝到用户空间
```

**Redis 为什么在用户态操作数据？**
- Redis 本身就是应用程序，运行在用户态
- 内存分配（jemalloc）在用户态完成，不需要系统调用
- 唯一需要内核参与的是网络 IO（epoll_wait）和持久化（write fsync）

**零拷贝优化**：AOF rewrite 时，Redis 将父子进程通过共享内存传递数据，避免不必要的拷贝。

### 3. Redis 的 5 种 IO 模型详解（阻塞/非阻塞/多路复用/信号驱动/异步）
> 理解 IO 模型演进对深入理解 Redis 网络模型至关重要。

```text
1. 阻塞 IO（BIO）
   应用调用 recvfrom -> 内核等待数据 -> 数据从内核拷贝到用户空间
   -> 返回。整个过程阻塞，不能做其他事。

2. 非阻塞 IO（NIO）
   应用轮询调用 recvfrom -> 如果数据没准备好，立即返回 EWOULDBLOCK
   -> 应用可以做其他事 -> 过一会再轮询。轮询消耗 CPU。

3. IO 多路复用（Redis 使用）
   应用调用 select/poll/epoll -> 内核监控多个 fd -> 任一就绪即返回
   -> 应用遍历就绪 fd 处理。单线程处理多连接，无需轮询。

4. 信号驱动 IO（SIGIO）
   应用发起 SIGIO 信号处理 -> 内核数据就绪时发送信号
   -> 应用在信号处理函数中读取数据。

5. 异步 IO（AIO）
   应用调用 aio_read -> 立即返回 -> 内核完成数据读取后通知应用
   -> 应用直接使用数据。无需阻塞等待。
```

**Redis 的实际 IO 路径**：
```
客户端请求 -> epoll_wait（内核等待）-> 就绪通知 -> 读取数据 -> 命令执行 -> 写入响应
                      ^ IO 多路复用传输层            ^ 单线程命令执行
```

### 4. Redis 通信协议 RESP 详解
> RESP（Redis Serialization Protocol）是 Redis 客户端和服务器的通信协议。

**RESP 数据类型**：
```text
+OK\r\n                    # 简单字符串（Simple String）
-ERR message\r\n           # 错误（Error）
:1000\r\n                  # 整数（Integer）
$5\r\nhello\r\n            # 批量字符串（Bulk String，$长度\r\n数据\r\n）
$-1\r\n                    # 空值（Nil Bulk String）
*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n  # 数组（Array）
```

**SET keyvalue 命令的 RESP 编码**：
```
*3\r\n           # 数组长度 3
$3\r\nSET\r\n    # 第一个元素 "SET"
$3\r\nkey\r\n    # 第二个元素 "key"
$5\r\nvalue\r\n  # 第三个元素 "value"
```

> 💡 RESP 的优点是：简单、易解析、二进制安全（长度前缀决定数据，不受特殊字符影响）。

### 5. Redis 单线程架构的底层原因和性能极限
> 深入理解 Redis 单线程架构不是"做不了多线程"，而是"单线程已经足够"。

**为什么 Redis 设计为单线程？**
1. **性能瓶颈不在 CPU**：Redis 的瓶颈是内存和网络，单线程操作内存已达纳秒级
2. **避免多线程复杂性**：没有锁竞争、没有上下文切换、没有死锁
3. **原子性天然保证**：单线程执行命令天然就是原子的
4. **实现简单**：开发和维护成本低

**单线程的极限在哪里？**
- 纯 GET/SET 操作：10w+ QPS
- 复杂命令（ZRANGE 1000）：1w-3w QPS
- Pipeline 批处理：100w+ QPS
- 瓶颈场景：大 key 操作（100w+ 元素的集合）、长时间 Lua 脚本

**什么时候 Redis 多线程了？**
- 6.0：网络 I/O 多线程（读写 socket）
- 异步删除（UNLINK、FLUSHALL ASYNC）
- BGSAVE、AOF rewrite（子进程）
- 后台线程（close、lazy free）

> 🎯 面试题："Redis 单线程如何处理高并发？" 关键回答点：epoll 事件驱动 + 内存操作 + 非阻塞 IO + 快速命令。

### 6. WSL（Write System call Latency）对 Redis 性能的影响
> 理解 fsync 等系统调用对 Redis 性能的影响。

**Redis 的写文件路径**：
```text
Redis 内存操作 -> 写入 OS Page Cache -> fsync 刷新到磁盘
                  (用户态)        (系统调用，内核态)
```

**AOF 配置对性能的影响**：
| appendfsync | 安全级别 | 性能影响 | 崩溃丢失 |
|-------------|:-------:|:--------:|:--------:|
| always | 最高 | 最慢（每次写 fsync） | 0 数据 |
| everysec | 中 | 快（每秒 fsync） | 1 秒数据 |
| no | 最低 | 最快（OS 决定） | 不确定 |

- `appendfsync everysec` 是安全与性能的最佳平衡
- Redis 主线程不会直接执行 fsync，而是由后台线程每 1 秒执行一次
- 即使如此，如果磁盘 IO 负载过高（如大量写入），fsync 仍可能阻塞主线程

### 7. 写时复制（Copy-On-Write）原理及其对 Redis 的影响
> COW 是 BGSAVE 和 AOF rewrite 期间的关键机制。

**基本原理**：
```
fork 子进程时：
  - 父进程和子进程共享同一物理内存
  - 所有内存页标记为"只读"
  - 父进程修改某页时，触发缺页中断
  - 内核复制该页，父子进程各自持有独立副本
```

**对 Redis 的影响**：
1. **内存翻倍风险**：写操作多的场景下，COW 可能导致内存使用量翻倍（每次写都复制）
2. **延迟增加**：缺页中断处理需要时间，最坏情况下单个请求延迟可能从微妙级升到毫秒级
3. **fork 耗时**：实例越大 fork 越慢（页表复制），百 GB 级别可能 fork 耗时数秒

```bash
# 查看 COW 内存大小
INFO persistence
# fork_copy_process_size: 当前 COW 复制的内存大小
```

**优化措施**：
- 控制单实例内存大小（建议不超过 64GB）
- 避开高峰期执行 BGSAVE
- `lazyfree-lazy-eviction yes` 开启惰性释放

## 三、实战场景题

### 1. （阿里）Redis 的过期 key 淘汰与内存淘汰混用场景如何处理？
> 过期策略和淘汰策略是两套独立但相关的机制。

**场景分析**：
```
过期 key 清理（eviction）：针对设置了 TTL 且已过期的 key
内存淘汰（maxmemory-policy）：针对内存超限时选择哪些 key 删除
```

**典型问题**：当内存已满且大量 key 已过时，如果只依赖惰性删除，内存不会释放。需要触发淘汰来释放空间。

```bash
# 推荐的配置方案
maxmemory 8gb                # 最大内存
maxmemory-policy allkeys-lru # 淘汰策略
```

**不推荐的配置**：
```bash
maxmemory-policy noeviction  # 内存写满后所有写入都报错！
```

> 💡 正确做法：所有 key 设置合理 TTL 作为"主动管理"，淘汰策略作为"最后防线"。

### 3. （阿里）Redis 在主从全量同步时对性能的影响及优化
> 主从全量同步是 Redis 运维中最影响性能的事件之一。

**影响分析**：
1. **主库 BGSAVE**：fork 子进程，COW 可能导致内存翻倍和延迟抖动
2. **网络带宽打满**：RDB 文件传输占用大量带宽（尤其是大实例）
3. **从库加载 RDB**：加载期间从库不可服务
4. **缓冲溢出**：如果 RDB 生成和传输期间写命令积压超过 `client-output-buffer-limit`，同步失败

**优化策略**：
```bash
# 1. 控制单实例大小（不超过 32GB）
# 2. 使用磁盘复制替代网络复制
repl-diskless-sync no    # 默认：基于磁盘复制
# repl-diskless-sync yes # 基于网络复制（不落盘）

# 3. 调整客户端缓冲区限制
client-output-buffer-limit slave 256mb 64mb 60

# 4. 使用增量同步尽量代替全量同步
repl-backlog-size 512mb   # 增大 backlog，避免断连后触发全量
```

**最佳实践**：
- 避免在主库压力大时触发全量同步
- 从库尽量挂载到低峰期
- 监控同步状态，及时感知大延迟

### 7. Redis 与数据库的一致性哈希应用
> 一致性哈希解决分布式缓存系统的扩缩容问题。

**传统取模**的问题：
```text
3 节点：key -> hash(key) % 3 -> 节点 0/1/2
扩容到 4 节点后：key -> hash(key) % 4 -> 大部分 key 需要迁移
数据迁移量 ~75%！
```

**一致性哈希**：
```text
哈希环（0 ~ 2^32-1）：
  - 节点映射到环上
  - key 映射到环上，顺时针找最近的节点
  - 扩容时只影响相邻节点的部分数据

节点 A    节点 B
  |         |
  v         v
--o---------o---- 哈希环
    \       /
     \     /
      o---o
    节点 C  节点 D

扩缩容影响：只影响相邻节点的数据
```

**虚拟节点**：每个物理节点对应多个虚拟节点（如 150 个），解决数据分布不均的问题。

> 💡 Redis Cluster 没有使用一致性哈希，而是使用哈希槽（16384 个槽）。一致性哈希的好处是扩缩容迁移量更少，但哈希槽的实现更简单可靠。

```java
@Component
public class TokenBucketRateLimiter {
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    /**
     * 令牌桶限流
     * @param key       限流 key
     * @param rate      每秒速率（令牌数）
     * @param capacity  桶容量（最大积攒令牌数）
     * @param request   本次请求消耗的令牌数
     * @return 是否通过
     */
    public boolean tryAcquire(String key, int rate, int capacity, int request) {
        String luaScript = 
            "local key = KEYS[1] " +
            "local now = tonumber(ARGV[1]) " +
            "local rate = tonumber(ARGV[2]) " +
            "local capacity = tonumber(ARGV[3]) " +
            "local request = tonumber(ARGV[4]) " +
            "local lastRefillTime = tonumber(redis.call('hget', key, 'lastRefillTime') or '0') " +
            "local tokens = tonumber(redis.call('hget', key, 'tokens') or '0') " +
            "if lastRefillTime == 0 then " +
            "    tokens = capacity " +
            "    lastRefillTime = now " +
            "end " +
            "local elapsed = math.max(0, now - lastRefillTime) " +
            "local newTokens = math.min(capacity, tokens + elapsed * rate / 1000) " +
            "if newTokens >= request then " +
            "    redis.call('hset', key, 'tokens', newTokens - request) " +
            "    redis.call('hset', key, 'lastRefillTime', now) " +
            "    redis.call('expire', key, 10) " +
            "    return 1 " +
            "else " +
            "    return 0 " +
            "end";
        
        Long result = redisTemplate.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            Collections.singletonList("rate:token:" + key),
            String.valueOf(System.currentTimeMillis()),
            String.valueOf(rate),
            String.valueOf(capacity),
            String.valueOf(request)
        );
        return result == 1L;
    }
}
```

### 4. Redis 限流 + 缓存穿透防护代码
```java
@Component
public class CacheProtectionService {
    @Autowired
    private StringRedisTemplate redisTemplate;
    
    // 缓存穿透防护（布隆过滤器 + 空值缓存）
    public <T> T queryWithProtection(String key, Class<T> type, 
                                      Supplier<T> dbQuery, long ttlSeconds) {
        // 1. 查缓存
        String json = redisTemplate.opsForValue().get(key);
        if (json != null) {
            if ("NULL".equals(json)) {
                return null; // 空值缓存
            }
            return JSON.parseObject(json, type);
        }
        
        // 2. 查数据库
        T data = dbQuery.get();
        if (data == null) {
            // 3. 缓存空值（防穿透）
            redisTemplate.opsForValue().set(key, "NULL", 60, TimeUnit.SECONDS);
            return null;
        }
        
        // 4. 回填缓存
        redisTemplate.opsForValue().set(
            key, 
            JSON.toJSONString(data), 
            ttlSeconds + ThreadLocalRandom.current().nextLong(ttlSeconds / 5), 
            TimeUnit.SECONDS
        );
        return data;
    }
    
    // 缓存击穿防护（互斥锁）
    public <T> T queryWithMutex(String key, Class<T> type,
                                  Supplier<T> dbQuery, long ttlSeconds) {
        // 1. 查缓存
        String json = redisTemplate.opsForValue().get(key);
        if (json != null) {
            if ("NULL".equals(json)) return null;
            return JSON.parseObject(json, type);
        }
        
        // 2. 获取互斥锁
        String lockKey = "lock:" + key;
        Boolean locked = redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);
        
        if (Boolean.TRUE.equals(locked)) {
            try {
                // 双重检查（可能其他线程已经回填了）
                json = redisTemplate.opsForValue().get(key);
                if (json != null) {
                    if ("NULL".equals(json)) return null;
                    return JSON.parseObject(json, type);
                }
                // 查数据库
                T data = dbQuery.get();
                if (data == null) {
                    redisTemplate.opsForValue().set(key, "NULL", 60, TimeUnit.SECONDS);
                } else {
                    redisTemplate.opsForValue().set(key, JSON.toJSONString(data), ttlSeconds, TimeUnit.SECONDS);
                }
                return data;
            } finally {
                redisTemplate.delete(lockKey);
            }
        } else {
            // 3. 没有获取到锁，等待重试
            try {
                Thread.sleep(50);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            return queryWithMutex(key, type, dbQuery, ttlSeconds);
        }
    }
}
```

```java
                redisTemplate.opsForZSet().remove(TASK_KEY, task);
                break;

        }
```

```java
// 自定义 Redis 路由逻辑
public class RedisRouter {
    private static final int SLOT_COUNT = 16384;
    private final Map<Integer, RedisNode> slotMapping = new ConcurrentHashMap<>();
    
    public RedisNode route(String key) {
        // 处理 Hash Tag
        String hashKey = key;
        int tagStart = key.indexOf('{');
        if (tagStart >= 0) {
            int tagEnd = key.indexOf('}', tagStart);
            if (tagEnd > tagStart + 1) {
                hashKey = key.substring(tagStart + 1, tagEnd);
            }
        }
        // 计算哈希槽
        int slot = CRC16.crc16(hashKey.getBytes()) % SLOT_COUNT;
        return slotMapping.get(slot);
    }
}
```

### 5. 设计一个跨地域多活 Redis 架构
> 异地多活是大型互联网公司的核心基础设施。

**设计目标**：异地容灾，单数据中心故障时可快速切换。

**架构方案**：
```text
          [数据中心 A]                    [数据中心 B]
              |                               |
    主-从架构(主)                   主-从架构(备)
          |                               |
          +------- 数据同步(双向/单向) ------+
                    (通过中间件或自研工具)
```

**关键问题及解决方案**：
| 问题 | 说明 | 解决方案 |
|------|------|---------|
| 数据冲突 | 两地同时修改同一 key | 按数据中心优先级，或最后写入获胜（LWW） |
| 网络延迟 | 跨地域网络延迟高 | 异步复制，不阻塞写入 |
| 时钟不同步 | key 过期时间不一致 | NTP 时钟同步 |
| 故障切换 | 主中心断电 | DNS 切换、Redis 哨兵或全局负载均衡 |

**Google 的原则**：跨地域复制应使用最终一致性模型，只有在单个地域内才能保证强一致。

## 六、常见坑点与最佳实践

### 常见坑点

| 坑点 | 原因 | 解决方案 |
|------|------|---------|
| Hash Tag 使用不当导致数据倾斜 | 大量 key 使用相同 hash tag | 合理设计 hash tag 粒度 |
| 客户端连接池泄漏 | 用完连接未归还 | try-with-resources 或 finally 释放 |
| SORT 命令阻塞 | 对大型集合排序 | 在应用层排序 |
| Redis Cluster 不支持跨槽事务 | 集群模式下 MULTI 命令受限 | 使用 Hash Tag 或 LUA |
| AOF 重写 CPU 飙升 | AOF rewrite 在子进程执行 | 调整 auto-aof-rewrite-percentage |
| Sentinel 脑裂 | 网络分区 + 配置不当 | min-slaves-to-write + min-slaves-max-lag |
| Cluster 集群间网络抖动 | 集群节点频繁 Ping Pong | cluster-node-timeout 合理设置 |
| 序列化后 key 不可读 | 使用 JDK 序列化 | 改用 JSON/Protobuf |
| EXPIR 命令对集合类型只作用于 key 本身 | 集合内的元素不会过期 | 使用 ZSet 按 score 做过期清理 |
| BGSAVE 期间写入性能下降 | COW 导致内存复制 | 控制单实例大小，低峰期执行 |

### 最佳实践

| 实践 | 说明 |
|------|------|
| 控制单实例内存 | 建议不超过 32GB，减少 fork 耗时和 BGSAVE 影响 |
| 使用 SCAN 替代 KEYS | KEYS * 会阻塞 Redis，SCAN 分批返回不阻塞 |
| 连接池配置 | maxTotal 按业务 QPS 计算，建议 8-32，预留 30% 余量 |
| 批量操作用 Pipeline | 减少 RTT，建议 500 条一批 |
| 监控命中率 | 缓存命中率 < 85% 需要排查原因 |
| 设置合理 maxmemory | 预留 20%-30% 内存给 COW 和碎片 |
| 开启 lazyfree | lazyfree-lazy-eviction yes，UNLINK 替代 DEL |
| 读写分离注意一致性问题 | 写后立即读的场景强制读主库 |
| 合理使用 TTL | 所有缓存设置过期时间，避免死数据 |
| 使用连接池而不是直连 | 减少连接创建销毁开销 |

## 七、面试回答模板

### 模板1：谈谈你对 Redis 集群的理解
> 面试官期望：哈希槽 + 节点通信 + 故障转移

**回答结构**：
1. **数据分片**：16384 个哈希槽，CRC16(key) % 16384 决定 key 所在槽
2. **节点通信**：Gossip 协议（PING/PONG/PONG），节点间相互交换状态
3. **请求路由**：MOVED 重定向（客户端缓存槽位映射）和 ASK 重定向（迁移中）
4. **高可用**：主从复制 + 哨兵 + 自动故障转移
5. **劣势**：不支持跨节点事务、批量操作需 Hash Tag
6. **适用场景**：数据量超过单机内存，需要水平扩展

### 模板2：Redis 分布式锁的完整实现过程
> 面试官期望：SET NX EX -> Lua 释放 -> Redisson WatchDog

**回答结构**：
1. **加锁**：`SET key value NX EX 30`，保证原子性，value 要唯一标识持有者
2. **解锁**：Lua 脚本 GET + DEL 保证原子性
3. **可重入**：使用 Hash + 计数器，同一个线程可重入加锁
4. **自动续期**：WatchDog 机制，每 10 秒检查并续期
5. **多节点场景**：RedLock 算法，需要在多个独立节点获取锁
6. **常见问题**：锁过期业务未完成、误删其他线程的锁、死锁

### 模板3：Redis 如何实现高可用？
> 面试官期望：主从 -> 哨兵 -> 集群的完整演进

**回答结构**：
1. **主从复制**：一主多从，异步复制，主库写从库读。解决读瓶颈，但无法自动故障转移
2. **哨兵模式**：在主从上加了监控和故障转移。解决高可用，但单节点存储有上限
3. **Redis Cluster**：去中心化，分片 + 复制。解决海量数据 + 高可用
4. **最佳实践**：数据量小时用主从+哨兵，数据量大时用集群
5. **注意事项**：主从延迟监控、集群节点数量规划（建议奇数个 master）

### 模板4：Redis 大 key 和热 key 的发现与解决方案
> 面试官期望：能讲清楚识别方法和治理手段

**回答结构**：
1. **大 key 发现**：`redis-cli --bigkeys`、`MEMORY USAGE key`、`DEBUG OBJECT key`
2. **大 key 处理**：拆分（Hash 分桶）、压缩、选择合适数据类型
3. **热 key 发现**：`redis-cli --hotkeys`、monitor 命令分析、代理层统计
4. **热 key 处理**：本地缓存、读写分离、散列（key 加随机后缀）
5. **监控**：实时告警，热 key 自动降级

### 模板5：深度分析 Redis 持久化策略的选择
> 面试官期望：RDB + AOF + 混合持久化的全方案对比

**回答结构**：
1. **RDB 二进制快照**：适合备份、快速恢复；可能丢失较多数据
2. **AOF 命令追加**：数据安全（everysec 丢失 1s 数据）；文件大、恢复慢
3. **混合持久化（4.0+）**：rewrite 时先生成 RDB 快照，再追加增量 AOF；兼顾速度和安全
4. **配置建议**：默认两者都开启；AOF 使用 everysec
5. **生产关注点**：避免高峰期 BGSAVE、控制 AOF 文件大小、监控 fork 耗时
6. **场景选择**：数据可丢失（日志、缓存）-> RDB 即可；数据重要（订单、用户）-> 混合持久化
