# 技术深挖：缓存与一致性
> 缓存是项目深挖的第一高频战场：面试官沿着"原理 → 边界 → 线上问题 → 取舍落地"递进追问——删缓存还是更新缓存、先删还是先写、穿透击穿雪崩怎么防、多级缓存怎么保持一致——每一问都要求"场景推演"而非"背答案"。

## 1. 核心一问：为什么写路径是"更新 DB + 删缓存"

缓存一致性最经典的一问，也是分水岭——**标准答案是"更新数据库后删除缓存"，而不是更新缓存**。要把"为什么"讲到面试官满意，需要三层：

**第一层（为什么删而不是更新）**：双写模式（更新 DB + 更新缓存）有覆盖写风险——两个并发写请求分别写不同值，DB 最终是新值，但缓存可能被旧值覆盖（后写缓存的请求先到），产生持久脏数据；**删除是幂等操作**——下一次读自动触发"读 DB + 回写缓存"，且懒加载省资源。

**第二层（为什么先 DB 后缓存）**：反序（先删缓存再更新 DB）的竞态——写请求删缓存后，并发读请求读到 DB 旧值并回写缓存，导致缓存永久驻留脏数据（等缓存过期才能自愈）；先更新 DB 再删缓存，即使读请求在删除前读到旧值，删除后也会强制回源——**脏数据窗口从"永久"缩小到"毫秒级"**。

**第三层（代价与兜底）**：先 DB 后删缓存仍有极端竞态（读请求在 DB 更新后、缓存删除前读到旧值并回写——需要"延迟双删"或"版本号"）；工程兜底是**对账任务**（定时扫描 Redis 与 MySQL 差异，发现不一致触发告警修复，以 MySQL 为准）——**主动讲出"方案引入的新问题 + 兜底方案"，是工程成熟度的直接体现**（06 篇取舍讲法）。

## 2. 缓存三兄弟：穿透、击穿、雪崩

三个高频场景的追问与标准应答（每个都要能讲"定义 + 危害 + 方案 + 方案的代价"）：

**穿透**（查询不存在的数据）：每次查询都直达 DB——**方案**：布隆过滤器拦截非法 key 或缓存空值（短过期）。**追问点**：布隆过滤器有误判率怎么处理？（缓存空值兜底）；缓存空值会占内存怎么办？（短 TTL + 只对热点非法 key）。

**击穿**（热点 key 过期瞬间高并发直达 DB）：**方案**：互斥锁重建（请求中只有一人查 DB 回写，其余等待）或逻辑过期（key 永不过期，后台异步重建）。**追问点**：互斥锁用本地锁还是分布式锁？（单机本地锁，集群分布式锁——要能讲清选择依据）；锁超时怎么办？（Redisson 看门狗续期 + 业务状态二次校验）。

**雪崩**（大量 key 同时过期，或 Redis 宕机）：**方案**：过期时间加随机抖动 + 多级缓存（本地缓存先挡）+ 熔断降级。**追问点**：Redis 宕机怎么办？（多级缓存 + 限流保护 DB，DB 扛不住就降级返回旧数据/静态化）。

**记忆口诀**：穿透是"查不存在的"，击穿是"一个热点挂了"，雪崩是"一片全挂了"——**先把三个场景分清，再讲方案**（很多候选人三兄弟讲混，是深挖里最尴尬的翻车点）。

## 3. 多级缓存与一致性：本地缓存 + Redis + DB

"本地缓存（Caffeine）+ Redis + DB"三级缓存是 2026 年项目里的标配方案，追问集中在两级之间的一致性：

- **本地缓存与 Redis 不一致**（本地缓存命中旧值）：**方案**——基于版本号的更新策略：Redis 里存版本号，本地缓存带版本，请求时先比版本、落后则从 Redis 拉取；或"本地缓存只放高频只读数据，写路径全走 Redis"（数据分类规避）。**要点**：承认"一致性有窗口"并讲窗口大小与兜底（版本号方案窗口为 0）
- **本地缓存更新方式**：用 Redis 的订阅发布（Pub/Sub）或消息通知各节点失效本地缓存——**要能讲清"为什么用 Pub/Sub 而不是轮询"**（实时性 vs 复杂度，小集群 Pub/Sub 够用，大规模可用 RocketMQ 广播）
- **多级缓存的"级"怎么定**：命中率最高的数据（热点商品、配置）放本地，次热点放 Redis，冷数据直查 DB——**"数据分级"是架构判断力的问题，值得准备一个具体的分级例子**

## 4. 缓存深挖的追问全景与答题纪律

把缓存相关追问串成全景（2026 年面试官亲述的递进逻辑）：**用法**（你项目里缓存怎么用的）→ **原理**（为什么删缓存不更新缓存）→ **边界**（缓存三兄弟各是什么场景）→ **线上问题**（遇到过缓存导致的线上故障吗、怎么排查的）→ **取舍落地**（缓存一致性窗口怎么接受、对账怎么做的、如果重做改哪里）。

三条答题纪律：**第一，不要一上来就"加缓存"**——先确认场景与指标（QPS 多少、读多写少吗、一致性要求），"只说方案不说场景"是 2026 年面试官最烦的模板化回答；**第二，主动讲代价**——每个方案主动带出"它引入的新问题"（一致性窗口、内存成本、运维复杂度），讲代价的候选人才算真做过；**第三，用场景推演代替背结论**——"先删缓存再更新 DB 会怎样"要能现场推演出"读请求回写旧值"的竞态链条，推演能力是"背答案"与"真理解"的分水岭。

## 5. 缓存深挖的准备实操：从项目到弹药

把缓存理论变成"你的弹药"需要四步实操：**第一步，盘点项目里的缓存点**——你的项目里哪里用了缓存（商品详情、登录态、配置、验证码……），每个点回答"为什么这里适合缓存"（读多写少？数据时效要求？）——**每个缓存点都是一道"为什么"题**；**第二步，为每个缓存点配齐三件套**：实现细节（数据结构、过期策略、序列化方式）、踩坑记录（有没有遇到过穿透/击穿/雪崩、怎么处理的）、指标数据（命中率、RT 对比）——三件套即 DETAIL 五细节的缓存版；**第三步，写一份"缓存方案说明书"**：一页纸讲清你的缓存架构（几级、每级放什么、一致性怎么保证、失败了怎么办）——这是"为什么这么设计"的完整答案（06 篇 ADR 的缓存版）；**第四步，预演追问链**：用第 4 节的追问全景（用法→原理→边界→线上→取舍）自问自答，卡壳处补课（知识库 `Redis` 体系是补课资源）。

**准备到位后的表现**：被问到缓存时，你的回答自动带出"场景 → 方案 → 代价 → 兜底"完整链（"商品详情读多写少所以加了 Redis 多级缓存，一致性靠版本号，代价是内存成本，兜底是对账任务"）——**面试官听到这种"完整链"回答时的判断是"这人真做过"**，而不是"这人背过缓存八股"——这就是技术深挖准备的最终验收标准。

> 🎯 **核心要点**：缓存深挖的主线是"原理→边界→线上→取舍"四层递进——写路径"更新 DB + 删缓存"要能讲三层（删优于更新的幂等性、先 DB 后缓存把脏窗口从永久缩到毫秒、对账兜底）；三兄弟要分清场景再讲方案（穿透查不存在、击穿热点挂了、雪崩一片全挂）；多级缓存一致性用版本号与数据分级应对；三条纪律——先讲场景再谈方案、主动讲代价、用场景推演代替背结论——"能现场推演出竞态链条"是缓存深挖的高分标志。
