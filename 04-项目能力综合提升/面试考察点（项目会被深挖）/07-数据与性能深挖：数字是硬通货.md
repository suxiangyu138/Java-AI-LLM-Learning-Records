# 数据与性能深挖：数字是硬通货
> 深挖回答里最有说服力的是数字——QPS、RT、P99、命中率、优化前后对比；2026 年面试官亲述："每个形容词后面必须跟具体数字"，而数字的可靠性来自压测方法论——没有压测记录支撑的"性能提升"，在追问下是最大的破绽。

## 1. 数字清单：每个项目必备的七个指标

给每个核心项目准备一张"数字卡片"，七个指标为底：**QPS**（线上峰值与压测值）、**RT/P99**（优化前与优化后）、**缓存命中率**（98% 这类数字要有监控来源）、**数据规模**（表行数、单表大小）、**并发量**（线程池大小、连接数）、**资源占用**（CPU、内存、GC 频率）、**可用性**（故障次数、恢复时间）。每个数字要能回答三个追问：**怎么测的**（压测工具、场景、时长）、**什么时候的数据**（上线前还是上线后、哪次压测）、**来源在哪**（压测报告、监控截图、日志统计）。

**数字的语法**：面试回答里"P99 从 800ms 降到 120ms"与"性能大幅提升"的区别，就是"通过"与"不通过"的区别——**数字让抽象变成可验证的事实**，而"可验证"正是 2026 年深挖的核心理念（01 篇验证真实性）。

## 2. 压测方法论：数字背后的可靠性

面试官对数字的第二问一定是"怎么测的"——**数字的可靠性 = 压测方法的可靠性**，标准的方法论四要素：

**工具与场景**：JMeter/Gatling/自研压测脚本，场景要覆盖业务真实比例（读多写少按 9:1 混合，不是全读）；**指标口径**：RT 要分平均与分位（P50/P95/P99——只说平均会被追问"长尾呢"）；**施压方式**：逐步加压（从 100 并发逐步加到 5000）观察拐点——"拐点在哪"的回答展示了"找到瓶颈"的过程；**资源观测**：压测时同步看 CPU/内存/GC/连接池——"CPU 先到 90% 还是 DB 连接池先满"决定了瓶颈在哪一层。

**压测的经典追问**：压测环境与线上差异怎么处理？（压测机配置、数据量、网络——承认差异并说明"压测值是下限参考"）；压测会不会影响线上？（压测环境隔离或低峰期压测——"生产压测"的灰度做法）；QPS 数据会不会虚高？（请求都走缓存 vs 真实读写比——**口径一致性**是防"数字造假"追问的关键）。

## 3. 优化叙事：前后对比 + 根因链

性能优化的深挖回答，标准结构是"问题 → 定位 → 优化 → 验证"四段（02 篇故事四节点的性能版）：

**问题**：具体到指标与时间——"商品详情接口高峰期 P99 800ms"。**定位**（最有信息量的部分）：用工具层层缩小——监控发现 DB 慢查询 → Explain 发现索引未命中（隐式类型转换/函数操作/不满足最左前缀）→ 修复索引后仍未解决 → Arthas 追踪到热点方法在序列化 → 引入缓存。**优化**：每个手段配"为什么选它"（缓存选 Redis 因为……）；**验证**：压测复测 P99 到 120ms + 上线后监控确认（**上线后监控数据是"优化真实有效"的最终证据**）。

**根因链的价值**：面试官最想看的不是"你加了缓存"，而是"你**怎么找到**要加缓存"——定位过程（用哪些工具、每步排除了什么）展示排查方法论；只讲"我加了缓存所以快了"的回答，在"怎么定位到缓存的"追问下必然卡壳。

## 4. 线上排查框架：由表及里四层

"线上出过什么问题？怎么排查的？"是深挖的必考题，标准框架是**由表及里四层**（2026 年面试官认可的口径）：

**第一层，指标监控**：CPU、内存、磁盘 IO、网络流量——先判断"全局还是局部"（所有接口都慢 vs 单个接口慢，决定查基础设施还是查应用）；**第二层，链路追踪**：微服务用 APM（SkyWalking 等）定位"哪个服务、哪个接口、哪段调用耗时异常"——链路追踪把问题从"现象"缩小到"环节"；**第三层，深入分析**：DB 慢（慢查询日志 + Explain）、外部 API 慢（调用超时）、GC 问题（GC 日志 + jstack 看线程堆栈——死锁/阻塞）、内存问题（jmap 堆转储分析）；**第四层，数据层**：索引失效场景、缓存穿透导致请求直达 DB、连接池耗尽。

**排查叙事的要点**：每层都要有"**排除法**"的痕迹——"先看了监控发现是单接口问题，排除了基础设施；再看链路发现耗时在 DB，排除了应用代码；Explain 发现索引没走，定位到隐式类型转换"——**"我排除了 X，所以查 Y"的句式，是排查方法论的最好证明**（08 篇故障叙事的同款结构）。

## 5. 数字纪律：一致性、诚实性与口径

数字相关的三条纪律（深挖翻车重灾区）：**第一，口径一致**——简历、一面、二面的数字必须完全一致（"命中率 98%"不能变成"95%"），多轮面试前过一遍"项目事实表"（10 篇）；**第二，诚实标注来源**——"这个数字是压测的，线上还没到过这个量级"比"线上就是这个量级"更可信——**主动标注"压测 vs 线上"的口径差异，反而增加可信度**（编造者不会主动暴露差异）；**第三，数字的边界**——没有压测过就说"没压过，预估是……"——**2026 年面试官对"诚实 + 推理"的评价高于"硬编数字"**，编数字被识破的代价是整个项目可信度崩塌（03 篇一致性防线）。

## 6. 数据准备的具体方法：从项目里"挖"数字

数字不是靠记，而是靠"挖"——三步把项目里的数据资产盘点出来：**第一步，翻记录**——压测报告（没有就现在补跑一次）、监控截图（Grafana 面板）、慢查询日志、GC 日志、线上告警记录——**"挖数据"本身就在补项目的真实性证据**（01 篇验证目的：有记录的数字才经得起追问）；**第二步，补测量**——项目里"感觉很快"的地方补一次测量（"详情接口感觉挺快"→ 压测或日志统计出 P99）——**每个"感觉"补成数字，简历上的形容词就全部落地**（03 篇布防）；**第三步，建事实表**——把全部数字整理成一张"项目事实表"（指标 / 数值 / 来源 / 时间），面试前夜过一遍——**事实表同时服务三个场景**：简历一致性（03 篇）、多轮面试一致（10 篇）、被追问"怎么测的"时的来源引证（第 2 节）。

**挖数字的常见误区**：只挖"好看的数字"（命中率 99%）不挖"不好看的"（压测 5000 QPS 时 CPU 飙到 90% 的瓶颈点）——**"瓶颈数字"恰恰是深挖最有价值的弹药**（"我压测发现 CPU 先到瓶颈，定位到是序列化开销，换了 Protobuf"——瓶颈数字是四节点故事（02 篇）的天然素材）；诚实呈现"不好看"的数字，比包装"好看"的数字可信得多（第 5 节纪律三）。

> 🎯 **核心要点**：数字是深挖回答的硬通货——每个项目准备七指标数字卡（QPS/RT/命中率/规模/并发/资源/可用性），每个数字能回答"怎么测的、什么时候、来源在哪"三连问；数字可靠性靠压测方法论（工具、口径、逐步加压、资源观测）；优化叙事按"问题→定位→优化→验证"四段，定位过程（排除法）比优化手段更值钱；线上排查按"指标→链路→深入→数据"四层递进；三条数字纪律——口径一致、诚实标注压测与线上的差异、没有数据就说"没压过"——诚实加推理，永远胜过硬编的数字。
