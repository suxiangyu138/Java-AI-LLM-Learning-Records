# 技术深挖：事务、并发与消息
> 缓存之外的第二大深挖战场：事务（@Transactional 的边界、分布式事务）、并发（防重、分布式锁、扣库存）、消息队列（为什么用 MQ、不丢、幂等、顺序）——每个话题都有一组"连环拷问"，准备的标准是"能扛住五层追问"。

## 1. 事务深挖：@Transactional 的边界与分布式事务

**第一问：@Transactional 只管理数据库事务**——Redis 操作、远程调用、MQ 发送都不在事务范围内：先写 MySQL 成功、写 Redis 失败，数据就不一致——**标准应对**：讲清"事务的边界是 DB"，配套重试与补偿（写 Redis 失败则重试或标记待补偿）。

**第二问：同类内调用事务方法会失效**（Spring AOP 代理问题）——方法内部 this 调用不走代理。**标准应对**：注入自身代理或拆出独立 Bean——这个细节是"真写过事务"与"看过教程"的分水岭。

**第三问：分布式事务怎么保证一致性**——2026 年标准答案是"**最终一致性**"，三条路线：**事务型消息**（RocketMQ 半事务消息：发送半消息 → 执行本地事务 → commit/rollback，MQ 回查兜底）；**本地消息表**（本地事务写业务表 + 消息表，异步投递）；**补偿机制**（重试、告警、人工介入）。**加分表达**：主动承认"极致性能下牺牲强一致性"并给出补救（对账 + 补偿），并说清"什么场景必须强一致（资金）什么场景可以最终一致（积分）"——**"场景化的一致性分级"是成熟工程师的签名**。

## 2. 并发深挖：防重、分布式锁与扣库存

**防重（幂等）三重防线**：本地缓存（快速拦截）→ Redis 分布式锁（跨节点互斥）→ **数据库唯一索引（最终屏障）**——三层的每层都有追问：唯一索引冲突怎么处理？（捕获 DuplicateKeyException 返回"已处理"）；Redis 锁和唯一索引谁更可靠？（唯一索引是权威，Redis 锁是性能优化）。

**分布式锁超时问题（经典连环拷问）**：锁超时释放但业务没执行完 → 另一个线程进入 → 重复处理。**标准应对三层**：合理设置锁超时（评估业务最大耗时）；Redisson 看门狗自动续期（锁过期自动延长）；**业务状态二次校验**（进入临界区后先查 DB 是否已处理——"锁只是入口闸门，DB 状态才是真相"）。**追问延伸**：Redisson 看门狗的原理（后台定时续期线程）、锁的公平性、主从切换时锁丢失（RedLock 的争议——讲出争议本身就是加分）。

**扣库存的两种方案**：**同步**——Redis 预扣（Lua 脚本保证原子性）+ DB 事务内更新，并发受限于 DB；**异步**——Redis 预扣 + MQ 下单 + 消费者落库（秒杀标准方案，06 篇展开）。**追问点**：Lua 脚本为什么原子？（Redis 单线程执行脚本）；Redis 预扣了但 MQ 消费失败怎么办？（对账 + 定时回补库存）；库存扣多了/少了怎么发现？（每日对账脚本）。

## 3. 消息队列四问：为什么、不丢、幂等、顺序

**第一问：为什么用 MQ 而不用线程池**——MQ 提供**持久化、重试、削峰**能力，高峰流量有缓冲；线程池无法保证消息不丢（进程挂了全没）。**加分表达**：MQ 的核心价值不只是"解耦"，而是削峰、缓冲、异步、下游故障隔离四件套——"解耦"是入门答案，四件套是进阶答案。

**第二问：消息怎么不丢**——三段：生产者（acks=all，写入所有副本）；Broker（min.insync.replicas=2）；消费者（**手动提交 offset，处理完再提交**）。**追问点**：手动提交的坑（处理完没提交 → 重复消费——引出幂等）；"不丢"和"不重复"是矛盾的怎么取舍（至少一次 vs 至多一次，Kafka 默认至少一次 + 幂等兜底）。

**第三问：消息怎么不重复（幂等）**——**每条消息带唯一业务 ID（或业务唯一键），消费前先查 DB 是否已处理**——唯一键进 MySQL（联合唯一索引是最终屏障，与防重三重防线同构）。**追问点**：唯一键怎么设计（user_id + action + timestamp 或全局 ID）；查了再插有竞态怎么办（靠唯一索引兜底，不用锁）。

**第四问：消息顺序性怎么保证**——Kafka 按分区保序：**同一业务 key（如 user_id）进同一分区 + 单消费者线程消费**。**追问点**：扩容后顺序还成立吗？（按 key 分区策略不变则成立——分区数变了 key 的映射会变，要讲清"扩容要保序需固定分区数或重算 key"）；消费者挂了重启后顺序呢？（从上次提交的 offset 续消费）。

## 4. 事务并发消息的追问全景与准备纪律

三个话题的追问全景（递进逻辑与缓存一致）：**用法**（项目里怎么用的）→ **原理**（为什么这么设计）→ **边界**（不满足什么条件会失效）→ **线上问题**（遇到过什么故障）→ **取舍落地**（代价与替代方案）。

准备纪律四条：**第一，每个技术点准备"一个项目实例 + 一个故障故事"**——"遇到过缓存击穿"比"我了解缓存击穿"高一个量级（08 篇）；**第二，连环拷问要能现场推演**——"先删缓存会怎样""锁超时了会怎样""消费失败会怎样"，推演链条是"真做过"的证据；**第三，主动讲方案的代价**——分布式事务的最终一致性窗口、MQ 的重复消费、锁的运维复杂度——"承认代价 + 给出兜底"是工程成熟度的签名（06 篇）；**第四，诚实边界**——没做过的场景直说"我的项目里没遇到，但我的理解是……"，2026 年面试官对"诚实 + 推理"的评价远高于"硬编一个故事"（10 篇避坑）。

## 5. 事务并发消息的准备实操：三类弹药库

三大话题的准备各建一个"弹药库"，每个话题至少五条弹药：**事务弹药库**——项目里哪些操作需要事务（下单、扣库存、发奖）、@Transactional 失效踩过坑吗、分布式事务遇到过吗（没有就准备"如果遇到我会……"的推理答案）、对账脚本写过吗、最终一致性怎么向业务解释；**并发弹药库**——项目里并发最高的是什么操作（QPS 多少）、防重做过吗（唯一索引？分布式锁？）、锁超时想过吗、压测时并发表现如何、并发 bug 排查过吗（怎么定位的）；**消息弹药库**——为什么引入 MQ（什么场景）、消息丢失/重复/乱序分别遇到过吗、消费失败怎么处理（重试策略）、消息堆积怎么办、为什么不直接用 HTTP 调用。

**弹药库的用法**：每个话题挑"最有故事性的一条"做四节点主故事（08 篇难点选择），其余做备选弹药；**面试回答的自动装配**：被问到"你项目里事务怎么用的"时，用主故事开场（场景+问题+方案+数据），追问时按弹药库逐层递进——**"主故事 + 弹药库"的结构让回答既完整又可扩展**，不会出现"问一个答一个、答完就没了"的被动局面。**补课路径**：弹药库里的空白点按知识库 `MySQL/Redis/消息队列` 体系补原理，但**原理补课之后必须回填进项目语境**（"这个知识点我的项目里能对应哪个场景"）——背下来的原理是八股，回填过的原理才是深挖弹药。

> 🎯 **核心要点**：事务/并发/消息三大深挖战场各有标准答案链——事务（@Transactional 只管 DB、同类调用失效、分布式事务最终一致性 + 事务消息 + 场景化分级）；并发（防重三重防线、锁超时三层应对、Lua 原子扣库存）；MQ 四问（为什么用（四件套）、不丢（三段 acks）、幂等（唯一键 + 唯一索引）、顺序（按 key 分区））；总纪律——每个点配一个项目实例加一个故障故事、能现场推演竞态、主动讲代价、诚实边界；"能扛住五层追问"就是全部准备目标。
