## 1. 三项目一句话定位

面试开场 3 分钟内，你需要在面试官脑中建立三个清晰的「项目标签」。每个项目的定位必须能在 10 秒内讲清楚：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Flavor Dash（单体美食）          SuGuangMall（微服务电商）        LingShu（医疗AI） │
│  ┌─────────────────────┐  ┌──────────────────────────┐  ┌──────────────────────┐ │
│  │ 技术验证型项目        │  │ 架构打磨型项目            │  │ 垂直深耕型项目        │ │
│  │ 验证 AI+后端融合     │  │ 大厂微服务全面实践        │  │ AI 工程化深度探索     │ │
│  │ Spring Boot 单体     │  │ Spring Cloud Alibaba     │  │ 14步RAG 管线         │ │
│  └─────────────────────┘  └──────────────────────────┘  └──────────────────────┘ │
└──────────────────────────────────────────────────────────────────────────┘
```

### 1.1 Flavor Dash —— 技术验证型

> **一句话定位**：基于 Spring Boot 单体架构 + AI Agent 框架的智能外卖平台，通过 LLM Client Factory（工厂+策略模式）统一管理 DeepSeek/通义千问等多模型接入，Agent 框架 Think→Act→Observe 驱动智能客服 Function Calling，日均处理 5000 单，是 AI+后端融合的技术验证项目。

**补充标签**：单体架构演示 / LLM 多模型网关 / Agent 框架实战 / 容错设计

**技术关键词**：LLM Client Factory、Agent (T→A→O)、Function Calling、Resilience4j 熔断（滑动窗口 COUNT_BASED 10次→失败率>50%→OPEN 60s）、Redis 缓存、RAG 基础管线（DocumentSplitter 语义分段 + overlap 10-15%）

### 1.2 SuGuangMall —— 架构打磨型

> **一句话定位**：基于 Spring Cloud Alibaba 的 12 微服务 + 7 AI 服务电商平台，实现 QPS 2000+ 零超卖秒杀系统、Multi-Agent 购物管家（6 专业 Agent + AgentRouter 意图路由）、Redis Lua 原子扣库存、Seata AT 分布式事务、ShardingSphere 16 分表，是面向大厂高并发场景的微服务全栈实践。

**补充标签**：微服务全家桶 / 高并发硬核场景 / 分布式事务实战 / Multi-Agent 协作

**技术关键词**：Spring Cloud Alibaba、Nacos、Sentinel、Seata AT、ShardingSphere（user_id 分 16 表）、Redis Lua 原子库存、RabbitMQ 死信延迟 15min 关单、Caffeine+Redis 多级缓存、CLIP 以图搜图 512 维（Milvus IVF_FLAT+PQ）、JWT+RBAC 双 token（access 30min + refresh 7d）、Prometheus+Grafana

### 1.3 LingShu/灵枢 —— 垂直深耕型

> **一句话定位**：基于 14 步 RAG 管线 + 全链路安全护栏的医学 AI 知识问答系统，BM25+向量混合检索+RRF k=60 实现 85-88% 召回率，四级异常分类体系（L1-L4）保障医疗场景可靠性，Ollama 本地部署 qwen2:1.5b/llama3.2:3b 双模型（8GB 内存），Docker Compose 9 服务编排，是 AI 工程化的深度探索。

**补充标签**：RAG 全链路实战 / 医疗安全合规 / 本地模型部署 / 混合检索调优

**技术关键词**：14 步 RAG 管线、安全护栏（输入 3 级检测 + 输出 6 条危险模式）、PHI 脱敏（姓名/电话/身份证掩码）、四级异常分类（L1 参数校验→L2 业务异常→L3 第三方失败→L4 未知异常）、Ollama 本地部署、BM25+向量混合检索+RRF k=60、BGE Embedding + Milvus、Docker Compose 9 服务编排、Python 爬虫医学百科

### 3.2 阶段一：Flavor Dash —— 单体基础 + AI 初探

| 层面 | 技术栈 | 掌握程度 | 为下一阶段埋下的伏笔 |
|:----:|:------:|:--------:|:------------------:|
| Web 框架 | Spring Boot、MyBatis-Plus、Spring MVC | 熟练掌握 | 发现单体架构扩展性瓶颈 |
| 数据层 | MySQL、Redis、RabbitMQ | 熟练掌握 | 需要分库分表 + 多级缓存 |
| AI 集成 | LLM Client Factory、Agent T→A→O、Function Calling | 核心亮点 | 外部 API 延迟不稳定，需要本地化 |
| 容错 | Resilience4j（COUNT_BASED 10次→50%→60s） | 理解原理 | 需要更完善的流控（Sentinel） |
| 部署 | JAR 包单机部署 | 基础 | 需要容器化编排 |

**学到什么**：
- 单体架构的优缺点（开发快 > 但扩展性差，团队协作冲突）
- AI 集成的基本模式（工厂模式统一管理多模型，策略模式支持热切换）
- Agent 框架的设计（Think→Act→Observe 循环，步数控制 + 重复检测）
- 服务容错机制（Resilience4j 三态：CLOSED→OPEN→HALF_OPEN）

**瓶颈发现**：业务扩展困难 → 功能耦合严重 → 需要微服务

### 3.3 阶段二：SuGuangMall —— 微服务全家桶 + 高并发

| 层面 | 技术栈 | 掌握程度 | 为下一阶段埋下的伏笔 |
|:----:|:------:|:--------:|:------------------:|
| 微服务 | Spring Cloud Alibaba、Nacos、Gateway、Feign | 熟练掌握 | 服务多了，运维复杂 |
| 高并发 | Redis Lua、Sentinel、Caffeine+Redis 多级缓存 | 核心亮点 | 需要更好的限流策略 |
| 数据 | ShardingSphere（16 分表）、Seata AT、ES | 理解原理 | 一致性 vs 性能的权衡 |
| AI | Multi-Agent × 6、AgentRouter、CLIP 以图搜图 | 核心亮点 | 依赖外部 API 延时不稳定 |
| 安全 | JWT+RBAC 双 token、Sentinel 流控 | 熟练掌握 | 需要更细粒度的安全控制 |
| 监控 | Prometheus + Grafana | 理解原理 | 需要异常分类体系 |

**学到什么**：
- 微服务拆分方法论（DDD 限界上下文）
- 分布式事务的取舍（AT vs TCC vs 消息最终一致）
- 高并发设计模式（缓存 → 削峰 → 限流 → 降级）
- 分库分表实战（ShardingSphere user_id % 16）
- Multi-Agent 从单体 Agent 进化到多 Agent 协作架构

**瓶颈发现**：AI 依赖外部 API → 延时不稳定 → 需要本地部署

### 3.4 阶段三：LingShu/灵枢 —— AI 工程化深度

| 层面 | 技术栈 | 掌握程度 | 方向 |
|:----:|:------:|:--------:|:----:|
| RAG | 14 步 RAG 管线、BM25+向量混合检索、RRF k=60 | 核心亮点 | 继续优化召回率 |
| 安全 | 输入 3 级检测、输出 6 条危险模式、PHI 脱敏 | 核心亮点 | 扩展到多模态安全 |
| AI 部署 | Ollama（qwen2:1.5b / llama3.2:3b）、8GB 内存 | 理解原理 | 模型微调 + 量化 |
| 异常 | L1-L4 四级异常分类体系 | 熟练掌握 | 自适应降级 |
| 容器化 | Docker Compose 9 服务编排 | 熟练掌握 | K8s 编排 |
| 数据 | Python 爬虫 + 2000 条 QA 标注测试集 | 理解原理 | 自动化数据标注 |

**学到什么**：
- RAG 管线的逐步优化（3→7→14 步的演进过程）
- 混合检索调优（BM25 关键词 + 向量语义 + RRF 融合排序）
- 安全护栏的完整性（输入输出双向检测 + 数据脱敏）
- 异常分类与容错（L1-L4 四级体系，不同级别不同策略）
- 本地模型部署的关键（Ollama 管理、模型选择、资源限制）

**持续方向**：模型微调 → 端侧部署 → 更复杂的 Multi-Agent 协作

### 3.5 演进核心思路

> 💡 **面试话术**：这三个项目背后有一条清晰的技术进化线——从单体到分布式再到 AI 工程化。
>
> **单体阶段**，我快速验证了 AI+后端的可行性，但也发现了扩展性限制——功能耦合严重、团队协作困难、高并发扛不住。
>
> **微服务阶段**，我系统性地解决了这些问题——12 微服务拆分、Redis Lua 秒杀 2000+ QPS、Seata AT 分布式事务，但又发现了新的瓶颈：外部 AI API 的延迟和稳定性不可控。
>
> **AI 深耕阶段**，我把重心放在 AI 工程化——本地部署 qwen2/llama3.2 模型、构建完整的 14 步 RAG 管线、实现全链路安全控制。这个演进过程本质上是一个**「发现问题 → 解决问题 → 发现新问题」**的螺旋上升。

DocumentSplitter 语义分段，overlap 10-15% 防止段落断裂。
结论是：AI 和后端可以融合，但需要精心设计的架构——容错、限流、降级一个都不能少。

**SuGuangMall 解决的问题：高并发和分布式系统的工程化落地。**
Flavor Dash 验证了单体架构下 AI+后端的可行性，但单体架构的瓶颈很明显：
高并发扛不住（200 QPS 就到顶了），团队协作困难（代码冲突频繁），功能耦合严重。
SuGuangMall 就是针对这些问题的解决方案——
12 微服务按 DDD 限界上下文拆分，解决耦合和协作问题；
Redis Lua + Sentinel 限流 + RabbitMQ 削峰解决高并发问题，QPS 从 200 提升到 2000+；
Seata AT 保证跨服务的分布式事务一致性；
ShardingSphere user_id 分 16 表解决数据量增长问题。
Multi-Agent 购物管家则是在 AI 层面的进化——从单 Agent 到 6 Agent 并行协作，
AgentRouter 做意图路由，Orchestrator 协调执行，能处理更复杂的业务场景。
这个项目回答的是：**怎么把单体 demo 变成能扛住真实流量的系统。**

**LingShu 解决的问题：AI 从原型到工程化的完整链路。**
前两个项目都依赖外部 AI API——延时高、不稳定、有隐私风险，这在医疗领域是不可接受的。
LingShu 验证了一个自包含的 AI 系统应该怎么做：
本地部署模型——Ollama 管理 qwen2:1.5b/llama3.2:3b，8GB 就能跑，延时稳定在 200ms 以内；
完整的 14 步 RAG 管线——从文档加载到答案生成，每步都可监控、可 Debug；

医学级别的安全——输入 3 级检测、输出 6 条危险模式、PHI 三层脱敏、L1-L4 四级异常分类。
这个项目回答的是：**AI 系统怎么从实验原型变成可靠可用的工程产品。**

**三个项目本质上是对同一个问题的三个不同角度的回答：后端工程师如何与 AI 协同工作。**
Flavor Dash 试水——验证可行性；
SuGuangMall 扩展——解决规模化问题；

### 6.6 Q5：「你在项目中遇到的最大困难是什么？怎么解决的？」（STAR-R 格式完整故事）

> **STAR-R 框架**：Situation（背景）→ Task（任务）→ Action（行动，含尝试/失败/改进）→ Result（结果）→ Reflection（反思）

> **标准答法**（选择 SuGuangMall 秒杀库存一致性）：

**Situation（背景）：**
"最大的困难来自 SuGuangMall 秒杀系统的库存一致性保障。
秒杀高峰期有 2000+ QPS 的并发请求同时扣减同一商品库存，系统要在保证不超卖的前提下，
还要有流畅的用户体验。库存一旦超卖，就会导致用户下单后无法发货，这是电商平台的严重事故。"

**Task（任务）：**
"我的任务是设计并实现一个高并发库存扣减方案，目标有两个硬性指标：
第一，零超卖——扣减库存必须绝对精确；
第二，QPS 2000+——秒杀页面要扛住峰值流量。
软性指标是：架构要有可扩展性，不能为了性能牺牲代码可维护性。"

**Action（行动，含三轮迭代）：**

"**第一轮：MySQL 行级锁 + 乐观锁。**
一开始我们直接依赖数据库的锁机制。每次扣库存前先 `SELECT ... FOR UPDATE` 锁住行，
扣减后检查库存 >= 0。压测结果很不理想——QPS 只能到 200 左右，
数据库连接池迅速打满，大部分请求都在等锁。
这个方案的根本问题是：数据库行锁在高并发下成为瓶颈，且乐观锁的大量重放浪费了连接资源。

**第二轮：Redis 单机扣库存 + Lua 脚本原子操作。**
吸取教训后，我们把库存扣减前置到 Redis，利用 Redis 的单线程模型保证原子性。
核心是写了一个 Lua 脚本三步走：检查库存 → 扣减库存 → 记录用户已秒杀。
性能提升到 QPS 1000+，但又遇到两个新问题：
一是 Redis 单点故障直接导致秒杀不可用；
二是多个应用节点竞争同一商品，需要分布式锁保护。

**第三轮：多级缓存 + 哨兵模式 + 分布式锁 + 限流。**
最终方案是多管齐下：
Caffeine 做第一级本地缓存（热点商品预热约 500 条），Redis Sentinel 做第二级，
库存扣减用 Redisson 分布式锁保护 Lua 脚本执行，同时配置了看门狗自动续期防止锁过期。
Sentinel 做限流，超出阈值的请求直接返回'排队中'，用 RabbitMQ 异步处理落库。

**踩过最深的坑：**
有一次 Lua 脚本中的库存变量类型写成了 string 而不是 number，
在 Redis 中 `DECRBY` 时出现了隐式类型转换问题，高并发下出现了负数库存。
排查了一整个下午——最后是同事提醒用 `Redis MONITOR` 命令一条一条回放执行记录，
才发现是类型问题。这个教训让我养成了三个习惯：
1) Lua 脚本上线前必须做 JMeter 压测验证
2) 所有扣减操作后都要加 `>= 0` 的非负断言
3) 监控大盘上必须有库存变化实时曲线，一眼能看到异常"

**Result（结果）：**
"最终方案达到：QPS 2000+，线上运行零超卖，订单全流程成功率 99.5%，
P99 响应时间在 300ms 以内。这个方案在生产环境稳定运行至今。"

**Reflection（反思）：**
"如果现在重做，我会有两点改进：
第一，预先生成库存 Token 机制——提前将库存拆分为 Token 并预热到 Caffeine 本地缓存，
用户抢购时先抢 Token，抢到后再异步落库。
这样可以进一步降低 Redis 压力，理论上 QPS 能到 5000+。
第二，限流和熔断的阈值可以做成动态的，根据实时流量自适应调整，
而不是现在这种固定配置。"

> 🎯 **核心要点**：Q5 几乎必问，你的回答要包含完整的「问题 → 尝试 → 失败 → 改进 → 结果 → 反思」链路。避坑经历和反思比成功更打动人。STAR-R 框架中的 R（反思）是面试官最看重的部分，展示你的复盘和成长能力。

    → 问最大困难、线上故障经历、团队冲突
    → 应对：用 STAR-R 框架 + 真实的情绪 + 反思改进

【二面场景题应对策略】
- 多用「为什么不选 A 而选 B」的对比句式，展示技术判断力
- 每个技术决策都要给出取舍逻辑（性能 vs 一致性 vs 开发成本）
- 准备 2-3 个「踩坑 → 解决 → 反思」的完整故事
- 展示技术热情——"我最近在学 LangChain4j，因为我觉得它可以让 Agent 框架更规范"
```

### 8.4 三面面试官的心理与应对

```
三面面试官的心理活动：
├─ "技术人员的格局怎么样？"（权重最高）
│   → 问架构演进、技术趋势、行业理解
│   → 应对：展示从单体到微服务到 AI 的演进思考
│   → 举例："从 Flavor Dash 到 LingShu 的演进，本质是我对
│             '后端工程师如何与 AI 协作'这个问题的不断深入"
│
├─ "能不能站在业务角度看技术？"
│   → 问技术对业务的价值、投入产出比、技术选型的经济性
│   → 应对：说清楚每个技术投入产生了什么业务效果
│   → 举例："引入多级缓存后 DB 查询减少 80%，节省了 2 台 MySQL 从库成本"
│
├─ "有架构思维吗？能独立设计系统吗？"
│   → 问系统设计题、高可用架构、容灾方案
│   → 应对：展示从整体到局部的结构化思维
│   → 举例："如果我来设计一个秒杀系统，我会从流量入口开始分层——
│             浏览器端限频 → CDN 静态化 → Nginx 限流 → 业务层削峰 → 数据层保护"
│
└─ "未来能不能成长为技术骨干？"
    → 问学习方向、技术规划、最近在看什么书
    → 应对：给出清晰的技术发展规划（1年/3年/5年）
    → 举例："1 年内深入 Java 并发和 JVM 调优，3 年内做到能独立设计
             中大型系统架构，5 年往 AI 基础设施方向走"

【三面场景题应对策略】
- 多讲技术选型的宏观思考（技术生态、社区活跃度、学习成本）
- 展示你对技术趋势的理解（Spring AI、云原生、AI 工程化、MCP 协议）
- 在对比中体现「成本意识」——"选 Seata AT 是因为 AT 对业务代码无侵入"
- 主动展示学习能力——"我通过看官方文档和源码来学习，大致花了 2 周跑通"
```

### 8.6 面试中的「红线」——千万不能做的事

| 红线行为 | 为什么不能做 | 正确做法 |
|:--------:|:-----------:|:---------:|
| **背课文** | 面试官立刻知道你是在准备面试而不是真实做过 | 适当停顿思考，用自己自然的语气讲，允许"嗯…让我想想" |
| **夸大项目** | 被追问细节会穿帮，一旦被质疑真实性全盘皆输 | 诚实地分层，主动说"这部分我的参与度不高" |
| **回避问题** | 显得你不真诚或技术不行 | 遇到不会的：先承认不会 → 再说自己的理解 → 给出学习计划 |
| **否定面试官** | 技术讨论中直接否定对方观点 | 先肯定再补充："您说的有道理，另外我的实践情况是..." |
| **过度炫技** | 用大量术语轰炸，显得华而不实 | 用大白话讲清楚核心逻辑，术语用于精准表达不是堆积 |
| **抱怨团队** | 说团队不行、同事不行、资源不够 | 即使有团队问题，也要从正面角度表达——"我们在努力改善协作流程" |

## 9. 常见开场陷阱与应对

面试官有时会故意抛出一些有挑战性的开场问题来测试你。以下三种最常见的情景及应对策略：

### 9.1 陷阱一：贬低项目 —— 「你这个项目看起来很简单，不就是 CRUD 吗？」

**面试官心理**：想看你面对质疑时的反应——是慌乱辩解，还是能冷静分析并展示技术深度。

**错误应对**：
```
❌ "不是的，我这个项目很复杂，有高并发有分布式..."
   （显得急于辩解，反而心虚）
❌ "确实比较简单，我还在学习中..."
   （自我贬低，失去谈判筹码）
```

**正确策略**：承认基础 + 快速甩出技术亮点 + 反问引导

> **标准应对话术**：
>
> "从业务层面来看，确实核心是 CRUD——任何后端系统本质上都是对数据的增删改查。但我觉得区分一个项目水平的关键不是有没有 CRUD，而是在 CRUD 之外做了什么。
>
> 以 SuGuangMall 的秒杀系统为例，同样是订单的'增'——我们要在 2000+ QPS 的并发下保证库存不超卖，这就不是简单 INSERT 能解决的。我们用了 Redis Lua 保证原子扣减、Sentinel 限流、RabbitMQ 削峰、Seata 保证事务一致性，Caffeine+Redis 做多级缓存加速。每一个环节背后都有对应的技术挑战和优化。
>
> 另外，如果光看 API 接口是 CRUD，但每个接口内部的实现——比如 Agent 框架的 Think→Act→Observe 循环实现、LLM Client Factory 的多模型策略管理、ShardingSphere 的分片路由——这些都不是 CRUD 能概括的。
>
> 所以我的理解是：CRUD 是表象，真正的技术含量在于 CRUD 之上的**架构设计、性能优化、异常处理、安全控制**这些非功能性需求的实现。您觉得呢？"

### 9.2 陷阱二：质疑选择 —— 「你这微服务拆得太碎了吧？有必要吗？」

**面试官心理**：测试你的技术决策是否经过了独立思考，还是"为了微服务而微服务"。

**错误应对**：
```
❌ "是有点碎，但大家都这么拆..."
   （没有自己的判断）
❌ "不碎啊，12 个刚刚好"
   （不接受反馈，固执）
```

**正确策略**：承认 tradeoff + 给出当时的决策逻辑 + 现在复盘有新认识

> **标准应对话术**：
>
> "您说得有道理，12 个微服务确实带来了运维复杂度。其实这个拆分粒度是我们经过两轮调整后确定的。
>
> 一开始我们只有 5 个服务（用户、商品、订单、支付、秒杀），但随着业务扩展发现几个问题：第一，商品服务里混了搜索逻辑，一次改动影响面很大；第二，秒杀的库存扣减和普通下单耦合在一起，影响了非秒杀场景的稳定性。
>
> 所以第二轮我们按照 DDD 限界上下文重新切分——把搜索独立成搜索服务、秒杀独立成秒杀服务、AI 相关独立成 7 个 AI 服务。最终是 12+7 的结构。
>
> 但坦白说，现在复盘看，**不是所有的服务都需要独立部署**。比如评价服务和用户服务的数据关联很强，其实可以合并在一个服务里。我的教训是：微服务拆分的粒度应该由**业务变更频率和独立部署需求**驱动，而不是为了拆分而拆分。
>
> 如果现在重做，我会把关联性强的几个服务合并，比如评价合到用户、优惠券合到订单，减少到 8 个核心业务服务。AI 服务保持独立是因为它们的技术栈和迭代节奏和业务服务不同。"
>

> 💡 **关键点**：这种问题的本质是看你有没有**反思能力**。能自己说出"这里拆得太细"比面试官指出来要好得多。主动承认不足并给出改进方案，展示了成熟的技术判断力。

### 9.3 陷阱三：追问真实性 —— 「你一个学生，怎么一个人做了19个服务？」

**面试官心理**：学生对项目规模的描述往往存在夸大嫌疑，面试官在验证项目真实性。

**错误应对**：
```
❌ "虽然 19 个服务但我很努力……"
   （答非所问）
❌ "不是一个人，团队好几个人一起"
   （虽然正确但太简单，显得防御性）
```

**正确策略**：诚实说明分工 + 展示你负责的核心模块 + 说明项目的迭代性质

> **标准应对话术**：
>
> "其实有两个背景需要说明：
>
> **第一，不是一个人做的。** 我们是 3 个人的项目小组，我主要负责后端核心逻辑——包括秒杀系统、Agent 框架、订单流程、以及 AI 服务的落地。同学负责前端和部分基础服务（用户、商品 CRUD），另一个同学负责运维和测试。
>
> **第二，19 个服务不是一开始就有的，是迭代的结果。** SuGuangMall 是从 Flavor Dash 演进过来的，很多代码和设计在前一个项目已经验证过。实际开发周期大概 4 个月，平均每周上线 2-3 个新服务。
>
> **第三，19 个服务中，有 7 个是 AI 微服务。** 这些 AI 服务的代码量其实不大——每个 Agent 服务核心代码约 500-800 行，主要是 Agent 的逻辑编排和工具调用，因为底层的 LLM 调用通过封装好的 ClientFactory 统一管理。真正代码量大的还是业务服务，比如订单服务大概 3000 行、秒杀服务 2000 行。
>
> 我从 Flavor Dash 的大约 3 万行代码，到 SuGuangMall 的大约 5 万行——不是一夜之间写出来的，而是持续 8 个月的迭代积累。"
>

> 💡 **关键点**：诚实地分享分工和迭代过程。面试官不是真的要拆穿你，而是测试你面对压力问题时的反应和项目的真实参与度。

### 9.4 陷阱扩展：压力测试汇总

| 陷阱类型 | 典型话术 | 核心应对原则 |
|:--------:|----------|:------------:|
| 贬低项目 | "这不就是 CRUD 吗？" | 承认 CRUD 基础 + 秒甩亮点 + 反问 |
| 质疑选择 | "这架构有必要吗？" | 承认 tradeoff + 展示决策逻辑 + 主动复盘 |
| 质疑真实性 | "你一个人做的？" | 诚实分工 + 展示负责模块 + 说明迭代过程 |
| 压力打断 | 频繁打断追问细节 | 保持节奏不受影响，停顿后接着说 |
| 沉默施压 | 你讲完后不说话看着你 | 补充一个亮点或反问"您想了解哪个部分的细节？" |
| 否定结论 | "你的方案有问题" | "您说的这个场景我可能没考虑到，能具体说说吗？" |
| 极限假设 | "如果 QPS 再加 10 倍呢？" | 展示扩展思路 + 说明当前架构的扩展性设计 |

---

> 🎯 **核心要点**：面试本质上是一次**「技术信任建立」**的过程。面试官通过你的项目描述来判断三件事：**你真的做过**（真实性）、**你真的理解**（深度）、**你真的会思考**（复盘能力）。这份 01 模块的目的是帮你在开场阶段就建立起这种信任。
