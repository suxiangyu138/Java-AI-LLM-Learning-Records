## 1. 场景题 1：CPU 突然飙升到 100%，你怎么排查？

> **面试官意图**：考察 Linux 基础 + JVM 调优能力 + 是否真的上过线。背过 jstack 命令的人很多，能完整说出排查链路的很少。

### 标准回答：完整排查链路（5 步法）

**Step 1：`top` 找到高 CPU 进程**

```bash
# 按 CPU 使用率降序，找到吃 CPU 的 Java 进程
top -c
```

输出示例：

```
top - 14:32:10 up 30 days,  2:15,  1 user,  load average: 12.5, 10.2, 8.1
Tasks: 235 total,   3 running, 232 sleeping
%Cpu(s): 98.5 us,  1.0 sy,  0.0 ni,  0.0 id,  0.0 wa,  0.0 hi,  0.5 si
  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
12345 admin     20   0 4.5g 1.2g  45m  S  350%  15.0  123:45 java -jar app.jar
```

> 现象：Java 进程 PID=12345，CPU 占用 350%（多核），RES 1.2GB 正常，说明不是内存问题，是 CPU 密集计算问题。

**Step 2：`top -Hp` 找到高 CPU 线程**

```bash
top -Hp 12345
```

输出示例：

```
  PID USER      PR  NI    VIRT    RES    SHR S %CPU
12389 admin     20   0 4.5g 1.2g  45m  R 98.0
12390 admin     20   0 4.5g 1.2g  45m  R 97.5
12391 admin     20   0 4.5g 1.2g  45m  R 96.8
```

> 现象：3 个线程（PID=12389/12390/12391）各占近 100%，说明是多线程并发问题。

**Step 3：`printf '%x'` 转 16 进制（jstack 用）**

```bash
# jstack 的 nid 是 16 进制，需要转换
printf '%x\n' 12389 12390 12391
# 输出：3065  3066  3067
```

**Step 4：`jstack` 拉线程快照**

```bash
# 拉一次不够，3 次隔 5 秒，找始终 RUNNABLE 的线程
jstack 12345 > thread_dump_1.txt
sleep 5
jstack 12345 > thread_dump_2.txt
sleep 5
jstack 12345 > thread_dump_3.txt
```

**Step 5：分析线程栈，定位代码行**

```bash
# 在 dump 文件中搜索 nid=0x3065
grep -A 20 'nid=0x3065' thread_dump_1.txt
```

输出示例：

```
"pool-1-thread-3" #14 prio=5 os_prio=0 tid=0x00007f nid=0x3065 runnable [0x00007f]
   java.lang.Thread.State: RUNNABLE
    at com.example.service.OrderService.calculatePrice(OrderService.java:85)
    at com.example.service.OrderService.processOrder(OrderService.java:120)
    at java.util.concurrent.ThreadPoolExecutor.runWorker(ThreadPoolExecutor.java:1149)
    at java.util.concurrent.ThreadPoolExecutor$Worker.run(ThreadPoolExecutor.java:624)
    at java.lang.Thread.run(Thread.java:748)
```

> 定位到 `OrderService.java:85` 的 `calculatePrice` 方法。

### 常见 CPU 飙升原因

| 原因 | 典型特征 | 快速验证 |
|------|---------|---------|
| **死循环** | 线程永远 RUNNABLE，jstack 看到同一个栈 | `jstack` 多拍对比，代码 review |
| **Full GC 频繁** | CPU 高但 USER 不高，SYS 高 | `jstat -gcutil 12345 1000` 看 FGC |
| **正则回溯** | `(a|aa)*b` 类模式匹配长文本 | 线上正则改为预编译 Pattern，加超时 |
| **JSON 大对象序列化** | Jackson/FastJson 序列化大 List | 限制序列化大小，改用流式处理 |
| **死锁自旋** | 线程 BLOCKED + 循环重试 | jstack 看锁等待关系 |

### 真实案例：FastJson 序列化大对象导致 CPU 100%

Flavor Dash 项目曾遇到：导出订单报表时，`JSON.toJSONString(orderList)` 序列化 10 万条订单，CPU 瞬间打满 100%，持续 3 分钟。

**根因**：FastJson 序列化大 List 时，会触发 `FieldInfo` 反射缓存膨胀，加上循环引用检测算法复杂度高。

**解决**：
- 限制单次导出数量 ≤ 5000 条
- 改用流式 JSON 处理（`JsonWriter`）
- 加入异步导出 + 文件下载

> 💡 **面试追问 1**：如果 jstack 看不到业务线程栈怎么办？
> 
> 答：可能不是 Java 进程的 CPU 问题，用 `pidstat -t -p 12345 1` 确认是 JVM 线程还是 GC 线程。如果是 GC 线程（VMThread）高，说明是 GC 导致的 CPU 飙升，用 `jstat -gcutil` 分析 GC 情况。

> 💡 **面试追问 2**：线上不能用 jstack 怎么办（权限限制）？
> 
> 答：用 Arthas 的 `thread -n 5` 命令，不需要 root 权限；或者用 `arthas-boot.jar` 附加到进程。

> 💡 **面试追问 3**：Docker 容器里怎么排查？
> 
> 答：进入容器 `docker exec -it <container> bash`，Alpine 基础镜像没有 `top`，用 `cat /proc/1/status` 或 `apk add procps`。

> 🎯 **核心要点**：CPU 问题排查三板斧——`top` 找进程 → `top -Hp` 找线程 → `jstack` 定位代码。关键在于能完整说出每一步命令+输出解读，这比背概念更能证明实力。

## 2. 场景题 2：线上 OOM 了，怎么排查？怎么定位是哪块代码导致的？

> **面试官意图**：考察 JVM 内存管理理解 + 实际排错经验。OOM 是最常见的线上事故之一，能说清楚排查链路是基本功。

### 标准回答：OOM 排查 4 步法

**Step 1：确认 OOM 现象**

检查应用日志、告警信息：

```text
java.lang.OutOfMemoryError: Java heap space
        at java.util.Arrays.copyOf(Arrays.java:3236)
        at java.util.ArrayList.grow(ArrayList.java:261)
```

JVM 参数中必须提前加上 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/dump.hprof`

**Step 2：`jmap` 导出堆快照**

如果进程还活着：

```bash
# 先看堆概要
jmap -heap 12345

# 查看存活对象统计
jmap -histo:live 12345 | head -30
```

输出示例：

```
 num     #instances         #bytes  class name
----------------------------------------------
   1:        450000      180000000  [Ljava.util.HashMap$Node;
   2:        350000       84000000  com.example.entity.Order
   3:        200000       64000000  com.example.entity.UserSession
   4:        150000       48000000  [B
   5:         50000       32000000  java.util.concurrent.ConcurrentHashMap
```

> 发现 `UserSession` 实例数异常多（20 万），正常情况下应该只有几百。

```bash
# 导出完整 dump（大内存注意磁盘空间）
jmap -dump:live,format=b,file=/tmp/heap_dump.hprof 12345
```

如果进程已挂，找启动参数里 `HeapDumpPath` 自动生成的 `.hprof` 文件。

**Step 3：MAT 分析堆快照**

使用 Eclipse MAT（Memory Analyzer Tool）分析：

1. **Leak Suspects Report**：MAT 自动生成泄漏嫌疑报告
2. **Dominator Tree**：按保留堆大小排序，看最大的对象
3. **GC Roots**：从 GC Root 到嫌疑对象的引用链

MAT 关键操作：

```
// 打开 dump 文件后，常用操作：
1. Leak Suspects → 看自动分析报告
2. Histogram → class name 过滤 "UserSession"
   - 右击 → Merge Shortest Paths to GC Roots → exclude weak/soft references
3. 找到持有引用的 Thread → 定位到代码
```

**Step 4：定位到具体代码**

MAT 分析示例：

```
One instance of "java.util.concurrent.ConcurrentHashMap" loaded by "<system class loader>" occupy
1,200,000,000 (60%) bytes. 

The thread "http-nio-8080-exec-15" maintains a static reference to this Map.
→ com.example.config.UserSessionManager.sessionCache
  → Line 45: private static final Map<String, UserSession> sessionCache = new ConcurrentHashMap<>();
```

> 发现是 `UserSessionManager` 中的静态 Map 一直在增加，没有清理机制。

### 常见 OOM 类型

| OOM 类型 | 触发场景 | 排查方向 |
|---------|---------|---------|
| **Java heap space** | 堆内存不足 | MAT 分析大对象、内存泄漏 |
| **Metaspace** | 加载了太多类（CGLib 动态代理、热部署） | `jstat -gcmetacapacity`，检查类加载器 |
| **Direct buffer memory** | NIO 堆外内存泄漏（Netty） | `-XX:MaxDirectMemorySize`，用 `pmap` 查看 |
| **Unable to create native thread** | 线程数超限（Linux 进程限制） | `ulimit -u`，`cat /proc/sys/kernel/threads-max` |
| **GC overhead limit exceeded** | 98% 时间花在 GC，回收不到 2% | `jstat -gcutil` 看 GC 频率，多半是内存泄漏 |

### 真实案例：ThreadLocal 没清理导致内存泄漏（SuGuangMall）

**场景**：SuGuangMall 订单服务上线 3 天后 OOM，每次 GC 后内存回收不到 10%。

**根因**：

```java
// 问题代码
private static final ThreadLocal<UserContext> userContextHolder = new ThreadLocal<>();

public void processOrder(OrderRequest request) {
    UserContext ctx = new UserContext(request.getUserId(), request.getRole());
    userContextHolder.set(ctx);
    // ... 业务逻辑 ...
    // 忘记：userContextHolder.remove();
}
```

线程池的线程复用时，`ThreadLocal` 持有 `UserContext` 对象不被释放 → `UserContext` 又持有大量权限数据 → 内存泄漏。

**解决**：
```java
try {
    userContextHolder.set(ctx);
    // 业务逻辑
} finally {
    userContextHolder.remove(); // 核心：必须 finally 中清理
}
```

**验证**：MAT 分析发现 `ThreadLocal` 的 `ThreadLocalMap$Entry` 中 key=null 但 value 未被回收。

> 💡 **面试追问 1**：OOM 一定能 dump 到吗？
> 
> 答：不一定。如果操作系统 kill 了进程（OOM Killer），JVM 来不及生成 dump。这时候看系统日志 `dmesg | tail -20` 或 `/var/log/messages` 会看到 `Out of memory: Kill process 12345 (java)`。

> 💡 **面试追问 2**：生产环境内存很大（32G），dump 不了怎么办？
> 
> 答：用轻量级方案：(1) `jmap -histo:live` 先看对象分布；(2) Arthas `dashboard` 实时看内存；(3) 用 `jcmd` 代替 jmap；(4) 用 async-profiler 采样。

> 💡 **面试追问 3**：Metaspace OOM 通常什么原因？
> 
> 答：最常见的是 CGLib/动态代理生成大量代理类，或者热部署时类加载器没释放。`jstat -gcmetacapacity` 看 Metaspace 使用趋势，`-XX:MaxMetaspaceSize` 限制上限。

> 💡 **面试追问 4**：进程没挂但频繁 Full GC 怎么办？
> 
> 答：不要急于重启！先 dump 堆，再重启。重启会丢失现场，问题还会复现。用 `jstat -gcutil 12345 1000 10` 每 1 秒看一次 GC 情况。

> 🎯 **核心要点**：OOM 排查四步法——确认现象（看日志）→ 导出堆（jmap/jcmd）→ MAT 分析（Leak Suspects/Dominator Tree）→ 定位代码。关键经验：生产环境一定要加 `-XX:+HeapDumpOnOutOfMemoryError`，这是最后的救命稻草。

## 3. 场景题 3：接口响应突然变慢，从 50ms 到 2s，怎么排查？

> **面试官意图**：考察分层排查能力 + 链路追踪经验 + 对全栈技术栈的掌控力。不是单一原因，需要系统思维。

### 标准回答：分层排查链路（自底向上 / 自顶向下）

**常用策略：自顶向下分层排查**

```
┌────────────────────────────────────────────┐
│ ① 网络层：ping / traceroute / mtr          │
├────────────────────────────────────────────┤
│ ② 网关层：Nginx access log / Gateway 监控   │
├────────────────────────────────────────────┤
│ ③ 应用层：Arthas trace/watch/tt           │
├────────────────────────────────────────────┤
│ ④ 中间件层：Redis / MQ / ES 状态           │
├────────────────────────────────────────────┤
│ ⑤ 数据层：慢 SQL / 连接池 / 锁等待         │
├────────────────────────────────────────────┤
│ ⑥ JVM 层：GC 停顿 / 线程阻塞               │
└────────────────────────────────────────────┘
```

#### Step 1：网络层

```bash
# ① 检查网络延迟
ping target-service-host
# 正常：< 1ms（内网）

# ② 确认路由
traceroute target-service-host
# 看每跳延迟，排除网络瓶颈

# ③ 更精准的
mtr --report target-service-host
```

#### Step 2：网关层

查看 Nginx 日志 / Spring Cloud Gateway 指标：

```bash
# Nginx access log 分析响应时间
tail -1000 /var/log/nginx/access.log | awk '{print $NF}' | sort -n | tail -10
# 看 P99 响应时间
```

#### Step 3：应用层（核心——Arthas 大显身手）

```bash
# ① trace 整个调用链，看哪一步最慢
trace com.example.service.OrderService createOrder -n 5 --skipJDKMethod false
```

输出示例：

```
`---ts=2026-07-28 10:15:30;thread_name=http-nio-8080-exec-5;id=12;is_daemon=true;priority=5;
    `---[1986.32ms] com.example.service.OrderService:createOrder()
        +---[0.03ms] com.example.service.OrderService:validateParams()
        +---[0.12ms] com.example.service.OrderService:buildOrderContext()
        +---[180.45ms] com.example.service.OrderService:deductStock()        ← 耗时异常
        |   `---[178.23ms] com.example.dao.StockDao:updateStock()
        +---[1200.15ms] com.example.service.OrderService:calculatePrice()    ← 最慢
        |   `---[1198.50ms] com.example.dao.PriceRuleDao:queryRules()
        +---[0.50ms] com.example.service.OrderService:saveOrder()
```

> 清晰看到：`PriceRuleDao.queryRules()` 耗时 1.2s，占比超过 60%。

```bash
# ② watch 具体方法的入参和出参
watch com.example.dao.PriceRuleDao queryRules "{params,returnObj}" -x 3 -n 5

# ③ 如果方法生产数据量大，用 tt（TimeTunnel）回放
tt -t com.example.dao.PriceRuleDao queryRules -n 3
# 回放某次请求
tt -i 1001 -p
```

#### Step 4：中间件层

```bash
# Redis 慢查询
redis-cli SLOWLOG GET 10

# RabbitMQ 状态
rabbitmqctl list_queues name messages consumers

# ES 慢查询
curl -X GET "localhost:9200/_cat/thread_pool?v&h=host,queue,rejected,completed"
```

#### Step 5：数据层（最频繁的问题源）

```sql
-- ① 查慢 SQL（MySQL）
SELECT * FROM information_schema.processlist WHERE command != 'Sleep' ORDER BY time DESC;

-- ② 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;

-- ③ 查看锁等待
SELECT * FROM information_schema.INNODB_LOCKS;
SELECT * FROM information_schema.INNODB_LOCK_WAITS;
```

#### Step 6：JVM 层

```bash
# 看 GC 停顿
jstat -gcutil 12345 1000 10

# Arthas 看内存
dashboard

# 看线程状态
thread -b  # 死锁检测
thread -n 3  # 最忙的 3 个线程
```

### 真实案例：慢 SQL + 缓存失效叠加导致接口雪崩（SuGuangMall）

**现象**：订单列表接口从 50ms 变 2s，持续 10 分钟后恢复，每天同一时间出现。

**排查过程**：

1. Arthas trace → `OrderDao.queryOrders()` 耗时 1.8s
2. 慢 SQL 日志 → 发现 `ORDER BY create_time DESC` 没有索引，全表扫描
3. 同时发现 Redis 缓存刚好在整点过期（大量 key 同时失效）→ 缓存击穿
4. 慢 SQL + 缓存失效叠加 → 数据库连接池打满 → 接口全面变慢

**解决**：
- 给 `create_time` 加索引
- 缓存过期时间增加随机偏移 `base + random(0, 300)` 秒
- 配合本地缓存（Caffeine）做二级保护

> 💡 **面试追问 1**：Arthas trace 对生产有性能影响吗？
> 
> 答：有，但影响很小（微秒级）。不建议长时间 trace，采样几次后关闭即可。Arthas 的 `trace` 基于字节码增强，只在增强的方法调用前后插桩。

> 💡 **面试追问 2**：如果没有 Arthas，还有什么方案？
> 
> 答：(1) SkyWalking/Pinpoint APM 全链路追踪；(2) 业务日志 + MDC traceId 串联；(3) 阿里云 ARMS / 火山引擎 APM 等商业化方案。

> 💡 **面试追问 3**：接口偶尔慢一下（TP99 高）怎么定位？
> 
> 答：看 GC 日志是否有 STW 停顿、看 Full GC 频率、看 YGC 时间。用 `-XX:+PrintGCApplicationStoppedTime` 打印 STW 时间。

> 🎯 **核心要点**：接口变慢不是单一原因，要有分层排查的思维框架。Arthas trace 是杀手锏——能秒级定位"哪个方法最慢"。生产环境加好监控（Prometheus + Grafana），把平均响应时间和 P99 响应时间都监控起来。

## 4. 场景题 4：Redis 内存满了怎么办？淘汰策略怎么选？

> **面试官意图**：考察 Redis 内存管理理解 + 实际运维经验。别看简单，里面有很多坑。

### 标准回答：排查与处理流程

#### 第一步：确认内存状态

```bash
# ① 查看内存使用
redis-cli INFO memory

# 关键指标
used_memory_human: 6.5G          # 已使用
maxmemory_human: 8.0G            # 最大值
used_memory_peak_human: 7.2G     # 峰值
mem_fragmentation_ratio: 1.2     # 碎片率（>1.5 说明碎片严重）

# ② 查看当前淘汰策略
redis-cli CONFIG GET maxmemory-policy
# 输出：1) "maxmemory-policy"  2) "noeviction"

# ③ 查看 key 数量
redis-cli DBSIZE
redis-cli INFO keyspace
```

#### 第二步：找出大 Key

```bash
# ① 使用 --bigkeys 扫描（不会阻塞长时间，但会扫描全库）
redis-cli --bigkeys

# 输出示例
-------- biggest string found ---------
key: "user:12345:session"  bytes: 45000000   ← 45MB！
-------- biggest list found ---------
key: "queue:order:dead_letter"  len: 120000  ← 12 万条

# ② 更精确的 memory usage 分析
redis-cli MEMORY USAGE "user:12345:session"
# 输出：(integer) 45012300

# ③ 扫描所有大 Key（生产环境慎用，建议在从库或低峰期）
redis-cli --scan --pattern "*" | while read KEY; do
  SIZE=$(redis-cli MEMORY USAGE "$KEY")
  if [ "$SIZE" -gt 1048576 ]; then  # > 1MB 的 key
    echo "$KEY $SIZE"
  fi
done
```

#### 第三步：选择淘汰策略

| 策略 | 规则 | 适用场景 |
|------|------|---------|
| **noeviction** | 不淘汰，写请求直接返回 OOM 错误 | 默认策略，数据库缓存慎用！ |
| **allkeys-lru** | 所有 key 中淘汰最近最少使用的 | ⭐ 通用缓存（推荐） |
| **allkeys-lfu** | 所有 key 中淘汰最不经常使用的 | 访问频率差异大的缓存 |
| **volatile-lru** | 在设置了 TTL 的 key 中淘汰最近最少使用的 | 会话缓存（Session） |
| **volatile-lfu** | 在设置了 TTL 的 key 中淘汰最不经常使用的 | 带 TTL 的热度缓存 |
| **volatile-ttl** | 在设置了 TTL 的 key 中淘汰 TTL 最小的（即将过期的） | 优先保留新数据 |
| **allkeys-random** | 所有 key 中随机淘汰 | 数据访问均匀的场景 |
| **volatile-random** | 在设置了 TTL 的 key 中随机淘汰 | 很少用 |

#### 选择建议

```bash
# 方案 A：通用缓存（推荐，Favor Dash / SuGuangMall 使用）
CONFIG SET maxmemory-policy allkeys-lru
CONFIG SET maxmemory 8gb

# 方案 B：Session 缓存（易用 volatile）
CONFIG SET maxmemory-policy volatile-lru
CONFIG SET maxmemory 4gb

# 方案 C：数据不可丢失（比如消息队列场景）
CONFIG SET maxmemory-policy noeviction
# 但要监控内存，及时告警
```

#### 第四步：紧急处理

```bash
# ① 删除无用的大 Key（生产环境要用 unlink 异步删除）
redis-cli UNLINK "user:12345:session"

# ② 批量删除符合模式的 key
redis-cli --scan --pattern "cache:temp:*" | xargs redis-cli UNLINK

# ③ 紧急扩容：修改 maxmemory
redis-cli CONFIG SET maxmemory 16gb
redis-cli CONFIG REWRITE  # 写入配置文件

# ④ 如果还需要更多时间，临时清空历史数据
# （要看业务是否允许）
```

### 真实案例：缓存未设置 TTL 导致 Redis 内存打满（Flavor Dash）

**现象**：Flavor Dash 上线 2 周后 Redis 告警内存使用率 95%。

**根因**：开发同学存了用户画像数据到 Redis，没有设置 expire 时间：

```java
// 问题代码
ValueOperations<String, UserProfile> ops = redisTemplate.opsForValue();
ops.set("profile:" + userId, profile);  // 没有 set timeout
```

用户量从 1000 涨到 10000，profile 数据从 10MB 涨到 800MB，Redis 撑爆。

**解决**：
```java
// 修复代码
ops.set("profile:" + userId, profile, 24, TimeUnit.HOURS);  // 设置 24h 过期
// 对于活跃用户，每次访问时刷新 TTL
```

> 💡 **面试追问 1**：allkeys-lru 和 volatile-lru 有什么区别？如果 key 都没有 TTL，volatile-lru 会怎样？
> 
> 答：volatile-lru 只在有 TTL 的 key 中淘汰。如果所有 key 都没有 TTL，volatile-lru 退化为 noeviction——写入会 OOM。这是常见陷阱！

> 💡 **面试追问 2**：Redis 内存碎片高了怎么办？
> 
> 答：`INFO memory` 查看 `mem_fragmentation_ratio > 1.5`。解决方案：(1) 重启主从切换，重新加载数据；(2) 升级 Redis 4.0+ 用 `MEMORY PURGE` 整理碎片；(3) 调小 `jemalloc` 的 `--with-lg-page`。

> 🎯 **核心要点**：Redis 内存管理的关键三点——(1) 所有缓存都要设 TTL；(2) 业务缓存用 allkeys-lru；(3) 用 `--bigkeys` 定期扫描大 Key。最血的教训：别用 noeviction 做缓存，除非你确定数据不会超过内存。

## 5. 场景题 5：RabbitMQ 消息积压了几百万条怎么办？

> **面试官意图**：考察消息队列的深度理解 + 生产问题应急处理能力。消息积压是中大厂高频排查场景。

### 标准回答：紧急处理 + 根因分析 + 预防措施

#### 紧急处理（止血阶段）

**Step 1：确认积压情况**

```bash
# RabbitMQ 管理 CLI
rabbitmqctl list_queues name messages consumers memory

# 或通过 HTTP API
curl -s -u guest:guest http://localhost:15672/api/queues | jq '.[] | {name: .name, messages: .messages, consumers: .consumers}'
```


**Step 3：紧急扩容 Consumer**

```java
// 在 @RabbitListener 中配置并发
@RabbitListener(queues = "order.create.queue", concurrency = "5-20")
public void handleOrderCreate(OrderMessage message) {
    // 并发从 3 提升到 20
}
```

```yaml
# 或者 spring 配置

  rabbitmq:
    listener:
      simple:
        concurrency: 10
        max-concurrency: 30
        prefetch: 50  # 每次预取 50 条，提升吞吐
```

**Step 4：开启手动 ack + 批量消费**

```java
// 手动确认模式
@RabbitListener(queues = "order.create.queue", containerFactory = "batchFactory")
public void handleBatch(List<OrderMessage> messages, Channel channel, @Header(AmqpHeaders.DELIVERY_TAG) List<Long> tags) {
    try {
        // 批量处理
        orderService.batchCreateOrders(messages);
        // 批量 ack
        for (long tag : tags) {
            channel.basicAck(tag, false);
        }
    } catch (Exception e) {
        // 单条处理失败
        for (int i = 0; i < messages.size(); i++) {
            try {
                orderService.createOrder(messages.get(i));
                channel.basicAck(tags.get(i), false);
            } catch (Exception ex) {
                channel.basicNack(tags.get(i), false, true);
            }
        }
    }
}
```

**Step 5：如果还是处理不过来——跳过非关键消息**

```bash
# 方案 A：新建高性能消费者，丢弃非关键数据（如日志）
# 方案 B：清空队列（业务允许的情况下）
rabbitmqctl purge_queue order.create.queue

# 方案 C：路由到新队列，分流处理
```

#### 根因分析

| 原因 | 现象 | 排查方法 |
|------|------|---------|
| **Consumer 处理慢** | 每消息处理时间 > 100ms | `trace` Consumer 方法耗时 |
| **Consumer 挂了** | Consumer 数为 0 | `list_consumers` 确认 |
| **Producer 激增** | 发布速率远超消费速率 | 查看监控（Prometheus） |
| **RabbitMQ 故障** | Cluster 分区、节点宕机 | `rabbitmqctl cluster_status` |
| **死信队列无限重试** | 消息在死信队列循环 | 检查死信重试策略 |

#### 预防措施

```yaml
# 1. 积压告警（Prometheus + Grafana）

- alert: RabbitMQQueueDepth
  expr: rabbitmq_queue_messages_ready{queue="order.create.queue"} > 10000
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "订单队列积压 {{ $value }} 条"

# 2. 自动动态扩缩容（K8s HPA + RabbitMQ 指标）

kind: HorizontalPodAutoscaler
metadata:
  name: order-consumer-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-consumer
  metrics:
  - type: External
    external:
      metric:
        name: rabbitmq_queue_messages_ready
        selector:
          matchLabels:
            queue: order.create.queue
      target:
        type: AverageValue
        averageValue: 1000
```

### 真实案例：批量导入 + 慢 Consumer 导致积压（SuGuangMall）

**场景**：运营后台批量导入 10 万条商品，每条商品发送一条 MQ 消息，Consumer 处理每条商品需要调用外部 OCR 服务（平均 500ms），导致队列积压 10 万条。

**解决**：
1. 临时扩容 Consumer 从 5 到 30
2. 将 OCR 调用改为异步（发送到 OCR 专用队列）
3. 批量合并：将 100 条商品合并为一条 MQ 消息，batch 处理

> 💡 **面试追问 1**：消息积压后，重启 Consumer 会不会导致消息丢失？
> 
> 答：取决于 ack 模式。自动 ack（`AUTO`）会丢失未处理的消息。生产环境必须用手动 ack（`MANUAL`），重启后消息重新入队。

> 💡 **面试追问 2**：RabbitMQ 本身能存多少消息？无限积压会怎样？
> 
> 答：RabbitMQ 的消息存储在内存和磁盘，优先内存。无限积压会导致：(1) 内存打满 → RabbitMQ 本身 OOM；(2) 磁盘写满 → RabbitMQ 强制停止。应该在队列上设置 `x-max-length` 和 `x-overflow`（`drop-head` / `reject-publish`）。

> 🎯 **核心要点**：消息积压处理三阶段——止血（扩容 + 跳过非关键消息）→ 排查（Consumer 慢 / 挂了 / 激增）→ 预防（告警 + HPA + 死信兜底）。最核心的：Consumer 一定要做幂等处理，因为消息可能会被重复消费。

#### 第三步：根因排查

**原因 1：慢 SQL 撑满连接池**

```sql
-- 找出消耗时间最长的 SQL（MySQL）
SELECT * FROM sys.statement_analysis WHERE avg_latency > '1s' ORDER BY exec_count DESC;

-- 查看是否有全表扫描的 SQL
SELECT * FROM sys.schema_tables_with_full_table_scans;
```

**原因 2：连接泄露**

连接池最常见的死法——获取了连接但没归还。

```java
// 问题代码：try-without-finally
Connection conn = dataSource.getConnection();
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery(sql);
// 处理结果...
// 没有关闭连接！——连接泄露
```

```yaml
# 配置 Druid 自动回收泄露连接（救急用，但不能依赖）
spring:
  datasource:
    druid:
      remove-abandoned: true
      remove-abandoned-timeout: 60    # 60 秒未关闭视为泄露
      log-abandoned: true             # 打印泄露的堆栈
```

> ⚠️ **注意**：`removeAbandoned` 是粗暴手段，会强制中断连接上的事务，可能导致数据不一致。开发环境用来找泄露，生产环境慎用。

**原因 3：数据库连接被 DBA 或防火墙杀掉**

```bash
# 查看 MySQL 最大连接数
SHOW VARIABLES LIKE 'max_connections';

# 查看当前连接数
SHOW STATUS LIKE 'Threads_connected';

# 查看每个 IP 的连接数
SELECT SUBSTRING_INDEX(host, ':', 1) AS ip, COUNT(*) FROM information_schema.processlist GROUP BY ip;
```

**原因 4：应用线程阻塞，连接被长期占用**

```bash
# 用 Arthas 看线程堆栈，找出持有连接不放的线程
thread -b  # 先看死锁
thread | grep "WAITING\|BLOCKED"  # 看等待的线程
```

#### 根本解决方案

| 方案 | 适用场景 | 实施成本 |
|------|---------|---------|
| **慢 SQL 优化** | SQL 本身有问题 | 低（加索引、改写 SQL） |
| **读写分离** | 读多写少，查询占用连接 | 中（引入 ShardingSphere 或 MyCat） |
| **异步化改造** | 非核心写入逻辑 | 中（MQ 异步） |
| **缓存降级** | 热点数据查询 | 低（Redis 缓存） |
| **连接池参数优化** | 连接数配置不合理 | 低 |

> 💡 **面试追问 1**：连接池的 maxActive 设置多大合适？
> 
> 答：公式：`maxActive = (core_count * 2) + effective_spindle_count`。但要根据实际压测结果调整。通常中小系统 20~50，大型系统 50~200。不是越大越好！越大 → 数据库负担越重 → 查询越慢 → 恶性循环。

> 💡 **面试追问 2**：连接池满了和线程池满了有什么关系？
> 
> 答：Tomcat 线程池执行请求时从连接池获取连接。如果 Tomcat 线程池（默认 200）远大于数据库连接池（20），会导致大量线程在等待连接（WAITING），Tomcat 线程池也可能填满。需要保持协调：`Tomcat max-threads ≈ 2× Druid max-active`。

> 💡 **面试追问 3**：HikariCP 和 Druid 怎么选？
> 
> 答：Druid 监控更丰富（SQL 分析、防火墙、日志），适合国内企业。HikariCP 性能更高（字节码级别优化），Spring Boot 2.x 默认。Flavor Dash 用 Druid（需要监控），SuGuangMall 配了 Druid + 阿里云 RDS 的 SQL 审计。

> 🎯 **核心要点**：连接池满了本质是"连接的生产跟不上消费"或"连接被泄露不归还"。Druid 监控是首选排查手段，`removeAbandoned` 是紧急止血方案，慢 SQL 优化是根本。面试中要能说出"连接数不是越大越好"这个关键认知。


> 💡 **面试追问 1**：什么样的故障需要立即叫醒 Leader？
> 
> 答：(1) 影响核心业务（支付、登录、下单）；(2) 30 分钟内无法解决；(3) 涉及数据丢失；(4) 需要跨团队协调。大部分故障自己可以搞定，叫醒 Leader 是因为需要他做跨团队协调决策。

> 💡 **面试追问 2**：如果根因一时查不到怎么办？
> 
> 答：先止血而不是死磕根因。止血手段：回滚、重启、切流。系统恢复后，再在低峰期排查根因。"会止血"比"会查根因"更重要。

> 🎯 **核心要点**：应急响应最重要的是"止血优先于查因"。不是所有人都能 30 分钟找到根因，但所有人都应该 10 分钟内止血。复盘的 5 Whys 分析法是区分"好复盘"和"差复盘"的关键——问到第五层才是真根因。

## 8. 场景题 8：发布新版本后系统变慢了，怎么回滚？怎么避免？

> **面试官意图**：考察发布流程理解 + 灰度发布经验 + 变更风险管理意识。

### 标准回答：回滚策略与灰度发布

#### 发布前的准备：灰度发布 / 金丝雀发布

```yaml
# Kubernetes 金丝雀发布配置
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service-canary
spec:
  replicas: 1  # 金丝雀 1 个实例
  selector:
    matchLabels:
      app: order-service
      version: v2.1.0
  template:
    metadata:
      labels:
        app: order-service
        version: v2.1.0
    spec:
      containers:
      - name: order-service
        image: order-service:2.1.0
        readinessProbe:  # 就绪探针
          httpGet:
            path: /actuator/health
            port: 8080
          initialDelaySeconds: 10
          periodSeconds: 5
```

```yaml
# Nginx / Gateway 灰度流量控制
# 方式一：权重路由（Nginx）
upstream order-service {
    server 10.0.1.1:8080 weight=90;   # 老版本 90%
    server 10.0.1.2:8080 weight=10;   # 新版本 10%
}

# 方式二：header 路由（Spring Cloud Gateway）
spring:
  cloud:
    gateway:
      routes:
      - id: order-service-canary
        uri: lb://order-service-canary
        predicates:
        - Header=version, v2.1.0  # 只有带 version: v2.1.0 header 的请求走新版本
```

#### 发布后变慢的排查

```bash
# 对比发布前后的监控数据
# QPS 对比
grafana: 发布前 2000 QPS → 发布后 1200 QPS

# RT 对比
grafana: 发布前 P99 100ms → 发布后 P99 500ms

# 错误率对比
grafana: 发布前 0.1% → 发布后 2.5%
```

使用 Arthas 热比对：

```bash
# 对比两个版本的类加载情况
# 新版本是否引入了新的耗时代码？
trace com.example.service.OrderService createOrder -n 10
```

#### 三种回滚策略

| 策略 | 操作 | 耗时 | 风险 | 适用场景 |
|------|------|:---:|:----:|---------|
| **代码回滚** | Git revert + 重新部署 | 10~30min | 低 | 纯代码变更问题 |
| **配置回滚** | 恢复上一版配置 + 重启 | 5~10min | 低 | 配置变更导致的异常 |
| **数据回滚** | 数据库回档 / 补偿脚本 | 30min~2h | 高 | 数据迁移导致的问题 |

```bash
# 代码回滚流程

# 1. 立即停止灰度流量
kubectl delete -f order-service-canary.yaml

# 2. 回滚 Deployment
kubectl rollout undo deployment/order-service -n production

# 3. 验证回滚成功
kubectl rollout status deployment/order-service -n production

# 4. 观察监控指标恢复
kubectl get pods -n production -l app=order-service
```

#### 预防措施：上线检查清单

```markdown
# Pre-Release Checklist

## 代码层面
[ ] Code Review 已完成
[ ] 所有单元测试通过
[ ] 没有硬编码的配置
[ ] 新依赖已经安全审查

## 数据层面
[ ] 数据库脚本已 review（特别注意索引）
[ ] 数据库迁移有回滚脚本
[ ] 新表/字段兼容老版本代码

## 配置层面
[ ] 配置已提交到配置中心（Nacos）
[ ] 不需要修改配置就部署（配置隔离）

## 监控层面
[ ] 核心接口已有监控 + 告警
[ ] 发布前后的 QPS/RT/错误率可对比
[ ] 新加的功能有单独的监控指标

## 回滚层面
[ ] 回滚方案已确认
[ ] 回滚脚本已准备
[ ] 数据回滚有能力执行
```

### 真实案例：Flavor Dash 某次上线引发的问题

**问题**：上线新版本后，短信发送接口从 200ms 变到 3s。

**回滚过程**：
1. 金丝雀 10% 流量先发现问题（监控告警 RT 超阈值）
2. 立即 reject 灰度流量，流量切回老版本
3. 排查发现：新版本引入了 `HttpClient` 连接池配置错误（`maxConnPerRoute=5` 太小，导致请求排队）
4. 修复配置后，重新灰度发布验证

**关键经验**：如果没有金丝雀，这次就是 P0 事故——全量发布后才发现问题。

> 💡 **面试追问 1**：回滚后，新版本代码怎么处理？
> 
> 答：不能直接丢弃。需要：(1) 复盘找到根因；(2) 修复后再灰度；(3) 累计多次验证无问题 → 全量发布。千万别修了一个 bug 后，不经验证就再次全量发布。

> 💡 **面试追问 2**：数据库回滚怎么保证数据不丢？
> 
> 答：(1) 数据库变更必须 forward + backward 兼容，保证老代码也能读写；(2) 用 flyway/liquibase 管理迁移版本；(3) 数据迁移脚本必须是可逆的（有 `rollback` SQL）；(4) 重要的数据变更要双写 + 对账。

> 🎯 **核心要点**：灰度发布不是可选项，而是工程规范。"回滚比上线快"才是好的发布流程——100% 的发布都应该有回滚方案。在面试中，提到金丝雀发布 + 灰度流量控制 + 监控对比，就证明了你有正规的生产发布经验。

## 9. 应急响应通用 SOP

### 故障分级标准

| 级别 | 定义 | SLO | 响应要求 |
|:----:|------|:---:|---------|
| **P0** | 核心功能完全不可用（支付/登录/下单失败） | MTTR < 30min | 立即响应，全员处理 |
| **P1** | 主要功能受损（接口变慢/部分用户异常） | MTTR < 2h | 15min 响应，专人处理 |
| **P2** | 非核心功能异常（报表延迟/推荐不准） | MTTR < 24h | 工单跟踪 |
| **P3** | 轻微异常（UI 问题/文案错误） | 下个迭代修复 | 记录 bug |

### 告警规则示例（Prometheus + Alertmanager）

```yaml
# prometheus-alert-rules.yaml
groups:
- name: java-service-alerts
  rules:
  # 1. 服务存活告警
  - alert: ServiceDown
    expr: up{job="order-service"} == 0
    for: 1m
    labels:
      severity: critical
    annotations:
      summary: "{{ $labels.job }} 服务不可用"
      description: "{{ $labels.instance }} 已停止响应持续 1 分钟"

  # 2. 接口响应时间告警
  - alert: HighLatency
    expr: histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) > 1
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "P99 响应时间超过 1s"
      description: "当前 P99 {{ $value }}s"

  # 3. 错误率告警
  - alert: HighErrorRate
    expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.01
    for: 3m
    labels:
      severity: critical
    annotations:
      summary: "错误率超过 1%"
      description: "当前错误率 {{ $value | humanizePercentage }}"

  # 4. JVM 内存告警
  - alert: HeapMemoryHigh
    expr: jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"} > 0.85
    for: 10m
    labels:
      severity: warning
    annotations:
      summary: "JVM 堆内存使用超过 85%"
      description: "当前使用率 {{ $value | humanizePercentage }}"

  # 5. GC 频率告警
  - alert: FrequentGC
    expr: rate(jvm_gc_pause_seconds_count{action="end of major GC"}[5m]) > 0.1
    for: 5m
    labels:
      severity: critical
    annotations:
      summary: "Full GC 频率过高"
      description: "每分钟 Full GC {{ $value }} 次"
```
