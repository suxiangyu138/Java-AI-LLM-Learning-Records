# 06 架构决策的坑：过度与空洞

> 架构问题的两面坑：一面是**过度设计**（面试官问"为什么需要微服务"，答不出业务理由），一面是**空洞设计**（被问"为什么这么选型"，只有"大家都用"）。决策能力是 2026 年深挖面的核心考点。

## 1. 坑一：过度设计，为炫技而复杂

**症状**：一个 3 个接口的校园项目用了 Spring Cloud 全家桶（Nacos + Gateway + Sentinel + Seata）+ K8s 部署，被问"你的业务规模需要微服务吗"，答"想练一下微服务"。过度设计的项目在深挖面全面失守：每个组件都是"为了用而用"，问动机、取舍、演进全答不出——因为决策的出发点就是错的。

**根因**：把"技术复杂度"当"项目含金量"，忽略了架构第一性原则——**架构是业务的函数**：单体、微服务、事件驱动各有适用边界，业务复杂度不够时每个组件都是负资产（运维、学习、追问成本）。

**防复发**：给每个架构决策准备**规模论证**：当前业务量级是多少、为什么引入这个组件、业务量减半还需要吗。合格项目的架构轨迹是"演进式"的：单体先跑通 → 业务复杂度触发拆分 → 性能瓶颈触发缓存/异步——每个组件都能指认一个真实痛点。面试主动讲"我先用了单体，后来状态流转变复杂才拆出订单服务"——演进叙事比"一开始就微服务"可信十倍。仓库「项目场景题」07 篇有演进架构案例。

## 2. 坑二：选型无理由，"大家都用"

**症状**："为什么用 RabbitMQ？""因为大家都用它。"选型无理由的直接后果：面试官判断你**不具备技术决策能力**——只会跟随，不会选择。2026 年面试官要筛选"能做出技术决策的人"，选型理由是最直接的证据。

**根因**：选型时没做对比分析，或做了没留下痕迹。"大家都用"不是理由，是**回避思考**——把决策责任外包给了社区。

**防复发**：每个选型补上**决策三问**：**背景**——要解决什么问题（"订单超时未支付要自动关单"）；**候选**——有哪些方案（定时任务扫描 / 延迟队列 / 死信队列）；**选择**——为什么选它、放弃的理由（"定时扫描有分钟级延迟和 DB 压力；死信队列延迟精确，缺点是依赖 MQ"）。三问写进 ADR（见第 6 节）。面试回答的标准结构：**"我需要解决 X；对比了 A（优点…缺点…）和 B（优点…缺点…）；选 X 是因为在当前量级与延迟要求下它最优"**。选型没有唯一正解，面试官要的是"思考过程完整"，不是"你选对了"。

## 3. 坑三：说不出"为什么不用 X"

**症状**："为什么用 Redis 不用 Caffeine？"答不上。**"为什么不用 X"比"为什么用 X"更狠**：它专测知识边界。知道"用什么"可以靠教程，知道"为什么不用别的"必须靠真实对比——没对比过的选型必然露馅。

**根因**：学习时只看"正脸"不看"侧脸"——知道优点，没收集适用边界与缺陷。技术选型知识应该是"对比网格"而不是"优点清单"。

**防复发**：给核心组件建**替代方案卡**，每个组件准备"3 个为什么不用"：为什么不用 Caffeine（多实例缓存不一致）、为什么不用 Kafka（延迟高、运维重）、为什么不用自研锁（分布式场景不靠谱）。仓库中间件体系（Redis vs Memcached、RabbitMQ vs Kafka）有现成对比模块，按目录收集。练习方法：**主动问"我用的每个方案，替代品是谁？三个不选的理由？"**——能答出三条，选型就立住了。

## 4. 坑四：决策无记录，面试临时编

**症状**：被问"为什么表结构这么设计"，当场思考、现场编理由——编得磕绊，面试官一眼看穿。**决策是当时做的，理由却不记得了**：写代码时的权衡（为什么冗余字段、为什么这种索引）被时间冲走，只能即兴发挥。

**根因**：决策没有文档化。代码提交了，决策过程（比较了什么、放弃了什么）没有沉淀成"隐性知识"——而它的保质期只有几周。

**防复发**：**决策文档化**是面试的护城河：每次"在两个方案间纠结并做出选择"的时刻，花 5 分钟写一条决策记录（背景、候选、选择、理由、日期）。攒 10-20 条就是你的"决策档案"。面试前复习，被问任何"为什么"都能答出当时权衡——**真实的理由比编的更可信，因为它带细节**（"当时为了兼容旧数据格式所以保留了冗余字段"）。ADR 模板见「面试考察点」06 篇。

## 5. 坑五：架构照搬教程，与业务脱节

**症状**：架构图与某教程项目一模一样（缓存 + MQ + 分库分表全套），但问"你的数据量真的需要分库分表吗""你的业务和秒杀有什么区别"——答不出。照搬的本质问题：**架构与业务脱节**——项目没有产生这个架构的动机，架构成了贴上去的标签。

**根因**：先选架构后编业务，或业务太薄撑不起架构。教程架构是为教程的业务设计的，你的业务量级对不上，架构就成了"空中楼阁"。

**防复发**：架构与业务对齐检查：**每个组件都能指认一个业务痛点**——缓存指认"热点读多"、MQ 指认"峰值削峰"、分库指认"单表数据量大"。指认不出的，要么删掉，要么把业务做厚（加真实场景）。想展示微服务能力，先造出"确实需要拆分"的业务复杂度（独立部署、独立伸缩的场景），而不是硬拆。判断标准：**把架构图讲给不懂这个教程的人听，他能理解"为什么是这种结构"**——能理解，架构就是你的；听不懂，架构就是借的。

## 6. 决策三问与 ADR 写作

把决策能力变成可交付的资产，方法是**ADR（架构决策记录）**，每条四段、一页以内：**背景**（要解决什么问题、有什么约束，如"订单量增长，单表查询变慢"）；**候选方案**（两到三个：分库分表 / 读写分离 / 缓存 + 归档）；**决策与理由**（选了什么、为什么——"选读写分离：成本低、解决 80% 读压力；分库分表等数据量真上来再做"）；**后果与后续**（代价是什么、何时重估——"引入主从延迟，读链路接受秒级延迟；数据量翻倍时重估"）。每条 15 分钟，项目做 10-20 条。面试被问"为什么这样设计"，答案直接从 ADR 读："当时有三个方案——…，我选了…因为…，代价是…，计划在…时重估。"**含金量不在于选对，而在于留下了决策的完整轨迹**——这是"设计过系统"与"抄过系统"的最终分野。

## 7. 核心要点

1. 每个组件必须能指认一个业务痛点，指认不出的删掉或做厚业务。
2. 选型决策三问：背景、候选、选择理由；"大家都用"不是理由。
3. 备替代方案卡：每个核心组件准备 3 个"为什么不用 X"。
4. 决策文档化：每次纠结的决策花 5 分钟写记录，攒成决策档案。
5. 架构是业务的函数：演进式架构叙事比"一开始就微服务"可信十倍。

> 🎯 **核心要点**：架构深挖考的不是"你会不会用框架"，而是"你的决策过程完不完整"。过度设计与空洞设计是两个极端，中间那条线是**决策痕迹**——有背景、有候选、有理由、有代价的每个组件，都经得起追问；反之，任何追问都会塌。
