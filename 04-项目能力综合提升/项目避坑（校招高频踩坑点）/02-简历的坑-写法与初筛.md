# 02 简历的坑：写法与初筛

## 1. 坑一：ATS 初筛被拦

**症状**：简历投了几十份零回复，问题出在投递前的初筛环节。2026 年的 ATS 系统会做三件事：解析格式、提取关键词、给岗位匹配打分。以下形态直接扣分或淘汰：左右分栏、表格、文本框、图片式 PDF、关键词与 JD 不匹配、文件名随意、联系方式写错（HR 联系不上你）。

**根因**：把简历当"设计作品"而不是"可解析数据"。机器读不了你的排版，亮点就停留在硬盘里。关键词缺失的深层原因是没有研究 JD——不知道岗位要什么，自然写不出它想看的词。

**防复发**：格式上回归朴素——**单栏结构、常用字体、优先 .docx 或文本型 PDF、一页为限**；文件名改为"姓名_学校_应聘岗位_手机号"；投递前从 JD 提取 3-5 个高频关键词（如"高并发""分布式事务""RAG"），自然嵌入技能与项目描述。投递前用 ATS 工具或请同学模拟解析，确认文字可提取。

## 2. 坑二：形容词与低阶词

**症状**：两类词会直接触发追问或降权。一类是形容词："大幅提升""显著优化""高效稳定"——面试官听到必问"具体是多少"，答不出具体数字，形容词就成了虚张声势的证据。另一类是低阶词：2026 年秋招 ATS 已配置硬规则，简历核心技能出现"功能测试""手工回归"且无自动化/工程化关键词平衡的**直接降权**——这类词在语义向量空间落在"执行层"中心，与目标岗位能力模型错配。

**根因**：把"态度"当"证据"。形容词表达的是主观评价，面试官要的是可验证的事实；低阶词的根因是经历本身只有手动执行，没有自动化与质量闭环。

**防复发**：形容词全部替换为数字（"大幅提升"→"QPS 提升 40%"、"高效"→"响应 P95 从 800ms 降到 200ms"）；低阶经历用工程化语言重构——"手工回归"改写为"编写自动化回归脚本覆盖核心链路，执行时间从 2 小时降到 15 分钟"。改写的底线是**事实不变**，只是从执行视角换成工程视角。

## 3. 坑三：只列项目名，无角色无数据

**症状**：项目经历写成"XX 管理系统（Spring Boot + Vue）"，一行了事；或三行描述全是"负责了 XX 模块的开发"。面试官（或机器）无法判断：你解决了什么问题、你的角色是什么、结果怎么样。2026 年招聘方明确：只列标题的项目经历等于没有项目经历。

**根因**：把"做了"当"写出了"。不会用 STAR 拆解经历——背景（问题）→ 任务（你的角色）→ 行动（关键决策）→ 结果（数据），只写了中间的"任务"两个字。

**防复发**：每条项目经历按四行模板重写，第一行是定位与问题，后面是角色与关键动作，每行以数字或结论开头：

```text
智能客服系统（Java + Python 双栈，已上线，日均 500 次对话）
- 独立设计 Agent 工具调用链路：业务能力封装为 10 个 Tool API，归属校验 + 幂等控制，退款经人工确认后零资损
- 优化首 token 延迟：混合检索（向量 0.7 + BM25 0.3）+ 流式转发，P95 从 2.8s 降到 1.2s
- 搭建双栈监控：OTel 全链路追踪贯通 Java/Python，故障定位从小时级降到分钟级
```

每条 bullet 都能被追问到代码与数据，这是简历的唯一合格标准。

## 4. 坑四：技能列表无证明

**症状**：技能区列 20 个名词，没有项目或经历支撑——"Redis（熟练）、Kafka（熟悉）、K8s（了解）"，项目里没有一处体现。面试官的默认判断是"从网上抄的"：随便抽一个问基础概念，答不出就失去信任——**信任失去后讲得再好也白搭**。

**根因**：把"见过"当"会了"。技能区的潜规则是：**列表里的每个词，都默认你要为它被追问负责**。列出 20 个词 = 承诺能答 20 个方向的深挖，而实际只能答 3 个。

**防复发**：技能区与项目经历强绑定——每个技能词都能指回简历上的一个项目或一段经历；做不到的删掉。一个更稳的写法：把技能融进项目描述里（"基于 Redis 实现分布式锁"比技能区单列"Redis"有力得多），技能区只保留 6-8 个核心词。

## 5. 坑五：夸大与造假

**症状**：实习时长虚报、项目"参与"写"主导"、绩效数字编造。2026 年招聘方对简历真实性的核查在加强：背调覆盖学历、经历与绩效；更重要的是**面试深挖本身就是检验场**——"你参与的项目为什么能说成主导？"两轮追问就露馅。

**根因**：把"想得到 offer"当"必须现在兑现"。夸大造假的代价不是扣分而是**一票否决**：诚信问题在技术圈是行业级污点，一次穿帮毁掉的是整个求职季甚至更长。

**防复发**：诚实表述 + 策略性强化。想强化就**把参与的部分做深**——哪怕只负责一个模块，把它做到"能讲五层"的程度，价值高于虚报十个模块。面试官看的是任何一个模块的深度，不是模块数量。

## 6. 坑六：一份简历投所有岗

**症状**：同一份简历投 Java 后端、测试、产品、运维四个方向；或投两家不同业务的 Java 岗，简历一字不改。ATS 匹配分低的直接原因就是"定位模糊"——系统无法判断你适合哪个岗位，HR 的默认判断是"你自己也不知道要做什么"。

**根因**：图省事 + 方向不清。求职方向没想清楚，用海投代替决策；每份简历都做定制又觉得成本高，于是用"通用版"降低成本，结果全线低匹配。

**防复发**：按岗位做 2-3 个版本（后端版、AI 应用版等），每个版本调整三处：技能区排序（目标岗位关键词前置）、项目描述侧重（同一项目，投后端突出架构与高并发，投 AI 突出检索与评估）、自我评价。注意一致性：**两个版本不要出现互相矛盾的内容**，面试官看多个版本时会发现。

## 7. 简历自查与改写方法

改写一份简历按四步走：**做减法**——删掉所有形容词、答不出的技能、无关经历，每删一项问"它能证明我解决过什么问题吗"；**换证据**——留下的每条经历改成"问题→动作→数字"结构；**做对齐**——对照目标 JD 把关键词自然嵌入，确认单栏、一页、文本可解析；**五层自测**——对简历每句话连问五个"为什么"，任何一层答不出就改写或删除。写完让同学当面试官过一遍，问"你最想追问哪个点"，你答得最虚的那个点就是简历的漏洞。

## 8. 核心要点

1. ATS 是 2026 第一关：单栏格式、JD 关键词嵌入、文件名规范、联系方式正确。
2. 形容词换数字、低阶词换工程化语言，事实不变只换视角。
3. 项目经历四行模板：定位 + 角色 + 关键动作 + 数据，每条可追问。
4. 技能区与项目强绑定，写 20 个词等于承诺答 20 个方向的深挖。
5. 夸大造假是一票否决；诚实表述 + 把参与的部分做深，价值更高。

> 🎯 **核心要点**：简历的坑本质是同一个：**写的不是证据，是态度**。ATS 和面试官要的东西一致——可解析、可验证、可追问。把每一行都改成"问题→动作→数字"的证据格式，简历就同时过了机器关与人关。
