# 03 技术深挖的坑：讲不深、答不上

> 2026 年面试官追着项目问，细到"某字段为什么用这个类型、某行日志怎么打的"。深度不足是校招生项目挂掉的第一主因——但深度不是天赋，是训练方法。

## 1. 深挖的五层结构与垮塌点

面试官的项目追问遵循固定递进结构，每一层都是一个"坑"：**第一层用法**（这个功能怎么实现的）→ **第二层原理**（底层为什么这么工作）→ **第三层取舍**（为什么不用别的方案）→ **第四层演进**（如果数据量/并发翻十倍怎么改）→ **第五层边界**（什么场景下这个设计会失效）。校招生的典型垮塌点分布：第一层普遍能答，第二层开始含糊，第三层"没想过"，第四层"没做过"，第五层"不知道"。

垮塌本身不是问题——**问题在于垮塌的位置**。面试官考察的不是你全会，而是你会在哪里停：止步于第二层的候选人答"我查过原理但记不清了，我可以讲下我的理解"，比硬编一个答案的候选人可信得多。但如果你只停留在第一层，说明项目深度确实不够，需要训练。

## 2. 坑一：只背用法，不问原理

**症状**：项目用了 Redis 缓存，被问"Redis 为什么快"能答"内存快"；被问"单线程为什么还快"就卡壳。用了 MQ 做异步，被问"消息丢失怎么保证"答"有重试"；被问"重试怎么保证不重复消费"没想过。这是最常见的深挖塌方：**会用 API，不懂机理**。

**根因**：学习模式停留在"复制代码能跑"阶段。写代码时只关注"怎么调"，不关注"内部发生了什么"；遇到异常只改参数，不追根因。长期如此，积累的是接口记忆而不是系统知识。

**防复发**：对项目里用到的每个核心组件做**原理三问**——它解决什么问题、内部核心机制是什么（一句话能讲清的数据结构或协议）、它的瓶颈在哪。例如：Redis 快 = 内存 + 单线程避免竞争 + IO 多路复用，瓶颈在内存容量与网络；MQ 不丢消息 = 生产者确认 + broker 刷盘 + 消费者手动 ack，瓶颈在消费吞吐。仓库的中间件体系（Redis、MQ、MySQL）每个都有"原理"模块，按这个目录逐组件过一遍即可。每个组件 30 分钟，项目核心组件不超过 5 个，一个周末可完成。

## 3. 坑二：无方案对比，答不出取舍

**症状**：被问"为什么用 Redisson 分布式锁而不用 setnx 自己写"，答"大家都这么用"；被问"为什么选 RabbitMQ 不选 Kafka"，答"RabbitMQ 更简单"。2026 年面试官明确说，他们要筛选的是"能做出技术决策的人"——**方案对比是深挖面最核心的考察点**，没有对比的选型理由等于没有理由。

**根因**：选型时没有做对比，或做了对比但没记录。用"大家都用""教程推荐"代替了思考。深度不够的直接后果：面试官无法判断你是"会用"还是"会选"——而后者才是工程师的核心价值。

**防复发**：给项目里的每个技术选型补一份**决策小记**（一句话背景 + 两三个候选方案 + 对比维度 + 选择理由 + 放弃理由），写成 ADR 文档放进项目仓库。被问"为什么选 X"时的标准答案结构：**"我对比过 A 和 B——A 的优势是…但它的问题是…；B 的优势是…；我最终选 X 是因为在这个场景下…"**。这个结构本身就是"决策者"的信号。仓库「面试考察点」06 篇有完整的 ADR 写法与案例。

## 4. 坑三：没想过边界与异常

**症状**：项目链路讲得行云流水，被问"缓存击穿了怎么办""MQ 挂了怎么办""重复请求怎么防"——回答"没想过"或"不会发生"。边界与异常是深挖面的**分水岭题**：正常链路背得再熟只能证明你会用，异常链路答得出才证明你设计过。

**根因**：开发时只验证了 happy path（正常路径），没有做故障推演。项目评审、代码走读、压测都围绕"功能对不对"，没人问"挂了会怎样"。思维习惯层面，缺少"如果 X 失败"的提问模板。

**防复发**：给项目核心链路做**故障推演表**——列出链路上的每个依赖（缓存、DB、MQ、第三方 API），逐个问"它挂了会怎样、重试会怎样、重试失败会怎样"，每个问题给出答案或降级方案，写进项目文档。面试答边界问题的标准范式：**"正常情况是 A；异常情况是 B，我做了 C 兜底；如果 C 也失败，会走 D（人工/降级）"**。能讲出这条链，就是"设计过系统"的证据。仓库「项目场景题」06 篇（线上故障排查）提供了现成的故障推演框架。

## 5. 坑四：源码级细节空白

**症状**：面试官问"你的 Tool API 里幂等是怎么做的"，答"用唯一键判断"，被追问"唯一键冲突报错后你怎么处理""并发重复请求同时到了怎么办"——答不上。字节一面"挑一个你写得最爽的代码片段讲讲设计"、阿里二面"扔一个线上 bug 让你十分钟定位"，都在考**源码级细节**：你写过的代码的每一行决策。

**根因**：写完代码不回顾。项目做完就扔，三个月后面试时对自己的代码陌生程度和面试官差不多。细节记忆被时间冲淡，又没有文档兜底。

**防复发**：面试前一周做**代码走读**：把项目核心文件逐个过一遍，为每个关键方法准备"为什么这么写"的回答（复杂度、边界处理、踩过的坑）；挑选 1-2 个"写得最爽"的代码片段，准备 3 分钟讲解（设计动机 → 关键实现 → 踩坑与改进）。走读时重点检查：if 分支为什么这么分、异常为什么这么抛、常量为什么是这个值——面试官的追问点全在这里。

## 6. 深挖训练法：五层追问自测

深度不是突击出来的，是**训练出来的**，方法就是五层追问自测：对项目里每个核心设计（缓存策略、锁、事务、消息、表结构），自己按五层连续追问——怎么实现的 → 底层原理 → 为什么不用别的 → 数据量翻十倍怎么办 → 什么情况会失效。每一层必须给出**有信息增量的回答**（不是复述问题），答不出的标记为"待补"，当天查资料补上并写成笔记。

训练频率：每天 2 个设计点，两周覆盖项目全部核心设计。判断训练是否到位的标准：**找同学当面试官，随机抽你的项目设计点连续追问五层，你能在 6 层追问内始终给出新信息**。做到这一步，深挖面不再是失分点而是得分点——因为大部分候选人在第三层就停了，你走到第五层，差距就出来了。

## 7. 核心要点

1. 五层结构：用法 → 原理 → 取舍 → 演进 → 边界，提前知道每层的坑在哪。
2. 每个核心组件做原理三问：解决什么、内部机制、瓶颈在哪。
3. 每个选型写决策小记：候选方案 + 对比 + 选择理由 + 放弃理由。
4. 故障推演表：核心链路的每个依赖逐个推演"挂了会怎样"。
5. 五层追问自测是训练方法：每天 2 个设计点，两周覆盖，同学随机抽验。

> 🎯 **核心要点**：深度不足不是智力问题，是**训练覆盖问题**——面试官的五层追问是可以预演的，每一层的垮塌点都是固定的。把项目核心设计按五层全部过一遍，深挖面从"怕被问"变成"等他问"。
