# 08 故障复盘的坑：没故事与假故事

> "项目上线后遇到过什么真实问题？怎么解决的？"是 2026 年三个必问题之一。这一题的两类失败：**没故障可讲**（项目太顺 = 没深入）和**假故障**（编的故事经不起追问）。

## 1. 坑一：没故障可讲，"都很顺利"

**症状**：被问"遇到过什么问题"，回答"项目比较顺利"或"都是小问题，记不清了"。**"没故障"在面试官耳里等于"没深入"**——真实开发不可能没有故障：环境、数据、并发、性能、第三方，任何真做过的项目都会踩。"都很顺利"只有两种可能：项目是抄的，或出了问题没追根因。

**根因**：开发时没有"问题记录"习惯——故障发生、解决、翻篇，没有沉淀；另一个根因是项目复杂度太低——CRUD 项目没什么故障可讲，又回到 01 篇的"伪项目"问题。**故障素材是项目真实度的直接产物**。

**防复发**：开发期建**问题日志**：每次卡壳超 30 分钟的问题记一行"现象 + 解决过程 + 根因"，项目结束至少 10-20 条，从中选 2-3 条整理成完整故障故事。如果问题日志凑不满 5 条，说明项目复杂度不够，先回头补项目——**故障故事不是讲出来的，是做出来的**。

## 2. 坑二：编故障，细节一问就穿

**症状**：没有真实故障，但觉得必须有"难点"，于是编一个："上线后遇到缓存穿透，用布隆过滤器解决了。"被追问"穿透率多少？误判率怎么调？压测验证过吗？"——答不出。故障故事的细节是无限追问点：现象、时间线、工具、日志、修复代码、验证方式，任何一环编不出来就穿帮，穿帮后整个项目可信度被连坐否定。

**根因**：把"必须有故障"误解为"必须编一个高级故障"。忽略了**"小故障讲得深"比"大故障编得假"更有价值**——真实的"Nginx 配置错误导致 502"比编造的"分布式事务故障"可信十倍。

**防复发**：铁律——**只讲真实发生过的故障**。筛选标准：亲身排障的、能回忆出定位过程的（用了什么工具、看了什么日志）、记得住细节的。没有大故障就用小故障——**故障的价值在复盘深度，不在故障大小**。

## 3. 坑三：甩锅式复盘，归因外部

**症状**："是网络问题""第三方 API 不稳定""测试环境配置不对"。被追问"那你做了什么"——"我等着它恢复"。甩锅式复盘的致命处：**面试官听不到你的主动性**——2026 年要筛选的是"能动手解决未知问题的人"，甩锅等于宣告"遇到问题只会等"。

**根因**：外部归因省事（不用反思自己），却暴露工程态度缺陷：不追根因、不主动、不担责。真实故障往往有内因（没做校验、没设超时、没写幂等），归因外部是回避自己可改进的部分。

**防复发**：复盘强制**内因优先**：即使主因是外部（第三方超时），也要讲自己做了什么——"第三方超时（外部触发），但我发现我的代码没设超时、没做降级（内因），所以补了超时与熔断，并写进排查清单"。**内因 + 改进的结构把甩锅场景变成成长场景**："这暴露了我的设计缺陷，我改进了 XX"——面试官听到的不是"你错了"，而是"你能从错误里长出能力"。归因原则：外因可以提（显示客观），改进必须归内（显示担当）。

## 4. 坑四：只讲现象，不讲定位过程

**症状**："遇到 Redis 缓存不一致，我删了缓存就好了。"被问"怎么定位到是缓存问题的"——答"网上搜的"。只讲现象不讲定位过程的故障故事是**空壳**：面试官要验证的是"你会不会解决未知问题"——定位过程（现象 → 假设 → 验证 → 根因）才是问题解决能力的证据，跳过它就等于跳过考察点。

**根因**：记录故障时只记了结果，没记过程。排障过程转瞬即逝，不记录就蒸发——面试时只剩一个"删缓存就好了"的空壳。

**防复发**：每个故障故事必须能讲出**定位链**：**现象**（什么信号触发：报错、监控、用户反馈）→ **假设**（怀疑什么，为什么）→ **验证**（什么手段：日志、抓包、复现）→ **根因** → **修复与验证**（改了什么、怎么确认修好）。示例："线上订单查询变慢（现象），监控发现 Redis 命中率骤降，怀疑缓存失效逻辑，查日志发现更新订单时删缓存异常被吞，根因是 catch 只打印没上报，改成先删缓存后更新 + 异常上报（修复），命中率恢复（验证）"。**一条完整的定位链，比十个修复方案值钱**。

## 5. 坑五：有教训无改进，故事断尾

**症状**："遇到缓存穿透，用布隆过滤器解决了。"——故事到此为止。被问"之后怎么防复发"，回答"没有，就是解决了"。断尾的故障故事浪费了最值钱的部分：**面试官对故障故事的考察终点是成长性**——你从这次故障里沉淀了什么（防复发机制、排查清单、监控告警、设计规范）。

**根因**：把"修复"当"复盘"终点。修复是止血，复盘是重建——高手在故障后做三件事：修当前问题、防同类问题（加监控、加校验、加规范）、防关联问题（排查其他代码有没有同款坑）。第三件事校招生极少做到，做到了就是显著区分点。

**防复发**：故障故事标准结尾是**改进三连**："这次之后我做了三件事：一是加了 XX 监控告警（同类问题提前暴露）；二是把 XX 写进排查清单/代码规范（防止再犯）；三是排查了项目里其他 XX 场景有没有同款问题（扩展防御）"。**改进三连把故障故事从"事故记录"升级为"能力证明"**。

## 6. 故障叙事五要素

一个合格的故障故事按五要素组织，2-3 分钟：**背景**（什么系统、什么场景）→ **现象**（什么信号触发，带错误信息或监控数据）→ **定位**（假设与验证的完整链路，核心，占一半时间）→ **修复**（改了什么、怎么确认）→ **复盘**（根因归内、改进三连）。五要素对应五类必问题：背景对应"当时环境是什么"，现象对应"你怎么发现的"，定位对应"你怎么排除其他可能的"，修复对应"你验证过吗"，复盘对应"之后怎么防复发"。**五要素齐备的故障故事，面试官问无可问**。素材靠日常收集：开发期问题日志 + 排障时边排边记（当时的细节事后永远回忆不起来）+ 每季度把 2-3 条最深的整理成故事练到 2 分钟讲完。

## 7. 核心要点

1. "没故障"等于"没深入"：开发期建问题日志，项目结束至少 10-20 条素材。
2. 只讲真实故障：小故障 + 完整定位过程，比编造的大故障可信十倍。
3. 复盘归因内因优先：外因可以提，改进必须归内。
4. 定位链是核心：现象 → 假设 → 验证 → 根因 → 修复验证，占故事一半篇幅。
5. 改进三连结尾：监控告警 + 排查清单 + 同类排查，让故事升级为能力证明。

> 🎯 **核心要点**：故障题考察的不是"你有没有遇过故障"，而是**"遇到未知问题时的处理能力"**。真实 + 定位链 + 内因复盘 + 改进沉淀，四者齐备是深挖面的王牌；缺任何一环，这张牌就会反噬。
