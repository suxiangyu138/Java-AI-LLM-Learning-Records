## 3. 学习路线推荐

**标准路径（4-6 周，选做 4-6 篇）**：01-02 必做（AI 深度是 Python LLM 方向的差异化核心）；04 必做（高并发是后端通用能力）；从 03/05/06/07/08/09 中按兴趣选 1-2 篇（简历需要哪个方向补哪篇）。

**校招冲刺路径（2 周，3 篇）**：01 多 Agent + 02 Agentic RAG + 10 面试冲刺——这三篇把简历从"做了个 RAG 项目"升级为"做过 Agent 系统"，面试深挖点最密集。

**在职进阶路径（8 周，全做）**：按 01→09 顺序全做，每篇 4-5 天——目标不是简历而是真实工程能力，与仓库「主流 Agent 范式」「Milvus」「CI CD灰度发布」等体系对照推进。

**投入原则**：本层是"加分项"不是"必须项"——**Level2 未毕业前不要碰 Level3**（地基不牢的加分项在面试深挖下是减分项）；时间紧张时优先 01、02、10，其余留待工作后补。

**三个"先想清楚再动手"的检查**（每篇开工前 5 分钟自问）：**这个加分项装进简历后，面试官深挖的第一问是什么，我答得上来吗**（答不上先回 Level2 对应篇补课）；**项目当前形态真的需要它吗**（"为了简历"和"为了项目"都是正当理由，但要诚实——把理由写进决策记录）；**投入产出比是否合理**（投入 5-7 天换一个差异化点，值不值——本层是"边际投入"，时间管理的优先级低于 Level2 的核心项目）。三个检查过完再开工，本层的每一周都花在刀刃上。

## 4. 核心概念速查

| 概念 | 一句话速查 |
|---|---|
| 多 Agent | 多个专业 Agent 协作完成任务，Supervisor 集中路由 / Swarm 对等交接 |
| Agentic RAG | RAG 流程由 Agent 驱动：检索不足自动改写、多跳分解、失败自愈 |
| prompt caching | 相同前缀的请求复用缓存，输入成本降 50-90% |
| 量化 | 模型权重压缩（INT8/4bit），显存与延迟双降 |
| locust | Python 压测工具，脚本即压测场景 |
| Milvus 3.0 | 湖原生向量库（2026-07-29 发布），生产级检索基础设施 |
| OTel | 可观测性开放标准，日志/追踪/指标三支柱统一 |
| K8s | 容器编排平台，部署、伸缩、自愈的云原生标准 |

## 5. Level3 在能力建设中的定位

三级结构的逻辑是**递进收口**：Level1 打通链路、Level2 做成工程、Level3 做出差异化。**Level3 回答面试官最后那个问题："你的项目和其他候选人的有什么区别？"**——多 Agent 编排、Agentic RAG、推理成本优化，这些是 2026 年 AI 岗位面试里最高频的深挖方向，也是多数候选人简历上"做过的项目"里没有的内容。**加分项的本质是"别人不会的你会"**——每个模块都要问自己：这个能力装进简历后，面试官深挖时我能不能讲出"为什么、怎么做、效果多少"。

与仓库其他体系的关系：本层是它们的**项目化落地**——「主流 Agent 范式」讲模式理论（01 篇是工程实现）；「RAG 拓展优化深化」讲检索进化全景（02 篇是 Agentic 落地）；「Milvus」体系讲向量库原理（06 篇是迁移实践）；「Docker」「CI CD灰度发布」讲容器与发布（09 篇是 K8s 落地）；「日志监控指标」体系讲三支柱（07 篇是全家桶实践）。**深挖时从本层项目出发，往这些体系里找原理**——这与 Level2 的用法一致。

与「Java‑AI 后端项目能力建设」Level3 的对称关系：Java 侧加分项是微服务全家桶（Nacos/Feign/Sentinel/Seata/K8s），Python 侧是 AI 深度（多 Agent/Agentic RAG/推理优化）+ 工程演进（Redis/数据升级/可观测/K8s）。**两套 Level3 的战略分工**：Python 侧重"AI 智能化深度"，Java 侧重"大规模工程化"——校招简历里两者各占一个差异化方向，双栈完成 = "AI 场景实现能力 + 后端工程能力"的双引擎。

## 6. 加分项全景与投入节奏

| 加分项 | 简历表述 | 建议投入 |
|---|---|---|
| 多 Agent 编排 | 设计 Supervisor 多 Agent 架构，路由准确率 ~94% | 5-7 天 |
| Agentic RAG | 检索失败自动改写重试，评估提升 XX% | 4-5 天 |
| 推理成本优化 | prompt caching + 小模型路由，成本降 60% | 3-4 天 |
| 高并发压测 | locust 压测定位瓶颈，P95 优化 XX% | 3-4 天 |
| Redis/数据升级 | Redis 缓存 + Milvus 向量库，10 万级向量检索 | 4-5 天 |
| 可观测全家桶 | Prometheus/Grafana/OTel，SLO 达标 | 3-4 天 |
| 多租户 | 租户隔离 + 权限体系，SaaS 化形态 | 4-5 天 |
| K8s 云原生 | Helm 部署 + 灰度发布，GitOps 流程 | 5-7 天 |

节奏建议：**一次只做一个加分项**（多 Agent 做一半换 Redis，两个都做不成）；每个加分项做完后**更新一次简历与答辩稿**（"做完即沉淀"——积累到 10 篇再整理，会忘掉一半细节）。**投入时间分配**（4-6 周预算参考）：01 多 Agent 与 02 Agentic RAG 各 5 天（AI 深度核心），04 高并发 4 天（通用能力），选做项各 3-4 天——预算外的"再加一个吧"一律下个月再说，本层最贵的成本是"每样做一半"。

## 7. 使用建议

每个模块的结构一致：**目标 → 设计 → 实现 → 验证 → 常见坑**。本层与前两层的最大区别：**每个模块都强调"量化结果"**——压测报告、评估提升、成本下降、延迟优化，没有数字的加分项在简历上是空话。建议沿用 Level2 的"工程日志"习惯，每个加分项的实验数据（前后对比）当天记入 docs/。**时间管理提醒**：本层每篇都可能"深不见底"（多 Agent 可以永远优化下去），**按模块开头"目标与验收"的边界收手**——验收过了就进入下一篇，追求完美是加分项的天敌。

> 🎯 **核心要点**：Level3 的唯一目标是**让项目在"人人都做过 RAG"的候选人群里脱颖而出**——多 Agent、Agentic RAG、成本优化、高并发、云原生，每掌握一项就多一个差异化深挖点。加分项的意义不在"会"，在于"会且能讲、能讲且有效果数字"——本层每一篇的"验证"小节都要求记录真实数据，这是加分项与"看过教程"之间最实在的分界线。
