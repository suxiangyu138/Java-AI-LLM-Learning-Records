## 1. 目标与验收

本模块的产出：locust 压测脚本 + 压测报告（基线/优化后两轮，QPS、P95/P99、错误率对比）。验收标准：**能说出系统的当前容量（X QPS 时 P95 多少）**；**能定位至少一个真实瓶颈并优化（附前后数据）**；**能讲清异步模型下"为什么异步了还慢"的常见原因**。与 Java 侧 Level3 的分工：那边用 JVM 工具（JFR/Arthas）与虚拟线程，本模块用 Python 侧对应物（async profiling、uvloop、多 worker）——方法论同源，工具链不同。

## 2. 压测方法论：先基线后优化

性能优化的第一法则：**先有基线，再谈优化**——没有基线的优化是感觉，有基线的优化是工程。压测方法论五步：**定目标**（可接受延迟：P95 < 3s、错误率 < 1%——从 Level2 10 的延迟预算表继承）；**建脚本**（locust 模拟真实请求模式——不是纯打 /health，要混合对话、检索、上传的比例）；**跑基线**（固定并发梯度 10/50/100/200，记录每档的 QPS 与 P95——找到"拐点"：QPS 不再随并发上升的点，就是容量上限）；**定位瓶颈**（第 4 节）；**优化并复测**（一次只改一个变量，复测同一组并发梯度——与 Level2 06 的调优纪律同源）。**压测的环境纪律**：压测不要打生产环境（打坏真实数据），用测试环境或本地；压测要固定模型调用（LLM 外部依赖的延迟抖动会污染数据——压测分两档：mock 模型的"系统压测"与真实调用的"端到端压测"）；**压测报告的结构**（本模块交付物模板）：环境说明（机器规格、worker 数、mock/真实模型）、并发梯度表（每档 QPS/P95/P99/错误率）、瓶颈定位记录（解剖数据）、优化清单与效果（前后对比）、结论（当前容量上限与扩展建议——04 篇的数据直接喂给 09 篇的 HPA 配置）。

## 3. locust 压测脚本

locust（2026 年 Python 生态首选压测工具）：脚本即压测场景，`uv add --dev locust` 后写任务文件：

```python
# locustfile.py —— 模拟混合请求
from locust import HttpUser, task, between

class ChatUser(HttpUser):
    wait_time = between(0.5, 2)          # 模拟真实思考间隔
    session_id = "load-test-session"

    @task(7)                             # 70% 对话请求（主要负载）
    def chat(self):
        self.client.post("/api/chat", json={
            "session_id": self.session_id, "question": "什么是 RAG？"})

    @task(2)                             # 20% 流式请求
    def chat_stream(self):
        with self.client.stream("POST", "/api/chat/stream", json={
                "session_id": self.session_id, "question": "讲一下混合检索"}) as resp:
            list(resp.iter_lines())      # 消费完整流，模拟真实前端

    @task(1)                             # 10% 健康检查
    def health(self):
        self.client.get("/health")
```

运行与产出：`locust --host http://localhost:8000 --headless -u 100 -r 10 -t 3m`（100 并发、每秒 10 个启动、跑 3 分钟），Web 界面或 CSV 报告（`--csv=report`）。**压测脚本的三个规范**：**请求混合比例贴近真实**（纯对话接口压测会高估容量——流式与上传都要占比例）；**session_id 固定或少量**（每个用户独立会话——模拟真实隔离，也验证多会话并发正确性）；**断言加进任务**（`resp.status_code == 200`，压测同时是并发正确性测试——返回 500 的压测报告是废纸）。

## 4. 瓶颈定位：四类瓶颈与判定

压测数据出来后的定位方法——按"四类瓶颈"逐个排除：**IO 瓶颈**（最常见）——等待外部（LLM API、数据库、磁盘）：指标是"CPU 占用低但 P95 高"；判定：压测时看 CPU 利用率 <50% 且延迟高 → IO 等待（async 下看 await 密集点）；**CPU 瓶颈**——同步计算（分块、重排、JSON 序列化）占满核心：指标是 CPU 100% 而 QPS 不再涨；**连接池瓶颈**——SQLite/Chroma/LLM client 连接数见顶：指标是"连接等待超时"错误与池大小日志；**锁与串行化**——单进程内 GIL 与同步库拖累：指标是"并发数增加但 QPS 不变甚至下降"。定位工具：**压测期间的观测**（08 篇的指标在压测时全程记录——请求日志的 latency_ms 分布直接看 P95 构成：检索 X ms + 模型 Y ms + 落库 Z ms，哪段最大就优化哪段——**"延迟解剖"是定位的第一刀**）；uvloop 事件循环替换（`uvicorn` 用 `--loop uvloop`，标准库 asyncio 的 2-4 倍事件循环吞吐）；py-spy 采样（阻塞点速查——`py-spy top --pid <pid>` 看到卡在哪个函数）。

## 5. 优化清单：按收益排序

定位到瓶颈后，按投入产出排序动手（本项目形态）：**连接池与复用**（最高收益）——OpenAI client 全局单例（Level2 03 已做）、SQLite 连接池参数调优（WAL + 合理池大小，Level2 04）、Chroma 客户端复用（不要每请求新建——embedding 模型加载是 Level1 教训的延续）；**异步化补漏**——检查是否有同步库在 async 路径上阻塞（如同步版 sentence-transformers 调用——用 `run_in_executor`/`asyncio.to_thread` 包异步，或换异步推理接口）；**序列化瘦身**——响应体字段裁剪（response_model 只返回需要的字段）、历史消息压缩（Level2 04 的上下文裁剪在这里也是性能优化——输入越小 LLM 越快）；**重排批量推理**（Level2 06 已做——检查是否真的批量化）；**检索缓存**（03 篇的响应缓存在高并发下也是延迟优化——命中缓存省掉一次完整检索+生成链路）。**不要做的优化**：数据量没到就上索引花活、单 worker 内微优化（先扩 worker 再微调）。**优化后的"验收闭环"**：每个优化改动跑"同一组并发梯度"的复测（基线 10/50/100/200 各档重跑），对比表记录"哪档提升了多少、哪档没变"——**"优化有效"的证据是同一把尺子量出来的**，换尺子（改压测参数）的对比是自欺欺人。

## 6. 多 worker 与水平扩展

单进程优化有天花板（GIL + 单核），**多 worker 是 Python 服务的标准水平扩展**：Uvicorn `--workers N`（N = 核数，Level2 09 已用 2 个）——**扩 worker 的三件事**（Level2 09 已铺垫，本模块验证）：SQLite WAL（并发写）、日志与指标聚合（进程内指标失效——Level3 07 的 Prometheus 从各 worker 采集合并）、共享状态外置（进程内缓存变 Redis——05 篇的引入动机）。**worker 数怎么定**：压测 2/4/8 worker 的 QPS 曲线——**不是越多越好**（SQLite 锁、LLM 连接数、内存都会成为新瓶颈），找"线性增长区间的终点"。**水平扩展的前景**：单机多 worker → 多机（前面挂 LB/Nginx 负载均衡——K8s 的 Replica 扩展是 09 篇的正式形态）——**"为什么不用多机"的决策记录**（单机够用就不加机器，加机器是运维复杂度）与前面所有选型决策同逻辑。

## 7. 常见坑

**压测打生产**：压测流量污染生产数据与监控——测试环境或本地，session 用独立前缀。

**压测时 LLM 真实调用**：外部延迟抖动污染数据——mock 版压测（系统容量）与真实版压测（端到端体验）分开跑，结论分开写。

**只看 QPS 不看 P95**：QPS 好看 P95 爆炸（尾延迟）——两个指标一起看，AI 应用的体验由 P95 决定。

**并发上去错误率飙**：压测发现的并发 bug（会话串扰、连接池耗尽）——**压测的价值一半在"并发正确性"**，错误响应分类统计（5xx 是资源、4xx 是契约——两种修法完全不同）。

**异步优化变成了同步**：`async def` 里调了同步 IO——定位工具（py-spy、延迟解剖）找出阻塞点，asyncio.to_thread 包住或换异步库。

**优化后不复测**：改完不跑同一组压测——优化是否有效没有证据，所有改动配"同一并发梯度"的复测。

**测试环境与生产差异**：本地压测通过、生产卡顿——机器规格、worker 数、网络延迟都不同，压测报告的环境说明（第 2 节模板）在迁移环境后要重跑一遍基线。

> 🎯 **核心要点**：高并发优化的本质是**"先测再改、一次一变量、数字说话"**——基线告诉你能扛多少、解剖告诉你慢在哪、清单告诉你先改什么、多 worker 告诉你怎么扩。压测报告（基线/优化后两轮对比）是简历里"我做了性能优化"这句话的证据链，也是 Level3 09 篇 K8s 自动伸缩的输入数据。
