# 07 可观测性全家桶

> 第七个加分项：把 Level2 的"轻量可观测"升级为"全家桶"——Prometheus + Grafana 指标可视化、OpenTelemetry 标准埋点、Jaeger 分布式追踪、SLO 与告警体系。当系统从单服务变成多组件（API + Redis + Milvus + PG），可观测性从"加分"变成"刚需"。

## 1. 目标与验收

本模块的产出：docker-compose 加四件套（Prometheus、Grafana、Jaeger、OTel Collector），服务接 OTel 埋点，Grafana 出 2-3 张仪表盘（请求量/延迟/成本），SLO 文档与告警规则。验收标准：**一次故障能在 Grafana 看到指标异常、在 Jaeger 看到完整调用链**（自己做一次故障演练验证）；**仪表盘是"打开就能用"的**（不是只配了没看）；**SLO 有数字有告警有复盘**。与仓库「日志监控指标」体系的分工：那边是三支柱原理全景，本模块是项目的全家桶落地。

## 2. 全家桶全景：组件与分工

可观测全家桶的组件分工（2026 标准形态）：**Prometheus**（指标采集与存储——时序数据库，拉模式抓取 /metrics）；**Grafana**（指标可视化——仪表盘、告警面板，2026 年监控 UI 的事实标准）；**OpenTelemetry**（统一埋点标准——日志/追踪/指标三支柱的 SDK 与协议，一次埋点多处消费）；**Jaeger**（分布式追踪后端——链路查询与可视化，OTel 数据的消费者之一）；**OTel Collector**（采集网关——应用把 OTel 数据发给它，它再分发给 Prometheus/Jaeger/日志平台——**"应用只埋一次点，数据分发交给 Collector"**是 2026 年的标准架构，应用侧零后端依赖）。**组件关系一句话**：应用埋 OTel → Collector 收 → Prometheus 存指标 + Jaeger 存链路 → Grafana 画给人和告警。全家桶不是"为了全家桶"——**触发时机**：组件变多（05/06 篇加了 Redis/Milvus/PG）后，单服务的日志 grep 已经找不到跨组件的故障链路——"多组件时代的定位需求"驱动全家桶，与 05 篇 Redis 的引入逻辑一致。

## 3. Prometheus + Grafana：指标可视化

Level2 08 的 /metrics 接口（内存指标）在 Prometheus 下正式升级：**Prometheus 拉取**（/metrics 输出 Prometheus 文本格式，compose 里配 scrape 目标）；**Grafana 可视化**（数据源连 Prometheus，仪表盘用 PromQL 查询）。本项目的四张核心仪表盘（从 Level2 08 的埋点直接升级）：**请求总览**（QPS、P95/P99、5xx 占比——按接口分）；**LLM 成本**（每日 token/费用曲线——03 篇成本优化的效果可视化）；**检索质量**（检索延迟、重排延迟、检索失败率——02 篇 Agentic 的自愈触发次数）；**组件健康**（Redis/Milvus/PG 的连接数、延迟、错误）。**PromQL 必学三条**（仪表盘最小语法）：`rate(http_requests_total[5m])`（QPS）、`histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))`（P95）、`sum(rate(...)) by (endpoint)`（按维度聚合）。**仪表盘的验收标准**：打开即用（不用现场调查询）、图上有告警线（阈值可视化）、每张图有名字注释（别人能看懂）。

## 4. OpenTelemetry 标准埋点

Level2 08 的手工 trace_id 在这里升级为 **OTel 标准埋点**——一次埋点，追踪（span）与指标（metric）同时产出，且跨组件传播（HTTP header 自动传递 trace_id）：

```python
from opentelemetry import trace
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor
from opentelemetry.instrumentation.httpx import HTTPXClientInstrumentor

# main.py 里两行接入（instrumentor 自动给路由/HTTP 客户端打 span）
FastAPIInstrumentor.instrument_app(app)
HTTPXClientInstrumentor().instrument()

# 业务自定义 span（关键节点，如检索/生成）
tracer = trace.get_tracer("kbqa")

def ask(question: str) -> str:
    with tracer.start_as_current_span("chat.ask") as span:
        span.set_attribute("question_length", len(question))
        context = retrieve(question)      # span: chat.retrieve
        ...
```

三个认知：**instrumentor 覆盖 80% 埋点**（框架与客户端库的自动埋点——FastAPI、httpx、redis、SQLAlchemy 都有官方 instrumentor，两行接入）；**业务 span 只加关键节点**（检索/生成/工具调用——"覆盖所有细节"的 span 是噪音）；**跨组件传播自动**（OTel 的 context propagation 通过 HTTP header 传递 trace_id——**Level2 08 手工中间件可以退役了，同一套 trace 概念升级为标准实现**）。**落地的注意点**：埋点改动要跑 Level2 07 的测试（埋点不该改变业务行为——测试是回归保险丝）；Trace 采样（生产流量全量打 Jaeger 会爆存储——采样率 10% 起步，错误链路强制全采（`sampler` 配置：尾采样或基于错误状态的采样）。

## 5. Jaeger 分布式追踪：跨组件定位

跨组件故障（"用户反馈慢了"）的定位流程在全家桶下变成：**Grafana 看指标**（哪个组件延迟飙了）→ **Jaeger 看链路**（该时段的完整调用链：API → Redis 缓存 → Milvus 检索 → LLM 调用，每段耗时一目了然）→ **日志看细节**（该 trace_id 的日志——Level2 08 的 trace_id 概念与 Jaeger 的 trace ID 统一（OTel 标准下同一个 ID））。**Jaeger UI 的必会操作**：按服务过滤、按延迟排序（找最慢的链路）、展开 span 看耗时占比（发现"检索占 80% 时间"）、错误 span 直接跳日志。**追踪的价值演示**（本模块验收实验）：人为制造一次慢检索（把 Milvus 连接断开或加人为延迟），从 Grafana 延迟曲线 → Jaeger 链路 → 日志细节，全程 5 分钟内定位——**这个演示做一遍，全家桶的每个组件你都知道它是干嘛的**。

## 6. SLO 与告警体系

SLO（服务等级目标）把"系统好不好"变成可度量的数字契约：**SLI → SLO → 告警 → 复盘**的闭环。本项目的 SLO 草案：**可用性**（请求成功占比 99.5%/月——5xx 与超时计入失败）；**延迟**（P95 对话接口 < 3s/月）；**成本**（日 LLM 费用 < 预算阈值）。告警分级（从 Level2 08 升级）：**P1 紧急**（可用性跌破 SLO、全接口 5xx——立即处理）；**P2 警告**（P95 接近阈值、成本环比 >20%——当天处理）；**P3 提示**（检索失败率上升、磁盘接近阈值——本周处理）。**告警的工程纪律**：**告警必须带排查路径**（每条告警对应文档里的一段"现象→查什么"）；**告警阈值用数据校准**（04 篇压测数据 + 两周观察分布——不拍脑袋）；**告警要演练**（人为故障触发一次 P1 告警，走一遍响应流程——"演练过的告警"才是真告警）。**SLO 复盘**（月度一次）：烧了多少错误预算、最大的可用性风险是什么、下月改善什么——**SLO 复盘的记录是面试"运维思维"的最佳素材**（"我用 SLO 管理项目质量，烧掉的错误预算驱动了下月的优化计划"）。

**全家桶的落地顺序建议**（避免一次全上消化不良）：**第一批**（1 天）：Prometheus + Grafana 接现有 /metrics（Level2 08 的埋点直接可视化——最小闭环）；**第二批**（1-2 天）：OTel 标准埋点 + Jaeger（追踪上线，trace_id 从手工升级为标准）；**第三批**（半天）：告警与 SLO 文档（阈值用前两批的真实数据校准）。**分批的理由**：每一批都是"能用且验证过"的闭环，出问题定位范围小——全家桶不是一次大爆炸，是三次小升级。

## 7. 常见坑

**全家桶全上但没人看**：仪表盘配了从不打开——验收标准是"打开就能用 + 故障演练做过"，不是"配置存在"。

**采样率不配**：全量 trace 打爆 Jaeger 存储——采样率从 10% 起步、错误全采，存储告警进 P3。

**埋点影响性能**：业务 span 里做了重计算（如埋点里调 embedding）——span 只记录轻量属性，重活不进埋点。

**Grafana 仪表盘成摆设**：阈值线没有、注释没有——别人（包括 3 个月后的自己）看不懂的仪表盘等于没有，每张图配注释与告警线。

**Collector 单点**：OTel Collector 挂了全家桶全挂——Collector 是高可用组件（多副本部署），或者先接受单点（记录风险，规模到了再解）。

**告警风暴**：一个故障触发 20 条告警——告警聚合（按服务/按类型分组）与降噪（同一根因只发一条），P1 不重复刷屏。

**仪表盘权限裸奔**：Grafana 默认匿名可读——生产环境配账号权限（Viewer/Editor 分权），与 08 篇的用户体系同纪律（内部工具也防未授权访问）。

**日志追踪脱节**：日志里没有 trace_id 或与 Jaeger ID 不一致——统一用 OTel 标准（日志 span context 自动注入 trace_id），手工 ID 方案退役后保持全链路可串。

> 🎯 **核心要点**：全家桶的本质是**把"故障定位"从"查日志猜"升级为"指标→链路→日志的三段定位"**——Prometheus 看状态、Jaeger 看链路、Grafana 呈现、SLO 定契约。多组件时代的系统没有全家桶等于"蒙眼运维"，有了它，一次故障 5 分钟定位就是日常。
