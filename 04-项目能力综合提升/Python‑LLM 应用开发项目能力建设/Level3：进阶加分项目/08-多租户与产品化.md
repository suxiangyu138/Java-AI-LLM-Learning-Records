## 1. 目标与验收

本模块的产出：用户注册/登录接口（JWT 认证）、租户与文档权限模型（用户只见自己的文档）、用量统计（每租户 token 消耗——03 篇成本埋点的产品化）。验收标准：**两个用户各自上传文档互不可见**（隔离实验）；**未登录请求被 401 拦截**；**用量报表能按租户导出**。**"产品化"的验收核心是场景**：模拟"两个企业客户同时使用"的完整流程走通——这个演示本身就是面试最有力的素材。

## 2. 产品化形态：从工具到 SaaS

单用户工具 → 多租户 SaaS 的演进，本质是**把"一人用的系统"拆出"客户边界"**：工具只有功能，产品有**用户**（谁在用）、**权限**（能用什么、看什么）、**隔离**（你的数据我的数据不混）、**计量**（用了多少、怎么收钱）。Level2 的 session 是"一次对话的容器"，产品化的最小升级是：**session 之上加用户，用户之上加租户**——三层归属关系（租户 1—N 用户 1—N 会话）。**SaaS 化的两套模式**（2026 选型）：**共享数据库 + 租户字段**（一张表里按 tenant_id 过滤——简单、成本低、隔离靠代码纪律——**本项目用这套**：规模小、成本优先）；**每租户独立库**（隔离强、运维重——客户数据敏感到必须物理隔离时才用）。**模式决策记录**（"为什么共享库够用"——数据非敏感、单租户规模小、成本敏感——又是标准的选型叙事）。

## 3. 用户体系：注册登录与 JWT

用户体系的最小完整实现：**注册**（用户名 + 密码哈希——密码用 argon2/bcrypt 哈希，绝不存明文）、**登录**（验证通过发 JWT）、**鉴权中间件**（每个受保护接口校验 JWT、解析用户身份）。实现要点（仓库「Cookie & Session」「Web 高阶知识」体系有协议原理，这里是落地）：

```python
from fastapi import Depends, HTTPException, Security
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials
import jwt  # PyJWT

SECRET = settings.jwt_secret          # 配置管理（Level2 02）

def create_token(user_id: int, tenant_id: int) -> str:
    return jwt.encode({"sub": str(user_id), "tenant_id": tenant_id,
                       "exp": datetime.now(timezone.utc) + timedelta(days=7)},
                      SECRET, algorithm="HS256")

def get_current_user(cred: HTTPAuthorizationCredentials = Security(HTTPBearer())):
    try:
        payload = jwt.decode(cred.credentials, SECRET, algorithms=["HS256"])
        return {"user_id": int(payload["sub"]), "tenant_id": payload["tenant_id"]}
    except jwt.PyJWTError:
        raise HTTPException(status_code=401, code="INVALID_TOKEN")   # 错误契约复用
```

三个细节：**JWT 有效期**（7 天 + 无状态——登出/封号需黑名单，产品化后加 Redis 黑名单（05 篇的 Redis 顺手的事））；**SECRET 进配置管理**（换 Secret 全部 token 失效——发布时注意）；**错误契约统一**（401 的 code 字段与 Level2 03 的契约体系一致——前端已就绪的分支逻辑直接复用）。

## 4. 租户隔离：数据边界设计

租户隔离是产品化的**安全核心**——隔离失败 = 数据泄漏事故。实现三件事：**数据模型加 tenant_id**（Session/Document/Message 表都挂 tenant_id——Level2 04 的三表升级）；**查询强制过滤**（Repository 层所有查询自动带 `WHERE tenant_id = ?`——**"过滤内置于数据访问层，业务代码无从绕过"**是隔离的第一纪律，靠每个业务代码自觉加 where 是必漏的）；**检索链路隔离**（向量检索按租户过滤——Milvus 的 partition 或 metadata 过滤（Level2 06 的 filter-then-search 在此变成"租户过滤先于检索"——**向量库的租户隔离是 2026 年的公认难点**，partition 方案是标准姿势）。

```python
async def get_recent_messages(db, tenant_id: int, session_key: str) -> list[Message]:
    stmt = (select(Message).join(Session)
            .where(Session.tenant_id == tenant_id)      # 隔离过滤：强制层
            .where(Session.session_key == session_key))
    ...
```

**隔离的验证实验**（本模块验收核心）：用户 A 建文档、用户 B 提问——**B 的检索结果与历史里绝不能出现 A 的数据**；安全测试（Level2 10 的自测清单升级）：B 拿 A 的 session_id 请求——404 而非数据（**越权访问返回"不存在"而不是"无权限"，不泄露存在性**——这是 2026 年越权防护的标准姿势，仓库「Web 高阶知识」IDOR 章节同源）。**隔离测试自动化**（Level2 07 的测试体系在此是刚需）：隔离实验写成 pytest——"B 用户访问 A 用户资源断言 404""B 用户检索结果断言无 A 文档"，放进 CI 每次回归跑——**隔离是安全属性，安全属性必须被测试锁死**，靠人工验收的隔离会在一次重构后悄悄失效。

## 5. 权限与文档管理

租户内部还要细分权限（产品化的第二层边界）：**角色模型**（最小可用两角色）——**管理员**（管理文档库、看用量、管理成员）与**成员**（问答、上传文档）；**文档级权限**——文档分为"公开（租户内）"与"私有（上传者/管理员）"，检索时按权限过滤。实现要点：**角色字段在用户表**（Demo 级够用；RBAC 完整模型（角色/权限/资源矩阵）在 Level3 之外——记录边界）；**文档权限的检索过滤**（检索的 metadata 过滤加权限条件——与租户过滤同一条链路叠加，**权限过滤永远在检索层完成，不做"先检后滤"**（先检后滤会把不该见的向量拖进内存再丢弃——性能与安全的双重问题））。**权限模型的面试价值**：讲"我设计了租户-角色-文档三级权限，隔离在数据层与检索层双层强制"——这是"产品安全意识"的直接证据。

## 6. 用量计费与配额

产品化的经济闭环：**计量**（每租户的 token 与费用——Level2 08 的 llm_calls 表加 tenant_id 字段，03 篇的成本埋点升级为计费数据源）；**配额**（每租户上限——月 token 额度，超限降级（答"额度已用尽"）或限流（05 篇的 Redis 限流按租户维度加一档））；**报表**（管理员看板：租户用量列表——08 篇指标 + 本模块数据表组合）。**计费的两个工程细节**：**计量要准**（以 usage 字段为准，缓存命中与失败请求的计量口径写清——缓存命中算不算用量是产品决策，不是技术问题，写进文档）；**配额要有缓冲**（80% 时提前告警（07 篇告警），100% 才硬性拦截——"配额预警"是产品体验的一部分）。**计费的演示**（面试素材）：压测两个租户的用量差异 → 导出报表——"我的系统能给客户出账单"是完整产品能力的证明。

## 7. 常见坑

**密码明文存储**：泄漏即事故——argon2/bcrypt 哈希必上，日志与指标里绝不出现密码字段。

**JWT 无注销**：封号不生效——短 TTL + Redis 黑名单（05 篇顺手），或升级为刷新令牌机制。

**隔离只做一半**：查询过滤了但缓存没隔离——Redis 缓存键带 tenant_id（05 篇命名规范），向量检索的 partition 过滤同样在缓存层复验。

**越权返回"无权限"**：暴露资源存在性——统一返回 404（不存在语义），错误日志里才记真实原因。

**配额实现太硬**：到 100% 直接 500——配额拦截是业务响应（错误契约 code=QUOTA_EXCEEDED，前端友好提示），不是技术异常。

**测试没覆盖隔离**：隔离实验不做成自动化测试——**隔离场景写成 pytest（Level2 07 的测试体系升级）**：用户 B 访问用户 A 的资源断言 404，这条测试是产品化的安全保险丝。

**配额与计费的计量口径漂移**：缓存命中算不算用量、失败请求算不算——计量口径是产品决策，写进文档并在计费报表里标注（"费用含缓存命中"一行说明），口径变更要发版记录——**计费数字的可信度 = 口径的清晰度**。

> 🎯 **核心要点**：产品化的本质是**"给系统画上客户边界"**——用户认证管身份、租户隔离管数据、权限模型管访问、用量计量管经济。四层边界齐了，项目从"技术演示"变成"可交付产品"；面试时"我的系统服务多个租户，隔离在数据层与检索层双重强制"——这句话的含金量远超"我做了个 RAG 问答"。
