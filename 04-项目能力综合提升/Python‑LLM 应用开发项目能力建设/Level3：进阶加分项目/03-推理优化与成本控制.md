## 1. 目标与验收

本模块的产出：成本优化三件套落地——prompt caching 生效（前缀命中验证）、响应缓存（重复问题命中）、小模型路由（简单任务走 flash）；一份"优化前后成本对比表"（每问题平均成本下降 X%）。验收标准：**能用数据说明成本降了多少**（对比表是硬性交付物）；**能讲清每个优化的原理与适用边界**；**成本监控（Level2 08）继续工作，优化效果可观测**。与仓库「模型推理与部署」「量化背后硬件约束」体系的分工：那边是推理原理全景，本模块是 API 调用侧的工程优化。

## 2. 成本构成：先算清钱花在哪

优化前先记账（Level2 08 的成本埋点在这里出成果）：对话请求的成本大头通常不是"单次输出"，而是**三块隐性开销**——**重复输入**（多轮对话每轮重发历史、RAG 每问重发上下文——输入 token 占总消耗 60-80%）；**重复调用**（同一问题反复问、同一文档反复检索生成）；**模型错配**（简单任务用贵模型）。三块对应三个优化方向：prompt caching（重复输入）、响应缓存（重复调用）、小模型路由（模型错配）——**先记清楚账，再对症下药**，这是成本优化的方法论起点。记账公式（配置里的单价是配置项，Level2 08 已建）：每问题成本 = 输入 token × 输入单价 + 输出 token × 输出单价，两个单价在 settings 里维护。

## 3. prompt caching：输入成本降 50-90%

prompt caching（提示词缓存）是 2026 年投入产出比最高的成本优化：**模型服务端缓存相同的前缀**，命中缓存的部分按约 1/50 的价格计费（DeepSeek V4：缓存命中输入 0.02 元/百万 vs 未命中 1 元/百万——50 倍价差），同时首字延迟下降。适用对象：**system 提示词 + 工具声明 + RAG 注入的静态上下文**（每次请求都带、内容不变的前缀）。实现：

```python
# OpenAI 兼容协议：SDK 自动管理缓存断点，只需保证前缀稳定
resp = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[system_prompt, *static_context, {"role": "user", "content": question}],
    extra_body={"cache_control": True},    # 各家参数名不同，以官方文档为准
)
log.info("缓存命中 tokens: %s / %s", resp.usage.prompt_tokens_details.get("cached_tokens", 0),
         resp.usage.prompt_tokens)
```

**缓存命中率是设计出来的，不是运气**——五条铁律：**前缀固定顺序**（system 在前、工具声明固定排序——Level2 06 的"工具排序固定"在这里加倍重要，改顺序=缓存全失效）；**动态内容放尾部**（历史消息、当前问题——可变部分永远在 messages 末尾）；**冻结 system 模板**（提示词改一个字，缓存前缀断了——提示词版本管理（Level1 04）与缓存共用一个版本号）；**验证命中**（每次调用读 prompt_tokens_details 的 cached_tokens，监控命中率——<50% 说明前缀在漂移，是调试信号）；**不要缓存敏感内容**（用户隐私数据进前缀会留在服务端缓存——缓存纪律与安全基线（Level2 10）联动）。

## 4. 响应缓存与语义缓存

prompt caching 省的是"重复输入的价"，**响应缓存**省的是"重复调用的钱"——相同问题直接返回缓存答案，连模型都不调。两种形态：**精确缓存**（Redis key = 问题哈希，命中直接返回——Level2 10 提到的高频问题缓存，本模块落地）；**语义缓存**（问题语义相近也命中——key 是问题的 embedding 向量，检索"最近邻"判断是否同义——语义缓存是 2026 年的进阶做法，命中率更高但多一次向量查询，与 Redis 配合实现）。实现要点：**缓存键设计**——session 无关的全局问题缓存（知识问答场景"什么是 RAG"人人会问，缓存收益最大）；**TTL 策略**——知识库更新后缓存要失效（文档重新入库 → 清相关缓存，与 Level2 04 的删除流程联动）；**缓存穿透防护**——未命中时加锁防并发重复调用（Redis 的 SETNX 或本地锁）。**响应缓存的验收**：同一问题连问两次，第二次不产生 LLM 调用（08 篇的 llm_calls 表计数验证）——这个验证实验本身就是面试素材。

## 5. 小模型路由：分级调用

**模型错配**是隐性成本的第三大头：总结、分类、改写这类简单任务用 flash 就够，没必要上 pro；复杂推理（多跳分析、代码审查）才用 pro。**分级路由**实现：路由层（01 篇的 supervisor 顺手做的）按任务复杂度分派模型——规则可简单起步（"问题长度 > N 或含比较词走 pro"），进阶用模型判断（一个小分类模型或让 flash 自己标"复杂度等级"）。成本配比数据（本项目的典型形态）：**95% 请求走 flash、5% 走 pro**，总成本相比"全 pro"下降 60-80%，质量几乎无感——"路由准确率 94% 集中路由 + 分级模型"是 2026 年的标准组合。**分级路由的评估**：路由错了怎么办——把"被路由到 pro 的请求里，flash 也能答的比例"作为指标（定期抽检，过高说明路由太保守），路由策略与评估联动（02 篇的评估方法论复用）。

## 6. 本地模型与量化部署

第三层优化：**部分能力本地化**——embedding 与重排模型已经本地跑（Level2 06），进一步可以把**简单生成任务**（标题生成、分类、改写）部署本地小模型（Qwen 7B/14B 量化版、DeepSeek 蒸馏版），通过 Ollama/vLLM 提供 OpenAI 兼容接口（仓库「部署工具」「模型推理与部署」体系有全景）。**量化**是本地部署的标配：权重从 FP16 压到 INT8/4bit（显存降 50-75%、速度升），质量损失对简单任务可忽略——**"量化 + 小模型 + 简单任务"是本地化的甜区**，复杂任务仍走云端大模型。**本地化的账要算清**：省的是 API 调用费，花的是服务器算力（GPU 成本）与运维成本（模型更新、推理服务稳定性）——**Demo 期的结论通常是"云端 API 更划算"**，但把"为什么不上本地模型"的决策记录写清楚，比盲目本地化专业——本地化真正的场景是数据合规（敏感数据不出内网）与规模化后的边际成本，这两点在面试里讲得出就是深度。

## 7. 常见坑

**缓存命中率低还不看**：前缀在漂移（改过 system 提示词）——监控 cached_tokens 占比，命中率 <50% 先查前缀稳定性。

**响应缓存与知识库更新脱节**：文档更新后旧答案继续命中——入库流程里加"清缓存"动作（Level2 04 的删除一致性流程扩展），缓存失效是正确性的底线。

**语义缓存误命中**：语义相近但答案不同的问题命中旧答案——语义缓存的相似度阈值调严（宁可漏命中不错命中），且只缓存"事实型"问题（"是什么"），不缓存"观点型"（"你怎么看"）。

**prompt caching 与思考模式冲突**：推理模型的思考内容可能不进缓存或需特殊处理——以各家文档为准，先验证 cached_tokens 字段真的在涨。

**全量走小模型省出质量问题**：路由策略太激进，复杂问题用 flash 答砸——抽检 + 用户反馈通道，路由阈值定期校准。

**成本优化动摇了功能**：为了省 token 砍了必要的上下文（检索只给 2 块）——优化的第一原则是"质量不变的前提下省钱"，评估集（Level2 06）在每次成本优化后重跑，质量回退的优化是伪优化。

> 🎯 **核心要点**：成本优化的本质是**"该省的省、该花的花"**——prompt caching 省重复输入的价、响应缓存省重复调用的钱、分级路由省模型错配、量化本地化省规模化成本。每一笔省下的钱都要有监控数据佐证（Level2 08 的成本埋点），**"成本下降 60% 且质量不掉"是简历里最有说服力的一类数字**。
