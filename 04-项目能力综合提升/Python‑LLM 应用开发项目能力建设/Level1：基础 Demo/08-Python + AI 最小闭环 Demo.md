## 1. 目标与验收

本 Demo 的产出：一个完整的 Streamlit 应用——侧边栏上传文档（txt/md），主区对话，回答基于文档内容并标注依据。验收标准：**能画出完整数据流图**（上传→分块→向量化→入库；提问→检索→注入→生成）；**能说出每层复用了前面哪篇的代码**；**做出一份调优记录**（改了什么参数、效果如何）。这是 Level1 的总验收：链路覆盖（界面 + 检索 + 工具）、代码可读（模块化拆文件）、理解到位（能讲清每一环节）。完成后对照 10 篇毕业检查单。

## 2. 整体架构：三模块整合

闭环应用的代码拆成三个文件，各司其职——这是"Demo 也要能读"的底线：

```text
app.py            # Streamlit 界面层：上传、对话、渲染（05 篇三原语）
rag.py            # RAG 层：分块、向量化、入库、检索（06 篇链路）
agent.py          # 编排层：组装上下文、调模型、工具调用循环（03/04/07 篇）
```

数据流分两条：**离线链路**（一次性）——上传文档 → rag.py 分块 → 向量化 → 入库 Chroma；**在线链路**（每次提问）——agent.py 收到问题 → 检索相关块 → 注入提示词 → 调模型 → 回答。两条链路在 agent.py 汇合：**RAG 检索的结果，本质上就是注入到 system 提示词里的"上下文"**——与 07 篇工具调用是同一种机制（把外部信息带进对话），只是信息来源不同（向量库 vs 代码执行）。理解这个统一：**AI 应用 = 模型 + 信息来源（检索/工具）+ 提示词编排**，08 篇就是这三个组件的集成。

模块边界的设计原则一句话：**界面层不碰模型、编排层不碰存储**。app.py 只调 rag.ingest 和 agent.ask 两个函数（不 import openai、不碰 chromadb）；rag.py 只做入库与检索（不拼提示词）；agent.py 只做编排（不管界面）。Demo 阶段这样的分层看似小题大做，但它让每个文件都能单独调试（`python -c "import rag; print(rag.ingest(open(...).read()))"`），也让 Level2 的工程化改造有现成的骨架——把 app.py 换成 FastAPI 路由、rag.py 换成 Repository 层，就是标准的分层迁移。

## 3. 文档上传与入库

界面层用 st.file_uploader 接收文件，调 rag.py 入库——入库操作放"上传按钮"里显式触发（而不是每次 rerun 重跑），这是 Streamlit 里做"一次性重型操作"的标准姿势：

```python
# app.py 片段
uploaded = st.file_uploader("上传知识文档", type=["txt", "md"])
if uploaded is not None and st.button("导入知识库"):
    text = uploaded.read().decode("utf-8", errors="replace")
    count = rag.ingest(text)          # 分块 + 向量化 + 入库，返回块数
    st.success(f"已导入 {count} 块文档，可以开始提问了")
```

rag.py 的 ingest 函数把 06 篇的四步封装成一次调用（分块 → embed → 入库），并处理重复导入（入库前按文档名清理旧块，或给 id 加文档前缀——`doc-{name}-{i}`，重复导入同一文件时先 delete 再 add）。注意 `decode("utf-8", errors="replace")` 兜底编码问题（用户可能传 GBK 文件）——宁可个别字符变成 �，也不要整个崩溃。embedding 模型加载放进 @st.cache_resource（06 篇的坑，这里正式解决）。

导入过程的可视化：本地 embedding 几百块文档要几十秒，用户会以为卡死了。两处小改进就够：**按钮点击后先 st.spinner("正在导入...")**（旋转动画提示在干活）；**ingest 里按块 yield 进度**（每处理 50 块打一次 st.progress 或日志），导入完成 st.success 显示块数与耗时。这段"导入体验"代码本身不复杂，但它把 Demo 从"能跑"推向"能用"——面试讲项目时"我处理了长导入的体验问题"是真实的产品感信号。

## 4. 问答链路：RAG + 工具调用组合

问答主循环在 agent.py：检索注入 + 工具调用两套机制按需触发——**提问先走检索**（知识问答），**模型在回答过程中需要实时数据时再调工具**（比如问"文档里没写的问题"）。组合后的主循环：

```python
# agent.py
def ask(question: str, collection, messages: list[dict]) -> str:
    # 1. 检索相关块（06 篇）
    results = collection.query(query_embeddings=embed([question]), n_results=3)
    context = "\n\n".join(f"[文档{i+1}] {d}" for i, d in enumerate(results["documents"][0]))

    # 2. 组装带上下文的 system 提示词（04 篇三件套）
    system = f"""你是知识库助手。
【上下文】
{context}
【约束】
1. 优先依据上下文回答，标注依据的文档编号
2. 上下文没有的，明确说"文档中未找到"，不要编造
3. 需要实时数据（天气、时间等）时调用对应工具"""
    messages.append({"role": "user", "content": question})
    return run_tool_loop(system, messages)   # 07 篇的五步循环（带上 tools）

# 07 篇的 while 循环在此复用：工具调用 + 回传 + 最终回答
```

两个设计决策及其理由：**检索在每次提问都执行**（文档随时可能更新，且检索便宜）；**系统提示词是"组装出来的"**（上下文、约束、工具声明都是变量拼进提示词——这就是 04 篇"提示词即配置"的工程化形态）。一个容易忽视的细节：检索的 top_k 结果**不要全部塞进上下文**——先把检出的块按相关度排序、检查数量（比如检索 5 块但只注入 3 块），避免无关块稀释注意力；简化的做法是注入前打印一次检索结果，人工确认相关性（调试期标配）。整个问答链路代码量约 150 行，却覆盖了 Level1 的全部知识点——**每行都要能讲出出处**（哪篇学的、为什么这么写），这是 10 篇答辩的基础。

## 5. 调优记录：参数与效果

Level1 与"抄教程"的区别，在于**留下调优记录**——面试讲项目时，"我调过分块大小、对比过 top_k，效果从 X 变成 Y"是极强的加分素材。记录格式建议：

```text
## 调优记录
- 基线：size=500, overlap=80, top_k=3, temperature=0.2 —— 回答可用，但长文档检索到无关块
- 实验1：size 500→800 —— 无关块变多（块大语义杂），回退
- 实验2：top_k 3→5 —— 长问题覆盖更全，短问题引入噪音，保持 3
- 实验3：temperature 0.2→0 —— 输出更稳定，格式错误减少
- 结论：size=500/overlap=80/top_k=3/temp=0 为本项目最优组合
```

调优方法论三条：**一次只改一个参数**（同时改两个无法归因）；**用固定问题集评估**（5 个问题：3 个文档内 + 2 个文档外，每次改完全量重跑——文档外问题检验"拒答"是否仍成立）；**记录基线再动手**（没有基线无从比较）。评估的观察维度两条：**回答正确性**（正例是否答对、负例是否拒答）与**成本**（usage 的 token 数——分块大小直接影响输入成本）。这套"参数-实验-结论"的文档化习惯，Level2 的每个性能优化都会用到。

## 6. 验收清单与常见坑

功能验收：**正例问答正确**（文档里的内容能答对并标注编号）；**负例拒答**（文档外问题答"未找到"）；**工具调用生效**（问实时问题时模型调用工具）；**界面完整**（上传、导入提示、多轮对话、流式输出）。代码验收：**三文件分工清晰**；**每个函数能讲清输入输出**；**调优记录完整**。

常见坑：**上传后提问没变化**（入库失败——检查 ingest 是否真的执行了，按钮分支里加 st.success 确认）；**重复导入重复入库**（id 冲突——按文档名清理旧块）；**长文档首次导入很慢**（embedding 本地推理，几百块要几十秒——加进度提示 st.progress，让用户知道在干活）；**对话历史与检索上下文冲突**（历史里带了旧的上下文、新提问又拼新上下文——历史只存 user/assistant 消息，上下文每轮现拼）；**流式 + 工具调用组合卡住**（流式模式下工具调用回调不同——Demo 阶段工具场景用非流式，Level2 处理流式工具回调）。

> 🎯 **核心要点**：本 Demo 是 Level1 的"毕业作品"——界面（Streamlit）、外挂记忆（RAG）、行动能力（工具调用）三件套集成。**能不看文档独立重写它、每行能讲出来源**，Level1 就毕业了；这个应用的工程化改造（FastAPI 化、测试、部署），就是 Level2 的第一课。
