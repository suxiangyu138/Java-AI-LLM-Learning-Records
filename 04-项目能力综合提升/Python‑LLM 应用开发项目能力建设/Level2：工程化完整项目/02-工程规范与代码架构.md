## 1. 目标与验收

本模块的产出：项目的完整骨架——目录结构、pyproject.toml（含依赖与工具配置）、config.py、.env 三态样例、Git 初始化。验收标准：**`uv run ruff check .` 与 `uv run mypy app/` 零错误通过**；**能讲清每层目录的职责与依赖方向**；**配置能在 dev/test/prod 三态切换**。这套骨架是 Level2 全部代码的容器，值得花一天打磨——后面每一篇的代码都按这里的规范写，返工成本最低。

## 2. 目录分层：一个文件一个职责

目录按"分层架构"组织，依赖方向单向：**api 层依赖 service 层，service 层依赖 repository/rag 层，禁止反向**。这是 Level1 三文件结构（app/rag/agent）的正式化：

```text
kbqa/                        # 项目根
├── pyproject.toml           # 依赖 + ruff/mypy/pytest 配置
├── uv.lock                  # 锁定版本
├── .env.example             # 配置样例（提交 Git）
├── .env                     # 本地配置（不提交）
├── app/
│   ├── main.py              # FastAPI 入口：创建 app、注册路由
│   ├── config.py            # pydantic-settings 配置模型
│   ├── api/                 # 路由层：HTTP 与业务的边界
│   │   ├── chat.py          # 对话接口（含 SSE 流式）
│   │   └── documents.py     # 文档上传/列表接口
│   ├── schemas.py           # Pydantic 请求/响应模型
│   ├── services/            # 业务层：对话编排、文档处理
│   │   ├── chat_service.py
│   │   └── doc_service.py
│   ├── rag/                 # 能力层：检索与生成
│   │   ├── ingest.py        # 分块/向量化/入库
│   │   ├── retrieve.py      # 混合检索 + 重排序
│   │   └── graph.py         # LangGraph 编排（05 篇）
│   ├── repository/          # 数据层：SQLModel 表与 CRUD
│   │   ├── models.py
│   │   └── db.py
│   └── core/                # 基础设施：日志、异常、工具
│       ├── logging.py
│       └── exceptions.py
├── tests/                   # 测试（07 篇）
├── scripts/                 # 部署与运维脚本
├── data/                    # SQLite 与 Chroma 数据（不提交）
└── docs/                    # 立项/调优/部署文档
```

三条铁律：**api 层不碰数据库**（请求校验与业务分离）；**service 层不写 HTTP 细节**（可被接口与测试两方复用）；**rag 层不依赖 FastAPI**（纯业务逻辑，可独立测试）。每条铁律违反一次就记一次"架构债"，验收前统一还清。

## 3. 配置管理：pydantic-settings 三态配置

配置的工程化标准：**代码里零硬编码、配置按环境切换、密钥不进代码**。pydantic-settings 是 FastAPI 生态的标准配置方案，从 .env 读取并校验类型：

```python
# app/config.py
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_prefix="KBQA_")

    # 模型
    deepseek_api_key: str
    model_name: str = "deepseek-v4-flash"
    embedding_model: str = "BAAI/bge-small-zh-v1.5"
    rerank_model: str = "BAAI/bge-reranker-v2-m3"

    # 存储
    db_url: str = "sqlite+aiosqlite:///./data/kbqa.db"
    chroma_dir: str = "./data/chroma"

    # 运行时
    log_level: str = "INFO"
    max_history_turns: int = 10

settings = Settings()   # 全局单例，各模块 import 使用
```

三态切换：**dev**（本地 .env，默认参数）、**test**（tests 用临时目录与内存库，07 篇覆盖）、**prod**（Docker 环境变量注入，09 篇覆盖）。两个实践：**env_prefix 加前缀**（KBQA_ 开头，避免与系统变量冲突）；**.env.example 提交 Git**（记录全部配置项与说明，真实 .env 不提交）——新环境照 example 复制改密钥即可，这是"15 分钟部署"的配置侧保证。

配置读取的三个纪律：**启动时校验**（Settings() 实例化即校验——Key 缺失在启动时报错，而不是请求时 401，把"环境问题"挡在部署之前）；**配置即默认值**（非敏感项在模型里给默认，.env 只覆盖差异——少一行配置少一个出错点）；**禁止运行时改配置**（改了 .env 要重启服务才生效——这是特性不是缺陷，配置是启动快照）。

## 4. 质量门禁：ruff + mypy

代码质量不是靠自觉，是靠**工具门禁**。2026 年 Python 的事实标准组合：**ruff**（格式化 + lint 一体，Rust 实现极快）与 **mypy**（类型检查，pyright 亦可）。pyproject.toml 里配置，命令一键跑：

```toml
[tool.ruff]
line-length = 100
target-version = "py314"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM"]   # 错误/未用/导入排序/升级/内置陷阱/简化

[tool.mypy]
python_version = "3.14"
strict = true
check_untyped_defs = true
```

使用习惯：**改代码后必跑**（`uv run ruff check . && uv run ruff format .`，耗时秒级）；**mypy 严格模式起步**（开头严格，后面不用补债；类型错误在写的时候就暴露，比运行时崩溃便宜一百倍）；**配 VS Code 自动执行**（保存即 format + lint）。面试讲点：**"我用 ruff 统一代码风格、mypy 严格模式做静态类型检查，CI 里强制跑"**——这句在 Java 侧对应"Checkstyle + SpotBugs"，面试官立刻知道你懂工程化。

**pre-commit 钩子**把门禁从"习惯"变成"强制"：`uvx pre-commit install` 后在每次 commit 前自动跑 ruff + mypy + 快速测试，不合格直接拦截提交。.pre-commit-config.yaml 配三个钩子（ruff-check、ruff-format、mypy）即可，钩子失败的信息就是"改好再提交"的提示。习惯链条完整化：**保存时 IDE 格式化 → 提交前 pre-commit 检查 → CI 全量门禁**——三道关卡对应"个人习惯 → 本地强制 → 团队强制"，任何一道漏了后面都能兜住。

## 5. Git 工作流与依赖管理

Git 从 Level1 就该用起来，Level2 正式化：**分支模型**——main（可部署）→ feature 分支（按模块开）→ 合并用 PR/merge 加简短描述；**提交规范**——`feat(chat): 新增 SSE 流式接口`、`fix(retrieve): 修复 RRF 融合排序` 的 Conventional Commits 格式，一次提交一个逻辑；**每篇一个里程碑提交**（本模块提交"工程骨架"），Git 历史就是项目演进日志——面试讲"项目怎么迭代的"直接看 log。

依赖管理两条铁律：**uv.lock 必须提交**（环境可复现）；**升级依赖走 uv add 显式操作**（不手动改 pyproject.toml 版本号）。分环境依赖：`uv add --dev pytest ruff mypy pytest-asyncio httpx`（测试工具不污染生产依赖），`uv sync` 默认装 dev，`uv sync --no-dev` 生产安装（09 篇 Dockerfile 用它）。

命名与提交规范（小而重要，统一才有生产力）：**文件/函数/变量**——模块名小写下划线（chat_service.py）、类名 PascalCase、常量全大写；**提交信息**——`feat(chat): 新增流式接口` / `fix(retrieve): RRF 融合顺序修正` / `docs(README): 补充部署说明`，格式为"类型(模块): 摘要"，一次提交一个逻辑单元（不把"改接口+改测试+改文档"混成一个提交）；**分支名**——feature/chat-stream、fix/retrieve-fusion，合回 main 即删。这些约定没有技术含量，但**Git 历史是可读的项目演进日志**——面试官看你的提交历史就知道你有没有工程纪律。

**分层架构的自我检查**（骨架期间的三个问题）：**"这个 import 方向对吗？"**（api → service → repository/rag，反了就是架构债）；**"这个逻辑放哪层？"**（不知道放哪层说明职责划分不清——回看第 2 节的层职责表）；**"删掉这一层代码，其他层会怎样？"**（无感知——分层合理；连锁崩——耦合过深）。三个问题在每次 code review 前过一遍，架构债不积累。

## 6. 环境验证与常见坑

骨架搭完的验证清单（一条命令验证一个环节）：`uv run python -c "from app.config import settings; print(settings.model_name)"` 验证配置读取与 .env 加载；`uv run ruff check .` 与 `uv run mypy app/` 验证门禁；`git log --oneline` 验证提交规范；`uv run python -c "import app.main"` 验证包导入链完整。**骨架验证的价值**：后续 03-09 篇的代码都长在这副骨架上，骨架有问题（导入错、配置错）会在每一篇里重复爆发——第一天花 10 分钟全验证一遍，是性价比最高的时间投入。

**目录分层形同虚设**：service 里 import api 的东西、rag 层直接用 FastAPI 的 Request——遇到即改，用 import 方向检查（`import-linter` 工具可自动化）。

**配置硬编码回潮**：新写的代码里出现 `"deepseek-v4-flash"` 字符串常量——统一从 settings 读，code review 时重点查。

**ruff 与 mypy 只配不跑**：门禁的价值在执行——CI（09 篇）里强制跑，本地配 pre-commit 钩子（`uvx pre-commit install`）。

**.env 被提交**：.gitignore 里写死 `.env`（不只写 .env.example 例外）；误提交立即按 Level1 01 篇的预案处理（重置 Key）。

**类型检查过严导致抱怨**：mypy strict 初期会烦，用 `# type: ignore[arg-type]` 逐点豁免并写理由——"豁免有理由"比"全开全关"专业。

**工具链版本与 Python 版本不匹配**：ruff/mypy 对 3.14 的支持依赖自身版本——`uvx ruff --version` 检查，旧版本升级；pyproject.toml 里 `target-version = "py314"` 与 `python_version = "3.14"` 保持同步，不同步会在语法解析与类型推断上产生诡异报错。**依赖升级节奏**：锁定版本是常态（uv.lock），但每月给"安全/工具类"依赖（ruff、mypy、pydantic 补丁）做一次升级——工具链的版本债同样会积累，久不升级的代价是一次性大迁移。升级后跑一遍全套门禁（第 6 节清单），确认无回归再提交。

> 🎯 **核心要点**：工程规范的全部价值是**让代码可靠地生长**——目录分层定结构、配置管理定参数、质量门禁定标准、Git 定演进。骨架立好，后面 8 个模块的代码只是往里长，不会长歪。
