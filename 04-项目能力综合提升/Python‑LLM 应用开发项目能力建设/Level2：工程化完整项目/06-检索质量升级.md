## 1. 目标与验收

本模块的产出：升级后的检索组件（语义分块 + 混合检索 + 重排序）+ 评估集与 RAGAS 报告（升级前后指标对比）。验收标准：**评估报告显示检索质量提升（NDCG/上下文精度等至少一项显著上升）**；**能画出"检索 → 融合 → 重排 → 生成"的四步链路**；**能讲清每个升级解决了什么缺陷**。行业基线（2026-08）：**检索是 RAG 系统约 73% 故障的根源**（而非生成），混合检索 + 重排序是生产基线，纯向量检索已不算完整方案。

## 2. 为什么检索是 RAG 成败的关键

RAG 的故障大多不在"模型回答得不好"，而在"模型没拿到对的内容"——检索质量决定上限，生成只是在下限之上工作。两个典型失败：**语义盲区**——用户问"RNN 和 LSTM 的区别"但文档里用的是全称缩写（向量检索对精确术语、编号、缩写不敏感）；**词面盲区**——用户用同义词提问（BM25 关键词检索对改写不敏感）。**混合检索的意义就是两条路互补**：向量管语义、关键词管精确，融合后两种盲区同时被覆盖——2026 年实践数据：混合检索对比纯向量在 NDCG@10 上提升 15-25 个百分点，是"投入产出比最高的单点升级"。理解了这个"为什么"，下面的实现每一步都有目的。

## 3. 语义分块：结构优先

Level1 的按字符切块会切碎语义（把段落从中间劈开）。生产级分块遵循**结构优先**：尊重文档的标题层级与段落边界（Markdown 按 ## 分节、代码按函数切、法律文本按条款切），块大小为 512-1024 token、overlap 128 左右。实现路径：解析结构（读标题/段落）→ 结构单元切分 → 超长单元再按句切。2026 实践数据：**结构化分块对比固定长度分块，忠实度/精度提升 8-12%**。

```python
# app/rag/ingest.py —— Markdown 按标题层级分块（结构优先）
import re

def chunk_markdown(text: str, max_chars: int = 800) -> list[str]:
    sections = re.split(r"(?m)^(#{1,3} .+)$", text)   # 按标题切分
    chunks, current = [], ""
    for part in sections:
        if re.match(r"^#{1,3} ", part):               # 是标题：封当前块
            if current.strip(): chunks.append(current.strip())
            current = part
        else:
            current += part
            if len(current) > max_chars:              # 超长再按段落续切
                chunks.append(current[:max_chars]); current = current[max_chars:]
    if current.strip(): chunks.append(current.strip())
    return chunks
```

配套的两个升级：**metadata 必带**（每块记录来源文档名、章节、创建时间——检索后过滤、回答时溯源、删除文档时定位，全部靠它）；**过滤先于检索**（"只看文档 X"这类问题先按 metadata 过滤再检索，省时又提精度——2026 实践：filter-then-search 能砍掉 60-80% 的延迟并提升精度）：

```python
collection.query(
    query_embeddings=embed([question]),
    n_results=top_k,
    where={"document_id": doc_id},      # Chroma 的 metadata 过滤
)
```

**查询改写（Query Transformation）**是检索侧最后的进阶手段：问题太模糊或太复杂时，先让模型改写——**HyDE**（让模型先"假设性回答"一遍，再检索这个假答案的相似文档——对模糊问题提升 5-8 个 NDCG 点）、**多查询扩展**（把一个问题拆成几个子问题分别检索再合并）。成本是多次模型调用，所以**默认不用、评估暴露短板再用**——判断标准回到 06 篇的评估数据：模糊问题的上下文召回低，才引入改写。

## 4. 混合检索：BM25 + 向量 + RRF

混合检索三件套：**向量检索**（Level1 的 Chroma，管语义）+ **BM25 关键词检索**（管精确匹配）+ **RRF 融合**（合并两份排名）。RRF（Reciprocal Rank Fusion）是 2026 年的推荐融合法——原理极简：`score = Σ 1/(k + rank_i)`（k=60），每个候选在两份排名中的位次越好分越高，**无需调参、无需训练、开箱即用**（实践数据：RRF 在约 80% 的部署中优于学习的融合方法）。

```python
# app/rag/retrieve.py
from rank_bm25 import BM25Okapi   # uv add rank-bm25

def hybrid_search(question: str, top_k: int = 50) -> list[tuple[str, float]]:
    vector_hits = chroma_collection.query(            # 1. 向量路
        query_embeddings=embed([question]), n_results=top_k)
    bm25_hits = bm25_index.search(tokenize(question), k=top_k)   # 2. 关键词路

    scores: dict[str, float] = {}
    for rank, hit in enumerate(vector_hits["documents"][0]):     # 3. RRF 融合
        scores[hit] = scores.get(hit, 0) + 1 / (60 + rank + 1)
    for rank, doc in enumerate(bm25_hits):
        scores[doc] = scores.get(doc, 0) + 1 / (60 + rank + 1)
    return sorted(scores.items(), key=lambda x: -x[1])[:top_k]
```

实现要点：**BM25 索引在入库时构建**（与向量化并行——ingest 里分词建 BM25 索引，存内存/落盘）；**中文分词是 BM25 的前提**（jieba 分词后喂 BM25，直接按字符切会让关键词匹配失效）；**两份结果的文档标识要对齐**（都用块 id/内容做 key）。混合检索的候选集要**取大一点（top_k=50）**——这是给下一步重排序留发挥空间。

## 5. 重排序：top-50 → top-5

检索的"召回"完成 50 个候选后，用**交叉编码器重排序**做"精排"：对每对（问题, 候选块）整体编码打分（双向注意力，语义匹配精度高，但无法预计算所以只精排小集合）。实践数据：**重排序是 RAG 系统"投资回报率最高"的升级**——NDCG@10 提升 5-15 分，端到端准确率提升 33-40%，代价约 120ms 延迟。选型：开源首选 **BAAI/bge-reranker-v2-m3**（多语言、MIT 协议、中文效果好），商用 API 可选 Cohere Rerank。

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

def rerank(question: str, candidates: list[tuple[str, float]], top_k: int = 5) -> list[str]:
    pairs = [[question, doc] for doc, _ in candidates]
    scores = reranker.predict(pairs)                 # 一次批量推理打分
    ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])[:top_k]
    return [doc for (doc, _), _ in ranked]
```

使用规范：**候选集 50 → 精排 5**（给重排器留空间，给模型好材料——最终注入 4-8 块是 2026 年的共识量，塞 20-30 块反而互相矛盾）；**一次批量推理**（不要逐条打分）；**记录重排前后的位次变化**（哪类问题重排救回来了——这是调试与面试素材）。最终链路上线：retrieve（50）→ rerank（5）→ 注入生成。

## 6. 评估先行：RAGAS 评估集

没有评估，一切"优化"都是感觉——**评估集与基线先于优化建立**。评估集构造：从真实使用场景收集 50-200 条（问题, 参考答案, 答案依据的原文片段）三元组，人工标注（真实问题优于合成问题——合成集抓不住长尾）。**RAGAS**（0.4）用 LLM-as-judge 自动化计算四项指标：**忠实度**（答案是否忠于检索内容——幻觉检测）、**答案相关性**（答的是否所问）、**上下文精度**（检索结果里相关片段占比）、**上下文召回**（相关片段被检出的比例）。

```python
# scripts/eval_rag.py —— 评估脚本，每次检索/提示词改动后重跑
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall

result = evaluate(dataset=eval_set, metrics=[
    faithfulness, answer_relevancy, context_precision, context_recall])
print(result.to_pandas())   # 逐条 + 均值报告
```

**发布门槛建议**：忠实度 > 0.85、上下文召回 > 0.85、上下文精度 > 0.7（企业基线）；每次改动（分块参数、检索方式、提示词）全量重跑，**指标回退就回滚**——评估进 CI（09 篇）变成自动门禁。本模块的验收产出——"升级前后对比表"（基线纯向量 vs 混合检索 vs 混合+重排，每档四项指标）——是简历项目里最硬的量化素材，务必保留真实数据；跑评估的成本提示：LLM-as-judge 一次评估 100 条约 3-10 美元，用 flash 级模型做 judge 即可（评估是开发期工具，不必用最贵的模型）。

## 7. 常见坑

**分块参数拍脑袋**：只改分块不跑评估——每档参数配一组指标，让数据选参数，不靠感觉。

**BM25 中文失效**：不分词直接喂——jieba 分词是必须步骤，测试用"缩写/术语"问题验证关键词路是否真的生效。

**重排器与检索器模型不匹配**：bge 家族 embedding 与 reranker 混用一般没问题（跨家族效果差）——同生态搭配最稳，换了 embedding 就重跑评估。

**候选集太小**：top_k=5 直接重排——召回不够，重排无米下锅；先召回 50 再精排 5。

**评估集污染**：评估问题出现在入库文档里（模型直接背诵）——评估集独立管理，不进知识库。

**指标看不懂**：跑完不看细节——逐条看失败样本（忠实度低是答案编造？上下文精度低是检索跑偏？），**失败样本分析才是优化方向的来源**。

> 🎯 **核心要点**：检索升级的主线是"**召回够多、精排够准、评估够硬**"——语义分块提结构、混合检索补盲区、重排序提精度、RAGAS 给尺子。四件套做完，你的 RAG 从"能检索"升级为"可度量、可优化、可辩护"，这是简历与面试深挖的核心竞争力。
