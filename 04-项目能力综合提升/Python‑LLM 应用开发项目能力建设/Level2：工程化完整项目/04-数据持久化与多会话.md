# 04 数据持久化与多会话

> Level1 的对话历史存在内存里，重启即失。本模块用 SQLModel + SQLite 落地三张表（会话、对话、文档），实现对话持久化与多会话隔离，为多轮记忆、文档管理、后续多用户打地基。

## 1. 目标与验收

本模块的产出：SQLite 数据库三张表（conversations/sessions、messages、documents），Repository 层 CRUD，对话历史落库与读取，会话隔离生效。验收标准：**对话后查库能看到消息记录**；**重启服务后同一会话能继续对话**（历史不丢）；**两个会话互不干扰**；**删除文档后库与向量库同步清理**。版本基线（2026-08）：SQLModel 0.0.38、SQLAlchemy 2.0.47、aiosqlite。技术选型说明：单机项目 SQLite 足够（零部署、文件即库），SQLModel 是 FastAPI 作者出品（Pydantic + SQLAlchemy 融合，与 schemas 天然联动）——迁移到 PostgreSQL 时只改 db_url 一行（Level3/双栈再动）；异步引擎是配套选择（FastAPI 事件循环内不阻塞），同步 SQLite 驱动会让异步接口整体卡顿。

## 2. 表设计：三表模型与关系

先想清楚"要持久化什么"，再建表。三个实体：**会话**（Session——一次对话的容器，记录创建时间与文档绑定）；**消息**（Message——每条 user/assistant 消息，属于某会话，有序）；**文档**（Document——上传的知识文档元数据，与其 Chroma 中的块对应）。

```text
Session 1 ──── N Message        （一个会话多条消息，按 created_at 排序）
Session N ──── M Document       （一个会话可绑定多份文档，多对多通过会话文档关联）
Document 1 ──── N chunk         （一份文档对应 Chroma 中多个块，按文档名前缀管理）
```

关系设计要点：**消息表是核心**（对话历史的唯一真相——RAG 注入的上下文每次现拼，不落库；落库的是"用户问过什么、模型答过什么"）；**文档表与 Chroma 靠文档名/id 关联**（Chroma 的 metadata 里存 document_id，删除文档时先删库记录再清向量块——两库一致性是 Level2 的一个真命题，简单方案：文档元数据在 SQLite、向量在 Chroma，操作按"先 SQLite 后 Chroma"顺序 + 日志兜底）。

## 3. SQLModel 建模与异步引擎

建模与引擎初始化：

```python
# app/repository/models.py
from datetime import datetime, timezone
from sqlmodel import Field, Relationship, SQLModel

class Session(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    session_key: str = Field(index=True, unique=True)   # 前端传入的 UUID
    title: str = "新对话"
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
    messages: list["Message"] = Relationship(back_populates="session")

class Message(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    session_id: int = Field(foreign_key="session.id", index=True)
    role: str                                          # user / assistant
    content: str = Field(max_length=20000)
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
    session: Session | None = Relationship(back_populates="messages")

class Document(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    name: str = Field(index=True)
    chunk_count: int = 0
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
```

```python
# app/repository/db.py
from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine
from sqlmodel import SQLModel, create_async_engine  # SQLModel 导出 async 引擎
from app.config import settings

engine = create_async_engine(settings.db_url, echo=False)
async def init_db() -> None:
    async with engine.begin() as conn:
        await conn.run_sync(SQLModel.metadata.create_all)   # 启动时建表

async def get_session() -> AsyncSession:      # FastAPI 依赖（03 篇）
    async with AsyncSession(engine, expire_on_commit=False) as session:
        yield session
```

三个要点：**session_key 唯一索引**（前端 UUID 是逻辑主键，内部 id 是物理主键——对外接口永远用 session_key，不暴露自增 id）；**Message 用外键 + 索引**（按会话查历史是最高频查询，session_id 索引必建）；**AsyncSession 依赖注入**（`get_session` 以 yield 形式做依赖，FastAPI 自动管理事务关闭）。

**字段与时区的两个细节**：created_at 统一存 UTC（`datetime.now(timezone.utc)`），展示时再转本地时区——混用本地时间会导致"对话顺序错乱"这类最难查的 bug；**外键级联策略**——删除会话时消息怎么办，显式选择（SQLModel 里 `ondelete="CASCADE"` 或应用层先删消息再删会话），不要留默认行为让人猜。这两个细节不在任何教程的醒目位置，但都是线上事故的高发点——**写进 09 篇的部署检查单**。

## 4. Repository 层：CRUD 与查询

Repository 层封装"数据怎么存取"，service 层只关心"业务怎么编排"：

```python
# app/repository/message_repo.py
from sqlmodel import select
from sqlalchemy.ext.asyncio import AsyncSession
from app.repository.models import Message, Session

async def get_or_create_session(db: AsyncSession, session_key: str) -> Session:
    stmt = select(Session).where(Session.session_key == session_key)
    session = (await db.execute(stmt)).scalar_one_or_none()
    if session is None:
        session = Session(session_key=session_key)
        db.add(session)
        await db.commit()
        await db.refresh(session)
    return session

async def get_recent_messages(db: AsyncSession, session_key: str,
                              limit: int = 20) -> list[Message]:
    stmt = (select(Message)
            .join(Session)
            .where(Session.session_key == session_key)
            .order_by(Message.created_at.desc())
            .limit(limit))
    rows = (await db.execute(stmt)).scalars().all()
    return list(reversed(rows))               # 倒序取后翻正序返回

async def save_message(db: AsyncSession, session_id: int, role: str, content: str) -> None:
    db.add(Message(session_id=session_id, role=role, content=content))
    await db.commit()
```

三个规范：**函数只做一件事**（get_or_create、get_recent、save 各自独立，测试好写）；**查询用 select() 表达式**（SQLModel 的 SQLAlchemy 风格，防注入）；**commit 在 Repository 内**（demo 期简单化；复杂事务场景 service 层用 db.begin() 控制边界）。**上下文裁剪的落库**：历史读取 limit=20 只是粗控，真正的上下文管理在 service 层（按 token 数裁剪后再拼 messages——Level1 03 篇的"历史裁剪"在这里正式实现）。

## 5. 与检索链路的配合：会话上下文

持久化后，在线链路的组装变成"三路输入"：**会话历史**（Repository 读库）＋ **检索结果**（rag 层）＋ **当前问题**（请求）。service 层编排：

```python
async def ask(db: AsyncSession, session_key: str, question: str) -> str:
    session = await get_or_create_session(db, session_key)
    history = await get_recent_messages(db, session_key, limit=10)
    context = await retrieve_top_k(question)          # 06 篇：混合检索 + 重排
    answer = await generate(history, context, question)  # 05 篇：LangGraph 编排
    await save_message(db, session.id, "user", question)
    await save_message(db, session.id, "assistant", answer)
    return answer
```

设计要点：**"先读后写"**（生成前读历史、生成后写消息——回答失败时不落库，前端重试不会产生重复消息）；**历史与上下文分离**（历史是事实、上下文是素材——模型看到的 messages 是两者拼装，绝不混淆）；**保存时机**（流式场景等完整回答落库，中途断流不落半截）。这个编排是 05 篇 LangGraph 图的"手工版"，图化后流程显式化、可打断、可观测。

**文档删除的一致性流程**（SQLite 与 Chroma 双库，最易出 bug 的地方）：删除文档要同时清两份数据——先删 SQLite 记录（元数据事实），再删 Chroma 中该文档的全部块（按 metadata 里的 document_id 过滤删除），任一步失败都要有日志兜底（08 篇的"删除失败"告警点）。删除流程的验证：删掉后重问该文档的问题，应答"未找到"（检索不到块）——这正是 06 篇负例测试的复用。**一致性方案的选择**：Level2 用"顺序操作 + 日志兜底"够用；双库事务（真正原子）是 Level3 或双栈项目的话题，记录在文档里作为已知边界。

## 6. 示例查询与数据管理

数据层的"能查"和"能管"同样重要：**巡检查询**（看项目跑起来后的真实数据）与**初始化脚本**（开发环境一键造数）。三个常用查询示例：

```python
# scripts/inspect_db.py —— 数据巡检脚本（08 篇指标联动）
async def inspect() -> None:
    async with AsyncSession(engine) as db:
        sessions = (await db.execute(select(Session))).scalars().all()
        messages = (await db.execute(select(Message))).scalars().all()
        docs = (await db.execute(select(Document))).scalars().all()
        print(f"会话 {len(sessions)} / 消息 {len(messages)} / 文档 {len(docs)}")
        # 每个会话的平均消息数（对话是否健康）
        for s in sessions:
            n = sum(1 for m in messages if m.session_id == s.id)
            print(f"  {s.session_key}: {n} 条消息")
```

巡检的价值：**对话量、每会话深度、文档数量**是项目"有没有人用"的证据——面试讲"上线后的数据观察"时，这些数字就是素材。初始化脚本（scripts/seed.py）：造 2-3 个测试会话与若干消息，开发调试时省去手工造数。**数据备份**：SQLite 就是单文件（cp 即备份，09 篇挂卷后连文件一起备份）；Chroma 目录同理。数据层的管理动作（巡检/备份/清理）都写成 scripts/ 下的脚本，不手工敲——**能脚本化的操作绝不手做**是数据安全的第一条纪律。

## 7. 常见坑

**async 引擎忘装驱动**：`sqlite+aiosqlite://` 需要 `uv add aiosqlite`——连接报错先查驱动。

**启动时表没建**：init_db() 要在 main.py 的 lifespan 里调用（FastAPI 启动事件），不是每次请求建表。

**会话数据互相串**：session_key 传错/为空——接口层必填校验（03 篇 Field），前端生成 UUID 一次、全程复用。

**历史乱序**：order_by(created_at) 在同毫秒内不稳定——加 id 作为次级排序键（created_at, id）。

**内存占用**：历史越读越长——get_recent_messages 的 limit 是保护，service 层再按 token 数裁剪，双保险。

**SQLite 并发写锁**：单机单进程一般没事；多 worker 部署（09 篇）会偶发 "database is locked"——WAL 模式（`PRAGMA journal_mode=WAL`）开启即可。

**数据迁移需求出现**：加了字段或新表——Level2 用"启动时 create_all + 字段带默认值"的轻量方案（建表幂等，老库自动补列；删列/改类型这类破坏性变更直接备份后重建，数据量小可承受）；正式迁移工具（Alembic）在 Level3 数据量上来后引入——**把"现在不引入 Alembic"的理由记进文档**，避免以后为追架构债而自我怀疑。

**备份与恢复演练**：数据是项目的资产——备份脚本（cp data 目录 + 日期戳）放进 scripts/，并**实际演练一次恢复**（删库 → 恢复 → 对话历史还在）。没演练过的备份等于没有备份。备份时机建议：每次重大改动前备份 + 每日巡检时顺手备份（08 篇的巡检联动），恢复演练至少做一次——"能恢复"与"以为能恢复"之间隔着一场演练。备份是数据层的最后一道防线，写进 09 篇部署检查单。

> 🎯 **核心要点**：持久化的本质是**让对话成为数据而非状态**——会话、消息、文档三表落库后，重启不丢、多会话隔离、历史可查可裁剪。数据层的三张表，就是项目从"演示"走向"产品"的证据。
