## 1. 目标与验收

本模块的产出：Dockerfile + docker-compose.yml + .env.prod 样例 + CI 配置（GitHub Actions），`docker compose up -d` 一键启动，`curl /health` 返回健康。验收标准：**全新机器上按 README 三步（clone、配密钥、compose up）能跑起服务**；**日志与数据持久化到宿主机（重启容器不丢）**；**能讲清镜像分层、数据卷、健康检查三个概念**。版本基线（2026-08）：Docker Compose v5（version 字段已废弃，直接用最新语法）、Uvicorn 0.51 多 worker、GitHub Actions（仓库「CI CD灰度发布」体系配套）。

## 2. 部署目标与形态

部署目标一句话：**任何机器（本地/服务器）一条命令跑起完整服务**。形态设计：**两个容器**——api（FastAPI + Uvicorn）与 client（Streamlit 演示界面），通过 docker network 内网互通；**三个数据卷**——SQLite 数据、Chroma 向量库、日志目录（挂载宿主机目录，容器重建不丢）；**环境变量注入**——API Key 等敏感配置不进镜像，运行时从宿主机 .env 注入（02 篇的配置三态在此收口为 prod 态）。镜像大小与安全的基本线：**非 root 用户运行**、**依赖锁定（uv.lock 同步安装）**、**Python 3.14 slim 基础镜像**。

## 3. Dockerfile：镜像构建规范

Dockerfile 的三个关键设计：**多阶段构建**（构建依赖与运行依赖分离，镜像瘦身）、**依赖缓存分层**（uv.lock 先拷先装，源码改动不触发依赖层重建——构建加速的收益在 CI 里被反复放大）、**非 root 运行**（安全基线）：

```dockerfile
# Dockerfile —— 多阶段构建
FROM python:3.14-slim AS base
ENV PYTHONUNBUFFERED=1 PIP_NO_CACHE_DIR=1
WORKDIR /app

# 阶段一：安装依赖（先装依赖再拷源码 → 缓存分层）
FROM base AS deps
COPY uv.lock pyproject.toml ./
RUN pip install uv && uv sync --frozen --no-dev --no-editable

# 阶段二：运行镜像
FROM base AS runtime
COPY --from=deps /app/.venv /app/.venv
COPY app/ app/
COPY scripts/ scripts/
RUN useradd -m appuser && chown -R appuser:appuser /app
USER appuser
EXPOSE 8000
CMD ["/app/.venv/bin/uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "2"]
```

三个细节：**`uv sync --frozen`**（严格按 uv.lock 装，版本漂移杜绝）；**`--no-editable`**（可编辑安装只在开发有用，镜像里要纯副本）；**CMD 用 .venv 内绝对路径**（环境变量 PATH 不可靠）。**Uvicorn workers=2**（单机多进程：SQLite 并发写需 WAL 模式（04 篇）、日志与指标在进程间独立（08 篇的内存指标此时失效——这是"单进程埋点"方案在多 worker 下的已知边界，记录在文档，Level3 换外部存储）。

**.dockerignore 是安全第一关**（防密钥进镜像的物理屏障）：

```text
# .dockerignore
.env
data/
logs/
tests/
.git/
__pycache__/
*.pyc
.venv/
```

四条必写：**.env**（密钥）、**data/**（用户数据与 Chroma——镜像里不该有运行数据）、**tests/**（测试不进生产镜像，体积与安全双赢）、**.git/**（历史泄漏风险）。检查方法：`docker build` 后 `docker run ... ls /app` 确认没有 .env——**这个验证进上线检查单**。

## 4. docker-compose：一键编排

compose 编排两个服务 + 卷 + 网络（Compose v5 语法，无 version 字段）：

```yaml
# docker-compose.yml
services:
  api:
    build: .
    env_file: .env                    # 宿主机 .env 注入密钥与配置
    volumes:
      - ./data:/app/data              # SQLite + Chroma 持久化
      - ./logs:/app/logs
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
    ports: ["8000:8000"]
    restart: unless-stopped

  client:
    image: python:3.14-slim
    command: sh -c "pip install -q streamlit && streamlit run /app/client/app.py"
    volumes:
      - ./client:/app/client
    depends_on:
      api:
        condition: service_healthy     # 等 API 健康后再启动界面
    ports: ["8501:8501"]

volumes: {}
```

设计要点：**env_file 注入 .env**（.env 在宿主机、不进镜像、不入 Git——README 写清从 .env.example 复制）；**healthcheck + depends_on 联动**（界面等服务健康再起，启动时序可控）；**restart: unless-stopped**（崩溃自动拉起，宕机自愈的第一步）。**启动验证**：`docker compose up -d` → `docker compose ps`（两服务 healthy）→ `curl localhost:8000/health`（200）→ 浏览器开 8501 对话。

## 5. 健康检查与优雅停止

健康检查（healthcheck）与优雅停止是"可运维"的底线：**健康检查**——/health 接口不只要返回 200，要**真正检查依赖**（数据库能连、Chroma 能查：`GET /health` 内部跑 `SELECT 1` 与一次 Chroma count，失败返回 503）——"假健康"（容器活着但服务废了）是最坑的运维事故；**优雅停止**——Uvicorn 默认处理 SIGTERM 时停止接收新请求、等处理中请求完成再退出（timeout_graceful_shutdown 参数控制等待时间）；**日志输出到 stdout + 文件双写**（容器日志 docker logs 可查、宿主机 logs/ 目录留档——08 篇的结构化日志直接进 JSON 文件，接日志平台零改造）。

上线检查单（部署前的最后一遍）：镜像构建成功且大小合理；compose up 两服务 healthy；健康检查能真实反映故障（人为停数据库，/health 应变 503）；数据卷挂载正确（重启容器数据仍在）；日志有输出且带 trace_id；密钥在宿主机 .env 而非镜像内；**故障演练**（部署完的必做动作）——`docker compose stop api` 再 `up -d`，观察重启后数据是否完整、服务是否自动恢复（restart 策略生效），演练一次比读十遍文档有用——"**部署的验收是重启不丢、故障能起**"。

## 6. CI 流水线：测试 → 镜像 → 发布

CI 把"机器验证"自动化（GitHub Actions，仓库「CI CD灰度发布」体系有全景）：**push 触发 → 三步流水线**——① 质量门禁（ruff + mypy + pytest，07 篇的门禁在此强制执行，含覆盖率红线）；② 构建镜像（Docker build，缓存加速）；③ 发布（推镜像到镜像仓库（Docker Hub/Harbor），打版本 tag）。核心 yaml 骨架：

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy app/
      - run: uv run pytest          # 覆盖率门禁在 addopts 里
  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t ${{ secrets.REGISTRY }}/kbqa:${{ github.sha }} .
      - run: docker push ${{ secrets.REGISTRY }}/kbqa:${{ github.sha }}
```

CI 的三个价值：**门禁不可绕过**（本地可跳过的检查在 CI 强制）；**测试无密钥可跑**（mock 到位的测试在 CI 全绿——07 篇"不依赖真实 Key"的硬要求在 CI 兑现）；**镜像可追溯**（tag 绑 commit，线上出问题回滚到指定 commit 的镜像——发布即 Git 回退的 GitOps 雏形，深挖见「CI CD灰度发布」体系）。

**回滚流程与部署文档**：回滚是部署的一部分，不是事故才想的事——**回滚三分钟**：`docker compose down && 切回上一个镜像 tag && docker compose up -d`（数据卷不动，SQLite/Chroma 天然保留——"数据与代码分离"设计的收益在此兑现）。部署文档（README 的 Deploy 节）写清四件事：**前置条件**（Docker 版本、网络要求）；**三步启动**（clone → 配 .env → compose up）；**验证步骤**（curl /health、开 8501 对话）；**故障排查**（容器起不来/健康检查红/连不上模型——每个现象一条排查路径，09 篇的坑全在这里）。**"文档能让人 15 分钟复现部署"是部署交付的验收线**——和 Level1 的环境复现是同一个标准。

## 7. 常见坑

**镜像里缺文件**：.dockerignore 忘配，把 .env/data 打进镜像——.dockerignore 必写（.env、data/、tests/、.git），密钥泄漏是 P0 事故。

**端口冲突**：8501/8000 被占——compose 里改端口映射，README 记录。

**容器内连不上宿主机资源**：模型/向量库在容器内路径——统一挂载 data 卷，代码里路径全部相对 /app/data（配置项管理，02 篇）。

**healthcheck 用了镜像里没有的 curl**：python:slim 无 curl——用 python -c urllib 请求 /health 或镜像里装 curl。

**启动顺序问题**：api 没就绪 client 就启动——depends_on + service_healthy（第 4 节），不要 sleep 硬等。

**多 worker 的本地内存指标失真**：metrics 进程隔离——文档记录边界，/metrics 聚合靠 Level3 外部存储。

**uv sync --frozen 报 lock 不一致**：uv.lock 与 pyproject.toml 不同步——本地 uv sync 先跑一遍，lock 提交后 CI 只读。

**容器时间与宿主机不一致**：日志时间戳错乱（容器默认 UTC）——compose 里 `environment: - TZ=Asia/Shanghai`，与 04 篇"库内存 UTC、展示转本地"的约定配套，排查时避免"时间对不上"的假线索。

**磁盘与日志无限增长**：日志文件与数据卷不设上限——logs/ 挂载 + 日志轮转（按大小/天数切割，08 篇的日志配置加 RotatingFileHandler），数据目录定期巡检（04 篇巡检脚本），磁盘告警进指标（08 篇）。

**服务器防火墙**：端口映射配了但外部访问不通——检查宿主防火墙 8000/8501 放行；只对内网演示就保持不开放（安全优先，10 篇基线）。

**部署文档与实际不符**：README 里写的步骤已经失效（改了端口/加了依赖）——每次部署变更同步更新文档，CI 里加"文档中命令可执行"的检查（把 README 的启动命令抽成脚本，CI 跑脚本验证）；**文档漂移比没有文档更危险**——它让人"照文档做还失败"，直接摧毁对项目的信任。部署文档是项目"可交接"的最后一环——10 篇毕业时，文档与代码一起交付。

> 🎯 **核心要点**：部署交付的本质是**把"项目"变成"产品"**——Docker 化保证任意机器可跑、compose 保证一键起、健康检查保证真健康、CI 保证改动不破坏。能部署的代码才叫交付，这一篇做完，你的简历项目具备了"上线"的全部能力。
