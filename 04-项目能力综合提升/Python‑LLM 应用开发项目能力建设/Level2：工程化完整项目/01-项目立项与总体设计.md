# 01 项目立项与总体设计

> 工程化的第一步不是写代码，是**定边界**：这个项目做什么、不做什么、用什么技术、长什么样。本模块产出立项文档（需求拆解、技术选型决策树、架构图、里程碑），它是后续所有模块的地基。

## 1. 目标与验收

本模块的产出：项目根目录的 `docs/01-立项.md`，包含项目定位、需求清单、选型决策记录、架构图、里程碑表。验收标准：**能向陌生人用 3 句话讲清项目是什么**（一句话定位 + 主要功能 + 技术亮点）；**每个选型决定都能说出"为什么是这个、换什么更好"**（选型决策树是面试深挖第一问）；**架构图能徒手画出数据流**。立项文档不是形式主义——它是后续每篇的"需求来源"：哪个模块做什么功能，回立项文档找答案，防止边写边加需求导致项目失控。

## 2. 项目定位：一句话与五层需求

项目一句话定位：**"企业知识库问答助手——上传文档建知识库，用自然语言问问题，答案可溯源、对话有记忆"**。这句话拆出三个核心能力：文档知识问答（RAG）、多轮对话记忆（持久化）、答案可溯源（引用标注）。

需求拆解用五层结构，每层对应后续一个或多个模块：

| 层 | 需求 | 对应模块 |
|---|---|---|
| 界面层 | 对话界面、文档上传、引用展示 | Streamlit（复用 Level1 05） |
| 服务层 | 对话 API、流式输出、错误处理 | 03 FastAPI |
| 数据层 | 对话历史、文档元数据、用户/会话 | 04 持久化 |
| 能力层 | RAG 链路、工具调用、检索优化 | 05 框架化、06 检索升级 |
| 工程层 | 测试、日志、部署、安全 | 07/08/09/10 |

**明确的非需求**（划清边界，防止范围膨胀）：不做前端工程化（用 Streamlit 演示即可，Level3 或双栈再上正式前端）；不做微服务（单服务部署，Level3 加高并发）；不做用户注册登录体系（单用户 + 会话隔离，Level3 加多租户）。**写"不做什么"和"做什么"同样重要**——面试问"为什么不做多用户"时，"立项时定位单用户 MVP，多用户是 Level3 演进"是清晰的产品思维答案。

## 3. 技术选型决策树

选型的原则是**每个选择都有对比和理由**，记录成表格进立项文档：

| 技术点 | 选型 | 备选与弃用理由 |
|---|---|---|
| Web 框架 | FastAPI 0.139 | Flask（同步、无 Pydantic 原生校验）；Django（太重） |
| 数据校验 | Pydantic 2.13 | FastAPI 原生集成，dataclass 的升级替代 |
| 数据库 | SQLite + SQLModel | 单机零部署；MySQL/PostgreSQL 留待 Level3 或双栈 |
| 向量库 | Chroma（升级持久化） | Milvus/ES 部署成本高，Level3 再演进 |
| 编排框架 | LangGraph | 手写循环已懂原理（Level1 07），框架接管状态与重试 |
| 检索 | 混合检索 + 重排序 | 纯向量检索有术语盲区，2026 基线做法（06 篇详述） |
| 评估 | RAGAS | 开源、四项核心指标、LLM-as-judge |
| 部署 | Docker Compose | 单机一键启动，K8s 留待 Level3 |

两个选型原则：**先满足当前需求再考虑扩展**（SQLite 够用就不上 MySQL，"能用但差点"比"大而全"更符合简历项目定位）；**选型决策要可辩护**（每个"弃用"都有一句话理由——面试官最反感"大家都用所以我也用"）。第三个原则是**版本锚定**：每个技术点记录选用版本与日期（如 FastAPI 0.139 / 2026-08），AI 生态演进快，锚定版本让决策可复现、可升级——也顺带满足"文档时效性"的知识库惯例。

## 4. 系统架构图与数据流

架构图（立项文档里用 ASCII 图，后续所有模块对照它）：

```text
┌─────────────┐     ┌──────────────────┐     ┌──────────────┐
│ Streamlit   │HTTP │ FastAPI 服务      │     │ 能力层        │
│ 对话/上传 UI │────▶│ 路由/校验/SSE    │────▶│ LangGraph    │
└─────────────┘     │ 依赖注入/错误契约 │     │  RAG+工具编排 │
                    └───────┬──────────┘     └──────┬───────┘
                            │                       │
                    ┌───────▼──────────┐    ┌───────▼───────┐
                    │ 数据层           │    │ 检索层        │
                    │ SQLite(SQLModel) │    │ Chroma+BM25  │
                    │ 对话/文档/会话   │    │ +重排序       │
                    └──────────────────┘    └───────────────┘
```

数据流两条（与 Level1 08 一致，但每步都有工程化改造）：**离线链路**——上传文档 → 语义分块（06 升级）→ 向量化 + BM25 索引 → 入库 Chroma；**在线链路**——提问 → 会话上下文读取（04）→ LangGraph 编排（05）→ 混合检索 + 重排序（06）→ 注入生成 → 流式返回（03）→ 对话落库（04）。**改动说明**：相比 Level1，新增了持久化（对话不再丢）、编排层（流程显式化）、检索升级（质量可度量）——这就是"工程化"的全部含义：每个环节从"能跑"到"可靠、可测、可度量"。**架构图的维护纪律**：每篇实现后回来核对架构图，实现与图不符时改的是实现不是图——图是契约，实现是履约。架构图也是面试讲解的第一张图——**讲项目先从图讲起**，再展开到每个模块，比从代码讲起清晰十倍。

## 5. 里程碑规划与风险

把 3-4 周拆成五个里程碑，每个里程碑有明确的"完成标志"（机器可验证）：

| 里程碑 | 内容 | 完成标志 |
|---|---|---|
| M1（第 1 周） | 02-04：工程骨架 + FastAPI + 持久化 | 接口测试通过、对话可落库 |
| M2（第 1-2 周） | 05-06：LangGraph 编排 + 检索升级 | 评估集跑通、指标对比表产出 |
| M3（第 2-3 周） | 07-08：测试体系 + 可观测 | 覆盖率 ≥ 70%、日志链路完整 |
| M4（第 3 周） | 09：Docker 部署 | compose 一键启动、健康检查通过 |
| M5（第 3-4 周） | 10：安全、性能、答辩素材 | 毕业检查单全勾 |

风险清单（立项时就写，遇险不慌）：**检索质量不达标**（评估集提前建，06 篇的升级路径就是应急预案）；**依赖生态变动**（uv.lock 锁定版本，LangChain 版本线在 05 篇校准）；**时间超支**（每篇的"验证"都是硬性交付物，不做完不进入下一篇）；**模型服务不可用**（DeepSeek 2026-08 预告价格调整与高峰加价——配置里模型名/端点可切换（02 篇配置管理），万一官方波动可快速换兼容服务商，测试用 mock 不受影响）。里程碑的价值：**卡住时知道整个项目没崩，只是某一步慢**——按里程碑汇报进度，也是简历项目"过程管理"素材。

单人开发与团队协作的差异也要在立项时想清楚（面试常问"你怎么规划项目"）：单人项目**里程碑就是自审点**（每篇验收即自审），文档比代码重要（几周后回看的只有文档）；如果有协作（课设/实习小组），立项文档升级为**接口契约文档**（03 篇的 API 定义先行，两边并行开发不冲突）。本层按单人节奏设计，但文档规范按"可交接"标准写——**"如果明天把项目交给别人，他能接住吗"是文档质量的检验题**。

## 6. 常见坑

**立项文档写了不用**：文档和代码脱节——每篇开工前先读立项，改需求先改文档，保持"文档即真相"。

**选型过度**：为了简历好看上 Milvus、Redis、Kafka——Level2 单机项目用不上就是负债（部署复杂、面试解释不清），加分项留给 Level3，那里才是它们的舞台。

**需求膨胀**：边做边加功能（"顺便加个网页搜索""顺便支持图片"）——每个新需求先问"属于哪个里程碑"，不属于就进 backlog，项目完成后再评估。

**架构图与实现不一致**：实现偏离架构（比如把检索逻辑写进路由层）——03 篇的分层规范就是为了锁住架构，发现偏差立即纠正，不要让偏差积累成"两层设计"。

> 🎯 **核心要点**：立项文档是项目的"宪法"——定位定方向、选型定技术、架构定结构、里程碑定节奏。写完这份文档，整个 Level2 的施工图就画完了，后续每篇都是按图施工。
