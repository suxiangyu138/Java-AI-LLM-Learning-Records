## 1. 目标与验收

本模块的产出：统一的日志模块（JSON 结构化 + trace_id 注入）、请求中间件（自动生成/传递 trace_id）、关键指标埋点（请求量/延迟/错误率/LLM 调用量与费用）、一个告警脚本（或规则配置）。验收标准：**一个对话请求的完整调用链能在日志里按 trace_id 串起来**；**能看到每个请求的耗时与 LLM token 消耗**；**能说清"日志、追踪、指标"各自回答什么问题**。版本基线（2026-08）：Python 标准 logging + structlog 风格（Demo 级用 json 格式器即可）、OpenTelemetry（行业标准，Alloy/Prometheus 生态配套）。

## 2. 可观测性三支柱与项目现状

可观测性三支柱：**日志**（Logs——发生了什么，逐条事件，最细粒度）；**追踪**（Traces——一次请求跨了哪些步骤，链路关系，耗时分布）；**指标**（Metrics——系统整体状态，聚合数值，阈值告警）。三者的关系：**指标报警 → 追踪定位 → 日志细节**——告警告诉你"坏了"，追踪告诉你"坏在哪条链"，日志告诉你"具体什么错"。Level1 的 logging 是"日志"的雏形（还没有结构化与追踪），本模块补全三支柱——对一个单服务项目，**轻量方案完全够**：结构化日志 + trace_id 手工贯穿 + 指标埋点，不上完整 OTel 后端（Level3 再上 Prometheus/Grafana 全家桶），但**埋点口径按 OTel 标准来**（后续迁移零成本）。

## 3. 结构化日志：从 print 到 JSON 行

日志的工程化标准是**结构化**：每行日志是一个 JSON 对象（字段可检索、可聚合），而不是一串拼好的文本：

```python
# app/core/logging.py
import json, logging, uuid

class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        entry = {
            "ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S"),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
            "trace_id": getattr(record, "trace_id", None),   # 中间件注入
        }
        if record.exc_info:
            entry["exc"] = self.formatException(record.exc_info)
        return json.dumps(entry, ensure_ascii=False)

def setup_logging(level: str = "INFO") -> None:
    handler = logging.StreamHandler()
    handler.setFormatter(JsonFormatter())
    logging.basicConfig(level=level, handlers=[handler], force=True)

def log_extra(trace_id: str, **extra) -> dict:  # 业务字段挂载辅助
    return {"extra": {"trace_id": trace_id, **extra}}
```

三条铁律：**JSON 一行一事件**（可被日志平台直接吃，Level3 接 EFK/Loki 零改造）；**关键字段进结构化字段**（msg 只放"发生了什么"，trace_id/耗时/token 数放字段——检索"trace_id=abc 的所有日志"是排错第一步）；**日志分级有纪律**（INFO 记流程、WARNING 记可恢复异常、ERROR 记需人工介入——全 INFO 等于没日志，全 ERROR 等于噪音）。

## 4. 链路追踪：trace_id 贯穿请求

一次对话请求的完整链路：HTTP 入口 → 校验 → 会话读取 → 检索 → 重排 → 模型调用 → 工具执行 → 落库 → 流式返回。**trace_id 贯穿全链**，任何一环出问题都能按 ID 串出整条链。实现（中间件生成 + 日志携带 + 业务透传）：

```python
# app/core/middleware.py —— trace_id 中间件（与请求日志合并，一次穿越两个需求）
import time, uuid, logging
from starlette.middleware.base import BaseHTTPMiddleware

log = logging.getLogger("http")

class TraceIdMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        trace_id = request.headers.get("X-Trace-Id") or uuid.uuid4().hex[:16]
        request.state.trace_id = trace_id
        start = time.perf_counter()
        response = await call_next(request)
        log.info("请求完成", extra={
            "trace_id": trace_id,
            "method": request.method,
            "path": request.url.path,
            "status": response.status_code,
            "latency_ms": round((time.perf_counter() - start) * 1000, 1),
        })
        response.headers["X-Trace-Id"] = trace_id   # 回传，前端可留痕
        return response
```

**请求日志是每个请求的"自动留痕"**——方法、路径、状态码、耗时四字段让"哪个接口慢了、哪个接口报错了"直接可见，配合 trace_id 五分钟内定位任意一次慢请求。这两件套（trace_id + 请求日志）是单服务项目可观测性的最小完整形态，务必最先落地。

```python
# 业务日志携带 trace_id：通过请求上下文获取
def current_trace_id(request: Request) -> str:
    return request.state.trace_id

log.info("LLM 调用完成", extra={"trace_id": current_trace_id(request),
                               "model": settings.model_name, "tokens": usage.total_tokens})
```

两个进阶点：**SSE 长流式的追踪**——流式响应的耗时统计在流结束后打（一个 chunk 一个日志会刷屏）；**LangGraph 节点的链路整合**——05 篇的节点日志带上同一 trace_id（图节点是链路的天然分段点，恰好是排错分水岭）。排查流程演示：告警说错误率升 → 挑一个失败请求的 trace_id → grep 出它的检索日志与模型调用日志 → 定位是模型超时还是检索空结果。

## 5. 指标与告警：用数据看系统

指标是"聚合的数值"：请求量（QPS）、延迟（P50/P95/P99）、错误率（5xx 占比）、LLM 调用量/费用。轻量实现：自定义 Metrics 模块 + 每请求埋点 + /metrics 接口输出（Prometheus 格式，Level3 直接接采集器）：

```python
# app/core/metrics.py —— 内存指标收集（单进程够用）
from collections import Counter
import time

class Metrics:
    def __init__(self):
        self.requests = Counter()          # 按状态码计数
        self.latencies: list[float] = []   # 近窗口耗时（简单方案）
        self.llm_calls = 0
        self.llm_tokens_in = 0
        self.llm_tokens_out = 0
        self.llm_cost_cny = 0.0            # 按单价折算（03 篇 usage）

metrics = Metrics()

def record_request(status: int, latency_ms: float) -> None:
    metrics.requests[status] += 1
    metrics.latencies.append(latency_ms)
```

告警的门槛值（2026 基线）：**P95 延迟 > 5s**（模型慢或检索退化）；**5xx 占比 > 1%**（故障阈值）；**错误率 24h 环比上升 > 50%**（回退信号）；**LLM 费用日增长 > 20%**（成本失控信号）。告警规则写进 docs/，脚本或平台触发后按"trace_id 排查流程"走。**告警的意义不是发通知，是触发动作**——每条告警对应一个已知的排查路径（文档化），没有排查路径的告警是噪音。

## 6. 成本监控：AI 应用的专项

AI 应用比传统应用多一个监控维度：**钱**。每次 LLM 调用的 token 消耗与费用（03 篇的 usage 字段在这里派上大用场）必须记账：**调用点埋点**（每次 create 后记录 model/输入 token/输出 token/耗时/估算费用）；**按会话聚合**（哪个会话烧钱多——长对话历史未裁剪的迹象）；**按天聚合**（日成本曲线，超阈值告警）。实现就三行埋点 + 一张 SQLite 表（04 篇的基建直接复用：llm_calls 表），但它是 AI 项目的"保命项"——**不加成本监控的项目，一次失控的提示词循环（工具反复调用）就能烧掉一整个月的预算**（Level1 07 的 max_iterations 上限在服务层要设为硬约束）。成本监控的三个观察点：**单次调用费用异常**（突然变贵——上下文暴涨？）；**单会话累计费用异常**（历史未裁剪？）；**每日总额趋势**（环比上升超 20% 告警）。费用单价是配置项不是魔法数字——模型调价（2026-08 DeepSeek 已预告）只改配置不改代码。

## 7. 常见坑

**日志只记不查**：日志写了没人看——本模块验收要"用 trace_id 实际排查一次故障"（自己人为制造一次错误再定位），查得动才算可观测。

**trace_id 断了**：中间件注入但业务代码忘了带——日志字段统一从请求上下文取，测试里断言"关键日志都带 trace_id"。

**指标口径漂移**：耗时统计含排队不含排队、错误含 4xx 不含 4xx——口径写进文档，测试锁口径（固定输入断言耗时区间）。

**敏感信息进日志**：把完整对话/Key 打进日志——脱敏规则（用户内容截断、Key 只记前 4 位），泄漏事故在简历上是最差的故事。

**流式日志刷屏**：每 chunk 一日志——按请求汇总打（流结束后一条，含总耗时/总 token）。

**告警疲劳**：阈值太低天天响——从"观察两周的真实分布"定阈值，先建基线再设告警。

**指标只埋不读**：埋了点但没人看——每个指标配一个"谁在什么场景看"的说明（写进 docs/ 指标说明表），指标的意义是触发决策，不是躺在代码里。

**日志与指标不一致**：日志记录的请求数 ≠ 指标计数（口径漂移）——统一从同一中间件取数（请求日志与请求指标在同一个 dispatch 里记录），测试锁口径。

**可观测性也要防泄漏**：日志与指标里混入用户对话原文会变成隐私事故——日志脱敏规则（内容截断到前 N 字、Key 掩码）写进统一封装，埋点一律走封装函数，不裸打 request body。

> 🎯 **核心要点**：可观测性的本质是**让系统的每一次行为都可回放**——结构化日志留痕、trace_id 串链、指标给状态、费用给成本。四件套齐了，你的项目从"跑着"变成"被理解地跑着"，排错从"猜"变成"查"，这是工程化最直观的体验跃迁。
