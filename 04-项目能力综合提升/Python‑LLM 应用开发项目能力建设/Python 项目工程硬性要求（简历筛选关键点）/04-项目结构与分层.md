# 04 项目结构与分层

> 第四项硬性要求：**项目结构有没有设计感**——目录分层清晰、依赖方向单向、模块职责单一。筛选者看仓库的目录树（3 秒）判断"这是组织过的工程还是堆出来的代码"，面试官深挖时按层追问——结构是项目的第一张地图。

## 1. 筛选者看什么

面试官打开仓库的目录树（3 秒判定）：**根目录是否整洁**（一堆 `main.py`、`test1.py`、`final2.py` 平铺 = 作业味；`app/`、`tests/`、`docs/`、`scripts/` 分层 = 工程味）；**结构是否有逻辑**（API 层、服务层、数据层分目录 = 有架构意识；全部塞在一个文件 = 脚本升级版）；**AI 项目特有的观察点**（检索、编排、提示词是否有独立模块——AI 代码与业务代码混在一起 = 没有设计）。**深挖时的路径**：面试官按结构追问——"你的检索逻辑在哪""测试怎么组织的""部署配置在哪"——**结构清晰的项目，每个问题都有明确的答案位置**；结构混乱的项目，深挖时会"找半天说不清"。**结构的本质是"项目的第一张地图"**——地图画得清，探索者（面试官）才有信心深入。

## 2. 硬性标准：分层清晰、单向依赖

项目结构的硬性标准三条：**分层清晰**（按职责分层——API/服务/数据/AI 能力各自成目录，Level2 02 的架构已实践）；**单向依赖**（上层依赖下层，禁止反向——API 层不能 import 数据层细节、AI 能力层不依赖 FastAPI——Level2 02 的"三条铁律"）；**边界可讲**（每层职责一句话能讲清——"API 层管 HTTP 契约、服务层管业务编排、数据层管存取"——**分层不是目录分类，是职责契约**）。**衡量方法**：**目录树自检**（3 秒看根目录——8 个以内的顶层目录、每个目录名表意）；**依赖方向检查**（工具 `import-linter` 或 code review 时盯"反向 import"）；**职责追问**（随机指一个文件，3 句话讲清它属于哪层、做什么——讲不清就是职责不清）。

## 3. 标准目录形态：分层架构

2026 年 Python AI 项目的标准目录形态（Level2 02 的完整版，这里列筛选者眼中的"标准答案"）：

```text
项目根/
├── app/                      # 应用主体（分层核心）
│   ├── main.py               # 入口：创建应用、挂路由、lifespan
│   ├── config.py             # 配置模型（pydantic-settings）
│   ├── api/                  # 路由层：HTTP 契约
│   ├── schemas.py            # 请求/响应模型
│   ├── services/             # 业务层：编排
│   ├── rag/                  # AI 能力层：检索/生成/编排图
│   ├── repository/           # 数据层：模型与 CRUD
│   └── core/                 # 基础设施：日志/异常/指标
├── tests/                    # 测试（与 app/ 同构）
├── scripts/                  # 运维脚本：巡检/迁移/压测
├── docs/                     # 文档：立项/调优/部署/答辩
├── data/                     # 运行数据（不提交）
├── pyproject.toml            # 项目清单
├── uv.lock                   # 依赖锁定
├── README.md                 # 门面
└── .env.example              # 配置模板
```

**筛选者视角的标准答案特征**：根目录 ≤ 8 个顶层条目、`app/` 内部按层分目录、`tests/` 与 `app/` 同构（找测试顺着结构走）、docs/ 存在（有文档意识）——**这个形态本身就在说"我懂分层"**，不需要任何解释。

## 4. 依赖方向：单向的纪律

分层的灵魂是**依赖方向单向**（Level2 02 的"三条铁律"在筛选视角的强化）：**api → services → repository/rag**，禁止：**反向**（repository 里 import api 的 schema——下层知道上层的存在 = 分层破裂）；**跳层**（api 直接操作数据库——绕过 service 的业务规则）；**循环**（a import b、b import a——Python 的循环导入是结构混乱的显性症状）。**违反的代价**（筛选者视角的深挖后果）：面试官问"改一个字段要动几个文件"——分层正确的项目"改 schema + 对应 service + 测试"三处；混乱的项目"到处都要动还怕漏"——**"改动的影响范围"是分层质量的量化指标**。**检查方法**：`import-linter` 配置层间规则（CI 里强制——Level2 02 已提）；人工检查——新代码 review 时问"这个 import 方向对吗"。**AI 项目的特殊纪律**：rag 层（检索/编排）是纯业务逻辑，不依赖 FastAPI/Streamlit——**"AI 能力与 Web 框架解耦"**是 2026 年 AI 项目的分层红线（可独立测试、可迁移框架，Level2 02 已实践）。

## 5. 模块职责：一个文件一件事

目录之下是文件的职责纪律：**一个文件一件事**（`chat_service.py` 只管对话编排，不顺便写日志格式——职责单一的文件改名、复用、测试都容易）；**文件大小有界**（超过 300-400 行就该拆——拆不动说明职责混杂；AI 项目里"prompt 拼接 + 检索 + 模型调用"写在一个文件是常见病，按层拆开）；**模块命名表意**（文件名即职责说明——`retrieve.py`、`ingest.py`、`graph.py`——Level2 02 的命名规范）；**内部函数组织**（公开函数在上、私有辅助在下（`_` 前缀）——读文件从上到下的顺序就是理解路径）。**"一个文件一件事"的检验**：文件改名测试（"这个文件改名成另一个名字，还贴切吗"——不贴切说明职责混杂）；删除测试（"删掉这个文件，影响是否局部"——连锁崩说明耦合过深）。

**结构反例对照**（筛选者眼中"作业味"的典型形态，自查时对照排除）：**单文件巨兽**（一个 main.py 两千行——检索、对话、存储全在里面——"能跑但没法维护"）；**平铺目录**（根目录 20 个文件无子目录——"所有代码平等"= 没有设计）；**双胞胎目录**（utils/ 与 helper/ 并存——职责重叠是结构没想清楚的症状）；**空壳分层**（目录分了但互相 import 混乱——分层是"规则"不是"文件夹"，单向依赖不守就是摆设）。**修法路径**（从乱到标准的三步）：先画职责清单（这个项目有哪些职责——检索/对话/存储/配置），再按清单归目录，最后用 import-linter 锁依赖方向——**"先职责后目录"是结构整理的顺序**，反过来（先建目录再塞文件）整理不出来。

**结构与可演进的关联**（筛选者深挖时的第二层问题）：结构好的项目**演进成本低**——加一个新能力（比如"加一个文档导入格式"）只动一层（ingest 模块）；结构乱的项目**演进是事故**——加功能到处改，改一处崩三处。**面试官的相关追问**："你的项目后来加了什么功能，改动集中在哪"——**"集中在哪"的答案就是结构的体检报告**：集中在一层（结构好）vs 散落各处（结构乱）。**AI 项目的演进方向预判**（提前想好结构怎么留余地）：新增 Agent 类型 → 编排层加节点（Level2 05 的图结构天然支持）；新增数据源 → 检索层加路（Level2 06 的组件化）；新增前端 → API 契约不变（Level2 03 的契约设计）——**"结构为演进留白"是架构意识的高级形态**。

## 6. 自查清单

- [ ] 根目录整洁：≤ 8 个顶层条目，无 main.py/test1.py 式平铺
- [ ] app/ 内按 api/services/rag/repository/core 分层
- [ ] tests/ 与 app/ 同构，测试位置可预期
- [ ] scripts/、docs/ 存在（运维与文档有家）
- [ ] 无反向 import、无循环导入（工具检查 + review 盯）
- [ ] rag 层不依赖 Web 框架（AI 能力独立可测）
- [ ] 每个文件职责单一（>400 行检查拆分的必要）
- [ ] 文件命名表意，私有函数 `_` 前缀
- [ ] **验证实验**：给不熟悉项目的人看目录树，3 分钟后他能说出"检索在哪、测试在哪、部署在哪"

**达标标准**：目录树达标 + 依赖方向无违规 + "改字段动三处"的追问能答。项目结构是"设计感"的唯一实体——**地图画得清，才有资格被深挖**。

> 🎯 **核心要点**：项目结构的硬性标准是"**分层清晰、单向依赖、职责单一**"——目录树是地图、依赖方向是交通规则、文件职责是街区划分。结构达标的项目，面试官的任何追问都能"顺着地图找到答案"——**结构是深挖的入场券**。
