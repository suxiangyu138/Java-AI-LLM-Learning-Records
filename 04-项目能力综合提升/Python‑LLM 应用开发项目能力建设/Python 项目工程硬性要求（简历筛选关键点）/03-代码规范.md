# 03 代码规范

> 第三项硬性要求：**代码像不像工程**——风格统一、类型标注、命名清晰、文档字符串齐全。筛选者可能只看一眼源码样例，但深挖时面试官会真的读代码——代码规范是"专业度"的第一证据。

## 1. 筛选者看什么

代码规范是"专业度投影"：**风格是否统一**（一个文件驼峰一个文件下划线、引号风格混乱 = 个人代码，统一 = 工程代码——ruff 格式化过的代码一眼可辨）；**有没有类型标注**（全项目裸参数 = 老式脚本风格；全面标注 = 现代工程习惯——2026 年 Python 岗位的代码审美已全面类型化）；**函数有没有文档**（docstring 与类型注解是"给下一个读代码的人"的信号——**筛选者心里有个问题：这代码是给机器跑的，还是给人维护的**——答案写在每一行注释与每个函数签名里）；**AI 项目的特殊性**：AI 代码（prompt 拼接、Agent 编排、检索链路）比业务代码更容易写成一团——规范与否的对比在 AI 项目里更刺眼，也因此更值钱。

## 2. 硬性标准：统一、可读、有类型

代码规范的硬性标准三条：**统一**（格式化交给工具——ruff format 一个命令全库统一，不靠人自觉）；**可读**（命名表意、函数短小、逻辑分层——"读代码像读文章"）；**有类型**（mypy 严格模式零错误——Level2 02 已实践）。**衡量方法**：**抽查法**（随便打开 3 个文件，风格是否一致、函数是否有签名与 docstring）；**工具法**（`ruff check` 与 `mypy` 是否零错误——**能跑通工具门禁的代码才是工程代码**，这是"代码规范"的机器验证）；**自读法**（三个月后自己重读代码，能否不查文档就理解每个函数——"时间的读者"是最真实的评审员）。

## 3. 风格统一：ruff 管一切

风格统一不靠自觉靠工具（Level2 02 已实践）：**ruff 是 2026 年的事实标准**（format + lint 一体、Rust 实现秒级）：`ruff format .`（统一格式——缩进、引号、行宽 100）与 `ruff check .`（规则检查——未用导入、潜在 bug、可简化代码）。硬性配置（pyproject.toml）：`line-length = 100`（行宽是风格的地基）、`select` 规则集（E/F/I/UP/B/SIM——错误/未用/导入排序/现代语法/内置陷阱/简化——Level2 02 已列）。**执行的强制链**：IDE 保存自动格式化（VS Code 插件）→ pre-commit 钩子拦截 → CI 强制（Level2 02/09）——**三道关卡**保证"风格统一"不依赖任何人的自律。**筛选者视角**：`ruff format` 处理过的代码有一种"机器统一"的观感（对齐、缩进、空行节奏）——**看代码前 5 行就知道有没有过工具**，这就是"统一"的验收信号。

## 4. 类型标注：mypy 严格模式

类型标注是现代 Python 工程的分水岭：**函数签名必标**（参数与返回值——"没标返回值的函数 AI 改起来最容易出错"，Level1 02 的训诫）；**数据结构用 TypedDict/dataclass**（messages、State、配置——Level1 02 已实践）；**mypy 严格模式**（`strict = true`——全项目类型检查零错误，Level2 02 已配置）。**类型标注的工程价值**（不只是审美）：**重构安全**（改函数签名，所有调用点报红——类型系统是免费的重构检查）；**AI 协作友好**（2026 年用 AI 写代码是常态，类型标注让 AI 的产出质量大幅提升——"类型是给 AI 的提示词"）；**自我审查**（写类型的过程就是在想"这个函数的契约是什么"——类型即契约）。**边界与豁免**：`# type: ignore` 逐点豁免并写理由（Level2 02）——"豁免有理由"比"全开全关"专业；第三方库缺类型（stub 未装）用 `# type: ignore[import-untyped]` 集中处理。

**AI 项目代码规范的特殊性**（2026 年筛选者会重点看的 AI 代码形态）：**prompt 与代码的边界**——提示词散落在业务代码里（f-string 拼接散落各处）是 AI 项目的常见病，规范形态是提示词独立成模块/常量（Level1 04 的模板化实践——"prompt 集中管理"是 AI 代码规范的第一条）；**配置项的类型化**——模型名、温度、top_k 这类 AI 参数散落魔法数字（`temperature=0.7` 到处写）vs 集中到配置模型（Level2 02 的 Settings——"AI 参数也是配置"）；**图编排的可读性**——LangGraph 的节点函数命名表意（`retrieve_node` 而非 `node1`）、State 字段有类型（Level2 05 的 State TypedDict）——**AI 编排代码的可读性决定"能不能被 review"**。**AI 代码规范的检验**：随机打开一个 AI 模块文件——prompt 在不在代码里、参数有没有魔法数字、节点命名表不表意——三项过，AI 代码也是工程代码。

## 5. 命名与 docstring：代码即文档

命名与 docstring 是"可读性"的实体：**命名三原则**（Level2 02 已实践）：**表意**（`get_recent_messages` 不是 `get_data`）；**动词开头**（函数）、**名词集合**（模块/变量）；**一致性**（同义概念全库同名——`question` 与 `query` 不能混用）。**docstring 规范**：**函数必有一行 docstring**（做什么 + 参数 + 返回——"docstring 会被喂给大模型做上下文"（Level1 02），AI 时代 docstring 的读者多了一个"AI 协作者"）；**复杂逻辑写"为什么"**（代码写"怎么做"，注释写"为什么这么做"——决策类注释（"这里用 RRF 而非加权融合因为……"）是工程注释与作业注释的区别）；**注释不是翻译**（`# 加 1` 这种注释是噪音——注释解释意图，不重复代码）。**检验标准**：删掉所有注释后，代码是否仍然可读（命名好）——读不懂的部分才是注释该写的地方。

**注释的三个层次**（从工程视角区分价值）：**决策注释**（最值钱——"为什么用 RRF 不用加权融合"，记录的是思考过程，代码表达不了）；**背景注释**（有价值——"该接口兼容旧版客户端，勿改字段名"）；**翻译注释**（零价值——`# 加 1`，重复代码内容）。**代码 review 时的注释纪律**：新代码的注释只写前两类，翻译注释直接删——**"注释量"不是指标，"注释价值密度"才是**。AI 项目的决策注释尤其重要：检索参数、路由阈值、prompt 设计选择——这些"为什么"注释是面试深挖时"我当时为什么这么选"的存档（Level2 06 的调优记录同源）。

## 6. 自查清单

- [ ] `uv run ruff check .` 零错误、`uv run ruff format .` 无改动（已格式化）
- [ ] `uv run mypy app/` 零错误（严格模式）
- [ ] 全项目函数有参数/返回值类型标注
- [ ] 全项目函数有一行 docstring（做什么）
- [ ] 命名表意一致（无 get_data 式烂名、无中英混写变量）
- [ ] 复杂逻辑有"为什么"注释，无"翻译代码"注释
- [ ] ruff/mypy 配置在 pyproject.toml（不是命令行参数）
- [ ] pre-commit 钩子已配置且生效
- [ ] **验证实验**：随机抽查 3 个文件——风格一致、签名完整、docstring 在；3 个月后重读代码能理解每个函数

**达标标准**：工具门禁全过 + 抽查三文件达标。代码规范是最"看得见"的硬性要求——面试官读代码时的内心评分，从这里开始。

**代码规范与 AI 协作的时代背景**（2026 年写代码的方式变了，规范的含义也变了）：用 AI 写代码已是常态——**类型标注与 docstring 的读者多了一个"AI 协作者"**（Level1 02 的训诫：类型是给 AI 的提示词）——规范代码 + AI 协作的产出质量，远高于裸代码 + AI 硬猜；**"代码 review"的对象也包含 AI 生成的代码**（AI 写出来的代码同样要过 ruff/mypy——**"AI 生成的代码不豁免规范"是 2026 年的工程纪律**，本体系的门禁（工具化、强制执行）天然适配这个时代——**规范的意义从"个人审美"升级为"人与 AI 协作的共同语言"**，这也是硬性要求里代码规范分量上升的原因。

> 🎯 **核心要点**：代码规范的硬性标准是"**统一、可读、有类型**"——ruff 统一风格、mypy 锁类型、命名表意、docstring 给读者（包括 AI 协作者）。工具门禁是机器验证、抽查自读是人验证——双重验证通过，"代码像工程"就从印象变成了事实。
