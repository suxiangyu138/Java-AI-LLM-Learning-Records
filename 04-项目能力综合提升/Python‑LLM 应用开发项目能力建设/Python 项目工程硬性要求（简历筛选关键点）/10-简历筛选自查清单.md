## 1. 使用方式：三遍核对

本清单的使用方式——**三遍核对**：**第一遍：全量核对**（提交简历前 1-2 周）——九大类逐项打勾，未达标项记成行动项，按"成本从低到高"排序完成（README 补写 2 小时 < 测试补齐 2 天 < 结构重构 3 天）；**第二遍：门面核对**（提交前 48 小时）——只核对筛选者 30 秒可见的项（README 第一屏、GitHub 仓库整洁、CI 绿、提交历史、界面截图），**门面决定"有没有机会被深挖"**；**第三遍：临场核对**（提交前 2 小时）——冷启动验证（新克隆 + 一键运行 + 健康检查——**"提交前最后一遍跑通"是防翻车的最后一道**（面试官现场 clone 是最坏场景，预案就是"自己先 clone 一遍"）。**三遍的节奏设计**：全量核对防"漏"、门面核对防"偏"、临场核对防"翻车"——三层保险覆盖筛选者从 30 秒到现场验证的整个链条。

## 2. 最终自查清单：九大类逐项

**① 环境可复现**（01 篇）：README 环境说明齐全；uv.lock 已提交；陌生人 15 分钟复现验证通过。**② 依赖规范**（02 篇）：pyproject.toml 元信息完整；依赖分组；许可证在。**③ 代码规范**（03 篇）：ruff/mypy 零错误；类型标注与 docstring 齐全。**④ 结构分层**（04 篇）：目录树整洁；无反向依赖；"改字段动三处"可答。**⑤ 配置密钥**（05 篇）：零硬编码；零泄漏（含历史）；预案在文档。**⑥ Git 协作**（06 篇）：提交规范；.gitignore 完整；CI 绿。**⑦ 测试**（07 篇）：tests/ 同构；断网全绿；覆盖率数字 + CI 门禁。**⑧ 文档**（08 篇）：README 三件套；API/部署文档；调优记录。**⑨ 可运行维护**（09 篇）：一键起；健康检查真；日志可定位。**核对方法**：逐项打勾不是"感觉做了"而是"验证过了"——**每一项的验证动作（断网跑测试、停库看 503、grep 密钥）都实际执行过**——"验证过"与"应该可以"之间差一个实验，本清单要求前者。

## 3. 简历翻译：达标项 → 简历语言

达标项翻译成简历语言的黄金句式（Level3 10 的"我用了 X，解决了 Y，效果是 Z"延续）：**环境** → "uv 管理依赖（锁文件），新环境 15 分钟复现"；**规范** → "ruff + mypy 严格模式，CI 强制"；**测试** → "pytest 三层测试（单元/接口/评估），覆盖率 70% 门禁"；**部署** → "Docker Compose 一键部署，健康检查 + 故障演练通过"；**可观测** → "结构化日志 + trace_id，故障 5 分钟定位"；**AI 深度**（Level3 成果并入） → "混合检索 + 重排，RAGAS 评估忠实度 0.85"；**产品化**（如做了） → "JWT + 租户隔离，隔离测试进 CI"。**翻译的三条红线**：**只写验证过的**（每条对应一个实验记录——"数字的出处"是面试的弹药（Level3 10 的纪律）；**动词优先**（"构建""实现""优化"而非"了解""接触"）；**控制总量**（简历一页、项目要点 5-6 条——**"少而深"远胜"多而浅"**（项目避坑体系 02 篇的教训）。

**筛选阶段的一票否决项**（任何一项命中，九项全过也救不回来——提交前重点排查）：**仓库打不开/是空的**（链接失效或仓库无内容——提交前逐个点开简历里的链接验证）；**README 是模板残留**（"# Project Title" 没改——一眼假）；**代码里有密钥**（05 篇的 grep 检查——硬红线）；**CI 红着/没 CI**（README 宣称工程化但没有门禁——言行不一）；**项目与简历不符**（简历写"高并发"仓库里没有对应代码——**深挖时最致命的失信**（项目避坑体系 01 篇的"真实性"教训）；**最后一次提交在半年前**（"完工即弃"信号——**近期的提交（哪怕只是 README 更新）证明项目还活着**，筛选者更信任活跃项目）。**一票否决项的排查顺序**：链接 → 密钥 → README → CI → 活跃度——**提交前 2 小时按此顺序走一遍**，任何一项命中立即处理（大多数 10 分钟内可修）。

## 4. GitHub 门面三件套

筛选者点开 GitHub 链接后的"门面三件套"（30 秒决策材料）：**仓库主页**（项目名 + 描述一句话 + Topics 标签——**描述与标签是搜索与筛选的命中来源**（06 篇已提）；README 第一屏信息完整（08 篇）；**代码浏览路径**（目录树整洁（04 篇）、tests/ 存在（07 篇）、docs/ 存在（08 篇）——**"结构可读"让筛选者愿意继续翻**）；**Actions 与历史**（CI 绿徽章 + 提交历史规范（06 篇）——**"过程工程感"的最后确认**）。**门面的检验**：以"完全不认识你"的视角打开自己的仓库主页——30 秒内能回答三个问题吗（这是什么项目？能跑吗？像工程吗）——**三个问题的答案是门面的验收标准**。**门面优化清单**（2-3 小时搞定）：README 补截图与亮点、描述与 Topics 补全、CI 徽章挂上、仓库置顶（个人主页）——**花在门面上的时间，是筛选阶段回报率最高的投资**。

## 5. 提交前 24 小时检查

提交前 24 小时的最终检查（时间表）：**24 小时前**：完成 02 篇清单（全量核对），未达标行动项清零或明确"已知缺口"（写进文档——"诚实标注缺口"比"装作没有"专业）；**12 小时前**：门面核对（README 第一屏、截图、CI 绿、提交历史）——发现的问题立即修（README 改 10 分钟）；**6 小时前**：冷启动验证（新目录 clone → 按 README 一键运行 → 健康检查 200 → 调一个核心接口）——**"自己先 clone 一遍"是最重要的临场预案**；**2 小时前**：静默检查（不再改代码——最后 2 小时只做验证不做改动，"手痒加个功能"是提交前翻车的头号原因）；**提交后**：把仓库链接、简历、README 一起过一遍——**"提交不是终点，是筛选的起点"**——之后进入面试阶段（面试考察点与面试冲刺体系接续）。

**本体系与面试准备的衔接**（提交后做什么）：**简历上每个要点对应一篇深挖弹药**（环境/规范/测试/文档每项都能展开成"我的做法 + 为什么 + 数字"——本体系每篇的"面试叙事"段就是答案骨架）；**面试考察点体系（04 层）**提供知识侧广度题库，本体系提供项目侧深度答案——**"项目深挖"与"知识广度"两条线在面试前合并过一遍**；**模拟面试**（找朋友/录音自问自答）按简历逐条问"怎么做的、为什么、数字多少"——卡壳处回本体系对应篇——**本体系的九大类就是模拟面试的追问大纲**：能对九大类各答 2 分钟 = 项目侧面试及格线。**提交与面试之间的一周**：回读本体系每篇的"面试叙事"段落 + Level3 10 的 20 问——**"简历能过筛选，面试能过深挖"，是这一周的全部目标**。

> 🎯 **核心要点**：自查清单的本质是"**把九大硬性要求从'应该达标'变成'验证达标'**"——三遍核对覆盖全量/门面/临场三个层次，达标项翻译成简历语言、门面三件套做好第一印象、24 小时检查防翻车。**九大类全部"验证过"的那一刻，你的 GitHub 链接就不再是简历附件，而是筛选阶段最有力的自我介绍**——达标即提交，进入面试战场。
