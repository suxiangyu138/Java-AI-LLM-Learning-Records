# 09 可运行与可维护

## 1. 筛选者看什么

可运行与可维护是"产品形态"的检验：**一键运行**（README 一条命令能起服务——`uv run uvicorn` 或 `docker compose up -d`（Level2 09）——启动要"三步以内"，启动要 5 分钟手动配环境 = 演示片段）；**有没有健康检查**（/health 端点存在且真实检查依赖（Level2 09 的"假健康"教训）——**"系统会自报状态"是运维形态的第一信号**）；**错误处理**（接口返回统一错误格式（Level2 03 的错误契约）而非裸堆栈——"curl 一个错误请求看返回"是筛选者的常见操作）；**日志**（有日志且结构化（Level2 08）——"出问题能查吗"；**AI 项目的形态检查**（Docker 化（能一键部署）、模型加载预热（首问不卡死——Level2 03 的 lifespan）、成本与用量有埋点（Level2 08）。**筛选者的潜台词**："**这个项目停在'能跑'还是到了'能运营'**"——能运营的标志：一键起、自报状态、出错可查。

## 2. 硬性标准：一键起、能自检、有留痕

可运行与可维护的硬性标准三条：**一键起**（一条命令从零到服务——依赖、外部服务、密钥三件事 README 全包（01 篇的四问）；**能自检**（健康检查真实反映系统状态——/health 检查数据库与向量库连通（Level2 09 的"真健康"实践）——"容器活着但服务废了"的假健康是运维事故（Level2 09）；**有留痕**（日志覆盖关键路径、错误可追溯——"出问题 5 分钟内能定位"（Level3 07 的追踪标准，单服务最低线是日志）。**三项的衡量方法**：**一键**——新环境 clone + 一条命令 + 健康检查 200（01 篇验证实验的延伸）；**自检**——人为停掉数据库，/health 应变 503（Level2 09 的故障演练）；**留痕**——制造一次错误，按日志（或 trace_id）5 分钟内定位（Level3 07 的定位实验）。

## 3. 一键运行：命令即契约

一键运行的"命令即契约"：**启动命令唯一且最短**（`docker compose up -d` 或 `uv run uvicorn app.main:app`——README 的快速开始只有这一条核心命令；启动前的准备（装 uv、配 .env）是 README 的"前置段落"，不算启动步骤）；**外部服务一并起**（compose 文件包含全部依赖服务（Redis/Milvus/DB——Level3 05-06 已实践）——**"一键"意味着依赖也被一键管理**，手动起 Redis 再起服务不算一键）；**停止与重启也有命令**（`docker compose down` / `--scale`——"能起也要能收"）；**启动有验证**（启动后 `curl /health` 是 README 验证段的标准动作——**"启动 + 验证"成对出现**是命令即契约的完整形态）。**一键运行的验收**：README 复制粘贴三段命令（装依赖、起服务、验健康）——新机器上全过——**"复制粘贴可用"是命令文档的最低标准**（命令里留了"你的路径"占位符 = 不合格）。

## 4. 健康检查：系统会自报状态

健康检查是"可维护"的第一信号：**/health 端点必存在**；**检查内容真实**（数据库 `SELECT 1`、向量库 count 查询、依赖服务 ping——Level2 09 的"真健康"实践——**"真实检查依赖"与"固定返回 200"是运维形态与演示形态的分水岭**）；**状态码语义化**（200 正常 / 503 不健康——负载均衡与编排系统（K8s 探针——Level3 09）依赖这个语义）；**详情可查**（503 时响应体或日志说明"哪个依赖挂了"——排错不靠猜）；**配套的启动检查**（lifespan 预热与 readiness 配合——模型加载期间 503、就绪后 200（Level2 03 + Level3 09 的探针实践）。**健康检查的验收实验**（Level2 09 的故障演练）：人为停数据库 → /health 变 503 → 恢复 → 200——**"健康检查能反映真实故障"是它的全部意义**，不能反映故障的健康检查是形式主义。

## 5. 错误处理与日志：出问题可查

**错误处理**的硬性标准：**统一错误契约**（业务异常返回 `{"code": ..., "message": ...}` 的统一格式（Level2 03 的 BizError）——前端与测试按 code 分支（Level2 03）；**不泄漏堆栈**（生产环境返回通用错误，堆栈进日志（Level2 10 的安全基线）——裸堆栈响应 = 信息泄漏 + 不专业）；**错误可区分**（4xx 是业务问题、5xx 是系统问题——客户端能据此判断"重试还是改参数"）。**日志**的硬性标准：**关键路径有日志**（请求入口/检索/模型调用/错误——Level2 08 的埋点清单）；**结构化**（JSON 行、字段可检索（Level2 08）——"grep 能查"是日志的最低可用性）；**trace_id 贯穿**（一次请求的日志可串（Level2 08 + Level3 07 的 OTel 升级）——**"出问题按 trace_id 找全链路日志"是留痕的验收动作**。**验收实验**（Level3 07 的定位实验简化版）：人为制造一次 500 → 按日志 5 分钟内说清"哪里出错、为什么"——**能定位的留痕才是留痕**。

## 6. 可维护的最低线

"可维护"的完整最低线（九项之外的最后一道）：**可观测**（日志 + 健康检查 + 关键指标——Level2 08 的三件套，全家桶（Level3 07）是升级版）；**可部署**（Docker 化 + 配置三态——Level2 09）；**可回滚**（部署可回退——compose 切镜像 tag / helm rollback（Level2 09/Level3 09）——**"能回滚"是维护的最后兜底**）；**可迁移**（AI 项目的特殊性：模型名/API 端点可配置切换（Level2 02 的配置管理）——供应商波动时不慌（Level2 01 的风险预案）。**"最低线"的筛选价值**：它决定"这个项目能不能被运维"——**能运维的项目是"作品"，只能跑的项目是"演示"**——面试官问"你考虑过上线后怎么维护吗"，最低线齐全的项目有完整答案。

**可运行性的三个演示场景**（把"能运行"变成面试可讲的证据）：**冷启动演示**（新环境一键起 + 健康检查 200——"15 分钟从零到可用"的现场演示是环境可复现（01 篇）与一键运行（本节）的合体）；**故障演示**（停掉数据库 → /health 503 → 恢复 → 200——"系统会自报状态"的可视化证据（Level2 09 的故障演练）；**定位演示**（制造一次错误 → 按日志/trace_id 说出"哪里出错、为什么"——"留痕可查"的演示（Level3 07 的定位实验）。**三个演示的共性**：都是"提前准备、现场重放"——**"演练过的场景"在面试现场是行云流水，"没演练过的"是手忙脚乱**——可运行性不是写在 README 里的承诺，是演示过的事实。

## 7. 自查清单

- [ ] 一条命令从零起服务（README 复制粘贴三段可用）
- [ ] compose 包含全部外部依赖（一键含依赖）
- [ ] /health 存在且真实检查依赖（停库应变 503）
- [ ] 启动预热与健康状态配合（加载期 503、就绪后 200）
- [ ] 错误契约统一（code 字段），不泄漏堆栈
- [ ] 关键路径有日志，JSON 结构化可 grep
- [ ] trace_id 贯穿（一次请求日志可串）
- [ ] Docker 化完成、配置三态可切换
- [ ] 部署可回滚（命令已在部署文档）
- [ ] **验证实验**：制造 500 → 按日志 5 分钟定位；停库 → /health 503

**达标标准**：一键起 + 自检真 + 留痕可查——"能跑"升级为"能运营"。这一项是九项里的"产品形态"检验——**前八项是工程素养，这一项是产品意识**。

> 🎯 **核心要点**：可运行与可维护的硬性标准是"**一键起、能自检、有留痕**"——命令即契约、健康检查反映真实、日志可定位。九项硬性要求走完，项目从"能跑的代码"变成"能运营的系统"——**这是简历上"完整交付"四个字的全部含义**。
