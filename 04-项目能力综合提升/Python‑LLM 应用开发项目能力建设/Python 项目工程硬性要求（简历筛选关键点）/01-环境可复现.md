## 1. 筛选者看什么

面试官打开你的 GitHub 仓库，30 秒内的潜台词：**"我能不能把它跑起来？"**——跑不起来 = "这是个作业"；README 三行能跑起来 = "这是个作品"。筛选者会依次验证：**README 里有没有环境说明**（没有 = 扣分）；**说明是否具体**（"需要 Python 3.14" vs "安装依赖即可"——后者等于没说）；**按说明能否复现**（面试官真的会 clone 下来跑——2026 年技术面试官点开仓库实操的比例远高于想象，尤其是 AI 岗位：项目能跑是"真实做过"的最强证据）。**环境可复现为什么是硬性要求**：它是唯一"筛选者亲自验证"的指标——代码质量要读完才懂，环境跑通是 5 分钟内可验证的事实，它的权重因此远超同类。

## 2. 硬性标准：15 分钟复现

环境可复现的验收线：**一位陌生开发者（或 3 个月后的你自己）在一台新机器上，按 README 的说明，15 分钟内让项目跑起来**。15 分钟的三段拆解：**前置准备 ≤ 5 分钟**（Python 与 uv 安装——README 写明命令）；**依赖安装 ≤ 5 分钟**（一条命令装完——uv sync 秒级）；**启动验证 ≤ 5 分钟**（一条命令启动 + 健康检查通过）。**"15 分钟"不是拍脑袋**——超过 15 分钟的复现过程，筛选者大概率放弃（面试官时间更紧）；少于 5 分钟说明项目本身太简单。**复现的验证方法**：找同学/朋友按 README 走一遍（不许问你问题），记录他们卡住的地方——**"卡点清单"就是 README 的补丁清单**，这个测试是环境可复现的验收实验。

**复现失败的四个高频卡点**（90% 的复现失败集中在这四类，README 写作时逐个预防）：**命令缺环**（README 只说 `uv sync` 没说 uv 怎么装——命令链的每一环都要写全，从"装 uv"开始）；**路径假设**（README 假设在项目根执行——写明"在项目根目录执行以下命令"，或用 `cd` 显式进入）；**密钥缺失**（.env.example 提供了但 README 没说"复制并填 Key"——环境说明的四问（装/起/配/要）里"配"是最高频的卡点）；**版本陷阱**（README 说"Python 3"但代码要 3.14——版本必须精确到小版本。**卡点预防的写法**：README 的快速开始按"新人视角"从头写（不假设任何前置），每一行命令都可独立执行——**"按顺序复制粘贴即可跑通"是快速开始的验收线**。

## 3. 三件套之一：解释器锁定

"环境可复现"的第一层：**Python 解释器版本必须锁定**——项目在 3.14 上开发，别人用 3.12 跑出诡异报错（语法/库兼容），排查半天发现是版本问题，这是最浪费筛选者耐心的失败方式。锁定手段（Level2 02 已实践）：**`.python-version` 文件**（uv 项目自动生成与读取——`uv sync` 自动用指定版本）；**README 写明版本**（"Python 3.14（3.12+ 亦可，未经测试）"——写清"建议版本"与"兼容范围"的边界）；**CI 里锁版本**（GitHub Actions 的 `setup-python` / `setup-uv` 指定 3.14——CI 是环境复现的机器化验证）。**边界说明**：只写"Python 3"的 README 等于没写（3.8 与 3.14 的差异巨大）；写了版本但代码里用了未兼容语法，同样不合格——**版本锁定是"声明"与"行为"双重的**，CI 就是行为的验证。

## 4. 三件套之二：依赖锁定

"能跑"的第二层：**依赖必须可复现**——`pip install -r requirements.txt` 装的依赖是不确定集合（版本漂移：昨天能跑今天崩），`uv.lock` 锁定的是精确版本（每个人、每次安装都拿到完全一致的依赖集）。硬性标准（Level2 02 的实践延续）：**uv.lock 提交进 Git**（锁文件在仓库里，环境可复现才有依据）；**README 说明安装命令**（`uv sync` 或 `uv add`——写清"克隆后第一步做什么"）；**requirements.txt 时代的迁移**（老项目还在用——升级到 pyproject.toml + uv.lock，这是 2026 年的基线）；**依赖分组的边界**（dev 依赖（测试/工具）与生产依赖分离——`uv sync --no-dev` 生产安装，README 写明两套安装方式）。**筛选者的验证路径**：README 说 `uv sync` → 执行 → 报错"没有 uv"→ 说明里没写 uv 安装命令——**"说全"与"说对"同等重要**，命令链的每一环都要写明。

## 5. 三件套之三：环境说明

第三层是"软环境"说明——依赖之外，项目还有什么前置条件（2026 年 Python AI 项目的典型项）：**外部服务**（数据库、Redis、向量库——compose 一键起（Level2 09/Level3 05-06 已实践）还是需要手动装，README 写明）；**密钥要求**（.env.example 提供模板（Level2 02）——"复制 .env.example 为 .env 并填入 Key"是标准句式）；**硬件要求**（本地 embedding 模型的显存/内存需求——Level2 06 的 bge 模型几百 MB，README 写明避免"跑一半 OOM"）；**网络要求**（模型下载/API 调用需要外网——镜像源说明（Level1 01 的 uv 镜像、HF 镜像））。**环境说明的检验标准**：README 的环境段落能回答"陌生人的四个问题"——装什么（解释器与依赖）、起什么（外部服务）、配什么（密钥）、要什么（硬件网络）——四问全答即合格。

**AI 项目环境说明的两个特殊项**（2026 年高频踩坑）：**模型下载的首次体验**——本地 embedding/重排模型首次运行要下载几百 MB（Level2 06 的 bge 模型），README 要说明"首次运行会下载模型（约 X MB），网络受限时配置镜像（HF_ENDPOINT）"——不写这条，陌生人首次运行会以为"卡死了"；**API Key 的获取路径**——README 写明"到 platform.deepseek.com 注册获取 Key"（Level1 01 的步骤），"Key 从哪来"是 AI 项目复现的最后一个隐藏卡点——**四问之外，AI 项目加一问："模型从哪来（Key/下载）"**。

## 6. 自查清单

- [ ] 仓库根目录有 README.md，且第一屏就有"环境要求"与"快速开始"两节
- [ ] `.python-version` 存在且与 pyproject.toml 的 requires-python 一致
- [ ] uv.lock 已提交，README 写明 `uv sync` 安装命令与 uv 的安装方式
- [ ] 外部服务（DB/Redis/向量库）有 compose 文件或明确的手动安装说明
- [ ] .env.example 存在，README 写明"复制并填 Key"的步骤
- [ ] 硬件/网络要求（模型下载、显存、镜像）有说明
- [ ] 启动命令只有一条（`uv run uvicorn ...` 或 `docker compose up -d`），且健康检查方式已写明
- [ ] **验证实验**：找一位没接触过项目的人按 README 走一遍，15 分钟内跑通，卡点已修进 README

**达标标准**：清单全勾 + 验证实验通过——"环境可复现"从"我认为可以"变成"实际验证过"。这一项是第一印象的基石：**跑得起来，面试官才会继续看代码**。

**环境说明的三档完成度**（对照自己的 README 定位）：**第一档**（合格）——命令链完整、四问全覆盖、按序可跑；**第二档**（加分）——一档之上加"常见问题"段（模型下载慢/镜像配置/端口占用——把 01 篇的四类卡点提前写进 FAQ，陌生人不用来问）；**第三档**（优秀）——二档之上加"环境验证脚本"（`scripts/check_env.py` 一键检查 Python 版本、依赖、密钥、外部服务连通——**"环境自检脚本"是环境可复现的工程化形态**（01 篇的自查清单升级为脚本），新环境跑一遍脚本，所有前置条件一目了然。**三档的推进建议**：先到一档（成本 2 小时），项目定型后补二档，提交简历前有余力再上三档——**每一档都是"陌生人更少问问题"的增量**。

> 🎯 **核心要点**：环境可复现的验收线是"**陌生人 15 分钟跑起来**"——解释器锁定版本、依赖锁定精确、说明覆盖四问（装/起/配/要）。三项全过，GitHub 链接的第一印象分就拿到了——这是筛选阶段投入产出比最高的一项硬性要求。
