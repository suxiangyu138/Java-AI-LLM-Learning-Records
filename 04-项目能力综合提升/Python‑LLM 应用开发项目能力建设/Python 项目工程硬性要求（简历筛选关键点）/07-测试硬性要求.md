# 07 测试硬性要求

> 第七项硬性要求：**测试存在、可信、有数字**——pytest 用例在、不依赖真实外部服务、覆盖率有报告、CI 强制执行。测试是"工程可维护"的最硬证据——AI 项目的测试（mock LLM）还多一层"可信度"的挑战。

## 1. 筛选者看什么

测试是筛选者判断"可维护性"的硬证据：**tests/ 目录存不存在**（没有 = 扣分最重的一项——"没测试的项目 = 改代码靠祈祷"）；**测试规模**（几十个用例 = 认真写过；两个用例 = 摆设）；**测试内容**（断言具体行为 vs 只打印不断言——"看着像测试的占位符"一眼可辨）；**覆盖率报告**（README 或 CI 输出里有数字——"覆盖率 70%"是硬指标，没有数字的"我写过测试"是软话）；**AI 项目特有的检查**（测试是否 mock 了 LLM——测试里直接调真实模型 = 测试不可重复、依赖网络与钱——**"测试可离线跑"是 AI 项目测试可信的第一标准**）。**筛选者的潜台词**："**这个项目改坏了会有人知道吗**"——测试就是那个"知道的人"。

## 2. 硬性标准：存在、可信、有数字

测试的硬性标准三条：**存在**（tests/ 目录与 app/ 同构——每个模块都有对应测试（Level2 07 已实践）；**可信**（测试可重复——同一份代码同一结果；不依赖真实外部服务——mock 到位（Level2 07 的"无 Key 可跑"）；快速——秒级完成（分钟级的测试没人跑，等于没有））；**有数字**（覆盖率报告存在（pytest-cov 输出）、覆盖率阈值在 CI 强制执行（Level2 07 的 `--cov-fail-under=70`）——**"数字 + 门禁"是测试从"我写了"到"我保证"的升级**。**衡量方法**：`uv run pytest`（能跑、全绿、秒级）；`pytest --cov`（有覆盖率输出）；README/CI 有覆盖率徽章或数字。

## 3. 测试存在：tests/ 的结构

测试的结构规范（Level2 07 已实践，这里是验收视角）：**与 app/ 同构**（`tests/api/`、`tests/unit/`、`tests/eval/`——找测试顺着结构走，别人（和未来的你）才知道"新功能的测试放哪"）；**三层覆盖**（单元（函数级）、接口（契约级）、评估（质量级——RAGAS 评估集，Level2 06）——**"三层"说明测试有设计**，只测单元不测接口 = 契约裸奔）；**命名即文档**（`test_检索_融合两份结果`——失败时名字告诉你哪坏了（Level2 07 的命名规范））；**fixture 组织**（conftest.py 放共享 fixture、factories.py 放数据工厂（Level2 07）——测试之间隔离不共享状态）。**结构的存在感**：打开 tests/ 目录树——每个 app/ 下的模块都有影子，新开发者能说出"新功能测试放哪"——**测试结构是项目可维护性的可视化**。

## 4. 测试可信：mock 边界

"测试存在"之后是"测试可信"——**mock 的边界决定可信度**（Level2 07 已实践）：**外部依赖一律 mock**（LLM API、网络、真实数据库——测试里出现真实网络调用 = 不可重复 + 不可离线 + 花钱）；**mock 的"像"**（mock 响应结构要与真实结构一致（`choices[0].message.content` 能取到——Level2 07 的 FakeResp 例子），mock 得太假会让测试测了个寂寞）；**mock 的边界在"接口"不在"实现"**（mock SDK 的调用入口，不 mock 内部属性——重构不崩（Level2 07 的纪律））；**真实链路留一个冒烟**（端到端冒烟测试（标记 `@pytest.mark.smoke`，不默认跑）验证"mock 没骗自己"——**"mock 的世界里测试全绿，真实世界一跑就崩"是 mock 过头的经典事故**，冒烟测试是解药）。**可信度的检验**：断网跑 `uv run pytest`——全绿才可信；把 mock 返回值改错——测试应该报红（**测试能发现 mock 的错误 = mock 真的被用上了**）。

## 5. 覆盖率与 CI 门禁

覆盖率是"测试有没有漏"的粗尺子，**数字 + 门禁**才是硬性要求（Level2 07 已实践）：**阈值明确**（单元 + 接口 ≥ 70%、关键路径 ≥ 85%——"关键路径"（检索、对话编排、错误处理）单独统计——**"70% 全库"不如"关键路径 85% + 全库 70%"有含金量**，说明你知道哪里重要）；**CI 强制执行**（`--cov-fail-under=70` 在 CI 的 pytest 命令里——本地可绕过、CI 不可绕过（Level2 09 的纪律）；**覆盖率的诚实**（覆盖率 100% 但全是空断言 = 数字造假——**覆盖率是"下限"不是"目标"**，数字之外要看断言质量（第 4 节的 mock 边界）。**门禁的筛选价值**：README/CI 上的"coverage 73%"徽章——一个数字说明"测试是被强制执行的质量纪律"——这比"我写过测试"（无数字）的说服力高一个数量级。

## 6. AI 项目测试的特殊要求

AI 项目的测试比传统项目多三层：**LLM 输出不确定性**——同输入不同输出，传统断言（"等于 X"）失效——**测试断言"结构"而非"内容"**（断言消息结构、工具调用参数、错误契约字段，不断言模型措辞——Level2 07 的"断言 messages 结构"实践）；**评估测试（RAGAS）独立成层**（分钟级、进 CI 的独立 job——Level2 07 的 `-m "not eval"` 分流——**"快测试秒级、评估测试分钟级"的分层是 AI 项目测试设计感**）；**prompt 变更回归**（改提示词后跑评估集（Level2 06）——**提示词也是代码，改它要回归**——"提示词版本 + 评估结果"的记录是 AI 项目的测试纪律延伸）。**AI 测试的面试价值**："我的测试策略分三层——单元 mock LLM 测逻辑、接口测契约、RAGAS 评估集防质量回退，CI 里评估独立跑"——这是 2026 年 AI 岗位最标准的测试叙事。

**"没写测试"的常见借口与反驳**（自查时对照，别让借口过关）：**"Demo 项目不需要测试"**——反驳：测试是"改代码敢不敢"的底气，Demo 也会迭代，没有测试的迭代是踩雷；**"AI 输出不确定没法测"**——反驳：测"结构"不测"内容"（第 6 节）——消息结构、工具调用、错误契约都是确定的；**"写测试的时间不如写功能"**——反驳：测试的收益在"改功能时"兑现——**"测试是给未来的改动买的保险，不是给现在的功能做的展示"**；**"覆盖率够高就行"**——反驳：覆盖率是下限不是目标，断言质量才是关键（空断言 100% 覆盖率 = 自欺）。**测试写作的最小启动点**：从纯函数开始（分块、消息裁剪、配置校验——Level2 07 的"甜区"），先有 10 个高质量单元测试，再往接口与评估层扩——**"先甜区后难点"是测试体系的启动顺序**。

## 7. 自查清单

- [ ] tests/ 存在且与 app/ 同构，新功能测试位置可预期
- [ ] 三层测试：单元 + 接口 + 评估（评估为选做但建议）
- [ ] 断网跑 pytest 全绿（无真实外部依赖）
- [ ] mock 结构真实（能取出 choices[0].message.content 这类字段）
- [ ] 有端到端冒烟测试（标记不默认跑）
- [ ] 覆盖率报告存在（全库 ≥ 70%，关键路径单独统计）
- [ ] CI 里 pytest + 覆盖率门禁强制执行
- [ ] 测试断言结构不断言措辞（AI 项目）
- [ ] 提示词变更跑过评估回归（AI 项目）
- [ ] **验证实验**：改坏一处逻辑 → pytest 当场报红；断网全绿

**达标标准**：存在 + 可信 + 有数字——三项齐了，"可维护"就是可验证的事实。测试是九项里区分度最高的一项——**大多数人没有，你有就是差异**。

**测试的面试叙事**（达标后怎么讲最加分）：**"我的测试分三层"**（单元 mock LLM 测逻辑、接口 TestClient 验契约、RAGAS 评估集防质量回退——Level2 07 的体系一句话讲清）；**"测试的可信度设计"**（断网全绿——不依赖真实 API；mock 结构真实——能取出 choices 字段；端到端冒烟防 mock 骗人——Level2 07 的三层可信）；**"测试驱动的改进案例"**（讲一个真实故事："覆盖率从 40% 提到 72% 的过程中，接口测试抓到一个 SSE 格式 bug"——**"测试抓到过真 bug"比"覆盖率 70%"有说服力十倍**——测试的价值在"它真的救过你一次"，这个故事要在项目期间攒一个。

> 🎯 **核心要点**：测试的硬性标准是"**存在、可信、有数字**"——tests/ 同构是存在、断网全绿是可信、覆盖率达 CI 门禁是有数字。AI 项目加一层"断言结构 + 评估回归"的特殊纪律——**测试是全套硬性要求里"专业度证据"最重的一项**。
