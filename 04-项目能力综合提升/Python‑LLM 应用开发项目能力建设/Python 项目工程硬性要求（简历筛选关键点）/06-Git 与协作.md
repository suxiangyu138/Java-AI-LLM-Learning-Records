## 1. 筛选者看什么

Git 是筛选者"看历史"的唯一窗口（30 秒）：**提交频率与分布**——提交稀疏（几周一次、一次几百个文件）像"作业提交"，提交频繁且增量小像"真实开发"（**Git 历史是项目真实性的证据链**——"一次提交一个逻辑"的仓库，历史本身就是可读的项目演进日志，Level2 02 已实践）；**提交信息质量**——`feat(chat): 新增流式接口` vs `更新` vs `asdf`——提交信息是给未来读者（含面试官）的索引；**仓库是否整洁**——有没有 .gitignore（data/、.env 不该出现在历史里）、有没有把依赖和密钥提交上去（Level3 09 的教训）；**CI 徽章**（README 上的 passing 徽章——2026 年"CI 绿"几乎是工程仓库的默认配置，没有反而醒目）。**筛选者的潜台词**："**这个项目的开发过程像不像真实的工程过程**"——Git 历史是过程的最诚实记录，编不出来。

## 2. 硬性标准：历史可读、门禁执行

Git 与协作的硬性标准两条主线：**历史可读**（一次提交一个逻辑、信息规范、仓库整洁——"git log 能当项目文档读"是验收线；**门禁执行**（质量门禁（ruff/mypy/pytest）在 CI 强制跑——"本地可跳过、CI 不可绕过"（Level2 09）——**CI 是"规范说了算"的机器执行者**：规则不写成流水线就是建议，写成流水线才是纪律）。**"门禁执行"的筛选价值**：README 说"代码规范"没人信，CI 里跑 `ruff check` 且绿——一验便知；CI 配了但一直红 = 更糟（说明项目已经放弃了自己的门禁）。**衡量方法**：`git log --oneline | head -30`（信息质量抽查）；`git log --stat`（提交粒度）；GitHub 页面看 Actions 状态（最近几次 push 是否绿）。

## 3. 提交规范：Conventional Commits

提交信息的标准格式（Level2 02 已实践，这里是筛选视角的验收）：`类型(模块): 摘要`——类型（feat/fix/docs/refactor/test/chore）、模块（chat/retrieve/deploy）、一句话摘要（动词开头、说明改动而非描述代码）。三条纪律：**一次提交一个逻辑**（"改接口 + 改测试 + 改文档"拆成三个提交——回滚与 review 才可控，`git log` 才可读）；**信息说明"为什么"**（`fix(retrieve): RRF 融合改用 k=60（解决长尾排序不稳）`——带背景的提交信息是工程文档的一部分；**不做微提交**（`fix typo` 频繁刷屏——相关改动合并，一次提交完成一个目标）。**验收实验**：让不熟悉项目的人读 20 条提交信息——能复述出"项目经历了什么"（加功能、修 bug、升级检索、加测试）——**提交历史能讲故事，才算"历史可读"**。

**提交信息反例对照**（写信息时的"不要"清单）：`update`（最烂——说了等于没说）；`更新代码`（中文无内容）；`fix bug`（没说哪个 bug）；`finish project`（作业感拉满）；`asdf`/`1`（键盘滚脸）。**正例对照**（同一条改动的两种写法）：`fix`（烂）vs `fix(retrieve): RRF 融合改用 k=60 解决长尾排序不稳`（好——类型 + 模块 + 动词开头 + 背景）。**写提交信息的判断标准**：**"三个月后的自己（或面试官）看到这条信息，能知道这次改动解决了什么"**——能就知道够了；再进一步的信息（为什么这么修）放提交正文（`git commit -m` 换行写正文，或 PR 描述）。**提交信息的产出纪律**：写完代码不急着提交，先想"这次改动的一句话是什么"——**想不出的一句话 = 这次改动可能不是一件事**（拆提交的信号）。

## 4. 仓库整洁：.gitignore 与分支

仓库整洁的硬性要求：**.gitignore 完整**（至少覆盖：.env 与变体、data/（运行数据）、.venv/、__pycache__/、*.pyc、日志文件、IDE 配置——**"仓库里没有运行产物"**是整洁的第一标准；误提交过的产物按 05 篇的预案清理（Git 历史中的大文件用 filter-repo——仓库「Git 知识体系」有完整流程）；**分支规范**（main 保持可部署、功能分支 feature/xxx、合并用 PR + 简短描述——Level2 02 已实践；**单人项目的分支可以简化但 main 必须是绿的**——"main 永远可部署"是 Git 协作的第一纪律）；**README 与仓库信息**（项目名、描述、Topics（语言/框架标签——GitHub 搜索与筛选的命中来源）——**仓库的"门面信息"（描述与 Topics）是简历链接被点开后的第一印象**，花 10 分钟写全）。**仓库整洁的检验**：clone 到新目录——没有多余的运行产物、README 第一屏信息完整、main 分支绿——"新克隆体验"就是筛选者的体验。

## 5. CI 绿灯：门禁的机器执行

CI（GitHub Actions 等）是"工程纪律的机器执行"（Level2 09 已实践，这里是验收视角）：**必配的三个 job**——质量门禁（ruff + mypy——Level2 02 的本地门禁在 CI 强制执行）、测试（pytest + 覆盖率红线——Level2 07 的覆盖率门禁）、构建（镜像构建验证——Level2 09）；**配置的完整性**（`.github/workflows/ci.yml` 存在且最近 N 次 run 全绿——**"配置存在"与"实际执行"是两回事**，看 Actions 页面的最近记录）；**无密钥可跑**（CI 环境无真实 API Key 也能全绿——测试 mock 到位（Level2 07 的硬要求）——**CI 绿且有信心的前提是测试不依赖外部服务**）。**CI 的面试价值**："我的项目 CI 自动跑质量门禁与测试，覆盖率低于 70% 不合并"——这是"工程纪律"一句话证明，2026 年大厂筛简历时 CI 徽章与 Actions 记录是加分确认项。

**CI 配置的三个常见失败形态**（配了 CI 不等于有 CI）：**CI 一直红**（配置过时/测试不稳定——红着的 CI 比没有更糟，它宣告"项目已经放弃质量门禁"——**"CI 必须保持绿"是纪律，红了立即修**，红了三天没人管 = 门禁名存实亡）；**CI 只跑构建不跑检查**（"门禁"形同虚设——质量检查（ruff/mypy/pytest）才是门禁主体，构建只是验证）；**CI 依赖本地环境**（工作流里手动装依赖且不锁版本——CI 是"干净环境的复现实验"（01 篇的 15 分钟复现的机器版），用 `uv sync --frozen` 保证与本地一致——**CI 与本地环境一致性**是 CI 可信的前提。

## 6. 自查清单

- [ ] git log 最近 30 条信息规范（类型+模块+摘要），无"更新"式烂信息
- [ ] 一次提交一个逻辑，无一次几百文件的大提交
- [ ] .gitignore 覆盖 .env/data/.venv/__pycache__/日志
- [ ] Git 历史无运行产物与密钥（有则已按预案清理）
- [ ] main 分支绿且可部署，功能走分支
- [ ] README 有项目描述与 Topics 标签
- [ ] .github/workflows/ci.yml 存在：ruff+mypy+pytest+覆盖率
- [ ] Actions 最近记录全绿（不是配了没跑）
- [ ] CI 无真实密钥依赖（无密钥全绿验证过）
- [ ] **验证实验**：新克隆仓库 → README 信息完整、无运行产物、main 绿

**达标标准**：历史可讲故事 + CI 实际绿。Git 与协作是"工程纪律"的诚实记录器——**它做不了假，也就最有说服力**。

**Git 的面试叙事**（从提交历史反推面试问题）：面试官看提交历史后常问——**"这个项目你做了多久、节奏怎么样"**（历史里的提交密度与时间线就是答案：每周几次提交、每篇模块一个里程碑（Level2 02 的里程碑提交）——**"Git 历史即项目进度表"**）；**"你修过什么印象深刻的 bug"**（历史里的 fix 提交就是素材库——"fix(retrieve): 修复 RRF 长尾排序"这类提交背后都有故事可讲（Level2 10 的"失败与修复"素材）；**"你和别人合作过吗"**（分支与 PR 历史证明协作形态——单人项目诚实说"单人开发，但按团队规范走分支与提交"——**"单人按团队规范"比"从不规范"专业得多**。**Git 历史是面试素材的存档**——提交信息写得越规范，面试时翻历史找素材越方便——"规范的提交 = 规范的可追溯"。

> 🎯 **核心要点**：Git 与协作的硬性标准是"**历史可读、仓库整洁、门禁执行**"——提交规范让历史可讲故事、.gitignore 让仓库干净、CI 让门禁不可绕过。Git 历史是筛选者唯一能"看到过程"的地方——**过程的工程感，从这里被验证**。
