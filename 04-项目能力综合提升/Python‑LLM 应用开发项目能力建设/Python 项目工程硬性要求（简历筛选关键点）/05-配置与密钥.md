## 1. 筛选者看什么

配置与密钥是筛选者"翻仓库就能验证"的安全指标：**搜硬编码**——`grep` 一下代码里有没有 `sk-` 开头的字符串（**在公开仓库里搜到 API Key = 一票否决**，这是 2026 年 AI 岗位筛选的硬红线——Key 泄露 = 白嫖/盗刷风险 + 工程素养缺失）；**看 .env 是否被提交**（仓库里躺着 `.env` 文件 = 同上）；**看配置管理方式**（配置是集中模型还是散落各处——`.env.example` 的存在是"懂配置管理"的信号）；**看密钥的存放形态**（开发 .env、测试 mock、生产 Secret——分环境管理的意识）。**筛选者的潜台词**：**"这个开发者把密钥当回事吗"**——密钥管理是安全意识的最小可见单元，安全意识是 2026 年工程岗的底线素质。

## 2. 硬性标准：零硬编码、零泄漏

配置与密钥的硬性标准两条主线：**零硬编码**（代码里没有任何环境相关的常量——模型名、连接串、阈值全部走配置（Level2 02 的 pydantic-settings 已实践）；"换个环境只改配置不改代码"是验收线——dev/test/prod 三态切换（Level2 02 的三态设计））；**零泄漏**（密钥只存在于 .env（本地）与 Secret（部署）——不进代码、不进镜像、不进日志（Level2 10 的日志脱敏）；**泄漏有预案**（Level1 01 的预案：发现泄漏 → 平台重置 Key → 更新 .env——预案写在文档里，不是"真出事了再想"）。**两项的验证方法**：`grep -r "sk-" --include="*.py"`（代码零命中）；`git log --all -S "sk-"`（历史零泄漏——**历史里有 Key 同样算泄漏**，公开仓库要清历史或用"历史误提交"的处置流程）。

## 3. 配置集中：pydantic-settings 三态

配置管理的标准形态（Level2 02 已实践，这里是筛选视角的验收）：**集中模型**（一个 `config.py` + Settings 类——所有配置一个出处，不散落）；**类型校验**（配置是"强类型模型"不是字符串字典——启动即校验，Key 缺失在启动时报错而非请求时 401（Level2 02 的"启动时校验"纪律））；**三态切换**（dev/test/prod 三套配置可切换——.env（本地）/ tests 覆盖（测试）/ 环境变量注入（部署）——**"三态切换"是配置管理是否合格的验收实验**：同一份代码，三个环境都能跑）。**配置即文档**：`.env.example` 列出全部配置项与注释（每个配置的用途、默认值、取值范围）——**新环境照 example 复制即用**（Level2 02），这份 example 是"配置的说明书"。**配置的边界纪律**：非敏感配置进 Settings 默认值（模型名、阈值）、敏感配置必须 .env（Key、密码）——**"敏感与不敏感的边界"写在配置文档里**，防止有人把 Key 顺手写进默认值。

## 4. 密钥安全：.env 与预案

密钥安全的完整链路：**存放**（本地 .env 文件、部署 Secret（Level3 09）/ 容器环境变量（Level2 09）——密钥不进代码与镜像）；**忽略**（.gitignore 必须含 `.env`、`.env.local` 等变体——`.dockerignore` 同样排除（Level2 09 的教训）——**"忽略列表"是防泄漏的第一道物理屏障**）；**轮换**（定期重置 + 泄漏即重置——"轮换成本低、泄漏成本高"，Key 从创建起就假设"终将被泄漏"，轮换是常态动作）；**监控**（平台用量告警（Level1 01）——异常消耗是泄漏的早期信号）。**泄漏预案的完整流程**（写进项目文档）：发现泄漏（告警/自查）→ 平台立即重置 Key（先止损后排查——**重置优先于删历史**）→ 更新所有环境 → 排查泄漏面（代码/日志/镜像/CI 缓存）→ 记录复盘。**预案写没写是分界线**——"没出过事"不是安全的证明，"有预案且演练过"才是。

## 5. AI 项目的密钥特殊性

AI 项目的密钥管理比传统项目多三个特殊性：**Key 即钱**（API Key 直接关联账单——泄漏 = 白嫖你的 token 额度，2026 年 AI 岗筛选对 Key 泄漏的容忍度为零）；**多 Key 并存**（模型 API、向量库、可能的第三方服务——**统一前缀规范**（`KBQA_DEEPSEEK_KEY`、`KBQA_MILVUS_URI`）与统一读取入口（config 一处加载），防"Key 散落各处"）；**提示词与密钥的边界**（模型可能输出内部配置（prompt leak）——**响应过滤与日志脱敏**（Level2 10 的防护点）是 AI 特有的密钥防线——"密钥不能进对话上下文"是 AI 应用的硬纪律）。**AI 密钥管理的加分动作**：用量监控（Level2 08 的成本埋点——"密钥安全 + 成本可见"双保险）、权限最小化（平台子账号/限流额度——"就算泄漏也损失有限"的纵深防御）。

**常见密钥事故与处置对照**（2026 年 GitHub 公开仓库的真实事故形态）：**事故一：Key 提交进了公开仓库**——处置按 05 篇预案（平台重置优先——**Git 历史里的 Key 照样会被爬虫抓走盗刷，删文件不重置 = 白删**；重置后用 filter-repo 清历史（仓库「Git 知识体系」流程）；**事故二：Key 进了镜像**（Dockerfile 里 ENV 或构建层缓存——Level2 09 的 .dockerignore 教训——镜像会被 pull 后反查层内容；处置：重建镜像 + 重置 Key + .dockerignore 补上）；**事故三：Key 出现在日志/错误响应**（模型输出或异常堆栈带出配置——Level2 10 的日志脱敏防线；处置：脱敏规则补全 + 重置 Key）。**三个事故的共同规律**：**处置的第一步永远是"重置 Key"**（止损优先），清理只是善后——**"重置优先"写进预案文档的标题位置**。

## 6. 自查清单

- [ ] `grep -r "sk-" --include="*.py"` 零命中（代码无硬编码密钥）
- [ ] git 历史无密钥（`git log -S` 检查，有则按预案处置）
- [ ] .gitignore/.dockerignore 含 .env 及变体
- [ ] 配置集中在 config.py（Settings 模型），代码零散配置读值
- [ ] .env.example 齐全（每个配置有注释），新环境照抄即用
- [ ] 三态切换验证过（dev/test/prod 同一份代码都能跑）
- [ ] 启动时校验配置（Key 缺失启动即报错）
- [ ] 日志脱敏（Key 只记前 4 位），模型输出过滤内部配置
- [ ] 泄漏预案写在文档（重置优先流程 + 演练记录）
- [ ] 平台用量告警已开启，密钥有轮换机制

**达标标准**：零硬编码 + 零泄漏 + 预案在文档。配置与密钥是"一票否决"项——**这项不过，其他九项全过也白搭**；这项过了，"安全底线"就成了简历与面试的加分叙事。

**密钥管理的面试叙事**（达标后怎么讲）："我的项目密钥管理有完整链路——开发用 .env（.gitignore 排除、代码零硬编码），部署用 Secret/环境变量注入，日志脱敏（Key 只记前四位），平台开了用量告警，泄漏预案文档化（重置优先）"——**这一段是 2026 年安全问题的标准答案形态**；被追问时再往下讲："我还考虑了纵深防御——API 平台用子账号限额度，就算泄漏损失也可控"——**"纵深防御"四个字是安全意识的高级表达**。**反面案例警示**：面试里最常见的翻车现场是"我的 Key 不小心提交过，后来删了"——**删文件不等于安全（Git 历史还在），重置才是**——回答"怎么处理的"时说出"重置 + 清理历史 + 复盘"三步，翻车现场也能变成安全意识的展示。

> 🎯 **核心要点**：配置与密钥的硬性标准是"**零硬编码、零泄漏、有预案**"——配置集中管、密钥分开藏、泄漏有流程。AI 项目的密钥即钱，安全底线是筛选的一票否决项——**这项达标不是加分，是入场券**。
