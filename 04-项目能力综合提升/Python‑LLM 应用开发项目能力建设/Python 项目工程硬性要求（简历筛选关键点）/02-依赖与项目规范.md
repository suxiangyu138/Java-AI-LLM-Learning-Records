# 02 依赖与项目规范

> 第二项硬性要求：**项目清单（pyproject.toml）管得清不清楚**——依赖分组合理、版本策略明确、许可证合规、项目元信息完整。筛选者看依赖管理，判断的是"这个开发者懂不懂工程底线"。

## 1. 筛选者看什么

依赖管理是筛选者判断"工程底线"的窗口：**看 pyproject.toml 一眼**——依赖是分组管理的还是一个大杂烩列表？版本是锁定策略还是裸版本号？**看依赖是否合理**——AI 项目里出现 `requests` 合理、出现 `numpy` 合理，但出现 `django` 就要想"这个项目到底做什么"（依赖与项目定位不符 = 项目可能是拼凑的）；**看依赖数量**——几十个依赖的项目（把 demo 依赖全塞进生产依赖）说明没做过环境分类。**筛选者的潜台词**：依赖管理乱的开发者，代码大概率也乱——**依赖清单是代码质量的第一层投影**，5 秒可验证。

## 2. 硬性标准：依赖可审、清单可读

依赖管理的硬性标准三条：**可审**（任何依赖都能回答"为什么引入它"——README 或代码注释能解释，说不出来源的依赖是负债）；**可分组**（生产依赖与开发依赖分离——`uv add --dev` 装的工具不污染生产环境）；**版本可追踪**（uv.lock 锁定精确版本，升级有记录——`uv add` 显式操作而非手改版本号（Level2 02 的纪律））。**"可读"的体现**：pyproject.toml 的依赖列表按类别组织（AI 依赖、Web 依赖、工具依赖分节注释），新开发者 30 秒能判断"这个项目用什么栈"——**清单即文档**，这是"项目规范"的第一层。

## 3. pyproject.toml：项目的身份证

pyproject.toml 是 2026 年 Python 项目的"身份证"（PEP 621 标准，替代 requirements.txt 与 setup.py 的碎片化）：元信息（name/version/description）、依赖声明、工具配置（ruff/mypy/pytest 全在这里——Level2 02 已实践）三合一。硬性要求：**name 与 description 完整**（仓库名 ≠ 项目名时尤其重要——description 一句话讲清项目做什么，这是筛选者在 GitHub 列表页看到的第一个信息）；**requires-python 声明**（与 .python-version 一致——01 篇的版本锁定在清单侧再确认一次）；**依赖分节**（`[project]` 的生产依赖与 `[dependency-groups]` / dev 依赖分开——`uv sync --no-dev` 可生产安装）；**工具配置集中**（ruff/mypy/pytest 的配置都在 pyproject.toml 里——"配置一处管理"让新开发者一眼看到质量门禁。**检查方法**：打开自己的 pyproject.toml——如果它只有依赖列表没有元信息与工具配置，就是"半成品身份证"。

## 4. 依赖分组与版本策略

**分组**（2026 基线）：`[project] dependencies` 只放运行时依赖（fastapi、uvicorn、openai、langgraph 等）；开发依赖（pytest、ruff、mypy、locust、pre-commit）走 `uv add --dev`（进 `[dependency-groups]`）——分组的直接收益：生产镜像用 `uv sync --no-dev` 体积小、攻击面小（Level2 09 的 Dockerfile 已受益）。**版本策略**：声明下限（`langgraph>=1.0`——保证新装者拿到可用版本）与锁文件（uv.lock——保证每次安装精确一致）双层——**"下限声明 + 锁文件精确"是 2026 年的标准组合**（裸写 `langgraph` 无下限 = 未来版本可能破坏；手写精确版本号 = 升级困难）。**升级策略**：`uv add --upgrade` 显式升级 + 升级后跑全套门禁（Level2 02 的第 6 节清单）——**升级是"动作"不是"结果"**，每次升级的验证记录是工程纪律的证据。

**依赖管理的三个常见"病态"与修法**：**依赖臃肿**（几十个依赖没有来源解释——修法：逐个追问"为什么引入"，回答不出的移除或注释原因；AI 项目特别容易堆"看着可能有用"的库——**依赖是负债，每多一个就多一个维护与安全点**）；**版本裸奔**（pyproject 里 `langgraph` 无版本约束——修法：补下限版本，锁文件保证精确；**"下限 + 锁文件"双层策略**是 2026 年标准（第 4 节））；**依赖与代码脱节**（README 说要装 A 但代码用的是 B——修法：`uv sync --frozen` 冷启动验证（01 篇的复现实验顺带查出这类问题）。**依赖审计的进阶**（2026 年工程惯例）：`uv audit`（或 pip-audit 类工具）扫描依赖的安全漏洞（CVE）——**"依赖有安全扫描"是 2026 年工程仓库的加分信号**（仓库「GitHub License」体系的依赖合规章节同源），个人项目至少知道这个动作存在。

**依赖管理的筛选信号**（面试官从依赖清单读出什么）：**依赖与项目定位的匹配度**（AI 项目用 fastapi/openai/langgraph/chromadb——技术线清晰；混入无关重量级框架 = 项目可能拼凑）；**依赖的"新旧感"**（还在用 `flask` + `requests` 手写一切 vs `fastapi` + `httpx`——2026 年的技术审美会看栈是否现代，老栈不是不能用，但"选型停滞"是一个信号）；**依赖的克制**（**能少则少**——每个依赖都是"我评估过"的宣言，依赖越克制越显得每个选择有理由——**"依赖列表是选型能力的投影"**，这也是面试深挖第一问（"为什么用这个库"）的素材来源。**"为什么用这个库"的答案模板**（依赖清单上的每个库都该能答）：**它解决了什么问题**（"chromadb 解决本地向量检索零部署"）→ **为什么不是别的**（"比 FAISS 多了持久化与过滤，比 Milvus 部署轻"）→ **边界是什么**（"单机规模够用，规模化换 Milvus——Level3 已演进"）——**三问能答的依赖是真选型，答不出的依赖是随大流**。**依赖清单的定期体检**（每完成一个 Level 后 10 分钟）：逐个依赖过三问——答不出的移除或补注释，版本过旧的升级——**"依赖清单与项目同步演进"是依赖管理的生命周期**，不是一次配好就完了。

## 5. 许可证与合规

2026 年开源合规是筛选者（尤其大厂）会看的细节：**项目自身的许可证**（README 或 LICENSE 文件——没有 LICENSE 的项目是"不可用的开源"；个人项目 MIT 起步（仓库「GitHub License」体系有完整选型））；**依赖的许可证风险**（AGPL 类依赖对商用项目的传染性——2026 年 AI 生态里 GGUF/量化工具、向量库的许可证各不同（Chroma 开源、Milvus Apache-2.0、部分 AI 组件是 AGPL）——**商用场景的合规检查**：依赖清单过一遍许可证（仓库「GitHub License」体系的依赖合规章节），个人学习项目记录"已知风险"即可）；**版权与数据合规**（项目里用的模型、数据集、代码片段注明来源——"借鉴了开源项目的 xxx 部分（Apache-2.0）"一句话，比被查出来专业得多）。**合规的简历价值**："我检查过项目依赖的许可证，选择了 Apache-2.0 的向量库"——这句话在 2026 年的大厂面试里是加分项（企业越来越重视开源合规）。

## 6. 自查清单

- [ ] pyproject.toml 有 name/version/description 完整元信息
- [ ] requires-python 与 .python-version 一致
- [ ] 生产依赖与开发依赖分组，`uv sync --no-dev` 可验证
- [ ] 依赖都有来源解释（README 或代码注释，说不出处的不引入）
- [ ] uv.lock 已提交且 `uv sync --frozen` 可执行
- [ ] 升级走 uv add 显式操作，升级记录与验证留存
- [ ] 项目有 LICENSE 文件（个人项目 MIT）
- [ ] 依赖许可证过一遍，商用风险已记录
- [ ] 使用的外部代码/模型/数据集注明来源
- [ ] **验证实验**：`uv sync --frozen --no-dev` 在干净环境执行成功

**达标标准**：清单全勾 + 依赖列表"每个都能说出为什么"。依赖规范是"看不见的工程素养"——筛选者不一定会细看，但深挖时（"你的项目为什么用这个库"）它决定回答的底气。

> 🎯 **核心要点**：依赖规范的硬性标准是"**可审、可分组、版本可追踪、合规可交代**"——pyproject.toml 是身份证、分组是边界、锁文件是精确、许可证是底线。四项齐了，依赖管理从"随缘"变成"工程"，而"为什么用这个库"也是面试深挖的第一类问题——**依赖管理就是面试答案的第一层**。
