## 1. 服务结构与模块划分

双栈项目中 Java 侧建议拆成两个可独立部署的应用，而不是一个大单体：**业务服务**（用户/订单/权限/支付）与 **AI 网关服务**（统一鉴权、路由、流式转发）。拆分的理由是变更隔离——AI 网关是双栈粘合点，迭代最频繁（协议调整、流式优化），独立部署避免每次改动都拖累业务服务发布。

模块划分以业务域为界：`user`（注册登录、RBAC 权限）、`order`（订单状态机、退款）、`address`（收货地址）、`tool`（Tool API 注册与分发）。`tool` 模块是双栈架构特有的，独立成包，因为它同时被"业务接口层"与"AI 工具调用层"两个入口复用——同一个能力（如改地址）既可以被前端直接调用，也可以被 AI Agent 工具调用触发，两条入口必须共用同一套服务方法、校验逻辑与幂等控制，否则会出现"前端改成功了、AI 调用同样的操作却报了不同错误"的诡异现象。

## 2. 业务能力实现要点

业务逻辑本身复用仓库既有知识（Spring 事务、MyBatisPlus、Redis 缓存、Sentinel 限流），双栈项目只强调三个差异点：

**第一，接口层设计双入口复用**。工具调用与前端调用走同一 Service 方法，Controller 层只做参数装配与鉴权，避免逻辑分叉：

```java
// 同一 Service 方法，两种入口复用
@Service
public class OrderService {
    @Transactional
    public OrderVO updateAddress(Long userId, Long orderId, AddressDTO addr) {
        // 订单归属校验（防越权：userId 必须匹配 orderId 归属）
        Order order = orderMapper.selectById(orderId);
        if (!order.getUserId().equals(userId)) throw new BizException("无权操作他人订单");
        // 状态机校验：仅待发货可改地址
        if (order.getStatus() != OrderStatus.PENDING_SHIP) throw new BizException("当前状态不可改地址");
        // ... 更新地址、记录操作日志（审计）
        return OrderVO.from(order);
    }
}
```

**第二，审计留痕贯穿所有写操作**。AI 触发的业务动作必须记录 `operator_type`（USER / AGENT）、`agent_session_id`、工具调用参数快照。面试官一定会问"AI 乱下单/乱退款怎么办"，审计表 + 人工确认位是最直接的答案。

**第三，退款等敏感操作设置人工确认状态位**。Agent 只能把退款单置为 `PENDING_APPROVE`，由用户前端确认后才真正执行。这既符合业务安全，也是 Agent 安全设计（禁止自主执行高危操作）的落地。

## 3. Tool API 设计（核心）

Tool API 是 Java 侧给 Python 的"能力清单"，设计质量直接决定 Agent 的可用性。三条硬规则：

**规则一：参数即决策负担，一个工具只做一件事**。把"改地址"拆成 `query_address`（查）与 `update_address`（改）两个工具，而不是一个 `address` 工具带 `action` 枚举——模型对"何时调用哪个工具"的判断越简单，工具调用准确率越高。工具总参数不超过 5 个，每个参数写清楚含义与取值范围（通过 JSON Schema 的 `description` 传给模型）。

**规则二：服务端校验，不信任模型输出**。模型的参数输出可能有幻觉（订单号格式错误、userId 越权），Tool API 必须做完整校验：格式校验、归属校验、状态机校验、幂等校验。校验失败返回结构化错误（`{"code": 4001, "message": "订单不存在"}`）而不是 500，这样 Agent 能把错误回传给模型做二次规划。

**规则三：幂等设计**。退款、下单这类操作必须可重试：用业务单号（如退款单号）做唯一键，重复调用返回第一次的结果而不是重复执行。工具调用在 Agent 循环里天然会重试，幂等缺失会导致"用户退了一次款，账上扣了两笔"。

Java 侧注册工具时维护一个工具清单表（工具名、入参 Schema、鉴权要求、是否需人工确认、QPS 限制），它同时被三处消费：Python 侧的工具声明生成、网关的调用鉴权、审计的调用留痕。

## 4. 网关与限流

网关承担双栈的第一道防线：**前端只进 Java 网关，Python 服务不暴露公网**。网关职责：

- **鉴权**：校验 JWT，解析 userId 放入请求头（`X-User-Id`），下游业务服务与 Python 侧都信任该头；
- **AI 对话路由**：`/api/v1/ai/chat` 等对话类接口转发到 Python 服务，并做流式转发（05 篇详述 SSE 链路）；
- **限流**：Sentinel 按 userId 维度限流（每人每分钟 N 次对话），防止单个用户打爆 AI 服务——AI 服务是成本敏感型，一次对话可能消耗上千 token；
- **工具调用鉴权**：Agent 回调 Tool API 时校验会话身份（网关签发 service token），并核对工具权限（该 Agent 是否被允许调用退款类工具）。

## 5. 缓存与事务

业务侧沿用仓库既有模式：读多写少的订单快照、地址等走 Redis 缓存 + 旁路更新；订单状态机变更走 MySQL 事务 + 乐观锁（`UPDATE ... WHERE status = ?` 防并发改单）。双栈场景新增一个注意点：**对话相关的热点数据（会话摘要、意图上下文）也放 Redis**，Key 设计为 `ai:session:{sessionId}`，由 Python 侧读写、Java 侧网关只透传 sessionId——数据归属清晰，避免两端各存一份。

分布式事务按业务需要引入：退款涉及订单表、退款单表、余额表三处更新，可先用本地事务 + 消息最终一致（退款成功发 MQ 事件）；如果面试要展示 Seata，可把"退款→库存回补"设计成 AT 事务。展示顺序建议：先讲本地事务 + 最终一致的默认方案，再讲 Seata 的引入动机，体现"知道什么时候不需要分布式事务"。

## 6. 降级兜底

AI 服务故障不能拖垮业务，Java 侧必须具备独立降级能力：对话接口返回兜底话术（"客服繁忙，请拨打热线"）+ 转人工提示；工具调用链路不受影响（前端直接调用业务接口仍可用）；网关对 Python 服务做超时熔断（Resilience4j：连续失败 N 次进入 OPEN，半开探测恢复），避免 Python 假死导致请求堆积。降级开关放配置中心（Nacos），做到秒级切换。

## 7. 核心要点

1. 业务能力双入口复用：前端调用与 AI 工具调用共用同一 Service 方法，杜绝逻辑分叉。
2. Tool API 三规则：一工具一职责、服务端校验不信任模型、幂等可重试。
3. 敏感操作（退款）必须人工确认状态位，Agent 无自主高危操作权限。
4. 网关三条防线：JWT 鉴权、userId 维度限流、工具调用权限核对。
5. 降级是面试必问：关掉 Python，对话兜底话术、业务接口无损。

> 🎯 **核心要点**：Java 底座的面试叙事是"**把不可靠的 AI 决策接到可靠的业务执行上**"——Tool API 的校验、幂等、审计、人工确认四件套，就是这道接缝处的安全网。面试官深挖的每一个异常分支，都在这四件套里有对应设计。
