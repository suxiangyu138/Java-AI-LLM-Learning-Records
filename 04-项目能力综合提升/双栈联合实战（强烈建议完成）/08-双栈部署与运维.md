## 1. 一体化编排（Docker Compose）

本地开发与演示环境用 Docker Compose 一键拉起全部服务（2026-08 基准 Compose v5，`version` 字段已废弃）：

```yaml
services:
  mysql:        { image: mysql:8.4, environment: { MYSQL_ROOT_PASSWORD: ... } }
  redis:        { image: redis:8 }
  milvus:       { image: milvusdb/milvus:latest }
  minio:        { image: minio/minio:RELEASE.2026-04-21T20-19-49Z }
  java-gateway: { build: ./java/gateway, ports: ["8080:8080"], depends_on: [mysql, redis] }
  java-service: { build: ./java/service, depends_on: [mysql, redis, rocketmq] }
  ai-service:   { build: ./python, environment: { LLM_BASE_URL: "http://host.docker.internal:11434/v1" } }
  nginx:        { image: nginx, ports: ["80:80"], depends_on: [java-gateway] }
```

三个编排要点：**服务发现**——内网用 Compose 服务名直连（`http://ai-service:8000`），不引入注册中心，降低复杂度；**密钥注入**——service token、MySQL 密码用 `.env` + Docker secrets 注入，不进镜像；**启动顺序**——`depends_on` 配合健康检查（`healthcheck`），Java 服务等 MySQL/Redis 就绪再启动，Python 服务等 Milvus 就绪再启动。本地模型（Ollama）跑在宿主机用 `host.docker.internal` 访问，容器内不装模型——这既省镜像体积，也符合"模型与代码分离"的管理原则。

## 2. 双栈镜像构建规范

两套技术栈的镜像规范各异，但原则一致：**小、快、安全**。

Java 侧用多阶段构建（基础镜像 maven → 编译 → 运行镜像 eclipse-temurin，只带 Jar 与配置文件），构建缓存利用依赖层；运行镜像禁用 root（`USER app`）。Python 侧两个关键决策：**依赖锁定**——用 `uv`（2026 主流）或 requirements.txt 哈希锁定，禁止裸 `pip install -r`（依赖漂移是 Python 镜像最常见的事故源）；**虚拟环境内置**——镜像内不装系统 Python 包，避免与宿主机冲突。

版本管理纪律：镜像一律打双标签（`latest` + 具体版本如 `v1.4.2-<commit>`），回滚时拉具体版本标签而不是 latest——latest 回滚等于回滚到不知道什么版本，是生产事故的高发姿势。

## 3. CI/CD 双流水线

双栈项目用**两条独立流水线**，而不是一条串行大流水线：Java 流水线（Maven 构建 → 测试 → 镜像 → 发布 Java 服务）与 Python 流水线（uv sync → pytest → 镜像 → 发布 AI 服务）。两条流水线可并行、可独立回滚，这是双栈"变更隔离"在工程上的延伸。

流水线共同的门禁：静态检查（Java Checkstyle / Python Ruff）、单元测试、镜像漏洞扫描（Trivy，CVSS ≥ 7 阻断）。发布策略按服务重要度分级：Java 业务服务用滚动发布或蓝绿（订单类接口不容有损），Python AI 服务用金丝雀（先 10% 流量验证模型行为无回归，再全量）——AI 服务的行为变更难以用单元测试覆盖，灰度是唯一可靠的验证手段。

**跨栈联调是 CI 的盲区**：单元测试各自通过不代表联合可用，流水线中加一道"契约测试"（用 Pact 或轻量脚本校验 Java 与 Python 的接口契约字段一致），双栈项目的发布事故一半以上是契约漂移，门禁放在 CI 里最划算。

## 4. 扩缩容与并发模型

Python AI 服务的性能画像与 Java 完全不同：**AI 调用是 IO 密集型 + 外部依赖**（模型 API 响应秒级），CPU 消耗集中在向量化与 token 处理。并发模型对应设计：

- **Uvicorn workers**：多 worker 提升吞吐，worker 数 ≈ CPU 核数 × 2（有 GIL 限制，纯 CPU 任务多 worker 收益递减）；异步接口（SSE 流式、模型流式）在单个 worker 内用 asyncio 并发承载——流式场景 worker 多反而可能拖累内存，单 worker + 高并发异步是流式服务的正确姿势；
- **无状态设计**：会话状态在 Redis + LangGraph 检查点（Postgres/Redis checkpointer），任意实例可接管任意会话——这是扩缩容的前提，也是 04 篇检查点设计的复用；
- **独立扩缩容**：AI 服务流量暴涨时只扩 Python（对话高峰），不碰 Java——双栈的弹性红利。

Java 侧沿用仓库体系：虚拟线程或 Tomcat 线程池调优、Sentinel 限流。面试叙事：压测数据（如 SSE 流式 200 并发、首 token P95 < 1.5s、单实例承载 N 路并发对话）要真实测得并写进文档，这是 10 篇简历量化的素材。

## 5. 模型与依赖管理

模型是双栈项目中最特别的"依赖"，管理纪律三条：

- **模型与代码分离**：模型选择是配置（环境变量），不是代码；切换模型（云端 API 换本地 Ollama）零代码改动，发布会话中不携带模型切换；
- **版本与降级**：记录每次模型变更的评估结果（同批测试集问答准确率对比），保留上一版本配置以便快速回退——模型行为突变（供应商更新模型）是线上事故源，必须有回退路径；
- **成本可见**：对话量 × token 单价要能按月统计（网关记录 token 用量），超出预算自动降级到小模型或限流——AI 服务的成本失控是 2026 生产运维的头号话题，能讲出成本治理的项目在面试中是稀缺品。

Python 依赖与模型同理：依赖锁文件提交仓库、模型锁版本（供应商 API 模型名锁定，不用 `latest` 语义），两类"外部可变依赖"都要显式管理。

## 6. 监控告警与故障演练

监控沿用仓库可观测体系（Prometheus + Grafana），双栈新增两个维度的指标：**跨栈链路指标**（对话请求量、首 token 延迟 P50/P95、工具调用成功率、Python 服务错误率）与**成本指标**（每日 token 消耗、按会话类型分布）。

告警基线（示例）：首 token P95 > 2s 持续 5 分钟告警、工具调用失败率 > 10% 告警、Python 服务 5xx 率 > 1% 告警、token 消耗环比 > 50% 告警。告警要配套收敛策略：同一 traceId 下的多条告警聚合为一条（一次 Python 故障会同时触发 5xx、延迟、错误率三条告警，不聚合就是告警疲劳，2026 告警治理的行业共识是"告警要让人愿意看，而不是让人习惯忽略"）；P1 告警接电话、P2 走工作群、P3 只记录，分级避免噪音淹没真故障。

**故障演练是面试杀手锏**：每月演练一次"关掉 Python 服务"（验证降级话术与业务无损）与"kill Java 网关进程"（验证前端报错可读、恢复后会话可续），演练记录写进项目文档——面试官问"你怎么保证系统可靠"，一份带日期的演练报告比十句承诺有力。

## 7. 核心要点

1. Compose 一键编排：服务名内网互连、密钥 secrets 注入、健康检查控制启动顺序。
2. 镜像双规范：Java 多阶段构建非 root；Python 依赖哈希锁定、镜像内置虚拟环境。
3. 双流水线：Java/Python 独立构建发布独立回滚，CI 加契约测试堵住跨栈漂移。
4. Python 扩缩容前提：无状态 + 检查点持久化；流式服务单 worker 异步并发。
5. 模型即依赖：配置化、版本化、可回退，成本按月可见，超预算自动降级。

> 🎯 **核心要点**：部署运维的面试价值是"工程成熟度"的证据链：一键编排脚本、双流水线配置、压测数据、演练报告——每一项都是可验证的交付物。面试官看到的不只是"你会用 Docker"，而是"你把一个双栈系统当生产系统在管理"。
