## 1. 面试官考察地图

深挖双栈项目时，面试官背后只有四个问题：**做过吗**（细节与源码）、**理解吗**（决策理由）、**踩过坑吗**（故障复盘）、**扛得住吗**（工程化运维）。四条线对应：

| 考察线 | 提问方向 | 判断标准 |
|---|---|---|
| 真实性 | 源码细节、表结构、异常分支、具体数字 | 答得出"我的代码里 XX 怎么写的" |
| 决策理解 | 为什么双栈、为什么 LangGraph、为什么 SSE | 有取舍分析，不是"大家都这么用" |
| 故障复盘 | 调试中遇到的最大问题、怎么定位的 | 有真实事故 + 定位方法 + 复盘结论 |
| 工程能力 | 部署、监控、演练、成本治理 | 有可验证的交付物（脚本/报告/数据） |

答不好的共性：讲述停在"功能"层（做了什么），没进入"决策与取舍"层（为什么、代价）。以下答法全部按决策层组织。

## 2. 高频追问与标准答法

**Q1：为什么 Java + Python 双栈，不直接用 Spring AI？**
答：职责边界不同。Java 侧需要承载订单、退款这类强一致业务，Python 侧需要快速迭代 Agent 编排与检索——LangChain/LangGraph 的工具链成熟度和迭代速度远超 Java AI 生态。拆分后换模型只改 Python 配置、Prompt 迭代不重启业务服务、AI 故障可降级不影响交易链路。**补充**：AI 深度不高时 Spring AI 也够用——主动说清边界更得分。

**Q2：前端为什么不直连 Python 服务？**
答：统一鉴权与审计。Python 不暴露公网，所有请求经 Java 网关：JWT 解析、限流（对话是成本敏感操作）、工具权限核对、trace 起点都在网关一处。前端直连等于身份验证与审计散落两套体系，安全排查双失控。

**Q3：Python 侧怎么保证不写坏业务数据？**
答：单写者规则 + 权限隔离。每份数据只有一个写入者：业务表只有 Java 写，对话数据只有 Python 写。MySQL 给 Python 仅独立库 `ai_chat_db` 权限，Milvus/ES 关闭 Java 写入。Python 需要业务数据一律经 Java 查询类 Tool API 获取。

**Q4：Agent 调用退款工具出错了怎么办？**
答：三层防线。决策层：退款工具默认需人工确认（PENDING_APPROVE）；执行层：Java 侧全量校验（归属、状态机、幂等），失败返回结构化错误码供模型重新规划；补偿层：审计表全量留痕可回滚。模型不可信是前提，安全边界全落在 Java。

**Q5：模型切了供应商，怎么验证没变差？**
答：回归集评估。维护固定测试集（50-100 条问答 + 工具用例），切换前后跑同一套评估（准确率 + 工具调用正确率 + 首 token 延迟），通过才放量，保留旧配置可回退。模型行为会突变（供应商更新），三件套缺一不可。

**Q6：一次对话很慢，你怎么定位？**
答：链路追踪三步。先在 OTel 面板看 span 分布：慢在意图识别、检索还是工具调用；再对拍契约（字段/超时配置）；最后按 traceId 对时日志。真实案例：慢不在模型而在 ES BM25 字段名写错导致检索超时重试——事故复盘就是定位方法的证明。

**Q7：Python 服务挂了，系统会怎样？**
答：降级设计。网关对 Python 熔断（滑动窗口），对话接口返回兜底话术 + 转人工，业务接口不受影响；Python 恢复后半开探测自动回归。每月演练一次，记录在案。

**Q8：双栈数据怎么保证一致？**
答：跨栈数据承认最终一致，收敛靠四层：状态机（PENDING → PARSING → READY/FAILED）、幂等重试（ingest 以 doc_id 为幂等键）、超时巡检、人工兜底（死信 + 告警）。强一致只存在于 Java 业务域内部。

**Q9：SSE 断了怎么办？**
答：三层恢复。前端 EventSource 自动重连（Last-Event-ID 续传）；网关空闲超时 60s 与总时长 5 分钟分离，心跳帧 15s 防代理断连；Python 侧会话在 LangGraph 检查点，重连后续推未消费帧。断连恢复靠完整设计而非默认行为。

**Q10：项目里最大的坑是什么？**
答：讲真实事故（优先跨栈特性）：ES BM25 字段名不匹配静默返回零结果、工具回调未设超时导致 Agent 卡死、SSE 断流是代理空闲超时。叙事模板：现象 → 定位（追踪/日志/对拍）→ 根因 → 防复发。

## 3. 简历写法

简历核心是**量化与归因**，每条 bullet 都要能被追问到源码与数据：

- **量化结果**：不说"实现智能客服"，说"对话意图识别准确率 92%（200 条测试集）、首 token 延迟 P95 1.2s、SSE 流式 200 并发压测无断流、退款经人工确认后零资损事故"；
- **动作动词 + 架构决策**：不说"用了 LangGraph"，说"基于 LangGraph StateGraph 设计四节点 Agent 编排，以检查点实现会话断点续流"；
- **体现工程化**：双栈 CI 流水线、契约测试门禁、OTel 全链路追踪、月度故障演练——这些是"校招项目"与"真实系统"的分界线；
- **按岗位侧重**：投 Java 后端突出 Tool API 设计、网关限流、单写者数据设计；投 AI 应用突出 Agent 编排、混合检索、护栏设计；不堆砌关键词，每句可深挖。

## 4. 双栈项目十大避坑

1. **Jython 嵌入 JVM**：只支持 Python 2.7，跑不了现代框架——双栈必须独立服务；
2. **前端直连 Python**：鉴权与审计双体系失控，违反网关前置铁律；
3. **双栈双写业务数据**：没有单写者规则，订单状态被两端覆盖，数据漂移无解；
4. **跨栈调用不设超时**：Python 假死拖死 Java 线程池、Java 慢查询拖死 Agent 循环——超时分级第一天就要做；
5. **无降级设计**：AI 服务一挂整个系统不可用，面试一问"挂了怎么办"直接露怯；
6. **模型名写错**：供应商真实 ID 与代码不一致（deepseek-chat 被路由错供应商），报错信息误导排障；
7. **WebSocket 做对话流式**：为不需要的双向能力付出心跳、缓冲、代理配置三套复杂度，SSE 更简单可靠；
8. **ES 字段名不匹配**：BM25 检索静默返回零结果，问题难发现——先查索引映射；
9. **契约无版本无清单**：两端同步改字段，发布不同步直接生产事故；
10. **把模型当代码**：没版本化、没回归评估、没回退路径，供应商一更新行为突变无法应对。

每条避坑的完整展开在对应模块，面试前挑 3-4 条真实相关的练成事故故事。

## 5. 面试演练建议

- **自问自答**：对着 Q1-Q10 逐题录音作答，检查是否有取舍分析；说不出理由就是没真懂，回对应模块补；
- **交叉追问演练**：让同伴从简历任一句话连续追问 5 层"为什么"，答不出就是软肋；
- **演示彩排**：五场景演示彩排 3 遍，异常分支必须演练——现场出题时稳住的唯一方式是预演过；
- **数据核对**：简历每个数字都要能现场复现或出示压测记录，说错比没有更致命。

## 6. 核心要点

1. 考察四线：真实性、决策理解、故障复盘、工程能力——答案全部落在"决策与取舍"层。
2. 十问十答是骨架，每条都能扩展成 2-3 分钟回答并关联到代码与数据。
3. 简历量化 + 按岗位侧重，每句可深挖，数字可复现。
4. 十大避坑挑 3-4 条真实相关者，练成事故故事（现象 → 定位 → 根因 → 防复发）。
5. 演练三件套：录音自答、5 层追问、异常分支彩排。
> 🎯 **核心要点**：双栈项目的面试成败不在技术深度，而在**讲述的真实性与决策的完整性**。把 09 篇的验收演示、调试事故、复盘清单当作全部回答的素材底座，把本页十问当作骨架——你回答的每一句都该让面试官看到"这个人真的把系统从零设计到上线过"。
