## 1. 通信方式四选型

Java 与 Python 之间的通信方式没有银弹，按场景四选一（2026 行业统一规范）：

| 方式 | 适用场景 | 本项目用法 | 注意点 |
|---|---|---|---|
| REST / JSON | 常规问答、单次工具调用 | 工具回调 Java Tool API | 同步语义，超时必须分级 |
| 消息队列（RocketMQ/Kafka） | 长周期任务、批量处理、异步解耦 | 文档批量入库、异步审计 | 消费幂等、顺序性按需 |
| gRPC + Protobuf | 高实时调度、批量流式传输 | 一般项目可不用，面试提即可 | 序列化约为 JSON 1/5 带宽，但调试成本高 |
| MCP 协议 | 跨语言工具调用标准化 | 进阶方向，工具发现与鉴权统一 | 2026 官方推荐方向 |

选型决策的原则是**按延迟与同步性需求排序**：对话链路上的同步调用（工具回调）用 REST；不要求即时反馈的用 MQ；只有高频批量流式场景才值得上 gRPC——不要为了展示技术栈而引入 gRPC，面试官会问"JSON 为什么不行"，答案应该是"行，所以我们没用 gRPC"。

MCP 作为 2026 年的演进方向要能讲清楚：Java 侧集成 MCP Client，Python 侧工具通过 MCP 暴露，工具注册、鉴权、发现从"两方约定"升级为"协议统一"，双栈协作的未来形态。

## 2. 接口契约规范

跨栈接口最容易出的问题不是功能，而是**契约漂移**——Java 改了字段名，Python 不知道；Python 返回了新错误码，Java 没有兜底。三类规范在立项第 1 周就冻结：

**响应结构统一**：所有跨栈接口统一 `{"code": 0, "message": "ok", "data": {...}}` 包裹。`code` 分段约定：0 成功、4xxx 业务错误（4001 订单不存在、4002 无权限）、5xxx 服务错误。错误信息必须对人类和模型都可读——Agent 要把错误回传给模型做二次规划。

**时间与数字格式统一**：时间戳一律用毫秒级整数或 ISO 8601 字符串，禁止 Java 的 `LocalDateTime` 序列化格式直传（Python 解析会炸）；金额一律用分（整数）传输，杜绝浮点精度问题——这是金融业务红线。

**跨栈 SDK 共享**：两个栈各自维护一个契约客户端模块（Java 侧 `AiClient`、Python 侧 `JavaClient`），接口路径、字段名、错误码枚举集中定义，改动走双端同步评审。项目里可以没有共享契约文件，但必须有一个"契约变更清单"文档，记录每次字段/错误码变更与两端同步情况——面试展示这个清单，胜过展示任何框架。

**错误语义的跨栈一致性**：Java 侧抛出的业务异常（如"订单不存在"）在 Python 侧不能变成笼统的 500——错误码 4xxx 段必须原样透传，Python 把 `code + message` 组织成模型可读的文本回传（"订单 10086 不存在，请核对订单号"），模型据此修正追问或道歉。这要求两端的错误码表是一份文档的两栏（Java 枚举 ↔ Python 常量），任何一端新增错误码都要同步另一端，否则"模型读到未知错误码只能瞎猜"就会成为回答质量事故。

## 3. SSE 流式链路

对话流式链路是双栈通信最复杂的部分，完整链路：**前端 EventSource → Java 网关 → Python StreamingResponse → 模型流 → 原路回传**。

Java 侧用 `SseEmitter` 做代理转发，核心是"流式转发不能缓存"：

```java
@GetMapping("/api/v1/ai/chat/stream")
public SseEmitter chatStream(@RequestHeader("X-User-Id") Long userId, @RequestBody ChatReq req) {
    SseEmitter emitter = new SseEmitter(60_000L);           // 60s 空闲超时
    WebClient.create("http://ai-service:8000")
        .post().uri("/api/v1/chat").bodyValue(req)
        .retrieve().bodyToFlux(String.class)
        .doOnNext(frame -> emitter.send(frame))              // 逐帧透传，不做缓冲
        .doOnComplete(emitter::complete)
        .doOnError(e -> emitter.completeWithError(e))
        .subscribe();
    return emitter;
}
```

三个工程要点：**超时设计**——Python 侧模型流式响应可能持续数十秒，网关空闲超时（60s）与总时长上限（如 5 分钟）分开设置；**心跳**——每 15s 发一条注释帧（`: ping`），防止中间代理（Nginx）因空闲断开连接；**断连重连**——前端 EventSource 自动重连，Python 侧通过会话 ID 支持重放未消费的增量，配合 LangGraph 检查点实现"断点续流"。

断连重放的具体机制：每帧带自增 `seq` 序号，前端在 `Last-Event-ID` 头回传最后收到的 seq，Python 侧从检查点恢复后先重放 `seq+1` 之后的历史帧再续推新帧——这样掉线 10 秒重连后，用户看到的是连续完整的回答而不是从零开始。帧序号设计看似细节，但它同时解决了丢帧检测（seq 不连续即补帧）与重连续流两个问题，是流式链路稳定性的基石。

为什么不用 WebSocket：SSE 基于 HTTP、天然过代理、自动重连、单向足够（对话就是服务端往客户端推）。WebSocket 的双向能力在本场景用不上，却要处理心跳、帧缓冲、代理配置三套复杂度——选型时能讲清这个取舍，就是面试加分。

## 4. 超时、重试与熔断

跨栈调用必须有超时分级，并配套重试与熔断策略：

- **超时分级**：工具调用（同步、通常 < 1s）→ 2s；对话请求建立（首个字节）→ 3s；流式整体 → 5 分钟；RAG 检索 → 3s。每级超时独立配置，方便定位"慢在哪一段"；
- **重试策略**：仅对幂等操作重试（查询类可重试、退款不可盲重试），指数退避 + 抖动，最多 2-3 次。重试判断依据是错误类型：网络错误（连接失败、超时）可重试，4xx 业务错误不重试；
- **熔断**：Java 侧对 Python 服务做熔断（Resilience4j：滑动窗口统计失败率，超阈值 OPEN，半开探测恢复），Python 侧对 Java Tool API 同样做超时兜底（工具调用失败转错误回传模型，模型换策略或直接致歉）。

降级链路的面试叙事：Python 挂了 → Java 网关熔断 → 对话接口返回兜底话术 → 业务接口不受影响 → 监控告警 → Python 恢复后半开探测自动回归。每一步都有明确触发条件与恢复路径。

## 5. 版本管理与契约演进

跨栈接口从第一天就带版本：URL 前缀 `/api/v1/`，破坏性变更升 `v2`，旧版本保留 3-6 个月下线。两条演进铁律：

- **新增字段向后兼容**：Python 端新增返回字段，Java 端容忍未知字段（Jackson `FAIL_ON_UNKNOWN_PROPERTIES=false`）；Java 端新增入参，Python 端必须可选；
- **删除字段先下线后删码**：先停止生产流量使用，观察窗口过后再删字段，禁止"两端同时改"的发布方式。

契约变更的流程要文档化：变更发起 → 双端评审 → 排期同步发布 → 观察窗口 → 旧契约下线。双栈项目的发布天然不是原子操作（两套流水线先后执行），契约兼容策略就是为此兜底。

## 6. 核心要点

1. 四选型按需取用：对话同步走 REST、异步走 MQ、高频批量才上 gRPC、演进方向是 MCP。
2. 契约三统一：响应包裹结构、时间戳毫秒/金额分、错误码分段 0/4xxx/5xxx。
3. SSE 三件套：空闲超时与总时长分离、15s 心跳帧、EventSource 自动重连 + 检查点续流。
4. 熔断降级叙事完整：触发条件、兜底行为、恢复路径三步俱全。
5. 契约演进两铁律：新增兼容、删除先下线后删码，发布不同步靠兼容策略兜底。

> 🎯 **核心要点**：双栈通信的面试考核点集中在**决策与异常**：为什么 SSE 不用 WebSocket、工具调用失败怎么处理、Python 假死 Java 会怎样。把每一个"如果…会怎样"的答案提前想清楚，这一篇就是你的完整回答素材。
