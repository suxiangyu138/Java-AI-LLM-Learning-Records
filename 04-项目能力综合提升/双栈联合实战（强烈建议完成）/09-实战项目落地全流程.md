## 1. 项目全景与核心链路

项目定义：**支持订单自助服务的电商智能客服系统**。用户通过 Web 对话界面，让 AI 完成查订单、改地址、退款申请、知识问答、转人工五类任务，业务动作由 Java 底座执行，AI 能力由 Python 服务提供。

核心链路（面试画图必背）：**用户 → Java 网关（鉴权/限流）→ Python Agent（意图识别 → 工具决策 → 调用 Java Tool API → 生成）→ SSE 流式回传 → 前端逐字展示**。一次"帮我把订单 10086 的地址改成新地址"的完整流转：网关验 JWT → Python 识别意图 `update_address` → 工具声明匹配 → 回调 Java `update_address`（归属校验 + 状态机校验 + 幂等 + 审计）→ 成功返回 → Python 生成确认话术 → 流式返回用户。全链路 trace 可见、审计留痕、敏感操作（退款）置人工确认。

## 2. 端到端代码走查

**链路一：对话入口（Java 网关 → Python）**。网关收前端请求，携带用户身份转发 Python，并透传 trace 头：

```java
// Java 网关：对话请求转发 + 身份注入
@PostMapping("/api/v1/ai/chat")
public Flux<ChatFrame> chat(@RequestHeader("Authorization") String token, @RequestBody ChatReq req) {
    Long userId = jwtUtil.parse(token).getUserId();
    return webClient.post().uri("http://ai-service:8000/api/v1/chat")
        .header("X-User-Id", userId.toString())
        .header("traceparent", tracer.getTraceparent())   // 全链路追踪透传
        .bodyValue(req)
        .retrieve().bodyToFlux(ChatFrame.class);
}
```

**链路二：Agent 工具循环（Python）**。LangGraph 图节点：`route` 判断是否调用工具，`ToolNode` 执行工具声明（回调 Java）：

```python
# Python：工具调用回调 Java Tool API
@tool
def update_address(user_id: int, order_id: str, address: str) -> dict:
    """修改订单收货地址。仅待发货订单可修改，需先调用 query_order 确认订单状态。"""
    resp = java_client.post("/api/v1/tools/order/update-address",
                            json={"userId": user_id, "orderId": order_id, "address": address})
    return resp.json()   # {"code":0} 或 {"code":4002,"message":"订单不属于该用户"}
```

**链路三：工具执行（Java 业务服务）**。与 03 篇双入口复用的 `updateAddress` 同一方法，此处只多一层工具会话鉴权（校验 service token 与会话工具权限）。三条链路串起来即是完整闭环，代码量控制在三个类以内——项目复杂度主要在"把每条链路的异常分支想全"，不在代码量。

## 3. 五场景验收演示

| 场景 | 演示要点 | 验收标准 |
|---|---|---|
| 查订单 | "帮我看看最近的订单" | 意图识别正确、工具调用、流式返回订单摘要与状态 |
| 改地址 | "订单 10086 改地址" | 归属校验拦截他人订单；待发货才可改；成功回执 |
| 退款申请 | "退掉订单 10086" | 置人工确认、前端确认后执行、余额正确回补 |
| 知识问答 | "退换货政策是什么" | 混合检索返回带引用来源的回答，索引无过期内容 |
| 转人工 | "我要投诉" | 识别转人工意图、生成工单、人工接管后会话衔接 |

演示脚本要点：每个场景配好测试数据（固定用户、固定订单号），演示前清空状态并用脚本批量重灌测试数据——上次验收的残留数据是演示翻车的第一原因；加分项是演示"异常分支"——查不存在的订单、改他人订单、AI 服务断开后的降级话术。面试官现场出题时，异常分支才是你与"背稿型"候选人的分水岭。

## 4. 调试三板斧

双栈联调的问题定位遵循固定顺序，每板斧都要能当场演示：

**第一斧：链路追踪看全貌**。一次"回答慢/报错"先在追踪面板看完整 span 链：慢在 Python 生成（模型侧）还是 Java 工具调用（业务侧），问题域立刻收敛。注意：如果 trace 显示调用链断了，先查 `traceparent` 头是否透传，这是双栈追踪第一大坑。

**第二斧：契约与序列化排查**。跨栈报错 90% 是契约问题：字段名拼写、时间戳格式、金额精度、枚举值不一致。对拍方法：同一请求分别用 Java 与 Python 的客户端调用目标接口，比对报文差异；Java 侧确认 `FAIL_ON_UNKNOWN_PROPERTIES=false`，Python 侧确认 Pydantic 模型字段名与 JSON 大小写一致。

**第三斧：日志对时定位**。链路追踪查不到时，回到 JSON 日志按 traceId 关联双端日志，比对时间戳与关键节点。日志排查的前提是 07 篇的统一格式规范——没有统一字段，这一步就是大海捞针。三板斧用完还定位不到，考虑网络层（容器网络、防火墙、DNS 解析）问题。

## 5. 工作量复盘与经验

单人 3-4 周的工作量分布与排期复盘：第 1 周立项与契约（最容易被低估——契约没冻结，后面每周都在改接口）；第 2 周 Java 底座与 Tool API（代码量最大但难度可控）；第 3 周 Python 服务与链路打通（最耗时的是流式调试而非 Agent 编写）；第 4 周安全部署与验收（验收清单逐项过，补降级与演练）。

三条经验直接复用：**契约先行**——第 1 周冻结的契约变更清单，后面每改动一次都有记录，双栈项目没有契约文档 = 双倍返工；**先跑通最小闭环再添功能**——第 3 周第一天只做"一句话 → 模型回答"的直连，第二天再接工具调用，链路越长越要小步走；**异常分支的演示即面试素材**——把调试中遇到的真事故（BM25 字段名错误、工具回调超时、SSE 断流）整理成复盘清单，每一个都是 10 篇面试的弹药。

项目交付时整理四份文档，是面试深挖的完整素材库：**需求文档**（功能/非功能/栈归属拆分表，立项那周的产物）；**接口契约清单**（跨栈接口、字段、错误码，每次变更留记录）；**验收脚本**（五场景 + 异常分支的可复现操作步骤与预期结果）；**事故复盘记录**（现象 → 定位 → 根因 → 防复发的完整故事）。四份文档加代码仓库，就是"项目是你设计的"最硬证据——面试官可以随时要求打开任意一份展开讲。

最后给"完成"下个可判定的定义：**不是代码写完了，而是验收清单全绿、四份文档齐备、五场景演示可复现**。这一定义写入排期文档，复盘时按它逐项核对，项目收尾才有客观标准，而不是"感觉做得差不多了"。

## 6. 核心要点

1. 核心链路一句话背熟：网关鉴权 → Agent 决策 → Tool API 执行 → SSE 回传。
2. 双入口复用是代码正确性的关键：前端与 Agent 走同一 Service 方法。
3. 验收五场景 + 异常分支演练，演示脚本固定数据、提前清状态。
4. 调试三板斧：追踪看全貌 → 契约对拍 → 日志对时，顺序固定。
5. 契约先行、最小闭环先通、事故即素材——三条经验贯穿全流程。

> 🎯 **核心要点**：实战篇的价值不是代码本身，而是**可演示的完整闭环与可讲述的真实事故**。验收脚本、调试记录、复盘清单三份文档，撑起 10 篇面试的每一句回答。
