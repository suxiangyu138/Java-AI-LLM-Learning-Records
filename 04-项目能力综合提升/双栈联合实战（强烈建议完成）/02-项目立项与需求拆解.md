## 1. 项目选型：三大方向

2026 年校招双栈项目的主流方向有三个，各有侧重：

**方向一：AI 智能客服（推荐）**。用户对话 → 意图识别 → 工具调用（查订单、改地址、退款）→ 业务动作执行 → 流式回答。它的优势是**业务闭环完整**：有真实状态流转（订单状态机）、有真实的工具调用（不是演示性的"天气查询"）、有对话与业务数据的双向依赖。智能客服是金融与电商场景的原生刚需，企业里真实存在，面试官天然认可，追问素材最多——本文体系 09 篇的端到端案例即以此为主线。

**方向二：企业知识问答（RAG 深潜）**。文档上传、解析、向量化入库、混合检索、引用溯源。优势是 AI 侧深度突出（分块策略、混合检索、重排、评估），但业务侧天然薄弱——Java 端容易只剩文件管理 CRUD，双栈分工失衡。适合已经在 LingShu 做过 RAG、想加深检索调优的同学，此时应主动给 Java 端加业务职责（权限、审计、发布流程）。

**方向三：多 Agent 助理（编排深潜）**。旅游规划、会议纪要、购物管家等多 Agent 协作。优势是 Agent 编排的复杂度和故事性最强（Supervisor 模式、Fan-out/Fan-in 并行、降级循环），但工具调用的真实性依赖业务侧支撑，纯 Demo 风险最高。

选型判断标准三条：**有没有真实用户价值、有没有状态流转、有没有非 AI 不可的理由**。三者都满足（智能客服）最佳；只能满足前两者的（知识问答），靠加业务职责补救；三者都弱的，换项目。

## 2. 需求拆解方法

立项后先用一页纸把需求拆成两半：功能需求与非功能需求，双栈项目还要多拆一层"栈归属"。

**功能需求**（以智能客服为例）：多轮对话、意图识别（查订单/改地址/退款/咨询）、工具调用与人工确认（退款必须确认）、知识库问答（常见问题）、工单转人工、对话历史查询。每个功能都要能回答"触发条件、输入输出、异常分支"三个问题，例如退款：用户提出 → 校验订单归属 → 金额与原因确认 → Java 执行退款 → 结果回填对话。

**非功能需求**：首 token 延迟（一般目标 < 1.5s）、并发对话数、AI 服务不可用时的降级行为（规则引擎/缓存话术兜底）、敏感信息脱敏（身份证、手机号）、审计留痕（谁在什么时间让 AI 做了什么）。

**栈归属拆分**：把每个功能点标上"Java / Python / 双栈"。判定规则沿用 01 篇的分工判别法——涉及状态变更的归 Java（退款执行、地址修改），涉及理解生成的归 Python（意图识别、回答生成），链路类功能标双栈（对话请求经网关、工具回调回 Java）。标注完成后检查：如果 Python 侧功能点少于 4 个，说明项目偏业务；Java 侧少于 3 个，说明业务底座单薄，两种情况都要在需求阶段补平。

## 3. 技术选型矩阵

选型原则：**能用熟悉的不冒险，需要展示深度的选有讨论空间的主流方案**。以 2026-08 为基准的推荐组合：

| 层 | 选型 | 版本基准 | 选型理由 |
|---|---|---|---|
| Java 框架 | Spring Boot | 4.1.x / Framework 7.0 | 仓库体系主线，工程化成熟 |
| Java 数据 | MySQL + Redis + RocketMQ | MySQL 8.4 / Redis 8 | 业务库、缓存、异步解耦 |
| Java 治理 | Sentinel / Seata | 1.8.x / 2.6.x | 限流熔断与分布式事务，面试硬通货 |
| Python 框架 | FastAPI | 0.139 / Pydantic 2.13 | AI 服务事实标准，SSE 原生支持 |
| Agent 编排 | LangGraph | 1.2.x | 图编排 + 检查点持久化 + 人工介入 |
| 向量检索 | Milvus | 3.x | 仓库已有体系，混合检索成熟 |
| 模型接入 | OpenAI 兼容协议 | DeepSeek / Qwen | 协议统一，模型切换只改配置 |
| 部署 | Docker Compose → K8s | Compose v5 | 本地一体化，后续可上 K8s |

两处容易被面试追问的取舍要提前想好理由：Agent 编排为什么用 LangGraph 而不是 LangChain 原生链式（有状态、可持久化、支持人工审批中断点恢复）；向量库为什么用 Milvus 而不是 Chroma（生产级、混合检索、分片扩容），若机器内存有限用 Chroma 起步也可以，但要在文档里写明"本地开发替换 Milvus 的取舍"。

## 4. 里程碑规划与工作量

按"两端并行 + 横切主题串行"的原则排期，单人 3-4 周为合理预算：

| 周次 | 里程碑 | 交付物 |
|---|---|---|
| 第 1 周 | 立项 + 两端骨架 | 需求文档、接口契约 v1、Java/Python 服务可启动 |
| 第 2 周 | Java 业务底座 + Tool API | 订单/用户模块、Tool API 全部就绪 |
| 第 3 周 | Python AI 服务 + 通信打通 | Agent 编排跑通、SSE 流式全链路、RAG 入库 |
| 第 4 周 | 安全/部署/验收 | 认证与追踪、Compose 一键起、验收清单全过 |

排期最常见的失败模式是"先把 AI 做漂亮，最后补业务"——Python 侧的 Demo 效果诱惑大，但第 4 周你会发现 Java 业务还没闭环，验收与面试深挖全部落空。正确的顺序是**先业务后 AI**：第 2 周业务底座与 Tool API 完成后，Agent 才有真实工具可调。

## 5. 验收标准

验收不是"能跑"，而是能讲、能演示、能扛追问：

- **业务闭环**：5 个核心场景端到端可演示（对话查订单、改地址、退款确认、知识问答、转人工），每个场景都能讲清跨栈链路；
- **性能指标**：首 token 延迟 < 1.5s、SSE 流式稳定不中断、Java 网关限流生效（压测可见 429）；
- **降级演练**：关掉 Python 服务，对话模块仍返回规则兜底话术，业务接口不受影响；
- **安全演练**：提示注入样本不生效、脱敏字段不出现在日志与回答中、越权工具调用（查别人的订单）被 Java 拦截；
- **工程化**：Docker Compose 一键启动、链路追踪能在控制台看到一次对话跨 Java/Python 的完整 trace。

每项验收都对应一段可复现的演示脚本，这是 10 篇面试深挖的素材底座。

## 6. 核心要点

1. 项目选型三标准：真实用户价值、状态流转、非 AI 不可——智能客服三项全中。
2. 需求拆解必须多做一步"栈归属拆分"，两端功能点数要平衡。
3. 排期先业务后 AI：第 2 周 Tool API 就绪，第 3 周 Agent 才有真工具可调。
4. 验收五类（闭环/性能/降级/安全/工程化）逐项可演示，是面试故事的来源。

> 🎯 **核心要点**：立项阶段产出的需求文档、接口契约、验收清单，在面试中被深挖时的价值不亚于代码本身——它们证明你是"设计了系统"而不是"抄了个项目"。保留选型讨论记录（为什么 MQ 不用 Kafka、向量库为什么选 Milvus），面试直接引用。
