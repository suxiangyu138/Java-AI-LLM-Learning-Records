## 1. 数据域划分

双栈项目的存储不是"Java 用 MySQL、Python 用 Milvus"这么简单，而是按**数据域**划分所有权。以智能客服项目为例，数据分成四域：

| 数据域 | 归属 | 存储 | 写入者 | 说明 |
|---|---|---|---|---|
| 业务数据 | Java | MySQL + Redis | 仅 Java | 用户、订单、地址、退款单，生命线 |
| 对话数据 | Python | MySQL（Java 侧库）+ Redis | 仅 Python | 会话记录、消息历史、会话摘要 |
| 知识数据 | Python | Milvus + ES | 仅 Python | 文档块、向量、BM25 索引 |
| 文件数据 | 共享 | MinIO | 按类型 | 上传文件 Java 管元数据，Python 管解析 |

对话数据归 Python 写的理由：对话结构与 Agent 流程强耦合（检查点、会话摘要格式随编排演进），Java 侧只透传 sessionId，不解析内容。但对话数据可以物理上存在 Java 侧的 MySQL（Python 用独立库 `ai_chat_db` 隔离），避免再引入一套数据库运维。

## 2. 单写者规则

**单写者规则**：每份数据只有一个栈负责写入，另一栈只能通过 API 读取。这是双栈数据设计的第一铁律，对应 03 篇"Python 不直接操作业务数据"的设计。

违规的典型形态是"双栈双写"：Java 与 Python 各自维护一份订单状态副本并互相覆盖。为什么会发生？因为 Python 侧觉得"我只是更新一下会话里带的订单状态缓存"，Java 侧觉得"我更新了订单表"——两边都改，最终谁先提交谁赢，数据漂移。正确的替代方案：

- Python 需要业务数据（订单状态、用户信息）→ 通过 Java 的**查询类 Tool API** 获取，而不是直连 MySQL；
- Python 需要临时缓存 → 用独立 Redis 实例或独立 Key 前缀（`ai:`），严禁写 Java 业务 Key；
- Java 需要对话摘要 → 通过 Python 提供的查询接口或读独立库，严禁跨库解析。

单写者的执行保障是**权限隔离**而非自觉：MySQL 为 Python 创建仅库级权限账号（只能操作 `ai_chat_db`），Milvus 与 ES 为 Java 关闭写入账号（只读或不可达）。面试官问"怎么保证 Python 不写业务表"，答案是权限配置 + 规范文档双保险，不是口头约定。

两栈共享同一 Redis 实例时，**Key 命名与 TTL 规范**是防踩踏的细则：业务键 `biz:` 前缀、AI 键 `ai:` 前缀分区管理，所有 Key 显式设置 TTL（会话摘要 24h、临时上下文 10min），既防 Key 泄漏也防过期风暴——两端互不修改对方前缀下的 Key，是单写者规则在缓存层的延伸。

## 3. 知识库与向量库协作

知识数据链路横跨两端：**Java 收文件 → Python 解析入库 → 检索服务化**。完整链路：

1. 用户上传文档 → Java 校验权限与类型 → 存 MinIO → 业务表记 `doc_id` 与状态 `PENDING`；
2. Java 发 MQ 消息给 Python（或调 `/rag/ingest`）→ Python 下载文件、解析（PDF/Word/Markdown）、分块、向量化、写 Milvus + ES → 回写状态 `READY`；
3. 对话中知识检索由 Python 完成，结果只作为上下文注入，不回写 Java 业务库。

这条链路有两个高频事故点。其一是**入库与检索的索引一致性**：文档更新后必须"先删旧向量再插新向量"（幂等 ingest），否则旧版本文档块残留，检索出过期内容；其二是**失败重试的幂等**：`/rag/ingest` 以 `doc_id` 为幂等键，重复调用不产生重复向量。增量更新可以用定时全量重建（数据量小时最简单可靠），量大再上 CDC（监听 MySQL binlog 触发增量入库）——按数据量选方案，先简单后复杂。

## 4. 跨栈文件协作

文件数据走 MinIO（仓库已有完整体系，此处只讲双栈分工）：

- **Java 负责**：文件上传接口、元数据表（`file_meta`：文件名、大小、所有者、`doc_id`）、访问权限校验、生命周期管理（删除、归档）；
- **Python 负责**：从 MinIO 拉文件做解析处理，处理结果（向量、块文本）写自己的知识库，不碰元数据表。

分工依据仍然是单写者：文件本体在 MinIO 是共享资源（两边都读），但文件**元数据**只有一个写入者（Java）。Python 需要的任何元数据（文档类型、分块数、解析状态）都通过 ingest 回调参数传递，或由 Java 提供查询接口——这样即使 Python 侧把文件解析崩了，文件与元数据依然完整，重试即可。

## 5. 最终一致与补偿

双栈项目中"强一致"只存在于 Java 业务域内部；跨栈的数据流动（文档状态、对话会话、知识索引）都是**最终一致**，设计要点是让收敛路径可见、可补偿：

- **状态机驱动**：文档状态 `PENDING → PARSING → READY / FAILED`，每一步都有超时巡检（定时任务扫描 PENDING 超过 N 分钟的文档，重新投递或标记失败）；
- **消息兜底**：MQ 投递失败用死信队列 + 人工处理通道，消息成功但处理失败靠幂等重试，两种失败形态分开治理；
- **补偿清单**：明确记录"什么失败、怎么补偿、补偿多久收敛"，例如：向量入库失败 → 重试 3 次 → 置 FAILED 并告警 → 前端提示用户重新上传。

面试叙事的关键是承认"跨栈数据不可能强一致，但必须有收敛保证"——能讲出状态机 + 重试 + 巡检 + 人工兜底四层补偿的同学，和只回答"用 MQ 保证一致性"的同学，差距是整一层工程认知。

**数据重建与备份**要作为常规运维设计而非应急动作。知识库是跨栈数据里最需要重建能力的：向量与 BM25 索引的构建逻辑在 Python 侧，重建脚本必须以原始文档（MinIO 中的源文件 + 业务表的 `doc_id` 清单）为唯一输入、幂等可重跑——模型升级了 embedding 后旧向量全部作废，一键全量重灌是刚需；业务库沿用仓库备份体系（每日全量 + binlog 增量），恢复演练写进验收清单。面试口径：双栈项目的数据安全边界是"任何一份数据都要能回答三个问题——存在哪、谁写它、坏了怎么重建"。

## 6. 核心要点

1. 数据四域划分：业务（Java）/对话（Python）/知识（Python）/文件（共享），所有权先行。
2. 单写者铁律：每份数据一个写入者，另一栈只读 API，权限隔离保证执行。
3. 知识链路幂等：ingest 以 doc_id 为幂等键、先删后插，防止旧向量残留。
4. 文件协作：本体共享、元数据单写（Java），Python 只拉文件做解析。
5. 最终一致四层补偿：状态机 + 幂等重试 + 超时巡检 + 人工兜底，收敛路径可见。

> 🎯 **核心要点**：数据层的面试叙事是"**所有权**"三个字——能画出每张表/每个库/每个 Key 的写入者与读取路径，说明你真的设计过系统；答不出"这份数据归谁写"，再炫的架构图也会在追问下塌方。
