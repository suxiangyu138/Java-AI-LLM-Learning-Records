## 1. 项目选题：为什么是 AI 知识库问答助手

本层项目工程代号 `kb-prod`，定位是**「AI 知识库问答助手」**：用户上传文档 → 异步解析与向量化入库 → 提问时 RAG 检索增强生成 → SSE 流式返回。选题理由三句话：**有业务闭环**——「上传→入库→问答→流式返回」是一条完整的用户可见链路，演示时从上传文档到拿到答案，观众能看懂每一步在干什么；**有工程纵深**——链路里的每个环节都埋着工程问题：文档解析慢要异步（05 篇）、向量存内存会丢要 Milvus（03 篇）、AI 服务不稳定要降级（06 篇）、全链路要可观测（08 篇），这些恰恰是面试深挖的富矿；**技术栈主流**——RAG + Agent 是 2026 年 Java 后端 + AI 方向招聘的核心词，项目天然踩在热点上，简历关键词不牵强。

对比两个常见错误选题：**「又一个电商/博客系统」**——没有 AI 成分，与仓库已有项目重复，面试官一听就免疫；**「纯 API 封装项目」**——只调了 LLM 接口没业务，深挖两轮就到底。知识库问答助手的价值在于它同时覆盖「业务系统能力（CRUD/缓存/异步/限流）」与「AI 能力（RAG/评估/Agent）」，两端都有深挖空间。

## 2. 技术选型矩阵（2026-08 基准）

选型原则：**生产主流 + 简历价值 + 学习成本平衡**。每个组件选型时都问一句「换掉它行不行、为什么不行」，这组问答就是面试时「为什么选它」的答案来源：

| 组件 | 选型 | 版本基准（2026-08） | 选型理由 |
|---|---|---|---|
| 语言 | JDK 25 LTS | 25.0.4 | 与 Level1 一致，Boot 4.x 要求 21+ |
| 框架 | Spring Boot | 4.1.0（2026-06-10） | 当前主线，配套 Framework 7.0 / Jackson 3 |
| AI 框架 | Spring AI | 2.0.0 GA（2026-06-12） | ChatClient 主 API、ToolCallingAdvisor 自动注册、MCP 一等公民 |
| LLM | DeepSeek V4 | deepseek-v4-flash / v4-pro | OpenAI 兼容、1M 上下文、成本可控 |
| 关系库 | MySQL | 8.4 LTS | 文档元数据、用户、问答记录 |
| 缓存 | Redis | 8.x | 旁路缓存、限流计数、幂等键 |
| 向量库 | Milvus | 3.0.0（2026-07-29） | 湖原生、Docker 部署、Java SDK 成熟 |
| 消息队列 | RabbitMQ | 4.3.1 | Quorum Queue 数据安全、延迟重试原生支持 |
| 测试 | JUnit | 6.1.1 | 三平台架构，配合 AssertJ/Mockito/Testcontainers |
| 容器 | Docker Compose | v5 | 全栈一键编排，`version` 字段已废弃 |
| 监控 | Micrometer + Prometheus | 1.17 | Boot 4 内置集成，指标一行接入 |

两个需要论证的选型：**向量库为什么选 Milvus 而不是 PostgreSQL pgvector 或 Elasticsearch**——Milvus 是专职向量库，HNSW 索引性能与十亿级规模是 pgvector 的数十倍，而 ES 的向量检索是附赠能力，混合检索场景要自建服务；对简历项目，Milvus 是「专职向量库」的代表词，面试辨识度更高。**MQ 为什么选 RabbitMQ 而不是 Kafka**——本项目的异步场景是「文档解析任务队列」，量级小（每秒几条到几十条），RabbitMQ 的 Quorum Queue 开箱即用、延迟低、部署轻，Kafka 的吞吐优势在这个量级完全用不上，反而引入分区与消费者组复杂度。

选型还要回答一个总纲问题：**为什么用 Spring Boot 4.1 而不是 3.x**——4.x 是 2026 年的当前主线（Boot 4.1.0 于 2026-06-10 发布，配套 Framework 7.0 / Jackson 3 / Servlet 6.1），Spring AI 2.0 专为 Boot 4.0/4.1 设计，新项目没有任何理由回到 3.x 去踩「老基线 + 新 AI 框架不兼容」的坑；JDK 25 LTS 与 Boot 4.1 的基线匹配，Level1 已是 25，无需迁移。**多模块的代价也讲清**——四模块带来构建顺序与依赖管理的复杂度（kb-api 改了要重编整个依赖链），对个人项目，边界清晰的价值大于构建开销；如果未来拆微服务（Level3），模块边界就是服务边界，今天的拆分是为明天的拆分打地基。

## 3. 模块划分与包结构

按 Maven 多模块拆成四个工程，理由一句话：**依赖方向清晰、构建并行、边界可讲**：

```
kb-prod/
├── kb-common/      # 通用层：统一响应体、错误码、全局异常、工具类、日志规范
├── kb-core/        # 业务层：文档、知识库、问答领域模型 + service + mapper
├── kb-ai/          # AI 层：Embedding、RAG 检索、LLM 调用、Agent 工具（依赖 core）
└── kb-api/         # 接口层：Controller、DTO、VO、SSE 端点（依赖 core + ai）
```

包结构规范在 02 篇展开，这里定三条总纲：**依赖单向**——api → core → common，ai → core → common，禁止反向依赖与循环依赖，这是 Maven 模块化能讲清的第一课；**职责单一**——common 里不放业务代码，ai 里不放 Controller；**命名统一**——包名 `com.you.kb.*` 三级起，接口一律 `XxxController / XxxService / XxxServiceImpl / XxxMapper`。

## 4. 里程碑拆解

| 里程碑 | 周期 | 交付物 | 验收标志 |
|---|---|---|---|
| M1 工程化 | 第 1 周 | 四模块骨架 + 统一响应体/异常/校验/日志 | 全链路接口按新规范返回，代码过一遍评审 |
| M2 可靠性 | 第 2-3 周 | Milvus 入库检索、缓存一致性、MQ 异步解析、限流降级 | 四个模块各自有验证实验数据 |
| M3 交付 | 第 4 周 | 测试达标、指标面板、docker compose up 一键部署 | 新机器 10 分钟拉起全栈 |
| M4 AI 深度 | 第 5-6 周 | RAG 评估报告、Agent 工具调用、SSE 流式 | 评估指标可量化、面试题库过一遍 |

拆解原则：**每个里程碑都可演示、可验证、有明确结束点**；周计划细化到「每天一个可验证小目标」（今天让 Milvus 集合建好、今天让确认机制生效），延续 Level1 的正反馈节奏；**延期规则**——一个里程碑延期超过一周，砍范围而不是砍质量，M4 的 Agent 部分可以降级为「先工具后编排」。

## 5. 需求与验收标准

功能需求用用户故事定义（优先级 P0/P1/P2）：**P0 上传文档并解析入库**——支持 PDF/Markdown/TXT，解析成功后文档可见、失败有明确报错；**P0 基于知识库问答**——只基于库内文档回答，检索为空时明确告知；**P1 流式回答**——SSE 逐字返回，中断可重连；**P1 问答历史**——按用户维度保存与查看；**P2 Agent 工具调用**——文档统计、向量库状态查询等工具（10 篇展开）。

非功能需求是简历项目的差异化所在，必须写成**可度量指标**：**性能**——普通提问 P95 首字延迟 < 3s（含检索与模型首 token）；**可靠性**——AI 服务不可用时降级可用，缓存故障不阻塞写路径；**一致性**——缓存与数据库最终一致，最大窗口 < 1 分钟；**可维护性**——测试覆盖率 >= 70%，新增接口接入统一响应体与异常。指标的意义：**「压测过」和「压测过且 P95 3s 内」在面试里的说服力完全不同**，后续每篇的验证实验都对齐这里的指标。

## 6. 项目文档规范

代码之外的文档是「面试讲项目」的底稿，四个文件必须齐全：**README**——一句话定位、架构图、快速启动（10 分钟）、核心接口清单、测试与压测数据；**docs/design.md**——总体设计：模块图、数据流（上传链路 + 问答链路两条）、关键决策记录（ADR：为什么 Milvus、为什么 RabbitMQ，每条含背景/方案/理由）；**docs/eval.md**——RAG 评估报告（10 篇产出），含测试集、指标、对比实验；**CHANGELOG.md**——按里程碑记录「加了什么、为什么加、验证数据」，这是面试讲演进式开发的素材。规范原则：**文档跟着里程碑走，M1 结束 README 就要能看懂 M1 的内容，而不是最后补**。

## 7. 核心要点

1. 选题「AI 知识库问答助手」同时覆盖业务系统能力与 AI 能力，演示闭环清晰、深挖富矿充足。
2. 选型矩阵每个组件都能回答「为什么是它」，版本全部锚定 2026-08 最新主线。
3. Maven 四模块依赖单向（api → core/ai → common），边界清晰才能讲清架构。
4. 四个里程碑可演示可验证，非功能需求写成可度量指标（P95 < 3s、覆盖率 >= 70%）。
5. 文档跟里程碑走：README、design.md（含 ADR）、eval.md、CHANGELOG 四件套。

> 🎯 **核心要点**：立项阶段决定项目上限——**选题决定面试故事，选型决定深挖空间，里程碑决定能否做完**。本层的每一篇都是对这三个决策的兑现，设计文档里的每个 ADR 都是面试追问的标准答案。
