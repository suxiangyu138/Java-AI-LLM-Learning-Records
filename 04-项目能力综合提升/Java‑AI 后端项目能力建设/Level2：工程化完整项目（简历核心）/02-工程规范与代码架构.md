## 1. 分层架构与职责边界

分层架构的价值不是「分层」本身，而是**让每一层只回答一个问题**：Controller 回答「请求怎么进来、响应怎么出去」，Service 回答「业务规则是什么」，Mapper 回答「数据怎么存取」。三层职责混在一起的项目，改一个需求要动三个地方，排查一个 bug 要通读全链路——这就是 Level1 代码在工程化后必须拆开的根本原因。

Controller 层三条铁律：**只做参数接收与结果组装**，不写任何业务逻辑——判断「文档是否已存在」属于 Service，Controller 里出现 if 业务判断就是坏味道；**入参用 DTO 出参用 VO**，Entity 禁止直接暴露给前端（避免字段泄漏与耦合）；**方法命名用动作 + 资源**——`uploadDocument`、`askQuestion`，不叫 `doUpload` 这类无信息量名字。

Service 层两条铁律：**一个方法一个事务边界**，事务注解打在 Service 方法上而不是 Controller 上（Controller 层的事务会包含响应序列化，锁得久且作用域失控）；**业务异常用自定义异常抛出**，由全局异常处理器统一转响应，而不是在 Service 里组装错误结果返回——「抛异常」与「返回错误值」的选择标准是：异常要中断当前流程并统一处理，返回错误值只是数据的一种形态。

DTO/VO/Entity 的转换是分层架构的日常动作，两个选型要定：**对象转换用 MapStruct**——编译期生成转换代码，性能与手写一致，远快于 BeanUtils 的反射拷贝（反射拷贝在大批量转换场景是性能隐患，且字段名不匹配时静默丢字段），DTO/VO 之间、Entity/VO 之间的转换统一声明 Mapper 接口；**不可变模型优先用 record**——DTO 与返回值一律 record（JDK 25 一等公民，`equals/hashCode/toString` 开箱即得），Entity 保持可变类（ORM 需要 setter）。取舍原则一句话：**模板代码交给工具，业务语义留给类型**——分层不是为了制造转换代码，而是为了让每一层只知道自己该知道的东西。

## 2. 统一响应体与错误码体系

统一响应体的直接收益是**前端与调用方的处理逻辑只有一套**：不管成功失败，响应结构永远一致，HTTP 状态码永远 200（业务错误用错误码表达）。`kb-common` 里定义通用 Result：

```java
public record Result<T>(int code, String message, T data, long timestamp) {
    public static <T> Result<T> ok(T data) { return new Result<>(0, "ok", data, System.currentTimeMillis()); }
    public static <T> Result<T> fail(ErrorCode ec) { return new Result<>(ec.code(), ec.message(), null, System.currentTimeMillis()); }
}
```

错误码体系是容易被忽视的工程资产：**分段编码**——1xxx 参数错误、2xxx 业务错误、3xxx 数据错误、4xxx AI/外部服务错误、5xxx 系统错误，例如 `DOC_NOT_FOUND = 2001`、`LLM_TIMEOUT = 4002`。分段的理由：**错误码能被监控聚合**——按段统计就能看出「错误集中在参数还是外部依赖」，08 篇的告警规则直接消费这个分段；**排查快**——看到 4xxx 直接想到 AI 链路，不用翻文档。错误码定义在 `ErrorCode` 枚举（kb-common），message 对外返回，不能泄露堆栈细节。

错误码的演进纪律：**错误码一旦对外发布就是接口契约**——新增可以，改语义与删号不行（前端与调用方可能已按旧语义处理，改语义等于无声的破坏性变更）；**「对外简洁、对内详尽」是错误响应的分界线**——内部错误（5xxx）对外只给笼统文案与错误码，详细堆栈只在服务端日志里（08 篇的日志链路消费它），泄露堆栈细节等于把系统内部结构白送给攻击者，这是安全视角下必须守住的底线。

## 3. 全局异常处理

全局异常处理器是「统一响应体」的执行者：**所有异常在到达 Controller 边界时被拦截，翻译成统一响应**。`kb-api` 里注册一个 `@RestControllerAdvice`：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BizException.class)
    public Result<Void> handleBiz(BizException e) { return Result.fail(e.getErrorCode()); }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result<Void> handleValid(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
            .map(er -> er.getField() + ": " + er.getDefaultMessage())
            .collect(Collectors.joining("; "));
        return new Result<>(1001, msg, null, System.currentTimeMillis());
    }

    @ExceptionHandler(Exception.class)
    public Result<Void> handleOther(Exception e) {
        log.error("unexpected error", e);   // 未知异常必须打全栈日志
        return new Result<>(5000, "system error", null, System.currentTimeMillis());
    }
}
```

三条规则：**BizException 是业务异常的唯一出口**——Service 里 `throw new BizException(ErrorCode.DOC_NOT_FOUND)`，处理器按错误码翻译；**未知异常兜底 5000**——但必须 `log.error` 打全栈，否则线上出了问题没有任何日志可查；**校验异常单独处理**——把字段错误拼成人话返回（"title: 不能为空; file: 不能为空"），而不是给前端一个笼统的 400。

## 4. 参数校验

参数校验用 Bean Validation 3（jakarta.validation，Boot 4.1 内置），**声明式替代手写 if 判空**——手写校验散落在各方法里，声明式集中定义在 DTO 上，规则一目了然且可复用：

```java
public record DocUploadDTO(
    @NotBlank(message = "文档标题不能为空") @Size(max = 200) String title,
    @NotNull(message = "文档类型不能为空") DocType type,
    @NotNull(message = "文件不能为空") MultipartFile file
) {}
```

校验三条经验：**分组校验**——新增用 `Create` 组、更新用 `Update` 组，同一 DTO 在两种场景规则不同（新增必须传 title，更新可不传），`@Validated(Create.class)` 显式指定；**跨界校验写方法级校验器**——「结束时间必须晚于开始时间」这类字段间约束，用 `@AssertTrue` 在 DTO 里写个布尔方法，或者用自定义注解，不要写在 Service 里——写在 Service 里的校验逻辑无法被 Controller 层拦截，校验错误码不统一；**数据库层兜底**——校验能拦掉 95% 的脏参数，但唯一约束、外键这些必须由数据库兜底，应用层校验是「体验优化」，数据库约束是「正确性保证」，两层都要。

## 5. 日志规范

日志规范的目标是**「线上出问题时，日志能回答问题」**：什么时间、哪个请求、做了什么、结果如何。核心是 SLF4J 门面 + Logback 实现（Boot 默认），四条规定：**只用占位符不用字符串拼接**——`log.info("upload doc {}, size {}", id, size)`，`log.info("upload " + id)` 在参数为 null 或含敏感信息时直接埋雷，且拼接发生在日志级别过滤之前，白白浪费性能；**级别用对**——ERROR 记录「系统无法继续或数据错误」、WARN 记录「可降级但需要关注」（AI 降级、缓存 miss）、INFO 记录「关键业务流程」（上传成功、问答完成），业务日志全打 INFO 会淹没关键信息，DEBUG 禁止进生产配置；**MDC 注入 traceId**——请求进入时生成 UUID 放进 MDC，日志 pattern 输出 `[%X{traceId}]`，一次请求的所有日志行用 traceId 串起来（08 篇的链路追溯依赖它，Logback pattern 里必须配，否则这条规范等于没写）；**敏感信息脱敏**——手机号、API Key 在日志输出前打码，AI 调用日志禁止打印完整 prompt 与密钥（10 篇的 AI 日志里单独强调）。

```xml
<pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [%X{traceId}] %logger{36} - %msg%n</pattern>
```

日志规范的自检清单（M1 验收用）：grep 代码库确认没有字符串拼接日志（`log.info("a" + b)` 零容忍）；确认所有业务入口有关键 INFO 日志（上传成功、问答完成、降级触发——降级日志尤其重要，它是 08 篇告警的数据源）；确认 `%X{traceId}` 在 Logback pattern 里且链路实验能捞出全链路日志；确认日志里搜不到明文 API Key 与手机号。自检清单的目的：**规范是「评审标准」不是「写在文档里的话」**——代码评审时逐条对照打分，比事后补规范有效得多。

## 6. 核心要点

1. 分层职责单一：Controller 收参组装、Service 业务规则、Mapper 数据存取，Entity 不直接出参。
2. 统一响应体 Result + 分段错误码（1xxx 参数/2xxx 业务/4xxx 外部/AI、5xxx 系统），HTTP 永远 200。
3. 全局异常处理器是统一响应体的执行者：BizException 唯一业务出口、未知异常打全栈、校验异常拼人话。
4. 参数校验声明式（Bean Validation 3），分组校验 + 数据库兜底，不写散落 if。
5. 日志四规定：占位符、级别用对、MDC traceId、敏感信息脱敏。

> 🎯 **核心要点**：工程规范五件套的本质是**把「偶发的正确处理」变成「默认的正确」**——不写统一响应体，每个接口的错误形态都不同；不写全局异常，每个 Service 都要自己 try-catch。规范消除的是「每个开发者各自为政」的熵，这正是工程化与 Demo 的分界线。
