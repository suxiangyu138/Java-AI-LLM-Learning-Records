## 1. 动机：为什么必须给 AI 服务加防线

Level1 的 AI 调用是裸奔的：不设超时（服务挂了接口挂到天荒地老）、不设重试（网络抖动一次失败就失败）、不设限流（免费额度被刷爆才知道）、不设降级（AI 报错用户直接看到 500 和英文异常）。三个现实把「给 AI 加防线」从可选变成必须：**AI 服务不稳定**——高峰期限流（429）、模型加载慢、provider 故障，是常态不是意外；**成本敏感**——DeepSeek V4 2026-07 起执行峰谷定价（高峰 9:00-12:00、14:00-18:00 价格翻倍），v4-pro 缓存未命中输入 3 元/百万 token、输出 6 元/百万 token，高峰一次长对话可能吃掉数毛钱，被刷一夜是真实亏损；**外部依赖失控**——调用方的吞吐不在你控制内，但账单和故障在你头上。防线的结构三层：**限流把流量挡在门外**，**降级保证失败时有替代方案**，**超时/重试/熔断管理失败的成本**。

## 2. 限流：算法与落地

限流算法四选一，先理解再选型：**固定窗口**——每 60s 一个窗口计数，简单但窗口边界会双倍放行；**滑动窗口**——把窗口切成小格滑动计数，边界问题缓解，精度换内存；**令牌桶**——匀速发放令牌、可突发，适合「允许短时突发但平均受限」的 AI 调用；**漏桶**——固定速率流出，平滑但拒绝突发。AI 调用场景选**令牌桶**：问答是突发型流量（用户集中提问），令牌桶允许桶内突发（桶容量 = 突发上限）、长期平滑（补充速率 = 平均配额），正好匹配「平时够用、高峰别爆」的需求。

落地两处：**接口层限流**——用 Redis + Lua 实现令牌桶（原子脚本，分布式生效），`kb.api` 的问答接口按用户维度限流（如每用户 20 次/分钟），防单用户刷爆；**AI 调用层限流**——按 provider 配额限流（如总调用 100 次/分钟），防多个接口合起来打爆 provider 限额。两个限流的区别要讲清：**接口层保护用户体验（不被某个用户拖垮），调用层保护成本与 provider 配额**。

## 3. 降级策略：AI 不可用时怎么办

降级的核心问题：**AI 不可用时，用户应该看到什么**？三个层次由轻到重：**L1 兜底回答**——AI 调用失败（超时/429/熔断）时，返回「检索命中但生成失败」的降级响应：把 topK 命中的原文片段原样返回给用户（「以下内容来自您的文档」+ 片段），用户仍然拿到有用的信息，只是少了润色——这是最推荐的降级，因为检索结果本身有价值；**L2 缓存回答**——相同问题的历史回答缓存（Redis，TTL 7 天），命中直接返回，顺带省成本；**L3 友好提示**——以上都没有，返回「AI 服务暂时不可用，请稍后重试」的统一文案 + 建议稍后再试。降级的触发条件统一在**调用 AI 的出口**（一个封装了 Spring AI ChatClient 的 `AiGateway`）里判断，而不是散落在每个 Service——集中处理才可观测、可演练。面试讲降级的分寸：**降级方案必须是「用户还能获得价值」，而不是「报个错让用户走」**。

## 4. 超时与重试

不给 AI 调用设超时是最常见的生产事故。Spring AI 的 HTTP 客户端（WebClient/RestClient）必须显式配置三层超时：**连接超时**（2s）——连接建立不上就别等；**读超时**（30s）——模型生成慢但可以等；**总超时**（50s 上限）——SSE 流式场景按首 token 超时与空闲超时分别控制（10 篇流式里细讲）。重试策略：**只重试可重试的错误**——网络异常（connect/read timeout）、5xx、429 可以重试；业务 4xx（参数错误、余额不足）重试一万次也是白费；**指数退避 + 抖动**——`1s → 2s → 4s` 递增，加随机抖动（±20%）防止多个请求同时重试打爆服务（重试风暴）；**重试次数上限 3 次**——超过交给降级，重试不是万能药，重试的每一轮都在烧成本与时间。**重试幂等**——AI 调用本身幂等（同 prompt 结果不影响数据），但重试要带请求 ID 供日志串联（08 篇 traceId 复用）。

## 5. 熔断：Resilience4j 与 Sentinel 选型

熔断与重试的区别：**重试是「这一次没成再来一次」，熔断是「连续失败就暂停尝试，让服务喘息」**——没有熔断，AI 服务故障时所有请求都冲进去试一遍然后失败，重试还会放大流量（重试风暴）。两个主流框架选型：

| 维度 | Resilience4j | Sentinel |
|---|---|---|
| 定位 | 轻量库，纯 Java 代码配置 | 重量级框架，控制台可视化 |
| 能力 | 熔断/限流/隔离/重试/超时 | 限流/熔断/降级/系统保护/规则持久化 |
| 部署成本 | 依赖即用，无外部组件 | 需控制台（dashboard） |
| 适合场景 | 单体或少量服务 | 微服务体系、需要可视化规则管理 |

本项目选 **Resilience4j**：`kb-prod` 是单体多模块，不需要控制台；熔断规则（失败率阈值 50%、滑动窗口 10 次、熔断 10s）写死在配置里、可演讲解透；Sentinel 留给 Level3 微服务化时升级（仓库有完整 Sentinel 体系，届时对照迁移）。熔断器状态机是面试高频：**CLOSED（正常）→ OPEN（失败率超阈值，直接拒绝 + 快速失败）→ HALF_OPEN（熔断期后放一个探测请求）→ 成功回 CLOSED / 失败回 OPEN**——熔断不是「永久关闭」，是「给下游喘气的机会」。

## 6. 验证实验与降级演练

三个验证：**限流验证**——JMeter 压问答接口，速率超过阈值后观察 429 响应与 Redis 计数（`TTL` 与剩余配额正确）；**熔断验证**——把 AI 服务指向一个假死端点，压 50 个请求，观察熔断器 OPEN → 请求快速失败（毫秒级）→ 恢复后 HALF_OPEN 探测成功回 CLOSED，全程记录；**降级演练**——关掉 AI 服务配置（模拟故障），问答接口依次验证 L1 片段兜底 → L2 缓存回答 → L3 提示文案三层都生效，**演练要在上线前做，而不是故障时第一次见**。演练的产出记进 CHANGELOG：故障场景、触发条件、降级行为、恢复行为——这就是面试「出过问题吗」的标准素材。

## 7. 核心要点

1. 三层防线：限流挡流量、降级保体验、超时/重试/熔断管失败成本——AI 依赖必须全上。
2. 限流选令牌桶（突发 + 平滑），接口层按用户、调用层按 provider 配额，两处都要。
3. 降级三层次：L1 检索片段兜底（推荐，仍有价值）→ L2 缓存回答 → L3 友好提示；触发集中在 AiGateway 出口。
4. 超时三层显式配置（连接 2s/读 30s/总 50s），只重试网络类错误，指数退避 + 抖动 + 上限 3 次。
5. 熔断选 Resilience4j（单体够用），状态机 CLOSED → OPEN → HALF_OPEN 要能画出来。
6. 降级演练上线前做，故障场景与行为记进 CHANGELOG。

> 🎯 **核心要点**：限流降级的工程哲学是**「把外部依赖的不可靠，隔离在用户体验之外」**——用户应该永远得到「可用」的响应，AI 服务只是决定响应质量的因素之一。三层防线 + 演练数据，是「生产级项目」与「调接口 Demo」的分水岭。
