# 03 向量数据库升级：Milvus 替换内存存储

> 可靠性改造的第一刀：Level1 的向量存在 JVM 内存里，重启即丢、无法过滤、无法扩量——这是「Demo」与「项目」最刺眼的差距。本模块用 Milvus 3.0（2026-07-29 发布的湖原生版本）替换内存存储，打通「写入 → 索引 → 检索」的完整向量库链路。

## 1. 动机：内存向量存储的四个边界

Level1 的向量存在 `ConcurrentHashMap<id, float[]>` 或简单的内存列表里，四个边界决定了它撑不起简历项目：**不可持久化**——重启即丢，用户上传的文档知识全部蒸发，演示时一次重启就露馅；**无法过滤**——检索只能在「全部向量」里做余弦相似度，按文档 ID、按知识库、按创建时间过滤都做不到，而真实场景 80% 的检索都带过滤条件；**无法扩量**——内存搜索是 O(n) 全量扫描，几千条向量还行，几万条就开始卡，几十万条直接不可用，索引（HNSW）只有向量库才有；**没有配套能力**——混合检索（关键词 + 向量）、标量排序、数据生命周期（TTL）都要自己造轮子。换向量库不是「换个存储」，而是**「从 O(n) 暴力搜索升级为带索引、带过滤、可持久化的检索服务」**。

## 2. Milvus 3.0 关键能力速览

Milvus 3.0.0 于 2026-07-29 正式发布（Apache 2.0、LF AI & Data 毕业项目），是 Milvus 史上最大的架构升级——从「向量数据库」迈向「湖原生（Lake-Native）Vector Lakebase」。对简历项目有三个直接相关的亮点：**Loon 存储引擎**——基于 manifest 的列式存储，专为 ANN 检索后的窄点查询设计，随机点读 I/O 相比 Parquet 基线提升约 135 倍（9.4MB → 0.07MB）；**TEXT 一等数据类型**——同一字段同时存原始文本与向量，做混合检索不用再双写一份数据；**服务端 ORDER BY 与聚合**——检索结果可按标量字段（时间、评分）排序、聚合统计，以前要拉回应用层做的事现在引擎内完成。选型论证（面试要能讲）：相比 pgvector（PostgreSQL 插件），Milvus 是专职向量库，HNSW 索引与十亿级规模是插件形态给不了的；相比 ES 的向量能力，Milvus 的混合检索（BM25 + 向量统一打分）开箱即用，ES 要自建融合逻辑。

## 3. 部署与集合设计

Docker 部署 standalone 模式即可（3.0 支持 Docker/K8s/离线安装，本项目 Compose 编排见 09 篇）：

```yaml
milvus:
  image: milvusdb/milvus:v3.0.0
  ports: ["19530:19530"]
  environment:
    ETCD_ENDPOINTS: etcd:2379
    MINIO_ADDRESS: minio:9000
```

集合设计是整个向量库改造的核心决策，先想清楚再动手：**一个 Collection 还是多个**——本项目一个 Collection（`kb_doc_chunk`），按 `kb_id`（知识库 ID）做过滤字段，而不是每库建一个集合；理由：Collection 是索引与分区的边界，建多了管理成本翻倍，过滤字段才是正确的多租户手段。**Schema 字段设计**：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | INT64 | 主键，业务侧用雪花 ID |
| kb_id | INT64 | 知识库 ID，检索过滤字段（标量索引） |
| doc_id | VARCHAR | 文档 ID，聚合与展示 |
| chunk_text | TEXT | 原始文本（3.0 一等类型，混合检索直接用） |
| embedding | FLOAT_VECTOR(1536) | 向量，维度以 Embedding 模型为准 |

**索引设计**：向量索引用 HNSW（`metric_type=IP` 内积或 COSINE），参数 `M=16, efConstruction=200` 起步，检索时 `ef=64` 起步——`ef` 越大召回越准、延迟越高，这是 10 篇评估实验的调参对象；标量字段（kb_id）建 `STL_SORT` 索引加速过滤。集合建好后**先验证索引生效再写业务代码**——`describe_index` 能看到索引状态，这是第一个验证实验。

Embedding 模型的选择与维度强相关，且是写入链路的起点：**本地模型（Ollama 的 bge-m3，1024 维）**离线可用、零成本、RAG 链路全离线可演示（不依赖外网与密钥）；**云端模型（如 text-embedding-v3，1536 维）**效果更好但引入网络依赖与调用成本。本项目基线用 bge-m3 本地模型，评估（10 篇）发现召回不足再切云端——**换模型 = 重建向量索引**（维度可能变化，Schema 里的向量维度是写死的），这个决策的权衡要在设计文档里写明，面试被问「Embedding 模型怎么选的」时就是这套答案。

## 4. Java SDK 写入与检索

Milvus 官方 Java SDK（milvus-sdk-java，3.x 对应新接口），核心两段代码。写入（向量化在 kb-ai 层完成，这里只负责落库）：

```java
List<InsertRequest.Field> fields = List.of(
    new InsertRequest.Field("id", ids),
    new InsertRequest.Field("kb_id", kbIds),
    new InsertRequest.Field("chunk_text", texts),
    new InsertRequest.Field("embedding", embeddings)   // List<List<Float>>
);
InsertResp resp = client.insert(InsertReq.builder()
    .collectionName("kb_doc_chunk").fields(fields).build());
```

检索（带过滤 + topK）：

```java
SearchResp resp = client.search(SearchReq.builder()
    .collectionName("kb_doc_chunk")
    .data(questionEmbedding)
    .filter("kb_id == " + kbId)          // 先过滤再检索，命中过滤字段索引
    .topK(5)
    .outputFields(List.of("chunk_text"))  // 只取需要的字段，避免拉全量
    .build());
```

两个高频坑：**维度不一致**——Embedding 模型输出 1536 维，集合建成了 1024 维，写入直接报错，维度是写死在 Schema 里的，换模型必须重建集合或加列；**写入异步可见性**——插入默认异步，刚插入就检索可能查不到（consistency level 设为 Strong 或轮询 flush），生产用 `Bounded` 级别 + 业务侧延迟兜底。

## 5. 混合检索：向量 + BM25

纯向量检索的两个盲区：**专有名词与缩写**——"Milvus" 这类词语义向量可能召回偏、关键词精确命中更可靠；**检索失败时的兜底**——向量检索 topK 为空，关键词检索还能捞回。Milvus 3.0 的 TEXT 字段原生支持 BM25 稀疏索引，同一集合上做**向量 + BM25 混合检索**：查询时并行跑两个 search，分别拿回 topK，再用 RRF（Reciprocal Rank Fusion，`1/(k+rank)` 加权合并）融合排序。项目落地顺序：**先纯向量跑通（M2 验收点），再上混合检索（M4 优化点）**——混合检索是评估指标提升的素材，实验数据进 10 篇的评估报告。搜索质量对比实验：同一批问题，纯向量 vs 混合检索各跑一遍，记录命中率差异——这就是「效果可度量」的直接证据。

RRF 融合的细节值得讲透：对两个检索结果集，每条命中的融合分是 `Σ 1/(k + rank)`（k 取 60），rank 越靠前分越高，融合后按分数重排取 topK。两个坑：**两个结果集的分数单位不同**（余弦相似度 0-1 与 BM25 分数无上界），直接加权平均是错的，RRF 只依赖排名不依赖原始分数，这正是它适合跨模型融合的原因；**融合的 topK 要放大**——各自取 top10 再融合取 top5，避免融合把某一侧的优秀命中挤掉。面试讲混合检索，能把 RRF 的这两个细节讲清楚，就与「调了个 API」的选手拉开了差距。

## 6. 数据迁移与验证实验

迁移策略（Level1 内存数据 → Milvus）：**先迁移后验证**——写一个一次性迁移任务：读内存数据（或重新解析源文档）→ 向量化 → 批量插入 Milvus（`insert` 支持批量，几千条一次提交）；**迁移后做一致性抽查**——随机取 10 条 chunk，检索各自对应的原文，确认检索能命中；**清理**——迁移确认无误后删除内存存储代码，内存容器只在测试兜底。验证实验（必须记录数据）：**检索质量**——构造 20 个「问题 → 期望命中 chunk」的测试对，跑检索看 top5 命中率（目标 >= 80%，不达标先调 `ef` 与分块大小）；**性能**——同机对比内存 O(n) 搜索 vs Milvus HNSW：1000 条向量内存 50ms vs Milvus 5ms（数量越大差距越大），这个对比数据是面试「为什么用向量库」的量化答案。

## 7. 核心要点

1. 内存存储四个边界：不持久化、不能过滤、不能扩量、无混合检索——这是换库的根本动机。
2. Milvus 3.0 湖原生：Loon 存储引擎、TEXT 一等类型（文本+向量同字段）、服务端排序聚合。
3. 集合设计核心决策：单集合 + kb_id 过滤字段，不用多集合；维度与 Embedding 模型强绑定。
4. Java SDK 两坑：维度不一致报错、插入异步可见性（consistency level 与 flush）。
5. 混合检索（向量 + BM25 + RRF 融合）是 M4 优化点，先纯向量跑通再叠加。
6. 迁移先做一致性抽查，检索质量与性能对比实验必须留数据。

> 🎯 **核心要点**：向量库升级的本质是**「把检索从应用内存里的玩具，变成数据独立的服务」**——文档知识不再随 JVM 重启蒸发，检索带上了索引、过滤与混合能力。Milvus 3.0 的湖原生能力对简历项目是加分项，而「为什么用专职向量库 + 量化对比数据」才是面试加分题。
