# 04 缓存一致性升级

> 可靠性改造的第二刀：Level1 的旁路缓存（Cache-Aside）在并发下存在脏数据窗口，且完全裸奔——没有三防、没有监控。本模块把缓存升级为「延迟双删 + 消息兜底 + 三防 + 命中率监控」的生产级方案，对齐 01 篇「缓存与数据库最终一致，窗口 < 1 分钟」的指标。

## 1. 动机：旁路缓存的并发问题

Level1 的缓存操作是「先更新数据库，再删缓存」（Cache-Aside），单线程下没问题，并发下有三个脏窗口：**删缓存与读缓存的竞争**——线程 A 更新数据库后删缓存，删之前线程 B 恰好把旧值写回缓存（B 读缓存 miss → 读库拿到旧值 → 写缓存），此后旧值驻留缓存，数据库已是新值；**更新与更新的竞争**——两次更新数据库的顺序和两次删缓存的顺序可以不同，缓存被后删的旧数据占据；**删缓存失败**——删除操作本身可能失败（网络抖动、Redis 超时），失败后缓存永不刷新，脏数据窗口无限长。这三个问题不解决，缓存就成了「时灵时不灵」的谜之组件——Level2 要把「靠运气」变成「靠方案」。

## 2. 延迟双删：方案与取舍

延迟双删（Delayed Double Delete）解决「删缓存与写缓存竞争」的经典方案，流程四步：**更新数据库 → 删除缓存 → 休眠一小段时间（如 500ms）→ 再次删除缓存**。第二次删除干掉的是「休眠期间被并发读线程写回的旧值」——因为读线程写缓存的时间窗口远小于休眠时间，二次删除能覆盖绝大多数竞争。三个落地细节：**休眠时长是唯一关键参数**——必须大于「读线程从 miss 到写回缓存」的最大耗时（依赖 DB 查询与网络延迟，生产用 P99 读延迟 × 2 作为初值，本项目 500ms 起步），太短等于没删，太长阻塞写路径；**二次删除失败要重试**——二删是最终一致性兜底的前置，失败交给 05 篇的消息重试（或延时任务）补偿；**延迟双删不是强一致**——极端并发下（休眠窗口内多轮竞争）仍可能残留脏值，它的定位是「把脏窗口从无限压缩到秒级」，是工程上的务实取舍，不是理论正确——面试被追问时能讲清这个边界才是真懂。

## 3. 最终一致性兜底：消息重试

延迟双删解决「正常路径」，兜底解决「失败路径」：**任何一次删缓存失败，发一条「缓存清理」消息到 MQ**，由消费者在几秒后重删。链路：Service 删缓存失败 → 不阻塞主流程（记录失败）→ 发 `cache-evict` 消息（携带 key）→ 消费者延迟消费执行删除 → 删除仍失败则死信队列人工介入（05 篇的死信机制复用）。这个设计的价值：**写路径永远不被缓存故障阻塞**（01 篇「缓存故障不阻塞写路径」指标的落地），删除失败从「静默」变成「可观测、可补偿」。面试讲这个方案时一句话收尾：「缓存与数据库的最终一致性 = 延迟双删（正常路径）+ 消息重试（失败路径），最大不一致窗口取决于休眠时长与重试延迟，本项目控制在 1 分钟内」。

## 4. 三防：穿透、击穿、雪崩

缓存穿透、击穿、雪崩是缓存面试的三大必考，工程落地的方案必须真做：

| 问题 | 现象 | 方案 | 本项目落地 |
|---|---|---|---|
| 穿透 | 查询不存在的 key，缓存永远 miss，打到 DB | 布隆过滤器 / 缓存空值 | 文档详情查询缓存空值（TTL 60s，带业务标记防误读） |
| 击穿 | 单个热点 key 过期瞬间，大量请求打 DB | 互斥锁重建 / 逻辑过期 | `SETNX` 互斥锁：一个线程重建，其余线程等锁后读新缓存 |
| 雪崩 | 大量 key 同时过期，DB 被瞬时压垮 | 过期时间加随机值 / 多级缓存 | TTL = 基础值 + 随机 0-300s，过期时间错峰 |

穿透的空值缓存是高频坑：**空值必须区分「真不存在」与「暂时无数据」**——用占位值（如 `NULL_MARKER`）+ 短 TTL，避免业务层把占位值当真实数据返回；击穿的互斥锁注意**锁必须带过期时间防死锁**，且锁粒度到 key 级别（`SETNX cache:lock:doc:{id}`），锁住整个缓存命名空间会引入串行瓶颈。

## 5. Spring Cache 集成与 Redis 配置

Spring Cache 抽象（`@Cacheable/@CacheEvict`）解决「缓存代码与业务代码耦合」的问题：业务方法只关心逻辑，缓存注解声明行为。本项目两种用法并存：**查询用注解**——`@Cacheable(cacheNames = "kb:doc", key = "#id")` 声明式读缓存；**写路径用手写代码**——更新 + 删缓存必须在同一个事务边界内编排（先更新库，事务提交后删缓存），注解的 `@CacheEvict` 触发时机难以精确控制，手写更可控。

Redis 配置三个必改项：**序列化**——默认 JDK 序列化可读性差且性能低，改用 JSON 序列化（GenericJackson2JsonRedisSerializer），但注意存储带类型信息、类结构变更会反序列化失败；**连接池**——Lettuce 默认连接数在并发下不够，`spring.data.redis.lettuce.pool.max-active` 按压测结果调（08 篇压测对齐）；**Key 命名规范**——`业务:对象:id`（`kb:doc:1001`），统一前缀是后续做缓存扫描、批量清理、监控统计的前提。

## 6. 验证实验与命中率监控

两个验证实验必须留数据：**一致性验证**——并发压测：10 线程同时「读旧值 + 更新 + 读新值」各 100 次，统计读到旧值的次数；改造前（裸旁路缓存）与改造后（延迟双删 + 重试）各跑一遍，目标改造后旧值读取次数 < 5 次（残留窗口内概率性出现是方案边界，讲得清即可）；**命中率监控**——Redis 服务端 `INFO stats` 有 `keyspace_hits / keyspace_misses`，算命中率并接入 08 篇的指标面板；同时业务侧埋点：缓存读 miss 次数、空值缓存命中次数（穿透告警信号）、互斥锁等待时长（击穿告警信号）。命中率不是越高越好——**缓存命中率异常高（> 98%）可能意味着数据很久没更新，异常低（< 60%）说明缓存策略失效**，监控的价值是「发现异常」，不是「追求好看」。

监控的三条信号线再明确一遍：**命中率骤降**——大概率是缓存 key 前缀变更或清理逻辑误删，查最近变更（CHANGELOG 的回溯价值在这里）；**空值缓存命中率上升**——穿透攻击或查询参数异常，限流（06 篇）与空值 TTL 是两道闸；**互斥锁等待时长爬升**——热点 key 过期瞬间的击穿迹象，检查 TTL 分布是否集中。信号线要与 08 篇的告警规则绑定——缓存监控不是「看一眼面板」，是「规则驱动的自动发现」。

## 7. 核心要点

1. 旁路缓存三个并发脏窗口：删读竞争、双写顺序、删缓存失败——Level2 用方案消灭「靠运气」。
2. 延迟双删：先更新库 → 删缓存 → 休眠（P99 读延迟 × 2）→ 再删；是工程务实取舍，不是强一致。
3. 失败兜底：删缓存失败发 MQ 消息延迟重删，写路径永不阻塞，最终一致窗口 < 1 分钟。
4. 三防落地：空值缓存（带标记防误读）、SETNX 互斥锁（带超时防死锁）、TTL 加随机值错峰。
5. 写路径手写编排（事务提交后删缓存），读路径用 @Cacheable；Redis 必改序列化与连接池。
6. 一致性压测对比与命中率监控进 08 面板——缓存改造必须「有数据」。

> 🎯 **核心要点**：缓存一致性的工程本质是**「承认分布式下没有强一致，但把不一致窗口压缩到可接受范围并让它可观测」**——延迟双删压缩窗口、消息重试覆盖失败、监控暴露残留。这套「方案 + 兜底 + 观测」的三层结构，是后面 MQ、降级等所有可靠性模块的通用范式。
