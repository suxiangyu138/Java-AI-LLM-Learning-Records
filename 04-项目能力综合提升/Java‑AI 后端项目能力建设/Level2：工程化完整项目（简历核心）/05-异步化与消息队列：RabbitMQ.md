# 05 异步化与消息队列：RabbitMQ

> 可靠性改造的第三刀：文档解析与向量化是「秒级 + 可重试」的重任务，同步处理会阻塞上传接口、拖垮用户体验。本模块用 RabbitMQ 4.3（2026-05 基线）把重任务改造成异步任务队列，并建立「可靠投递 + 手动确认 + 重试死信 + 幂等消费」的完整消息可靠性链路。

## 1. 动机：为什么把文档解析异步化

上传文档的链路：接收文件 → 解析 PDF/Markdown → 分块 → Embedding 向量化 → 写入 Milvus。同步处理时，接口要等整个链路走完才返回——向量化一次调用 1-3s，解析大文档更久，上传接口 P95 直接飙到 5s+，用户等得心慌。异步化把链路切成两段：**接口只做「接收文件 + 落库 + 发消息」**，毫秒级返回「解析中」；**消费者异步完成「解析 → 向量化 → 入库」**，完成后更新文档状态。收益三个：**体验**——上传秒回，解析进度通过状态轮询可见；**解耦**——解析逻辑升级（换分块策略、换 Embedding 模型）不影响上传接口；**削峰与重试**——解析任务排队执行，失败可重试，不会因一次失败丢文档。异步化的代价也要讲清：**链路变长、一致性变复杂**——用户看到的「解析中」依赖状态流转，失败要有兜底（05 篇的死信 + 06 篇的降级），「即时性换可靠性」是这个改造的本质。

## 2. RabbitMQ 4.3 核心模型

RabbitMQ 的消息模型三件套：**Exchange（交换机）**——消息入口，决定路由规则；**Queue（队列）**——消息存储与消费单位；**Binding（绑定）**——把交换机与队列用 routing key 连起来。生产者只发消息到交换机，消费者只从队列取消息，**两者永远不直接通信**——这个解耦是 MQ 的本质价值。本项目用 Direct 交换机（精确路由）加两个队列：

| 队列 | routing key | 消费者 | 用途 |
|---|---|---|---|
| kb.doc.parse | doc.parse | 文档解析服务 | 上传后触发解析 |
| kb.cache.evict | cache.evict | 缓存清理服务 | 04 篇删缓存失败重试 |

Spring AMQP 集成用注解式监听（Boot 4.1 内置）：

```java
@RabbitListener(queues = "kb.doc.parse")
public void onParse(DocParseMessage msg) {
    docService.parseAndIndex(msg.getDocId());   // 解析 + 向量化 + 入库
}
```

消息体设计是链路可维护性的起点：**消息只携带业务 ID 与元数据，不携带业务数据**——`DocParseMessage(docId, kbId, traceId)`，消费者按 ID 查库拿完整数据再处理。三个理由：消息体积小（性能与存储都受益）；数据以数据库为唯一真相（消息是「任务单」不是「数据拷贝」，数据变了不用改消息格式）；幂等与重试都围绕 ID 展开（状态表按 docId 判重）。traceId 放消息头——消费者从消息头取出恢复 MDC，这是 08 篇链路实验能跨线程捞全日志的前提，消息设计在链路设计里是最容易被忽略却最影响排查效率的一环。

## 3. 队列选型：Quorum Queue

RabbitMQ 4.x 的一个关键事实：**经典队列镜像已在 4.0 彻底移除**，Quorum Queue 与 Streams 是仅有的两种复制类型，而 **Quorum Queue 是唯一提供数据安全保证的复制队列**——基于 Raft 共识，数据写入多数副本才算成功，节点宕机不丢消息。本项目全部队列声明为 Quorum：

```java
@Bean
Queue parseQueue() {
    return QueueBuilder.durable("kb.doc.parse")
        .quorum()                          // x-queue-type=quorum
        .build();
}
```

单机部署下 Quorum 的优势不明显，但两个理由必须坚持：**面试口径**——「我用的是 Quorum Queue，因为它是 4.x 唯一带数据安全保证的队列类型，宕机不丢消息」是一句有含金量的话；**升级路径**——项目上线后加节点变集群，Quorum 无需改造直接生效。注意：**Quorum 队列默认 `delivery-limit` 重试语义与经典队列不同**（按投递次数而非确认次数），重试配置要对齐 RabbitMQ 4.3 的语义（4.3 起原生支持按 delivery-count 的限制）。

## 4. 生产者可靠投递

「消息发出去了」不等于「消息到达了队列」——网络抖动、交换机不存在、写入失败都会让消息丢失。生产者侧两级保障：**publisher confirm**——开启 `spring.rabbitmq.publisher-confirm-type: correlated`，发送时拿到 correlation data，回调里确认消息被 Broker 接收；**mandatory + ReturnCallback**——消息无法路由到任何队列时触发 return 回调，落入补偿逻辑（记录 + 重发）。标准代码结构：confirm 回调里收到 nack 或超时 → 重试发送（带重试次数上限）；return 回调 → 记录错误消息到死信。一句话原则：**「发出去」以 confirm 为准，不以 send 返回为准**——这条是面试「怎么保证消息不丢」的标准答案开头。

## 5. 消费者：ack、重试、死信与幂等

消费者侧可靠性四件套，缺一个都会出问题：**手动 ack**——`acknowledge-mode: manual`，业务处理成功才 `basicAck`，抛异常则 `basicNack`（requeue=false），消息回到队列或进死信；自动 ack 的坑是「消费即删」——处理到一半进程崩溃，消息就丢了；**重试策略**——消费失败先本地重试（`RetryInterceptor`，指数退避），重试耗尽再进死信队列，而不是无限 requeue——无限 requeue 会把坏消息在队列里反复消费打满 CPU（RabbitMQ 4.3 的延迟重试特性可做按投递次数的退避重试）；**死信队列**——`x-dead-letter-exchange` 声明死信交换机，重试耗尽的消息进 `kb.doc.parse.dlq`，人工介入或定时任务补偿；**幂等消费**——MQ 是 at-least-once 语义，同一条消息可能被投递多次（重试、节点切换），消费者必须幂等：处理前查任务状态表，已处理（成功）直接 ack 跳过。本项目解析任务幂等键用 `docId`，状态机 `PENDING → PARSING → READY/FAILED`，状态表就是幂等与重试的真相来源。

RabbitMQ 4.3 的**延迟重试**特性值得用：经典做法是「本地重试 N 次 → 死信」，4.3 支持按投递次数配置指数退避的延迟重试，重试间隔随次数增长，坏消息不会在队列里空转打满 CPU，达到 delivery-limit 才进死信——本项目解析任务配置 3 次重试（1s/4s/16s 退避），重试耗尽进 DLQ。这个配置的面试价值：说明你「知道 4.x 的新特性且用到了正确场景」，而不是停留在「重试 = requeue」的旧认知——requeue 是立刻重投，退避是延迟重投，前者在故障持续时会形成重试风暴。

## 6. 验证实验

三个验证实验，数据都记录：**可靠性验证**——生产端关闭 RabbitMQ 再发消息，确认 confirm 回调 nack、消息不丢（待服务恢复重发成功）；**重试与死信验证**——消费者里故意抛异常，观察「重试 N 次 → 进死信队列 → DLQ 有消息」，确认链路完整；**幂等验证**——同一条解析消息手动重投两次，确认文档只被解析一次（状态表里只有一条 READY 记录）。**异步化收益压测**——同步版 vs 异步版上传接口各压 100 次，对比 P95 响应时间（预期：5s+ → < 500ms），这个对比是 01 篇「解析秒回」指标的直接证据，也是面试「为什么用 MQ」的量化答案。

## 7. 核心要点

1. 异步化切两段：接口秒回 + 消费者重任务，收益是体验、解耦、削峰重试，代价是链路与状态复杂度。
2. 模型三件套：Exchange（路由）→ Binding → Queue（存储），生产与消费永不直连。
3. Quorum Queue 是 4.x 唯一数据安全队列（经典镜像已移除），单机也坚持用，集群直接复用。
4. 可靠投递以 publisher confirm 为准，不可路由用 mandatory 回调补偿。
5. 消费四件套：手动 ack、指数退避重试（上限）、死信队列、状态表幂等——at-least-once 必须幂等。
6. 三个验证实验留数据：确认可靠性、重试死信链路、同步 vs 异步 P95 对比。

> 🎯 **核心要点**：MQ 可靠性的心智模型一句话：**「每一环都可能失败，每一环都要有兜底」**——confirm 兜底发送失败、重试兜底处理失败、死信兜底重试失败、幂等兜底重复投递。四层兜底齐了，消息链路才敢说「不丢不重不卡」。
