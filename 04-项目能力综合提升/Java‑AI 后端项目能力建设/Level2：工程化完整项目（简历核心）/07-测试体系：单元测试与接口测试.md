# 07 测试体系：单元测试与接口测试

## 1. 动机：测试是「改得动」的保障

Level1 没写测试是合理的——Demo 期代码每天都改，测试是拖累。但 Level2 进入 M2 后情况反转：**可靠性改造（03-06 篇）动的是 Level1 已经跑通的链路**——换掉向量存储、加 MQ、加缓存清理，任何一步都可能悄悄弄坏原功能。没有测试，回归只能靠手动点一遍接口，漏一个就是线上事故；有测试，每次改造后 `mvn test` 一把梭，坏在哪一屏见分晓。测试的核心价值不是「证明现在能跑」，而是**「保证以后改不坏」**——它是 M2-M4 持续改造的安全网，也是面试「你怎么保证代码质量」的直接答案。代价也讲清：测试有编写成本，所以要用金字塔策略把成本花在刀刃上。

## 2. 测试金字塔与本项目分层

测试金字塔的经典比例：**底层单元测试（70%）快而多、中层接口/组件测试（20%）真而稳、顶层端到端测试（10%）少而贵**。理由：单元测试毫秒级、不依赖外部组件，跑一次全量才几分钟；端到端测试要拉起全部中间件，慢且脆——把大部分断言押在金字塔底层，是「低成本高保障」的工程取舍。本项目落地三层：

| 层 | 工具 | 覆盖对象 | 特性 |
|---|---|---|---|
| 单元测试 | JUnit 6 + AssertJ + Mockito | Service 业务逻辑、工具类、错误码 | 毫秒级，mock 掉依赖 |
| 接口测试 | MockMvc（WebMvcTest/SpringBootTest） | Controller 全链路（响应体/异常/校验） | 起应用上下文，不打真中间件 |
| 集成测试 | Testcontainers + SpringBootTest | Mapper、MQ 消费、Milvus 检索 | 起真实中间件容器，慢而全 |

分层原则：**每个测试只测一层**——Controller 测试 mock 掉 Service，Service 单元测试 mock 掉 Mapper——否则测试失败时你不知道是 Controller 的锅还是 Service 的锅，排查成本翻倍。

## 3. 单元测试：JUnit 6 + Mockito

JUnit 6（2026 基准，三平台架构：Jupiter/Platform/Engine 各自独立）下，Service 单元测试的标准形态：**被测对象真实创建，依赖全部 mock**——测 DocService 时不连 MySQL，Mapper 用 `@Mock` + `when(...).thenReturn(...)` 打桩。断言用 AssertJ（可读性远超 JUnit 内置）：

```java
@ExtendWith(MockitoExtension.class)
class DocServiceTest {
    @Mock DocMapper docMapper;
    @InjectMocks DocService docService;

    @Test
    void shouldThrowWhenDocNotFound() {
        when(docMapper.selectById(1001L)).thenReturn(null);
        assertThatThrownBy(() -> docService.getDoc(1001L))
            .isInstanceOf(BizException.class)
            .extracting("code").isEqualTo(ErrorCode.DOC_NOT_FOUND.code());
    }
}
```

单元测试三条纪律：**只测行为不测实现**——断言返回值与异常，不断言「调用了哪个方法」这类实现细节（重构时测试全红的元凶）；**mock 的边界要讲清**——mock 掉的是「你自己代码的外部依赖」，不是「你自己的逻辑」，测 DocService 的逻辑就要把 Mapper 当黑盒；**异常路径与边界必测**——空参数、不存在 ID、重复上传，异常分支的测试比主路径更有价值（线上故障大多发生在分支上）。

mock 的两个常见误用要避免：**过度 mock**——把被测对象内部的依赖也 mock 掉（Service 内部再调 Service），测试变成「验证 mock 行为」而不是「验证业务逻辑」，重构时全红且没有任何保护价值；**mock 与真实混跑**——同一个测试类里有的依赖真连、有的 mock，失败时定位成本翻倍。原则：**一个测试类里的依赖边界只能有一个**——测 Service 全部 mock 外部依赖，测 Controller 只 mock Service，集成测试全部真连——分层测试与分层架构是同一套心智。

## 4. 接口测试：MockMvc

接口测试验证的是「Controller + 全局异常 + 校验」这一层对外契约：**请求进来，响应是不是统一响应体格式**。用 `@WebMvcTest(DocController.class)` 起最小上下文（只加载 Web 层，Service mock），MockMvc 发请求断言响应：

```java
mockMvc.perform(post("/api/docs")
        .contentType(MediaType.MULTIPART_FORM_DATA)
        .param("title", "t").param("type", "PDF"))
    .andExpect(status().isOk())
    .andExpect(jsonPath("$.code").value(1001))       // 校验失败错误码
    .andExpect(jsonPath("$.message").value(containsString("不能为空")));
```

接口测试必测的三个场景：**正常链路**——成功时 code=0、data 结构正确；**校验失败**——缺参/超长，错误码 1xxx、message 可读；**业务异常**——不存在的 ID，错误码正确且不泄漏堆栈。这三类覆盖了「统一响应体 + 全局异常 + 校验」三件套的验收，也是 02 篇规范生效的直接证据。

## 5. 集成测试：Testcontainers

单元测试与接口测试都绕开了真实中间件，但 **Mapper SQL 对不对、MQ 消息消费链路通不通、Milvus 检索真实效果如何，只有真中间件才知道**。Testcontainers 用 Docker 起真实组件（测试完自动销毁），本项目集成测试组合：MySQL 8.4 + Redis 8 + Milvus 3.0 + RabbitMQ 4.3，一个 `@SpringBootTest` 集成测试类同时拉起：

```java
@Testcontainers
@SpringBootTest
class DocIndexIntegrationTest {
    @Container static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.4");
    @Container static MilvusContainer milvus = new MilvusContainer("milvusdb/milvus:v3.0.0");
    // RedisContainer + RabbitMQContainer 同理，用 @DynamicPropertySource 注入连接配置
}
```

集成测试的取舍要讲清：**慢且重（分钟级）**，所以只测「单元测不了的」——Mapper 的 SQL 正确性（含事务回滚）、MQ 的「发消息 → 消费 → 状态更新」闭环、Milvus 的「写入 → 检索」闭环；**CI 里 Docker 是前置**（09 篇流水线处理）。覆盖顺序：先保证每个中间件有一条集成测试闭环，再谈数量——**一条真链路测试的价值大于十条 mock 测试**。

## 6. AI 链路测试与覆盖率门禁

AI 链路测试的特殊性：**不能真调 LLM**——慢（秒级）、烧钱、结果不确定（同 prompt 输出不固定，断言无法稳定）。策略是**在 AiGateway 出口打桩**：集成测试里把 ChatClient mock 成「返回固定响应」，这样 RAG 全链路（检索 → 注入 → 生成 → 响应）可测，只有 AiGateway 本身是桩——这正是 06 篇「AI 调用集中在出口」设计的测试收益。**覆盖率门禁**用 JaCoCo：`mvn verify` 时执行 `jacoco:check`，行覆盖率 >= 70%、分支 >= 60%，不达标构建失败——门禁的意义是**把覆盖率从「自觉」变成「强制」**，否则测试永远是「有时间才写」。

覆盖率数字的解读要诚实：**70% 行覆盖率不意味着 70% 的安全感**——关键路径（上传、删除、AI 降级、MQ 消费）的分支要 100% 覆盖，record 与工具类的样板代码覆盖没有意义；JaCoCo 报告里的红色分支就是「未测到的风险」，评审时优先看核心 Service 与降级链路的红色区域。诚实的原则也适用于面试：**能讲清「哪些覆盖率是核心的、哪些是凑数的」**，比报一个虚高的数字更可信——面试官追问「为什么不是 100%」时，标准答案就是「样板代码与边界场景的投入产出比不值得」。

## 7. 验证实验

一个验收实验：全量跑 `mvn test` + `mvn verify`，确认三件事——**测试全绿**（记录用例总数：目标 80+ 条）；**覆盖率达标**（行 >= 70%，JaCoCo 报告里看各模块分布，Service 层要达到 80%+，Controller 层 60%+ 合理）；**改造回归验证**——故意改坏一处逻辑（如把 Milvus 检索 topK 改成 0），跑测试确认对应用例变红，再改回来——这个「故意弄坏」的实验证明测试真的能拦住回归，而不是摆设。测试数据（用例数、覆盖率、跑测耗时）记进 README 的质量小节。

## 8. 核心要点

1. 测试的价值是「以后改不坏」，不是「现在能跑」——它是 M2-M4 改造的安全网。
2. 金字塔策略：单元 70% / 接口 20% / 集成 10%，每层只测一层，mock 掉外部依赖。
3. 单元测试只测行为不断言实现，异常路径与边界必测。
4. 接口测试必测三场景：正常、校验失败、业务异常——这是统一响应体三件套的验收。
5. Testcontainers 用真中间件测 SQL 与 MQ/Milvus 闭环，一条真链路 > 十条 mock。
6. AI 链路在 AiGateway 出口打桩，JaCoCo 门禁强制行覆盖率 >= 70%。

> 🎯 **核心要点**：测试体系的最终形态是**「改造的安全网 + 质量的度量尺」**——安全网让 03-06 的每一刀都敢动，度量尺让「质量高」有了数据（80+ 用例、70% 覆盖率、故意弄坏能拦住）。这套体系本身就是面试「工程质量」的最强论据。
