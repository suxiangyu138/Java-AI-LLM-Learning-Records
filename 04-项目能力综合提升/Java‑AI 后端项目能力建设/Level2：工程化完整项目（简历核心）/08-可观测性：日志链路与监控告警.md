# 08 可观测性：日志链路与监控告警

> 交付保障的第一块：可观测性回答三个问题——**「系统还活着吗」（健康检查）、「哪一步慢了」（traceId 与耗时指标）、「出了什么事」（日志与告警）**。本模块建立「MDC traceId 链路 + Micrometer 四类指标 + Prometheus/Grafana + 告警」的完整可观测体系，让故障从「猜」变成「看」。

## 1. 动机：没有可观测性，故障就是黑盒

Level1 排障的方式是「看控制台报错」——单机单用户，看得过来。Level2 引入 MQ 异步、Milvus、限流降级后，一个请求会穿过「Controller → Service → 缓存 → MQ → 消费者 → Milvus → AI」七八个环节，**报错可能发生在任何一环，且日志散落在不同的线程与进程里**——用户报「回答不出来」，你手上有几千行日志，不知道哪几行属于这个请求。可观测性的目标：**任何一个故障，10 分钟内能回答「哪个请求、哪一步、为什么」**。三根支柱分工：**日志**回答「发生了什么」（带 traceId 串联），**指标**回答「变慢变多了吗」（趋势与告警），**健康检查**回答「活着吗」（探针）。本项目按「先链路、后指标、再告警」的顺序落地。

## 2. traceId 链路：一次请求的完整画像

traceId 是日志排障的骨架：**每个请求一个唯一 ID，贯穿所有日志行**。落地三步：**入口生成**——Filter 里检查请求头（上游传入则复用，否则 `UUID.randomUUID()` 生成），放入 MDC（02 篇日志规范已配 `%X{traceId}` pattern）；**跨线程传递**——MDC 是线程本地变量，MQ 消费者线程、异步线程池里 MDC 是空的——消费者监听器开头从消息头取 traceId 重新 `MDC.put`，异步任务用 `TaskDecorator` 传递，否则 traceId 在异步环节断裂；**跨服务传递**——将来拆微服务时，在 Feign/HTTP 客户端统一拦截器里把 traceId 塞进请求头（本项目单体用不上，但接口预留）。验证标准：**一次「上传 → 解析 → 问答」全链路，grep traceId 能捞出从接口入口到 AI 响应的每一行日志**——链路的完成度用这个实验验收。

```java
@Component
public class TraceIdFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) {
        String traceId = req.getHeader("X-Trace-Id");
        if (traceId == null || traceId.isBlank()) traceId = UUID.randomUUID().toString();
        MDC.put("traceId", traceId);
        res.setHeader("X-Trace-Id", traceId);   // 返回给前端，报障时提供
        try { chain.doFilter(req, res); } finally { MDC.clear(); }
    }
}
```

## 3. 指标体系：四类业务指标

指标（Metrics）回答「变慢变多了吗」，用 Micrometer（Boot 4.1 内置）埋点。**先想清楚要监控什么，再动手埋点**——本项目四类指标对应四个故障面：

| 类别 | 指标 | 告警信号 |
|---|---|---|
| HTTP | 请求量、P95/P99 延迟、5xx 错误率 | 延迟爬升 = 下游或代码问题 |
| 缓存 | 命中率、miss 数、空值缓存命中数、锁等待时长 | 命中率骤降 = 缓存策略失效；空值命中多 = 穿透 |
| MQ | 队列深度、消费失败数、DLQ 消息数 | 队列堆积 = 消费者故障；DLQ 有货 = 死信告警 |
| AI | 调用量、成功率、平均/首 token 延迟、token 消耗、降级次数 | 成功率下降 = provider 故障；降级多 = 限流或熔断 |

埋点方式：HTTP 指标由 Micrometer 自动埋（`management.metrics`），缓存/MQ/AI 三类用 `MeterRegistry.counter("kb.cache.miss")` 手动计数——**手动埋点要克制**：只埋「出故障时你要看什么」的指标，埋一堆没人看的指标是浪费。token 消耗指标额外记金额（按 06 篇的单价换算），**AI 成本可视化**是简历项目的差异化亮点——「我监控了 AI 成本，因为这是真实账本」。

手动埋点要统一封装：`KbMetrics` 组件持有 MeterRegistry，各模块注入后调 `kbMetrics.aiCallFailed(cause)`、`kbMetrics.cacheMiss()`——**指标命名有规范**（`kb.{模块}.{事件}`，同类事件统一命名），否则 Grafana 的聚合查询会因命名漂移而失效；面板里的口径（累加值 vs 速率）要在标题标注，`rate()` 是默认查询姿势——「总量 vs 速率」口径混乱是监控面板最常见的翻车点，同一指标在面板上既显示总量又显示速率，看的人会得出矛盾结论。

## 4. 监控基建：Actuator + Prometheus + Grafana

采集链路：**应用暴露指标 → Prometheus 抓取 → Grafana 展示**。Actuator 是 Boot 提供的指标出口（`spring-boot-starter-actuator` + `micrometer-registry-prometheus`），暴露 `/actuator/prometheus` 端点，Prometheus 配置抓取目标即完成接入：

```yaml
scrape_configs:
  - job_name: kb-prod
    metrics_path: /actuator/prometheus
    static_configs: [{ targets: ["kb-api:8080"] }]   # 09 篇 Compose 网络内地址
```

三个实践要点：**端点安全**——Actuator 端点不能裸奔公网，`management.endpoints.web.exposure.include: health,info,prometheus` 只暴露必要端点，内网抓取（09 篇网络配置）；**健康检查与探针**——`/actuator/health` 聚合各组件健康状态（Redis/MySQL/Milvus/RabbitMQ 的 `HealthIndicator` 自动注册），Docker 的 healthcheck 与 K8s 探针都消费它，**健康检查挂了组件要能体现在指标面板上**；**Grafana 面板**——四块面板对应四类指标：请求延迟与错误率、缓存命中率、队列深度、AI 成功率与成本，每块面板一个标题一个图，**面板是给「人」看的，克制比花哨重要**。

## 5. 告警规则设计

指标不告警等于没有监控——**告警是「深夜被叫醒」的规则，必须精心设计**。三条原则：**只告警需要行动的事**——队列堆积告警（需要扩容/排查消费者）值得叫醒，请求量波动（正常业务变化）不值得；**告警要有阈值依据**——错误率 > 5% 持续 5 分钟、队列深度 > 1000 持续 10 分钟、AI 成功率 < 90% 持续 3 分钟，阈值来自 08 篇压测基线（正常值之上留余量），拍脑袋的阈值会产生告警疲劳；**告警分级**——P1（AI 全挂、队列堆积）电话级，P2（错误率升高、DLQ 有货）工作群级，P3（命中率下降）次日处理级。告警消息要带上下文：**「kb.cache.miss 上升，命中率 50% < 80% 基线，最近 1 小时，怀疑缓存策略失效」**——收到告警的人应该能直接开始排查，而不是先查这是什么指标。

## 6. 压测与性能基线

压测的价值是**给「性能」定基线**——没有基线，指标告警没有阈值，面试讲性能没有数字。用 JMeter 或 wrk 压三个场景：**问答接口**（核心链路，含 RAG 与 AI）——测 P95/P99 首字延迟与吞吐，对齐 01 篇「P95 首字 < 3s」指标；**上传接口**（异步化验证，05 篇补 P95 对比）；**缓存命中场景**——命中时延迟 vs miss 时延迟对比（证明缓存有效）。压测纪律：**每轮压测记录环境**（几核、并发数、数据量），否则数字不可比；**测完更新基线文档**（docs/perf.md）：场景、并发、P95、P99、吞吐、机器配置，面试讲性能时直接背这张表。注意压测不要打真 AI——mock 掉 AiGateway（07 篇的桩复用），否则成本失控且结果被 provider 抖动污染；AI 真实延迟单独测（一次带真实调用的冒烟测试，记录平均首 token 时间）。

## 7. 验证实验

三个验收实验：**链路实验**——发起一次「上传 + 问答」，在日志里按 traceId 捞出全链路日志，确认 8 个环节都在、耗时字段可读；**指标实验**——用 JMeter 制造负载（含一个 5xx 场景），在 Grafana 面板看到「请求量曲线、P95 曲线、错误率曲线」随压测变化，确认指标真实反映系统状态；**告警实验**——临时把 AI 服务地址改错，确认 P1 告警触发（AI 成功率下降）且 5 分钟内可定位到 AiGateway 日志。三个实验做完，可观测体系才算「能用了」——**面板不是给截图用的，是给排障用的**。

## 8. 核心要点

1. 可观测三问：活着吗（健康检查）、哪一步慢（traceId + 耗时）、出了什么（日志 + 告警）。
2. traceId 三步：入口 Filter 生成入 MDC、MQ/异步线程重新 put、跨服务塞请求头（预留）。
3. 四类指标对应四个故障面：HTTP / 缓存 / MQ / AI（含成本），手动埋点只埋「故障时要看」的。
4. Actuator 限端点暴露 + Prometheus 抓取 + Grafana 四面板；健康检查聚合全组件。
5. 告警三原则：只告警要行动的事、阈值来自压测基线、分级 + 带上下文。
6. 压测建基线（docs/perf.md），mock AI 压应用链路，AI 真实延迟单独冒烟测。

> 🎯 **核心要点**：可观测性的终局是**「10 分钟内从告警到根因」**——告警告诉你「AI 成功率掉了」，traceId 让你捞出这一个请求的全部日志，指标告诉你「从什么时候开始的、影响了多少」——三件套合起来，黑盒排障变成白盒看诊。这套能力是「生产级」与「Demo」最直观的差距。
