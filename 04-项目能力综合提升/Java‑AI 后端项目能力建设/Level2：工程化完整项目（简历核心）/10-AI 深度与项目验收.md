## 1. RAG 评估体系：效果要能度量

Level1 的 RAG「能回答」但「效果如何」没有答案——这正是简历项目与 Demo 的分水岭。评估体系三件套：**测试集**——50 条「问题 → 期望命中 chunk → 参考答案」三元组，来源三路：从文档内容反写（阅读理解式）、真实用户提问收集（演示时让同学问过的问题）、边界问题构造（检索不到的、模糊的、跨文档的）；**指标**——**检索质量**用 Recall@5（期望命中 chunk 是否在 top5）与 MRR（命中的排名位置），**生成质量**用上下文相关性（LLM-as-Judge 打分 1-5）与答案正确性（参考标准答案比对），**体验**用端到端延迟；**评估脚本**——Python 或 Java 小工具批量跑 50 题，输出指标表。评估的意义：**每次改动（分块大小、topK、ef、混合检索、prompt 模板）前后各跑一遍，指标差异就是「这刀改对了没有」的证据**——「我把 topK 从 3 调到 5，Recall@5 从 78% 升到 86%，但延迟从 1.2s 升到 1.8s」这句话在面试里的分量远超「我的 RAG 效果很好」。

调参记录是评估体系的副产品：**docs/eval.md** 里维护「参数 → 指标 → 结论」表（分块 500/1000 字、topK 3/5/8、ef 32/64/128、纯向量 vs 混合检索各一轮），每个参数至少一轮实验。**评估的边界也要讲清**：LLM-as-Judge 有偏好偏差（喜欢更长答案、自我偏好），50 题测试集覆盖不了长尾——评估是「趋势度量」不是「绝对真理」，这个认知本身就是面试加分点。

## 2. Agent 与工具调用：Function Calling 落地

把问答从「纯生成」升级为「能干活」：用户问「库里有多少篇文档」「最近上传了哪些」「统计一下各知识库的文档数」——纯 RAG 回答不了，工具调用能。Spring AI 2.0 的工具调用是一等公民：**`@Tool` 注解定义工具**（方法即工具，参数 JSON Schema 自动生成），**ToolCallingAdvisor 自动注册**，模型按需调用、框架自动执行并把结果回传。落地两个工具：**文档统计**（`countDocs(kbId)`——按知识库统计文档数，参数化防止全表扫描）与**库状态查询**（`listRecentDocs(kbId, limit)`——最近上传列表），工具方法在 `kb-ai` 层、内部复用 `kb-core` 的 Service：

```java
@Tool(description = "统计指定知识库的文档数量")
public long countDocs(long kbId) {
    return docService.countByKb(kbId);
}
```

落地的三个工程要点：**工具描述要写清「什么时候用」**——模型靠描述决定是否调用，描述模糊的工具等于没有；**工具结果要结构化**——返回 JSON 或简单类型，不要返回大段文本让模型再解析；**工具调用要可观测**——记录「模型调了哪个工具、参数是什么、结果如何」进日志与指标（08 篇 AI 指标加一类「工具调用次数」），面试展示 Agent 日志是「我真的做过 Agent」的实锤。范围克制：**两个工具就够**——工具链是展示「机制」，不是堆「数量」，M4 时间有限，把两个工具做到「调用 → 执行 → 回传 → 回答」全链路可演示即可。

## 3. 流式完整实现：SSE 体验

流式（SSE）是「AI 应用体验」的基本盘——等 5 秒一整块返回 vs 0.5 秒开始逐字渲染，观感天差地别。实现链路：**Controller 返回 `SseEmitter`**（或 `Flux<ServerSentEvent>`），**AiGateway 用流式 API**（Spring AI 2.0 `ChatClient.prompt().stream()`）拿 token 流，**逐块推给前端**。工程细节五个：**首 token 时间**——流式体验的指标是「首 token 延迟」而不是「总时长」，前端显示打字机效果的关键是尽快吐出第一个 token；**流中断处理**——`onError` 发事件并结束、`onComplete` 发结束标记（前端停止 loading），用户断网或服务端异常不能让前端无限等待；**超时控制**——SSE 连接的空闲超时（如 2 分钟无数据自动断开）与总时长上限，防连接泄漏（08 篇超时体系延伸到流式）；**与 MQ/异步共存**——流式是同步长连接，与解析任务异步化不冲突：**流式用在「回答」路径（用户等着），异步用在「解析」路径（用户不用等）**——这个「什么该等、什么不该等」的判断要能讲清；**兼容降级**——流式路径失败时回落到 06 篇的降级策略（L1 片段兜底也可流式逐段推）。

## 4. 面试深挖：精选题库

面试官深挖的是「为什么」，本层每篇的「动机与取舍」就是答案。精选高频题按方向分类：**工程规范**——「统一响应体为什么 HTTP 永远 200？」「全局异常和 try-catch 的关系？」「参数校验为什么用声明式？」；**可靠性**——「延迟双删解决什么问题？它的边界是什么？」「为什么用 Milvus 不用 pgvector？」「MQ 怎么保证不丢不重？」「RabbitMQ 为什么用 Quorum Queue？」「AI 降级分几层？为什么？」「限流为什么选令牌桶？」；**质量与交付**——「测试金字塔为什么这么分配？」「Testcontainers 解决了什么？」「traceId 跨线程怎么传递？」「告警阈值怎么定的？」「Compose 里 depends_on 为什么用 service_healthy？」；**AI 深度**——「RAG 评估指标有哪些？Recall@5 和 MRR 区别？」「调参都调过哪些？结果如何？」「工具调用是怎么循环的？」「SSE 和 WebSocket 为什么选 SSE？」。答题范式：**先给结论、再讲方案、最后给本项目的数据**——「我用延迟双删 + 消息重试，实测并发下旧值读取从 N 次降到 < 5 次」。题库答案在文档里都能找到，但**要求用自己的话讲出来，对着录音练三遍**。

## 5. 项目验收检查单

三硬指标逐项打勾：**能演示**——干净机器 `docker compose up` 10 分钟拉起，演示检查单全过，演示剧本（上传文档 → 提问 → 流式回答 → 工具调用 → 面板展示）完整走过；**能压测**——docs/perf.md 有压测基线（问答 P95 首字 < 3s、上传接口 P95 < 500ms、缓存命中率、AI 成功率），指标面板与告警规则就位；**能深挖**——每个组件能讲「为什么选它、怎么改的、验证数据」，题库 40+ 题能对答；**代码质量**——分层清晰、测试 80+ 条、覆盖率 >= 70%、README/design.md/eval.md/CHANGELOG 四件套齐全。另加三个「简历硬伤」自检：**项目不是抄的**——每个模块的重写痕迹与踩坑记录在 CHANGELOG 里；**数据不是编的**——压测与评估数据全部来自真实实验，能现场复现；**能讲边界**——延迟双删不是强一致、评估有偏差、工具链只有两个——「知道方案的边界」比「方案完美」更能证明工程成熟度。

## 6. Level3 预告

Level2 收官后，项目已具备「单体工程化」的全部要素，Level3 的进阶方向在三个轴上继续深挖：**高并发**——压测发现瓶颈（连接池、Milvus 查询、AI 并发配额），做性能优化专项；**微服务化**——按 kb-core/kb-ai 拆独立服务，引入 Spring Cloud Alibaba（Nacos 注册配置、OpenFeign 调用、Sentinel 流控——06 篇的 Resilience4j 正好对照升级），MQ 链路变跨服务链路，traceId 跨服务传递真正落地（08 篇预留的请求头逻辑启用）；**分布式与云原生**——分布式事务（Seata，如上传后的多库一致性）、Kubernetes 部署替代 Compose、GitOps 流水线。Level3 的深挖顺序：**先高并发压测找瓶颈（知道缺什么），再按瓶颈方向做微服务化（缺什么补什么）**——带着 Level2 的数据基线进 Level3，每一步优化都有「前后对比」。

## 7. 核心要点

1. RAG 评估三件套：50 题测试集 + 检索/生成/体验三类指标 + 评估脚本，每次调参前后跑一遍留数据。
2. Agent 工具调用：Spring AI 2.0 @Tool 定义、ToolCallingAdvisor 自动注册，工具描述写明触发条件、结果结构化、调用可观测。
3. SSE 流式：流式用于「回答」（用户等）、异步用于「解析」（不用等），首 token 时间是体验指标，断流与超时必须有处理。
4. 面试深挖题库 40+ 题按四方向分类，答题范式「结论 → 方案 → 项目数据」，对着录音练三遍。
5. 验收三硬指标 + 三硬伤自检：能演示、能压测、能深挖；项目不抄、数据不编、能讲边界。
6. Level3 进阶：先压测找瓶颈，再做微服务化与云原生，每一步都有数据基线可对比。

> 🎯 **核心要点**：Level2 的终局一句话：**「项目是长在数据上的」**——评估指标告诉你效果好不好，压测基线告诉你性能行不行，验收检查单告诉你敢不敢上简历。当「为什么这么改」每个问题都有「动机 + 方案 + 数据」三层答案时，这个项目就真正配得上「简历核心」——它不再是一个项目，而是一整套工程决策的证据链。
