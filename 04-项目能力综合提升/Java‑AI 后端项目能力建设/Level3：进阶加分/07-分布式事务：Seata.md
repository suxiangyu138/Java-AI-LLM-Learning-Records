# 07 分布式事务：Seata

> 微服务化的第四根支柱：Level2 的事务是「一个方法一个事务」（本地事务），微服务化后跨服务的数据一致性成为新问题——Seata 提供强一致方案（AT/TCC/XA），MQ 提供最终一致方案。本模块讲清「什么场景需要、AT 模式怎么工作的、什么时候不用它」。

## 1. 问题：跨服务事务为什么是难题

Level2 单体里「上传文档 → 更新状态」是一个本地事务：`@Transactional` 一个方法搞定，失败全回滚。微服务化后这个操作跨了两个服务（kb-doc 建文档记录、kb-ai 触发向量化），**本地事务的边界消失了**：kb-doc 提交成功、kb-ai 失败——数据库里出现「有文档记录但没向量化」的中间状态。为什么不能「两个服务共用一个事务」？因为事务的本质（ACID）依赖「同一个数据库的锁与日志」，跨服务跨库后没有统一的事务管理器——**分布式事务是「把本地事务的 ACID，扩展成跨服务的一致」**，难点在「分布式环境下没有单一的回滚锚点」。必须清醒：**分布式事务有代价（性能损耗、复杂度），能避免就避免**——面试口径：「我用分布式事务解决 A 场景，但优先通过『接口设计成幂等 + 最终一致』避免引入分布式事务」。

## 2. Seata 架构：TC/TM/RM 三组件

Seata 2.6.x（SCA 2025.1.0.0 内置）解决分布式事务的三组件架构（面试必背）：**TC（Transaction Coordinator，事务协调者）**——独立部署的服务，管理全局事务的状态（提交/回滚的决策者）；**TM（Transaction Manager，事务管理器）**——业务代码里，发起全局事务（`@GlobalTransactional` 标注的方法），向 TC 请求「开一个全局事务」；**RM（Resource Manager，资源管理器）**——各服务的数据库操作，向 TC 汇报「我这边本地事务的结果」，响应 TC 的提交/回滚指令。数据流：TM 开启全局事务 → 各服务 RM 执行本地事务并注册 → 全部成功 TC 通知各 RM 提交；任一失败 TC 通知各 RM 回滚——**「全局决策在 TC，本地执行在各 RM」**是三组件的核心分工。

## 3. AT 模式：原理与取舍

AT（Automatic Transaction）是 Seata 的招牌模式，原理三句话：**第一阶段：业务 SQL 照常执行，Seata 在背后记录 undo_log**（操作前镜像 + 操作后镜像，undo_log 表在各业务库内）；**第二阶段：全部成功 → 删除 undo_log（异步清理）**；**任一失败 → 用 undo_log 的镜像数据反向生成补偿 SQL 回滚**。关键认知：**AT 不是「两阶段锁」**——第一阶段业务事务已提交（资源释放，性能好），回滚靠「补偿」（用镜像数据反做），而不是「锁住资源等所有人表决」。取舍：**优势**——业务代码无侵入（`@GlobalTransactional` 一个注解，SQL 不用改）、性能好（一阶段提交）；**代价**——**全局锁**（AT 在二阶段前对回滚涉及的数据加全局锁，写并发会排队）、undo_log 有存储开销、隔离级别被降级（读未提交——中间态可能被读到，要用防脏读配置）。面试讲 AT 的标准姿势：「AT 是补偿式事务，一阶段提交、二阶段补偿，用 undo_log 做回滚，代价是全局锁与隔离级别降级」。

## 4. 模式选型：AT / TCC / XA / MQ 对比

分布式事务没有银弹，四选一按场景：

| 模式 | 一致性 | 侵入性 | 性能 | 适用场景 |
|---|---|---|---|---|
| AT | 强（有窗口） | 低（注解即可） | 中（全局锁） | 简单跨服务写操作（本项目默认） |
| TCC | 强 | 高（Try/Confirm/Cancel 三方法手写） | 高（无锁） | 复杂业务（预扣款、预订） |
| XA | 强 | 低（但依赖 DB 支持） | 低（全程锁） | 银行等强一致低并发场景 |
| MQ 最终一致 | 最终 | 中（消息 + 幂等） | 高 | 可容忍延迟一致的场景（本项目大部分） |

选型原则：**先问「必须强一致吗」**——能接受最终一致（秒级）就用 MQ（Level2 05 篇的消息可靠性四件套 + 幂等就是最终一致的实现），性能最好、无全局锁；**必须强一致且简单**——AT；**必须强一致且复杂**——TCC（手写三方法，成本高）；XA 在互联网业务基本不用（性能代价太大）。**「先 MQ 后 AT」是本项目的最终答案**——解析任务链路（文档记录 + 向量化）用 MQ 最终一致（失败重试 + 死信，Level2 05 篇已有），上传 + 状态更新的即时一致用 AT。面试的完整回答 = 场景分析 + 选型理由 + 代价认知。

## 5. 本项目的落地与边界

落地一个 AT 场景：**「创建知识库 + 初始化默认文档」**跨 kb-doc 与 kb-ai——`@GlobalTransactional` 标注 Service 方法，两个服务的本地事务注册进全局事务，Seata 服务端（TC）随 09 篇 Compose/K8s 部署（需要独立数据库存事务状态）。四个工程细节：**undo_log 表要先建**（AT 依赖它，表缺失 = 一阶段成功二阶段无法回滚）；**事务超时与重试**——全局事务默认超时（如 60s），超时 TC 回滚，超时长的分支事务（调 AI 这类慢外部服务）**不应该放进全局事务**——全局事务包住秒级以上的外部调用，会把锁和决策窗口拖长，这是 AT 场景设计的第一原则；**性能观测**——全局锁等待时间进指标（Level2 08 篇面板加一类 Seata 指标），锁等待长 = 写并发热点，考虑改 TCC 或 MQ；**回滚日志要能查**——TC 的事务日志是排查「为什么回滚」的唯一线索（哪个分支失败、失败原因、回滚是否成功），Seata 的 TC 日志与业务日志要一并纳入 08 篇的日志聚合，否则「回滚了但不知道为什么」无从查起。

边界与克制（面试分水岭）：**能用 MQ 不用 AT**——本项目的解析链路、缓存清理链路都是 MQ 最终一致（Level2 04/05 篇已建立）；**能用幂等不用事务**——「重复上传幂等」靠状态表解决（Level2 05 篇），不需要分布式事务；**只保核心场景**——全链路套 `@GlobalTransactional` 是把性能与复杂度拉满的错误示范。**「知道什么时候不用分布式事务」与「知道怎么用」同等重要**——这是与「背了 Seata 就到处用」的选手的区分点。

## 6. 验证实验

三个验收实验：**成功实验**——创建知识库全链路成功，TC 事务状态「提交」、undo_log 被清理；**失败实验**——人为让 kb-ai 的初始化接口抛异常，观察 TC 回滚、kb-doc 侧数据被补偿（undo_log 反向 SQL 生效）、最终数据一致；**对照实验**——同一场景对比「本地事务（拆服务前）」与「AT（拆服务后）」的耗时差异，记录全局锁带来的性能代价（数据诚实记录）。三个实验 + 「为什么解析链路用 MQ 而这里用 AT」的选型论证，就是分布式事务模块的完整验收。

## 7. 核心要点

1. 分布式事务 = 把本地 ACID 扩展成跨服务一致，没有单一回滚锚点是难点的本质。
2. 三组件分工：TM 发起、TC 决策、RM 执行——全局决策在 TC，本地执行在各 RM。
3. AT 是补偿式事务：一阶段提交（性能好）、二阶段 undo_log 补偿回滚；代价是全局锁与隔离降级。
4. 选型顺序：能 MQ 最终一致就不用事务；强一致简单用 AT；强一致复杂用 TCC；XA 基本不用。
5. 落地细节：undo_log 表先建、事务超时、Seata 指标进面板、回滚日志可查。
6. 克制是深度：幂等能解决的不上事务，全链路套 @GlobalTransactional 是错误示范。

> 🎯 **核心要点**：分布式事务的工程哲学是**「能避免就避免，非用不可时选最轻的」**——最终一致优先（MQ + 幂等），强一致按复杂度选 AT/TCC。Seata 只是工具，「什么场景需要、什么时候不用」的决策能力才是分布式事务面试的考察点。
