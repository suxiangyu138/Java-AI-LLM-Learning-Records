## 1. 优化一：Caffeine + Redis 多级缓存

Level2 的缓存是「应用 → Redis」两级（应用进程外），热点问题：**每个实例的每个请求都打到 Redis**——同一个热点 key 被 100 个并发请求读 100 次 Redis，Redis 成了新的瓶颈点。多级缓存加一层「进程内」：**Caffeine（本地 JVM 缓存）→ Redis（分布式缓存）→ 数据库**。读路径：先查 Caffeine（纳秒级命中），miss 再查 Redis（毫秒级），再 miss 查库并回填两级。收益与代价：

| 维度 | 收益/代价 |
|---|---|
| 读性能 | 热点命中从「毫秒级 Redis 往返」降到「纳秒级本地内存」，QPS 5000 场景收益显著 |
| Redis 压力 | 热点请求不再打 Redis，Redis 的瓶颈点被稀释 |
| 一致性问题 | 两级缓存 = 两份副本 = 一致性难题加倍：本地缓存过期如何同步？ |
| 部署复杂度 | 多实例部署时每实例一份本地缓存，缓存一致性靠「过期时间 + 广播失效」 |

一致性方案（面试必考）：本地缓存 TTL 设短（如 30s）+ 写路径主动失效——Level2 的「删 Redis」升级为「删 Redis + 本地失效」，本地失效单实例用 `Caffeine.invalidate`，多实例用 MQ 广播（复用 Level2 05 篇的 `cache-evict` 队列，消息里带 `cacheKey + nodeId`）。**多级缓存不适合所有数据**——热点读多写少的数据（文档元数据、配置）收益大；写频繁的数据（问答记录）收益小且一致性成本高，只放 Redis 不放本地。Caffeine 配置三件套：`maximumSize`（上限防 OOM）、`expireAfterWrite(30s)`（一致性窗口）、`recordStats`（命中率指标进 Level2 08 篇面板——多级缓存必须有命中率数据支撑「有效」这个结论）。

两个工程细节：**本地缓存不能缓存「用户相关数据」**——Caffeine 在实例间独立，用户 A 的数据缓存在实例 1、请求路由到实例 2 就 miss 且造成数据串读风险，**多级缓存只用于全局共享的读多写少数据**（文档元数据、配置），用户维度的缓存仍走 Redis；**缓存预热**——热点 key（如首页热门文档列表）在应用启动时主动加载进本地缓存，避免冷启动后第一波请求全部 miss 打 Redis——预热逻辑写在 `ApplicationRunner` 里，与 Level2 的监听器知识呼应。

## 2. 优化二：虚拟线程替代平台线程

虚拟线程（JDK 25 成熟特性，JEP 491 已修复 pinning 问题、JEP 525 结构化并发配套）是 IO 密集型服务的吞吐量级提升方案。原理一句话：**平台线程是「1:1 绑定 OS 线程」，虚拟线程是「N:1 映射到少量载体线程」**——线程创建成本从微秒级降到纳秒级，线程数从「几千」到「百万」不再受 OS 限制。本项目的高价值改造点：**问答接口**（IO 密集：检索 Milvus + 调 LLM，一次请求 80% 时间在等 IO）+ **MQ 消费者**（每个消息都在等外部 IO）。

Spring Boot 4.x 的启用方式：`spring.threads.virtual.enabled=true`（Boot 4 起对 Tomcat 与 `@Async` 生效），MQ 消费者把 `SimpleAsyncTaskExecutor` 换成虚拟线程执行器。两个关键认知：**虚拟线程 ≠ 万能**——CPU 密集（计算、加解密）用虚拟线程无收益甚至更差（调度开销），选型标准是「IO 等待占比」；**虚拟线程不能无脑换**——synchronized 里的 IO 会 pinning（阻塞载体线程），JDK 25 已修复大部分场景（JEP 491），但锁竞争热点仍要实测——**改造前用 JFR 看 lock contention，改造后对比 P95 与吞吐**。面试讲虚拟线程的深度姿势：「平台线程 1:1 OS、虚拟线程 N:1 载体线程、适合 IO 密集、pinning 的 JEP 491 修复、与 structured concurrency（JEP 525）配合」——五句话完整。应用侧还有一个隐性收益：**连接池与线程池的压力同降**——线程数不再受 OS 限制后，「每请求一线程」模型直接成立，业务代码不用再纠结「用共享线程池还是自建线程池」——虚拟线程的收益不只是吞吐，还有**并发编程模型的简化**。

## 3. 优化三：连接池与线程池调参

零成本优化（改配置不改代码），按 01 篇归因结果调参，三个池：**数据库连接池（HikariCP）**——`maximum-pool-size` 不是越大越好（每连接一份内存与锁开销，过大反而性能下降），按「并发数 × 每请求平均占用连接数」估算起步值（如 100 并发 × 0.5 连接 = 50），实测找最优；`connection-timeout` 设短（3s）——池满时快速失败进降级，而不是无限等导致线程堆满；**HTTP 客户端连接池**——Spring AI 的 WebClient/RestClient 连接复用（`max-connections`、`max-idle-time`），AI 调用是外部依赖，连接池耗尽 = 全部调用排队，这是「AI 调用多但连接池小」的典型事故；**线程池（业务异步）**——`@Async` 线程池显式配置核心/最大线程数与队列（默认的 SimpleAsyncTaskExecutor 每次新建线程，高并发下线程数失控），虚拟线程启用后此池可被替代。

调参的验证纪律：**一次调一个参数**——连接池与线程池参数相互影响（池满的表现可能是线程池排队引起的），同轮调两个参数无法归因；**调参结果记录进 perf.md**——「池 10→50，QPS 500 时 P95 2s→300ms」，面试直接背这张表。

## 4. 优化不做什么：边界与克制

「不做什么」是进阶项目的成熟度体现，三条克制：**不做无数据的优化**——大模型推理加速（量化、投机采样）是本项目用不上的能力，做了也是「为做而做」；**不动 AI 链路的随机性**——LLM 的 P95 由 provider 决定，代码优化改不了外部延迟，能做的只有「并发控制 + 降级」——**区分「能优化的」与「只能降级的」**是性能思维的成熟标志；**不提前优化**——压测数据里没有的问题不优化，例如「用户量 100 时的连接池调优」是伪优化——优化目标永远是「01 篇定位的真实瓶颈」。

## 5. 性能对比实验

三个优化的验收实验，全部前后对比：**多级缓存实验**——同压测场景（问答 + 文档元数据），对比「Redis 单级」vs「Caffeine + Redis」：记录 P95、Redis QPS（预期大幅下降）、本地命中率（预期 > 60%）；**虚拟线程实验**——同一压测脚本，`spring.threads.virtual.enabled=false` vs `true`：记录吞吐（预期提升 2-5 倍，IO 密集场景）与 P95 稳定性；**调参实验**——连接池参数前后对比（预期 P95 与池耗尽次数下降）。三个实验的数据进 perf.md 的「优化记录」表——**「压测数据 + 优化前后对比」就是简历项目模块里『高并发优化』亮点的全部素材**。

## 6. 核心要点

1. 多级缓存（Caffeine + Redis）降热点：本地 TTL 短 + 写路径广播失效，只适合读多写少的热点数据。
2. 虚拟线程替代平台线程：IO 密集才有效、CPU 密集无收益；JDK 25 的 pinning 修复（JEP 491）与结构化并发（JEP 525）是配套知识。
3. 三个池的调参纪律：一次一个参数、起步值按估算 + 实测找最优、池满快速失败进降级。
4. 克制三原则：无数据不优化、外部随机性只能降级、压测没暴露的问题不提前优化。
5. 每个优化必须有前后对比数据（P95/吞吐/命中率），这是简历「高并发优化」亮点的全部素材。

> 🎯 **核心要点**：高并发优化的本质是**「把钱花在刀刃上」**——多级缓存花成本降热点、虚拟线程换结构提吞吐、调参零成本捡漏，三个优化覆盖「热点、结构、参数」三个层面，每一层都有 01 篇的瓶颈数据支撑。优化的终点不是「更快」，而是**「知道为什么快了」**。
