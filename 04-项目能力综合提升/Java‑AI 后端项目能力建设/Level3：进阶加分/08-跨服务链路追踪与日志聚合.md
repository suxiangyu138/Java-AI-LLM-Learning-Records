# 08 跨服务链路追踪与日志聚合

> 微服务化的第五根支柱：单体时代「grep traceId 捞全链路」在微服务下失效——日志散落在多个服务与实例里。本模块把 Level2 的 traceId 升级为**跨服务传递 + 追踪系统可视化 + 日志聚合检索**，让分布式排障从「翻四个服务的日志」变成「一条链路图」。

## 1. 问题：单体排障方法在微服务下失效

Level2 08 篇的排障流程：告警 → 拿到 traceId → 单体日志里 grep 出全链路。微服务化后这个方法失效：**一次「上传 → 解析 → 问答」的请求穿过 kb-gateway → kb-doc → RabbitMQ → kb-ai → kb-doc」**，日志在 4 个服务的 12 个实例里——grep 哪个实例？traceId 能不能跨服务保持同一个？**每个服务只知道自己的日志，没有人能看到整条链**。分布式排障的三个难题：**分散**——日志在多个服务多个实例，检索要聚合；**断裂**——traceId 不传递，链路就断在各服务边界；**无视图**——没有可视化，靠脑补链路拓扑。本模块三个能力一一对应：日志聚合（解决分散）、traceId 传递（解决断裂）、追踪系统（解决视图）。

## 2. 跨服务 traceId 传递

traceId 跨服务传递是 05 篇 Feign 拦截器的延续（前置已做），现在补全三处：**Feign 调用**（已写：`RequestInterceptor` 从 MDC 取 traceId 塞请求头）；**MQ 消息**（已写：Level2 05 篇消息头带 traceId，消费者恢复 MDC）；**网关入口**（kb-gateway 的 GlobalFilter：接收或生成 traceId，塞进转发头，响应回传——用户报障时前端提供的 traceId 从这里来）。传递的完整性验证标准：**一次跨服务请求，4 个服务的日志里 grep 同一个 traceId，能按时间顺序拼出完整链路**——这个实验在验证前先做，追踪系统是它的可视化升级。链路完整性还有一个配套约定：**traceId 的日志输出位置统一**——所有服务的日志 pattern 都含 `[%X{traceId}]`（Level2 02 篇的规范在微服务下升级为「所有服务统一」），否则「有 traceId 但有些日志行没打出来」，聚合检索时就断档。细节坑：**异步线程 MDC 不继承**（Level2 08 篇的 TaskDecorator 在微服务下每个服务都要配）、**traceId 生成规则统一**（全链路一个 ID，不重新生成——网关生成了，服务间只传递不重造）。

## 3. 追踪系统：Micrometer Tracing / SkyWalking 选型

traceId 传递解决「日志能串起来」，追踪系统解决「不用 grep、直接看图」——自动记录每次调用的调用链（服务 → 服务 → 数据库），展示耗时瀑布图。两个主流选型：

| 维度 | Micrometer Tracing + OTel | SkyWalking |
|---|---|---|
| 定位 | 官方标准、埋点库（配合 OTel Collector） | 独立 APM 平台（Agent 无侵入） |
| 接入 | 依赖 + 配置 + OTel 采集器 | Java Agent 一行参数 |
| 数据 | trace 指标由自己定义展示（配 Grafana） | 自带 UI：链路图/拓扑/告警 |
| 部署 | 需自搭采集与存储链 | 一套服务端（OAP + UI） |

本项目选 **Micrometer Tracing（Boot 4 内置）+ OTel**：理由与 Level2 08 篇一脉相承——Boot 4 原生集成（`management.tracing` 配置即可，traceId/spanId 自动与日志关联）、与现有 Prometheus/Grafana 面板同生态（链路数据与指标数据一张图）、OTel 是行业标准（仓库可观测体系有完整知识，将来上 OTel Collector 无痛）；SkyWalking 的 Agent 无侵入很诱人，但多一套服务端要维护，且与既有面板生态割裂——**「选型看生态协同」是这里的判断标准**。落地三件套：依赖 `micrometer-tracing-bridge-otel` + 配置 exporter 到 OTel Collector（或直接 Prometheus 兼容端点）+ Grafana 的 Traces 数据源。

**采样策略**是追踪落地的关键配置：全量采样每个请求都记录，高流量下存储成本不可控（且大部分请求是正常路径，排查价值低）；**按需采样**——默认 10% 采样 + 错误请求 100% 采样（错误链路全量留痕），是生产标准姿势。本项目演示量小可 100%，但配置必须理解采样策略——面试被问「追踪系统在高峰期的开销」时，答案就是「采样率权衡」。

**span 命名与语义**要规范：每个服务对入口操作命名 `服务名/操作`（kb-doc/parse），链路图的可读性全靠命名规范——不规范的命名让瀑布图变成天书。

## 4. 日志聚合：EFK / Loki 选型

日志聚合解决「日志散在实例里搜不了」：所有服务的日志统一采集到一个平台，按 traceId/服务/时间检索。两个选型：

| 维度 | EFK（ES + Fluentd/Filebeat + Kibana） | Loki + Promtail + Grafana |
|---|---|---|
| 定位 | 全文检索引擎生态 | 轻量日志栈（Grafana 同生态） |
| 索引 | 全量索引，检索功能强 | 只索引标签，内容按需拉取 |
| 资源占用 | 高（ES 吃内存） | 低 |
| 与现有体系 | 需接入 Kibana（新面板） | Grafana 里直接看（零新 UI） |

本项目选 **Loki + Promtail + Grafana**：与 Level2 08 篇的 Prometheus + Grafana 同一生态（指标与日志一个入口，按 traceId 关联跳转：指标告警 → 日志详情）、资源占用低（演示机器扛得住 ES 集群不现实）、检索场景够用（按服务/级别/traceId 过滤，不需要 ES 的复杂全文能力）。落地：Promtail 以 Docker 日志驱动采集（09 篇 Compose 里配置 `logging.driver: loki` 或 Promtail 抓 docker socket）→ Loki → Grafana 加数据源——**「指标 + 日志 + 链路」三数据源同一入口**，就是可观测性三支柱的完整形态。

## 5. 排障实战：一次跨服务故障的定位

用真实排障流程验证体系，故障剧本：「用户上传文档后一直显示解析中」。定位路径：**面板看指标**——Grafana 队列深度面板：kb.doc.parse 队列堆积（指标定位到「消费者慢了或挂了」）→ 看 MQ 消费者所在服务 kb-doc 的错误率与 CPU；**日志看细节**——Loki 里按 `service=kb-doc` + 时间过滤，看消费者日志：`向量化调用失败，重试 3 次后进死信`（日志定位到「kb-ai 的向量化接口超时」）；**链路看全程**——Grafana Traces 打开一条死信消息的 traceId：kb-doc → kb-ai 的调用耗时 3s（超时）、kb-ai 的 LLM 调用段标红——**根因：AI provider 高峰限流（DeepSeek V4 峰谷定价时段）导致向量化超时**。结论：加 AI 调用的重试退避 + 降级策略（Level2 06 篇已建，这里验证跨服务链路下依然生效）。**这套「指标 → 日志 → 链路」的三步定位法，就是面试「你怎么排分布式故障」的标准答案**。

## 6. 验证实验

三个验收实验：**传递实验**——发起一次上传 + 问答，在 Loki 里按 traceId 搜出 4 个服务的日志，时间顺序拼出完整链路（traceId 跨服务不断裂）；**可视化实验**——Grafana Traces 里看到一次调用的瀑布图（kb-gateway → kb-doc → kb-ai，各段耗时标注）；**排障实验**——按「故障剧本」走一遍三步定位法，从告警/指标到根因，全程截图存档（这是面试「排障案例」的素材）。三个实验完成，分布式可观测闭环验收通过。

## 7. 核心要点

1. 分布式排障三难题：分散（日志聚合解决）、断裂（traceId 传递解决）、无视图（追踪系统解决）。
2. traceId 传递三处补全：Feign 拦截器（05 篇已写）、MQ 消息头（Level2 已写）、网关入口；只传递不重造。
3. 追踪系统选 Micrometer Tracing + OTel（Boot 4 内置、与 Grafana 同生态），SkyWalking 的 Agent 无侵入是备选。
4. 日志聚合选 Loki + Promtail（轻量、同生态），「指标 + 日志 + 链路」三数据源同一入口。
5. 排障三步法：指标定位「哪慢了」→ 日志看「为什么」→ 链路看「全程」——这是分布式排障的标准答案。
6. 验证三件套：traceId 跨服务可捞、瀑布图可看、故障剧本三步定位可复现。

> 🎯 **核心要点**：分布式可观测的本质是**「把分散的日志与调用，重组成一条可视化的链路」**——traceId 是胶水（串联），日志聚合是仓库（检索），追踪系统是地图（视图）。三件套齐了，「这个请求经历了什么」在微服务下不再是翻日志的苦役，而是一个可复现的定位流程。
