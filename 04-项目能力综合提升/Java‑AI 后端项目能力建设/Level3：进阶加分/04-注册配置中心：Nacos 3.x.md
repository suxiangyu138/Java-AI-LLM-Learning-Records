# 04 注册配置中心：Nacos 3.x

> 微服务化的第一根支柱：服务之间「怎么找到彼此」（注册发现）与「怎么统一改配置」（配置中心）。Nacos 3.x 同时解决这两个问题——注册发现用临时实例 AP 模式，配置中心用长轮询推送，两个机制、一套心智。本项目三个服务 + 网关全部接入。

## 1. 为什么需要注册中心：从写死地址到动态发现

单体里没有「服务地址」问题——方法调用是 JVM 内跳转。微服务化后 kb-ai 调用 kb-doc，第一个问题就是**「kb-doc 在哪」**：写死 IP + 端口？三个不可接受——**部署环境不同地址不同**（本地/测试/生产各一套配置）；**实例扩缩容地址会变**（kb-doc 加到 3 个实例，写死只能指向一个，负载均衡失效）；**实例故障无从感知**（写死的地址指向一个挂了的实例，调用方不知道也换不了）。注册中心的答案：**服务启动时自报家门（服务名 + IP + 端口）到注册中心，调用方按服务名查询，拿到存活实例列表后自行负载均衡**——地址从「写死」变成「动态发现」，扩缩容与故障摘除自动生效。一句话面试口径：「注册中心解决的是『服务发现』——服务名到实例地址的动态映射，配健康检查实现故障摘除」。

## 2. 部署与版本对齐

Nacos 3.x 部署（Docker，09 篇 K8s 部署的过渡形态）：单机演示用内嵌 Derby 即可，集群或生产必须外置 MySQL（`mysql-schema.sql` 要与 Nacos 版本同版本——3.x 用 3.x 的脚本，混用 2.x 脚本是部署事故）。必须开放的端口：**8848**（HTTP 控制台与配置）、**9848**（gRPC 主端口，Nacos 2.x+ 客户端与服务端的通信走 gRPC，只开 8848 会导致注册失败——这是最高频的部署坑）、**9849**（gRPC 服务端间通信）。生产要开鉴权：`nacos.core.auth.enabled=true` + Token 密钥，默认无鉴权的 Nacos 是内网安全隐患。

版本对齐纪律（承 03 篇）：**服务端与客户端同大版本**——SCA 2025.1.0.0 内置客户端 3.1.1，服务端用 3.x（如 v3.1.1 或更高），配 2.x 服务端无法拉取配置；**客户端版本以 SCA BOM 为准**——不要手动改 nacos-client 版本，BOM 管理的一致性优先。

## 3. 服务注册与发现

接入两步：依赖 `spring-cloud-starter-alibaba-nacos-discovery` + 配置：

```yaml
spring:
  application:
    name: kb-doc            # 服务名：注册发现与 Feign 调用的唯一标识
  cloud:
    nacos:
      discovery:
        server-addr: nacos:8848
```

注册后的机制（面试深挖点）：**心跳续约**——实例每 5s 发心跳，Nacos 15s 未收到标记为不健康、30s 未收到摘除（默认值），调用方通过订阅拿到最新列表；**负载均衡**——Feign 底层 LoadBalancer 从注册列表里选实例（轮询/随机/权重策略，05 篇展开）；**故障摘除**——实例下线（优雅停机或心跳超时）后从列表移除，调用方不再路由到它——03 篇验证实验里「下线一个服务 Feign 自动摘除」就是这条链路。两个工程细节：**注册要在应用真正就绪后发生**（Boot 4 的 readiness 机制默认处理，不要手动提前注册——提前注册会把未就绪的实例暴露给调用方，造成「一启动就报错」）；**服务名全局唯一**——大小写敏感，跨环境用命名空间隔离（见下节）。另有一个保护机制值得了解：**服务保护阈值**——当健康实例比例低于阈值（默认 0.8）时，Nacos 不再摘除不健康实例，而是把所有实例（含不健康）都返回给调用方——这个设计反直觉但合理：**实例大面积不可用时，「少而全」优于「多而空」**，避免「注册中心把实例摘光、调用方无服务可用」的雪崩。

## 4. 配置中心：动态刷新与命名空间

配置中心的动机与注册发现同源：**配置不该在代码与本地文件里**——环境差异（本地/测试/生产连接串不同）、修改成本（改个限流阈值要重新发布）、审计缺失（谁改的、什么时候改的）。Nacos 配置中心把配置外置到服务端，**改配置推送到服务，服务热更新**（`@RefreshScope` 作用域的 Bean 动态重建）。推送机制值得讲透：客户端启动时向服务端发起**长轮询**（连接挂起 30s，配置有变更服务端立即返回，无变更 30s 后重连再挂起）——「改一条配置秒级生效」的实现是长轮询，不是 WebSocket 推送；这个机制决定了配置中心的实时性上限（秒级），也决定了它不适合做「毫秒级开关」——需要毫秒级开关的场景（如流量切换）用其他方案。

接入配置：`spring.config.import: nacos:kb-doc.yml`（SCA 2025 系列唯一方式，bootstrap 已移除）+ `@RefreshScope` 标注需要动态刷新的 Bean。三个实践要点：**命名空间做环境隔离**——dev/test/prod 三个命名空间，同一服务名在各环境注册互不干扰，这是「一套代码多环境」的标准做法；**配置分级**——公共配置（数据源、Redis）进共享 dataId，服务独有配置（端口、限流阈值）进服务自己的 dataId；**敏感配置不进 Nacos 明文**——密码/密钥用环境变量或密钥管理，Nacos 存非敏感配置，与 Level2 09 篇的密钥外置原则一致。

## 5. 一致性模型：AP 与 CP 的取舍

Nacos 的一致性模型是面试高频，两句话讲透：**注册发现是 AP（可用性优先）**——服务实例列表允许短暂不一致（一个实例刚下线，列表里还有它，调用一次失败但重试或摘除后恢复），因为「注册中心挂了服务不能不能用」——AP 保证注册中心部分故障时服务仍可用；**配置是 CP（一致性优先）**——配置变更必须全量生效，「一个节点配了新阈值、另一个还是旧的」会造成行为分裂，CP 保证配置强一致。心智模型：**「发现」可以错一点但不能停，「配置」必须一致不能分叉**——这个区分是架构取舍不是技术细节，面试答出「为什么注册用 AP、配置用 CP」就是深度。

## 6. 验证实验

四个验收实验：**注册实验**——三个服务 + 网关启动后，Nacos 控制台「服务列表」看到全部实例，`curl /nacos/v1/ns/instance/list?serviceName=kb-doc` 返回实例列表；**发现实验**——下线 kb-doc 一个实例（直接 kill 进程），观察控制台心跳超时后实例消失、Feign 调用不再路由到它；**配置实验**——Nacos 里改 `kb-doc.yml` 的限流阈值，观察服务日志「配置刷新」与行为变化（配置热更新生效）；**命名空间实验**——dev/prod 两个命名空间各注册一套，确认互不干扰。四个实验过完，Nacos 支柱验收通过。

## 7. 核心要点

1. 注册中心解决「服务发现」：服务名 → 实例地址动态映射 + 心跳续约 + 故障摘除。
2. 版本对齐：客户端 3.1.1（SCA BOM 管理）配服务端 3.x；9848 gRPC 端口必须开；鉴权必开。
3. 配置中心：spring.config.import 加载（bootstrap 已移除）+ @RefreshScope 热更新 + 命名空间环境隔离。
4. 一致性取舍：注册 AP（可错不可停）、配置 CP（必须一致），这个区分是架构深度的体现。
5. 四个验收实验：注册列表、故障摘除、热更新、命名空间隔离。

> 🎯 **核心要点**：Nacos 双功能的本质是**「把『在哪里』与『怎么配』从代码里抽出来，变成运行时数据」**——服务地址不再写死（发现）、配置不再随代码发布（热更新）、环境隔离不再靠改文件（命名空间）。微服务化的「可运维性」，一半来自这两个能力。
