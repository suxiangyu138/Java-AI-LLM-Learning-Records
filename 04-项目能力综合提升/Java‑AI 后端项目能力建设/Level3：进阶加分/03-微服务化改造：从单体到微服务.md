# 03 微服务化改造：从单体到微服务

> Level3 的核心工程决策：把 Level2 的 `kb-prod` 单体拆成多个服务。微服务是手段不是目的——拆不拆、拆什么、怎么拆，全部由 01 篇的压测数据与业务边界决定。这一篇产出的「拆分决策 + 改造顺序」是面试「为什么微服务化」的标准答案。

## 1. 拆不拆：由数据与边界决定

微服务化的第一课是**「拆不拆」**——拆错了是灾难：服务间网络调用增加延迟、数据一致性变成分布式问题、排查链路翻倍。两个判据：**容量判据**（来自 01 篇）——单机压测拐点 QPS 与业务峰值的关系：拐点远高于峰值（如 5000 vs 500）**不拆**，单体是更简单的正确方案；拐点接近峰值（如 500 vs 1000）才具备「必须横向扩展」的动机。**边界判据**（更本质）——业务能力是否有清晰的独立边界：本项目 `kb-core`（文档/知识库业务）与 `kb-ai`（RAG/AI 调用）边界清晰——AI 的演进（换模型、加 Agent）不应影响文档业务；而 `kb-core` 内部按功能再拆则边界模糊、拆分只有成本没有收益。面试的标准答案：「我拆服务不是因为『微服务是潮流』，而是压测显示文档解析的峰值吞吐已接近单机容量，且 kb-ai 与 kb-core 的业务演进节奏明显不同——**容量 + 边界两个判据都满足才拆**」。

## 2. 服务划分：按业务能力切分

按 Level2 的模块边界演进为三个服务 + 一个网关（模块变服务，改造成本最低）：

| 服务 | 原模块 | 职责 | 独立数据库 |
|---|---|---|---|
| kb-user | —（新增） | 用户与鉴权 | 有（独立演进，Level2 未做，作为演示扩展） |
| kb-doc | kb-core | 文档/知识库/问答记录 CRUD、解析任务消费 | 有（MySQL 独立 schema） |
| kb-ai | kb-ai | RAG 检索、Embedding、LLM 调用、Agent 工具 | 无（只读 kb-doc 数据接口 + Milvus 归属本服务） |

划分的三条原则：**一个服务一个数据主权**——kb-doc 的 MySQL 归 kb-doc、kb-ai 的 Milvus 归 kb-ai，其他服务只能通过接口访问，**数据库不跨服务共享**是微服务的红线（共享库 = 伪微服务，耦合没拆掉只是换了层皮）；**依赖单向**——kb-ai 调 kb-doc 的接口，kb-doc 不反向依赖（与 Level2 模块依赖方向一致，拆出来的服务依赖图是原来的模块依赖图）；**网关只做路由与鉴权**——`kb-gateway`（Spring Cloud Gateway 5.0.2）统一入口，业务逻辑不进网关。服务间通信统一走 OpenFeign（04-05 篇），跨服务事务与数据一致性是 07 篇的主题。

## 3. 技术栈矩阵：SCA 2025.1.0.0

微服务化不是自建轮子，用 Spring Cloud Alibaba 全家桶（2026-08 基准，仓库各体系有完整原理深潜）：

| 组件 | 选型 | 版本 | 职责 |
|---|---|---|---|
| 注册/配置中心 | Nacos | 3.x 服务端（客户端 3.1.1） | 服务注册发现 + 配置动态刷新 |
| 服务调用 | OpenFeign | 5.0.2（SC 2025.1） | 声明式 HTTP 调用 |
| 负载均衡 | Spring Cloud LoadBalancer | 5.0.2 | Feign 底层路由（Ribbon 继任者） |
| 流量治理 | Sentinel | 1.8.9（SCA 2025.1.0.0） | 限流熔断降级（替代 Level2 的 Resilience4j） |
| 网关 | Spring Cloud Gateway | 5.0.2 | 统一入口、路由、鉴权 |
| 分布式事务 | Seata | 2.6.x（SCA 2025.1.0.0） | 跨服务事务（07 篇） |

版本纪律三条：**SCA 与 Spring Cloud/Boot 版本矩阵对齐**——SCA 2025.1.0.0 配 Boot 4.x + Spring Cloud 2025.1.x，混配会出兼容性事故；**Nacos 客户端与服务端同大版本**——SCA 2025.1.0.0 内置客户端 3.1.1，服务端必须 3.x，2.x 服务端将无法获取配置（官方 Issue #4098 明确）；**配置加载用 `spring.config.import`**——SCA 2025 系列已移除 bootstrap 配置方式，这是老教程失效的高频坑。

## 4. 改造顺序与风险控制

微服务化最大风险是「一步到位」——一次把单体拆完上线，出问题无法定位是哪个服务。正确姿势是**绞杀者模式（Strangler Pattern）**：按依赖顺序逐个抽离，每抽一个服务就独立部署、独立验证、全链路回归：

1. **先加网关**：接入 kb-gateway，路由全部打到单体（行为不变，先建立统一入口）；
2. **抽 kb-ai**：AI 调用独立成服务（与核心业务耦合最浅），Nacos 注册 + Feign 从单体调用；
3. **抽 kb-doc**：核心业务独立（解析任务消费者一并迁移），跨服务调用改为 Feign；
4. **加 kb-user 与鉴权**：网关层统一鉴权（JWT），服务间内部调用带身份传递；
5. **验证与收尾**：全链路回归（上传 → 解析 → 问答）+ 01 篇的 perf-check 回归（防性能回退）。

每一步的验收：**单服务可独立重启**（不拖垮其他服务）、**Nacos 注册列表正确**、**全链路压测不劣化**。风险控制三件套：**每步可回滚**（保留单体可运行版本，出问题回退不是耻辱是工程）；**数据不动**（拆服务期间数据库 schema 不动，动数据是拆服务阶段最大的风险源——库表结构变更与拆服务同时发生，出问题无法归因）；**监控先行**（Level2 08 篇的指标面板在改造期间持续看——服务化引入的网络延迟与连接管理问题会第一时间暴露在面板上）。

改造的另一个高频坑是**「拆了服务没拆团队心智」**——代码拆开了，但开发者还是按单体思维改代码：跨服务调用被写成「先调 A 接口再直接查 B 的库」——**绕过服务接口直查对方数据库是拆服务后第一件禁止的事**（数据主权红线），评审时抓到这类代码要当场改回接口调用。这个坑写进改造的 code review 清单，比事后补规范有效。

## 5. 单体的遗留：哪些不拆

克制与边界：**kb-common 不拆成服务**——通用工具与统一响应体以依赖库形式保留（每个服务依赖它），拆成「common 服务」是分布式反模式（所有服务调它 = 单点 + 网络延迟）；**Milvus 不重复部署**——kb-ai 独占即可，多服务共享向量库会引入索引竞争；**RabbitMQ/Redis/MySQL 不服务化**——中间件本来就是独立的，服务化的是业务代码不是基础设施。**「哪些不拆」与「哪些拆」同样体现架构判断力**——面试追问「为什么 common 不拆」时，这套答案就是区分度。

## 6. 验证实验

三个验收实验：**拆分实验**——按绞杀者顺序完成 kb-ai、kb-doc 独立部署，演示「kb-ai 重启不影响 kb-doc 提供文档接口」；**注册实验**——Nacos 控制台截图：三个服务注册成功、下线一个服务后 Feign 自动摘除不报错（负载均衡的健康摘除）；**回归实验**——全链路（上传 → 解析 → 问答）跑通 + perf-check 对比拆分前后：记录 P95 差异（预期微升 < 15%，服务间网络开销是拆分的成本，数据要诚实记录），这个「拆分的代价」数据在面试里反而是加分项——**知道成本还能决定拆，才是真决策**。

## 7. 核心要点

1. 拆不拆由两个判据决定：容量判据（压测拐点 vs 峰值）+ 边界判据（业务演进节奏不同）——都满足才拆。
2. 服务划分三原则：一服务一数据主权（库不共享）、依赖单向、网关只做路由鉴权。
3. 版本矩阵对齐：SCA 2025.1.0.0 + Boot 4.x + SC 2025.1.x + Nacos 3.x 同大版本；配置用 spring.config.import。
4. 绞杀者模式：网关先行 → 浅耦合先抽 → 每步独立部署验证可回滚，数据 schema 拆分期间不动。
5. 克制：common 不服务化、Milvus 不重复部署、中间件不服务化——不拆清单体现判断力。
6. 拆分成本诚实记录（P95 微升），回归压测防性能回退。

> 🎯 **核心要点**：微服务化的本质是**「用架构复杂度换取扩展性与演进独立性」**——这比「把单体拆开」难得多：拆错了是负资产，拆对了是架构能力。判断标准只有一个：**拆完后每个服务能独立演进、独立扩缩容，且成本（延迟、一致性、排查）是可控的**——本层后续 04-08 篇就是在为这个「可控」补全组件。
