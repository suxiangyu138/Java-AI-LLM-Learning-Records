# 01 高并发压测与瓶颈定位

> Level3 的第一块地基：用压测数据回答「项目能不能扛住并发、瓶颈在哪里」。压测不是「跑出个数字」，而是「归因」——把延迟从哪一层来、CPU/内存/连接/IO 哪个先到极限查清楚，优化才有方向。这一篇的方法论决定后续所有优化专项的价值。

## 1. 动机：为什么先压测再优化

Level2 已有一份性能基线（docs/perf.md：问答 P95 首字 < 3s、上传 P95 < 500ms）。Level3 的第一个动作是**把它做深**——从「整体延迟达标」升级为「知道每一层的耗时构成」：一次问答的 2 秒里，检索占多少、LLM 首 token 占多少、序列化占多少？不加压时系统满负荷跑起来，哪个组件先撑不住？两个理由：**优化的前提是归因**——不压测就优化是猜，猜中的概率不高，且「优化了 A 结果瓶颈在 B」是最常见的无效工作；**微服务化的前提是数据**——拆不拆服务、拆什么，取决于压测发现的瓶颈是不是「单机结构造成的」（01 篇的结论直接决定 03 篇的拆分决策）。面试口径也依赖这份数据：「我压测发现 MySQL 连接池先到瓶颈，QPS 500 时池耗尽、P95 从 80ms 飙到 2s」——有归因的性能讲述才有说服力。

## 2. 压测方法论：场景、工具与纪律

三个场景对应三条链路，分别压：**问答接口**（核心链路：RAG + AI，关注 P95 首字延迟与成功率——AI 打桩，见 Level2 07 篇，避免烧钱与 provider 抖动干扰）；**上传接口**（异步链路：落库 + 发 MQ，关注响应延迟与 MQ 堆积曲线）；**缓存命中场景**（缓存链路：命中 vs miss 延迟对比，验证缓存收益）。工具：JMeter（图形化、适合演示）与 wrk（命令行、高并发稳定）二选一，本项目 JMeter 为主——压测结果要能截图进面试材料。

纪律四条：**环境固定**——每轮压测记录机器配置、JVM 参数、并发数、数据量（千万条数据的压测结果不可比）；**从低到高打**——并发 50 → 100 → 200 → 400 逐级加压，记录每级的 P95 与错误率，找到「拐点」（P95 开始飙升的并发数），拐点就是系统的真实容量；**单变量**——一次只改一个变量（并发数或参数），否则结果无法归因；**压测不是一次性的**——每次优化前后各跑一遍同场景，前后对比是唯一的验收方式。

## 3. 瓶颈四查：连接池、数据库、MQ、AI

压测发现 P95 飙升后，按四查顺序归因（顺序即概率从高到低）：**第一查连接池**——`HikariCP` 的 `active` 连接数与 `pool size` 对比，池打满的典型特征：P95 突增且线程池排队日志出现，伴随 `Connection is not available, request timed out` 异常——这是单体项目最高频的瓶颈（每个接口都吃连接，异步任务还抢池）；**第二查数据库**——`SHOW PROCESSLIST` 看慢查询与锁等待，`EXPLAIN` 看执行计划，慢 SQL 的特征是 P95 随数据量线性增长；**第三查 MQ**——上传接口延迟正常但文档「解析中」状态长时间不更新，查队列深度（RabbitMQ 管理台/指标），堆积意味着消费者慢于生产者；**第四查 AI**——问答接口 P95 高且连接池正常，测 AI 调用本身的耗时（Level2 08 篇的 AI 指标里就有调用耗时与成功率）——provider 高峰期限流（DeepSeek V4 2026-07 起峰谷定价、高峰吞吐下降）是外部因素，属于「降级处理」而非「代码优化」。

归因的排障工具链（复用 Level2 08 篇）：**Arthas**（生产诊断三件套：`dashboard` 看线程与内存、`trace` 看方法耗时、`watch` 看参数返回值）；**JFR**（JDK 自带，飞行记录看 GC 与锁竞争）；**Grafana 面板**（四类指标曲线与压测时间轴对齐）。归因的终点是一句话：**「瓶颈在 X，特征数据是 Y」**——写进压测报告，而不是「系统变慢了」。

四查还有一个容易被忽视的维度：**数据量对瓶颈的放大**——同一 SQL 在 1 万条数据时 5ms、100 万条时 500ms，压测必须在「接近真实的数据量」下进行（演示库数据量小会让慢 SQL 藏起来）；同理缓存命中率与数据分布强相关（热点集中的场景缓存收益大）。**「压测环境的数据量与生产差异」是所有压测结论的第一前提**——写压测报告时先声明数据规模，面试讲性能数据时主动带上这个前提，比被追问时承认要专业得多。

## 4. 优化优先级：先算收益再动手

瓶颈定位后，按「收益/成本」排序优化，三个原则：**先改配置后改代码**——连接池参数、JVM 堆、线程池参数是零成本改动，先调参再写代码（调参解决 60% 的连接池类瓶颈）；**先改热点后改全量**——压测数据会暴露热点接口（问答占了 70% 的流量），优化热点接口的收益是优化冷门接口的十倍；**缓存优先于扩容**——加缓存（02 篇多级缓存）是「降本」的优化，扩容是「花钱」的优化，先降本后花钱。每个优化的验收都是同一句话：**前后对比的 P95/吞吐/连接数曲线**——「QPS 500 时 P95 从 2s 降到 300ms」比「我优化了性能」有说服力一百倍。

## 5. 性能基线与回归机制

压测产出三样东西，缺一不可：**基线文档升级**——docs/perf.md 增加「各层耗时构成」表（检索/LLM/序列化占比）与「瓶颈归因」记录（每个瓶颈：特征数据、根因、优化方案、前后对比）；**回归机制**——把「问答接口压测脚本」做成可重复执行的检查项（`scripts/perf-check.sh`），每次微服务改造（03-08 篇）前后跑一遍，防止改造引入性能回退——**微服务化的最大风险是性能回退**（服务间网络调用增加延迟），回归机制是改造的安全网；**容量预估**——按「拐点并发 × 平均请求量」推算单机容量，这是 03 篇「要不要拆服务」的关键输入：单机 QPS 500 且业务量 1000 时拆；单机 QPS 5000 且业务量 500 时**不需要拆**——拆服务是有成本的，数据证明需要才拆。

## 6. 验证实验

三个验收实验：**基线实验**——按方法论重压三个场景，产出完整的耗时构成表与瓶颈归因（至少定位一个真实瓶颈，记录特征数据）；**调参实验**——对定位的瓶颈做至少一轮调参优化（如 HikariCP `maximum-pool-size` 从 10 调到 50、JVM 堆大小调整），记录前后对比；**回归验证**——跑通 `perf-check.sh`，确认「同一场景、同参数」压测可重复、结果稳定（波动 < 20%）。三个实验完成，01 篇毕业——带着「瓶颈清单 + 基线数据」进入 02 篇的优化实战。

## 7. 核心要点

1. 优化的前提是归因：压测 → 定位瓶颈（特征数据）→ 优化 → 前后对比，猜出来的优化是无效工作。
2. 三场景三链路：问答（AI 打桩）、上传（MQ 堆积曲线）、缓存（命中 vs miss）。
3. 瓶颈四查按概率排序：连接池 → 数据库 → MQ → AI 外部因素，工具链用 Arthas/JFR/面板。
4. 优化排序：先配置后代码、先热点后全量、缓存优先于扩容。
5. 压测产出三件套：基线文档、可重复的回归脚本、容量预估——容量预估直接决定 03 篇拆不拆服务。
6. 微服务化的最大风险是性能回退，改造前后必跑回归压测。

> 🎯 **核心要点**：压测的本质是**「给系统照 X 光」**——不加压时一切正常，加压后哪一层先撑不住一目了然。Level3 所有进阶（多级缓存、虚拟线程、拆服务、上 K8s）的动机都要从这里的数据出发，否则就是「为了进阶而进阶」。
