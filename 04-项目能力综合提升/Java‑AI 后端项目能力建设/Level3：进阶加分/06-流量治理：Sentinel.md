# 06 流量治理：Sentinel

## 1. 为什么从 Resilience4j 升级到 Sentinel

Level2 06 篇选了 Resilience4j（单体够用），微服务化后三个新需求让它不够用：**分布式视角**——单体限流在「本进程内」计数，微服务化后 kb-doc 有 3 个实例，每实例限流 100 意味着集群能扛 300——**集群维度的流量控制（如对某用户全局限流）需要分布式计数**（Sentinel 集群流控模式）；**可视化治理**——微服务 4 个服务、几十个接口，规则散落在每个服务的配置文件里，改一条规则要改代码重发布——Sentinel 控制台提供「运行中改规则 + 实时监控」；**生态集成**——Sentinel 与 SCA 全家桶（Feign/网关）官方集成，Feign 熔断一行配置。升级的取舍也讲清：Sentinel 引入控制台与持久化组件（部署成本），对「演示 + 面试」场景收益明确——**「我单体用 Resilience4j、微服务化升级到 Sentinel，因为需要集群限流与可视化规则管理」是一句完整的选型演进答案**（仓库 Sentinel 体系有原理深潜）。

## 2. 核心模型：资源、规则与 Slot 链

Sentinel 的两个抽象：**资源**——「被保护的对象」（一个接口、一个方法、一段代码），用 `SphU.entry("资源名")` 或注解 `@SentinelResource("资源名")` 声明；**规则**——对资源的保护策略（限流/熔断/降级/热点），规则独立于资源定义。**规则与资源分离**是 Sentinel 的设计精髓：业务代码只声明「我要保护什么」，治理策略（限流阈值等）运行时调整——这就是「可视化治理」的基础。规则数据模型三要素：`resource`（资源名）、`grade`（阈值类型）、`count`（阈值）；链路模型：资源进入后过 **Slot 链**（责任链：限流 → 熔断 → 系统保护等各司其职），每个 Slot 是一个治理维度，理解「资源过链」比背 API 重要。

## 3. 限流：三种阈值与热点参数

限流规则按阈值类型（grade）分三种，覆盖不同场景：**QPS 阈值**——接口级流控（如 kb-doc 的问答接口 200 QPS），防突发打爆；**线程数阈值**——并发控制（如 kb-ai 的 LLM 调用同时最多 10 个），防线程堆积拖垮服务——**线程数限流是最贴近「资源保护」的阈值**，比 QPS 更直接；**关联限流**——资源 A 与资源 B 的联动（如写接口触发的读接口降级）。限流模式有直接/关联/链路三种，本项目用到前两种：**直接**——对资源本身限流（接口 QPS）；**关联**——A 资源的流量触发时限制 B（如「写入接口高频时限制读取接口」，保护数据库写路径不被读流量挤占）。关联限流的场景判断：**两个资源共享同一个下游瓶颈**（都打同一张表、同一连接池）时，对「非核心资源」限流保护「核心资源」——面试讲关联限流时，能说出「共享瓶颈」这个触发条件比背概念更有说服力。

热点参数限流是面试亮点：**同一接口不同参数不同阈值**——「按用户限流」比「接口级限流」精细得多：普通用户 20 QPS、VIP 用户 100 QPS，`@SentinelResource` + 热点规则按参数值（userId）单独计数。Level2 06 篇的「接口层按用户限流」用 Redis + Lua 手写，Sentinel 的热点参数限流是它的框架化升级——**同一个需求、从手写到框架**的演进叙事是面试的好素材。控制台实操：实时监控页看每个资源的 QPS 曲线，点「新增流控规则」改阈值，**5 秒生效**——「运行中调整」就是可视化治理的直观演示。

## 4. 熔断降级与 Feign 集成

熔断降级的机制与 Level2 06 篇一致（状态机 CLOSED → OPEN → HALF_OPEN），Sentinel 的两个差异化点：**降级规则的类型更细**——慢调用比例（P95 超阈值比例 > X% 熔断）、异常比例、异常数三种策略可选，比 Resilience4j 的「失败率」更贴近真实故障模式（慢服务是微服务故障的第一形态，慢调用比例规则直接命中）；**与 Feign 官方集成**——`feign.sentinel.enabled=true` + `@FeignClient(fallback = XxxFallback.class)` 声明降级类，服务调用失败（超时/熔断）自动走 fallback 逻辑（返回兜底数据或抛统一错误）——**Feign 的 fallback 是 Level2 06 篇 AiGateway 降级的分布式形态**：单体里降级在一个出口，微服务里降级在每个 Feign 客户端的 fallback。降级链路的心智不变：**用户永远拿到「可用」的响应，服务故障只是质量降级**。

## 5. 规则持久化与系统保护

两个工程细节决定 Sentinel 能否用于生产：**规则持久化**——控制台改的规则默认存在内存里，**重启即失**（控制台是「临时改」，不是「持久配置」）；生产落地用「规则推模式」：规则存 Nacos（配置中心），Sentinel 监听 Nacos 变更实时加载——**规则配置化 + 配置中心化**是微服务治理的完整形态（规则文件进 Nacos 的命名空间，与 04 篇的配置管理统一）；**系统保护规则**——Sentinel 的差异化能力：不针对单个资源，而是按系统维度（入口 QPS、CPU 使用率、平均 RT）自适应限流——「CPU 超过 70% 自动降级入口流量」——这是**「保护系统不被自己压垮」的最后一道闸**，比资源级规则更根本（资源级规则是「防单点被压垮」，系统保护是「防整体被打挂」，两道闸缺一不可）。验证姿势：压测时打开系统保护规则，观察 CPU 超阈值后入口流量被自动削平——「系统保护」是面试「Sentinel 有什么独特能力」的标准答案。

## 6. 验证实验

四个验收实验：**限流实验**——JMeter 压 kb-doc 问答接口超过 QPS 阈值，观察超过阈值的请求被拒绝（返回统一限流响应），控制台 QPS 曲线平顶；**热点实验**——两个用户不同阈值（20 vs 100 QPS），确认热点参数规则按用户生效；**熔断实验**——人为让 kb-doc 的一个接口变慢（sleep），观察慢调用比例规则触发熔断、Feign fallback 生效返回兜底；**持久化实验**——规则写入 Nacos 后重启服务，确认规则加载不丢；**系统保护实验**——压测观察 CPU 保护生效。五个实验是「流量治理可用」的完整证据。

## 7. 核心要点

1. 升级动因：集群维度限流（分布式计数）+ 可视化治理 + SCA 生态集成——单体用 Resilience4j 的演进答案。
2. 资源与规则分离：业务声明「保护什么」，治理策略运行时调整——可视化治理的基础。
3. 三种阈值（QPS/线程数/关联）+ 热点参数限流（按用户分阈值）——从手写 Redis+Lua 到框架化。
4. 降级规则按「慢调用比例/异常比例/异常数」三种，Feign fallback 是降级的分布式形态。
5. 规则持久化进 Nacos（控制台改规则内存态重启即失），系统保护是「防自压垮」的最后一闸。
6. 五个验证实验：限流平顶、热点分档、熔断 fallback、持久化、CPU 系统保护。

> 🎯 **核心要点**：Sentinel 的价值是**「把流量治理从『写在代码里的规则』变成『运行时可调整的配置』」**——资源声明与规则分离，让治理动作（限流/熔断/降级）不需要发布代码就能完成；规则进 Nacos 让治理具备版本与审计。微服务化的「可治理性」，到这里才真正闭环。
