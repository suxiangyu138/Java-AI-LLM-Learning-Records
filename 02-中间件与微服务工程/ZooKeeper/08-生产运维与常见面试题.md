## 1. 关键参数调优

```properties
# zoo.cfg 生产配置
tickTime=2000
initLimit=10              # 初始同步：20s
syncLimit=5               # 同步超时：10s
dataDir=/data/zookeeper/snapshot
dataLogDir=/data/zookeeper/translog     # ⭐ 独立磁盘（随机写 vs 顺序写分离）
maxClientCnxns=60
autopurge.snapRetainCount=3
autopurge.purgeInterval=1
```

### JVM 参数

```bash
# zkEnv.sh
export JVMFLAGS="-Xms4g -Xmx4g \
  -XX:+UseG1GC \
  -XX:MaxGCPauseMillis=50 \
  -verbose:gc -Xlog:gc*:file=/var/log/zookeeper/gc.log:time"
```

| 参数 | 说明 |
|------|------|
| `dataLogDir` 独立磁盘 | 事务日志是顺序写；快照是随机写。同盘会互相干扰 |
| `autopurge` | 自动清理旧快照（不要让快照无限累积占满磁盘） |
| G1 GC | ZK 对延迟敏感，G1 比 CMS 更适合 |

## 2. 监控指标

### 四字命令

```bash
echo mntr | nc localhost 2181
```

| 指标 | 含义 | 告警阈值 |
|------|------|:---:|
| `zk_server_state` | 角色：leader/follower | follower ≠ leader 必告警 |
| `zk_outstanding_requests` | 排队请求数 | > 50 |
| `zk_avg_latency` | 平均延迟（ms） | > 100 |
| `zk_max_latency` | 最大延迟（ms） | > 1000 |
| `zk_num_alive_connections` | 活跃连接数 | 接近 maxClientCnxns |
| `zk_znode_count` | ZNode 总数 | 持续增长需检查 |
| `zk_watch_count` | Watch 数量 | > 10000 |
| `zk_open_file_descriptor_count` | 文件句柄数 | 接近 ulimit |
| `zk_synced_followers` | 已同步 Follower 数 | < 集群数/2（可能脑裂） |

### JMX 暴露

```bash
# 启动参数开启 JMX
-Dcom.sun.management.jmxremote.port=9995
-Dcom.sun.management.jmxremote.ssl=false
-Dcom.sun.management.jmxremote.authenticate=false
```

### Prometheus JMX Exporter

```bash
# ZK 3.6+ 内置 Prometheus Metrics
curl http://localhost:7000/metrics
```

## 3. 快照与日志管理

```bash
# ⚠️ 快照不清理会一直累积占满磁盘！

# 手动清理
zkCleanup.sh -n 3          # 保留最近 3 个快照

# 自动清理
# zoo.cfg:
autopurge.snapRetainCount=3
autopurge.purgeInterval=1   # 每小时清理一次

# 查看快照文件
java -cp zookeeper.jar:lib/* org.apache.zookeeper.server.SnapshotFormatter snapshot.xxx
```

## 4. 扩容方案

```text
3 台 → 5 台 扩容步骤：

1. 修改新节点的 zoo.cfg（添加所有 server.x 配置）
2. 新节点设置正确的 myid
3. 修改老节点的 zoo.cfg（添加新 server.x 配置）
4. 重启 Leader（最后重启）
5. 验证集群状态：echo stat | nc localhost 2181

⚠️ 注意：
  → 扩容期间集群仍可用（过半存活原则）
  → 优先重启 Follower，最后重启 Leader
  → 不要一次性重启所有节点
```

## 5. 20 道高频面试题

### Q1：ZooKeeper 是如何保证一致性的？

> ZAB 协议：写请求统一由 Leader 处理 → 生成 Proposal → 广播给所有 Follower → 过半 ACK → Commit。保证所有节点按相同顺序应用事务。

### Q2：ZooKeeper 是强一致性吗？

> 严格说是**顺序一致性**（Sequential Consistency）。写操作按全局顺序执行；读操作可能读到旧数据（Leader 已 Commit 但 Follower 未同步完）。要保证读最新数据，用 `sync()` 方法。

### Q3：ZK 集群为什么要是奇数台？

> 过半存活原则：3 台允许 1 台挂、5 台允许 2 台挂。4 台（允许 1 台挂）和 3 台容错能力相同，浪费一台。奇数台性价比最高。

### Q4：临时节点和持久节点的区别？

> 持久节点：显式删除才消失，用于配置数据。临时节点：客户端 Session 断开自动删除，用于服务注册、分布式锁。临时节点不能有子节点。

### Q5：ZK 的 Watch 机制有什么缺点？

> 一次性触发（触发后需重新注册）；批量通知（一个 ZNode 的所有 Watch 同时被触发）；不是实时推送（异步通知，有延迟）。

### Q6：ZK 的 Session 过期后会发生什么？

> 该 Session 创建的所有**临时节点被删除**，所有 Watch 失效。客户端需要**创建新的 ZK 连接**（`new ZooKeeper(...)`），不能用旧连接。

### Q7：如何用 ZK 实现分布式锁？

> 所有线程在 `/lock` 下创建临时顺序节点 → 序号最小的获得锁 → 其他线程 Watch 前驱 → 前驱释放后自己被通知 → 获得锁。Curator `InterProcessMutex` 封装了这一切。

### Q8：什么是羊群效应？如何避免？

> 所有客户端 Watch 同一个节点导致同时被唤醒。解决：Watch 前驱节点，只有前驱释放时才自己被唤醒。每个节点只唤醒一个等待者。

### Q9：ZooKeeper 和 etcd 的区别？

> ZK：Java、ZAB协议、顺序一致性、Watch一次性、树形存储。etcd：Go、Raft、强一致性、Watch流式持续、KV存储。etcd 是 K8s 后端存储，新项目微服务推荐 etcd/Nacos。

### Q10：ZK 集群扩容后数据会自动均衡吗？

> 不会！ZK 不提供自动数据再平衡，老数据留在原节点。新写入的数据也不保证均衡分布。ZK 不是分布式存储，是协调服务。

> 🎯 面试重点：ZAB 协议、临时顺序节点、Watch 机制、过半存活、Session 过期处理。掌握这 5 点，ZK 面试基本通杀。
