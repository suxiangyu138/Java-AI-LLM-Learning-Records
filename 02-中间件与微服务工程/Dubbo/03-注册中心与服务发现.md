## 1. 注册中心的作用

```
没有注册中心 → 硬编码 Provider 地址（死板）

有了注册中心：
  Provider → 启动 → 向注册中心注册「我是 user-service，IP=10.0.1.10:20880」
  Consumer → 启动 → 向注册中心订阅「谁提供 user-service？」
  Registry → 推送 Provider 地址列表 + 变更通知
```

| 功能 | 说明 |
|------|------|
| **服务注册** | Provider 启动后将自己的地址写入注册中心 |
| **服务发现** | Consumer 从注册中心获取 Provider 列表 |
| **动态感知** | Provider 宕机/扩容时实时推送变更 |
| **健康检查** | 注册中心检测 Provider 存活性 |

## 2. 支持的注册中心对比

| 注册中心 | CAP | 成熟度 | 推荐场景 |
|----------|:---:|:---:|------|
| **ZooKeeper** | CP | ⭐⭐⭐ | 传统 Dubbo 项目，成熟稳定 |
| **Nacos** | AP/CP 可切换 | ⭐⭐⭐ | ⭐ 阿里生态，注册+配置一体 |
| **Redis** | AP | ⭐⭐ | 轻量场景 |
| **Consul** | CP | ⭐⭐ | HashiCorp 生态 |
| **etcd** | CP | ⭐ | K8s 环境 |

## 3. ZooKeeper 注册中心原理

### 3.1 目录结构（Dubbo 2.x 接口级）

```
/dubbo
  └── /com.example.UserService
      ├── /providers
      │   ├── dubbo://10.0.1.10:20880/com.example.UserService?...  (临时节点)
      │   └── dubbo://10.0.1.11:20880/com.example.UserService?...  (临时节点)
      └── /consumers
          ├── consumer://10.0.2.10/com.example.UserService?...  (临时节点)
          └── consumer://10.0.2.11/com.example.UserService?...
```

| 节点类型 | 作用 |
|----------|------|
| `/dubbo/{interface}/providers` | 服务提供者 URL 列表 |
| `/dubbo/{interface}/consumers` | 服务消费者 URL 列表 |
| `/dubbo/{interface}/configurators` | 动态配置覆盖规则 |

### 3.2 临时节点机制

```text
Provider 启动 → 在 ZK 创建临时节点
Provider 宕机 → Session 断开 → ZK 自动删除临时节点
Consumer Watch → ZK 通知 Consumer 更新 Provider 列表

优点：宕机自动摘除，无需额外健康检查
```

## 4. Nacos 注册中心详解

### 4.1 Nacos vs ZooKeeper

| 维度 | Nacos | ZooKeeper |
|------|-------|-----------|
| 一致性 | AP/CP 可切换 | CP |
| 健康检查 | TCP + HTTP + MySQL | Session 心跳 |
| 配置中心 | ✅ 内置 | ❌ 需另搭 |
| 控制台 | ✅ 完善 | ❌ 需另装 |
| 与 Spring Cloud | ⭐ 无缝集成 | 需适配 |
| 推荐度 | ⭐⭐⭐ Dubbo 3.x 首选 | ⭐⭐ 经典方案 |

### 4.2 Nacos 配置

```yaml
dubbo:
  registry:
    address: nacos://127.0.0.1:8848
    parameters:
      namespace: prod                    # 命名空间隔离
      group: DUBBO_GROUP
```

```properties
# Nacos 命名空间设计
public:    # 公共命名空间
  ├── DUBBO_GROUP    # Dubbo 服务分组
  │   ├── user-provider
  │   └── order-provider
  └── CONFIG_GROUP   # 配置文件分组
```

## 5. Dubbo 3.x 应用级服务发现

> ⚠️ **Dubbo 3.x 的核心变更**：从接口级服务发现升级为应用级服务发现。

### 5.1 为什么需要应用级发现

```
接口级（Dubbo 2.x）：
  注册粒度 = 接口
  → 100 个接口 × 100 个 Provider = 10000 个 URL 存在 ZK
  → ZK 压力大、推送慢、内存占用高

应用级（Dubbo 3.x）：
  注册粒度 = 应用
  → 100 个应用 × 100 个 Provider = 100 个 URL
  → 注册中心压力降低 100 倍！
```

### 5.2 两种模式的对比

| 维度 | 接口级 | 应用级 |
|------|--------|--------|
| 注册中心存储 | `/dubbo/{interface}/providers` | `/dubbo/{application}/instances` |
| 注册数量 | 接口数 × 实例数 | 应用数 × 实例数 |
| 元数据 | 内嵌在 URL 中 | 存储到元数据中心 |
| 兼容性 | Dubbo 2.x | Dubbo 3.x（推荐） |
| 与 Spring Cloud 互通 | ❌ | ✅ 模型统一 |

### 5.3 配置

```yaml
dubbo:
  application:
    name: user-provider
    register-mode: instance    # instance(应用级) / interface(接口级) / all(双注册，迁移过渡)
  registry:
    address: nacos://127.0.0.1:8848
```

## 6. 元数据中心

> 💡 Dubbo 3.x 中，接口定义从 URL 中剥离，存储到元数据中心。

```
元数据中心存储的内容：
  ├── 接口定义（方法签名、参数类型）
  ├── 服务参数（超时、重试次数等配置）
  └── 应用信息

支持的元数据中心：
  ├── Nacos（推荐）
  ├── ZooKeeper
  └── Redis
```

```yaml
dubbo:
  metadata-report:
    address: nacos://127.0.0.1:8848
```

> 🎯 **Dubbo 3.x 最佳实践**：注册中心用 Nacos、开启应用级发现（`register-mode: instance`）、元数据中心也指向 Nacos。这是阿里推荐的"三位一体"配置。
