## 1. 可观测性三大支柱

### 1.1 三大支柱

```
                ┌──────────────────────┐
                │    可观测性三大支柱     │
                └──────────────────────┘
                         │
        ┌───────────────┼───────────────────┐
        ▼               ▼                   ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────────┐
│    Logs     │ │   Metrics   │ │     Traces       │
│   日志       │ │   指标       │ │     追踪          │
│             │ │             │ │                  │
│ "发生了错误" │ │ "错误率 5%"│ │ "请求经过的服务链" │
│ "用户登录成功"│ │ "QPS 1000" │ │ "span A → span B" │
│             │ │ "P99 200ms" │ │ "耗时主要在 DB"   │
└──────────────┘ └──────────────┘ └──────────────────┘
     │                 │                  │
     ▼                 ▼                  ▼
  ELK/Loki        Prometheus          Jaeger/Zipkin
  (集中存储)      (时序数据库)         (追踪存储)
```

**三大支柱的关系：**
- **Logs**：告诉你"发生了什么"，事件驱动
- **Metrics**：告诉你"系统状态"，聚合数据
- **Traces**：告诉你"请求路径"，端到端

### 1.2 为什么需要三者

| 场景 | 只用 Logs | 只用 Metrics | 只用 Traces |
|------|-----------|-------------|-------------|
| 高延迟 | 需要逐行查日志 | 看见 P99 升高 | 看到慢的 span |
| 错误排查 | 看到具体错误 | 看到错误率上升 | 看到失败链路 |
| 容量规划 | 不行 | 看到趋势 | 不行 |
| 分布式问题 | 需要手动关联 | 无法追踪 | 完美解决 |

## 2. 日志体系

### 2.1 SLF4J + Logback

SLF4J 是日志门面（Facade），Logback 是具体实现。

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <!-- Spring Boot 已经集成了 SLF4J + Logback -->
</dependency>
```

```java
// 使用 SLF4J (不在代码中直接依赖 Logback)
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

@Service
public class UserService {
    private static final Logger log = LoggerFactory.getLogger(UserService.class);

    public User createUser(CreateUserRequest request) {
        log.info("Creating user: {}", request.getUsername());
        try {
            User user = saveUser(request);
            log.info("User created successfully: id={}, username={}",
                user.getId(), user.getUsername());
            return user;
        } catch (DataAccessException e) {
            log.error("Failed to create user: username={}, error={}",
                request.getUsername(), e.getMessage(), e);
            throw e;
        }
    }
}
```

### 2.2 Logback 配置详解

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!-- src/main/resources/logback-spring.xml -->
<configuration scan="true" scanPeriod="30 seconds">

    <!-- 1. 属性定义 -->
    <springProperty scope="context" name="appName" source="spring.application.name"
        defaultValue="unknown-app"/>
    <springProperty scope="context" name="activeProfile" source="spring.profiles.active"
        defaultValue="dev"/>

    <property name="LOG_PATH" value="${LOG_PATH:-./logs}"/>
    <property name="LOG_PATTERN"
        value="%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{traceId}] - %msg%n"/>
    <property name="MAX_FILE_SIZE" value="100MB"/>
    <property name="MAX_HISTORY" value="30"/>
    <property name="TOTAL_SIZE_CAP" value="3GB"/>

    <!-- 2. Appender: 控制台 -->
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} %highlight(%-5level) [%cyan(%thread)] %yellow(%logger{36}) - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 3. Appender: 滚动文件 (INFO) -->
    <appender name="FILE-INFO" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_PATH}/info.log</file>
        <filter class="ch.qos.logback.classic.filter.ThresholdFilter">
            <level>INFO</level>
        </filter>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>${LOG_PATH}/info-%d{yyyy-MM-dd}.%i.log</fileNamePattern>
            <timeBasedFileNamingAndTriggeringPolicy
                class="ch.qos.logback.core.rolling.SizeAndTimeBasedFNATP">
                <maxFileSize>${MAX_FILE_SIZE}</maxFileSize>
            </timeBasedFileNamingAndTriggeringPolicy>
            <maxHistory>${MAX_HISTORY}</maxHistory>
            <totalSizeCap>${TOTAL_SIZE_CAP}</totalSizeCap>
        </rollingPolicy>
        <encoder>
            <pattern>${LOG_PATTERN}</pattern>
        </encoder>
    </appender>

    <!-- 4. Appender: 错误日志单独输出 -->
    <appender name="FILE-ERROR" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_PATH}/error.log</file>
        <filter class="ch.qos.logback.classic.filter.LevelFilter">
            <level>ERROR</level>
            <onMatch>ACCEPT</onMatch>
            <onMismatch>DENY</onMismatch>
        </filter>
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <fileNamePattern>${LOG_PATH}/error-%d{yyyy-MM-dd}.%i.log</fileNamePattern>
            <timeBasedFileNamingAndTriggeringPolicy
                class="ch.qos.logback.core.rolling.SizeAndTimeBasedFNATP">
                <maxFileSize>${MAX_FILE_SIZE}</maxFileSize>
            </timeBasedFileNamingAndTriggeringPolicy>
            <maxHistory>90</maxHistory>  <!-- 错误日志保留更久 -->
            <totalSizeCap>${TOTAL_SIZE_CAP}</totalSizeCap>
        </rollingPolicy>
        <encoder>
            <pattern>${LOG_PATTERN}</pattern>
        </encoder>
    </appender>

    <!-- 5. 异步 Appender (推荐用于生产) -->
    <appender name="ASYNC-INFO" class="ch.qos.logback.classic.AsyncAppender">
        <appender-ref ref="FILE-INFO"/>
        <queueSize>1024</queueSize>
        <discardingThreshold>0</discardingThreshold>
        <neverBlock>true</neverBlock>
        <includeCallerData>false</includeCallerData>
    </appender>

    <!-- 6. 日志级别配置 -->
    <logger name="com.company" level="DEBUG"/>
    <logger name="org.springframework.web" level="INFO"/>
    <logger name="org.springframework.jdbc" level="WARN"/>
    <logger name="org.hibernate.SQL" level="DEBUG"/>
    <logger name="org.hibernate.type.descriptor.sql.BasicBinder" level="TRACE"/>

    <!-- 7. Spring Profile 特定配置 -->
    <springProfile name="dev">
        <root level="INFO">
            <appender-ref ref="CONSOLE"/>
            <appender-ref ref="ASYNC-INFO"/>
        </root>
    </springProfile>

    <springProfile name="prod">
        <root level="INFO">
            <appender-ref ref="ASYNC-INFO"/>
            <appender-ref ref="FILE-ERROR"/>
        </root>
        <!-- 生产环境只打 WARN+ 级别的 Spring 日志 -->
        <logger name="org.springframework" level="WARN"/>
    </springProfile>

</configuration>
```

### 2.3 日志级别

| 级别 | 用途 | 示例 |
|------|------|------|
| **TRACE** | 最详细的调试信息 | SQL 参数绑定值、循环中的每一步 |
| **DEBUG** | 开发调试信息 | 方法入口/出口、条件判断结果 |
| **INFO** | 重要业务事件 | 用户注册成功、订单创建、任务调度 |
| **WARN** | 潜在问题但系统自动恢复 | 重试操作、降级切换、配置缺失（使用默认值） |
| **ERROR** | 需要关注的错误 | 数据库连接失败、API 调用异常、数据不一致 |

**生产环境建议：**
```
root: WARN → INFO
com.company: INFO
第三方库: WARN 或 ERROR
```

### 2.5 MDC (Mapped Diagnostic Context)

MDC 可以在不修改方法签名的情况下，在日志中自动包含上下文信息。

```java
// 1. 过滤器：在每个请求开始和结束时设置/清除 MDC
@Component
public class MdcFilter implements Filter {

    private static final String TRACE_ID = "traceId";
    private static final String USER_ID = "userId";
    private static final String REQUEST_PATH = "requestPath";

    @Override
    public void doFilter(ServletRequest request, ServletResponse response,
                         FilterChain chain) throws IOException, ServletException {

        try {
            // 设置 MDC
            MDC.put(TRACE_ID, generateTraceId());  // 或从请求头获取
            MDC.put(REQUEST_PATH,
                ((HttpServletRequest) request).getRequestURI());

            if (request instanceof HttpServletRequest) {
                String userId = extractUserId((HttpServletRequest) request);
                if (userId != null) {
                    MDC.put(USER_ID, userId);
                }
            }

            chain.doFilter(request, response);

        } finally {
            // 必须清理！防止线程池复用导致 MDC 泄露
            MDC.clear();
        }
    }

    private String generateTraceId() {
        return UUID.randomUUID().toString().replace("-", "");
    }
}

// 2. 使用 MDC
@Service
public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    public Order createOrder(CreateOrderRequest request) {
        // traceId 和 userId 由 Filter 设置，日志自动包含
        log.info("Creating order: amount={}", request.getAmount());

        // 运行时也可以动态添加 MDC
        MDC.put("orderId", order.getId().toString());

        log.info("Order created");

        // 注意：MDC 通常应该在 Filter 或 AOP 中统一管理
        return order;
    }
}

// 3. 异步线程传递 MDC
// 自定义 TaskDecorator 将 MDC 传递给子线程
@Component
public class MdcTaskDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable task) {
        Map<String, String> contextMap = MDC.getCopyOfContextMap();
        return () -> {
            try {
                MDC.setContextMap(contextMap);
                task.run();
            } finally {
                MDC.clear();
            }
        };
    }
}

@Configuration
public class ThreadPoolConfig {
    @Bean
    public ThreadPoolTaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setTaskDecorator(new MdcTaskDecorator());
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(20);
        return executor;
    }
}
```

### 2.6 异步日志

```xml
<!-- 异步 Appender 配置 -->
<appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
    <!-- 引用一个或多个同步 Appender -->
    <appender-ref ref="FILE"/>

    <!-- 队列大小 -->
    <queueSize>1024</queueSize>

    <!-- 队列剩余 20% 时丢弃 TRACE/DEBUG -->
    <discardingThreshold>0</discardingThreshold>

    <!-- 不阻塞业务线程 -->
    <neverBlock>true</neverBlock>

    <!-- 不包含调用者数据（提升性能） -->
    <includeCallerData>false</includeCallerData>

    <!-- 刷新间隔 -->
    <maxFlushTime>1000</maxFlushTime>
</appender>
```

**同步 vs 异步性能对比：**

| 指标 | 同步 | 异步 |
|------|------|------|
| 单次日志写入时间 | 0.5-5ms | ~0.001ms |
| 高并发下业务线程阻塞 | 可能阻塞 | 不阻塞（队列满时丢弃） |
| 日志不丢失保证 | 保证 | 应用崩溃时可能丢失 |
| CPU 消耗 | 低 | 额外一个线程 |
| 适用场景 | 低并发、调试 | 生产环境高并发 |

### 2.7 日志安全管理

```java
// 敏感数据脱敏
public class SensitiveDataConverter extends MessageConverter {

    private static final Pattern PASSWORD_PATTERN =
        Pattern.compile("\"password\"\\s*:\\s*\"([^\"]+)\"");

    private static final Pattern PHONE_PATTERN =
        Pattern.compile("\"phone\"\\s*:\\s*\"([^\"]+)\"");

    private static final Pattern ID_CARD_PATTERN =
        Pattern.compile("\"idCard\"\\s*:\\s*\"([^\"]+)\"");

    @Override
    public String convert(ILoggingEvent event) {
        String message = event.getFormattedMessage();

        // 脱敏处理
        message = PASSWORD_PATTERN.matcher(message)
            .replaceAll("\"password\":\"******\"");
        message = PHONE_PATTERN.matcher(message)
            .replaceAll("\"phone\":\"$1****\"");
        message = ID_CARD_PATTERN.matcher(message)
            .replaceAll("\"idCard\":\"$1****\"");

        return message;
    }
}
```

### 2.9 日志管理最佳实践

| 实践 | 说明 |
|------|------|
| 用参数化日志 | `log.info("user: {}", name)` 而非字符串拼接 |
| 日志带上 traceId | 通过 MDC 自动注入，方便关联请求 |
| 不要日志中打印密码 | 任何敏感信息都不能出现在日志 |
| 区分业务日志和系统日志 | 分开 Appender 和文件 |
| 设置合理保留期 | INFO 30天，ERROR 90天 |
| 控制日志量 | 避免循环中打印日志，使用采样 |
| 统一日志格式 | JSON 格式方便解析 |

### 3.1 Micrometer 指标门面

Micrometer 是 Java 的指标门面（类似 SLF4J 对于日志），统一了各种监控系统的 API。


### 3.2 指标类型

```java
// 1. Counter (计数器) — 只能增长
Counter requestCounter = Counter.builder("api.requests")
    .tag("endpoint", "/api/users")
    .tag("method", "GET")
    .register(meterRegistry);

requestCounter.increment();
requestCounter.increment(2.0);

// 2. Gauge (仪表盘) — 可增可减
Gauge.builder("jdbc.connections.active", connectionPool,
        ConnectionPool::getActiveConnections)
    .tag("pool", "primary")
    .register(meterRegistry);

// 3. Timer (计时器) — 记录延迟和频率
Timer timer = Timer.builder("api.request.duration")
    .tag("endpoint", "/api/users")
    .publishPercentiles(0.5, 0.95, 0.99)  // P50, P95, P99
    .sla(Duration.ofMillis(100), Duration.ofMillis(500))  // SLA 边界
    .register(meterRegistry);

// 用法 1: 函数式
timer.record(() -> handleRequest());

// 用法 2: 自动计时
Timer.Sample sample = Timer.start(meterRegistry);
try {
    handleRequest();
} finally {
    sample.stop(timer);
}

// 4. DistributionSummary (分布摘要) — 记录事件的分布
DistributionSummary summary = DistributionSummary.builder("order.amount")
    .tag("currency", "CNY")
    .publishPercentiles(0.5, 0.95, 0.99)
    .serviceLevelObjectives(
        new BigDecimal("100"),  // < 100
        new BigDecimal("1000")  // < 1000
    )
    .register(meterRegistry);

summary.record(order.getAmount().doubleValue());
```

```java
// 自定义业务指标
@Component
public class OrderMetrics {

    private final Counter orderCreatedCounter;
    private final Counter orderPaidCounter;
    private final Timer orderProcessTimer;
    private final DistributionSummary orderAmountSummary;

    public OrderMetrics(MeterRegistry registry) {
        this.orderCreatedCounter = Counter.builder("order.created.total")
            .description("Total orders created")
            .register(registry);

        this.orderPaidCounter = Counter.builder("order.paid.total")
            .description("Total orders paid")
            .register(registry);

        this.orderProcessTimer = Timer.builder("order.process.duration")
            .description("Order processing duration")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(registry);

        this.orderAmountSummary = DistributionSummary.builder("order.amount")
            .description("Order amount distribution")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(registry);
    }

    @Timed(value = "order.create", description = "Time taken to create order")
    public void recordOrderCreated(Order order) {
        orderCreatedCounter.increment();
        orderAmountSummary.record(order.getTotalAmount().doubleValue());
    }

    public void recordOrderPaid(Order order) {
        orderPaidCounter.increment();
    }
}
```

### 3.6 关键指标模型

#### RED 方法 (服务级指标)

| 指标 | 含义 | 示例 PromQL |
|------|------|-------------|
| **R**ate | 每秒请求数 | `rate(http_requests_total[1m])` |
| **E**rrors | 失败请求数 | `rate(http_requests_total{status=~"5.."}[1m])` |
| **D**uration | 请求延迟分布 | `histogram_quantile(0.99, rate(...))` |

#### USE 方法 (资源级指标)

| 指标 | 含义 | 示例 |
|------|------|------|
| **U**tilization | 资源利用率 | CPU 90%, 内存 80% |
| **S**aturation | 资源饱和程度 | 等待队列长度 |
| **E**rrors | 资源错误计数 | 磁盘 I/O 错误 |

#### 四大黄金信号

| 信号 | 含义 | 监控对象 |
|------|------|---------|
| **Latency** | 延迟 | 请求处理时间、数据库查询时间 |
| **Traffic** | 流量 | QPS、带宽、并发连接数 |
| **Errors** | 错误 | HTTP 5xx、异常率、超时率 |
| **Saturation** | 饱和度 | CPU 使用率、内存使用率、连接池使用率 |

```java
// 代码中创建 Span
@Service
public class UserService {
    private static final Logger log = LoggerFactory.getLogger(UserService.class);

    private final Tracer tracer;

    public UserService(Tracer tracer) {
        this.tracer = tracer;
    }

    public User getUserById(Long id) {
        // 创建自定义 Span
        Span span = tracer.nextSpan().name("getUserWithDetails").start();
        try (Scope scope = span.makeCurrent()) {
            span.setAttribute("user.id", id);
            span.setAttribute("db.query", "SELECT * FROM users WHERE id = ?");

            User user = userRepository.findById(id)
                .orElseThrow(() -> new UserNotFoundException(id));

            // 子 Span: 加载订单
            Span orderSpan = tracer.nextSpan().name("loadUserOrders").start();
            try (Scope orderScope = orderSpan.makeCurrent()) {
                user.setOrders(orderRepository.findByUserId(id));
            } finally {
                orderSpan.end();
            }

            return user;
        } catch (Exception e) {
            span.setAttribute("error", e.getMessage());
            span.setStatus(StatusCode.ERROR);
            throw e;
        } finally {
            span.end();
        }
    }
}
```

### 4.5 采样策略

| 策略 | 描述 | 适用场景 |
|------|------|---------|
| Head-based | 请求入口处决定是否采样 | 简单，但可能丢失重要错误链 |
| Tail-based | 先记录所有 span，再根据条件采样 | 能保留所有错误链，但成本高 |
| 概率采样 | 随机采样一定比例 (如 10%) | 通用推荐 |
| 速率限制 | 每秒最多采样 N 个 | 高流量场景 |

## 5. 告警体系

### 5.1 Prometheus Alerting Rules

```yaml
# prometheus-alerts.yml
groups:
  - name: java-app-alerts
    interval: 30s
    rules:
      # 服务不可用
      - alert: InstanceDown
        expr: up{job="spring-boot-app"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Instance {{ $labels.instance }} down"
          description: "{{ $labels.instance }} has been down for more than 1 minute"

      # 高错误率
      - alert: HighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
            / sum(rate(http_server_requests_seconds_count[5m])) > 0.05
        for: 3m
        labels:
          severity: critical
        annotations:
          summary: "High error rate on {{ $labels.application }}"
          description: "Error rate is {{ $value | humanizePercentage }}"

      # 高延迟
      - alert: HighLatency
        expr: |
          histogram_quantile(0.99,
            rate(http_server_requests_seconds_bucket[5m])) > 2
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "High P99 latency on {{ $labels.application }}"
          description: "P99 latency is {{ $value }}s"

      # GC 暂停时间过长
      - alert: LongGCPause
        expr: rate(jvm_gc_pause_seconds_sum[5m]) > 1
        for: 3m
        labels:
          severity: warning
        annotations:
          summary: "Long GC pause on {{ $labels.instance }}"
          description: "GC pause rate is {{ $value }}s/s"

      # 堆内存使用率过高
      - alert: HighHeapUsage
        expr: |
          jvm_memory_used_bytes{area="heap"}
            / jvm_memory_max_bytes{area="heap"} > 0.9
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "High heap usage on {{ $labels.instance }}"
          description: "Heap usage is {{ $value | humanizePercentage }}"

      # 线程阻塞
      - alert: BlockedThreads
        expr: |
          jvm_threads_states_threads{state="blocked"} > 10
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Blocked threads on {{ $labels.instance }}"
          description: "{{ $value }} threads are blocked"
```

### 5.3 告警设计原则

| 原则 | 好的告警 | 不好的告警 |
|------|---------|-----------|
| 标题明确 | `[Critical] High error rate on user-service` | `Something went wrong` |
| 可操作 | 告诉工程师下一步怎么做 | 只告诉你"CPU 高了" |
| 有上下文 | 错误率 25%，正常值 < 5% | 错误率 25% |
| 分级合理 | critical/warning/info | 全部都是 critical |
| 无重复 | Grouped by alertname | 同一问题发 50 条告警 |
| 有 Runbook | 附上排查链接 | 什么都没有 |

### 5.4 告警疲劳避免

| 策略 | 说明 |
|------|------|
| 升级间隔 | 同一告警 4 小时内不重复 |
| 静默期 | 已知问题在修复期间静默 |
| 聚合告警 | 同类告警合并为一条 |
| 分级处理 | critical 才通知 on-call, warning 发 slack |
| 减少噪音 | 定期 review 告警规则，删掉无用的 |
| 自愈告警 | 系统自动恢复的不通知 |

## 9. 面试高频题

### 基础概念类

**Q: 可观测性三大支柱是什么？为什么要三者？**
A: Logs, Metrics, Traces。Logs 告诉你具体事件，Metrics 告诉你聚合状态，Traces 告诉你请求路径。三者互补：只看 Metrics 知道错误率高了，但不知道具体哪个请求出错了；配合 Logs 知道具体错误，Traces 知道请求经过哪些服务。

**Q: SLF4J 是什么？为什么不直接用 Logback？**
A: SLF4J 是日志门面 (Facade)，提供统一的日志 API。好处是：
1. 解耦应用代码和日志实现
2. 可切换实现（Logback → Log4j2 无需改代码）
3. 统一第三方库的日志（通过桥接包）

**Q: Micrometer 是什么？为什么需要它？**
A: Micrometer 是指标门面，统一了指标 API。类似 SLF4J 对于日志。支持写入 Prometheus, Datadog, New Relic, Graphite 等后端。Spring Boot Actuator 默认使用 Micrometer。

### 实战类

**Q: 如何将一个请求的日志、指标和追踪关联起来？**
A: 使用 Trace ID。在请求入口生成 traceId，放入 MDC（日志）、Span 的 Tag（追踪）、Metrics 的 Tag（指标）。三者共享同一个 traceId，可以通过 traceId 跨系统关联。

**Q: 日志应该用 JSON 格式还是纯文本？**
A: 生产环境推荐 JSON 格式。JSON 可被 Logstash/Fluentd 直接解析，支持结构化字段（traceId, userId），便于在 Kibana/Grafana Loki 中搜索和过滤。纯文本适合开发环境人工阅读。

**Q: Prometheus 的 Pull 模型和 Push 模型有什么区别？**
A: Pull 模型（Prometheus 默认）：Prometheus Server 定期从目标拉取指标。好处是容易管理，不需要客户端推。Push 模型（如 Graphite）：应用主动推送指标。适合短期任务、防火墙后的环境。Prometheus 也支持 Pushgateway。

### 场景类

**Q: 线上突然 QPS 下降 50%，如何排查？**
A:
1. 先检查告警，看是否有下游服务不可用
2. 看 Metrics：错误率是否升高？延迟是否升高？
3. 看 Logs：是否有大量超时或异常日志？
4. 看 Traces：哪个环节耗时最长？
5. 检查基础设施：CPU？内存？网络？数据库？
6. 检查是否有发布变更

**Q: 什么情况下应该用 async 日志？有什么风险？**
A: 高并发场景下使用异步日志避免业务线程阻塞。风险：
1. 应用 Crash 时未写入的日志丢失（可用 `neverBlock=false` 缓解）
2. 队列满时丢弃低级别日志
3. 多一个 I/O 线程的 CPU 消耗

**Q: 如何设计一个 alert 规则，既能及时发现问题又不产生告警疲劳？**
A:
1. 分级处理：Critical (10分钟内响应) / Warning (24小时内处理) / Info (记录即可)
2. 设置持续时间：瞬时波动不告警（如 CPU 高持续 5 分钟才告警）
3. 聚合：相同类型的告警归并
4. 设置静默期和升级机制
5. 提供 Runbook，让接收告警的人知道怎么做
