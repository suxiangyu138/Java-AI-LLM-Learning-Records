## 1. 测试基础概念与原则

### 1.1 核心认知

| 概念 | 说明 |
|------|------|
| **测试目的** | 发现错误，证明软件满足需求 — **不是为了证明"软件是对的"** |
| **测试本质** | 用有限的测试用例，在有限的时间内，尽可能多地发现缺陷 |
| **测试成本** | 缺陷发现越晚修复成本越高（需求阶段 vs 生产环境，差 100 倍+） |

### 1.2 七大测试原则

| # | 原则 | 含义 | 实践指导 |
|---|------|------|----------|
| 1 | **穷举测试不可能** | 无法测试所有输入组合 | 用等价类/边界值选代表性用例 |
| 2 | **缺陷集群性** | 80%的错误集中在20%的模块 | 对历史Bug多的模块重点测试 |
| 3 | **杀虫剂悖论** | 同一组用例重复使用会失效 | 定期更新测试用例、引入新的测试角度 |
| 4 | **尽早测试** | 缺陷发现越早修复成本越低 | 需求阶段就介入测试分析 |
| 5 | **测试依赖上下文** | 不同系统测试策略不同 | 金融系统≠社交App的测试重点 |
| 6 | **零缺陷谬误** | 没有发现缺陷≠系统完美 | 可能只是测试用例不够好 |
| 7 | **测试是风险驱动的** | 测试资源有限，按风险优先级分配 | 先测核心交易、后测辅助功能 |

## 2. 测试分类体系

### 2.1 按测试阶段分类

| 阶段 | 英文 | 测试对象 | 执行者 | 工具(Java) |
|------|------|----------|--------|-----------|
| **单元测试** | Unit Test | 单个类/方法 | 开发者 | JUnit5 + Mockito |
| **集成测试** | Integration Test | 模块间接口 | 开发者 | SpringBootTest, REST Assured |
| **系统测试** | System Test | 完整系统 | 测试团队 | JMeter, Selenium |
| **验收测试** | UAT (User Acceptance Test) | 业务场景 | 产品/用户 | Cucumber, 手动测试 |

### 2.2 按是否查看代码分类

| 方法 | 说明 | 技术 | 优势 | 局限 |
|------|------|------|------|------|
| **黑盒测试** | 不看代码，关注输入输出 | 等价类、边界值、因果图、场景法 | 关注用户视角 | 无法保证代码覆盖度 |
| **白盒测试** | 看代码，关注逻辑覆盖 | 语句覆盖→分支覆盖→路径覆盖→条件组合覆盖 | 精确度量覆盖 | 成本高 |
| **灰盒测试** | 两者结合 | 介于黑白之间 | 平衡成本和有效性 | — |

### 2.3 按测试目的分类

| 类型 | 英文 | 目的 | 工具 |
|------|------|------|------|
| **功能测试** | Functional | 验证功能是否满足需求 | 手动/JUnit |
| **性能测试** | Performance | 评估系统响应时间、吞吐量 | JMeter, Gatling |
| **负载测试** | Load | 在预期负载下的表现 | JMeter, k6 |
| **压力测试** | Stress | 超负荷下的表现和恢复能力 | wrk, JMeter |
| **安全测试** | Security | 发现安全漏洞 | OWASP ZAP, Burp Suite |
| **兼容性测试** | Compatibility | 不同环境/浏览器/设备 | BrowserStack |
| **回归测试** | Regression | 确保新代码不影响已有功能 | CI/CD 自动运行全部测试 |

## 3. 测试用例设计方法

### 3.1 等价类划分

> 🎯 将输入域划分为若干等价类，每类至少选一个代表性用例，减少测试用例数量。

```text
示例：年龄输入（1-150之间的整数）

有效等价类： [1, 150]
无效等价类1： ≤0 （如 -1）
无效等价类2： >150 （如 200）
无效等价类3： 非整数 （如 "abc"）
无效等价类4： 空值

至少需要 4 个测试用例覆盖以上所有等价类。
```

### 3.2 边界值分析

> ⚠️ Bug 常出现在边界！边界上、边界内、边界外的值都需要测试。

```text
示例：数组索引 [0, length-1]
边界值：-1（下边界外）、0（下边界上）、
        length-1（上边界上）、length（上边界外）

示例：金额校验 0.01 ~ 99999.99
测试点：0.00、0.01、99999.99、100000.00
```

### 3.3 判定表/因果图

> 多条件组合场景使用判定表，确保不遗漏组合。

```text
场景：电商优惠券使用条件
条件：
  C1: 用户是VIP
  C2: 订单金额 > 100
  C3: 优惠券未过期

动作：
  A1: 可以使用优惠券
  A2: 提示"不满足条件"

| C1 | C2  | C3  | 结果 |
|----|-----|-----|------|
| T  | T   | T   | A1   |
| T  | T   | F   | A2   |
| T  | F   | T   | A2   |
| T  | F   | F   | A2   |
| F  | T   | T   | A2   |
| F  | T   | F   | A2   |
| F  | F   | T   | A2   |
| F  | F   | F   | A2   |
```

### 3.4 场景法（业务流程测试）

```text
电商下单主流程：
✅ 正常流程：登录 → 选商品 → 加购物车 → 下单 → 支付 → 查看订单
⚠️ 分支1：登录 → 选商品 → 加购物车 → 库存不足 → 提示
⚠️ 分支2：登录 → 下单 → 支付 → 余额不足 → 提示
⚠️ 异常1：未登录 → 下单 → 跳转登录页
⚠️ 异常2：下单 → 支付超时 → 订单取消
```

### 3.5 方法对比与选择

| 方法 | 适用场景 | 产出 | 效率 |
|------|----------|------|------|
| 等价类 | 输入有明确取值范围 | 减少用例数量 | ⭐⭐⭐⭐ |
| 边界值 | 数值/字符串长度/数组索引 | 捕获边界Bug | ⭐⭐⭐⭐⭐ |
| 判定表 | 多条件组合规则 | 逻辑完整性 | ⭐⭐⭐ |
| 场景法 | 业务流程、用户路径 | 业务覆盖 | ⭐⭐⭐⭐ |
| 错误推测 | 基于经验的易错点 | 针对性补漏 | ⭐⭐⭐ |

## 4. 单元测试实践

### 4.1 好的单元测试特征（FIRST原则）

| 原则 | 说明 | 反面示例 |
|------|------|----------|
| **F**ast | 毫秒级完成 | 单元测试连接真实数据库 |
| **I**ndependent | 不依赖其他测试 | 测试B依赖测试A创建的记录 |
| **R**epeatable | 任何时候结果一致 | 依赖系统时间`LocalDate.now()` |
| **S**elf-Validating | 自动判断通过/失败 | 靠`System.out.println()`人工判断 |
| **T**imely | 在生产代码之前/同时编写 | 上线后才补测试 |

### 4.2 Java单元测试标准写法

```java
@Test
void shouldReturnSum() {
    assertEquals(5, calculator.add(2, 3));
}

@Test
void shouldThrowForNullInput() {
    assertThrows(IllegalArgumentException.class, 
        () -> calculator.add(null, 3));
}

@ParameterizedTest
@CsvSource({"1,2,3", "0,0,0", "-1,1,0"})
void shouldAddCorrectly(int a, int b, int expected) {
    assertEquals(expected, calculator.add(a, b));
}
```

### 4.3 Mock/Stub的核心区别

| 概念 | 含义 | 使用场景 |
|------|------|----------|
| **Stub** | 返回预设值的假对象 | 验证**状态**（返回值是否正确） |
| **Mock** | 可记录和验证调用行为的假对象 | 验证**行为**（是否被调用、调用次数） |
| **Spy** | 部分Mock，保留真实对象部分行为 | 只想Mock部分方法 |

## 6. TDD测试驱动开发

### 6.1 Red-Green-Refactor 循环

```
① RED：写一个失败的测试
   (先思考"什么行为是期望的"，写出测试 → 运行 → 看到失败 ✅)

② GREEN：写最少代码让测试通过
   (不要过度设计！哪怕hardcode返回值，先让测试通过)

③ REFACTOR：重构代码
   (消除重复、改善设计 → 运行测试确认仍然通过 ✅)
```

### 6.2 TDD适用/不适用场景

| 适用 ✅ | 不适用 ❌ |
|---------|----------|
| 核心业务逻辑、算法 | UI频繁变化 |
| 工具库、SDK开发 | 原型探索阶段 |
| 有明确输入输出的方法 | 一次性脚本 |
| 多人协作的复杂模块 | 需求极不明确的探索 |

## 7. 测试度量与质量评估

### 7.1 代码覆盖率

| 指标 | 合理目标 | 说明 |
|------|----------|------|
| 行覆盖率 | ≥ 80% | 最直观的指标 |
| 分支覆盖率 | ≥ 70% | 比行覆盖更重要，暴露未测试分支 |
| 方法覆盖率 | ≥ 90% | 方法级别 |

> ⚠️ 覆盖率是必要条件，不是充分条件。100%覆盖率的无断言测试 = 废纸。

### 7.2 缺陷密度

```text
缺陷密度 = 发现的缺陷数 / 代码规模(KLOC)
    合理范围：1-5 个/KLOC
    优秀水平：< 1 个/KLOC
```

### 7.3 测试投入产出比

```text
测试ROI = 预防的生产事故损失 / 测试投入成本
    每投入1元测试 = 节约5-10元生产事故损失
```

---

> 🎯 **核心原则**：测试不是"附加项"，而是"质量内嵌"。尽早测试、分层测试、自动化测试——三者构成现代软件质量保障的铁三角。
