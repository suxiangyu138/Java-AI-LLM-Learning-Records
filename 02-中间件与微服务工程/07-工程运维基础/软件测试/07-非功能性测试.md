## 1. 非功能性测试全景

```
非功能性测试分类：
├── ⚡ 性能测试     → 系统有多快、能扛多少流量
├── 🔒 安全测试     → 系统有多安全
├── 📱 兼容性测试   → 在不同环境能用吗
├── 👤 可用性测试   → 好用吗、用户会操作吗
├── 🔄 可靠性测试   → 能连续运行多久不出问题
├── 📐 可维护性测试 → 改起来容易吗
└── 🌍 国际化测试   → 多语言、多时区支持
```

| 维度 | 功能测试 | 非功能性测试 |
|------|----------|-------------|
| 问的是 | "系统做对了吗？" | "系统做得好吗？" |
| 验证 | 功能正确性 | 性能、安全、体验 |
| 失败后果 | 功能不可用 | 体验差/性能差/安全问题 |

## 2. 性能测试

### 2.1 性能测试子类型

| 类型 | 目的 | 方法 | 工具 |
|------|------|------|------|
| **负载测试** | 预期负载下的表现 | 模拟正常QPS | JMeter, k6 |
| **压力测试** | 找到系统瓶颈和极限 | 逐步加大负载直到崩溃 | JMeter, wrk |
| **稳定性测试** | 长时间运行是否稳定 | 80%最大负载持续≥8h | JMeter |
| **容量测试** | 支撑多少用户/数据量 | 从基准推算 | 压测+建模 |
| **峰值测试** | 突发流量冲击 | 模拟瞬时峰值QPS | JMeter, vegeta |
| **基准测试** | 建立性能基线 | 单接口/单用户 | wrk, ab |

### 2.2 性能场景设计

```text
电商大促场景设计：
  场景1：浏览商品（GET /api/products，占总流量70%）
  场景2：搜索商品（GET /api/products?keyword=xxx，15%）
  场景3：加入购物车（POST /api/cart，10%）
  场景4：下单（POST /api/orders，5%）

目标：混合场景需支持 5000 QPS，P99 < 500ms
```

### 2.3 性能测试报告关键数据

```text
核心指标：
  QPS/TPS：每秒处理请求数（巅峰值+稳定值）
  响应时间：P50/P90/P95/P99/Max
  错误率：目标 < 0.1%
  资源使用：CPU/memory/network/disk
  
容量结论：
  单实例峰值 = 1200 QPS
  大促预估峰值 = 5000 QPS
  需要实例数 = 5000/1200 × 1.3 = 5.4 → 部署6个实例
```

## 3. 安全测试

### 3.1 安全测试层次

| 层次 | 测试内容 | 工具 |
|------|----------|------|
| **SAST静态分析** | 源代码安全漏洞扫描 | SonarQube, SpotBugs, Checkmarx |
| **DAST动态分析** | 运行中的应用安全扫描 | OWASP ZAP, Burp Suite, Acunetix |
| **依赖检查** | 第三方库已知漏洞(CVE) | OWASP Dependency Check, Snyk |
| **渗透测试** | 模拟攻击者入侵 | 专业渗透测试团队/Kali工具集 |
| **配置审计** | 安全配置基线检查 | CIS Benchmark, OpenSCAP |

### 3.2 OWASP Top 10 测试重点

| 排名 | 风险 | 简述 | 测试方法 |
|:---:|------|------|------|
| A01 | 访问控制失效 | URL可被未授权访问 | 尝试未登录/低权限用户访问管理接口 |
| A02 | 加密失败 | 明文传输、弱加密 | 检查HTTPS、敏感数据加密 |
| A03 | **注入** | SQL/LDAP/命令注入 | `' OR '1'='1` 测试所有输入点 |
| A04 | 不安全设计 | 架构层面安全设计缺失 | 威胁建模审查 |
| A05 | 安全配置错误 | 默认密码未改、错误信息暴露 | 检查默认配置是否修改 |
| A06 | 易受攻击的组件 | 依赖库有CVE漏洞 | `mvn dependency-check:check` |
| A07 | 认证失败 | 弱密码策略、暴力破解 | 测试弱密码+暴力破解 |
| A08 | 软件和数据完整性 | 反序列化攻击、CI/CD投毒 | 检查反序列化入口 |
| A09 | 日志和监控失败 | 攻击行为无记录 | 确认关键操作有审计日志 |
| A10 | SSRF服务端请求伪造 | 服务端请求被操控 | 检查URL参数是否可指向内网 |

## 4. 兼容性测试

### 4.1 兼容性测试矩阵

| 维度 | 关注点 |
|------|--------|
| **浏览器** | Chrome/Firefox/Safari/Edge 最近3个主版本 |
| **操作系统** | Windows 10/11, macOS, Linux发行版 |
| **移动端** | iOS最新2版, Android主流版本 |
| **屏幕分辨率** | 1920×1080, 1366×768, 375×667(手机) |
| **API版本** | 新版本API需兼容旧版Client至少2个大版本 |

### 4.2 兼容性测试策略

```
1. 确定目标受众的设备/浏览器分布（看数据分析或行业报告）
2. 按占比排序：覆盖Top 90%的用户环境
3. 自动化：Selenium Grid / BrowserStack 多浏览器并行测试
4. 手动抽查：关键页面在不同设备上的显示
```

## 5. 可用性与可访问性测试

### 5.1 可用性测试

| 评估维度 | 说明 | 评估方法 |
|----------|------|----------|
| **可学习性** | 新用户多久能完成基本任务？ | 给新用户任务，计时+观察 |
| **效率** | 熟练用户完成任务的效率？ | 操作步骤数、点击次数 |
| **可记忆性** | 不常用后还能记得怎么用吗？ | 间隔2周再测同一用户 |
| **错误率** | 用户犯错的频率和严重性？ | 统计错误操作和回退 |
| **满意度** | 用户的主观满意度？ | SUS问卷(System Usability Scale) |

### 5.2 可用性启发式原则（Nielsen's 10）

```
1. 系统状态可见性（如"正在处理..."提示）
2. 系统与现实匹配（用户熟悉的语言和概念）
3. 用户控制与自由（撤销、返回功能）
4. 一致性与标准（同一个按钮不同页面不能变位置）
5. 错误预防（删除前确认弹窗）
6. 识别而非回忆（可选项展示出来，不要让用户记）
7. 使用的灵活性与效率（快捷键支持）
8. 美观与简约设计
9. 帮助用户识别和恢复错误（清晰的错误提示+解决方案）
10. 帮助文档
```

## 6. 可靠性测试

| 测试类型 | 目的 | 方法 |
|----------|------|------|
| **故障恢复测试** | 系统从故障中恢复的能力 | 强制kill服务 → 观察是否自动恢复 |
| **数据备份恢复** | 备份恢复流程是否可靠 | 定期演练备份恢复 |
| **长时间运行测试** | 长时间运行无内存泄漏 | 7×24h持续运行+监控 |
| **降级测试** | 非核心功能挂了对核心功能的影响 | 关掉推荐服务 → 交易是否正常 |

---

> 🎯 **非功能测试的核心价值**：功能正常只是上线标准，性能达标+安全可靠+用户满意才是交付标准。
