## 1. 黑盒测试详解

### 1.1 定义

**黑盒测试 (Black-Box Testing)** 将被测系统视为一个"黑盒子"——不关心内部结构、不阅读代码，只关注**输入数据**和**输出结果**。

```text
         ┌─────────────────┐
  输入 ──→│                  │──→ 输出
         │   黑盒（系统）    │
         │   （不关心内部）  │
         └─────────────────┘

关注点：
  ✓ 功能是否按需求实现
  ✓ 输入是否被正确接受和处理
  ✓ 输出是否符合预期
  ✓ 异常情况是否妥善处理
  ✗ 代码怎么实现的不关心
```

### 1.2 黑盒测试的别名

| 别名 | 说明 |
|------|------|
| **功能测试 (Functional Testing)** | 最常用的别称，验证系统功能是否满足需求 |
| **数据驱动测试 (Data-Driven Testing)** | 关注输入数据对输出的影响 |
| **规范验证 (Specification-Based Testing)** | 对照需求规格说明书的验证 |
| **行为测试 (Behavioral Testing)** | 关注系统的外部行为而非内部实现 |

### 1.3 核心认知

> 💡 **黑盒测试本质上等价于"从用户视角验证系统行为"**。测试人员只关心：输入什么 → 期望什么 → 实际得到什么。不关心代码里是 `if-else` 还是 `switch-case`。

### 1.4 黑盒测试的典型场景

| 场景 | 说明 | 示例 |
|------|------|------|
| **功能验证** | 功能是否符合需求 | 登录功能 — 输入正确密码能登录 |
| **输入校验** | 非法输入的处理 | 输入特殊字符、超长文本 |
| **边界测试** | 数值/长度的边界 | 密码长度 6~20 位的边界值 |
| **业务流程** | 完整用户操作路径 | 注册 → 登录 → 下单 → 支付 → 收货 |
| **异常处理** | 系统异常时的表现 | 网络断开、数据库超时 |
| **兼容性** | 不同环境下的表现 | 不同浏览器、操作系统 |

### 1.5 黑盒测试 ≠ "乱点"

> ⚠️ **常见误解**：很多人以为黑盒测试就是"随便打开系统点点看有没有Bug"。实际上，黑盒测试有一套**系统化的方法论**，从需求分析到用例设计再到数据准备，每一步都有章可循。

```text
❌ 错误认知：黑盒测试 = 打开系统 → 随便点点 → 看有没有Bug
✅ 正确流程：需求分析 → 等价类划分 → 边界值确定 → 判定表制作 →
             场景设计 → 数据准备 → 按步骤执行 → 结果比对 → 缺陷提交
```

## 2. 黑盒测试技术体系

黑盒测试有完善的**技术方法论**支持，以下是 6 种核心的黑盒测试设计技术（详见 `02-测试用例设计方法详解.md`）：

| 技术 | 简要说明 | 适用场景 |
|------|---------|----------|
| **等价类划分** | 将输入域划分为互不相交的等价类，每类选代表值 | 有明确取值范围的输入 |
| **边界值分析** | 在等价类的边界处取点测试 | 数值、长度、集合大小 |
| **判定表方法** | 系统化枚举多条件组合 | 复杂业务规则（VIP+金额+时间） |
| **状态转换测试** | 基于状态机覆盖状态迁移 | 订单状态、工作流、会话 |
| **场景法** | 基于用户业务流程设计 | 端到端业务流程 |
| **因果图法** | 图形化分析条件-结果关系 | 分析复杂逻辑关系 |

> 🎯 **所有黑盒测试技术本质上都是"如何从无限输入中选取有限且有效的样本"的方法论。**

## 3. 黑盒测试的优缺点

### 3.1 优点

| 优点 | 说明 | 示例 |
|------|------|------|
| **贴近用户视角** | 从用户使用系统的角度测试 | 用户不关心代码结构，只关心功能能用 |
| **不依赖实现** | 无需了解代码、无需编程技能 | 业务人员也能参与黑盒测试设计 |
| **适合大系统** | 系统越大，黑盒测试优势越明显 | 微服务架构、第三方集成 |
| **需求覆盖直接** | 直接对照需求规格说明 | 每个需求点对应一个测试场景 |
| **测试与开发解耦** | 测试可与开发并行 | 需求确定后即可设计用例，不等代码完成 |
| **发现遗漏功能** | 容易发现"该有的功能没有" | 需求写了"导出Excel"，但系统没有实现 |

### 3.2 缺点

| 缺点 | 说明 | 影响 |
|------|------|------|
| **覆盖难度量** | 无法知道"代码里还有哪些路径没测" | 白盒覆盖指标无法获取 |
| **冗余多** | 不同测试可能有相同的代码路径 | 无效用例多，增加维护成本 |
| **无法发现逻辑缺陷** | 看似功能正确，但代码逻辑有Bug | 如果输入输出恰好匹配需求，但内部路径错了 |
| **盲点** | 某些代码路径很难通过外部输入触发 | 极端的异常路径、死代码 |
| **低效的重复** | 如果界面频繁变化，用例维护量大 | UI自动化的典型痛点 |

### 3.3 黑盒测试的典型盲点示例

```java
public int calculateDiscount(int amount) {
    // 需求：满100减10，满200减30
    // Bug：满200时实际只减了20（不是需求说的30）
    if (amount >= 200) {
        return amount - 20;  // Bug! 应该是 amount - 30
    } else if (amount >= 100) {
        return amount - 10;
    }
    return amount;
}
```

> ⚠️ **黑盒测试单独无法发现这个 Bug** — 因为输入 `amount=200` 时，输出 `180`，从用户视角"确实是减了钱"。但如果需求文档也写错了（需求上写的是满200减20），黑盒测试会认为功能正确，彻底"将错就错"。白盒测试能从代码中直接发现 `20` 与需求设计不一致。

## 4. 白盒测试详解

### 4.1 定义

**白盒测试 (White-Box Testing)** 将系统视为一个**透明盒子**——测试人员需要阅读和分析**源代码**，基于代码的内部逻辑来设计测试用例。也称为**结构测试 (Structural Testing)** 或**玻璃盒测试 (Glass-Box Testing)**。

```text
         ┌─────────────────┐
  输入 ──→│                  │──→ 输出
         │   白盒（系统）    │
         │  (关注内部结构)   │
         └─────────────────┘

关注点：
  ✓ 每条代码语句是否被执行
  ✓ 每个分支是否被覆盖
  ✓ 每个条件是否取到真/假
  ✓ 每个路径是否被走过
  ✗ 外部功能是否正确（那是黑盒的事）
```

### 4.2 白盒测试回答的核心问题

| 问题 | 对应的覆盖准则 | 通俗理解 |
|------|--------------|---------|
| **是否每行代码都执行过？** | 语句覆盖 | "每句话都念到了吗" |
| **每个 if 的真/假分支都走到过？** | 分支覆盖 | "每个岔路都走过了吗" |
| **每个复合条件的每个子条件都取过真/假？** | 条件覆盖 | "每个开关都拨过两边了吗" |
| **所有条件的组合都测过？** | 条件组合覆盖 | "所有开关的所有组合都试过了吗" |
| **所有可能的执行路径都走过？** | 路径覆盖 | "所有可能的路线都走过了吗" |
| **每个条件是否独立地影响判定结果？** | MC/DC | "每个开关都能独立控制结果吗" |

### 4.3 白盒测试的适用场景

| 场景 | 说明 |
|------|------|
| **单元测试** | 白盒测试最经典的应用场景 |
| **核心算法** | 排序、加密、金融计算等关键逻辑 |
| **安全关键系统** | 航空、医疗、自动驾驶（DO-178C 要求 MC/DC） |
| **代码审查配合** | 审查 + 白盒测试双保险 |
| **遗留系统重构** | 先写白盒测试做"安全网"再重构 |

## 5. 白盒覆盖准则（从低到高）

### 5.1 覆盖准则层级全景

```text
覆盖强度（从低到高）：

                                         ┌─ 路径覆盖 (Path Coverage)
                                         │  (所有路径 → 可能指数爆炸)
                                        ┌┤
                              ┌─ 条件组合覆盖 ┤└─ MC/DC (修正条件判定覆盖)
                              │  (所有条件组合 → 2ⁿ 个用例)  (n+1 个用例)
                             ┌┤
                   ┌─ 条件覆盖 ┤
                   │  (每个子条件取 T/F)
                  ┌┤
        ┌─ 分支覆盖 ┤
        │  (每个判定的 T/F 分支)
       ┌┤
┌─ 语句覆盖 ┤
│  (每句至少一次)             ← 覆盖强度越高越难达到100%
```

### 5.2 语句覆盖 (Statement Coverage) — 最弱

**定义**：程序中的**每条可执行语句**至少被执行一次。

**别名**：行覆盖 (Line Coverage)、代码覆盖 (Code Coverage)。

**度量公式**：
```text
语句覆盖率 = 已执行的语句数 / 总语句数 × 100%
```

**特点**：
- ✅ 最基础的覆盖要求，几乎所有覆盖率工具都支持
- ❌ 无法保证分支被覆盖（一条 if 语句可能只测了真分支）
- ❌ 无法发现逻辑运算符的错误（`&&` 写成 `||` 不一定能发现）
- ❌ 即使达到 100%，也可能遗漏大量缺陷

### 5.3 分支覆盖 (Branch/Decision Coverage)

**定义**：程序中的**每个判定（Decision）** 的真假分支至少各执行一次。

**别名**：判定覆盖 (Decision Coverage)。

**度量公式**：
```text
分支覆盖率 = 已执行的分支数 / 总分分支数 × 100%
```

**特点**：
- ✅ 比语句覆盖更强，能发现"某分支从来没人走过"
- ❌ 对于复合条件（`if (a && b)`），无法保证每个子条件的真假都覆盖
- ✅ 多数项目的推荐最低覆盖标准

### 5.4 条件覆盖 (Condition Coverage)

**定义**：程序中的**每个原子条件（Atomic Condition）** 的真假值至少各取一次。

**举例**：`if (a > 0 && b > 0)`
- 需要让 `a > 0` 至少为 T 一次、F 一次
- 需要让 `b > 0` 至少为 T 一次、F 一次

**特点**：
- ✅ 比分支覆盖更细粒度，能发现子条件层面的问题
- ❌ **条件覆盖不一定覆盖所有分支** — 可能出现所有条件都取过 T/F，但判定结果始终相同的情况

### 5.5 条件组合覆盖 (Multiple Condition Coverage)

**定义**：所有原子条件的**真值组合**至少各出现一次。

**度量公式**：
```text
组合数 = 2ⁿ （n = 原子条件数量）
```

**特点**：
- ✅ 最强的"传统"覆盖准则，不遗漏任何组合
- ❌ **用例数随条件数量指数增长**（n=10 → 1024 个用例，实际不可行）
- ❌ 通常只适用于关键模块的核心逻辑

### 5.6 路径覆盖 (Path Coverage)

**定义**：程序中**所有可能的执行路径**至少各执行一次。

**特点**：
- ✅ 理论上能发现所有控制流导致的缺陷
- ❌ 路径数随分支数量**指数爆炸**（循环结构甚至无限路径）
- ❌ 实际项目中几乎不可能做到 100%
- ❌ 即使路径覆盖 100%，也不保证发现所有数据相关的缺陷

### 5.7 覆盖准则之间的关系

```text
               路径覆盖
                  │
                  │ (包含关系)
                  ▼
            条件组合覆盖
              ╱      ╲
             ╱        ╲
      分支覆盖          条件覆盖
            ╲        ╱
             ╲      ╱
             语句覆盖
```

> 💡 **注意**：这些覆盖准则之间是**增强关系**而非严格的包含关系。例如，条件覆盖 100% 不一定意味着分支覆盖 100%（见下面的演示部分）。

## 6. 覆盖准则对比：同一段代码的完整演示

### 6.1 被测代码

```java
public class DiscountCalculator {

    /**
     * 计算折扣：
     * 如果 VIP 会员 且 金额 > 100，打8折
     * 否则不打折
     *
     * @param isVIP  是否是VIP会员
     * @param amount 订单金额
     * @return 折扣后的金额
     */
    public double calculate(boolean isVIP, double amount) {
        double result = amount;          // 语句1

        if (isVIP && amount > 100) {     // 判定D：复合条件
            result = amount * 0.8;       // 语句2（真分支）
        }                                // 子条件C1: isVIP
                                         // 子条件C2: amount > 100
        return result;                   // 语句3
    }
}
```

**控制流图：**

```text
        ┌───────────┐
        │  result = │
        │  amount   │ ← 语句1
        └─────┬─────┘
              │
        ┌─────▼─────┐
        │  isVIP && │
   T ←─│ amount>100│──→ F
        └─────┬─────┘
              │ T
        ┌─────▼─────┐
        │  result*= │
        │  0.8      │ ← 语句2
        └─────┬─────┘
              │
        ┌─────▼─────┐
        │  return   │
        │  result   │ ← 语句3
        └───────────┘
```

**分析参数**：
- 总语句数：3
- 总判定节点：1（复合条件 `isVIP && amount > 100`）
- 总分分支：2（真分支、假分支）
- 总原子条件：2（C1: isVIP, C2: amount > 100）
- 总路径：2（走 if / 不走 if）

### 6.2 语句覆盖演示

**用例：**

| 用例ID | isVIP | amount | 结果 | 覆盖语句 |
|-------|-------|--------|------|---------|
| TC-1 | true | 200 | 160 | 语句1, 语句2, 语句3 |

```text
语句覆盖率 = 3/3 = 100% ✅  （仅需1个用例）
```

| 能发现的Bug | 遗漏的Bug |
|------------|-----------|
| 语句2的算法错误（如 `0.8` 写成 `0.08`） | 分支逻辑错误（如 `&&` 写成 `||`） |
| 语句3的返回错误 | 边界条件错误（如 `> 100` 写成 `>= 100`） |
| — | 假分支完全未覆盖 |
| — | `isVIP=false` 的情况完全未测试 |

### 6.3 分支覆盖演示

**用例：**

| 用例ID | isVIP | amount | 结果 | 覆盖分支 |
|-------|-------|--------|------|---------|
| TC-1 | true | 200 | 160 | 真分支 ✅ |
| TC-2 | false | 50 | 50 | 假分支 ✅ |

```text
分支覆盖率 = 2/2 = 100% ✅  （需要2个用例）
```

| 能发现的Bug | 遗漏的Bug |
|------------|-----------|
| 真分支逻辑错误（如 `&&` 错误地进了真分支） | 复合条件中某个条件永远为真或假 |
| 假分支漏处理 | `amount > 100` 的值从未为假 |

### 6.4 条件覆盖演示

**用例组A（同时满足条件覆盖和分支覆盖）：**

| 用例 | isVIP | amount | C1: isVIP | C2: amount>100 | 判定 |
|------|-------|--------|-----------|---------------|------|
| TC-1 | true | 200 | T | T | T（进真分支）|
| TC-2 | false | 50 | F | F | F（进假分支）|

```text
条件覆盖率 = C1(T/F)✅ C2(T/F)✅ = 100%
分支覆盖率 = 2/2 = 100% ✅（这次刚好也覆盖了分支）
```

**用例组B（满足条件覆盖但不满足分支覆盖）：**

| 用例 | isVIP | amount | C1 | C2 | 判定 |
|------|-------|--------|----|----|------|
| TC-A | true | 50 | T | F | F（不进 if）|
| TC-B | false | 200 | F | T | F（不进 if）|

```text
条件覆盖率 = C1(T/F)✅ C2(T/F)✅ = 100%
分支覆盖率 = 假分支✅ 真分支❌ = 50% ❌
```

> ⚠️ **条件覆盖不保证分支覆盖！** 上述 TC-A + TC-B 中，判定 `isVIP && amount > 100` 的结果始终为 F，真分支从未被执行。这是条件覆盖的典型陷阱。

### 6.5 条件组合覆盖演示

2 个条件 → 4 种组合：

| 组合编号 | C1: isVIP | C2: amount>100 | 判定结果 | 说明 |
|---------|-----------|---------------|---------|------|
| ① | T | T | T | VIP且超100 → 打折 |
| ② | T | F | F | VIP但金额不足 |
| ③ | F | T | F | 非VIP但金额超100 |
| ④ | F | F | F | 非VIP且金额不足 |

**完整用例（4个）：**

| 用例ID | isVIP | amount | 覆盖组合 |
|-------|-------|--------|---------|
| TC-1 | true | 200 | ① |
| TC-2 | true | 50 | ② |
| TC-3 | false | 200 | ③ |
| TC-4 | false | 50 | ④ |

```text
条件组合覆盖率 = 4/4 = 100% ✅  （需要4个用例）
```

| 优势 | 代价 |
|------|------|
| 完全覆盖所有逻辑组合 | 条件每增加一个，用例数翻倍 |
| 能发现特定组合下的隐蔽Bug | 3条件→8用例，4条件→16用例 |

### 6.6 路径覆盖演示

2 条可能路径：

| 用例ID | isVIP | amount | 路径 |
|-------|-------|--------|------|
| TC-1 | true | 200 | 语句1 → if(T) → 语句2 → 语句3 |
| TC-2 | false | 50 | 语句1 → if(F) → 语句3 |

```text
路径覆盖率 = 2/2 = 100% ✅  （需要2个用例）

注意：对于含有循环的程序，路径数可能是无限的。
```

### 6.7 MC/DC 演示

需要证明**每个条件独立影响判定结果**：

**证明 C1 (isVIP) 独立影响：**
- 固定 C2 = T（即 `amount > 100` 为真）
- C1=T → 判定 = T；C1=F → 判定 = F
- 结论：C1 变化导致了判定变化 ✅

**证明 C2 (amount > 100) 独立影响：**
- 固定 C1 = T（即 `isVIP` 为真）
- C2=T → 判定 = T；C2=F → 判定 = F
- 结论：C2 变化导致了判定变化 ✅

**最小用例集（3个）：**

| 用例ID | isVIP | amount | C1 | C2 | 判定 | 用途 |
|-------|-------|--------|----|----|------|------|
| TC-1 | true | 200 | T | T | T | 基准用例 |
| TC-2 | false | 200 | F | T | F | 证明 C1 独立 |
| TC-3 | true | 50 | T | F | F | 证明 C2 独立 |

```text
MC/DC 覆盖率 = 满足 ✅（只需 3 个用例，而非条件组合的 4 个）
```

> 🎯 **MC/DC 的核心价值**：用 n+1 个用例（而非 2ⁿ 个），达到接近条件组合覆盖的测试质量。在航空/医疗等安全关键领域是硬性要求。

### 6.8 各覆盖准则综合对比表

| 覆盖准则 | 本示例所需用例数 | 用例数公式 (n=条件数) | 覆盖强度 | 能否发现 `&&` 写成 `||` | 实践中是否推荐 |
|---------|---------------|---------------------|---------|----------------------|--------------|
| **语句覆盖** | 1 | — | ⭐ | ❌ 不能 | ❌ 太弱，不推荐单独使用 |
| **分支覆盖** | 2 | n+1 | ⭐⭐ | 部分能（取决于输入） | ✅ 最低推荐标准 |
| **条件覆盖** | 2 | n+1 | ⭐⭐ | 部分能 | ⚠️ 需配合分支覆盖 |
| **条件组合覆盖** | 4 | 2ⁿ | ⭐⭐⭐⭐ | ✅ 能 | ⚠️ 仅关键模块 |
| **MC/DC** | 3 | n+1 | ⭐⭐⭐ | ✅ 能 | ✅ 安全关键系统必须 |
| **路径覆盖** | 2 | — | ⭐⭐⭐⭐⭐ | ✅ 能 | ❌ 实际不可行 |

## 7. 圈复杂度 (Cyclomatic Complexity)

### 7.1 定义

圈复杂度（Cyclomatic Complexity, CC）由 Thomas McCabe 于 1976 年提出，用于度量程序的**逻辑复杂性**。圈复杂度越高，代码越复杂，需要的测试用例越多。

### 7.2 三种等价的计算公式

| 公式 | 说明 | 适用场景 |
|------|------|---------|
| **V(G) = 判定节点数 + 1** | 最常用，直观 | 快速估算 |
| **V(G) = E - N + 2** | 基于控制流图 | 严格计算 |
| **V(G) = R + 1** | R = 封闭区域数 | 图论视角 |

**判定节点包括**：`if`、`else if`、`for`、`while`、`do-while`、`case`、`catch`、`&&`、`||`、`?:`（三元运算符）

### 7.3 计算示例

```java
public String checkAccess(int age, boolean isVIP, boolean isHoliday) {
    // V(G) = 1（起始值）
    String result = "denied";

    if (age >= 18) {            // 第1个判定节点
        result = "allowed";
    }

    if (isVIP && isHoliday) {    // 第2个判定节点（复合条件整体算一个节点）
        result = "VIP_ACCESS";
    }

    return result;
}
```

**计算**：
- **方法一**：V(G) = 判定节点数(2) + 1 = **3**
- **方法二**：V(G) = 边数(7) - 节点数(6) + 2 = **3**
- **方法三**：V(G) = 封闭区域数(2) + 1 = **3**

> 💡 圈复杂度 V(G) = 3 意味着至少需要 **3 个测试用例**才能达到 100% 分支覆盖。

### 7.4 更多计算示例

| 代码结构 | 判定节点数 | V(G) |
|---------|-----------|------|
| 无分支的顺序代码 | 0 | 1 |
| 一个 if-else | 1 | 2 |
| if-else + 循环 | 2 | 3 |
| if-else + 循环 + switch(3个case) | 5 | 6 |
| 嵌套三层 if | 3 | 4 |
| 多个 `&&` 或 `||`（每个算一个判定节点） | n | n+1 |

### 7.5 圈复杂度与测试用例数的关系

| 覆盖准则 | 用例数与 V(G) 的关系 |
|---------|-------------------|
| **语句覆盖** | 最少需要 1 个用例，最多 ≤ V(G) 个 |
| **分支覆盖** | **最少需要 V(G) 个用例** — McCabe 指出分支覆盖的下限就是 V(G) |
| **路径覆盖** | 可能远大于 V(G)，在循环结构中可能无限 |

### 7.6 圈复杂度的参考标准

| V(G) | 风险等级 | 说明 | 建议 |
|:----:|---------|------|------|
| 1 ~ 5 | 🟢 低风险 | 代码简单，易于测试 | 保持 |
| 6 ~ 10 | 🟡 中风险 | 需要关注 | 代码评审时重点关注 |
| 11 ~ 20 | 🟠 高风险 | 代码复杂 | **建议重构**，提取子方法 |
| 21 ~ 50 | 🔴 极高风险 | 非常复杂 | 必须重构 |
| > 50 | ☠️ 不可测 | 几乎无法测试 | 彻底重写 |

### 7.7 降低圈复杂度的方法

```java
// 重构前：V(G) = 6（5个判定节点 + 1）
public double calculatePrice(String userType, double amount, boolean isHoliday) {
    double finalPrice = amount;
    if ("VIP".equals(userType)) {
        if (amount > 100) {
            if (isHoliday) {
                finalPrice = amount * 0.7;
            } else {
                finalPrice = amount * 0.8;
            }
        } else {
            finalPrice = amount * 0.95;
        }
    } else if ("NORMAL".equals(userType)) {
        if (amount > 200) {
            finalPrice = amount * 0.9;
        }
    }
    return finalPrice;
}

// 重构后：V(G) = 2（提取策略模式，每个方法只负责一个逻辑）
public double calculatePrice(String userType, double amount, boolean isHoliday) {
    DiscountStrategy strategy = DiscountStrategyFactory.getStrategy(userType);
    return strategy.apply(amount, isHoliday);
}
```

## 8. MC/DC：修正条件判定覆盖

### 8.1 起源与标准

MC/DC（Modified Condition / Decision Coverage）由航空安全标准 **DO-178B/C** 正式提出，是**安全关键系统（Safety-Critical Systems）** 的硬性要求。

| 软件等级 | 失效后果 | 覆盖要求 | 典型系统 |
|---------|---------|---------|---------|
| **Level A** | 灾难性（导致坠机） | **MC/DC** | 飞控系统、发动机控制 |
| **Level B** | 严重（可能伤害） | 条件组合覆盖 | 导航系统、防撞系统 |
| **Level C** | 较大（影响任务） | 分支覆盖 | 客舱管理系统 |
| **Level D** | 较小（不影响安全） | 语句覆盖 | 娱乐系统 |
| **Level E** | 无影响 | 无要求 | 日志系统 |

### 8.2 MC/DC 的四条要求

1. **每个入口和出口至少被执行一次** — 等价于语句覆盖
2. **每个判定的所有可能结果至少取一次** — 等价于分支覆盖
3. **每个条件的所有可能结果至少取一次** — 等价于条件覆盖
4. **每个条件都能独立地影响判定结果** — MC/DC 的核心要求

**"独立影响"的严格定义：**
> 存在一组测试用例，在该组中改变条件 C 的值（其他所有条件不变），判定结果随之改变。

### 8.3 MC/DC 的用例生成过程（3个条件的详细演示）

```java
// 场景：三个条件组合
// 判定 D = C1 && C2 && C3
// 例如：if (isVIP && amount > 100 && isHoliday)
```

**步骤1：构建全真值表（2³ = 8 行）**

| # | C1 | C2 | C3 | D = C1 && C2 && C3 |
|---|----|----|----|-------------------|
| 1 | T | T | T | **T** |
| 2 | T | T | F | **F** |
| 3 | T | F | T | **F** |
| 4 | T | F | F | F |
| 5 | F | T | T | **F** |
| 6 | F | T | F | F |
| 7 | F | F | T | F |
| 8 | F | F | F | F |

**步骤2：为每个条件寻找"独立对"**

条件 C1 的独立对：C1 变化时，判定结果变化
- 行1 (T,T,T)→D=T vs 行5 (F,T,T)→D=F ✅（C2=C3=T保持不变，C1变化导致D变化）

条件 C2 的独立对：C2 变化时，判定结果变化
- 行1 (T,T,T)→D=T vs 行3 (T,F,T)→D=F ✅（C1=C3=T保持不变，C2变化导致D变化）

条件 C3 的独立对：C3 变化时，判定结果变化
- 行1 (T,T,T)→D=T vs 行2 (T,T,F)→D=F ✅（C1=C2=T保持不变，C3变化导致D变化）

**步骤3：合并为最小用例集**

| 用例 | C1 | C2 | C3 | D | 覆盖的独立对 |
|------|----|----|----|---|-------------|
| TC-1 | T | T | T | T | 基准用例 |
| TC-2 | F | T | T | F | 证明 C1 独立 |
| TC-3 | T | F | T | F | 证明 C2 独立 |
| TC-4 | T | T | F | F | 证明 C3 独立 |

```text
MC/DC 所需用例数 = n + 1 = 3 + 1 = 4
条件组合覆盖所需用例数 = 2ⁿ = 8

节省了 50% 的用例！
```

### 8.4 MC/DC vs 条件组合覆盖对比

| 维度 | MC/DC | 条件组合覆盖 |
|------|-------|------------|
| 用例数 | **n + 1** | **2ⁿ** |
| n=3时用例数 | 4 | 8 |
| n=5时用例数 | 6 | 32 |
| n=10时用例数 | 11 | 1024 |
| 覆盖质量 | 接近条件组合 | 完全覆盖 |
| 实际可行性 | ✅ 可行 | ❌ n>5时不可行 |

> 🎯 **MC/DC 的战略意义**：当条件数量较多时（n > 5），条件组合覆盖的 2ⁿ 用例数变得不可接受，而 MC/DC 的 n+1 增长是线性的，是用最少用例达到高覆盖质量的最佳选择。

### 8.5 MC/DC 在 Java 中的实践

| 工具 | 说明 | MC/DC 支持 |
|------|------|-----------|
| **JaCoCo** | 最常用的 Java 覆盖率工具 | 0.8.8+ 支持 MC/DC |
| **CodeCover** | 开源 Java 覆盖率工具 | 支持 |
| **BullseyeCoverage** | 商业 C/C++ 工具 | 支持 |
| **RTRT (Rational Test RealTime)** | IBM 工具 | 支持 |

> ⚠️ **实际建议**：除非你在做航空、高铁、医疗设备或核电站控制软件，否则不需要追求 MC/DC 100%。对于大多数业务系统，**分支覆盖 80%~90% + 核心模块条件组合覆盖**就已经是非常好的水平。

## 9. 灰盒测试

### 9.1 定义

灰盒测试（Gray-Box Testing）介于黑盒测试和白盒测试之间——测试人员**了解部分内部结构**（如数据库表结构、API 协议、架构分层），但**不深入代码细节**。

```text
黑盒 ────── 灰盒 ────── 白盒
  ↑           ↑           ↑
纯功能   了解内部结构   深入代码逻辑
不看代码  (但不看代码)  逐行分析代码
```

### 9.2 灰盒测试关注什么

| 关注点 | 说明 | 示例 |
|--------|------|------|
| **数据库结构** | 表关系、索引、约束 | 测试完数据是否落到了正确的表 |
| **接口协议** | API 请求/响应结构 | 验证接口返回的 JSON 字段 |
| **架构设计** | 模块间依赖和通信 | 调用链是否正确 |
| **日志/监控** | 关键路径是否有日志 | 异常时是否有错误日志输出 |
| **配置项** | 配置对行为的影响 | 切换 feature flag 后的行为变化 |

### 9.3 灰盒测试的典型代码场景

```java
// 黑盒视角：输入 userId → 输出 orderList
// 灰盒视角：知道背后会查询 orders 表，知道有缓存层，知道会调用用户服务

@Test
void testGetUserOrders_ShouldQueryDatabase() {
    // 灰盒：已知数据库结构，直接验证SQL正确性
    List<Order> orders = orderService.getOrdersByUserId(1001);

    assertThat(orders)
        .hasSize(3)
        .allMatch(o -> o.getUserId() == 1001);

    // 灰盒验证：确认SQL执行次数（防止N+1查询问题）
    assertThat(sqlMonitor.getQueryCount("orders")).isLessThan(2);
}

@Test
void testGetUserOrders_ShouldUseCache() {
    // 灰盒：已知缓存架构，验证缓存命中
    List<Order> firstCall = orderService.getOrdersByUserId(1001);
    List<Order> secondCall = orderService.getOrdersByUserId(1001);

    // 第二次调用不应查数据库
    assertThat(sqlMonitor.getQueryCount("orders")).isEqualTo(1);
}
```

### 9.4 灰盒测试的优缺点

| 优点 | 缺点 |
|------|------|
| 结合了黑盒和白盒的优势 | 需要了解系统内部，入门成本比黑盒高 |
| 能发现黑盒发现不了的数据问题 | 可能忽略某些黑盒用户视角的问题 |
| 比白盒成本低（不需要逐行看代码） | 不如白盒精确（不知道具体的代码路径） |
| 特别适合集成测试和 API 测试 | 对测试人员的技术要求较高 |

### 9.5 灰盒测试的典型应用场景

| 场景 | 说明 | 为什么是灰盒而不是黑白 |
|------|------|---------------------|
| **集成测试** | 验证模块间交互 | 需要知道接口协议（灰），但不需看每个模块内部（白） |
| **数据库测试** | 验证CRUD和数据完整性 | 需要知道表结构（灰），但不需看DAO实现代码（白） |
| **API 测试** | 验证接口正确性 | 需要知道请求/响应格式（灰），但不需看具体业务逻辑（白） |
| **性能测试** | 定位性能瓶颈 | 需要知道架构分层（灰），但不需逐行分析（白） |
| **安全渗透测试** | 发现安全漏洞 | 需要了解系统架构（灰），结合黑盒攻击手法 |

## 10. 黑盒 vs 白盒 vs 灰盒：如何选择

### 10.1 三者的核心区别

| 维度 | 黑盒测试 | 白盒测试 | 灰盒测试 |
|------|---------|---------|---------|
| **对代码的了解** | 不需要 | 深入（逐行看） | 部分（架构/接口/数据） |
| **被测对象** | 功能/系统/用户界面 | 代码/方法/类 | 组件/服务/模块接口 |
| **主要执行者** | 测试工程师 | 开发工程师 | 测试 + 开发 |
| **测试阶段** | 系统测试、验收测试 | 单元测试 | 集成测试 |
| **覆盖度量** | 需求覆盖（功能点） | 代码覆盖（语句/分支） | 接口覆盖 |
| **用例来源** | 需求文档、用户故事 | 源代码、流程图 | 架构设计、接口文档 |
| **主要技术** | 等价类、边界值、判定表 | 语句/分支/路径/条件覆盖 | 数据验证、接口测试 |
| **成本** | 低 | 高 | 中 |
| **发现缺陷类型** | 功能缺失、逻辑遗漏 | 死代码、分支遗漏 | 数据问题、接口兼容性 |

### 10.2 按测试阶段推荐

| 测试阶段 | 推荐方法 | 理由 |
|---------|---------|------|
| **单元测试** | **白盒** | 关注代码逻辑正确性，需要高覆盖率 |
| **集成测试** | **灰盒** | 关注模块间交互，需要了解接口和数据流 |
| **系统测试** | **黑盒** | 关注端到端功能，从用户视角验证 |
| **验收测试** | **黑盒** | 用户只关心功能，不关心代码实现 |
| **性能测试** | **灰盒** | 需要了解架构以便定位瓶颈 |
| **安全测试** | 白盒 + 黑盒 | 白盒找代码漏洞，黑盒找攻击面 |
| **回归测试** | **黑盒**(自动化) | 快速验证已有功能是否正常 |
| **兼容性测试** | **黑盒** | 只看表现在不同环境下的展示 |

### 10.3 按项目类型推荐

| 项目类型 | 重点测试方法 | 参考覆盖率目标 |
|---------|------------|--------------|
| **业务系统（ERP/CRM）** | 黑盒为主，单元测试用白盒 | 分支覆盖 ≥ 80%，功能点覆盖 100% |
| **金融系统（交易/结算）** | 白盒 + 黑盒并重 | 分支覆盖 ≥ 90%，核心模块条件组合覆盖 |
| **安全关键系统（航空/医疗）** | 白盒为主（MC/DC 必须） | MC/DC 100%（Level A） |
| **中间件/工具库/SDK** | 白盒为主 | 分支覆盖 ≥ 90%，方法覆盖 ≥ 95% |
| **移动App** | 黑盒（UI） + 灰盒（API） | 功能点覆盖 100%，接口覆盖 100% |
| **微服务架构** | 灰盒（契约测试） + 黑盒（E2E） | 接口覆盖 100%，消费者契约通过率 100% |
| **Web 前端** | 黑盒为主 + 少量白盒 | 页面元素覆盖率 ≥ 85% |

### 10.4 测试金字塔中的角色

```text
         ┌───────────┐
         │   E2E     │  ← 黑盒测试（系统级别）
         │   ~5%     │     等价类、边界值、场景法
        ┌┴───────────┴┐
        │  集成测试    │  ← 灰盒测试（组件级别）
        │   ~20%      │     接口契约、数据流验证
       ┌┴─────────────┴┐
       │   单元测试     │  ← 白盒测试（代码级别）
       │    ~75%       │     语句覆盖、分支覆盖
       └───────────────┘
```

> 💡 **不同层级用不同的"盒子"**：
> - **塔底（单元测试）**：**白盒** — 开发人员编写，追求代码覆盖率
> - **塔中（集成测试）**：**灰盒** — 关注模块间交互和数据流
> - **塔顶（E2E测试）**：**黑盒** — 模拟真实用户操作

### 10.5 最佳实践：三者结合构建质量护城河

```text
                        目标：100% 功能覆盖
                        ┌─────────────────────────────┐
        黑盒测试        │  ✔ 所有用户故事都测试通过    │

                        └───────────┬─────────────────┘
                                    │
         灰盒测试       ┌───────────▼─────────────────┐
(集成测试/API测试)      │  ✔ 所有模块接口正常交互      │
                        │  ✔ 数据流转正确,无丢失      │
                        └───────────┬─────────────────┘
                                    │
         白盒测试       ┌───────────▼─────────────────┐
(单元测试)             │  ✔ 分支覆盖 ≥ 80%            │
                        │  ✔ 核心模块条件组合覆盖      │
                        │  ✔ 无死代码,无逻辑缺陷       │
                        └─────────────────────────────┘
```

### 10.6 选择原则总结

```text
方法选择的黄金法则：

  越靠近用户 → 越黑盒    (系统测试、验收测试 → 等价类、场景法)
  越靠近代码 → 越白盒    (单元测试 → 分支覆盖、条件覆盖)
  两者之间   → 灰盒      (集成测试 → 接口覆盖、数据验证)

质量目标 = 黑盒(功能正确) + 白盒(代码正确) + 灰盒(集成正确)
```

> 🎯 **不要纠结于"黑盒好还是白盒好"**。**黑盒测试保证"做对了事情"（验证功能需求），白盒测试保证"事情做对了"（确保代码质量）。** 两者结合，再加上灰盒测试作为桥梁，才是一个完整的测试质量保障体系。

---

## 总结

| 测试方法 | 一句话总结 |
|---------|-----------|
| **黑盒测试** | 不关心代码，从用户视角验证功能，用等价类/边界值/判定表/场景法设计用例 |
| **白盒测试** | 深入代码，用语句/分支/条件/MC/DC/路径等覆盖准则度量测试充分性 |
| **灰盒测试** | 介于黑白之间，了解架构和数据但不过问具体代码实现 |

| 关键概念 | 核心要点 |
|---------|---------|
| **语句覆盖** | 最弱，只需所有语句执行一次 |
| **分支覆盖** | 每个判定的 T/F 分支都走到，推荐最低标准 |
| **条件覆盖** | 每个原子条件取 T/F，注意：不保证分支覆盖 |
| **条件组合覆盖** | 所有条件组合都覆盖，但用例数 2ⁿ 指数爆炸 |
| **MC/DC** | n+1 个用例达到接近条件组合的质量，安全关键系统必须 |
| **路径覆盖** | 理论上最强，实际几乎不可行 |
| **圈复杂度 V(G)** | V(G)=判定节点数+1，分支覆盖最少需要 V(G) 个用例，V(G)>10 建议重构 |
