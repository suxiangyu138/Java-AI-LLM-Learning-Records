## 1. K8s存储体系概述

K8s存储体系分为三个层次，从底层Volume到顶层动态存储供应：

```
                    ┌─────────────────────────────────┐
                    │     StorageClass (动态供应)      │
                    │  provisioner: kubernetes.io/nfs  │
                    └──────────────┬──────────────────┘
                                   │ 自动创建
                    ┌──────────────▼──────────────────┐
                    │       PV (集群存储资源)           │
                    │  容量: 10Gi / 访问模式: RWO      │
                    └──────────────┬──────────────────┘
                                   │ 绑定
                    ┌──────────────▼──────────────────┐
                    │     PVC (用户存储申请)            │
                    │  "我要5GB ReadWriteOnce存储"     │
                    └──────────────┬──────────────────┘
                                   │ 挂载
                    ┌──────────────▼──────────────────┐
                    │     Volume (Pod内的挂载点)        │
                    │   emptyDir / hostPath / nfs     │
                    └─────────────────────────────────┘
```

| 层次 | 管理方 | 生命周期 | 类似概念 |
|------|--------|----------|----------|
| Volume | 开发者 | Pod生命周期内 | Docker的mount bind / volume |
| PV | 集群管理员 | 独立于Pod | 云硬盘 / 物理磁盘 |
| PVC | 开发者 | 绑定到Pod | "申请单" |
| StorageClass | 集群管理员 | 永久 | 云存储模板（AWS EBS / GCE PD） |

> 💡 理解K8s存储的核心：**Pod是瞬态的，数据必须脱离Pod存在**。Volume把外部存储"接入"Pod内部，PV/PVC把存储声明与存储资源解耦。

## 2. Volume类型速查

K8s支持超过20种Volume类型，以下是生产中最常用的：

| Volume类型 | 存储位置 | 生命周期 | 典型用途 | 持久化 |
|------------|----------|----------|----------|--------|
| `emptyDir` | Pod宿主机临时目录 | Pod生命周期 | 日志缓存、共享临时数据 | ❌ |
| `hostPath` | 宿主机指定目录 | 宿主机生命周期 | 读取宿主机数据（谨慎） | ✅（但Pod漂移失效） |
| `nfs` | NFS服务器 | 独立于集群 | 共享存储（ReadWriteMany） | ✅ |
| `cephfs` | Ceph集群 | 独立于集群 | 高性能分布式存储 | ✅ |
| `configMap` | K8s API | ConfigMap生命周期 | 配置文件注入 | ❌ |
| `secret` | K8s API | Secret生命周期 | 敏感信息注入 | ❌ |
| `pvc` | 后端存储（云盘/NFS等） | 独立于Pod | **生产首选持久化方案** | ✅ |
| `hostPath`（谨慎） | 宿主机 | 宿主机生命周期 | 临时调试 | ⚠️ 部分 |
| `local` | 本地磁盘 | 节点生命周期 | 高性能本地存储（LocalSSD） | ⚠️ 受节点约束 |

> ⚠️ **hostPath的致命问题**：Pod被调度到不同节点后数据丢失！生产环境仅适合DaemonSet（如监控Agent读取宿主机`/var/log`），**不要**用于数据库等有状态应用。

## 3. emptyDir — Pod生命周期临时存储

### 3.1 核心特性

`emptyDir`是最简单的Volume类型：Pod创建时分配空目录，Pod删除时目录被清除。

> 💡 emptyDir的典型使用场景：Sidecar容器从主容器读取日志文件，sidecar将日志转发到集中日志系统。

### 3.2 基础示例：两个容器共享日志

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: log-pod
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: log-volume
      mountPath: /var/log/nginx
  - name: sidecar-logger
    image: busybox
    command: ["sh", "-c", "tail -f /logs/access.log"]
    volumeMounts:
    - name: log-volume
      mountPath: /logs
  volumes:
  - name: log-volume
    emptyDir:
      sizeLimit: 500Mi  # ⭐ K8s 1.20+ 支持限制emptyDir大小
```

### 3.3 emptyDir的存储介质

```yaml
volumes:
- name: fast-volume
  emptyDir:
    medium: Memory   # 使用tmpfs（内存），极快但占用RAM
    sizeLimit: 100Mi
```

| medium | 存储介质 | 性能 | 适用场景 |
|--------|----------|------|----------|
| 空（默认） | 磁盘（Pod所在节点） | 普通 | 通用临时存储 |
| `Memory` | tmpfs（RAM） | 极高 | 高性能临时缓存、共享内存 |

> ⚠️ emptyDir使用Memory模式时，数据占用的是Pod的**内存配额**（`resources.limits.memory`），超大emptyDir会导致Pod被OOM Kill！

## 4. hostPath — 宿主机挂载

### 4.1 基础示例

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hostpath-pod
spec:
  containers:
  - name: test
    image: nginx
    volumeMounts:
    - name: host-log
      mountPath: /host-log
  volumes:
  - name: host-log
    hostPath:
      path: /var/log  # 宿主机路径
      type: Directory  # 类型校验
```

### 4.2 hostPath类型及用途

| type值 | 行为 | 用途 |
|--------|------|------|
| `DirectoryOrCreate` | 目录不存在时自动创建 | 数据采集Agent |
| `Directory` | 目录必须存在 | 读取固定日志目录 |
| `FileOrCreate` | 文件不存在时自动创建 | 写入锁文件 |
| `File` | 文件必须存在 | 读取宿主机配置 |
| `Socket` | Unix socket必须存在 | Docker socket挂载 |

### 4.3 生产建议

> ⚠️ hostPath仅推荐以下场景：**DaemonSet + 监控/日志采集**（如Filebeat读取宿主机日志），**不得**用于数据库或业务数据持久化。原因：Pod重建可能调度到不同节点 → 数据丢失。

```yaml
# ✅ 可接受的使用场景：DaemonSet采集日志
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
spec:
  template:
    spec:
      containers:
      - name: fluentd
        volumeMounts:
        - name: varlog
          mountPath: /var/log
        - name: docker-containers
          mountPath: /var/lib/docker/containers
          readOnly: true
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
      - name: docker-containers
        hostPath:
          path: /var/lib/docker/containers
```

## 5. PV与PVC — 持久化存储标准方案

### 5.1 核心概念

| 概念 | 角色 | 描述 | 类比 |
|------|------|------|------|
| **PV** (PersistentVolume) | 管理员 | 集群级存储资源，独立于任何Pod | 物理硬盘 / 云硬盘 |
| **PVC** (PersistentVolumeClaim) | 开发者 | 用户对存储的请求（容量+模式） | "我要买500GB的SSD" |
| **StorageClass** | 管理员 | 动态PV创建模板 | "这是AWS EBS的SSD套餐" |

### 5.2 PV与PVC的工作流程

```
                    ┌──────────────┐
                    │  管理员创建PV  │  ← 静态供应
                    │  10Gi, RWO   │
                    └──────┬───────┘
                           │ 等待绑定
    ┌──────────────┐       │       ┌──────────────────┐
    │  开发者创建PVC  ├──────┼──────►│  PVC与PV匹配绑定   │
    │  8Gi, RWO     │      │       │  (容量+模式+Class) │
    └──────────────┘       │       └────────┬─────────┘
                           │                │
                    ┌──────▼───────┐        ▼
                    │ StorageClass  │  ┌─────────────────┐
                    │ 动态创建PV    │  │  Pod使用PVC挂载   │
                    │ (动态供应)    │  │  volumes[].pvc   │
                    └──────────────┘  └─────────────────┘
```

### 5.3 PV完整示例

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs-001
  labels:
    type: nfs
spec:
  capacity:
    storage: 10Gi                     # ⭐ 容量
  accessModes:                        # ⭐ 访问模式
    - ReadWriteOnce                   # 单节点读写
    - ReadOnlyMany                    # 多节点只读
  persistentVolumeReclaimPolicy: Retain  # ⭐ 回收策略
  storageClassName: slow              # ⭐ 关联StorageClass
  nfs:
    server: 192.168.1.100
    path: /data/k8s-volume
```

### 5.4 PVC完整示例

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
  namespace: production
spec:
  accessModes:                        # 需要的访问模式
    - ReadWriteOnce
  resources:
    requests:
      storage: 8Gi                    # 申请8GB
  storageClassName: slow              # 匹配PV的Class
  selector:                           # 额外标签选择器（可选）
    matchLabels:
      type: nfs
```

### 5.5 PV与PVC绑定机制

PV与PVC的绑定是**一对一**的，一旦绑定，该PV不能再被其他PVC使用。

绑定匹配条件（**三个条件必须同时满足**）：

| 条件 | 说明 | 示例 |
|------|------|------|
| **容量匹配** | PVC请求容量 ≤ PV容量 | PVC 8Gi → PV 10Gi（✅），PVC 10Gi → PV 8Gi（❌） |
| **访问模式匹配** | PVC模式必须在PV的accessModes列表中 | PVC需要RWO，PV支持RWO+ROX（✅） |
| **StorageClass匹配** | `storageClassName`必须一致或PVC不指定Class | 都指定`slow`（✅），PVC不指定而PV也不指定（✅） |

> 💡 PVC会优先绑定最"合适"的PV（容量最接近但又不小于需求的PV）。如果找不到匹配的PV，PVC会保持`Pending`状态等待新的PV创建。

### 5.6 访问模式

| 模式 | 缩写 | 说明 | 典型后端 |
|------|------|------|----------|
| `ReadWriteOnce` | RWO | 单节点读写（**最常用**） | AWS EBS、GCE PD、Azure Disk |
| `ReadOnlyMany` | ROX | 多节点只读 | NFS、CephFS、AWS EFS |
| `ReadWriteMany` | RWX | 多节点读写 | NFS、CephFS、AWS EFS、GlusterFS |
| `ReadWriteOncePod` | RWOP | 单Pod读写（K8s 1.22+） | CSI驱动 |

> ⚠️ **常见陷阱**：AWS EBS只支持RWO，但很多人误以为它可以多节点共享！需要多Pod共享读写时必须用EFS或NFS。MySQL等数据库单节点写入用RWO即可，**不要**试图用RWX跑数据库。

### 5.7 回收策略

当PVC被删除后，PV的回收策略决定了数据如何处理：

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| **Retain**（保留） | PV进入`Released`状态，**数据保留**，需管理员手动清理 | 生产数据库、重要数据 |
| **Delete**（删除） | PV和后端存储**一并删除** | 自动管理的云盘，无需操心清理 |
| **Recycle**（已弃用） | PV数据被清空（`rm -rf /volume/*`），然后可被重新使用 | K8s 1.15后已弃用，被Dynamic Provisioning取代 |

```yaml
# Retain策略的PV — 安全第一
apiVersion: v1
kind: PersistentVolume
metadata:
  name: critical-data-pv
spec:
  capacity:
    storage: 50Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain  # 删除PVC后保留数据
  nfs:
    server: 192.168.1.100
    path: /data/mysql-backup
```

### 5.8 在Pod中使用PVC

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: storage-consumer
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: data
      mountPath: /usr/share/nginx/html  # PVC挂载到容器路径
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: my-pvc                # 引用PVC名称
      readOnly: false                  # 是否只读挂载
```

## 6. StorageClass — 动态存储供应

### 6.1 为什么需要StorageClass？

没有StorageClass时，管理员需要手动创建PV → 开发者创建PVC → 绑定。当PV用尽时，开发者无法创建新的PVC（Pending）。

StorageClass实现了**动态供应**：开发者在PVC中指定StorageClass，系统自动创建对应的PV和后端存储。

### 6.2 StorageClass示例

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs    # ⭐ 存储供应商
parameters:
  type: gp3                           # AWS gp3 SSD
  fsType: ext4
  iopsPerGB: "10"
reclaimPolicy: Delete                 # ⭐ 动态创建的PV默认回收策略
allowVolumeExpansion: true            # ⭐ 允许在线扩容
mountOptions:
  - discard                           # trim优化
```

### 6.3 常见StorageClass供应商

| Provisioner | 云平台 | 典型参数 | 访问模式 |
|-------------|--------|----------|----------|
| `kubernetes.io/aws-ebs` | AWS | type=gp3/i1, fsType=ext4 | RWO |
| `kubernetes.io/gce-pd` | GCP | type=pd-ssd, replication-type=none | RWO |
| `kubernetes.io/azure-disk` | Azure | skuName=Premium_LRS | RWO |
| `kubernetes.io/azure-file` | Azure | skuName=Standard_LRS | RWX |
| `kubernetes.io/nfs` | 自建NFS | server, path | RWO / ROX / RWX |
| `k8s.io/minikube-hostpath` | Minikube | type=Directory | RWO |
| `ceph.com/cephfs` | Ceph | monitors, adminId, adminSecretName | RWX |
| `rook-ceph.rbd.csi.ceph.com` | Rook/Ceph | clusterID, pool | RWO |

### 6.4 PVC使用动态供应

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: dynamic-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
  storageClassName: fast-ssd           # ⭐ 引用StorageClass → 自动创建PV
```

> 💡 如果PVC不指定`storageClassName`，集群使用默认StorageClass（`kubectl get storageclass`中标记为`(default)`的那个）。每个集群通常有一个默认StorageClass，如托管K8s集群默认使用云厂商SSD。

### 6.5 在线扩容

K8s 1.11+支持PVC在线扩容（需要StorageClass开启`allowVolumeExpansion: true`）：

```bash
# 直接修改PVC的storage大小
kubectl edit pvc dynamic-pvc
# 修改: resources.requests.storage: 20Gi → 30Gi
```

> ⚠️ 在线扩容需要后端存储支持（如AWS EBS支持扩容），且挂载该PVC的Pod可能需要重启才能识别新容量。

## 7. StatefulSet持久化 — volumeClaimTemplates

### 7.1 为什么需要volumeClaimTemplates？

Deployment的所有Pod共享同一个存储模板，但**StatefulSet的有状态应用（如MySQL集群、Elasticsearch）需要每个Pod拥有独立的持久化存储**。

`volumeClaimTemplates`为StatefulSet中**每个Pod自动创建独立的PVC**，命名格式为：`<volumeClaimTemplate名称>-<Pod名称>`。

### 7.2 volumeClaimTemplates机制

```
StatefulSet: mysql-cluster
  ├── mysql-cluster-0 → PVC: data-mysql-cluster-0  → PV-1
  ├── mysql-cluster-1 → PVC: data-mysql-cluster-1  → PV-2
  └── mysql-cluster-2 → PVC: data-mysql-cluster-2  → PV-3

Pod重建后→ 使用相同PVC名 → 数据恢复！
```

> 🎯 **关键特性**：StatefulSet的Pod有稳定的标识（`statefulset_name-index`），即使Pod被删除重建，新Pod会绑定到**同一个PVC**，数据完好无损。这是有状态应用在K8s运行的基石。

### 7.3 基础示例

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: "nginx"
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:                # ⭐ 为每个Pod创建独立PVC
  - metadata:
      name: www
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 1Gi
      storageClassName: standard
```

## 8. SpringBoot应用存储实践

### 8.1 存储需求分析

SpringBoot应用在K8s中通常涉及三类存储需求：

| 存储内容 | 推荐方案 | 说明 |
|----------|----------|------|
| 日志文件 (logs/) | emptyDir | Pod重启即丢弃，通过Sidecar采集到ELK/Loki |
| 上传文件 (uploads/) | PVC (RWO) | 需要持久化，单副本用RWO |
| 共享文件 (public/) | PVC (RWX + NFS) | 多副本共享，需NFS/EFS后端 |
| 配置文件 (application.yml) | ConfigMap | 非敏感配置，见[05-ConfigMap与Secret](../05-ConfigMap与Secret.md) |
| 数据库密码 | Secret | 敏感信息挂载 |
| 临时缓存 (temp/) | emptyDir + Memory模式 | 高性能临时缓存 |

### 8.2 日志用emptyDir + Sidecar采集

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: user-service
        image: user-service:latest
        volumeMounts:
        - name: log-volume
          mountPath: /app/logs
      # Sidecar容器：采集日志到集中日志系统
      - name: filebeat
        image: docker.elastic.co/beats/filebeat:8.10.0
        volumeMounts:
        - name: log-volume
          mountPath: /app/logs
          readOnly: true
      volumes:
      - name: log-volume
        emptyDir:
          sizeLimit: 1Gi
```

### 8.3 文件上传用PVC

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: file-service
spec:
  replicas: 2  # ⚠️ 如果是RWO的PVC副本只能设为1
  template:
    spec:
      containers:
      - name: file-service
        image: file-service:latest
        env:
        - name: UPLOAD_DIR
          value: /app/uploads
        volumeMounts:
        - name: upload-storage
          mountPath: /app/uploads
      volumes:
      - name: upload-storage
        persistentVolumeClaim:
          claimName: file-upload-pvc
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: file-upload-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 50Gi
  storageClassName: fast-ssd
```

> ⚠️ 如果Deployment需要多副本共享上传文件，必须使用支持RWX的存储后端（NFS/CephFS/EFS），否则只有第一个Pod能挂载成功。

## 9. 完整示例：MySQL StatefulSet + PVC持久化

以下是一个生产级MySQL单实例的StatefulSet配置，涵盖PVC自动创建、配置注入、安全凭证、健康检查：

### 9.1 完整YAML

```yaml
---
# 1. Secret：数据库密码
apiVersion: v1
kind: Secret
metadata:
  name: mysql-secret
type: Opaque
data:
  root-password: cm9vdDEyMzQ1Ng==  # root123456的base64
  user-password: dXNlcnAxMjM0NTY=  # userp123456的base64

---
# 2. ConfigMap：MySQL配置
apiVersion: v1
kind: ConfigMap
metadata:
  name: mysql-config
data:
  my.cnf: |
    [mysqld]
    character-set-server=utf8mb4
    collation-server=utf8mb4_unicode_ci
    max_connections=500
    innodb_buffer_pool_size=1G
    slow_query_log=1
    long_query_time=2

---
# 3. Service：Headless Service + 普通Service
apiVersion: v1
kind: Service
metadata:
  name: mysql
spec:
  ports:
  - port: 3306
    targetPort: 3306
  selector:
    app: mysql

---
apiVersion: v1
kind: Service
metadata:
  name: mysql-headless
spec:
  clusterIP: None                    # Headless Service
  ports:
  - port: 3306
  selector:
    app: mysql

---
# 4. StorageClass（假设使用NFS动态供应）
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: mysql-storage
provisioner: kubernetes.io/nfs
reclaimPolicy: Retain                # MySQL数据重要，用Retain

---
# 5. StatefulSet + volumeClaimTemplates
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-headless
  replicas: 1
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-secret
              key: root-password
        - name: MYSQL_DATABASE
          value: myapp
        - name: MYSQL_USER
          value: appuser
        - name: MYSQL_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-secret
              key: user-password
        ports:
        - containerPort: 3306
          name: mysql
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql   # ⭐ MySQL数据目录 → PVC
        - name: config
          mountPath: /etc/mysql/conf.d
        resources:
          requests:
            memory: "1Gi"
            cpu: "500m"
          limits:
            memory: "2Gi"
            cpu: "1000m"
        livenessProbe:
          exec:
            command: ["mysqladmin", "ping", "-u", "root", "-p$(MYSQL_ROOT_PASSWORD)"]
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          exec:
            command: ["mysql", "-u", "root", "-p$(MYSQL_ROOT_PASSWORD)", "-e", "SELECT 1"]
          initialDelaySeconds: 5
          periodSeconds: 5
      volumes:
      - name: config
        configMap:
          name: mysql-config
  volumeClaimTemplates:               # ⭐ 自动为每个Pod创建独立PVC
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]  # MySQL单节点写入
      resources:
        requests:
          storage: 20Gi               # 申请20GB
      storageClassName: mysql-storage
```

### 9.2 验证存储

```bash
# 查看创建的PVC（自动命名为data-mysql-0）
kubectl get pvc
# NAME           STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS
# data-mysql-0   Bound    pvc-a1b2c3d4-xxxx-xxxx-xxxx-xxxxxxxxxxxx   20Gi       RWO            mysql-storage

# 查看PV
kubectl get pv
# NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM
# pvc-a1b2c3d4-xxxx-xxxx-xxxx-xxxxxxxxxxxx   20Gi       RWO            Retain           Bound    default/data-mysql-0

# 模拟Pod删除重建 → 数据不丢

# 验证数据持久化

```

### 9.3 存储故障排查

| 现象 | 原因 | 排查命令 |
|------|------|----------|
| PVC一直Pending | PV不满足匹配条件，或StorageClass不存在 | `kubectl describe pvc <name>` |
| Pod挂载卷失败 | PVC未Bound，或后端存储不可达 | `kubectl describe pod <name>` |
| Pod被调度到错误节点 | hostPath存储但Pod漂移到其他节点 | `kubectl get pod -o wide` |
| 数据写入慢 | 后端存储性能不足（如NFS网络延迟） | `kubectl exec <pod> -- iostat -x 1` |
| PVC扩容无效 | StorageClass未启用`allowVolumeExpansion` | `kubectl describe sc <name>` |

---

> 🎯 **存储持久化核心要点**：emptyDir适合临时数据，hostPath仅用于监控/日志采集，PVC是生产环境持久化**标准方案**，StorageClass实现动态供应免去管理员手动创建PV的麻烦，StatefulSet + volumeClaimTemplates是K8s上有状态应用的**唯一正确姿势**。使用前先确认访问模式（RWO/RWX）和后端存储能力（AWS EBS不支持RWX！），这是K8s存储最常见的坑。
