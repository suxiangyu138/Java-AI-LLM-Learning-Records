## 1. 三种探针对比

| 探针 | 目的 | 失败后果 | 成功条件 |
|------|------|----------|----------|
| **Liveness** | 检测容器是否还"活着" | **重启容器** | 返回200 |
| **Readiness** | 检测容器是否准备好接收流量 | **从Service摘除** | 返回200 |
| **Startup** | 慢启动应用的初始检测 | **重启容器** | 返回200 |

```text
启动流程：
  ① Startup Probe → 成功 → 停止Startup，启动Liveness+Readiness
  ② Liveness Probe → 持续检测（挂了就重启）
  ③ Readiness Probe → 持续检测（没准备好就不给流量）

关键区分：
  Liveness失败 → KILL + RESTART（应用卡死/死锁）
  Readiness失败 → 摘除流量（应用暂时忙/依赖未就绪，等等就好）
```

> ⚠️ Liveness Probe 不要检查数据库连接！数据库暂时不可用→ Liveness失败→重启→还是连不上→重启循环。数据库连通性应放在Readiness Probe中。

## 2. 探针配置详解

### 2.1 三种检测方式

| 方式 | 配置 | 适用场景 |
|------|------|----------|
| **HTTP GET** | `httpGet: path: /health, port: 8080` | ✅ 推荐，Web应用首选 |
| **TCP Socket** | `tcpSocket: port: 8080` | 非HTTP应用（数据库、缓存） |
| **Exec命令** | `exec: command: ["check.sh"]` | 自定义检测逻辑 |

### 2.2 探针参数

```yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 30     # 容器启动后等多久才第一次检测
  periodSeconds: 15            # 每隔多久检测一次
  timeoutSeconds: 5            # 探测超时时间
  successThreshold: 1          # 连续成功几次才算成功
  failureThreshold: 3          # 连续失败几次才算失败
```

| 参数 | 含义 | 建议值 |
|------|------|:---:|
| `initialDelaySeconds` | 首次探测延迟 | ≥应用启动时间 |
| `periodSeconds` | 探测间隔 | 10-15s |
| `timeoutSeconds` | 探测超时 | 5s |
| `failureThreshold` | 失败几次标记为失败 | Liveness=3, Readiness=3 |
| `successThreshold` | 成功几次标记为健康 | 1 |

## 3. SpringBoot Actuator + K8s探针

### 3.1 依赖与配置

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

```yaml
# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health               # 只暴露health
  endpoint:
    health:
      probes:
        enabled: true                 # 启用K8s探针端点
      show-details: never             # 不暴露详情（安全）
```

### 3.2 探针端点

```bash
# Liveness Probe → 检查应用是否存活
curl /actuator/health/liveness     # {"status":"UP"}
# 只要Spring上下文还在，就返回UP。不检查DB/Redis等外部依赖。

# Readiness Probe → 检查应用是否就绪
curl /actuator/health/readiness    # {"status":"UP"}
# 检查DB连接池/Redis连接等。任一外部依赖不可用→返回DOWN→摘除流量。
```

### 3.3 Readiness控制外部依赖

```java
// 自定义Readiness：数据库连接池状态
@Component
public class DatabaseHealthIndicator implements HealthIndicator {
    
    @Autowired
    private HikariDataSource dataSource;
    
    @Override
    public Health health() {
        try (Connection conn = dataSource.getConnection()) {
            if (conn.isValid(3)) {
                return Health.up().build();
            }
        } catch (Exception e) {
            return Health.down().withException(e).build();
        }
        return Health.down().build();
    }
}
```

## 4. 优雅停机全链路

### 4.1 理想停机流程

```text
1. K8s发送 SIGTERM 信号给Pod
2. preStop Hook执行（如果有）→ 等待几秒，让Service摘除本Pod
3. SpringBoot收到SIGTERM → 优雅停机：
   a. 停止接收新请求
   b. 等待现有请求处理完毕（最长等timeout-per-shutdown-phase）
   c. 关闭数据库连接池
   d. 关闭Spring上下文
4. K8s等待 terminationGracePeriodSeconds
5. 超时后 KILL（SIGKILL）
```

### 4.2 完整配置

```yaml
# SpringBoot配置
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s   # 优雅停机最长等待30s

# Deployment配置
spec:
  template:
    spec:
      terminationGracePeriodSeconds: 45  # K8s等待45秒才SIGKILL
      containers:
        - name: user-service
          lifecycle:
            preStop:
              exec:
                command:
                  - /bin/sh
                  - -c
                  - sleep 10              # 等10秒让Service更新Endpoints
```

### 4.3 为什么需要preStop sleep

```text
问题：K8s同时做了两件事
  A. 给Pod发SIGTERM
  B. 更新Service的Endpoints（移除本Pod IP）

如果A比B快：
  → Pod已经停止 → 但Service还指向它 → 流量到达 → 连接拒绝

preStop sleep 10秒：
  → 确保Service先完成Endpoints更新 → 然后再停机
```

## 5. 零宕机部署检查清单

```checkbox
□ SpringBoot Actuator health探针已启用
□ Liveness Probe：检查存活，不检查外部依赖
□ Readiness Probe：检查就绪，可检查外部依赖
□ Startup Probe：如果启动>30s，添加Startup探针
□ server.shutdown=graceful
□ spring.lifecycle.timeout-per-shutdown-phase 合理设置
□ terminationGracePeriodSeconds > shutdown超时时间
□ preStop Hook：sleep确保摘除流量
□ 滚动更新：maxSurge=1, maxUnavailable=0
□ 资源限制：requests和limits已设置（防OOMKilled）
```
