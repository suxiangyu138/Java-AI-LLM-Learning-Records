# 软件需求管理：架构驱动开发的基石

> **核心观点**：需求管理并非单纯的"收集需求、整理文档"，而是要将业务需求转化为可落地、可适配架构、可复用的技术需求，衔接业务与技术，为架构设计、编码实现、测试部署提供明确依据。

## 1. 需求管理的核心定位

### 1.1 需求是架构设计的"输入源"

脱离需求的架构设计只是"空中楼阁"。例如，电商系统的"订单支付"需求直接决定是否需要引入分布式事务（Seata）、消息队列（RocketMQ/Kafka）以及支付接口的幂等性设计。

### 1.2 需求管理是架构落地的"连接器"

需求管理的核心是将业务需求拆分为"可分配、可落地、可验证"的技术需求，与架构拆分形成对应。基于 DDD 架构开发时，需求管理需先区分核心域、支撑域、通用域，再将每个域的需求映射到对应的领域模型。

### 1.3 需求管理是架构迭代的"校准器"

当业务需求从"单一支付渠道"升级为"多支付渠道"时，后端开发者需评估变更对支付模块架构的影响——是否需要重构支付接口、引入策略模式、调整分布式事务方案。

## 2. 需求管理的全流程实施

### 2.1 需求收集：聚焦"业务本质 + 技术可行性"

**核心要点**：

- 明确需求来源：业务方（核心需求）、产品经理（文档）、运维人员（可维护性）、测试人员（可测试性）
- 按"功能性需求 + 非功能性需求"分类
- 主动沟通澄清：模糊需求需细化，如"用户登录"需明确第三方登录、密码加密、登录失败限制等细节

> **示例**：电商系统"订单创建"需求，后端需补充的技术细节包括订单号生成规则（雪花算法/UUID）、数据存储方式（分库分表/单表）、幂等性设计、异常回滚逻辑。

### 2.2 需求分析：从"业务语言"转化为"技术语言"

| 步骤 | 说明 |
|------|------|
| 拆解业务逻辑 | 将"订单管理"拆分为创建、查询、修改、取消、支付等子场景 |
| 识别技术关键点 | 提取缓存优化、索引设计、跨模块查询等核心诉求 |
| 匹配架构模式 | 简单后台管理用单体，复杂电商/金融用微服务或 DDD |
| 优先级排序 | MoSCoW 法则（必须有、应该有、可以有、暂不需要） |

### 2.3 需求建模：转化为"架构可识别的模型"

#### 数据模型建模（适用于单体架构、简单微服务）

设计数据库表结构、接口模型，例如用户表（user_id、username、password、phone）+ 登录接口（POST /api/user/login）。

#### 领域模型建模（适用于 DDD 架构、复杂微服务）

基于 DDD 思想，将需求转化为聚合根、实体、值对象、领域服务、应用服务。例如"订单管理"中，Order 作为聚合根，包含 OrderItem（实体）、Address（值对象）。

### 2.4 需求拆解：与架构拆分同步

| 架构类型 | 拆解方式 |
|----------|----------|
| 单体架构 | 按 Controller / Service / Dao 分层拆解 |
| 微服务架构 | 按业务模块（用户服务、订单服务）拆解 |
| DDD 架构 | 按限界上下文（订单上下文、支付上下文）拆解 |

### 2.5 需求基线：锁定核心需求

**核心原则**：基线前自由，基线后受控。

- 需求评审通过后形成基线文档
- 基线建立后的变更必须通过正式变更控制流程
- 基线需版本控制（V1.0、V1.1、V2.0），保留历史记录

### 2.6 需求变更：可控管理

| 步骤 | 内容 |
|------|------|
| 变更申请 | 提交书面申请，描述变更内容、理由、紧急程度 |
| 影响评估 | 评估对架构、代码、数据库、测试的影响 |
| 变更审批 | CCB（变更控制委员会）集体审批 |
| 实施与验证 | 更新需求基线、架构文档、代码、测试用例 |
| 变更归档 | 归档所有变更相关文档 |

### 2.7 需求验证：确保落地与架构适配

| 验证类型 | 目标 |
|----------|------|
| 单元测试 | 验证代码实现符合需求 |
| 接口测试 | 验证接口参数、返回值、性能 |
| 集成测试 | 验证模块间交互正常 |
| 业务验证 | 与产品、业务方共同验证业务场景 |

## 3. 常见痛点及解决方案

### 3.1 需求模糊、不明确

**场景**：PRD 仅描述业务场景，未明确接口参数、异常处理、非功能需求。

**解决方案**：
- 建立需求模板，明确必含内容
- 后端开发者主动参与需求评审
- 编写"需求理解备忘录"提交确认

### 3.2 需求变更频繁

**场景**：业务方频繁变更需求，未经过规范流程。

**解决方案**：
- 建立严格的变更控制流程
- 架构设计预留扩展点（策略模式、接口隔离）
- 采用迭代式开发，变更纳入下一迭代

### 3.3 需求与架构脱节

**场景**：架构设计过于复杂（微服务做后台管理）或过于简单（单体做高并发电商）。

**解决方案**：
- 坚持"需求驱动架构"
- 架构设计前进行需求评估
- 建立需求与架构的映射关系

### 3.4 需求落地困难

**场景**：需求拆解不细，开发与需求不符；技术无法落地。

**解决方案**：
- 细化需求拆解，明确交付标准
- 加强开发过程中的需求同步
- 技术难题提前预研验证

---

## 4. 总结

> 架构驱动的需求管理，核心是将业务需求转化为可落地、可适配架构、可复用的技术需求。

**四大核心原则**：
1. **需求引领架构，架构适配需求**：相互支撑、迭代优化
2. **技术与业务融合**：后端开发者深入理解业务，将业务语言转化为技术语言
3. **可控变更，预留扩展**：规范变更流程，架构设计预留扩展点
4. **闭环管理，全程验证**：从收集到验证全程严谨，确保落地与架构适配
