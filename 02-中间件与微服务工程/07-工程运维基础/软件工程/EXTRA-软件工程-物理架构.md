# 物理架构配置：架构驱动开发的落地载体

> **核心观点**：物理架构配置是架构落地的"最后一公里"，将逻辑组件"映射"到具体的服务器、容器、网络节点。Java 后端开发者需要深度参与物理架构配置，避免"开发的代码无法适配部署环境"。

## 1. 核心认知

### 逻辑架构 vs 物理架构

| 维度 | 逻辑架构（Layer） | 物理架构（Tier） |
|------|-------------------|------------------|
| 定义 | 功能层面的分层 | 部署层面的分层 |
| 示例 | Controller 层、Service 层、Dao 层 | 应用服务器、数据库服务器、缓存节点 |
| 关系 | 抽象功能模块划分 | 具体硬件节点与部署方案 |

> 一个物理节点可部署多个逻辑层，一个逻辑层也可分布式部署在多个物理节点上。

## 2. 物理架构配置的核心原则

### 2.1 适配性原则：贴合 Java 技术栈与逻辑架构

| 架构类型 | 物理部署方案 |
|----------|-------------|
| 单体架构（Spring Boot） | 应用服务器 + 数据库服务器 |
| 微服务架构（Spring Cloud Alibaba） | 服务节点 + 注册中心 + 配置中心 + 网关节点 + 数据节点 |

JVM 内存分配与 GC 策略需与服务器硬件匹配：
- 堆内存 ≥ 8G 场景推荐 G1GC
- 高并发场景需为应用服务器配置足够内存

### 2.2 高可用原则：规避单点故障

| 层面 | 配置方案 |
|------|----------|
| 应用层冗余 | 多个应用节点 + 负载均衡（Nginx/LVS），无状态设计便于水平扩展 |
| 中间件冗余 | 数据库主从复制 + 读写分离，Redis 主从 + 哨兵/集群模式 |
| 硬件与网络冗余 | 多机房部署（异地多活），双链路备份，预留 30% 冗余资源 |

### 2.3 可扩展性原则：支撑业务增长

| 扩展方式 | 说明 |
|----------|------|
| 横向扩容 | 增加服务器/容器节点，K8s HPA 自动弹性伸缩，数据库分库分表 |
| 纵向升级 | 提升单机硬件配置（CPU、内存、NVMe SSD） |

### 2.4 可维护性原则：简化运维

| 要点 | 方案 |
|------|------|
| 标准化部署 | Docker + K8s，配置中心（Nacos/Apollo） |
| 集中化监控 | Prometheus + Grafana + ELK |
| 模块化部署 | 网关、认证、业务、数据服务分别部署 |

## 3. 物理架构配置的分层落地

### 3.1 边缘层：流量入口

| 组件 | 配置要点 |
|------|----------|
| 负载均衡（Nginx/LVS） | 轮询/权重/IP 哈希策略，健康检查，Keepalived 高可用 |
| 安全防护 | WAF + NAT 网关 + SSL/HTTPS |
| CDN | 静态资源就近分发 |

### 3.2 应用层：Java 业务核心

#### 单体架构（小型业务）

| 配置项 | 推荐值 |
|--------|--------|
| 应用服务器 | 1-2 台（主备），CPU ≥ 4 核，内存 ≥ 8G |
| JDK | JDK 11+ |
| JVM 堆内存 | 物理内存 50%-70%，新生代:老年代 = 1:2 |
| GC 收集器 | 堆 < 4G 用 Parallel GC，堆 ≥ 8G 用 G1GC |

#### 微服务架构（中大型业务）

| 配置项 | 推荐值 |
|--------|--------|
| 部署方式 | Docker + K8s，Deployment + HPA |
| 节点配置 | CPU ≥ 2 核，内存 ≥ 4G |
| JVM 容器适配 | `-XX:MaxRAMPercentage=70.0` |
| 辅助节点 | 注册中心（Nacos）+ 配置中心 + 网关（Spring Cloud Gateway） |

### 3.3 中间件层：支撑中枢

#### 数据库

| 数据库 | 部署方案 | 节点配置 |
|--------|----------|----------|
| MySQL | 主从复制 + 读写分离（或 MGR 集群） | CPU ≥ 4 核，内存 ≥ 8G，SSD 磁盘 ≥ 100G |
| MongoDB | 分片集群 + 副本集 | CPU ≥ 4 核，内存 ≥ 16G |

#### 缓存

| 模式 | 适用场景 | 配置 |
|------|----------|------|
| 主从 + 哨兵 | 中小规模 | 1 主 2 从 + 3 哨兵，CPU ≥ 2 核，内存 ≥ 8G |
| Redis Cluster | 大规模高并发 | 至少 3 主 3 从，可支撑百万级 QPS |

#### 消息队列

| 中间件 | 部署方案 | 节点配置 |
|--------|----------|----------|
| RocketMQ | 2 NameServer + 2 Broker（主从） | CPU ≥ 4 核，内存 ≥ 8G，SSD ≥ 200G |
| Kafka | 3 Broker + 3 ZooKeeper | CPU ≥ 4 核，内存 ≥ 16G，磁盘 ≥ 500G |

#### 搜索引擎

- **Elasticsearch**：至少 3 节点（1 主 + 2 数据节点），CPU ≥ 4 核，内存 ≥ 16G，SSD ≥ 500G

### 3.4 数据层：数据安全与备份

| 维度 | 方案 |
|------|------|
| 备份 | MySQL：全量备份（每日）+ 增量备份（每小时），备份至异地节点 |
| 持久化 | Redis：RDB + AOF 混合持久化 |
| 存储扩展 | 本地 RAID10，分布式存储 MinIO/HDFS |
| 数据安全 | 透明加密（TDE）、HTTPS/SSL 传输加密、网络访问控制（ACL） |

### 3.5 基础设施层：硬件与网络

| 服务类型 | 服务器配置 |
|----------|-----------|
| 计算密集型 | CPU ≥ 8 核（Xeon E5/E7），内存 ≥ 16G |
| IO 密集型 | NVMe SSD（IOPS ≥ 10 万），千兆以上网卡 |
| 通用服务 | CPU ≥ 4 核，内存 ≥ 8G，SSD ≥ 100G |

## 4. 常见问题与优化方案

| 问题 | 表现 | 优化方案 |
|------|------|----------|
| 资源配置失衡 | 内存溢出、CPU 浪费、磁盘 IO 不足 | 动态调整资源，Prometheus + Grafana 监控，容器化部署 |
| 高可用设计缺失 | 单点故障导致服务中断 | 冗余部署、主从 + 哨兵/集群模式、异地多活 |
| 运维成本过高 | 环境不一致、日志分散、监控不完善 | Docker + K8s 标准化、ELK 集中日志、Prometheus 监控 |
| 可扩展性不足 | 无法应对业务增长 | 微服务拆分、分库分表、集群模式、预留扩容接口 |

---

## 5. 总结

> 物理架构配置并非"运维专属"，而是架构驱动软件开发的核心环节，是"逻辑架构落地为生产系统"的关键桥梁。

对于 Java 后端开发者而言，深度参与物理架构配置能避免"开发与部署脱节"，从根源上优化系统性能、提升可用性、降低运维成本。需遵循适配性、高可用、可扩展性、可维护性四大原则，结合业务场景选择合适的部署方案。
