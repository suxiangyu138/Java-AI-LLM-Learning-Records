# 架构驱动的软件开发：制定功能架构

> **核心观点**：功能架构是 ADSD 的核心环节，是连接业务需求与技术实现的桥梁。其本质是结合 Java 生态特性（Spring 生态、微服务架构、中间件选型），将业务需求转化为可落地、可扩展、可维护的后端功能模块体系，同时兼顾性能、安全性与可迭代性。

## 一、功能架构的核心定位

在架构驱动的软件开发中，功能架构是"业务需求的技术化映射"，区别于技术架构和部署架构：

| 架构类型 | 解决的问题 | Java 后端示例 |
|----------|-----------|--------------|
| **功能架构** | 系统要做什么、模块间如何协作 | 认证模块、订单模块的职责与边界 |
| 技术架构 | 用什么技术实现 | Spring Cloud、MyBatis、Redis |
| 部署架构 | 如何部署上线 | Docker、K8s、Nginx 集群 |

### 三大定位

| 定位 | 说明 |
|------|------|
| **业务与技术的衔接点** | 将产品需求转化为可开发的功能模块，明确每个模块的职责边界 |
| **Java 生态的适配载体** | 单体架构对应 Java 包结构（controller/service/dao）；微服务架构对应微服务实例 |
| **质量管控的前置保障** | 决定系统的可扩展性、可维护性、安全性，是项目长期迭代的基础 |

> **注意**：功能架构并非一成不变，而是随着业务迭代、技术升级动态调整，但核心原则（职责单一、高内聚低耦合）始终不变。

## 二、制定功能架构的核心前提

架构驱动的核心是"架构先行"，功能架构的制定需基于三个核心前提：

---

### 2.1 需求分层与优先级梳理

Java 后端面对的需求往往"混杂"，需先对需求分层，结合后端特性梳理优先级：

| 需求层次 | 定义 | Java 后端处理方式 |
|----------|------|-------------------|
| **核心业务需求** | 直接支撑业务目标，必须落地 | 设计为核心功能模块，采用 DDD 聚合根思想，优先保障业务逻辑完整性与准确性 |
| **非核心业务需求** | 辅助支撑系统正常运行 | 设计为通用功能模块，如基于 Spring Security 的认证模块、基于 Logback 的日志模块 |
| **隐性需求** | 未明确提出但必须具备 | 融入各模块，如统一异常处理（GlobalExceptionHandler）、接口幂等性、数据脱敏 |

> 需求梳理的核心是"明确边界"，避免将不同层级的需求混入同一个功能模块。这是 Java 后端项目中"代码冗余、维护困难"的主要原因之一。

---

### 2.2 技术栈适配与约束

功能架构的设计必须贴合 Java 后端的技术栈选择，技术栈约束直接决定模块拆分方式与实现逻辑：

| 架构模式 | 功能架构设计方式 | 关键技术 |
|----------|-----------------|----------|
| **单体架构**（Spring Boot） | 纵向分层（Controller/Service/DAO）+ 横向拆分业务模块 | Spring Boot、Maven 多模块 |
| **微服务架构**（Spring Cloud） | 按微服务实例拆分，每个服务对应核心模块 + 通用微服务 | Spring Cloud Alibaba、Feign、Nacos、Gateway |
| **分布式场景** | 预留中间件适配接口 | Seata（分布式事务）、Redis（缓存）、RocketMQ/Kafka（消息队列） |

此外，需统一技术规范融入架构设计：

- 统一接口返回格式
- 统一异常编码
- 统一代码规范（包命名、类命名、方法命名）

---

### 2.3 架构原则的落地

| 原则 | 说明 | Java 后端实践 |
|------|------|--------------|
| **高内聚低耦合** | 模块只负责自身职责，通过标准化接口通信 | user 模块与 order 模块通过"用户 ID"关联，通过接口调用获取信息 |
| **职责单一** | 避免一个模块做所有事 | 订单处理与支付回调拆分为独立模块 |
| **可扩展性** | 预留扩展接口应对业务迭代 | 商品模块预留"商品规格扩展""商品分类扩展"接口 |

---

## 三、功能架构的制定流程

从需求到落地共 5 个核心步骤：

```
需求建模与领域拆分 → 功能模块拆分 → 依赖与接口设计 → 技术适配 → 架构评审
```

---

### 步骤 1：需求建模与领域拆分

**核心**：将业务需求转化为 Java 后端可理解的"领域模型"，推荐采用 DDD 进行需求建模。

**具体操作**：

| 阶段 | 内容 | 示例 |
|------|------|------|
| 梳理核心业务领域 | 每个领域对应一个核心功能模块 | 用户领域、商品领域、订单领域、支付领域 |
| 确定聚合根 | 领域的核心实体 | 用户领域的 `User`，订单领域的 `Order` |
| 拆分子模块 | 按业务功能细分为子模块 | 用户领域拆分为认证子模块、信息管理子模块、权限子模块，对应包结构如 `com.example.user.auth` |

> **注意**：需求建模阶段需避免"技术先行"，先基于业务需求拆分领域，再结合技术栈适配实现方式。

---

### 步骤 2：功能模块拆分与职责定义

基于需求建模结果，将领域拆分为三类功能模块：

#### 2.1 核心业务模块

| 模块 | 职责 | 技术实现要点 |
|------|------|-------------|
| 用户模块 | 用户注册、登录、信息修改、权限分配 | Spring Security 认证授权，MyBatis/MyBatis-Plus 持久化 |
| 订单模块 | 订单创建、修改、取消、查询 | 关联商品与用户，对接支付模块，处理分布式事务 |
| 商品模块 | 商品增删改查、库存管理、分类管理 | Redis 缓存提升查询性能，处理商品规格动态扩展 |

每个核心模块需明确"对外提供的接口"与"依赖的接口"。

#### 2.2 通用功能模块

| 模块 | 技术栈 | 职责 |
|------|--------|------|
| 认证授权模块 | Spring Security / OAuth 2 | 统一登录认证、权限校验 |
| 异常处理模块 | 自定义 | 统一拦截各模块异常，返回标准化信息 |
| 数据校验模块 | JSR 380 / Hibernate Validator | 统一参数校验，减少业务模块校验代码 |
| 日志模块 | Logback / Log4j2 | 统一日志打印规范，支持分级和持久化 |

> **设计原则**：无状态、可配置。例如认证模块可配置不同认证方式，日志模块可配置输出格式与存储路径。

#### 2.3 支撑模块

| 模块 | 技术栈 | 职责 |
|------|--------|------|
| 数据访问模块 | MyBatis / JPA | 数据库连接、ORM 映射、统一数据访问接口 |
| 缓存模块 | Redis | 数据缓存、缓存更新策略（过期时间、主动更新） |
| 消息队列模块 | RabbitMQ / Kafka | 异步任务处理、模块间解耦 |

---

### 步骤 3：模块依赖与接口设计

#### 接口设计原则

| 原则 | 说明 | Java 实现方式 |
|------|------|--------------|
| **依赖倒置** | 核心模块依赖接口而非具体实现 | 订单模块依赖 `AuthService` 接口而非 `AuthServiceImpl` |
| **接口标准化** | 统一返回格式和命名规范 | JSON 格式（code + message + data），查询用 `getXXX`，新增用 `addXXX` |
| **避免循环依赖** | 禁止模块间循环依赖 | 出现循环依赖时引入中间模块或调整职责，如新增"订单商品关联模块" |

**具体实践**：通过"接口定义（interface）+ 实现类"的方式解耦。

```java
// 认证模块定义接口
public interface AuthService {
    Token login(String username, String password);
    boolean checkPermission(Long userId, String permission);
}

// 核心业务模块注入接口，而非具体实现
@Service
public class OrderServiceImpl implements OrderService {
    @Autowired
    private AuthService authService; // 依赖接口，而非实现类
}
```

---

### 步骤 4：技术适配与细节补充

| 关注点 | 说明 |
|--------|------|
| **分层设计适配** | 每个模块遵循 Controller → Service → DAO 分层，避免跨层调用 |
| **中间件集成** | 明确各模块与中间件的适配方式，如订单模块通过 RabbitMQ 发送订单创建消息 |
| **可扩展性设计** | 为核心模块预留扩展接口，如商品模块预留"商品搜索扩展接口"对接 Elasticsearch |

---

### 步骤 5：架构评审与优化

#### 评审重点

- 模块职责是否清晰，是否存在职责重叠或遗漏
- 模块间依赖是否合理，是否存在循环依赖
- 技术适配是否可行，是否存在技术瓶颈
- 是否具备可扩展性和可维护性
- 是否符合软件工程规范，是否便于团队协作

#### 优化示例

| 发现的问题 | 优化方案 |
|-----------|---------|
| 订单模块与支付模块耦合过紧（直接调用实现类） | 改为调用支付模块接口，通过 Feign（微服务）或接口注入（单体）实现 |
| 通用模块可复用性不足 | 优化接口设计，增加可配置参数，提升复用性 |

## 四、实践要点与常见误区

### 4.1 实践要点

| 要点 | 说明 |
|------|------|
| **贴合 Java 生态特性** | 利用 Spring Boot 自动配置简化模块开发，利用 Spring Cloud 实现微服务协作 |
| **兼顾性能与可维护性** | 缓存模块考虑命中率与更新成本，核心模块平衡业务逻辑清晰性与执行效率 |
| **重视接口文档与规范** | 使用 Swagger 制定接口文档，明确参数、返回值、异常信息；制定 Java 代码规范 |
| **动态迭代架构** | 功能架构随业务迭代和技术升级动态调整，新业务可新增模块而无需重构整个架构 |

### 4.2 常见误区

| 误区 | 表现 | 正确做法 |
|------|------|----------|
| **模块拆分过细或过粗** | 过细导致依赖过多，过粗导致职责混乱 | 以业务边界为依据，拆分出粒度适中的模块 |
| **技术先行，忽视业务** | 先选技术栈再强行拆分模块 | 先基于业务需求拆分模块，再结合业务规模选择技术栈 |
| **忽视通用模块设计** | 每个模块单独实现参数校验、异常处理 | 提前设计通用模块，实现代码复用 |
| **模块间耦合过高** | 直接依赖实现类、直接操作其他模块数据库 | 通过接口调用实现协作，遵循高内聚低耦合原则 |

---

## 五、总结

从 Java 后端开发视角看，功能架构的制定是"业务需求落地的核心环节"，其核心逻辑为：

```
需求建模 → 领域拆分 → 模块定义 → 接口设计 → 技术适配 → 架构评审
```

> **核心认知**：功能架构需兼顾"业务合理性"与"技术可行性"，既要贴合业务需求，确保功能模块支撑业务目标，也要贴合 Java 生态，确保架构可落地、可迭代。

对于 Java 后端开发者，制定功能架构时需坚守**高内聚低耦合**和**职责单一**原则，规避常见误区，让功能架构成为后端系统长期迭代的基础，助力实现软件工程的最终目标——**高效、高质量地开发出满足业务需求的软件系统**。
