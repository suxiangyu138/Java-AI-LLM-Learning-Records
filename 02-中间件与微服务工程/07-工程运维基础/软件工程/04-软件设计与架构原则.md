## 1. 设计原则概述

### 1.1 为什么需要设计原则

| 没有原则的代码 | 遵循原则的代码 |
|--------------|--------------|
| 改一个功能需要改5个文件 | 改一个功能只需改1个文件 |
| 新来的人要花2周才能看懂 | 新来的人半天就能上手 |
| 单元测试覆盖率很难提升 | 模块独立，容易编写单测 |
| 每次发布都提心吊胆 | 变更自信，回滚可控 |

> 💡 **核心认知**：设计原则不是"最佳实践的说教"，而是无数工程师在真实项目中用血的教训总结出的**封装变化、隔离复杂度**的共识。

### 1.2 原则的分层体系

```
设计层次                  对应原则
┌─────────────────────────────────────────┐
│  架构层面（宏观）      │ 分层、依赖方向、模块边界 │
├─────────────────────────────────────────┤
│  类/接口层面（中观）   │ SOLID、组合优于继承    │
├─────────────────────────────────────────┤
│  代码层面（微观）      │ DRY、KISS、YAGNI     │
└─────────────────────────────────────────┘
```

## 2. SOLID 原则

SOLID 是面向对象设计的五个基本原则的首字母缩写，由 Robert C. Martin（Uncle Bob）提出，是所有 Java 开发者的必修课。

### 2.1 S — 单一职责原则（Single Responsibility Principle）

> **一个类只应有一个引起它变化的原因**——即一个类只负责一个职责。

**反例：一个类承担多处职责**

```java
// ❌ 违背 SRP：这个类同时负责员工数据的持久化、展示和工资计算
public class Employee {
    private String name;
    private double salary;

    // 数据访问职责
    public void saveToDatabase() {
        try (Connection conn = DriverManager.getConnection("jdbc:mysql://...")) {
            PreparedStatement ps = conn.prepareStatement("INSERT INTO employee VALUES (?,?)");
            ps.setString(1, name);
            ps.setDouble(2, salary);
            ps.executeUpdate();
        } catch (SQLException e) { /* ... */ }
    }

    // 展示职责
    public void printReport() {
        System.out.println("<html><body><h1>" + name + "</h1><p>" + salary + "</p></body></html>");
    }

    // 业务职责
    public double calculatePay() {
        if (salary > 10000) {
            return salary * 0.8; // 高税率
        }
        return salary * 0.9; // 低税率
    }
}
```

**正例：拆分到三个独立的类**

```java
// ✅ 遵循 SRP：每个类只有一个职责
public class Employee {
    private String name;
    private double salary;
    // getter / setter（纯数据对象）
}

// 职责1：持久化
public class EmployeeRepository {
    public void save(Employee employee) {
        // JDBC 操作...
    }
}

// 职责2：展示
public class EmployeeReportService {
    public String generateHtml(Employee employee) {
        return "<html><body><h1>" + employee.getName() + "</h1></body></html>";
    }
}

// 职责3：工资计算
public class PayCalculator {
    public double calculate(Employee employee) {
        double salary = employee.getSalary();
        return salary > 10000 ? salary * 0.8 : salary * 0.9;
    }
}
```

### 2.2 O — 开闭原则（Open-Closed Principle）

> **对扩展开放，对修改关闭**——通过扩展（新增类）来改变行为，而不是修改已有的代码。

**反例：需要修改已有代码来支持新类型**

```java
// ❌ 违背 OCP：每增加一种支付方式都要修改该方法
public class PaymentProcessor {
    public void process(String type, double amount) {
        if ("ALIPAY".equals(type)) {
            // 调用支付宝API
        } else if ("WECHAT".equals(type)) {
            // 调用微信支付API
        } else if ("CREDIT_CARD".equals(type)) {
            // 调用信用卡API
        }
        // 每次新增支付方式，都要在这里加一个 else if
    }
}
```

**正例：通过抽象接口实现扩展**

```java
// ✅ 遵循 OCP
public interface PaymentMethod {
    void pay(double amount);
}

public class Alipay implements PaymentMethod {
    @Override
    public void pay(double amount) {
        // 调用支付宝API
    }
}

public class WechatPay implements PaymentMethod {
    @Override
    public void pay(double amount) {
        // 调用微信支付API
    }
}

// 新增一种支付方式，只需新建类，无需修改已有代码
public class ApplePay implements PaymentMethod {
    @Override
    public void pay(double amount) {
        // 调用苹果支付API
    }
}

public class PaymentProcessor {
    private PaymentMethod paymentMethod;

    // 通过构造器注入具体的支付方式
    public PaymentProcessor(PaymentMethod paymentMethod) {
        this.paymentMethod = paymentMethod;
    }

    public void process(double amount) {
        paymentMethod.pay(amount);
    }
}
```

### 2.3 L — 里氏替换原则（Liskov Substitution Principle）

> **子类必须能够替换其父类**——使用父类引用的地方，传入子类实例时不应导致程序错误。

**反例：子类削弱了父类的行为**

```java
// ❌ 违背 LSP：正方形继承矩形，但行为不一致
public class Rectangle {
    private int width;
    private int height;

    public void setWidth(int width) { this.width = width; }
    public void setHeight(int height) { this.height = height; }
    public int getArea() { return width * height; }
}

public class Square extends Rectangle {
    @Override
    public void setWidth(int width) {
        super.setWidth(width);
        super.setHeight(width); // 维持正方形约束
    }

    @Override
    public void setHeight(int height) {
        super.setWidth(height);
        super.setHeight(height);
    }
}

// 测试代码 —— 对矩形成立，对正方形不成立
public void testArea(Rectangle rect) {
    rect.setWidth(5);
    rect.setHeight(4);
    // 期望：20，但 Square 传进来结果是 16（因为 setHeight 把 width 也改了）
    assert rect.getArea() == 20;
}
```

**正例：使用抽象类或接口暴露正确的契约**

```java
// ✅ 遵循 LSP：让 Rectangle 和 Square 都实现 Shape 接口
public interface Shape {
    int getArea();
}

public class Rectangle implements Shape {
    private int width;
    private int height;

    public Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public int getArea() { return width * height; }
}

public class Square implements Shape {
    private int side;

    public Square(int side) {
        this.side = side;
    }

    @Override
    public int getArea() { return side * side; }
}
```

> ⚠️ **LSP 的核心**：继承不是用来复用的，是用来**建立 is-a 关系的**。如果子类不需要父类的全部方法，或需要重写父类方法使其行为不一致，就应该优先考虑组合而非继承。

### 2.4 I — 接口隔离原则（Interface Segregation Principle）

> **不应该强迫客户端依赖它不使用的方法**——接口应该小而专，避免"胖接口"。

**反例：胖接口强迫实现类实现不需要的方法**

```java
// ❌ 违背 ISP：一个万能接口包含所有可能的方法
public interface Worker {
    void work();
    void eat();
    void sleep();
}

public class Robot implements Worker {
    @Override
    public void work() { /* 工作正常 */ }

    @Override
    public void eat() {
        throw new UnsupportedOperationException("机器人不需要吃饭！");
    }

    @Override
    public void sleep() {
        throw new UnsupportedOperationException("机器人不需要睡觉！");
    }
}
```

**正例：拆分为多个专用接口**

```java
// ✅ 遵循 ISP：接口职责单一
public interface Workable {
    void work();
}

public interface Eatable {
    void eat();
}

public interface Sleepable {
    void sleep();
}

public class HumanWorker implements Workable, Eatable, Sleepable {
    @Override
    public void work() { /* ... */ }
    @Override
    public void eat() { /* ... */ }
    @Override
    public void sleep() { /* ... */ }
}

public class RobotWorker implements Workable {
    @Override
    public void work() { /* ... */ }
}
```

### 2.5 D — 依赖反转原则（Dependency Inversion Principle）

> **高层模块不应依赖低层模块，二者都应依赖于抽象。抽象不应依赖细节，细节应依赖抽象。**

**反例：高层直接依赖低层实现**

```java
// ❌ 违背 DIP：Service 直接依赖 MySQL 的具体实现
public class UserService {
    private MySqlUserRepository repository = new MySqlUserRepository();

    public User findUser(Long id) {
        return repository.findById(id);
    }
}

// 如果要切换到 PostgreSQL，必须修改 UserService 代码
```

**正例：通过接口反转依赖方向**

```java
// ✅ 遵循 DIP
// 1. 抽象（接口）定义契约
public interface UserRepository {
    User findById(Long id);
}

// 2. 低层实现依赖抽象
public class MySqlUserRepository implements UserRepository {
    @Override
    public User findById(Long id) { /* MySQL 实现 */ }
}

public class PostgresUserRepository implements UserRepository {
    @Override
    public User findById(Long id) { /* PostgreSQL 实现 */ }
}

// 3. 高层模块只依赖抽象
public class UserService {
    private final UserRepository userRepository;

    // 依赖注入（DI）：由外部注入具体实现
    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public User findUser(Long id) {
        return userRepository.findById(id);
    }
}

// 4. 组装（通常由 DI 容器完成）
UserService service = new UserService(new MySqlUserRepository());
```

> 💡 **DIP 与 IoC/DI 的关系**：
> - **DIP**（依赖反转原则）是**设计原则**——定义"谁依赖谁"的规则
> - **IoC**（控制反转）是**设计思想**——将控制权从对象本身转移到外部容器
> - **DI**（依赖注入）是 **IoC 的实现方式**——通过构造器/Setter/接口注入依赖
> - Spring 的 IoC 容器通过 DI 机制实现 DIP

### 2.6 SOLID 原则的相互关联

```
     SRP（类职责单一）
         │
         ▼
     ISP（接口小而专） ◄─── 保证 OCP（开闭原则）的前提
         │
         ▼
     DIP（依赖抽象） ───► 支撑 LSP（子类可替换）
```

> 🎯 五条原则共同作用，实现一个核心目标：**高内聚、低耦合，让系统易于扩展和维护**。

## 3. DRY 与 WET

### 3.1 DRY（Don't Repeat Yourself）

> **每一段知识（Knowledge）在系统中应有单一、明确、权威的表示。**

| DRY 层面 | 反例 | 正例 |
|---------|------|------|
| **代码级别** | 多处重复相同的校验逻辑 | 抽取为 `ValidationUtils` 工具方法 |
| **数据级别** | 用户手机号同时存在3张表中 | 唯一数据源，其他通过引用获取 |
| **逻辑级别** | 接口代码和测试代码定义相同常量 | 统一在公共常量类中定义 |
| **知识级别** | 业务规则同时写在代码和文档中 | 以代码为唯一真相源，文档引用代码 |

### 3.2 WET（Write Everything Twice）

WET 是 DRY 的反面——"写两次"（或多次）。

> ⚠️ **DRY 并非绝对真理**。在某些场景下，适度重复优于强行抽象：
> - 两个业务逻辑当前相同但预期会分开演化
> - 抽象后引入的耦合大于重复带来的维护成本
> - 泛化接口增加了调用方的理解难度

**判断标准**：如果两个"重复"的代码片段**修改原因相同**，就应该 DRY；如果修改原因不同，分开反而更合理。

## 4. KISS 原则

> **Keep It Simple, Stupid** —— 简单是最高级的复杂。

### 4.1 过度工程化（Over-Engineering）的警告信号

| 警告信号 | 表现 | 后果 |
|---------|------|------|
| **框架泛滥** | 只查一次 Redis 却引入 Redisson | 增加维护复杂度 |
| **过度抽象** | 为了"通用性"设计了3层接口+5个抽象类 | 新人不理解，开发效率下降 |
| **过早优化** | 还没上线就开始优化 QPS | 浪费精力，增加 Bug |
| **设计模式滥用** | 一个简单条件判断却用了策略模式+工厂模式 | 代码可读性急剧下降 |

```java
// ❌ 过度设计：一个简单的类型检查被包装成策略模式
public class StringUtils {
    // 能用三行代码解决的
    public static boolean isEmpty(String str) {
        Strategy strategy = StrategyFactory.getStrategy("isEmpty");
        return strategy.execute(str);
    }
}

// ✅ KISS 版本：三行解决
public static boolean isEmpty(String str) {
    return str == null || str.trim().isEmpty();
}
```

> 💡 **KISS 的实践指南**：
> 1. 先写出**最直白的可工作代码**
> 2. 等真的出现重复或扩展需求时，再考虑抽象
> 3. 每次抽象前问自己："如果没有这个抽象，代码会更差吗？"

## 5. YAGNI 原则

> **You Aren't Gonna Need It** —— 永远只为当前需求实现功能，不要猜测未来的需要。

### 5.1 YAGNI 的常见陷阱

| 典型场景 | 开发者的"理由" | YAGNI 的回应 |
|---------|---------------|-------------|
| 为"将来可能"的功能预留扩展点 | "等以后再加会很麻烦" | 等真的需要时再加——那时候你更了解需求 |
| 提前实现缓存层 | "系统迟早会扛不住" | 等性能瓶颈真的出现再优化 |
| 设计通用的配置框架 | "说不定以后其他团队也会用" | 现在只用专注当前团队的需求 |

```java
// ❌ 违反 YAGNI：为了"万一"做了过度泛化
public interface PaymentGateway<T extends PaymentRequest, R extends PaymentResponse> {
    R pay(T request);
    R refund(T request);
    R query(T request);
}
// 实际项目中只有一种支付方式，根本不需要泛型

// ✅ YAGNI 版本：直接实现具体类型
public class AlipayGateway {
    public AlipayResponse pay(AlipayRequest request) { /* ... */ }
}
```

> ⚠️ **YAGNI ≠ 不做设计**。合理的架构设计（如分层的模块边界）是必要的，YAGNI 反对的是为**不确定性需求**提前投入成本。

## 6. 组合优于继承

### 6.1 继承的问题

```java
// ❌ 继承的陷阱：深层次继承导致"脆弱的基类"问题
public class Bird {
    public void fly() { System.out.println("飞"); }
}

public class Penguin extends Bird {
    @Override
    // 企鹅不会飞！必须重写覆盖 —— 破坏了 LSP
    public void fly() {
        throw new UnsupportedOperationException("企鹅不会飞！");
    }
}

// 当需要增加"游泳"能力时，继承体系更加复杂
```

### 6.2 组合方案的对比

```java
// ✅ 组合优于继承：将行为委托给独立的策略对象
public interface MoveBehavior {
    void move();
}

public class FlyBehavior implements MoveBehavior {
    @Override
    public void move() { System.out.println("飞翔"); }
}

public class SwimBehavior implements MoveBehavior {
    @Override
    public void move() { System.out.println("游泳"); }
}

public class WalkBehavior implements MoveBehavior {
    @Override
    public void move() { System.out.println("行走"); }
}

public class Bird {
    private MoveBehavior moveBehavior;

    // 通过构造器或 Setter 注入行为
    public Bird(MoveBehavior moveBehavior) {
        this.moveBehavior = moveBehavior;
    }

    public void performMove() {
        moveBehavior.move();
    }
}

// 使用
Bird sparrow = new Bird(new FlyBehavior());
Bird penguin = new Bird(new SwimBehavior());
Bird ostrich = new Bird(new WalkBehavior());
```

| 维度 | 继承（Inheritance） | 组合（Composition） |
|------|-------------------|-------------------|
| **关系** | is-a（是一个） | has-a（有一个） |
| **复用粒度** | 类级别，可能继承不需要的方法 | 接口/行为级别，精确控制 |
| **运行期改变** | 不可变（编译期绑定） | 灵活（运行期可替换） |
| **耦合度** | 强耦合（子类依赖父类实现） | 松耦合（依赖接口） |
| **适用场景** | 真正的 is-a 关系且行为一致 | 大多数情况下推荐优先使用 |

## 7. 设计模式总览

### 7.1 GoF 23 种设计模式分类

设计模式（Design Patterns）源自 1994 年的经典著作 *Design Patterns: Elements of Reusable Object-Oriented Software*（GoF 四人帮），分为三大类：

#### 创建型模式（Creational Patterns）—— 5种

| 模式 | 核心意图 | 一句话场景 |
|------|---------|-----------|
| **Singleton** | 确保类只有一个实例 | 全局配置、数据库连接池 |
| **Factory Method** | 由子类决定要实例化的类 | 日志框架（决定哪种日志格式） |
| **Abstract Factory** | 创建相关或依赖对象的家族 | UI 组件库（不同风格） |
| **Builder** | 将一个复杂对象的构建与表示分离 | 构造参数很多的对象（Lombok @Builder） |
| **Prototype** | 通过拷贝已有对象创建新对象 | 创建成本高但差异小的对象 |

#### 结构型模式（Structural Patterns）—— 7种

| 模式 | 核心意图 | 一句话场景 |
|------|---------|-----------|
| **Adapter** | 将不兼容的接口转换为目标接口 | 旧系统接口适配新接口 |
| **Decorator** | 动态地为对象添加额外职责 | IO 流的多层包装 |
| **Proxy** | 为另一个对象提供替身或占位符 | AOP 代理、延迟加载 |
| **Facade** | 为子系统提供统一的简化接口 | REST 接口封装底层复杂逻辑 |
| **Bridge** | 将抽象部分与实现部分分离 | 跨平台图形渲染 |
| **Composite** | 将对象组合成树形结构表示"部分-整体" | 文件系统（文件夹/文件） |
| **Flyweight** | 通过共享高效地支持大量细粒度对象 | 连接池、线程池 |

#### 行为型模式（Behavioral Patterns）—— 11种

| 模式 | 核心意图 | 一句话场景 |
|------|---------|-----------|
| **Observer** | 定义一对多依赖，状态变化时自动通知 | 事件监听、消息订阅 |
| **Strategy** | 定义算法族，使其可以互相替换 | 支付方式、排序算法 |
| **Template Method** | 定义算法骨架，子类实现具体步骤 | JdbcTemplate（Spring） |
| **Chain of Responsibility** | 将请求在处理器链上传递 | 过滤器链、拦截器 |
| **Command** | 将请求封装为对象 | 撤销/重做、任务队列 |
| **State** | 对象在内部状态变化时改变其行为 | 订单状态机 |
| **Iterator** | 提供顺序访问聚合对象元素的方法 | 集合遍历 |
| **Mediator** | 用中介对象封装对象间的交互 | 聊天室、消息中间件 |
| **Memento** | 捕获和恢复对象的内部状态 | 保存点/快照 |
| **Interpreter** | 定义文法并解释语句 | SQL 解析、表达式计算 |
| **Visitor** | 将操作与对象结构分离 | 编译器 AST 处理 |

## 8. Spring 中的设计模式实战

### 8.1 Singleton（单例）

Spring 中所有 Bean 的默认作用域是 **singleton**——每个 IoC 容器中每个 Bean 定义只有一个实例。

```java
@Component // 默认 singleton，相当于 Spring 管理的单例工厂
public class UserService {
    // 这个类的所有依赖注入都指向同一个实例
}

// 手动注册一个单例 Bean
@Configuration
public class AppConfig {
    @Bean
    public DataSource dataSource() {
        return new HikariDataSource(); // 整个容器只有一个 DataSource 实例
    }
}
```

### 8.2 Factory（工厂模式）—— BeanFactory

Spring 的 **BeanFactory** 和 **ApplicationContext** 都是工厂模式的经典实现：

```java
// Spring 的 BeanFactory 是最基础的 IoC 容器
BeanFactory factory = new XmlBeanFactory(new ClassPathResource("beans.xml"));
UserService service = factory.getBean(UserService.class);

// ApplicationContext 是更高级的工厂（支持 AOP、事件、国际化）
ApplicationContext ctx = new AnnotationConfigApplicationContext(AppConfig.class);
UserService service = ctx.getBean(UserService.class);
```

Spring 通过**延迟初始化**（Lazy Init）和**提前初始化**（Eager Init）两种策略创建 Bean，开发者无需关心对象的创建逻辑，只需声明依赖。

### 8.3 Proxy（代理模式）—— AOP

Spring AOP 的核心是 **动态代理**：

```java
// 定义一个切面 —— Spring 自动为目标对象创建代理
@Aspect
@Component
public class LoggingAspect {

    @Around("execution(* com.example.service.*.*(..))")
    public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        Object result = joinPoint.proceed();
        long elapsed = System.currentTimeMillis() - start;
        System.out.println(joinPoint.getSignature() + " 执行耗时: " + elapsed + "ms");
        return result;
    }
}
```

| 代理方式 | 原理 | 适用条件 |
|---------|------|---------|
| **JDK 动态代理** | 基于接口的代理（`InvocationHandler`） | 目标类实现了至少一个接口 |
| **CGLIB 代理** | 基于子类的代理（字节码增强） | 目标类没有实现接口或需要代理类本身 |

### 8.4 Template Method（模板方法）—— JdbcTemplate

```java
// JdbcTemplate 定义了执行 SQL 的"骨架"，子步骤由回调实现
@Repository
public class UserDao {

    @Autowired
    private JdbcTemplate jdbcTemplate;

    public User findById(Long id) {
        // queryForObject 是模板方法，ResultSetExtractor 是具体步骤的实现
        return jdbcTemplate.queryForObject(
            "SELECT * FROM users WHERE id = ?",
            (rs, rowNum) -> new User(rs.getLong("id"), rs.getString("name")),
            id
        );
    }
}
```

| 类 | 模板方法 | 回调接口 | 功能 |
|----|---------|---------|------|
| `JdbcTemplate` | `execute()` / `query()` / `update()` | `PreparedStatementCallback` / `ResultSetExtractor` | 数据库操作 |
| `RestTemplate` | `getForObject()` / `exchange()` | `ResponseExtractor` | HTTP 请求 |
| `JmsTemplate` | `convertAndSend()` / `receive()` | `MessageCreator` | 消息队列 |

### 8.5 Observer（观察者）—— ApplicationEvent

```java
// 1. 定义事件
public class OrderCompletedEvent extends ApplicationEvent {
    private final Long orderId;

    public OrderCompletedEvent(Object source, Long orderId) {
        super(source);
        this.orderId = orderId;
    }

    public Long getOrderId() { return orderId; }
}

// 2. 发布事件
@Service
public class OrderService {
    @Autowired
    private ApplicationEventPublisher publisher;

    public void completeOrder(Long orderId) {
        // 完成订单...
        publisher.publishEvent(new OrderCompletedEvent(this, orderId));
        // 无需关心谁监听、做什么——松耦合
    }
}

// 3. 监听事件（可以有多个监听器）
@Component
public class SmsNotificationListener {
    @EventListener
    public void onOrderCompleted(OrderCompletedEvent event) {
        System.out.println("发送短信通知: 订单 " + event.getOrderId() + " 已完成");
    }
}
```

## 9. 架构模式

### 9.1 分层架构（Layered Architecture）

最经典的架构模式，广泛用于 Java Web 应用：

```
┌──────────────────────────────────────┐
│         Controller 层                │  ← HTTP/API 入口
│     （处理请求、参数校验、响应）        │
├──────────────────────────────────────┤
│         Service 层                   │  ← 业务逻辑
│     （事务管理、业务编排、权限）        │
├──────────────────────────────────────┤
│         Repository 层                │  ← 数据访问
│     （数据库 CRUD、ORM 操作）          │
├──────────────────────────────────────┤
│         Domain/Model 层              │  ← 领域模型
│     （实体、值对象、VO/DTO）           │
└──────────────────────────────────────┘
```

| 优势 | 劣势 |
|------|------|
| 简单直观，易于理解 | 随着业务复杂，层间容易"漏层调用" |
| 前后端分离，各层可独立修改 | 大泥球（Big Ball of Mud）倾向——每层都越过下层 |
| 大多数框架支持（Spring MVC） | 业务逻辑容易散落在 Controller 中 |
| 易于测试（各层可 Mock） | 代码膨胀后缺乏领域表达力 |

### 9.2 六边形架构（Ports & Adapters）

由 Alistair Cockburn 提出，核心思想：**业务逻辑（Domain）处于中心，通过端口（Port）与外界交互，适配器（Adapter）实现端口的具体技术**。

```
                   ┌─────────────────────┐
                   │   Inbound Adapter   │
                   │  (REST Controller)  │
                   └────────┬────────────┘
                            │ 调用（Inbound Port）
                   ┌────────▼────────────┐
                   │    Application      │
                   │    (Use Cases)      │
                   │                     │
                   │    Domain Core      │
                   │  (Entity/Value Obj) │
                   └────────▲────────────┘
                            │ 实现（Outbound Port）
                   ┌────────┴────────────┐
                   │   Outbound Adapter  │
                   │  (JPA/MongoDB/Redis)│
                   └─────────────────────┘
```

```java
// Port（端口）：定义业务接口
public interface OrderRepository {
    Order save(Order order);
    Optional<Order> findById(Long id);
}

// Adapter（适配器）：实现具体技术
@Repository
public class OrderJpaRepository implements OrderRepository {
    private final SpringDataJpaOrderRepo jpaRepo;

    @Override
    public Order save(Order order) {
        return jpaRepo.save(order);
    }

    @Override
    public Optional<Order> findById(Long id) {
        return jpaRepo.findById(id);
    }
}

// 核心业务逻辑完全不知道 JPA 的存在——它只依赖 OrderRepository 接口
```

> 💡 **六边形架构的价值**：业务逻辑与基础设施解耦，替换数据库（如 MySQL → MongoDB）或通信协议（如 REST → gRPC）时，Domain 层完全不受影响。

### 9.3 微服务架构（Microservices）

| 对比维度 | 单体架构（Monolith） | 微服务架构 |
|---------|-------------------|-----------|
| **部署** | 一个包部署所有功能 | 每个服务独立部署 |
| **扩展** | 垂直扩展（升级硬件） | 水平扩展（按需增加服务实例） |
| **团队** | 大团队共用一个代码库 | 小团队拥有独立的服务 |
| **技术栈** | 单一技术栈 | 每个服务可选不同技术栈 |
| **通信** | 进程内方法调用 | HTTP/RPC/消息队列 |
| **故障隔离** | 一个 Bug 可能导致整个系统宕机 | 故障局限在单个服务内 |
| **复杂度** | 代码复杂但运维简单 | 代码简单但运维复杂（服务发现、熔断、链路追踪） |

**微服务的关键挑战**：

| 挑战 | 解决方案 |
|------|---------|
| 服务发现 | Eureka、Consul、Nacos |
| 配置管理 | Spring Cloud Config、Apollo |
| 服务间调用 | Feign（声明式 HTTP）、gRPC |
| 分布式事务 | Saga 模式、TCC、Seata |
| 链路追踪 | Sleuth + Zipkin、SkyWalking |
| 熔断降级 | Sentinel、Resilience4j |
| 容器编排 | Kubernetes、Docker Compose |

### 9.4 事件驱动架构（Event-Driven Architecture）

```
服务A ──► 发布事件 ──► 消息中间件 ──► 服务B（订阅）
                           │
                           ├──► 服务C（订阅）
                           │
                           └──► 审计服务（订阅）
```

| 特点 | 说明 |
|------|------|
| **异步** | 生产者不阻塞等待消费者处理完成 |
| **松耦合** | 服务之间通过事件交互，不直接依赖 |
| **可扩展** | 消费者可独立扩展，支持多消费者 |
| **最终一致性** | 分布式系统中以最终一致性代替强一致性 |

### 9.5 CQRS（Command Query Responsibility Segregation）

> 将"写操作（Command）"和"读操作（Query）"分离为不同的模型。

```
┌────────────────────────────────────────────┐
│                 客户端                        │
└──────────┬──────────┬──────────────────────┘
           │          │
     ┌─────▼──┐  ┌───▼──────┐
     │Command │  │  Query   │
     │ Side   │  │  Side    │
     ├────────┤  ├──────────┤
     │创建/更新│  │ 查询/读取│
     │插入/删除│  │ 聚合/统计│
     └────┬───┘  └────┬─────┘
          │           │
     ┌────▼───────────▼────┐
     │     数据存储          │
     │  (写库: 3NF / 读库: │
     │   反范式化/物化视图)   │
     └─────────────────────┘
```

| 使用场景 | 不适合场景 |
|---------|-----------|
| 读写负载差异巨大 | 简单的 CRUD 应用 |
| 同一数据需要不同的查询视图 | 对强一致性有极高要求 |
| 与事件溯源（Event Sourcing）配合 | —— |

## 10. UML 基础

### 10.1 类图（Class Diagram）

UML 类图是 Java 开发者最常用的建模工具之一：

```
┌──────────────────────────┐
│        User              │  ← 类名
├──────────────────────────┤
│ - id: Long               │  ← 属性（- = private, + = public, # = protected）
│ - name: String           │
│ - email: String          │
│ + createdAt: LocalDateTime│
├──────────────────────────┤
│ + login()                │  ← 方法
│ + logout()               │
│ - validateEmail()        │
└──────────────────────────┘
```

#### 关系表示

| 关系 | UML 符号 | Java 表示 | 示例 |
|------|---------|----------|------|
| **关联**（Association） | `─────►` | 字段引用 | `User` → `Address` |
| **聚合**（Aggregation） | `─────◇` | 弱拥有关系（生命周期独立） | `Department` ◇ `Employee` |
| **组合**（Composition） | `─────◆` | 强拥有关系（生命周期一致） | `Order` ◆ `OrderItem` |
| **继承**（Generalization） | `─────▷` | `extends` / `implements` | `Dog` ▷ `Animal` |
| **依赖**（Dependency） | `─ ─ ─►` | 方法参数或局部变量 | `OrderService` ~> `PaymentGateway` |

```java
// 关联 —— 类之间的关系
public class Order {
    // 组合：Order 不存在时 OrderItem 没有意义
    private List<OrderItem> items;     // ◆

    // 聚合：User 可以没有 Order，Order 也可以独立存在
    private User user;                  // ◇

    // 依赖：只在方法中使用
    public void pay(PaymentGateway gateway) {  // ~>
        gateway.charge(this.totalAmount);
    }
}
```

## 11. 设计质量度量

### 11.1 耦合度（Coupling）vs 内聚度（Cohesion）

| 维度 | 高内聚（High Cohesion） | 低耦合（Low Coupling） |
|------|----------------------|----------------------|
| **含义** | 类内部元素目的统一、关联紧密 | 类之间的依赖关系少且明确 |
| **好设计** | 一个类只做一件事（SRP） | 依赖接口而非具体实现（DIP） |
| **坏设计** | 一个类同时处理数据库、展示、计算 | 修改 A 类导致 B、C、D 都需要改 |
| **目标** | 高内聚 | 低耦合 |

### 11.2 常用度量指标

| 指标 | 定义 | 计算方法 | 质量含义 |
|------|------|---------|---------|
| **Fan-out** | 一个类直接依赖的其他类数量 | 统计 `import` + 字段类型引用 | 过大表示耦合高 |
| **Fan-in** | 依赖该类的其他类数量 | 统计被引用次数 | 过小表示独立但可能缺乏复用 |
| **LCOM**（方法内聚缺乏度） | 方法访问相同字段的程度 | 0=高内聚, 1=低内聚 | 接近0好，接近1说明职责分散 |
| **NOC**（子类数） | 直接子类数量 | 统计 `extends` | 过大可能继承层次不合理 |
| **DIT**（继承深度） | 继承树中的深度 | 从 Object 到类的层次数 | 过深表示设计过于抽象 |
| **Instability**（不稳定性） | 衡量模块变更受影响程度 | `I = Ce / (Ce + Ca)` | I=1 最不稳定，I=0 最稳定 |
| **Abstractness**（抽象度） | 模块中抽象类/接口的比例 | `A = Na / Nc` | A=0 全具体类，A=1 全接口 |
| **Distance from Main Sequence** | 理想线上的偏离距离 | `D = |A + I - 1|` | D→0 最佳，D→1 差 |

### 11.3 主序列距离（Distance from Main Sequence）

```
抽象度 (A)
  ↑
  │   Zone of Pain（痛苦区）
  │   （高度抽象但高度不稳定 — 接口经常变）
  │         ×
  │
  │      理想线 (A + I = 1)
  │      ╱
  │     ╱  × 好设计
  │    ╱
  │   ╱
  │  ╱          Zone of Uselessness（无用区）
  │ ╱            （高度具体但高度稳定 — 僵尸模块）
  │╱               ×
  └───────────────────────────────────────► 不稳定性 (I)
```

| 区域 | 特征 | 诊断 | 建议 |
|------|------|------|------|
| **主序列附近** | 抽象度与稳定性匹配 | 良好的模块设计 | 保持 |
| **痛苦区** | 高抽象度 + 高不稳定性 | 接口频繁变更 | 拆分职责，缩小接口范围 |
| **无用区** | 低抽象度 + 高稳定性 | 具体实现死板僵化 | 考虑引入抽象层 |

> 🎯 **设计质量的核心座右铭**：好的设计不是在第一次就做出完美的决定，而是在后续变化中能以**最小的代价**进行演进。SOLID + 合理的设计模式 + 恰当的架构风格 + 持续的度量反馈 = 可维护的软件系统。
