# 软件工程概论实验

## 课程概述
- **课程性质**：专业核心必修课（配套实验课）
- **适用专业**：计算机类各专业
- **开课学期**：与软件工程概论理论课同步
- **考核方式**：项目答辩 + 文档评审 + 团队贡献评价

## 核心知识点

### 实验一：团队组建与项目选题
- 团队组建
  - 3-5人开发团队，角色分工：
    - 项目经理(PM)：进度管理、会议组织、对外沟通
    - 技术负责人(Tech Lead)：技术选型、架构设计、代码审查
    - 开发人员(Developer)：编码实现
    - 测试人员(QA)：测试用例设计、质量保证
  - 制定团队章程：沟通方式、会议频率、决策机制、冲突处理
- 项目选题
  - 选题原则：功能明确、2-3个月内可完成、技术栈可控
  - 典型选题：在线考试系统、图书管理系统、校园二手交易平台、课程评价系统
  - 撰写项目愿景：一句话描述项目要解决什么问题、目标用户是谁
- Git/GitHub仓库建立
  - 创建Organization或Repository
  - 添加团队成员为Collaborator
  - 设置分支保护规则（main分支需要PR+Review才能合并）
  - 初始化项目README

### 实验二：需求分析
- 需求获取
  - 用户故事(User Story)：作为<角色>，我希望<功能>，以便<价值>
  - 用例建模
    - 识别参与者(Actor)：使用系统的角色（如学生、教师、管理员）
    - 用例图：参与者→用例的关联关系
    - 用例描述：用例名、前置条件、基本事件流、备选事件流、后置条件
- 需求文档撰写
  - 功能需求：系统需要做什么（功能列表+详细描述）
  - 非功能需求：性能要求（响应时间<200ms）、安全性（权限控制）、可用性（99.9%）
  - 界面原型：使用Figma/Axure制作低保真或高保真原型
- 需求评审
  - 团队成员互相检查需求的完整性和一致性
  - 与"用户代表"（可邀请同学扮演）确认需求理解正确

### 实验三：系统设计
- 体系结构设计
  - 前端：单页应用(SPA) / 多页应用(MPA) / 服务端渲染(SSR)
  - 后端：MVC / 三层架构（表现层→业务逻辑层→数据访问层）/ 微服务
  - 整体架构图：前端→API网关→业务服务→数据库，各层之间的通信方式
- 技术选型
  - 前端：React/Vue + 组件库(Ant Design/Element UI) + 状态管理(Redux/Pinia)
  - 后端：Java(Spring Boot)/Python(Django/FastAPI)/Node.js(Express/Koa)
  - 数据库：MySQL + Redis缓存
  - 部署：Docker + Docker Compose
- 数据库设计
  - E-R图：实体识别→属性定义→联系分析
  - 数据库表设计：列出所有表，每表含字段名/类型/约束
  - 索引设计：在常用查询条件列建索引
- 详细设计
  - 类图：核心类的属性、方法、类间关系（继承/关联/依赖）
  - 时序图：关键业务流程的时序图（如用户登录→验证→返回Token→跳转）
  - API接口设计：RESTful API，列表形式列出所有接口（URL/Method/参数/返回值）

### 实验四：编码实现（多轮迭代）
- Git分支管理
  - 分支模型（Git Flow简化版）：
    - main：稳定发布分支
    - develop：开发主分支
    - feature/xxx：功能分支（从develop分出，完成后合并回develop）
    - hotfix/xxx：紧急修复分支（从main分出，完成后合并到main和develop）
  - 日常工作流：git pull → git checkout -b feature/xxx → 编码→ git add/commit → git push → 创建Pull Request
- 代码规范
  - 命名规范：类名大驼峰、方法名小驼峰、常量全大写、数据库表名下划线
  - 代码格式化：使用Prettier(前端)/Google Java Format(后端)/Black(Python)
  - 注释规范：复杂逻辑加注释说明WHY，公共接口写文档注释
- 代码审查(Code Review)
  - PR提交：标题简洁描述做了什么，描述区写实现要点和测试说明
  - Review要点：功能是否正确、是否有Bug、代码是否简洁、是否遵循规范
  - Review意见分类：必须修改(blocking)、建议修改(non-blocking)、提问(question)
- 持续集成
  - 配置GitHub Actions：每次push触发自动构建+自动测试
  - 测试失败不允许合并PR

### 实验五：软件测试
- 单元测试
  - 前端：Jest/Vitest测试组件和工具函数
  - 后端：JUnit(JAVA)/pytest(Python)测试Service层
  - 测试覆盖率要求：核心业务逻辑 > 80%
- 集成测试
  - 测试API接口：用Postman/Swagger或编写自动化集成测试
  - 测试数据库交互：使用测试数据库或内存数据库(H2/SQLite)
- 黑盒测试
  - 等价类划分：将输入域分为有效等价类和无效等价类
  - 边界值分析：测试边界值及其两侧（如输入范围1-100，测试0,1,100,101）
  - 编写测试用例表格：用例编号/测试项/输入/预期输出/实际结果
- Bug管理
  - 在GitHub Issues中记录Bug：标题+复现步骤+预期结果+实际结果+截图
  - Bug生命周期：新建→确认→修复中→已修复→已验证→关闭

### 实验六：项目部署与交付
- 部署
  - Dockerfile编写：FROM基础镜像→COPY代码→RUN安装依赖→EXPOSE端口→CMD启动
  - Docker Compose编排：定义多个服务(前端+后端+数据库)及其依赖关系
  - 部署到云服务器（如阿里云ECS学生机）或使用Vercel/Netlify等平台
- 用户文档
  - 用户手册：系统介绍、安装指南、功能说明（配截图）
  - API文档：Swagger自动生成或手写Markdown
- 项目演示与答辩
  - 演示准备：准备测试数据、预演核心流程
  - PPT结构：项目背景→需求概述→系统设计→核心功能演示→测试报告→项目总结
  - 答辩：每人介绍自己负责的部分

### 实验七：项目回顾
- 团队复盘(Retrospective)
  - 做的好的(Keep)：哪些做法值得继续保持
  - 需要改进的(Improve)：哪些地方可以做得更好
  - 停止做的(Stop)：哪些做法不应该再发生
- 个人总结
  - 技术收获：掌握了哪些新技术/框架
  - 软技能收获：团队协作/沟通的经验
  - 经验教训：如果重来一次会怎么改进
