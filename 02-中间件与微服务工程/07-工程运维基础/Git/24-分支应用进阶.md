## 1. 分支底层原理回顾

### 1.1 分支的本质

```text
分支 = 指向某个commit的指针（一个40字节的文件，内容是40位SHA-1哈希）

创建分支 → 在 .git/refs/heads/ 下新建一个文件
切换分支 → 移动 HEAD 指针 + 更新工作区文件
删除分支 → 删除 .git/refs/heads/ 下的指针文件（commit数据不丢失）
```

```bash
# 验证：查看分支指针的内容
cat .git/refs/heads/main
# 输出：8f3a2c9b1d4e5f6a7b8c9d0e1f2a3b4c5d6e7f80

# 查看这个commit
git cat-file -t 8f3a2c9b1d4
# commit

# 分支有多轻量？
ls -la .git/refs/heads/
# 每个分支文件 = 41字节（40位哈希 + 换行符）
```

### 1.2 HEAD与detached HEAD

| 状态 | HEAD指向 | 场景 | 风险 |
|------|----------|------|:---:|
| **正常** | 指向某个分支引用 | 日常开发 | 无 |
| **detached HEAD** | 直接指向某个commit | `git checkout <commit>` 查看历史 | ⚠️ 在此状态提交可能丢失 |

```bash
# 进入detached HEAD
git checkout 8f3a2c9b

# 修复：为当前状态创建分支
git switch -c temp-branch    # 如果已经有了提交，这样保住代码

# 如果只是查看，直接切回分支即可
git switch main
```

## 2. 企业级分支命名规范

| 前缀 | 用途 | 拉取来源 | 合并目标 | 示例 |
|------|------|----------|----------|------|
| `feature/` | 新功能开发 | `develop` | `develop` | `feature/user-auth` |
| `fix/` | 非生产Bug修复 | `develop` | `develop` | `fix/order-total` |
| `hotfix/` | 生产紧急修复 | `main` | `main` + `develop` | `hotfix/pay-timeout` |
| `release/` | 发布准备 | `develop` | `main` | `release/v2.1.0` |
| `refactor/` | 代码重构 | `develop` | `develop` | `refactor/extract-service` |
| `chore/` | 构建/依赖/工具 | `develop` | `develop` | `chore/upgrade-spring` |

```bash
# 分支命名示例
feature/user-center-auth        # ✅ 小写+连字符
feature/UserAuth                # ❌ 驼峰命名
feature/user_auth               # ❌ 下划线
feature/user-auth-and-profile   # ❌ 太长了
```

> 🎯 **命名原则**：小写字母 + 连字符分隔，前缀明确意图，名称简短（≤4个单词）。

## 3. 三大分支策略深度对比

### 3.1 全景对比表

| 维度 | GitFlow | GitHub Flow | GitLab Flow |
|------|---------|-------------|-------------|
| **长期分支** | main + develop | main | main + 环境分支 |
| **分支数量** | 5种（main/develop/feature/release/hotfix） | 2种（main/feature） | 3-4种（按环境） |
| **发布节奏** | 固定周期（周/月） | 随时发布 | 按环境推进 |
| **版本管理** | 每个release独立分支 | main即最新 | 环境分支即版本 |
| **复杂度** | ⚠️ 高 | ✅ 低 | ⚠️ 中 |
| **CI/CD友好度** | ⚠️ 中 | ✅ 高 | ✅ 高 |
| **适用团队** | 10+人传统企业 | 2-10人互联网 | 中型多环境团队 |

### 3.2 GitFlow（传统企业首选）

```text
main     ●────●────────────●──────  v1.0    v1.1
         │    │            │
develop  ●────┼────●───────┼──────
         │    │    │       │
feature/ ●──┐ │    ●──┐    │
         │  │ │       │    │
release/ │  ●─┘       │  ●─┘
         │            │
hotfix/  │  ●─────────┘
```

```text
适用：Java传统项目、金融、政务、版本发布周期长
优点：结构严谨、版本清晰可追溯
缺点：分支多、合并频繁、敏捷团队会觉得"重"
```

### 3.3 GitHub Flow（互联网微服务首选）

```text
main ──●────────●────────●────  (始终可部署)
       │        │        │
       ●──┐     ●──┐     ●──┐
feature │ feature │ feature │
       ●──┘     ●──┘     ●──┘
       合并      合并      合并
```

```text
适用：Spring Cloud微服务、快速迭代、持续部署
核心规则：
  ① main分支始终可部署
  ② 所有开发从main拉feature分支
  ③ feature分支通过PR合并回main
  ④ main合并触发自动部署
```

### 3.4 GitLab Flow（多环境企业推荐）

```text
main ──●───●────────●────●────
       │   │        │    │
test   │   ●────────●────●────  ← 部署到测试环境
       │            │    │
pre    │            ●────●────  ← 部署到预发环境
       │                 │
prod   ●─────────────────●────  ← 部署到生产环境
```

```text
环境分支 = 环境的"当前版本"
代码流动方向：main → test → pre → prod
每个环境合并前自动运行对应级别的测试
```

### 3.5 选择决策

| 如果你的项目... | 选择 |
|----------------|------|
| 有固定发布周期、需要维护多个版本 | GitFlow |
| 互联网SaaS、持续部署、小团队 | GitHub Flow |
| 多环境（dev/test/pre/prod)、中型企业 | GitLab Flow |

## 4. cherry-pick：精准提交移植

### 4.1 使用场景

| 场景 | 命令 |
|------|------|
| 把dev上的一个Bug修复同步到main | `git cherry-pick <commit>` |
| 把hotfix的修复合并回develop | `git cherry-pick <commit>` |
| 只想要别人的某几个提交，不需要全部merge | `git cherry-pick <C> <D> <E>` |

### 4.2 完整操作

```bash
# 场景：hotfix分支上的安全修复需要移植到develop

# 1. 找到需要移植的commit
git log hotfix --oneline -5
# a1b2c3d fix: 修复SQL注入漏洞(← 只需要这个)
# e4f5g6h chore: 更新版本号
# i7j8k9l docs: 补充注释

# 2. 切换到目标分支
git switch develop

# 3. 精准移植
git cherry-pick a1b2c3d           # 只移植这一个commit

# 4. 如果有冲突 → 解决后
git add .
git cherry-pick --continue         # 继续

# 5. 放弃cherry-pick
git cherry-pick --abort
```

```bash
# 移植多个连续的commit
git cherry-pick a1b2c3d..e4f5g6h   # (a1b2c3d, e4f5g6h] 左开右闭

# 移植多个不连续的commit
git cherry-pick a1b2c3d i7j8k9l
```

> ⚠️ cherry-pick会创建**新的commit**（SHA-1不同），即使内容完全相同。这导致同一个修改在两个分支有不同commit hash，后续merge时Git可能无法识别为"已合并"。

## 5. rebase：历史整理与变基

### 5.1 rebase vs merge

```text
merge（合并）:
  main:    A---B---C
                \     
  feature:       D---E
  结果:     A---B---C---M   ← M是merge commit
                \     /
                 D---E

rebase（变基）:
  main:    A---B---C
                \
  feature:       D---E
  结果:     A---B---C---D'---E'   ← D'和E'是新的commit
```

| 维度 | merge | rebase |
|------|-------|--------|
| 历史记录 | 保留真实分支拓扑 | 线性历史，更干净 |
| commit SHA | 不变 | 重新生成（改写历史） |
| 冲突解决 | 一次性解决 | 每个commit逐一解决 |
| 安全性 | ✅ 安全 | ⚠️ 改变历史 |
| 适用场景 | 公共分支合并 | **个人**功能分支整理 |

### 5.2 rebase安全法则

> ⚠️ **黄金法则：永远不要rebase已经push到公共仓库的commit！**

```bash
# ✅ 安全：整理自己本地的feature分支
git switch feature/my-work
git rebase -i HEAD~3           # 交互式整理最近3个commit
# 操作后
git push --force-with-lease    # 仅当确认无人基于此分支工作时！

# ✅ 安全：将feature变基到最新的main上
git switch feature/my-work
git fetch origin
git rebase origin/main         # 把feature的提交"搬到"最新main上

# ❌ 危险：rebase公共分支
git switch develop             # develop是团队共享的！
git rebase main                # ❌❌❌ 绝对禁止！
```

### 5.3 交互式rebase

```bash
git rebase -i HEAD~4
# 打开编辑器：
pick a1b2c3d feat: 添加用户登录
pick d4e5f6g fix: 修复typo
pick g7h8i9j feat: 补充登录日志
pick j0k1l2m fix: 再修复一个typo

# 修改为：
pick a1b2c3d feat: 添加用户登录
squash g7h8i9j feat: 补充登录日志    # 压入上一个commit
fixup d4e5f6g fix: 修复typo          # 压入且丢弃commit message
fixup j0k1l2m fix: 再修复一个typo
# 结果：4个commit → 1个干净的 "feat: 添加用户登录"
```

| rebase命令 | 作用 |
|-----------|------|
| `pick` | 保留此commit（默认） |
| `squash` | 压入上一个commit，合并commit message |
| `fixup` | 压入上一个commit，丢弃commit message |
| `reword` | 修改commit message |
| `drop` | 删除此commit |
| `reorder` | 改变commit顺序（拖动行） |

## 6. revert：生产安全回滚

### 6.1 revert vs reset

| 操作 | 原理 | 历史 | 远程安全 | 适用 |
|------|------|:---:|:---:|------|
| `git revert` | 创建反向commit抵消目标commit | ✅ 保留 | ✅ 安全 | **生产回滚唯一选择** |
| `git reset` | 移动分支指针到历史commit | ❌ 改写 | ❌ 禁止 | 仅本地未push的commit |

```bash
# revert：生产安全回滚
git revert a1b2c3d                 # 回滚单个commit
git revert a1b2c3d..e4f5g6h        # 回滚多个commit（左开右闭）
git revert -m 1 <merge-commit>     # 回滚merge commit（-m指定保留哪一边）

# revert的revert：取消回滚（恢复被revert的代码）
git revert <revert-commit>
```

> 💡 `git revert` 是Java生产环境唯一推荐的回滚方式。它不删除历史，只是新增一个反向操作，CI/CD历史清晰可审计。

## 7. worktree：多分支并行开发

### 7.1 使用场景

```text
传统方式：一个工作区，频繁stash + switch
  → 切换分支耗时、stash容易搞混、IDE重新索引

worktree方式：多个工作区目录，每个对应一个分支
  → 同时打开两个IDE窗口、互不干扰
```

### 7.2 命令速查

```bash
# 创建worktree
git worktree add ../project-hotfix hotfix/critical
# 在 ../project-hotfix 目录 checkout hotfix/critical 分支

# 查看所有worktree
git worktree list
# /path/to/project        a1b2c3d [main]
# /path/to/project-hotfix d4e5f6g [hotfix/critical]

# 删除worktree
git worktree remove ../project-hotfix

# 清理已删除目录的worktree记录
git worktree prune
```

### 7.3 典型场景

```bash
# 场景：正在feature分支开发，突然需要紧急hotfix

# 1. 当前工作区不变，创建hotfix的worktree
git worktree add ../project-hotfix main
cd ../project-hotfix
git switch -c hotfix/critical-payment

# 2. 在hotfix worktree中修复bug、提交、合并
# ... 修复操作 ...

# 3. 切回原工作区继续开发
cd ../project
git worktree remove ../project-hotfix
```

> 💡 Java后端实战：一个worktree跑`feature/user-module`，另一个worktree跑`feature/order-module`，两个IDEA窗口同时开发，互不干扰。

## 8. 分支保护与权限控制

### 8.1 保护规则配置

```yaml
# GitHub/GitLab 分支保护推荐配置
main / develop 分支：
  ✅ 禁止直接push（必须通过PR/MR）
  ✅ 要求至少1个Approval
  ✅ 要求CI检查全部通过
  ✅ 要求对话全部解决
  ✅ 要求线性历史（禁止merge commit绕过）
  ✅ 禁止force push
  ✅ 合并前分支必须是最新的

release/* 分支：
  ✅ 禁止直接push
  ✅ 要求至少2个Approval
  ✅ 要求CI检查全部通过
```

### 8.2 角色与权限

| 角色 | 可创建分支 | 可合并到 | 可删除分支 | 可修改保护规则 |
|------|:---:|:---:|:---:|:---:|
| Developer | feature/fix/* | — | 自己的feature | — |
| Tech Lead | 全部 | develop | feature/fix | — |
| Maintainer | 全部 | main/release | 全部 | ✅ |

## 9. 分支与CI/CD集成

```yaml
# GitHub Actions：按分支类型触发不同级别的CI
name: CI Pipeline
on:
  push:
    branches:
      - 'feature/**'    # 触发：基础构建+单元测试
      - 'fix/**'
      - 'develop'       # 触发：构建+测试+部署到测试环境
      - 'main'          # 触发：完整流水线+部署到生产
      - 'hotfix/**'     # 触发：快速通道（跳过非关键检查）

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Unit Tests
        run: mvn test
      - name: Deploy to Test (develop only)
        if: github.ref == 'refs/heads/develop'
        run: deploy-to-test.sh
      - name: Deploy to Prod (main only)
        if: github.ref == 'refs/heads/main'
        run: deploy-to-prod.sh
```

## 10. 高频陷阱与避坑指南

| 陷阱 | 后果 | 正确做法 |
|------|------|----------|
| 在公共分支上rebase | 团队历史混乱，冲突地狱 | 仅rebase个人分支 |
| 直接push到main | 绕过CR和CI，线上风险 | 开启分支保护 |
| 长期不合并的分支 | 巨量冲突，合并困难 | feature分支存活≤3天 |
| 忘记删除已合并分支 | 仓库臃肿，`git branch` 几千行 | CI自动删除，手动定期清理 |
| detached HEAD下提交 | 代码可能丢失 | 立即`git switch -c temp` 创建分支 |
| hotfix未合并回develop | 下次发布重复踩坑 | hotfix必须合并到main和develop |
| cherry-pick后用merge | Git无法识别已合并 | cherry-pick后记下commit，避免重复合并 |
| force push公共分支 | 别人基于旧commit的工作全丢 | 仅用 `--force-with-lease` 且仅自己的分支 |

---

> 🎯 **分支进阶的核心**：不是学更多命令，而是建立工程化思维——分支 = 环境隔离 + 需求边界 + 版本管理 + 安全防线。
