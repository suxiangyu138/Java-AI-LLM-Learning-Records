## 1. 多模块工程架构设计

### 1.1 为什么需要多模块架构

单一模块 (Single-Module) 项目在小规模时工作良好，但当项目增长到一定程度后：

| 问题 | 单模块 | 多模块 |
|------|--------|--------|
| 编译时间 | 改一行代码也要编译全量 | 增量编译，只编译变更模块 |
| 依赖关系 | 所有代码互相可见，容易耦合 | 模块间有明确的依赖边界 |
| 团队协作 | 多人修改同一模块，冲突频繁 | 不同团队负责不同模块 |
| 复用性 | 难以抽取公共组件 | common/api 模块可被其他项目复用 |
| 构建配置 | 一套 pom.xml 覆盖所有 | 每个模块可独立配置 |
| 发布粒度 | 必须整体发布 | 可独立版本化和发布 |

### 1.2 企业级模块模板

一个典型的企业级多模块项目结构：

```
company-project/
├── pom.xml                                    # 父 POM (聚合 + 继承)
├── company-bom/                               # Bill of Materials
│   └── pom.xml
├── company-common/                            # 公共工具模块
│   └── pom.xml
├── company-api/                               # API 接口定义 (DTO, Feign 接口)
│   └── pom.xml
├── company-domain/                            # 领域模型模块
│   └── pom.xml
├── company-dao/                               # 数据访问模块
│   └── pom.xml
├── company-service/                           # 业务服务模块
│   └── pom.xml
├── company-web/                               # Web 层模块
│   └── pom.xml
├── company-starter/                           # Spring Boot Starter
│   └── pom.xml
├── company-integration-test/                  # 集成测试模块
│   └── pom.xml
└── company-application/                       # 可执行应用模块
    └── pom.xml
```

### 1.3 模块设计原则

#### Common 模块
```xml
<!-- company-common/pom.xml -->
<project>
    <parent>
        <groupId>com.company</groupId>
        <artifactId>company-parent</artifactId>
        <version>1.0.0-SNAPSHOT</version>
    </parent>
    <artifactId>company-common</artifactId>

    <dependencies>
        <!-- 只依赖最基础的第三方库，不依赖任何内部模块 -->
        <dependency>
            <groupId>cn.hutool</groupId>
            <artifactId>hutool-all</artifactId>
        </dependency>
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
        </dependency>
    </dependencies>
</project>
```

**Common 模块包含的内容：**
- 通用工具类 (StringUtils, DateUtils, CollectionUtils)
- 通用异常定义 (BusinessException, ErrorCode)
- 通用响应封装 (ApiResponse<T>, PageResult<T>)
- 常量定义
- 自定义注解

#### API 模块
```xml
<!-- company-api/pom.xml -->
<project>
    <parent>
        <groupId>com.company</groupId>
```

**API 模块包含的内容：**
- DTO (Data Transfer Object)

### 1.4 依赖管理策略

#### BOM (Bill of Materials) 模式

BOM 是一种集中管理依赖版本的 POM 模式。父 POM 的 `<dependencyManagement>` 只锁定版本，子模块需要显式声明依赖（不写版本号）。

```xml
<!-- company-bom/pom.xml -->
<project>
    <groupId>com.company</groupId>
    <artifactId>company-bom</artifactId>
    <version>1.0.0</version>
    <packaging>pom</packaging>

    <dependencyManagement>
        <dependencies>
            <!-- 锁定所有内部模块版本 -->
            <dependency>
                <groupId>com.company</groupId>
                <artifactId>company-common</artifactId>
                <version>1.0.0</version>
            </dependency>
            <dependency>
                <groupId>com.company</groupId>
                <artifactId>company-api</artifactId>
                <version>1.0.0</version>
            </dependency>
            <!-- 锁定第三方依赖版本 -->
            <dependency>
                <groupId>com.google.guava</groupId>
                <artifactId>guava</artifactId>
                <version>33.0.0-jre</version>
            </dependency>
            <dependency>
                <groupId>cn.hutool</groupId>
                <artifactId>hutool-all</artifactId>
                <version>5.8.25</version>
            </dependency>
        </dependencies>
    </dependencyManagement>
</project>
```

**BOM 的使用方式：**

A 项目使用 BOM：
```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.company</groupId>
            <artifactId>company-bom</artifactId>
            <version>1.0.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

#### Dependency Convergence

Maven Enforcer 的 Dependency Convergence 规则要求一个依赖在依赖树中只能有一个版本：

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-enforcer-plugin</artifactId>
    <version>3.4.1</version>
    <executions>
        <execution>
            <id>enforce-dependency-convergence</id>
            <goals><goal>enforce</goal></goals>
            <configuration>
                <rules>
                    <dependencyConvergence/>
                    <bannedDependencies>
                        <excludes>
                            <!-- 禁止引入过时的依赖 -->
                            <exclude>commons-logging:commons-logging</exclude>
                            <exclude>log4j:log4j</exclude>
                            <exclude>javax.servlet:javax.servlet-api</exclude>
                        </excludes>
                    </bannedDependencies>
                    <requireJavaVersion>
                        <version>[17,)</version>
                    </requireJavaVersion>
                    <requireMavenVersion>
                        <version>[3.8,)</version>
                    </requireMavenVersion>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

#### 依赖冲突解决策略

当 Maven 遇到同一个依赖的多个版本时，使用以下策略：

1. **最短路径优先**：依赖树中路径最短的版本胜出
2. **最先声明优先**：路径相同的情况下，在 POM 中先声明的胜出

**排查冲突的命令：**

```bash
# 查看依赖树
mvn dependency:tree

# 查看特定依赖的冲突
mvn dependency:tree -Dincludes=com.google.guava:guava

# 分析未使用/未声明的依赖
mvn dependency:analyze

# 输出详细信息到文件
mvn dependency:tree -DoutputFile=dependency-tree.txt
```

**依赖树输出示例：**


### 1.5 构建顺序与模块间依赖

Maven 会根据模块间的 `<dependencies>` 自动计算构建顺序：

```
Root
├── company-bom (no dependencies)
├── company-common (no internal dependencies)
├── company-domain (no internal dependencies)
├── company-api → company-common
├── company-dao → company-domain, company-common
├── company-service → company-api, company-dao, company-common
├── company-web → company-service, company-api
├── company-starter → company-common
├── company-application → company-web, company-starter
└── company-integration-test → 所有模块
```

**强制构建顺序：**

```bash
# 构建特定模块及其依赖
mvn -pl company-service -am package

# 构建特定模块及其依赖的模块
mvn -pl company-service -amd package

# 跳过指定模块
mvn -pl '!company-integration-test' install
```

## 2. Maven 高级配置

### 2.1 构建生命周期 (Lifecycle) 深入

Maven 有三个内置生命周期：

| 生命周期 | 用途 | 主要阶段 |
|----------|------|---------|
| **clean** | 清理构建产物 | pre-clean, clean, post-clean |
| **default** | 主构建流程 | validate, compile, test, package, verify, install, deploy |
| **site** | 生成项目文档 | pre-site, site, post-site, site-deploy |

**Default 生命周期核心阶段详解：**

| 阶段 | 描述 | 对应插件 |
|------|------|---------|
| validate | 验证项目配置正确 | maven-enforcer-plugin |
| initialize | 初始化构建状态 | 自定义 |
| generate-sources | 生成源代码 | mapstruct-processor, protobuf |
| process-sources | 处理源代码 | 自定义 |
| generate-resources | 生成资源文件 | 自定义 |
| process-resources | 复制资源到输出目录 | maven-resources-plugin |
| **compile** | 编译源代码 | maven-compiler-plugin |
| process-classes | 字节码后处理 | 自定义 |
| generate-test-sources | 生成测试代码 | 自定义 |
| process-test-sources | 处理测试代码 | 自定义 |
| test-compile | 编译测试代码 | maven-compiler-plugin |
| **test** | 运行测试 | maven-surefire-plugin |
| prepare-package | 打包前准备 | 自定义 |
| **package** | 打包为 JAR/WAR | maven-jar-plugin |
| **verify** | 验证包质量 | maven-enforcer-plugin, jacoco |
| **install** | 安装到本地仓库 | maven-install-plugin |
| **deploy** | 部署到远程仓库 | maven-deploy-plugin |

### 2.2 自定义生命周期扩展

通过 maven-lifecycle 扩展，可以在生命周期中插入自定义逻辑：

```xml
<!-- extensions.xml (位于 META-INF/maven/) -->
<lifecycle>
    <id>quality-check</id>
    <phases>
        <phase>
            <id>pre-package</id>
            <executions>
                <execution>
                    <goals>
                        <goal>checkstyle</goal>
                        <goal>spotbugs</goal>
                    </goals>
                </execution>
            </executions>
        </phase>
        <phase>
            <id>post-integration-test</id>
            <executions>
                <execution>
                    <goals>
                        <goal>sonar-verify</goal>
                    </goals>
                </execution>
            </executions>
        </phase>
    </phases>
</lifecycle>
```

### 2.3 自定义 Maven 插件开发 (Mojo)

Maven 的插件模型基于 Mojo (Maven plain Old Java Object)，每个 Mojo 对应一个插件目标 (goal)。

#### 创建 Mojo 项目

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project>
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.company</groupId>
    <artifactId>company-maven-plugin</artifactId>
    <version>1.0.0</version>
    <packaging>maven-plugin</packaging>

    <dependencies>
        <dependency>
            <groupId>org.apache.maven</groupId>
            <artifactId>maven-plugin-api</artifactId>
            <version>3.9.6</version>
        </dependency>
        <dependency>
            <groupId>org.apache.maven.plugin-tools</groupId>
            <artifactId>maven-plugin-annotations</artifactId>
            <version>3.9.0</version>
            <scope>provided</scope>
        </dependency>
        <dependency>
            <groupId>org.apache.maven</groupId>
            <artifactId>maven-project</artifactId>
            <version>3.0-alpha-2</version>
        </dependency>
    </dependencies>
</project>
```

#### Mojo 实现示例

```java
package com.company.maven.plugin;

import org.apache.maven.plugin.AbstractMojo;
import org.apache.maven.plugin.MojoExecutionException;
import org.apache.maven.plugin.MojoFailureException;
import org.apache.maven.plugins.annotations.LifecyclePhase;
import org.apache.maven.plugins.annotations.Mojo;
import org.apache.maven.plugins.annotations.Parameter;
import org.apache.maven.project.MavenProject;

import java.io.File;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import java.util.stream.Collectors;

/**
 * 自动生成 API 文档的 Mojo 插件。
 * 扫描所有 Controller 类，生成 OpenAPI 风格文档。
 */
@Mojo(
    name = "generate-api-doc",
    defaultPhase = LifecyclePhase.PACKAGE,
    requiresProject = true,
    threadSafe = true
)
public class ApiDocGeneratorMojo extends AbstractMojo {

    /**
     * 扫描的基础包路径
     */
    @Parameter(property = "scanPackage", defaultValue = "com.company")
    private String scanPackage;

    /**
     * 输出目录
     */
    @Parameter(property = "outputDir",
               defaultValue = "${project.build.directory}/api-docs",
               required = true)
    private File outputDir;

    /**
     * 是否强制覆盖已存在的文档
     */
    @Parameter(property = "overwrite", defaultValue = "false")
    private boolean overwrite;

    /**
     * Maven 项目引用
     */
    @Parameter(defaultValue = "${project}", readonly = true)
    private MavenProject project;

    @Override
    public void execute() throws MojoExecutionException, MojoFailureException {
        getLog().info("Starting API documentation generation...");
        getLog().info("Scan package: " + scanPackage);
        getLog().info("Output directory: " + outputDir.getAbsolutePath());

        try {
            // 创建输出目录
            if (!outputDir.exists()) {
                outputDir.mkdirs();
            }

            // 扫描源代码目录查找 Controller
            List<String> sources = scanSourceDirectories();
            getLog().info("Found " + sources.size() + " source files");

            // 生成文档逻辑
            // ... (实际的 Controller 解析逻辑)

            getLog().info("API documentation generated successfully at " + outputDir);

        } catch (Exception e) {
            throw new MojoExecutionException("Failed to generate API docs", e);
        }
    }

    private List<String> scanSourceDirectories() {
        return project.getCompileSourceRoots().stream()
            .map(root -> new File(root, scanPackage.replace('.', File.separatorChar)))
            .filter(File::exists)
            .flatMap(dir -> {
                try {
                    return Files.walk(dir.toPath())
                        .filter(p -> p.toString().endsWith("Controller.java"))
                        .map(Path::toString);
                } catch (Exception e) {
                    getLog().warn("Failed to scan: " + dir, e);
                    return java.util.stream.Stream.empty();
                }
            })
            .collect(Collectors.toList());
    }
}
```

#### 使用自定义插件

```xml
<!-- 在项目中使用 -->
<build>
    <plugins>
        <plugin>
            <groupId>com.company</groupId>
            <artifactId>company-maven-plugin</artifactId>
            <version>1.0.0</version>
            <configuration>
                <scanPackage>com.company.app</scanPackage>
                <overwrite>true</overwrite>
            </configuration>
            <executions>
                <execution>
                    <goals><goal>generate-api-doc</goal></goals>
                    <phase>prepare-package</phase>
                </execution>
            </executions>
        </plugin>
    </plugins>
</build>
```

### 2.5 资源过滤 (Resource Filtering)

资源过滤允许在构建时替换资源文件中的占位符：


### 3.4 Configuration vs Execution Phase

这是 Gradle 最核心的概念之一：

```groovy
// 1. Configuration 阶段（整个文件都会执行）
println "This runs during CONFIGURATION phase"

def myVariable = "configured"
println "Variable created: $myVariable"

tasks.register('delayedTask') {
    // 2. 这部分也在 Configuration 阶段执行
    println "Task configuration runs during CONFIGURATION phase"

    // 3. doFirst/doLast 在 Execution 阶段执行
    doFirst {
        println "This runs during EXECUTION phase (doFirst)"
    }

    doLast {
        println "This runs during EXECUTION phase (doLast)"
    }
}

// 4. << 是 doLast 的简写（已弃用）
tasks.register('anotherTask') {
    doLast {
        println "Also EXECUTION phase"
    }
}

// 5. dependsOn 在 Configuration 阶段解析
tasks.register('dependent') {
    dependsOn('delayedTask')
    doLast {
        println "Runs after delayedTask"
    }
}
```

**重要原则：** Configuration 阶段的代码越少越好，所有耗时操作应该放在 Execution 阶段。

| Task execution time | 执行阶段耗时 | 充分利用缓存和并行 |
| Cache hit rate | 缓存命中率 | 确保 Task 输入不变输出不变 |
| GC pauses | GC 暂停时间 | 调整 JVM 参数 |
| Overlapping tasks | 重叠执行的任务 | 调整任务依赖 |

## 5. 版本管理

### 5.1 语义化版本 (Semantic Versioning)

```
MAJOR.MINOR.PATCH[-PRERELEASE][+BUILD]

示例:
1.2.3               # 正式版
1.2.3-SNAPSHOT      # 开发快照
1.2.3-alpha.1       # 内测版
1.2.3-beta.2        # 公测版
1.2.3-rc.1          # 候选发布版
1.2.3+build.20240101 # 包含构建元数据
```

**版本号变更规则：**

| 版本变化 | 规则 | 示例 |
|---------|------|------|
| MAJOR | 不兼容的 API 修改 | `1.x.x` → `2.0.0` |
| MINOR | 向下兼容的功能新增 | `1.1.x` → `1.2.0` |
| PATCH | 向下兼容的问题修复 | `1.1.1` → `1.1.2` |
| 预览版 | 在版本后加 `-alpha/beta/rc` | `1.0.0-beta.1` |

**SNAPSHOT 最佳实践：**

3. CI 流水线中 SNAPSHOT 默认不部署到 release 仓库
4. 使用 Enforcer 插件阻止发布包含 SNAPSHOT 依赖的 release

## 9. 面试高频题

### 基础概念类

**Q: Maven 的依赖仲裁机制是什么？**
A: 最短路径优先 + 最先声明优先。可以通过 `mvn dependency:tree` 查看依赖树，使用 `<exclusions>` 排除不需要的传递性依赖。

**Q: Gradle 的 Configuration 和 Execution 阶段有什么区别？**
A: Configuration 阶段执行 build.gradle 中的配置代码，构建 Task 依赖图；Execution 阶段按依赖顺序执行 Task 的 action。耗时操作应放在 Execution 阶段。

**Q: SNAPSHOT 版本的用途和注意事项？**
A: SNAPSHOT 表示开发中的不稳定版本，每次构建都会尝试拉取最新。Release 版本不允许依赖 SNAPSHOT，Enforcer 插件可以强制此规则。

### 实战类

**Q: 如何解决 Maven 依赖冲突导致的 ClassNotFoundException？**
A: 
1. 使用 `mvn dependency:tree -Dincludes=<groupId>:<artifactId>` 定位冲突
2. 在对应依赖中使用 `<exclusions>` 排除不需要的版本
3. 在父 POM 的 `<dependencyManagement>` 中明确指定版本
4. 使用 Enforcer 的 dependencyConvergence 规则

**Q: Gradle 多项目构建的优化策略有哪些？**
A:
1. 开启并行构建 (`org.gradle.parallel=true`)
2. 启用构建缓存 (local + remote)
3. 使用 Configuration Cache (`org.gradle.configuration-cache=true`)
4. 按需配置 (`org.gradle.configureondemand=true`)
5. 合理划分模块边界，减少跨模块依赖

**Q: 如何设计企业级 BOM？**
A:
1. 定义公司统一的依赖版本号
2. import Spring Boot、Spring Cloud 等第三方 BOM
3. 内部模块版本统一定义
4. 按照模块类别组织 properties
5. 使用 Enforcer 插件确保版本一致性
6. BOM 本身独立版本化，与业务项目版本解耦

### 场景类

**Q: 项目突然依赖了 logback 和 log4j，导致运行时冲突，怎么处理？**
A: 
1. `mvn dependency:tree` 找到是什么引入了 log4j
2. 在引入 log4j 的依赖上添加 `<exclusions><exclusion>`
3. 使用 SLF4J 桥接包 (log4j-over-slf4j) 统一日志框架
4. 配置 Enforcer 的 bannedDependencies 规则禁止 log4j

**Q: 如何实现构建时自动生成代码？**
A:
- 使用 `annotationProcessor` 在编译期生成代码 (Lombok, MapStruct)
- 编写 Mojo/Gradle Task 在 generate-sources 阶段生成代码
- 使用 Annotation Processing Tool (APT)
- Gradle 的 annotationProcessor 配置和增量编译支持
