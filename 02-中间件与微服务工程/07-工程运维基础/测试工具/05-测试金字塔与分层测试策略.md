## 1. 测试金字塔模型详解

### 1.1 经典三层金字塔

> 🎯 测试金字塔由 Mike Cohn 提出，是测试策略最核心的指导模型。

```
                   ┌─────────────┐
                  ╱               ╲         E2E (端到端测试)
                 ╱    UI Tests     ╲        ⚠️ 慢、脆弱、维护成本高
                ╱    (极少量)        ╲       数量: ~5%
               ╱─────────────────────╲
              ╱                       ╲      Integration (集成测试)
             ╱     Service Tests       ╲     ⚡ 中等速度
            ╱      (适量)               ╲    数量: ~15-20%
           ╱─────────────────────────────╲
          ╱                               ╲    Unit (单元测试)
         ╱         Unit Tests              ╲   ⚡⚡⚡ 快速、稳定
        ╱          (大量)                   ╲  数量: ~60-70%
       ╱─────────────────────────────────────╲
```

### 1.2 各层详细说明

| 层级 | 测试范围 | 工具 | 特点 | 执行时间 | 占比 |
|------|----------|------|------|----------|------|
| **单元测试** | 单个类/方法 | JUnit5 + Mockito | 快速、稳定、隔离、无外部依赖 | 毫秒级 | ~60% |
| **集成测试** | 多个组件交互 | @SpringBootTest, Testcontainers, REST Assured | 验证组件协作、数据库/缓存交互 | 秒级 | ~20% |
| **API/服务测试** | 完整HTTP请求-响应 | REST Assured, WireMock | 验证接口契约、业务场景 | 秒-分钟级 | ~15% |
| **E2E测试** | 完整用户流程 | Selenium, Playwright | 模拟真实用户操作、UI验证 | 分钟级 | ~5% |

### 1.3 反金字塔（冰淇淋甜筒）——常见坏味道

```
╔═══════════════════════╗
║      E2E Tests        ║     ❌ 大量手动/E2E测试
║      (大量)           ║     ❌ 运行慢、不稳定
╠═══════════════════════╣     ❌ 难以定位问题
║    Integration Tests   ║     ❌ 反馈周期长
║       (少量)          ║
╠═══════════════════════╣
║     Unit Tests         ║
║      (极少)           ║
╚═══════════════════════╝

这是"手工测试为主"团队的典型特征，必须扭转！
```

> ⚠️ **危害**：反馈周期长（E2E跑一次几十分钟）、不稳定（环境/网络波动导致误报）、维护成本高、开发效率低。

### 1.4 各层测试最佳实践

```java
// ===== 层1：单元测试（最多、最快） =====
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock private OrderRepository orderRepository;
    @Mock private InventoryClient inventoryClient;
    @InjectMocks private OrderService orderService;
    
    @Test
    void shouldCalculateTotalPrice() {
        // 纯逻辑测试，不涉及Spring容器
        Order order = new Order(List.of(
            new OrderItem("SKU1", 2, new BigDecimal("10.00")),
            new OrderItem("SKU2", 1, new BigDecimal("20.00"))
        ));
        assertEquals(new BigDecimal("40.00"), orderService.calculateTotal(order));
    }
}

// ===== 层2：Service集成测试（验证组件协作） =====
@SpringBootTest
@AutoConfigureMockMvc
class OrderControllerIntegrationTest {
    @Autowired private MockMvc mockMvc; // 不走真实HTTP，但验证完整Spring上下文
    
    @Test
    void shouldCreateOrder() throws Exception {
        mockMvc.perform(post("/api/orders")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"productId\":1,\"quantity\":2}"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.status").value("CREATED"));
    }
}

// ===== 层3：API集成测试（真实HTTP+真实DB） =====
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class OrderApiIntegrationTest {
    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15");
    
    @Test
    void shouldCompleteOrderFlow() {
        // 完整业务流程测试
        given()
            .contentType(ContentType.JSON)
            .body(orderDTO)
        .when()
            .post("/api/orders")
        .then()
            .statusCode(200)
            .body("status", equalTo("CREATED"));
    }
}
```

## 2. FIRST原则

> 🎯 好的单元测试应遵循FIRST原则（Clean Code by Robert C. Martin）

| 原则 | 含义 | 反面例子 | 检查方法 |
|------|------|----------|----------|
| **F**ast 快速 | 测试执行应非常快（毫秒级） | 单元测试中启动Spring容器、连真实数据库 | 运行全部单元测试应在10秒内完成 |
| **I**ndependent 独立 | 测试之间无依赖，可任意顺序执行 | 测试B依赖测试A创建的数据库记录 | 随机运行单个测试也能通过 |
| **R**epeatable 可重复 | 在任何环境、任何时间运行结果一致 | 依赖系统时间、随机数、外部API | CI和本地运行结果一致 |
| **S**elf-Validating 自验证 | 测试结果应明确通过/失败，无需人工判断 | 依赖`System.out.println()`人工看结果 | 只靠断言验证，不看日志 |
| **T**imely 及时 | 测试应在生产代码之前或同时编写 | 代码上线后才补测试 | TDD或至少同步编写 |

### 代码示例：违反 vs 遵守 FIRST

```java
// ❌ 违反 Fast：单元测试中启动Spring（秒级→毫秒级）
@SpringBootTest  // 启动整个Spring容器，3-5秒启动时间
class UserServiceTest {
    @Autowired private UserService userService; // 不必要
}

// ✅ 遵守 Fast：纯Mockito，毫秒级
@ExtendWith(MockitoExtension.class)
class UserServiceTest {
    @Mock private UserRepository repo;
    @InjectMocks private UserService userService;
}

// ❌ 违反 Independent：测试间共享可变状态
private static List<User> sharedUsers = new ArrayList<>(); // 静态可变状态！
@Test void testA() { sharedUsers.add(new User("A")); }
@Test void testB() { assertEquals(1, sharedUsers.size()); } // 依赖testA执行

// ✅ 遵守 Independent：每个测试独立准备数据
@Test void testA() { List<User> users = List.of(new User("A")); ... }
@Test void testB() { List<User> users = List.of(new User("B")); ... }

// ❌ 违反 Repeatable：依赖当前时间
@Test void shouldCheckExpiry() {
    if (LocalDate.now().getMonth() == Month.DECEMBER) { ... } // 12月才跑
}

// ✅ 遵守 Repeatable：使用固定时间
@Test void shouldCheckExpiry() {
    LocalDate fixedDate = LocalDate.of(2024, 12, 25); // 固定
    ...
}

// ❌ 违反 Self-Validating
@Test void test() {
    String result = service.process();
    System.out.println("Result: " + result); // 需人工看
}

// ✅ 遵守 Self-Validating
@Test void test() {
    String result = service.process();
    assertEquals("expected", result); // 自动断言
}
```

## 3. Spring Boot项目分层测试策略

### 3.1 测试切片注解速查

| 注解 | 加载的Bean | 适用场景 | 速度 |
|------|-----------|----------|------|
| `@SpringBootTest` | **全部** Bean | 完整集成测试 | ⚠️ 最慢 |
| `@WebMvcTest(UserController.class)` | **仅Web层** | Controller层测试 | ✅ 快 |
| `@DataJpaTest` | **仅JPA层** (EntityManager, Repository) | Repository测试 | ✅ 快 |
| `@JsonTest` | **仅JSON序列化** | JSON序列化/反序列化测试 | ✅✅ 最快 |
| `@RestClientTest` | **仅REST客户端** | RestTemplate/Feign测试 | ✅ 快 |
| `@DataJdbcTest` | **仅JDBC** | JDBC Repository测试 | ✅ 快 |
| `@JdbcTest` | **仅JDBC** | JdbcTemplate测试 | ✅ 快 |

### 3.2 分层测试代码模板

```java
// Controller层 → @WebMvcTest（只加载Web层）
@WebMvcTest(UserController.class)
class UserControllerTest {
    @Autowired private MockMvc mockMvc;
    @MockBean private UserService userService; // Service层用Mock
    
    @Test void shouldReturnUser() throws Exception {
        when(userService.getUser(1L)).thenReturn(new User(1L, "张三"));
        
        mockMvc.perform(get("/api/users/1"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.name").value("张三"));
    }
}

// Repository层 → @DataJpaTest（只加载JPA层，内嵌数据库）
@DataJpaTest
class UserRepositoryTest {
    @Autowired private TestEntityManager entityManager;
    @Autowired private UserRepository userRepository;
    
    @Test void shouldFindByName() {
        entityManager.persist(new User("张三"));
        Optional<User> result = userRepository.findByName("张三");
        assertTrue(result.isPresent());
    }
}

// Service层 → 纯Mockito（最快，不需要Spring上下文）
@ExtendWith(MockitoExtension.class)
class UserServiceTest {
    @Mock private UserRepository userRepository;
    @InjectMocks private UserService userService;
    
    @Test void shouldReturnUser() {
        when(userRepository.findById(1L)).thenReturn(Optional.of(new User(1L, "张三")));
        assertEquals("张三", userService.getUser(1L).getName());
    }
}

// 完整集成测试 → @SpringBootTest + Testcontainers
@SpringBootTest(webEnvironment = RANDOM_PORT)
@Testcontainers
class FullIntegrationTest {
    @Container
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:15");
    
    @DynamicPropertySource
    static void configure(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", pg::getJdbcUrl);
        registry.add("spring.datasource.username", pg::getUsername);
        registry.add("spring.datasource.password", pg::getPassword);
    }
    
    @Test void shouldCompleteBusinessFlow() { ... }
}
```

## 4. TDD与BDD方法论

### 4.1 TDD（Test-Driven Development）三步循环

```
         ┌──→ ① Red：先写失败的测试
         │        (描述期望行为)
         │
         │        ② Green：写最少代码让测试通过
         │        (不要过度设计)
         │
         └─── ③ Refactor：重构代码
                  (消除重复、改善设计、测试仍然通过)
```

**TDD核心规则**：
1. 只有在测试失败时才写生产代码
2. 只写刚好让测试通过的代码
3. 测试通过后立即重构

### 4.2 BDD（Behavior-Driven Development）

> TDD关注"代码是否正确"，BDD关注"行为是否符合预期"。BDD使用自然语言描述测试。

```java
// Mockito BDD风格
import static org.mockito.BDDMockito.*;

@Test
@DisplayName("用户存在时应返回用户信息")
void shouldReturnUserWhenExists() {
    // Given（前置条件）
    given(userRepository.findById(1L)).willReturn(Optional.of(new User(1L, "张三")));
    
    // When（执行操作）
    User result = userService.getUser(1L);
    
    // Then（验证结果）
    then(userRepository).should(times(1)).findById(1L);
    assertEquals("张三", result.getName());
}
```

## 5. 测试反模式与避坑

| 反模式 | 问题 | 改进 |
|--------|------|------|
| **冰淇淋甜筒** | E2E太多、单元测试太少 | 重构为金字塔：单元60%+集成25%+E2E 5% |
| **测试依赖顺序** | 测试B依赖测试A创建的数据 | 每个测试独立准备数据 |
| **测试私有方法** | 绕过公共接口测试实现细节 | 通过公共方法间接测试 |
| **过度Mock** | Mock了所有依赖，没测到真实交互 | 区分单元测试(Mock)和集成测试(真实) |
| **测试没有断言** | 只调用方法不验证结果 | 每个测试至少有一个assert |
| **Sleep等待** | `Thread.sleep(5000)` 等异步 | 用Awaitility等异步测试工具 |
| **脆弱的测试** | 测试依赖外部环境/时间/顺序 | Mock外部依赖，固定时间和数据 |
| **测试代码有if/for** | 测试逻辑有分支，本身可能出错 | 每个测试只测一个场景 |

## 6. 测试覆盖率的目标与误区

### 6.1 覆盖率指标

| 覆盖率类型 | 说明 | 合理目标 |
|-----------|------|----------|
| **行覆盖率(Line)** | 代码行被执行的比例 | ≥ 80% |
| **分支覆盖率(Branch)** | if/switch每个分支被执行 | ≥ 70% |
| **方法覆盖率(Method)** | 方法被调用的比例 | ≥ 90% |
| **类覆盖率(Class)** | 类被测试的比例 | ≥ 90% |

### 6.2 覆盖率误区

> ⚠️ **高覆盖率 ≠ 高质量测试**。100%覆盖率但所有测试都没有断言，仍然是废纸一堆。

```java
// ❌ 有覆盖率但无意义的测试
@Test void testGetter() {
    User user = new User();
    user.setName("张三");            // 这行被执行了 → 覆盖率+1
    assertEquals("张三", user.getName()); // 没有业务价值
}

// ✅ 有价值的测试
@Test void shouldApplyDiscountForVipUser() {
    User vipUser = new User("张三", UserType.VIP);
    BigDecimal price = pricingService.calculatePrice(vipUser, new BigDecimal("100"));
    assertEquals(new BigDecimal("80"), price); // 验证VIP折扣业务规则
}
```
