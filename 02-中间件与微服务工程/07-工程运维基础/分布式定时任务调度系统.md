# 分布式定时任务调度系统

## 一、定时任务基础

### 1.1 Java 原生定时任务方案

#### 1.1.1 Timer —— 单线程的隐患

Java 最早提供的定时任务工具是 `java.util.Timer`，配合 `TimerTask` 使用。其核心是单线程机制：内部只有一个工作线程串行执行所有任务。

```java
import java.util.Timer;
import java.util.TimerTask;

public class TimerDemo {
    public static void main(String[] args) {
        Timer timer = new Timer();

        timer.schedule(new TimerTask() {
            @Override
            public void run() {
                System.out.println("任务A执行: " + System.currentTimeMillis());
            }
        }, 0, 2000); // 延迟0ms，每2秒执行一次

        timer.schedule(new TimerTask() {
            @Override
            public void run() {
                System.out.println("任务B执行: " + System.currentTimeMillis());
                // 模拟异常
                throw new RuntimeException("任务B异常!");
            }
        }, 0, 2000);

        timer.schedule(new TimerTask() {
            @Override
            public void run() {
                // 由于任务B抛出异常，这个任务永远不会被执行
                System.out.println("任务C永远不会被执行");
            }
        }, 0, 2000);
    }
}
```

**Timer 的致命缺陷：**

- **单线程阻塞**：所有任务共用一个线程，一个任务执行时间过长会阻塞后续任务。
- **异常中断**：任何任务抛出未捕获异常都会导致整个 Timer 线程终止，后续任务全部失效。
- **不推荐生产使用**：Oracle 官方文档也建议使用 `ScheduledExecutorService` 替代 Timer。

#### 1.1.2 ScheduledExecutorService —— 线程池方案

`ScheduledExecutorService` 是 JUC 包提供的定时任务解决方案，基于线程池设计，完美解决了 Timer 的缺陷。

```java
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

public class ScheduledExecutorDemo {
    public static void main(String[] args) {
        ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(4);

        // scheduleAtFixedRate: 固定频率执行（不考虑任务执行时间）
        scheduler.scheduleAtFixedRate(() -> {
            System.out.println("固定频率任务 - " + Thread.currentThread().getName()
                    + " - " + System.currentTimeMillis());
        }, 0, 2, TimeUnit.SECONDS);

        // scheduleWithFixedDelay: 固定延迟（等上次执行完再计时）
        scheduler.scheduleWithFixedDelay(() -> {
            System.out.println("固定延迟任务 - " + Thread.currentThread().getName()
                    + " - " + System.currentTimeMillis());
        }, 0, 2, TimeUnit.SECONDS);

        // 一个任务异常不会影响其他任务
        scheduler.scheduleAtFixedRate(() -> {
            System.out.println("可能异常的任务 - " + Thread.currentThread().getName());
            throw new RuntimeException("异常仅影响当前线程");
        }, 0, 2, TimeUnit.SECONDS);

        // 即使上面的任务抛出异常，这个任务仍然可以正常执行
        scheduler.scheduleAtFixedRate(() -> {
            System.out.println("安全的任务依然运行 - " + Thread.currentThread().getName());
        }, 0, 2, TimeUnit.SECONDS);
    }
}
```

**核心方法解析：**

| 方法 | 行为 | 适用场景 |
|------|------|---------|
| `schedule(Runnable, delay, unit)` | 延迟指定时间后执行一次 | 延迟执行 |
| `scheduleAtFixedRate(task, initialDelay, period, unit)` | 固定频率，不受任务执行时间影响 | 心跳、监控采集 |
| `scheduleWithFixedDelay(task, initialDelay, delay, unit)` | 固定延迟，等上次结束才开始计时 | 数据同步、批处理 |

**fixedRate vs fixedDelay 的经典对比：**

假设任务执行耗时 3 秒，配置间隔 2 秒：
- `scheduleAtFixedRate`：0s 开始 → 3s 结束，第 2s 时本应触发但线程忙，立即补偿 → 第 3s 再次触发，实际执行间隔为 3s（任务时间）。
- `scheduleWithFixedDelay`：0s 开始 → 3s 结束，再等 2s → 第 5s 再次触发，实际执行间隔为 5s（任务时间 + 延迟时间）。

### 1.2 Spring @Scheduled

Spring 通过 `@EnableScheduling` + `@Scheduled` 注解提供了声明式定时任务支持，底层默认基于 `ScheduledExecutorService`。

#### 1.2.1 基础用法

```java
import org.springframework.scheduling.annotation.EnableScheduling;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

@Component
@EnableScheduling
public class ScheduledTasks {

    // cron表达式: 每秒执行一次
    @Scheduled(cron = "0/1 * * * * ?")
    public void taskWithCron() {
        System.out.println("Cron任务执行: " + System.currentTimeMillis());
    }

    // fixedRate: 上次任务开始后2秒执行下一次（不考虑执行时间）
    @Scheduled(fixedRate = 2000)
    public void taskWithFixedRate() {
        System.out.println("FixedRate任务: " + System.currentTimeMillis());
        try {
            Thread.sleep(5000); // 模拟长任务
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    // fixedDelay: 上次任务结束后2秒再执行
    @Scheduled(fixedDelay = 2000)
    public void taskWithFixedDelay() {
        System.out.println("FixedDelay任务: " + System.currentTimeMillis());
    }

    // 初始延迟5秒后，再按固定频率执行
    @Scheduled(initialDelay = 5000, fixedRate = 3000)
    public void taskWithInitialDelay() {
        System.out.println("延迟启动任务: " + System.currentTimeMillis());
    }
}
```

#### 1.2.2 配置线程池

Spring 默认使用单线程执行 `@Scheduled` 任务，这意味着如果有多个 `@Scheduled` 方法，它们会串行执行。生产环境必须配置线程池：

```java
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.annotation.EnableScheduling;
import org.springframework.scheduling.concurrent.ThreadPoolTaskScheduler;

@Configuration
@EnableScheduling
public class SchedulingConfig {

    @Bean
    public ThreadPoolTaskScheduler taskScheduler() {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(10);
        scheduler.setThreadNamePrefix("scheduled-task-");
        scheduler.setWaitForTasksToCompleteOnShutdown(true);
        scheduler.setAwaitTerminationSeconds(30);
        return scheduler;
    }
}
```

#### 1.2.3 @Scheduled 的局限性

- **单机限制**：@Scheduled 只在当前 JVM 进程内有效，如果部署多实例，每个实例都会执行一次任务，导致重复执行。
- **无任务治理**：没有暂停/恢复/重试/告警等运维能力。
- **无分片能力**：一个任务只能在一台机器上全量执行，无法拆分成子任务并行处理。
- **无依赖编排**：不支持任务之间的依赖关系，无法实现 A→B→C 的流程。

### 1.3 Cron 表达式详解

#### 1.3.1 格式

```
 ┌────────── 秒 (0-59)
 │ ┌──────── 分 (0-59)
 │ │ ┌────── 时 (0-23)
 │ │ │ ┌──── 日 (1-31)
 │ │ │ │ ┌── 月 (1-12)
 │ │ │ │ │ ┌ 周 (1-7, 1=周日)
 * * * * * *
```

#### 1.3.2 特殊字符

| 字符 | 含义 | 示例 | 说明 |
|------|------|------|------|
| `*` | 任意值 | `0 * * * * ?` | 每分钟的0秒执行 |
| `?` | 不指定（仅用于日和周） | `0 0 12 ? * *` | 每天12点，不指定星期 |
| `-` | 区间 | `0 0-5 * * * ?` | 每小时0-5分执行 |
| `,` | 枚举 | `0 0,15,30 * * * ?` | 每小时0/15/30分执行 |
| `/` | 步长 | `0 0/5 * * * ?` | 每5分钟执行 |
| `L` | 最后（Last） | `0 0 12 L * ?` | 每月最后一天12点 |
| `W` | 最近工作日 | `0 0 12 15W * ?` | 每月15号最近的工作日 |
| `#` | 第几个周几 | `0 0 12 ? * 1#3` | 每月第3个周日 |

#### 1.3.3 常用模板

```yaml
每5分钟执行:      "0 0/5 * * * ?"
每30秒执行:       "0/30 * * * * ?"
每小时执行:       "0 0 0/1 * * ?"
每天凌晨1点:      "0 0 1 * * ?"
每天中午12点:     "0 0 12 * * ?"
每天上午9点到下午5点: "0 0 9-17 * * ?"
每月1号凌晨2点:   "0 0 2 1 * ?"
每周一凌晨3点:    "0 0 3 ? * 2"
工作日每天9点半:  "0 30 9 ? * 2-6"
每月最后一天:     "0 0 12 L * ?"
每间隔10秒执行:   "*/10 * * * * *"
```

## 二、分布式调度核心问题

### 2.1 任务重复执行

**问题**：当应用部署多个实例时，如果每个实例都执行相同的定时任务，会导致数据重复处理、接口重复调用、资源浪费甚至数据错误。

**解决方案对比：**

| 方案 | 原理 | 缺点 |
|------|------|------|
| 数据库乐观锁 | 任务执行前更新状态，使用版本号 | 依赖数据库，有性能开销 |
| Redis分布式锁 | SETNX加锁，设置过期时间 | 需处理锁超时和释放问题 |
| 调度中心统一调度 | 调度中心触发，指定某个执行器执行 | 最推荐，解耦彻底 |

**Redis分布式锁实现示例：**

```java
@Service
public class OrderSyncTask {
    @Autowired
    private StringRedisTemplate redisTemplate;

    private static final String LOCK_KEY = "task:lock:orderSync";
    private static final long LOCK_TTL = 30; // 30秒

    @Scheduled(cron = "0 0/5 * * * ?")
    public void syncOrders() {
        String lockValue = UUID.randomUUID().toString();
        Boolean locked = redisTemplate.opsForValue()
                .setIfAbsent(LOCK_KEY, lockValue, LOCK_TTL, TimeUnit.SECONDS);

        if (Boolean.TRUE.equals(locked)) {
            try {
                // 执行任务...
                System.out.println("开始同步订单: " + Instant.now());
            } finally {
                // 使用Lua脚本确保原子性释放锁
                String script = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                                "return redis.call('del', KEYS[1]) else return 0 end";
                redisTemplate.execute(
                    new DefaultRedisScript<>(script, Long.class),
                    Collections.singletonList(LOCK_KEY),
                    lockValue
                );
            }
        } else {
            System.out.println("其他实例正在执行，跳过本次");
        }
    }
}
```

### 2.2 任务分片

当任务涉及海量数据（如处理 1000 万条用户数据），单机处理耗时过长，需要将数据拆分成多个分片，由多个执行器并行处理。

**分片策略示例：**

```java
public class ShardingTask {

    /**
     * 处理1000万用户数据，分10个分片
     * shardIndex: 当前分片索引 (0-9)
     * shardTotal: 总分片数 (10)
     */
    public void processUsers(int shardIndex, int shardTotal) {
        int totalUsers = 10_000_000;
        int pageSize = 1000;
        int totalPages = totalUsers / pageSize;

        for (int page = 0; page < totalPages; page++) {
            // 只处理当前分片负责的页面
            if (page % shardTotal != shardIndex) {
                continue;
            }

            // SELECT * FROM users LIMIT pageSize OFFSET page * pageSize
            List<User> users = userMapper.selectPage(pageSize, page * pageSize);
            for (User user : users) {
                process(user);
            }
        }
    }

    // 基于ID取模的分片方式（更优，避免分页偏移量问题）
    public void processUsersByIdMod(int shardIndex, int shardTotal) {
        // SELECT * FROM users WHERE id % #{shardTotal} = #{shardIndex}
        List<User> users = userMapper.selectByMod(shardTotal, shardIndex);
        for (User user : users) {
            process(user);
        }
    }
}
```

### 2.3 任务编排

复杂业务场景下，任务之间存在依赖关系，需要 DAG（有向无环图）编排能力。

```
    任务A（拉取数据）
       /        \
   任务B(清洗)  任务C(校验)
       \        /
    任务D（写入仓库）
       |
    任务E（发送通知）
```

**编排需求：**
- **串行依赖**：B 依赖 A，C 依赖 B → 按序执行
- **并行执行**：B 和 C 没有依赖关系 → 可同时执行
- **条件分支**：A 成功 → B，A 失败 → C
- **超时控制**：单个任务超时则 DAG 失败

### 2.4 任务治理

生产环境中定时任务需要完善的治理能力：

| 治理能力 | 说明 |
|---------|------|
| **暂停/恢复** | 运维需要临时停止任务，排查问题后再恢复 |
| **手动触发** | 跳过调度周期，立即执行一次 |
| **重试机制** | 失败后自动重试，支持重试次数和间隔配置 |
| **失败告警** | 钉钉/邮件/短信通知，及时响应 |
| **执行日志** | 每次执行的完整日志，支持在线查看 |
| **执行统计** | 成功率、耗时分布、执行次数趋势 |
| **故障转移** | 执行器宕机后自动切换到其他节点 |

### 2.5 高可用

分布式调度系统自身必须具备高可用能力：

- **调度中心集群**：多个调度中心节点，一台宕机不影响调度任务
- **执行器集群**：多台执行器注册到调度中心，调度中心智能分配
- **任务结果持久化**：调度记录持久化到数据库，丢失可追溯
- **幂等性设计**：同一条任务重复调度不会产生重复数据

## 三、XXL-JOB（重点）

XXL-JOB 是大众点评许雪里开源的分布式任务调度平台，国内使用最广泛，GitHub Star 超过 27k。它设计轻量、开箱即用、功能完善，是中小型公司的首选。

### 3.1 整体架构

```
┌─────────────────────────────────────────────────┐
│                  调度中心 Admin                    │
│  ┌───────────┐ ┌───────────┐ ┌───────────┐       │
│  │ Quartz    │ │触发器管理   │ │ 监控面板   │       │
│  │ (触发引擎) │ │(cron配置)  │ │ (执行记录)  │       │
│  └─────┬─────┘ └───────────┘ └───────────┘       │
│        │ 触发调度                                  │
│        ▼ HTTP请求(内嵌Netty)                       │
├────────┼─────────────────────────────────────────┤
│  执行器 │  执行器B  │  执行器C                      │
│  ┌─────┴─────┐                                   │
│  │ JobThread │                                   │
│  │  (任务线程) │                                   │
│  │ ┌────────┐ │                                   │
│  │ │任务实现 │ │                                   │
│  │ └────────┘ │                                   │
│  └───────────┘                                   │
└─────────────────────────────────────────────────┘
```

**核心组件：**

| 组件 | 职责 | 部署 |
|------|------|------|
| **调度中心（Admin）** | 管理任务、触发调度、监控日志、告警 | 独立部署，至少 2 节点 |
| **执行器（Executor）** | 接收调度指令，执行具体任务逻辑 | 业务系统内嵌入，集群部署 |

**交互流程：**
1. 执行器启动后注册到调度中心
2. 调度中心基于 Quartz 解析 cron 表达式，到时间触发任务
3. 调度中心根据路由策略选择目标执行器
4. 调度中心通过 HTTP POST 请求向执行器发送执行指令
5. 执行器启动 `JobThread` 执行任务
6. 执行完毕，执行器通过 HTTP POST 回调调度中心报告结果
7. 调度中心持久化执行记录

### 3.2 核心概念

#### 3.2.1 执行器（Executor）

执行器是业务系统中嵌入的组件，通过 `@XxlJobExecutor` 或 Spring XML 配置集成。

```yaml
# application.yml
xxl:
  job:
    executor:
      appname: my-executor          # 执行器AppName，用于注册
      address: ''                    # 执行器地址，空则自动获取IP
      ip: ''                         # 强制指定IP
      port: 9999                     # 执行器端口，用于与调度中心通信
      logpath: /data/applogs/xxl-job/jobhandler/  # 日志路径
      logretentiondays: 30           # 日志保留天数
    admin:
      addresses: http://localhost:8080/xxl-job-admin  # 调度中心地址
```

**注册方式：**
- **自动注册**（推荐）：执行器启动时自动上报 IP 和端口，调度中心维护在线列表
- **手动录入**：在 Admin 页面手动填写执行器地址，适合 IP 固定的场景

#### 3.2.2 任务（Job）

任务定义在 Admin 页面中配置，核心参数：

| 参数 | 说明 |
|------|------|
| **JobHandler** | 执行器中 @XxlJob 注解指定的名称 |
| **Cron** | cron 表达式 |
| **路由策略** | 选择一个执行器的方式 |
| **阻塞处理** | 任务超时未完成时新触发的处理策略 |
| **GLUE类型** | Java/Shell/Python 等 |
| **任务参数** | 以字符串形式传递给执行器 |

### 3.3 路由策略详解

XXL-JOB 提供了 9 种路由策略，满足不同场景需求：

#### 3.3.1 轮询（Round Robin）

按顺序依次分配执行器。`A→B→C→A→B→C`，适合所有执行器性能均匀的场景。

#### 3.3.2 随机（Random）

随机选择一个执行器。适合执行器性能相近的场景，负载均衡较为均匀。

#### 3.3.3 第一个 / 最后一个

固定选择注册列表中第一个或最后一个执行器。适合指定特定节点执行任务的场景。

#### 3.3.4 一致性哈希（Consistent Hash）

根据任务 ID 进行哈希计算，相同任务始终分配到同一执行器。具有亲和性，适合需要缓存或本地状态的场景。当执行器增减时，仅影响少量任务的分配。

#### 3.3.5 最不经常使用（LFU）

优先选择历史被调度次数最少的执行器。适合负载不均衡需动态调整的场景。

#### 3.3.6 最近最久未使用（LRU）

优先选择历史最久未被调度的执行器。适合执行器按需释放资源的场景。

#### 3.3.7 故障转移（Failover）

**核心策略之一。** 自动探测执行器是否在线，仅向在线节点下发任务。如果执行器宕机，自动切换到下一个可用节点，确保任务不丢失。

```java
// 故障转移核心逻辑（伪代码）
public ReturnT<String> failoverRoute(JobTriggerParam param, List<String> addressList) {
    for (String address : addressList) {
        if (isAlive(address)) { // 心跳检测
            return runTask(address, param);
        }
    }
    return new ReturnT<>(ReturnT.FAIL_CODE, "无可用执行器");
}
```

#### 3.3.8 忙碌转移（BusyOver）

发送任务前先检测执行器当前是否正在执行任务，如果忙碌则转移到下一个执行器。避免任务堆积在某一个节点上。

#### 3.3.9 分片广播（Sharding Broadcast）

**最重要、最强大的策略。** 调度中心向所有执行器下发任务，每个执行器接收到的任务相同，但携带不同的分片参数。执行器根据分片参数处理自己的那部分数据。

### 3.4 阻塞处理策略

当任务执行时间超过调度周期（如任务每 1 分钟调度一次，但执行耗时 3 分钟），新触发的调度该如何处理？

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **单机串行（默认）** | 新调度等待上次执行完成后再开始 | 通用场景 |
| **丢弃后续调度** | 上次未完成时，新调度直接丢弃 | 数据采集（丢失可控） |
| **覆盖之前调度** | 终止上次执行，开始新调度 | 配置刷新（立即生效） |

### 3.5 GLUE 模式

**GLUE（胶水）模式** 是 XXL-JOB 的特色功能，允许在 Admin 页面在线编写、修改任务代码，无需重新部署执行器。

**实现原理：**
1. 在 Admin 页面编辑 GLUE 代码（Groovy/Shell/Python 等）
2. Admin 将代码保存到数据库
3. Admin 将代码源文件推送到执行器
4. 执行器使用 GroovyClassLoader 动态编译并执行


### 3.6 分片广播原理（深度）

分片广播是 XXL-JOB 最核心的特性之一，用于处理大数据量任务的并行执行。

#### 3.6.1 执行流程

```
1. 调度中心从执行器注册表获取所有在线执行器列表
   例如: [192.168.1.10:9999, 192.168.1.11:9999, 192.168.1.12:9999]

2. 调度中心构造分片参数:
   - shardIndex: 执行器在列表中的索引 (0, 1, 2)
   - shardTotal: 执行器总数 (3)

3. 同时向3个执行器发起HTTP请求:
   请求A: .../run?shardIndex=0&shardTotal=3
   请求B: .../run?shardIndex=1&shardTotal=3
   请求C: .../run?shardIndex=2&shardTotal=3

4. 每个执行器根据 shardIndex/shardTotal 处理对应数据分片
```

#### 3.6.2 执行器端代码

```java
@Component
public class ShardingTask {

    @XxlJob("userDataShardingJob")
    public void userDataShardingHandler() {
        // 获取分片参数
        int shardIndex = XxlJobHelper.getShardIndex();   // 当前分片索引
        int shardTotal = XxlJobHelper.getShardTotal();   // 总分片数

        XxlJobHelper.log("当前分片: {}/{}", shardIndex, shardTotal);

        // 方式一：基于ID取模
        // SELECT id, name FROM users WHERE id % #{shardTotal} = #{shardIndex} AND deleted = 0
        List<User> users = userMapper.selectByIdMod(shardIndex, shardTotal);
        for (User user : users) {
            processUser(user);
            XxlJobHelper.log("处理用户: {}", user.getId());
        }

        // 方式二：基于偏移量
        int pageSize = 500;
        int pageNo = shardIndex * pageSize;
        while (true) {
            // SELECT * FROM users LIMIT #{pageSize} OFFSET #{pageNo}
            List<User> page = userMapper.selectPage(pageSize, pageNo);
            if (page.isEmpty()) break;
            for (User user : page) {
                // 只处理属于当前分片的数据
                if (pageNo / pageSize % shardTotal == shardIndex) {
                    processUser(user);
                }
            }
            pageNo += pageSize * shardTotal; // 跳过其他分片的数据范围
        }

        XxlJobHelper.handleSuccess("分片任务完成");
    }
}
```

#### 3.6.3 分片策略建议

| 数据特征 | 推荐分片策略 | SQL 写法 |
|---------|-------------|---------|
| 自增主键、连续 | ID 取模 | `WHERE id % ? = ?` |
| 非连续、数据量大 | 范围分片 | `WHERE id BETWEEN ? AND ?` |
| 按时间 | 日期分片 | `WHERE date BETWEEN ? AND ?` |
| 按区域 | 区域取模 | `WHERE region % ? = ?` |

### 4.1 ElasticJob

ElasticJob 是当当网开源的分布式调度框架，基于 Zookeeper 实现，在弹性伸缩和分片方面表现突出。

#### 4.1.1 核心特性

### 4.2 PowerJob

PowerJob（原 OhMyScheduler）是新一代分布式调度框架，由阿里技术团队开源，引入了 MapReduce 模型。

#### 4.2.1 MapReduce 任务模型

```java
@Component
public class PowerJobMapReduceTask implements MapReduceTask {

    @Override
    public ProcessResult process(TaskContext context) {
        // 1. 拆分阶段：将大任务拆分成多个子任务
        if (context.isRootTask()) {
            List<SubTask> subTasks = splitTasks();
            return map(subTasks, "PROCESS_SUB_TASK");
        }

        // 2. 执行阶段：子任务处理
        SubTask subTask = (SubTask) context.getSubTask();
        processSubTask(subTask);
        return new ProcessResult(true, "处理成功");
    }

    @Override
    public ProcessResult reduce(TaskContext context) {
        // 3. 聚合阶段：汇总所有子任务结果
        List<SubTaskResult> allResults = context.getSubTaskResults();
        aggregateResults(allResults);
        return new ProcessResult(true, "聚合完成");
    }
}
```

#### 4.2.2 PowerJob 的优势

- **MapReduce 模型**：类似大数据处理，任务自动拆分和聚合
- **工作流 DAG**：支持复杂的任务依赖编排
- **容器化部署**：支持 Docker 部署执行器
- **性能卓越**：单机支持数千 QPS 的调度频率

### 4.3 Quartz

Quartz 是 Java 领域最老牌的调度框架，XXL-JOB 等众多调度系统的底层都依赖它。

#### 4.3.1 核心 API

```java
public class QuartzDemo {
    public static void main(String[] args) throws Exception {
        // 1. 创建调度器
        SchedulerFactory schedulerFactory = new StdSchedulerFactory();
        Scheduler scheduler = schedulerFactory.getScheduler();

        // 2. 定义 JobDetail（任务描述）
        JobDetail jobDetail = JobBuilder.newJob(MyJob.class)
                .withIdentity("myJob", "group1")
                .usingJobData("key", "value")  // 传递参数
                .build();

        // 3. 定义 Trigger（触发器）
        Trigger trigger = TriggerBuilder.newTrigger()
                .withIdentity("myTrigger", "group1")
                .startNow()
                .withSchedule(CronScheduleBuilder.cronSchedule("0/5 * * * * ?"))
                .build();

        // 4. 调度器注册任务
        scheduler.scheduleJob(jobDetail, trigger);

        // 5. 启动调度器
        scheduler.start();
    }
}

// Job 实现
public class MyJob implements Job {
    @Override
    public void execute(JobExecutionContext context) {
        JobDataMap dataMap = context.getJobDetail().getJobDataMap();
        System.out.println("任务执行，参数: " + dataMap.getString("key"));
    }
}
```

**四要素关系：**

```
Scheduler（调度器）
    ├── 管理 JobDetail 和 Trigger
    ├── 启动/暂停/停止
    └── 一个 Scheduler 可以注册多个 JobDetail

JobDetail（任务实例）
    ├── Job 的元数据
    ├── 任务类 + 参数
    └── newInstance() → 每次触发创建新实例

Trigger（触发器）
    ├── CronTrigger: cron 表达式
    ├── SimpleTrigger: 简单频率
    └── 关联到唯一的 JobDetail

Job（任务逻辑）
    └── execute() 方法实现业务
```

#### 4.3.2 JobStore

| 存储方式 | 说明 | 适用场景 |
|---------|------|---------|
| **RAMJobStore** | 内存存储，性能高，重启丢失 | 开发测试 |
| **JobStoreTX** | JDBC 存储，支持事务，不依赖外部事务管理器 | 单机集群 |
| **JobStoreCMT** | JDBC + 容器管理事务 | Java EE 环境 |

#### 4.3.3 Quartz 集群模式

Quartz 通过数据库锁实现集群调度：

```properties
org.quartz.jobStore.isClustered = true
org.quartz.jobStore.clusterCheckinInterval = 20000
org.quartz.scheduler.instanceId = AUTO
```

**集群原理：**
- 所有节点共享同一个数据库
- 使用 `QRTZ_LOCKS` 表实现悲观锁
- 获取到锁的节点执行任务触发
- 心跳超时（clusterCheckinInterval）确定节点失效

**QRTZ_LOCKS 表结构：**

| 字段 | 类型 | 说明 |
|------|------|------|
| SCHED_NAME | VARCHAR(120) | 调度器名称 |
| LOCK_NAME | VARCHAR(40) | 锁名称（TRIGGER_ACCESS / JOB_ACCESS 等） |

**集群不足之处：**
- 数据库锁成为瓶颈，高并发场景性能受限
- 节点数增加时数据库竞争加剧
- 不支持任务分片
- 无管理界面

## 六、最佳实践与注意事项

### 6.1 任务幂等性

所有定时任务都应该设计为幂等的——重复执行不会产生副作用：

```java
@XxlJob("idempotentJob")
public void idempotentJob() {
    // 幂等性检查：先检查是否已处理
    String dateStr = LocalDate.now().toString();
    if (processLogMapper.exists(dateStr)) {
        XxlJobHelper.log("今日数据已处理，跳过");
        XxlJobHelper.handleSuccess("已处理，跳过");
        return;
    }

    // 执行处理
    doProcess();

    // 记录处理日志
    processLogMapper.insert(new ProcessLog(dateStr));
}
```

### 6.2 任务超时控制

长任务必须设置超时，避免资源泄漏：

```java
@XxlJob("timeoutControlledJob")
public void timeoutControlledJob() {
    long timeout = 30_000; // 30秒超时
    long deadline = System.currentTimeMillis() + timeout;

    while (System.currentTimeMillis() < deadline) {
        // 处理一批数据
        List<Data> batch = fetchBatch();
        if (batch.isEmpty()) {
            break;
        }
        processBatch(batch);
    }

    if (System.currentTimeMillis() >= deadline) {
        XxlJobHelper.handleFail("任务执行超时");
    } else {
        XxlJobHelper.handleSuccess("任务完成");
    }
}
```

### 6.3 日志规范

- 每个任务的关键步骤都要打日志
- 日志包含业务主键，方便问题追踪
- 使用 `XxlJobHelper.log()` 而非 `log.info()`，前者会上报到 Admin

### 6.4 生产部署建议

```
1. 调度中心集群：至少2个节点，通过Nginx反向代理
2. 执行器集群：至少2个节点，确保单点故障不影响业务
3. 数据库主备：调度中心数据库使用主备架构
4. 监控告警：配置钉钉/邮件告警，失败时及时通知
5. 灰度发布：新任务先在测试环境验证，再上线生产
6. 任务分片：数据量大的任务使用分片广播策略
```

## 总结

一个完整的分布式定时任务调度系统需要具备以下能力，可以作为技术选型的核心关注点：

- [ ] **可视化运维**：任务管理、日志查看、执行记录一目了然
- [ ] **路由策略**：支持轮询、随机、故障转移、分片广播等多种策略
- [ ] **分片执行**：大任务自动拆分为多个任务并行处理，大幅提升效率
- [ ] **任务编排**：支持任务依赖、DAG 执行流程，适应复杂业务
- [ ] **高可用**：调度中心和执行器均支持集群，无单点故障
- [ ] **弹性伸缩**：执行器动态上下线，自动分配任务
- [ ] **GLUE 模式**：在线编辑代码、热部署，适合敏捷迭代
- [ ] **失败重试**：失败后自动重试，可配置重试策略
- [ ] **告警通知**：任务失败时多渠道通知运维人员
- [ ] **权限控制**：多环境、多项目隔离，权限分级管理

在技术选型上，XXL-JOB 凭借其轻量、易用、功能全面的特点，适合大多数企业的分布式调度场景；ElasticJob 在弹性伸缩和分片方面更为出色；PowerJob 则代表了新一代的 MapReduce 调度方向。实际选型时，应结合团队技术储备、业务复杂度和运维能力综合考量。
