## 1. 数据模型：Metric + Labels

```text
<metric_name>{<label1>=<value1>, <label2>=<value2>, ...} <value> [timestamp]

示例：
http_requests_total{method="GET", handler="/api/users", status="200"} 10247 1705315200
```

| 组成部分 | 说明 | 示例 |
|----------|------|------|
| **Metric Name** | 指标名称，描述测量对象 | `http_requests_total` |
| **Labels** | Key-Value 维度标签 | `method="GET"`, `status="200"` |
| **Value** | 64 位浮点数 | `10247` |
| **Timestamp** | 毫秒级时间戳（可选） | `1705315200` |

> 💡 **核心理解**：`MetricName + 唯一的 Labels 组合` = 一条 Time Series（时间序列）。Label 值的每种组合都是一条独立的时间线。

## 2. Counter：只增不减的计数器

> Counter 是累计指标，只能增加或重置为零。适合计数类场景。

| 场景 | 指标示例 |
|------|----------|
| HTTP 请求总数 | `http_requests_total` |
| 错误次数 | `errors_total` |
| 任务完成数 | `tasks_completed_total` |
| 流量累计 | `network_bytes_received_total` |

```text
# Java Micrometer 暴露的 Counter 示例
http_server_requests_seconds_count{method="GET",uri="/api/users",status="200"} 15234
```

**PromQL 查询**：

```promql
# Counter 不能直接用绝对值，必须用 rate()/irate() 求速率
rate(http_requests_total[5m])              # 5 分钟内每秒请求速率
irate(http_requests_total[5m])             # 瞬时速率（用于高精度告警）

# 对比
increase(http_requests_total[1h])          # 1 小时内增量
```

## 3. Gauge：可增可减的仪表盘

> Gauge 是瞬时值，可升可降。适合状态类场景。

| 场景 | 指标示例 |
|------|----------|
| 内存使用量 | `jvm_memory_used_bytes` |
| CPU 使用率 | `node_cpu_seconds_total` (rate) |
| 线程数 | `jvm_threads_live_threads` |
| 连接池活跃数 | `hikaricp_connections_active` |
| 队列长度 | `queue_size` |

```text
# JVM 内存使用（Gauge）
jvm_memory_used_bytes{area="heap"} 5.24e+08

# 磁盘使用率
node_filesystem_avail_bytes{mountpoint="/"} 5.36870912e+10
```

**PromQL 查询**：

```promql
# Gauge 可直接使用
jvm_memory_used_bytes / jvm_memory_max_bytes * 100    # 堆内存使用率%
node_filesystem_avail_bytes / node_filesystem_size_bytes * 100  # 可用磁盘百分比

# Gauge 的聚合
avg_over_time(jvm_threads_live_threads[1h])            # 1 小时内平均线程数
```

## 4. Histogram：分布统计直方图

> Histogram 将观测值分桶统计，自动生成 `_bucket`、`_sum`、`_count` 三个子指标。**最常用的指标类型**。

```text
# HTTP 请求延迟 Histogram
http_request_duration_seconds_bucket{le="0.01"}  500
http_request_duration_seconds_bucket{le="0.05"}  2000
http_request_duration_seconds_bucket{le="0.1"}   3800
http_request_duration_seconds_bucket{le="0.5"}   4500
http_request_duration_seconds_bucket{le="1.0"}   4800
http_request_duration_seconds_bucket{le="+Inf"}  5000
http_request_duration_seconds_sum   1234.5
http_request_duration_seconds_count 5000
```

| 子指标 | 说明 |
|--------|------|
| `_bucket{le="X"}` | ≤X 秒的请求计数（累积） |
| `_sum` | 所有请求的总延迟（秒） |
| `_count` | 总请求数 |
| `_bucket{le="+Inf"}` | = `_count`（所有请求） |

**PromQL 查询**：

```promql
# P99 延迟（核心！）
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))

# P50 / P95
histogram_quantile(0.50, rate(http_request_duration_seconds_bucket[5m]))
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))

# 平均延迟
rate(http_request_duration_seconds_sum[5m]) / rate(http_request_duration_seconds_count[5m])
```

## 5. Summary：客户端分位数

> Summary 在客户端直接计算分位数，无需服务端 `histogram_quantile`。**灵活性低于 Histogram，不推荐新项目使用**。

```text
# Summary 暴露的指标
http_request_duration_seconds{quantile="0.5"} 0.045
http_request_duration_seconds{quantile="0.9"} 0.12
http_request_duration_seconds{quantile="0.99"} 0.35
http_request_duration_seconds_sum   1234.5
http_request_duration_seconds_count 5000
```

| 特性 | 说明 |
|------|------|
| 分位数计算 | 客户端已完成，直接暴露 `quantile` 标签 |
| 聚合能力 | ❌ 无法在服务端聚合多个实例的分位数 |
| 适用场景 | 单实例、不需要跨实例聚合的场景 |

---

## 6. Histogram vs Summary 选型

| 维度 | Histogram | Summary |
|------|-----------|---------|
| 分位数计算 | 服务端 `histogram_quantile()` | 客户端预计算 |
| 跨实例聚合 | ✅ 可聚合 | ❌ 无法聚合 |
| 任意分位数 | ✅ 可查任意 Pxx | ❌ 仅预定义分位数 |
| 精度 | 依赖 Bucket 设置 | 较精确 |
| 客户端开销 | 较低（仅计数） | 较高（计算分位数） |
| **推荐度** | ⭐⭐⭐ **首选** | ⭐ 特殊场景 |

> 🎯 **结论**：新项目一律使用 Histogram。仅在无法接受 Histogram 精度损失且不需要聚合的场景使用 Summary。

## 7. Label 使用最佳实践

### ✅ DO

```promql
# 合理 Label：稳定的维度
http_requests_total{method="GET", handler="/api/users", status="200"}
node_cpu_seconds_total{cpu="0", mode="idle"}
```

| 适合做 Label | 示例 |
|-------------|------|
| HTTP 方法 | `method="GET"` |
| 状态码 | `status="200"` |
| 接口路径 | `handler="/api/users"` |
| 实例标识 | `instance="10.0.1.10:8080"` |
| 环境标识 | `env="prod"` |

### ❌ DON'T

| 不要做 Label | 原因 | 替代方案 |
|-------------|------|----------|
| 用户 ID / 请求 ID | 造成 Series 爆炸 | 用日志追踪 |
| 时间戳 | 每条 Series 唯一 | Prometheus 自带时间戳 |
| 高基数 IP 地址 | 10 万 IP = 10 万 Series | 聚合去掉 IP，或用 Log 记录 |
| 随机值 | 无聚合价值 | 用 Counter |

> ⚠️ **Label 基数原则**：单个 Metric 的 Series 数量 = 各 Label 取值数量的乘积。Series 过多 → 内存爆炸 + 查询变慢。控制在 10 万以内。
