## 1. 为什么需要技术方案

| 价值 | 说明 |
|------|------|
| **统一认知** | 让团队对"做什么、怎么做、为什么这样做"达成一致 |
| **提前发现风险** | 设计阶段发现的问题修复成本远低于编码后 |
| **降低返工率** | 方案评审通过的代码很少需要大改 |
| **知识沉淀** | 文档是团队的长期资产，新人可以通过读方案理解系统 |
| **体现工程能力** | 写出清晰的方案是高级工程师的核心能力 |

> ⚠️ **常见误区**：技术方案≠详细代码。方案重在"决策依据"和"架构设计"，具体实现细节可以在编码阶段细化。

## 2. 技术方案标准模板

```markdown
# [项目名称] 技术方案

## 1. 背景与目标
- 业务背景：为什么要做这个需求？
- 核心目标：完成后的预期效果（尽量量化）
- 非目标：明确不做的是什么（防止范围蔓延）

## 2. 现状分析
- 当前系统架构（涉及的部分）
- 现有问题/痛点（用数据说话）

## 3. 方案设计
### 3.1 整体架构
  - 架构图（必画！文字描述无法替代架构图）
  - 核心流程（时序图/流程图）
### 3.2 数据库设计
  - 新增/修改的表结构
  - 索引设计（含依据：根据哪个查询）
### 3.3 接口设计
  - 对外API列表（URL/Method/Request/Response）
  - 接口调用时序
### 3.4 关键逻辑
  - 核心算法的伪代码/流程图
  - 状态机（如有状态流转）

## 4. 方案对比（可选但推荐）
  | 方案 | 优点 | 缺点 | 选择 |
  |------|------|------|------|
  | 方案A | ... | ... | ✅ |
  | 方案B | ... | ... | |

## 5. 风险与边界
- 技术风险：可能出问题的地方
- 边界条件：并发、幂等、超时、数据量大
- 降级方案：如果新功能出问题，如何快速下线？

## 6. 测试计划
- 单元测试重点
- 集成测试场景
- 性能测试指标（QPS目标、RT目标）

## 7. 上线计划
- 灰度策略（分批上线/功能开关）
- 监控告警
- 回滚方案
```

## 3. 需求分析与问题定义

### 3.1 5W1H分析框架

| 维度 | 问题 | 示例 |
|------|------|------|
| **Why** | 为什么要做？ | 用户投诉下单等太久 |
| **What** | 做什么功能？ | 订单超时自动取消 |
| **Who** | 影响谁？ | 用户、客服、运营 |
| **Where** | 在哪里实现？ | 订单服务 |
| **When** | 什么时候？ | 下单后30分钟未支付 |
| **How** | 怎么做？ | 定时任务轮询 vs 延迟消息 |

### 3.2 用数据说话

```
❌ 模糊描述："系统很慢，需要优化"
✅ 数据驱动："订单查询接口 P99=3.2s，高峰期QPS=200时错误率爬升到5%"
```

## 4. 方案对比与架构决策

### 4.1 决策矩阵

| 评估维度 | 权重 | 方案A: 定时任务轮询 | 方案B: 延迟消息 | 方案C: Redis过期回调 |
|----------|------|:---:|:---:|:---:|
| 实时性 | 30% | 3分(分钟级) | 5分(秒级) | 4分(10秒级) |
| 可靠性 | 25% | 4分 | 4分 | 3分(回调可能丢) |
| 复杂度 | 20% | 5分(简单) | 4分 | 3分(需额外处理) |
| 扩展性 | 15% | 3分 | 5分 | 3分 |
| 运维成本 | 10% | 4分 | 4分 | 3分 |

> 加权 = Σ(权重×分数)。方案B得分最高 → 选择延迟消息方案。

### 4.2 架构决策记录(ADR)

```markdown
# ADR-001: 订单超时取消使用RocketMQ延迟消息

**状态**: 已采纳
**日期**: 2024-01-15
**背景**: 需要实现订单30分钟未支付自动取消
**决策**: 使用RocketMQ延迟消息（delay level 18 = 30min）
**备选方案**: 
  - XXL-JOB定时轮询（延迟大，数据库压力）
  - Redis Keyspace Notifications（回调不可靠）
**后果**: 
  - 正面：实时性高，系统解耦
  - 负面：依赖RocketMQ，需保证消息可靠性
```

## 5. 风险评估与应急预案

### 5.1 风险矩阵

| 风险 | 概率 | 影响 | 等级 | 缓解措施 | 应急预案 |
|------|:---:|:---:|:---:|----------|----------|
| MQ消息丢失 | 低 | 高 | 中 | 生产者Confirm+消息持久化 | 定时任务兜底扫描 |
| 数据库死锁 | 低 | 中 | 低 | 缩短事务+合理加锁顺序 | 自动重试 |
| 并发扣库存 | 中 | 高 | 高 | Redis预扣+分布式锁 | 回滚+人工介入 |
| 第三方支付超时 | 中 | 中 | 中 | 设置合理超时+重试 | 降级到线下支付 |

### 5.2 功能开关（Feature Flag）

```java
// 新功能通过配置开关控制，出问题一键关闭
@Value("${feature.order-timeout.enabled:false}")
private boolean timeoutEnabled;

public void processOrder(Order order) {
    if (timeoutEnabled) {
        // 新逻辑
    } else {
        // 老逻辑（降级路径）
    }
}
```

## 6. 方案评审与迭代

### 6.1 评审检查清单

```checkbox
□ 架构是否合理？有没有更简单的方案？
□ 数据库设计：表的职责是否单一？索引是否够用？
□ 接口设计：是否符合RESTful规范？是否考虑了向后兼容？
□ 并发安全：是否有竞态条件？是否需要分布式锁？
□ 异常处理：核心流程的异常路径是否完整？
□ 性能：是否有N+1查询？是否有大事务？
□ 监控：关键指标是否可观测（日志/指标/链路）？
□ 可回滚：是否有回滚方案？数据库变更是否兼容旧代码？
```

### 6.2 好方案的三个标准

1. **可理解**：新人读完方案就能明白要做什么、为什么这样做
2. **可执行**：有明确的实现步骤，不需要再开很多会澄清
3. **可验证**：有清晰的验收标准，知道"做完"是什么样的

## 7. 实战案例：订单超时取消方案设计

```text
# 订单超时自动取消 技术方案（精简版）

## 1. 背景与目标
- 背景：未支付订单占库存，需自动释放
- 目标：下单30分钟后未支付→自动取消，释放库存
- 非目标：已支付订单的退款逻辑（已有独立退款流程）

## 2. 方案设计
整体流程：
用户下单 → 订单状态=UNPAID → 发送30min延迟消息
  → 30min后消费消息 → 检查订单状态
    → 仍未支付 → 取消订单+释放库存+通知用户
    → 已支付 → 忽略消息（幂等）

## 3. 核心接口
POST /api/orders           # 创建订单（内部发送延迟消息）
DELETE /api/orders/{id}    # 手动取消（用户主动取消）

## 4. 数据库变更
ALTER TABLE orders ADD COLUMN cancel_reason VARCHAR(50);
# 新增 cancel_reason 字段区分：TIMEOUT（超时自动）/ MANUAL（手动取消）

## 5. 风险与边界
- 幂等：消费者先查订单状态，已处理则跳过
- 并发：手动取消 vs 超时取消 → 乐观锁（version字段）
- 兜底：每小时全量扫描创建超过1h的未支付订单（防止消息丢失）

## 6. 灰度策略
Day 1: 仅对1%用户开启 → Day 3: 10% → Day 5: 50% → Day 7: 100%
全程监控：取消成功率、误取消率、MQ消息积压
```
