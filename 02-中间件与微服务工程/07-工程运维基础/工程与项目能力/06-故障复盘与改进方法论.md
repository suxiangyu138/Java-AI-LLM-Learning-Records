## 1. 故障复盘的价值

| 价值 | 说明 |
|------|------|
| **避免重复** | 同样的错误只犯一次 |
| **系统改进** | 每起事故背后都有可改进的流程/架构 |
| **知识沉淀** | 复盘报告 = 最好的培训材料 |
| **提升韧性** | 经历并复盘过的故障越多，系统越稳定 |

> ⚠️ **复盘的第一原则：对事不对人**。目标是找到"系统和流程出了什么问题"，不是"谁犯了错"。

## 2. Post-Mortem标准流程

### 2.1 时间线

```
故障发生 → T0: 发现告警 
  → T0+5min: 初步定位+Triage（判断严重等级）
  → T0+30min: 止血（限流/重启/回滚）
  → T0+2h: 根因定位+修复上线
  → T0+24h: 发送初步事故报告
  → T0+72h: 完成深度复盘报告+创建改进行动项
```

### 2.2 复盘报告模板

```markdown
# 故障复盘报告：[故障简述]

## 1. 故障概要
- **发生时间**: 2024-01-15 14:32 - 15:05（持续33分钟）
- **影响范围**: 下单接口P99从200ms飙升到30s，错误率30%
- **严重等级**: P1（核心业务受损）
- **责任人**: @zhangsan（排查）、@lisi（review）

## 2. 时间线
| 时间 | 事件 |
|------|------|
| 14:30 | 数据库连接池告警（最大连接数达到80%） |
| 14:32 | 用户投诉下单失败 |
| 14:35 | @zhangsan 开始排查 |
| 14:45 | 定位到慢SQL：未走索引的全表扫描 |
| 14:50 | 紧急添加索引 |
| 14:55 | 连接池恢复正常，错误率下降 |
| 15:05 | 全部恢复 |

## 3. 根因分析（5 Whys）
1. 为什么下单超时？→ 数据库连接池耗尽
2. 为什么连接池耗尽？→ 大量慢SQL占满连接
3. 为什么有慢SQL？→ order_item表按order_id查询没走索引
4. 为什么没索引？→ 表是新加字段后重建的，索引丢失
5. 为什么索引丢失被发现？→ DDL变更流程没有索引检查步骤

## 4. 直接原因
DDL变更后索引丢失，导致核心查询变成全表扫描

## 5. 根本原因
- **流程缺陷**：DDL变更流程缺少索引验证确认步骤
- **监控缺失**：慢SQL监控阈值设置过高(5s)，未在早期发现

## 6. 改进措施
| # | 措施 | 负责人 | 截止日期 | 状态 |
|---|------|--------|----------|:---:|
| 1 | DDL变更流程增加索引验证步骤 | @lisi | 01/20 | ✅ |
| 2 | 慢SQL告警阈值降至1s | @zhangsan | 01/18 | ✅ |
| 3 | 核心表增加索引覆盖度巡检 | @zhangsan | 01/30 | 🔄 |
| 4 | 团队周会进行本次复盘学习 | @lisi | 01/22 | ✅ |

## 7. 经验教训
- DDL操作是高风险操作，必须有checklist
- 监控阈值要"早发现"，不能等用户投诉
- 数据库连接池耗尽时，应自动熔断而非等待
```

## 3. 根因分析方法

### 3.1 5 Whys（五问法）

```
原则：每层答案追问"为什么"，直到找到可操作的流程/系统级别的根因

❌ 肤浅的5 Whys：
Q1: 为什么用户不能下单？ → 因为超时了
Q2: 为什么超时？ → 因为数据库慢了
Q3: 为什么数据库慢了？ → 因为SQL没走索引
→ 得出结论"加个索引就好了" ← 没有触及流程根因！

✅ 深度的5 Whys（必须追问到"流程为什么没拦住"）：
Q4: 为什么没索引？ → 因为DDL变更后索引丢了
Q5: 为什么变更后索引丢了但没人发现？ → 因为变更流程没检查索引
Q6: 为什么变更流程没检查索引？ → 因为变更checklist里没有这个步骤
→ 流程改进：在DDL变更checklist增加索引检查项！
```

### 3.2 鱼骨图(因果分析)

```text
                     ┌──────────────┐
                     │  流程问题     │
                     │ · 缺索引检查  │
                     │ · 缺灰度发布  │
                     └──────┬───────┘
                            │
  ┌──────────────┐         │         ┌──────────────┐
  │  代码问题     │         ↓         │  监控问题     │
  │ · 慢SQL      │───→ 下单超时 ←───│ · 告警太晚   │
  └──────────────┘                  └──────┬───────┘
                                           │
                            ┌──────────────┐
                            │  测试问题     │
                            │ · 缺性能测试  │
                            └──────────────┘
```

### 3.3 故障定级标准

| 等级 | 定义 | 响应时间 | 示例 |
|:---:|------|:---:|------|
| **P0** | 核心功能完全不可用 | 5min响应，30min止血 | 支付系统Down、全站无法访问 |
| **P1** | 核心功能部分受损 | 15min响应，1h止血 | 下单成功率下降50% |
| **P2** | 非核心功能受损 | 2h内处理 | 后台管理页面无法访问 |
| **P3** | 轻微影响、无用户感知 | 下一个工作日 | 报表数据延迟 |

## 4. 改进跟踪与闭环

### 4.1 Action Items 跟踪

```text
有效的Action必须是SMART的：
  Specific（具体）："慢SQL告警阈值从5s降到1s"
  Measurable（可度量）：有明确的改动值
  Assignable（可指派）：有明确的负责人
  Realistic（可实现）：技术上可落地
  Time-bound（有时限）：有明确的deadline

❌ "提高代码质量"
✅ "在SpotBugs规则中增加NP_NULL_PARAM_VIOLATION检查，@zhangsan 11月15日前完成"
```

### 4.2 故障演练

> 好的复盘不只是总结过去，还要面向未来做演习。

```
演练形式：
- 桌面演练(Tabletop)：团队围坐讨论"如果XX挂了怎么办"
- 混沌工程(Chaos Engineering)：主动注入故障验证恢复能力
  - kill一个Pod → K8s能否自动恢复？
  - 断开DB连接 → 应用能否自动重连？
  - 充满磁盘 → 日志轮转是否生效？
```

## 5. 复盘文化建设

### 5.1 健康 vs 不健康的复盘

| 健康的复盘 | 不健康的复盘 |
|-----------|-------------|
| "流程哪里出了问题？" | "这事是谁的锅？" |
| "下次怎么避免？" | "这次算你走运" |
| 所有相关方参与 | 只有领导在训话 |
| 产出可跟踪的Action | 开完会就没有然后了 |
| 分享给整个团队 | 只有当事人知道 |

### 5.2 复盘会议引导

```text
主持人开场白（抄下来用）：
"今天复盘的目标不是找责任人，而是找到流程和系统的改进点，
让我们下次遇到同样问题时能更好、更快地应对。
请大家用'我们'而不是'你'来描述问题，
例如：'我们缺少了索引检查步骤'而不是'你忘了加索引'。"
```

---

> 🎯 **核心原则**：Blameless（不指责）是复盘的前提。复盘的本质 = 把一次教训变成永久的能力。优秀团队是"不怕出事，但绝不犯同样的错"。
