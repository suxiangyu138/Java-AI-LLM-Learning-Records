## 1. 敏捷开发核心理念

### 1.1 敏捷宣言

```
个体和互动     >  流程和工具
可工作的软件   >  详尽的文档
客户合作       >  合同谈判
响应变化       >  遵循计划
```

> 🎯 敏捷不是"不做文档"或"不做计划"，而是当变化发生时，优先选择左边。

### 1.2 传统瀑布 vs 敏捷

| 维度 | 瀑布模型 | 敏捷开发 |
|------|----------|----------|
| 需求 | 一次性全部明确 | 逐步细化、拥抱变化 |
| 交付 | 项目结束一次性交付 | 每个Sprint持续交付 |
| 反馈 | 项目结束后 | 每个Sprint都有反馈 |
| 变更成本 | 后期变更代价极高 | 设计时就考虑可变性 |
| 风险管理 | 后期才暴露 | 早期持续暴露 |
| 适用场景 | 需求确定、一次性交付 | 需求不确定、需要快速验证 |

## 2. Scrum框架全解

### 2.1 三大角色

| 角色 | 职责 | 不可兼任 |
|------|------|----------|
| **Product Owner (PO)** | 定义需求优先级、维护Product Backlog、回答业务问题 | PO≠SM |
| **Scrum Master (SM)** | 确保Scrum流程正确、移除障碍、保护团队、引导会议 | SM≠PO |
| **Development Team** | 交付可工作的软件增量、自组织、跨职能 | 5-9人最佳 |

### 2.2 五大事件

```
Sprint 循环（通常2周）：

Sprint Planning（计划会，≤4h）
  → Daily Scrum（站会，15min/天）
    → 开发工作 + 持续更新Backlog
      → Sprint Review（评审会，≤2h）
        → Sprint Retro（回顾会，≤1.5h）
          → 下一个Sprint...

其中：Backlog Refinement（梳理会）按需进行
```

| 事件 | 时长(2周Sprint) | 目的 | 参与人 |
|------|:---:|------|--------|
| **Sprint Planning** | ≤4h | 确定Sprint目标 + 选择Backlog项 + 拆分任务 | 全员 |
| **Daily Scrum** | 15min | 同步进度：昨天做了什么/今天做什么/有什么障碍 | Dev Team |
| **Sprint Review** | ≤2h | 演示完成的功能，收集反馈 | 全员+干系人 |
| **Sprint Retro** | ≤1.5h | 改进流程：什么做得好/什么可以更好/下个Sprint改进什么 | Dev Team |
| **Backlog Refinement** | ≤Sprint 10% | 拆分大需求、估算、澄清 | Dev Team+PO |

### 2.3 三大工件

| 工件 | 内容 | 负责人 |
|------|------|--------|
| **Product Backlog** | 所有需求的有序列表 | PO维护优先级 |
| **Sprint Backlog** | 当前Sprint要完成的任务 | Dev Team |
| **Increment** | Sprint结束时完成的、可交付的软件增量 | Dev Team |

## 3. Sprint实战节奏

### 3.1 站会怎么开（Daily Scrum）

```text
每人回答3个问题（≤2分钟/人）：
1. 昨天我做了什么帮助团队达成Sprint目标？
2. 今天我要做什么？
3. 我遇到了什么障碍/阻塞？

❌ 反模式：
  - 向Scrum Master汇报（应该是团队成员间同步，不是汇报）
  - 变成问题解决会议（有问题会后单独讨论）
  - 迟到或缺席（站会是团队承诺）
  - 对着电脑/手机说（围在白板/屏幕上说）
```

### 3.2 回顾会怎么开（Retro）

```text
经典 Retro 格式（船/锚/帆）：
⛵ 帆（Sails）：什么推动了我们的进步？
⚓ 锚（Anchors）：什么拖慢了我们的进度？
🗻 暗礁（Rocks Ahead）：下个Sprint可能的风险？

产出：1-3个具体的改进Action Items
（不是"改进沟通"这种虚的，而是"每个PR必须在24h内Review"）
```

### 3.3 需求拆分（User Story → Tasks）

```text
Epic（史诗）：用户下单功能
  ↓ 拆分为 User Stories
Story 1: 作为用户，我可以把商品加入购物车
Story 2: 作为用户，我可以从购物车下单
Story 3: 作为用户，我可以在下单时选择优惠券
  ↓ 拆分为 Tasks（由Dev Team在Planning中拆分）
Task 2.1: 设计订单数据表
Task 2.2: 实现下单API
Task 2.3: 实现库存扣减逻辑
Task 2.4: 编写单元测试
Task 2.5: 编写集成测试
```

## 4. 需求估算与排期

### 4.1 故事点 vs 人天

| 维度 | 故事点(Story Points) | 人天(Man-Day) |
|------|:---:|:---:|
| 衡量什么 | 复杂度+不确定性+工作量 | 纯时间 |
| 是否依赖个人 | 否（团队基准） | 是（不同人速度不同） |
| 对比性 | ✅ 可跨Sprint对比 | ⚠️ 因人而异 |
| 推荐 | ✅ | 小团队过渡可用 |

### 4.2 估算扑克(Planning Poker)

```
流程：
1. PO讲解Story需求
2. 每个成员选估算牌（1,2,3,5,8,13,20,40,100）
3. 同时亮牌
4. 如果差异大（最高≠最低），请最高和最低的人解释理由
5. 再次投票直到收敛
```

| 故事点 | 含义 | 示例 |
|:---:|------|------|
| 1 | 极小，确定 | 修改一个配置项 |
| 2 | 小 | 新增一个简单查询接口 |
| 3 | 中等 | CRUD接口含基础校验 |
| 5 | 较大 | 含复杂业务逻辑+单元测试 |
| 8 | 大 | 涉及多服务协调 |
| 13 | 很大 | 需要先做技术调研 |
| ≥20 | 过大 | 需要进一步拆分 |

## 5. Kanban看板方法

### 5.1 看板 vs Scrum

| 维度 | Scrum | Kanban |
|------|-------|--------|
| 节奏 | 固定Sprint（2-4周） | 持续流动 |
| 角色 | PO + SM + Dev Team | 无强制角色 |
| WIP限制 | Sprint固定工作量 | 每个状态栏限制WIP |
| 变更 | Sprint内尽量不变 | 随时可以插入 |
| 适用场景 | 产品开发 | 运维/维护/持续交付 |

### 5.2 看板列结构

```
Backlog → Ready → In Progress → Code Review → Testing → Done
           (3)        (2)           (2)         (2)
                        ↑ WIP限制：每个栏括号内为上限
```

## 6. 常见反模式与避坑

| 反模式 | 表现 | 改进 |
|--------|------|------|
| **Scrum-But** | "我们用Scrum，但不做Retro/不限制WIP..." | 要么全做，要么改叫Kanban |
| **站会变汇报会** | 成员向SM汇报，SM分配任务 | Dev Team成员互相同步，自组织 |
| **永远在救火** | Sprint里总插紧急需求 | 预留Sprint 20%容量做buffer |
| **Sprint Review没人来** | 利益相关者不关心 | 邀请真正使用产品的干系人 |
| **Retro没有Action** | 每次都吐槽同样的问题 | 每期Retro产出≤3个具体Action并跟踪 |

---

> 🎯 **核心原则**：Scrum是框架不是教条。理解"为什么"比死记"怎么做"更重要。流程服务于团队效能，不是反过来。
