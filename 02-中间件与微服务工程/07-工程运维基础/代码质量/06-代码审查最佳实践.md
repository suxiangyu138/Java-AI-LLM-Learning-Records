## 1. 代码审查的价值与原则

### 1.1 为什么需要代码审查

| 价值 | 说明 | 数据支撑 |
|------|------|----------|
| **发现缺陷** | 在代码合入前发现Bug | 代码审查可发现60-70%的缺陷（比测试更早） |
| **知识共享** | 团队成员互相了解代码 | 降低"单点故障"风险（某人离职=知识全部流失） |
| **统一规范** | 强制执行编码标准和最佳实践 | 减少因风格不统一导致的认知负担 |
| **代码质量** | 持续提升代码可维护性 | 增加可读性、减少技术债务 |
| **团队成长** | 初级开发从审查中学习 | 最有效的On-the-Job Training形式 |
| **安全意识** | 审查中发现安全漏洞 | OWASP建议所有代码必须经过安全审查 |

### 1.2 审查的核心原则

| 原则 | 说明 |
|------|------|
| **审查代码，不是审查人** | 对事不对人，使用中性语言（"这段逻辑可以简化" vs "你写的什么鬼"） |
| **每次审查聚焦小批量** | 单次PR ≤ 400行变更（超过则审查质量断崖式下降） |
| **审查要快** | 24小时内完成review（不要让PR"烂掉"） |
| **自动化先行** | CI先跑通（编译+测试+Lint），人审查业务逻辑 |
| **审查者有责任理解代码** | 如果没看懂→要求作者补充注释/文档/设计说明 |

## 2. 审查流程与角色分工

### 2.1 标准PR审查流程

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│ 开发者    │    │ CI/CD    │    │ 审查者    │    │ 开发者    │    │ 合并     │
│ 提交PR    │→──→│ 自动检查  │→──→│ Review   │→──→│ 修改     │→──→│ Merge   │
└──────────┘    └─────┬────┘    └─────┬────┘    └──────────┘    └─────┬────┘
                      │ 失败          │ 通过                            │
                      ↓               ↓                                ↓
                  修复后重提      Approve                         合并到主分支
```

### 2.2 角色与职责

| 角色 | 职责 | 具体要求 |
|------|------|----------|
| **PR作者** | 提交清晰、小批量的PR | PR描述：背景+变更内容+测试说明+截图(如有UI) |
| **Reviewer** | 审查逻辑正确性+可维护性 | 每行代码都应该被理解，不能"看着差不多就Approve" |
| **Maintainer** | 最终批准合并 | 确保审查流程完整（至少1个Approve + CI通过） |

### 2.3 PR最佳模板

```markdown
## 📝 变更概述
修复订单取消时库存未恢复的bug

## 🔗 关联 Issue
Fixes #1234

## 🧪 测试
- [x] 单元测试：新增 OrderServiceTest.shouldRestoreInventoryOnCancel
- [x] 集成测试：取消订单→库存恢复验证
- [x] 手动回归：取消不同类型订单（待支付/已支付/已发货）

## 📸 截图（如有UI变更）
<截图>

## ⚠️ 风险提示
- 涉及库存扣减核心逻辑，请重点审查 `InventoryService.restore()`
- 需要考虑并发取消的情况（已加分布式锁）
```

## 3. 审查检查清单

### 3.1 功能正确性

```checkbox
□ 业务逻辑是否正确？是否符合需求？
□ 边界条件：null、空集合、0、负数、大数值、极限值
□ 异常处理：是否正确处理了所有可能的异常路径？
□ 并发安全：是否有线程安全问题？（共享状态、非线程安全集合）
□ 事务边界：事务范围是否合理？是否有事务失效风险？
□ 幂等性：重复调用是否产生副作用？
```

### 3.2 代码设计

```checkbox
□ 单一职责：类/方法是否只做一件事？
□ 命名：类名、方法名、变量名是否清晰表达意图？
□ 方法长度：是否超过50行？（应拆分）
□ 参数数量：是否超过4个参数？（考虑封装为对象）
□ 重复代码：是否有可提取的公共逻辑？
□ 依赖方向：是否依赖了不该依赖的层？（如Service依赖Controller）
□ 设计模式：是否过度设计？（一个if-else不需要策略模式）
```

### 3.3 安全与性能

```checkbox
□ SQL注入：是否使用参数化查询？（MyBatis ${} 检查）
□ XSS：用户输入是否正确转义？
□ 敏感信息：是否硬编码密码/Token/密钥？（应在配置中心）
□ 日志脱敏：手机号/身份证/密码是否在日志中脱敏？
□ N+1查询：JPA关联是否设置了正确的FetchType？是否用了@EntityGraph？
□ 连接泄露：资源是否在finally/try-with-resources中关闭？
□ 大事务：事务中是否有RPC/HTTP/文件IO等耗时操作？
```

### 3.4 可测试性与可维护性

```checkbox
□ 是否有足够的单元测试？覆盖了主流程+边界条件？
□ 依赖是否可Mock？（避免静态方法调用、new创建对象）
□ 是否有充分的注释？（WHY注释 > WHAT注释）
□ API变更：是否兼容旧版本？是否需要版本号升级？
```

## 4. 审查工具与平台

### 4.1 工具对比

| 平台 | 特点 | 适用 |
|------|------|------|
| **GitHub Pull Requests** | 生态最完善，Actions集成 | 开源+企业 |
| **GitLab Merge Requests** | 内置CI/CD，自托管友好 | 企业自托管 |
| **Gerrit** | 严格的逐Commit审查，+2机制 | 大型企业/严格流程 |
| **Phabricator** | 全功能项目管理+审查 | 已停止维护 |
| **Bitbucket** | Atlassian生态(Jira集成) | Atlassian用户 |

### 4.2 自动化审查工具集成

```yaml
# GitHub Actions: 自动运行审查辅助工具
name: Code Review Assist
on: [pull_request]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      
      - name: Java Checkstyle
        run: mvn checkstyle:check
      
      - name: SpotBugs Analysis
        run: mvn spotbugs:check
      
      - name: PMD Analysis
        run: mvn pmd:check
      
      - name: Unit Tests + JaCoCo
        run: mvn test jacoco:report
      
      - name: SonarQube Scan
        run: mvn sonar:sonar
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
```

## 5. 审查反模式与避坑

| 反模式 | 表现 | 改进 |
|--------|------|------|
| **橡皮图章** | 看都不看就LGTM/Approve | 有责任理解每行变更 |
| **审查牛车** | 一个PR拖一周还不看 | 设定SLA：≤24小时 |
| **完美主义** | 为命名争论一下午 | 有规范按规范，没规范按约定 |
| **巨无霸PR** | 一次提交2000行 | 拆分为多个小PR |
| **人身攻击** | "你写的什么垃圾" | 对事不对人，给出具体建议 |
| **只挑格式** | 只评论空格/换行/命名 | 自动化处理格式，人聚焦逻辑 |
| **幽灵审查** | 评论"这里要改"但不说明原因 | 每个评论说明WHY |

## 6. 审查度量与持续改进

### 6.1 关键度量指标

| 指标 | 说明 | 健康范围 |
|------|------|----------|
| **Review Time** | 从提交PR到第一次Review的时长 | < 24小时 |
| **PR Size** | 每次PR的代码变更行数 | < 400行 |
| **Review Depth** | 每条评论是"浅"(格式)还是"深"(逻辑) | 深度评论 > 60% |
| **Defect Escape Rate** | 审查未发现但生产发现的Bug比例 | < 10% |
| **Rework Rate** | PR被打回修改的比例 | 20-40% |

### 6.2 持续改进循环

```
度量 → 回顾 → 调整 → 再度量
  ↑                      │
  └──────────────────────┘
```

> 🎯 **最佳审查文化**：审查是团队学习的最高效方式——review别人代码等于读源码，被review等于免费编程私教课。
