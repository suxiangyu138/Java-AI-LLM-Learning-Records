## 1. 分布式系统概述

### 1.1 定义与衡量指标

> **定义**：由多个自治计算机通过网络互联组成的系统，对用户呈现为单一整体。

| 指标 | 说明 | 典型值 |
|------|------|--------|
| **可扩展性** | 水平扩展（加机器）vs 垂直扩展（加配置） | — |
| **可用性** | 正常运行时间比例 | 99.9%（3个9，年停机8.76h）→ 99.999%（5个9，年停机5.26min） |
| **可靠性** | 给定时间内无故障运行的能力 | — |
| **性能** | 吞吐量(QPS/TPS) + 延迟(P50/P99/P999) | — |
| **可维护性** | 便于运维、修复、迭代 | — |

### 1.2 分布式系统分类

| 类型 | 代表 | 说明 |
|------|------|------|
| 分布式计算 | MapReduce、Spark | 数据分片并行计算 |
| 分布式存储 | HDFS、Ceph | 数据分散存储 |
| 分布式数据库 | TiDB、CockroachDB | 分布式事务+SQL |
| 分布式缓存 | Redis Cluster | 内存数据分布式 |
| 分布式协调 | ZooKeeper、etcd | 配置/选主/锁 |
| 分布式消息 | Kafka、RocketMQ | 消息持久化传递 |

## 2. CAP 定理

> ⚠️ **Eric Brewer, 2000（Gilbert & Lynch 2002 证明）**：分布式系统中，Consistency(一致性)、Availability(可用性)、Partition Tolerance(分区容错) 三者最多同时满足两个。

### 2.1 三者定义

| 要素 | 定义 | 通俗理解 |
|------|------|----------|
| **C — 一致性** | 所有节点在同一时刻看到相同的数据 | 每次读都返回最新写的结果 |
| **A — 可用性** | 每个请求都能收到非错误的响应 | 系统始终能对外提供服务 |
| **P — 分区容错** | 即使网络分区，系统仍能正常运作 | 节点间断网也能继续工作 |

### 2.2 关键理解

```
P 是必须选的——网络分区在网络环境中不可避免！
→ 实际选择是 CP 还是 AP：

CP 系统：发生分区时牺牲 A 保障 C
  ├── ZooKeeper — Leader 宕机期间集群不可写
  ├── etcd — 选主期间不可写，保证强一致
  └── HBase — Master 故障时 Region 不可用

AP 系统：发生分区时牺牲 C 保障 A
  ├── Eureka — 各节点可能返回不同注册信息
  ├── Nacos（AP 模式）— 优先保证服务发现可用
  └── Cassandra — 最终一致性，高可用
```

| 场景 | 推荐选择 | 原因 |
|------|:---:|------|
| 配置中心/选主 | CP | 短暂不可用可接受，数据不一致不可接受 |
| 注册中心/服务发现 | AP | 宁可拿到旧实例也不能拿不到实例 |
| 银行转账 | CP | 余额不一致是灾难 |
| 社交动态/点赞 | AP | 短暂不一致不影响体验 |
| DNS | AP | 最终一致性的经典案例 |

## 3. BASE 理论

> 💡 BASE 是 CAP 中 AP 方案的延伸：牺牲强一致性（C），换取高可用性（A）。

| 字母 | 含义 | 说明 |
|:---:|------|------|
| **BA** | Basically Available（基本可用） | 允许损失部分可用性：响应变慢/功能降级，但不整体不可用 |
| **S** | Soft State（软状态） | 允许系统存在中间状态，数据副本间可短暂不一致 |
| **E** | Eventually Consistent（最终一致性） | 经过一段时间后，所有副本最终达到一致 |

```
ACID（传统数据库）vs BASE（分布式系统）

ACID: Atomicity + Consistency + Isolation + Durability
  → 强一致性、刚性事务、适合单体数据库

BASE: Basically Available + Soft State + Eventually Consistent
  → 最终一致性、柔性事务、适合大规模分布式系统
```

## 4. 一致性模型光谱

> 一致性从强到弱是一个光谱，而非二元对立。选择合适的一致性级别是架构权衡的核心。

```
强 ────────────────────────────────────────────→ 弱

强一致性 → 顺序一致性 → 因果一致性 → 最终一致性
(Linearizability) (Sequential) (Causal)  (Eventual)
```

| 一致性模型 | 保证 | 典型系统 |
|-----------|------|----------|
| **强一致性** | 所有操作像在单一副本上按全局顺序执行 | etcd、ZooKeeper（CP） |
| **顺序一致性** | 每个进程的操作按程序顺序，不同进程可交错 | — |
| **因果一致性** | 有因果关系的操作全局有序，无关操作可乱序 | COPS、MongoDB（可配置） |
| **读写一致性** | 用户总能看到自己写入的数据 | — |
| **单调读** | 读到的数据不会"倒退"到更旧版本 | — |
| **最终一致性** | 停止更新后，所有副本最终一致 | DNS、Cassandra、Redis 主从 |

### 4.1 最终一致性的变体

```text
DNS 是最经典的最终一致性案例：
  修改 DNS 记录后，全球生效需要几小时到 48 小时
  → 但最终所有 DNS 服务器会同步到新记录
```

## 5. 分布式系统的八大谬误

> Peter Deutsch (1994)：初学者对分布式系统的 8 个错误假设。

| # | 谬误 | 现实 |
|---|------|------|
| 1 | 网络是可靠的 | 丢包、延迟、断连是常态 |
| 2 | 延迟为零 | 光速也有极限，跨大洋 > 100ms |
| 3 | 带宽是无限的 | 大数据传输需考虑成本和耗时 |
| 4 | 网络是安全的 | 中间人攻击、DNS 劫持 |
| 5 | 拓扑不会变化 | 节点增删、故障切换是常态 |
| 6 | 只有一个管理员 | 多团队、多组织运维 |
| 7 | 传输成本为零 | 序列化/反序列化/加密有开销 |
| 8 | 网络是同构的 | 多种协议/设备/操作系统 |

## 6. 时间与时钟

> ⚠️ 分布式系统中**不能依赖物理时钟**判断事件顺序——NTP 同步仍有漂移。

### 6.1 三种时钟方案

| 方案 | 原理 | 特点 |
|------|------|------|
| **Lamport 时间戳** | 每个进程维护计数器，事件发生时递增，发送消息携带自己的时间戳 | 定义了 happen-before 偏序关系 |
| **向量时钟** | 每个进程维护所有进程的计数器向量 | 可判断事件是因果还是并发 |
| **TrueTime** | Google Spanner：原子钟+GPS 提供全球有界不确定时间 | 实现"外部一致性"，成本极高 |

```text
Lamport 逻辑时钟规则：
1. 进程 Pi 执行事件 → Ci = Ci + 1
2. Pi 发送消息 m → 附上 Ci
3. Pj 收到消息 m → Cj = max(Cj, Cm) + 1

如果 a → b（a happen-before b），则 C(a) < C(b)
但 C(a) < C(b) 不能推出 a → b（反命题不成立）
```

## 7. 面试高频问题

### Q1：CAP 为什么不能三者同时满足？

> 当网络分区（P 发生）时：如果要保证 C，必须拒绝写入（牺牲 A）；如果要保证 A，必须允许写入，但分区两侧可能产生不一致（牺牲 C）。没有网络分区时，C 和 A 可以同时满足。

### Q2：注册中心为什么选 AP 而不是 CP？

> 注册中心的核心职责是服务发现。如果因为 CP 导致注册中心短暂不可用，消费者拿不到任何实例 → 请求全部失败。选择 AP，消费者可能拿到旧实例（调用失败一次后重试别的实例），系统整体可用性更高。

### Q3：BASE 和 ACID 是什么关系？

> ACID 是传统单机数据库的事务模型，追求强一致性。BASE 是分布式系统的务实妥协，牺牲强一致性换取高可用。两者不是替代关系，而是不同场景的选择——银行核心账务用 ACID，社交动态用 BASE。

> 🎯 **记忆口诀**：CAP 是定律（只能三选二），BASE 是策略（AP 侧的具体方案），一致性是光谱（选适合的级别）。
