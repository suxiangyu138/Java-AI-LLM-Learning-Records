## 1. 微服务概述

### 1.1 定义与特征

| 特征 | 说明 |
|------|------|
| **独立部署** | 每个服务可独立构建、测试、部署 |
| **业务能力组织** | 围绕业务领域而非技术层划分 |
| **去中心化** | 每个服务有自己的数据库、技术栈 |
| **智能化端点 + 哑管道** | 服务间通过轻量级协议通信（HTTP/gRPC/MQ） |
| **基础设施自动化** | CI/CD、容器化、自动扩缩容 |

### 1.2 微服务的代价

| 挑战 | 说明 |
|------|------|
| 分布式复杂度 | 网络延迟、分布式事务、数据一致性 |
| 运维成本 | 多服务监控、日志聚合、链路追踪 |
| 调试困难 | 请求跨多个服务，需要分布式追踪 |
| 数据一致性 | 无法用单机事务，需要最终一致性 |
| 测试复杂 | 集成测试需要多个服务 |

## 2. 服务拆分策略

### 2.1 DDD 限界上下文（⭐ 推荐的拆分方法）

```
业务领域 → 限界上下文（Bounded Context）→ 微服务

电商系统的 DDD 拆分：
  ├── 用户上下文 → user-service
  ├── 商品上下文 → product-service
  ├── 订单上下文 → order-service
  ├── 库存上下文 → inventory-service
  └── 支付上下文 → payment-service
```

### 2.2 拆分原则

| 原则 | 说明 | 反面案例 |
|------|------|----------|
| **单一职责** | 一个服务只做一件事 | "万能服务"包含几十个接口 |
| **数据主权** | 每个服务有自己的数据库 | 多服务共享数据库 |
| **最小接口** | 只暴露必需接口，减少耦合 | 把内部表结构暴露给外部 |
| **独立部署** | 修改一个服务不影响其他 | 改一行代码全量部署 |

### 2.3 拆分模式

| 模式 | 说明 | 适用 |
|------|------|------|
| **按业务能力** | 按业务功能划分 | 最常用 |
| **按子域** | DDD 核心域/支撑域/通用域 | 复杂业务 |
| **按技术层** | Controller→Service→DAO | ❌ 不推荐，跨层耦合 |
| **按团队** | 康威定律：系统架构反映组织沟通结构 | 大组织 |

## 3. 服务通信模式

### 3.1 同步 vs 异步

| 维度 | 同步（REST/gRPC） | 异步（MQ/Event） |
|------|-------------------|-----------------|
| 耦合度 | 高（调用方等响应） | 低（发消息即返回） |
| 延迟 | 低（直接请求） | 高（消息排队） |
| 可靠性 | 依赖被调用方可用 | 消息持久化保证 |
| 适用 | 实时查询 | 异步处理、事件通知 |

### 3.2 通信协议对比

| 协议 | 格式 | 性能 | 兼容性 | 适用场景 |
|------|------|:---:|:---:|------|
| **REST/JSON** | JSON | ⭐⭐ | ⭐⭐⭐ 最好 | 对外开放 API |
| **gRPC/Protobuf** | Protobuf | ⭐⭐⭐ | ⭐⭐ 需 proto 文件 | 内部微服务间 |
| **消息队列** | 自定义 | ⭐⭐⭐ | ⭐⭐ | 异步解耦 |
| **Dubbo** | Hessian/Protobuf | ⭐⭐⭐ | ⭐ Java 限定 | Java 内部微服务 |

### 3.3 服务间调用组合

```text
SAGA 编排：
  Order → Inventory → Payment

API 组合（Aggregator）：
  Gateway 并行调用 → 聚合结果返回
  
事件驱动：
  Order 发布 OrderCreated 事件
  → Inventory 消费（扣库存）
  → Payment 消费（扣款）
```

## 4. 容错与韧性设计

### 4.1 三大容错模式

| 模式 | 原理 | 实现 |
|------|------|------|
| **断路器** | 错误率超阈值 → 打开断路器（快速失败）→ 半开后试探 | Hystrix → Sentinel |
| **舱壁隔离** | 不同服务用不同线程池，互不影响 | 线程池隔离 / 信号量 |
| **重试与退避** | 失败后指数退避重试 + 最大重试次数 | Spring Retry |

### 4.2 Sentinel 实战

```java
// Sentinel 注解式限流
@SentinelResource(value = "createOrder", blockHandler = "createOrderBlock")
public Order createOrder(OrderRequest req) {
    return orderService.create(req);
}

public Order createOrderBlock(OrderRequest req, BlockException e) {
    // 被限流后的降级处理
    return Order.fallback(req);
}
```

### 4.3 容错层次

```
调用方容错 ─────── 超时 + 重试 + 断路器
     │
负载均衡器容错 ──── 健康检查 + 自动摘除
     │
服务方容错 ─────── 限流 + 降级 + 隔离
```

## 5. 可观测性三支柱

| 支柱 | 解决的问题 | 工具 |
|------|-----------|------|
| **Logging（日志）** | 哪个服务在什么时候发生了什么 | ELK / Loki |
| **Metrics（指标）** | 系统整体健康状态（QPS/延迟/错误率） | Prometheus + Grafana |
| **Tracing（追踪）** | 一个请求跨服务的完整路径 | Jaeger / Zipkin / SkyWalking |

### 5.1 分布式追踪

```text
请求链路追踪：
Gateway → Order Service → Inventory Service → DB
  │           │               │
  Trace ID: abc123 ─────────────┘
  ├── Span 1: Gateway (50ms)
  ├── Span 2: Order Service (200ms)
  │   └── Span 3: Inventory Service (150ms)
  │       └── Span 4: DB Query (100ms)
```

## 6. 数据管理策略

### 6.1 Database per Service

| 模式 | 说明 | 适用 |
|------|------|------|
| **独立数据库** | 每个服务有自己的 DB | ⭐ 推荐 |
| **共享数据库** | 多个服务共享一个 DB | ❌ 不推荐（紧耦合） |
| **API 组合** | 通过 API 查询其他服务的数据 | 读数据 |
| **CQRS** | 读写分离，维护独立的读模型 | 复杂查询 |
| **Saga** | 跨服务事务 | 写数据 |

### 6.2 数据一致性保障

```text
最终一致性的经典模式：

1. 本地事务 + 事件表（Transactional Outbox）
   → 订单写入 orders 表 + 同时插入 outbox 表（同一事务）
   → 后台进程读取 outbox 发送到 MQ

2. CDC（Change Data Capture）
   → Debezium 监听 MySQL Binlog
   → 写入 Kafka → 下游消费者同步状态
```

## 7. 微服务 vs 单体决策

| 条件 | 推荐 | 理由 |
|------|:---:|------|
| 团队 < 5 人 | 单体 | 微服务运维开销 > 收益 |
| 业务不明确/快速迭代 | 单体 → 模块化单体 | 过早拆分代价高 |
| 团队可以独立负责 | 微服务 | 独立开发/测试/部署 |
| 部分模块有不同扩容需求 | 微服务 | 针对性扩容 |
| 遗留系统改造 | 绞杀者模式（Strangler Fig） | 逐步替换，风险可控 |

### 绞杀者模式

```
        外部请求 → [Gateway]
                      ├── 新功能 → 微服务
                      └── 旧功能 → 遗留单体（逐步废弃）

新老共存，渐进迁移 — 而不是大爆炸式重写
```

> 🎯 **核心原则**：先单体后拆分、按业务能力划分、每个服务有独立数据库、异步通信优先、容错设计是必修课。
