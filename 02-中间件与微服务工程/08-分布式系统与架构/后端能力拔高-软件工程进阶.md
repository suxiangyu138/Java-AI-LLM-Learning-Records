# 软件工程（进阶版）

> **优先级**：🔴 高优先级（必选）| **类型**：校内提升专业课 | **方向**：后端能力拔高

## 课程定位

**提升点**：架构设计方法论、模块化与组件化、软件生命周期管理、敏捷开发流程、测试体系搭建、项目质量管控、团队协作规范

**适用人群**：想从"写代码"进阶到"设计系统"的后端开发者、未来想做技术负责人/架构师

**学习目标**：能独立设计可维护可扩展的中大型项目，掌握敏捷团队协作流程，具备技术选型和架构评审能力

# 第一章：软件过程与生命周期

### 1.1 软件生命周期模型
- **瀑布模型（Waterfall）**：需求→设计→实现→测试→部署→维护——阶段严格顺序，文档驱动
  - 适用：需求明确稳定的项目（政府/军工/航天）
  - 缺点：后期变更成本高，用户看不到中间产物
- **V 模型**：瀑布的变体——每个开发阶段对应一个测试阶段（需求↔验收测试、设计↔系统测试）
- **增量模型**：分多个增量交付，每个增量是一个可运行的子集——先核心功能后附加功能
- **螺旋模型（Spiral）**：每次迭代包含风险分析——适合高风险大型项目
- **RUP（Rational Unified Process）**：用例驱动 + 架构为中心 + 迭代增量——4阶段（初始/细化/构造/交付）

### 1.2 敏捷开发（Agile）
- **敏捷宣言**：
  1. 个体和互动 > 流程和工具
  2. 可工作的软件 > 详尽的文档
  3. 客户合作 > 合同谈判
  4. 响应变化 > 遵循计划
- **Scrum 框架**：
  - 三角色：Product Owner（定需求优先级）、Scrum Master（保流程、排障碍）、Dev Team（自组织交付）
  - 三工件：Product Backlog（需求池）→ Sprint Backlog（本次Sprint任务）→ Increment（可交付增量）
  - 五事件：Sprint Planning → Daily Standup（15min，昨天做了什么/今天做什么/有什么障碍）→ Sprint Review（演示）→ Sprint Retrospective（复盘改进）
  - Sprint 固定时间盒（1-4周，通常2周），不中断不修改目标
- **Kanban**：可视化工作流 + WIP限制（限制同时进行的任务数）——适合运维型/持续性工作

### 1.3 DevOps
- **核心理念**：打破开发与运维的墙——"你 build it, you run it"
- **CI/CD 流水线**：代码提交→自动构建→自动测试→自动部署——缩短反馈环
- **CALMS 模型**：Culture（共享责任）+ Automation（自动化一切）+ Lean（精益）+ Measurement（数据驱动）+ Sharing（知识共享）

# 第二章：需求工程

### 2.1 需求获取
- **功能性需求**：系统"做什么"——用户故事（As a... I want to... So that...）
- **非功能性需求**：系统"做得怎么样"——性能（QPS/延迟）、可用性、安全性、可扩展性、可维护性
- **约束条件**：技术栈限制、合规要求、预算时间限制

### 2.2 需求分析
- **用例建模**：参与者（Actor） + 用例（Use Case） + 关系（包含/扩展/泛化）
- **用户故事映射（User Story Mapping）**：横轴=时间顺序，纵轴=优先级——规划 MVP 和迭代
- **MoSCoW 优先级**：Must have（必须）→ Should have（应该）→ Could have（可以）→ Won't have（不做）

### 2.3 需求规格说明
- **SRS（软件需求规格说明书）**：IEEE 830 标准
- **验收标准（Acceptance Criteria）**：Given-When-Then 格式——"Given 用户已登录，When 点击下单，Then 生成订单"

# 第三章：软件架构设计

### 3.1 架构设计基础
- **架构是什么**：系统的骨架——组件 + 组件间的关系 + 组件与环境的关系
- **架构视图（4+1 视图模型）**：
  - 逻辑视图：功能分解（类图/包图）——面向最终用户
  - 开发视图：模块组织（组件图）——面向开发者
  - 进程视图：运行时行为（活动图/时序图）——面向系统集成
  - 物理视图：部署拓扑（部署图）——面向运维
  - +1 场景视图：用例驱动（用例图）——串起所有视图

### 3.2 架构模式（⭐ 核心）
- **分层架构（Layered）**：表示层→业务层→持久层→数据库——最经典，OSI 也是分层的
- **六边形架构（端口-适配器）**：业务逻辑在中心，通过端口（接口）与外部适配器交互——DDD推崇
- **微服务架构**：按业务能力拆分为独立部署的小服务——独立开发/部署/扩展/技术栈
- **事件驱动架构**：生产者→事件总线→消费者——松耦合，异步
- **CQRS + Event Sourcing**：读写分离 + 事件为数据源
- **Service Mesh**：将服务治理下沉到 Sidecar 代理层（Envoy/Istio）

### 3.3 架构质量属性
- **性能**：响应时间、吞吐量——缓存/异步/并行
- **可用性**：冗余、故障转移、降级——MTTF/MTTR/MTBF
- **安全性**：认证、授权、加密、审计
- **可修改性**：高内聚低耦合——SOLID 原则
- **可测试性**：可 mock、可隔离——依赖注入
- **可部署性**：一键部署、灰度发布、回滚

### 3.4 架构评估方法
- **ATAM（架构权衡分析法）**：识别质量属性场景→分析架构方法→评估权衡点→识别风险和敏感点
- **ADR（架构决策记录）**：记录做了什么决策、为什么、有什么后果——防止"为什么当时选了那个技术"

# 第四章：软件设计

### 4.1 面向对象设计进阶
- **SOLID 原则**：
  - S（单一职责）：一个类只有一个变化的原因
  - O（开闭）：对扩展开放，对修改关闭——通过抽象和多态
  - L（里氏替换）：子类可以完全替换父类——不改变程序的正确性
  - I（接口隔离）：客户端不被迫依赖它不用的接口——接口拆细
  - D（依赖倒置）：高层不依赖低层，两者都依赖抽象——Spring IoC 的哲学

### 4.2 设计模式（GoF 23 种，核心 8 种）
- **创建型**：
  - 单例：全局唯一实例——配置管理、连接池
  - 工厂方法：子类决定实例化哪个类——解耦创建和使用
  - 建造者：分步构建复杂对象——Lombok @Builder
- **结构型**：
  - 适配器：接口转换——连接新旧系统
  - 装饰器：动态增强对象——Java IO（BufferedReader 装饰 Reader）
  - 代理：控制访问——AOP、延迟加载
- **行为型**：
  - 观察者：发布-订阅——事件驱动、消息通知
  - 策略：算法族可切换——支付方式、排序策略

### 4.3 领域驱动设计（DDD）
- **战略设计**：限界上下文（Bounded Context） + 上下文映射（Context Map）
- **战术设计**：实体（Entity）、值对象（Value Object）、聚合（Aggregate）、领域服务、Repository
- **统一语言（Ubiquitous Language）**：领域专家和开发者在同一套术语下交流

# 第五章：软件测试

### 5.1 测试体系
- **测试金字塔**：单元测试（最多）→ 集成测试 → 端到端测试 → 手工测试（最少）
- **测试象限**：面向技术/面向业务 × 支持团队/批判产品

### 5.2 测试技术
- **白盒测试**：看代码——语句覆盖→分支覆盖→条件覆盖→路径覆盖
- **黑盒测试**：不看代码——等价类划分 + 边界值分析 + 判定表 + 因果图
- **灰盒测试**：知道部分内部逻辑——重点测试关键路径

### 5.3 测试驱动开发（TDD）
- **红→绿→重构**：先写失败的测试→写最少代码通过→重构优化
- **TDD 的好处**：代码天然可测试、减少 Bug、重构有安全保障

### 5.4 自动化测试与持续测试
- **单元测试框架**：JUnit 5（@Test, @ParameterizedTest, @Mock）
- **Mock 框架**：Mockito——`when(...).thenReturn(...)` 隔离外部依赖
- **集成测试**：Spring Boot Test + Testcontainers（真实 MySQL/Redis 容器）
- **性能测试**：JMeter/Gatling——并发、TPS、响应时间分布

# 第六章：软件项目管理

### 6.1 项目管理基础
- **铁三角**：范围 × 时间 × 成本，质量是中心
- **WBS（工作分解结构）**：将项目拆分为可估算可分配的工作包
- **甘特图 vs 燃尽图**：计划进度 vs 剩余工作量

### 6.2 估算方法
- **故事点（Story Point）**：相对大小而非绝对时间——Fibonacci 数列
- **Planning Poker**：团队成员各自估算→揭示→讨论→重新估算→收敛
- **速度（Velocity）**：团队每个 Sprint 完成的故事点总数——预测交付能力

### 6.3 技术债务管理
- **技术债象限**：鲁莽的（不谨慎的）vs 慎重的，有意的 vs 无意的
- **偿还策略**：每个 Sprint 分配 10-20% 时间清理、Bug 修复与重构并行

### 6.4 版本发布管理
- **语义化版本（SemVer）**：MAJOR.MINOR.PATCH（破坏性.新功能.Bugfix）
- **发布策略**：蓝绿部署（两套环境切换）、金丝雀发布（小比例→全量）、滚动发布（逐个替换）

# 第七章：代码质量与重构

### 7.1 代码质量度量
- **圈复杂度（Cyclomatic Complexity）**：独立路径数 = E - N + 2P——超过 10 需要关注
- **代码重复率**：DRY 原则（Don't Repeat Yourself）——但避免过度抽象
- **认知复杂度**：代码对人类理解有多难——比圈复杂度更贴近可读性

### 7.2 代码坏味道（Code Smell）
- **长方法、大类、长参数列表**
- **发散式变化**：一个类因不同原因被改 → 违反单一职责
- **散弹式修改**：一个变化要改多个类 → 封装不充分
- **依恋情结**：方法过度依赖别的类 → 应该搬家

### 7.3 重构技术
- **提取方法/类**：大变小
- **以多态替换条件**：if/switch → 策略模式
- **引入参数对象**：多个参数 → 一个对象
- **用组合替换继承**：继承→委托

# 第八章：软件工程工具与实践

### 8.1 版本控制进阶
- **Git Flow** → **GitHub Flow** → **Trunk-Based Development**
- **Code Review 最佳实践**：小 PR（<200 行）、具体反馈、自动化检查先行

### 8.2 持续集成/持续交付
- **Jenkins / GitHub Actions / GitLab CI**
- **Pipeline as Code**：Jenkinsfile / .github/workflows/
- **质量门禁**：编译→单元测试→代码扫描（SonarQube）→安全扫描→构建镜像→推送仓库

### 8.3 文档与知识管理
- **API 文档**：OpenAPI/Swagger——代码即文档
- **架构文档**：C4 模型（Context→Container→Component→Code）——不同粒度给不同读者
- **技术文档**：README + ADR + Wiki——保证新人能快速上手
