## Why Message Queues?

### Core Benefits

```
┌──────────────────────────────────────────────────────────────┐
│                     Without MQ                               │
│                                                              │
│   Service A ───HTTP───▶ Service B ───HTTP───▶ Service C      │
│      │                    │                     │            │
│      │   If B is slow→ A threads are blocked    │            │
│      │   If B is down → A fails immediately     │            │
│      │   Traffic spike → All services overloaded │           │
│      └───────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│                     With MQ                                  │
│                                                              │
│   Producer ───Message──▶ Broker ───Message──▶ Consumer       │
│      │                    │                     │            │
│      │   Producer decoupled from consumer       │            │
│      │   Buffers traffic spikes                 │            │
│      │   Consumer processes at its own pace     │            │
│      │   Downstream failure doesn't affect producer │       │
│      └───────────────────────────────────────────────────────┘
```

| Benefit | Explanation | Example |
|---|---|---|
| **Decoupling** | Producer doesn't need to know about consumers | Order service publishes "order.created" — any service can consume |
| **Async processing** | Producer returns immediately, consumer processes later | User registration → send welcome email async |
| **Traffic peak shaving** | MQ buffers excess requests | Flash sale: 10K orders/sec → MQ → DB writes at 1K/sec |
| **Load leveling** | Consumers process at their own pace | Background jobs, report generation |
| **Fault tolerance** | Messages persist even if consumer is down | Payment events survive consumer restart |
| **Event-driven architecture** | Services react to events from others | Inventory updated → reorder triggered → supplier notified |
| **Broadcast** | One message → multiple consumers | Cache invalidation across all service instances |
| **Eventually consistency** | Reliability without distributed transactions | Order status updates, data replication |

### When NOT to Use MQ

- Request-response synchronous flows (use REST/gRPC)
- Real-time communication < 10ms latency
- Simple CRUD with no decoupling need
- System with very low traffic (MQ adds operational complexity)
- Exactly-one-processing required (most MQs deliver at-least-once)

## MQ Selection Guide

```
              RABBITMQ                  KAFKA                    ROCKETMQ
            ┌──────────┐            ┌──────────┐             ┌──────────┐
            │  AMQP    │            │  Log     │             │  Mixed   │
            │  Smart   │            │  Commit  │             │  Model   │
            │  Broker  │            │  Log     │             │          │
            └──────────┘            └──────────┘             └──────────┘

Throughput:   Medium (10K/s)         Very High (1M/s)        High (100K/s)
Latency:      Low (µs)               Low (ms)                Low (ms)
Persistence:  Optional               Required                Required
Ordering:     Per queue              Per partition           Per queue
Routing:      Flexible (exchanges)   Topic-based             Topic + tag
Protocol:     AMQP, MQTT, STOMP      Custom (binary)         Custom
Ops complexity: Medium                High                    Medium
Ecosystem:    Mature / Stable        Very Active             Active (China)
```

### Detailed Comparison

| Dimension | RabbitMQ | Kafka | RocketMQ | Pulsar |
|---|---|---|---|---|
| **Year created** | 2007 | 2011 | 2012 | 2016 |
| **Language** | Erlang | Scala/Java | Java | Java |
| **Protocol** | AMQP 0-9-1, MQTT, STOMP | Custom (binary) | Custom | Custom (binary) |
| **Messaging model** | Queue (push) | Log (pull) | Queue + Log (pull) | Log + Segment (pull) |
| **Routing** | Exchange (4 types) | Topic (regex) | Topic + Tag | Topic + Key |
| **Delivery** | Push (basic.consume) | Pull (poll) | Pull (long polling) | Pull |
| **Ordering** | Per queue | Per partition | Per queue | Per partition |
| **Deduplication** | Not built-in | Idempotent producer | Built-in (msg ID) | Not built-in |
| **Delayed messages** | Plugin | Not built-in | Built-in | Not built-in |
| **Dead letter** | DLX + DLQ | DLT (configurable) | Retry + DLQ | DLQ |
| **Transaction** | Publisher confirm | Idempotent + tx | Built-in | Built-in |
| **Throughput** | 10-20K/s | 1M+/s | 100K/s | 1M+ (segmented) |
| **Latency** | <10µs (no persist) | <10ms | <10ms | <10ms |
| **Persistence** | Optional (lazy queues) | Always (disk) | Always (disk) | Always (bookie) |
| **Replication** | Mirrored/Quorum queues | ISR (in-sync replicas) | Master-slave | BookKeeper |
| **Best for** | Task queues, routing | Event streaming, logs | Financial, e-com | Multi-tenant, cloud |

## Core Concepts

### Common Terminology Across MQs

| Concept | RabbitMQ | Kafka | RocketMQ |
|---|---|---|---|
| **Producer** | Publisher | Producer | Producer |
| **Consumer** | Consumer | Consumer | Consumer |
| **Message** | Message | Record | Message |
| **Topic/Exchange** | Exchange (routes to queues) | Topic | Topic |
| **Queue/Partition** | Queue | Partition | MessageQueue |
| **Broker** | Broker node | Broker node | Broker |
| **Cluster** | Node cluster | Broker cluster | NameServer cluster |
| **Consumer Group** | Competing consumers | Consumer Group | Consumer Group |
| **Offset/Tag** | Delivery tag | Offset | Queue offset + Tag |
| **Retention** | Queue length / TTL | Time / Size based | Time / Size based |

### Producer-Consumer Models

```
Point-to-Point (Queue Model):
  Producer → [Queue] → Consumer  (one-to-one consumption)

Publish-Subscribe (Topic Model):
  Producer → [Topic] → Consumer Group A
                     → Consumer Group B
                     → Consumer Group C  (broadcast to groups)

Competing Consumers:
  Producer → [Queue] → Consumer 1
                     → Consumer 2  (messages split across consumers)
                     → Consumer 3
```

## RabbitMQ Deep Dive

### AMQP 0-9-1 Protocol Model

```
                      ┌──────────────────────────┐
                      │      RabbitMQ Broker      │
                      │                           │
Producer ──Publish──▶ │  ┌─────────┐             │
                      │  │ Exchange │             │
                      │  └────┬────┘             │
                      │       │ Binding           │
                      │       ▼                   │
                      │  ┌─────────┐  ┌────────┐  │
                      │  │ Queue A │  │Queue B │  │
                      │  └────┬────┘  └───┬────┘  │
                      │       │           │        │
                      │  ┌────▼────┐ ┌────▼────┐  │
                      │  │Consumer1│ │Consumer2│  │
                      │  └─────────┘ └─────────┘  │
                      └──────────────────────────┘

Core Components:
- Producer: Publishes messages to exchanges
- Exchange: Routing engine, receives messages from producers
- Binding: Connects exchange to queue with routing key
- Queue: Stores messages until consumed
- Consumer: Receives messages from queues
```

### Exchange Types

```
Direct Exchange (routing key = queue name exactly):
  Producer: "warn" ──┐
                      ├── Direct Exchange ── Queue "error"
  Producer: "error" ──┘                      Queue "warn"

Fanout Exchange (broadcast to ALL bound queues):
  Producer ──▶ Fanout Exchange ──▶ Queue A
                                  Queue B
                                  Queue C

Topic Exchange (routing key pattern matching):
  Producer: "user.created" ──▶ Topic Exchange
                                    │
                              Binding: "user.*"  ── Queue "user-events"
                              Binding: "*.created" ── Queue "creation-events"
                              Binding: "#.error" ── Queue "error-log"

Headers Exchange (match by header attributes):
  Producer headers: {type: "pdf", size: "large"}
                  ──▶ Headers Exchange
                            │
                      Binding: x-match=all, type="pdf", size="large"
                            ── Queue "pdf-large"
```

### Producer

```java
@Service
public class OrderEventPublisher {

    private static final Logger log = LoggerFactory.getLogger(OrderEventPublisher.class);

    @Autowired
    private RabbitTemplate rabbitTemplate;

    // Publish with confirmation
    public void publishOrderCreated(OrderCreatedEvent event) {
        CorrelationData correlationData = new CorrelationData(event.getOrderId().toString());

        // Set correlation for confirmation callback
        rabbitTemplate.setConfirmCallback((correlation, ack, cause) -> {
            if (ack) {
                log.debug("Message confirmed: {}", correlation.getId());
            } else {
                log.error("Message NOT confirmed: {}, cause: {}", correlation.getId(), cause);
                // Handle failure — store in DB for retry
                saveFailedMessage(event, cause);
            }
        });

        // Set return callback (for unroutable messages)
        rabbitTemplate.setReturnsCallback(returned -> {
            log.error("Message returned: {} (reply code: {}, text: {})",
                returned.getMessage(), returned.getReplyCode(), returned.getReplyText());
        });

        // Mandatory: true = throw exception if message can't be routed
        rabbitTemplate.setMandatory(true);

        rabbitTemplate.convertAndSend(
            "order.exchange.direct",   // Exchange
            "order.created",            // Routing key
            event,                      // Message body (auto-serialized)
            message -> {                // Message post-processor
                message.getMessageProperties().setDeliveryMode(MessageDeliveryMode.PERSISTENT);
                message.getMessageProperties().setPriority(5);
                message.getMessageProperties().setHeader("source", "order-service");
                return message;
            },
            correlationData            // Correlation for confirm
        );
    }

    // Send with delay
    public void publishDelayedCancel(Long orderId, long delayMs) {
        rabbitTemplate.convertAndSend(
            "order.exchange.delayed",
            "order.cancel",
            new OrderCancelEvent(orderId),
            message -> {
                message.getMessageProperties()
                    .setDelay(Long.valueOf(delayMs).intValue());
                return message;
            }
        );
    }

    // Sync publish (wait for result)
    public <T> T publishAndReceive(String routingKey, Object message, Class<T> responseType) {
        return rabbitTemplate.convertSendAndReceiveAsType(
            "order.exchange.direct", routingKey, message,
            new ParameterizedTypeReference<T>() {}
        );
    }
}
```

### Consumer

```java
@Component
public class OrderEventConsumer {

    private static final Logger log = LoggerFactory.getLogger(OrderEventConsumer.class);

    // Basic consumer
    @RabbitListener(
        queues = "order.queue.created",
        concurrency = "3-10"
    )
    public void handleOrderCreated(OrderCreatedEvent event, Channel channel,
                                    @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag) {
        try {
            log.info("Processing order created: {}", event.getOrderId());
            processOrder(event);

            // Manual ACK
            channel.basicAck(deliveryTag, false);
        } catch (RetryableException e) {
            // Retry — don't ACK, message remains in queue
            log.warn("Retryable error for order {}, requeueing", event.getOrderId(), e);
            channel.basicNack(deliveryTag, false, true); // requeue = true
        } catch (FatalException e) {
            // Fatal — dead letter the message
            log.error("Fatal error for order {}, sending to DLQ", event.getOrderId(), e);
            channel.basicNack(deliveryTag, false, false); // requeue = false
        }
    }

    // Multiple queues on one listener
    @RabbitListener(queues = {"order.queue.payment", "order.queue.refund"})
    public void handlePaymentEvents(Message message, Channel channel) {
        // Generic handler for payment-related events
        try {
            OrderPaymentEvent event = (OrderPaymentEvent) message.getBody();
            // Process...
            channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
        } catch (Exception e) {
            channel.basicNack(message.getMessageProperties().getDeliveryTag(),
                false, false);
        }
    }

    // Direct reply-to (RPC-style)
    @RabbitListener(queues = "order.queue.status-check")
    public OrderStatusResponse handleStatusCheck(OrderStatusRequest request) {
        // Response is automatically sent to reply-to queue
        return checkOrderStatus(request.getOrderId());
    }
}
```

### RabbitMQ Reliability

```
Publisher Confirms (RabbitMQ)
┌──────────────┐        ┌────────────────┐
│  Publisher   │───────▶│  RabbitMQ      │
│  (channel)   │        │  Broker        │
│              │◀───────│                │
│  Confirm     │   ACK  │  Writes to     │
│  Callback    │        │  disk + routes │
│              │        │  to queue      │
└──────────────┘        └────────────────┘

Consumer Acknowledgments
┌────────────────┐        ┌──────────────┐
│  RabbitMQ      │───────▶│  Consumer    │
│  (queue)       │  msg   │              │
│                │◀───────│              │
│  Removes msg   │  ACK   │  Processed   │
│  from queue    │        │  OK          │
└────────────────┘        └──────────────┘
```

**Message Flow with Full Reliability:**

```java
// Step 1: Producer sends with publisher confirm
rabbitTemplate.convertAndSend("exchange", "key", message, correlationData);

// Step 2: On confirm ACK, mark message as sent in DB
rabbitTemplate.setConfirmCallback((correlation, ack, cause) -> {
    if (ack) {
        // Delete from "pending messages" table
        pendingMessageDao.delete(correlation.getId());
    } else {
        // Retry or alert
    }
});

// Step 3: Consumer processes and ACKs manually
@RabbitListener(queues = "queue")
public void handle(Message msg, Channel channel) {
    try {
        process(msg);
        channel.basicAck(deliveryTag, false);  // Manual ACK
    } catch (Exception e) {
        channel.basicNack(deliveryTag, false, e instanceof RetryableException);
    }
}
```

### Dead Letter Exchange (DLX)

Messages are sent to DLX when:
1. Consumer rejects with `basicNack(requeue=false)` or `basicReject`
2. Message TTL expires
3. Queue length limit exceeded

```java
@Configuration
public class DeadLetterConfig {

    // DLX Exchange (regular exchange, used as DLX)
    @Bean
    public DirectExchange dlxExchange() {
        return new DirectExchange("order.exchange.dlx");
    }

    // Main queue with DLX configured
    @Bean
    public Queue mainQueue() {
        return QueueBuilder.durable("order.queue.main")
            .deadLetterExchange("order.exchange.dlx")
            .deadLetterRoutingKey("order.queue.dlq")
            .build();
    }

    // Dead Letter Queue
    @Bean
    public Queue dlq() {
        return QueueBuilder.durable("order.queue.dlq")
            .build();
    }

    // DLQ consumer (monitor and alert)
    @RabbitListener(queues = "order.queue.dlq")
    public void handleDeadLetter(Message message, Channel channel) {
        log.error("DEAD LETTER: {}", new String(message.getBody()));

        // Extract original headers
        String originalExchange = message.getMessageProperties()
            .getHeader("x-death")[0].getExchange();
        String originalRoutingKey = message.getMessageProperties()
            .getHeader("x-death")[0].getRoutingKey();
        long originalTtl = message.getMessageProperties()
            .getHeader("x-message-ttl");

        // Alert operations team
        alertService.sendAlert("Message in DLQ", message);

        // Optionally, reprocess with delay
        channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
    }
}
```

```java
// Custom retry with container
@Bean
public SimpleRabbitListenerContainerFactory retryContainerFactory(
        ConnectionFactory connectionFactory,
        RetryOperationsInterceptor retryInterceptor) {

    SimpleRabbitListenerContainerFactory factory = new SimpleRabbitListenerContainerFactory();
    factory.setConnectionFactory(connectionFactory);
    factory.setAdviceChain(retryInterceptor);
    factory.setPrefetchCount(3);
    factory.setConcurrentConsumers(3);
    return factory;
}

// Custom retry operations
@Bean
public RetryOperationsInterceptor retryInterceptor() {
    return RetryInterceptorBuilder.stateless()
        .backOffOptions(1000, 2.0, 30000)  // initial, multiplier, max
        .maxAttempts(5)
        .recoverer((message, cause) -> {
            log.error("All retries exhausted: {}", message, cause);
            // Send to DLQ or log
        })
        .build();
}

// OR use exponential backoff with random jitter
@Bean
public RetryOperationsInterceptor retryWithJitter() {
    ExponentialBackOffPolicy backOff = new ExponentialBackOffPolicy();
    backOff.setInitialInterval(1000);
    backOff.setMultiplier(2.0);
    backOff.setMaxInterval(30000);

    // Jitter prevents all consumers retrying simultaneously
    UniformRandomBackOffPolicy withJitter = new UniformRandomBackOffPolicy();
    withJitter.setMinBackOffPeriod(500);
    withJitter.setMaxBackOffPeriod(30000);

    return RetryInterceptorBuilder.stateless()
        .backOffPolicy(withJitter)
        .maxAttempts(5)
        .build();
}
```

### Prefetch Count and Flow Control

```
Consumer A (prefetch=1):                              Consumer B (prefetch=10):
[msg1] ↔ processing                                    [msg1][msg2][msg3]... ↔ processing
        (waiting)                                                         buffer
                                                                         (fast pipeline)

RabbitMQ Flow Control:
- If consumers are slow → queue grows
- If memory/disk high → publisher flow control (blocked)
- Prefetch = 1 is safest but lower throughput
- Prefetch = 100+ for high-throughput consumers but risk of uneven distribution
```

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 10        # Default is 250
        # For fast consumers: higher prefetch (10-100)
        # For slow consumers: lower prefetch (1-5)
```

### Spring RabbitMQ Best Practices

```java
// 1. Always use manual ACK for production
// 2. Always configure DLX for every queue
// 3. Set prefetch appropriately
// 4. Use publisher confirms for critical messages
// 5. Implement idempotent consumers
// 6. Log message lifecycle (published, delivered, processed, failed)

// Idempotent consumer pattern
@Component
public class IdempotentConsumer {

    @Autowired
    private RedisTemplate<String, String> redis;

    @RabbitListener(queues = "order.queue.payment")
    public void handlePayment(OrderPaymentEvent event, Channel channel,
                              @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
        String dedupKey = "dedup:payment:" + event.getTransactionId();

        // Check if already processed (idempotency)
        Boolean firstProcessed = redis.opsForValue()
            .setIfAbsent(dedupKey, "PROCESSED", Duration.ofHours(24));

        if (Boolean.FALSE.equals(firstProcessed)) {
            log.info("Duplicate event (already processed): {}", event.getTransactionId());
            channel.basicAck(tag, false); // ACK but skip processing
            return;
        }

        try {
            processPayment(event);
            channel.basicAck(tag, false);
        } catch (Exception e) {
            redis.delete(dedupKey); // Allow retry
            channel.basicNack(tag, false, false);
        }
    }
}
```

### Key Concepts

| Concept | Description |
|---|---|
| **Topic** | Category/feed name to which messages are published |
| **Partition** | Ordered, immutable sequence of records (the commit log) |

| **Replica** | Copy of a partition (for fault tolerance) |
| **Leader** | The replica that handles all reads/writes for a partition |
| **ISR** | In-Sync Replicas — replicas that are caught up with the leader |
| **Consumer Group** | Group of consumers that divide partition processing |

### Storage: Segments and Indexing

```
Partition 0 on Disk:
  /data/kafka/order-events-0/
    ├── 00000000000000000000.log       # Segment 1: offsets 0-999
    ├── 00000000000000000000.index     # Offset → file position
    ├── 00000000000000000000.timeindex # Timestamp → offset
    ├── 00000000000000001000.log       # Segment 2: offsets 1000-1999
    ├── 00000000000000001000.index
    ├── 00000000000000002000.log       # Segment 3 (active, currently writing)
    └── 00000000000000002000.index
```

**How Kafka achieves high throughput:**

```
1. Sequential IO: Writing to disk is sequential (no random seeks)
   → Hard disk sequential: 200MB/s
   → Hard disk random: 1MB/s (200x difference!)

2. Zero-Copy (sendfile):
   Traditional:  Disk → OS cache → Application buffer → Socket buffer → NIC
   Zero-copy:    Disk → OS cache → NIC (via sendfile syscall)
   → Eliminates buffer copying between kernel and user space

3. Page Cache:
   Kafka relies on OS page cache (not JVM heap)
   → Hot data stays in memory automatically
   → No GC overhead
   → Warm cache from reads (no separate cache layer)

4. Batching:
   Producers batch messages → larger network packets → fewer requests
   Consumers fetch in bulk → fewer requests
   Brokers batch disk writes → sequential IO

5. Client-side optimization:
   Compression (snappy, gzip, zstd) reduces network and storage
   Partition-level parallelism
```

### Exactly-Once Semantics (EOS)

Kafka provides exactly-once semantics through:

1. **Idempotent Producer**: `enable.idempotence=true` — prevents duplicate messages due to retries
2. **Transactions**: Atomic writes across multiple partitions/topics
3. **Transactional Consumer**: Reads only committed messages

```java
// Idempotent producer configuration
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
props.put(ProducerConfig.ACKS_CONFIG, "all");         // Required with idempotence
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-producer-1"); // For transactions

// Exactly-once example: consume-process-produce pattern
@Component
public class ExactlyOnceProcessor {

    @Autowired
    private KafkaTemplate<String, Object> kafkaTemplate;

    public void processExactlyOnce(String topic, ConsumerRecord<String, Object> record) {
        // Use Kafka transactions for atomic read-process-write
        kafkaTemplate.executeInTransaction(operations -> {
            // 1. Process the message
            ProcessedResult result = process(record.value());

            // 2. Produce result (atomically committed alongside offset commit)
            operations.send("processed-events", result);

            // 3. Offset is committed as part of the transaction
            return true;
        });
    }
}
```

## Message Reliability Patterns

### Producer Reliability

```java
// Pattern: Idempotent Producer + Retry + Confirm
// 1. Use idempotent producer (Kafka built-in)
// 2. Use publisher confirm (RabbitMQ)
// 3. Store messages in "pending" table before sending
// 4. Delete from pending on successful confirm
// 5. Background job retries pending messages

@Component
public class ReliablePublisher {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    @Autowired
    private JdbcTemplate jdbc;

    @Transactional
    public void publishReliably(String exchange, String routingKey, Object message) {
        // 1. Save to outbox table (same DB transaction as business operation)
        String messageId = UUID.randomUUID().toString();
        String payload = objectMapper.writeValueAsString(message);
        jdbc.update(
            "INSERT INTO message_outbox (id, exchange, routing_key, payload, status) VALUES (?, ?, ?, ?, 'PENDING')",
            messageId, exchange, routingKey, payload
        );

        // 2. Send to MQ
        CorrelationData correlation = new CorrelationData(messageId);
        rabbitTemplate.convertAndSend(exchange, routingKey, message, correlation);
    }
}
```

### Consumer Reliability

```java
// Pattern: Manual ACK + Idempotent Processing + DLQ
@Component
public class ReliableConsumer {

    @RabbitListener(queues = "order.queue.process")
    public void handle(OrderEvent event, Channel channel,
                       @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {

        // 1. Idempotency check (prevent duplicate processing)
        Boolean processed = redis.opsForValue()
            .setIfAbsent("processed:order:" + event.getOrderId(), "1",
                Duration.ofHours(24));

        if (Boolean.FALSE.equals(processed)) {
            // Already processed — ACK and skip
            channel.basicAck(tag, false);
            return;
        }

        try {
            // 2. Business processing
            processOrder(event);

            // 3. Manual ACK (message removed from queue)
            channel.basicAck(tag, false);

        } catch (BusinessException e) {
            // Business error — don't retry, send to DLQ
            channel.basicNack(tag, false, false);
            log.error("Business error, sent to DLQ: {}", event.getOrderId(), e);

        } catch (TransientException e) {
            // Transient error — retry
            channel.basicNack(tag, false, true); // requeue = true

        }
    }
}
```

### Delivery Semantics

| Semantic | Description | How to Achieve |
|---|---|---|
| **At-most-once** | Message may be lost, never duplicated | Fire-and-forget, auto-ACK before processing |
| **At-least-once** | Message never lost, may be duplicated | Producer retry + consumer ACK after processing |
| **Exactly-once** | Message delivered exactly once | Kafka: idempotent producer + transactions + manual commit |
| | | RabbitMQ: Not natively supported (must deduplicate at consumer) |

```java
public void publishOrderEvents(Order order) {
    // All events for the same order go to the SAME partition
    String key = order.getId().toString();

    // Event 1 (guaranteed to be before Event 2 for this key)
    kafkaTemplate.send("order-events", key, new OrderCreatedEvent(order));
    // Event 2 (same partition, same key)
    kafkaTemplate.send("order-events", key, new OrderPaidEvent(order));
}
```

### RabbitMQ: Order Within a Queue

```
RabbitMQ ordering guarantee:
- Messages within a SINGLE queue are ordered
- Multiple consumers on same queue → order is NOT guaranteed
- Reason: Consumer A might process msg1 faster than Consumer B processes msg0

To preserve order with multiple consumers:
  Method 1: Single consumer (but slow)
  Method 2: Use consistent routing (same routing key → same queue → single consumer)
  Method 3: Kafka partition model (preferred for ordered processing)
```

### Event Sourcing

Store all state changes as a sequence of events in a log (Kafka).

```
Instead of: Current balance = 100
Store:      [01.01: Deposit 100] [01.02: Withdraw 30] [01.03: Deposit 50]
            → Current: 120
            → But you CAN recompute at ANY point in time
```

```java
            new OrderCreatedEvent(id, command));

        kafka.send("order-events", id.toString(),
            new ItemAddedEvent(id, command));

    public Order getOrder(OrderId id) {
        List<OrderEvent> events = loadEvents(id);
        Order order = new Order();
        for (OrderEvent event : events) {
            order.apply(event); // Replay all events
        }
        return order;
    }
}
```

### Transactional Outbox Pattern

Ensures that messages are sent exactly once, even if the broker is unavailable.

```sql
-- Outbox table (in the SAME database as business data)
CREATE TABLE message_outbox (
    id VARCHAR(36) PRIMARY KEY,
    aggregate_id VARCHAR(64) NOT NULL,
    aggregate_type VARCHAR(32) NOT NULL,
    event_type VARCHAR(64) NOT NULL,
    payload JSON NOT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'PENDING',  -- PENDING / SENT / FAILED
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    sent_at DATETIME,
    retry_count INT DEFAULT 0
);

CREATE INDEX idx_outbox_status ON message_outbox(status, created_at);
```

```java
// Transactional Outbox Implementation

// Step 1: Business logic writes to DB + outbox IN THE SAME TRANSACTION
@Service
public class OrderServiceWithOutbox {

    @Autowired
    private OrderRepository orderRepository;

    @Autowired
    private OutboxRepository outboxRepository;

    @Transactional
    public Order createOrder(CreateOrderRequest request) {
        // 1. Save order (business data)
        Order order = orderRepository.save(Order.from(request));

        // 2. Save outbox message (SAME database transaction!)
        outboxRepository.save(new OutboxMessage(
            order.getId().toString(),
            "Order",
            "OrderCreated",
            objectMapper.writeValueAsString(new OrderCreatedEvent(order))
        ));

        return order;
    }
}

// Step 2: Background job polls outbox and publishes to MQ
@Component
public class OutboxPublisher {

    @Scheduled(fixedRate = 1000) // Every second
    @Transactional
    public void publishPendingMessages() {
        List<OutboxMessage> pending = outboxRepository
            .findTop100ByStatusOrderByCreatedAt("PENDING");

        for (OutboxMessage msg : pending) {
            try {
                kafkaTemplate.send(
                    msg.getAggregateType().toLowerCase() + "-events",
                    msg.getAggregateId(),
                    objectMapper.readValue(msg.getPayload(), Object.class)
                );
                msg.setStatus("SENT");
                msg.setSentAt(LocalDateTime.now());
                outboxRepository.save(msg);
            } catch (Exception e) {
                msg.setRetryCount(msg.getRetryCount() + 1);
                if (msg.getRetryCount() >= 10) {
                    msg.setStatus("FAILED");
                    // Alert operations
                }
                outboxRepository.save(msg);
            }
        }
    }
}
```

## Interview Questions

### Basic

1. **"What is the difference between RabbitMQ and Kafka?"**
   - RabbitMQ: Smart broker, push-based, AMQP protocol, complex routing, lower throughput
   - Kafka: Log-based, pull-based, custom protocol, simple topic routing, very high throughput
   - RabbitMQ good for task distribution, Kafka good for event streaming

2. **"Explain the AMQP model."**
   - Producer → Exchange → (Binding with routing key) → Queue → Consumer
   - Exchange types: Direct, Fanout, Topic, Headers

3. **"What is a consumer group in Kafka?"**
   - Group of consumers that share the work of processing a topic
   - Each partition is consumed by exactly one consumer in the group
   - Enables parallel processing and fault tolerance

### Intermediate

4. **"How does Kafka guarantee message ordering?"**
   - Within a single partition: guaranteed order (append-only log)
   - Same key → same partition → ordered processing
   - Across partitions: no global order guarantee

5. **"How do you ensure at-least-once delivery?"**
   - Producer: Enable retry + acks=all
   - Broker: Replication (min.insync.replicas)
   - Consumer: Manual ACK after processing (enable.auto.commit=false)
   - Consumer: Idempotent processing (deduplication)

6. **"What is dead letter exchange and how is it used?"**
   - Messages that fail processing go to DLX/DLQ
   - Prevents message pile-up in main queue
   - Enables monitoring and alerting on failed messages
   - Messages can be analyzed, reprocessed, or manually handled

7. **"Explain the transactional outbox pattern."**
   - Write to DB + outbox table in same transaction
   - Background process publishes outbox messages to MQ
   - Ensures exactly-once message publishing
   - Handles broker failures gracefully

### Advanced

8. **"How does Kafka achieve high throughput?"**
   - Sequential disk IO (append-only log)
   - Zero-copy (sendfile system call)
   - OS page cache (not JVM heap)
   - Batching (producer batches, consumer batches)
   - Compression (snappy, zstd)
   - Partition parallelism

9. **"Design a reliable order processing system using MQ."**
   - Outbox pattern for reliable publishing
   - Kafka for event stream (order created, paid, shipped)
   - RabbitMQ for task distribution (email sending, notification)
   - Idempotent consumers with Redis dedup
   - DLQ for failed messages with alerting
   - Replay capability for reconciliation

10. **"How does Kafka's rebalance protocol work?"**
    - Consumer joins/exits group → triggers rebalance
    - Eager rebalance (old): Stop ALL consumers, reassign partitions, start
    - Cooperative rebalance (new, recommended): Incremental, reassign subset
    - Partition assignment strategies: Range, RoundRobin, Sticky, CooperativeSticky
    - ConsumerRebalanceListener: onPartitionsRevoked, onPartitionsAssigned

## Summary

| Topic | Key Takeaway |
|---|---|
| **RabbitMQ** | AMQP model, exchanges (direct/fanout/topic), publisher confirm, DLX, delayed messages |
| **Kafka** | Log-based, partitions, high throughput, exactly-once, consumer groups |
| **Reliability** | Outbox pattern, idempotent consumers, DLQ, retry with backoff |
| **Ordering** | Kafka: per-partition; RabbitMQ: per-queue (single consumer for strict order) |
| **Selection** | RabbitMQ for routing/tasks, Kafka for streaming/events, RocketMQ for financial |
