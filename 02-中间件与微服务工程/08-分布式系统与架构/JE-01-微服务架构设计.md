## Monolithic Architecture Analysis

### What is a Monolith?

A monolithic architecture is a traditional software model where all components of an application (UI, business logic, data access) are packaged into a single deployable unit — typically a single WAR/JAR file deployed on a single application server.

```
                    ┌─────────────────────────────────────────┐
                    │         Monolithic Application          │
                    │                                         │
                    │  ┌──────────┐ ┌──────────┐ ┌────────┐  │
                    │  │   User   │ │  Order   │ │Product │  │
                    │  │  Module  │ │  Module  │ │ Module │  │
                    │  └──────────┘ └──────────┘ └────────┘  │
                    │  ┌──────────┐ ┌──────────┐ ┌────────┐  │
                    │  │ Payment  │ │Inventory │ │Admin   │  │
                    │  │ Module   │ │ Module   │ │Module  │  │
                    │  └──────────┘ └──────────┘ └────────┘  │
                    │                                         │
                    │  ┌─────────────────────────────────┐    │
                    │  │      Shared Database (MySQL)     │    │
                    │  │  users | orders | products | ... │   │
                    │  └─────────────────────────────────┘    │
                    └─────────────────────────────────────────┘
```

### Advantages of Monolithic Architecture

| Advantage | Detail | When It Matters |
|---|---|---|
| **Simplicity** | Single codebase, standard IDE, straightforward debugging | Small teams, early-stage products |
| **Performance** | In-process method calls (no network overhead, no serialization) | Latency-sensitive features |
| **ACID Transactions** | Classic database transactions span all entities seamlessly | Strong consistency required |
| **End-to-End Testing** | Single deployment to test; integration tests are straightforward | High regulatory environments |
| **Deployment Simplicity** | One WAR/JAR, one server, one pipeline | No DevOps team |
| **Code Sharing** | Shared domain objects, utilities, repositories; no duplication | Consistent domain model |

### Pain Points and When They Hit

```java
// Example: The monolith that grows out of control

// Problem 1: Unclear boundaries — circular dependencies
// Module A calls Module B calls Module A
@Service
public class OrderService {
    private final UserService userService;
    private final InventoryService inventoryService;

    public Order createOrder(OrderRequest req) {
        User user = userService.getUser(req.getUserId()); // cross-module call
        Inventory inventory = inventoryService.deduct(req.getProductId(), req.getQuantity());
        // ... 50 lines of business logic
        return orderRepository.save(order);
    }
}

@Service
public class InventoryService {
    private final OrderService orderService; // CIRCULAR dependency!

    public void restock(Long productId, int quantity) {
        // checks pending orders that might need this stock
        List<Order> pendingOrders = orderService.getPendingOrders(productId);
        // ...
    }
}
```

**Pain Point Timeline:**

```
Team Size  │
   2-5     │  [Happy] Simple, fast iterations
           │
   5-10    │  [Mild Discomfort] Merge conflicts, longer build times
           │
   10-20   │  [Pain] Slow CI/CD, one team's bug blocks others, db contention
           │
   20+     │  [Crisis] Deployment once per month, production incidents daily
           │
           └──────────────────────────────────────────► Time
```

**Specific Pain Points Detailed:**

1. **Scaling Inefficiency**: If the order module is CPU-bound but the user module is memory-bound, you must scale the entire application — wasting resources.

2. **Deployment Friction**: A change to one JSP page requires rebuilding and redeploying the entire application. Teams deploy less frequently, accumulating risk.

3. **Technology Lock-In**: Choosing a framework at the start becomes a permanent decision. Want to migrate from Spring MVC to WebFlux? Rewrite everything.

4. **Database Coupling**: All modules access the same database. Schema changes require coordination across all teams. A slow query in the reporting module can bring down the order module.

5. **Onboarding Overhead**: New developers must understand the entire codebase before being productive. Code review bottlenecks emerge.

```java
// Problem 2: The "God Class" anti-pattern
@Component
public class OrderServiceThatDoesEverything {
    // 2000+ lines
    public Order createOrder(...) { /* validates, checks inventory, charges, sends email */ }
    public void cancelOrder(...) { /* refunds, restocks, notifies */ }
    public OrderReport generateReport(...) { /* complex SQL queries */ }
    public void sendPromotionalEmails(...) { /* marketing logic mixed in */ }
    public void processPaymentRefund(...) { /* payment logic */ }
    // ... 30 more methods
}
```

## Microservices Definition and Characteristics

### Definition

> **Microservices** — also known as the microservice architecture — is an architectural style that structures an application as a collection of **small autonomous services** modeled around a **business domain**. Each service is **independently deployable**, has its own **data store**, and communicates with other services via **lightweight mechanisms** (typically HTTP/REST or messaging). — Adapted from Martin Fowler & James Lewis

### Core Characteristics

```yaml
# Characteristic 1: Componentization via Services
# ────────────────────────────────────────────
# Library: linked into the same process, called via function calls.
# Service: runs in its own process, called via network (HTTP/RPC).

# Characteristic 2: Organized Around Business Capabilities
# ────────────────────────────────────────────
# Traditional: UI team | middleware team | database team
# Microservice: Order team (owns UI, logic, DB for orders)

# Characteristic 3: Products Not Projects
# ────────────────────────────────────────────
# Project: build it, hand it over → "throw over the wall"
# Product: build it, own it → "you build it, you run it"

# Characteristic 4: Smart Endpoints, Dumb Pipes
# ────────────────────────────────────────────
# Instead of ESB with routing, transformation, orchestration:
# Services communicate via thin REST API or lightweight message broker.
# All business logic resides in the service, not in middleware.

# Characteristic 5: Decentralized Governance
# ────────────────────────────────────────────
# Teams choose their own tech stack (polyglot).
# Standards emerge through shared practices, not central mandate.

# Characteristic 6: Decentralized Data Management
# ────────────────────────────────────────────
# Each service owns its database (Database per Service pattern).
# No shared database — integration happens via API calls.

# Characteristic 7: Infrastructure Automation
# ────────────────────────────────────────────
# CI/CD pipelines, container orchestration, automated testing.
# Without automation, microservices become operational nightmare.

# Characteristic 8: Design for Failure
# ────────────────────────────────────────────
# Assume services will fail. Build resilience patterns.
# Circuit breakers, bulkheads, retries with backoff, timeouts.

# Characteristic 9: Evolutionary Design
# ────────────────────────────────────────────
# Services can be replaced, merged, or split over time.
# Architecture evolves with business understanding.
```

### Comparison: Monolith vs Microservices

| Dimension | Monolith | Microservices |
|---|---|---|
| **Deployment** | Single unit | Independent services |
| **Scaling** | Scale everything | Scale per service |
| **Data** | Single database | Database per service |
| **Communication** | In-process method calls | Remote calls (REST/gRPC/message) |
| **Team structure** | Feature teams (cross-cutting) | Cross-functional (by domain) |
| **Testing** | End-to-end focused | Service-level + contract testing |
| **Failure isolation** | Complete outage | Partial outage (with bulkhead) |
| **Latency** | Low (in-process) | Higher (network, serialization) |
| **Consistency** | Strong (ACID) | Eventual (BASE) |
| **Governance** | Centralized | Decentralized |
| **Complexity** | Code complexity | Infrastructure + network complexity |

### Microservice Anti-Patterns to Avoid

1. **Distributed Monolith**: Services are split but tightly coupled (shared DB, synchronous calls everywhere, no independent deployment). This is the WORST of both worlds.

2. **Microservice for Microservice's Sake**: Splitting too early or too finely. A service should be as small as possible but no smaller.

3. **Shared Database**: Multiple services accessing the same database schema. This creates coupling at the data layer.

4. **Chatty Communication**: Services making dozens of round-trips to complete a single operation. This kills performance.

5. **Anemic Services**: Services are just CRUD wrappers around database tables with no business logic.

## Service Decomposition Strategies

### Strategy 1: By Business Capability (Bounded Context)

Derived from **Domain-Driven Design (DDD)** by Eric Evans. The core concept is the **Bounded Context** — a logical boundary where a particular domain model applies.

```
                   ┌─────────────────────────────────────────┐
                   │         E-Commerce Domain               │
                   │                                         │
                   │  ┌──────────────────┐                   │
                   │  │  Product Catalog │                   │
                   │  │  Bounded Context │                   │
                   │  │                  │                   │
                   │  │  Entities:       │                   │
                   │  │  Product, Category│                   │
                   │  │  Price, Inventory │                   │
                   │  │  (stock level)    │                   │
                   │  └──────┬───────────┘                   │
                   │         │                                │
                   │  ┌──────▼───────────┐                   │
                   │  │    Order Mgmt    │                   │
                   │  │  Bounded Context │                   │
                   │  │                  │                   │
                   │  │  Entities:       │                   │
                   │  │  Order, OrderItem│                   │
                   │  │  Payment, Shipment│                   │
                   │  └──────┬───────────┘                   │
                   │         │                                │
                   │  ┌──────▼───────────┐                   │
                   │  │   User/Account   │                   │
                   │  │  Bounded Context │                   │
                   │  │                  │                   │
                   │  │  Entities:       │                   │
                   │  │  User, Address,  │                   │
                   │  │  PaymentMethod   │                   │
                   │  └──────────────────┘                   │
                   └─────────────────────────────────────────┘
```

**Steps to decompose by business capability:**

1. **Identify business capabilities** (what the business does):
   - Manage products
   - Take orders
   - Process payments
   - Manage inventory
   - Ship products
   - Manage users

2. **Define bounded contexts** (which domain model applies where):
   - A "Product" in the catalog context has price and description
   - A "Product" in the inventory context has stock level and warehouse location
   - These are different representations — different services

3. **Draw context boundaries**:
   - Within a context: ubiquitous language, shared model
   - Between contexts: translation via anti-corruption layer

4. **Map to services**: Each bounded context becomes a candidate service.

```java
// Bounded Context 1: Product Catalog
// The Product entity in THIS context

@Service
@Validated
public class ProductCatalogService {

    @Cacheable(value = "products", key = "#productId")
    public ProductView getProductDetail(Long productId) {
        Product product = productRepository.findById(productId)
            .orElseThrow(() -> new ProductNotFoundException(productId));
        // This service only knows about catalog aspects
        return new ProductView(
            product.getId(),
            product.getName(),
            product.getDescription(),
            product.getPrice(),
            product.getImages()
        );
    }
}

// The Product entity in the catalog context
@Entity
@Table(name = "catalog_products")
public class Product {
    @Id
    private Long id;
    private String name;
    private String description;
    private BigDecimal price;
    private String imageUrls; // JSON array of URLs
    private Long categoryId;
    private String attributes; // JSON: color, size, etc.
    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;
}
```

```java
// Bounded Context 2: Inventory
// The Product in this context has different concerns

@Service
public class InventoryService {

    @Transactional
    public void deductStock(Long productId, int quantity) {
        InventoryRecord record = inventoryRepository.findByProductId(productId);
        if (record.getAvailableQuantity() < quantity) {
            throw new InsufficientStockException(productId, record.getAvailableQuantity(), quantity);
        }
        record.setAvailableQuantity(record.getAvailableQuantity() - quantity);
        record.setReservedQuantity(record.getReservedQuantity() + quantity);
        inventoryRepository.save(record);

        // Publish inventory event
        eventPublisher.publish(new StockDeductedEvent(productId, quantity));
    }
}

// The Inventory entity (NOT the same as Catalog Product!)
@Entity
@Table(name = "inventory_records")
public class InventoryRecord {
    @Id
    private Long id;
    private Long productId; // references catalog product, but no FK
    private Integer availableQuantity;
    private Integer reservedQuantity;
    private Integer warehouseId;
    private String locationCode; // e.g., "A-12-B3"
    private LocalDateTime lastStockCheck;
}
```

### Strategy 2: By Subdomain (Core, Supporting, Generic)

Based on DDD's subdomain types:

| Type | Description | Example | Build or Buy? |
|---|---|---|---|
| **Core Domain** | Key competitive advantage, most complex | Recommendation engine, pricing algorithm | Build in-house |
| **Supporting** | Needed but not core | Inventory management, user notifications | Build or outsource |
| **Generic** | Commodity capabilities | Authentication, email, logging | Buy/SaaS/Open source |

**Strategy**: Invest heavily in Core domain services (best engineers, custom solutions). For Generic domains, use off-the-shelf solutions (Auth0, SendGrid, etc.).

```
                    ┌─────────────────────────────────────┐
                    │         E-Commerce System           │
                    │                                     │
                    │  CORE DOMAIN (Build in-house)       │
                    │  ┌─────────────────────────────┐    │
                    │  │  Pricing Engine             │    │
                    │  │  Recommendation Engine      │    │
                    │  │  Order Processing            │    │
                    │  └─────────────────────────────┘    │
                    │                                     │
                    │  SUPPORTING (Build/Customize)       │
                    │  ┌─────────────────────────────┐    │
                    │  │  Product Catalog            │    │
                    │  │  Inventory Mgmt             │    │
                    │  │  User Management            │    │
                    │  └─────────────────────────────┘    │
                    │                                     │
                    │  GENERIC (Buy/Open Source)          │
                    │  ┌─────────────────────────────┐    │
                    │  │  Auth (Keycloak/Auth0)      │    │
                    │  │  Logging (ELK)             │    │
                    │  │  Monitoring (Prometheus)   │    │
                    │  │  Email (SendGrid)          │    │
                    │  └─────────────────────────────┘    │
                    └─────────────────────────────────────┘
```

### Strategy 3: By Technical Layer (Discouraged)

```
WRONG APPROACH:
┌──────────┐  ┌──────────┐  ┌──────────┐
│  Frontend│  │  Frontend│  │  Frontend│  ← Separate but still tightly coupled
└──────────┘  └──────────┘  └──────────┘
┌─────────────────────────────────────────┐
│         Business Logic Service          │  ← Single service for ALL logic
└─────────────────────────────────────────┘
┌─────────────────────────────────────────┐
│          Database Service               │  ← Single service wrapping DB
└─────────────────────────────────────────┘
```

This is an anti-pattern because:
- Changes to business logic still require a single deployment
- The "database service" becomes a bottleneck and single point of failure
- Teams cannot work independently
- Does not map to business domains

### Strategy 4: Strangler Fig Pattern for Migration

Named after the fig tree that grows around a host tree and eventually replaces it. Used to incrementally migrate from monolith to microservices.

```
Phase 1: Side-by-side
┌──────────────────┐     ┌──────────────────┐
│    Monolith      │     │   New Service    │
│  (all features)  │     │  (new feature)   │
└────────┬─────────┘     └────────┬─────────┘
         │                        │
         └────────────┬───────────┘
                      │
              ┌───────▼────────┐
              │  API Gateway   │
              │  (routes to    │
              │   monolith or  │
              │   new service) │
              └────────────────┘

Phase 2: Gradual extraction
┌──────────────────┐     ┌──────────────────┐
│    Monolith      │     │  User Service    │
│  (all features)  │◄────│  (extracted)     │
│   minus users    │     └──────────────────┘
│                  │     ┌──────────────────┐
│   [ ] user       │     │  Order Service   │
│   [X] order      │◄────│  (extracted)     │
│   [X] payment    │     └──────────────────┘
│   [ ] product    │     ┌──────────────────┐
└──────────────────┘     │  Product Service │
                          │  (extracted)     │
                          └──────────────────┘

Phase 3: Monolith eliminated
┌──────────────────┐
│  (empty)         │     ┌───┐ ┌───┐ ┌───┐
│                  │     │Usr│ │Ord│ │Prd│ ...
│   Monolith      │     └───┘ └───┘ └───┘
│   replaced by   │
│   microservices │
└──────────────────┘
```

**Implementation approach:**

```java
// Step 1: Add a routing layer in front of the monolith
// Using Spring Cloud Gateway

@Configuration
public class GatewayRoutingConfig {

    @Bean
    public RouteLocator monolithMigrationRoutes(RouteLocatorBuilder builder) {
        return builder.routes()
            // New user service — route directly
            .route("user-service", r -> r
                .path("/api/users/**")
                .uri("lb://user-service"))
            // Routes still handled by monolith
            .route("monolith", r -> r
                .path("/api/**")
                .uri("http://monolith:8080"))
            .build();
    }
}
```

```java
// Step 2: In the monolith, create a branching abstraction
// that delegates to the microservice when available

@Service
public class MonolithUserService {
    // This is the OLD implementation in the monolith
    // It's being replaced by the new User Service

    private final UserRepository userRepository;

    // Feature flag: when true, delegate to new service
    @Value("${feature.user-service.enabled:false}")
    private boolean newUserServiceEnabled;

    public User getUser(Long userId) {
        if (newUserServiceEnabled) {
            // Will throw exception if new service is unavailable
            // — forces us to handle the fallback
            throw new UnsupportedOperationException(
                "Call User Service directly via Gateway instead");
        }
        // Legacy implementation
        return userRepository.findById(userId).orElseThrow();
    }
}
```

**Strangler Fig Principles:**

1. **Identify seams** — Find places in the monolith where you can intercept calls
2. **Build the new service alongside** — Don't rewrite, build new capability
3. **Route selectively** — Use gateway or proxy to send some traffic to new service
4. **Iterate** — Extract one capability at a time, not everything at once
5. **Remove old code** — Once a capability is fully migrated, delete the monolith code

## Service Communication Patterns

### Synchronous Communication: REST

The most common pattern. Service A calls Service B via HTTP and waits for a response.

```
Service A                  Service B
    │                          │
    │──── HTTP Request ───────▶│
    │                          │
    │    (processing...)       │
    │                          │
    │◀─── HTTP Response ───────│
    │                          │
```

**When to use REST:**
- Request-response semantics needed (query data)
- Low latency acceptable (< 200ms round-trip)
- Simple CRUD operations
- External-facing APIs

**Tradeoffs:**
- Tight coupling in time (caller must wait)
- Cascading failures (Service A fails if Service B is slow)
- Lower availability (all services must be available simultaneously)

```java
// REST client using OpenFeign (declarative)
@FeignClient(name = "inventory-service", path = "/api/inventory")
public interface InventoryClient {

    @GetMapping("/products/{productId}/stock")
    StockResponse checkStock(@PathVariable Long productId);

    @PostMapping("/products/{productId}/deduct")
    DeductResponse deductStock(@PathVariable Long productId,
                               @RequestBody DeductRequest request);
}

// Usage in OrderService
@Service
public class OrderService {

    private final InventoryClient inventoryClient;

    public Order createOrder(CreateOrderRequest request) {
        // Synchronous call — caller waits
        StockResponse stock = inventoryClient.checkStock(request.getProductId());
        if (stock.getAvailableQuantity() < request.getQuantity()) {
            throw new InsufficientStockException();
        }
        // Proceed with order creation
        DeductResponse deduct = inventoryClient.deductStock(
            request.getProductId(),
            new DeductRequest(request.getQuantity())
        );
        return orderRepository.save(Order.from(request));
    }
}
```

### Synchronous Communication: gRPC

gRPC is a high-performance RPC framework using Protocol Buffers and HTTP/2.

**When to use gRPC over REST:**
- High-performance internal service-to-service communication
- Streaming use cases (server-streaming, client-streaming, bidirectional)
- Strongly typed contract (`.proto` files)
- Polyglot environments (native code generation in 11+ languages)

```protobuf
// proto/inventory.proto
syntax = "proto3";

package inventory;

option java_package = "com.example.inventory.grpc";
option java_multiple_files = true;

service InventoryService {
    rpc CheckStock(StockRequest) returns (StockResponse);
    rpc DeductStock(DeductRequest) returns (DeductResponse);
    rpc StockUpdates(StockRequest) returns (stream StockEvent); // server-streaming
}

message StockRequest {
    int64 product_id = 1;
}

message StockResponse {
    int64 product_id = 1;
    int32 available_quantity = 2;
    int32 reserved_quantity = 3;
}

message DeductRequest {
    int64 product_id = 1;
    int32 quantity = 2;
    string order_id = 3;
}

message DeductResponse {
    bool success = 1;
    int32 remaining_quantity = 2;
}

message StockEvent {
    enum EventType {
        STOCK_DEDUCTED = 0;
        STOCK_RESTOCKED = 1;
        LOW_STOCK_WARNING = 2;
    }
    EventType event_type = 1;
    int64 product_id = 2;
    int32 quantity = 3;
    int64 timestamp = 4;
}
```

**REST vs gRPC Decision Matrix:**

| Factor | REST | gRPC |
|---|---|---|
| **Human readability** | Excellent (JSON) | Poor (binary) |
| **Performance** | Good | Excellent (2-10x faster) |
| **Streaming** | SSE only (unidirectional) | Full bidirectional streaming |
| **Tooling** | Universal (curl, Postman, browsers) | Needs grpcurl, Postman gRPC |
| **Contract coupling** | Loose (documentation-based) | Tight (proto file) |
| **Browser support** | Native | Needs gRPC-Web proxy |
| **Payload size** | Larger (JSON verbosity) | Smaller (binary protobuf) |
| **Code generation** | OpenAPI → client/server | Native from .proto |

### Asynchronous Communication: Message Queue

Service A sends a message to a broker; Service B receives it when ready. No direct coupling in time or space.

```
Producer                  Broker                 Consumer
    │                        │                       │
    │─────── Message ──────▶│                       │
    │                        │─────── Message ──────▶│
    │                        │                       │
    │    (continues work)    │    (processes when    │
    │                        │     ready)            │
```

**When to use async:**
- Decoupling critical: one service must operate independently
- Traffic smoothing (peak shaving)
- Event-driven workflows
- Cross-service data replication
- Notification/event broadcasting

```java
// Producer: Order Service sends event
@Service
public class OrderEventPublisher {

    private final KafkaTemplate<String, Object> kafkaTemplate;

    public void orderCreated(Order order) {
        OrderCreatedEvent event = new OrderCreatedEvent(
            order.getId(),
            order.getUserId(),
            order.getTotalAmount(),
            order.getItems(),
            Instant.now()
        );
        kafkaTemplate.send("order.events", event.orderId(), event);
    }
}

// Consumer: Inventory Service receives event
@Component
public class InventoryEventConsumer {

    private final InventoryService inventoryService;

    @KafkaListener(topics = "order.events", groupId = "inventory-group")
    public void handleOrderCreated(OrderCreatedEvent event) {
        // Process independently — inventory might take 2 seconds or 2 minutes
        for (OrderItem item : event.items()) {
            inventoryService.deductStock(item.productId(), item.quantity());
        }
    }
}
```

### Asynchronous Communication: Event Bus (Event-Driven Architecture)

Services communicate through events via an event bus (Kafka, RabbitMQ, Pulsar, etc.). This is a superset of simple messaging — events represent something that happened in the past.

```
                    ┌──────────────────┐
                    │   Event Bus      │
                    │   (Kafka)        │
                    └──┬──┬──┬──┬──┬──┘
                       │  │  │  │  │
           ┌───────────┘  │  │  │  └───────────┐
           │              │  │  │               │
    ┌──────▼──┐   ┌──────▼──▼──▼──┐   ┌───────▼───┐
    │ Order   │   │  Inventory    │   │ Payment   │
    │ Service │   │  Service      │   │ Service   │
    └─────────┘   └───────────────┘   └───────────┘
          │                                    │
          │     Event: OrderCreated             │
          │     ┌──────────────────┐            │
          └────▶│  orderId: 12345  │────────────▶
                │  userId: 67890   │            │
                │  items: [...]    │            │
                │  total: 299.00   │            │
                └──────────────────┘            │
                                                │
          ┌──────────────────┐                  │
          │   Event:         │                  │
          │   PaymentDone    │◄─────────────────┘
          │   orderId: 12345 │
          │   status: OK     │
          └──────────────────┘
```

### Request-Response vs Event-Driven: Comparison Matrix

| Dimension | Request-Response (REST/RPC) | Event-Driven |
|---|---|---|
| **Coupling** | Temporal (client waits) | Temporal decoupling (async) |
| **Complexity** | Simple to implement | Higher (event schema evolution, eventual consistency) |
| **Performance** | Lower (waiting time) | Higher (no waiting, parallel processing) |
| **Resilience** | Fragile (chain failures) | Robust (isolated, replayable) |
| **Consistency** | Strong (can wait for confirmation) | Eventual (must handle temporary inconsistency) |
| **Traceability** | Simple (single trace) | Complex (event chains) |
| **Data flow** | Who needs what? Explicit calls | Anyone can listen |
| **Testing** | Direct service testing | Must set up event infrastructure |
| **Backpressure** | Implicit (caller waits) | Must implement explicitly |
| **Evolution** | API versioning needed | New consumers can join without producer changes |

### Hybrid Approach: Most Systems Use Both

```java
// Real-world order service uses BOTH sync and async

@Service
public class HybridOrderService {

    // Sync: Query data needed immediately
    private final UserClient userClient;
    private final ProductClient productClient;
    // Async: Notify downstream systems
    private final OrderEventPublisher eventPublisher;

    @Transactional
    public Order createOrder(CreateOrderRequest request) {
        // 1. Sync: Validate user exists
        User user = userClient.getUser(request.getUserId());

        // 2. Sync: Get product details for pricing
        List<Product> products = productClient.getProducts(
            request.getItems().stream().map(Item::getProductId).toList()
        );

        // 3. Calculate pricing
        Order order = calculateAndSaveOrder(user, products, request);

        // 4. Async: Notify other services
        //    — Don't block on inventory deduction, shipping, etc.
        eventPublisher.orderCreated(order);

        return order;
    }
}
```

## Distributed System Theory

### CAP Theorem

Proved by Eric Brewer (2000) and formalized by Seth Gilbert and Nancy Lynch (2002). In a distributed data store, you can only have at most two of three guarantees:

```
                  Consistency
                      │
                      │
                      │
        ┌─────────────┼─────────────┐
        │             │             │
        │   CP        │      AP     │
        │             │             │
        └─────────────┼─────────────┘
                      │
                      │
                   Partition
                   Tolerance
                      │
                      │
                      │
                      │
                   Availability
```

**Definitions:**

| Property | Meaning | Violation Example |
|---|---|---|
| **Consistency (C)** | Every read receives the most recent write or an error | Stale data returned |
| **Availability (A)** | Every request receives a (non-error) response, without guarantee it contains the latest write | Request times out |
| **Partition Tolerance (P)** | The system continues to operate despite network partitions between nodes | Network split between data centers |

**The Critical Insight**: In a distributed system, partitions (network failures) are inevitable. Therefore, you must choose between CP and AP. You cannot avoid P.

| Category | Choice | Tradeoff | Examples |
|---|---|---|---|
| **CP** | Consistency + Partition Tolerance | If partition occurs, some nodes become unavailable (reject requests) | Zookeeper, etcd, Consul, HBase |
| **AP** | Availability + Partition Tolerance | If partition occurs, all nodes accept requests, but data may be stale | Cassandra, DynamoDB, Couchbase, Eureka |
| **CA** | Consistency + Availability | Cannot exist in a distributed system (only single-node) | Single-node MySQL |

```
         ┌─────────────────────────────────────────┐
         │   CAP in Practice                        │
         │                                         │
         │   Scenario: Network partition between    │
         │   Node A (Beijing) and Node B (Shanghai)  │
         │                                         │
         │   CP decision (Zookeeper):               │
         │   - One side becomes "unavailable"       │
         │   - Reads/writes fail on minority side   │
         │   - Guarantee: no stale reads            │
         │                                         │
         │   AP decision (Cassandra):               │
         │   - Both sides accept reads/writes       │
         │   - Data may diverge (conflicts)         │
         │   - Conflict resolution later (LWW, etc) │
         │   - Guarantee: always available          │
         └─────────────────────────────────────────┘
```

### CAP and Microservices

In a microservice architecture, each service owns its database. CAP considerations apply to:
- **Configuration servers** (etcd/ZK/Consul): Typically CP — consistency of configuration is critical
- **Service registries** (Eureka/Nacos): Eureka is AP (favors availability), Nacos can be CP or AP
- **Caches** (Redis Cluster): Typically CP in cluster mode
- **Message queues** (Kafka): CP (ISR-based replication)
- **Your business data**: Depends on requirement (AP for most, CP for financial)

### BASE Theory

BASE is the practical alternative to ACID for distributed systems, proposed by Dan Pritchett (eBay).

| ACID | BASE |
|---|---|
| Atomic | Basically Available |
| Consistent | Soft state |
| Isolated | Eventually consistent |
| Durable | |

**Basically Available**: The system guarantees availability (as per CAP's A). Some responses may be degraded (e.g., showing cached data instead of real-time).

**Soft State**: The state of the system may change over time without input, due to eventual consistency processes (e.g., background reconciliation).

**Eventually Consistent**: Given enough time without new updates, all replicas will converge to the same value.

```
Time
│
│  Write "X=5" to Node A
│  ──────────────────────► ┌──────┐
│                          │ Node │    Node B has "X=0"
│                          │  A   │    Node C has "X=0"
│                          │ X=5  │
│                          └──────┘
│  Replication in progress...
│  ──────────────────────► ┌──────┐  ┌──────┐
│                          │ Node │  │ Node │
│                          │  A   │  │  B   │
│                          │ X=5  │  │ X=5  │
│                          └──────┘  └──────┘  Node C still "X=0"
│
│  Convergence complete
│  ──────────────────────► ┌──────┐  ┌──────┐  ┌──────┐
│                          │ Node │  │ Node │  │ Node │
│                          │  A   │  │  B   │  │  C   │
│                          │ X=5  │  │ X=5  │  │ X=5  │
│                          └──────┘  └──────┘  └──────┘
│
└──────────────────────────────────────────────────────────► Time
  "Eventually" — the system converges
```

**Eventual Consistency Windows**:

| System | Typical Window |
|---|---|
| DNS | Minutes to hours |
| Cassandra (within DC) | Milliseconds |
| Cassandra (cross-DC) | Seconds to minutes |
| DynamoDB (global tables) | < 1 second |
| MySQL async replication | Milliseconds to minutes |

## Service Discovery

### Why Service Discovery?

In a monolithic app, Service A calls Service B via a hardcoded reference. In microservices:
- Instances are dynamic (scale up/down, failures, rolling updates)
- IP addresses change
- You need a way to map service names → instance addresses

### Client-Side Discovery

```
Service A                    Registry              Service B Instance 1
    │                           │                        │
    │── 1. Register ───────────▶│◀── 1. Register ────────│
    │                           │                        │
    │── 2. Discover ───────────▶│                        │
    │◀─── [B: 10.0.0.1:8081,   │                        │
    │       10.0.0.2:8081] ─────│                        │
    │                           │                        │
    │── 3. Call ────────────────────────────────────────▶│
    │                           │                        │
```

**How it works:**
1. Service instances register with the registry on startup
2. Service A queries the registry to find available instances of Service B
3. Service A uses a client-side load balancer (e.g., Ribbon, Spring Cloud LoadBalancer) to select an instance
4. Service A calls Service B directly

**Advantages:**
- Fewer moving parts (no separate load balancer needed)
- Each service can implement its own load balancing strategy
- Eliminates a network hop (no LB bottleneck)

**Disadvantages:**
- Client logic coupling (each service needs discovery client code)
- More complex client code
- Still need a separate LB for external traffic

**Tools:** Netflix Eureka, Nacos, Consul, Kubernetes DNS

### Server-Side Discovery

```
                        ┌─────────────────────────────┐
                        │     Load Balancer /          │
                        │     API Gateway              │
                        │          │                   │
                        │    Registry integration      │
                        └─────┬───────┬───────┬────────┘
                              │       │       │
                        ┌─────▼───┐ ┌─▼─────┐ ┌▼────────┐
                        │ Service  │ │Service│ │ Service │
                        │ B Inst 1 │ │B Inst2│ │ B Inst3 │
                        └──────────┘ └───────┘ └─────────┘
```

**How it works:**
1. Client sends request to a load balancer (LB) or API Gateway
2. The LB queries the registry (or is itself aware of instances)
3. LB forwards the request to a healthy instance

**Advantages:**
- Client is simpler (just makes a single HTTP call to LB)
- Centralized load balancing and routing policies
- LB can handle cross-cutting concerns (auth, rate limiting)

**Disadvantages:**
- Additional network hop
- LB is a potential bottleneck/single point of failure
- LB must be configured as a cluster for HA

**Tools:** AWS ALB/NLB, Kubernetes Service, Kong, Spring Cloud Gateway

### Service Registry Comparison

| Feature | Nacos | Consul | Eureka | Zookeeper |
|---|---|---|---|---|
| **CAP** | CP + AP (switchable) | CP | AP | CP |
| **Health check** | HTTP/TCP/MySQL | HTTP/TCP/gRPC/script | HTTP heartbeat only | TCP session |
| **KV Store** | Included | Built-in | No | Included |
| **Multi-DC** | Yes | Yes | Yes (limited) | Yes |
| **Config Center** | Built-in | Built-in (KV) | No | No (3rd party) |
| **Spring Cloud** | Native via SC Alibaba | Spring Cloud Consul | Spring Cloud Netflix | Spring Cloud ZK |
| **Consistency Protocol** | Distro+Raft (switchable) | Raft | Peer-to-peer (AP) | Zab (Paxos-like) |
| **Maintenance** | Active (Alibaba) | Active (HashiCorp) | Maintenance mode (Netflix) | Active (Apache) |
| **Admin UI** | Excellent | Good | Basic | Command-line |

## Distributed Transactions

### Why Distributed Transactions Are Hard

In a monolith, a single database transaction ensures ACID:
```sql
BEGIN TRANSACTION;
    UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
    UPDATE orders SET status = 'paid' WHERE order_id = 123;
    INSERT INTO payment_log (order_id, amount) VALUES (123, 100);
COMMIT;
```

In microservices:
```java
// This CANNOT be a single database transaction across services
userService.deductBalance(userId, 100);   // Separate DB
orderService.markPaid(orderId);           // Separate DB
paymentService.saveLog(orderId, 100);     // Separate DB
// What if paymentService.saveLog fails after userService succeeded?
```

### Solution 1: 2PC (Two-Phase Commit)

```
Coordinator              Participant A        Participant B
    │                          │                    │
    │── Phase 1: Prepare ────▶│                    │
    │                          │── Can commit? ────│
    │◀────────────────────────│── Yes ────────────▶│
    │                          │                    │
    │── Phase 2: Commit ─────▶│                    │
    │                          │── Commit ─────────│
    │◀────────────────────────│── Done ───────────▶│
    │                          │                    │
```

**Drawbacks in microservices:**
- **Blocking protocol**: Participants hold locks during Phase 1
- **Single point of failure**: Coordinator crashes → participants wait indefinitely
- **No fault tolerance**: If a participant fails after committing, data is inconsistent
- **Performance**: High latency due to multiple round-trips

**Real-world**: 2PC is impractical for most microservice scenarios. Used only in very specific cases where the coordinator can be highly available (e.g., XA transactions in JTA with a robust TM).

### Solution 2: TCC (Try-Confirm/Cancel)

TCC is a more practical pattern for service-oriented systems. Each operation has three phases:

```
Phase    Service A             Service B             Service C
─────────────────────────────────────────────────────────────
Try      Reserve funds         Reserve stock         Reserve coupon
         (funds frozen)        (stock held)          (coupon held)
Confirm  Deduct funds          Deduct stock          Use coupon
         (funds gone)          (stock gone)          (coupon used)
Cancel   Release funds         Release stock         Release coupon
         (funds unfrozen)      (stock available)     (coupon available)
```

**TCC Implementation Example:**

```java
// TCC try phase — the service must be idempotent
@LocalTCC
public interface PaymentTccService {

    @TwoPhaseBusinessAction(
        name = "paymentTcc",
        commitMethod = "confirm",
        rollbackMethod = "cancel",
        useTCCFence = true
    )
    PaymentResult tryPay(@BusinessActionContextParameter(paramName = "paymentId") String paymentId,
                         @BusinessActionContextParameter(paramName = "amount") BigDecimal amount);

    boolean confirm(BusinessActionContext context);

    boolean cancel(BusinessActionContext context);
}
```

```java
// Implementation with Seata
@Service
public class PaymentTccServiceImpl implements PaymentTccService {

    @Autowired
    private PaymentMapper paymentMapper;

    @Override
    public PaymentResult tryPay(String paymentId, BigDecimal amount) {
        // Try: Freeze the amount
        PaymentRecord record = new PaymentRecord();
        record.setPaymentId(paymentId);
        record.setAmount(amount);
        record.setStatus("FROZEN");  // Frozen, not yet deducted
        paymentMapper.insert(record);
        return new PaymentResult(true, "Frozen");
    }

    @Override
    public boolean confirm(BusinessActionContext context) {
        // Confirm: Move from frozen to completed
        String paymentId = (String) context.getActionContext("paymentId");
        PaymentRecord record = paymentMapper.findByPaymentId(paymentId);
        record.setStatus("COMPLETED");
        paymentMapper.update(record);
        return true;
    }

    @Override
    public boolean cancel(BusinessActionContext context) {
        // Cancel: Release the frozen amount
        String paymentId = (String) context.getActionContext("paymentId");
        PaymentRecord record = paymentMapper.findByPaymentId(paymentId);
        if (record != null && "FROZEN".equals(record.getStatus())) {
            record.setStatus("CANCELLED");
            paymentMapper.update(record);
        }
        return true;
    }
}
```

**TCC Advantages:**
- Non-blocking (no locks held across network calls)
- Fault-tolerant (cancel can handle failures)
- More practical for microservices than 2PC

**TCC Disadvantages:**
- Requires idempotent implementations (try/confirm/cancel may be called multiple times)
- Business logic is split across three methods
- Complex to get right — must handle "dangling" confirms/cancels

### Solution 3: Saga Pattern

A saga is a sequence of local transactions where each step publishes an event that triggers the next step. If a step fails, the saga executes compensating transactions to undo previous steps.

#### Choreography Saga

```
Order Service          Payment Service         Inventory Service
    │                        │                        │
    │── OrderCreated ──────▶│                        │
    │                        │── PaymentProcessed ──▶│
    │◀───────────────────────│                        │
    │                        │                        │── StockDeducted ──▶ Order
    │◀───────────────────────────────────────────────│    Service marks
    │                        │                        │    order completed

On Failure:
    │                        │                        │
    │                        │── PaymentFailed ─────▶│
    │◀───────────────────────│                        │
    │                        │                        │── InventoryRelease
    │◀───────────────────────────────────────────────│
    │── OrderCancelled                               │
```

```java
// Choreography Saga Implementation
// Each service publishes and listens to events

// Step 1: Order Service creates order and publishes event
@Service
public class OrderSagaService {

    @Autowired
    private KafkaTemplate<String, Object> kafka;

    @Transactional
    public Order createOrder(OrderRequest request) {
        // Save order with status "PENDING"
        Order order = new Order(request);
        order.setStatus("PENDING_CREATED");
        orderRepository.save(order);

        // Publish event — triggers next step in saga
        kafka.send("saga.order", "order-created",
            new OrderCreatedEvent(order.getId(), order.getUserId(), order.getItems()));

        return order;
    }

    // Listen for completion
    @KafkaListener(topics = "saga.inventory", groupId = "order-group")
    public void onInventoryDeducted(StockDeductedEvent event) {
        Order order = orderRepository.findById(event.orderId());
        order.setStatus("CONFIRMED");
        orderRepository.save(order);
    }

    // Listen for failure — compensate
    @KafkaListener(topics = "saga.compensation", groupId = "order-group")
    public void onCompensation(SagaFailedEvent event) {
        Order order = orderRepository.findById(event.orderId());
        order.setStatus("CANCELLED");
        order.setCancelReason(event.reason());
        orderRepository.save(order);
    }
}
```

```java
// Step 2: Payment Service listens and processes payment
@Service
public class PaymentSagaService {

    @Autowired
    private KafkaTemplate<String, Object> kafka;

    @KafkaListener(topics = "saga.order", groupId = "payment-group")
    public void onOrderCreated(OrderCreatedEvent event) {
        try {
            // Process payment
            paymentService.charge(event.userId(), event.total());

            // Success → publish event for inventory
            kafka.send("saga.payment", "payment-done",
                new PaymentCompletedEvent(event.orderId()));
        } catch (Exception e) {
            // Failure → publish compensation event
            kafka.send("saga.compensation", "payment-failed",
                new SagaFailedEvent(event.orderId(), "Payment failed: " + e.getMessage()));
        }
    }
}
```

**Choreography Pros:**
- Simpler architecture (no coordinator)
- Loose coupling (services only know about events)
- Easy to add new participants

**Choreography Cons:**
- Logic is distributed — hard to understand the full saga flow
- Cyclic dependencies between services (A listens to B's events, B listens to A's)
- No central place for error handling

#### Orchestration Saga

```
                     Saga Orchestrator
                           │
              ┌────────────┼────────────┐
              │            │            │
        ┌─────▼────┐ ┌────▼────┐ ┌────▼────┐
        │   Order  │ │ Payment │ │Inventory│
        │  Service │ │ Service │ │ Service │
        └──────────┘ └─────────┘ └─────────┘

Flow:
SagaOrchestrator:
  1. Call OrderService.createOrder()
  2. Call PaymentService.charge()
  3. Call InventoryService.deduct()
  4. Call OrderService.complete()
  
  On any failure, run compensation:
    3b. (if step 3 fails) Call PaymentService.refund()
    2b. (if step 2 fails) Call OrderService.cancel()
```

```java
// Orchestrator — central coordinator for the saga
@Component
public class OrderSagaOrchestrator {

    private final Map<String, SagaState> sagaStates = new ConcurrentHashMap<>();

    public String startSaga(CreateOrderRequest request) {
        String sagaId = UUID.randomUUID().toString();

        SagaState state = new SagaState(sagaId, request);
        state.setCurrentStep("CREATE_ORDER");
        sagaStates.put(sagaId, state);

        // Start async execution
        CompletableFuture.runAsync(() -> executeSaga(state));

        return sagaId; // Return to caller for status polling
    }

    private void executeSaga(SagaState state) {
        try {
            // Step 1: Create Order
            Order order = orderClient.createOrder(state.getRequest());
            state.setOrderId(order.getId());
            state.addCompensation(() -> orderClient.cancelOrder(order.getId()));

            // Step 2: Process Payment
            PaymentResult payment = paymentClient.charge(
                state.getRequest().getUserId(), order.getTotal());
            state.setPaymentId(payment.transactionId());
            state.addCompensation(() -> paymentClient.refund(payment.transactionId()));

            // Step 3: Deduct Inventory
            inventoryClient.deductStock(state.getRequest().getItems());
            // No compensation for inventory typically (stock is physical)

            // Step 4: Complete Order
            orderClient.completeOrder(order.getId());
            state.setStatus("COMPLETED");

        } catch (Exception e) {
            // Run compensations in REVERSE order
            state.setStatus("COMPENSATING");
            List<Runnable> compensations = state.getCompensations();
            Collections.reverse(compensations);
            for (Runnable compensation : compensations) {
                try {
                    compensation.run();
                } catch (Exception ex) {
                    log.error("Compensation failed: {}", ex.getMessage());
                    // Log and continue — manual intervention needed
                }
            }
            state.setStatus("COMPENSATED");
            state.setError(e.getMessage());
        }
    }
}

// Saga state tracking
@Data
public class SagaState {
    private final String sagaId;
    private final CreateOrderRequest request;
    private Long orderId;
    private String paymentId;
    private String status; // PENDING, COMPLETED, COMPENSATING, COMPENSATED
    private String currentStep;
    private String error;
    private final List<Runnable> compensations = new ArrayList<>();

    // LIFO order for compensations
    public void addCompensation(Runnable compensation) {
        compensations.add(compensation);
    }
}
```

**Orchestration Pros:**
- Centralized saga logic — easy to understand and modify
- Clear flow control with explicit state machine
- Better error handling and monitoring

**Orchestration Cons:**
- Orchestrator is a potential central point of complexity
- Services are less autonomous (orchestrator tells them what to do)
- Orchestrator must be highly available

### Distributed Transaction Selection Guide

| Pattern | Consistency | Performance | Complexity | Use Case |
|---|---|---|---|---|
| **2PC/XA** | Strongest (ACID) | Poor (blocking) | High | Banking, very rare |
| **TCC** | Strong (non-blocking) | Medium | High | Payment reservation, inventory |
| **Saga (choreography)** | Eventual | High | Medium | Order processing, travel booking |
| **Saga (orchestration)** | Eventual | High | Medium (coordinated) | Complex multi-step workflows |
| **Seata AT** | Strong | Medium | Low (automatic) | When you need ACID-like, but must accept tradeoffs |
| **Best effort** | Weakest | Best | Low | Logging, notifications |
| **Outbox Pattern** | At-least-once | High | Medium | Reliable event publishing |

**Rule of Thumb:** Avoid distributed transactions if possible. Redesign the system to minimize cross-service operations. When you must, prefer Saga over 2PC, and choreography over orchestration for simple flows.

## Idempotency

### The Problem

In distributed systems, the same request can be delivered multiple times due to:
- Network timeouts (client retries)
- Message queue at-least-once delivery
- Consumer crashes after processing but before acknowledgment

Without idempotency, processing a payment twice or deducting inventory twice would be catastrophic.

### Pattern 1: Unique Request ID (Idempotency Key)

```java
@RestController
@RequestMapping("/api/payments")
public class PaymentController {

    @PostMapping
    public PaymentResult processPayment(
            @RequestBody @Valid PaymentRequest request,
            @RequestHeader("Idempotency-Key") String idempotencyKey) {

        // Check if this request has already been processed
        IdempotencyRecord existing = idempotencyRepository.findById(idempotencyKey);
        if (existing != null) {
            // Return the SAME result as before (not reprocess)
            return existing.getResult();
        }

        // Process the payment
        PaymentResult result = paymentService.process(request);

        // Store the result keyed by idempotency key
        idempotencyRepository.save(new IdempotencyRecord(idempotencyKey, result));

        return result;
    }
}

// Implementation detail: idempotency storage with TTL
@Repository
public class IdempotencyRepository {

    private final RedisTemplate<String, Object> redis;

    public IdempotencyRecord findById(String key) {
        return (IdempotencyRecord) redis.opsForValue()
            .get("idempotency:" + key);
    }

    public void save(IdempotencyRecord record) {
        // Auto-expire after 24 hours (adjust based on business needs)
        redis.opsForValue()
            .set("idempotency:" + record.getKey(), record, Duration.ofHours(24));
    }
}
```

**Client-side:**
```java
// Client always generates and sends idempotency key
@Service
public class PaymentClientService {

    public PaymentResult charge(String userId, BigDecimal amount) {
        String idempotencyKey = UUID.randomUUID().toString();

        HttpHeaders headers = new HttpHeaders();
```

### Pattern 2: Database Unique Constraint

Leverage database constraints to prevent duplicate processing:

```java
// Schema: unique constraint on business key
// CREATE TABLE payment (
//     id BIGINT AUTO_INCREMENT PRIMARY KEY,
//     business_ref_no VARCHAR(64) NOT NULL UNIQUE,  ← This is the business key
//     order_id BIGINT NOT NULL,
//     amount DECIMAL(10,2) NOT NULL,
//     status VARCHAR(20) NOT NULL,
//     created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
// );

@Service
public class IdempotentPaymentService {

    public PaymentResult processPayment(String businessRefNo, Long orderId, BigDecimal amount) {
        try {
            Payment payment = new Payment();
            payment.setBusinessRefNo(businessRefNo); // Must be unique
            payment.setOrderId(orderId);
            payment.setAmount(amount);
            payment.setStatus("PROCESSING");
            // If this INSERT violates the unique constraint, it's a duplicate
            paymentRepository.save(payment);

            // Process the actual payment...
            payment.setStatus("COMPLETED");
            paymentRepository.save(payment);

            return new PaymentResult(true, "Completed");

        } catch (DataIntegrityViolationException e) {
            // Unique constraint violation — this is a duplicate request
            Payment existing = paymentRepository.findByBusinessRefNo(businessRefNo);
            return new PaymentResult(true, "Already processed: " + existing.getStatus());
        }
    }
}
```

```java
@Service
public class TokenVerificationService {

    private final RedisTemplate<String, String> redis;

    public boolean verifyToken(String token) {
        // Atomic: get the token and delete it in one Lua script
        // Prevents race conditions (two concurrent requests can't both succeed)
        String script = """
            local token = redis.call('GET', KEYS[1])
            if token then
                redis.call('DEL', KEYS[1])
                return 1  -- Verified and consumed
            else
                return 0  -- Invalid or already consumed
            end
            """;

        Long result = redis.execute(
            new DefaultRedisScript<>(script, Long.class),
            Collections.singletonList("token:" + token)
        );

        return Long.valueOf(1).equals(result);
    }
}
```

### Pattern 4: State Machine

Ensure that state transitions are valid and idempotent:

```java
// Order states and valid transitions
public enum OrderStatus {
    PENDING,
    PAID,        // can only come from PENDING
    SHIPPED,     // can only come from PAID
    DELIVERED,   // can only come from SHIPPED
    CANCELLED;   // can only come from PENDING

    public boolean canTransitionTo(OrderStatus target) {
        switch (this) {
            case PENDING:
                return target == PAID || target == CANCELLED;
            case PAID:
                return target == SHIPPED;
            case SHIPPED:
                return target == DELIVERED;
            case DELIVERED:
            case CANCELLED:
                return false; // Terminal states
            default:
                return false;
        }
    }
}

// Usage
@Transactional
public void updateOrderStatus(Long orderId, OrderStatus newStatus) {
    Order order = orderRepository.findByIdForUpdate(orderId); // PESSIMISTIC lock!
    OrderStatus current = order.getStatus();

    if (current == newStatus) {
        // Idempotent: already in this state, no-op
        return;
    }

    if (!current.canTransitionTo(newStatus)) {
        throw new IllegalStateException(
            "Cannot transition from " + current + " to " + newStatus);
    }

    order.setStatus(newStatus);
    orderRepository.save(order);
}
```

## Distributed ID Generation

### Requirements

In a distributed system, particularly with sharded databases, auto-increment IDs don't work:

1. **Global uniqueness** — No two services generate the same ID
2. **Monotonically increasing** (or roughly so) — For database B-tree index efficiency
3. **High performance** — Generating IDs should not be a bottleneck
4. **Availability** — ID generation must work even during network partitions

### Comparison of Approaches

| Method | Length | Ordering | Performance | Dependency | Notes |
|---|---|---|---|---|---|
| **UUID v4** | 128-bit (36 chars) | Random | High (local) | None | Not index-friendly |
| **UUID v7** | 128-bit | Time-sorted | High (local) | None | Better for DB (2022 RFC) |
| **Snowflake** | 64-bit (long) | Time-sorted | Very high (local) | Clock sync | Twitter's algorithm |
| **Leaf (Meituan)** | 64-bit segment-based | Increasing | High | DB | Pre-allocates segments |
| **TinyID** | Variable | Increasing | High | DB | Baidu's segment + cache |
| **Redis INCR** | 64-bit | Strictly increasing | Very high | Redis | Single point of failure |
| **DB Sequence** | 64-bit | Strictly increasing | Low | DB | Bottleneck at high QPS |

### Snowflake Algorithm (Twitter)

```
Snowflake ID: 64-bit long
┌────────────────────────────────────────────────────────────────┐
│ 0 │ 41-bit timestamp │ 10-bit machine ID │ 12-bit sequence │
│(1)│ (millisecond epoch)│ (5 DC + 5 worker) │ (per ms)        │
└────────────────────────────────────────────────────────────────┘

- Bit 0: Unused (sign bit, always 0)
- Bits 1-41: Timestamp (milliseconds since custom epoch) — ~69 years
- Bits 42-51: Machine ID (10 bits = 1024 nodes)
- Bits 52-63: Sequence (12 bits = 4096 IDs per ms per node)
```

```java
// Snowflake ID Generator Implementation
public class SnowflakeIdGenerator {

    // Bits allocation
    private static final long TIMESTAMP_BITS = 41L;
    private static final long MACHINE_ID_BITS = 10L;
    private static final long SEQUENCE_BITS = 12L;

    // Maximum values
    private static final long MAX_MACHINE_ID = ~(-1L << MACHINE_ID_BITS);
    private static final long MAX_SEQUENCE = ~(-1L << SEQUENCE_BITS);

    // Shifts
    private static final long MACHINE_ID_SHIFT = SEQUENCE_BITS;
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + MACHINE_ID_BITS;

    // Custom epoch (2020-01-01T00:00:00Z)
    private static final long CUSTOM_EPOCH = 1577836800000L;

    private final long machineId;
    private long lastTimestamp = -1L;
    private long sequence = 0L;

    public SnowflakeIdGenerator(long machineId) {
        if (machineId < 0 || machineId > MAX_MACHINE_ID) {
            throw new IllegalArgumentException(
                "Machine ID must be between 0 and " + MAX_MACHINE_ID);
        }
        this.machineId = machineId;
    }

    public synchronized long nextId() {
        long currentTimestamp = System.currentTimeMillis();

        if (currentTimestamp < lastTimestamp) {
            // Clock moved backwards — handle by waiting or throwing
            long offset = lastTimestamp - currentTimestamp;
            if (offset <= 5000) {
                // Wait for clock to catch up (max 5 seconds)
                try {
                    Thread.sleep(offset);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    throw new IdGenerationException("Clock drift recovery interrupted");
                }
                currentTimestamp = System.currentTimeMillis();
            } else {
                throw new IdGenerationException(
                    "Clock moved backwards by " + offset + "ms");
            }
        }

        if (currentTimestamp == lastTimestamp) {
            sequence = (sequence + 1) & MAX_SEQUENCE;
            if (sequence == 0) {
                // Sequence exhausted in this millisecond — wait for next ms
                currentTimestamp = waitForNextMillis(currentTimestamp);
            }
        } else {
            sequence = 0L;
        }

        lastTimestamp = currentTimestamp;

        return ((currentTimestamp - CUSTOM_EPOCH) << TIMESTAMP_SHIFT)
            | (machineId << MACHINE_ID_SHIFT)
            | sequence;
    }

    private long waitForNextMillis(long currentTimestamp) {
        long ts = System.currentTimeMillis();
        while (ts <= currentTimestamp) {
            ts = System.currentTimeMillis();
        }
        return ts;
    }

    // Parse the ID back to its components (useful for debugging)
    public static IdComponents parse(long id) {
        long timestamp = (id >>> TIMESTAMP_SHIFT) + CUSTOM_EPOCH;
        long machineId = (id >>> MACHINE_ID_SHIFT) & MAX_MACHINE_ID;
        long sequence = id & MAX_SEQUENCE;
        return new IdComponents(timestamp, machineId, sequence);
    }

    public record IdComponents(long timestamp, long machineId, long sequence) {}
}
```

## API Gateway Pattern

### The Problem

In a microservice system, clients would otherwise need to:
- Know the location of every service
- Handle authentication for each service
- Implement their own retry logic, load balancing, etc.

### Gateway Responsibilities

```
                    │                                   │

                    │  │  Cross-cutting concerns:    │  │

                    │  │           /api/orders/* →   │  │

  ┌─────▼──────┐       ┌─────▼──────┐       ┌─────▼──────┐
```

### Gateway Responsibilities (Detailed)

| Responsibility | Description | Implementation |
|---|---|---|
| **Routing** | Route requests to appropriate services based on path | `Path` predicate, service discovery |
| **Authentication** | Validate JWT tokens, authenticate requests | Global filter (GatewayFilter) |
| **Rate Limiting** | Prevent abuse, ensure fair usage | `RequestRateLimiter` filter |
| **Logging** | Audit trail, request/response logging | Custom GlobalFilter |
| **Aggregation** | Combine responses from multiple services | Custom GatewayFilter |
| **Protocol Translation** | REST → gRPC, HTTP → WebSocket | Custom filter/route |
| **Circuit Breaking** | Protect services from cascading failures | `CircuitBreaker` filter |
| **CORS** | Cross-origin resource sharing | `CorsGlobalConfiguration` |
| **Caching** | Cache responses for idempotent GET requests | Custom filter + Redis |
| **Load Shedding** | Reject requests when overloaded | Custom filter + Sentinel |

```java
// Custom Global Filter: Authentication
@Component
public class JwtAuthenticationFilter implements GlobalFilter, Ordered {

    private final JwtTokenProvider tokenProvider;
    private final List<String> publicPaths = List.of(
        "/api/users/login", "/api/users/register", "/api/products"
    );

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getURI().getPath();

        // Skip public paths
        if (publicPaths.stream().anyMatch(path::startsWith)) {
            return chain.filter(exchange);
        }

        // Extract token
        String token = extractToken(exchange.getRequest());
        if (token == null || !tokenProvider.validateToken(token)) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }

        // Parse user info and pass to downstream service
        Claims claims = tokenProvider.getClaims(token);
        exchange.getRequest().mutate()
            .header("X-User-Id", claims.getSubject())
            .header("X-User-Role", claims.get("role", String.class));

        return chain.filter(exchange);
    }

    @Override
    public int getOrder() {
        return -100; // High priority
    }

    private String extractToken(ServerHttpRequest request) {
        String bearer = request.getHeaders().getFirst("Authorization");
        if (bearer != null && bearer.startsWith("Bearer ")) {
            return bearer.substring(7);
        }
        return null;
    }
}

@Component
public class RequestLoggingFilter implements GlobalFilter, Ordered {

    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {

            ServerHttpResponse response = exchange.getResponse();
            log.info("[{}] <-- {} {} in {}ms",
                requestId, response.getStatusCode(), request.getURI(), duration);
        }));
    }

    @Override
    public int getOrder() {
        return -50;
    }
```

## Circuit Breaker Pattern

### The Problem

When Service A calls Service B, and Service B becomes slow or fails:
1. Service A's threads become blocked waiting for Service B
2. Service A's thread pool is exhausted
3. Service A fails too — **cascading failure**
4. Every service calling Service A also fails — **avalanche**

### Circuit Breaker States

```
                    ┌──────────┐
       ┌────────────│  CLOSED  │◄────────────┐
       │            │ (Normal) │              │
       │            └─────┬────┘              │
       │                  │                    │
       │         Failures > threshold          │
       │                  │                    │
       │            ┌─────▼────┐     Timeout   │
       │            │   OPEN   │───────────────┘
       │            │(Rejecting)│
       │            └─────┬────┘
       │                  │
       │         After timeout
       │                  │
       │            ┌─────▼────┐
       └────────────│ HALF-OPEN│
                    │ (Trial)  │
                    └──────────┘
```

**State Machine:**
- **CLOSED**: Normal operation. Requests pass through. Failures are counted.
- **OPEN**: Failures exceed threshold. Requests are rejected immediately (fail-fast). A timer starts.
- **HALF-OPEN**: After the timeout, allow a limited number of trial requests. If they succeed → CLOSED. If they fail → OPEN again.

## Bulkhead Pattern

### The Problem

Without bulkheads, a resource leak in one part of the system can starve the entire system. Example: a slow downstream service exhausts the HTTP connection pool, blocking requests to all services.

### Bulkhead Implementation

```
Without Bulkhead:
┌──────────────────────────────────────────┐
│         Application Thread Pool          │
│  [T1][T2][T3][T4][T5][T6][T7][T8][T9]  │
│         │      │                         │
│         │      └────────────────┐        │
│         ▼                       ▼        │
│  ┌──────────┐           ┌──────────┐    │
│  │ Service A│           │ Service B│    │
│  │ (fast)   │           │ (slow)   │    │
│  └──────────┘           └──────────┘    │
│                                          │
│  Problem: Service B exhaustion blocks   │
│  threads needed for Service A calls     │
└──────────────────────────────────────────┘

With Bulkhead:
┌──────────────────────────────────────────┐
│    Fixed Thread Pool A     Fixed TP B    │
│  [A1][A2][A3][A4][A5]   [B1][B2][B3]   │
│         │                      │         │
│         ▼                      ▼         │
│  ┌──────────┐           ┌──────────┐    │
│  │ Service A│           │ Service B│    │
│  │ (fast)   │           │ (slow)   │    │
│  └──────────┘           └──────────┘    │
│                                          │
│  Benefit: Service B can exhaust its     │
│  3 threads, but Service A's 5 threads   │
│  remain available for other work        │
└──────────────────────────────────────────┘
```

### Implementation with Resilience4j

```yaml
        base-config: default

  thread-pool-bulkhead:
    configs:

        max-thread-pool-size: 10
```

## DDD for Microservice Modeling

### Why DDD for Microservices?

Domain-Driven Design provides the analytical tools to identify service boundaries correctly. Without DDD, services are often split by technical concerns (UI + logic + data), which creates the worst kind of distributed monolith.

### Strategic DDD Patterns

### Key DDD Building Blocks

| Building Block | Description | Microservice Mapping |
|---|---|---|
| **Entity** | Object with identity (ID) that changes over time | Core domain objects within a service |
| **Value Object** | Immutable object defined by attributes | Often used across services (Address, Money) |
| **Aggregate** | Cluster of entities with a root (consistency boundary) | Transaction boundary — usually maps to a service |
| **Repository** | Domain-oriented persistence interface | Data access within the service |
| **Domain Event** | Something that happened in the domain | Inter-service communication (events) |
| **Service** (domain) | Stateless operation that doesn't fit an entity | Can be a microservice or a capability within one |
| **Factory** | Creating complex aggregates | Constructor or factory method |

```java
// A DDD Aggregate: Order is the root
@Entity
@Table(name = "orders")
public class Order {                    // Aggregate Root

    @Id
    private OrderId id;                 // Value Object as ID

    @Enumerated(EnumType.STRING)
    private OrderStatus status;

    @Embedded
    private Money totalAmount;           // Value Object

    @OneToMany(cascade = ALL, orphanRemoval = true)
    @JoinColumn(name = "order_id")
    private List<OrderLine> items;       // Entities within the aggregate

    // Only created via factory method (not @NoArgsConstructor)
    protected Order() {} // JPA only

    public Order(OrderId id, List<OrderLine> items, Money totalAmount) {
        this.id = id;
        this.items = items;
        this.totalAmount = totalAmount;
        this.status = OrderStatus.PENDING;
        // Domain event — captured and published later
        this.addDomainEvent(new OrderCreatedEvent(id, items, totalAmount));
    }

    // Business behavior — not just getters and setters
    public void markAsPaid(PaymentId paymentId) {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException("Cannot pay order in state: " + status);
        }
        this.status = OrderStatus.PAID;
        this.paymentId = paymentId;
        addDomainEvent(new OrderPaidEvent(id, paymentId));
    }

    public void cancel(String reason) {
        if (status == OrderStatus.SHIPPED || status == OrderStatus.DELIVERED) {
            throw new IllegalStateException("Cannot cancel shipped/delivered order");
        }
        this.status = OrderStatus.CANCELLED;
        this.cancelReason = reason;
        addDomainEvent(new OrderCancelledEvent(id, reason));
    }
}

// Value Object
@Embeddable
public record Money(BigDecimal amount, String currency) {

    public Money {
        if (amount.compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException("Amount must be non-negative");
        }
        if (currency == null || currency.isBlank()) {
            currency = "CNY";
        }
    }

    public Money add(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("Currency mismatch");
        }
        return new Money(this.amount.add(other.amount), this.currency);
```

### Context Mapping Patterns

| Pattern | Description | When to Use |
|---|---|---|
| **Partnership** | Two teams collaborate on integration | Strong dependency between services |
| **Shared Kernel** | Share a subset of the domain model | Tightly coupled, but managed |
| **Customer-Supplier** | Upstream supplies, downstream uses | Typical API provider/consumer |
| **Conformist** | Downstream conforms to upstream model | No leverage to negotiate |
| **Anti-Corruption Layer** | Translate between models | Legacy integration, different schemas |
| **Open Host Service** | Protocol that many clients use | Public APIs |
| **Published Language** | Well-documented interchange format | Event schemas (Avro, Protobuf) |

## Interview Questions

### Basic

1. **"What is the CAP theorem? Give examples of CP and AP systems."**
   - CAP: Consistency, Availability, Partition Tolerance — pick 2
   - CP: Zookeeper, etcd, HBase
   - AP: Cassandra, DynamoDB, Eureka
   - P is non-negotiable in distributed systems

2. **"How is microservices different from SOA?"**
   - SOA: Shared schema, ESB middleware, heavy protocols (SOAP)
   - Microservices: Decentralized data, smart endpoints/dumb pipes, lightweight protocols (REST/gRPC), DevOps culture

3. **"What is the strangler fig pattern?"**
   - Incrementally replace monolith functions with microservices
   - Route new requests to new services via a gateway/proxy
   - Remove old code once fully migrated

### Intermediate

4. **"Explain the Saga pattern. When would you use choreography vs orchestration?"**
   - Saga: Choreography = decentralized, services listen/publish events
   - Orchestration = centralized coordinator manages flow
   - Use choreography for simple, linear flows; orchestration for complex branching flows

5. **"How do you ensure idempotency in a distributed payment system?"**
   - Unique idempotency key (client-generated)
   - Database unique constraint on business key
   - Token mechanism (pre-generated, atomically consumed)
   - State machine pattern

6. **"Compare Snowflake, UUID, and database sequence for distributed ID generation."**
   - Snowflake: 64-bit, time-sorted, high performance, needs clock sync
   - UUID: 128-bit, simple, but not index-friendly (except v7)
   - DB sequence: Simple, low performance, single point of failure

### Advanced

7. **"How would you migrate a large monolith to microservices without stopping development?"**
   - Strangler Fig pattern: identify seams, extract one capability at a time
   - Feature flags in the monolith to route to new service
   - Database strangler: shared database initially, extract as services mature
   - Parallel run: run both old and new, compare results

8. **"Design a resilient inter-service communication strategy for a high-traffic e-commerce platform."**
   - Hybrid: sync for reads (with caching), async for writes (event-driven)
   - Gateway-level: rate limiting, circuit breaking, authentication
   - Service-level: bulkheads, retries with exponential backoff, fallbacks
   - Observability: distributed tracing, structured logging, RED metrics

9. **"How does TCC distributed transaction work? What are the failure scenarios?"**
   - Try: freeze resources
   - Confirm: commit (when all Try succeed)
   - Cancel: release (when any Try fails)
   - Failures: network split during confirm/cancel → need idempotency and recovery

10. **"How do you model service boundaries using DDD?"**
    - Identify bounded contexts using event storming
    - Core domain = competitive advantage (build custom)
    - Supporting = needed but not core (build or outsource)
    - Generic = commodity (use open source or SaaS)
    - Aggregate = transactional consistency boundary
    - Service = bounded context or aggregate boundary

## Summary

| Topic | Key Takeaway |
|---|---|
| **Monolith** | Good for small teams, becomes painful at scale |
| **Service decomposition** | By business capability (DDD bounded context) |
| **Communication** | REST/gRPC for sync, MQ/events for async |
| **CAP/BASE** | Choose AP for availability, CP for consistency |
| **Service discovery** | Nacos, Eureka (AP), Consul (CP) |
| **Config management** | Centralized, dynamic, versioned, encrypted |
| **Distributed transactions** | Saga > TCC > 2PC for most cases |
| **Idempotency** | Every write operation must be idempotent |
| **API Gateway** | Single entry point for cross-cutting concerns |
| **Circuit breaker** | Fail fast to prevent cascading failures |
| **Bulkhead** | Resource isolation for fault containment |
| **Observability** | Logging + Metrics + Tracing |
| **DDD** | Strategic design for service boundaries |
