# 第一章：分布式系统概述

### 1.1 什么是分布式系统
- **定义**：由多个自治计算机通过网络互联组成的系统，对用户呈现为单一整体
- **为什么需要分布式系统**：单机性能极限（CPU/内存/磁盘）、单点故障、地理分布需求
- **分布式系统的挑战**：网络不可靠（丢包/延迟/分区）、时钟不同步、节点故障、数据一致性
- **八个谬误（Fallacies of Distributed Computing）**：
  1. 网络是可靠的
  2. 延迟为零
  3. 带宽是无限的
  4. 网络是安全的
  5. 拓扑不会变化
  6. 只有一个管理员
  7. 传输成本为零
  8. 网络是同构的

### 1.2 分布式系统的衡量指标
- **可扩展性（Scalability）**：水平扩展(加机器) vs 垂直扩展(加配置)
- **可用性（Availability）**：系统正常运行的时间比例——99.9%(3个9，年停机8.76h) → 99.999%(5个9，年停机5.26min)
- **可靠性（Reliability）**：系统在给定时间内无故障运行的能力
- **性能（Performance）**：吞吐量(Throughput, QPS/TPS) + 延迟(Latency, P50/P99/P999)
- **可维护性（Maintainability）**：便于运维、修复、迭代

### 1.3 分布式系统分类
- **分布式计算**：MapReduce、Spark——数据分片并行计算
- **分布式存储**：HDFS、Ceph——数据分散存储多节点
- **分布式数据库**：TiDB、CockroachDB——分布式事务+SQL
- **分布式缓存**：Redis Cluster、Memcached——内存数据的分布式方案
- **分布式协调**：ZooKeeper、etcd——配置管理/选主/分布式锁
- **分布式消息**：Kafka、RocketMQ——消息的持久化+分布式传递

# 第二章：CAP 理论与 BASE

### 2.1 CAP 定理（⭐ 核心）
- **C（Consistency，一致性）**：所有节点在同一时刻看到相同的数据——等同于访问单一最新副本
- **A（Availability，可用性）**：每个请求都能收到非错误的响应（但不保证是最新数据）
- **P（Partition Tolerance，分区容错性）**：即使网络分区（部分节点之间无法通信），系统仍能正常运作
- **CAP 证明（Gilbert & Lynch, 2002）**：异步网络模型中，三者最多同时满足两个
- **关键理解**：P 在网络环境中无法避免（交换机故障、网线断开等），实际选择是 CP 还是 AP
  - CP：发生分区时牺牲可用性保障一致性——ZooKeeper（Leader宕机期间不可写）
  - AP：发生分区时牺牲一致性保障可用性——Eureka（各节点可能返回不同数据）

### 2.2 BASE 理论
- **Basically Available（基本可用）**：允许损失部分可用性（响应时间变长/功能降级）
- **Soft State（软状态）**：允许系统存在中间状态，即数据副本间可短暂不一致
- **Eventually Consistent（最终一致性）**：经过一段时间后，所有副本最终达到一致
- **BASE 是 CAP 中 AP 方案的延伸**：牺牲强一致性换取可用性

### 2.3 一致性模型详解
- **强一致性（Linearizability）**：所有操作看起来像在单一副本上按某种全局顺序执行——CAP中的C
- **顺序一致性（Sequential Consistency）**：每个进程的操作按程序顺序执行，但不同进程间可交错
- **因果一致性（Causal Consistency）**：有因果关系的操作在所有节点上按相同顺序，无因果的可不同序
- **最终一致性（Eventual Consistency）**：如果不继续更新，最终所有副本会一致——DNS是最经典的例子
- **读写一致性（Read-Your-Writes）**：用户总能看到自己写入的数据
- **单调读一致性（Monotonic Reads）**：读到的数据不会"倒退"（不会看到比之前更旧的版本）

# 第三章：共识算法

### 3.1 共识问题定义
- **共识（Consensus）**：多个节点就某个值达成一致
- **三要素**：
  1. **终止性（Termination）**：每个正确节点最终都会做出决定
  2. **一致性（Agreement）**：所有正确节点决定的值相同
  3. **有效性（Validity）**：决定的值必须是某个节点提出的
- **FLP 不可能性（Fisher-Lynch-Paterson, 1985）**：在异步模型中，即使只有一个节点故障，也不存在确定性的共识算法——但实践中通过随机超时（部分同步模型）可以达成共识

### 3.2 Paxos
- **角色**：Proposer（提案者）、Acceptor（接受者）、Learner（学习者）
- **Basic Paxos 两阶段**：
  - **Phase 1（Prepare）**：Proposer 发送 Prepare(n) → Acceptor 承诺不接受 < n 的提案，并返回已接受的最大提案
  - **Phase 2（Accept）**：Proposer 根据 Phase 1 回复选择值，发送 Accept(n, value) → 多数派接受则达成共识
- **Multi-Paxos**：为多个值达成共识——选出一个 Leader，只有 Leader 发起提案，跳过 Phase 1
- **Paxos 的难点**：理论精巧但难理解、工程实现复杂、角落案例多

### 3.3 Raft（⭐ 主要学习对象）
- **设计哲学**：可理解性优先——将共识分解为三个相对独立的子问题
- **三个子问题**：
  1. **Leader 选举（Leader Election）**：每个 Server 有三种状态（Leader/Follower/Candidate），term 递增
     - Follower 超时未收到心跳 → 转为 Candidate → 发起选举 → 获得多数票即成为 Leader
     - 随机超时（150-300ms）防止多个 Candidate 同时竞选
  2. **日志复制（Log Replication）**：Leader 接收客户端请求 → 追加到本地日志 → 并行发给 Followers → 多数确认即提交 → 应用到状态机
  3. **安全性（Safety）**：选举限制（Candidate 的日志必须至少和多数节点一样新）+ 只提交当前 term 的日志
- **Raft vs Paxos**：Raft 更易理解、更易实现，etcd/Consul/TiKV 都基于 Raft

### 3.4 其他共识算法
- **ZAB（ZooKeeper Atomic Broadcast）**：ZooKeeper 专用——Leader 选举 + 原子广播 + 崩溃恢复
- **PBFT（实用拜占庭容错）**：可容忍不超过 1/3 的恶意节点——联盟链（Hyperledger Fabric）使用
- **PoW/PoS**：区块链的共识——算力竞赛（PoW）或权益质押（PoS），最终一致性而非强一致性

# 第四章：分布式事务

### 4.1 分布式事务的挑战
- **单机事务（ACID）**：A（原子性）、C（一致性）、I（隔离性）、D（持久性）
- **分布式场景下的问题**：数据分散在多个节点，如何保证跨节点的原子性？

### 4.2 刚性事务（强一致性方案）
- **2PC（两阶段提交）**：
  - **Phase 1（准备）**：协调者询问所有参与者是否准备好提交 → 参与者执行事务并锁资源 → 回复 yes/no
  - **Phase 2（提交）**：全部 yes → 协调者发 commit；任一个 no → 协调者发 rollback
  - 问题：同步阻塞（Phase 1到Phase 2之间锁资源）、单点故障（协调者宕机参与者也锁着）、数据不一致（部分 commit 部分未收到）
- **3PC（三阶段提交）**：2PC + 引入超时机制 + 增加预提交阶段（CanCommit → PreCommit → DoCommit），降低阻塞概率但增加消息轮次
- **XA 协议**：X/Open 的分布式事务标准——数据库实现 2PC 的接口规范（MySQL 的 XA 事务）

### 4.3 柔性事务（BASE 方案）
- **TCC（Try-Confirm-Cancel）**：
  - **Try**：预留资源/检查（如冻结库存）
  - **Confirm**：确认执行（如扣减库存）
  - **Cancel**：取消回滚（如解冻库存）
  - 优缺点：隔离性强、无锁——但业务侵入大（每接口需实现正向+反向操作）
- **SAGA**：
  - 长事务拆分为多个本地事务，每个本地事务有对应的补偿操作
  - 编排（Choreography）：事件驱动，每个服务自行决定下一步——松耦合但难以追踪
  - 协同（Orchestration）：中心化的 Saga 协调器——易追踪但单点
- **本地消息表 + 最大努力通知**：
  - 本地事务中同时写入业务数据和消息表 → 定时任务扫消息表发送 → 重试直到成功
  - RocketMQ 事务消息的底层原理（半消息 + 回查）

### 4.4 分布式事务框架
- **Seata（阿里开源）**：
  - AT 模式：自动补偿——拦截 SQL → 生成前镜像和后镜像（Undo Log）→ Commit 删 Undo Log / Rollback 回放 Undo Log
  - TCC 模式：手动实现 Try-Confirm-Cancel
  - SAGA 模式：长事务编排

# 第五章：数据分片与副本

### 5.1 数据分片（Sharding / Partitioning）
- **为什么要分片**：单库单表存储上限(约2000万行后性能下降) + 写入瓶颈
- **分片策略**：
  - **范围分片**：按 key 范围分配（A-G→Shard1, H-N→Shard2...）——易扩容但热点问题
  - **哈希分片**：`hash(key) % N`——均匀但扩容时需要大量数据迁移
  - **一致性哈希**：哈希环 + 虚拟节点——增删节点时只影响相邻节点 → 最少数据迁移
  - **目录分片**：维护 key→分片 的映射表（更灵活但需要额外查一次）
- **二级索引的分片**：
  - 本地索引（Document-Based）：每个分片只索引自己分片的数据 —— 查询需 scatter-gather
  - 全局索引（Term-Based）：单独维护一个跨分片的索引表

### 5.2 副本策略
- **主从复制（Leader-Follower / Master-Slave）**：
  - 写主读从：线性扩展读能力——MySQL 经典方案
  - 同步复制 vs 异步复制 vs 半同步：性能与一致性的权衡
- **多主复制（Multi-Leader）**：
  - 多数据中心每中心一主，本地写入低延迟
  - 挑战：写冲突必须解决——LWW（Last Write Wins）/ CRDT
- **无主复制（Leaderless）**：
  - Dynamo 风格（Cassandra/Riak）：写多个副本 + 读时修复（Read Repair）+ 反熵（Anti-Entropy）
  - 仲裁读写：W + R > N —— 写W个副本 + 读R个副本，保证至少交叠一个最新副本

### 5.3 再平衡（Rebalancing）
- **何时再平衡**：新增节点 / 节点故障 / 数据倾斜
- **策略**：固定分片数（分片数 >> 节点数，新节点时迁移几个分片即可）vs 动态分片

# 第六章：分布式一致性协议

### 6.1 全序广播（Total Order Broadcast）
- **原子广播（Atomic Broadcast）**：所有节点以相同顺序接收相同消息
- **等价关系**：共识 ↔ 全序广播 + 成员关系管理

### 6.2 共识在工业界的实现
- **ZooKeeper（ZAB）**：顺序一致性、CP 系统、会话机制、临时节点
- **etcd（Raft）**：强一致性 KV 存储、Watch 机制、MVCC + 多版本
- **Consul（Raft）**：服务发现 + 健康检查 + KV存储（一致性模型可配置）

### 6.3 分布式锁
- **基于 ZooKeeper**：临时顺序节点 + Watch 前驱——释放锁自然释放（Session 断开自动删除）
- **基于 Redis**：`SET key value NX EX 30` + Lua 脚本安全释放（Redlock 算法争议）
- **基于 etcd**：Lease 机制 + 事务 CAS

# 第七章：分布式系统设计模式

### 7.1 通信模式
- **同步 vs 异步**：请求-响应（同步）vs 消息传递（异步）
- **RPC vs 消息队列**：紧耦合低延迟 vs 松耦合削峰填谷

### 7.2 常见设计模式
- **Ambassador（大使/Sidecar）**：代理容器与应用容器共享 Pod——Service Mesh（Envoy/Istio）
- **CQRS（命令查询职责分离）**：Command 写模型 + Query 读模型分离——读写模型不同，分别优化
- **Event Sourcing（事件溯源）**：不存储当前状态，存储所有状态变更事件——可审计回放
- **Circuit Breaker（断路器）**：检测下游故障 → 打开断路器快速失败 → 半开后试探 → 恢复正常——Hystrix/Sentinel
- **Bulkhead（舱壁隔离）**：不同服务用不同线程池，一个慢了不影响另一个
- **Backpressure（背压）**：下游处理不过来时通知上游减速——Reactive Streams

# 第八章：分布式系统实战

### 8.1 故障检测
- **心跳机制**：定期发送心跳包，超时未收到即判定故障
- **Phi-Accrual Failure Detector**：基于心跳间隔的统计模型——Cassandra 采用
- **Gossip 协议**：每个节点随机选邻居同步状态——大规模集群的最终一致性成员管理

### 8.2 时间与顺序
- **物理时钟**：NTP 同步，但仍有漂移——不能依赖墙钟判断事件顺序
- **逻辑时钟（Lamport Timestamp）**：每个进程维护计数器，发生事件递增——定义了 happen-before 偏序
- **向量时钟（Vector Clock）**：每个进程维护所有进程的计数器向量——可判断并发关系
- **TrueTime（Google Spanner）**：原子钟 + GPS 提供全局有界不确定时间——实现外部一致性

### 8.3 分布式 ID 生成
- **UUID**：128位，标准但随机——无序，数据库索引不友好
- **Snowflake（雪花算法）**：1b保留 + 41b时间戳 + 10b机器ID + 12b序列号——趋势递增 + 高性能
- **号段模式（美团 Leaf）**：每次从 DB 取一批 ID 缓存在本地——兼顾性能与灵活
- **Redis 自增**：`INCR` 原子操作——简单但有单点风险
