## 1. 为什么需要消息队列

| 场景 | 无 MQ | 有 MQ |
|------|-------|------|
| **削峰填谷** | 流量尖峰直接压垮数据库 | MQ 缓冲，消费者匀速处理 |
| **异步解耦** | 服务间直接 RPC 调用，一个慢全链路慢 | 生产者发消息即返回，消费者异步处理 |
| **系统解耦** | A 服务需知道 B、C、D 的地址 | A 只发消息，B/C/D 各自订阅 |

```
同步调用（紧耦合）：
  订单 → 库存 → 物流 → 通知

异步解耦（松耦合）：
  订单 → [MQ] → 库存消费者
              → 物流消费者
              → 通知消费者
```

## 2. Kafka 核心架构

### 2.1 架构模型

```
Broker 集群
┌─────────────────────────────────────────────┐
│ Broker-1          Broker-2          Broker-3 │
│ ┌───────────┐    ┌───────────┐    ┌───────────┐ │
│ │ Partition 0 │    │ Partition 1 │    │ Partition 2 │ │ ← Topic 分布
│ │ (Leader)   │    │ (Leader)   │    │ (Leader)   │ │
│ └───────────┘    └───────────┘    └───────────┘ │
│ Partition 1(R)   Partition 2(R)   Partition 0(R)│ ← 副本
└─────────────────────────────────────────────┘
        ↑ 生产              ↓ 消费
   Producer            Consumer Group
```

### 2.2 核心概念

| 概念 | 说明 | 类比 |
|------|------|------|
| **Topic** | 消息的逻辑分类 | 数据库的表 |
| **Partition** | Topic 的物理分片，有序、可并行 | 表的分区 |
| **Segment** | Partition 的物理文件，顺序写磁盘 | — |
| **Consumer Group** | 消费者组，组内 Partition 独占 | — |
| **ISR** | In-Sync Replicas，与 Leader 同步的副本集合 | — |
| **HW** | High Watermark，消费者可见的最高偏移量 | — |

### 2.3 为什么 Kafka 这么快

```
1. 顺序写磁盘 → 比随机写快 1000 倍（Page Cache + 批量刷盘）
2. 零拷贝（sendfile）→ Producer → Broker → Consumer 无需 CPU 拷贝
3. 批量压缩 → Producer 批量发 + Broker 批量写
4. 分区并行 → 多 Partition 多消费者并行处理
5. 索引文件（稀疏索引）→ 快速定位消息位置
```

### 2.4 消费者偏移量管理

```text
Kafka 0.9 前：offset 存 ZK
Kafka 0.9+ ：offset 存内部 Topic __consumer_offsets
```

```java
// 手动提交偏移量（至少一次语义）
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
consumer.commitSync();   // 同步提交
consumer.commitAsync();  // 异步提交（推荐）
```

## 3. RocketMQ 核心架构

### 3.1 四大组件

```
Producer → NameServer(无状态) → Broker(Master + Slave)
                                  ↓
                               Consumer
```

| 组件 | 职责 |
|------|------|
| **NameServer** | 路由注册（无状态，类似 DNS），Broker 上报 Topic 路由信息 |
| **Broker** | 消息存储+投递，Master 写 + Slave 读 |
| **Producer** | 消息生产者 |
| **Consumer** | 消息消费者（Pull 模式，长轮询） |

### 3.2 特色功能

| 功能 | 说明 |
|------|------|
| **事务消息** | 半消息 + 回查，保证本地事务与消息发送原子性 |
| **延迟消息** | 18 个延迟级别（1s~2h），定时投递 |
| **顺序消息** | 同一业务 ID 的消息发到同一队列，单线程消费 |
| **消息过滤** | Tag + SQL 表达式过滤 |

### 3.3 Kafka vs RocketMQ

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| 定位 | 大数据流处理 | 业务消息中间件 |
| 事务消息 | ❌ 不支持（较新版本有） | ⭐ 原生支持 |
| 延迟消息 | ❌ 需外部实现 | ⭐ 内置 18 级 |
| 顺序消息 | Partition 内有序 | ⭐ 全局/局部有序 |
| 吞吐量 | ⭐⭐⭐ 极高 | ⭐⭐ 高 |
| 生态 | Kafka Streams/Connect | Spring Cloud Stream |

## 4. RabbitMQ 核心架构

### 4.1 AMQP 模型

```
Producer → Exchange → (Binding) → Queue → Consumer
              │
        四种路由类型：
        ├── Direct   — 精确匹配 Routing Key
        ├── Topic    — 模糊匹配 Routing Key（* 匹配一个词，# 匹配零或多）
        ├── Fanout   — 广播到所有绑定 Queue
        └── Headers  — 按消息 Header 匹配
```

### 4.2 适用场景

| 场景 | 方案 |
|------|------|
| 复杂路由 | Exchange → 多个 Queue，灵活分发 |
| RPC 调用 | 请求队列 + 临时回复队列 + CorrelationId |
| 死信队列 | 失败/过期消息 → Dead Letter Exchange → 人工处理 |
| 延迟队列 | TTL + 死信队列组合 |

## 5. 消息可靠性保障

### 5.1 消息丢失的三道防线

```
Producer → Broker → Consumer
  ①          ②         ③

① 生产者丢失：
   - Kafka: acks=all + retries
   - RocketMQ: 同步发送 + 重试
   - RabbitMQ: Publisher Confirm

② Broker 丢失：
   - Kafka: replication.factor ≥ 3 + min.insync.replicas ≥ 2
   - RocketMQ: 同步刷盘 + 主从同步复制
   - RabbitMQ: 持久化 Queue + 持久化消息

③ 消费者丢失：
   - Kafka: 手动提交 offset（处理完再提交）
   - RocketMQ: 消费成功返 CONSUME_SUCCESS
   - RabbitMQ: 手动 ACK
```

### 5.2 消息不重复（幂等）

| 方案 | 说明 |
|------|------|
| **数据库唯一键** | INSERT 去重，最可靠 |
| **Redis Set** | `SADD` 判断，适合高并发 |
| **业务状态机** | 订单状态（PENDING→PAID），已 PAID 跳过 |
| **消息 ID 去重表** | 消费前查去重表，消费后写入 |

## 6. Event Sourcing 与 CQRS

### 6.1 Event Sourcing（事件溯源）

```
传统 CRUD：
  UPDATE order SET status='PAID' WHERE id=1
  → 只存当前状态，历史丢失

Event Sourcing：
  INSERT INTO events (order_id, type, data) VALUES
    (1, 'OrderCreated', '{"amount":100}'),
    (1, 'OrderPaid', '{"method":"alipay"}'),
    (1, 'OrderShipped', '{"tracking":"SF123"}')
  → 所有状态变更作为事件存储，可审计回放
```

### 6.2 CQRS（命令查询职责分离）

```
Command Side（写）              Query Side（读）
   ↓                               ↓
 严格校验 + 业务逻辑             优化查询 + 去规范化
   ↓                               ↓
 事件写入 Event Store            从读模型查询
   ↓                               ↑
   └─── 事件发布 ───→ 读模型更新 ────┘

两个独立的数据模型：
  Write DB：规范化、事务、强一致性（MySQL）
  Read DB：去规范化、优化查询、最终一致性（Elasticsearch/Redis）
```

## 7. 主流 MQ 对比与选型

| 维度 | Kafka | RocketMQ | RabbitMQ |
|------|-------|----------|----------|
| 吞吐量 | ⭐⭐⭐ 百万级 | ⭐⭐⭐ 十万级 | ⭐⭐ 万级 |
| 延迟 | ms 级 | ms 级 | μs 级 |
| 事务消息 | 较新版本支持 | ⭐ 原生 | ❌ |
| 延迟消息 | ❌ | ⭐ 原生 | 插件 |
| 顺序消息 | Partition 内 | ⭐ 全局限 | ❌ |
| 路由灵活度 | ⭐ | ⭐⭐ | ⭐⭐⭐ |
| 协议 | 自定义 TCP | 自定义 TCP | AMQP 标准 |
| 社区生态 | ⭐⭐⭐ 极丰富 | ⭐⭐ 阿里 | ⭐⭐⭐ 成熟 |
| **推荐场景** | 大数据/日志/流 | 业务消息/电商 | 复杂路由 |

> 🎯 **选型口诀**：大数据+流处理选 Kafka；电商业务消息选 RocketMQ；复杂路由+小规模选 RabbitMQ。三者可共存，Kafka 做数据管道、RocketMQ 做业务消息是常见组合。
