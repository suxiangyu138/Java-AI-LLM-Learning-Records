## 2. 单体架构 vs 微服务架构

### 2.1 架构演进路线

```
单体架构 → 垂直拆分 → SOA → 微服务 → Service Mesh → Serverless
   ↓           ↓        ↓       ↓           ↓            ↓
 一个War   按业务拆     ESB   去中心化    Sidecar     函数级
 一个DB   多个War    企业总线  独立部署   基础设施下沉   按需执行
```

### 2.2 单体 vs 微服务全面对比

| 维度 | 单体架构 | 微服务架构 |
|------|----------|-----------|
| **代码结构** | 单一代码库，所有功能在一个工程 | 按业务拆分为多个独立服务 |
| **部署** | 整体打包部署，牵一发动全身 | 每个服务独立部署，互不影响 |
| **数据库** | 通常共享一个数据库 | 每个服务有自己的数据库（数据私有） |
| **扩展性** | 整体扩展，浪费资源 | 按需扩展热点服务 |
| **技术栈** | 单一技术栈 | 每个服务可选用不同技术栈 |
| **团队组织** | 按职能划分（前端/后端/DBA） | 按业务领域划分（跨职能小队） |
| **通信** | 进程内方法调用 | RPC/HTTP/MQ 进程间通信 |
| **复杂度** | 代码量大但架构简单 | 架构复杂，需处理分布式问题 |
| **适用场景** | 小型项目、早期MVP快速验证 | 中大型项目、多团队协作、高并发场景 |

> 🎯 **核心原则**：不要为了微服务而微服务！单体先行，业务复杂度达到一定程度后再演进到微服务。

### 2.3 微服务九大核心特征

1. **组件化**：每个服务是独立的组件，可独立替换和升级
2. **按业务组织**：围绕业务能力构建，而非技术层
3. **产品而非项目**：团队对服务的整个生命周期负责
4. **智能端点，哑管道**：RESTful HTTP 或 轻量级消息
5. **去中心化治理**：每个服务选择最适合的技术栈
6. **去中心化数据管理**：每个服务有独立的数据库
7. **基础设施自动化**：CI/CD、自动化测试、容器编排
8. **容错设计**：熔断、降级、限流、重试
9. **演进式设计**：允许服务独立演化

## 3. 微服务拆分原则与DDD基础

### 3.1 拆分原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **单一职责** | 一个服务只做一件事 | 订单服务同时管理物流 |
| **高内聚低耦合** | 服务内紧密关联、服务间松耦合 | 频繁的分布式事务 |
| **数据私有** | 每个服务有自己的数据库 | 多个服务共享一张表 |
| **业务边界对齐** | 按DDD限界上下文拆分 | 按技术层拆分（如"DAO服务"） |
| **独立部署** | 一个服务的变更不影响其他 | 修改A服务必须同时部署B |
| **团队对齐** | 一个团队负责1-2个微服务 | 一个团队负责10个微服务 |

### 3.2 DDD领域驱动设计核心概念

```
战略设计（宏观）
├── 领域 Domain：整个业务范围
├── 子域 Subdomain
│   ├── 核心域 Core：核心竞争力（如电商的订单域）
│   ├── 支撑域 Supporting：辅助核心域（如仓储域）
│   └── 通用域 Generic：通用的（如认证/通知）
├── 限界上下文 Bounded Context：服务拆分的边界依据
└── 上下文映射 Context Map：限界上下文之间的关系

战术设计（微观，服务内部）
├── 实体 Entity：有唯一标识，可变
├── 值对象 Value Object：无唯一标识，不可变
├── 聚合 Aggregate：一组关联对象的集合，由聚合根访问
├── 聚合根 Aggregate Root：聚合的入口，保证业务规则
├── 领域服务 Domain Service：无状态的业务逻辑
├── 仓储 Repository：持久化聚合
└── 领域事件 Domain Event：领域中发生的重要事件
```

### 3.3 电商领域拆分示例

```
电商系统
├── 用户服务 (User Service)
│   └── 限界上下文：注册、登录、个人信息、地址管理
├── 商品服务 (Product Service)
│   └── 限界上下文：商品信息、分类、SKU管理、库存
├── 订单服务 (Order Service)
│   └── 限界上下文：购物车、下单、订单状态流转
├── 支付服务 (Payment Service)
│   └── 限界上下文：支付渠道、对账、退款
├── 物流服务 (Logistics Service)
│   └── 限界上下文：发货、物流轨迹、签收
└── 营销服务 (Marketing Service)
    └── 限界上下文：优惠券、促销活动、积分
```

## 4. CAP定理与BASE理论

### 4.1 CAP定理

> 🎯 分布式系统中，**一致性(Consistency)**、**可用性(Availability)**、**分区容错性(Partition Tolerance)** 三者不可同时满足，最多只能同时满足两个。

| 选择 | 说明 | 代表组件 | 适用场景 |
|------|------|----------|----------|
| **CP（一致性+分区容错）** | 发生网络分区时，保证数据一致性，牺牲可用性 | ZooKeeper、Consul、Nacos(CP模式) | 对数据一致性要求极高的场景 |
| **AP（可用性+分区容错）** | 发生网络分区时，保证服务可用，可能数据不一致 | Eureka、Nacos(AP模式) | 对可用性要求极高，可容忍短暂不一致 |
| **CA（一致性+可用性）** | 不存在网络分区时有效 | 传统关系型数据库（单机） | 单机系统（分布式系统中无意义） |

> ⚠️ **关键理解**：P（分区容错性）在分布式系统中是必须保证的（网络分区不可避免），因此 CAP 实际上是 **CP vs AP** 的选择。

### 4.2 Nacos的AP/CP切换

```yaml
# Nacos支持AP和CP模式切换
spring:
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
        # Nacos 默认AP模式，可通过以下方式切换为CP
        # 实际上是通过client端调用时的参数控制的
```

### 4.3 BASE理论（对CAP中AP的补充）

| 概念 | 含义 |
|------|------|
| **B**asically Available 基本可用 | 系统故障时允许损失部分可用性（如响应时间变长、功能降级） |
| **S**oft State 软状态 | 允许系统存在中间状态，数据副本间不需要实时一致 |
| **E**ventually Consistent 最终一致性 | 经过一段时间后，所有数据副本最终达到一致 |

## 5. 微服务通信模式

### 5.1 同步通信 vs 异步通信

| 维度 | 同步通信（HTTP/RPC） | 异步通信（MQ） |
|------|---------------------|--------------|
| **实时性** | ✅ 立即响应 | ⚠️ 延迟处理 |
| **耦合度** | ⚠️ 高（等待响应） | ✅ 低（发送即忘） |
| **可靠性** | ⚠️ 需要处理超时/失败 | ✅ 消息持久化保证 |
| **代表技术** | REST(OpenFeign)、gRPC、Dubbo | RabbitMQ、RocketMQ、Kafka |
| **适用场景** | 查询类操作、强一致性要求 | 事件通知、异步解耦、削峰填谷 |

### 5.2 REST vs RPC对比

| 维度 | REST (OpenFeign) | RPC (Dubbo/gRPC) |
|------|-----------------|-----------------|
| 协议 | HTTP/1.1 或 HTTP/2 | TCP（自定义协议） |
| 数据格式 | JSON/XML（文本） | Protobuf/Hessian（二进制） |
| 性能 | ⚠️ 中等 | ✅ 高（二进制序列化更快） |
| 跨语言 | ✅ 天然支持 | ⚠️ 需要IDL定义 |
| 治理生态 | Spring Cloud全家桶 | Dubbo生态/Service Mesh |
| 学习成本 | ✅ 低 | ⚠️ 中 |

```java
// REST (OpenFeign)
@FeignClient(name = "user-service")
public interface UserClient {
    @GetMapping("/users/{id}")
    User getUser(@PathVariable Long id);
}

// RPC (Dubbo)
@DubboService
public class UserServiceImpl implements UserService {
    @Override
    public User getUser(Long id) { ... }
}
```

## 6. 微服务落地痛点与解决方案全景

| 痛点 | 问题描述 | 解决方案 | 对应技术 |
|------|----------|----------|----------|
| **服务发现** | 服务实例动态变化，如何找到对方？ | 注册中心 | Nacos/Eureka/Consul |
| **配置管理** | 多服务多环境配置如何统一管理？ | 配置中心 | Nacos Config/Apollo |
| **服务调用** | 跨进程调用的复杂性 | 声明式调用+负载均衡 | OpenFeign + LoadBalancer |
| **容错保护** | 服务故障的连锁反应（雪崩） | 熔断/降级/限流 | Sentinel/Resilience4j |
| **网关** | 外部请求如何路由到内部服务？ | API网关 | Spring Cloud Gateway |
| **分布式事务** | 跨服务的数据一致性 | 最终一致性方案 | Seata/RocketMQ事务消息 |
| **链路追踪** | 跨服务调用链如何排查？ | 分布式追踪 | SkyWalking/Zipkin |
| **安全** | 分布式环境下的认证授权 | 统一认证中心 | Spring Security OAuth2/JWT |
| **日志** | 多服务日志如何聚合？ | 日志中心 | ELK（Elasticsearch + Logstash + Kibana） |
| **部署运维** | 多服务的部署和运维复杂度 | 容器化+编排 | Docker + Kubernetes |

## 7. Spring Cloud生态全景

### 7.1 Spring Cloud Netflix vs Spring Cloud Alibaba

| 组件 | Spring Cloud Netflix | Spring Cloud Alibaba | 推荐 |
|------|---------------------|---------------------|------|
| 注册中心 | Eureka（已停维护） | **Nacos** | ✅ Alibaba |
| 配置中心 | Spring Cloud Config | **Nacos Config** | ✅ Alibaba |
| 服务调用 | Feign + Ribbon（停更） | **OpenFeign + LoadBalancer** | ✅ Alibaba |
| 熔断限流 | Hystrix（已停维护） | **Sentinel** | ✅ Alibaba |
| 网关 | Zuul1（阻塞）/Zuul2 | **Spring Cloud Gateway** | ✅ Spring |
| 分布式事务 | — | **Seata** | ✅ Alibaba |
| 分布式锁 | — | **Redisson** | ✅ Redisson |
| 链路追踪 | Spring Cloud Sleuth | **SkyWalking** | ✅ Apache |

> 🎯 **结论**：企业主流使用 Spring Cloud Alibaba 组件，Netflix 组件仅做对比了解。

## 8. 高频踩坑与误区

| 序号 | 误区 | 正确认识 |
|------|------|----------|
| 1 | "微服务一定比单体好" | 微服务增加了架构复杂度，小项目用单体更合适 |
| 2 | "拆得越细越好" | 过度拆分导致服务太多、调用链过长、分布式事务频繁 |
| 3 | "微服务一定要用DDD" | DDD是很好的方法论，但不是必须的，按需采用 |
| 4 | "每个服务必须独立数据库" | 初期可以共享数据库，逐步拆分 |
| 5 | "分布式事务很简单" | 分布式事务是微服务最大的难点之一，尽量避免 |

## 13. 精通拓展补充-P2

### 13.1 Service Mesh 概念

Service Mesh 将微服务通信的基础设施（服务发现、负载均衡、熔断、追踪）下沉到 Sidecar 代理（如 Envoy），应用代码无需感知。

| 方案 | 代表 | 特点 |
|------|------|------|
| Spring Cloud | SDK嵌入方式 | 功能丰富，但语言绑定Java |
| Service Mesh | Istio（Envoy代理） | 语言无关，但运维复杂度更高 |

### 13.2 微服务粒度评估指标

- **服务规模**：一般3-5人维护1-2个微服务
- **接口数量**：每个服务对外提供5-15个REST接口
- **独立部署频率**：如果能独立部署，通常是一个合理的微服务
- **数据独立性**：是否有自己的数据库和数据模型

### 13.3 康威定律

> 设计系统的组织，其设计出的系统架构等价于组织间的沟通结构。

**应用**：微服务拆分应与团队结构对齐。如果要拆分为5个微服务，最好有5个相对独立的小团队。
