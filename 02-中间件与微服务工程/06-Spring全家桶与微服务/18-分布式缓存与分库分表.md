## 2. 分层理论讲解

### 2.1 分布式缓存 (Distributed Cache)

#### 2.1.1 缓存穿透 (Cache Penetration)

**问题描述**

> ⚠️ 查询一个**不存在的数据**，缓存层没有，数据库层也没有。每次请求都穿过缓存直达数据库，导致数据库压力陡增。

```
请求 → 查缓存: MISS → 查数据库: 不存在(返回null) → 不写缓存
                              ↑ 下一次同样的请求，再次直达数据库
```

**危害**：恶意攻击者可以利用这个漏洞，构造大量不存在的key进行洪水攻击，直接打垮数据库。

**方案一：布隆过滤器 (Bloom Filter)**

布隆过滤器是一种**概率性**数据结构，可以非常高效地判断"一个元素**一定不在**集合中"或"**可能在**集合中"。

```java
// =============================================
// Guava BloomFilter 实现
// =============================================
import com.google.common.hash.BloomFilter;
import com.google.common.hash.Funnels;
import org.springframework.stereotype.Component;

import javax.annotation.PostConstruct;
import java.nio.charset.Charset;
import java.util.List;

@Component
public class BloomFilterService {

    // 预计数据量
    private static final long EXPECTED_INSERTIONS = 100_0000L;
    // 误判率（越低越准确，但占用空间越大）
    private static final double FPP = 0.01;

    private BloomFilter<String> bloomFilter;

    @PostConstruct
    public void init() {
        bloomFilter = BloomFilter.create(
            Funnels.stringFunnel(Charset.defaultCharset()),
            EXPECTED_INSERTIONS,
            FPP
        );
    }

    /**
     * 初始化布隆过滤器（从数据库加载所有商品ID）
     */
    public void initProductIds(List<Long> productIds) {
        productIds.forEach(id -> bloomFilter.put(String.valueOf(id)));
    }

    /**
     * 判断商品ID是否可能存在
     */
    public boolean mightContain(Long productId) {
        return bloomFilter.mightContain(String.valueOf(productId));
    }

    /**
     * 添加商品ID到布隆过滤器
     */
    public void add(Long productId) {
        bloomFilter.put(String.valueOf(productId));
    }
}
```

```java
// =============================================
// RedisBloom 模块实现
// =============================================
// Redis 4.0+ 提供了布隆过滤器插件 redisbloom
// 安装: redis-cli module load redisbloom.so

// Redis命令示例
// BF.RESERVE productFilter 0.01 1000000  → 创建过滤器（误判率1%，容量100万）
// BF.ADD productFilter 1001               → 添加元素
// BF.EXISTS productFilter 1001            → 检查是否存在 → (integer) 1
// BF.EXISTS productFilter 9999            → (integer) 0

// RedisTemplate 调用 RedisBloom
@Component
public class RedisBloomFilter {

    @Autowired
    private RedisTemplate<String, String> redisTemplate;

    private static final String BLOOM_KEY = "bloom:product";

    public boolean add(String value) {
        return redisTemplate.opsForValue()
            .setBit(BLOOM_KEY, hash(value), true);
    }

    public boolean mightContain(String value) {
        return redisTemplate.opsForValue()
            .getBit(BLOOM_KEY, hash(value));
    }

    private long hash(String value) {
        // 简化的哈希函数（生产环境应使用多个哈希函数）
        return Math.abs(value.hashCode() % 1000000);
    }
}
```

**方案二：缓存空值 (Cache Null Object)**

```java
@Service
public class ProductService {

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private ProductMapper productMapper;

    private static final String CACHE_KEY_PREFIX = "product:";
    // 空值标记
    private static final String NULL_VALUE = "NULL";
    // 空值缓存时间（短于正常缓存，通常30~60秒）
    private static final long NULL_TTL_SECONDS = 30;

    public Product getProduct(Long id) {
        String cacheKey = CACHE_KEY_PREFIX + id;

        // 1. 查缓存
        Object cacheObj = redisTemplate.opsForValue().get(cacheKey);

        if (cacheObj != null) {
            // 命中空值 → 说明数据库不存在，直接返回null
            if (NULL_VALUE.equals(cacheObj)) {
                return null;
            }
            return (Product) cacheObj;
        }

        // 2. 缓存未命中 → 查数据库
        Product product = productMapper.selectById(id);

        // 3. 结果写回缓存
        if (product == null) {
            // 空值也缓存，防止穿透
            redisTemplate.opsForValue()
                .set(cacheKey, NULL_VALUE, NULL_TTL_SECONDS, TimeUnit.SECONDS);
        } else {
            redisTemplate.opsForValue()
                .set(cacheKey, product, 1, TimeUnit.HOURS);
        }

        return product;
    }
}
```

**两种方案对比**

| 对比维度 | 布隆过滤器 | 缓存空值 |
|----------|-----------|----------|
| 实现复杂度 | 较高 | 简单 |
| 内存占用 | 极少（bit级别） | 每个空key占一定内存 |
| 误判风险 | 有误判率（可能误杀正常key） | 无 |
| 对恶意攻击防御 | ✅ 强 | ⚠️ 大量空key会占用缓存空间 |
| 适用场景 | 数据量极大、key集合相对固定 | 中小型系统，快速实现 |

> 💡 **最佳实践**：布隆过滤器做第一道防线拦截不存在的key + 缓存空值做第二道防线兜底。

#### 2.1.2 缓存击穿 (Cache Breakdown)

**问题描述**

> ⚠️ 一个**热点key**在缓存过期的一瞬间，大量并发请求同时涌入，全部穿透到数据库。

```
时间线：
  T0: 热点key刚刚过期
  T1: 1000个并发请求同时到达 → 全部缓存MISS
  T2: 1000个请求同时查数据库 → 数据库瞬间被打爆
```

**方案一：互斥锁 (Mutex Lock)**

```java
@Service
public class ProductServiceMutex {

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private StringRedisTemplate stringRedisTemplate;
    @Autowired
    private ProductMapper productMapper;

    private static final String CACHE_KEY_PREFIX = "product:";
    private static final String LOCK_KEY_PREFIX = "lock:product:";
    private static final long CACHE_TTL = 3600L;

    public Product getProductWithLock(Long id) {
        String cacheKey = CACHE_KEY_PREFIX + id;
        String lockKey = LOCK_KEY_PREFIX + id;

        // 1. 查缓存
        Object cacheObj = redisTemplate.opsForValue().get(cacheKey);
        if (cacheObj != null) {
            return (Product) cacheObj;
        }

        // 2. 缓存未命中 → 尝试获取分布式锁
        String requestId = UUID.randomUUID().toString();
        Boolean locked = stringRedisTemplate.opsForValue()
            .setIfAbsent(lockKey, requestId, 10, TimeUnit.SECONDS);

        if (Boolean.TRUE.equals(locked)) {
            // 3. 获取锁成功 → 查数据库 + 回写缓存
            try {
                // 双重检查：拿到锁后再次检查缓存，防止等待线程重复查DB
                Object doubleCheck = redisTemplate.opsForValue().get(cacheKey);
                if (doubleCheck != null) {
                    return (Product) doubleCheck;
                }

                Product product = productMapper.selectById(id);
                if (product != null) {
                    redisTemplate.opsForValue()
                        .set(cacheKey, product, CACHE_TTL, TimeUnit.SECONDS);
                }
                return product;
            } finally {
                // 释放锁（使用Lua脚本确保原子性）
                String script = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
                stringRedisTemplate.execute(
                    new DefaultRedisScript<>(script, Long.class),
                    Collections.singletonList(lockKey),
                    requestId
                );
            }
        } else {
            // 4. 获取锁失败 → 自旋等待 + 重试
            try {
                Thread.sleep(50);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            return getProductWithLock(id); // 递归重试
        }
    }
}
```

**方案二：逻辑过期 (Logical Expiry)**

所谓"逻辑过期"就是在value中存一个过期时间，而不是依赖Redis的TTL过期。后台定时刷新热点key，永远不让它真正过期。

```java
@Data
public class CacheItem<T> {
    private T data;           // 实际数据
    private Long expireTime;  // 逻辑过期时间戳
}

@Service
public class ProductServiceLogicalExpire {

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private ProductMapper productMapper;

    private static final String CACHE_KEY_PREFIX = "product:hot:";
    private static final long LOGICAL_TTL = 60 * 1000L; // 60秒逻辑过期

    public Product getProduct(Long id) {
        String cacheKey = CACHE_KEY_PREFIX + id;

        // 1. 查缓存
        CacheItem<Product> cacheItem = (CacheItem<Product>)
            redisTemplate.opsForValue().get(cacheKey);

        if (cacheItem == null) {
            // 2. 缓存不存在 → 同步查库 + 回写
            return loadAndCache(id, cacheKey);
        }

        // 3. 判断逻辑是否过期
        if (cacheItem.getExpireTime() > System.currentTimeMillis()) {
            // 未过期 → 直接返回
            return cacheItem.getData();
        }

        // 4. 逻辑过期 → 异步刷新缓存（先返回旧数据）
        asyncRefreshCache(id, cacheKey);

        return cacheItem.getData();
    }

    private Product loadAndCache(Long id, String cacheKey) {
        Product product = productMapper.selectById(id);
        if (product != null) {
            CacheItem<Product> item = new CacheItem<>();
            item.setData(product);
            item.setExpireTime(System.currentTimeMillis() + LOGICAL_TTL);
            redisTemplate.opsForValue().set(cacheKey, item);
        }
        return product;
    }

    private void asyncRefreshCache(Long id, String cacheKey) {
        // 使用线程池异步刷新
        CompletableFuture.runAsync(() -> {
            // 这里可以加一个分布式锁，防止多个线程同时刷新
            Product product = productMapper.selectById(id);
            if (product != null) {
                CacheItem<Product> item = new CacheItem<>();
                item.setData(product);
                item.setExpireTime(System.currentTimeMillis() + LOGICAL_TTL);
                redisTemplate.opsForValue().set(cacheKey, item);
            }
        });
    }
}
```

**两种方案对比**

| 对比维度 | 互斥锁 | 逻辑过期 |
|----------|--------|----------|
| 数据一致性 | ✅ 强一致（只有一个线程重建缓存） | ⚠️ 弱一致（可能读到旧数据） |
| 性能 | ⚠️ 有等待延迟 | ✅ 无需等待，立即返回 |
| 实现复杂度 | 中等 | 较高（需管理后台线程） |
| 适用场景 | 对一致性要求高的数据（库存、金额） | 对一致性要求不高的热点数据（商品详情、资讯内容） |

#### 2.1.3 缓存雪崩 (Cache Avalanche)

**问题描述**

> ⚠️ 大量key同时过期，或者Redis直接宕机，导致海量请求直击数据库，引发连锁反应。

**方案一：随机TTL (Random TTL)**

```java
@Component
public class CacheService {

    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    /**
     * 设置缓存，基础TTL + 随机偏移
     */
    public void setWithRandomTTL(String key, Object value, long baseTTL) {
        // 基础TTL ± 随机20%的偏移量
        long randomOffset = (long) (baseTTL * 0.2 * Math.random());
        long finalTTL = baseTTL + randomOffset;

        redisTemplate.opsForValue()
            .set(key, value, finalTTL, TimeUnit.SECONDS);
    }

    /**
     * 批量设置缓存，每个key加不同的随机偏移
     */
    public void batchSetWithRandomTTL(Map<String, Object> keyValueMap, long baseTTL) {
        keyValueMap.forEach((key, value) -> {
            long randomOffset = (long) (baseTTL * 0.2 * Math.random());
            redisTemplate.opsForValue()
                .set(key, value, baseTTL + randomOffset, TimeUnit.SECONDS);
        });
    }
}
```

**方案二：多级缓存 (Multi-Level Cache)**

```
请求 → L1: Caffeine(本地缓存) → 命中 → 返回
           ↓ MISS
         L2: Redis → 命中 → 返回 + 回写L1
           ↓ MISS
         数据库 → 回写L1 + L2
```

```java
// =============================================
// Caffeine 本地缓存配置
// =============================================
import com.github.benmanes.caffeine.cache.Cache;
import com.github.benmanes.caffeine.cache.Caffeine;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import java.util.concurrent.TimeUnit;

@Configuration
public class CaffeineConfig {

    @Bean
    public Cache<String, Object> caffeineCache() {
        return Caffeine.newBuilder()
            // 最大条目数
            .maximumSize(10_000)
            // 写入后过期时间
            .expireAfterWrite(60, TimeUnit.SECONDS)
            // 访问后过期时间（30分钟内未被访问则淘汰）
            .expireAfterAccess(30, TimeUnit.MINUTES)
            // 初始化容量
            .initialCapacity(1000)
            // 记录命中率（监控用）
            .recordStats()
            .build();
    }
}

// =============================================
// 多级缓存服务
// =============================================
@Service
public class MultiLevelCacheService {

    @Autowired
    private Cache<String, Object> caffeineCache;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private ProductMapper productMapper;

    private static final String CACHE_KEY_PREFIX = "product:";

    public Product getProduct(Long id) {
        String cacheKey = CACHE_KEY_PREFIX + id;

        // 1. L1: 查本地Caffeine缓存
        Object localCache = caffeineCache.getIfPresent(cacheKey);
        if (localCache != null) {
            return (Product) localCache;
        }

        // 2. L2: 查Redis缓存
        Object redisCache = redisTemplate.opsForValue().get(cacheKey);
        if (redisCache != null) {
            // 回写L1
            caffeineCache.put(cacheKey, redisCache);
            return (Product) redisCache;
        }

        // 3. 查数据库
        Product product = productMapper.selectById(id);
        if (product != null) {
            // 回写L1和L2
            caffeineCache.put(cacheKey, product);
            redisTemplate.opsForValue()
                .set(cacheKey, product, 1, TimeUnit.HOURS);
        }

        return product;
    }

    /**
     * 更新数据时，需要同时失效L1和L2
     */
    public void updateProduct(Product product) {
        // 更新数据库
        productMapper.updateById(product);

        // 失效L1
        caffeineCache.invalidate(CACHE_KEY_PREFIX + product.getId());
        // 失效L2
        redisTemplate.delete(CACHE_KEY_PREFIX + product.getId());
    }
}
```

```java
public class ProductService {

        fallback = "getProductFallback",       // 降级方法
        blockHandler = "getProductBlockHandler" // 限流方法
    )
    public Product getProduct(Long id) {
        // ... 正常业务逻辑
    }

    /**
     * 降级方法：缓存不可用时返回兜底数据
     */
    public Product getProductFallback(Long id, Throwable t) {
        // 返回缓存中的过期数据（允许一定程度的脏读）
        Product stale = (Product) redisTemplate.opsForValue()
            .get("product:stale:" + id);
        if (stale != null) {
            return stale;
        }
        // 连stale数据都没有 → 返回空对象（不要抛出异常）
        return Product.empty(id);
    }

    /**
     * 限流方法：超出QPS阈值时触发
     */
    public Product getProductBlockHandler(Long id, BlockException e) {
        // 返回限流提示
        return Product.empty(id);
    }
}
```

**三种雪崩应对方案对比**

| 方案 | 解决的问题 | 优点 | 缺点 |
|------|-----------|------|------|
| 随机TTL | key同时过期 | 简单有效，零额外依赖 | 不能应对Redis宕机 |
| 多级缓存 | Redis宕机 + 热点key过期 | 抗压能力强，CPU换性能 | 本地缓存占用内存，数据一致性弱 |
| 限流降级 | 数据库被打爆 | 保护整个系统不崩溃 | 用户体验下降（降级返回旧数据或空） |

> 💡 **生产最佳实践**：随机TTL + 多级缓存 + 限流降级 三者结合。多级缓存扛住99%的请求，随机TTL防止大量key同时过期，限流降级作为最后一道防线。

#### 2.1.4 RedisTemplate 配置

```java
// =============================================
// Redis 配置类
// =============================================
@Configuration
@EnableCaching
public class RedisConfig {

    @Bean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory factory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(factory);

        // 1. 创建JSON序列化器（用于Value）
        Jackson2JsonRedisSerializer<Object> jsonSerializer =
            new Jackson2JsonRedisSerializer<>(Object.class);
        ObjectMapper om = new ObjectMapper();
        om.setVisibility(PropertyAccessor.ALL, JsonAutoDetect.Visibility.ANY);
        om.activateDefaultTyping(
            ObjectMapper.getDefaultTyping(),
            ObjectMapper.DefaultTyping.NON_FINAL
        );
        // 支持Java 8时间类型
        om.registerModule(new JavaTimeModule());
        om.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
        jsonSerializer.setObjectMapper(om);

        // 2. 创建String序列化器（用于Key）
        StringRedisSerializer stringSerializer = new StringRedisSerializer();

        // Key 使用 String 序列化
        template.setKeySerializer(stringSerializer);
        template.setHashKeySerializer(stringSerializer);

        // Value 使用 JSON 序列化
        template.setValueSerializer(jsonSerializer);
        template.setHashValueSerializer(jsonSerializer);

        template.afterPropertiesSet();
        return template;
    }

    /**
     * 专门缓存字符串的 RedisTemplate
     * 用于分布式锁、计数器等场景
     */
    @Bean
    public StringRedisTemplate stringRedisTemplate(RedisConnectionFactory factory) {
        return new StringRedisTemplate(factory);
    }

    /**
     * Redis CacheManager 配置（供 @Cacheable 使用）
     */
    @Bean
    public CacheManager cacheManager(RedisConnectionFactory factory) {
        RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
            // 设置key序列化方式
            .serializeKeysWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(new StringRedisSerializer()))
            // 设置value序列化方式
            .serializeValuesWith(
                RedisSerializationContext.SerializationPair
                    .fromSerializer(new Jackson2JsonRedisSerializer<>(Object.class)))
            // 默认TTL 1小时
            .entryTtl(Duration.ofHours(1))
            // 禁止缓存null值（与缓存穿透的空值缓存方案不同，这里指防意外NullPointer）
            .disableCachingNullValues();

        return RedisCacheManager.builder(factory)
            .cacheDefaults(config)
            .transactionAware()
            .build();
    }
}
```

#### 2.1.5 Spring Cache 注解体系

Spring Cache 提供了一套声明式缓存抽象，支持 Redis、Caffeine、EhCache 等多种实现。

```java
@Service
@CacheConfig(cacheNames = "product") // 公共缓存前缀
public class ProductCacheService {

    // =============================================
    // @Cacheable: 缓存注解（查）
    // =============================================

    /**
     * 基础用法
     */
    @Cacheable(key = "#id")
    public Product getById(Long id) {
        return productMapper.selectById(id);
    }

    /**
     * sync = true 表示开启缓存同步（相当于上面讲的互斥锁方案）
     * 多个线程并发访问时，只有一个线程执行方法体，其他线程等待
     */
    @Cacheable(key = "#id", sync = true)
    public Product getByIdWithSync(Long id) {
        // 只有第一个线程会进入此方法
        // 后续线程等待结果返回（类似ReentrantLock效果）
        return productMapper.selectById(id);
    }

    /**
     * condition: 满足条件才缓存
     * unless: 满足条件不缓存
     */
    @Cacheable(
        key = "#id",
        condition = "#id > 0",         // id>0时才缓存
        unless = "#result == null"      // 返回null时不缓存（防止缓存空值，但和穿透缓存空值方案不同）
    )
    public Product getByIdConditional(Long id) {
        return productMapper.selectById(id);
    }

    /**
     * 多条件组合条件
     */
    @Cacheable(key = "#categoryId + ':' + #page + ':' + #size")
    public List<Product> listByCategory(Long categoryId, int page, int size) {
        return productMapper.selectByCategory(categoryId, page, size);
    }

    // =============================================
    // @CachePut: 更新缓存（写）
    // 每次都会执行方法体，并把返回值放入缓存
    // =============================================

    @CachePut(key = "#product.id")
    public Product updateProduct(Product product) {
        productMapper.updateById(product);
        return product; // 返回值写入缓存
    }

    // =============================================
    // @CacheEvict: 移除缓存（删）
    // =============================================

    /**
     * 移除单个缓存
     */
    @CacheEvict(key = "#id")
    public void deleteProduct(Long id) {
        productMapper.deleteById(id);
    }

    /**
     * allEntries: 清除该cacheNames下的所有缓存
     * 谨慎使用！批量清除代价较大
     */
    @CacheEvict(allEntries = true)
    public void clearAllProductCache() {
        // 清空 product 这个 cacheNames 下的全部缓存
    }

    /**
     * beforeInvocation: 在方法执行前清除缓存
     * 默认false（方法执行后清除），如果方法抛出异常则不清除
     * 设为true则无论方法成功与否都清除
     */
    @CacheEvict(key = "#id", beforeInvocation = true)
    public void forceDeleteCache(Long id) {
        // 即使这里抛出异常，缓存也会被清除
    }

    // =============================================
    // @Caching: 组合多个缓存操作
    // =============================================

    @Caching(
        put = {
            @CachePut(cacheNames = "product", key = "#product.id"),
            @CachePut(cacheNames = "product:name", key = "#product.name")
        },
        evict = {
            @CacheEvict(cacheNames = "product:list", allEntries = true)
        }
    )
    public Product saveProduct(Product product) {
        productMapper.insert(product);
        return product;
    }
}
```

**Spring Cache 注解使用要点**

| 注解 | 作用 | 是否执行业务方法 | 典型场景 |
|------|------|-----------------|----------|
| `@Cacheable` | 缓存存在时直接返回，不存在则执行并缓存 | 缓存MISS时执行 | 查询接口 |
| `@CachePut` | 始终执行方法体，更新缓存 | 始终执行 | 新增/更新接口 |
| `@CacheEvict` | 移除缓存 | 默认在方法执行后 | 删除接口 |
| `@Caching` | 组合多个缓存操作 | 取决于内部注解 | 复杂写操作 |
| `@CacheConfig` | 类级别共享配置 | 不适用 | 公共cacheNames设置 |

> 💡 **`@Cacheable(sync = true)` 原理**：底层通过 `CacheAspectSupport` 对同一个key加 `ReentrantLock` 实现，一个线程查库重建缓存，其他线程阻塞等待。适用于单机环境；分布式环境下建议用Redis分布式锁。

#### 2.1.6 缓存更新模式

**Cache-Aside Pattern（旁路缓存，最常用）**

```
读操作:
  请求 → 查缓存 → 命中 → 返回
               → MISS → 查DB → 写缓存 → 返回

写操作:
  更新DB → 删除缓存（不是更新缓存！）
```

```java
@Service
public class CacheAsideService {

    // 读操作
    public Product getProduct(Long id) {
        // 1. 从缓存读
        Product product = redisTemplate.opsForValue().get("product:" + id);
        if (product != null) {
            return product;
        }
        // 2. 从数据库读
        product = productMapper.selectById(id);
        if (product != null) {
            // 3. 写入缓存
            redisTemplate.opsForValue().set("product:" + id, product, 1, TimeUnit.HOURS);
        }
        return product;
    }

    // 写操作：更新数据库 → 删除缓存
    // ⚠️ 为什么是删除缓存而不是更新缓存？
    // 1. 避免并发写导致缓存数据不一致
    // 2. 懒加载：下次读时再写入，减少无效写
    @Transactional
    public void updateProduct(Product product) {
        productMapper.updateById(product);
        // 删除缓存（不是更新！）
        redisTemplate.delete("product:" + product.getId());
    }
}
```

> ⚠️ **Cache-Aside 写操作为什么要先更新DB再删缓存？** 如果是先删缓存再更新DB，在并发场景下会有问题：线程A删了缓存，线程B读取到旧数据并写入缓存，然后线程A才更新DB → 缓存中永远是旧数据。正确的做法是先更新DB再删缓存。

**Read-Through Pattern**

数据读取由缓存层负责，应用只跟缓存交互。

```
请求 → 缓存（Cache Provider）
         ↓ (缓存未命中时，Cache Provider自己查DB加载)
       数据库 → 缓存自动回写 → 返回给应用
```

Spring Cache 的 `@Cacheable` 就是典型的 Read-Through 实现。

**Write-Through Pattern**

数据写入时，先写入缓存，再由缓存写入数据库。

```
应用写数据 → 写缓存（缓存负责同步写入DB） → 返回
```

**Write-Behind Pattern**

数据写入先到缓存，缓存异步批量写入数据库（最终一致性）。

```
应用写数据 → 写缓存 → 立即返回
              ↓ (异步批量)
            数据库（延迟写入）
```

**四种模式对比**

| 模式 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|----------|
| **Cache-Aside** | 高（强一致） | 中等 | 低 | 通用业务，**最推荐** |
| **Read-Through** | 高 | 中等 | 低 | 读多写少，Spring Cache场景 |
| **Write-Through** | 高 | 较低（写串行） | 中 | 对一致性要求极高的写入 |
| **Write-Behind** | 低（最终一致） | 高（异步批量） | 高 | 日志、埋点、访问计数 |

#### 2.1.7 Caffeine 本地缓存 + Redis L1/L2 架构

> 🎯 **多级缓存的核心思想**：L1本地缓存（Caffeine）扛绝大部分热点请求（性能≈纳秒级），L2分布式缓存（Redis）做共享数据存储和跨进程数据同步。

```java
// =============================================
// 多级缓存服务完整实现
// =============================================
@Service
public class MultiLevelCacheManager {

    @Autowired
    private Cache<String, Object> caffeineCache;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    /**
     * 多级缓存写入
     * 先写L2 (Redis)，再写L1 (Caffeine)
     */
    public void put(String key, Object value, long ttl, TimeUnit unit) {
        // 先写Redis（作为主存储）
        redisTemplate.opsForValue().set(key, value, ttl, unit);
        // 再写本地缓存（L1）
        caffeineCache.put(key, value);
    }

    /**
     * 多级缓存读取
     */
    public Object get(String key) {
        // 1. 查L1
        Object value = caffeineCache.getIfPresent(key);
        if (value != null) {
            return value;
        }

        // 2. 查L2
        value = redisTemplate.opsForValue().get(key);
        if (value != null) {
            // 回写L1
            caffeineCache.put(key, value);
        }

        return value;
    }

    /**
     * 多级缓存移除
     */
    public void evict(String key) {
        // 同时失效两级缓存
        caffeineCache.invalidate(key);
        redisTemplate.delete(key);
    }

    /**
     * 使用Redis Pub/Sub 通知其他节点失效L1缓存
     * 解决多级缓存的一致性问题
     */
    public void evictWithNotification(String cacheName, String key) {
        // 失效本机L1 + L2
        evict(key);
        // 发送广播通知其他机器失效L1
        String message = cacheName + ":" + key;
        redisTemplate.convertAndSend("cache:evict", message);
    }
}

// =============================================
// Redis消息监听器配置（接收其他节点发来的缓存失效通知）
// =============================================
@Component
public class CacheEvictMessageListener implements MessageListener {

    @Autowired
    private Cache<String, Object> caffeineCache;

    @Override
    public void onMessage(Message message, byte[] pattern) {
        String msg = new String(message.getBody());
        // 消息格式: "cacheName:key"
        int separatorIndex = msg.indexOf(":");
        if (separatorIndex > 0) {
            String key = msg.substring(separatorIndex + 1);
            // 失效本地缓存
            caffeineCache.invalidate(key);
        }
    }
}
```

### 2.2 分库分表 (Database Sharding)

#### 2.2.1 垂直分表 vs 水平分表

**垂直分表 (Vertical Splitting)**

将一张表的列拆分成多张表，每张表存储部分列，通过主键关联。

```
原始表: product(id, name, price, description, image_urls, tech_specs, stock, create_time, update_time)
                              ↓ 垂直拆分
主表: product(id, name, price, stock, create_time, update_time)
详情表: product_detail(id, description, image_urls, tech_specs)
```

| 对比 | 垂直分表 | 水平分表 |
|------|----------|----------|
| 拆分维度 | 按列拆分（字段拆分） | 按行拆分（数据行拆分） |
| 数据分布 | 每张表结构不同，行数相同 | 每张表结构相同，行数不同 |
| 解决什么问题 | 单行数据过大、冷热字段分离 | 单表数据量过大（>500万行） |
| 查询影响 | 需JOIN回原表逻辑 | 路由到特定分片 |

**水平分表 (Horizontal Splitting)**

将一张表的数据按某个分片键分散到多张结构相同的表中。

```
原始表: orders(5000万行数据)
                 ↓ 水平拆分（按user_id取模）
order_0: user_id % 4 == 0 的数据
order_1: user_id % 4 == 1 的数据
order_2: user_id % 4 == 2 的数据
order_3: user_id % 4 == 3 的数据
```

**什么时候需要分库分表？**

> ⚠️ **经验阈值**：
> - 单表数据量超过 **500 万行**就需要考虑
> - 超过 **2000 万行**必须分表
> - 单库QPS超过 **2000** 考虑分库

> 💡 不要为了分库分表而分库分表。提前规划**分片键**的选择非常关键，选择不当会导致后续无法扩展。

---

#### 2.2.2 Sharding-JDBC 核心概念

Sharding-JDBC 是 Apache ShardingSphere 的核心组件，是一个轻量级 Java 框架，在 JDBC 层提供分库分表能力。

**核心概念**

| 概念 | 说明 | 示例 |
|------|------|------|
| **逻辑表 (Logic Table)** | 应用程序中使用的表名 | `order` |
| **实际表 (Actual Table)** | 物理上真实存在的表 | `order_0`, `order_1`, `order_2`, `order_3` |
| **数据节点 (Data Node)** | 数据源 + 实际表的组合 | `ds0.order_0`, `ds1.order_2` |
| **分片键 (Sharding Key)** | 用于分片的字段 | `user_id`, `order_id` |
| **分片算法 (Sharding Algorithm)** | 决定数据路由的逻辑 | `user_id % 4` |
| **绑定表 (Binding Table)** | 分片规则一致的表（关联查询优化） | `order` 和 `order_item` |
| **广播表 (Broadcast Table)** | 每个库都有一份的表 | `t_dict`（字典表） |

**绑定表 (Binding Table)**

```yaml
# 配置绑定表后，order 和 order_item 的关联查询
# 不会出现跨库JOIN，因为它们的分布规律一致
spring:
  shardingsphere:
    rules:
      sharding:
        binding-tables:
          - order, order_item
```

> 💡 **绑定表的作用**：避免跨分片JOIN。例如 `order` 和 `order_item` 都按 `user_id` 分片，同一个订单的数据在同一个分片上，JOIN查询不需要跨库。

**广播表 (Broadcast Table)**

```yaml
spring:
  shardingsphere:
    rules:
      sharding:
        broadcast-tables:
          - t_dict
          - t_config
```

#### 2.2.3 Sharding-JDBC 分片策略

**1. Inline 分片策略（行表达式，最常用）**

使用 Groovy 表达式，语法简单，适合按取模或枚举值分片。

**2. Standard 分片策略（标准分片）**

支持精确路由（=, IN）和范围路由（BETWEEN, >, <）。

```java
// 自定义标准分片算法
public class OrderStandardShardingAlgorithm implements StandardShardingAlgorithm<Long> {

    @Override
    public String doSharding(Collection<String> availableTargetNames,
                             PreciseShardingValue<Long> shardingValue) {
        // 精确分片：user_id % 4
        long value = shardingValue.getValue();
        String suffix = String.valueOf(value % 4);
        for (String target : availableTargetNames) {
            if (target.endsWith(suffix)) {
                return target;
            }
        }
        throw new UnsupportedOperationException("无法路由到目标分片");
    }

    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                         RangeShardingValue<Long> shardingValue) {
        // 范围分片：例如查询 user_id BETWEEN 1000 AND 2000
        Range<Long> range = shardingValue.getValueRange();
        Collection<String> result = new ArrayList<>();
        // 简化实现：扫描所有分片（生产环境应更精确）
        for (String target : availableTargetNames) {
            if (target.endsWith("0") || target.endsWith("1")
                || target.endsWith("2") || target.endsWith("3")) {
                result.add(target);
            }
        }
        return result;
    }
}
```

**3. Complex 分片策略（复合分片）**

支持多个分片键组合路由。

```java
public class OrderComplexShardingAlgorithm implements ComplexKeysShardingAlgorithm<Long> {

    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                         ComplexKeysShardingValue<Long> shardingValue) {
        // 获取多个分片键的值
        Map<String, Collection<Long>> columnValuesMap = shardingValue.getColumnNameAndShardingValuesMap();
        Collection<Long> userIdValues = columnValuesMap.get("user_id");
        Collection<Long> orderIdValues = columnValuesMap.get("order_id");

        // 自定义路由逻辑：根据user_id和order_id组合确定分片
        Set<String> result = new LinkedHashSet<>();
        if (userIdValues != null && !userIdValues.isEmpty()) {
            // 优先按user_id路由
            for (Long userId : userIdValues) {
                String suffix = String.valueOf(userId % 4);
                for (String target : availableTargetNames) {
                    if (target.endsWith(suffix)) {
                        result.add(target);
                    }
                }
            }
        } else if (orderIdValues != null && !orderIdValues.isEmpty()) {
            // 如果user_id没传，按order_id路由
            for (Long orderId : orderIdValues) {
                String suffix = String.valueOf(orderId % 4);
                for (String target : availableTargetNames) {
                    if (target.endsWith(suffix)) {
                        result.add(target);
                    }
                }
            }
        }
        return result;
    }
}
```

**4. Hint 分片策略（强制路由）**

不依赖SQL中的列，而是通过 `HintManager` 手动指定分片。

```java
@Service
public class OrderHintService {

    @Autowired
    private OrderMapper orderMapper;

    /**
     * 使用强制路由指定查询某个分片
     */
    public List<Order> queryByHint(Long userId) {
        try (HintManager hintManager = HintManager.getInstance()) {
            // 强制将 user_id 设为分片值
            hintManager.addTableShardingValue("order", userId);
            hintManager.addTableShardingValue("order_item", userId);
            return orderMapper.selectAll();
        }
    }
}
```

**四种分片策略对比**

| 策略 | 分片键数量 | 支持范围查询 | 使用方式 | 推荐度 |
|------|-----------|-------------|----------|--------|
| **Inline** | 单键 | 不支持 | YAML表达式 | ⭐⭐⭐⭐⭐（最常用） |
| **Standard** | 单键 | 支持 | 自定义Java类 | ⭐⭐⭐⭐ |
| **Complex** | 多键 | 支持 | 自定义Java类 | ⭐⭐⭐（特殊场景） |
| **Hint** | 手动指定 | 由实现决定 | HintManager API | ⭐⭐（强制路由） |

#### 2.2.4 分布式ID生成

**方案一：雪花算法 (Snowflake Algorithm)**

Twitter 开源，用64位Long型数字做ID，趋势递增。

```
Snowflake ID 结构 (64位):
  ┌──────────────────────────────────────────────────────────┐
  │ 0 │ 00000000000000000000000000000000000000000 │ 00000 │ 000000000000 │
  └──────────────────────────────────────────────────────────┘
   ↑                        ↑                         ↑            ↑
   符号位(1bit)          时间戳(41bit)          机器ID(10bit)  序列号(12bit)
   (始终为0)           (可表示69年, 自定义纪元)
                                                    ↓         ↓
                                                  工作机器ID   同一毫秒内序列号
                                                  (可部署最多  (4096个/毫秒)
                                                   1024台机器)
```

```java
// =============================================
// 雪花算法 Java 实现
// =============================================
public class SnowflakeIdWorker {

    // 开始时间戳（2021-01-01）
    private final long epoch = 1609430400000L;

    // 各部分的位数
    private final long workerIdBits = 10L;
    private final long sequenceBits = 12L;

    // 各部分最大值
    private final long maxWorkerId = ~(-1L << workerIdBits);
    private final long maxSequence = ~(-1L << sequenceBits);

    // 各部分左移位数
    private final long workerIdShift = sequenceBits;
    private final long timestampShift = sequenceBits + workerIdBits;

    private long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public SnowflakeIdWorker(long workerId) {
        if (workerId < 0 || workerId > maxWorkerId) {
            throw new IllegalArgumentException("workerId超出范围[0, " + maxWorkerId + "]");
        }
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long timestamp = timeGen();

        // 时钟回拨处理
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨，拒绝生成ID");
        }

        if (timestamp == lastTimestamp) {
            // 同一毫秒内，序列号递增
            sequence = (sequence + 1) & maxSequence;
            if (sequence == 0) {
                // 序列号耗尽，等待下一毫秒
                timestamp = tilNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }

        lastTimestamp = timestamp;

        // 组装ID
        return ((timestamp - epoch) << timestampShift)
            | (workerId << workerIdShift)
            | sequence;
    }

    private long tilNextMillis(long lastTimestamp) {
        long timestamp = timeGen();
        while (timestamp <= lastTimestamp) {
            timestamp = timeGen();
        }
        return timestamp;
    }

    private long timeGen() {
        return System.currentTimeMillis();
    }
}
```

**方案二：号段模式 (Segment ID)**

美团 Leaf 使用的方案：从数据库批量取号段，在内存中分配。

```
数据库表: leaf_segment(biz_tag, max_id, step, update_time)

1. Leaf Server 从DB申请一个号段: UPDATE leaf_segment SET max_id = max_id + step
2. 获取到号段 [old_max_id, new_max_id) 在内存中分配
3. 号段用掉一定比例后，异步加载下一个号段
```

```sql
-- Leaf 号段表结构
CREATE TABLE leaf_segment (
    biz_tag   VARCHAR(128) NOT NULL DEFAULT '' COMMENT '业务标识',
    max_id    BIGINT       NOT NULL DEFAULT 1 COMMENT '当前最大ID',
    step      INT          NOT NULL DEFAULT 1000 COMMENT '号段步长',
    version   INT          NOT NULL DEFAULT 1 COMMENT '乐观锁版本号',
    update_time DATETIME   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (biz_tag)
) ENGINE=InnoDB;

-- 获取号段（使用乐观锁）
UPDATE leaf_segment
SET max_id = max_id + step, version = version + 1
WHERE biz_tag = 'order_id' AND version = #{version};
```

**两种分布式ID方案对比**

| 对比维度 | 雪花算法 | 号段模式 |
|----------|---------|----------|
| **ID趋势** | 趋势递增（不是严格递增） | 严格递增（号段内连续） |
| **性能** | 纯内存计算，百万级/秒 | 依赖DB，但双buffer可到万级/秒 |
| **依赖性** | 依赖机器时钟（时钟回拨有问题） | 依赖数据库 |
| **长度** | 64位（Long类型） | 可自定（通常Long） |
| **可读性** | 好（可以反解析时间戳和机器ID） | 差（纯数字流水） |
| **适用场景** | 大多数业务场景 | 对ID趋势递增有强要求的场景 |

#### 2.2.5 读写分离 (Read/Write Splitting)

**主从复制原理**

```
Master（主库）                 Slave(s)（从库）
   │                              │
   ├─ 写入binlog ──────────────→   │
   │    (二进制日志)               ├─ 读取relay log
   │                              ├─ 重放SQL到从库
   │ 写入                         │ 完成复制
```

**Sharding-JDBC 读写分离配置**

```yaml

      names: ds-master, ds-slave-0, ds-slave-1

        url: jdbc:mysql://192.168.1.10:3306/order_db
        username: root
        password: root
      ds-slave-0:
        url: jdbc:mysql://192.168.1.11:3306/order_db
        username: root
        password: root
      ds-slave-1:
        url: jdbc:mysql://192.168.1.12:3306/order_db
        username: root
        password: root
    rules:
      # 读 写 分 离 配 置
      readwrite-splitting:
        data-sources:
          order-readwrite:
            write-data-source-name: ds-master
            read-data-source-names:
              - ds-slave-0
              - ds-slave-1
            # 负载均衡算法
            load-balancer-name: round-robin
        load-balancers:
          round-robin:
            type: ROUND_ROBIN
          random:
            type: RANDOM
```

**读写分离负载均衡算法**

| 算法 | 类型 | 说明 | 适用场景 |
|------|------|------|----------|
| ROUND_ROBIN | 内置 | 轮询，依次分配请求 | 从库性能均匀 |
| RANDOM | 内置 | 随机分配请求 | 从库性能有差异 |
| WEIGHT | 内置 | 按权重分配（需配置weight属性） | 从库配置不同 |

> 💡 **读写分离的注意事项**：主从复制的延迟问题。写入后立刻读取，可能因为复制延迟读到旧数据。解决方案：写后读强制走主库（Sharding-JDBC支持`hint`强制路由主库），或者短期内缓存写结果。

## 3. 高频踩坑与误区

### 3.1 缓存相关误区

#### 误区1：缓存穿透只发生在不存在的key

**错误理解**：只有恶意攻击使用不存在的key才会导致穿透。
**正解**：大量不存在的key确实会穿透，但**大量热点key同时过期**同样属于穿透变体。实际场景中，刚上线时缓存空窗期（缓存无数据，所有流量直奔数据库）也是一种穿透。

#### 误区2：布隆过滤器不会误杀

**正解**：布隆过滤器说"元素可能存在"时，有**一定概率误判**（False Positive）。更关键的是，**布隆过滤器不支持删除元素**。如果某个商品被下架了，它的ID在布隆过滤器中的标志位可能与其他元素共享，不能直接删除。解决方案是使用**Counting Bloom Filter**（计数布隆过滤器，支持删除）。

#### 误区3：@Cacheable(sync=true) 能完美解决击穿

**正解**：`sync=true`底层用 `ReentrantLock`，只在**单机**范围内互斥。如果部署了多个实例（多台机器），每台机器都会有一个线程去查数据库。分布式环境下需要用Redis分布式锁。

#### 误区4：先删缓存再更新DB

**典型错误**❌：
```java
// 错误写法：先删缓存再更新DB —— 并发场景下数据不一致
@Transactional
public void updateProduct(Product product) {
    redisTemplate.delete("product:" + product.getId()); // 先删缓存
    productMapper.updateById(product);                   // 后更新DB
}
```
线程A先删了缓存，线程B读取到旧数据写回缓存，线程A才更新DB → 缓存中是旧数据。**正确做法是先更新DB再删缓存**。

#### 误区5：更新缓存而不是删除缓存

**典型错误**❌：
```java
// 错误写法：更新DB同时更新缓存
@Transactional
public void updateProduct(Product product) {
    productMapper.updateById(product);
    redisTemplate.opsForValue().set("product:" + product.getId(), product); // 直接更新缓存
}
```
并发场景下，如果在写操作之间有读操作插入，缓存可能写入旧数据。**缓存只删除，不更新**（Cache-Aside模式的核心原则）。

### 3.2 分库分表相关误区

#### 误区1：分片键选错了无法改变

**正解**：分片键一旦选定，后续修改极为困难。选分片键的核心原则：
- **高频查询列**：80%以上的查询都带这个条件
- **数据分布均匀**：模运算后每个分片数据量接近
- **尽量避免跨分片查询**

> ⚠️ 分片键选择的心法：如果业务以用户维度查询，选 `user_id`；如果以时间维度查询，选 `create_time`（按月分片）。

#### 误区2：IN查询支持跨分片没问题

**正解**：`WHERE user_id IN (1, 2, 3, 100)` 当IN的列表长度较大时，需要广播到多个分片执行，然后合并结果。如果IN的列表很长（1000+），合并结果集的开销很大。建议限制IN查询的列表长度。

#### 误区3：分表后JOIN不受影响

**正解**：分表后，跨分片的JOIN会变成分布式查询，性能急剧下降。即使配置了绑定表可以减少跨分片JOIN，复杂的JOIN操作（3表以上）仍然不推荐。**分表场景下推荐反范式设计 + 冗余字段**。

#### 误区4：读写分离解决所有读压力

**正解**：读写分离只能缓解读压力，不能**消除**读压力。当读QPS达到千万级别时，从库的建立和维护成本也很大。需要配合缓存一起使用：**缓存扛热读 + 从库扛冷读**。

### 练习题1：缓存三大问题识别

判断以下场景属于缓存三大问题（穿透/击穿/雪崩）中的哪一种：

1. 某电商平台双十一大促，首页推荐系统所有缓存都在同一时刻过期，导致数据库连接数打满。
2. 恶意用户连续请求大量不存在的商品ID `/product/9999999`，每次请求都落到数据库。
3. 某热卖商品详情页缓存刚好过期，1000台手机同时刷新导致数据库负载飙高。
4. Redis集群因网络分区断开后恢复，大量缓存请求被转发到MySQL。

<details>
<summary>查看答案</summary>
1. 缓存雪崩（大量key同时过期）
2. 缓存穿透（不存在的数据穿透到DB）
3. 缓存击穿（单个热点key过期引发高并发）
4. 缓存雪崩（Redis宕机导致）
</details>

### 练习题2：判断Cache-Aside正确写法

以下哪段Java代码是符合Cache-Aside模式的正确实现？

```java
// 代码A
public void update(Product p) {
    redisTemplate.delete("product:" + p.getId());
    productMapper.updateById(p);
}

// 代码B
public void update(Product p) {
    productMapper.updateById(p);
    redisTemplate.delete("product:" + p.getId());
}

// 代码C
public void update(Product p) {
    productMapper.updateById(p);
    redisTemplate.opsForValue().set("product:" + p.getId(), p);

```

<details>
<summary>查看答案</summary>
**答案是B**。Cache-Aside模式要求先更新数据库，再删除缓存。代码A先删缓存再更新DB，存在并发写入数据不一致问题。代码C直接更新缓存而不是删除，不符合Cache-Aside模式。
</details>

```java
            ObjectMapper.DefaultTyping.NON_FINAL
        );
        mapper.registerModule(new JavaTimeModule());
        mapper.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);
        valueSerializer.setObjectMapper(mapper);

        template.setValueSerializer(valueSerializer);
        template.setHashValueSerializer(valueSerializer);
        template.afterPropertiesSet();

        return template;
    }

    @Bean
    public CacheManager cacheManager(RedisConnectionFactory factory) {
        // 自定义每个缓存空间的TTL
        Map<String, RedisCacheConfiguration> configMap = new HashMap<>();

        // 商品缓存：1小时
        configMap.put("product",
            RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofHours(1))
                .serializeKeysWith(
                    RedisSerializationContext.SerializationPair
                        .fromSerializer(new StringRedisSerializer()))
                .serializeValuesWith(
                    RedisSerializationContext.SerializationPair
                        .fromSerializer(new GenericJackson2JsonRedisSerializer())));

        // 订单缓存：30分钟
        configMap.put("order",
            RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(30))
                .serializeKeysWith(
                    RedisSerializationContext.SerializationPair
                        .fromSerializer(new StringRedisSerializer()))
                .serializeValuesWith(
                    RedisSerializationContext.SerializationPair
                        .fromSerializer(new GenericJackson2JsonRedisSerializer())));

        return RedisCacheManager.builder(factory)
            .cacheDefaults(
                RedisCacheConfiguration.defaultCacheConfig()
                    .entryTtl(Duration.ofHours(1))
                    .disableCachingNullValues())
            .withInitialCacheConfigurations(configMap)
            .transactionAware()
            .build();
    }
```

```java
// =============================================
```

```java
@Service
@Slf4j
public class OrderService {

    @Autowired
    private OrderMapper orderMapper;
    @Autowired
    private OrderItemMapper orderItemMapper;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;
    @Autowired
    private ProductService productService;

    private static final String ORDER_CACHE_PREFIX = "order:";

    // =========== 创建订单（写操作走主库） ===========

    @Transactional(rollbackFor = Exception.class)
    public Order createOrder(Long userId, Long productId, Integer quantity,
                             String address) {
        // 1. 查询商品（获取价格）
        Product product = productService.getProduct(productId);
        if (product == null || product.getStock() < quantity) {
            throw new RuntimeException("商品库存不足");
        }

        // 2. 创建订单（order_id由ShardingSphere雪花算法自动生成）
        Order order = new Order();
        order.setUserId(userId);
        order.setProductId(productId);
        order.setQuantity(quantity);
        order.setTotalAmount(product.getPrice().multiply(BigDecimal.valueOf(quantity)));
        order.setStatus(0); // 待支付
        order.setAddress(address);
        order.setCreateTime(LocalDateTime.now());
        orderMapper.insert(order);

        // 3. 创建订单明细
        OrderItem item = new OrderItem();
        item.setOrderId(order.getOrderId());
        item.setProductId(productId);
        item.setProductName(product.getName());
        item.setQuantity(quantity);
        item.setPrice(product.getPrice());
        orderItemMapper.insert(item);

        // 4. 缓存订单信息（写后缓存）
        String cacheKey = ORDER_CACHE_PREFIX + order.getOrderId();
        redisTemplate.opsForValue().set(cacheKey, order, 30, TimeUnit.MINUTES);

        log.info("订单创建成功: orderId={}, userId={}", order.getOrderId(), userId);
        return order;
    }

    // =========== 查询订单（读操作走从库） ===========

    /**
     * 按order_id查询（先查缓存，再查DB）
     */
    public Order getOrder(Long orderId) {
        // 1. 查缓存
        String cacheKey = ORDER_CACHE_PREFIX + orderId;
        Order cached = (Order) redisTemplate.opsForValue().get(cacheKey);
        if (cached != null) {
            return cached;
        }

        // 2. 缓存MISS，查数据库（ShardingSphere路由到从库）
        Order order = orderMapper.selectByOrderId(orderId);
        if (order != null) {
            redisTemplate.opsForValue()
                .set(cacheKey, order, 30, TimeUnit.MINUTES);
        }
        return order;
    }

    /**
     * 按用户ID查订单列表（ShardingSphere按user_id路由到对应分片）
     */
    public List<Order> getUserOrders(Long userId, int page, int size) {
        int offset = (page - 1) * size;
        // ShardingSphere会根据userId自动路由到正确分片
        return orderMapper.selectByUserId(userId, offset, size);
    }

    // =========== 更新订单状态 ===========

    @Transactional(rollbackFor = Exception.class)
    public void updateOrderStatus(Long orderId, Integer status) {
        // 1. 更新数据库（走主库）
        orderMapper.updateStatus(orderId, status);

        // 2. 清除订单缓存
        String cacheKey = ORDER_CACHE_PREFIX + orderId;
        redisTemplate.delete(cacheKey);
    }
}
```

## 7. 本章复盘速记清单

### 7.1 缓存篇

| 序号 | 知识点 | 一句话总结 | 关键细节 |
|------|--------|-----------|----------|
| 1 | 缓存穿透 | 查不存在的数据一直打到DB | BloomFilter或缓存空值 |
| 2 | 缓存击穿 | 热点key过期瞬间高并发打到DB | 互斥锁或逻辑过期 |
| 3 | 缓存雪崩 | 大量key同时过期或Redis宕机 | 随机TTL / 多级缓存 / 限流 |
| 4 | Cache-Aside | 先查缓存，查不到查DB再回写；更新时先更新DB再删缓存 | 更新时一定先DB后删缓存 |
| 5 | @Cacheable sync | 单机互斥锁，防止缓存击穿 | 分布式环境需Redis分布式锁 |
| 6 | 多级缓存 | L1 Caffeine + L2 Redis | 注意L1一致性：Redis Pub/Sub通知失效 |
| 7 | BloomFilter | 判断元素"一定不在"或"可能在" | FPP（误判率），不支持删除 |

### 7.2 分库分表篇

| 序号 | 知识点 | 一句话总结 | 关键细节 |
|------|--------|-----------|----------|
| 8 | 水平分表 | 行拆分，结构相同，分片键路由 | 分片键选型是核心 |
| 9 | 垂直分表 | 列拆分，冷热分离 | 通常结合水平分表使用 |
| 10 | Inline策略 | `user_id % 4` 表达式 | 最常用，不支持范围查询 |
| 11 | 绑定表 | 关联表分片规则一致 | 避免跨分片JOIN |
| 12 | 广播表 | 每个库都有一份 | 字典表、配置表 |
| 13 | 雪花算法 | 64位Long ID，趋势递增 | 时间戳+机器ID+序列号 |
| 14 | 号段模式 | DB批量取号段，内存分配 | Leaf-segment，双buffer优化 |
| 15 | 读写分离 | 主库写，从库读 | 注意主从复制延迟导致"写后读"不一致 |

### 7.3 速记口诀

```

分库分表 分片键 要选好
```

## 8. 精通拓展补充-P2

### 8.1 热点分片问题 (Hotspot Sharding)

**问题**：某些分片键对应的分片数据量远大于其他分片，导致单分片成为瓶颈。

**解决方案**：
1. **双分片键 + 二级索引**：设计两个分片键，主分片键用于日常查询，辅助索引用于备用查询。
2. **分片键加盐 (Salting)**：在分片键后面拼接随机数字，使数据分布更均匀。例如 `user_id + random(0~9)` 再取模。
3. **读写分离分流**：热点分片增加从库数量，分散读压力。

```java
// 分片键加盐示例
// 将 user_id 加上一个0~9的随机后缀再取模
// 这样同一个用户的数据会分布在10个不同的子分片上
@Service
public class OrderSaltService {

    /**
     * 带盐的分片ID生成
     */
    public String buildShardingId(Long userId) {
        int salt = userId.hashCode() % 10;
        if (salt < 0) salt = -salt;
        return userId + "_" + salt;
    }

    /**
     * 插入数据时，按带盐的分片键写入
     */
    public void createOrderWithSalt(Order order) {
        // 带盐的分片键
        String shardKey = buildShardingId(order.getUserId());
        order.setShardKey(shardKey);
        orderMapper.insert(order);
    }

    /**
     * 查询时，需要查询所有盐值子分片再合并
     */
    public List<Order> getUserOrdersWithSalt(Long userId) {
        // 需要查询10个盐值子分片
        List<Order> allOrders = new ArrayList<>();
        for (int salt = 0; salt < 10; salt++) {
            String shardKey = userId + "_" + salt;
            allOrders.addAll(orderMapper.selectByShardKey(shardKey));
        }
        // 排序后返回
        allOrders.sort(Comparator.comparing(Order::getCreateTime).reversed());
        return allOrders;
    }
}
```

### 8.2 分布式ID扩展 — Leaf-segment 双缓冲

美团 Leaf 方案的号段模式中，双缓冲（Double Buffer）解决了号段用尽时阻塞的问题：

```
                          ┌───────────────────┐
                          │  Leaf Server       │
                          │                    │
     Segment A (当前使用)  │  segment: [1, 1000]│ ← 用掉20%时触发异步加载
                          │                    │
     Segment B (预热)      │  segment: [1001,   │ ← 后台准备好，切换使用
                          │            2000]    │
                          └───────────────────┘
```

核心思想：当当前号段消耗到一定比例（如20%）时，就异步去DB加载下一个号段，保证始终有一个"预热"的号段可用。

### 8.3 分布式缓存 vs 本地缓存的选择

| 场景 | 推荐方案 | 原因 |
|------|---------|------|
| 数据一致性要求高 | 只用Redis | 集中存储，无多副本一致性问题 |
| 热点数据读多写少 | Caffeine + Redis | 本地缓存扛热点，Redis做灾备 |
| 数据频繁更新 | 只用Redis | 避免频繁广播失效L1，增加复杂度 |
| 大规模集群（100+节点） | 只用Redis | 广播失效L1的成本太高 |
| 中小型集群（<20节点） | Caffeine + Redis | 性能提升明显，一致性可控 |

### 8.4 缓存预热 (Cache Warming)

系统上线或重启后，缓存是空的，此时大量请求直接打到数据库（缓存穿透的一种变体）。解决方案：

```java
@Component
public class CacheWarmUpRunner implements CommandLineRunner {

    @Autowired
    private ProductMapper productMapper;
    @Autowired
    private RedisTemplate<String, Object> redisTemplate;

    @Override
    public void run(String... args) {
        log.info("开始缓存预热...");
        StopWatch watch = new StopWatch();
        watch.start();

        // 预热商品缓存（加载前1000个商品）
        List<Product> hotProducts = productMapper.selectHotProducts(1000);
        for (Product product : hotProducts) {
            String key = "product:" + product.getId();
            redisTemplate.opsForValue().set(key, product, 1, TimeUnit.HOURS);
        }

        watch.stop();
        log.info("缓存预热完成，预热{}条数据，耗时{}ms",
            hotProducts.size(), watch.getTotalTimeMillis());
    }
}
```
