# 分布式事务入门

## 什么是分布式事务

单体应用中，`@Transactional` 即可保证 ACID。在微服务架构下，一个操作跨越多个服务的数据库，本地事务力不从心。

例：下单流程
1. 订单服务 → 创建订单（订单库）
2. 库存服务 → 扣减库存（库存库）
3. 积分服务 → 增加积分（积分库）

不能简单的 `@Transactional`，需要分布式事务。

## CAP 定理

分布式系统三者只能同时满足两个：

- **一致性（Consistency）**：所有节点同一时刻数据相同
- **可用性（Availability）**：每个请求都能得到响应（不保证是最新数据）
- **分区容错（Partition Tolerance）**：网络分区时系统仍能工作

P 是不可避免的（网络总会出问题），所以实际中在 C 和 A 之间选择：
- CP：保证一致性，牺牲可用性（ZooKeeper、Seata AT 模式）
- AP：保证可用性，接受最终一致（消息队列方案、Seata TCC 模式）

## 主流方案

### 1. 可靠消息最终一致性（推荐）

```
服务 A 更新 DB → 发消息到 MQ（同事务） → 服务 B 消费消息 → 更新自己的 DB
```

实现要点：本地事务表 + 消息表 + 定时补偿

```java
@Transactional
public void createOrder(Order order) {
    // 1. 写业务数据
    orderMapper.insert(order);
    // 2. 写本地消息表（同一个数据库事务）
    messageMapper.insert(new OutboxMessage("order-created", JSON.toJSONString(order), "PENDING"));
}

// 3. 定时任务扫描 PENDING 消息发送到 MQ
// 4. 消费端做幂等处理
```

这是最务实的方案，不需要额外框架。

### 2. Seata AT 模式

无侵入的分布式事务，对业务代码透明：

```java
@GlobalTransactional  // 替换 @Transactional
public void createOrder(Order order) {
    orderService.create(order);       // 远程调用 1
    inventoryService.deduct(order);   // 远程调用 2
    pointsService.addPoints(order);   // 远程调用 3
}
```

Seata 通过 undo_log 表实现自动回滚。AT 模式适合对一致性要求较高的场景。

### 3. TCC 模式（Try-Confirm-Cancel）

业务层手动实现两阶段提交：

```java
// Try：预留资源
boolean frozen = inventoryService.freezeStock(orderId, 1);

// Confirm：确认执行
inventoryService.confirmDeduct(orderId);

// Cancel：回滚释放
inventoryService.cancelFreeze(orderId);
```

TCC 适合资金、库存等严格要求的场景，但代码侵入大。

## 方案对比

| 方案 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|----------|
| MQ 最终一致 | 最终一致 | 高 | 低 | 大部分业务（推荐） |
| Seata AT | 强一致 | 中 | 低 | 需要强一致性 |
| Seata TCC | 强一致 | 中 | 高 | 资金/库存 |
| SAGA | 最终一致 | 高 | 中 | 长事务链 |

## 实战建议

作为校招阶段：
1. 理解 CAP 和 BASE 理论，面试能说清楚
2. 熟练掌握"本地事务表 + MQ"的最终一致性方案
3. 知道 Seata 是什么，能说出 AT、TCC 的区别
4. 实际项目优先设计成可接受最终一致性，而不是强套分布式事务
