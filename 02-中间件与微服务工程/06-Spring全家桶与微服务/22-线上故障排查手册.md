## 2. 循环依赖排查

### 2.1 现象
启动Spring Boot应用时出现如下异常：

```text
***************************
APPLICATION FAILED TO START
***************************

Description:
The dependencies of some of the beans in the application context form a cycle:

|  AService (field private BService com.example.AService.bService)
|      ^
|      |
|  BService (field private AService com.example.BService.aService)
```

或更底层的异常：

```text
BeanCurrentlyInCreationException: Error creating bean with name 'aService':
Requested bean is currently in creation: Is there an unresolvable circular reference?
```

### 2.2 根因分析
循环依赖本质上是一个**图论中的环**：Bean A 依赖 Bean B，Bean B 又依赖 Bean A，Spring 在创建时无法决定谁先谁后。

**三种类型的循环依赖：**

| 类型 | 是否可解决 | 说明 |
|------|-----------|------|
| **构造器注入** 循环依赖 | 不可解决 | Spring三级缓存无法处理构造器循环 |
| **Setter/字段注入** 循环依赖 | Spring可自动解决 | 通过三级缓存机制 |
| **prototype作用域** 循环依赖 | 不可解决 | 三级缓存只对单例有效 |

### 2.3 Spring三级缓存机制
Spring通过三级缓存来解决Setter注入的循环依赖：

```text
一级缓存: singletonObjects（成品池）
  Map<String, Object> 存储完全初始化好的单例Bean
  对外暴露，getBean()优先从这里获取

二级缓存: earlySingletonObjects（半成品池）
  Map<String, Object> 存储提前曝光的早期Bean引用
  此时Bean的属性可能还未填充完毕

三级缓存: singletonFactories（工厂池）
  Map<String, ObjectFactory<?>> 存储Bean工厂
  每个工厂可生成一个早期引用（通常含AOP逻辑）
```

**三级缓存工作流程（以A→B→A为例）：**

```text
1. getBean(A) -> singletonObjects无 -> 开始创建A
2. 实例化A（调用构造器）-> 得到一个原始A对象
3. 将A放入三级缓存: singletonFactories.put(A, factory)
4. 填充A属性 -> 发现依赖B -> getBean(B)
5. getBean(B) -> 进入B的创建流程
6. 实例化B -> 将B放入三级缓存
7. 填充B属性 -> 发现依赖A -> getBean(A)
8. getBean(A) -> 一级缓存没有 -> 二级缓存没有 -> 三级缓存有!
9. 从三级缓存取出factory.getObject() -> 得到A的早期引用
10. 放入二级缓存 -> 删除三级缓存中的A
11. B拿到A的引用 -> B初始化完成 -> B进入一级缓存
12. 回到A的创建流程 -> A拿到完整B -> A初始化完成 -> A进入一级缓存
13. 删除A在二级/三级缓存中的记录
```

> 关键点：三级缓存存的不是Bean实例，而是ObjectFactory，延迟了早期引用的创建时机。这在AOP场景下很关键——可以让AOP代理在真正需要时才创建。

### 2.4 排查步骤

#### 步骤1：启用Spring启动debug日志
在application.yml中开启：

```yaml
logging:
  level:
    org.springframework.beans.factory: DEBUG
    org.springframework.context: DEBUG
```

重启后可以看到Bean创建的完整链路。

#### 步骤2：分析依赖链路
观察异常信息中的循环链路，Spring已经清晰标出哪些Bean之间形成了循环。

#### 步骤3：使用IDE辅助分析
IntelliJ IDEA提供循环依赖检测功能：File -> Project Structure -> Facets -> Spring -> 勾选Circular dependency check，或在Spring Beans Diagram视图中查看。

#### 步骤4：使用--debug启动参数
```bash
java -jar myapp.jar --debug
```
输出大量Spring Boot自动配置和Bean创建日志。

### 2.5 解决方案

#### 方案1：使用@Lazy（推荐，快速修复）
```java
@Service
public class AService {
    @Lazy
    @Autowired
    private BService bService;

    public void doSomething() {
        bService.execute();
    }
}

@Service
public class BService {
    @Autowired
    private AService aService;

    public void execute() {
        aService.handle();
    }
}
```

#### 方案2：构造器注入改为Setter注入
```java
@Service
public class AService {
    private BService bService;

    @Autowired
    public void setBService(BService bService) {
        this.bService = bService;
    }
}

@Service
public class BService {
    private AService aService;

    @Autowired
    public void setAService(AService aService) {
        this.aService = aService;
    }
}
```

#### 方案3：接口分离，消除双向依赖
```java
public interface IUserService {
    User findById(Long id);
}

public interface IOrderService {
    List<Order> getOrdersByUserId(Long userId);
}

@Service
public class UserServiceImpl implements IUserService {
    @Autowired
    private IOrderService orderService;
}

@Service
public class OrderServiceImpl implements IOrderService {
    @Autowired
    private IUserService userService;
}
```

#### 方案4：使用@PostConstruct + ApplicationContext.getBean()
```java
@Component
public class AService {
    private BService bService;

    @Autowired
    private ApplicationContext applicationContext;

    @PostConstruct
    public void init() {
        this.bService = applicationContext.getBean(BService.class);
    }
}
```

### 2.6 预防措施

| 措施 | 说明 | 优先级 |
|------|------|--------|
| 架构设计 | 避免双向依赖，采用分层设计 | 最高 |
| 代码规范 | Service层只依赖下层（DAO），不互相依赖 | 高 |
| 构造器注入 | 强制使用构造器注入，启动时就发现循环依赖 | 高 |
| 接口依赖 | 面向接口而非实现类编程 | 中 |
| 定期检测 | 使用maven插件或IDE检测循环依赖 | 中 |

> 警告：在微服务架构中，循环依赖往往是设计问题的信号。如果一个服务内出现大量循环依赖，说明拆分粒度可能不合理。

## 3. 事务失效排查

### 3.1 现象
- 方法执行抛出异常，但数据已经写入数据库（未回滚）
- 部分回滚：异常前的数据修改生效，异常后的没有
- @Transactional注解看上去"没起作用"

### 3.2 8大事务失效场景

#### 场景1：自调用（同一类中方法调用）
```java
@Service
public class OrderService {

    public void createOrder(Order order) {
        // 调用本类中的另一个方法，事务失效！
        this.saveOrder(order);
    }

    @Transactional
    public void saveOrder(Order order) {
        orderDao.insert(order);
        // 如果这里抛出异常，上面insert不会回滚！
        throw new RuntimeException("模拟异常");
    }
}
```

**根因**：this.saveOrder()调用的是当前对象的方法，没有经过Spring代理，@Transactional不会生效。

**解决方案**：

```java
// 方案A：注入自己（循环依赖风险）
@Service
public class OrderService {
    @Autowired
    private OrderService self; // 注入代理对象

    public void createOrder(Order order) {
        self.saveOrder(order); // 通过代理调用
    }

    @Transactional
    public void saveOrder(Order order) {
        orderDao.insert(order);
        throw new RuntimeException("模拟异常");
    }
}

// 方案B：拆分为两个Service
@Service
public class OrderService {
    @Autowired
    private OrderDetailService detailService;

    public void createOrder(Order order) {
        detailService.saveOrder(order);
    }
}

// 方案C：使用TransactionTemplate（最安全）
@Service
public class OrderService {
    @Autowired
    private TransactionTemplate transactionTemplate;

    public void createOrder(Order order) {
        transactionTemplate.execute(status -> {
            orderDao.insert(order);
            // 非受检异常自动回滚
            throw new RuntimeException("回滚");
        });
    }
}
```

#### 场景2：方法不是public
```java
@Service
public class OrderService {
    @Transactional
    protected void saveOrder(Order order) { // protected -> 事务失效
        orderDao.insert(order);
    }

    @Transactional
    private void saveOrderPrivate(Order order) { // private -> 事务失效
        orderDao.insert(order);
    }
}
```

**根因**：Spring AOP基于JDK动态代理或CGLIB，只能拦截public方法。AbstractFallbackTransactionAttributeSource中会检查方法修饰符。

**解决方案**：改为public方法。

#### 场景3：传播行为配置错误
```java
@Service
public class OrderService {
    @Autowired
    private OrderDao orderDao;
    @Autowired
    private LogService logService;

    @Transactional
    public void createOrder(Order order) {
        orderDao.insert(order);
        logService.saveLog("创建订单: " + order.getId());
        throw new RuntimeException("回滚");
    }
}

@Service
public class LogService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveLog(String msg) {
        // 这里会开启一个新事务
        // 但是外部异常时，新事务已经独立提交，不会回滚
        logDao.insert(new Log(msg));
    }
}
```

**根因**：REQUIRES_NEW会挂起当前事务并创建新事务，新事务独立提交/回滚，不受外部事务影响。

#### 场景4：rollbackFor未设置
```java
@Service
public class OrderService {
    @Transactional // 默认只回滚RuntimeException和Error
    public void createOrder(Order order) throws SQLException {
        orderDao.insert(order);
        // SQLException是受检异常，不会触发回滚！
        throw new SQLException("数据库异常");
    }
}
```

**根因**：Spring默认只对RuntimeException和Error回滚，受检异常不会回滚。

**解决方案**：
```java
@Transactional(rollbackFor = Exception.class) // 对所有异常回滚
@Transactional(rollbackFor = SQLException.class) // 对特定异常回滚
@Transactional(rollbackFor = {SQLException.class, BusinessException.class})
```

#### 场景5：catch异常吞没
```java
@Service
public class OrderService {
    @Transactional
    public void createOrder(Order order) {
        try {
            orderDao.insert(order);
            // 模拟异常
            int i = 1 / 0;
        } catch (Exception e) {
            // 异常被捕获并吞没，事务框架感知不到异常，最终正常提交
            log.error("发生错误", e);
        }
    }
}
```

**根因**：Spring事务是通过AOP拦截方法抛出的异常来判断回滚的。如果异常被catch且不重新抛出，AOP拦截器看到的是正常返回，于是执行提交。

**解决方案**：
```java
@Transactional
public void createOrder(Order order) {
    try {
        orderDao.insert(order);
    } catch (Exception e) {
        log.error("发生错误", e);
        // 方案A：重新抛出（推荐）
        throw e;
        // 方案B：手动回滚
        // TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
    }
}
```

#### 场景6：多线程调用
```java
@Service
public class OrderService {
    @Autowired
    private OrderDao orderDao;

    @Transactional
    public void createOrder(Order order) {
        orderDao.insert(order);
        // 新线程中的事务独立于当前线程
        new Thread(() -> {
            orderDao.updateStock(order.getProductId(), -1); // 事务失效！
        }).start();
    }
}
```

**根因**：Spring事务基于ThreadLocal实现，每个线程拥有独立的事务上下文。新线程中的操作不在父线程的事务范围内。

**解决方案**：
```java
// 方案：将多线程操作提取为独立的@Transactional方法在子线程中调用
@Service
public class InventoryService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void updateStock(Long productId, int delta) {
        inventoryDao.updateStock(productId, delta);
    }
}
```

#### 场景7：不同数据源
```java
@Bean
@Primary
public DataSource orderDataSource() { ... }

@Bean
public DataSource reportDataSource() { ... }

// 事务默认绑定主数据源
@Transactional // -> 只管理orderDataSource的事务
public void createOrder(Order order) {
    orderDao.insert(order);       // orderDataSource -> 事务管理
    reportDao.saveReport(report); // reportDataSource -> 不在事务管理范围内
}
```

**根因**：一个@Transactional只能绑定一个DataSource的TransactionManager。

**解决方案**：
```java
@Transactional("reportTransactionManager")
public void createOrder(Order order) {
    orderDao.insert(order);
    reportDao.saveReport(report);
}

// 或使用分布式事务方案（Seata、Atomikos等）
```

#### 场景8：没有被Spring代理管理
```java
// 不是Spring Bean，@Transactional自然不生效
public class OrderService {
    @Transactional
    public void createOrder(Order order) { ... }
}

// 或者通过new直接创建，不是从容器获取
OrderService service = new OrderService();
service.createOrder(order); // 事务失效
```

### 3.3 排查步骤

#### 步骤1：启用事务日志
```yaml
logging:
  level:
    org.springframework.transaction: TRACE
    org.springframework.jdbc.datasource: TRACE
```

观察日志中是否有：
```text
Creating new transaction with name [...]
Acquired Connection [...] for JDBC transaction
Participating in existing transaction
Rolling back transaction
Committing transaction
```

如果连"Creating new transaction"都没有，说明事务根本没创建。

#### 步骤2：检查TransactionSynchronizationManager
```java
// 在代码中嵌入诊断逻辑
System.out.println("是否有事务: " + TransactionSynchronizationManager.isActualTransactionActive());
System.out.println("当前事务名称: " + TransactionSynchronizationManager.getCurrentTransactionName());
System.out.println("只读: " + TransactionSynchronizationManager.isCurrentTransactionReadOnly());
```

#### 步骤3：验证代理状态
```java
import org.springframework.aop.framework.AopUtils;

@Service
public class OrderService {

    @Transactional
    public void createOrder(Order order) {
        // 诊断：检查当前对象是否是代理
        System.out.println("是代理对象? " + AopUtils.isAopProxy(this));
        System.out.println("是CGLIB代理? " + AopUtils.isCglibProxy(this));
        System.out.println("是JDK动态代理? " + AopUtils.isJdkDynamicProxy(this));
    }
}
```

#### 步骤4：Debug断点检查
在org.springframework.transaction.interceptor.TransactionInterceptor.invoke()处打上断点，观察是否进入该方法。如果没进入，说明@Transactional在编译或加载阶段就未被识别。

### 3.4 TransactionTemplate替代方案
```java
@Service
public class OrderService {
    @Autowired
    private TransactionTemplate transactionTemplate;

    public void createOrder(Order order) {
        // 编程式事务，完全可控
        transactionTemplate.execute(status -> {
            try {
                orderDao.insert(order);
                // 其他操作...
                return true;
            } catch (Exception e) {
                status.setRollbackOnly(); // 手动回滚
                throw e;
            }
        });
    }

    public void createOrderWithResult(Order order) {
        Order result = transactionTemplate.execute(status -> {
            Order saved = orderDao.insert(order);
            if (saved == null) {
                status.setRollbackOnly();
                return null;
            }
            return saved;
        });
    }
}
```

### 3.5 预防措施

| 措施 | 说明 |
|------|------|
| 统一rollbackFor配置 | 全局配置rollbackFor = Exception.class |
| 禁止try-cache吞异常 | 如需catch，必须重新抛出或手动回滚 |
| 自调用检查 | 避免this.method()调用，注入self代理 |
| 事务日志监控 | 线上环境保留WARN级别事务日志 |
| 单元测试覆盖 | 每个@Transactional方法都有测试验证回滚 |
| 代码审查 | Code Review时重点看事务边界 |

> 提示：事务失效是线上最常见的问题之一。排查时可以按这个思路走：先看方法是不是public -> 再看是不是自调用 -> 再看异常有没有被吃 -> 再看rollbackFor -> 最后看是不是非Spring Bean。

## 4. AOP代理失效排查

### 4.1 现象
- 方法上标注了@Around/@Before等注解但增强逻辑不执行
- 事务不生效（事务本质是AOP）
- @Cacheable缓存不生效

### 4.2 JDK代理 vs CGLIB代理

| 特性 | JDK动态代理 | CGLIB代理 |
|------|-------------|-----------|
| 原理 | 基于接口生成代理类 | 基于继承生成子类代理 |
| 要求 | 目标类必须实现接口 | 无需接口 |
| 目标类要求 | 必须是接口实现类 | 不能是final类，方法不能是final |
| 生成速度 | 较快（反射机制） | 较慢（字节码生成） |
| 调用速度 | 较慢（反射调用） | 较快（直接调用） |
| Spring默认 | Spring Boot 2.x+默认CGLIB | Spring Boot 2.x+默认CGLIB |
| 配置方式 | @EnableAspectJAutoProxy | @EnableAspectJAutoProxy(proxyTargetClass=true) |

### 4.3 AOP失效常见原因

#### 原因1：自调用导致AOP失效
```java
@Service
public class UserService {

    public void createUser(User user) {
        // this.checkUser()调用的是原始对象的方法，不是代理对象
        // 所以checkUser上的@Cacheable不会生效
        this.checkUser(user);
        userDao.insert(user);
    }

    @Cacheable(cacheNames = "users", key = "#user.id")
    public User checkUser(User user) {
        // 模拟慢查询
        return userDao.findById(user.getId());
    }
}
```

**解决方案**：
```java
@Service
public class UserService {
    @Autowired
    private UserService self; // 注入代理对象

    public void createUser(User user) {
        // 通过代理对象调用，AOP生效
        self.checkUser(user);
        userDao.insert(user);
    }

    @Cacheable(cacheNames = "users", key = "#user.id")
    public User checkUser(User user) {
        return userDao.findById(user.getId());
    }
}
```

#### 原因2：类不在AOP扫描路径
```java
// 这个类不在Spring容器扫描路径中
@Component
public class MyAspect {
    @Around("execution(* com.example.service.*.*(..))")
    public Object around(ProceedingJoinPoint pjp) {
        // 永远不会执行
        return pjp.proceed();
    }
}
```

**解决方案**：确保Aspect类被Spring管理，且开启AspectJ支持：
```java

@ComponentScan("com.example")
public class AppConfig {
}
```

#### 原因3：final方法或final类
```java
@Service

    @Transactional
    public void createUser(User user) { ... }
}

@Service
public class UserService {
    @Transactional
    public final void createUser(User user) { // final方法 -> 无法被重写
        ...
    }
}
```

#### 原因4：@EnableAspectJAutoProxy缺失
```java
@SpringBootApplication
// @EnableAspectJAutoProxy // 缺失此注解 -> 自定义Aspect不生效
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

> 提示：Spring Boot 2.x+中如果使用@Aspect注解，通常还需要引入spring-boot-starter-aop，它自动配置了@EnableAspectJAutoProxy。

#### 原因5：切点表达式写错
```java

    // 路径写错了 -> 永远不匹配
    @Around("execution(* com.example.wrong.service.*.*(..))")

```

## 5. Feign调用超时排查

### 5.1 现象
- 服务间调用时出现Read timed out或Connect timed out异常
- 接口偶尔超时、请求缓慢
- 调用链路上游服务报错，下游服务实际已经完成处理

```text
feign.RetryableException: Read timed out executing GET http://order-service/api/orders/1001
    at feign.FeignException.errorExecuting(FeignException.java:249)

Caused by: java.net.SocketTimeoutException: Read timed out
    at java.net.SocketInputStream.socketRead0(Native Method)
```

### 5.2 根因分析

#### connectTimeout vs readTimeout

| 参数 | 含义 | 默认值 | 触发条件 |
|------|------|--------|----------|
| connectTimeout | 建立TCP连接的超时时间 | 10秒 | 目标服务不可达、网络不通、防火墙拦截 |
| readTimeout | 建立连接后等待响应的超时时间 | 60秒 | 目标服务处理慢、响应数据量大、网络延迟高 |

#### Double Timeout问题（Feign + Hystrix/Sentinel）

当同时使用Feign和Hystrix/Sentinel时，会出现**多层超时**问题：

```text
客户端请求
  -> Feign（connectTimeout: 5s, readTimeout: 10s）
    -> Hystrix（execution.isolation.thread.timeoutInMilliseconds: 1000ms -> 1秒就熔断了！）
```

> 关键：Feign的超时 > Hystrix的超时，否则Hystrix已经熔断Feign还在等待。默认Hystrix超时是1秒，而Feign默认readTimeout是60秒。

#### Feign重试机制

```java
// 默认Retryer
// Default(100, SECONDS.toMillis(1), 5) -> 最多重试5次，每次间隔1秒
// 重试可能导致接口幂等性问题
```

### 5.3 排查步骤

#### 步骤1：开启Feign日志
```yaml

  level:
    com.example.order.client: DEBUG  # Feign Client接口包名

  client:
    config:
      default:
        loggerLevel: FULL  # NONE | BASIC | HEADERS | FULL
```

日志输出示例：
```text

[OrderServiceClient#getOrder] ---> END HTTP (0-byte body)
[OrderServiceClient#getOrder] <--- HTTP/1.1 200 (5234ms)  # 5234ms -> 耗时
[OrderServiceClient#getOrder] <--- END HTTP (328-byte body)
```

```java
        }
```
```java
    };

```

| 措施 | 说明 |
|------|------|
| 统一超时配置 | 建立Feign超时配置规范，避免各自设置 |
| 调用链监控 | 接入Zipkin/Skywalking监控全链路耗时 |
| 熔断降级 | 配置Hystrix/Sentinel熔断，防止级联故障 |
| 超时阶梯 | Feign > Hystrix > 网关 > 客户端，层层递增 |
| 幂等设计 | 接口天然幂等，支持重试 |

> 提示：Feign超时排查口诀——"先看日志级别够不够，再看超时配没配对，三看Hystrix是不是更小，最后抓包看网络。"

## 6. Nacos服务注册排查

### 6.1 现象
- 服务启动后，Nacos控制台看不到服务
- 服务间歇性从Nacos上下线
- 服务消费者报错：No available instances for service xxx
- 服务列表显示服务健康但实际调用失败

```text
Caused by: java.lang.IllegalStateException: No available instance for service order-service
    at com.alibaba.nacos.client.naming.NacosNamingService.selectOneHealthyInstance(NacosNamingService.java:132)
```

### 6.2 根因分析

#### 常见原因

| 原因 | 说明 | 频率 |
|------|------|------|
| 网络不通 | 服务无法连接Nacos Server | 高 |
| 心跳超时 | 服务未按时发送心跳，被Nacos踢出 | 高 |
| 命名空间不一致 | 服务提供者和消费者在不同namespace | 中 |
| 分组不一致 | 服务提供者和消费者在不同group | 中 |
| 集群名不一致 | 服务注册在不同集群 | 低 |
| 元数据异常 | 元数据配置导致路由异常 | 低 |
| 端口冲突 | 服务端口被占用导致启动失败 | 低 |

#### Nacos心跳机制

```text
服务实例
  |--- 每5秒发送一次心跳（beat）---> Nacos Server
  |                                    |
  |<--- 心跳响应（更新最后心跳时间）---   |
  |                                    |
  |--- 15秒未收到心跳 ---> 标记为不健康   |
  |--- 30秒未收到心跳 ---> 从服务列表移除  |
```

#### 关键参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| heart-beat-interval | 5秒 | 心跳发送间隔 |
| heart-beat-timeout | 15秒 | 心跳超时，超过标记为不健康 |
| ip-delete-timeout | 30秒 | 超过此时间未收到心跳删除实例 |
| instance-enabled | true | 实例是否可用 |

## 7. 内存泄漏排查

### 7.1 现象
- 应用运行一段时间后响应变慢，最终OOM
- 堆内存使用率持续上升，GC无法回收
- GC日志显示Full GC后老年代占用不降
- jstat显示O区（老年代）持续增长
- 出现 java.lang.OutOfMemoryError: Java heap space 或 GC overhead limit exceeded

### 7.2 常见内存泄漏模式

#### 模式1：ThreadLocal未清理
```java
@Component
public class RequestContextHolder {
    private static final ThreadLocal<User> userThreadLocal = new ThreadLocal<>();

    public void setUser(User user) {
        userThreadLocal.set(user);
    }

    public User getUser() {
        return userThreadLocal.get();
    }

    // 没有remove方法！线程池中的线程复用导致用户对象无法释放
}

// 使用线程池时，线程执行完任务后不会销毁
// ThreadLocal中的对象一直被线程持有引用，无法GC回收
// 随着请求增多，内存持续增长
```

**解决方案**：
```java
@Component
public class RequestContextHolder {
    private static final ThreadLocal<User> userThreadLocal = new ThreadLocal<>();

    public void setUser(User user) {
        userThreadLocal.set(user);
    }

    public User getUser() {
        return userThreadLocal.get();
    }

    public void remove() {
        userThreadLocal.remove();
    }
}

// 在Filter中使用try-finally确保清理
@Component
public class ContextFilter implements Filter {
    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
        try {
            // 设置上下文
            contextHolder.setUser(currentUser);
            chain.doFilter(request, response);
        } finally {
            // 确保清理
            contextHolder.remove();
        }
    }
}
```

#### 模式2：静态集合类
```java
@Component
public class CacheManager {
    // 静态Map，只增不减
    private static final Map<String, Object> cache = new HashMap<>();

    public void put(String key, Object value) {
        cache.put(key, value);
    }

    public Object get(String key) {
        return cache.get(key);
    }
    // 没有淘汰机制 -> OOM
}
```

**解决方案**：
```java
@Component
public class CacheManager {
    // 使用弱引用或限容Map
    private static final Map<String, Object> cache = new WeakHashMap<>();
    // 或使用Guava Cache
    // private static final Cache<String, Object> cache = Caffeine.newBuilder()
    //     .maximumSize(1000)
    //     .expireAfterWrite(10, TimeUnit.MINUTES)
    //     .build();
}
```

#### 模式3：未关闭连接/流
```java
@Component
public class FileProcessor {
    public void process(String path) throws IOException {
        // InputStream未关闭 -> 文件描述符泄漏
        FileInputStream fis = new FileInputStream(path);
        byte[] data = new byte[1024];
        fis.read(data);
        // 遗漏 fis.close();
    }
}

// 数据库连接未关闭
@Mapper
public interface UserMapper {
    @Select("SELECT * FROM user")
    List<User> findAll();
    // MyBatis会管理连接，但自定义的Connection必须手动关闭
}
```

**解决方案**：
```java
// 使用try-with-resources（JDK 7+）
public void process(String path) throws IOException {
    try (FileInputStream fis = new FileInputStream(path);
         BufferedInputStream bis = new BufferedInputStream(fis)) {
        byte[] data = new byte[1024];
        bis.read(data);
    } // 自动关闭
}
```

#### 模式4：内部类持有外部类引用
```java
@Component
public class OrderService {
    private byte[] bigData = new byte[100 * 1024 * 1024]; // 100MB

    class OrderProcessor {
        public void process(Order order) {
            // 非静态内部类持有外部类OrderService的隐式引用
            // 即使OrderService不再使用，只要OrderProcessor被引用，100MB就无法回收
            System.out.println("Processing: " + order.getId());
        }
    }
}
```

**解决方案**：
```java
@Component
public class OrderService {
    private byte[] bigData = new byte[100 * 1024 * 1024];

    // 改成静态内部类
    static class OrderProcessor {
        public void process(Order order) {
            System.out.println("Processing: " + order.getId());
        }
    }
}
```

#### 模式5：ClassLoader泄漏
```java
// 常见于Tomcat热部署、OSGI、自定义ClassLoader场景
// 每次重新部署时，新的ClassLoader加载新的类
// 旧的ClassLoader如果被某个对象引用，则整个类加载的所有类都无法卸载
// 导致Metaspace/OOM: PermGen space

// 典型场景：SPI、Thread.setContextClassLoader()未恢复
// 日志框架、第三方库缓存了ClassLoader引用
```

### 7.3 排查步骤

#### 步骤1：配置OOM时自动导出Heap Dump

## 8. GC频繁排查

### 8.1 现象
- 应用响应延迟明显增加，P99升高
- CPU使用率偏高（GC线程占用了大量CPU）
- JVM监控显示GC频率高，单次GC时间长
- System CPU和User CPU都高，但业务线程的CPU占比不高
- 出现GC overhead limit exceeded异常

```text
Exception in thread "http-nio-8080-exec-8" java.lang.OutOfMemoryError: GC overhead limit exceeded
```

### 8.2 GC指标理解

| 指标 | 含义 | 健康值 |
|------|------|--------|
| Young GC频率 | 对象从Eden区晋升到Survivor/Old的频率 | < 10次/秒 |
| Young GC耗时 | 每次Minor GC的停顿时间 | < 50ms |
| Full GC频率 | 老年代GC的频率 | 最好为0，或数小时一次 |
| Full GC耗时 | 每次Major GC的停顿时间 | < 1秒 |
| GC吞吐量 | 应用运行时间 / (应用运行时间 + GC时间) | > 99% |
| 晋升速率 | 对象从Young晋升到Old的速率 | 平稳 |

#### 步骤1：开启GC日志

### 8.4 常见GC问题模式

#### 模式1：Young GC频繁
**现象**：YGC每秒多次，每次几十毫秒

**根因**：Eden区过小，对象分配速率高，短期对象快速填满Eden

**解决方案**：
```bash
# 增大Eden空间（-Xmn或-XX:NewRatio）
-Xmn4096m           # 设置年轻代大小为4GB
-XX:NewRatio=2      # 老年代:年轻代 = 2:1
-XX:SurvivorRatio=8 # Eden:Survivor = 8:1:1

# 调整对象晋升阈值
-XX:MaxTenuringThreshold=15  # 最大晋升阈值
-XX:TargetSurvivorRatio=90   # Survivor使用率目标
```

#### 模式2：Full GC频繁
**现象**：FGC频繁，每次耗时几秒

**根因分析**：
- 老年代空间不足
- 大对象直接进入老年代
- 内存泄漏导致老年代持续增长
- CMS GC时出现Concurrent Mode Failure

**解决方案**：
```bash
# 调整堆大小
-Xms8g -Xmx8g        # 设置堆初始和最大为8GB

# CMS模式下
-XX:CMSInitiatingOccupancyFraction=70  # 老年代70%时开始CMS
-XX:+UseCMSInitiatingOccupancyOnly     # 只使用此阈值

# G1模式下
-XX:InitiatingHeapOccupancyPercent=45  # 触发Mixed GC的堆占用百分比
-XX:G1HeapRegionSize=4m                # Region大小
-XX:MaxGCPauseMillis=200               # 目标最大停顿时间
```

#### 模式3：CMS Concurrent Mode Failure
**现象**：CMS GC正在进行时，老年代被填满，触发Serial Old GC（单线程Full GC）

**根因**：CMS回收速度 < 对象分配速度

**解决方案**：
```bash
# 提前触发CMS
-XX:CMSInitiatingOccupancyFraction=60  # 从默认92%降到60%
-XX:+UseCMSInitiatingOccupancyOnly

# 增加CMS线程数
-XX:ParallelCMSThreads=8

# 优化对象分配，减少大对象
```

#### 模式4：G1 Mixed GC频繁
**现象**：Mixed GC频繁触发，但Region回收效率低

**根因分析**：G1的RSet过大，或存活对象比例高

**解决方案**：
```bash
# 调整Region大小
-XX:G1HeapRegionSize=8m

# 调整Mixed GC触发阈值
-XX:G1MixedGCLiveThresholdPercent=85  # Region存活对象超过85%时不回收

# 增加并发线程
-XX:ConcGCThreads=8
```

### 8.5 GC调优决策树

```text
GC频繁？
├── 看jstat -gcutil
│   ├── FGC > 0 ?
│   │   ├── YES -> 老年代O区占用?
│   │   │   ├── O区接近100% -> 内存泄漏? -> MAT分析Heap Dump
│   │   │   │                      └─ 非泄漏 -> 增大-Xmx
│   │   │   └── O区一般 -> CMS concurrent mode failure?
│   │   │       └── 降低CMSInitiatingOccupancyFraction
│   │   └── NO -> 看YGC频率和耗时
│   │
│   └── YGC频繁?
│       ├── Eden区小? -> 增大-Xmn
│       ├── 对象分配快? -> 检查是否频繁创建对象
│       │   └── 代码中String拼接? -> StringBuilder
│       │   └── 频繁new对象? -> 对象池/缓存
│       └── Survivor区太小? -> 调整SurvivorRatio
│
└── GC停顿时间长?
    ├── CMS -> 调整-XX:CMSInitiatingOccupancyFraction
    ├── G1 -> 调整-XX:MaxGCPauseMillis
    └── Parallel -> 调整-XX:ParallelGCThreads
```

## 10. CPU飙升排查

### 10.1 现象
- 服务器CPU使用率飙升至100%
- Load Average急剧升高（通常CPU核数的2倍以上）
- 应用响应极慢，甚至完全无响应
- 监控告警：CPU使用率超过阈值

### 10.2 根因分析

| 原因 | 特征 | 定位方式 |
|------|------|----------|
| 死循环/空转 | 业务线程CPU 100%，堆栈在某个方法内循环 | jstack分析 |
| 频繁GC | GC线程占用大量CPU | jstat看GC频率 |
| 死锁 | 线程互相等待，但CPU不一定高 | jstack检测deadlock |
| 正则回溯 | 输入构造导致正则匹配灾难性回溯 | jstack堆栈在Pattern |
| 序列化/反序列化 | 大数据量序列化耗时高 | trace序列化方法 |
| 线程上下文切换 | 线程数过多导致切换频繁 | vmstat 1观察context switch |

### 10.3 排查步骤（详细）

## 12. 高频踩坑与误区

### 误区1：认为@Transactional一定会回滚
```java
// 错误认知：只要加了@Transactional，任何异常都会回滚
@Transactional
public void createOrder(Order order) throws Exception {
    orderDao.insert(order);
    // 受检异常不会回滚！
    throw new Exception("业务异常");
}
```
**真相**：@Transactional默认只回滚RuntimeException和Error，受检异常不会回滚。
**正确做法**：显式指定`rollbackFor = Exception.class`。

### 误区2：日志中"Committing transaction"不代表数据已提交
```text
[TransactionInterceptor] Committing transaction after method execution
```
**真相**：这句话只表示Spring向底层事务管理器发出了commit指令。如果后面紧跟异常（如数据库连接断开），实际可能提交失败。要看最终数据库是否提交成功。

### 误区3：生产环境开启DEBUG日志
**问题**：有人在线上直接修改logback配置到DEBUG级别，导致磁盘被日志打满，应用OOM。
**正确做法**：使用Arthas的`logger --level INFO --name ROOT`动态调整，或使用`ognl`命令临时输出。不要直接改日志配置为DEBUG。

### 误区4：jmap -dump导致应用长时间STW
```bash
# 致命操作：在业务高峰期执行
jmap -dump:format=b,file=heap.hprof <pid>
```
**真相**：jmap导出Heap Dump时会触发Full GC，导致应用长时间停顿（STW）。堆越大，停顿越长。8GB堆可能停顿10-30秒。
**正确做法**：
```bash
# 使用jcmd（JDK 8+）
jcmd <pid> GC.heap_dump /path/to/heap.hprof

# 或使用gcore + jmap（先core dump，再离线分析）
gcore <pid>
jmap -dump:format=b,file=heap.hprof /usr/bin/java core.<pid>

# 或者使用MAT的自动导出（通过-XX:+HeapDumpOnOutOfMemoryError）
```

### 误区5：直接kill -9杀掉Java进程
**问题**：直接kill -9不会执行JVM的ShutdownHook，可能导致文件未关闭、事务未提交、注册中心未反注册等。
**正确做法**：
```bash
# 先尝试优雅关闭
kill <pid>
# 或通过应用的健康检查接口
curl -X POST http://localhost:8080/actuator/shutdown

# 等几秒后如果还没关闭，再强制杀
kill -9 <pid>
```

### 误区6：生产环境使用Arthas trace所有方法
```bash
# 危险操作：在生产环境trace无限制
trace com.example.*.* *
```
**真相**：Arthas的trace基于字节码增强，trace大量方法会产生大量开销，影响性能。
**正确做法**：精准trace，用完即停（`stop`或`shutdown`命令）。

### 误区7：Feign和Hystrix超时只配一个就行
**问题**：只配了Feign超时10秒，Hystrix默认1秒就熔断了。或者只配了Hystrix超时5秒，Feign默认60秒耗着。
**正解**：Feign超时 < Hystrix超时，且两个都要显式配置。

### 误区8：循环依赖就是代码有问题
**问题**：看到循环依赖就觉得架构设计有问题。
**正解**：Setter注入的循环依赖Spring可以处理。真正需要关注的是"构造器注入循环依赖"和"多模块间的循环依赖"。

### 误区9：OOM一定是内存泄漏
**问题**：应用OOM就认为是内存泄漏。
**正解**：也可能是以下情况：
- 业务高峰期对象分配速率过高，堆太小
- 单个请求处理大对象（如大文件导出）
- 元空间（Metaspace）被ClassLoader撑满
- 堆外内存（Direct Buffer）泄漏
- 线程栈过多（每个线程占用1MB）

### 误区10：GC调优就是调堆大小
**问题**：认为GC调优就是调Xmx和Xms。
**正解**：GC调优是系统性的：
- 先分析代码：减少对象创建，优化数据结构
- 再分析GC日志：确定是YGC频繁还是FGC频繁
- 再选择GC算法：CMS、G1、ZGC各有适用场景
- 最后调整参数：堆大小、代比例、触发阈值

```text
# 异常1：Feign超时
feign.RetryableException: Read timed out executing POST http://inventory-service/api/deduct
    at feign.FeignException.errorExecuting(FeignException.java:249)

# 异常2：事务异常
org.springframework.transaction.UnexpectedRollbackException:
    Transaction silently rolled back because it has been marked as rollback-only

# 异常3：Nacos异常
java.lang.IllegalStateException: No available instance for service payment-service

# 异常4：数据库异常
org.springframework.dao.DataIntegrityViolationException:
    Duplicate entry '12345' for key 'order_id'
```

**第二阶段：逐个分析**

**分析异常1：Feign超时**

检查Feign配置发现：
```yaml
feign:
  hystrix:
    enabled: true
  client:
    config:
      default:
        connectTimeout: 5000
        readTimeout: 10000
```

检查Hystrix配置发现——没有配置！使用默认值：
```text
Hystrix默认超时: 1000ms (1秒)
```

找到问题了！Feign readTimeout=10秒，但Hystrix超时=1秒。结果Hystrix在1秒后熔断，Feign重试机制再次发起请求（retry默认5次），每次都在1秒后熔断，导致请求失败和重复提交。

**分析异常2：UnexpectedRollbackException**

查看代码：
```java
@Service
public class OrderService {
    @Autowired
    private InventoryClient inventoryClient;

    @Transactional
    public Order createOrder(Order order) {
        orderDao.insert(order);

        try {
            // Feign调用可能抛出异常
            inventoryClient.deductStock(order.getProductId(), order.getQuantity());
        } catch (Exception e) {
            log.error("库存扣减失败", e);
            // 这里catch了异常但没标记回滚
            // 事务继续提交，但Hystrix可能已经标记了事务为rollback-only
        }

        return order;
    }
}
```

问题：Hystrix熔断时可能将当前事务标记为rollback-only，但代码中catch了异常继续执行。当事务提交时发现已被标记为rollback-only，抛出UnexpectedRollbackException。

**分析异常3：Nacos无可用实例**

检查Nacos控制台发现：payment-service在高峰期频繁上下线。

进一步排查发现：
```yaml
spring:
  cloud:
    nacos:
      discovery:
        heartbeat-timeout: 5000  # 5秒超时
```

Pod在CPU负载高时，GC停顿超过5秒，导致心跳发送超时，Nacos将实例标记为不健康。负载降低后心跳恢复，实例重新上线。频繁上下线导致消费者获取到的实例列表不稳定。

**分析异常4：数据重复**

结合Feign重试机制（默认最多5次，间隔1秒），加上Hystrix熔断后Feign重试，导致同一笔订单请求被多次发送到order-service。虽然订单表有唯一索引，但第一次请求的事务回滚后唯一索引约束被释放，第二次请求进来时创建了新的订单号，但用户侧的支付已经扣款。

#### 根因总结

```text
根因1: Hystrix超时(1s) < Feign超时(10s) -> 提前熔断 -> 触发Feign重试
根因2: Feign重试 -> 重复请求 -> 数据重复/唯一键冲突
根因3: Hystrix标记rollback-only + catch吞异常 -> UnexpectedRollbackException
根因4: GC停顿 > 5秒 -> Nacos心跳超时 -> 实例频繁上下线
```

#### 解决方案

**修复1：统一超时配置**
```yaml
feign:
  client:
    config:
      default:
        connectTimeout: 3000
        readTimeout: 5000

hystrix:
  command:
    default:
      execution:
        isolation:
          thread:
            timeoutInMilliseconds: 8000  # > Feign的5000ms
```

**修复2：关闭Feign重试，改为业务层可控重试**
```java
@Bean
public Retryer feignRetryer() {
    return Retryer.NEVER_RETRY;  // 关闭Feign重试
}
```

**修复3：修改事务代码，正确处理异常**
```java
@Transactional
public Order createOrder(Order order) {
    orderDao.insert(order);

    try {
        inventoryClient.deductStock(order.getProductId(), order.getQuantity());
    } catch (Exception e) {
        log.error("库存扣减失败", e);
        // 手动标记回滚
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        throw new BusinessException("库存扣减失败", e);  // 重新抛出
    }

    return order;
}
```

**修复4：增大Nacos心跳超时，增加GC停顿容忍度**
```yaml
spring:
  cloud:
    nacos:
      discovery:
        heart-beat-interval: 3000     # 3秒发送一次
        heart-beat-timeout: 12000     # 12秒超时（容忍GC停顿）
        ip-delete-timeout: 30000      # 30秒删除实例
```

**修复5：引入分布式链路追踪**
```yaml
spring:
  zipkin:
    base-url: http://zipkin:9411
  sleuth:
    sampler:
      probability: 1.0
```

#### 案例启示

1. **超时配置要统一管理**：Feign、Hystrix、Sentinel、网关的超时要形成"阶梯"。
2. **异常处理不能吞**：事务中的异常必须抛出或手动标记回滚。
3. **重试要考虑幂等**：不确定幂等的接口不要开重试。
4. **基础设施容错**：GC停顿可能影响注册中心心跳，要留够buffer。
5. **排查要全面**：孤立看每个异常似乎都不严重，但组合起来就是"诡异"故障。

### 17.1 Java Flight Recorder (JFR)

JFR是Oracle JDK自带的**低开销**事件收集框架，设计目标是生产环境可用。

#### 开启JFR

```bash
# 启动时开启JFR（JDK 8u40+ 需商业授权，JDK 11+ 开源免费）
java -XX:StartFlightRecording=name=myrecording,filename=/path/to/recording.jfr,duration=60s,settings=profile -jar app.jar

# 运行时动态开启（通过jcmd）
jcmd <pid> JFR.start name=myrecording duration=60s filename=/path/to/recording.jfr settings=profile

# 动态停止
jcmd <pid> JFR.stop name=myrecording

# 查看JFR状态
jcmd <pid> JFR.check
```

#### JFR分析内容

| 事件类型 | 分析目标 | 说明 |
|----------|----------|------|
| GC Events | GC频率、停顿时间 | 替代GC日志 |
| Allocation | 对象分配热点 | 找到高频分配的对象和位置 |
| Thread Sleep/Block | 线程等待原因 | 定位锁竞争 |
| File/Socket IO | IO耗时 | 定位IO瓶颈 |
| Class Loading | 类加载 | 排查ClassLoader泄漏 |
| Code Cache | JIT编译 | 检查编译状态 |
| Exception | 异常抛出 | 发现高频异常 |


### 17.4 OOM Killer与容器内存

#### Linux OOM Killer

当系统内存不足时，Linux内核会调用OOM Killer选择进程杀掉。

```bash
# 查看进程被OOM Killer杀掉的日志
dmesg | grep -i "killed process"

# 输出示例
# [12345.678] Killed process 12345 (java) total-vm:12345678kB, anon-rss:8765432kB, file-rss:1234kB

# 调整OOM Killer分数
# /proc/<pid>/oom_score_adj 范围 -1000 ~ 1000
# -1000 表示禁用OOM Killer
```

#### 容器环境内存限制

```yaml
# Kubernetes Pod内存限制
resources:
  requests:
    memory: "4Gi"
  limits:
    memory: "4Gi"
```

**容器内存坑点**：
```bash
# 问题：Pod设置memory limit=4G，但JVM看不到cgroup限制
# 如果jvm的-Xmx设置为4G，加上JVM本身开销、堆外内存、线程栈，
# 总内存可能超过4G被OOM Killer杀掉

# 解决方案：JDK 8u131+ 支持 -XX:+UseCGroupMemoryLimitForHeap
# JDK 10+ 自动识别容器内存限制

# 关键JVM参数（容器环境）
-XX:+UseContainerSupport           # JDK 10+，自动识别容器限制
-XX:InitialRAMPercentage=50.0      # 初始堆占容器内存50%
-XX:MaxRAMPercentage=75.0          # 最大堆占容器内存75%
-XX:MinRAMPercentage=50.0          # 最小堆占容器内存50%
```
