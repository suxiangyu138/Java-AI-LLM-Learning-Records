### 2.1 Spring @Scheduled（单机调度）

#### 2.1.1 @Scheduled 注解基本用法

Spring 提供 `@Scheduled` 注解，配合 `@EnableScheduling` 开启定时任务支持，适用于单机应用。

```java
@SpringBootApplication
@EnableScheduling  // 开启定时任务
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

#### 2.1.2 三种调度模式

| 模式 | 属性 | 说明 | 案例 |
|------|------|------|------|
| **固定频率** | `fixedRate` | 上一次 **开始** 执行后，等待固定毫秒再执行下一次 | `fixedRate = 5000` |
| **固定延迟** | `fixedDelay` | 上一次 **结束** 执行后，等待固定毫秒再执行下一次 | `fixedDelay = 5000` |
| **Cron表达式** | `cron` | 基于cron表达式灵活调度 | `cron = "0 0/5 * * * ?"` |

```java
@Component
public class ScheduledTasks {

    // 固定频率：每5秒执行一次（不关心上次是否完成）
    @Scheduled(fixedRate = 5000)
    public void reportCurrentTime() {
        System.out.println("Fixed Rate Task: " + LocalTime.now());
    }

    // 固定延迟：上次执行结束后延迟3秒再执行
    @Scheduled(fixedDelay = 3000)
    public void runAfterPreviousEnd() {
        System.out.println("Fixed Delay Task: " + LocalTime.now());
    }

    // 指定初始延迟：应用启动后延迟10秒首次执行
    @Scheduled(initialDelay = 10000, fixedRate = 5000)
    public void delayedStartTask() {
        System.out.println("Delayed Start Task: " + LocalTime.now());
    }

    // Cron表达式：每天中午12点执行
    @Scheduled(cron = "0 0 12 * * ?")
    public void cronTask() {
        System.out.println("Cron Task: 每天中午12点执行");
    }
}
```

> ⚠️ 默认情况下，`@Scheduled` 任务使用 **单线程线程池** 执行，一个任务阻塞会导致所有任务无法执行。详见下方踩坑章节。

#### 2.1.3 Cron表达式完全参考

Cron表达式由 **6~7个字段** 组成，以空格分隔：

```
 ┌───────── 秒 (0-59)
 │ ┌───────── 分 (0-59)
 │ │ ┌───────── 时 (0-23)
 │ │ │ ┌───────── 日 (1-31)
 │ │ │ │ ┌───────── 月 (1-12)
 │ │ │ │ │ ┌───────── 星期 (0-7, 0和7都代表SUN)
 │ │ │ │ │ │
 * * * * * *
```

| 字段 | 必需 | 取值范围 | 通配符 |
|------|------|----------|--------|
| 秒 | 是 | 0-59 | `,` `-` `*` `/` |
| 分 | 是 | 0-59 | `,` `-` `*` `/` |
| 时 | 是 | 0-23 | `,` `-` `*` `/` |
| 日 | 是 | 1-31 | `,` `-` `*` `/` `?` `L` `W` |
| 月 | 是 | 1-12 或 JAN-DEC | `,` `-` `*` `/` |
| 星期 | 是 | 0-7 或 SUN-SAT | `,` `-` `*` `/` `?` `L` `#` |
| 年 | 否 | 1970-2099 | `,` `-` `*` `/` |

**通配符说明**：

| 符号 | 含义 | 示例 |
|------|------|------|
| `*` | 所有值 | `*` 表示每一秒 |
| `?` | 不指定（日和星期互斥） | `0 0 12 ? * MON` 每月周一中午，不指定具体日 |
| `-` | 范围 | `10-15` 表示10到15区间 |
| `,` | 枚举 | `MON,WED,FRI` 表示周一、三、五 |
| `/` | 步长 | `0/5` 表示从0开始每5个单位 |
| `L` | 最后 | `L` 在日字段表示月末最后一天，在星期字段表示周六 |
| `W` | 最近工作日 | `15W` 表示15号最近的工作日 |
| `#` | 第N个星期几 | `2#1` 表示第一个周一 |

**常用Cron表达式参考表**：

| 表达式 | 含义 |
|--------|------|
| `0/5 * * * * ?` | 每5秒执行 |
| `0 0/1 * * * ?` | 每分钟执行 |
| `0 0 0/1 * * ?` | 每小时执行（整点） |
| `0 0 9,18 * * ?` | 每天9点和18点执行 |
| `0 0 2 * * ?` | 每天凌晨2点执行 |
| `0 0 0 * * ?` | 每天午夜执行 |
| `0 30 23 * * ?` | 每天23:30执行 |
| `0 0 0 1 * ?` | 每月1号零点执行 |
| `0 0 0 L * ?` | 每月最后一天零点执行 |
| `0 0 0 ? * MON` | 每周一零点执行 |
| `0 0 0 ? * 1#1` | 每月第一个周日零点执行 |
| `0 0 0 1 1 ?` | 每年1月1日零点执行 |
| `0 0/30 9-17 * * ?` | 朝九晚五，每半小时执行 |
| `0 0 0-8 * * ?` | 每天0点到8点，每小时执行 |

> 💡 **7字段cron**（带年）：`0 0 12 * * ? 2026` 表示只在2026年每天中午12点执行。Spring默认使用6字段cron（不含年），Quartz支持7字段。

#### 2.1.4 ThreadPoolTaskScheduler 配置

**问题**：`@Scheduled` 默认使用 `org.springframework.scheduling.concurrent.ThreadPoolTaskScheduler`，但线程池大小为 **1**。多个 `@Scheduled` 方法如果有一个阻塞，全部任务都会卡住。

```java
// 默认配置：单线程执行，一个任务阻塞 = 全部任务阻塞
@Scheduled(fixedRate = 1000)
public void taskA() throws InterruptedException {
    Thread.sleep(10000);  // taskA 执行10秒，taskB 无法调度
}

@Scheduled(fixedRate = 1000)
public void taskB() {
    // 此方法无法每秒执行，必须等 taskA 释放线程
}
```

**解决方案**：自定义 TaskScheduler Bean 配置线程池。

```java
@Configuration
@EnableScheduling
public class SchedulingConfig {

    @Bean
    public TaskScheduler taskScheduler() {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(10);                          // 核心线程数
        scheduler.setThreadNamePrefix("scheduled-task-");   // 线程名前缀
        scheduler.setAwaitTerminationSeconds(60);            // 优雅关闭等待时间
        scheduler.setWaitForTasksToCompleteOnShutdown(true); // 关闭时等待任务完成
        scheduler.setRejectedExecutionHandler(
            new ThreadPoolExecutor.CallerRunsPolicy()       // 拒绝策略：调用者线程执行
        );
        return scheduler;
    }
}
```

> 💡 **核心参数**：`poolSize` 决定并行任务数量，不等于cron任务数量。建议设置为预估的并发任务数 + 2。

#### 2.1.5 @Async + @Scheduled 异步执行

对于不需要等待结果的任务，可以结合 `@Async` 实现异步执行，避免阻塞调度线程。

```java
@Configuration
@EnableAsync  // 开启异步支持
@EnableScheduling
public class AsyncSchedulingConfig {
    // 可单独配置异步线程池
    @Bean
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(20);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("async-task-");
        executor.initialize();
        return executor;
    }
}
```

```java
@Component
public class AsyncScheduledTasks {

    // @Async 让任务在异步线程池执行，不阻塞 @Scheduled 调度线程
    @Async
    @Scheduled(fixedRate = 5000)
    public void asyncTask() {
        // 耗时操作，不会阻塞其他定时任务
        System.out.println("Async task running on: " + Thread.currentThread().getName()
            + " at " + LocalTime.now());
    }
}
```

> 💡 `@Async` + `@Scheduled` 本质是两层分离：`@Scheduled` 负责 **触发调度**，`@Async` 负责 **异步执行**，调度线程立即返回。

#### 2.1.6 SchedulingConfigurer 动态Cron

生产环境中，cron表达式可能需要动态修改（如从数据库读取），`@Scheduled` 注解的值是编译期常量无法修改。此时使用 `SchedulingConfigurer` 实现动态cron。

```java
@Component
public class DynamicCronTask implements SchedulingConfigurer {

    @Autowired
    private TaskConfigMapper taskConfigMapper;

    @Override
    public void configureTasks(ScheduledTaskRegistrar taskRegistrar) {
        // 注册一个周期性任务，cron从DB动态获取
        taskRegistrar.addCronTask(() -> {
            System.out.println("Dynamic cron task executed at: " + LocalDateTime.now());
            // 实际业务逻辑...
        }, this::fetchCronExpression);
    }

    /**
     * 从数据库获取cron表达式
     * 修改DB后，下一次调度即生效，无需重启
     */
    private String fetchCronExpression() {
        TaskConfig config = taskConfigMapper.selectByTaskName("dynamicTask");
        String cron = config != null ? config.getCron() : "0 0/1 * * * ?";
        System.out.println("Current cron: " + cron);
        return cron;
    }
}
```

```sql
CREATE TABLE task_config (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    task_name   VARCHAR(64)  NOT NULL UNIQUE COMMENT '任务名称',
    cron        VARCHAR(64)  NOT NULL COMMENT 'cron表达式',
    status      TINYINT      DEFAULT 1 COMMENT '状态 0-关闭 1-开启',
    updated_at  DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_task_name (task_name)
) COMMENT '定时任务配置表';
```

```java
@RestController
@RequestMapping("/admin/task")
public class TaskConfigController {

    @Autowired
    private TaskConfigMapper taskConfigMapper;

    @PutMapping("/cron")
    public Result updateCron(@RequestParam String taskName, @RequestParam String cron) {
        TaskConfig config = taskConfigMapper.selectByTaskName(taskName);
        if (config != null) {
            config.setCron(cron);
            taskConfigMapper.updateById(config);
        }
        return Result.success("Cron updated, will take effect on next trigger");
    }
}
```

> ⚠️ `SchedulingConfigurer` 的动态cron有一个局限：**cron表达式在每次执行时重新读取**，修改后无需重启，但不能做到秒级生效，因为读取时机是任务触发时。

#### 2.1.7 @Scheduled 的局限性

| 问题 | 说明 | 后果 |
|------|------|------|
| **无集群协调** | 多实例部署时每个实例都执行 | 任务重复执行，数据冲突 |
| **无故障转移** | 实例宕机后任务直接丢失 | 关键业务任务无法恢复 |
| **无任务追踪** | 没有任务执行日志、成功/失败记录 | 排障困难，无法审计 |
| **无任务依赖** | 无法配置任务A执行完再执行任务B | 复杂业务无法编排 |
| **无分片能力** | 大数据集只能单机处理 | 无法横向扩展 |
| **无管理界面** | 没有UI查看/启停任务 | 运维依赖研发 |

### 2.2 XXL-JOB 分布式任务调度平台

#### 2.2.1 架构总览

XXL-JOB 是一个轻量级分布式任务调度平台，核心设计是 **调度中心（Admin）** + **执行器（Executor）** 分离架构。

> 💡 **核心设计理念**：调度中心负责调度决策，执行器负责任务执行，二者通过HTTP/REST API通信解耦，调度中心不依赖执行器的代码。

```
 ┌──────────────────────────────────────────────────────────────────┐
 │                     XXL-JOB 调度中心 (Admin)                       │
 │  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌────────────────────┐  │
 │  │ 任务管理 │  │ 执行器管理 │  │ 调度日志 │  │ 告警通知 (邮件)    │  │
 │  └────┬────┘  └────┬────┘  └────┬────┘  └────────────────────┘  │
 │       │            │            │                                 │
 │  ┌────▼────────────▼────────────▼────────────────────────────┐   │
 │  │                  调度线程 (Quartz/自研)                     │   │
 │  │  触发 → 选择执行器 → 路由策略 → 发送请求 → 接收回调         │   │
 │  └───────────────────────────────────────────────────────────┘   │
 └────────────────┬─────────────────────────────────────────────────┘
                  │ HTTP(REST API)
    ┌─────────────┼─────────────┐
    ▼             ▼             ▼
 ┌─────────┐ ┌─────────┐ ┌─────────┐
 │ Executor│ │ Executor│ │ Executor│  ← 多实例注册（心跳上报）
 │ 实例1   │ │ 实例2   │ │ 实例3   │
 └────┬────┘ └────┬────┘ └────┬────┘
      │           │           │
 ┌────▼───────────▼───────────▼────────────┐
 │          @XxlJob 业务方法               │
 │   orderTimeoutCancel / dataSync / ...   │
 └─────────────────────────────────────────┘
```

**核心组件说明**：

| 组件 | 职责 | 部署方式 |
|------|------|----------|
| **调度中心（Admin）** | 管理任务、执行器、调度日志；触发任务执行；接收执行回调 | 独立部署，依赖DB（Quartz表） |
| **执行器（Executor）** | 注册到调度中心；接收调度请求；执行业务代码；回传结果 | 嵌入业务应用或独立部署 |
| **任务（Job）** | 用户定义的具体业务逻辑，通过 `@XxlJob` 绑定 | 代码级配置 |

#### 2.2.2 核心工作流程

```
1. 执行器启动 → 注册到调度中心（心跳每30秒）
2. 管理员在Admin UI配置任务 → 绑定执行器 + 设置cron + 选择路由策略
3. 调度中心到达触发时间 → 根据路由策略选择目标执行器
4. 调度中心向执行器发送HTTP触发请求
5. 执行器接收请求 → 反射调用 @XxlJob 方法
6. 方法执行完毕 → 执行器回调调度中心上报执行结果
7. 调度中心记录日志 → 失败则触发告警
```

#### 2.2.3 SpringBoot 集成 XXL-JOB

**第一步：引入依赖**

```xml
<!-- pom.xml -->
<dependency>
    <groupId>com.xuxueli</groupId>
    <artifactId>xxl-job-core</artifactId>
    <version>2.4.1</version>
</dependency>
```

**第二步：配置执行器**

```yaml
# application.yml
xxl:
  job:
    admin:
      addresses: http://192.168.1.100:8080/xxl-job-admin  # 调度中心地址（多个逗号分隔）
    executor:
      appname: xxl-job-executor-order                       # 执行器AppName（Admin注册使用）
      address: ''                                            # 执行器地址，空则自动获取
      ip: ''                                                 # 执行器IP，空则自动获取
      port: 9999                                             # 执行器端口（和业务端口不同）
      logpath: /data/applogs/xxl-job/jobhandler              # 日志路径
      logretentiondays: 30                                   # 日志保留天数
    accessToken: default_token                                # 通讯token（和Admin一致）
```

**第三步：配置 XxlJobSpringExecutor Bean**

```java
@Configuration
public class XxlJobConfig {

    @Value("${xxl.job.admin.addresses}")
    private String adminAddresses;

    @Value("${xxl.job.executor.appname}")
    private String appname;

    @Value("${xxl.job.executor.port}")
    private int port;

    @Value("${xxl.job.executor.logpath}")
    private String logPath;

    @Value("${xxl.job.executor.logretentiondays}")
    private int logRetentionDays;

    @Value("${xxl.job.accessToken}")
    private String accessToken;

    @Bean
    public XxlJobSpringExecutor xxlJobExecutor() {
        XxlJobSpringExecutor executor = new XxlJobSpringExecutor();
        executor.setAdminAddresses(adminAddresses);
        executor.setAppname(appname);
        executor.setAddress("");
        executor.setIp("");
        executor.setPort(port);
        executor.setAccessToken(accessToken);
        executor.setLogPath(logPath);
        executor.setLogRetentionDays(logRetentionDays);
        return executor;
    }
}
```

**第四步：编写任务处理器**

```java
@Component
public class SimpleJobHandler {

    @XxlJob("demoJob")
    public void demoJob() throws Exception {
        XxlJobHelper.log("XXL-JOB demo job start...");

        // 模拟业务处理
        for (int i = 0; i < 10; i++) {
            XxlJobHelper.log("Processing item: {}", i);
            Thread.sleep(1000);
        }

        XxlJobHelper.log("XXL-JOB demo job finished.");
        // 默认返回 SUCCESS
    }
}
```

> 💡 使用 `XxlJobHelper.log()` 代替 `System.out.println()` 或 `log.info()`，日志会自动同步到调度中心，可在Admin UI查看。

#### 2.2.4 任务类型：BEAN vs GLUE

| 特性 | BEAN 模式 | GLUE 模式 |
|------|-----------|------------|
| **代码位置** | 项目代码中 `@XxlJob` | 调度中心在线编辑（存储在数据库） |
| **发布方式** | 打包部署，需重启 | 在线更新，即时生效 |
| **适用场景** | 核心业务逻辑，稳定不变 | 频繁调整的脚本逻辑 |
| **调试** | 本地IDE调试方便 | 在线调试，配合日志 |
| **版本控制** | Git管理 | 调度中心内置版本管理 |
| **性能** | 编译执行，无额外开销 | 动态编译，有轻微开销 |

**GLUE模式使用**：在Admin UI创建GLUE任务 → 在线编辑Java代码 → 保存后即时生效。

```java
// GLUE示例代码（在线编辑）
package com.xxl.job.service.handler;

import com.xxl.job.core.context.XxlJobHelper;
import com.xxl.job.core.handler.IJobHandler;

public class GlueDemoHandler extends IJobHandler {
    @Override
    public void execute() throws Exception {
        XxlJobHelper.log("GLUE job executed at: {}", new java.util.Date());
        // 在线修改代码，保存即生效，无需重启
    }
}
```

> 🎯 **生产建议**：核心业务用BEAN模式（可控、可测试）；临时逻辑或排查问题时用GLUE模式（敏捷、零部署）。

#### 2.2.5 九种路由策略

XXL-JOB 支持 9 种路由策略，决定调度中心选择哪个执行器实例。

| 策略 | 英文 | 说明 | 适用场景 |
|------|------|------|----------|
| **第一个** | FIRST | 固定选择第一个注册的执行器 | 指定机器执行 |
| **最后一个** | LAST | 固定选择最后一个注册的执行器 | 灰度 / 指定机器 |
| **轮询** | ROUND | 按顺序轮流分发任务（带权轮询） | 通用负载均衡 |
| **随机** | RANDOM | 随机选择一个执行器 | 简单负载均衡 |
| **一致性HASH** | CONSISTENT_HASH | 对JobID哈希取模，相同任务固定到同一机器 | 有状态任务（需要缓存） |
| **最不经常使用** | LEAST_FREQUENTLY_USED | 选择历史调用次数最少的执行器 | 长任务 / 低频率 |
| **最近最久未使用** | LEAST_RECENTLY_USED | 选择最久未调度的执行器 | 均衡使用 |
| **故障转移** | FAILOVER | 健康检查后选择**第一个可用**的执行器 | 高可用任务（默认推荐） |
| **忙碌转移** | BUSYOVER | 检查执行器是否繁忙，繁忙则转移 | 避免机器过载 |
| **分片广播** | SHARDING_BROADCAST | **广播到所有执行器**，每台拿到分片参数自行处理 | 大数据分片处理 |

> 🎯 **推荐组合**：普通定时任务用 **ROUND** 或 **FAILOVER**；有状态任务用 **CONSISTENT_HASH**；大数据量处理用 **SHARDING_BROADCAST**。

#### 2.2.6 故障转移机制（Failover）

**执行器注册与心跳**：

1. 每个执行器启动时，向调度中心 `onRegister` 注册
2. 运行时每 **30秒** 发送心跳 `onBeat`
3. 调度中心记录执行器状态及最后心跳时间
4. 超过 **90秒** 未收到心跳 → 标记为 **下线**

**故障转移流程**：

```
调度中心 触发任务
    │
    ├── 获取注册的在线执行器列表
    │
    ├── 按路由策略选择目标执行器
    │
    ├── 发送HTTP请求到目标执行器
    │
    ├── 请求失败 / 超时
    │   └── 如果路由策略 = FAILOVER
    │       ├── 标记当前执行器不可用
    │       └── 选择下一个可用执行器重试
    │
    └── 请求成功 → 等待执行回调
```

```yaml
# executor 心跳相关配置
xxl:
  job:
    executor:
      # 默认配置即可，通常不需要修改
      # 心跳间隔: 30秒（调度中心控制）
      # 超时判定: 90秒（90秒无心跳标记为下线）
```

> 💡 **高可用最佳实践**：至少部署2个执行器实例 + FAILOVER路由策略。单实例宕机后，调度中心自动将任务调度到其余实例。

#### 2.2.7 分片广播（ShardingBroadcast）

分片广播是XXL-JOB **最核心的路由策略**，它将任务广播到所有执行器，每个执行器通过 `shardIndex` / `shardTotal` 参数知道自己应该处理哪部分数据。

**分片参数**：

| 参数 | 说明 | 示例 |
|------|------|------|
| `shardIndex` | 当前分片序号（从0开始） | 0, 1, 2, 3 |
| `shardTotal` | 总分片数（等于执行器实例数） | 4 |

**工作原理**：

```java
@XxlJob("shardingJob")
public void shardingJob() throws Exception {
    // 获取分片参数
    int shardIndex = XxlJobHelper.getShardIndex();
    int shardTotal = XxlJobHelper.getShardTotal();

    XxlJobHelper.log("Shard [{}/{}] started", shardIndex + 1, shardTotal);

    // 按分片查询自己负责的数据：WHERE id % shardTotal = shardIndex
    List<Order> orders = orderMapper.selectByShard(shardIndex, shardTotal);

    for (Order order : orders) {
        processOrder(order);
    }

    XxlJobHelper.log("Shard [{}/{}] completed, processed {} orders",
        shardIndex + 1, shardTotal, orders.size());
}
```

```sql
-- MyBatis Mapper: 按分片查询数据
<select id="selectByShard" resultType="Order">
    SELECT * FROM `order`
    WHERE order_status = 0   <!-- 待处理状态 -->
      AND MOD(id, #{shardTotal}) = #{shardIndex}  <!-- 核心分片逻辑 -->
    ORDER BY create_time ASC
    LIMIT 1000
</select>
```

**3台执行器分片广播执行示意图**：

```
 ┌───────────── 分片广播 ─────────────┐
 │                                    │
 ▼                                    ▼
Executor-1                   Executor-2                   Executor-3
shardIndex=0                 shardIndex=1                 shardIndex=2
shardTotal=3                 shardTotal=3                 shardTotal=3
         │                           │                           │
         ▼                           ▼                           ▼
WHERE id % 3 = 0            WHERE id % 3 = 1            WHERE id % 3 = 2
orders: 3, 6, 9, 12...      orders: 1, 4, 7, 10...     orders: 2, 5, 8, 11...
```

> 🎯 **分片广播适用场景**：全量数据扫描（订单超时取消、数据同步、对账、报表生成、数据清理）。数据量越大，分片优势越明显。

#### 2.2.8 任务依赖（子任务）

XXL-JOB 支持简单的任务依赖：一个任务执行完成后触发另一个任务。

**配置方式**：在Admin UI任务编辑页面，设置 **子任务ID**（多个用逗号分隔）。

```
任务A（cron触发）
    │
    ├── 任务A执行成功
    │       └── 触发 子任务B
    │               └── 触发 孙子务C
    │
    └── 任务A执行失败 → 不触发子任务
```

> ⚠️ XXL-JOB 的子任务依赖是 **一级传递**，即A→B→C需要分别在A和B上配置子任务ID，不支持DAG（有向无环图）编排。对于复杂DAG依赖，需要使用 Elastic-Job 或其他工作流调度平台。

## 3. 高频踩坑与误区

### 3.1 @Scheduled 单线程阻塞

**现象**：多个 `@Scheduled` 方法中有一个需要执行10秒，其他每秒执行的方法被阻塞。

**原因**：Spring默认创建 `ThreadPoolTaskScheduler` 的 `poolSize = 1`。

**解决**：自定义 `TaskScheduler` Bean，设置 `poolSize >= 2`，或给耗时任务增加 `@Async`。

### 3.2 @Scheduled 多实例重复执行

**现象**：应用部署2个实例，定时任务被执行2次。

**原因**：`@Scheduled` 是进程级别的，不感知多实例。

**解决**：
1. 引入分布式调度平台（推荐）
2. 使用分布式锁（Redis Lock / DB锁）做互斥
3. 配置仅允许一台机器执行（但失去高可用）

```java
// 临时方案：Redis分布式锁防重复
@Scheduled(cron = "0 0 2 * * ?")
public void dailyReport() {
    String lockKey = "task:dailyReport";
    Boolean locked = redisTemplate.opsForValue()
        .setIfAbsent(lockKey, "1", Duration.ofMinutes(10));
    if (Boolean.TRUE.equals(locked)) {
        try {
            // 执行定时任务
            generateDailyReport();
        } finally {
            redisTemplate.delete(lockKey);
        }
    }
}
```

### 3.3 @Scheduled cron 长达一年未执行

**现象**：某cron任务长时间未触发，检查发现cron表达式写错。

**常见错误**：

| 错误写法 | 问题 | 正确写法 |
|----------|------|----------|
| `0 0 12 * * *` | 6个*，但日与星期互斥用`*` | `0 0 12 * * ?` |
| `0 30 8 * * 1-5` | 星期1-5用`-`不包含周日语义 | `0 30 8 * * 1-5`（正确） |
| `*/10 * * * * *` | 非标准写法 | `0/10 * * * * ?` |
| `0 0 * * *` | 缺少秒字段 | `0 0 * * * ?` |

### 3.4 XXL-JOB 调度成功但执行器未执行

**现象**：Admin显示"调度成功"，但业务代码未执行。

**排查**：
1. 检查执行器是否在线（Admin → 执行器管理）
2. 检查 `appname` 是否匹配
3. 检查 `accessToken` 是否一致
4. 查看执行器日志（`logpath` 目录下）
5. 检查执行器端口是否被防火墙拦截

### 3.5 XXL-JOB 执行超时

**现象**：任务实际执行5分钟，但Admin显示失败/超时。

**原因**：XXL-JOB默认超时时间有限制。

**解决**：在Admin UI任务配置中设置 **超时时间**（单位秒）。

```text
Admin UI → 任务管理 → 编辑 → 高级配置
  ├── 超时时间: 600    （单位秒，0为不限）
  └── 失败重试次数: 3  （最多重试3次）
```

### 3.6 分片广播数据倾斜

**现象**：`MOD(id, shardTotal)` 分片不均匀，某些分片处理数据远多于其他。

**原因**：自增ID的步长和取模特性导致分布不均。

**优化方案**：

```sql
-- 方案1：使用 id 的哈希值分片（更均匀）
WHERE MOD(CRC32(id), #{shardTotal}) = #{shardIndex}

-- 方案2：基于时间范围分片（适合时间序列表）
WHERE order_status = 0
  AND create_time >= '2026-01-01'
  AND MOD(id, #{shardTotal}) = #{shardIndex}

-- 方案3：分批 + 分段查询（大数据量时）
-- 先查ID范围，再按分片过滤
```

### 4.2 练习二：识错

```java
@Component
public class BadScheduledTasks {

    @Scheduled(fixedRate = 1000)
    public void fastTask() {
        System.out.println("每秒执行");
    }

    @Scheduled(fixedRate = 1000)
    public void slowTask() throws InterruptedException {
        Thread.sleep(5000);  // 模拟耗时5秒
        System.out.println("慢任务");
    }
}
```

**问题**：`fastTask()` 每秒应该执行一次，实际能每秒执行吗？为什么？如何修复？

<details>
<summary>答案</summary>

**不能**。因为`ThreadPoolTaskScheduler`默认`poolSize=1`，`slowTask()`占用线程5秒，`fastTask()`无法按时调度。

**修复**：
1. 添加`@Async`到`slowTask()`方法，将耗时操作异步化
2. 或配置`TaskScheduler`的`poolSize`为大于1的值
3. 或使用`Thread.sleep()`以外的非阻塞方式

</details>

#### 5.1.6 任务处理器（核心代码）

```java
@Component
public class OrderTimeoutJobHandler {

    private static final Logger log = LoggerFactory.getLogger(OrderTimeoutJobHandler.class);

    @Autowired
    private OrderMapper orderMapper;

    @Autowired
    private RestTemplate restTemplate;  // 用于通知库存服务释放库存

    /**
     * 订单超时取消任务 — 使用分片广播分布式处理
     *
     * Admin配置：
     *   cron:          0 0/1 * * * ?
     *   路由策略:       SHARDING_BROADCAST
     *   执行器:         xxl-job-executor-order
     *   任务描述:       订单超时30分钟自动取消
     */
    @XxlJob("orderTimeoutCancel")
    public void orderTimeoutCancel() throws Exception {
        // 1. 获取分片参数
        int shardIndex = XxlJobHelper.getShardIndex();
        int shardTotal = XxlJobHelper.getShardTotal();

        // 2. 计算超时时间点（当前时间 - 30分钟）
        LocalDateTime timeoutTime = LocalDateTime.now().minusMinutes(30);

        XxlJobHelper.log("OrderTimeoutCancel started | shard [{}/{}] | timeoutBefore: {}",
            shardIndex + 1, shardTotal, timeoutTime);

        // 3. 分页处理，避免一次加载数据过多
        long totalProcessed = 0;
        int batchSize = 500;

        while (true) {
            // 4. 按分片扫描超时订单
            List<Order> timeoutOrders = orderMapper.selectTimeoutOrders(
                shardIndex, shardTotal, timeoutTime);

            if (timeoutOrders == null || timeoutOrders.isEmpty()) {
                break;  // 无更多数据，退出循环
            }

            // 5. 批量取消
            for (Order order : timeoutOrders) {
                try {
                    cancelOrder(order);
                    totalProcessed++;
                } catch (Exception e) {
                    XxlJobHelper.log("Cancel order failed | orderId: {} | error: {}",
                        order.getId(), e.getMessage());
                }
            }

            // 6. 避免一次扫描太多，每次处理后休眠200ms
            Thread.sleep(200);
        }

        XxlJobHelper.log("OrderTimeoutCancel completed | shard [{}/{}] | totalCancelled: {}",
            shardIndex + 1, shardTotal, totalProcessed);
    }

    /**
     * 执行取消订单逻辑
     */
    private void cancelOrder(Order order) {
        LocalDateTime now = LocalDateTime.now();

        // 6.1 更新订单状态为「已取消」
        int affected = orderMapper.cancelOrder(order.getId(), now);
        if (affected == 0) {
            XxlJobHelper.log("Order already cancelled or paid | orderNo: {}", order.getOrderNo());
            return;
        }

        // 6.2 通知库存服务释放库存（异步）
        String url = "http://inventory-service/api/inventory/release";
        Map<String, Object> params = new HashMap<>();
        params.put("orderNo", order.getOrderNo());
        params.put("cancelTime", now.toString());

        try {
            restTemplate.postForEntity(url, params, String.class);
            XxlJobHelper.log("Stock released | orderNo: {}", order.getOrderNo());
        } catch (Exception e) {
            // 库存释放失败可放入MQ重试，此处仅记录日志
            XxlJobHelper.log("Stock release failed | orderNo: {} | error: {}",
                order.getOrderNo(), e.getMessage());
        }

        // 6.3 记录操作日志
        XxlJobHelper.log("Order cancelled successfully | orderId: {} | orderNo: {}",
            order.getId(), order.getOrderNo());
    }
}
```

## 7. 本章复盘速记清单

### 7.1 核心速记

```
@Scheduled 三模式：fixedRate（等间隔开始）/ fixedDelay（上次结束+延迟）/ cron（表达式）
                ↓
  默认单线程阻塞 → 配置ThreadPoolTaskScheduler(poolSize=N) / @Async
                ↓
  无集群能力 → 分布式场景必须用任务调度平台

XXL-JOB 两核心：调度中心(Admin) + 执行器(Executor)
                ↓
  工作流：Admin触发 → HTTP请求 → Executor执行 → 回调结果
                ↓
  FAILOVER路由：健康检查 → 故障自动转移（90秒无心跳判下线）
                ↓
  分片广播：shardIndex + shardTotal → MOD(id, total) = index
                ↓
  SHARDING_BROADCAST用于全量数据扫描（超时取消/对账/数据同步）

框架选型：XXL-JOB（通用）> Elastic-Job（DAG复杂编排）> Quartz（老项目）
```

### 7.2 常见问题速查

| 问题 | 诊断 | 方案 |
|------|------|------|
| @Scheduled任务延迟/不执行 | 默认单线程阻塞 | 配置线程池 poolSize >= 2 |
| 多实例任务重复执行 | @Scheduled无集群能力 | 迁移到XXL-JOB或用Redis分布式锁 |
| 调度成功但业务未执行 | 执行器或appname配置错误 | 检查Admin执行器列表和accessToken |
| 任务执行超时 | 超时时间设置过短 | Admin配置超时时间（秒） |
| 分片数据不均 | MOD(id)分布不均 | 改用CRC32(id)取模或分段查询 |

### 7.3 速记口诀

```
Cron口诀：秒分时日月周年，星问横杠斜井L
@Scheduled口诀：单线程阻塞要小心，多实例重复用调度
XXL-JOB口诀：Admin管调度，Executor干业务，FAILOVER保命，Sharding治海量
分片口诀：一亿数据四台机，MOD分片不重不漏，一台挂了还有三
```

// XXL-JOB 调度核心：JobTriggerPoolHelper
// 调度线程池分为 fastTriggerPool（快速任务）和 slowTriggerPool（慢任务）
// 当某个任务的平均执行耗时超过阈值时，自动迁移到 slowTriggerPool

public class JobTriggerPoolHelper {
    // 快速触发线程池（核心线程数 10 ~ 最大 200）
    private ThreadPoolExecutor fastTriggerPool;
    // 慢触发线程池（核心线程数 10 ~ 最大 100）
    private ThreadPoolExecutor slowTriggerPool;

    // 触发入口
    public void trigger(int jobId, TriggerTypeEnum triggerType,
                        int failRetryCount, String executorShardingParam,
                        String executorParam, String addressList) {
        // 选择线程池（按任务历史平均耗时判断快慢）
        ThreadPoolExecutor triggerPool = fastTriggerPool;

        triggerPool.execute(() -> {
            // 1. 处理分片参数
            // 2. 根据路由策略选择执行器
            // 3. 构造HTTP请求发送到执行器
            // 4. 接收执行结果回调
        });
    }
}

#### 8.1.3 XXL-JOB 为什么不适用 Quartz 悲观锁

| 方案 | 机制 | 问题 |
|------|------|------|
| Quartz集群 | 数据库行锁（悲观锁） | 锁竞争影响性能，单DB瓶颈 |
| XXL-JOB | **数据库轮询 + 分布式调度锁** | 调度中心内置调度器，Admin集群靠DB唯一键保证不重复调度 |

> 💡 XXL-JOB 2.x 移除了对 Quartz 的依赖，改用自研调度器 **JobTriggerPool** + DB轮询，避免了 Quartz 的悲观锁问题。

/**
 * 分布式任务调度中间件 — 核心接口定义
 * 用于理解调度平台的设计思路
 */
public interface DistributedScheduler {

    /**
     * 1. 注册执行器
     */
    void registerExecutor(ExecutorInfo executor);

    /**
     * 2. 心跳上报
     */
    void heartbeat(String executorId);

    /**
     * 3. 任务分配（根据路由策略选择一个执行器）
     */
    String assignExecutor(JobInfo job, List<String> activeExecutors);

    /**
     * 4. 执行任务
     */
    void execute(JobInfo job, String executorAddress);

    /**
     * 5. 回调结果
     */
    void callback(CallbackResult result);

    /**
     * 6. 故障检测（检测心跳超时的执行器）
     */
    List<String> detectFailures(List<ExecutorInfo> executors);
}

/**
 * 任务信息
 */
class JobInfo {
    private Long jobId;
    private String jobHandler;        // 任务处理器名称
    private String cron;              // 调度表达式
    private String routeStrategy;     // 路由策略
    private int timeoutSeconds;       // 超时时间
    private int retryCount;           // 重试次数
}

/**
 * 执行器信息
 */
class ExecutorInfo {
    private String executorId;
    private String appName;           // 应用名

### 8.4 XXL-JOB vs Elastic-Job 深度对比

| 对比维度 | XXL-JOB | Elastic-Job |
|----------|---------|-------------|
| **一致性** | 最终一致（调度和执行分离） | 强一致（ZK协调） |
| **存储** | MySQL（调度中心）+ 本地日志 | ZooKeeper（元数据）+ 可扩展存储 |
| **弹性伸缩** | 执行器增减需Admin手动/自动感知 | 自动感知ZK节点变更，动态重分片 |
| **任务量上限** | 10万级别（受限于DB查询） | 万级别（受限于ZK节点数量） |
| **运维复杂度** | 低（一个DB + Admin + Executor） | 中（需维护ZK集群） |
| **易用性** | **胜出**（中文文档、功能完善） | 一般（文档偏少、概念偏复杂） |
| **开源协议** | GPL v3（对商用有约束） | Apache 2.0（宽松） |
| **技术栈依赖** | Spring + MySQL + Netty | ZK + 可选注册中心 |

> 🎯 **选型建议**：如果你的团队运维能力一般、希望快速上手 → 选 **XXL-JOB**。如果你有ZK基础设施、需要DAG编排、团队规模大 → 选 **Elastic-Job**。如果你只需要一个简单的集群调度 → 选 **XXL-JOB**。
