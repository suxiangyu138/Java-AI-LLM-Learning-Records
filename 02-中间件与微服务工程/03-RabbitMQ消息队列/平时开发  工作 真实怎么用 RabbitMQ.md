# 平时开发 / 工作真实怎么用 RabbitMQ

> **核心原则**：慢的、量大的、没必要同步做的、需要解耦的，全扔 MQ。

---

## 1. 什么时候必加 MQ？

| 场景 | 方案 |
|------|------|
| 接口响应太慢（发短信/邮件/推送） | 异步处理，接口立马返回 |
| 秒杀/高并发抢购 | 流量削峰，请求进队列慢慢消费 |
| 系统解耦 | 下单只发消息，其他服务各自监听 |
| 定时/延迟任务 | 死信队列实现 30 分钟未支付取消 |
| 最终一致性 | 可靠消息补偿 |

---

## 2. 日常只用的三种交换机

| 类型 | 匹配 | 用途 |
|------|------|------|
| **Direct** | `routingKey` 精确匹配 | 单服务点对点 |
| **Topic** ⭐ | `*` `#` 模糊匹配 | 日志、多模块订阅 |
| **Fanout** | 无视 key，全广播 | 全局通知、缓存刷新 |

---

## 3. SpringBoot 固定套路

```java
// 1. 配置类：声明交换机+队列+绑定（启动初始化一次）
@Bean DirectExchange exchange()
@Bean Queue queue()
@Bean Binding binding()

// 2. 生产者发消息
rabbitTemplate.convertAndSend("交换机", "路由key", 消息体);

// 3. 消费者监听
@RabbitListener(queues = "队列名")
public void handleMsg(String msg) { /* 执行业务 */ }
```

---

## 4. 生产必开四大保障

| 保障 | 作用 |
|------|------|
| **消息持久化** | 重启 MQ 消息不丢 |
| **生产者 Confirm** | 保证消息一定到达 MQ |
| **消费者手动 ACK** | 业务成功才签收，失败自动重试 |
| **死信队列** | 失败多次不卡死，进入死信人工处理 |

---

## 5. 极简人话总结

```text
① 复杂耗时操作异步 → 用 RabbitMQ
② 架构解耦、高并发削峰 → 全靠 MQ
③ 日常开发三件套：生产者发消息 → 交换机路由 → 消费者监听消费
④ 本地 Docker 部署，开发最舒服
⑤ 生产必须加：持久化、ACK、死信、消息确认
```
