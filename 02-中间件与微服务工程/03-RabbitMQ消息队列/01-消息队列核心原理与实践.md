# 消息队列核心原理：Kafka与RocketMQ

## 一、消息队列核心概念

### 1.1 为什么需要消息队列

在分布式系统架构中，消息队列（Message Queue，简称MQ）是解耦、异步、削峰的核心基础设施。理解这三个核心价值，是掌握MQ选型与使用的前提。

**解耦（Decoupling）**

在传统微服务架构中，服务之间通过RPC或HTTP直接调用，形成硬耦合关系。例如，订单服务下单后需要通知库存服务扣减库存、通知积分服务增加积分、通知短信服务发送通知。如果采用同步RPC调用，每增加一个下游服务，订单服务的代码就需要修改一次。更糟糕的是，如果某个下游服务不可用，订单服务可能直接被拖垮。

引入MQ后，订单服务只需将"订单创建成功"的消息发送到Topic，下游服务各自订阅消费，服务间不再直接依赖。订单服务不需要关心下游有多少个服务、它们是否在线。

```java
// 耦合的同步调用
public void createOrder(Order order) {
    saveOrder(order);
    inventoryService.deductStock(order);  // 强依赖
    pointsService.addPoints(order);       // 强依赖
    smsService.sendNotification(order);   // 强依赖
}
```

```java
// 解耦的消息队列方式
public void createOrder(Order order) {
    saveOrder(order);
    rocketMQTemplate.send("order-topic", order); // 只发消息，不关心谁消费
}
```

**异步（Asynchrony）**

同步调用模式下，一次请求的整体耗时 = 所有下游服务响应时间之和。如果库存扣减需要200ms、积分增加100ms、短信发送500ms，那么接口总耗时至少800ms，用户体验极差。使用MQ后，订单服务只做本地持久化和发消息（通常1-5ms），请求立即返回，下游服务异步处理。

```
同步模式: [请求] -> 订单DB(50ms) -> 库存(200ms) -> 积分(100ms) -> 短信(500ms) = 850ms
异步模式: [请求] -> 订单DB(50ms) -> 发MQ(5ms) = 55ms (响应返回，后端异步处理)
```

**削峰填谷（Peak Clipping）**

这是MQ最经典的应用场景。以电商秒杀为例，瞬时QPS可能达到数万甚至数十万，但后端订单系统和数据库的承受能力通常只有几千。如果不做保护，数据库直接被打挂，整个系统雪崩。

MQ像一个"大坝"，将洪峰流量缓存下来，后端消费者按自己的处理能力"匀速"消费，保护后端系统。

```
秒杀场景流量:
                 _____________
            /                  \
           /                    \
          /                      \   <-- 洪峰10万QPS
---------                          ----------
  |                                  |
  |    MQ队列(削峰)                  |
  v                                  v
后端以固定速率消费(如2000 QPS) -> 数据库安全
```

### 1.2 核心消息模型

无论哪种MQ，其核心模型都围绕以下概念展开：

**Producer（生产者）**：负责产生和发送消息的一方。生产者将业务数据封装成消息，发送到Broker。

**Broker（消息服务器）**：消息队列的服务器端，负责消息的存储、转发、调度。所有消息都存储在Broker上。

**Consumer（消费者）**：负责从Broker拉取或接收消息进行处理的一方。

**Topic（主题）**：消息的逻辑分类。生产者将消息发送到指定Topic，消费者订阅Topic来消费消息。一个Topic包含一个或多个Queue/Partition。

**Queue（队列）/ Partition（分区）**：Topic的物理分片。消息实际存储在Queue/Partition中，这是并行消费的基本单位。Kafka中称为Partition，RocketMQ中称为MessageQueue。

**Consumer Group（消费者组）**：消费者的逻辑分组。同一消费者组内的消费者共同消费一个Topic的消息，每条消息只会被组内的一个消费者消费（集群模式）。不同消费者组独立消费，互不影响。

```
                    ┌──────────────────────────┐
                    │       NameServer         │
                    │    (路由注册/发现)         │
                    └──────────┬───────────────┘
                               │
┌──────────┐    ┌──────────────┴───────────────┐    ┌──────────┐
│Producer1 │───▶│          Broker              │───▶│Consumer1 │
├──────────┤    │  ┌──────┐ ┌──────┐ ┌──────┐ │    ├──────────┤
│Producer2 │───▶│  │Queue1│ │Queue2│ │Queue3│ │───▶│Consumer2 │
└──────────┘    │  └──────┘ └──────┘ └──────┘ │    ├──────────┤
                └──────────────────────────────┘    │Consumer3 │
                                                     └──────────┘
```

### 1.3 消息协议与标准

**JMS（Java Message Service）**

JMS是Java EE规范，定义了Java应用中消息通信的标准API。它支持两种消息模型：
- **P2P（Point-to-Point）**：基于Queue，一条消息只有一个消费者
- **Pub/Sub（Publish-Subscribe）**：基于Topic，一条消息可被多个订阅者消费

JMS的局限性在于：仅限Java平台，不支持异构系统；规范比较老旧，不支持高级特性（如顺序消息、事务消息）。ActiveMQ是其典型实现。

**AMQP（Advanced Message Queuing Protocol）**

AMQP是一个应用层协议，核心在于定义了Exchange（交换机）、Queue（队列）、Binding（绑定）三层模型。生产者不直接将消息发送到Queue，而是发送到Exchange，由Exchange根据Routing Key将消息路由到一个或多个Queue。

```
Producer -> Exchange (根据Routing Key路由) -> Binding -> Queue -> Consumer
```

AMQP的灵活性极高，支持direct、topic、fanout、headers四种路由模式。RabbitMQ是AMQP的标杆实现。

**自定义协议（Kafka / RocketMQ）**

Kafka和RocketMQ均未遵循JMS或AMQP标准，而是定义了自己的私有协议：
- **Kafka**：基于TCP的二进制协议，高效紧凑，支持批量、压缩，专为高吞吐设计
- **RocketMQ**：基于TCP的自定义协议，通信模块参照Kafka设计，但增加了大量高级特性支持

### 1.4 主流MQ选型对比

| 特性 | Kafka | RocketMQ | RabbitMQ | Pulsar |
|------|-------|----------|----------|--------|
| **吞吐量** | 百万级/s | 十万级/s | 万级/s | 百万级/s |
| **延迟** | ms级 | ms级 | us级 | ms级 |
| **消息可靠性** | 高（结合ACK） | 非常高 | 高 | 非常高 |
| **事务消息** | 支持（0.11+） | 原生支持 | 不支持 | 支持 |
| **顺序消息** | 分区内有序 | 全局/分区有序 | 单队列有序 | 分区有序 |
| **延迟消息** | 不支持原生 | 18个级别 | 插件支持 | 支持 |
| **死信队列** | 需自建 | 原生支持 | 原生支持 | 原生支持 |
| **消息过滤** | Broker端不支持 | Tag+SQL | Exchange路由 | Key-based |
| **运维复杂度** | 中等（依赖ZK） | 低（无ZK） | 低 | 较高 |
| **适用场景** | 日志采集/流处理 | 业务消息/交易 | 小项目/复杂路由 | 云原生/多租户 |

**选型建议**：
- **Kafka**：大数据生态、日志收集、流式处理（Flink/Spark Streaming）、埋点数据采集
- **RocketMQ**：电商核心交易、金融级消息、事务消息、顺序消息、国内业务系统
- **RabbitMQ**：中小项目、复杂路由需求、低延迟场景、团队熟悉Erlang
- **Pulsar**：云原生架构、多租户场景、存储计算分离需求

## 二、消息可靠性（重中之重）

消息可靠性是消息队列选型和使用中最核心的议题。一个消息从生产到消费，经历了"三段旅程"：生产者 -> Broker -> 消费者，每一段都有可能丢失消息。

### 2.1 消息不丢失

#### 生产者端：确保消息成功发送到Broker

**方式一：同步发送 + 回调确认**

生产者发送消息后，同步等待Broker返回ACK确认。如果超时或收到异常，进行重试。

```java
// RocketMQ同步发送
SendResult sendResult = producer.send(message);
if (sendResult.getSendStatus() == SendStatus.SEND_OK) {
    // 发送成功
} else {
    // 发送失败，重试
}

// Kafka同步发送
RecordMetadata metadata = producer.send(record).get(); // 阻塞等待ACK
```

**方式二：异步发送 + 回调**

不阻塞主线程，通过回调函数处理发送结果。

```java
// RocketMQ异步发送
producer.asyncSend(message, new SendCallback() {
    @Override
    public void onSuccess(SendResult sendResult) {
        // 发送成功
    }
    @Override
    public void onException(Throwable e) {
        // 发送失败，重试处理
    }
});

// Kafka异步发送带回调
producer.send(record, (metadata, exception) -> {
    if (exception != null) {
        // 处理发送失败
    }
});
```

**方式三：重试机制**

发送失败后自动重试，需要配置合理的重试次数和重试间隔。

```java
// Kafka生产者配置重试
properties.put(ProducerConfig.RETRIES_CONFIG, 3);
properties.put(ProducerConfig.RETRY_BACKOFF_MS_CONFIG, 1000);

// RocketMQ默认重试2次
producer.setRetryTimesWhenSendFailed(3);
```

**方式四：事务消息（RocketMQ）**

适用于需要保证"本地数据库操作"和"消息发送"原子性的场景。详见第三章事务消息部分。

**关于ACK设置的说明**：

Kafka生产者的acks参数控制消息持久化的确认级别：
- `acks=0`：不等待任何确认，吞吐最高，可能丢消息
- `acks=1`：等待Leader写入本地日志即确认（默认），Leader宕机时可能丢消息
- `acks=all`（或-1）：等待Leader和所有ISR副本都写入，最安全但吞吐最低

```java
// 最高可靠性配置
properties.put(ProducerConfig.ACKS_CONFIG, "all");
properties.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true); // 幂等生产者
```

#### Broker端：确保消息持久化不丢失

**同步刷盘**

每条消息写入后，立即调用`fsync`将数据从Page Cache刷到磁盘。可靠性最高，但性能大幅下降（TPS降低约90%）。

```java
// RocketMQ同步刷盘配置（broker.conf）
flushDiskType=SYNC_FLUSH

// RocketMQ刷盘策略源码级别
// CommitLog.java
if (FlushDiskType.SYNC_FLUSH == flushDiskType) {
    synchronized (this) {
        flushCommitLog();
    }
}
```

**异步刷盘**

消息先写入Page Cache（内存），后台线程定时批量刷盘（默认500ms）。性能极高，但宕机时可能丢失Page Cache中尚未刷盘的消息。

```java
// RocketMQ异步刷盘配置（默认）
flushDiskType=ASYNC_FLUSH
```

**主从复制**

**同步复制**：Leader写入完成后，等待所有Slave写入完成后才返回ACK给生产者。数据安全性最高，延迟增加。
**异步复制**：Leader写入完成后立即返回ACK，Slave异步从Leader拉取数据。性能好，Leader宕机时可能丢消息（尚未同步到Slave的部分）。

```java
// RocketMQ broker.conf
// 同步复制
brokerRole=SYNC_MASTER
// 异步复制  
brokerRole=ASYNC_MASTER
```

**最佳实践组合**：

```
极高可靠性场景: 同步刷盘 + 同步复制  （如金融交易）
常规业务场景: 异步刷盘 + 同步复制  （推荐，性能与可靠性的平衡）
极致吞吐场景: 异步刷盘 + 异步复制  （如日志采集、埋点数据）
```

#### 消费者端：手动ACK，消费成功再确认

消费者从Broker拉取消息后，先处理业务逻辑，处理成功后再向Broker发送ACK确认。这是防止消费者端丢消息的关键。

```java
// RocketMQ手动ACK（推荐方式）
@RocketMQMessageListener(topic = "order-topic", 
                         consumerGroup = "order-group",
                         consumeMode = ConsumeMode.CONCURRENTLY)
public class OrderMessageListener implements RocketMQListener<OrderMessage> {
    @Override
    public ConsumeConcurrentlyStatus onMessage(OrderMessage message) {
        try {
            // 1. 执行业务逻辑
            processOrder(message);
            // 2. 消费成功，手动ACK
            return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
        } catch (Exception e) {
            // 3. 消费失败，稍后重试
            return ConsumeConcurrentlyStatus.RECONSUME_LATER;
        }
    }
}

// Kafka手动ACK
@KafkaListener(topics = "order-topic", groupId = "order-group")
public void listen(ConsumerRecord<String, String> record, 
                   Acknowledgment ack) {
    try {
        processOrder(record.value());
        ack.acknowledge(); // 手动提交offset
    } catch (Exception e) {
        // 不提交offset，下次重新消费
    }
}

// Kafka消费者配置手动提交
properties.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
```

### 2.2 消息不重复：幂等消费

#### 消息重复的原因

消息重复在分布式系统中几乎无法100%避免，主要原因有三：

1. **生产者重试**：生产者发送消息后未收到ACK（可能网络超时），触发重试，Broker收到了两条相同的消息
2. **Broker重发**：Leader宕机触发副本重新选举，可能导致消息被重复消费
3. **消费者Rebalance**：消费者组触发Rebalance时，未提交offset的分区会被分配给其他消费者，造成重复消费

#### 解决方案

**方案一：数据库唯一键去重**

利用数据库的唯一约束（唯一索引或主键）来实现幂等。

```sql
-- 建表时设置业务唯一键
CREATE TABLE order_process_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    message_id VARCHAR(64) UNIQUE,  -- 消息ID做唯一约束
    order_id VARCHAR(32),
    status TINYINT,
    create_time DATETIME
);
```

```java
public ConsumeConcurrentlyStatus onMessage(OrderMessage msg) {
    try {
        // 尝试插入唯一键
        insertProcessRecord(msg.getMessageId());
        // 插入成功，说明是首次消费
        processOrder(msg);
        return CONSUME_SUCCESS;
    } catch (DuplicateKeyException e) {
        // 插入失败，说明已经消费过，跳过
        return CONSUME_SUCCESS;
    }
}
```

**方案二：Redis Setnx去重**

利用Redis的SET NX命令实现分布式锁级去重，适合高并发场景。

```java
public boolean isMessageConsumed(String messageId) {
    // setnx: key不存在时设置成功，存在时设置失败
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent("msg:consumed:" + messageId, "1", 
                      Duration.ofHours(24)); // 设置过期时间防止内存泄漏
    return Boolean.TRUE.equals(success);
}

public ConsumeConcurrentlyStatus onMessage(OrderMessage msg) {
    // 先判断是否已消费
    if (!isMessageConsumed(msg.getMessageId())) {
        // 已消费过，直接ACK
        return CONSUME_SUCCESS;
    }
    try {
        processOrder(msg);
        return CONSUME_SUCCESS;
    } catch (Exception e) {
        // 处理失败时删除标识，允许下次重试
        redisTemplate.delete("msg:consumed:" + msg.getMessageId());
        return RECONSUME_LATER;
    }
}
```

**方案三：利用消息ID本身去重**

Kafka 0.11+引入了幂等生产者（Idempotent Producer），通过给每条消息分配Producer ID和序列号，Broker端自动去重。

```java
// Kafka幂等生产者配置
properties.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
// 开启幂等会自动设置 acks=all 且 retries > 0
```

**方案四：业务状态机**

利用业务自身的状态流转来保证幂等。例如订单状态只能从"待支付"流转到"已支付"，重复的消息到达时判断当前状态已为"已支付"，则直接跳过。

```sql
UPDATE orders 
SET status = 'PAID', pay_time = NOW()
WHERE order_id = ? AND status = 'PENDING_PAY';  -- 状态机条件
```

```java
public ConsumeConcurrentlyStatus onMessage(PayMessage msg) {
    int updated = orderMapper.updateStatus(
        msg.getOrderId(), 
        "PENDING_PAY", // 当前状态
        "PAID"         // 目标状态
    );
    if (updated > 0) {
        processAfterPay(msg);
    }
    // 无论是否更新成功都ACK（已处理过也是成功）
    return CONSUME_SUCCESS;
}
```

### 2.3 消息顺序性

#### 为什么消息会乱序

在MQ的分区并行模型下，消息天然是乱序的：
- 多个分区并行消费，不同分区的消费速度不同
- 生产者重试可能导致后发的消息先到达
- 消费者自动重试时，失败的消息阻塞后续消息

#### 解决方案

**核心思想：将需要保证顺序的消息发送到同一个分区（Queue），且单个消费者串行消费。**

**Kafka的顺序消息实现**

```java
// 生产者：用订单ID作为key，保证同一订单的消息进入同一分区
producer.send(new ProducerRecord<>("order-topic", 
    order.getOrderId(),  // key -> 相同key进入相同分区
    JSON.toJSONString(order)
));

// 消费者：分区内单线程消费
properties.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 1); // 每次只拉1条
// 同一个分区内的消息由同一个线程串行处理
```

**RocketMQ的顺序消息实现**

```java
// 生产者：使用MessageQueueSelector将同一业务key的消息发到同一队列
producer.send(message, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        String orderId = (String) arg;
        int queueIndex = orderId.hashCode() % mqs.size();
        return mqs.get(Math.abs(queueIndex));
    }
}, order.getOrderId());

// 消费者：使用顺序消费模式
@RocketMQMessageListener(
    topic = "order-topic",
    consumerGroup = "order-group",
    consumeMode = ConsumeMode.ORDERLY  // 顺序消费
)
public class OrderlyMessageListener implements RocketMQListener<OrderMessage> {
    @Override
    public ConsumeOrderlyStatus onMessage(OrderMessage message) {
        try {
            processOrder(message);
            return ConsumeOrderlyStatus.SUCCESS;
        } catch (Exception e) {
            // 顺序消费的重试不需要返回RECONSUME_LATER
            // 而是返回SUSPEND_CURRENT_QUEUE_A_MOMENT
            return ConsumeOrderlyStatus.SUSPEND_CURRENT_QUEUE_A_MOMENT;
        }
    }
}
```

**关于顺序消费的注意事项**：
- 顺序消费会大幅降低吞吐量，因为同一队列的消息被串行处理
- 高并发场景下，建议只对"同一业务实体"的粒度保证顺序（如同一个订单ID），而不是全局顺序
- 顺序消费失败时的处理策略需要谨慎：挂起当前队列会导致该队列后续所有消息都被阻塞

## 三、RocketMQ 深度解析（重点）

RocketMQ是阿里巴巴开源的分布式消息中间件，经过阿里双11万亿级消息的验证，是国内Java技术栈中使用最广泛的消息队列之一。

### 3.1 RocketMQ架构

RocketMQ的架构设计非常简洁清晰，主要包含四个核心角色：

```
                    ┌─────────────────────────────────────┐
                    │           NameServer Cluster         │
                    │  (无状态, 可水平扩展, 彼此不通信)      │
                    └─────┬─────────────────┬─────────────┘
                          │  注册/路由信息     │  注册/路由信息
                    ┌─────▼─────────────────▼─────────────┐
                    │           Broker Cluster             │
                    │  ┌─────────────────────────────┐     │
                    │  │  Broker Master A (主)        │     │
                    │  │  ├─ Broker Slave A1 (从)     │     │
                    │  │  └─ Broker Slave A2 (从)     │     │
                    │  ├─────────────────────────────┤     │
                    │  │  Broker Master B (主)        │     │
                    │  │  └─ Broker Slave B1 (从)     │     │
                    │  └─────────────────────────────┘     │
                    └─────────────────────────────────────┘
                          ▲                        ▲
                          │                        │
                    ┌─────┴────────┐       ┌───────┴──────┐
                    │  Producer    │       │  Consumer    │
                    │  (从NameServer │       │  (从NameServer│
                    │   获取路由)    │       │   获取路由)    │
                    └──────────────┘       └──────────────┘
```

**NameServer**：无状态的注册中心，每个NameServer节点独立运行，彼此不通信。功能类似于Kafka的ZooKeeper，但更轻量。Broker启动时向所有NameServer注册，Producer/Consumer通过NameServer获取Broker路由信息。

**Broker**：消息存储和投递的核心节点。每个Broker可以包含多个Topic，每个Topic包含多个MessageQueue。Broker分为Master和Slave，支持主从同步/异步复制。

**Producer**：消息生产者，从NameServer获取Topic的路由信息（哪些Broker上有哪些Queue），将消息发送到对应的MessageQueue。

**Consumer**：消息消费者，同样从NameServer获取路由信息，以消费者组的形式拉取消息。

### 3.2 RocketMQ消息类型

#### 普通消息

普通消息分为三种发送方式：

```java
// 1. 同步发送（可靠，常用）
SendResult result = producer.send(
    new Message("topic-test", "tag-a", "Hello RocketMQ".getBytes())
);

// 2. 异步发送（高吞吐，适合批量）
producer.asyncSend("topic-test", message, new SendCallback() {
    @Override public void onSuccess(SendResult result) { }
    @Override public void onException(Throwable e) { }
});

// 3. OneWay发送（只发不关心结果，吞吐最高，可靠性最低）
producer.sendOneWay("topic-test", message);
```

#### 顺序消息

保证同一业务Key的消息按照发送顺序被消费。详情见2.3节。

#### 延迟消息

RocketMQ支持18个级别的延迟消息，延迟时间固定不可自定义：

```java
// 延迟级别定义
// 1:1s  2:5s  3:10s  4:30s  5:1m  6:2m  7:3m  8:4m
// 9:5m  10:6m  11:7m  12:8m  13:9m  14:10m  15:20m
// 16:30m  17:1h  18:2h

Message message = new Message("order-topic", "tag-pay", 
    "支付超时取消".getBytes());
message.setDelayTimeLevel(5); // 延迟1分钟投递
producer.send(message);
```

**实现原理**：Broker收到延迟消息后，将其写入名为`SCHEDULE_TOPIC_XXXX`的系统Topic中对应的Queue（延迟级别n -> Queue n-1）。后台定时线程按时间粒度扫描，到达延迟时间的消息被重新投递到目标Topic。

#### 事务消息

RocketMQ的事务消息是其核心亮点，解决了"本地事务"和"消息发送"的分布式一致性问题。

**事务消息流程**：

```
Step 1: Producer发送 Half Message (半消息)
         ──> Broker存储半消息(对消费者不可见)
         
Step 2: Broker返回 Half Message ACK
         <──
         
Step 3: Producer执行本地事务(如插入订单数据)
         ──> 本地数据库操作
         
Step 4a: Producer Commit → Broker投递消息给消费者
Step 4b: Producer Rollback → Broker删除半消息
Step 4c: Producer 返回 UNKNOWN → Broker触发回查

(异常情况)
Step 5: Broker主动回查 Producer 检查本地事务状态
         ──> Producer查询本地事务是否成功
Step 6: Producer返回 Commit/Rollback
```

```java
// 1. 实现事务监听器
public class OrderTransactionListener implements TransactionListener {
    
    @Autowired
    private OrderService orderService;
    
    // 执行本地事务（在发送half消息后调用）
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            // arg中携带了订单信息
            orderService.createOrder((OrderDTO) arg);
            // 本地事务执行成功，提交消息
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            // 本地事务失败，回滚消息
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
    
    // 回查本地事务状态（Broker未收到Commit/Rollback时调用）
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        String orderId = msg.getKeys();
        // 查询数据库，检查订单是否存在
        boolean orderExist = orderService.checkOrderExist(orderId);
        if (orderExist) {
            return LocalTransactionState.COMMIT_MESSAGE;
        } else {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
}

// 2. 创建事务生产者并发送消息
TransactionMQProducer producer = new TransactionMQProducer("tx-producer-group");
producer.setTransactionListener(new OrderTransactionListener());
producer.start();

// 发送事务消息
OrderDTO order = new OrderDTO(); // 订单数据
Message message = new Message("order-topic", "tag-create", 
    order.toJSON().getBytes());
// 将order作为参数传递给executeLocalTransaction
TransactionSendResult result = producer.sendMessageInTransaction(
    message, order);
```

**事务消息的关键设计要点**：
- Half消息对消费者不可见，只有Commit后才可见
- 回查机制是防止"本地事务成功但Commit消息因网络问题未送达"的场景
- 回查次数有限（默认15次），超过后半消息会被标记为丢弃
- 要求业务提供幂等的回查接口

### 3.3 消息过滤

RocketMQ支持两种消息过滤方式：

**Tag过滤（简单模式）**

生产者发送时指定Tag，消费者订阅时按Tag过滤。Broker端直接过滤，性能极高。

```java
// 生产者：发送带Tag的消息
producer.send(new Message("topic-test", "tag-a", msg1.getBytes()));
producer.send(new Message("topic-test", "tag-b", msg2.getBytes()));

// 消费者：订阅特定Tag
@RocketMQMessageListener(topic = "topic-test", 
                         selectorExpression = "tag-a || tag-b")
public class TagFilterListener implements RocketMQListener<MessageExt> {
    // 只接收tag-a或tag-b的消息
}
```

**SQL属性过滤（灵活模式）**

Broker根据消息属性进行SQL表达式过滤，语法类似SQL的WHERE子句。

```java
// 生产者：设置消息属性
Message message = new Message("topic-test", "data".getBytes());
message.putUserProperty("age", "25");
message.putUserProperty("gender", "male");
producer.send(message);

// 消费者：SQL表达式过滤
@RocketMQMessageListener(
    topic = "topic-test",
    selectorType = SelectorType.SQL92,
    selectorExpression = "age > 18 AND gender = 'male'"
)
public class SqlFilterListener implements RocketMQListener<MessageExt> {
    // 只接收 age > 18 且 gender = 'male' 的消息
}
```

### 3.4 消费模式

**CLUSTERING（集群模式，默认）**

同一消费者组内，每条消息只被一个消费者消费。消息负载均衡到组内的所有消费者。

```java
// 集群模式下，组内消费者各分一部分消息
@RocketMQMessageListener(topic = "order-topic", 
                         consumerGroup = "order-group",
                         messageModel = MessageModel.CLUSTERING)
```

**BROADCASTING（广播模式）**

同一消费者组内的每个消费者都会收到Topic下的每一条消息。

```java
@RocketMQMessageListener(topic = "notice-topic",
                         consumerGroup = "notice-group",
                         messageModel = MessageModel.BROADCASTING)
```

### 3.5 消费进度与Offset管理

RocketMQ的消费进度（Offset）记录了消费者组在每个MessageQueue上的消费位置。

**存储方式**：
- **集群模式**：Offset存储在Broker端（`${user.home}/store/config/consumerOffset.json`）
- **广播模式**：Offset存储在消费者本地文件

**从哪开始消费**：

```java
// 消费者在第一次启动或Offset不存在时的行为
// CONSUME_FROM_LAST_OFFSET (默认): 从最新的消息开始消费
// CONSUME_FROM_FIRST_OFFSET: 从最早的消息开始消费
// CONSUME_FROM_TIMESTAMP: 从指定时间戳开始消费

DefaultMQPushConsumer consumer = new DefaultMQPushConsumer("group-test");
consumer.setConsumeFromWhere(ConsumeFromWhere.CONSUME_FROM_FIRST_OFFSET);
consumer.setConsumeTimestamp("20240613120000"); // 配合TIMESTAMP模式
```

### 3.6 消息重试与死信队列

RocketMQ的消费重试机制非常完善。

**重试间隔**：

RocketMQ为每条消息提供了16个级别的重试延迟，消费失败的消息先进入重试队列（Topic名为`%RETRY%{consumerGroup}`），按延迟级别逐步增加等待时间：

```
第1次重试: 10s   第5次重试: 3m    第9次重试: 10m   第13次重试: 1h
第2次重试: 30s   第6次重试: 4m    第10次重试: 20m  第14次重试: 2h
第3次重试: 1m    第7次重试: 5m    第11次重试: 30m  第15次重试: 无
第4次重试: 2m    第8次重试: 6m    第12次重试: 1h   第16次重试: 无
```

**死信队列（Dead Letter Queue, DLQ）**：

当消息重试次数达到最大值（默认16次）后，消息被投递到死信队列。死信队列的Topic名为`%DLQ%{consumerGroup}`。

```java
// 监听死信队列消息（告警或人工处理）
@RocketMQMessageListener(topic = "%DLQ%order-group",
                         consumerGroup = "dlq-alert-group")
public class DlqListener implements RocketMQListener<MessageExt> {
    @Override
    public void onMessage(MessageExt message) {
        // 发送告警通知
        alertService.sendAlert("消息进入死信队列", message);
        // 记录日志，人工介入处理
    }
}
```

### 3.7 高可用与主从切换

RocketMQ的高可用架构经历了三个阶段的演进：

**1. 传统主从模式（手动切换）**

Master宕机后，Slave可以继续提供读服务（消费），但不能写入（生产）。手动修改配置重启Slave为Master。

**2. Dledger模式（自动切换）**

基于Raft协议的自动Leader选举。Dledger是阿里自研的Raft实现，部署时建议用3个节点组成Raft Group。

```yaml
# broker.conf - Dledger模式配置
brokerClusterName = default-cluster
brokerName = broker-a
brokerId = 0
enableDLegerCommitLog = true
dLegerGroup = broker-a-group
dLegerPeers = n0-192.168.1.1:40911;n1-192.168.1.2:40911;n2-192.168.1.3:40911
dLegerSelfId = n0
```

Dledger模式下，集群自动选举Leader，Leader宕机后会自动选主，无需人工干预。

**3. Controller模式（推荐）**

RocketMQ 5.0引入的新模式，引入独立的Controller组件（内嵌或独立部署）来管理Broker的主从切换，不再依赖Dledger的多日志复制限制。Controller模式支持更灵活的部署架构，推荐新项目使用。

## 四、Kafka 核心原理（补充）

Kafka最初由LinkedIn开发，后捐献给Apache基金会，已成为大数据领域事实上的消息队列标准。

### 4.1 Kafka架构

```
                    ┌─────────────────────────┐
                    │   ZooKeeper / KRaft     │
                    │   (集群元数据管理)        │
                    └───────────┬─────────────┘
                                │
┌──────────┐    ┌──────────────┴──────────────────────────────┐    ┌──────────┐
│Producer1 │───▶│              Kafka Cluster                   │───▶│Consumer1 │
├──────────┤    │  ┌─────────┐ ┌─────────┐ ┌─────────┐       │    ├──────────┤
│Producer2 │───▶│  │Broker 1 │ │Broker 2 │ │Broker 3 │       │───▶│Consumer2 │
└──────────┘    │  │ P0 P3   │ │ P1 P4   │ │ P2 P5   │       │    ├──────────┤
                │  │  ▲      │ │  ▲      │ │  ▲      │       │    │Consumer3 │
                │  │  └──────│──└───────│─┴──│────── │       │    └──────────┘
                │  │        Leader      │          │         │
                │  │        ┌───────────┘          │         │
                │  │        │     Follower         │         │
                │  │        ▼                      ▼         │
                │  │ P0(S)   P1(S)               P2(S)      │
                │  └─────────────────────────────────────────┘
                └────────────────────────────────────────────┘
```

**Broker**：Kafka集群由多个Broker组成，每个Broker是一个独立的服务器进程。

**Topic**：消息的逻辑分类，一个Topic包含多个Partition。

**Partition**：Topic的物理分片，每个Partition是一个有序的、不可变的日志文件（append-only log）。Partition是Kafka并行处理的基本单位。

**Segment**：Partition内部由多个Segment组成。每个Segment包含：
- `.log` 文件：消息数据本身，顺序写入
- `.index` 文件：偏移量索引，映射offset到物理位置
- `.timeindex` 文件：时间戳索引，映射时间戳到物理位置

```
Partition-0
├── 00000000000000000000.log      # 第一个Segment (offset从0开始)
├── 00000000000000000000.index
├── 00000000000000000000.timeindex
├── 00000000000000102453.log      # 第二个Segment (offset从102453开始)
├── 00000000000000102453.index
├── 00000000000000102453.timeindex
└── ...
```

### 4.2 高吞吐量的核心原因

Kafka的高吞吐是其最突出的优势，百万级TPS的奥秘来自以下三点：

**1. 顺序写磁盘**

这是Kafka性能最核心的保障。传统消息队列使用随机写磁盘（如数据库索引），磁头需要频繁寻道。Kafka利用**磁盘顺序写**的特性：每个Partition的日志文件只追加写入，不修改已有数据。

```
机械硬盘性能对比:
  随机写: 约 200 IOPS (每秒I/O操作数)
  顺序写: 约 200 MB/s (带宽)

SSD性能趋势类似，顺序写比随机写快约10倍
```

实测数据：在6块7200转SATA盘组成的RAID-5阵列上，Kafka的顺序写可以达到约600MB/s，而随机写通常不到20MB/s，差距超过3个数量级。

**2. 零拷贝（Zero Copy）**

零拷贝是Kafka在消费端实现高性能的关键技术。理解零拷贝需要先看传统的数据传输流程。

**传统数据读取 + 网络发送（4次拷贝 + 2次CPU上下文切换）**：

```
磁盘 → Page Cache (DMA拷贝) → 应用缓冲区 (CPU拷贝) → Socket缓冲区 (CPU拷贝) → 网卡 (DMA拷贝)
  ① DMA读             ② CPU拷贝              ③ CPU拷贝              ④ DMA写
```

**Kafka零拷贝（2次DMA拷贝 + 0次CPU拷贝）**：

```
磁盘 → Page Cache (DMA拷贝) → Socket缓冲区 (DMA拷贝 via SG-DMA) → 网卡
  ① DMA读（送入Page Cache）    ② DMA拷贝（Page Cache → Socket，无需CPU）
```

Kafka使用`FileChannel.transferTo()`方法（底层是`sendfile`系统调用），数据从Page Cache直接发送到网卡，完全绕过应用程序内存。

```java
// Kafka源码中使用零拷贝（FileChannel.transferTo）
// kafka.network.Processor
FileChannel fileChannel = new FileInputStream(logFile).getChannel();
long bytesTransferred = fileChannel.transferTo(position, count, socketChannel);
```

**3. 批量压缩和批量发送**

Kafka在Producer端支持批量发送，将多条消息打包成一个批次（Batch），经过压缩后再发送到Broker。

```java
// Kafka生产者批量配置
properties.put(ProducerConfig.BATCH_SIZE_CONFIG, 16384);     // 16KB批次大小
properties.put(ProducerConfig.LINGER_MS_CONFIG, 10);          // 最多等待10ms
properties.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "snappy"); // Snappy压缩

// 支持的压缩算法: gzip, snappy, lz4, zstd
```

批量发送的好处：减少网络请求次数，提高压缩率（多条相似数据的压缩比更高），降低存储空间。

### 4.3 消费者组与Rebalance

**消费者组**是Kafka实现点对点消息的核心机制。一个Partition在同一个消费者组内只能被一个消费者实例消费，但一个消费者可以消费多个Partition。

```
Topic有4个Partition (P0-P3)

消费者组有2个消费者:
  Consumer-A → P0, P1
  Consumer-B → P2, P3

消费者组有4个消费者:
  Consumer-A → P0
  Consumer-B → P1
  Consumer-C → P2
  Consumer-D → P3

消费者组有5个消费者:
  多余的消费者空闲（无分区可分配）
```

**Rebalance触发时机**：
1. 消费者加入或离开消费者组
2. Topic的分区数发生变化
3. 消费者组订阅的Topic发生变化

**Rebalance分区分配策略**：

```java
// 三种策略配置
properties.put(ConsumerConfig.PARTITION_ASSIGNMENT_STRATEGY_CONFIG,
    RangeAssignor.class.getName());
```

| 策略 | 说明 | 特点 |
|------|------|------|
| **RangeAssignor** | 按Topic分配，每个Topic独立分配 | 可能导致消费者间分区数不均 |
| **RoundRobinAssignor** | 所有Topic的分区轮流分配给消费者 | 分配均匀，但rebalance开销大 |
| **StickyAssignor** | 尽量保持上次分配结果，最小化重分配 | 减少rebalance时的分区移动 |

**Rebalance的问题**：Rebalance期间消费者组停止消费，且可能造成消息重复消费（未提交的offset在新消费者上被重新拉取）。Kafka引入了**静态消费者组**（GroupInstanceId）和**增量式Rebalance**（Cooperative Sticky Assignor）来缓解此问题。

### 4.4 高水位（HW）与LEO

理解HW和LEO是理解Kafka副本同步的核心：

- **LEO（Log End Offset）**：每个副本（Leader和Follower）当前日志的最后一条消息的offset
- **HW（High Watermark，高水位）**：所有ISR副本都已同步的offset位置，消费者只能消费HW之前的消息

```
Leader Partition:
消息: offset:0 | offset:1 | offset:2 | offset:3 | offset:4 | offset:5 |
        已消费区域                    ↑HW=3          未消费区域(不可见)
                                    LEO=6

Follower 1: offset:0 | offset:1 | offset:2 | offset:3 | offset:4 |
                                                            ↑HW=3 LEO=5
Follower 2: offset:0 | offset:1 | offset:2 | offset:3 |
                                                     ↑HW=3 LEO=4
```

**同步机制**：
1. Follower向Leader发起Fetch请求，拉取消息
2. Leader收到Follower的Fetch请求后，更新所有副本的最新LEO
3. 当所有ISR副本的LEO都达到某个位置时，该位置成为新的HW
4. HW会同步给Follower，Follower截断超过HW的消息

**崩溃恢复**：如果Leader宕机，新的Leader会从ISR中选举产生。所有Follower会截断到新Leader的HW位置，保证数据一致性。这意味着HW之后的消息可能丢失（未完全同步的消息）。

### 4.5 ISR（In-Sync Replicas）

ISR是与Leader保持同步的副本集合。Kafka通过ISR机制在"数据一致性"和"可用性"之间取得平衡。

```yaml
# Kafka Broker配置
min.insync.replicas=2     # 最小同步副本数
default.replication.factor=3  # 副本因子
```

**ISR的维护**：
- Follower定期向Leader发送Fetch请求（默认每500ms）
- 如果Follower超过 `replica.lag.time.max.ms`（默认30s）未同步，则被踢出ISR
- 落后Follower赶上Leader后，重新加入ISR

**关键配置**：
- `min.insync.replicas=2`：写入时要求至少有2个副本同步，否则返回异常
- 当ISR大小 < `min.insync.replicas` 时，生产和消费可能不可用（CAP中的CP模式）

**Leader选举**：Kafka从ISR中选举新的Leader。如果ISR为空且 `unclean.leader.election.enable=true`，则允许非ISR副本成为Leader（可能丢数据但保证可用性）。生产中建议关闭此选项。

### 4.6 Kafka消息语义

Kafka提供三种消息传递语义：

**At Most Once（至多一次，可能丢消息）**

```java
// 关闭自动提交，先处理再提交（如果处理失败则不再重新消费）
properties.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, true);
properties.put(ConsumerConfig.AUTO_COMMIT_INTERVAL_MS_CONFIG, 5000);
// 自动提交可能在消费处理前提交，宕机时消息未被处理
```

**At Least Once（至少一次，可能重复）**

```java
// 处理完消息后手动提交
properties.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);

// 先处理业务逻辑，再提交offset
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        process(record);   // 先处理
    }
    consumer.commitSync(); // 后提交（如果处理成功但提交前宕机，消息会重复处理）
}
```

**Exactly Once（精确一次）**

Kafka 0.11+通过**幂等生产者**和**事务**实现精确一次语义。

```java
// 幂等生产者配置
properties.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
properties.put(ProducerConfig.ACKS_CONFIG, "all");

// 事务生产者
properties.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "tx-id-001");
producer.initTransactions();

// 事务性写入：将多个Topic写入包装在一个事务中
producer.beginTransaction();
producer.send(new ProducerRecord<>("topic-a", key, value));
producer.send(new ProducerRecord<>("topic-b", key, value));
producer.commitTransaction();
```

**Kafka Streams精确一次**：流处理场景下，Kafka Streams通过事务确保"处理 + 输出"的原子性，实现端到端的精确一次处理。

### 4.7 RocketMQ vs Kafka 选型对比

| 维度 | RocketMQ | Kafka |
|------|----------|-------|
| **消息模型** | Queue-based，Consumer自行拉取 | Partition-based，Consumer拉取 |
| **顺序消息** | 支持全局严格顺序（单队列） | 分区内有序 |
| **事务消息** | 原生、成熟、半消息+回查 | 0.11+支持，事务协调器 |
| **延迟消息** | 原生18个级别 | 不支持（需应用层实现） |
| **消息过滤** | Tag + SQL92表达式 | 仅Broker端按key过滤 |
| **死信队列** | 原生内置，自动投递 | 需自建或走DLQ Topic |
| **消费重试** | 精细化分级重试 | 无内置重试（seek offset） |
| **运维** | 无ZK依赖，部署简单 | 原依赖ZK，KRaft演进中 |
| **吞吐量** | 10万级/s | 百万级/s |
| **生态** | 国内Java生态广泛 | 大数据生态（Flink/Spark） |

**选型决策**：

- 业务系统（交易、订单、通知）-> **RocketMQ**：事务消息、顺序消息、延迟消息开箱即用
- 大数据/流处理/日志 -> **Kafka**：高吞吐、与Flink/Spark深度集成
- 阿里云/AWS国内云 -> 优先RocketMQ（阿里云RocketMQ商业化成熟）
- Kafka在金融等场景也有广泛应用（经过配置优化）

```java
@Component
public class OrderProducer {
    
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    
    // 发送普通消息
    public void sendOrderMessage(OrderDTO order) {
        rocketMQTemplate.convertAndSend("order-topic:tag-create", order);
    }
    
    // 发送同步消息（带结果）
    public SendResult sendSync(OrderDTO order) {
        Message<OrderDTO> message = MessageBuilder.withPayload(order).build();
        return rocketMQTemplate.syncSend("order-topic", message);
    }
    
    // 发送延迟消息
    public void sendDelayMessage(OrderDTO order, int delayLevel) {
        Message<OrderDTO> message = MessageBuilder.withPayload(order).build();
        rocketMQTemplate.syncSend("order-topic", message, 3000, delayLevel);
    }
    
    // 发送顺序消息
    public void sendOrderlyMessage(List<OrderDTO> orders) {
        for (OrderDTO order : orders) {
            rocketMQTemplate.syncSendOrderly(
                "order-topic", order, order.getOrderId());
        }
    }
    
    // 发送事务消息
    @Transactional
    public void createOrderWithTransaction(OrderDTO order) {
        // 1. 本地事务操作
        orderService.saveOrder(order);
        // 2. 发送事务消息
        Message<OrderDTO> message = MessageBuilder.withPayload(order).build();
        TransactionSendResult result = rocketMQTemplate.sendMessageInTransaction(
            "order-topic", message, order);
    }
}
```

```java
@Component
public class KafkaOrderProducer {
    
    @Autowired
    private KafkaTemplate<String, Object> kafkaTemplate;
    
    // 发送消息（带OrderId作为key，保证同订单消息进入同一分区）
    public void sendOrder(OrderDTO order) {
        ListenableFuture<SendResult<String, Object>> future = 
            kafkaTemplate.send("order-topic", order.getOrderId(), order);
        
        // 异步回调
        future.addCallback(
            result -> log.info("发送成功: offset={}", 
                result.getRecordMetadata().offset()),
            ex -> log.error("发送失败", ex)
        );
    }
    
    // 发送事务消息
    @Transactional
    public void sendWithTransaction(OrderDTO order) {
        kafkaTemplate.executeInTransaction(operations -> {
            operations.send("order-topic-a", order);
            operations.send("order-topic-b", order);
            return true;
        });
    }
    
    // 批量发送（提高吞吐）
    public void sendBatch(List<OrderDTO> orders) {
        orders.forEach(this::sendOrder);
        kafkaTemplate.flush();
    }
}
```

```java
@Component
@Slf4j
public class KafkaOrderConsumer {
    
    // 单条消息消费（手动ACK）
    @KafkaListener(topics = "order-topic", groupId = "order-group")
    public void listenWithAck(ConsumerRecord<String, OrderDTO> record,
                               Acknowledgment ack) {
        try {
            OrderDTO order = record.value();
            log.info("收到消息: offset={}, partition={}, key={}",
                record.offset(), record.partition(), record.key());
            orderService.processOrder(order);
            ack.acknowledge(); // 手动提交偏移量
        } catch (Exception e) {
            log.error("消费失败，稍后重试", e);
            // 不提交offset，下次poll时重新消费
        }
    }
    
    // 批量消费
    @KafkaListener(topics = "order-topic", groupId = "order-batch-group")
    public void listenBatch(List<ConsumerRecord<String, OrderDTO>> records,
                             Acknowledgment ack) {
        try {
            for (ConsumerRecord<String, OrderDTO> record : records) {
                orderService.processOrder(record.value());
            }
        } finally {
            ack.acknowledge(); // 批量提交
        }
    }
    
    // 过滤消费
    @KafkaListener(topics = "order-topic", groupId = "order-filter-group")
    @Headers
    public void listenWithFilter(ConsumerRecord<String, OrderDTO> record,
                                  Acknowledgment ack) {
        if (!"VIP".equals(record.headers().lastHeader("userLevel"))) {
            ack.acknowledge();
            return; // 跳过非VIP用户消息
        }
        orderService.processVipOrder(record.value());
        ack.acknowledge();
    }
    
    // 自定义ErrorHandler（处理消费异常）
    @Bean
    public DefaultErrorHandler kafkaErrorHandler() {
        // 重试3次，每次间隔1秒
        DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(
            kafkaTemplate, 
            (record, ex) -> new TopicPartition("order-topic-dlq", 
                record.partition())
        );
        DefaultErrorHandler handler = new DefaultErrorHandler(recoverer,
            new FixedBackOff(1000L, 3));
        handler.addNotRetryableExceptions(ValidationException.class);
        return handler;
    }
}
```

## 六、总结与核心要点速查

### 消息队列三大核心价值

| 价值 | 说明 | 典型场景 |
|------|------|----------|
| **解耦** | 服务间不直接调用，通过MQ间接通信 | 微服务间事件通知 |
| **异步** | 请求快速返回，后台异步处理 | 注册成功后发邮件/短信 |
| **削峰** | 洪峰流量缓存，匀速消费保护后端 | 秒杀、大促 |

### 消息可靠性三条防线

```
Producer端 (第一道防线)        Broker端 (第二道防线)         Consumer端 (第三道防线)
┌─────────────────┐          ┌─────────────────┐          ┌─────────────────┐
│ 同步发送+回调     │         │ 同步/异步刷盘     │         │ 手动ACK          │
│ 重试机制          │         │ 主从同步/异步复制  │         │ 消费幂等          │
│ 事务消息          │         │ Dledger/Controller│         │ 重试+死信队列     │
│ acks=all         │         │ Raft选主          │         │ 业务状态机        │
└─────────────────┘          └─────────────────┘          └─────────────────┘
```

### RocketMQ vs Kafka 一句话速记

- **RocketMQ**：业务消息之王，事务/顺序/延迟/死信开箱即用，国内面试和岗位首选
- **Kafka**：大数据流引擎，百万吞吐/零拷贝/流处理，大厂面试常考

### 消息队列选型速查表

```
场景                         推荐                 不推荐
─────────────────────────────────────────────────────────
电商核心交易                  RocketMQ            RabbitMQ (吞吐不够)
日志采集/埋点                  Kafka               RabbitMQ/RocketMQ
金融/支付(强一致性)             RocketMQ            Kafka (丢数据风险)
物联网/IoT消息                  Pulsar              RabbitMQ
微服务通知/事件驱动              RabbitMQ            Kafka (太重)
大数据流处理(Flink)             Kafka               RocketMQ
国内云/阿里云                   RocketMQ            Pulsar
```

### 生产环境最佳实践

1. **Producer端**：同步发送 + 重试 + 回调，关键业务开启事务消息或幂等生产者
2. **Broker端**：异步刷盘 + 同步复制（性能与可靠性的最佳平衡）
3. **Consumer端**：手动ACK + 幂等消费 + 合理的重试策略
4. **监控告警**：关注消息堆积量、消费延迟、死信队列
5. **容量规划**：Partition/Queue数量建议为消费者的整数倍，便于负载均衡
6. **消息体**：不宜过大（建议<1MB），大消息异步处理或存到OSS后发URL
7. **Tag使用**：RocketMQ一个Topic建议不超过10个Tag，复杂过滤用SQL属性
8. **运维注意**：Kafka关闭 `unclean.leader.election.enable`，RocketMQ配置Dledger或Controller模式
