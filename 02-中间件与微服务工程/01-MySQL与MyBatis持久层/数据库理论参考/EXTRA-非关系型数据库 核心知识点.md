## 一、核心定义

### 1.1 什么是 NoSQL

**NoSQL（Not Only SQL）** 是一类非关系型数据库的统称，其核心特征：

- **无需预定义表结构**：支持动态扩展字段
- **不依赖 SQL**：有专属的数据操作方式
- **弱化事务**：部分支持弱事务，不严格遵循 ACID，优先保证高性能和高可用
- **多样的数据存储形式**：键值对、文档、列族、图形等
- **易于水平扩展**：适配高并发、大数据量场景

### 1.2 主流产品

| 产品 | 类型 | Bookstore 核心应用 |
|------|------|-------------------|
| **Redis** | 键值型 | 缓存、购物车、登录令牌、库存计数、限流 |
| **MongoDB** | 文档型 | 评论、用户行为日志 |
| **Elasticsearch** | 搜索引擎型 | 书籍全文搜索 |
| **HBase** | 列族型 | 大规模订单历史归档 |

## 二、核心类型及场景适配

### 2.1 键值型数据库（Redis）

- **存储形式**：key-value 键值对，value 支持字符串、哈希、列表、集合、有序集合等类型
- **Bookstore 应用场景**：用户登录令牌、购物车数据、热门书籍缓存、库存计数、接口限流

### 2.2 文档型数据库（MongoDB）

- **存储形式**：JSON 格式的文档，支持嵌套字段，无需固定结构
- **Bookstore 应用场景**：
  - 书籍评论：字段不固定，可包含图片、点赞数、回复
  - 用户行为日志：字段动态扩展

### 2.3 搜索引擎型数据库（Elasticsearch）

- **存储形式**：倒排索引结构，专为全文检索优化
- **Bookstore 应用场景**：书籍全文搜索（按书名、作者、简介模糊检索，支持分词）

### 2.4 列族型数据库（HBase）

- **存储形式**：按列族存储，适配海量结构化数据
- **Bookstore 应用场景**：大规模订单历史数据归档（百万/千万级订单存储）

## 三、Redis 核心应用

### 3.1 核心数据类型及使用场景

#### 字符串（String）

存储用户登录 token、书籍库存、订单编号生成。

```bash
# 用户ID=1的登录令牌
SET user:token:1 "abc123"

# 书籍ID=1的库存
SET book:stock:1 100
```

#### 哈希（Hash）

存储用户购物车（key=cart:user:1，value={bookId:数量, ...}）。

```bash
# 用户1的购物车中，书籍1数量为2
HSET cart:user:1 1 2

# 获取数量
HGET cart:user:1 1
```

#### 列表（List）

存储热门书籍ID（按访问量排序）、订单消息队列。

```bash
# 添加热门书籍ID
LPUSH hot:books 1 3 5

# 获取前10本热门书籍
LRANGE hot:books 0 9
```

#### 有序集合（ZSet）

存储书籍销量排名、用户积分排名。

```bash
# 书籍1销量100，书籍2销量80
ZADD book:sales 100 1 80 2

# 销量前10
ZREVRANGE book:sales 0 9
```

### 3.2 Bookstore 核心应用场景

| 场景 | 说明 | 优势 |
|------|------|------|
| **缓存热门数据** | 首页热门书籍、分类书籍列表缓存到 Redis | 减少 MySQL 查询压力 |
| **购物车存储** | 用户登录后同步到 Redis | 比数据库读写更快 |
| **登录状态保持** | 生成 token 存入 Redis，设置过期时间 | 替代 Session 共享（集群场景） |
| **库存限流** | 秒杀/热销书籍时，用 INCR/DECR 控制库存 | 防止超卖 |
| **接口限流** | 限制单用户/IP 访问频率 | 如登录接口 1 分钟最多 5 次 |

**缓存流程**：

```text
请求 → Redis查询 → 有数据 → 直接返回
                    → 无数据 → 查MySQL → 写入Redis → 返回
```

### 3.3 核心操作命令

| 操作 | 命令 | 说明 |
|------|------|------|
| 新增/修改 | `SET key value EX 3600` | 设置值并指定过期时间 1 小时 |
| 新增/修改 | `HSET hashKey field value` | 设置哈希字段值 |
| 查询 | `GET key` | 获取值 |
| 查询 | `HGET hashKey field` | 获取哈希字段值 |
| 查询 | `LRANGE listKey start end` | 获取列表范围 |
| 删除 | `DEL key` | 删除键 |
| 删除 | `HDEL hashKey field` | 删除哈希字段 |
| 过期设置 | `EXPIRE key 3600` | 设置过期时间 |
| 过期查看 | `TTL key` | 查看剩余过期时间 |
| 原子操作 | `INCR key` | 数值 +1 |
| 原子操作 | `DECR key` | 数值 -1 |
| 原子操作 | `HINCRBY hashKey field num` | 哈希字段数值增减 |

## 四、MongoDB 核心应用

### 4.1 核心存储形式

MongoDB 使用 **BSON（JSON 扩展格式）** 文档存储数据。

```json
{
  "_id": "comment123",
  "bookId": 1,
  "userId": 2,
  "content": "这本书讲解JavaWeb很详细",
  "createTime": "2026-03-16",
  "likeNum": 5,
  "reply": [
    {"userId": 3, "content": "同意，我也觉得不错"}
  ]
}
```

### 4.2 Bookstore 应用场景

- **书籍评论存储**：评论的回复、点赞数等字段动态变化，无需固定表结构
- **用户行为日志**：记录用户浏览、搜索、加购行为，字段可灵活扩展
- **非核心业务数据**：如用户收藏夹（字段简单，无需关联查询）

### 4.3 核心操作

```javascript
// 新增文档
db.comments.insertOne({bookId: 1, userId: 2, content: "好评"});

// 查询文档（按时间倒序）
db.comments.find({bookId: 1}).sort({createTime: -1});

// 修改文档（更新点赞数）
db.comments.updateOne({_id: "comment123"}, {$set: {likeNum: 6}});
```

## 五、关系型 vs 非关系型数据库对比

| 维度 | 关系型数据库（MySQL） | 非关系型数据库（Redis/MongoDB） |
|------|---------------------|-------------------------------|
| **数据结构** | 固定二维表，需预定义结构 | 灵活，无固定结构 |
| **事务支持** | 强事务（ACID） | 弱事务（Redis 仅部分支持） |
| **查询能力** | 复杂关联查询（JOIN）强 | 简单查询快，复杂关联弱 |
| **性能** | 中低并发，适合复杂查询 | 高并发，读写速度极快 |
| **扩展方式** | 垂直扩展（升级硬件）为主 | 水平扩展（增加节点）为主 |
| **Bookstore 用途** | 核心业务数据（用户、订单、书籍） | 缓存、购物车、评论、日志 |

## 六、Bookstore 项目中混合使用策略

### 6.1 核心原则

> 核心业务用 MySQL，非核心/高并发场景用 NoSQL。

### 6.2 具体策略

| 数据库 | 存储内容 | 选型理由 |
|--------|---------|---------|
| **MySQL** | 用户信息、书籍基础信息、订单、订单项 | 需事务和关联查询 |
| **Redis** | 登录 token、购物车、热门书籍缓存、库存计数、限流 | 高并发、快读写 |
| **MongoDB** | 书籍评论、用户行为日志 | 结构灵活，无需关联 |
| **Elasticsearch** | 书籍全文检索数据 | 优化搜索体验 |

### 6.3 数据一致性保证

- **写操作**：先写 MySQL，再更新 Redis（或设置 Redis 过期时间，失效后自动从 MySQL 加载）
- **读操作**：优先读 Redis，缺失则读 MySQL 并回写 Redis
- **避免直接修改 Redis 核心数据**，以 MySQL 为数据最终来源

---

## 七、核心总结

> 1. **NoSQL 数据库** 结构灵活、高性能、易扩展，弥补关系型数据库在高并发、灵活结构场景的不足。
> 2. **Redis** 是 Bookstore 项目的核心 NoSQL 数据库，用于缓存、购物车、登录状态、限流等高频场景。
> 3. 企业开发中采用 **"关系型 + 非关系型"混合架构**：MySQL 存核心业务，Redis 提升性能，MongoDB 适配灵活数据。
> 4. **选型原则**：需事务/关联查询用 MySQL，高并发/灵活结构用 NoSQL，保证数据最终一致性。
