# 索引与查询优化

## 📌 课程定位
索引是数据库性能的核心——一条SQL快还是慢，80%取决于索引设计。理解B+树、聚集索引、覆盖索引、最左前缀，是后端工程师的核心技能。

## 🎯 核心章节

### 1. 索引基础
- **索引是什么**：一种有序的数据结构，帮助快速查找数据
- **索引的代价**：占用磁盘空间 + 写操作(INSERT/UPDATE/DELETE)需要额外维护索引
- **索引不是越多越好**：每个索引都拖慢写操作

### 2. B+树索引（⭐ InnoDB默认）
- **为什么是B+树不是B树？**
  - B+树数据只在叶子层 → 查询路径固定O(log n)，B树数据各层都有 → 不稳定
  - B+树叶层有双向链表 → 范围查询极高效（一次定位+顺序扫描）
  - B+树非叶层只存索引 → 一页能存更多key → 树更矮 → IO次数更少
- **MySQL一页16KB**，3层B+树约存2000万+条数据（约2000³/2=4亿？不，大概2000万）

### 3. 聚集索引 vs 非聚集索引
- **聚集索引（主键索引）**：叶子节点直接存整行数据——一个表只能有一个（InnoDB必须有）
  - 主键建议自增——避免页分裂+保持B+树紧凑
- **非聚集索引（二级索引）**：叶子节点存主键值——需要回表查完整数据
  - **覆盖索引**：查询列全在索引中→不需要回表→EXPLAIN显示Using index（⭐ 重要优化手段）

### 4. 联合索引与最左前缀原则（⭐ 必掌握）
```sql
CREATE INDEX idx_a_b_c ON t(a, b, c);
```
- **最左前缀原则**：B+树按(a,b,c)的优先级排序
  - WHERE a=1 ✅ 走索引
  - WHERE a=1 AND b=2 ✅ 走索引
  - WHERE b=2 ❌ 不走索引（跳过了a）
  - WHERE a=1 AND c=3 ✅ 只用到a列（中间跳过了b，c用不上）
  - WHERE a=1 AND b>2 AND c=3 ✅ a=1走等值，b>2走范围，c=3不走

### 5. 索引失效场景
1. **LIKE 以%开头**：`LIKE '%abc'`→全表扫描，`LIKE 'abc%'`→走索引
2. **隐式类型转换**：`WHERE phone=13800138000`（phone是varchar）→索引失效
3. **OR 条件中部分列无索引**：`WHERE a=1 OR b=2`（b无索引）→可能不走索引
4. **对索引列使用函数/运算**：`WHERE YEAR(create_time)=2024`→失效，改为范围`WHERE create_time BETWEEN '2024-01-01' AND '2024-12-31'`
5. **联合索引不满足最左前缀**：跳过了第一列

### 6. EXPLAIN 执行计划（⭐ 调优必备）
```sql
EXPLAIN SELECT * FROM users WHERE name = 'tom';
```
- **type（最重要！从好到差）**：system > const > eq_ref > ref > range > index > ALL（全表扫描=灾难）
- **key**：实际使用的索引
- **rows**：预估扫描行数——越小越好
- **Extra**：
  - Using index（覆盖索引，好）
  - Using where（在server层过滤）
  - Using filesort（文件排序，差——需要优化）
  - Using temporary（临时表，差——需要优化）
  - Using index condition（ICP——索引条件下推，MySQL 5.6+的优化）

### 7. 慢查询分析
- **开启慢查询日志**：`slow_query_log=ON`, `long_query_time=1`
- **mysqldumpslow**：分析慢查询日志工具
- **SQL优化流程**：
  1. EXPLAIN 看type → 如果是ALL先建索引
  2. 看key → 索引是否被正确使用
  3. 看Extra → 有无filesort/temporary
  4. 必要时刻：profiling 分析SQL各阶段耗时
