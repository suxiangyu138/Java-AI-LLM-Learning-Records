## 一、查询优化核心内容（原书框架）

### 1. 查询优化概述

> 数据库自动选择代价最低的执行计划，提升查询效率。

分为两大类别：

| 优化类型 | 说明 |
|----------|------|
| 逻辑优化 | 关系代数等价变换（选择下推、投影下推等） |
| 物理优化 | 执行算法选择（访问路径、连接算法等） |

### 2. 逻辑查询优化

- 选择下推
- 投影下推
- 连接变换
- 子查询优化
- 等价谓词重写

### 3. 物理查询优化

- 访问路径选择（索引、全表扫描）
- 连接算法选择
- 连接顺序优化

### 4. 代价估算模型

> I/O 代价、CPU 代价、内存代价，基于统计信息计算。

### 5. 启发式规则

- 小表驱动大表
- 先过滤后连接
- 避免笛卡尔积

### 6. 常见优化技术

- 覆盖索引
- 索引下推
- 分区表
- 查询重写

## 二、Java 后端开发视角深度剖析

### （一）逻辑优化：Java 后端 SQL 编写的底层准则

#### 1. 选择下推

先执行 `WHERE` 过滤，再进行连接/分组，减少中间数据量。

> **Java 实践**：查询条件精准，避免大范围数据后过滤。
>
> **反例**：先关联全表再过滤，产生大量临时数据。

#### 2. 投影下推

仅查询业务需要的字段，减少网络传输与内存占用。

> **Java 反例**：`SELECT *`，返回冗余字段，增加序列化开销。

#### 3. 子查询优化

子查询转为 `JOIN`，避免嵌套执行。

> **Java 高频场景**：`IN` 子查询大数据量时，改为 `LEFT JOIN + IS NULL`。

#### 4. 等价谓词重写

- `OR` 转 `UNION`
- `LIKE` 前缀查询
- `NOT EXISTS` 替代 `NOT IN`

> **Java 注意**：避免使用导致索引失效的谓词。

### （二）物理优化：Java 后端索引与执行计划核心

#### 1. 访问路径选择

优化器优先选择索引扫描，避免全表扫描。

> **Java 实践**：高频查询字段建索引，复合索引遵循最左前缀。
>
> **索引失效场景**：函数操作、隐式类型转换、`NOT IN`、`!=`。

#### 2. 连接算法选择

| 算法 | 适用场景 |
|------|----------|
| 嵌套循环连接 | 小表驱动大表，无索引场景适用 |
| 归并连接 | 有序字段关联，利用索引有序性 |
| 哈希连接 | 大数据量关联，内存充足时最优 |

> **Java 后端**：控制关联表数据量，优先使用索引连接。

#### 3. 连接顺序优化

小表驱动大表，减少循环次数。

> **MyBatis 实践**：关联查询时主表数据量小，从表走索引。
>
> **反例**：大表驱动小表，嵌套循环次数爆炸。

### （三）代价估算：Java 后端性能调优依据

#### 1. I/O 代价（核心）

磁盘读写次数决定查询效率。

| 优化方向 | 做法 |
|----------|------|
| 顺序 I/O | 自增 ID 优于 UUID |
| 深度分页 | 避免 `LIMIT 10000, 10`，减少页读取 |

#### 2. CPU 代价

数据计算、排序、分组开销。

> **优化**：`GROUP BY` 字段建索引，避免 `Using filesort`。

#### 3. 统计信息依赖

数据库通过表行数、区分度选择计划。

> **Java 实践**：定期 `ANALYZE TABLE`，更新统计信息。

### （四）启发式规则：Java 后端 SQL 开发规范

1. **避免全表扫描**：高频查询必须建索引，禁止无 `WHERE` 查询
2. **小表驱动大表**：关联查询时，小表作为驱动表
3. **避免使用函数操作索引列**：如 `DATE(create_time)`、`UPPER(name)` 导致索引失效
4. **禁止使用 `SELECT *`**：按需查询字段，减少网络与内存开销
5. **控制连接表数量**：超过 3 张表关联，考虑冗余字段或分库分表

### （五）高级优化技术：Java 后端高并发场景适配

#### 1. 覆盖索引

查询字段全部包含在索引中，避免回表。

> **Java 实践**：复合索引包含查询、排序、分组字段。

#### 2. 索引下推（ICP）

索引过滤条件提前执行，减少回表次数。

> MySQL 5.6+ 支持，Java 后端默认启用。

#### 3. 分区表优化

按时间/ID 分区，查询仅扫描对应分区。

> **适用场景**：日志表、订单表等时序数据。

#### 4. 查询重写

复杂 SQL 拆分为简单 SQL，结合缓存。

> **微服务场景**：跨服务查询拆分，降低数据库压力。

### （六）查询优化与 Java 后端技术栈结合

#### 1. MyBatis 优化

- 动态 SQL 避免全表扫描，精准过滤
- 批量操作：`foreach` 批量插入，减少网络交互

#### 2. 缓存机制

- Redis 缓存热点查询结果，避免重复查询数据库
- 缓存策略：Cache Aside，保证一致性

#### 3. 分库分表

- Sharding-JDBC 水平拆分，降低单表数据量
- 路由键选择：`hash(user_id)`，均匀分布数据

#### 4. 慢查询监控

> 使用 Druid、SkyWalking 监控慢查询，及时优化。定期分析慢查询日志，优化索引与 SQL。

## 三、查询优化对 Java 后端核心价值

1. **提升系统响应速度**：减少慢查询，降低接口响应时间
2. **支撑高并发场景**：降低数据库 CPU、I/O 负载，提升吞吐量
3. **规范 SQL 开发行为**：遵循优化规则，写出高效、可维护的 SQL
4. **降低运维成本**：减少数据库故障，提升系统稳定性

## 四、Java 后端查询优化常见误区

| 误区 | 后果 |
|------|------|
| 索引越多越好 | 增删改性能下降，存储空间浪费 |
| 忽视 SQL 写法影响 | 随意使用函数、隐式转换，导致索引失效 |
| 大表驱动小表 | 关联顺序错误，查询性能急剧下降 |
| 深度分页未优化 | LIMIT 偏移量过大，全表扫描慢查询 |
| 依赖 ORM 自动生成 SQL | 不关注执行计划，产生低效查询 |
