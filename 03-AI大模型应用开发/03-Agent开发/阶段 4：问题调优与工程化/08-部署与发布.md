## 1. 部署的三个前提

```text
前提一：评估就绪（06 篇）——没有门禁的发布是赌命
前提二：可观测就绪（07 篇）——没有追踪的发布是盲飞
前提三：熔断就绪（01 篇）——没有熔断的发布是裸奔
```

> 🎯 **核心要点**：2026 铁律——**"评估 + 可观测 + 熔断"三件套未就绪，Agent 不上生产**。上线后发现缺件 = 带伤上线。

## 2. HITL：人工介入是一等节点

### 2.1 三个触发条件（设计期就定，不是事故后补）

| 触发 | 例子 | 处理 |
|------|------|------|
| 低置信 | judge 分数 < 0.7 | 转人工评审 |
| 高利害 | 转账、删除、外发 | 人工批准 |
| 不可逆 | 覆盖文件、停服 | 人工批准（或禁止） |

### 2.2 实现模式

```python
"""agent/hitl.py — 人工审批节点（LangGraph interrupt 或自建）"""
def approval_node(state):
    """高危动作必须过人工审批——一等节点，不是兜底"""
    action = state["pending_action"]
    if action["level"] == "risky":
        # 挂起会话，通知人工（邮件/IM），等待 approve/deny
        decision = wait_human_approval(action)      # 带超时
        if not decision.approved:
            return {"status": "rejected",
                    "message": f"人工拒绝了操作 {action['name']}"}
        if decision.timed_out:
            return {"status": "timed_out",
                    "message": "审批超时，操作已取消（默认拒绝）"}
    return {"status": "approved"}
```

| 模式 | 行为 |
|------|------|
| kill 模式 | 确定性立即终止（循环/策略违规，不可覆盖） |
| alert 模式 | 暂停 → 通知人工 → 批准/拒绝/延期 → 超时自动终止 |
| 审批工具 | 高危工具挂起，直到人工手动批准 |

> 💡 **合规视角**：EU AI Act 第 14 条（人工监督）2026-08-02 生效——HITL 从最佳实践升级为高风险系统的合规要求。**设计期没有 HITL = 上市期补合规**。

### 2.3 HITL 指标

```text
审批率：多少动作被提交审批（过高 = 自主性不足；过低 = 授权过度）
拒绝率：多少被拒绝（持续高拒绝 = 模型决策质量差）
审批延迟：人工响应时间（超时默认拒绝要写清）
```

## 3. 渐进自主路线

2026 部署共识：**先固定工作流，再逐步放开自主**：

```text
阶段 A：固定工作流（无 LLM 决策）
  → 验证常见用例稳定

阶段 B：LLM 决策 + 全量人工审批
  → 收集真实数据，校准评估

阶段 C：低风险自动 + 高风险审批
  → 稳定性证明后逐步放开

阶段 D：完全自主 + 监控兜底
  → 只有 B/C 阶段数据支撑才进入
```

| 阶段 | 自主度 | 人工参与 | 前置条件 |
|:---:|:---:|:---:|------|
| A | 无 | 全量 | 用例清单 |
| B | 决策 | 全量审批 | 评估套件 |
| C | 低风险 | 高危审批 | 采样评估通过 |
| D | 全自动 | 例外 | 监控 + 熔断 + runbook |

> ⚠️ **自主度与稳定性正相关**——2026 调研：70% 组织"部署速度超过团队准备度"后预计大规模重建系统，原因几乎都是"上线前运维基础（含评估）没就位"。

## 4. 发布形态与 CI/CD

| 形态 | 说明 |
|------|------|
| API 服务 | LangServe / FastAPI 包装（阶段 2 技能复用） |
| 批处理 | 定时任务（报告生成等） |
| 嵌入应用 | 现有系统内嵌 |

**CI/CD 管线（Agent 版）**：

```text
PR → 单元测试 + 评估套件（06 篇四门禁）
   → 安全扫描（依赖/提示词泄露检查）
   → 成本估算（变更影响预算）
   → 通过 → 合并 → 金丝雀（1-5% 流量）
   → 全量（评估通过 + 监控稳定）
   → 版本化（prompt/工具/配置全部版本化）
```

```text
金丝雀决策：新 prompt/模型 1-5% 流量 → 在线采样评估（06 篇）
          → 指标无回归 → 全量
          → 指标回归 → 自动回滚（工具/prompt 版本化支持）
```

## 5. 12 项部署清单

| # | 检查项 | 完成标准 |
|:---:|--------|---------|
| 1 | 工作流基线 | 固定流程先跑通常见用例 |
| 2 | 渐进发布 | 沙箱 → 限量 beta → 全量 |
| 3 | CI 门禁 | 评估套件 + 安全扫描 + 成本估算 |
| 4 | 四层评估 | 单元/工具调用/输出/行为评估就绪 |
| 5 | 离线 + 在线评估 | 回归检测 + 漂移检测 + 失败回流 |
| 6 | 人工审批 | 高利害动作从第一天就需审批 |
| 7 | 监控告警 | 工具错误率/成本尖峰/延迟 + 接收者 |
| 8 | 事故 runbook | 回滚流程/日志诊断/禁用流程 |
| 9 | 合规审查 | 数据流审计（GDPR/HIPAA/个保法） |
| 10 | 全量版本化 | prompt/工具/Agent 逻辑/护栏规则 |
| 11 | 用户培训 | 能力边界/何时确认/如何给好输入 |
| 12 | 失败模式清单 | 注入/过度权限/超时/非幂等/回归/成本失控逐项过 |

## 6. 事故响应 runbook

```text
发现（告警/用户上报）
  → 止血（优先级）：
      ① 熔断/禁用 Agent（kill switch）
      ② 回滚到上一版本（prompt/工具版本化）
      ③ 转人工流程（HITL 兜底）
  → 诊断：trace 回放 + 失败样本取证（07 篇）
  → 修复：根因 → 补评估用例 → 修复代码
  → 复盘：四段式（现象/根因/措施/验证）

自动回滚触发：错误率尖峰 / 行为出护栏 / 成本异常
```

**runbook 必备三件事**：

```text
① 回滚路径：一条命令回到上个版本（含 prompt/工具/护栏）
② 日志诊断：trace_id 定位一次完整会话（用户输入→每一步→最终输出）
③ 禁用流程：kill switch 的操作位置与权限人
```

> 🎯 **核心要点**：部署与发布 = **三前提（评估/可观测/熔断）+ HITL 一等节点 + 渐进自主 + 12 项清单 + runbook**。把 Agent 当"受治理的软件服务"而不是"聪明的提示词"——这句话是 2026 生产化方法论的总纲。
