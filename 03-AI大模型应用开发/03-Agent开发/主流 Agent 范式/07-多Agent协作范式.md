## 1. 为什么需要多 Agent

### 1.1 多 Agent 的动机

```text
多 Agent 协作的动机：
  ① 任务分解：复杂任务拆给多个专业 Agent
  ② 角色分工：不同角色（研究/编码/审查）各司其职
  ③ 并行加速：独立任务并行处理
  ④ 质量提升：评审/辩论提升结果

常见形态：
  Orchestrator-Workers（中央委派）
  团队（角色分工）
  辩论（观点碰撞）
  流水线（接力）
```

### 1.2 多 Agent 的代价

```text
多 Agent 的代价（诚实评估）：
  ① 成本：多个模型实例（token 倍增）
  ② 协调复杂度：通信/上下文传递
  ③ 错误传播：一个 Agent 的错误影响下游
  ④ 延迟：串行协作变慢
  ⑤ 调试困难：多 Agent 轨迹复杂

2025-2026 的关键反思：
  "单 Agent + 强推理模型 > 多 Agent + 弱模型"
  → 先问"真的需要多 Agent 吗？"
```

> 🎯 核心认知：**多 Agent 是"分工协作"而非"越多越好"**——任务分解/角色分工/并行/评审是真实价值，但成本、协调、错误传播是真实代价。2025-2026 的共识：单 Agent（强模型）优先，多 Agent 只在"角色隔离/并行/评审"有明确收益时使用。

## 2. 协作结构模式

### 2.1 四种结构

| 结构 | 形态 | 适用 |
|------|------|------|
| 中央委派（Orchestrator） | 中央分解 → Workers 执行 | 任务可分解 |
| 流水线（Pipeline） | 接力传递（A→B→C） | 顺序依赖 |
| 辩论（Debate） | 多 Agent 观点碰撞 | 质量提升 |
| 团队（Team） | 角色分工协作 | 复杂项目 |

```text
结构的共同要素：
  ① 角色定义（每个 Agent 的职责）
  ② 通信机制（消息/上下文传递）
  ③ 协调者（中央/协议/隐式）
  ④ 结果聚合（汇总/选择/投票）

选择依据：
  任务能否分解 → 委派/流水线
  需要质量保证 → 辩论/评审
  角色天然分离 → 团队
```

### 2.2 消息传递 vs 共享上下文

```text
多 Agent 通信的两种模式：
  ① 消息传递：Agent 间显式通信（消息队列/协议）
     → 松耦合、可扩展
  ② 共享上下文：全部 Agent 读写同一上下文
     → 简单但上下文膨胀

工程权衡：
  消息传递：需要协议（A2A 见第 5 节）
  共享上下文：适合小团队（上下文可控）

2025-2026 趋势：
  消息传递（A2A）标准化
  → 跨平台多 Agent 协作成为可能
```

## 3. Orchestrator-Workers 深入

### 3.1 模式结构

```text
Orchestrator-Workers（02 模块工作流的多 Agent 版）：

  Orchestrator（协调者）：
    ① 分析任务 → 分解子任务
    ② 委派给 Workers（带指令）
    ③ 收集结果 → 汇总/验证

  Workers（执行者）：
    各自执行子任务（专用工具/提示）
    返回结果

流程控制：
  工作流版：代码控制分解（确定）
  Agent 版：Orchestrator 自主分解（动态）
```

### 3.2 工程实现

```text
Orchestrator 的设计要点：
  ① 分解质量（子任务粒度/依赖识别）
  ② 委派指令（上下文传递：任务 + 所需信息）
  ③ 结果汇总（去重/冲突处理）
  ④ 失败处理（Worker 失败重试/重新委派）

Worker 的设计：
  ① 角色明确（单一职责）
  ② 工具专用（领域工具）
  ③ 输出结构化（汇总友好）

2025-2026 实践：
  强模型做 Orchestrator（分解质量关键）
  便宜模型做 Workers（执行简单）
  → 与 PnE 的 Planner/Executor 分工同构
```

### 3.3 适用与边界

```text
Orchestrator 适用：
  任务可分解且子任务独立
  需要动态分解（不确定）
  子任务需要不同工具/模型

不适用：
  子任务强依赖（流水线更合适）
  任务简单（单 Agent 足够）

对比单 Agent：
  单 Agent（强模型）：内部处理一切
  Orchestrator：显式分解（可审计）
  → 需要"分解可审计"时用 Orchestrator
```

## 4. Debate 与评审模式

### 4.1 多 Agent 辩论

```text
Debate（辩论）：多个 Agent 独立生成 + 互相评审

流程：
  ① 各 Agent 独立生成答案（多样化）
  ② 互相评审（指出问题/给分）
  ③ 迭代/聚合（达成一致或投票）

价值：
  减少单一模型的偏见/错误
  多视角覆盖（多样性）

2025-2026 现实：
  辩论成本高（多 Agent × 多轮）
  收益集中在高风险决策
  → 替代：单 Agent + 强反思（更便宜）
```

### 4.2 评审模式（Reviewer）

```text
评审模式：生成 Agent + 评审 Agent（分离）

流程：
  生成 Agent：产出（代码/文档/方案）
  评审 Agent：审查（找问题/评分）
  反馈 → 生成改进（迭代）

与 Self-Refine 的区别：
  Self-Refine：同一模型自我批评
  评审模式：独立 Agent 批评（减少自我确认）

适用：
  有客观标准（测试/规范）
  需要"外部视角"（代码审查/安全评审）

2025-2026 实践：
  代码审查 Agent（找 bug/安全）
  评审者使用不同模型/提示（视角差异）
```

### 4.3 评审的工程要点

```text
评审 Agent 的设计：
  ① 评审标准（检查清单/评分维度）
  ② 视角设计（安全/性能/风格分离）
  ③ 反馈具体性（可执行的问题列表）
  ④ 迭代上限（成本控制）

与验证器的关系：
  评审 Agent ≈ 模型验证器（05 模块）
  确定性验证器（测试）永远优先
  → 评审用于"测试覆盖不到"的质量维度
```

## 5. A2A 协议

### 5.1 什么是 A2A

```text
A2A（Agent-to-Agent，2025-04 发布）：
  Google 主导的 Agent 间通信协议

定位：
  MCP：Agent ↔ 工具（人与工具之间）
  A2A：Agent ↔ Agent（Agent 之间）
  → 两种协议互补（工具层 + 协作层）

核心能力：
  ① Agent 发现（能力描述）
  ② 任务委派（任务卡）
  ③ 进度/结果通信（状态更新）
  ④ 多 Agent 协作（跨平台）

2026 状态：
  A2A 成为多 Agent 协作的标准方向
  （与 MCP 构成 Agent 生态的协议层）
```

### 5.2 A2A 的关键概念

```text
A2A 的核心抽象：
  Agent Card：能力声明（做什么/如何调用）
  Task：委派的任务（状态机：提交→进行→完成）
  Message：Agent 间通信（结构化）

协作流程：
  ① 发现：查询 Agent Card（能力匹配）
  ② 委派：创建 Task（带上下文）
  ③ 执行：Agent 处理（进度更新）
  ④ 完成：返回结果（产物）

与 MCP 的协作：
  MCP：工具访问（Agent 调用工具）
  A2A：Agent 协作（Agent 委派 Agent）
  → 一个 Agent 的"工具"可以是另一个 Agent（A2A 桥接）
```

### 5.3 A2A 的工程意义

```text
A2A 的价值（2025-2026）：
  ① 跨平台协作（不同厂商 Agent 互通）
  ② 标准化委派（任务卡统一）
  ③ 可观测（任务状态标准化）

实践状态：
  规范发布（2025-04）→ 生态跟进中
  Java 生态：A2A SDK（Java）可用
  → 多 Agent 协作的"标准协议"方向

注意：
  A2A 解决"通信"不解决"编排"
  协作结构（委派/辩论）仍需设计
  → 协议 + 范式结合
```

## 6. 2025-2026 的反思与指导

### 6.1 "单 Agent 优先"共识

```text
2025-2026 的明确共识：
  "单 Agent + 强推理模型 + MCP 工具
   优于 多 Agent + 弱模型 + 复杂编排"

理由：
  ① 强模型内化循环（06 模块）→ 外部编排冗余
  ② 多 Agent 的协调成本 > 分工收益（多数场景）
  ③ 错误传播/调试复杂度真实存在

参考案例：
  Claude Code：单 Agent（SWE-bench 87.6%）
  复杂多 Agent 编排的收益常被夸大

指导原则：
  先试单 Agent（强模型）
  有明确理由再加多 Agent
  → "少即是多"（Agent 数量）
```

### 6.2 何时真正需要多 Agent

```text
多 Agent 的合理场景（2025-2026）：
  ① 角色隔离需求（权限/上下文分离）
  ② 并行独立任务（吞吐）
  ③ 外部视角（评审/审计）
  ④ 跨平台协作（A2A 生态）
  ⑤ 超长任务（上下文超限——分 Agent 分上下文）

判断标准：
  单 Agent 失败在"能力"→ 换更强模型
  单 Agent 失败在"隔离/并行/视角"→ 多 Agent
  → 先排除"模型不够强"的可能
```

### 6.3 构建指导

```text
多 Agent 构建五步：
  ① 确认必要性（单 Agent 先试）
  ② 角色定义（最小 Agent 集）
  ③ 通信设计（消息/A2A/共享上下文）
  ④ 协调者（委派/汇总/冲突处理）
  ⑤ 观测护栏（轨迹/预算/人工点）

常见错误：
  角色重叠（职责不清）
  过度通信（上下文爆炸）
  无汇总逻辑（结果拼接）
  忽略失败传播（单点失败扩散）

2026 趋势：
  多 Agent 从"炫技"回归"工程"
  → 结构简单、角色清晰、协议标准（A2A）
```

> 🎯 **核心要点**：多 Agent 协作 = 分工（委派/流水线/辩论/团队）+ 协议（A2A）+ 协调（Orchestrator/汇总）。2025-2026 的清醒共识：**单 Agent（强模型）优先，多 Agent 只在隔离/并行/外部视角有明确收益时使用**——"少即是多"。A2A 协议（2025-04）为跨平台协作提供标准；MCP（工具）与 A2A（协作）构成 Agent 生态的协议双层。
