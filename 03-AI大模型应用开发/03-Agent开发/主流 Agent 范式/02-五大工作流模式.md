## 1. 模式总览

### 1.1 五种模式一览

| 模式 | 核心 | 适用 | 复杂度 |
|------|------|------|:---:|
| Prompt Chaining | 固定顺序流水线 | 清晰分解的步骤 | 低 |
| Routing | 分类后分发 | 异构输入 | 低 |
| Parallelization | 并行扇出 | 独立子任务/投票 | 中 |
| Orchestrator-Workers | 动态分解委派 | 分解不确定 | 中高 |
| Evaluator-Optimizer | 生成-批评循环 | 有明确标准 | 中 |

```text
共同特征（工作流）：
  流程由代码控制（确定性）
  每步是 LLM 调用（工具/提示）
  可测试、可预测、成本可控

使用前提（Anthropic）：
  在升级到 Agent 前"穷尽"这些模式
  大多数任务都能用它们解决
```

### 1.2 模式的使用哲学

```text
Anthropic 的指导：
  "先用这五种模式解决，解决不了再上 Agent"

原因：
  工作流的可靠性（代码控制）
  工作流的可测试性（每步独立验证）
  工作流的成本（无自主探索的浪费）

2025-2026 状态：
  这些模式是生产 Agent 系统的主体
  （多数"Agent 平台"底层就是这些工作流）
  → 掌握五种模式 = 掌握生产主力
```

> 🎯 核心认知：**五大工作流 = 确定性编排的"设计模式"**——它们覆盖了大多数生产任务（固定流程/分类分发/并行/分解/迭代），是升级到 Agent 前的必经阶梯。Anthropic 的告诫：多数任务应止步于此。

## 2. Prompt Chaining

### 2.1 定义

```text
Prompt Chaining：固定顺序的流水线
  任务分解为清晰步骤 → 每步一个 LLM 调用
  前一步输出 → 后一步输入（可选门控）

流程：
  步骤1 → 输出1 →（门控检查）→ 步骤2 → 输出2 → ...

门控（Gates）：
  程序化检查（输出格式/质量阈值）
  不通过 → 提前终止/重试

适用（Anthropic）：
  任务能干净分解为顺序步骤
  每步输出是下一步的必要输入
```

### 2.2 示例

```text
文档生成流水线：
  ① 大纲生成（LLM）
  ② 章节撰写（LLM，输入大纲）
  ③ 格式转换（LLM/代码）
  ④ 质量检查（门控：长度/格式）

代码分析流水线：
  ① 代码提取（代码）
  ② 问题分类（LLM）
  ③ 修复建议（LLM，输入分类）
  ④ 检查修复（门控 + LLM）

适用判断：
  步骤顺序固定 → Chaining
  步骤可交换/并行 → 其他模式
```

### 2.3 优劣

| 优点 | 缺点 |
|------|------|
| 简单（顺序流水线） | 步骤多时延迟累积 |
| 每步可独立测试 | 前步错误传播 |
| 门控提供质量控制 | 灵活性低（固定顺序） |
| 成本可预测 | 不适合并行 |

```text
工程要点：
  门控设计（何时终止/重试）
  步骤间契约（输出格式明确）
  中间结果持久化（调试）
```

## 3. Routing

### 3.1 定义

```text
Routing：分类后分发
  输入分类（LLM/规则）→ 路由到专用处理

流程：
  输入 → 分类器 → 专用提示/模型/工具

分类的粒度：
  提示（同一模型不同提示）
  模型（简单用 Haiku、难用 Sonnet——Anthropic 示例）
  流程（不同工作流）

适用（Anthropic）：
  异构输入需要不同处理
  不同输入类型有各自最优处理方式
```

### 3.2 示例

```text
客户支持路由：
  输入工单 → 分类（退款/技术/投诉）
  → 各路由到专用处理提示/流程

代码问题路由：
  问题类型 → 分类
  → 各路由到专用分析提示

模型路由（成本优化）：
  简单问题 → 小模型（便宜）
  复杂问题 → 大模型（昂贵）
  → 成本节省 30-70%（常见实践）
```

### 3.3 优劣与要点

| 优点 | 缺点 |
|------|------|
| 专用处理（质量高） | 分类错误 → 错误路由 |
| 成本优化（模型分级） | 需维护多个专用提示 |
| 隔离（互不影响） | 分类器本身是依赖点 |

```text
工程要点：
  分类器设计（LLM 分类 vs 规则分类）
  路由失败兜底（默认路径）
  分类质量监控（错误路由率）

2025-2026 实践：
  模型路由（小模型处理简单请求）成为成本优化标配
  → Routing 是"性价比"模式
```

## 4. Parallelization

### 4.1 定义

```text
Parallelization：并行扇出
  任务拆分为独立子任务 → 并行处理 → 聚合

两种形式（Anthropic）：
  ① Sectioning：任务分解为独立部分（并行处理）
  ② Voting：同一任务多次执行（投票取优）

适用（Anthropic）：
  子任务独立（可并行）
  需要低延迟（并行加速）
  需要多样性/鲁棒（投票）
```

### 4.2 两种形式示例

```text
Sectioning（任务分解并行）：
  文档审阅：各章节并行审查 → 汇总意见
  代码审查：安全/性能/风格并行检查 → 汇总报告

Voting（投票并行）：
  代码审查：3 个独立审查 → 汇总（多数一致）
  内容生成：多个生成 → 选择最优（评分）
  → 提升鲁棒性（单一 LLM 的随机性）

适用判断：
  子任务独立 → Sectioning
  结果不确定 → Voting（多次取优）
```

### 4.3 优劣与要点

| 优点 | 缺点 |
|------|------|
| 延迟降低（并行） | 成本倍增（多路调用） |
| 鲁棒性（投票） | 聚合复杂度 |
| 覆盖广（多角度） | 结果一致性挑战 |

```text
工程要点：
  任务独立性判断（不独立则串行）
  聚合逻辑（投票规则/汇总模板）
  成本控制（并行路数）

2025-2026 实践：
  投票模式用于高风险决策（审查/评估）
  并行扇出配合异步（吞吐提升）
```

## 5. Orchestrator-Workers

### 5.1 定义

```text
Orchestrator-Workers：中央 LLM 动态分解委派
  Orchestrator：分析任务 → 分解 → 委派给 Workers
  Workers：执行子任务（专用提示/工具）
  Orchestrator：汇总结果

与 Chaining 的区别：
  Chaining：步骤预定义（代码）
  Orchestrator：分解由 LLM 动态决定

适用（Anthropic）：
  分解方式在设计时不确定
  子任务数量/类型动态变化
```

### 5.2 示例

```text
代码库分析：
  Orchestrator：分析任务 → 决定需要检查哪些模块
  Workers：各模块并行分析（专用工具）
  Orchestrator：汇总发现

研究任务：
  Orchestrator：分解研究问题 → 分配子问题
  Workers：各子问题研究（搜索工具）
  Orchestrator：综合结论

关键：Orchestrator 的"动态性"
  → 子任务列表不是预先写死的
```

### 5.3 优劣与要点

| 优点 | 缺点 |
|------|------|
| 动态分解（灵活） | Orchestrator 是单点 |
| 任务并行（效率） | 分解错误传播 |
| 结构化（可审计） | 复杂度高 |

```text
工程要点：
  Orchestrator 的分解质量（提示设计）
  Worker 的接口契约（输入输出明确）
  汇总逻辑（去重/冲突处理）
  失败处理（Worker 失败重试/降级）

对比 Agent：
  Orchestrator 流程在代码层面（结构化）
  Agent 完全自主（无固定分解）
  → Orchestrator 是"结构化版的动态分解"
```

## 6. Evaluator-Optimizer

### 6.1 定义

```text
Evaluator-Optimizer：生成-批评循环
  生成器：生成答案/方案
  评估器：批评/评分（标准明确）
  循环：根据反馈改进（有上限）

流程：
  生成 → 评估 →（不达标）→ 改进 → 再评估 →（达标/上限）→ 输出

适用（Anthropic）：
  有明确评估标准
  迭代能带来实质改进
  （代码/文案/翻译等"可评判"任务）
```

### 6.2 示例

```text
代码生成循环：
  ① 生成代码（LLM）
  ② 评估（测试运行/代码检查）
  ③ 失败 → 反馈给生成器（错误信息）
  ④ 改进重试（有上限）

文案优化：
  ① 生成文案
  ② 评估（评分标准：清晰度/说服力）
  ③ 反馈改进（多轮）

关键：评估器必须有"可执行的标准"
  （测试、规则、评分模板）
  → 无标准 → 自我确认偏差（05 模块）
```

### 6.3 优劣与要点

| 优点 | 缺点 |
|------|------|
| 质量提升（迭代） | 成本倍增（多轮） |
| 有明确退出条件 | 评估标准难设计 |
| 可控（上限） | 改进可能收敛慢 |

```text
工程要点：
  评估器的标准设计（客观可执行）
  循环上限（成本控制）
  反馈质量（具体反馈 > 笼统批评）

2025-2026 实践：
  与测试驱动结合（代码：测试即评估器）
  与 Reflexion 对比：Evaluator 是工作流（代码控制），
  Reflexion 是范式（模型自我批评）——05 模块
```

## 7. 模式选择

### 7.1 选择决策

```text
模式选择的判断：
  任务可分解为顺序步骤？→ Prompt Chaining
  输入异构需不同处理？→ Routing
  子任务独立可并行？→ Parallelization
  分解方式动态未知？→ Orchestrator-Workers
  有明确标准可迭代？→ Evaluator-Optimizer
  以上都不行？→ Agent 范式（03-07 模块）

组合使用：
  模式可嵌套（Routing → Chaining 子流程）
  模式可混合（Orchestrator 内含 Evaluator）

2025-2026 现实：
  生产系统 = 多种模式的组合
  （框架支持：LangGraph 可编排任意组合）
```

### 7.2 工程清单

```text
工作流工程化五件事：
  ① 步骤契约（输入输出 Schema）
  ② 门控/退出条件
  ③ 失败处理（重试/降级）
  ④ 可观测性（每步日志）
  ⑤ 成本预算（步数/模型分级）

与 Agent 的边界（01 模块）：
  流程可知 → 工作流（本模块）
  流程未知 → Agent（03-07 模块）
  → 先工作流后 Agent（渐进升级）
```

> 🎯 **核心要点**：五大工作流 = 确定性编排的完整工具集——Chaining（顺序）、Routing（分发）、Parallelization（并行）、Orchestrator（动态分解）、Evaluator（迭代优化）。它们是生产 Agent 系统的主体（多数"Agent"实为这些模式的组合）；掌握选择判断（五问）与工程化（契约/门控/失败/观测/预算），就能覆盖大多数生产任务——**升级到 Agent 前先穷尽这五种模式**。
