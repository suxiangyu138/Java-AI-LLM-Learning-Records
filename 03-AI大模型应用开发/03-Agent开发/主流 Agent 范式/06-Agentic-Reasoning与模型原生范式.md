## 1. 范式转变的背景

### 1.1 转变的驱动力

```text
2025-2026 的架构转变：
  规划、工具选择、自我修正从"框架循环"移入"模型推理链"

驱动因素：
  ① 推理模型成熟（o1/R1/Claude Thinking）
  ② 模型内化计划-执行-反思（长思维链）
  ③ 框架循环成为冗余（模型自己做）

结果：
  框架级编排收缩
  "单 Agent + 强推理模型 + MCP 工具
   优于 多 Agent + 弱模型 + 复杂编排"
```

### 1.2 转变的时间线

```text
演进：
  2023：ReAct 循环（外部框架）
  2024：o1 发布（推理时计算，内部思考）
  2025：DeepSeek-R1/Claude 3.7 Thinking
        → 开源推理模型普及
  2025-2026：Model-Native Harness 共识
        → OpenAI/Anthropic/Google 对齐

2026 状态（检索共识）：
  手写 ReAct 循环被视为"legacy"
  模型原生编排成为新默认
  → 但底层思想（推理-行动交替）不变
```

> 🎯 核心认知：**2025-2026 的最大范式转变 = "循环从外部走向内部"**——推理模型把计划-执行-反思放进思维链，框架级编排收缩为"提示 + 工具 + 预算"。范式思想（ReAct/PnE/反思）不变，实现从"代码循环"变成"模型内化"。

## 2. Agentic Reasoning 模型

### 2.1 代表模型

| 模型 | 特点 | 关键 |
|------|------|------|
| OpenAI o1 系列 | 推理时计算（长思考） | 内部计划-反思 |
| DeepSeek-R1 | 开源推理（RL 训练） | 思维链可观察 |
| Claude 3.7+ Thinking | 混合推理（快速/思考） | 可控思考预算 |
| Claude Opus 4.x | 控制循环训练 | 模型卡强调内部循环 |

```text
共同特征：
  ① 生成数千 token 的 <thinking>（内部推理）
  ② 推理链包含：计划 → 执行 → 反思
  ③ 工具调用与推理交织（模型内）

与普通模型的区别：
  普通模型：直接输出（无内部推理）
  推理模型：先思考后回答（推理时计算）
```

### 2.2 推理时计算（Test-time Compute）

```text
推理时计算：把"计算预算"花在推理阶段
  训练时：模型学知识（权重）
  推理时：模型学思考（思维链）

效果：
  长思考 → 复杂任务更好（数学/规划/编码）
  思考预算可调（快速 vs 深度）

与 ToT/Reflexion 的关系：
  推理模型内化搜索（隐式 ToT）
  推理模型内化反思（隐式 Reflexion）
  → 外部显式实现被内化
```

### 2.3 可观察性差异

```text
推理模型的使用差异：
  思维链是否可见：
    o1：隐藏（摘要）
    R1：可见（开源）
    Claude Thinking：可见（可控）
  → 影响调试与审计方式

工程影响：
  可见思维链 → 可审计（R1/Claude）
  隐藏思维链 → 黑盒（o1）
  → 按合规/审计需求选择
```

## 3. 模型内化的循环

### 3.1 内化的内容

```text
推理模型内化的循环（对应外部范式）：
  计划（→ PnE 的 Planner）
  执行（→ ReAct 的 Action）
  反思（→ Reflexion 的自我批评）
  搜索（→ ToT 的分支评估）

示例（思维链内部）：
  <thinking>
  我需要：1) 理解问题 2) 搜索信息 3) 验证
  搜索工具调用... 结果...
  这个结果不完整，尝试另一个角度...
  综合信息，验证逻辑...
  </thinking>
  最终回答

→ 外部循环（框架）被内部循环（模型）替代
```

### 3.2 工具调用的新模式

```text
推理模型 + 工具（新交互模式）：
  模型在思维链中决定何时调用工具
  工具结果作为思维的一部分继续推理
  最终输出答案

对比传统 ReAct：
  传统：框架控制循环（Thought/Action/Observation 格式）
  新：模型控制循环（思维链 + 工具调用原生）

实现：
  模型 API 支持 tool_calls（流式）
  框架只需：提示 + 工具 + 预算
  → 框架职责大幅简化
```

### 3.3 对 Agent 性能的影响

```text
推理模型的 Agent 表现（2025-2026）：
  Claude Opus 4.7：SWE-bench 87.6%（2026-04）
  简单循环 + 强模型 > 复杂编排 + 弱模型

含义：
  ① 模型能力是 Agent 的第一变量
  ② 编排复杂度边际收益递减
  ③ 工具设计仍关键（好工具 + 强模型 = 最佳）

设计启示：
  把预算花在"选好模型 + 设计好工具"
  > 花在"复杂编排/多 Agent"
```

## 4. Model-Native Harness

### 4.1 定义

```text
Model-Native Harness（模型原生编排，2026）：
  OpenAI/Anthropic/Google 对齐的编排方式

组件：
  ① 提示（Prompt）：任务定义 + 边界
  ② 工具（MCP 描述）：工具 schema
  ③ 预算（Budget）：步骤/成本/时间限制
  → 模型内部处理循环

代表：
  Anthropic Managed Agents 平台
  Claude Code Cowork
  OpenAI 的 Agent 运行时
```

### 4.2 平台与产品

```text
Model-Native 的产品形态（2026）：
  Anthropic：Managed Agents（平台托管循环）
  OpenAI：Agents SDK + 托管
  Google：Agent 运行时（Gemini）

共同模式：
  开发者提供：提示 + 工具 + 预算
  平台提供：循环执行、可观测性、护栏

开发者的角色转变：
  从"写循环"到"写提示 + 设计工具"
  → 工具设计（schema）成为核心技能
```

### 4.3 对开发者的意义

```text
开发者需要的新技能：
  ① 提示设计（任务定义 + 边界约束）
  ② 工具设计（schema 精确、描述清晰）
  ③ 预算设计（步骤/成本/风险控制）
  ④ 可观测性（跟踪/审计）
  ⑤ 护栏（安全/合规）

不再需要：
  手写 ReAct 循环（框架/平台处理）
  复杂的多 Agent 编排（模型内化）
  → "少写代码，多设计"

但范式理解仍然必要：
  调试/选型/边界判断依赖原理
  → 本目录 01-05 模块的"思想"不过时
```

## 5. 对既有范式的影响

### 5.1 范式的新定位

| 范式 | 旧角色（外部实现） | 新角色（2025-2026） |
|------|:---:|:---:|
| ReAct | 主循环（手写） | 思想（模型内化/平台实现） |
| PnE | 显式计划器 | 计划产物（可审计）/提示设计 |
| Reflexion | 显式反思循环 | 模型内化（思维链） |
| ToT | 显式搜索 | 模型内化（隐式搜索） |
| 多 Agent | 团队编排 | 简化（单 Agent 优先） |

```text
不变的部分：
  范式思想（推理-行动、计划-执行、生成-批评）
  工具协议（MCP 成为标准）
  护栏（预算/检查点/审计）

变化的部分：
  实现位置（外部 → 模型内/平台）
  开发者职责（写循环 → 写提示设计工具）
```

### 5.2 工作流的地位

```text
重要保留：工作流仍然主流
  确定性流程（02 模块）不受影响：
    固定管道/路由/并行 = 代码控制（模型内化不适用）

Anthropic 的持续告诫：
  "大多数任务用工作流（确定性优先）"
  推理模型让 Agent 更强，但没改变
  "先简单后复杂"的原则

结论：
  工作流（确定性）继续用于流程已知
  Agent（模型原生）用于流程未知
  → 分界线不变（01 模块），实现方式演进
```

### 5.3 对框架的影响

```text
框架的转型（2025-2026）：
  LangGraph：从"手写图"到"原生 Agent 运行时"
  OpenAI Agents SDK：内置循环（模型原生）
  CrewAI：团队抽象（多 Agent 简化）

框架的新职责：
  ① 循环托管（模型原生）
  ② 可观测性（跟踪/审计）
  ③ 护栏（预算/检查点）
  ④ 工具管理（MCP 集成）

Java 生态：
  LangChain4j/Spring AI：工具调用原生支持
  → 推理模型接入（R1/Claude Thinking）
```

## 6. 实践指引

### 6.1 新范式下的构建流程

```text
Model-Native 构建五步：
  ① 选模型：强推理模型（能力第一）
  ② 设计工具：MCP schema（精确/清晰）
  ③ 写提示：任务定义 + 边界 + 预算
  ④ 配护栏：步骤上限/成本/人工检查点
  ⑤ 观测审计：轨迹/成本/质量

预算设计：
  思考预算（Thinking 级别）
  步骤预算（max_steps）
  成本预算（token/调用）

对比旧流程：
  少：循环代码/多 Agent 编排
  多：工具设计/提示精修/护栏配置
```

### 6.2 何时仍用外部范式

```text
仍需显式范式的情况：
  ① 计划产物需要审计（合规）→ 显式 PnE
  ② 每步需要人工确认 → 显式循环 + 检查点
  ③ 弱模型（无内化）→ 外部增强（Reflexion 等）
  ④ 团队协作（多角色）→ 显式多 Agent

选择判断：
  模型足够强？→ Model-Native（简）
  需要审计/控制？→ 显式范式（重）
  → 按需求混合（没有银弹）
```

### 6.3 2026 学习建议

```text
① 理解范式思想（本目录 01-05）——不过时
② 掌握推理模型用法（thinking/工具调用）
③ 精进工具设计（MCP schema）——新核心技能
④ 熟悉 Model-Native 平台（Managed Agents 等）
⑤ 保持工作流优先（确定性流程仍是主流）

配套阅读：
  Agent开发/（P-A-M-E 方法论）
  Agent与MCP协议/（工具协议）
  03-Multi-Agent与MCP协议/（深度）
  04-DeepSeek/（R1 推理模型）
```

> 🎯 **核心要点**：2025-2026 的范式转变 = **循环从外部框架移入模型思维链**——推理模型（o1/R1/Thinking）内化计划-执行-反思，Model-Native Harness（提示 + 工具 + 预算）成为共识。开发者职责从"写循环"转向"选模型 + 设计工具 + 配护栏"；范式思想不过时（调试/选型依赖原理），但实现方式彻底演进。工作流（确定性）依然主流——分界线未变，实现变了。
