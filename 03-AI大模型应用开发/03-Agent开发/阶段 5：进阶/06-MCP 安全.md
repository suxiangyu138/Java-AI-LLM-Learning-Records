## 1. 为什么 MCP 是重点攻击面

```text
MCP 的定位悖论：它是"工具接口的 USB-C"——便利 = 攻击面统一
2026 事实：
├─ 约 20 万 MCP 服务器实例（含 7000+ 公网 IP）
├─ 9/11 公共 MCP 注册表无审查接受恶意包
├─ ≥10 个高危/严重 CVE（LiteLLM、Windsurf、GPT Researcher...）
└─ 安全界结论：MCP 是"默认不可信"的基础设施，不是集成细节
```

> 🎯 **核心要点**：2026 安全共识——**把 MCP 当关键攻击面管理**：资产清单、白名单、沙箱、采购标准四件套，而不是"接上就能用"。

## 2. STDIO RCE 事件复盘（2026-05）

**事件**：OX Security 披露 STDIO 传输的架构级漏洞——**用户可控输入直接流入命令执行，官方 SDK（Python/TS/Java/Rust）无消毒**。

```text
攻击链：恶意输入 → MCP 服务器（stdio 子进程）→ 未消毒的命令执行 → RCE

波及：Claude Code、Cursor、Windsurf、Gemini-CLI 等编码工具
     （零点击提示注入 → 工具执行恶意命令）
```

| 争议焦点 | 立场 |
|---------|------|
| Anthropic | **拒绝修补协议**：STDIO 执行行为"符合设计"，输入消毒是开发者责任 |
| 安全界 | "震惊的缺口"——20 万开发者不可能各自消毒正确 |
| 结果 | ≥10 个 CVE；MCP Inspector 另有 CVSS 9.4 的独立 RCE |

**工程教训**（不管立场如何，防御在你手上）：

```text
① 不连接不可信的 MCP 服务器（注册表默认不可信）
② stdio 服务器不给网络/文件/敏感环境变量权限
③ 服务器进程沙箱化（容器/受限用户）
④ 输入在到达命令执行前必须消毒（永远假设输入是恶意）
```

## 3. 攻击技术家族

| 攻击 | 机制 | 防御 |
|------|------|------|
| **提示注入** | 工具返回内容藏指令 | 工具输出按不可信数据处理（阶段 4 基线） |
| **恶意包分发** | 注册表无审查（9/11 接受 PoC） | 只从可信源安装 + 供应链审查 |
| **过度授权工具** | 服务器声明了超额权限工具 | 最小工具集 + 分级 |
| **混淆代理（Confused Deputy）** | 借 Agent 身份执行越权操作 | 目的绑定凭据 + iss 校验 |
| **请求走私（desync）** | 新版 MCP 头映射滥用 | 头字段不放密钥/敏感数据 |
| **无鉴权远程** | 公网服务器裸奔 | OAuth 2.1 强制 |

## 4. 2026 新版的强化与新增风险

### 4.1 强化（2026-07-28 修订）

| 强化 | 说明 |
|------|------|
| OAuth 2.1/OIDC 授权 | 企业 IdP 路由（与 Okta 联合开发） |
| **强制 iss 校验（SEP 2468）** | 协议级关闭 OAuth mix-up 攻击类 |
| 关闭会话劫持 | 无状态设计消除会话身份复用 |
| 关闭未授权服务器推送 | 服务器不能单方面推提示词 |

### 4.2 新增风险（无状态的代价）

```text
⚠️ 信任决策转移：每个请求都要重建授权上下文 → token 处理负担更重
⚠️ MCP 头映射：密钥/token/个人数据映射进 MCP 头
   → 对负载均衡器、代理、日志系统全部可见（数据泄露面扩大）
⚠️ MCP Apps iframe：服务器渲染的 HTML UI 进沙箱 iframe → 新的审查面
⚠️ 提示注入与工具越权仍是活问题（协议层无法根治）
```

> 💡 **新版安全心态**："协议变安全了，但责任转移到实现者"——2026 修订把安全从协议层推到部署层，**你的安全基线比协议版本更重要**。

## 5. MCP 安全基线六条

| # | 基线 | 落地 |
|:---:|------|------|
| 1 | **资产清单** | 谁在跑哪些 MCP 服务器、什么传输、什么权限（不知有 20 万暴露者无防） |
| 2 | **来源白名单** | 只允许可信源安装；注册表包过供应链审查 |
| 3 | **最小权限** | 服务器最小工具集；进程无网络/文件/敏感环境变量权限；沙箱化 |
| 4 | **鉴权强制** | 远程一律 OAuth 2.1 + iss 校验；凭据短生命周期 |
| 5 | **输入输出双向消毒** | 输入到命令前消毒；工具输出按不可信数据处理 |
| 6 | **监控审计** | 工具调用留痕、异常调用告警（阶段 4 可观测复用） |

```python
"""mcp_security.py — 基线落地骨架"""
ALLOWED_MCP_SOURCES = ["team-registry.internal"]   # ① 白名单
BLOCKED_TOOL_PATTERNS = ["shell", "exec", "fs.write"]   # ③ 最小工具


def audit_mcp_call(server: str, tool: str, args: dict) -> None:
    """⑤⑥ 审计：每次 MCP 调用留痕"""
    log_structured({
        "event": "mcp_call", "server": server,
        "tool": tool, "args_sanitized": sanitize(args),
        "caller": current_agent(), "ts": now(),
    })


def sanitize_input(raw: str) -> str:
    """⑤ 输入消毒：命令执行前必须过（永远假设恶意）"""
    import shlex
    return shlex.quote(raw)
```

## 6. 接入审查清单

接入任何 MCP 服务器前过一遍：

| 检查项 | 标准 |
|--------|------|
| 来源可信？ | 内部构建 / 知名维护者 / 审查过源码 |
| 权限最小？ | 只暴露完成任务所需工具 |
| 传输正确？ | 本地 stdio / 远程 HTTP+鉴权 |
| 鉴权强制？ | OAuth 2.1 + iss 校验 |
| 沙箱隔离？ | 进程级/容器级隔离 |
| 输入消毒？ | 命令执行前过消毒层 |
| 输出降权？ | 结果按不可信数据处理 |
| 审计接入？ | 调用留痕 + 异常告警 |
| 数据合规？ | 不把密钥/token 放 MCP 头 |

> 🎯 **核心要点**：MCP 安全的本质 = **"默认不可信 + 最小权限 + 双向消毒 + 全量审计"**。协议层的强化（OAuth/iss）值得用，但**真正的防线在部署层**——STDIO 事件证明：协议"by design"的缺陷，只能靠你的基线来兜。
