## 1. 延迟分解：慢在哪里

```text
一次 Agent 请求的总延迟 = Σ（模型推理 + 工具 I/O + 编排开销）

2026 关键认知（DynAMO 实测）：
├─ LLM 推理与编排 >90% 的端到端时间
├─ 工具 I/O 只有 ~9%
└─ → 优化重心：推理（缓存/路由），不是工具调用本身
```

| 延迟段 | 占比 | 杠杆 |
|--------|:---:|------|
| LLM 推理（prefill） | 大 | 缓存命中（-50-70% TTFT） |
| LLM 推理（decode） | 中 | 投机采样、模型选择 |
| 工具 I/O | ~9% | 并行执行（-1.6-1.8×） |
| 编排/框架开销 | 小 | 流式展示掩盖 |

> 🎯 **核心要点**：延迟优化的第一问是"**推理段能不能命中缓存**"——2026 年所有延迟优化文章的共识：缓存是 TTFT 的第一大杠杆。

## 2. 杠杆一：Prompt Caching（API 场景首选）

### 2.1 经济学（2026 实测）

| 供应商 | 命中收益 | 写成本 | 回本点 |
|--------|---------|--------|--------|
| Anthropic | 输入成本 -85%，TTFT -50-70% | 125%（5 分钟 TTL）/ 200%（1 小时） | 5 分钟：读 2 次；1 小时：读 3 次 |
| OpenAI | 输入 -90%（≥1024 token 前缀自动） | 无显式写成本 | 前缀稳定即命中 |
| Gemini | 隐式免费缓存 + 显式 Context Caching API | 低 | 长会话必用 |

### 2.2 落地动作（立即做）

```python
"""cache_setup.py — Prompt Caching 落地（2026 基线）"""
CACHE_RULES = """
① 稳定前缀：system prompt + 工具定义放最前，永不动态修改
② 动态内容（检索结果/用户输入）放前缀之后（user 区/消息末尾）
③ 缓存断点：有意的断点设计（Anthropic 最多 4 个/请求）
   —— 系统提示词一个断点，工具定义一个断点，让最大复用段命中
④ 命中率监控：稳态 >80%（<50% 预警）
⑤ 放弃场景：单次 prompt、前缀含随机 token（ID/时间戳）、用户内容前置
"""

# 工具定义固定排序（顺序变 = 前缀变 = 全失效）——阶段 4 已立铁律
# 检查清单：system prompt 冻结了吗？工具顺序固定吗？动态内容在后吗？
```

| 检查项 | 标准 |
|--------|------|
| system prompt 冻结 | 不塞时间戳/随机数/用户数据 |
| 工具定义排序 | 固定（不随会话变化） |
| 动态内容位置 | 固定前缀之后 |
| 命中率 | 稳态 >80%，<50% 告警 |
| 回本核算 | 会话 ≥2-3 轮用 5 分钟缓存才划算 |

## 3. 杠杆二：缓存感知路由（自托管推理）

> ⚠️ **2026 最重要警告**：轮询负载均衡对缓存推理"主动有害"——多区域盲轮询可把前缀缓存命中率打到 8%，TTFT p90 差 57×。

### 3.1 原理

```text
普通路由：轮询/随机 → 请求分散到不同副本 → 每个副本都要重新 prefill
缓存感知路由：按前缀哈希路由 → 相同前缀去同一副本 → KV 缓存命中

参考实现：vLLM Router（PrefixAwareRouter/KvawareRouter）、
         llm-d（CNCF Sandbox，57× TTFT 实测）、
         NVIDIA Dynamo（KV 路由器，prefill/decode 分离）
```

| 实测数据 | 数值 |
|---------|------|
| 缓存命中 vs 未命中 TTFT | ~80ms vs ~800ms（2K prompt，Llama 3.3 70B） |
| llm-d vs 随机路由 | TTFT p90 0.54s vs 92.6s（57×） |
| AWS EKS 实测 | 持续负载下 p90 TTFT 1.4s vs 4.4s |
| 多区域注意 | 跨区域 RTT 65-220ms——远程缓存命中可能不如本地未命中 |

### 3.2 落地要点

| 要点 | 说明 |
|------|------|
| 前缀哈希 | O(1) 查找：前缀哈希 → 副本索引 |
| 负载均衡兜底 | 命中优先 + GPU 利用率/队列深度平局裁决 |
| 防热点 | 纯前缀路由会热点——**前缀 + 负载双打分** |
| 跨区域 | 网络 RTT 计入路由目标（2026 GORGO 方向） |

## 4. 杠杆三：流式与感知延迟

| 手段 | 收益 | 成本 |
|------|------|------|
| 流式输出 | 首字可见，感知延迟大幅改善 | 低（阶段 2 技能） |
| 流式 + partial JSON | 结构化输出感知延迟 -2.1× | 低 |
| 工具轮次进度提示 | "正在查询…"消除空白等待 | 极低 |
| 预热 schema | strict 首请求免编译（-5-8% 首 token） | 极低 |

```python
# 预热 schema：部署时发哑请求，编译缓存（阶段 2 02 篇）
def warm_schemas(client, models: list):
    """部署钩子：预热所有用到的 schema"""
    for schema in models:
        try:
            client.beta.chat.completions.parse(
                model="gpt-4o-mini",
                messages=[{"role": "user", "content": "test"}],
                response_format=schema, max_tokens=1,
            )
        except Exception:
            pass   # 预热失败不阻塞部署，只警告
```

## 5. 杠杆四：并行与投机采样

| 技术 | 原理 | 收益 | 适用 |
|------|------|------|------|
| 并行工具执行 | asyncio.gather 并发独立调用 | -1.6-1.8×（阶段 2 技能） | 多独立调用 |
| 投机采样 | 小模型预 draft，大模型验证 | decode 提速（自托管） | 可预测 token（代码） |
| 推理分离 | prefill/decode 分 GPU | TTFT -11%、TBT -47%（2026 实测） | 自托管重型 |
| 批处理 | 非紧急任务合并请求 | 吞吐提升 | 评估/批任务 |

> ⚠️ **别过度**：单次工具调用 <10ms 时并行开销反超收益；投机采样只在可预测 token 场景有效（阶段 2 结论）。

## 6. 延迟调优决策树

```text
自托管推理？
├─ 是 → 缓存感知路由（最大杠杆）+ 投机采样 + 推理分离（重型）
└─ 否（API 供应商）→ Prompt Caching 前缀冻结（最大杠杆）
                     + 流式体验
                     + 预热 schema
长会话？
├─ 是 → 缓存断点设计 + 上下文压缩（03/04 篇联动）
多独立工具调用？
├─ 是 → 并行执行（-1.6-1.8×）
目标 TTFT：P95 < 1.5s（交互场景参考）
```

> 🎯 **核心要点**：延迟调优四杠杆按序——**缓存（路由或前缀）→ 流式 → 并行 → 投机/分离**。2026 的共识：缓存是第一杠杆，轮询是敌人；感知延迟（流式）是用户体验最快的赢面。
