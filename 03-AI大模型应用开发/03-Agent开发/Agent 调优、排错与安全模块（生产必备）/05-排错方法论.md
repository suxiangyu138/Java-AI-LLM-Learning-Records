## 1. 为什么 Agent 排错不一样

> "Agent 静默失败、模糊失败、事后失败"——2026 排错共识

| 传统软件 | Agent |
|---------|-------|
| 失败即报错 | 静默失败（工具返回空继续） |
| 堆栈定位 | 错误在"哪一步"而非"哪个函数" |
| 确定性复现 | 非确定性（9/10 成功） |
| 单请求视角 | 会话/线程级视角 |
| 问"发生了什么" | 问"哪次变更导致的回归" |

> 🎯 **核心要点**：Agent 排错的第一性原理——**问题不是"发生了什么"（trace 里看得见），是"为什么发生"（哪个 prompt 变更/代码提交/模型切换导致的回归）**。trace-first 是回答"发生了什么"的地基。

## 2. trace-first 五步法

```text
① 复现/取证 —— 拿到失败会话的完整 trace（不猜）
② 差异对比 —— 失败 trace vs 成功 trace / 历史基线（46.2% 案例对比优于单看！）
③ 变更关联 —— 关联部署事件：prompt 变更/模型切换/检索重索引（RCA 核心）
④ 根因假设 —— 数据驱动的假设（不凭感觉）
⑤ 修复+验证 —— 最小修复 + 评估门禁 + 补回归用例
```

| 步 | 关键动作 | 反模式 |
|:---:|---------|--------|
| ① | 完整 trace + 原始输出 | 凭报错猜 |
| ② | 成功/失败对比（AgentFixer：46.2% 案例对比定位更准，无一案例单看更优） | 只分析失败 trace |
| ③ | 变更清单核对（PR/配置/模型版本） | 忽略 7 天前的 PR |
| ④ | 最小复现验证假设 | 假设未验证就动手 |
| ⑤ | 补评估用例 + 版本化 | 修完不补测 |

> 💡 **对比是灵魂**：成功 vs 失败轨迹的差分定位在 46.2% 案例中更准，没有任何案例单看失败轨迹更优（AgentFixer，ACM 2026）——**永远找对照组**。

## 3. trace 关键字段：prompt hash 与工具结果

```python
"""trace_schema.py — trace 关键字段（2026 标准）"""
TRACE_ESSENTIALS = {
    # ① prompt hash：秒判 prompt 是否变了（最重要的诊断信号）
    "prompt_hash": "sha256(prompt)",          # 渲染后 prompt 的哈希
    # ② 全量工具结果：截断 ~8KB（幻觉来源的黄金取证点）
    "tool_result": "truncated_to_8kb",
    # ③ 检索步骤：召回内容 + 重排结果
    "retrieval": {"query", "docs", "scores"},
    # ④ 交接（多 Agent）：交接 payload 必须可检查
    "handoff_payload": "inspectable",
    # ⑤ 会话/线程关联：完整轨迹可回放
    "session_id": "thread_id",
}

"""
为什么 prompt hash 是第 1 信号：
同一输入两次运行 prompt hash 不同 → 有人改了 prompt 或上下文组装
（无需看 diff，秒级定位"变更回归"）
为什么工具结果全量（8KB）：
幻觉的源头常常在工具返回的内容里（截断太短=查不到来源）
"""
```

| 字段 | 诊断价值 |
|------|---------|
| prompt hash | prompt/上下文组装变更检测 |
| 工具结果（8KB） | 幻觉来源取证 |
| 检索内容 | 检索污染定位 |
| 交接 payload | 多 Agent 错误传播定位 |
| 会话回放 | 多轮失败模式可见 |

## 4. 会话级视角：线程比单 trace 重要

> 多轮失败模式（第一轮识别问题、第二轮检索政策、第三轮错误应用）只有看完整会话轨迹才可见——**单 trace 会漏掉大部分多轮故障**。

```text
指标视角切换（2026）：
❌ 单请求：延迟、错误率
✅ 会话级：解决率（resolution rate）、升级率（escalation）、目标完成率

排错视角：
❌ 只看一次调用
✅ 回放完整会话：rewind 到任一步，检查状态，forward 看后果
```

| 会话级能力 | 工具 |
|-----------|------|
| 会话回放 | LangSmith / Langfuse / AgentOps |
| 状态检查 | 回放任意步的状态快照 |
| 多轮轨迹 | 完整对话树（含子 Agent） |
| 失败样本回流 | 问题会话 → 标注 → 回归集（阶段 4） |

## 5. 失败形态分类与修复

2026 已知失败形态速查（与 06 篇速查表联动）：

| 失败形态 | 特征 | 修复 |
|---------|------|------|
| 卡死循环 | 同一工具连续调 8-47 次 | 错误响应标 `retry: false` + 循环计数器（"已调 3 次，禁止再调"） |
| 参数幻觉 | 参数无来源（用户输入/工具结果中不存在） | 工具描述收紧 + enum 参数 + "不知道就问用户" |
| 上下文丢失 | 忘了前几轮 | 上下文组装审计 + 截断保首尾 + 每轮记录渲染后 prompt |
| 规划错误 | 编排器计划形状错 | 检查首个 LLM 调用的计划输出 |
| 上下文累积 | token 线性涨、质量降 | 已完成子任务摘要/裁剪 |
| 多 Agent 交接失败 | 接收 Agent 拿到残缺上下文传播错误 | 交接 payload 必须可检查 |

## 6. 自动 RCA 工具

| 工具 | 能力 | 价值 |
|------|------|------|
| Monte Carlo Troubleshooting Agent | 失败 trace 对比历史基线 + 关联部署事件（PR/模型/配置/prompt diff）→ 根因假设 + 验证清单 | 30-60 分钟人工 → 分钟级 |
| Pathfinder（ACM 2026） | 对抗自博弈：Injector 生成 50 类故障（8 类），Detector 用可执行代码定位（非 RAG） | 自动化失败分类 |
| agent-triage（开源） | 从 system prompt 提取行为策略、跨会话评分、根因分类（prompt/编排/RAG）+ 严重度 + 修复建议 | 策略级诊断 |
| 传统工具链 | LangSmith/Langfuse 对比 + 手动关联部署事件 | 全流程兜底 |

> 💡 **自动 RCA 的边界**：AI 排错工具给"假设 + 证据"，**验证与决策仍是工程师的职责**——工具压缩排查时间，不替代判断。

## 7. 排错工具箱

| 工具 | 定位 |
|------|------|
| LangSmith / Langfuse | trace 平台（会话回放 + 对比） |
| LangGraph Studio | 图可视化调试（多 Agent） |
| OTel + 追踪平台 | 标准埋点（阶段 4 07 篇） |
| 失败样本回流 | 问题会话 → 黄金数据集（阶段 4 06 篇） |
| 自动 RCA | 上述三类工具 |
| 速查表 | 本模块 06 篇（现场查表） |

> 🎯 **核心要点**：排错方法论 = **trace-first（取证）+ 对比（对照组）+ 变更关联（根因）+ 分类修复（形态库）+ 自动 RCA（加速）**。记住三个"永远"：永远先拿完整 trace、永远找成功对照组、永远把变更清单和故障时间线对齐。
