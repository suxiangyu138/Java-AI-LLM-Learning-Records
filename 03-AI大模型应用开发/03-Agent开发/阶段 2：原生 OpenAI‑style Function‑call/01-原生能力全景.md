## 2. 升级点逐项对照

### 2.1 格式保证升级：从"prompt 建议"到"协议约束"

| 层级 | 机制 | 保证 | 阶段 |
|------|------|------|:---:|
| prompt 要求 | "请输出 JSON" | 2026 前沿模型仍约 0.4% 失效 | 1 |
| 修复循环 | 校验失败带错误重试 | >95% 恢复（有限次） | 1 |
| **约束解码（strict）** | 采样期物理屏蔽非法 token | **99.5%+ schema 合规** | **2** |
| 工具调用（原生） | 服务端结构保证 | 工具参数结构天然受控 | 2 |

### 2.2 执行模型升级：串行 → 并行

| 维度 | 阶段 1 | 阶段 2 |
|------|--------|--------|
| 工具执行 | for 循环串行 | asyncio.gather 并发 |
| 延迟 | 工具耗时累加 | 取最慢者（实测 1.6-1.8× 收益） |
| 结果配对 | 按顺序 | **按 id**（乱序到达） |
| 失败处理 | 单点失败即断 | 部分失败优雅降级 |

### 2.3 状态管理升级：客户端全程 → 服务端辅助

| 维度 | 阶段 1 | 阶段 2（Responses） |
|------|--------|-------------------|
| 历史传递 | 客户端维护 messages 数组，每轮全量重发 | `previous_response_id` 链式引用 |
| 推理模型上下文 | 不支持跨轮 | KV 缓存跨轮复用（40-80% 缓存利用率提升） |
| 内置工具 | 无 | web_search / code_interpreter 等平台托管执行 |

## 3. 能力归属：Chat Completions vs Responses API

| 能力 | Chat Completions | Responses API |
|------|:---:|:---:|
| 自定义函数工具（`function`） | ✅ | ✅ |
| 并行 tool_calls | ✅ | ✅ |
| Strict Structured Output | ✅ `response_format` | ✅ `text.format` |
| JSON Mode（旧） | ✅ | ⚠️ 迁移至 json_schema |
| 流式 | delta 拼接 | 语义事件 |
| 内置工具（web_search 等） | ❌ | ✅ |
| previous_response_id | ❌ | ✅ |
| 服务端会话存储 | ❌ | ✅（store: true） |
| 推理上下文跨轮 | ❌ | ✅ |
| 非 OpenAI 兼容（DeepSeek 等） | ✅（事实标准） | ❌（仅 OpenAI） |

> 💡 **选型速判**：只调自定义函数 + 多供应商 → Chat Completions（协议通吃）；纯 OpenAI 新项目 + 要内置工具/托管状态 → Responses。

## 4. 学习策略：按需升级而非全面重写

```text
评估你的项目（按优先级自问）：
① 输出格式频繁坏？        → 升级 Structured Output（02/03）
② 工具调用多且独立？      → 升级并行（04）
③ 用户体验要求首字快？    → 升级流式（05）
④ 需要搜索/代码执行内置？ → 评估 Responses（07）
⑤ 都暂时不需要？          → 先学 02 + 06（最普适），其余按需
```

> ⚠️ **不要为了升级而升级**：阶段 1 的循环在 90% 场景完全够用。本阶段是**能力库**——生产时按需调用，不是强制迁移。

> 🎯 **核心要点**：原生能力全景 = 一张"痛点 → 能力"的映射表。学完本阶段，你看到任何一个 Agent 工程痛点，都能说出对应的原生解法。
