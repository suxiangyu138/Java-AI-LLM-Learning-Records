## 1. 并行的收益与边界

### 1.1 收益（2026 实测数据）

| 场景 | 收益 |
|------|------|
| 独立工具调用（DynAMO 工业工作流） | 端到端延迟降 **1.6× 中位 / 1.8× 最佳** |
| SWE-bench（AsyncFC） | 1.44× 提速，无显著准确率损失 |
| 多调用工具延迟 | 独立调用合计降 70-90% |
| 延迟方差 | 标准差降 >2.4×（最坏情况更可预期） |

### 1.2 边界（什么时候并行没用）

```text
❌ 严格线性链：B 依赖 A 的输出 → 并行零收益（DynAMO 实测近乎零提升）
❌ 单次工具延迟极低（<10ms）→ 并行开销反而更慢
❌ 推理是瓶颈：工具 I/O 只占 ~9% 端到端时间（LLM 推理 >90%）
```

> 🎯 **核心要点**：并行优化的是"工具 I/O 重叠"，不是"推理加速"。模型一次返回多个独立调用时并行才有效——**先做依赖分析，再谈并发**。

## 2. 依赖分析：哪些能并行

| 依赖关系 | 例子 | 策略 |
|---------|------|------|
| 完全独立 | 查北京天气 + 查东京天气 | ✅ 并行 |
| 输入依赖 | 先搜文章 → 再总结文章 | ❌ 串行（或拆成两轮） |
| 副作用顺序 | 先创建再删除 | ❌ 串行 |
| 部分重叠 | 共享同一份缓存数据 | ✅ 并行（共享只读资源） |

**工程判定法**：

```text
问三个问题：
① 工具 B 的参数是否包含工具 A 的结果？  → 是则串行
② 两个工具是否有写副作用？            → 任一写则串行
③ 是否依赖共享的可变状态？            → 是则串行
全否 → 并行
```

## 3. asyncio 并发执行（正确姿势）

### 3.1 为什么用 asyncio 而不是 ThreadPoolExecutor

> ⚠️ **2026 实测结论（The Neural Base）**：Python GIL 下 `ThreadPoolExecutor` 对真实 HTTP 阻塞 I/O **不保证真并发**——用 `async/await + asyncio.gather()`。

```python
import asyncio
import json

async def execute_tool_async(name: str, args: dict) -> tuple[str, dict]:
    """异步执行单个工具：返回 (工具结果字符串, 原始调用信息)"""
    # 实际工具调用可以是 aiohttp/httpx 异步请求
    await asyncio.sleep(0.2)   # 模拟真实 I/O
    return json.dumps({"ok": True, "name": name, **args}, ensure_ascii=False)


async def run_parallel_tools(tool_calls) -> list[dict]:
    """并发执行模型返回的所有工具调用"""
    tasks = [
        asyncio.create_task(
            execute_tool_async(tc.function.name,
                               json.loads(tc.function.arguments or "{}"))
        )
        for tc in tool_calls
    ]
    # 全部等待；单个失败不炸整体（return_exceptions=True）
    results = await asyncio.gather(*tasks, return_exceptions=True)

    # 逐条配对回传（顺序与 tool_calls 对应）
    tool_messages = []
    for tc, res in zip(tool_calls, results):
        if isinstance(res, Exception):
            content = json.dumps({"error": f"{type(res).__name__}: {res}"},
                                 ensure_ascii=False)
        else:
            content = res
        tool_messages.append({
            "role": "tool",
            "tool_call_id": tc.id,       # ★ 原样 id
            "content": content,
        })
    return tool_messages
```

### 3.2 完整并行循环（合并进 Agent 主循环）

```python
async def agent_loop_parallel(messages, tools, max_turns=10):
    for _ in range(max_turns):
        response = client.chat.completions.create(
            model="deepseek-v4-flash", messages=messages, tools=tools,
            parallel_tool_calls=True,        # 允许模型一次返回多个
        )
        msg = response.choices[0].message
        messages.append(msg)
        if not msg.tool_calls:
            return msg.content
        messages.extend(await run_parallel_tools(msg.tool_calls))   # ← 并发执行
    return "（已达最大轮数）"
```

| 要点 | 说明 |
|------|------|
| `parallel_tool_calls: true` | 默认即开；模型自行决定一次返回几个 |
| `asyncio.gather(return_exceptions=True)` | 单任务异常不炸整体 |
| 每任务独立超时 | `asyncio.wait_for(task, timeout)` 按工具 SLA 配置 |

## 4. 结果配对：永远按 id

> ⚠️ 并行执行返回**乱序**——`as_completed` 不保证提交顺序。**必须按 `tool_call_id` 配对，绝不按数组位置**。

```text
❌ 危险：结果数组[0] 对应调用[0]（并发下可能错位 → 张冠李戴）
✅ 正确：每个结果记录自己的 call_id，回传时按 id 找对应调用
```

**乱序到达的高级形态**（2026 前沿）：工具完成后"先到先回"，模型在后续轮次里按 id 认领结果——要求模型不编造未到结果（AsyncFC future-based 模式，SWE-bench 1.44× 无准确率损失）。

## 5. 部分失败：优雅降级

并行放大了失败面——**不要让单个失败拖垮整批**：

| 策略 | 做法 |
|------|------|
| 不炸整体 | `return_exceptions=True`，异常转错误 JSON |
| 标记失败 | 失败工具在结果中带 `{"error": ...}`，模型自行决定重试/降级/告知用户 |
| 分支隔离 | 非关键分支超时 → 隔离异常，其余分支继续（DynAMO 故障注入实测） |
| 每工具超时 | 按 SLA 配置（搜索 5s、数据库 10s 等） |

## 6. 并行 × strict 的冲突

| 冲突 | 场景 | 解法 |
|------|------|------|
| 精确形状保证 | 每个工具参数必须精确匹配 schema | `parallel_tool_calls: false`（交错到达破坏形状保证） |
| 有状态工具 | 并行执行状态竞争 | 代码层强制串行（跳过并发） |
| 限流 | max_workers 超过供应商限额 | 并发数 ≤ 限流配额；指数退避保留 |

## 7. 可观测与安全

| 维度 | 实践 |
|------|------|
| 追踪 | OTel 把并发工具的每个调用作为子 span，trace 贯穿会话（失败归因：上游输入 vs 上下文饱和 vs 输出冲突） |
| 日志 | 每次并行批次记录：调用数、成功/失败数、耗时分布 |
| 权限 | 并行不改变权限模型——每个工具仍按 L0-L3 分级（见失败模式 08 篇） |
| 秘密 | 工具结果含密钥时**不进上下文**——用 SecretRef 占位符，执行时解析 |

> 🎯 **核心要点**：并行工程化的四条铁律——**依赖分析先行、asyncio.gather 并发、按 id 配对、部分失败降级**。收益 1.6× 是"工具 I/O 重叠"换来的，别指望它加速推理。
