## 1. 五大框架的范式分类

```text
2026 单 Agent 框架 = 五种"范式"，不是五个"同类工具"：

┌─────────────────────────────────────────────────────────────┐
│ 状态机范式    LangGraph        显式图 + 共享状态 + 持久化       │
│ 轻量原语范式  OpenAI Agents SDK 最小原语集 + 会话 + 护栏        │
│ 代码执行范式  Smolagents        Agent 写 Python 而非 JSON 调用  │
│ 类型安全范式  Pydantic AI       Pydantic 校验一切 + 可插拔能力   │
│ 完整 harness  Claude Agent SDK Claude Code 打包为库            │
└─────────────────────────────────────────────────────────────┘

选择框架 = 选择范式：范式的取舍决定了能力的边界，
细节差异（API 风格）都是次要的
```

> 🎯 **一句话**：别按"哪个框架流行"选，按"我的 Agent 属于哪种形态"选——任务状态复杂选状态机，输出必须结构化选类型安全，任务本质是写代码选代码执行。

## 2. 各框架生态位速览

| 框架 | 范式 | 核心抽象 | 强项 | 弱项 | 语言 |
|------|------|---------|------|------|------|
| LangGraph | 状态机 | StateGraph / create_agent + checkpointer | 复杂状态流、持久化、HITL、时间旅行；"第 7 步挂了怎么办"有原生答案 | 抽象重、学习曲线陡、简单聊天杀鸡用牛刀 | Python/JS |
| OpenAI Agents SDK | 轻量原语 | Agent + Handoff + Guardrail + Session + Trace | 半天上手、OpenAI 生态原生、handoff 链天然对应客服分流 | OpenAI 模型优先、类型安全弱于 Pydantic AI、复杂流程要自己编排 | Python/TS |
| Smolagents | 代码执行 | CodeAgent / ToolCallingAgent | 多步任务省 ~30% 步数与 LLM 调用、代码可读可审计、模型无关（含本地模型） | 极简=生态靠你自己；沙箱非自动；单线程执行 | Python |
| Pydantic AI | 类型安全 | Agent + Pydantic 模型 + Capability | 类型安全最强、40+ 模型供应商、原生 MCP、Logfire/OTel 内置、v2 Capability 可插拔 | Python only；pre-1.0 演进快需锁版本；多 Agent 编排薄 | Python |
| Claude Agent SDK | 完整 harness | query() / ClaudeSDKClient + ClaudeAgentOptions | 开箱即用的 Claude Code harness（文件/bash/网页/子 Agent）、hooks、权限六模式、自动压缩 | 绑定 Claude 生态；语言限 Python/TS；其他语言要跑 CLI 子进程 | Python/TS |

### 2.1 一个决策实例（ADR 视角）

> 某团队 2026 的框架选型 ADR（rmednitzer/agents）评估后弃用 LangGraph 作为默认运行时——理由：抽象重、依赖面大、学习曲线陡。最终选 Pydantic AI：类型化 I/O、多供应商可移植、原生 MCP 支持。结论并非"LangGraph 不好"，而是"默认运行时要轻"——复杂状态流场景他们仍会临时引入图框架。

**启示**：选型要写 ADR（决策记录），记录"评估了什么、为什么选、代价是什么"——换框架时有据可查。

## 3. 选型决策树

```text
开始
│
├─ 需要"用代码完成任务"（文件操作/数据处理/自动化）？
│   └─ 是 → Smolagents（代码执行天然优势；多步任务省 30% 调用）
│
├─ 输出必须是强类型结构化数据（提取/校验/工具结果）？
│   ├─ 是 → Pydantic AI（类型安全是它的存在理由）
│   └─ 否 ↓
│
├─ 深度绑定 OpenAI 模型生态（Responses API/直连）？
│   ├─ 是 → OpenAI Agents SDK（官方原语，半天上手）
│   └─ 否 ↓
│
├─ 任务需要复杂状态流/多分支/暂停恢复/持久化？
│   ├─ 是 → LangGraph（StateGraph + checkpointer 无人能比）
│   └─ 否 ↓
│
├─ 要开箱即用的完整 harness（文件/网页/子 Agent 全内置）？
│   ├─ 是 → Claude Agent SDK（Claude Code 能力直接嵌入）
│   └─ 否 ↓
│
└─ 简单对话/单轮工具调用？
    └─ Pydantic AI（最轻且类型安全）或 OpenAI Agents SDK（OpenAI 用户）
```

## 4. 框架不可知论：MCP/A2A 与组合使用

### 4.1 2026 选型共识

```text
1. 没有单一赢家——五大框架生态位不同，选型是"匹配"不是"排名"
2. 生产系统多框架组合是常态：
   LangGraph 管编排 + Pydantic AI 管结构化工具输出
   Claude Agent SDK 管主循环 + 子 Agent 用轻量框架
3. MCP 协议让"工具"与框架解耦：工具一次实现，五框架通用
4. A2A 协议让"Agent"与框架解耦：跨框架 Agent 可互调
5. 适配器模式（ADR 0001）：把运行时藏在接口后，换框架不换业务代码
```

### 4.2 组合示例

```text
场景：客服 Agent（查询 + 退款审批）
  Claude Agent SDK 主循环（harness 完整、hooks 做审批门）
  └─ 工具层走 MCP（订单查询 server 一次实现）
  退款金额校验用确定性代码（工程化模块混合架构）
  结构化输出用 output_format json_schema（SDK 原生支持）
```

## 5. Java 侧对照

| Python 框架 | Java 对照 | 说明 |
|------------|----------|------|
| LangGraph | LangChain4j（AiServices） | Java 侧主流；链路式而非图式 |
| OpenAI Agents SDK | Spring AI（ChatClient + ToolCallingAdvisor） | 见 [Java AI 生态体系](../../../05-AI开发框架/Java%20AI生态/00-Java%20AI生态总览.md) |
| Claude Agent SDK | 无 Java SDK | 官方仅 Python/TS；Java 用 CLI 子进程或直接 API |

> Java 学习者注意：本模块以 Python 框架为主（单 Agent 框架的生态重心在 Python），但 07 章"循环通用架构"与 08 章"能力对比"的结论对 Java 侧同样适用——框架本质是 agent loop + 工具 + 上下文的组合。

## 6. 选型陷阱

| 陷阱 | 症状 | 修正 |
|------|------|------|
| 追新不追匹配 | 简单聊天上了 LangGraph | 按决策树先分类任务形态 |
| 绑定单一闭源 | Assistants API 弃用后迁移痛苦 | 2026 教训：新项目用 Agents SDK/Responses API；评估数据可导出 |
| 忽略版本漂移 | Pydantic AI v1→v2 破坏性变更 | pre-1.0 框架锁版本 + 跟进 changelog |
| 框架全能错觉 | 一个框架硬扛所有场景 | 组合使用（编排/结构化/工具分层） |
| 把框架当架构 | MCP 是集成层，不是架构起点 | 先设计工具契约，再选框架接入 |
| 忽略 harness 差异 | 换框架后行为大变 | 评估门禁 + 版本快照（工程化模块 06/10 篇） |
