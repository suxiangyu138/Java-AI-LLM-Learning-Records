## 1. 为什么要先验证再写码

```text
手写 Agent 框架的沉没成本：
LangGraph/OpenAI SDK/Claude Agent SDK 学习曲线 → 1-2 周
真实需求调研（用户要什么、流程怎么走）→ 更关键但常被跳过
→ 直接写码的最大风险：花 3 周写了一个没人要的 Agent

低代码平台的价值：把"验证需求"与"技术实现"解耦
需求不确定 → 平台 1-3 天出原型 → 给用户试 → 验证/推翻
→ 需求确定了 → 再决定：平台直接用 or 迁移代码框架
```

> 🎯 **一句话**：低代码平台是 Agent 开发的"最小可行原型（MVP）加速器"——先用 10% 的成本验证 90% 的需求不确定性，再决定后续投入。

## 2. 验证什么：五问验证法

| 问题 | 验证方式 | 通过标准 |
|------|---------|---------|
| ① 用户真的要吗？ | 原型给 5-10 个真实用户试 | 3 人以上主动复购使用/要求继续 |
| ② 流程对吗？ | 跟踪用户的真实对话路径 | 80% 以上会话符合预期流程 |
| ③ 模型能力够吗？ | 20+ 典型用例跑分（准确率/完成率） | 核心用例完成率 ≥ 80% |
| ④ RAG 效果行吗？ | 知识库检索命中率测试 | 检索命中率 ≥ 80%，幻觉率可接受 |
| ⑤ 成本可控吗？ | 估算单次对话 token 成本 × 预期量 | 单次成本 × 月量在预算内 |

> 💡 **验证的真正产出**：不是"原型本身"，而是这五个问题的**数据化答案**——迁移与否的决策依据是数据，不是感觉。

## 3. 验证流程：三天验证模板

```text
Day 1：需求切片 + 平台选型
  ├─ 从需求里切出 1 个核心闭环（含 RAG + 1 次工具调用）
  ├─ 按 01/08 篇决策树选平台（默认 Dify 或 Coze）
  └─ 搭好平台（Docker 或云账号）

Day 2：原型搭建 + 用例准备
  ├─ 画布搭出核心流程（知识库上传 → 检索 → 生成 → 工具调用）
  ├─ 准备 20 个典型用例（10 正常 + 5 边界 + 5 刁钻）
  └─ 配好模型（按预算选，注意 BYO Key）

Day 3：实测 + 记录 + 决策
  ├─ 跑 20 用例，记录完成率与失败模式
  ├─ 给 2-3 个真实用户试，收集反馈
  └─ 按五问填表 → 决策：平台即终态 / 迁移 / 放弃
```

**常见失败模式与对策**：

| 失败模式 | 表现 | 对策 |
|---------|------|------|
| 幻觉严重 | 回答自信但错误 | 加强 RAG 检索 + 提示词约束 + 引用来源 |
| 工具调用错乱 | 顺序错/参数错 | 简化工具、改名改描述、减少并行 |
| 流程发散 | Agent 偏离目标 | 改用 Workflow 确定性流程约束关键路径 |
| 延迟过高 | 单轮 > 10s | 换快模型、减上下文、开流式 |

## 4. 低代码 vs 手写框架：全面对比

| 维度 | 低代码平台 | 代码框架（LangGraph/OpenAI SDK/Claude Agent SDK） |
|------|-----------|--------------------------------------------------|
| 上手速度 | 小时级（Coze 甚至分钟级） | 1-2 周（含学习） |
| 需求验证 | ●●● | ● |
| 复杂状态/图编排 | ●（受限） | ●●●（状态机/时间旅行/持久化） |
| 深度定制 | ● | ●●● |
| 细粒度控制 | ● | ●●● |
| 可测试性 | ●●（平台评估） | ●●●（CI/单测/回放） |
| 可观测 | ●●（平台内置） | ●●●（OTel 全链路） |
| 运维 | 平台托管/少 | 自己管（部署/监控/升级） |
| 成本 | 平台费+模型费（自托管=人力） | 全部自己承担 |
| 锁定 | 平台锁定（流程难迁） | 代码是资产，可迁移 |
| 适合阶段 | **验证/原型/中等生产** | **生产/复杂/大规模** |

> 🎯 **本质差异**：低代码平台卖的是"**解决 80% 常见场景的成品架构**"，代码框架卖的是"**100% 场景的原材料**"——前者适合需求不确定期，后者适合需求确定后的长期资产。

## 5. 平台即终态：什么情况不用迁移

```text
以下情况，低代码平台就是终态（不用迁移）：
✓ 流程中等复杂度、DAG 能表达（无图级状态需求）
✓ 交付形态平台已覆盖（Web App / API / 嵌入）
✓ 吞吐量在平台能力内（并发几十到几百）
✓ 团队没有深度定制需求（UI/控制流/底层）
✓ 平台许可满足商用
典型：客服知识库 Agent、内部运营助手、表单处理 Agent、
      内容生成 Agent、入门级销售助手
```

> 💡 判断参考：Dify/n8n 已支撑大量企业生产级 Agent——"低代码 = 只能验证"是 2023 年的刻板印象，2026 年大量场景平台即终态。

## 6. 迁移信号：什么时候必须走

```text
出现以下任一信号，开始评估迁移：
⚠️ 复杂状态管理：需要多轮会话的状态机/时间旅行/回滚
⚠️ 细粒度控制：需要在循环内嵌人业务逻辑（审批流/回调）
⚠️ 性能瓶颈：并发数百以上、延迟 P99 超 SLA
⚠️ 深度集成：需要与自有代码库/内部框架无缝集成
⚠️ 测试要求：需要 CI 单测/回放测试/评估流水线
⚠️ 许可受限：商用条款不支持当前商业模式
⚠️ 平台演进风险：收购/版本变动/核心维护者流失
```

## 7. 迁移路线图：从平台到代码框架

```text
迁移不是重写，是"翻译"——平台的流程模型与代码框架一一对应：

平台概念          → 代码框架概念
──────────────────────────────────────────────
Workflow 节点图    → LangGraph StateGraph（节点+边）
变量聚合           → 共享 State（TypedDict）
条件分支           → conditional_edges
LLM 节点           → 节点内 LLM 调用
知识检索节点       → RAG 检索函数（向量库调用）
工具/HTTP 节点     → @tool 装饰器注册
Agent 循环         → ReAct 循环 / 框架内置 Agent
HITL 暂停          → interrupt() / 人工确认节点
会话记忆           → checkpointer（Postgres 持久化）
发布 API           → FastAPI / 框架 SDK 服务
```

**迁移三步法**：
```text
第 1 步：冻结功能边界——把平台原型的功能清单写死（验收标准）
第 2 步：逐节点翻译——按上表映射，先跑通主链路
第 3 步：差异补齐——补平台帮你做了的事：并发、超时、重试、可观测、
        评估（这些在平台是内置的，代码框架要自己写）
```

> ⚠️ **迁移最大坑**：以为"翻译过去就完了"——平台内置的可靠性（重试、限流、日志、记忆管理）在代码框架里都要自己实现，这部分工作量通常占迁移总工时的 40-60%。

**迁移目标框架速配**（对应 [单 Agent 框架](../单%20Agent%20框架/00-总览：单%20Agent%20框架知识体系.md)）：

| 原平台 | 迁移目标 | 理由 |
|--------|---------|------|
| Dify Workflow | LangGraph | 状态图一一对应，checkpointer 承接记忆 |
| Dify Agent | OpenAI Agents SDK / Claude Agent SDK | 轻量循环原语 |
| n8n 自动化 | n8n 保留（或自写编排服务） | 集成资产优先保留 |
| Langflow | LangChain 代码 | 对象级映射最顺 |
| 百炼 Agent | 百炼 SDK（OpenAI 兼容 API） | 模型能力 API 化保留 |

## 8. 混合模式：低代码验证 + 代码生产

2026 年主流团队的常态是**混合架构**，不是非此即彼：

```text
模式 A：平台出原型 → 代码复刻生产
  低代码（1-3 天验证）→ 迁移到 LangGraph 等（生产）
  适用：复杂状态/高并发/深度定制

模式 B：平台出原型 → 平台直接生产
  低代码验证 → 平台调优（评估/限流/发布）→ 平台即终态
  适用：中等复杂度、平台能力覆盖

模式 C：双层架构（最前沿）
  Workflow 层：确定性流程用平台（Dify Workflow/n8n）——稳定、可审计
  Agent 层：复杂决策用代码框架（LangGraph/Claude Agent SDK）
  连接：MCP 协议互操作（平台导出 MCP / 平台消费 MCP）
  适用：大型系统，编排复杂

模式 D：让编码 Agent 用平台流程
  Langflow 拖流程 → 一键导出 MCP Server → Claude Code 调用
  → "业务人员画流程，编码 Agent 跑流程"
```

## 9. 实战案例

### 案例 1：电商客服 Agent（验证 → 平台即终态）

```text
需求：售前咨询（商品知识 RAG）+ 售后工单（调用订单 API）
Day 1：Dify 搭建：知识库上传商品手册 → 检索节点 → LLM 生成 → 工具调用订单 API
Day 2：20 用例测试：10 咨询 8 通过；5 售后 5 通过；5 刁钻 4 通过
Day 3：决策：完成率 85%，平台 API 发布，限流+密钥配好
结果：平台即终态（Dify Web App + API），无需迁移
原因：无复杂状态、DAG 可表达、吞吐在平台能力内
```

### 案例 2：销售调研 Agent（验证 → 迁移代码框架）

```text
需求：多轮调研（目标公司 → 竞品对比 → 生成提案），需跨会话状态
Day 1-3：Coze 原型验证：流程与交互得到业务认可，但发现：
  - 跨会话状态丢失（调研中途中断无法续）
  - 需要嵌入内部 CRM 回调（平台 HITL 不够）
信号：状态管理 + 深度集成 → 迁移
迁移：LangGraph（StateGraph 承接调研状态机 + Postgres checkpointer 续跑）
结果：核心流程复用原型逻辑，补了状态与集成，总周期 2 周
```

### 案例 3：Langflow MCP 协作（新型混合）

```text
需求：业务团队想复用已有"周报生成"流程，让编码 Agent 也能调用
实现：Langflow 拖拽周报流程 → 一键导出 MCP Server → 发布内网
      → Claude Code 在终端把该流程当工具调用
结果：业务人员维护画布流程，开发者无需改代码——跨角色协作
```

## 10. 核心要点

> 🎯 **核心要点**：
> 1. 低代码平台的本模块价值 = **原型快速验证**：1-3 天用 10% 成本验证 90% 需求不确定性
> 2. 验证产出是**五问的数据化答案**（要不要/流程对吗/能力够吗/RAG 行吗/成本可控吗），不是原型本身
> 3. 平台即终态的条件：中等复杂度 + 平台发布能力覆盖 + 吞吐在能力内 + 许可满足商用
> 4. 迁移信号：复杂状态、细粒度控制、性能、深度集成、测试要求、许可受限
> 5. 迁移 = 逐节点"翻译" + **补齐平台内置的可靠性**（占迁移工时 40-60%）
> 6. 2026 前沿是混合架构：平台管确定性流程 + 代码框架管复杂决策，**MCP 协议互操作**（模式 C/D）
