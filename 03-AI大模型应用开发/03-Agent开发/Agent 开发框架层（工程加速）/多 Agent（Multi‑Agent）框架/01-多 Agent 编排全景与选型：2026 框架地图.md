## 1. 市场格局

2026 Q1 生产部署份额估计（第三方调研，方向性参考）：

```text
LangGraph   ~38%   ── 图状态机，生产编排标杆
自定义编排   ~28%   ── 直接手写编排（框架之上的自研层）
CrewAI      ~12%   ── 角色化 Crew，原型最快
AutoGen      ~9%   ── 含迁移中的存量部署
Google ADK   ~4%   ── Google 生态
其他         ~9%   ── OpenAI 方案 / 新兴框架 / 自研
```

**两个结构性事实**：
1. **没有全能框架**——LangGraph 赢生产就绪、ADK 赢协议完整、CrewAI 赢上手速度；选型取决于编排模式、语言栈、部署目标
2. **价值向运营迁移**——框架本身差异在缩小，持久的问题是**运营**（可观测/评估/监控），如 LangSmith；框架选择的重要性低于模型选择、评估基建、人工检查点设计

> 💡 额外警示：**别按 GitHub stars 选框架**——AutoGen stars 最多但已进维护模式；用真实工作流测试。

## 2. AutoGen 三分裂：2026 最大框架事件

```text
2025-09-30  AutoGen v0.7.5 ── 最后一个带新功能的版本
2025-10     Microsoft 宣布 AutoGen 与 Semantic Kernel 合并为 Agent Framework（公开预览）
2026-02     Agent Framework 达 Release Candidate；确认 AutoGen/SK 进入维护模式
2026-04-03  Microsoft Agent Framework 1.0 GA（Python/.NET，MIT）

→ AutoGen 这个名字现在指三样东西：
```

| 实体 | 状态 | 特征 | 适用 |
|------|------|------|------|
| 经典 AutoGen（microsoft/autogen） | **维护模式** | 只收 bug 与安全补丁；2026 Q3 预期 API 弃用 | 存量部署 |
| AG2（ag2ai/ag2） | **活跃社区 fork** | 原作者（Chi Wang/Qingyun Wu）维护；Apache 2.0；向 v1.0 演进；`pip install autogen` 已指向它 | AutoGen v0.2 用户无缝续接 |
| Microsoft Agent Framework | **官方继任者** | AutoGen + Semantic Kernel 合并；Python/.NET 双栈；原生 MCP/A2A | Azure/.NET 企业新项目 |

> 🎯 **结论**：新项目跳过 AutoGen——按需选 LangGraph / CrewAI / Agent Framework / 提供商原生 SDK。AutoGen 的遗产（群聊、辩论、HumanProxy 对话模式）仍适合研究与 HITL 协商场景，但代价是单次交互 20+ LLM 调用。

## 5. 选型决策树

```text
要做一个多 Agent 系统，框架怎么选？

第一问：核心需求是什么？
├─ 长流程/分支/重试/状态机/时间旅行 → LangGraph
├─ 最快出角色化流水线原型 → CrewAI
├─ Azure/.NET 栈或 AutoGen 存量 → Microsoft Agent Framework
├─ Google Cloud/Gemini 栈或多语言 → Google ADK
├─ 极简 handoff（会话式转交）→ OpenAI Agents SDK
└─ 研究/群聊协商 → AG2

第二问：生产要求？
├─ 需要持久化/回放/审计 → LangGraph（checkpointer 最成熟）
├─ 需要跨厂商互操作 → 选 A2A 原生支持（ADK/CrewAI 领先）
└─ 需要多语言 SDK → ADK（Python/Java/Go/TS）

第三问：团队与生态？
├─ LangChain 生态 → LangGraph
├─ Google 生态 → ADK
├─ Microsoft 生态 → Agent Framework
└─ 无绑定 → 按需求与范式选（LangGraph/CrewAI 默认候选）

一句话版：生产编排 → LangGraph；快速原型 → CrewAI；
         Google 栈 → ADK；微软栈 → MAF；会话式转交 → OpenAI SDK
```

## 6. 多 Agent 值不值得：先回答这个问题

2026 年行业共识：**多 Agent 是手段不是目的**——单 Agent 能解决的别拆。判断清单：

| 该拆（多 Agent 加分） | 不该拆（单 Agent 更优） |
|----------------------|----------------------|
| 角色差异大（研究/写作/审查） | 同一角色重复工作 |
| 需要并行处理多个独立子任务 | 串行单链路 |
| 需要专业领域隔离（提示词/工具隔离） | 上下文可共享 |
| 需要独立的状态/记忆边界 | 共享一个上下文足够 |
| 人机协作点清晰（每步可人工介入） | 无人工介入需求 |

> 💡 **成本警告**：每个 Agent 都是独立 LLM 调用循环——AutoGen 群聊单交互 20+ 调用是极端案例；即使轻量编排，多 Agent 的 token 成本通常数倍于单 Agent。**先问"一个 Agent + 好工具链能否解决"，再考虑拆**。

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 2026 格局：LangGraph 领跑生产（~38%），CrewAI 领跑原型，无全能框架
> 2. **AutoGen 已三分裂**：经典=维护模式、AG2=社区 fork、MAF=官方继任者（1.0 GA）——新项目跳过 AutoGen
> 3. 选型三问：核心需求（状态机/角色化/云生态）→ 生产要求（持久化/互操作/多语言）→ 团队生态
> 4. 多 Agent 是手段不是目的：先判断"值不值得拆"，再选框架；成本通常数倍于单 Agent
