# 行动组件：执行与反馈闭环

> 四大组件之"手脚的执行官"：把决策变成动作、把动作结果变成观察。行动组件的质量决定 Agent 在真实世界的"成功率"——执行、观察、重试、终止四件事，一件都不能含糊。

## 1. 行动组件的四职责

| 职责 | 内容 | 失败后果 |
|---|---|---|
| 执行 | 调用工具/API/文件操作 | 动作没发生 |
| 观察 | 收集执行结果与副作用 | 决策基于错误事实 |
| 重试 | 瞬时失败自动恢复 | 一次失败毁整任务 |
| 终止 | 完成/失败/超限判定 | 死循环/白烧钱 |

> 🎯 核心要点：行动组件是"真实世界"与"模型世界"之间的转换器——**模型输出的是"意图"，行动组件负责"落地"并如实回报**，中间不能有任何想当然。

## 2. 执行：动作的落地规则

| 规则 | 说明 |
|---|---|
| 参数化执行 | 一切输入参数化绑定（SQL/Shell/HTTP 同） |
| 超时控制 | 每动作超时（如 10-30s），防止挂死 |
| 副作用感知 | 写操作标记（权限/审批，见[数据库交互](..%2FAgent%20配套技术生态模块%2F数据库交互%2F07-写入场景：数据录入与审批.md) 07 篇） |
| 幂等设计 | 可重试动作幂等（重放安全） |
| 沙箱隔离 | 不可信代码沙箱执行（见[代码执行沙盒](../Agent%20配套技术生态模块/代码执行沙盒/00-代码执行沙盒总览.md)） |

## 3. 观察：反馈回路的质量

| 观察维度 | 收集什么 | 喂给模型 |
|---|---|---|
| 结果 | 返回值/输出 | 截断后的结果（4KB） |
| 状态 | 成功/失败/部分成功 | 状态标记 |
| 错误 | 错误信息（脱敏） | 可行动的错误+建议 |
| 副作用 | 写操作的影响（行数/状态） | 影响摘要 |
| 成本 | 耗时/token | 预算监控（不进上下文） |

> ⚠️ 观察失真的两种死法：**反馈不足**（模型瞎猜下一步）与**反馈过载**（上下文被塞爆）——观察层要"如实但精炼"，这是行动组件最重要的工程细节。

## 4. 重试策略：什么该重试、什么不该

| 错误类型 | 是否重试 | 策略 |
|---|---|---|
| 瞬时错误（网络/超时） | ✅ | 指数退避（1s/2s/4s）+ 抖动 |
| 限流（429） | ✅ | 按 Retry-After 等待 |
| 逻辑错误（参数/权限） | ❌ | 回传模型调整，不自动重试 |
| 校验失败 | ❌ | 回传错误信息让模型改 |
| 非幂等写操作 | ⚠️ | 必须幂等设计后才能重试 |

```python
def with_retry(fn, max_retries=3, backoff=1.0):
    for i in range(max_retries):
        try:
            return fn()
        except TransientError:
            time.sleep(backoff * 2 ** i + random.uniform(0, 0.5))
    raise FinalError("重试耗尽")
```

## 5. 终止条件：什么时候停下来

| 终止条件 | 说明 | 防止 |
|---|---|---|
| 任务完成 | 目标达成判定 | 空转 |
| 步骤上限 | MaxIterations（8-12 默认） | 死循环 |
| 成本上限 | token/金额预算 | 烧钱级联（$5-50 事故） |
| 时间上限 | 总时长 | 长任务失控 |
| 用户中断 | 停止信号 | 用户干预 |
| 明确失败 | 重试耗尽/不可恢复错误 | 无限重试 |

> ⚠️ 2026 年运营警示：无预算约束的 Agent 可级联 50-500 次 LLM 调用（$5-50）——**Step Budget 是硬需求不是建议**，每层循环（内层工具重试、中层行动、外层任务）都要有上限。

## 6. 行动编排：多动作的序列控制

| 编排方式 | 适用 |
|---|---|
| 顺序执行 | 步骤有依赖（默认） |
| 并行执行 | 独立动作（asyncio.gather/parallel） |
| 条件分支 | 观察驱动（if/else） |
| 循环 | 固定迭代（如处理每页） |

```python
# 并行执行独立动作（工具层并行，2026 主流优化）
import asyncio

async def run_parallel(tools: list):
    results = await asyncio.gather(*(execute(t) for t in tools),
                                   return_exceptions=True)
    return [r if not isinstance(r, Exception) else {"error": str(r)}
            for r in results]
```

> 💡 并行能显著降延迟（多个独立查询同时跑），但要小心：**写操作不要并行**（幂等/顺序要求）；共享资源（连接池）注意并发上限。并行度建议：读操作 ≤5 并发（多数收益在前 5 个），写操作恒串行。另一个并行陷阱是**有依赖的"假并行"**——看似独立的动作实际共享同一前置结果时，并行会造成竞态，依赖分析先于并行调度。

## 7. 行动组件的安全护栏

| 护栏 | 说明 |
|---|---|
| 动作白名单 | 可执行动作类型限制（禁 shell/文件删除等） |
| 写操作审批 | HITL（见[数据库交互](..%2FAgent%20配套技术生态模块%2F数据库交互%2F00-数据库交互总览.md) 07 篇） |
| 沙箱 | 代码执行隔离（代码执行沙盒体系） |
| 限流 | 动作频率限制（防风暴） |
| 审计 | 全动作日志（谁/何时/什么/结果） |
| 防注入 | 动作参数脱敏/转义 |

## 8. 行动组件监控指标

| 指标 | 信号 |
|---|---|
| 动作成功率 | 下降 → 上游或参数问题 |
| 重试率 | 异常 → 瞬时错误风暴 |
| 终止原因分布 | "超预算"占比高 → 任务拆分/规划问题 |
| 平均动作耗时 | 慢动作 TopN |
| 副作用影响 | 写操作行数（异常大 → 告警） |

> 🎯 核心要点：行动组件的三大纪律——**执行要安全（参数化+沙箱）、观察要如实（截断但不失真）、终止要坚决（预算硬上限）**。行动组件是 Agent 的"刹车"，没有刹车的 Agent 不是快，是危险。

## 8.5 多 Agent 行动编排

| 编排模式 | 做法 | 适用 |
|---|---|---|
| 顺序委派 | 主 Agent 串行派活给子 Agent | 有依赖的管线 |
| 并行委派 | 多个子 Agent 同时干活 | 独立子任务 |
| 主管-工人 | Supervisor 拆活分发 | 动态任务分解 |
| 会签 | 多 Agent 产出合并投票 | 需要多视角 |

| 编排风险 | 防线 |
|---|---|
| 子 Agent 目标漂移 | 任务边界 + 目标锚定 |
| 上下文交叉泄漏 | 子任务独立上下文 |
| 并行风暴 | 并发上限 |
| 结果冲突 | 裁决规则（优先级/投票） |

> 💡 多 Agent 编排是行动组件的放大形态——单 Agent 的"动作"变成子 Agent 的"任务"，四大纪律（安全/观察/重试/终止）逐级适用。详见[主流 Agent 范式](../主流%20Agent%20范式/07-多Agent协作范式.md) 07 篇。

## 9. 行动组件常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 无超时 | 动作挂死整个 Agent | 每动作超时 |
| 无终止上限 | 死循环烧钱 | Step Budget 四件套 |
| 观察不截断 | 上下文爆炸 | 4KB 截断 + 摘要 |
| 观察失真 | 反馈半截/含错误 | 状态标记 + 脱敏 |
| 无重试策略 | 瞬时失败毁任务 | 退避重试 + 不重试清单 |
| 非幂等重试 | 双倍副作用 | 幂等设计先行 |
| 并行写操作 | 顺序混乱 | 写操作串行 |
| 动作无审计 | 无法追责 | 全动作日志 |
| 忽略副作用 | 写操作影响未知 | 影响行数/状态回传 |
| 重试与终止混用 | 该停的不停 | 重试清单（瞬时可重试）+ 终止判定独立 |
