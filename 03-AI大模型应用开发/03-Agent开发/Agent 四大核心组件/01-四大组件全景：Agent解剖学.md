# 四大组件全景：Agent 解剖学

> Agent = LLM 大脑 + 规划反思 + 记忆 + 工具行动——四大组件在循环里各司其职。本章给出解剖学定义、协作循环与体系分工，是后续各篇的地基。

## 1. 四大组件定义（2026 共识）

| 组件 | 角色 | 回答的问题 | 类比 |
|---|---|---|---|
| LLM 大脑 | 推理决策核心 | "下一步做什么、怎么想" | 大脑 |
| 规划反思 | 目标分解与自我评估 | "任务怎么拆、做得对不对" | 参谋部 |
| 记忆 | 跨轮信息保持 | "我记住了什么、上下文是什么" | 海马体 |
| 工具行动 | 连接外部世界 | "怎么执行、效果如何" | 手和脚 |

> 🎯 核心要点：**四组件不是四个模块，是一个循环中的四个角色**——同一轮任务里，大脑决策→规划分解→记忆供给上下文→工具执行→反思校准→记忆回写，循环往复直到任务完成。

## 2. 协作循环：一次任务的组件走位

```text
用户目标
  │
  ▼
┌──────────────────────────────────────────────┐
│  LLM 大脑（决策）                              │
│   ├─→ 规划组件：目标 → 步骤列表                │
│   ├─→ 记忆组件：检索历史/偏好 → 注入上下文      │
│   └─→ 行动组件：调工具执行 → 收集观察          │
│                                              │
│  ── 循环 ←── 反思组件：评估结果，决定继续/重试/重规划 │
│       │                                      │
│       └─→ 记忆回写：新事实/结果 → 长期记忆       │
└──────────────────────────────────────────────┘
  │
  ▼
最终答案 / 产物
```

| 阶段 | 主导组件 | 产出 |
|---|---|---|
| 理解 | LLM 大脑 + 记忆 | 任务理解 + 相关上下文 |
| 规划 | 规划组件 | 步骤列表（可执行） |
| 执行 | 工具/行动组件 | 观察结果（工具输出） |
| 评估 | 反思组件 | 继续/重试/重规划决策 |
| 收尾 | LLM 大脑 + 记忆 | 最终答案 + 记忆回写 |

## 4. 组件之间的四种耦合

| 耦合 | 例子 | 设计要点 |
|---|---|---|
| 大脑↔规划 | 大脑按计划逐步决策 | 计划以结构化 JSON 传递 |
| 记忆↔大脑 | 上下文注入 | 记忆管理器决定注入多少 |
| 工具↔大脑 | Function Calling 声明 | 工具 schema 描述决定调用质量 |
| 反思↔规划 | 重规划触发 | 反思结论回写计划 |

| 耦合设计错误 | 后果 |
|---|---|
| 计划丢失 | 执行器忘了原目标（goal drift） |
| 上下文无预算 | 记忆灌满窗口，规划退化 |
| 工具描述含糊 | 模型乱调工具（schema > 模型，2026 共识） |
| 反思无 oracle | 自我确认偏差（04 篇） |

## 5. 组件质量的三条主线

| 主线 | 问题 | 对应模块 |
|---|---|---|
| 决策质量 | 大脑想得对不对 | 02 |
| 计划质量 | 分解得好不好、评估准不准 | 03/04 |
| 执行质量 | 上下文全不全、工具灵不灵 | 05/06/07 |

> 🎯 核心要点：调 Agent 的顺序从大到小——**先修记忆（上下文对不对）→ 再修工具（执行灵不灵）→ 然后修规划（分解好不好）→ 最后修模型（决策强不强）**。大多数"Agent 不行"是前三项的问题，不是模型不够强。

## 6. 心智模型：一张组件责任表

| 任务环节 | 该谁负责 | 常见甩锅 |
|---|---|---|
| 答非所问 | 记忆（上下文没注入） | 怪模型 |
| 步骤乱序 | 规划（分解质量差） | 怪模型 |
| 工具调用失败 | 工具（schema/注册/校验） | 怪模型 |
| 重复犯错 | 反思（无 oracle 或没接） | 怪模型 |
| 上下文爆炸 | 记忆（无预算管理） | 怪上下文窗口 |

> 🎯 核心要点：**排查 Agent 问题先按组件归因，再谈换模型**——组件级归因是 2026 年 Agent 调试的第一方法论（详见 10 篇避坑清单）。

## 7. 四组件的成熟度模型

| 组件 | L1（能用） | L2（可靠） | L3（可演进） |
|---|---|---|---|
| 大脑 | 直接生成 | 结构化输出 + 提示词冻结 | 角色分工（规划/执行分模型） |
| 规划 | 无（ReAct 直想） | 计划 JSON + 步骤上限 | Plan-Execute-Reflect + 目标锚定 |
| 记忆 | session 状态 | 分层 + 有界读取 | 记忆管理器 + claim 生命周期 |
| 工具 | 单工具硬编码 | 注册表 + schema 校验 | MCP 生态 + 审批 + 幂等 |
| 反思 | 无 | 有 oracle 的 act-then-reflect | Reflexion + 独立评判器 |

**判断你的 Agent 在 L1 还是 L3**：问三个问题——① 上下文满了怎么办？（L1 会炸，L3 有管理器）② 工具错了怎么办？（L1 重试，L3 回传+重规划）③ 任务跑偏了怎么办？（L1 等它跑完，L3 有目标锚定与反思）。

> 💡 成熟度不是"全都要 L3"——演示与内部工具 L1 足够；对外产品至少 L2；只有长任务/高价值场景值得 L3 的全套成本。

## 8. 常见误区

| 误区 | 真相 |
|---|---|
| "四组件=四个类" | 是循环里的四个角色，可能共享同一个模型 |
| "组件越多越好" | 每个组件都有成本——短任务别加规划器 |
| "反思=高级重试" | 反思先评估后修改；无 oracle 时反思是自我确认 |
| "记忆=上下文全部" | 记忆是"挑着喂"，全量注入是灾难 |
| "工具=一个函数" | 工具是声明+注册+校验+回传的完整系统 |
| "先选框架再想组件" | 先想清楚组件责任，框架只是外壳 |
| "四组件缺一不可" | 短任务可只有大脑+工具（ReAct），组件按需配置 |
