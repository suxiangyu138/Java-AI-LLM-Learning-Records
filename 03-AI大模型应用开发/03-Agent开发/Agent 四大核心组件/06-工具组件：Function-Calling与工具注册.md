# 工具组件：Function Calling 与工具注册

> 四大组件之"手脚"：连接外部世界的接口层。2026 年共识——**工具 schema 设计比模型选择更重要**（Anthropic 在工具提示词上的投入超过主提示词），工具组件是 Agent 能力的天花板。

## 1. 工具组件的四层结构

```text
声明层（Schema）   JSON Schema 描述工具（名称/参数/描述）
  → 注册层（Registry） 工具注册表：发现、校验、权限
    → 执行层（Executor） 参数校验 → 执行 → 结果序列化
      → 回传层（Feedback） 结果/错误回传模型（驱动下一轮决策）
```

| 层 | 失败后果 | 对应模块 |
|---|---|---|
| 声明层 | 模型选错工具/参数 | 本模块 2 节 |
| 注册层 | 工具找不到/越权 | 本模块 3 节 |
| 执行层 | 参数注入/执行错误 | 本模块 4-5 节 |
| 回传层 | 模型卡死/重复失败 | 本模块 6 节 |

## 2. 声明层：工具描述的质量杠杆

| 描述要点 | 作用 | 反例 |
|---|---|---|
| 做什么 | 模型知道用途 | "执行查询" |
| 何时用 | 模型知道触发条件 | "获取用户信息" |
| 边界 | 模型不越权调用 | 没写"仅查询"→ 被用于写操作 |
| 参数说明 | 模型填对参数 | "id: 用户 ID" |

```json
{
  "name": "search_orders",
  "description": "按条件查询订单（只读）。当用户询问订单状态/历史时使用。"
    "不修改任何数据；如需修改请调用 update_order（需审批）。"
    "参数不明确时先调用 describe 工具确认字段。",
  "parameters": { ... }
}
```

> 🎯 核心要点：**工具描述三件套 = 做什么 + 何时用 + 边界**——写得越好，模型调用越准，越权越少。2026 年实测：工具描述打磨的收益常大于换模型。描述还有隐性收益：**描述是模型的语义锚点**——多工具并存时，描述越精确，模型越不会混淆相似工具（如"查订单"与"查物流"）。

**工具命名规范**（低成本高收益）：

| 规范 | 例子 | 避免 |
|---|---|---|
| 动词开头 | `search_orders` / `create_refund` | `orders`（不知道干嘛） |
| 一工具一职责 | `send_email` / `send_sms` 分开 | `notify`（模型难选） |
| 副作用可见 | `update_order` 带"需审批" | `process`（黑盒感） |
| 领域一致 | 同一业务统一前缀 `order_*` | 中英混排 |

命名 + 描述共同决定模型调用准确率——**工具名的"可猜测性"和描述的"触发条件"是两大杠杆**，都比调模型便宜。

## 3. 注册层：工具注册表设计

| 能力 | 实现 | 价值 |
|---|---|---|
| 注册 | 装饰器/注解声明式注册 | 扩展只加类 |
| 发现 | 反射/自动装配收集 | 零手工维护 |
| 校验 | 参数 schema 校验（执行前） | 拦截畸形调用 |
| 权限 | 工具级权限标记（只读/需审批） | 安全边界 |
| 审计 | 调用日志（谁/何时/参数） | 追责与监控 |
| 去重 | 同名工具冲突检测 | 防覆盖 |

```python
# 装饰器注册表示例
_TOOL_REGISTRY: dict[str, Tool] = {}

def tool(name: str, description: str, schema: dict, requires_approval=False):
    def deco(fn):
        _TOOL_REGISTRY[name] = Tool(name, description, schema, fn, requires_approval)
        return fn
    return deco

@tool("search_orders", "查询订单（只读）...", ORDERS_SCHEMA)
def search_orders(params: dict) -> dict:
    return db_query(params)          # 只读执行
```

## 4. 执行层：参数校验与安全执行

| 防线 | 做法 |
|---|---|
| schema 校验 | strict 模式（additionalProperties: false，全必填） |
| 业务校验 | 值域/枚举/范围（模型输出不可信） |
| 权限执行 | 工具级权限 + 角色过滤 |
| 隔离执行 | 危险工具沙箱/审批 |
| 超时 | 工具执行超时（防止挂死） |
| 幂等 | 写工具幂等设计（重试安全） |

> ⚠️ 模型输出是"建议"不是"指令"——**执行层必须重新校验**：参数类型、值域、权限、写操作审批，一道都不能少（详见 Function Calling 体系的参数校验篇）。

## 5. 回传层：错误与结果的循环驱动

| 回传内容 | 模型行为 |
|---|---|
| 成功结果（截断） | 继续下一步 |
| 错误信息（脱敏+建议） | 调整后重试 |
| 权限拒绝 | 换工具或询问用户 |
| 审批请求 | 触发 HITL 流程 |

```python
def execute_with_feedback(name: str, params: dict) -> dict:
    try:
        result = _TOOL_REGISTRY[name].fn(params)
        return {"status": "success", "result": truncate(result, 4000)}
    except ToolError as e:
        return {"status": "error",
                "message": f"{e.sanitized}。建议：{e.hint}"}   # 可行动的错误
```

| 错误回传技巧 | 效果 |
|---|---|
| 错误脱敏 | 防泄漏内部信息 |
| 附建议（"先 describe_table"） | 模型照做，成功率大升 |
| 截断结果（4KB） | 防上下文爆炸 |
| 明确"不要重试"的情况 | 防死循环 |

## 6. 工具组件与 MCP

| 接入方式 | 说明 |
|---|---|
| 自研工具 | 深度定制（审批/幂等/审计） |
| MCP 工具 | 生态复用（DB/搜索/文档等标准服务器） |
| 混合 | 核心工具自研 + 通用能力 MCP |

```text
工具组件架构（2026 主流）：
  Agent 运行时 ←→ 工具注册表 ←→ 自研工具（深度定制）
                              ←→ MCP 客户端（DBHub 等生态）
```

> 💡 MCP 生态细节见[Agent 配套技术生态模块](../Agent%20配套技术生态模块/数据库交互/00-数据库交互总览.md)（其下 数据库交互/联网搜索/文档解析 等体系均为工具组件的最佳实践落点）。

## 6.5 一次工具调用的完整生命周期

```text
1. 大脑决策 → 生成 tool_calls（工具名 + 参数 JSON）
2. 注册表校验 → 工具存在？权限允许？（拒绝则回传错误）
3. 参数校验 → schema 校验 + 业务校验（strict 模式）
4. 审批检查 → 需审批工具 → HITL 流程（写操作）
5. 执行 → 带超时调用工具函数（沙箱/隔离）
6. 序列化 → 结果截断（4KB）+ 脱敏
7. 回传 → tool 消息（tool_call_id 配对）→ 模型继续决策
8. 审计 → 记录参数/结果摘要/耗时/调用方
```

| 环节 | 防什么 |
|---|---|
| 2-3 | 越权/畸形调用 |
| 4 | 危险操作 |
| 5 | 挂死/恶意代码 |
| 6 | 上下文爆炸/泄露 |
| 7 | 模型卡死（配对错误） |
| 8 | 无据可查 |

## 7. 工具组件的监控指标

| 指标 | 信号 |
|---|---|
| 工具选择正确率 | 下降 → 描述待打磨 |
| 参数校验失败率 | 升高 → schema 描述不清 |
| 工具失败率 | 升高 → 上游服务问题 |
| 单任务工具调用数 | 超限 → 任务拆分/记忆问题 |
| 审批触发率 | 异常 → 权限边界调整 |
| 工具耗时 TopN | 慢工具定位 | 

## 9. 与 Function Calling 协议层的关系

| 层 | 内容 | 归属 |
|---|---|---|
| 协议层 | tool_calls 结构、回传配对、流式组装 | Function Calling 体系（[知识体系总览](../..%2F02-大模型基础与Prompt工程%2FFunction%20Calling%20函数调用%E3%80%90Agent%20基石%E3%80%91%2F00-FunctionCalling知识体系总览.md)） |
| 组件层 | 注册表/校验/执行/审计（本模块） | 本模块 |
| 生态层 | MCP 服务器、工具市场 | Agent 配套技术生态模块 |

```text
分工原则：协议层解决"模型怎么调用"（格式正确），
        组件层解决"调用是否被允许且安全"（边界正确），
        生态层解决"有哪些工具可用"（能力供给）。
        三层各自独立演进，别混为一谈。
```

> 💡 面试加分点：能说清"tool_calls 是协议，工具注册表是工程，MCP 是生态"三者的边界，说明对工具体系有完整认知。

> 🎯 核心要点：**工具组件的质量 = 描述（选得对）× 校验（调得对）× 回传（续得上）**——三者乘积决定"手脚"好不好用。工具组件深化（工具开发规范、高级注册机制）在[Tool 工具开发与注册]专项（目录待建）；协议层见 Function Calling 体系。

## 8. 工具组件常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 描述含糊 | 模型乱选工具/参数 | schema 三件套（做什么/何时用/边界） |
| 参数不校验 | 注入/越界参数执行 | 执行层严格校验 |
| 错误不回传 | 模型重复同样失败 | 脱敏错误 + 可行动建议 |
| 结果不截断 | 上下文爆炸 | 4KB 截断 + 摘要 |
| 无权限模型 | 工具谁都能调 | 工具级权限 + 审批 |
| 无幂等 | 重试双倍副作用 | 写工具幂等设计 |
| 工具无限重试 | 风暴 | 重试上限 + 退避 |
| 工具名冲突 | 覆盖/错调 | 注册表冲突检测 |
| 不记审计 | 事故无法定位 | 全调用日志 |
