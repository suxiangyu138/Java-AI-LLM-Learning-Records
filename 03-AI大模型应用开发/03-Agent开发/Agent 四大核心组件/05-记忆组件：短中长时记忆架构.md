# 记忆组件：短中长时记忆架构

> 四大组件之"海马体"：记忆是 Agent 与"无状态提示词系统"的分水岭。2026 年共识——分层记忆 + 记忆管理器，用"最小的有用上下文包"喂给大脑。

## 1. 三层记忆模型

| 层 | 类比 | 载体 | 存什么 | 生命周期 |
|---|---|---|---|---|
| 工作记忆（短期） | 便签 | LLM 上下文窗口 | 当前任务消息/中间结果 | 单任务 |
| 情景记忆（中期） | 日志 | 会话存储/检查点 | 本轮事件、失败教训 | 会话级 |
| 长期记忆 | 档案 | 向量库/关系表/文件 | 事实、偏好、经验 | 跨会话 |

> 🎯 核心要点：**三层记忆的分工是"快取、准记、久存"**——工作记忆要省（token 预算），情景记忆要全（审计），长期记忆要准（结构化+可检索）。三层都有对应存储方案（见[数据库交互](..%2FAgent%20配套技术生态模块%2F数据库交互%2F05-Agent结构化记忆：会话与状态持久化.md) 05 篇）。

## 2. 记忆管理器：大脑的"上下文采购员"

| 职责 | 问题 |
|---|---|
| 决定存什么 | 什么值得写入长期记忆 |
| 决定取什么 | 本轮注入哪些记忆 |
| 决定摘要什么 | 超窗历史如何压缩 |
| 决定丢什么 | 过期/废弃记忆如何淘汰 |

```text
记忆管理器装配优先级（2026 共识）：
  当前消息 → 近期轮次 → 活跃结构化决策 → 情景事件 → 滚动摘要 → 向量检索
  按此顺序装进上下文，直到 token 预算耗尽
```

| 误区 | 后果 |
|---|---|
| 全量历史进上下文 | 窗口爆炸、信噪崩塌 |
| 无摘要机制 | 长会话必然超窗 |
| 记忆无淘汰 | 过期事实误导决策 |
| 无记忆管理器 | 上下文内容随机（每轮不同） |

## 3. 工作记忆：上下文预算管理

| 项 | 建议 |
|---|---|
| 单轮预算 | 明确的 token 上限（如 60% 窗口） |
| 消息裁剪 | 只保留最近 N 条 + 滚动摘要 |
| 工具结果 | 截断（4KB）+ 摘要 |
| 提示词冻结 | system 层不动（利于缓存，降本） |
| 记忆注入 | 记忆管理器按优先级装配 |

> ⚠️ 上下文溢出仍是 2026 年调查列出的头号挑战——工作记忆管理的本质是"**宁可少喂，不可乱喂**"：信息不足模型会问/会漏，信息过载模型会迷失。

## 4. 长期记忆的两种形态

| 形态 | 存储 | 检索 | 适合 |
|---|---|---|---|
| 语义记忆（向量） | 向量库/PGVector | 相似度 TopK | 知识片段、文档化记忆 |
| 结构化记忆（事实） | 关系表/KV | 精确查询/规则过滤 | 偏好、事实、状态（claim 表） |

| 记忆类型 | 例子 | 存储选择 |
|---|---|---|
| 用户偏好 | "用户要简洁回答" | 关系表（KV） |
| 事实 | "订单 1023 已取消" | claim 表（带生命周期） |
| 经验教训 | "上次 SQL 报错是因为列名" | 情景记忆（反思回写） |
| 文档知识 | 知识库内容 | 向量库（RAG） |

## 5. 写入：什么时候记、记什么

| 写入时机 | 内容 | 价值 |
|---|---|---|
| 任务完成 | 结论/产出摘要 | 下次直接复用 |
| 失败之后 | 教训（反思回写） | 避免重复踩坑 |
| 用户明确表达 | 偏好/指令 | 个性化 |
| 关键状态变化 | 业务状态 | 上下文续接 |
| 定期摘要 | 长会话压缩 | 防超窗 |

```text
写入质量三问：
  ① 这条信息以后还会用到吗？ ② 用什么检索词能找到它？
  ③ 会不会与已有记忆矛盾？（矛盾 → 需冲突处理，见数据库交互 05 篇 claim 生命周期）
```

## 6. 召回：把记忆装回上下文

| 召回方式 | 做法 | 适用 |
|---|---|---|
| 精确查询 | 按用户/实体取 KV | 偏好、状态 |
| 语义检索 | 向量 TopK | 知识片段 |
| 时效召回 | 最近 N 条 | 情景记忆 |
| 混合召回 | 多路 + RRF 融合 | 复杂长期记忆 |

> 💡 记忆召回不是"越多越好"——**检索噪声是 2026 年记忆系统的头号质量问题**（原始对话 RAG 的信噪崩塌已被实证），记忆管理器负责过滤。

## 7. 记忆产品与框架（2026 现状）

| 方案 | 定位 | 说明 |
|---|---|---|
| Mem0 | 长期记忆产品 | 分层记忆 + 提取/召回 API |
| Letta（MemGPT） | 记忆 Agent 框架 | 虚拟上下文管理 |
| Zep | 记忆后端 | 对话记忆服务化 |
| LangGraph Store | 框架内建 | 命名空间 KV + 向量索引 |
| 自研 | 关系表+向量（见[数据库交互](..%2FAgent%20配套技术生态模块%2F数据库交互%2F00-数据库交互总览.md)） | 完全可控 |

| 选型 | 场景 |
|---|---|
| 产品化记忆 | Mem0/Zep（少开发） |
| 框架内建 | LangGraph Store（已有 LangGraph 栈） |
| 自研 | 要审计/合规/深度定制 |

## 8. 记忆安全与合规

| 风险 | 防线 |
|---|---|
| 记忆泄露 | 按用户隔离；PII 脱敏存储 |
| 记忆污染（注入） | 记忆内容当数据不当指令 |
| 过期记忆误导 | claim 生命周期（DEPRECATED 过滤） |
| 记忆膨胀 | 保留策略 + 定期清理 |
| 审计 | 记忆写入日志（谁/何时/什么） |

> 🎯 核心要点：记忆组件的成熟度分四档——**能存（历史表）→ 能挑（管理器）→ 能弃（淘汰机制）→ 能守（安全合规）**。大多数 Agent 死在第二档：存了一堆，但没想清楚"每轮该喂什么"。

## 9. 记忆组件常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 全量历史注入 | 上下文爆炸 | 有界读取 + 摘要 |
| 无记忆管理器 | 每轮记忆内容随机 | 装配优先级固定 |
| 只存不检 | 检索噪声淹没信号 | 混合召回 + RRF 过滤 |
| 无淘汰机制 | 过期事实误导 | claim 生命周期 |
| 记忆不隔离 | 用户 A 记到 B 头上 | 按用户/命名空间隔离 |
| 敏感数据入库 | PII 泄露 | 脱敏存储 |
| 记忆注入被污染 | 注入内容带指令 | 记忆当数据不当指令 |
| 摘要丢失关键信息 | 长会话关键事实丢 | 结构化事实单独存（不走摘要） |
