# 反思组件：自我评估与纠错

> 四大组件之"质检员"：让 Agent 评估自己的输出并改进。2026 年的核心共识是**"反思只在有可验证 oracle 时才有价值"**——没有 oracle，反思退化为自我确认偏差。

## 1. 反思 vs 重试：本质区别

| 维度 | 重试（Retry） | 反思（Reflection） |
|---|---|---|
| 目的 | 处理瞬时失败 | 有意识地提升质量 |
| 机制 | 原样再跑 | 先自评再修改 |
| 问的问题 | "再试一次？" | "我哪里做得不好？如何改进？" |
| 例 | 网络超时重发 | "我是否考虑了合规风险？增长假设站得住吗？" |

> 🎯 核心要点：**重试治"手抖"，反思治"脑子没想全"**——把重试当反思用是常见的错误（失败原因没变，重试只会重复失败）。

## 2. Reflexion：无权重更新的自我批评

| 维度 | 说明 |
|---|---|
| 原理 | 语言化自我批评（verbal reinforcement learning），不更新权重 |
| 机制 | 执行→失败/不足→自我反思→改进建议存入情景记忆→下轮改进 |
| 效果 | HumanEval 80%→91%（Shinn et al.） |
| 成本 | 每轮反思额外 1-2 次 LLM 调用 |

```text
Reflexion 循环：
  尝试 → 失败 → 自我批评（"我忽略了 X"）→ 记忆该批评 → 再尝试
  记忆中的批评随轮次积累，Agent 越试越会避开已知错误
```

## 3. Oracle 条件：反思的生死线（2026 共识）

| 有 oracle（可验证基准） | 无 oracle |
|---|---|
| 测试套件、编译器、标准答案 | 开放式生成（写作/摘要/创意） |
| 反思有效：能真实评估"错没错" | 反思退化：自我确认偏差 |
| 例：代码任务（测试跑不过→重写） | 例：让模型自评文章质量（它总觉得自己不错） |

> ⚠️ 2026 年最佳实践：**没有 verifiable oracle 的任务，别加反思组件**——"LLM 自我评估"在没有基准时不是评估，是自我安慰。非要加，用人工抽查/外部评判器替代。

## 4. Act-then-reflect 模式（Microsoft 官方模式）

```text
模式：产出 → 注入"请批评你的输出" → 修订版
实现：追加一条自我批评消息（不重置会话），再生成一次
```

| 应用 | 轮数建议 |
|---|---|
| 复杂输出质量提升（报告/方案） | 2-3 轮审查 |
| 不确定性高的解空间 | 3-5 轮迭代细化 |
| 计划执行类 | 每步后轻量评估 |

```python
# 实现骨架：act-then-reflect
def act_then_reflect(prompt: str, rounds=2) -> str:
    result = generate(prompt)
    for _ in range(rounds):
        critique = generate(f"{prompt}\n\n这是我的输出：{result}\n请批评它："
                            "找出逻辑漏洞、遗漏、可改进处（不客气）")
        result = generate(f"{prompt}\n\n根据批评修订：{critique}")
    return result
```

## 5. 反思的三种实现层级

| 层级 | 做法 | 成本 | 适用 |
|---|---|---|---|
| 内隐 | 推理模型自带 thinking（先想后答） | 低 | 默认 |
| 外显单轮 | act-then-reflect（追加自评消息） | 中 | 有 oracle/人工审查 |
| 外显循环 | Reflexion（批评入记忆，跨轮积累） | 高 | 可验证长任务 |

> 💡 顺序建议：**先用内隐（推理模型）→ 不够再外显单轮 → 仍不够才上 Reflexion**——反思不是越重越好，每加一层都是一轮 LLM 成本。

## 6. LLM 评判器（Critic）：反思的工程化

| 评判器类型 | 做法 | 用途 |
|---|---|---|
| 自我评判 | 同一模型评自己 | 便宜，有偏差 |
| 独立评判器 | 另一模型/提示词评产出 | 偏差更小 |
| 规则评判器 | 断言/测试/正则（真 oracle） | 最可靠 |
| 人工抽查 | 采样评审 | 高价值任务兜底 |

```text
反思链路的可靠性排序：
  规则评判器 > 独立评判器 > 自我评判 > 不评判
  成本排序恰好相反——工程上按"可靠性需求"选层级
```

## 7. 反思触发时机与频率

| 触发 | 频率 | 例子 |
|---|---|---|
| 失败后 | 每次失败 | 工具报错 → 反思 → 换策略 |
| 里程碑 | 每 N 步 | 每 3 步小结进度 |
| 完成时 | 每次任务 | 最终输出自评（有 oracle 时） |
| 预算内 | 按预算 | 反思轮数受 step budget 约束 |

> 🎯 核心要点：反思组件的三原则——**有 oracle 才加、有偏差就换独立评判器、有预算才循环**。反思是质量组件，不是流程装饰；没想清楚"拿什么当标准答案"之前，别先上 Reflexion。

## 8. 反思的价值如何评测

| 评测方法 | 做法 |
|---|---|
| A/B 对比 | 同一任务集（有/无反思），对比成功率 |
| 反思命中率 | 批评意见中"真实问题"的占比（人工抽检） |
| 修正收益 | 反思后输出与反思前差异的改进程度 |
| 成本增量 | 每轮反思的额外 LLM 调用 vs 质量收益 |
| 偏差检测 | 独立评判器与自我评判的一致率 |

> 💡 反思组件上线前必答一题：**"加了反思，任务成功率涨了多少？"**——涨不了就拆掉。反思是锦上添花，不是流程标配；有 oracle 的任务是它的主场，开放生成是它的坟场。

## 9. 反思组件常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 无 oracle 硬上 | 自我确认偏差（自评全通过） | 先建可验证基准 |
| 自我评判 | 评自己总觉得自己对 | 独立评判器/规则评判器 |
| 反思不落地 | 批评了但输出没改 | 强制"按批评修订"步骤 |
| 反思无记忆 | 每轮从零想 | 教训入情景记忆（Reflexion） |
| 反思轮数失控 | 每任务 5+ 轮反思 | 预算内限轮数（2-3） |
| 批评空泛 | "可以更好"无具体 | 提示词要求具体缺陷+改进 |
| 反思打断节奏 | 简单任务也反思 | 按任务复杂度分级触发 |

## 10. 反思边界速查（要不要加反思）

| 任务特征 | 结论 | 理由 |
|---|---|---|
| 有测试/编译器/标准答案 | ✅ 加（Reflexion 首选） | oracle 让批评真实有效 |
| 代码/数学/检索验证类 | ✅ 加 | 执行可判对错 |
| 有独立评判器可用 | ✅ 加（用独立评判） | 偏差小于自我评判 |
| 开放写作/创意 | ⚠️ 谨慎（人工评审） | 自我评估无效 |
| 短任务（≤3 步） | ❌ 不加 | 反思成本 > 收益 |
| 无 oracle 也无人工 | ❌ 不加 | 加了是自我安慰 |
| 有预算且任务长 | ✅ 限量加（2-3 轮） | 成本可控 |
| 多轮对话质量维护 | ⚠️ 每轮轻量自检（不追加模型调用） | 用规则检查替代完整反思 |

> 💡 速记：**"反思的收益 = oracle 的质量 × 批评的独立性 × 修订的执行力"**——三因子任一为零，反思都是白花钱。

## 11. 反思与规划组件的联动

```text
反思结论 → 两种去向：
  ① 重规划：更新剩余步骤（Plan-Execute-Reflect 的 Reflect）
  ② 记忆回写：把教训写入长期记忆（下次任务直接避开）
```

| 联动 | 效果 |
|---|---|
| 反思→重规划 | 当前任务内纠偏 |
| 反思→记忆 | 跨任务经验积累（Reflexion 的进阶用法） |
