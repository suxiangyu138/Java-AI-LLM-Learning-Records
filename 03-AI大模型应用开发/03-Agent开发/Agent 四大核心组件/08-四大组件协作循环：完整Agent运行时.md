# 四大组件协作循环：完整 Agent 运行时

> 四组件拆开是解剖学，合起来是运行时。本章把 ReAct 循环放大到组件级：一次任务中，大脑/规划/记忆/工具/行动/反思怎么轮流上场、状态怎么流转、失败怎么注入。

## 1. 组件级 ReAct 循环

```text
每轮循环（ReAct 的组件视角）：
  Thought（大脑+记忆）：读上下文 → 决定下一步
    → Action（工具组件）：调用工具/动作
      → Observation（行动组件）：收集结果
        → 记忆回写（记忆组件）：新事实入库
          → 反思检查（反思组件）：需要重规划/停止吗？
            → 下一轮 Thought ...
```

| 范式 | 组件编排 |
|---|---|
| ReAct | 大脑决策 + 工具执行（轻规划） |
| Plan-and-Execute | 规划组件前置，执行器循环 |
| Reflexion | 反思组件注入每轮失败后 |
| ToT | 大脑多分支探索（重规划） |

## 2. 一次完整任务走查（带状态流转）

```text
任务："分析 2026 Q2 销售下滑原因并给出建议"
  ① 大脑+记忆：理解任务；记忆注入（用户背景/历史分析）
  ② 规划组件：出 5 步计划（查数据→对比→归因→建议→报告）
  ③ 循环开始：
     执行器 Step1 → search_orders 工具（查 Q2 数据）
     观察：订单 12,430 单（Q1 15,208）→ 记忆回写中间结果
     反思：数据齐了吗？→ 继续
     Step2 → db_query（对比 Q1/Q2 品类）→ 观察 → 反思
     ...
     第 4 步发现数据异常（退款率飙升）→ Replanner 重规划：
       追加"分析退款原因"步骤
  ④ 收尾：汇总报告（大脑）+ 结论与建议
  ⑤ 记忆回写：分析结论入长期记忆（下次直接引用）
```

| 流转要点 | 状态载体 |
|---|---|
| 计划状态 | 步骤列表（pending/running/done） |
| 中间结果 | 工作记忆（上下文）或会话存储 |
| 反思结论 | 情景记忆（失败教训） |
| 最终产出 | 答案 + 记忆回写 |

## 3. 状态管理：运行时的"血液循环"

| 状态类型 | 内容 | 存储 | 生命周期 |
|---|---|---|---|
| 任务状态 | 计划/进度/预算 | 运行时内存（或检查点） | 任务级 |
| 会话状态 | 消息历史/上下文 | 会话存储（Redis/DB） | 会话级 |
| 记忆状态 | 长期事实/经验 | 记忆组件（向量/关系表） | 跨会话 |
| 审计状态 | 全部动作日志 | 审计存储 | 永久 |

### 3.1 状态流转的纪律

| 纪律 | 说明 |
|---|---|
| 状态显式化 | 计划/进度/预算都入 State，不藏在局部变量 |
| 单写者 | 同一状态段只有单一组件可写（防竞争） |
| 可序列化 | 状态可整体落盘（检查点/恢复的前提） |
| 版本化 | 状态 schema 变更需迁移（持久化后） |
| 最小化 | 只存"重建上下文所需"，不存全部痕迹 |

> 💡 状态设计的检验标准：**"崩溃后能否从检查点恢复并继续任务"**——能，状态设计合格；不能，状态没管好（这是 LangGraph Checkpointer 存在的全部理由）。注意检查点粒度与成本的平衡：每步存是最全但最贵，实践中"每 N 步 + 关键节点"即可满足恢复需求。

> 💡 框架落地：LangGraph 的 checkpointer（按步保存图状态）就是任务+会话状态的工程化——崩溃可恢复、可回放、可分支（见 Loop Engineering 体系）。

## 4. 失败注入：组件视角的故障排查

| 现象 | 故障组件 | 排查 |
|---|---|---|
| 答非所问 | 记忆（上下文缺失） | 查记忆注入日志 |
| 步骤乱序/遗漏 | 规划（分解质量） | 查计划 JSON |
| 工具调用错误 | 工具（schema/执行） | 查工具调用日志 |
| 重复同样失败 | 反思（未接 oracle/记忆未回写） | 查反思触发与教训记忆 |
| 死循环/烧钱 | 行动（终止条件缺失） | 查 Step Budget |
| 目标漂移 | 规划（目标未锚定） | 查 replan 输入 |

> 🎯 核心要点：**故障排查按组件归因，而不是"换模型"**——90% 的运行时故障能用组件日志定位到具体组件（详见 10 篇避坑）。

## 5. 预算与并发：运行时的资源治理

| 治理项 | 默认值 | 防止 |
|---|---|---|
| 任务步骤上限 | 8-12 轮 | 死循环 |
| 成本上限 | 每任务固定预算 | $5-50 失控级联 |
| 并发 | 工具并行 ≤5；写操作串行 | 资源风暴 |
| 上下文预算 | 窗口 60% | 上下文爆炸 |
| 重试 | ≤3 次 + 退避 | 重试风暴 |

## 6. 可观测性：给运行时装仪表盘

| 观测面 | 指标 |
|---|---|
| 组件级 | 各组件耗时/调用次数/失败率 |
| 循环级 | 轮数、终止原因分布 |
| 记忆级 | 注入量、命中率 |
| 工具级 | 调用分布、成功率 |
| 成本级 | token/任务、成本/任务 |

```text
观测设计原则：每个组件产出一条可追踪的事件流
  （大脑决策事件 / 计划变更事件 / 记忆读写事件 / 工具调用事件）
  请求 id 贯穿 → 任何问题都能回放到具体组件
```

## 7. 从组件到架构：运行时选型

| 复杂度 | 运行时形态 | 适合 |
|---|---|---|
| 简单 | 手写循环（几十行） | 学习/单工具任务 |
| 中 | LangGraph/Spring AI（图编排） | 生产标准 |
| 复杂 | 多 Agent + 专用运行时（Harness） | 企业级（见 Harness Engineering 体系） |

> 🎯 核心要点：运行时的本质是**"让四组件按纪律协作"**——计划有状态、失败有归因、预算有上限、全程可观测。这四件事做到，四组件才能从"概念"变成"系统"。

## 8. 运行时常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 组件事件不记录 | 故障无法回放 | 组件级事件流 |
| 状态只存内存 | 崩溃丢任务 | 检查点持久化 |
| 预算只配一处 | 内层循环无上限 | 每层循环都配上限 |
| 观察不进状态 | 决策缺上下文 | 观察写入状态 |
| 记忆不回写 | 每任务从零开始 | 任务结束记忆回写 |
| 重规划不锚目标 | 越跑越偏 | 原目标注入每轮 |
| 并发无上限 | 工具风暴 | 并发信号量 |
| 写操作并行 | 顺序混乱 | 写操作串行队列 |
| 无用户中断 | 长任务无法干预 | 停止信号贯穿 |
| 组件依赖隐式 | 迁移框架困难 | 组件接口契约化 |

## 9. 运行时演进趋势（2026）

| 趋势 | 现状 | 影响 |
|---|---|---|
| 持久化运行时（Durable） | 检查点 + 恢复成标配 | 任务可中断续跑 |
| 运行时即控制平面 | 中断/审批/回放内建 | 前端可操控（见[前端演示界面](..%2FAgent%20配套技术生态模块%2F前端演示界面%2F08-Agent专属界面：思考过程与工具调用可视化.md)） |
| 组件可观测标准化 | OpenTelemetry Agent 扩展 | 组件级 trace 统一 |
| 组件商品化 | 记忆（Mem0/Zep）与工具（MCP）产品化 | 自研聚焦编排与业务 |
| 预算内建 | Step Budget 框架化 | 防失控成为默认 |

## 10. 与循环体系的衔接

本模块讲"四组件怎么协作"；[Loop Engineering](..%2FAgent开发%2FLoop%20Engineering%2F00-Loop%20Engineering知识体系总览.md) 讲"循环有哪些种类、怎么调"——两者是"协作机制"与"循环模式"的关系：组件决定能力，循环决定行为。实际落地时两者同时发生：四组件在循环里轮流上场，循环的每一轮都在调用四组件——设计时先定组件责任，再定循环节奏。
