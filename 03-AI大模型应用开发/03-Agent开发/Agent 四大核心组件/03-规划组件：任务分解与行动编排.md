# 规划组件：任务分解与行动编排

> 四大组件之"参谋部"：把目标拆成可执行步骤。2026 年的核心问题是"什么时候该规划、怎么拆才不塌"——Plan-and-Execute 与 ReWOO 的选择，取决于计划是否能预先定死。

## 1. 规划要解决什么

| 不规划的后果 | 规划的收益 |
|---|---|
| 长任务中途迷失目标（goal drift） | 步骤清单锚定方向 |
| 重复探索已走过路径 | 计划去重 |
| 步骤依赖不明确 | 显式依赖编排 |
| 无终止判断 | 明确完成条件 |

> 🎯 核心要点：**规划的本质是把"一个长决策"变成"一串短决策"**——每步决策更简单、更可验证、更可审计；短任务（≤3 步）不需要规划器。

## 2. Plan-and-Execute：规划与执行分离

```text
Planner（前沿模型，1-2 次调用）→ 步骤列表 JSON
Executor（便宜模型，每步 1 次）→ 按步执行（调工具）
Replanner（执行后评估）→ 完成则收尾 / 偏离则更新计划
```

| 角色 | 模型档位 | 职责 | 调用次数 |
|---|---|---|---|
| Planner | 前沿推理 | 出步骤列表 | 1-2 |
| Executor | 便宜（14B 可） | 单步执行+工具调用 | 每步 1 |
| Replanner | 中档 | 评估进度、重规划 | 每步 1（或按需） |

```python
# 伪代码：Plan-Execute 骨架
def plan_execute(goal: str, tools: dict, max_iter=8) -> str:
    plan = planner(goal)                    # 1. 规划：步骤列表
    for i in range(max_iter):
        step = plan.next_pending()
        if step is None:
            return plan.final_answer()      # 2a. 步骤耗尽 → 收尾
        result = executor(step, tools)      # 2b. 执行一步
        plan = replanner(goal, plan, result)  # 3. 评估+可能重规划
    return plan.summarize(goal, "达到迭代上限")
```

## 3. 任务分解质量：好计划的五条标准

| 标准 | 好的例子 | 坏的例子 |
|---|---|---|
| 原子性 | "查询订单表" | "处理所有数据" |
| 自包含 | "用 search 工具查 2026 财报" | "找数据"（工具不明） |
| 顺序依赖显式 | "先查 schema 再写 SQL" | 无先后 |
| 可验证 | "核对结果 >100 条" | "确保正确" |
| 最后一步产出答案 | "汇总为报告" | 步骤完没有收尾 |

> ⚠️ 分解的两大失败：**过细**（10+ 步的小任务，规划开销>收益）与**过粗**（一步塞三件事，执行器无法完成）。

## 4. 动态规划：Replan 的触发时机

| 触发信号 | 例子 | 动作 |
|---|---|---|
| 执行失败 | 工具报错 | 局部调整该步 |
| 观察偏离 | 数据与预期不符 | 更新后续步骤 |
| 新信息出现 | 搜索结果改变前提 | 重写计划 |
| 目标已达成 | 提前完成 | 提前收尾 |

```text
静态 vs 动态的权衡：
  静态（ReWOO/Blueprint）：计划一次定死 → 便宜（~2 次 LLM 调用，省 20 倍）
                          但"不能应变"——适合可预知的 DAG 型任务
  动态（Plan-Execute-Reflect）：每步观察后调整 → 贵
                          但能处理"调试-直到-通过"类任务
```

| 任务类型 | 选型 |
|---|---|
| 静态可分解（生成 N 个文件、拉 N 个源） | ReWOO/Blueprint（一次规划） |
| 观察驱动（调试、分支决策、易变 IO） | Plan-Execute-Reflect |

## 5. 规划组件的实现要点

| 要点 | 做法 |
|---|---|
| 计划存储 | 会话状态/内存（结构化 JSON） |
| 计划可编辑 | Replanner 可增删改步骤（不是重写全计划） |
| 进度追踪 | 每步状态（pending/running/done/failed） |
| 去重 | 已完成步骤标记，防止循环执行 |
| 上下文管理 | 别把整个执行历史塞进规划器（会爆窗） |
| 预算 | 步骤数上限（MaxIterations）+ 成本上限 |
| 目标锚定 | 把原始目标注入每轮 replan（防 goal drift） |

> 💡 已知失败模式（2026 运营警示）：**context blow-up**（Planner 把全部执行痕迹塞进下一轮提示词导致超窗）与 **goal drift**（子代理多轮后偏离原目标）——两者都要靠"只传必要状态 + 目标锚定"治理。

## 6. 规划策略选型矩阵（2026 实测）

| 策略 | LLM 调用 | 迭代 | 适用 | 最低模型 |
|---|---|---|---|---|
| ReAct | 低-中 | 3-10 | 简单工具任务 | 4B+ |
| Blueprint/ReWOO | ~2 | 静态 | 可预知 DAG | 4B+ |
| Plan-Execute-Reflect | 中-高 | 5-15 | 观察驱动工作流 | 14B+ |
| Reflexion | 中 | 3-8 | 准确率关键任务 | 8B+ |
| Tree-of-Thought | 高 | 5-20 | 创意/歧义问题 | 14B+ |

> 🎯 核心要点：**规划的复杂度要匹配任务的不可预知性**——可预知任务用 Blueprint（省 20 倍），不可预知才用 Plan-Execute-Reflect；无脑上"规划+反思"是小任务的最贵解。

## 7. 规划质量如何评测

| 评测方法 | 做法 | 说明 |
|---|---|---|
| 人工评审 | 20-50 任务抽查计划 JSON | 五条标准逐项打分 |
| 端到端回归 | 任务成功率对比（有/无规划器） | 判断规划是否值得 |
| 规划稳定性 | 同一任务多次规划一致性 | 计划随机 ≠ 质量差（看执行结果） |
| 重规划频率 | 计划被推翻的比例 | 过高 → 初始计划质量差 |
| 步骤利用率 | 计划步骤被执行的比例 | 大量未用步骤 → 计划冗余 |
| 分解粒度得分 | 五条标准（原子/自包含/依赖/可验证/收尾）逐项打分 | 人工抽检 20 份计划 |

> 💡 规划器的取舍判据：**加了规划器后任务成功率是否提升**——用 A/B 测。短任务（≤3 步）规划器常常是负收益（多一次 LLM 调用），长任务才是主场。另一个判据是"任务可预知性"：目标与步骤在开头就能说清 → Blueprint；必须边做边看 → Plan-Execute-Reflect。

## 8. 规划组件常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 计划过细 | 10+ 步的小任务 | 步骤粒度对齐任务复杂度 |
| 计划过粗 | 一步塞三件事 | 原子性标准 |
| 无 Replan | 观察与计划不符硬执行 | 观察驱动重规划 |
| 计划不存状态 | 重启丢计划 | 计划入会话状态/检查点 |
| 重复规划已做步骤 | 循环执行 | 进度追踪去重 |
| Planner 上下文爆炸 | 塞全部执行痕迹 | 只传必要状态 |
| 目标漂移 | 多轮后跑偏 | 每轮锚定原始目标 |
