# 日志、评估与质量层

> 质量层 = 观测之上回答"做得好不好"的一层。2026 两大原则：**遥测契约——不信 Agent 自报**（遇错模型常产出"看似合理"的输出而非报错）；**评估是持续流水线不是上线门禁**（"上个月通过的 eval 说明不了这周"）。本章给日志→评估→质量的完整链路。

## 1. 日志 vs 可观测 vs 评估

| 层 | 回答 | 手段 |
|---|---|---|
| 日志 | 发生了什么 | 结构化日志、遥测 |
| 可观测（Trace/指标） | 做了什么、多快、多贵 | OTel trace + 四类指标 |
| 评估（Eval） | 做得好不好 | LLM-judge/代码检查/人工 |

> 🎯 核心要点：**三层递进不重叠**——日志是原始证据、trace 是执行结构、评估是质量判断。2026 共识：日志对 LLM 系统"不够用"（Logging vs Observability 2026 专题），评估层不可省。

## 2. 遥测契约：不信 Agent 自报

| 项 | 说明 |
|---|---|
| 问题 | Agent 遇错常产出"看似合理"的输出而非错误消息——自报不可信 |
| 遥测契约 | 规范定义必须采集的状态转移/工具调用结果/决策点 |
| 机制 | 从执行器/工具层采集，独立于 Agent 内部推理 |
| 价值 | 捕获隐藏失败模式（"工具失败但 Agent 假装成功"） |

> ⚠️ 2026 金句（MLflow）：**"别相信 Agent 告诉你它做了什么"**——工具调用结果从执行器采集（Tool 06 篇执行器的审计职责联动），不从模型输出推断。

## 3. 评估手段谱系

| 手段 | 机制 | 适用 |
|---|---|---|
| LLM-as-judge | 评分模型打准确性/相关性/指令遵循 | 主观质量（采样 10-20%） |
| 代码评估 | 程序化检查（路径收敛、schema、状态） | 客观可验证 |
| 人工评审 | 抽查/标注队列 | 校准与疑难样本 |
| 启发式 | 规则/正则（长度、格式、关键词） | 快速第一道 |

> 🎯 核心要点：**评估手段按"可验证性"路由**——能代码验证的（状态/路径）用代码，不能的（相关性/指令遵循）用 judge，全部校准人工（2026 规范：自定义评估器要与人类判断校准）。

## 4. 三级评估粒度（LangChain 2026）

| 粒度 | 对象 | 例子 | 占比 |
|---|---|---|---|
| 单步 | run/span | 日历 Agent 是否先 find_meeting_times 再 schedule_meeting | ~一半测试套件 |
| 全轮 | trace | 轨迹（工具调全了吗）、最终响应质量、状态变化 | 核心 |
| 多轮 | thread/session | 上下文持久与累积（跨轮目标达成） | 会话级 |

> 💡 粒度选择逻辑：**单步测"决策对不对"，全轮测"轨迹好不好"，多轮测"会话成没成"**——只测最终回答会漏掉"工具选错但答案碰对"的失败（2026 共识：最终答案评分抓不住工具选择/重试/检索遗漏/循环行为）。

## 5. LLM-judge 生产模式

| 环节 | 做法 |
|---|---|
| 采样 | 线上流量 10-20%（全量评估成本失控） |
| 评分 | 事实准确性/相关性/指令遵循/目标完成 |
| 回写 | 分数写 span 属性——与延迟/token 同查（03 篇） |
| 告警 | 质量分阈值告警（09 篇） |
| 校准 | 自定义评估器与人工判断对齐 |

> ⚠️ **Evaluation Trust Tax**：外部 LLM judge 成本不可忽略——**~$260K/年 @500K traces/天**（Fiddler 2026）。预算成本治理（05 篇）时必须把评估成本算进去；小模型/自托管 judge 是降本路径。

## 6. 多轮评估：会话级质量

| 维度 | 内容 |
|---|---|
| 语义意图 | 整段会话的用户意图是否被满足 |
| 结果达成 | 最终产物是否符合目标 |
| 轨迹质量 | 跨轮行为是否高效/无漂移 |
| 上下文累积 | 第 N 轮是否正确使用了前 N-1 轮信息 |

> 🎯 核心要点：**多轮评估跑在 thread 上**（02 篇）——单轮判分 + 会话轨迹判分是 2026 标配（Observe 六表面之一：evals on traces）；最终回答评分对多轮 Agent 是残缺评估。

## 7. 与相邻体系分工

| 体系 | 分工 |
|---|---|
| Feedback & Evaluation 组件（平行） | 评估体系讲"评估工程本体"（数据集/指标/流程）；本体系讲"评估在可观测栈中的位置" |
| Guardrails 03 输出护栏 | 护栏在线拦截（主动）；评估离线/采样判分（被动）——护栏触发率是评估输入 |
| Reflection 08 评测 | 反思评测测反思价值；本体系测 Agent 整体质量 |

## 8. 常见误区

| 误区 | 真相 |
|---|---|
| "Agent 报错=失败" | 遇错常产出合理输出——遥测契约从执行层采集 |
| "日志够用" | 日志不判"好不好"——评估层不可省 |
| "只评最终回答" | 抓不住工具选择/重试/检索遗漏——三级粒度 |
| "全量评估" | 成本失控（Trust Tax）——10-20% 采样 |
| "评估器免校准" | 现成评估器不匹配你的"好"定义——需人类校准 |
| "评估是上线门禁" | 持续流水线——上个月过的 eval 说明不了这周 |
| "judge 便宜" | Trust Tax ~$260K/年——预算要算评估成本 |
| "评估同步跑" | 增加延迟——异步处理，不同步阻塞 |

## 9. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 三层递进？ | 日志（发生什么）→ 可观测（做了什么）→ 评估（好不好） |
| 遥测契约？ | 规范必须采集的状态/工具结果——不信 Agent 自报 |
| 评估手段？ | LLM-judge/代码/人工/启发式——按可验证性路由 |
| 三级粒度？ | 单步（决策）/全轮（轨迹）/多轮（会话） |
| 只评最终回答的问题？ | 抓不住工具选错但答案碰对 |
| LLM-judge 采样？ | 10-20%——全量成本失控 |
| Trust Tax？ | 外部 judge ~$260K/年 @500K traces/天——预算要算 |
| 评估器校准？ | 现成评估器不匹配你的"好"——人工校准 |
| 评估是门禁吗？ | 不是——持续流水线，每周都在变 |
| 多轮评估跑在哪？ | thread 上——单轮判分+轨迹判分 |
| 与护栏分工？ | 护栏拦截（主动）、评估判分（被动）——触发率是评估输入 |
| 与 Feedback & Evaluation 分工？ | 它讲评估工程本体，本体系讲评估在可观测栈的位置 |
