# 评估指标体系

> 指标 = 评估的"度量衡"。2026 两大陷阱：**同名指标不可互换**（"DeepEval 的 Faithfulness ≠ Ragas 的 Faithfulness"——不同 judge 提示词产出不同分数）与**选指标靠名字不靠实现**。本章给指标分类、同名陷阱与选型规范。

## 1. 指标五类地图

| 类别 | 指标 | 典型框架 |
|---|---|---|
| 文本质量 | 相关性、忠实度、连贯性、语气 | DeepEval/Promptfoo |
| RAG 专用 | Faithfulness、Response Relevancy、Context Precision/Recall | Ragas/DeepEval |
| 轨迹 | Tool Correctness、Argument Correctness、Step Efficiency（03 篇） | DeepEval/Ragas |
| 安全 | 毒性、偏见、注入、PII、越狱 | Promptfoo（红队） |
| 成本/系统 | 成本/样本、通过率、延迟 | 自建/观测 |

> 🎯 核心要点：**指标按任务域选，不是按框架选**——RAG 任务用 Ragas 系指标、Agent 轨迹用轨迹指标、安全用红队指标；"一个框架全包"是错觉（07 篇框架对比）。

## 2. 同名指标陷阱

| 陷阱 | 机制 | 防御 |
|---|---|---|
| 同名不同实现 | "Faithfulness in DeepEval 与 Ragas 不是同一个"——judge 提示词不同 → 分数不同 | 锁定实现 + 版本 |
| 指标名字靠猜 | 不验证实现细节就用 | 读实现文档/源码 |
| 跨框架不可比 | 同一数据集两框架分数不同 | 报告时标注框架+版本 |

> ⚠️ 2026 规范：**指标 = 名称 + 实现 + 版本 + judge 配置四元组**——报告分数必须带齐四元组；"提升 5 分"若不说明度量实现，等于没说。

## 3. 指标选择原则

| 原则 | 做法 |
|---|---|
| 任务对齐 | 指标测任务目标，不测框架擅长项 |
| 可验证优先 | 能代码验证的（状态/路径）用代码——judge 只留主观项 |
| 结果导向 | **outcome-grounded metrics**：行业特定 judge（ticket-resolved、claim-filed、appointment-booked）叠在通用指标上 |
| 覆盖静默失败 | 安全指标覆盖全会话（04 篇）——不只可见拒绝 |
| 分层组合 | 确定性 + 分类器 + judge 组合（02 篇 tier） |
| 校准 | 与人类判断对齐（08 篇） |

> 💡 **Outcome-grounded 是 2026 趋势**——"工单解决了吗/索赔提交了吗/预约成功了吗"是业务真相；通用指标（相关性/语气）是代理度量；**代理度量可能骗人，业务结果不骗人**。

## 4. 指标 vs 度量方式

| 度量方式 | 指标例子 | 延迟 | 成本 |
|---|---|---|---|
| 确定性代码 | schema 校验、状态检查 | 毫秒 | ~0 |
| 嵌入相似 | 余弦相似、语义距离 | 毫秒 | 低 |
| 训练分类器 | 毒性、注入 | 毫秒 | 低 |
| LLM-judge | 相关性、忠实度 | 数百 ms | 高（02 篇） |
| 人工 | 疑难评审 | 小时 | 最高 |

> 🎯 核心要点：**同一指标名可对应不同度量方式**——"相关性"既可用嵌入也可用 judge；选度量方式 = 精度 × 成本 × 延迟的权衡（分层 tier 的微观版）。

## 5. 指标版本治理

| 治理项 | 规范 |
|---|---|
| 版本化 | 指标实现+judge 配置锁定（02 篇） |
| 一致性监控 | 同一指标跨时间分数漂移检测 |
| 变更流程 | 指标升级走评估集回归——防"换尺子"假提升 |
| 报告规范 | 分数带四元组（名称/实现/版本/judge 配置） |
| 基准校准 | 人类标注子集持续比对（08 篇） |

> ⚠️ **"换尺子"与"产品变好"要分开**——指标升级必须对同一数据集跑新旧两版，报告 delta；否则"提升"可能是度量变化。

## 6. 指标选型速查（2026）

| 场景 | 推荐指标组合 |
|---|---|
| RAG 应用 | Faithfulness + Context Precision/Recall + Response Relevancy |
| 客服 Agent | Task Completion + Tool Correctness + ticket-resolved（outcome） |
| 编码 Agent | 执行验证通过率 + pass^k + 成本/任务 |
| 通用对话 | 相关性 + 连贯性 + 安全指标 |
| 高合规场景 | 轨迹指标 + 审计 + 人工复核 |

> 💡 组合逻辑：**通用指标打底 + 领域 outcome 指标定真相**——"相关性 0.9"是过程信号，"工单解决率 85%"是结果真相；两者都要。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "同名指标可互换" | 不同实现不同分数——锁定四元组 |
| "指标多=评估好" | 任务对齐 + 可验证优先——少而准 |
| "通用指标够用" | outcome-grounded 才是业务真相 |
| "嵌入相关性=judge 相关性" | 度量方式不同——标注方式 |
| "指标升级无感" | 换尺子假提升——新旧同跑报 delta |
| "一个框架全包" | 指标按域选——RAG/轨迹/安全分工 |
| "分数不用带上下文" | 报告带四元组——否则不可比 |
