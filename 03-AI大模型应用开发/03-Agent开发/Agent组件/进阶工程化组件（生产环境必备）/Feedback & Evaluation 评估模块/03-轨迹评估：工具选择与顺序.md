# 轨迹评估：工具选择与顺序

> 轨迹评估 = 以工具调用轨迹为评估单位：工具**是否被正确选择、正确参数化、正确排序**——2026 评估的核心战场。TRAJECT-Bench（ICLR 2026）是轨迹感知基准的里程碑；**执行验证**（查数据库状态/跑测试）取代最终文本检查。本章给轨迹评估完整设计。

## 1. 为什么轨迹是评估单位

| 输出评测的盲区 | 轨迹评估覆盖 |
|---|---|
| "答对了"掩盖"过程错" | 工具选对了吗 |
| 看不到参数错误 | 参数化正确吗 |
| 看不到顺序错误 | 依赖满足吗 |
| 看不到重试/循环 | 步骤高效吗 |

> ⚠️ 2026 金句（TRAJECT-Bench 团队）：**"正确输出可以掩盖错误的推理"**——尤其合规领域需要审计轨迹；轨迹评估是捕获"错误在放大前"的唯一手段。

## 2. TRAJECT-Bench（ICLR 2026）

| 项 | 说明 |
|---|---|
| 定位 | 轨迹感知的 Agent 工具使用基准 |
| 检验 | 工具选择/参数化/排序的正确性（超越最终答案） |
| 工具 | 高保真可执行工具 + 生产风格 API |
| 轨迹合成 | 宽度（并行调用）与深度（依赖链）变化 |
| 诊断 | 轨迹级：工具选择/参数正确性 + 依赖/顺序满足 |

| 发现的失败模式 | 机制 |
|---|---|
| 相似工具混淆 | 模型选了名字相似但错误的工具 |
| 参数盲目选择 | 参数填充靠猜而非验证 |
| 短→中轨迹瓶颈 | 从短轨迹到中长轨迹出现扩展瓶颈 |

> 🎯 核心要点：TRAJECT-Bench 的贡献是**把"轨迹正确性"变成可度量对象**——选择/参数/顺序三个维度各自可测，为生产轨迹评估提供了基准模板。

## 3. 轨迹指标族（DeepEval 2025 首发）

| 指标 | 含义 |
|---|---|
| Task Completion | 任务是否完成 |
| Tool Correctness | 工具选择是否正确 |
| Argument Correctness | 参数是否正确 |
| Step Efficiency | 步骤是否高效（无冗余调用） |
| Plan Adherence | 是否按计划执行 |

> 💡 轨迹指标是生产评估的基础件——**最终答案评分 + 轨迹指标组合**是 2026 标准配置（"评分最终状态，不只最后一条消息"）。

## 4. 工具选择指标：别漏 irrelevance bucket

| 指标 | 内容 |
|---|---|
| 选择准确率 | 该调的调对了吗 |
| **Irrelevance bucket** | **不该调的时候调了吗**（BFCL v3 2025 新增） |
| 参数验证 | 参数合法性 |
| 调用准确率 | 函数名/参数完全匹配 |

> ⚠️ 2026 陷阱警示：**工具选择只在"预期调用工具"的用例上评分 → 过度调用回归不可见**——"不需要工具却调了"（成本+污染）必须单列 bucket；BFCL v3 补上此桶是行业修正的标志。

## 5. 执行验证：最终状态 > 最终文本

| 验证方式 | 机制 | 优势 |
|---|---|---|
| 语法检查 | 工具调用语法 | 弱——语法对不代表动作对 |
| 最终文本检查 | 答案关键词 | 弱——可编造 |
| **执行验证** | 检查数据库状态/跑测试套件 | **强——状态为证** |
| 代理状态评估 | LLM 状态追踪器从轨迹推结构化状态（ACL 2026 Industry） | 无后端成本，人机一致 >90% |

> 🎯 核心要点：**tau-bench 的范式——"验证最终答案 AND 验证结果数据库状态"**——回答"已退款"不算完成，数据库里退款记录存在才算；标准 pass/fail 漏 65-93% 安全问题正因此（01 篇）。

## 6. 轨迹评估的工程落地

| 环节 | 做法 |
|---|---|
| 采集 | trace 执行树（观测 02 篇结构）——轨迹评估的原料 |
| 打分 | 轨迹指标（§3）+ 执行验证（§5） |
| 校准 | 人类标注轨迹子集——轨迹评估器与人工对齐 |
| 门禁 | 轨迹指标进 CI（09 篇）——不只最终答案通过率 |
| 诊断 | 失败轨迹归因：选择错/参数错/顺序错（分类学） |

> 💡 与观测体系衔接：**轨迹评估消费 trace 执行树**（观测 02 篇）——工具 span 挂推理 span 的结构正是轨迹打分的输入；"评估与观测共享同一数据平面"是 2026 架构原则。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "最终答案对就行" | 正确输出掩盖错误推理——轨迹评估 |
| "工具选择只在预期用例评分" | 漏 irrelevance bucket——过度调用不可见 |
| "语法检查够了" | 执行验证（状态为证）才是强验证 |
| "轨迹评估=打分工具" | 是消费 trace 的完整工程（采集→打分→校准→门禁） |
| "参数错不影响" | Argument Correctness 是核心维度 |
| "一次轨迹评估终身有效" | 模型/工具演进——轨迹指标持续监控 |
| "轨迹评估贵" | 确定性轨迹检查毫秒级——LLM judge 只评争议 |
