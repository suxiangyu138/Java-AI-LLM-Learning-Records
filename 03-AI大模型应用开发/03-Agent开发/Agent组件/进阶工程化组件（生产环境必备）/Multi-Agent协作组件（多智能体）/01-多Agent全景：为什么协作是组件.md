# 多 Agent 全景：为什么协作是组件

> 多 Agent = 用一群专业 Agent 协作替代单体 Agent。2026 生产共识：**swarm 取代单体**——Triage 路由 + 窄专家比"一个大模型挂几十个工具"更可靠；但多 Agent 是**代价高昂的工程决策**（token 3-10x、级联风险、治理复杂度）。本章立起全景：价值、代价与"何时不用"。

## 1. Swarm 模式：2026 生产主流

| 单体 Agent | Swarm（多 Agent） |
|---|---|
| 一个大模型 + 几十个工具 | Triage Agent 路由 + 窄专家（SQL Agent 一个工具、Python Agent 隔离容器） |
| 工具选择负担全在模型 | 每个专家只做一件事 |
| 上下文膨胀（工具定义全量） | 每个 Agent 上下文最小化 |
| 单点失败 | 分工隔离（也带来新风险） |

> 🎯 核心要点：**swarm 的本质是"决策负担分而治之"**——不是"模型不够强"，而是"几十个工具的上下文让任何模型都变笨"（Tool 05 篇数量治理的架构级解）。

## 2. 协作的价值

| 价值 | 机制 |
|---|---|
| 专业化 | 每个 Agent 最小上下文 + 专注任务 |
| 隔离 | 危险操作隔离（Python 容器化） |
| 并行 | 独立子任务并发执行 |
| 组合 | 可复用的 Agent 库（研究/代码/合规） |
| 权限最小化 | 每个 Agent 只有任务所需权限（Guardrails 09 篇 JIT） |

## 3. 协作的代价

| 代价 | 数据/机制 |
|---|---|
| Token 乘数 | 每次交接新 LLM 调用——**多 Agent token 是单 Agent 的 3-10x** |
| 延迟叠加 | 串行交接 × 每次推理 |
| 级联失败 | ~12% 长运行含传播错误（08 篇） |
| 治理复杂度 | 87% 优先互操作 vs 7-8% 成熟治理（00 篇） |
| 调试难度 | 跨 Agent 归因（09 篇） |

> ⚠️ 2026 金句：**"单 Agent + 好工具定义通常胜过编排糟糕的三 Agent 团队"**（框架对比共识）——多 Agent 是手段不是目的；先问"单 Agent 真的不行吗"。

## 4. 何时该上多 Agent

| 信号 | 单 Agent | 多 Agent |
|---|---|---|
| 任务域 | 单一领域 | 多域协作（研究+编码+合规） |
| 工具数 | <20 | 工具生态按域可分组 |
| 权限 | 统一权限可接受 | 需要按域隔离权限 |
| 并行 | 串行可接受 | 独立子任务需并行 |
| 专家知识 | 模型通用能力够 | 各域需要不同提示/模型 |
| 失败容忍 | 低（单点） | 需要隔离故障域 |

> 🎯 核心要点：**多 Agent 的决策矩阵是"域 × 权限 × 并行 × 失败隔离"**——四维任一强烈成立才值得多 Agent；"为了酷而上多 Agent"是 2026 最常见的架构错误（3-10x token 白付）。

## 5. 无状态原则

| 原则 | 说明 |
|---|---|
| Agent 无状态 | 单个 Agent 每次调用无状态——系统跨流程保状态 |
| 状态归属 | 编排层/存储层持有状态（记忆体系） |
| 交接语义 | 交接传递"任务+上下文"，不传"历史"（05 篇） |
| 收益 | 可重试/可替换/可水平扩展 |

> 💡 与感知 08 篇 state-carry 同源：**交接传类型化状态，不重放完整轨迹**——O(n²)→O(n) token；无状态 Agent 是水平扩展与故障恢复的前提。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "多 Agent 一定更好" | 单 Agent+好工具通常赢——3-10x token 白付 |
| "Agent 越多越强" | 每加一个 Agent 加一条交接——级联面扩大 |
| "多 Agent=大模型不够" | 是决策负担分治——上下文管理问题 |
| "交接免费" | token 乘数 + 延迟叠加 + 上下文碎片 |
| "Agent 要带全历史" | 无状态 + 交接传状态——O(n²)→O(n) |
| "隔离自动带来安全" | 分工隔离也带来信任边界新风险（08 篇） |
| "先上再优化" | 决策矩阵四维先评估——域×权限×并行×隔离 |
