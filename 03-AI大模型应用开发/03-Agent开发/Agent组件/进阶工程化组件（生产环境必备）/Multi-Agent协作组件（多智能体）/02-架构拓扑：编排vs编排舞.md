# 架构拓扑：编排 vs 编排舞

> 拓扑 = 多 Agent 系统的"组织架构"：谁指挥谁、谁听谁的、谁防止循环。2026 共识：**生产系统刻意混合编排与编排舞**——需审计合规的步骤编排、需速度弹性的步骤编排舞；**DAG 约束防无限循环**是铁律。本章给拓扑全景与选型。

## 1. 两种基本组织模式

| 维度 | 编排（Orchestration） | 编排舞（Choreography） |
|---|---|---|
| 控制 | 中央控制器分解目标按序调用 | 无中央——Agent 订阅事件自主行动 |
| 审计 | ✅ 天然审计轨迹 | ❌ 难追溯 |
| 调试 | 单一调试点 | 分布式排查 |
| 瓶颈 | 中央控制器瓶颈/单点失败 | 无瓶颈 |
| 速度 | 串行决策 | 事件驱动并行 |
| 弹性 | 控制器挂了全停 | 成员自治存活 |

> 🎯 核心要点：**不是二选一，是混合**——"需要审计与合规签字的步骤用编排，需要速度与弹性的步骤用编排舞"（2026 生产共识）；纯编排 = 单点脆弱，纯编排舞 = 无法审计。

## 2. 常见拓扑模式

| 模式 | 结构 | 适用 |
|---|---|---|
| 顺序（Sequential） | 管线式 A→B→C | 固定流程 |
| 并发（Concurrent） | 并行扇出 | 独立子任务 |
| Hub-and-Spoke | 中央路由到专家 | 任务路由（三站式） |
| 层级监督（Hierarchical） | supervisor 树 | 大任务分解 |
| 群聊（Group Chat） | 多 Agent 对话（06 篇） | 协作讨论 |
| 交接（Handoff） | 委托-完成-回传 | 跨域任务 |
| 联邦（Federated） | 无主 Agent——动态结盟 | 涌现协作 |

> 💡 2026 平台现状：hub-and-spoke 与层级监督已成为 Microsoft Foundry 等平台的标准模式；联邦/涌现编排（递归委派、自组织群）是前沿方向——"一个 Agent 失败，请求方无缝改约替代提供者"。

## 3. DAG 约束：防循环铁律

| 原则 | 说明 |
|---|---|
| 有向无环图 | 控制流必须是 DAG——禁止循环依赖 |
| 顶层规划 | 顶层 planner 调用下游执行者 |
| 执行者纪律 | **执行者之间不互调、不回调编排者** |
| 工具 | LangGraph StateGraph 类显式图结构 |
| 反例 | 两 Agent 自引用对话 9 天消费 60,000+ token（08 篇） |

> ⚠️ 2026 教训：**九日无限循环**——两个 Agent 进入自引用对话，无终止、无属主通知、60,000+ token——DAG 约束 + 轮次上限 + 断路器（09 篇）三件套缺一即事故。

## 4. 拓扑选型决策

```text
拓扑选型：
├─ 固定流程 → 顺序/并发（管线）
├─ 任务路由（域多） → Hub-and-Spoke（Triage）
├─ 大任务分解 → 层级监督（supervisor 树）
├─ 需审计 → 编排（轨迹天然）
├─ 需弹性 → 编排舞（事件驱动）
└─ 自治生态 → 联邦（前沿）
```

| 维度 | 决策 |
|---|---|
| 审计要求 | 高 → 编排 |
| 弹性要求 | 高 → 编排舞 |
| 任务形态 | 路由 → hub；分解 → 层级 |
| 流程确定性 | 固定 → 顺序管线 |
| 协作深度 | 讨论 → 群聊 |

> 🎯 核心要点：拓扑是**按任务特征选**不是按流行选——固定流程用管线、多域用路由、大任务用层级、讨论用群聊；混合是常态（编排+编排舞并存）。

## 5. 编排层的职责边界

| 职责 | 说明 |
|---|---|
| 路由 | 任务 → 专家分配（Triage） |
| 状态管理 | 跨 Agent 状态持有（01 篇无状态原则） |
| 环境执行 | 沙箱/权限/资源（Guardrails 联动） |
| 审计 | 编排步骤的天然轨迹 |
| 失败处理 | 重试/降级/人工升级（08 篇） |

> 💡 2026 认知：**基础模型原生推理后，外部反思脚手架（Plan-Execute 循环）大多冗余**——编排层的真正工作从"推理脚手架"变成"路由 + 状态 + 环境执行"（范式 04 篇联动）。

## 6. 编排舞的实现机制

| 机制 | 说明 |
|---|---|
| 事件总线 | Agent 订阅/发布事件（解耦） |
| 契约 | 事件 schema 版本化（防断裂） |
| 补偿 | 事件失败的事务补偿 |
| 可观测 | 事件流追踪（W3C traceparent，09 篇） |
| 治理 | 事件审计窗口（合规） |

> ⚠️ 编排舞的代价：**无中央 = 无自然审计点**——事件流必须补追踪与审计，否则合规场景无法上线（治理成熟度 7-8% 的现实原因之一）。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "编排或编排舞二选一" | 生产混合——审计步骤编排、弹性步骤编排舞 |
| "DAG 限制能力" | DAG 防循环——执行者互调是事故源头 |
| "群聊=全员参与" | 群聊有 token 开销——广播 vs 定向要选 |
| "联邦编排=无治理" | 无主 ≠ 无治理——事件审计要补 |
| "拓扑选流行" | 按任务特征选——固定流程管线、多域路由 |
| "编排层管推理" | 2026 编排层管路由/状态/环境——推理是模型的事 |
| "编排舞免费" | 无自然审计点——追踪审计要自己补 |

## 8. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 编排 vs 编排舞？ | 中央控制器 vs 事件自治——审计 vs 弹性 |
| 2026 共识？ | 混合——审计步骤编排、弹性步骤编排舞 |
| 常见拓扑？ | 顺序/并发/hub/层级/群聊/交接/联邦 |
| DAG 铁律？ | 有向无环 + 执行者不互调不回调 |
| 九日循环教训？ | 自引用对话无终止——DAG+轮次上限+断路器 |
| 编排层职责 2026？ | 路由/状态/环境执行——不是推理脚手架 |
| 编排舞代价？ | 无自然审计点——追踪审计自补 |
| Hub-and-Spoke？ | Triage 路由到专家——三站式 |
| 层级监督？ | supervisor 树——大任务分解 |
| 联邦编排？ | 无主动态结盟——递归委派（前沿） |
| 拓扑选型第一问？ | 审计要求 vs 弹性要求 |
| 与 08 篇关系？ | 拓扑决定信任边界形状——级联风险面 |
