# 文本感知：输入清洗与预处理

> 文本感知 = 用户输入/文档/日志等文本源进入 Agent 的第一道处理：清洗、结构化、去噪。2026 实证必须内化：**噪声上下文比不检索还差（8.0% vs 23.6%）**；上下文填到 80% 窗口精度从 94% 掉到 61%——文本感知的第一原则是"让窗口里的每个 token 都高信号"。本章给文本感知完整设计。

## 1. 文本感知的三层职责

| 层 | 职责 | 例子 |
|---|---|---|
| 清洗 | 格式归一、编码修复、噪声剔除 | 乱码修复、HTML 标签剥离、BOM/控制字符 |
| 结构化 | 从自由文本提取可处理结构 | JSON 解析、日志字段化、表格识别 |
| 增强 | 补充决策所需上下文 | 实体链接、时间归一、引用解析 |

> 🎯 核心要点：文本感知不是"把文本原样交给模型"——是**"把文本加工成模型能高效消费的高信号形式"**。原始文本进窗口的成本由 Agent 买单：token、注意力、错误推理。

## 2. 清洗规则清单

| 类别 | 规则 | 反例 |
|---|---|---|
| 编码 | 统一 UTF-8；乱码修复（GBK/UTF-8 混淆） | 直接拼接带 BOM/控制字符文本 |
| 格式 | 空白归一、换行策略（保留段落语义） | 全部压成一行（丢失结构） |
| 标记 | HTML/XML 标签剥离（保留语义标签） | 标签原文进窗口（噪声） |
| 噪声 | 时间戳/日志前缀折叠、重复行去重 | 千条同构日志全量进窗口 |
| 安全 | 链接/凭据识别（脱敏前置，Guardrails 02 篇衔接） | 敏感数据进窗口才处理 |

> 💡 清洗的目标不是"干净"，是**"保留语义、去掉冗余"**——过度清洗（如把所有换行压没）反而破坏模型理解段落结构。

## 3. 去噪实证：噪声为什么致命

| 实证（Redis 2026） | 数据 |
|---|---|
| 纯噪声上下文 vs 不检索 | 8.0% vs 23.6% 精确匹配——**噪声比没有更差** |
| 窗口填充 40% → 80% | 精度 94% → 61%（内容全相关！）——**体积本身就是敌人** |
| 完美检索下输入变长 | 性能仍降 13.9-85%——上下文分心（distraction） |
| 注意力 U 型 | 相关文档居中 → 20 文档 QA 精度 -20%；GPT-3.5 第 10/20 文档 52.9% < 无文档 56.1% |

> ⚠️ 2026 金句：**"小窗口+对的信息 > 大窗口+全的信息"**——文本感知的 KPI 不是"覆盖多少信息"，而是"窗口里高信号占比多高"。这条实证是 08 篇装配策略的立论基础。

## 4. 感知失败模式：五宗罪

| 失败模式 | 机制 | 防御 |
|---|---|---|
| 毒化（Poisoning） | 错误/对抗信息当真理；多步流程早期错误变既定事实 | 来源标记、交叉验证、护栏 |
| 分心（Distraction） | 历史/工具输出淹没推理 | 窗口治理、压缩（Memory 02 篇） |
| 混淆（Confusion） | 无关工具/文档导致选错 | 工具过滤（Tool 02 篇）、文档裁剪 |
| 冲突（Clash） | 同窗口矛盾信息 | 冲突检测、来源优先级 |
| 腐烂（Rot） | 上下文填满后整体退化（token 内也会发生） | 主动修剪、turn-atomic（Memory 体系） |

> 🎯 核心要点：五宗罪是文本感知的**体检清单**——每次装配前问：这窗口里有毒化信息吗？会被分心吗？会选错吗？有冲突吗？腐烂了吗？五个"否"才是合格装配。

## 5. 结构化：从文本到可处理结构

| 输入 | 结构化做法 | 产出 |
|---|---|---|
| 日志 | 正则/模式解析 → 字段 | {时间, 级别, 服务, 消息} |
| 表格 | 表格识别 → 行对象 | [{列1, 列2}] |
| 对话 | 角色分离、意图标记 | [{role, content}] |
| 文档 | 分块 + 元数据（RAG 04 篇衔接） | {chunk, 标题, 位置} |
| JSON 字符串 | 解析 + schema 校验（Output Parser 02 篇反向应用） | 对象 |

> 💡 结构化的度：**够决策即可**——不需要把每个细节都结构化，只结构化"影响下一步动作"的部分；过度结构化 = 特征提取噪声（02 篇）。

## 6. 与相邻体系的分工

| 体系 | 分工 |
|---|---|
| 爬虫体系 | 爬虫管"怎么把网页数据拿到手"（采集）；感知管"拿到后怎么进 Agent 窗口"（处理） |
| RAG 文档 ETL | 文档加载/解析/切片是 RAG 侧的感知；文本感知是 Agent 侧的通用输入处理 |
| 输入护栏 | 护栏管"安全策略"（拦截/脱敏）；感知管"信号质量"（清洗/去噪）——先安全后质量 |
| Memory 工作记忆 | 感知处理"当前输入"，工作记忆治理"窗口存量" |

> ⚠️ 爬虫与感知的分界：爬虫体系在"数据获取工具链"层（requests/解析库/反爬），感知模块在"Agent 运行时输入处理"层——同一个网页，爬虫拿到手，感知模块决定怎么进窗口。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "原始文本最保真" | 噪声/冗余稀释信号——清洗是第一投资 |
| "全检索进来总比漏好" | 噪声比不检索差 15.6 点——检索质量先于数量 |
| "窗口大就安全" | 80% 填充精度 94%→61%——体积是敌人 |
| "清洗=删东西" | 清洗=保留语义去冗余——过度清洗毁结构 |
| "结构化越全越好" | 够决策即可——过度结构化制造噪声 |
| "文本感知=爬虫" | 爬虫管采集，感知管窗口处理——两个层 |
| "失败模式上线后再说" | 毒化/分心是架构问题——装配前就要体检 |

## 8. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 文本感知三层？ | 清洗（格式/编码/噪声）/ 结构化 / 增强 |
| 噪声实证？ | 纯噪声 8.0% vs 不检索 23.6%——噪声比没有更差 |
| 体积实证？ | 40%→80% 填充精度 94%→61%——体积是敌人 |
| 五宗罪？ | 毒化/分心/混淆/冲突/腐烂 |
| U 型注意力？ | 关键内容居中比不检索更糟——放首尾 |
| 清洗目标？ | 保留语义去冗余，不追求"干净" |
| 结构化原则？ | 够决策即可 |
| 与爬虫分工？ | 爬虫管采集，感知管进窗口 |
| 与护栏顺序？ | 外部输入先安全（拦/脱敏）后质量（清洗） |
| KPI？ | 窗口高信号占比，不是信息覆盖量 |
| 毒化怎么防？ | 来源标记+交叉验证+护栏 |
| 与 RAG ETL 关系？ | RAG 文档处理是检索侧感知，文本感知是通用输入处理 |
