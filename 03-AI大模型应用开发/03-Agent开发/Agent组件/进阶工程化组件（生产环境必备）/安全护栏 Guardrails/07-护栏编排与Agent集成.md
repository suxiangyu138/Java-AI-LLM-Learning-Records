# 护栏编排与 Agent 集成

> 编排 = 把五类护栏放进 Agent 循环的正确位置，用正确的语义、正确的顺序执行。2026 铁律：**护栏是一等执行逻辑，不是事后附加**——只在部分路径运行、可被绕过的护栏提供的是假信心。本章给护栏编排的完整设计。

## 1. 护栏在 Agent 循环中的位置

```text
Agent 循环 + 护栏（五 rail 落位）：
  用户输入 ──→ [Input rail：注入检测 + PII 脱敏]
                    ↓
  上下文装配 ──→ [Retrieval rail：检索块源验证 + 隔离]
                    ↓
              LLM 推理（工具选择）
                    ↓
  工具调用 ──→ [Execution rail：授权 + 参数校验 + 风险分级] ──→ 执行 → 结果回注
                    ↓
              LLM 推理（最终输出）
                    ↓
  输出 ──→ [Output rail：幻觉 + 毒性 + 格式 + PII]
                    ↓
  多轮 ──→ [Dialog rail：话题边界 + 流程控制]
```

> 🎯 核心要点：**护栏的位置 = 拦截点的位置**——每个数据跨越系统边界处都是一道闸：用户输入进系统、检索内容进上下文、工具调用出系统、模型输出出系统。任何一跳缺失都是攻击通道。

## 2. 执行顺序与延迟分层

| 顺序 | 护栏 | 成本 | 策略 |
|---|---|---|---|
| 1 | 规则闸（正则/黑名单） | ~0 | 所有请求必经，毫秒级 |
| 2 | 轻分类器（注入/PII） | 5-15ms | 所有请求必经 |
| 3 | 专用分类器（毒性等） | 低 | 按风险场景开关 |
| 4 | 模型判断（幻觉/复杂语义） | 高 | 仅高风险输出 |
| 5 | 人工确认 | 极高 | 仅 DANGEROUS 动作 |

> ⚠️ 2026 校准原则：**全栈护栏留给不可逆高风险动作**（支付、删除、发布）；**低风险高并发请求走轻量并行检查**——不是每类请求都过全栈（01 篇"校准而非最大化"）。

## 3. 护栏的四种执行语义

| 语义 | 行为 | 场景 |
|---|---|---|
| 静默检查 | 检查通过才继续，失败静默处理 | 格式校验、PII 脱敏 |
| 结构化回退 | 失败 → 错误回传（模型可修正） | invalid_arguments、可修复违规 |
| Tripwire | 触发即中断整个循环 | 注入检测、攻击特征（OpenAI Agents SDK 语义） |
| 人工接管 | 暂停，等待人类决策 | DANGEROUS 级动作确认 |

> 💡 Tripwire 与普通拦截的本质区别：**普通拦截是"拦这一下"，tripwire 是"停整台机器"**——攻击可能借后续步骤完成，检测到攻击特征时继续循环本身就是风险。

## 4. 护栏即反馈：与循环的质保集成

```text
护栏即反馈（生产模式）：
  输出护栏检测到问题（如幻觉断言）
    → 构造定向修正提示（"此断言无支撑，请修正"）
    → 追加为消息回喂模型
    → 模型重新生成
    → 重检（护栏再跑）
    → 通过 → 放行；仍失败 → 达重试上限 → 降级/人工
```

| 集成点 | 做法 |
|---|---|
| 重试上限 | 2-3 次（防延迟成本失控） |
| 失败降级 | 达上限 → refrain 后备响应或人工 |
| 遥测 | 每轮修正记录：触发护栏、修正内容、重试次数 |
| 与反思的关系 | 护栏回喂是"外部化反思"——Reflection 06 篇的外部验证同源 |

> 🎯 核心要点：护栏即反馈把"安全阀"升级为"质量循环"——拦截不是终点，修正才是；这也让护栏的 FPR（误报）代价大幅下降（误报 → 一次修正，而非一次拒绝）。

## 5. 与 Agent 组件的集成点

| 组件 | 集成方式 |
|---|---|
| 工具执行器 | Execution rail 挂执行器前置钩子（Tool 06 篇五步循环的"授权"步） |
| 记忆系统 | 写入前护栏（防记忆投毒）+ 读出注入前检查 |
| 检索系统 | Retrieval rail：块级源验证、脱敏、隔离标记 |
| 反思模块 | 护栏回喂可作为反思的外部信号（Reflection 06 篇） |
| 规划器 | 执行前对计划整体做策略校验（危险动作序列预警） |
| 可观测组件 | 护栏决策全部发遥测：触发率/位置/结果 |

> ⚠️ 记忆是护栏最容易漏的点：**攻击者借工具结果投毒记忆，跨会话生效**（OWASP 记忆投毒，09 篇）——记忆写入要过护栏，读出要检查注入特征。

## 6. 编排模式：影子流量与灰度

| 模式 | 做法 | 用途 |
|---|---|---|
| 旁路（shadow） | 护栏决策与线上对照，不执行拦截 | 新护栏上线前评估误报率 |
| 灰度拦截 | 按比例/租户逐步开启拦截 | 控制风险面 |
| 流量镜像 | 决策记录与真实流量对比 | 阈值校准（08 篇） |
| 强制模式 | 高风险路径永远全量拦截 | 不可逆动作 |

> 💡 2026 实践：新护栏策略先进 shadow 对照流量 → 校准阈值 → 灰度开启 → 全量；**护栏策略本身也要版本管理与回滚**——错误的护栏策略（高误报）比没有护栏更伤产品。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "护栏在关键路径加一下就行" | 只跑部分路径的护栏是假信心——所有边界都要覆盖 |
| "每层检查都要模型判断" | 按顺序分层：规则→分类器→模型——成本递增 |
| "Tripwire 太激进" | 检测到攻击特征继续循环才是风险——高危必须停 |
| "护栏回馈=无限重试" | 上限 2-3 次，达上限降级——不失控 |
| "护栏决策不用记" | 遥测是改进与审计的基础——决策全留痕 |
| "记忆不用过护栏" | 记忆投毒跨会话生效——写入读出都要检查 |
| "直接全量开新护栏" | shadow → 灰度 → 全量——策略也要版本管理与回滚 |

## 8. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 五 rail 落位？ | 输入进系统/检索进上下文/工具出系统/输出出系统/多轮流 |
| 延迟分层顺序？ | 规则→轻分类器→专用分类器→模型判断→人工 |
| 四种执行语义？ | 静默/结构化回退/Tripwire（中断循环）/人工接管 |
| Tripwire 与普通拦截区别？ | 拦"这一下" vs 停"整台机器" |
| 护栏即反馈流程？ | 检测→定向修正回喂→重检→通过或降级 |
| 重试上限？ | 2-3 次，达上限降级/人工 |
| 护栏与记忆集成？ | 写入防投毒 + 读出查注入——防跨会话攻击 |
| shadow 模式？ | 决策对照不拦截——新护栏先评估误报 |
| 护栏策略要不要版本管理？ | 要——高误报策略比没有护栏更伤产品 |
| 与反思关系？ | 护栏回喂是外部化反思（Reflection 06 同源） |
| 与工具执行器集成？ | Execution rail 挂执行器前置钩子（授权步） |
| 校准原则？ | 全栈给不可逆动作，轻量给高并发低风险 |
