# 工具与执行护栏：动作层防线

> 工具护栏 = 模型生成 tool call 之后、真实动作执行之前的动作层校验。2026 关键认知：**中间工具调用是独立风险面**——只查最终文本的输出策略，挡不住编码 Agent 选择破坏性工具。ToolSafe（ACL 2026）证明步骤级护栏可使有害工具调用减少 65%。本章给动作层防线完整设计。

## 1. 为什么工具层需要独立护栏

| 现实 | 后果 |
|---|---|
| 输出策略只查最终文本 | 编码 Agent 已调用破坏性工具（中间动作逃逸） |
| 工具参数是模型生成 | 参数注入/危险参数直接进执行器 |
| Agent 有宽工具权限 | 攻击可借合法工具链做坏事（读文件→外连 47 次） |
| 工具结果是注入面 | 返回内容可携带指令影响后续决策 |

> 🎯 核心要点：**护栏的拦截点必须覆盖"动作层"**——不只是"模型说了什么"，而是"模型让系统做了什么"。五 rail 中的 execution rail 是这个问题的标准答案。

## 2. 工具护栏的四道校验

| 校验 | 内容 | 例子 |
|---|---|---|
| 工具选择校验 | 该工具是否被授权、是否在风险白名单 | 拒绝未注册/被禁用工具 |
| 参数校验 | schema 合规 + 业务规则 + 危险值拦截 | URL 非白名单域、路径越界 |
| 动作风险评估 | 工具+参数的副作用分级 | 只读自动 / 写节流 / 危险确认 |
| 调用序列校验 | 序列模式是否异常 | 读文件→外连网络组合告警 |

```python
# 工具护栏最小逻辑（示意）
def execution_guardrail(tool_call, ctx):
    tool, args = tool_call.name, tool_call.arguments
    # 1. 授权检查
    if tool not in ctx.allowed_tools:          # 最小权限（Tool 08 篇）
        return BLOCK, "工具未授权"
    # 2. 参数校验（schema + 业务）
    violations = validate_args(tool, args)     # 危险值/白名单/格式
    if violations:
        return FIX, {"status": "error", "code": "invalid_arguments", ...}
    # 3. 风险分级
    risk = risk_level(tool, args)              # READ/WRITE/DANGEROUS
    if risk == DANGEROUS and not ctx.approved:
        return ASK_USER, "确认执行？"          # 确认模式衔接
    # 4. 序列检测
    if anomaly_pattern(ctx.history, tool):     # 行为异常
        return BLOCK, "调用序列异常，已拦截"
    return PASS, args
```

> ⚠️ 与 [Tool 工具开发与注册 08 篇](..%2F..%2F..%2FAgent%20子组件专项学习%2FTool%20工具开发与注册%2F08-工具安全：权限-注入与治理.md) 的分工：工具体系讲"工具本体的安全设计"（注册期校验、最小权限、五道防线）；本体系讲"护栏组件如何在执行层做运行时拦截"——两者接口在 execution rail。

## 3. ToolSafe：步骤级工具护栏（ACL 2026）

| 项 | 说明 |
|---|---|
| 问题 | 传统护栏只查输入/输出，不查"每一步工具调用是否安全" |
| TS-Bench | 步骤级工具调用安全检测基准（攻击+良性混合） |
| TS-Guard | 多任务 RL 工具护栏：在工具调用时判断安全性 |
| 效果 | ReAct 式 Agent 有害工具调用平均减少 **65%**；注入攻击下良性任务完成提升 ~10% |
| 意义 | 证明"动作层护栏"可量化改进——不只防住攻击，还保住了良性完成率 |

> 🎯 核心要点：ToolSafe 的贡献是**把工具护栏从"校验器"升级为"可训练决策器"**——用 RL 学"什么工具序列安全"；其基准 TS-Bench 是工具护栏的评测基础设施（08 篇评测方法可套用）。

## 4. 执行拦截机制：tripwire 与审批流

| 机制 | 语义 | 场景 |
|---|---|---|
| 静默拦截 | 直接阻断，模型感知不到 | 低危违规（参数格式） |
| 结构化回退 | 拦截 + 错误回传模型 | 可修复错误（invalid_arguments） |
| Tripwire | 触发即中断整个循环 | 高危（检测到注入/攻击特征） |
| 人工确认 | 暂停等待人类决策 | DANGEROUS 级动作（确认模式） |
| 终止会话 | 中断 + 冻结 + 告警 | 检测到正在进行的攻击 |

> 💡 Tripwire 是 OpenAI Agents SDK 的护栏机制：输入/输出护栏触发时**立即停止执行**——比"拦截后继续"更安全（攻击可能借后续步骤完成）。2026 实践：高危事件用 tripwire 语义，普通违规用结构化回退。

## 5. 参数层防护：模型输出不可信

| 防护 | 做法 |
|---|---|
| schema 校验 | 严格模式 + 业务规则校验（Tool 03 篇契约） |
| 白名单参数 | URL/路径/ID 只接受白名单集 |
| 参数化执行 | 永不字符串拼接 SQL/Shell/路径（Tool 08 篇） |
| 危险值拦截 | 禁用 `rm -rf`、通配删除、批量外发 |
| 参数溯源 | 危险参数必须来自用户确认而非模型推断 |

> ⚠️ 2026 铁律：**工具参数是模型提供的不可信数据**——与外部用户输入同等待遇。校验失败不要"执行再说"，要返回结构化错误让模型自我修正（Tool 06 篇）。

## 6. 工具护栏的观测

| 指标 | 含义 |
|---|---|
| 拦截率 | 被拦调用占比（分原因：授权/参数/风险/序列） |
| 误拦率 | 良性调用被拦占比（须跟踪，护栏杀手） |
| 确认触发率 | 人工确认占比 |
| 逃逸率 | 应拦未拦（红队/样本审计） |
| 修复成功率 | 结构化回退后模型修正成功的比例 |

> 🎯 核心要点：工具护栏的绩效是**"防住 + 不误伤"双指标**——ToolSafe 的 65% 减少 + 10% 提升证明两者可兼得；只看拦截率会鼓励过度拦截，毁掉 Agent 可用性。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "输出检查够了" | 中间工具调用是独立风险面——动作层必须独立护栏 |
| "工具注册了就安全" | 注册是静态的；运行时参数/序列校验是动态的——两者都要 |
| "确认模式烦人" | 只对 DANGEROUS 级触发——校准范围，不砍机制 |
| "拦截=中断" | 分语义：静默拦/回退/确认/终止——按风险选 |
| "工具护栏只查参数" | 还要查工具选择、风险分级、调用序列模式 |
| "RL 护栏不成熟" | ToolSafe 实证 65% 减少——动作层决策器已是 2026 方向 |
| "护栏拦截后要重试" | 高危拦截要 tripwire 语义——不是重试，是停止 |
