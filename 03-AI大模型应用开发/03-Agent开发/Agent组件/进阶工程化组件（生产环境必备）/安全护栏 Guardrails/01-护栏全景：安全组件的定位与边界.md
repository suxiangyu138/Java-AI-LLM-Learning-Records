# 护栏全景：安全组件的定位与边界

> 护栏 = 运行时策略控制组件：检查提示词、检索上下文、模型输出与工具调用，在**不安全/不合规行为到达用户或下游系统前**拦截。2026 定位：护栏是确定性控件，用来约束概率系统——但它不是安全的全部，行为监控与最小权限同样不可或缺。本章立起全景与边界。

## 1. 护栏是什么：定义与职责

| 项 | 说明 |
|---|---|
| 定义 | 运行时策略控制层：在拦截点检查输入/输出/工具调用，阻断不安全行为 |
| 拦截对象 | 提示注入、越狱、PII 泄漏、毒性内容、幻觉、策略违规、格式不合规 |
| 与评测的区别 | 护栏是运行时拦截（在线）；评测是部署前衡量（离线）——两者互补不替代 |
| 本质 | **确定性控件**（规则/分类器/校验器）约束概率系统（LLM）的输出 |

> 🎯 核心要点：护栏的元问题——**"在哪个拦截点、用什么手段、拦住什么"**。回答不了这三个问题的护栏，要么漏防要么误伤。

## 2. 两个核心拦截点：Pre-LLM 与 Post-LLM

| 维度 | 输入护栏（Pre-LLM） | 输出护栏（Post-LLM） |
|---|---|---|
| 位置 | 模型调用前（用户输入+上下文入模型前） | 模型返回后（送达用户/下游前） |
| 典型职责 | PII 检测脱敏、敏感数据阻断、注入/越狱检测 | 幻觉检测、毒性过滤、格式合规、输出 PII |
| 延迟预算 | 热路径，须快——规则/正则/轻分类器（5-15ms） | 可用模型判断，成本刻意（按场景开） |
| 失败语义 | 拦截输入（拒绝/脱敏） | 拦截输出（refrain/fix/reask，03 篇） |

> ⚠️ 2026 最佳实践第一条：**预-LLM 护栏保持快速与确定性**——正则 PII 检测、规则注入筛查只加毫秒级延迟；避免在输入路径上用 LLM 判断（除非必须）。**后-LLM 护栏成本刻意**——幻觉/毒性模型判断每次请求都要花钱，按"该判断是否真的需要"来开。

## 3. 五 rail 分类：护栏的完整地图

| Rail | 拦截点 | 防什么 | 典型实现 |
|---|---|---|---|
| Input rail | 用户输入入模型前 | 注入、越狱、PII、违规话题 | 规则/轻分类器 |
| Dialog rail | 多轮对话流中 | 话题漂移、流程越界 | Colang 对话流（NeMo） |
| Retrieval rail | RAG 检索块注入上下文前 | 检索内容注入（间接注入） | 检索块筛查/源验证 |
| Execution rail | 工具/动作执行前 | 危险工具调用、参数违规 | tool call 校验（04 篇） |
| Output rail | 模型输出送达前 | 幻觉、毒性、PII、格式 | 校验器/分类器 |

> 🎯 核心要点：**Agent 的护栏必须多层**——单顶层检查太薄：Agent 检索上下文、调 API、跨 Agent 委派、跨轮记忆，攻击可在任何边界渗入。五 rail 是 NeMo Guardrails 提出的覆盖模型，2026 仍是标准地图。

## 4. 护栏 vs 相邻安全组件

| 组件 | 职责 | 与护栏关系 |
|---|---|---|
| 威胁框架（OWASP Top 10） | 识别威胁类别 | 护栏的"要防什么"清单（09 篇） |
| 加固清单 | 部署前查缺 | 护栏的"要装什么"清单 |
| 权限/身份 | 谁能做什么 | 护栏的硬边界（执行层） |
| 行为监控 | 检测动作序列异常 | 护栏的升级版——动态意图偏离检测 |
| 审计日志 | 事后追溯 | 护栏决策留痕的接收方 |
| 红队测试 | 部署前攻击演练 | 护栏的"测试集"来源 |

> 💡 一句话分工：**威胁框架告诉你敌人长什么样，护栏挡住已知攻击，行为监控抓未知攻击，权限限制破坏半径，审计留下证据**——五个组件是一个系统。

## 5. 2026 认知反转：护栏对自主 Agent 不够

| 传统假设 | Agent 现实 |
|---|---|
| 人类提示 → 模型响应 → 检查输入输出 | Agent 自提示、链式行动、跨轮记忆、跨 Agent 交互——安全相关行为发生在**提示与提示之间** |
| 内容检测能发现攻击 | 攻击"看起来合法"：隐藏指令藏进正常邮件，Agent 执行授权动作、改记忆、外泄数据——**无策略违规、无恶意提示、无违禁输出** |
| 静态控制管住复杂度 | 宽工具权限 + 记忆 + 多 Agent 交互的复杂度超出静态规则 |

> ⚠️ 2026 金句：**"Agent 的意图被劫持了，而攻击看起来完全合法"**（Radware）——这正是传统护栏失守的场景。护栏仍是必要的防线（挡住已知攻击），但必须升级：内容过滤 → 行为/意图安全（09 篇四支柱）。

## 6. 护栏的工程原则（2026）

| 原则 | 做法 |
|---|---|
| 校准而非最大化 | 不是每层都加满——高风险动作（不可逆）全栈防护，低风险高并发轻量并行检查 |
| 一等执行逻辑 | 护栏进 Agent 循环，不是事后附加——只偶尔运行/可被绕过的护栏是假信心 |
| 干预发遥测 | 每次触发记录：护栏名、拦截对象、决策路由、步骤位置；评估器按群组看失败率 |
| 构建期 + 运行时双轨 | 构建期：红队+CI 对抗性评测集；运行时：线上拦截——运行时是未知攻击面前唯一防线 |
| 护栏即反馈 | 比"拦/放"更强大：检测到问题 → 定向修正提示回喂模型 → 重检 → 通过或达重试上限（03 篇） |
| 失败语义明确 | 拦截时给策略安全的后备响应或脱敏片段，并记录决策 |

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "护栏越多越安全" | 每层加延迟、加误报——按动作风险校准，不是堆叠 |
| "输出检查一遍就够" | Agent 的中间工具调用是独立风险面——编码 Agent 可能因只查最终文本而调用破坏性工具 |
| "护栏=安全全部" | 护栏挡已知；行为监控抓未知；权限限破坏半径——缺一不可 |
| "输入检查用大模型最准" | 热路径 LLM 判断 = 延迟炸弹——规则/轻分类器优先 |
| "通用毒性过滤够用" | Perspective 之类挡不住礼貌式越狱（如温和地教撬锁步骤），还误伤敏感话题 |
| "工具不管你的策略" | 框架/分类器只执行公共分类法——退款规则、禁用话题要自己训 |
| "拦截=处理完成" | 拦截后要发遥测、留审计、可回放——否则无法改进 |

## 8. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 护栏是什么？ | 运行时策略控制层：在拦截点检查输入/输出/工具调用，阻断不安全行为 |
| 输入输出护栏区别？ | 预-LLM 拦截（快、确定、PII/注入）vs 后-LLM 校验（成本刻意、幻觉/毒性/格式） |
| 五 rail 是哪些？ | input/dialog/retrieval/execution/output |
| 为什么 Agent 要多层护栏？ | 单顶层太薄——检索/工具/记忆/多 Agent 都是渗入边界 |
| 护栏与评测关系？ | 护栏在线拦截、评测离线衡量——互补不替代 |
| 2026 护栏认知反转？ | 传统护栏对自主 Agent 不够——攻击发生在提示与提示之间 |
| 护栏工程第一原则？ | 校准而非最大化：按动作风险决定防护深度 |
| 输入护栏延迟预算？ | 5-15ms 级（轻分类器），避免 LLM 判断进热路径 |
| 护栏即反馈是什么？ | 检测→定向修正回喂→重检，把拦截变质量保障 |
| 护栏与行为监控分工？ | 护栏挡已知攻击，行为监控抓未知攻击 |
| 护栏失败语义？ | 拦截时给策略安全后备响应/脱敏片段 + 记录决策 |
| 护栏的本质？ | 确定性控件约束概率系统 |
