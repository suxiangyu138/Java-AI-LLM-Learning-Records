## 1. agent.stream：一行流式

```python
agent = create_agent(model=model, tools=tools, system_prompt="...")

for event in agent.stream(
    {"messages": [("user", "北京和上海天气对比")]},
    stream_mode="values",                      # ★ 每步完整状态
):
    last = event["messages"][-1]
    last.pretty_print()                        # 逐步打印每轮消息
```

| 与手写对照 | 手写（阶段 2 流式拼装） | agent.stream |
|-----------|----------------------|-------------|
| 事件内容 | 手动按 index 拼装 tool_calls | 框架输出每步完整消息 |
| 工具执行 | 手动 asyncio.gather | 框架内部自动 |
| 中间可见 | 手动打印 | 每轮事件天然可见 |
| 代码量 | ~50 行 | 3 行 |

> 🎯 **核心要点**：agent.stream 是"调试开关 + 用户体验"一体的——开发时看中间过程，生产时给用户逐字体验。**同一套代码，两种用途**。

## 2. stream_mode 全解

| stream_mode | 事件内容 | 用途 |
|------------|---------|------|
| `"values"` | 每步完整状态（含全部消息） | **推荐**：看每一步决策 |
| `"updates"` | 每步的节点更新 | 看节点粒度变化 |
| `"messages"` | 逐 token 流（LLM 输出流） | 逐字体验 |
| `"custom"` | 自定义事件 | 高级 |

```python
# 逐 token 体验（聊天界面用）：
for chunk in agent.stream(
    {"messages": [("user", "讲个笑话")]},
    stream_mode="messages",
):
    if chunk[0].content:
        print(chunk[0].content, end="", flush=True)
```

> 💡 **组合用法**：界面展示用 `"messages"`（逐字），调试分析用 `"values"`（看完整轨迹）——两个模式不冲突。

## 3. 流式中看工具决策

`"values"` 模式的核心价值：**每一步的 tool_calls 都可见**（等于阶段 2 手写的调试三板斧第 ③ 板斧——打印 finish_reason，框架给了全程轨迹）：

```python
for event in agent.stream({"messages": [("user", "北京和上海天气对比")]},
                          stream_mode="values"):
    last = event["messages"][-1]
    if getattr(last, "tool_calls", None):
        for tc in last.tool_calls:
            print(f"→ 调用工具: {tc['name']} 参数: {tc['args']}")
    elif last.content:
        print(f"→ 回答: {last.content}")
```

```text
→ 调用工具: get_weather 参数: {'city': '北京'}
→ 调用工具: get_weather 参数: {'city': '上海'}     ← 并行可见
→ 回答: 北京 22℃ 晴天，上海 25℃ 多云...
```

> ⚠️ **行为一致性的保障**：框架流式看到的事件 = 你手写循环的每轮状态——**阶段 2 的"按 id 配对"等纪律框架已内置**，你只需消费事件，不需要拼装。

## 5. 调试三板斧（框架版）

| 板斧 | 手写版（阶段 1/2） | 框架版 |
|------|------------------|--------|
| ① 看原始响应 | dump_response() | stream(values) 打印每步 |
| ② 看消息历史 | 打印 messages | pretty_print() |
| ③ 看终止逻辑 | 打印 finish_reason | 观察条件路由（无 tool_calls → END） |

**框架报错排查顺序**：

```text
① 报错在模型层？（供应商错误/参数）    → 看 trace 的第一段
② 报错在工具层？（执行失败）          → 工具异常已被框架转回传，查工具函数
③ 报错在循环层？（路由/上限）         → recursion_limit、条件边
④ 报错在状态层？（消息结构）          → 检查 state schema / reducer
```

## 6. 常见坑速查

| 坑 | 现象 | 修复 |
|----|------|------|
| 忘设 LANGCHAIN_TRACING_V2 | LangSmith 无数据 | 设置环境变量 |
| 误用 stream_mode="messages" 做调试 | 只见 token 不见决策 | 调试用 "values" |
| 自定义状态字段无 reducer | 覆盖而非累积 | 字段加 Annotated reducer |
| 生产开 verbose=True | 日志爆炸 | 用 stream 或 LangSmith 代替 |
| 流式事件顺序错乱 | 打印顺序异常 | 用 stream_mode="values" 看完整快照 |
| 框架异常堆栈深 | 看不懂报错 | 从最内层异常看起（供应商/工具层） |

> 🎯 **核心要点**：框架的可观测优势 = **事件流自带全程状态**。你手写时"打印 messages"的调试动作，在框架里是标准输出——调试心智不变，效率翻倍。
