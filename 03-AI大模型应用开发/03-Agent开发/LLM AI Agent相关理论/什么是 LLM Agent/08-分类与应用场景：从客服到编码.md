# 分类与应用场景：从客服到编码

> 理论篇：Agent 的**形态分类**（按自主程度/任务范围/结构）与**典型落地场景**（编码、客服、数据分析、安全响应），以及"什么任务适合做成 Agent"的选择方法。多 Agent 系统深潜见 [区分概念 07-Agent-vs-多智能体-vs-子Agent](../区分概念（面试容易混淆）/07-Agent-vs-多智能体-vs-子Agent.md)。

## 1. 分类维度

| 维度 | 分类 | 说明 |
|---|---|---|
| **自主程度** | 辅助型 / 半自主 / 全自主 | 人工介入频率从"每步确认"到"仅检查点"到"放手" |
| **任务范围** | 任务型（task-specific）/ 通用型 | 2026 主流是任务型——便宜、可靠、易调试 |
| **结构** | 单 Agent / 多 Agent | 复杂度与协调成本递增 |
| **驱动方式** | 回合制 / 目标驱动 / 定时 / 主动（Claude Code 四原语） | 见 03 篇 Loop 工程 |

> 🎯 2026 市场事实（Gartner）：**任务型 Agent 是 40% 预测的主角**——一个任务做精做透（客服工单、线索补充、代码审查），而不是万能通用 Agent。面试说分类先讲任务型 vs 通用型，再讲自主程度。

## 2. 典型分类详表

### 按自主程度

| 类型 | 人工介入 | 适用 | 例子 |
|---|---|---|---|
| 辅助型 | 每步确认 | 高影响操作 | 医疗建议、财务操作 |
| 半自主 | 检查点/审批门 | 常规业务 | 客服退款（超阈值需人工） |
| 全自主 | 仅目标下达与结果验收 | 低风险高反馈 | 代码修改、数据清洗 |

### 按结构（单 Agent vs 多 Agent）

| 模式 | 机制 | 代表 | 适用 |
|---|---|---|---|
| 单 Agent 循环 | 一个模型闭环干到底 | 多数客服/编码 Agent | 起步默认——**先用单 Agent，复杂度不够再升级** |
| Manager（主管） | 中央 Agent 委派子任务给专业子 Agent | OpenAI Agents SDK | 子任务边界清晰、可委派 |
| Orchestrator-workers（编排-工人） | 主 Agent 拆解分派 + 并行探索 + 综合 | Anthropic Claude Research | 多文件修改、多源搜索 |
| Handoff（交接） | 对等 Agent 按专长转移控制权 | 多角色客服流 | 专业分工明确 |

> 💡 社区共识：**多数生产系统从单 Agent 循环起步，只有复杂性需要时才升级多 Agent**（Anthropic 简单性原则）。面试答"什么时候上多 Agent"——"任务可分解为专业子任务、需要并行、且协调成本 < 收益时"。

## 3. 落地场景全景（2026 实证最强领域）

| 场景 | 为什么 Agent 行 | 代表形态 | 成功可衡量性 |
|---|---|---|---|
| **编码 Agent** | 测试可验证、迭代反馈闭环 | Claude Code / Cursor / Copilot 自主模式 | 高（测试通过=完成） |
| **客户支持** | 对话+工具操作、成功可按"解决工单"计量 | 客服 Agent（查单/改单/退款） | 高（可计费） |
| **数据分析/研究** | 多轮检索+计算+交叉验证 | 深度调研 Agent、报表 Agent | 中高（产出可审计） |
| **安全响应** | 实时扫描+自动处置（Gartner 官方举例） | 威胁响应 Agent | 中（误报需人工复核） |
| **企业 RPA 升级** | 规则 RPA 无法处理非结构化输入 | 流程 Agent（单据识别+录入） | 中高 |
| **个人效率** | 邮件、日程、会议整理 | 个人助理 Agent | 中 |

> 🎯 Anthropic 判断依据（面试背这条）：**最好的 Agent 场景具备三个特征——① 任务成功可衡量（测试/解决/验收）；② 有环境反馈可迭代；③ 失败代价可控（沙箱可测）**。编码与客服同时满足三者，所以最先成熟。

## 4. 场景选择方法：什么任务适合做成 Agent

| 问题 | 答案 = 适合 | 答案 = 不适合 |
|---|---|---|
| 步骤可预写吗？ | 不可预写（开放问题） | 可预写 → Workflow |
| 有环境反馈吗？ | 有（工具返回/执行结果） | 无 → 单次生成 |
| 成功可衡量吗？ | 可（测试/解决/验收） | 不可 → 人工完成 |
| 失败代价可控吗？ | 可控（沙箱/可回滚/可人工介入） | 不可 → 人工在环 |
| 延迟/成本敏感吗？ | 不敏感（可接受循环多轮） | 敏感 → 直接调用 |

> ⚠️ 决策金句（Anthropic）：**"Agentic systems often trade latency and cost for better task performance"**——Agent 是用延迟和成本换任务质量；换不来（不可衡量）或换不起（成本爆炸）就不该上 Agent。

## 6. 面试速记

| 问题 | 一句话答案 |
|---|---|
| Agent 怎么分类？ | 自主程度（辅助/半自主/全自主）× 任务范围（任务型/通用）× 结构（单/多） |
| 2026 主流是哪类？ | 任务型 Agent（Gartner 40% 预测的主角）——便宜、可靠、易调试 |
| 单/多 Agent 怎么选？ | 先单 Agent 起步，可分解+需并行+协调成本 < 收益才上多 |
| 多 Agent 三种模式？ | Manager（主管委派）/ Orchestrator-workers（拆解分派并行）/ Handoff（按专长交接） |
| 最佳 Agent 场景三特征？ | 成功可衡量 + 环境反馈可迭代 + 失败代价可控 |
| 最先成熟的场景？ | 编码（测试可验证）与客服（成功可计量） |
| 什么任务不适合 Agent？ | 步骤可预写→Workflow；无反馈；不可衡量；失败代价不可控；延迟敏感 |
| Agent 的代价？ | 以延迟和成本换任务性能（Anthropic） |
