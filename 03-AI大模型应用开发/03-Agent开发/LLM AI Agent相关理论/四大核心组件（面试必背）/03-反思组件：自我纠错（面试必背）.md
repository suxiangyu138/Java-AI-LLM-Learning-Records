# 反思组件：自我纠错（面试必背）

> 背诵篇：四大核心组件之「反思组件」——30 秒背诵卡 + 4 个面试高频题 + oracle 前提与成本纪律。深化见 [Agent 四大核心组件 04 篇](..%2F..%2FAgent%20四大核心组件%2F04-反思组件：自我评估与纠错.md)，速记见 [Planning & Reflection 最简定义](..%2F..%2FAgent组件%2F四大基础核心组件（最简定义）%2FPlanning%20%26%20Reflection%20规划反思组件%2F00-PlanningReflection规划反思组件最简定义总览.md)。

## 1. 30 秒背诵卡

| 概念 | 背诵版一句话 |
|---|---|
| 反思组件 | 对已产生的结果做批判性评估 → 生成改进指令 → 重新生成——Agent 的"质检员" |
| 循环结构 | 生成（generate）→ 批评（critique）→ 改进（refine），可迭代多轮 |
| 独立批评者 | 批评必须独立（独立 prompt 或独立模型）——否则自我确认偏差 |
| 迭代上限 | 显式轮次限制（反思会放大成本——每轮一次完整调用） |
| oracle 前提 | Reflexion 依赖外部信号（测试/验证器）才能有效——无 oracle 反思易空转 |
| 三大出口 | 继续 / 重试 / 重规划（与规划组件联动） |
| 2026 升级 | 前瞻反思（PreFlect：执行前批判计划）优于事后纠错 |
| 适用判断 | 高价值任务才值——反思成本高，低价值任务直接重试更划算 |

## 2. 面试高频问题（背诵版）

**Q1. 反思组件是什么？和"重试"有什么区别？**
> 答：反思是**结构化自我批评循环**——生成 → 批判性评估 → 改进指令 → 再生成；重试只是原样再来一次。区别：重试不带改进（错因未消除，可能重复犯错）；反思要"找到错因、给出修正"，所以能消除系统性错误（Reflexion 在 HumanEval 达 91%）。但注意：**反思失败 = 重试**（如果批评意见没有产生信息量），所以反思必须有评估依据。

**Q2. 反思为什么需要"独立批评者"？**
> 答：**自我确认偏差**——让同一个模型既生成又批评自己，批评意见往往只是"换个说法同意自己"。解法：① 独立 prompt（不同的批评视角）；② 独立模型（如生成用强模型、批评用另一个模型/评审角色）；③ 外部 oracle（测试用例、验证器、人工评审）——**oracle 是反思有效的关键前提**（Reflexion 范式在可验证任务上才显著有效；纯开放任务反思易空转）。2026 实证：AgentDebug 用分层错误分类（记忆/反思/规划/行动/系统五层）给定向反馈，任务成功率相对提升最高 26%。

**Q3. 反思的成本怎么控制？**
> 答：三个纪律——① **迭代上限**：反思每轮一次完整 LLM 调用，必须显式设轮数上限（社区经验 2-3 轮后收益锐减）；② **价值过滤**：反思适合"高价值、有 oracle、错误代价高"的任务；低价值任务直接重试或一次性完成更划算；③ **错误分类定向**：先判断错在哪层（记忆/规划/行动/系统），只反思对应层——全量反思浪费 token。实证反面：Reflexion 每轮一次调用，无 oracle 的开放任务上可能空转烧钱。

**Q4. 反思组件 2026 有什么新趋势？**
> 答：**从事后纠错转向执行前前瞻（prospective）**——PreFlect 批判的是"计划本身"而非"执行结果"：从历史轨迹提炼成败模式，在执行前拦截坏计划；Devil's Advocate 预演批判减少 45% 计划返工与试错；MIRROR 做执行前多视角内省。同时重规划机制增强（执行中遇到意外偏离时动态更新计划）。面试表述：**"2026 反思研究的主线是从'recover after failure'走向'prevent before execution'"**。

## 3. 避坑与易混点

| 坑 | 澄清 |
|---|---|
| "反思 = 让模型再想想" | 反思必须有批评-改进结构 + 独立批评者，否则是重试 |
| "反思越多越好" | 迭代上限必须显式设——反思每轮一次完整调用，成本放大 |
| "反思不需要验证" | oracle 前提——无可验证信号时反思易自我确认空转 |
| "反思只处理执行错误" | 反思可指向计划（重规划出口）、执行（重试出口）、答案（改进出口） |
| 反思 vs 重试 vs 重规划 | 反思是评估机制，重试/重规划是它的三个执行出口 |
