# Agent in RAG：检索流程智能化

> 理论篇：**不引入完整 Agent 循环，把"判断力"拆进 RAG 流水线的关键决策点**——路由分类器（Adaptive RAG）、查询改写、检索器选择（learned policy）、纠正与反思。与 05 篇分工：05 讲"检索进 Agent"（完整循环），本篇讲"Agent 判断进 RAG"（流水线内决策）。

## 1. 理论定位：智能化的六决策点

```text
智能 RAG 流水线（决策点标注 ⚙）：
  查询 ⚙路由分类器 → ⚙查询改写 → ⚙检索器选择 → 检索 → ⚙相关性评估
    → 通过 → ⚙faithfulness 校验 → 生成
    → 不通过 → ⚙纠正（改写重检/换源）→ 回到检索
```

| 决策点 | 传统 RAG | 智能化 RAG | 理论依据 |
|---|---|---|---|
| ① 路由 | 一律深度处理 | **分类器分流**（简单→快速路径，复杂→agentic 路径） | 简单查询不值得循环成本 |
| ② 改写 | 原文检索 | 改写/拆解/多路查询 | 用户查询≠检索友好表达 |
| ③ 检索器 | 固定配置 | **按查询选**（BM25/稠密/混合/图 + top-k + 重排深度） | 检索策略因查询而异（learned policy） |
| ④ 评估 | 无 | 相关性判断 | 检索结果质量可度量 |
| ⑤ 纠正 | 硬用 | CRAG 式纠正 | 差结果必须处理，不能进上下文 |
| ⑥ 校验 | 无 | faithfulness 检查 | 生成必须 grounded（Self-RAG） |

> 🎯 核心要点（背诵版）：**"Agent in RAG"= 在不付完整 Agent 循环成本的前提下，把 6 个决策点逐个智能化**——每个决策点省的是"不该花的检索"或"不该用的垃圾上下文"；决策点越多，越接近 Agentic RAG，成本越高。这是"融合谱"的中间段。

## 2. 路由分类器：Adaptive RAG 理论

| 维度 | 内容 |
|---|---|
| 机制 | 查询进入时由轻量分类器判断复杂度 → 路由到不同路径 |
| 三条路径 | 简单（直接生成，不检索）/ 中等（单次检索）/ 复杂（agentic 多轮） |
| 理论依据 | **按复杂度分配推理与检索资源**（与 LLM 大脑的"按难度路由 thinking"同构） |
| 实证 | 混合复杂度生产负载中，分类器路由是 2026 推荐基线 |
| 分类器实现 | 轻量模型分类 or 零成本规则分类器（正则/关键词映射） |

> 💡 理论洞察：**路由分类器是"决策化"的最小单元**——它把"检不检"这个 Agent 决策降级为一次便宜的分类调用。70% 简单查询走快速路径的场景下，整体成本可省 50-60%（与客服场景 70/25/5 分流同一原理）。

## 3. 检索器选择：检索策略作为 learned policy

| 概念 | 内容 |
|---|---|
| 传统 | 全查询用同一个检索器配置（固定 BM25 或固定向量） |
| learned policy（2026 趋势） | Agent/策略按查询选择：检索器类型（BM25/稠密/混合/图）、top-k、重排器深度、切片大小 |
| 实证收益 | 早期系统检索质量提升 **15-20%**（vs 静态配置） |
| 失败模式 | **工具误路由**——语义查询选了 BM25（词面不匹配） |
| 度量 | ToolSelectionAccuracy（工具选择准确率）——检索器选择也是"工具选择" |

> ⚠️ 与图检索的交汇：2026 检索架构调查（Computer Science Review 2026，300+ 引用）把 RAG 建模为 **Index-Retrieve-Fuse-Generate** 四阶段设计空间——向量/图/混合/多模态都在同一框架下选型；**关系型查询（多实体关联）选图索引，语义查询选向量**，这就是"怎么检"决策的理论内容。

## 4. 查询改写理论：为什么用户查询不能直接检

| 问题 | 机制 | 例子 |
|---|---|---|
| 指代消解 | "它的预算"→ 明确实体 | "查该项目预算，对比它去年数据" |
| 口语化→检索友好 | 疑问句→关键词/短语组合 | "你们有没有那种能自动扩容的数据库"→"自动扩容 数据库 能力" |
| 多路查询 | 一个查询拆多路并行检索再融合 | "优缺点对比"→ 优点查询 + 缺点查询 |
| 子问题分解 | 复合问题拆成原子子问题 | "A 和 B 的成本与性能"→ 4 个子查询 |

> 🎯 理论结论：**改写是"检索语言"与"用户语言"之间的翻译层**——检索器是词面/语义匹配器，不是意图理解器；不翻译就检索 = 把翻译成本转嫁给召回失败。工程实现（HyDE/多路查询/子问题分解）见 [RAG 体系 14-查询优化](..%2F..%2F..%2F04-RAG检索增强生成%2F14-查询优化-改写与多路查询.md)。

## 5. 纠正与反思：流水线内的"小循环"

| 机制 | 在流水线的位置 | 与 05 篇的区别 |
|---|---|---|
| CRAG 式纠正 | 检索后、生成前 | 单次纠正，不进完整循环 |
| Self-RAG 反思标记 | 生成中 | 生成器自查（检索需求/相关/忠实） |
| 重排+上下文压缩 | 检索后 | 固定机制（不是决策） |
| 完整 Agent 循环 | 全局 | 05 篇——多个检索-评估回合 |

> 💡 选型口诀：**"一次纠正能解决 = 用 CRAG 式小循环；要'边查边想边改' = 上完整 Agentic RAG"**——错误少、可单次纠正的负载用流水线内决策，错误多、需迭代的负载用完整循环。

## 6. 面试速记

| 问题 | 一句话答案 |
|---|---|
| Agent in RAG 是什么？ | 把判断力拆进流水线六决策点（路由/改写/选检索器/评估/纠正/校验） |
| Adaptive RAG？ | 分类器按复杂度路由：简单不检/中等单检/复杂 agentic |
| learned policy？ | 按查询选检索器+top-k+重排深度——检索质量 +15-20% |
| 查询改写为什么必要？ | 用户语言≠检索语言——翻译层缺失 = 召回失败 |
| 与 Agentic RAG 区别？ | 流水线内单次决策 vs 完整检索-评估循环——按错误率选 |
| 检索器选型理论？ | Index-Retrieve-Fuse-Generate 四阶段框架——关系查询选图、语义选向量 |
