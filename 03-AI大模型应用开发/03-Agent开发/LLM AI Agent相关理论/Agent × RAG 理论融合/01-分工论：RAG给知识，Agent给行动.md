# 分工论：RAG 给知识，Agent 给行动

> 理论篇：Agent × RAG 融合的地基——**两个正交能力维度**（知识轴 × 行动轴）、四象限定位、为什么"RAG+Agent"不是叠加而是分工。面试"RAG 和 Agent 是什么关系"的理论答案。

## 1. 核心分工：知识 vs 行动

| 能力 | 回答的问题 | 解决什么 | 实现 |
|---|---|---|---|
| **知识（RAG）** | "我知道什么" | 事实性、时效性、私有数据、幻觉 | 检索增强（向量/图/混合检索） |
| **行动（Agent）** | "我能做什么" | 多步任务、工具调用、目标达成 | 推理循环 + 工具 + 反馈 |

> 🎯 核心要点（背诵版）：**RAG 回答"知道什么"，Agent 回答"做什么"——两者是正交维度，不是同一条能力线上的高低档。** "RAG 比 Agent 弱"是常见误区：它们解决的是不同问题（知识问题 vs 行动问题），大多数真实任务同时需要两者。

## 2. 四象限：任务定位图（理论框架）

```text
行动轴（Agent 强）
  ▲
  │  II 工具型 Agent           IV Agentic RAG（融合主形态）
  │    低知识需求               高知识需求
  │    多步行动（计算/API/编排）  多步行动 + 事实支撑（调研/客服/编码）
  │
  ─┼───────────────────────────► 知识轴（RAG 强）
  │
  │  I 直接生成                III 纯 RAG 问答
  │    低知识低行动              高知识低行动
  │    闲聊/简单创作             知识库问答/文档检索
  ▼
```

| 象限 | 任务特征 | 架构 | 例子 |
|---|---|---|---|
| I 直接生成 | 不需要外部知识、不需要行动 | 单次 LLM 调用 | 闲聊、改写、摘要 |
| II 工具型 Agent | 需要行动、知识可内建 | Agent（无检索） | 计算器、代码生成、流程编排 |
| III 纯 RAG 问答 | 需要知识、一次问答足够 | RAG 流水线 | 知识库 FAQ、文档问答 |
| **IV 融合** | **既需要知识又需要行动** | **Agentic RAG** | 客服（查单+知识库+改单）、调研（多源检索+综合） |

> 💡 面试用法：被问"什么时候用 RAG，什么时候用 Agent"——先答"它们是正交的，看任务落在哪个象限"；大多数企业任务落在 **IV 融合象限**（既要查知识库又要走流程），这就是 2026 企业 Agent 大多内置 RAG 的原因。

## 3. 为什么不能互相替代

| 误解 | 澄清 |
|---|---|
| "有了 Agent 还要 RAG 干什么" | Agent 解决不了知识问题——幻觉、知识截止、私有数据仍然存在 |
| "有了 RAG 还要 Agent 干什么" | RAG 解决不了行动问题——多跳检索、动态决策、工具调用仍需循环 |
| "检索也是一种行动，Agent 天然包含 RAG" | Agent 需要**检索基础设施**（索引/检索/重排）——RAG 是知识供给端，Agent 是决策端，二者是供应链关系 |
| "长上下文可以取代两者" | 全量塞入 vs 按需检索 + 动态决策——长上下文解决"带多少"不解决"做什么"（见 [区分概念 08](..%2F区分概念（面试容易混淆）%2F08-RAG-vs-微调-vs-长上下文-vs-Agent.md)） |

## 4. 融合的本质：检索从"流水线一步"变"一次决策"

| 阶段 | RAG 的检索 | Agent 的检索（Agentic RAG） |
|---|---|---|
| 触发 | 强制（每次请求都检索） | 决策（Agent 判断要不要检） |
| 查询 | 原始问题直接检 | 改写/拆解/多路查询 |
| 次数 | 一次 | 可多轮迭代（查 A 用结果查 B） |
| 评价 | 不评价（拿来就用） | 评估相关性（够不够/准不准） |
| 失败处理 | 硬用（污染生成） | 重检索/换源/放弃（CRAG 纠正） |

> 🎯 理论一句话：**融合 = 把检索从"流水线的固定步骤"重铸为"Agent 决策空间里的一个可调用工具"**——检索获得"判断力"（何时检、检什么、检几次、够不够），Agent 获得"知识供给"（事实、时效、私有数据）。

## 5. 融合的理论前提：各取其长

| RAG 的长处（Agent 缺的） | Agent 的长处（RAG 缺的） |
|---|---|
| 事实准确（grounded，可溯源） | 多步推理（goal-directed） |
| 知识更新（改索引即可） | 动态决策（根据反馈调整） |
| 私有数据访问（企业文档） | 工具调用（查系统、改状态） |
| 低成本（单次流水线） | 复杂任务完成（端到端交付） |

> ⚠️ 2026 反模式（面试避坑题）：① 简单 Q&A 上 Agent（零收益加成本延迟）；② 需要多跳推理的问答用纯 RAG（单次检索 50-60% 上限硬卡住）；③ 知识密集任务裸 Agent 不接 RAG（幻觉输出自信错误）；④ 未验证简单方案先上融合架构（复杂度的唯一理由是实证改进）。

## 6. 面试速记

| 问题 | 一句话答案 |
|---|---|
| RAG 和 Agent 的分工？ | RAG 回答"知道什么"，Agent 回答"做什么"——正交维度 |
| 四象限？ | 直接生成/工具型 Agent/纯 RAG/Agentic RAG（融合主形态） |
| 为什么不能互相替代？ | 知识问题与行动问题是两类问题——Agent 要知识供给，RAG 要决策驱动 |
| 融合的本质？ | 检索从流水线固定步骤变成 Agent 决策空间里的可调用工具 |
| 反模式？ | 简单 Q&A 上 Agent / 多跳问答用纯 RAG / 知识任务裸 Agent |
