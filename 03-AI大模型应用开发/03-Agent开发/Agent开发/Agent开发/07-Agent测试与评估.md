## 1. Agent 测试的范式差异

### 1.1 传统测试 vs Agent 评估

| 维度 | 传统软件测试 | Agent 评估 |
|------|-------------|-----------|
| 输出 | 确定性（断言） | **概率性（评分）** |
| 用例 | 输入 → 期望输出 | 任务 → 成功标准 |
| 失败 | 可复现 | **不可复现** |
| 覆盖 | 代码路径 | 行为空间 |
| 判定 | 通过/失败 | **评分 + 阈值** |

> ⚠️ **核心困境**：同一任务两次运行可能走不同路径、得不同结果——Agent 测试的本质是**统计性质量评估**。

### 1.2 Agent 特有的评估难点

```text
三大难点
├── ① 轨迹多样：合法完成路径无穷多
├── ② 副作用：工具调用有真实影响
├── ③ 环境依赖：外部服务状态影响结果
→ 对策：结果质量 + 行为轨迹双维度评估
```

## 2. 五维评估指标体系

| 维度 | 指标 | 测量方式 | 权重参考 |
|------|------|---------|:---:|
| **正确性** | 任务完成率 | 评估集自动跑分 | 40% |
| **工具使用** | 工具调用准确率 | 调用比对 | 20% |
| **轨迹质量** | 轨迹对齐度 | 路径编辑距离 | 15% |
| **性能** | 端到端延迟（P95/P99） | 埋点 | 10% |
| **可靠性** | 幻觉率 | RAGAS / FactScore | 15% |

### 2.1 各指标详解

**正确性（任务完成率）**

```text
完成判定三要素
├── 结果正确：最终输出与预期一致（可自动比对）
├── 过程正确：使用了正确的工具与参数
├── 无幻觉：没有编造事实/数据
→ 判定方式：自动化断言 + 验证器评分
```

**工具调用准确率**

```text
评估内容
├── 调用了正确的工具（该用 query_order 没用 query_payment）
├── 参数正确（order_id 传递无误）
├── 未调用多余工具（无意义调用）
└── 调用频次合理（无重复/浪费）
```

**端到端延迟**

```text
性能指标
├── P50：典型任务耗时
├── P95：大多数用户感知
├── P99：长尾（异常/重试场景）
└── 基准参考：简单任务 <5s，复杂任务 <60s
```

## 3. 评估集设计

### 3.1 评估集组成

```text
评估集五类用例
├── ① 主流程用例（40%）：典型任务（覆盖核心能力）
├── ② 边界用例（20%）：空输入/超长/极端值
├── ③ 失败场景（20%）：工具报错/超时/模型拒绝
├── ④ 安全用例（10%）：注入/越权/敏感信息
└── ⑤ 回归用例（10%）：历史 bug 复测
```

### 3.2 评估用例格式

```json
{
  "task": "查询订单 ORD-1001 状态并通知客户",
  "setup": {"db_state": "fixture-orders", "tools": ["query_order", "send_email"]},
  "success_criteria": {
    "result_correct": true,
    "tools_used": ["query_order", "send_email"],
    "no_unneeded_tools": true,
    "no_fabrication": true
  },
  "difficulty": "medium",
  "category": "main_flow"
}
```

> 🎯 **评估集铁律**：**先建评估集，再开发 Agent**——没有成功标准就开发，等于没有靶心射箭。50 个代表性用例起步。

## 4. 轨迹对齐度：核心硬指标

### 4.1 定义

**轨迹对齐度（Trajectory Alignment）**：计算 Agent 实际执行路径与**最优路径**的编辑距离——衡量「过程正确性」，防止「结果碰巧对了、过程一团糟」：

```text
轨迹比对示例
├── 最优路径：查询订单 → 查询支付 → 通知客户（3 步）
├── Agent 路径 A：查询订单 → 查询支付 → 通知客户（3 步）✅ 完全对齐
├── Agent 路径 B：查询订单 → 查询所有订单 → 查询支付 → 通知客户（4 步）⚠️ 1 步偏差
└── Agent 路径 C：查询订单 → 编造状态 → 通知客户（3 步）❌ 幻觉（结果可能是错的）
```

### 4.2 实现方式

```text
轨迹对齐实现
├── 定义最优路径：人工标注/专家示例/逐步规划
├── 计算距离：编辑距离（增加/删除/替换工具调用）
├── 归一化：距离 / 最优路径长度 → 对齐度分数
└── 阈值：>0.8 优秀 / 0.6-0.8 可接受 / <0.6 需优化
```

> 💡 **为什么重要**：任务完成率只看「结果」，轨迹对齐度看「过程」——**过程错了，结果可能碰巧对，但系统不可靠**。

## 5. 因果链追踪

### 5.1 为什么需要

> ⚠️ 生产环境仅靠日志排查 Agent 故障极其低效——多 Agent 系统中一个失败可能由 10 步之前的某个决策引发，普通日志无法关联。

### 5.2 因果链追踪（Causal Trace）

```text
因果链追踪
┌──────────────────────────────────────────────┐
│ trace_id: trace-abc123                        │
│ ① 用户请求 "处理退款"                          │
│ ② Router Agent 决策 → 分发 Refund Agent       │
│ ③ Refund Agent 调用 check_balance（超时 2s）  │
│ ④ Refund Agent 调用 refund（失败：余额不足）   │
│ ⑤ Evaluator 判定失败 → 回溯到 ③ 超时根因      │
└──────────────────────────────────────────────┘
→ 通过 trace_id 查看决策全链路
→ 定位：是「工具调用超时」还是「模型幻觉」导致失败
```

### 5.3 埋点要求

```text
埋点三要素（每次模型调用/工具调用/状态转换）
├── trace_id：贯穿全链路的唯一标识
├── span：单次调用（含输入摘要/输出摘要/耗时/状态）
├── parent_span_id：父调用关联（因果链）
→ 落库：可查询、可回放、可聚合
```

> 🎯 **2026 金句**：胜出的团队不是提示词最好的团队，而是**遥测最好的团队**——先埋点再优化。

## 6. LLM-as-Judge 的陷阱

### 6.1 三大陷阱

| 陷阱 | 表现 | 对策 |
|------|------|------|
| **自评偏差** | Agent 评估自己 → 必然放水 | **验证器独立进程**（全新上下文 + 只读） |
| **位置偏差** | 偏好先出现的答案 | 双盲评估（打乱顺序） |
| **风格掩盖** | 流畅但错误的答案得分高 | 规则优先于风格（硬断言先行） |

### 6.2 验证器独立进程

```text
正确设计
┌─────────────┐       ┌─────────────────┐
│ 生成器（Agent）│       │ 验证器（独立）      │
│ 完整工具权限   │ 输出 →  │ 全新上下文窗口      │
│ 会找"理由"    │       │ 只读权限          │
└─────────────┘       │ 按计划与策略规则评分  │
                      └─────────────────┘
价值：
├── 排除自评放水（验证器看不到 Agent 的"借口"）
├── 规则纯净（只有计划 + 策略，不被任务污染）
└── 权限隔离（验证器被攻陷也无破坏力）
```

## 7. 评估流水线

### 7.1 三层评估金字塔

```text
        ▲ 端到端评估（少量、重）
       / \     影子模式：生产环境抽样验证
      /   \
    / 场景评估 \
  /___________\
 / 单元评估（大量、轻）\
/_____________________\
├── 单元评估：单步决策/单工具调用（200+ 用例）
├── 场景评估：完整任务（50 用例）
└── 端到端评估：真实生产影子运行（抽样）
```

### 7.2 CI 集成

```yaml
# eval-pipeline.yml
on: [push, pull_request]
jobs:
  eval:
    steps:
      - name: 单元评估
        run: eval-run --level unit --suite core
      - name: 场景评估
        run: eval-run --level scenario
      - name: 安全评估（注入用例）
        run: eval-run --level security
      - name: 质量门禁
        run: check-gate --min-score 85
```

### 7.3 评估驱动开发（Eval-Driven Development）

```text
评估驱动开发流程
├── ① 定义成功标准（50 用例）→ ② 跑基线（当前得分）
├── ③ 开发功能 → ④ 跑评估 → ⑤ 得分对比
├── 改进：得分上升 = 有效改进；下降 = 回滚
└── 迭代：持续扩充评估集（每次 bug 都转成评估用例）
→ 核心：让 Agent 改进「有据可依」，而不是凭感觉
```

---

## 8. 核心要点

> 🎯 **核心要点**：
> 1. Agent 评估是统计性质量评估：五维指标（完成率/工具准确率/轨迹对齐/延迟/幻觉率）
> 2. 轨迹对齐度是关键硬指标：防止「结果碰巧对、过程一团糟」
> 3. 因果链追踪（trace_id + span + parent）：多 Agent 排障的基础设施
> 4. LLM-as-Judge 三大陷阱（自评/位置/风格）→ 验证器独立进程；评估驱动开发让改进有据可依
