## 1. 多 Agent 的核心价值

### 1.1 为什么需要多 Agent

| 单 Agent 的瓶颈 | 多 Agent 的解法 |
|----------------|----------------|
| 上下文容量有限 | 分工承载各自上下文 |
| 角色冲突（写+审同体） | 专业 Agent 各自专注 |
| 串行执行慢 | **并行执行** |
| 无多视角验证 | 投票/联合决策降低幻觉 |
| 长任务漂移 | 分层治理（监督者纠偏） |

### 1.2 收益数据

| 指标 | 单 Agent | 多 Agent（Planner） |
|------|:---:|:---:|
| 代码审查耗时 | 8 分钟 | **2.5 分钟** |
| 误判率 | 15% | **4%** |
| 任务恢复粒度 | 从头重来 | **从失败步重做** |

> ⚠️ **成本的另一面**：多 Agent 系统同任务 token 消耗约为单 Agent 对话的 **15 倍**——收益必须大于成本，否则是负优化。**先证明单 Agent 不够，再上多 Agent**。

## 2. 协作模式全景

| 模式 | 结构 | 适用场景 | 复杂度 |
|------|------|---------|:---:|
| **职能分工** | 路由 Agent → 专业子 Agent | 意图分流（客服/多域） | ⭐⭐ |
| **Planner 模式** | Planner 拆解 → Worker 执行 → Evaluator 汇总 | 长任务/可中断可恢复 | ⭐⭐⭐ |
| **Supervisor-Worker** | 监督者调度 + Worker 自治循环 | 企业级流程/防漂移 | ⭐⭐⭐⭐ |
| **去中心化共识** | 消息总线 + 优先级投票 | 无单点故障/多 Agent 协商 | ⭐⭐⭐⭐⭐ |

### 2.1 职能分工模式

```text
职能分工：路由 + 专业分工
┌─────────────┐
│  路由 Agent   │ ← 分析意图，分发给专业子 Agent
└──┬───┬───┬──┘
   │   │   │
   ▼   ▼   ▼
 客服  技术  售后
 Agent Agent Agent
 各自：不同 Prompt + 工具集 + 知识库
扩展：多个 Agent 投票/联合决策降低幻觉
```

**适用**：意图域清晰可分、各域工具差异大（客服 vs 技术 vs 售后）。

## 3. Planner 模式详解

### 3.1 结构

```text
Planner 模式三角色
┌─────────────┐
│ Planner Agent│ ← 拆解大任务为子步骤（计划）
└──────┬──────┘
       │ 分派子任务
       ▼
┌─────────────┐   执行  ┌─────────────┐
│ Worker Agent │ ←─────→ │ 各子任务      │
│ (执行器)      │   结果  │ (步骤 1..n)   │
└──────┬──────┘         └─────────────┘
       │ 汇总结果
       ▼
┌─────────────┐
│ Evaluator    │ ← 验收汇总（或回退重做）
└─────────────┘
```

### 3.2 核心优势：可中断、可恢复

```text
Planner 模式 vs 单 Agent 的失败恢复
├── 单 Agent：第 4 步失败 → 整个任务从头再来
└── Planner：第 4 步失败 → 只需重做第 4 步
    ├── Worker 状态独立
    ├── 已完成步骤结果保留
    └── Evaluator 只验收失败步骤
→ 长任务场景效率差异巨大
```

### 3.3 实现要点

```text
Planner 实现清单
├── 计划格式：结构化（JSON：步骤 + 依赖 + 验收标准）
├── 步骤粒度：每步可独立验证（2-4 小时工作量）
├── 依赖管理：步骤间的输入输出契约
├── 失败处理：失败步重试 → 重规划 → 人工介入
└── 预算控制：每步 token 预算 + 总预算
```

## 4. Supervisor-Worker 分层

### 4.1 结构

```text
Supervisor-Worker 分层
┌──────────────────────┐
│ Supervisor（监督者）    │
│ ├── 任务分解与路由      │
│ ├── 进度监控与纠偏      │
│ └── 结果验收与汇总      │
└─────────┬────────────┘
          │ 子任务 + 上下文
          ▼
┌──────────────────────┐
│ Worker（执行者）       │
│ └── 自己的 ReAct 循环   │ ← 自治执行，故障局部化
└──────────────────────┘
```

### 4.2 与 Planner 的区别

| 维度 | Planner 模式 | Supervisor-Worker |
|------|-------------|------------------|
| 核心 | 计划驱动 | **层级治理** |
| Worker 自治度 | 低（按计划执行） | **高（独立 ReAct 循环）** |
| 防漂移 | 计划约束 | **监督者实时纠偏** |
| 故障影响 | 单步重做 | **故障局部化** |
| 适用 | 结构化流程 | 长周期自主任务 |

> 🎯 **选择**：流程已知（选 Planner，计划强约束）；流程探索性高（选 Supervisor-Worker，自治 + 监督）。

## 5. 去中心化共识机制

### 5.1 为什么去中心化

> ⚠️ 中心化调度器（Planner/Supervisor）有**单点故障**风险——调度器挂了，全部 Agent 停摆。2026 年实践引入去中心化共识：

### 5.2 消息总线 + 优先级投票

```text
去中心化共识流程
┌──────────┐ 提案  ┌──────────┐
│ Agent A   │ ────→ │          │
└──────────┘        │ 消息总线   │ ← 各 Agent 发布带优先级的提案
┌──────────┐ 提案  │          │
│ Agent B   │ ────→ │          │
└──────────┘        └────┬─────┘
                         │ 投票
                         ▼
                ┌──────────────────┐
                │ 最高优先级提案获胜   │
                │ 其余 Agent → YIELD │
                │ (配合模式)         │
                └──────────────────┘
```

| 要素 | 说明 |
|------|------|
| **提案（Proposal）** | 带优先级的行动建议 |
| **投票（Vote）** | 按规则选出最高优先级提案 |
| **YIELD（配合）** | 落选 Agent 转为支持执行 |

### 5.3 实现方式

```text
去中心化共识的工程实现
├── LangGraph 中构建：
│   感知 → 提案 → 协商 → 执行 决策图
├── 消息总线：Redis Pub/Sub / 消息队列
├── 冲突仲裁：优先级规则 + 超时机制
└── 可验证性：所有提案/投票留痕（审计）
```

> 💡 **价值**：去中心化消除单点故障 + 支持异构 Agent（不同模型/厂商）协作。

## 6. 通信协议设计

### 6.1 通信层选择

| 方案 | 特点 | 适用 |
|------|------|------|
| **进程内调用** | 快、简单 | 同进程子 Agent |
| **消息队列** | 异步、可靠、可重试 | 跨服务 Agent |
| **MCP 多 Agent 支持**（v2.0） | 标准化、认证、权限 | 异构 Agent 生态 |
| **HTTP/gRPC** | 通用、跨语言 | 服务化 Agent |

### 6.2 消息契约设计

```json
{
  "message_id": "msg-20260803-001",
  "from": "planner",
  "to": "worker-3",
  "type": "task_assign",
  "payload": {
    "task_id": "T-0042",
    "description": "生成客户列表 API",
    "inputs": {"schema": "customer-schema-v3"},
    "acceptance": "单元测试通过 + 文档齐全",
    "budget": {"tokens": 50000, "timeout": 1800}
  },
  "trace_id": "trace-abc123"
}
```

| 契约字段 | 作用 |
|---------|------|
| trace_id | 因果链追踪（跨 Agent 全链路） |
| acceptance | 验收标准（让 Worker 知道「完成」的定义） |
| budget | 预算约束（token/时间） |
| inputs | 输入契约（依赖前置产物） |

## 7. 多 Agent 开发注意事项

### 7.1 五大坑与对策

| # | 坑 | 对策 |
|---|-----|------|
| 1 | **握手循环**（Agent 互相交接不干活） | 每个任务明确所有者 + 交接预算（≤3 次） |
| 2 | **级联错误**（一个错感染全部） | 每个 Agent 输出先过验证器再传播 |
| 3 | **上下文膨胀**（编排器失控） | 子 Agent 只回传摘要（决策 + 结果） |
| 4 | **资源冲突**（并发写同一资源） | 锁/队列/事务门/结构化协议 |
| 5 | **成本失控**（15 倍 token） | token 预算 + 每任务成本指标 |

### 7.2 生产级检查清单

```text
多 Agent 上线前检查
[ ] 每个 Agent 有明确所有者与职责边界
[ ] 消息契约有 trace_id（因果链可追踪）
[ ] 子 Agent 输出经过验证器校验
[ ] 共享资源有并发控制
[ ] token 预算与成本告警已配置
[ ] 单点故障有降级方案（去中心化或备用）
[ ] 失败恢复粒度已测试（从中断步恢复）
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 四种协作模式：职能分工（路由）/Planner（计划+可恢复）/Supervisor-Worker（层级治理）/去中心化共识（无单点）
> 2. Planner 模式核心价值：可中断可恢复（审查 8min→2.5min、误判 15%→4%）
> 3. 去中心化共识：消息总线 + 优先级投票 + YIELD 配合，消除单点故障
> 4. 五大坑：握手循环/级联错误/上下文膨胀/资源冲突/成本失控——每个都要结构性治理；成本 15 倍是硬约束
