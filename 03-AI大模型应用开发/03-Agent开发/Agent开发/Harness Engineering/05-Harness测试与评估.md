## 1. 为什么 Agent 测试如此不同

### 1.1 测试范式的差异

| 维度 | 传统软件测试 | Agent 测试 |
|------|-------------|-----------|
| 输出 | 确定性（可断言） | **概率性（可统计）** |
| 用例 | 输入 → 期望输出 | 任务 → 期望行为轨迹 |
| 失败 | 可复现 | **不可复现（换次运行结果不同）** |
| 覆盖 | 代码路径 | **行为空间（无限）** |
| 判据 | 断言通过/失败 | **质量评分 + 阈值** |

> ⚠️ **核心困境**：Agent 的输出无法用 `assertEquals` 断言——同一任务两次运行可能走不同路径。因此 Agent 测试的本质是**统计性质量评估**而非确定性验证。

### 1.2 Agent 特有的测试难点

```text
三大测试难点
├── ① 轨迹多样：同一任务合法路径无穷多
├── ② 副作用：工具调用有真实影响（发邮件/写库）
├── ③ 环境依赖：外部服务状态影响结果
└── 对策：用「行为轨迹 + 结果质量」双维度评估
```

## 2. 先建评估再建 Agent

### 2.1 方法论

> 🎯 **铁律：先建评估（Eval），再建 Agent。** 没有评估基准就开发 Agent = 没有靶心就射箭。

```text
错误顺序：开发 Agent → 功能看起来没问题 → 上线 → 无法判断好坏
正确顺序：定义"成功"标准 → 建立评估集 → 边开发边跑评估 → 达标才发布
```

### 2.2 实施步骤

| 步骤 | 动作 | 产出 |
|------|------|------|
| ① 定义成功 | 为约 **50 个代表性用例**书面定义"成功运行"标准 | 成功标准文档 |
| ② 建立评估集 | 覆盖：主流程/边界/失败场景/注入攻击 | 评估数据集 |
| ③ 评估自动化 | 评估接入 CI，每天对构建结果运行 | 自动评估流水线 |
| ④ 质量门禁 | 评分作为 CD 流水线质量门，不达标不发布 | 门禁规则 |

```text
# eval 用例定义示例（JSON Lines）
{"task": "查询订单 ORD-1001 状态并通知客户",
 "tools": ["query_order", "send_email"],
 "success_criteria": {
   "result_correct": true,          # 结果正确
   "tool_used": ["query_order"],    # 使用了正确的工具
   "no_unneeded_tools": true,       # 没有多余工具调用
   "no_fabrication": true           # 没有编造数据
 }}
```

## 3. AI Evals：Agent 质量门禁

### 3.1 什么是 AI Evals

**AI Evals（智能体评估）**：Agent 感知的质量门禁体系——自动评估 Agent 的**正确性、性能与安全性**，并将评分作为 CD 流水线中的质量门。

### 3.2 评估对象分类

| 类别 | 评估内容 | 示例 |
|------|---------|------|
| **正确性** | 结果是否正确、是否编造 | 事实一致性、工具使用准确率 |
| **性能** | 快不快、贵不贵 | 端到端延迟、token 消耗 |
| **安全性** | 是否越权、是否被注入 | 注入成功率、越权动作次数 |
| **鲁棒性** | 异常输入/环境变化表现 | 失败恢复、超时处理 |

### 3.3 评估方法（LLM-as-Judge 的陷阱）

```text
LLM-as-Judge 的三大陷阱
├── ① 自评偏差：让 Agent 评估自己 → 必然放水
├── ② 位置偏差：评估器偏好先出现的答案
├── ③ 风格掩盖：流畅但错误的答案得分更高
└── 对策：独立验证器 + 双盲评估 + 规则优先于风格
```

## 4. 验证器独立进程

> ⚠️ **关键纪律**：**生成器与评估器不得处于同一上下文窗口。**

```
正确设计：验证器独立进程
┌─────────────┐         ┌─────────────────┐
│ 生成器（Agent）│         │ 验证器（独立）      │
│ 完整工具权限   │ ──输出──→ │ 全新上下文窗口      │
│ 会找"理由"    │         │ 只读权限          │
└─────────────┘         │ 按计划与策略规则评分  │
                        └─────────────────┘
```

| 独立化的价值 | 说明 |
|-------------|------|
| **排除自评偏差** | 验证器看不到生成器的"借口" |
| **规则纯净** | 验证器上下文只有计划 + 策略，不被任务污染 |
| **权限隔离** | 验证器只读，即使被攻陷也无破坏力 |
| **一整类失败模式的修复** | 提示词调优永远无法修复「自评放水」 |

> 🎯 **实践**：这条纪律排除了提示词调优无法修复的一整类失败模式——"Agent 声称任务完成"但实际未完成的幻象成功。

## 5. 评估维度体系

### 5.1 五维评估模型

| 维度 | 指标 | 测量方式 |
|------|------|---------|
| **任务完成率** | 成功完成的任务占比 | 评估集自动跑分 |
| **工具调用准确率** | 调用的工具/参数是否正确 | 轨迹比对 |
| **轨迹对齐度** | 执行路径与最优路径的编辑距离 | 路径编辑距离 |
| **端到端延迟** | P95/P99 耗时 | 性能埋点 |
| **幻觉率** | 编造事实/数据占比 | RAGAS / FactScore |

### 5.2 评估分层的金字塔

```text
         ▲ 端到端评估（少量，重）
        / \
       /   \
    / 场景评估  \
  /____________\
 / 单元评估（大量，轻） \
/____________________\
每个层级解决不同问题：
├── 单元评估：单个工具调用/单步决策是否正确
├── 场景评估：完整任务流程是否成功（50 用例集）
└── 端到端评估：真实生产环境抽样验证（影子模式）
```

### 5.3 持续评估（CI 中的 Agent）

```yaml
# eval-pipeline.yml 评估流水线
on: [push, pull_request]
jobs:
  eval:
    steps:
      - name: 单元评估（200 用例，轻量）
        run: eval-run --level unit --suite core
      - name: 场景评估（50 用例，完整）
        run: eval-run --level scenario --suite production
      - name: 安全红队（20 注入用例）
        run: eval-run --level security --suite redteam
      - name: 门禁判定
        run: check-gate --score-file result.json --min 90
```

## 6. 红队与对抗性测试

### 6.1 红队测试目标

```text
Agent 红队五类攻击面
├── ① 提示词注入：网页/邮件/文档携带恶意指令
├── ② 工具滥用：引导调用未授权/高影响工具
├── ③ 凭据窃取：诱导输出密钥/令牌
├── ④ 越权访问：跨身份/跨权限访问数据
└── ⑤ 输出投毒：引导生成恶意/有害内容
```

### 6.2 红队实践

| 环节 | 做法 |
|------|------|
| **用例库** | 基于 OWASP Top 10 for LLMs 建立注入用例库 |
| **自动化红队** | 每天自动跑注入套件，评分入门禁 |
| **人工红队** | 每季度深度攻击测试（组合攻击、业务逻辑攻击） |
| **AIBOM 核验** | 核对依赖供应链（技能/插件/模型）完整性 |

### 6.3 红队发现的管理

```text
红队发现的严重度分级
├── 🔴 严重：数据外泄/资金损失可能 → 立即停用修复
├── 🟠 高危：越权/破坏性操作 → 本迭代修复
├── 🟡 中危：信息泄露/降级 → 下迭代修复
└── 🟢 低危：体验/性能 → 记录跟踪
```

## 7. 评估的评估：模型-Harness 对

### 7.1 核心观点

> 🎯 **评估对象是「模型-Harness 对」，而非模型本身。** 强模型在缺乏稳定接口、结构化记忆、作用域权限与恢复机制时可能表现不佳；较弱模型在良好 Harness 下可能更可靠。

```text
案例：两个候选对比
├── 方案 A：顶级模型 + 无状态/无权限/无恢复
│    → 场景评估得分：62（能力被 Harness 拖垮）
├── 方案 B：中等模型 + 完整 Harness（记忆/权限/恢复/评估）
│    → 场景评估得分：84（稳定可靠）
└── 结论：评估选型必须「模型 × Harness」组合测试
```

### 7.2 组合评估矩阵

| Harness 成熟度 | 强模型 | 弱模型 |
|---------------|:---:|:---:|
| **L1 实验级** | 能力溢出，稳定性差 | 双双失败 |
| **L2 工程级** | 表现良好 | 勉强可用 |
| **L3 生产级** | **最佳组合** | 性价比之选 |

> 💡 **实践含义**：评估时不要只换模型——先评估 Harness 完整性，再在完整 Harness 上对比模型；很多"模型不够强"的结论，实际是"Harness 不够好"。

---

## 8. 核心要点

> 🎯 **核心要点**：
> 1. Agent 测试是统计性质量评估而非确定性验证——评估集 + 阈值 + 门禁是标配
> 2. 铁律：先建评估（50 用例成功标准）再建 Agent，评估接入 CD 质量门
> 3. 验证器独立进程：生成器与评估器分离上下文，排除自评放水这一整类失败
> 4. 评估对象是「模型-Harness 对」——Harness 不完整时，换更强的模型只是浪费预算
