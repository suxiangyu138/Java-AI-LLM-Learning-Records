## 1. 分层架构总览

```text
┌─────────────────────────────────────────────────┐
│ 接口层（Interface）        HTTP / SSE / MCP / CLI  │
├─────────────────────────────────────────────────┤
│ 编排层（Orchestration）    Agent 主循环、状态机、    │
│                           工具调用循环、重试策略    │
├─────────────────────────────────────────────────┤
│ 工具层（Tools）            纯函数式工具、MCP 客户端、 │
│                           外部 API 适配器          │
├─────────────────────────────────────────────────┤
│ 数据层（Data）             会话存储、记忆、向量库、    │
│                           上下文组装                │
├─────────────────────────────────────────────────┤
│ 基础设施层（Infra）        LLM Provider、缓存、      │
│                           遥测、配置、密钥            │
└─────────────────────────────────────────────────┘
```

> 🎯 **核心原则**：上层依赖下层接口、下层不知道上层存在；编排层是唯一允许"知道 LLM 存在"的层。demo 里 LLM 调用散落各处，生产里必须收拢到一条主循环。

### 1.1 各层职责边界

| 层 | 职责 | 不该做的事 | 常见失误 |
|----|------|-----------|---------|
| 接口层 | 参数校验、鉴权、响应格式、流式协议 | 业务逻辑、LLM 调用 | 在 handler 里直接调 LLM |
| 编排层 | 循环控制、工具调度、错误恢复、终止条件 | 工具实现细节、数据库操作 | 逻辑散落在各工具内 |
| 工具层 | 单一职责的可执行动作（幂等、无状态） | 自行调 LLM、自行改状态 | 工具里混入编排逻辑 |
| 数据层 | 存取会话/记忆/检索结果 | 模型调用 | 记忆与代码耦合 |
| 基础设施层 | Provider 适配、缓存、遥测、密钥 | 业务决策 | 把 provider 细节泄漏到上层 |

### 1.2 单向依赖与接口方向

```text
接口层 → 编排层 → 工具层/数据层 → 基础设施层
                        ↑
                所有 LLM 调用只能发生在编排层内部，
                通过 LLMProvider 抽象访问
```

## 2. 核心抽象：五个必须有的接口

### 2.1 LLMProvider——多供应商可替换的支点

```python
class LLMProvider(Protocol):
    async def chat(self, messages: list[Message], **kwargs) -> LLMResponse: ...
    async def chat_stream(self, messages: list[Message], **kwargs) -> AsyncIterator[str]: ...

# 实现：OpenAIProvider / AnthropicProvider / DeepSeekProvider / LocalVLLMProvider
# 生产要求：超时、重试（指数退避）、节流全部在 Provider 内部收敛，业务代码无感
```

**为什么必须有**：模型供应商升级、故障切换、路由（便宜/贵模型分流）都发生在这一层。没有抽象时，改供应商=改全项目。

### 2.2 Message——跨供应商统一消息结构

```python
@dataclass
class Message:
    role: Literal["system", "user", "assistant", "tool"]
    content: str
    tool_call_id: str | None = None   # 工具回传配对
    name: str | None = None
```

**陷阱**：各家模型对 `system`/`tool` 消息的约束不同（如 DeepSeek 需回传 `reasoning_content`、部分国产模型拒绝多 system 消息）。抽象层负责在 Provider 适配器里做方言转换，业务代码只见统一结构。

### 2.3 Tool——有界、可测、自描述

```python
class Tool(ABC):
    name: str                 # 动词开头，一工具一职责
    description: str          # 做什么、何时用、边界（写清楚！）
    parameters: JSONSchema    # 参数即决策负担：参数越少模型越不容易错

    @abstractmethod
    async def execute(self, args: dict) -> ToolResult: ...
```

**ToolResult 必须包含**：`ok/error` 状态、结构化错误码（`retry: true/false`）、耗时、幂等键。错误信息要能让 LLM"看明白后自救"——这是消除 80% 卡死循环的关键（详见 [Function Calling 体系 03 篇](../../02-大模型基础与Prompt工程/Function%20Calling%20函数调用【Agent%20基石】/03-调用循环工程.md)）。

### 2.4 AgentState——可序列化的会话状态

```python
@dataclass
class AgentState:
    session_id: str
    history: list[Message]      # 可截断/压缩
    tool_meta: dict             # 每轮工具调用留痕
    budget: Budget              # token/轮数/成本预算
    version: tuple[str, str]    # (prompt_version, model_version)
```

**生产要求**：`AgentState` 必须可序列化（json）——长任务要落库、断点续跑、故障回放都靠它。不可序列化的状态（如持有锁、open socket）是生产事故温床。

### 2.5 Registry——按需发现工具

```python
class ToolRegistry:
    def get(self, name: str) -> Tool: ...
    def list_for_role(self, role: str) -> list[Tool]: ...  # 角色过滤 = 最小权限
    def schema_bundle(self) -> list[dict]: ...             # 供 tools 参数声明
```

**2026 新趋势**：工具规模大了之后，把全部 schema 塞进每轮请求会浪费 token。主流方案是 `tool_search` / `defer_loading` 按需发现（OpenAI gpt-5.x 与 Claude 5 系均已原生支持，详见 [Function Calling 体系 01 篇](../../02-大模型基础与Prompt工程/Function%20Calling%20函数调用【Agent%20基石】/01-原理与演进.md)）。

## 3. 目录结构模板

```text
agent-service/
├── pyproject.toml              # 依赖锁版本（可复现构建）
├── Dockerfile                  # 从第一天就容器化
├── src/agent/
│   ├── api/                    # 接口层：FastAPI 路由、SSE、鉴权
│   │   ├── routes_chat.py
│   │   └── routes_jobs.py      # 异步任务接口（见 09 篇）
│   ├── orchestration/          # 编排层：主循环、状态机、重试
│   │   ├── agent_loop.py
│   │   └── policies.py         # 终止条件、预算、审批门
│   ├── tools/                  # 工具层：一文件一工具
│   │   ├── base.py             # Tool 基类 + ToolResult
│   │   ├── registry.py
│   │   ├── order_query.py
│   │   └── refund.py
│   ├── data/                   # 数据层：会话、记忆、检索
│   │   ├── session_store.py
│   │   └── memory.py
│   ├── infra/                  # 基础设施层
│   │   ├── llm/                # Provider 适配器（openai/anthropic/deepseek...）
│   │   ├── cache.py            # prompt/语义缓存
│   │   ├── telemetry.py        # OTel 埋点
│   │   └── config.py           # pydantic-settings 配置模型
│   └── prompts/                # 只放版本号引用，不存字符串（见 10 篇）
├── tests/                      # 见 05 篇
│   ├── unit/  ├── contract/  └── e2e/
└── evals/                      # golden set 与评分脚本（见 06 篇）
    ├── datasets/  └── metrics/
```

> 💡 **识别反模式**：demo 项目里 `agent.py` 单文件超过 800 行、`if __name__ == "__main__"` 里塞交互逻辑、工具函数直接 `openai.chat.completions.create`——都是需要按本模板重构的信号。

## 4. LLM 与确定性代码的职责边界

2026 生产共识（MLflow/Mindflow/Google Bake-Off 一致）：**混合架构**——LLM 做"高容错决策"，确定性代码做"零容错计算"。

| 该交给 LLM | 该交给代码 |
|-----------|-----------|
| 意图识别、意图分类 | 事务、金额计算、折扣规则 |
| 工具选择与参数起草 | 参数校验、幂等、并发控制 |
| 自然语言总结、回答组织 | 数据库读写、审计、配额扣减 |
| 模糊指令理解 | 任何"错一次就要赔钱"的运算 |

**边界判定问题**："这句话要不要走 LLM？"——如果结果错了，人工兜底成本高不高？高→确定性代码。

**落地示例**：退款流程中，LLM 只负责"理解用户诉求并起草退款请求"，金额上限校验、双重退款防重、审批流全部走确定性代码（详见 08 篇审批门）。

## 5. 工具层设计契约

| 契约 | 要求 | 理由 |
|------|------|------|
| 幂等 | 相同参数重复执行结果一致（带 `idempotency_key`） | 重试/超时重放不产生副作用（双扣款、重复工单） |
| 无状态 | 工具不持有会话状态，状态走 AgentState | 水平扩展、断点续跑 |
| 超时 | 每个工具独立超时（秒级） | 慢工具拖垮整体；配合编排层"放弃并继续" |
| 错误结构化 | `ToolResult{ok, error_code, retryable, message_for_llm}` | LLM 能据错误码自救；`retry: false` 防死循环 |
| 审计 | 敏感工具记录入参、调用者、审批人 | 事后追责（08 篇） |
| 最小权限 | 按角色暴露工具子集（`list_for_role`） | 一次注入不至于全工具可用 |

> ⚠️ **MCP 定位**：MCP 是"工具接入的协议层"，不是架构起点。先按上面契约定义好工具，再用 MCP 暴露/消费——否则你会被框架的便利绑架出违背契约的代码。

## 6. 可测试性与依赖注入

**核心手法：依赖注入，让"LLM 调用"和"工具副作用"都成为可替换的依赖。**

```python
class Agent:
    def __init__(self, llm: LLMProvider, tools: ToolRegistry,
                 store: SessionStore, clock: Clock = SystemClock):
        ...

# 生产：Agent(llm=OpenAIProvider(...), tools=real_registry, ...)
# 测试：Agent(llm=ReplayProvider(fixtures), tools=fake_registry, ...)
```

| 手法 | 做法 | 收益 |
|------|------|------|
| ReplayProvider | 录制真实对话回放（VCR 模式） | 单测不烧 API 钱、可复现 |
| FakeTool | 内存版工具实现 | 编排逻辑全量可测 |
| Clock 抽象 | 时间注入（超时/预算逻辑） | 时间相关测试稳定 |
| 无 I/O 核心 | 纯函数层（决策、校验）与 I/O 分离 | 覆盖率高、心智负担小 |

> 💡 测试细节（Mock 三层、契约测试、故障注入）见 [05-测试体系](05-测试体系：Mock、契约与端到端测试.md)。

## 7. 单体 Agent 的拆分模式

| 模式 | 适用 | 代价 | 2026 实证 |
|------|------|------|----------|
| 单 Agent 大 prompt | 任务简单稳定 | 改一处影响全局 | 调试呈指数变难 |
| 子 Agent + Supervisor | 复杂流程、能力异构 | 协调开销、交接信息丢失 | 团队实测 1 小时 → 10 分钟（并行 + 职责单一） |
| 流水线 Agent | 阶段明确（如 提取→清洗→生成） | 阶段间耦合 | 每阶段可独立评估调优 |

**拆分要点**：
- 每个子 Agent 只做一件事，prompt 职责单一
- 交接信息（payload）必须可检查、可审计——多 Agent 系统约 23% 故障是协调问题
- 路由/意图分类优先用便宜快模型，把复杂任务转给专业子 Agent

## 8. 2026 架构共识与反模式

**共识**：
- 混合架构（LLM + 确定性代码）是 2026 生产标配
- 工具优先设计：先定义有界可测动作，MCP 只是集成层
- Harness impermanence：能力演进快（多步任务可能变成一步 prompt），用版本化接口 + 锁依赖保持可弃换
- 容器化 + 无状态 + 水平扩展从第一天开始

**反模式速查**：

| 反模式 | 症状 | 修正 |
|--------|------|------|
| 上帝 Agent | 一个 agent 管所有事 | 拆职责单一子 Agent |
| LLM 调用散落 | 各模块直接调 provider | 收拢到编排层 |
| 工具不可测 | 工具内直接写库/发请求 | 注入依赖 + 契约化 |
| 状态藏内存 | 重启丢会话 | AgentState 序列化落库 |
| prompt 内联 | 字符串写死在代码 | 版本注册表（10 篇） |
| 忽略 harness | 模型升级后行为漂移 | 评估门禁 + 版本快照（06/10 篇） |
