## 1. 性能与成本的杠杆排序

```text
按"投入产出比"排序（2026 生产实践）：
  1. Prompt Caching        —— 输入成本省 ~85-90%，TTFT 降 50-70%（改配置即生效）
  2. 缓存感知路由          —— 提升缓存命中率（命中率可差 7 倍）
  3. 语义缓存              —— 高频重复场景成本-70%、延迟降 30 倍
  4. 工具结果 memoization —— 相同调用不重跑
  5. 模型路由              —— 简单请求用便宜模型
  6. 并发/连接复用         —— 吞吐与延迟
  7. 流式                  —— 感知延迟（不是真实延迟）
```

> 🎯 **核心认知**：Agent 的成本 = 轮数 × 全量上下文 × 单价。每多一轮对话，前面所有轮次的输入 token 都要重发——**上下文增长是成本曲线陡增的主因**，缓存是把这条曲线压平的核心手段。

## 2. Prompt Caching：缓存经济学

### 2.1 机制

```text
稳定前缀命中缓存（各家实现不同）：
  Anthropic：显式 cache_control 断点，5 分钟 TTL
  OpenAI：≥1024 token 前缀自动缓存（约 90% 省输入成本）
  Gemini：隐式免费

命中效果：输入成本省 ~85-90%；TTFT 降 50-70%
回本点：5 分钟缓存读 2 次回本；1 小时缓存读 3 次回本（写成本更高）
```

### 2.2 缓存铁律（不遵守则命中率崩塌）

| 铁律 | 说明 |
|------|------|
| 前缀必须稳定 | system prompt + 固定工具声明按固定顺序排最前 |
| 不增删工具 | 增删工具 = 前缀变化 = 全缓存失效（工具声明是前缀的一部分） |
| 固定排序 | 工具声明顺序锁定，禁止字典序抖动 |
| 冻结 system | system prompt 每个词都是缓存的一部分 |
| 会话内长对话 | 把历史压缩后重放，保持前缀命中（上下文管理三件套） |

> ⚠️ **Agent 特有陷阱**：工具结果、历史消息逐轮追加时，必须**从尾部追加、头部保持稳定**；一旦把"上一轮工具结果"插入到前缀中间，整条缓存失效。命中率目标 >80%。

## 3. 缓存感知路由：别盲轮询

```text
问题：多实例/多后端负载均衡时，同一请求前缀被随机分到不同 KV 缓存 → 缓存命中率暴跌
实测：盲轮询下命中率可跌至 8%，TTFT p90 与缓存感知路由差 57 倍

方案：缓存感知路由——按 KV 缓存前缀哈希把相同前缀路由到同一后端
参考实现：vLLM PrefixAwareRouter / KvawareRouter（Rust）
         llm-d（CNCF Sandbox）、NVIDIA Dynamo
实证：AWS EKS 缓存感知路由 p90 TTFT 1.4s vs 轮询 4.4s
```

> 🎯 **2026 生产延迟优化第一大杠杆**——在加机器、换模型之前，先确认路由策略没有把缓存打散。

## 4. 语义缓存：命中"意思相近"

| 项 | 内容 |
|----|------|
| 原理 | 请求向量化 → 向量库相似度检索 → 命中则直接返回缓存结果 |
| 命中率 | 重复/近似工作负载（FAQ、文档问答）60-85% |
| 收益 | API 调用减 ~69%；延迟 ~1.67s → ~0.052s（约 32 倍） |
| 适用 | 高重复、答案可复用、对新鲜度不敏感的场景 |
| 不适用 | 个性化回答、时效敏感（价格/库存）、需要工具执行的场景 |

**工程注意**：
- 相似度阈值要校准（太高漏命中、太低误命中错误答案）
- 缓存结果要带"有效期"（LLM 答案会过期）
- 语义缓存与 eval 结合：命中率与错误率同时监控
- 实现选型：Redis + embedding 或专用向量库（见 [向量数据库](../../04-RAG检索增强生成/) 体系）

## 5. 并发与连接复用

### 5.1 并行工具调用

```text
Agent 每轮可能调用多个无依赖工具——串行执行是纯浪费
方案：协议层允许并行（parallel_tool_calls）时用 asyncio.gather 并发执行
前提：工具必须幂等（02 篇契约）——有依赖的工具之间必须关并行

收益：一轮 3 个工具从 3× 延迟 → 1× 延迟
注意：并行放大 token 突发，预算与限流要跟着配（11 篇）
```

### 5.2 连接复用与节流

| 手段 | 效果 |
|------|------|
| HTTP 连接池复用（httpx/aiohttp/OpenAI SDK 默认池） | 免去 TLS 握手开销 |
| 并发上限（信号量） | 防供应商限流 429、防本地资源打满 |
| 指数退避重试（Provider 层） | 429/5xx 自动恢复 |
| 批处理 | 同批任务合并（成本与吞吐双赢） |

## 6. 流式输出与 TTFT 优化

| 目标 | 手段 | 说明 |
|------|------|------|
| 感知延迟 | SSE 流式（首 token 秒出） | 用户"觉得快"，比真实延迟重要 |
| TTFT | Prompt 缓存命中 + 流式 | 缓存命中 TTFT 降 50-70% |
| 中间进度 | Agent 状态流式（工具调用过程可见） | 用户看到"正在查订单→正在退款"，信任感大增 |
| 断线恢复 | SSE `Last-Event-ID` 重连（09 篇） | 事件流可重放 |

> 💡 **Agent 流式要流"过程"而非只流"答案"**：工具调用开始/结束、步骤切换都是可流式事件（09 篇异步架构详解）。

## 7. 模型路由：便宜模型先上

```text
模式：意图分类/简单问答 → 便宜快模型；复杂推理 → 强模型
收益：多模型路由可达到或超过单一强模型质量，成本显著下降
开销：路由决策本身 5-20ms 延迟 + 阈值调优成本

落地层级：
  Provider 层：应用内路由（分类先行）
  网关层：LiteLLM Proxy 路由 + fallback（09 篇，详见 LiteLLM 体系）
```

| 路由策略 | 适用 |
|---------|------|
| 按意图 | 闲聊走便宜模型、任务走强模型 |
| 按复杂度 | 简单查询短回答走快模型 |
| 按轮次 | 前几轮快速响应，深入时升级模型 |
| fallback | 主模型故障/限流 → 备用模型（保持可用性） |

## 8. 成本预算与监控

```text
三层预算（全部要配）：
  单请求：token 上限 + 成本上限（超限中断循环）
  单会话：累计预算（防长会话烧钱）
  单用户/租户：日/月上限（LLM10 无界消耗治理，见 11 篇）

监控闭环：
  token-per-success 滚动指标（成本效率）
  按模型/工具/路由路径聚合成本（找黑洞）
  预算告警分级：预警（80%）→ 硬限（100% 熔断）
```

**成本黑洞自查**：
- 长上下文重发未缓存（先查缓存命中率）
- 循环超长（max_steps 上限过宽）
- 全量历史不压缩（长会话 token 爆炸）
- 大模型大材小用（无路由）
