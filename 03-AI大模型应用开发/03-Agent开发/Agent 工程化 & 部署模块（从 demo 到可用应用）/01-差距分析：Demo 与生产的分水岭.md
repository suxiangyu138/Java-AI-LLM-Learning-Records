## 1. Demo 与生产的本质区别

```text
Demo 回答的问题：这个 Agent 能不能做到？（证明可行性）
生产回答的问题：这个 Agent 能不能 99.9% 时间做到？
                    —— 可靠性、成本、安全、演进、合规缺一不可

demo 里 LLM 是主角，代码是胶水；
生产里代码才是骨架，LLM 是骨架上的"决策器"。
```

> 🎯 **一句话**：demo 证明"一次能成"，生产要求"每次可控"。两者之间的工程差距，就是本模块 02-11 篇要补的内容。

### 1.1 为什么"多写几轮 prompt"补不上差距

Agent 生产化的难点不在 prompt，而在 LLM 的不确定性放大效应：

| 不确定源 | demo 场景影响 | 生产场景影响 |
|---------|--------------|-------------|
| 输出格式漂移 | 重试一次即可 | 下游解析崩溃，引发级联失败 |
| 工具调用偏差 | 人工纠正 | 未授权操作、无限循环（同一工具连续调用 8-47 次） |
| 上下文累积漂移 | 无所谓 | 多轮后行为退化，Pathfinder（ACM 2026）发现 41% 生产 bug 是级联故障，主根因是上下文/token 管理 |
| 模型版本更新 | 感觉变了 | 评估分数漂移、用户投诉（无评估基线时不可察觉） |

### 1.2 一个思想实验

> demo 的验收标准是"演示成功"；生产的验收标准是"把 demo 时人工兜住的每种意外，都变成代码里的显式处理"。

## 2. 八大分水岭

| # | 维度 | Demo（原型态） | 生产（工程态） | 对应篇章 |
|:---:|------|--------------|--------------|---------|
| 1 | 架构 | 单文件脚本 / notebook，LLM 调用散落各处 | 分层架构：接口/编排/工具/数据；LLM 只做决策，代码做计算 | 02 |
| 2 | 配置 | key 写在代码里、模型写死 | 环境隔离、密钥托管、模型/prompt 外置动态配置 | 03 |
| 3 | 可观测 | `print()` 打点、翻终端日志 | trace 贯通、结构化日志、成本指标，trace-first 排错 | 04 |
| 4 | 测试 | 手动点几遍"看起来没问题" | Mock LLM 单元测试 + 契约测试 + 故障注入 + E2E | 05 |
| 5 | 评估 | "凭感觉还行" | golden set + 统计回归门禁 + LLM-as-Judge 在线采样 | 06 |
| 6 | 性能成本 | 不关心延迟与账单 | Prompt 缓存、语义缓存、模型路由、预算告警 | 07 |
| 7 | 安全 | key 裸奔、工具全权限、无审计 | 最小权限、提示注入防线、审批门、数据治理、审计 | 08 |
| 8 | 部署与演进 | `python main.py`、改完就上 | 容器/网关/队列、金丝雀发布、可回滚、SLO 治理 | 09/10/11 |

> ⚠️ **顺序陷阱**：很多团队先补 9（部署）再补 5（评估）——部署了无法回滚的版本、上线了无法评判质量。正确顺序是先建"看得到"（04/06），再送"跑得起"（09）。

## 3. Demo 地狱：三个典型翻车现场

### 3.1 场景 A：依赖链裸奔

- **现象**：demo 依赖本机 Python 环境、直接访问第三方 API、模型 key 用环境变量写死在 shell 配置里。
- **上线后果**：换台机器跑不起来；供应商限流直接 429 全挂；key 泄露后账单爆表。
- **根因**：没有把"运行环境"当成交付物。
- **工程解法**：容器化（`Dockerfile` + 锁版本依赖）、配置外置（03 篇）、网关兜底限流（09 篇）。

### 3.2 场景 B：工具失控

- **现象**：demo 里 Agent 有 5 个工具，全部放开；循环上限 20 轮写死；工具无超时。
- **上线后果**：一次注入让 Agent 循环调用 40 次付费工具；某工具慢 30 秒拖垮整个请求；工具失败导致死循环（无错误回传机制时，卡死循环实测可达 8-47 次调用）。
- **根因**：把"模型有工具"当成了"工具安全"。
- **工程解法**：最小权限（per-tool allow-list）、`maxSteps ~20 / maxToolCalls ~50`、工具超时 + 结构化错误回传（08 篇）。

### 3.3 场景 C：改一版挂一版

- **现象**：prompt 直接写在代码字符串里；模型一升级就换代码重新部署；没有评估就全量上线。
- **上线后果**：0 到 100% 一把梭（2026 年被称作"agentic 部署的原罪"）；模型更新后行为漂移无感知；回滚=回滚代码+丢数据。
- **根因**：prompt/模型/代码三者版本纠缠，无法独立演进。
- **工程解法**：prompt 版本注册表 + label 部署 + 金丝雀 5% + 评估门禁（10 篇）。

## 4. 2026 生产基线共识

综合 2026 年工程实践共识（MLflow、Mindflow、Google Agent Bake-Off、LLMOps 社区）：

| 共识 | 内容 | 实践落点 |
|------|------|---------|
| 混合架构 | LLM 管感知/推理/意图分类，确定性代码管事务/金融计算/二进制正确性 | 02 篇分层设计 |
| 拆单体 | 复杂 Agent 拆成职责单一的子 Agent，由 supervisor 编排 | 团队实测 1 小时 → 10 分钟（并行） |
| 工具优先 | 先定义有界、可测试的工具；MCP 是集成层而非架构起点 | 02 篇工具契约 |
| Eval 即规范 | golden set（50-100 题）+ 评分门禁在每次生产发布前必跑 | 06 篇三层门禁 |
| 全程可观测 | 每次 plan-act-observe-reflect 循环输出结构化 JSON 事件 | 04 篇 trace 体系 |
| 运行时治理 | 治理决策在动作发出前强制执行（权限环、kill switch、审计汇） | 08 篇安全 |
| 容器化交付 | 从第一天就容器化，保持无状态以水平扩展 | 09 篇部署 |
| 外部化 prompt | prompt 作为版本化配置与代码分离，支持 A/B 与回滚 | 10 篇版本管理 |

```text
□ 01 差距篇    —— 已列出本项目的差距清单并排序
□ 02 架构      —— 代码已分层；LLM 决策与确定性计算边界清晰；工具无 I/O 可测

□ 08 安全      —— 最小权限；不可逆操作有人审门；输出当不可信处理；审计齐全
□ 09 部署      —— 容器化；无状态可水平扩展；长任务走队列+SSE；网关兜底
□ 10 版本      —— prompt 已迁出代码；金丝雀 5%；回滚演练过
□ 11 治理      —— SLO 已定义；配额/限流生效；成本与质量告警闭环
□ 12 案例      —— 对照完整旅程核对过所有环节
```

## 6. 阶段自评：你的 Agent 在哪一档

| 档位 | 特征 | 判定信号 | 下一步 |
|------|------|---------|--------|
| L0 脚本 | 单文件，print 排错，key 硬编码 | 换机器跑不起来 | 先读 02/03 |
