## 1. 配置的三个层次

| 层次 | 内容 | 变更频率 | 变更方式 |
|------|------|---------|---------|
| 部署配置 | 环境变量、端口、连接串、密钥引用 | 低 | 发版/编排系统注入 |
| 应用配置 | 模型选择、temperature、超时、限流阈值 | 中 | 配置中心 / 注册表，热更新 |
| 版本化配置 | prompt、eval 基线、路由策略 | 高 | 版本注册表 + label（见 10 篇） |

> 🎯 **核心原则**：与"跑起来"相关的是部署配置，与"行为"相关的是动态配置，与"质量"相关的是版本化配置——三者必须分开管理，混在一起就会出现"改个 prompt 要发版"或"发个版改了模型"的事故。

### 1.1 为什么 demo 的配置方式到生产必炸

```text
demo：key 写在代码里 / .env 提交进 git / 模型写死 "gpt-4o"
生产后果：
  1. key 泄露进 git 历史 → 公网扫描即被盗 → 账单爆表（LLM10 无界消耗事故高发入口）
  2. 全环境共用一个 key → 无法按租户/环境审计与限流
  3. 模型写死 → 升级/降级/回退都要改代码
```

## 2. 环境隔离：dev / staging / prod

### 2.1 三环境基线

| 项 | dev | staging | prod |
|----|-----|---------|------|
| 模型 | 便宜快模型或本地模型 | 与 prod 一致 | 生产模型 |
| key | 独立开发者 key（低配额） | staging key（独立账户） | prod key（最高配额+预算告警） |
| 数据 | 合成/脱敏 | 脱敏近真实 | 真实 |
| 预算 | 无 | 中 | 硬上限 + 告警 |
| 评估门禁 | 不跑 | 必跑（06 篇） | 金丝雀 + 在线采样 |

> ⚠️ **最常被忽略**：staging 与 prod 必须用**不同的供应商账户/API key**，否则 staging 的压测和调试流量会污染 prod 的配额、限流和成本报表。

### 2.2 实现方式

```text
本地开发：.env（不进 git，.gitignore 必配）
CI/CD：   CI 平台 Secret 注入
云端：    K8s Secret / 云厂商 Secret Manager，运行时注入环境变量

推荐配置模型：pydantic-settings（Python）——用类型化模型加载配置，
启动时校验，缺失必填项直接拒绝启动而不是运行中炸
```

## 3. 密钥管理：从 .env 到 KMS

### 3.1 演进路径与选型

| 阶段 | 方案 | 适用规模 | 代价 |
|------|------|---------|------|
| 起步 | 环境变量 + .gitignore | 个人/小团队 | 人工轮换、无审计 |
| 团队 | CI Secret + 平台密钥库（Vault/云 KMS） | 中型团队 | 需要运维投入 |
| 规模化 | Secret Manager + 自动轮换 + 审计 | 多服务/多租户 | 成本与复杂度上升 |

### 3.2 API key 生命周期管理

```text
创建 → 授权（最小权限：只给需要的模型/工具）→ 使用（服务端注入，客户端不可见）
     → 监控（用量、异常调用）→ 轮换（定期 + 泄露立即）→ 吊销（按需）
```

| 生命周期环节 | 生产要求 | 常见事故 |
|-------------|---------|---------|
| 创建 | 按环境/租户/用途分离，注释用途 | 一把 key 全项目共用 |
| 授权 | 供应商后台限制模型白名单、IP 白名单 | key 有全模型权限 |
| 使用 | 服务端持有，客户端走网关（见 09 篇） | 前端/SDK 直连暴露 key |
| 轮换 | 双 key 交替（grace period）实现零停机轮换 | 轮换后未更新全部引用 |
| 吊销 | 泄露后立即吊销 + 全库扫描历史泄露 | key 留在 git 历史/日志里 |

> 💡 **零停机轮换法**：同时配置新旧两个 key，切流量到新 key 观察稳定后再吊销旧的——供应商端双 key 各占一个配额，轮换期预算上限翻倍是正常现象。

### 3.3 2026 安全基线相关

- LLM07（系统提示泄漏）：密钥/租户标识/内部规则**绝不进 prompt**——prompt 必然会被某种方式泄漏（输出、日志、第三方），放进 prompt 就等于公开
- Agent 身份（08 篇）：多 Agent 用 OAuth 2.1 + PKCE 的可验证身份，**不用共享 key**，每个 Agent 可独立吊销、独立审计
- MCP 供应链：MCP server 的 token/凭据同样走密钥管理，版本锁 pin（MCP STDIO RCE 事件 ≥10 CVE 后的基线）

## 4. 模型与行为配置外置

### 4.1 模型选择外置

```python
# 配置示例（pydantic-settings 风格）
models:
  default: "deepseek-chat"          # 默认对话
  reasoner: "deepseek-reasoner"     # 复杂推理
  judge: "gpt-4.1"                  # 评估（06 篇）
  embedding: "text-embedding-3-large"
```

**为什么必须外置**：
- 供应商故障时一键切换 fallback（09 篇网关）
- 金丝雀发布模型版本（10 篇）
- 按用户/租户路由不同模型（灰度配置）

### 4.2 行为参数外置

```python
runtime:
  max_tool_calls_per_run: 50      # 循环上限（LLM06 最小权限）
  max_steps: 20
  tool_timeout_seconds: 30
  default_temperature: 0.2
  budget_per_request_usd: 0.05    # 单请求成本上限
  retry_policy: {max_retries: 3, backoff: "exponential"}
```

> ⚠️ 这些参数属于"行为配置"，建议进配置中心支持热更新——生产事故（如死循环）时能**不改代码、不重启**就收紧上限（例如把 `max_tool_calls` 从 50 降到 5 止血）。

## 5. 动态配置：运行时变更与灰度

### 5.1 三层动态化

| 层 | 手段 | 示例 |
|----|------|------|
| 参数热更新 | 配置中心（Nacos/Consul） | 限流阈值、超时、预算 |
| prompt 版本 | Prompt 注册表 label（10 篇） | prod 标签指向 v12 → v13 |
| 用户级灰度 | Feature Flag（OpenFeature 标准） | 5% 用户用新模型组合 |

### 5.2 Feature Flag 用法

```text
场景：新模型组合（prompt v13 + gpt-5）只给 5% 用户
方案：flag = "agent.prompt_v13_model_v2"，按 user_id 哈希灰度
回滚：flag 关掉即回退，无需发版

要求：flag 必须入 trace（04 篇），否则无法解释"同一请求为什么行为不同"
```

> 💡 灰度的完整机制（shadow → canary 5% → 100%）在 [10-版本管理与发布](10-版本管理与发布：Prompt、模型与代码协同演进.md)。

## 6. 配置安全红线：密钥绝不进 prompt

| 红线 | 说明 |
|------|------|
| key/密码/token 不进 system prompt | LLM07 系统提示泄漏：prompt 会以输出/日志/trace 形式外泄 |
| 内部规则不进 prompt | 安全策略进代码，不进提示词（提示词可被提取） |
| 租户标识不混入公共 prompt | 多租户场景防跨租户泄漏（LLM08 向量弱点相关） |
| 日志/trace 脱敏 | 配置与请求体中的敏感字段一律 mask（04 篇） |
| 用 canary token 监测 | 在 system prompt 埋随机 token，输出中出现即报警（08 篇） |

## 7. 配置校验与事故复盘

### 7.1 启动校验

```text
启动时校验（fail-fast）：
  1. 必填配置缺失 → 拒绝启动（不默认值糊弄）
  2. 模型名/工具名存在性校验（防拼写错误）
  3. 配额/预算配置合法性（负数、缺失上限 → 报错）
  4. 环境标识一致（prod 环境不许用 dev 账户 key）
```

### 7.2 典型配置事故复盘

| 事故 | 根因 | 修复 |
|------|------|------|
| key 提交进 git，公网被抓 | 无 .gitignore / 无扫描 | pre-commit hook 扫描密钥 + 历史清理（filter-repo）+ 立即吊销轮换 |
| staging 压测打爆 prod 配额 | 共用 key/账户 | 环境隔离独立账户 |
| 改 prompt 要发版 | prompt 内联代码 | 迁到注册表（10 篇） |
| 生产改限流要重启 | 参数写死 | 配置中心热更新 |
| 灰度无法回滚 | 无 feature flag | OpenFeature 接入 |

## 8. 落地检查单

```text
□ 三个环境（dev/staging/prod）配置隔离，key 独立账户
□ .gitignore 覆盖 .env*；CI 密钥扫描已接入
□ 密钥全部走 Secret Manager，代码零明文
□ 模型/行为参数外置，支持热更新
□ prompt 已迁出版本注册表（未完成则见 10 篇）
□ Feature Flag 已接入灰度场景并进入 trace
□ 启动 fail-fast 校验齐全
□ 无任何敏感信息出现在 prompt/trace/日志（脱敏已生效）
```
