# 工具封装实战：连接、查询与返回

> 把数据库变成 Agent 的"三四个好工具"而非"一个万能入口"：list_tables / schema / query / explain 的分工、连接与超时治理、结果截断与错误回传——这套工具链就是 Text-to-SQL 工程化的核心资产。

## 1. 工具设计总原则：让模型"会探索，少犯错"

| 原则 | 说明 | 反面 |
|---|---|---|
| 小步探索 | 先看表清单→再看相关表 schema→再写查询 | 一次塞全库 schema |
| 只读默认 | 查询工具只做 SELECT，读写分离 | 一个 execute 万能工具 |
| 强约束返回 | 强制 LIMIT、返回截断、错误信息清洗 | 全量返回撑爆上下文 |
| 自纠错闭环 | 报错信息回喂模型，允许重写重试 | 报错即终局 |
| 可审计 | 每次调用记日志（SQL/耗时/行数） | 黑盒执行 |

> 🎯 核心要点：**工具链的价值在于把"一次复杂推理"拆成"几次简单决策"**——模型每个工具调用只做一个动作，错误边界清晰，审计颗粒度细。

## 2. 四件套工具清单（LangChain SQLDatabaseToolkit 同构）

| 工具 | 输入 → 输出 | 要点 |
|---|---|---|
| `list_tables` | → 表名列表 | 轻量，先摸全貌 |
| `describe_table` | 表名 → DDL+样例行 | 按需加载，一次 ≤3 张表 |
| `query` | SQL → 行数据 | 只读校验 + LIMIT 钳制 + 超时 |
| `explain` | SQL → 执行计划 | 帮模型判断查询是否低效 |

```python
# 伪代码：四工具的最小实现骨架
class SqlTools:
    def __init__(self, conn_factory, read_only=True, max_rows=100):
        self.conn_factory = conn_factory
        self.max_rows = max_rows

    def list_tables(self) -> list[str]:
        with self.conn_factory() as c:
            return [r[0] for r in c.execute(
                "SELECT name FROM sqlite_master WHERE type='table'")]

    def describe_table(self, table: str) -> str:
        with self.conn_factory() as c:
            ddl = c.execute(f"SELECT sql FROM sqlite_master WHERE name=?", [table]).fetchone()
            rows = c.execute(f"SELECT * FROM {table} LIMIT 3", []).fetchall()  # 样例行
            return f"{ddl}\n样例:\n{rows}"

    def query(self, sql: str) -> dict:
        sql = self._validate_read_only(sql)      # 文本守卫（见 03 篇）
        sql = self._clamp_limit(sql, self.max_rows)  # 强制 LIMIT
        with self.conn_factory() as c:
            c.execute(f"PRAGMA query_only=ON")   # SQLite 层只读兜底
            rows = c.execute(sql, []).fetchmany(self.max_rows)
        return {"rows": rows, "row_count": len(rows)}
```

## 3. 连接层治理：连接池、超时、并发

| 项 | 建议 | 理由 |
|---|---|---|
| 连接池 | HikariCP（Java）/ psycopg pool（Python） | 复用连接，防连接风暴 |
| 最大连接数 | 4-8（Agent 专用池） | 防止 Agent 循环耗尽连接拖垮生产 |
| 语句超时 | 10s（可配置） | 防止无 LIMIT 全表扫描挂死 |
| 连接超时 | 5s | 快速失败重试 |
| 并发上限 | 同会话 1-2 个并发查询 | 控制成本与资源 |
| 只读账号 | 连接全部走只读角色（03 篇） | 最后一道闸 |

```python
def make_conn():
    """只读工厂：每次工具调用拿新连接，用完即还"""
    conn = sqlite3.connect("file:app.db?mode=ro", uri=True)
    conn.execute("PRAGMA query_only=ON")
    return conn
```

## 4. 返回处理：截断、序列化、Token 预算

| 问题 | 方案 |
|---|---|
| 结果太多撑爆上下文 | 强制 LIMIT（默认 100 上限 1000）+ 只取前 N 行 |
| 单元格巨大（长文本/BLOB） | 每格截断（如 200 字符）+ 省略号 |
| 二进制/JSON 列 | 序列化为摘要（`[blob 8KB]`/`[json 3 keys]`） |
| 列数爆炸 | 只返回模型可消费的列（按 select 列表） |
| 返回给模型前的加工 | 转 Markdown 表格/摘要统计（如"共 347 行，显示前 10"） |

```python
def format_rows(rows, max_chars=4000):
    """截断到 Token 预算内：先按行数截，再按总字符截"""
    text = "\n".join("| " + " | ".join(str(v)[:200] for v in r) + " |" for r in rows[:10])
    if len(rows) > 10:
        text += f"\n... 共 {len(rows)} 行，仅显示前 10"
    return text[:max_chars]
```

## 5. 错误处理与自纠错闭环

```python
def safe_query(self, sql: str, max_retries=3) -> dict:
    for attempt in range(max_retries):
        try:
            return self.query(sql)
        except SqlGuardError as e:      # 守卫拦截（注入/非只读）
            return {"error": e.sanitized_msg}   # 错误已脱敏
        except sqlite3.OperationalError as e:
            error = sanitize(e)         # 清洗驱动报错（防泄 schema）
            sql = self._rewrite_with_feedback(sql, error)  # 回喂模型重写
    return {"error": "重试 3 次仍失败，请换一种查询思路"}
```

| 错误类别 | 处理 |
|---|---|
| 守卫拦截 | 直接拒绝，返回"仅支持只读 SELECT" |
| 语法错误 | 回喂原始报错（脱敏后）让模型重写 |
| 列名不存在 | 提示模型"先 describe_table 确认列名" |
| 超时 | 建议加 LIMIT / 拆查询 |
| 连接失败 | 指数退避重试 2 次后放弃 |

> 💡 关键技巧：**把"工具使用建议"写进错误信息**——"列名 products.price 不存在，请先调用 describe_table"——模型会照做，自纠错成功率大幅提升。

## 6. 完整 Agent 循环示例（Python）

```python
from langchain_community.agent_toolkits import SQLDatabaseToolkit
from langchain_community.utilities import SQLDatabase
from langchain_openai import ChatOpenAI

db = SQLDatabase.from_uri("sqlite:///app.db", sample_rows_in_table_info=3)
llm = ChatOpenAI(model="deepseek-chat", temperature=0)

toolkit = SQLDatabaseToolkit(db=db, llm=llm)
tools = toolkit.get_tools()   # list_tables / schema / query_checker / query

SYSTEM = """你是数据分析师。规则：
1. 先 list_tables 查看可用表，再 describe 相关表
2. 只查询需要的列，禁止 SELECT *
3. LIMIT 结果默认 5 条
4. 执行前用 query_checker 复查；出错根据报错修正重试
5. 严禁 DML/DDL，你只有只读权限"""
```

> ⚠️ 即便工具链内置校验，**数据库角色只读仍是前提**（03 篇）——LangChain 的 query_checker 也只是"模型自查"，不是安全边界。

## 6.5 工具定义的 JSON Schema（给模型的"说明书"）

工具描述即模型的行为说明书——写得好坏直接决定模型调用质量：

```json
{
  "type": "function",
  "function": {
    "name": "query",
    "description": "对数据库执行只读 SELECT 查询。返回最多 max_rows 行。"
      "仅用于读；任何写操作请调用 propose_change（需人工审批）。"
      "结果可能被截断，必要时缩小查询范围。",
    "parameters": {
      "type": "object",
      "properties": {
        "sql": {
          "type": "string",
          "description": "完整 SELECT 语句，必须引用 schema 中真实存在的表与列；"
            "如不确定列名，先调用 describe_table"
        }
      },
      "required": ["sql"]
    }
  }
}
```

| 描述要点 | 作用 |
|---|---|
| 声明只读 + 指向写工具 | 防止模型误用 query 执行写操作 |
| 提示"先 describe_table" | 减少编造列名（最常见的失败） |
| 提示结果截断 | 模型会主动缩小范围而不是抱怨数据不全 |
| 参数即决策 | 只暴露 sql 一个参数，降低误用面 |

## 7. 性能与成本

| 项 | 手段 |
|---|---|
| schema 缓存 | describe_table 结果缓存（5 分钟 TTL），避免每次元数据查询（实测 120ms→<15ms） |
| few-shot 缓存 | 向量检索历史成功 SQL 作为样例（见 02 篇 6 节） |
| 工具调用上限 | 单轮任务工具调用 ≤8-12 次，防死循环 |
| Token 预算 | 结果回传上限（4KB 截断）+ schema 上下文预算（≤20 表） |
| 并发节流 | 同用户查询队列，防并行风暴 |

### 7.1 监控指标（工具链健康度）

| 指标 | 信号 |
|---|---|
| 工具调用成功率 | 下降 → 模型选错工具/参数 |
| 单轮平均工具调用数 | >8 → 探索效率低，schema 上下文不足 |
| 查询平均耗时 | 升高 → 缺 LIMIT/索引差 |
| 首查错误率 | 升高 → schema 描述与真实结构不符 |
| 结果截断率 | 高 → 模型查询范围过大，few-shot 待补 |
| 守卫拦截率 | 升高 → 模型被注入或描述误导 |

## 7.2 与 Text-to-SQL 现状的对照

工具链的每个设计决策都对应 [02 模块](02-核心模式：Text-to-SQL现状与演进.md) 的基准事实：

| 02 篇结论 | 本模块的落地 |
|---|---|
| 企业 schema 准确率仅 ~39%，差距在业务规则 | describe 带样例行、口径注入、按域拆分 |
| 执行反馈是最高性价比纠错手段 | safe_query 报错回喂 + 附工具使用建议 |
| 测试时扩展（多候选）SOTA 但贵 | 仅高价值查询开启多候选，默认单次生成 |
| schema 链接是前处理关键 | 工具描述引导"先 describe 再写列名" |

> 💡 工程取舍的参照系：**每加一个"模型能力项"（多候选/RL 微调）都要先确认工程项（口径/样例/缓存）已做满**——基准数据支持先工程后模型。

## 8. 工具链自检清单（上线前逐项打勾）

```text
□ 只读工具走只读角色连接；守卫层 + 数据库层双重只读
□ 工具描述准确：声明只读、提示先 describe、说明截断规则

□ 强制 LIMIT + 语句超时 + 单条语句
□ 错误脱敏后回喂模型；附"工具使用建议"

□ schema 缓存 + 按域拆分（≤20 表/次）
□ 工具调用上限 12 次、同一错误重试 ≤3 次
□ 监控指标接线（成功率/耗时/拦截率/截断率）
□ 审计日志含完整 SQL/耗时/行数
```
