# 为什么 Agent 需要数据库交互

> Agent 的推理是"大脑"，数据库是"记忆与业务数据中枢"：它让 Agent 既能查业务事实（分析），也能改业务状态（操作），更能记住自己（持久化）。没有数据库的 Agent 只有上下文窗口那么大的世界。

## 1. 三类需求：Agent 为什么必须碰数据库

| 需求 | 问的问题 | 例子 | 对应模块 |
|---|---|---|---|
| 查询分析（读） | "现在是什么情况？" | "上月销量 Top10 商品"、"这个用户 VIP 等级" | 06 |
| 业务操作（写） | "帮我改变什么？" | 创建订单、更新状态、批量打标签 | 07 |
| 记忆持久化（存） | "我上次聊了什么？" | 会话历史、用户偏好、任务状态 | 05 |

> 🎯 核心要点：**读（分析）、写（操作）、存（记忆）是三个不同问题域**——安全策略、工具设计、失败模式各不相同，生产系统必须分而治之，不能一把 SELECT 走天下。

## 2. 数据库 vs 向量库 vs 文件：存储三兄弟的分工

| 维度 | 关系型数据库 | 向量数据库 | 文件/对象存储 |
|---|---|---|---|
| 数据形态 | 结构化表（行/列） | 高维向量 | 非结构化文档 |
| 查询方式 | SQL（精确/聚合/事务） | 语义相似度 TopK | 路径/全文检索 |
| 强项 | 业务事实、聚合分析、ACID | 相似性召回（RAG） | 大文件、源码、备份 |
| 弱项 | 语义模糊查询 | 精确计数/事务 | 无聚合计算 |
| Agent 角色 | **业务中枢+记忆** | 知识召回（RAG） | 素材与产出物 |

**典型组合**（2026 主流架构）：

```text
业务库（MySQL/PG）── 事实与状态（金额/订单/用户）
向量库（Milvus/PGVector）── 知识片段（RAG 召回）
文件存储（MinIO/本地）── 附件/报表/代码
```

> 💡 注意趋势：2026 年"一库化"兴起——Oracle AI Database / Snowflake / Redis 都把向量列、聊天历史、语义缓存塞进同一个库（见 [05 模块](05-Agent结构化记忆：会话与状态持久化.md)），中小项目一个 PG 可以同时当业务库+向量库。

## 3. 在 Agent 配套技术生态中的位置

```text
Agent（大脑）
├── 代码执行沙盒（手：执行不可信代码）
├── 联网搜索工具（眼：获取实时外部信息）
├── 前端演示界面（脸：交互呈现）
├── 数据库交互（记忆：结构化持久化 + 业务中枢）   ← 本文
└── 文档解析（口：读取外部文档）
```

数据库交互与"记忆"的关系最紧密，但不止于记忆：

| 能力 | 数据库角色 |
|---|---|
| 会话历史 | 前端界面刷新的底气（[前端演示界面](..%2F前端演示界面%2F00-前端演示界面总览.md) 05 篇 Data Layer） |
| 业务查询 | 客服/财务/运营 Agent 的核心工具 |
| 工具状态 | 执行沙盒的任务记录、搜索工具的结果缓存 |
| 长期记忆 | 用户偏好、事实、经验的结构化存储 |

## 4. 演进主线：从插件到一等公民

```text
V1 硬编码查询（函数写死 SQL，参数化输入）
 → V2 Text-to-SQL（模型生成 SQL，人审执行）
 → V3 工具化（list_tables / schema / query 多工具链 + 自纠错）   ← 当前主流
 → V4 Agent 化（写操作 HITL 审批、记忆自管理、MCP 统一接入）
```

| 阶段 | 特点 | 局限 |
|---|---|---|
| 硬编码 | 稳定、零风险 | 场景写死，Agent 无灵活性 |
| Text-to-SQL | 自然语言即可查库 | 准确率受限、风险大（裸 SQL 执行） |
| 工具化 | 链式探索 schema→生成→校验→执行→纠错 | 只读场景成熟，写操作仍悬 |
| Agent 化 | 审批闭环 + 记忆治理 + MCP 标准化 | 复杂，需全套治理 |

> 🎯 核心要点：**2026 年的最佳实践是"工具化 + Agent 化"的结合**——读走多工具链（V3），写走审批闭环（V4），一切封装成 MCP 工具（V4），见 [04](04-工具封装实战：连接查询与返回.md) 与 [08](08-MCP数据库服务器全景.md)。

## 5. 为什么必须专门讲安全

Agent 访问数据库与人类开发者访问数据库的差异是本质性的：

| 维度 | 人类开发者 | Agent |
|---|---|---|
| 输入 | 明确意图 | 自然语言，可能被提示注入劫持 |
| 生成 | 手写 SQL，天然可控 | 模型生成，概率性输出 |
| 权限 | 有边界意识 | 无边界意识，给什么权限用什么权限 |
| 审计 | 可追溯人 | 需专门日志链 |
| 错误 | 会停下思考 | 可能反复重试放大错误 |

> ⚠️ OWASP LLM06（Excessive Agency，过度代理）明确点名：**给 Agent 写权限当只需要读时，提示注入落地即灾难**。安全是数据库交互的"第一公民"，详细防线见 [03 模块](03-安全第一：Agent数据库访问防线.md)。

## 7. 成本与延迟意识

数据库交互不是免费的——三类成本要进架构预算：

| 成本 | 来源 | 治理 |
|---|---|---|
| Token 成本 | schema 上下文、工具定义、结果回传每次都占 token | 按域拆分 schema、结果截断 4KB、工具载荷精简（DBHub 1.4k tokens 范本） |
| 延迟 | 多轮工具调用链（探索→生成→执行→纠错） | schema 缓存、少轮次、查询超时 10s |
| 资源成本 | 全表扫描/无 LIMIT 拖垮数据库 | 强制 LIMIT + 慢查询告警 + 并发限制 |
| 事故成本 | 写操作失误/权限滥用 | 只读默认 + 写审批 + 审计（03/07 篇） |
| 维护成本 | schema 变更后准确率暴跌（案例：58%→97% 的恢复依赖动态元数据） | schema 缓存 + 变更检测 + 定期回归测试 |

> 💡 一条经验法则：**单轮查询任务的工具调用 ≤8-12 次、结果回传 ≤4KB、schema 上下文 ≤20 表**——超出这三个数的方案先优化结构，而不是加预算。

## 8. 心智模型：三个先决问题

接入任何数据库前先回答：

| 问题 | 决定 |
|---|---|
| 1. 只读还是要写？ | 只读=默认选择（角色+读副本）；要写=审批闭环 |
| 2. 表范围多大？ | 全库=上下文爆炸+风险面大；按业务域白名单（<20 表） |
| 3. 谁在什么条件下能访问？ | 专用低权限账号、来源受限、限流审计 |

> 🎯 核心要点：**数据库交互的本质是"把权限与正确性从人转移到机器"**——转移的正确姿势是：数据库层收权（只读角色）、应用层守卫（文本校验）、交互层审批（写操作 HITL）、全程留痕（审计）。
