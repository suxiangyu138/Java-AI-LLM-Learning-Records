# 写入场景：数据录入与审批

> 让 Agent 写数据库 = 把"改业务状态"的权力交给概率性系统。2026 共识：**写操作必须走 HITL 审批闭环 + 独立高权限账号 + 全量审计**——写入工具与只读工具从设计上就分家。

## 1. 为什么写操作不能像读操作一样放开

| 风险 | 后果 | 概率 |
|---|---|---|
| 模型理解错意图 | "把 A 的订单取消"误删全部 | 非零 |
| 提示注入劫持写工具 | 注入指令触发 DELETE | 真实发生过 |
| 参数越界 | 更新金额为负数/空值 | 非零 |
| 幂等缺失 | 重复执行双重扣款/双倍积分 | 高（重试机制放大） |
| 无审计 | 出事故无法定位 | 常见 |
| 事务缺失 | 半途失败留下脏数据 | 常见（重试加剧） |

> 🎯 核心要点：**读工具的错误是"数据拿错了"（可重试），写工具的错误是"数据坏了"（不可逆）**——不对称风险要求不对称设计。

## 2. 写入工具设计：与读工具彻底分家

| 设计决策 | 读工具 | 写工具 |
|---|---|---|
| 连接 | 只读角色 | **独立写账号**（最小 DML 权限，无 DDL） |
| 数据源 | 主库或读副本 | 仅主库 |
| 审批 | 无 | **必须 HITL 审批** |
| 语句 | SELECT | 白名单 INSERT/UPDATE/DELETE（禁 DROP/TRUNCATE/ALTER） |
| 幂等 | 天然 | 必须显式设计 |
| 审计 | 记录 | **全量审计 + 变更前后快照** |

```python
# 写工具骨架：三阶段（拟变更 → 审批 → 执行）
def propose_change(user_prompt: str) -> dict:
    """第一阶段：生成拟执行的 SQL + 影响预估，不执行"""
    sql = generate_sql(user_prompt)              # 模型生成
    impact = estimate_impact(sql)                # SELECT COUNT 预估影响行数
    return {"sql": sql, "impact": impact, "preview": fetch_preview(sql)}

def approve_and_execute(sql: str, approved_by: str) -> dict:
    """第二阶段：仅在人工批准后执行；返回变更前后快照"""
    before = snapshot(sql)                       # 受影响行变更前快照
    with write_conn() as c:
        c.execute("BEGIN")
        c.execute(sql)                           # 单条语句 + 参数化
        c.execute("COMMIT")
    log_audit(approved_by, sql, before)          # 审计：谁批准、改了什么
    return {"changed_rows": ..., "before": before}
```

## 3. HITL 审批闭环（写操作的生死线）

```text
用户 → 写工具调用 → 审批请求（拟变更 + 影响 + 预览）
   → UI 弹审批卡（谁/何时/影响行数/可看预览）
   → 批准 → 执行 → 结果 + 审计
   → 拒绝 → 原因回喂模型调整（"把范围限制到订单 1023"）
```

| 实现层 | 机制 | 参考 |
|---|---|---|
| 协议 | 工具调用标记 `needs_approval`，事件流发审批请求 | [前端演示界面](..%2F前端演示界面%2F08-Agent专属界面：思考过程与工具调用可视化.md) 控制平面 |
| 前端 | 审批卡片（AI SDK needsApproval / Chainlit Action） | 前端体系 07/05 篇 |
| 后端 | 一次性审批令牌，签名有效期 60s | 防重放 |
| 数据库 | 审批后仍走独立写账号 + 行级校验 | 03 篇 |

> ⚠️ 审批不是 UI 按钮，是**安全边界**：审批令牌必须一次性、绑定 SQL 指纹、超时失效——"点了同意但 SQL 已被替换"是常见绕过。

## 4. 幂等设计：写操作的第一法则

| 场景 | 幂等方案 |
|---|---|
| 创建订单 | 业务唯一键（订单号/外部流水号）UNIQUE，冲突则返回已存在 |
| 更新状态 | 状态机约束：`UPDATE ... WHERE status='pending'`（条件更新，重放不生效） |
| 加积分/扣款 | 用事务 + 条件：`UPDATE ... SET balance=balance-100 WHERE balance>=100` |
| 批量操作 | 任务表记录批次号，重试前查批次状态 |

```sql
-- 条件更新：天然幂等（第二次执行影响 0 行）
UPDATE orders SET status='cancelled'
WHERE id=$1 AND status='pending';
```

> 💡 让 Agent 的重试机制（指数退避）和幂等设计配合：**重试是写场景的常态，幂等是重试的通行证**。

## 5. 危险操作清单与硬拦截

| 操作 | 处置 |
|---|---|
| DROP/TRUNCATE/ALTER | **一律拒绝**（写账号也无此权限） |
| 无 WHERE 的 DELETE/UPDATE | 拦截（除非显式"清空"审批流） |
| 批量更新 > 阈值 | 分页执行 + 每页审批 |
| 修改敏感表（users/payments） | 额外确认 + 更高权限账号 |
| 跨表级联 | 事务内校验外键约束 |
| 存储过程/动态 SQL | 禁止 |

## 6. 事务与一致性

| 原则 | 做法 |
|---|---|
| 单条语句 | 一次工具调用只做一件事（禁多语句拼接） |
| 显式事务 | 写操作包在 BEGIN/COMMIT，出错 ROLLBACK |
| 校验前置 | 执行前应用层校验（必填/枚举/金额范围） |
| 变更快照 | 受影响行变更前快照入库（可回滚审计） |
| 关联一致性 | 需要多表变更时走服务端事务工具而非裸 SQL |

## 7. 审计：写操作的完整证据链

```sql
CREATE TABLE write_audit (
    id BIGSERIAL PRIMARY KEY,
    session_id TEXT,          -- Agent 会话
    tool_name TEXT,           -- 工具名
    sql_text TEXT,            -- 完整 SQL
    proposed_by TEXT,         -- 发起 Agent
    approved_by TEXT,         -- 批准人
    approved_at TIMESTAMPTZ,
    changed_rows INT,
    before_snapshot JSONB,    -- 变更前快照
    ip TEXT
);
```

| 审计项 | 价值 |
|---|---|
| 谁提议/谁批准/何时 | 追责闭环 |
| SQL + 前后快照 | 可回滚、可复现 |
| 变更行数 | 异常识别（一次 10 万行？） |
| 失败尝试 | 发现注入探测与反复重试 |

## 8. 落地检查单

```text
□ 写账号与读账号分离，写账号仅 DML 且无 DDL/FILE
□ 所有写工具调用必须 HITL 审批（一次性令牌 + SQL 指纹）
□ 幂等设计：唯一键/条件更新/批次号三选一
□ DROP/TRUNCATE/ALTER 物理不可执行（权限层）
□ 无 WHERE 的修改被拦截；批量超阈值分页审批
□ 写操作显式事务，变更前快照入库
□ 审计日志含提议人/批准人/SQL/前后快照
□ 敏感表（users/payments）双人确认或禁止直写
```

> 🎯 核心要点：**写入场景的本质是"把不可逆操作变成可审批、可回滚、可追溯的流程"**——权限（独立账号）、审批（HITL）、幂等（唯一键/条件）、审计（快照）四件套齐了，写工具才允许上线。

## 9. 审批令牌实现要点

```python
import hmac, hashlib, time

def create_approval_token(sql: str, tool: str, user: str, ttl=60) -> str:
    """一次性审批令牌：绑定 SQL 指纹 + 过期时间 + 签名"""
    fingerprint = hashlib.sha256(sql.encode()).hexdigest()
    payload = f"{tool}|{fingerprint}|{int(time.time()) + ttl}|{user}"
    sig = hmac.new(APPROVAL_SECRET, payload.encode(), hashlib.sha256).hexdigest()
    return f"{payload}|{sig}"

def verify_and_execute(token: str, sql: str) -> dict:
    tool, fp, expire_ts, user, sig = token.split("|")
    # 校验：签名 + 未过期 + SQL 指纹一致（防"同意 A 执行 B"）
    assert hmac.compare_digest(hmac.new(APPROVAL_SECRET,
        f"{tool}|{fp}|{expire_ts}|{user}".encode(), hashlib.sha256).hexdigest(), sig)
    assert int(expire_ts) > time.time(), "审批已过期，请重新提交"
    assert fp == hashlib.sha256(sql.encode()).hexdigest(), "SQL 与审批内容不一致"
    return execute_write(user, sql)   # 再走独立写账号 + 审计
```

| 防绕过项 | 手段 |
|---|---|
| 重放攻击 | 令牌一次性（执行后标记失效） |
| 偷梁换柱 | SQL 指纹绑定（批准的 SQL ≠ 执行的 SQL 直接拒绝） |
| 过期利用 | TTL 60s |
| 冒用审批人 | HMAC 签名 + 用户字段 |

## 10. 危险操作分级表（按需启用不同审批强度）

| 级别 | 操作示例 | 审批强度 |
|---|---|---|
| L0 | 插入新记录（无敏感字段） | 普通审批 |
| L1 | 更新业务状态（订单发货） | 普通审批 + 影响行数确认 |
| L2 | 批量更新/删除（>100 行） | 双人审批 + 分页执行 |
| L3 | 触碰敏感表（users/payments） | 禁止直写，走服务端专用 API |
| L4 | DDL（建表/改表） | 一律拒绝（写账号无此权限） |

## 11. 写工具的测试清单（上线前必跑）

| 测试 | 验证点 |
|---|---|
| 注入演练 | 提示词注入 + SQL 拼接注入 → 均被拦截、审计留痕 |
| 幂等重放 | 同一写请求重放 2 次 → 第 2 次影响 0 行（条件更新） |
| 审批绕过 | 过期令牌 / 改 SQL / 重放令牌 → 全部拒绝 |
| 越权尝试 | 用写工具执行 DROP/ALTER → 权限层拒绝 |
| 无 WHERE 修改 | 全表 UPDATE/DELETE → 守卫拦截 |
| 批量超限 | 超阈值批量 → 分页 + 二次确认 |
| 事务回滚 | 模拟中途失败 → 数据回到变更前（快照比对） |
| 审计核验 | 每条写操作可查：谁/何时/改了什么/前后快照 |

> 💡 写操作与 [05 模块](05-Agent结构化记忆：会话与状态持久化.md) 的联动：审批结果与变更快照本身就是 Agent 记忆的一部分——"用户上次改了订单 1023 的状态"这类事实入 claim 表后，Agent 后续对话能正确引用自己的操作历史，避免"改完又问改没改"的失忆。
