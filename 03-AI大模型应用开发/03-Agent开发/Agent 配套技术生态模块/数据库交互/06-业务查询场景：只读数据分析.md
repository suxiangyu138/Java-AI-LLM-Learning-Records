# 业务查询场景：只读数据分析

> "帮我看看上个月的销售情况"——查询类 Agent 是 Text-to-SQL 最成熟、最赚钱的场景。本章把只读分析的完整套路讲透：角色与副本、schema 上下文工程、few-shot、结果叙事。

## 1. 场景定位与适用范围

| 维度 | 说明 |
|---|---|
| 典型用户 | 运营/财务/客服，不懂 SQL |
| 典型问题 | 趋势、排行、对比、明细、异常 |
| 成功率现实 | 学术基准 75%+，**企业 schema 只有 ~39%**（见 02 篇） |
| 关键前提 | 只读角色 + 读副本（03 篇），本文不再重复安全 |

> 🎯 核心要点：查询 Agent 的成败不在"模型会不会写 SQL"，而在**上下文里有什么**——schema 是否可消化、口径是否说清、样例是否给足。

## 2. 架构：查询 Agent 的标准链路

```text
用户问题
  → 1. 意图解析（查询？范围？指标？）
  → 2. Schema 探索（list_tables → describe 相关表）
  → 3. SQL 生成（schema + 口径 + few-shot）
  → 4. 校验执行（只读守卫 + LIMIT + 超时）
  → 5. 自纠错（报错回喂重写 ≤3 次）
  → 6. 结果叙事（数据 → 结论 + 图表建议）
```

| 环节 | 关键动作 | 失败重灾区 |
|---|---|---|
| 意图解析 | 区分"查数"与"聊天" | 把闲聊当真查询 |
| Schema 探索 | 只摸相关表（≤3 张/次） | 全库 schema 灌上下文 |
| SQL 生成 | 用样例行理解脏数据 | 空值/类型错乱 |
| 校验执行 | 守卫 + 超时 | 无 LIMIT 全表扫描 |
| 自纠错 | 报错回喂重写 | 同错误反复重试 |
| 结果叙事 | 结论先行 + 引用数据 | 只给裸表格 |

## 3. Schema 上下文工程（决定成败的关键细节）

### 3.1 表选择：按业务域拆，别全塞

| 做法 | 效果 |
|---|---|
| 全库 schema 注入 | 20+ 表 → 上下文溢出，准确率暴跌 |
| 按域拆分（订单域/用户域） | 每域 ≤20 表，schema 预算可控 |
| 表名索引层 | 先给"表名+一句话职责"清单，让模型选 |

### 3.2 样例行：理解脏数据的钥匙

```text
描述表 orders：
  CREATE TABLE orders (id, user_id, status, amount TEXT, created_at)
  样例: ('1023', 42, 'paid', '129.00', '2026-07-01 10:23:05')
        ('1024', 43, 'REFUNDED', '0', '2026-07-01 11:02:11')
```

- `amount TEXT` 是字符串 → 模型自动知道要 CAST。
- 状态枚举出现 `REFUNDED` 大写 → 模型知道比较要精确匹配。

### 3.3 口径注入：业务规则文档化

```text
【口径定义】
- 有效订单 = status IN ('paid','delivered') 且 amount > 0
- 销售额 = SUM(amount) 按支付时间（paid_at）归期
- "上月" = 自然月（UTC+8）
```

> 💡 2026 报告明确指出：**context layers（口径/合法连接/业务规则）是拉平企业与学术准确率差距的第一杠杆**，见 02 篇。

## 4. few-shot：用"历史成功查询"喂样例

| 方式 | 做法 |
|---|---|
| 静态 few-shot | 每类问题（排行/趋势/对比）预置 2-3 条优质样例 |
| 动态检索（2026 主流） | 新问题 embedding → 向量检索最相似的**历史成功 SQL** 作样例 |
| 样例质量 | 只存"已验证正确"的查询；错误查询不入库 |

```text
【相似问题范例】
Q: "上月销量最高的商品？"
SQL: SELECT p.name, SUM(o.amount) AS sales FROM orders o
     JOIN products p ON o.product_id = p.id
     WHERE o.status='paid' AND o.paid_at >= '2026-07-01' AND o.paid_at < '2026-08-01'
     GROUP BY p.name ORDER BY sales DESC LIMIT 5
```

## 5. 结果叙事：从裸数据到"人话"

```python
def narrate(question: str, rows: list) -> str:
    if not rows:
        return "查询无结果。可能原因：① 该时段无数据 ② 过滤条件过严 ③ 状态口径不同——请确认。"
    top = rows[0]
    return (
        f"**结论**：{top['name']} 领先，{top['sales']} 单。\n"
        f"**明细**（前 {len(rows)} 条）：\n" + to_markdown(rows) + "\n"
        "💡 需要的话我可以：按周拆分看趋势 / 对比去年同期 / 导出明细。"
    )
```

| 叙事原则 | 例子 |
|---|---|
| 结论先行 | "无线耳机领跑，7 月 1.2 万单" |
| 口径透明 | "销售额=已支付订单（含退款已剔除）" |
| 数据可核 | 附 Markdown 表格或图表 |
| 边界透明 | "仅统计 paid 状态，退款单未计入" |
| 空结果给线索 | "可能是状态口径不同" |
| 给下一步 | "要看周趋势吗？" |

## 6. 查询质量控制

| 手段 | 说明 |
|---|---|
| query_checker | 执行前让模型自查一遍（LangChain 内置，防低级错误） |
| 计划预览 | 大查询先 EXPLAIN 看行数估计，超阈值提示用户确认 |
| LIMIT 钳制 | 默认 100 上限 1000；聚合查询除外（COUNT 不受限） |
| 死循环防护 | 工具调用上限 8-12 次；同一错误重试 >3 次切换策略 |
| 慢查询告警 | >5s 的查询记录 + 慢查询日志归因 |
| 缓存 | 相同问题短 TTL 缓存（如 60s），降成本提速 |
| 一致性 | 同一问题短时间重复查询结果一致（缓存/快照），供前端"查看 SQL"溯源 |

## 7. 常见失败模式与对策

| 失败 | 例子 | 对策 |
|---|---|---|
| 编造列名 | `SELECT refund_rate FROM orders`（不存在） | describe 后再写；报错提示列清单 |
| 连接错误 | orders 直接 join users（缺中间表） | 口径文档写明合法连接路径 |
| 聚合口径错 | 退款单计入销售额 | 口径注入 + few-shot 覆盖 |
| 时区错乱 | 按 UTC 统计"今天" | 口径写明时区；日期列统一 |
| 数据为空误报 | 无结果就说"没数据" | 空结果给排查线索 |
| 幻觉叙事 | 结论超出数据范围 | 结论必须能追溯到查询结果 |

> 🎯 核心要点：查询 Agent 的工程重心依次是 **schema 上下文（可消化）→ 口径（可说清）→ few-shot（可模仿）→ 叙事（可信）**——前三者决定准确率，后者决定信任度，一个都不能省。

## 8. 查询 Agent 与前端界面的配合

查询结果不是终点，界面呈现是信任的最后一公里（衔接[前端演示界面](..%2F前端演示界面%2F00-前端演示界面总览.md)体系）：

| 界面元素 | 查询 Agent 的用法 |
|---|---|
| 工具卡片 | 显示"正在查询 orders 表 / 影响 347 行"，过程透明 |
| 表格组件 | 结果直接渲染 DataFrame/表格，可排序 |
| 图表建议 | Agent 建议"按周拆分看趋势"→ 前端自动出图（ECharts/Plotly） |
| 引用溯源 | 结论后附"数据来源：SELECT ...（2026-08-07 10:23 查询）" |
| 下载导出 | 一键导出 CSV/Excel（BI 化） |
| 缓存指示 | 显示"结果来自缓存"（60s TTL 时），避免用户误解实时性 |

```text
查询 Agent 输出 → {结论, 明细表, 图表类型建议, 查询 SQL, 查询时间}
前端渲染 → 结论卡片 + 表格 + 图表按钮 + "查看 SQL"折叠
```

> 💡 给用户的"查看 SQL"折叠是最便宜的信任构建——业务用户看到真实查询，比任何口头解释都可信。

## 9. 慢查询与成本治理

| 手段 | 做法 |
|---|---|
| 查询缓存 | 相同问题 60s TTL 缓存（结果+SQL），降本提速 |
| 慢查询告警 | >5s 记录并告警，归因（缺索引/无 LIMIT/大表扫描） |
| 并发上限 | 同用户 1-2 并发，防并行风暴拖垮库 |
| 结果压缩 | 大结果集先聚合摘要再回传（如"按状态分组统计"而非全量行） |
| 降级策略 | 高峰期只读查询走分析副本，主库仅供写 |
| 实时性标注 | 缓存命中的结果界面标注"缓存于 HH:MM"，避免用户误读为实时 |
| 降级预案 | 数据库不可用时提示"查询服务暂不可用"并展示最近缓存结果 |
