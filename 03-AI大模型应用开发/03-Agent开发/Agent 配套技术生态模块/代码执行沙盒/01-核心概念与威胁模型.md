# 核心概念与威胁模型

> 为什么 Agent 必须沙盒化 + 隔离层级全景：LLM 生成的代码默认不可信——不隔离，一次提示注入就能让宿主沦陷。本文是全体系地基。

## 1. 为什么需要沙盒

Agent 的本质是"模型 + 工具 + 循环"。代码执行工具（Code Interpreter、终端、脚本运行）赋予 Agent 任意代码能力，但代码由 LLM 生成，**LLM 的输出不可信**：

| 不可信来源 | 示例 | 本质 |
|---|---|---|
| 模型幻觉/推理错误 | 写出 `rm -rf` 类危险命令、无限循环、资源耗尽 | 能力不足 |
| 提示注入（直接） | 恶意 prompt 让模型生成恶意代码 | 被攻击者利用 |
| 提示注入（间接，2026 主流） | 网页/PDF/README 中隐藏恶意指令，Agent 读取后被篡改意图 | 被攻击者利用 |
| 工具输出污染 | 上游 API 返回内容携带恶意指令 | 被攻击者利用 |
| 模型被攻破/API 泄露 | 攻击者直接控制生成内容 | 被攻击者利用 |

沙盒不解决"模型是否聪明"，解决"**即使代码是恶意的，也造成不了伤害**"。这是语义层防线（提示词、对齐）与物理层防线（OS 隔离）的分工——提示注入可以在语义层欺骗模型，但隔离边界在 OS 层物理生效。

> 🎯 核心要点：沙盒是 Agent 体系的最后一道物理防线，纵深防御的兜底层。所有语义层防护失效后，它仍然生效。

## 2. 核心概念

| 概念 | 说明 |
|---|---|
| 沙盒（Sandbox） | 隔离不可信代码执行的环境，限制文件/网络/进程/资源访问 |
| 信任边界 | 数据或代码可信度发生变化的点；沙盒即 Agent 体系中最重要的信任边界 |
| 纵深防御 | 多层独立防线叠加：沙箱 + 网络策略 + 权限 + 审计，单层失效不致命 |
| 最小权限 | 只授予任务所需的最小能力：白名单路径、白名单域名、配额内资源 |
| 会话（Session） | 沙盒的存活周期；Agent 任务通常一次执行一个沙盒会话 |
| 冷启动 / 温池 | 冷启动=创建耗时；温池=预创建沙盒池消除冷启动（OpenSandbox O(1) 批量创建） |
| 快照 | 冻结沙盒内存+磁盘状态，之后秒级恢复（长任务/调试关键能力） |
| 数据驻留 | 沙盒运行的地域/基础设施归属（E2B 美欧双区、BYOC 企业自控） |

## 3. 威胁模型（攻击者视角）

### 3.1 攻击入口

1. **直接提示注入**：用户输入恶意 prompt → 模型生成恶意代码
2. **间接提示注入**（2026 主流）：恶意文件（README/CSV/PDF）、恶意网页被 Agent 读取后注入指令——无需直接对话即可发起
3. **供应链**：恶意依赖包、恶意 MCP 工具、恶意模板镜像

### 3.2 攻击目标

| 目标 | 手段 | 后果 |
|---|---|---|
| 数据窃取 | 读宿主环境变量/密钥/文件 → 外传 | 凭据、PII、源码泄露 |
| 持久化 | 写启动项、后门、挖矿驻留 | 长期驻留 |
| 横向移动 | 逃逸后利用宿主网络访问内网 | 内网渗透 |
| 资源滥用 | 挖矿、代理、DDoS | 成本损失 |
| 服务中断 | fork 炸弹、OOM、磁盘写满 | DoS |

### 3.3 2026 经典攻击链

```text
恶意网页/仓库 → Agent 读取（间接提示注入）→ 模型生成恶意代码/命令
→ 沙箱内执行 → [逃逸] → 宿主任意代码执行 → 窃取凭据 → DNS 隧道外泄
```

> ⚠️ 2026-05 微软披露：提示注入在 Semantic Kernel 中达到宿主级 RCE；OpenClaw 四连环漏洞（CVSS 9.6）证明"链式利用"已成为标准攻击范式。2026 漏洞详情见 [09-安全攻防案例与加固](09-安全攻防案例与加固.md)。

## 4. 隔离层级全景（六层光谱）

| 层级 | 技术 | 隔离强度 | 冷启动 | 关键说明 |
|---|---|---|---|---|
| L1 语言级 | WASM / QuickJS / Pyodide / RestrictedPython | 弱-中 | 微秒级 | 解释器层限制，无 OS 访问；**Pyodide 不能当安全边界** |
| L2 进程级 | 受限 token / Landlock / seccomp 组合 | 中 | 毫秒级 | OS 原语组合，需逐层正确配置 |
| L3 容器 | Docker / Podman / runc | 弱 | <1s | 共享宿主内核，**内核漏洞=逃逸** |
| L4 用户态内核 | gVisor / Kata | 中强 | 50-100ms | 系统调用不触达真实内核，兼容性有损 |
| L5 微虚拟机 | Firecracker / Cloud Hypervisor | 强（业界默认） | ~125ms | 每沙箱独立内核，攻破需打穿 hypervisor |
| L6 机密计算 | AMD SEV-SNP / Intel TDX | 最强 | - | 内存硬件加密，2026 仍处前沿未实用化 |

### 各层级代表实践

| 场景 | 层级 | 代表方案 |
|---|---|---|
| 快速原型 / 低风险代码 | L1 | WASM 沙箱（QuickJS/MicroQuickJS） |
| 本地开发环境 | L2 | Codex 三策略、Claude Code sandboxed Bash |
| 可信内部代码执行 | L3 | 内部 CI 容器、自研工具链 |
| 高并发托管沙箱 | L4 | ChatGPT Code Interpreter、Modal |
| 最高隔离多租户 | L5 | E2B、Vercel Sandbox、AWS Lambda MicroVMs |
| 合规敏感数据 | L6 | 金融/政府前沿探索 |

### 2026 行业共识

- **"每个超大规模厂商都拿最强隔离原语对准 AI，没有一家选容器"**——微软 Semantic Kernel 2026-05 提示注入达宿主级 RCE 佐证容器不足
- ChatGPT 用 gVisor（务实选择：K8s 节点本身是 VM，无 /dev/kvm）；E2B/AWS Lambda/Vercel 用 Firecracker
- 结论：**容器只适合可信内部代码；不可信 LLM 代码默认 L4/L5**

## 5. 安全属性 vs 安全事实（评估红线）

| 厂商宣称 | 2026 实测/披露 | 教训 |
|---|---|---|
| "完全隔离" | AWS AgentCore Code Interpreter 允许出站 DNS → DNS 隧道外泄 | 隔离声明要按信道逐项验证 |
| "沙箱已过滤" | Claude Code SOCKS5 空字节注入绕过出站白名单（2025-10-20 至 2026-03-31 暴露） | 过滤器本身是新攻击面 |
| "只读沙箱" | Pyodide on node 可执行任意 JS（CVE-2026-24002），非安全边界 | 语言级沙箱≠OS 级沙箱 |
| "权限最小化" | 沙箱进程持有用户全部凭据，逃逸即完全接管 | 凭据短时化、作用域化、网络边界注入 |

> 🎯 核心要点：评估沙箱时，把"隔离声明"翻译成"具体信道清单"（文件、网络、DNS、进程、IPC、时钟…），逐项验证后再信任。DNS 是最常被漏掉的信道。

## 6. 选型第一原则

```text
威胁等级 = f(代码来源可信度, 数据敏感度, 多租户规模)
├── 可信代码 + 内部网络     → L3 容器（够用）
├── 半可信 + 少量租户       → L4 gVisor（性价比甜区）
├── 不可信 + 多租户         → L5 Firecracker（业界默认）
└── 极高敏 + 合规强制       → L6 机密计算（观察期）
```

> 💡 预算紧张可 L3 + gVisor runtime 升级到 L4；需要 GPU 注意平台差异（E2B 无 GPU，Modal/Daytona 有）。完整选型见 [10-生产实践与面试冲刺](10-生产实践与面试冲刺.md)。

## 面试速记

1. 沙盒解决"LLM 输出不可信"——即使代码恶意也造成不了伤害，是 Agent 最后一道物理防线。
2. 2026 标准攻击链：间接提示注入 → 沙箱内执行 → 逃逸 → 凭据窃取 → DNS 外泄。
3. 六层隔离光谱：语言级→进程级→容器→用户态内核→微VM→机密计算，强度/成本递增。
4. 容器共享内核是天生弱点，内核漏洞即逃逸面；不可信代码业界默认微VM。
5. 隔离声明不可信，按信道清单验证；DNS 是最常被漏掉的信道。
