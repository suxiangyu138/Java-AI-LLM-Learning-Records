# 性能优化与成本治理

> 搜索是 Agent 成本结构中"看不见的大头"：一次研究任务可发 10-20 次查询、每次带数千 token 内容。本文给出缓存、限流、分层供应商与成本模型。

## 1. 成本结构拆解

```text
单次搜索成本 = 查询费（API 按次） + 提取费（抓取页面） + Token 费（内容进上下文）
研究任务成本 = 单次搜索成本 × 搜索轮数 × 平均内容长度
```

**典型数量级**（研究任务）：

| 项 | 数量级 |
|---|---|
| 查询次数 | 5-15 次/任务 |
| 每查询入上下文内容 | 2-10k token |
| 一次任务总 token | 20-150k |
| 主导成本 | **Token 费 > 查询费**（查询 $0.004-0.008 级，Token 按模型计费） |

> 🎯 核心要点：**省钱的第一杠杆不是换便宜查询 API，而是减少"垃圾内容入上下文"**——动态过滤与 `response_inclusion` 就是为此设计。

## 2. 缓存策略（成本下降 50-90%）

| 层 | 缓存内容 | TTL 建议 | 命中收益 |
|---|---|---|---|
| 查询结果级 | 搜索 API 原始响应 | 新闻 5min / 稳定 24h | 免查询费 |
| 提取内容级 | 页面 Markdown（按 URL） | 稳定页 7 天 | 免抓取费+免解析 |
| 答案级 | 最终综合答案 | 按任务类型 | 整任务免重算 |
| 供应商级 | `external_web_access: cached`（OpenAI） | 平台缓存 | 平台级降本 |

```python
# 查询级缓存（Redis）
cache_key = f"search:{sha256(query)}:{freshness}"
if hit := redis.get(cache_key):
    return hit
result = search_api(query, freshness=freshness)
redis.set(cache_key, result, ex=ttl_by_freshness(freshness))
```

> ⚠️ 缓存与新鲜度必须联动：新闻类查询禁缓存（`live`），否则答错版本/价格；"缓存命中率"与"答案新鲜度"是 trade-off。

## 3. 限流与重试

### 3.1 三层限流配额

| 配额 | 来源 | 特征 |
|---|---|---|
| 模型 token 限流 | 模型平台 | 常规，可重试 |
| **服务端工具限流**（Claude web_search） | 工具配额 | **HTTP 200 + 体内 `too_many_requests`，重试无效** |
| 第三方 API 配额 | 供应商 | 429，退避重试有效 |

### 3.2 重试规范

| 场景 | 策略 |
|---|---|
| 429（第三方） | 指数退避 + 抖动：1s→2s→4s→8s，上限 3-5 次；带 `Retry-After` 则尊重 |
| 服务端工具限流 | **不重试**，降级（缓存 → 模型知识 → 告知用户） |
| 超时（10s） | 单次重试 + 切备用供应商 |
| 500/5xx | 切备用供应商（生产双供应商的价值） |

## 4. 并发控制

```text
单任务并发上限 = min(供应商配额, 任务预算, 检索相关性需求)
```

| 场景 | 并发建议 |
|---|---|
| 多查询并行 | 3-8 并发（研究任务），`asyncio.gather` 或框架 ToolNode |
| 页面提取 | 2-4 并发/域名（礼貌爬虫：每域名 1 并发 + 延迟） |
| 极端场景 | pi-codex-search 支持 1-32 并行查询——按预算选 |

## 5. 分层供应商（Tiered Providers）

```text
第一层（廉价/免费）：Brave 免费层 / Tavily basic / Serper —— 大多数查询在这层完成
第二层（增强）：Exa 语义 / Tavily advanced —— 第一层结果弱时升级
第三层（兜底）：备用供应商（不同索引/不同失败模式）
```

| 场景 | 分层动作 |
|---|---|
| 简单事实查询 | 第一层 basic depth 够用 |
| 结果相关性差 | 升级第二层（advanced 深度 / 语义检索） |
| 第一层限流/故障 | 自动切第三层 |
| 精确技术查询 | 直接 Exa keyword 模式或 `site:` 语法 |

> 💡 分层的本质：**便宜先打，贵在刀刃上**——90% 查询用不到 advanced，省下的钱投在 10% 关键查询上。

## 6. Token 优化清单

| 手段 | 收益 |
|---|---|
| 动态过滤（Claude 默认） | **输入 token -24%**（官方基准） |
| `response_inclusion: "excluded"` | 多步 Agent 丢弃已消费结果块，输出 token 大降 |
| 只提取 top-N（3 条而非 10 条） | 内容量 -70% |
| 内容截断（每源 ≤4000 字符 / 段落级提取） | 上下文瘦身 |
| 摘要先行（先发摘要入上下文，需要再取全文） | 首轮 token -80% |
| 引用不计 token（Claude cited_text） | 引用免费 |
| 缓存 + 模型知识优先 | 搜索次数本身减少 |

## 7. 成本治理闭环

```text
记账（每任务记录：查询数×单价 + token 数×单价 + 提取数）
→ 分析（单任务成本 / 每成功答案成本 / 缓存命中率）
→ 路由（预算内用便宜层，超出降级：advanced→basic→模型知识）
→ 复盘（高频查询固化进缓存/RAG 知识库，从"每次搜"变"不再搜"）
```

**关键指标**：

| 指标 | 定义 | 健康值 |
|---|---|---|
| 每成功答案成本 | 总成本 ÷ 成功答案数 | 持续下降 |
| 缓存命中率 | 命中 ÷ 总查询 | >40% |
| 无效搜索率 | 结果未采信的比例 | <30% |
| 查询/任务 | 平均搜索次数 | 事实 1-3 / 研究 5-15 |

## 8. 易错点

- 只比查询单价不比总成本：便宜 SERP + 自建爬虫常比一站式更贵
- 缓存不分新鲜度：新闻查缓存 = 答旧事
- 服务端工具限流当普通错误重试：浪费配额
- 单供应商单索引：一挂全挂
- 全量内容入上下文：Token 费爆炸
- 每任务从零搜起：高频查询应固化进知识库

## 面试速记

1. 成本主导是 Token 不是查询费——第一杠杆是减少垃圾内容入上下文（动态过滤 -24%）。
2. 缓存三档 TTL：新闻 5min / 稳定 24h / 答案级；新鲜度与命中率 trade-off。
3. 服务端工具限流（体内 too_many_requests）重试无效，降级处理。
4. 分层供应商：便宜先打、贵在刀刃、双供应商兜底。
5. 治理闭环：记账→分析→路由→复盘；高频查询固化进 RAG 知识库。
