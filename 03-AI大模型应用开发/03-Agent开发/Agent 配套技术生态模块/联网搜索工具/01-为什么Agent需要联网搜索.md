# 为什么 Agent 需要联网搜索

> 模型知识有边界、有截止日期；搜索给 Agent 实时之眼——搜索 vs RAG 的分工，是 Agent 检索能力的完整拼图。

## 1. 模型的三个先天不足

| 不足 | 表现 | 后果 |
|---|---|---|
| 知识截止 | 训练数据有截止日期（cutoff） | 问不到最新事件/版本/价格 |
| 幻觉倾向 | 不知道就编造，且"编得很自信" | 错误答案无来源可溯 |
| 长尾知识稀疏 | 小众领域/内部文档训练数据不足 | 回答浮于表面 |

**联网搜索解决的正是这三点**：实时性（最新资讯）、可溯源性（引用 URL）、覆盖度（长尾查询）。

> 🎯 核心要点：搜索是 Agent 的"外接实时知识接口"——模型负责理解与推理，搜索负责提供"现在的事实"。

## 2. 搜索 vs 模型知识 vs RAG

| 维度 | 模型知识 | 联网搜索 | RAG（知识库） |
|---|---|---|---|
| 数据源 | 训练语料 | 实时互联网 | 企业私有文档 |
| 时新性 | 截止到训练 | **实时** | 按索引更新 |
| 成本 | 无额外 | 按查询计费 | 按索引/存储 |
| 延迟 | 最低 | 中（0.5-3s） | 中 |
| 覆盖 | 广但浅 | 全网（受索引限制） | 特定域 |
| 可溯源性 | 无 | **URL 引用** | 文档引用 |
| 适用 | 常识/推理 | 实时资讯/长尾 | 私有知识/合规 |

**三者是互补关系，不是替代关系**：

```text
先模型知识（快、零成本）→ 不确定/需要新 → 搜索（实时）或 RAG（私有）
```

> 💡 Gemini Grounding 的 **dynamic retrieval** 就是这种分工的实现：模型自己判断"这个问题是否需要搜索"（"法国首都是哪"直接答，"最新电影票房"才搜）——省成本又保质量。

## 3. 搜索在 Agent 体系中的定位

Agent 配套技术生态（本目录体系）：

```text
Agent（大脑）
├── 代码执行沙盒（手：执行不可信代码）
├── 联网搜索工具（眼：获取实时外部信息）  ← 本文
├── 前端演示界面（脸：交互呈现）
├── 数据库交互（记忆：结构化持久化）
└── 文档解析（口：读取外部文档）
```

搜索工具是 Agent 的信息输入通道中最"宽"的一条：不依赖用户上传、不依赖内部数据，直接对接整个世界。

## 4. Agent 搜索的三类典型场景

| 场景 | 示例 | 关键要求 |
|---|---|---|
| 事实查询 | "2026 年 Redis 最新版本？""今天天气" | 准、快、引用 |
| 深度研究 | "对比五个向量数据库的 2026 基准" | 多轮、多源、交叉验证 |
| 持续监控 | 竞品动态、漏洞通告、价格跟踪 | 定时、增量、缓存 |

## 5. 搜索能力的演进路线

```text
2023-2024：工具调用（Tool Use）时代——Agent 调第三方 API，拼装搜索
2025：原生工具时代——OpenAI/Anthropic/Gemini 内建 server-side 搜索工具
2026：动态过滤 + 深度研究——搜索工具自动过滤结果、多步自主研究
未来：Grounding 索引——专为 AI 答案设计的"段落级检索 + 引用"索引
```

关键转折点：

- **2025-2026 原生工具**：Claude/OpenAI/Gemini 把搜索做进模型平台——模型自己决定何时搜、搜什么，结果带引用回传，不需要 Agent 开发者拼装
- **2026-02 动态过滤**：Claude 搜索工具自动写代码过滤结果，只把相关内容送进上下文——**准确率 +11%、输入 token -24%**（BrowseComp/DeepsearchQA 实测）
- **2026 Grounding 索引**：Bing 等开始构建"专为 AI 合成设计"的索引——按段落检索、强调事实保真与可归因（见 [02](02-搜索引擎原理与检索基础.md)）

## 6. 何时不该用搜索

| 情况 | 替代方案 |
|---|---|
| 常识/稳定知识 | 直接模型知识 |
| 企业私有数据 | RAG |
| 低延迟高并发查询 | 预构建缓存 + 批量更新 |
| 完全内网环境 | 内部索引（ES/OpenSearch）或禁止搜索 |

> ⚠️ 搜索不是免费的：每次查询都有延迟与成本，且结果本身可能是投毒内容（见 [08-搜索安全与内容信任](08-搜索安全与内容信任.md)）——"能不问就不问，问了就要交叉验证"。

## 7. 搜索的失败模式与对策（设计自检）

| 失败模式 | 表现 | 对策 |
|---|---|---|
| 索引盲区 | 搜不到（独立索引长尾有洞） | 双供应商互补；`site:` 直查目标域 |
| 语义错位 | 搜到相似但错误内容 | Exa keyword 模式 / 精确词查询 |
| 内容污染 | 结果被 SEO/投毒操纵 | 内容信任层（见 [08](08-搜索安全与内容信任.md)） |
| 新鲜度错配 | 答旧版本/旧价格 | 新鲜度策略：新闻强制 live 不缓存 |
| 上下文淹没 | 大量无关内容挤占窗口 | 动态过滤 / 只提取 top-N / 截断 |
| 成本失控 | 研究任务烧钱 | 预算上限 + 终止条件（见 [09](09-性能优化与成本治理.md)） |
| 限流误判 | 服务端配额当普通错误重试 | 识别体内错误对象，降级不重试 |

> 💡 设计搜索型 Agent 时先过一遍此表：每个失败模式都有明确对策，才算"可上线"。

## 面试速记

1. 模型三不足：知识截止、幻觉、长尾稀疏——搜索补实时性、可溯源、覆盖面。
2. 搜索 vs RAG：实时互联网 vs 私有文档，互补不替代；dynamic retrieval 是"模型自判要不要搜"。
3. 能力演进：工具调用 → 原生工具 → 动态过滤 → 深度研究 → Grounding 索引。
4. 动态过滤价值：准确率 +11%、输入 token -24%（Claude 2026-02）。
5. 搜索要"省着用"：有缓存/模型知识可答就不搜；搜了要验证来源。
