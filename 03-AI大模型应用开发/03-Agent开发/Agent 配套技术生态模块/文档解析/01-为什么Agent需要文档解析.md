# 为什么 Agent 需要文档解析

> Agent 的知识来自三处：模型训练、联网搜索、**用户给的文档**——文档是私有信息的主要载体。解析是让 Agent"读得懂"的第一步，解析错了，后面 RAG、问答、总结全部建立在沙子上。

## 1. 三类文档：解析难度的分水岭

| 类型 | 形态 | 解析难度 | 例子 |
|---|---|---|---|
| 可搜索文本 | PDF 带文本层 / DOCX / 网页 | 低（直接提取） | 数字化合同、导出的报告 |
| 半结构化 | 表格/版面复杂的 PDF | 中（需版面分析） | 财报、论文、发票 |
| 扫描件/图像 | 纯图片 PDF、照片、手写 | 高（需 OCR/VLM） | 扫描合同、老档案、扫描发票 |

> 🎯 核心要点：**解析失败的第一大根因是"文档类型判断错误"**——把扫描 PDF 当文本 PDF 提取，会静默得到空文本；把所有文档都送 OCR，又慢又贵。先分类，再选路。

## 2. 解析 vs 提取 vs 理解：三个层次

```text
提取（Extraction）    从文档里把字取出来（可能有版面错乱）
  → 解析（Parsing）   恢复结构：标题层级/表格/阅读顺序/页眉页脚
    → 理解（Understanding） 语义级：抽关键字段、答问题、总结
```

| 层次 | 输出 | 工具 | 失败表现 |
|---|---|---|---|
| 提取 | 纯文本流 | PyMuPDF/pdfplumber | 顺序乱、表格摊平、页眉混入 |
| 解析 | Markdown/JSON（含结构） | Docling、PaddleOCR-VL | 结构错、表格错 |
| 理解 | 字段/答案/摘要 | VLM、Agent 循环 | 幻觉、漏字段 |

> 💡 Agent 的文档工具链要**分层消费**：先解析出结构化结果，理解层（模型）只处理结构化的输入——跳过解析直接让模型读原始 PDF 是 2023 年的老路，2026 年已证实在复杂文档上成本高且不稳定。

## 3. 解析在 Agent 体系中的位置

```text
Agent（大脑）
├── 代码执行沙盒（手：执行不可信代码）
├── 联网搜索工具（眼：获取实时外部信息）
├── 前端演示界面（脸：交互呈现）
├── 数据库交互（记忆：结构化持久化）
└── 文档解析（口：读取外部文档）          ← 本文
```

文档解析与两个模块强耦合：

| 下游 | 依赖解析什么 | 解析失败的后果 |
|---|---|---|
| RAG 检索（[04-RAG检索增强生成](../../../04-RAG检索增强生成/00-RAG知识体系总览.md)） | 结构正确的 Markdown + 分块 | 检索召回噪声、表格数据丢 |
| 前端演示界面（[前端演示界面](../前端演示界面/00-前端演示界面总览.md)） | 引用溯源（页码/位置） | 无法定位来源，信任崩塌 |
| 数据库交互（[..%2F数据库交互%2F00-数据库交互总览.md](..%2F数据库交互%2F00-数据库交互总览.md)） | 结构化表格数据 | 无法入库分析 |

## 4. 解析错误的四种代价

| 错误 | 现象 | 代价 |
|---|---|---|
| 静默丢内容 | 扫描页返回空文本、表格摊平成乱码 | 回答"资料里没有"——**最贵，不可见** |
| 结构破坏 | 标题层级丢失、阅读顺序错乱 | RAG 分块错位，检索质量崩塌 |
| 幻觉性错误 | VLM 直读编造不存在的数值 | 字段提取"看起来很对"实际是编的 |
| 成本失控 | 全量送 VLM/商用 API | 每页 1-5 秒 + token 账单 |

> 🎯 核心要点：解析质量是"不可见的工程"——错误不报错，只让下游悄悄变差。因此解析必须**可评估**（基准指标见 02 篇）且**可路由**（简单文档别浪费贵引擎）。

## 5. Agent 文档处理的典型场景

| 场景 | 输入 | 解析需求 | 关键成功要素 |
|---|---|---|---|
| 合同问答 | 扫描 PDF | OCR + 版面 | 页码溯源、字段准确 |
| 财报分析 | 复杂表格 PDF | 表格结构化 | TEDS 高的引擎 |
| 论文综述 | 双栏 PDF | 阅读顺序 + 公式 | 公式转 LaTeX |
| 知识库导入 | 混合格式批量 | 全类型路由 | 分类→分块→入库流水线 |
| 发票录入 | 模板化扫描件 | 字段抽取 | 模板/区域抽取 |
| 网页资料抓取 | 动态 HTML | 去噪+正文提取 | 爬虫体系[阶段2-5]衔接 |
| 邮件/附件处理 | 混合格式 | 全类型路由 | 附件分类解析 |
| 知识库批量迁移 | 历史档案（扫描+数字化混合） | 页面级路由 | 混合文档逐页判定 |

> 💡 共性规律：**所有场景的第一步都是"分类"**——文件类型、有无文本层、表格密度，三个判断做完，解析引擎的候选就只剩一两个。这也是 [09 工具链](09-Agent文档解析工具链.md) 路由入口的设计基础。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "解析就是把字提出来" | 结构（表格/层级/顺序）比字更重要——摊平的文字流喂 RAG 是灾难 |
| "爬虫抓到的网页不用解析" | 网页正文需去噪（导航/广告）——爬虫负责抓、解析负责净 |
| "扫描件也能直接提取" | 扫描 PDF 无文本层，提取静默为空——必须先 OCR |
| "最贵的引擎最好" | 简单文档用贵引擎是浪费；路由式混合（便宜打底+贵兜底）才是最优 |
| "VLM 看图什么都能读" | 能读但会编——幻觉需要交叉验证，不能直接进业务 |
| "换引擎不用回归" | 解析器版本升级可能悄悄变差——自有基准必须回归 |
| "解析一次一劳永逸" | 文档更新/引擎升级后缓存失效，需增量重解析 |

## 9. 心智模型：三问定方案

| 问题 | 决定 |
|---|---|
| 1. 文档有文本层吗？ | 有 → 快库提取（PyMuPDF）；无 → OCR/VLM |
| 2. 表格/版面重吗？ | 重 → Docling/PaddleOCR-VL（TEDS 高者）；轻 → 任意 |
| 3. 数量与成本？ | 大批量同模板 → 便宜引擎+模板；少量高价值 → VLM/商用 API |
| 4. 下游要什么？ | 纯检索 → Markdown 分块；字段抽取 → JSON 结构化；问答 → 可结合 VLM 直读 |
| 5. 数据敏感吗？ | 涉密 → 全自托管（PaddleOCR-VL 本地）；可外发 → 商用 API 省事 |

> 🎯 核心要点：**解析架构 = 路由 + 分层**——先按类型路由（文本/扫描/复杂版面），再按价值分层（便宜引擎打底、贵引擎兜底），这是 2026 年生产共识，也是本体系贯穿始终的主线。
