# 表格与版面结构化

> 表格是文档解析的"兵家必争之地"——摊平毁一切。本章讲透：表格识别（TEDS）、跨页合并、复杂表格的 Markdown vs JSON 双轨、版面分析的正确用法。

## 1. 为什么表格是成败关键

| 表格处理方式 | 后果 |
|---|---|
| 摊平成文本流 | 行列关系全毁——"Q1 收入 12.4M"与"Q1 成本 8.1M"无法对应 |
| 正确结构化 | 可检索、可入库、可问答（"2025Q3 利润多少"） |
| 错误结构化 | 行列错位——比没有更糟（回答"看起来对"实则错） |

> 🎯 核心要点：**表格必须作为"原子单元"保留结构**——任何把表格线性化的解析器输出，都不应该进入 RAG 或数据库。

## 2. 表格识别的度量与现状

| 指标 | 测什么 | 2026 现状 |
|---|---|---|
| TEDS | 表格结构相似度（行列树） | Docling 0.89（开源最强）；Nutrient 0.71-0.94 |
| 单元格正确率 | 格子内容对不对 | PaddleOCR-VL 表格理解 92.8（v1.5 第一） |
| 跨页完整性 | 跨页表格是否合并 | PaddleOCR-VL 自动合并；需手动兜底 |

| 引擎 | 表格能力 | 适用 |
|---|---|---|
| Docling | TEDS 0.89，跨页处理 | 数字化 PDF/表格重文档 |
| PaddleOCR-VL | 92.8 分，跨页自动合并 | 扫描件表格 |
| pymupdf4llm | TEDS 0.54-0.61（弱） | 表格少时兜底 |
| pdfplumber | 坐标级表格提取 | 简单规则表格、调试 |

## 3. 表格的三种结构化输出

| 格式 | 适用 | 局限 |
|---|---|---|
| Markdown 表格 | 常规表格、LLM 消费 | 合并单元格/嵌套表达不了 |
| JSON（规范） | 复杂表格（合并/嵌套/跨页） | 人读不便 |
| 按行分块（RAG） | 检索场景 | 需携带上下文（见 08 篇） |

```text
复杂表格（合并单元格/多级表头/跨页）
  → JSON 为规范格式（权威），Markdown 为衍生（给人看）
  → 简单表格 → Markdown 直接可用
```

```json
{
  "title": "季度收入表",
  "page_range": [3, 4],
  "headers": ["季度", "收入", "成本", "利润"],
  "rows": [
    {"季度": "Q1", "收入": 12.4, "成本": 8.1, "利润": 4.3},
    {"季度": "Q2", "收入": 15.2, "成本": 9.0, "利润": 6.2}
  ],
  "merged_cells": [{"from": [0, 0], "to": [0, 0]}]
}
```

## 4. 跨页表格：必须合并再入库

```text
第 3 页：| 产品 | Q1 |   （表头+前 20 行）
第 4 页：| 产品 | Q1 |   （重复表头+后 30 行）
           ↓ 合并
一张逻辑表：| 产品 | Q1 | （表头 1 次 + 全部 50 行）
```

| 实现 | 说明 |
|---|---|
| PaddleOCR-VL | 自动合并（begin/end 标记） |
| Docling | 内置跨页处理 |
| 手动兜底 | 检测"同表头连续页"拼接（table-preserving-doc-standard 方案） |

> ⚠️ 不合并的后果：检索第 3 页的"Q1 收入"答"12.4"，检索第 4 页答"12.4"但丢了下半年数据——分块各自为政，问答残缺。

## 5. 版面分析：解析的"骨架"

| 版面元素 | 解析动作 | 典型来源 |
|---|---|---|
| 标题层级 | 保留为分块边界 | Docling/PP-DocLayoutV2 |
| 阅读顺序 | 双栏/多栏正确还原 | NID 指标衡量 |
| 页眉页脚 | 剔除（防每页重复噪音） | Docling 配置 |
| 图表 | 区域标注 + 建议描述 | 图表问答 |
| 公式 | LaTeX 输出 | 数学场景 |
| 印章/水印 | 识别并剔除 | 扫描合同 |

```python
# Docling：配置化版面处理
from docling.document_converter import DocumentConverter

converter = DocumentConverter()
result = converter.convert("annual.pdf")
doc = result.document
md = doc.export_to_markdown()      # 标题层级/表格/列表全保留
# 版面元素（表格/图片/公式）带坐标，供引用溯源
```

## 6. 表格入库与检索的两种路线

### 路线 A：表格整体为块（RAG）

```text
整表 → 一个 chunk（可能超长）→ 检索命中后整表进上下文
适合：表不大（≤50 行）、问题多针对整表
```

### 路线 B：按行分块 + 摘要块（2026 主流）

```text
摘要块：标题+列名+页码范围（"季度收入表：Q1-Q4 收入/成本/利润"）
行块：每行一个 chunk，携带表头上下文（"季度: Q1 / 收入: 12.4M / 成本: 8.1M"）
```

| 路线 | 优点 | 缺点 |
|---|---|---|
| 整表为块 | 简单 | 大表超上下文；检索粒度粗 |
| 按行分块 | 检索精准、上下文省 | 需携带表头上下文；实现复杂 |

> 💡 混合：小表整块、大表按行——"原子块"原则不变（行内不可再切）。

## 7. 表格质量检查单

```text
□ TEDS/人工抽检：行列对应正确（抽查 10 个单元格）
□ 跨页表格已合并（页范围正确）
□ 合并单元格无信息丢失（JSON 保留 merged_cells）
□ 表头语义保留（每行块带列名上下文）
□ 空单元格 ≠ 丢失（区分"无值"与"提取漏了"）
□ 数字未变字符串化（保留类型）
□ 表格从未被摊平（纯文本输出中禁止表格）
```

> 🎯 核心要点：表格结构化的三原则——**不摊平、不拆分、不合并错**（表格保持原子、跨页先合并、合并单元格不丢信息）。做到这三点，表格才能从"解析产物"升级为"可检索资产"。

## 8. 表格问答实战：从解析到回答

```text
用户："2025Q3 利润是多少？"
  → 检索命中：季度收入表块（页码 3）
  → 上下文：整表 Markdown/JSON 注入
  → 模型回答："8.6M（2025Q3 收入 15.2M - 成本 6.6M）" + 引用[第3页]
```

| 关键点 | 做法 |
|---|---|
| 表格块可检索 | 整表块或行块带表头上下文（08 篇路线 B） |
| 计算可溯源 | 答案附计算依据（收入-成本）与页码 |
| 复杂表格 | JSON 进上下文（模型更易读行列关系） |
| 大表 | 摘要块定位 + 行块细节 |

## 9. 表格解析常见坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 摊平成文本 | 行列关系丢失 | 表格专用引擎 + 输出断言（含 | 分隔） |
| 跨页表格断裂 | 检索结果残缺 | 合并后再分块 |
| 合并单元格丢值 | 格子空白 | merged_cells 回填 / JSON 保留关系 |
| 表头行错位 | 列对不上 | 多级表头用 JSON 规范格式 |
| 空单元格误判 | 无值≠丢失 | 输出中区分 null 与遗漏 |
| 数字变字符串 | 类型丢失 | 保留类型信息（JSON） |
| 表内嵌套表格 | 结构复杂 | 降级为独立块 + 引用关系 |
| 页眉含表格 | 每页重复"表头噪音" | 版面分析剔除页眉区域 |
| 表格斜线头 | 结构识别失败 | 斜线单元格按文本拼接处理 |
| 图片型表格（截图） | 无文本结构 | 直接走 OCR 表格识别（PaddleOCR-VL） |

> 💡 表格识别的"最后一公里"是**验收**：抽 10 张表人工核对（行列对应、合并单元格、数值完整），任何自动指标都无法替代人工抽检——表格错误是静默的，用户只会在问答时发现"数字对不上"。

## 10. 版面分析与分块的联动

```text
版面分析输出（标题层级/元素类型/顺序）
  → 分块器消费：
      标题 → 块边界（heading path）
      表格 → 原子块（不切穿）
      页眉页脚 → 剔除
      图表 → 独立块 + 描述
```

版面分析是分块的"骨架输入"——**标题认错=分块边界错=整个检索全错**。选型时版面分析准确率（PP-DocLayoutV2/V3 96.4% 阅读顺序）应纳入核心指标。

## 11. 表格输出的统一规范建议

| 字段 | 说明 | 必填 |
|---|---|---|
| `title` | 表格标题/题注（无则取上文最近标题） | ✅ |
| `page_range` | 起止页码（跨页表格必须） | ✅ |
| `headers` | 列名数组（多级表头用嵌套或 JSON 结构） | ✅ |
| `rows` | 行数据（每行为对象，键=列名） | ✅ |
| `merged_cells` | 合并单元格坐标（JSON 规范格式） | 复杂表 |
| `source` | 文件路径/URL | ✅ |
| `section_path` | 所属章节路径（衔接 heading path） | ✅ |
| `table_type` | 常规/跨页/嵌套 | 建议 |

```text
统一规范的价值：
  ① 任意引擎输出 → 同一 schema → 下游（RAG/数据库）零改造
  ② 跨引擎对比（换 Docling 换 PaddleOCR-VL）只比分数不比格式
  ③ 表格问答/入库直接消费，无需再写适配器
```

> 💡 建议把表格 schema 定为团队内部"解析契约"——引擎可以换，输出格式不变。这正是"解析层与下游解耦"的工程体现。
