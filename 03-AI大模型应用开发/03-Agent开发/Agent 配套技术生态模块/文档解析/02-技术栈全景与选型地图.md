# 技术栈全景与选型地图

> 文档解析的选型不是"哪个库最好"，而是"哪种文档走哪条路"——快库、准库、OCR、VLM 各有主场。本章给出格式矩阵、三层架构与选型决策工具。

## 1. 格式矩阵：文档类型 × 解析难度

| 格式 | 文本可提取 | 结构保留难度 | 主要挑战 |
|---|---|---|---|
| PDF（数字化） | ✅ 直接 | 中 | 双栏、表格、页眉页脚 |
| PDF（扫描件） | ❌ 需 OCR | 高 | 先图像后识别 |
| DOCX | ✅ 直接 | 低 | 样式嵌套、公式（OMML） |
| PPTX | ✅ 直接 | 低-中 | 图形/文本框分散 |
| XLSX | ✅ 直接 | 低 | 合并单元格、公式 |
| HTML | ✅ 直接 | 中 | 嵌套标签、广告噪音 |
| 图片（PNG/JPG） | ❌ 需 OCR | 高 | 手写、低分辨率、倾斜 |
| 邮件/RTF | 部分 | 中 | 编码、格式混乱 |

> 🎯 核心要点：**能直接提取的格式别用 OCR，能提取的别送 VLM**——每升一级，成本与延迟跳一个量级。

## 2. 三层架构：解析流水线的通用骨架

```text
第一层：分类与路由（类型判断）
  ├── 有文本层？→ 快库提取（PyMuPDF 等，0.01-0.05s/页）
  ├── 无文本层？→ OCR / VLM（0.3s-5s/页）
  └── 表格重？→ 表格专用引擎（Docling/PaddleOCR-VL）

第二层：结构化解析（版面 → Markdown/JSON）
  ├── 版面分析（标题/段落/表格/图表/顺序）
  ├── 表格结构化（TEDS 指标）
  └── 元数据（页码、标题路径、来源）

第三层：下游加工（分块入库 / 字段抽取 / 问答）
  └── 结构感知分块 → RAG 向量库（08 模块）
```

## 3. 工具矩阵（2026-08 基准，opendataloader-bench 实测）

| 工具 | 综合分 | 表格 TEDS | 速度 | 许可证 | 特点 |
|---|---|---|---|---|---|
| Nutrient API（商用） | 0.93 | 0.71-0.94 | 网络延迟 | 付费 | 准确率最高 |
| Docling 2.110 | 0.877-0.89 | **0.89** | 0.3-3s/页 | MIT | 开源表格最强；模型 ~500MB |
| Unstructured | 0.788-0.89 | 0.70-0.86 | 中 | Apache | 企业 API 化，云版强于开源版 |
| pymupdf4llm 1.28 | 0.80-0.86 | 0.54-0.61 | **0.01-0.05s/页** | AGPL | 最快；表格弱；无 OCR |
| 路由混合（pdfmux/OpenDataLoader） | **~0.905** | 混合 | 混合 | 开源 | 分页路由，省时 80-95% |

| 选型维度 | 优先项 |
|---|---|
| 速度优先 | PyMuPDF（数字化文本）、路由混合 |
| 表格优先 | Docling、PaddleOCR-VL、Nutrient |
| 许可宽松 | Docling（MIT）、Unstructured（Apache） |
| 扫描件 | OCR/VLM（PyMuPDF 会静默空文本！） |
| 批量同模板 | 模板区域抽取（比通用引擎快 10-100 倍） |

## 4. 核心评估指标：怎么算"解析得好"

| 指标 | 测什么 | 说明 |
|---|---|---|
| NID | 阅读顺序误差 | 顺序错 → RAG 分块错位 |
| TEDS | 表格结构准确率 | 表格识别的事实标准 |
| MHS | 标题层级准确率 | 层级错 → 分块边界错 |
| 字符错误率（CER） | OCR 文字准确度 | 扫描件用 |
| 字段级准确率 | 抽取字段对不对 | 理解层用 |

> 💡 落地时用 20-50 份**自己的**文档建小基准：公开基准（opendataloader-bench 等）只说明相对位次，你的文档分布才是选型依据——金融表格多的团队与论文多的团队结论完全不同。

## 5. 三档预算方案

| 方案 | 构成 | 单页成本 | 适用 |
|---|---|---|---|
| 免费档 | PyMuPDF + Docling + Tesseract | 几乎 0（CPU） | 个人/学习/内部 |
| 均衡档 | 路由：PyMuPDF 快路径 + PaddleOCR-VL 自托管 | 分/页（GPU 自持） | 中小团队生产 |
| 顶级档 | 商用 API（Nutrient/LlamaParse/TextIn）+ VLM 兜底 | 元/页量级 | 高价值文档、合规 |

## 6. 路由式混合：2026 生产共识

```text
每页分类 → 分发
├── 数字化文本页（干净） → PyMuPDF 直提（快）
├── 表格重页面         → Docling/PaddleOCR-VL（准）
├── 扫描/手写页         → OCR 或 VLM（兜底）
└── 低质量/难识别页      → VLM 直读（贵但可靠）
```

| 路由收益 | 数据 |
|---|---|
| 处理时间 | 降 80-95%（混合 vs 全量重型引擎） |
| 综合准确率 | 免费工具中最高（~0.905） |
| 成本 | 大部分页走免费快路径 |

> 🎯 核心要点：**2026 年没有"一个万能解析器"**——所有基准都指向同一结论：按页分类、各走各的引擎，比任何单一工具都好。路由逻辑本身（3 层 if + 简单分类模型）成本极低，值得所有生产系统内置。

## 8.5 一句话选型速查

| 我面对的文档 | 选 | 理由 |
|---|---|---|
| 论文/报告（数字化） | pymupdf4llm | 快（0.01-0.05s/页）且顺序好 |
| 财报/招股书 | Docling | 表格 TEDS 0.89 开源最强 |
| 扫描合同/发票 | PaddleOCR-VL | 96.33% SOTA、版面+表格一体 |
| 手写/疑难杂症 | VLM 直读 | 语义兜底（配交叉验证） |
| 混合档案库 | 路由式混合 | 免费工具里综合最强 ~0.905 |
| 商用高合规 | Nutrient/LlamaParse | 准确率最高、有 SLA |
| Office 三件套 | python-docx/pptx/openpyxl | 结构天然存在，直接走 XML |

选型心法一句话：**先看文档有没有文本层，再看表格重不重，最后看敏感不敏感**——三个问题答完，引擎列表就只剩 1-2 个候选了。

## 7. 入门行动清单（半小时搭出最小流水线）

```bash
# 1. 安装三件套（免费档方案）
pip install pymupdf pymupdf4llm docling
# 2. 有文本层的 PDF → 快路径
python -c "import pymupdf4llm as m; print(m.to_markdown('demo.pdf'))"
# 3. 表格重的 PDF → Docling
python -c "from docling.document_converter import DocumentConverter as D; \
print(D().convert('tables.pdf').document.export_to_markdown())"
# 4. 扫描件 → PaddleOCR-VL（需 GPU/PaddlePaddle 3.2.1+）
#    paddleocr doc_parser --pipeline_version v1.6 --input_path scan.pdf --output_dir out/
```

| 步骤 | 验证点 |
|---|---|
| 快路径 | 输出 Markdown 无乱码、顺序正确 |
| Docling | 表格结构完整（可转回表格渲染核对） |
| OCR | 扫描件输出与原文一致率 |
| 路由 | 同一份文档三路结果对比，确定"哪条路适合我的文档" |

> 💡 半小时的目的是**亲手摸到三类引擎的输出差异**——比读十篇对比文章更能建立"该给哪种文档走哪条路"的直觉。
