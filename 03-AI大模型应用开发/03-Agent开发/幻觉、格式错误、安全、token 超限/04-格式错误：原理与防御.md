## 1. 格式错误全景

### 1.1 为什么格式错误是第一大失败源

Agent 架构把"格式正确"变成了**硬性依赖**：

```text
模型输出 → 解析器 → 工具参数 / 状态更新 / 下一步决策
              ↑
         解析失败 = 整条链中断
```

| 场景 | 格式错误后果 |
|------|------------|
| 工具参数 | 参数解析失败 → 工具无法执行 |
| 规划器输出 | 计划解析失败 → 执行器崩溃 |
| 状态更新 | 状态 JSON 损坏 → 会话状态机失效 |
| 结构化输出校验 | schema 校验失败 → 触发修复循环（成本） |

### 1.2 AgentFixer 数据（ACM AGENT '26）

生产 Agent 系统任务失败中：**解析/格式类失败约 38%**——畸形 JSON、缺失 schema 字段、不遵守指令格式，是单一最大执行失败源。

## 2. JSON 失败模式图谱

| 失败模式 | 典型样例 | 根因 |
|---------|---------|------|
| 代码围栏包裹 | ` ```json {...} ``` ` | 模型习惯性加 Markdown |
| 前缀废话 | `Sure, here's your JSON: {...}` | 对话惯性 |
| 引号未转义 | `{"msg": "他说"你好""}` | 转义规则未被遵守 |
| 尾逗号 | `{"a": 1,}` | 写作习惯 |
| 截断 | `{"a": 1, "b": 2`（无闭合） | max_tokens 截断/中途停止 |
| 字段缺失 | 该有 `price` 没有 | schema 遵循失败 |
| 类型错误 | `"price": "abc"` | 语义理解偏差 |
| 括号不配对 | `{"a": [1,2}` | 结构生成错误 |
| 空响应 | （无内容） | 拒绝/超时/模型异常 |
| 推理通道输出（reasoning） | 答案跑进 reasoning 通道，正文空 | 推理解析器开启时约束未绑定 |

> ⚠️ **模型换版漂移**：供应商更新模型后，输出格式习惯会悄然变化（更爱加围栏、更爱写前缀）——格式错误常在新模型灰度期集中爆发。**格式通过率必须纳入版本灰度观测**。

## 3. 防御路线一：生成期结构化输出

### 3.1 原生 API 能力（2026 现状）

| 供应商 | 能力 | 保证程度 |
|--------|------|---------|
| OpenAI | Strict Mode（`.parse()` + `response_format: json_schema`） | 100% schema 合规（硬保证） |
| Anthropic | `output_config` 直接支持 JSON Schema | 100% 合规 |
| Google Gemini | `response_schema` | 100% 合规 |
| DeepSeek 等 OpenAI 兼容系 | 兼容 OpenAI 格式，能力因版本而异 | 需探针验证 |

**特点**：单供应商 + 简单扁平 schema 时"真的够用"；schema 覆盖有限（复杂嵌套、anyOf 支持不一）。

### 3.2 为什么原生 API 也可能失败

| 场景 | 失败方式 |
|------|---------|
| 服务端不兼容 | strict 标志被静默忽略 |
| 与工具调用叠加 | 约束冲突（见第 6 节） |
| 推理通道 | 输出逃逸到未约束的 reasoning 通道（vLLM #44012 类问题） |
| 多供应商适配 | 各家的 strict 语义不一致 |

## 4. 防御路线二：约束解码

### 4.1 原理

约束解码（Constrained Decoding）在**生成期**屏蔽非法 token：把 JSON Schema / Pydantic 模型 / 正则编译成有限状态自动机或 CFG，每一步只允许符合语法约束的 token 被采样——**非法 JSON 从物理上不可能生成**。

```text
自由生成:  模型采样任意 token → 可能产出坏 JSON
约束解码:  语法约束状态机 → 每个位置只允许合法 token → 结构必然合法
```

### 4.2 主流工具对比（2026）

| 工具 | 阵营 | 特点 | 注意点 |
|------|------|------|--------|
| **Outlines**（dottxt，~15k star） | 开源 | Pydantic/JSON Schema/正则 → FSA；任意后端 | 复杂 schema 小模型易挣扎 |
| **Guidance**（微软，~19k star） | 开源 | token 级约束 + 代码交织；`gen()`/`select()` | 复杂分支逻辑最强 |
| **XGrammar**（MLC） | 运行时 | GPU 批处理多 schema 同批约束 | 面向专用 GPU 推理服务 |
| **LM Format Enforcer** | 轻量 | logit processor 挂进现有管线 | 侵入最小 |
| **SGLang** | 服务层 | 编译 EBNF 语法内建结构化输出 | 与 vLLM 同层 |
| **Jsonformer**（~4.9k star） | 开源 | 只让模型生成字段值，固定 token 由库填写 | 复杂嵌套/anyOf 受限，2024 后停更，不推荐新项目 |
| 原生 API（OpenAI/Claude/Gemini） | 云 | 硬保证、零部署 | 覆盖有限、绑定供应商 |

### 4.3 关键数据

| 指标 | 数值 |
|------|------|
| 约束解码合法 JSON 率 | 99%+ |
| 延迟开销 | <10%（语法法 GBNF 8-12%） |
| 对推理质量影响 | 无损害，甚至小幅提升（GSM8K 80.1% → 83.8%） |
| schema token 开销 | 每请求约 300-600 输入 token |

> 💡 **结论**：约束解码不是"更慢的妥协"，而是**把格式保证从"运气"变成"结构"**。2026 年 JSONSchemaBench 的结论：原生 API 覆盖有限、约束解码覆盖更全——生产建议两者组合。

## 5. 防御路线三：修复循环

### 5.1 修复循环的标准形态

```text
生成 → 解析 → 失败？ → 提取错误信息 → 带错误信息重试（限次） → 仍失败则降级
```

**Instructor 模式（12.3k star，结构化输出 #1 排名）**：包装任意 LLM 客户端，Pydantic 校验失败自动带错误信息重试。实测：schema <15 字段时重试恢复率 >95%，strict 模式下重试率 <2%。

### 5.2 重试风暴——最大的隐藏坑

> ⚠️ **真实事故复盘**：一个编码 Agent 的 catch 处理器对同一错误反复重试同一个坏 prompt，一夜之间 token 花费翻三倍——循环里没有 JSON 合法性评估，重试只是烧钱。

**正确修复循环的四个必要条件**：

| 必要条件 | 说明 |
|---------|------|
| 带反馈重试 | 每次重试必须携带**具体错误信息**（"缺字段 price；类型应为 number"），不是原样重发 |
| 重试上限 | 2-3 次封顶（成本控制） |
| 指数退避 | 失败间隔递增，避免风暴 |
| 换路降级 | 超过上限 → 换模型 / 换格式策略 / 转人工，而不是继续烧 |

**坏重试循环（反面教材）**：

```python
for attempt in range(10):          # 无上限的 10 次
    try:
        result = parse(llm_call(prompt))   # 同一 prompt 原样重发
    except ParseError:
        time.sleep(0.5)                    # 固定间隔
        continue                            # 没有错误反馈、没有退避、没有降级
```

**好重试循环（示范）**：

```python
def call_with_repair(gen_fn, validate, max_retries=3):
    last_error = None
    for attempt in range(max_retries):
        raw = gen_fn(last_error)                # 每次携带错误反馈
        if raw is None or not raw.strip():
            last_error = "输出为空，请重新生成"
        else:
            ok, err = validate(raw)             # 解析 + schema + 语义校验
            if ok:
                return raw
            last_error = err                    # 具体错误信息回传
        time.sleep(2 ** attempt)                # 指数退避
    return None  # 触发降级路径（换模型/转人工），不继续烧
```

### 5.3 JSON 修复工具的现实

`jsonrepair` 类修复库可以补括号、去围栏、修尾逗号——**但只解决"小伤"**：

| 问题 | 能否修复 |
|------|---------|
| 围栏/前缀/尾逗号/缺闭合 | 能 |
| 字段缺失/类型错误 | 不能（语义问题） |
| 截断 | 能修到"合法但残缺"，须配合重试 |

> ⚠️ 修复库只作为兜底，**不能替代 schema 校验与重试反馈**——语义错误修复不了。

## 6. Structured Output × 工具调用的冲突

2026 年反复出现的高频坑（vLLM PR #32127/#44134、openai-agents-python #3709）：

| 冲突 | 现象 | 解法 |
|------|------|------|
| `response_format` + `tool_choice: required` 并存 | 引擎崩溃 / 校验报错"只能使用一种结构化约束" | 二选一，不在同一轮叠加 |
| strict 服务端 + 工具 + response_format | 约束从第一个 token 就生效，**抑制工具调用**——模型输出 schema 形状的"假答案"而不调工具 | 分离回合：工具调用回合不用 response_format |
| 推理解析器 + json_schema | 答案逃逸到未约束的 reasoning 通道，正文空 | 关闭推理解析器或约束绑定到正文通道 |

**通用解法：延迟结构化（Deferred Structuring）**——运行循环时不约束，只在**最终回答**这一轮应用 schema：

> Anthropic Agent SDK 已将此做成标准模式：`output_format` 作用于 run 级，`ResultMessage.structured_output` 仅在终止轮生效。

```text
工具循环（自由格式） → 最终回答轮（应用 output_format） → 结构化结果
```

## 7. 工具链选型决策树

```text
代码栈是 Python Agent？
├─ 是 → PydanticAI（v1 稳定，2026-04）或 Instructor（校验+自动重试）
└─ 否 → 自托管推理（vLLM/Ollama/llama.cpp）？
        ├─ 是 → Outlines / XGrammar / LM Format Enforcer（解码期保证）
        └─ 否 → 云供应商原生 structured output 优先，复杂 schema 加 Instructor
TypeScript/边缘运行时 → Zod + zodResponseFormat / ajv
对话式护栏 → NeMo Guardrails（Colang DSL）
内容安全校验 → Guardrails AI（validator 注册表）
```

**生产配置基线**：

```text
第一层：解码期/原生保证      —— 结构必然合法（硬约束）
第二层：Pydantic/Zod 校验    —— 结构 + 部分语义（业务规则）
第三层：修复循环（≤3 次）     —— 带错误反馈重试
第四层：降级路径             —— 换模型 / 转人工 / 记录失败样本
监控：is_json_pass_rate 按模型/版本/prompt 版本分组跟踪
```

> 🎯 **核心要点**：格式错误的工程本质是"把格式保证从 prompt 建议升级为系统约束"。四层防御（生成期约束 → 校验 → 修复循环 → 降级）中，前两层决定成功率，后两层决定失败的成本。
