## 1. 为什么是这四类失败

Agent = 模型 + 工具 + 循环（memory/上下文）。每一环都有其必然失败点：

| 环节 | 失败模式 | 本质原因 |
|------|---------|---------|
| 模型生成 | 幻觉 | 语言模型的天性是"流利地编造"，不是"查证" |
| 模型输出 | 格式错误 | 输出是概率采样，schema 只是"建议"而非约束 |
| 循环状态 | Token 超限 | 上下文是有限"工作记忆"，而 Agent 是无限状态机 |
| 输入/工具面 | 安全（提示注入等） | 模型无法可靠区分"指令"与"内容" |

> 🎯 **核心要点**：四类失败不是 bug，而是 LLM 系统的**固有属性**。生产工程的目标不是消灭它们，而是建立"检测 → 修复 → 恢复"的防御闭环。

## 2. 失败模式频率分布（生产数据）

### 2.1 AgentFixer 生产统计（ACM AGENT '26）

在 IBM CUGA 等生产级 Agent 系统的故障统计中，任务失败按根因分布：

| 根因类别 | 占比 | 典型表现 |
|---------|:---:|---------|
| **解析/格式类失败** | **~38%** | 畸形 JSON、缺 schema 字段、不遵守指令格式 |
| 工具调用错误 | 20-25% | 错选工具、参数错误、幻觉式调用不存在的工具 |
| 推理/规划偏差 | 15-20% | planner 与执行器目标不一致、步骤缺失 |
| 上下文/Token 类 | 8-12% | 上下文溢出、关键信息被压缩丢失 |
| 安全/其他 | <10% | 注入命中、越权动作、死循环 |

> ⚠️ 解析类失败是**第一大失败源**，远超"模型答错"——这也是格式错误单独成体系的理由。

### 2.2 幻觉率基准（ORCA-bench 2026）

ORCA-bench 让 Agent 在真实 OTel 插桩系统中做 SRE 接警：

| 指标 | 数值 |
|------|------|
| 最佳根因分析准确率（Medium） | 40% |
| 最佳根因分析准确率（Hard） | 25.3% |
| 幻觉率 | 7-10% |
| 遥测调用出错/返回空比例 | 26-40% |

> 💡 **启示**：2026 年的前沿 Agent 远未达到生产接警水平。对 Agent 输出做**默认不信任**处理是正确姿势。

## 3. 现象 → 根因映射表

| 你看到的"现象" | 最可能的根因 | 次可能根因 |
|---------------|------------|-----------|
| 工具参数全是编的 | 幻觉式工具调用 | 工具描述不清晰、schema 太松 |
| 回答与检索文档矛盾 | 上下文幻觉 | 检索质量差（召回噪声） |
| JSON 解析报错 | 格式错误（坏 JSON） | 模型换版导致格式漂移 |
| 工具该调用却没调 | 结构化输出与 tool_choice 冲突 | 格式约束抑制了工具调用 |
| 请求被 400 拒绝 | Token 超限 | 单次工具结果过大 |
| Agent 忘了早期任务 | 上下文被压缩/滑出窗口 | 压缩丢失关键数值 |
| 成本爆炸式增长 | Token 超限+重试风暴 | Prompt Caching 未命中 |
| 模型突然说"我是 AI 助手" | 提示注入命中/提示词泄露 | 角色约束被内容覆盖 |
| 循环卡死反复重试 | 修复循环缺陷 | 格式错误+无评估的重试 |
| 生成长度异常 | 流式拼接错误 | 推理通道输出未约束 |

## 4. 五步诊断法

```text
现象收集 → 分层定位 → 数据取证 → 根因确认 → 修复+验证
  (1)       (2)        (3)        (4)       (5)
```

### 4.1 现象收集（1 分钟）

- 复现路径：哪个用户、哪次会话、第几步失败
- 失败形态：报错信息 / 超时 / 静默错误（最危险）
- 时间线：最近变更了什么（模型版本、prompt、schema、工具）

### 4.2 分层定位（核心）

按 Agent 调用链从外到内切分：

| 层 | 问题 | 判定方法 |
|----|------|---------|
| 网关/路由层 | 模型切换、供应商 400 | 检查请求体大小、响应状态码 |
| 编排层 | 循环逻辑、重试策略 | 看 trace 步骤数、重试次数 |
| 工具层 | 工具返回异常 | 检查工具调用参数与实际响应 |
| 生成层 | 幻觉/格式 | 检查原始模型输出（不经过解析器） |
| 上下文层 | 超限/压缩丢失 | 检查 token 统计与压缩前后对比 |

### 4.3 数据取证（关键动作）

- **原始输出优先**：解析器报错时，先看模型**原始字符串**——坏 JSON 长什么样（被代码围栏包裹？被截断？多余前缀？）
- **trace 完整链路**：目标 → 工具调用 → 工具响应 → 下一步决策
- **token 统计**：每次请求的 input/output token 数、累计成本

### 4.4 根因确认

- 对照[映射表](#3-现象--根因映射表)形成假设
- 用**最小复现**验证：去掉无关步骤，单独重放失败步骤
- 注意：Agent 自报的日志/错误信息**不可信**（Agent 会"编造"合理的失败解释）——以外部遥测为准

### 4.5 修复 + 验证

- 修复必须能回答："为什么这次修复是根因级的，不是打补丁"
- 验证三件套：复现用例通过 / 回归集不退化 / 监控指标改善

> 🎯 **核心要点**：五步法的灵魂是**分层定位 + 原始数据取证**。90% 的"幻觉问题"最后发现是检索问题，90% 的"格式问题"最后发现是约束缺失——不做数据取证就修，是打地鼠。

## 5. 诊断工具与断点

| 工具类型 | 代表 | 诊断价值 |
|---------|------|---------|
| 分布式追踪 | OpenTelemetry + Jaeger/Langfuse | Agent 会话级 span：目标、工具、决策全记录 |
| 回放工具 | AgentOps、LangSmith | 失败会话回放、多 Agent 协作复盘 |
| 网关代理 | Portkey、Helicone | 请求/响应拦截、重试与成本统计 |
| 评估框架 | Agentic CLEAR、FailProbe | 自动发现重复失败模式（14 类失败分类） |
| 规则引擎 | 策略内核（OPA Rego/Cedar） | 亚毫秒拦截违规动作，独立于模型自述 |

**断点设置优先级**（按性价比）：

1. 每次工具调用的入参/出参（记录但不拦截）
2. 每次 LLM 调用的原始输出（格式错误的案发现场）
3. 上下文压缩动作（压缩前后快照对比）
4. 会话级成本/轮数计数器（触发熔断）

## 6. 四类失败的关系网

四类失败不是孤立的——它们互相诱发：

```text
安全(注入) ──命中后──▶ 工具被诱导执行错误动作 ──▶ 幻觉式调用/数据污染
                              ▲
                              │
格式错误 ◀── 结构约束过强 ── 抑制工具调用 ──▶ Agent 用文本"假装"调用 ──▶ 解析失败
                              │
Token 超限 ◀── 工具结果过大/轮数过多 ── 重试风暴(无评估的重试) ──▶ 成本爆炸
                              │
                              ▼
                    上下文压缩丢失关键数值 ──▶ 幻觉式补全数值 ──▶ 级联幻觉
```

**典型事故链（真实复盘）**：一个编码 Agent 的 catch 处理器对同一错误反复重试 → 一夜 token 花费翻三倍 → 触发成本熔断 → 排查发现根因是格式错误 + 修复循环里没有 JSON 合法性评估。

> 💡 **启示**：防御设计必须考虑"失败联动"——例如重试必须带指数退避 + 幂等 + 格式评估，压缩必须保全关键数值，工具权限必须最小化。
