## 1. 上下文窗口是什么

上下文窗口 = 模型单次请求能"看到"的 token 上限。对 Agent 而言，窗口被五类内容瓜分：

```text
┌─────────────── 上下文窗口（如 128K tokens）───────────────┐
│ 系统提示词      │ 工具定义        │ 对话历史           │ 工具调用+结果 │ 即将生成的输出 │
│ (常驻, 1-8K)   │ (常驻, 1-15K)   │ (随轮数增长)       │ (增长最快)   │ (预留)         │
└───────────────┴────────────────┴───────────────────┴─────────────┴───────────────┘
```

| 内容 | 增长特性 | Agent 场景占比（典型） |
|------|---------|:---:|
| 系统提示词 | 固定 | 3-8% |
| 工具定义 | 固定（除非动态过滤） | 8-20% |
| 对话历史 | 线性增长 | 30-60% |
| 工具调用 + 结果 | **超线性增长**（大结果如文件内容/搜索响应） | 30-60% |
| 输出预留 | 需为生成留余量 | 5-15% |

> 🎯 **核心要点**：Agent 和单轮对话的本质区别——**工具结果把上下文增长速度从"对话长度"变成"操作规模"**。一次 `read_file` 返回 50K token，顶得上几十轮对话。

## 2. Token 计量与成本模型

### 2.1 计量单位

| 计量 | 规则 |
|------|------|
| 1 token ≈ 0.75 英文单词 / 0.5-1 汉字 | 中文 token 化开销需实测 |
| 输入 + 输出分开计费 | 输出单价通常是输入的数倍（按供应商） |
| 请求头/尾额外 token | schema、角色标记等隐性开销 |
| max_tokens 预留 | 不给输出留余量 → 输出被截断（截断 → 格式错误！） |

### 2.2 成本超线性增长的数学

LLM API 无状态，**每轮都重发全部历史**：

```text
N 轮会话总输入 token ≈ Σ(每轮的累积历史) ≈ O(N² × 单轮增量)
```

| 轮数 | 每轮增量 | 累积发送量 |
|:---:|:---:|:---:|
| 10 | 2K | ~110K |
| 20 | 2K | ~420K |
| 40 | 2K | ~1.6M |

> 💡 **推论**：长会话的成本不是线性而是**近二次增长**——缓存与上下文管理对 Agent 是经济必需，不只是性能优化。

## 3. 超限的三种形态

| 形态 | 表现 | 判定 | 后果 |
|------|------|------|------|
| 硬超限 | 供应商 400 拒绝请求 | 报错提示超出窗口 | 会话卡死 |
| 软截断 | 请求塞入但被截断 | 尾部内容丢失 | 丢失最近信息（最反直觉） |
| 输出截断 | max_tokens 用尽 | 输出戛然而止 | **坏 JSON + 语义残缺** |

### 3.1 硬超限的常见触发点

```text
工具结果过大：read_file 返回整个大文件、search 返回 20 条长摘要
轮数过多：重试风暴（见 04-格式错误）加速塞满窗口
动态工具集：工具定义本身占窗口大头
```

### 3.2 输出截断 = 格式错误的隐藏入口

> ⚠️ 输出截断是最容易误判的失败——`max_tokens` 不够时模型"正常停止"，但 JSON 缺了闭合括号，解析器报"格式错误"，实际根因是**窗口余量不足**。诊断时先查输出是否被截断，再查 JSON 本身。

## 4. 硬限制之前：性能衰减

窗口满之前，性能已经崩了。**NoLiMa 基准（2026）**：

> 13 个宣称支持 128K 的模型中，11 个在 32K token 输入时得分**低于其短输入性能的一半**。

| 输入长度 | 有效性能 | 说明 |
|:---:|:---:|------|
| 2-8K | 100% | 甜点区 |
| 16-32K | 60-80% | 开始衰减 |
| 64K+ | <50% | 多数模型已腰斩 |

**衰减的机制原因**：

1. **注意力稀释**：token 越多，每个 token 获得的注意力预算越薄
2. **位置编码退化**：长距离依赖变弱
3. **信息检索负担**：模型要在海量上下文中"找到"关键信息

> 🎯 **核心要点**：不要按"窗口大小"设计 Agent，要按**有效上下文（effective context）**设计——通常取窗口的 25-50% 作为工程上限。

## 5. Lost-in-the-Middle 效应

长上下文中，**中间位置的信息利用率最差**：

| 位置 | 信息利用率 | 用途建议 |
|------|:---:|---------|
| 开头（primacy） | 高 | 系统指令、最关键约束、核心事实 |
| 结尾（recency） | 最高 | 最新状态、即将执行的任务、最近的工具结果 |
| 中间 | 低 | 参考性材料、可丢失的细节 |

**工程推论**：

```text
关键信息布局原则：
├─ 铁律（必须遵守）→ 开头，且永不沉没
├─ 即时任务相关 → 结尾（最新）
├─ 参考材料 → 中间，且最好压缩
└─ 约束防衰减 → 关键约束不仅放开头，还要在结尾"复述"
```

> ⚠️ **约束衰减**：早期硬规则（"永远输出合法 JSON"）埋在中部后被忽略——长会话里约束必须周期性重申。

## 6. "更大的窗口"为什么不是解药

2026 年的明确共识（Redis 等生产方公开结论）：

| 买更大窗口的错觉 | 现实 |
|-----------------|------|
| "128K 就够用了" | 性能在 32K 就腰斩；大窗口 ≠ 有效窗口 |
| "塞进去总比没有好" | 塞入越多，Lost-in-the-Middle 越严重，幻觉率上升 |
| "一劳永逸" | 会话跨天/跨任务后仍然要管理记忆 |
| "省了上下文管理" | 成本反而爆炸（输入计费按 token 数） |

**上下文窗口的正确定位**：

> "上下文窗口是工作记忆（working memory），不是存储（storage）。"——2026 生产 Agent 共识

| 应该放窗口 | 应该放窗口外 |
|-----------|------------|
| 当前任务状态 | 历史决策细节 |
| 本轮工具结果 | 大文件全文 |
| 活跃约束 | 已完成的子任务记录 |
| 近期对话 | 用户长期偏好 |
