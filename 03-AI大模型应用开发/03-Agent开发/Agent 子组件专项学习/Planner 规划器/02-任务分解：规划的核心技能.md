# 任务分解：规划的核心技能

> 分解是规划器的"看家本领"：把长目标拆成原子步骤。2026 年实证（Mano-P）：**分解质量比单步执行准确率更决定任务完成率**；MAP 发现 LLM 单独能分解，但"分解+协调"是瓶颈——本章把分解讲透。

## 1. 分解的目标：好计划的三层标准

| 层 | 标准 | 例子 |
|---|---|---|
| 原子性 | 每步是单动作（一工具一查） | "查订单表"而非"处理订单" |
| 自包含 | 每步说明做什么/用什么 | "用 search 工具查 2026 财报" |
| 可验证 | 每步有完成判定 | "核对结果 >100 条" |

> 🎯 核心要点：分解的本质是**"把一个长决策变成一串短决策"**——每步越简单，执行越稳、失败越容易定位、重规划越便宜。

## 2. 分解的粒度选择：任务的不可预知性决定

| 任务特征 | 粒度 | 理由 |
|---|---|---|
| 可预知（流水线/批处理） | 细（20+ 步） | 计划稳定，一次到位 |
| 半预知（标准任务） | 中（8-12 步） | 默认 |
| 不可预知（研究/调试） | 粗（3-5 阶段） | 细计划迅速过时 |
| 混合（有探索有执行） | 阶段+细化 | 阶段粗、阶段内细 |

```text
分解粒度公式（经验）：
  步骤数 ≈ 任务可预知度 × 任务复杂度
  过细：计划漂移快（每步都要重规划）
  过粗：执行器一步塞多事（无法完成）
```

## 3. 三种分解方法

| 方法 | 做法 | 适用 |
|---|---|---|
| 自上而下 | 目标 → 阶段 → 步骤（顶层分解） | 复杂任务（默认） |
| 自下而上 | 已知动作 → 组装流程 | 流水线类 |
| 递归分解 | 步骤内再分解（层级计划） | 超长任务 |

```text
自上而下示例（研究报告任务）：
  目标：输出 2026 数据库选型报告
  → 阶段1 调研（搜索+文档）→ 阶段2 对比分析 → 阶段3 撰写
  → 阶段1 再分解：搜索基准 → 整理数据 → 交叉验证
```

## 4. 分解的约束处理（2026 关键发现）

| 发现 | 说明 |
|---|---|
| 单约束好处理 | 模型能处理单个约束（如"只查上月"） |
| **耦合约束骤降** | 多约束叠加（"上月且含退款且按品类"）成功率暴跌（PlanningBench 实证） |
| 约束显式化 | 约束写进每步（而非只在目标里） |
| 约束检查 | 每步对照约束清单（验证增强，06 篇） |

> ⚠️ PlanningBench 关键结论：**open 与 closed 前沿模型都受耦合约束困扰**——"约束分解"（把多约束拆到各步骤）是 2026 年最值得投入的工程点之一。

## 5. MAP 模块化分解（2026 架构启示）

| MAP 模块 | 职能 | 独立 vs 协调 |
|---|---|---|
| 冲突监控 | 检测计划与状态冲突 | ✅ LLM 可独立做 |
| 状态预测 | 预测步骤后状态 | ✅ 可独立 |
| 状态评估 | 评估当前状态好坏 | ✅ 可独立 |
| 任务分解 | 拆分子目标 | ✅ 可独立 |
| 任务协调 | 组装/调度子目标 | ⚠️ **自主协调是瓶颈** |

> 💡 MAP 的工程启示：**把分解与协调分开实现**——分解交给 LLM（它擅长），协调交给代码/状态机（确定性）——"LLM 分解 + 代码协调"是 2026 推荐的混合架构。

## 6. 分解失败模式与对策

| 失败 | 现象 | 对策 |
|---|---|---|
| 过度分解 | 10+ 步小任务 | 粒度与复杂度匹配 |
| 欠分解 | 一步塞多事 | 原子性检查 |
| 依赖缺失 | 步骤顺序隐含（未声明） | 显式依赖字段 |
| 成功标准缺失 | 无法判断完成 | 每步可验证目标 |
| 约束丢失 | 约束只在目标里 | 约束下放到每步 |
| 幻觉步骤 | 编造不存在的动作 | 工具清单约束 + 验证 |
| 分解漂移 | 后续步骤偏离原目标 | 目标锚定（05 篇） |

## 7. 分解质量评测

| 评测项 | 方法 |
|---|---|
| 原子性 | 每步是否单动作（人工抽查） |
| 完成率 | 计划步骤执行完成比例 |
| 步骤利用率 | 计划步骤被真实执行的比例（低=冗余） |
| 重规划率 | 计划被推翻的比例（高=初始分解差） |
| 端到端 | 有/无分解的任务成功率 A/B |

> 🎯 核心要点：分解是规划器的"50% 功力"——**"分解粒度匹配任务"+"约束下放到步骤"+"每步可验证"**三件事做好，规划的失败率大幅下降；分解不好，再好的执行器也白搭。

## 8. 分解提示词模板要点

| 要素 | 模板写法 |
|---|---|
| 粒度要求 | "每步是单个可执行动作，不超过 12 步" |
| 自包含 | "每步说明：做什么、用什么工具、预期结果" |
| 可验证 | "每步给出完成判定" |
| 约束下放 | "把约束写进涉及步骤" |
| 依赖显式 | "标注步骤依赖（before/after/parallel）" |
| 收尾步骤 | "最后一步直接产出最终答案" |

## 9. 分解与记忆的协作（规划经验资产化）

| 协作点 | 说明 |
|---|---|
| 成功计划入记忆 | 任务完成后的计划存为"经验模板"（下次相似任务直接复用） |
| 失败计划入记忆 | 失败教训（"该任务约束要下放"）写入记忆（反思回写） |
| 分解模式复用 | 相似任务的分解结构检索复用（少一次规划调用） |
| 工具使用经验 | 哪个工具适合什么任务（工具选择经验） |

> 💡 分解经验与[Memory 记忆系统](../Memory%20记忆系统/00-Memory记忆系统总览.md)的联动：**"计划即经验"**——把验证通过的计划沉淀为模板，是规划成本下降的第二大杠杆（第一大是 ReWOO 静态化）。

## 10. 分解常见误区

| 误区 | 真相 |
|---|---|
| "步骤越多越严谨" | 过度分解=计划漂移快 |
| "约束写目标里就够" | 耦合约束需下放到步骤（PlanningBench 实证） |
| "分解是模型的事" | 代码协调（依赖/状态机）是确定性部分 |
| "分解一次定终身" | 重规划时也要再分解 |
| "所有任务都要分解" | 短任务分解是负收益 |
| "分解不用评测" | 重规划率/步骤利用率是分解质量指标 |

## 11. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 好分解的标准？ | 原子性（单动作）+ 自包含（工具明确）+ 可验证（完成判定） |
| 分解粒度怎么定？ | 与任务不可预知度成反比：可预知细、不可预知粗 |
| 耦合约束为什么难？ | 多约束叠加成功率骤降（PlanningBench）——约束下放到步骤 |
| MAP 的启示？ | LLM 单独能分解，协调是瓶颈——LLM 分解 + 代码协调 |
| 分解质量怎么测？ | 重规划率 + 步骤利用率 + 端到端 A/B |
| 分解的工程分工？ | 分解给 LLM（擅长）、协调/依赖/状态机给代码（确定性）——"LLM 分解 + 代码协调" |
| 分解的三层标准速记？ | 原子（单动作）/ 自包含（工具明确）/ 可验证（完成判定）——三者齐才合格 |
