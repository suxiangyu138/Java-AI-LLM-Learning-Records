# 规划表示：计划的数据结构

> 计划是规划器的"产品"——它的数据结构决定执行器怎么消费、重规划怎么改、审计怎么查。2026 年标准：**计划 JSON 契约 + 步骤状态机 + 依赖关系（序列或 DAG）**。

## 1. 计划 JSON 契约（与 Output Parser 体系衔接）

```json
{
  "goal": "分析 2026 Q2 销售下滑原因",
  "steps": [
    {"id": 1, "summary": "查询 Q2 销售数据", "action": "query",
     "tool": "search_orders", "params": {"period": "2026Q2"},
     "depends_on": [], "success_criteria": "返回 100 条以内订单",
     "state": "pending"},
    {"id": 2, "summary": "对比 Q1/Q2 品类数据", "action": "query",
     "tool": "db_query", "params": {"compare": ["Q1", "Q2"]},
     "depends_on": [1], "success_criteria": "得到品类对比表",
     "state": "pending"}
  ],
  "constraints": {"max_steps": 8, "budget": "5 美元"},
  "termination": "全部步骤 done 或达到上限"
}
```

| 字段 | 作用 | 消费方 |
|---|---|---|
| goal | 目标锚定（防漂移） | 重规划器 |
| steps[].summary | 步骤语义 | 执行器 |
| steps[].tool/params | 动作定义 | 工具层 |
| steps[].depends_on | 依赖编排 | 调度器 |
| steps[].success_criteria | 完成判定 | 反思/执行器 |
| steps[].state | 进度状态机 | 调度器/前端 |
| constraints | 预算（防失控） | 运行时 |

> 🎯 核心要点：**计划是"目标 + 步骤 + 约束 + 状态"的完整契约**——只存步骤列表的计划是半成品（无法防漂移、无法管预算、无法审计）。计划 JSON 的 schema 校验复用[Output Parser 输出解析器](../Output%20Parser%20输出解析器/00-OutputParser输出解析器总览.md)体系的 strict 模式。

## 2. 步骤状态机

```text
pending（待执行）
  → running（执行中）
    → done（成功，完成判定通过）
    → failed（失败，可重试）
      → skipped（重规划删除）
      → blocked（依赖失败，级联跳过）
```

| 状态 | 转出条件 | 防什么 |
|---|---|---|
| pending→running | 依赖全部 done | 顺序错乱 |
| running→done | success_criteria 通过 | 假完成 |
| running→failed | 重试耗尽 | 无限重试 |
| 任意→blocked | 依赖 failed | 级联执行浪费 |
| 任意→skipped | 重规划移除 | 执行无用步骤 |

> 💡 状态机是"执行纪律"的实现——**步骤不是"做完"而是"验证过"**（success_criteria 通过才 done），这是 2026"验证增强规划"的最小落地。

## 3. 依赖关系的两种表示

| 表示 | 结构 | 适用 |
|---|---|---|
| 序列（线性） | steps 数组按序 | 简单任务（默认） |
| DAG（有向无环图） | steps + depends_on | 有并行/分支的任务 |

```text
DAG 示例（并行调研 + 汇总）：
  step1 搜索基准数据 ─┐
  step2 搜索厂商信息 ─┼→ step4 汇总对比报告
  step3 搜索安全公告 ─┘
  （step1-3 可并行，step4 依赖三者）
```

| DAG 调度要点 | 说明 |
|---|---|
| 就绪判定 | 依赖全部 done 才 running |
| 并行度 | 就绪步骤并发（读操作） |
| 环检测 | depends_on 成环 → 计划非法（校验） |
| 级联阻塞 | 依赖 failed → blocked |

## 4. 计划存储与恢复

| 存储 | 用途 |
|---|---|
| 运行时内存 | 当前任务计划（默认） |
| 会话状态/检查点 | 崩溃恢复（衔接[Memory 记忆系统](../Memory%20记忆系统/03-情景记忆：会话历史与检查点.md)检查点） |
| 审计存储 | 计划演变留痕（重规划历史） |

```text
计划恢复场景：
  崩溃 → 从检查点恢复计划 → 续跑未完成步骤
  （依赖状态机：已 done 的步骤不重跑）
```

## 5. 计划版本与审计

| 项 | 做法 |
|---|---|
| 计划版本 | 每次重规划生成新版本（v1/v2/...） |
| 变更记录 | 记录：谁触发、改了什么、为什么 |
| 审计价值 | 计划 vs 执行的差异 = 决策质量数据 |
| 回放 | 计划演变可回放（调试） |

> 💡 计划审计是 2026 年规划评测的数据基础——**"初始计划 vs 最终执行"的差异分析**（07 篇重规划率指标）依赖完整的计划版本链。

## 6. 规划表示常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 无 goal 字段 | 重规划漂移 | 目标锚定入契约 |
| 无 success_criteria | 假完成 | 每步可验证 |
| 无状态机 | 顺序/重试失控 | 状态机六态 |
| depends_on 成环 | 死锁 | 环检测校验 |
| 约束不入计划 | 预算失控 | constraints 字段 |
| 计划不落库 | 崩溃丢计划 | 检查点 |
| 重规划不留痕 | 无法审计 | 计划版本链 |

> 🎯 核心要点：规划表示的完整度 = 规划的工程成熟度——**"目标+步骤+依赖+状态+约束+版本"六件套齐备**，规划才从"一段文本"变成"可执行的资产"。

## 7. 计划接口与消费端

| 消费端 | 消费什么 | 接口形式 |
|---|---|---|
| 执行器 | 当前 pending 步骤 | `get_next_step(plan)` |
| 调度器 | 依赖与并行 | `get_ready_steps(plan)` |
| 前端 | 计划展示（进度条/步骤卡） | 计划 JSON（只读投影） |
| 审计 | 计划演变 | 版本链 |
| 重规划器 | 已完成摘要+剩余计划 | 裁剪视图（05 篇） |

> 💡 计划接口设计的要点：**消费端拿"视图"而非"全部"**——执行器只拿下一步、前端只拿展示字段、重规划器只拿摘要——视图隔离防止消费端误改计划本体。

## 8. 计划可视化（前端展示）

| 展示 | 组件 | 衔接 |
|---|---|---|
| 步骤列表+状态 | 任务列表（TaskList） | 前端演示界面 08 篇 |
| 依赖图 | DAG 图（Mermaid） | 计划即图 |
| 进度 | 步骤 X/Y + 完成率 | 实时状态流 |
| 重规划记录 | 计划版本时间线 | 审计可视化 |

> 💡 计划可视化是"过程透明"的最小实现——用户看着 Agent 按计划执行，信任度大幅提升（前端演示界面体系的渐进式披露原则）。

## 9. 计划数据结构常见坑（补充）

| 坑 | 现象 | 解法 |
|---|---|---|
| 视图与本体不分 | 消费端误改计划 | 只读投影 |
| 无依赖显式 | 顺序靠隐式 | depends_on 字段 |
| 计划不校验 | 非法计划进执行 | strict schema 校验 |
| 版本链缺失 | 重规划无法回放 | 版本号递增 |
| 成功标准字符串化 | 无法程序判定 | 结构化 criteria |

## 10. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 计划的数据结构？ | goal + steps（summary/tool/params/depends_on/success_criteria/state）+ constraints + version |
| 步骤状态机？ | pending→running→done/failed/skipped/blocked 六态 |
| 依赖怎么表示？ | depends_on 数组（序列或 DAG）；成环检测 |
| 计划存哪？ | 运行时内存 + 检查点（恢复）+ 审计存储 |
| 计划为什么要版本？ | 重规划回放 + 审计 + 评测数据 |
| 计划契约谁校验？ | 输出解析器 strict 模式（同 schema 两处消费） |
| 计划存储三态？ | 运行时内存（执行）+ 检查点（恢复）+ 审计（版本链）——一计划三存储各司其职 |
