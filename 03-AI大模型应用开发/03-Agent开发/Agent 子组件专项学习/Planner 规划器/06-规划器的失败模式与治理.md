# 规划器的失败模式与治理

> 2026 调查（200+ 论文）把规划失败归为三类：**级联失败、动作 schema 幻觉、进度误判**——破局方向是"验证增强规划"。本章给出失败目录、验证机制与治理框架。

## 1. 三大失败模式（2026 调查共识）

| 失败 | 机制 | 例子 | 代价 |
|---|---|---|---|
| 级联失败 | 早期一步错 → 后续全错（无事务/回滚） | 第 2 步数据错，第 3-10 步全建立在错数据上 | 全部执行浪费 |
| 动作 schema 幻觉 | 类型复杂场景生成貌似合理的错误动作 | 编造不存在的工具/参数组合 | 执行失败 |
| 进度误判 | 不知道自己走到哪 | 提前终止（活没干完）/冗余循环（白烧钱） | 任务不完整 |

> 🎯 核心要点：三类失败的共同根因是**"计划没有验证机制"**——模型"感觉对了"就继续。治理的方向统一：给计划加"客观检查"（约束校验/成功标准/进度指标）。

## 2. 级联失败的治理：事务思维

| 治理 | 做法 | 类比 |
|---|---|---|
| 每步验证 | success_criteria 通过才 done | 原子提交 |
| 检查点 | 计划+状态定期落库 | 事务日志 |
| 回滚 | 失败步骤可撤销（工具幂等） | 回滚 |
| 依赖阻断 | 依赖 failed → blocked | 级联回滚 |

```text
级联失败的工程化防线：
  ① 每步可验证（03 篇 success_criteria）
  ② 依赖阻断（blocked 不执行）
  ③ 检查点恢复（Memory 03 篇）
  ④ 写操作幂等（可安全重跑）
  四件套 = 规划的"事务语义"
```

> 💡 2026 调查明确建议：**verification-augmented planning（验证增强规划）**——中间步骤对照形式化约束检查，是最被看好的破局方向。

## 3. 动作 schema 幻觉的治理

| 治理 | 做法 |
|---|---|
| 工具清单约束 | 计划只允许引用已注册工具 |
| schema 校验 | 计划 JSON 过工具 schema 校验（Output Parser 07 篇） |
| 参数回查 | 工具参数与真实 schema 比对 |
| 提示词约束 | "只使用提供的工具清单" |
| 幻觉检测 | 未知工具名 → 计划非法（校验拦截） |

```python
def validate_plan_tools(plan, registry):
    for step in plan["steps"]:
        tool = step.get("tool")
        if tool and tool not in registry:      # 幻觉工具拦截
            raise PlanError(f"步骤 {step['id']} 引用未注册工具 {tool}")
        if tool and not schema_ok(step["params"], registry[tool].schema):
            raise PlanError(f"步骤 {step['id']} 参数不符 {tool} schema")
```

## 4. 进度误判的治理

| 治理 | 做法 |
|---|---|
| 显式进度指标 | 步骤状态机 + 完成判定 |
| 进度小结 | 每 N 步输出"已完成 X/Y" |
| 提前终止检查 | 终止前验证"目标达成"而非"步骤耗尽" |
| 冗余检测 | 相同步骤重复执行 → 告警 |

```text
进度误判的两种死法：
  提前终止：步骤没做完就说完成（success_criteria 缺失）
  冗余循环：做完了还在做（无终止检查）
  解法：终止条件 = 目标达成判定，不是"步骤耗尽"
```

## 5. 验证增强规划（2026 破局方向）

| 验证层 | 验证什么 | 机制 |
|---|---|---|
| 语法验证 | 计划 JSON 合法 | schema 校验（Output Parser） |
| 工具验证 | 工具存在/参数合规 | 注册表校验 |
| 约束验证 | 满足约束清单 | 规则引擎（约束下放，02 篇） |
| 状态验证 | 步骤前置状态正确 | 状态机 |
| 结果验证 | 步骤结果符合预期 | success_criteria + 反思 |

```text
验证增强的落点：
  每次执行前验证该步（计划与状态）
  每次完成后验证该步（结果与标准）
  关键节点做全计划一致性检查
  —— "验证"不是事后审计，是执行纪律的一部分
```

> 🎯 核心要点：验证增强的哲学——**"模型生成计划，代码验证计划"**（与 02 篇"LLM 分解 + 代码协调"同构）：让 LLM 负责创造性部分，让确定性代码负责检查部分。

## 6. 失败诊断：失败模式 → 根因 → 修复

| 现象 | 根因排查 | 修复 |
|---|---|---|
| 后续步骤全错 | 查第 2 步是否验证缺失 | 补 success_criteria |
| 计划引用未知工具 | 工具清单未约束 | 计划校验接入注册表 |
| 提前收尾 | 终止判定缺失 | 目标达成检查 |
| 重复执行 | 状态机缺失 | 状态机 + 冗余检测 |
| 重规划风暴 | 初始计划质量差 | 02 篇分解质量 |
| 长程退化 | 计划过细/无验证 | 粒度调粗 + 验证增强 |

## 7. 治理框架：失败的三道防线

```text
第一道：预防（分解质量 + 工具约束 + 粒度匹配）——让计划少错
第二道：检测（验证增强 + 状态机 + 成功标准）——让错误早发现
第三道：恢复（重规划 + 检查点 + 幂等）——让错误可修复
```

| 防线 | 对应篇 | 成本 |
|---|---|---|
| 预防 | 02（分解） | 低（提示词/契约） |
| 检测 | 03/06（验证） | 低（校验代码） |
| 恢复 | 05（重规划） | 中（LLM 调用） |

> 🎯 核心要点：治理的投资顺序**预防 > 检测 > 恢复**——每前移一道防线，成本降一个量级；"计划验证"（检测）是 2026 年 ROI 最高的投入点（VOLTS 实证：逐 token 验证让小模型 76% 合法计划 vs GPT-4o 7%）。

## 8. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 无验证直接执行 | 级联失败 | 每步验证 |
| 工具不限清单 | 幻觉工具 | 注册表校验 |
| 终止看步骤不看目标 | 提前/过度 | 目标达成判定 |
| 依赖不阻断 | 级联执行 | blocked |
| 验证与执行脱节 | 验证形同虚设 | 执行前验证 |
| 只预防不检测 | 漏网之鱼 | 三道防线齐全 |
| 失败不分类 | 无法对症 | 三大失败目录 |

## 9. 验证增强的落地清单

| 验证点 | 实现 | 成本 |
|---|---|---|
| 计划语法 | strict schema 校验（Output Parser） | 0 |
| 工具存在 | 注册表检查 | 0 |
| 参数合规 | 工具 schema 校验 | 0 |
| 约束满足 | 约束清单检查（PlanningBench 方法） | 0 |
| 依赖合法 | 成环检测 | 0 |
| 步骤结果 | success_criteria 判定 | 0 |
| 状态前置 | 状态机合法性 | 0 |

> 💡 验证增强的全部成本都是"代码成本"（无 LLM 调用）——**这是规划体系 ROI 最高的投入**：一次实现，全部任务受益。VOLTS 的数字（76% vs 7%）是它的上限证明。

## 10. 治理常见误区

| 误区 | 真相 |
|---|---|
| "失败是模型不够强" | 三大失败都是"无验证"的结构性问题 |
| "验证是事后审计" | 验证是执行纪律（执行前+完成后） |
| "级联失败没法防" | 每步验证+依赖阻断+检查点可防 |
| "进度误判靠提示词" | 靠成功标准与目标达成判定（结构） |
| "幻觉动作靠换模型" | 靠工具注册表校验（结构） |
| "验证增强太复杂" | 清单全是零成本代码校验 |

## 11. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 规划三大失败？ | 级联失败（无验证）、动作 schema 幻觉（工具不限）、进度误判（无终止判定） |
| 级联失败怎么防？ | 每步 success_criteria + 依赖阻断（blocked）+ 检查点 + 幂等（事务思维） |
| 验证增强是什么？ | "模型生成计划，代码验证计划"——工具/约束/状态/结果全代码校验 |
| 验证增强的 ROI？ | 全零成本（无 LLM 调用）；VOLTS：小模型 76% vs GPT-4o 7% |
| 三道防线？ | 预防（分解）> 检测（验证）> 恢复（重规划）——投资按此顺序 |
