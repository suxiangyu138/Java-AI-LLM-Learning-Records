# 规划器框架与实现

> 规划器的落地形态：框架内建（LangGraph 显式图）、手写实现（理解本质）、模块化架构（MAP 启示）。2026 年结论：**"LLM 分解 + 代码协调"是推荐的实现哲学**。

## 1. 框架中的规划实现

| 框架 | 规划能力 | 形态 |
|---|---|---|
| LangGraph | 显式图节点（planner/executor 节点） | 最灵活 |
| LangChain | create_plan_execute_agent / Plan 工具 | 开箱即用 |
| Spring AI | Advisor 链 + 手写规划节点 | 需自行组装 |
| CloudWeGo Eino | Plan-Execute 官方示例 | 参考实现 |
| OpenSearch | Plan-Execute-Reflect 注册类型 | 预制角色 |

```python
# LangGraph 规划实现（规划器节点 + 执行循环）
from langgraph.graph import StateGraph, END

def planner_node(state):                    # 规划器
    plan = plan_model.invoke(PLAN_PROMPT.format(goal=state["goal"]))
    return {"plan": parse_plan(plan)}       # 计划 JSON（03 篇契约）

def executor_node(state):                   # 执行器（取一个 pending 步）
    step = next_pending(state["plan"])
    if step is None:
        return {"done": True}
    result = execute_step(step)             # 工具执行
    return {"observation": result, "current_step": step["id"]}

def replanner_node(state):                  # 重规划器（05 篇）
    return {"plan": replan(state, REPLAN_PROMPT)}

graph = StateGraph(State)
graph.add_node("planner", planner_node)
graph.add_node("executor", executor_node)
graph.add_node("replanner", replanner_node)
graph.add_edge("planner", "executor")
graph.add_conditional_edges("executor", decide_next,
    {"continue": "executor", "replan": "replanner", "done": END})
```

| LangGraph 机制 | 对应规划概念 |
|---|---|
| State.plan | 计划状态（03 篇） |
| planner 节点 | 初始规划 |
| conditional edges | 执行/重规划决策 |
| checkpointer | 计划恢复（Memory 03 篇） |

## 2. 手写规划器（50 行理解本质）

```python
class Planner:
    def __init__(self, llm, tools, max_steps=8):
        self.llm, self.tools, self.max_steps = llm, tools, max_steps

    def plan(self, goal, context=""):
        plan = self.llm.generate(PLAN_PROMPT.format(
            goal=goal, context=context, tools=self.tools,
            max_steps=self.max_steps))
        return validate_plan(plan, self.tools)   # 验证增强（06 篇）

    def execute_loop(self, goal):
        plan = self.plan(goal)
        for i in range(self.max_steps):
            step = next_pending(plan)
            if step is None:
                return plan.summarize()          # 步骤耗尽 → 收尾
            result = call_tool(step)             # 执行（工具层）
            if step_failed(result):
                plan = self.replan(goal, plan, result)  # 重规划（05 篇）
            else:
                mark_done(plan, step["id"])
        return plan.summarize(truncated=True)
```

> 💡 手写的价值：把规划器的"规划→执行→重规划→验证"刻进骨子里——与[阶段 1：手写极简 Function-call Agent](../../阶段%201：手写极简%20Function‑call%20Agent/00-阶段总览：手写极简Function-call%20Agent.md) 同哲学：先手写再框架。

## 3. MAP 模块化架构（2026 设计启示）

```text
MAP 五模块（Mila，2026）：
  ├── 冲突监控（检测计划与状态冲突）
  ├── 状态预测（预测步骤后状态）
  ├── 状态评估（评估当前状态）
  ├── 任务分解（拆分子目标）
  └── 任务协调（组装/调度）← 瓶颈所在

生产启示：
  LLM 擅长：分解、评估、预测（独立模块）
  代码擅长：协调、调度、状态机（确定性）
  → 分工：LLM 模块 + 代码协调器（混合架构）
```

| 混合架构 | 组成 | 优势 |
|---|---|---|
| LLM 部分 | 分解/评估/预测提示词 | 灵活性 |
| 代码部分 | 状态机/调度/验证 | 确定性 |
| 结合 | 规划器 = LLM 模块 + 代码骨架 | 又活又稳 |

## 4. 规划器与四组件的接线

| 组件 | 接口 |
|---|---|
| 大脑 | 决策按计划走（step 上下文注入） |
| 执行器/工具 | 计划步骤 → 工具调用（03/07 篇契约） |
| 记忆 | 计划存储（检查点）+ 规划经验（反思回写） |
| 反思 | 重规划触发（05 篇） |
| 输出解析器 | 计划 JSON 解析校验（03 篇） |

> 💡 规划器的"接线图"是[四大核心组件](..%2F..%2FAgent%20四大核心组件%2F08-四大组件协作循环：完整Agent运行时.md) 08 篇运行时的一个切面——规划器在循环中出计划、收观察、发重规划。

## 6. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 规划节点无状态 | 计划丢失 | 计划入 State/检查点 |
| 执行节点无验证 | 级联失败 | 每步验证（06 篇） |
| 全部逻辑塞规划器 | 规划器变大脑 | 职责分离（01 篇） |
| 无重规划边 | 跑偏到底 | conditional edges |
| 检查点粒度粗 | 恢复丢计划 | 计划入检查点 |
| 手写无验证 | 裸循环 | 验证增强必接 |
| 框架隐式规划 | 失控 | 显式节点/显式控制 |

> 🎯 核心要点：规划器实现的成败不在"框架选哪个"，在**"计划有没有状态、执行有没有验证、失败有没有重规划"**——三个有没有决定规划器的可靠性（06 篇三道防线）。

## 7. 规划器测试策略（三层）

| 层 | 测什么 | 工具 |
|---|---|---|
| 单元测试 | 计划校验/状态机/依赖调度 | 单测（纯函数） |
| 集成测试 | 规划→执行→重规划闭环 | 模拟工具环境 |
| 评测回归 | 业务任务集（07 篇） | CI 门禁 |

```text
测试要点：
  校验函数纯测（无 LLM）
  闭环测试用模拟工具（确定性）
  评测集必跑（真实 LLM，协议固定）
  故障注入：工具失败/数据缺失/约束冲突
```

> 💡 规划器的"可测性"是架构质量的风向标——**计划是 JSON、校验是纯函数、状态机是数据结构**，三者可测，规划器就可测；哪一环不可测，哪一环就是隐患。

## 8. 实现常见误区

| 误区 | 真相 |
|---|---|
| "框架内建规划器够用" | 默认无验证/无契约，需自行加固 |
| "规划器不用测试" | 三层测试是可靠性前提 |
| "状态藏全局变量" | 计划/状态必须入 State/检查点 |
| "重规划随便触发" | 触发纪律（05 篇预算） |
| "手写=简陋" | 手写+验证增强是可靠的最小实现 |
| "规划逻辑全给 LLM" | 协调/验证/状态机归代码（确定性） |
