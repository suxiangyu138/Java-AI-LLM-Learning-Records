# 规划评测：从 PlanBench 到生产

> 规划器评测 2026 年体系成形：**PlanningBench（可扩展可验证）、PlanBench-XL（大规模工具生态）、TRAJECT-Bench（过程正确性）**。生产的核心是自建场景集——公开基准只定"模型档位"，自建集才定"业务可用性"。

## 1. 2026 规划基准全景

| 基准 | 测什么 | 规模 | 关键发现 |
|---|---|---|---|
| PlanningBench | 规划正确性（约束清单逐步验证） | 467 实例/6 类/30+ 任务 | 耦合约束骤降；GPT-5.4 全通过 63.17% |
| PlanBench-XL | 大规模工具生态长程规划 | 327 任务/1665 工具 | 阻塞时 51.9%→11.36% |
| TRAJECT-Bench | 工具选择/参数/依赖正确性 | 轨迹级 | 相似工具混淆 |
| PlanBench | 经典规划域 | 多域 | 编排器 ~55% |
| NL-PDDL-Bench | 自然语言→PDDL | 多域 | Llama3.1-8B 计划成功率 80.7% |

> 🎯 核心要点：**基准答案 = "当前模型档位能到哪"**——GPT-5.4 全通过 63%、小模型+验证 76-80%（PDDL 域）——规划不是"模型不行"，是"没做验证增强"。

## 2. PlanningBench 的评测方法（可借鉴到生产）

| 方法 | 说明 |
|---|---|
| 约束清单 | 每个任务配约束检查清单（逐步可验证） |
| 全通过 vs 平均通过 | 全通过（所有约束满足）与平均通过（部分约束）分开报 |
| 可扩展生成 | 数据可程序化生成（规模扩展） |
| RL 可用 | 验证数据可训练（08 篇） |

```text
对生产的启示：
  ① 任务的"约束清单"= 验收标准（规划评测的最小单元）
  ② 全通过/平均通过分开统计（"部分对"与"全对"是不同能力）
  ③ 测试数据程序化生成（回归自动化）
```

## 3. 过程正确性：TRAJECT-Bench 的三元评测

| 维度 | 测什么 | 失败模式 |
|---|---|---|
| 工具选择正确性 | 选了该选的工具吗 | 相似工具混淆 |
| 参数正确性 | 参数填对了吗 | 参数盲选 |
| 依赖/顺序正确性 | 顺序对了吗 | 依赖错序 |

> 💡 只测最终答案会掩盖过程错误（"结果对但过程错"在规划中不可接受——步骤错了结果对是运气）。**轨迹级评测是规划评测的 2026 标准**。

## 4. 自建规划评测集（生产必做）

```text
自建集组成（30-60 个任务）：
  ✓ 代表性任务（覆盖你的业务场景）
  ✓ 多约束任务（耦合约束专项）
  ✓ 长任务（10+ 步）
  ✓ 干扰任务（工具/数据有干扰）
  ✓ 失败注入（工具故障/数据缺失）
```

| 评测指标 | 定义 |
|---|---|
| 计划完成率 | 计划执行到 done 的比例 |
| 目标达成率 | 最终目标真实达成（≠步骤耗尽） |
| 重规划率 | 重规划次数/任务（高=初始计划差） |
| 步骤利用率 | 计划步骤被真实执行比例 |
| 无效动作率 | 幻觉工具/参数占比 |
| 成本/任务 | 规划+执行的 LLM 调用与 token |
| 首计划成功率 | 不重规划直接成功的比例（质量核心） |

## 5. 评测协议固定（跨版本可比）

| 协议项 | 固定 |
|---|---|
| 任务集 | 同一批任务（版本化） |
| 模型 | 同模型档位 |
| 采样 | temperature=0 |
| 判定 | 约束清单判定（非 LLM 主观判） |
| 报告 | 全通过/平均通过分开 |

> ⚠️ 协议陷阱（与 Output Parser 10 篇同源）：**判题方式变化会让分数失真**——用约束清单（确定性判定）而非 LLM 判题（主观波动）。

## 6. 评测结果的使用：三个决策

| 决策 | 依据 |
|---|---|
| 模型档位选择 | 基准成绩 + 成本（规划器档位 vs 质量） |
| 是否微调 | 自建集成绩低 + 场景固定 → 微调路线（08 篇） |
| 架构调整 | 重规划率/首计划成功率 → 分解质量/粒度 |

```text
评测驱动的优化顺序（2026 实践）：
  ① 验证增强（检测层，零模型成本）
  ② 分解质量（提示词/契约）
  ③ 粒度匹配（任务特征）
  ④ 模型升级/微调（最后才花大钱）
```

## 7. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 只测最终答案 | 过程错误被掩盖 | 轨迹级评测 |
| 无约束清单 | 判定主观 | 确定性判定 |
| 公开基准当验收 | 与业务脱节 | 自建集 |
| 无失败注入 | 只看 happy path | 故障任务 |
| 首计划成功率不看 | 重规划掩盖低质 | 分指标报告 |
| 协议不固定 | 版本不可比 | 协议锁定 |
| 评测不回归 | 退化不可知 | CI 回归 |

> 🎯 核心要点：规划评测的三支柱——**自建集（业务相关）+ 轨迹级（过程正确）+ 确定性判定（可复现）**。公开基准定档位，自建集定可用性，两者都不可缺。

## 8. 规划评测自动化（CI 回归）

| 环节 | 自动化做法 |
|---|---|
| 触发 | 模型/提示词/契约/计划结构变更时 |
| 执行 | 同一任务集同一协议重跑 |
| 判定 | 约束清单自动判定（确定性） |
| 门禁 | 首计划成功率回退 >3% 拦截 |
| 报告 | 指标对比（旧基线 vs 新） |

```text
规划评测的 CI 化要点：
  任务集版本化（改动记录）
  判定代码化（约束清单 → 断言）
  指标入仪表盘（07 篇指标全列）
  门禁配置（防静默退化）
```

## 9. 规划评测常见误区

| 误区 | 真相 |
|---|---|
| "公开基准够用" | 与业务分布脱节（自建集必做） |
| "只测最终答案" | 过程错误被掩盖（轨迹级） |
| "LLM 判题就行" | 主观波动大（确定性判定） |
| "评测一次完成" | 持续回归（CI） |
| "失败注入不必要" | 故障任务暴露真实弱点 |
| "指标只看完成率" | 重规划率/无效动作率才是质量信号 |

> 💡 评测的终极目标不是"分数好看"，是**"改动可归因"**——任何一次规划器变更，能立刻知道它提升/回退了什么。没有 CI 回归的规划器，等于没有刹车地改引擎。

## 10. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 规划怎么评测？ | 自建集 + 轨迹级（工具选择/参数/依赖）+ 确定性判定（约束清单） |
| 关键指标？ | 首计划成功率（核心）、重规划率、无效动作率、步骤利用率、成本/任务 |
| PlanningBench 发现？ | 耦合约束骤降；GPT-5.4 全通过 63.17% |
| PlanBench-XL 发现？ | 大规模工具生态：无阻塞 51.9% → 严重阻塞 11.36% |
| 公开基准 vs 自建集？ | 公开定模型档位，自建定业务可用性——两者都不可缺 |
| 评测协议为什么固定？ | 判题/模型/采样变则分数失真（同输出解析器 10 篇） |
| 评测自动化怎么做？ | CI 触发（模型/契约变更）→ 同集同协议重跑 → 约束清单判定 → 门禁（首计划成功率回退 >3% 拦截） |
| 失败注入测什么？ | 工具故障/数据缺失/约束冲突——暴露 happy path 看不到的弱点 |
| 评测三支柱速记？ | 自建集（业务相关）+ 轨迹级（过程正确）+ 确定性判定（可复现） |
| 评测驱动优化的顺序？ | 验证增强（零成本）→ 分解质量 → 粒度匹配 → 模型升级/微调（最后花大钱） |
