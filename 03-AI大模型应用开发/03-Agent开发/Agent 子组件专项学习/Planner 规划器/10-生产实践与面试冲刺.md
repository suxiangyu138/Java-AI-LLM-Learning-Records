# 生产实践与面试冲刺

> 从"能规划"到"可靠规划"：预算治理、12 避坑、面试题与落地检查单——规划器体系收官篇。

## 1. 生产基线（规划器）

| 领域 | 基线 |
|---|---|
| 计划契约 | goal+步骤+依赖+状态+约束+版本六件套（03 篇） |
| 分解质量 | 粒度匹配、约束下放、每步可验证（02 篇） |
| 验证增强 | 工具注册表校验 + 状态机 + 约束检查（06 篇） |
| 重规划 | 目标锚定 + 上下文裁剪 + 最小力度 + 预算（05 篇） |
| 模式选择 | 可预知→ReWOO / 不可预知→PER（04 篇） |
| 评测 | 自建集 + 轨迹级 + 确定性判定（07 篇） |
| 预算 | 重规划 ≤3-5 次、全量重写 ≤1 次、单任务成本上限 |

## 2. 预算治理

| 层 | 预算 | 防什么 |
|---|---|---|
| 规划调用 | 任务 1-2 次初始规划 | 规划风暴 |
| 重规划 | ≤3-5 次/任务 + 触发冷却 | 每观察都重规划 |
| 步骤数 | ≤8-12（默认） | 计划膨胀 |
| 全量重写 | ≤1 次/任务 | 计划反复推倒 |
| 单任务 | 成本上限（token/金额） | 失控级联 |
| 规划输入 | 重规划器输入固定预算（防爆窗） | 上下文爆炸 |

## 2.1 与体系其他模块的协作

| 模块 | 规划器协作点 |
|---|---|
| 记忆系统 | 计划存储（检查点）+ 规划经验资产化（02 篇） |
| 输出解析器 | 计划 JSON 的 strict/校验/修复（03 篇） |
| 反思组件 | 重规划触发 + 教训回写（05 篇） |
| 工具组件 | 步骤→工具调用 + 参数校验（07 篇） |
| 四大核心组件 | 规划器是四组件之一（总览篇） |

> 💡 规划器的"邻居关系"决定了它的边界：**计划吃记忆的上下文、出解析器的契约、触发反思的重规划、调用工具的执行**——接线接对，规划器才"活"在系统里。

## 2.2 面试速记（本体系一页纸）

| 主题 | 核心结论 |
|---|---|
| 定位 | 只回答"做什么按什么序"，职责边界第一 |
| 分解 | 原子/自包含/可验证；粒度与不可预知度成反比 |
| 表示 | 六件套契约（goal/步骤/依赖/状态/约束/版本） |
| 模式 | 可预知→ReWOO（省 20 倍），不可预知→PER（活） |
| 重规划 | 最小力度 + 目标锚定 + 裁剪 + 预算 |
| 失败 | 级联/幻觉/进度误判 → 验证增强（零成本高 ROI） |
| 评测 | 自建集 + 轨迹级 + 确定性判定 + CI 回归 |
| 工程化 | 提示词→验证→微调→换模型（按 ROI 排序） |
| 实现 | "LLM 分解 + 代码协调"混合架构 |

## 3. 12 避坑清单

| # | 坑 | 后果 | 解法 |
|---|---|---|---|
| 1 | 无验证直接执行 | 级联失败 | 每步 success_criteria |
| 2 | 工具不限清单 | 动作幻觉 | 注册表校验 |
| 3 | 重规划无目标锚定 | goal drift | 目标注入 |
| 4 | 重规划塞全量痕迹 | 上下文爆炸 | 摘要+裁剪 |
| 5 | 可预知任务用动态 | 成本翻倍 | ReWOO |
| 6 | 不可预知任务用静态 | 计划过时 | PER |
| 7 | 分解过度/不足 | 漂移或无法执行 | 粒度匹配 |
| 8 | 约束只在目标里 | 耦合约束失败 | 约束下放 |
| 9 | 终止看步骤不看目标 | 提前/过度收尾 | 目标达成判定 |
| 10 | 无评测集 | 退化不可知 | 自建集回归 |
| 11 | 跳过验证直接微调 | 固化错误 | 先验证增强 |
| 12 | 规划器越权 | 变第二个大脑 | 职责边界（01 篇） |

## 4. 面试题（高频 12 题 + 答题要点）

| 题 | 答题要点 |
|---|---|
| 1. 规划器在 Agent 中的角色？ | 任务分解+依赖编排+计划维护；只回答"做什么按什么序"，执行/评估/上下文归其他组件 |
| 2. 任务怎么分解？ | 原子性/自包含/可验证三标准；粒度与不可预知性成反比；约束下放到步骤；MAP：LLM 分解+代码协调 |
| 3. Plan-Execute 和 ReWOO 区别？ | 动态（观察驱动，贵但活）vs 静态（一次 DAG，省 20 倍不能应变）；按可预知度选 |
| 4. 重规划怎么触发？ | 步骤失败/观察偏离/新信息/进度异常；最小力度（步骤级）→升级；目标锚定+上下文裁剪 |
| 5. 规划失败的主要模式？ | 级联失败（无验证）、动作 schema 幻觉（工具不限）、进度误判（无终止判定）；治理=验证增强 |
| 6. 验证增强规划是什么？ | 中间步骤对照约束检查；VOLTS 实证小模型 76% vs GPT-4o 7%；"模型生成计划，代码验证计划" |
| 7. 规划怎么评测？ | 自建集+轨迹级（工具选择/参数/依赖）+确定性判定（约束清单）；首计划成功率/重规划率指标 |
| 8. 规划器成本怎么控？ | 前沿规划+便宜执行；ReWOO 静态化；重规划预算；QLoRA 小模型微调降本 |
| 9. 规划器要微调吗？ | 场景固定+批量大+基线低才微调；SFT+GRPO/QLoRA；验证过滤数据；先提示词+验证增强 |
| 10. 计划的数据结构？ | goal+步骤（summary/tool/params/depends_on/success_criteria/state）+约束+版本；状态机六态 |
| 11. 目标漂移怎么防？ | 重规划注入原始目标 + 已完成摘要 + 状态机防重复 + 里程碑检查 |
| 12. 2026 规划研究最一致的发现？ | 长程退化；编排器 PlanBench ~55%、网页导航 14% vs 78%；Gartner >40% 项目取消；破局=验证增强+分层分解 |

## 5. 演进趋势（2026-2027）

| 趋势 | 现状 | 影响 |
|---|---|---|
| 验证增强标配化 | VOLTS 式验证进入生产 | 小模型可用性大增 |
| 规划微调产品化 | SFT+GRPO 工具化 | 规划器专训成本下降 |
| 混合规划（LLM+经典） | PDDL/搜索结合 | 确定性规划回归 |
| 评测体系化 | PlanningBench 开源 | 规划评测有统一工具 |
| 长程规划攻坚 | 12-24 个月成熟预估 | 工程先做"窄而稳" |

> 💡 工程启示：**2026-2027 规划器的投入顺序——验证增强 > 分解质量 > 模式选型 > 评测回归 > 微调**。别把规划可靠性押在"换更强模型"上。

## 6. 落地检查单（上线前逐项打勾）

```text
□ 计划契约六件套（goal/步骤/依赖/状态/约束/版本）
□ 分解：粒度匹配 + 约束下放 + 每步可验证
□ 验证增强：工具校验 + 状态机 + 约束检查
□ 模式选型：按可预知度选 ReWOO/PER（含混合）
□ 重规划：目标锚定 + 裁剪 + 力度分级 + 预算
□ 评测集 30-60 任务 + 首计划成功率基线
□ 预算：重规划/步骤/成本上限齐
□ 监控：重规划率/无效动作率/成本每任务
□ 故障演练：工具故障/数据缺失/耦合约束各一次
□ 与记忆/解析器接口一致性（计划契约 + 版本）
```
