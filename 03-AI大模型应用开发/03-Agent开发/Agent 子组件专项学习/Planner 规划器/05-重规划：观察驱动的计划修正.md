# 重规划：观察驱动的计划修正

> 计划是"假设"，执行是"验证"——观察与计划不符是常态，重规划是让计划跟上现实的机制。2026 年两大纪律：**目标锚定（防漂移）+ 上下文裁剪（防爆窗）**。

## 1. 重规划的触发信号

| 信号 | 例子 | 动作 |
|---|---|---|
| 步骤失败 | 工具报错 | 局部调整该步 |
| 观察偏离 | 数据与预期不符 | 更新后续步骤 |
| 新信息 | 搜索结果改变前提 | 重写相关部分 |
| 进度异常 | 提前完成/严重滞后 | 提前收尾/加步 |
| 约束变化 | 预算/时间收紧 | 简化剩余计划 |

> 🎯 核心要点：**不是每个观察都要重规划**——"微调该步"与"重写计划"是不同量级的动作；过度重规划 = 每次观察都烧一次 LLM 调用（成本与不稳定之源）。

## 2. 重规划的三种力度

| 力度 | 动作 | 成本 | 适用 |
|---|---|---|---|
| 步骤级 | 改/删/加单步 | 低 | 单步失败（默认） |
| 段级 | 重写后续一段 | 中 | 阶段性偏离 |
| 全量重写 | 重新规划整个任务 | 高 | 目标变化/根本性偏离 |

```text
力度选择原则：
  先最小力度（步骤级）→ 不够再升级
  全量重写是最后手段（等于承认初始计划失效）
```

## 3. 目标锚定：重规划的"北极星"

| 做法 | 说明 |
|---|---|
| 原始目标注入 | 每次重规划把 goal 原样带入提示词 |
| 已完成摘要 | 告诉重规划器"已做了什么"（防重复） |
| 剩余约束 | 预算/时间/资源现状 |
| 偏离原因 | 为什么触发重规划（决策依据） |

```python
REPLAN_PROMPT = """原始目标：{goal}
已完成步骤摘要：{done_summary}
当前观察：{observation}
偏离原因：{reason}
请更新剩余计划（保留已完成步骤，只输出剩余步骤）：
{remaining_plan}"""

# 目标锚定 + 防重复 + 上下文裁剪（三合一）
```

> ⚠️ 目标漂移（goal drift）是重规划的头号失败：**子代理多轮后逐渐偏离原目标**——锚定原始目标 + 已完成摘要，是 2026 年验证过的防线。

## 4. 上下文裁剪：防 context blow-up

| 错误做法 | 后果 |
|---|---|
| 把全部执行痕迹塞给重规划器 | 上下文爆炸（超窗） |
| 全量历史重述 | 每轮 token 翻倍 |
| 不传已完成摘要 | 重规划器重复已做步骤 |

| 正确做法 | 说明 |
|---|---|
| 只传必要状态 | goal + 摘要 + 当前观察 + 剩余计划 |
| 已完成摘要化 | 每步一行（"step2: 已查 Q2 数据"） |
| 观察截断 | 工具结果 4KB 截断 |
| 预算内 | 重规划输入固定预算 |

> 💡 上下文裁剪是 2026 年运营警示的第一名（Planner 把整个 trace 塞进下一轮提示词导致超窗）——重规划器的输入应该"小而全"，不是"全而杂"。

## 5. 重规划与状态机配合

```text
重规划动作对状态机的影响：
  新增步骤 → pending
  删除步骤 → skipped
  修改步骤 → 重置为 pending（若未执行）
  已完成步骤 → 不动（防重复）
```

| 配合纪律 | 说明 |
|---|---|
| 已完成不重做 | 状态机保护（防重复执行烧钱） |
| 删除留痕 | skipped 而非物理删除（审计） |
| 依赖重算 | 修改后依赖链校验（成环检测） |

## 6. 重规划的预算控制

| 项 | 默认 | 防什么 |
|---|---|---|
| 重规划次数上限 | 3-5 次/任务 | 重规划风暴 |
| 重规划触发冷却 | 连续失败才触发 | 每观察都重规划 |
| 重规划输入预算 | 固定 token | 上下文爆炸 |
| 全量重写限制 | ≤1 次/任务 | 计划反复推倒 |

> ⚠️ 重规划是成本大户（每次 1-2 次 LLM 调用）——**监控重规划率**（07 篇指标）：过高 = 初始计划质量差，不是重规划机制的问题。

## 7. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 无目标锚定 | 越跑越偏 | goal 注入 |
| 无已完成摘要 | 重复执行 | 摘要传递 |
| 全量痕迹传入 | 超窗 | 上下文裁剪 |
| 过度重规划 | 每观察都烧钱 | 触发冷却+力度分级 |
| 重规划不留痕 | 无法审计 | 计划版本链 |
| 已完成步骤重做 | 浪费 | 状态机保护 |
| 全量重写频繁 | 计划不稳 | 全量重写限额 |

> 🎯 核心要点：重规划的正确姿势是**"最小力度 + 目标锚定 + 上下文裁剪 + 预算限制"**四件套——重规划是"修正"不是"重来"，是"小步调整"不是"推倒重来"。

## 8. 重规划与反思的分工

| 维度 | 重规划（本模块） | 反思（反思模块） |
|---|---|---|
| 触发 | 观察与计划不符 | 结果质量不足/失败 |
| 动作 | 更新计划 | 改进策略/提示词 |
| 频率 | 每步可触发（预算内） | 里程碑/失败后 |
| 产出 | 新计划版本 | 教训/批评意见 |
| 关系 | 反思的结论可作为重规划输入 | 重规划的结果供反思评估 |

> 💡 边界：**重规划是"改路线"，反思是"改策略"**——工具失败了重规划换路（改计划），多次失败反思换法（改做法）。两者配合：反思结论 → 记忆 → 下次任务规划直接采用（02 篇 9 节经验资产化）。

## 9. 重规划案例走查（调试场景）

```text
任务：修复 CI 失败（不可预知任务，Plan-Execute）
① 初始计划：查日志 → 定位错误 → 修复 → 重跑验证
② 执行 step1：日志查询成功 → 观察：错误指向依赖版本
③ 偏离检测：计划步骤 2"定位错误"已完成（成功标准满足）→ 继续
④ 执行 step3 修复：改版本号 → 重跑失败（新错误：API 变更）
⑤ 触发重规划（步骤级）：新增"查 API 变更文档"步骤（最小力度）
⑥ 执行新增步骤 → 修复成功 → 重跑通过 → 收尾
⑦ 教训记忆化：该项目的依赖升级需查 API 变更（跨任务收益）
```

| 走查要点 | 对应纪律 |
|---|---|
| 步骤级重规划（非全量） | 最小力度 |
| 成功标准判定继续 | 状态机 |
| 教训入记忆 | 经验资产化 |
| 预算内（1 次重规划） | 预算限制 |

## 10. 重规划常见误区

| 误区 | 真相 |
|---|---|
| "重规划=全量重写" | 步骤级调整是默认，全量是最后手段 |
| "每观察都重规划" | 触发冷却 + 成功标准判定 |
| "重规划器看全部痕迹" | 上下文裁剪（摘要+观察） |
| "目标不用重申" | 无锚定必漂移 |
| "重规划无预算" | 每次都是 LLM 调用，必须限额 |
| "重规划不留痕" | 版本链是审计与评测的数据基础 |

## 11. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 重规划触发时机？ | 步骤失败/观察偏离/新信息/进度异常 |
| 重规划力度怎么选？ | 最小力度优先：步骤级→段级→全量重写（最后手段） |
| 目标漂移怎么防？ | 每轮重规划注入原始目标 + 已完成摘要 |
| 上下文爆炸怎么防？ | 重规划器只收"goal+摘要+观察+剩余计划"（裁剪） |
| 重规划预算？ | ≤3-5 次/任务 + 触发冷却 + 全量重写 ≤1 次 |
| 重规划 vs 反思？ | 重规划改路线（计划），反思改策略（做法）；反思结论入记忆供下次规划 |
| 重规划输入裁剪清单？ | goal + 已完成摘要 + 当前观察（截断）+ 剩余计划——四件套，别带全量痕迹 |
| 重规划触发冷却？ | 连续失败才升级触发（步骤级→段级→全量），防每观察都烧钱 |
| 重规划四件套速记？ | 最小力度 + 目标锚定 + 上下文裁剪 + 预算限制——缺一不可 |
| 重规划对状态机的影响？ | 新增→pending、删除→skipped、修改→重置 pending、已完成不动——防重复执行 |
| 重规划的成本量级？ | 每次 1-2 次 LLM 调用——重规划率 >30% 说明初始计划质量差，先修分解而非重规划 |
| 重规划是修正还是重来？ | 小步调整（步骤级）是常态，推倒重来（全量重写）是最后手段且限额 1 次 |
