# 工作记忆：上下文窗口管理

> 工作记忆 = 模型此刻"看得到"的全部内容。2026 年核心矛盾：上下文窗口越来越大（1M+），但"喂得多 ≠ 答得好"——窗口管理的本质是**预算纪律**。

## 1. 工作记忆的组成与预算

| 组成 | 占比建议 | 说明 |
|---|---|---|
| 系统提示词 | 固定（冻结） | 缓存友好、降本 50-90% |
| 对话历史 | 预算大头 | 有界读取 + 滚动摘要 |
| 记忆注入 | ≤10-15% | 记忆管理器装配 |
| 工具结果 | ≤10% | 截断 + 摘要 |
| 当前输入 | 余量 | 给模型思考空间 |

```text
预算公式（示例，窗口 200K）：
  system 5K + 历史 100K（最近 30 条 + 摘要）+ 记忆 15K + 工具结果 20K + 输入 60K
  —— 固定比例 + 按任务调节
```

> 🎯 核心要点：**上下文预算必须"显式分配"而非"自然填满"**——没有预算的窗口管理，最后总是被工具结果和历史撑爆。

## 2. 有界读取：历史不是全给

| 策略 | 做法 | 适用 |
|---|---|---|
| 最近 N 条 | 只取最近 N 条消息（如 30） | 默认 |
| 时间窗 | 只取最近 M 分钟 | 实时会话 |
| 摘要前置 | 旧历史压缩成摘要 + 最近原文 | 长会话标配 |
| 关键词回溯 | 命中关键词的历史单独检索 | 需要旧细节时 |

```python
def bounded_history(thread, n=30, summary_fn=None):
    msgs = load_recent(thread, n)              # 有界读取：不删行，只不喂
    if older_exists(thread, n):
        summary = summary_fn(load_all(thread))  # 超窗部分 → 滚动摘要
        return [{"role": "system", "content": f"历史摘要：{summary}"}] + msgs
    return msgs
```

> 💡 关键区别：**"不喂给模型"≠"删除数据"**——完整历史仍入库（审计/回溯/重切），工作记忆只是视图。有界读取是视图，不是删除。

## 3. 滚动摘要：压缩的艺术

| 摘要方式 | 做法 | 优缺点 |
|---|---|---|
| 单轮摘要 | 超窗时一次压缩全部旧历史 | 简单，丢细节 |
| 增量摘要 | 每 N 轮更新一次摘要 | 保持最新，成本可控 |
| 分层摘要 | 周/日/会话三级摘要树 | 可回溯任意粒度 |
| 结构化事实 + 摘要 | 关键事实单独存（不走摘要） | **防摘要丢关键信息** |

| 摘要常见坑 | 后果 | 解法 |
|---|---|---|
| 关键数字被吞 | "订单 1023 已取消"没了 | 事实单独结构化存储 |
| 摘要里带指令 | 注入风险 | 摘要当数据不当指令 |
| 每次全量重摘要 | 成本翻倍 | 增量摘要 |
| 摘要过长 | 失去压缩意义 | 限制摘要 token（如 1-2K） |

## 4. 记忆注入：给模型"该知道的"而不是"所有的"

```text
注入优先级（2026 共识，记忆管理器装配）：
  当前问题相关事实 → 活跃决策 → 用户偏好 → 近期事件 → 滚动摘要
  按此顺序装到注入预算为止
```

| 注入质量指标 | 说明 |
|---|---|
| 命中率 | 用户提及的历史事实能否注入 |
| 噪声率 | 注入内容中无关项占比 |
| 注入成本 | 每轮记忆注入的 token |
| 决策影响 | 注入后回答质量提升（A/B） |

> ⚠️ 注入的两极失败：**不注入**（模型失忆，用户重复信息）与 **全注入**（噪声淹没信号，模型迷失）。注入是"挑着给"，不是"能给就给"。

## 5. 工具结果的上下文管理

| 原则 | 做法 |
|---|---|
| 截断 | 单次结果 ≤4KB，超长摘要 |
| 只留最后 | 中间结果只保留最新状态 |
| 结构化压缩 | 表格→摘要统计，长文→要点 |
| 写操作结果 | 记录影响摘要（行数/状态） |

## 6. 提示词冻结与缓存（工作记忆的经济学）

| 做法 | 收益 |
|---|---|
| system 层冻结 | prompt caching 命中（降本 50-90%） |
| 工具定义固定排序 | 缓存键稳定 |
| 记忆注入位置固定 | 缓存前缀不失效 |
| 变化内容放尾部 | 前缀缓存最大化 |

> 🎯 核心要点：工作记忆管理的三原则——**有界（历史按需取）、有序（注入按优先级）、有价（缓存最大化）**。窗口再大也治不好"什么都塞"的病。

## 7. 工作记忆的监控指标

| 指标 | 信号 |
|---|---|
| 每轮上下文 token | 超预算 → 有界读取失效 |
| 摘要更新频率 | 过高 → 摘要策略过细 |
| 注入命中率 | 低 → 召回/提取问题（06/05 篇） |
| 缓存命中率 | 低 → 提示词/顺序不稳定 |
| 超窗率 | >0 需关注 → 压缩策略待改 |

## 8. 摘要质量评估

| 评估方法 | 做法 |
|---|---|
| 关键事实保全率 | 摘要后抽查原对话中的 10 个关键事实是否还在摘要里 |
| 摘要长度 | 是否在预算内（1-2K token） |
| 信息失真率 | 摘要与原文矛盾项占比 |
| 检索可用性 | 摘要能否被检索定位（关键词命中） |

```text
摘要质量的工程保险：
  关键事实单独结构化存储（不走摘要）——摘要允许"丢失细节"，不允许"丢失事实"
```

## 9. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 无预算分配 | 自然填满窗口 | 显式分配（02 篇 1 节公式） |
| 历史全量注入 | 长会话必爆 | 有界读取 + 摘要 |
| 摘要吞事实 | 关键信息丢失 | 事实单独存 |
| 注入无优先级 | 噪音优先于相关 | 装配优先级（04 节） |
| 工具结果不截断 | 结果堆积 | 4KB 截断 + 摘要 |
| 提示词频繁改 | 缓存失效 | 冻结 system 层 |
| 记忆注入位置乱 | 缓存前缀失效 | 固定注入位置 |
| 每轮重复摘要 | 成本翻倍 | 增量摘要 |

## 9.5 自动压缩（Auto-Compaction）：超窗的自动处理

| 触发条件 | 动作 |
|---|---|
| 上下文达到阈值（如 80%） | 自动触发压缩 |
| 用户新消息到达但预算不足 | 压缩后继续 |
| 工具结果超大 | 立即截断+摘要 |

| 压缩策略 | 说明 |
|---|---|
| 丢弃最旧 + 摘要 | 默认（旧消息 → 摘要，保留最近原文） |
| 丢弃工具结果中间态 | 只留最终状态 |
| 事实优先保留 | 关键事实移出摘要（结构化存储） |
| 用户固定提示 | 锚定不可压缩内容 |

> 💡 自动压缩是"最后防线"而非"默认策略"——**它应该很少被触发**（触发频繁 = 预算设计不合理）。2026 年生产实践：显式预算 + 增量摘要为主，自动压缩兜底。

## 10. 实战演练：200 条消息压缩进 30K 上下文

```text
场景：32K 窗口（留 2K 给输入与思考），历史 200 条消息共 60K token
目标：压缩到 30K

步骤：
  ① 固定 system（2K）
  ② 最近 20 条原文（15K）——核心上下文，不压缩
  ③ 中间 60 条滚动摘要（5K）——增量摘要生成
  ④ 最旧 120 条 → 事实提取（结构化入库）+ 年度级摘要（3K）
  ⑤ 记忆注入（3K，按优先级装配）
  ⑥ 工具结果摘要（2K）
  合计：2+15+5+3+3+2 = 30K ✅

关键取舍：旧消息的价值通过"事实提取"保留（细节丢了，
         但"发生了什么"没丢——这正是记忆系统存在的意义）
```

## 11. 窗口管理在不同框架中的落地

| 框架 | 机制 | 本模块对照 |
|---|---|---|
| LangChain | ConversationBufferWindowMemory / SummaryMemory | 有界读取 / 滚动摘要 |
| LangGraph | 消息裁剪节点 + summarization 节点 | 自动压缩 |
| Spring AI | MessageChatMemoryAdvisor（window 参数） | 有界读取 |
| Mem0 等产品 | 记忆注入（产品内建） | 注入装配 |

> 💡 框架的内存组件只解决"存取"，**预算分配与装配优先级（本模块核心）仍需应用层配置**——框架给容器，工程给纪律。面试速记：窗口管理三问——"历史给多少？记忆给多少？超了怎么办？"能答出预算分配、装配优先级、自动压缩三层，即为合格。
