# 记忆冲突与时序：更新与遗忘

> 事实会变（用户搬家了、订单取消了）、会矛盾（新旧偏好冲突）。2026 年两条主线：**claim 生命周期状态机**（结构化淘汰）与**双时间戳**（"什么时候是事实"可查）——记忆系统的"成熟"标志是会更新、会遗忘。

## 1. 为什么要处理冲突

| 不处理的后果 | 例子 |
|---|---|
| 矛盾事实同时召回 | "用户住上海"与"用户住北京"都注入 |
| 过期事实误导 | 用旧地址下单 |
| 无法追溯演变 | 不知道用户何时搬的家 |
| 决策不稳定 | 每次召回结果不同（注入随机） |

> 🎯 核心要点：**"不更新"的记忆是负债**——过期事实比没有事实更危险（它"看起来对"）。记忆系统的分水岭不是"能不能存"，是"能不能正确地忘"。

## 2. claim 生命周期状态机

```text
PROPOSED（新提取，未验证）
  → ACCEPTED（被确认/多次提及）
  → DEPRECATED（被新事实取代/过期）
```

| 状态 | 是否参与召回 | 转出条件 |
|---|---|---|
| PROPOSED | ⚠️ 低权重 | 用户确认/重复提及 → ACCEPTED |
| ACCEPTED | ✅ 正常召回 | 被 supersedes → DEPRECATED |
| DEPRECATED | ❌ SQL 级过滤 | 保留归档（审计），永不召回 |

```sql
-- 查询只读 ACCEPTED（SQL 级淘汰，性能好且不漏审计）
SELECT * FROM claims
WHERE entity = $1 AND state = 'ACCEPTED'
  AND (valid_until IS NULL OR valid_until > now());
```

> 💡 **DEPRECATED 不是删除**：旧事实归档保留（演进可查、审计可溯），只是不参与召回——"降权归档"是 2026 年记忆维护的黄金法则。

## 3. 矛盾处理：supersedes 链

| 冲突类型 | 例子 | 处理 |
|---|---|---|
| 直接取代 | "住上海"→"住北京" | 新 claim supersedes 旧 claim |
| 部分修正 | "喜欢 Python"→"更喜欢 Go" | 并存 + 时效权重 |
| 范畴变化 | "上班"→"退休" | 旧 claim 批量废弃 |
| 暂时波动 | "本周很忙" | 不升 ACCEPTED（低置信度） |

```python
def ingest_claim(entity, text, confidence=0.8):
    with tx():
        conflicts = find_conflicts(entity, text)     # 冲突检测
        new = insert_claim(entity, text, confidence)
        for old in conflicts:
            update(old, state="DEPRECATED", supersedes=new.id)  # 原子废弃
        return new
```

> ⚠️ 冲突检测的时机：**保存时**（写入路径内检测邻近事实）——2026 前沿（MOSAIC）证明"保存时检测"优于"召回时仲裁"：前者一次事务解决，后者每次召回都要裁决。

## 4. 双时间戳：事实的"成立时间"与"得知时间"

| 时间戳 | 含义 | 例子 |
|---|---|---|
| event_time | 事实在世界成立的时间 | "2026-03-01 起住北京" |
| ingested_at | 系统得知的时间 | "2026-08-09 系统知道" |

| 价值 | 应用 |
|---|---|
| 点查询（As-of） | "2026-06 时用户住哪？"→ 按 event_time 查 |
| 时效加权 | 召回时新事实权重高 |
| 冲突裁决 | event_time 靠后的胜出（而非"谁后听说"） |
| 审计 | 得知时间与事实时间分离 |

```text
双时间戳是 Zep/Graphiti 的核心（bi-temporal 模型）：
  迁移事件（用户搬家）→ 两个时间戳都有记录
  → "他什么时候搬的？"与"我们什么时候知道的？"是两个问题，都能答
```

## 5. 遗忘机制：主动的"放下"

| 遗忘方式 | 做法 | 适用 |
|---|---|---|
| 状态废弃 | DEPRECATED（保留归档） | 矛盾/取代（默认） |
| 置信度降级 | 低置信度不参与召回 | 一次性/波动事实 |
| 时间衰减 | 过旧事实降权 | 非关键偏好 |
| 保留期清理 | 合规要求的硬删 | 隐私/合规 |
| 用户主动删除 | 记忆管理 UI（veto） | 用户控制权 |

> 💡 用户控制权是 2026 记忆产品的合规焦点（Zep 内置 user veto）——**"记住"要用户同意，"忘掉"要用户可操作**，双向才有信任。

## 6. 时序推理：让记忆"会算时间"

| 能力 | 实现 | 收益 |
|---|---|---|
| 时效加权 | 召回按 event_time 加权 | 新事实优先 |
| 演变链 | supersedes 链回放 | "用户偏好的演变"可讲 |
| 点查询 | event_time 条件查询 | 历史事实问答 |
| 趋势识别 | 同实体事实时间线 | 行为分析 |

## 7. 维护任务与预算

| 维护任务 | 频率 | 成本 |
|---|---|---|
| 冲突检测 | 每次写入 | 低（SQL 邻近查询） |
| 状态晋升 | 事件触发 | 低 |
| 批量清理 | 定期（周/月） | 中 |
| 归档迁移 | 定期 | 中 |

> 🎯 核心要点：记忆维护的三原则——**保存时检测冲突（一次事务解决）、废弃不删除（归档可审计）、时间戳双轨（演变可追溯）**。做到这三点，记忆系统才从"仓库"变成"活的知识"。

## 8. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 覆盖式更新 | 旧事实被删，演变不可查 | ADD-only + supersedes |
| 召回时仲裁 | 每轮都裁决矛盾 | 写入时检测 |
| 无状态机 | 无法区分新旧 | claim 生命周期 |
| 单时间戳 | 不知道"何时成立" | 双时间戳 |
| 遗忘=删除 | 审计断链 | 归档优先 |
| 无用户 veto | 隐私投诉 | 记忆管理 UI |
| 冲突检测过重 | 写入延迟 | SQL 邻近查询 + 异步 |

## 9. 记忆演变的可观测性

| 观测面 | 指标 |
|---|---|
| 冲突率 | 每百条事实的冲突数（高 → 提取粒度问题） |
| 废弃率 | DEPRECATED 占比（高 → 事实时效性强，提取该标注 valid_until） |
| 演变链长度 | 同实体 supersedes 链平均长度（长 → 用户偏好频繁变化） |
| 召回命中分布 | 命中事实的时效（旧事实占比高 → 遗忘机制失效） |
| 遗忘任务量 | 定期清理规模（评估归档效率） |

```text
可观测性价值：记忆维护是"持续工程"而非"上线即完"
  —— 冲突率/废弃率/演变链是记忆健康度仪表盘
```

## 10. 记忆维护时间线示例

| 时间点 | 事件 | 记忆操作 |
|---|---|---|
| T1 | 用户："我住上海" | PROPOSED 入库（置信 0.7） |
| T2 | 用户再确认（"上海好呀"） | 晋升 ACCEPTED |
| T3 | 用户："我搬北京了" | 新 claim supersedes 旧 claim（旧 DEPRECATED） |
| T4 | 问题"用户住哪？" | 召回 ACCEPTED（北京） |
| T5 | 问题"用户 2026-06 住哪？" | 点查询 event_time（上海） |
| T6 | 用户："删掉我的位置信息" | 硬删（用户 veto）或匿名化 |

> 💡 这个时间线是"记忆维护的标准答案"——新事实入状态机、冲突走 supersedes、旧事实可点查询、用户可删除。面试题"记忆怎么更新"就按这条线答，完整且有 2026 依据。注意 T3 的正确姿势：**不是 UPDATE 旧行，而是新增行 + supersedes 指向**——这正是"单遍 ADD-only 哲学"在维护层的延伸。
