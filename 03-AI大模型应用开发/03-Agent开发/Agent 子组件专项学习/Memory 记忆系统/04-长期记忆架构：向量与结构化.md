# 长期记忆架构：向量与结构化

> 长期记忆 = 跨会话持久的事实与知识。2026 年架构共识：**向量（语义片段）+ 结构化事实（关系表/图谱）双轨制**，复杂系统再加时序图谱——"一个库全装"成为主流趋势。

## 1. 长期记忆的两种存储形态

| 形态 | 存什么 | 检索方式 | 代表 |
|---|---|---|---|
| 语义记忆（向量） | 知识片段/文档化记忆 | 相似度 TopK | 向量库、PGVector |
| 结构化记忆（事实） | 事实/偏好/状态（带属性） | 精确查询、图谱遍历 | claim 表、KV、图谱 |

```text
长期记忆选型心法：
  "这条记忆要语义召回还是精确查询？"
  知识片段 → 向量；事实/偏好 → 结构化；随时间变的事实 → 时序图谱（07 篇）
```

> 🎯 核心要点：**向量管"像不像"，结构化管"对不对"**——用户偏好"要简洁回答"用结构化（精确命中），知识库内容用向量（语义召回）。2026 年主流是双轨并行，不是二选一。

## 2. 结构化事实：claim 表（关系表即图谱）

```sql
CREATE TABLE claims (
    id          BIGSERIAL PRIMARY KEY,
    agent_id    TEXT NOT NULL,           -- 记忆归属（用户/Agent 命名空间）
    entity      TEXT NOT NULL,           -- 实体：user:42 / order:1023
    claim       TEXT NOT NULL,           -- 事实："偏好简洁回答"
    state       TEXT DEFAULT 'PROPOSED', -- PROPOSED→ACCEPTED→DEPRECATED
    confidence  REAL,
    event_time  TIMESTAMPTZ,             -- 事实在世界成立的时间
    ingested_at TIMESTAMPTZ DEFAULT now(), -- 系统得知时间（双时间戳见 07 篇）
    evidence    JSONB,                   -- 溯源：来源消息/文档
    supersedes  BIGINT REFERENCES claims(id)
);
CREATE INDEX idx_claims_entity ON claims (entity) WHERE state = 'ACCEPTED';
```

| 设计点 | 作用 |
|---|---|
| state 过滤 | 查询只读 ACCEPTED（SQL 级淘汰） |
| entity 索引 | 按实体精确召回 |
| evidence | 溯源（答案→claim→证据→来源） |
| supersedes | 矛盾处理（新事实取代旧事实） |

> 💡 "关系表即图谱"是 2026 年重要趋势（Capital One 等）——不用专用图数据库，用 claim 表 + 递归 CTE 做多跳遍历，一套权限/备份/审计解决。

## 3. 向量记忆：语义召回通道

| 维度 | 配置建议 |
|---|---|
| 向量维度 | 与嵌入模型匹配（如 1024/1536） |
| 分块 | 记忆片段粒度（一事一记） |
| 混合索引 | 向量 + BM25（召回融合用） |
| 元数据 | agent_id/类型/时间戳（过滤用） |

```text
语义召回陷阱：
  向量相似 ≠ 事实正确（"用户喜欢 Python"与"用户会用 Python"相似但不同）
  → 结构化事实走精确查询，向量只做"候选召回"再校验
```

## 4. 混合检索：三通道融合

| 通道 | 覆盖 | 代表技术 |
|---|---|---|
| 语义 | 相似表达 | 向量 TopK |
| 关键词 | 精确词 | BM25/FTS5 |
| 图谱 | 关系链 | 2 跳遍历（递归 CTE） |
| 时效 | 最新事实 | 时间加权 |

```text
融合：多路召回 → RRF（互惠排名融合，无参）→ 按 token 预算截断
```

| 融合要点 | 说明 |
|---|---|
| RRF 无参 | 按排名倒数求和，不需调权重 |
| 去重 | 多路命中同一 claim 去重 |
| 时效加权 | 新事实权重高（配合 07 篇时序） |
| 预算截断 | 融合后按注入预算截断 |

## 5. 一库化：向量 + 事实 + 历史一个库

| 方案 | 结构 | 适合 |
|---|---|---|
| PG 一库化 | 向量列 + claims 表 + chat 表 + 语义缓存 | 中小项目（默认推荐） |
| Redis 一库化 | Hash/JSON + 向量检索 + TTL | 延迟敏感 |
| 多库分工 | 业务库 + 向量库 + Redis | 大项目/既有架构 |

> 💡 一库化收益：一套权限/备份/审计（合规成本骤降）。OpenFang 模式：单 SQLite 三个表（kv_store/memory_fragments/entities-relations）即可跑通个人项目，生产平滑迁移 PG。

## 6. 长期记忆的写入事务

| 纪律 | 做法 |
|---|---|
| ACID 写路径 | 提取+落库+废弃旧事实在**一个事务**（防半成品） |
| 幂等 | 同事实重复提取不重复落库（唯一键） |
| 异步化 | 提取与检索异步（不阻塞主对话） |
| 写入预算 | 每轮写入 ≤N 条（防事实轰炸） |

## 7. 长期记忆架构自检清单

```text
□ 知识片段与事实分离存储（向量 vs claim 表）
□ 事实带状态机（PROPOSED/ACCEPTED/DEPRECATED）
□ 事实带溯源（evidence）与时间戳（双时间戳）
□ 混合检索（语义+关键词+图谱+时效）已接入
□ 注入预算与装配优先级已配置
□ 写入走事务 + 幂等 + 异步
□ 一库化或明确的多库分工
□ 按 agent_id 隔离（多用户不串）
```

> 🎯 核心要点：长期记忆的架构判断标准——**"跨会话后，该记住的还能精确命中吗？"**——能，说明双轨制成立；不能，先查召回（06 篇）再查提取（05 篇），别先加存储。

## 8. 存储选型落地表

| 记忆类型 | 存储推荐 | 理由 |
|---|---|---|
| 结构化事实（claims） | PostgreSQL（一库化） | 事务/索引/RLS/审计全套 |
| 语义片段 | PGVector / Milvus | 向量 + 混合检索 |
| 会话历史 | PostgreSQL | 关系表标准应用 |
| 高频 KV 状态 | Redis | 亚毫秒 + TTL |
| 个人项目 | SQLite（OpenFang 三表） | 零运维 |
| 图谱（时序） | Neo4j/FalkorDB（Zep 系） | 双时间戳图遍历 |

| 选型心法 | 说明 |
|---|---|
| 默认 PG 一库化 | 一套权限/备份/审计，合规成本最低 |
| Redis 只放热状态 | 别把事实/历史塞 Redis（丢失风险） |
| 图谱按需 | 只有"事实随时间变化是核心"才上图谱 |
| SQLite 只做个人/教学 | 生产必须 PG |

## 9. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 事实全塞向量 | 精确查询退化 | 结构化 + 向量双轨 |
| 图谱当摆设 | 无点查询需求也上图谱 | 时序敏感才用图谱 |
| 一库化后无隔离 | 多租户串 | agent_id 分区 + RLS |
| 索引不更新 | schema 变更后召回失效 | 迁移 + 重建索引 |
| 写入不事务 | 半成品事实入库 | ACID 写路径 |
| 幂等缺失 | 重复提取重复入库 | 唯一键（entity+claim） |
| 存储与召回脱节 | 存了取不出 | 先设计召回再定存储 |

## 10. 何时升级到时序图谱（claim 表 → Zep/Graphiti）

| 信号 | 说明 | 动作 |
|---|---|---|
| 点查询成为需求 | "他 6 月住哪"被频繁提问 | 双时间戳建模 |
| 事实频繁变化 | 用户偏好月月变 | 演变链 + 时效加权 |
| 冲突率上升 | 新旧事实打架多 | 状态机升级图谱 |
| 合规要求溯源 | "何时知道"必须可查 | 双时间戳 + 审计 |
| 多跳推理需求 | "和他都换过城市的用户" | 图谱遍历 |

```text
升级判断：claim 表（关系表）能覆盖"当前事实 + 简单演变"；
         Zep/Graphiti 解决"时间维度的一等公民查询"
         —— 需求出现前，别提前上图谱（成本与复杂度）
```

## 11. 容量与成本规划

| 项 | 估算公式 | 示例（10 万用户） |
|---|---|---|
| 事实量 | 用户 × 每用户事实（50-200 条） | 500-2000 万条 claim |
| 向量量 | 事实量 + 知识片段 | 同量级 |
| 存储 | claim ~200B/条 + 向量 ~1KB/条 | 数百 GB 级 |
| 索引 | 向量索引内存占用 | 与向量数线性 |
| 写入吞吐 | 用户活跃度 × 提取频率 | 数百 TPS |

```text
成本治理要点：
  事实去重与合并（减少 30-50% 冗余）
  冷热分层（热用户内存，冷用户归档）
  向量索引量化（精度可接受时）
  定期清理（保留策略驱动）
```

> 💡 长期记忆是"持久资产"，成本随用户线性增长——**上线前就要做容量模型**（本表公式），否则增长期被迫迁移架构是最大的隐性成本（迁移远贵于扩容）。
