# 反思与工具：外部验证

> 反思的黄金标准是**外部验证**：测试跑不跑得过、检索核不核得上、执行成不成功——"这通过了测试"永远优于"我觉得对"。2026 年：外部验证从"可选项"变成"结构性需求"（out-of-band）。

## 1. 为什么外部验证优于自我评判

| 维度 | 自我评判 | 外部验证 |
|---|---|---|
| 证据 | "我觉得对" | "测试通过了/检索核上了" |
| 盲区 | 与生成器共享 | 无（客观） |
| 可审计 | 不可复现 | 可复现 |
| 失败模式 | 谄媚/幻影 | 少（源错则错） |
| 成本 | LLM 调用 | 工具调用（常更便宜） |

> 🎯 核心要点：**外部验证把"反思"从"观点"变成"事实"**——评判器从"模型判"降级为"工具验"，可靠性层级直接从 L4 跳到 L1-L2（03 篇）。

## 2. 外部验证的类型

| 验证类型 | 工具 | 验证什么 |
|---|---|---|
| 执行验证 | 测试套件/代码执行 | 代码/动作是否正确 |
| 检索验证 | 搜索/数据库查询 | 事实是否真实存在 |
| Schema 验证 | JSON Schema 校验 | 结构是否合规 |
| 一致性验证 | 交叉比对多源 | 结论是否被支持 |
| 动作验证 | 幂等/状态检查 | 副作用是否符合预期 |

## 3. CRITIC 模式：外部知识批评

```text
CRITIC 循环：
  输出 → 外部工具（web 搜索/DB/代码解释器）→ 事实性批评 → 修订 → 再验证
  专治：事实幻觉（"编造的引用""错误的价格"）
  局限：外部源本身错则批评错；批评者=生成者则盲区
```

| CRITIC 要点 | 说明 |
|---|---|
| 验证工具化 | 每个 claim 可核验 |
| 适用 | 知识密集任务 |
| 与 RAG 联动 | 检索即验证（Self-RAG token 同类） |
| 成本 | 固定每检查点开销 |

> 💡 CRITIC 与[文档解析](../../Agent%20配套技术生态模块/文档解析/00-文档解析总览.md)/[联网搜索](../../Agent%20配套技术生态模块/联网搜索工具/00-联网搜索工具总览.md)体系的联动：外部验证的"工具"正是 Agent 配套技术生态模块的产物——搜索验证事实、数据库验证状态、代码沙盒验证执行。

## 4. Out-of-band 评估：结构性需求（2026 关键结论）

| 概念 | 说明 |
|---|---|
| In-band | 成功信号在记录内（评委看记录判断） |
| Out-of-band | 成功信号在真实世界（真实结果验证） |

```text
Zenodo 2026 结论：
  当目标的成功信号在记录之外（如"用户满意度"），
  任何看记录的评判器都会产生进度幻影
  → out-of-band 评估（真实世界结果）是结构性需求
  → 放大评判器规模无法解决（最强 in-band 仍错 44%）
```

| 场景 | 验证方式 |
|---|---|
| 代码任务 | 测试执行（in-band 可用） |
| 问答 | 检索核验（in-band 可用） |
| 业务目标（留存/转化） | 真实指标（**必须 out-of-band**） |
| 用户满意度 | 真实反馈（out-of-band） |

## 5. 验证增强反思的实现

```python
def verify_reflect(claim_draft, tools):
    # ① 提取可验证声明
    claims = extract_claims(claim_draft)
    # ② 外部验证每个声明
    results = {}
    for c in claims:
        results[c] = verify_with_tools(c, tools)   # 搜索/DB/执行
    # ③ 失败声明 → 批评 → 修订
    failed = [c for c, r in results.items() if not r.passed]
    if failed:
        critique = {"verdict": "fail",
                    "issues": [{"claim": c, "evidence": f"核验失败: {r.reason}"
                                } for c, r in zip(failed, results.values())]}
        return revise(claim_draft, critique)
    return claim_draft
```

| 实现要点 | 说明 |
|---|---|
| 声明提取 | 把输出拆成可验证单元 |
| 逐条验证 | 每条声明独立核验 |
| 失败反馈 | 批评带 evidence（核验结果） |
| 修订闭环 | 修订后重新验证（循环） |

## 6. 验证成本与级联（与 04 篇衔接）

```text
验证成本控制：
  ① 先验便宜的（schema/正则）
  ② 再验中等的（DB 查询）
  ③ 最后验贵的（搜索/外部 API）
  ④ 全部失败才反思修订
  级联验证 = 04 篇级联反思的验证侧
```

## 7. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 自评当验证 | 进度幻影 | out-of-band |
| 验证源不可信 | 源错则错 | 多源交叉 |
| 验证无级联 | 全走贵验证 | 先便宜后贵 |
| 声明不提取 | 整段验证模糊 | 声明级验证 |
| 验证不修订 | 验了不改 | 闭环 |
| in-band 评业务目标 | 幻影 | 真实指标 |
| 验证结果不进审计 | 无法复现 | 验证日志 |

## 8. 验证工具选型表

| 验证需求 | 工具 | 成本 | 可靠性 |
|---|---|---|---|
| 代码/动作正确 | 测试套件/代码沙盒 | 低 | 最高 |
| 事实核验 | 搜索 API/数据库 | 中 | 高 |
| 结构合规 | JSON Schema 校验 | 0 | 最高 |
| 数据一致性 | 交叉比对多源 | 中 | 高 |
| 业务状态 | 状态机/幂等检查 | 低 | 高 |
| 数值合理性 | 规则断言（金额>0） | 0 | 最高 |

> 💡 验证工具与[Agent 配套技术生态模块](../../Agent%20配套技术生态模块/数据库交互/00-数据库交互总览.md)的映射：数据库交互（状态验证）、联网搜索（事实核验）、代码执行沙盒（执行验证）、文档解析（来源核验）——外部验证的"工具库"就是配套生态的产物。

## 9. 验证级联的完整实现

```text
验证级联（从便宜到贵）：
  ① schema 校验（0 成本）→ 结构错 → 直接修复
  ② 规则断言（0 成本）→ 值域错 → 直接修复
  ③ 数据库查询（低）→ 状态错 → 触发反思
  ④ 搜索核验（中）→ 事实错 → 触发反思
  ⑤ 代码执行（中）→ 运行错 → 触发反思
  —— 大部分错误在第 1-2 层被"非反思"地修掉
```

| 级联收益 | 数据 |
|---|---|
| 反思触发率 | 从"每次"降到"真失败才触发" |
| 成本 | 反思成本省 50-80% |
| 修复质量 | 规则修复确定性 > LLM 反思 |

## 10. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 为什么外部验证优于自评？ | "这通过了测试"是事实，"我觉得对"是观点 |
| 外部验证类型？ | 执行/检索/schema/一致性/动作五类 |
| CRITIC 模式？ | 输出→外部工具核验→事实批评→修订→再验证（治幻觉） |
| out-of-band 是什么？ | 成功信号在记录外 → 真实世界验证（结构性需求） |
| 验证怎么省钱？ | 级联：schema→规则→DB→搜索→执行（便宜先行） |
| 验证的审计？ | 验证日志（可复现） |
| in-band vs out-of-band？ | 信号在记录内（测试）vs 在真实世界（业务指标）——后者必须 out-of-band |
| 验证与反思的闭环？ | 验证失败 → 批评（带 evidence）→ 修订 → 再验证——"验-批-修-验"循环 |
| 验证的失败模式？ | 验证源本身错（外部源不可信）——多源交叉验证兜底 |
| 验证与级联的关系？ | 验证级联（schema→规则→DB→搜索→执行）与反思级联同构——便宜先行 |
| 验证的审计价值？ | 验证日志可复现——"通过了什么验证"是审计的第一证据 |

## 8.5 验证驱动反思的指标

| 指标 | 目标 |
|---|---|
| 验证覆盖率 | 可验证输出 100% 覆盖 |
| 验证通过率 | 与反思触发率负相关（通过率高=反思少） |
| 验证-反思命中率 | 验证失败被反思修正的比例 |
| 修正后通过率 | 反思后重新验证的通过率（闭环质量） |

## 8.6 外部验证的优先级排序

| 优先级 | 验证方式 | 原因 |
|---|---|---|
| 1 | 执行验证（测试/沙盒） | 最客观（通过/失败无歧义） |
| 2 | Schema 校验 | 零成本且确定 |
| 3 | 数据库/状态验证 | 业务事实锚点 |
| 4 | 检索核验 | 事实可追溯 |
| 5 | 多源交叉 | 单源不可信时 |
| 6 | LLM 评判 | 最后手段（前五都无法验证时） |

> 💡 优先级原则：**能执行就不检索、能检索就不评判**——外部验证的"客观性"排序就是优先级排序，LLM 评判永远是最后手段（03 篇可靠性层级同构）。

> 🎯 核心要点：外部验证是反思的"地基"——**"有验证的反思是工程，无验证的反思是仪式"**。2026 年的投入方向：把能验证的都验证掉（执行/检索/schema），剩下的才交给评判器。
