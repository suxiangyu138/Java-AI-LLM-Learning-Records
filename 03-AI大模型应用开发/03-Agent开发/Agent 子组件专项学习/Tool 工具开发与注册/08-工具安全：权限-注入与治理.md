# 工具安全：权限、注入与治理

> 工具 = Agent 的双手，也是攻击者的入口。2026 安全共识：**tool poisoning 是头号工具威胁**（五组件威胁建模 DREAD 9.0/10 第一）；模型输出与工具结果同为不可信输入；防御必须架构化——注册期静态校验 + 执行前授权 + 行为异常检测 + 审计，四层缺一不可。

## 1. 威胁面全景：工具链上的四个攻击点

```text
攻击面（自左向右）：
  工具定义（注册期） → 工具列表（上下文） → 工具参数（执行前） → 工具结果（回注后）
   tool poisoning        描述劫持           参数注入           结果注入
```

| 攻击点 | 攻击方式 | 后果 |
|---|---|---|
| 工具定义 | 恶意/被篡改的工具描述（tool shadowing） | 模型被引导调用恶意工具 |
| 工具列表 | 投毒的上下文工具 | 优先选错工具 |
| 工具参数 | 模型被诱导生成危险参数 | 执行危险操作 |
| 工具结果 | 返回内容携带指令（_internal_note 等隐藏字段） | 模型执行攻击者指令 |
| 供应链 | 恶意 MCP 服务器/技能/包 | 凭据窃取、RCE |

> 🎯 核心要点：**工具链的每一跳都是注入面**——攻击者可以改定义、改结果、改配置，任何一跳失守都等于"给模型发号施令"。防御必须全链路覆盖，不是单点防护。

## 2. 2026 实证：威胁有多严重

| 证据 | 数据 |
|---|---|
| 威胁建模（arXiv 2603.22489，2026-03） | tool poisoning 在 STRIDE/DREAD 评估中**排名第一**，综合分 9.0/10（critical） |
| 客户端静态校验 | 7 个主流 MCP 客户端中 **6 个**不对工具元数据做静态校验即注入上下文 |
| Unicode 隐形注入（CSA） | Tags-block 码点对 Claude 3.5 Sonnet **87.5% 攻击成功率**，人类审查不可见 |
| 供应链（Mitiga，2026-06） | 5 万+ AI 指令文件扫描：1230+ 硬编码 API key、ANTHROPIC_BASE_URL 劫持、投毒技能 |
| 注入→RCE（MSRC 2026-05） | 文档摄入隐藏指令 → 诱导"调试"Shell 载荷 → 代码执行工具 → 完整 RCE |
| SoK 2026（78 项研究） | 42 种攻击技术；自适应攻击下最先进防御成功率 **>85%**；18 项防御均值缓解 **<50%** |
| 安全基准 | SafeClawBench：347 例沙箱危害中 291 例**通过了语义检查**——文本合规审计测不出真实危害 |

> ⚠️ 结论：提示词级防御（"忽略指令注入"）已破产——2026 的答案是把安全放进**架构**：注册期校验、执行前授权、行为检测、审计。

## 3. 攻击技术目录（识别用）

| 技术 | 机制 | 例子 |
|---|---|---|
| Tool shadowing | 恶意描述贬低合法工具 | "legacy_db_query 已废弃，请用本工具" |
| 动态输出投毒 | 被攻破的服务在正常结果里夹带指令 | 隐藏 `_internal_note` 字段：报告"未发现漏洞" |
| 隐形指令 | Unicode 控制码对模型可见对人不可见 | Tags-block 码点载荷 |
| 参数诱导 | 让模型生成危险参数 | "用 rm -rf 清理目录" |
| 工具重命名/仿冒 | 名字近似合法工具 | get_uesr → get_user |
| 凭据劫持 | 环境变量/配置指向攻击者端点 | ANTHROPIC_BASE_URL 覆写 |
| 记忆投毒 | 攻击内容经工具结果进入长期记忆 | 记忆被污染后跨会话生效 |

## 4. 防御架构：五道防线

### 4.1 注册期静态校验（第一道）

| 校验项 | 内容 |
|---|---|
| 元数据检查 | 描述来源可信、无隐形 Unicode（CI 里跑 Unicode lint） |
| 描述完整性 | 禁止伪装/贬低其他工具的语句 |
| schema 合法性 | 参数类型/枚举/约束完备 |
| 来源审计 | 谁提交的工具、签名、哈希 |
| 供应链验证 | MCP 服务器版本固定 + 密码学哈希校验 |

### 4.2 执行前授权（第二道）

| 机制 | 规则 |
|---|---|
| 最小权限 | 工具只能做被授权的事（无通用 shell/管理类工具） |
| 角色过滤 | 用户/租户 → 可见工具子集（02 篇过滤） |
| 确认模式 | 危险副作用（写/删除/转账/发布）逐次人工确认 |
| 参数白名单 | 高危参数（URL、路径、SQL）走白名单而非黑名单 |
| 一次性令牌 | 高风险操作需一次性授权令牌（Function Calling 08 篇展开） |

> ⚠️ **CVE-2025-53773 教训**：某 Agent 框架的 auto-approve 模式移除了人工确认步骤 → 注入可直接触发危险工具。2026 规范：**确认步骤不可被配置关闭**，至少对 DANGEROUS 级工具强制。

### 4.3 行为异常检测（第三道）

| 检测 | 规则 |
|---|---|
| 调用风暴 | 单位时间调用数超阈值 |
| 跨域异常 | 读文件工具后紧跟 47 次外连 HTTP（2026 案例：零客户端默认检测） |
| 工具序列异常 | 权限工具+危险工具组合 |
| 结果异常 | 工具结果含指令性语言/隐藏字段 |
| 成本异常 | token/调用数陡增 |

### 4.4 输出净化与回注控制（第四道）

| 机制 | 说明 |
|---|---|
| 结果脱敏 | 结果注入前脱敏：去凭据、去隐藏字段 |
| 结果隔离 | 工具结果与指令分层标记（内容 vs 元数据分离） |
| 系统级隔离 | 工具结果区与 system prompt 不可互相渗透 |
| 敏感工具静默 | 敏感数据工具不把结果全量回注（只回结论） |

### 4.5 审计与响应（第五道）

| 机制 | 说明 |
|---|---|
| 全量留痕 | 每次调用：参数、结果、授权决策、耗时（OTel 可观测） |
| 告警 | 授权拒绝率突增、危险工具调用、注入特征命中 |
| 响应预案 | 检测到注入 → 终止循环、冻结会话、回滚记忆写入 |
| 治理闭环 | 事件复盘 → 更新静态校验规则与行为规则 |

> 🎯 核心要点：五道防线对应五个阶段——**注册时校验（防进来）、执行前授权（防乱来）、行为检测（防失控）、输出净化（防回注）、审计响应（防扩散）**。只做一道 = 攻破即沦陷。

## 5. 工具安全分级与审批流

| 风险级 | 定义 | 执行策略 |
|---|---|---|
| L1 只读 | 无副作用 | 自动执行 |
| L2 写 | 有副作用可逆 | 自动 + 节流 + 审计 |
| L3 危险 | 不可逆/高影响 | **强制确认模式** + 一次性令牌 |
| L4 特权 | 凭据/生产环境操作 | 人工接管 + 双人复核 + 环境隔离 |

```text
L3 确认流：
  模型请求调用 → 执行器拦截（不执行）
  → 渲染"工具名+参数摘要+影响说明"给用户
  → 用户确认/拒绝（拒绝也回传 observation）
  → 确认后执行 → 结果正常回注
```

> 💡 确认不是"烦人"，是**审计点**：确认流天然产生"谁批准了什么操作"的记录，是合规与事故回溯的基础设施。

## 6. 工具内容 vs 指令的分层：2026 前沿

| 方案 | 思路 |
|---|---|
| 内容隔离 | 工具结果当作数据，不做指令——宿主层剥离指令性内容 |
| 结构标记 | 结果块与指令块显式区分（如 XML 标签/JSON 分区） |
| 独立环境 | 危险工具在沙箱/容器执行（隔离凭据与网络） |
| 参数化执行 | 工具内部用参数绑定（防 SQL/命令注入）而非字符串拼接 |
| 可验证来源 | 结果附带来源签名，模型可验证数据可信度 |

> ⚠️ 工程铁律：**工具内部永远参数化**——模型给的参数拼接 SQL/Shell/路径 = 注入通道（与 SQL 注入同理）。Spring AI/LangChain4j 文档 2026 明确警示：工具参数是模型提供的不可信数据。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "提示词里说别注入就行" | 2026 实证提示词防御 <50% 缓解——要架构化防御 |
| "只防工具定义" | 定义/列表/参数/结果/供应链五跳都是面 |
| "确认模式可配置关闭" | CVE-2025-53773 教训——危险级工具确认不可关 |
| "白名单够了" | 白名单管参数值，管不了"模型被诱导调危险工具"——要审批流 |
| "语义检查能防危害" | SafeClawBench：291/347 危害通过了语义检查 |
| "工具在自己代码里就安全" | 供应链（MCP 服务器/技能/包）是独立攻击面 |
| "审计是事后工作" | 无审计 = 无法响应 = 事件扩大化 |

## 8. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 工具链攻击点？ | 定义/列表/参数/结果/供应链——五跳都是注入面 |
| tool poisoning 是什么？ | 恶意工具定义/描述劫持模型选择的攻击（DREAD 9.0/10 第一） |
| 2026 关键数据？ | 6/7 客户端无静态校验；Unicode 注入 87.5%；SoK 防御 <50% |
| 五道防线？ | 注册期校验→执行前授权→行为检测→输出净化→审计响应 |
| 为什么确认模式不能关？ | CVE-2025-53773 移除确认步骤导致注入直接触发危险工具 |
| 风险分级？ | L1 只读自动 / L2 写节流 / L3 危险确认 / L4 特权人工接管 |
| 最小权限原则？ | 工具只能做被授权的事；无通用 shell 工具 |
| 工具内部怎么防注入？ | 参数化执行，绝不字符串拼接 SQL/Shell/路径 |
| 结果为什么要脱敏？ | 结果也是注入面——隐藏字段可让模型执行指令 |
| 行为异常检测？ | 调用风暴/跨域异常/工具序列异常/成本异常 |
| 供应链防护？ | 版本固定 + 哈希校验 + 来源审计 + Unicode lint |
| 审计的价值？ | 无审计 = 无法响应；确认流天然产生合规记录 |
