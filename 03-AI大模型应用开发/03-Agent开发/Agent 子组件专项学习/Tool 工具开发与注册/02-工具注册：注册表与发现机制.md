# 工具注册：注册表与发现机制

> 注册表 = 工具的"户口本"：name → 定义 + 执行器 + 元数据（权限/分类/版本）的单一事实来源。2026 共识：注册从"启动时全量塞入"走向"运行时按需发现"，但注册表始终是中枢——所有声明、过滤、校验、审计都围着它转。

## 1. 注册表是什么

| 项 | 说明 |
|---|---|
| 定义 | 工具元数据的集中存储：name、description、schema、执行器引用、权限、tag、版本 |
| 定位 | 单一事实来源（Single Source of Truth）：声明、发现、过滤、审计都读它 |
| 形态 | 内存 Map（单进程）/ Bean 容器（Spring）/ 独立服务（多 Agent 共享）/ 配置中心（跨部署） |

```java
// 工具注册记录的最小字段（示意）
record ToolRegistration(
    String name,            // 唯一标识：create_issue
    String description,     // 模型决策依据
    JsonSchema schema,      // 参数契约
    ToolExecutor executor,  // 执行器引用
    Set<ToolTag> tags,      // 分类/权限/域（过滤与治理用）
    String version,         // 版本号，支持灰度与回滚
    RiskLevel risk,         // 风险分级：READ / WRITE / DANGEROUS
    boolean enabled         // 开关：下线不删
) {}
```

> 🎯 核心要点：注册表回答三件事——**"有哪些工具"（枚举）、"这个工具是什么"（契约）、"谁可以用、能不能自动跑"（权限/风险）**。第三件事最容易被忽略，却是生产事故的高发区。

## 2. 注册时机：静态注册 vs 动态注册

| 方式 | 时机 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 静态注册 | 应用启动时扫描注解/配置文件 | 简单、可预检冲突 | 工具多了全量入上下文 | 工具 <20 的小型 Agent |
| 动态注册 | 运行时按需注册/注销 | 上下文精简、支持插件热装 | 需要发现与缓存机制 | 工具生态大、多租户 |
| 外部注册中心 | 独立服务管理，多 Agent 共享 | 统一治理、跨应用复用 | 多一跳网络、一致性成本 | 企业级多 Agent 平台 |

> 💡 2026 趋势：**注册与声明分离**——注册表全量保存，声明（注入模型上下文）按需进行。注册是"有没有"，声明是"给不给模型看"，两者别混为一谈（05 篇 tool_search）。

## 3. 注册表的核心操作

| 操作 | 职责 | 关键点 |
|---|---|---|
| register | 登记新工具 | 冲突检测：重名、schema 校验、描述唯一性 |
| lookup | 按 name 查定义 | 执行循环的查找入口（O(1)） |
| filter | 按 tag/权限过滤 | 声明前的过滤：不给模型看无权工具 |
| list | 枚举全部/部分 | 管理界面、审计用 |
| update | 升级定义 | 版本化：旧调用兼容 or 明确废弃 |
| unregister | 下线 | 不硬删——先禁用（enabled=false），观察无调用再删 |
| validate | 注册期静态校验 | 描述/参数/返回值结构检查（08 篇安全防线第一道） |

> ⚠️ 注册期的静态校验是 2026 安全共识的**第一道防线**：工具元数据在进上下文前就应被检查——2026 威胁建模实证 6/7 主流客户端完全不做这一步，使 tool poisoning 成为 DREAD 9.0/10 的头号威胁（08 篇）。

## 4. 冲突检测：注册时就要解决的问题

| 冲突类型 | 场景 | 处置 |
|---|---|---|
| 重名 | 两个模块都注册 get_user | 启动即报错（fail-fast），不允许覆盖 |
| 描述重叠 | 两个工具描述高度相似 | 拒绝注册并提示改写——模型无法区分重叠描述（2026 实测选错率高） |
| schema 冲突 | 同名参数类型不同 | 拒绝，防止模型按旧契约调用 |
| 权限冲突 | 工具声明只读、实现有写操作 | 注册期强制校验实现签名/注解，不匹配拒绝 |
| 版本冲突 | 新旧版本并存 | 显式版本号 + 路由策略（灰度/回滚） |

> 🎯 核心要点：冲突检测不是"运行时遇到再说"，而是**注册期 fail-fast**——一次模糊的注册，会在每次调用时放大成本（选错工具、调错参数、重试风暴）。

## 5. 工具过滤：给模型"够用"的列表

2026 最佳实践：与其给模型 60 个工具让它挑，不如先过滤到 ~8 个相关工具再让它选——两阶段选择（先分类、后选具体工具）显著优于全量选择。

| 过滤维度 | 规则 | 例子 |
|---|---|---|
| 权限 | 只注入当前用户/租户有权的工具 | 普通用户不见 admin 工具 |
| 域（domain） | 按任务域过滤 | 订单域任务只注入订单工具 |
| 前提条件 | 环境不满足的不注入 | 未连数据库不注入 SQL 工具 |
| 风险 | 危险工具默认不自动注入 | 转账工具需显式开启 |
| 会话状态 | 按会话进度动态增删 | 上一步完成才注入下一步工具 |

```text
声明管线（2026 标准）：
  注册表全量
    → 权限过滤（用户/租户）
    → 域过滤（任务上下文）
    → 数量治理（保留 Top-N，超限转动态发现）
    → 注入模型上下文（静态部分）
    + 动态发现兜底（tool_search 按需加载，05 篇）
```

> 💡 过滤不是"删掉用不到的工具"，而是**把决策负担从模型移回应用**——模型擅长在 8 个工具里选，不擅长在 60 个里选。

## 6. 注册表与声明的解耦：2026 架构

| 架构 | 做法 | 收益 |
|---|---|---|
| 传统（注册=声明） | 注册表里有什么全注入 | 简单，但 >20 工具即上下文膨胀 |
| 解耦（注册≠声明） | 注册表全量，声明按需 | token 下降、选择准确率上升 |
| 外部注册中心 + 运行时校验 | schema 存中心（如 Cloud Storage），模型先识别意图、再拉取相关描述符、逐字段程序化校验（Google Context-Aware Polymorphic Schema Validation，Gemini 3 Flash/ADK） | 注册中心热更新免重部署、跨 Agent 交接确定性校验、防"注意力弥散" |

> ⚠️ 2026 重要变化：Google 的运行时 schema 校验方案把"注册中心"提升为**一等基础设施**——schema 不再打包进提示词，而是像 DNS 一样按需解析。这对工具生态 >50 个的企业是方向性选择（05 篇对比 OpenAI tool_search）。

## 7. 注册表治理：版本与生命周期

| 治理项 | 规范 |
|---|---|
| 版本管理 | 语义化版本；破坏性变更必升 major |
| 灰度上线 | 新版本先 10% 流量，观察调用成功率和模型选择率 |
| 废弃流程 | 先禁用 → 观察 N 天无调用 → 删除定义 → 移除执行器 |
| 调用统计 | 每次调用记：工具名、耗时、结果状态、token 成本 |
| 审计日志 | 谁注册的、谁改过、何时下线（合规必备） |
| 性能 | lookup O(1)；过滤在注册表层完成，不在循环内扫全表 |

> 🎯 核心要点：工具注册表在 2026 已经不只是"内存 Map"——它是**治理层**：过滤、版本、审计、静态校验全在注册边界完成。把注册表做成纯查找表，等于放弃所有治理机会。

## 8. 常见误区

| 误区 | 真相 |
|---|---|
| "注册=启动时扫描注解" | 那只覆盖静态注册；动态注册/外部中心是生态变大后的必然 |
| "工具冲突运行时解决" | 注册期 fail-fast 更便宜——运行时冲突已造成错误调用 |
| "注册表就是工具列表" | 注册表还承载权限、过滤、版本、审计 |
| "工具越多越好，全注入" | 过滤到 ~8 个相关工具，选择准确率显著更高 |
| "下线=删除" | 先禁用观察，防存量调用/旧会话引用断裂 |
| "注册不需要校验" | 注册期静态校验是反 tool poisoning 的第一道防线（6/7 客户端缺失） |
| "所有 Agent 共享一个注册表" | 多 Agent 用外部中心但要分区：全局公共 + 租户私有 |

## 9. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 工具注册表是什么？ | name → 定义+执行器+元数据的单一事实来源 |
| 注册表四要素？ | 唯一 name、description、schema、executor，外加权限/风险/版本元数据 |
| 静态注册 vs 动态注册？ | 启动全量扫描 vs 运行时按需——生态大了必须动态 |
| 注册和声明的关系？ | 注册是"有没有"，声明是"给不给模型看"——2026 已解耦 |
| 冲突检测有哪些？ | 重名、描述重叠、schema 冲突、权限冲突、版本冲突——注册期 fail-fast |
| 工具过滤维度？ | 权限/域/前提条件/风险/会话状态——先过滤再选择 |
| 为什么只给 ~8 个工具？ | 两阶段选择优于全量选择，模型在少量工具中选得更准 |
| 注册期静态校验做什么？ | 检查工具元数据合法性，防 tool poisoning 进上下文 |
| 工具下线流程？ | 禁用 → 观察无调用 → 删除定义 → 移除执行器 |
| 注册表在 2026 的定位？ | 治理层（过滤/版本/审计/校验），不只是查找表 |
| Google 运行时 schema 校验？ | 注册中心化 + 意图识别 + 按需拉取描述符 + 逐字段校验 |
| 注册表性能要求？ | lookup O(1)，过滤在注册层完成，不进循环内扫表 |
