# 工具声明与协议：从提示词到原生协议

> 声明 = 把工具定义交给模型的方式。演进主线：**提示词手写 JSON → 各家原生协议 → MCP 统一分发**。2026 现状：OpenAI `parameters`/Anthropic `input_schema`/MCP `inputSchema` 三分天下但同源（都是 JSON Schema），协议层封装是生产标配。本章对照三协议并给出统一适配方案。

## 1. 演进史：三代声明方式

| 代 | 方式 | 特点 | 结局 |
|---|---|---|---|
| 1.0 | 提示词手写 JSON 格式 | 无需协议支持、旧模型可用 | 格式漂移、无结构校验——淘汰 |
| 2.0 | 原生工具协议（FC） | 结构化声明、流式、校验 | 2024 至今主流（OpenAI 事实标准） |
| 3.0 | MCP 分发协议 | 一次定义多宿主、跨语言跨进程 | 2026 生态收敛方向 |

> 🎯 核心要点：协议解决的是"**怎么把契约传给模型、怎么把结果传回来**"的格式问题；工具本体的质量（描述/schema）在任何协议下都是决定性变量（03 篇）。

## 2. OpenAI 协议（事实标准）

```json
// 声明侧：tools 数组
{
  "tools": [{
    "type": "function",
    "function": {
      "name": "get_weather",
      "description": "查询城市天气。",
      "parameters": { "type": "object", "properties": { "city": { "type": "string" } }, "required": ["city"] }
    },
    "strict": true
  }],
  "tool_choice": "auto",
  "parallel_tool_calls": true
}
```

```jsonc
// 调用侧：模型输出 tool_calls 数组
{ "tool_calls": [
    { "id": "call_abc123",
      "type": "function",
      "function": { "name": "get_weather", "arguments": "{\"city\":\"北京\"}" } }
  ] }

// 回传侧：tool 消息（arguments 是 JSON 字符串，需解析）
{ "role": "tool", "tool_call_id": "call_abc123", "content": "晴 32°C" }
```

| 要点 | 说明 |
|---|---|
| `tool_choice` | auto / required / none / 指定工具名（强制调用场景） |
| `parallel_tool_calls` | 是否允许一轮多调用（默认 true，有依赖时关掉） |
| `strict` | 参数结构强约束（03 篇） |
| 回传配对 | tool 消息必须引用已存在的 tool_call_id |

## 3. Anthropic 协议（块结构）

```json
// 声明侧
{ "tools": [{
    "name": "get_weather",
    "description": "查询城市天气。",
    "input_schema": { "type": "object", "properties": { "city": { "type": "string" } }, "required": ["city"] }
  }] }
```

```jsonc
// 调用侧：content 块结构
{ "content": [
    { "type": "tool_use", "id": "toolu_01", "name": "get_weather",
      "input": { "city": "北京" } }   // input 已是对象，无需二次解析
  ],
  "stop_reason": "tool_use" }

// 回传侧：user 消息内的 tool_result 块
{ "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "toolu_01", "content": "晴 32°C" }
  ] }
```

> 💡 与 OpenAI 关键差异：① input 直接是对象（OpenAI 是字符串要 parse）；② 结果包在 user 消息的块里（OpenAI 是独立 tool 角色）；③ 工具描述支持缓存断点（Anthropic 缓存读折扣，Function Calling 09 篇有缓存深潜）。

## 4. MCP 协议（分发层）

| 项 | 说明 |
|---|---|
| 工具定义 | `inputSchema`（JSON Schema），与 OpenAI/Anthropic 同源 |
| 调用方式 | `tools/call`（请求）/ 结果 JSON 返回 |
| 声明时机 | 客户端 `tools/list` 拉取服务器全部工具 |
| 分发形态 | 一次定义，Copilot/Claude Code/Cursor 等任何兼容宿主可调 |
| 适配成本 | 单宿主工具走 MCP 有 client-server 开销（JSON-RPC/传输层） |

```text
MCP 工具定义（简）：
  tools: [
    { name: "create_issue",
      description: "创建 Issue",
      inputSchema: { type: "object", properties: {...}, required: [...] } }
  ]
```

> 🎯 核心要点：MCP 不发明新契约——**契约仍是 JSON Schema，MCP 解决的是"谁在执行、怎么跨进程调用、怎么发现"**。工具定义写一次，MCP 让它处处可用（09 篇服务器架构）。

## 5. 三协议对照表

| 维度 | OpenAI | Anthropic | MCP |
|---|---|---|---|
| 参数键 | `parameters` | `input_schema` | `inputSchema` |
| 参数形态 | 字符串（arguments 需 parse） | 对象（input 直接可用） | 对象 |
| 调用输出 | `tool_calls` 数组 | `tool_use` 块（content 内） | `tools/call` 响应 |
| 结果回传 | `role: tool` 消息 | user 消息内 `tool_result` 块 | 响应 result |
| 配对键 | `tool_call_id` | `tool_use_id` | `_meta`/按序 |
| 强制调用 | tool_choice 指定名 | tool_choice + 工具名 | 无标准（宿主决定） |
| strict 支持 | ✅ | ✅ | ❌（宿主层） |
| 动态发现 | tool_search（05 篇） | 工具发现（defer_loading 变体） | tools/list + 注册中心演进 |
| 适用 | 单模型应用 | 单模型应用 | 跨宿主/跨语言/共享工具 |

## 6. 统一适配层：为什么要封装

| 问题 | 适配层解法 |
|---|---|
| 各家参数键/回传格式不同 | 抽象 ToolCall 内部模型：name + arguments(对象) + callId |
| 供应商切换要改调用代码 | 协议适配器把各家消息互转为内部规范 |
| 工具定义要发给多供应商 | 一份 JSON Schema 定义，适配层翻译成各家键名 |
| 框架已封装（Spring AI/LangChain4j） | 直接用框架抽象，别手写协议（09 篇） |

```java
// 统一适配层核心模型（示意）
record ToolCall(String name, Map<String, Object> arguments, String callId) {}
record ToolResult(String callId, String content, boolean success) {}
// 适配层职责：OpenAI JSON 字符串 → parse → ToolCall；Anthropic 块 → ToolCall
```

> ⚠️ 生产铁律：**协议认 OpenAI，能力看需求**——OpenAI 格式是事实互转标准（DeepSeek/Qwen 等国产模型均兼容）；但 strict、并行、流式差异要在适配层做能力探测，别假设所有供应商行为一致（Function Calling 10 篇有探针验证方法）。

## 7. 声明的编排：system prompt 与 tools 的分工

| 内容 | 放哪 | 理由 |
|---|---|---|
| 工具使用规则（何时调、调完怎么用） | system prompt | 全局策略，不走 schema |
| 工具描述（三要素） | tools 数组/schema | 结构化，协议处理 |
| 工具间的依赖说明 | 各自 description | 模型按描述组织顺序 |
| 安全规则（禁止调用的、审批要求） | system prompt + 执行层强控 | 提示词是软约束，执行层才是硬边界（08 篇） |

> 🎯 核心要点：**软约束进提示词、硬约束进执行层**——提示词告诉模型"应该怎么做"，执行层保证"只能怎么做"。2026 安全共识：模型遵守提示词是期望，不是保障。

## 8. 常见误区

| 误区 | 真相 |
|---|---|
| "还在提示词里手写 JSON 工具" | 1.0 时代做法——无结构校验，格式漂移 |
| "参数要自己 parse 成对象" | OpenAI 要 parse，Anthropic/MCP 直接给对象——适配层统一 |
| "MCP 是协议替代品" | MCP 是分发层，契约仍是 JSON Schema，与 FC 互补 |
| "适配层多余" | 多供应商切换时适配层省的是全项目改动 |
| "strict 各家一致" | 能力要探测：国产兼容 ≠ 同能力 |
| "描述放 schema 里就行" | 使用规则/依赖关系放 system prompt 更清晰 |

## 9. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 三代声明方式？ | 提示词 JSON → 原生 FC → MCP 分发 |
| OpenAI 参数与回传？ | parameters 定义、arguments 是 JSON 字符串、role:tool + tool_call_id 配对 |
| Anthropic 差异？ | input_schema、input 直接是对象、tool_result 块在 user 消息 |
| MCP 差异？ | inputSchema、tools/list 发现、tools/call 调用、跨宿主分发 |
| 为什么需要适配层？ | 各家键名/形态不同，抽象 ToolCall/ToolResult 一次封装全兼容 |
| strict 支持面？ | OpenAI/Anthropic 支持；MCP 无标准（宿主层） |
| 硬约束放哪？ | 执行层——提示词是软约束，执行层是硬边界 |
| 协议选型？ | 协议认 OpenAI（事实标准）、能力看需求（探针验证） |
| tool_choice 四值？ | auto/required/none/指定名——强制调用场景用指定名 |
| 结果回传配对键？ | tool_call_id（OpenAI）/ tool_use_id（Anthropic）——必须配对存在 |
| 与 Output Parser 07 篇分工？ | 本篇讲协议形态；07 篇讲参数解析校验与失败修复 |
| 2026 声明趋势？ | 从全量声明走向按需加载（tool_search/命名空间，05 篇） |
