# 工具结果处理：反馈回路设计

> 结果 = 工具给模型的"反馈信号"，质量决定 Agent 下一步正确性。2026 三大课题：**截断别截错**（最新结果最相关，截错会误导）、**失败要记住**（重复失败检测防重蹈覆辙）、**压缩保配对**（tool-call/tool-result 成对剪除，拆对即 API 拒收）。本章给出反馈回路完整设计。

## 1. 结果注入：反馈的格式规范

| 维度 | 规范 |
|---|---|
| 形态 | 字符串 observation（模型处理文本） |
| 结构 | 可选项：状态、内容、元数据（耗时/分页） |
| 配对 | 引用 tool_call_id / tool_use_id（协议要求） |
| 顺序 | tool_calls 消息先追加，结果后追加（顺序颠倒 → 校验错误） |
| 单轮完整性 | 每个调用恰好一个结果，缺失 = 悬空调用 |

```jsonc
// 结果注入形态（OpenAI 生态）
{ "role": "tool", "tool_call_id": "call_abc123",
  "content": "晴 32°C，湿度 45%。查询耗时 120ms。" }
```

> 🎯 核心要点：结果不是"给模型看的数据"，是**下轮决策的输入**——要按模型怎么用它来写：可读、结构稳定、含关键结论，别让模型猜"这个结果说明什么"。

## 2. 截断：反馈的瘦身术

| 截断策略 | 做法 | 问题 |
|---|---|---|
| ❌ 截最新结果 | 超过上限裁掉新结果 | **最差实践**：最新结果最相关，模型可能把"结果太大"误判为工具失败 → 重复调用/错误决策 |
| ❌ 无阈值全截 | 小结果也裁 | 小结果无损却被破坏 |
| ❌ 整段删除 | 内容全删 | 丢失结果语义 |
| ✅ 由旧到新 | 先处理旧消息（旧结果大概率已被消化） | 保留最新上下文 |
| ✅ 阈值触发 | 超过字符阈值才截 | 小结果原样保留 |
| ✅ 头尾保留 | 保留首 200 字符与尾，中段标记截断量 | 保留语义锚点 |
| ✅ 图片占位 | 旧图片替换为描述占位符 `[image: x.png, 1024x768]` | 减 token 留语义 |

> 💡 实测数据：头尾保留式截断 + 旧消息优先，约 **67% token 减少**且保留度更高（harness-sdk 实践）。

## 3. 结果摘要与清理：上下文的二级压缩

| 手段 | 做法 | 成本 | 保真 |
|---|---|---|---|
| 截断 | 超阈值裁剪 | 无 | 中（丢细节） |
| 摘要 | LLM 压缩旧结果 | 一次调用/次压缩 | 高（有损） |
| 工具结果清理 | 清掉已消费的原始结果（只留结论/引用） | 无 | 高（Anthropic 称之为"最安全最轻量的压缩形式"） |
| 事实钉扎 | 确认过的业务值（订单总额/地址）进永不压缩的固定存储，每次注入 | 注入成本 | 极高 |

> 🎯 核心要点（Anthropic 2026 上下文工程）：**混合方案是主流**——近期轮次逐字保留、远期轮次摘要、已确认事实钉扎、原始工具结果清理；每次压缩**记录丢弃了什么**（可审计）。

## 4. 重复失败检测：让模型"记得"自己失败过

2026 实证痛点：模型只处理上下文窗口、不处理执行历史——压缩抹掉失败证据后，Agent 真的不知道自己已试过某方案（Copilot 1526 个 worktree、$8 读同一文件 1000 次）。

| 机制（Narrowing 三 API） | 职责 |
|---|---|
| `checkProposal()` | 执行前拦截：已知失败的策略直接阻止 |
| `recordOutcome()` | 执行后登记：提取失败签名、归类责任、播种约束 |
| `isDone()` | 收敛检测：判断是否已无法取得进展 |

| 约束类型 | 规则 |
|---|---|
| banned_strategy | 某策略失败 2+ 次 → 禁用 |
| radius_limit | 修改量的渐进上限 |
| parameter_ban | 特定值证明不可行 → 禁用 |

> ⚠️ **Blame 分类是核心**：Agent 自身故障（语法错误、文件不存在、编辑失败）→ 播种约束；**基础设施故障（超时、限流、权限）→ 只记录不约束**——否则基础设施噪声会缩小搜索空间直到 Agent"无路可走"（毒化之井）。

## 5. 上下文管理：turn-atomic pruning

| 原则 | 说明 |
|---|---|
| 整轮剪除 | 剪旧轮次要**成对**剪：assistant 的 tool_calls 消息 + 其全部 tool_result——拆对 = API 拒收 |
| 永不剪头部 | system prompt + 首条用户消息保留 |
| 永不剪最新轮 | 最新上下文对当前决策最相关 |
| 配对守卫 | 无法确认配对时宁可不剪（cheap guard，交给 provider 判定） |
| 估算器 | 按内容类型估算 token（散文 ~3.5 字符/token、密集 JSON ~2.5），校准因子 >1.0 宁可高估 |
| 优雅失败 | 剪到地板仍超预算 → 不发请求，抛 `ContextTruncatedException`（非重试终止原因）而非误分类的 4xx |

> 💡 为什么不用摘要代替剪除：摘要每次压缩多一次模型调用（成本+延迟+非确定性）；整轮剪除是确定性的、便宜的、可证明安全的——**热路径上确定性优先**。

## 6. 反馈回路的质量指标

| 指标 | 目标 | 说明 |
|---|---|---|
| 结果消费率 | 高 | 结果是否被模型实际使用（引用工具结果的轮次占比） |
| 重试率 | <5% | 超过 = 契约或模型问题（06 篇） |
| 截断触发率 | 可控 | 高频截断 = 工具结果设计过大 |
| 重复失败率 | 下降 | 失败签名命中 → 约束生效 |
| 上下文命中 | 不超预算 | 压缩有效性（token/轮） |

> 🎯 核心要点：反馈回路的目标不是"把结果给到模型"，而是**让模型在有限的上下文里持续做出正确决策**——截断、摘要、剪除、失败记忆全是这个目标的手段。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "截最新结果保上下文" | 最新结果最相关，截错 = 误判工具失败 + 重复调用 |
| "结果越大越好" | 结果按 max_tool_result_chars 设计，超限必截 |
| "摘要替代一切" | 摘要每压缩一次多一次调用+有损；整轮剪除确定性更好 |
| "失败过的事模型会记得" | 模型只处理上下文——压缩抹掉证据就真忘了，必须显式失败记忆 |
| "重试失败也算进展" | 同策略失败 2+ 次要禁用（banned_strategy） |
| "所有失败都约束" | 基础设施故障不约束——否则毒化搜索空间 |
| "剪除随便剪" | 拆对剪除 = API 拒收——turn-atomic 是铁律 |
| "压缩不用记账" | 每次丢弃要记录——审计与调试都靠它 |

## 8. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 结果注入规范？ | 字符串 observation、引用 call_id、tool_calls 先于结果追加 |
| 截断最佳实践？ | 旧消息优先 + 阈值触发 + 头尾保留（~67% token 减少） |
| 为什么不能截最新结果？ | 最新结果最相关，截了模型误判工具失败 |
| 二级压缩手段？ | 截断/摘要/工具结果清理/事实钉扎——混合使用 |
| 重复失败检测？ | checkProposal 拦截 + recordOutcome 登记 + isDone 收敛 |
| blame 分类？ | Agent 故障播种约束；基础设施故障只记录不约束 |
| turn-atomic pruning？ | 成对剪 tool_calls+tool_result，拆对 = API 拒收 |
| 为什么不用摘要代替剪除？ | 摘要多一次调用+有损；剪除确定性、便宜、可证安全 |
| 结果消费率是什么？ | 模型引用工具结果的轮次占比 |
| 重试率红线？ | <5%——超过修契约不堆重试 |
| ContextTruncatedException？ | 剪到地板仍超预算时抛非重试终止原因，别误报 4xx |
| 反馈回路的目标？ | 有限上下文内持续正确决策——截断/摘要/记忆全是手段 |
