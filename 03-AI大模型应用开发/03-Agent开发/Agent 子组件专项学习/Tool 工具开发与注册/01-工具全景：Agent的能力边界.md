# 工具全景：Agent 的能力边界

> 工具 = Agent 与外部世界之间的唯一桥梁：**模型不执行工具，它只发出结构化请求**，由宿主执行并把结果回注。2026 共识：工具是契约（描述+schema），代码只是执行细节——工具质量直接决定 Agent 上限。本章立起全景：工具是什么、分几类、走哪几个阶段、与函数调用/MCP 如何分工。

## 1. 工具的本质：决策与执行的分离

| 层 | 谁做 | 做什么 | 例子 |
|---|---|---|---|
| 决策层 | LLM | 判断"该不该调、调哪个、传什么参数" | 输出 tool_call |
| 执行层 | 宿主/执行器 | 校验、授权、执行、返回结果 | 调 API、跑 SQL、写文件 |
| 反馈层 | 模型 | 读结果决定下一步 | 继续调/回答/结束 |

```text
工具调用的完整链路：
  1. 声明    —— 工具定义（name+description+schema）注入上下文
  2. 选择    —— 模型在工具列表中选出目标并生成参数（tool_call）
  3. 执行    —— 宿主校验授权后执行真实动作
  4. 反馈    —— 结果以 tool_result 回注上下文
  5. 循环    —— 模型消化结果继续，直到回答或终止
```

> 🎯 核心要点：模型从不直接触碰外部世界——它"建议"，宿主"执行"。这意味着：**所有安全边界、权限、审计都必须在执行层**，因为模型输出是不可信输入（08 篇）。

## 2. 工具的分类

| 分类 | 特征 | 例子 | 风险等级 |
|---|---|---|---|
| 只读工具 | 查询、检索、计算 | 查天气、向量检索、calculator | 低 |
| 写工具 | 修改系统状态 | 发邮件、创建工单 | 中 |
| 危险工具 | 不可逆副作用 | 转账、删除、发布 | 高（需审批） |
| 计算工具 | 纯函数、无副作用 | 数学、格式化 | 极低 |
| 推理/验证工具 | 外部验证 | 编译器、测试运行、搜索 | 低 |
| 多模态工具 | 非文本数据 | 图像生成、语音合成 | 中 |
| 代理型工具 | 调用另一个 Agent | 子 Agent 委派 | 高 |

> 💡 风险分级是工具注册表的核心元数据——只读工具可自动执行，写工具要有节流，危险工具必须确认模式（02/08 篇展开）。

## 3. 工具 vs 相邻概念

| 概念 | 与工具的关系 |
|---|---|
| 函数调用（Function Calling） | 工具声明与调用的**协议层**（怎么把工具描述给模型、怎么传回结果）——工具是概念，FC 是载体 |
| MCP | 工具的**分发与互操作协议**——一次定义、多宿主调用（09 篇） |
| 插件（Plugin） | 工具概念的旧形态：偏"应用级集成"；2026 被"工具 + MCP"统一 |
| Agent | 工具是 Agent 的能力库；Agent = 模型 + 工具 + 循环 |
| 行动（Action） | Agent 内部的动作原语，工具是行动的标准化封装（四大核心组件 07 篇） |
| API | 工具是 API 的"LLM 适配层"：加描述、加 schema、加授权 |

> 🎯 核心要点：四层分工——**业务能力在 API，工具是 API 的适配层，FC 是协议层，MCP 是分发层**。写一个"工具"实际是写 API 的说明书（描述）与契约（schema）。

## 4. 工具为什么决定 Agent 上限

| 维度 | 工具差的表现 | 工具好的表现 |
|---|---|---|
| 选择准确率 | 模糊描述 → 选错工具/不调 | 描述带示例与边界 → 该调时调、该跳过时跳过 |
| 参数正确率 | 缺参数描述 → 幻觉参数 | 全参数描述 + 枚举 → 一次调用成功率高 |
| 上下文成本 | 工具定义臃肿/过多 → 占 30%+ token | 精简 + 按需加载 → 定义成本 <10% |
| 容错 | 错误抛异常 → 循环卡死 | 结构化错误 → 模型自我纠正 |
| 安全 | 参数拼接 SQL/Shell → 注入 | 白名单/确认模式 → 可控 |

> ⚠️ 2026 实证：描述含示例使工具选择准确率提升约 **25%**；工具数量超过 20 个后模型混淆率显著上升，30 个是硬拒绝线——**工具列表不是越多越好，而是越精越好**（05 篇数量治理）。

## 5. 工具的 2026 设计原则总览

| 原则 | 一句话 | 出处（详见章节） |
|---|---|---|
| 契约优先 | 描述与 schema 是产品，实现是细节 | 03 篇 |
| 动词命名 | create_issue、list_repos，拒绝 do_github | 03 篇 |
| 少而精 | <20 个工具、10-15 个/上下文 | 05 篇 |
| 绝对标识 | 绝对路径/ID，消除歧义（poka-yoke） | 03 篇 |
| 结构化错误 | 失败返回模型可读的 observation | 06 篇 |
| 分层组织 | namespace/分类先行，再选具体工具 | 05 篇 |
| 最小权限 | 工具只能做被授权的事 | 08 篇 |
| 可观测 | 每个调用留痕：tool name/call id/参数/结果 | 10 篇 |
| 一次定义多处调用 | 走 MCP 生态，写一次多宿主可用 | 09 篇 |

## 6. 工具生命周期

| 阶段 | 动作 | 关键决策 |
|---|---|---|
| 开发 | 写函数 + 注释 → 生成 schema | 描述怎么写、参数几个 |
| 注册 | 登记进注册表 | 命名、分类、权限、冲突检测 |
| 声明 | 注入模型上下文 | 全量 vs 按需（tool_search） |
| 执行 | 校验 → 授权 → 调用 → 返回 | 超时、重试、并行、预算 |
| 反馈 | 结果回注/截断/摘要 | 上下文成本控制 |
| 治理 | 审计、监控、下线 | 调用量、失败率、误用检测 |
| 演进 | 版本升级、废弃 | 旧版本兼容（02 篇版本管理） |

> 🎯 核心要点：工具不是"写完就完"的静态代码，而是**有生命周期的产品**——注册、治理、下线与开发同等重要。多数团队死在"工具越加越多，从未治理"。

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "工具=函数" | 函数只是实现；描述、schema、权限、观测才是工具 |
| "工具越多能力越强" | >20 个混淆率上升，>30 硬拒绝——靠动态发现解决 |
| "描述随便写写" | 描述比实现重要，模糊描述 = 选错工具 |
| "参数越全越好" | 每多一个参数就多一分幻觉概率——够用即可 |
| "模型会自己读懂代码" | 模型只看 description 和 schema，永远不看实现 |
| "工具失败重试就行" | 重试率 >5% 说明契约或模型有问题（07 篇） |
| "工具安全=执行安全" | 工具结果也是注入面——返回内容同样不可信（08 篇） |

## 8. 面试速记

| 问题 | 一句话答案 |
|---|---|
| 工具是什么？ | 模型只发出结构化请求、宿主执行的标准化外部能力封装 |
| 模型看得见工具的什么？ | 只有 name + description + JSON Schema——永远看不见实现 |
| 工具调用链路几步？ | 声明→选择→执行→反馈→循环（五步） |
| 工具、函数调用、MCP 关系？ | 工具是概念，FC 是协议层，MCP 是分发层（概念/载体/生态） |
| 为什么描述比实现重要？ | 模型靠描述决定"何时调"，模糊描述 = 选错工具；示例提升 ~25% |
| 工具数量红线？ | <20 建议、30 硬拒绝、单上下文 10-15 准确率边界 |
| 安全边界放哪？ | 执行层——模型输出不可信，校验/授权/审计都在宿主 |
| 工具生命周期几阶段？ | 开发→注册→声明→执行→反馈→治理→演进 |
| 工具分类维度？ | 按副作用分级：只读/写/危险——决定自动 or 确认 |
| 2026 工具设计第一原则？ | 契约优先：描述与 schema 是产品，代码是执行细节 |
| 工具与插件区别？ | 插件是旧形态的应用级集成；2026 统一为"工具 + MCP" |
| 工具质量三大指标？ | 选择准确率、参数正确率、调用成本（token/轮数） |
