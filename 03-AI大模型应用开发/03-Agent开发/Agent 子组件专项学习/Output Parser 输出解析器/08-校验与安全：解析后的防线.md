# 校验与安全：解析后的防线

> 解析保证"语法"，校验保证"语义"，安全保证"无害"。2026 年共识：**即使 strict 模式也必须在应用层继续校验**——strict 是采样层保证，业务语义与安全永远在应用层。

## 1. 双层校验体系

```text
① Schema 校验（结构层）：jsonschema/AJV 按 JSON Schema 验证
  → ② 业务校验（语义层）：值域/规则/权限/一致性
    → ③ 安全校验（无害层）：注入/敏感/危险操作
```

| 层 | 工具 | 防什么 |
|---|---|---|
| Schema | jsonschema（Python）/AJV（JS） | 缺字段/类型错/额外属性 |
| 业务 | 自定义规则 | 值域越界/逻辑矛盾 |
| 安全 | 注入检测/脱敏 | 输出夹带指令/敏感泄露 |

> 🎯 核心要点：**strict 模式 ≠ 免校验**——strict 保证"符合 schema"，不保证"值合理、无危害"。2026 年最佳实践清单第一条："Always validate downstream, even with strict mode."

## 2. Schema 校验落地

```python
import jsonschema

def validate_schema(obj, schema):
    try:
        jsonschema.validate(obj, schema)
        return []
    except jsonschema.ValidationError as e:
        return [{"path": list(e.path), "message": e.message}]

errors = validate_schema(data, ORDER_SCHEMA)
if errors:
    return {"status": "error", "errors": errors}   # 校验错误回传（04 篇闭环）
```

| 校验点 | 说明 |
|---|---|
| 必填字段 | required 数组 |
| 类型 | 严格类型（数字不是字符串） |
| 枚举 | enum 值域 |
| 格式 | format（email/date 等） |
| 嵌套 | 每层校验 |

## 3. 业务校验：值域的最后一关

| 校验类型 | 例子 |
|---|---|
| 值域 | 金额 >0、数量 ≤1000 |
| 枚举业务态 | status 与订单状态机一致 |
| 交叉一致性 | 发货日期 ≥ 下单日期 |
| 权限 | 用户对该数据有权限 |
| 幂等键 | 唯一约束（写操作） |

```python
def business_validate(order, user):
    checks = []
    if order["amount"] <= 0: checks.append("金额必须大于 0")
    if order["ship_date"] < order["order_date"]: checks.append("发货日期早于下单")
    if not has_permission(user, order): checks.append("无权限")
    return checks
```

> 💡 业务校验的提示：**校验规则与 schema 同文件管理**（契约文件 = schema + 规则 + 描述），模型描述与校验规则永不脱节。

## 4. 输出注入防御：模型输出夹带指令

| 风险 | 场景 | 防线 |
|---|---|---|
| 输出带指令 | 模型生成"请忽略上一条指令..." | 输出当数据不当指令 |
| 渲染注入 | 输出含 HTML/脚本 | 前端转义（前端体系） |
| 工具参数注入 | 参数夹带命令 | 参数化执行 |
| 存储注入 | 输出入库带恶意内容 | 入库前消毒 |

```text
分域原则：模型输出的一切都视为"数据"，永不视为"指令"
  消费端（前端/工具/数据库）负责隔离与转义
```

## 5. Refusal 与敏感内容处理

| 情况 | 检测 | 处理 |
|---|---|---|
| 安全拒绝 | refusal 字段 | 显示"无法处理"，不重试 |
| 敏感信息生成 | 输出含 PII | 脱敏后交付 |
| 违规内容 | 内容过滤 | 拦截 + 日志 |

## 6. 校验失败的错误契约（与 04 篇闭环）

```python
# 校验错误统一契约：可编程、可回传、可行动
{"status": "validation_failed",
 "errors": [{"path": "status", "message": "不在枚举内", "hint": "可选: paid/pending"}],
 "attempt": 2, "max_attempts": 3}
```

| 错误契约价值 | 说明 |
|---|---|
| 回传模型 | 带 hint 的修正（04/07 篇） |
| 可编程 | 调用方按 status 分流 |
| 可观测 | attempts 暴露重试成本 |

## 7. 校验性能与成本

| 项 | 建议 |
|---|---|
| 校验延迟 | <1ms（纯内存校验） |
| 校验时机 | 解析后立即（不延迟到消费端） |
| 校验幂等 | 同输入同结果（可测） |
| 校验覆盖 | 100% 输出（不是抽样） |

> 🎯 核心要点：校验是解析器的"另一半"——**没有校验的解析器只完成了一半工作**。三层校验（schema/业务/安全）各司其职，配合 04 篇的失败闭环，输出解析才完整。

## 8. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 只解析不校验 | 静默错误进下游 | 三层校验 |
| 校验错误不回传 | 模型重复错 | 错误契约回传 |
| 输出当指令 | 注入执行 | 分域原则 |
| refusal 重试 | 无限重试 | refusal 单独处理 |
| 校验规则与 schema 脱节 | 规则过期 | 同文件管理 |
| 校验抽样 | 漏网之鱼 | 100% 覆盖 |
| 敏感输出不脱敏 | 泄露 | 交付前脱敏 |

## 9. 校验规则与模型描述的一致性

| 一致性要求 | 做法 |
|---|---|
| 规则同源 | schema + 规则 + 描述同一文件 |
| 描述含规则 | 模型生成时知道规则（"金额必须>0"进描述） |
| 校验含描述 | 校验规则与描述同步更新 |
| 冲突检测 | 描述与规则矛盾时以规则为准 + 告警 |

```text
一致性断裂的代价（2026 实测）：
  描述说"金额单位元"，规则按分校验 → 模型按描述生成、校验按规则拒绝
  → 永远校验失败 → 重试风暴
  解法：描述与规则同源生成、同文件管理、变更同评审
```

## 10. 校验流水线完整示例

```python
def validate_pipeline(obj, schema, rules, user):
    # ① schema 校验（结构）
    schema_errors = validate_schema(obj, schema)
    # ② 业务校验（语义）
    biz_errors = business_validate(obj, rules)
    # ③ 安全校验（无害）
    sec_errors = security_validate(obj, user)
    # ④ 汇总错误契约（可回传模型）
    all_errors = schema_errors + biz_errors + sec_errors
    if all_errors:
        return {"status": "validation_failed",
                "errors": [{"path": e.path, "message": e.message,
                            "hint": e.hint} for e in all_errors],
                "attempts": count_attempts(obj)}
    return {"status": "ok", "data": obj}
```

| 校验环节 | 延迟 | 可回传 |
|---|---|---|
| schema | <1ms | ✅（带 path） |
| 业务 | <1ms | ✅（带 hint） |
| 安全 | <1ms | ⚠️（脱敏后） |

> 🎯 核心要点：校验流水线的输出就是 04 篇错误回传的输入——**"校验 → 错误契约 → 回传模型"是一个闭环**，不是两件独立的事。校验不是"拦下来"，是"帮模型改对"。

## 11. 校验覆盖矩阵（各消费端必校验项）

| 消费端 | schema | 业务 | 安全 |
|---|---|---|---|
| 工具执行 | ✅ 参数类型 | ✅ 值域/权限 | ✅ 注入/命令 |
| 数据库写入 | ✅ 类型 | ✅ 约束对齐 | ✅ SQL 注入 |
| 前端渲染 | ✅ 结构 | ⚠️ 展示规则 | ✅ XSS 转义 |
| 记忆写入 | ✅ 事实格式 | ✅ 时效/去重 | ✅ PII 脱敏 |
| 下游 API | ✅ 字段 | ✅ 业务状态 | ✅ 令牌 |

> 💡 覆盖矩阵的价值：**"谁消费谁校验"清单化**——每个消费端都要有自己的校验职责，而不是"解析器校验过了就都安全了"。

## 12. 常见校验反模式

| 反模式 | 表现 | 正解 |
|---|---|---|
| 校验在消费端补 | 每个消费端各写一套 | 解析器统一校验 + 消费端复核 |
| 校验规则写死在代码 | 改规则要发版 | 规则外部化（配置/契约文件） |
| 校验只测 happy path | 边界漏 | 边界用例集（空/超长/非法枚举） |
| 校验错误直接抛 | 无法回传修正 | 错误契约回传 |
| 敏感校验不过滤 | 违规内容入库 | 安全校验前置 |
| 校验与模型描述脱节 | 模型按描述生成被拒 | 描述规则同源 |

> 🎯 核心要点：校验的工程化——**统一入口（解析器）→ 规则外部化（契约文件）→ 错误可回传（闭环）→ 边界有测试**。四件事做到，校验从"散落的 if"变成"可信的防线"。与[数据库交互](../../Agent%20配套技术生态模块/数据库交互/00-数据库交互总览.md)体系的衔接：数据库写入场景的校验（值域/权限/注入）即本模块三层校验的具体应用，规则应复用同一契约文件。面试速记：校验三问——"schema 过了吗（结构）、业务值合理吗（语义）、内容无害吗（安全）"——三层答全即合格。防线顺序提醒：**校验永远在解析之后、执行之前**——先解析（得到对象）→ 再校验（确认对象）→ 后执行（使用对象），顺序颠倒等于没校验。校验的"静默失败检测"还有一个常被忽略的动作：**校验通过后的抽样复核**——对已通过校验的输出定期抽查语义正确率（评测集），因为"校验规则本身"也可能过时（业务规则变了而规则文件没更新）。
