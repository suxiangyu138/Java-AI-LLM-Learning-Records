# 解析失败处理：修复与重试

> 失败是解析器的日常。2026 年的处理框架：**失败模式目录（refused/partial/truncated/degraded）→ 修复工具链 → fallback 链**——先分类再行动，禁止"报错就重试"的盲目循环。

## 1. 失败模式目录（排查框架）

| 模式 | 表现 | 根因 | 对策 |
|---|---|---|---|
| refused | 无内容/拒绝字段 | 安全策略 | 明确提示，不重试 |
| partial | JSON 半截/缺字段 | 截断/中断 | 修复或重试（增大上限） |
| truncated | finish_reason=length | token 上限 | 增上限/分段，**别盲目重试** |
| degraded | 合规但值错 | 模型能力/歧义 | 语义校验 + 重试/人工 |
| 注入 | 输出带指令 | 输入污染 | 分域处理（08 篇） |

> 🎯 核心要点：**失败处理的第一步是分类，不是重试**——refused 重试一万次还是 refused，truncated 重试一万次还是 truncated，只有 partial（偶然残缺）才值得重试。

## 2. 修复工具链（2026 成熟方案）

| 工具 | 平台 | 能力 |
|---|---|---|
| jsonmend | Python | 单遍流式修复（"补好 LLM 差点写对的 JSON"） |
| repair-json-stream | JS/多平台 | 增量修复（push(chunk) → 实时修复输出 → end() 补全） |
| json_repair | Python | 通用修复（围栏/单引号/尾逗号/注释） |
| 自研修复 | 任意 | 剥围栏 + 补引号 + 补括号（02 篇提取函数） |

```python
# 修复链示例：普通解析 → 修复 → 再解析
import json
from json_repair import repair_json

def robust_parse(text: str) -> dict:
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        fixed = repair_json(text)              # 修复工具
        if fixed:
            return json.loads(fixed)
        raise ParseError("修复失败，转重试链")
```

| 修复策略 | 适用 |
|---|---|
| 轻修复（剥围栏/尾逗号） | 常见小错（80% 场景） |
| 工具修复（jsonmend 等） | 通用残缺 |
| LLM 修复（回喂重生成） | 语义级错误（贵，最后用） |

## 3. 重试设计：带反馈的重试

| 重试方式 | 做法 | 成本 |
|---|---|---|
| 盲重试 | 原样重发 | 低但无效（同样错误） |
| **反馈重试** | 报错信息回喂 + 指示修正 | 中（推荐） |
| 多候选 | 生成 N 个选最优 | 高（N 倍调用） |

```python
def generate_with_feedback(prompt, schema, max_retries=3):
    for attempt in range(max_retries):
        out = llm.generate(prompt)
        try:
            return validate(extract_json(out), schema)
        except (ParseError, ValidationError) as e:
            prompt = f"{prompt}\n\n上次输出无效：{e.sanitized}\n"
                    f"请重新输出，严格遵守 schema。上次输出：{out[:500]}"
    raise RetryExhausted("重试 3 次仍失败")
```

| 反馈内容 | 效果 |
|---|---|
| 具体错误（缺什么字段） | 模型能改对 |
| 原始输出片段 | 模型知道错在哪 |
| 修正指示（"输出纯 JSON 无围栏"） | 防重复犯错 |
| 错误脱敏 | 防内部信息泄露 |

> ⚠️ 重试成本审计（2026 评测要求）：**约束解码的重试被头榜解析率掩盖**——99.5% 的解析率可能是 10% 重试堆出来的。监控重试率并纳入成本核算。

## 4. Fallback 链：从强到弱逐级降级

```text
① strict 模式（最强保证）
  → ② 普通 JSON + schema 校验（模型不支持 strict 时）
    → ③ 提示词约束 + 修复工具（无 strict 的模型）
      → ④ 重生成（LLM 修复）
        → ⑤ 降级输出（返回错误契约给调用方，明确失败）
```

| 降级层 | 何时触发 | 代价 |
|---|---|---|
| strict | 默认 | 0 |
| JSON+校验 | strict 不可用 | 0 |
| 提示词+修复 | 模型太弱 | 修复成本 |
| 重生成 | 修复失败 | 1 次额外调用 |
| 错误契约 | 全部失败 | 业务侧处理 |

```python
def structured_call(prompt, schema):
    if provider.supports_strict():
        return strict_call(prompt, schema)
    try:
        return json_call_with_validate(prompt, schema)
    except ParseError:
        return repair_and_retry(prompt, schema, max_retries=3)
```

> 💡 Fallback 链的意义：**不在一个模型上死磕**——OpenAI strict 失败 → 降级 Anthropic tool use / Gemini responseSchema（各家强制力不同，多备一路）。

## 5. 错误契约：让失败"可见且可处理"

```python
# 输出统一错误契约（取代抛异常）
{"status": "error", "code": "parse_failed",
 "message": "输出无法解析", "attempts": 3,
 "fallback": "请提供更明确的输入"}
```

| 错误契约字段 | 作用 |
|---|---|
| status/code | 可编程处理 |
| attempts | 重试次数（成本可见） |
| fallback 建议 | 调用方可行动 |
| sanitized 细节 | 日志诊断 |

## 6. 重试与修复的预算

| 预算 | 默认 | 防什么 |
|---|---|---|
| 修复次数 | ≤2 | 修复风暴 |
| 重试次数 | ≤3 | 重试风暴 |
| 多候选数 | ≤3 | 成本爆炸 |
| 重试退避 | 有 | 限流 |
| 单任务解析成本 | 上限 | 预算失控 |

> 🎯 核心要点：失败处理的完整纪律——**分类先行（目录）→ 修复工具（低成本）→ 反馈重试（带信息）→ fallback 链（多备路）→ 错误契约（可见）→ 预算封顶（防失控）**。六步齐，解析失败从"事故"变成"流程"。

## 7. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 盲目重试 | 同样错误重复 | 失败分类 |
| 截断当解析错 | 反复截断 | 查 finish_reason |
| 重试无反馈 | 改了也没用 | 错误回喂 |
| 修复风暴 | 修复套修复 | 修复次数上限 |
| 无 fallback | 单点模型 | fallback 链 |
| 错误不可见 | 静默失败 | 错误契约 |
| 重试率不监控 | 成本黑洞 | 重试审计 |

## 8. 失败处理决策树（落地速查）

```text
输出到达
 ├─ 拒绝（refusal）？ → 提示用户，不重试 → 结束
 ├─ 截断（finish_reason=length）？ → 增大 max_tokens 或分段 → 结束
 ├─ 解析失败？ → 修复工具（≤2 次）→ 仍败？
 │     ├─ 反馈重试（≤3 次，错误回喂）
 │     └─ 仍败 → 换模式（strict→tool use）→ fallback 链
 ├─ 校验失败？ → 错误回传（带 hint）→ 模型修正
 └─ 全部失败 → 错误契约（status/errors/attempts）→ 调用方处理
```

| 分支 | 成本上限 | 关键动作 |
|---|---|---|
| 修复 | 2 次 | 修复工具链 |
| 反馈重试 | 3 次 | 错误+原始输出回喂 |
| 模式切换 | 1 轮 | strict → tool use / JSON |
| 错误契约 | 1 次 | 可见失败，进监控 |

## 9. 失败教训的记忆化（与 Memory 联动）

| 失败类型 | 写入记忆的教训 | 后续收益 |
|---|---|---|
| 重复解析失败 | "该任务用 strict 模式" | 下次直接走对路 |
| 枚举频繁越界 | "status 需加 unknown 兜底" | 契约改进 |
| 厂商强制力不足 | "厂商 X strict 不可靠" | 选型记忆 |
| 提示词致错 | "描述缺单位导致误解" | 契约描述改进 |

> 💡 失败处理与[Memory 记忆系统](../Memory%20记忆系统/00-Memory记忆系统总览.md)的联动：解析失败的教训写入记忆（反思组件的产出路径），Agent 下次任务直接调用正确模式——失败从"每次重来"变成"一次学会"。

## 10. 失败处理监控指标

| 指标 | 信号 | 告警 |
|---|---|---|
| 解析失败率（按模式） | 分模式趋势 | >1% 持续上升 |
| 重试率 | 重试/总调用 | >5% |
| 修复成功率 | 修复后解析成功占比 | <80% |
| 修复/重试成本 | 额外调用与 token | 超预算 |
| 失败分布 | refused/partial/truncated 占比 | truncated 占比升高=上限配置问题 |
| fallback 触发率 | 降级路径使用频率 | 异常升高=主路径退化 |
| 错误契约率 | 最终失败占比 | >0.5% |

> 💡 指标入 CI 回归（10 篇检查单）：任何模型/契约/模式变更，先看这些指标有没有回退——失败处理的质量是解析器可靠性的温度计。
