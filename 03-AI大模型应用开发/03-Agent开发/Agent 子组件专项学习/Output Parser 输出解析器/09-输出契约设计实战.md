# 输出契约设计实战

> 契约（schema + 规则 + 描述）是解析器的"宪法"：字段怎么命名、枚举怎么定、嵌套怎么拆、版本怎么管。契约设计质量直接决定解析成功率——"schema 是给模型看的说明书，也是给系统定的规矩"。

## 1. 契约设计四原则

| 原则 | 说明 |
|---|---|
| 简单优先 | 从简开始，复杂度递增（strict 编译快、易维护） |
| 命名即语义 | 字段名与描述承载提取语义 |
| 枚举优先 | 类别数据全用枚举（准确率+可校验） |
| 契约即文档 | schema + 规则 + 描述一体管理 |

> 🎯 核心要点：**模型靠字段名与描述提取数据**——`customer_email` 的提取准确率远高于 `field1`（2026 实测）。契约是"零成本准确率杠杆"。

## 2. 字段设计规范

| 规范 | 例子 | 避免 |
|---|---|---|
| 语义化命名 | `order_amount` | `field1` |
| 描述写清语义 | "含税总金额（元）" | 无描述 |
| 单位进描述 | "金额单位：元" | 单位不明 |
| 枚举带说明 | "paid=已支付" | 裸枚举 |
| 数量级标注 | "数量（整数）" | 类型歧义 |

```json
{
  "order_amount": {"type": "number",
    "description": "订单含税总金额，单位元，保留两位小数"},
  "status": {"type": "string", "enum": ["paid", "pending", "cancelled"],
    "description": "paid=已支付, pending=待支付, cancelled=已取消"}
}
```

## 3. 契约模式库（可复用模板）

| 模式 | 结构 | 适用 |
|---|---|---|
| 单记录 | 一个 object | 单实体抽取 |
| 记录+数组 | 主记录 + items 数组 | 列表+详情 |
| 枚举+兜底 | enum + unknown | 类别不确定 |
| 错误契约 | status/errors/attempts | 失败输出（04 篇） |
| 分步契约 | 状态机字段 | 流程型输出 |

```python
# 错误契约模式（与 04/08 篇统一）
ERROR_CONTRACT = {
    "type": "object",
    "properties": {
        "status": {"type": "string", "enum": ["ok", "error"]},
        "errors": {"type": "array", "items": {"type": "object",
            "properties": {"path": {"type": "string"}, "message": {"type": "string"}},
            "required": ["path", "message"], "additionalProperties": false}},
        "attempts": {"type": "integer"}
    },
    "required": ["status"], "additionalProperties": false
}
```

## 4. 嵌套与拆分：大契约的退化问题

| 问题 | 表现 | 解法 |
|---|---|---|
| 50+ 字段嵌套 | 准确率暴跌 | 拆分多步生成 |
| 深层嵌套 | strict 限制 | 拍平（≤5 层） |
| 复杂 union | 确定性失败 | 简化 |

```text
大契约拆分策略：
  ① 分步生成（先主体后明细，两次调用）
  ② 子对象独立契约（customer 单独抽取）
  ③ 分块校验（每步校验再合并）
  —— 5 字段的准确率 >> 50 字段（2026 评测共识）
```

## 5. 版本化：契约的演进管理

| 版本策略 | 做法 |
|---|---|
| 显式版本号 | schema 元数据带 version |
| 向后兼容 | 新增字段可空（null union） |
| 迁移期 | 双版本并存 + 灰度 |
| 变更回归 | 契约变更跑评测集 |

```text
契约变更流程：
  评估（影响哪些消费端）→ 版本化（新版本号）
  → 双跑（新旧并行）→ 迁移（消费端切换）→ 下线（旧契约）
```

> ⚠️ 契约是"公共接口"——**变更契约 = 变更所有消费端的行为**。输出契约的变更要像 API 版本一样管理，不能随手改（数据库交互/前端都会消费它）。

## 6. 契约与跨层衔接

| 消费端 | 契约的用法 |
|---|---|
| 工具执行 | 工具 schema 即契约（07 篇） |
| 数据库 | 校验规则对齐表约束（[数据库交互](..%2F..%2FAgent%20配套技术生态模块%2F数据库交互%2F00-数据库交互总览.md)） |
| 前端 | 渲染组件按契约类型（前端演示界面） |
| 记忆系统 | 事实提取契约（Memory 05 篇） |
| 多 Agent | 消息契约（A2A 协议） |

## 7. 契约自检清单

```text
□ 命名语义化（customer_email 而非 field1）
□ 枚举带说明 + unknown 兜底
□ 嵌套 ≤5 层，50 字段以上已拆分
□ 可选字段 null union（strict 兼容）
□ 顶层 object，additionalProperties: false
□ 错误契约统一（status/errors/attempts）
□ 版本号 + 变更流程
□ 描述与校验规则同文件
□ 契约变更跑评测回归
```

> 🎯 核心要点：契约是解析器的"宪法"——**设计契约时想的是"模型怎么生成、系统怎么消费"，而不是"字段叫什么"**。契约质量 = 解析成功率 + 消费端稳定性，双倍收益。

## 8. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 无描述字段 | 模型提取差 | 描述写全 |
| 大契约硬上 | 准确率暴跌 | 拆分 |
| 无版本 | 变更失控 | 版本化 |
| 枚举无兜底 | 新值崩 | unknown |
| 契约与校验脱节 | 规则过期 | 同文件 |
| 变更不回归 | 消费端坏 | 评测集 |
| 记录+数组混 | 解析歧义 | 清晰模式 |

## 9. 完整案例：客服订单抽取契约（端到端）

```text
需求：从客服对话中抽取订单信息 → 生成工单
契约设计五步：

① 定义实体（最小字段集）
   order: order_id, customer_name, items[], total_amount, status

② 枚举与描述
   status: pending(待确认)/confirmed(已确认)/cancelled(已取消)/unknown(无法判定)
   total_amount: "含税总金额，单位元"（描述防歧义）

③ 错误契约（抽取失败时可表达）
   status: ok/error + errors[] + attempts

④ 校验规则（与 schema 同文件）
   金额>0、items 非空、order_id 格式校验

⑤ 版本与消费端
   v1：抽取 → 工单系统（数据库交互 07 篇写入）
   v2（预留）：抽取 → 多 Agent 分派（消息契约）
```

| 设计决策 | 理由 |
|---|---|
| 最小字段集 | 5 字段准确率 >> 50 字段（2026 评测共识） |
| unknown 兜底 | 模型不确定时不瞎猜 |
| 错误契约 | 失败可见可回传 |
| 规则同文件 | 描述与校验永不脱节 |

## 10. 契约与多 Agent 消息（A2A 衔接）

| 消息类型 | 契约形态 | 说明 |
|---|---|---|
| 任务派发 | 目标 + 约束 + 预算 | 主管→工人 |
| 结果回传 | 状态 + 数据 + 引用 | 工人→主管 |
| 审批请求 | 动作 + 影响 + 一次性令牌 | HITL（数据库交互 07 篇） |
| 记忆写入 | 事实契约（Memory 05 篇） | 跨组件沉淀 |

> 💡 多 Agent 场景的契约原则：**消息即契约**——每个消息类型都有 schema + 版本号，接收方按版本解析（A2A 协议的工程实现）；与[多 Agent 范式](../..%2F主流%20Agent%20范式%2F07-多Agent协作范式.md)的消息设计呼应。

## 11. 契约文件规范（契约即文档）

```text
推荐目录结构（每契约一套）：
contracts/
├── order_extract/
│   ├── schema.json          # JSON Schema（strict 用）
│   ├── rules.yaml           # 业务校验规则（与 schema 同源）
│   ├── examples.json        # 正例/反例（评测与 few-shot）
│   ├── prompts.md           # 生成提示词（描述与规则一致）
│   └── CHANGELOG.md         # 版本变更记录
```

| 文件 | 消费方 |
|---|---|
| schema.json | strict 模式 + 解析校验 |
| rules.yaml | 业务校验（08 篇） |
| examples.json | 评测集 + 模型 few-shot |
| prompts.md | 生成侧（描述来源） |
| CHANGELOG.md | 版本化（05 节流程） |

> 💡 契约文件化的价值：**一套文件同时服务"生成（prompt）、约束（schema）、校验（rules）、评测（examples）"四方**——四方同源，永不脱节。

## 12. 契约评审清单（发布前）

| 评审项 | 检查 |
|---|---|
| 命名语义化 | 字段名=业务语义 |
| 描述完整性 | 每个字段有描述（单位/边界） |
| 枚举兜底 | 有 unknown 或合理默认 |
| 结构简单 | 嵌套 ≤5、字段 ≤50（大则拆分） |
| strict 兼容 | 全必填/null union/顶层 object |
| 错误契约 | status/errors/attempts 齐 |
| 规则同源 | rules 与 schema 同步 |
| 版本号 | CHANGELOG 记录 |
| 消费端确认 | 前端/数据库/工具按契约消费 |
| 评测集 | examples 覆盖正反例 |

> 🎯 核心要点：契约是解析器的"宪法"，评审是宪法的"立法程序"——**契约变更与代码变更同权重**（走评审+回归），这是 2026 年"契约工程化"的落地标准。契约的"宪法地位"还意味着：契约文件应入版本库管理（git），变更可追溯——schema.json 的 diff 就是契约演变的完整历史，评审与审计都基于它。契约设计心法一句话：**"模型读描述生成、系统读 schema 校验、评测读 examples 打分"——一份契约服务三个读者，三读一致才合格**。三个读者不一致的典型事故：描述说"金额单位元"而 schema 定义 integer——模型生成 12.5、schema 校验失败、评测集没覆盖——三读脱节即事故源头，契约文件化正是为了强制三读同源。
