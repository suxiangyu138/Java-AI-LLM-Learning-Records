# 流式输出解析

> 流式是 LLM 的默认姿势，但 JSON 是"整体才合法"的格式——矛盾所在。2026 年两条路：**修复派**（把残缺补合法）与**部分解析派**（产出不完整但可用的对象）。打字机效果与结构化解析可以兼得。

## 1. 流式解析的矛盾

| 事实 | 矛盾 |
|---|---|
| LLM 逐 token 生成 | JSON 必须整体合法 |
| 用户要逐字体验 | 解析要等完整对象 |
| 首 token 要快 | 攒完再解析 = 首屏等待 |

> 🎯 核心要点：流式解析的本质是**"在完整与及时之间做工程取舍"**——不是所有输出都要实时解析（决策类输出可以等，渲染类输出才要流式）。

## 2. 三种流式解析策略

| 策略 | 做法 | 适用 |
|---|---|---|
| 攒完再解析（collect-then-parse） | 收完 token 再整体解析 | 决策类（默认） |
| 修复流（repair） | 边收边修，输出合法 JSON | 需要渲染的场景 |
| 部分解析（partial parse） | 实时产出"不完整但可用"对象 | UI 实时渲染 |

```text
选型速判：
  输出给流程（数据库/工具）→ 攒完再解析（简单可靠）
  输出给用户看（聊天/表单）→ 部分解析（实时体验）
  输出给两端 → 双轨（内部攒完 + 前端流式渲染）
```

## 3. 攒完再解析：最简单可靠的默认

```python
async def collect_and_parse(stream, schema):
    chunks = []
    async for chunk in stream:
        chunks.append(chunk)
        yield None                      # 给前端原始增量（渲染用）
    data = parse("".join(chunks))       # 攒完统一解析
    yield validate(data, schema)        # 校验后交付
```

| 优点 | 缺点 |
|---|---|
| 简单可靠（无流式解析器依赖） | 结构化结果延迟到结尾 |
| 修复/校验路径复用 | 无法实时驱动 UI |

> 💡 大量生产场景其实用这个就够——"前端要打字机效果"与"后端要结构化数据"可以**双轨并行**（文本流给前端、对象流给后端），不一定要流式解析。

## 4. 修复派：边收边修

```python
# repair-json-stream 模式：push(chunk) → 实时修复输出 → end() 补全
from json_repair import repair_json

buf = ""
for chunk in stream:
    buf += chunk
    repaired = repair_json(buf)          # 每块尝试修复（可能为 None）
    if repaired:
        yield repaired                   # 实时输出合法 JSON（可能还不完整）
yield repair_json(buf + close_json(buf))  # end()：补全括号/引号
```

| 工具 | 能力 |
|---|---|
| jsonmend（Python） | 单遍流式修复，快 |
| repair-json-stream（JS） | push/end 状态化增量修复 |
| json_repair | 通用单次修复（配合缓冲） |

| 修复派注意 | 说明 |
|---|---|
| 重复修复成本 | 每 chunk 修复一次（可用节流） |
| 输出波动 | 补全前字段可能变化（UI 需容忍） |
| end 补全 | 最后必须补全括号保证 parse 成功 |

## 5. 部分解析派：永不报错的增量对象

| 库 | 特点 |
|---|---|
| jsiphon | 追加式模型（数据只增不改）、歧义树、容错前置文本、"永不抛错" |
| jsoncurrent | **补丁协议**：add/append/insert/complete 四操作，传输无关（SSE/WS） |
| stable-stream-core | 零布局偏移、Zod schema 水合、strictMerge 防幻觉字段 |

```text
jsoncurrent 架构：tokens → Emitter（解析+补丁）→ 中间件链（脱敏/转换）
                 → Collector（组装对象）→ UI
补丁操作：add(路径,值) / append(数组) / insert(索引) / complete(完成)
```

```python
# 部分解析的消费模式（伪代码）
for snapshot in partial_parse(stream):     # 每个快照都是"当前已知"
    form.update(snapshot)                  # UI 增量更新
# 快照永不完整，但永远可用——这就是"部分解析"的哲学
```

| 部分解析要点 | 说明 |
|---|---|
| 追加式 | 数据只增不改（UI 无需回滚） |
| 永不出错 | 非法输入返回部分结果 |
| 补丁增量 | 只传变化（省带宽） |
| 歧义容忍 | 流中途字段不确定是正常的 |

> ⚠️ 部分解析的 Unicode 陷阱（2026 实测）：**emoji 的代理对（😀）会被逐个解码产生孤立代理**——流式解析器必须按代理对解码，否则字符串值被破坏（vLLM/onyx 都踩过此坑）。

## 6. 框架级流式结构化：streamObject

```python
# Vercel AI SDK：流式对象生成（内部部分解析 + schema 水合）
const result = streamObject({
  model, schema: orderSchema,
  prompt: "分析订单...",
});
for await (const partial of result.partialObjectStream) {
  updateUI(partial);         // 实时部分对象
}
const final = await result.object;   // 最终完整对象
```

| 框架 | 流式结构化能力 |
|---|---|
| Vercel AI SDK | streamObject（部分对象流 + 最终对象） |
| LangChain | 流式 + 末尾解析（自行组装） |
| Spring AI | 流式 + 末尾解析 |
| 原生 SDK | 自行实现（本模块策略） |

## 7. 流式解析的评测与监控

| 指标 | 测什么 |
|---|---|
| 首对象时间 | 首个可用部分对象的延迟 |
| 快照稳定性 | 部分对象字段变化频率（高 → UI 抖动） |
| 最终正确率 | 完整解析后的 schema/语义正确率 |
| 流式开销 | 修复/解析的额外 CPU/延迟 |
| 代理对错误率 | Unicode 破坏率（应 0） |

> 🎯 核心要点：流式解析的工程原则——**"决策类输出攒完再解析，渲染类输出部分解析，能双轨就别混轨"**。流式解析是体验优化，不是正确性依赖——最终正确性永远以完整解析为准。

## 8. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| 全场景流式解析 | 决策输出也流式 | 按输出类型选策略 |
| 代理对乱码 | emoji 破坏 | 按对解码 |
| 修复风暴 | 每 chunk 全量修复 | 节流/状态化修复 |
| UI 依赖最终值 | 部分对象渲染错 | 快照容忍 + 最终覆盖 |
| 流式与校验脱节 | 流式过的没校验 | 最终校验兜底 |
| 无最终兜底 | 部分解析当正确 | collect-then-parse 收尾 |

## 9. 流式解析与前端渲染的配合

| 前端需求 | 流式方案 | 衔接 |
|---|---|---|
| 打字机效果（文本） | 文本流直接渲染 | 前端演示界面 06 篇 |
| 实时表单（部分对象） | 部分解析快照驱动 | jsiphon 模式 |
| 进度展示（结构化） | 补丁流（jsoncurrent）增量更新 | 补丁协议 |
| 最终一致 | collect-then-parse 交付 | 最终校验兜底 |

```text
典型组合（聊天 UI + 结构化输出）：
  文本流 → 打字机渲染（用户体验）
  结构化流 → 部分对象 → 卡片实时更新（信息密度）
  流结束 → 完整对象 → 最终校验 → 业务动作
  —— 三轨并行，各司其职（前端体系 02/08 篇协议支撑）
```

> 💡 工程要点：流式解析的输出格式（部分对象/补丁）要与前端组件约定一致——**"流式契约"是输出契约的流式形态**（09 篇契约体系的一部分），双端都要遵守。

## 10. 流式解析评测扩展

| 指标 | 目标 |
|---|---|
| 首部分对象延迟 | <1s（渲染场景） |
| 快照抖动率 | 字段变化次数/秒（低） |
| 增量效率 | 补丁字节/对象字节（低=省带宽） |
| 最终一致性 | 部分对象最终值与完整解析一致 |
| 资源开销 | 解析 CPU/内存（流式常驻） |

## 11. 流式解析选型速查表

| 场景 | 推荐 | 理由 |
|---|---|---|
| 决策输出（内部消费） | 攒完再解析 | 简单可靠 |
| 聊天文本（打字机） | 文本流直渲（不解析） | 无需结构化 |
| 实时表单/卡片 | 部分解析（jsiphon） | 实时对象 |
| 增量 UI 更新 | 补丁流（jsoncurrent） | 省带宽 |
| 工具参数流式 | 协议级累积（07 篇） | 按 index 缓冲 |
| 最终一致性要求 | 双轨（流式渲染 + 攒完校验） | 体验与正确兼得 |

> 🎯 核心要点：流式解析的选型口诀——**"内部消费攒完、用户消费部分解析、工具参数协议累积、永远最终校验"**。流式是体验层优化，正确性永远以完整解析为准。面试速记：先答"流式解析有攒完/修复/部分解析三种策略"，再答"按消费端选型、最终校验兜底"——完整且有条理。
