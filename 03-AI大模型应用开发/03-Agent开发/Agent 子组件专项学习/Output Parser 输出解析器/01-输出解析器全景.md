# 输出解析器全景

> 模型输出是"建议"不是"数据"——输出解析器是模型世界与应用世界之间的海关：解析、校验、修复三环节把关，结构化契约是通行证。2026 年共识：strict 模式保"格式"，应用层校验保"语义"。

## 1. 为什么需要输出解析器

| 模型输出的天性 | 后果 |
|---|---|
| 概率性生成 | 同输入不同输出（可能格式错） |
| 可能拒绝（refusal） | 安全拒绝时无内容 |
| 可能截断（token 上限） | JSON 半截 |
| 可能幻觉字段 | "看起来对"的值是编的 |
| 可能夹带指令 | 输出注入（后续消费端风险） |

> 🎯 核心要点：**解析器存在的唯一理由：把"可能出错的文本"变成"确定可用的数据"**——没有解析校验的 Agent 管道，是在"赌"模型每次都对。

## 2. 三环节：解析 → 校验 → 修复

```text
模型输出
  → ① 解析（Parse）：文本 → 结构化（JSON 等）
  → ② 校验（Validate）：schema 合规 + 业务语义
  → ③ 修复（Repair）：失败 → 重试/修复工具/降级
  → 可消费的结构化数据
```

| 环节 | 问题 | 失败后果 |
|---|---|---|
| 解析 | 语法对不对 | 直接崩/报错 |
| 校验 | 结构对不对、值合不合理 | 静默错误（最危险） |
| 修复 | 错了怎么救 | 重试成本失控 |

> ⚠️ 常见错误：**只做解析不做校验**——"JSON.parse 成功"≠"数据正确"（枚举错、类型错、字段缺都不报错）。校验是解析器的另一半。

## 3. 解析器在 Agent 管道中的位置

```text
大脑（模型输出）
  ├─ 普通文本 → 渲染（前端/聊天）
  ├─ 结构化输出 → 输出解析器（本体系）
  │     ├─ 工具参数 → Function Calling 协议层（工具组件）
  │     ├─ 规划/反思 → 计划/评估契约（规划/反思组件）
  │     └─ 业务数据 → 数据库交互（业务校验）
  └─ 流式 → 流式解析（05 篇）
```

| 消费端 | 需要的保障 |
|---|---|
| 工具执行 | 参数 schema 合规（07 篇） |
| 数据库写入 | 业务值域校验（08 篇） |
| 前端渲染 | 结构稳定（前端演示界面体系） |
| 下游流程 | 契约版本一致（09 篇） |

## 4. 与 Function Calling 体系的分工

| 维度 | 协议层（Function Calling 体系） | 本体系（输出解析器） |
|---|---|---|
| 范围 | tool_calls 的传输格式与回传协议 | 一切结构化输出的解析-校验-修复 |
| 关注 | "模型怎么声明与调用工具" | "输出怎么变成可靠数据" |
| 含 | tools 声明、tool_call_id 配对、流式组装 | strict 模式、失败修复、语义校验 |

> 💡 面试答题口径：tool_calls 是协议，输出解析器是工程——协议保证"格式对"，解析器保证"数据可靠"，两层缺一不可。

## 5. 失败代价：解析问题的四种死法

| 死法 | 场景 | 危害 |
|---|---|---|
| 崩溃式 | JSON.parse 抛异常 | 流程中断（显眼，好修） |
| 静默式 | 字段缺了/枚举错了不报错 | 下游用错数据（**最危险**） |
| 重试风暴 | 失败后盲目重试 | 成本失控（10 倍调用） |
| 延迟爆炸 | 流式不解析只等结尾 | 首屏等待翻倍 |

> 🎯 核心要点：**"解析失败"本身不可怕，可怕的是静默失败与盲目重试**——本章的每一篇都在回答同一个问题："输出错了，怎么让它快速、低成本、可察觉地变对"。

## 6. 2026 年解析器的能力演进

| 演进 | 旧 | 新 |
|---|---|---|
| 格式保证 | 提示词要求"输出 JSON" | strict 模式（采样层约束） |
| 评测标准 | 解析率（99.5%） | 语义质量（字段级） |
| 失败处理 | 报错重试 | 失败模式目录 + 修复工具链 |
| 流式 | 攒完再解析 | 增量部分解析（补丁协议） |
| 校验 | 不校验 | schema + 业务双层校验 |

> 🎯 核心要点：2026 年的输出解析是**"strict 保格式 + 校验保语义 + 修复保可用"**的三层防线——只依赖任何一层都会翻车（strict 挡不住语义错，校验挡不住语法错，修复挡不住业务错）。三层防线对应三类失败：格式错（strict/修复）、语义错（校验）、流程错（错误契约）——排查时先定位失败类型再选防线。

## 7. 心智模型：解析器四问

| 问题 | 答案决定 |
|---|---|
| 输出要什么格式？ | 契约设计（09 篇） |
| 格式怎么保证？ | strict 模式 or 提示词（03 篇） |
| 错了怎么救？ | 失败处理策略（04 篇） |
| 怎么证明它对了？ | 语义评测（10 篇） |

## 8. 完整工作流示例（一次契约输出的全旅程）

```python
def structured_extract(text: str, schema: dict) -> dict:
    # ① 生成（strict 优先）
    out = llm.generate(text, response_format={"type": "json_schema",
                                              "json_schema": {"strict": True,
                                                              "schema": schema}})
    if out.refusal:                                # ② 拒绝检测
        return error_contract("refused", "内容无法处理")

    # ③ 解析（剥围栏 + JSON.parse + 修复）
    try:
        obj = extract_json(out.text)
    except ParseError:
        obj = repair_and_parse(out.text)           # 修复工具（04 篇）

    # ④ 校验（schema + 业务）
    errors = validate_all(obj, schema)             # 三层校验（08 篇）
    if errors:
        return error_contract("validation_failed", errors)

    # ⑤ 交付（契约化输出）
    return {"status": "ok", "data": obj}
```

| 环节 | 失败 → 下一动作 |
|---|---|
| 拒绝 | 提示用户，不重试 |
| 解析失败 | 修复工具 → 重试（带反馈） |
| 校验失败 | 错误回传 → 重生成 |
| 全部失败 | 错误契约（可见失败） |

## 9. 常见误区

| 误区 | 真相 |
|---|---|
| "strict 就够了" | strict 保格式不保语义，校验必须接 |
| "解析率 99% 就放心" | 语义错不体现在解析率里 |
| "失败就重试" | refused/truncated 重试无效 |
| "框架帮我解析了" | 框架不校验语义 |
| "JSON 就是一切" | 格式选择依消费端（09 篇） |
| "解析器是一次性组件" | 契约/评测需要持续维护 |

## 10. 输出解析器的成熟度模型

| 成熟度 | 解析 | 校验 | 失败处理 | 评测 |
|---|---|---|---|---|
| L1（能用） | 提示词+JSON.parse | 无 | 报错重试 | 无 |
| L2（可靠） | strict 模式 | schema 校验 | 反馈重试 | 解析率 |
| L3（可演进） | strict+fallback 链 | 三层校验 | 失败目录+修复链 | 语义评测 |
| L4（企业级） | 模式矩阵选型 | 校验即回传闭环 | 教训记忆化 | 自建集+回归 CI |

**判断你的解析器在几级**：三问——① 输出错了能分类处理吗？（L1 只会重试）② 校验挡得住语义错吗？（L2 只挡格式）③ 评测测的是"值对不对"吗？（L3 才测语义）。

> 💡 成熟度速查：L1 是"能跑"，L2 是"能稳"，L3 是"能优"，L4 是"能证"——对外产品至少 L3；评测进 CI 是 L4 的标志。

## 11. 解析器在四组件中的归属

| 组件 | 解析器角色 |
|---|---|
| 大脑 | 输出结构化的第一道工序（本体系） |
| 工具 | 工具参数解析（07 篇） |
| 记忆 | 事实提取契约（Memory 05 篇） |
| 规划/反思 | 计划/评估契约（输出都是结构化） |

> 💡 四大核心组件（大脑/规划/反思/工具）的输出全部要过解析器——**输出解析器是四组件的公共底座**，这也是它成为"子组件专项"的原因。学习路径建议：先本体系（解析全流程）→ 再 Function Calling 体系（协议层）→ 后四大核心组件（组件整合）——解析器是理解其他组件输出的钥匙。一个合格的 Agent 工程师生涯里，调得最多的三样东西就是：提示词、工具描述、输出契约——三者都与本体系直接相关。本体系与[Memory 记忆系统](../Memory%20记忆系统/00-Memory记忆系统总览.md)同为"子组件专项"：记忆系统管"输入什么进上下文"，输出解析器管"输出什么进系统"——一个管入口一个管出口，共同构成 Agent 的数据完整性边界。
