# 函数调用与结构化输出：工具参数解析

> tool_calls 本身就是"最强形式的结构化输出"——参数由模型按 schema 生成。但流式参数是部分 JSON、strict 与并行调用互相冲突、各家强制力不同——工具参数解析是输出解析器在 Agent 场景的主战场。

## 1. tool_calls 即结构化输出

| 维度 | 普通结构化输出 | tool_calls 参数 |
|---|---|---|
| Schema 来源 | 你定义 | 工具声明（tools 参数） |
| 强制力 | strict 可选 | 各家不同（07 篇 4 节） |
| 流式 | 自选策略 | **协议级流式（增量累积）** |
| 消费方 | 应用流程 | 工具注册表（四大核心组件 06 篇） |

> 🎯 核心要点：**工具调用把"输出解析"前移到了协议层**——模型直接产出结构化参数，解析器的工作变成"累积、校验、执行"。

## 2. 流式参数累积：部分 JSON 的协议级处理

```text
流式 tool_calls 到达：
  chunk1: {"id":"t1","function":{"name":"search","arguments":"{\"q\":"}}
  chunk2: {"id":"t1","function":{"arguments":"\"天气\""}}
  chunk3: {"id":"t1","function":{"arguments":"}"}}
  → 按 id 累积 arguments → 完整后整体 JSON.parse
```

```python
def accumulate_tool_calls(stream):
    buffers = {}                        # tool_call_id → 参数累积缓冲
    for chunk in stream:
        for tc in chunk.choices[0].delta.tool_calls or []:
            buf = buffers.setdefault(tc.index, {"name": "", "args": ""})
            buf["name"] += tc.function.name or ""
            buf["args"] += tc.function.arguments or ""
            yield {"index": tc.index, "partial_args": buf["args"]}  # 增量
    # 流结束后：buffers 中的 args 是完整 JSON → 解析
    return {i: json.loads(b["args"]) for i, b in buffers.items()}
```

| 累积要点 | 说明 |
|---|---|
| 按 index 累积 | 并行工具调用多个 index |
| 片段不可 parse | 每个 chunk 是部分 JSON，**不能单独 JSON.parse** |
| 结束时才解析 | 完整后整体解析 |
| 空名处理 | name 可能只出现在首 chunk |

> ⚠️ 经典错误：对单个 chunk 的 arguments 做 JSON.parse 会抛异常——必须累积到完整。工具组件层的完整生命周期见[四大核心组件](..%2F..%2FAgent%20四大核心组件%2F06-工具组件：Function-Calling与工具注册.md) 06 篇。

## 3. 参数校验：模型输出不可信（与 08 篇衔接）

```python
def execute_tool_safely(name, args):
    tool = registry.get(name)
    args = schema_validate(args, tool.schema)   # ① schema 校验（strict 参数）
    args = business_validate(args, tool.rules)  # ② 业务校验（值域/权限）
    return tool.execute(args)
```

| 校验层 | 防什么 |
|---|---|
| schema 校验 | 缺字段/类型错/额外属性 |
| 业务校验 | 值域越界/无权限/危险操作 |
| 注入校验 | 参数里夹带指令 |

## 4. 强制调用与 strict 的冲突

| 场景 | 冲突 | 解法 |
|---|---|---|
| strict + 并行调用 | **strict 下并行调用失效**（规范限制） | 关并行或关 strict |
| 强制调用 tool_choice | 参数必须合法 | 配合参数校验 |
| 多工具路由 | 选错工具 | tool_choice 指定或描述优化 |

```text
2026 已知限制：OpenAI strict 模式下并行工具调用不可用——
  需要并行时：① 关 strict ② 用非 strict 的并行 ③ 业务层合并调用
```

> 💡 工程取舍：**strict 优先于并行**（参数正确性 > 速度）；确有并行需求时用"单工具 + 批量参数"替代多工具并行。

## 5. 工具参数解析的失败处理

| 失败 | 处理 |
|---|---|
| 参数解析失败 | 错误 JSON 回传模型（tool 消息）→ 重生成 |
| 参数校验失败 | 校验错误回传 → 模型修正 |
| 工具不存在 | 回传"未知工具"→ 模型换工具 |
| 参数截断 | 增大 max_tokens 或提示分段 |

```python
# 错误回传（消除 80% 工具卡死的关键模式）
tool_message = {"role": "tool", "tool_call_id": tc_id,
                "content": json.dumps({"error": "参数校验失败：status 必须在枚举内",
                                       "hint": "可选值: paid/pending/cancelled"})}
messages.append(tool_message)          # 回传 → 模型修正后重试
```

> 🎯 核心要点：工具参数解析的黄金闭环是**"解析失败 → 错误信息回传（带 hint）→ 模型修正 → 再执行"**——这比任何重试策略都有效（Function Calling 体系的实测结论）。

## 6. 各家工具调用的 schema 强制力

| 提供商 | 强制机制 | 说明 |
|---|---|---|
| OpenAI | strict tools | 采样级（新模型） |
| Anthropic | input_schema + tool_choice | 提示词级（强提示） |
| Gemini | function_declarations | 一般 |
| DeepSeek 等兼容 | OpenAI 兼容 | **实测为准**（探针测试） |

## 7. 常见坑速查

| 坑 | 现象 | 解法 |
|---|---|---|
| chunk 直接 parse | 抛异常 | 按 index 累积 |
| strict 下并行 | 并行失效 | 关并行或关 strict |
| 校验缺失 | 坏参数执行 | schema+业务双校验 |
| 错误不回传 | 模型重复错 | tool 消息回传 |
| 参数截断 | JSON 半截 | 增大上限/重试 |
| 工具名拼错 | 找不到工具 | 回传换工具 |
| 无 hint 报错 | 模型不知道怎么改 | 错误带建议 |

## 8. 工具参数解析完整示例（端到端）

```python
def handle_tool_calls(stream, registry):
    buffers = {}                                  # ① 累积缓冲
    for chunk in stream:
        for tc in chunk.choices[0].delta.tool_calls or []:
            buf = buffers.setdefault(tc.index, {"name": "", "args": ""})
            buf["name"] += tc.function.name or ""
            buf["args"] += tc.function.arguments or ""

    results = []
    for idx, buf in buffers.items():              # ② 流结束统一解析
        try:
            args = json.loads(buf["args"])        # 完整 JSON 解析
            args = validate_args(buf["name"], args)   # ③ schema+业务校验
            result = registry.execute(buf["name"], args)  # ④ 执行
            results.append(tool_result(idx, result))
        except ToolError as e:
            results.append(tool_result(idx, {"error": e.sanitized,
                                             "hint": e.hint}))  # ⑤ 回传
    return results
```

| 环节 | 关键 | 失败路径 |
|---|---|---|
| 累积 | 按 index 缓冲 | 片段不 parse |
| 解析 | 完整后统一 | 错误 JSON 回传 |
| 校验 | schema+业务 | 错误+hint 回传 |
| 执行 | 注册表调用 | 错误回传 |
| 回传 | tool 消息配对 | 配对错 → 模型卡死 |

## 9. 工具参数错误回传模板

| 错误 | 回传内容（tool 消息） |
|---|---|
| 参数解析失败 | `{"error": "arguments 无法解析为 JSON", "raw": "<片段>"}` |
| 校验失败 | `{"error": "status 非法", "hint": "可选: paid/pending/cancelled"}` |
| 工具不存在 | `{"error": "未知工具 search_oders", "hint": "可用: search_orders"}` |
| 权限拒绝 | `{"error": "无权限", "hint": "请使用只读查询"}` |
| 执行超时 | `{"error": "超时", "hint": "请缩小查询范围"}` |

> 🎯 核心要点：工具参数解析的黄金闭环——**累积（不 parse 片段）→ 解析（完整后）→ 校验（双校验）→ 执行（注册表）→ 回传（错误带 hint）**。五步闭环是工具调用成功率的第一杠杆（实测消除 80% 工具卡死）。

## 10. 工具参数 schema 设计要点

| 要点 | 说明 |
|---|---|
| 参数即决策负担 | 每个参数都增加模型负担——**能省则省** |
| 可选参数独立成工具 | 减少必填项（Function Calling 体系结论） |
| 枚举参数优先 | 类别参数用枚举（准确率+校验） |
| 描述写边界 | "仅查询，不修改"（越权防护） |
| 默认值声明 | 描述中写明缺省行为 |
| 大小限制 | 字符串长度/数组长度上限（防注入巨参） |

```text
参数设计心法：
  模型每填一个参数就多一分错的可能
  → 参数越少，工具调用越稳（"最小参数原则"）
```

**工具参数解析与输出契约的同一性**：工具 schema 本质是"输出契约"的一种——模型按 schema 生成参数。因此 09 篇的契约原则（语义命名/枚举兜底/版本化）对工具 schema 同样适用，且工具 schema 变更会影响所有调用方（模型行为+校验规则），版本管理比业务契约更严格（工具描述参与缓存键，变更即缓存失效）。
