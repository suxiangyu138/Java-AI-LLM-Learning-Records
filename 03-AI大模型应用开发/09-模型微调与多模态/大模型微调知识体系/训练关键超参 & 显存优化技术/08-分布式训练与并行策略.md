# 分布式训练与并行策略

> 多卡时代的选型地图：并行四策略（DP/ZeRO/TP/PP）、10B 规则（FSDP vs DeepSpeed）、LoRA 混合分片（通信量 ↓89%）——先确认"真的需要多卡吗"

## 1. 并行四策略

分布式训练的四种并行方式，解决不同的问题：

**数据并行（DP）**：每卡一份完整模型副本，各吃不同 batch，梯度同步（AllReduce）——最常用，但**每卡显存 = 单卡全量微调显存**（不省显存，只省时间）。

**分片数据并行（ZeRO/FSDP）**：数据并行的进阶——把权重/梯度/优化器状态**分片**到各卡（ZeRO-1 只分优化器状态、ZeRO-2 加梯度、ZeRO-3 全分片），**每卡显存 ≈ 单卡 ÷ 卡数**——省显存的分布式方案（06 篇的"账本除法"）。

**张量并行（TP）**：**单层内**拆分（注意力/FFN 的矩阵切到多卡，层内 AllReduce）——单层装不下时用；通信量极大（每层全量同步），**只适合 NVLink 高速互联的节点内**（4-8 卡）。

**流水线并行（PP）**：**按层切段**，段间流水线执行——跨节点通信少但有空泡（pipeline bubble）；512+ 卡规模才需要。

**3D 并行**（ZeRO/FSDP + TP + PP）：大模型全量预训练的标准组合（70B 级 8×A100 用 ZeRO-3 + TP；405B 级 16384 卡用 TP8 + PP16 + DP128）——微调场景极少需要。

## 2. 10B 规则：FSDP vs DeepSpeed

**10B 参数是分布式框架选型的决策阈值**（2026 实测）：

| 场景 | 选型 | 依据 |
|------|------|------|
| <10B | **FSDP** | 轻量原生集成，7B 4×A100 实测 3159 vs 3095 tokens/s（微优） |
| 10B+（显存受限） | **DeepSpeed ZeRO-3** | ZeRO-Infinity 的 CPU/NVMe offload 解决 OOM |
| 高速互联（NVLink） | FSDP | 通信开销可忽略 |
| PCIe 互联 | 慎用 FSDP | 4 卡实测只到 ~2.5× 线性加速（all-gather 延迟） |

HuggingFace Accelerate 把两者抽象在统一 API 后（单配置切换引擎），选型成本更低——但 **10B 规则的物理依据不变**：FSDP 轻量快、DeepSpeed 的 offload 是显存极限场景的刚需。

## 3. 通信成本：隐藏的性能杀手

分片并行的通信开销：**每步 ~3× 模型大小的通信量**（all-gather 权重 + reduce-scatter 梯度）vs 普通 DP 的 2× 梯度——**通信超过计算时间的 20% = 通信受限（communication-bound）**，表现是"加卡不加速"。

优化手段：梯度累积（减少同步次数）、通信与计算重叠（FSDP 默认支持）、更大 micro-batch、ZeRO-2/ZeRO-1 降档（通信更少）、**互联选择**（NVLink ~900GB/s vs PCIe ~32GB/s——互联是隐藏瓶颈，PCIe 上 4 卡 FSDP 只有 ~2.5× 加速）。

**offload 的代价**：ZeRO-Infinity 的 CPU/NVMe offload 让 70B 在 24GB 卡上可训，但**训练速度掉 20-50%**（DeepSpeed 官方 20-30%，CPU offload 一般 30-50%）——offload 是"显存换时间"的最后手段。

## 4. LoRA 混合分片：LoRA 并行的正确姿势

**LoRA 的参数不该像全量权重那样分片**（低秩参数 shard 后通信浪费）——2026 年 5 月实测（LLaMA-2-7B，A100×32）：**DeepSpeed ZeRO-3 + FSDP 混合分片**（底座 ZeRO-3 分片、LoRA 适配器 FSDP 分片）把 Adapter 参数通信量降低 **89%**、吞吐提升 **2.7×**（对比标准分片）；单节点 A100×8 上 LoRA 梯度同步曾占 step 时间的 **63%**——LoRA 场景的通信优化收益巨大。

**实践含义**：多卡 LoRA/QLoRA 微调不要直接套全量分片配置——用支持混合分片的框架配置（或至少确认适配器参数的分片方式）；小模型（7B 级）单节点内通信开销占比高，**先确认"多卡真的比单卡快"**（7B QLoRA 单卡 24GB 就能跑，多卡只省时间不省显存）。

**加速比的预期管理**：分布式不是线性的——2 卡理想 1.9×、实际 1.5-1.8×（通信 + 调度开销）；4 卡理想 3.8×、实际 2.5-3.2×（PCIe 环境更差，08 篇第 3 节）；**"加卡到收益拐点就停"**——7B 级 4 卡是常见甜点（再往上通信占比压过计算收益），70B 级才需要 8-64 卡——**加速比预期写进训练排期**（按实际 70-80% 折扣算），避免"4 卡以为 4 倍速"的排期翻车。

**多卡环境的排障要点**（与 `../微调常见问题/06-显存与性能问题.md` 04 节互补）：启动前检查——卡间 NCCL 连通（`nccl-tests` 或小模型冒烟）、端口不冲突（MASTER_PORT 随机高位）、共享存储就绪（checkpoint 落共享盘）；训练中监控——各卡显存/利用率均衡（某卡 OOM 其他卡空闲 = 分片配置问题）、loss 分卡一致（某卡 loss 异常 = 该卡数据/配置问题）；**"卡数减半排障"技巧**：8 卡出问题先 4 卡复现——问题仍在 = 逻辑问题（与卡数无关），问题消失 = 通信/同步问题——一步隔离两个方向。

**分布式与单卡的心理预期**：分布式解决的是"**装不下**"（显存）与"**训太久**"（时间）两个问题——**装不下才需要分片，训太久才需要并行**；QLoRA 时代 7B-14B 几乎总装得下（单卡 24GB），"多卡微调"的多数真实需求其实是"时间"（数据量大时单卡要跑几天）——**先算单卡时间**（09 篇公式：总 token ÷ 吞吐），单卡 2 天内能完成就单卡跑（省掉分布式全部复杂度）；只有"单卡 5 天+ 且排期等不起"才值得上多卡。

**并行策略的"混合现实"**：真实生产中很少单用一种并行——**ZeRO-3 + TP 是 70B 级常见组合**（ZeRO 分片解决显存、TP 解决单层装不下，实测 4×4 组合把 70B 压到 ~26GB/卡）；LoRA 场景是"ZeRO-3 底座 + FSDP 适配器"的混合分片（第 4 节）；**读框架文档时先确认它支持哪种混合**（DeepSpeed 配置的 zero_optimization + tensor_parallel 组合、FSDP 的 sharding_strategy 与 TP 的搭配）——"框架支持的混合"决定"你能用的策略"，规划时先查支持矩阵再定组合。

## 5. 分布式规划决策树

2026 参考决策树（`../完整微调工程流程/06-训练配置与启动.md` 04 节）：**单卡能跑吗**（QLoRA 账本算过）→ 能：单卡（少一套复杂度）；不能 → **单层装得下吗**（模型分片后单层能放下）→ 装不下：
TP（节点内）；装得下 → **节点内装得下吗** → 装不下：PP；装得下 → **数据并行（FSDP/ZeRO-3）**——配置示例：7B → 8 卡 TP=1 DP=8 FSDP；70B → 64 卡 TP=8 DP=8 FSDP；405B → 16384 卡 3D 并行。**分布式是复杂度大户**（通信/NCCL/多卡排障，`../微调常见问题/06-显存与性能问题.md` 04 节）——单卡能解决的问题不要上多卡。

## 6. 2026 趋势

FSDP2 + TP + PP（TorchTitan）与 Megatron-Core 是 70B 全量预训练推荐栈；MoE 大模型（405B+）用 Megatron-Core（EP/CP）或 DeepSpeed MoE；
Blackwell GB200 上每 token 训练成本比 H100 低 30-40%（FSDP2 把万亿 token 的 70B 训练压到约一周）；2027 展望：torch.compile + FSDP2 成默认、DeepSpeed 收窄到 ZeRO++ 通信优化与 NVMe offload 细分——**微调场景的落地结论不变：<10B 用 FSDP、LoRA 用混合分片、先确认多卡值得**。

> 🎯 **核心要点**：并行四策略——DP（不省显存）/ZeRO-FSDP（账本除法）/TP（单层内，限 NVLink）/PP（按层切段，512+ 卡）；10B 规则——<10B FSDP、>10B 显存受限 ZeRO-3（offload 掉 20-50% 速度）；通信成本每步 3× 模型大小，>20% 时间即通信受限，PCIe 互联慎用 FSDP；LoRA 混合分片（ZeRO-3+FSDP）通信 ↓89% 吞吐 2.7×——LoRA 场景别套全量分片；决策树从"单卡能不能跑"开始，分布式是复杂度大户。
