# 数据清洗

> 数据进入训练集前的第一道关卡：格式清洗、内容过滤、完整性检查——清洗的目的是"让数据可被训练"，坏数据在源头拦下

## 1. 清洗的定位与顺序

清洗（cleaning）与去重（05 篇）、评估筛选（07 篇）构成数据流水线的三个连续关卡：**清洗处理"数据本身的问题"（格式/内容/完整性），去重处理"数据之间的关系"（重复/污染），评估处理"数据的质量分级"（好坏取舍）**。顺序上清洗先行——格式乱的样本在去重（哈希/分词）和评估（judge）环节都会出错。

清洗目标一句话：**让每条样本格式统一、内容干净、结构完整，具备被训练的基本资格**——它不是"提升质量"（那是 07 篇的活），而是"排除不合格品"。

清洗的验收标准：清洗后抽样 20 条人工检查——格式统一、内容干净、无截断、无模板残留；不合格返回上一环节或调规则库。**没有验收的清洗等于没洗**——跑完脚本不做检查，脏数据照样溜进训练集。

## 2. 格式清洗

格式问题不解决，训练器可能直接报错或静默学错：

**编码与字符**：统一 UTF-8（历史数据常混 GBK/Latin-1，Python 读文件时指定 `encoding="utf-8"` 并捕获 UnicodeDecodeError 记入异常清单）；BOM 头剥离（UTF-8 BOM 会让首条文本带不可见字符）；清理不可见字符、控制字符、零宽空格（`​` 这类在文本里看不见但 token 化后产生垃圾 token）；全角/半角标点按需统一（中文场景半角引号混入会在分词时出错）；换行统一（CRLF → LF，混用会破坏按行解析的 JSONL）。

**模板残留**：从网页/系统导出的数据常带模板痕迹——"本回答由 AI 生成""来源：xxx.com""图 1：xxx"等；从对话系统导出的可能带 UI 元素（按钮文案、时间戳）。用模板特征（正则 + 频率统计）识别并剥离。

**Markdown/HTML 残留**：需要结构化输出的任务，残留的 HTML 标签、乱掉的 Markdown 语法会让模型学到错误的输出格式（format leakage）——按任务需要统一保留或剥离。

**JSON 合法性**：工具调用/结构化数据样本，arguments 字段必须是可解析的合法 JSON——整库扫描校验（`json.loads` 全量跑一遍），解析失败的样本标记待修或剔除（与 `../基础概念/08-指令数据与对话格式基础.md` 的工具数据铁律呼应）。

## 3. 内容过滤

内容过滤解决"数据里有什么不该有的"：

**毒性/有害内容**：显式色情、暴力、仇恨言论——用分类器（Detoxify 类）批量扫 + 人工抽检。注意边界：行业数据（医疗讨论、法律案件）可能含敏感词但合法——**过滤规则要按业务语义设计**，一刀切会误杀有效数据。

**PII 与隐私**：姓名、手机号、邮箱、身份证、地址——规则识别（正则）+ 模型识别（Presidio、spaCy NER 等）双通道；命中 PII 的样本按策略处置：脱敏（替换为假名）、剔除、或标记人工复核。PII 处理的完整合规链路在 09 篇——清洗阶段先把"带敏感信息的样本"找出来，处置决定留给治理流程：**清洗只标记不擅自删除**（PII 类型、命中位置写入样本元数据），删除决策由治理流程按合规要求执行——擅自删数据会让血缘断裂、审计说不清。

**语言一致性**：中英混用的脏样本（回答里夹带乱码语言）、纯外语样本误入中文任务——语言检测（fastText lid 类）按任务语言过滤或分桶。

**广告/噪声文本**：从网页爬取的文本常带广告、导航、版权声明——用启发式规则（行长度、重复率、域名特征）批量识别。

## 4. 完整性检查

完整性检查在清洗最后做，防止"能解析但内容残缺"的样本混入：

- **字段完整性**：messages 是否齐三角色（system/user/assistant）、回答是否为空、role 是否合法——schema 校验脚本全量跑。
- **NaN/异常值**：数值字段的 NaN、null、空串、纯空白——Unsloth 等框架的训练前置校验明确要求 NaN 检查（NaN 会静默污染梯度，训练 loss 突然跳变常有它一份功劳）。
- **截断痕迹**：样本是否被截断（末尾无结束 token、回答戛然而止）——长文本清洗时常见，截断样本要么补全要么剔除。
- **长度异常**：长度分布直方图检查（IQR 法找离群值）——超短（一两 token 的回答）通常是空转样本；超长（远超 max_seq_length）要么截断要么拆分成多轮。

## 5. 清洗流水线工程化

清洗不是一次性脚本，而是可复现的流水线（与 09 篇版本管理联动）：

- **阶段化**：格式清洗 → 内容过滤 → 完整性检查，每阶段输出统计报告（处理了多少、删了多少、各原因占比）——报告既是质量审计证据，也是下一轮清洗的改进依据。
- **可复现**：清洗规则版本化（规则脚本进 git），清洗前后数据都保留（原始版 + 清洗版双份），任何规则变更可回溯"哪些样本被删了、为什么"。
- **误删审计**：每个清洗步骤都留"删除清单"（样本 ID + 删除原因）——生产级要求是删除可逆（清单在手，误删能恢复）；宁可多留待人工复核，不要一刀切误杀。

清洗规则要沉淀成**规则库**：正则规则（模板特征、广告模式、编码异常）按类别维护，新规则带测试用例（针对已知脏样本验证命中/误伤）；规则库版本化（改动走 git，与数据版本联动）——清洗脚本的价值 20% 在首次执行，80% 在规则库的持续积累。

2026 年工业 SOP 的形态（参考中文社区工业清洗方案）：规则清洗 → 三阶去重（05 篇）→ 质量评分 → 分层采样——清洗是流水线的第一步，后面还有三道关卡，别指望一步到位。

> 🎯 **核心要点**：清洗 = 格式统一（编码/模板残留/JSON 合法性）+ 内容过滤（毒性/PII/语言/广告）+ 完整性检查（字段/NaN/截断/长度）；清洗解决"数据本身的问题"，与去重（关系）、评估（分级）分工；流水线阶段化 + 删除清单可逆 + 规则版本化——清洗是可审计的工程，不是一次性脚本。
