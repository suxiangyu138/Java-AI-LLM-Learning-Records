# 数据质量评估与筛选

> 清洗拦"不合格品"，评估选"优良品"：红旗清单逐条检查 + LLM judge 批量打分 + 数据集级体检——质量筛子是微调效果的最终防线

## 1. 评估的三层结构

数据质量评估分三层，从单条到整体：

**逐条检查**（样本级）：每条样本过红旗清单——不合格直接拒。
**批量打分**（judge 级）：LLM judge 给每条打分，淘汰底部 10-20%。
**整体体检**（数据集级）：分布统计 + 检查清单——保证"集合"健康，而不只是"个体"健康。

三层缺一不可：只有逐条检查（人力不够，只能抽检）、只有 judge（judge 会漏系统性偏差）、只有体检（发现时已晚）。三层联动才构成完整的质量筛。三层的成本顺序也遵循"便宜前置"原则：体检最便宜（脚本全量跑）、judge 中等（API 批量调用）、人工抽检最贵（只做小样）——**越贵的检查越往后，每层都在为下一层缩减输入量**。

## 2. 逐条检查：红旗清单

2026 年标准红旗清单（命中任一即拒）：

- **自相矛盾**：回答前后冲突（前半说支持、后半说不行）。
- **有害内容未拒答**：问题有害但回答照答（安全对齐要求拒答示范进数据）。
- **幻觉引用**：编造来源/链接/数字（事实类任务的红线）。
- **指令复述**：回答只是把问题重说一遍，没有实际内容。
- **模糊未澄清**：指令明显有歧义但回答未澄清直接猜。
- **格式错误**：要求 JSON 却输出散文、角色越界（assistant 说 user 的话）。

反向的合格判据：**相关性**（回答对题）、**准确性**（事实/逻辑正确）、**完整性**（该说的都说了）、**简洁性**（不注水）、**格式一致性**（符合任务模板）。人工抽检标准：随机 20 条人工过一遍红旗清单，抽样误检率超标则整批重审。

## 3. LLM judge：批量打分

人力无法逐条评估，2026 年标准做法是 **LLM judge（大模型裁判）**：让一个强模型（judge 模型）按评分标准给每条样本打分，设定阈值淘汰。流程：

**评分标准**：明确四个打分维度（指令遵循度、忠实度、安全性、正确性）——judge prompt 里写清维度定义与打分刻度（1-5 分），维度定义要可执行（"出现幻觉引用扣到 1 分"）。

**阈值与淘汰**：低于阈值（如 3 分）剔除；**通常淘汰底部 10-20%**——微软工作流的标准动作。淘汰比例过高说明生成阶段有问题（回去调教师模型），过低说明标准太松（调阈值或 judge）。

**judge 模型选择**：用强于训练目标的模型（一般选比学生强一档的 API 模型）；**避免用生成数据的同一模型当 judge**（自我打分偏差）；judge 要与人工基准对齐——先跑 50 条人工标注 vs judge 打分，一致性（Kappa）低则改 judge prompt。

**质量漂移**：judge prompt 在前 1 万条有效，可能漏掉第 5 万-10 万条的新失败模式（2026 明确提醒）——**judge 定期重校准**：每批抽检 20-50 条人工复核，发现新失败模式就更新评分标准。

**judge 评分的工程细节**：评分用结构化输出（judge 返回 JSON：各维度分数 + 一条理由），理由文本是人工复核的索引（只查"给高分但理由可疑"的样本）；分数分布要体检——全部 5 分（太宽松，调标准）或全部 2 分（太严格，调阈值）都是异常；judge 调用带温度 0（评分任务要确定性，与生成任务的多样性要求相反）；打分维度拆分而不是"整体打一个分"——维度分在人工复核时能定位具体问题。

## 4. 数据集级体检清单

单条都合格不代表集合健康，训练前过一遍整体清单（2026 标准）：

- **来源占比**：任一来源/模板的样本不超过总量 5%——防模板过拟合（一个模板生成 1 万条，MinHash 去重没抓净的话，模型学会模板而非任务）。
- **有效 token 占比**：至少 80% 的回答 token 是有意义的（非重复、非填充、非停用词堆砌）。
- **回答长度分布**：平均 50-200 token，过长过短要查（极端长度通常是空转/注水/截断）。
- **system 多样性**：至少 10 个不同 system prompt——只用一个 system 会让模型在换 system 时行为漂移。
- **重复检查**：精确/近似重复率统计（抽样哈希 + MinHash），超过阈值（如 5%）返回去重环节。
- **类别平衡**：任务类别分布与真实请求分布对齐（方法论在 08 篇）。
- **污染检查**：与 benchmark 重叠检测（05 篇第 5 节，hard reject 级要求）。

## 5. 评估 → 筛选 → 迭代的闭环

质量评估不是一次性的，而是训练迭代的一环（微软六步工作流的数据部分）：

1. **评估集先行**：种子集（金标）拆出 5-10% 做离线回归集——每次训练后必跑，防止回归。
2. **训练后重评**：用同一批 judge 对训练后的模型输出重新打分——**数据质量与模型质量对账**：judge 认为模型输出差但数据样本好，说明训练问题；两者都差，说明数据问题。

迭代节奏参考：**周更闭环**（每周一次：收集失败案例 → 补数据 → 重训 → 回归集验证）是生产常态；有线上日志的项目可以更快（日志回流驱动）。每次迭代必须过回归集（离线评估集）——**回归失败 = 本次数据迭代引入回归，先修数据再上线**；回归通过才进灰度。数据迭代的速度上限由评估集质量决定——评估集跟不上（漏覆盖新任务），迭代就盲目。
3. **失败模式驱动补数据**：从评估失败样本反推缺口——哪类任务、哪类边界做不好，针对性生成/补充该模式的数据，重训。**这是数据迭代的正确节奏：不是"一次把数据做到完美"，而是"评估 → 找缺口 → 补数据 → 再评估"的闭环**。

> 🎯 **核心要点**：三层质量筛——红旗清单逐条拒（自相矛盾/有害未拒/幻觉/复述/模糊/格式错）、LLM judge 批量打分淘汰底部 10-20%（judge 要与人工对齐、定期重校准防质量漂移）、数据集级体检（来源≤5%/有效 token≥80%/长度 50-200/system≥10 个/污染必查）；质量是评估→找缺口→补数据的迭代闭环，不是一次性动作。
