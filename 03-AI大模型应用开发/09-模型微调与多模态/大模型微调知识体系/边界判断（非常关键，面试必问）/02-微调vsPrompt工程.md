# 微调 vs Prompt 工程

> 提示词能解决的边界、few-shot 与提示缓存的成本优势、Prompt 失效的信号、切换微调的判据

## 1. Prompt 工程的能力边界

Prompt 工程是零成本杠杆（改文字即可），它擅长解决**行为缺口**的全部常见形态：**风格与语气**（"用专业但易懂的语气回答"）、**格式要求**（"输出 JSON，字段为 title/content"）、**行为约束**（"不确定就说不确定，不要编造"）、**少量示例引导**（few-shot 示范期望的输出形态）。

它不擅长解决的：**一致性不可靠**（复杂格式偶尔跑偏——提示词无法 100% 锁定格式时）；**长指令成本**（每次请求都带长 system prompt 的 token 成本）；**模型根本不具备的模式**（few-shot 示范了但模型学不会——提示词不能教模型做它权重里没有的事）。

判断口诀：**"说得清 + 稳定复现" → Prompt；"说得清但偶尔跑偏" → few-shot 加强或评估微调；"说不清/学不会" → 换方案**。

## 2. few-shot 与提示缓存的成本优势

Prompt 路径的经济性在 2026 年显著上升：**提示缓存（prompt caching）**让重复前缀的缓存读成本降到约输入的 10%——"系统提示 + 固定示例"这种稳定前缀，在多轮会话与批量请求下几乎免费。

```text
方案对比（每请求成本视角）：
Prompt + 缓存：首次全价，后续缓存读 ≈ 10% 输入成本
微调模型：    训练成本（一次性）+ 推理无 prompt 冗余（权重内化行为）
```

工程含义：**行为缺口且 prompt 前缀稳定** → Prompt + 缓存可能是比微调更便宜的方案（微调有训练成本 + 托管成本 + 重训周期）；**行为缺口且每次指令都变**（无法缓存）→ 微调的"行为内化"优势显现。成本边界不是"Prompt 便宜"一句话，是**缓存命中率 × 请求量 × 训练摊销**的算术题（09 篇 ROI 细算）。

Prompt 与微调的可组合形态（不是二选一）：**微调管"基座不擅长的格式"，Prompt 管"场景相关的行为"**——微调后的模型仍带 system prompt 做会话级控制（守卫规则、语气微调、临时指令）；**微调 + few-shot 的互补**（微调学不到的边角案例用 few-shot 补，避免为 5% 场景重训）；**Prompt 是微调模型的运行时配置**（需求漂移先改 Prompt 验证，稳定后再决定是否重训）。组合的落点：**微调与 Prompt 是分层不是替代**——微调进权重、Prompt 在运行时，两层各管各的（与 09 篇 form/orchestrate 分层同构）。

## 3. Prompt 失效的信号（切换到微调的判据）

Prompt 路径什么时候算"试过了但失败"，三个可测信号：

1. **一致性不达标**：同一输入多次调用，格式/行为 90% 稳定但关键场景 10% 跑偏（如 JSON 偶发缺字段）——业务容忍度内可接受，容忍度外是微调判据。
2. **指令膨胀**：system prompt 超过 2-3K token 仍不够——每加一条规则就压垮前一条（指令冲突），说明"行为复杂度超出提示词表达力"。
3. **few-shot 无效**：加示例不改善（示例教不会）——模型权重里没有这个模式，提示词无能为力。

判据的量化版本：**用标注集评估 Prompt 方案的命中率**（如格式合规率 95%），业务红线（如 99%）就是切换线——不是"感觉不行"就微调，是指标低于红线才升级（与 07 篇的评估纪律一致）。

## 4. 切换微调前的最后检查

从 Prompt 升级到微调前，过三道检查（防冲动升级）：

1. **RAG 试了吗**：缺口里有没有知识成分？有 → 先加 RAG（03 篇）——很多"Prompt 搞不定"其实是"缺知识"，不是"行为"。
2. **Tools 试了吗**：缺口是"需要动作"吗？要查库/计算/调 API → 工具调用（04 篇），不是微调。
3. **评估基线定了吗**：标注集 + 当前 Prompt 方案的指标——没有基线，微调后无法证明"值了"。

三道检查全过，才进入微调——**升级路径是"Prompt 失败 → 排查缺口类型 → 确认是行为且数据够"三连**，跳过任何一步都是常见翻车点（面试答"怎么判断该微调了"时按这三连答，就是深度）。

## 5. Prompt 失败的深层原因分类

切换微调前先归因，"Prompt 不行"是四个问题的开头：

1. **表达问题**：指令写得不清楚——重写 Prompt 即可，不是微调理由。
2. **容量问题**：提示词表达力不够（格式太复杂、规则冲突）——微调候选。
3. **知识问题**：模型不知道——RAG，不是微调。
4. **能力问题**：模型权重里没有该模式——微调候选，但先验证数据量（07 篇）。

四个归因对应四条路（重写 Prompt / 微调 / RAG / 微调+数据验证）——**归因错误 = 方案错误**，这是"Prompt 失败后怎么办"的标准排查顺序。

## 6. 双向迁移：微调后还能回 Prompt

边界判断不是单向的：**已经微调的模型，需求变化时评估"回退到 Prompt + 缓存"**——微调模型的维护成本（重训 + 评估 + 版本管理）可能高于"基座 + 长 Prompt + 缓存"；新需求只是风格微调时，Prompt 先试的成本远低于重训。**"微调是终态"是错觉**——权重内化的行为在需求漂移时会变成负债，Prompt 的灵活性是资产。生产实践：保留基座模型 + Prompt 配置作为回退路径（与数据库"保留旧版本可回滚"同思路）。评估这个回退的触发信号：**新需求只是风格/语气级变化**（Prompt 可覆盖 → 回退或不动）；**新需求是格式/行为级变化**（Prompt 覆盖不了 → 重训或升级）；**基座升级后微调模型未同步**（微调模型落后于基座能力 → 先评估"基座 + Prompt"是否已够——基座进步有时直接消灭微调需求）。回退不是失败，是成本纪律。

> 🎯 **核心要点**：Prompt 管"说得清且稳定复现"的行为缺口；提示缓存让 Prompt 路径成本大降（缓存读 ≈ 输入 10%）；失效三信号（一致性/指令膨胀/few-shot 无效）用标注集量化判定；升级前查 RAG/Tools/基线三连；微调不是终态，保留 Prompt 回退路径。
