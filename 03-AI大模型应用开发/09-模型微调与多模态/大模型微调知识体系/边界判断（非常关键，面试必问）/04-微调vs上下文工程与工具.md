# 微调 vs 上下文工程与工具

> 长上下文时代的边界迁移——上下文放得下的用上下文、需要动作的用工具，微调的领地进一步收缩

## 1. 长上下文时代的边界迁移

2026 年的模型上下文窗口已到百万 token 级（Claude 5 系、Gemini 系等）——这直接改写"微调 vs 上下文"的边界：**过去需要微调内化的"知识"，现在可以直接塞进上下文**。

边界迁移的三条线：

1. **知识量 < 上下文容量** → 上下文工程（system prompt + 资料）即可，无需微调——文档、FAQ、产品手册直接进上下文。
2. **知识量 > 上下文容量但可检索** → RAG（检索压缩进上下文的子集）——上下文工程是"全量塞"，RAG 是"检索塞"。
3. **知识量巨大且高频** → 微调内化才值得评估——上下文/RAG 都放不下或检索成本过高时。

判断口诀：**"放得下" → 上下文；"放不下但找得到" → RAG；"又大又高频" → 微调候选**。长上下文没有消灭微调，但把微调的有效边界推向了"更大、更高频、更稳定"的数据。

上下文工程的三个工程细节（决定它是否真的替代微调）：**检索辅助的上下文组装**（长文档塞进上下文前先检索关键片段——"塞全量"是浪费，组装质量决定效果）；**提示缓存的前缀设计**（稳定前缀（身份/规则/示例）放最前，变化部分（本次查询）放最后——缓存命中最大化，成本降一个量级）；**注意力稀释验证**（上下文超长时用标注集验证关键信息是否仍被正确使用——"迷失在中间"是真实风险，实测发现才敢上长上下文方案）。

## 2. 上下文工程 vs 微调的成本对比

上下文路径的三大成本项：**输入 token 成本**（每次请求带全量上下文——提示缓存把稳定前缀降到约 10% 输入成本）；**延迟**（长上下文的首 token 延迟上升——百万 token 上下文的处理时间不可忽略）；**注意力稀释**（上下文过长时模型对关键信息的注意力下降——"迷失在中间"现象）。

微调路径的成本项：**训练成本**（一次性，LoRA 约 $0.8-3/百万训练 token）；**托管成本**（微调模型长期部署）；**重训周期**（基座升级/需求变化要重训）。

```text
决策视角：
高频稳定行为 + 上下文重复 → 微调内化（省每请求 token）
低频多变上下文           → 上下文工程（灵活，无训练成本）
折中                     → 微调管稳定行为 + 上下文管变化部分（混合）
```

量化判据：**请求量 × 冗余上下文 token × 单价 vs 训练摊销 + 托管增量**——量大且上下文冗余多，微调内化的经济性浮现（09 篇 ROI 细算）。

## 3. 工具调用：动作型缺口的正解

另一条被低估的边界：**缺口是"需要动作"时（查数据库、调 API、做计算、写文件），正解是工具调用（Function Calling/工具协议），不是微调**。

工具调用的边界：**模型不需要"学会做"动作**（权重里不需要有 SQL/API 知识），只需要"学会调用"——工具层负责执行，模型只负责决策与参数生成。这与微调的本质区别：**微调教模型"会做"，工具教模型"会用"**——后者成本低一个量级且能力边界随工具扩展。

判断：**"需要执行动作" → Tools（决策顺序第 3 步）；"动作本身要学（如领域计算规则）" → 微调候选**。工具 + 微调的常见组合：微调管"何时调用哪个工具"的决策模式（行为），工具管执行（能力）——行为与能力的分离是 2026 年 Agent 架构的核心思路。

工具调用的工程边界（避免"工具万能论"）：**工具描述质量决定调用准确率**（模型靠描述理解工具——描述不清晰的工具永远调不对，先修描述再考虑微调）；**参数生成是调用准确率的瓶颈**（模型参数幻觉（编造不存在的 ID）——校验层（schema 验证）兜底，微调只在该场景高频时入场）；**工具数量与选择复杂度**（几十个工具时模型选择能力下降——工具分层/命名规范优先，微调候选在后）。落点：**工具路径的多数问题靠工程修（描述/校验/分层），微调只在"决策模式稳定且 Prompt 修不动"时入场**——与 02 篇"归因先行"同纪律。

## 4. 上下文放不下 vs 微调学不会

两个方向的"无效尝试"要能识别：

**上下文放不下的场景**：知识总量超窗口（几十万文档）且无法有效检索——硬塞上下文会爆窗或稀释；这种场景 RAG 是正解（检索子集），微调是次解（高频知识内化 + 低频靠检索）——**"放不下"不是微调的理由，是 RAG 的理由**。

**微调学不会的场景**：行为需要"外部事实的实时判断"（如按最新法规判断）——微调内化的是训练时点的法规，实时判断仍要靠检索；**微调学不会"需要实时输入的判断"，只能学会"固定模式"**——区分"模式"（可微调）与"事实"（不可微调）是边界判断的精细活。

## 5. 2026 边界速查表

| 场景 | 首选 | 微调时机 |
|------|------|---------|
| 知识 < 上下文 | 上下文工程 | 不微调 |
| 知识 > 上下文、可检索 | RAG | 高频子集内化 |
| 需要动作 | 工具调用 | 调用决策模式 |
| 行为固定（格式/风格） | Prompt | Prompt 失败后 |
| 行为复杂 + 数据 1k+ | PEFT | 直接候选 |

速查表的用法：**每一行先走首选，首选失败的"缺口类型"决定微调是否入场**——上下文/RAG/Tools 三个先手依次失效后，微调的候选集已经缩到"固定行为模式"一个方向，判断成本大降。

> 🎯 **核心要点**：长上下文把微调边界推向"更大/更高频/更稳定"的数据（放得下→上下文、找得到→RAG、又大又高频→微调）；工具调用管动作型缺口（教"会用"而非"会做"）；"放不下"是 RAG 的理由不是微调的理由；微调只能学固定模式、学不会实时事实判断；成本判据是"冗余上下文 token 账"。
