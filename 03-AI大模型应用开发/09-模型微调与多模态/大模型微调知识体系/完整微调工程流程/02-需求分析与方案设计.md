# 需求分析与方案设计

> 微调工程的第一阶段：把业务诉求翻译成可测量的任务定义，指标先行、方案四选（底座/方法/框架/预算）——方案错了，执行越勤奋损失越大

## 1. 任务定义：把"更专业"翻译成可测量

需求分析的产出是一份**任务定义文档**，三要素：

**任务类型**：分类（意图识别/情感判断）？生成（摘要/改写/对话）？推理（数学/代码/多步逻辑）？工具调用（Agent 任务）？不同类型决定后续所有选择——指标、数据形态、方法都随任务类型走。

**行为规范**：具体到可判定的规则——"JSON 输出且 99% 可解析""客服话术符合 20 条规范""拒答边界：不讨论竞品价格"。规范条目化的意义：它直接变成评估集的设计依据（规范 = 评估维度）。

**边界与约束**：数据合规约束（客户数据可否入训练？见 `../数据集体系（非常重要）/09-数据版本管理与合规治理.md`）、延迟与成本预算、部署环境（本地/云/边缘）。

**先做边界判断**：需求分析的第一步不是设计微调，而是回答"该不该微调"——知识缺口走 RAG、行为缺口先 Prompt（决策框架在 `../边界判断（非常关键，面试必问）/01-微调决策全景与判断框架.md`）。需求分析阶段就否决"不该微调的需求"，是成本最低的止损。

## 2. 指标先行：先定考卷再训练

任务定义的同时定义**评估指标**——指标决定"好坏怎么算"，是后续评估集、验收门禁的依据：

| 任务类型 | 指标 |
|---------|------|
| 分类 | 准确率、F1（类别不平衡时） |
| 生成 | BLEU/ROUGE/BERTScore + LLM judge 质量分 |
| 推理 | Pass@k、答案正确率（可验证） |
| 工具调用 | 工具选择准确率、参数 JSON 解析率 |
| 结构化输出 | 格式解析率、字段准确率 |
| 综合助手 | LLM judge（MT-Bench 风格）+ 人工抽样 |

指标先行的两个硬要求：**指标必须可计算**（评估脚本在训练前就写好并跑通）；**指标必须覆盖核心需求**（业务诉求是"客服语气好"，指标里就要有语气维度，不能只测格式）。

指标与业务的对账：每个指标都要能回答"它对应业务上的什么价值"——JSON 解析率对应"下游系统的对接成本"、话术命中率对应"客服质检通过率"、judge 质量分对应"用户主观体验"。对不上账的指标是"刷分指标"（数字好看但业务不认可）——验收时业务方不认账，往往就是指标先行阶段漏了对账。

## 3. 方案四选：底座、方法、框架、预算

**选底座**（三判据见 `../基础概念/02-大模型训练三阶段范式.md` 04 节）：能力匹配（推理需求选 Reasoning 类、通用对话选 Chat 类）、许可协议（商用条款）、生态工具链。2026 常见选型：通用业务 Qwen/Llama 系、推理 DeepSeek/Qwen Reasoning、垂直领域看社区生态。

**选方法**：行为格式类 → SFT；偏好排序类 → SFT + DPO；推理类 → 考虑 GRPO/RLVR（方法全景与选型在 `../基础概念/07-微调方法全景图谱.md`，能否微调的决策在边界判断体系）。2026 企业默认：**QLoRA SFT → DPO → 评估**。

**选框架**：四大框架（Unsloth/TRL/LLaMA-Factory/Axolotl）的实测对比与决策矩阵在 04 篇——快速原型用 Unsloth、对齐训练用 TRL、可复现生产用 Axolotl、WebUI 探索用 LLaMA-Factory。

**算预算**：成本 = GPU 时长 × 单价。GPU 时长的粗估公式：样本数 × epoch × 平均 token 数 ÷ 吞吐（tokens/s，04 篇框架实测参考）——7B QLoRA 单卡吞吐约 1500-4000 tokens/s，1 万条 × 2 epoch × 500 token ≈ 1000 万 token ≈ 1-2 小时。2026 量级参考：QLoRA 微调 7B-14B 单卡 RTX 5090 约 6-10 小时；70B QLoRA 约 36 小时（RTX 6000 Pro 级）；全量微调 70B 需多卡集群约 5 天。预算评估要含**重训余量**（数据迭代会反复重训，第一次预算 ×2-3 是常态）。

**技术预检**：方案落地前花半天做底座能力验证——拿底座（含目标 Prompt）跑 20-50 条代表性样本，人工看输出上限：底座连"方向都不对"的任务（如不会结构化输出），微调也教不会——方案要回炉（换底座或降需求预期）。

## 4. 风险评估：最贵的错误提前发现

方案设计阶段的三个风险评估：

**数据风险**：数据是否可得（种子集谁能写、标注人力够不够）、质量能否达标（预检：先采样 100 条人工看质量，别等全集做完才发现方向错）。**技术风险**：底座能力能否满足任务（先拿底座跑 20 条样本看上限——底座做不到的，微调大概率也做不到）；方法选择是否超出团队能力（GRPO 需要算力与可验证奖励，小团队慎选）；底座与框架兼容性（新发布的模型在 Unsloth 等框架的内核支持可能滞后，查框架支持矩阵再定底座）。**合规风险**：数据许可、客户数据边界、EU AI Act 要求（2026-08 已执法）——合规不通过，技术全白做。

风险清单的产出是**决策记录**（选了什么、为什么、放弃什么、风险接受谁批）——这是方案文档的一部分，也是 09 篇审计产物的起点。

## 5. 方案文档的结构

一份合格的方案文档（一到两页）包含：任务定义（类型 + 行为规范 + 边界）、指标定义（可计算 + 覆盖需求）、底座/方法/框架选型及理由、成本预算（含重训余量）、风险清单与决策记录、里程碑（阶段划分 + 每阶段验收点）。

**方案文档不是给领导看的，是给三个月后的自己看的**——迭代到第 5 轮重训时，靠它回答"当时为什么这么选、现在要不要改"。文档的更新纪律：**决策变了就改文档并记变更原因**（方案文档是活文档），与数据 manifest（05 篇）、训练配置（06 篇）一样版本化——"方案漂移"（实际做的与文档写的脱节）是迭代后期排障难的第一原因。

> 🎯 **核心要点**：需求分析 = 任务定义（类型/规范/边界）+ 指标先行（可计算 + 覆盖需求）+ 方案四选（底座三判据/方法全景/框架矩阵/预算含重训余量）+ 风险清单（数据/技术/合规）；先做边界判断（该不该微调）是第一阶段的第一动作；方案文档是迭代的锚点，不是形式。
