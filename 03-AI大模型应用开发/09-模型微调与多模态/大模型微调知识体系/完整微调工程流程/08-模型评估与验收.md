# 模型评估与验收

> 流程第 8 阶段：训练产物过评估矩阵、对照基线走验收门禁——"训得好不好"不是感觉，是对比基线的门禁决策

## 1. 评估矩阵：四维度全检

验收不是跑一个指标，而是四维度评估矩阵（与 03 篇的基线报告同构，保证可比）：

**任务指标**（评估集核心）：03 篇预设的指标（分类 F1、生成 BLEU/ROUGE、JSON 解析率等）——测"任务达成度"。

**通用能力回测**：标准基准（MMLU 类）+ 通用对话样本——测"有没有遗忘"（灾难性遗忘检测，`../基础概念/09-评估基础损失曲线与过拟合.md` 03 节）；**只测任务不测通用 = 残缺评估**。

**LLM judge 评分**：领域 LLM judge 按评分指令打分（任务指标之外的软质量：语气、完整性、安全性）——judge 配置与可信保证在 `../数据集体系（非常重要）/07-数据质量评估与筛选.md` 03 节（与人工对齐、定期重校准）。

**人工抽检**：50-100 条双盲对比（微调模型 vs 基线 vs 底座）——**judge 与指标都可能有系统偏差，人工是最终裁判**（尤其语气/风格类需求，人工感知不可替代）。

## 2. 评估工具链

- **标准基准**：`lm-evaluation-harness`（EleutherAI）——MMLU 等标准基准的行业标准工具；支持通过本地 OpenAI 兼容端点评估已部署模型（`lm_eval --model local-completions --model_args model=finance,base_url=http://localhost:8000/v1/completions,tokenizer=<base> --tasks mmlu`——**评估走过的服务路径**，验证的是"上线后的真实行为"而非训练时的内存态）。
- **任务评估**：自写脚本（评估集 + 指标计算）——03 篇基线阶段已就绪，训练后直接复用。
- **LLM judge**：judge prompt 版本化管理（与评估集同级治理）；judge 输出结构化 JSON（维度分 + 理由）。
- **注意**：**评估脚本环境要 lock、评估配置（温度/max_tokens）固定**——评估漂移会让两轮训练不可比（03 篇 05 节）。

**评估报告格式**（每轮训练必产）：评估矩阵四维度分数表（含基线对照）、门禁项逐条判定（达标/不达标 + 数据）、结论（上线/回炉 + 理由）、附录（评估脚本版本、评估配置、日期）——报告就是验收记录的存档形态，与训练日志、数据 manifest 一起构成"这轮训练的完整档案"（09 篇审计链路的组成）。

## 3. 对比什么：三线对照

验收的核心是对比，标准做法是**三线对照**：底座（裸跑）、底座 + Prompt（Prompt 基线，03 篇已测）、微调模型。微调的增量 = 微调模型 vs Prompt 基线（不是 vs 底座裸跑）——**Prompt 能解决的部分不算微调功劳**，这样对比才能回答"微调值不值"（边界判断体系 02 篇：先试 Prompt 再微调的决策在验收时兑现为对比基准）。

一个 2026 实测警示（评估通过服务路径的案例）：提取的 LoRA 在 mmlu_econometrics 上 0.4561，**没有超过底座 0.4825**，而完整全量微调 0.5526 超过了——**LoRA 提取/合并的版本差异、评估路径差异都会改变结论**，验收必须用"将要上线的产物"（合并后的模型/服务路径）来测，而不是训练时的中间产物。

## 4. 验收门禁决策

按 03 篇预设的门禁逐条过（权重与一票否决项写清楚）：

| 门禁项 | 标准（参考） | 决策 |
|--------|-------------|------|
| 自定义评估集 | 相对 Prompt 基线提升 >3% | 不达标 = 微调失败，排查（数据/训练） |
| 标准基准回归 | 相对基线回归 <1% | 超限 = 遗忘信号，一票否决或降 epoch 重训 |
| 业务核心指标 | 需求文档指标达标 | 不达标 = 需求未满足 |
| 人工双盲 | 50-100 条对比胜出 | 不胜 = 感知质量未提升 |

**门禁结果只有两种：上线 / 回炉**。回炉方向：指标没提升 → 查数据（量/质量）与训练（epoch/lr）；基准回归 → 降 epoch、加通用数据混入（`../数据集体系（非常重要）/08-数据平衡与多样性.md` 05 节）；人工不认可 → 查需求理解（指标与需求的偏差）。**验收报告归档**（每项分数 + 决策 + 理由）——它就是 09 篇上线记录与审计产物的一部分。

**回炉前的分层诊断**（不达标别盲目重训）：先确认"是模型问题还是评估问题"——用基线重跑同一评估脚本，基线分数与基线报告不一致 = 评估环境漂移，先修评估；再分维度看"是能力问题还是分布问题"——单类任务差 = 该类数据不足（补数据）、全类都差 = 训练问题（epoch/lr）、边界样本差 = 覆盖缺口（补边界样本）。**跳过诊断直接重训是回炉环节最大的时间浪费**。

## 5. 回归集：迭代的守门员

验收之后，评估集升级为**回归集**：每次后续迭代（重训/数据增补）都必须全量重跑——**回归失败 = 本次迭代引入回归 = 先修再上线**（`../数据集体系（非常重要）/07-数据质量评估与筛选.md` 05 节）。

回归集的管理：版本化（增补走评审，防止注水）、跨时段（新收集的线上失败样本定期补入——但补入前先验证训练集不含同源样本）。回归集规模 300-800 条——跑一轮回归的算力与时间要计入迭代成本，规模过大反而拖慢迭代节奏。

门禁判定的输入统一用"服务路径评估"的结果（评估走部署路径的原则），不用训练内存态——**评估与上线一致是门禁可信的前提**。

评估的最终检验标准（2026 共识）：**评估结论与线上效果一致**——评估集说"提升了"，线上灰度（09 篇）却显示没提升，说明评估集与真实请求分布错位（`../数据集体系（非常重要）/08-数据平衡与多样性.md` 06 节），回头补评估集的分布对齐。

> 🎯 **核心要点**：评估矩阵四维度（任务指标/通用回测/judge/人工双盲）；三线对照（底座 vs Prompt 基线 vs 微调）——微调增量是对 Prompt 基线的增量；用"上线产物"评估（合并后模型/服务路径），LoRA 提取版本会改变结论；门禁决策只有上线/回炉两种，验收报告归档；评估集升级为回归集守门每次迭代，评估与线上不一致时先补评估集分布对齐。
