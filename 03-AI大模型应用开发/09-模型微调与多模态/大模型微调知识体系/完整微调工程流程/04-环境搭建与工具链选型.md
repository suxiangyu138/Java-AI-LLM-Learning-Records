# 环境搭建与工具链选型

> 训练开始前的基建：四大框架的定位与实测、2026 组合模式、GPU 硬件选型、环境可复现——工具选错，效率差一个量级

## 1. 四大框架定位（2026 实测）

2026 年开源微调框架的四个主力（实测基准：LLaMA 3.1 8B + LoRA r=16 + 4-bit + A100 80GB）：

| 框架 | Tokens/s | 显存 | 定位 | 适合场景 |
|------|:---:|:---:|------|---------|
| Unsloth | ~4,200（2.8x） | ~8GB | 速度与省显存之王 | 单卡原型、消费级显卡 |
| Axolotl | ~1,500 | ~16GB | YAML 可复现生产 | 生产配置、多架构 |
| LLaMA-Factory | ~1,480 | ~16GB | 模型支持最广 + WebUI | 图形化探索、快速试错 |
| TRL | ~1,450 | ~18GB | HF 官方对齐训练 | DPO/GRPO/RLHF 对齐 |

**Unsloth**：自研 Triton 内核重写了 Flash Attention、交叉熵损失、LoRA——速度 2-5 倍（MoE 模型最高 12 倍）、省显存约 35%。2026 年 2 月版本新增 MoE 训练、embedding 微调、FP8 训练。短板：自定义内核滞后新模型架构（几天到几周）、多 GPU 支持弱、Pro 订阅模式有争议（免费版已够原型用）。

**TRL**：HuggingFace 官方库，SFT/DPO/GRPO/KTO/ORPO/PPO 全对齐方法——**对齐训练的事实标准**，与 HF 生态（datasets/tokenizers）天然集成。

**LLaMA-Factory**：star 最多（68.4K），模型支持最广，带 LlamaBoard WebUI——图形化选模型、配参数、起训练、看曲线，**非算法背景成员（数据同学/业务同学）也能自助跑微调**，团队协作价值大。短板：文档不一致、配置项过多（"太多旋钮"）、发版节奏放缓。

**Axolotl**：YAML 配置驱动，生产可复现的"安静工作马"——配置可以进 git、可审计；学习曲线中等，YAML 可能上百行。

## 2. 2026 组合模式：框架不是单选

2026 年的共识是**框架互补组合**，三个已验证模式：

**Unsloth + TRL（轻量对齐）**：Unsloth 做 SFT 加速（`FastLanguageModel` 加载 + TRL 的 SFTTrainer），DPO 用 TRL 的 DPOTrainer（配 `ref_model=None` 省显存）——2026 标准配方"QLoRA SFT → DPO → 评估"的标准实现。

**LLaMA-Factory + Unsloth（编排 + 加速）**：LLaMA-Factory 当训练编排器、Unsloth 当 SFT 加速后端（实测 Qwen3-8B 提速 ~2 倍、省显存 ~70%）；DPO 阶段回退 LLaMA-Factory 原生 TRL 后端（Unsloth 对 DPO/KTO 加速不可靠）。注意：LLaMA-Factory 的 Python API 在演进，**生产优先用 CLI**。

**Axolotl + Unsloth（可复现 + 加速）**：Axolotl 管配置与复现，Unsloth 管加速——生产流水线的稳健组合。

**切换时机**：原型阶段（速度优先）用 Unsloth；规模化/生产（稳定优先）切 TRL/LLaMA-Factory——"快速原型，规模后切"是 2026 通用建议。

**框架选择的非技术因素**：社区活跃度（bug 修复速度与文档更新）、团队熟悉度（切换框架的学习成本）、生态兼容（数据工具链、评估工具链是否对接顺滑）——技术指标只决定"上限"，非技术因素决定"能不能落地"。切换成本要算进选型账：框架迁移（数据格式、配置、脚本）一次投入数人天，**选型是低频高成本决策，值得花一个下午做冒烟对比**。评估框架的标准动作：**拿自己的数据跑一个 50 步冒烟**（对比启动难度、配置复杂度、日志可读性）——别信文档宣传，信自己的冒烟。

## 3. GPU 硬件选型

按模型规模与预算的 2026 选型：

| 场景 | 硬件 | 说明 |
|------|------|------|
| 7B-14B QLoRA 单卡 | RTX 4090（24GB）/5090（32GB） | 性价比之王，6-10 小时一轮 |
| 7B 极限省显存 | RTX 3080（10GB） | 仅 Unsloth 可行（其他框架需 24GB） |
| 32B+ QLoRA | RTX 6000 Pro 级（48GB+） | 70B QLoRA 约 36 小时 |
| 全量微调 7B+ | 多卡 A100/H100 集群 | 70B 全量约 5 天 |
| MoE 大模型 | DGX Spark 类（128GB 统一内存） | NVFP4 量化训练/服务 30B-120B |
| Mac 统一内存 | M3 Ultra（192GB） | 70B 可跑（MLX 生态） |

选型逻辑：**先算显存账**（`../基础概念/03-Transformer与参数基础.md` 05 节：推理 1 份、LoRA ~1.1 份、全量 4-5 份），再对照预算——QLoRA 是单卡微调的事实标准，全量微调只在数据量 50k+ 或预算充足时考虑（阈值见边界判断 06 篇）。

采购策略补充：**自购卡做原型、按需云 GPU 做生产训练**是 2026 年常见组合——生产训练的 GPU 需求波动大（重训/扩容），按需云避免闲置成本；自购卡维护简单（无需跨机房传数据）。预算敏感团队先用 14B 验证方案，投产再升规模（小模型验证、大模型投产）。

## 4. 环境可复现：从"能跑"到"能重跑"

环境搭建的验收标准不是"训练能跑"，而是**"三个月后能原样重跑"**：

- **Python 环境 lock**：`requirements.txt` 精确版本（transformers、peft、trl、bitsandbytes 全 pin 版本——transformers 小版本升级都可能导致行为漂移）。
- **CUDA 栈一致性**：PyTorch/CUDA/cuDNN 版本记录在案（评估脚本环境漂移会让基线分数偏移，见 03 篇第 5 节）。
- **镜像化**：Docker 镜像（含框架版本 + 内核依赖）是生产标准——团队共享镜像，新机器分钟级就绪。
- **模型下载治理**：底座权重与 tokenizer 固定版本（模型文件 hash 记录），走内部制品库（`03-AI大模型应用开发/` 的 HuggingFace 体系有 hf-mirror/hfd 实践）。

环境搭建检查清单：GPU 驱动与显存确认（`nvidia-smi`）、框架版本一致性（`pip show`）、模型加载冒烟（加载底座跑一次生成）、数据路径挂载、日志目录创建——**启动前检查清单**（06 篇）的前置部分。

**环境验证的实操顺序**：先跑最便宜的验证（`nvidia-smi` + `torch.cuda.is_available()`）→ 再跑框架冒烟（加载底座 + 一次前向）→ 最后跑 50 步训练冒烟（数据 + 训练器全链路）——验证成本递增，每级通过才进下一级；**任何一步失败先查环境版本矩阵**（Python/transformers/peft/trl/bitsandbytes 的兼容组合——2026 年大量"莫名报错"的根因是版本矩阵错位，环境文件里写明兼容组合是排障第一线索）。

**环境常见问题速查**：模型下载失败/断点续传（配 hf-mirror 或 hfd 多线程工具，见 `03-AI大模型应用开发/02-大模型基础与Prompt工程/HuggingFace/` 体系）；bitsandbytes 与 CUDA 版本不匹配（4-bit 加载报错的第一嫌疑——按官方矩阵重装）；显存被其他进程占满（`nvidia-smi` 查 PID，训练前确认显存空闲）；磁盘空间不足（底座 + checkpoint + 日志总量预算：7B 底座约 15GB、每 checkpoint GB 级，启动前 `df -h` 确认）——这些低级问题占环境排障的 80%，全部可以靠"启动前检查清单"（06 篇）提前拦截。

**环境可复现的终极验收**：从零重建——在新机器（或干净容器）上按环境文档跑 50 步冒烟训练，能通过才算环境文档合格。这个验收每季度或大版本升级后做一次，防"文档说的环境"与"实际跑的环境"漂移（环境漂移是"上周还能跑、这周报错"的第一来源）。

> 🎯 **核心要点**：四大框架各司其职——Unsloth 速度（2.8x/省 35%）、TRL 对齐（DPO/GRPO 标准）、LLaMA-Factory 广度（WebUI）、Axolotl 可复现（YAML）；2026 组合模式 = Unsloth 原型 + TRL 对齐 + 生产编排器；硬件先算显存账（QLoRA 单卡 7B-14B 是甜点）；环境可复现 = 版本 lock + 镜像化 + 模型 hash——"能重跑"是环境搭建的验收标准。
