# 数据准备与训练集构建

> 流程第 5 阶段：把数据集体系的方法论落地为可执行流水线——种子集→合成→清洗→去重→格式→切分→manifest，产出"可进训练器的训练集版本"

## 1. 数据流水线的工程落地

数据准备阶段要交付的不是"一份数据"，而是一条**可复现的数据流水线**（数据集体系的完整方法论在此执行）：

```text
种子集（人工 150-200 条）→ 合成扩写 → 清洗（格式/内容/完整性）
→ 去重（三级：精确→模糊→语义）→ 质量评估（红旗清单 + LLM judge）
→ 格式统一（messages）→ 平衡配比 → 训练/验证切分 → manifest + SHA256
```

每一步的细节都在 `../数据集体系（非常重要）/`（03 篇获取、04 篇清洗、05 篇去重、07 篇评估、08 篇平衡），本阶段的任务是**把它们串成脚本流水线**：每步有输入、有脚本、有输出统计，全链路可一键重跑。**流水线的价值在可重跑**——数据迭代（09 篇的周更闭环）每次都要重跑流水线，手工操作一次是实验，两次是事故。

流水线的工程约定：**每步的输入输出都是中间产物文件**（带版本与统计），步骤之间不共享内存状态（断了从产物续跑，不从头来）；每步产出一份统计 JSON（处理量/删除量/原因分布），汇总进 manifest；流水线脚本进 git（数据迭代 = 跑流水线的新版本，不是手改数据）——**数据流水线的验收标准：任何人拿到 manifest + 脚本 + 原始数据，能复现出完全相同的训练集**。

## 2. 切分：训练/验证/评估的关系

切分纪律（与评估集的关系是新手最常搞混的）：

- **训练集**：流水线产出主体，进训练器。
- **验证集**：训练中监控 eval loss 用——从训练数据同分布切出（90/10），**必须与训练集严格隔离**（去重环节后切分，防止同源样本跨集）。验证集规模参考：500-2000 条（太小 eval loss 噪声大、波动剧烈无法判断过拟合拐点；太大浪费训练显存与时间——eval 步也要吃算力），数量与类别分布要和训练集一致（类别比例失衡的验证集测不出真实的过拟合信号）。
- **金标评估集**：03 阶段已建，**独立于训练/验证**——它是"考试卷"，训练/验证是"作业本"，三者永不相交。

切分时机有讲究：**先去重再切分**——先切分后去重，验证集可能混入训练集同源样本（eval loss 假象，`../基础概念/09-评估基础损失曲线与过拟合.md` 02 节）；**污染检测在切分后跑**——训练/验证集与 benchmark 的重叠检查（`../数据集体系（非常重要）/05-数据去重与污染检测.md` 05 节），命中即剔除。

## 3. manifest：数据的身份证

数据准备阶段的最终产物是**数据 manifest**（随数据一起进版本管理，`../数据集体系（非常重要）/09-数据版本管理与合规治理.md` 02 节）：数据集 ID + 版本号 + 时间戳（如 `cust-sft-v3-20260810`）、SHA256、行数、schema 版本、来源构成（各来源/合成批次占比）、清洗统计（各环节删减量）、judge 分数分布、类别分布、负责人与变更摘要。

manifest 的工程价值在训练时兑现：**训练配置里记录数据 manifest 版本**——训练日志与数据版本绑定，验收/排障时"这版模型用了哪版数据"一秒可查。这也是"每一步有产物"原则在数据阶段的落地。

manifest 的示例结构：

```json
{
  "dataset_id": "cust-sft-v3-20260810",
  "sha256": "9f2c...",
  "rows": 12480,
  "schema_version": "messages-v1",
  "sources": {"seed": 200, "synthetic": 9800, "public": 2480},
  "dedup_stats": {"exact": 320, "minhash": 1150, "semantic": 780},
  "judge_avg": 4.2, "categories": {"qa": 0.5, "tool": 0.3, "other": 0.2},
  "owner": "zhang", "changelog": "v2 基础上补 2000 条工具调用失败案例"
}
```

这个文件是数据阶段的"产物身份证"——训练配置引用它，验收报告引用它，审计（`../数据集体系（非常重要）/09-数据版本管理与合规治理.md`）也引用它。

## 4. 训练器对接：格式与字段

训练集最终要能被训练器直接消费（以 TRL SFTTrainer 为例的对接要点，其他框架同理）：

- **消息形态**：`{"messages": [...]}` 数组（统一 messages 格式，`../数据集体系（非常重要）/06-数据格式与转换.md`），训练器内部走 `apply_chat_template` 渲染。
- **字段约定**：`dataset_text_field`（打包成文本时的字段）与 `max_seq_length`、`packing` 开关的配合——长文本任务开 packing（`../基础概念/06-训练循环Epoch-Batch-Step.md` 06 节）。
- **掩码**：框架默认 user 位置自动掩码（label=-100）；多轮任务按策略选 final-turn only 或 all turns（`../基础概念/08-指令数据与对话格式基础.md` 04 节）。
- **偏好数据**：DPO 用 `{"prompt", "chosen", "rejected"}` 字段（`../数据集体系（非常重要）/02-数据集类型全景.md` 03 节）。

**对接验证**：正式训练前跑一个 50 步的"冒烟训练"（极小步数）——验证数据加载、模板渲染、掩码、长度切分全链路无报错，**别等正式训练跑 2 小时才发现数据字段错了**。冒烟训练同时检查三件事：样本条数（数据全量加载）、token 长度分布（截断率是否异常高）、掩码生效（user 位置 loss 贡献为 0）——三个数字都对，数据对接才算通过。

## 5. 数据质量的最后一道人工检查

流水线自动化之外，训练前留最后一道**人工抽检**：随机 50-100 条——看渲染后的文本（`apply_chat_template` 输出）是否符合预期（角色、特殊 token、结束标记）、回答质量是否达标、类别分布是否合理。自动化流水线查"规则"，人工抽检查"感觉"——**规则查不出的"不对劲"（语气、内容、语义），人一眼能看出来**。这道检查也是数据质量门禁的收官（07 篇的三层评估结构的人工层）。

抽检的反馈闭环：抽检发现的问题分类处理——"规则可查的"（如模板残留）回补流水线规则，"规则查不出的"（如语义偏差）进人工评审清单——**每轮抽检都在补流水线的盲区**，流水线质量随迭代次数的增长而收敛。

> 🎯 **核心要点**：数据准备 = 把数据集体系方法论落地为可重跑流水线（种子→合成→清洗→去重→评估→格式→切分）；切分纪律 = 先去重后切分 + 金标评估集独立 + 切分后跑污染检测；manifest（版本 + 统计 + 负责人）绑定训练配置；训练器对接四要点（messages 形态/字段/掩码/冒烟验证）；收官人工抽检 50-100 条——"规则查规则，人查感觉"。
