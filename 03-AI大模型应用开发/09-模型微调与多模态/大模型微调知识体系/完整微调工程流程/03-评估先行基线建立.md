# 评估先行：基线建立

> eval-first 纪律的落地：训练开始前完成三件事——金标评估集、底座基线报告、验收标准预设——没有基线的微调无法证明任何提升

## 1. eval-first：为什么评估必须先于训练

微调工程最常见的失败模式是"训完才发现不知道好不好"——根因是评估后置。eval-first（评估先行）要求：**训练开始前，评估体系必须完整就绪**。三个理由：

**门禁需要对比对象**：验收是"对比基线的提升"——底座基线（微调前的表现）必须在训练前测好，训练后才有参照系。先训练后测基线 = 基线已经污染（或者根本没法测）。

**评估集需要人工精力**：金标评估集要人工编写/审核（数百条），这项工作与训练无依赖，应该先做——它同时是数据质量的"度量衡"（`../数据集体系（非常重要）/01-数据角色与质量第一性原理.md` 04 节），数据建设期就发挥价值。

**早期暴露问题**：评估脚本跑通 = 指标可计算 = 训练后立刻能验收；评估脚本写不出来 = 需求定义有问题，趁早改。

## 2. 金标评估集的构建

评估集三原则（`../基础概念/09-评估基础损失曲线与过拟合.md` 06 节）：严格隔离（与训练集零重叠）、跨时段采样（时间靠后的样本做验证）、困难样本分层（长尾/边界/对抗样本都要有）。工程落地三步：

**从需求文档生成**：任务定义里的行为规范直接变成评估维度——"JSON 格式可解析"就是一条评估维度，"拒答边界"是另一条。每条规范配 10-20 条测试样本。

**数量与结构**：每类任务 100-200 条，总集 300-800 条（金标，人工编写或人工审核）。结构：`{"id", "prompt", "reference", "evaluation_instructions"}`——reference 是参考答案或判定标准，evaluation_instructions 是给评测器（LLM judge）的评分指令。

**评估集 = 版本化资产**：评估集要进版本管理（与数据同等待遇），**评估集变更 = 验收标准变更**——评估集被"注水"（加简单样本）会让门禁失真，所以评估集的增补要像改需求一样走评审。

**评估集的维护节奏**：需求演进（新增任务类型/行为规范变更）时评估集同步增补；线上失败案例回流时"先补评估集再补训练集"（`../完整微调工程流程/09-导出部署与上线运维.md` 05 节）；每次评估集变更记录变更摘要（加了多少、为什么、影响哪些维度）——评估集的历史变更本身就是需求的演进史。

## 3. 底座基线评估

训练前对底座（及底座 + Prompt 组合）跑完整评估，产出**基线报告**：

**测什么**：评估集全量 + 标准基准抽样（MMLU 类通用能力，用于回归检测）。**怎么测**：推理脚本与最终验收同一套（保证可比性）；Prompt 也要测（底座 + 任务 Prompt vs 底座裸跑——记录 Prompt 本身的贡献，后续微调效果是"相对 Prompt 基线的增量"）。**记录什么**：逐项指标分数、评估配置（温度、max_tokens、评估脚本版本）、日期与模型版本。

基线报告的三重用途：**验收参照**（门禁对比对象）；**预期管理**（底座 60 分，微调目标是 65+，不是 99——**微调只能改进底座已有的能力方向**）；**决策依据**（基线过低 = 底座选错，回到方案设计）。

基线报告的字段结构（与验收报告同构，保证可比）：模型版本与 Prompt 版本、评估集版本、逐维度分数（任务指标/通用基准/judge/人工抽检）、评估配置（温度/max_tokens/脚本版本）、日期与操作人——字段固定下来，两轮报告才能并排对比。基线报告归档在评估仓库（与评估集同级治理），训练记录（06 篇）引用它的版本。

## 4. 验收标准预设：门禁写在训练前

验收门禁在训练前写好，训练后按门禁决策——**门禁预设避免"事后找理由"**（训完说"虽然指标没提升但感觉变好了"是最典型的自我欺骗）。2026 年参考门禁：

- **自定义评估集**：相对基线提升 >3% 才考虑上线（分类/结构化任务可更严，>5%）。
- **标准基准回归**：MMLU 类通用能力基准相对基线**回归 <1%**（回归超限 = 灾难性遗忘信号，`../基础概念/09-评估基础损失曲线与过拟合.md` 03 节）。
- **业务指标**：需求文档里的核心指标（格式解析率/话术命中率等）达标。
- **人工抽检**：上线前 50-100 条人工双盲对比（微调模型 vs 基线），胜出才算数。

门禁不是"全部满足才上线"，而是**明确每条标准的权重与一票否决项**（如"标准基准回归 >2% 一票否决"）——写清楚规则，验收时才不会扯皮。

门禁还有一个容易被忽略的组成：**成本与收益的账**——提升 3% 是否值回训练与维护成本（边际收益评估，`../边界判断（非常关键，面试必问）/09-成本收益量化与混合策略.md` 的 ROI 方法在此兑现）——技术上达标但经济上不值，同样该回炉或放弃。

## 5. 基线的复验与更新

基线不是测一次就完：**每次数据迭代重训后，基线报告要能复现**（同脚本同配置），防止"环境漂移"把基准值测歪（CUDA/库版本变化会让同一模型分数漂移——评估脚本环境要 lock）。另外基线会过时：底座升级（Qwen 发新版）、Prompt 体系变化都会改变基线——**基线报告带版本，每次验收注明"对比哪个基线的哪一版"**（与 09 篇的版本治理联动）。

> 🎯 **核心要点**：eval-first = 训练前完成金标评估集（从需求规范生成、300-800 条、版本化管理）+ 底座基线报告（同套评估脚本 + Prompt 基线）+ 门禁预设（>3% 提升、<1% 回归、业务指标、人工双盲）；门禁写在训练前防止事后找理由；基线带版本、可复现——微调只能改进底座已有方向，基线就是预期管理的锚。
