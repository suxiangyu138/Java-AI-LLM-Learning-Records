# 训练过程监控与干预

> 流程第 7 阶段：长任务必须监控——三件套（wandb/日志/系统）、曲线读法、OOM 五步调试、故障处理与续训——监控是止损的第一道防线

## 1. 监控三件套

**长训练（>2 小时）必须监控**——一次故障可能浪费数万元算力（2026 估算：失败一轮训练成本可达 1 万美元+）。监控三件套各司其职：

**训练指标**（wandb 或 TensorBoard）：loss、eval loss、学习率、梯度范数、吞吐（tokens/s）——wandb 是生产推荐（实时看板、自动记录 divergence 的准确 step、HF Hub 集成；代价是外部服务 + 1-2% 训练开销）；本地/离线环境用 TensorBoard + 文件日志；告警通道：企业 IM 机器人推送 + 邮件兜底（长任务过夜前必配）。**配置要点**：`logging_steps=50`、`report_to=["wandb"]`，wandb 调用加 try/except（**日志失败不能弄崩训练**）。

**系统指标**：GPU 显存/温度/利用率、CPU 与内存、磁盘——显存泄漏（训练 2 小时显存缓慢爬升）只能靠系统指标发现；`torch.cuda.memory_allocated()` 前后对比可验证显存是否释放。监控项的最小清单：显存占用（峰值与趋势）、GPU 利用率（低于 60% 查数据管线）、磁盘剩余（checkpoint 写入失败的静默杀手）、温度（过热降频是吞吐骤降的隐蔽原因）——四类指标各设告警阈值，长任务挂机过夜前务必配好告警（wandb 告警或自写脚本推送）。

**文件日志**：stdout/stderr 落文件（排障第一手资料）+ checkpoint 目录——双日志（wandb + 文件）是生产标准，wandb 挂了还有文件兜底。

## 2. 曲线读法与干预矩阵

训练中的四条关键曲线（`../基础概念/06-训练循环Epoch-Batch-Step.md` 05 节）与干预动作：

| 信号 | 含义 | 干预 |
|------|------|------|
| train loss 平滑下降、eval 同步 | 健康 | 继续，盯 eval 拐点 |
| train 降、eval 背离（gap 拉大） | 过拟合前兆 | 准备 early stopping（`../基础概念/09-评估基础损失曲线与过拟合.md` 02 节） |
| loss 后期平坦 | 正常（幂律收敛，`../基础概念/04-损失函数与训练目标.md` 06 节） | 以 eval 为准判断 |
| loss NaN/Inf | 数值问题 | 立即停：查学习率（降 3-5 倍）/查数据（NaN/脏样本）/查精度（bf16 溢出） |
| grad norm 异常飙升 | 数据或数值问题 | 查数据优先（重复/脏样本），再查梯度裁剪配置 |
| 吞吐骤降 | 数据管线阻塞/磁盘 IO | 查 dataloader 进程、磁盘满 |

**干预纪律**：先诊断再动手（"别用改配置来掩盖 bug"）——OOM 就按 OOM 顺序调，NaN 先查数据；改完记录到实验日志并重跑冒烟。**止损优先**：判定训练已坏（eval 连续 N 点背离、loss 发散），该停就停——省下的算力用于排查，比硬跑完更值。

**干预的量化标准**：eval loss 连续 2-3 个评估点不降反升 = 准备停止的信号（配合 `load_best_model_at_end` 兜底）；eval 与 train 的 gap 超过历史差距的 1.5 倍 = 过拟合确认；任何"看起来不对"的信号先截图/导出曲线再动手（干预记录 = 事后复盘的第一手数据）。

## 3. OOM 调试五步（按序执行）

CUDA out of memory 是训练第一高频错误，按顺序试（每步都有显存账本依据，`../基础概念/03-Transformer与参数基础.md` 05 节）：

1. **启用 QLoRA**（若还没用）——省 ~75% 显存，最大杠杆。
2. **降 batch size**——降到 1 为止；配合梯度累积补回有效 batch（`../基础概念/06-训练循环Epoch-Batch-Step.md` 02 节）。
3. **开梯度检查点**——省 ~30% 显存、费 ~20% 速度。
4. **降 max_seq_length**——激活值显存随序列长度线性增长，长上下文是隐藏显存大头（512→128 立省大半）。
5. **换小模型**——7B → 1-3B 级（TinyLlama 类），换模型要重新评估基线（03 篇）。

顺序逻辑：从"保留方案"到"改变方案"——前四步不改模型与效果假设，第五步才动模型。**报错排查习惯**：看错误信息最后一行（最有用）、报问题带 OS/Python/GPU 型号/显存/完整 traceback。

## 4. 故障处理工作流

2026 年标准故障处理流程（experiment-debugger 流程）：**查日志与配置 → 最小复现 → 定向修复 → 冒烟验证 → 重新提交**。

- **查日志与配置**：stdout 文件 + wandb 曲线 + 训练配置三者对照——先判断是"工程 bug"还是"科学信号"（loss 不降可能是 bug 也可能是数据问题，性质不同处理不同）。
- **最小复现**：用小数据/小步数复现问题——能复现 = 能定位；不能复现 = 环境/随机性问题（查 seed、查 checkpoint 加载的 step、查多 worker 数据加载的确定性）。
- **定向修复**：修代码/配置（**不要用临时 shell 覆盖**——修复要进 git/配置，否则下次重蹈）；修复后冒烟验证，再重新提交训练。
- **记录**：每个故障写 debug 记录（现象/根因/修复）——这是 `../微调常见问题/` 体系的素材来源，也是团队的知识资产。

常见故障类型速查（六类占微调事故 90% 以上，排查路径都落在本体系对应章节）：**OOM**（第 3 节五步）；**NaN/Inf**（先查学习率与精度，再查数据）；**训练中断**（断电/超时/节点故障——断点续训，第 5 节）；**吞吐骤降**（先查 dataloader 与磁盘，再查 GPU 利用率与温度）。

**显存泄漏**（长跑显存缓升——查自定义代码缓存未释放，配周期显存检查）；**结果不可复现**（先查 seed 与 checkpoint 加载 step，再查多 worker 数据顺序）。

## 5. 断点续训与长时间运行

长训练（数天）的运行保障：**checkpoint 频率**（save_steps 与故障恢复成本的平衡：save 太疏，故障丢几小时进度；save 太密，磁盘与 IO 开销——500-1000 步为常用区间）；**磁盘监控**（checkpoint + 日志 + wandb 缓存都会吃盘，磁盘满 = 静默故障，监控里必须有磁盘项）。

**恢复验证**：resume 后确认——step 计数连续、scheduler 从保存点继续、loss 曲线无跳变——**从错误 step 恢复是隐蔽 bug**，恢复后前几十步与原曲线对比。

**2026 提醒**：多 GPU/多节点训练日志聚合（stdout 分节点落盘 + wandb 聚合）是排障基础；训练完成后用 `torch.cuda.memory_allocated()` 验证显存释放（内存泄漏在长时间运行里会累积成隐性故障）。

> 🎯 **核心要点**：监控三件套 = 训练指标（wandb，日志失败不崩训练）+ 系统指标（显存泄漏只有系统指标能发现）+ 文件日志（兜底）；干预矩阵按信号对表（NaN 降 lr/查数据、grad norm 飙升先查数据）；OOM 五步按序（QLoRA→降 batch→梯度检查点→降长度→换小模型）从"保留方案"到"改变方案"；故障处理 = 查→复现→修→冒烟→重提交，修复进 git；断点续训要验证恢复正确（step/scheduler/曲线连续）。
