# 导出部署与上线运维

> 流程第 9 阶段：验收通过后的交付——LoRA 合并（float16、不可逆）、量化与服务（vLLM 单模型/多 LoRA）、灰度上线与数据回流迭代——上线不是终点，迭代是常态

## 1. 部署路径选择：合并 vs 动态多 LoRA

微调产物（LoRA 适配器）有两条部署路径：

**路径 A：合并进底座**（merge_and_unload）。数学上把适配器写回底座权重（W_merged = W + A·B·(alpha/r)），产出标准 transformer checkpoint——任何推理框架可加载。**硬前提**：合并必须用 **float16 加载底座**（不能用 4-bit——量化底座合并会损失精度）；**合并不可逆**（想回退只能从原始底座重新来）。合并后可选再量化（GGUF 供 CPU/Mac 的 Ollama/llama.cpp、AWQ 供服务端 GPU、EXL2 供 RTX）——**注意这是部署期量化，与训练期 QLoRA 的 4-bit 是两回事**（06 篇）。

**路径 B：动态多 LoRA 服务**。底座常驻显存，按请求热挂适配器——一个底座服务几十个微调变体（适配器仅底座 0.1-1%，r=64 的 7B 适配器约 15MB）；推理开销约 2-5%。**vLLM 硬约束**：`enable_lora=True` + 适配器**预注册**（LoRARequest）；**适配器必须纯低秩**（`modules_to_save` 为 null——embed_tokens/lm_head/norm 的全秩张量 vLLM 运行时不支持）；适配器数量 >50 时注意延迟，显存预算按 10-15% 裕量。

**选型判据**：单一模型服务 → 合并（简单可靠，NVIDIA 2026 实测"merge-then-serve"最稳）；多变体/频繁切换 → 动态多 LoRA；**混合**：主线合并、试验变体动态挂。

## 2. 导出流程（合并四步）

```text
加载 tokenizer → 加载底座（float16）→ PEFT 加载 LoRA 并 merge_and_unload() → 保存完整模型 + tokenizer
```

产物目录：config.json、safetensors 权重、tokenizer 文件、export_metadata.json（导出配置：底座版本、适配器版本、合并时间）——**导出记录 = 部署版本的身份证**（与 09 篇版本治理联动）。

合并后**必须重跑验收冒烟**：合并过程可能引入数值差异——checkpoint 选择（最后一步 vs 最优 eval loss）的差异是离线评估与线上表现不一致的常见来源（08 篇）；服务启动前验证目录与 config.json 存在（启动失败的最常见低级原因）。

## 3. 服务部署（vLLM）

2026 年服务标准是 vLLM（或 SGLang；轻量场景 Ollama/llama.cpp 走 GGUF）：

- **合并模型服务**：`vllm serve <merged-model-path> --port 8000 --tensor-parallel-size N --max-model-len 4096`——chat template 从合并模型的 tokenizer_config 自动加载（**模板在训练时就得对**，`../基础概念/08-指令数据与对话格式基础.md` 03 节）。
- **多 LoRA 服务**：`--enable-lora --lora-modules finance=...` + `--max-lora-rank 128` + `--gpu-memory-utilization 0.85`。
- **OpenAI 兼容端点**：`/v1/chat/completions`——应用层零改动接入（与 API 微调、LiteLLM 网关等生态互通）。接入示例：应用侧只需改 `base_url` 指向本地 vLLM 服务（`http://localhost:8000/v1`），请求体与 OpenAI 格式完全一致（model 参数填部署的模型名）——**API 微调、自训模型、云服务三者在应用层无感知切换**是 2026 服务架构的标准姿态。
- **服务验证链**：smoke test（发一条请求——健康检查 + 输出非空 + 角色格式正确）→ 性能基准（TTFT/吞吐，`03-AI大模型应用开发/05-模型部署与工程化/` 体系深潜）→ 结构化输出稳定性检查（同 prompt 跑 50 次，JSON 解析率与字段一致性）→ **评估走服务路径**（08 篇，验证上线后的真实行为）。

## 4. 灰度上线与监控

上线采用**分阶段推进**（与 `02-.../CI CD灰度发布/` 的通用方法论一致，此处是模型特化）：

- **影子模式**：新模型与线上模型并行跑，对比输出（不接用户流量）——上线前的最后验收（行为对比 + 延迟对比）。
- **灰度放量**：5% → 20% → 50% → 100%，每档对比业务指标（任务成功率、用户反馈、延迟、成本/token）。
- **回滚预案**：模型服务多版本并存（路由切换秒级回滚）——**多 LoRA 架构下回滚 = 切适配器版本**，比合并模型重部署快一个量级，这是动态多 LoRA 的运维红利。
- **上线监控**：推理指标（TTFT/吞吐/错误率/显存）+ 业务指标（任务成功率/格式解析率）+ **安全与背出监控**（`../数据集体系（非常重要）/09-数据版本管理与合规治理.md` 04 节：背出探测定期跑）。

**回滚条件预设**（灰度前写清楚，防"该回滚时不回滚"）：业务指标较基线下降 >5% 持续 30 分钟、错误率/超时率异常上升、安全事件（背出/越权输出）任何一例即回滚——回滚动作要演练过（多 LoRA 架构秒级切版本，合并模型重部署按分钟计），**没演练过的回滚预案等于没有预案**。
- **适配器生命周期**（2026 生产标准）：staging → shadow → production → archived 四态推进，注册表记录训练指标（loss/eval_loss）——状态机让"哪个版本在线上"永远可查。

## 5. 数据回流：迭代闭环

上线不是终点——**生产数据是微调迭代的最大矿藏**：

**失败案例回流**：线上失败样本（格式解析失败、用户投诉、judge 打分低）按周收集 → 人工筛选与标注 → 补入数据流水线（周更闭环，`../数据集体系（非常重要）/07-数据质量评估与筛选.md` 05 节）→ 重训 → 回归集验证 → 灰度上线。

**回流纪律**：回流样本先进评估集还是训练集要分清（**评估集先补"新失败模式"、训练集后补"同类样本"**——先让考卷认识新题型，再让模型学会新题型）；回流数据与已有训练集先去重（防重复强化，`../数据集体系（非常重要）/05-数据去重与污染检测.md`）；回流质量仍要过质量门禁（线上失败样本不等于好训练样本，清洗 + 人工复核不能省）。回流的数据量级参考：每周 200-1000 条精选新样本足以驱动一轮有效迭代。

**迭代节奏**：周更是 2026 生产常态（一次全流程：收集 → 数据 → 训练 → 回归 → 灰度）；迭代成熟后，微调的边际收益逐渐收敛——**迭代放缓的信号出现时（连续两轮门禁不提升），回到边界判断体系重新审视"还要不要继续微调"**。

> 🎯 **核心要点**：部署两路径——合并（float16 加载、不可逆、单模型最稳）vs 动态多 LoRA（modules_to_save 必须 null、预注册、多变体 + 秒级回滚）；导出四步 + 合并后必须重验；vLLM 服务（模板自动加载、OpenAI 兼容、评估走服务路径）；灰度五档（影子→5%→100%）+ 适配器四态生命周期；数据回流闭环（失败案例 → 评估集先补 → 训练集后补 → 重训 → 回归 → 灰度）——周更常态，边际收敛时回边界判断重审。
