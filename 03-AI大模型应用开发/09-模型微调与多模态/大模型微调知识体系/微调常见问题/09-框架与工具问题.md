# 框架与工具问题

> "莫名报错"的 80% 根因是环境问题：版本矩阵错位、bitsandbytes 依赖、transformers 兼容、模型下载——报错信息最后一行 + 完整 traceback + 版本矩阵核对是标准动作

## 1. 版本矩阵错位：莫名报错第一来源

**症状**：上周能跑的脚本这周报错、照教程装的库莫名不兼容、升级一个小版本后行为变化——2026 年"莫名报错"的第一根因是版本矩阵错位（Python/transformers/peft/trl/bitsandbytes/accelerate 的兼容组合）。

**诊断**：`pip check` 查依赖冲突；`pip freeze` 对比"能跑的环境"与"报错的环境"（有基线环境的 diff 是最高效的定位）；报错堆栈里的版本信息（transformers 报错常带版本提示）。

**预防**（`../完整微调工程流程/04-环境搭建与工具链选型.md` 04 节）：环境文件（requirements.txt）**精确 pin 版本**（不用 >=/latest）；环境文档写明"已验证兼容矩阵"（哪个 Python × 哪个 transformers × 哪个 peft）；Docker 镜像化（团队共享同一镜像）；**环境变更走记录**（升级前记录、升级后冒烟——"环境漂移"是"结果不可复现"的第一来源）。

## 2. bitsandbytes 问题

QLoRA 的 4-bit 依赖 bitsandbytes，三个高频报错：

**CUDA 版本不匹配**（第一高频）：bitsandbytes 报 `CUDA Setup failed` / 找不到库——bitsandbytes 的编译产物与 CUDA 版本绑定，**按官方兼容矩阵重装**（pip 安装时指定与本地 CUDA 匹配的版本）；验证：`import bitsandbytes` 无报错 + 小模型 4-bit 加载冒烟。

**Windows 支持问题**：bitsandbytes 在 Windows 上的支持长期落后（Linux/WSL2 是标准环境）——Windows 本地报 4-bit 相关错误，优先切 WSL2 或 Docker（`03-AI大模型应用开发/部署工具/` 体系的 Docker 实践）。

**量化配置错误**：`bnb_4bit_compute_dtype` 与模型 dtype 不匹配报类型错误——配置统一用 bf16（`../完整微调工程流程/06-训练配置与启动.md` 02 节标准配置）。

## 3. transformers/peft/trl 兼容问题

**症状**：`AttributeError`（某参数不存在）、`UserWarning` 突然变报错、微调结果与文档不一致。根因与处置：

**小版本行为漂移**：transformers 小版本升级会改默认参数/弃用 API——`pip check` + 版本对比 + **升级框架后必跑 50 步冒烟**（`../完整微调工程流程/06-训练配置与启动.md` 05 节）——"升级后不冒烟"是静默漂移的来源。

**新特性需要新版本**：`apply_chat_template` 的 labels 支持（transformers 4.46+）、TRL 新方法（GRPO）需要特定版本——报错提示"requires newer version"时按提示升级，升级后全量冒烟。

**缓存问题**：transformers 模型缓存（`~/.cache/huggingface`）损坏/版本混杂（同一模型多个版本）——清缓存重下（`hf_hub_download` 或删除缓存目录）——症状：加载报错与文件相关。

## 4. 模型下载问题

**症状**：下载慢、断点失败、`Connection error`、权限错误。处置（详见 `03-AI大模型应用开发/02-大模型基础与Prompt工程/HuggingFace/` 体系）：

**网络问题**：国内环境配 `HF_ENDPOINT=https://hf-mirror.com`（环境变量，import 前设置）；大模型用 hfd.sh 多线程工具（70B 实测 4 小时 → 22 分钟）；断点续传（下载工具支持 resume）。

**权限问题**：gated 模型（Llama 系）需要 token——`HF_TOKEN` 环境变量 + HuggingFace 账号授权（模型卡上申请）。

**磁盘问题**：模型下载一半磁盘满（7B 约 15GB，先 `df -h`）——下载失败后重试会继续占盘，清理缓存后重下。

## 5. 框架特定坑

**Unsloth**：**内置模板滞后新模型**（02 篇的 Gemma-4 案例——旧模板静默训错格式）——用新模型前查 Unsloth 发布说明，或跳过其模板直接用官方 tokenizer；自定义内核滞后新架构（模型发布后几天-几周才支持）——加载报错查支持矩阵。

**LLaMA-Factory**：配置项过多（"太多旋钮"），**配置与文档版本不匹配**（文档与发版不同步）——以安装版本的 README/示例配置为准；Python API 在演进，生产用 CLI。

**Axolotl**：YAML 数百行，**配置项拼写错误不报错**（未知字段被忽略）——配置校验（`axolotl validate`）必跑；升级大版本注意默认值变化。

**框架问题的通用排查顺序**（不针对特定框架）：报错先读最后一行 + 完整 traceback → 判断"环境类"还是"用法类"（版本相关报错 = 环境类，API 调用报错 = 用法类）→ 环境类查版本矩阵（第 1 节），用法类查该框架当前版本的文档/示例（**教程与版本脱节是用法报错的第一来源**——2026 年框架迭代快，半年前的教程可能已失效）→ 修复后 50 步冒烟验证。**官方示例是最可靠的"正确姿势"基准**：用官方示例跑通 → 逐步替换为自己的数据/配置 → 出问题定位在替换的那一步。

**TRL**：与 HF 生态深度绑定，**依赖版本敏感**（trl 新版本可能要求新的 transformers）——按官方 requirements 安装；SFTTrainer 参数名随版本演进（旧教程的 `training_args` 写法可能失效）。

**框架问题的时间成本**：环境类问题（版本/依赖/下载）通常 30 分钟内可定位（pip check + 版本对比），用法类问题（API/配置）可能半天——**先花五分钟判断类型**（报错信息里出现版本号/库名 = 环境类，出现 API/参数名 = 用法类），类型判断错 = 在错误方向排查浪费半天。**环境类问题的标准动作**：报错信息 + `pip check` + `pip freeze` 对比基线环境——三件套 80% 环境问题当场定位。

**模型加载类报错速查**：`KeyError`/`AttributeError`（config 与权重不匹配——底座与 tokenizer/config 版本混杂，用同一版本的三个文件）；`safetensors` 格式错误（下载损坏——删除重下）；`device_map` 错误（多卡分配失败——显存不足或 device_map 配置与模型不兼容，`../完整微调工程流程/06-训练配置与启动.md` 04 节）；`trust_remote_code` 报错（远程代码模型需要显式信任——确认来源后加参数）——四类报错覆盖模型加载阶段的 90% 问题。

**框架问题的终点是"预防"**：90% 的框架问题可以被环境纪律提前拦截——版本 pin 死、升级必冒烟、镜像化、环境变更记录（`../完整微调工程流程/04-环境搭建与工具链选型.md` 04 节）；每踩一个新坑，就把"预防检查"补进启动清单——**排障手册的成熟度 = 启动清单的长度**。

**框架问题共性纪律**：报错先看**错误最后一行**（最有用的信息）；报问题带完整 traceback + OS/Python/GPU/版本（别人才能帮）；**框架升级是"变更"不是"日常"**——升级 = 冒烟 + 记录，与代码变更同等对待（`../完整微调工程流程/07-训练过程监控与干预.md` 04 节）。

> 🎯 **核心要点**：版本矩阵错位是莫名报错第一来源（pip check + 冻结版本 + 环境 diff）；bitsandbytes 三坑——CUDA 版本匹配（按官方矩阵装）、Windows 落后（切 WSL2/Docker）、compute_dtype 统一 bf16；transformers 小版本行为漂移——升级必冒烟；下载四招——hf-mirror/hfd/断点续传/HF_TOKEN；框架特定坑——Unsloth 模板滞后、LLaMA-Factory 文档脱节、Axolotl 配置静默忽略、TRL 依赖敏感；纪律 = 错误最后一行 + 完整 traceback + 升级当变更。
