# 问题全景与排查方法论

> 排障手册的总纲：问题分类地图（模板/数据/训练/显存/效果/部署/工具七类）+ 排查五步法（复现→隔离→假设→验证→记录）+ nonce 测试——先诊断再动手是唯一纪律

## 1. 问题分类地图

微调全流程的问题按"出问题的环节"分七类，每类有典型的症状指纹：

| 类别 | 典型症状 | 第一嫌疑 |
|------|---------|---------|
| 模板类（02 篇） | 输出垃圾、角色混乱、格式全错 | chat template 不匹配 |
| 数据类（03 篇） | 评估虚高、训练 loss 假象、效果偏科 | 同源泄漏/重复/负样本缺失 |
| 训练类（04-05 篇） | loss 不降/NaN/发散/过拟合/遗忘 | 学习率/数据/epoch |
| 显存类（06 篇） | OOM、训练慢、卡死 | 配置/硬件 |
| 效果类（07 篇） | 没提升、变差、幻觉增加 | train-serve 错配/需求误判 |
| 部署类（08 篇） | 合并后变差、量化崩、服务异常 | 精度/量化方案 |
| 工具类（09 篇） | 莫名报错、装不上、加载失败 | 版本矩阵 |

分类的价值在**定位优先**：看到一个症状先归类，再进对应章节按诊断路径查——而不是随机试各种"可能的原因"（随机排查是最昂贵的排查，一次训练重启的成本可能数小时）。

## 2. 排查五步法

所有排障的统一流程（2026 年 experiment-debugger 工作流的一致形态）：

**第一步：复现**。拿到可复现的最小场景——完整错误信息（最后一行 + 完整 traceback）、训练配置、数据样本、环境版本。**"偶发"不是答案**：把复现条件尽量收窄（小数据、小步数、单卡）。

**第二步：隔离**。把问题限制在最小环节——数据问题还是训练问题？模板问题还是模型问题？做法：换环节组件（用最小数据跑、用官方示例跑、用最小配置跑）——哪个换掉后问题消失，问题就在哪个环节。

**第三步：假设**。基于症状列出有序假设（按概率排序），**一次只验证一个**——同时改多个变量 = 无法归因。

**第四步：验证**。用最便宜的实验验证假设——nonce 测试（见第 3 节）、渲染 diff、小步数冒烟。验证通过才动手修。

**第五步：记录**。修复进 git（不临时覆盖）、写 debug 记录（现象/根因/修复）——**这是团队知识资产**，也是本体系各篇案例的来源。

**元纪律**：先诊断再动手——"别用改配置来掩盖 bug"（改学习率可能"碰巧"绕过症状但没找到根因，下次换个数据又炸）。OOM 就按 OOM 顺序调、NaN 先查数据——每类问题有标准路径（后续各篇），不跳步。

五步法的一次完整演示（模板问题为例）：复现（找到一条必现的垃圾输出样本）→ 隔离（用官方模板跑同一样本——官方模板正常 = 问题在自定义模板）→ 假设（模板家族用错/渲染不对称/掩码错误，按概率排序）→ 验证（渲染 diff 定位具体 token 差异）→ 记录（修复进模板文件 + debug 记录）——全过程不碰训练配置，十分钟完成。

## 3. nonce 测试：两小时定位链路问题的快测

nonce（一次性令牌）测试是 2026 年排障的高价值技巧：**用 4 个样本 + 一个"不可能出现"的目标标签做极短训练**（如把 `DEBUG_TOKEN_7F3A` 作为目标输出），训练几轮后让模型在训练样本上生成——**如果模型连训练样本上的 nonce 都吐不出来，说明适配器、标签、模板或训练循环有问题**（模型连"背题"都做不到，链路必坏）。

nonce 测试能定位什么：模板渲染错误（角色/掩码错）、标签错位（prompt masking 掩错了）、训练循环问题（梯度没到适配器）、数据加载问题。**定位不了的**：数据质量、超参选择（那是后续排查）。nonce 测试的变体："简化目标"测试——把 JSON 格式任务临时退化成纯分类（safe/unsafe），如果连 4 个样本的分类都过拟合不了，问题在目标/模板/输入，不在解析器。

## 4. 渲染 diff：模板问题的第一检查

训练与推理的**渲染不一致**是 2026 年确认的"第一大静默杀手"（02 篇详述）——预防它的第一手段是渲染 diff：

**做法**：把同一条样本分别用"训练模式"与"推理模式"渲染成 token 序列，逐字节对比——角色标记一致？assistant 起始标记位置正确？结束 token 在训练时进了 loss 掩码、推理时正常生成？训练样本里没有意外出现 generation prompt？**两个模式渲染出的序列必须逐 token 一致（除了推理模式的 generation prompt 追加）**。

**为什么必做**：模板是"位置依赖的函数"而非序列化格式——训练模式与推理模式的输出不保证一致（Qwen3 的 think 块在工具轮次被丢弃、Gemma4 全新模板与 Unsloth 旧模板不匹配都是 2026 实锤案例）。任何组件单独检查都正确，组合起来却坏了——**渲染 diff 是唯一能抓住"组合错误"的廉价手段**（12 行的 prefix-preserving 属性测试可以自动化检查任意 tokenizer）。

**排障的算力经济**：一次完整重训数小时到数天，一次诊断（渲染 diff/nonce 测试/日志分析）几分钟——**诊断的投入产出比极高**，"多花十分钟诊断、省一次重训"是排障手册存在的意义；反过来，跳过诊断直接重训，是把最贵的资源（算力）花在最便宜的问题上。

## 5. 排障的记录与复盘

排障的最后一步是记录，记录的价值在**复用**：同一个坑（模板不匹配、batch 忘配累积）团队里往往反复踩——debug 记录（现象/根因/修复 + 关联章节）沉淀成团队排障手册；**每季度复盘高频故障**（哪类问题花时间最多），反向推动流程改进（比如"模板问题季度 Top1 → 把渲染 diff 写进启动检查清单"）——排障手册的终极目标是"让坑不再需要查"（预防 > 排查）。

> 🎯 **核心要点**：问题分七类（模板/数据/训练/显存/效果/部署/工具）先定位再查；排查五步（复现→隔离→假设→验证→记录）一次只验一个假设；nonce 测试（4 样本 + 不可能标签）两小时定位链路问题；渲染 diff 是抓"组合错误"的廉价手段（模板是位置依赖函数，训练/推理渲染不保证一致）；修复进 git + debug 记录沉淀复用；元纪律"先诊断再动手"——预防 > 排查。
