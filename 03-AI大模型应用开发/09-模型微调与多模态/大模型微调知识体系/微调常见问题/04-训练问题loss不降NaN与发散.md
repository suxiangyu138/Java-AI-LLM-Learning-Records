# 训练问题（上）：loss 不降、NaN 与发散

> 训练期三大症状：loss 不降（原因树排查）、NaN（数值问题排查链）、发散（立即止损）——以及 2026 年最贵的失败模式"destroyed weights"（loss 正常但权重已毁）

## 1. loss 不降：原因树

loss 前几百步不动或降幅极小，按概率从高到低排查：

**数据问题（第一嫌疑）**：标签与输入错位（masking 掩错了位置，模型只在学"预测 user"或学空序列）；样本全是同一类（模型没东西可学）；数据量过小（几百条训几个 epoch 也可能"不动"——先确认数据量与任务难度匹配）。**验证**：nonce 测试（4 样本 + 不可能标签——模型连背题都做不到，链路必坏，01 篇第 3 节）；单样本过拟合测试（拿 10 条数据训 50 步，loss 应该显著下降——不降 = 数据/链路问题）。

**学习率问题**：学习率过低（LoRA 2e-4 量级起，`../基础概念/05-优化器与梯度更新.md` 03 节）——曲线平滑但极慢；warmup 过长（warmup 占比超 10% 会浪费早期步数）。**验证**：看 lr 曲线（是否在预期位置）；临时升 3-5 倍 lr 观察（诊断手段，不是修复）。

**梯度问题**：梯度被掩码吞掉（`assistant_only_loss` 配置下掩码范围错误——所有 token 都被掩，梯度为零，loss 恒为初始值）；梯度范数为 0（查 grad norm 日志，07 篇干预矩阵）。**验证**：nonce 测试直接命中这一类。

**损失计算问题**：loss 恒等于某个常数（如 log(vocab)）——说明模型输出均匀分布，权重没被更新（优化器/梯度链路问题）。

**loss 不降的"时间尺度"判断**：几百步内"不降"与"降得慢"是两回事——微调初期 loss 通常先快速下降（底座已懂语言，校准行为很快见效），如果 200 步内完全不动（变化 <1%），大概率是链路问题而非"训练慢"；如果 200 步后缓慢下降，可能是学习率低或数据模式难学——**先确认"完全不动"还是"慢"，再决定查链路还是调超参**。

## 2. NaN 与 Inf：数值问题排查链

loss 变 NaN/Inf 的排查顺序（按概率）：

1. **学习率过高**：数值发散的最常见原因——降 3-5 倍（`../基础概念/05-优化器与梯度更新.md`）；warmup 缺失（训练初期大步长打爆）。
2. **数据问题**：数据里有 NaN/Inf 值（清洗不净的文本字段）、重复样本爆炸、异常长的样本（数值溢出）。
3. **精度问题**：fp16 训练溢出（loss scale 管理不当）——换 bf16（范围大不易溢出，2026 标准）；bf16 在极小学习率 + 高精度需求场景也偶发，降 lr 或换 fp32 混合。
4. **优化器状态损坏**：断点恢复后优化器状态错位（从错误 step 恢复，`../完整微调工程流程/07-训练过程监控与干预.md` 05 节）——重训前先确认恢复正确。

**诊断纪律**：NaN 出现立即停（止损，`../完整微调工程流程/07-训练过程监控与干预.md` 02 节）；**定位到第一个 NaN 的 step**（wandb 曲线/日志定位 divergence 的确切位置）——第一个 NaN 的上下文就是根因线索；修复后从 NaN 前的 checkpoint 重训（不是从头）。

**NaN 的定位技巧**：用 `torch.autograd.set_detect_anomaly(True)` 跑小步数复现——PyTorch 会直接指出"哪个 backward 调用产生了 NaN"（指向具体层/具体数据）；代价是训练显著变慢，所以只用于诊断复现（小步数），修复后关闭。另一个便宜信号：**NaN 前几步的 grad norm 趋势**——梯度先爆炸后 NaN = 学习率问题；梯度正常但 loss 突 NaN = 数据/数值问题。

## 3. 发散：立即止损

loss 飙升或震荡加剧（grad norm 爆炸）——**判定训练已坏，立即停止**（继续跑只是烧钱）。止损后的排查：梯度裁剪是否配置（max norm 1.0 是标准保险丝）；学习率是否过高；数据是否有极端异常样本（脏样本引发单步梯度爆炸）；多卡场景查通信问题（NCCL 错误引发梯度错位）。

**止损纪律**：停止后**先保存现场**（当前曲线截图、日志、配置）再动手——"任何看起来不对的信号先留证据再改"（`../完整微调工程流程/07-训练过程监控与干预.md` 02 节）；修复后重跑冒烟验证再提交正式训练。**发散与 NaN 的共因**：两者经常同源（学习率过高是发散也是 NaN 的第一嫌疑），按"先降 lr 再看数据"的顺序一次排查，避免两套流程重复跑。

## 4. destroyed weights：2026 年最贵的失败模式

**症状**：训练 loss 正常下降、评估看着还行，但模型输出"自由生成垃圾到 token 上限"——2026 年实锤案例：微调模型 F1 0.81 vs 底座 0.977，输出日期从"2026-10-06"变成"206-10-06"（数字被毁）；更诡异的是**加数据反而单调变差**（69 条 → F1 0.81，122 条 → 0.214，2122 条 → 0.000）。

**根因**：训练过程把**权重本身破坏了**（不是格式问题）——检测方法：**原始输出探测**（不带任何约束/grammar 直接生成，01 篇第 3 节）——裸生成也是垃圾 = 权重已毁。

**排查链**：先确认不是模板问题（渲染 diff）→ 非量化问题（同一权重过 f16/Q8_0/Q4_K_M 对比，损伤在量化前就存在）→ 怀疑训练配方（学习率、epoch、数据毒化）→ 用极小数据集回归测试（10 条数据训 50 步看输出是否合理）。**2026 教训**：loss 收敛不是模型健康的证据——**"loss 降"只是必要条件，输出探测 + 任务指标才是判据**（`../基础概念/09-评估基础损失曲线与过拟合.md`）。

## 5. 三症状的共性纪律

三个症状共享的排障纪律：**先看日志证据再动手**（loss 曲线、grad norm、wandb 记录是排障的地基）；**一次只改一个变量**（同时改 lr 和 epoch 无法归因）；**小步快跑验证**（每次修复先冒烟再正式）；**修复进 git**（改配置不是修复，进配置库才算）——以及最重要的：**止损优先**，判定训练已坏该停就停，省下算力排查，比硬跑完更值（`../完整微调工程流程/07-训练过程监控与干预.md` 02 节）。

> 🎯 **核心要点**：loss 不降按原因树查——数据（nonce 测试/单样本过拟合测试）→ 学习率（lr 曲线/临时升 lr 诊断）→ 梯度（掩码吞梯度）→ 损失计算（恒常数 = 权重没更新）；NaN 按序查——lr 过高 → 数据 NaN → fp16 溢出换 bf16 → 优化器状态错位，定位第一个 NaN 的 step、从 NaN 前 checkpoint 重训；发散立即止损先留证据；destroyed weights = loss 正常但权重已毁（裸生成探测），加数据可能更坏——"loss 降"不是模型健康的证据。
