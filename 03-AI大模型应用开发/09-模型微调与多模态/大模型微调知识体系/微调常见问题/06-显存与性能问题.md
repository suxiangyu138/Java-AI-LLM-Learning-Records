# 显存与性能问题

> 训练期第一高频错误 OOM、隐性杀手显存泄漏、性能下降（吞吐骤降）与多卡问题——显存账本是一切调试的依据，顺序即逻辑

## 1. OOM：五步调试（按序执行）

CUDA out of memory 是训练第一高频错误，**五步按序**（每步的显存账本依据见 `../基础概念/03-Transformer与参数基础.md` 05 节，完整论述在 `../完整微调工程流程/07-训练过程监控与干预.md` 03 节）：

1. **启用 QLoRA**（若还没用）——省 ~75% 显存，最大杠杆。
2. **降 batch size**——降到 1 为止，配梯度累积补回有效 batch（`../基础概念/06-训练循环Epoch-Batch-Step.md` 02 节）。
3. **开梯度检查点**——省 ~30% 显存、费 ~20% 速度。
4. **降 max_seq_length**——激活值显存随序列长度线性增长（512→128 立省大半；先查数据长度分布——如果 99% 样本都短，是 max_seq_length 设置浪费，不是数据问题）。
5. **换小模型**——7B → 1-3B 级；换模型重新评估基线（`../完整微调工程流程/03-评估先行基线建立.md`）。

**调试细节**：看错误最后一行（有用信息在末尾）；OOM 发生的确切位置（前向/反向/优化器 step）决定调整方向（前向 OOM = 激活值/长度问题，优化器 step OOM = 优化器状态问题）；`torch.cuda.empty_cache()` 是治标（碎片整理），不解决预算问题；**显存预算检查**（启动前 `nvidia-smi` 确认无其他进程占用——共机被占是"莫名 OOM"的第一嫌疑）。

**OOM 的"碎片化"陷阱**：显存够用但频繁 OOM——PyTorch 显存碎片化（大张量分配失败）的典型表现；处理：`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`（新版 PyTorch 支持）或降 batch 后重试——**碎片化 OOM 与预算不足 OOM 的区分**：预算不足是"报错时显存已满"，碎片化是"显存有空但块不连续"（`torch.cuda.memory_summary()` 看 large pool 分段）。

## 2. 显存泄漏：长跑隐性杀手

**症状**：训练 2 小时后显存缓慢爬升、最终 OOM——但起步时显存正常。**根因**：代码里的缓存未释放（自定义 dataset/tokenizer 缓存、日志累积、非训练张量被保留）。

**诊断**：周期性打印 `torch.cuda.memory_allocated()`（每 500 步记录显存趋势——**趋势**是泄漏信号，瞬时值不是）；对比每 step 显存是否单调增长；用 `torch.cuda.memory_summary()` 看哪类张量在增长。

**修复**：定位增长源（通常是自定义代码里的 list/tensor 累积）；`del` + `gc.collect()` 及时释放；**注意 LoRA 训练器某些版本有已知泄漏**（升级版本或用框架官方 trainer——自写训练循环是泄漏高发区）。修复后验证：训练 1-2 小时显存曲线平稳才算修好。

**显存峰值与"省显存套餐"**：启动时报 OOM 但运行正常（峰值出现在前向第一步）与运行中 OOM（激活值/状态累积）是两类问题——前者按第 1 节五步调，后者按本节约束排查。省显存套餐（按收益排序）：QLoRA（-75%）→ 梯度检查点（-30%）→ 8bit 优化器（-30% 优化器状态）→ 降 batch（-按比例）→ 降长度（-按比例）——**套餐组合可以叠加**，QLoRA + 检查点 + 8bit 优化器是单卡微调 7B-14B 的标准组合（`../完整微调工程流程/06-训练配置与启动.md` 02 节）。

## 3. 吞吐骤降与训练慢

**症状**：训练变慢（tokens/s 骤降）或整体偏慢。按序排查：

**dataloader 瓶颈（第一嫌疑）**：num_workers 不足（数据加载跟不上 GPU）——吞吐曲线看 GPU 利用率（利用率低 + CPU 满 = dataloader 瓶颈）；加 num_workers + persistent_workers；磁盘慢（数据在机械盘/网络盘）——数据先拷本地/SSD。

**GPU 利用率问题**：利用率 <60% 持续 = 有瓶颈（按上条查）；**温度过热降频**（利用率高但吞吐低——查温度，机房散热问题）；多卡场景查通信等待（NCCL 卡在同步——`nvidia-smi` 看其他卡是否空闲）。

**配置问题**：梯度检查点过密（每层都检查点比选择性重算慢得多）；packing 未开（padding 浪费算力，`../基础概念/06-训练循环Epoch-Batch-Step.md` 06 节）；max_seq_length 过大（大部分 padding）。

**预期管理**：先算理论吞吐（框架实测基准：QLoRA 7B 单卡约 1500-4200 tokens/s，`../完整微调工程流程/04-环境搭建与工具链选型.md` 01 节）——低于理论值 50% 才叫"慢"，别把正常速度当问题。

**慢的"收益排序"**：训练慢的优化按"投入产出"排——packing 开没开（一行配置，吞吐可能翻倍，第一优先级）→ 数据加载（num_workers/本地盘）→ 精度配置（bf16 混合精度）→ 框架切换（Unsloth 类加速框架，收益大但引入新依赖）——**先检查零成本配置项（packing/worker），再考虑换框架**；换框架是最后的选项（新依赖、新坑，`../完整微调工程流程/04-环境搭建与工具链选型.md` 02 节）。

## 4. 多卡问题

**症状**：多卡训练报 NCCL 错误、loss 不一致、吞吐不随卡数线性增长。常见根因：**NCCL 通信错误**（多任务共机 `MASTER_PORT` 冲突、网络防火墙、`NCCL_P2P_DISABLE` 需要时）；**显存不均衡**（某卡 OOM 其他卡空闲——数据不均/ZeRO 配置问题）；**吞吐不线性**（小模型 + 多卡的通信开销占比高——7B QLoRA 单卡就能跑，多卡收益有限，`../完整微调工程流程/06-训练配置与启动.md` 04 节）。

**诊断**：`nvidia-smi` 看各卡显存/利用率是否均衡；NCCL 报错看**具体 stage**（init/rank 相关 = 环境问题；allreduce 相关 = 通信问题）；loss 分卡记录对比（某卡 loss 异常 = 该卡数据/配置问题）。

**修复**：端口冲突改 `MASTER_PORT`（随机高位）；网络问题按 NCCL 文档调（`NCCL_DEBUG=INFO` 看通信日志）；模型小就不上多卡（单卡 QLoRA 是默认，`../完整微调工程流程/04-环境搭建与工具链选型.md` 03 节）。

## 5. 显存问题排查的共性

显存问题统一遵循"**先算账再调参**"：显存账本（权重/梯度/优化器状态/激活值四部分）先算清楚（`../基础概念/03-Transformer与参数基础.md` 05 节公式），再对账本逐项找"超支项"——OOM 在哪一步、哪类张量占最多，都从账本推得出来；**调参顺序 = 从账本里"最贵的项目"开始省**（QLoRA 省权重、梯度检查点省激活、8bit 优化器省状态）——顺序不是拍脑袋，是账本优先级的排序。

> 🎯 **核心要点**：OOM 五步按序（QLoRA→降 batch→检查点→降长度→换小模型），先看错误最后一行与 OOM 位置；显存泄漏靠趋势监控（memory_allocated 周期记录），自写训练循环是高发区；吞吐慢先查 dataloader（GPU 利用率低 + CPU 满）再查温度与配置（packing/检查点密度），先算理论值再判断"慢"；多卡查 NCCL stage 与卡间均衡，小模型别上多卡；一切显存问题"先算账再调参"——顺序 = 账本优先级。
