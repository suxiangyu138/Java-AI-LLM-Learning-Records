# 评估基础：损失曲线与过拟合

> "训练跑起来了"不等于"模型训好了"：训练 loss 与验证 loss 的分野、过拟合三信号、灾难性遗忘——评估能力是微调工程成熟度的分水岭

## 1. 训练 loss vs 验证 loss：两条曲线

训练日志里永远有两条 loss：**训练 loss**（模型在训练集上的损失）和**验证 loss**（模型在 held-out 验证集上的损失）。二者之差是整个评估体系的核心信号：

- 训练 loss 衡量"背没背下来"——只看它，模型背题会一直"表现良好"。
- 验证 loss 衡量"学没学会"——验证集样本模型没见过，测的是**泛化**（generalization）：对未见输入的正确反应能力。

**loss 曲线会欺骗**：训练 loss 平滑下降但验证 loss 停滞甚至上升，说明模型在记忆而非学习。所以评估纪律第一条：**验证集必须 held-out（与训练集严格隔离）且最好跨时段采样**（数据收集时间靠后的样本做验证，防止"同批数据泄漏"）——只用训练 loss 判断好坏，等于考试只做自己出的题。

## 2. 过拟合三信号

过拟合（overfitting）指模型记住了训练样本而非学习泛化规律。三个典型信号：

1. **训练 loss 逼近 0，验证 loss 不降反升**——最经典的背离曲线，train-eval gap 持续拉大。
2. **复读训练样本**：模型能一字不差背出训练集里的回答（问"你好"它背出"你好"那一条训练数据），对未见提问只会模式化套话。
3. **验证指标恶化**：下游任务指标（准确率/格式正确率）在某个 checkpoint 后下滑——loss 与任务指标不总同步，任务指标才是最终裁判。

触发条件（2026 共识）：**epoch 超过 3**（见 06 篇）、小数据集 + 大模型（容量远超数据需求，天然倾向记忆）、学习率过高（快速钻进训练集尖峰）。

对策按序：early stopping（验证 loss 连续 N 点不降即停）→ 降 epoch → 降学习率 → 加正则（weight decay、dropout；注意 2026 研究提示 LoRA dropout 在短训练里作为正则不可靠）。

## 3. 灾难性遗忘：微调的第一副作用

**灾难性遗忘**（catastrophic forgetting）：微调让模型在目标任务上变好的同时，**丢失了预训练学到的通用能力**——不会普通对话了、通用知识问答退化、指令遵循风格漂移。

高危条件与量级：**小数据 + 大模型 + 2 个 epoch 就可能发生**（数据 <1000 条时尤其高危——模型容量太大，全力拟合小数据集必然挤掉旧能力）。检测方法：微调前后跑同一组"通用能力测试题"（通用 QA、普通对话、风格样本）对比——只测目标任务不测通用能力的评估是**残缺评估**。

缓解手段：限制 epoch（1-2）、混入 ~10% 通用对话数据（见 08 篇）、低学习率（5e-5 量级保护旧权重）、LoRA 冻结底座天然免疫大部分遗忘、评估通用能力回测（不只在任务指标上验收）。完整止损框架（何时该停、窄有效窗口、遗忘检测）在边界判断体系 08 篇（`../边界判断（非常关键，面试必问）/08-失败信号与止损边界.md`）——概念层先建立"遗忘是真实的、可测的"这个认识。

## 4. 欠拟合与"训不动"的区分

与过拟合相对的另一端：**欠拟合**（underfitting）——训练 loss 和验证 loss 都偏高，模型没学到目标行为。信号：训练 loss 几乎不降、输出仍是底座原样。排查方向：数据量不足、学习率过低（或 warmup 过长浪费步数）、批次内样本差异过大（数据噪声）。

判断口诀：**两条曲线都高 → 欠拟合，加量/加时/加学习率；train 低 eval 高 → 过拟合，停/减 epoch/减学习率；两条都低 → 正常收敛**。多数微调踩坑案例是"后一种"——跑太久了。

## 5. 评估纪律：何时评、怎么评

2026 年实践共识：

- **不要等训练结束才评估**：第一个 checkpoint 后（训练 10-20% 处）就开评——早发现问题早止损。
- **eval_steps 100-500**：评估间隔太疏会错过最优 checkpoint 窗口。
- **自动保存最优**：`load_best_model_at_end=True` + `metric_for_best_model="eval_loss"` + `greater_is_better=False`——按验证 loss 自动挑最优，而不是按最后一个 checkpoint。
- **指标维度三件套**：验证 loss（收敛性）+ 任务指标（目标达成）+ 通用能力回测（遗忘检测）——缺一不可。

**2026 开放问题**：Baseten 研究指出"验证 loss 是否忠实排序下游质量"仍是活跃研究问题（loss 平坦度与任务指标的关系未完全清楚）——所以任务指标（业务效果）永远优先于 loss 数字。实际例子：JSON 输出任务里两个 checkpoint 的验证 loss 只差 0.01，但 JSON 解析成功率可能差 10 个百分点——**业务指标对格式类任务的区分度远高于 loss**，评估必须绑定业务指标而不是只看 loss 曲线。

## 6. 评估集设计的三个原则

评估集怎么切，直接决定评估结果可不可信，三个原则缺一不可：

**严格隔离**：验证集与训练集必须零重叠。尤其注意去重——从公开数据集取数时先做全局去重（相似样本用 minhash 或嵌入相似度排查），否则"验证 loss 漂亮"其实是"背过的题又考了一遍"。训练日志里的 eval 若与训练数据同源（如从同一批导出），结果是假的。

**跨时段采样**：按时间切分——用收集时间靠后的数据做验证集。生产场景中模型会遇到"未来"的输入，跨时段验证才能暴露"只拟合过去"的问题。时序数据的反例：随机切分会把未来的信息泄漏进训练集。

**困难样本分层**：验证集要包含边缘与困难样本（长尾格式、罕见实体、对抗性提问），不能只挑"答得对的容易题"。只评容易样本会让验证 loss 漂亮但生产效果崩——评估集的困难度分布要向真实请求分布靠拢。

评估集的质量决定评估结论的质量：**评估集就是微调的"考试卷"，出卷人偷懒，考生分数就没有意义**。

> 🎯 **核心要点**：训练 loss 测"背没背下来"，验证 loss 测"学没学会"，验证集必须 held-out 且跨时段；过拟合三信号 = train→0 + eval 背离 + 复读；灾难性遗忘 = 小数据+大模型 2 epoch 高危，必须做通用能力回测；评估纪律 = 10-20% 处开评 + load_best_model_at_end + 指标三件套——"loss 降"只是必要条件，不是成功证明。
