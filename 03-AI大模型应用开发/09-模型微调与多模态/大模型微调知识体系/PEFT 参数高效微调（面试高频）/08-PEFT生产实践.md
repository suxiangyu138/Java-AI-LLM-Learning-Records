# PEFT 生产实践

> 适配器即产品：合并 vs 多 LoRA 两条部署路径、适配器生命周期管理（staging → production）、热切换与版本治理——PEFT 的生产形态与全量完全不同

## 1. 两条部署路径

LoRA 适配器的部署有两条路（`../完整微调工程流程/09-导出部署与上线运维.md` 01 节的选型在此展开）：

**路径 A：合并进底座**（merge_and_unload）——W₀ + ΔW 写回一个完整模型——单模型服务最稳（NVIDIA 2026 实测 merge-then-serve 最可靠）、推理零开销；**硬前提**：float16 加载底座合并（4bit 合并损精度）、合并不可逆（回退从原始底座重来）、合并后必须重验（`../完整微调工程流程/09-导出部署与上线运维.md` 02 节）。

**路径 B：动态多 LoRA 服务**——底座常驻显存、适配器按请求热挂——**一个底座服务几十个微调变体**（适配器 0.1-1% 大小）；推理开销 2-5%；**vLLM 硬约束**：`enable_lora=True` + 适配器预注册（LoRARequest）+ **modules_to_save 必须为 null**（全秩张量 vLLM 运行时不支持，`../微调常见问题/02-模板与格式类问题.md` 的模板坑之外最常见的部署坑）。

**选型判据**：单一模型 → 合并（简单可靠）；多变体/频繁迭代 → 动态多 LoRA（**白得秒级回滚**：回滚 = 切适配器版本，比合并模型重部署快一个量级）；混合：主线合并、试验变体动态挂。

## 2. 适配器生命周期管理

适配器作为"产品资产"的治理（2026 生产标准，与 `../数据集体系（非常重要）/09-数据版本管理与合规治理.md` 的版本治理同构）：

**四态推进**：staging（训练产物，未验证）→ shadow（影子对比，与线上并行验证）→ production（灰度通过，正式服务）→ archived（退役归档）——**状态机让"哪个适配器在线上"永远可查**（`../完整微调工程流程/09-导出部署与上线运维.md` 04 节的 AdapterRegistry 实践）。

**注册表信息**：适配器 ID、底座版本、数据版本（manifest 引用）、训练指标（loss/eval_loss）、评估分数、灰度结果、负责人——**一个适配器一条记录**，上线问题五秒定位"这个适配器哪来的、用的什么数据"。

**保留与清理**：生产中的适配器永久保留（审计要求）；试验版本滚动清理（保留策略与数据版本一致，`../数据集体系（非常重要）/09-数据版本管理与合规治理.md` 02 节）。

## 3. 热切换与灰度

多 LoRA 架构的运维红利：

**热切换**：适配器切换不重载底座（常驻）——**业务侧按路由规则选适配器**（用户分群、A/B 分流、版本灰度）——灰度就是"把 X% 流量路由到新适配器"（`../完整微调工程流程/09-导出部署与上线运维.md` 04 节的灰度五档落地形态）。

**回滚**：问题适配器从路由表摘除——秒级生效（合并模型需要重新部署，分钟级）——**多变体架构的运维弹性是 PEFT 生产友好性的核心**。

**注意**：**适配器与底座的版本耦合**——适配器训练时的底座版本与服务时的底座版本必须一致（换底座 = 适配器需重训或重验证——"底座升级"是 PEFT 生产的第一大变更风险，升级后全量回归适配器）。

## 4. 多适配器共存的工程细节

**显存预算**：每多一个适配器显存增加（r=64 的 7B 适配器约 15MB 级，`../完整微调工程流程/09-导出部署与上线运维.md` 03 节）——适配器数量 >50 时注意延迟与显存裕量（按 10-15% 裕量预算）。

**名称与路由规范**：适配器命名（业务语义：`finance-v3` 而非 `lora-20260810`）；路由键与适配器映射进配置中心（改动走配置发布而非改代码）。

**冲突管理**：**同一底座的多个适配器互不干扰**（各自的 ΔW 独立）——但同一请求不能同时挂两个适配器（要么合并为多适配器叠加，要么按路由二选一）——"叠加"有研究（模型合并/融合方向）但生产默认单选。

**适配器与 RAG/Agent 的配合**：多 LoRA 架构天然适配"按场景切换"的生产形态——**Agent 场景可以按任务类型挂不同适配器**（客服格式适配器 + 代码适配器按路由分发）；与 RAG 组合时（`../PEFT 参数高效微调（面试高频）/09-PEFT选型与边界.md` 04 节）适配器管"检索结果如何组织成回答"——**路由粒度 = 业务粒度**：按业务线/按任务类型/按用户分群，路由规则与适配器一一对应，改动走配置中心。

## 5. 合并流程的工程化

合并不是"训完顺手跑一下"，要按变更管理走（`../完整微调工程流程/09-导出部署与上线运维.md` 02 节）：**导出四步**（加载 tokenizer → float16 加载底座 → merge_and_unload → 保存完整模型 + tokenizer + export_metadata）。

**合并后模型体积**：7B 合并产物 ≈ 14GB（float16）——比适配器（15MB）大三个数量级——**存储与分发成本是合并路径的隐藏代价**（多 LoRA 架构 15MB vs 合并 14GB/变体，`../PEFT 参数高效微调（面试高频）/07-PEFT显存与性能.md` 05 节的存储对比在此落地）。

**合并后必验**（重跑验收冒烟——checkpoint 选择差异是离线与线上不一致的来源）；**导出记录进注册表**（适配器版本 → 合并模型版本的映射，回滚时能对应回适配器）。

## 6. PEFT 生产检查清单

上线前的 PEFT 专项检查：**合并正确性**（float16 加载/合并后重验）；**多 LoRA 兼容**（modules_to_save null/适配器预注册/名称规范）；**底座版本一致性**（训练与服务的底座同版本）；
**生命周期状态**（staging→production 的推进记录完整）；**回滚预案**（路由摘除演练过——"没演练过的回滚预案等于没有预案"，`../完整微调工程流程/09-导出部署与上线运维.md` 04 节）；**评估走服务路径**（`../完整微调工程流程/08-模型评估与验收.md` 03 节）——六项全过才上线。

> 🎯 **核心要点**：两条部署路径——合并（float16/不可逆/单模型最稳）vs 多 LoRA（modules_to_save null/预注册/秒级回滚），多变体选多 LoRA、单模型选合并；适配器生命周期四态（staging→shadow→production→archived）+ 注册表（底座/数据/指标/灰度全记录）；热切换 = 路由控制（灰度与回滚都靠路由表）；底座升级是第一变更风险（升级后全量回归适配器）；合并流程按变更管理（四步 + 重验 + 导出记录）；上线六查（合并正确/多 LoRA 兼容/底座一致/生命周期/回滚演练/服务路径评估）。
