# 10-生产实践与面试冲刺

> 定位：把前九篇收束成可执行的工程清单与可背诵的面试弹药。本文给出端到端生产检查单、故障排查表、适配器治理规范与 12 道高频面试题。

## 端到端生产清单

1. **场景判定**：任务是否落在预训练能力内（复用为主）→ 是则 LoRA；全新知识领域 → 考虑全参 SFT。
2. **环境钉版本**：Python 3.10+、peft 0.19.x、transformers 5.x、trl 0.15.2+、bitsandbytes 0.49.x；GPU 规格决定 QLoRA vs LoRA。
3. **数据工程**：去重 + 污染检查；窄任务 500-1000 条、通用 5k-10k；序列长度取 95 分位。
4. **配置基线**：r=16/α=16、全 7 个线性层、bias=none、LR SFT 2e-4（RL 5e-6）、warmup 3-10% + cosine、adamw_8bit。
5. **训练**：先 1 epoch 冒烟（验证 loss 下降、适配器权重真在变——checksum 验证），再全量；开 gradient checkpointing。
6. **评估**：任务指标 + 通用能力回测（灾难性遗忘检测）+ 对抗样本抽查（对齐是否被破坏）。
7. **交付选型**：单任务 → merge 分发；多任务 → vLLM 多适配器（--lora-modules + 运行时更新）。
8. **适配器治理**：命名规范（task-version-date）、适配器注册表（底座版本+超参+数据 hash 三要素）、第三方适配器只信签名来源。
9. **监控**：推理侧按适配器维度统计 QPS/延迟/质量指标；多适配器平台盯 LRU 逐出率（逐出率高说明池容量不足）。
10. **复盘**：记录 r/α/use_rslora/loftq/LR 五项元数据，缺失即不可复现。

## 故障排查表

| 现象 | 第一怀疑 | 定位步骤 |
|---|---|---|
| loss 不降 | 数据未套 chat template | 检查 tokenize 后样本首 token 与标签错位 |
| loss 降但评估差 | 过拟合/遗忘 | 查验证集与训练集 overlap；降 epoch 或数据去重 |
| 效果"不如基座" | 适配器没训上 | checksum 验证 A 权重；确认 target_modules 拼写 |
| 训练 OOM | batch 过大 | 先 batch=1 + 累积；开 checkpointing；确认未误挂 modules_to_save |
| merge 后行为突变 | 变体合并精度 | DoRA 需 peft ≥ 0.10；尝试 fp32 临时精度合并 |
| 加载适配器报 key 错 | 底座不匹配 | 核对 config 的 base_model_name 与 tokenizer 完全一致 |
| 多适配器 QPS 抖动 | LRU 逐出 | 扩容 GPU 缓冲或降适配器驻留尺寸 |
| QLoRA 加载静默失败 | bnb 版本不匹配 | 检查检查点内版本元数据，锁定 bnb 版本 |

## 适配器生命周期管理

生产环境的适配器要当"软件制品"管理而非"权重文件"。完整生命周期：**注册**（入库登记：底座版本、peft 版本、r/α/use_rslora/loftq/LR 五项元数据、训练数据 hash、评估报告链接）→ **准入**（过安全评估清单 + 任务评估 + 通用通道评估，全绿才发布）→ **灰度**（多适配器服务里按比例放流量，逐适配器监控质量指标）→ **监控**（每适配器维度的 QPS/延迟/质量指标，异常自动摘除）→ **退役**（下线并归档元数据）。两个易被忽视的环节：**适配器版本化**——同名适配器迭代必须走新版本号，禁止覆盖旧文件（回滚依赖它）；**底座升级联动**——底座模型升级（如 8B→8B-instruct）后所有适配器需重跑准入测试，低秩适配器对底座敏感，不能假设兼容。这套管理占生产工作量的一半以上，但缺了它，LoRA 的"低成本"会变成"低质量上线"。

## 经典故障案例复盘

**案例一：QLoRA 训练 loss 0.8 不动**。排查发现数据未套 chat template，标签直接对齐了纯文本，模型在"猜角色名"而非"学回复"。修复数据管线后 loss 降至 0.3 区间。教训：loss 不降先查数据格式，再查超参——顺序反了浪费一周。

**案例二：r 从 8 提到 32 效果反而下降**。回查代码发现 α 仍为 8（原 α/r=1.0，改后 0.25），有效缩放缩水四倍。修复 α=32 后效果随秩提升。教训：α 必须随 r 同调，比例先钉死。

**案例三：多适配器服务 QPS 周期性掉 50%**。监控显示掉点时刻与 LRU 逐出时刻重合——适配器池容量 10，线上实际 40+ 个适配器轮转，每个请求都触发逐出加载。扩容 GPU 缓冲并把冷适配器改为"加载即锁"后恢复。教训：容量规划按"峰值激活数"而非"适配器总数"。

**案例四：合并后模型输出与适配器版不一致**。核对发现 PEFT 版本 0.9（DoRA 合并 bug 时代），升级到 0.19 后一致。教训：变体合并有版本下限，发布清单必须包含 peft 版本。

## 面试 12 题（含答题范式）

1. **LoRA 的核心公式与为什么低秩安全** → W₀x + (α/r)BAx；内在低秩假设 + B 零初始化收敛域重叠。
2. **r 与 α 怎么选** → 先钉比例（1.0/2.0）再调 r；16 甜点；显存随 r 线性。
3. **为什么 B 零初始化 A 随机** → 初始 ΔW=0 不扰动预训练；梯度经 B 回流防止首步爆炸。
4. **LoRA vs Adapter vs Prompt Tuning** → 改动位置（权重旁路 vs 结构 vs 输入）与可合并性是分水岭。
5. **QLoRA 三件套** → NF4 分位量化、双重量化、分页优化器；各省什么。
6. **LoRA 与全参微调的本质区别** → 可训练参数子空间受限但覆盖低秩流形；全参在高维冗余空间中移动。
7. **DoRA 为什么在 RL 中胜出** → 幅度/方向解耦让"学多大量"与"学哪方向"独立，RL 优化对方向更敏感。
8. **PiSSA 的失败模式** → RL 谱坍缩：主分量方向与 RL 优化需求错位；LR 需降约 10 倍。
9. **merge 与动态服务怎么选** → 单任务零开销 vs 多任务共享底座；Punica 内核解决批处理分片。
10. **多适配器服务的显存模型** → 驻留按"同时激活数"而非总数；LRU 逐出兜底。
11. **LoRA 能做什么不能做什么** → 能做：风格/指令/领域适配；不能：全新知识注入、超高维推理（提秩或全参）。
12. **LoRA 的安全风险** → 对齐失效（CSULoRA 校正）、后门投毒、供应链验证；适配器是代码。

## 加分深度题（拉开差距）

**Q：LoRA 的参数量与显存关系，能现场算吗？** 能：可训练参数 ≈ 2×r×Σ(挂载层 d_in×d_out)；7B 全层挂载 r=16 约 0.2% 可训练比；Adam 状态 12 字节/参数，优化器显存 ≈ 0.2%×7B×12B ≈ 0.17GB。全参则是 84GB——"三个数量级"要能脱口而出。

**Q：为什么 QLoRA 比 LoRA 慢但流行？** 慢：4-bit 反量化每次前向展开（慢 10-30%）；流行：显存降 3.2 倍，让消费卡可训。回答要点是"显存是硬约束时 QLoRA，否则 fp16 LoRA"，以及"探索用 QLoRA、定稿用全精度"的分阶段策略。

**Q：多 LoRA 服务为什么能"显存不随适配器数增长"？** 因为权重驻留在共享池、按需加载 + LRU 逐出，池容量固定；激活值只与同时激活的适配器数相关。对比"每适配器一个副本"方案的 N 倍显存。

**Q：如何检测"微调中毒"的适配器？** 触发测试（越狱/恶意样本对比启用/禁用差异）、后门探测（功能域外异常输入）、来源审计（hash/数据公开对照）、合并产物重测。

## 面试答题节奏建议

LoRA 相关面试题的考察本质是三件事：**底层原理是否真懂**（公式、初始化、为什么低秩安全——用 01/02 篇的内容组织回答）、**工程经验是否有细节**（超参、显存账、报错——用 03/04/06 篇的排查表佐证）、**选型判断是否成熟**（何时全参、何时 QLoRA、何时多适配器服务——用 05/07 篇的决策树）。答题节奏建议：原理题答 30 秒直击核心公式与一句话直觉，再展开论证；工程题先给结论（基线配置）再给反例（什么情况不行）；选型题用"分场景回答"结构——面试官要的不是唯一答案，而是你是否有条件化的判断框架。把本体系的决策树、速查表、排查表背熟，足以覆盖 95% 的 LoRA 面试题。

## 面试速记

1. LoRA = 冻结 W₀ + 低秩增量 BA，缩放 α/r，可 merge 零开销。
2. 默认 r=16/α=16 全线性层 + LR 2e-4，就处于 95% 性能区间。
3. 变体选型一句话：SFT 调 vanilla 的 LR，RL 换 DoRA，PiSSA 只在 SFT 快速验证。
4. QLoRA 让 7B 在 8GB 卡可训；FSDP 大模型钥匙是 bnb_4bit_quant_storage。
5. 多适配器服务 = 单底座 + Punica 内核 + LRU 缓存，容量看同时激活数。

> 🎯 **核心要点**：生产的最后一公里是治理——版本、元数据、信任边界三件事。训练能跑通只是起点，可复现、可追溯、可回滚的适配器生命周期管理，才是 LoRA 工程化与"跑 demo"的分界线。
