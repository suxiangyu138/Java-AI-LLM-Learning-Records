# 上下文与工程缺陷

> 多模态的"使用成本"问题：图像 token 超长、多图限制与集成失败、延迟、缓存、流式——工程缺陷决定"模型能不能用"，不是"模型好不好"

## 1. 图像 token 的算账

**图像进上下文 = token 消耗**：一张图被切分/编码成**数百到上千个 token**（取决于分辨率与模型——典型 256-1024+ token/图，高分辨率更多）——**"一张图顶几千字"**（文本 1000 token 的上下文，图 1 张就占掉）。

**成本与限制的连锁**：**上下文窗口消耗**（长文档 RAG 的"多证据 + 多图像"轻松超窗口——`多模态/多模态 RAG/08-多模态RAG工程实现.md` 的"上下文超长事故"）；**成本**（图像 token 的推理成本按 token 计——多图请求的成本是文本请求的数倍）；**性能**（长输入 = 长 prefill = 高延迟，08 篇）。

**工程含义**：**图像数量与尺寸要预算**（每请求最多 N 图、图像缩放/压缩——`多模态/多模态 RAG/08-多模态RAG工程实现.md` 的集成要点）；**"先文本后图像"的降级设计**（图像证据用文本描述替代（双表示，`多模态/多模态 RAG/06-表格与图表RAG.md`）——预算超限时降级为描述）。

**图像 token 的"看不见的成本"**：**图像 token 与文本 token 的计算成本不等价**（图像 token 走视觉编码路径——计算量远高于文本 token 的 embedding——"1 个图像 token ≈ 数个文本 token 的计算成本"）——**"token 数"不是成本的完整度量**（按"计算量"而非"token 数"预算）；**低效图像**（大尺寸 + 小内容——空白多/内容集中一角）是常见的隐性浪费——**"裁剪去边 + 缩放"是图像预处理的第一道成本优化**（`多模态/多模态 RAG/` 的预处理方法论在此复用）。

## 2. 多图限制与集成失败

**多图输入的问题分两类**：

**硬限制**：模型/服务对单请求图像数量的上限（服务端限制、上下文窗口限制）——超出报错或截断；**软失败**：多图时**集成能力下降**（03 篇 MIOH：跨图表征绑定失败——图 A 的物体被安到图 B；回答只引用其中一张图——**"给了 3 张图，模型只看 1 张"**）。

**工程应对**：**逐图标注**（每张图编号 + 图例说明——"图 1：产品 A 的正面"——帮助模型绑定）；**逐图提问**（复杂多图任务拆成单图问答再合并——降低集成负担）；**证据引用强制**（"回答必须注明引用图号"——绑定失败的对抗）；**多图高风险的预判**（对比类/长文档多页类任务——默认加引用与编号保障，06 篇）。

## 3. 延迟：多模态的 SLA 难题

多模态生成的延迟构成（`多模态/多模态 RAG/08-多模态RAG工程实现.md` 的延迟数据）：**图像 token 处理 +1.5-3 秒**（对比文本管线 P95 800ms-1.5s）——**"子 2 秒实时对话 SLA"与多模态生成冲突**——延迟的来源：图像编码（prefill 长）、高分辨率处理、多图串行。

**延迟的工程对策**：**分层响应**（先回文本骨架、图像/详细内容流式补——`多模态/多模态 RAG/` 的降级设计）；**图像缓存**（同一图像重复请求不重复编码——`多模态/多模态 RAG/08-多模态RAG工程实现.md` 的 base64 vs URL 引用）；**分辨率按需**（低分辨率先答、高分辨率按需重试——"先粗后精"的多模态版）；**延迟敏感交互文本优先**（查询路由的延迟感知——`多模态/多模态 RAG/05-多模态RAG架构设计.md`）。

## 4. 流式与交互缺陷

**流式（SSE/流式输出）的多模态问题**：文本流式成熟（逐 token），但**图像输出不能流式**（图像是整体生成——"图流式"不可行，只能"生成完成再发"）；**混合输出**（文本流式 + 图像后发——时序编排的工程问题）；**中断/重试**（流式中断后的图像状态管理）。

**多轮对话的视觉衰减**：**长对话中早期图像被"遗忘"**（06 篇的视觉接地随距离衰减）——"第一轮发过图，第三轮问图里的细节"——模型可能答错（视觉衰减）——**对策**：**关键图像重发**（每轮携带相关图——token 成本换准确率）或**图像摘要持久化**（对话状态里存图像的结构化摘要——"图 1 的关键事实"——低成本的重接地）。

## 5. 缓存与成本治理

多模态的缓存与成本（`多模态/多模态 RAG/08-多模态RAG工程实现.md` 的成本账延伸）：

**图像级缓存**：相同图像（同一 URL/base64 哈希）的编码结果缓存——重复请求省编码成本（多模态应用的常见重复：同一文档页被多次问）；**前缀缓存**（prompt caching——图像 token 在固定前缀里可缓存——`02-大模型基础与Prompt工程/` 的缓存方法论对图像 token 同样适用）；**成本监控**（每请求 token 构成（文本/图像比例）——"图像 token 占比"是成本告警指标——图像超预算 = 应用在烧钱）。

**降级策略矩阵**（成本/质量权衡）：图像 → 文本描述（双表示降级）；多图 → 单图（优先级选择）；高分辨率 → 低分辨率（按需重试）；检索证据 → 精简（Top-1 而非 Top-5）——**"预算内最优质量"是降级设计的统一目标**。

## 6. 工程缺陷的评估与监控

工程缺陷的监控指标（与模型质量指标分开）：**token 构成**（图像 token 占比——成本与延迟的先行指标）；**延迟分解**（编码/检索/生成三段——定位瓶颈，`多模态/多模态 RAG/08-多模态RAG工程实现.md` 的延迟预算）；
**多图成功率**（多图请求的完成率与引用正确率——集成失败的可观测化）；**降级触发率**（降级策略实际触发的比例——触发过多 = 预算或上下文配置不合理）——**"工程健康度"与"模型质量"是两个独立监控面**（模型再好，工程缺陷让应用不可用）。

> 🎯 **核心要点**：图像 token 算账——一张图 256-1024+ token（顶几千字），上下文/成本/延迟三连锁——图像数量与尺寸要预算；多图两类问题——硬限制（服务/窗口上限）与软失败（集成能力下降、跨图绑定失败）——逐图标注/逐图提问/引用强制；延迟——图像处理 +1.5-3s 与子 2 秒 SLA 冲突——分层响应/图像缓存/分辨率按需；流式——图像不能流式（整体生成）、长对话视觉衰减（关键图重发/摘要持久化）；缓存与成本——图像级缓存/前缀缓存/图像 token 占比监控/降级策略矩阵（预算内最优质量）；监控——token 构成/延迟分解/多图成功率/降级触发率——工程健康度与模型质量是两个独立监控面。
