# 多模态 RAG 工程实现

> 从架构到落地：工具链全景（Qdrant 多向量/Visual RAG Toolkit）、成本账（ColPali $0.01-0.05/页 vs OCR $0.001）、规模化与 Java/Spring AI 集成——"组装而非造轮子"

## 1. 工具链全景（2026）

多模态 RAG 的"组装件"（01 篇的生态闭环在此展开）：

| 环节 | 工具 |
|------|------|
| 文档解析 | Docling / MMORE（15+ 文件类型） |
| 视觉检索模型 | ColPali 家族（ColSmol-500M 轻量 / ColPali-v1.3 / ColQwen） |
| 图像嵌入 | CLIP / SigLIP |
| 音频转写 | Whisper（说话人标签 + 时间戳） |
| 向量库（多向量） | Qdrant（命名向量 + prefetch+query 多阶段）/ Milvus |
| 重排 | BGE-reranker-v2 / Cohere Rerank 3（跨模态） |
| 生成 | Qwen-VL / GPT-4o 类 VLM |
| 检索效率 | Visual RAG Toolkit（池化 + 多阶段） |

**选型原则**：**能用开源先用开源**（ColSmol-500M 单消费卡可跑、MMORE 开源管线）；**规模化瓶颈在向量库**（多向量检索需要"命名向量 + 多阶段查询"能力——Qdrant 的 prefetch+query API 是 2026 实测路径，08 篇第 4 节）。

**工具链的"三选"决策**：每个环节三选——开源自建（可控、要运维）、云服务（省运维、数据出境问题——`03-AI大模型应用开发/` 的私有化考虑）、托管平台（RAG 平台类——快但锁定）——**选型判据**：数据敏感度（私有数据 → 开源自建）、团队运维能力、预算——**"多模态 RAG 的 90% 工作是数据与运维，不是模型"**（模型是组装件，数据管道与治理才是工作量主体——与 `../大模型微调知识体系/数据集体系（非常重要）/` 的结论同构）。

## 2. 成本账：全量视觉化的真实代价

ColPali 类视觉索引的成本（与 OCR/文本对比，2026 实测）：

| 项 | ColPali 视觉索引 | OCR/文本管线 |
|------|:---:|:---:|
| 摄入成本 | $0.01-0.05/页 | ~$0.001/页 |
| 摄入速度 | 2-5 秒/页 | 快（数量级） |
| 存储 | 每页 ~1000 个 128 维向量 | 每页 1 个向量 + 文本 |
| 索引规模 | 100 万页 ≈ 10 亿向量 | 100 万页 ≈ 百万向量 |

**百万页文档的账**：视觉索引 ≈ 10 亿向量（需 PLAID 类压缩索引或量化）+ 摄入成本 $1-5 万——**"全量视觉化"不是默认选项**。

**2026 解法：选择性视觉化**——**按页面复杂度路由**：纯文本页走 OCR/文本索引（$0.001/页）、图表页走 ColPali（$0.01-0.05/页）——**混合索引把成本降一个数量级**（先版面分析分类页面，再按类路由——05 篇摄入路由的成本落地）；**再加池化压缩**（Visual RAG Toolkit：每页千级向量 → 数十级，存储降 8-10 倍、吞吐 4 倍——03 篇）。

## 3. 规模化：百万页文档的工程

**索引管线**：文档 → 版面分析（页面分类）→ 分流（文本/视觉）→ 并行摄入 → 证据图入库——**吞吐规划**：ColPali 2-5 秒/页 → 百万页 ≈ 70-140 小时（单机）——**并行摄入**（多卡/多机分片，`04-向量数据库/` 的摄入管道方法论）与**增量更新**（只重索引变更页，04 篇）是规模化的两个必备。

**向量库选型**：多向量检索需要"**每个文档多组向量 + 组内检索**"能力——Qdrant 命名向量（一个点存多组向量）与 prefetch+query（先粗后精两阶段）是 2026 实测路径；Milvus 的 group 检索同类能力——**"先粗后精"（pooled 预取 + 精确重排）是规模化检索的标准形态**（03 篇的多阶段检索在工程上的落地）；**量化**：多向量场景向量量化（标量/乘积量化）降存储（`04-向量数据库/` 的压缩方法论）。

## 4. Java/Spring AI 集成

Java 生态接入多模态 RAG 的三层（`02-.../06-Spring全家桶/Spring AI/` 的 RAG 方法论在此多模态化）：

**模型层**：Spring AI 的 ChatClient 接 VLM（Qwen-VL 类，图像输入支持——`mcp 工具` 与 `Advisor 链` 的既有能力）；**检索层**：向量库客户端（Qdrant/Milvus 的 Java 客户端——多向量检索的 API 调用）或自建检索服务（Python 侧做视觉检索，Java 侧 HTTP 调用——**"检索服务化"**：视觉检索的模型生态在 Python，Java 通过 OpenAI 兼容端点/专用 API 消费）；**编排层**：Spring AI 的 Advisor 链实现"查询路由 → 多通道检索 → 重排 → 组装"（`RagQuestionAnswerAdvisor` 的多模态版——自定义 Advisor 把图像证据注入上下文）。

**集成要点**：**图像进上下文的格式**（base64 或 URL——Spring AI 的 Message 内容类型支持图像）；**重排服务的接入**（cross-encoder 在 Python 侧，Java 消费）；**证据元数据透传**（坐标/时间戳/权限随证据传给应用层——05 篇证据图的 Java 侧数据结构）。

**集成的事故预防**（多模态 RAG 的 Java 侧常见坑）：**上下文超长**（图像 token 远多于文本——一张图 ≈ 数百到上千 token——"多证据 + 多图像"轻松超上下文窗口——**证据数量与图像尺寸要预算**（每请求最多 N 图，超出降级为文本描述）；**base64 与 URL 的缓存**（同一图像重复请求避免重复编码——URL 引用优于内联 base64）；**权限校验位置**（证据的权限检查在应用层做——"检索到了但用户无权看"的拦截，`09-多模态RAG评估与挑战.md` 05 节的多模态安全在此落地）。

## 5. 检索服务的部署形态

**模型部署**：ColPali 类视觉检索模型部署为**专用检索服务**（TEI 类推理端点或 vLLM 兼容端点——`多模态/推理部署工程/` 的部署方法论）；轻量模型（ColSmol-500M）可嵌入应用进程；**向量库独立部署**（`04-向量数据库/` 的部署实践）。

**延迟预算**：多模态检索链路（路由 + 多通道 + 重排）比文本 RAG 多 1.5-3 秒（图像 token 处理，`09-多模态RAG评估与挑战.md` 的延迟数据）——**"子 2 秒实时对话 SLA"与多模态生成冲突**（文本管线 P95 800ms-1.5s vs 多模态 +1.5-3s）——**延迟敏感的交互用文本通道优先、视觉兜底**（查询路由的延迟感知）。

## 6. 工程验收清单

多模态 RAG 上线的工程检查：**成本预算**（选择性视觉化后的每页成本 ≤ 预算——先算账再摄入）；**吞吐达标**（摄入吞吐按排期——并行度够不够）；**检索延迟**（P95 在 SLA 内——路由/多通道/重排各环节计时）；
**证据可追溯**（检索结果带证据图元数据——坐标/来源/权限）；**增量更新跑通**（解析器升级/文档更新 → 增量重建验证）；**回滚路径**（检索服务/向量库的版本回退）——六项全过才上线（与 `../大模型微调知识体系/完整微调工程流程/` 的门禁纪律同构）。

> 🎯 **核心要点**：工具链组装件（解析 MMORE/检索 ColPali/向量库 Qdrant 多向量/重排跨模态/生成 VLM）；成本账——ColPali $0.01-0.05/页 vs OCR $0.001/页、每页千级向量——**选择性视觉化**（版面分类后按页路由）是成本解药、池化压缩是存储解药；规模化三件（并行摄入/增量更新/先粗后精检索）；Java/Spring AI 三层接入（ChatClient 接 VLM/检索服务化/Advisor 编排）——视觉检索生态在 Python，Java 消费服务；延迟预算（多模态 +1.5-3s，延迟敏感用文本优先）；工程验收六查（成本/吞吐/延迟/追溯/增量/回滚）。
