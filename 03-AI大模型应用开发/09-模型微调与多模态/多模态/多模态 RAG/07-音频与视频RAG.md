# 音频与视频 RAG

> 音视频检索的 2026 现状：音频"转写优先"是默认（Whisper）、说话人标签与时间戳、视频检索的关键缺口（时间线被忽略）、原生音频检索的新兴方向

## 1. 音频 RAG 的两条路线

音频检索有两条路线（2026 现状）：

**转写优先（Transcription-first）**：音频先 ASR 转文本 → 文本 RAG（标准管线）——**默认方案**：Whisper 类模型转写（干净英文 WER <5%），转写文本分块、嵌入、检索——**"音频变成文本再检索"**。

**原生音频检索（Native audio retrieval）**：音频波形直接嵌入（与文本同空间，WavRAG 类双模态编码）——保留语气/音调/背景音等转写丢失的信息——**2026 仍未产品化**（主流框架不原生支持）——**现状结论：转写优先是工程默认，原生是研究前沿**。

**转写的丢失**：说话人身份、语气、强调、背景音——**"谁说的"和"怎么说"在转写里消失**——解决：转写时带**说话人标签（speaker diarization）与词级时间戳**（Whisper 的对齐输出）——"声音的元数据"补回转写丢失的部分。

## 2. 音频 RAG 的工程形态

2026 生产实践（音频检索的标准配方）：

**摄入**：音频 → Whisper 转写（说话人标签 + 词级时间戳）→ 文本块索引 + **原音频片段引用**（每块带时间戳区间与源音频 URI）——**"检索文本、返回音频"**：检索命中文本块 → 回答时引用对应时间戳的原音频（证据可听）。

**回答**：检索到的文本块 + 原音频片段交给**原生音频 LLM**（GPT-4o、Gemini 1.5 Pro 类——能直接听音频）做最终推理——"转写用于检索、原音频用于推理"（与图表的"描述用于检索、原图用于回答"同构——06 篇双表示思想在音频上的延伸）。

**场景**：会议纪要（"上周周会说了什么决策"）、播客检索、客服录音 QA（"客户投诉了什么问题"）——**音频 RAG 解决"语音内容可检索"**，配合说话人标签可以答"谁说的"。

## 3. 视频 RAG：关键缺口

视频 = 视觉流 + 音频流 + **时间线**——2026 视频 RAG 的现状与缺口：

**常用做法**：**帧抽取 + 视觉检索**（关键帧/片段用 CLIP 类嵌入——"找画面"）；**音频转写 + 文本检索**（对白/解说——"找内容"）；**双塔**（Wav2Vec2.0 音频分支 + CLIP/ViT 视觉分支——"音画联合"）——**检索单元**：视频片段（带时间区间）而非整条视频。

**关键缺口**：**时间线信息被忽略**——检索时"第几分钟发生了什么"（时序依赖）通常不参与索引（ACL 2026 调研确认）——"先讲结论后讲原因"的因果顺序在片段化检索中丢失；**多轮对话/跨片段推理**（"这个方案在第三次讨论时怎么变的"）需要时序建模——**视频 RAG 的下一步是"带时间线的检索"**（片段元数据 + 时序感知的重排/推理）。

## 4. 音视频的元数据设计

音视频检索的元数据（05 篇证据图的音视频版）：**时间戳区间**（检索返回"第 12-15 分钟"——可跳转定位）；**说话人标签**（谁说的——会议/访谈场景的核心维度）；**源引用**（原音频/原视频片段 URI——证据可听可看）；**场景标签**（视频的镜头/章节——"介绍"、"演示"、"问答"）；**转写来源版本**（ASR 模型版本——转写错误可追溯，04 篇的 parser 版本纪律）。

**元数据的查询价值**：时间戳让"回到证据"可行（文本 RAG 只有文字引用，音视频 RAG 有"可播放的证据"）；说话人标签支持"谁说了什么"类查询——**"元数据即检索维度"**（音视频 RAG 的检索不只是相似度，还有时间/说话人/场景的过滤——混合检索的音视频版）。

**音频检索的"转写错误传播"**：转写 WER 是音频 RAG 的地基误差——**"转写错了，检索与回答都建立在错的内容上"**——两类错误的影响不同：**替换错误**（同音词"账户/帐户"——检索可能仍命中）vs **关键信息错误**（数字/人名/产品名——检索与回答全错）——**高风险内容的转写后校验**（数字/实体抽检——客服录音的金额、会议纪要的人名——"转写后抽验高风险实体"是音频 RAG 的质量底线）。

## 5. 音视频检索的评估特化

**转写质量**（WER——检索的地基：转写错了检索就错，`04-向量数据库/` 的"检索先行"在音视频的第一层是"转写先行"）；**片段检索**（时间区间命中——"说到了但时间对不上"是常见失败）；**说话人归属**（"谁说的"答对率——说话人标签错误会答错归属）；**时序推理**（跨片段的因果/变化类问题——当前模型的短板，第 3 节）；**音频检索与文本检索的对齐**（检索到的转写块 vs 实际音频内容一致——转写与音频的对应关系验证）。

## 6. 音视频 RAG 的选型建议

**什么时候建**：音视频内容占比高且需要内容检索（会议/播客/教学视频库）——纯文本场景别建（决策门槛同 01 篇）；**最小可用**：Whisper 转写 + 说话人标签 + 文本 RAG + 时间戳引用——**大多数需求转写优先就够**（原生音频检索的收益在"语气/音调"类需求，占比低）；**视频先问需求**："找画面"（帧检索）还是"找内容"（转写检索）还是"找因果"（时序推理——2026 仍难）——**需求决定通道**（05 篇查询路由的音视频版）。

> 🎯 **核心要点**：音频两路线——转写优先（Whisper，WER<5%，工程默认）vs 原生音频检索（保留语气，2026 未产品化）；转写的丢失（说话人/语气）用元数据补回（说话人标签 + 词级时间戳）；工程配方——"转写用于检索、原音频用于推理"（检索文本块 + 原音频给原生音频 LLM）；视频 RAG——帧检索（CLIP）+ 转写检索（Whisper）+ 双塔，**关键缺口是时间线被忽略**（时序依赖丢失，下一步方向）；音视频元数据即检索维度（时间戳/说话人/场景）；评估特化（WER 先行/片段命中/说话人归属/时序推理）；选型——转写优先是默认、视频先问"找画面/找内容/找因果"。
