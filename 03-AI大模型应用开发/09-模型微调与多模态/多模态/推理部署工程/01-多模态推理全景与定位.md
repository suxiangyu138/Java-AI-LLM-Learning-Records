# 多模态推理全景与定位

> 多模态推理的链路与差异：编码→投影→prefill→decode 四阶段、与文本推理的根本差异（视觉 token 与编码器开销）、部署形态（合设/分离）——"推理链路是性能分析的坐标系"

## 1. 推理链路：四阶段

多模态推理（VLM）的完整链路（与 `多模态/多模态基础概念/05-视觉语言模型VLM架构.md` 的架构对应）：

**编码（Encode）**：图像进视觉编码器（ViT——`多模态/多模态基础概念/02-视觉编码器与图像tokenization.md`）→ patch 特征（视觉 token）——**多模态独有的阶段**（文本推理没有）；**投影（Project）**：视觉 token 进投影层 → 语言嵌入空间（`多模态/多模态基础概念/04-投影层与视觉语言桥接.md`）——轻量（MLP 层）；**预填充（Prefill）**：输入序列（视觉 token + 文本 token）一次前向 → 计算 KV cache——**长输入的重计算阶段**（图像 token 越多 prefill 越长）；**解码（Decode）**：逐 token 生成回答（自回归——`大模型微调知识体系/` 的生成）——**内存带宽受限**（`大模型微调知识体系/模型推理与部署/` 的文本推理方法论在此适用）。

**四阶段的性能角色**：编码（视觉开销——图像数量/分辨率决定）；prefill（输入开销——token 数决定——**多模态的 prefill 远长于文本**）；decode（输出开销——回答长度决定——与文本相同）——**"多模态的额外成本集中在编码 + prefill"**（文档负载中大部分计算来自长视觉输入而非回答生成——HSE 2026）。

**链路的优化映射**：四阶段各有优化杠杆（03 篇详述）——**编码**（CUDA Graphs/数据并行/processor cache）；**prefill**（token 压缩/分块/分离池）；**decode**（推测解码/量化）；**投影**（轻量——非瓶颈）——**"性能分析按阶段、优化也按阶段"**（先定位慢的阶段、再用对应杠杆——`多模态/多模态基础概念/02-多模态推理性能分析.md` 的阶段分解与 03 篇的优化矩阵一一对应）。

## 2. 与文本推理的根本差异

多模态推理与文本推理的三条差异（`多模态/多模态基础概念/01-多模态模型全景与定位.md` 的推理视角）：

**多一个编码阶段**：图像先进视觉编码器（额外的模型前向——GPU 算力/延迟）——**文本请求无此开销**（文本直接 tokenize）；**视觉 token 的 prefill 膨胀**：一张图 576 到数千 token（`多模态/多模态基础概念/06-多模态token与输入处理.md`）——**prefill 计算量远大于同长度文本**（视觉 token 走完整处理路径——`多模态/多模态微调（PEFT）/08-多模态微调工程实践.md` 的"1 图像 token ≈ 数文本 token 计算"）；**KV cache 的视觉占比**：长视觉输入 → KV cache 被视觉 token 占据（`大模型微调知识体系/模型推理与部署/` 的 KV 方法论——多模态的 KV 大头是视觉 token）。

**推论**：**"多模态推理贵在视觉处理"**——编码 + 视觉 prefill 是额外成本——优化空间也在这里（03 篇的 token 压缩/编码器优化）。

## 3. 部署形态：合设 vs 分离

多模态服务的两种部署形态（04 篇详述，此处给定位）：

**合设（Colocated）**：编码/prefill/decode 在同一实例——**简单、TTFT 低**——**代价**：编码器推理打断 prefill 计算（编码与 prefill 争抢 GPU）——**适用**：<64 并发/延迟敏感交互（`多模态/多模态常见问题与缺陷/07-上下文与工程缺陷.md` 的子 2 秒 SLA）；**分离（Disaggregated E-P-D）**：编码/prefill/decode 分实例（2026 趋势——04 篇）——**收益**：专有 prefill 池 3-4× 吞吐、图像重负载 1.5-2.5×——**代价**：跨实例 KV/特征传输开销（NIXL 3-12ms）——**适用**：>64 并发/吞吐优化批处理——**"部署形态的选择 = 并发规模 × 延迟敏感度"**。

## 4. 部署的服务形态

多模态服务的接入形态（工程视角）：**OpenAI 兼容端点**（vLLM 类——`/v1/chat/completions` 支持图像输入——应用层零改动接入——`大模型微调知识体系/完整微调工程流程/09-导出部署与上线运维.md` 的兼容端点方法论多模态版）。

**图像输入的格式约定**（base64/URL——`多模态/多模态微调（PEFT）/08-多模态微调工程实践.md` 04 节的集成要点——接口层与训练模板一致（`多模态/多模态数据集/07-数据格式与处理.md` 03 节的多模态 chat template——"服务的图像输入格式 = 训练时的模板格式"）；
**多模态网关**（多模型路由——Agent 场景——08 篇）；**专用服务**（computer use 专用 VLM——07 篇）——**"服务形态按消费方定"**（对话应用兼容端点/Agent 网关/专用任务专用服务）。

## 5. 部署的资源基线

多模态服务的资源基线（2026 参考）：**显存**（模型权重 + KV cache——Qwen2.5-VL 7B 约 17GB 权重 + 每会话 4K 上下文约 2GB KV——H200 141GB 约 50 会话——
AWQ INT4 权重减半约 80-100 会话——05/06 篇的账本）；**主机资源**（多模态张量处理需要高主机内存（256GiB 级）与大 /dev/shm（90GiB）——
llm-d 实践——**"多模态服务的主机资源需求高于文本"**（图像张量在主机与 GPU 间传输）；**预热**（模型加载 15-45 秒——`多模态/多模态常见问题与缺陷/07-上下文与工程缺陷.md` 的冷启动——**"至少保持一个节点热"**（Agent 场景的延迟预算——07 篇）。

## 6. 定位总结

多模态推理部署的定位：**"训练产出模型、部署消费模型"**——本体系是服务侧（vLLM 类引擎 + 优化 + 架构 + 运维）；与文本推理部署（`大模型微调知识体系/模型推理与部署/` 体系）的关系——**文本方法论是基础、本体系是多模态扩展**（多编码阶段 + 视觉 token + 图像缓存）——"先懂文本推理部署，再学多模态版"（与 `多模态/多模态基础概念/` 的"先文本 RAG 再多模态"同构——**"多模态是文本的扩展层"**贯穿本知识库）。

**体系的"生命周期"闭环**：本体系是多模态体系的最后一环——**基础概念（原理）→ 数据集（数据）→ 微调（模型）→ RAG（检索）→ 缺陷（排障）→ 本体系（服务）**——"训练产出模型、本体系消费模型并反馈缺陷（`多模态/多模态常见问题与缺陷/` 的服务侧监控）"——**多模态知识体系在服务环节闭环**（模型从训练到上线到迭代的完整生命周期）。

> 🎯 **核心要点**：四阶段链路——编码（多模态独有）/投影（轻量）/prefill（长输入重计算——多模态远长）/decode（与文本相同）——**额外成本集中在编码 + prefill**（文档负载大头是视觉输入不是回答）；三条差异——多编码阶段/视觉 prefill 膨胀/KV 视觉占比——"多模态推理贵在视觉处理"；部署形态——合设（简单 TTFT 低——编码打断 prefill）vs 分离（1.5-2.5× 吞吐——NIXL 开销）——"并发规模 × 延迟敏感度"决定；服务形态——兼容端点/网关/专用；资源基线——显存账本（7B 约 17GB 权重 + 每会话 2GB KV）/主机内存（256GiB）/预热（15-45s 保持热）；定位——文本部署方法论是基础、多模态是扩展层。
