# 多模态服务架构

> 服务架构的两种形态：合设（简单 TTFT 低）vs E-P-D 分离（2026 趋势——吞吐 1.5-2.5×）、vLLM 多模态支持、并发与批处理、模态感知调度——"架构选择 = 并发规模 × 延迟敏感度"

## 1. 合设 vs 分离

多模态服务架构的核心选择（01 篇的形态在此展开）：

**合设（Colocated/Aggregated）**：编码/prefill/decode 在同一实例——**优点**：简单（一套部署）、TTFT 低（无跨实例传输）；**缺点**：**编码器推理打断 prefill 计算**（ViT 与语言塔争抢 GPU——prefill 吞吐被拖累）；**适用**：<64 并发多模态请求 / 延迟敏感交互——**"合设是默认起点"**（chunked prefill + 内核优化后的形态）。

**分离（Disaggregated E-P-D）**：**编码（E）/预填充（P）/解码（D）分离成独立 vLLM 实例**（2026 主要趋势）——**优点**：独立细粒度扩缩（编码器扩缩与语言塔解耦）、**纯文本请求绕过编码器**（TTFT 更低）、跨进程编码输出复用（ECConnector）；**缺点**：跨实例传输开销（NIXL 连接——RDMA 3-12ms、TCP 约 4 倍）；**适用**：>64 并发 / 吞吐优化批处理。

**实测收益**（vLLM-Omni/Spheron）：**专有 prefill 池 3-4× prefill 吞吐**（ViT 不再打断 prefill）；图像重负载 **1.5-2.5× 吞吐**、音频重 1.3-2.0×、混合 1.4-1.8×（128 并发）——**盈亏平衡点：64+ 并发 / 96+ GPU**——以下合设更简单 TTFT 更低（"低于 64 并发，合设 + chunked prefill 是更好选择"）。

## 2. vLLM 多模态支持

**vLLM 是 2026 多模态服务的事实引擎**（SGLang/TensorRT-LLM/Dynamo 为其他选项）——多模态支持清单：**模型支持**（Qwen-VL 系/LLaVA/InternVL/Pixtral/Gemma Vision/GLM-4.5V——107B/12B 激活 MoE——recipes.vllm.ai 一键部署）；**多模态特性**（编码器 CUDA Graphs/数据并行编码器/processor cache/前缀缓存/多 LoRA 四组件（`多模态/多模态微调（PEFT）/08-多模态微调工程实践.md` 04 节））；**接口**（OpenAI 兼容——图像输入——应用层零改动）。

**引擎选型**：vLLM（通用默认——生态最全）；SGLang（推理性能激进——`多模态/多模态基础概念/` 的社区选择）；TensorRT-LLM（生产优化）；**Dynamo**（大规模分离推理——NVIDIA——E-P-D 的框架级支持）——**"引擎按规模与生态选"**（小规模 vLLM 够、大规模分离考虑 Dynamo）。

**引擎的"多模态就绪"检查**（选型时跑一遍）：**模型支持清单**（目标模型是否官方支持——`多模态/多模态基础概念/05-视觉语言模型VLM架构.md` 的模型家族）；**多模态特性**（编码器 CUDA Graphs/processor cache/多 LoRA——03/05 篇的特性是否齐）；**OpenAI 兼容**（图像输入的接口——`多模态/多模态基础概念/01-多模态推理全景与定位.md` 04 节的服务形态）——**"先查引擎的多模态就绪度再选型"**（文本引擎的多模态支持参差不齐——`多模态/多模态基础概念/` 的组装件选型纪律）。

## 3. 并发与批处理

多模态的并发与批处理（`大模型微调知识体系/模型推理与部署/` 的批处理方法论多模态版）：**混排的挑战**——prefill（重）与 decode（轻）混排的平衡（chunked prefill 的标准解法）；
**图像 batch 的显存**——图像 token 多 → batch 内 token 数波动大（`多模态/多模态基础概念/06-多模态token与输入处理.md` 的 token 预算——**"批处理按 token 预算而非请求数"**（图像请求的 token 权重不同））；**并发上限**——KV 容量决定（`大模型微调知识体系/模型推理与部署/` 的会话账本——7B 每会话 2GB KV——50 会话/H200——`多模态/多模态微调（PEFT）/08-多模态微调工程实践.md` 01 节）。

**多模态批处理的注意**：**编码批处理**（多图请求的编码可批——编码器 batch——CUDA Graphs 的多 token 预算为此）；**图像与文本的混合批**（图像重请求拖慢文本请求——`多模态/多模态基础概念/` 的模态感知调度缓解——`多模态/多模态微调（PEFT）/07-多模态token与输入处理.md` 的模态失衡在服务侧的对应——**"服务侧的模态分组"**（图像任务与文本任务分队列——文本请求不排队等图像））。

**批处理的"图像显存预算"**：图像 batch 的显存波动大（图像 token 数百到数千——`多模态/多模态基础概念/06-多模态token与输入处理.md` 的 token 账本）——**"按 token 预算而非请求数配 batch"**（batch 内图像请求的 token 权重高——`大模型微调知识体系/训练关键超参 & 显存优化技术/03-批量大小与梯度累积.md` 的显存账本多模态版——图像多时降 batch 或分块——`多模态/多模态微调（PEFT）/08-多模态微调工程实践.md` 的激活值瓶颈在服务侧的对应）。

## 4. 模态感知调度

**模态感知调度（2026）**：调度器理解模态差异——**Duet-Infer（IEEE 2026）**：视觉-语言执行解耦 + 预处理并行 + 共享内存管理器（编码器缓存共享）+ 公平感知调度——**P99 TTFT -33.7%、端到端延迟 -20%**（单 GPU vLLM 混合负载）——**"调度器懂模态比不懂模态更优"**——图像任务优先编码（并行处理）、文本任务快速通过（不被图像拖累）——**"模态感知 = 公平性的多模态版"**（图像与文本请求的公平调度——`大模型微调知识体系/模型推理与部署/` 的调度公平性多模态化）。

## 5. 服务拓扑：多模态网关

**多模态网关**：多模型/多模态路由（Agent 场景必需——07/08 篇）——**拓扑形态**：请求 → 网关 → 路由（按模态/任务/模型）→ 多引擎池——**网关的职责**：模态路由（文本/图像/音频分池）、缓存路由（06 篇——图像哈希路由）、A/B（08 篇）、限流与配额——**"网关是服务架构的控制面"**（多模态 Agent 每请求调用多个模型——`多模态/多模态基础概念/07-指令遵循与多模态推理.md` 的 Agent——网关编排）。

## 6. 架构决策清单

多模态服务架构的决策流程：**1) 规模评估**（并发/请求率——"<64 并发起步合设"）；**2) 延迟预算**（交互型子 2 秒 vs 批处理——`多模态/多模态基础概念/09-多模态能力评估与基准.md` 的 SLA——
合设优先交互）；**3) 负载构成**（图像重/文本重——图像重 = 分离收益大）；**4) 内核优化先行**（token 压缩/编码器 CUDA Graphs/processor cache——"先榨干单实例"）；**5) 分离评估**（>64 并发 + 吞吐瓶颈 → E-P-D 分离）——**"先合设优化、后分离扩展"**（架构演进路线——与 03 篇的优化顺序呼应）。

> 🎯 **核心要点**：合设 vs 分离——合设（简单 TTFT 低、编码打断 prefill——<64 并发默认）vs E-P-D 分离（专有 prefill 池 3-4×、图像重 1.5-2.5×、NIXL 3-12ms——64 并发/96 GPU 盈亏点——"低于 64 合设更好"）；vLLM 事实引擎（模型支持/编码器特性/OpenAI 兼容——Dynamo 大规模分离）；并发批处理——按 token 预算而非请求数/模态分组（图像文本分队列）/KV 容量定并发上限；模态感知调度（Duet-Infer P99 TTFT -33.7%——"调度器懂模态更优"）；多模态网关——控制面（模态路由/缓存路由/A-B/限流——Agent 场景必需）；决策清单——规模→延迟→负载→内核优化先行→分离——"先合设优化、后分离扩展"。
