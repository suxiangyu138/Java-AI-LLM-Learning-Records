## 4. 场景三：线上 Bug 排查与修复

### Prompt

```text
"以下是生产环境出现的一个随机性 NPE 的堆栈信息：

java.lang.NullPointerException
  at com.example.order.service.OrderService.processOrder(OrderService.java:156)
  at java.base/java.util.concurrent.CompletableFuture$UniApply.tryFire(...)

相关代码片段：
[提供了 80 行包含 CompletableFuture 链式调用 + 
  @Transactional 的方法]

请：
1. 定位 Bug 根因
2. 分析为什么是随机发生的
3. 给出修复方案（含代码）
4. 建议防范措施"
```

### 评分

| 模型 | 定位准确 | 根因分析 | 修复质量 | 防范建议 | 总分 |
|------|:---:|:---:|:---:|:---:|:---:|
| **MiniMax M3** | **9.8** | **9.7** | 9.3 | 9.5 | **38.3** |
| Claude Opus 5 | 9.5 | 9.3 | **9.5** | **9.7** | 38.0 |
| Kimi K3 | 9.3 | 9.0 | 9.0 | 9.0 | 36.3 |
| DeepSeek V4 Pro | 9.0 | 8.8 | 8.8 | 8.5 | 35.1 |
| GPT-5.6 Sol | 9.0 | 9.0 | 9.0 | 9.2 | 36.2 |
| Qwen3.7-Max | 8.8 | 8.5 | 9.0 | 9.0 | 35.3 |

### 点评

```text
MiniMax M3：Bug 诊断最强（名不虚传！）
  ✅ 准确定位：CompletableFuture 的 thenApplyAsync 使用了
     commonPool，事务上下文（TransactionSynchronization）
     在异步线程中丢失，导致懒加载的关联对象为 null
  ✅ "随机发生"的根因：commonPool 线程复用 + 线程本地变量
     + GC 时机共同决定的竞态条件
  ✅ 给出了 3 层修复方案：
     一层：使用自定义线程池 + 事务传播
     二层：主动 fetch 关联数据（避免懒加载）
     三层：添加防御性 null 检查 + 监控告警
  ✅ 防范建议包括代码审查 Checklist 和静态分析规则

Claude Opus 5：修复代码最工程化
  ✅ 修复代码考虑了向后兼容（新增重载方法，不改变现有接口）
  ✅ 单元测试 + 集成测试双覆盖
  ✅ 建议了 TransactionTemplate 替代 @Transactional 的方案
```

### 8.2 场景化最佳选择

| 场景 | 🥇 首选 | 理由 |
|------|------|------|
| **日常 CRUD 开发** | Claude Opus 5 | 代码质量最高，Spring 生态理解最深 |
| **复杂并发编程** | DeepSeek V4 Pro | 虚拟线程 + 并发模式最擅长 |
| **线上 Bug 排查** | MiniMax M3 | Bug 诊断能力碾压，根因分析最透彻 |
| **代码重构** | Claude Opus 5 | 重构方案最工程化，迁移步骤最完善 |
| **架构设计** | Claude Opus 5 | 技术选型最新最全面，考虑最周全 |
| **JVM 调优** | Claude Opus 5 | GC 分析和参数优化最专业 |
| **中文文档/注释** | Qwen3.7-Max | 阿里规范对齐，中文最自然 |
| **极致性价比** | DeepSeek V4 Pro | 总分第三但价格 1/20，CPP 最高 |

> 🎯 **核心要点**：Claude Opus 5 在 6 个 Java 场景中拿下 5 个第一，是 Java 后端开发的首选模型。但有两个场景被"专长生"超越——并发编程（DeepSeek V4 Pro）和 Bug 排查（MiniMax M3）。**最佳策略：Claude Opus 5 主力 + MiniMax M3 排 Bug + DeepSeek V4 Pro 省钱批量**。
