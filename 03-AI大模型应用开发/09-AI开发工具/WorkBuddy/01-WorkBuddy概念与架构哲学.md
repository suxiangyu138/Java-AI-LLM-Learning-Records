## 1. 什么是 WorkBuddy

WorkBuddy 是腾讯推出的 **AI Agent 产品**，核心理念是将大模型的能力通过工程手段转化为**可用、可靠、可扩展的产品**。它不是一个单纯的 Chat UI，而是一套完整的 Agent 工程体系。

### 1.1 核心定位

| 维度 | 定位 |
|------|------|
| **产品形态** | AI Agent 工作搭子，桌面端 + 命令行双形态 |
| **目标用户** | 开发者、内容创作者、知识工作者 |
| **核心能力** | 工具调用、多 Agent 协作、知识库对接、任务自动化 |
| **差异化** | Harness 工程体系 + 四层能力模型 + 专家团协作 |

### 1.2 关键里程碑

```text
2024 Q4   MCP 协议发布（Anthropic），WorkBuddy 基于此构建工具生态
2025 H1   WorkBuddy 内测，确立"模型无状态"核心架构
2025 H2   专家团功能上线，多 Agent 协作模式验证
2026      三层降级架构落地，成本控制体系成熟
2026 H2   MCP Apps 扩展，工具可返回交互式 UI
```

## 2. 核心架构哲学：模型是无状态函数

### 2.1 为什么说模型是"无状态函数"

这是理解 WorkBuddy 架构的**第一性原理**：

```text
模型 = f(System Prompt + Tools + History + Context + User Input) → Text Output

┌─────────────────────────────────────────────────────────┐
│                    模型（Model）                          │
│                                                         │
│  输入                                                   │
│  ├── System Prompt    ← 角色、规则、约束                  │
│  ├── Tool Definitions ← 可用工具列表                       │
│  ├── Conversation     ← 会话历史                          │
│  ├── Context          ← 知识库检索、文件、记忆              │
│  └── User Input       ← 当前用户指令                      │
│                                                         │
│  输出 → 下一个 Token（文字 or 工具调用请求）                │
└─────────────────────────────────────────────────────────┘
```

> 💡 **关键洞察**：模型不知道"我是谁"、"我之前做了什么"、"我能用什么工具"——所有这些都是外部注入的。模型只是根据输入的上下文，预测下一个最可能的 token。

### 2.2 产品层 vs 模型层的职责划分

| 职责 | 模型层 | 产品层（WorkBuddy） |
|------|:---:|:---:|
| 语言理解与生成 | ✅ | — |
| 工具调用决策 | ✅ 生成调用请求 | ✅ 执行调用、校验结果 |
| 状态维护 | — | ✅ 会话历史、任务进度 |
| 记忆管理 | — | ✅ 长期记忆读写 |
| 权限控制 | — | ✅ Sandbox、Approval Gate |
| 多 Agent 编排 | — | ✅ 角色分配、通信协议 |
| 上下文组织 | — | ✅ 写入/选择/检索/压缩/隔离 |

> 🎯 **核心要点**：模型的边界很清楚——它只能"说"（输出 token）。所有"做"的事情——执行工具、维护状态、控制权限——都是产品层的职责。

## 3. 四层能力模型

WorkBuddy 定义了从底层到上层的四级能力组织方式：

```text
┌──────────────────────────────────────────────┐
│  L4: Plugin（插件）                            │
│  能力组合包：MCP + Skills + Rules + Hooks      │
│  "能力组合如何安装与分发"                        │
├──────────────────────────────────────────────┤
│  L3: Skill（技能）                             │
│  任务流程模板：步骤、约束、脚本、验收标准          │
│  "这类任务应该怎么做"                            │
├──────────────────────────────────────────────┤
│  L2: MCP（模型上下文协议）                       │
│  标准化连接协议：Resources / Tools / Prompts    │
│  "如何标准化连接外部系统"                        │
├──────────────────────────────────────────────┤
│  L1: Tool / Function Call（工具调用）           │
│  结构化协议：模型生成调用 → Agent 执行            │
│  "模型如何与外部世界交互"                        │
└──────────────────────────────────────────────┘
```

### 3.1 L1：Function Call

```text
用户："帮我查一下今天北京天气"

→ 模型判断：需要调用 get_weather 工具
→ 生成结构化请求：{"name": "get_weather", "arguments": {"city": "北京", "date": "today"}}
→ Agent 执行：调用天气 API
→ 返回结果注入上下文："北京今天晴，22-30°C"
→ 模型用自然语言回复用户
```

> ⚠️ **安全要点**：权限校验、审批机制在**模型外部**工程层完成，不能让模型自己决定是否有权限。

### 3.2 L2：MCP 协议

MCP 定义了三种原语（Primitives）：

| 原语 | 方向 | 说明 | 示例 |
|------|------|------|------|
| **Resources** | Server → Model（只读） | 暴露数据给模型 | 文件内容、数据库记录、API 文档 |
| **Tools** | Model → Server（执行） | 模型驱动的动作 | 创建文件、发送消息、查询数据库 |
| **Prompts** | Server → User（模板） | 用户驱动的提示模板 | "帮我写一份周报"的标准化模板 |

### 3.3 L3：Skill

Skill 将一类任务的执行方式沉淀为结构化模板：

```yaml
# Skill 结构示例
name: "代码审查"
version: "1.2.0"
steps:
  - name: "静态分析"
    tool: "run_linter"
    timeout: 30s
  - name: "安全检查"
    tool: "security_scan"
    constraints: ["只检查本次变更"]
  - name: "生成报告"
    format: "markdown"
    sections: ["问题汇总", "严重程度", "修复建议"]
acceptance_criteria:
  - "所有 Critical 问题必须有修复建议"
  - "报告不超过 2000 字"
```

> 💡 **Skill vs Prompt**：Prompt 告诉模型"做什么"，Skill 告诉 Agent 系统"怎么做"——包括步骤、工具、约束、验收标准。

### 3.4 L4：Plugin

Plugin 是最高层的封装，将多个能力打包为一个可安装分发的单元：

```text
Plugin = MCP Server 配置
       + Skills 定义文件
       + Rules / Hooks
       + 安装说明
       + 版本清单
```

## 4. ReAct 执行循环

### 4.1 基本模式

WorkBuddy 采用 **ReAct（Reasoning + Acting）** 模式执行任务：

```text
┌──────────────────────────────────────────────────┐
│                                                  │
│   用户输入                                         │
│      ↓                                           │
│   ┌──────────┐    是工具调用？                     │
│   │ 模型判断  │────────── 是 ──→ 执行工具           │
│   └──────────┘                    ↓               │
│      ↓ 否                       观察结果            │
│   直接回复                         ↓               │
│                              ┌──────────┐         │
│                              │ 模型再判断 │←────────│
│                              └──────────┘         │
│                                 ↓ 否              │
│                              最终回复给用户          │
│                                                  │
│   ◄── 一轮 ReAct ──►                              │
└──────────────────────────────────────────────────┘
```

### 4.2 ReAct 循环的工程挑战

| 挑战 | 工程对策 |
|------|---------|
| **无限循环** | 设置最大轮次上限（如 20 轮），超限强制终止 |
| **工具调用失败** | 重试机制（最多 3 次）+ 降级策略 |
| **上下文膨胀** | 每轮压缩：只保留结论 + 证据位置，删除中间过程 |
| **用户等待焦虑** | 流式输出 + 进度提示（"正在查询天气..."） |
| **模型幻觉调用** | 工具 Schema 严格校验，不合法参数拒绝执行 |

## 6. 与 Claude Code / Copilot 的对比

| 维度 | WorkBuddy | Claude Code | GitHub Copilot |
|------|-----------|-------------|----------------|
| **定位** | 通用 AI Agent 平台 | AI 编程助手 | 代码补全 + 聊天 |
| **工具生态** | MCP + 自定义工具 | MCP + 内置工具 | 有限 |
| **多 Agent** | 专家团模式 | 子 Agent 机制 | 不支持 |
| **记忆系统** | 五类记忆 + 作用域层级 | 文件级记忆 | 会话级 |
| **Skill 体系** | 完整的版本化 Skill | Hooks + Skills | 不支持 |
| **成本控制** | 三层降级架构 | API 层配置 | 不透明 |
| **上下文工程** | 五项操作策略 | Prompt Cache 优化 | 自动管理 |
| **适用场景** | 通用任务自动化 | 软件开发 | 代码编写 |

---

> 🎯 **核心要点**：WorkBuddy 不是一个更好的聊天机器人，而是一个 Agent 操作系统。它的核心创新在于：把模型当作无状态函数，用 Harness 层提供驾驭、约束和整合能力，通过四层能力模型让工具、协议、技能和插件层层递进。
