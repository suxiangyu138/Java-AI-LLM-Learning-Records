## 1. 面试高频题与答题框架

### 1.1 概念类（基础必答）

**Q1：什么是 Vibe Coding？它和传统编程的本质区别？**

```text
答题框架：
① 定义：Karpathy 2025.02 提出，意图驱动、AI 写码、效果迭代
② 本质：从「代码（Code）」转向「意图（Intent）」的范式革命
③ 人的角色转变：编码执行者 → 意图架构师
④ 核心公式：AI 生成效果 = LLM(Task+Context+Prompt)，Context 权重最大
⑤ 数据佐证：71% 开发者尝试（Stack Overflow 2025）
```

**Q2：Vibe Coding 的核心公式是什么？为什么 Context 最重要？**

```text
① 公式：AI 生成效果 = LLM(Task + Context + Prompt)
② 原因：Task/Prompt 单次可优化、边际收益递减；
        Context 决定风格一致性、架构对齐、约束执行，决定"整个项目成不成"
③ 落地：CLAUDE.md 规则文件 + 参考文件引用 + 上下文五层模型
```

**Q3：纯粹模式和负责任模式的区别？何时用哪种？**

| 维度 | 纯粹模式 | 负责任模式 |
|------|---------|-----------|
| 信任度 | 完全信任 AI | AI = pair programmer |
| 适用 | 原型/Demo/探索 | 生产级开发 |
| 风险 | 技术债 | 人工成本 |
| 策略 | 混合：探索用纯粹，交付用负责任 |

### 1.2 方法类（核心必答）

**Q4：请描述你的 Vibe Coding 标准工作流（五步法）**

```text
① 需求精确定义：四要素（用户-场景-问题-方案）+ 非功能需求 + 边界
② 任务拆解排序：四象限（核心→重要→次要→优化），2-4h 粒度
③ 结构化 Prompt：角色-任务-约束-输出四段式
④ 生成与迭代：生成→验证→反馈→迭代闭环，增量修改
⑤ 集成与部署：集成测试 + CI/CD + 回滚计划
```

**Q5：如何设计一个高质量的 Vibe Coding 提示词？**

```text
四段式 + 两个进阶技巧：
├── 角色：资深 XX 工程师，熟悉本项目规范
├── 任务：原子化，编号子步骤
├── 约束：技术栈/风格/禁止项/参考文件（关键）
├── 输出：文件清单 + 测试要求
├── 进阶 1：引用现有代码作 few-shot（风格一致性利器）
└── 进阶 2：约束段声明禁止修改的文件（防越权）
```

**Q6：什么是上下文腐烂？如何治理？**

```text
① 定义：上下文过多 → 模型无法判断优先级 → 质量下降
② 信号：指令衰减、重点模糊、前后矛盾、token 暴涨
③ 治理三板斧：裁剪（只带任务+规则两级）/ 归档（完成项移入 ADR）/ 刷新（信号出现立即 /clear）
```

### 1.3 工程类（加分必答）

**Q7：如何保证 AI 生成代码的质量？**

```text
四道防线：
① 规则前置：CLAUDE.md（技术栈/规范/安全基线）
② 人工审查：三道闸（生成时/PR 时/发布前），AI 代码审查六重点
③ 门禁拦截：测试 + 覆盖率 + SAST + SCA 四道 CI/CD 门禁
④ 测试验收：AI 生成测试 = 可执行验收标准
数据：非标准化返工 +72%（McKinsey），规范团队成功率 90% vs 30%
```

**Q8：AI 代码审查和人类代码审查的侧重点有何不同？**

```text
AI 代码特有审查重点：
① 幻觉检查：方法/类/依赖是否真实存在
② 边界检查：空值/超长/并发/超时（AI 最弱项）
③ 风格一致性：AI 倾向自创风格
④ 安全检查：SQL 注入/XSS/硬编码密钥
⑤ 过度设计：无用抽象（YAGNI）
⑥ 回归影响：是否误改相关文件
```

**Q9：如何处理 AI 幻觉的依赖（Slopsquatting 风险）？**

```text
① 依赖白名单：规则文件声明允许清单，新增必须人工确认
② 版本锁定：lock 文件入库
③ SCA 扫描：每个 PR 自动扫描
④ 包真实性核验：新依赖查官方仓库
```

### 1.4 场景类（实战必答）

**Q10：哪些场景适合 Vibe Coding？哪些必须禁用？**

```text
✅ 适合：MVP 原型（-47% 耗时）、内部工具、成熟库增量开发、技术预研 Demo
❌ 禁用：核心支付链路、用户隐私数据处理、强监管合规功能
（强规则场景效率提升不足 10%，风险却不可控）
```

**Q11：0→1 冷启动和 1→N 增量开发的方法有何不同？**

| 维度 | 0→1 冷启动 | 1→N 增量开发 |
|------|-----------|-------------|
| 上下文来源 | 规则 + 意图 | 既有代码 |
| 首要风险 | 方向错误 | 破坏现有功能 |
| 工具推荐 | Claude Code | Codex |
| 核心动作 | 边界收缩、59 分先跑 | 先出方案确认、禁止夹带修改 |

**Q12：如何组织多 Agent 协作？上下文如何在 Agent 间流动？**

```text
① 架构：主从式（主 Agent 规划/仲裁 + 执行 Agent 分工）
② 隔离：worktree 并行开发防冲突
③ 上下文流动：最高指令软链接法
   CLAUDE.md + COLLABORATION.md 共享规则文件 = 唯一事实源
④ 知识沉淀：SOLVED.md + Skill 化
```

**Q13：Vibe Coding 的成本如何控制？**

```text
① 工具选型：上下文效率对比（Codex 1x / Claude Code 4x）
② 场景分级：原型用便宜模型、生产用强模型
③ 上下文裁剪：只带必要上下文（token = 成本）
④ 新计费模式：2026 年 Copilot/Codex 转向按用量计费，精算后再用
```

### 1.5 风险类（深度加分）

**Q14：Vibe Coding 有哪些主要风险？如何应对？**

```text
五大风险 + 对策：
① 代码幻觉 → 人工审查 + 测试
② 架构漂移 → 结构化重构（每 2-3 迭代）
③ Slopsquatting → 依赖白名单 + SCA
④ 提示注入（CVSS 9.4 "Comment and Control"）→ 最小权限 + 补丁 + 审查
⑤ 安全默认值缺失 → 安全基线进 CLAUDE.md
```

**Q15：2026 年 Vibe Coding 有什么新趋势？你如何跟上？**

```text
六大趋势：多 Agent 协同常态化 / 意图工程标准化 / 全链路一体化平台
          / AI 开发合规体系 / 多模态融合 / 普惠开发
跟上方式：上下文工程 + 多 Agent 编排 + 审查能力三硬技能，
          系统品味 + 技术判断两软技能，抢占「意图架构师」生态位
```

## 2. 开放题：Vibe Coding 会取代程序员吗

> 这是 2026 年面试最高频的开放题，给出结构化观点：

```text
观点框架：
① 被取代的：单纯「写代码」的执行性工作（AI 已接管 80% 的编码量）
② 被需要的：「想清楚」的创造性工作
    - 意图定义（需求拆解、验收量化）
    - 架构决策（边界、取舍、演进路径）
    - 质量把控（审查、门禁、重构）
    - 上下文管理（规则、知识沉淀）
③ 历史类比：Excel 没有取代会计，而是让会计转型为分析师
    AI 编码没有取代程序员，而是让程序员转型为意图架构师
④ 结论：程序员不会消失，但「只写代码的程序员」会消失
```

> 🎯 **答题金句**：AI 接管的是「写」，人接管的是「想」——Vibe Coding 淘汰的不是程序员，而是不思考的程序员。

## 3. 五大常见误区

| # | 误区 | 真相 |
|---|------|------|
| 1 | 「Vibe Coding 就是丢一句话让 AI 干活」 | 一句话 = 能跑的 demo，好产品 = 工作流 + 规范 |
| 2 | 「提示词越精致效果越好」 | 上下文工程 > 提示词工程，规则先行才有效 |
| 3 | 「AI 写的代码可以直接上生产」 | 43% 需要调试，必须审查 + 测试 + 门禁 |
| 4 | 「用了 AI 就不需要写代码能力了」 | 判断 AI 输出质量的前提是更强的技术认知 |
| 5 | 「多 Agent 就是多开几个窗口」 | 核心是上下文治理与共享规则，否则更乱 |
