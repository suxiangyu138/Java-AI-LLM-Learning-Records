## 1. 案例一：从 0 到 1 的 MVP 冷启动

### 1.1 项目背景

> 需求：给某 SaaS 公司做一个**客户跟进 CRM**，验证销售团队是否愿意用。传统方式 7-10 天，要求 4-8 小时内出可演示版本。

### 1.2 执行过程（时间线）

```text
T+0:00  意图定义（30min）
        ├── 用户：销售主管（非技术）
        ├── 场景：50+ 客户跟进、状态同步
        ├── 功能：客户 CRUD + 跟进记录 + 状态看板 + 简易登录
        └── 约束：Java + Spring Boot 3 + Vue 3 + MySQL，暂不要权限体系

T+0:30  规则文件（20min）
        ├── CLAUDE.md：技术栈/目录结构/规范（复用项目模板）
        └── 锁定依赖版本

T+0:50  架构与任务拆解（30min）
        ├── 主 Agent 输出架构文档：表结构 + API 清单 + 页面清单
        ├── 人工确认 5 分钟
        └── 拆为 6 个原子任务（2-4h 粒度 → 压到 30-60min 粒度）

T+1:20  多 Agent 并行开发（2h）
        ├── 后端 Agent：用户 + 客户 + 跟进记录 3 组 API
        ├── 前端 Agent：登录页 + 客户列表 + 跟进弹窗 + 看板
        └── 测试 Agent：核心接口测试

T+3:20  集成联调（1h）
        ├── 自动化测试 → 修 3 个 bug（均为边界条件）
        └── 端到端手工验证主流程

T+4:20  部署演示（0.5h）
        └── Docker 镜像 + 一键部署脚本
```

**总耗时 ≈ 4.5 小时**，产出可演示 MVP。

### 1.3 关键决策记录

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 模式 | 纯粹模式为主 | 验证方向优先，允许粗糙 |
| 权限 | 不做多角色权限 | 边界收缩防蔓延（四要素里的边界条款） |
| 数据库 | MySQL 直接上 | 后期要真用，避免 SQLite 迁移成本 |
| 测试 | 核心接口 + 主流程 | MVP 阶段不做全量覆盖 |

> 🎯 **复盘结论**：0→1 冷启动 = 意图定义（占 15% 时间）+ 规则前置 + 多 Agent 并行 + 边界收缩。**「59 分可运行版本先出来，再逐步补齐」**是 MVP 的正确节奏。

## 2. 案例二：成熟项目增量开发

### 2.1 项目背景

> 一个已有 3 年历史的订单系统（约 200 个 Java 文件），需新增「订单导出 Excel」功能。这是 **1→N 增量开发**的典型场景。

### 2.2 与 0→1 的差异点

| 维度 | 0→1 冷启动 | 1→N 增量开发 |
|------|-----------|-------------|
| 上下文来源 | 规则文件 + 意图 | **既有代码即上下文** |
| 首要风险 | 方向错误 | **破坏现有功能** |
| AI 工具推荐 | Claude Code | Codex（定点修改、token 省 3/4） |
| 核心约束 | 少 | 多（必须对齐现有模式） |

### 2.3 执行要点

```text
Step 1：让 AI 先「读懂」现状（1 个任务）
        读取 OrderController/OrderService/Order 实体
        → 输出「实现方案」供人工确认（禁止直接开写）

Step 2：确认对齐点
        ├── 遵循现有 Controller 命名与返回结构（R<T> 包装）
        ├── 复用现有 EasyExcel 依赖（不新增 POI 全量）
        ├── 导出接口走异步任务表（对齐现有报表模式）
        └── 权限注解 @PreAuthorize("hasRole('ADMIN')")

Step 3：增量实现（明确禁止改动范围）
        【约束】只新增 OrderExportService 及 Controller 方法
        【禁止】修改 OrderServiceImpl 现有方法；修改数据库表

Step 4：回归验证
        ├── 新增 3 个测试 + 全量测试跑通
        └── 人工回归 2 条核心链路（下单/查询）
```

> ⚠️ **增量开发铁律**：先「读现状出方案」，人工确认后再动手；改动范围显式声明，禁止夹带修改——成熟项目最大的 AI 事故就是「顺手重构了别人的代码」。

## 3. 案例三：内部工具快速交付

### 3.1 项目背景

> 运维团队需要「日志关键字告警配置页」，替换手工编辑配置文件。内部工具、用户 5 人、无安全合规压力——Vibe Coding 最佳适配场景。

### 3.2 轻量方案（2 小时交付）

```text
技术选型：直接选轻量栈（FastAPI + SQLite + 单页 HTML）
├── 理由：内部工具不需要 Java 全家桶
├── 让 AI 生成：CRUD + 正则匹配测试器 + 配置文件生成器
└── 交付：替换手工编辑，出活即可

验收标准（内部工具版）
├── 能增删改查告警规则 ✅
├── 能实时测试正则表达式 ✅
├── 生成的配置直接可用 ✅
└── 界面不丑（不追求精美） ✅
```

### 3.3 内部工具场景的取舍

| 事项 | 内部工具 | 生产系统 |
|------|---------|---------|
| 架构 | 能跑就行的单层 | 分层严谨 |
| 测试 | 主流程冒烟 | 覆盖率 80%+ |
| 安全 | 内网 + 基本鉴权 | 全面防护 |
| 文档 | 使用说明即可 | 完整文档 |
| 耗时 | 小时级 | 天级 |

> 💡 **适配思维**：场景决定工程强度——内部工具上「生产级规范」是浪费，生产系统用「内部工具标准」是事故。Vibe Coding 的成熟 = 知道**什么时候该多认真**。

## 4. 案例四：翻车复盘

### 4.1 事故经过

```text
背景：某团队用 Vibe Coding 做进销存系统，需求仅一句「做一个进销存」

第 1 天：AI 生成了完整可运行版本，团队欢呼
第 5 天：加「库存预警」功能时发现
         ├── 没有统一的库存 Service，逻辑散落在 6 个 Controller
         ├── 商品删除是物理删除（应该软删除 + 历史记录）
         ├── 订单金额用 Double（浮点误差导致对不上账）
         └── 无任何参数校验，前端传负数也能下单
第 12 天：重构成本远超重新开发，团队决定推倒重来
```

### 4.2 事故根因分析

| 根因 | 违反的原则 | 正确做法 |
|------|-----------|---------|
| 需求只有一句话 | 需求精确定义 | 四要素模板 + 验收标准量化 |
| 无规则文件 | 规则前置 | CLAUDE.md 先于代码 |
| 跳过拆解直接生成 | 四象限拆解 | 原子任务 + 优先级 |
| 无测试无审查 | 质量门禁 | 测试 + 三道闸审查 |
| 无重构规划 | 结构化重构 | 迭代周期内定期重构 |

### 4.3 反事故清单（一句话版）

```text
开工前问自己 5 个问题：
① 需求能写满四要素吗？（用户/场景/问题/方案）
② CLAUDE.md 写了吗？（技术栈/规范/安全基线）
③ 验收标准量化了吗？（性能/覆盖率/页面效果）
④ 任务拆到 2-4 小时粒度了吗？
⑤ 测试和审查计划安排了吗？
5 个问题有 3 个「没有」→ 不要开工，先补规范
```

## 5. 任务模板库

### 5.1 后端任务模板

```text
【角色】资深 {语言} 后端工程师，熟悉本项目分层架构
【任务】{功能描述，编号子步骤}
【约束】
- 技术栈：{框架/库/版本}，禁止引入未列出的依赖
- 架构：{分层要求}，参考 {代表文件} 的风格
- 安全：{认证/校验/防注入要求}
- 禁止：{禁止修改的文件 / 禁止使用的方式}
【输出】
- 文件清单 + 每个文件一句话职责
- 单元测试：{场景列表}
- 自检报告：代码是否符合上述约束
```

### 5.2 前端任务模板

```text
【角色】资深 {框架} 前端工程师
【任务】实现 {页面/组件}，功能点：{列表}
【约束】
- UI 组件库：{Element Plus / Antd...}，禁止自造组件
- 样式：{CSS 方案}，禁止内联样式散落
- 交互：{加载态/空态/错误态} 三态必须齐全
- API 对接：{baseURL + 拦截器约定}，参考 {示例文件}
- 禁止：修改 {公共组件/路由配置} 等文件
【输出】组件文件 + 交互说明 + 三态截图描述
```

### 5.3 测试任务模板

```text
【角色】资深测试工程师
【任务】为 {类/接口} 编写测试
【约束】
- 框架：{JUnit5+Mockito / Vitest...}，禁止新增框架
- 覆盖场景：{列出必测场景 + 边界}
- 命名：{given_when_then / describe_it}
- 断言：{断言库}，禁止 System.out 验证
【输出】测试文件 + 每个用例的测试意图一句话
```

## 6. 上手第一周行动计划

| 天 | 目标 | 行动 |
|---|------|------|
| Day 1 | 工具落地 | 选定主工具（推荐 Claude Code + Cursor 组合），跑通最小 demo |
| Day 2 | 规则体系 | 为自己的项目写 CLAUDE.md（技术栈/结构/规范），复盘后迭代 |
| Day 3 | 工作流练手 | 用一个真实小需求完整走五步法：四要素 → 拆解 → 四段式 → 迭代 → 验收 |
| Day 4 | 审查能力 | 对 AI 输出做三道闸审查，记录 AI 常见错误类型（幻觉/边界/风格） |
| Day 5 | 上下文工程 | 学会引用参考文件、反馈公式、增量修改，观察迭代轮次下降 |
| Day 6 | 多 Agent 尝试 | 拆 2 个并行子任务体验并行开发，熟悉 worktree 隔离 |
| Day 7 | 复盘沉淀 | 把一周踩坑写入 SOLVED.md，沉淀 2-3 个 Skill，形成个人工作流 |

### 6.1 第一周里程碑检验

```text
Day 7 检验清单：
[ ] 能 30 分钟内产出可运行 demo（0→1）
[ ] 能在成熟代码库安全增量开发（1→N，不破坏现有功能）
[ ] 反馈迭代平均 ≤ 2 轮收敛（模糊反馈消失了）
[ ] 有自己的 CLAUDE.md 模板 + 任务模板 + 踩坑记录
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 0→1 冷启动：意图定义 + 规则前置 + 多 Agent 并行 + 边界收缩，「59 分版本先跑起来」
> 2. 1→N 增量开发：先读现状出方案、人工确认后再动手，改动范围显式声明
> 3. 场景决定工程强度：内部工具小时级出活，生产系统规范拉满——成熟 = 知道何时多认真
> 4. 翻车复盘证明：规范缺一环，返工翻十倍；开工前 5 问能拦住 90% 的事故
