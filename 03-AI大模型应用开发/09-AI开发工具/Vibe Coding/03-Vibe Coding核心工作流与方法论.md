## 1. 核心认知：定义不是关键，工作流才是

> ⚠️ 多篇实战文章反复验证的核心结论：**Vibe Coding 的效率上限，取决于前置落地的标准化工程规则，而非提示词的精细程度。**

### 1.1 典型翻车案例

```text
❌ 错误姿势：丢一句口语化需求，让 AI 自由开发
输入：「做一个进销存系统」
结果：表面可运行
 ├── 目录混乱，无分层架构
 ├── 无参数校验，SQL 注入漏洞
 ├── 无任何测试
 └── 后期返工耗时远超规范开发

✅ 正确姿势：规则先行、AI 后置
输入：分层意图（业务 + 技术约束 + 验收标准）
结果：可交付、可维护、可演进
```

### 1.2 工作流 vs Prompt 的权重

| 环节 | 对成功率贡献 | 常见误区 |
|------|:---:|------|
| 需求精确定义 | **35%** | 需求含糊就开干 |
| 任务拆解与排序 | **25%** | 一个 Prompt 想干完所有事 |
| 上下文预配置 | **20%** | 不告诉 AI 代码风格/架构 |
| Prompt 设计 | 10% | 沉迷提示词技巧 |
| 反馈迭代 | 10% | 反馈模糊（「不对，重写」） |

## 2. 两种实践模式

| 维度 | 纯粹模式（Pure） | 负责任模式（Responsible） |
|------|-----------------|--------------------------|
| 哲学 | 完全信任 AI 输出 | AI 是 pair programmer |
| 人的介入 | 只看运行结果 | 逐段审查 + 测试把关 |
| 迭代速度 | 极快 | 中等 |
| 适用场景 | 快速原型、概念验证、Demo | **生产级开发** |
| 风险 | 技术债累积 | 人工成本 |
| 建议占比 | 20%（探索期） | 80%（交付期） |

> 🎯 **混合策略**：探索阶段用纯粹模式快速验证方向（"59 分可运行版本"），确认方向后切换负责任模式补齐工程能力——这是"99% AI + 1% 方向"渐进式开发的核心。

## 3. 标准化五步工作流

以「开发 CRM SaaS」为例完整走一遍：

### 第 1 步：需求精确定义

用**四要素模板**描述需求，并明确非功能需求：

```text
用户：销售主管（非技术人员）
场景：每天需要跟进 50+ 客户的销售进度
问题：Excel 管理混乱，跟进状态无法实时同步
解决方案：Web 端 CRM，自动记录跟进记录与待办提醒

非功能需求：
├── 性能：页面首屏 < 2s，支持 500 并发
├── 安全：登录需 2FA，数据加密存储
├── 兼容：Chrome/Edge 最新版本
└── 边界：本期不做移动端、不做 BI 报表
```

> ⚠️ 明确边界防范围蔓延——「做完再扩展」优于「边说边做」。

### 第 2 步：任务拆解与优先级排序

按**四象限**拆分（见第 4 节），核心要求：

- 每个任务控制在 **2-4 小时**可完成
- 明确依赖关系（先做数据层 → 再 API → 再页面）
- 为每个任务编写**独立 Prompt**，不混做

### 第 3 步：结构化 Prompt 设计

采用**角色-任务-约束-输出格式**四部分结构：

```text
【角色】你是一名资深 Java 全栈工程师，精通 Spring Boot 3 + Vue 3
【任务】实现客户列表页的分页查询 API
        - 使用 RESTful 规范，路径 /api/customers
        - 支持 keyword 模糊搜索（姓名/手机号）
        - 支持按跟进状态筛选
【约束】项目使用 MyBatis-Plus，禁止写原生 SQL 拼接
        代码风格遵循项目已有规范（参考 CustomerController 示例）
        所有异常统一抛出 BusinessException
【输出】Controller + Service + Mapper 三个文件
        附带 3 个单元测试用例
```

### 第 4 步：代码生成与迭代优化

「**生成 → 验证 → 反馈 → 迭代**」闭环：

| 环节 | 要点 |
|------|------|
| 生成 | 一次只做一个小任务，确保上下文完整 |
| 验证 | 运行、看效果、查日志、跑测试 |
| 反馈 | **必须具体精准**：✅「接口返回的 JSON 格式不正确，date 字段应为 yyyy-MM-dd」；❌「不对，重写」 |
| 迭代 | 增量修改，**拒绝全量重写**（会丢失有效逻辑、破坏规范） |

### 第 5 步：集成测试与部署

```text
① 编写集成测试（跨模块调用、数据库交互）
② 搭建 CI/CD 流水线（提交 → 构建 → 测试 → 部署）
③ 准备回滚计划（一键回滚到上一版本）
④ 灰度发布，观察监控指标
```

## 4. 四象限任务拆解法

按「**核心 → 重要 → 次要 → 优化**」四象限拆分：

```
                高价值
                 │
    ⚡ 核心（先做）      ⭐ 重要（随后）
    登录/权限/主流程     报表、通知、高级查询
                 │
                 ├────────────────── 高优先级
                 │
    🔹 次要（再做）       🌱 优化（最后）
    辅助页面、设置       动效、SEO、暗色模式
                 │
                低价值
```

| 象限 | 处理策略 | 示例 |
|------|---------|------|
| 核心 | 最高优先级，负责任模式开发 | 认证、支付、主业务流 |
| 重要 | 第二批次，可并行 Agent | 报表、导入导出 |
| 次要 | 批量交付，接受粗糙度 | 关于页、帮助中心 |
| 优化 | 有富余再做，纯模式试水 | 暗色主题、交互动效 |

## 5. 场景适配边界

### 5.1 四类高适配场景

| 场景 | 原因 | 效率提升 |
|------|------|:---:|
| **MVP 原型开发** | 快速验证、允许粗糙 | **-47% 耗时** |
| **内部工具迭代** | 低风险、迭代快 | 高 |
| **成熟代码库小功能增量** | 上下文充足、边界清晰 | 高 |
| **技术预研 Demo** | 一次性、不进生产 | 高 |

### 5.2 三类禁用场景

| 场景 | 风险 | 正确做法 |
|------|------|---------|
| **核心支付链路** | 模糊逻辑引发资金事故 | 严格评审 + 结构化需求文档 |
| **用户隐私数据处理** | 泄露风险、合规处罚 | 人工逐行审查 |
| **强监管合规功能** | 审计要求、责任归属 | 传统开发流程 + 代码溯源 |

> 📊 实测数据：原型阶段合理使用 Vibe Coding 降低 47% 耗时；**核心交易系统等强规则场景效率提升不足 10%**——工具不万能，场景决定价值。

## 6. 避坑要点清单

| # | 避坑要点 | 说明 |
|---|---------|------|
| 1 | **角色不能缺位** | AI 生成代码必须人工校验后再合并，不能无脑信任 |
| 2 | **上下文预配置** | 代码风格、依赖版本、架构逻辑提前同步给 AI |
| 3 | **增量修改，拒绝全量重写** | 全量重写 = 丢失有效逻辑 + 破坏规范 |
| 4 | **大型项目分片检索** | 超千文件项目用向量数据库分片存代码，按需检索防上下文丢失 |
| 5 | **结构化重构规划** | 每 2-3 个迭代周期做一次重构，避免技术债堆积 |
| 6 | **反馈精准化** | 模糊反馈 = 无效迭代（「不对」不如「这里错了」） |
| 7 | **日志可观测** | 让 AI 产出的代码自带日志，报错可追溯 |
| 8 | **验收标准前置** | 性能阈值、测试用例在开工前就写死 |

## 7. 效率度量方法

用数据验证 Vibe Coding 是否真的提效：

| 指标 | 定义 | 基线参考 |
|------|------|---------|
| 需求 → 可运行 MVP 时间 | 从意图定义到首个可运行版本 | 规范团队 4-8 小时 |
| 迭代单次成功率 | AI 修改一次直接通过的比例 | 纯模式 50-70% |
| 返工率 | 因需求含糊导致的返工占比 | 规范化后 <15% |
| 代码审查通过率 | 一次审查即合并的比例 | 规范团队 >80% |
| 长期可维护性 | 3 个月后改需求成本 | 有规范 vs 无规范差距 3-5 倍 |

> 🎯 一句话：**Vibe Coding 不是省掉流程，而是把流程前置**——前 20% 的时间花在意图定义与工程规范上，后 80% 的时间节省 10 倍。

---

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 工作流 > Prompt：五步法（需求 → 拆解 → Prompt → 迭代 → 部署）是效率基石
> 2. 两种模式按阶段切换：探索用纯粹模式、交付用负责任模式
> 3. 场景边界要清醒：MVP/内部工具/增量开发拥抱；支付/隐私/合规场景禁用
> 4. 反馈必须具体、迭代必须增量、验收必须前置——这三条决定成败
