# 04 - Codex 底层架构与训练

> 🎯 GPT-5-Codex = Transformer Decoder + 代码专项微调 + RLHF 工程对齐。理解训练流程才能理解为什么它有时"幻觉"

---

## 1. 基础架构

标准 Transformer 解码器架构，针对代码场景专项优化：

- 14KB 长代码记忆容量（足以读取完整仓库多文件上下文）
- 针对代码缩进、换行、特殊符号强化 Tokenizer
- 支持 FIM（Fill-in-the-Middle）补全模式——标准 Decoder 的增强

---

## 2. 训练数据

| 类别 | 内容 | 作用 |
|------|------|------|
| 开源代码 | GitHub 公开仓库 | 学习语法、框架 API、编程范式 |
| 技术文档 | 官方文档、API Reference | 学习正确 API 调用方式 |
| 编程问答 | StackOverflow、Issues、PR 讨论 | 学习 Debug 和问题解决模式 |
| 需求-代码对 | 自然语言描述 → 代码实现 | 学习从需求到代码的映射 |

---

## 3. 三阶段训练流程

### 阶段一：预训练（Pre-training）

```text
数据：海量自然语言 + 代码混合语料
目标：Next Token Prediction
产出：学会语法、逻辑、基本编程范式
```

### 阶段二：代码微调（Code Fine-tuning）

```text
数据：海量真实开发任务（需求→代码、Bug→修复、代码→审查意见）
目标：对齐人类工程师的编码习惯
产出：能从自然语言生成可用代码
```

### 阶段三：RLHF 工程对齐

```text
数据：基于真实 PR 接受率、代码审查通过率、测试通过率的人类反馈
目标：减少幻觉、提升代码可用性、学习"什么代码会被接受"
产出：更少幻觉、更符合工程规范的代码

关键：RLHF 教给模型的不是"怎么写代码"，而是"怎么写会被接受的代码"
  → 变量命名规范
  → 错误处理完整
  → 测试覆盖
  → 符合项目已有风格
```

## 4. Agent 自主工作核心机制

新一代 Codex 独有的完整闭环流程：

```text
Step 1: 接收自然语言需求
  "在 UserController 中添加根据邮箱查询用户的接口，包含参数校验和 Swagger 文档注解"

Step 2: 读取关联代码仓库
  → git clone / 读取项目结构
  → 分析现有 Controller/Service/Mapper 代码风格
  → 理解项目依赖和配置

Step 3: 生成代码变更 diff
  → 生成完整的 Controller 方法
  → 生成对应的 Service 方法
  → 生成单元测试

Step 4: 云端沙箱执行验证
  → 编译 → 运行测试 → 检查 Swagger 文档生成
  → 修复编译错误 → 重新测试

Step 5: 迭代修改
  → 测试失败 → 分析原因 → 修改代码 → 再测试
  → 直到所有测试通过

Step 6: 生成 PR
  → git diff + commit message
  → PR 标题 + 描述（改动说明、测试结果、风险点）
```

## 5. 关键前置假设（假设不成立会怎样）

| 假设 | 不成立的后果 |
|------|------------|
| 需求描述清晰、无歧义 | Codex 猜测意图→生成不符合预期的代码 |
| 项目代码规范、依赖可公开获取 | 依赖是内部私有 SDK→Codex 编造不存在的 API（幻觉） |
| 无高度私有的未开源框架 | 同上 |
