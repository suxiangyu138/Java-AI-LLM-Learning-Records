## 1. token 是性能的计量单位

**LLM 推理的所有性能指标都以 token 为轴**：**吞吐**（tokens/s——每秒生成多少个 token）、**延迟**（TTFT——首 token 到达时间；TPOT——每输出 token 的时间）、**显存**（KV cache 按 token 存）。**三个指标对应三个问题**：**"同时服务多少人"看吞吐**（批处理/连续批处理）、**"用户等多久"看 TTFT**（前缀缓存/投机采样）、**"模型装得下吗"看 KV cache**（显存预算）。**"性能优化的本质是 token 的调度"**——同一个模型，调度得好（批、缓存、投机）与调度得差，吞吐差 5-10 倍。**本体系的视角**：**不重讲推理框架**（部署工具体系/vLLM 体系讲调度），**讲 token 与性能的关系——为什么 token 是这些指标的天然单位**。

## 2. 吞吐与延迟：tokens/s 与 TTFT

**吞吐（throughput）**：**tokens/s**——单位时间生成的 token 总数——**服务端指标**：批量越大吞吐越高（GPU 算力摊薄），但单请求延迟越差——**"吞吐与延迟是跷跷板，批大小是支点"**。**2026 事实**：vLLM 的连续批处理（continuous batching）让吞吐随批大小近线性涨——**"满批跑，吞吐翻倍；单条跑，显存白费"**。

**延迟（latency）**：**TTFT（首 token 时间）**——从请求到第一个输出 token——**"用户感知的'快慢'主要是 TTFT"**：TTFT 决定首屏，TPOT 决定输出速度感。**TTFT 的组成**：**prompt 处理时间（输入 token 数 × 每 token 处理时间）+ 排队时间**——**"输入 token 多，TTFT 线性涨"**——长 prompt（RAG 检索结果、长历史）直接推高首屏延迟（07 篇窗口账本的性能面）。

## 3. KV cache：token 即显存

**KV cache 是 Transformer 推理的显存大头**：**每个已处理的 token 都要缓存其 K/V 向量**，供后续 token 的注意力计算使用——**"KV cache 大小 ≈ token 数 × 层数 × 头数 × 向量维度 × 2（K+V）× 字节数"**——**显存随 token 数线性涨**。**三个工程事实**：其一，**长上下文 = 大 KV cache**——128K 窗口的 KV cache 可达十几 GB——"**窗口不是白送的，每格都占显存**"（07 篇的硬件面）；其二，**批处理放大 KV**——**每个并发请求都有自己的一份 KV cache**——**"批大小 × 序列长度 = 显存预算"**；其三，**KV cache 复用是加速关键**——**前缀缓存（prefix caching）**：相同 prompt 前缀的 KV 直接复用（跳过重复 prefill）——"**缓存命中省的不是 token 钱，是 prefill 时间**"（07 篇 prompt caching 的性能面：vLLM 的 prefix caching 与 OpenAI 的 prompt caching 是同一思路的两端）。

## 4. 输入 token 与输出 token 的算力差异

**prefill（输入处理）与 decode（输出生成）是两种算力形态**：**prefill 是并行密集**——整个输入一次性计算（矩阵乘，GPU 利用率高）；**decode 是串行瓶颈**——**每次只生成 1 个 token，且要重新过一遍模型**（内存带宽受限，GPU 利用率低）——**"LLM 的慢，慢在 decode 的串行"**。**两个推论**：其一，**输入长影响 TTFT，输出长影响总时长**——**"省输出 token 不只是省钱，是省时间"**（06 篇成本优化与本节延迟优化的汇合点）；其二，**decode 阶段是投机采样的主战场**——（第 5 节）。**给应用工程师的结论**：**max_tokens 设得越紧，用户体验与成本越好**——"**输出 token 是成本与延迟的双重乘法因子**"。

## 5. 推理加速的 token 侧手段

**手段一：投机采样（speculative decoding）**——**小模型先草拟 N 个 token，大模型一次验证**——草拟对了就一次出 N 个（decode 从串行变批量）——**"用一个小模型的成本，买大模型的准确性"**——部署工具体系详讲（`../07-模型部署与工程化/` 交叉），token 侧认知：**"投机采样赌的是'下一个 token 可预测'——草拟接受率决定收益"**。

**手段二：前缀缓存（prefix caching）**——相同 prompt 前缀复用 KV——**多轮对话、RAG 固定上下文、工具定义常驻场景收益最大**——"**把稳定内容放前面，让缓存可以复用**"（07 篇第 6 节与本节同源）。

**手段三：输入压缩（prompt 压缩）**——**长 prompt 压缩后进窗口**（摘要/语义压缩）：prefill 时间线性降——"**输入 token 是 TTFT 的乘数，压缩输入 = 压缩首屏等待**"。

**手段四：批处理与并发**——连续批处理让 GPU 满跑——服务端手段（vLLM 体系交叉）。

**选型主线**：**"前缀缓存是免费的（改 prompt 结构即可），投机采样是模型侧的，输入压缩是应用侧的——先吃免费的前缀缓存，再谈别的"**。

## 6. 长文本与性能

**长文本是性能的放大镜**：**prefill 时间随输入线性涨**（1M token 的 prefill 即使并行也要数秒到数十秒）；**KV cache 显存线性涨**（128K 窗口十几 GB）；**注意力计算平方项**（完整注意力随序列长度平方涨——**长窗口模型靠稀疏注意力/线性注意力缓解，但仍是瓶颈**）。**长文本场景的三条实践**：其一，**能分块就分块**（RAG 化，07 篇策略三）——"**1M 文档全塞窗口 = 慢 + 贵 + 显存爆；检索 5K 进窗口 = 快 + 便宜 + 效果还好**"；其二，**异步处理长任务**——长文档分析走队列/批处理（用户不等同步响应）；其三，**测长文本性能用"每千 token 的 prefill 耗时"**——**"性能数字要按 token 归一化才可比"**（第 7 节）。

## 7. 性能实测方法论

**实测三件套**：**① TTFT**——`time.time()` 记录请求发出到首 token 流式到达（流式 API 场景）；**② 吞吐**——压测工具（wrk/自写并发脚本）测 tokens/s——**注意区分"单请求 tokens/s"与"服务端聚合 tokens/s"**（前者用户感知，后者成本效率）；**③ KV/显存**——`nvidia-smi` 或框架日志看 KV cache 占用——**"显存 = 模型权重 + KV cache + 激活值"三件套对账**。**对比纪律**：**同模型同 prompt 同批大小才有可比性**——"**性能数字要带上下文：模型、序列长度、批大小、硬件四要素缺一不可**"；**按 token 归一化**——"每千 token 的 prefill 毫秒数"比"1M token 处理 30 秒"更有迁移价值（第 6 节）。

## 8. 五个常见坑

- **坑一**：只测总耗时不拆 TTFT/TPOT——**"慢"不知道慢在哪段；流式接口分别记录**；
- **坑二**：拿吞吐当延迟——**服务端吞吐高 ≠ 用户响应快**；两个指标分开看（第 2 节）；
- **坑三**：长 prompt 不压缩直接上——**TTFT 线性涨；RAG/摘要先行**（第 6 节）；
- **坑四**：忽略 KV cache 显存——**并发一开 OOM；批大小 × 序列长度先算预算**（第 3 节）；
- **坑五**：性能对比不写四要素——**不可复现的 benchmark 等于没有；模型/长度/批大小/硬件写全**。
