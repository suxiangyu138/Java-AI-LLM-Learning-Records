## 1. Token：三个身份的同一件事

**Token（词元）是 LLM 处理文本的最小单位**——模型既不是按字符、也不是按单词理解文本，而是按 token 理解。它同时有三个身份：**语义单位**（模型在 token 序列上做注意力计算——输入的每个 token 映射为向量进入 Transformer）、**计费单位**（API 按 token 计价，input/output 分开计）、**窗口单位**（上下文窗口以 token 数度量——"128K 上下文"指 128K 个 token，KV cache 也按 token 占显存）。**"学 Token 就是学这三本账"**：模型内部怎么切（分词算法，02 篇）、按什么付钱（计数与成本，06 篇）、窗口怎么算（07/09 篇）——本体系 11 篇就是这三本账的展开。

## 2. 为什么需要分词

把文本喂给模型之前，必须先切成离散单元——**"连续文本 → 离散 token 序列"**这个动作叫分词（Tokenization）。为什么不能直接按字符或按单词？

**按字符的缺陷**：序列太长——英文单词平均 5-8 个字符，序列长度直接放大 5 倍以上，Transformer 的注意力计算随序列长度平方增长——**"按字符喂 = 计算量爆炸"**。

**按单词的缺陷**：词表爆炸与 OOV——英语有几十万常用词形（run/runs/ran/running…），词表存不下；新词、拼写变体、多语言词汇直接落到 <UNK>（未知词）——**"按单词喂 = 见不到的词就丢"**。

**子词方案（2026 年主流）**：在字符与单词之间找平衡——**"常见词整词保留（如 the/hello），罕见词拆成子词（如 tokenization → token + ization）"**——词表几万到几十万规模、序列长度可控、未知词总能拆成已知子词。**"分词的三层演进（字符→单词→子词）本质是'序列长度 vs 词表大小 vs 覆盖率'的三角权衡"**——子词是 2026 年唯一实践的答案（算法细节 02 篇）。

## 3. 一个画面：中英文的 token 差异

把同一句话放进 OpenAI 的 Tokenizer 可视化工具（00 篇参考来源），会看到：

```text
英文 "Hello world, this is a tokenizer test."
→ 8 个 token：约 3 个 token 覆盖 1 个英文单词

中文 "你好，世界。这是一个分词测试。"
→ 约 14-18 个 token：中文 1 个字 ≈ 1-2 个 token

代码 "def fibonacci(n): return n if n < 2 else fibonacci(n-1)+fibonacci(n-2)"
→ 约 18-22 个 token：代码的 token 密度介于中英文之间
```

**这个画面回答两个高频问题**：其一，"我的提示词该按多少 token 算"——**英文按"字数 ÷ 3"粗估、中文按"字数 × 1.5"粗估**（05 篇精确方法）；其二，"为什么中文贵"——**中文在 cl100k/o200k 里的词表覆盖不如英文**，同语义文本 token 更多（多语言公平性，05 篇）。**"看到画面再谈成本"——一切的估算直觉从这张表开始**。

## 4. 2026 现状与基线

**2026-08 基线：tiktoken 0.13.0（2026-07 发布）**。几个关键现状：

**算法**：**byte-level BPE 主导**——GPT-2/3/4、Llama、Gemma、Qwen2、Mistral 全部采用（02 篇）；2026 研究在"频率合并"之外探索统计显著性合并（Significance-Gain BPE，WikiText-103 困惑度降 13%）、跨语言公平（Parity-Aware BPE，语言成本基尼系数降 89%）、可学习分词（FLEXITOKENS）——**了解即可，工程上还是 byte-level BPE 的天下**。

**编码体系**：OpenAI 两代——**cl100k_base**（GPT-3.5/GPT-4 Turbo 及更早）与 **o200k_base**（GPT-4o 家族与 GPT-5 系，词表 20 万级、多语言覆盖更好）——"**2026 新模型都是 o200k 系，老编码只在存量模型上**"。

**工具**：tiktoken（OpenAI 官方，Rust 核心）仍是计数标准；puretiktoken（2026 新工具）零依赖纯 Python 逐字节兼容，适合受限环境（04 篇）；**版本纪律成为生产共识**——tiktoken 升级可致计数漂移 ±12%（04 篇坑）。

**定价**：输入 $0.10/M 到 $30/M、输出 $0.28/M 到 $180/M，**跨度 600 倍**——"**同一个应用，模型选错，成本差 48 倍**"（06 篇完整表）。

## 5. Token 与字节/字符/单词的关系

| 单位 | 与 token 的关系 | 一句话 |
|------|----------------|--------|
| 字节 | **token 的底层原料**：byte-level BPE 从 256 字节起步，任何字节序列都能编码 | 零 <UNK> 的保证 |
| 字符 | token 的平均覆盖：英文约 4 字符/token、中文约 0.7-1 字/token | 密度语言相关 |
| 单词 | 常见词整词 = 1 token；罕见词拆成 2-4 token | "3 token ≈ 1 词"是经验值 |
| 子词 | token 的本质形态：词根/词缀/字符组 | "token 是子词"才精确 |

**两个推论**：其一，**token 数是"文本长度 × 语言系数"**——同语义的英文/中文/代码，token 数不同（05 篇）；其二，**字节是唯一跨 tokenizer 公平的度量**——比成本、比压缩率时回到字节维度（BPB 度量，05 篇）。

## 6. 生态位置与五条边界

**生态位置**：token 是 LLM 全链路的"通用计量单位"——**Prompt 工程（窗口）、Function Calling（每轮调用计费）、RAG（检索内容入窗口）、LiteLLM（记账）、性能（tokens/s 吞吐）全以 token 为轴**。学它的价值：**会估算成本、会管窗口、会排 tokenizer 相关的错**——"token 是 AI 工程师的'元认知'：看得见模型的每一次呼吸"（00 篇分工）。

**五条边界**：其一，**token 不是语义单位**——同一个 token 在不同上下文里意思不同，模型学到的是"token 序列 → 语义"的映射，不是 token 本身有意义；其二，**tokenizer 不是通用的**——每个模型一套，跨模型直接比 token 数没有意义（08 篇）；其三，**token 计数不等于计费**——客户端估算 vs 服务端 usage，以 usage 为准（06 篇）；其四，**token 数不决定质量**——同样的 prompt 同样的 token 数，模型不同效果不同——"省 token 是工程问题，效果是模型问题"；其五，**本体系讲 token 的工程面**——模型的内部表示（embedding 层）看 Embedding 体系，注意力计算看 LLM 体系 01 篇。
