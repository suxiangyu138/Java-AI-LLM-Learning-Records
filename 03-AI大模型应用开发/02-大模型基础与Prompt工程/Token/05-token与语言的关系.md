## 1. token 密度的语言差异

**同一句话，不同语言 token 数不同**——这是 tokenizer 设计的直接后果，也是成本差异的根源。经验值（00 篇画面已见）：

| 文本类型 | token 密度 | 一句话 |
|---------|-----------|--------|
| 英文 | ~3 token/单词（约 4 字符/token） | 常见词整词 1 token |
| 中文 | 1 字 ≈ 1-2 token | 单字多被拆成 1-2 子词 |
| 日文/韩文 | 1 字 ≈ 1-3 token（平假名/谚文拆得更碎） | 语系距离英文最远 |
| 代码 | 介于中英文之间（约 2-4 token/词） | 标识符/符号混合 |
| emoji/生僻字 | 1 个 = 1-4 token（字节拆分） | byte-level 保证能编但贵 |

**"3 token ≈ 1 英文单词、中文 1 字 ≈ 1-2 token"是估算起点**——精确值永远以实际编码为准（04 篇 `len(enc.encode(...))`）；**估算应用场景**：prompt 长度预检、成本预算、窗口管理都用这个系数起步，再按实测校准（10 篇工具）。

## 2. 为什么中文 token 更多

**根源在词表的"语言配比"**：tokenizer 的词表由训练语料决定（03 篇第 4 节）——**英文语料占比高，英文常见词/词根整词进词表**；中文虽然也进词表，但**中文字符组合（词）的覆盖率远低于英文**——英文 "understand" 整词 1 token，中文"理解"大概率拆成 "理"+"解" 两个 token（或更多）。

**第二个原因是信息密度**：中文**单字信息密度高**——1 个字的信息量 ≈ 英文 1-2 个词——"**同样的信息量，中文天然需要更少的字，但每个字拆得更碎**"，两者叠加后中文同语义文本的 token 数约为英文的 1.2-1.5 倍（随词表质量波动）。**第三是编码历史**：早期词表（cl100k 时代）中文覆盖差，同文本 token 数高得离谱；**o200k 及 Llama-3/Qwen 的 100K+ 词表大幅改善**——"**词表越大，中文越便宜**"是 2026 的实测趋势（第 4 节）。

## 3. 代码与特殊文本

**代码的 token 密度介于中英文之间**：标识符（`def`/`return`）常见整词 1 token、驼峰/蛇形拼写被拆、符号（`{`/`=>`）单独成 token——**实测经验：代码行数 × 6-8 ≈ token 数**（一行 20-40 字符，约 6-8 token）。**代码场景的两个额外成本**：**缩进与空格**（Python 的空格是语法——空格的 token 也计费）；**长标识符**（`calculate_total_revenue` 拆成 3-5 token）。**特殊文本**：emoji 与生僻字靠 byte-level 编码（02 篇）——**"能编 ≠ 便宜"**：1 个 emoji 可能 2-4 token，**大量 emoji 的文本 token 数会显著高于字数直觉**。**给工程师的提示**：**系统提示词里少放长 emoji 串**（好看但不便宜），代码场景注意格式化的空白。

## 4. 多语言公平性：2026 的进展与账本

**2023 年的经典研究**（Petrov et al.）：**缅甸语/泰米尔语/马拉雅拉姆语用户每字符支付的 token 是英语的 5-15 倍**——"**说英语是免费，说小语种是溢价**"——这是 tokenizer 语料偏置的直接账单。

**2026 的进展**：**o200k_base、Llama-3、Gemma-2 的词表大幅收窄了语言差距**（大词表 + 多语言语料）；研究侧出现专门算法——**Parity-Aware BPE（ACL 2026）**：合并时优先提升"当前压缩最差语言"，跨语言 token 成本基尼系数降 89%；**写作系统级适配**：把词表重训适配新语言（乌克兰语 token 密度 2.71→1.80），保留原映射的 77-78%。**给工程者的账本**：**多语言产品的成本估算必须按语言分列**——"同一个功能，用户说中文和说英语，你的账单不一样"（06 篇预算治理）。

## 5. 三把公平的尺：TPC / BPC / BPB

**跨 tokenizer 比较 token 数没有意义**（词表不同），2026 年社区用三把"与 tokenizer 无关"的尺：

- **TPC（tokens per character，每字符 token 数）** = token 数 ÷ 字符数——**压缩率的直观度量**（英文约 0.25、中文约 1.0-1.5）；
- **BPC（bits per character，每字符比特）** = 每字符负对数似然 ÷ ln2——**跨 tokenizer 的语言模型质量比较**（per-token 困惑度跨词表不可比，BPC 可比）；
- **BPB（bits per byte，每字节比特）** = (val_loss / ln2) × (token 数 / 字节数)——**最公平的尺：回到字节**（字节是 tokenizer 无关的底层单位，01 篇第 5 节）。

**三把尺的使用场景**：**估算成本用 TPC**（字符数 × 语言系数 → token 数）；**论文/选型比模型用 BPC/BPB**（Parameter Golf 挑战赛就是用 BPB 比较 256-token 字节级与 32K BPE 词表）；**"说"成本时先问对方用的哪把尺**——"**TPC 是日常账本，BPC/BPB 是科研账本**"。

## 6. tokenizer 换版对成本的影响

**tokenizer 是"隐藏的版本变更"**：模型升级常带新 tokenizer（词表重训）——**同一文本 token 数可能大变**，成本与延迟随之变。**2026 的著名案例**：**Claude Opus 4.7 换新 tokenizer 后，同一文本生成的 token 比旧版多最高 35%**——"模型没变贵，tokenizer 让它变贵了"。**给工程者的三个动作**：其一，**升级模型时对比新旧 tokenizer 的 token 数**（跑同一批语料样本，看 TPC 漂移）；其二，**成本看板把"模型版本 + tokenizer 版本"作为维度**（成本异常先查 tokenizer 变更，00 篇误区二）；其三，**预算预留 10-20% 的 tokenizer 漂移余量**——"**tokenizer 换版是 2026 年成本波动的隐藏原因**"。

## 7. 五个常见坑

- **坑一**：拿英文 3 token/词 的系数估中文文本——**token 数差 2-3 倍；按语言分列估算**；
- **坑二**：以为词表大了所有语言都便宜——**大词表收窄差距但不消除**；小语种先实测再估（第 4 节）；
- **坑三**：代码场景按"字数"估——**按行数 × 6-8 更准**；缩进与长标识符是隐藏成本；
- **坑四**：跨 tokenizer 比"我的 prompt 多少 token"——**数字不可比；回到 TPC/字节维度**；
- **坑五**：模型升级不重测 token 数——**tokenizer 换版静默改变成本；升级必跑样本对比**（第 6 节）。
