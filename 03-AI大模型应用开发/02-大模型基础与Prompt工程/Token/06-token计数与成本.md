## 1. 计费结构：input / output / cache

**LLM API 的计费不是"一价全包"，而是三部分**：**输入 token**（prompt——含系统提示、历史消息、工具定义）按输入价计；**输出 token**（模型生成的内容）按输出价计——**输出价比输入价贵 2-6 倍**（成本结构里生成比读入贵）；**缓存命中 token**（prompt caching——重复的 prompt 前缀）按折扣价计——**Claude 的 prompt caching 折扣 90%**、**DeepSeek cache-hit 折扣 98%**（V4 Flash 命中后输入约 $0.0028/M）。

**两个推论**：其一，**"省钱先省输出"**——输出单价高，控制 max_tokens、引导短回答收益最大（第 6 节）；其二，**"重复的 prompt 前缀就是钱"**——把稳定内容（系统提示/工具定义）放 prompt 开头，让缓存命中——**"提示词的结构决定缓存命中率，缓存命中率决定折扣"**（07 篇详讲）。

**三个结构性事实**：其一，**价格跨度 600 倍**——输入从 $0.10 到 $30，输出从 $0.28 到 $180——"**价格不是围绕一个中位数的波动，是三个数量级的坐标系**"；其二，**前沿输出价差 >100 倍**——GPT-5.5 $30/M vs DeepSeek V4 Flash $0.28/M——**同任务换模型成本差 48 倍**（$12,000/月 vs $252/月的真实案例）；其三，**Batch API 打 5 折**——**不实时要求的任务走 batch，立刻半价**。**选型心法**：**能力达标的前提下按成本排序**——"先验证效果，再算账选型"（08 篇选型）。

## 3. 成本估算公式

```python
def estimate_cost(model: str, prompt_tokens: int, output_tokens: int,
                  cache_hit_tokens: int = 0, price: dict | None = None) -> float:
    """估算单次调用成本（美元）。价格表从 06 篇定价表维护。"""
    p = price or PRICES[model]
    cost = (prompt_tokens - cache_hit_tokens) * p["input"] / 1e6 \
         + cache_hit_tokens * p["cache"] / 1e6 \
         + output_tokens * p["output"] / 1e6
    return cost

# 调用前估算 prompt 长度（04 篇 tiktoken），输出按历史均值或 max_tokens 上限估
prompt_cost = estimate_cost("gpt-5.4", prompt_tokens=len(enc.encode(prompt)), output_tokens=500)
```

**估算四步**：**① 数 prompt token**（tiktoken/HF，04 篇）；**② 估输出 token**（按任务历史均值，冷启动用 max_tokens 上限——**"预算用上限，报告用实际"**）；**③ 算缓存命中**（稳定前缀长度，07 篇）；**④ 乘单价加总**。**月成本 = 单次成本 × 调用量**——**"先把单次成本公式写对，月账单就是乘个数"**；量大的应用把估算器变成中间件（第 5 节）。

## 4. 账单真相：usage 字段

**客户端估算只是估算，账单以 API 返回的 `usage` 字段为准**——每次响应都带 `usage.prompt_tokens` / `usage.completion_tokens` / `usage.total_tokens`（部分供应商含 `cache_read_input_tokens`）。**三个纪律**：其一，**计费口径以 usage 为准**——估算用于预算与预警，结算看 usage；其二，**推理模型（o1/o3 类）的显示 token 数与计费数可能不同**——内部思维链的 token 计费口径特殊，"**别拿 tiktoken 数完就当账单**"（04 篇坑七）；其三，**把 usage 落库**——每次调用的 usage 进日志/数据库，**成本看板从 usage 聚合，不从估算器聚合**（LiteLLM 的记账功能就是这个模式——`../LiteLLM 多模型适配/00-LiteLLM知识体系总览.md` 交叉）。**"估算用于预算，usage 用于结算"是成本管理的铁律**。

**usage 的扩展字段**：部分供应商返回 `cache_read_input_tokens`/`cache_creation_input_tokens`（缓存命中与缓存写入分列）与 `reasoning_tokens`（推理模型思维链）——**按字段分类记账**："缓存折扣"与"思维链成本"是 2026 成本看板的两大新列——只看 total_tokens 会漏掉"缓存到底省了多少"与"思考到底花了多少"。

## 5. 预算治理实践

**预算治理五件套**：**① 单次预算**——每次调用设 max_tokens + 超限告警（输出失控的第一道闸）；**② 单用户/单租户预算**——按 API key/租户设月预算（LiteLLM 的虚拟 key 预算能力，交叉）；**③ 日成本看板**——按"模型 × 租户 × 功能"聚合 usage（**tokenizer 换版导致的成本漂移先在看板露头**，05 篇第 6 节）；**④ 告警阈值**——日成本超预期 20% 告警、超 50% 熔断降级（换便宜模型/降采样）；**⑤ 月度复盘**——**"成本是产品指标不是财务指标"**：每月的"每千次请求成本"趋势，比绝对金额更有管理价值。**2026 的治理主线**：**"预算不是事后看账单，是事前的单价选择 + 事中的 usage 监控 + 事后的趋势复盘"**。

## 6. 成本优化的 token 侧手段

**优化优先级排序（按性价比）**：**① 控输出**——max_tokens 设实际需要、提示词引导短答（输出单价最高）；**② 吃缓存折扣**——稳定内容前置、工具定义固定排序（Claude 90%/DeepSeek 98% 折扣，07 篇）；**③ 减输入**——精简系统提示（prompt 压缩、去掉冗余示例）、历史消息窗口化（07 篇）；**④ 模型降级**——简单任务走 mini/flash 档（$0.75 vs $2.50，同模型族三倍价差）；**⑤ Batch 化**——非实时任务 batch 半价。**心法**：**"先省贵的（输出），再省多的（输入），最后省单价（选型）"**——多数团队把顺序做反了（一上来就换模型，其实输出失控才是大头）。

## 7. 五个常见坑

- **坑一**：只按输入价估算——**输出价高 2-6 倍，输出失控才是成本大头**；
- **坑二**：缓存折扣不算进预算——**缓存命中率高的应用，实际成本比估算低得多**（反之亦然）；
- **坑三**：拿估算器当月账单——**以 usage 为准**；估算器只做预算与预警（第 4 节）；
- **坑四**：全任务用旗舰模型——**简单任务 mini/flash 档 + batch 半价**，能力与成本分开选；
- **坑五**：预算告警只看绝对值——**看"每千次请求成本"趋势**，绝对值随调用量涨跌没有告警意义；
- **坑六**：只设总额不设单租户限额——**一个租户打爆全月预算；按租户/按 API key 分列限额**（LiteLLM 虚拟 key 的预算能力，交叉）。
