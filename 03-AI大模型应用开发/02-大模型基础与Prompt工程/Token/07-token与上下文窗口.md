## 1. 上下文窗口：token 的"内存"

**上下文窗口（context window）是模型一次调用能"看到"的 token 总量**——包括系统提示、历史消息、工具定义、用户输入和生成内容。**"窗口是模型的内存，token 是内存的字节"**：一次调用里，窗口塞不下就是截断/报错；塞得下但太大，就是延迟与成本的平方级增长（注意力计算与输入 token 数相关）。**两个推论**：其一，**窗口不是"越大越好"，是"够用 + 付得起"**——2026 年主流 128K-1M，但**填满 1M 的成本各模型差 36 倍**（第 2 节）；其二，**窗口管理是 AI 应用的"内存管理"**——**"应用工程师的日常不是调模型，是决定什么进窗口、什么不进、什么先走"**。

## 2. 2026 窗口格局

| 模型 | 上下文 | 填满 1M 的价格（输入） |
|------|--------|----------------------|
| DeepSeek V4 Flash | 1M | $0.14 |
| GPT-5.4 | 272K-1M | $2.50 |
| Claude Sonnet 4.6 | 200K-1M | $3.00 |
| GPT-5.5 / Claude Opus 4.8 | 1M / 200K-1M | $5.00 |
| Claude Haiku 4.5 | 200K-1M | $1.00（0.2M 档） |

**2026 的三个趋势**：其一，**窗口军备竞赛放缓**——200K-1M 成为主流区间，**拼"窗口内怎么用"超过拼"窗口多大"**；其二，**长窗口便宜化**——DeepSeek 把 1M 档打到了 $0.14——"**窗口的稀缺性在 2026 已经变成价格问题**"；其三，**输出上限成为新瓶颈**——部分模型输出限制远小于窗口（如 384K 输出已是大者），**"读得进 1M，写得出多少"是两件事**。**选型心法**：**短任务（问答/分类）选小窗口模型省钱，长文档任务选大窗口**——"窗口按任务配，不按参数配"。

## 3. 窗口的组成与计价

**一次调用的窗口消费 = 系统提示 + 工具定义 + 历史消息 + 当前输入 + 输出**——**五个部分全按 token 计费，且每次调用都要重复支付"已见过的 token"**（除非缓存命中，第 6 节）。**多轮对话的窗口账本**：第 N 轮的成本 = 累计全部历史 + 本轮输入 + 输出——**"对话越长，每轮越贵"**是长会话成本曲线的本质（00 篇误区六的机制层）。**给应用架构的启示**：**把"窗口里的内容"分层管理**——稳定层（系统提示/工具定义：不变，吃缓存）、会话层（历史消息：滚动）、即时层（当前输入：必在）——**"分层是窗口管理的第一步"**（第 4 节策略落地）。

## 4. 窗口管理三策略

**策略一：截断（truncation）**——**窗口超限时丢最旧的消息**（或按重要性丢）。实现简单、成本可控，但**丢的是"早期事实"**——多轮对话里用户第一轮的需求被丢，模型后期"失忆"。**适用**：短会话、上下文强依赖当前轮的任务。**细节**：**丢历史不丢系统提示**；保留最近 N 轮 + 首轮（首轮常含任务定义）是通用折中。

**策略二：压缩（summarization）**——**超限时把旧消息压缩成摘要**再进窗口。多一次摘要调用（成本 + 延迟），但**保住"全局事实"**。**适用**：长会话（客服/Agent 多轮）、事实累计型任务。**细节**：**异步压缩**（空闲时压，不进请求路径）、摘要放窗口头部（07 篇缓存逻辑）。

**策略三：外部化（RAG 化）**——**不把全部历史塞窗口，把"需要的事实"检索进窗口**——历史落库/向量化，每次按相关性取回。**窗口消费从 O(会话长度) 降到 O(检索结果)**。**适用**：知识密集型、超长文档（RAG 体系交叉：`../04-RAG检索增强生成/` 全链路）。**三策略选型主线**：**"短会话截断、长会话压缩、超长文档 RAG"**——多数应用是"截断兜底 + 压缩降级 + RAG 治本"的组合（10 篇实战）。

## 5. 截断与摘要：工程细节

**截断的工程四问**：**① 按什么截**——按消息（保留完整语义）而不是按字符硬切（硬切会切断半句话）；**② 留多少**——保留最近 N 轮 + 首轮（任务定义常在首轮）；**③ 谁来算**——编码计数（04 篇），**截断后必须重算再发**；**④ 超限怎么办**——客户端截断（自己控制）vs 服务端 400（放弃控制）——**"永远客户端先截，别把 400 当兜底"**。

**摘要的工程三问**：**① 谁摘要**——单独调用小模型（Haiku/Mini 档）做摘要，**"摘要的活别让主模型干"**（贵）；**② 何时摘要**——**异步/空闲时**（聊天场景用户打字间隙），不进请求路径；**③ 摘要格式**——**保留"事实清单"而非"叙述"**（"用户要求退款，订单号 A1024"优于"用户表达了退款意愿"）——**摘要的质量决定后期效果**。**注意**：摘要也有 token 成本与信息损耗——**"压缩是花小钱省大钱，但压缩率太高等于失忆"**（50% 压缩率是经验安全线）。

## 6. prompt caching 与窗口

**prompt caching（提示缓存）是窗口计费的最大折扣**：**相同的 prompt 前缀（系统提示/工具定义/历史开头）被服务端缓存，命中部分按折扣价计费**——Claude 90% 折扣、DeepSeek 98%（命中后 V4 Flash 输入约 $0.0028/M）。**四个实战要点**：**① 稳定内容前置**——系统提示、工具定义、固定示例放 prompt 最前面（**缓存按前缀匹配，越靠前越稳定越易命中**）；**② 工具定义固定排序**——**同一批工具每次声明顺序一致**（顺序变了 = 前缀变了 = 缓存失效——Function Calling 体系的"缓存纪律"交叉）；**③ 动态内容后置**——用户输入、时间戳、动态检索结果放后面（前缀不动）；**④ 长会话天然吃缓存**——历史消息前段稳定命中，**多轮对话的边际成本远低于直觉**。**"提示词的结构决定缓存命中率，缓存命中率决定折扣"**（06 篇的机制层）。

## 7. 与 RAG / Function Calling 的配合

**RAG 的窗口账**：检索结果进窗口（临时）→ 每条结果 = token 成本 → **检索数量与窗口的权衡**——"检索 10 条 × 500 token = 5K token 输入"——**top_k 不是效果参数，是成本参数**（RAG 体系检索优化交叉）；**2026 长上下文 + RAG 的组合**：窗口大到能装下"整库切片"时，RAG 退化为"选哪一段装窗口"——**"窗口大了，检索的目标从'找事实'变成'挑预算'**"。

**Function Calling 的窗口账**：**工具定义常驻窗口**（每次调用都付）——**工具越多定义越长，输入成本线性涨**；工具调用结果回传也占窗口。**优化纪律**（Function Calling 体系交叉）：**工具描述 100-200 token 内、不用的工具别声明、工具结果 4KB 截断/摘要**——"**工具是窗口的常驻居民，瘦身等于减租**"。

## 8. 五个常见坑

- **坑一**：窗口超限等 400 报错——**客户端先截断再发**（第 5 节）；
- **坑二**：按字符硬截断——**切断半句话，模型输出质量崩**；按消息截；
- **坑三**：工具定义顺序每次不同——**缓存命中率归零**；固定排序（第 6 节）；
- **坑四**：摘要用主模型 + 同步做——**又贵又慢**；小模型异步压缩；
- **坑五**：以为窗口大就不用 RAG——**窗口大 ≠ 便宜**（1M 填满 $0.14-$5）；**检索是成本治理不是效果妥协**。
