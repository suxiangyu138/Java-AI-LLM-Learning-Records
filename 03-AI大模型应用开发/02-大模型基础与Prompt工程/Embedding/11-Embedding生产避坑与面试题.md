## 1. 生产避坑 TOP 10

| # | 坑 | 现象 | 解决方案 |
|---|------|------|----------|
| 1 | **不同模型向量混用** | 检索结果随机、完全不对 | 入库和查询必须用同一个模型 |
| 2 | **未做向量归一化** | 内积 ≠ 余弦相似度 | 检索前归一化到单位长度 |
| 3 | **文本未预处理** | 换行符、多余空格影响向量 | strip + 替换 \n + 合并空格 |
| 4 | **切片过大** | 向量被无关信息稀释 | chunk_size 控制在 300-800 |
| 5 | **忽视 Overlap** | 边界信息丢失 | 设 10-15% 重叠 |
| 6 | **无缓存重复计算** | API 费用暴涨、响应慢 | 加 SQLite/Redis 持久化缓存 |
| 7 | **维度选择盲目** | 256 维精度不够、3072 维存储爆炸 | 512-1024 维是最佳平衡 |
| 8 | **只用 Dense 检索** | 专有名词/代码匹配差 | 加 BM25 做混合检索 |
| 9 | **忽略 Rate Limit** | 批量操作被限流 → 超时 | 加指数退避重试 |
| 10 | **无降级方案** | API 挂掉 → RAG 瘫痪 | 本地 Ollama 作为 fallback |

## 2. 性能陷阱与优化

### 2.1 内存陷阱

```text
陷阱：10 万 × 1024 维 × 4 bytes = 400MB → 还好
      100 万 × 1024 维 × 4 bytes = 4GB → 开始疼
      1000 万 × 1024 维 × 4 bytes = 40GB → 单机扛不住

优化：
  ✅ 降低维度（1024→512）→ 内存减半
  ✅ 乘积量化（PQ）：向量压缩 4-8 倍
  ✅ 磁盘索引（DiskANN）：热数据在内存，冷数据在 SSD
```

### 2.2 检索延迟陷阱

```text
陷阱：暴力检索 O(N×dim) — 100 万 × 1024 维 → ~100ms → 太慢
     用户期望 < 50ms！

优化：
  ✅ HNSW 图索引：~1ms（精度 ≈98%）
  ✅ IVF+PQ：~5ms（精度 ≈95%）
  ✅ GPU 加速：10 万+ 向量用 GPU FAISS
```

## 3. 数据质量陷阱

| 陷阱 | 现象 | 预防 |
|------|------|------|
| **空文本入库** | 零向量 → 所有 query 都与它相似 → 垃圾结果排在前面 | 索引前过滤空文本 |
| **文档重复** | 同一内容多处出现 → 检索结果重复 | 索引前去重（MD5/SimHash） |
| **语言混合** | 中英混杂的向量 → 检索不准 | 分开处理不同语言 |
| **格式噪音** | PDF 转文本的页眉页脚混入 | 预处理管线清除 |
| **过期文档** | 旧版本文档仍在索引中 | 版本化索引 + 定时清理 |

## 4. 模型陷阱

### 4.1 模型选择陷阱

```text
陷阱 1：用英文模型处理中文
  → text-embedding-ada-002 的中文效果远不如 BGE-M3
  → 中文场景必须用中文优化模型

陷阱 2：追求最大维度
  → 3072 维 vs 1024 维 → 精度提升 2%，存储增加 3 倍
  → 大多数场景 512-1024 维足够

陷阱 3：忽略模型更新
  → ada-002 → text-embedding-3-small：价格降 80%，精度升
  → 定期关注新模型发布

陷阱 4：微调 Embedding 模型
  → 通用 Embedding 模型已经很好了
  → 微调需要大量高质量标注数据
  → 大多数场景不需要微调
```

### 4.2 模型版本管理

```python
class ModelVersionManager:
    """Embedding 模型版本管理"""
    
    def __init__(self):
        self.versions = {
            "v1": {"model": "text-embedding-ada-002", "dim": 1536},
            "v2": {"model": "text-embedding-3-small", "dim": 1536},
            "v3": {"model": "bge-m3", "dim": 1024},
        }
    
    def migrate_index(self, index, from_version, to_version):
        """模型升级时迁移索引"""
        if from_version == to_version:
            return index
        
        print(f"警告：模型变更 → 需要重建所有向量索引！")
        print(f"  从: {self.versions[from_version]}")
        print(f"  到: {self.versions[to_version]}")
        print(f"  影响: {index.ntotal} 个向量需要重新计算")
        
        # 必须全量重建（不同模型向量空间不同）
        return None  # 返回 None 表示需要重建
```

## 5. 高频面试题精选

### Q1: Embedding 和 One-Hot 编码的区别？

```text
One-Hot：
  "猫" → [1, 0, 0, ..., 0]（词表大小维，极其稀疏）
  所有词距离相同 → 无语义信息

Embedding：
  "猫" → [0.12, -0.34, ..., 0.78]（低维密集向量）
  "猫咪" 与之距离近 → 有语义信息

本质区别：One-Hot 是符号表示，Embedding 是语义表示
```

### Q2: 余弦相似度和欧氏距离怎么选？

```text
余弦相似度：只关心方向 → 适合文本（长度不影响语义）
  例："数据库连接超时" vs "连接超时" → 余弦高 ✅

欧氏距离：关心绝对距离 → 适合需要考量"量级"的场景
  例：图片像素差异 → 欧氏距离 ✅

RAG 默认用余弦相似度
```

### Q3: Embedding 模型和 LLM 的关系？

```text
Embedding 模型：Encoder-Only，输出固定长度向量，不能生成文本
LLM：Decoder-Only，输出文本序列，不能直接给向量

两者是搭档：
  Embedding → 找到相关文档（检索）
  LLM → 基于文档生成回答（生成）
```

### Q4: 为什么不同 Embedding 模型的向量不能混用？

```text
每个模型有自己独立的向量空间：
  BGE-M3 的 [0.5, -0.3, 0.8] ≠ text-embedding-3 的 [0.5, -0.3, 0.8]
  同一个数字在不同模型空间中的"含义"完全不同

类比：中文的"手紙"（信）≠ 日文的"手紙"（信）→ 同一写法不同含义

解决方案：
  ✅ 永远用同一个模型做索引和查询
  ✅ 换模型 → 必须重建所有索引
```

### Q5: 如何评估 Embedding 模型的好坏？

```text
① MTEB 基准（通用评估）
  涵盖检索、分类、聚类、STS 等 8 类任务

② 业务自评估（关键！）
  用真实业务数据构建评估集
  计算 Recall@K、NDCG@K

③ 人工评估
  抽检 Top-5 检索结果 → 人工判断相关性

④ 用户反馈
  ✅ 查看 / ❌ 跳过 / ⚠️ 投诉
```

## 核心要点回顾

- 生产第一坑：不同模型向量混用 → 检索结果全错
- 向量归一化是基本功（内积=余弦相似度的前提）
- 缓存是性能优化第一手段（相同文本绝不重复计算）
- Dense + Sparse 混合检索 → 精度天花板最高
- 换模型 = 全量重建索引，做好版本管理和迁移规划
