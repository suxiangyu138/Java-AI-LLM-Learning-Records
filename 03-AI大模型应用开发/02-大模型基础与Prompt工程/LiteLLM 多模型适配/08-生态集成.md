## 1. 集成全景：三种接入层次

```text
层次一：Python 代码内（SDK）
  业务代码 → litellm.completion()     （02 章）

层次二：任何语言（Proxy OpenAI 兼容）
  Python/Java/Node/Go → OpenAI SDK 换 base_url  （本章）

层次三：框架内嵌（LangChain 等）
  LangChain → ChatLiteLLM / OpenAI 兼容端点
```

| 层次 | 适用 | 特性 |
|------|------|------|
| SDK | Python 单体 | 零部署、回调丰富 |
| Proxy | 多语言/多服务 | 治理统一、语言无关 |
| 框架 | LangChain 生态 | 框架原生 |

> 🎯 **核心要点**：**三层次覆盖所有接入场景**——Python 单体用 SDK，企业异构栈用 Proxy，框架生态用框架适配器。核心思想一致：**业务代码只认统一接口**。

## 2. OpenAI SDK 直连 Proxy

```python
# Python：OpenAI SDK 换两个配置即接入（06 章 §3）
from openai import OpenAI

client = OpenAI(
    base_url="http://litellm-proxy:4000/v1",
    api_key="sk-virtual-key-xxx",       # 虚拟 key
)

resp = client.chat.completions.create(
    model="pro-llm",                    # 逻辑名
    messages=[{"role": "user", "content": "你好"}],
)
```

```bash
# 命令行 curl（脚本/调试）
curl http://litellm-proxy:4000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer sk-virtual-key-xxx" \
  -d '{"model": "pro-llm", "messages": [{"role": "user", "content": "你好"}]}'
```

| 接入点 | 改动 | 说明 |
|--------|------|------|
| base_url | 指向网关 | 唯一必改 |
| api_key | 虚拟 key | 权限/预算绑定 |
| model | 逻辑名 | 03 章别名 |

> 💡 **"OpenAI 兼容"的威力**：凡是有 OpenAI SDK 的语言（Python/Java/Node/Go/.NET/Rust）都能用——**换 base_url 就是接入**。这就是网关"语言无关"的含义。

## 3. 其他语言：curl / Node / Java / Go

```javascript
// Node.js：openai 包换 base_url
import OpenAI from "openai";
const client = new OpenAI({
  baseURL: "http://litellm-proxy:4000/v1",
  apiKey: "sk-virtual-key-xxx",
});
const resp = await client.chat.completions.create({
  model: "pro-llm",
  messages: [{ role: "user", content: "你好" }],
});
```

```java
// Java：OpenAI Java SDK 换 baseUrl
OpenAIClient client = OpenAIClient.builder()
    .baseUrl(URI.create("http://litellm-proxy:4000/v1"))
    .apiKey("sk-virtual-key-xxx")
    .build();
ChatCompletion completion = client.chatCompletions().create(
    ChatCompletionRequest.builder()
        .model("pro-llm")
        .messages(List.of(ChatMessage.of("user", "你好")))
        .build());
```

```go
// Go：openai-go / 任意 OpenAI 兼容客户端
// 相同模式：base URL + 虚拟 key + 逻辑名
```

| 语言 | 客户端 | 接入方式 |
|------|--------|---------|
| Python | openai | base_url + api_key |
| Node.js | openai npm | baseURL + apiKey |
| Java | OpenAI Java SDK | baseUrl + apiKey |
| Go | openai-go | BaseURL + APIKey |
| 其他 | 任意 OpenAI 兼容客户端 | 同模式 |

> 🎯 **核心要点**：**接入 Proxy = 语言无关**——任何语言都只需"OpenAI 兼容客户端 + base_url 指向网关"。Java 后端（本仓库主线）接入 LiteLLM 就三行配置（Java 生态集成实践在 OpenAI兼容接口/05 有更多细节）。

## 4. LangChain / LlamaIndex 集成

```python
# LangChain：ChatLiteLLM（框架原生适配器）
from langchain_litellm import ChatLiteLLM

llm = ChatLiteLLM(model="gpt-4o")          # 直接统一接口
# 或走 Proxy（OpenAI 兼容）
from langchain_openai import ChatOpenAI
llm = ChatOpenAI(
    base_url="http://litellm-proxy:4000/v1",
    api_key="sk-virtual-key-xxx",
    model="pro-llm",
)

# 框架链/Agent 直接用
chain = prompt | llm | parser
```

```python
# LlamaIndex：同模式（LiteLLM 或 OpenAI 兼容端点）
from llama_index.llms.litellm import LiteLLM
llm = LiteLLM(model="gpt-4o")
```

| 框架 | 适配器 | 说明 |
|------|--------|------|
| LangChain | `langchain_litellm.ChatLiteLLM` | 原生接入 SDK |
| LangChain | ChatOpenAI + base_url | 经 Proxy |
| LlamaIndex | `llama_index.llms.litellm` | 原生接入 |

> 💡 框架集成的意义：**Chain/Agent 代码用框架抽象，模型层用 LiteLLM**——"框架管编排、LiteLLM 管模型"，职责清晰（与 FC 体系 08 章适配层思想一致）。

## 5. FastAPI 服务内嵌

```python
# FastAPI + LiteLLM：异步优先（02 章 §3 铁律）
from fastapi import FastAPI
from litellm import Router

app = FastAPI()
router = Router(model_list=[...])          # 全局单例（复用连接）

@app.post("/chat")
async def chat(req: ChatRequest):
    resp = await router.acompletion(       # ⭐ 必须异步版
        model=req.model,
        messages=req.messages,
        metadata={"user_id": req.user_id}, # 成本归属
    )
    return {"content": resp.choices[0].message.content}

@app.post("/chat/stream")
async def chat_stream(req: ChatRequest):
    async def gen():
        async for chunk in router.acompletion(model=req.model,
                                              messages=req.messages, stream=True):
            yield f"data: {chunk.choices[0].delta.content}\n\n"
    return StreamingResponse(gen(), media_type="text/event-stream")   # SSE
```

| FastAPI 集成要点 | 说明 |
|-----------------|------|
| Router 全局单例 | 复用连接池（lifespan 建，FastAPI 体系 04 章） |
| acompletion | async 环境必须异步版 |
| metadata | 成本归属（05 章） |
| SSE 流式 | StreamingResponse（FastAPI 体系 08 章） |

> 🎯 **核心要点**：FastAPI + LiteLLM = "**生产 API 的标准组合**"——`lifespan 建 Router + acompletion + SSE` 三段式（FastAPI 体系 09 章部署直接适用）。Agent 循环（FC 体系）的模型层换 LiteLLM 即多平台。

## 6. 与 Agent / MCP 生态结合

```text
Agent 栈中的位置：
  业务/Agent 循环（FC 体系）
       ↓ 模型调用
  LiteLLM（统一接入层）      ← 本体系
       ↓
  OpenAI/Claude/DeepSeek/vLLM

MCP 结合：
  MCP 管"工具分发"（06-MCP协议 体系）
  LiteLLM 管"模型接入"
  → 工具 + 模型两条管线并行，各管一段
```

| 结合点 | 做法 |
|--------|------|
| Agent 循环 | 循环里模型名换逻辑名（FC 体系 03 章循环 + 本体系） |
| 多平台 Agent | 一套循环代码，LiteLLM 换平台（FC 体系 08 章适配层的现成实现） |
| MCP 工具 | 工具侧 MCP，模型侧 LiteLLM，互不干扰 |
| 成本归属 | metadata 带 user_id → Agent 会话级成本 |

> 💡 完整栈的心智：**MCP（工具怎么来）+ LiteLLM（模型怎么调）+ FC 循环（怎么编排）+ FastAPI（怎么服务）**——四条管线各管一段，2026 年生产 Agent 栈的标准拼图。

## 7. 集成选型决策

```text
接入方式怎么选？
├─ Python 单体/脚本 → SDK（litellm.completion）
├─ 多语言/多服务/多团队 → Proxy（OpenAI 兼容端点）
├─ LangChain 生态 → langchain_litellm
├─ 已有 OpenAI 代码 → 换 base_url 即接入 Proxy
└─ Java 后端 → OpenAI Java SDK + base_url
```

| 场景 | 推荐 |
|------|------|
| 快速实验 | SDK |
| 生产多服务 | Proxy |
| LangChain 项目 | 框架适配器 |
| 存量 OpenAI 代码 | base_url 迁移（最小改动） |

## 8. 常见坑

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 1 | async 环境用同步 | 事件循环冻结 | acompletion |
| 2 | 忘传虚拟 key | 401 | 每个调用方独立 key |
| 3 | 模型名用物理名 | 网关不认识 | 用逻辑名 |
| 4 | LangChain 版本不匹配 | 适配器报错 | 锁定版本 |
| 5 | Router 每次请求新建 | 连接浪费 | 全局单例（lifespan） |
| 6 | 流式忘处理 delta | 输出拼不全 | 增量拼接（FC 体系 07 章） |
| 7 | metadata 不传 | 成本无归属 | 强制 metadata |
| 8 | 框架层与模型层耦合 | 换栈困难 | 框架管编排、LiteLLM 管模型 |

## 9. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 三层次：SDK（Python）/ Proxy（多语言）/ 框架适配器 |
| 2 | Proxy 接入 = base_url + 虚拟 key + 逻辑名三配置 |
| 3 | 语言无关：任何 OpenAI 兼容客户端都能接 |
| 4 | LangChain/LlamaIndex 有原生适配器 |
| 5 | FastAPI 组合：lifespan Router + acompletion + SSE |
| 6 | Agent 栈：MCP 管工具、LiteLLM 管模型、FC 管编排 |
| 7 | 选型：单体 SDK、生产 Proxy、框架原生 |
| 8 | 八大坑：异步/虚拟 key/逻辑名/单例/流式 |
