## 1. Router：SDK 的路由器

```python
from litellm import Router

router = Router(
    model_list=[...],                  # 03 章：注册表
    routing_strategy="simple-shuffle", # 负载均衡策略
    num_retries=2,                     # 失败重试次数
    timeout=30,
    allowed_fails=3,                   # 连续失败 N 次标记不健康
    cooldown_time=30,                  # 冷却秒
)

# 业务代码：router.completion 与 completion 同构
resp = router.completion(model="gpt-4o", messages=...)
```

| Router 职责 | 说明 |
|-----------|------|
| 负载均衡 | 同模型多 key/多端点分摊流量 |
| 故障转移 | 某 key/端点失败自动换 |
| 重试 | 限流/超时自动重试 |
| 健康管理 | 连续失败冷却，恢复后自动回归 |
| 成本路由 | 按模型别名选便宜/贵 |

> 🎯 **核心要点**：Router = "**模型层的负载均衡器**"——业务代码只调 `router.completion(model=逻辑名)`，谁被调、失败怎么换全由 Router 管。可靠性从"代码 try/except"升级为"配置策略"。

## 2. 负载均衡策略

```python
router = Router(
    model_list=[...],
    routing_strategy="simple-shuffle",   # 默认：随机轮换（防单 key 限流）
)
```

| 策略 | 行为 | 适用 |
|------|------|------|
| `simple-shuffle`（默认） | 随机打散请求 | ⭐ 多 key 均摊 |
| `least-busy` | 选最空闲端点 | 异构端点 |
| `usage-based-routing` | 按预算剩余路由（v1.9x+） | 成本控制 |
| `latency-based-routing` | 按延迟路由 | 低延迟优先 |

> 💡 为什么默认打散：**API 限流是按 key/端点计的**——同一 key 高频请求触发 429，随机打散让多个 key 均摊额度（与 07 章代理池思想一致）。多 key 场景第一件事：开 `simple-shuffle`。

## 3. Fallback：主备切换

```python
# ① 配置级：同逻辑名下多模型（主 + 备）
model_list = [
    {"model_name": "pro-llm", "litellm_params": {"model": "gpt-4o"}},
    {"model_name": "pro-llm", "litellm_params": {"model": "anthropic/claude-sonnet-5"}},  # 备
    {"model_name": "pro-llm", "litellm_params": {"model": "deepseek/deepseek-v4-pro"}},   # 备备
]

# ② 调用级：显式 fallbacks（按任务指定）
resp = router.completion(
    model="pro-llm",
    messages=[...],
    fallbacks=["cheap-llm"],          # 主失败切便宜模型
)

# ③ Proxy 配置级（06 章）：config.yaml 同样支持
```

| fallback 层级 | 配置位置 | 场景 |
|-------------|---------|------|
| 同逻辑名多模型 | model_list | 同能力多供应商（自动切） |
| 调用级 fallbacks | 请求参数 | 任务级降级（贵→便宜） |
| Proxy 全局 | config.yaml | 网关统一策略 |

> 🎯 **核心要点**：fallback 链 = "**主模型失败 → 备模型接力**"——同一逻辑名下按顺序试。2026 年生产标准：**至少双供应商 fallback**（供应商故障时业务无感）。

## 4. 重试与健康检查

```python
router = Router(
    model_list=[...],
    num_retries=3,               # 失败重试 3 次（自动切到其他端点）
    allowed_fails=3,             # 连续 3 次失败 → 标记不健康
    cooldown_time=60,            # 冷却 60s
    retry_interval=1,            # 重试间隔
)
```

| 机制 | 参数 | 行为 |
|------|------|------|
| 重试 | `num_retries` | 限流/5xx/超时自动重试（切端点） |
| 健康检测 | `allowed_fails` | 连续失败计数 |
| 冷却 | `cooldown_time` | 不健康端点冷却后自动回归 |
| 重试间隔 | `retry_interval` | 防止风暴 |

> ⚠️ 重试铁律（与 FC 体系 03 章一致）：**读操作放心重试；写操作重试前必须幂等**（LiteLLM 只管重发，幂等是你的业务职责）。

## 5. 超时与并发控制

```python
router = Router(
    model_list=[...],
    timeout=30,                     # 单请求超时
    client_ttl=3600,                # 底层 HTTP 客户端重建周期
    num_retries=2,
)
# 并发控制：应用侧（FastAPI 体系信号量）或 Proxy 侧（速率限制，06 章）
```

| 层 | 控制手段 |
|----|---------|
| Router | timeout / num_retries |
| 应用 | asyncio.Semaphore（FastAPI 体系 02 章） |
| Proxy | 虚拟 key RPM/TPM 限制（06 章） |

> 💡 三层限速的分工：**Router 管"失败重试"，应用管"自身并发"，Proxy 管"调用方配额"**——各管一段，不重叠。

## 6. Router Plugins（v1.94+）

**2026 新能力**：自定义路由信号流水线（不等待官方核心功能，插件化扩展路由决策）：

```yaml
# config.yaml 中配置（Proxy 侧）
router_settings:
  plugins:
    - name: language_detector          # 自定义插件
      config: {default_lang: "zh"}
    - name: budget_checker
      config: {max_budget: 100}
```

```python
# 插件语义（v1.94 官方设计）：
# 每个插件收到路由上下文 → 只允许"缩小候选模型集" → 写信号给下游插件
# 插件把候选从 [A,B,C] 缩到 [B] → 路由在缩小后的集里选
# ⚠️ 缩空候选 = 请求报错（不会静默 fallback）
```

| 插件能力 | 场景 |
|---------|------|
| 语言检测 | 中文请求路由到中文强模型 |
| 域分类 | 代码任务 → 代码模型 |
| 租户策略 | 不同租户不同模型集 |
| 预算上限 | 超预算路由到便宜模型 |
| 会话亲和 | 同一会话固定同一模型（Auto-Router v2 默认） |

> 🎯 **核心要点**：Router Plugins = "**路由决策可编程**"——把"按什么信号路由"从内置策略变成团队自己的插件流水线。**插件只能缩小候选（安全设计）**：宁可报错也不静默乱路由。

## 7. 路由配置实战

```yaml
# 生产路由配置模板（config.yaml）
model_list:
  - model_name: pro-llm                    # 主力：双供应商 fallback
    litellm_params: {model: gpt-4o}
  - model_name: pro-llm
    litellm_params: {model: anthropic/claude-sonnet-5}
  - model_name: cheap-llm                   # 降级/批量任务
    litellm_params: {model: deepseek/deepseek-v4-flash}
  - model_name: local-llm                   # 本地（内网/离线）
    litellm_params:
      model: openai/qwen2.5-72b
      api_base: http://vllm:8000/v1

router_settings:
  routing_strategy: simple-shuffle
  num_retries: 2
  allowed_fails: 3
  cooldown_time: 60
```

```python
# 业务使用：按任务选逻辑名
summary = await router.acompletion(model="cheap-llm", ...)   # 摘要用便宜模型
analysis = await router.acompletion(model="pro-llm", ...)    # 深度分析用贵模型
chat = await router.acompletion(model="local-llm", ...)      # 内网服务用本地
```

> 💡 路由架构的三层心智：**逻辑名（业务）→ 策略（Router）→ 物理模型（供应商）**。业务写"我要什么能力"，策略管"怎么达到"，运维管"用哪家"。

## 8. 常见坑

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 1 | 只配单模型无 fallback | 供应商故障全挂 | 同逻辑名至少双模型 |
| 2 | 重试写操作 | 重复扣款/下单 | 写操作幂等先行 |
| 3 | 冷却参数太小 | 坏端点反复被选 | allowed_fails/cooldown 调大 |
| 4 | 策略不理解就开 | 路由不符合预期 | 默认 simple-shuffle 起步 |
| 5 | 插件缩空候选 | 请求 400 | 插件保守设计（只缩不扩） |
| 6 | 别名不按能力命名 | 业务与路由耦合 | cheap/pro/local 命名 |
| 7 | timeout 太大 | 请求悬挂 | 30s 上限 |
| 8 | 忽略限流重试 | 429 直接失败 | num_retries ≥ 2 |

## 9. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | Router = 模型层负载均衡：业务只调逻辑名 |
| 2 | simple-shuffle 默认打散（多 key 防限流） |
| 3 | fallback 三层级：同逻辑名 / 调用级 / Proxy 全局 |
| 4 | 生产标准：至少双供应商 fallback |
| 5 | 健康机制：num_retries + allowed_fails + cooldown |
| 6 | 写操作重试前先幂等 |
| 7 | Router Plugins（v1.94）：路由信号可编程，只缩不扩 |
| 8 | 三层心智：逻辑名（业务）→ 策略（Router）→ 物理（供应商） |
