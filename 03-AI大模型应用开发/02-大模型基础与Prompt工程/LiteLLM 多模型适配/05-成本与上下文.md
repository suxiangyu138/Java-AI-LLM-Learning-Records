## 1. 成本模型：多模型花销从哪来

```text
总成本 = Σ（每模型 token 单价 × token 用量）
       + 多模型的管理成本（key 混乱/重复调用/浪费）

多模型放大成本的三个典型：
① 模型选贵：所有任务都用旗舰模型（摘要也用 gpt-4o）
② 重复调用：没有缓存，相同 prompt 反复付费
③ 无人记账：花多少、谁花的，完全黑盒
```

| 成本因素 | 省法 | 章节 |
|---------|------|:---:|
| 模型单价 | 便宜模型兜底（cheap-llm 别名） | 03/04 |
| token 用量 | 上下文压缩/精简 prompt | 本节 |
| 重复调用 | Prompt 缓存 | 本节 |
| 黑盒花销 | Spend tracking + 预算 | 本节 |

> 🎯 **核心要点**：**多模型时代的成本问题 = "管理问题"多于"单价问题"**——便宜模型不路由过去用、相同内容反复付费、没人记账，才是成本失控的主因。LiteLLM 的记账/预算/缓存就是治这三件事。

## 2. SDK 层成本追踪

```python
import litellm
from litellm import completion

# ① 单次调用成本（自动计价）
resp = completion(model="gpt-4o", messages=...)
cost = resp._hidden_params.get("response_cost")   # 美元
print(f"本次成本: ${cost:.6f}")

# ② 全局回调：每次调用自动记账（02 章 §6）
def track_spend(kwargs, completion_response, start_time, end_time):
    data = {
        "model": kwargs.get("model"),
        "cost": kwargs.get("response_cost"),
        "prompt_tokens": kwargs.get("prompt_tokens"),
        "completion_tokens": kwargs.get("completion_tokens"),
        "user": kwargs.get("metadata", {}).get("user_id"),
    }
    write_to_db(data)          # 落库/推监控

litellm.success_callback = [track_spend]

# ③ 调用时带归属元数据
resp = completion(model="gpt-4o", messages=...,
                  metadata={"user_id": "u123", "team": "客服", "task": "summary"})
```

| 记账维度 | 手段 |
|---------|------|
| 每次调用成本 | response_cost（价格表自动算） |
| 归属 | metadata（user_id/team/task） |
| 集中记录 | success_callback 落库 |
| 监控 | 推送 Prometheus/日志系统 |

> 💡 SDK 记账的工程化：**回调里落库 + 按 metadata 聚合**——"客服组本周花了多少钱、哪家占比多少"这类报表就出来了。单体应用够用；多服务上 Proxy 的 Spend Logs（06 章）。

## 3. 预算控制：团队/用户/key 三级

**Proxy 侧（06 章）是预算控制的完整形态**：

```text
预算层级（从大到小）：
  全局预算      → 所有 key 合计上限
  团队预算      → 按团队（客服/研发/运营）
  用户预算      → 按用户
  Key 预算      → 单个虚拟 key 上限（周期：每天/每周/每月）
  Token 预算    → TPM（每分钟 token）/ RPM（每分钟请求）
```

```yaml
# config.yaml（Proxy）：虚拟 key 预算示例
litellm_settings:
  max_budget: 1000                    # 全局月度预算

# 创建虚拟 key 时（API/UI）：
#  curl /key/generate -d '{"budget": 50, "budget_duration": "30d", "models": ["cheap-llm"]}'
```

| 预算能力 | 防什么 |
|---------|--------|
| key 预算 | 单个应用/调用方烧穿 |
| 模型限制 | key 只能用指定模型 |
| TPM/RPM | 突发流量/滥用 |
| 超预算行为 | 拒绝请求 + 告警 |

> 🎯 **核心要点**：**预算 = 给调用方戴上"额度"**——每个 key 能花多少、能用哪些模型、每分钟多少 token，全部可控。这是"多团队共享模型"场景的安全底线（防止一个团队烧穿全局预算）。

## 4. Prompt 缓存：降本第一杠杆

```python
# LiteLLM 的缓存能力（SDK + Proxy 都有）

# ① 响应缓存（相同请求直接命中）
import litellm
litellm.cache = litellm.Cache(type="redis")          # Redis 后端
resp = completion(model="gpt-4o", messages=messages) # 首次：真实调用
resp2 = completion(model="gpt-4o", messages=messages) # 命中缓存：零成本

# ② 供应商侧缓存（各家原生 prompt caching，LiteLLM 透传）
# OpenAI 自动缓存 / Anthropic cache_control（FC 体系 09 章）
# LiteLLM 配置：cache=true 请求参数或全局开关
```

| 缓存类型 | 机制 | 收益 |
|---------|------|------|
| 响应缓存（LiteLLM Redis） | 相同请求返回缓存 | 完全零成本（相同输入） |
| 语义缓存（v1.9x+） | 相似 prompt 命中 | 覆盖"问法不同意思相同" |
| 供应商 prompt caching | 前缀命中 | 输入降 50-90%（FC 体系 09 章） |
| Cache leakage 监控 | v1.94 成本页 | 发现缓存未命中浪费 |

> ⚠️ 缓存三大纪律：**① 敏感数据不缓存**（用户隐私）；**② 有时效性要求的请求不缓存**（行情/状态查询）；**③ 语义缓存的相似度阈值要测试**（误命中 = 答错题）。缓存是"省钱的债"——命中率靠监控（v1.94 成本页的 Cache leakage）。

## 5. 上下文压缩与 Memory API

**v1.83.14+ 新能力**：

```python
# ① Prompt compression：压缩长上下文（长会话/长文档场景）
from litellm import completion

resp = completion(
    model="gpt-4o",
    messages=long_messages,          # 超长历史/文档
    enable_prompt_compression=True,  # ⭐ 自动压缩再发送（省 token）
)

# ② Memory API（/v1/memory）：会话记忆 CRUD（长会话状态外置）
# 存记忆 → 检索 → 注入 prompt（Agent 记忆体系）
```

| 能力 | 解决什么 | 代价 |
|------|---------|------|
| Prompt compression | 长上下文 token 爆炸 | 压缩质量损失（摘要式） |
| Memory API | 会话记忆管理 | 需设计记忆结构 |
| 响应缓存 | 重复调用 | 数据时效 |

> 💡 使用原则：**压缩是"代价换空间"**——只在上下文超预算时启用（与 FC 体系 07 章压缩三方案同思想）；高频重复的固定前缀靠缓存，不用压缩。

## 6. 成本治理实战

```text
成本治理三步走：
① 记账（看得见）：success_callback / Spend Logs → 周报：哪家/哪个团队/哪个任务最烧钱
② 路由（花得对）：cheap-llm 兜底 + pro-llm 按任务（04 章）
③ 预算（控得住）：key/团队预算 + 缓存 + 压缩

周报模板：
  总成本（按周对比）
  按供应商占比（哪家占比异常高 → 检查路由）
  按团队占比（哪组超支 → 预算收紧）
  缓存命中率（<50% → 查 cache leakage）
  单请求均成本（趋势：涨 → 检查 prompt 膨胀）
```

| 治理动作 | 手段 |
|---------|------|
| 记账 | Spend Logs / 回调落库 |
| 路由省钱 | cheap 兜底 + 缓存 + 压缩 |
| 预算 | 三级预算 + 超支告警 |
| 复盘 | 周报四指标（总/供应商/团队/命中率） |

> 🎯 **核心要点**：成本治理 = "**记账 → 路由 → 预算 → 复盘**"闭环。**先记账再省钱**——不知道钱花在哪，一切优化都是盲人摸象。

## 7. 常见坑

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 1 | 缓存了时效数据 | 返回旧数据 | 时效请求禁缓存 |
| 2 | 缓存敏感数据 | 隐私泄漏 | 白名单/脱敏 |
| 3 | 语义缓存误命中 | 答非所问 | 阈值调高 + 测试集 |
| 4 | 价格表缺失 | cost=None | 升级版本/手动 cost map |
| 5 | 预算设太小 | 业务被拒 | 预算周期与告警留余量 |
| 6 | 压缩质量损失 | 回答变差 | 只压超预算会话 |
| 7 | 只记账不治理 | 报表有了没人管 | 周报 + 告警闭环 |
| 8 | 多 key 不记账 | 分不清谁花的 | metadata 强制携带 |

## 8. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 成本失控主因：选贵/重复/黑盒——不是单价 |
| 2 | 记账：response_cost + metadata + 回调落库 |
| 3 | 预算三级：团队/用户/key + TPM/RPM |
| 4 | 缓存三类型：响应/语义/供应商 prompt caching |
| 5 | 缓存三纪律：敏感不缓、时效不缓、阈值测试 |
| 6 | 压缩与 Memory API（v1.83.14+）：长上下文省 token |
| 7 | 治理闭环：记账 → 路由 → 预算 → 复盘 |
| 8 | 先记账再省钱——报表先行 |
