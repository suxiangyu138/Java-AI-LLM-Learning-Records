## 1. 多模型时代的三大痛点

```text
2026 年的事实：没有一家模型通吃
  - 推理/代码 → 特定模型更强
  - 成本敏感 → 需要便宜模型兜底
  - 区域/合规 → 需要国内 + 国外双通道
  - 供应商风险 → 不能吊死一家

三大痛点：
① 切换成本：每家 API 格式不同（Function Calling 体系 08 章的适配器要每家写一遍）
② key 管理：多模型 = 多 key 散落在代码/环境变量
③ 成本失控：看不到"谁花了多少、花在哪家"
```

| 痛点 | 手写方案 | LiteLLM 方案 |
|------|---------|-------------|
| 切换成本 | 每家写适配器（FC 体系 08 章） | 统一接口 + 换 model 名 |
| key 管理 | 环境变量堆砌 | 配置中心/Proxy 虚拟 key |
| 成本 | 手动记账 | Spend tracking 自动记账 |
| 故障切换 | 手写 try/except | Router fallback 一行配置 |
| 预算 | 无 | 团队/用户/key 级预算 |

> 🎯 **核心要点**：LiteLLM 解决的不是"调用模型"，是"**管理模型**"——统一、可观测、可控。**单模型场景用不用它都行；多模型/多团队场景它是事实标准**。

## 2. LiteLLM 双形态：SDK 与 Proxy

```text
形态一：SDK（Python 库）——代码内统一接入
  你的代码 → litellm.completion(model="gpt-4o", ...)
             → 自动路由到 OpenAI/Claude/DeepSeek/...
  适合：单体应用、脚本、快速切换

形态二：Proxy（网关服务）——集中管理
  你的代码 → OpenAI SDK → http://litellm-proxy:4000/v1 → 各模型
  所有 key/路由/预算/审计集中在网关
  适合：多服务/多团队/生产环境
```

```python
# SDK 形态：一行切换三家
import litellm

resp = litellm.completion(model="gpt-4o", messages=[{"role": "user", "content": "你好"}])
# 换成 Claude 只需改 model 名（key 由环境变量管理）
resp = litellm.completion(model="claude-sonnet-5", messages=[{"role": "user", "content": "你好"}])
```

| 维度 | SDK | Proxy |
|------|:---:|:---:|
| 部署 | 零部署（pip 装） | 独立服务 |
| 统一接口 | Python 专用 | **OpenAI 兼容**（任何语言） |
| key 管理 | 环境变量 | 虚拟 key（预算/速率/模型限定） |
| 成本统计 | 代码内 | 集中 Spend Logs |
| 多团队 | 弱 | 强（团队/SSO/审计） |
| 适用 | 单体/脚本 | 生产/多服务 |

> 🎯 **核心要点**：**SDK 是"接口统一"，Proxy 是"治理统一"**。演进路线：先用 SDK 快速接入 → 多服务后上 Proxy 集中治理——两者配置同源（同一个 model_list 概念），升级平滑。

## 3. 统一抽象层的价值

```text
没有 LiteLLM：                              有 LiteLLM：
代码 → OpenAI SDK（只认 OpenAI）            代码 → LiteLLM → OpenAI / Claude / DeepSeek /
代码 → Anthropic SDK（只认 Claude）               Qwen / Gemini / 本地 vLLM ...
代码 → DeepSeek SDK（只认 DeepSeek）              ↑ 一次编写
代码 → 自研适配器（FC 体系 08 章）                  ↓ 到处运行

代码里 model = "gpt-4o" 换成 "deepseek-v4-pro" = 切换完成
```

| 抽象层收益 | 说明 |
|-----------|------|
| 一次编写 | 业务代码只认统一接口 |
| 模型可配置 | 换模型 = 换配置不是改代码 |
| 供应商可插拔 | 主备切换/成本优化随时做 |
| 参数统一 | temperature/max_tokens 等参数自动映射到各家 |
| 可观测 | 每次调用自动记录成本/耗时 |

> 💡 与 FC 体系 08 章"统一适配层"的关系：那是**自己写的适配层**（每家写解析/回传）；LiteLLM 是**现成的适配层**（100+ 供应商帮你适配完）——自己做 3 家，LiteLLM 做 100 家。先评估 LiteLLM，再决定要不要自研。

## 4. 2026 版本线速览

**基准：v1.94.0（2026-07-28）**

| 版本 | 时间 | 关键能力 |
|------|------|---------|
| v1.83.14 | 2026 上半年 | GPT-5.5 支持、**Prompt compression（上下文压缩）**、Memory API（/v1/memory） |
| v1.9x | 2026 中 | Responses API 改进、Realtime WebRTC 端点、视频 API |
| **v1.94.0** | 2026-07-28 | **Router Plugins**（自定义路由信号）、MCP client-held credentials、Shared DataTable UI、Cost Optimization 页面、**Python 3.14 支持** |
| Rust 迁移 | 2026 进行中 | 同配置同 API，性能数量级提升（§5） |

**v1.94.0 重点新能力**：

| 能力 | 说明 |
|------|------|
| Router Plugins | 自定义路由信号流水线（语言检测/域分类/租户策略/预算上限），只缩候选不越权 |
| Auto-Router v2 | 软地板自适应、会话亲和默认开、分层随机选、用户触发升级关键词 |
| Cost Optimization 页 | 按驱动/工具/缓存泄漏看成本 |
| MCP 客户端凭证 | 交互式 SSO 登录、客户端持有刷新信封 |
| Python 3.14 | 新版本支持 |

> 💡 版本节奏：LiteLLM 迭代极快（每周多个 minor），**生产务必锁定版本**（09 章）。关注 release notes 里的 Breaking Changes 标记。

## 5. Rust 网关迁移

**2026 年最大基础设施动作**：Proxy 内核从 Python 迁移到 Rust。

```text
目标：sub-1ms 开销、sub-100MB 内存
实测（官方基准）：
  吞吐：453 → 6,782 RPS（~15 倍）
  内存：359MB → 32MB（~11 倍）
  每请求开销：~7.5ms → ~0.05ms
  AIGatewayBench：p99 最低、占用最小（比 Bifrost 低 7 倍开销）

对用户透明：同一个 config.yaml、同一个数据库、同一个客户端 API、100+ 供应商覆盖
状态：早期 beta（2026）
```

| 迁移影响 | 说明 |
|---------|------|
| 配置不变 | config.yaml 全兼容 |
| 客户端不变 | OpenAI 兼容 API 不变 |
| 性能提升 | 网关不再是瓶颈 |
| 版本策略 | 生产等稳定版，beta 环境试 |

> 🎯 **核心要点**：Rust 迁移 = "**同样的功能，数量级的性能**"——网关开销从"每请求 7.5ms"降到"0.05ms"，意味着 **LiteLLM 网关不再是性能瓶颈**（此前 Python 网关在高 QPS 下是热点）。

## 6. 生态位置：谁在用 LiteLLM

```text
定位：LLM 接入层的"标准件"（类似 JDBC 之于数据库）

使用场景：
  - 企业生产：多模型路由 + key 治理 + 预算（Proxy）
  - 开源项目：框架内置（LangChain/LlamaIndex 等大量使用）
  - 自研 Agent：统一接入层（FC 体系 08 章适配层的现成替代）
  - 网关类产品：One-API/New-API 的同类，但走 OpenAI 兼容 + 生态集成路线

在栈中的位置：
  应用/Agent → LiteLLM（SDK/Proxy） → OpenAI/Claude/DeepSeek/vLLM/本地
```

> 💡 与 One-API 的定位差异（选型在 09 章）：One-API 是"**多模型管理平台**"（UI 重、渠道管理）；LiteLLM 是"**开发者生态适配层**"（代码优先、Python 生态深度集成）。2026 年 Python 栈开发者通常选 LiteLLM。
