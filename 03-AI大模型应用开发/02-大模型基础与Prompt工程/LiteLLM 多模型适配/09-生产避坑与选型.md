## 1. 网关方案全景与决策树

```text
多模型接入层方案全景（2026）：
  开源自建：LiteLLM / One-API / New-API
  商业服务：OpenRouter / 各家云网关
  自研：自己的适配层（FC 体系 08 章）

选型决策树：
  需要什么？
  ├─ 代码内统一接口（Python）→ LiteLLM SDK
  ├─ 自建网关（key/预算/审计）→ LiteLLM Proxy（或 One-API）
  ├─ 不想运维 → OpenRouter / 云网关
  ├─ Java/企业平台 → One-API（UI 管理强）/ LiteLLM Proxy
  └─ 极致定制 → 自研适配层（成本高，慎选）
```

| 方案 | 形态 | 适合 |
|------|------|------|
| LiteLLM SDK | 库 | Python 单体 |
| LiteLLM Proxy | 服务 | Python 栈团队 |
| One-API | 服务 + UI | 国内企业/非 Python 栈 |
| New-API | One-API 增强 | 需要更多渠道功能 |
| OpenRouter | SaaS | 不想运维/出海 |
| 自研 | 代码 | 极特殊需求 |

> 🎯 **核心要点**：**先定需求再选型**——代码统一（SDK）、网关治理（Proxy/One-API）、省运维（SaaS）、极致定制（自研）。LiteLLM 在"Python 生态 + 开发者体验"上是 2026 最优解。

## 2. LiteLLM vs One-API vs New-API

| 维度 | LiteLLM | One-API | New-API |
|------|:---:|:---:|:---:|
| 语言 | Python | Go | Go |
| 生态定位 | 开发者适配层 | 管理平台 | 管理平台增强 |
| UI | 管理界面（v1.94 强化） | 成熟 Web UI | 更丰富的 UI |
| 配置方式 | config.yaml（代码友好） | 界面/渠道管理 | 界面 |
| 供应商覆盖 | 100+ | 几十家渠道 | 更多渠道 |
| 预算/虚拟 key | ✅ 强 | ✅ | ✅ |
| 框架集成 | LangChain 原生 | 通用 OpenAI 兼容 | 通用 |
| 开发体验 | ⭐ 代码优先 | 运维优先 | 运维优先 |
| 适用 | Python 栈/开发者 | 国内企业/非 Python | 渠道丰富的企业 |

> 💡 选型参考（聚合网关 04 章也有全景）：**Python 开发者团队 → LiteLLM**（配置即代码、生态集成深）；**非 Python/重 UI 管理 → One-API/New-API**（Go 单体 + Web UI 成熟）。两者都是 OpenAI 兼容，迁移成本不高。

## 3. LiteLLM vs OpenRouter vs 云网关

| 维度 | LiteLLM 自建 | OpenRouter（SaaS） | 云厂商网关 |
|------|:---:|:---:|:---:|
| 运维 | 自管（Docker） | 零 | 零 |
| 成本 | 服务器费 | 订阅/流量费 | 云账单 |
| 控制力 | 完全 | 平台限制 | 平台限制 |
| 供应商 | 100+ 直连 | 聚合多模型 | 自家为主 |
| 数据 | 完全自控 | 过第三方 | 云厂商 |
| 合规 | 自控 | 需评估 | 看区域 |
| 适用 | 生产/合规敏感 | 出海/快速 | 云栈统一 |

> ⚠️ 数据合规关键点：**OpenRouter/SaaS 网关 = 数据过第三方**——涉及隐私/合规（个保法）的业务，自建网关是更安全的选择（数据不出内网，只出到最终模型供应商）。

## 4. LiteLLM vs 自研适配层

| 维度 | LiteLLM | 自研（FC 体系 08 章） |
|------|:---:|:---:|
| 覆盖 | 100+ 供应商 | 3-5 家手写 |
| 时间 | 小时级 | 周-月级 |
| 维护 | 社区迭代 | 自己扛 |
| 定制 | 插件/前缀参数 | 完全自由 |
| 治理 | 预算/key/审计全套 | 自己写 |
| 适用 | 绝大多数场景 | 特殊协议/完全掌控 |

> 🎯 **核心要点**：**自研适配层的唯一理由 = "LiteLLM 覆盖不了"**（专有协议/特殊计费/完全掌控）。先评估 LiteLLM 的能力边界，再决定自研——**"3 家自己写"的成本永远高于"100 家用现成"**。

| # | 坑 | 归属章 | 一句话解法 |

## 6. 落地检查清单

- [ ] 模型注册表（model_list）配置好，逻辑名按能力命名
- [ ] 至少双供应商 fallback（同逻辑名）
- [ ] 虚拟 key 全部分发（预算/模型白名单/TPM-RPM）
- [ ] master_key 环境变量设置，config 零密钥
- [ ] PostgreSQL 持久化 + 每日备份
- [ ] Redis 缓存配置（响应缓存 + 缓存纪律）
- [ ] OTel 可观测接入 + 告警三件套（成本/失败率/缓存命中）
- [ ] Docker 锁定版本 + 健康检查
- [ ] 网关内网部署 + Nginx TLS
- [ ] 压测过（吞吐/延迟，07 章数据面验证）
- [ ] 升级流程（release notes → 测试 → 灰度）
- [ ] 成本周报闭环（记账 → 路由 → 预算 → 复盘）

## 7. 常见坑速查表

| 症状 | 根因 | 解法 |
|------|------|------|
| 401 认证失败 | 虚拟 key 错/未传 | 检查 key 与请求头 |
| 模型不存在 | 逻辑名拼错/未注册 | model_list 对照 |
| 429 限流 | key TPM/RPM 超 | 调限额/多 key shuffle |
| 延迟飙升 | 控制面拖累/供应商慢 | 数据面分离/fallback |
| 成本爆炸 | 选贵/无缓存/无预算 | 05 章治理闭环 |
| 重启丢 key | 无数据库 | PG 持久化 |
| 某供应商全失败 | 供应商故障无 fallback | 04 章双供应商 |
