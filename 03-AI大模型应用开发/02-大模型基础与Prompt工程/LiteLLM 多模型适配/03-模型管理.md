## 1. model_list：模型注册表

```yaml
# 模型注册表：声明"有哪些模型可用、怎么调"（SDK 与 Proxy 共用此概念）
model_list:
  - model_name: gpt-4o                      # 统一别名（业务代码用的名字）
    litellm_params:
      model: openai/gpt-4o                  # 真实模型（供应商前缀）
      api_key: os.environ/OPENAI_API_KEY    # key 来源

  - model_name: claude-sonnet-5
    litellm_params:
      model: anthropic/claude-sonnet-5
      api_key: os.environ/ANTHROPIC_API_KEY

  - model_name: cheap-llm                   # 别名指向便宜模型（成本路由用）
    litellm_params:
      model: deepseek/deepseek-v4-flash
      api_key: os.environ/DEEPSEEK_API_KEY
```

| 字段 | 作用 |
|------|------|
| `model_name` | 统一别名（代码/调用方可见的名字） |
| `litellm_params.model` | 真实模型 ID（供应商前缀 + 模型名） |
| `litellm_params.api_key` | 该模型的 key（环境变量引用） |
| `litellm_params.api_base` | 自定义端点（本地服务用） |

> 🎯 **核心要点**：model_list = "**逻辑名 → 物理模型**"的映射表。业务代码只认逻辑名（`gpt-4o`/`cheap-llm`），物理模型（供应商/版本/价格）全在配置层——**换供应商不碰代码**。

## 2. model_name：统一别名机制

```python
# 别名机制：SDK 里用 Router 加载 model_list 后，业务代码写逻辑名
from litellm import Router

router = Router(model_list=model_list)          # model_list 同源（§6）

resp = router.completion(
    model="gpt-4o",              # 逻辑名
    messages=[...],
)
resp = router.completion(
    model="cheap-llm",           # 逻辑名（实际是 DeepSeek）
    messages=[...],
)
```

| 别名能力 | 场景 |
|---------|------|
| 供应商隐藏 | 业务代码不知道也不该知道背后是哪家 |
| 成本路由 | `cheap-llm` = 便宜模型，`pro-llm` = 贵模型，按任务选 |
| 版本升级 | 别名指向 v1 → 指向 v2，下游零改动 |
| AB 实验 | 同一别名下两个模型轮换 |
| 故障切换 | 别名 → 主模型 + fallback（04 章） |

> 💡 **别名设计规范**：按**能力/成本**命名（`cheap-llm`/`pro-llm`/`fast-llm`/`rag-llm`）而不是按供应商命名——业务按需求选模型，供应商是运维决策。

## 3. 密钥管理：环境变量与动态 key

```python
# 方式一：环境变量（最常用，01 章 §1）
# OPENAI_API_KEY / ANTHROPIC_API_KEY / DEEPSEEK_API_KEY ...

# 方式二：model_list 里显式指定（多 key 轮换/不同模型不同 key）
model_list = [{
    "model_name": "gpt-4o",
    "litellm_params": {
        "model": "openai/gpt-4o",
        "api_key": "sk-xxx",                     # ⚠️ 生产用环境变量引用
    },
}]

# 方式三：动态 key（运行期提供）
import litellm
litellm.api_key = "sk-xxx"              # 全局默认
# 或每次调用
resp = litellm.completion(model="gpt-4o", messages=..., api_key="sk-xxx")
```

| key 管理规范 | 做法 |
|-------------|------|
| 环境变量 | ⭐ 首选（`os.environ/NAME` 引用） |
| 密钥系统 | 生产对接 KMS/Vault（读出来放环境） |
| 多 key 轮换 | model_list 配多个 provider key |
| Proxy 虚拟 key | 团队场景用网关分发（06 章） |
| 禁止 | 代码里硬编码 / git 提交 |

> ⚠️ key 安全基线（与 FC 体系 06 章一致）：**环境变量/密钥系统，零明文**。LiteLLM 的 `os.environ/XXX` 引用让 key 只存在于环境，不进配置文件。

## 4. 供应商接入清单

| 供应商 | 模型名前缀 | key 环境变量 | 说明 |
|--------|-----------|-------------|------|
| OpenAI | `openai/` 或省略 | OPENAI_API_KEY | 默认 |
| Anthropic | `anthropic/` | ANTHROPIC_API_KEY | Claude 系 |
| DeepSeek | `deepseek/` | DEEPSEEK_API_KEY | V4 系 |
| Google | `gemini/` | GEMINI_API_KEY | Gemini |
| 阿里 Qwen | `openai/qwen-...`（DashScope） | DASHSCOPE_API_KEY | OpenAI 兼容端点 |
| Ollama | `ollama/` | 无（本地） | 本地推理 |
| vLLM | `openai/` + api_base | 无 | 自建服务 |
| Bedrock | `bedrock/` | AWS 凭证 | AWS 托管 |
| Vertex AI | `vertex_ai/` | GCP 凭证 | GCP 托管 |
| HuggingFace | `huggingface/` | HUGGINGFACE_API_KEY | HF 推理端点 |

> 💡 100+ 供应商全覆盖是 LiteLLM 的核心资产——**列表以官方文档为准**（新增快）。国内常用：DeepSeek、DashScope（Qwen）、Moonshot、智谱、MiniMax 均支持。

## 5. 自定义模型：本地 vLLM / Ollama / 自研服务

```yaml
# 本地 vLLM（OpenAI 兼容端点）
model_list:
  - model_name: local-llm
    litellm_params:
      model: openai/qwen2.5-72b            # 用 openai 前缀
      api_base: http://vllm-server:8000/v1  # 指向自建服务
      api_key: dummy                        # 本地服务无鉴权

# Ollama（本地推理）
  - model_name: ollama-llm
    litellm_params:
      model: ollama/llama3.1:8b
      api_base: http://localhost:11434
```

```python
# 代码里：本地模型与其他模型完全同构
resp = router.completion(model="local-llm", messages=...)
resp = router.completion(model="gpt-4o", messages=...)
```

| 自定义模型场景 | 配置要点 |
|---------------|---------|
| 本地 vLLM | `openai/` 前缀 + `api_base` 指向 vLLM |
| Ollama | `ollama/` 前缀 |
| 自研 OpenAI 兼容服务 | `openai/` + api_base（任何兼容服务） |
| 混合路由 | 本地便宜任务 + 云端强任务（04 章） |

> 🎯 **核心要点**：**"OpenAI 兼容 = 可接入"**——vLLM/Ollama/自研服务的接入都是"前缀 + api_base"两行配置。混合架构（本地低成本 + 云端高质量）通过 model_list 一个表搞定。

## 6. SDK 与 Proxy 配置同源

```python
# 同一份 model_list 两种用法：
# ① SDK：Router(model_list=...)
router = Router(model_list=model_list)

# ② Proxy：config.yaml 里写 model_list，起服务
#    litellm --config config.yaml
#    → 所有模型变成 OpenAI 兼容端点 http://localhost:4000/v1
```

| 形态 | 配置来源 | 迁移 |
|------|---------|------|
| SDK | Python dict / yaml 文件 | 直接复用 |
| Proxy | config.yaml | 直接复用 |

> 💡 **配置同源是 LiteLLM 设计的精髓**：单体应用用 SDK（Router），升级多服务直接把这套 model_list 搬进 Proxy——**模型治理逻辑零重写**。这也是"先 SDK 后 Proxy"演进路线成立的原因。

## 7. 常见坑

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 1 | model_list 没加载 | 模型不存在 | Router(model_list=...) 必须传 |
| 2 | 别名与真实名混淆 | 调错模型 | 逻辑名 → 物理名对照表 |
| 3 | key 写进 yaml | 泄漏风险 | os.environ/ 引用 |
| 4 | api_base 漏配 | 打到默认端点 | 本地服务必配 api_base |
| 5 | 供应商前缀写错 | 认证/端点错 | 按官方前缀表 |
| 6 | 版本升级后模型名变化 | 404 | 查 release notes 别名映射 |
| 7 | 多 key 不轮换 | 单 key 限流 | 同模型配多个 provider key |
| 8 | 逻辑名含供应商名 | 换供应商要改代码 | 按能力/成本命名别名 |

## 8. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | model_list = 逻辑名 → 物理模型映射表，换供应商不碰代码 |
| 2 | 别名按能力/成本命名（cheap-llm/pro-llm），不按供应商 |
| 3 | key 三规范：环境变量、os.environ 引用、零明文 |
| 4 | 100+ 供应商全覆盖；国内 DeepSeek/DashScope/智谱等均支持 |
| 5 | 本地模型 = `openai/` + api_base（vLLM/Ollama/自研） |
| 6 | SDK 与 Proxy 配置同源：Router ↔ config.yaml |
| 7 | 八大坑：别名/前缀/key/api_base/版本 |
| 8 | 模型管理是路由（04 章）、成本（05 章）、网关（06 章）的共同地基 |
