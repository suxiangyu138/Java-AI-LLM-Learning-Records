# 09-工程实践与训练框架

> 后训练算法本身只有几十行，工程实现却是"训练引擎 + 推理引擎 + 奖励服务 + 数据管道"四套系统协同。显存怎么算、采样怎么加速、权重怎么同步、奖励怎么接、训练怎么监控，决定了算法能不能跑起来。本篇给出一套可落地的工程视角。

## 1. 系统全景

```text
┌─────────────────────────────────────────────────────────────┐
│                        训练引擎                              │
│   FSDP / ZeRO / Megatron                                    │
│   策略更新、梯度计算、优化器                                  │
└───────────────┬─────────────────────────────▲───────────────┘
                │ 权重同步                     │ 梯度
                ▼                             │
┌─────────────────────────────────────────────────────────────┐
│                        推理引擎                              │
│   vLLM / SGLang                                             │
│   批量采样、KV Cache、连续批处理                              │
└───────────────┬─────────────────────────────▲───────────────┘
                │ 生成回答                     │ prompt
                ▼                             │
┌─────────────────────────────────────────────────────────────┐
│                        奖励服务                              │
│   规则验证 / 奖励模型 / 单元测试 / 工具执行                    │
└───────────────┬─────────────────────────────▲───────────────┘
                │ 奖励分数                     │
                ▼                             │
┌─────────────────────────────────────────────────────────────┐
│                        数据管道                              │
│   prompt 池、难度分层、去重、过滤、课程学习                    │
└─────────────────────────────────────────────────────────────┘
```

四套系统的职责：

| 系统 | 职责 | 关键指标 |
|------|------|---------|
| 训练引擎 | 前向、反向、更新 | 吞吐（tokens/s）、显存 |
| 推理引擎 | 采样回答 | 吞吐、TTFT、延迟 |
| 奖励服务 | 打分 | QPS、延迟、准确率 |
| 数据管道 | 供题与管理 | 覆盖率、难度分布 |

## 2. 框架选型

| 框架 | 定位 | 优势 | 局限 |
|------|------|------|------|
| TRL | HuggingFace 官方后训练库 | 生态完整、上手快、DPO/GRPO/PPO 齐全 | 超大规模效率一般 |
| verl | 字节开源，RL 训练框架 | R1/Qwen 复现的事实标准，GRPO/DAPO/GSPO 支持好 | 学习曲线陡 |
| OpenRLHF | 开源 RLHF 框架 | PPO/GRPO/DPO 完整，Ray 调度 | 社区规模中等 |
| NeMo-RL | NVIDIA 生态 | 与 Megatron 深度集成 | 依赖 NVIDIA 栈 |
| axolotl | 微调框架 | 配置化，支持 DPO/ORPO | RL 能力相对有限 |
| prime-rl | 研究向 | 新算法集成快 | 生产成熟度待验证 |

选型建议：

```text
快速实验 / 中小模型 → TRL
复现 R1 系列 / 大规模 GRPO → verl
已有 Ray + Megatron 体系 → OpenRLHF / NeMo-RL
只做 DPO 类离线偏好优化 → TRL / axolotl
```

> **提示**：框架版本迭代很快，选型前先看目标算法的官方示例是否在目标框架里有可运行实现。没有示例的框架，等于要自己踩完所有坑。

## 3. 显存计算

### 3.1 训练显存的组成

```text
总显存 =
  模型权重
+ 梯度
+ 优化器状态
+ 激活值
+ 临时缓冲
+ 通信缓冲
```

按精度估算每参数字节：

| 训练方式 | 权重 | 梯度 | 优化器 | 合计 |
|---------|:---:|:---:|:-----:|:---:|
| 全参 bf16 + Adam | 2 | 2 | 8（fp32 m/v） | 12 |
| 全参 bf16 + 8bit Adam | 2 | 2 | 2 | 6 |
| LoRA bf16 | 2（底座冻结） | 2（适配器） | 8（适配器） | 2 + 12×适配器比例 |
| 推理 bf16 | 2 | 0 | 0 | 2 |

### 3.2 例子

```text
7B 模型全参训练：
  权重 14GB + 梯度 14GB + 优化器 56GB = 84GB
  + 激活值（取决于 batch 与序列长度）
  → 单卡 80GB 不够，需要 FSDP/ZeRO 切分

70B 模型全参训练：
  84GB × 10 = 840GB
  → 至少 11 张 80GB 卡，实际要 32-64 张

70B 模型 LoRA 训练（适配器 1%）：
  底座 140GB（可 4bit 量化到 35GB）
  + 适配器与优化器约 1GB
  → 单机 8 卡可跑
```

### 3.3 激活值

激活显存与以下因素成正比：

$$M_{act}\approx b\times s\times h\times L\times k$$

其中 $b$ 是 batch，$s$ 是序列长度，$h$ 是隐藏维度，$L$ 是层数，$k$ 是与实现相关的常数（通常 10-20）。

降低激活的手段：

```text
① 梯度检查点（Gradient Checkpointing）
   用计算换显存，激活降低 3-5 倍，训练慢 20-30%

② 序列并行（Sequence Parallel）
   把序列维度切到多卡

③ 分块计算 / FlashAttention
   减少注意力矩阵的显存
```

### 3.4 KV Cache

推理采样时的 KV Cache：

$$M_{KV} = 2\times L\times n_{kv}\times d_{head}\times s\times b\times \text{bytes}$$

以 7B 模型（32 层、32 头、head_dim=128、GQA 8 个 KV 头）为例：

```text
单 token 的 KV：
  2 × 32 × 8 × 128 × 2 字节 = 131072 字节 ≈ 128KB（bf16）

4096 token：
  128KB × 4096 ≈ 512MB（单条序列）

批量 32 条：
  约 16GB
```

这就是 RL 采样阶段显存的主要开销之一。

## 4. 并行策略

| 策略 | 切分对象 | 适用 | 通信开销 |
|------|---------|------|---------|
| 数据并行（DP） | batch | 通用 | 中（梯度 all-reduce） |
| ZeRO-1 | 优化器状态 | 减少优化器显存 | 中 |
| ZeRO-2 | 优化器 + 梯度 | 中等规模 | 较高 |
| ZeRO-3 / FSDP | 参数 + 梯度 + 优化器 | 大模型 | 高 |
| 张量并行（TP） | 层内矩阵 | 单机多卡 | 高（频繁） |
| 流水并行（PP） | 层 | 多机 | 中（气泡） |
| 序列并行（SP） | 序列维度 | 长序列 | 中 |
| 专家并行（EP） | MoE 专家 | MoE 模型 | 高 |

组合原则：

```text
单机内：TP（利用 NVLink 高带宽）
跨机：PP 或 DP
显存不足：ZeRO-3/FSDP
长序列：SP + 梯度检查点
MoE：EP + TP
```

RL 训练的特殊之处：

```text
训练与推理两套引擎的并行方式可能不同
  → 权重需要重分片（resharding）
  → 这是工程复杂度的主要来源之一
```

## 5. 采样加速

### 5.1 为什么采样是瓶颈

```text
GRPO 每个 prompt 采样 G 个回答
  7B 模型、4096 token、G=8
  单 prompt 生成 32768 token
  1000 个 prompt → 3276 万 token

用 HuggingFace generate：
  吞吐低，可能几小时
用 vLLM：
  连续批处理 + PagedAttention，吞吐高一个数量级
```

### 5.2 推理引擎选型

| 引擎 | 特点 | 适合 |
|------|------|------|
| vLLM | PagedAttention、连续批处理、生态成熟 | 通用 RL 采样 |
| SGLang | RadixAttention、前缀缓存、结构化生成 | 长 prompt、多轮 |
| TensorRT-LLM | NVIDIA 优化、吞吐最高 | 固定硬件、追求极致 |

### 5.3 采样参数

```text
temperature：
  控制探索
  太高 → 回答质量差、奖励噪声大
  太低 → 组内雷同、优势为 0

top_p / top_k：
  限制候选集
  常用 top_p=0.95-1.0

max_new_tokens：
  控制单条成本
  数学/代码任务要给足（4k-16k）

n（每个 prompt 的采样数）：
  GRPO 的 G
  8-16 常 used
```

### 5.4 采样与训练的交替

```text
同步模式：
  采样一批 → 训练 → 更新权重 → 再采样
  简单，但采样与训练不能重叠

异步模式：
  采样与训练流水线化
  用旧权重采样的数据训练新权重
  → 需要处理 off-policy 偏差（重要性采样）
  → 吞吐高，但稳定性要求高

工程主流：
  中小规模用同步
  大规模用异步 + 严格版本控制
```

## 6. 权重同步

训练引擎更新参数后，推理引擎要拿到新权重：

```text
方式一：广播
  训练进程把权重广播到推理进程
  简单，但大模型传输慢

方式二：共享内存/显存
  同机部署时用共享内存
  快，但受单机限制

方式三：重分片（Resharding）
  训练用 FSDP/TP，推理用 TP/PP
  需要按目标布局重新切分权重
  工程复杂，但灵活

方式四：检查点中转
  训练保存 checkpoint，推理加载
  最慢，但最稳
```

同步频率的权衡：

```text
每步同步：
  推理总是用最新策略，on-policy 程度高
  同步开销大

每 N 步同步：
  吞吐高
  但推理用的是旧策略，产生 off-policy 数据
  → 需要重要性修正或接受偏差
```

## 7. 奖励服务工程

### 7.1 三类奖励

| 类型 | 实现 | 延迟 | 成本 |
|------|------|------|------|
| 规则奖励 | 正则、答案比对、格式校验 | 微秒到毫秒 | 极低 |
| 执行奖励 | 跑单元测试、调工具 | 毫秒到秒 | 中 |
| 模型奖励 | RM/PRM 前向 | 毫秒到百毫秒 | 高（GPU） |

### 7.2 混合奖励

```text
总奖励 = w1 × 规则奖励 + w2 × 执行奖励 + w3 × 模型奖励

设计原则：
  规则保底线（格式、长度、语言）
  执行保正确性（单测、答案）
  模型管质量（可读性、有用性）

权重需要调：
  规则权重过高 → 模型学会刷格式
  模型权重过高 → 奖励黑客
```

### 7.3 奖励服务的部署

```text
规则奖励：
  与训练同进程，或独立 CPU 服务

执行奖励：
  沙箱容器（隔离、限时、限内存）
  并发执行，注意资源隔离

模型奖励：
  独立推理服务（vLLM/TGI）
  批量打分，GPU 复用
  注意与训练抢显存
```

> **警告**：执行用户/模型生成的代码必须在沙箱里。裸跑单元测试等于把训练环境交给模型。要限制 CPU、内存、执行时间、网络访问、文件系统。

## 8. 数据工程

### 8.1 Prompt 池

```text
来源：
  公开数据集（数学、代码、通用）
  业务数据（脱敏后）
  合成数据（强模型生成）

质量要求：
  答案可验证
  难度有梯度
  去重（精确 + 语义）
  防止测试集泄漏
```

### 8.2 难度分层与课程学习

```text
按当前模型的表现分层：
  简单：Pass@1 > 80%
  中等：20%-80%
  困难：< 20%

训练策略：
  初期多给中等题（有梯度）
  后期加入困难题（提升上限）
  简单题定期回炉（防止遗忘）

动态调整：
  每轮评估后重新分层
  这就是"课程学习"
```

### 8.3 数据配比

```text
数学 : 代码 : 通用 : 工具调用
需要按目标能力配比

注意：
  单一任务过多 → 通用能力退化
  配比失衡 → 模型偏科
  需要定期做通用能力回测
```

## 9. 训练监控

### 9.1 必看指标

| 指标 | 含义 | 异常信号 |
|------|------|---------|
| `reward_mean` | 平均奖励 | 长期不涨（无学习）或暴涨（奖励黑客） |
| `reward_std` | 组内奖励标准差 | 接近 0（零梯度组多） |
| `entropy` | 策略熵 | 快速下降（探索不足） |
| `approx_kl` | 新旧策略差异 | > 0.02 说明更新过大 |
| `clip_fraction` | 被裁剪比例 | > 0.3 说明策略变化大 |
| `response_length` | 回答长度 | 持续上涨（长度失控） |
| `grad_norm` | 梯度范数 | 爆炸或消失 |
| `learning_rate` | 学习率 | 是否按计划衰减 |
| `pass@1` | 验证集正确率 | 是否真的在提升 |
| `zero_std_ratio` | 零梯度组比例 | 过高说明题目太简单/太难 |

### 9.2 监控面板

```text
面板一：训练健康
  loss、grad_norm、learning_rate、approx_kl、clip_fraction

面板二：奖励与探索
  reward_mean、reward_std、entropy、response_length

面板三：能力评估
  pass@1、各任务正确率、通用能力回测

面板四：系统
  GPU 利用率、显存、采样吞吐、奖励服务延迟
```

### 9.3 早停条件

```text
① approx_kl 持续超阈值
② 熵低于下限
③ 奖励均值暴涨但验证集不涨（奖励黑客）
④ 回答长度失控
⑤ 出现大量重复/乱码
⑥ 通用能力显著下降
```

## 10. 常见故障

| 现象 | 可能原因 | 处理 |
|------|---------|------|
| 奖励不涨 | 学习率太小、题目太难、优势全 0 | 调难度、查零梯度组比例 |
| 奖励暴涨但评估不涨 | 奖励黑客 | 加 KL、改奖励、人工抽检 |
| 熵快速下降 | 探索不足、clip 太紧 | 调温度、Clip-Higher、加熵奖励 |
| 回答越写越长 | 长度偏差、奖励偏好长文 | 长度惩罚、长度归一化 |
| 训练崩溃（loss NaN） | 学习率过大、梯度爆炸、数据异常 | 降学习率、梯度裁剪、清洗数据 |
| 显存 OOM | batch/序列太长、KV Cache 太大 | 梯度检查点、减 batch、加卡 |
| 采样极慢 | 推理引擎配置差、奖励服务瓶颈 | 换 vLLM、批量打分、异步 |
| 权重同步慢 | 模型太大、跨机带宽低 | 重分片优化、同机部署 |
| 通用能力退化 | 任务太单一、KL 太松 | 加通用数据、加 KL、回测 |
| 输出格式混乱 | 多语言混杂、格式奖励不足 | 加格式奖励、语言一致性奖励 |

## 11. 成本估算

以 7B 模型、GRPO、1000 个 prompt、G=8、平均 2048 token 为例：

```text
采样成本：
  1000 × 8 × 2048 = 1638 万 token
  vLLM 吞吐按 2000 token/s/卡 估算
  → 约 2.3 卡小时/轮

训练成本：
  1638 万 token 前向 + 反向
  训练吞吐按 1000 token/s/卡 估算
  → 约 4.5 卡小时/轮

奖励成本：
  规则奖励可忽略
  RM 打分按 500 token/s/卡 估算
  → 约 9 卡小时/轮

单轮合计约 16 卡小时
1000 轮约 16000 卡小时
```

成本优化的三个杠杆：

```text
① 减少无效采样
   动态采样过滤零梯度组
   难度分层，避免在已掌握的题上浪费

② 提高吞吐
   vLLM 连续批处理
   奖励批量打分
   采样与训练重叠

③ 降低模型规模
   LoRA 代替全参
   量化推理
   小模型做探索、大模型做蒸馏
```

## 12. 配置示例

### 12.1 TRL GRPO 配置

```python
from trl import GRPOConfig, GRPOTrainer

config = GRPOConfig(
    output_dir="./grpo-output",
    learning_rate=1e-6,
    per_device_train_batch_size=1,
    gradient_accumulation_steps=8,
    num_generations=8,
    max_prompt_length=1024,
    max_completion_length=2048,
    temperature=0.9,
    beta=0.01,
    epsilon=0.2,
    num_train_epochs=1,
    logging_steps=10,
    save_steps=200,
    bf16=True,
    gradient_checkpointing=True,
)

trainer = GRPOTrainer(
    model="Qwen/Qwen2.5-7B-Instruct",
    reward_funcs=[math_reward, format_reward],
    args=config,
    train_dataset=dataset,
)
trainer.train()
```

### 12.2 verl 配置要点

```yaml
actor_rollout_ref:
  model:
    path: Qwen/Qwen2.5-7B-Instruct
    enable_gradient_checkpointing: true
  actor:
    optim:
      lr: 1.0e-6

  adv_estimator: grpo
  kl_ctrl:
    type: fixed
    kl_coef: 0.001

trainer:
  total_epochs: 15
  save_freq: 200
```

## 13. 生产建议

```text
① 先跑通小规模
   7B 模型 + 1000 条数据 + 单机
   验证奖励、监控、评估链路
   再上大规模

② 基线先行
   先复现 SFT 与 DPO 基线
   再上 GRPO/RLVR
   否则无法判断 RL 是否真的带来提升

③ 奖励要可解释
   每条奖励能追溯到规则/测试/模型
   否则调不动

④ 评估独立
   训练集、验证集、测试集严格隔离
   防止数据泄漏导致的虚高

⑤ 版本管理
   模型、数据、奖励函数、配置四者版本绑定
   否则无法复现

⑥ 保留通用能力
   定期回测通用任务
   防止"数学变强、对话变笨"

⑦ 安全边界
   代码执行沙箱
   奖励模型的对抗测试
   输出内容审核
```
