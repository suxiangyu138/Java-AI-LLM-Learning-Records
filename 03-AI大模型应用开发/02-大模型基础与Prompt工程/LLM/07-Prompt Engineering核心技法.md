## 1. Prompt 工程框架

### 1.1 黄金模板

```text
好的 Prompt = 角色 + 任务 + 格式 + 约束 + 示例

┌─────────────────────────────────────────────┐
│ [角色] 你是一个 Java 后端专家                 │
│ [任务] 审查以下代码，找出潜在问题               │
│ [格式] 用表格输出，包含：行号/问题/严重性/建议  │
│ [约束] 不讨论代码风格，只找功能性bug            │
│ [示例] （可选）参考以下格式...                 │
└─────────────────────────────────────────────┘
```

### 1.2 核心原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **具体** | 明确说明任务、格式、标准 | "帮我写代码" |
| **分层** | 复杂任务拆解为子步骤 | 一段话描述所有需求 |
| **约束** | 限制输出长度/格式/范围 | 不设边界 |
| **示例** | 给 2-3 个示例比长篇描述更有效 | 只描述不给例子 |

## 2. Few-shot 示例学习

```text
Zero-shot:  不给示例 → 翻译：Hello → （模型自己理解"翻译"）
One-shot:   给 1 个示例 → 翻译：Apple→苹果\n翻译：Hello→
Few-shot:   给 3-5 个示例 → 翻译：Apple→苹果\nDog→狗\nCat→猫\n翻译：Hello→

选择：复杂/少见任务 → Few-shot；常见任务 → Zero-shot 够了
```

### Few-shot 示例设计

```text
好的 Few-shot 示例：
1. 覆盖边界情况（不只是简单case）
2. 多样化的输入（不同长度/格式/风格）
3. 示例顺序从简单到复杂
4. 每个示例提供清晰的"输入→输出"映射
```

## 3. CoT 思维链

### 3.1 为什么需要 CoT

```text
直接问："小明有 5 个苹果，给了小红 2 个，又买了 3 个，
        吃了 1 个，还剩几个？"
GPT 直接回答 → 可能出错

加一句 "Let's think step by step"：
  Step 1: 小明一开始有 5 个苹果
  Step 2: 给小红 2 个后，剩 5-2=3 个
  Step 3: 买了 3 个后，有 3+3=6 个
  Step 4: 吃了 1 个后，剩 6-1=5 个
  Answer: 5 个

→ CoT 将"一步推理"变成"多步验证"，准确率大幅提升
```

### 3.2 CoT 的三种方式

| 方式 | 做法 | 效果 |
|------|------|:---:|
| **Zero-shot CoT** | 加 "Let's think step by step" | +10-20% 准确率 |
| **Few-shot CoT** | 给几个带推理过程的示例 | +20-40% |
| **Auto-CoT** | 让模型自己生成推理链 | 自动化 |

## 4. ReAct 推理+行动

```text
ReAct = Reasoning + Acting = "边想边做"

传统 LLM：只有"思考"（纯文本输出）
ReAct：思考 → 行动 → 观察 → 思考 → 行动 → ...
      Thought → Action → Observation → ...

示例：
用户："北京今天天气怎么样？"

Thought: 我需要查询北京的天气
Action: search("北京 天气 2026-07-27")
Observation: 北京今天晴，22-32°C
Thought: 我已获得天气信息，可以回答了
Answer: 北京今天晴，气温 22 到 32 摄氏度，适合户外活动

→ ReAct 是 Agent 模式的基础
```

## 5. System Prompt 设计

### 5.1 层次结构

```text
System Prompt 的推荐结构：

1. 角色定义
   "你是一个 [角色]，擅长 [领域]"

2. 行为准则
   "始终 [行为1]，永远不要 [行为2]"

3. 能力边界
   "你可以 [能力A/B/C]，不能 [限制X/Y/Z]"

4. 输出格式
   "用以下格式回答：..."

5. 特殊规则
   "如果不知道答案，说'我不知道'而不是编造"
```

### 5.2 实战模板

```text
你是一个 Java 后端代码审查专家。

行为准则：
- 优先找出功能性 bug 和安全漏洞
- 不讨论代码风格（缩进/命名等）
- 每个问题标注严重性（Critical/High/Medium/Low）

输出格式（Markdown 表格）：
| 行号 | 问题 | 严重性 | 建议修复 |

如果代码没有明显问题，只输出 "✅ 未发现明显问题"。
如果你不确定某个问题是否存在，明确说"不确定"并解释原因。
```

## 核心要点回顾

- 好的 Prompt = 角色 + 任务 + 格式 + 约束 + 示例
- Few-shot > Zero-shot：复杂任务至少给 2-3 个示例
- CoT = "Let's think step by step" → 推理准确率 +20-40%
- ReAct = Thought → Action → Observation 循环 → Agent 基础
- System Prompt 层次：角色 → 准则 → 边界 → 格式 → 规则
- 黄金法则：具体 > 模糊，示例 > 描述，约束 > 开放
