## 1. 模型能"调用函数"吗：能力的本质

**关键认知：模型从不执行任何函数。** Function Calling 的全部能力 = 模型在响应中输出**结构化的"调用意图"**：

```json
// 模型输出的不是"执行结果"，而是"我要做什么"的指令
{
  "tool_calls": [
    {
      "id": "call_abc123",
      "function": {
        "name": "get_weather",
        "arguments": "{\"city\": \"北京\", \"unit\": \"celsius\"}"
      }
    }
  ]
}
```

```text
职责边界（本体系第一原则）：
  模型：  决定"调哪个工具" + 填写参数（可能填错、可能幻觉）
  你的代码：解析指令 → 校验参数 → 真实执行 → 把结果回传
```

| 谁 | 做什么 | 可信度 |
|----|--------|:---:|
| 模型 | 工具选择 + 参数生成 | ⚠️ 不保证正确 |
| 你的代码 | 执行 + 校验 + 安全 | 100% 可控 |

> 🎯 **核心要点**：FC 的本质是**"决策与执行的分离"**——模型负责智能决策，代码负责可靠执行。所有 Agent 架构（ReAct、Plan-and-Execute、多 Agent）都是在这个分离之上搭积木。

## 2. 演进史：从 JSON 提示到协议级 FC

| 阶段 | 时间 | 做法 | 痛点 |
|------|------|------|------|
| 0：提示词手写 | 2022-2023 | 系统提示里写"如果要查天气，输出 `{"action": "get_weather", "args": {...}}`" | 格式不稳定、解析靠正则、错误率高 |
| 1：Chat Completions 正式化 | 2023-06 | OpenAI 引入 `functions`/`tools` 参数，模型原生输出 `tool_calls` | 参数仍是 JSON 字符串，需自解析 |
| 2：并行与严格化 | 2024-2025 | `parallel_tool_calls`、`strict` 严格模式、Structured Outputs | 各平台格式分叉 |
| 3：Responses API | 2025-2026 | OpenAI Responses API 扁平化函数调用（顶层 `function_call`、`call_id` 回传） | 生态向 Responses 迁移 |
| 4：工具发现与 MCP | 2025-2026 | `tool_search`、Claude `defer_loading` 工具按需发现；MCP 成为工具分发标准 | 工具数量爆炸 |

> 💡 演进主线一句话：**从"模型假装输出 JSON"到"协议保证输出结构"**——每一步演进都在把不确定性从"应用层"移到"协议层"。

## 3. 与"提示词里写 JSON"的本质差异

| 维度 | 提示词手写 JSON | 协议级 Function Calling |
|------|:---:|:---:|
| 输出格式 | 靠提示词约束，常跑偏 | 结构内建，可靠得多 |
| 参数校验 | 无，手写解析 | JSON Schema 约束（strict 模式更强） |
| 并行调用 | 无 | 原生支持（一次多个调用） |
| 循环支持 | 手动拼接 | 标准 tool 消息回传 |
| 流式 | 解析麻烦 | 增量 chunk 语义完整 |
| 成本 | 提示词模板占 token | 工具定义占 token（可缓存） |
| 适用 | 简单/演示场景 | 生产 Agent |

> 🎯 **核心要点**：提示词 JSON 是"**让模型假装**"，FC 是"**协议保证**"。生产环境一律用协议级 FC——手写 JSON 解析在参数嵌套、转义、流式场景下是永无止境的补丁工程。

## 4. 为什么是 Agent 基石

Agent = **模型 + 工具 + 循环**（Harness 体系的核心公式）。三个要素 FC 占两个：

```text
        ┌─────────────┐
        │    模型      │  智能决策：下一步做什么
        └──────┬──────┘
               │ 输出调用意图（FC）
        ┌──────▼──────┐
        │ 工具执行层   │  ← FC 的产物：可执行、可校验、可审计
        └──────┬──────┘
               │ 执行结果回传
        ┌──────▼──────┐
        │  Agent 循环  │  终止/重试/上下文管理（03 章）
        └─────────────┘
```

**没有 FC 的 Agent 是残缺的**：

| Agent 能力 | 依赖 FC 的哪部分 |
|-----------|-----------------|
| 查天气/查库/发邮件 | 工具声明 + 调用 |
| 多步推理（先查再算） | 循环 + 结果回传 |
| 自主规划（Plan-and-Execute） | 工具选择 + 参数化 |
| 安全治理（危险操作确认） | 校验 + 审计（05 章） |
| 人机协作 | tool_choice 控制 |

> 💡 与 ReAct 的关系：ReAct 是"推理-行动-观察"的**认知范式**（提示词层面）；FC 是"调用指令结构化"的**协议层**。现代 Agent = ReAct 的思考 + FC 的手脚。两者不冲突，互为上下层。

## 5. 2026 生态全景

```text
协议层：
  OpenAI Chat Completions（tools 格式，事实标准，DeepSeek/Qwen/国产模型全兼容）
  OpenAI Responses API（新形态：顶层 function_call + call_id，2026 主推）
  Anthropic Tool Use（tools + tool_use/tool_result 块，缓存友好）
  Gemini Function Calling（OpenAI 兼容 + 原生）

发现层：
  OpenAI tool_search（gpt-5.4+，先搜索再加载工具）
  Claude defer_loading + tool_search（工具存根按需加载）

分发层：
  MCP（Model Context Protocol）——工具的标准分发协议，一次接入处处复用
  （与 FC 互补：MCP 管"工具怎么来"，FC 管"调用怎么发生"）

框架层：
  LangChain/LangGraph、OpenAI Agents SDK、Claude Agent SDK、smolagents
  底层全部走 FC 协议；上层只是循环与编排的封装
```

| 关键趋势（2026） | 含义 |
|-----------------|------|
| 推理模型支持工具调用 | o 系列、DeepSeek thinking 模式都能 FC，但带特殊规则（07 章） |
| 严格模式普及 | OpenAI strict、Gemini 约束解码；Anthropic 仍靠提示词 + 校验 |
| 工具缓存成为成本主轴 | 工具定义是 prompt caching 的主要对象（09 章） |
| 工具数量爆炸 → 发现机制 | 几十上百个工具时代，按需加载是标准姿势 |
| MCP 统一分发 | 2025-2026 工具生态向 MCP 收敛（本仓库 06-MCP协议 体系） |

> 🎯 **核心要点**：2026 年学 FC 的正确姿势 = **吃透 OpenAI tools 协议（事实标准）+ 各家差异点（08 章）+ 循环与安全工程（03/05 章）**——底层协议稳定，变化都在生态层。

## 6. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 模型只输出"调用意图"，执行永远是代码的职责 |
| 2 | 演进主线：提示词 JSON → 协议级 FC → 并行/严格 → 工具发现/MCP |
| 3 | 协议级 FC 与手写 JSON 的本质差：结构保证 vs 提示约束 |
| 4 | Agent = 模型 + 工具 + 循环；FC 是"手"和"决策出口" |
| 5 | ReAct 是认知范式、FC 是协议层，互为上下层 |
| 6 | 2026 生态：OpenAI 兼容协议为事实标准，推理模型/缓存/MCP 是三大变量 |
