## 1. 流式下 tool_calls 的完整组装

```python
# 流式完整组装（02 章 §5 的完整版）：含推理模型、错误处理
import json
from openai import AsyncOpenAI

aclient = AsyncOpenAI()

async def stream_tool_calls(messages, tools):
    """流式请求，返回 (最终消息, 组装的 tool_calls 列表)"""
    stream = await aclient.chat.completions.create(
        model="gpt-5.2", messages=messages, tools=tools, stream=True,
    )
    tool_calls: dict[int, dict] = {}
    reasoning = ""                      # 推理模型：思维链增量
    content_parts = []

    async for chunk in stream:
        delta = chunk.choices[0].delta
        if delta.reasoning_content:     # DeepSeek 推理流
            reasoning += delta.reasoning_content
        if delta.content:
            content_parts.append(delta.content)
        if delta.tool_calls:
            for tc in delta.tool_calls:
                idx = tc.index
                slot = tool_calls.setdefault(idx, {"id": "", "name": "", "arguments": ""})
                if tc.id: slot["id"] = tc.id
                if tc.function and tc.function.name: slot["name"] = tc.function.name
                if tc.function and tc.function.arguments:
                    slot["arguments"] += tc.function.arguments     # 增量拼接

    return {
        "content": "".join(content_parts) or None,
        "tool_calls": [
            {"id": s["id"], "name": s["name"], "arguments": s["arguments"]}
            for s in sorted(tool_calls.values(), key=lambda x: x["arguments"])  # 保持顺序
        ],
        "reasoning": reasoning,
    }
```

| 组装要点 | 说明 |
|---------|------|
| `index` 聚合 | 并行调用的每个 chunk 标 index，按 index 分组拼 |
| `arguments` 增量 | 逐 chunk 拼接，结束才完整——**中途不能 json.loads** |
| `name` 单次出现 | 通常首个 chunk 给全，后续为 null |
| `reasoning_content` | 推理模型思维链单独字段（DeepSeek） |
| `finish_reason` | `"tool_calls"` 出现 = 拼装结束 |

> ⚠️ 流式最容易翻车的点：**把"每个 chunk"当成"完整调用"**——`arguments` 必须等 finish 才能解析，流式进度 UI 只能显示"正在准备调用…"，不能显示参数内容。

## 2. 推理模型的特殊规则

o 系列 / DeepSeek thinking / Gemini 推理模型的工具调用与普通模型不同：

| 差异 | 说明 | 应对 |
|------|------|------|
| 先思考后调用 | 响应先出 reasoning 再出 tool_calls | 流式 UI 展示"思考中" |
| 延迟更高 | 推理消耗时间 | 用户预期管理（思考动画） |
| 参数支持差异 | 部分推理模型不接受 `parallel_tool_calls` | 按模型查文档（02 章 §4.2） |
| 工具循环耦合 | 推理内部可能"推理-调用-再推理" | 循环照常，但轮数预算更紧 |
| 成本更高 | 推理 token 额外计费 | 09 章成本模型含 reasoning_tokens |

```python
# 推理模型成本统计（DeepSeek：usage.reasoning_tokens 单独返回）
usage = resp.usage
total_cost = (usage.prompt_tokens * P_IN + usage.completion_tokens * P_OUT
              + getattr(usage, "reasoning_tokens", 0) * P_REASON)
```

> 🎯 **核心要点**：推理模型 = "**调用前先想清楚**"——正确率更高但更慢更贵。生产取舍：**简单任务用非推理模型（快省）、复杂多步任务用推理模型（准）**，混合路由是 2026 标配（06 章路由模式）。

## 3. DeepSeek thinking 模式的工具调用坑

**2026 实测高频坑（多轮工具调用必须回传 reasoning_content）**：

```python
# 场景：thinking 模式下，第一轮模型调用工具并附带了推理
# 第二轮请求必须把上轮 assistant 消息的 reasoning_content 原样带回，
# 否则报 400：
#   "The reasoning_content in the thinking mode must be passed back to the API"

# ✅ 正确：保存并原样回传
assistant_msg = {
    "role": "assistant",
    "content": None,
    "reasoning_content": reasoning_content,     # ⭐ 必须存
    "tool_calls": [{"id": tc.id, "type": "function",
                    "function": {"name": tc.name, "arguments": tc.arguments}}],
}
messages.append(assistant_msg)

# ❌ 错误：只回传 tool_calls 不带 reasoning_content → 400
```

| DeepSeek V4 工具调用要点（2026） | 说明 |
|---------------------------------|------|
| 模型命名 | `deepseek-v4-pro` / `deepseek-v4-flash`（2026-07-24 起，chat/reasoner 旧名弃用） |
| 思考模式 | `thinking_mode: thinking / thinking_max`，**支持工具调用** |
| 回传铁律 | 多轮工具对话必须回传 `reasoning_content`（官方要求） |
| JSON Schema 严格 | 根 `parameters` 必须含 `type: "object"` |
| 流式 | `reasoning_content` 单独增量字段 |
| 成本 | flash 输入 1 元/M（缓存命中 0.02）、输出 2 元/M；pro 3/0.025/6 元/M |

> 💡 生态现状：LangChain `langchain_deepseek_v4`、CAMEL 等框架已内置 reasoning_content 回传处理（曾经大量 400 报错的坑已被框架层消化）；**手写循环时务必自己处理**（本节代码）。

## 4. 工具结果截断与摘要

**工具结果占上下文大头（查询返回几十 KB 是常态）——回传给模型前必须瘦身**：

```python
def truncate_tool_result(result: dict, max_chars: int = 4000) -> dict:
    """截断 + 结构保留：只留摘要信息"""
    if isinstance(result, dict) and "data" in result and len(str(result)) > max_chars:
        data = result["data"]
        if isinstance(data, list):
            return {**result, "data": data[:10],     # 只留前 10 条
                    "_truncated": True,
                    "_total_count": len(data),       # 总数告诉模型
                    "_summary": summarize(data)}     # 或摘要
        return {**result, "data": str(data)[:max_chars], "_truncated": True}
    return result

# 回传前：truncate_tool_result(result)
# 模型需要更多细节时会主动再调（配合 limit 参数，04 章）
```

| 策略 | 做法 | 适用 |
|------|------|------|
| 硬截断 | 4KB 上限 + `_truncated` 标记 | 默认兜底 |
| 前 N 条 + 总数 | 列表数据留 10 条 + 告知总数 | 搜索结果 |
| 摘要 | 大文本转摘要（一次小模型调用） | 长文档 |
| 分页 | 工具带 limit 参数，按需再取 | 结构化数据 |
| **结果-内容分离** | 完整结果存 DB/内存，只回传摘要 | 后续需要原始数据时 |

> 🎯 **核心要点**：**"模型该看什么"由你决定**——工具结果不是"全量回传"，是"回传能支撑决策的最小信息"（+ 需要时再取的路径）。官方建议上限 ~4KB/工具结果，超标即截断或摘要。

## 5. 上下文压缩：长会话三方案

```python
# 方案一：窗口（最简）
messages = messages[-10:]                          # 丢旧保新

# 方案二：摘要压缩（中间转摘要）
async def compress(messages, head=2, tail=8):
    head_msgs = messages[:head]                    # system + 首条
    tail_msgs = messages[-tail:]
    middle = messages[head:-tail]
    if not middle:
        return messages
    summary = await summarize_messages(middle)     # 小模型生成摘要
    return [*head_msgs,
            {"role": "user", "content": f"[历史摘要] {summary}"},
            *tail_msgs]

# 方案三：关键状态保留（只留"事实"不留"过程"）
# 例：查询类 Agent 把"订单已查过，状态=已发货"作为状态注入，丢弃中间轮
```

| 方案 | 成本 | 信息损失 | 适用 |
|------|:---:|:---:|------|
| 窗口 | 低 | 高 | 短会话/简单任务 |
| 摘要压缩 | 中（一次小模型调用） | 中 | ⭐ 长会话默认 |
| 状态保留 | 低-中 | 低（结构化） | 有明确状态的业务（订单/审批） |
| 向量记忆（RAG） | 高 | 检索式 | 超长/跨会话 |

> 💡 压缩触发时机：每轮请求前估算 token，超预算才压缩（06 章 §6 的 manage_context）。**压缩是"代价换空间"**——摘要本身花一次模型调用，别对小会话滥用。

## 6. 流式体验设计：边执行边回答

```text
用户视角的完整 Agent 体验流：
  ① 思考中（推理模型：显示"思考中…"动画）
  ② 工具调用（显示"正在查询订单…"，不暴露参数细节）
  ③ 工具执行（可显示进度：查询到 3/5 条）
  ④ 最终回答（流式打字机效果）

实现：SSE 事件流（FastAPI 体系 08/09 章 + 前端 EventSource）
事件类型：thinking_start / tool_call_start(tool 名) /
         tool_call_end(结果摘要) / text_delta / done
```

```python
# FastAPI 流式 Agent 端点（骨架）
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/agent")
async def agent_endpoint(req: UserRequest):
    async def event_stream():
        async for event in run_agent_streaming(req.message):
            yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"   # SSE
    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

| 体验设计要点 | 说明 |
|-------------|------|
| 思考动画 | 推理阶段 UI 反馈（不是空白等待） |
| 工具调用透明 | 显示"正在查订单"，隐藏参数与密钥 |
| 结果摘要反馈 | 执行完显示"已找到 3 条"，不等最终回答 |
| 取消支持 | 长循环可中断（03 章终止条件） |
| 错误可见 | 工具失败 UI 提示（不是静默跳过） |

> 🎯 **核心要点**：流式不仅是"快"，是"**过程可见**"——用户看到 Agent 在思考、在查、在算，信任感与等待耐心都来自过程透明度。这是 2026 年 Agent 产品体验的第一工程。

## 7. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 流式组装：index 聚合 + arguments 增量拼接 + finish_reason 收尾 |
| 2 | 推理模型：先思后调、更慢更贵，混合路由是标配 |
| 3 | DeepSeek thinking 多轮工具调用**必须回传 reasoning_content**（否则 400） |
| 4 | 工具结果瘦身：4KB 截断 + _truncated + 总数 + 摘要 |
| 5 | 压缩三方案：窗口 / 摘要 / 状态保留；超预算才触发 |
| 6 | 流式体验 = 过程透明：思考/调用/结果/回答四阶段事件 |
| 7 | SSE 事件流（FastAPI StreamingResponse）是 Agent API 的标准形态 |
