## 1. JSON Schema：工具的参数契约

```python
# 完整要素版：一个生产级工具定义
get_order_tool = {
    "type": "function",
    "function": {
        "name": "get_order",
        "description": "按订单号查询订单状态与物流信息。当用户询问订单进度、物流轨迹时使用。",
        "parameters": {
            "type": "object",
            "properties": {
                "order_id": {
                    "type": "string",
                    "description": "订单号，形如 20260801001，来自用户消息或前文上下文",
                },
                "include_items": {
                    "type": "boolean",
                    "description": "是否返回商品明细，默认 false（返回摘要更快）",
                    "default": False,
                },
                "limit": {
                    "type": "integer",
                    "description": "物流轨迹最多返回几条",
                    "minimum": 1,
                    "maximum": 20,
                    "default": 5,
                },
            },
            "required": ["order_id"],
        },
    },
}
```

**Schema 要素速查**：

| 要素 | 作用 | 使用建议 |
|------|------|---------|
| `type` | 类型（string/number/integer/boolean/array/object） | 尽量精确 |
| `description` | 字段语义说明 | **必写**——模型没有你的业务上下文 |
| `enum` | 枚举白名单 | 有限取值就用（单位/状态） |
| `default` | 默认值 | 可选参数给默认，模型少填一项少错一项 |
| `required` | 必填列表 | 精简：只留真正必填 |
| `minimum/maximum` | 数值范围 | 防模型填离谱值 |
| `pattern` | 正则（string） | 订单号/邮箱格式 |

> 🎯 **核心要点**：**工具定义的每个字段都写给模型看**——模型唯一知道的关于你工具的信息，就是 name + description + schema。业务语义（"订单号长什么样"）不写进 schema，模型就只能猜。

## 2. 描述的艺术：从模型的视角写

**官方最佳实践：描述 = "做什么" + "什么时候用"**：

```python
# ❌ 只写"做什么"（模型不知道何时该用）
"description": "获取天气数据"

# ✅ 写清"何时用"（触发条件明确，减少误调用）
"description": "获取指定城市的当前天气与未来 3 天预报。"
                 "当用户询问温度、天气状况、是否下雨、出行建议时使用。"
                 "城市名必须是中文常用名（北京、上海、广州等），"
                 "不接受英文缩写。"

# ❌ 含糊歧义（两个工具边界重叠 → 模型随机选）
"name": "search_users", "description": "搜索用户"
"name": "find_user",   "description": "查找用户"

# ✅ 边界清晰
"name": "search_users",  "description": "按昵称/邮箱模糊搜索用户列表，用于后台管理查询"
"name": "get_user",      "description": "按用户 ID 获取单个用户详情，需先通过 search_users 得到 ID"
```

**描述三原则**：

| 原则 | 做法 |
|------|------|
| 写触发条件 | "当用户……时使用"比"获取……"强一个量级 |
| 写边界 | "不接受英文缩写"、"只支持国内城市"——提前挡幻觉 |
| 写上下文依赖 | "需先通过 search_users 得到 ID"——引导正确调用链 |

> 💡 描述里可以写"约束指令"：`"若订单号格式非法，返回错误而不是尝试查询"`——相当于把业务规则免费塞进工具声明。

## 3. 参数设计：缩小决策空间

**核心思想（官方原则）：每个可选参数都在扩大模型的决策空间**——可选项越多，误填概率越大。

| 设计原则 | 反例 | 正例 |
|---------|------|------|
| 可选参数独立成工具 | `get_weather(city, unit, lang, source, cache, format, detail_level...)` | `get_weather(city, unit)` + 需要详情再单独工具 |
| 高频路径参数化 | 固定查询写死 | 常用查询提供快捷参数 |
| 不常用功能拆出去 | 一个"全能"工具 | 主工具 + 边缘工具 |
| 返回结构可选项少 | `include_a/b/c/d...` 一堆布尔 | 默认返回合理摘要 |
| 枚举代替自由文本 | `unit: str`（模型填 "C"/"摄氏"/"°C"） | `unit: enum["celsius","fahrenheit"]` |

> 🎯 **核心要点**：**工具参数 = 模型的决策负担**。每个参数都在消耗模型的"判断力"——目标是让模型"看一眼就知道填什么"。宁可多一个工具，不要多一个可选参数。

## 4. 命名与粒度：工具的组织哲学

### 4.1 命名规范

| 规范 | 说明 |
|------|------|
| 动词开头 | `get_` / `search_` / `create_` / `update_` / `delete_` / `send_` |
| 语义唯一 | 同一语义不重复建工具（search_users vs find_user 是灾难） |
| 长度适中 | 20-40 字符，模型容易准确复述 |
| 操作对象统一 | `get_order` 与 `get_order_items`（主从关系） |

### 4.2 粒度选择：一个工具一个职责

```text
❌ 万能工具: process_data(type=订单/用户/商品, action=查/删/改, ...)
   → 参数决策空间爆炸、误调用率飙升、审计困难

✅ 职责工具: get_order / cancel_order / search_users / update_user_profile
   → 每个工具语义清晰、安全边界明确、可单独测试
```

**粒度权衡表**：

| 场景 | 建议 |
|------|------|
| 查询类 | 细分（get_x / search_x） |
| 写操作 | 细分 + 确认模式（05 章） |
| 内部工具（Agent 专用） | 可比用户工具更细 |
| 工具超过 20 个 | 角色拆分（客服 6 个 / 管理 6 个）或工具发现（06 章） |

> ⚠️ **工具名重叠是隐性问题**：名字相似、边界模糊的工具，模型会随机选错（用户投诉"查天气给我推送了广告"往往就是两个工具描述重叠）。设计时对每个工具问：**"两个模型会混淆吗？"**

## 5. 工具数量与成本约束

**成本真相（2026 实测）**：

```text
每个工具定义 ≈ 100-200 输入 token/请求
10 个工具 ≈ 1000-2000 token/请求（≈ 每轮都付）
工具调用本身比纯聊天增加 15-30% 的每请求 token 成本

成本 = 工具定义 token × 调用轮数 × 请求次数
```

| 工具数量 | 每请求成本 | 模型选择准确率 | 建议 |
|:---:|:---:|:---:|------|
| 1-5 | 低 | 高 | ✅ 默认 |
| 6-10 | 中 | 中高 | ✅ 常用区间 |
| 10-20 | 高 | 中（开始混淆） | 角色拆分 |
| 20+ | 很高 | 低 | ⚠️ 必须工具发现/子 Agent |

**三个降本手段（09 章展开）**：

1. **prompt caching**：工具定义是稳定前缀，缓存后读取成本降 90%（Anthropic 显式断点、OpenAI 自动）——**工具多时缓存收益巨大**；
2. **角色拆分**：客服 Agent 只挂客服工具（4-6 个），管理 Agent 只挂管理工具——每个 Agent 的工具集小且聚焦；
3. **工具发现**：`tool_search`（OpenAI gpt-5.4+）/ `defer_loading`（Claude）——先传存根，按需加载真身（06 章）。

> 🎯 **核心要点**：工具是"**免费声明、每轮付费**"的资源——数量不是越多越好，而是**"够用 + 可缓存 + 可拆分"**三平衡。20+ 工具时代，工具发现机制是标准答案。

## 6. 装饰器注册：工程化工具表

```python
# tools/registry.py —— 装饰器注册表（生产标准形态）
import json, inspect
from typing import Callable

_TOOL_REGISTRY: dict[str, dict] = {}     # name -> {"schema":..., "fn":...}


def tool(name: str, description: str, schema: dict):
    """注册工具：把 Python 函数 + JSON Schema 绑定"""
    def decorator(fn: Callable):
        _TOOL_REGISTRY[name] = {"fn": fn, "schema": {
            "type": "function",
            "function": {"name": name, "description": description, "parameters": schema},
        }}
        return fn
    return decorator


@tool(
    "get_weather",
    "获取城市天气，用户问温度/天气时使用",
    {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]},
)
async def get_weather(city: str, unit: str = "celsius"):
    """真实实现（可以接 API/DB）"""
    ...


def get_tools(names: list[str] | None = None) -> list[dict]:
    """按需取工具定义（角色拆分/工具发现的基础）"""
    if names is None:
        return [r["schema"] for r in _TOOL_REGISTRY.values()]
    return [_TOOL_REGISTRY[n]["schema"] for n in names if n in _TOOL_REGISTRY]
```

| 注册表能力 | 价值 |
|-----------|------|
| 定义与实现同文件 | 改一处生效 |
| 按需取用 | 角色拆分：客服取 6 个、管理取 6 个 |
| 统一执行入口 | 循环里 `_TOOL_REGISTRY[name]["fn"](**args)` 一行分发 |
| 可测试 | 单测直接调 fn |
| 可审计 | 遍历注册表生成工具清单/文档 |

> 💡 工程化收益：装饰器注册 = **"声明式工具表"**——新增一个工具 = 加一个装饰器函数，循环、文档、测试全自动跟上。这是 Agent 代码库的"一页式"组织方式。

## 7. 工具定义自检清单

- [ ] 描述写了"何时用"（触发条件）而不是只有"做什么"
- [ ] 每个字段都有 description（模型能读懂业务语义）
- [ ] 有限取值用了 enum，数值有范围，格式有 pattern
- [ ] required 只含真正必填项
- [ ] 可选参数尽量少（决策空间小）
- [ ] 名称动词开头、语义唯一、无重叠工具
- [ ] 一个工具一个职责，写操作与查询分离
- [ ] 返回结果结构声明过（模型知道会拿到什么）
- [ ] 错误返回有 code+message（03 章）
- [ ] 工具数在 10 个内或已规划角色拆分/工具发现

## 8. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | schema = 模型的"业务文档"，description 必写、enum/范围/pattern 用足 |
| 2 | 描述 = 做什么 + 何时用 + 边界约束，三件套 |
| 3 | 参数即决策负担：可选参数独立成工具，别做万能工具 |
| 4 | 命名动词开头、语义唯一；一工具一职责 |
| 5 | 工具 ≈ 100-200 token/请求；10 个内最优，20+ 必须拆分/发现 |
| 6 | 降本三件套：prompt caching + 角色拆分 + 工具发现 |
| 7 | 装饰器注册表是工具组织的生产标准形态 |
| 8 | 自检清单：描述/字段/枚举/范围/职责/成本六问 |
