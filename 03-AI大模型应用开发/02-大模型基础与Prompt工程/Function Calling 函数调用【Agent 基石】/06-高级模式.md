## 1. 并行调用：一次响应多个工具

```python
# 已开启 parallel_tool_calls=True（默认）时，复合问题触发多个调用
resp = client.chat.completions.create(
    model="gpt-5.2",
    messages=[{"role": "user", "content": "北京和上海的天气，加上苹果股价"}],
    tools=[weather_tool, weather_tool, stock_tool],
)

calls = resp.choices[0].message.tool_calls   # 可能 3 个
# 执行：asyncio.gather 并发（03 章 §4）
# 回传：每个调用一条 tool 消息（02 章 §3）
```

| 并行调用的收益 | 说明 |
|---------------|------|
| 延迟 | 3 个串行 6s → 并发 2s |
| 轮数 | 一轮问完 vs 三轮 |
| 上下文 | 每轮全量上下文，少轮 = 少 token |

**并行使用纪律（02 章 §4.2 回顾）**：

- 有顺序依赖 → `parallel_tool_calls=False`（协议层关闭）
- strict 结构保证 → 关闭并行（官方明确）
- 危险/副作用 → 关闭并行 + 确认模式（05 章）
- **处理代码永远按数组循环**——不管你开不开并行，模型都可能一次给多个（OpenAI 官方：assume multiple）

> 🎯 **核心要点**：并行是"白拿的吞吐"，前提是**工具间无依赖**。判断依赖的可靠方法：问自己"这个工具的参数需要另一个工具的返回值吗？"——需要，就关并行。

## 2. 强制调用：路由与提取

```python
# 场景一：意图路由（先分类再分发）
# 用强制指定工具让模型"选择路径"
router_tool = {
    "type": "function",
    "function": {
        "name": "route_intent",
        "description": "判断用户意图并路由",
        "parameters": {
            "type": "object",
            "properties": {
                "intent": {"type": "string",
                           "enum": ["order_query", "refund", "complaint", "chat"]},
            },
            "required": ["intent"],
        },
    },
}

resp = client.chat.completions.create(
    model="gpt-5.2",
    messages=[{"role": "user", "content": user_msg}],
    tools=[router_tool],
    tool_choice={"type": "function", "function": {"name": "route_intent"}},  # 强制
)
intent = json.loads(resp.choices[0].message.tool_calls[0].function.arguments)["intent"]
# → 按 intent 分发给不同子 Agent / 流程（§5）

# 场景二：实体提取（结构化输出形态，见 §3）
```

| 强制调用场景 | tool_choice | 说明 |
|------------|------------|------|
| 意图路由 | 指定 router 工具 | 模型"必须"分类，分类错误也返回（好过自由发挥） |
| 实体提取 | 指定 extract 工具 | 参数结构由 schema 保证 |
| 必须查询 | `"required"` | 实时数据任务防"模型直接编答案"（DeepSeek 官方建议） |
| 最终总结 | `"none"` | 工具结果回填后关闭调用，出最终答案 |

> 💡 **"必须查"模式**（DeepSeek 官方实践）：查询类任务用 `tool_choice="required"`——否则模型可能跳过查询直接生成答案（编造数据）。查询结果回填后的最终回答阶段再切 `"none"`。

## 3. 结构化输出：FC 的提取形态

**用"强制指定工具"实现可靠的结构化提取**（比 JSON mode 更强的 Schema 保证）：

```python
extract_schema = {
    "type": "object",
    "properties": {
        "order_id": {"type": "string"},
        "items": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {"name": {"type": "string"}, "qty": {"type": "integer"}},
                "required": ["name", "qty"],
                "additionalProperties": False,
            },
        },
        "total": {"type": "number"},
    },
    "required": ["order_id", "items", "total"],
    "additionalProperties": False,
}

# strict: True + 强制指定 + 并行关闭（05 章 §3：严格模式下的调用组合）
resp = client.chat.completions.create(
    model="gpt-5.2",
    messages=[{"role": "user", "content": "我的订单 20260801001 有两件 T 恤，共 99 元"}],
    tools=[{"type": "function", "function": {
        "name": "extract_order", "description": "从消息提取订单信息",
        "strict": True, "parameters": extract_schema}}],
    tool_choice={"type": "function", "function": {"name": "extract_order"}},
    parallel_tool_calls=False,
)
```

| 提取方式对比（2026） | 结构保证 | 适用 |
|---------------------|:---:|------|
| JSON mode（response_format） | 中（合法 JSON，不保证 schema） | 简单提取 |
| 强制指定工具 + strict | 高（schema 强约束） | ⭐ 生产首选 |
| Pydantic 客户端校验兜底 | 应用层保证 | 永远要加 |

> 🎯 **核心要点**：**"提取"与"调用"是 FC 的一体两面**——强制指定工具 = 结构化输出。业务数据的"模型转结构"（订单解析、简历解析、意图分类）全部用这个模式，配合 05 章的 Pydantic 二次校验。

## 4. 工具发现：20+ 工具时代

工具数量爆炸后，"每个请求全量声明"在成本与准确率两端都不可行——2026 年两大官方方案：

### 4.1 OpenAI tool_search（gpt-5.4+）

```python
resp = client.chat.completions.create(
    model="gpt-5.4",
    messages=[...],
    tools=[...100 个工具...],
    tool_search={"max_results": 8},      # 先搜索最相关 8 个再调用
)
```

### 4.2 Claude defer_loading（存根 + 按需加载）

```python
tools = [
    {"name": "weather_api", "defer_loading": True},   # 存根：只传名字
    # ... 数十个存根
    {"name": "tool_search", "description": "搜索可用的工具", ...},  # 发现工具本身
]
```

| 方案 | 机制 | 收益 |
|------|------|------|
| OpenAI tool_search | 模型内部先搜后调 | 只付"被选工具"的上下文 |
| Claude defer_loading | 存根占位，调用时加载真身 | 工具集变更不破坏缓存（09 章） |
| 自研工具检索 | 向量检索工具描述 + 动态注入 | 全平台通用（配合 Embedding 体系） |

> 💡 工程务实路线（2026）：**10 个以内全量声明**（简单可靠）；**10-50 个用角色拆分 + 按需 get_tools（04 章注册表）**；**50+ 用官方工具发现或自研检索**。工具发现的本质 = "把工具选择从模型内部决策变成可检索的工程决策"。

## 5. 动态工具注册与多角色子 Agent

```python
# 子 Agent 模式：一个 Agent 一组工具（04 章注册表按需取用）
AGENTS = {
    "customer_service": {
        "system": "你是客服，处理订单查询与售后",
        "tools": get_tools(["get_order", "search_orders", "propose_refund", "ask_human"]),
    },
    "data_analyst": {
        "system": "你是数据分析师，查询并解读数据",
        "tools": get_tools(["query_warehouse", "run_sql", "visualize"]),
    },
    "admin": {
        "system": "你是管理员助手",
        "tools": get_tools(permission="admin"),     # 权限过滤（05 章 §4）
    },
}


async def run_agent(agent_name: str, messages: list) -> str:
    cfg = AGENTS[agent_name]
    # 每个子 Agent 独立循环（03 章）
    return await agent_loop(
        messages=messages,
        system=cfg["system"],
        tools=cfg["tools"],
    )


# 顶层编排：router 决定交给哪个子 Agent（§2 路由），或主 Agent 把任务委派
```

| 模式 | 场景 | 工具集 |
|------|------|:---:|
| 单 Agent | 简单任务 | 4-10 |
| **多角色子 Agent** | 客服 + 管理 + 数据分析并存 | 每组 4-6 |
| 多 Agent 协作 | 规划 → 执行 → 审查 | 每组专职 |

> 🎯 **核心要点**：**"角色拆分"同时解决成本、准确率、安全三个问题**（04 章 §5 / 05 章 §4）——每个子 Agent 的工具集小（成本低）、聚焦（准确率高）、边界明确（危险工具不可见）。这是 2026 年 Agent 系统的事实标准架构。

## 6. 多轮记忆与上下文策略

```python
# 长会话上下文管理三件套
MAX_CONTEXT_TOKENS = 32000

def manage_context(messages: list, tools_tokens: int) -> list:
    """超预算时压缩：摘要旧轮 + 保留工具调用轮"""
    total = estimate_tokens(messages)
    if total + tools_tokens <= MAX_CONTEXT_TOKENS:
        return messages
    # ① 保留第一轮（用户原始诉求）+ 最近 N 轮
    head = messages[:2]                          # system + 首条 user
    recent = messages[-8:]                       # 最近 8 条消息
    # ② 中间轮次摘要（07 章压缩实现）
    summary = summarize(messages[2:-8])
    return [*head, {"role": "user", "content": f"[历史摘要] {summary}"}, *recent]
```

| 策略 | 做法 | 注意 |
|------|------|------|
| 窗口截断 | 只留最近 N 轮 | 简单但丢关键上下文 |
| 摘要压缩 | 旧轮转摘要（07 章） | 摘要本身是一次模型调用成本 |
| **工具结果精简** | 结果只回传摘要（截断 4KB，07 章） | ⭐ 最实用：工具结果占大头 |
| 向量记忆 | 外部记忆库检索（RAG 体系） | 超长会话 |

> 💡 记忆的本质：**上下文预算 = 模型的有效工作记忆**。工具结果是大头（查询返回 50KB 就爆预算）——"工具返回什么"与"给模型看什么"分离（07 章 §3 截断/摘要）。

## 7. 模式选型决策树

```text
任务是什么？
├─ 纯聊天 → 无工具 / tool_choice="none"
├─ 实时数据查询 → 工具 + tool_choice="required" + 结果回填后 "none"
├─ 提取/分类 → 强制指定工具 + strict（结构化输出）
├─ 多步任务（查→算→查）→ 循环 + 依赖处关并行
├─ 危险操作 → 确认-执行两段式（05 章）
├─ 多领域并存 → 角色拆分子 Agent
└─ 工具 50+ → 工具发现/检索
```

## 8. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 并行 = 无依赖时的白拿吞吐；有依赖/危险/严格场景关掉 |
| 2 | 强制调用双场景：意图路由 + 实体提取 |
| 3 | 结构化输出 = 强制指定工具 + strict + 关并行 + Pydantic 兜底 |
| 4 | 查询任务用 required 防"编答案"；总结阶段切 none |
| 5 | 工具发现：10 内全量 / 10-50 角色拆分 / 50+ 官方发现或检索 |
| 6 | 多角色子 Agent = 成本 + 准确率 + 安全三赢 |
| 7 | 上下文管理：工具结果精简最实用，摘要/窗口兜底 |
| 8 | 模式选型走决策树：先定任务类型再选机制 |
