## 1. 成本模型：FC 的每一分钱花在哪

```text
Agent 单次任务成本 = 请求次数 × (输入 + 输出 + 工具定义) × 单价

放大因素：
  ① 工具定义：每个 ≈100-200 token × 每轮请求（10 工具 × 5 轮 = 5000-10000 token 纯工具开销）
  ② 循环轮数：每轮全量上下文重发（历史 + 工具结果累积）
  ③ 推理模型：reasoning_tokens 单独计费（可能占输出大头）
  ④ 结果回传：工具结果越大越贵（07 章截断）
```

**成本优化优先级（按 ROI 排序）**：

| # | 手段 | 效果 | 章节 |
|:---:|------|------|:---:|
| 1 | **Prompt caching** | 输入成本降 50-90% | 本节 |
| 2 | 工具结果截断/摘要 | 输入大头直接削 | 07 |
| 3 | 工具定义精简 | 每轮省 100-200 token/工具 | 04 |
| 4 | 角色拆分（小工具集） | 少声明 = 少付 | 06 |
| 5 | 轮数控制 | 每轮 = 全量成本 | 03 |
| 6 | 模型路由（简单任务用 flash） | 单价差 2-3 倍 | 08 |
| 7 | 推理模型按需（非默认） | 省 reasoning token | 07 |

> 🎯 **核心要点**：Agent 成本 = **"每轮全量上下文 × 轮数"** 的乘法问题——**砍轮数、砍工具、砍结果**三个方向同时做，成本可以降一个数量级。先用成本模型估算，再上缓存（§2）。

## 2. Prompt Caching：工具定义的缓存艺术

### 2.1 机制

```text
缓存 = 前缀精确匹配：提示词前部（工具定义 + system）在 5 分钟内不变 → 命中缓存
命中价格（Anthropic 2026 参考）：读 $0.30/M（90% 折扣），写 $3.75/M（25% 溢价）
OpenAI：缓存命中输入半价（50% 折扣），自动生效
DeepSeek：缓存命中 0.02 元/M vs 未命中 1 元/M（98% 折扣！）
```

### 2.2 Anthropic 显式断点（工具定义是主要缓存对象）

```python
tools = [
    {..., "cache_control": {"type": "ephemeral"}},    # 中间工具也可打
    {..., "cache_control": {"type": "ephemeral"}},    # ⭐ 最后一个工具打断点
    # → 打断点后：tools 整体作为缓存前缀
]

# 多轮会话：在最新一轮末尾再打一个断点（随会话增长增量命中）
messages = [
    {"role": "user", "content": [{"type": "text", "text": "查询订单",
      "cache_control": {"type": "ephemeral"}}]},      # 最近轮次的断点
]
```

### 2.3 缓存铁律（Anthropic 官方 + 社区共识）

| 铁律 | 违反的代价 |
|------|-----------|
| **会话中途不增删/重排工具** | 工具在提示词最前，一变全失效 |
| 工具排序确定性（如按名称排序） | 随机顺序 = 缓存永远不命中 |
| system 提示词冻结（不插时间/用户名） | 前缀一变全部失效 |
| 动态信息走消息（不走提示词编辑） | 用 user/assistant 消息注入更新 |
| 模型中途不切换 | 缓存按模型隔离 |
| 变化的内容放尾部（断点之后） | 保持共享前缀稳定 |

> ⚠️ 实测数据：工具前缀稳定 + 正确打断点，**85% 命中率 / 60-90% 成本降幅**是社区常态；"会话里加了个工具"就能让成本瞬间回到 3-4 倍。**缓存设计从第一天就要考虑**——工具集变更策略（defer 存根而非删除，06 章 §4）就是为缓存设计的。

## 3. 监控与告警

```python
# 指标清单（Prometheus / 自研）
AGENT_REQUESTS_TOTAL{tool, provider}      # 工具调用次数分布
AGENT_TOOL_LATENCY{tool}                  # 工具执行耗时（P50/P95/P99）
AGENT_TOOL_ERRORS{tool, code}             # 工具错误码分布
AGENT_COST_USD{turn, provider}            # token 成本（按轮累计）
AGENT_LOOP_TURNS{turn_count}              # 轮数分布（卡循环检测）
AGENT_TOKENS{tool_result_size}            # 工具结果大小分布（截断率）
```

| 告警规则 | 触发 | 动作 |
|---------|------|------|
| 成本飙升 | 单会话成本 > 阈值 | 冻结会话 / 切便宜模型 |
| 卡循环 | 轮数 > 上限 × 2 且未终止 | 强制终止 + 复盘提示词 |
| 工具错误率升高 | 某工具 ERROR > 10% | 停用该工具 / 修实现 |
| 结果截断率异常 | 截断 > 90% | 检查工具返回设计（07 章） |
| 缓存命中率下降 | 命中率 < 50% | 检查工具集是否被改动 |

> 🎯 **核心要点**：Agent 监控三件事——**钱（成本）、卡（轮数）、错（工具）**。这三类指标直接对应三大生产事故：烧钱、死循环、功能坏。

## 4. 测试体系：没有模型的 CI

**核心思想：确定性测试不依赖模型**（模型输出是概率的，CI 里测不了）：

```python
# ① 工具单测：参数校验 + 业务逻辑（无模型）
def test_get_order_validation():
    with pytest.raises(ToolArgsError):
        validate_args("get_order", {"order_id": "abc"}, GetOrderArgs)   # 格式错

def test_cancel_order_business_rules():
    # 状态拦截：已发货不可取消
    assert cancel_order_tool("1", user)["error"]["code"] == "STATUS_BLOCKED"

# ② 循环单测：mock 模型响应（固定 tool_calls）
def test_loop_executes_and_returns(mock_llm):
    mock_llm.side_effect = [
        AssistantWithTools([ToolCall("get_weather", {"city": "北京"})]),
        AssistantText("北京今天 25°C"),
    ]
    result = agent_loop("北京天气？", tools)
    assert result == "北京今天 25°C"
    assert mock_llm.call_count == 2

# ③ 回归测试：真实模型冒烟（CI 之外，灰度环境）
# 固定用例集跑一遍，断言"工具选择正确率"不低于阈值
```

| 测试层 | 内容 | 跑在哪 |
|--------|------|--------|
| 工具单元测试 | 校验/业务规则/权限 | CI（每次提交） |
| 循环单元测试 | mock LLM 的调用编排 | CI |
| 协议适配测试 | 各家解析/回传（08 章适配器） | CI |
| 冒烟回归 | 真实模型固定用例 | 灰度环境（发布前） |
| 黄金数据集 | 工具选择准确率基线 | 定期评估 |

> 💡 **模型不可测，逻辑可测**——把"模型输出的处理逻辑"（校验/执行/循环）做成可 mock 的纯函数，90% 的代码都能进 CI。真实模型的行为用"冒烟 + 黄金数据集"在外围把关。

## 5. 日志与可观测

```python
# 每轮调用的标准日志（03 章 §6 强化版）
logger.info({
    "event": "agent.tool_call",
    "trace_id": trace_id,          # 会话追踪
    "turn": turn,
    "tool": tc.function.name,
    "args": redact(tc.function.arguments),   # 脱敏（05 章 §7）
    "result_code": result.get("code", "ok"),
    "latency_ms": ms,
    "cost_usd": round(cost, 6),
    "tokens": {"prompt": p, "completion": c, "reasoning": r},
})
```

| 必记字段 | 用途 |
|---------|------|
| trace_id + turn | 会话级回溯 |
| tool + args（脱敏） | 行为审计 |
| result_code | 成功率统计 |
| latency / cost / tokens | 性能与成本 |

> 💡 日志与审计一体：**生产日志 = 调试工具 + 审计记录 + 成本账本**三合一（05 章 §7 的审计要求直接复用）。

## 6. 生产架构参考

```text
用户/前端
   │ (SSE 流式，07 章)
   ▼
API 网关（FastAPI，JWT 认证）
   ▼
Agent 编排服务（循环引擎，03 章）
   ├── 模型路由层（08 章适配器：OpenAI/DeepSeek 主备）
   ├── 工具注册表（04 章装饰器，角色过滤 05 章）
   ├── 工具执行层（超时/重试/幂等 03 章）
   ├── 缓存层（Redis：prompt 缓存由平台侧 + 业务缓存）
   └── 可观测（日志/指标/审计，本节）
   │
   ├── 业务系统（订单/支付/DB，07 章 FastAPI 体系）
   └── MCP 工具服务器（工具分发，06-MCP协议 体系）
```

| 架构要点 | 说明 |
|---------|------|
| 循环与工具分离 | 编排服务只管循环，工具是插件 |
| 主备供应商 | 适配层 + 降级（一家挂自动切） |
| 会话状态外置 | Redis 存会话/上下文（多实例水平扩展） |
| 异步任务 | 长任务进队列（FastAPI 体系后台任务） |

> 🎯 **核心要点**：生产 Agent 服务 = **FastAPI（传输层）+ 循环引擎（编排）+ 工具注册表（能力）+ 可观测（护城河）**——本体系 03/04/05 章 + FastAPI 体系拼起来就是完整生产架构。

## 7. 12 大避坑清单

| # | 坑 | 章节 | 一句话解法 |
|:---:|-----|:---:|------|
| 1 | `tool_calls[0]` 只处理第一个 | 02 | 永远循环处理（官方：assume multiple） |
| 2 | `arguments` 当 dict 用 | 02 | 先 json.loads（Anthropic 除外） |
| 3 | 回传时删了 assistant 消息 | 02 | assistant 消息原样带 tool_calls |
| 4 | 工具异常直接抛 | 03 | 错误转 JSON 回传（80% 卡死解药） |
| 5 | 依赖场景还开并行 | 02/06 | parallel_tool_calls=False |
| 6 | 不写业务校验 | 05 | 三层校验：strict→Pydantic→业务 |
| 7 | 危险操作模型直接执行 | 05 | 确认-执行两段式 |
| 8 | 提示注入裸奔 | 05 | 工具结果标记为数据 |
| 9 | DeepSeek 不回传 reasoning_content | 07 | 多轮工具调用 400 的元凶 |
| 10 | 工具结果全量回传 | 07 | 4KB 截断 + 摘要 |
| 11 | 会话中改工具集 | 09 | 缓存全失效，成本翻几倍 |
| 12 | 循环无上限 | 03 | 8-12 轮上限 + 预算兜底 |

## 8. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 成本 = 轮数 × 全量上下文 × 单价；砍轮/砍工具/砍结果三管齐下 |
| 2 | Prompt caching：工具前缀稳定 + 正确断点 = 50-90% 降本 |
| 3 | 缓存铁律：不增删工具、固定排序、冻结 system、不换模型 |
| 4 | 监控三件事：钱（成本）/ 卡（轮数）/ 错（工具错误） |
| 5 | 测试：工具/循环/适配三层 CI（mock 模型），冒烟在外围 |
| 6 | 日志 = 调试 + 审计 + 成本账本三合一，全字段脱敏 |
| 7 | 生产架构：FastAPI + 循环引擎 + 工具注册表 + 可观测 |
| 8 | 12 避坑三大根因：解析错误、校验缺失、缓存破坏 |
