## 1. 横向对比总表

| 维度 | OpenAI | Anthropic | DeepSeek V4 | Gemini | Qwen（通义） |
|------|:---:|:---:|:---:|:---:|:---:|
| 协议 | Chat Completions + **Responses** | 原生 Tool Use | **OpenAI 兼容**（Chat） | OpenAI 兼容 + 原生 | OpenAI 兼容 |
| Schema 字段 | `parameters` | `input_schema` | `parameters` | `parameters` | `parameters` |
| 参数形态 | JSON 字符串 | dict | JSON 字符串 | 字符串/dict | 字符串 |
| 严格模式 | ✅ strict | ❌ 无 | 部分（schema 严） | 部分模型约束解码 | ❌ 无 |
| 并行调用 | ✅ 默认开 | ✅ | ✅（默认关更稳） | ✅ | ✅ |
| 工具缓存 | 自动 prompt caching | 显式 cache_control | 缓存命中价极低 | 自动 | 自动 |
| 推理模型 FC | o 系列支持 | ✅ | ✅ thinking 模式 | ✅ | ✅ |
| 特殊坑 | strict+并行不兼容 | code_execution 块不可缓存 | **reasoning_content 必回传** | 格式随版本变动 | 兼容层偶有字段差异 |
| 2026 基准模型 | gpt-5.x | Claude 5 系 | v4-pro / v4-flash | Gemini 3.x | Qwen3 系 |

> 🎯 **核心要点**：**OpenAI Chat Completions 是事实协议**——DeepSeek/Qwen/国产全家都兼容它；Anthropic 是"同概念不同名"的原生格式；真正"多一套概念"的只有 Anthropic。**统一封装层（§6）是跨平台标配**。

## 2. OpenAI：事实标准

```python
# 能力清单（2026）
# ✅ 并行调用（默认）      ✅ strict 严格模式       ✅ 强制指定工具
# ✅ Responses API 新范式  ✅ tool_search 工具发现  ✅ 内置工具（web_search 等）
# ✅ 流式 tool_calls      ✅ prompt caching 自动
```

| 特性 | 用法 | 备注 |
|------|------|------|
| strict | `"strict": True` | 规则见 05 章 §3；并行下不保证 |
| Responses | 顶层 function_call + call_id | 新功能主阵地（02 章 §7） |
| tool_search | `tool_search={"max_results": 8}` | gpt-5.4+；06 章 §4 |
| 内置工具 | web_search / code_interpreter 等 | Responses 原生，省自研 |

> 💡 OpenAI 的定位：**功能最全、文档最全、生态最全**——学 FC 首选平台，实现新特性最早（strict、工具发现都是它先推）。

## 3. Anthropic：缓存与块结构

```python
# Anthropic 与 OpenAI 的关键差异（02 章 §6 细节补充）
# ① 块结构：content 数组里 type="tool_use" / "tool_result"
# ② 缓存：工具定义用 cache_control 显式打断点（09 章）
# ③ 无 strict：靠提示词 + 客户端校验
# ④ 工具发现：defer_loading 存根 + tool_search（06 章 §4）

tools = [
    {"name": "get_weather", "description": "...",
     "input_schema": {...},
     "cache_control": {"type": "ephemeral"}},    # ⭐ 最后一个工具上打断点
]
```

| Anthropic 优势 | 说明 |
|---------------|------|
| 缓存控制力强 | 显式断点，工具前缀稳定时读价 90% 折扣 |
| 长上下文 | 大工具集/长会话友好 |
| 工具数量上限高 | 支持数百工具 + 存根机制 |

> ⚠️ Anthropic 缓存铁律（09 章展开）：**会话中途绝不增删/重排工具**（缓存前缀失效）；要"移除"工具用 defer_loading 存根而不是真删。

## 4. DeepSeek V4：推理与工具的结合

```python
# DeepSeek V4 工具调用（2026 基准）
from openai import OpenAI

client = OpenAI(base_url="https://api.deepseek.com/v1", api_key=...)

resp = client.chat.completions.create(
    model="deepseek-v4-flash",               # or deepseek-v4-pro
    messages=[...],
    tools=[...],                             # OpenAI 兼容格式
    tool_choice="auto",
    thinking_mode="non-thinking",            # non-thinking / thinking / thinking_max
    stream=True,
)
```

| 特性 | 说明 |
|------|------|
| 模型 | `deepseek-v4-pro`（3 元/6 元 M）/ `deepseek-v4-flash`（1 元/2 元 M），1M 上下文 |
| 兼容性 | OpenAI SDK 改 base_url 即用 |
| **thinking 模式支持工具调用** | 但多轮必须回传 reasoning_content（07 章 §3） |
| tool_choice | auto / required / none / 指定工具全支持 |
| 严格性 | JSON Schema 校验严格（根 parameters 必须 type:"object"） |
| 价格优势 | 缓存命中 0.02-0.025 元/M（读价极低）——长会话成本友好 |

> 🎯 **核心要点**：DeepSeek 是"**OpenAI 兼容 + 推理能力 + 极致低价**"组合——国内生产 Agent 的主流选择。最大的坑就是 thinking 模式的 reasoning_content 回传（07 章 §3 完整解法）。

## 5. Gemini 与国产模型（Qwen 等）

```python
# Gemini：OpenAI 兼容 + 原生 SDK 双轨
# 原生（google-genai）：
from google import genai
client = genai.Client(api_key=...)
resp = client.models.generate_content(
    model="gemini-3-pro",
    contents="北京天气？",
    config={"tools": [{"function_declarations": [{"name": "get_weather",
                                                  "description": "...",
                                                  "parameters": {...}}]}],
            "automatic_function_calling": {"disable": True}},   # 默认自动执行，可关闭
)
# 兼容模式：OpenAI SDK + base_url（GOOGLE 官方支持兼容端点）

# Qwen（通义千问）：OpenAI 兼容（dashscope 兼容端点）
#   - Qwen3 系支持工具调用，部分模型默认关闭 parallel_tool_calls（与 DeepSeek 相似）
#   - 兼容层偶有字段差异（如某些版本 tools 内嵌格式），以官方文档为准
```

| 平台 | 接入方式 | 注意事项 |
|------|---------|---------|
| Gemini | 原生 SDK 或 OpenAI 兼容端点 | `automatic_function_calling` 默认自动执行，**关掉它自己控制循环** |
| Qwen | OpenAI 兼容（DashScope） | 版本差异：按官方文档核对 tools 字段 |
| Kimi/Moonshot、MiniMax、智谱 | OpenAI 兼容 | 能力随模型版本波动，生产前逐个验证 |

> 💡 国产模型共性问题：**"OpenAI 兼容"≠"OpenAI 同能力"**——strict 支持、并行支持、工具数量上限各家不同。生产接入流程：**先写兼容性探针（probe）跑通工具调用，再上线**（deepseek-compat-kit 提供了现成 probe 工具）。

## 6. 统一适配层设计

```python
# provider.py —— 跨平台适配层（概念版；LLM-API/09 有完整实现）
from abc import ABC, abstractmethod


class ToolProvider(ABC):
    """平台适配器接口：声明/解析/回传三个差异点全部收敛"""
    @abstractmethod
    def build_tools(self, tools: list[dict]) -> list: ...
    @abstractmethod
    def parse_calls(self, raw_response) -> list[ToolCall]: ...   # 统一 ToolCall 结构
    @abstractmethod
    def build_result_message(self, call: ToolCall, result: str) -> dict: ...


class OpenAIChatProvider(ToolProvider):
    def parse_calls(self, resp):
        return [ToolCall(id=tc.id, name=tc.function.name,
                         args=json.loads(tc.function.arguments))
                for tc in (resp.choices[0].message.tool_calls or [])]

class AnthropicProvider(ToolProvider):
    def parse_calls(self, resp):
        return [ToolCall(id=b.id, name=b.name, args=b.input)
                for b in resp.content if b.type == "tool_use"]

class DeepSeekProvider(OpenAIChatProvider):
    """OpenAI 兼容 → 继承 + 补 reasoning_content 回传"""


# 统一循环只依赖 ToolCall 抽象（03 章循环零改动换平台）
```

| 适配层收益 | 说明 |
|-----------|------|
| 循环只写一遍 | 解析/回传差异全在适配器 |
| 平台可插拔 | 配置切换，成本/能力/地理需求换供应商 |
| 统一日志/审计 | 中间件层统一记录 ToolCall |
| 兼容性探针 | 适配器附带"平台能力检测"（strict/并行/上限） |

> 🎯 **核心要点**：**抽象"调用"而非抽象"平台"**——统一的数据结构（ToolCall: id/name/args）把三家协议的差异消解在适配器层，Agent 循环、日志、测试全部基于抽象编写。这是 2026 年多模型生产的事实架构。

## 7. 选型决策

| 需求 | 推荐 | 理由 |
|------|------|------|
| 功能最新最全 | OpenAI（gpt-5.x / Responses） | strict、工具发现、内置工具 |
| 长会话/大工具集 | Anthropic（Claude 5） | 缓存控制 + 工具上限高 |
| 性价比 + 推理 | DeepSeek V4 | OpenAI 兼容 + 低价 + thinking 模式 |
| 国内合规/出海 | Qwen / Gemini | 区域政策与网络环境 |
| 多平台生产 | 统一适配层 + 主备切换 | 供应商风险与成本优化 |

> 💡 **选型口诀**：**协议认 OpenAI（兼容性最广）、能力看需求（strict/缓存/推理）、生产必封装（适配层）**——把"选哪个模型"降级为"改一行配置"。

## 8. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | OpenAI Chat Completions 是事实协议，国产全家兼容；Anthropic 是唯一"另一套概念" |
| 2 | OpenAI：strict + 并行 + Responses + 工具发现，功能全 |
| 3 | Anthropic：块结构 + 显式缓存断点，长会话/大工具集强 |
| 4 | DeepSeek V4：OpenAI 兼容 + 低价 + thinking 支持工具调用（回传坑） |
| 5 | Gemini：automatic_function_calling 默认自动执行，记得关掉 |
| 6 | 国产模型"兼容 ≠ 同能力"，生产前跑兼容性探针 |
| 7 | 统一适配层：抽象 ToolCall，循环/日志/测试零平台依赖 |
| 8 | 选型：协议认 OpenAI、能力看需求、生产必封装 |
