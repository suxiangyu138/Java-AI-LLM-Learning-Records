## 1. Agent loop：最小完整实现

```python
# agent.py —— 最小生产级 Agent 循环（单文件版）
import json
from openai import OpenAI

client = OpenAI()
TOOLS = [...]          # 工具定义（02 章）
MAX_TURNS = 10         # 循环上限


class ToolError(Exception):
    """工具执行失败（转成可回传的错误结果，不让循环崩）"""


def execute_tool(name: str, arguments: dict) -> dict:
    """工具注册表：按名字分发到真实函数（04 章扩展为装饰器注册）"""
    registry = {"get_weather": get_weather, "get_stock_price": get_stock_price}
    if name not in registry:
        raise ToolError(f"未知工具: {name}")
    return registry[name](**arguments)


async def agent_loop(user_message: str, tools: list, max_turns: int = MAX_TURNS):
    messages = [{"role": "user", "content": user_message}]
    for turn in range(max_turns):
        resp = client.chat.completions.create(
            model="gpt-5.2",
            messages=messages,
            tools=tools,
            tool_choice="auto",
        )
        message = resp.choices[0].message
        messages.append(message)                 # ① 先存 assistant 消息（含 tool_calls）

        if not message.tool_calls:               # ② 没有调用 = 回答完成 → 退出
            return message.content

        for tc in message.tool_calls:            # ③ 执行每个调用（可并行，§4）
            try:
                result = execute_tool(tc.function.name, json.loads(tc.function.arguments))
            except Exception as exc:             # ④ 错误也回传，不让循环崩
                result = {"error": str(exc)}
            messages.append({                    # ⑤ 结果回传
                "role": "tool",
                "tool_call_id": tc.id,
                "content": json.dumps(result, ensure_ascii=False),
            })
    return "抱歉，我无法在限制轮数内完成此任务。"   # ⑥ 轮数耗尽兜底
```

> 🎯 **核心要点**：完整循环 = **"追加 assistant 消息 → 判空退出 → 执行工具 → 回传结果 → 下一轮"**五步。`return message.content` 是唯一正常出口；循环上限是保命绳。50 行的循环就是 Agent 的全部骨架。

## 2. 循环状态机与终止条件

```text
                    ┌────────────┐
                    │   开始      │
                    └─────┬──────┘
                          ▼
              ┌───────────────────┐
              │  调用模型          │◄───────────┐
              └──────┬────────────┘            │
                     ▼                         │
        ┌───────────┴───────────┐              │
        ▼                       ▼              │
  有 tool_calls？          无 → 回答完成 ✓ 退出 │
        │                                     │
        ▼                                     │
   执行工具（并行/串行）                        │
        ▼                                     │
   回传 tool 结果 ─────────────────────────────┘
        （同时检查轮数/上下文预算/取消信号）
```

| 终止条件 | 判断 | 优先级 |
|---------|------|:---:|
| 正常完成 | `tool_calls` 为空（或 content 有最终回答） | 1 |
| 轮数上限 | `turn >= MAX_TURNS` | 2 |
| 上下文预算 | 累计 token 超预算（07 章压缩） | 2 |
| 用户取消 | 取消信号（异步实现） | 3 |
| 致命错误 | API 连续失败超阈值 | 3 |

> ⚠️ 终止纪律：**"零工具调用 = 我完成了"是循环的唯一自然出口**——别在代码里猜"该不该停"，把决定权交给模型；但必须用轮数/预算兜底，防止模型陷入"查了又查"的循环黑洞。

## 3. 错误处理：让循环永远活着

**第一原则：工具错误永远回传，绝不抛出。** 生产实践表明：把错误作为 JSON 回传给模型，可以消除约 80% 的"Agent 卡死"事故。

```python
# 工具执行器：所有错误转成结构化结果
def safe_execute(name: str, arguments: dict) -> dict:
    try:
        return {"ok": True, "data": execute_tool(name, arguments)}
    except KeyError as e:
        return {"ok": False, "error": {"code": "UNKNOWN_TOOL", "message": f"未知工具: {e}"}}
    except TypeError as e:
        return {"ok": False, "error": {"code": "BAD_ARGS", "message": f"参数不匹配: {e}"}}
    except TimeoutError as e:
        return {"ok": False, "error": {"code": "TIMEOUT", "message": f"执行超时: {e}"}}
    except Exception as e:
        return {"ok": False, "error": {"code": "INTERNAL", "message": f"内部错误: {e}"}}
```

**错误回传的三层价值**：

| 层 | 收益 |
|----|------|
| 模型层 | 模型读到错误描述 → 能自己修正参数重试（自愈） |
| 用户层 | 最终回答能解释"查不到的原因" |
| 工程层 | 循环不崩、错误可统计（05 章审计） |

> 💡 **错误要"可解释"**：回传内容带 `code + message`（如 `{"code": "BAD_ARGS", "message": "city 字段缺失"}`），模型才能据此修正。只回传"出错"两个字的错误结果等于没回传。

## 4. 并行执行与顺序依赖

```python
import asyncio, json
from openai import AsyncOpenAI

aclient = AsyncOpenAI()

# 并行执行（02 章：parallel_tool_calls=True 时响应会有多个调用）
async def execute_all(tool_calls: list, registry: dict) -> list:
    async def one(tc):
        args = json.loads(tc.function.arguments)
        try:
            result = await registry[tc.function.name](**args)
        except Exception as exc:
            result = {"error": str(exc)}
        return {"role": "tool", "tool_call_id": tc.id, "content": json.dumps(result)}

    results = await asyncio.gather(*(one(tc) for tc in tool_calls))   # 并发执行
    return results
```

| 场景 | 执行方式 | 原因 |
|------|---------|------|
| 独立查询（天气+股价） | **并发**（gather） | 4 个调用串行 8s → 并发 2s |
| 顺序依赖（A→B） | 串行 + `parallel_tool_calls=False` | 协议层就阻止并行 |
| 共享状态的工具 | 串行 | 竞态风险 |
| 危险操作 | 永不并行 + 确认模式 | 05 章 |

> 🎯 **核心要点**：**并发执行只提速、不改语义**——工具间无依赖时用 `asyncio.gather` 并发（吞吐翻几倍）；有依赖时必须在**请求层**就关掉并行（`parallel_tool_calls=False`），靠"模型自觉按顺序"不可靠。

## 5. 超时与重试

```python
import asyncio

# 工具级超时：慢工具不能拖死整个循环
async def with_timeout(coro, seconds: float = 10):
    try:
        async with asyncio.timeout(seconds):
            return await coro
    except TimeoutError:
        return {"error": {"code": "TIMEOUT", "message": f"工具执行超过 {seconds}s"}}

# API 级重试：429/5xx 指数退避（封顶 30s）
async def chat_with_retry(aclient, **kwargs):
    for attempt in range(4):
        try:
            return await aclient.chat.completions.create(**kwargs)
        except Exception as exc:
            if attempt == 3 or getattr(exc, "status_code", None) in (400, 401, 403):
                raise                     # 参数错误类不重试
            await asyncio.sleep(min(2 ** attempt, 30))    # 指数退避
    raise RuntimeError("API 重试耗尽")
```

| 层 | 超时/重试策略 |
|----|-------------|
| API 调用 | 指数退避重试 429/5xx（2^n 封顶 30s）；400/401/403 不重试 |
| 工具执行 | 每工具独立超时（10s 默认），超时回传 TIMEOUT 错误 |
| 整个循环 | 总时长上限（如 120s） |

> ⚠️ 重试幂等铁律：**写类工具（发邮件/扣款/下单）绝不能盲目重试**——重试 = 重复执行。幂等键（idempotency key）或"确认-执行"模式（05 章）先行，再谈重试。

| 必须观测的指标 | 说明 |
|---------------|------|
| 每轮调用次数 | 判断模型是否"一次问全"（并行利用度） |

> 💡 可观测性的产品价值：**"Agent 为什么回答怪"= 翻工具调用日志**。每轮调用都留痕（工具名+参数+结果摘要+耗时），问题定位时间从小时级降到分钟级。

## 7. 循环的边界：多少轮合适

| 任务类型 | 典型轮数 | 上限建议 |
|---------|:---:|:---:|
| 单查询（查天气） | 1-2 | 4 |
| 多步推理（查+算+查） | 2-5 | 8 |
| 复杂任务（Plan-and-Execute） | 5-10 | 12 |
| 自主长任务（写代码类） | 10-30+ | 20-30（配合子任务拆分） |

> 💡 轮数不是越大越好：每轮都是"全量上下文 × 模型调用"的成本；**轮数上限 8-12 是生产经验甜区**——超过就触发"任务拆分"（子 Agent/子任务）而不是盲目加轮数。另外每轮的工具定义都在重发（缓存可摊薄，09 章）。

## 8. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 循环五步：追加 assistant → 判空退出 → 执行 → 回传 → 下一轮 |
| 2 | 终止：模型零调用 = 自然出口；轮数/预算/取消是保命兜底 |
| 3 | 工具错误回传不回抛——消除 80% 卡死；错误带 code+message 可解释 |
| 4 | 无依赖工具并发执行；有依赖在请求层关并行 |
| 5 | 三层超时重试：API 退避重试 / 工具独立超时 / 循环总时长 |
| 6 | 写操作重试前先解决幂等 |
| 7 | 每轮全量留痕（工具名/参数/耗时/成本）是可观测底线 |
| 8 | 轮数上限 8-12 是甜区，超限走任务拆分 |
