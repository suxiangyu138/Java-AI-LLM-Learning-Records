## 传统调试的困境

开发者在排查 **Redis** 连接超时等错误时，常常在 StackOverflow 翻阅十余页仍找不到有效方案。根本原因在于：

- **搜索结果泛化**：通用方案无法匹配具体环境配置
- **答案碎片化**：缺少系统性的诊断链路
- **版本差异**：过时方案因版本变更而失效

> **重点**：解决问题的效率取决于提问的质量，而非搜索的时长。AI 工具已能大幅提升排查效率，但前提是掌握正确的提问方法。

## AI 诊断四步法

### 精准提问：提供完整上下文

向 AI 描述错误时，必须包含三类信息：**错误栈（Error Stack Trace）**、**环境版本**、**配置文件**。缺少任何一项，AI 只能给出泛化回答。

以下是一个标准的提问模板：

```java
我遇到以下错误，请帮我诊断：

【错误栈】
java.net.SocketTimeoutException: connect timed out
    at redis.clients.jedis.Connection.connect(Connection.java:184)
    at redis.clients.jedis.BinaryJedis.connect(BinaryJedis.java:1600)
    ...

【环境信息】
- Spring Boot 版本：2.7.14
- Jedis 版本：4.3.1
- Redis 版本：7.0.5（Docker 部署）
- 配置文件：
  spring.redis.host=192.168.1.100
  spring.redis.port=6379
  spring.redis.timeout=2000ms
  spring.redis.jedis.pool.max-active=8
```

> **重点**：错误栈 + 版本号 + 配置 = AI 精准定位的前提。完整上下文能让 AI 从"猜测"升级为"推理"。

### 穷举可能原因

要求 AI 按概率从高到低列出多种可能原因，每种原因附带根因解释、验证命令和解决方案：

```text
请列出导致此错误的 5 种可能原因（按概率从高到低），
每种原因给出：
- 根因解释
- 验证方法（具体命令）
- 解决方案
```

### 逐步验证

AI 给出候选原因后，按以下流程逐一排除：

1. 从概率最高的原因开始验证
2. 执行 AI 提供的验证命令
3. 排除当前原因后进入下一候选
4. 将验证过程中发现的新信息反馈给 AI，动态修正诊断方向

> **注意**：切忌跳过验证步骤直接照做。每个环境存在差异，AI 提供的方案需要通过实际验证确认其有效性。

### 交叉验证：多 AI 互审

利用多个 AI 工具（如 **ChatGPT**、**Claude**）进行交叉审查，可以弥补单一模型的盲区：

```text
第 1 轮：
ChatGPT："问题应该是 Redis 绑定了 127.0.0.1 而非 0.0.0.0"

第 2 轮：
用户："ChatGPT 的上述诊断有什么遗漏？请审查"
Claude："还可能是 Docker 端口映射未配置、防火墙规则阻拦、或 Jedis 连接池耗尽"

第 3 轮：
用户："Claude 提出了 3 个补充原因，请逐一验证方法"
```

通过多轮交叉验证，可将初始诊断覆盖范围扩大 2-3 倍。

## 进阶技巧

### 追问"这是最优解吗？"

AI 倾向于给出"够用"而非"最优"的答案。追问机制可以迫使 AI 重新评估方案质量：

```text
我："这个问题用 Redis Lua 脚本解决对吗？"
AI："对，这样可以保证原子性。"

我："你确定这是最优解吗？"
AI（被追问后）："实际上，如果 Redis 版本 >= 2.6，可以用
SET key value NX EX seconds 一条命令替代，不需要 Lua 脚本。"
```

> **重点**：追问"这是最优解吗？"能触发 AI 的深度搜索机制，从"第一方案"切换到"最优方案"。

### 要求代码级别的修复

提问时避免笼统的"怎么修复"，而是要求具体的代码变更：

```text
不推荐："怎么修复这个 Bug？"
推荐："给出完整的修复代码 diff，包括改动前后的对比"
```

### 要求解释"为什么这样修"

获取修复方案后，要求 AI 用因果链解释修复逻辑：

```text
"请用因果链解释：这个修复为什么能解决问题？
从根因 -> 异常链路 -> 修复点，逐一说明。"
```

这能帮助开发者建立对问题的深层理解，避免"复制粘贴后碰巧修好"的盲修现象。

## 反模式与最佳实践

### 反模式（应避免的行为）

```text
1. 贴一半错误栈，缺少关键异常类型
2. 不提供版本号和环境信息
3. AI 给方案后不验证直接上线
4. 只用 1 个 AI 工具
5. AI 说"应该是 X 原因"就停止追问
```

### 最佳实践（应遵循的标准）

```text
1. 提供完整错误栈 + 环境信息 + 已尝试的方法
2. 要求列出多种可能原因
3. 逐个验证并反馈结果
4. 至少 2 个 AI 交叉审查方案
5. 追问 3 层直到触及根因
```

## 核心要点回顾

- 精准提问是高效调试的前提：始终提供错误栈、版本号和配置文件三要素
- AI 诊断四步法：精准提问 -> 穷举原因 -> 逐步验证 -> 交叉审校
- 追问"这是最优解吗？"能够触发 AI 的深度搜索，获得更优方案
- 要求代码级别的修复 diff 而非笼统的修复思路
- 用因果链要求 AI 解释修复原理，建立深层理解
- 多 AI 交叉验证可以覆盖单一模型的盲区，提升诊断准确率
- 至少追问三层以触及根因，避免停留在表面原因
