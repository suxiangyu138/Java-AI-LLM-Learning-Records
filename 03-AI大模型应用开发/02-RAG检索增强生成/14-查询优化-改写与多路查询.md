## 1. 为什么查询需要优化

**检索失败的第一大原因不是索引差，而是"查询与文档的表述不对齐"**：

```text
用户查询：    "少年在瓜田里刺猹"（描述性，来自鲁迅《故乡》）
文档内容：    "闰土手捏一柄钢叉，向一匹猹尽力地刺去"
向量相似度：  语义相近但字面差异大 → 可能召回不到

用户查询：    "报销流程是什么"
文档内容：    "费用申请、审批、打款"（术语不同）
BM25：       词完全对不上 → 召回差

查询改写的作用：把"用户的话"翻译成"文档的语言"
```

**查询优化的成本-收益比**（为什么优先做）：

```text
① 零索引成本（不动文档库）
② 每次查询的 LLM 开销小（改写 50-100 token）
③ 收益显著：Multi-Query 对召回提升 10-20%（社区基准量级）
④ 与重排/混合检索正交叠加（各自解决不同问题）
```

> 🎯 **核心要点**：查询优化解决"**问得不对**"——在"查"之前把问题改好，比在"查"之后调索引更便宜。生产 RAG 的优化顺序：**查询改写 → 混合检索 → 重排**（按性价比）。

## 2. 查询改写三流派：HyDE / Step-back / Decomposition

**三流派（2026 标准划分）**：

| 流派 | 做法 | 解决 | 代价 |
|------|------|------|------|
| **HyDE** | 让 LLM 生成"假设答案"，用假设答案检索 | 查询-文档表述不对齐 | 多一次 LLM 调用；答案跑偏则检索失败 |
| **Step-back** | 改写为更泛化的问题再检索 | 具体问题召回差（抽象层次不匹配） | 泛化可能丢细节（与原始查询结合用） |
| **Decomposition** | 多部分问题拆成子查询分别检索 | 复合问题（"A 和 B 的关系"） | 需子结果融合逻辑 |

```python
# HyDE 的实现（LangChain 风格伪代码）
def hyde_search(question: str) -> list[Document]:
    # ① 先生成假设答案（LLM）
    hypothetical = llm(f"写一段回答以下问题的文本：{question}")
    # ② 用假设答案检索（文档-查询语义对齐）
    return vectorstore.similarity_search(hypothetical, k=10)
    # 原理：假设答案的语言更接近文档语言 → 检索命中率提升
```

```python
# Decomposition 的实现
def decompose_search(question: str) -> list[Document]:
    sub_queries = llm(f"把问题拆成 2-3 个独立子问题：{question}")
    results = [vectorstore.search(q) for q in sub_queries]
    return merge_dedupe(results)      # 子结果去重融合
```

**选型建议**：

```text
查询-文档语言差异大（口语 vs 书面）→ HyDE
问题太具体/术语杂（"咱家报销咋弄"）→ Step-back（先泛化再回查）
复合问题（"对比 A 和 B 的差异"）→ Decomposition
生产组合：HyDE + Multi-Query 是最常见搭配
```

> 🎯 **核心要点**：三流派解决三类"问得不对"——**表述不对齐（HyDE）、层次不对齐（Step-back）、粒度不对齐（Decomposition）**。面试答"查询改写有哪些"时按"三不对齐"框架展开 = 结构化满分。

## 3. Multi-Query 与 RAG-Fusion

**Multi-Query**：一个问题从多个角度生成多条查询，并行检索后融合——**换角度而不是换表述**：

```python
def multi_query(question: str) -> list[Document]:
    # ① 生成多个角度的查询（LLM）
    queries = llm(f"""
        为以下问题生成 3 条不同角度的检索查询（关键词/表述/视角都不同）：
        {question}
    """)
    # ② 每条查询独立检索
    all_results = [vectorstore.search(q, k=5) for q in queries]
    # ③ RRF 融合去重
    return rrf_fuse(all_results, k=60)
```

**RAG-Fusion**：Multi-Query + RRF 的完整管线（2023 年提出后成为标配）：

```text
问题 → 4 条角度查询 → 4 路检索（各 Top-10）
→ RRF 融合（倒数排名相加）
→ 取融合后 Top-10 → 重排 → 生成

RRF 得分 = Σ 1/(k + rank_i)，k 通常 60
优势：不需要分数归一化（各路检索分数不可比）
```

**Multi-Query 的收益与代价**：

| 维度 | 说明 |
|------|------|
| 收益 | 召回率提升 10-20%（多角度覆盖） |
| 代价 | 检索调用 ×N（延迟与成本） |
| 权衡 | 2-4 路常见；延迟敏感场景用 2 路 |
| 注意 | 融合后**必须重排**（多路噪声更大） |

> 🎯 **核心要点**：Multi-Query 是"**用并行换召回**"——多角度查询 × RRF 融合是 Advanced RAG 的标准配置；与 HyDE 可叠加（HyDE 生成假设答案也可作为一路查询）。

## 4. 查询路由 Router

**查询路由**：先判断"这个问题该走哪条检索路径"，再路由——**Advanced RAG 到 Agentic RAG 的桥梁**：

```python
def route(question: str) -> str:
    # ① LLM 判断问题类型（或分类器/规则）
    decision = llm(f"""
        判断问题类型，返回其中一个：
        - vector：单点事实查询（适合向量检索）
        - graph：全局总结/关系查询（适合图谱）
        - sql：结构化数据查询（适合数据库）
        - web：需要实时信息（适合网络搜索）
        问题：{question}
    """)
    return decision

# ② 按路由结果走不同检索路径
match route(question):
    case "vector": return vector_rag(question)
    case "graph":  return graph_rag(question)
    case "sql":    return sql_rag(question)
    case "web":    return web_search(question)
```

**路由的实现方式对比**：

| 方式 | 优点 | 缺点 |
|------|------|------|
| 规则/关键词 | 零成本、可解释 | 覆盖有限 |
| 分类模型（小模型） | 快、便宜 | 需训练/标注 |
| **LLM 路由** | 灵活、零训练 | 有延迟与成本；需约束输出格式 |

**路由的价值**：**让每种问题只走最合适的路径**——单点事实不用 GraphRAG（贵）、全局问题不用向量 RAG（查不到）——这是 2026 "问题-策略映射"的落地形态（见 01 模块第 5 节）。

> 🎯 **核心要点**：Router = "**问题分类器 + 检索策略分发器**"——从"一套流水线处理所有问题"进化为"按问题类型动态选路"。它是 Modular/Agentic RAG 的架构基石。

## 5. 查询优化与评估闭环

**查询优化的正确姿势：效果必须可度量**（否则就是玄学调参）：

```text
① 建立黄金集：50-200 条"问题 → 正确文档"对（见 08 模块）
② 基线：原查询的 Hit Rate@K / MRR
③ 实验：逐一叠加查询改写方案（HyDE / Multi-Query / Step-back）
④ 对比：指标提升多少？代价（延迟/成本）多少？
⑤ 决策：收益/代价比决定保留与否
```

**常见陷阱**：

| 陷阱 | 说明 |
|------|------|
| HyDE 幻觉污染 | 假设答案跑偏 → 检索更差——评估时单独验证 HyDE 的升降 |
| 改写过度 | 改写把问题改"歪"（信息丢失）——保留原始查询做一路 |
| 多路噪声放大 | Multi-Query 融合后噪声更大——**必须接重排** |
| 只测 Hit Rate | 命中率升了但回答质量没升（检索-生成鸿沟，见 04 模块）——端到端也要测 |

> 🎯 **核心要点**：查询优化的验收 = "**黄金集上的 Hit Rate/MRR 提升，且端到端回答质量同步提升**"——只升检索指标不升回答质量 = 优化了错误的目标（"检索-生成鸿沟"是 2026 年评估研究的核心发现，见 16/20 模块）。

**查询优化落地清单**（生产检查表）：

```text
□ 查询改写：HyDE 或 Step-back 至少一种（黄金集验证后保留）
□ Multi-Query：角度数 2-4（延迟敏感 2 路）；融合后必接重排
□ 路由：按问题类型分发（vector/graph/sql/web）
□ 缓存：查询改写结果缓存（同问题不重复改写）
□ 兜底：改写失败/超时 → 原查询直接检索（降级路径）
□ 评估：每次改动跑黄金集（Hit Rate + 端到端），防"改歪"
```
