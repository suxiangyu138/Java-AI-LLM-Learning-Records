## 1. 切片的核心矛盾

```text
Chunk Size 太大（>2000 tokens）：
  ✅ 上下文完整 → 语义丰富
  ❌ 向量"稀释" → 检索不准
  ❌ LLM 上下文被大量无关信息占据

Chunk Size 太小（<100 tokens）：
  ✅ 信息密度高 → 检索精准
  ❌ 语义断裂 → "这个"、"它"无法解析
  ❌ 块数暴增 → 存储 + 检索成本高

黄金区间：300-800 tokens（中英文混合约 500-1500 字）
```

## 2. 递归切片（生产首选）

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    separators=["\n\n", "\n", "。", "！", "？", ".", "!", "?", " ", ""],
    chunk_size=500,        # 每块最大字符数
    chunk_overlap=50,      # 重叠字符数（10%）
    length_function=len,
)

chunks = splitter.split_text(long_document)

# 递归优先级：先按段落切 → 按句子切 → 按字符切
# → 尽量在自然边界断开，保证语义完整性
```

### Chunk Size 选择指南

| 场景 | Chunk Size | Overlap | 原因 |
|------|:---:|:---:|------|
| FAQ 问答对 | 100-200 | 0 | 每条 FAQ 天然独立 |
| 技术文档 | 500-800 | 10% | 需要完整段落 |
| 法律/合同 | 800-1500 | 15% | 条款间的引用关系 |
| 代码 | 整个函数 | — | 不切片，保留完整函数 |

## 3. 语义切片

```text
语义切片 = 根据语义相似度自动找切分点

  对相邻句子计算 Embedding 相似度
  相似度骤降 → 语义转折 → 在此切分

优势：语义完整性最好
劣势：计算成本高（需对每个句子做 Embedding）
适用：高精度 RAG 系统
```

## 4. 特殊文档的切片策略

| 文档类型 | 策略 | 注意 |
|----------|------|------|
| **API 文档** | 每个 API 一个块 | 保留参数/返回值/示例 |
| **对话记录** | 按对话轮次 | 保留 user/assistant 角色 |
| **代码** | 按函数/类边界 | 不切片，完整保留 |
| **表格** | 保留表格结构或转 Markdown | 不要破坏表格 |
| **FAQ** | 每个 QA 对一块 | 问题+答案在一起 |

## 5. 多粒度索引

```text
多粒度索引 = 同一文档用多种粒度索引

  小粒度（句子级）：精准匹配
  大粒度（段落级）：完整上下文

检索策略：
  ① 先用小粒度检索 → 找到最相关的句子
  ② 找到该句子所属的大粒度块 → 作为上下文给 LLM

  → 兼具精准匹配 + 完整上下文的优势

LlamaIndex 的 SentenceWindowNodeParser 就是这种思路
```

---

## 核心要点回顾

- Chunk Size 500-800 + Overlap 10% = 最佳默认配置
- 递归切片优先：段落 → 句子 → 字符
- 代码不切片，FAQ 短切片，法律合同长切片
- 多粒度索引 = 小粒度检索 + 大粒度上下文 → 精度天花板最高
