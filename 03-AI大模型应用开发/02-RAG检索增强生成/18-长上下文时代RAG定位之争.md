## 1. 长上下文革命：1M+ token 意味着什么

**2025-2026 上下文窗口的飞跃**：

```text
2024 年主流：128K token（约一本 300 页书）
2025-2026 年旗舰：1M+ token（GPT-5.4 / Claude Opus 4.6 等，约 8 倍提升）
Gemini 系列：1M-2M；Llama 4 Scout：10M 实验窗口

意味着：整本文档（甚至整个项目代码库）可以一次塞进上下文
→ "还要 RAG 干嘛？直接全喂进去" —— 2026 年最响亮的论调
```

**"RAG 已死"论调的论证链**：

```text
① 上下文够大：1M token ≈ 全部相关知识库
② 直接输入：无需切块/索引/检索（架构大幅简化）
③ 无信息损失：RAG 可能漏掉关键块，全量输入不漏
→ 结论（表面）：长上下文取代 RAG

但——两个实验事实推翻了这个结论（下两节）
```

> 🎯 **核心要点**：长上下文是真实的革命（上下文 8 倍、整文档输入成为常态），但它**没有消灭检索需求，而是改变了检索的形态**——"更大的草堆"不等于"更容易找到针"。

## 2. 反驳论据一：Lost in the Middle

**Lost in the Middle（Liu et al., 2023）**——长上下文的"注意力盲区"：

```text
实验事实：检索增强问答中，相关文档位于上下文【中间】时，
  模型准确率从 ~75%（位置靠前）下降到 ~50%（位置居中）

原因：Transformer 对上下文中间位置的注意力偏弱
  → 开头（模型偏好）与结尾（最近信息）更受关注

关键推论：窗口再大，也不能保证"相关的针"正好在好位置
  → 全量输入 1M token = 把针埋在 100 万 token 的草堆中间
  → 模型极可能忽略真正相关的段落（幻觉/错误回答）
```

**对 RAG 的意义**：**RAG 的"检索"本质上是在做"把针从草堆里拿出来、放到开头"**——即使长上下文可用，**"提前定位相关段落"仍然是必要步骤**（这正是重排的价值：把最相关的块排到第 1 位，见 15 模块）。

> 🎯 **核心要点**：Lost in the Middle 是"长上下文消灭 RAG"论调的最硬反驳——**"能装下" ≠ "能注意到"**。检索与重排的本质是"注意力工程"：让模型的目光必然落在正确的针上。

## 3. 反驳论据二：Context Rot

**Context Rot（上下文腐烂）**：长上下文推理质量的持续衰减——2025-2026 年的系统性发现：

```text
现象：上下文越长，推理能力下降越明显
  即使在 1M-10M token 窗口的模型（Gemini / Claude / Llama 4 Scout）上
  文档化记录：窗口的理论上限远超"可用上限"

机制（部分解释）：
  ① 注意力稀释：token 越多，每个 token 的平均注意力越低
  ② 位置偏差累积：长序列中中间位置的弱化被放大
  ③ 指令跟随衰减：长上下文中模型对系统指令的遵循度下降

工程含义：长上下文的"可用长度"远小于"宣称长度"
  → "全量输入"在真实长文档场景会踩 Context Rot
```

**"声明窗口 vs 可用窗口"的差距**（面试谈资）：

```text
宣称 1M token 的模型，可用质量窗口可能只有 100K-200K
（量级因模型而异，但"声明 > 可用"是普遍现象）
→ 评估自己的场景时，用真实任务测"哪个长度开始掉质量"
→ 别信宣传数字，信实测曲线
```

> 🎯 **核心要点**：Context Rot 说明"**越长越差**"是长上下文的固有倾向——**全量输入的收益有上限，检索的必要性不因窗口扩大而消失**。这是 2026 年 RAG 研究/工程共识的核心依据之一。

## 4. 成本视角：长上下文不便宜

**Token 成本的算术**（长上下文方案最容易被忽略的账）：

```text
成本 = 输入 token × 单价
长上下文方案：1M token 输入（每次请求都付）
RAG 方案：    5-10 块 × 平均 300 token = 2-3K token 输入

以常见 API 定价量级估算（仅输入成本）：
  长上下文（100K token 输入）：每次请求 ~百倍于 RAG 的输入成本
  RAG（3K token 输入）：每次请求输入成本低 1-2 个数量级

结论：长上下文"全量输入"在频繁查询场景下成本爆炸
  提示缓存（见第 6 节）能缓解，但不能消除
```

**延迟视角**：

```text
生成前处理时间随输入长度增长：
  1M token 输入 → 首 token 延迟显著高于 3K token 输入
  （预填充阶段的计算量 = 输入长度 × 模型规模）
→ 交互式场景（聊天/搜索）长上下文方案延迟更差
```

> 🎯 **核心要点**：成本与延迟是"全量输入"的硬约束——**"上下文能装下"和"付得起、等得起"是两回事**。RAG 的"少喂精喂"在成本维度依然碾压全量输入（提示缓存缩小了差距，见第 6 节）。

## 5. 混合决策框架：何时用 RAG / 长上下文 / 混合

**2026 年共识：不是二选一，是混合决策框架**（Glasp/业界 2026 框架）：

| 场景 | 方案 | 理由 |
|------|------|------|
| 单文档深读（合同/论文，<100K-1M token） | **纯长上下文** | 无需检索，直接输入 |
| 单点事实查询（FAQ/知识库查词条） | **Top-K RAG** | 便宜、快、可溯源 |
| 需要新鲜数据/权限控制/引用溯源 | **RAG** | 长上下文做不到（数据是静态快照） |
| 多文档综合/深度跨文档推理 | **混合：检索 50K-200K 再推理** | 兼顾相关性与全局性 |
| 频繁交互查询 | RAG | 成本与延迟不可接受 |

**"为什么生产环境几乎总落在混合"**（面试必答）：

```text
真实工作负载至少有一个约束会打破"纯长上下文"：
  ① 多租户/权限：不能把 A 租户数据喂给 B 租户 → 必须检索隔离
  ② 数据新鲜度：知识库在更新 → 长上下文是静态快照 → 必须实时检索
  ③ 成本：高频查询全量输入 = 成本失控
  ④ 溯源：长上下文无法给出"哪份文档支持了这个回答"
同时也有一个约束打破"纯 Top-K RAG"：
  ⑤ 跨文档深度推理需要大窗口
→ 结论：绝大多数生产系统 = 混合（检索 + 适度长上下文）
```

> 🎯 **核心要点**：混合决策框架 = "**单文档深读用长上下文、单点查询用 RAG、多文档综合用混合**"——**RAG 管"找到对的"、长上下文管"读得深"**，两者是互补不是替代。能讲清"为什么生产几乎总是混合"（五条约束）是 2026 年架构题的高分答案。

## 6. 提示缓存与 RAG 的成本再平衡

**提示缓存（Prompt Caching）**：相同前缀的输入 token 缓存复用（2024-2026 各大 API 支持）——对"长上下文方案"的成本是重大利好：

```text
机制：输入前 N 千 token（前缀）命中缓存 → 只付缓存读价（约为全价的 1/10）
长上下文 + 缓存：
  静态知识文档放前缀 → 多轮对话共享缓存 → 成本大幅下降
  → 部分缓解了"长上下文贵"的问题
缓存失效条件：前缀任何变化（文档更新）→ 缓存失效重算
```

**2026 年成本再平衡后的判断**：

| 方案 | 缓存后成本 | 结论 |
|------|:----------:|------|
| 长上下文（静态文档 + 缓存） | 中（共享前缀摊薄） | 静态单文档场景可行 |
| RAG（动态检索） | 低（每请求 2-3K token） | 高频/动态数据仍占优 |
| 混合 | 中低 | **多数生产负载的最终选择** |

**缓存时代的 RAG 新策略**：

```text
① 知识库变更不频繁时：大块缓存（文档整体进前缀）+ 变更时重算
② 混合：稳定文档走缓存（长上下文）、变动数据走检索（RAG）
③ 评估：按"缓存命中率"建模真实成本（别按全价算长上下文）
```

> 🎯 **核心要点**：提示缓存让"长上下文 vs RAG"的账重新算——**静态知识用缓存摊薄、动态数据用检索**，2026 年的成本最优解同样是混合。**决策依据永远是"你的负载特征"（静态比/动态比/查询频率），不是框架口号**。

**长上下文时代的 RAG 改造清单**（窗口变大后的策略调整）：

```text
① 切分粒度放宽：大窗口允许更大的块（1000-2000 token），减少切分信息损失
   （窗口 128K → 1M 后，"小块保精度"的约束松动）
② 块级上下文增强：Contextual Retrieval 的上下文描述可以更长（语境更完整）
③ 检索量上调：长上下文让"召回 20 条全喂"成为可能（质量换成本）
   —— 但注意 Lost in the Middle：喂得多 ≠ 用得好，重排依然必要
④ 新增"直输"通道：单文档查询直接全文输入（跳过检索，18 模块决策表）
⑤ 评估适配：用真实"可用窗口"测（别信宣传数字——Context Rot）

判断口诀：窗口变大 → 检索的上限放松（可以少检/大块），但"定位相关段落"
的必要性不变（Lost in the Middle 与成本）——"少检但精"优于"全喂但乱"
```
