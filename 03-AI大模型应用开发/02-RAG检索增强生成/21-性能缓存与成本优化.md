## 1. 延迟拆解：RAG 的每一毫秒去哪了

**RAG 请求的延迟构成**（生产链路逐段拆解）：

```text
总延迟 = 查询处理 + 检索 + 重排 + 上下文组装 + LLM 生成

典型量级（参考）：
  ① 查询改写（HyDE/多查询）：+50-200ms（LLM 调用）
  ② 混合检索：50-200ms（向量 + BM25 并行）
  ③ Cross-Encoder 重排（Top-20）：+50-150ms
  ④ 上下文压缩：+30-100ms（可选）
  ⑤ LLM 生成：首 token 500ms-2s+（大头！）
  → 生成阶段通常占总延迟的 60-80%
```

**优化优先级（按收益）**：

```text
① 生成侧（大头）：
   - 流式输出（首 token 先行，感知延迟大幅下降）
   - 上下文瘦身（重排 Top-5 + 压缩 → 输入 token 少 → 首 token 快）
   - 模型选择（小模型/蒸馏模型做简单查询）
② 检索侧：
   - 混合检索并行（BM25 与向量同时跑）
   - 向量库性能（索引 ef 调优，见 Milvus 系统）
③ 查询侧：
   - 重排数量权衡（Top-20 → Top-10：延迟减半，精度略降）
   - 查询改写缓存（同问题不重复改写）
```

> 🎯 **核心要点**：延迟优化的铁律 = "**先打大头（生成），再抠小头（检索）**"——**流式输出是感知延迟的第一优化**（首 token 快 = 用户觉得快）；上下文越精，生成越快且越便宜（双赢）。

## 2. 语义缓存：缓存分层与命中率

**语义缓存（Semantic Caching）**：相似问题直接返回缓存答案——RAG 的"查重利器"：

```text
问题：相似问题反复触发完整 RAG 链路（检索 + 重排 + 生成 = 贵且慢）
方案：语义缓存
  新问题 → Embedding → 与缓存问题比较相似度
  → 相似度 > 阈值（如 0.95）→ 直接返回缓存答案（毫秒级）
  → 否则 → 完整 RAG → 答案入缓存

与精确缓存（Map<问题, 答案>）的区别：
  精确缓存：问题完全一样才命中（命中率低）
  语义缓存：问题"语义相近"即命中（命中率大幅提升）
```

**缓存分层设计**（生产实践）：

| 层 | 缓存内容 | 存储 | 命中场景 |
|----|---------|------|---------|
| L1 精确缓存 | 完全相同问题 | Redis（毫秒级） | 高频重复查询 |
| L2 语义缓存 | 语义相近问题 | Redis + Embedding 索引 | 相似问法 |
| L3 组件缓存 | 查询改写结果/检索结果 | Redis（短 TTL） | 复用改写/检索 |

**缓存的关键参数**：

```text
语义阈值：0.90-0.95（太低 → 错误命中给错答案；太高 → 命中率低）
TTL：动态内容短（分钟级）、静态知识长（小时-天级）
失效：知识库更新 → 相关缓存失效（按文档/块级联失效）
评估：缓存命中率 + 误命中率（错误命中是缓存头号风险）
```

> 🎯 **核心要点**：语义缓存 = "**RAG 的 CDN**"——相似问题秒回，命中率是核心指标（30-50% 命中 = 成本与延迟砍半）。**误命中比不命中更危险**（给了错误答案），阈值宁高勿低。

## 3. 路由分流：预检索决策

**路由 = 成本与延迟的第一道闸门**（在检索之前就分流）：

```text
无路由：所有请求走完整 RAG（贵）
有路由：
  简单问题（问候/闲聊/无需知识）→ 直接 LLM 回答（省检索+生成）
  常见问题（高命中缓存）→ 缓存秒回
  标准知识查询 → 标准 RAG
  复杂/多跳 → Agentic（贵，但值得）
  → 平均成本与延迟大幅下降
```

**路由的实现与收益**：

| 路由维度 | 判断依据 | 收益 |
|---------|---------|------|
| 是否需要检索 | LLM/分类器判断（问题含知识需求吗） | 省 20-40% 检索调用 |
| 缓存命中 | 语义相似度 | 秒回（见第 2 节） |
| 检索策略 | 问题类型 → 向量/图谱/Agentic | 每类问题走最优路径 |
| 模型选择 | 难度 → 大模型/小模型 | 简单问题用小模型（省 80%+ 生成成本） |

```python
# 分层路由伪代码
def serve(question):
    if semantic_cache_hit(question):          # ① 缓存
        return cached_answer
    route = router(question)                  # ② 路由（LLM 或分类器）
    if route == "no_kb":                      # ③ 无需知识
        return small_llm(question)            #   小模型直接答
    if route == "simple":
        return rag_pipeline(question, small_model=True)
    return rag_pipeline(question, agentic=True)   # 复杂问题走 Agentic
```

> 🎯 **核心要点**：路由分流 = "**让每个请求只付它该付的钱**"——缓存（秒回）、无需知识（小模型直答）、标准查询（标准 RAG）、复杂查询（Agentic）。**路由层是 2026 年 RAG 成本优化的第一杠杆**（见 14 模块 Router 深化）。

## 4. Token 成本模型

**RAG 的成本建模**（生产预算必算的账）：

```text
单次 RAG 请求成本 ≈ 输入 token × 单价 + 输出 token × 单价
输入 token = 系统提示 + 检索上下文（Top-5 × ~300 token ≈ 1.5-3K）
         + 查询改写/反思的 LLM 调用（50-200 token × 次数）

成本优化杠杆（按影响排序）：
① 路由（简单问题小模型/免检索）：-30-60%
② 语义缓存（重复查询秒回）：-30-50%（命中时）
③ 上下文精简（Top-5 + 压缩 + 只喂必要字段）：-40-60% 输入 token
④ 查询改写次数限制（max 1 次改写，别反复）：防 Agentic 烧钱
⑤ 模型选择（7B/14B 小模型做简单任务）：-70-90% 生成成本
```

**成本-质量-延迟三角**（2026 决策框架）：

```text
每次优化都是三角权衡：
  提质量（更多上下文/更强模型/多跳）→ 成本↑ 延迟↑
  降成本（缓存/路由/小模型）→ 质量可能↓（要评估兜底）
决策流程：
  ① 定质量底线（黄金集指标，见 20 模块）
  ② 定延迟预算（P95 目标）
  ③ 在约束内最小化成本（缓存 → 路由 → 精简 → 模型降级）
```

**成本监控**：

```text
必看指标：
  每次请求的 token 数（输入/输出）、缓存命中率、路由分布
  每千次请求成本（RAG 的"单位成本"——优化效果的度量）
  → 监控系统记录（LangSmith 等可观测平台天然支持）
```

> 🎯 **核心要点**：RAG 成本优化 = "**缓存（重复的别重做）+ 路由（简单的别贵做）+ 精简（无关的别喂）+ 分级（小模型能干的别用大模型）**"四板斧——**先定质量底线与延迟预算，再在约束内砍成本**（砍到质量崩了 = 假省钱）。

## 5. "检索失败率 <5%"：工程目标

**2026 年 RAG 工程的量化目标**——把"感觉还行"变成"可考核"：

```text
检索失败率（Retrieval Failure Rate）定义：
  检索结果中"不含回答所需信息"的请求占比
  （通过黄金集/在线评估的 Context Recall 计算）

2026 工程目标：检索失败率 < 5%
  从"偶尔答错"到"可接受"的行业基准线
  意味着：95%+ 的查询能检索到足够信息 → 生成质量的上限有了保障
```

**达到 <5% 的优化路径**（综合本体系各模块）：

```text
① 基础层：混合检索 + 重排（入场券，见 15）
② 查询层：改写（HyDE/多查询，见 14）
③ 索引层：Contextual Retrieval（块质量，见 13）
④ 结构层：GraphRAG（全局问题，见 16）/ 多模态（图表，见 19）
⑤ 兜底层：反思重查（Agentic 上限内，见 17）
→ 逐层叠加，用黄金集验证每层的失败率降幅
```

**监控方式**：

```text
离线：黄金集上测 Context Recall（发布门禁）
在线：抽样评估"检索结果相关性"（5-10% 流量）
告警：失败率趋势上升 → 检查知识库更新/查询分布变化/索引过期
```

> 🎯 **最终核心要点**：RAG 性能与成本的完整方法论 = "**延迟打大头（生成/流式）+ 缓存杀重复（语义缓存）+ 路由分流（按需付费）+ 成本建模（四板斧）+ 失败率目标（<5%）**"——**一切优化的验收标准是黄金集指标与失败率，不是感觉**（评估体系见 20 模块，形成闭环）。
