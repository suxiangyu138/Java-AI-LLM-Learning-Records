## 2. stdio 本地传输

### 2.1 工作原理

```text
stdio 传输 = 标准输入输出 + 子进程

  Client (父进程)          Server (子进程)
  ┌──────────┐             ┌──────────┐
  │          │──stdin─────►│          │
  │          │             │          │
  │          │◄─stdout─────│          │
  └──────────┘             └──────────┘

通信过程：
  ① Client 启动 Server 子进程
  ② Client 将 JSON-RPC 消息写入 Server 的 stdin
  ③ Server 处理后将 JSON-RPC 消息写入 stdout
  ④ 每个 JSON-RPC 消息以换行符 \n 分隔
  ⑤ stderr 用于 Server 自身的日志输出（不参与协议通信）
```

### 2.2 配置方式

```jsonc
// Claude Desktop 配置示例（claude_desktop_config.json）
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "/Users/username/Documents"
      ]
    },
    "weather": {
      "command": "python",
      "args": ["-m", "weather_mcp_server"],
      "env": {
        "API_KEY": "${WEATHER_API_KEY}"   // 环境变量注入
      }
    },
    "database": {
      "command": "java",
      "args": [
        "-jar",
        "database-mcp-server.jar",
        "--db-url=jdbc:postgresql://localhost:5432/mydb"
      ]
    }
  }
}
```

### 2.3 stdio 的优势与限制

```text
✅ 优势：
  • 零网络开销（本地 IPC）
  • 无需网络配置（无端口、无防火墙）
  • 安全性高（进程隔离）
  • 部署简单（一个命令启动）
  • 调试方便（可直接 attach 调试器）

❌ 限制：
  • 只能本地使用（Server 和 Client 必须在同一台机器）
  • 无法多 Client 共享（一个进程对应一个 Client）
  • 无 OAuth 支持
  • 进程崩溃 = 连接断开
  • 不支持服务发现
```

## 3. HTTP + SSE 远程传输

### 3.1 双通道架构

```text
HTTP + SSE 传输 = POST 发请求 + GET 收事件

  ┌──────────────────────────────────────────────────────┐
  │                     HTTP + SSE                        │
  ├──────────────────────────────────────────────────────┤
  │                                                       │
  │  Client                          Server               │
  │  ┌──────────┐                    ┌──────────┐        │
  │  │          │──POST /mcp───────►│          │        │
  │  │ 请求通道 │                    │  JSON-RPC│        │
  │  │          │◄──200 OK──────────│  处理器   │        │
  │  │          │                    │          │        │
  │  │          │──GET /sse────────►│          │        │
  │  │ 事件通道 │                    │  SSE     │        │
  │  │          │◄──SSE stream──────│  推送器   │        │
  │  └──────────┘                    └──────────┘        │
  │                                                       │
  │  POST 通道：Client → Server 的 JSON-RPC 请求           │
  │  GET/SSE 通道：Server → Client 的通知和流式响应        │
  └──────────────────────────────────────────────────────┘
```

### 3.2 通信流程

```text
HTTP + SSE 完整通信流程：

  ① Client 建立 SSE 连接：
     GET /sse HTTP/1.1
     Accept: text/event-stream
    
     Server 响应：
     HTTP/1.1 200 OK
     Content-Type: text/event-stream
     
     event: endpoint
     data: /mcp?sessionId=abc123   ← 获得 Session ID

  ② Client 发送 JSON-RPC 请求：
     POST /mcp?sessionId=abc123 HTTP/1.1
     Content-Type: application/json
     
     { "jsonrpc": "2.0", "id": 1, "method": "tools/list" }

  ③ Server 通过 POST 同步响应：
     HTTP/1.1 200 OK
     { "jsonrpc": "2.0", "id": 1, "result": { "tools": [...] } }

  ④ Server 通过 SSE 异步推送通知：
     event: message
     data: {"jsonrpc":"2.0","method":"notifications/tools/list_changed"}
```

### 3.3 请求-响应匹配（SSE 通道）

```text
对于长时间运行的工具调用，响应也走 SSE 通道：

  ① Client:
     POST /mcp?sessionId=abc123
     { "jsonrpc": "2.0", "id": 42, "method": "tools/call", "params": {...} }
  
  ② Server:
     HTTP/1.1 202 Accepted    ← 请求已接受，通过 SSE 异步返回
  
  ③ Server 通过 SSE 推送结果：
     event: message
     data: {"jsonrpc":"2.0","id":42,"result":{...}}
```

## 4. Streamable HTTP（2025 新标准）

### 4.1 为什么需要 Streamable HTTP

```text
旧 HTTP+SSE 的问题：

  ① 双通道复杂：需要同时维护 POST 和 GET 两条连接
  ② 部署困难：负载均衡器/API 网关对 SSE 支持不一致
  ③ 无 OAuth 标准：OAuth 需要明确的请求-响应模型
  ④ 连接状态耦合：GET/SSE 断开 → 整个 Session 失效

Streamable HTTP 的改进：

  ① 单通道：所有通信走同一个 HTTP 端点
  ② 灵活响应：同一次请求可选普通响应 or SSE流 or 混合
  ③ OAuth 原生支持：标准 HTTP Authorization 头
  ④ 无状态恢复：支持 Last-Event-ID 断点续传
```

### 4.2 Streamable HTTP 架构

```text
Streamable HTTP = 一个端点，多种响应模式

  POST /mcp HTTP/1.1
  Accept: application/json, text/event-stream
  Authorization: Bearer <token>
  Content-Type: application/json

  { "jsonrpc": "2.0", "id": 1, "method": "tools/list" }

  Server 根据 Accept 头决定响应方式：

  ┌───────────────────────────────────────────────────────┐
  │ Accept: application/json                              │
  │ → 标准 JSON 响应（同步工具）                            │
  │ HTTP/1.1 200 OK                                       │
  │ { "jsonrpc": "2.0", "id": 1, "result": {...} }        │
  ├───────────────────────────────────────────────────────┤
  │ Accept: text/event-stream                             │
  │ → SSE 流式响应（长任务 / 流式输出）                     │
  │ HTTP/1.1 200 OK                                       │
  │ Content-Type: text/event-stream                       │
  │ event: message                                        │
  │ data: {"jsonrpc":"2.0","id":1,"result":{"content":...}}│
  ╞═══════════════════════════════════════════════════════╡
  │ 混合模式：先返回 headers（202 Accepted），再 SSE 流    │
  │ HTTP/1.1 200 OK                                       │
  │ Content-Type: text/event-stream                       │
  │                                                       │
  │ # 第一个 event 是最终 JSON-RPC 响应                    │
  │ event: message                                        │
  │ data: {"jsonrpc":"2.0","id":1,"result":{"content":[]}}│
  │                                                       │
  │ # 后续 event 是进度/日志通知                           │
  │ event: message                                        │
  │ data: {"jsonrpc":"2.0","method":"notifications/progress",│
  │        "params":{"progress":50,"total":100}}           │
  └───────────────────────────────────────────────────────┘
```

### 4.3 服务发现（.well-known）

```text
Streamable HTTP 支持标准化服务发现：

  GET /.well-known/mcp HTTP/1.1
  → 返回 Server 的 MCP 端点信息

  {
    "endpoints": [
      {
        "url": "https://api.example.com/mcp",
        "transport": "streamable-http",
        "protocolVersions": ["2025-03-26", "2024-11-05"]
      }
    ],
    "authentication": {
      "type": "oauth2",
      "authorizationUrl": "https://auth.example.com/authorize",
      "tokenUrl": "https://auth.example.com/token"
    },
    "serverInfo": {
      "name": "example-mcp-server",
      "version": "2.0.0"
    }
  }
```

## 5. 传输选型决策指南

### 5.1 决策树

```text
你的 MCP Server 部署在哪里？

├── 和 Client 同一台机器
│   ├── 本地开发工具（Claude Desktop、VS Code）
│   │   → stdio ✅（最简单）
│   │
│   └── 需要多 Client 使用同一个 Server
│       → HTTP + SSE 或 Streamable HTTP
│
├── 远程服务器
│   ├── 需要 OAuth 认证
│   │   → Streamable HTTP ✅（原生支持）
│   │
│   ├── 需要穿透企业防火墙
│   │   → Streamable HTTP ✅（标准 HTTP 端口）
│   │
│   └── 简单场景，不需要 OAuth
│       → HTTP + SSE（成熟稳定）
│
└── 混合场景（本地 + 远程）
    → Streamable HTTP 作为统一传输
```

### 5.2 传输配置最佳实践

```yaml
# 推荐的 MCP Server 配置最佳实践

# 本地开发 Server
local_server:
  transport: stdio
  advantages: [零配置, 安全隔离, 调试方便]
  
# 企业内部远程 Server
internal_server:
  transport: streamable-http
  port: 8080
  auth: none                    # 内网免认证 或 API Key
  cors:
    allowed_origins: ["https://internal-tools.company.com"]
  
# 公开 SaaS Server
public_server:
  transport: streamable-http
  port: 443
  tls: true
  auth: oauth2                  # OAuth 2.0 必选
  rate_limiting:
    requests_per_minute: 60
  cors:
    allowed_origins: ["*"]      # 或具体域名
```

> 🎯 **核心要点**：本地用 stdio（最简单）、远程用 Streamable HTTP（最新、最全）、需要 OAuth 必须 Streamable HTTP。传输层只负责消息搬运，与上层 JSON-RPC 解耦
