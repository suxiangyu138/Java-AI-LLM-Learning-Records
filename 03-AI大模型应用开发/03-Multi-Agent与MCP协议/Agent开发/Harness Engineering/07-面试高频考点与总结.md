## 1. 面试高频题与答题框架

### 1.1 概念类

**Q1：什么是 Harness Engineering？它和 Prompt Engineering / Context Engineering 的关系？**

```text
答题框架：
① 定义：为主动执行任务的 Agent 搭建全流程约束、监控、校验体系的工程实践
② 演进：Prompt（2022-24，雕琢语言）→ Context（2025，管理信息）→ Harness（2026，管控行为）
③ 公式：Agent = Model + Harness——模型定能力上限，Harness 定稳定下限
④ 关系：Prompt/Context 是 Harness 的子集（指令层/上下文管理组件）
⑤ 驱动：AI 从"只会说"到"能动手"，风险从"说错话"升级为"做错事"
```

**Q2：Agent = Model + Harness 这个公式怎么理解？**

```text
① Model：推理/语言/知识能力，决定上限，只能选不能改
② Harness：代码+配置+执行规则（工具白名单/权限/观测/评估/约束），决定下限
③ 含义：裸模型 ≠ Agent；Agent 出事故先查 Harness 而非怪模型
④ 案例：强模型缺 Harness 表现不如弱模型+完整 Harness（评估"模型-Harness 对"）
```

**Q3：Harness 的三大基础属性是什么？**

```text
① 可执行性（Executable）：能验证 Agent 实际做了什么，而非声称
② 可检查性（Inspectable）：失败时产生可操作的诊断输出
③ 有状态性（Stateful）：会话状态外部化，跨会话连续
→ 三问自检：真做了吗？能诊断吗？崩了能续吗？
```

### 1.2 架构类

**Q4：请描述 Harness 的七层架构。**

```text
自底向上：
① 指令层（要干什么）→ ② 工具层（能干什么）→ ③ 状态层（走到哪）
→ ④ 观测层（查得清）→ ⑤ 评估层（判得准）→ ⑥ 约束层（守得住）→ ⑦ 反馈层（能进化）
上层四层做对事，下层三层管得住，反馈层让体系自我迭代
```

**Q5：九大工程组件有哪些？你们项目缺了哪些？**

```text
① While-loop 引擎 ② 上下文管理 ③ 工具注册表 ④ 子智能体管理 ⑤ 内置技能
⑥ 会话持久化 ⑦ 动态提示组装 ⑧ 生命周期钩子 ⑨ 权限执行
→ 加分点：大多数失败项目缺 ⑥⑧⑨（崩溃全丢/无法插审批/工具全开）
→ Claude Code 是九组件最完整的生产级参考实现
```

### 1.3 安全类

**Q6：Agent 面临哪些安全风险？「致命三要素」是什么？**

```text
七大风险：提示词注入/工具爆炸半径/凭据滥用/记忆投毒/子Agent提权/供应链/目标漂移
致命三要素：私有数据 + 不可信内容 + 外部通信 = 数据外泄路径
→ 防御：切断任一环节（内容过滤/网络隔离/最小权限）
→ 数据佐证：64% 企业发现影子 Agent；93% 权限请求未经充分审查
```

**Q7：四层隔离模型是什么？为什么结构性隔离优于人工审查？**

```text
① 镜像加固（构建时剥离工具）→ ② 进程隔离（三用户分离）
→ ③ 密钥隔离（Agent 零凭据字节）→ ④ 网络隔离（白名单代理）
核心假设：Agent 已被攻陷（瑞士奶酪模型）
人工审查局限：93% 权限请求无人细看 → 只用于高影响低频决策
```

**Q8：什么是 AIBOM？Slopsquatting/技能投毒如何防护？**

```text
AIBOM = AI 物料清单：模型/工具/技能/依赖的完整清单
→ IDC 预测 2028 年 50% 企业要求 AIBOM
供应链防护：可信来源 + 静态扫描 + 版本锁定 + SCA
→ OpenClaw 事件：12% 技能含恶意代码（CVE-2026-25253）
→ 技能/MCP/插件按软件供应链组件同等管理
```

### 1.4 治理与评估类

**Q9：「治理继承而非集成」怎么理解？**

```text
Agent 应运行在组织已有治理框架内：
身份（SSO/OAuth）+ 权限（RBAC）+ 审计（SIEM）+ 审批（审批门）+ 策略（OPA）
→ 判断标准：如果 Agent 需要单独设计权限系统，治理设计就错了
→ 流水线内治理：限制部署的策略同样限制 Agent
```

**Q10：什么是 Agent DLC？影子 Agent 如何防控？**

```text
Agent DLC：构建→测试→存储→部署→运行→治理 全生命周期
影子 Agent 防控：AI 资产目录（自动发现/登记/所有者绑定/评分卡）
→ IDC：64% 企业发现未授权智能体运行于关键流程
```

**Q11：为什么「先建评估再建 Agent」？评估如何入门禁？**

```text
① 没有靶心射箭：没有成功标准就开发 = 无法判断好坏
② 50 个代表用例定义"成功运行"，每天跑
③ AI Evals：正确性/性能/安全性评分 → CD 流水线质量门
④ 验证器独立进程：生成器与评估器分离上下文，排除自评放水
```

**Q12：Agent 测试与传统软件测试有什么不同？**

```text
① 概率性 vs 确定性：无法 assertEquals，用统计质量评估
② 不可复现：同一任务两次运行不同路径
③ 行为空间无限：用「行为轨迹 + 结果质量」双维评估
④ 五维指标：任务完成率/工具调用准确率/轨迹对齐度/延迟 P95/幻觉率
```

### 1.5 落地类

**Q13：多 Agent 系统的结构性失败模式有哪些？**

```text
① 握手循环 → 所有者 + 交接预算
② 级联错误（单一错误感染 100% Agent）→ 验证器防火墙
③ 上下文膨胀 → 子 Agent 只回传摘要
④ 共享资源冲突 → 锁/队列/事务门
⑤ 成本失控（15 倍 token）→ token 预算 + 每任务成本指标
```

**Q14：企业如何组织 Harness 工程？落地步骤？**

```text
组织：内部智能体平台团队（拥有原语）+ 产品团队（组合智能体）
步骤：有界工作流验证 → 深化（评估门禁/审批/审计）→ 规模化（DLC/资产目录/红队）
预算：Harness 平台建设占 40-50%（最大投入项）
十二实践金句：先埋点再优化、工具即产品、确定性基础+概率性上层
```

## 2. 开放题：Harness 工程会取代什么

```text
观点框架：
① 取代的不是人，是"裸模型当 Agent 用"的粗放阶段
② 取代的是：无治理的 Agent 部署（影子 Agent）、无评估的开发（看着能跑）
③ 创造的是：AI 平台工程师（Harness 工程岗）、评估工程师（Evals）、红队工程师
④ 类比：DevOps 没有取代运维，而是把运维变成平台工程
    Harness 工程正在把 AI 部署变成平台工程
⑤ 结论：2026 年的关键岗位缺口 = 能构建 Harness 的工程师
```

> 🎯 **答题金句**：模型厂商负责"造发动机"，Harness 工程师负责"装底盘、铺路、设交规"——没有后者的体系，再强的发动机也上不了路。

## 3. 五大常见误区

| # | 误区 | 真相 |
|---|------|------|
| 1 | 「Agent 不行就换更强模型」 | 失败大多出在 Harness（无状态/权限宽/不可审计），换模型是改上限不是补下限 |
| 2 | 「人工审查足够安全」 | 93% 权限请求未经细看——结构性隔离才是承重墙 |
| 3 | 「评估就是 LLM-as-Judge 打分」 | 自评放水 + 位置偏差——验证器必须独立进程 |
| 4 | 「Harness 是安全团队的事」 | 是平台工程：运行时/评估/观测/治理一体，安全只是约束层之一 |
| 5 | 「治理系统要另起炉灶」 | 治理继承：Agent 直接活在组织已有身份/权限/审计框架里 |
