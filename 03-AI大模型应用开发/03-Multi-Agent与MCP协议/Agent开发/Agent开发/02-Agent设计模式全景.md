## 1. 五大经典架构总览

| 架构 | 核心机制 | 特点 | 适用场景 |
|------|---------|------|---------|
| **ReAct** | 推理+行动交替（思考→行动→观察） | 最基础，紧密反馈循环 | 开放式工具使用、研究类、客服 |
| **Plan-Execute** | 先完整规划再执行 | 计划作为契约防漂移 | 报告生成、结构化流程 |
| **Reflexion** | 基础循环 + 自我批判层 | 评估后修正 | 代码生成、数学推理 |
| **Tree-of-Thoughts** | 推理视为搜索（多分支+剪枝） | 探索多种可能 | 战略规划、谜题、多约束优化 |
| **Multi-Agent** | 监督 Agent 路由给专业 Worker | 分工并行 | 长周期、并行、企业级 |

> 🎯 **选型铁律**：先从 ReAct 起步，数据证明精度不足再叠加 Reflexion，单个 Agent 确实处理不了才升级 Multi-Agent——**每一步复杂度提升都要有数据依据**。

## 2. ReAct：一切的基础

### 2.1 核心机制

**ReAct（Reasoning + Acting）**：推理与行动交替的循环模式——模型先「想」，再「做」，看「结果」，再「想」……

```text
ReAct 循环
┌─────────┐     ┌─────────┐     ┌─────────┐
│ 思考     │ ──→ │ 行动     │ ──→ │ 观察     │ ──┐
│ Thought │     │ Action  │     │Observation│  │
└─────────┘     └─────────┘     └─────────┘  │
      ↑                                     │
      └─────────── 循环 ────────────────────┘
```

```
示例（查询订单状态）：
Thought: 用户想知道订单状态，我需要先查询订单信息
Action: query_order(order_id="ORD-1001")
Observation: {status: "PAYING", amount: 299.0}
Thought: 订单在支付中，还需要查支付状态
Action: query_payment(order_id="ORD-1001")
Observation: {paid: false, expired_in: "30min"}
Thought: 订单未支付，告知用户剩余支付时间
Answer: 您的订单 ORD-1001 当前处于待支付状态，剩余支付时间 30 分钟
```

### 2.2 优势与缺陷

| 优势 | 缺陷 |
|------|------|
| 简单直观，90% 简单场景够用 | **无自我纠错**：推理偏差会沿错误方向持续执行 |
| 工具使用灵活 | 可能循环（重复同一失败动作） |
| 上下文开销小 | 长任务目标漂移 |

> 💡 ReAct 是**起点模式**——所有复杂模式都是它的增强。裸 ReAct 的失败（一错到底）催生了 H-V-R 与 Reflexion。

## 3. Plan-Execute：计划即契约

### 3.1 核心机制

**Plan-Execute**：先让 Agent 制定完整计划，再逐步执行——计划成为执行期间的「契约」，减少中途漂移：

```text
阶段一：规划（Plan）
├── 拆解任务为子步骤
├── 标注每步依赖的工具
└── 输出完整执行计划

阶段二：执行（Execute）
├── 按计划逐步执行
├── 每步观察结果
└── 偏差超阈值时返回规划阶段（重新计划）
```

### 3.2 适用场景

| 场景 | 为什么适合 |
|------|-----------|
| 报告生成 | 结构固定，计划先定框架 |
| 代码审查流水线 | 步骤明确、可预测 |
| 数据处理流程 | 多阶段、依赖清晰 |

> 🎯 **价值**：计划让 Agent「先想清楚再动手」——对**结构化流程**（步骤明确）比 ReAct 更稳；对**开放式探索**（路径未知）不如 ReAct 灵活。

## 4. Reflexion：自我批判层

### 4.1 核心机制

**Reflexion**：在基础循环上增加**自我批判层**——Agent 完成任务后评估自身表现，将反思结果反馈到下一轮尝试：

```text
Reflexion 循环
任务 → 尝试（ReAct 循环）→ 评估（批判）→ 反思（总结经验）
  ↑                                             │
  └──────────── 下一轮尝试（带上反思）──────────┘
```

```
示例（代码生成）：
Attempt 1: 生成代码 → 测试失败（数组越界）
Reflection: 失败原因是边界条件未处理，下一轮必须在循环前检查索引范围
Attempt 2: 生成代码 → 测试通过
```

### 4.2 与 H-V-R 的区别

| 维度 | Reflexion | H-V-R |
|------|-----------|-------|
| 反思时机 | 任务完成后（整轮反思） | **每步执行后**（即时反思） |
| 粒度 | 粗（一轮一次） | 细（一步一次） |
| 适用 | 迭代式任务（编程/写作） | 实时决策任务 |
| 开销 | 中 | 高 |

> 💡 叠加时机：只有当数据证明 ReAct 精度不足时，才叠加 Reflexion——它为每次失败支付额外 token，成本要算清楚。

## 5. Tree-of-Thoughts：推理即搜索

### 5.1 核心机制

**ToT（思维树）**：把推理视为搜索问题——每一步生成**多个候选分支**，评估后**剪枝**，保留最有希望的路径继续：

```text
ToT 搜索树
        根（初始状态）
       /    |    \
    分支A   分支B   分支C
    / \     / \     / \
   A1 A2   B1 B2   C1 C2
   │          │
  剪枝掉    保留
  (评估分低) (评估分高)
```

| 要素 | 说明 |
|------|------|
| **分支生成** | 每步生成 k 个候选方案 |
| **评估剪枝** | 评分后剪掉低分分支 |
| **回溯** | 死路时回溯到上一步 |

### 5.2 适用场景与代价

| 适用 | 代价 |
|------|------|
| 战略规划、谜题求解、多约束优化 | token 消耗指数级（k 倍分支） |

> ⚠️ 使用门槛：ToT 的成本是 ReAct 的 k 倍以上——**只有高价值、低频率、可并行评估的任务**才值得用（如代码调试、数学证明）。

## 6. Multi-Agent：专业化分工

### 6.1 核心机制

**Multi-Agent（多智能体）**：监督 Agent 将子任务路由给专业 Worker Agent——职责分离 + 协调机制：

```text
Multi-Agent 结构
┌─────────────┐
│ 监督者 Agent  │ ← 任务分解 + 路由 + 汇总
└──┬───┬───┬──┘
   │   │   │
   ▼   ▼   ▼
 Worker1  Worker2  Worker3
 专业工具  专业工具  专业工具
```

### 6.2 多 Agent 的价值（案例）

| 案例 | 单 Agent | Planner 模式 |
|------|---------|-------------|
| 代码审查 | 8 分钟 | **2.5 分钟** |
| 误判率 | 15% | **4%** |

> 🎯 **Planner 模式的核心优势：可中断、可恢复**——执行到第 4 步出错只需重做第 4 步，而单 Agent 需要从头再来。

> ⚠️ 注意：多 Agent 的 token 消耗约为单 Agent 对话的 **15 倍**——收益（并行+专业）必须大于成本，否则是负优化。

## 7. 2026 新范式：H-V-R

### 7.1 为什么替代 ReAct

> ⚠️ ReAct 的致命弱点：**缺乏自我纠错机制**——智能体一旦推理偏差，会沿错误方向持续执行（一错到底）。

### 7.2 H-V-R 三阶段

**H-V-R（Hypothesis-Verification-Reflection，假设-验证-反思）**：

```
① Hypothesize（假设）
   ├── 生成可执行的分步方案
   └── 标注每步依赖的工具

② Verify（验证）
   ├── 实际执行工具调用
   └── 计算置信度分数（Confidence Score）

③ Reflect（反思）
   ├── 置信度 < 阈值（如 0.7）时触发
   ├── 基于失败信息提出修正方案
   └── 回到假设阶段重试
```

```python
# H-V-R 循环骨架（伪代码）
def hvr_loop(task, confidence_threshold=0.7, max_retries=3):
    for attempt in range(max_retries):
        plan = hypothesize(task)              # ① 假设：生成方案
        results = [verify(step) for step in plan]  # ② 验证：执行+打分
        confidence = compute_confidence(results)
        if confidence >= confidence_threshold:
            return assemble_answer(results)   # 通过 → 输出
        feedback = reflect(results)           # ③ 反思：生成修正
        task = apply_feedback(task, feedback) # 带着反思重试
    return fallback_answer(results)           # 超限 → 降级输出
```

### 7.3 与 ReAct 的对比

| 维度 | ReAct | H-V-R |
|------|-------|-------|
| 纠错机制 | ❌ 无 | ✅ 置信度驱动的反思 |
| 决策依据 | 单步推理 | **执行验证数据** |
| 失败处理 | 一错到底 | 失败 → 反思 → 重试 |
| 可靠性 | 低 | **高** |
| 成本 | 低 | 中（验证步骤开销） |

> 🎯 **2026 定位**：H-V-R 是 ReAct 的进化——用「验证数据」代替「纯推理」，让 Agent 的每一步都有依据。需要高可靠性的生产 Agent 优先考虑。

## 8. 模式选择决策树

```text
                开始
                 │
         任务是否需要工具交互？
        ┌───────┴───────┐
       否│               │是
        ▼               ▼
   纯推理任务         需要外部工具
        │               │
        ▼               ▼
   简单问题？     执行路径可预测？
   ┌──┴──┐        ┌──┴──┐
  是│    │否    是│    │否
   ▼    ▼        ▼    ▼
 单次   ToT     Plan-   ReAct
 调用   （高价值  Execute （开放式）
        才用）    │        │
                 │     精度不足？
                 │     ┌──┴──┐
                 │   是│    │否
                 │    ▼    ▼
                 │  H-V-R/ ReAct
                 │  Reflexion
                 │        │
                 │   单Agent搞不定？
                 │    ┌──┴──┐
                 └────│ 是   │否 → 保持
                      ▼
                  Multi-Agent
```

### 8.1 选择原则总结

| 原则 | 说明 |
|------|------|
| **简单优先** | 90% 场景 ReAct 足够，不炫耀复杂度 |
| **数据驱动** | 升级复杂度前先有评估数据证明必要性 |
| **成本意识** | 每级复杂度对应 token 增长（Reflexion×2、ToT×k、Multi-Agent×15） |
| **组合使用** | 生产系统通常组合多种模式（ReAct 主体 + Reflexion 附加） |

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 五大架构：ReAct（基础）/Plan-Execute（契约）/Reflexion（批判）/ToT（搜索）/Multi-Agent（分工）
> 2. 2026 新范式 H-V-R：假设→验证→反思，用置信度驱动纠错，解决 ReAct 一错到底
> 3. 选型铁律：从 ReAct 起步，数据驱动升级，每级复杂度对应 token 成本
> 4. Multi-Agent 收益明确（审查 8min→2.5min）但成本 15 倍——收益必须大于成本
