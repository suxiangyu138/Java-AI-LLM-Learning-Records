## 1. Agent 评估的层次模型

**Agent 评估为什么不能只看端到端**：

```text
端到端指标的问题：
  任务完成率 80% —— 但不知道失败在哪层：
  → 工具选错了？参数传错了？还是生成错了？
  → 无法指导优化方向

分层评估（2026 共识）：
  ① 工具选择层：ToolSelectionAccuracy —— 选对工具了吗
  ② 函数调用层：FunctionCallAccuracy —— 参数/Schema 对吗
  ③ 任务完成层：TaskCompletion —— 端到端成了吗
  ④ 质量层：回答质量/用户满意度
```

**分层定位示例**：

| 现象 | 工具层 | 函数层 | 任务层 | 定位 |
|------|:------:|:------:|:------:|------|
| 选错工具 | ❌ | ✅ | ❌ | 工具层（描述问题） |
| 参数错 | ✅ | ❌ | ❌ | 函数层（Schema 问题） |
| 都对了但结果差 | ✅ | ✅ | ❌ | 任务层（任务设计问题） |

> 🎯 **核心要点**：评估分层 = "**工具选择 → 函数调用 → 任务完成**"三明治——**端到端指标会掩盖工具层缺陷**（2026 评估共识的核心），分层度量才能指导优化。

## 2. 核心指标：ToolSelectionAccuracy 等

**2026 推荐指标集**：

| 指标 | 定义 | 度量方式 | 优化杠杆 |
|------|------|---------|---------|
| **ToolSelectionAccuracy** | Agent 选对工具的比例 | 黄金集（问题 → 正确工具） | **工具描述质量** |
| **FunctionCallAccuracy** | 参数正确 + Schema 校验通过率 | 黄金集 + 日志 | 参数 Schema 示例 |
| **TaskCompletion** | 端到端任务成功率 | 黄金集 | 规划/流程设计 |
| 平均步数 | 完成任务的平均工具调用数 | Trace | 效率（冗余步骤） |
| Token 消耗 | 单任务成本 | Trace | 成本优化 |
| 恢复率 | 失败后成功恢复的比例 | Trace | 反思机制 |

**黄金集的构建**（Agent 版）：

```text
结构与 RAG 黄金集类似（见 02-RAG 深化 20 号）：
  问题 → 期望的工具序列（ground truth）
  问题 → 期望的参数
  问题 → 期望的最终答案
规模：50-200 条，覆盖主要工具组合与失败模式
```

> 🎯 **核心要点**：Agent 黄金集的关键 = "**标注'期望工具序列'而非只标答案**"——只有这样才能度量 ToolSelectionAccuracy（2026 区分度最高的指标）。

## 3. Trace 驱动的开发流程

**"用 Trace 替代 Demo"**（2026 生产方法论核心）：

```text
传统：开发时演示 Demo → 上线后看日志 → 出了问题才看 Trace
2026：Trace 是一等公民 —— 开发、测试、发布全流程围绕 Trace

Trace 记录的内容（每次 Agent 运行）：
  完整工具调用链（选了什么、参数、结果、耗时）
  每步推理（Thought）
  状态变化（记忆/上下文）
  成本（token/延迟）
```

**Trace 驱动的开发闭环**：

```text
① 开发：每次改动跑黄金集 → 生成 Trace
② 回归：CI 中对比 Trace 与基线
   → 工具调用序列变化了？参数变化了？→ 自动检测行为漂移
③ 发布：Trace 通过门禁（指标阈值）→ 放行
④ 上线：生产 Trace 实时可查（问题定位从"猜"变"看"）
```

**Trace 回归的价值**：

```text
传统回归：只测"答案对不对"（输出黑盒）
Trace 回归：检查"过程对不对"（工具选择/调用顺序）
  → 能捕获"答案碰对了但过程错了"的回归
  → 例：Agent 本应查数据库却调了搜索，答案碰巧对
  → Trace 回归发现工具序列变化 → 阻断
```

> 🎯 **核心要点**：Trace 驱动 = "**过程可回归**"——CI 中对比工具调用链而非只看答案，**捕获"答案对但过程错"的隐蔽回归**是 2026 评估体系的进化点。

## 4. 模拟压测与发布门禁

**发布门禁的 2026 标准做法**：

```text
① 模拟用户生成：Persona/ScenarioGenerator 生成 200-500 个虚拟用户
   → 覆盖：正常用户、边缘用户、恶意用户（注入攻击）
② Staging 压测：虚拟用户对 staging 环境跑真实 Agent
   → 模拟生产负载与查询分布
③ 指标门禁：发布前检查
   → ToolSelectionAccuracy ≥ 阈值
   → TaskCompletion ≥ 阈值
   → 平均步数 ≤ 阈值（防低效循环）
   → 注入攻击拦截率 = 100%
④ 不达标 → 阻断发布（回滚/修复）

价值：把"上线后发现问题"提前到"发布前"
```

**门禁阈值设置原则**：

```text
① 与基线对比（相对阈值）：新版本 vs 当前版本的指标差
   → 下降超 2-3% 阻断（防回归）
② 绝对底线：ToolSelectionAccuracy 低于行业实践基线（如 85-90%）告警
③ 分场景门禁：高风险场景（支付/医疗）阈值更严
```

> 🎯 **核心要点**：发布门禁 = "**模拟压测（200-500 虚拟用户）+ 分层指标阈值 + 相对基线对比**"三件套——2026 年"指标阈值作为发布门禁"是生产团队的标配动作。

## 5. 可观测性：统一追踪与 SLI

**统一追踪的架构**（2026 标准）：

```text
网关 + OpenTelemetry 实现跨客户端统一追踪：
  Client → Agent 网关 → 工具/MCP Server → 外部系统
  每个环节产生 span：
    Agent 推理（LLM 调用：模型/token/延迟）
    工具调用（工具名/参数/结果/耗时/错误）
    记忆读写（命中/写入）
  关联：trace_id 贯穿（与 RAG/API 的 traceId 同源）

工具命名规范：命名空间前缀避免跨服务器工具名冲突
  → jira.search_issues / github.create_issue（而非 search_issues）
```

**Agent SLI 清单**（2026 推荐）：

| SLI | 指标 |
|-----|------|
| 工具选择准确率 | ToolSelectionAccuracy |
| 函数调用准确率 | Schema 校验成功率 |
| 任务完成率 | TaskCompletion |
| 工具延迟 | 每个工具 P95 |
| 工具错误率 | 每工具错误数/调用数 |
| 资源新鲜度 | 知识/数据过期检测 |
| 成本 | 单任务 token/步数 |

**告警设计**：

```text
① 工具选择准确率下降 → 检查工具描述/模型升级影响
② 某工具错误率飙升 → 外部依赖故障（快速定位）
③ 平均步数上升 → 规划效率退化（反思循环过多）
④ 缓存命中率/记忆命中率 → 知识新鲜度
```

> 🎯 **核心要点**：可观测性 = "**OTel 统一追踪（trace_id 贯穿）+ 分层 SLI + 告警设计**"——**工具命名带命名空间前缀**是 2026 的细节规范（多服务器场景防冲突）。

## 6. 工具描述优化

**工具描述是 ToolSelectionAccuracy 的第一杠杆**：

```text
问题：描述写不好 → Agent 选错工具
  "search" vs "query" vs "lookup" —— 语义模糊 → 误选
  description 太泛/太简/与实现不符 → 系统性选错

2026 优化方案：描述优化器自动改进
  ProTeGi / GEPA / PromptWizard 等
  → 用失败案例反馈迭代工具描述
  → ToolSelectionAccuracy 可提升 10-25 个百分点（社区基准）
```

**工具描述优化流程**：

```text
① 收集失败案例：Trace 中"选错工具"的记录
② 分析原因：描述歧义/缺失场景/示例不足
③ 优化描述：补场景、补示例、消歧义（人工或优化器）
④ 评估：黄金集验证 ToolSelectionAccuracy 提升
⑤ 安全注意：描述变更走审批（防投毒，见 14 号）
```

**工具描述的黄金结构**：

```text
工具名：动词 + 对象（search_orders）
描述要点：
  ① 什么时候用（触发场景）
  ② 什么时候不用（排除场景，防误选）
  ③ 参数说明与示例
  ④ 返回内容概述
```

> 🎯 **核心要点**：工具描述 = "**Agent 的工具说明书，也是最大的可优化杠杆**"——**失败案例驱动迭代 + 黄金集验证 + 变更审批**三件套；描述质量直接决定 ToolSelectionAccuracy（2026 最核心的 Agent 指标）。
