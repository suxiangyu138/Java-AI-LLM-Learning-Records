## 2. 2026-07 无状态规范核心变化

**四大核心变化**：

| 变化 | 旧（有状态） | 新（无状态） |
|------|------------|------------|
| **协议核心** | 双向有状态（Session ID 粘性） | **请求/响应无状态** |
| **调用方式** | 两次 HTTP（initialize 拿 Session → 再调用工具） | **单次请求完成调用**（请求头传协议版本与方法） |
| **服务器部署** | 需粘性路由（负载均衡难） | **标准负载均衡器之后即可**（K8s 云原生） |
| **状态管理** | 服务端会话状态 | **状态随请求传输**（payload 变大，可压缩） |

**其他规范变化**：

```text
① 12 个月弃用政策：功能从标记弃用到移除至少 12 个月过渡期
   → 企业级稳定性契约（关键安全更新除外）
② 移除低使用率能力：带外服务器日志（out-of-band logging）
   → 维护者称"全 GitHub 几乎无人使用"
③ 多轮往返请求（multi-round-trip requests）
④ 基于请求头的路由
⑤ 可缓存列表结果（list 结果缓存）
```

> 🎯 **核心要点**：无状态化的本质 = "**让 MCP Server 成为标准的云原生服务**"——可负载均衡、可水平扩展、可用 K8s 管理，扫清企业大规模部署的最大障碍。**面试答"2026 MCP 最大变化"= 无状态 + 单请求 + 12 个月弃用政策**。

## 3. 有状态 vs 无状态：部署影响

**旧协议的部署痛点**（为什么要改）：

```text
旧：Client 连接 Server 后建立 Session
  → 后续请求必须路由到同一实例（粘性会话）
  → 负载均衡器需要 Session Affinity 配置
  → 实例重启 = 会话断裂 = 调用失败
  → 企业多实例/自动扩缩容场景寸步难行

新：无状态请求/响应
  → 任何请求可路由到任何实例
  → 标准负载均衡器 + K8s 原生
  → 实例重启无感（状态在请求中）
  → 企业级部署解锁
```

**部署架构对比**：

```text
旧（有状态）：
  Client → LB（粘性路由！）→ Server A（持有 Session）
                            → Server B（无法接管 A 的会话）

新（无状态）：
  Client → LB（普通路由）→ Server A / Server B / Server C（任意）
  → 水平扩展、滚动升级、故障转移全部标准化
```

**权衡与代价**（面试能谈"代价"是加分）：

| 代价 | 说明 | 缓解 |
|------|------|------|
| payload 变大 | 状态随请求传输 | 压缩 |
| 每次请求重复鉴权上下文 | 认证开销 | 令牌缓存 |
| 长会话状态管理迁移 | 旧应用改造 | 12 个月过渡期 |

> 🎯 **核心要点**：无状态 = "**部署自由**"——K8s 原生、负载均衡、水平扩展全部解锁；代价是 payload 与鉴权开销，换来的是企业级可用性。**"无状态"是 2026 MCP 面试的第一关键词**。

## 4. 授权与安全加固

**2026-07 规范的安全强化**（协议层）：

| 安全项 | 说明 |
|--------|------|
| **OAuth issuer 强制校验** | 强制验证 `iss` 参数——从协议层封堵"混淆攻击"（mix-up attacks） |
| **Enterprise Managed Authorization** | 与 Okta 合作：企业身份提供商（IdP）作为 MCP Server 访问的权威守门人 |
| 授权粒度 | OAuth 2.0 client credentials、**按工具粒度 scope** |
| 审计日志 | 全链路授权审计 |

**部署侧的安全实践**（配合规范）：

```text
① 用户级令牌代理：杜绝 API Key 硬编码在客户端
② 网关层鉴权：凭据留在网关，Server 侧无凭据
③ 工具白名单（allowlist）：不整体信任服务器
④ 固定工具描述：静默变更即失败（防工具投毒，见 14 号）
⑤ 传输加密：TLS（HTTP+SSE 传输）
```

> 🎯 **核心要点**：2026 安全主线 = "**协议层强制（iss 校验）+ 网关层集中（凭据/授权）+ 应用层防御（白名单/固定描述）**"——MCP 从"能连"进化为"安全地连"。

## 5. 官方扩展：Apps 与 Tasks

**两个扩展从实验升级为官方**（2026-07）：

### MCP Apps（服务器端渲染的交互式 UI）

```text
作用：MCP Server 不只是"返回数据"，还能渲染交互界面
  → Server 端渲染 UI 组件，Client 端展示
  → Agent 的"工具"从纯文本调用升级为交互式操作
场景：表单填写、审批界面、仪表盘
```

### MCP Tasks（长时异步任务）

```text
作用：长时任务的协议级支持
  → 返回持久化任务句柄（task handle）
  → 客户端可断开后恢复轮询（断点恢复）
  → 与 Agent 长任务需求对齐（见 06 号第 6 节）

流程：
  Client 提交任务 → Server 返回 task_id → 异步执行
  → Client 可断开（句柄持久化）→ 恢复轮询状态 → 完成取结果
场景：批量处理、数据管道、长时间推理
```

> 🎯 **核心要点**：Apps/Tasks 转正 = "**MCP 从'工具调用协议'扩展为'交互与任务协议'**"——Apps 管交互（UI）、Tasks 管长任务（持久句柄），2026 年 Agent 生产化的两个关键能力在协议层落地。

## 7. 迁移要点与兼容性

**从旧版（有状态）迁移到无状态的检查清单**：

```text
① 调用方式：两次请求 → 单次请求（请求头传协议版本与方法）
② 部署架构：粘性路由 → 标准负载均衡（K8s 原生）
③ 状态管理：服务端会话 → 请求内传递（大状态考虑压缩）
④ 弃用功能检查：带外日志等被移除能力是否有依赖
⑤ 鉴权升级：OAuth iss 校验必须实现（协议强制）
⑥ 过渡期安排：12 个月弃用政策内的功能可平滑迁移
```

**兼容性认知**（避免踩坑）：

```text
① 旧 Client 连新 Server / 新 Client 连旧 Server：需要版本协商
② "1.0 正式版"与"2.0/无状态"的称呼差异：核心事实一致（无状态转型）
③ SDK 升级优先：官方 SDK 已适配新规范，业务代码改动最小
④ 国内厂商适配节奏：钉钉/飞书等已发布原生 Server，接口以官方为准
```

> 🎯 **核心要点**：迁移 = "**调用方式（单次）+ 部署（无粘性）+ 鉴权（iss 强制）+ 弃用检查**"四件事——**先升级 SDK、再改部署、最后验证弃用功能**；12 个月弃用政策给了企业平滑过渡的窗口。
