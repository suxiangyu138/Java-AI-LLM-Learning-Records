## 1. 分布式的本质

**分布式爬虫 = 多台机器（或多进程）协作爬取——共享"任务"与"去重"**：

```text
分布式要解决的三件事
├── 任务共享：A 机爬的 URL，B 机不重复爬（共享待爬队列）
├── 去重共享：已爬的 URL 全集群记住（共享去重集合）
└── 调度统一：谁爬什么、按什么顺序（共享调度器）
    ——"单机是'一个人干所有活'，分布式是'一群人分工'——共享的是'脑子'（Redis）"
```

**本质心智**：**"分布式的核心不是'多台机器'，是'共享状态'"**——**"三台机器各爬各的 = 三份重复劳动；三台机器共享一个队列 = 一份劳动 × 三倍速度"**（"Redis 是分布式的'公共大脑'——队列/去重/调度都在它里面"）；**分布式的收益**——"速度（并行）× 稳定性（一台挂了别的继续）× 规模（单机爬不完的）——**'收益的前提：任务可并行（无强依赖）——顺序依赖的任务不适合分布式'"**；**分布式的成本**——"架构复杂度（队列/去重/监控）+ Redis 运维 + 网络开销——**'阶段 6 的问题：什么时候上分布式？——单机到瓶颈（速度/内存/IP 被封）才上'"**（"小爬虫用分布式是杀鸡用牛刀——先单机再分布式"）。

## 2. 任务队列：Redis 的两种形态

**Redis 任务队列两种形态——按任务类型选**：

```python
import redis

r = redis.Redis(host="redis-host", port=6379, decode_responses=True)

# 形态一：List（FIFO 先进先出）——普通 URL 队列
# lpush（生产）+ brpop（消费——阻塞等待，空闲不空转）
r.lpush("crawl:queue", "https://page1.com", "https://page2.com")
url = r.brpop("crawl:queue", timeout=30)[1]     # 阻塞取——没有就等 30 秒

# 形态二：ZSet（带优先级/延迟）——需要优先级的任务（大促优先/重试延迟）
# score = 优先级（小先出）或 时间戳（定时任务——延迟重试）
r.zadd("crawl:priority", {"https://hot.com": 1, "https://normal.com": 5})
url = r.zrange("crawl:priority", 0, 0)[0]       # 取优先级最高的
r.zrem("crawl:priority", url)                   # 取出即删除
```

**队列心智**：**"队列选型：List 简单够用（FIFO）、ZSet 要优先级/延迟（score 是'权重'）"**——**"延迟重试的经典实现：失败 URL 放进 ZSet（score=重试时间戳），定时任务把到期的移回 List——'ZSet 是爬虫的'闹钟'"**（"重试不是立刻重试——延迟重试是礼貌爬虫的纪律（阶段 4 频率哲学）"）；**队列的容量**——"待爬几百万 URL 很常见——Redis 内存要评估——**'队列是分布式的命脉——队列挂了 = 全集群停摆——Redis 要持久化（AOF）+ 主从（高可用）'"**；**消费的幂等**——"brpop 取出后机器崩了 = URL 丢了——**'先取后删的风险：丢了任务——先删后取的风险：重复消费——分布式的一致性没有完美解，靠'去重兜底'（下节）'"**。

## 3. 分布式去重

**分布式去重 = 全集群记住"爬过什么"**——三档方案（精度 × 内存权衡）：

```python
# 方案一：Redis Set（精确去重——小规模）
# 百万 URL 以内：Set 精确且简单
r.sadd("crawl:seen", url)
is_seen = r.sismember("crawl:seen", url)

# 方案二：Bloom Filter（布隆过滤器——阶段 6 已提，本课讲透）
# 原理：URL 哈希到 N 个位置——位置都"有标记" = 可能爬过（误判率 p）
# 代价：会误判（没爬过的说爬过——漏爬，不会重复爬）——换内存的巨大节省
from pybloom_live import BloomFilter
# 1000 万 URL：Set 约 500MB+ vs Bloom 约 20MB（误判率 1%）
bloom = BloomFilter(capacity=10_000_000, error_rate=0.01)
if url not in bloom:
    bloom.add(url)              # 没爬过 → 爬它
# 方案三：RedisBloom（Redis 模块——生产级布隆——多机共享）
```

**去重心智**：**"去重选型：Set 精确简单（百万级）、布隆省内存（千万级——误判换空间）"**——**"布隆的代价：误判 = 漏爬（没爬过被说爬过）——爬虫场景可接受（漏几条 vs 内存爆）——'布隆是爬虫的'标准去重器'——用 20MB 换 500MB，漏 1% 可接受'"**（阶段 6"1000 万 URL 2GB+→200MB"的机制课）；**去重的粒度**——"URL 去重（简单——同 URL 同内容）vs 内容指纹去重（07 篇——同内容不同 URL——翻页参数/时间戳污染 URL——**'URL 去重是基础，指纹去重是进阶——两档配合'"**）；**去重的时序**——"入队前去重（队列里没有重复）+ 出队后去重（防止重复消费）——**'双保险：去重不是一次性的，是流水线上两道闸'"**（"分布式环境下去重要'先查后加'的原子性——Redis 的 SADD 天生原子——'用 Redis 做去重 = 借它的原子性'"）。

## 4. 调度器原理

**Scrapy-Redis 调度器 = 把 Scrapy 的"内存队列"换成"Redis 队列"**：

```text
调度器原理（Scrapy-Redis 做了什么）
├── 默认 Scrapy：待爬队列在内存（单机独享）
├── Scrapy-Redis：调度器换成 Redis 版——队列/去重/指纹全在 Redis
├── 爬虫从"从 Redis 取 URL"（不关心是哪台机器放的）
└── 结果：多台机器共享队列 = 天然分布式
    ——"Scrapy-Redis 的魔法：'把爬虫的肠子换成 Redis 的'——爬虫代码几乎不用改"
```

```python
# Scrapy-Redis 配置（阶段 6 已用——本课讲为什么）
# settings.py
SCHEDULER = "scrapy_redis.scheduler.Scheduler"       # 调度器换 Redis 版
DUPEFILTER_CLASS = "scrapy_redis.dupefilter.RFPDupeFilter"  # 去重换 Redis 版
REDIS_URL = "redis://redis-host:6379"

# 爬虫继承 RedisSpider（从 Redis 队列读起始 URL——多机可同时启动）
from scrapy_redis.spiders import RedisSpider

class MySpider(RedisSpider):
    name = "my_spider"
    redis_key = "my_spider:start_urls"      # 往这个 key push 起始 URL
    # redis-cli LPUSH my_spider:start_urls https://start1.com
```

**调度器心智**：**"调度器替换的边界：'三个组件换 Redis 版——队列/去重/指纹'——其余逻辑（下载/解析/管道）不变"**——**"理解原理的价值：出问题知道查哪——'队列在 Redis 的 key 是哪个、去重误判率多少、指纹怎么算的——会查 Redis 就是会调分布式'"**（"排障工具：`redis-cli LLEN crawl:queue`（队列长度）、`SCARD crawl:seen`（已爬数）、`ZRANGE`（延迟队列）——**'分布式的监控 = Redis 的 key 体检'"**）；**调度器的选择**——"Scrapy-Redis（阶段 6：停维护但稳定——生态最熟）vs 自研调度（队列+去重自己拼——灵活但工作量大）——**'2026 年：小集群 Scrapy-Redis 够用，大厂自研（Kafka 队列 + 自研调度）'"**（"工具选型跟着规模走——阶段 6 结论延续"）。

## 5. 多机部署与稳定性

**分布式部署 = 多机 + 稳定性设计**：

```text
多机部署架构
├── Redis 集群（主从 + 持久化——分布式的心脏，先保它）
├── 爬虫机 N 台（每台跑 N 个爬虫进程——Scrapy 并发调优——06 篇）
├── 存储（MySQL/MongoDB——阶段 3——共享库）
└── 监控（08 篇——队列积压/爬取速率/失败率）
    ——"部署顺序：先 Redis 高可用 → 再爬虫机 → 最后监控——心脏先行"
```

**稳定性心智**：**"分布式稳定性的三个设计"**——**"① 幂等消费（去重兜底——重复爬不重复入库——数据库 UNIQUE——阶段 3）；② 断点恢复（进程重启从 Redis 队列续爬——队列是'天然断点'）；③ 单机故障不致命（一台挂了，队列还在，别的机器接着爬——'分布式的容错 = 状态不在单机'"**（"对比单机：进程挂了队列在内存丢了——**'分布式把'记忆'放在了 Redis——机器的生死不影响任务'"**）；**部署的运维**——"Docker 化（阶段 6 部署课——每台机跑同样的镜像——'机器是同构的，差异只在 Redis'）+ 版本管理（爬虫代码 Git——升级灰度——'分布式升级 = 逐个重启机器'）——**'分布式不是部署的结束，是运维的开始'"**（08 篇监控的入口）；**什么时候该分布式**（本课 1 节的答案）——"单机到瓶颈三信号：速度不够（时间预算）、内存不够（去重集合太大）、IP 不够（单 IP 被封）——**'三个信号出现一个，考虑分布式'"**。
