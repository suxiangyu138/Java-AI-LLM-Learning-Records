## 1. 性能瓶颈在哪

**爬虫的耗时分布——先找瓶颈再优化**（测量的第一步）：

```text
爬虫耗时分布（典型）
├── 网络等待（IO）：80%+——请求发出去等响应（瓶颈之王）
├── 解析（CPU）：10%——HTML/JSON 解析
├── 存储（IO）：5%——数据库写入
└── 调度/其他：5%
    ——"爬虫是 IO 密集型——优化的主战场在网络等待，不是解析"
```

**瓶颈心智**：**"IO 密集型的优化逻辑：'等待时间并行化'——一个请求等 1 秒，100 个并发 = 同样 1 秒拿到 100 个响应"**——**"爬虫提速的第一思路：把'等待'叠起来（并发），不是把'代码'改快（解析不是瓶颈）"**（"CPU 密集优化代码，IO 密集优化并发——爬虫是后者"）；**测量先行**（性能第一纪律——数据分析阶段 2 NumPy 08 篇同款）——"优化前先测：耗时分布（请求/解析/存储各多少）——**'不测量的优化是碰运气——90% 的时间在等待，优化解析是白费'"**（"profile 工具：简单用时间戳统计各环节耗时"）。

## 2. 并发模型

**并发三模型——按场景选**（Python 并发体系——`../../01-Python语言/Python%20异步%20+%20FastAPI/` 的爬虫版）：

```python
# 模型一：多线程（ThreadPoolExecutor——IO 密集的经典解）
# 场景：requests 同步请求（阶段 2 体系）——线程池并发
from concurrent.futures import ThreadPoolExecutor

def fetch(url):
    resp = requests.get(url, timeout=(3, 15))
    return parse(resp)

with ThreadPoolExecutor(max_workers=32) as pool:    # 32 线程并发
    results = list(pool.map(fetch, urls[:1000]))

# 模型二：异步（asyncio + httpx——单线程事件循环，2026 主流）
import asyncio
import httpx

async def fetch_async(client, url):
    resp = await client.get(url, timeout=15)
    return parse(resp)

async def main():
    async with httpx.AsyncClient() as client:
        tasks = [fetch_async(client, u) for u in urls[:1000]]
        results = await asyncio.gather(*tasks)      # 1000 个并发请求

asyncio.run(main())

# 模型三：Scrapy 原生并发（阶段 6——CONCURRENT_REQUESTS 调参）
# CONCURRENT_REQUESTS = 32（默认 16——按目标站承受力调）
```

**并发心智**：**"并发模型选型：requests 用户用线程池（简单）、新项目用 asyncio+httpx（高效——2026 主流）、Scrapy 项目调 CONCURRENT_REQUESTS"**——**"异步 vs 线程：异步是'单线程里的并发'（事件循环——省内存，万级并发）、线程是'多线程的并行'（简单直接——千级）——'目标站请求量大用异步，改造量小用线程'"**（阶段 6 2.14 的 AsyncCrawlerProcess 是 Scrapy 的异步化）；**并发的边界**——"并发不是越高越好：目标站的承受力（打崩 = 拒绝服务——合规红线 01 篇）+ IP 触发反爬（阶段 4 频率哲学）——**'并发上限 = min(目标承受力, IP 池容量, 你的道德底线)'"**（"32 并发对普通站可能已经算'攻击'了——从 5 并发开始试，压测定上限（本课第 4 节）"）。

## 3. 限速调优

**限速 = 性能与安全的平衡——不是"慢"，是"稳"**：

```text
限速的两个维度
├── 全局速率：每秒多少请求（RPS——由目标承受力与反爬阈值决定）
├── 单 IP 速率：每个 IP 每秒多少请求（阶段 4 纪律——1 IP / 3-5 秒）
└── 分布式限速：多机共享限速（Redis 计数——05 篇的公共大脑）
    ——"限速的目的是'不被封'——被封的重爬成本远大于限速的慢"
```

```python
# Scrapy 限速配置（AutoThrottle——阶段 6 提过，本课讲调优）
# settings.py
AUTOTHROTTLE_ENABLED = True          # 自动限速（根据响应延迟自适应）
AUTOTHROTTLE_START_DELAY = 5.0       # 起始延迟（从保守开始）
AUTOTHROTTLE_MAX_DELAY = 60.0        # 最大延迟（被拖慢时的上限）
AUTOTHROTTLE_TARGET_CONCURRENCY = 8  # 目标并发（AutoThrottle 据此自适应）
```

**限速心智**：**"限速调优的黄金流程：'从保守开始，压测探上限，稳定运行在上限的 80%'"**——**"AutoThrottle 的价值：'自适应'——目标站响应慢（快被封）自动降速，响应快自动提速——'让限速跟着目标站的心跳走'"**（"AutoThrottle 是 Scrapy 的'自动驾驶'——手动限速是'手动挡'——大站自动，特殊站手动"）；**限速的监测**——"429 出现率（反爬信号——阶段 4）、响应延迟趋势（被拖慢 = 被限流了）——**'限速调优的反馈回路：监控 429 与延迟 → 调整参数 → 再监控'"**（08 篇监控的输入）；**分布式限速**——"多台机器 = 总速率是 N 倍——**'分布式限速 = 总速率恒定（按 IP 池/目标承受力），不是每台机器各跑各的'"**（Redis 计数窗口——"分布式的公共大脑（05 篇）第二次出场——限速也要共享"）。

## 4. 压测方法论

**压测 = 确定"目标站能承受多少、我能安全跑多少"**：

```text
压测四步
├── ① 基线：单 IP 5 并发跑 10 分钟——记录响应延迟/429 数（基线数据）
├── ② 爬坡：5 → 10 → 20 → 40 并发逐级加（每级 10 分钟）——找拐点
├── ③ 判拐点：延迟陡增 / 429 出现 / 验证码出现 = 过了安全线
└── ④ 定档：安全并发 = 拐点 × 0.8（留安全余量）
    ——"压测的目的不是'跑多快'，是'知道安全线在哪'"
```

```python
# 压测脚本简化版（统计延迟与 429）
import time
import requests

def load_test(urls, concurrency, duration=600):
    """简单压测：统计平均延迟与 429 比例"""
    start = time.time()
    latencies, errors = [], 0
    # 并发请求（简化为循环示意——实际用线程池/异步）
    for url in urls:
        t0 = time.time()
        resp = requests.get(url, timeout=(3, 15))
        latencies.append(time.time() - t0)
        if resp.status_code == 429:
            errors += 1
    avg_latency = sum(latencies) / len(latencies)
    print(f"并发 {concurrency}: 平均延迟 {avg_latency:.2f}s / 429 比例 {errors/len(urls):.1%}")
```

**压测心智**：**"压测的价值观：'尊重目标站'——压测不是为了打垮，是为了找到'友好上限'"**——**"爬坡式压测（逐级加）vs 一上来全速（打崩目标 = 拒绝服务——合规红线 01 篇）——'压测是'试探'不是'攻击'——试探的节奏要温和'"**（"真正专业的爬虫团队：压测记录存档 + 目标站有配合（合作站）——**'压测数据 = 你'礼貌'的证据'"**）；**压测的指标**——"延迟（性能）、429 率（反爬）、验证码率（会话健康度——03 篇）——**'三个指标画成曲线，拐点一目了然'"**；**压测的产物**——"压测报告（并发/延迟/429 的表格 + 安全线结论）——**'压测报告 = 运维的基线文档——上线后的限速参数从它来'"**（08 篇监控的基准值来源）。

## 5. 性能调优清单

**性能调优完整清单（从收益大到小排列）**：

```text
性能调优清单（按 ROI 排序）
├── ① 并发模型：IO 等待并行化（本课 2 节——收益最大——10-100 倍）
├── ② 限速参数：AutoThrottle/单 IP 速率（本课 3 节——稳）
├── ③ 解析优化：lxml 解析器（阶段 2——比 html.parser 快 5-10 倍）/ 少用正则
├── ④ 存储优化：批量写入（executemany/管道批量——阶段 3——少连接）
├── ⑤ 连接复用：Session/连接池（阶段 2——握手成本省掉）
├── ⑥ 请求精简：只取需要的字段（usecols 思维——数据分析阶段 3 03 篇）
└── ⑦ 基础设施：代理池质量（02 篇——高质量代理延迟低）
    ——"先动①，最后才碰③——优化的顺序 = 收益的顺序"
```

**清单心智**：**"性能调优 80% 的收益来自并发（①）——其余是锦上添花"**——**"别在解析优化上花一周，并发加一档就翻倍——'爬虫性能的第一定律：并发是王，解析是臣'"**；**调优的验证**——"每次调优记录前后对比（吞吐量/延迟）——**'调优报告 = 参数 + 数据——没有对比数字的调优是自我安慰'"**（"性能调优报告格式：改了什么参数 / 吞吐从多少到多少 / 429 变化"）；**性能与稳定的平衡**——"快不是唯一目标：稳定（不封）+ 质量（数据完整）才是——**'调优的终点是'安全地快'——性能指标永远配着风险指标看（429/验证码）'"**。

## 7. 本节验收

**验收动作**：① 对同一批 URL 测三种方案（串行/线程池/异步）的耗时（记录对比数字）；② 做一次爬坡压测（5→10→20 并发——记录延迟与 429 拐点）；③ 写调优报告（参数/前后对比/安全线）——**"并发 + 限速 + 压测 + 清单 = 性能调优能力"**——**练习纪律**：任何调优先测基线再动手——"不测量的优化是碰运气"。

> 🎯 **核心要点**：爬虫是 IO 密集（**瓶颈在网络等待——优化主战场是并发不是解析**）；**并发三模型（线程池 requests/异步 httpx 2026 主流/Scrapy 调参——并发上限 = min(目标承受力, IP 池, 底线)）**；**限速调优（AutoThrottle 自适应 + 压测探上限 + 80% 余量——分布式限速要共享）**；**压测四步（基线→爬坡→判拐点→定档——试探不是攻击——压测报告是运维基线）**；调优清单（**并发是王解析是臣——每次调优记录对比数字**）——"快 2 倍是听说的，快多少是自己测的"。
