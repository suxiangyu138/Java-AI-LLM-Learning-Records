## 1. 存储选型矩阵

| 数据形态 | 推荐存储 | 原因 |
|---------|---------|------|
| 结构化表格（列表/统计） | **MySQL** | 关系模型 + SQL + 事务 |
| 嵌套/结构多变（详情/评论） | **MongoDB** | 文档模型零转换 |
| 小数据/单机 | SQLite / CSV | 零依赖 |
| 海量小文件 | 对象存储（MinIO） | 文件归文件（[MinIO 体系](../../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MinIO/00-MinIO总览.md)） |
| 去重/计数缓存 | Redis | 高性能（阶段 6） |

```text
决策问题（按顺序）：
  ① 数据是文件还是结构化数据？ → 文件 → 对象存储
  ② 结构固定吗？ → 固定 → MySQL；多变/嵌套 → MongoDB
  ③ 数据量多大？ → 小 → SQLite/CSV
  ④ 需要事务吗？ → 需要 → MySQL
```

> 🎯 选型一句话：**"表格型数据进 MySQL、嵌套型进 MongoDB、文件进 MinIO、小数据用文件"**——别用一个存储硬扛所有形态。

## 2. 索引设计

```sql
-- ═══ 索引设计三原则 ═══
-- ① 查询 WHERE 的字段建索引
CREATE INDEX idx_date ON news (publish_time);
CREATE INDEX idx_status_time ON crawl_tasks (status, crawl_time);   -- 复合

-- ② 去重字段唯一索引
CREATE UNIQUE INDEX uk_url ON news (url(255));

-- ③ 索引不是越多越好（写放大）
-- 每多一个索引 = 每次写入多维护一份

-- ═══ 索引验证 ═══
EXPLAIN SELECT * FROM news WHERE publish_time > '2026-08-01';
-- 看 type 列：ALL（全表扫描，要优化）/ range（范围）/ ref（引用）
```

| 索引设计 | 做法 |
|---------|------|
| 查询字段 | WHERE 条件字段（高频查询优先） |
| 去重字段 | UNIQUE（url/fingerprint） |
| 复合索引 | 多条件组合（最左前缀原则） |
| 验证 | EXPLAIN 看是否走索引 |
| 克制 | 只建实际查询用的（写放大） |

> ⚠️ 索引是"查询加速器"不是"越多越好"：**一个表 5-10 个索引是上限**——每多一个索引，写入/更新都变慢。先写查询，再为查询建索引（[MySQL 索引体系](../../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MySQL/00-MySQL总览与技术术语.md) 深挖）。

## 3. 建表生产规范

```sql
-- ═══ 爬虫建表生产规范 ═══
CREATE TABLE news (
    id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    -- 业务字段：类型正确（数字/日期不用 VARCHAR）
    title       VARCHAR(512) NOT NULL,
    url         VARCHAR(1024) NOT NULL,
    -- 去重键
    fingerprint CHAR(32) DEFAULT NULL,
    -- 状态与审计
    status      TINYINT NOT NULL DEFAULT 0,
    crawl_time  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                ON UPDATE CURRENT_TIMESTAMP,
    -- 约束与索引
    UNIQUE KEY uk_url (url(255)),
    UNIQUE KEY uk_fp (fingerprint),
    KEY idx_status_crawl (status, crawl_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='新闻数据表';
```

```text
建表规范清单：
  □ 表名小写蛇形（news / crawl_tasks）
  □ InnoDB + utf8mb4（事务 + 全字符）
  □ 主键自增 BIGINT
  □ 字段类型正确（数字/日期/文本分开）
  □ 去重键（UNIQUE）+ 查询索引（KEY）
  □ 状态字段 + 时间审计（crawl_time/updated_at）
  □ 字段注释（COMMENT）——爬虫表也要文档
  □ 预留扩展（不用 VARCHAR(10) 卡死）
```

> 🎯 规范价值：**"建表 5 分钟，改表 5 小时"**——类型/编码/索引在第一天定对，后面零返工；`COMMENT` 注释让半年后的自己（和同事）看得懂这表干嘛的。

## 4. 数据治理：保留与归档

```text
数据治理三问（爬虫数据量增长是必然）：
  ① 数据要留多久？       → 保留策略（新闻 3 年/日志 30 天）
  ② 旧数据怎么处理？     → 删除 or 归档（冷热分离）
  ③ 表越来越大怎么办？   → 分区/分表/归档表

归档策略：
  热数据（近期）→ 主表（查询快）
  冷数据（历史）→ 归档表/文件（存储省）
  定时任务：每月把 90 天前的数据搬到 archive 表
```

```sql
-- 保留策略（定时执行）
DELETE FROM news WHERE crawl_time < DATE_SUB(NOW(), INTERVAL 1 YEAR);

-- 归档（移动而非删除）
INSERT INTO news_archive SELECT * FROM news WHERE crawl_time < DATE_SUB(NOW(), INTERVAL 90 DAY);
DELETE FROM news WHERE crawl_time < DATE_SUB(NOW(), INTERVAL 90 DAY);

-- 分区表（大数据量标配）
CREATE TABLE news (
    ...,
    crawl_time DATETIME
) PARTITION BY RANGE (TO_DAYS(crawl_time)) (
    PARTITION p2026q1 VALUES LESS THAN (TO_DAYS('2026-04-01')),
    PARTITION p2026q2 VALUES LESS THAN (TO_DAYS('2026-07-01')),
    PARTITION p_max VALUES LESS THAN MAXVALUE
);
```

> 🎯 治理认知：**"爬虫的数据只进不出 = 存储慢性死亡"**——保留策略 + 归档 + 分区三件套，让数据量"可控增长"。与 [MinIO 生命周期](../../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/MinIO/01-对象存储核心概念与S3模型.md) 同理念：治理是存储的一部分。

## 5. 生产巡检清单

```text
数据库巡检（每周）：
  □ 容量：数据量/磁盘水位（告警阈值 80%）
  □ 慢查询：慢日志/SHOW PROCESSLIST 抓慢 SQL
  □ 索引失效：EXPLAIN 抽查高频查询
  □ 重复数据：按 url 计数抽查（去重是否生效）
  □ 任务队列：crawl_tasks 各状态分布（卡住的 status=1?）
  □ 失败率：status=3 占比（>5% 要查原因）
  □ 备份：每日备份 + 恢复演练（阶段 2 §7 已有文件级，库级同样）

备份（每日）：
  mysqldump -u root -p crawler_db > crawler_$(date +%F).sql
  mongodump --db crawler_db --out /backup/mongo/
```

> 🎯 本阶段毕业标准：**"数据存得住（选型对）、不重复（三层去重）、抓得新（增量策略）、洗得净（pandas 流水线）、管得久（治理+备份）"**——五条全达标，进入[阶段 4：反爬基础](../阶段%204：反爬基础（高频遇到）/00-阶段4反爬基础总览.md)。
