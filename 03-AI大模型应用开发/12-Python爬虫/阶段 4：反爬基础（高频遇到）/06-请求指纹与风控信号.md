## 1. 指纹：比 Headers 更深的身份

```text
Headers 是"自报家门"（可伪造）
指纹是"体检报告"（难以伪造）

服务器怎么看指纹：
  浏览器加载页面 → 页面里的 JS 执行
  → JS 探测浏览器环境（Canvas/WebGL/字体/时区...）
  → 上报"指纹特征"到服务器
  → 服务器对比"正常浏览器指纹库" → 判定

为什么 requests 躲不过指纹：
  requests 不执行 JS → 指纹检测 JS 无法运行
  → 服务器发现"页面 JS 没执行" → 非浏览器信号！
```

> 🎯 认知升级：**"UA 伪装是'穿衣服'，指纹检测是'验血'"**——只改请求头躲不过指纹；指纹检测的前提是"页面有 JS 检测逻辑"，而 requests 根本不执行 JS（这是阶段 5 动态渲染的另一个动机）。

## 2. 设备指纹的组成

```text
浏览器指纹的常用信号源：
  Canvas 指纹：JS 画图 → 提取渲染结果哈希（GPU 差异）
  WebGL 指纹：3D 渲染信息（显卡型号/驱动）
  字体指纹：检测已安装字体列表
  时区/语言：系统时区/语言设置
  屏幕参数：分辨率/色深/触摸支持
  硬件信息：CPU 核心数/内存（navigator 暴露）
  Audio 指纹：音频处理特性

组合逻辑：
  单个信号可伪造，几十个信号组合几乎唯一
  （真实浏览器指纹的"熵"极高）

风控用途：
  同一指纹多次触发风控 → 标记该"设备"
  指纹与 IP/UA 交叉关联 → 识别"同一爬虫换 IP"
```

| 指纹信号 | 获取方式（JS） | 伪造难度 |
|---------|--------------|:---:|
| Canvas | canvas.toDataURL() | 中 |
| WebGL | 渲染信息 | 高 |
| 字体 | font 检测 | 中 |
| 时区/语言 | Intl/navigator | 低 |
| 屏幕/硬件 | navigator/screen | 低 |
| Audio | AudioContext | 高 |

> 🎯 关键认知：**"指纹的威力在'组合'与'交叉'"**——单看 UA 能伪装，但"UA 是 Windows + 时区是 UTC + 字体是 Linux 默认集"这种组合矛盾就暴露了。这也是 [02 §5](02-UA与Headers伪装.md) 强调"一致性"的原因。

## 3. JS 检测：服务器怎么"问"浏览器

```text
JS 检测的典型机制：
  ① 页面加载 JS 检测脚本（隐藏请求）
  ② JS 探测环境 → 上报特征（异步请求）
  ③ 服务器比对 → 下发"通过令牌"或"验证码"
  ④ 后续请求必须带"通过令牌"才能拿数据

检测什么：
  · 自动化工具标志（webdriver 属性/Selenium 特征）
  · 无头浏览器特征（Headless Chrome 的差异）
  · 环境矛盾（指纹组合不合理）
  · 执行环境异常（JS 引擎版本/缺失）

常见表现：
  页面正常加载，但数据请求返回 403/验证码
  页面里出现"浏览器环境异常"提示
  get 数据需要额外的"验证令牌"参数
```

> ⚠️ 识别信号：**"页面能开、代码 403"**且已排除 UA/频率/登录——大概率是 JS 检测。本阶段不硬碰（阶段 5 用真实浏览器/Playwright 应对，因为 Playwright 会真正执行 JS）。

## 4. 风控信号与评分

```text
风控系统 = 多维信号 → 综合评分 → 分级处置

信号维度（本阶段全部接触过）：
  · 请求头质量（UA/完整性/一致性）—— 02 章
  · 频率与节奏（速率/规律性）—— 03 章
  · IP 信誉（历史行为/是否代理/是否黑名单）—— 04 章
  · 会话行为（登录态/Cookie 连续性）—— 05 章
  · 指纹质量（JS 检测结果/组合矛盾）—— 本章

分级处置（分数由低到高）：
  正常放行 → 增加验证码概率 → 数据降级 → 403 → 封禁
```

| 风控信号 | 低风险 | 高风险 |
|---------|--------|--------|
| UA | 完整浏览器 | 库 UA/缺失 |
| 频率 | 随机间隔 | 固定高速 |
| IP | 住宅/干净 | 数据中心/黑名单 |
| 会话 | 连续 Cookie | 每次新会话 |
| 指纹 | 真实浏览器 | 无 JS 执行/矛盾 |

> 🎯 风控本质：**"风控不是'单点拦截'，是'综合评分'**——每个维度都做得像人，总分才低；单一维度再完美，其他维度暴露照样触发。这就是"成套伪装 + 礼貌节奏 + 会话一致"全部重要的原因。

## 5. requests 的指纹短板

```text
requests 在指纹维度的天生短板：
  ① 不执行 JS → 指纹检测直接暴露"非浏览器"
  ② 无浏览器环境 → 无法提供真实指纹
  ③ 无 Cookie 容器 → 会话连续性靠 Session 模拟（有限）

哪些站点会用到指纹：
  · 商业级风控（大平台/电商/社交）
  · 高价值数据（价格对比/舆情/情报）
  · 有 JS 检测逻辑的站点

requests 的适用边界：
  ✅ 无 JS 检测的站点（大多数中小站）—— 本阶段能力覆盖
  ❌ 强指纹风控的站点 → 需要真实浏览器（阶段 5）
```

> 🎯 能力边界认知：**"requests 解决'请求层'反爬，解决不了'浏览器层'反爬"**——遇到强指纹风控，requests 再怎么伪装都白搭，正确路线是阶段 5 的 Playwright（真实浏览器执行 JS）。

## 6. 本阶段的应对策略

```text
本阶段（requests 路线）的指纹应对：
  ① 识别：页面正常但代码 403 → 怀疑 JS 检测
  ② 验证：用 Playwright 打开（阶段 5）→ 能开 = JS 检测实锤
  ③ 决策：
     · 中小站/无 JS 检测 → requests 继续（本阶段全套）
     · 强风控站 → 标记"需要浏览器"（阶段 5 处理）
     · 极强风控 → 评估换数据源/放弃（07 章）

工程动作：
  把站点分级（在配置里）：
  SITE_LEVEL = {
      "example.com": "normal",      # requests 可爬
      "bigsite.com": "browser",     # 需要 Playwright
      "hardcore.com": "skip",       # 放弃/换源
  }
```

| 站点分级 | 应对 | 工具 |
|---------|------|------|
| normal | requests 全套（02-05） | 本阶段 |
| browser | 动态渲染（阶段 5） | Playwright |
| skip | 换数据源/放弃（07） | - |

> 🎯 本章小结：**"指纹是'组合与交叉'的深身份，requests 不执行 JS 是天生短板"**——本阶段的合格认知是：**能识别、能分级、知道下一步去哪**。真正的指纹对抗（真实浏览器）是阶段 5 的事；"该不该对抗"是 07 章的事。
