## 1. 频率为什么是第二道校验

```text
服务器看频率判断"是不是人"：
  人：每分钟 5-30 次请求，有停顿有节奏
  机器：每秒 10 次，24 小时不停，节奏均匀

频率校验的三个观察维度：
  ① 瞬时速率（次/秒）—— 每秒 N 次 = 机器
  ② 单位时间总量（次/小时）—— 万级 = 机器
  ③ 节奏规律（间隔分布）—— 固定间隔 = 机器

被频率拦截的表现：
  429 Too Many Requests（明确限流）
  403 + "访问过于频繁"
  验证码突然出现
```

> 🎯 认知：**"频率是伪装之后的第一道真防线"**——UA 装得像人，但每秒 20 次请求直接暴露机器身份。**频率控制不是"慢一点"，是"像人一点"**。

## 2. 随机延迟：打破机器节奏

```python
import random
import time

# ═══ 随机延迟（像人）═══
time.sleep(random.uniform(1.0, 3.0))     # 1-3 秒随机

# ═══ 分场景节奏（不同请求不同延迟）═══
def polite_sleep(request_type: str = "normal"):
    """按请求类型控制节奏（页面重请求慢、接口轻请求快）"""
    ranges = {
        "detail": (2.0, 5.0),       # 详情页（重请求）：2-5 秒
        "list": (1.0, 3.0),         # 列表页：1-3 秒
        "api": (0.5, 1.5),          # 接口：0.5-1.5 秒
        "static": (0.2, 0.5),       # 静态资源：0.2-0.5 秒
    }
    low, high = ranges.get(request_type, (1.0, 2.0))
    time.sleep(random.uniform(low, high))

# ═══ 使用 ═══
for url in detail_urls:
    fetch(url)
    polite_sleep("detail")          # 详情页节奏
```

| 延迟设计 | 说明 |
|---------|------|
| 随机范围 | 别固定值（固定 1s = 机器节奏） |
| 场景分级 | 重请求慢、轻请求快（像人的取舍） |
| 上限 | 总速率别超站点容忍（见 §5 探测） |
| 与重试配合 | 失败重试的退避（阶段 2 §3） |

> ⚠️ 随机延迟的两个极端：**固定延迟**（机器特征）与**完全不延迟**（必被限）——随机范围是两者之间的正解；范围大小按站点压力调整（小站 2-5 秒，大平台可 0.5-1 秒）。

## 3. 请求节流：全局速率控制

```python
# ═══ 全局节流（token bucket 简单实现）═══
import threading
import time

class RateLimiter:
    """令牌桶限速器：全局控制请求速率"""

    def __init__(self, rate: float, burst: int = 10):
        self.min_interval = 1.0 / rate    # 速率 → 最小间隔
        self.burst = burst
        self.tokens = burst
        self.last_refill = time.time()
        self.lock = threading.Lock()

    def acquire(self):
        """获取令牌（不够则等待）"""
        with self.lock:
            now = time.time()
            self.tokens = min(self.burst,
                              self.tokens + (now - self.last_refill) * self.rate())
            self.last_refill = now
            if self.tokens >= 1:
                self.tokens -= 1
                return
        # 令牌不足 → 等待到下一个令牌
        time.sleep(self.min_interval)
        self.acquire()

    def rate(self):
        return 1.0 / self.min_interval

# 使用：全局 3 次/秒
limiter = RateLimiter(rate=3.0)
for url in urls:
    limiter.acquire()              # 全局节流（多线程也安全）
    fetch(url)
```

| 节流方案 | 说明 |
|---------|------|
| 简单 sleep | 单线程够用 |
| **令牌桶** | 多线程/全局统一（上面实现） |
| 第三方 | `ratelimit` 库 / aiohttp 自带（阶段 6） |

> 🎯 节流价值：**"全局速率封顶 = 不越线"**——无论代码多乱（多线程/重试/循环），RateLimiter 保证每秒不超过 N 次；这是生产爬虫的"安全阀"（防自己把自己爬封）。

## 4. 429 与限流应对

```python
# ═══ 429 的完整应对 ═══
def fetch_with_rate_handling(session, url, max_wait=600):
    """请求 + 429 自动降速"""
    for attempt in range(5):
        resp = session.get(url, timeout=(3, 15))
        if resp.status_code == 429:
            # ① 读 Retry-After（服务器建议等待时间）
            retry_after = resp.headers.get("Retry-After")
            wait = int(retry_after) if retry_after and retry_after.isdigit() else 60
            wait = min(wait, max_wait)          # 上限保护
            print(f"429 限流：等待 {wait}s")
            time.sleep(wait)
            continue
        resp.raise_for_status()
        return resp
    raise RuntimeError(f"持续限流: {url}")

# ═══ 收到 429 后的正确动作 ═══
# ① 立即停止（别重试硬冲）
# ② 读 Retry-After 或等 60s+
# ③ 降低全局速率（limiter.rate 减半）
# ④ 检查是否 IP 被封（换 IP 见 04）
# ⑤ 长期方案：把速率降到站点容忍线以下（§5）
```

| 429 应对 | 动作 |
|---------|------|
| 立即停止 | 别硬冲（硬冲 = 封 IP） |
| Retry-After | 优先尊重服务器建议 |
| 全局降速 | 速率减半（从源头解决） |
| 换 IP | 可能是 IP 维度限流（04 章） |
| 记录 | 限流日志（频率趋势分析） |

> ⚠️ **429 是"服务器的医嘱"**：Retry-After 说等多久就等多久；无视医嘱的爬虫 = 从"临时限流"升级为"永久封禁"。**429 出现时先改自己，不是先换 IP**。

## 5. 限流边界探测

```text
为什么要探测边界：
  每个站点的容忍度不同（小站 1 次/秒，大平台 10 次/秒）
  拍脑袋定频率 → 太慢浪费 / 太快被封

探测方法（渐进式）：
  ① 从慢开始：1 次/2 秒
  ② 逐步加速：观察 30 分钟无 429/403 → 提速 20%
  ③ 触到边界：出现 429 → 回退 30% 作为安全速率
  ④ 记录结论：该站安全速率 ≈ X 次/秒

探测红线：
  每次探测在低峰时段
  别用"直接拉满"试探（可能直接封 IP）
  探测结果写入配置（每站一档）
```

```python
# ═══ 边界探测脚本骨架 ═══
def probe_rate_limit(session, url, start_rate=0.5, max_rate=10.0):
    """渐进探测站点容忍速率"""
    rate = start_rate
    for _ in range(8):                        # 最多 8 轮
        ok = test_interval(session, url, rate)   # 该速率跑 30 个请求
        if ok:
            print(f"速率 {rate:.1f}/s ✅ 通过，继续加速")
            rate = min(rate * 1.5, max_rate)
        else:
            safe = rate * 0.7                  # 回退 30%
            print(f"速率 {rate:.1f}/s ❌ 被限，安全速率 ≈ {safe:.1f}/s")
            return safe
    print(f"未触界，安全速率 ≥ {rate:.1f}/s")
    return rate
```

> 🎯 边界探测的价值：**"用 30 分钟探测换 3 个月的稳定"**——每站一档速率配置（`SITE_RATE = {"example.com": 2.0}`），比"所有站一个速"高效且安全。

## 6. 频率控制工程规范

```text
频率控制自查：
  □ 随机延迟（非固定）—— 像人节奏
  □ 全局节流（RateLimiter）—— 速率封顶
  □ 429 处理（Retry-After + 降速）—— 尊重医嘱
  □ 边界探测记录（每站一档）—— 不拍脑袋
  □ 与伪装配合（UA 池 + 会话一致）—— 成套
  □ 合规（礼貌爬虫是底线，阶段 1 §8）—— 慢而稳

频率哲学：
  "爬得快不是能力，爬得稳才是"
  稳定采集 1 个月 > 猛爬 3 天被封
```

> 🎯 本章小结：**"频率控制 = 随机节奏 + 全局节流 + 尊重 429 + 边界探测"**——四件套齐了，第二层反爬基本通关。下一关是"IP"（[04-IP代理基础](04-IP代理基础.md)）——同 IP 总量超限时，需要换出口。
