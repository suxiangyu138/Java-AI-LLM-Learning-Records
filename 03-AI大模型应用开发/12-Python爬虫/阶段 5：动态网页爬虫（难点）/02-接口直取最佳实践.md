## 1. 为什么接口直取是最优解

```text
同一动态页的两种爬法对比：
  接口直取：requests 拿 JSON → 直接解析
    毫秒级、几 KB 流量、零浏览器开销

  浏览器渲染：Playwright 开浏览器 → 加载页面 → 等 JS → 解析 DOM
    秒级、几百 MB 内存、每页都是重开销

对比结论（生产数据）：
  速度：快 10-50 倍
  资源：万分之一
  稳定性：接口契约稳定 > DOM 结构易变
  反爬：接口更容易被防护（但通常防护在登录/签名层）
```

> 🎯 铁律：**"动态页先花 5 分钟找接口，找不到再考虑渲染"**——接口直取的时间成本（F12 定位）远低于渲染的运行成本（每页秒级 + 内存）。

## 2. F12 定位接口五步（实战版）

```text
① 打开目标页 → F12 → Network → 勾 Preserve log
② 刷新页面（或触发"加载更多"）
③ 筛选 Fetch/XHR（接口专用筛选）
④ 逐个点看 Response：找含目标数据的接口
   · 看名字/路径猜（/api/list、/api/data 之类）
   · 看大小（数据接口通常响应大）
⑤ 确认后记录完整调用信息：
   · URL（含 query 参数）
   · 方法（GET/POST）
   · Headers（UA/Cookie/Referer/自定义头）
   · Payload（POST body/表单）
   · 分页规律（page/size/offset 变化）
```

```python
# 五步的产出 = 接口调用说明书（直接翻译成代码）
# 例：找到的接口
# GET https://example.com/api/articles?page=1&size=20
# Headers: Cookie: session=xxx
# 响应: {"code":0,"data":{"list":[...],"total":100}}
```

> 🎯 定位技巧：**"接口名 + 响应大小是两条线索"**——`/api/` 前缀的路径基本都是接口；响应最大的 XHR 大概率是数据接口（阶段 1 §7 已学，此处实战应用）。

## 3. 复刻接口请求

```python
import requests

# ═══ 复刻接口（从 F12 说明书翻译）═══
def fetch_articles(page: int, size: int = 20):
    session = requests.Session()
    session.headers.update({
        "User-Agent": "Mozilla/5.0 ...",
        "Referer": "https://example.com/list",    # 接口常校验来源
        "Accept": "application/json",
        # Cookie 从 F12 复制或代码登录（阶段 4 §5）
    })
    resp = session.get(
        "https://example.com/api/articles",
        params={"page": page, "size": size},
        timeout=10,
    )
    resp.raise_for_status()
    return resp.json()               # 直接拿 JSON（不用解析 HTML！）

# ═══ 使用 ═══
data = fetch_articles(1)
print(data["data"]["total"])          # 总数
for item in data["data"]["list"]:
    print(item["title"], item["url"]) # 结构化数据直接可用
```

| 复刻要素 | 来源 |
|---------|------|
| URL + 参数 | F12 请求行 |
| Headers | F12 请求头（全套复制） |
| Cookie | F12 复制 or 代码登录 |
| Payload | F12 Payload 页 |
| 分页规律 | 翻页对比两请求差异 |

> 🎯 复刻核心：**"F12 里有什么就带什么"**——最稳的复刻是 Copy as cURL 整体翻译（阶段 1 §7）；接口直取的本质就是"把浏览器的接口调用换成 requests"。

## 4. 接口分页与参数

```python
# ═══ 分页模式识别（阶段 2 §6 的接口版）═══
# 模式一：page/size（最常见）
#   /api/list?page=1&size=20
# 模式二：offset/limit
#   /api/list?offset=20&limit=20
# 模式三：游标/ID
#   /api/list?cursor=abc123（下一页的游标在响应里）
# 模式四：时间
#   /api/list?since=2026-08-08

# ═══ 通用翻页实现（适配三种模式）═══
def fetch_all(base_url, params_builder, extract_list, max_pages=100):
    """通用接口翻页：按响应判断是否到底"""
    all_items = []
    for page in range(1, max_pages + 1):
        params = params_builder(page)              # 构造本页参数
        data = requests.get(base_url, params=params, timeout=10).json()
        items = extract_list(data)                  # 提取列表
        if not items:
            break                                   # 空页终止
        all_items.extend(items)
        # 游标模式：下一页游标在响应里
        cursor = data.get("data", {}).get("next_cursor")
        if cursor is None and "cursor" in params_builder.__code__.co_varnames:
            break
        if page >= max_pages:
            break
    return all_items
```

| 分页模式 | 参数 | 终止判断 |
|---------|------|---------|
| page/size | page 递增 | 空列表 |
| offset/limit | offset += size | 空列表/总数到达 |
| 游标 | cursor（响应给） | 无 next_cursor |
| 时间 | since 递增 | 空列表/时间越界 |

> 🎯 接口分页与 HTML 翻页同构（阶段 2 §6 的知识直接迁移）：**"空页终止 + 上限保护"双保险不变**——只是解析从 HTML 换成 JSON（更简单）。

## 5. 接口直取的坑

| 坑 | 现象 | 解法 |
|----|------|------|
| **参数签名** | 接口需要 sign/token 参数 | 分析签名逻辑（阶段 7）或渲染兜底 |
| **Cookie 依赖** | 无 Cookie 返回空/401 | 先访问首页拿 Cookie（Session 热身） |
| **Referer 校验** | 无 Referer 403 | 补上来源页 URL |
| **频率限制** | 接口 429/频繁验证码 | 降速（阶段 4 §3） |
| **数据加密** | 返回密文/混淆 | 渲染兜底（本阶段）或逆向（阶段 7） |
| **字段变化** | JSON 字段名改了 | 接口契约监控（抓取校验） |
| **伪造接口** | 接口返回假数据（反爬） | 与页面数据对比验证 |

```python
# ═══ 接口热身（Cookie 依赖场景）═══
session = requests.Session()
session.get("https://example.com", timeout=10)     # 先访问拿 Cookie
session.headers["Referer"] = "https://example.com/list"
data = session.get("https://example.com/api/data", timeout=10).json()
```

> ⚠️ 接口直取的主要对手：**参数签名与数据加密**（反爬第四层）——遇到这两类，直取路线到头（阶段 7 逆向 or 渲染兜底）。**先确认"接口拿的是不是真数据"**（与页面对比），再批量。

## 6. 直取 vs 渲染：何时切换

```text
切换决策：
  接口直取失败的两类原因：
  ① 拿不到（签名/加密/Cookie 复杂）→ 渲染兜底
  ② 拿得到但数据不对（伪造/降级）→ 渲染验证/兜底

切换阈值（工程判断）：
  接口能直取 → 永远直取（性能压倒一切）
  接口需签名 → 评估逆向成本（阶段 7）vs 渲染成本
  接口加密 → 直接渲染（本阶段不逆向）
  渲染成本 > 数据价值 → 放弃/换源（阶段 4 §7）

混合架构（生产常见）：
  80% 页面接口直取（快） + 20% 渲染兜底（稳）
```

> 🎯 本章小结：**"接口直取 = 动态页的最优解"**——F12 五步定位 + 复刻请求 + 分页处理，覆盖 80% 动态页；遇到签名/加密才轮到渲染（03-05 章）。**先直取，后渲染**是本阶段的行动纲领。
