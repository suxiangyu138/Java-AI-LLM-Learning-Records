## 1. 为什么需要分布式：单机的三个瓶颈

| 瓶颈 | 表现 | 数据量级参考 |
|------|------|------------|
| CPU/IO | 单进程解析慢、下载慢 | 单机稳定 10-50 QPS 已需大量调优 |
| 带宽 | 下载带宽被单个出口吃满 | 1G 带宽理论上限 ~120MB/s |
| 被封 | 单 IP 高频请求触发风控（最现实） | 多数站点单 IP 每秒 1-10 请求封禁 |

> 🎯 **核心要点**：**分布式解决的核心问题不是"快"，而是"多 IP + 任务协同 + 断点续爬"**——多节点天然分散出口 IP（配合代理池），共享一个任务队列避免重复抓取，任何节点挂了任务不丢。单机没调优之前，先别谈分布式。

## 2. scrapy-redis 原理：换掉两个组件

scrapy-redis（0.7.3，2026 仍是最主流方案，但已停止维护）通过 **settings 替换两个组件**实现分布式：

```text
单机模式                          scrapy-redis 分布式模式
─────────────────────            ─────────────────────────────
Scheduler（内存队列）      →      Scheduler（Redis 列表：所有节点共享）
RFPDupeFilter（内存 Set）  →      RFPDupeFilter（Redis Set：全局去重）
```

```python
# settings.py —— 分布式改造的全部配置
SCHEDULER = "scrapy_redis.scheduler.Scheduler"          # ① 调度器换 Redis 版
DUPEFILTER_CLASS = "scrapy_redis.dupefilter.RFPDupeFilter"  # ② 去重器换 Redis 版
SCHEDULER_PERSIST = True          # ③ 爬完不清 Redis，任务保留
SCHEDULER_QUEUE_CLASS = "scrapy_redis.queue.FifoQueue"  # 队列类型（默认 PriorityQueue）
REDIS_URL = os.environ.get("REDIS_URL", "redis://:password@redis:6379/0")

# 增量相关（可选）
SCHEDULER_FLUSH_ON_START = False  # 启动时不清空 Redis（与 ③ 配合做增量）
SCHEDULER_IDLE_BEFORE_CLOSE = 10  # 队列空后等 10s 再关（多节点协同，防"假空"）
```

**工作机制**：

```text
节点 A ──┐
         ├── 同一个 Redis 实例 ──→ 任务队列(LIST) + 去重集合(SET)
节点 B ──┘        ↑                    ↑
                  └─ 任意节点 yield 的新请求 push 进队列 ──┘
                所有节点用 lpop/brpop 抢队列任务 → 天然负载均衡、天然去重
```

> 💡 为什么"替换两个组件"就够了：Scrapy 的组件边界清晰（01 章架构），调度与去重是唯一需要"全局共享"的状态；下载器、Spider、Pipeline 都是节点本地的，无需改造。**这就是"架构好，分布式只改配置"的原因**。

## 3. 配置清单与改造步骤

| 步骤 | 操作 | 说明 |
|:---:|------|------|
| 1 | `pip install scrapy-redis` | 0.7.3 |
| 2 | settings 替换 SCHEDULER / DUPEFILTER_CLASS | §2 四行配置 |
| 3 | `SCHEDULER_PERSIST = True` | 任务不丢 |
| 4 | Spider 改造：继承 `RedisSpider` | 起始 URL 从 Redis 注入，不再写死 start_urls |

```python
# spiders/redis_seeded.py —— 起始 URL 由 Redis 注入
from scrapy_redis.spiders import RedisSpider


class DistributedSpider(RedisSpider):
    name = "distributed"
    redis_key = "mycrawler:start_urls"      # 起始 URL 队列名

    def parse(self, response):
        yield {"url": response.url}
```

```bash
# 运维：往起始队列注入种子 URL（任一节点执行即可）
redis-cli lpush mycrawler:start_urls "https://example.com/seed/1"
# 任意节点启动爬虫（多台机器同一命令）
scrapy crawl distributed
```

> 🎯 **核心要点**：改造 = **替换 2 个组件 + 继承 1 个基类 + 持久化开关**。业务代码（parse/管道/中间件）一行不改——这就是 scrapy-redis 作为"最主流方案"的底气。

## 4. 断点续爬：任务持久化

```python
# 已在 §2 开启
SCHEDULER_PERSIST = True        # Redis 队列/去重集在爬虫关闭后保留
```

| 场景 | 行为 |
|------|------|
| 节点 A 崩溃/断电 | 任务还在 Redis，重启 `scrapy crawl` 继续抢队列 |
| 全量任务跑完 | 队列空 + 去重集保留 → 再启动不会重复抓（增量） |
| 需要重跑全量 | `SCHEDULER_FLUSH_ON_START = True` 清空再跑（或手动 del 键） |
| 队列空但可能"假空" | `SCHEDULER_IDLE_BEFORE_CLOSE=10` 等一会儿再关（多节点协同） |

> ⚠️ 断点续爬的边界（诚实说明）：scrapy-redis 持久化的是"**队列 + 去重集**"，**在途请求**（下载中/解析中）节点崩溃时会丢——靠重试机制逼近可靠性，做不到 100% 恰好一次（与 Kafka 等有语义差距）。对"丢几条可接受"的场景足够；对强一致场景看 §7 替代方案。

## 5. 去重优化：从 Set 到布隆过滤器

**内存真相**：RFPDupeFilter 在 Redis 里用 Set 存指纹，**约 1000 万 URL 消耗 2GB+ 内存**（每个指纹 ~200B 集合开销）。

| 方案 | 内存 | 代价 |
|------|:---:|------|
| Redis Set（默认） | 1000 万 ≈ 2GB+ | 零误判 |
| **布隆过滤器**（pybloom_live 等） | 1000 万 ≈ 100-200MB | 极小概率误判（会漏抓，可接受） |
| RedisBloom（模块） | 省内存 | **云 Redis 通常不支持**，自建 Redis 需装模块 |

```python
# 用布隆过滤器的去重器实现思路（替换 RFPDupeFilter）
class BloomDupeFilter:
    """基于 pybloom_live 的布隆去重器（内存占用降 10 倍+）"""
    def __init__(self, capacity=10_000_000, error_rate=0.001):
        self.bf = BloomFilter(capacity, error_rate)

    def request_seen(self, request):
        fp = request_fingerprint(request)      # 复用 scrapy 指纹
        if fp in self.bf:
            return True                        # 已见过
        self.bf.add(fp)
        return False
```

> ⚠️ 布隆过滤器的误判方向是"**见过说成见过**"（把没抓过的误判为已抓）→ 效果是**少量漏抓**。增量爬虫场景可接受；需要零漏抓就别用。内存与精度的权衡是 2026 分布式爬虫的经典面试题。

## 6. 队列消费优化与多节点部署

### 6.1 队列消费：lpop 轮询 vs brpop 阻塞

| 方式 | 行为 | 代价 |
|------|------|------|
| 默认（lpop 轮询） | 每 5 秒轮询一次队列 | 空转 Redis 连接、延迟感知慢 |
| 改造（brpop 阻塞） | 无任务时挂起等消息 | 即时响应、Redis 压力小 |

> 💡 生产可接受默认；任务到达不频繁、追求低延迟时改 brpop（参考 §8 坑位注意：改用 brpop 后需配套超时参数，否则节点间协同异常）。

### 6.2 多节点部署形态

```yaml
# docker-compose.yml —— 一个 Redis + N 个爬虫节点
services:
  redis:
    image: redis:8
    command: redis-server --requirepass ${REDIS_PASSWORD}
    volumes: ["redis-data:/data"]          # ⚠️ 持久化，防重启丢任务

  crawler:
    build: .
    depends_on: [redis]
    environment:
      REDIS_URL: redis://:${REDIS_PASSWORD}@redis:6379/0
    command: scrapy crawl distributed
    # 水平扩展：docker compose up -d --scale crawler=5
```

| 部署项 | 要点 |
|--------|------|
| Redis 持久化 | 必须 AOF/RDB（业务数据可再抓，**任务队列丢了就要从头来**） |
| 扩展方式 | `--scale crawler=5` / K8s Deployment replica=5 |
| 监控 | Redis `llen 队列键` = 待抓任务量（08 章监控指标） |
| 队列键名 | `项目名:requests`（调度队列）/ `项目名:dupefilter`（去重集） |

> 🎯 **核心要点**：分布式的最小闭环 = **Redis（状态中枢）+ N 个同镜像节点（无状态）**。节点无状态是关键——随便扩缩、随便重启，状态都在 Redis。

## 7. 维护状态与替代方案选型

### 7.1 scrapy-redis 的诚实评估（2026）

- **已停止维护**（社区共识，但仍是"最稳定可用"的分布式标准组件）；
- 与 Scrapy 2.14+ 异步现代化**没有冲突**（替换的只是调度/去重，2.14 API 不涉及）；
- 局限：任务失败只能靠 `RETRY_TIMES`，重试耗尽后**无失败队列**（"没人管"）；无任务状态追踪；强一致场景不够。

### 7.2 替代方案对比

| 方案 | 适用规模 | 状态管理 | 失败处理 | 成本 |
|------|:---:|:---:|------|:---:|
| **scrapy-redis** | 中小型 | 队列+去重集 | 重试，无失败队列 | 低 |
| **Celery + requests**（自研爬虫） | 中型 | 任务状态机完善 | 重试/死信/告警齐 | 中 |
| **Kafka + Celery** | 高并发 | 分区=并行度 | 消费组重平衡、可回放 | 高 |
| 云厂商爬虫服务 | 大型 | 平台托管 | 平台兜底 | 最高 |

**选型决策树**：

```text
任务量多大？
├─ < 百万级/天 → scrapy-redis（够用且简单，2026 主流）
├─ 百万级 + 需要任务状态/失败告警 → Celery + requests 自研
├─ 千万级 + 流式协同 → Kafka + Celery（或 Scrapy 节点 + Kafka 队列自研）
└─ 不想运维 → 云爬虫服务（Zyte Scrapy Cloud 等）
```

> 💡 **真实工程建议**：中小项目**继续用 scrapy-redis**（停止维护 ≠ 不能用，稳定运行多年、生态文档最全），把精力花在布隆去重、失败补偿、监控上；只有"任务状态管理"成为硬需求时才升级 Celery 路线。

## 8. 常见坑

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 1 | Redis 无持久化 | 重启后任务全丢 | AOF 开启 + 数据卷 |
| 2 | 节点时间戳类 URL | 每个节点生成不同 URL → 全局去重失效 | URL 清洗统一（01 章 §4.2） |
| 3 | 队列"假空"提前关闭 | 节点各自为政、尾部任务漏抓 | `SCHEDULER_IDLE_BEFORE_CLOSE` 调大 |
| 4 | 重试请求被全局去重 | 节点 A 重试的请求被节点 B 判重丢弃 | 重试时 `dont_filter=True` + 失败队列兜底 |
| 5 | Redis 连接风暴 | 节点多 + 轮询频繁 | brpop 改造 / 提高轮询间隔 |
| 6 | 云 Redis 布隆模块不可用 | 用 redisbloom 后报错 | 用纯 Python 布隆（pybloom_live） |
| 7 | 多节点管道重复入库 | 两个节点解析同一 URL 变体 | 数据层唯一键 + UPSERT（04 章 §3 两层幂等） |
| 8 | 把 scrapy-redis 当"银弹" | 部署复杂化、收益低 | 先单机调优（05 章），不够再上分布式 |

## 9. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 分布式 = 共享队列 + 全局去重 + 多节点抢占，本质是"多 IP + 协同" |
| 2 | scrapy-redis 改造 = 替换 Scheduler/DupeFilter 两组件 + RedisSpider + PERSIST |
| 3 | 断点续爬：PERSIST + FLUSH_ON_START 控制重跑语义 |
| 4 | Set 去重 1000 万 URL ≈ 2GB+，布隆过滤器省 10 倍内存（代价：少量漏抓） |
| 5 | 节点无状态 + Redis 持久化 + 水平扩展，是最小分布式闭环 |
| 6 | scrapy-redis 已停维护但稳定；任务状态强需求 → Celery/Kafka 路线 |
| 7 | 两层幂等：请求层全局去重 + 数据层唯一键，缺一不可 |
| 8 | 先单机调优再分布式——"多节点跑慢代码 = 多节点封 IP" |
