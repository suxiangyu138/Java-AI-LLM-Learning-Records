## 1. 部署方案全景与选型

| 方案 | 维护状态（2026） | 适合 | 成本 |
|------|----------------|------|:---:|
| **Scrapyd** | 低活跃维护（1.6.0，仍被官方文档列为热门选择） | 单机/少量机器轻量发布 | 低 |
| **Docker + 自管** | 生态成熟 | 团队项目、环境一致性强需求 | 中 |
| **Zyte Scrapy Cloud** | 官方云服务（Zyte 出品，与 Scrapyd 兼容） | 不想运维、企业级 SLA | 高 |
| **K8s（scrapyd-k8s / estela）** | 社区项目 | 已有 K8s 集群的大团队 | 高 |

**选型决策树**：

```text
有几个爬虫、几个人维护？
├─ 单人/小团队、单机 → Scrapyd（最快落地）
├─ 团队、多机、依赖复杂 → Docker + CI/CD
├─ 有 K8s 平台 → scrapyd-k8s（API 兼容 Scrapyd）或裸 Deployment + CronJob
└─ 预算充足不想运维 → Zyte Scrapy Cloud
```

> 🎯 **核心要点**：**部署的本质是"环境一致 + 可回滚 + 可观测"**。小项目用 Scrapyd 图省事，但"本地能跑、服务器不能跑"的坑只有 Docker 能根治——2026 年团队项目默认 Docker。

## 2. Scrapyd：轻量发布平台

### 2.1 安装与部署

```bash
pip install scrapyd scrapyd-client
scrapyd &                        # 启动服务（默认 6800 端口）
# 项目根目录配置 scrapy.cfg
```

```ini
# scrapy.cfg —— 声明部署目标
[deploy:prod]
url = http://crawler-server:6800/
project = quotes
```

```bash
scrapyd-deploy prod              # 打 egg 上传发布
curl http://crawler-server:6800/schedule.json -d project=quotes -d spider=quotes_spider
# 常用 API：daemonstatus / listprojects / listspiders / cancel / logs
```

| API | 用途 |
|-----|------|
| `daemonstatus.json` | 服务状态（运行中/待机/队列） |
| `schedule.json` | 启动 Spider |
| `cancel.json` | 取消运行 |
| `listjobs.json` | 任务状态（running/finished/pending） |
| `logs/` | 任务日志查看 |

### 2.2 安全与运维注意（2026 现状）

- **6800 端口绝不暴露公网**：无认证 API，任何人可 `schedule` 你的爬虫（等于 RCE 面）；
- 官方文档声明 Scrapyd 是"由部分 Scrapy 开发者维护"的轻量工具，**不是完整调度平台**（无资源隔离/跨机排队）；
- 生产建议：内网 + 反向代理限 IP + 用 `scrapydweb`/自研管理面板包一层。

> 💡 社区镜像 `EasyPi/docker-scrapyd`（scrapy 2.17.0 + scrapyd 1.6.0 + scrapyd-client 2.0.3）可直接 `docker compose up` 起一套，省去环境折腾——但**Docker 不会自动解决调度、重试、限速问题**，那些是业务层的事。

## 3. Docker 部署：环境一致性

```dockerfile
# Dockerfile
FROM python:3.14-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

# 非 root 运行（安全基线）
RUN useradd -m crawler && chown -R crawler /app
USER crawler

CMD ["scrapy", "crawl", "quotes_spider"]
```

```yaml
# docker-compose.yml（单机 + 定时 + 持久化）
services:
  crawler:
    build: .
    restart: unless-stopped            # 崩溃自动拉起（配合"不无脑重启"的告警判断）
    environment:
      - CRAWLER_MYSQL_PASSWORD=${CRAWLER_MYSQL_PASSWORD}   # 敏感信息走环境变量
      - REDIS_URL=${REDIS_URL}
    volumes:
      - ./jobdata:/app/jobdata         # 断点续爬数据持久化
      - ./logs:/app/logs               # 日志出容器
```

| Docker 化收益 | 说明 |
|--------------|------|
| 环境一致 | Python/系统库/lxml 编译产物全锁定 |
| 可回滚 | 镜像 tag = 版本号，`docker pull 旧tag` 即回滚 |
| 可扩展 | 07 章 `--scale crawler=5` 横向扩 |
| 依赖复杂 | Playwright 用 `mcr.microsoft.com/playwright/python` 基础镜像（预装浏览器） |

> ⚠️ 进程管理纪律：容器内**单进程**（一个爬虫一个容器/一个 task），别在容器里塞 systemd/supervisor；裸机则用 systemd 管理。且**不要无脑自动重启**——403 激增时重启只会继续被封（阶段 4 对抗升级代价）。

## 4. Kubernetes 部署（进阶）

| 方案 | 形态 | 要点 |
|------|------|------|
| 裸 Deployment | 常驻爬虫（增量循环） | 简单直接，用 K8s 探针做健康检查 |
| **CronJob** | 定时全量/增量 | 天然调度，`failedJobsHistoryLimit` 控制保留 |
| **scrapyd-k8s** | Scrapyd 兼容层 | 每个爬虫=一个 Job，API 兼容 6800 端口 |
| estela | 完整爬虫集群平台 | REST API + Web UI + Celery 队列，重但全 |

```yaml
# cronjob.yaml —— 每日增量爬取
apiVersion: batch/v1
kind: CronJob
metadata:
  name: quotes-daily
spec:
  schedule: "0 3 * * *"                # 每天 03:00
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: crawler
              image: registry/quotes-crawler:1.2.0
              args: ["crawl", "quotes_spider"]
              envFrom:
                - secretRef: {name: crawler-secrets}   # 密钥进 Secret
```

> 💡 K8s 的价值不在"跑爬虫"而在"**平台化**"：CronJob 调度、资源配额、监控（Prometheus）、日志（Loki/EFK）、回滚（镜像 tag）都是平台给的。没有这些诉求前，Docker Compose 完全够用。

## 5. 日志体系与 StatsCollection

### 5.1 日志分层

| 层 | 位置 | 内容 |
|----|------|------|
| 框架日志 | LOG_FILE / stdout | 请求/响应/错误（Scrapy 自带） |
| 业务日志 | Spider/Pipeline 里 `self.logger` | 解析异常、DropItem 原因、业务事件 |
| 统计 | 结束打印 / StatsCollector | 指标数值（§5.2） |

```python
# Spider/Pipeline 中规范打日志（不要用 print）
self.logger.info("开始解析列表页: %s", response.url)
self.logger.warning("详情页下载失败，待补抓: %s", url)   # 09 章增量队列
self.logger.error("解析异常: %s | %s", response.url, exc, exc_info=True)
```

### 5.2 关键统计指标（StatsCollection）

爬虫结束时自动打印，也是监控的数据源：

| 指标 | 含义 | 异常信号 |
|------|------|---------|
| `downloader/response_status_count/200` | 各状态码计数 | 403/429 突增 = 风控 |
| `item_scraped_count` | 成功产出 Item 数 | 骤降 = 解析规则失效 |
| `item_dropped_count` | 被 Pipeline 丢弃数 | 持续 >0 = 数据质量问题 |
| `dupefilter/filtered` | 去重丢弃请求数 | 异常高 = 可能误判/URL 清洗问题 |
| `downloader/request_bytes` | 下载流量 | 成本监控 |

> 🎯 **核心要点**：**统计 ≠ 监控**。统计是爬虫自己报的"体检报告"，监控是外部系统持续的"心电监护"——生产必须把关键指标（item_scraped_count 等）从日志解析出来喂给监控系统。

## 6. 监控与告警

```text
数据链路：Scrapy 日志 →（解析/采集）→ Prometheus → Grafana 面板 + Alertmanager 告警
         或 Loki/EFK：日志聚合 + LogQL 告警规则
```

**告警规则设计（按 08 章运维体系方法论）**：

| 规则 | 表达式思路 | 级别 |
|------|-----------|:---:|
| 爬取量为 0 | `item_scraped_count == 0` 且任务已结束 | P1 |
| 403/429 激增 | 429 占比 > 阈值 | P1（先停） |
| 错误率上升 | ERROR 日志计数 > 基线 × 2 | P2 |
| 任务卡死 | 运行时长 > 预期 × 2 | P2 |
| 数据库写入失败 | Pipeline 异常计数 > 0 | P1 |

> 💡 告警纪律：**先止血再定位**——触发"被风控"告警第一动作是暂停任务（手动/自动化），不是冲进去改代码。参考网络问题排查与中间件运维体系的"现象分级 P1 先止血"方法论。

## 7. 定时调度与增量任务

| 方式 | 适用 | 示例 |
|------|------|------|
| 系统 cron / CronJob | 固定时间点跑 | 每日 03:00 全量 |
| Scrapyd schedule API | Scrapyd 生态 | 外部 cron 调 schedule.json |
| APScheduler（代码内） | 需要动态调度逻辑 | 任务自身定时触发 |

**增量爬虫三要素**（与 04 章数据层呼应）：

1. **去重集保留**：`SCHEDULER_PERSIST = True`（07 章）或数据库唯一键判断；
2. **种子来源变化**：Redis 队列注入新 URL（07 章 `RedisSpider`）或读库查"未抓/待更新"列表；
3. **更新语义**：`ON DUPLICATE KEY UPDATE` + `updated_at`（04 章 §3）。

> ⚠️ 定时任务的**幂等**是硬要求：同一时刻重复触发（cron 重叠/手动重跑）不能造成数据重复——唯一键 + UPSERT + 去重集三保险齐上。

## 8. CI/CD 发布流水线

```yaml
# .github/workflows/deploy.yml —— 提交即构建，Tag 即发布
name: deploy-crawler
on:
  push:
    tags: ["v*"]                    # 打 tag 触发发布
jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: {python-version: "3.14"}
      - run: pip install -r requirements.txt && pip check   # 依赖一致性检查
      - run: python -m compileall spiders pipelines          # 语法门禁
      - run: pytest tests/ -q                                 # 单测门禁（09 章）
      - uses: docker/build-push-action@v6                    # 构建镜像
        with:
          push: true
          tags: registry/quotes-crawler:${{ github.ref_name }}  # 版本号=tag
      - run: |
          # 发布到服务器（SSH + docker compose pull && up -d）
          ssh ${{ secrets.HOST }} "cd /opt/crawler && \
            docker compose pull && docker compose up -d"
```

| 门禁 | 拦截什么 |
|------|---------|
| `pip check` | 依赖冲突 |
| `compileall` | 语法错误（上线必炸的错误提前暴露） |
| pytest | 解析规则回归（09 章 §2 最小测试） |
| 镜像 tag=git tag | 版本可追溯、可回滚 |

> 🎯 **核心要点**：CI/CD 对爬虫项目同样适用——**"改一行解析规则就上线"是事故温床**；先测试后发布、版本可回滚，是工程化的分水岭。发布成功标准：**任务被调度、请求正常、Item 入库、错误率正常**——不是"进程还在跑"。

## 9. 部署成功标准与常见坑

**上线检查清单（逐项打勾）**：

- [ ] 依赖锁定（requirements.txt / lock 文件），本地与服务器版本一致
- [ ] 敏感配置全部环境变量/密钥系统，代码零明文
- [ ] 任务队列/断点续爬数据持久化（容器卷 / Redis AOF）
- [ ] 日志输出位置统一，能检索
- [ ] 关键指标（item 数/错误数）接入监控
- [ ] 调度触发幂等（重复触发不重复入库）
- [ ] 回滚预案（镜像旧 tag / 代码旧版本）

| # | 坑 | 解法 |
|:---:|-----|------|
| 1 | 6800 公网裸奔 | 内网 + 限 IP |
| 2 | 依赖漂移"本地能跑" | Docker 化 + 锁定版本 |
| 3 | 日志进容器内层丢失 | 挂卷/stdout 采集 |
| 4 | 定时重叠重复入库 | 唯一键 + UPSERT + 锁 |
| 5 | 403 风暴还自动重启 | 告警先停，人工决策 |
| 6 | 监控只看"进程活着" | 看业务指标（item 数/错误率） |
| 7 | 密钥写进镜像 | 环境变量 / Secret，镜像内不落密钥 |

## 10. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 部署四方案：Scrapyd（轻量）/ Docker（团队默认）/ Zyte Cloud（托管）/ K8s（平台化） |
| 2 | Scrapyd 1.6.0 低活跃维护，6800 端口绝不公网 |
| 3 | Docker = 环境一致 + 镜像 tag 回滚；Playwright 用官方基础镜像 |
| 4 | 日志分层 + StatsCollection 关键指标；统计≠监控，指标要进外部系统 |
| 5 | 告警先止血（暂停）再定位；403 激增第一动作是停 |
| 6 | 增量三要素：去重集保留 + 种子可变 + UPSERT 更新语义 |
| 7 | CI/CD 门禁：依赖检查 + 语法 + 单测 + 版本化镜像 |
| 8 | 部署成功标准看"业务指标正常"，不是"进程还活着" |
