## 1. 为什么动态页必须在框架内解决

阶段 5 的结论是"接口直取优先，渲染兜底"。进入框架后，渲染必须**成为 Downloader 的一种形态**，否则：

| 手写 Selenium 脚本 + Scrapy | scrapy-playwright（框架内渲染） |
|------------------------------|-------------------------------|
| 浏览器流程在框架外，数据回流靠拼接 | 渲染后的页面就是 **Response**，走同一套回调/Pipeline |
| 无法复用去重/并发/中间件 | 请求级开关，静态页零开销，渲染页按需 |
| 并发与浏览器数量各管各的 | 框架并发模型统一管理 |
| 登录态/指纹自己折腾 | 上下文隔离 + 反检测内核可选 |

> 🎯 **核心要点**：scrapy-playwright 是一个 **Download Handler**（05 章 §7 的 2.14 新接口的实践者）——把 Playwright 浏览器渲染包装成"下载器的一种实现"，所以渲染页与其他请求**完全同构**：同样进回调、同样走 Pipeline、同样被去重。

## 2. 安装与配置：三个关键步骤

```bash
pip install scrapy-playwright        # 当前 0.0.48（2026-08）
playwright install chromium          # 下载浏览器内核
```

```python
# settings.py —— 三步配置缺一不可
DOWNLOAD_HANDLERS = {
    "http": "scrapy_playwright.handler.ScrapyPlaywrightDownloadHandler",
    "https": "scrapy_playwright.handler.ScrapyPlaywrightDownloadHandler",
}

# ⚠️ Playwright 是 asyncio 原生，必须切换到 asyncio reactor（01 章 §5）
TWISTED_REACTOR = "twisted.internet.asyncioreactor.AsyncioSelectorReactor"

# 可选：浏览器启动参数（反检测常用）
PLAYWRIGHT_LAUNCH_OPTIONS = {
    "headless": True,
    "args": ["--disable-blink-features=AutomationControlled"],   # 隐藏自动化标志
}
```

> ⚠️ 三件套漏配的后果：不配 DOWNLOAD_HANDLERS → 渲染不生效；不配 reactor → 启动即崩（`ReactorNotInstalledError`）；浏览器没 `playwright install` → 运行时报找不到 chromium。

## 3. 混合请求策略：按需开启渲染

**性能核心**：只有标记 `meta={"playwright": True}` 的请求才用浏览器，其余走原生下载器——**静态页绝不浪费浏览器资源**。

```python
import scrapy


class MixedSpider(scrapy.Spider):
    name = "mixed"
    start_urls = ["https://example.com/catalog"]

    def parse(self, response):
        """列表页是动态渲染的 → 开启浏览器"""
        for card in response.css("div.card"):
            detail_url = card.css("a::attr(href)").get()
            yield scrapy.Request(
                detail_url,
                callback=self.parse_detail,
                meta={"playwright": True},           # 只对详情页开渲染
            )

    def parse_detail(self, response):
        # 这里的 response 已经是 JS 渲染后的完整 DOM
        yield {
            "title": response.css("h1::text").get(),
            "price": response.css(".price::text").get(),
        }
```

**性能对比量级**（同一站点实测参考）：

| 请求类型 | 单请求耗时 | 内存占用 |
|---------|:---:|:---:|
| 原生下载器 | 50-200ms | ~0 |
| Playwright 渲染 | 1-5s | ~100MB/上下文 |

> 💡 **混合策略黄金法则**：**默认全原生，只给"确实需要 JS 的页面"开渲染**。判断法（阶段 5 §1）：接口直取能拿 → 用接口；HTML 里已有数据 → 原生；空壳 HTML + 接口加密 → 才渲染。

## 4. PageMethod：渲染前动作编排

需要"等元素、滚动、点按钮"才能拿全数据时，用 `PageMethod` 编排渲染后的浏览器动作：

```python
from scrapy_playwright.page import PageMethod

yield scrapy.Request(
    url="https://example.com/news",
    callback=self.parse_news,
    meta={
        "playwright": True,
        "playwright_page_methods": [
            PageMethod("wait_for_selector", "div.news-item"),   # 等列表出现
            PageMethod("evaluate", "window.scrollTo(0, document.body.scrollHeight)"),  # 滚到底
            PageMethod("wait_for_timeout", 2000),               # 等懒加载
            PageMethod("screenshot", path="debug/news.png", full_page=True),  # 调试留证
        ],
    },
)
```

| PageMethod | 典型场景 |
|-----------|---------|
| `wait_for_selector` | 核心内容异步加载完成 |
| `wait_for_timeout` | 固定等待（懒加载/动画） |
| `evaluate` | 执行 JS：滚动、点击"加载更多" |
| `screenshot` | 调试留证/质量抽检 |
| `route`（拦截） | 阻断图片/字体/统计请求，加速渲染（阶段 5 §5） |

> 🎯 **核心要点**：PageMethod 在**请求前编排、下载时执行**——爬虫代码里不需要任何"等渲染完再解析"的手动同步逻辑，渲染与解析仍是"请求 → 响应"的标准流程。

## 5. 多浏览器上下文与登录态

**上下文（context）≈ 独立的浏览器身份**：各自持有一份 Cookie/storage，互不干扰。

```python
# settings.py —— 启动时预定义两个上下文
PLAYWRIGHT_CONTEXTS = {
    "default": {},                      # 默认身份
    "user": {"storage_state": "state_user.json"},   # 带登录态的持久上下文
}
```

```python
# Spider —— 按请求选择身份
yield scrapy.Request(
    url="https://example.com/profile",
    callback=self.parse_profile,
    meta={"playwright": True, "playwright_context": "user"},   # 用"user"身份
)
```

| 场景 | 配置 |
|------|------|
| 单身份简单爬 | 默认上下文，不用配 |
| 多账号轮换 | 多个 named contexts，`PLAYWRIGHT_MAX_PAGES_PER_CONTEXT=1`（一页一身份） |
| 登录态持久化 | `storage_state`（Playwright 导出 JSON）复用会话 |
| 每请求新身份 | `playwright_context` 不指定 + `PLAYWRIGHT_MAX_PAGES_PER_CONTEXT` 控制 |

> ⚠️ **身份隔离是反爬的正确姿势**：多个请求共享一个上下文 = 共享一套 Cookie = 一损俱损。生产按"身份"划分上下文，比反复清 Cookie 干净得多。

## 6. PLAYWRIGHT_BROWSER_PROVIDER：camoufox 反检测内核

**2026 新增能力**（Zyte 官方博客重点介绍）：`PLAYWRIGHT_BROWSER_PROVIDER` 允许**替换浏览器生命周期来源**——不再只用补丁版 Chromium，可以接入任何 Playwright 兼容浏览器，官方例子是 **camoufox**（反指纹浏览器，隐藏自动化特征）。

```python
# settings.py
PLAYWRIGHT_BROWSER_PROVIDER = "camoufox"   # 反检测内核
PLAYWRIGHT_LAUNCH_OPTIONS = {"headless": True}
```

**反检测内核 vs 传统补丁**（阶段 5 §6 升级）：

| 手段 | 强度 | 说明 |
|------|:---:|------|
| 原生 Chromium + `--disable-blink-features` | 弱 | 可被 `navigator.webdriver` 等探针识别 |
| stealth 补丁（JS 抹除） | 中 | 补丁会留痕，强风控可测出 |
| **camoufox 反检测内核**（2026 推荐） | 强 | 指纹级伪装，无需 JS 补丁 |
| 远程 CDP（真浏览器农场） | 最强 | 最贵，`PLAYWRIGHT_CDP_URL` 接入 |

> 💡 反检测的态度不变（阶段 5 §6）：**先确认目标站是否有强风控再决定投入**——多数站点普通 UA + 随机延迟就够；只有大厂风控才值得上 camoufox 级方案。

## 7. 高级用法：拿回 Page 对象与拦截响应

```python
async def parse_hybrid(self, response):
    # meta["playwright_page"] 拿到真实 Page 对象（需 playwright_include_page=True）
    page = response.meta.get("playwright_page")
    try:
        if page is not None:
            # 可以继续执行浏览器操作后手动取数据
            html = await page.content()
            # 或直接拦截响应拿接口数据（阶段 5 的 route 思路）
            api_data = await page.evaluate("() => window.__DATA__")
            yield {"url": response.url, "api": api_data}
    finally:
        if page is not None:
            await page.close()   # ⚠️ 必须关闭，否则页面泄漏撑爆上下文上限
```

> ⚠️ 高级用法的纪律：**`playwright_include_page=True` 的请求，回调里必须负责关闭 page**（try/finally + errback 兜底）——泄漏页面会撞上 `PLAYWRIGHT_MAX_PAGES_PER_CONTEXT` 上限导致爬取卡死。90% 的需求用 PageMethod 就够，拿 Page 是少数定制场景。

## 8. 内存治理与常见坑

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 1 | 全站开渲染 | 内存暴涨、速度骤降 | 混合策略：只给需要 JS 的页面开（§3） |
| 2 | 页面泄漏 | 跑到一半卡死/崩溃 | include_page 必须 close；PageMethod 场景无需 include_page 就别开 |
| 3 | `MAX_PAGES_PER_CONTEXT` 撞顶 | 请求长时间无响应 | 合理设 `PLAYWRIGHT_MAX_PAGES_PER_CONTEXT`（默认 100），单页用完即关 |
| 4 | 并发过高 | 单机 OOM | 渲染请求的并发收敛：渲染页 `CONCURRENT_REQUESTS_PER_DOMAIN` 调小，约 100MB/上下文 |
| 5 | 忘了 reactor | `ReactorNotInstalledError` | TWISTED_REACTOR 必须配（§2 三件套） |
| 6 | 登录态失效 | 渲染页 302 到登录页 | storage_state 定期刷新；上下文按身份隔离 |
| 7 | 代理与渲染叠加 | 浏览器请求没走代理 | 渲染请求的代理用 `playwright_context_kwargs={"proxy": {...}}`（与 05 章代理中间件分工） |

> 💡 性能基线（2026 实测经验）：单机渲染并发 **2-4 个页面**比较稳（100MB+/上下文）；一批渲染请求之间加 `DOWNLOAD_DELAY` 随机化；**接口直取能解决的页面永远优先接口**——浏览器是最后的兜底，不是默认姿势。

## 9. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | scrapy-playwright（0.0.48）是 Download Handler：渲染页 = 普通 Response |
| 2 | 配置三件套：DOWNLOAD_HANDLERS + asyncio reactor + 浏览器安装 |
| 3 | 混合策略：meta playwright=True 按需开渲染，静态页零开销 |
| 4 | PageMethod 编排渲染前动作（等待/滚动/截图/拦截） |
| 5 | 多上下文 = 多身份，登录态 storage_state 持久化 |
| 6 | PLAYWRIGHT_BROWSER_PROVIDER（2026 新）可接 camoufox 反检测内核 |
| 7 | 页面必关、并发收敛、接口优先——渲染是兜底不是默认 |
| 8 | scrapy-splash 已停止维护，2026 一律用 scrapy-playwright |
