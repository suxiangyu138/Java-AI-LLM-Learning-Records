## 1. 两套回收机制

```text
   ┌──────────────────────────────────────────────────────┐
   │  机制一：引用计数（Reference Counting）—— 主力          │
   │  · 每个对象带 ob_refcnt 字段                           │
   │  · 归零立即释放，实时性好                               │
   │  · 缺陷：无法处理循环引用                               │
   └──────────────────────────────────────────────────────┘
                            ↓ 兜底
   ┌──────────────────────────────────────────────────────┐
   │  机制二：分代标记清除（Generational GC）—— 补充          │
   │  · 只处理「容器对象」（list/dict/set/自定义类实例）       │
   │  · 三代分代，按阈值触发                                 │
   │  · 专门解决循环引用                                     │
   └──────────────────────────────────────────────────────┘
```

| 维度 | CPython | JVM |
|------|---------|-----|
| 主机制 | 引用计数 | 可达性分析（GC Roots） |
| 辅助机制 | 分代标记清除（仅循环引用） | 分代复制 + 标记整理 |
| 回收时机 | **计数归零立即回收** | GC 触发时批量回收 |
| STW | 分代 GC 时有（很短） | 有（G1/ZGC 已很短） |
| 内存整理 | ❌ 不移动对象 | ✅ 压缩整理 |
| 是否可关 | ✅ `gc.disable()`（引用计数关不掉） | ❌ |
| 内存归还 OS | 部分（arena 空了才还） | 取决于收集器 |

> 💡 引用计数的最大优点是**确定性**：`with open(...)` 之外的 `f = open(...)`，只要 `f` 重新绑定，文件就立即关闭。JVM 里没有这种保证——这也是 Python 不那么依赖 `finally` 的原因（但仍然应该用 `with`）。

## 2. 引用计数详解

```python
import sys

a = []
print(sys.getrefcount(a))     # 2 —— 1 个来自 a，1 个来自 getrefcount 的参数（临时+1）

b = a
print(sys.getrefcount(a))     # 3

lst = [a]
print(sys.getrefcount(a))     # 4

del b
print(sys.getrefcount(a))     # 3
lst.clear()
print(sys.getrefcount(a))     # 2
```

引用计数变化的时机：

| +1 | -1 |
|----|-----|
| 对象被创建并绑定名字 | `del name` |
| 赋值给新名字 `b = a` | 名字重新绑定到别的对象 |
| 放入容器 `lst.append(a)` | 从容器中移除 |
| 作为参数传入函数（形参绑定） | 函数返回，栈帧销毁 |
| 成为对象属性 `obj.x = a` | 属性被删除/覆盖 |

```python
# 验证「归零立即释放」
class Tracked:
    def __del__(self): print("→ 已释放")

t = Tracked()
print("重新绑定前")
t = None                       # → 已释放（立即，不等 GC）
print("重新绑定后")
```

```python
# 函数返回时局部变量自动 -1
def f():
    x = Tracked()
    print("函数内")
f()                            # 函数内 → 已释放
```

> ⚠️ `sys.getrefcount()` 的返回值总比实际多 1（参数传递本身产生一次引用）。判断「有没有额外引用」时要记得减掉这个 1。

## 3. 循环引用与分代 GC

### 3.1 引用计数解决不了的问题

```python
import gc

class Node:
    def __init__(self, name): self.name, self.ref = name, None
    def __del__(self): print(f"释放 {self.name}")

a, b = Node("A"), Node("B")
a.ref = b          # A → B
b.ref = a          # B → A   形成环
del a, b           # 什么都没打印！refcnt 各自还是 1

print(gc.collect())   # 触发回收 → 释放 A / 释放 B
```

```text
   del a, b 之后：

   ┌─────────┐  ref   ┌─────────┐
   │ Node A  │ ─────→ │ Node B  │
   │refcnt=1 │ ←───── │refcnt=1 │
   └─────────┘  ref   └─────────┘
        ↑                  ↑
     外部已无引用，但互相引用使计数不为 0 → 引用计数无能为力
```

### 3.2 分代 GC 的工作方式

```text
   所有「可能含循环引用的容器对象」被登记到三个链表（代）：

   第 0 代（新生）  ── 阈值 700 次「分配-释放」差 → 触发
        │ 存活下来的晋升
        ▼
   第 1 代         ── 第 0 代回收 10 次 → 触发
        │ 存活下来的晋升
        ▼
   第 2 代（老年）  ── 第 1 代回收 10 次 → 触发（全量扫描，最慢）

   算法：标记-清除
   ① 对代内每个对象，把「代内引用」从 refcnt 副本里减掉
   ② 副本 refcnt > 0 的 → 有外部引用 → 存活（及其可达对象）
   ③ 剩下的都是纯内部循环 → 回收
```

```python
import gc
print(gc.get_threshold())      # (700, 10, 10)
print(gc.get_count())          # (各代当前计数)
gc.set_threshold(1000, 15, 15) # 可调（减少 GC 频率，代价是内存峰值升高）
```

哪些对象会被 GC 追踪：

```python
print(gc.is_tracked([]))       # True   容器
print(gc.is_tracked({}))       # True
print(gc.is_tracked(1))        # False  不可变标量，不可能形成环
print(gc.is_tracked("s"))      # False
print(gc.is_tracked((1, 2)))   # False  纯不可变元素的 tuple 会被「解除追踪」
print(gc.is_tracked(([],)))    # True   含可变元素
```

### 3.3 常见的循环引用来源

```python
# ① 双向链表 / 树的父子指针
class TreeNode:
    def __init__(self): self.parent, self.children = None, []
    def add(self, c): c.parent = self; self.children.append(c)   # 环

# ② 对象持有自己方法的引用（闭包/回调）
class Handler:
    def __init__(self):
        self.callback = self.on_event      # self → bound method → self
    def on_event(self): pass

# ③ 异常的 traceback 持有栈帧，栈帧持有局部变量
try:
    1 / 0
except ZeroDivisionError as e:
    tb = e.__traceback__       # 保存了 traceback → 整个调用栈的局部变量都活着
    # 3.x 里 except 块结束会自动 del e，但手动保存 tb 就会泄漏

# ④ 缓存装饰器持有 self
class Service:
    @functools.lru_cache(maxsize=128)      # ❌ 缓存 key 含 self → 实例永不释放
    def query(self, q): ...
```

> 🎯 结论：**循环引用不会造成永久泄漏（GC 能回收），但会延迟释放并增加 GC 负担**。真正的永久泄漏来自「全局容器/缓存里的强引用」——这是下面 §7 的重点。

## 4. gc 模块实操

```python
import gc

gc.collect()                  # 手动全量回收，返回回收的对象数
gc.collect(generation=0)       # 只回收第 0 代（快）

gc.disable()                   # 关闭分代 GC（引用计数仍工作）
gc.enable()
print(gc.isenabled())

gc.get_objects()               # 所有被追踪对象（很大，慎用）
gc.get_referrers(obj)          # 谁引用了 obj  ← 排查泄漏的关键
gc.get_referents(obj)          # obj 引用了谁

gc.set_debug(gc.DEBUG_LEAK)    # 打印无法回收的对象
gc.garbage                     # 无法回收的对象列表（现代 Python 里通常为空）
```

```python
# 找出「谁还引用着这个对象」——泄漏排查核心手法
import gc

class Target: pass
t = Target()
holder = {"key": t}
some_list = [t]

for ref in gc.get_referrers(t):
    if ref is not globals():
        print(type(ref), str(ref)[:60])
# <class 'dict'> {'key': <__main__.Target object at ...>}
# <class 'list'> [<__main__.Target object at ...>]
```

### 4.1 什么时候该关 GC

```python
# 场景：批量加载大量长生命周期对象（如加载百万条数据/构建大索引）
gc.disable()
try:
    data = load_millions_of_records()      # 期间不做无用的分代扫描
finally:
    gc.enable()
    gc.collect()                            # 结束后手动收一次
```

| 场景 | 建议 |
|------|------|
| 短命脚本 | 可 `gc.disable()`，进程退出即释放 |
| 批量构建大对象图 | 临时关闭，完成后 `enable + collect` |
| 长期运行的服务 | **保持开启**，关掉迟早 OOM |
| 延迟敏感的实时路径 | 用 `gc.freeze()`（3.7+）把启动期对象移出 GC 扫描范围 |

```python
# gc.freeze()：把已加载的模块/类等永久对象移到「永久代」，不再扫描
# 典型用于 fork 前（如 gunicorn preload），能显著降低 CoW 内存和 GC 开销
import gc
# ... 加载所有模块和模型 ...
gc.freeze()
# ... fork worker 进程 ...
```

## 5. 内存分配层级

CPython 不是每个对象都直接 `malloc`：

```text
   ┌─────────────────────────────────────────────┐
   │ 层 3：对象特化缓存                            │
   │  小整数池 [-5,256] / 字符串驻留 / 空 tuple      │
   │  list/dict/frame 的 freelist（复用已释放的壳）  │
   └─────────────────────────────────────────────┘
                       ↓ miss
   ┌─────────────────────────────────────────────┐
   │ 层 2：pymalloc（≤ 512 字节的小对象）            │
   │  Arena(1MB) → Pool(4KB) → Block(8~512B 按 8 对齐)│
   └─────────────────────────────────────────────┘
                       ↓ > 512 字节
   ┌─────────────────────────────────────────────┐
   │ 层 1：系统 malloc                             │
   └─────────────────────────────────────────────┘
```

```python
import sys
print(sys.getsizeof(0))            # 28   一个 int 的成本
print(sys.getsizeof(""))           # 49
print(sys.getsizeof([]))           # 56   空 list 的壳
print(sys.getsizeof([1,2,3]))      # 88   壳 + 3 个指针（8B 各）
print(sys.getsizeof({}))           # 64
print(sys.getsizeof(set()))        # 216

# getsizeof 只算「壳」，不递归算内容！
big = [[0]*1000 for _ in range(100)]
print(sys.getsizeof(big))          # 856  ← 严重低估
print(sum(sys.getsizeof(x) for x in big) + sys.getsizeof(big))   # 真实量级
```

```python
# list 的动态扩容策略（类似 Java ArrayList，但增长因子更小）
import sys
prev = 0
for i in range(20):
    lst = [0] * 0
    for _ in range(i): lst.append(0)
    size = sys.getsizeof(lst)
    if size != prev: print(f"len={len(lst)} size={size}")
    prev = size
# 容量按 0,4,8,16,25,35,46,58,72,88... 增长（约 1.125 倍 + 常数）
```

> ⚠️ **「内存不还给 OS」的真相**：pymalloc 只在整个 arena（1MB）完全空闲时才归还。大量小对象释放后，若碎片分布在多个 arena 里，RSS 不会下降。这不是泄漏，但在容器里会顶到内存 limit。对策：把大批量处理放到子进程里，进程退出时 OS 强制回收。

## 6. weakref 弱引用

弱引用**不增加引用计数**，因此不阻止对象被回收——这是打破循环引用和实现缓存的标准工具。

```python
import weakref

class Model:
    def __init__(self, name): self.name = name
    def __del__(self): print(f"释放 {self.name}")

m = Model("bert")
r = weakref.ref(m)                 # 弱引用
print(r(), r().name)               # <Model> bert     调用它取回对象
print(weakref.getweakrefcount(m))  # 1

del m                              # 释放 bert  ← 弱引用没阻止回收
print(r())                         # None       ← 对象已死，返回 None
```

```python
# ① WeakValueDictionary：值被回收则条目自动消失（缓存的正确姿势）
cache = weakref.WeakValueDictionary()
m = Model("gpt")
cache["gpt"] = m
print(list(cache.keys()))          # ['gpt']
del m                              # 释放 gpt
print(list(cache.keys()))          # []  ← 条目自动清理，不会泄漏

# ② WeakKeyDictionary：给第三方对象「挂」额外数据而不影响其生命周期
metadata = weakref.WeakKeyDictionary()
obj = Model("a")
metadata[obj] = {"created_at": "2026-07-28"}

# ③ 打破循环引用：子节点用弱引用指向父节点
class TreeNode:
    def __init__(self, name):
        self.name, self.children, self._parent = name, [], None
    @property
    def parent(self): return self._parent() if self._parent else None
    def add(self, child):
        child._parent = weakref.ref(self)      # ← 弱引用，不成环
        self.children.append(child)

# ④ finalize：比 __del__ 更可靠的清理钩子
def cleanup(name): print(f"清理 {name}")
m = Model("x")
weakref.finalize(m, cleanup, "x")   # m 被回收时调用 cleanup("x")
```

| 工具 | 用途 |
|------|------|
| `weakref.ref(obj)` | 基础弱引用，调用取值 |
| `weakref.proxy(obj)` | 透明代理，像对象本身一样用（属性访问直接透传） |
| `WeakValueDictionary` | **缓存**：值死了条目自动删 |
| `WeakKeyDictionary` | **附加元数据**：不影响 key 的生命周期 |
| `WeakSet` | 弱引用集合（观察者列表） |
| `weakref.finalize` | 可靠的终结回调，替代 `__del__` |

```python
# 观察者模式：用 WeakSet 避免「监听器泄漏」
class EventBus:
    def __init__(self): self._listeners = weakref.WeakSet()
    def subscribe(self, l): self._listeners.add(l)
    def emit(self, e):
        for l in list(self._listeners): l.on_event(e)
# 监听器对象被销毁后自动从总线移除，无需手动 unsubscribe
```

> 💡 `__slots__` 的类默认**不支持弱引用**，需要显式加上：`__slots__ = ("x", "__weakref__")`。

## 7. 内存泄漏排查

### 7.1 Python 泄漏的四种真实原因

| 原因 | 表现 | 定位手法 |
|------|------|---------|
| **全局容器只增不减** | 内存线性上涨 | `gc.get_referrers`、检查模块级 dict/list |
| **缓存无上限** | 阶梯上涨后平台 | 查 `lru_cache(maxsize=None)`、自建 dict 缓存 |
| **循环引用 + `gc.disable()`** | 缓慢上涨 | `gc.collect()` 后内存是否下降 |
| **C 扩展泄漏** | Python 层查不到 | `tracemalloc` 看不见，需 valgrind / 换版本 |

```python
# 典型泄漏 1：模块级容器
_ALL_SESSIONS = {}                       # ❌ 永远不清理
def create_session(uid):
    _ALL_SESSIONS[uid] = Session(uid)    # 内存单向增长

# ✅ 修复：加上限 + 过期
from cachetools import TTLCache
_ALL_SESSIONS = TTLCache(maxsize=10_000, ttl=3600)
```

```python
# 典型泄漏 2：lru_cache 装实例方法 → 缓存 key 含 self → 实例永生
class Embedder:
    @functools.lru_cache(maxsize=None)   # ❌ 双重问题：无上限 + 持有 self
    def embed(self, text): ...

# ✅ 修复 A：把缓存放到实例上
class Embedder:
    def __init__(self): self._cache = {}
    def embed(self, text):
        if text not in self._cache: self._cache[text] = self._compute(text)
        return self._cache[text]

# ✅ 修复 B：缓存无状态的模块级函数
@functools.lru_cache(maxsize=10000)
def _embed(text: str) -> tuple[float, ...]: ...
```

### 7.2 tracemalloc：定位分配点

```python
import tracemalloc

tracemalloc.start(25)                    # 保留 25 层调用栈

snap1 = tracemalloc.take_snapshot()
run_suspect_workload()
snap2 = tracemalloc.take_snapshot()

# 对比两个快照，按增量排序
for stat in snap2.compare_to(snap1, "lineno")[:10]:
    print(stat)
# app/cache.py:42: size=180 MiB (+180 MiB), count=1200000 (+1200000)

# 看某一处的完整调用栈
top = snap2.statistics("traceback")[0]
print("\n".join(top.traceback.format()))

cur, peak = tracemalloc.get_traced_memory()
print(f"当前 {cur/1e6:.1f}MB，峰值 {peak/1e6:.1f}MB")
tracemalloc.stop()
```

| `pympler` | 对象树汇总 | 中 | 递归算容器真实大小 |

### 7.4 排查流程

```text
   内存持续上涨
        │
        ├─ ① gc.collect() 后是否下降？
        │     是 → 循环引用积压：检查是否 gc.disable()，或调高阈值太激进
        │     否 → 继续
        │
        ├─ ② objgraph.show_growth() 找出增长的类型
        │
        ├─ ③ gc.get_referrers(样本对象) 找出持有者
        │     → 通常是模块级 dict / 缓存 / 事件监听列表
        │
        ├─ ④ tracemalloc 快照对比确认分配代码行
        │
        └─ ⑤ 若 Python 层完全查不到 → 怀疑 C 扩展（numpy/torch/驱动）
              → 用子进程隔离，或升级/更换扩展版本
```

## 8. 内存优化实践

```python
# ① __slots__：省掉每实例的 __dict__（详见 05 章）
class Point:
    __slots__ = ("x", "y")
    def __init__(self, x, y): self.x, self.y = x, y
# 100 万实例：普通类 ~180MB → __slots__ ~64MB（约省 60%）

# ② 生成器替代列表：常量内存
total = sum(len(line) for line in open("10GB.jsonl"))    # ✅ 流式
# total = sum(len(l) for l in open("10GB.jsonl").readlines())  # ❌ 全量入内存

# ③ array / numpy 替代 list 存数值
import array, sys
py_list = [i for i in range(1_000_000)]        # ~40MB（指针 + int 对象）
arr = array.array("i", range(1_000_000))       # ~4MB（紧凑 C 数组）
import numpy as np
np_arr = np.arange(1_000_000, dtype=np.int32)  # ~4MB + 向量化运算

# ④ 大量重复字符串 → 手动 intern
import sys
tags = [sys.intern(t) for t in load_tags()]    # 相同字符串共享一份内存

# ⑤ 分块处理，避免峰值
def batched_process(path, batch_size=1000):
    batch = []
    for line in open(path):
        batch.append(json.loads(line))
        if len(batch) >= batch_size:
            yield process(batch)
            batch.clear()                       # ← 复用列表对象
    if batch: yield process(batch)

# ⑥ 及时断开引用，让引用计数生效
def train():
    model = load_big_model()
    result = model.predict(data)
    del model                                   # 立即释放，不等函数结束
    return heavy_postprocess(result)            # 后续步骤内存峰值更低
```

| 数据规模 | 推荐结构 | 理由 |
|---------|---------|------|
| 少量异构对象 | `dataclass` | 可读性好 |
| 百万级同构对象 | `dataclass(slots=True)` / `NamedTuple` | 省 `__dict__` |
| 纯数值数组 | `array.array` / `numpy` | 紧凑存储 + 向量化 |
| 大表格数据 | `pandas` / `polars` / Arrow | 列式存储 + 零拷贝 |
| 超出内存的数据 | 生成器 / `mmap` / 分块读 | 常量内存 |
| 需要跨进程共享 | `multiprocessing.shared_memory` | 避免 pickle 拷贝 |

```python
# AI 场景：GPU 显存与 Python 内存是两码事
import torch, gc
del model                     # Python 对象引用断开
gc.collect()                  # 回收循环引用（PyTorch 模块图常有环）
torch.cuda.empty_cache()      # ← 必须显式调用，才把缓存块还给显卡
print(torch.cuda.memory_allocated() / 1e9, "GB")
print(torch.cuda.max_memory_allocated() / 1e9, "GB peak")
```

> ⚠️ **RSS 不降不等于泄漏**。判断标准是「持续增长且不收敛」。稳定在某个平台上的高内存是 arena 碎片 + 缓存，属正常现象；线性无上限上涨才是泄漏。

## 9. 核心要点回顾

- CPython **引用计数为主**（归零立即释放，确定性好）、**分代标记清除为辅**（只管循环引用）
- `sys.getrefcount()` 的返回值总比实际多 1
- 循环引用不会永久泄漏，但延迟释放并加重 GC；`__del__` + 循环引用在旧版本曾导致完全无法回收
- GC 只追踪**容器对象**；不可变标量和纯不可变 tuple 不被追踪
- 分代阈值默认 `(700, 10, 10)`；`gc.freeze()` 适合 fork 前把启动期对象移出扫描范围
- 分配三层：**对象缓存/freelist → pymalloc（≤512B）→ 系统 malloc**；arena 全空才归还 OS
- `sys.getsizeof` **不递归**，容器只算壳
- 真正的泄漏几乎都是「**全局容器/无上限缓存里的强引用**」，不是 GC 的锅
- `lru_cache` 装实例方法会让实例永生——AI 项目里的高频坑
- **weakref 是打破环和做缓存的正确工具**：`WeakValueDictionary` 做缓存，`WeakKeyDictionary` 挂元数据，`finalize` 替代 `__del__`
- 排查顺序：`gc.collect()` 试探 → `objgraph` 找类型 → `get_referrers` 找持有者 → `tracemalloc` 定位行
- 优化四板斧：`__slots__`、生成器流式、`array`/`numpy`、分块处理
- GPU 显存需 `del` + `gc.collect()` + `torch.cuda.empty_cache()` 三连
