## 1. Python 的设计哲学

### 1.1 Zen of Python

在解释器里执行 `import this` 会打印 19 条格言，这是 Tim Peters 写的 PEP 20。真正影响日常编码决策的是这几条：

| 原文 | 含义 | 落到代码上 |
|------|------|-----------|
| Explicit is better than implicit | 显式优于隐式 | 不用魔法全局变量；`from x import *` 是反模式 |
| Simple is better than complex | 简单优于复杂 | 能用函数别用类，能用类别用元类 |
| Flat is better than nested | 扁平优于嵌套 | 用 `continue`/提前 `return` 消除深层 `if` |
| Readability counts | 可读性很重要 | 变量名宁长勿短，`user_count` > `uc` |
| There should be one obvious way to do it | 应有一种显而易见的做法 | 与 Perl 的「TMTOWTDI」相反 |
| Errors should never pass silently | 错误不应静默传递 | 禁止裸 `except: pass` |
| Practicality beats purity | 实用胜过纯粹 | 所以有 `+=`、有 `str.join` 这种不太优雅的 API |

> 💡 Java 的哲学是「用类型系统和约束把错误挡在编译期」，Python 的哲学是「用可读性和约定让人写对」。前者靠编译器，后者靠人和工具链（lint/type checker/测试）。

### 1.2 鸭子类型（Duck Typing）

```python
# 「如果它走起来像鸭子、叫起来像鸭子，那它就是鸭子」
# Python 不关心对象的类型，只关心对象有没有需要的方法

class FileWriter:
    def write(self, s): print(f"[file] {s}")

class SocketWriter:
    def write(self, s): print(f"[socket] {s}")

def log(writer, msg):
    writer.write(msg)      # 不检查类型，只要求有 write 方法

log(FileWriter(), "hi")    # [file] hi
log(SocketWriter(), "hi")  # [socket] hi
```

对照 Java：Java 必须先定义 `interface Writer { void write(String s); }`，两个类都 `implements Writer`，函数签名才能写成 `log(Writer w, String msg)`。**Java 的接口是名义子类型（nominal），必须显式声明继承关系；Python 是结构化子类型（structural），有方法就行。**

Python 3.8 之后可以用 `typing.Protocol` 给鸭子类型加上静态检查，兼顾灵活与安全（详见 [10-类型系统](./10-类型系统与类型提示.md)）：

```python
from typing import Protocol

class Writable(Protocol):
    def write(self, s: str) -> None: ...

def log(writer: Writable, msg: str) -> None:   # mypy 能检查，运行时不强制
    writer.write(msg)
```

### 1.3 EAFP vs LBYL

这是 Python 与 Java 在错误处理上最大的风格差异。

| 风格 | 全称 | 思路 | 代表语言 |
|------|------|------|---------|
| **EAFP** | Easier to Ask Forgiveness than Permission | 先做，出错再处理 | Python（推荐） |
| **LBYL** | Look Before You Leap | 先检查，再做 | Java / C |

```python
# ❌ LBYL 风格：有竞态风险（检查后文件可能被删）
import os
if os.path.exists(path):
    with open(path) as f:
        data = f.read()

# ✅ EAFP 风格：Pythonic
try:
    with open(path) as f:
        data = f.read()
except FileNotFoundError:
    data = ""

# 字典取值同理
# ❌ if key in d: v = d[key]        两次哈希查找
# ✅ v = d.get(key, default)         一次
```

> ⚠️ EAFP 不等于「乱用异常」。异常在 Python 里是廉价的控制流手段（`StopIteration` 就是迭代终止信号），但仍不要用异常代替普通分支逻辑。

### 1.4 一切皆对象

```python
# 数字、函数、类、模块、甚至类型本身都是对象，都有 id/type/属性
print(type(1), type(int), type(type))       # <class 'int'> <class 'type'> <class 'type'>
print(type(len), type(lambda: 0))           # builtin_function_or_method / function

def f(): pass
f.author = "me"                             # 函数可以挂属性
print(f.author)                             # me

funcs = [len, str.upper, abs]               # 函数可放进容器
print([g("ab") if g is not abs else g(-1) for g in funcs])   # [2, 'AB', 1]
```

Java 里 `int` 是原始类型不是对象，方法不是对象（只能靠 `Method` 反射对象或 lambda 包装）。Python 没有这个割裂——**这是装饰器、高阶函数、元编程能存在的根本原因**。

## 2. 语言定位：动态强类型解释型

三个维度经常被混淆，逐个拆开：

| 维度 | Python | Java | 说明 |
|------|--------|------|------|
| **类型检查时机** | 动态（运行时） | 静态（编译期） | 变量无类型，对象有类型 |
| **类型转换严格度** | 强类型 | 强类型 | `1 + "a"` 直接报错（JS 是弱类型，会得到 `"1a"`） |
| **执行方式** | 解释执行字节码 | 编译成字节码 + JIT | 都有字节码，区别在 JIT |

```python
x = 1            # x 是「名字」，绑定到 int 对象
x = "hello"      # 重新绑定到 str 对象——变量本身没有类型
print(1 + "a")   # TypeError: 强类型，不做隐式转换
```

> 🎯 一句话记牢：**Python 的变量是「贴在对象上的标签」，Java 的变量是「装着值或引用的盒子」**。这个差别是理解赋值、传参、可变性的总钥匙（详见 [02-对象模型](./02-对象模型与数据模型.md)）。

## 3. 执行模型：从源码到字节码到 PVM

### 3.1 完整执行链路

```text
  hello.py（源码，UTF-8 文本）
      │
      │ ① 词法分析 Tokenize
      ▼
  Token 流（NAME/OP/NUMBER/NEWLINE...）
      │
      │ ② 语法分析 Parse（3.9+ 用 PEG 解析器，PEP 617）
      ▼
  AST 抽象语法树（可用 ast 模块查看）
      │
      │ ③ 编译 Compile
      ▼
  Code Object（字节码 + 常量表 + 变量名表）
      │  └── 缓存到 __pycache__/hello.cpython-312.pyc
      │
      │ ④ 求值循环 Eval Loop（ceval.c 里的巨型 switch）
      ▼
  PVM（Python Virtual Machine，栈式虚拟机）
      │
      ▼
  执行结果
```

```python
# 亲自看每一步
import ast, dis

src = "x = a + 1"
print(ast.dump(ast.parse(src), indent=2)[:200])   # ② AST
dis.dis(compile(src, "<s>", "exec"))              # ③④ 字节码
# LOAD_NAME    a
# LOAD_CONST   1
# BINARY_OP    +
# STORE_NAME   x
```

### 3.2 Code Object 与 pyc 缓存

```python
def add(a, b=1):
    c = a + b
    return c

co = add.__code__
print(co.co_varnames)     # ('a', 'b', 'c')   局部变量名（含参数）
print(co.co_consts)       # (None,)           常量表
print(co.co_argcount)     # 2                 位置参数个数
print(co.co_stacksize)    # 2                 需要的栈深度
print(co.co_flags)        # 67                标志位（是否生成器/协程等）
```

| 事实 | 说明 |
|------|------|
| `.pyc` 只是编译缓存 | 删掉不影响功能，只是下次启动稍慢 |
| 只对 `import` 的模块生成 | 直接 `python main.py` 的主模块不缓存 |
| 校验方式 | 默认比对源文件 mtime + size；也支持 hash 模式（PEP 552） |
| `.pyc` 不是保护 | `dis`/反编译器能还原，别当加密手段 |

### 3.3 为什么 Python 慢

| 原因 | 具体表现 | Java 对比 |
|------|---------|-----------|
| 逐条解释字节码 | 每条指令都要走 eval loop 分发 | JIT 编译成机器码 |
| 动态类型分派 | `a + b` 运行时才查 `__add__` | 编译期已知 `iadd` 指令 |
| 对象开销大 | 每个 int 28 字节，带 refcnt + type | 原始类型直接在栈上 |
| 无内联优化 | 函数调用要建栈帧 | JIT 会内联热点方法 |
| GIL 限制 | CPU 密集多线程无加速 | 真并行 |

Python 3.11 起的 Faster CPython 项目（PEP 659 自适应特化解释器）把常见操作提速 10-60%，3.13 加入实验性 JIT，但和 JVM 仍有量级差距。

> 🎯 工程结论：**Python 的定位是「胶水 + 上层编排」**。计算密集部分交给 NumPy / PyTorch（底层 C/CUDA），Python 只负责调度。这也是 AI 生态选 Python 的原因——慢的部分根本不在 Python 里跑。

## 4. Python 实现家族

| 实现 | 宿主语言 | 特点 | 适用场景 |
|------|---------|------|---------|
| **CPython** | C | 官方参考实现，有 GIL，生态最全 | 默认选它 |
| **PyPy** | RPython | 带 JIT，纯 Python 计算快 5-50× | 纯 Python 计算密集，C 扩展兼容性差 |
| **GraalPy** | Java (GraalVM) | 跑在 JVM 上，能互调 Java | Java 系统里嵌 Python |
| **Jython** | Java | 老牌 JVM 实现，停留在 Py2.7 | 已不建议新项目使用 |
| **IronPython** | C# | .NET 平台 | .NET 集成 |
| **MicroPython** | C | 极简，几百 KB | 嵌入式 / 单片机 |

```bash
# 查看当前实现
python -c "import platform; print(platform.python_implementation(), platform.python_version())"
# CPython 3.12.4
```

> ⚠️ 「Python 慢」严格说是「CPython 慢」。但 NumPy/PyTorch 等库依赖 CPython 的 C-API，PyPy 上往往跑不动或没优势，所以 AI 领域基本锁定 CPython。GraalPy 值得 Java 后端关注——它能在同一个 JVM 进程里让 Java 调 Python（详见 [05-Python与Java联动实战](../05-Python与Java联动实战.md)）。

## 5. PEP 流程与版本演进

**PEP**（Python Enhancement Proposal）是 Python 的特性提案机制，所有语言变更都必须先过 PEP。

| PEP | 主题 | 为什么该知道 |
|-----|------|-------------|
| PEP 8 | 代码风格指南 | 事实标准，black/ruff 都以它为基准 |
| PEP 20 | Zen of Python | 设计哲学 |
| PEP 257 | Docstring 约定 | 文档规范 |
| PEP 484 | 类型提示 | 类型注解的起点 |
| PEP 492 | async/await | 协程语法 |
| PEP 572 | 海象运算符 `:=` | 3.8 争议特性 |
| PEP 634 | 结构化模式匹配 `match` | 3.10 |
| PEP 703 | 可选禁用 GIL | 3.13 起，Python 未来的分水岭 |

### 5.1 版本节奏

```text
每年 10 月发一个大版本（3.x），支持周期 5 年
  ├── 前 2 年：bugfix（发小版本 3.x.y）
  └── 后 3 年：仅安全修复

3.8  (2019) │ 海象运算符、位置限定参数 /、f-string 的 =
3.9  (2020) │ dict 合并 | 、PEG 解析器、内置泛型 list[int]
3.10 (2021) │ match 语句、X | Y 联合类型、更好的报错信息
3.11 (2022) │ 提速 10-60%、异常组、Self 类型
3.12 (2023) │ PEP 695 类型参数语法、f-string 放宽、子解释器
3.13 (2024) │ free-threading（实验）、JIT（实验）、新 REPL
3.14 (2025) │ 延迟注解求值（PEP 649）、free-threading 转正式支持
```

> 💡 生产环境选版本的经验法则：**发布 6-12 个月后的版本**（等主流库补齐 wheel）。写业务代码用 3.11/3.12 是当下稳妥选择；AI 项目要额外确认 PyTorch/CUDA 的支持矩阵。

## 6. 核心要点回顾

- Python 哲学的落脚点：**可读性优先、显式优于隐式、一种显而易见的做法**
- **鸭子类型**是结构化子类型，靠「有没有这个方法」而非「继承自谁」；`Protocol` 给它补上了静态检查
- **EAFP**（先做再捕获）是 Python 的地道错误处理风格，异常在这里是廉价的控制流
- 一切皆对象——函数、类、模块都是一等公民，这是元编程能力的根源
- 执行链路：**源码 → Token → AST → Code Object（.pyc） → PVM 求值循环**
- 慢的根因是**逐条解释 + 动态分派 + 对象开销**，解法是把热点交给 C 扩展
- CPython 是默认选择；「Python 慢」准确说是「CPython 慢」
- 所有语言特性变更都走 **PEP**，每年 10 月发版，支持 5 年
