## 1. 多工具协同架构

### 1.1 2026 典型协同栈

```text
多工具协同全景（2026）
┌─────────────────────────────────────────────┐
│ 数据科学/AI 项目                             │
│   conda（环境 + CUDA/原生依赖）               │
│     └── uv（纯 Python 包，快 10-100 倍）      │
├─────────────────────────────────────────────┤
│ 纯 Python 项目                               │
│   uv（一切：环境 + 依赖 + 运行）               │
├─────────────────────────────────────────────┤
│ 库项目（发布 PyPI）                          │
│   uv 或 Poetry（锁文件 + 发布）               │
├─────────────────────────────────────────────┤
│ 全局 CLI 工具                                │
│   uv tool install / pipx                     │
└─────────────────────────────────────────────┘
```

### 1.2 工具职责边界

| 工具 | 只管什么 | 不碰什么 |
|------|---------|---------|
| **conda** | 环境 + Python 版本 + 原生二进制 | 纯 Python 包的日常管理 |
| **uv** | 环境 + 依赖解析 + 锁文件 + 运行 | 系统级原生依赖 |
| **pipx** | 全局 CLI 隔离 | 项目依赖 |
| **venv** | 兜底创建环境 | 依赖解析 |

> 🎯 **协同原则**：**每层用最合适的工具，接口（pyproject.toml/environment.yml）标准化**——工具之间通过标准配置文件对话。

## 2. CI 流水线实践

### 2.1 GitHub Actions + uv

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # 安装 uv（官方 action）
      - uses: astral-sh/setup-uv@v3

      # 严格按锁文件同步（确定性构建）
      - name: Sync dependencies
        run: uv sync --frozen --no-dev

      # 质量检查
      - name: Lint
        run: uv run ruff check .

      # 测试
      - name: Test
        run: uv run pytest
```

### 2.2 CI 提速收益

```text
uv 在 CI 的价值
├── 构建时间缩短 30-90 秒（缓存复用）
├── --frozen 保证确定性（同锁文件同结果）
├── 缓存策略：uv cache 可跨流水线持久化
└── 多 Python 版本测试：
    uv python install 3.10 3.11 3.12 3.13
    uv run --python 3.10 pytest
```

### 2.3 conda 项目的 CI

```yaml
# conda 项目 CI 要点
steps:
  - uses: conda-incubator/setup-miniconda@v3
    with:
      environment-file: environment.yml   # 按 yml 复现
      python-version: "3.10"
  - name: Run tests
    run: |
      conda activate ml-project
      pytest
```

> 💡 **CI 原则**：环境构建必须**完全从锁文件/环境文件**出发（`--frozen` / `environment-file`），禁止在 CI 里重新解析依赖。

## 3. Docker 镜像最佳实践

### 3.1 推荐：uv 构建

```dockerfile
# Dockerfile（Python 项目 + uv 推荐方案）
# ① 多阶段：用 uv 镜像构建依赖层
FROM ghcr.io/astral-sh/uv:latest AS builder
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project

# ② 运行镜像：复制依赖层（体积小、缓存命中）
FROM python:3.13-slim
WORKDIR /app
ENV PATH="/app/.venv/bin:$PATH"
COPY --from=builder /app/.venv .venv
COPY . .
CMD ["python", "app.py"]
```

### 3.2 容器内三条铁律

```text
Docker 内 Python 环境铁律
├── ① 容器内用虚拟环境（uv 推荐），不要全局 pip install
│   → 现代基础镜像会拒绝全局 pip（PEP 668 externally-managed）
├── ② 不要在应用容器内用 conda
│   → 体积大、构建慢、层缓存差
├── ③ 依赖层独立 COPY
│   → 依赖不变时利用 Docker 层缓存（构建提速）
```

### 3.3 对比

| 方案 | 镜像体积 | 构建速度 | 可复现 | 推荐 |
|------|:---:|:---:|:---:|:---:|
| uv + venv | 小 | 快 | ✅ | ✅✅ |
| pip + requirements | 中 | 中 | 弱 | 一般 |
| conda | 巨大 | 慢 | 中 | ❌ |

> 🎯 **结论**：容器内 `uv sync --frozen --no-dev` + 复制 `.venv` 是 2026 年标准做法。

## 4. 迁移路径大全

### 4.1 四种迁移路线

```text
① requirements.txt → uv（最常见）
   uv init
   uv add -r requirements.txt
   uv sync

② Poetry → uv（现有健康项目不必迁）
   uvx migrate-to-uv        # 官方迁移助手
   # 或将 [tool.poetry.dependencies] 转为 [project] 依赖数组

③ Pipenv → uv（Pipenv 已维护模式）
   pipenv requirements > requirements.txt
   # 然后按 ① 迁移（不要绕道 Poetry）

④ conda → uv（纯 Python 部分）
   conda list --export
   # 手工筛选纯 Python 包 → uv add
   # 注意：原生依赖（CUDA 等）仍留 conda
```

### 4.2 迁移决策矩阵

| 现状 | 迁移？ | 路径 |
|------|:---:|------|
| venv + requirements.txt | ✅ | 直接迁 uv |
| Poetry（CI 正常） | ❌ | 保持 |
| Pipenv | ✅ | Pipenv → uv（绕开 Poetry） |
| conda（有原生依赖） | ⚠️ 部分 | conda 留原生 + uv 装纯 Python |
| conda（纯 Python） | ✅ | 迁 uv |

> ⚠️ **迁移黄金法则**：工具迁移的唯一理由是解决实际问题（速度/可复现/维护状态），不是追新。

## 5. Git 与团队协作规范

### 5.1 .gitignore 规范

```gitignore
# Python 项目 .gitignore 核心条目
.venv/               # 虚拟环境（绝不提交）
__pycache__/         # Python 缓存
*.pyc
.pytest_cache/
.ruff_cache/
*.egg-info/
build/
dist/

# 必须提交（反面清单）
uv.lock              # ✅ 锁文件必须提交
pyproject.toml       # ✅ 配置必须提交
environment.yml      # ✅ conda 环境文件必须提交
```

### 5.2 团队协作规范

```text
团队 Python 环境协作五规范
├── ① 新人上手三步：git clone → uv sync → uv run pytest
├── ② 依赖变更流程：uv add pkg（锁文件自动更新）→ 提交 pyproject + uv.lock
├── ③ 禁止手动改锁文件（一致性破坏）
├── ④ CI 强制 --frozen（锁文件过期即失败）
└── ⑤ 环境问题优先看锁文件差异（不是重装）
```

### 5.3 版本兼容矩阵

```yaml
# 项目环境声明（README 推荐写法）
Python: >=3.10（推荐 3.12/3.13）
工具: uv >= 0.4
复现: git clone && uv sync --frozen
```

## 6. 常见故障排查

| # | 症状 | 根因 | 解法 |
|---|------|------|------|
| 1 | `python` 还是系统版 | 未激活/激活失败 | `which python` 检查；用 `uv run` |
| 2 | 包装在别处 | PATH 顺序错 | 重新激活；确认 pip 来自 .venv |
| 3 | conda 里 pip 包消失 | conda 覆盖了 pip 包 | 遵守先 conda 后 pip；pip 包入 environment.yml |
| 4 | 锁文件报过期 | pyproject 改了未 lock | `uv lock` 后提交 |
| 5 | PEP 668 externally-managed | 全局 pip install 被拒 | 用虚拟环境（uv sync） |
| 6 | .venv 拷到别的机器报错 | home 绝对路径失效 | 删除重建（秒级） |
| 7 | Docker 构建慢 | 依赖层未独立 | 依赖 COPY 独立层（见 3.1） |
| 8 | 网络受限装不上 | 内网无 PyPI 访问 | 配置内部索引（UV_INDEX_URL） |

### 6.1 排查万能三步

```text
环境问题万能排查
├── ① 我在哪？which python / conda env list
├── ② 装的什么？pip list / uv pip list
└── ③ 和锁文件一致吗？uv sync --frozen（自动修复差异）
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 协同架构：conda 管原生依赖 + uv 管 Python 包 + pipx 管 CLI——每层用最合适的工具
> 2. CI 铁律：`uv sync --frozen` 确定性构建（提速 30-90 秒）；conda 项目按 environment-file 复现
> 3. Docker 三铁律：容器内用 venv（uv 推荐）、不用 conda、依赖层独立 COPY
> 4. 迁移四路径 + 黄金法则（解决实际问题才迁）；锁文件提交 Git、.venv 永不提交
