## 1. Provider 生态与统一模型字符串

> 🎯 **1.x 用统一字符串格式 `provider:model` 指定模型**——无需先 import 对应包即可切换厂商（跨厂商迁移零代码改动）。

```python
from langchain.agents import create_agent

# 统一模型字符串（2026 常见写法）
agent = create_agent(
    model="openai:gpt-5.5",                      # OpenAI
    tools=[...],
)
agent = create_agent(model="anthropic:claude-sonnet-4-6", tools=[...])  # Anthropic
agent = create_agent(model="google_genai:gemini-3.5-flash", tools=[...])  # Google
agent = create_agent(model="deepseek:deepseek-chat", tools=[...])       # DeepSeek
agent = create_agent(model="ollama:north-mini-code-1.0", tools=[...])   # 本地 Ollama
agent = create_agent(model="openrouter:z-ai/glm-5.2", tools=[...])      # 聚合平台
```

**Provider 集成方式对比**：

| 方式 | 适用 | 说明 |
|------|------|------|
| 独立包 `langchain-openai` | 常规项目 | `ChatOpenAI(model="gpt-5.5")`，显式 import |
| 统一字符串 `openai:gpt-5.5` | create_agent 场景 | 字符串即配置，可存于 yaml/env |
| `langchain-community` | 小众/自建服务 | 0.4 独立版本，社区维护 |
| OpenAI 兼容端点 | 本地推理（vLLM/Ollama） | `base_url` 指向本地服务 |

```python
# 本地模型（Ollama/vLLM 走 OpenAI 兼容协议）
from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model="qwen3:32b",
    base_url="http://localhost:8000/v1",  # vLLM 兼容端点
    api_key="EMPTY",                       # 本地无需密钥
)
```

> 💡 **环境变量优先**：`OPENAI_API_KEY` / `ANTHROPIC_API_KEY` / `DEEPSEEK_API_KEY` 等——密钥放环境变量，绝不写进代码。

## 2. ChatModel 与消息抽象

> 🎯 **一切对话皆消息**——模型输入输出都是消息列表，消息类型决定「谁在说话」。

```python
from langchain_core.messages import (
    SystemMessage,     # 系统指令（设定角色/规则）
    HumanMessage,      # 用户输入
    AIMessage,         # 模型回答（含 tool_calls）
    ToolMessage,       # 工具返回结果（对应 tool_call_id）
    HumanMessageChunk, # 流式分片（消息的 chunk 类型）
)

messages = [
    SystemMessage(content="你是资深 Java 架构师"),
    HumanMessage(content="如何设计高可用订单系统？"),
]
response = model.invoke(messages)  # → AIMessage
print(response.content)            # 文本回答
```

**消息模型的要点**：

```text
消息序列语义（工具调用闭环）
├── user → ai(tool_calls) → tool(tool_message_content) → ai(最终回答)
├── 每个 ToolMessage 必须带 tool_call_id 对应 AI 的工具调用
└── 1.x 结构化输出可定制 tool_message_content（默认显示结构体数据）

⚠️ 常见错误
├── 忘记传历史消息 → 模型「失忆」
├── ToolMessage 缺 tool_call_id → 工具结果无法关联
└── 消息顺序错乱 → 模型理解偏差（System 必须最前）
```

## 3. ChatPromptTemplate 消息模板

> 🎯 **模板 = 消息的工厂**——把「固定结构 + 变量注入」分离，是 Prompt 工程落地的基本单元。

```python
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是{role}专家，请用中文回答"),
    MessagesPlaceholder("history"),        # ← 历史消息占位（对话记忆）
    ("user", "{question}"),
])

# 渲染检查
prompt.invoke({"role": "RAG", "history": [], "question": "什么是向量检索？"})
```

**MessagesPlaceholder 两种用法**：

| 用法 | 写法 | 场景 |
|------|------|------|
| 历史消息 | `MessagesPlaceholder("history")` | 多轮对话插入历史 |
| 任意消息变量 | `MessagesPlaceholder("messages", optional=True)` | Agent 全消息流 |

**Few-shot 注入**（示例化，比纯指令更有效）：

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", "把用户描述转成 SQL，只输出 SQL"),
    ("user", "查所有订单金额超过 100 的客户名"),
    ("ai", "SELECT DISTINCT c.name FROM customers c JOIN orders o ON c.id = o.customer_id WHERE o.amount > 100;"),
    ("user", "{question}"),
])
```

> ⚠️ **Prompt 是迭代出来的，不是设计出来的**——先跑基线，再用 LangSmith 对比各版本效果；少写"请务必准确回答"类废话指令，多用示例和格式约束。

## 4. bind_tools 工具绑定

> 🎯 **工具调用（function calling）是 Agent 能力的地基**——`bind_tools` 把工具 schema 注入模型，模型在回答中声明要调用哪个工具。

```python
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询城市天气（city: 城市名，返回温度与天气状况）"""
    return f"{city}：25°C，晴"

model_with_tools = model.bind_tools([get_weather])

response = model_with_tools.invoke("上海天气如何？")
response.tool_calls
# → [{'name': 'get_weather', 'args': {'city': '上海'}, 'id': 'call_xxx'}]
```

**工具定义的三要素**：

```text
@tool 的隐藏约定
├── ① docstring → 模型的「触发说明书」（最重要！写清何时用、参数含义）
├── ② 类型注解 → 参数 schema 来源（Pydantic 自动生成）
├── ③ 返回值 → 字符串或结构体（作为 ToolMessage 返回模型）
└── 金句：工具写得像人话，模型才调得准
```

> ⚠️ **绑定 vs 注册**：`bind_tools` 只是让模型「会声明调用」；真正执行工具并回填结果需要 Agent 循环（create_agent）或手写循环——LCEL 链里 `bind_tools` 后要自己处理 `tool_calls` 分发。

## 5. 结构化输出：response_format

> 🎯 **1.x 结构化输出在主循环内直接生成**——无需额外 LLM 调用（比 0.x 省一次调用成本），且与 Agent 无缝集成。

```python
from pydantic import BaseModel
from langchain.agents import create_agent

class Answer(BaseModel):
    summary: str        # 摘要
    confidence: float   # 置信度 0-1

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[...],
    response_format=Answer,          # ← Pydantic 即 schema
)
result = agent.invoke({"messages": [{"role": "user", "content": "总结 AI 趋势"}]})
result["structured_response"]  # → Answer(summary="...", confidence=0.92)
```

**三种策略（ProviderStrategy 自动选择）**：

| 策略 | 机制 | 适用 |
|------|------|------|
| `ProviderStrategy`（默认） | 模型原生结构化输出（如 OpenAI JSON schema / Anthropic tool） | 主流厂商，质量最高 |
| `ToolStrategy` | 用工具调用来"逼"出结构体 | Provider 不支持原生结构化时 |
| 自动策略 | 按模型能力自动挑选以上两者 | 多厂商切换时兜底 |

```python
# 显式指定策略（跨厂商场景保证一致性）
from langchain.agents.structured_output import ProviderStrategy

create_agent(
    model="...",
    response_format=ProviderStrategy(
        schema=my_schema_dict,   # dict 形式 JSON Schema
        strict=True,             # 严格模式：字段必填/类型强约束
    ),
)
```

> 💡 **strict=True 的代价**：严格模式保证字段完整，但会降低模型自由度（部分模型在复杂嵌套结构下会失败重试）——非关键字段放宽到 optional。

## 6. ContentBlocks 与推理输出

> 🎯 **1.x 统一输出结构**：模型返回的 content 由多个 ContentBlock 组成——自动区分 **reasoning（推理过程）** 与 **text（最终回答）**，推理过程不再靠"猜格式"。

```python
response = model.invoke("1+1=?")

# content 是块列表（Block 类型：text / reasoning / tool_call 等）
for block in response.content:
    if block.type == "reasoning":
        print("🧠 推理:", block.reasoning)   # 模型内部推理链
    elif block.type == "text":
        print("💬 回答:", block.text)         # 最终答案
```

**ContentBlocks 的应用场景**：

```text
├── ① 推理可见：多步推理中间过程展示（debug/审计）
├── ② 成本控制：reasoning 也计 token——公开「深度思考」模型时注意
├── ③ 输出解析：text 块进下游链，reasoning 块单独处理（如存日志）
└── ④ StringOutputParser：默认取第一个 text 块 → 兼容旧代码
```

> ⚠️ **不要给模型施压"不要输出思考过程"**——DeepSeek/Claude 等模型的思考链是质量来源，1.x 推荐用 ContentBlocks 正常消费而非屏蔽。

## 7. 输出解析器

| 解析器 | 输入 → 输出 | 场景 |
|--------|------------|------|
| `StrOutputParser` | AIMessage → str | 最常见，取 text 内容 |
| `PydanticOutputParser` | AIMessage → Pydantic | 旧式结构化输出（0.x 兼容） |
| `JsonOutputParser` | AIMessage → dict | JSON 提取/校验 |
| `CommaSeparatedListOutputParser` | AIMessage → list | 列表式输出 |
| 自研 parser | 任意 → 任意 | 后处理（清洗/校验） |

```python
from langchain_core.output_parsers import StrOutputParser, JsonOutputParser

# LCEL 管道中的解析器
chain = prompt | model | StrOutputParser()      # 最终 str
json_chain = prompt | model | JsonOutputParser() # 最终 dict

# 解析失败策略（重要边界）
# ① 模型输出不合法 JSON → 抛 OutputParserException
# ② 兜底：with_fallbacks 切换到宽松链
safe_chain = (prompt | model | JsonOutputParser()
              ).with_fallbacks([prompt | model | StrOutputParser()])
```

> ⚠️ **1.x 新代码优先 `response_format`（在主循环内生成结构体），解析器主要用于 LCEL 链的轻量格式转换**——两者不冲突，按场景选。

## 8. 调用参数与边界

```python
from langchain_openai import ChatOpenAI

model = ChatOpenAI(
    model="gpt-5.5",
    temperature=0.2,          # 0=确定，1=创造；代码/提取用 0-0.3，创意用 0.7+
    max_tokens=2048,          # 输出上限（防失控；长文分页生成）
    timeout=60,               # 请求超时（生产必配）
    max_retries=2,            # SDK 层重试
)
```

**参数权衡表**：

| 参数 | 调低 | 调高 | 边界坑 |
|------|:---:|:---:|------|
| temperature | 事实性任务 | 创意任务 | 部分模型不支持（gemini 系列忽略） |
| max_tokens | 省成本 | 长回答 | 超限被截断——无提示直接断尾 |
| timeout | 快速失败 | 大请求 | 流式场景 timeout 计算方式不同 |
| max_retries | 少等待 | 高可用 | 只对可重试异常有效 |

> 💡 **Token 成本核算**：LangSmith 自动记录每次调用的 token——生产环境按 trace 聚合做成本看板；`with_llm_usage()` 可在代码层取用量。

## 9. 核心要点

> 🎯 **核心要点**：
> 1. **统一模型字符串** `provider:model`——跨厂商零改动切换
> 2. **消息模型**是对话的基础：System/User/AI/Tool 四类消息闭环
> 3. **ChatPromptTemplate** 模板化 Prompt，MessagesPlaceholder 管理历史
> 4. **bind_tools** 给模型「工具声明能力」，docstring 决定触发率
> 5. **response_format** 主循环内结构化输出——省一次调用，ProviderStrategy 自动选策略
> 6. **ContentBlocks** 区分推理与回答，适配深度思考模型
> 7. **参数边界**：timeout/max_retries 生产必配，temperature 按任务类型调
