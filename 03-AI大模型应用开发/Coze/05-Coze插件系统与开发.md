## 1. 插件市场概览

### 1.1 插件是什么

```text
Coze 插件 = Bot 的"外部工具"

没有插件：Bot 只能用自己记住的知识回答问题
有插件：Bot 可以搜索最新信息、读取网页、生成图片、
        查天气、调 API、发邮件、操作数据库...

插件类型：
├── 官方插件：Coze 团队开发和维护（质量保证）
├── 社区插件：第三方开发者发布
├── 自定义插件：你自己开发的私有插件
└── 代码节点：一次性临时的"内置插件"
```

### 1.2 安装与使用

```text
Bot 编辑页 → 技能 → 插件 → 添加插件

1. 搜索插件
   输入："天气" / "搜索" / "图片" / "翻译"

2. 添加插件
   点击"添加" → 自动安装到 Bot

3. 使用插件
   Bot 对话时会自动判断是否需要调用插件
   也可在工作流中拖入插件节点
```

## 3. 自定义插件开发

### 3.1 两种创建方式

```text
插件 → 我的插件 → 创建插件

方式一：API 插件（推荐）
  → 对接外部系统：自研系统/SaaS 服务/公共 API
  → 技术栈：OpenAPI(Swagger) 或 手动配置
  → 适用：有后端 API 的团队

方式二：IDE 插件（高级）
  → 云端 IDE 写 Python/Node.js
  → 适用：需要复杂逻辑、数据处理、状态管理
```

### 3.2 API 插件开发流程

```text
步骤 1：准备 API 信息
  你的后端 API：https://api.yourcompany.com/v1
  认证方式：Bearer Token / API Key

步骤 2：创建插件
  插件 → 创建 → API 插件

  填写：
  ├── 插件名称：如 "订单查询系统"
  ├── 插件描述：如 "查询和操作电商订单的 API"
  ├── 插件图标
  ├── API 基础 URL：https://api.yourcompany.com/v1
  └── 认证方式：Bearer Token → {{API_KEY}}

步骤 3：添加 API 端点
  端点 1：查询订单
  ├── 方法：GET
  ├── 路径：/orders/{order_id}
  ├── 参数：order_id (path, required, string)
  └── 描述：根据订单号查询订单详情

  端点 2：搜索订单
  ├── 方法：GET
  ├── 路径：/orders
  ├── 参数：
  │   ├── keyword (query, string) — 搜索关键词
  │   ├── status (query, string) — 订单状态
  │   └── page (query, integer, default=1) — 页码
  └── 描述：按条件搜索订单列表

  端点 3：创建订单
  ├── 方法：POST
  ├── 路径：/orders
  ├── 请求体 (JSON Schema)
  │   {
  │     "product_id": "string (必填)",
  │     "quantity": "integer (必填, 最小1)",
  │     "address": "string (必填)"
  │   }
  └── 描述：创建新订单

步骤 4：测试
  每个端点 → 测试 → 输入参数 → 查看响应 → 确认正确

步骤 5：发布
  插件 → 发布 → Bot 中即可搜索和添加
```

### 3.3 OpenAPI 批量导入

```yaml
# 如果有 Swagger/OpenAPI 文档，直接导入
openapi: "3.0.0"
info:
  title: 订单系统 API
  version: "1.0.0"
  description: 电商订单管理系统接口
servers:
  - url: https://api.example.com/v1
paths:
  /orders:
    get:
      operationId: searchOrders
      summary: 搜索订单列表
      parameters:
        - name: keyword
          in: query
          schema:
            type: string
          description: 搜索关键词
        - name: status
          in: query
          schema:
            type: string
            enum: [pending, shipped, completed, cancelled]
      responses:
        '200':
          description: 订单列表
  /orders/{orderId}:
    get:
      operationId: getOrder
      summary: 获取订单详情
      parameters:
        - name: orderId
          in: path
          required: true
          schema:
            type: string
      responses:
        '200':
          description: 订单详情
```

## 4. 代码节点 vs 插件节点

### 4.1 对比

| 维度 | 代码节点 | 插件节点 |
|------|:---:|:---:|
| **定义位置** | 工作流内直接写代码 | 独立创建，全局复用 |
| **复用性** | ❌ 仅当前工作流 | ✅ 可被任意 Bot/工作流使用 |
| **复杂度** | ⭐⭐ 简单 | ⭐⭐⭐⭐ 复杂 |
| **适用场景** | 数据处理、格式转换、简单计算 | 外部 API 对接、标准化工具 |
| **开发语言** | Python / JavaScript | API 配置 / IDE 开发 |
| **参数配置** | 手写函数签名 | 可视化定义输入/输出 |
| **调试** | 工作流中直接调试 | 独立测试 → 工作流中使用 |
| **权限管理** | 无 | 可设置可见范围 |

### 4.2 决策指南

```text
用代码节点：
✅ 数据格式转换（JSON → 提取字段 → 重组）
✅ 简单的数学/字符串/日期处理
✅ 临时数据处理逻辑
✅ 原型阶段快速验证

用插件节点：
✅ 对接外部 API（公司系统/第三方服务）
✅ 需要在多个 Bot 中复用
✅ 需要参数校验和错误处理
✅ 需要团队协作维护
```

## 5. 插件最佳实践

### 5.1 设计原则

```text
插件设计的 SOLID 原则（简化版）：

1. 单一职责
   ✅ 一个插件只做一件事
   ❌ "万能工具插件"（搜索+天气+翻译+图片...）

2. 清晰的输入输出
   ✅ 输入参数有明确的类型和描述
   ❌ 模糊的参数如 data: "string"

3. 友好的错误处理
   ✅ API 出错时返回可读的错误信息
   ❌ 返回原始 HTTP 500 HTML 页面

4. 合理的默认值
   ✅ 非必填参数有默认值
   ❌ 每个参数都必填

5. 完整的描述文档
   ✅ Bot 能理解什么时候该调用这个插件
   ❌ "这是一个工具插件"
```

### 5.2 插件描述的艺术

```text
插件的"描述"字段决定了 Bot 会不会调用它：

❌ 不好的描述：
   "订单 API"或"查询订单"

✅ 好的描述：
   "当用户询问订单状态、物流信息、退款进度时，使用此插件查询订单详情。
   输入参数 order_id 是订单号（如20260730001）。
   返回订单的当前状态、物流单号、金额、时间等信息。
   如果订单不存在，返回错误信息'订单不存在'。
   不要用此插件创建或修改订单。"
```

### 5.3 安全注意事项

```text
插件安全底线：

🔒 敏感信息保护：
├── API Key/Token 使用 {{变量}} 而非硬编码
├── 不在插件描述中暴露 API 地址细节
└── 返回值做数据脱敏（手机号/身份证中间打码）

🛡️ 权限控制：
├── 插件设置可见范围（仅自己/团队/公开）
├── 需要认证的插件确保 Bot 调用时有有效凭证
└── 定期轮换 API Token

⚠️ 滥用防护：
├── 设置调用频率限制
├── 参数校验（防止 SQL 注入 / 命令注入）
└── 不要开放删除/修改等危险操作的插件端点
```
