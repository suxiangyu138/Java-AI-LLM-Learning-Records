## 1. Uvicorn 部署形态与版本线

**基准：Uvicorn 0.51.0（2026-07-08）**

| 版本 | 时间 | 关键变化 |
|------|------|---------|
| 0.48.0 | 2026-05-24 | 忽略重复转发头；ssl_ciphers 默认走 OpenSSL |
| 0.49.0 | 2026-06 | httptools 最低 0.8.0 |
| 0.50.0 | 2026-07-04 | `--ws auto` 默认 websockets-sansio（旧实现弃用）；启动失败退出码 3 |
| **0.51.0** | 2026-07-08 | **SIGHUP 热重启带重叠窗口（近零停机）**；移除 colorama |

```bash
# 开发
uvicorn app.main:app --reload --port 8000

# 生产（标准形态）
uvicorn app.main:app \
  --host 0.0.0.0 --port 8000 \
  --workers 4 \
  --loop uvloop --http httptools \
  --limit-concurrency 1000 \
  --timeout-keep-alive 30

# 热重启（0.51 新能力：SIGHUP 新 worker 先起、旧 worker 后停）
kill -HUP <uvicorn-master-pid>
```

| 参数 | 作用 | 建议 |
|------|------|------|
| `--workers N` | worker 进程数（每进程一个事件循环） | CPU 核数 × 1-2 |
| `--loop uvloop` | 更快的循环实现（C 加速） | ⭐ 生产开 |
| `--http httptools` | 更快的 HTTP 解析（C 加速） | ⭐ 生产开 |
| `--limit-concurrency` | 在途请求上限（背压保护） | 1000-5000 |
| `--timeout-keep-alive` | 空闲连接保持 | 30-60s |

> 🎯 **核心要点**：**uvloop + httptools 是白捡的性能**（C 实现的循环与解析器，快 30-50%）；多 worker 提供多核并行（Python 默认 GIL 下单进程只能吃一核，3.14 free-threaded 构建可单进程多核）。**worker 数 × 连接池上限 = 数据库连接需求**（07 章 §2 乘法法则）。

## 2. 多 worker 与进程模型

```text
生产形态（推荐）：
  Nginx（反代 + TLS + 静态） → Uvicorn master
                                  ├── worker 1（事件循环 × 1）
                                  ├── worker 2（事件循环 × 1）
                                  └── worker 3（事件循环 × 1）
```

| 问题 | 答案 |
|------|------|
| 为什么默认 GIL 下要多 worker？ | 单进程一个事件循环只能吃一核；多进程 = 多核并行 |
| worker 间共享什么？ | **不共享内存状态**（每进程独立） |
| worker 间必须共享的怎么办？ | 放外部：Redis/DB（会话、缓存、限流计数） |
| 3.14 free-threaded 需要多 worker 吗？ | 仍建议多进程（隔离 + 弹性），但单进程已可多核 |
| gunicorn vs uvicorn？ | 2026 直接用 `uvicorn --workers`（自带进程管理）；gunicorn 仅在需其生态（超时管理/优雅重启兼容旧脚本）时用 |

> ⚠️ **多 worker 的三个连带**：(1) 内存里的状态（计数器/缓存）各进程独立——需要全局的放 Redis；(2) 连接池按 worker 翻倍（07 章）；(3) 日志采集要聚合（各 worker stdout 统一收集，08 章）。

## 3. Docker 部署与反向代理

```dockerfile
# Dockerfile —— 多阶段构建
FROM python:3.14-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

FROM python:3.14-slim
WORKDIR /app
COPY --from=builder /usr/local/lib/python3.14/site-packages /usr/local/lib/python3.14/site-packages
COPY --from=builder /usr/local/bin /usr/local/bin
COPY app/ ./app/
USER nobody                                     # 非 root 运行（安全基线）
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--workers", "4", "--loop", "uvloop", "--http", "httptools"]
```

```yaml
# docker-compose.yml
services:
  api:
    build: .
    restart: unless-stopped
    environment:
      - JWT_SECRET=${JWT_SECRET}          # 密钥环境变量（06 章）
      - DATABASE_URL=${DATABASE_URL}
    healthcheck:                          # 就绪探针（08 章）
      test: ["CMD", "curl", "-sf", "http://localhost:8000/readyz"]
      interval: 10s
      timeout: 3s
      retries: 3
    deploy:
      resources:
        limits: {memory: 512M}
  nginx:
    image: nginx:1.28
    ports: ["443:443", "80:80"]
    volumes: ["./nginx.conf:/etc/nginx/conf.d/default.conf:ro"]
```

```nginx
# nginx.conf —— 反向代理要点
upstream api { server api:8000; keepalive 32; }

server {
    listen 443 ssl http2;
    server_name api.example.com;
    ssl_certificate /etc/nginx/tls/fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/privkey.pem;

    location / {
        proxy_pass http://api;
        proxy_http_version 1.1;                 # keepalive 必需
        proxy_set_header Connection "";
        proxy_set_header X-Real-IP $remote_addr;      # 真实 IP（日志/限流）
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Host $host;
        proxy_read_timeout 120s;                # 长请求（AI 流式/SSE）
        proxy_buffering off;                    # SSE/流式必须关缓冲
    }
}
```

> 🎯 **核心要点**：**Nginx 干四件事：TLS 终止、静态资源、负载均衡、头传递**。API 服务本身只管业务——配置里最容易漏的是 `X-Real-IP`（日志/限流/IP 白名单都靠它）和流式场景的 `proxy_buffering off`（AI 服务必配）。

## 4. 压测方法论

```bash
# 工具：wrk（单机快速压测）
wrk -t8 -c100 -d30s --latency http://localhost:8000/items/1

# 工具：locust（更精细：RPS 目标/分布/Web 报告，Python 生态）
# locust -f locustfile.py --host=http://localhost:8000 --users 100 --spawn-rate 10

# 报告解读
#   Requests/sec       = 吞吐（核心指标）
#   Latency Distribution: p50/p95/p99 = 延迟分布（别只看平均）
#   Socket errors      = 连接层问题（服务扛不住）
```

| 指标 | 含义 | 关注点 |
|------|------|--------|
| QPS（吞吐） | 每秒完成请求 | 与期望容量对比 |
| **P99 延迟** | 99% 请求在 X ms 内 | ⭐ 比平均更能暴露长尾（卡顿） |
| 错误率 | 4xx/5xx 占比 | 目标 < 0.1% |
| CPU/内存 | 资源利用率 | 找到瓶颈资源 |

**压测流程（科学方法）**：

```text
① 基线：小并发（10）跑通 → 确认功能与延迟基线
② 加压：逐步加并发（50→100→500）→ 观察 QPS 是否线性增长
③ 找拐点：QPS 不再随并发涨 → 记录拐点 = 系统容量
④ 定位：瓶颈在 CPU（代码/序列化）？IO（DB/下游）？内存（池/队列）？
⑤ 回测：优化一项 → 重压 → 对比（一次只改一个变量）
```

> 💡 **压测铁律**：压测环境与生产等规格（连接池、worker 数、DB）；**先压自己再上生产**；压测时开好监控（08 章三支柱），用数据说话。

| 2 | **response_model（Rust 序列化）** | ⭐⭐⭐ 2 倍+ 响应序列化 | 05 |
| 3 | 连接池正确配置（DB/Redis/HTTP） | ⭐⭐⭐ 避免每请求建连 | 03/07 |
| 4 | 缓存热数据（Redis） | ⭐⭐⭐ 读多场景降 DB 压力 | 03 |
| 5 | uvloop + httptools | ⭐⭐ 循环与解析加速 30-50% | 09 |
| 6 | 多 worker 吃满多核 | ⭐⭐ 线性扩展（受 GIL 限制） | 09 |
| 7 | 避免 N+1（selectinload） | ⭐⭐ 慢查询大头 | 07 |
| 8 | 请求体/响应精简（只传必要字段） | ⭐⭐ 序列化与带宽 | 05 |
| 9 | 后台任务出请求周期（队列） | ⭐⭐ 重活不阻塞响应 | 03 |
| 10 | GZip 大响应 | ⭐ 带宽优化 | 08 |
| 11 | 连接复用（AsyncClient 全局） | ⭐⭐ 下游调用提速 | 03 |
| 12 | 慢查询优化（索引/分页） | ⭐⭐ 数据层大头 | 07 |

**性能验证闭环**：改一项 → 压测对比 P99/QPS → 确认收益再动下一项。**别做无压测支撑的"优化"**（过度优化是反模式）。

## 6. 慢请求治理与常见瓶颈

**"接口慢"定位三步**（08 章 OTel 拆解）：

```text
慢在哪儿？
├─ 网络层（P99 均匀高） → 反代/带宽/TLS
├─ 应用层（拆 span 看占比）
│    ├─ DB 查询慢 → 索引/慢 SQL/N+1（07 章）
│    ├─ 下游 HTTP 慢 → 超时/连接池/重试策略（03 章）
│    ├─ 序列化慢 → response_model / 精简字段
│    └─ CPU 热点 → 缓存/算法/异步化
└─ 排队（请求堆积） → 并发限制/worker 不足/限流
```

| 症状 | 常见根因 | 对策 |
|------|---------|------|
| P99 高但 P50 正常 | 长尾：个别慢查询/GC/下游超时 | OTel 定位 + 超时收敛 |
| 全部请求都慢 | 资源耗尽（连接池/线程池/CPU） | 扩容/调池/加缓存 |
| 并发越高越慢 | 锁竞争/伪异步（同步阻塞） | 全链路异步化（02 章反模式） |
| 偶发秒级尖峰 | GC 暂停（CPython 大对象） | 分页/缓存/对象复用 |

> 🎯 **核心要点**：慢请求治理 = **"测量（OTel）→ 定位（拆 span）→ 对症（表驱动）"**，一次只动一个变量。90% 的 FastAPI 慢接口根因是：伪异步（同步库）、N+1、没缓存、没超时。

## 7. 优雅停机与发布

```python
# 优雅停机的三要素
# ① 信号处理：SIGTERM 触发——先停止接收新请求
# ② 在途请求完成：等已接收请求处理完（uvicorn 默认行为）
# ③ 资源清理：lifespan 的关闭段执行（04 章 §5：关闭连接池/客户端）
```

| 发布方式 | 停机时长 | 说明 |
|---------|:---:|------|
| 直接重启 | 秒级 | 请求 502，可接受性看 SLA |
| 滚动发布（Docker Compose） | 近零 | 先起新、探针通过后摘旧 |
| K8s Deployment | 近零 | readiness 摘流量 + rollingUpdate |
| Uvicorn 0.51 SIGHUP | 近零 | 新 worker 与旧 worker 重叠过渡（内建） |

> 💡 发布检查单：**发布前**——新版本压测过、DB 迁移可回滚、配置环境变量就绪；**发布中**——看就绪探针、监控 P99/错误率；**发布后**——观察 15 分钟黄金期，异常立即回滚（回滚 = 拉旧镜像 tag）。
