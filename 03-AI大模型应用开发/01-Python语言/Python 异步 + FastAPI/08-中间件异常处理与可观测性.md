## 1. 中间件机制：洋葱模型与执行顺序

```text
请求 → [CORS] → [追踪] → [日志] → [路由] → 端点 → 响应
            ←        ←        ←        ←
注册顺序决定执行顺序：先注册的在外层（先进后出）
```

```python
from fastapi import FastAPI
from starlette.middleware.base import BaseHTTPMiddleware

app = FastAPI()


@app.middleware("http")
async def request_timing(request: Request, call_next):
    """最简单的自定义中间件：计时 + 统一响应头"""
    start = time.perf_counter()
    response = await call_next(request)        # ⭐ 调用下一个中间件/端点
    response.headers["X-Process-Time"] = f"{time.perf_counter() - start:.4f}"
    return response
```

| 中间件关键点 | 说明 |
|-------------|------|
| `call_next` | 洋葱的核心：调用下一层，返回 Response |
| 注册顺序 | 先注册在外层（请求先进、响应后出） |
| 耗时敏感 | 中间件里别做重活（每请求都执行） |
| async 支持 | FastAPI 的 `@app.middleware("http")` 自动处理 |
| Starlette 1.0 | `middleware=[Middleware(...)]` 参数化注册（04 章 §6） |

> 🎯 **核心要点**：中间件 = **"每请求必过的横切层"**。放这里的事：计时、追踪 ID、安全头、压缩、限流——**只放"所有请求都该有"的逻辑**；只对特定路由生效的放依赖（06 章）。

## 2. 内置中间件：CORS / TrustedHost / GZip

```python
from fastapi.middleware.cors import CORSMiddleware
from starlette.middleware.trustedhost import TrustedHostMiddleware
from starlette.middleware.gzip import GZipMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://admin.example.com"],   # ⚠️ 精确白名单，不用 "*"
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
)
app.add_middleware(TrustedHostMiddleware, allowed_hosts=["api.example.com"])  # 防 Host 头攻击
app.add_middleware(GZipMiddleware, minimum_size=1024)                        # 大响应压缩
```

| 中间件 | 防护/功能 | 配置要点 |
|--------|----------|---------|
| CORS | 浏览器跨域控制 | `allow_origins` 精确白名单（`"*"` + credentials 非法组合） |
| TrustedHost | 防 Host 头注入 | 白名单域名（反代场景必须配） |
| GZip | 响应压缩 | 大 JSON/文本收益明显（API 场景谨慎，见 §8） |
| HTTPSRedirect | 强制 HTTPS | 反代处理时不用 |

> ⚠️ **CORS 是浏览器策略，不是安全边界**：它防的是"浏览器里的恶意 JS 读取你的接口"，防不了 curl/服务器直连。**真正的接口安全 = 认证 + 授权（06 章）**，CORS 只是体验层配置。生产必须精确 allow_origins，`"*"` 是事故。

## 3. 自定义中间件：请求日志与追踪 ID

```python
import uuid
from starlette.middleware.base import BaseHTTPMiddleware


class RequestIdMiddleware(BaseHTTPMiddleware):
    """为每个请求注入 trace_id（贯穿日志/响应头/下游调用）"""
    async def dispatch(self, request: Request, call_next):
        trace_id = request.headers.get("X-Trace-Id") or str(uuid.uuid4())[:16]
        request.state.trace_id = trace_id                 # 请求内全局可读
        response = await call_next(request)
        response.headers["X-Trace-Id"] = trace_id         # 响应带回（排查闭环）
        return response


# 使用：端点和依赖里都能读
@app.get("/items/{item_id}")
async def get_item(item_id: int, request: Request):
    logger.info("请求处理", extra={"trace_id": request.state.trace_id})
    return {"id": item_id}
```

**排查链路价值**：前端拿到 `X-Trace-Id` → 报障时把 ID 给后端 → 日志里按 trace_id 捞出完整链路（含 DB 查询、下游调用、异常堆栈）。**这是生产 API 运维的第一性基础设施**（可观测性体系在 02-后端 07-运维 有全景）。

## 4. 全局异常处理：从 500 到可读错误

```python
from fastapi import FastAPI, Request, HTTPException
from fastapi.responses import JSONResponse

app = FastAPI()


# ① 业务异常统一出口（推荐自定义异常基类）
class BizError(Exception):
    def __init__(self, code: str, message: str, status: int = 400):
        self.code, self.message, self.status = code, message, status


@app.exception_handler(BizError)
async def biz_error_handler(request: Request, exc: BizError):
    return JSONResponse(
        status_code=exc.status,
        content={"code": exc.code, "message": exc.message, "trace_id": request.state.trace_id},
    )


# ② 兜底：未捕获异常 → 统一 500 + 不泄漏内部细节
@app.exception_handler(Exception)
async def unhandled_handler(request: Request, exc: Exception):
    logger.exception("未捕获异常", exc_info=exc, extra={"trace_id": request.state.trace_id})
    return JSONResponse(status_code=500, content={"code": "INTERNAL", "message": "服务器内部错误"})


# ③ 业务代码只需
@app.get("/orders/{oid}")
async def get_order(oid: int):
    order = await repo.get(oid)
    if order is None:
        raise BizError("ORDER_NOT_FOUND", "订单不存在", 404)   # 干净利落
    return order
```

| 异常层 | 状态码 | 响应体 |
|--------|:---:|--------|
| Pydantic 校验失败 | 422 | 自动（detail 数组） |
| HTTPException | 4xx | detail 字符串 |
| **BizError（自定义）** | 业务语义 4xx | `{code, message, trace_id}` 统一结构 |
| 未捕获 | 500 | 统一兜底 + 日志全堆栈 |

> 🎯 **核心要点**：**统一错误契约**（code + message + trace_id）是联调/前端/排查三方的共同语言——错误码可程序化判断、message 给人看、trace_id 给排查用。业务代码只抛异常，格式统一由处理器管。

## 5. 可观测性三支柱落地

```text
三支柱（与 02-后端 07-工程运维 日志监控指标 体系呼应）：
  Metrics（指标）   → Prometheus + /metrics 端点
  Logs（日志）      → 结构化 JSON + 采集（Loki/EFK）
  Traces（链路）    → OpenTelemetry 自动埋点 + 后端（Jaeger/Tempo）
```

```python
# OpenTelemetry 自动埋点（FastAPI 一键接入）
from opentelemetry import trace
from opentelemetry.instrumentation.fastapi import FastAPIInstrumentor
from opentelemetry.instrumentation.httpx import HTTPXClientInstrumentor
from opentelemetry.instrumentation.sqlalchemy import SQLAlchemyInstrumentor

# app 创建后：
FastAPIInstrumentor.instrument_app(app)          # HTTP 层自动 span
HTTPXClientInstrumentor().instrument()           # 下游 HTTP 调用自动 span
SQLAlchemyInstrumentor().instrument(engine=engine)  # DB 查询自动 span

tracer = trace.get_tracer("my-app")

# 业务关键路径手动 span
with tracer.start_as_current_span("cache.get") as span:
    span.set_attribute("cache.key", key)
    value = await cache.get(key)
```

| 支柱 | 采集 | 看什么 |
|------|------|--------|
| Metrics | /metrics（prometheus-client） | QPS、P99 延迟、错误率、连接池 |
| Logs | 结构化 JSON + trace_id | 业务事件、异常、审计 |
| Traces | OTel 自动埋点 | 慢请求拆解（DB 慢/下游慢/代码慢） |

> 💡 排障三步走：**Metrics 发现异常（P99 飙升）→ Traces 定位环节（DB？下游？）→ Logs 看细节（trace_id 捞日志）**。2026 年 OTel 是行业标准（Alloy 采集 + Grafana 全家桶）。

## 6. 结构化日志规范

```python
import logging, sys, json
from datetime import datetime, timezone

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {
            "ts": datetime.now(timezone.utc).isoformat(),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
            "trace_id": getattr(record, "trace_id", ""),   # 中间件注入
            "path": getattr(record, "path", ""),
        }
        if record.exc_info:
            payload["exc"] = self.formatException(record.exc_info)
        return json.dumps(payload, ensure_ascii=False)

# 配置一次，全应用生效
logging.basicConfig(level=logging.INFO, handlers=[logging.StreamHandler(sys.stdout)])
logging.getLogger().handlers[0].setFormatter(JsonFormatter())
logger = logging.getLogger("app")

# 使用：extra 带上下文
logger.info("下单成功", extra={"order_id": 42, "trace_id": request.state.trace_id})
```

| 规范 | 说明 |
|------|------|
| JSON 结构化 | 机器可读，采集/检索友好（Loki 等按字段过滤） |
| trace_id 贯穿 | 每行日志带（中间件注入 extra） |
| 级别纪律 | INFO 业务事件 / WARNING 可恢复问题 / ERROR 异常 |
| 敏感脱敏 | 日志里不打印密码/token（打印前脱敏） |
| 上下文 | extra 带业务键（order_id 等），检索粒度更细 |

> ⚠️ 日志纪律：**别把日志当调试输出**（print/DEBUG 刷屏 = 没人看的噪音）；生产只留有用事件；**敏感字段（token/密码/身份证）禁止进日志**——数据合规是底线（个保法）。

## 7. 健康检查与就绪探针

```python
@app.get("/healthz")                     # 存活探针（Liveness）：进程活着
async def healthz():
    return {"status": "ok"}

@app.get("/readyz")                      # 就绪探针（Readiness）：依赖可用
async def readyz():
    try:
        async with engine.connect() as conn:      # 探测 DB
            await conn.execute(text("SELECT 1"))
        await app.state.redis.ping()              # 探测 Redis
    except Exception as exc:
        return JSONResponse(status_code=503, content={"status": "degraded", "detail": str(exc)})
    return {"status": "ok"}
```

| 探针 | 语义 | 用途 |
|------|------|------|
| `/healthz` | 进程存活 | 容器/编排重启判定 |
| `/readyz` | 依赖就绪（DB/Redis/下游） | 负载均衡摘除/滚动发布判定 |
| `/metrics` | 指标采集 | Prometheus 抓取 |

> 🎯 **核心要点**：**就绪探针 = 依赖体检**——DB 挂了就该 503，让负载均衡摘流量，而不是"进程活着但每个请求都 500"。K8s 三探针 + 蓝绿/金丝雀的配合见 CI/CD 灰度发布体系。

## 8. 常见坑

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 1 | 中间件里做重活 | 每请求延迟 + 中间件排队 | 只放轻逻辑；重活放依赖/后台任务 |
| 2 | CORS 用 `"*"` | 安全问题（配合 credentials 直接报错） | 精确白名单 |
| 3 | 未捕获异常裸奔 | 500 泄漏内部堆栈/内部细节 | 全局处理器 + 不泄漏细节 |
| 4 | GZip 压小响应 | CPU 白烧、TLS 下收益低 | 只压大 JSON（>1KB）+ 权衡 |
| 5 | 日志无 trace_id | 报障无法串链路 | 中间件注入 + 结构化 extra |
| 6 | 探针探了业务 DB | 业务故障时探针抖动误判 | 探针用独立只读连接/专用账号 |
| 7 | 异常处理器忘了 record.exception | 日志只有 message 没堆栈 | logger.exception 必带 exc_info |
| 8 | OTel 埋点重复 | span 爆炸、采集成本高 | 按需 instrument + 采样策略 |

## 9. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 中间件 = 每请求横切层（洋葱模型，先注册在外层） |
| 2 | CORS 精确白名单 + TrustedHost + GZip（按需） |
| 3 | 追踪 ID 中间件：请求注入、响应带回、日志贯穿——排查闭环 |
| 4 | 统一错误契约：BizError + 全局处理器（code/message/trace_id） |
| 5 | OTel 三行接入：FastAPI/httpx/SQLAlchemy 自动 span |
| 6 | 排障三步：Metrics 发现 → Traces 定位 → Logs 看细节 |
| 7 | 结构化 JSON 日志 + trace_id + 脱敏纪律 |
| 8 | 双探针（healthz/readyz）+ metrics；就绪探针探依赖 |
