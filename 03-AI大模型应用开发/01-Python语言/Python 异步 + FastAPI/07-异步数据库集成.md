## 1. 为什么异步 ORM 是生产标准

| 组合 | 效果 | 评价 |
|------|------|------|
| `async def` 端点 + **同步 ORM** | 看似异步实则阻塞：每次查询冻结事件循环 | ❌ 伪异步 |
| `def` 端点 + 同步 ORM | 不冻结循环，但每个请求占一个线程 | 线程池上限 = 吞吐上限 |
| **`async def` + SQLAlchemy async** | 真异步：等待期间事件循环处理其他请求 | ⭐ 生产标准 |

> 🎯 **核心要点**：**"异步端点 + 同步数据库"是最贵的伪异步**——请求在高并发时全部卡在数据库调用上（每个 DB 查询 5-50ms，期间事件循环被冻结）。选型口诀：**SQLAlchemy async + asyncpg 方言 + async 端点**三件套，缺一不可（03 章兼容矩阵）。

## 2. create_async_engine 全参数配置

```python
# app/core/db.py —— 数据库核心（生产模板）
from sqlalchemy.ext.asyncio import (
    create_async_engine,
    async_sessionmaker,
    AsyncSession,
)
from sqlalchemy import AsyncAdaptedQueuePool

engine = create_async_engine(
    "postgresql+asyncpg://user:pass@localhost/mydb",   # asyncpg 方言
    poolclass=AsyncAdaptedQueuePool,                   # 异步连接池（默认）
    pool_size=20,                                      # 稳态连接数
    max_overflow=10,                                   # 突发容量（总上限 = pool_size + max_overflow = 30）
    pool_pre_ping=True,                                # ⭐ 取用前验证连接（剔除死连接）
    pool_recycle=1800,                                 # 每 30 分钟轮换连接（防僵死/SSL 断连）
    pool_timeout=30,                                   # 拿不到连接等多久
    echo=False,                                        # 生产关 SQL 日志
)

# 会话工厂：应用全局唯一，注入到依赖
AsyncSessionLocal = async_sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False,        # ⭐ 提交后不失效（避免后续访问触发隐式查询）
    autoflush=False,               # 显式控制 flush 时机
)
```

| 参数 | 推荐值 | 作用 |
|------|:---:|------|
| `pool_size` | 20-50 | 稳态连接（并发请求数 × 每请求 DB 操作估算 + 缓冲） |
| `max_overflow` | 10 | 突发容忍（总上限 = 二者之和） |
| `pool_pre_ping` | **True** | 防拿到失效连接（网络抖动/重启后） |
| `pool_recycle` | 1800-3600 | 防连接僵死、SSL 断连 |
| `pool_timeout` | 30 | 池耗尽时等待（避免无限挂起） |
| `expire_on_commit` | **False** | 提交后对象属性仍可访问 |

> ⚠️ **多 worker 乘法**：`uvicorn --workers 4` 时总连接 = 4 × (pool_size + max_overflow)。PostgreSQL max_connections 200 的话，4 workers × 30 = 120 是安全值——**连接池大小必须考虑 worker 数**，否则 `TooManyConnectionsError`。

## 3. 会话工厂与依赖注入

```python
# app/api/deps.py —— 会话依赖（06 章 §3 模式落地）
from typing import AsyncGenerator
from fastapi import Depends


async def get_db() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()          # 端点正常 → 提交
        except Exception:
            await session.rollback()        # 端点异常 → 回滚
            raise                           # 异常继续向上（全局处理器兜底）


# 端点使用
@app.post("/orders")
async def create_order(
    payload: OrderIn,
    db: AsyncSession = Depends(get_db),     # 每个请求独立会话
):
    order = Order(**payload.model_dump())
    db.add(order)
    # 不显式 commit —— 依赖退出时统一提交
    return order
```

| 会话管理规则 | 说明 |
|-------------|------|
| **每请求一个会话** | 不跨请求共享 AsyncSession（非线程安全、状态混乱） |
| 提交在依赖层 | 端点不写 commit，统一在 get_db 退出时提交 |
| 回滚兜底 | 异常自动回滚 + 上抛 |
| 不跨并发任务共享 | 同一个 Session 不用于并发 task（数据竞争） |

> 🎯 **核心要点**：**"依赖管生命周期、端点管业务"**——端点里永远看不到 open/commit/close 的样板代码，只写业务。这是 06 章 yield 依赖的最佳实践落点。

## 4. 事务管理模式

```python
# 单端点多步操作：显式事务（默认 autobegin，commit 时统一提交）
async def transfer(db: AsyncSession, from_id: int, to_id: int, amount: float):
    async with db.begin():                          # 显式事务块
        a = await db.get(Account, from_id, with_for_update=True)   # 行锁防并发扣减
        b = await db.get(Account, to_id, with_for_update=True)
        if a.balance < amount:
            raise ValueError("余额不足")             # 抛异常 → 事务回滚
        a.balance -= amount
        b.balance += amount
    # 退出 async with db.begin() 自动提交
```

| 场景 | 手段 |
|------|------|
| 单条写 | 依赖退出统一提交（§3） |
| 多步强一致 | `async with db.begin()` 显式事务 |
| 并发扣减/余额 | `with_for_update=True` 行锁 |
| 读多写少 | 普通读不用事务（自动快照） |
| 跨服务事务 | 不适用——用 Saga/Outbox（分布式事务体系） |

> ⚠️ **事务三不要**：不要在事务里做外部 IO（HTTP 调用等，锁持有时间 = 死锁风险）；不要长事务（大查询 + 锁）；不要手动 `await session.commit()` 后再用对象（expire_on_commit=False 是防它的）。

## 5. 模型定义与异步查询

```python
# app/models.py
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship
from sqlalchemy import String, ForeignKey, select


class Base(DeclarativeBase):
    pass


class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(64))
    orders: Mapped[list["Order"]] = relationship(
        back_populates="user",
        lazy="raise",                # ⭐ 禁止隐式懒加载（见 §6）
    )


class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    user: Mapped[User] = relationship(back_populates="orders", lazy="raise")


# 异步查询（execute + scalars）
async def get_user_with_orders(db: AsyncSession, uid: int):
    stmt = (
        select(User)
        .where(User.id == uid)
        .options(selectinload(User.orders))     # 预加载（防 N+1）
    )
    return (await db.execute(stmt)).scalar_one_or_none()
```

## 6. N+1 与 MissingGreenlet 治理

### 6.1 症状

```python
# N+1：查 100 个订单 → 额外 100 次查询拉用户
orders = (await db.execute(select(Order).limit(100))).scalars().all()
for o in orders:
    print(o.user.name)        # ⚠️ 每访问一次 o.user 就发一次查询（同步 ORM 下）

# 异步下更糟：直接报错
#   sqlalchemy.exc.MissingGreenlet: greenlet_spawn has not been called
#   原因：异步 Session 不能在"没有 await 的访问"里隐式发 IO
```

### 6.2 治理三件套

```python
# ① 关系一律 lazy="raise" —— 隐式访问直接报错，强迫你显式预加载
# ② 查询时显式预加载
stmt = select(Order).options(
    selectinload(Order.user),                    # 列表场景（两轮查询，安全）
    # joinedload(Order.user)                     # join 场景（一轮，注意膨胀）
).limit(100)

# ③ 复杂聚合用 select 表达式，不靠关系
stmt = select(Order.user_id, func.count(Order.id)).group_by(Order.user_id)
```

| 手段 | 场景 | 说明 |
|------|------|------|
| `lazy="raise"` | 全部关系 | **强制显式加载**（把隐患变成报错） |
| `selectinload` | 列表 + 关系 | 两轮查询取全部（N+1 → N+2） |
| `joinedload` | 一对一/聚合 | JOIN 一轮（结果集可能膨胀） |
| 裸字段查询 | 只要几列 | 不整行加载 |

> 🎯 **核心要点**：**异步 ORM 的 N+1 不是性能问题，是崩溃问题**（MissingGreenlet）。根治 = `lazy="raise"` + 显式 `selectinload`——把"忘写预加载"从静默慢查询变成必现报错，质量立刻可感知。

## 7. 连接池监控与 PgBouncer

| 监控信号 | 含义 | 动作 |
|---------|------|------|
| 池利用率 > 80% | 池偏小或查询慢 | 加池/查慢 SQL |
| 频繁 max_overflow | 突发流量超稳态 | 调大 pool_size |
| `QueuePool limit exceeded` | **连接泄漏**（会话没归还） | 查 async with/依赖管理 |
| `TooManyConnectionsError` | 池 × worker 超 DB 上限 | 调小池或 DB max_connections |
| `pg_stat_activity` 长期 idle in transaction | 事务没提交/回滚 | 查事务管理 |

```sql
-- PostgreSQL 侧体检（生产运维）
SELECT pid, state, wait_event_type, query
FROM pg_stat_activity WHERE datname = 'mydb';
```

**PgBouncer（端口 6432）**：数据库前的连接池代理——高并发 + 多 worker 场景（特别是云数据库连接数受限、Docker Compose 部署）下在应用与 PG 之间加一层，把"应用池 × worker"与"DB 连接上限"解耦。

> 💡 什么时候必须上 PgBouncer：连接需求 > 数据库 max_connections 的 70%；云 RDS 连接数按规格受限；多服务共享一个库。轻量场景先调好应用池参数，不必过早引入。

## 8. asyncpg 直连 vs SQLAlchemy async 选型

| 维度 | asyncpg 直连 | SQLAlchemy async |
|------|:---:|:---:|
| 性能 | ⭐ 最快（少一层） | 接近（~5% 差距） |
| 生产力 | 手写 SQL + 手管结果映射 | ORM + 类型 + 迁移生态 |
| 迁移工具 | 无 | **Alembic** 自动迁移 |
| 复杂查询 | 手写 | 表达式/原生 SQL 均可 |
| 适合 | 纯高性能数据层/脚本 | ⭐ FastAPI 业务 API |

> 🎯 **核心要点**：**业务 API 选 SQLAlchemy async**（迁移、类型、生产力全胜，性能差距可忽略）；只有"极致性能 + 简单 SQL"的专用路径（如离线批处理）才直连 asyncpg。**别为了 5% 性能放弃整个 ORM 生态**。

## 9. 常见坑与排查

| # | 坑 | 现象 | 解法 |
|:---:|-----|------|------|
| 1 | 同步 ORM 在 async 端点 | 高并发延迟暴涨 | 全链路 SQLAlchemy async |
| 2 | MissingGreenlet | 访问关系字段崩溃 | lazy="raise" + selectinload |
| 3 | 连接泄漏 | QueuePool limit exceeded | 会话必须 async with/依赖管理 |
| 4 | expire_on_commit=True（默认） | 提交后访问属性发隐式查询 | 设 False |
| 5 | 跨请求共享 Session | 数据串/并发错乱 | 每请求新会话 |
| 6 | 多 worker 连接超限 | TooManyConnectionsError | 池 × worker ≤ DB 上限 |
| 7 | 事务里做 HTTP 调用 | 锁长持、死锁 | 事务内只做 DB 操作 |
| 8 | 中文/emoji 报错 | 编码错误 | DB utf8mb4（PG 无需，MySQL 需） |
| 9 | 会话在 task 里共享 | 并发写同会话 | 每个任务独立会话 |
| 10 | 忘 commit 数据"丢" | 端点正常但没入库 | 依赖统一 commit（§3） |

## 10. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 真异步 = async 端点 + async 引擎 + async 会话三件套 |
| 2 | 引擎参数：pool_size/max_overflow/pre_ping/recycle/timeout 五参数一次配好 |
| 3 | expire_on_commit=False + autoflush=False（会话工厂） |
| 4 | get_db 依赖：yield 会话、退出 commit、异常 rollback |
| 5 | 每请求独立会话；不跨任务共享；事务内不做外部 IO |
| 6 | N+1 治理：lazy="raise" + selectinload，MissingGreenlet 是设计反馈 |
| 7 | 监控池信号（泄漏/溢出）；高并发上 PgBouncer |
| 8 | 业务 API 选 SQLAlchemy async + Alembic，asyncpg 直连留给极速场景 |
