## 1. 并发控制三件套：信号量/锁/事件

```python
import asyncio

sem = asyncio.Semaphore(5)        # 最多 5 个并发
lock = asyncio.Lock()             # 互斥（保护共享状态）
event = asyncio.Event()           # 跨任务通知

async def limited_task(i):
    async with sem:               # 获取不到就排队等
        await asyncio.sleep(0.1)
        return i
```

| 原语 | 语义 | 典型场景 |
|------|------|---------|
| `Semaphore(n)` | 并发闸门：最多 n 个同时进入 | 限制并发请求数、连接池保护 |
| `Lock` | 互斥：同一时刻只有一个持有 | 保护共享状态（计数器/缓存写） |
| `Event` | 信号：set/wait，广播通知 | 就绪通知、优雅关闭 |
| `Condition` | 锁 + 条件等待 | 复杂同步 |

> ⚠️ **异步锁的正确性前提**：锁必须在**同一个事件循环**内使用；跨线程的共享状态不要用 asyncio 锁（3.14 官方文档明确：跨线程用 threading 原语，见 01 章 §8）。另外**锁内禁止 await 耗时操作**（相当于串行化所有请求）。

## 2. 限流模式：令牌桶与滑动窗口

**场景**：调用第三方 API 有配额（如每秒 10 次），或爬虫要控制抓取节奏。

```python
# 令牌桶：每 interval 秒生成 1 个令牌，最多攒 capacity 个
class TokenBucket:
    def __init__(self, rate: float, capacity: int):
        self.rate = rate                # 每秒补充令牌数
        self.capacity = capacity        # 桶容量（突发上限）
        self.tokens = capacity
        self.updated = asyncio.get_event_loop().time()

    async def acquire(self):
        while True:
            now = asyncio.get_event_loop().time()
            self.tokens = min(self.capacity,
                              self.tokens + (now - self.updated) * self.rate)
            self.updated = now
            if self.tokens >= 1:
                self.tokens -= 1
                return
            await asyncio.sleep((1 - self.tokens) / self.rate)   # 等令牌
```

> 💡 限流在异步里是**协程级等待**（sleep），不是线程级阻塞——限流 100 个协程也不占线程。这也是"异步 + 反爬/API 配额"场景的主流做法（阶段 6 的 AutoThrottle 是框架内置版）。

## 3. 扇出模式：请求分发给 N 个协程

**模式**：一个入口任务 → 拆成 N 个子任务并行 → 汇总。

```python
async def fan_out(urls, concurrency=10):
    sem = asyncio.Semaphore(concurrency)      # 限制同时进行的下载数

    async def fetch_one(url):
        async with sem:
            return await http_get(url)        # 伪代码：真实用 httpx（03 章）

    # 方式一：gather（需要全部结果，失败会抛）
    results = await asyncio.gather(*(fetch_one(u) for u in urls))

    # 方式二：TaskGroup（推荐，结构化）
    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(fetch_one(u)) for u in urls]
    return [t.result() for t in tasks]
```

| 场景 | 手段 | 注意 |
|------|------|------|
| 全部结果都要 | gather / TaskGroup | 一个失败全体失败（gather）或全取消（TaskGroup） |
| 部分失败可容忍 | gather(return_exceptions=True) | 逐个检查异常 |
| 结果随到随处理 | 回调式：async 循环 + queue | 见 §5 |
| 数量巨大（10 万 URL） | 分批扇出 + 信号量 | 别一次性 create_task 十万个 |

> 🎯 **核心要点**：扇出三件套 = **信号量（限流）+ TaskGroup（管理）+ 结果聚合**。并发上限永远用信号量显式控制——"create_task 一万个"是事故，不是性能。

## 4. 背压：生产者快于消费者怎么办

**问题**：生产者产任务的速度 >> 消费者处理速度 → 任务堆积 → 内存爆炸（爬虫抓 URL 列队、消息进队列都是典型）。

**背压 = 让生产速度被消费能力拉住**，三个层级手段：

| 层级 | 手段 | 说明 |
|------|------|------|
| 队列上限 | `asyncio.Queue(maxsize=N)` | `put` 满时阻塞生产者（天然背压） |
| 信号量闸门 | 生产者在 `async with sem` 内 yield 任务 | 在途任务数封顶 |
| 分批生产 | 每批 N 个，等这批消费完再生产 | 全量数据不进内存 |

```python
# 队列上限 = 最简单可靠的背压
queue: asyncio.Queue = asyncio.Queue(maxsize=100)

async def producer():
    for url in range(10000):
        await queue.put(url)        # 队列满 → 生产者挂起（背压生效）
        # 消费者消费后 put 返回，继续生产

async def consumer():
    while True:
        url = await queue.get()
        await process(url)
        queue.task_done()           # 告知队列：处理完
```

> ⚠️ 背压失败的症状 = **内存持续增长 + GC 压力**。排查时先问："队列有没有上限？在途任务有没有上限？"——没有上限的异步系统，高峰就是 OOM。

## 5. 生产者-消费者：asyncio.Queue

```python
async def worker(name, queue):
    while True:
        item = await queue.get()
        try:
            await handle(item)
        finally:
            queue.task_done()

async def main():
    q = asyncio.Queue(maxsize=50)
    workers = [asyncio.create_task(worker(f"w{i}", q)) for i in range(3)]  # 3 个消费者

    for item in range(100):
        await q.put(item)           # 生产者（此处可 await 背压）
    await q.join()                  # 等队列清空（所有 task_done）
    for w in workers: w.cancel()    # 收尾：取消消费者
```

| 方法 | 作用 |
|------|------|
| `put(item)` | 入队（满则挂起） |
| `get()` | 出队（空则挂起） |
| `task_done()` | 通知队列"本元素处理完"（与 `join()` 配对） |
| `join()` | 等所有已入队元素被 task_done |
| `shutdown()` | 3.13+：关闭队列，拒绝新 put，让 get 正常耗尽 |

> 💡 `get()` 出来后**必须 finally 里 task_done**——任务处理抛异常时 `join()` 才不会永远等待。队列消费是异步系统的常见骨架（日志收集、消息分发、爬虫待抓队列）。

## 6. 线程桥接：to_thread 与 run_in_executor

**场景**：不得不调用**同步阻塞**代码（同步 SDK、CPU 密集计算）时，丢进线程池，别让事件循环卡死。

```python
import asyncio, time

async def main():
    # 方式一（推荐）：asyncio.to_thread —— 线程池执行，await 等待
    result = await asyncio.to_thread(sync_heavy_work, arg1)      # 返回结果

    # 方式二：run_in_executor —— 自定义池（复用线程）
    loop = asyncio.get_running_loop()
    with concurrent.futures.ThreadPoolExecutor(max_workers=8) as pool:
        result = await loop.run_in_executor(pool, sync_heavy_work, arg1)

    # 方式三：CPU 密集用进程池（多核真并行）
    with concurrent.futures.ProcessPoolExecutor() as pool:
        result = await loop.run_in_executor(pool, cpu_bound_work, arg1)
```

| 桥接对象 | 适用 | 并发数建议 |
|---------|------|:---:|
| `asyncio.to_thread` | 单次同步调用（文件解析/哈希/同步 SDK） | 默认池 32 线程 |
| ThreadPoolExecutor | 批量同步 IO 任务、受控线程数 | 4-8 × CPU 核 |
| ProcessPoolExecutor | CPU 密集（图像/数学/大数据处理） | = CPU 核数 |
| 3.14 自由线程构建 | 线程真并行 | 视核数 |

> 🎯 **核心要点**：`to_thread` 是"**兼容世界**"的桥——异步生态没有替代品的同步库（PyMySQL、requests、OpenCV 等），一律 `await asyncio.to_thread(...)` 调用。**代价是线程池有限**：并发需求大时优先换真异步库（03 章兼容矩阵），to_thread 只做兜底。

## 7. 异步反模式黑名单

| # | 反模式 | 后果 | 正确做法 |
|:---:|-------|------|---------|
| 1 | `time.sleep()` | 冻结整个事件循环（所有请求卡住） | `await asyncio.sleep()` |
| 2 | `requests.get()` / 同步 ORM | 同上（阻塞系统调用） | `httpx.AsyncClient`（03 章） |
| 3 | `open()` 读写大文件 | 阻塞磁盘 IO 冻结循环 | `aiofiles` / to_thread |
| 4 | 同步循环里调用 async 函数 | `RuntimeWarning`，协程不执行 | 结构重写 / create_task |
| 5 | `asyncio.run()` 嵌套调用 | RuntimeError（循环已存在） | 顶层只调一次 |
| 6 | 无界 create_task | 内存爆炸、孤儿任务 | TaskGroup + 信号量 |
| 7 | 锁内长时间 await | 全局串行化、吞吐崩塌 | 锁保护最小临界区 |
| 8 | 跨线程用 asyncio 原语 | 数据竞争/未定义行为 | threading 原语 / run_coroutine_threadsafe |
| 9 | 无超时的外部 IO | 上游卡死 → 全服务拖死 | asyncio.timeout 包裹 |
| 10 | 直接 `loop.run_until_complete` 乱搭 | 循环泄漏 | asyncio.run / Runner |

> 💡 **反模式识别信号**：服务并发高时延迟暴涨（同步阻塞）？内存持续增长（无背压）？CPU 单核 100% 但请求卡死（time.sleep 冻结）？——三种症状对应前三条反模式。

## 8. 核心要点

| 序号 | 要点 |
|:---:|------|
| 1 | 信号量限并发、锁保护状态、Event 做通知；异步原语只在单循环内用 |
| 2 | 令牌桶 = 异步限流标准形态（协程级等待，不占线程） |
| 3 | 扇出三件套：信号量 + TaskGroup + 结果聚合 |
| 4 | 背压 = 队列上限/信号量/分批生产；无上限的队列是 OOM 温床 |
| 5 | Queue 消费：get 后 finally 里 task_done；join 等耗尽；3.13+ 可 shutdown |
| 6 | 同步代码用 asyncio.to_thread 桥接（线程池），CPU 密集用进程池 |
| 7 | 十大反模式：阻塞调用、无超时、无界任务、锁内长等待是重灾区 |
| 8 | 设计模式核心思想：**一切并发都有上限、一切等待都有超时、一切任务都有人管** |
