## 1. 为什么需要 A2A

**多 Agent 协作的通信问题**：

```text
场景：告警分流 Agent 需要把"诊断任务"交给诊断 Agent
问题：
  ① 每个 Agent 用私有协议通信 → N×N 集成地狱（与 API 时代同病）
  ② Agent 间需要"委派 + 回传"语义（不只是数据交换）
  ③ 跨团队/跨组织的 Agent 需要互操作标准

A2A 的答案：标准化的 Agent-to-Agent 通信协议
  → 任何实现了 A2A 的 Agent 都能互相协作
  → 类比：MCP 是"USB-C 接口"（接外设），A2A 是"通用插座"（Agent 互连）
```

**A2A 解决的三件事**：

| 能力 | 说明 |
|------|------|
| 能力发现 | Agent Card 声明"我能做什么"（类似 MCP 的工具列表） |
| 任务委派 | 把一个任务交给另一个 Agent（异步、可追踪） |
| 结果回传 | 完成状态与结果的通知机制 |

> 🎯 **核心要点**：A2A 的动机 = "**Agent 之间也需要标准**"——没有 A2A，每个多 Agent 系统都是私有协议，跨组织协作无从谈起。

## 2. A2A 核心概念

**A2A 的四个核心概念**：

```text
① Agent Card（Agent 能力卡）
   → Agent 的"自我介绍"：能力、端点、认证方式、可用工具
   → 类比：HTTP 时代的 robots.txt / OpenAPI 描述
   → 客户端通过 Agent Card 发现"这个 Agent 能帮我做什么"

② Task（任务）
   → Agent 间的协作单元（与 MCP Tasks 呼应）
   → 生命周期：submitted → working → completed / failed / cancelled
   → 可异步追踪（task_id）

③ Message（消息）
   → Agent 间传递的内容（文本/结构化数据/工具调用请求）

④ Artifact（产物）
   → 任务产出的文件/数据（任务完成后的交付物）
```

```text
典型交互流（A2A 简化版）：
  Client Agent → 读取 Agent Card（发现诊断 Agent）
  → 提交 Task（委派诊断任务）
  → 轮询/订阅 Task 状态（working...）
  → Task completed → 获取 Artifact（诊断结果）
```

**A2A 与 MCP Tasks 的关系**：MCP Tasks 是"Agent 与服务器之间的长任务"；A2A Task 是"Agent 与 Agent 之间的协作任务"——层次不同、概念呼应。

> 🎯 **核心要点**：A2A 的记忆锚 = "**Agent Card（我是谁）+ Task（帮我做什么）+ Artifact（给我什么）**"三件套——能力发现、任务委派、结果交付，一次协作的完整闭环。

## 3. A2A vs MCP：分层与边界

**2026 最关键的架构认知——两者分层共存，不是二选一**：

```text
MCP：垂直协议（Agent ↔ 工具/数据）—— "接入"
A2A：水平协议（Agent ↔ Agent）—— "协作"

分层示例：
  告警分流 Agent
    ├── MCP → Prometheus（查指标）/ GitHub（建 Issue）/ K8s（查状态）
    └── A2A → 诊断 Agent（委派根因分析）→ 修复 Agent（执行修复）
```

| 维度 | MCP | A2A |
|------|:---:|:---:|
| 连接对象 | Agent ↔ 工具/数据 | Agent ↔ Agent |
| 方向 | 垂直（接入） | 水平（协作） |
| 类比 | USB-C 接口 | 通用插座 |
| 核心能力 | 工具调用/资源读取 | 能力发现/任务委派 |
| 发布 | 2024-11（Anthropic） | 2025-04（Google） |
| 2026 状态 | 无状态规范（2026-07） | v1.0 稳定（150+ 组织） |
| 治理 | Linux 基金会 AAIF | 开放标准（多家共建） |

**常见误区**（2026 面试陷阱）：

```text
❌ "A2A 会取代 MCP" → 层次不同，取代无从谈起
❌ "MCP 也能做 Agent 协作" → MCP 的 Tools 是"给 Agent 用的工具"，
   不是"Agent 间的委派语义"（缺 Agent Card/任务生命周期）
✅ 正确姿势：MCP 管工具接入、A2A 管 Agent 协作，各司其职
```

> 🎯 **核心要点**：A2A vs MCP 的面试标准答案 = "**MCP 垂直（工具）、A2A 水平（Agent）**——同一 Incident 流程里两者同时出现、互不重叠"。能画出分层示例图 = 满分。

## 4. 典型场景：Incident 处理链路

**A2A + MCP 协同的完整示例**（2026 行业标准场景）：

```text
场景：生产告警 → 自动分流 → 诊断 → 修复 → 通知

① 分流 Agent（A2A 编排者）
   ├── MCP → Prometheus：查告警指标详情
   ├── MCP → K8s：查服务状态/日志
   └── 判断：问题类型 → 决定委派给谁
② 诊断 Agent（A2A 被委派者）
   ├── 接收 Task（含上下文：告警信息 + 初步数据）
   ├── MCP → 日志系统：深度检索
   ├── MCP → 追踪系统：查调用链
   └── 产出诊断结论（Artifact）
③ 修复 Agent
   ├── 接收修复任务（含诊断结论）
   ├── MCP → CI/CD：触发回滚/重启
   └── 回传结果
④ 分流 Agent：汇总 → 通知（钉钉/飞书，MCP 调用）
```

**这个链路的工程要点**：

```text
① 任务上下文传递：委派时带上"中间结果"（诊断数据），避免接收方重复查
② 失败回退：诊断 Agent 失败 → 分流 Agent 降级（人工介入或简化诊断）
③ 审计：全链路 Task 状态与消息留痕（谁委派了谁、结果如何）
④ 超时：每个委派设置超时（防链式挂起）
```

> 🎯 **核心要点**：Incident 链路是"**MCP 横向（每层接工具）+ A2A 纵向（Agent 间委派）**"的教科书——**每个 Agent 内部是 MCP 工具集，Agent 之间是 A2A 委派链**。

## 5. A2A 安全：Agent Card 与身份

**A2A 的安全模型**（2026 状态）：

```text
核心风险：身份伪造（伪造 Agent Card 骗取任务/数据）

安全措施：
① Agent Card 签名：生产环境拒绝未签名 Agent Card
   → 验证 Card 的发布者身份（类似 TLS 证书链）
② 任务授权：委派任务前校验接收方身份与权限
③ 传输安全：TLS 加密（与 MCP 一致）
④ 审计：协作全程日志（委派/消息/产物）

A2A 与 MCP 的安全差异：
  MCP 的风险重点是"工具投毒"（描述注入）
  A2A 的风险重点是"身份伪造"（Card 欺骗）
```

**企业落地的 A2A 安全清单**：

```text
① 内网部署：Agent 间通信不出内网（网络隔离）
② 身份管理：企业 IdP 对接（与 MCP 的 Enterprise Managed Authorization 呼应）
③ 白名单协作：只允许与"已知 Agent Card"协作
④ 审批门：跨组织委派需要审批（不可逆操作）
```

> 🎯 **核心要点**：A2A 安全主线 = "**签名 Agent Card（防伪造）+ 网络隔离（防外联）+ 白名单协作（防未知）**"——与 MCP 的"工具投毒防御"互补，构成 2026 Agent 安全的完整拼图。

## 6. A2A 的实现与生态

**A2A 的实现方式**：

```text
① 框架内置：主流框架（LangGraph/AutoGen 等）逐步支持 A2A 互操作
② 独立 SDK：A2A 官方 SDK（Python/TypeScript/Java 生态跟进中）
③ HTTP 传输：基于 JSON-RPC over HTTP（与 MCP 传输层同思路）
④ 网关集成：企业 Agent Gateway（AAIF 项目）统一管理与策略执行
```

**A2A 生态 2026 状态**：

| 维度 | 状态 |
|------|------|
| 协议版本 | v1.0 稳定（2025-04 发布后快速收敛） |
| 生产采用 | 150+ 组织生产使用 |
| 框架支持 | 主流框架逐步原生支持 |
| 与 MCP 关系 | 分层共存（AAIF 同时治理两者） |
| 国内生态 | 与 MCP 同步跟进中 |

**实现选型建议（2026）**：

```text
同进程多 Agent → 框架原生协作（LangGraph 图），无需 A2A
跨服务/跨组织 Agent → A2A（标准化互操作）
混合 → 内部框架协作 + 对外 A2A 暴露（边界层适配）
```

> 🎯 **核心要点**：A2A 的落地判断 = "**同进程用框架、跨服务用 A2A**"——2026 年它已从"新协议"进入"生产标准"阶段（150+ 组织）；与 MCP 共同构成 Agent 连接与协作的完整协议栈。
