## 1. 范式原理

### 1.1 定义

```text
Plan-and-Execute（PnE，源于 Plan-and-Solve）：
  计划与执行分离为两个阶段

流程：
  Planner（计划器）：
    生成完整有序的步骤列表（一次/少量调用）
  Executor（执行器）：
    逐步执行计划（每步一次调用）

关键特征：
  计划显式（可审计、可修改）
  执行独立（步骤间无需重新规划）
  → 对比 ReAct 的"边想边做"
```

### 1.2 与 ReAct 的本质区别

| 维度 | ReAct | Plan-and-Execute |
|------|:---:|:---:|
| 计划时机 | 每步动态决策 | 先完整计划 |
| 计划形态 | 隐式（Thought 序列） | 显式（步骤列表） |
| 执行方式 | 决策-行动交替 | 按计划逐步执行 |
| 长任务 | 漂移（20+ 步退化） | 稳定（计划约束） |
| 成本 | 每步推理（高） | 计划一次（低） |
| 灵活性 | 高（随时调整） | 低（计划可能过时） |

```text
核心权衡：
  ReAct：灵活但贵（每步思考）
  PnE：便宜但僵（计划先行）
  → 分水岭：任务可预测性（第 5 节）
```

> 🎯 核心认知：**PnE = "先计划后执行"**——把"思考"集中到计划阶段（一次），执行阶段专注行动（便宜的执行器）。代价是计划可能错/过时；收益是长任务稳定、成本可控、计划可审计。这是长任务场景对 ReAct 漂移的工程化回答。

## 2. Planner 与 Executor

### 2.1 角色分工

```text
Planner（计划器）：
  输入：任务描述 + 可用工具
  输出：有序步骤列表（含每步的预期工具/输出）
  模型选择：强模型（计划质量关键）

Executor（执行器）：
  输入：单步指令
  输出：执行结果（工具调用）
  模型选择：便宜模型（步骤简单）

分工的意义：
  强模型只用于计划（一次）
  便宜模型用于执行（多次）
  → 成本优化的核心（见下节）
```

### 2.2 实现示例

```python
# 简化 PnE 实现
def plan_and_execute(llm_planner, llm_executor, tools, task, max_steps=10):
    # ① 计划（一次调用）
    plan = llm_planner.invoke(f"为任务制定步骤计划: {task}\n"
                              f"可用工具: {list(tools)}")
    steps = parse_steps(plan)          # 解析为步骤列表

    results = []
    for step in steps[:max_steps]:
        # ② 执行（每步一次调用，便宜模型）
        result = llm_executor.invoke(step, tools=tools)
        results.append(result)
    return results
```

## 3. 成本分析

### 3.1 成本模型

```text
ReAct 的成本（N 步）：
  每步：输入（scratchpad 增长）+ 输出（推理）
  总成本 ≈ Σ(1..N) 每步成本（scratchpad 递增）

PnE 的成本（N 步）：
  计划：1 次强模型调用（大输出）
  执行：N 次便宜模型调用（小输出）
  总成本 ≈ 计划一次 + N × 执行单步

对比（10 步任务，检索共识）：
  ReAct：10 步 × 增长的上下文（3-5 倍于 PnE）
  PnE：计划（大）+ 10 × 执行（小）
  → PnE 可节省 3-5 倍 token
```

### 3.2 成本来源分解

| 成本项 | ReAct | PnE |
|--------|:---:|:---:|
| 推理（Thought） | 每步（重复） | 计划一次 |
| 上下文重读 | 每步全量（增长） | 执行步独立（小） |
| 模型选择 | 统一（或分级） | 计划强 + 执行便宜 |
| 失败重试 | 步内（额外） | 执行步重试（小） |

```text
成本结论（2025-2026 共识）：
  长任务（6+ 步）→ PnE 成本优势显著
  短任务（<5 步）→ 差异不大（ReAct 灵活性更值）

工程建议：
  成本敏感 + 步骤可预测 → PnE
  灵活性优先 + 短任务 → ReAct
```

## 4. 混合变体

### 4.1 重规划（Replanning）

```text
重规划：执行中发现意外 → 触发重新计划

流程：
  执行步骤 → 结果异常/新信息
  → Executor 通知 Planner（或自身重计划）
  → 更新剩余计划 → 继续执行

解决 PnE 的核心缺陷（计划过时）：
  静态计划 vs 动态环境
  → 重规划 = PnE 的"适应性补丁"

实现：
  检查点（每 K 步评估是否需要重计划）
  异常触发（工具结果不符预期）
```

### 4.2 层次化计划（Hierarchical Planning）

```text
层次化：两级计划
  Phase 级计划（粗粒度阶段）
  每阶段内 Step 级计划（细粒度）

流程：
  Planner：阶段列表（phase-level）
  每阶段开始 → Step 级计划（step-level）
  执行 → 下一阶段

价值：
  计划粒度与执行反馈匹配
  阶段间可调整（比全局计划灵活）
  复杂度管理（长任务分解）

适用：非常长的任务（研究/工程）
```

### 4.3 有界 ReAct（Bounded ReAct）

```text
有界 ReAct：ReAct 循环 + 强制检查点

流程：
  ReAct 执行 → 第 N 步强制检查
  → 评估进展（是否需要重计划/继续/终止）
  → 继续（或重计划）

本质：ReAct 与 PnE 的融合
  ReAct 的灵活性 + PnE 的计划锚点

适用：
  无法完全预先计划（ReAct 理由）
  但需要控制漂移（PnE 理由）
  → 长任务的折中方案
```

| 变体 | 机制 | 适用 |
|------|------|------|
| 重规划 | 意外触发重计划 | 环境动态 |
| 层次化 | 阶段+步骤两级 | 超长任务 |
| 有界 ReAct | ReAct + 检查点 | 半可预测 |

## 5. 分水岭：何时选 PnE

### 5.1 选择规则（Anthropic 建议）

```text
选择规则（2025-2026 共识）：
  "能预先写清单吗？"
    能（步骤可枚举、可预测）→ Plan-and-Execute
    不能（每步需要自适应推理）→ ReAct

步骤数分水岭：
  < 4-5 步：ReAct（灵活性价值 > 成本差异）
  6+ 步：PnE（成本与稳定性优势显现）

综合判断：
  可预测 + 长任务 → PnE（或变体）
  不可预测 + 短任务 → ReAct
  不可预测 + 长任务 → 有界 ReAct/重规划
```

### 5.2 场景对照

| 场景 | 推荐 | 理由 |
|------|------|------|
| 数据采集（固定步骤） | PnE | 步骤可枚举 + 长 |
| 报告生成（多源） | PnE | 计划先行 + 可审计 |
| 客服对话（动态） | ReAct | 每步不可预测 |
| 代码修复（探索） | ReAct | 需动态决策 |
| 大型重构（多文件） | 层次化 PnE | 超长 + 阶段调整 |
| 半可预测流程 | 有界 ReAct | 折中 |

### 5.3 工程决策清单

```text
选 PnE 前的检查：
  ① 步骤真的可枚举吗？（写个清单试试）
  ② 环境稳定吗？（执行期间变化大 → 重规划）
  ③ 成本敏感吗？（长任务 PnE 省 3-5 倍）
  ④ 需要计划可审计吗？（PnE 计划是产物）

选 ReAct 的理由：
  ① 每步都不可预测
  ② 任务短（<5 步）
  ③ 灵活性 > 成本
```

## 6. 工程实践

### 6.1 生产配置清单

```text
PnE 生产化五件事：
  ① 计划 Schema（步骤格式：指令/工具/预期输出）
  ② 计划验证（格式/可行性检查）
  ③ 执行器工具接口（与计划匹配）
  ④ 重规划触发条件（异常/检查点）
  ⑤ 计划审计（可观测性：计划是产物）

模型选择：
  Planner：强推理模型（计划质量）
  Executor：便宜模型（成本）
  重规划：强模型（关键决策）
```

### 6.2 失败处理

```text
PnE 的失败模式：
  ① 计划错误（第一步就错）
  ② 计划过时（环境变化）
  ③ 执行失败（工具/数据）

对策：
  ① 计划验证（先检查再执行）
  ② 重规划（异常触发）
  ③ 执行重试 + 降级

调试：
  计划审查（第一步就对吗）
  步骤日志（哪步失败）
  重规划日志（触发是否合理）
```

### 6.3 与框架结合

```text
框架支持：
  LangGraph：Plan/Execute 节点（官方模式）
  CrewAI：计划-执行任务抽象
  自研：Planner/Executor 两个 LLM 调用

2025-2026 趋势：
  推理模型内化计划（06 模块）→ 外部 PnE 简化
  但显式 PnE 仍用于：可审计计划/成本控制/团队协作
  → 计划产物（plan artifact）价值不变
```

> 🎯 **核心要点**：PnE = "先计划后执行"——强模型计划一次、便宜模型执行多次，长任务成本省 3-5 倍、计划可审计。分水岭清晰：**步骤可预先枚举（6+ 步）→ PnE；不可预测（<5 步）→ ReAct**。混合变体解决 PnE 的僵化（重规划/层次化/有界 ReAct）；2025-2026 推理模型内化计划后，显式 PnE 的价值聚焦在"计划产物可审计"与"成本控制"。
