## 1. 范式家族概览

### 1.1 共同思想

```text
反思范式的核心：
  生成（Generation）→ 批评（Critique）→ 改进（Improvement）

共同前提：
  ① 有"评价"手段（验证器/标准/自我判断）
  ② 迭代能带来改进（错误可识别、可修正）

家族成员：
  Reflexion：失败 → 语言反思 → 重试（episodic memory）
  Self-Refine：生成 → 自我反馈 → 精炼（循环）
  ToT：树状搜索 + 自评 + 回溯（搜索）
  Evaluator-Optimizer：外部评估器循环（02 模块工作流）

与 Evaluator 的区别：
  Evaluator-Optimizer：代码控制（工作流）
  反思范式：模型自我批评（范式）
```

### 1.2 适用的前提

```text
反思有效的前提（关键）：
  ① 有可验证的信号（测试/编译器/标准答案）
  ② 失败模式是"接近正确"（可修正）

无效的情况（自我确认偏差）：
  开放式创作（无客观标准）
  模型自信的错误（自我批评也错）

Anthropic 的建议：
  "有 pass/fail 信号且失败模式是'差点就对'时使用"
  → 代码（测试信号）是反思的最佳场景
```

> 🎯 核心认知：**反思范式 = "失败后的自我修正"**——通过语言反馈（而非权重更新）让 Agent 从错误中学习。有效性依赖两个前提：可验证的信号（测试/标准）与可修正的失败（接近正确）。代码生成（有编译器/测试）是反思范式的最佳应用场景。

## 2. Reflexion

### 2.1 原理

```text
Reflexion（Shinn et al. 2023）：
  强化学习的语言版本（不更新权重）

循环：
  ① 执行任务（Agent 轨迹）
  ② 自我评分（对输出评估）
  ③ 语言反思（写下失败原因）
  ④ 反思存入"情景记忆"（episodic memory）
  ⑤ 带着反思重试

关键：反思是"语言"而非梯度
  → 反思文本作为下次尝试的上下文
```

### 2.2 实现流程

```text
Reflexion 的典型循环（代码任务）：

  尝试 1：
    生成代码 → 运行测试 → 失败（2/5 通过）
    反思：数组越界，未处理空输入
  尝试 2：
    输入 = 任务 + 反思1（情景记忆）
    生成改进代码 → 测试 → 失败（4/5 通过）
    反思：还有边界情况未覆盖
  尝试 3：
    输入 = 任务 + 反思1 + 反思2
    生成 → 测试 → 通过（5/5）

效果（论文，HumanEval）：
  GPT-4 基础：91% pass@1（此前 SOTA 80%）
  → +11 个百分点的显著提升
```

### 2.3 优劣

| 优点 | 缺点 |
|------|------|
| 显著提升（有信号时） | 依赖验证器（无信号失效） |
| 无权重更新（简单） | 成本翻倍+（多轮） |
| 记忆累积（越试越好） | 自我确认偏差（开放式） |
| 与 ReAct 兼容（反思增强） | 反思质量影响效果 |

```text
适用判断：
  有测试/编译器 → 强烈适用（代码/数学）
  有标准答案 → 适用（QA/推理）
  开放式创作 → 慎用（自我确认）

工程注意：
  反思质量 > 反思次数（高质量反思一次胜过低质量多次）
  成本控制（最大尝试次数）
```

## 3. Self-Refine

### 3.1 原理

```text
Self-Refine（Madaan et al. 2023）：
  同一模型：生成 → 自我反馈 → 精炼（迭代）

循环：
  ① 生成（G）：初始输出
  ② 反馈（F）：模型批评自己（找出问题）
  ③ 精炼（R）：根据反馈改进输出
  ④ 迭代直到收敛/上限

与 Reflexion 的区别：
  Reflexion：失败后反思（重试整个任务）
  Self-Refine：单输出内精炼（反馈-改进循环）
```

### 3.2 实现与效果

```text
Self-Refine 循环（单任务内）：
  生成 → 自我反馈 → 精炼 → 再反馈 → ... → 输出

效果（论文）：
  多个任务提升 20%（平均）
  代码/文案/翻译等均有改进

关键：反馈质量
  同一模型自我反馈（无外部信号）
  → 依赖模型自我批评能力
  → 强模型效果好、弱模型自我确认

对比 Reflexion：
  Self-Refine：单轮任务内迭代（精炼）
  Reflexion：跨尝试记忆（重试）
  → 可组合（精炼 + 重试）
```

### 3.3 适用与注意

```text
适用：
  输出可改进（文本/代码/方案）
  模型足够强（自我批评可靠）

注意：
  反馈的"具体性"（具体问题 > 笼统批评）
  收敛判断（改进停滞即停止）
  成本（每轮 2-3 次调用）

工程建议：
  Self-Refine 作为"输出精炼"步骤
  与外部验证器结合（有信号时优先外部）
```

## 4. Tree of Thoughts

### 4.1 原理

```text
Tree of Thoughts（ToT，Yao et al. 2023）：
  把思维链从"线"扩展为"树"（搜索）

机制：
  ① 分支：每步生成多个候选（思路）
  ② 评估：对候选自评（价值/可行性）
  ③ 搜索：选择分支继续（BFS/DFS）
  ④ 回溯：分支失败 → 回到其他候选

对比 CoT：
  CoT：一条线走到底（无回溯）
  ToT：树状搜索（可回溯、可评估）
  → ToT 是"搜索增强的推理"
```

### 4.2 效果与代价

```text
效果（论文，Game of 24）：
  GPT-4 + CoT：4% 成功率
  GPT-4 + ToT：74% 成功率
  → 搜索 + 评估的巨大提升

代价：
  计算量爆炸（每步多分支 × 深度）
  评估质量依赖模型

适用（2025-2026 共识）：
  搜索密集型任务（谜题/规划/组合）
  需要探索多个路径的场景
  非通用（成本高，日常任务用不到）

对比 Agentic Reasoning（06 模块）：
  o1/R1 的内部搜索（隐式 ToT）
  → ToT 的外部实现被推理模型内化
```

### 4.3 工程判断

```text
ToT 的使用判断：
  ① 任务有"中间评估"价值吗？（能判断部分解）
  ② 搜索空间合理吗？（分支 × 深度可控）
  ③ 成本可接受吗？（多分支 = 多调用）

2025-2026 现实：
  显式 ToT 实现较少（成本高）
  推理模型内化搜索（06 模块）
  → ToT 是"思想"（搜索+评估），实现让给模型
```

## 5. 验证器驱动范式

### 5.1 验证器的价值

```text
验证器（Verifier）：对输出的客观评估

验证器类型：
  ① 确定性：测试/编译器/规则（最可靠）
  ② 模型：LLM 评估（有标准时）
  ③ 人工：人工检查（高风险）

反思范式的关键：
  验证器质量决定反思质量
  外部验证器 > 自我批评（可靠性）

工程模式：
  生成 → 验证 → 失败反馈 → 改进
  = Evaluator-Optimizer（工作流版）
  = Reflexion（范式版）
  → 核心都是"验证驱动的迭代"
```

### 5.2 测试驱动 Agent（TDD for Agents）

```text
代码 Agent 的最佳实践（2025-2026）：
  先写测试 → Agent 生成实现 → 测试验证 → 失败反馈

流程：
  ① 任务 → 测试用例（LLM/人工）
  ② Agent 实现（ReAct/PnE）
  ③ 运行测试 → 结果作为观察
  ④ 失败 → 反馈（错误信息）→ 改进

价值：
  验证器 = 测试（客观、可执行）
  → 反思范式的理想信号源

案例（Claude Code 等）：
  SWE-bench 高分系统都依赖测试验证
  → 测试是代码 Agent 的"地面真相"
```

### 5.3 范式组合

```text
反思范式的组合模式：
  ReAct + Reflexion：失败后反思重试
  PnE + 验证：每步验证（计划执行质量）
  Self-Refine + 测试：精炼直到测试通过
  ToT + 启发式：搜索评估

2025-2026 趋势：
  推理模型内化反思（06 模块）
  外部反思用于：可审计、成本控制、弱模型增强
  → 反思"思想"保留，"实现"向模型迁移
```

## 6. 工程实践

### 6.1 生产配置清单

```text
反思范式生产化五件事：
  ① 验证器设计（测试/规则/评分——最优先）
  ② 反思格式（结构化：失败原因/改进方向）
  ③ 尝试上限（成本控制：2-5 次）
  ④ 记忆管理（反思累积 vs 上下文膨胀）
  ⑤ 可观测性（尝试轨迹/反思文本）

验证器优先级：
  确定性（测试）> 模型评估（有标准）> 自我批评
  → 外部信号永远优先于自我感觉
```

### 6.2 成本控制

```text
反思范式的成本模型：
  每次尝试 = 1 次生成 + 反思（额外）
  3 次尝试 ≈ 4-5 次调用（vs 1 次无反思）

控制手段：
  ① 尝试上限（最大 N 次）
  ② 反思压缩（只保留关键失败）
  ③ 验证器先行（先便宜验证再反思）
  ④ 分级模型（生成强 + 反思便宜）

ROI 判断：
  反思收益 > 成本时使用
  （代码任务：测试通过率提升明显）
```

### 6.3 调试方法

```text
反思 Agent 的调试：
  ① 检查反思质量（反思是否找对根因）
  ② 验证器正确性（测试是否合理）
  ③ 尝试轨迹（第几次改进的关键）

常见问题：
  反思笼统 → 改进"具体性"提示
  验证器误判 → 修正测试/标准
  重复失败 → 反思未利用（上下文丢失）
  自我确认 → 换外部验证器
```

> 🎯 **核心要点**：反思范式家族 = "生成-批评-改进"——Reflexion（失败后语言反思重试，HumanEval 91%）、Self-Refine（输出内自我精炼）、ToT（树状搜索 + 自评回溯，Game of 24: 4%→74%）。有效性的前提：**可验证的信号（测试/标准）+ 接近正确的失败**。验证器驱动（TDD for Agents）是最佳实践；2025-2026 推理模型内化反思后，外部反思聚焦"可审计 + 成本控制 + 弱模型增强"。
