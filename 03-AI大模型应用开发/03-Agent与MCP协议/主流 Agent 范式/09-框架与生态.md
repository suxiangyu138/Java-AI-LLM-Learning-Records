## 1. 框架全景

### 1.1 主要框架（2025-2026）

| 框架 | 定位 | 特点 |
|------|------|------|
| LangGraph | 图状态机（通用） | 持久检查点、1.0（2025-10） |
| OpenAI Agents SDK | 模型原生（官方） | Swarm 继任、内置循环 |
| CrewAI | 多 Agent 团队 | 角色/任务抽象 |
| Microsoft Agent Framework | 企业级 | Azure 集成 |
| AutoGen v0.4+ | 多 Agent 研究 | 事件驱动 |
| LangChain4j（Java） | Java LLM 框架 | AiServices 工具调用 |
| Spring AI | Java 生态 | 与 Spring 集成 |

```text
框架的演化（2025-2026）：
  从"手写循环库"到"Agent 运行时"：
    ① 内置模型原生循环（06 模块）
    ② 持久检查点（状态恢复）
    ③ 可观测性（内置追踪）
    ④ 护栏（预算/工具管理）
  → 框架职责 = 循环托管 + 观测 + 护栏
```

### 1.2 框架解决什么

```text
框架的价值（不重复造轮子）：
  ① 循环实现（ReAct/模型原生）
  ② 工具管理（注册/调用/Schema）
  ③ 状态持久化（检查点/恢复）
  ④ 可观测性（轨迹/成本）
  ⑤ 多 Agent 协调（委派/通信）

框架不解决什么：
  范式选择（08 模块决策树）
  工具设计（业务相关）
  评估体系（自建）
  → 框架是"工具"，范式是"思想"
```

> 🎯 核心认知：**框架 = 循环托管 + 观测 + 护栏的工程化**——2025-2026 的框架都向"模型原生运行时"收敛（内置循环、持久检查点、追踪）。选框架看四点：模型支持、工具生态、Java 集成、观测能力；范式选择与工具设计是框架之上的人工作。

## 2. LangGraph

### 2.1 定位

```text
LangGraph：图状态机 Agent 框架（LangChain 生态）

核心模型：
  图（Graph）：节点（处理）+ 边（流转）
  状态（State）：跨节点共享（可持久化）
  检查点（Checkpoint）：状态持久（恢复）

特点：
  ① 灵活（任意图结构 = 任意范式）
  ② 持久（检查点：中断/恢复/人工点）
  ③ 可观测（内置追踪/流式）
  ④ 生态（LangChain 工具/集成）

版本：1.0（2025-10 发布，生产稳定）
```

### 2.2 范式实现

```text
LangGraph 与范式的对应：
  ReAct：create_react_agent（预构建）
  工作流：图节点编排（02 模块模式）
  多 Agent：子图/团队
  人工点：interrupt（HITL）

示例（ReAct Agent）：
  from langgraph.prebuilt import create_react_agent
  agent = create_react_agent(model, tools)

示例（自定义工作流）：
  节点：generate → evaluate → 条件边（pass/fail）
  → 实现 Evaluator-Optimizer

特性：
  检查点 → 会话恢复/人工干预
  流式 → 实时输出
  → 生产级功能（对比轻量库）
```

### 2.3 适用与注意

```text
LangGraph 适用：
  复杂范式（自定义图）
  需要持久状态（长会话/恢复）
  需要人工检查点
  Python 生态

注意：
  学习曲线（图概念）
  与 LangChain 绑定（生态锁定）
  Java 支持有限（LangChain4j 有图支持？——评估）

2025-2026 状态：
  LangGraph 1.0 稳定（生产主流）
  但模型原生趋势下，简单 Agent 用更轻方案
  → 复杂编排/持久状态时选它
```

## 3. OpenAI Agents SDK

### 3.1 定位

```text
OpenAI Agents SDK：官方 Agent 框架（Swarm 继任）

核心抽象：
  Agent：提示 + 工具 + 模型（配置单元）
  Handoff：Agent 间交接（委派）
  Guardrails：护栏（输入/输出检查）

特点：
  ① 模型原生（内置循环——06 模块）
  ② 简单（少量概念）
  ③ 官方支持（OpenAI 模型最优）
  ④ 内置护栏

适用：
  OpenAI 生态
  简单到中等复杂度 Agent
  快速原型 → 生产
```

### 3.2 核心概念

```text
Agent 配置：
  Agent(name, instructions, tools, model)

Handoff（交接）：
  Agent A → Handoff → Agent B（角色切换）
  → 多 Agent 的"轻量委派"

Guardrails：
  输入护栏（内容检查）
  输出护栏（结果验证）
  → 框架级安全

运行循环（模型原生）：
  提示 + 工具 + 预算 → 模型内部循环
  → 开发者不写循环（06 模块的体现）
```

### 3.3 适用与注意

```text
适用：
  OpenAI 模型用户（最佳配合）
  简单-中等 Agent（快速开发）
  模型原生范式（06 模块）

注意：
  绑定 OpenAI（其他模型支持有限？——可配置）
  复杂图编排弱于 LangGraph
  持久状态需自行设计

2025-2026 状态：
  Agents SDK 是 OpenAI 生态标准
  与 Responses API 深度集成
  → "官方最简单路径"
```

## 4. CrewAI 与多 Agent 框架

### 4.1 CrewAI

```text
CrewAI：多 Agent 团队框架

核心抽象：
  Agent：角色（role/goal/backstory）
  Task：任务（描述/预期输出）
  Crew：团队（Agent + Task 编排）
  Process：流程（顺序/层次）

特点：
  ① 角色化（类似团队管理）
  ② 任务驱动（任务卡）
  ③ 简单上手（声明式）

适用：
  多 Agent 团队（07 模块）
  角色分离场景（研究/写作/审查）
```

### 4.2 其他多 Agent 框架

```text
AutoGen v0.4+（Microsoft）：
  事件驱动多 Agent
  研究导向（复杂协作研究）

Microsoft Agent Framework：
  企业级（Azure 集成）
  跨语言（C#/Python/JS）

对比（多 Agent 框架）：
  CrewAI：简单（角色/任务）
  AutoGen：灵活（事件驱动）
  Agent Framework：企业（生态）
  → 按复杂度与生态选
```

### 4.3 多 Agent 框架的现实

```text
2025-2026 的多 Agent 现实：
  ① 单 Agent 优先共识（07 模块）
  ② 多 Agent 框架用于"真需要"的场景
  ③ 简单委派可用 Handoff（Agents SDK）
  ④ 复杂团队用 CrewAI/AutoGen

选择建议：
  简单委派 → Agents SDK（Handoff）
  角色团队 → CrewAI
  复杂研究 → AutoGen
  企业 → Agent Framework

注意：多 Agent 的收益需验证（评估）
  → 别为"炫技"引入复杂度
```

## 5. Java 生态

### 5.1 LangChain4j

```xml
<!-- Java LLM 框架：LangChain4j -->
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j</artifactId>
    <version>1.x</version>
</dependency>
```

```java
// AiServices：工具调用（ReAct 思想）
interface Assistant {
    @SystemMessage("你是订单助手，使用工具回答")
    String chat(String userMessage);
}

Assistant assistant = AiServices.builder(Assistant.class)
    .chatLanguageModel(model)
    .tools(new OrderTools())       // 工具注册
    .build();

String answer = assistant.chat("查询订单 123 状态");
// 框架处理：模型调用 → 工具执行 → 继续循环（内置）
```

### 5.2 Spring AI

```xml
<!-- Spring AI：Java 生态 Agent -->
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-openai</artifactId>
</dependency>
```

```java
// Spring AI：ChatClient 工具调用
@Configuration
public class AgentConfig {
    @Bean
    ChatClient chatClient(ChatClient.Builder builder) {
        return builder.defaultSystem("你是订单助手")
            .defaultTools(new OrderTools())     // 工具
            .build();
    }
}

// 使用：chatClient.prompt().user("查询订单 123").call().content()
// 推理模型支持：o1/R1/Thinking 接入
```

### 5.3 Java 生态对比

| 框架 | 定位 | 特点 |
|------|------|------|
| LangChain4j | 通用 LLM 框架 | AiServices 工具循环 |
| Spring AI | Spring 生态 | ChatClient 工具 |
| 自研 | 精确控制 | 循环 + 护栏自建 |

```text
Java Agent 实践：
  简单工具调用 → LangChain4j/Spring AI（内置循环）
  复杂编排 → 自研（或等生态演进）
  多 Agent → 较少（Java 生态弱于 Python）

注意：
  推理模型支持（Java 客户端接入 o1/R1）
  MCP 支持（Java MCP SDK——见 Agent与MCP协议目录）
  → Java Agent 生态在成熟中
```

## 6. 框架选型

### 6.1 选型决策

```text
框架选型四问：
  ① 语言生态？（Python vs Java）
  ② 复杂度？（简单 Agent vs 复杂编排）
  ③ 模型绑定？（OpenAI vs 多模型）
  ④ 生产需求？（持久/观测/护栏）

选型建议：
  Python + 复杂编排 → LangGraph
  Python + OpenAI 生态 → Agents SDK
  Python + 多 Agent 团队 → CrewAI
  Java + Spring → Spring AI / LangChain4j
  Java + 精确控制 → 自研循环
```

### 6.2 选型对照

| 维度 | LangGraph | Agents SDK | CrewAI | LangChain4j |
|------|:---:|:---:|:---:|:---:|
| 语言 | Python | Python | Python | Java |
| 复杂度 | 高（图） | 低（简单） | 中（团队） | 中 |
| 模型 | 多模型 | OpenAI 优先 | 多模型 | 多模型 |
| 持久状态 | ✅（检查点） | 需自建 | 有限 | 有限 |
| 多 Agent | ✅（子图） | ✅（Handoff） | ✅（核心） | 有限 |
| 观测 | ✅（内置） | ✅ | 中 | 中 |

### 6.3 2026 趋势与建议

```text
框架趋势（2025-2026）：
  ① 模型原生收敛（简单循环内置）
  ② 可观测性成为标配（OTel）
  ③ 多 Agent 简化（单 Agent 优先）
  ④ Java 生态追赶（Spring AI 成熟）

学习建议：
  ① 先掌握范式思想（本目录 01-08）
  ② 再选一个框架实践（按生态）
  ③ 工具设计与护栏是核心竞争力
  ④ 关注模型演进（06 模块）> 框架演进

最终建议：
  框架是手段不是目的
  范式理解 + 模型能力 + 工具设计 = Agent 质量
  → 框架选择是"次要决策"
```

> 🎯 **核心要点**：框架生态 2025-2026 = "模型原生运行时"收敛——LangGraph（复杂图/持久）、Agents SDK（官方简单/Handoff）、CrewAI（多 Agent 团队）、Java 生态（LangChain4j/Spring AI）。选型四问：语言、复杂度、模型、生产需求。**框架是手段**——范式理解、模型能力、工具设计才是 Agent 质量的真正决定因素（"框架选择是次要决策"）。
