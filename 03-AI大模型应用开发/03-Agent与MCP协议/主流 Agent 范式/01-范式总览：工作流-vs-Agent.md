## 1. 工作流 vs Agent：定义

### 1.1 核心区别

| 维度 | 工作流（Workflow） | Agent |
|------|:---:|:---:|
| 流程控制 | 预定义代码路径 | LLM 自主决定 |
| 确定性 | 高（可预测） | 低（动态适应） |
| 工具调用 | 代码编排 | 模型自主选择 |
| 适用 | 流程明确 | 流程未知 |
| 调试 | 容易 | 困难 |

```text
Anthropic 的经典定义（《Building Effective Agents》）：
  Workflow：通过预定义代码路径编排 LLM 和工具的系统
  Agent：LLM 动态主导自身流程和工具使用的系统

关键区分：
  流程控制权在谁手里？
  代码（工作流）vs 模型（Agent）

残酷现实：大多数生产"Agent"（LangChain 等构建的）
  实际上是工作流（代码路径是预定义的）
```

### 1.2 为什么区分重要

```text
区分的重要性（工程决策）：
  ① 工作流：可预测、可测试、成本可控
  ② Agent：灵活、但不可预测、成本高

选择错误的结果：
  该用工作流却用 Agent → 成本爆炸 + 不可靠
  该用 Agent 却用工作流 → 无法处理动态任务

Anthropic 的建议（原话）：
  "从最简单的能工作的方案开始"
  "确定性管道能解决 → 用它"

→ 范式选择的第一原则：简单优先（渐进升级）
```

> 🎯 核心认知：**工作流与 Agent 的分界 = "流程控制权"**——代码控制是工作流，模型控制才是 Agent。工程纪律：从工作流开始，只有任务真正需要动态适应时才升级到 Agent（"毕业"条件见第 3 节）。

## 2. Anthropic 的分类框架

### 2.1 五种工作流 + Agent

```text
Anthropic 的完整分类（2024-12 提出，2025-2026 广泛采用）：
  工作流（5 种）：
    ① Prompt Chaining：固定流水线（可选门控）
    ② Routing：分类分发（路由到专用提示/模型）
    ③ Parallelization：并行扇出（独立子任务/投票）
    ④ Orchestrator-Workers：中央 LLM 分解委派
    ⑤ Evaluator-Optimizer：生成-批评循环
  Agent（1 种）：
    全自主 Agent（步骤预算 + 人工检查点）

→ 02 模块详解五种工作流
→ 03-07 模块详解各种 Agent 范式
```

### 2.2 分类的工程价值

```text
为什么这个分类重要：
  ① 提供"模式库"（遇到任务先匹配模式）
  ② 明确升级路径（工作流 → Agent 渐进）
  ③ 控制复杂度（先简单后复杂）

分类的使用方式：
  需求分析 → 匹配模式 → 实现 → 验证
  模式不满足 → 升级（更复杂模式/Agent）

2025-2026 状态：
  Anthropic 的分类成为行业标准
  大多数框架（LangGraph 等）直接实现这些模式
  → 掌握分类 = 掌握 Agent 构建的"设计模式"
```

## 3. 何时用 Agent

### 3.1 毕业条件（Anthropic）

```text
从工作流升级到 Agent 的条件：
  ① 流程在设计时真正未知（无法预先枚举）
  ② 需要大量工具调用且调用顺序不定
  ③ 需要自主决策（根据中间结果调整）

典型场景：
  编码任务（探索代码库 → 修改 → 测试）
  信息检索（多源查询 → 综合）
  复杂问题求解（路径不确定）

反例（不该用 Agent）：
  流程固定的批处理 → Prompt Chaining
  输入分类明确 → Routing
  有明确标准的迭代 → Evaluator-Optimizer
```

### 3.2 Agent 的前提条件

```text
使用 Agent 的前提（Anthropic）：
  ① 模型足够强（弱模型无法可靠自主）
  ② 工具设计良好（工具 schema 比提示更重要）
  ③ 有护栏（步骤预算/人工检查点/日志）

2025-2026 的共识：
  "单 Agent + 强推理模型 + MCP 工具
   优于 多 Agent + 弱模型 + 复杂编排"
  → 模型能力是 Agent 的第一前提

参考（Claude Code）：
  简单循环（bash + 文本编辑器工具）+ 强模型
  Claude Opus 4.7 SWE-bench 87.6%（2026-04）
  → 最简单循环 + 精心设计的工具 > 复杂编排
```

## 4. 可靠性复合定律

### 4.1 定律内容

```text
可靠性复合（Reliability Compounds）：
  每步成功率 p、步骤数 n → 整体成功率 pⁿ

量化示例：
  95%/步：
    5 步 → 77%
    10 步 → 60%
    20 步 → 36%
  99%/步：
    10 步 → 90%
    20 步 → 82%

含义：长链路 Agent 的可靠性指数级衰减
  → 每步都要"高可靠"（而非"高智能"）
```

### 4.2 工程含义

```text
可靠性优先于自主性（Anthropic 的建议）：
  ① 先用确定性/半确定模式（工作流）
  ② Agent 内每步加验证（减少错误传播）
  ③ 步骤预算（限制长度）
  ④ 人工检查点（关键决策）

降低步数的策略：
  ① 工具合并（一次调用完成多件事）
  ② 上下文精简（减少重读）
  ③ 计划先行（Plan-and-Execute 减少试错）

成本含义（复合）：
  步数 × 每步 token = 总成本
  10 步 ReAct 的 token 消耗是 5 步的 2-3 倍
  → 范式选择直接决定成本（08 模块）
```

### 4.3 可靠性设计原则

```text
可靠性设计五原则：
  ① 简单优先（工作流 > Agent）
  ② 步骤压缩（减少链路长度）
  ③ 每步验证（输出校验/工具结果检查）
  ④ 护栏（预算/检查点/回退）
  ⑤ 约束场景（领域限定 Agent 更可靠）

"受约束的领域专用 Agent + 清晰边界"
  > "通用全自主 Agent"
  → 2025-2026 生产共识
```

## 5. 范式选择的第一原则

### 5.1 选择阶梯

```text
范式选择阶梯（从简单到复杂）：
  ① 单次提示（无流程）——最简单
  ② Prompt Chaining（固定流水线）
  ③ Routing / Parallelization（结构化）
  ④ Evaluator-Optimizer（迭代）
  ⑤ Orchestrator-Workers（动态分解）
  ⑥ ReAct（自主推理-行动）
  ⑦ Plan-and-Execute（计划-执行）
  ⑧ 反思增强（Reflexion 等）
  ⑨ 多 Agent / 全自主 Agent

原则：停在"能满足需求的最简单层级"
  → 每一步升级都有明确理由
```

### 5.2 判断问题

```text
选择前的四个问题：
  ① 流程在设计时可知吗？
     可知 → 工作流；未知 → Agent
  ② 有明确的质量标准吗？
     有 → Evaluator-Optimizer；无 → 其他
  ③ 步骤能预先枚举吗？
     能 → Plan-and-Execute；不能 → ReAct
  ④ 需要并行吗？
     需要 → Parallelization/Orchestrator

（完整决策树见 08 模块）
```

### 5.3 2025-2026 的现实

```text
范式选择的现状：
  ① 工作流仍是生产默认（确定性优先）
  ② Agent 场景集中在：编码/研究/客服/自动化
  ③ 推理模型改变选择（06 模块）：
     模型内化循环 → 外部范式可简化
  ④ 成本与可靠性成为首要权衡

一句话总结：
  "大多数任务用工作流，少数任务用 Agent，
   用 Agent 时选择最简循环 + 最强模型"
```

> 🎯 **核心要点**：Agent 构建的第一性原理 = **工作流优先、可靠性优先**——Anthropic 的分类提供模式库，毕业条件决定何时升级，可靠性复合定律警告长链路的指数衰减。工程纪律：停在最简单的满足需求的层级；用 Agent 时"最简循环 + 强模型 + 好工具"优于复杂编排。范式选择是"克制"的艺术，不是"炫技"的舞台。
