## 1. 三层记忆架构

```text
人类记忆 → AI Agent 对应设计：

感觉记忆 (几秒)    → 当前对话的 Context Window
工作记忆 (几分钟)   → Session 内的对话历史
长期记忆 (几天-年) → 持久化存储 (MEMORY.md / Vector DB)

实现映射：
┌──────────────────┐
│ L1: Context Window│ ← 当前轮对话 (128K tokens)
├──────────────────┤
│ L2: Session Memory│ ← 本次会话完整历史 (Frozen Snapshot)
├──────────────────┤
│ L3: Long-term     │ ← 跨会话持久化 (文件 / 向量库)
└──────────────────┘
```

| 层级 | 存储 | 容量 | 速度 | 什么时候用 |
|------|------|:---:|:---:|------|
| **L1 上下文中** | GPU 显存 | 128K tokens | 极快 | 当前轮对话 |
| **L2 会话** | 内存 | 无限制 | 快 | 同一会话的历史 |
| **L3 长期** | 磁盘/向量库 | 无限制 | 慢 | 跨会话的知识 |

## 2. 记忆写入循环

### 2.1 写入决策

```text
不是所有对话都值得记下来

写入判断标准：
  ✅ 用户明确表达偏好： "我喜欢简短的代码，不要注释"
  ✅ 项目特定知识：    "我们这个系统用的是 Kafka 不是 RabbitMQ"
  ✅ Agent 学到的教训： "直接修改文件前必须先备份"
  ❌ 一次性的信息：     "帮我查一下今天的天气"
  ❌ 纯闲聊：          "讲个笑话"
  ❌ 已经记录过的：    去重检查
```

### 2.2 写入触发机制

```python
class MemoryWriteLoop:
    def __init__(self, llm):
        self.llm = llm
        self.buffer = []     # 写入缓冲区

    def should_write(self, turn: dict) -> bool:
        """判断这一轮对话是否值得写入记忆"""
        prompt = f"""判断以下对话是否包含需要长期记住的信息：

对话：{turn}

需要记住的信息特征：
- 用户偏好或习惯
- 项目特定知识
- 重要的经验教训
- 跨会话需要的信息

返回 JSON:
{{"should_write": true/false, "reason": "...", "importance": 1-5}}
"""
        result = self.llm.chat_json(prompt)
        return result["should_write"] and result["importance"] >= 3

    def write_cycle(self, conversation: list[dict]):
        for turn in conversation:
            if self.should_write(turn):
                memory = self._extract_memory(turn)
                self._write_to_storage(memory)
                self.buffer.append(memory)

        # 批量写入优化
        if len(self.buffer) >= 5:
            self._flush_buffer()
```

## 3. 记忆压缩循环

### 3.1 为什么需要压缩

```text
问题：Agent 运行 1000 次会话后，MEMORY.md 爆了

原始记忆（无压缩）：
  "用户 5 月 1 日说喜欢 Java 17"
  "用户 5 月 3 日说要用 Spring Boot 3.2"
  "用户 5 月 8 日说数据库是 PostgreSQL 16"
  ...持续增长 → 文件无限膨胀

压缩后：
  "项目技术栈：Java 17 + Spring Boot 3.2 + PostgreSQL 16（2025年5月确立）"
```

### 3.2 压缩策略

```python
class MemoryCompressor:
    def __init__(self, max_size=2200):  # 对应 MEMORY.md 的 2200 字符限制
        self.max_size = max_size

    def compress_cycle(self, memories: list[str]) -> str:
        """压缩循环：去重 → 合并 → 摘要 → 去旧"""
        if len("".join(memories)) <= self.max_size:
            return "\n".join(memories)

        # 1. 去重
        unique = self._deduplicate(memories)

        # 2. 同主题合并
        grouped = self._group_by_topic(unique)

        # 3. LLM 摘要压缩
        compressed = []
        for topic, items in grouped.items():
            if len(items) == 1:
                compressed.append(items[0])
            else:
                summary = self.llm.chat(
                    f"将以下关于'{topic}'的记忆合并为一条简洁的记录：\n" +
                    "\n".join(items)
                )
                compressed.append(summary)

        return "\n".join(compressed)
```

### 3.3 Frozen Snapshot 模式

```text
关键设计决策：什么时候注入记忆？

方案 A: 实时注入
  写入记忆 → 立即更新 System Prompt
  问题: System Prompt 变了 → 前缀缓存失效 → API 成本暴涨 10x

方案 B: Frozen Snapshot（推荐）
  会话开始时: 读取 MEMORY.md → 创建 Snapshot → 注入 System Prompt
  会话进行中: 写入磁盘（持久化）但不更新 System Prompt
  下次会话: 加载最新 MEMORY.md
  优势: 整个会话前缀缓存稳定 → 成本降低 90%

→ 这是 Hermes-Agent 和 Claude Code 的通用做法
```

## 4. 记忆检索循环

```text
检索循环：什么时候查记忆？查多少？怎么排序？

被动检索（每轮自动）：
  用户提问 → 检索相关记忆 → 注入上下文 → LLM 回答

主动检索（Agent 主动查）：
  Agent 在 Think 阶段 → 判断"我需要回顾之前的..." → 主动检索

检索 → Rerank → 注入 的循环：
  Query → Embedding → 向量检索 Top-N
  → LLM Rerank（判断哪条真正相关）
  → 注入 Top-K 条 → 如果不够 → 调整 Query → 再次检索
```

## 核心要点回顾

- 三层记忆：L1 上下文(128K) / L2 会话(内存) / L3 长期(磁盘/向量)
- 写入循环：判断值得记 → 提取 → 写入 → 批量冲刷
- 压缩循环：去重 → 合并 → LLM 摘要 → 去旧（防止无限膨胀）
- Frozen Snapshot = 会话开始时拍快照注入，会话内写入不更新 → 缓存友好
- 检索循环：Query → Embedding → 向量检索 → Rerank → 注入
