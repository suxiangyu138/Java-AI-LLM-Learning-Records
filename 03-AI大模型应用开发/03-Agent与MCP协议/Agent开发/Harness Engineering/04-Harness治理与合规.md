## 1. 治理核心逻辑：继承而非集成

> 🎯 **核心认知**：Agent 治理不是发明一套新治理体系，而是**让 Agent 继承组织已有的治理框架**——身份、权限、审计、合规能力直接复用。

```
错误姿势（事后集成）              正确姿势（治理继承）
├── Agent 独立于治理体系          ├── Agent 接入企业身份（SSO/OAuth）
├── 自建一套 Agent 权限           ├── 复用 RBAC 权限体系
├── 日志另存一套                  ├── 审计日志进企业 SIEM
└── 合规检查另起炉灶              └── 沿用现有合规流程与审批门
```

| 继承对象 | 继承方式 |
|---------|---------|
| 身份 | SSO/OAuth/OIDC 统一身份 |
| 权限 | RBAC/ABAC 现有角色体系 |
| 审计 | 日志接入现有 SIEM/审计平台 |
| 审批 | 复用现有审批门流程 |
| 策略 | OPA 等策略引擎统一管理 |

> 💡 **判断标准**：如果一个 Agent 需要「为它单独设计权限系统」，说明治理设计出了问题——它应该直接活在组织的治理框架里。

## 2. 全生命周期治理：Agent DLC

### 2.1 治理全生命周期

```text
Agent DLC 治理视图
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ 构建治理   │→│ 测试治理   │→│ 存储治理   │→│ 部署治理   │→│ 运行治理   │→│ 治理治理   │
│ 规范/模板  │ │ 门禁/Evals│ │ 资产目录   │ │ 审批/灰度  │ │ 监控/约束  │ │ 回收/审计  │
└──────────┘  └──────────┘  └──────────┘  └──────────┘  └──────────┘  └──────────┘
```

### 2.2 AI 资产目录（AI Asset Catalog）

> ⚠️ 组织需要知道：**存在哪些 Agent？谁拥有它们？是否已有 Agent 解决当前问题？**——答案来自资产目录。

| 目录功能 | 说明 | 解决痛点 |
|---------|------|---------|
| **自动发现** | 扫描运行时/仓库中的 Agent | 影子 Agent 蔓延 |
| **注册登记** | 名称/用途/所有者/版本/模型 | 责任归属 |
| **所有者绑定** | 每个 Agent 绑定负责人 | 出事找得到人 |
| **标准评分卡** | 安全/性能/合规评分 | 门槛统一 |
| **复用查询** | 新建前先查是否已存在 | 重复建设 |

```yaml
# 资产目录条目示例
agent:
  id: AGT-0042
  name: order-refund-agent
  owner: 支付团队-张工
  model: claude-sonnet-5
  version: 2.3.1
  tools: [mcp-payment, mcp-notify]
  scorecard: {security: 92, compliance: 88, reliability: 95}
  status: production
  last_audit: 2026-07-15
```

## 3. 流水线内治理

### 3.1 核心思想

Agent 作为流水线步骤执行时，**继承流水线已有的治理能力**：

```text
治理继承映射
├── OPA 策略门禁     → Agent 动作同样过策略检查
├── RBAC 权限控制    → 控制谁能触发 Agent 的权限 = 控制 Agent 的权限
├── 审批门           → Agent 的高危动作走同一审批流
└── 审计追踪         → Agent 的每次执行进同一审计体系

核心原则：
- 限制生产部署的策略同样限制 Agent
- 控制谁能推送生产环境的 RBAC 同样控制谁能触发 Agent
```

### 3.2 策略即代码示例

```rego
# OPA 策略示例：Agent 动作策略
package agent_policy

# 高危动作必须有人类审批标记
deny[msg] {
  input.action.type == "delete"
  not input.approval.human_approved
  msg := "删除类操作必须经人工审批"
}

# Agent 只能访问声明的数据源
deny[msg] {
  input.action.target == "database"
  not input.agent.declared_data_sources[input.action.db]
  msg := sprintf("数据库 %v 未在 Agent 声明范围", [input.action.db])
}
```

## 4. 可审计性：从提示词到契约

### 4.1 传统可审计性的缺陷

```text
传统模式：提示词（不可审计）
├── 行为写在自然语言提示里 → 不可验证 Agent 实际做了什么
├── 模型声称 ≠ 实际执行     → 无法确认真实性
└── 不可检查                → 失败时无诊断输出

目标模式：契约（可审计）
├── 行为迁入代码所有的"契约"
└── 每次产出答案都是可审计的工程制品
```

### 4.2 契约化五件套（arXiv《From Prompts to Contracts》）

| 契约组件 | 作用 | 说明 |
|---------|------|------|
| **源清单（Source Manifests）** | 定义可用数据源 | 明确 Agent 能碰哪些数据 |
| **源背书声明（Source-backed Claims）** | 定义可进上下文的陈述 | 不可信内容过滤 |
| **路由元数据** | 绑定问题到实体 | 溯源：这个问题来自哪 |
| **答案契约** | 定义可见输出 | 输出结构受约束 |
| **追踪记录** | 记录答案如何组装 | 每个答案可还原组装过程 |

### 4.3 可审计执行链

```text
每次 Agent 执行的完整溯源链
├── 触发者：谁/什么触发了 Agent（用户请求/定时任务/事件）
├── 模板版本：哪个提示词/契约版本
├── 每项动作：工具调用 + 参数 + 时间戳
├── 中间结果：决策路径 + 推理摘要
└── 最终结果：交付物 + 验收判定

脱敏要求：提示词与推理链持久化前剥离密钥与 PII
```

> 🎯 **可审计性的验收标准**：给审计员一句话回答三个问题——「它做了什么？为什么这么做？结果可信吗？」——能回答，可审计；不能，回炉。

## 5. 人机共控模式

### 5.1 从自治到共控

> 💡 企业级 AI 应从「自治」（Agent 全自主）转向「**共控**」（人类为核心决策与校准主体，Agent 聚焦战术执行）。

```
共控模式（人机协同控制旋钮）
├── 阈值以下：Agent 自主行动（战术执行）
├── 阈值以上：Agent 提议 → 人类批准（关键决策）
├── 旋钮可调：不重新部署模型即可调整自治边界
└── 人类定位：核心决策与校准主体
```

### 5.2 共控的实施

| 层级 | 自治度 | 人类角色 | 适用场景 |
|------|:---:|---------|---------|
| **完全自主** | 高 | 事后审计 | 低风险内部工具 |
| **提议-批准** | 中 | 审批关键动作 | 生产流程（默认推荐） |
| **协作执行** | 低 | 每步确认 | 高风险合规场景 |
| **人工主导** | 无 | Agent 仅建议 | 核心支付/隐私链路 |

### 5.3 自治边界调整示例

```yaml
# autonomy-config.yaml 自治旋钮配置
autonomy:
  level: propose-approve      # 模式：提议-批准
  auto_actions:               # 阈值以下自动执行
    - read_database
    - send_internal_message
  approval_required:          # 阈值以上必须批准
    - payment_transfer
    - delete_data
    - external_api_call
  adjustable: true            # 可在运行时调整，无需重部署
```

## 6. 治理主体与政策建议

联合国大学《Engineering and Governing the Agent Harness》报告提出的治理主张：

| 建议 | 内容 |
|------|------|
| **Harness 作为治理对象** | 采购与合格评定中要求风险分级的 Harness 保证 |
| **供应链组件化管理** | 技能/MCP/插件/工具包装器视为软件供应链组件 |
| **采购标准** | 纳入可读性、可恢复性与可替换性要求 |
| **开放参考 Harness** | 投资开放参考实现，避免供应商锁定 |
| **AI 治理分层** | 技术层（运行时）+ 组织层（流程）+ 政策层（监管）协同 |

> 💡 治理视角的 Harness：不仅是技术组件，更是**治理对象**——企业采购 Agent 平台时，应把「Harness 是否可读、可恢复、可替换」作为与「模型能力」同等重要的评估维度。

## 7. 治理检查清单

```text
部署前（一次性）：
[ ] Agent 已注册到资产目录，绑定所有者
[ ] 权限继承企业 RBAC，高危动作映射审批门
[ ] 审计日志接入 SIEM，含触发源/动作/结果
[ ] AIBOM 已生成并纳入供应链管理
[ ] 自治边界（旋钮）已配置并文档化

运行中（持续）：
[ ] 影子 Agent 扫描定期执行
[ ] 策略变更走评审并记录（策略即代码）
[ ] 提示词/技能变更留痕可回溯
[ ] 季度安全评分卡更新

事件响应（事故时）：
[ ] 能回放完整执行链（溯源三问）
[ ] 能一键隔离/回滚 Agent
[ ] 审计报告可导出给合规部门
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 治理继承而非集成：Agent 直接活在组织已有身份/权限/审计/审批框架里
> 2. Agent DLC 六阶段治理 + AI 资产目录（自动发现/登记/所有者绑定/评分卡）防影子 Agent
> 3. 可审计性从「提示词」走向「契约」：源清单、背书声明、追踪记录让每次执行可还原
> 4. 人机共控：阈值以下自主、阈值以上批准、旋钮可运行时调整；Harness 本身也是治理对象
