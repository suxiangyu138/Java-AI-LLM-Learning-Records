# 定位与版本演进

> 先回答三个问题：PgVector 在向量存储谱系里站在哪？0.8 升级带来了什么？老教程为什么需要更新？

## 1. 在向量存储谱系中的位置

向量存储分三个象限：**嵌入式单机库**（Chroma、FAISS）、**独立服务向量库**（Milvus、Qdrant、Weaviate）、**通用数据库扩展**（PgVector、Redis Stack、ES kNN）。PgVector 属于第三象限——它不是独立的数据库，而是 PostgreSQL 的一个扩展（Extension），`CREATE EXTENSION vector` 一条命令即可获得向量列类型与相似度索引。

这个身份决定了它的核心价值与边界：

| 维度 | PgVector 的立场 |
|------|----------------|
| 部署 | 零新增服务——PG 集群里"长"出一个向量能力 |
| 数据 | 向量与业务数据同库，支持 JOIN、事务、行级权限 |
| 运维 | 复用 PG 全家桶：备份、监控、复制、高可用 |
| 边界 | 50M-100M 向量上限；无内置 embedding 管道 |

与 Chroma（嵌入式优先）和 Milvus（分布式优先）相比，PgVector 的第一问题不是"它最强"，而是"**我有没有 PG**"——有，且向量需求在规模红线内，它就是成本最低的解。

## 2. 版本演进：0.5 → 0.7 → 0.8.x

| 版本 | 时间 | 核心变化 |
|------|:----:|---------|
| 0.5.x | 2022-2023 | 基础类型 vector、HNSW/IVFFlat 索引、六操作符定型 |
| 0.7.x | 2024 | 稳定期，支持 PG 12-16，社区大规模采用 |
| **0.8.0** | 2025 末 | **iterative scans、sparsevec、binary_quantize、halfvec、并行建索引** |
| 0.8.1 | 2026 初 | sparsevec 稳定、ef_search 默认提升到 40 |
| 0.8.2 | 2026-02 | 修复并行 HNSW 构建 buffer overflow、PG 18 EXPLAIN 兼容 |
| 0.8.3 | 2026-06 | 修复 HNSW vacuum 索引损坏、PG 18 Hamming/Jaccard 性能回退 |
| 0.8.4 | 2026-06-30 | 修复 HNSW vacuum 期间插入错误、IVFFlat 内存超 maintenance_work_mem |
| 0.8.5 | 2026-07-08 | IVFFlat 小表建索引内存优化 |
| **0.8.6** | **2026-07-29** | **当前最新（2026-08 基线）；修复 IVFFlat 32 位系统 buffer overflow** |

版本节奏稳定（每月小版本），升级成本低（0.8.x 内平滑），但 **0.7 → 0.8 跨大版本升级必须 REINDEX 已有 HNSW 索引**（0.8 索引格式有优化，0.8.3 还修过 HNSW vacuum 损坏——旧索引可能带伤）。

## 3. 0.8 的四大增量（理解现状的钥匙）

1. **iterative scans（迭代扫描）**：0.8.0 最重要的修复——此前"WHERE 过滤 + ANN 索引"是 post-filter：索引先按距离取候选，再套 WHERE，过滤选择性高时结果被静默截断。0.8 的迭代扫描在候选不足时**重新进入索引继续扫描**（strict_order 保持排序、relaxed_order 优先补足数量），把"过滤吞结果"从无解变成可配（详见 05 篇）。
2. **sparsevec 稀疏向量**：原生支持 BM25/SPLADE 类稀疏向量（只存非零维度），让"稠密 + 稀疏"混合检索在同库内完成（详见 06 篇）。
3. **binary_quantize 二进制量化**：把 float32 向量压成 bit（1536 维从 6KB 到 192 字节，32× 缩小），配合两阶段检索（量化索引粗召回 + 全精度精排）实现 90-95% 召回（详见 07 篇）。
4. **性能工程**：并行 HNSW 建索引、HNSW 构建快约 40%、SIMD（AVX-512）让 `<#>`/`<->` 计算快 20-30%——同样的机器，0.8 比 0.7 能扛更大的规模。

## 4. 与专用向量库的定位差异

**"已有 PG 就用 PG"的适用边界**：PgVector 强在"关系型能力 + 向量检索"的融合——按业务字段过滤、与业务表 JOIN、事务内写向量、SQL 生态（BI 工具、pg_dump 备份、逻辑复制）。专用向量库强在"规模与检索专项"——亿级以上、过滤感知索引（Qdrant）、分布式扩展（Milvus）、量化与多租户。

判断口诀：**向量是应用的一个功能 → PgVector；向量是应用的核心资产且规模巨大 → 专用库**。50M-100M 向量是公认的经验分水岭——边界之上 PgVector 的内存占用与 post-filter 代价会让位给专用方案（详见 09 篇）。

## 5. 生态位与命名混淆

两个必须澄清的混淆点：一是**扩展名是 `vector` 不是 `pgvector`**（`CREATE EXTENSION vector`），"pgvector" 是项目名/社区名，SQL 里写错会报"extension does not exist"；二是**pgvector 与 pg_embedding 是两个不同的项目**——pg_embedding（Neon 出品）用 HNSW 但 API 不同、活跃度低，**生态与文档都输了，2026 年选型直接排除**。官方推荐与社区事实标准就是 pgvector，Supabase/Neon/TencentDB 等全部内置。

生态成熟度是 PgVector 的另一层竞争力：LangChain/LlamaIndex/Spring AI 官方支持、云厂商（RDS/Aurora/Supabase/TencentDB/阿里云 PolarDB）全部内置、pgvector-java 等语言驱动齐备、大量 RAG 生产案例——"有 PG 就装扩展"的路径已经是最平滑的向量接入方式，新项目选它几乎没有生态风险。

## 6. 0.8 之后的方向

社区路线与观察：**PG 18 兼容性**是 0.8.x 后半程的主线（EXPLAIN 输出、距离操作符性能已在 0.8.2/0.8.3 修复）；**filtered HNSW**（过滤感知索引）是社区讨论多年的方向，若落地将根治 post-filter 短板；**性能工程**持续（SIMD 覆盖更多操作符、索引构建并行度）。给工程实践者的建议：升级到 0.8.4+ 获得 vacuum 修复，**每个小版本发布后关注 CHANGELOG 的 bugfix 类条目**——0.8.x 的修复记录（buffer overflow、索引损坏）说明这类扩展的"稳定"是相对而言的，生产环境锁版本 + 定期升级验证是正确姿势。

**"已有 PG 就用 PG"的适用边界**：PgVector 强在"关系型能力 + 向量检索"的融合——按业务字段过滤、与业务表 JOIN、事务内写向量、SQL 生态（BI 工具、pg_dump 备份、逻辑复制）。专用向量库强在"规模与检索专项"——亿级以上、过滤感知索引（Qdrant）、分布式扩展（Milvus）、量化与多租户。

判断口诀：**向量是应用的一个功能 → PgVector；向量是应用的核心资产且规模巨大 → 专用库**。50M-100M 向量是公认的经验分水岭——边界之上 PgVector 的内存占用与 post-filter 代价会让位给专用方案（详见 09 篇）。

与同目录其他体系的分工：`Chroma/` 体系是嵌入式向量库（轻量原型、<2M 规模）、`Milvus/` 体系是分布式向量库（十亿级、企业能力）、本体系讲"PG 上的向量能力"——三者覆盖"轻 → 中 → 重"完整谱系；通用向量库体系（`04-向量数据库/`）讲索引原理通识与多库横向对比，本体系把 PgVector 这条线做深（类型/操作符/混合检索/Java 集成）。读法建议：先通用体系打底（HNSW 原理），再按场景进 PgVector 或 Chroma 深化。

> 🎯 **核心要点**：PgVector = "PostgreSQL 上的向量能力"，零新增基础设施是最大卖点；0.8 的迭代扫描修复了历史最大缺陷、sparsevec 补上混合检索短板；规模分水岭 50M 向量，之上再谈专用库。
