# 安装与扩展启用

> 从 `CREATE EXTENSION vector` 到生产可用——版本支持矩阵、云厂商形态、Docker 自建、0.7→0.8 升级路径

## 1. 版本支持矩阵

PgVector 以扩展形式随 PostgreSQL 版本提供支持，**选择 PgVector 版本前先确认 PG 版本**：

| PgVector | PostgreSQL 支持 |
|----------|:--------------:|
| 0.7.x | PG 12-16 |
| **0.8.x** | **PG 12-17**（PG 17 必须 0.8+） |
| 0.8.3+ | 兼容 PG 18 部分行为（EXPLAIN 输出、距离操作符性能修复） |

配套注意：PG 18 时代（2026 观察期）0.8.x 已有针对性修复，但正式支持以官方发布为准；云厂商托管的 PG（RDS/Aurora/Supabase 等）内置扩展但**版本可能滞后**，启用前先查 `SELECT extversion FROM pg_extension WHERE extname = 'vector'`。

## 2. 启用与验证

```sql
-- 需要超级用户或扩展安装权限（云厂商常提供 EXTENSION 权限角色）
CREATE EXTENSION IF NOT EXISTS vector;

-- 验证
SELECT extversion FROM pg_extension WHERE extname = 'vector';
-- 0.8.6

-- 冒烟测试：类型、操作符、索引一把通
CREATE TABLE smoke (id bigserial PRIMARY KEY, v vector(3));
INSERT INTO smoke (v) VALUES ('[1,2,3]'), ('[4,5,6]');
CREATE INDEX ON smoke USING hnsw (v vector_cosine_ops);
SELECT id FROM smoke ORDER BY v <=> '[3,3,3]' LIMIT 1;
DROP TABLE smoke;
```

三条注意：**扩展名是 `vector` 不是 `pgvector`**（惯用混淆点）；`CREATE EXTENSION` 只能建一次，团队规范里把它放进迁移脚本首条；无权限时找 DBA 开 `CREATE EXTENSION` 权限，而不是换库绕过。

权限与角色细节：`CREATE EXTENSION` 需要超级用户或 `CREATE` 权限（PG 13+ 支持受信扩展在普通库上由库属主安装）；**向量数据的使用不需要超级用户**——建表、插向量、建索引都是普通权限，所以生产环境的权限设计是"安装时超级用户、使用时普通角色"，不要图省事全库用超户。另外扩展是**库级安装**（每个库独立 `CREATE EXTENSION`），多库环境注意逐库安装，而不是以为一次装全实例生效。

## 3. 部署形态：云厂商与自建

**云厂商托管**（最省心，2026 现状）：AWS RDS/Aurora、Google Cloud SQL、Supabase（免费档内置）、TencentDB for PostgreSQL（内置 0.8.x）、阿里云 PolarDB for PostgreSQL 全部支持——形态差异只在**扩展版本与权限粒度**，SQL 完全一致。选云厂商时把"扩展版本是否 0.8+"列为硬指标：0.7 的 post-filter 缺陷没有 iterative scans 兜底。

云厂商对比速查：

| 平台 | 扩展版本 | 权限模型 | 备注 |
|------|---------|---------|------|
| AWS RDS/Aurora | 随引擎更新，通常新 | 需 rds_superuser | 生产主流 |
| Supabase | 内置（较新） | 免费档可用 | 原型最快 |
| TencentDB PG | 内置 0.8.x | 普通权限可建扩展 | 国内主流 |
| 阿里云 PolarDB | 内置 | 普通权限可建扩展 | 国内主流 |
| 自建/私有化 | 完全可控 | 完全可控 | 版本自由 |

排查"扩展不可用"的清单按序：先 `SHOW shared_preload_libraries`（某些云环境需预加载）；再 `SELECT extversion FROM pg_extension WHERE extname='vector'`（装了没、版本够不够）；然后确认当前库（`\c 库名` 后重试——扩展是库级的）；最后看权限（`\dx` 报权限不足找 DBA）。四条走完，95% 的"装不上"问题定位。

**Docker 自建**（本地开发/私有化）：

```yaml
services:
  pg:
    image: pgvector/pgvector:pg17        # 官方镜像：pg 版本为 tag
    environment:
      POSTGRES_PASSWORD: postgres
    ports: ["5432:5432"]
    volumes: [pg-data:/var/lib/postgresql/data]
volumes:
  pg-data:
```

官方镜像 `pgvector/pgvector` 的 tag 规则是 `pg<版本>`（如 pg16/pg17），**不是 pgvector 版本**——容器内版本跟随 PG 版本走，检查实际版本用第 2 节的查询。自建时注意 PostgreSQL 本体版本与扩展的配套关系（PG 17 必须 PgVector 0.8+）。本机连容器做冒烟：`docker exec -it pg psql -U postgres` 后跑 `CREATE EXTENSION vector; SELECT extversion ...`——镜像内扩展已预装，验证的是"启用"而非"安装"，装不上的问题 90% 出在权限与库选择上（排查清单见下）。

## 4. 升级路径：0.7 → 0.8

跨大版本升级四步，每步都有明确理由：

1. **备份**：pg_dump 或 PITR 就绪——升级失败可回滚。
2. **升级扩展**：安装新版本二进制后 `ALTER EXTENSION vector UPDATE TO '0.8.6';`（或包管理器升级后自动完成）。
3. **REINDEX 所有 HNSW/IVFFlat 索引**：0.8 索引格式有优化，且 0.8.3 修过 HNSW vacuum 索引损坏——旧索引可能"带伤上岗"。`REINDEX INDEX CONCURRENTLY idx_xxx;` 逐个重建，避免锁表。
4. **回归验证**：抽样 query 对比召回与延迟、跑 EXPLAIN 确认 iterative scans 配置生效（见 05 篇）、监控 vacuum 行为。

升级在低峰窗口执行，先在一台副本上演练，再切主——与任何 PG 大版本升级的节奏一致。0.8.x 内部的月级小版本（0.8.5→0.8.6）通常只需替换二进制重启，无需 REINDEX，但仍建议小版本升级后跑一遍验证查询。

升级失败的处置预案：**0.7→0.8 的 ALTER EXTENSION 失败**通常源于二进制未替换（扩展二进制与 SQL 版本不匹配）——先重装二进制再重试；**升级后索引异常**（查询报错或性能骤降）走两步：`REINDEX` 重建所有向量索引，若仍未恢复则回滚到备份（这也是第 1 步必须备份的原因）。经验法则：升级窗口的验证查询与回滚脚本**先写成 SQL 文件**（验证：count + 抽样 query + EXPLAIN 索引路径；回滚：停写 → 恢复备份 → 校验），而不是升级时现场想——事故窗口里人的判断力不可靠，脚本才是可靠的。

日常巡检补一句：**锁版本 + 跟进发布**——生产镜像/云实例固定扩展版本，每月看一次 CHANGELOG 的 bugfix 条目决定是否升级（0.8.2 的 buffer overflow、0.8.3 的索引损坏都是值得立即升级的级别）。

升级检查清单（写进团队 runbook）：**升级前**——确认备份可用（pg_dump 恢复演练过）、确认所有连接串的驱动版本兼容（pgvector-java 与扩展版本解耦但要做冒烟）、准备验证 SQL 与回滚脚本；**小版本升级（0.8.5→0.8.6）可以简化**——只做备份 + 替换二进制 + 验证查询，不必 REINDEX（REINDEX 只在大版本如 0.7→0.8 时强制）；**升级中**——低峰窗口、先副本后主、`ALTER EXTENSION` 失败先查二进制；**升级后**——REINDEX 所有向量索引（CONCURRENTLY 逐个）、跑验证 SQL（count + 抽样 query + EXPLAIN 索引路径）、监控查询延迟与 vacuum 行为 24 小时。清单的价值在"每步都有确认动作"，比"升级完觉得没问题"可靠一个量级——向量扩展升级翻车的案例大多不是升级本身，而是升级后索引没重建。一个反直觉但重要的认知：**扩展升级的失败成本比业务表 schema 变更高**——业务表可以回滚 DDL，扩展版本回滚通常要恢复备份（二进制降级不保证数据格式兼容），所以升级前备份不是可选项而是必须项。

> 🎯 **核心要点**：`CREATE EXTENSION vector` 是唯一起点，`extversion` 是唯一版本真相；云厂商选型把"0.8+"列为硬指标；0.7→0.8 必须 REINDEX + 回归验证；官方 Docker 镜像 tag 是 PG 版本不是扩展版本。
