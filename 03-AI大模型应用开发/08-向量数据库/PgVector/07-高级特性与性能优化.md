# 高级特性与性能优化

> 两阶段量化检索、并行建索引、SIMD、EXPLAIN 调优、vacuum 运维、分区分表——从"能用"到"扛住规模"

## 1. 两阶段检索：binary_quantize + 全精度精排

0.8 的二进制量化让"大集合 + 低内存"成为可能。两阶段的核心思想：**粗召回用 bit 索引（内存极小、速度极快），精排用全精度向量（召回准确）**：

```sql
-- 阶段一：bit 量化列（1536 维 → 192 字节，32× 缩小）
ALTER TABLE documents ADD COLUMN bq bit(1536)
  GENERATED ALWAYS AS (binary_quantize(embedding)) STORED;
CREATE INDEX ON documents USING hnsw (bq bit_hamming_ops);

-- 阶段二：检索时先按 bit 取 100 候选，再按全精度排序
WITH candidates AS (
    SELECT id FROM documents
    ORDER BY bq <-> binary_quantize($1::vector)
    LIMIT 100
)
SELECT id, 1 - (embedding <=> $1) AS similarity
FROM documents WHERE id IN (SELECT id FROM candidates)
ORDER BY embedding <=> $1
LIMIT 10;
```

效果：**90-95% 的全精度召回，内存开销只有十分之一**（bit 索引 ≈ 0.2KB/条 vs float32 6KB/条）。适用：内存红线（50M 向量场景）、高维模型（text-embedding-3-large 3072 维）；召回要求 99%+ 的场景不要省这层（直接用全精度 HNSW）。

## 2. 并行建索引与内存治理

```sql
SET max_parallel_maintenance_workers = 7;   -- 并行 worker（默认受核数限制）
SET maintenance_work_mem = '8GB';           -- 建索引内存预算
CREATE INDEX CONCURRENTLY ... USING hnsw ...;
```

三个工程事实：**0.8 的 HNSW 构建比 0.7 快约 40%**，且支持并行；`maintenance_work_mem` 不足时索引构建 spill 到磁盘（0.8.4/0.8.5 连续修 IVFFlat 内存问题，说明这是高频事故点）；**并行构建有 buffer overflow 历史 bug**（0.8.2 修复）——升级到 0.8.2+ 再开并行。磁盘预留：1M 行 1536 维索引 ≈ 6GB（构建时临时空间还要翻倍），磁盘不足先看这个账。

## 3. SIMD 加速与 EXPLAIN 调优

- **SIMD**：0.8 对 `<#>` 和 `<->` 的距离计算做了 AVX-512 向量化，实测快 20-30%——**归一化向量优先用 `<#>`**（内积计算吃满 SIMD，且与 cosine 排序等价，见 03 篇）。
- **EXPLAIN ANALYZE 三看**：一看 `Index Scan` 还是 `Seq Scan`（索引失效排查）；二看 `actual time` 与 `Rows Removed by Filter`（过滤吞结果信号，见 05 篇）；三看并行度与 Buffer 命中率（`Buffers: shared hit=...` 低命中说明内存不足）。

一个实际执行计划的解读示例（带过滤的向量查询）：

```text
Index Scan using idx_docs_cosine on documents
  Order By: (embedding <=> '[0.1,...]'::vector)
  Rows Removed by Filter: 4821          ← 过滤吞掉 4821 行候选
  Filter: (category = 'jvm')
  Buffers: shared hit=936               ← 全部内存命中（hit 占比 100%）
```

`Rows Removed by Filter` 是核心信号：它显示 ANN 召回后**被过滤条件丢弃的候选行数**——数字长期接近候选总数（如上例候选约 5000 几乎全被过滤），说明 post-filter 在空转，优先考虑 partial index（05 篇）；`Buffers: shared hit` 占比低（大量 `read`）说明索引页没进 shared_buffers，HNSW 索引常驻内存的收益没吃到——调大 `shared_buffers` 或核对内存预算。
- **GUC 组合**：`hnsw.ef_search`（查询质量）、`hnsw.iterative_scan`（过滤兜底）、`work_mem`（排序内存）——按查询类型组合设置，写入连接池的 session 初始化参数。

## 4. VACUUM / REINDEX 运维

- **VACUUM**：向量表的更新/删除产生死元组，autovacuum 默认覆盖，但**高频 upsert 的向量表要调大 autovacuum 阈值**（向量表行宽大，VACUUM 成本高）；HNSW 索引在 vacuum 期间的行为有过 bug（0.8.3/0.8.4 修复"vacuum 时插入报错"），升级到 0.8.4+ 更稳。调整姿势：`ALTER TABLE documents SET (autovacuum_vacuum_scale_factor = 0.05, autovacuum_analyze_scale_factor = 0.05)`（默认 0.2 对向量表太懒），或按表级 `autovacuum_vacuum_threshold` 调低触发线——向量表是"写多改少"形态，vacuum 频率跟着写入走而不是跟着表大小走。
- **REINDEX**：HNSW 索引大版本升级后重建（02 篇）；索引膨胀（频繁删除后）定期 `REINDEX INDEX CONCURRENTLY`——CONCURRENTLY 版本不锁写，但耗时翻倍，低峰执行。
- **监控**：把 `pg_stat_user_tables.n_dead_tup` 与索引膨胀率（`pgstatindex`）纳入巡检——向量表是"行宽大、更新少、删除少"的形态，重点盯死元组比例即可。

## 5. 分区分表与高可用

- **分表（partition）**：按时间/分类做 RANGE/LIST 分区，向量列随表分区——**分区键不能是向量本身**（向量无法做分区键），用业务字段分区后每个分区可建 partial HNSW（见 05 篇），查询剪枝 + 过滤推进双赢。

```sql
CREATE TABLE docs (
    id BIGSERIAL, created_at DATE, embedding vector(1536)
) PARTITION BY RANGE (created_at);

CREATE TABLE docs_2026q3 PARTITION OF docs
    FOR VALUES FROM ('2026-07-01') TO ('2026-10-01');
CREATE INDEX ON docs_2026q3 USING hnsw (embedding vector_cosine_ops);
```

分区配合向量检索的三个要点：**查询必须带分区键过滤**（`WHERE created_at >= ...`）让优化器剪枝，否则全分区扫描抵消索引收益；**每个分区单独建 HNSW**（分区级 partial index 思路，见 05 篇）；**过期分区直接 DROP**（比 delete 高效一个量级，数据生命周期管理天然落地）。分区表的运维注意：`CREATE INDEX CONCURRENTLY` 在分区表上逐分区生效，脚本要按分区循环执行。
- **高可用**：PgVector 完全复用 PG 的流复制与 Patroni——向量数据跟着 PG 一起复制、一起切换，**这是对比专用向量库的运维红利**；只读副本可承担检索流量（副本上建同样的索引即可）。
- **备份**：pg_dump 与 PITR 原生覆盖向量表，无需额外备份方案——"同库"的红利在灾难恢复时体现得最充分。

向量表的容量规划模板（按行数 × 维度估算三账）：**磁盘账**——向量本体 = 行数 × 维度 × 4 字节（halfvec 2 字节），HNSW 索引 ≈ 本体 × 1.0-1.5（图链接开销），加 1.5 倍构建临时空间；**内存账**——索引常驻 + shared_buffers 页缓存，按"1M 行 1536 维 ≈ 6GB"线性外推；**备份账**——pg_dump 全量备份体积 ≈ 数据 + 索引，恢复演练的磁盘另算。示例：5000 万行 × 768 维（halfvec）→ 本体约 76GB、索引约 100GB、内存账约 100GB——**这已经摸到 50M 上限的边缘**，量化或换库二选一。规划时把"半年增长 × 2 的余量"写进文档，容量问题提前暴露比晚暴露好一个量级。

容量监控落地：**磁盘按 70% 告警**（留出构建临时空间与 WAL）、**内存按"索引常驻 + 连接并发 × work_mem"预算告警**、**行数按周跟踪**并与规划模型对比——三条线任意一条破阈值就触发 09 篇 ADR 里的"触发条件"评审，而不是等到查询变慢才查原因。监控工具直接复用 PG 全家桶（pg_stat_activity 看连接、pg_stat_user_tables 看行数、pgstatindex 看膨胀），Prometheus + postgres_exporter 一条链路覆盖——向量表不需要任何专属监控设施，这是"同库"红利的又一处兑现。查询侧再补两个指标：**P95 查询延迟**（向量查询波动大，P95 比平均值诚实）与 **返回结果数 / topK 比值**（持续低于 1 是过滤吞结果的早期信号，见 05 篇）——检索质量与基础设施两条线都有人在看，向量库才不会"悄悄变坏"。

> 🎯 **核心要点**：两阶段量化把 50M 向量拉回内存预算内（90-95% 召回）；并行建索引 + maintenance_work_mem + 磁盘翻倍预算三件事同时规划；EXPLAIN 三看（扫描方式/过滤行数/命中率）是调优入口；向量表运维就两件事——盯死元组、定期 REINDEX；分区与复制全部复用 PG 能力。
