# 精确检索与过滤

> 精确 KNN、WHERE 过滤的 post-filter 本质、0.8 iterative scans 的修复原理、partial index 兜底——过滤是 PgVector 检索质量的主战场

## 1. 精确检索与索引启用

精确 KNN（暴力扫描全表）不需要任何索引，小表/临时表直接用：

```sql
SELECT id, content, 1 - (embedding <=> $1) AS similarity
FROM documents
ORDER BY embedding <=> $1
LIMIT 10;
```

数据量大时（万级以上）改用 HNSW 近似检索：**查询写法完全不变，索引自动启用**——`EXPLAIN` 验证索引生效：`Index Scan using ... (order by: embedding <=> ...)`，若出现 `Seq Scan` 说明索引没建对（操作符与索引 opclass 不匹配，见 03 篇）。**近似检索返回的是"最可能的近邻"，不保证全局最优**——需要精确结果的小数据量场景直接去掉索引走精确扫描，语义最稳。

精确与近似的选型判断：**万级以下直接精确扫描**（全表排序，毫秒级返回，结果 100% 正确）；**万到百万级用 HNSW**（召回 99%+，代价可接受）；**需要绝对正确或作为基准评测**时始终保留精确查询能力（临时禁用索引：`SET enable_indexscan = off` 或用 `SET LOCAL` 控制）——用"索引召回 + 精确重排"的组合（与 07 篇量化两阶段同构）是兼顾两者的工程常态。

索引路径的匹配规则值得单独强调：**`ORDER BY embedding <=> $1 LIMIT k` 要命中索引，必须满足三点**——操作符与索引 opclass 一致（`<=>` 对 `vector_cosine_ops`）；LIMIT 存在（无 LIMIT 的 ORDER BY 全排序不走 ANN）；无其他排序条件干扰（ORDER BY 里混入业务字段会让优化器放弃向量索引）。这三点不满足时查询静默退化全表扫描——EXPLAIN 是唯一发现手段，所有"突然变慢"的向量查询第一件事就是看执行计划。

## 2. WHERE 过滤的 post-filter 本质

```sql
SELECT id FROM documents
WHERE category = 'jvm'
ORDER BY embedding <=> $1
LIMIT 10;
```

这条查询的**执行语义**：索引先按距离召回候选，再在候选上套 WHERE（post-filter）。问题与 Chroma 同源：**category 过滤选择性高时，候选集里可能没有几条满足条件**——结果少于 10 条甚至为空，且 EXPLAIN 不报错。这是 0.8 之前 PgVector 最著名的坑：**"索引 + 过滤"组合的召回静默丢失**。

## 3. 0.8 iterative scans：修复"过滤吞结果"

0.8.0 引入迭代扫描（iterative scans），用 GUC 参数开启：

```sql
-- 开启后，过滤候选不足时自动重入索引继续扫描
SET hnsw.iterative_scan = 'strict_order';    -- 保持距离排序严格性（默认）
-- 或
SET hnsw.iterative_scan = 'relaxed_order';   -- 放宽排序，优先凑够数量

-- 配套控制参数
SET hnsw.max_scan_tuples = 100000;           -- 单次扫描候选上限
SET hnsw.scan_mem_multiplier = 2;            -- 扫描内存放大倍数
```

两个模式取舍：**strict_order** 保证结果按距离严格排序（符合"最相似的在前"的语义），但补足数量时可能扫描很多行；**relaxed_order** 优先补够 LIMIT 数量（结果可能略偏离最优排序），适合"数量比精确排序重要"的场景（如 RAG 上下文只要够 5 条）。IVFFlat 有同族配置（`ivfflat.iterative_scan` / `ivfflat.max_probes`）。

生产建议：**默认开启 strict_order**（语义最稳）；RAG 检索场景如果频繁出现"结果不足 k 条"，评估 relaxed_order 或换 partial index（下节）——iterative scans 是缓解不是根治，**高选择性过滤仍然是 PgVector 的短板**，这也是 09 篇选型对比的论据之一。

iterative scans 的部署细节：三个 GUC（`hnsw.iterative_scan` / `hnsw.max_scan_tuples` / `hnsw.scan_mem_multiplier`）都是会话级——**在连接池初始化 SQL 里统一开启**（HikariCP `connection-init-sql`），避免每处查询各自 SET 造成配置漂移；`max_scan_tuples` 是防失控的保险丝（扫描候选上限，默认 100k），过滤极稀疏场景（百万条里只匹配几十条）调大它并接受更长延迟；`scan_mem_multiplier` 控制重扫的内存放大（默认 2）。升级到 0.8.0+ 后 iterative scans 需要显式开启还是默认生效取决于发行版配置——**生产环境确认一遍 GUC 值再上量**，别指望"升级即自动修复"。

## 4. partial index：为高选择性过滤建专用索引

最有效的根治手段是**为常用过滤组合建部分索引**（partial index）——索引本身只包含满足条件的数据：

```sql
-- 场景：大部分查询都带 category = 'jvm'
CREATE INDEX CONCURRENTLY idx_docs_jvm
ON documents USING hnsw (embedding vector_cosine_ops)
WHERE category = 'jvm';
```

查询 `WHERE category = 'jvm' ORDER BY embedding <=> $1` 会命中这个索引——**过滤被推进索引，候选集本身就是该分类的数据**，彻底绕开 post-filter。适用条件：**过滤值是静态/低频变化**（租户 ID、分类枚举）；动态值（用户 ID 海量）建不了那么多索引，回到 iterative scans 或换库。这是"热门租户/热门分类"场景的标准做法，也是 09 篇里"强过滤场景 PgVector 的答案"。

## 5. 排序稳定与投影优化

- **排序稳定性**：`ORDER BY embedding <=> $1 LIMIT k` 的返回顺序在 HNSW 下是近似的；需要稳定分页（翻页）时，**LIMIT/OFFSET 不适合向量检索**——向量检索按相关性而非行序，OFFSET 翻页会重复/漏数据，RAG 场景一次取 k 条即可，翻页用游标（上次结果的最低分做阈值）。

游标式翻页的实现：记录上次结果的最后一条的（id, 距离），下一页查询把条件改为"距离大于该值"（l2/余弦下越小越近，即 `embedding <=> $1 < 上次阈值`——注意方向随度量翻转），配合 `ORDER BY ... LIMIT k` 取下一批。局限是**阈值翻页与并行写入冲突**（新写入的记录可能改变距离序），适合只读场景；需要严格稳定分页的场景，先把候选集物化到临时表再加行号——代价是两次查询，但语义完全可控。
- **投影瘦身**：`SELECT` 只取需要的列（id + content），不取大字段（如整篇文档）——向量查询的 IO 大头在返回行，投影越小延迟越低；需要全文时再二次查询。
- **EXPLAIN 验证清单**：Index Scan 而非 Seq Scan；`hnsw.iterative_scan` 生效（过滤场景）；`Rows Removed by Filter` 数值合理（被过滤比例过高说明要上 partial index）。
- **索引失效的常见诱因**：查询里对向量列做了函数包装（`lower(embedding)` 或 `embedding::halfvec` 没建对应函数索引）、操作符与 opclass 错配、LIMIT 缺失（见第 1 节三点规则）——排障时先检查 SQL 形态再怀疑索引损坏，90% 的"索引失效"是写法问题而非索引问题。

> 🎯 **核心要点**：索引自动启用、EXPLAIN 是唯一验证手段；WHERE + ANN 是 post-filter，选择性高就吞结果——0.8 的 iterative scans 是缓解、partial index 是根治、过滤值动态则换库；向量检索不做 OFFSET 翻页，一次取够 + 投影瘦身。
