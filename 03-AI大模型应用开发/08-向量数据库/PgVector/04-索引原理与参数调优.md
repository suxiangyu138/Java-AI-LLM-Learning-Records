# 索引原理与参数调优

> HNSW 与 IVFFlat 二选一，参数三件套 m / ef_construction / ef_search——用实测基准数据校准你的决策

## 1. HNSW vs IVFFlat：原理与取舍

**HNSW（分层可导航小世界图）**：把向量组织成多层图——顶层节点稀疏（长距离跳转）、底层节点稠密（精确邻居），搜索从顶层出发逐层贪婪下钻，直到最底层收敛到最近邻。无需训练阶段——**空表即可建索引**（这是它碾压 IVFFlat 体验的最大优势）；查询快、召回高；代价是建索引慢、占内存（每节点 m 条链接）。

```text
HNSW 搜索路径：顶层粗定位 → 逐层下钻 → 底层精收
    L2:  A ──── C ──── E         ← 稀疏层
    L1:  A ─ B ─ C ─ D ─ E
    L0:  A-B-C-D-E-F-G-H         ← 稠密层（精确邻居）
   查询 x：从 A 开始逐层找最近邻，下钻到 L0 返回
```

**IVFFlat（倒排文件 + 暴力扫描）**：先用聚类算法（k-means）把数据分成 lists 个桶，查询时只扫 probes 个最近的桶。**必须先有数据再建索引**（聚类中心从数据中推导），lists = 行数开方（百万级取 sqrt）或行数/1000；召回靠提高 probes（但越扫越慢）；内存占用低、建索引快。

| 维度 | HNSW | IVFFlat |
|------|:----:|:-------:|
| 建索引前提 | 无（空表可建） | 需先有数据 |
| 召回（1M 向量实测） | ~99.2%（m=16, ef=64） | ~94.5%（lists=1000, probes=10） |
| 查询延迟（同数据） | ~2ms | ~8ms |
| 内存/存储 | 高（图结构） | 低 |
| 适用 | **生产默认推荐** | 内存受限/高写入场景 |

结论一句话：**没有特殊理由就用 HNSW**；IVFFlat 只留给"内存真的不够"或"频繁重建索引的临时表"。

## 2. 参数三件套

| 参数 | 默认 | 控制阶段 | 调大后果 |
|------|:----:|---------|---------|
| `m` | 16 | 建图 | 召回↑、内存↑、建图慢 |
| `ef_construction` | 64 | 建图 | 索引质量↑、构建慢 |
| `ef_search` | 40（0.8.1+） | 查询 | 召回↑、查询慢（可运行时调） |

```sql
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- 查询期调 ef_search（会话/事务级）
SET hnsw.ef_search = 100;
SELECT ... ORDER BY embedding <=> $1 LIMIT 10;
```

调参逻辑与 Chroma/Milvus 同源：**召回不足先调 ef_search**（免费，不动索引）；建图质量不够再动 ef_construction（需重建）；m 是最后手段（内存代价最大）。生产推荐区间：m 8-48、ef_construction 32-256、ef_search 20-200——先跑基准（召回率-延迟曲线）再定值，别照搬默认。

ef_search 的生产配置姿势：它是 GUC（会话级参数），**连接池场景在初始化 SQL 里统一设置**（如 HikariCP 的 `connection-init-sql: SET hnsw.ef_search = 100`），或按查询类型在事务内 `SET LOCAL` 临时覆盖——同一连接的不同查询用不同 ef_search 是合法的（高召回检索 200、低延迟检索 40），比全局一个值灵活得多。IVFFlat 侧的同族参数是 `ivfflat.probes`（查询时扫描的桶数，会话级）与建索引时的 `lists`（桶数）——lists 过大每个桶太小、过小每个桶扫描成本高，`lists = sqrt(rows)` 是经验公式（百万级取 1000）。

## 3. 建索引工程实践

```sql
-- 生产建索引：不锁写 + 并行 + 大内存
SET max_parallel_maintenance_workers = 7;
SET maintenance_work_mem = '8GB';
CREATE INDEX CONCURRENTLY idx_docs_cosine
ON documents USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 128);
```

四条铁律：**生产用 `CREATE INDEX CONCURRENTLY`**（普通 CREATE INDEX 阻塞写入，百万级表阻塞分钟级）；**maintenance_work_mem 按数据量调**（HNSW 建图内存超限会 spill 到磁盘拖慢数倍，0.8.4 修过 IVFFlat 内存超限问题，说明这是真实战场）；**0.8 并行建索引默认多 worker**，注意 max_parallel_maintenance_workers 配额；**升级 0.7→0.8 后 REINDEX**（格式优化 + 潜在损坏修复，见 02 篇）。

何时重建索引（REINDEX）的判断：**升级大版本后必建**（格式与修复）；**大量删除后索引膨胀**——HNSW 图里被删节点留下空洞，查询仍扫描它们，`pgstatindex` 查索引膨胀率（`avg_leaf_density` 低于 60% 触发）；**ef_construction/m 调参后**——参数只在建索引时生效，改完必须重建才起作用。重建窗口选低峰，用 CONCURRENTLY 不锁写，一次一个索引逐个来。

## 4. 基准数据与规模心智

1M 向量、1536 维、cosine 度量的实测（2026）：

| 配置 | 召回率 | 平均查询延迟 |
|------|:-----:|:-----------:|
| HNSW m=16, ef_search=64 | ~99.2% | ~2ms |
| HNSW m=16, ef_search=100 | ~99.7% | ~4.2ms |
| IVFFlat lists=1000, probes=10 | ~94.5% | ~8ms |

配套资源心智：**1M 行 1536 维的 HNSW 索引 ≈ 6GB 磁盘**，常驻内存量级相近——50M 向量意味着 300GB 量级内存与磁盘，这就是"50M-100M 上限"的资源本质。用 halfvec 可以砍半（召回损失 1-2%），binary_quantize 再砍 16 倍（配合两阶段，见 07）——**规模不够时先量化，而不是先换库**。

召回-延迟曲线怎么读：基准数据揭示的规律是**召回率在 99% 附近进入"边际收益递减区"**——从 94% 提到 99% 只需要 modest 的 ef_search 提升（延迟 2ms 级别），但从 99% 提到 99.9% 要付出数倍延迟与内存。工程含义：**RAG 场景的召回目标定在 98-99.5% 即可**（下游 LLM 对少量漏检有容忍度），把资源留给吞吐；金融/检索类严格场景才追求 99.9%+（用精确重排而非无限调参，见 07 篇两阶段）。定目标前先跑自己数据的曲线——**基准数据只能给量级，自己数据的分布（embedding 质量、聚类程度）才决定最终参数**，照搬他人数值是最常见的调参错误。

IVFFlat 什么时候真的值得用，把条件列清楚：**内存是硬约束**（HNSW 图结构吃不起）；**写入吞吐优先**（高 ingest 场景，IVFFlat 建索引/更新成本低）；**数据频繁整体重建**（聚类中心跟着数据走，重建成本可控）。三个条件都不满足，IVFFlat 的召回劣势（94.5% vs 99.2%）无法接受——**"为了省内存用 IVFFlat"不如"用 halfvec 或量化后的 HNSW"**，后者在同内存下召回更高，这是 0.8 时代 IVFFlat 加速边缘化的根本原因。

参数设置的层级总结（调参时对号入座）：**索引创建参数**（m、ef_construction、lists）在建索引时固化，改动需重建；**查询级 GUC**（ef_search、probes、iterative_scan）会话内生效，连接池初始化或 SET LOCAL 控制；**系统级**（maintenance_work_mem、parallel workers）影响构建资源。三层的心智模型是"**建索引管质量上限、查询参数管运行弹性、系统参数管资源供给**"——调参先想清楚动的是哪一层，避免把查询参数当建索引参数改（改完不重建等于没改）。

> 🎯 **核心要点**：HNSW 是默认答案，IVFFlat 是内存妥协；调参顺序 ef_search → ef_construction → m，召回不足先动查询参数；CONCURRENTLY + maintenance_work_mem + 并行 worker 是生产建索引三件套；1M/6GB 的资源心智决定 50M 是规模红线。
