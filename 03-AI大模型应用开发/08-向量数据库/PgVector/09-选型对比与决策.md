# 选型对比与决策

> PgVector vs Chroma / Milvus / Qdrant / ES kNN——"已有 PG 就用 PG"的口诀边界在哪，规模红线怎么划

## 1. 竞品全景与定位差异

向量存储选型三象限（同 Chroma 体系 09 篇的分类）：**嵌入式单机**（Chroma、FAISS）、**独立服务向量库**（Milvus、Qdrant、Weaviate）、**通用数据库扩展**（PgVector、Redis Stack、ES kNN）。PgVector 站在第三象限，对手不是"更快的向量库"，而是"我不新增基础设施"——这是它的战略定位。

| 维度 | PgVector 0.8.6 | Chroma 1.5.x | Milvus 3.0 | Qdrant |
|------|---------------|-------------|-----------|--------|
| 形态 | PG 扩展 | 嵌入式/单节点 | 分布式集群 | 单节点/集群 |
| 部署成本 | 零（已有 PG） | 零（pip） | 高（K8s） | 中（Docker） |
| 规模上限 | 50M-100M | 1-2M | 十亿级 | 亿级 |
| 过滤 | post-filter（0.8 迭代扫描缓解） | post-filter | pre-filter 强 | 过滤感知索引 |
| 混合检索 | FTS + RRF（原生） | BM25/SPLADE（较新） | 原生成熟 | 原生成熟 |
| 量化 | binary_quantize + halfvec | 无 | SQ8/GPQ | 有 |
| SQL/事务 | **完整（灵魂）** | 无 | 有限 | 有限 |
| Java 生态 | Spring AI 官方 | Spring AI 官方 | Spring AI 官方 | Spring AI 官方 |

## 2. 逐个竞品的取舍分析

**vs Chroma**：Chroma 是"嵌入最省事"（pip 即用、单机文件），PgVector 是"已有 PG 最省事"（一条 CREATE EXTENSION）。分水岭：**有没有 PG、要不要事务与 SQL**——向量只是应用功能且有 PG，PgVector 白赚事务/JOIN/备份；纯原型探索无 PG 依赖时 Chroma 上手更快。规模上 PgVector（50M）碾压 Chroma（1-2M）——这是 0.8 迭代扫描 + 量化补齐后最直接的差距。

**vs Qdrant**：最有力的"纯向量库"对手。Qdrant 的过滤感知索引（pre-filter 不丢召回）、成熟混合检索、量化都是 PgVector 的短板或半成品。但 Qdrant 换来这些的代价是**独立服务 + 独立运维 + 数据与应用分离**。判断：**过滤是核心查询模式、规模持续增长 → Qdrant**；过滤简单、规模在 50M 内、PG 已有 → PgVector 够用且更省。

**vs Milvus**：Milvus 是十亿级分布式答案（3.0 Lake-Native），带 RBAC/多租户/监控全家桶。PgVector 与 Milvus 几乎不构成竞争——**10M 内用 PgVector 是务实，10M 以上且要分布式是 Milvus 的地盘**。中间地带（10M-50M）看增长预期与运维能力：增长平缓就 PgVector，激进增长直接上 Milvus 避免二次迁移。

**vs ES kNN**：已有 Elasticsearch 且要做文本检索的场景，ES kNN 顺手；但 ES 的向量能力（HNSW 实现、过滤）弱于 PgVector，且 ES 不擅长事务。**文本搜索为主 + 向量为辅 → ES kNN；向量为主 → PgVector**。

**vs Redis Stack**：Redis 8 的向量模块（`VECTOR` 字段 + KNN 检索）适合"缓存 + 向量"融合场景——低延迟、数据可丢失、无强一致要求。但 Redis 没有 SQL、没有事务性过滤、持久化弱于 PG——**向量是缓存层数据 → Redis Stack；向量是需要保证的数据 → PgVector**。两者的抉择几乎不纠结：Redis Stack 是"顺手存"，PgVector 是"认真存"。

**vs 其他 PG 扩展**：pg_embedding（Neon）API 不兼容且活跃度低；PGVector 是社区事实标准，Supabase/Neon/TencentDB 全内置——**扩展层面的竞争已经结束，2026 年不需要在 PG 内部纠结**。

## 3. "已有 PG 就用 PG"的口诀边界

口诀成立的条件（四条，全满足才是 PgVector 甜区）：**数据量 < 50M 向量**（超了就量化再评估，量化后仍超就换库）；**过滤条件简单**（枚举值 partial index 能覆盖，动态高基数过滤放弃）；**无多租户行级权限需求**（PG 的 RLS 其实能扛多租户——这点比 Chroma 强，但同表 RLS + HNSW 的过滤损失要实测）；**团队会运维 PG**（不会的话，托管云 PG 也算会）。

口诀失效的信号：查询频繁出现"过滤后结果不足"（post-filter 代价超限）；内存账算不平（50M × 6GB/1M = 300GB）；需要向量库专属能力（内置 embedding 管道、多租户隔离、跨区域写）。

## 4. 典型选型场景（推演）

**场景 A：已有 PG 的业务系统加"语义搜索"功能**（商品搜索、文档检索）。数据千万级、过滤是分类枚举、事务与业务 JOIN 是刚需。选 PgVector——零新增服务，SQL JOIN 业务表直接复用，backup/监控/HA 全部继承。**这是 PgVector 的主场，90% 的"已有 PG"场景落在这里**。

**场景 B：RAG 原型 + 无 PG 依赖**。快速验证检索质量、数据量小。Chroma 起步（零依赖）；转生产时若已有 PG 资产再评估迁 PgVector（表结构同构，迁移成本低）。

**场景 C：电商客服知识库，强过滤（类目 × 地区 × 时间）**。过滤是核心模式，post-filter 损失不可接受。选 Qdrant（过滤感知索引）——PgVector 的 iterative scans 是缓解，partial index 只能覆盖枚举组合，动态过滤无能为力。

## 5. 选型决策树

```text
已有 PostgreSQL？
├── 否 → 有现成 ES？ → 是：ES kNN（文本为主）或 PgVector（向量为主，需建 PG）
│        数据 <2M 且要零部署？ → 是：Chroma
│        否则 → Qdrant（简单）或 Milvus（十亿级/分布式）
├── 是 → 数据 <50M 且过滤简单？ → 是：PgVector（默认答案）
│        → 过滤是核心模式且动态？ → Qdrant
│        → 预期 >100M 或需分布式？ → Milvus
```

决策树之外两条纪律：**向量需求 90% 会增长**——用 Spring AI VectorStore 抽象保留换库路径（08 篇）；**先量化再换库**——50M 边缘先用 halfvec + binary_quantize 压缩（07 篇），换库是最后手段。决策树的输出不是"选型结论"而是"选型 + 边界 + 触发信号"三件套，缺一不可。

决策落地时写一份**选型记录**（ADR，架构决策记录），字段五条：背景（业务场景与数据量现状）、备选方案（PgVector/Chroma/Qdrant/Milvus 各自的成本与能力）、决策（选谁 + 一句话理由）、触发条件（什么信号出现就换——如"数据量 6 个月后达 40M"或"过滤查询占比超 30%"）、回滚路径（数据怎么迁出）。ADR 写进仓库与代码同管（docs/adr/），评审时它就是讨论的锚点——避免"选型靠口头、换库靠回忆"的团队常态。**ADR 的价值在触发条件**——把"什么时候该换库"写成可观测信号（监控指标、数据量预测），比事后拍脑袋决策可靠；团队里写过 ADR 的选型，六个月后回头看决策质量高一个量级。

> 🎯 **核心要点**：PgVector 的主场是"已有 PG + <50M + 过滤简单"——零新增基础设施换 SQL/事务/运维红利；强过滤动态场景让位 Qdrant，十亿级让位 Milvus；选型纪律"先量化再换库"+"VectorStore 抽象留退路"双保险。
