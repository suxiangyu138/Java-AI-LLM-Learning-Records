# 生产实践与面试题

> 把前面九篇沉淀为"避坑清单 + 生产清单 + 面试弹药"——验收你是否真的能上生产

## 1. 性能真相

先用数据校准预期（0.8.6，2026 基线）：1M 向量、1536 维、cosine：HNSW（m=16, ef=64）约 99.2% 召回、2ms 查询；ef=100 升到 99.7%、4.2ms；IVFFlat（lists=1000, probes=10）94.5%、8ms。**HNSW 的 2ms 是"索引常驻内存"的结果**——1M 行 1536 维索引 ≈ 6GB 磁盘/内存，50M 向量 ≈ 300GB，这是规模红线的资源本质。0.8 的 SIMD（`<#>`/`<->` 快 20-30%）与并行建索引（快 40%）是白拿的性能，前提是版本 >= 0.8.2。

把性能数字翻译成业务语言：**2ms 查询意味着单实例可支撑每秒数百次检索**（IO 与连接池是瓶颈而非检索本身）；50M 向量的 300GB 内存意味着这台机器的月成本可能超过"换库 + 运维"的月成本——**性能数字背后的成本账，才是选型决策的真正依据**（09 篇 ADR 里的"触发条件"就该写这个账）。

## 2. 避坑清单（Top 12）

1. **`<#>` 负内积忘记取负**：展示分数直接用了负数，排序没问题但展示全错。
2. **操作符与索引 opclass 不匹配**：`<=>` 查询 + `vector_l2_ops` 索引 → 静默全表扫描，EXPLAIN 才看得见。
3. **`?::vector` 类型转换缺失**：JDBC 参数绑定不带类型转换 → "operator does not exist"。
4. **WHERE 过滤吞结果**：post-filter 语义，高选择性过滤静默丢召回——开 iterative scans、建 partial index。
5. **CREATE INDEX 阻塞写入**：百万级表普通建索引锁写分钟级——必须 CONCURRENTLY。
6. **0.7→0.8 不 REINDEX**：索引格式不升级，历史 bug（vacuum 损坏）未修复。
7. **IVFFlat 在空表上建索引**：聚类中心从数据推导，空表建了等于没建——必须填充后建。
8. **维度与 embedding 模型不一致**：1536 的列写 3072 的向量直接报错；改模型忘建新表。
9. **3072 维模型用 vector 类型**：vector 上限 2000 维——用 halfvec 或量化。
10. **忽略 EF 调参顺序**：召回不足先调 ef_search（查询级），别上来重建索引调 m。
11. **中文 FTS 用默认分词**：`to_tsvector('simple', '向量数据库')` 整串处理——要 zhparser。
12. **向量翻页用 OFFSET**：向量检索无稳定行序，OFFSET 翻页重复/漏数据——一次取够或用游标。

## 3. 生产落地清单

- 部署：扩展版本 0.8.4+（含 vacuum 修复）、版本矩阵确认（PG 17 需 0.8+）、云厂商扩展版本抽查。
- Schema：Flyway 管理（CREATE EXTENSION + 建表 + 索引 + partial index）、embedding 维度与模型记录在案。
- 索引：HNSW + CONCURRENTLY + maintenance_work_mem 预算、操作符与索引一一对应。
- 检索：EXPLAIN 验证 Index Scan、iterative scans 开启、投影瘦身、topK 合理。
- 混合检索：FTS 生成列 + GIN 索引、RRF 融合 SQL 模板化。
- 监控：死元组比例、索引膨胀（pgstatindex）、慢查询（pg_stat_statements）、内存账（6GB/1M）。
- 备份：pg_dump/PITR 原生覆盖、恢复演练季度一次。
- 增长预案：50M 边缘先量化（halfvec + binary_quantize），预留 Qdrant/Milvus 迁移路径。

## 4. 面试高频题与答题范式

**Q1：PgVector 和专用向量数据库的本质区别？**
答：PgVector 是 PG 扩展不是独立数据库——零新增服务、向量与业务数据同库同事务、复用 PG 备份/复制/HA；边界在 50M-100M 向量与 post-filter 过滤。横向对比时主动引出 Chroma/Qdrant/Milvus 的定位（见 09）。

**Q2：HNSW 和 IVFFlat 怎么选？**
答：HNSW 无需训练可建在空表、召回高（99%+）查询快、代价是内存；IVFFlat 必须先有数据（聚类推导 lists）、召回靠 probes、内存低。默认 HNSW，IVFFlat 留给内存受限与高写入场景。1M 向量实测：HNSW 99.2%/2ms vs IVFFlat 94.5%/8ms。

**Q3：WHERE + 向量索引为什么丢结果？0.8 怎么解决的？**
答：post-filter 语义——索引先按距离取候选再套过滤，高选择性过滤导致候选不足。0.8 iterative scans 在候选不足时重入索引（strict_order 保排序 / relaxed_order 补数量）；根治用 partial index（过滤推进索引）；动态过滤则评估换库。

**Q4：混合检索怎么实现？为什么用 RRF？**
答：向量（`<=>` 语义召回）+ FTS（tsvector 关键词召回）两路各取排名，RRF 按 1/(60+rank) 融合——不用归一化分数（向量距离与 ts_rank 尺度不可比）是 RRF 相对加权融合的核心优势；有稀疏向量源时双列加权一次查询。

**Q5：PgVector 的规模上限？怎么突破？**
答：约 50M-100M 向量（内存与过滤代价决定）。突破路径按序：halfvec 减半存储 → binary_quantize 两阶段检索（32× 压缩、90-95% 召回）→ 分区 + partial index → 最后换 Qdrant/Milvus。

**Q6：Java 项目怎么接入 PgVector？**
答：三路径——Spring AI `spring-ai-pgvector-store-spring-boot-starter`（统一 VectorStore 抽象）；JdbcTemplate + `ORDER BY embedding <=> ?::vector`（最小成本，注意 pgvector-java 驱动）；Spring Data JPA + Flyway（生产形态，实体层与检索层分离）。

**Q7：混合检索比纯语义检索好在哪？怎么评估？**
答：语义检索对专有名词/型号不敏感，关键词检索对同义改写无计可施——混合检索两路互补，实测命中率提升 10-20%。实现用 RRF（排名倒数融合，免分数归一化）或稠密+稀疏双列加权。评估：100-200 条标注问答对，对比纯语义 vs 混合的命中率（top-5 是否含答案）与 MRR（答案排名倒数均值）——**指标说话，融合参数（k、权重、候选量）按评估结果调**。

**Q8：pgvector 数据量涨到 5000 万后怎么办？**
答：按"压缩 → 裁剪 → 换库"三步走。第一步量化：halfvec（存储减半）+ binary_quantize 两阶段（32× 压缩，90-95% 召回）——多数场景这步就能续命；第二步裁剪：删除低频旧数据、分区表按时间裁剪、partial index 聚焦热门分类；第三步才考虑换库：数据仍超限或过滤需求变强，评估 Qdrant（过滤感知）或 Milvus（分布式），用 Spring AI VectorStore 抽象保留业务层零改动（见 08 篇）。

**答题范式**：先定位（扩展 vs 专用库）→ 再给原理（索引/过滤/融合机制）→ 最后给边界与替代方案。与 Chroma 体系的答题范式一致——"定位 → 原理 → 边界"三段式，向量库面试通用。

> 🎯 **核心要点**：十二条避坑清单覆盖 90% 生产事故；"索引对操作符、过滤看 EXPLAIN、升级必 REINDEX、规模先量化"四条总纲；面试记住 HNSW 基准数字（99.2%/2ms）与 RRF 免归一化论证，答出深度。
