# 向量类型与操作符

> 四类向量列类型 + 六个距离操作符 + 二进制量化——PgVector 的全部"语言"，先背熟再谈检索

## 1. 四种向量类型

| 类型 | 存储精度 | 维度上限 | 存储体积（1536 维示例） | 适用场景 |
|------|---------|:-------:|----------------------|---------|
| `vector` | float32 | 2000 | 6.1KB | 通用默认 |
| `halfvec` | float16 | 4000 | 3.1KB（减半） | 高维模型/存储敏感 |
| `sparsevec` | 稀疏 float32 | 1000 非零元素 | 仅非零维度 | BM25/SPLADE 稀疏向量 |
| `bit` | 0/1 | 64000 | 0.2KB（量化后） | binary_quantize 结果 |

建表与插入：

```sql
CREATE TABLE documents (
    id BIGSERIAL PRIMARY KEY,
    content TEXT,
    embedding vector(1536)          -- 维度在建表时固定
);

-- 三种文本格式
INSERT INTO documents (embedding) VALUES ('[0.1,0.2,0.3,...]'::vector);
INSERT INTO docs_sparse (embedding) VALUES ('{1:0.5,100:0.3,999:0.8}/30000'::sparsevec);
INSERT INTO docs_binary (embedding) VALUES ('1011010...'::bit(1536));
```

选型判断：**默认 vector**；存储吃紧或维度 >2000（如 text-embedding-3-large 的 3072 维超了 vector 上限）用 **halfvec**（召回损失通常 1-2%）；关键词/BM25 场景用 **sparsevec**；两阶段检索的粗召回层用 **bit**（配合 binary_quantize，见 07）。

向量文本格式的细节决定 API 对接的正确性：`vector` 用 `'[a,b,c]'` 方括号格式（PostgreSQL 数组风格的方括号而非花括号——`'{a,b,c}'` 是 PG 数组，`'[a,b,c]'` 才是向量，写错会解析失败）；`sparsevec` 用 `'{1:0.5,100:0.3}/30000'` 格式（索引从 1 开始、冒号分隔索引与值、斜杠后是总维度）；`bit` 用 `'1011010'::bit(1536)` 字符串格式。数值精度：vector 默认保留 float32 精度，**输入超过 float32 精度的数会被舍入**（如 0.123456789 存成 0.12345679）——对检索无影响，但用做唯一键会出问题（向量不适合做键，这是另一个主题）。

`bit` 类型在 binary_quantize 之外的两个用途：**预计算哈希签名**（相似哈希/LSH 类应用，Hamming 距离天然匹配）；**布尔特征向量**（用户画像位图等结构化场景）。与 float 向量不同，bit 上只有 Hamming 与 Jaccard 两个度量，不要试图拿 bit 做余弦——语义已丢。

操作符的适用细节：**`<->` 支持 sparsevec**（`sparsevec_l2_ops`），`<=>` 不支持 sparsevec（稀疏向量没做余弦 opclass，0.8 现状）——稀疏向量混用度量时先转 vector；**同一列只能有一个距离索引**（索引表达式决定度量），需要多度量查询就建多列（embedding 与 embedding_l2 各存一份）或多表达式索引。

操作符与索引 opclass 的对应速查（建索引时对照，混配即全表扫描，记忆口诀"**度量名即 opclass 名**"——`cosine_ops` 配 `<=>`、`l2_ops` 配 `<->`，照表核对比记忆可靠）：

| 操作符 | vector | halfvec | sparsevec | bit |
|--------|:------:|:-------:|:---------:|:---:|
| `<->` L2 | vector_l2_ops | halfvec_l2_ops | sparsevec_l2_ops | — |
| `<=>` 余弦 | vector_cosine_ops | halfvec_cosine_ops | — | — |
| `<#>` 内积 | vector_ip_ops | halfvec_ip_ops | — | — |
| `<+>` L1 | vector_l1_ops | — | — | — |
| Hamming | — | — | — | bit_hamming_ops |
| Jaccard | — | — | — | bit_jaccard_ops |

操作符的语义细节补充三条：**`<=>` 返回的是"余弦距离"（1 - 余弦相似度）不是相似度本身**——查询里转相似度要 `1 - (embedding <=> $1)`；**`<+>` L1 只支持 vector**（halfvec/sparsevec 无 opclass，表里可见）；**bit 的 Hamming/Jaccard 查询同样要 LIMIT**（与 float 向量一致，无 LIMIT 无法走 ANN 索引）。这些细节是"看表建索引、看查询写代码"时的最后一公里，混一个就出全表扫描或结果颠倒。建议把速查表打印成团队 wiki 一页（建索引与写查询各一份对照），排障时少一次"EXPLAIN 才发现的低级错误"。

## 2. 六个距离操作符

| 操作符 | 度量 | 适用类型 | 语义 |
|--------|------|---------|------|
| `<->` | L2 欧氏距离 | vector/halfvec/sparsevec | 越小越近 |
| `<=>` | 余弦距离 | vector/halfvec | 越小越近（RAG 默认） |
| `<#>` | **负**内积 | vector/halfvec | **值越小越近**（负号坑） |
| `<+>` | L1 曼哈顿距离 | vector | 越小越近（0.7+） |
| Hamming | 汉明距离 | bit | 位不同的数量 |
| Jaccard | 杰卡德距离 | bit | 集合相似度 |

查询写法（cosine 是最常用度量）：

```sql
SELECT id, content, 1 - (embedding <=> $1) AS similarity
FROM documents
ORDER BY embedding <=> $1
LIMIT 10;
```

三个高频坑：**`<#>` 返回负内积**——展示分数要取负（`(embedding <#> $1) * -1`）；**归一化向量用 `<#>` 替代 `<=>`**——单位向量下两者排序等价但内积计算更省（SIMD 加速更明显）；**每个距离函数要建对应的索引**——`<=>` 查询必须有 `vector_cosine_ops` 索引，`<->` 必须有 `vector_l2_ops`，混用会退化为全表扫描（或按顺序扫描索引但无法用到）。

## 3. binary_quantize 二进制量化

0.8 提供 `binary_quantize()` 函数，把 float32 向量压成 bit 向量（逐维取符号位）：

```sql
CREATE TABLE docs_bq AS
SELECT id, content, binary_quantize(embedding) AS bq   -- 1536 维 → 192 字节
FROM documents;

CREATE INDEX ON docs_bq USING hnsw (bq bit_hamming_ops);
```

量化是**有损的**（只保留方向符号），直接检索召回不达标——正确用法是**两阶段**：bit 索引粗召回候选集（速度极快、内存极小），再用全精度向量精排（见 07 篇）。量化后可以用 Hamming 距离（bit 上计算比 float 快一个量级）也可以转回 vector 用原度量。

一个容易误用的细节：`binary_quantize()` 是**逐维取符号位**——正数 1、负数 0，与"向量中每个维度是否非零"无关，所以它对**稠密 embedding 效果好、对稀疏向量无意义**（稀疏向量绝大多数维为 0，量化后全是 0，信息全丢）。量化只在 float 稠密向量上用；sparsevec 本身就是压缩形态，不需要再量化。

## 4. 类型互转与 cast

```sql
-- 高维模型超 2000 维：vector → halfvec 建索引（类型本身不可建 2000+ 维 vector 列）
CREATE INDEX ON documents USING hnsw ((embedding::halfvec(3072)) halfvec_cosine_ops);

-- sparsevec 与 vector 互转（用于统一度量计算）
SELECT embedding::sparsevec FROM documents;
```

互转注意：`::` 转换发生在查询/索引表达式中时，**索引必须建在同样的表达式上**（函数索引），否则用不上；halfvec 索引召回后若要全精度精排，需保留原 vector 列或再转回。

归一化与预计算是向量工程的高频动作：**入库前把向量 L2 归一化**（模长为 1）后，cosine 与内积等价——查询可以用更省的内积（`<#>` 且 SIMD 加速，见 07 篇），还可以在应用层预计算部分结果。归一化的两种姿势：入库时在应用侧归一化（模型输出 → 归一化 → 入库，最可控）；或在 SQL 里用 `embedding / l2_norm(embedding)` 表达式列（函数索引）——**应用侧归一化是主流**，因为查询向量同样要归一化（两边都要做，做在应用层一次到位）。

数值边界的坑：`sparsevec` 的索引从 **1 开始**（不是 0）且**不允许负索引**；`halfvec` 存储时对超出 float16 范围的值（|x| > 65504）会饱和——极端离群值会被截断，对检索几乎无影响但调试时可能困惑。这些边界细节写进团队 schema 注释，比事后查文档省时。

> 🎯 **核心要点**：默认 vector、高维用 halfvec、关键词用 sparsevec、量化层用 bit——四类型各有主场；六个操作符里 cosine 是 RAG 默认、`<#>` 负号是高频坑、索引必须与操作符一一对应；binary_quantize 的价值只在两阶段检索，单独用是浪费。
