# 混合检索与全文检索

> 语义召回 + 关键词召回的互补——RRF 融合、稀疏向量混合、以及 PG 全文检索的中文方案

## 1. 为什么需要混合检索

纯向量检索（语义）对**专有名词、精确词句、数字型号**不敏感——"JVM 垃圾回收器 CMS 参数"这类查询，语义可能漂到别的垃圾回收文章；纯全文检索（FTS）对**同义改写、口语表达**无计可施。混合检索把两条路的结果融合，实测比纯语义检索提升 10-20% 召回，是 2025 年后 RAG 工程的标准配置。

PgVector 做混合检索有一个独门优势：**FTS 是 PostgreSQL 原生能力**（tsvector/tsquery），向量与全文在同库、同查询、同事务——不需要像 Chroma/Qdrant 那样外挂 ES 或稀疏向量服务。

## 2. 基础：PostgreSQL 全文检索（FTS）

```sql
ALTER TABLE documents ADD COLUMN content_tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', content)) STORED;
CREATE INDEX idx_docs_tsv ON documents USING GIN (content_tsv);

-- 关键词检索
SELECT id, content, ts_rank_cd(content_tsv, query) AS rank
FROM documents, to_tsquery('english', 'JVM & GC') query
WHERE content_tsv @@ query
ORDER BY rank DESC
LIMIT 10;
```

要点：**tsvector 用生成列**（插入时自动计算，避免应用层维护）；GIN 索引是 FTS 标配；`ts_rank_cd` 给出相关性排序。**分词配置（text search configuration）决定检索行为**：`simple` 不处理词形（"JVM" 与 "jvm" 不同）、`english` 做词干化（"running"→"run"）、`pg_catalog.english` 是最常用起步配置——按内容语言选择，混语言内容用 `simple` 最稳（不丢词）。`to_tsquery('english', 'JVM & GC')` 的 `&`/`|`/`!` 是查询语法（与/或/非），注意与向量查询的写法区分。

中文注意：PG 默认分词器（simple/english）对中文**按整串处理**，`to_tsvector('simple', '向量数据库')` 不会切成词——中文混合检索需要自定义分词（zhparser/pg_jieba 扩展）或接受整词匹配（详见第 5 节）。此外 FTS 匹配是**词项匹配不是子串匹配**——`$contains` 风格的子串模糊查询 FTS 做不了，那是 like/正则的活；FTS 的价值在"词边界 + 词形 + 权重"的精确语义。

## 3. RRF 融合：混合检索的标准答案

RRF（Reciprocal Rank Fusion）用**排名倒数**融合两条结果，无需统一分数尺度：

```sql
WITH semantic AS (
    SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS rank
    FROM documents ORDER BY embedding <=> $1 LIMIT 20
),
lexical AS (
    SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank_cd(content_tsv, query) DESC) AS rank
    FROM documents, to_tsquery('english', $2) query
    WHERE content_tsv @@ query LIMIT 20
)
SELECT id, SUM(1.0 / (60 + rank)) AS score   -- 60 为常数 k，压制排名靠后项的分数
FROM (SELECT * FROM semantic UNION ALL SELECT * FROM lexical) t
GROUP BY id
ORDER BY score DESC
LIMIT 10;
```

RRF 的取舍：**不需要归一化分数**（向量距离与 ts_rank 尺度完全不同，直接加权不可比——这是 RRF 相对加权融合的核心优势）；常数 k 越大，排名靠后的项越不重要（常用 60）。代价是**每路都要取足候选**（如上例各 20 条），两条查询的延迟叠加。

RRF 查询的两处工程化：一是**候选量选择**——每路候选量取目标 topK 的 2-4 倍（如上例目标 10 取 20），太少了融合后漏项、太多了放大扫描成本；二是**只在一路有结果时退化为单路**——`UNION ALL` 天然处理（另一路空集不影响），但要确认结果里同时包含"语义命中但关键词没命中"的条目（这正是混合检索的价值）。融合后用同一批标注数据评估：混合 vs 纯语义的命中率对比（实测提升 10-20%）——**没有评估就上混合检索，等于不知道融合参数调没调对**（评估方法与 Chroma 体系 08 篇一致：命中率 + MRR）。

## 4. 加权融合与稀疏向量混合

**加权融合**（分数可比时）：向量距离与 FTS 分数归一化到 [0,1] 后线性加权（如语义 0.7 + 关键词 0.3）——权重可调是优势，但归一化本身引入误差，且融合结果不是排名融合。

**稀疏向量混合**（0.8 起）：同一查询里稠密 + 稀疏双列各算距离，加权合成：

```sql
SELECT id,
       (embedding <=> $1) * 0.7 + (bm25_vec <#> $2) * 0.3 AS score
FROM documents
ORDER BY score
LIMIT 10;
```

其中 `bm25_vec` 是 sparsevec 列（BM25/SPLADE 模型输出）。适用场景：embedding 管道直接产出稀疏向量（SPLADE/BGE-M3）时**库内一次查询完成融合**，无需 FTS 列与两路查询——比 RRF 少一次查询，但需要稀疏向量来源与权重调优。

## 5. 中文全文检索方案

PG 默认分词对中文的局限与对策：**zhparser 扩展**（基于 SCWS 词库，`CREATE EXTENSION zhparser` + 自定义 text search configuration）是最成熟方案——建配置、绑定 zhparser、重建 tsvector 列，之后 `to_tsvector('zh_cfg', content)` 正常分词；**pg_jieba** 是轻量替代；实在不想装扩展，用"整句匹配 + 向量召回"混合——中文短词检索质量会打折，接受即可。

工程判断：中文 RAG 的混合检索，**语义向量召回是主力，FTS 只补专有名词与型号**——对中文，给 FTS 配 zhparser 的收益在"精确词命中"场景明显；如果检索质量仍不达标，把稀疏向量（BGE-M3 同时出稠密+稀疏）纳入混合是 2026 年中文 RAG 的进阶方向。

融合权重的调优方法：RRF 无权重概念（排名融合，k 值即隐式权重），加权融合才有权重——**用标注集做网格搜索**（0.5/0.5、0.7/0.3、0.8/0.2 等组合跑命中率），而不是拍脑袋定值；融合方式的进阶认知：**RRF 适合"两路分数不可比"**（向量距离 vs ts_rank）、**加权适合"两路分数已归一化"**（如都是 [0,1] 的相似度）——实际系统常以 RRF 起步（无需归一化），需要精细控制时切换加权，两种融合在工程上都有成熟实现。

混合检索还有一个隐藏收益：**它天然是"关键词兜底"**——纯语义检索在专有名词/型号上翻车时，FTS/稀疏路能救回——所以"混合上线后单路挂了降级到另一路"也成立（两路独立查询，一路超时就只用另一路），检索的可用性架构白拿。部署时把两路查询的耗时与失败率分开监控，降级阈值写进配置。两路都返回空时进入显式兜底（如返回"无结果"而非空上下文喂给 LLM 编造答案）——空结果的处理是 RAG 生产上线前最容易被忽略的边界。

> 🎯 **核心要点**：混合检索 = 语义 + 关键词，实测召回 +10-20%；RRF 是标准答案（排名融合免归一化，k=60 常用）；有稀疏向量源时用双列加权一次查询；中文 FTS 必须 zhparser 或接受整词匹配，中文混合检索主力仍是语义召回。
