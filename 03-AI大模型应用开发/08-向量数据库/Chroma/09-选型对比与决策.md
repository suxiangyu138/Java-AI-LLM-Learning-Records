# 选型对比与决策

> Chroma 不是所有场景的答案——与 Milvus/Qdrant/PgVector/Redis Stack/FAISS 逐项对比，最后给一张可执行的决策树

## 1. 竞品全景与定位差异

向量存储的选型首先分清楚三个象限：**嵌入式单机库**（Chroma、FAISS、LanceDB）、**独立服务向量库**（Milvus、Qdrant、Weaviate）、**通用数据库扩展**（PgVector、Redis Stack、ES kNN）。Chroma 站在第一象限——"客户端即服务"，零部署启动是它的本质优势，也是它的规模天花板来源。

| 维度 | Chroma 1.5.x | Milvus 3.0 | Qdrant | PgVector | Redis Stack | FAISS |
|------|-------------|-----------|--------|----------|-------------|-------|
| 形态 | 嵌入式/单节点 | 分布式集群 | 单节点/集群 | PG 扩展 | Redis 模块 | 纯库 |
| 部署成本 | 零（pip） | 高（K8s） | 中（Docker） | 中（需 PG） | 低 | 零 |
| 规模天花板 | 1-2M 向量 | 十亿级 | 亿级 | 千万级 | 百万级 | 取决于宿主 |
| 过滤 | post-filter | pre-filter 强 | **过滤感知索引** | SQL 强 | 中等 | 无 |
| 混合检索 | BM25/SPLADE（较新） | 原生成熟 | 原生成熟 | 稀疏向量 | 无 | 无 |
| 量化 | 无 | SQ8/GPQ 等 | 有 | 半精度 | 无 | SQ/IVF |
| 多租户/认证 | 无（1.x 网络层） | 有（RBAC） | 有 | PG 用户体系 | ACL | 无 |
| Java 生态 | Spring AI 官方 | Spring AI 官方 | Spring AI 官方 | Spring Data/JPA | Spring Data | 需自封装 |
| 协议 | Apache 2.0 | Apache 2.0 | Apache 2.0 | PostgreSQL | Redis | MIT |

## 2. 逐个竞品的取舍分析

**vs Qdrant**：最大对手。Qdrant 的过滤是"过滤感知"（pre-filter 或过滤感知 HNSW），强过滤场景召回不丢；有量化降低内存；混合检索更成熟。Chroma 仅在两处占优：**零部署的嵌入式体验**与**更低的运维心智**。规模超过 2M 向量或过滤条件复杂，Qdrant 是更稳的选择。

**vs Milvus**：Milvus 面向十亿级与分布式（3.0 Lake-Native 架构直连数据湖），带 RBAC/多租户/监控全家桶，是"企业级 AI 数据基础设施"。但部署复杂度高出两个量级——10M 向量以内用 Chroma 是过度工程，10M 以上用 Milvus 才是正路。中间地带（2-10M）看团队运维能力与增长预期。

**vs PgVector**：事务型应用已有 PostgreSQL 时的自然选择——向量与业务数据同库，支持 SQL 过滤与事务。代价是向量能力弱于专业库（索引选择少、无内置 embedding 管道）。**选型口诀：已有 PG 且向量需求简单 → PgVector；向量是核心诉求 → Chroma/Qdrant**。

**vs Redis Stack**：只适合"向量 + 缓存"融合场景（低延迟、数据量小、可丢失容忍），向量只是 Redis 的一个模块。Chroma 在持久化与检索能力上全面占优。

**vs FAISS**：FAISS 是库不是数据库——无持久化、无过滤、无并发控制，需要自己写全套工程。**Chroma 可以理解为"FAISS + 存储 + 过滤 + 客户端"的完整封装**，只追求极致检索性能（且不介意自建工程）才裸用 FAISS。

## 3. Chroma 的真实适用边界

**适合（甜区）**：RAG 原型与教学；单机应用内嵌知识库（本地文档问答）；小团队生产（<1M 向量、简单过滤、无多租户）；需要"代码级零运维"的场景；Agent 记忆存储（会话级，数据量天然小）。

**不适合（红线）**：>2M 向量且持续增长；强选择性过滤是核心查询模式；需要多租户隔离与行级权限；中文全文检索是核心需求（trigram 局限，见 06）；要求数据库自带认证与审计；多区域高可用。

选型要把**增长预期**算进去：数据量半年翻倍的项目，第一版就按 Qdrant 设计（迁移成本远高于首版部署成本）；增速平缓的内部工具则放心用 Chroma，等真到边界再迁移也不迟——09 篇第 6 节的决策树配合"增长曲线"一起看，比单点判断更稳。

## 4. 三个典型选型场景（推演）

把决策树落到具体场景，判断逻辑比结论更重要：

**场景 A：单机桌面文档问答工具**。数据量几十万条、单用户、无过滤需求、要"装完就能用"。选 Embedded 模式的 Chroma——零部署、随应用分发（数据目录跟着应用走）、无运维成本。此场景选 Milvus 或 Qdrant 都是过度工程：多一个要拉起的服务，就多一份安装失败的可能。

**场景 B：电商客服知识库（带商品分类过滤）**。百万级商品问答 + 高频"按类目 + 按价格区间"过滤。Chroma 的 post-filter 在"类目过滤"这类中等选择性条件下还能接受，但**过滤条件一旦收紧（如精确型号 + 地区 + 时间），召回损失立刻暴露**；且团队要上多进程服务。结论：Qdrant 的过滤感知索引直接规避掉这个已知缺陷，选 Qdrant。

**场景 C：金融内部知识检索（合规敏感）**。亿级文档、要求 RBAC 多租户隔离、审计日志、高可用。Chroma 三项全缺（无内置认证、无多租户、无分片），Cloud 形态又过不了数据出域审查。结论：Milvus（企业版带 RBAC）或私有化 Qdrant。

三个场景的共性判断口诀：**规模问上限、过滤问机制、合规问特性、运维问团队**——四问过后，Chroma 的适用边界自然清晰。

## 5. Chroma Cloud：付费层的真实价值

2026 年 Chroma Cloud 的能力：Serverless 自动扩缩、S3/GCS 对象存储底座、EU 区域、AWS PrivateLink、CMEK 客户密钥、SOC 2 Type II、企业 BYOC。定价：Starter 免费（含 $5 额度）、Team $250/月、企业定制。

需要清醒认知两点：一是 **Cloud 解决的是运维与合规，不解决架构天花板**——开源版无分片，Cloud 的规模能力同样有限；二是数据出域问题——选择 Cloud 意味着向量数据（可能含敏感文档）进入托管方，合规敏感场景优先私有化部署。

## 6. 选型决策树

```text
数据量 < 1-2M 向量？
├── 否 → 需要十亿级/分布式？ → 是：Milvus；否：Qdrant
├── 是 → 已有 PostgreSQL 且向量需求简单？ → 是：PgVector
│         → 已有 Redis 且可容忍丢数据？ → 是：Redis Stack
│         → 需要中文全文检索或强过滤？ → 是：Qdrant
│         → 需要多租户/RBAC/审计？ → 是：Qdrant/Milvus
│         → 否则 → Chroma（嵌入式/Server 按需切换）
```

决策树只回答"第一版"——向量需求 90% 会增长，**上线时记录 embedding 模型与集合 schema，预留换库路径**（Spring AI 统一 VectorStore 接口正是为此设计，见 08）。

> 🎯 **核心要点**：Chroma 的甜区是"<1-2M 向量、零运维、嵌入式"；过线就换 Qdrant（规模+过滤）或 Milvus（十亿级+企业能力）；"已有 PG 用 PgVector、向量是核心诉求才用专业库"是通用选型口诀；Cloud 解决运维不解决架构，选型时把增长预期算进去。
