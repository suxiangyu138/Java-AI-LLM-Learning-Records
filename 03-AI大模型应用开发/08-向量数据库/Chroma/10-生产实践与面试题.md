# 生产实践与面试题

> 把前面九篇沉淀为"避坑清单 + 生产清单 + 面试弹药"——最后一篇不学新概念，验收你是否真的能上生产

## 1. 性能真相

先用数据校准预期（1.5.x，2026 基线）：

- **写入**：Server 模式约 4 万+ 向量/秒（Rust 核心 + WAL 批量追加），批量 50-250/批打满。
- **查询**：中小规模 p95 约 10ms（HNSW 全内存）；规模增长后延迟曲线受内存带宽约束，无量化意味着每条记录的内存成本固定。
- **天花板**：1-2M 向量是性能甜区边界——超出后"查询延迟 + 后置过滤召回损失 + 内存成本"三者同时恶化。

## 2. 避坑清单（Top 12）

1. **并发写损坏库**：`PersistentClient` 多进程并发 upsert 会永久损坏数据库（本地索引非线程安全）——多写者必须 Server 模式。
2. **`n_results` 超量报错**：`k = min(k, collection.count())` 钳制；结果判空再取 `ids[0]`。
3. **embedding 不一致**：写读换模型 = 检索结果无意义；模型名写进 collection metadata 留痕。
4. **space/维度创建后不可变**：改度量只能删集合重建，建集合前想清楚。
5. **post-filter 吞结果**：强过滤 + 大集合时结果数 < n_results，先 `get(include=[])` 验证命中量。
6. **中文全文检索静默空结果**：trigram 需 ≥3 字符；1-2 字符中文子串查询直接空——预分词或 $regex 兜底。
7. **`update` 只改 documents 会重算向量**：依赖默认 embedding 函数时会发起网络请求。
8. **`$in/$nin` 列表类型不一致报错**：数组元数据须同类型、不嵌套、不为空。
9. **忘记持久卷**：1.x 无内存模式，Docker 不挂卷重启即丢数据；Helm PVC 默认 Delete 要改 Retain。
10. **镜像 tag 不锁定**：每周一发布的新版本可能带行为变化，用 `chroma run`/镜像 tag 锁版本。
11. **备份拷活库文件**：WAL + segment 不一致 = 损坏备份；只做文件系统级快照。
12. **1.x 认证配置静默忽略**：`chromadb.auth.*` 不报错但无效，安全靠网络层（内网 + 反代认证 + mTLS）。

## 3. 生产落地清单

- 部署：持久卷挂载、镜像 tag 锁定、`/api/v1/heartbeat` 探活、资源限制（内存按 10M≈57GB 公式预算）。
- 数据：批量 50-250/批写入、模型名入 collection metadata、写前数据清洗（去重/脱敏）。
- 检索：topK 钳制、include 最小化、过滤条件先验证命中量、混合检索补召回。
- 安全：内网隔离、反代认证 + TLS、应用层 token（Spring AI `withKeyToken`）。
- 可观测：heartbeat 告警、查询 P95 与结果数监控（结果数骤降 = post-filter 事故）、OTel tracing。
- 备份：每日文件级快照 + 季度恢复演练 + 快照保留周期。
- 增长预案：记录 embedding 模型与 schema，预留 Qdrant/Milvus 迁移路径（Spring AI VectorStore 抽象）。

## 4. 面试高频题与答题范式

**Q1：Chroma 和其他向量数据库的本质区别？**
答：嵌入式优先——`pip install` 即可进程内使用，客户端即服务；1.0 Rust 重写后 4× 性能；代价是单节点 1-2M 向量天花板、无分片。横向对比时主动引出 Qdrant/Milvus 的定位差异（见 09）。

**Q2：Chroma 的存储架构是怎样的？**
答：日志结构化——SQLite 承载 sysdb/WAL/元数据/FTS5，每集合 UUID 目录存 HNSW 二进制；写操作先追加 WAL 立即返回，后台 compaction 物化进 segment；查询合并 segment + WAL。分布式形态换 PostgreSQL/Spanner + 对象存储。

**Q3：HNSW 三个参数怎么调？**
答：M 控图密度（16 默认）、construction_ef 控建图质量（100-200）、search_ef 控查询召回（100-300，可运行时调）；召回不足先加 search_ef，再不够重建索引调 M/construction_ef。space 与维度创建后不可变。

**Q4：为什么强过滤场景 Chroma 会丢结果？**
答：post-filter 语义——HNSW 先召回 k 个近邻再做谓词过滤，强选择性条件下候选集可能无一条满足，结果数 < n_results。解法：过滤条件弱化/提前、或换 Qdrant 的过滤感知索引。

**Q5：Chroma 适合哪些场景、不适合哪些？**
答：适合 RAG 原型、单机内嵌知识库、Agent 记忆、小团队 <1M 向量生产；不适合 >2M 向量、强过滤、多租户、中文全文检索核心诉求、要求内置认证的场景。

**Q6：Java 项目怎么接入 Chroma？**
答：Spring AI 官方 starter（`spring-ai-starter-vector-store-chroma`），`ChromaApi` + `ChromaVectorStore` 实现统一 `VectorStore` 接口，换库只换依赖与配置。配置要点：host/port、collection-name、initialize-schema。

**Q7：生产环境怎么保障 Chroma 安全？**
答：1.x 内置认证已失效（静默忽略）——内网不暴露 8000、反代终止认证与 TLS、应用层 token、敏感场景 mTLS。

**Q8：线上检索召回率突然下降，你怎么排查？**
答：按"数据 → 参数 → 过滤 → 索引"四层排查。先确认数据侧（新入库数据的 embedding 模型是否一致、是否混入脏数据）；再查查询参数（search_ef 是否被覆盖调小、topK 是否变化）；然后看过滤条件（post-filter 下新增的强过滤条件会直接吞结果——用 `get(where=..., include=[])` 验证命中量）；最后看索引（集合是否超出 1-2M 规模、HNSW 参数是否被误改）。**"先验证命中量、再谈召回率"是排查这类问题的黄金第一步**——它把问题二分到"没召回到"（过滤/索引）还是"召回到没排前"（参数/数据）。

**Q9：现有 Chroma 数据怎么平滑迁移到 Qdrant？**
答：迁移的本质是"同源向量重放"，不是拷贝文件（存储格式不兼容）。流程四步：先在 Qdrant 建同名集合（space 与维度保持一致）；再用**同一 embedding 模型**批量读出 Chroma 记录（`get(include=["documents","metadatas","embeddings"])`）写入 Qdrant；切流前用同一组 query_texts 双库对拍召回质量（差距明显说明参数或模型不一致）；最后切换读流量、保留 Chroma 只读一段时间兜底回滚。**Spring AI 的 VectorStore 抽象让业务代码零改动**——这正是 08 篇强调"换库零成本"的落地场景。

**答题范式**：先定位（嵌入式 vs 分布式）→ 再给原理（存储/索引/过滤机制）→ 最后给边界与替代方案。向量库面试题的三段式结构比背参数值更能拿分。

> 🎯 **核心要点**：十二条避坑清单覆盖 90% 生产事故；"建集合想清楚、写读同模型、过滤先验证、快照保数据、增长留退路"是五条总纲；面试答题记住"定位 → 原理 → 边界"三段式。
