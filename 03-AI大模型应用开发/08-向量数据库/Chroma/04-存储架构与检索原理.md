# 存储架构与检索原理

> Chroma 1.x 的存储是"日志结构化 + 分段 + 惰性物化"的教科书实现——看懂它，就懂了整个向量库家族的共同骨架

## 1. 整体数据路径

1.x 的读写路径（Rust 核心）是一条清晰的管道：

```text
Client 调用 → API 层（Rust）→ Segment 层（每集合 3 个分段）→ Index（HNSW/SPANN）→ 持久化
```

- **本地单节点**：sysdb 用 SQLite，segment 落本地磁盘文件。
- **分布式形态**（K8s/Cloud）：同一套代码换组件接线——sysdb 换成 PostgreSQL（多区域用 Spanner），日志与 segment 放到 S3/GCS 对象存储。

也就是说，**Chroma 本地版不是"阉割版"**，而是分布式版同一代码库的单机接线，架构认知可以无缝迁移到云端。

## 2. 持久化目录解剖

`PersistentClient(path="./chroma")` 会在 path 下生成一个 `chroma.sqlite3` 文件 + 若干 UUID 命名子目录（每个 collection 一个，装 HNSW 索引二进制文件）。SQLite 承担四类数据：

| 数据 | 表/内容 | 职责 |
|------|---------|------|
| sysdb | tenants/databases/collections/segments 及其 metadata | 元数据编目：谁存在、配置是什么 |
| WAL | embeddings_queue / max_seq_id 等 | 写日志：每次 add/update/delete/upsert 先追加 |
| 元数据段 | embeddings / embedding_metadata / embedding_fulltext_search（FTS5 虚拟表） | 记录本体：文档、键值对、全文索引 |
| migrations | 版本迁移记录 | schema 演进 |

每个 collection 对应三个 segment 文件组：**记录段**（用户 ID ↔ 内部偏移映射）、**元数据段**（document/metadata/fulltext 三份 blockfile）、**向量段**（HNSW/SPANN 二进制：header、data、link_lists 等）。

## 3. 写路径：WAL 追加与后台 compaction

Chroma 采用日志结构化存储，这是它吞吐高的根基：

1. 写操作先**追加到 WAL**（`embeddings_queue`），返回成功——延迟只花一次顺序追加。
2. 后台 **compaction** 异步把日志物化进各 segment 索引：记录段按用户 ID 对操作做去重合并（add/update/delete 按 ID 归并），向量段把新向量批量插入 HNSW。
3. 查询时**合并 compacted segment 与 WAL 中的新日志**，保证刚写入的数据立即可见。

三个工程含义：一是"写后立即读"一致性由查询期合并保证，不用等 compaction；二是**断电恢复**靠 WAL 重放（`max_seq_id` 记录重放起点），这也是为什么直接拷贝活库文件做备份不安全（见 07）；三是 HNSW 索引**常驻内存**，启动时从磁盘加载——大数据量冷启动慢是正常现象。

## 4. 读路径：HNSW 召回 + 过滤精炼

查询分两步走，理解这两步是理解 Chroma 性能特性的关键：

1. **粗召回**：用 query embedding 在 HNSW 图上做近似最近邻搜索，取出候选集合（不受过滤条件影响）。
2. **精炼过滤**：在候选集合上应用 `where`（SQLite/blockfile 谓词）与 `where_document`（FTS5），返回满足条件的记录。

这解释了 Chroma 最著名的缺陷——**元数据过滤是 post-filter（后置过滤）**：过滤发生在召回之后。当过滤条件强选择性（比如 1000 万条里只匹配 5 条）时，HNSW 召回的前 k 个候选可能一条都不满足条件，结果就是返回远少于 `n_results` 甚至为空。同类竞品（Qdrant 等）支持 pre-filter 或过滤感知索引，这是规模场景弃 Chroma 转 Qdrant 的核心原因之一（见 09）。

## 5. 删除/更新的日志语义与冷启动

日志结构化架构下，**删除与更新都不是原地修改**，理解这一点能解释很多"奇怪"行为：

- **delete**：WAL 追加一条墓碑（tombstone），物理删除发生在后台 compaction——查询期合并逻辑会把墓碑 ID 过滤掉。所以删除后的集合 count 会立即减少（合并逻辑生效），但磁盘文件在 compaction 前不会缩小。
- **update/upsert**：同样是 WAL 追加，compaction 按用户 ID 归并时"后写的覆盖先写的"——同批内多条同 ID 记录按追加顺序取最后一条。
- **add 与 upsert 的差异在 WAL 层不体现**：add 的重复 ID 检查发生在写路径校验层（UniqueConstraintError），upsert 跳过检查直接追加——这是两者性能几乎无差、语义不同的根源。

**冷启动**是另一个工程现实：HNSW 索引常驻内存、启动时全量从磁盘加载——1M 向量级别的加载要数秒到数十秒，10M 级别以分钟计。三个应对：生产服务用 Server 模式长驻（只加载一次）；Embedded 模式复用 PersistentClient 实例（避免每次重建索引）；升级/重启窗口预留加载时间，探活端点（/api/v1/heartbeat）在加载完成前不应报就绪。

## 6. 一致性级别

分布式形态下，读取一致性可配置为两级（配置项 `default_read_consistency_level`）：

| 级别 | 行为 | 适用 |
|------|------|------|
| `INDEX_AND_WAL` | 查询合并已物化索引 + WAL 未物化日志 | 强一致，写后立即可见 |
| `INDEX_ONLY` | 只查已物化索引 | 弱一致，吞吐更高，WAL 里的新数据暂不可见 |

单机嵌入式模式天然强一致（同一进程直接读 WAL），此配置主要影响服务模式与分布式部署。

## 7. 规模边界与资源特征

基于上述架构，Chroma 的资源画像清晰且残酷：

- **内存**：HNSW 全量常驻内存，且**无内置量化**（0.x 时代有过量化实验，1.x 未内置）——10M 向量 float32 约需 57GB 内存，这决定了本地版的实际天花板。
- **写入吞吐**：服务模式约 4 万+ 向量/秒（Rust 核心 + 批量 WAL 追加），p95 查询延迟约 10ms（中小规模）。
- **过滤代价**：选择性越强、集合越大，post-filter 的召回损失越严重——规模 + 强过滤是 Chroma 的两个并发杀手，出现即考虑迁移。

两个杀手对应两条**预警指标**：查询返回数 / n_results 的比值（持续低于 1 说明过滤在吞召回）与内存增长曲线（HNSW 无量化，线性增长）。两者进监控面板后，"要不要换库"从拍脑袋变成看数据——比值跌破阈值或内存越线，就是触发 09 篇决策树的信号。

> 🎯 **核心要点**：Chroma = SQLite（sysdb/WAL/元数据）+ HNSW 内存索引 + 后台 compaction 的日志结构化架构；"先 HNSW 召回、后谓词过滤"的 post-filter 语义是它所有性能缺陷的总根源；看懂这一节，Milvus/Qdrant 的架构文档读起来全是熟面孔。
