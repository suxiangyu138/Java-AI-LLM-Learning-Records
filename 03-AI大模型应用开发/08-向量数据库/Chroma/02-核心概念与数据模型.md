# 核心概念与数据模型

> Chroma 的数据模型只有四层命名空间 + 一个四元组记录结构——搞懂这两件事，所有 API 行为都能推导出来

## 1. 四层命名空间

Chroma 用 **Client → Tenant → Database → Collection** 四级结构组织数据，从顶层到底层逐级隔离：

| 层级 | 默认值 | 作用 | 类比（关系型） |
|------|--------|------|--------------|
| Client | — | 访问入口，持有连接配置 | Driver/连接 |
| Tenant | `default_tenant` | 租户级隔离（多团队/多客户） | 实例 |
| Database | `default_database` | 租户内再分库 | 库 |
| Collection | 需命名 | 向量数据容器，含 embedding 函数与索引配置 | 表 |

操作中通常只需关心 Collection 层——Tenant/Database 使用默认值即可，`HttpClient` 构造时可指定，多租户场景才需要显式创建。一个 Collection 内可以混合存储不同来源的向量（通过 metadata 区分），但**同一个 Collection 的 embedding 维度和距离度量必须一致**，这是设计时的硬约束。

## 2. Collection：名称、配置与元数据

创建 Collection 时需要确定三件事：

- **名称**：创建后不可改（需先删再建）；1.x 起名称规则放宽为可含点/下划线等字符。
- **Embedding 函数**：可选。不指定时客户端用默认模型（0.5+ 为 nomic-embed-text-v1.5，会向官方端点请求）；指定后向量由你自己的模型生成。**凡是自己生成向量，一律显式传 `embedding_function=None` 并直接给 embeddings，避免隐式网络调用**。
- **索引配置**：通过 `metadata={"hnsw:space": "cosine"}` 传入。注意 **space 在创建后不可变**——想改距离度量只能删集合重建。

Collection 还可以携带业务元数据（如 embedding 模型名、版本号），官方建议把 embedding 模型名存进 collection metadata，换模型时用来审计一致性。

## 3. 记录四元组

Collection 中的每条记录由四个字段组成，Python API 中按"列"传参（每个参数是列表，长度必须一致）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|:---:|------|
| `ids` | str | 是 | 用户自定义唯一 ID，跨 collection 不要求全局唯一 |
| `embeddings` | List[float] | 视情况 | 维度必须与 collection 创建时一致；也可只传 documents 让 embedding 函数生成 |
| `metadatas` | dict | 否 | 过滤用的键值对，值仅支持 str/int/float/bool/数组 |
| `documents` | str | 否 | 原始文本，可用于全文检索与 embedding 生成 |

四个字段可以部分填充：只写 `ids + embeddings` 可以（纯向量存储）；只写 `ids + documents` 也可以（客户端用 embedding 函数生成向量）。`uris` 是第五个可选字段（2026 扩展，指向文件/资源，多模态场景用）。

元数据（metadata）的约束值得单独强调——它的值类型只有四种：`str`、`int`、`float`、`bool`，以及 1.5+ 支持的同类型标量数组。写 `None`、嵌套 dict、混合类型数组都会在写入时被拒（服务端开启 schema 验证后更严格）。元数据同时是过滤的主战场：过滤字段设计直接决定查询效率与 post-filter 召回损失——**高基数字段（如 ID、时间戳）适合做过滤，低基数宽泛字段（如"是/否"标志）过滤收益低**；每个集合的元数据字段应有明确的字段字典（命名、类型、语义），与关系型数据库的列设计同等重视，因为过滤是 06 篇所有 where 操作符的地基。

## 4. 命名空间操作与多租户

Tenant/Database 平时被默认值掩盖，多租户时才是主角。Python 客户端操作方式：

```python
client.create_tenant(name="team_a")
client.create_database(name="docs", tenant="team_a")   # 数据库必须挂在租户下
col = client.get_or_create_collection("kb", tenant="team_a", database="docs")
```

租户（Tenant）与数据库（Database）的隔离语义：**租户间完全隔离**（元数据、集合互不可见，认证/计费维度），**库间隔离但共享租户上下文**。无内置 RBAC 的前提下，多租户的数据隔离靠命名空间 + 应用层权限控制实现——1.x 不提供行级权限，敏感数据不能只靠命名空间保护（见 07 安全）。

## 5. 距离度量与维度约束

Chroma 支持三种相似度度量，作为 HNSW 的 `space` 参数，创建集合时确定、之后不可变：

| space | 全称 | 适用场景 | 备注 |
|-------|------|---------|------|
| `l2` | 欧氏距离 | 通用默认 | 越小越相似 |
| `cosine` | 余弦相似度 | 文本语义检索 | 对向量长度不敏感，RAG 首选 |
| `ip` | 内积 | 已归一化向量 | 等价于归一化后的余弦 |

维度约束是新手最常见的报错来源：collection 创建时通过第一条数据隐式固定维度（或显式声明），之后**任何维度不一致的写入都会抛错**。查询端同样如此——`query_embeddings` 的维度必须匹配。跨 embedding 模型复用 collection 是不允许的，这也是"换模型必须建新集合 + forking 对比"的根本原因。

度量选择的实操判断：**默认用 cosine**，它不惩罚向量长度差异，对文本语义检索最稳；embedding 模型输出已做归一化（模长为 1）时，cosine 与 ip 数学等价——此时可改用 ip（少一次归一化计算）；l2 适合"向量长度本身携带信息"的场景（如频率型特征），文本 RAG 里几乎不用。注意返回的 `distances` 随 space 语义不同：l2 越小越近（0 为完全一致），cosine 越小越远（0 为垂直）——**展示相似度分数给用户前先换算**（cosine 相似度 = 1 - distance），这是集成层最常写错的地方。

## 6. 与关系型数据库的概念映射

用 SQL 心智迁移到 Chroma：

- 建表 = `create_collection(name, metadata={"hnsw:space": ...})`
- 插入 = `collection.add(ids, embeddings, metadatas, documents)`（批量按列传参，类似 executemany）
- 主键冲突 = `add` 重复 ID 抛 `UniqueConstraintError`，用 `upsert` 覆盖
- WHERE 过滤 = `where`（元数据）+ `where_document`（文档内容），两者隐式 AND
- 精确查询 = `get(ids=[...], where={...})`，支持 `limit/offset` 分页
- 相似搜索 = `query(query_embeddings=..., n_results=k)`——关系型没有对应物，这是向量库存在的意义

注意两个与 SQL 直觉相悖的点：一是 **metadata 过滤发生在 HNSW 召回之后**（post-filter），过滤条件越强，返回结果可能越少于 `n_results`；二是 `get` 返回的是扁平列表（列主序），`query` 返回的是按输入查询分组的嵌套列表——解析结果前先确认形态，这是最常见的取数 bug。

> 🎯 **核心要点**：四级命名空间 + 记录四元组 = Chroma 数据模型的全部；两个不可变约束（embedding 维度、space）决定建集合必须想清楚，两个结果形态（get 扁平 / query 嵌套）决定取数必须分清楚。
