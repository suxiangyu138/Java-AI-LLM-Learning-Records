# 索引配置与参数调优

> HNSW 是 Chroma 的默认索引，也是你唯一需要真正理解的数据结构——三个参数控制召回率与开销的此消彼长

## 1. HNSW：图式近邻索引的工作原理

HNSW（Hierarchical Navigable Small World）把向量组织成**多层图**：顶层节点稀疏（长距离跳转），底层节点稠密（精确邻居）。搜索时从顶层出发，每层贪婪地走向最近的邻居，逐层下降直到最底层——查询复杂度是 polylogarithmic（随规模增长极慢），这是它能扛千万级向量的原因。

```text
搜索路径示意：顶层粗定位 → 逐层下钻 → 底层精确收敛
    L3:  A ──── C ──── E          ← 稀疏层，长跳
    L2:  A ─ B ─ C ─ D ─ E
    L1:  A-B-C-D-E-F-G-H          ← 稠密层，精确邻居
   查询 x：从 A 开始，逐层找最近邻，下钻到底层返回结果
```

三个特点决定它的工程属性：**全内存运行**（启动时从磁盘加载，见 04）；**插入即用**（无需批量构建索引，逐条 add 自动入图）；**近似检索**（牺牲可接受精度换取速度——精度由 ef 参数控制，调到足够大时逼近暴力搜索）。

## 2. 参数全解：M、construction_ef、search_ef

HNSW 三个核心参数，作用各有分工：

| 参数 | 控制阶段 | 作用 | 调大后果 |
|------|---------|------|---------|
| `M` | 建图 | 每个节点最多连接的邻居数，决定图密度 | 召回↑、内存↑、建图与查询变慢 |
| `construction_ef` | 建图 | 插入向量时探索的候选节点数 | 索引质量↑、构建耗时↑ |
| `search_ef` | 查询 | 搜索时探索的候选节点数 | 召回↑、查询延迟↑（可运行时调） |

参数取值经验线：`M` 常用 16-32（16 是精度/内存平衡点，32 偏向高召回）；`construction_ef` 常用 100-200；`search_ef` 常用 100-300，且**不必与 construction_ef 相同**——查询质量不足时先调 search_ef，它只影响查询延迟不影响索引本身。调参的本质是拿开销换召回：召回率不足先加 search_ef（最便宜），还不够再加 M（贵，且要重建索引）。

## 3. 1.0+ 的配置方式：YAML 配置字典

1.0 起 HNSW 配置从 collection metadata 迁移到 **YAML 配置字典**，两种方式并存但后者是正路：

```python
collection = client.create_collection(
    name="docs",
    configuration={
        "hnsw": {
            "space": "cosine",
            "M": 16,
            "construction_ef": 100,
            "search_ef": 100,
        }
    },
)
# 查询期调 search_ef（不改索引本身）
collection.query(query_texts=[...], n_results=10,
                 configuration={"hnsw": {"search_ef": 200}})
```

全套可用参数还包括 `num_threads`（建图线程数，默认 CPU 核数）、`resize_factor`（图容量将满时的扩增倍率）、`batch_size`（向量先积攒在暴力索引、满批后再转入 HNSW 的批量大小）。**旧的 `metadata={"hnsw:space": "cosine"}` 写法仍兼容但已标记弃用**——新代码一律用 configuration。

三条不可变铁律：**`space` 创建后不可改**（想换度量只能删集合重建）；**configuration 在集合创建后只能部分调整**（如 search_ef 可运行时覆盖，M/construction_ef 不可）；**换 embedding 模型必须建新集合**——向量空间都变了，索引参数调得再好也没用。

查询期的 configuration 覆盖是生产中最常用的调优旋钮——**同一集合在不同查询场景用不同 search_ef**（首页检索用低延迟配置 ef=100，深度检索用高召回配置 ef=300），不重建索引、不改集合，纯查询参数。覆盖规则：查询覆盖只作用于本次调用，且只允许覆盖查询侧参数（search_ef），建图参数（M、construction_ef、space）在查询期传入会被忽略。

从 0.x 迁移的老集合注意：旧的 `metadata={"hnsw:space": "cosine", "hnsw:M": 16}` 写法虽然仍兼容，但**与 1.x 的 configuration 同时存在时以 configuration 为准**；迁移存量代码时把 metadata 中的 hnsw:* 键清掉、统一走 configuration，避免两套配置互相打架的排查地狱。

## 4. SPANN：分布式/云端的索引选项

`default_knn_index` 配置决定新建集合默认使用哪种索引：单节点默认 `hnsw`，分布式与 Chroma Cloud 可选 `spann`。SPANN（Spatially Partitioned ANN）把图索引切分到多节点，用"集群中心 + 分区图"两级结构支撑百亿级向量——单机场景不需要它，知道"云端换引擎、参数语义不同"即可，避免把 HNSW 的调参经验生搬到 SPANN 上。

单节点时另两个参数影响写入路径：`num_threads` 默认取机器 CPU 核数——**容器部署要按 CPU limit 显式设置**，否则建图线程数与配额不匹配，反而因调度竞争变慢；`batch_size` 决定向量先在暴力索引积攒多少再批量入图——**批量导入任务调大（提升吞吐），在线小流量写入保持默认**（降低单条延迟与峰值内存）。

## 5. 调优决策树与内存预算

按症状选动作：

1. **召回率不够（漏检多）**：优先调大查询期 `search_ef` → 仍不足则重建索引调大 `M` 与 `construction_ef`。
2. **查询慢**：调小 `search_ef`、减小 `n_results`、缩小 `include` 返回字段——三者都不够则集合超规模了。
3. **内存吃紧**：HNSW 无量化，唯一正路是减少向量数（降维/过滤旧数据）或换库（Qdrant 有量化，见 09）。
4. **写入慢**：批量 50-250 条/批、调大 `batch_size` 减少 HNSW 图插入频率、调大 `num_threads`。

内存估算粗线：float32 每向量 = 维度 × 4 字节 + HNSW 图链接开销（每个节点 M × 8 字节量级）。768 维 × 100 万条 ≈ 3GB 向量本体 + 约 0.3-1GB 图结构——**10M 向量总内存轻松破 10GB，接近 57GB（含元数据与过滤结构）**。预算不够就回到 1-2M 向量的安全区，或者按 09 的决策树换方案。

调优常见误区五条，避免在错误的方向上浪费时间：一是**一上来就调 M**——先确认 search_ef 已拉满，M 影响建图需要重建索引，代价最大；二是**把 construction_ef 当查询参数**——它只影响建图质量，查询期调了等于没调；三是**用查询性能反推建图参数**——查询快慢由 search_ef 与集合规模决定，与建图参数无关；四是**忽略 embedding 分布**——低质量 embedding（大量重复、聚类严重）让 HNSW 图结构退化，调参治标不治本，先换模型；五是**对同一集合混用不同度量认知**——space 固定是 cosine 就永远按 cosine 解读 distance，别拿 l2 的直觉套 cosine 结果。

> 🎯 **核心要点**：调优三板斧——召回不足调 search_ef（最便宜）、建图质量调 construction_ef、图密度调 M（最贵且要重建）；space 与维度创建后不可变是红线；内存预算先算 float32 本体再算图开销，超 1-2M 向量就考虑换库。
