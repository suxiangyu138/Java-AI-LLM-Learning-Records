# 定位与版本演进

> 先回答三个问题：Chroma 在向量数据库谱系里站在哪？它为什么在 2025 年重写核心？旧教程为什么全面失效？

## 1. 在向量数据库谱系中的位置

向量数据库按运行形态分两类：**嵌入式（embedded）**与**独立服务（client-server）**。Chroma 的核心身份是嵌入式优先——`pip install chromadb` 后直接在自己的 Python 进程里读写向量，不需要部署任何服务、不需要配置文件。这让它成为学习向量检索、做 RAG 原型、跑本地实验的默认选择。

但这不意味着它只能嵌入。Chroma 支持四种部署形态，同一套 API 从嵌入式平滑升级到分布式：

| 形态 | 运行方式 | 适用场景 |
|------|---------|---------|
| EphemeralClient | 内存中，不落盘 | 测试、教学 |
| PersistentClient | 进程内 + 本地磁盘持久化 | 单机应用、原型 |
| HttpClient（Server 模式） | `chroma run` 独立服务 | 多进程/多语言访问 |
| Chroma Cloud | 托管 Serverless | 生产、多区域 |

与同级竞品对照：Milvus/Qdrant 本质是"部署一个服务再用客户端连"，Chroma 是"客户端即服务"。后者的代价是单节点天花板——开源版最优规模在 1-2M 向量以内，超出后查询性能明显衰减（详见 09 选型对比）。

## 2. 版本演进：0.x → 1.0 的 Rust 重写

Chroma 的版本史以 **v1.0.0（2025 年 3 月）**为分水岭，此前此后是两个不同的产品：

| 版本 | 时间 | 核心变化 |
|------|:----:|---------|
| 0.4.x | 2023-2024 | 纯 Python 核心，DuckDB+Parquet 存储，内置 Basic Auth（htpasswd） |
| 0.5.x | 2024 | 默认 Embedding 从 all-MiniLM-L6-v2 换为 nomic-embed-text-v1.5 |
| **1.0.0** | **2025-03** | **Rust 核心重写，4× 性能；存储改 SQLite+HNSW 文件；内置认证被静默忽略** |
| 1.5.0 | 2026-02 | Rust sysdb 实现、`$contains` 数组过滤、SPANN 配置支持 |
| 1.5.3 | 2026-03 | Python 3.14 支持（移除 Pydantic v1 兼容层）、删除操作带 limit |
| **1.5.9** | **2026-05-05** | 当前最新（2026-08 基线）；项目保持每周一发布节奏 |

重写带来的三个根本变化，决定了"老教程不可信"：

1. **性能**：写入/查询约 4× 加速（服务模式约 1 万 → 4 万+ 向量/秒），p95 延迟稳定在约 10ms。
2. **存储架构**：0.x 的 DuckDB+Parquet 被替换为 SQLite（sysdb/WAL/元数据）+ 每集合 HNSW 二进制文件，分布式形态下可换成 PostgreSQL/Spanner + S3 对象存储（见 04 存储架构）。
3. **认证语义**：`chromadb.auth.*` 配置在 1.0+ 仍被接受但**静默忽略**——官方立场转为"认证交给网络层"（反代/mTLS/私有网络），这直接改变了生产部署方式（见 07 部署）。

## 3. 2026 年 1.5.x 的能力扩展

1.5.x 系列在稳定核心之上持续补能力，方向是"让中小规模生产更顺手"：

- **数组元数据过滤**：`$contains` / `$not_contains` 判断数组字段是否包含某标量（1.5.0）。
- **混合检索**：原生稀疏向量支持（BM25/SPLADE），与稠密向量互补召回（见 06）。
- **全文检索增强**：`$regex` / `$not_regex` 正则过滤，配合 trigram 子串匹配。
- **Chroma Sync**：从 S3、GitHub、Web 源自动摄取数据入库（见 08）。
- **集合分叉（Collection Forking）**：复制集合做 A/B 测试，典型场景是对比两个 Embedding 模型的效果。
- **GroupBy 查询**：按元数据字段聚合搜索结果。
- **元数据 Schema 验证**：服务端校验元数据字段类型，防脏数据。
- **可观测性**：OpenTelemetry tracing（OTLP gRPC）接入。
- **高级检索 API**：1.5.x 转正出 beta。

此外 2026 年发布了 **Context-1**：Apache 2.0 开源、200B 参数的 agentic search 模型（基于 gpt-oss-20b + LoRA + RL 训练），定位多轮检索场景，与 Chroma 本身配套形成"模型 + 数据库"组合。

## 5. Embedding 生态：向量从哪来

Chroma 本身不产向量，它是向量生态的"存储侧"——上游是 Embedding 模型。理解这条供应链才能正确选型：文本/图像 → Embedding 模型（OpenAI text-embedding、BGE、nomic-embed、OpenCLIP）→ 向量 → Chroma。三个工程事实：

1. **客户端内置默认 embedding 函数**：不显式指定时，chromadb 用内置模型并**发起网络请求**——0.5+ 默认是 nomic-embed-text-v1.5（早期版本为 all-MiniLM-L6-v2），换默认模型意味着 0.x 时代的老持久化数据必须显式指定原模型才能保持一致性。
2. **Embedding 维度 = 集合的硬约束**：768 维的集合写不进 1536 维的向量，query 端同样受限——换模型必须新建集合，这正是 Collection Forking 存在的意义（见 06）。
3. **距离度量与 embedding 模型配套**：cosine 是文本语义检索默认（对向量长度不敏感），归一化后的向量可以用 ip 等价替换——度量选择与模型输出的向量特性绑定（见 02、05）。

配合 `02-大模型基础与Prompt工程/Embedding` 体系阅读：那边讲"向量怎么算出来"，本体系讲"向量存哪、怎么查"——中间由 embedding 函数这层胶水连接。

## 6. 开源协议与商业生态

- **协议**：Apache 2.0，核心用 Rust（2025 起），Python/JS/TS 客户端为主，Go 客户端（本地/持久化）2026 年新增。
- **商业形态**：Chroma Cloud 提供 Serverless 托管（对象存储架构 S3/GCS、EU 区域、AWS PrivateLink、CMEK 客户密钥、SOC 2 Type II、企业 BYOC）；定价 Starter 免费档（含 $5 额度）、Team $250/月、企业定制——单节点免费版解决不了的问题，付费层也不解决架构天花板（无分片），这是选型时的清醒认知。

> 🎯 **核心要点**：Chroma = "嵌入式优先的 RAG 利器"；1.0 Rust 重写是理解一切现状的钥匙——性能、存储、认证三条线全被它改写；规模边界（1-2M 向量）是选型时不可回避的底线。
