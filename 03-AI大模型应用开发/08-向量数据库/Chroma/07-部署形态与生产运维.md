# 部署形态与生产运维

> embedded / Server / Cloud 三种形态怎么选、Docker 怎么起、1.x 认证失效后安全靠什么、备份监控怎么做——生产落地前必须读的一篇

## 1. 三种部署形态选型

| 形态 | 启动方式 | 数据位置 | 适用 | 局限 |
|------|---------|---------|------|------|
| Embedded | `PersistentClient(path=...)` | 进程内 + 本地磁盘 | 单进程应用、原型 | 多进程并发写会损坏库 |
| Server | `chroma run` 或 Docker | 服务端持久卷 | 多进程/多语言/生产 | 单节点，无分片 |
| Cloud | 托管控制台 | 云端对象存储 | 跨区域生产 | 数据出域、费用 |

三种形态**API 完全一致**——Python/Java/JS 客户端只需换连接方式。升级路径是"Embedded 跑通 → Server 承接多进程 → Cloud 承接规模"，代码零改动。Server 模式默认端口 8000，健康检查端点 `/api/v1/heartbeat`（返回 200 即活）。

## 2. Docker 部署与持久化铁律

```bash
docker run -d -p 8000:8000 \
  -v /data/chroma:/chroma/chroma \          # 持久卷：必须挂！
  --name chroma chromadb/chroma:1.5.9       # 镜像 tag 必须锁定
```

Rust 重写带来一条部署红线：**1.0+ 没有内存模式，服务始终写盘**——不挂持久卷，容器重启即丢全部数据。镜像 tag 要锁定具体版本（`chroma run` 与官方镜像默认无认证），避免滚动到未测试版本。K8s 用官方 Helm chart（注意 PVC 保留策略默认 Delete，卸载即删数据，需改 Retain）。

不用 Docker 时的等价做法是直接跑 CLI：`chroma run --path /data/chroma --host 0.0.0.0 --port 8000`（`--path` 指定持久目录，与 PersistentClient 的 path 同构——**可以直接把本地实验的目录原样交给服务模式加载**，这是 Embedded → Server 迁移零成本的关键）。Docker Compose 形态：

```yaml
services:
  chroma:
    image: chromadb/chroma:1.5.9
    ports: ["8000:8000"]
    volumes: ["chroma-data:/chroma/chroma"]
    environment:
      - CHROMA_SERVER_HOST=0.0.0.0
      - CHROMA_TELEMETRY=FALSE
      - IS_PERSISTENT=TRUE
volumes:
  chroma-data:
```

环境变量三件套（`CHROMA_SERVER_HOST`/`CHROMA_SERVER_PORT`/`CHROMA_TELEMETRY`）是部署时的高频配置；`IS_PERSISTENT=TRUE` 显式声明持久化意图，与挂载卷配套使用。

## 3. 安全：1.x 内置认证失效后的现实方案

**v1.0 起 `chromadb.auth.*` 认证配置被接受但静默忽略**——老教程的 htpasswd Basic Auth 方案已失效。当前官方立场：认证交给网络层。生产落地顺序：

1. **不暴露 8000 端口**到公网；服务放在内网（K8s ClusterIP），只允许应用网段访问。
2. **反向代理/网关终止认证**：nginx/Caddy 前面做 Basic Auth 或 OAuth2 代理，加 TLS（Let's Encrypt）。
3. **要求更高时用 mTLS** 双向证书认证，替代内置认证的"用户名密码"。
4. **加一层应用层 token**：Spring AI 的 `withKeyToken()` / `withBasicAuthCredentials()` 由应用自己校验，数据库本身不做安全假设。

安全基线一句话：**数据库无认证 ≠ 服务无认证**，把 Chroma 当"内网数据库"对待，认证与加密全部前置到接入层。

落地时按"最小安全清单"逐项打勾：端口不出公网（防火墙/安全组仅放行应用网段）；反代开启 TLS（Let's Encrypt 自动续期）；反代强制 Basic Auth 或 OAuth2 校验；环境变量与连接串不落明文（应用用密钥管理注入）；数据落盘加密（云盘加密/EBS 加密即可覆盖磁盘层）；遥测与日志脱敏（文档内容可能含敏感信息，日志只留元数据不落 document 原文）。六项做完，Chroma 的"裸奔"缺陷在接入层被完全补上。

## 4. 备份与恢复

备份只认**文件系统级快照**，理由在 04 讲过——WAL 与 segment 文件在持续写入时处于不一致状态，直接拷贝活库文件会得到损坏备份。推荐做法：

- **停机式**：短暂停写（`docker stop` 或暂停应用写入），对持久卷目录做 `tar` 压缩。
- **热备**：ZFS/btrfs 快照、云盘快照（AWS EBS snapshot 等）——文件系统级一致性由快照机制保证。
- **频率**：与数据重要度匹配，至少每日 + 写前快照；恢复演练按季度做，别等事故。

恢复就是"停服务 → 解压/回滚快照 → 起服务"三步。没有增量备份概念——量级在 GB 级的 Chroma 数据直接全量快照即可，1-2M 向量的数据量完全扛得住。备份的有效性由**恢复演练**验证而非备份本身：每季度选一个快照恢复到临时目录，起服务后跑 `collection.count()` 对比源库条数 + 抽 3-5 条 query 对拍结果，一致才算备份合格——"备份了但没验证"等于没备份。

## 5. 监控与可观测性

- **探活**：`/api/v1/heartbeat` 周期探测，挂了即告警。
- **Tracing**：1.5.x 支持 OpenTelemetry，通过 OTLP gRPC 导出 span——查慢查询链路用。
- **Prometheus 指标**：服务模式暴露向量写入数、查询延迟、内存占用等；重点盯内存（HNSW 全内存 + 无量化）与查询 P95。
- **应用侧**：Java 侧用 Micrometer 记录相似搜索耗时与结果数——**结果数明显少于 n_results 是 post-filter 吞结果的信号**，比数据库指标更早暴露检索质量问题。

健康检查的落地细节：`/api/v1/heartbeat` 只反映进程存活，**不反映索引就绪**——冷启动加载 HNSW 期间（大集合可达分钟级）进程已响应 heartbeat 但查询会变慢或等待。生产上把探针与就绪区分开：存活探针用 heartbeat，就绪探针在应用层做一次"count + 小查询"验证索引可用后再接流量。K8s 场景用 startupProbe 给足加载时间（initialDelay 按数据量估算），避免启动即被打死重启的循环。

## 6. 容量规划

给足内存，算清天花板：

- 内存公式：向量本体（float32 = 维度 × 4 字节 × 条数）+ HNSW 图链接开销 + SQLite 页缓存 + 元数据。经验值：**10M 条 768 维 ≈ 57GB**（含元数据），1M 条 ≈ 6-8GB。
- 磁盘：向量本体（float32 全量落盘）+ 文档原文 + WAL + 备份余量，预留 1.5-2 倍。
- 规模红线：**1-2M 向量**以内性能稳定；超出后 HNSW 内存与 post-filter 代价同时恶化，认真考虑 Qdrant（量化）或 Milvus（分布式）。
- 写入吞吐预算：Server 模式约 4 万+ 向量/秒，批量 50-250/批写入可打满；单条写入的吞吐上限低一个量级。

> 🎯 **核心要点**：挂持久卷 + 锁镜像 tag 是部署两条命；1.x 认证失效后"内网隔离 + 反代认证 + 应用层 token"三件套替代内置认证；备份只做文件级快照、恢复演练要定期；容量规划先算 57GB/10M 的账，超 1-2M 向量提前换方案。
