# 检索过滤与全文检索

> query/get 只是入口，where 与 where_document 才是检索质量的操纵杆——全操作符、中文全文检索的坑、混合检索与高级检索能力一网打尽

## 1. 过滤模型总览

Chroma 提供两套过滤，作用于 `query` 与 `get`：

- **`where`**：结构化元数据过滤（键值对比较）。
- **`where_document`**：文档内容过滤（全文/正则）。

两者同时给出时**隐式 AND**；内部实现上 where 走 SQLite 谓词、where_document 走 FTS5 全文索引。过滤发生在 HNSW 召回之后（post-filter，见 04）——高选择性过滤会吞结果，这是所有过滤操作的心智前提。

执行路径的差异影响性能策略：where 的谓词在 SQLite 层求值（索引助力有限，主要是行扫描），where_document 走 FTS5 倒排索引（子串/正则匹配快）。因此**优先用 where_document 做文本类过滤、用 where 做结构化过滤**；把高选择性的过滤字段（时间、分类）放在 where 里时，记得加大 `n_results` 作为缓冲（召回更多候选再过滤），这是对抗 post-filter 吞结果最便宜的手段。

## 2. where 元数据过滤全操作符

| 操作符 | 语义 | 示例 |
|--------|------|------|
| `$eq` / 简写 | 等于（`{"field": value}` 即 $eq） | `{"status": {"$eq": "active"}}` |
| `$ne` | 不等于 | `{"count": {"$ne": 5}}` |
| `$gt` / `$gte` / `$lt` / `$lte` | 数值比较（仅 int/float） | `{"price": {"$gt": 100}}` |
| `$in` / `$nin` | 在/不在列表中（列表须同类型） | `{"category": {"$in": ["tech", "ai"]}}` |
| `$contains` / `$not_contains` | **数组字段**含/不含某标量（≥1.5.0） | `{"tags": {"$contains": "tech"}}` |
| `$and` / `$or` | 逻辑组合，可嵌套 | `{"$and": [{"a": 1}, {"b": 2}]}` |

语法约束：每个过滤对象只允许一个字段或一个逻辑操作符；同一字段只能一个操作符；`$in/$nin` 列表须同类型；数组元数据须同类型、不可嵌套、不可为空。**大小写敏感**是元数据过滤的默认行为，`$ne` 与 `$nin` 会匹配到"字段缺失"的记录，写业务逻辑时注意。

## 3. where_document 文档内容过滤

| 操作符 | 语义 | 示例 |
|--------|------|------|
| `$contains` | 区分大小写的子串匹配 | `{"$contains": "JVM"}` |
| `$not_contains` | 不含某子串 | `{"$not_contains": "draft"}` |
| `$regex` / `$not_regex` | 正则匹配（可锚定） | `{"$regex": "^[0-9]{6}"}` |
| `$and` / `$or` | 逻辑组合 | `{"$or": [{"$contains": "a"}, {"$regex": "b.*"}]}` |

正则过滤功能强但**在大集合上很慢**——优先锚定与具体模式。调试过滤条件先用 `get(where=..., where_document=..., include=[])` 看命中 ID，再上 query 排序，避免在排序后才发现问题。

两套过滤组合的典型模板（业务查询 90% 落在这三种形态）：**分类 + 关键词**（`where={"category": "docs"}` + `where_document={"$contains": "JVM"}`——最常见，结构化筛选后文本精筛）；**时间范围 + 语义**（`where={"year": {"$gte": 2024}}` + query_texts 语义召回——"最近两年相关资料"）；**多条件或**（`where={"$or": [{"status": "draft"}, {"status": "archived"}]}`——状态白名单）。写组合查询时保持过滤条件"宽进严出"：先放宽 where 确认召回，再逐步收紧到目标选择性，避免一上来就把候选集过滤到空——配合 `n_results` 放大缓冲（如默认 10 调到 30）一起用，是 post-filter 场景保住有效结果的标准姿势。

## 4. 中文全文检索的致命局限

Chroma 本地全文检索底层是 **SQLite FTS5 + trigram tokenizer**，对 CJK（中日韩）文本有三个已知问题：

1. **trigram 要求 ≥3 字符才能匹配**：1-2 字符的中文子串查询（如"缓存"）**静默返回空结果**——不报错，这是最阴险的坑。
2. **unicode61/porter tokenizer 对中文完全失效**：它们按空白分词，而中文无词间空格，整段文本会被当作一个 token，多字符词也匹配不上。
3. **ICU 分词器至今未实现**：社区提案的 CJK 正解（issue #1073）长期未落地。

工程对策三条：**索引前用 jieba 等分词器预分词**（把分词结果写进 metadata 或 document 做预处理）；短模式用 `$regex` 兜底（正则走 LIKE 语义可匹配短串）；需要强中文全文检索就放弃 where_document，改用混合检索的稀疏向量（BM25 视角，见下）或直接选 Qdrant/Elasticsearch。

## 5. 混合检索：稠密 + 稀疏互补

1.x 提供第一等公民的稀疏向量支持（BM25 / SPLADE），与稠密向量配合解决"语义检索丢失关键词精确匹配"的问题：

- **稠密向量**（默认）：语义相近召回，但对专有名词、精确词句不敏感。
- **稀疏向量**（BM25/SPLADE）：关键词精确命中，对语义泛化不敏感。
- **融合**：两种检索结果合并去重（如 RRF 加权），显著提升长尾查询的召回。

写法上在 add 时携带稀疏向量（sparse_embeddings），query 时同样传入：

```python
from chromadb.api.types import SparseEmbeddingFunction   # 稀疏向量函数接口

# 入库：稠密 + 稀疏双向量
collection.upsert(
    ids=["d1"],
    documents=["Chroma 向量数据库选型指南"],
    embeddings=[[0.01, ...]],            # 稠密：语义
    sparse_embeddings={3: 0.8, 45: 0.5, 88: 0.9},  # 稀疏：词项→权重（BM25/SPLADE 输出）
)

# 查询：双路召回由库内融合（如 RRF），无需应用层合并
results = collection.query(
    query_texts=["向量数据库怎么选"],
    query_embeddings=[[...]],
    query_sparse_embeddings=[{7: 0.6, 45: 0.7}],
    n_results=10,
)
```

注意官方口径：Chroma 的混合检索**成熟度不及 Qdrant/Weaviate**——原型可用，生产规模需验证（见 09）。融合算法、权重策略目前可配置面窄，强混合检索诉求优先评估 Qdrant。

## 6. 高级检索能力（1.5.x）

- **GroupBy 查询**：按元数据字段聚合搜索结果，如"按分类统计命中的文档数"——用查询端聚合替代应用层二次处理。
- **Collection Forking**：复制现有集合（含数据与配置）用于 A/B 测试——最典型场景是**对比新旧两个 embedding 模型**的检索质量，对比完删掉分叉集合即可。
- **元数据 Schema 验证**：服务端可开启字段类型校验，写错类型（如把 int 写成 str）直接拒绝——防脏数据进库，替代应用层自检。
- **删除带 limit**（1.5.3）：`delete(where=..., limit=...)` 控制单次删除规模，防大范围误删与长事务。
- **Advanced Search API**：1.5.x 转正出 beta，用于云端更复杂的检索编排。

两个高频能力的真实用法：

```python
# GroupBy：按分类聚合命中结果
groups = collection.query(
    query_texts=["向量数据库选型"],
    n_results=100,
    group_by={"field": "category", "top_k": 5},   # 每分类取前 5
)
# 返回按 category 分组的命中，替代应用层二次聚合

# Collection Forking：对比新旧 embedding 模型（A/B 测试）
new_col = client.create_collection(
    name="kb_v2", configuration={"hnsw": {"space": "cosine"}},
    # fork 参数复制原集合结构与数据
)
new_col.add(ids=old_ids, documents=old_docs, metadatas=old_metas,
            embeddings=new_model_embeddings)      # 同数据换模型入库
# 同一组 query_texts 分别查两个集合，对比命中质量后决定去留
```

Forking 的用法要点：分叉集合独立演进（改数据不影响原集合），对比完直接 `delete_collection` 清理——**验证成本被压到"建集合 + 删集合"两个动作**，这是 06 篇换模型铁律（01 篇提到的维度约束）的配套工具。

> 🎯 **核心要点**：where 管结构化过滤、where_document 管文本过滤、两者隐式 AND；中文全文检索记住"trigram ≥3 字符 + 预分词 + 正则兜底"三件套；混合检索（稠密+稀疏）是 2026 年 RAG 召回质量的关键增量；Forking 让换 embedding 模型的验证成本降为零。
