# 核心概念与数据模型

> Collection → Point → Payload 三级模型 + 命名向量——Qdrant 数据模型的全部，理解后所有 API 行为可推导

## 1. 三级数据模型

**Collection（集合）**是顶层容器，创建时固化三类配置：**向量配置**（维度、距离度量 cosine/dot/l2）、**分片配置**（shard 数、副本因子）、**索引与优化器配置**（HNSW 参数、quantization、segment 优化策略）。

Collection 配置创建后大部分可改（1.18 起命名向量可增删），但**维度与度量变更需要重建**——与 Chroma/PgVector 相同的不可变铁律。

**Point（点）**是最小数据单元，四要素：**Point ID**（u64 数字或 UUID）、**向量**（一个或多个）、**Payload**（自由 JSON）、**版本号**（乐观并发控制用，每次更新递增）。点级操作（upsert/update/delete）全部按 ID 寻址。

**Payload（负载）**是附着在点上的 JSON 元数据——过滤的主战场。

与 Chroma 的 metadata 相比，Qdrant 的 payload 有两个升级：**类型系统**（keyword/integer/float/bool/geo/text/datetime/uuid 八类，见 06 篇）与**惰性索引**（默认存原样 JSON，声明 schema 后才建索引）——"不声明不索引"既是灵活性也是性能陷阱。

## 2. 命名向量：一个点多个向量

Qdrant 最独特的数据模型能力：**一个 Point 可以携带多个命名向量**（named vectors）——稠密向量（dense）、稀疏向量（sparse）、多稠密向量（multi-dense）并存：

| 向量类型 | 用途 | 典型来源 |
|---------|------|---------|
| dense | 语义相似度（默认） | BGE/text-embedding 系列 |
| sparse | 关键词/词项权重 | BM25/SPLADE |
| multi-dense | 分段多向量（晚交互） | ColBERT |

```python
client.create_collection(。
    collection_name="docs",。
    vectors_config={。
        "dense": models.VectorParams(size=768, distance=models.Distance.COSINE),。
        "sparse": models.SparseVectorParams(),。
    },。
)。
# upsert 时同时写两个命名向量
client.upsert(collection_name="docs", points=[。
    models.PointStruct(。
        id=1,。
        vector={。
            "dense": [0.1, 0.2, ...],。
            "sparse": models.SparseVector(indices=[3, 45, 88], values=[0.8, 0.5, 0.9]),。
        },。
        payload={"category": "jvm", "year": 2026},。
    ),。
])。
```

工程含义三条：**多向量是混合检索的同库基础**（一个点同时参与 dense 与 sparse 检索，06 篇细讲）；**ColBERT 晚交互**用 multi-dense 每个 token 一个向量（1.19 的 Turbo4 对这类集合压缩收益最大）；**查询时指定命名向量**（`query_vector=("dense", [...] )`），不指定默认用第一个。

## 3. ID 与版本号

**Point ID 设计**是生产事故高发区：业务主键（如文档 id）直接做 Point ID 是最佳实践——upsert 天然幂等（同 ID 覆盖）、删改按业务键寻址；自增数字 ID 会与向量语义无关地漂移；UUID 适合无业务主键场景。**版本号**（SeqNumber）由服务端维护，写入冲突时客户端可对比版本做乐观并发——多写者场景（任务重跑、并发导入）用它防覆盖错乱。

## 4. Payload Schema：声明即索引

Payload 是自由 JSON，但**检索性能依赖 schema 声明**——Qdrant 的惰性索引：不声明 schema 的字段按原样存储、可过滤但无索引（全段扫描）；声明 schema 后按类型建索引（过滤感知搜索的基数估算依赖它）。建集合时同步声明是生产铁律：

```python
client.create_collection(。
    collection_name="docs",。
    vectors_config=models.VectorParams(size=768, distance=models.Distance.COSINE),。
)。
client.create_payload_index(。
    collection_name="docs",。
    field_name="category",。
    field_schema=models.PayloadSchemaType.KEYWORD,   # keyword: 枚举过滤。
)。
client.create_payload_index(。
    collection_name="docs",。
    field_name="year",。
    field_schema=models.PayloadSchemaType.INTEGER,   # 数值范围过滤。
)。
```

schema 设计三原则：**过滤字段才声明**（索引有内存/磁盘代价，不是越多越好）；**类型与过滤操作符匹配**（text 类型才能用 text 匹配、geo 类型才能用地理位置过滤——类型声明错，操作符不可用）。

**多租户字段用 tenant 类型**（专用物理局域化优化，见 06 篇）。schema 声明是"配置即文档"——把 payload 字段字典（字段名/类型/用途）写进集合注释或迁移脚本，团队协作时少一半排障。

## 5. 与关系型数据库的概念映射

用 SQL 心智迁移：建表 = `create_collection`（向量配置即列定义）；插入 = `upsert`（同 ID 覆盖 = UPSERT 语义）；WHERE 过滤 = `filter`（payload 条件，见 06 篇）。

精确查询 = `retrieve`（按 ID）；相似搜索 = `query`（`nearest` 是核心）。两个与 SQL 直觉的差异：**过滤是"与查询一起下推"而非 WHERE 后过滤**（过滤感知，见 04 篇）。

**点没有固定的"列结构"**——payload 是自由 JSON，不同点可以有不同的 payload 字段（schema 灵活性是特性也是治理成本）。

## 6. Collection 配置全解

创建 Collection 的完整配置项值得逐项过一遍（都是生产决策点）：**vectors_config**（维度/度量/量化——度量与量化创建后部分可改，维度不可变）。

**shard_number**（分片数，创建后不可变——宁多勿少，后面只能重分片不能减）；**replication_factor**（副本数，可调整）；**hnsw_config**（m/ef_construct）。

**optimizers_config**（段合并与索引阈值，04 篇）；**wal_config**（WAL 大小与清理策略）；**on_disk_payload**（payload 是否落盘，默认内存）。

**sparse_vectors_config**（稀疏向量配置）。配置哲学：**创建时保守（分片数宁多勿少）、运行期调优（副本/ef/量化可动）**——创建后不可变的部分（维度/分片数）是唯一需要创建前想清楚的两件事。

## 7. 数据生命周期与命名规范

Collection 命名规范（`[a-zA-Z0-9_-]+`，长度限制 255）。

Collection 数量无硬限制但每个都有索引与优化器开销——**不要为每个业务场景建独立 Collection**（推荐：按向量维度/度量分组，业务区分用 payload 字段，如 `category`），因为每个 Collection 的检索都要独立遍历，Collection 过多会让分片与内存碎片化。

删除 Collection 即删全部数据（快照恢复除外），生产规范要求删除前先做快照。

命名与环境的实践：**环境隔离用 Collection 前缀或独立实例**（`dev_docs` / `prod_docs`——同实例多环境会让分片与备份混乱，优先独立实例）。

**Collection 与 embedding 模型绑定命名**（`docs_bge_m3` / `docs_text_emb3`——换模型 = 新 Collection，命名里带模型名防止"换模型忘换集合"的维度事故）。

**别名（alias）**用于无感切换——新旧 Collection 通过别名切换查询流量，验证后再删旧库（与数据库表的蓝绿切换同思路）。

这套命名规范与 Chroma/PgVector 体系的"模型名入集合 metadata"纪律同源——三个体系对"换模型事故"的防御是同一件事，只是实现载体不同（命名/元数据/注释）。

> 🎯 **核心要点**：三级模型（Collection/Point/Payload）+ 命名向量（dense/sparse/multi-dense）是 Qdrant 数据模型的全部；业务主键做 Point ID 保幂等；payload 声明 schema 才建索引（惰性索引是性能陷阱）；多向量是同库混合检索的地基。
