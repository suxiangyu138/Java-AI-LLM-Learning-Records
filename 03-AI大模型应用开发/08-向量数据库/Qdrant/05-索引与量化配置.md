# 索引与量化配置

> HNSW 参数调优 + 量化全景（scalar/binary/PQ/TurboQuant/Turbo4）+ 两阶段重排 + 内存层级——Qdrant 的性能工程全部

## 1. HNSW 参数与调优

Qdrant 的 HNSW 与 Chroma/PgVector 同源（分层图），参数名与语义一致：

| 参数 | 默认 | 控制阶段 | 调大后果 |
|------|:----:|---------|---------|
| `m` | 16 | 建图 | 召回↑、内存↑、建图慢 |
| `ef_construct` | 100 | 建图 | 索引质量↑、构建慢 |
| `ef` | 100 | 查询 | 召回↑、查询慢（可运行时调） |

调优顺序与 Chroma 体系一致：**召回不足先调 ef**（查询参数，免费）；建图质量不够再动 ef_construct；m 是最后手段（内存代价）。三个注意：**`ef` 是查询参数**（搜索请求里传 `search_params`），不用改集合配置。

**`m` 与内存线性相关**（每节点 m 条链接），大内存账从 m 开始算；**量化与 HNSW 参数是两套独立旋钮**——量化压向量本体、HNSW 参数控图质量，两者配合才是完整调优（先量化再调图，顺序别反）。

## 2. 量化全景：五级压缩

Qdrant 是唯一把量化做成"完整阶梯"的开源向量库（2026 现状）：

| 量化方式 | 压缩比 | 召回 | 典型场景 |
|---------|:------:|:----:|---------|
| 无（float32） | 1× | 100% | 小数据/高召回 |
| scalar（int8） | ~4× | 高 | 通用入门 |
| **TurboQuant** | ~8× | 高（同召回 2× 压缩比） | **生产默认推荐（1.18+）** |
| **Turbo4** | ~9×（4-bit 唯一表示） | 中高 | 存储红线/ColBERT 多向量 |
| binary | 32-40× | 中 | 粗召回层 |

**TurboQuant 原理**（Google Research 方法，Qdrant 2026 落地）：压缩前先对向量做**快速 Hadamard 旋转**（打散方向分布，让各坐标接近独立同分布），再做标量量化——旋转让量化误差均匀化，**同召回下压缩比翻倍**。

Qdrant 实现加了长度归一化、逐坐标校准与 SIMD 加速。**Turbo4（1.19）更进一步**：4-bit 量化作为唯一存储表示（不保留全精度副本），存储减 9 倍、读写吞吐提升——注意它是"存储优先"的取舍，高召回场景不适用。

**两阶段重排**（高召回 + 低内存的标准答案）：量化向量粗召回 top-k（如 100），再从磁盘读全精度向量精排 top-10——90-95% 召回 + 内存压缩 8 倍（与 PgVector 的 binary_quantize 两阶段同构）。

```python
# 查询时启用两阶段：量化粗召回 + 全精度精排
client.query_points(。
    collection_name="docs",。
    query=[0.1, 0.2, ...],。
    limit=10,。
    search_params=models.SearchParams(。
        quantization=models.QuantizationSearchParams(。
            rescore=True,            # 粗召回后全精度重排。
            rescore_limit=100,       # 粗召回候选数（10-20× 目标 topK）。
            oversampling=2.0,        # 量化检索放大采样，弥补量化召回损失。
        ),。
    ),。
)。
```

三个参数的分工：`rescore` 开关精排、`rescore_limit` 控制精排候选量（目标 topK 的 10-20 倍）、`oversampling` 在量化检索时多取候选（量化有损，放大采样补偿）——**两阶段不是"开了就行"，三个参数按召回目标联动调**：召回不足先加 oversampling，再加大 rescore_limit。

## 3. 量化配置实战

```python
client.create_collection(。
    collection_name="docs",。
    vectors_config=models.VectorParams(。
        size=768, distance=models.Distance.COSINE,。
        quantization_config=models.ScalarQuantization(。
            scalar=models.ScalarQuantizationConfig(。
                type=models.ScalarType.INT8,。
                quantile=0.99,          # 裁剪异常值的分位数。
                always_ram=True,        # 量化向量常驻内存。
            ),。
        ),。
    ),。
    hnsw_config=models.HnswConfigDiff(。
        m=16, ef_construct=100,。
        quantization_ignore=True,       # 图遍历时不考虑量化（纯图导航）。
    ),。
)。
```

三个要点：**`quantile` 裁剪极端值**（0.99 忽略 1% 离群值，防量化误差被离群点放大）；**`quantization_ignore` 与 `rescore`**（1.19 起内存层级统一管理）控制两阶段行为；**量化配置可在集合创建后修改**（1.18 起）——先小数据调参再上全量，比创建时拍脑袋可靠。

## 4. Unified Memory Tiers：内存层级

1.19 的统一内存模型，用单一 `memory` 参数替代旧的多组件标志：

| 层级 | 语义 | 适用 |
|------|------|------|
| `pinned` | 常驻 RAM，零加载延迟 | HNSW 图链接、热数据 |
| `cached` | 走 OS 页缓存，按需加载 | 量化向量、稀疏索引 |
| `cold` | 磁盘冷存，访问最慢 | payload 索引、历史数据 |

```python
models.HnswConfigDiff(。
    m=16,。
    memory=models.MemoryConfigDiff(。
        pinned=models.PinnedMemoryConfigDiff(enable=True),   # 图链接常驻。
    ),。
)。
```

工程含义：**内存预算从"一刀切"变成"按组件配"**——大规模部署的典型组合是"图 pinned + 向量 cached + payload cold"，内存与延迟的每个百分比都可控。内存监控（1.18 Web UI/API）按组件（向量/payload/索引）分解显示磁盘、RAM、页缓存占用——调内存层级前先看监控，别猜。

## 5. 量化选择决策树

量化方式怎么选，按三条问题对号入座：

```text
召回要求 99%+？ → 否：TurboQuant 起步（8×，生产默认）
                 是：内存够？ → 是：不量化（全精度）
                              否：TurboQuant + 两阶段重排（粗召回 + 精排）
存储/磁盘是红线？ → 是：Turbo4（9×+，接受召回牺牲）或 binary（粗召回层）
ColBERT 多向量？ → 是：Turbo4 收益最大（多向量压缩比例更高）
```

决策依据不是"量化越好"，而是**召回目标 × 内存预算的交叉**：RAG 场景召回 95-98% 就够（TurboQuant 无压力）；检索严格场景（合规/金融）要 99.5%+（两阶段重排）；演示项目直接全精度（省事）。

量化变更的成本与收益要量化评估：**先跑量化前后同一批标注集的召回对比**（命中率 + MRR，方法论见 08 篇）——量化不是拍脑袋的省钱手段，是"召回预算换内存预算"的工程决策。

## 6. 调优决策树与内存预算

1. **召回不足** → 调查询 `ef`（100 → 200）→ 仍不足重建索引调 `ef_construct`/`m`。
2. **内存超标** → 先 TurboQuant（8×）→ 仍超标 Turbo4（9×+）或降级 cached/cold 层级 → 都到顶再考虑换节点/分布式。
3. **查询慢** → 降 `ef`、加缓存层级、检查段数（optimizer 是否合并到位）。
4. **写入慢** → 关掉不必要的实时索引、批量 upsert（万级/批）、调 optimizer 阈值。

内存预算公式（无量化）：`向量本体 + HNSW 图（约本体 30-50%）+ payload 索引` ≈ **原始向量 × 1.5-2**；TurboQuant 后压到约 0.2-0.3×；Turbo4 更低。

示例：1M × 768 维 float32（3GB）→ 无量化 4.5-6GB、TurboQuant 约 1GB——**量化是 Qdrant 规模心智的起点，不是终点**（配合 07 篇分布式继续扩展）。

调优的工程节奏建议：**先量化后调图**（量化把内存打下来，HNSW 参数在缩小的内存空间里调召回）；**每轮只动一个变量**（ef 或量化或 m，别同时动——指标回归没法归因）；**用标注集验证每轮**（命中率 + MRR 对比，08 篇评估脚本）——调参是工程实验不是手感，指标说话才可回归。

与 Chroma/PgVector 体系的调优方法论对照：三套体系的 HNSW 参数同源（ef/ef_search 都是查询级旋钮）、量化思路同构（先压缩再精排）——**学会一套，另两套的文档读起来全是熟面孔**，这是向量库知识的可迁移性。

> 🎯 **核心要点**：调优顺序 ef → ef_construct → m，先量化再调图；量化五级阶梯（scalar/TurboQuant/Turbo4/binary）里 TurboQuant 是 2026 生产默认；两阶段重排（量化粗召回 + 全精度精排）保召回；Unified Memory Tiers（pinned/cached/cold）让内存按组件精细控制；内存预算从 1.5-2× 原始向量起算，量化后指数下降。
