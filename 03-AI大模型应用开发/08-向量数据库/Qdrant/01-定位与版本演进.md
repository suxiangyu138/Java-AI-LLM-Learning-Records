# 定位与版本演进

> 先回答三个问题：Qdrant 在向量数据库谱系里站在哪？2026 年三个版本各自带来了什么？它与 Chroma/PgVector 的本质差异是什么？

## 1. 在向量数据库谱系中的位置

Qdrant 是 Rust 编写的开源向量数据库，交付形态是**单个二进制**——同一个二进制既能以单机模式运行，也能组成分布式集群（Raft 元数据共识 + 自定义分片复制层）。API 双通道：REST（6333 端口）与 gRPC（6334 端口），Python/Java/Go/JS 客户端齐全。

与同级竞品对照，它的定位落在"中间段"：比 Chroma（嵌入式、<2M 规模）更重——是独立服务；比 Milvus（K8s 全家桶、十亿级）更轻——单二进制可跑 Docker 也能上集群。这个"中间段"恰好是生产级 RAG 的主战场：**要规模与专业能力，又不想背运维包袱**。

| 维度 | Qdrant 的立场 |
|------|--------------|
| 部署 | 单二进制，Docker 一条命令；集群同一二进制 |
| 规模 | 单机百万级、集群亿级（分片水平扩展） |
| 过滤 | **过滤感知搜索**（过滤融入图遍历，非事后） |
| 量化 | 全套：scalar/binary/PQ/TurboQuant/Turbo4 |
| 协议 | Apache 2.0（开源版），Cloud 收费 |

## 2. 版本演进：2026 年的三次跃迁

| 版本 | 时间 | 核心变化 |
|------|:----:|---------|
| 1.10-1.15 | 2024-2025 | 命名向量、gRPC 完善、稳定演进 |
| **1.17** | **2026-02-20** | **Relevance Feedback 查询（相关性反馈）、更新队列（背压控制）、延迟 fan-out（副本兜底尾延迟）、集群级遥测 API** |
| **1.18** | **2026-05-11** | **TurboQuant 量化（Hadamard 旋转，2× 压缩比）、内存监控 Web UI、命名向量增删、审计日志 API、严格模式** |
| **1.19** | **2026** | **Turbo4（4-bit 唯一存储表示，存储减 9 倍）、Unified Memory Tiers（pinned/cached/cold 统一内存层级）、Per-Tenant IDF、前缀匹配过滤、slice 过滤、io_uring 存储** |

版本节奏稳定（季度大版本），升级成本低（单二进制替换 + 快照回滚）。三条演进主线值得提炼：**压缩**（量化从 scalar → TurboQuant → Turbo4 一路压存储）、**可观测**（遥测 API → 内存监控 → 审计日志，云原生必备）、**检索质量**（Relevance Feedback → Per-Tenant IDF，让检索更懂业务）。

## 3. 2026 新特性的工程含义

**TurboQuant（1.18）**：Google Research 提出的量化方法——压缩前先做快速 Hadamard 旋转打散向量方向分布，再用标量量化，**同召回下压缩比翻倍**（scalar 4× → TurboQuant 8×）；Qdrant 实现加了长度归一化、逐坐标校准、SIMD 加速，支持 cosine/dot/l2 三种度量。工程含义：内存预算直接砍半，50M 向量从"不敢想"变成"可评估"。

**Turbo4（1.19）**：4-bit 量化作为**唯一存储表示**（不再保留全精度副本）——存储减 9 倍，读写吞吐提升；对 ColBERT 多向量集合收益更大。注意取舍：Turbo4 适合"召回要求中等 + 内存红线"场景，高召回场景仍走两阶段（量化粗召回 + 全精度精排，见 05 篇）。

**Relevance Feedback（1.17）**：用轻量模型对 top 结果生成反馈（"更像/更不像"）微调查询——**不重训模型、不需要人工标注**，在十亿级向量上直接提升召回。工程含义：RAG 的检索质量优化从"换模型/调参"扩展到"反馈回路"，是 2026 年检索增强的新方向（详见 06 篇）。

## 4. Cloud 企业能力（2026-04-28）

Qdrant Cloud Enterprise 三件套：**GPU 索引**——NVIDIA T4 上 HNSW 构建快 4 倍（高写入场景关键，AWS 集群可用）；**Multi-AZ**——三可用区复制，Premium Multi-AZ 档 99.95% SLA（Standard 99.5%、Premium 99.9%）；**审计日志**——全部 API 操作（查询/upsert/删除/集合管理/快照）输出结构化 JSON，带用户/API key 归属、时间戳、授权结果，可经 API 接入 SIEM。

选型意义：开源版覆盖"能跑"，Cloud 覆盖"合规与可用性"（审计、多 AZ、GPU）——国内合规敏感场景注意数据出域问题，优先私有化部署（详见 07 篇）。

## 5. 生态与部署形态

Qdrant 的生态成熟度是选型的重要筹码：**客户端**——官方 Python/Java/Go/JS/Rust 客户端齐全（gRPC 为主、REST 兜底）；**框架**——LangChain/LlamaIndex/Spring AI/LangChain4j 全部官方支持；**周边**——FastEmbed（自家本地 embedding 库）、Web UI（集合可视化、重分片进度、内存监控）、官方 Helm chart 与 Docker 镜像。部署形态四档：**Embedded 模式**（1.x 起的进程内嵌入能力，原型用）、**单机 Docker**（开发与小型生产）、**集群**（同一二进制组 Raft 集群）、**Qdrant Cloud**（托管：Serverless/企业）。注意与 Chroma 的"嵌入式"区分——Qdrant 的 Embedded 是**进程内嵌入库**（Rust 核心 FFI），但它本质仍是"服务化设计"，多进程并发写仍建议独立服务。

命名澄清：**Qdrant 与 Qdrant Cloud 是同一个产品线的开源版与托管版**（不像 Milvus 有 Zilliz 的复杂关系）；开源版 Apache 2.0，无内置认证（安全靠网络层，见 07 篇）；Cloud 收费层买的是 SLA、审计与 GPU——"开源版能力不缩水、Cloud 卖运维与合规"是它的商业模型。

## 6. 与 Chroma / PgVector 的本质差异

三者选型不纠结的核心判断：**Chroma 是嵌入式（客户端即服务）**，适合原型与 <2M 单机；**PgVector 是 PG 扩展**，适合"已有 PG 且过滤简单"；**Qdrant 是独立服务向量库**，适合"过滤是核心模式 + 规模持续增长"。Qdrant 相对前两者的两个不可替代点：**过滤感知搜索**（Chroma/PgVector 都是 post-filter，过滤选择性高就吞结果）与**完整的量化体系**（Chroma 无量化、PgVector 的 binary_quantize 只是单点工具）——这两点正是"生产级 RAG 检索质量"的胜负手（详见 09 篇对比）。与同目录 Milvus 体系的分工：Milvus 是百亿级与湖仓原生场景，Qdrant 是"亿级以内的独立服务"甜区——两者在 100M 上下交界，选型看增长预期与运维能力（09 篇决策树）。

> 🎯 **核心要点**：Qdrant = "中间段的生产级向量库"——单二进制、过滤感知、量化全家桶；2026 年三条演进主线是压缩（Turbo4 减 9 倍）、可观测（审计/遥测/内存监控）、检索质量（反馈/Per-Tenant IDF）；与 Chroma/PgVector 的本质差异是过滤感知搜索，这是选型与面试的锚点。
