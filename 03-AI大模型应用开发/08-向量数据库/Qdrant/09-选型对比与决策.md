# 选型对比与决策

> Qdrant vs Chroma / PgVector / Milvus / Weaviate——过滤感知是差异化王牌，规模与成本的权衡，最终落到决策树

## 1. 竞品全景与定位差异

四象限回顾（与 Chroma/PgVector 体系一致）：**嵌入式**（Chroma）、**PG 扩展**（PgVector）、**独立服务向量库**（Qdrant、Milvus、Weaviate）。Qdrant 站在"独立服务"象限的中间段——比 Chroma 重（是服务）、比 Milvus 轻（单二进制）。

| 维度 | Qdrant 1.19 | Chroma 1.5.x | PgVector 0.8.x | Milvus 3.0 |
|------|------------|-------------|----------------|-----------|
| 形态 | Rust 单二进制服务 | 嵌入式 | PG 扩展 | 分布式集群 |
| 部署成本 | 低（Docker/单二进制） | 零（pip） | 零（已有 PG） | 高（K8s） |
| 规模 | 单机百万 / 集群亿级 | 1-2M | 50M-100M | 十亿级 |
| 过滤 | **过滤感知（不吞召回）** | post-filter | post-filter（0.8 缓解） | pre-filter 强 |
| 量化 | **五级阶梯（TurboQuant/Turbo4）** | 无 | binary_quantize/halfvec | SQ8/GPQ |
| 混合检索 | 库内原生（RRF 算子） | BM25/SPLADE（较新） | FTS+RRF（SQL 融合） | 原生成熟 |
| 多租户 | **tenant 索引一等公民** | 无 | RLS（应用层） | partition_key |
| 分布式 | Raft + 分片副本（同二进制） | 无 | 随 PG 复制 | 完整组件化 |
| Java 生态 | 官方客户端/LangChain4j/Spring AI | Spring AI | Spring AI | Spring AI |

## 2. 逐个竞品的取舍分析

**vs Chroma**：Chroma 的嵌入式优势（零部署、进程内）在原型与小数据（<1M）场景不可替代。

但 Qdrant 在三个维度全面超越：**过滤感知**（Chroma post-filter 吞结果）、**量化**（Chroma 无量化，内存成本线性）、**规模**（Chroma 1-2M 封顶，Qdrant 集群亿级）。

判断：**原型实验用 Chroma，转生产且要过滤/规模 → Qdrant**——升级路径平滑（数据重放，见 10 篇 Q9）。

**vs PgVector**：PgVector 的"已有 PG 零新增"红利在简单过滤、<50M 规模场景不可替代。

但 PgVector 的 post-filter（iterative scans 只是缓解）与 SQL 融合的混合检索（两路查询应用层融合）在**强过滤 + 混合检索 + 多租户**三要素齐备时让位 Qdrant。

判断口诀：**过滤是核心模式或要原生多租户 → Qdrant；已有 PG 且过滤简单 → PgVector 够用**。

**vs Milvus**：Milvus 是十亿级与分布式企业能力（RBAC、监控全家桶、3.0 Lake-Native）的答案，代价是运维复杂度两个量级。Qdrant 在**亿级以内**是更务实的中间解——同二进制单机可起、集群可扩，运维心智低一个量级。判断：**10M-100M 且要分布式 → Qdrant；百亿级/湖仓集成 → Milvus**。

**vs Weaviate**：同为 Rust/Go 生态的独立向量库，Weaviate 强在图检索（GraphQL 原生）、混合检索成熟、模块化（向量化模块内置）；Qdrant 强在**过滤性能与量化体系**（TurboQuant 是 2026 独有）、更纯粹（不做内置向量化，专注检索）。判断：**需要图查询或内置向量化管道 → Weaviate；需要极致过滤与量化 → Qdrant**。

## 3. Qdrant 的甜区与红线

**甜区（选它没错）**：过滤是核心查询模式（RAG 按分类/时间/租户过滤）；规模从百万到亿级且要平滑扩展；多租户是硬需求（tenant 索引）；内存敏感（量化体系完整）；团队要"单二进制起服务"的部署心智。

**红线（别选它）**：数据 <100 万且零部署诉求（Chroma 更轻）；已有 PG 且过滤简单（PgVector 白赚事务）；十亿级以上或要湖仓原生（Milvus）；需要图结构检索（Weaviate/Neo4j）。

## 4. 三个典型选型场景（推演）

**场景 A：已有 PG 的商品搜索加语义**。数据千万级、过滤是分类枚举、事务与 JOIN 是刚需。PgVector 是默认答案——白赚 SQL/事务/备份；除非过滤条件动态复杂（Qdrant 的过滤感知才值得引入第二个服务）。

**场景 B：多租户 SaaS 知识库（强过滤）**。每个租户过滤自己的数据 + 分类/时间组合过滤 + 规模持续增长。**Qdrant 是最佳答案**——tenant 索引物理局域化、过滤感知不吞召回、分片副本随租户量扩展；Chroma/PgVector 的多租户都要应用层造轮子且过滤会吞结果。

**场景 C：企业 RAG 平台（亿级文档、多团队）**。需要分布式、审计、SLA，团队有 K8s 运维能力。**Qdrant 集群（或 Cloud Premium）是甜区**——单二进制集群 + 量化 + 快照；百亿级预期则直接 Milvus。

## 5. 成本账：机器、运维与迁移

选型不止比能力，还要算三本账。

**机器账**：Qdrant 单节点内存 ≈ 向量 × 1.5-2，量化后骤降（1M × 768 维从 4.5-6GB 到约 1GB）。量化的机器成本收益是"先于选型"的决策——先量化再评估要不要换库。

**运维账**：Qdrant 单二进制的运维成本（Docker/Helm 一条命令）显著低于 Milvus（K8s 全家桶），但高于 Chroma（零部署）与 PgVector（复用 PG 运维）——"多一个服务的月成本"要用业务价值对冲。

**迁移账**：换库成本 = 数据重放（同向量重写入新库）+ 业务代码改动（Spring AI VectorStore 抽象下趋近于零）+ 双跑验证期。迁移账最小的是"一开始就选对"（ADR + 触发条件，见第 6 节）。

## 6. 选型决策树

```text
数据 <1M 且零部署诉求？ → 是：Chroma
已有 PostgreSQL？ → 是：过滤简单且 <50M？ → 是：PgVector
                             过滤复杂/多租户？ → 跳到 Qdrant
需要分布式与过滤感知？
├── 否（单机够用）→ Qdrant 单机
├── 是 → 预期 <100M？ → Qdrant 集群
│        → 百亿级/湖仓？ → Milvus
```

决策树之外三条纪律：**选型写 ADR**（背景/备选/决策/触发条件/回滚路径——与 PgVector 体系 09 篇同款）；**用 Spring AI VectorStore 抽象保留换库路径**；**先量化再扩容**（50M 边缘先 TurboQuant 再考虑加节点）。

执行纪律：决策树的输出是"选型 + 边界 + 触发信号"三件套（缺一不可），触发信号要写成可观测指标（数据量预测、过滤查询占比、P95 阈值）——指标破线就启动评审，而不是等故障驱动选型复盘。

决策树本身也要进版本管理（docs/adr/），六个月的选型复盘回头看，当时的分界线（如"50M"）是否还成立——**选型是过程不是结论**。

> 🎯 **核心要点**：Qdrant 的甜区 = "过滤是核心模式 + 规模持续增长 + 要原生多租户"；vs Chroma（原型转生产）、vs PgVector（过滤复杂）、vs Milvus（亿级中间解）三个分界线是选型锚点；决策树 + ADR + VectorStore 抽象三件套让选型可回滚、可复盘。
