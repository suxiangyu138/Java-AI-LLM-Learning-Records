# 快速开始与客户端

> Docker 一条命令起服务，Python 客户端跑通 CRUD 全流程，Java 客户端与 REST/gRPC 直调备选——最小闭环一篇打通

## 1. Docker 启动与端口

```bash
docker run -d -p 6333:6333 -p 6334:6334 \
  -v $(pwd)/qdrant_storage:/qdrant/storage \
  --name qdrant qdrant/qdrant:v1.19.0
```

两个端口的分工：**6333 = REST API**（HTTP，调试与语言客户端内部转换用）、**6334 = gRPC API**（官方客户端默认走 gRPC，性能更好）。持久卷必须挂 `/qdrant/storage`（镜像内默认路径），不挂卷容器重建即丢数据——与 Chroma/PgVector 相同的部署红线。健康检查：`GET /healthz`（返回 `{"status":"ok"}`）或 `GET /livez`；版本确认 `GET /` 的 `version` 字段。

## 2. Python 客户端 CRUD 全流程

```bash
pip install qdrant-client
```

```python
from qdrant_client import QdrantClient, models

client = QdrantClient(host="localhost", port=6333)
# 或云端/HTTPS：QdrantClient(url="https://xxx.qdrant.io", api_key="...")

# 1. 建集合：维度 + 度量 + 分片
client.create_collection(
    collection_name="docs",
    vectors_config=models.VectorParams(size=768, distance=models.Distance.COSINE),
    shard_number=2,              # 分片数（集群水平扩展）
)

# 2. 写：upsert（同 ID 覆盖 = 幂等）
client.upsert(collection_name="docs", points=[
    models.PointStruct(
        id=1,                    # 业务主键直接用
        vector=[0.1, 0.2, ...],
        payload={"title": "JVM 内存模型", "category": "jvm", "year": 2026},
    ),
])

# 3. 查：相似搜索 + 过滤 + topK
hits = client.query_points(
    collection_name="docs",
    query=[0.1, 0.2, ...],
    query_filter=models.Filter(
        must=[models.FieldCondition(key="category", match=models.MatchValue(value="jvm"))],
    ),
    limit=10,
).points
for h in hits:
    print(h.id, h.score, h.payload["title"])
```

写操作三兄弟的语义：**upsert**（存在覆盖、不存在插入，幂等首选）、**update**（按 ID 定点更新，可只更 payload 或只更向量）、**delete**（按 ID 或按 filter 删）。注意 filter 删除（`delete(collection_name, points_selector=models.FilterSelector(...))`）是批量清理利器——先 filter 检索验证命中再删，防误删（Qdrant 没有"回收站"，删了只能靠快照恢复）。

批处理与工程习惯：**批量 upsert 用 `client.upsert(points=[...])` 传列表**（客户端自动分批，默认 64/批，可调 `batch_size`）——逐条 upsert 会放大网络往返，万级数据差一个量级；**幂等重跑靠"业务主键做 ID"**（同 ID 覆盖，重跑任务不产生重复点）；**读多写少场景复用客户端实例**（QdrantClient 是重量级对象，连接池复用，不要在每次请求里重建）；**写入节奏**：批量 + 批间小间隔，配合 optimizer 的异步合并，避免瞬时写入风暴拖慢查询。

## 3. 检索结果与分数语义

`query_points` 返回的每个点带 `score`：**cosine 度量下 score 越大越相似**（cosine 相似度，范围 [-1,1]）；**l2 度量下 score 是距离越小越近**（Qdrant 内部统一转成"越大越好"的分数——l2 的 score 显示为 `1/(1+distance)` 形式）；**dot 度量下越大越近**。三个度量的 score 语义不同，**阈值（score_threshold）要按度量换算**——这是跨度量应用最常写错的地方（cosine 阈值 0.7 与 l2 的 0.7 完全不是一回事）。

## 4. 查询全形态

`query_points` 是统一入口，query 参数决定检索形态——五种高频形态：

```python
# 1. 纯向量最近邻（最基础）
client.query_points(collection_name="docs", query=[0.1, 0.2, ...], limit=10)

# 2. 向量 + 过滤（过滤感知搜索，04 篇原理）
client.query_points(collection_name="docs", query=[...],
                    query_filter=models.Filter(must=[...]), limit=10)

# 3. 指定命名向量（多向量集合必须指定）
client.query_points(collection_name="docs", query=models.NearestQuery(
    nearest=models.DenseVector([...]), using="dense"), limit=10)

# 4. 按 ID 查询向量（"相似于这条"的语义）
client.query_points(collection_name="docs", query=models.NearestQuery(
    nearest=42), limit=10)              # 用点 ID 作为查询向量源

# 5. 多路 prefetch + 融合（混合检索，06 篇细讲）
client.query_points(collection_name="docs",
                    prefetch=[...], query=models.FusionQuery(fusion=models.Fusion.RRF), limit=10)
```

每种形态都支持 `score_threshold`（分数下限过滤）与 `search_params`（ef 等查询参数）。**查询语义的完整矩阵**：向量查询（query=向量）、ID 查询（query=点 ID）、文本查询（query=文本 + 内置 embedding 函数，需配置 FastEmbed/OpenAI）、融合查询（FusionQuery）、分组查询（group_by）——五种形态覆盖 RAG 与业务检索的全部入口。

## 5. Java 客户端与 REST 直调

**Java 官方客户端**（gRPC 实现）：

```xml
<dependency>
    <groupId>io.qdrant</groupId>
    <artifactId>client</artifactId>
    <version>1.15.0</version>
</dependency>
```

```java
QdrantClient client = QdrantGrpcClient.newBuilder("localhost", 6334, false).build();
// 建集合 + upsert + 搜索（异步 API：createCollectionAsync/upsertAsync/queryAsync）
client.upsertAsync(UpsertPoints.newBuilder()
        .setCollectionName("docs")
        .addPoints(PointStruct.newBuilder()
                .setId(1)
                .addVectors(Vector.newBuilder().addAllData(List.of(0.1f, 0.2f)))
                .build())
        .build()).get();
```

Java 客户端的使用要点：**API 全是异步风格**（`xxxAsync(...)` 返回 CompletableFuture，阻塞场景 `.get()` 取值，高吞吐场景回调/组合）——官方客户端面向 gRPC 的背压设计，同步包装层只是便利；**超时与重试自己管**（客户端不默认重试，生产封装重试 + 指数退避，注意写操作重试要幂等——Qdrant 的 upsert 天然幂等，安全）；**TLS 与认证**：`QdrantGrpcClient.newBuilder(host, port, useTls)` + `apiKey` 配置，连 Qdrant Cloud 必须开 TLS 与 key。

**REST 直调**（非官方客户端场景/调试）：`POST /collections/{name}/points` 建集合、`PUT /collections/{name}/points` upsert、`POST /collections/{name}/points/query` 搜索——curl 一把梭调试（如 `curl -s localhost:6333/collections` 列集合）。REST 与 gRPC 的能力完全对等（同一 API 面），性能敏感场景优先 gRPC（协议开销更小、流式支持更好）。

## 6. Web UI：可视化运维入口

Qdrant 自带 Web UI（默认端口 6333 的 `/dashboard`），四个高频用途：**集合可视化器**——直观浏览集合/分片/段的状态与数据分布（1.19 起支持数万点的规模）；**重分片进度**——扩容时实时查看分片迁移进度（比盯日志强一个量级）；**payload 索引管理**——可视化创建/删除 payload 索引（替代记 API）；**内存监控**（1.18）——按组件（向量/payload/索引）分解的 RAM/磁盘/页缓存占用面板。Web UI 是"入门友好 + 运维兜底"的双重入口——**线上操作仍以 API/客户端为准**（UI 适合观察与排查，不适合批量操作脚本化）。

## 7. 快速排错四板斧

- **维度不匹配**：upsert 报 "wrong number of coordinates"——核对模型输出维度与集合配置（768/1024/1536 是高频值）。
- **集合不存在**：REST 404 / gRPC NOT_FOUND——确认 collection_name 大小写与命名规范。
- **过滤不生效**：返回结果与 filter 不符——检查 payload 字段是否声明了索引（未索引字段也能过滤但慢，且部分操作符不可用，见 06 篇）。
- **连接被拒**：6333/6334 端口混淆、Docker 未映射端口、云实例的 api_key 缺失——三种情况按报错信息区分。
- **配置核对**：集合维度/度量/分片数用 `GET /collections/{name}` 核对（返回完整配置），与客户端配置比对——建集合时拍脑袋的参数，排查时在这里现形。

排错的心智模型：**报错信息分层定位**——连接层（端口/TLS/key）→ 集合层（存在性/命名）→ 数据层（维度/ID）→ 检索层（过滤/度量）——从下往上按层排查，比乱试快一个量级。官方文档的 `GET /collections` 与 `/cluster` 端点随时可查全局状态，先看全局再钻细节。

客户端选型的一句话总结：**原型用 Python**（表达式最直接）、**生产 Java**（gRPC 性能 + 类型安全）、**调试 REST**（curl 可视化）——三种入口覆盖"探索 → 交付 → 排查"全生命周期，它们操作的是同一个 API 面，技能互不浪费。语言客户端能力对等（Python/Java/Go/JS 都是官方维护、覆盖全部 API）——选型只看出身团队的语言栈，不必为能力差异纠结。客户端的健康度检查随手可用：`client.get_collections()` 列全集合即证明"连接 + 认证 + 集合三层通"——一条命令完成环境连通性验证，比逐层排查省一半时间。

> 🎯 **核心要点**：6333 REST / 6334 gRPC + 持久卷是部署铁律；upsert 幂等 + 业务主键做 ID 是写路径标配；score 语义随度量不同（cosine 越大越近、l2 是距离变形），阈值按度量换算；filter 删除先检索验证再删。
