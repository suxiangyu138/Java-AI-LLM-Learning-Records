# 存储架构与检索原理

> Collection → Shard → Segment 三级存储 + WAL 写路径 + 过滤感知搜索——看懂这一篇，Qdrant 的性能特性全部可推导

## 1. 存储层级：Collection → Shard → Segment

Qdrant 的存储组织是三层树：**Collection** 水平切分为若干 **Shard**（分片），每个 Shard 内部由若干 **Segment**（段）组成。

| 层级 | 职责 | 关键属性 |
|------|------|---------|
| Collection | 顶层容器 | 向量配置、分片数、副本数 |
| Shard | 数据水平分区（按 ID 哈希） | 创建时定分片数，终身不变 |
| Segment | 分片内存储单元 | appendable（可写）/ optimized（只读） |

**Segment 是理解 Qdrant 写入模型的关键**：新数据先进入可写段（appendable），查询时所有段并集扫描。

后台 **optimizer（优化器）**把可写段合并/重排为只读的优化段（optimized，向量按内存布局紧凑化）——这就是"日志结构化 + 后台 compaction"的 Qdrant 版。工程含义三条：**写入不阻塞查询**（分段隔离，索引更新无锁）。

**删除是标记删除**（段内 tombstone，物理回收在 compaction）；**查询延迟包含"段数开销"**——段过多时查询变慢，optimizer 会合并段治理。

optimizer 的行为由集合配置的 `optimizers_config` 控制：`default_segment_number`（合并目标段数）、`memmap_threshold`（段大小超阈值转 mmap）、`indexing_threshold`（段内点数超阈值建索引）——**高写入场景的调优旋钮**：写入风暴时临时调高 `indexing_threshold` 减少频繁建索引、低峰再恢复。

生产监控把"段数/集合"纳入指标：段数持续上涨说明 optimizer 跟不上写入速度（写入 > 合并能力），需要调参或扩节点——**段数是 Qdrant 写入压力的晴雨表**。

## 2. WAL 写路径与数据一致性

每次写入（upsert/update/delete）的完整路径：

1. **写 WAL**（RecoverableWal）：操作先落日志，获得全局递增的**序号**（作为点的版本号）——持久性由 WAL 保证。
2. **应用更新**：UpdateHandler 异步把操作应用到 SegmentHolder；每个段检查操作序号与自身版本——**旧序号自动跳过**（幂等重放安全）。
3. **复制**（分布式）：主副本先写 WAL 再同步到跟随副本，写确认后返回客户端。

与 Chroma/PgVector 的 WAL 语义一致（写先落日志、后台物化），但 Qdrant 有两处升级：**序号即版本**（乐观并发控制天然集成，冲突检测免费）；**重放幂等**（崩溃恢复、分片迁移、副本追赶都靠序号跳过旧操作）——崩溃安全、迁移安全、扩容安全三个场景共用同一机制。

## 3. 过滤感知搜索：Qdrant 的灵魂

这是与 Chroma/PgVector（post-filter）最本质的差异，必须讲透原理。当查询带 filter 时，Qdrant 的搜索路径分两步：

1. **基数估算**：先查 payload 索引，估算过滤条件的命中基数（有多少点满足过滤）。
2. **路径选择**：
   - 过滤选择性低（命中点多）→ **约束 HNSW 遍历**：图搜索时跳过不满足过滤的邻居节点，直接在"过滤后的图上"做 ANN——召回不丢、延迟与无过滤时接近。
   - 过滤选择性高（命中点极少）→ **精确扫描**：过滤条件能把候选集压到很小，直接对命中子集暴力排序（比走图更快、且 100% 精确）。

```text
post-filter（Chroma/PgVector）：HNSW 召回 top-k → 再套过滤 → 选择性高时结果被吞
filter-aware（Qdrant）：       估算基数 → 约束图遍历 或 精确子集扫描 → 延迟可预测
```

工程含义：**"过滤是核心查询模式"的场景，Qdrant 的召回不随过滤选择性衰减**——这是 09 篇选型对比里 Qdrant 相对 Chroma/PgVector 最硬的论据。

代价与注意：过滤感知要求 **payload 字段建索引**（不建索引的字段无法参与基数估算，退化为事后过滤）；过滤条件复杂度与索引选择有关（见 06 篇）。

**基数估算本身有成本**——极高频查询（百万 QPS 级）中估算开销占比上升，但这种规模下 Qdrant 早已是集群形态，权衡交给实测。

## 4. 索引结构与内存布局

**HNSW** 是主索引（内存常驻的分层图）：参数 `m`（节点最大连接数）、`ef_construct`（建图候选）、`ef`（查询候选，可运行时调）。搜索从顶层贪婪下钻到底层 beam search。量化后（scalar/binary/TurboQuant，见 05 篇）向量本体可压缩存储，HNSW 图链接仍常驻内存。

内存布局（1.19 的 **Unified Memory Tiers** 统一管理）：每个组件（向量本体/图链接/量化向量/payload 索引）可以独立指定 **pinned（常驻内存）/ cached（页缓存）/ cold（磁盘）**——替代旧的 on_disk/always_ram 碎片化配置。

工程含义：**量化 + 内存层级 = 内存预算的精细控制**（图链接 pinned、量化向量 cached、payload 索引 cold），大规模部署的内存账从这里算。

## 5. 查询引擎与多向量

查询执行是**操作符管道**（与 Chroma 的 QueryService 同思路）：query 可以是向量最近邻、过滤+最近邻、多路融合（dense+sparse，见 06 篇）、分组查询（group by payload 字段）等——管道把查询分解为可组合步骤，这也是 1.17 Relevance Feedback（反馈环进入管道）能实现的架构基础。

多向量（ColBERT 晚交互）走 multi-dense 专用路径：逐段相似度 + MaxSim 聚合，1.19 的 Turbo4 对这类集合压缩收益最大。

## 6. 规模心智

资源经验公式（官方建议）：**内存 ≈ 原始向量大小 × 1.5-2**（向量本体 + HNSW 图 + payload 索引）；磁盘 ≈ 内存 + WAL + 段冗余（追加式写入的段冗余约 10-20%）。

示例：100 万条 768 维 float32（约 3GB）→ 内存预算 4.5-6GB。

量化介入后（TurboQuant 8×）内存可压到 1GB 内——**"先量化再评估规模"是 Qdrant 的心智模型**（与 PgVector 体系的"先量化再换库"同构）。

> 🎯 **核心要点**：三级存储（Collection/Shard/Segment）+ WAL 序号版本是 Qdrant 的架构骨架；**过滤感知搜索**（基数估算 → 约束遍历/精确扫描）是灵魂，过滤不吞召回、延迟可预测；Unified Memory Tiers 让内存精细控制；资源账 = 1.5-2× 原始向量大小，量化后指数级下降。
