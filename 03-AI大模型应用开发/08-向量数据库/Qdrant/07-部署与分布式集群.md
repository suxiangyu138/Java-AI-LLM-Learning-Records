# 部署与分布式集群

> 单机 Docker/K8s → 分布式集群（Raft + 分片 + 副本）→ 扩缩容与监控备份 → Qdrant Cloud——生产部署全路径

## 1. 单机部署：Docker 与 K8s

单机部署（03 篇的 Docker 命令）之外，生产环境三条增强：**资源限制**（容器内存按 1.5-2× 向量大小预算，见 05 篇；CPU 限制防 optimizer 挤占查询）。

**持久卷**（`/qdrant/storage` 挂云盘，SSD 是 HNSW 冷数据读取的关键）；**探活**（`/healthz` 做 readiness、`/livez` 做 liveness，与 Chroma 体系的探针分工一致）。

K8s 部署用官方 Helm chart（`qdrant/qdrant`）：StatefulSet + PVC + Service 一条命令起。

生产模板至少改三处——**PVC 保留策略 Retain**（默认 Delete 卸载即删数据，与 PgVector 体系的 Helm 坑同源）、**资源 requests/limits 显式设置**、**副本数 ≥ 2 时配置集群模式**（单副本的 K8s 部署只是"跑在容器里的单机"，不自动获得分布式能力）。

## 2. 分布式集群架构

Qdrant 集群 = 多个对等节点（peer），两个协议分工：

| 协议层 | 负责 | 关键行为 |
|--------|------|---------|
| **Raft** | 集群元数据共识 | 节点成员、分片分配、副本拓扑——元数据强一致 |
| **自定义复制层** | 点级数据 | 分片主副本写、跟随副本异步追、读任一副本 |

**分片（sharding）**：Collection 数据按点 ID 一致哈希分布到各节点（分片数创建时定，查询吞吐随节点数近线性扩展）。**副本（replication）**：每个分片在多个节点上保存副本（副本因子决定冗余度），**写同步跨副本确认**（主写 + 跟随确认），读可任一副本——分片给容量、副本给可用性，两者组合才是生产级。

```text
集群拓扑示例（3 节点，Collection 分片 4、副本 2）：
节点 A: shard0(主) shard1(主) shard2(副)
节点 B: shard2(主) shard3(主) shard0(副)
节点 C: shard1(副) shard3(副)
任一节点挂 → 对应分片副提升为主，集群继续服务
```

部署要点：**节点数 ≥ 副本数 + 1**（保证容错）；**奇数节点利于 Raft 选举**（3/5/7 节点是常见形态）；**Raft 元数据节点与数据节点同进程**（无需单独部署控制面——单二进制的红利）。

## 3. 扩缩容与重分片

- **水平扩容**：加入新节点 → 触发**重分片（resharding）**——把现有分片迁移/拆分到新节点；1.19 起 Web UI 实时显示重分片进度；重分片期间服务不中断（ProxyShard 代理跟踪变更）。
- **垂直扩容**：单节点升配（内存/磁盘），重启生效，数据不动。
- **缩容**：下线节点前先把该节点分片迁走（重分片到剩余节点），禁止直接 kill——分片副本数会跌破下限，数据处于降级状态。

扩容的工程纪律：**先扩副本再扩分片**（先保可用性再提吞吐）；重分片是 IO 密集操作，低峰执行；扩容后验证 `GET /cluster` 的分片分布均匀性（哈希分布天然均匀，但副本拓扑要人工抽查）。

## 4. 监控与备份

**监控**：`/metrics` 暴露 Prometheus 指标（查询延迟、吞吐、内存、段数）；1.17 起**集群级遥测 API**（`/cluster/telemetry`：leader 选举、重分片、分片迁移状态）。

1.18 起**内存监控**（按组件分解的 RAM/磁盘/页缓存占用，Web UI 与 API 双通道）。监控三件事：**段数**（过多 → 查询变慢信号）、**内存占用**（超预算 → 量化或扩容）、**副本状态**（落后 → 可用性风险）。

核心指标清单（Grafana 面板五块）：**查询**——QPS、P95 延迟（向量查询波动大，P95 比均值诚实）、`score_threshold` 命中率（持续下降 = 数据质量问题）；**写入**——写入速率、WAL 积压（写入 > 应用速度时 WAL 增长，是写入风暴信号）；**存储**——段数/集合、磁盘占用、内存按组件（向量/payload/索引）。

**集群**——节点状态、副本同步延迟（`GET /cluster` 与遥测 API）、分片分布均匀性；**资源**——CPU（optimizer 与查询争抢的信号）、页缓存命中。

告警阈值参考：P95 > 100ms（数据规模/参数问题）、段数 > 50/集合（optimizer 跟不上）、副本落后 > 1 分钟（网络或 IO 问题）——先报警再定位，别等用户报告慢查询。

**备份**：快照（snapshot）是官方推荐——`POST /collections/{name}/snapshots` 生成集合级快照（存到快照目录，可下载恢复）；多节点集群建议**逐分片一致性快照**或直接文件系统级备份（与 PgVector 体系的"文件级快照"纪律一致——活库文件直接拷贝不安全）；恢复演练季度一次：快照恢复到临时实例 → 抽样 query 对拍 → 通过才算合格。

## 5. Qdrant Cloud 与合规

Cloud 分层（2026-04-28 现状）：**Standard**（99.5% SLA）、**Premium**（99.9%）、**Premium Multi-AZ**（99.95%，三可用区复制）。

企业功能：**GPU 索引**（T4 上 HNSW 构建快 4 倍，高写入场景）、**审计日志**（全部 API 操作结构化 JSON + 用户归属，可接 SIEM）。

选型判断：开源版覆盖功能、Cloud 覆盖合规与 SLA——**数据出域敏感场景（金融/政务/企业内部知识）优先私有化**（Helm 部署 + 自建监控），Cloud 留给无合规约束或团队无运维能力的场景。

## 6. 部署清单（生产上线前逐项打勾）

- 持久卷挂载 + PVC Retain；镜像 tag 锁定（1.19.0）
- 资源限制（内存 1.5-2× 向量 + 页缓存余量；CPU 留 optimizer 余量）
- 探活就绪（/healthz + /livez）；Prometheus 指标接入
- 快照策略（每日集合快照 + 季度恢复演练）
- 认证：开源版无内置认证——**网络层隔离**（内网 + API key 由网关校验）或 Cloud（托管认证）
- 分布式：节点数 ≥ 副本+1、奇数节点、扩容预案写入 runbook

> 🎯 **核心要点**：单二进制既是单机也是集群——Raft 管元数据、自定义复制管数据；分片给容量、副本给可用性，写同步确认、读任一副本；扩容先扩副本再重分片；快照备份 + 季度演练；开源版无内置认证靠网络层，Cloud 买 SLA 与审计、私有化保数据主权。
