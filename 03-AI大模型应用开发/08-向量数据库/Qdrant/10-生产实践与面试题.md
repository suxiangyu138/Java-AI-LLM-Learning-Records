# 生产实践与面试题

> 把前面九篇沉淀为"避坑清单 + 生产清单 + 面试弹药"——验收你是否真的能上生产

## 1. 性能真相

用数据校准预期（1.19，2026 基线）：
**内存** ≈ 原始向量 × 1.5-2（无量化），TurboQuant 后压到约 0.2-0.3×——量化是规模的第一杠杆；

**吞吐**：单节点查询吞吐随 ef 与数据规模变化，Rust 实现的单机 QPS 在千级到万级（与数据集与参数强相关，上线前用自己数据压测）；

**分布式**：分片让吞吐随节点近线性扩展，副本保障可用性（写同步确认有跨节点延迟，写密集场景注意副本因子权衡）；

**过滤感知**：过滤条件下的查询延迟与无过滤接近（选择性低时），这是相对 post-filter 派系的实测差异点。

## 2. 避坑清单（Top 12）

1. **未建 payload 索引的过滤**：能跑但慢、部分操作符不可用——建集合时同步声明 schema。
2. **score 语义混淆**：cosine 越大越近、l2 是距离变形——阈值按度量换算，跨度量搬阈值必翻车。
3. **维度不匹配**：upsert 报 wrong number of coordinates——核对模型与集合。
4. **点 ID 用自增数字**：与业务主键脱节，幂等与溯源全乱——业务主键直接做 ID。
5. **忘记持久卷**：Docker 不挂 `/qdrant/storage` 容器重建即丢数据。
6. **K8s PVC 默认 Delete**：Helm 默认保留策略卸载即删——改 Retain。
7. **单副本当集群用**：K8s 里单副本只是容器化的单机，没有分布式能力。
8. **重分片高峰执行**：IO 密集操作拖垮在线查询——低峰执行 + 1.19 看实时进度。
9. **filter 删除不验证**：删了没有回收站——先 count/filter 检索验证再删。
10. **多租户不用 tenant 索引**：基数字段白用普通 keyword——物理局域化优势全丢。
11. **开源版当公网服务**：无内置认证，端口直接暴露公网等于裸奔——网络层隔离 + API key 网关。
12. **快照不演练**：快照存在但从未恢复过——季度恢复演练 + 抽样对拍。

## 3. 生产落地清单

- 部署：镜像锁版本、持久卷 + PVC Retain、/healthz + /livez 探活、资源限制（1.5-2× 内存账）。
- 数据：业务主键做 ID、payload schema 建索引、批量 upsert（64/批）、模型名记录在集合配置。
- 索引：HNSW 参数（ef 查询级调）、量化（TurboQuant 起步）、内存层级按组件配。
- 检索：过滤感知利用（索引先行）、混合检索（dense+sparse+RRF）、score 阈值按度量换算。
- 分布式：节点 ≥ 副本+1、奇数节点、扩容先副本后分片、重分片低峰。
- 监控：Prometheus 指标（段数/内存/副本状态）、集群遥测、内存监控按组件。
- 备份：每日快照 + 季度恢复演练；审计（Cloud 或自建网关日志）。
- 增长预案：量化 → 加副本 → 重分片 → 评估 Cloud/Milvus，触发条件写进 ADR。

## 4. 面试高频题与答题范式

**Q1：Qdrant 和 Chroma/PgVector 的本质区别？**。
答：定位差异（独立服务 vs 嵌入式 vs PG 扩展）+ 两个硬差异：**过滤感知搜索**（过滤融入图遍历而非 post-filter，召回不随选择性衰减）与**完整量化体系**（TurboQuant 8× 压缩）。横向对比时主动引出去噪（见 09 篇对比表）。

**Q2：过滤感知搜索的原理？为什么延迟可预测？**。
答：两步——先查 payload 索引估算过滤基数；选择性低走**约束 HNSW 遍历**（图搜索跳过不匹配邻居，召回不丢、延迟接近无过滤），选择性高走**精确子集扫描**（候选集小到暴力排序更快且 100% 精确）。对比 post-filter 派系（先 ANN 后过滤，选择性高吞结果）——这是 Qdrant 相对 Chroma/PgVector 最值钱的原理。

**Q3：TurboQuant 和传统量化的区别？**。
答：传统 scalar 量化直接压 float32 为 int8（误差与方向分布耦合）。

TurboQuant 压缩前先做**快速 Hadamard 旋转**打散方向分布，量化误差均匀化，**同召回下压缩比翻倍**（scalar 4× → TurboQuant 8×）；Qdrant 实现加长度归一化、逐坐标校准与 SIMD。

1.19 的 Turbo4 更进一步——4-bit 作为唯一存储表示，存储减 9 倍（牺牲召回，适合存储红线场景）。

**Q4：Qdrant 分布式用什么协议？分片和副本的区别？**。
答：Raft 管元数据共识（节点/分片分配），自定义复制层管点级数据（主写 + 异步跟随 + 同步确认）。分片 = 数据水平切分（一致哈希，给容量与吞吐，创建时定数）；副本 = 分片冗余（给可用性，写跨副本确认、读任一副本）。节点数 ≥ 副本 + 1，奇数节点利于选举。

**Q5：混合检索怎么做？**。
答：命名向量让 dense + sparse 同库并存——`prefetch` 两路各取候选、`FusionQuery(RRF)` 融合（排名倒数免归一化）。稠密路管语义、稀疏路（BM25/SPLADE）管专有名词与精确词句，实测提升 10-20%，用标注集验证。

**Q6：Java 项目怎么接入 Qdrant？**。
答：三路径——官方 `io.qdrant:client`（gRPC 底层）、LangChain4j `QdrantEmbeddingStore`（RAG 组件最全）、Spring AI `spring-ai-starter-vector-store-qdrant`（统一 VectorStore 抽象，换库零成本）。生产组合：Spring AI 管检索 + LangChain4j 管切分。

**Q7：线上检索召回率下降怎么排查？**。
答：四层排查——数据层（embedding 模型是否一致、upsert 是否覆盖了旧数据）、参数层（ef 是否被调小、量化配置是否变更）、过滤层（新过滤条件与 payload 索引是否匹配——**未建索引字段过滤会静默退化**）、集群层（副本落后、重分片进行中）。先验证"过滤命中量"再谈召回，与 Chroma/PgVector 体系 Q8 的排查框架一致。

**答题范式**：先定位（服务 vs 嵌入式 vs 扩展）→ 再给原理（过滤感知/量化/分布式机制）→ 最后给边界与替代方案。"定位 → 原理 → 边界"三段式，与 Chroma/PgVector 体系共用，向量库面试通用。

> 🎯 **核心要点**：十二坑清单覆盖 90% 生产事故；"索引先行、ID 用业务键、持久卷、副本 + 节点数、快照演练"五条总纲；面试记住过滤感知原理与 TurboQuant（Hadamard 旋转）两个硬考点，答出深度就是加分项。
