# 检索过滤与混合检索

> 过滤操作符全解、payload 索引类型、dense+sparse 混合检索、Relevance Feedback——检索质量的主战场

## 1. 过滤操作符全解

Qdrant 的过滤是 `Filter` 结构：`must`（全部满足）、`should`（至少一个）、`must_not`（全部不满足）三个条件列表，条件可嵌套。核心操作符：

| 操作符 | 语义 | 示例 |
|--------|------|------|
| `match` | 精确匹配（keyword/int/bool） | `{"key": "category", "match": {"value": "jvm"}}` |
| `match_any` | 多值任一 | `{"match_any": {"any": ["jvm", "cache"]}}` |
| `range` | 数值范围（gt/gte/lt/lte） | `{"range": {"gte": 2024, "lt": 2027}}` |
| `geo_radius` / `geo_bounding_box` | 地理位置 | `{"geo_radius": {"center": {...}, "radius": 1000}}` |
| `nested` | 嵌套 payload 对象过滤 | `{"nested": {"key": "metadata", "filter": {...}}}` |
| `has_id` | 按 ID 集合过滤 | `{"has_id": [1, 2, 3]}` |
| **`prefix`** | **关键字前缀匹配（1.19）** | `{"prefix": "qdrant-"}` |
| **`slice`** | **确定性分区子集（1.19）** | 把点划分为不相交的确定性子集 |

组合示例（RAG 常见"分类 + 时间 + 关键词"）：

```python
query_filter=models.Filter(。
    must=[。
        models.FieldCondition(key="category", match=models.MatchValue(value="jvm")),。
        models.FieldCondition(key="year", range=models.Range(gte=2024)),。
    ],。
    should=[。
        models.FieldCondition(key="title", text=models.MatchText(text="GC")),。
    ],。
)。
```

过滤的工程铁律：**先声明 payload schema 建索引**（Qdrant 惰性索引——不建索引的字段也能过滤但退化为全段扫描，且 text/geo 等类型必须建索引才能用对应操作符）；**嵌套对象用 nested 操作符**（直接点路径 `metadata.tags` 的过滤语义不同）；**过滤条件与过滤感知搜索配合**（04 篇：建了索引的字段才能参与基数估算）。

## 2. payload 索引类型

| 索引类型 | 适用字段 | 支持的过滤 |
|---------|---------|-----------|
| keyword | 字符串/枚举 | match/prefix/match_any |
| integer/float | 数值 | range/match |
| bool | 布尔 | match |
| geo | 经纬度对象 | geo_radius/geo_bounding_box |
| text | 长文本 | text（全文匹配） |
| datetime | RFC3339 时间戳 | range（内部转 64 位微秒） |
| uuid | UUID 字符串 | match/match_any |
| **tenant** | 租户 ID（专用优化） | match——数据按租户物理局域化 |

**tenant 索引**是 Qdrant 的多租户优化：声明 tenant 字段后，数据在磁盘上按租户局域化存储（同租户数据相邻）——过滤感知搜索的基数估算更准、精确扫描路径更快。**principal 索引**（时间序列场景）同类优化。

工程含义：**多租户是 Qdrant 的一等公民**（对比 Chroma/PgVector 的多租户都要应用层造轮子），租户过滤场景优先用 tenant 索引而非普通 keyword。

## 3. 全文检索（text 索引）与中文注意

payload 的 **text 索引**支持对字符串字段做全文匹配（`text` 操作符，分词后倒排匹配）——Qdrant 提供"轻量全文检索"能力，注意它的定位与边界：**适合 payload 字段的短文本匹配**（标题、标签、摘要），**不是通用搜索引擎**（无相关性排序复杂度、无高级查询语法、中文分词依赖内置 tokenizer 的简单切分——中文长文本全文检索仍是 ES 的领域）。

工程判断：**混合检索的"关键词路"优先用 sparse 向量**（BM25/SPLADE，质量与可控性都更好），text 索引留给"payload 里的精确字段匹配"（如 `title` 字段的文本条件）。

中文场景：payload 文本匹配对中文短词（1-2 字符）支持有限，专有名词/型号匹配用 sparse 向量或 keyword match 更稳。

过滤性能策略三条：**过滤字段建索引**（基数估算的前提，04 篇）；**高选择性过滤优先**（Qdrant 在选择性高时自动精确扫描——比"宽泛过滤 + 大 topK"更高效）；**组合过滤用 must + should 分层**（must 收窄、should 加权排序，而不是把全部条件塞 must）。

## 4. 混合检索：dense + sparse + RRF

命名向量让混合检索在**同库一次查询**内完成（对比 Chroma 的稀疏支持较新、PgVector 需要两路 SQL 融合）：

```python
client.query_points(。
    collection_name="docs",。
    prefetch=[。
        models.Prefetch(query=models.SparseVector(indices=[3, 45], values=[0.8, 0.5]),。
                        using="sparse", limit=20),      # 稀疏路：关键词。
        models.Prefetch(query=[0.1, 0.2, ...],。
                        using="dense", limit=20),       # 稠密路：语义。
    ],。
    query=models.FusionQuery(fusion=models.Fusion.RRF), # RRF 融合。
    limit=10,。
)。
```

两条路的取长补短：**稠密路**（语义相似）擅长同义改写、口语表达；**稀疏路**（BM25/SPLADE 词项权重）擅长专有名词、型号、精确词句。

**RRF 融合**（排名倒数）免分数归一化（与 PgVector 体系的 RRF 语义一致，Qdrant 把它做成库内原生算子）。1.19 的 **Per-Tenant IDF** 让稀疏路在多租户场景的词项稀有度按租户语料计算（BM25 打分更准）。

混合检索的评估与调参（候选量、RRF k、权重）与 Chroma/PgVector 体系的评估方法论一致：命中率 + MRR 指标说话。

## 5. Relevance Feedback：反馈驱动检索

1.17 的相关性反馈是检索增强的新形态：对 top 结果做轻量"更像/更不像"标记（模型生成或用户点击），反馈编码进查询再次检索——**不重训模型、不需人工标注**，在十亿级向量上直接提升召回。

工程场景：RAG 的"用户点了第 3 条"反馈闭环、搜索结果个性化。注意它是**查询级能力**（每次查询独立反馈），不是全局模型更新——与 RAG 的 Rerank 环节互补（Rerank 是后处理精排，反馈是查询端修正）。

## 6. 分组查询与高级检索

- **GroupBy 分组**：按 payload 字段分组返回（每租户 top-k、每分类 top-k）——`group_by` 参数配合 `limit_per_group`，替代"应用层二次聚合"。

```python
# 每分类返回 top-3（典型的多租户/多分类场景）
client.query_points(。
    collection_name="docs",。
    query=[0.1, 0.2, ...],。
    group_by="category",          # 按分类分组。
    limit=3,                      # 每分类 3 条。
    with_payload=True,。
)。
```

分组查询注意：**先过滤再分组**（过滤条件在 query_filter 里，分组是对命中集合的分组）。

**分组结果的 ordering 与 limit 语义**（每组的分数排序、组内条数上限）——用 `limit`（组内条数）与 `group_size`（组数上限）区分，两个参数别搞混。

分组查询是"多租户首页"类场景的标准实现（每租户 3 条热门 + 每分类 3 条最新），替代应用层"先拉全量再分组"的内存灾难。
- **Scroll 遍历**：`scroll` 按 ID/过滤游标式拉全量数据（导出、重建索引、迁移场景），不用 OFFSET 翻页。
- **Count**：`count` 统计命中数（过滤验证与监控用，配合"filter 删除前验证"流程）——`count` 也支持 filter 与分组参数（`exact=true` 时精确统计），数据量核对与容量规划的第一手数据源。
- **Scroll 与 Count 的组合**：导出/迁移场景"Scroll 拉全量 + Count 对账"（拉完比对条数），重建索引前的数据完整性校验标准动作——与 PgVector 体系的"恢复演练对拍 count"同一纪律。

> 🎯 **核心要点**：Filter 三条件（must/should/must_not）+ 八类 payload 索引是过滤的全部；**先建索引再过滤**是铁律，tenant 索引让多租户成为一等公民；混合检索（dense+sparse+RRF）在同库一次查询完成；Relevance Feedback 是 2026 年检索增强新方向；分组/游标/计数覆盖高级检索形态。
