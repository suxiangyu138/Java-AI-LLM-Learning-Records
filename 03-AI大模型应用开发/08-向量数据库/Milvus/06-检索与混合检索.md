## 1. 相似度度量：L2 / IP / COSINE

**度量 = "怎么算两条向量有多像"**——与索引类型一起在创建时指定：

| 度量 | 公式语义 | 适用 | 注意 |
|------|---------|------|------|
| **L2（欧氏距离）** | 距离越小越相似 | 原始向量（未归一化） | 结果按距离**升序** |
| **IP（内积）** | 内积越大越相似 | **归一化向量 / 稀疏向量（必须 IP）** | 未归一化时受模长影响 |
| **COSINE（余弦）** | 余弦相似度 | **语义检索标准**（不敏感模长） | 内部会做归一化 |

```python
# 选型标准（面试必答）：
# ① 稠密语义检索 → COSINE（文本 Embedding 的标准选择）
# ② 稀疏向量（BM25/Splade）→ IP（必须，权重累加语义）
# ③ 图像/未归一化 → L2
# ④ 与索引一致性：度量在 create_index 与 search 时必须一致！

index = {"index_type": "HNSW", "metric_type": "COSINE"}
result = collection.search(query_vectors, "embedding",
        param={"metric_type": "COSINE", "params": {"ef": 128}}, limit=10)
```

> ⚠️ **一致性红线**：**索引度量和查询度量必须一致**——建了 COSINE 索引却用 IP 查询会报错或结果错误。COSINE 是文本语义检索的事实标准（Embedding 模型输出常已归一化，此时 COSINE ≈ IP）。

## 2. search API 与过滤条件

```python
# 标准检索（含标量过滤 —— 生产必备）
result = collection.search(
    data=[query_embedding],                # 查询向量（1 个或多个）
    anns_field="embedding",                # 向量字段
    param={"metric_type": "COSINE", "params": {"ef": 128}},
    limit=10,                              # TopK
    expr='status == 1 and document_id != "doc_999"',   # 标量过滤（SQL 风格）
    output_fields=["title", "content", "document_id"]  # 返回字段（不返回 embedding！）
)

# 结果处理
for hit in result[0]:
    print(hit.id, hit.score, hit.entity.get("title"), hit.entity.get("content"))
```

**过滤的三层用法**（性能递进）：

| 方式 | 语法 | 性能 | 场景 |
|------|------|:----:|------|
| 表达式过滤（expr） | `expr='status == 1'` | 中 | 常规过滤（有标量索引更快） |
| 分区裁剪 | `partition_names=["p2026-08"]` | 快 | 按业务维度裁剪（如按月） |
| 分区键路由 | Schema `is_partition_key=True` | **最快** | 多租户（自动路由） |

**过滤字段的标量索引**（加速过滤）：

```python
# 频繁过滤的标量字段建索引（2.4+）
collection.create_index("status", {"index_type": "INVERTED"})   # 倒排标量索引
collection.create_index("tenant_id", {"index_type": "INVERTED"})
```

> 🎯 **核心要点**：检索的"四段式" = **向量查询 + 标量过滤（expr）+ 分区裁剪 + 返回字段控制**——过滤字段建标量索引、租户走分区键、返回字段不包含 embedding，三条规范同时做到，检索又快又省。

## 3. 混合检索：稠密 + 稀疏 + RRF

**混合检索（2.5+ 原生支持）**——RAG 质量的关键：

```text
为什么混合：稠密向量管"语义"（描述性查询），稀疏向量管"关键词"（精确术语）
单用语义：查"藤野先生"（精确人名）可能召回不全 —— 语义相近但词不同
单用关键词：查"少年在瓜田刺猹"（描述性）召回差 —— 词对不上语义
混合：两路同时查 → 融合排序 → 两者互补，召回率显著提升
```

**实现方式**（pymilvus 2.5+，两个向量字段 + BM25 内置函数）：

```python
# ① Schema：稠密 + 稀疏双向量字段（见 04 模块模板）
# ② 插入：BM25BuiltInFunction 自动从 content 生成稀疏向量（无需外部计算！）
from pymilvus import Function, FunctionType

bm25 = Function(name="bm25", function_type=FunctionType.BM25,
        input_field_names=["content"], output_field_names=["sparse"])

# ③ 混合检索：RRFRanker 融合
from pymilvus import RRFRanker

result = collection.hybrid_search(
    reqs=[
        {"vector": query_vec, "anns_field": "embedding",
         "param": {"metric_type": "COSINE"}, "limit": 50},       # 稠密路（召回多取）
        {"vector": query_vec, "anns_field": "sparse",
         "param": {"metric_type": "IP"}, "limit": 50},           # 稀疏路
    ],
    rerank=RRFRanker(k=60),       # 倒数排名融合（RRF）
    limit=10
)
```

**RRF（Reciprocal Rank Fusion）原理**：融合 = 各路的倒数排名相加——**排名靠前的候选在两路都出现时得分更高**（无需归一化分数）：

```text
RRF 得分 = Σ 1/(k + rank_i)
候选 X：稠密路排第 3、稀疏路排第 5 → 1/(60+3) + 1/(60+5)
候选 Y：仅稠密路排第 1      → 1/(60+1) + 0
→ X 综合更靠前（两路都有）
```

**加权替代**（无 RRF 时的简单方案）：`final_score = 0.7 × dense + 0.3 × sparse`（dense 权重 0.6-0.8 常见）。

> 🎯 **核心要点**：混合检索的完整链 = **稠密（语义）+ 稀疏（BM25 关键词）+ RRF 融合**——BM25 内置函数（2.5+）让稀疏向量零成本生成，RRF 让两路分数可比。**这是 2025 后 RAG 工程的标配检索形态**。

## 4. 全文检索：TEXT_MATCH 与内置分词

**全文检索（2.5+，Tantivy 集成）**——纯关键词匹配，不需要向量：

```python
# ① 内置分词（含中文）—— 建索引时指定
analyzer = {
    "type": "chinese",       # 中文分词器（jieba 风格）；标准：standard；自定义：custom
    "stop_words": ["的", "了"],   # 停用词（可配）
}
collection.create_index("content", {"index_type": "INVERTED",
        "analyzer_params": analyzer, "params": {"bm25_k1": 1.2, "bm25_b": 0.75}})

# ② TEXT_MATCH 检索（SQL 风格关键词匹配）
result = collection.search(...,
        expr='TEXT_MATCH(content, "Spring AI 集成")')
```

**全文检索 vs 稀疏向量（同源不同用）**：

| 维度 | TEXT_MATCH | 稀疏向量（BM25 函数） |
|------|:----------:|:---------------------:|
| 本质 | 布尔/评分检索 | 向量检索 |
| 用途 | 精确关键词过滤 | 参与混合检索融合 |
| 分词 | 检索时分析 | 写入时生成稀疏向量 |
| 场景 | "必须包含某词" | 关键词相关度排序 |

> 💡 工程实践：**"必须含某词"的硬条件用 TEXT_MATCH（过滤），"关键词相关"的软排序用稀疏向量（融合）**——两者互补而非替代。

## 5. 3.0 服务端聚合与 ORDER BY

**3.0 检索引擎从"Top-K 检索"扩展为"完整分析"**：

```python
# ① 服务端聚合（COUNT/SUM/AVG/GROUP BY）
#    —— 统计类查询不再需要"全量拉回客户端再算"
count = collection.query(expr="status == 1", output_fields=["COUNT(*) as cnt"])
# group_by：faceted search（维度统计）

# ② ORDER BY（多字段排序下推引擎）
result = collection.query(expr="...", output_fields=["price", "title"],
        order_by="price DESC, title ASC")       # 多字段排序在服务端完成

# ③ StructList：多向量检索（ColBERT/ColPali late-interaction）
#    每实体多个向量（chunk 级），检索时逐对比较 —— 文档级精确匹配
```

**工程价值**：聚合/排序下推 = **大数据量的"统计/排序"不用拉到客户端**——配合快照（08 模块）可做评估/去重/回填批处理。

> 🎯 **核心要点**：3.0 的检索 = "**Top-K 向量检索 + 标量过滤 + 服务端聚合/排序 + 多向量（StructList）**"——Milvus 从"向量搜索"走向"**向量分析引擎**"。

## 6. 检索质量评估与调优

**检索质量的度量**（RAG 效果的第一步）：

| 指标 | 含义 | 评估方式 |
|------|------|---------|
| 召回率（Recall@K） | TopK 中相关文档占比 | 人工标注的评测集 |
| 命中率（Hit Rate） | 答案所需文档是否在 TopK | 黄金数据集 |
| MRR（倒数排名） | 首个相关文档的位置 | 排序质量 |
| 检索延迟 | P95 延迟 | 监控 |

**调优路径**（按性价比）：

```text
① 检索形态：单路 → 混合检索（dense+sparse+RRF）—— 召回提升最显著
② 切分质量：chunk 大小/重叠（500-1000 字符 + 50-150 重叠，见 RAG 体系）
③ 重排序：Top-50 召回 → Cross-Encoder 重排 → Top-5 给 LLM（质量提升大）
④ 索引参数：HNSW ef（128 → 256 试召回）
⑤ Embedding 模型：换更强模型（bge-m3 等）—— 最后手段（成本最高）
```

```python
# 重排序的标准姿势（衔接 07 模块 LangChain4j/Java 生态）
# 召回 Top-50 → Cross-Encoder 打分 → 取 Top-5
# Java 生态：LangChain4j 的 EmbeddingModel + RerankModel 编排
```

> 🎯 **核心要点**：检索质量调优的顺序 = "**形态（混合）→ 切分（chunk）→ 重排（Cross-Encoder）→ 参数（ef）→ 模型（Embedding）**"——**先改检索形态与切分，不要一上来换模型**（成本与收益不成比例）。
