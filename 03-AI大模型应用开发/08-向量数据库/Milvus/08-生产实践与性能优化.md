## 1. 监控体系：Prometheus + Grafana

**指标端点**：每个组件暴露 `/metrics`（9091 端口）——Prometheus 抓取 + Grafana 看板：

| 组件 | 核心指标 | 告警阈值参考 |
|------|---------|-------------|
| **Proxy** | QPS、请求延迟（P95/P99）、错误率 | P95 > 200ms 告警 |
| **QueryNode** | 检索延迟、内存使用、段加载数 | 内存 > 80% 告警 |
| **DataNode** | 写入吞吐、日志积压（lag） | 积压持续增长告警 |
| **IndexNode** | 索引构建任务数与耗时 | 任务积压告警 |
| 系统 | CPU、内存、磁盘 IO | 常规 |

**RAG 业务质量指标**（检索侧）：

```text
平均检索时间 < 100ms（P95 < 200ms 可接受）
相似度分布（过低说明知识库与查询不匹配）
召回率人工评估（定期抽样）
用户反馈（"答非所问"率）
```

```yaml
# Prometheus 抓取配置（片段）
scrape_configs:
  - job_name: milvus
    metrics_path: /metrics
    static_configs:
      - targets: ["milvus-proxy:9091", "milvus-querynode:9091"]
```

> 🎯 **核心要点**：监控四看 = "**延迟看 Proxy/QueryNode、写入看 DataNode、索引看 IndexNode、质量看检索指标**"——与 03 模块的排障地图一一对应。

## 2. 性能调优：内存 / 检索延迟 / 写入吞吐

### 检索延迟调优（按优先级）

```text
① 索引形态：未走索引（暴力扫描）→ 等索引构建 / 优化索引（HNSW）
② ef 参数：ef 128 → 64（延迟↓召回↓）；必要时做召回/延迟权衡
③ 数据量：集集合过大 → 分区裁剪 / 分库
④ 过滤：标量索引（INVERTED）加速过滤字段
⑤ 资源：QueryNode 副本数/内存（水平扩展）
```

### 内存调优

```text
内存占用 = 加载的数据量 + 索引结构 + 查询缓存
① 索引量化：HNSW → IVF_SQ8（省 70-75% 内存）
② 只加载必要字段：embedding 字段是内存大头 —— 评估能否精简/量化
③ 释放不用的集合：release()（多集合场景）
④ 2.6 的优化红利：内存占用降 72% —— 升级 2.6+ 本身就是调优
```

### 写入吞吐调优

```text
① 批量写入：一次 insert 大批量（内部自动分批），勿逐条
② 分片数：写入瓶颈时可增加 shard 数（建集时）
③ 索引构建错峰：写入高峰与索引构建错开（IndexNode 独立）
④ 2.6 红利：写入吞吐提升 2.5 倍 —— 先升级再优化
```

> 🎯 **核心要点**：性能调优的第一原则 = "**先升级版本（2.6 的性能红利），再调参数（ef/量化/批量），最后扩资源（节点）**"——成本从低到高，收益从大到小。

## 3. 多租户：partition_key 物理隔离

**多租户的三种方案**（从简单到标准）：

| 方案 | 实现 | 性能 | 安全 | 适用 |
|------|------|:----:|:----:|------|
| ① 过滤条件 | 检索加 `tenant_id = ?` | 中（全库扫+过滤） | 中（依赖代码正确） | 小规模 |
| ② 独立 Collection | 每租户一个集 | 高 | 高（物理隔离） | 租户数少 |
| **③ 分区键（推荐）** | Schema `is_partition_key=True` | **高（自动路由）** | **高（物理隔离）** | **标准方案** |

```python
# 分区键方案（2.4+）
FieldSchema(name="tenant_id", dtype=DataType.INT64, is_partition_key=True)

# 写入：自动按 tenant_id 路由分区（无需手动管理分区）
# 检索：hybrid_search/search 时带 tenant 条件 → 只扫本租户分区
# 收益：
#   ① 安全：租户数据物理隔离（误查其他租户 = 查不到而非数据泄露）
#   ② 性能：检索范围裁剪（只扫本租户分区）
#   ③ 删除：按租户删除（drop 分区 = 快速清理）
```

> ⚠️ **安全认知**：方案 ①（过滤条件）的隔离**依赖代码不出错**——漏写 tenant 条件就是跨租户数据泄露（SaaS 最高危事故）；**分区键的隔离是物理的**（检索根本不扫其他分区）。**多租户生产必选分区键**（与 MP 的多租户插件是同一安全哲学，见 `MyBatisPlus/06`）。

## 4. 数据生命周期与 TTL

**数据生命周期管理**（RAG 知识库的日常运维）：

```text
新增文档 → upsert（幂等）
修改文档 → 重跑管道 → upsert 覆盖（主键相同）
删除文档 → delete by document_id（删全部 chunk）
过期数据 → 分区清理 / TTL（3.0 实体级）
```

**TTL（3.0 实体级）**——合规与数据过期场景：

```python
# 3.0：TIMESTAMPTZ 字段 + TTL 配置 —— 实体自动过期
FieldSchema(name="expires_at", dtype=DataType.TIMESTAMPTZ)
# 检索/查询时自动过滤已过期实体
# 场景：情景记忆（对话日志 30-90 天）、合规数据保留期
```

**分区级生命周期**（2.x 的做法，3.0 仍可用）：

```python
# 按月分区：p2026-08 / p2026-09
collection.add_partition("p2026-08")
# 过期月 → drop_partition（快速整区清理）
collection.drop_partition("p2025-01")   # 远快于逐条 delete
```

> 🎯 **核心要点**：生命周期三件套 = "**upsert（改）+ delete by PK（删）+ 分区/TTL（过期）**"——按月分区是 2.x 的清理利器（drop 分区秒级），3.0 的实体级 TTL 让"逐条过期"成为可能。

## 5. 3.0 快照备份与恢复

**3.0 快照（Snapshots）**——备份与批处理的基础设施：

```text
快照 = 在线集合的时间点只读视图（MVCC 隔离）
特点：
① 创建成本极低（增量存储，不复制数据）
② 生产写入不受影响（快照期间照常读写）
③ 多个快照共存（时间旅行）
用途：
① 备份：快照 → 导出/归档（恢复点）
② 评估：对快照跑评测（不干扰生产数据）
③ 批处理：去重/回填在快照上执行
④ 回滚：数据问题 → 恢复到快照
```

**2.x 的备份方式**（升级前）：Milvus Backup 工具（导出为文件）——3.0 快照是原生替代。

> 🎯 **核心要点**：3.0 快照 = "**时间点视图 + 零成本 + 生产无感**"——备份、评估、回滚三个场景一个机制解决。**"升级 3.0 的理由清单"里，快照与在线 Schema 演进排前二**（运维侧收益最大）。

## 6. 常见坑清单（15 条）

| # | 坑 | 现象 | 解法 |
|:-:|-----|------|------|
| 1 | **vm.max_map_count 未设** | 启动失败 | `sysctl -w vm.max_map_count=262144` |
| 2 | **collection not loaded** | search 报错 | 检索前 `collection.load()` |
| 3 | 写入后立即查不到 | 一致性级别 | Bounded 默认 5s / 强一致 / flush |
| 4 | 查询慢（刚写入） | 未索引段暴力扫描 | 等索引构建 / 优化索引 |
| 5 | 度量不一致 | 检索报错/结果错 | 索引与查询度量必须一致 |
| 6 | 向量维度不匹配 | insert 报错 | 与 Embedding 模型输出对齐 |
| 7 | 过滤字段无标量索引 | 过滤慢 | `create_index`（INVERTED） |
| 8 | 动态字段当过滤用 | $meta 不可索引 | 频繁过滤字段进 Schema |
| 9 | 逐条 insert | 写入极慢 | 批量写入 |
| 10 | 多租户只靠过滤条件 | 跨租户泄露风险 | 分区键（物理隔离） |
| 11 | 检索返回 embedding | 带宽浪费 | `output_fields` 不含 embedding |
| 12 | 无阈值检索 | 相似度低也返回 | similarityThreshold 过滤 |
| 13 | 索引参数只调构建不调查询 | 召回不升 | **先调 ef（查询期）** |
| 14 | pymilvus 与 Lite 版本不匹配 | 连接异常 | `pymilvus>=2.4.11` + `milvus-lite==2.4.10` |
| 15 | 升级 3.0 不看 SDK 节奏 | Java SDK 暂缺 | 3.0 首发 Python/Go/Node，Java 稍后 |

> 🎯 **核心要点**：坑清单的三大根源 = "**环境前置（map_count）、生命周期（load/一致性）、配置一致（度量/维度/索引）**"——把 15 条过一遍，生产事故少一半。

## 7. 生产架构选型

**生产选型决策树**：

```text
数据规模与租户数？
├── < 百万级 + 单租户 → 单机 Docker（2.6：2G 内存可跑）✅
├── < 千万级 + 多租户 → 单机/小集群 + 分区键 ✅
├── 千万级 + 高并发 → K8s 集群（QueryNode 水平扩展）✅
├── 亿级 + 超大规模 → 集群 + DiskANN + 分片优化
└── 已有数据湖（Lance/Iceberg） → 3.0 外部集合（零拷贝）✅
运维能力弱 → Zilliz Cloud（托管）
```

**高可用与容量规划**：

| 维度 | 规划 |
|------|------|
| 高可用 | K8s 多副本（Proxy/QueryNode ≥ 2）+ etcd 3 节点 |
| 存储 | 对象存储冗余（S3 跨可用区） |
| 容量 | 数据量 × 索引膨胀系数（HNSW 约 1.3-1.5×）≈ 存储规划 |
| 内存 | QueryNode 内存 ≈ 加载集合体积（embedding 是大头） |
| 升级 | 3.0 的迁移：评估外部集合收益 + SDK 节奏（Java 稍后） |

> 🎯 **最终核心要点**：Milvus 的生产化 = "**监控（四看）+ 调优（先版本后参数再资源）+ 安全（分区键多租户）+ 生命周期（upsert/分区/TTL）+ 备份（3.0 快照）**"五件套——前四件 2.x 已成熟，第五件是 3.0 的升级红利。生产团队按五件套逐项落地，Milvus 就是可靠的基础设施。
