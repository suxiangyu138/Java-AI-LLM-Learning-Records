## 1. 必背考点：十二问

### 1.1 Milvus 是什么？和 FAISS/Chroma 的区别？

**答题链**：分布式向量数据库（Apache 2.0，LF AI & Data）→ 定位对比：FAISS 是索引库（无数据管理）、Chroma 轻量（万级）、Milvus 生产级（亿级、云原生、混合检索）→ 核心竞争力（存算分离/混合检索/数据管理/生态集成）。

### 1.2 Collection 和 Schema 是什么？

**答题链**：Collection = 表；Schema = 建表语句（创建后 2.x 不可改、**3.0 可在线演进**）→ 字段类型（向量/标量/JSON/**3.0 TEXT/BLOB**）→ 设计四件套（主键幂等/溯源字段/过滤字段可索引/向量字段声明维度）。

### 1.3 索引有哪些？怎么选？

**答题链**：FLAT（<10 万精确）→ IVF（百万，量化省内存）→ **HNSW（千万级生产首选）** → DiskANN（亿级磁盘）→ 稀疏用倒排（**3.0 SINDI 默认**）→ 选型 = 规模定类型、内存定量化、延迟定 ef。

### 1.4 HNSW 的三个参数？

**答题链**：**M**（图连接数，管内存/召回）、**efConstruction**（构建质量）、**ef**（查询召回，**查询期可动态调**）→ 调优顺序：先 ef（零重建）→ 再 M/efConstruction（需重建）→ 经验值 M=16-32、efConstruction=200-300、ef=128（约 92% 召回）。

### 1.5 稠密向量和稀疏向量的区别？

**答题链**：稠密 = 固定维数（1536）语义相似；稀疏 = 高维大部分为 0（词表）**关键词精确匹配** → 擅长互补（语义 vs 术语）→ 来源（Embedding vs BM25/Splade）→ 索引（HNSW vs 倒排/SINDI）→ **混合检索 = 两者结合**。

### 1.6 混合检索怎么实现？

**答题链**：双向量字段（dense + sparse）→ BM25BuiltInFunction 自动生成稀疏向量（2.5+）→ 两路同时 search → **RRF 融合**（倒数排名相加）→ 权重替代方案（0.7 dense + 0.3 sparse）→ 收益：召回率显著提升。

### 1.7 RRF 的原理？

**答题链**：RRF 得分 = Σ 1/(k + rank_i)——各路排名倒数相加 → 不依赖分数归一化（稠密分数和稀疏分数不可比！）→ 两路都靠前的候选胜出 → k 一般 60。

### 1.8 Spring AI 怎么集成 Milvus？

**答题链**：依赖 `spring-ai-milvus-store` + `milvus-sdk-java` → yml 配置（host/collection/index-type/metric-type/dimension）→ 注入 `VectorStore` → 三方法（add/similaritySearch/delete）→ filterExpression 过滤 → 完整 RAG：检索 → 拼上下文 → LLM。

### 1.9 多租户怎么做？

**答题链**：三方案对比（过滤条件/独立 Collection/**分区键**）→ 分区键（2.4+）物理隔离 + 检索自动路由 → **安全认知：物理隔离 > 逻辑过滤**（漏写条件 = 数据泄露）。

### 1.10 Milvus 3.0 的核心变化？

**答题链**（时效性）：**2026-07-16 GA，Lake-Native** → 外部集合（数据湖 Lance/Iceberg 直读，零拷贝）→ Loon 存储（Vortex 列式，点读 I/O 降 135 倍）→ 快照（MVCC 时间点视图）→ StructList（多向量/ColBERT）→ SINDI 稀疏索引 → TEXT/BLOB/可空向量 → 在线 Schema 演进 → v3.1 规划（谓词下推/UDF）。

### 1.11 写入后查不到是为什么？

**答题链**：一致性级别（Bounded 默认 5s 可见）→ 解法三选（等待/Strong 一致/flush）→ 加上"索引异步构建"（未索引段暴力扫描）→ "写入可见"与"走索引"是两个机制。

### 1.12 检索质量怎么调优？

**答题链**：调优顺序 = 形态（单路 → 混合）→ 切分（chunk 500-1000 + 重叠）→ 重排（Top-50 → Cross-Encoder → Top-5）→ 参数（ef）→ 模型（Embedding 升级，最后手段）→ 度量（Hit Rate/Recall@K/MRR）。

## 2. 高频陷阱题 12 连问

1. **对错**：Milvus 3.0 是 2025 年 6 月发布的。（❌ **2026-07-16 GA**；2025 发布的是 2.5/2.6）
2. **对错**：Collection 创建后字段可以随便改。（❌ 2.x 不可改；**3.0 起支持在线演进**）
3. **结果**：`collection.search()` 之前忘记 `load()`？（报错 collection not loaded）
4. **对错**：FLAT 索引召回率不是 100%。（❌ FLAT 是暴力扫描，100% 召回）
5. **结果**：HNSW 的 ef 在哪调整？（**查询期** search 参数——不用重建索引）
6. **对错**：稀疏向量可以用 COSINE 度量。（❌ 稀疏必须 IP（内积））
7. **对错**：稠密检索能查准"藤野先生"这类精确术语。（不一定——混合检索才是答案）
8. **结果**：RRF 需要两路分数归一化吗？（不需要——RRF 用排名不用分数）
9. **对错**：多租户用"检索加 tenant 过滤"就足够安全。（❌ 依赖代码正确性；分区键物理隔离才安全）
10. **结果**：插入时向量维度与 Schema 不符？（报错——维数必须与声明一致）
11. **对错**：Milvus Lite 可以用于生产环境。（❌ 单用户本地文件，开发测试用）
12. **结果**：`vm.max_map_count` 不设置会怎样？（Milvus 启动失败——必须 262144）

## 3. 高频追问速答

| 追问 | 速答 |
|------|------|
| 检索为什么不返回 embedding 字段？ | 维度大浪费带宽——output_fields 只返回需要的标量字段 |
| 文档更新了怎么同步？ | 重跑管道 upsert（主键相同覆盖）——主键 = 文档ID:chunk序号 |
| 分片和分区的区别？ | 分片管写入并行（自动哈希）、分区管检索裁剪（业务维度） |
| Bounded 一致性是多久？ | 默认约 5 秒内可见（可配置） |
| 全文检索（TEXT_MATCH）和稀疏向量什么关系？ | 同源于 BM25/分词：TEXT_MATCH 是硬条件过滤、稀疏向量参与排序融合 |
| 亿级数据用什么索引？ | DiskANN（磁盘索引）或分片集群 + HNSW |
| 索引和查询的度量不一致会怎样？ | 报错或结果错误——必须一致 |
| 为什么先调 ef 而不是 M？ | ef 是查询期参数（零重建），M 要重建索引 |
| Spring AI 和 LangChain4j 怎么选？ | Spring Boot 标准项目用 Spring AI；需要重排等细编排用 LangChain4j |
| 3.0 对 Java 生态的影响？ | 首发 Python/Go/Node SDK，Java 稍后——Java 项目初期评估后升级 |
| 分区键和过滤条件哪个快？ | 分区键（物理裁剪只扫本分区）；过滤是扫后滤（全库扫 + 条件） |
| 检索结果能直接给 LLM 吗？ | 先重排（Top-50 → Cross-Encoder → Top-5）——直接给 Top-10 噪音大 |
| 亿级数据内存不够怎么办？ | DiskANN（磁盘索引）或 IVFPQ 量化 + 分片集群 |
| 如何评估检索质量？ | 黄金数据集测 Hit Rate/Recall@K/MRR；线上抽样人工评估 |
| 3.0 外部集合适合什么场景？ | 已有数据湖（Lance/Iceberg）的团队——数据零拷贝直接检索 |
| 写入吞吐怎么提升？ | 批量写入（勿逐条）+ 增加分片 + 升级 2.6+（吞吐 2.5 倍） |
| 索引构建慢怎么办？ | 检查 IndexNode 资源；小数据先暴力查询（未索引段）；错峰构建 |
| 快照能做什么？ | 备份/恢复点、评测隔离、批处理（去重/回填）——MVCC 不阻塞生产写入 |
| 中文检索怎么优化？ | 内置中文分词器（chinese）+ 自定义词典/同义词（3.0 FileResource） |

## 4. 场景题：RAG 存储层设计

**题目**：设计一个企业知识库 RAG 系统的存储层（Milvus），要求：多租户、混合检索、文档增删改、百万级数据。

**答题框架**（按评分点展开）：

```text
① 版本与部署：2.6 单机起步（百万级），预留 K8s 集群升级路径；评估 3.0（外部集合/快照）
② Schema 设计：
   - 主键 = document_id:chunk_index（幂等）
   - 溯源字段：document_id/title/content/metadata（JSON）
   - 多租户：tenant_id 字段 is_partition_key=True（物理隔离）
   - 向量：embedding（FLOAT_VECTOR 1536）+ sparse（SPARSE_FLOAT_VECTOR）
③ 索引：稠密 HNSW（M=32, ef=128 起步）、稀疏倒排/SINDI、过滤字段标量索引
④ 检索：混合检索（BM25 内置函数 + RRF）→ Top-50 → Cross-Encoder 重排 → Top-5
⑤ 数据管道：解析 → 切分（500-1000 字符 + 重叠）→ Embedding → upsert（幂等）
⑥ 生命周期：文档删除 delete by document_id、按月分区、3.0 TTL
⑦ 监控：检索延迟 P95、写入积压、召回率抽样评估
⑧ 加分点：
   - 一致性级别选择（管道 Bounded、交互式 Strong）
   - 相似度阈值 + 无结果兜底
   - 3.0 快照做备份与评测
```

## 5. 面试加分项：架构视角

**面试官追问"你们 RAG 存储层怎么设计的"时的完整作答框架**：

```text
① 选型理由：为什么 Milvus（生产级/混合检索/Java 生态集成）而非 Chroma/FAISS
② 版本认知：2.6 单机起步 → 3.0 湖仓原生评估（外部集合/快照收益）
③ 数据设计：Schema 四件套 + 分区键多租户 + 主键幂等
④ 检索设计：混合检索（dense+sparse+RRF）→ 重排（Cross-Encoder）→ 阈值兜底
⑤ 生产保障：监控四看 + 一致性级别选择 + 备份（快照）+ 数据生命周期
⑥ 演进路线：数据量增长 → K8s 集群 → DiskANN/分片 → 湖仓整合（3.0）
```

**三个"谈资级"观点**（能讲出 = 架构成熟度）：

| 观点 | 展开 |
|------|------|
| "检索质量的上限在召回，下限在切分" | 切分质量差，再好的检索也白搭；混合检索是召回提升的第一杠杆 |
| "向量库的运维坑大多在'静默'" | 索引未建、度量不一致、集合未 load——都不报错但结果不对 |
| "3.0 的价值在运维侧" | 在线 Schema 演进 + 快照解决的是 2.x 最痛的两个运维问题 |

> 🎯 **核心要点**：架构视角的答题公式 = **选型理由 → 数据设计 → 检索设计 → 生产保障 → 演进路线**五段式——能按这个框架讲，Milvus 从"会用"升维为"能设计"。
