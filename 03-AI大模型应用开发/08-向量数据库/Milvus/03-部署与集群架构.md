## 1. 部署形态总览

| 形态 | 适用 | 资源 | 一致性 |
|------|------|------|--------|
| **Milvus Lite** | 本地开发/测试/教学 | 内存 ~500MB，无 Docker | 单进程 |
| 单机（Docker Compose） | 中小项目生产 | 2G 内存起（2.6+） | 完整 |
| **集群（K8s Operator）** | 生产标准 | 多节点 | 完整 |
| 3.0 湖仓原生 | 数据湖场景（S3/Iceberg/Lance） | 与对象存储配合 | 完整 |
| Zilliz Cloud | 托管（免运维） | 按需 | 完整 |

**选型决策**：

```text
本地开发/演示 → Milvus Lite（pip install，30 秒上手）
单机生产（<百万级） → Docker Compose（2.6 起 2G 内存可跑）
生产标准（百万-亿级） → K8s Operator（可水平扩展）
数据湖已有 → 3.0 外部集合（免迁移）
无运维团队 → Zilliz Cloud
```

> 🎯 **核心要点**：部署形态 = **数据规模与运维能力的函数**——开发用 Lite（零成本）、生产上 K8s（可扩展）、云原生用 Cloud。**不要在开发环境直接上集群**，Lite 与单机已覆盖 95% 的开发需求。

## 2. Milvus Lite：本地开发

**Milvus Lite**：嵌入式版本——无需 Docker，pip 安装即用，内存 ~500MB，本地文件持久化：

```bash
# 安装（版本绑定严格）
pip install pymilvus>=2.4.11 milvus-lite==2.4.10

# 启动：pymilvus 自动检测到 lite 后本地直连
```

```python
from pymilvus import connections, Collection

# 连接本地文件存储的 Lite 实例
connections.connect(uri="./milvus_lite.db")   # 本地文件即"数据库"

collection = Collection("demo_kb")
# ... 与完整版 API 完全一致
```

**Lite 的边界**：

| 维度 | Lite | 完整版 |
|------|:----:|:------:|
| 部署 | 进程内（无服务） | 独立服务/集群 |
| 并发 | 单用户 | 多用户/高并发 |
| 持久化 | 本地文件 | 对象存储（S3 等） |
| 生产 | ❌ 不适合 | ✅ |
| 适用 | 开发/测试/教学/小 Demo | 生产 |

> 🎯 **核心要点**：**Lite = "Milvus 的 SQLite"**——API 与完整版一致（`pymilvus` 同一套），开发期代码无缝迁移到生产。**开发用 Lite、生产用集群，代码零改动**是标准工作流。

## 3. 单机部署：Docker Compose

**单机（standalone）**：所有组件在一个进程/容器中——2.6 起 2G 内存可运行：

```yaml
# docker-compose.yml（简化版）
services:
  etcd:                              # 元数据存储
    image: quay.io/coreos/etcd:v3.5.5
  minio:                             # 对象存储（数据持久化）
    image: minio/minio:RELEASE.2023-03-20T20-16-18Z
  standalone:
    image: milvusdb/milvus:v2.6.3    # Milvus 单机
    command: ["milvus", "run", "standalone"]
    environment:
      ETCD_ENDPOINTS: etcd:2379
      MINIO_ADDRESS: minio:9000
    ports: ["19530:19530"]           # 客户端端口（gRPC）
```

**单机的三个依赖组件**：

| 组件 | 职责 | 类比 |
|------|------|------|
| **etcd** | 元数据存储（Collection/索引元信息） | 注册中心 |
| **MinIO** | 数据文件存储（段/索引文件） | 对象存储 |
| Milvus 本体 | 计算 + 协调 | 数据库服务 |

**启动后验证**：

```bash
curl -X GET http://localhost:19530/healthz    # 健康检查
# 或 Python：connections.connect(host="localhost", port="19530")
```

> 🎯 **核心要点**：单机 = "**三容器组合**"（etcd + MinIO + Milvus）——理解这个组合，就理解了 Milvus 的存算分离雏形：**元数据（etcd）、数据文件（MinIO）、计算（Milvus）三者分离**，集群只是把 Milvus 拆成更多组件。

## 4. 集群架构：七大组件

**集群模式 = 存算分离的完整形态**（生产排障必懂的地图）：

```text
客户端（pymilvus / Java SDK / Spring AI）
        │ gRPC
        ▼
   ┌─ Proxy（接入层）───────────┐
   │  请求路由/鉴权/限流          │
   └───┬──────────────────────┘
       ▼
┌──────────────┬───────────────────┐
│ Coordinator  │    Worker 节点     │
│ RootCoord     │  DataNode（数据）  │
│ QueryCoord    │  QueryNode（检索） │
│ DataCoord     │  IndexNode（索引） │
└──────┬───────┴───────────────────┘
       ▼
   etcd（元数据） + MinIO/S3（数据文件）
```

| 组件 | 职责 | 类比 | 排障关注 |
|------|------|------|---------|
| **Proxy** | 接入、路由、鉴权 | API 网关 | QPS、请求延迟 |
| **RootCoord** | DDL 协调（建集/删集） | 管理节点 | 元数据操作 |
| **QueryCoord / QueryNode** | 检索调度 / 执行检索 | 查询引擎 | **检索延迟、内存** |
| **DataCoord / DataNode** | 写入调度 / 数据落盘 | 写入引擎 | **写入吞吐、积压** |
| **IndexCoord / IndexNode** | 索引任务调度 / 构建索引 | 索引工人 | 索引构建耗时 |
| etcd | 元数据 | 协调存储 | 容量 |
| MinIO/S3 | 数据文件（段+索引） | 数据仓库 | IO 延迟 |

**理解集群的三个关键**：

1. **存算分离**：计算（Query/Data/Index Node）与存储（S3）独立扩展——**检索慢扩 QueryNode、写入慢扩 DataNode**；
2. **写入链路**：Proxy → DataNode → 段落盘 S3 → 索引构建（IndexNode）→ 可检索（QueryNode 加载）——"写入后要等索引/加载完成才可搜"是 2.x 的常见认知点；
3. **扩展方向**：水平扩展以"节点副本"为单位，分片分布到各节点。

> 🎯 **核心要点**：集群排障地图 = "**查延迟看 QueryNode、查写入看 DataNode、查索引看 IndexNode、查元数据看 etcd**"——四个"看"覆盖 90% 的集群问题定位（监控指标见 08 模块）。

## 5. K8s 部署：Milvus Operator

**Milvus Operator**：K8s 上的官方部署方式——CRD 声明式管理集群生命周期：

```yaml
# milvuscluster.yaml（核心声明）
apiVersion: milvus.io/v1beta1
kind: MilvusCluster
metadata:
  name: milvus-prod
spec:
  components:                          # 各组件独立扩缩容
    proxy:
      replicas: 2                      # 接入层副本
    queryNode:
      replicas: 3                      # 检索节点（按检索负载扩）
      resources:
        requests: {memory: 4Gi, cpu: "2"}
    dataNode:
      replicas: 2
  dependencies:
    etcd: {inCluster: {values: {replicaCount: 3}}}
    storage: {s3: {endpoint: "minio.minio.svc:9000"}}   # 对接对象存储
```

```bash
kubectl apply -f milvuscluster.yaml
kubectl get milvuscluster    # 观察集群状态
```

**K8s 部署的收益与要点**：

| 收益 | 要点 |
|------|------|
| 组件独立扩缩容（按负载） | QueryNode 是检索瓶颈，优先扩容 |
| 滚动升级（2.6+） | 版本升级不停服 |
| 声明式运维 | GitOps 友好 |
| 多集群/联邦（2.4+） | 跨地域部署 |

> 🎯 **核心要点**：K8s = "**生产标准部署**"——Operator 把"七大组件的部署与扩缩容"变成 YAML 声明。小团队从单机起步，负载上来再迁集群（2.6 的性能提升让"单机撑更久"）。

## 6. 3.0 的湖仓原生部署形态

**3.0 的部署差异**（衔接 01 模块的 Lake-Native）：

```text
2.x 部署：数据必须写入 Milvus（复制一份到对象存储）
3.0 部署：数据湖（S3 上的 Lance/Iceberg/Parquet）是"主数据"
  → Milvus 只建索引（外部集合），数据不拷贝
  → 支持 S3 兼容存储 / GCS / Azure Blob
  → 离线/内网环境（air-gapped）可部署
```

**3.0 部署的注意点**：

1. **外部集合的索引存储**：索引仍由 Milvus 管理（可放不同存储），源数据不动；
2. **增量同步**：外部集合支持增量同步——数据湖新数据自动入索引；
3. **SDK 节奏**：3.0 首发 Python/Go/Node.js SDK，**Java SDK 稍后发布**——Java 生态用户 3.0 初期注意版本对齐。

> 🎯 **核心要点**：3.0 部署的核心变化 = "**Milvus 从数据副本的宿主，变成数据湖的索引层**"——已有数据湖（Iceberg/Lance）的团队，3.0 的迁移成本大幅降低（数据零拷贝）。

## 7. 部署前置与常见问题

**部署前置条件（必查）**：

| 检查项 | 值 | 不设的后果 |
|--------|:--:|-----------|
| **vm.max_map_count** | `262144`（`sysctl -w vm.max_map_count=262144`） | **Milvus 启动失败**（内存映射不足） |
| 内存 | 单机 2G+（2.6）；Lite 500MB | OOM |
| 端口 | 19530（gRPC）/ 9091（metrics） | 连通性 |
| 对象存储 | MinIO/S3 可写 | 数据落盘失败 |

**部署排障速查**：

```bash
# 健康检查
curl http://localhost:9091/healthz           # 组件健康
curl http://localhost:9091/metrics           # Prometheus 指标（见 08 模块）

# 常见启动失败
# ① vm.max_map_count 不足 → 日志报 mmap 相关错误 → 调 sysctl
# ② etcd 未就绪 → 检查 etcd 健康（单机 compose 里 etcd 最先起）
# ③ 数据卷权限 → MinIO/etcd 目录权限
```

> 🎯 **核心要点**：部署前置的"**一个必查 + 一个必设**"——`vm.max_map_count=262144`（不设启动失败）与内存下限——其余问题大多能在 `/healthz` 与日志中定位。
