## 3. 核心概念速查

### 3.1 核心指标

| 指标 | 含义 | 生产参考 |
|------|------|---------|
| Recall@K | 召回率（Top-K 中相关占比） | **0.95 生产甜点**（0.99 代价 2-5 倍延迟） |
| QPS | 每秒查询数 | 按业务定 |
| P95/P99 延迟 | 检索耗时 | HNSW 内存 5-15ms / DiskANN 30-80ms |
| 内存占用 | 索引常驻内存 | 1 亿条 768 维 ≈ 350GB（亿级需磁盘索引） |

### 3.2 索引家族

| 索引 | 定位 | 2026 状态 |
|------|------|:---------:|
| FLAT | 暴力扫描（小数据精确） | 原型 |
| IVF/IVF-PQ | 聚类分桶 + 量化 | 让位 HNSW，量化仍关键 |
| **HNSW** | 图索引（精度/吞吐均衡） | **事实默认** |
| **DiskANN** | 磁盘图索引（亿级） | **亿级标配**（Milvus/pgvectorscale） |

### 3.3 五条赛道

| 赛道 | 代表 | 一句话 |
|------|------|--------|
| 纯向量库 | Milvus/Qdrant/Weaviate/Pinecone | 专用能力 |
| 关系型扩展 | **pgvector** | SQL 统一 + 零新增 |
| 搜索扩展 | Elasticsearch/OpenSearch | 全文 + 向量一体 |
| NoSQL 扩展 | MongoDB/Redis | 既有栈内嵌 |
| 算法库 | FAISS/DiskANN | 索引组件 |

## 4. 2026 格局速查

**双轨并行 + 商品化**（2026-08 检索核实）：

| 趋势 | 说明 |
|------|------|
| 商品化 | 向量库从"新兴技术"变为"基础设施"（RAG 成熟） |
| 双轨并行 | 独立向量库 vs 通用库向量化（pgvector 崛起） |
| **混合检索刚需** | BM25 + 稠密 + RRF 是生产标配（纯语义不够） |
| **pgvector 默认起点** | 已有 Postgres 且 <5000 万向量 → 零新增基础设施 |
| **DiskANN 亿级标配** | 突破内存限制（Milvus/pgvectorscale 支持） |
| 融合型（SQL+AI） | 金仓/OceanBase 等原生向量能力（高合规场景） |
| 选型核心 | **向量与关系数据的关联程度**（而非"谁快"） |

**各产品定位一句话**：

```text
Milvus：十亿级云原生（运维成本最高，杀鸡不用牛刀）
Qdrant：自托管性价比之王（Rust、过滤原生最强）
Weaviate：混合检索最成熟（原生 BM25+RRF）
pgvector：门槛最低（HNSW 后性能接近专用库，5000 万上限）
Pinecone：全托管（快速验证，锁定 + 规模化成本）
Chroma/FAISS：原型/嵌入式
```

## 5. 学习路线

**路线一：概念与原理（1~2 天，01-02）**
概述与指标 → 索引原理（重点 HNSW 与 DiskANN 的 2026 定位）——理解"召回/延迟/内存"三角。

**路线二：实战上手（2~3 天，03-06）**
Chroma 原型 → Milvus 生产部署 → FAISS 索引 → 云服务对比；选一条主路径（生产推荐 Milvus 或 Qdrant）跑通"入库 → 检索"。

**路线三：工程与选型（1 周，07-09）**
性能优化 → 选型对比（结合 2026 格局）→ RAG 集成；结合 `Milvus/` 专题系统（深度）与 `02-RAG检索增强生成/`（检索策略）形成完整认知。

> 🎯 **核心要点**：向量库学习的终点 = "**懂指标（召回/延迟/内存）、会选型（按数据架构）、能调优（索引/混合/过滤）**"——2026 年选型的第一问不是"哪个库最强"，而是"**我的数据在哪里、和关系数据什么关系**"。

## 6. 常见误区

| 误区 | 真相 |
|------|------|
| "向量库就是更好的 FAISS" | 库管数据生命周期（写入/过滤/并发/事务），FAISS 只是索引组件 |
| "索引越快越好" | 召回率 0.95 → 0.99 要付 2-5 倍延迟与 1.5-3 倍内存——生产 0.95 足够 |
| "亿级数据必须用分布式" | **DiskANN 磁盘索引**让单机也能处理亿级（延迟换成本） |
| "专用向量库一定更好" | 数据与关系表强关联时，**pgvector 一条 SQL 搞定**更优 |
| "混合检索是加分项" | 2026 已从加分项变为**刚需**（精确 SKU/术语查询） |
| "先搜索后过滤没关系" | 高度选择性过滤下"先搜后滤"伤害召回——选"过滤原生"的库（Qdrant） |
| "基准测试决定选型" | 用**真实数据 + 真实过滤条件**做 POC，别信基准测试 |
| "向量库会取代全文检索" | 二者互补——BM25 管精确、向量管语义，混合才是正解 |
