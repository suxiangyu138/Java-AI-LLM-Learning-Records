# 向量索引与检索原理

> VECTOR 字段定义、HNSW/FLAT/SVS-VAMANA 三种索引、KNN 查询语法、距离度量与分数语义——Redis 8 向量检索的全部

## 1. VECTOR 字段定义

向量字段在 `FT.CREATE` 的 SCHEMA 里声明，核心参数：

```bash
FT.CREATE idx:vec ON JSON PREFIX 1 item:
  SCHEMA
    $.embedding AS embedding VECTOR HNSW 6 TYPE FLOAT32 DIM 768 DISTANCE_METRIC COSINE
```

| 参数 | 取值 | 说明 |
|------|------|------|
| 算法 | HNSW / FLAT / SVS-VAMANA（8.4） | 近似/精确/大规模 |
| TYPE | FLOAT32（当前支持） | 向量精度 |
| DIM | 维度数 | 与 embedding 模型一致（硬约束） |
| DISTANCE_METRIC | COSINE / L2 / IP | 距离度量，创建后不可变 |

存储形态差异：**JSON 文档里向量是浮点数组**（`[0.1, 0.2, ...]`），**Hash 里是原始二进制**（应用层序列化）。查询时两者都传字节 blob（`PARAMS` 传参）——维度必须与 DIM 匹配，这是最常见的报错点。

## 2. 三种索引算法

| 算法 | 检索方式 | 召回 | 适用规模 | 说明 |
|------|---------|:----:|---------|------|
| **FLAT** | 暴力全扫 | 100% 精确 | <10 万 | 小数据集/精确需求 |
| **HNSW** | 分层图近似 | 高 | 万-百万级 | **生产默认** |
| **SVS-VAMANA** | 图近似（8.4 新增） | 高 | 大规模 | 内存更优 |

选型判断：**默认 HNSW**（召回/速度/内存平衡）；**<10 万且要精确**用 FLAT（全扫更省事且无近似误差）；**大规模 + 内存敏感**评估 SVS-VAMANA（8.4 新索引，针对超大向量集优化）。与 Chroma/Qdrant 的 HNSW 同源（分层图、逐层下钻），参数语义一致——HNSW 原理详见 `04-向量数据库/` 通用体系的索引原理篇。

选型决策树（向量索引三选一）：**数据 <10 万且要精确** → FLAT；**10 万-百万级** → HNSW（生产默认，调 EF_RUNTIME 控召回）；**百万级以上且内存敏感** → 评估 SVS-VAMANA（8.4）或换独立向量库（Qdrant 有量化，内存账更优）——**Redis 8 的向量规模红线在百万级附近**（无量化 + 缓存同池），超过先评估"换库"而非"硬撑"（09 篇决策树同源结论）。

## 3. HNSW 参数与调优

| 参数 | 阶段 | 默认 | 调大后果 |
|------|------|:----:|---------|
| `M` | 建图 | 16 | 召回↑、内存↑、建图慢 |
| `EF_CONSTRUCTION` | 建图 | 200 | 索引质量↑、构建慢 |
| `EF_RUNTIME` | 查询 | 10 | 召回↑、查询慢（可运行时调） |

```bash
# 建索引时指定
FT.CREATE idx:vec ... VECTOR HNSW 10 TYPE FLOAT32 DIM 768 DISTANCE_METRIC COSINE
  # 第 10 个参数位后是键值对：M 16 EF_CONSTRUCTION 200
  M 16 EF_CONSTRUCTION 200

# 查询期调 EF_RUNTIME：PARAMS 里传
FT.SEARCH idx:vec "*=>[KNN 10 @embedding $vec EF_RUNTIME 100]"
  PARAMS 2 vec $blob DIALECT 2
```

调优逻辑与三套向量库体系一致：**召回不足先调 EF_RUNTIME**（查询参数，免费）；建图质量不够动 EF_CONSTRUCTION（需重建索引）；M 是最后手段。注意 **EF_RUNTIME 默认仅 10**——生产环境按数据集大小调到 50-200，默认值偏保守。调优的工程节奏：**先小数据验证 EF_RUNTIME 的召回-延迟曲线**（100 条标注集，ef 10/50/100/200 各跑一轮），定出"召回够用的最小 ef"再上线——与 Chroma/Qdrant/PgVector 体系的调优方法论一致（先查询参数、再建图参数、最后 M），四套体系共用"每轮只动一个变量 + 标注集验证"的纪律。

## 4. KNN 查询语法详解

```bash
FT.SEARCH idx:vec "<主过滤查询>=>[KNN <k> @<向量字段> $<参数> [AS <距离字段>]]"
  PARAMS <数量> <参数名> <向量字节>
  SORTBY <距离字段>
  DIALECT 2
```

各部分语义：**主过滤查询**（`*` = 全部，或 `@category:{jvm}` 等过滤条件，见 06 篇混合查询）；**KNN 子句**（k = 返回条数、向量字段、字节参数）；**距离字段**（默认 `__<字段>_score`，`AS score` 改名后 `SORTBY score`）；**分数语义**：距离越小越相似（COSINE 距离 = 1 - 余弦相似度）——与 Chroma/PgVector 的"cosine 越大越近"**方向相反**，跨库迁移阈值时必踩。

## 5. Embedding 管道配合

Redis 8 **不内置 embedding 生成**（对比 Milvus 的集成管道）——向量化是应用侧职责（与 Chroma/Qdrant/PgVector 体系一致）：文本 → Embedding 模型 → 字节 blob → Redis。三个工程要点：

1. **模型与 DIM 绑定**：换模型 = 换维度 = 重建索引——索引名带模型名（`idx:docs_bge`），换模型建新索引（与三套体系"模型名入命名"纪律同源）。
2. **写入节奏**：批量 `JSON.SET`/`HSET`（管道或事务批量），索引异步同步——大批量入库后 `FT.INFO` 确认 `indexing` 完成再查询（同步滞后是新数据查不到的常见原因）。
3. **向量字节缓存**：同一文本的 embedding 结果可缓存（文本指纹 → 向量），避免重复调用模型——大文档库入库时省一半模型调用（与语义缓存同思路，应用层实现）。

## 6. 查询执行与内存心智

- **执行模式**：KNN 先按图/全扫取近似候选，再套主过滤（HNSW 是近似路径）；过滤极强时退化为"先过滤后暴力"（见 06 篇优化模式）。
- **内存账**：向量本体（float32 = DIM × 4 字节 × 条数）+ HNSW 图链接 + 索引结构——与 Chroma/Qdrant 同数量级（1M 条 768 维 ≈ 3GB 本体 + 图开销），Redis 还叠加"缓存数据同池"——**Redis 的向量规模上限 = 内存预算减去业务数据占用**。

内存优化的四个实践：**控制维度**（768 维模型比 1536 维省一半——检索质量可接受时优先低维模型）；**控制文档冗余**（向量字段只存必须的，别把全文塞进 JSON 文档——全文走 TEXT 索引的倒排，不重复存原文）；**INITIAL_CAP 预分配**（建索引时按预估条数设 `INITIAL_CAP`，减少索引增长期的重分配）；**冷热分离**（热向量在 Redis、冷向量归档磁盘存储——Redis 只做"活跃检索集"，与 09 篇的"缓存层向量"定位一致）。
- **无量化**：Redis 8 的向量索引无内置量化（对比 Qdrant 的 TurboQuant）——内存敏感场景优先评估"向量单独存"或换 Qdrant。

规模心智与四套向量库体系对齐：**1M 条 768 维 float32 ≈ 3GB 本体 + 约 1GB 图结构**（与 Chroma/Qdrant/PgVector 同数量级）——Redis 的差异在"叠加缓存数据同池"：**向量规模上限 = 内存预算 − 业务数据 − 缓存**。示例：8GB 内存实例、业务数据 3GB、缓存 2GB → 向量预算只剩 3GB ≈ 75 万条 768 维——**先算这笔账再决定向量规模**，这就是 09 篇"内存账先算再定"的来源。超预算的三条路：降维（768→384 省一半）、冷热分离（热向量在 Redis）、换 Qdrant（量化 + 独立内存）。

> 🎯 **核心要点**：VECTOR 字段五参数（算法/TYPE/DIM/度量）；HNSW 生产默认、FLAT 精确小规模、SVS-VAMANA 大规模；调参顺序 EF_RUNTIME → EF_CONSTRUCTION → M；KNN 距离字段默认 `__xxx_score` 且**越小越近**（与 cosine 直觉相反）；无量化 + 缓存同池 = 内存预算双重约束。
