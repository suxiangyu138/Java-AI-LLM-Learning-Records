# 选型对比与决策

> Redis 8 vs Chroma / Qdrant / PgVector——"已有 Redis"的第一决策变量、语义缓存独有红利、规模红线，最终落到决策树

## 1. 竞品全景与定位差异

Redis 8 的定位是"**缓存型多模型数据库**"——向量是它的一个模型，不是全部。对照四象限：Chroma（嵌入式）、PgVector（PG 扩展）、Qdrant（独立服务）、**Redis 8（缓存 + 多模型）**。

| 维度 | Redis 8 | Chroma 1.5.x | Qdrant 1.19 | PgVector 0.8.x |
|------|---------|-------------|-------------|----------------|
| 形态 | 缓存 + 多模型 | 嵌入式 | 独立服务 | PG 扩展 |
| 部署成本 | 零（已有 Redis） | 零（pip） | 低（Docker） | 零（已有 PG） |
| 规模 | 内存约束（百万级） | 1-2M | 集群亿级 | 50M-100M |
| 混合查询 | **pre-filter + KNN / FT.HYBRID** | post-filter | 过滤感知 | post-filter（缓解） |
| 全文检索 | **原生（BM25）** | 弱 | 弱 | 原生（FTS） |
| 语义缓存 | **独有** | 无 | 无 | 无 |
| 量化 | 无 | 无 | TurboQuant/Turbo4 | binary/halfvec |
| Java 生态 | Spring AI/Data Redis/OM/Redisson | Spring AI | 官方客户端/LangChain4j | Spring AI |

## 2. 逐个竞品的取舍分析

**vs Chroma**：Chroma 是"嵌入最省事"（pip 即用、磁盘持久化），Redis 8 是"已有 Redis 最省事"。分水岭：**有没有 Redis、要不要缓存能力**——有 Redis 且向量规模可控，Redis 8 白赚缓存/全文/语义缓存；纯原型无 Redis 依赖，Chroma 上手更快。**规模上 Redis 受内存约束**（缓存数据与向量同池），Chroma 落盘可超内存——数据量大的向量库场景 Chroma 反而更稳。

**vs Qdrant**：Qdrant 是"纯向量库"最强形态——过滤感知、量化、分布式集群，向量专业度全面领先。Redis 8 的相对优势只剩两点：**已有 Redis 零新增**与**语义缓存独有**。判断：**向量是核心资产、规模持续增长 → Qdrant**；**向量是应用的辅助功能 + 已有 Redis → Redis 8 够用**（语义缓存的红利只此一家）。

**vs PgVector**：PgVector 白赚 SQL/事务/备份，Redis 8 白赚缓存/全文/语义缓存——**两者都吃"已有基础设施"红利，分水岭在已有哪个**。补充差异：PgVector 可落盘（规模上限高一个量级）、Redis 8 检索性能更极致（内存 + 单线程低延迟）、混合查询更强（pre-filter vs post-filter）。判断：**已有 PG → PgVector；已有 Redis → Redis 8**；两者都有 → 向量是核心 → PgVector（持久化稳），检索延迟敏感 + 语义缓存 → Redis 8。

**vs Milvus**：Milvus 是十亿级分布式答案——Redis 8 与它几乎不构成竞争（规模差三个量级）；Redis 8 只做"缓存层向量"（热数据 + 语义缓存），Milvus 做"核心向量资产"。

## 3. Redis 8 的甜区与红线

**甜区（选它没错）**：已有 Redis 基础设施（最常见场景）；语义缓存是刚需（RAG 降本）；混合查询（全文 + 过滤 + 向量一条命令）；向量规模在百万级内（内存可控）；"一个实例覆盖缓存 + 数据 + 向量"的运维收敛诉求。

**红线（别选它）**：向量是核心资产且规模持续增长（内存红线 + 无量化）；需要磁盘级持久化向量（Redis 是内存优先设计）；多节点分布式向量（Redis Cluster 的向量索引能力有限，对比 Qdrant/Milvus）；强一致 + 复杂事务的向量场景（Redis 无事务性向量操作）。

## 4. 三个典型选型场景（推演）

**场景 A：已有 Redis 的业务系统加"语义搜索"**。数据百万级、缓存已是 Redis、团队不想新增服务。**Redis 8 是默认答案**——FT 索引 + KNN 一条命令接入，语义缓存顺带降本；零新增基础设施（与 PgVector 体系的场景 A 同构，只是"已有 PG"换成"已有 Redis"）。

**场景 B：RAG 平台 + 语义缓存降本**。问答量大、重复问题占比高、LLM 成本敏感。**Redis 8 的语义缓存是不可替代项**（相似问题命中缓存，成本直降 30%+）——即使主向量库是 Qdrant，语义缓存层仍建议 Redis（08 篇的缓存架构）。

**场景 C：亿级向量核心资产**。文档规模增长快、需要分布式与量化。**Redis 8 出局**——内存账算不平（无量化 + 缓存同池），选 Qdrant（量化 + 集群）或 Milvus（十亿级）。

## 5. 选型决策树

```text
已有 Redis 且向量规模可控（百万级内）？
├── 是 → 语义缓存是刚需？ → 是：Redis 8（独有）
│        向量是辅助功能？ → 是：Redis 8（零新增）
│        向量是核心资产？ → Qdrant（或 PgVector，看已有基础设施）
├── 否 → 已有 PG？ → PgVector
│       已有 Redis 但规模会涨？ → 评估 Qdrant（先缓存层用 Redis）
│       原型/无基础设施 → Chroma
│       十亿级/分布式 → Milvus
```

决策纪律（与三套向量库体系共用）：**选型写 ADR**（背景/备选/决策/触发条件/回滚路径）；**用 Spring AI VectorStore 抽象保留换库路径**；**内存账先算再定**（Redis 向量规模 = 内存预算减缓存占用——触发条件之一写成"内存占用 > 70%"）。执行纪律：决策树输出"选型 + 边界 + 触发信号"三件套，触发信号写成可观测指标（内存占用、向量规模预测、语义缓存命中率）——指标破线启动评审，而不是等故障驱动复盘；ADR 进版本管理（docs/adr/），半年后的选型复盘回头看"百万级"分界线是否还成立——选型是过程不是结论。语义缓存的价值评估要单独写进 ADR 的收益项（命中率 30% = LLM 成本降 30%——这是 Redis 8 相对其他向量库的独有收益，决策时量化进去）。

成本三本账：**机器账**——Redis 8 零新增服务（已有 Redis 的场景机器成本为 0），但向量 + 缓存同池的内存增长要按"1M 条 768 维 ≈ 4GB"预算（无量化，只能控规模）；**运维账**——零新增是最大红利（备份/监控/高可用全复用 Redis 体系），代价是向量规模红线（超线要引入第二个存储，运维面反而变大）；**迁移账**——从 Stack 迁 8 是命令兼容的（三查后无感），从 Redis 向量迁 Qdrant 是数据重放（同向量重写，业务代码经 VectorStore 抽象趋近于零）——**触发条件写清"什么时候加 Qdrant"**（内存 >70% 或向量规模预测破百万），指标破线启动评审而不是等故障。

> 🎯 **核心要点**：Redis 8 的甜区 = "已有 Redis + 百万级内 + 语义缓存刚需"；vs Chroma（有无 Redis）、vs PgVector（已有哪个基础设施）、vs Qdrant（向量专业度）三个分界线是选型锚点；语义缓存是独有不可替代项；内存账（向量 + 缓存同池）是 Redis 向量规模的硬约束。
