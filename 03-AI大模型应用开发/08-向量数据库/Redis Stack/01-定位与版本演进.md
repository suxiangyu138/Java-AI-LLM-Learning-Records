# 定位与版本演进

> 先回答三个问题：Redis Stack 是什么？为什么 2025 年并入 Redis 8？2026 年用"Redis Stack"意味着什么？

## 1. 历史定位：模块化时代的 Redis Stack

Redis Stack 是 Redis 官方的**模块集合发行版**，把四个能力模块打包分发：**RediSearch**（全文搜索 + 二级索引 + 向量检索）、**RedisJSON**（原生 JSON 文档）、**RedisTimeSeries**（时序数据）、**RedisBloom**（概率数据结构）。

它的存在解决了 Redis 本体"只有键值结构"的短板——让 Redis 从缓存中间件升级为"多模型数据库"。

Stack 时代的形态：独立发行版（`redis-stack-server` 二进制或 Docker 镜像 `redis/redis-stack`），模块可加载（`loadmodule` 配置）、版本与 Redis 本体解耦、维护独立的版本矩阵（6.2/7.2/7.4 三线并行）。

## 2. 范式合并：Redis 8.0（2025-05-02）

2025 年 5 月，Redis 官方发布 **Redis 8.0**：Redis Stack 与 Redis Community Edition（CE）合并为统一的 **Redis Open Source** 发行版——**"Redis Stack"作为独立产品不复存在**。

合并带来的四个根本变化：

1. **模块内置**：搜索、JSON、时序、Bloom 全部编译进 Redis 8 核心，无需 `loadmodule`、无需模块版本矩阵。
2. **版本统一**：一个二进制、一个版本号、一条升级路径——不再有"Redis 7.4 + RediSearch 2.10"式的组合核对。
3. **API 演进**：`FT.SEARCH` 默认打分从 TF-IDF 改为 **BM25**；`FT.ADD`/`FT.DEL`/`FT.SYNADD` 等一批旧命令弃用（04 篇细讲）。
4. **ACL 变化**：模块命令归入标准 `@read`/`@write` 类别——存量 ACL 规则可能意外放行或拦截，必须重审（10 篇迁移清单）。

配套的硬事实：**Redis Stack 维护版（6.2/7.2/7.4）已于 2025 年 12 月停止维护**——任何还在跑 Redis Stack 的部署已无安全补丁，迁移到 Redis 8 是安全必选项而非可选项。

合并对存量用户的三个直接影响：**Docker 镜像**（`redis/redis-stack` 不再更新，换 `redis:8.x`）；**模块配置**（`loadmodule` 指令移除，模块随核心分发）；**命令行为**（BM25 默认打分、FT.* 旧命令弃用——存量查询脚本的排序结果与报错行为可能变化）。存量用户迁移的完整清单见 10 篇，这里记住结论：**命令兼容、配置要改、行为要验**。

## 3. 2026 版本线：8.0 → 8.2 → 8.4

| 版本 | 时间 | 关键变化 |
|------|:----:|---------|
| **8.0** | 2025-05-02 | 合并发行；搜索/JSON/时序/Bloom 内置；BM25 默认；Vector Set（beta）引入 |
| 8.0.6 | 2026-02-22 | 8.0 分支最新稳定版 |
| 8.2 | 2026-03 | 大版本增强（IBM Cloud 等托管平台 GA） |
| **8.4** | 2026 | **FT.HYBRID（词法+向量双腿 RRF 融合）、SVS-VAMANA 向量索引、Vector Set 成熟** |

2026 年 8.x 的开发主线是 **AI 原生能力**（2025-11 起六个月持续迭代）：向量搜索、Vector Set、语义缓存、多线程 IO（命令延迟最高降 87%、吞吐约 2 倍）。**业务数据 + 缓存 + 向量同库同实例**是 Redis 8 的定位宣言——"不需要再单独部署 Milvus/Qdrant/Pinecone"。性能数字的工程含义：**同一实例同时扛缓存读写与向量检索**（多线程 IO 解耦了吞吐瓶颈），对比"缓存 + 独立向量库"的双服务架构，Redis 8 少一跳网络、少一个运维面——这是"零新增"红利的量化版本。

## 4. 2026 年"Redis Stack"的正确理解

2026 年谈"Redis Stack"有两个含义，必须分清：

1. **历史产品**（已停更）：`redis/redis-stack` 镜像、Stack 版本矩阵——**新项目一律不用**。
2. **能力集合**（已内置）：搜索、JSON、时序、Bloom、向量——即 Redis 8 核心能力，本体系按此撰写。

实战含义：文档与代码示例里的 `FT.*`/`JSON.*` 命令在 Redis 8 直接可用（RDB 文件兼容、绝大多数命令无感迁移）；需要检查的只有三处——**ACL 规则、弃用的 `FT.*` 命令、`loadmodule` 配置移除**（10 篇迁移清单细讲）。

## 5. 许可变化与生态影响

Redis 8 采用**三许可并存**：RSALv2（Redis Source Available License）、SSPLv1（Server Side Public License）、**AGPLv3（2025 新增，OSI 批准的开源选项）**——用户可按合规需求选择许可。工程影响两条：**云厂商托管**（AWS/IBM Cloud 等）已支持 Redis 8（IBM Cloud 2026-03 提供 8.2）——托管环境的许可风险由平台消化；**自建部署**按团队合规偏好选许可（AGPLv3 是 OSI 开源路径）。

生态配套（2026 现状）：客户端库全部兼容（Jedis/Lettuce/Redisson/Spring Data Redis 均支持 8.x）；Redis Insight（官方 GUI）是排查向量索引的标配工具（8001 端口）；Spring AI 2.0 的 RedisVectorStore 以 Redis 8 为基准开发——生态成熟度不构成选型障碍。

## 6. 与 Redis 主体系的分工

`02-.../02-非关系型数据库/Redis/` 主体系讲 Redis 本体：数据结构、持久化、集群、缓存策略、Lua、高可用。本体系讲 **Redis 8 的搜索与向量能力**：RediSearch 全文检索、向量索引与 KNN、混合查询、Vector Set、Spring AI 集成——两体系互补，**读本体系前先过主体系的"Redis 核心概念"篇**（命令模型、内存模型、持久化是搜索能力的地基）。

## 7. 定位总结：Redis 8 在向量谱系中的位置

Redis 8 是"**缓存型多模型数据库**"——向量能力是它的一个模型，不是全部。对照四象限：Chroma（嵌入式）、PgVector（PG 扩展）、Qdrant（独立服务）、**Redis 8（缓存 + 多模型）**。它的独特性：**语义缓存**（向量相似度命中缓存）只有缓存型存储能天然提供；代价是**规模与专业度**让位给独立向量库（内存约束、无持久化优先设计）。定位一句话：**"已有 Redis + 向量规模可控"场景的第一候选，语义缓存场景的唯一候选**（09 篇决策树细讲）。对比四套向量库体系的定位结论：Chroma（嵌入式原型）、PgVector（已有 PG）、Qdrant（向量核心资产）、Redis 8（已有 Redis + 缓存红利）——**四套体系按"已有基础设施"与"向量定位"两个维度互斥互补**，选型时先答"我有什么"，再答"向量是什么地位"。

> 🎯 **核心要点**：Redis Stack 已于 2025-05 并入 Redis 8（模块内置、版本统一、Stack 停更）；2026 年"Redis Stack"= Redis 8 能力集合；迁移三查（ACL/FT.* 弃用/loadmodule）；定位是"缓存型多模型"，语义缓存是独有红利。
