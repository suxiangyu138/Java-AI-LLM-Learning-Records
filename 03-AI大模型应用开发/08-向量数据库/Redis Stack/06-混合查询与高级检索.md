# 混合查询与高级检索

> pre-filter + KNN、FT.HYBRID（8.4 双腿 RRF 融合）、向量范围检索、查询优化模式——检索质量与性能的操纵杆

## 1. pre-filter + KNN：过滤感知的向量检索

混合查询把"业务过滤"与"向量相似"放在一条命令：过滤条件是 KNN 子句前的**主查询**。

```bash
# 场景：jvm 分类 + 2024 年后 + 语义相似
FT.SEARCH idx:docs "@category:{jvm} @year:[2024 +inf]=>[KNN 10 @embedding $vec AS score]"
  PARAMS 2 vec $blob
  SORTBY score
  DIALECT 2
```

执行机制（Redis 自动二选一）：**batches 模式**——批量取高分向量，只保留通过过滤的（HNSW 近似路径，过滤中等时高效）；**ad-hoc 暴力模式**——对全部通过过滤的向量精确打分（过滤集合很小时触发，**即使 HNSW 索引也 100% 准确**）。

工程含义三条：**过滤是 pre-filter 而非 post-filter**（过滤进查询路径，不吞召回——与 Qdrant 的过滤感知同思路，优于 Chroma/PgVector 的 post-filter）；**强过滤时自动暴力模式**（过滤集小到暴力更快且精确，这是 Redis 混合查询的性能自调节）；**过滤字段必须建索引**（TAG/NUMERIC 声明进 SCHEMA，未索引字段无法参与主查询）。

## 2. FT.HYBRID（8.4）：词法 + 向量双腿融合

8.4 引入专用命令 `FT.HYBRID`：显式的**双腿查询**（词法路 + 向量路）+ **融合阶段**（RRF 或线性加权）：

```bash
FT.HYBRID idx:docs
  SEARCH "@title:transformers" SCORER BM25 YIELD_SCORE_AS lexscore   # 词法腿
  VSIM embedding $vec KNN count 1 K 50 YIELD_SCORE_AS vecscore       # 向量腿
  COMBINE RRF 2 CONSTANT 60                                          # RRF 融合（k=60）
  PARAMS 2 vec "..."
```

各段语义：**SEARCH 腿**（词法检索，可带 SCORER 与过滤）；**VSIM 腿**（向量 KNN，K 是候选量）；**COMBINE**（`RRF 数量 CONSTANT k` 排名倒数融合，或 `LINEAR` 线性加权）——与 Qdrant 的 prefetch + FusionQuery、PgVector 的 SQL RRF 同构，只是做成了 Redis 原生命令。

适用场景：**语义 + 关键词双路召回**（RAG 标准形态，词法路保专有名词、向量路保语义泛化）；Redis < 8.4 的等价实现是"主查询过滤 + KNN"（06 篇第 1 节）或应用层双查询 RRF 融合。

## 3. 向量范围检索 VECTOR_RANGE

按"距离半径"而非"top-k"检索：

```bash
FT.SEARCH idx:vec "@embedding:[VECTOR_RANGE 0.2 $vec]=>[KNN 100 @embedding $vec]"
  PARAMS 2 vec $blob
  DIALECT 2
```

语义：返回与查询向量距离 **≤ 0.2** 的全部文档（配合 `LIMIT` 控制返回量）。适用场景：**相似度阈值业务**（"相似度低于阈值的不算命中"——与 Spring AI 的 `similarityThreshold` 同语义，库内实现）；范围检索与 KNN 可叠加（范围内取 top-k）。

## 4. 聚合查询 FT.AGGREGATE

```bash
FT.AGGREGATE idx:docs "*"
  GROUPBY 1 @category
  REDUCE COUNT 0 AS count
  SORTBY 2 @count DESC
  DIALECT 2
```

聚合语法：**GROUPBY 分组字段 → REDUCE 聚合函数（COUNT/SUM/AVG/MIN/MAX）→ SORTBY 排序**——替代应用层"拉全量再统计"（与 Qdrant 的 GroupBy、PgVector 的 SQL GROUP BY 对应）。`APPLY` 步骤可做字段计算（时间格式化、数学运算），复杂聚合场景的补充。

聚合的实战场景：**按分类统计命中数**（`GROUPBY 1 @category REDUCE COUNT 0`——"每分类多少文档"）；**按时间桶统计**（`APPLY` 把时间戳截断到小时再 GROUPBY——"每小时检索量"）；**向量 + 聚合组合**（KNN 结果集上做 GROUPBY——"每租户 top-k"的库内实现）。注意聚合是**内存内执行**（全量数据在内存——大数据集聚合评估内存账，超大聚合集用 `LOAD` 控制字段载入）。

## 5. 查询优化与性能心智

- **混合查询的选择**：过滤强（命中集小）→ 主查询 + KNN 自动暴力模式；双路召回 → FT.HYBRID；阈值业务 → VECTOR_RANGE。
- **候选量设置**：FT.HYBRID 的 VSIM K 取目标 top-k 的 2-5 倍（融合后有富余，与 Qdrant prefetch 同纪律）。
- **EXPLAIN 等价**：`FT.EXPLAIN idx:docs "<查询>"` 输出查询执行树——排查"为什么这个查询慢/结果不对"的第一工具。
- **内存与延迟**：KNN 候选量大、过滤字段多会放大执行时间——压测用 `redis-benchmark` 带 FT.SEARCH 场景；P95 监控进面板（向量查询波动大，P95 比均值诚实）。

FT.EXPLAIN 的实际用法与解读：

```bash
FT.EXPLAIN idx:docs "@category:{jvm}=>[KNN 10 @embedding $vec]"
# 输出示例（执行树）：
#   INTERSECT {
#     @category:{jvm}         ← TAG 过滤先执行（收窄候选）
#     KNN 10 @embedding       ← 再向量近邻
#   }
```

执行树读法：**过滤在向量之前**（pre-filter 语义的直观证据）；`INTERSECT`/`UNION` 显示组合方式；节点顺序即执行顺序——**过滤条件顺序影响性能**（选择性强的过滤放前面先收窄，KNN 的候选量就小）。调优流程：FT.EXPLAIN 看结构 → FT.INFO 看统计 → 改过滤顺序/候选量 → 复测 P95。

混合检索的评估闭环（与四套向量库体系共用方法论）：**100-200 条标注问答对**（问题 → 期望命中的文档 id）→ 跑三种形态（纯向量 / 纯词法 / FT.HYBRID）→ 统计**命中率**（top-5 是否含期望 id）与 **MRR**（期望 id 排名倒数均值）→ 参数变更（候选量、RRF 常数、过滤条件）触发重跑。评估脚本进 CI——**"混合检索提升多少"用自己数据的指标回答**；与 Qdrant 的 prefetch+RRF、PgVector 的 SQL RRF 是同一套方法论，标注集可共用。

混合检索 vs 纯向量（Redis 场景）：**词法腿的价值在专有名词与型号**——中文场景尤其明显（向量对"JVM 参数"这类精确词不敏感，词法腿直接命中）；**词法腿的代价是查询复杂度**（双腿 + 融合，参数多一套）——评估结论"混合提升 <5%"时直接用纯向量 + 过滤，别为仪式感上 FT.HYBRID；评估结论"提升 >10%"时混合是标配——**指标决定架构，不是趋势决定架构**。

查询优化的量化基准（给调优一个起点）：**单条 KNN 查询的 p95 目标 <10ms**（内存数据 + 万级索引的正常水平，超了先查 EF_RUNTIME 与候选量）；**混合查询的延迟 ≈ 词法腿 + 向量腿 + 融合**（两腿各跑各的，融合是内存内排名——预算延迟时两条腿分开压测）；**批量查询用管道**（客户端 pipeline 合并多条 FT.SEARCH——单线程模型下管道吞吐提升显著）。基准数字只能给量级，**上线前用自己数据压测**（redis-benchmark 自定义 FT.SEARCH 场景），与四套向量库体系的"自己数据说话"纪律一致。混合查询的调优顺序建议：先定词法腿与向量腿各自的候选量（各 2-5 倍目标 top-k）→ 再定 RRF 常数（60 起步）→ 最后调 EF_RUNTIME——每轮只动一个变量，指标回归可归因。

> 🎯 **核心要点**：pre-filter + KNN 是过滤感知检索（强过滤自动暴力精确模式）；FT.HYBRID（8.4）是双腿 RRF 融合的原生实现；VECTOR_RANGE 做阈值业务；FT.AGGREGATE 做库内聚合；候选量 2-5 倍 + FT.EXPLAIN 是调优两件套。
