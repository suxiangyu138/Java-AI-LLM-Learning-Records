# 生产实践与面试题

> 迁移三查、避坑清单、生产清单、面试弹药——验收你是否真的能上生产

## 1. 性能真相

用数据校准预期（Redis 8，2026 基线）：**延迟**——8.x 多线程 IO 后命令延迟最高降 87%、吞吐约 2 倍（对比 7.x），向量 KNN 在内存数据上毫秒级返回（数据规模内）；**内存**——向量本体（float32 = DIM × 4 字节 × 条数）+ HNSW 图开销 + **缓存数据同池**（向量规模 = 内存预算减业务数据，双重约束）；**无量化**——对比 Qdrant 的 TurboQuant（8× 压缩），Redis 8 的内存账只能靠"控制规模"而不是"压缩"；**全文**——BM25 打分原生，分词后的检索延迟与倒排索引大小相关。

## 2. 迁移三查（Stack → Redis 8）

从 Redis Stack 迁移到 Redis 8 只需检查三件事（其余命令/RDB 兼容）：

1. **ACL 规则**：模块命令（FT./JSON./TS./BF.）归入标准 `@read`/`@write` 类别——存量 ACL 可能意外放行（原模块命令不在类别里）或拦截（新归类后受类别限制），**逐条重审 ACL**。
2. **弃用命令**：`FT.ADD`/`FT.SAFEADD`/`FT.DEL`/`FT.GET`/`FT.MGET`/`FT.SYNADD`/`FT.DROP`——全局搜索替换为 `FT.CREATE` + `JSON.SET` + `FT.SEARCH` 模式；`FT.SYNADD` 用 `FT.SYNUPDATE`。
3. **loadmodule 配置**：`redis.conf` 里的 `loadmodule` 指令移除（模块已内置，保留会报错或冗余）；`redis-stack` 镜像换 `redis:8.x`。

迁移流程：备份 RDB → 新实例加载（RDB 兼容）→ 三查逐项验证 → 回归测试（查询结果对比）→ 切流。Stack 维护版已停更（2025-12），**迁移不是优化选项而是安全必选**。

## 3. 避坑清单（Top 12）

1. **距离方向写反**：Redis 距离越小越相似（COSINE 距离 = 1 - 相似度）——与 cosine 直觉相反，跨库搬阈值必踩。
2. **`initialize-schema` 默认 false**（Spring AI 2.0）：忘开 = 索引不存在。
3. **维度不匹配**：向量字节数与 `DIM` 不符（4 维 = 16 字节 float32）——JSON 数组 vs Hash 二进制的序列化差异是常见来源。
4. **`DIALECT 1` 语法**：老教程的查询方言——统一 `DIALECT 2`。
5. **EF_RUNTIME 默认 10**：生产按数据集调到 50-200，默认偏保守。
6. **缓存数据与向量同池**：`maxmemory` 淘汰策略可能悄悄清掉向量数据（LRU 对"低频但重要"的向量不友好）——向量场景优先 noeviction 或分区。
7. **Stack 镜像还在用**：`redis/redis-stack` 已停更——换 `redis:8.x`。
8. **FT.* 弃用命令**：存量脚本的 `FT.ADD` 等直接报错或行为变化。
9. **PREFIX 过宽**：把无关 key 拉进索引，索引膨胀 + 同步开销。
10. **Vector Set 上生产**：beta 状态——生产主路径是 FT 向量索引。
11. **语义缓存阈值太低**：误命中 = 答非所问，比 miss 更糟——阈值 0.9+。
12. **中文全文当 ES 用**：Redis 8 的中文分词有限——中文检索主力是向量，全文做辅助。

## 4. 生产落地清单

- 部署：`redis:8.x` 镜像、持久化（AOF/RDB 按业务）、内存预算（向量 + 缓存 + 索引三账）。
- 索引：FT.CREATE 字段类型选型、DIM 与模型一致、PREFIX 精准、EF_RUNTIME 调优。
- 数据：业务主键做文档 ID、TTL 策略、Bloom 去重防重复入库。
- 检索：DIALECT 2、混合查询（pre-filter + KNN / FT.HYBRID）、阈值方向验证。
- 缓存：语义缓存高阈值 + 命中率监控 + 过期策略。
- 安全：ACL 重审（迁移后）、命令权限最小化、Redis Insight 访问控制。
- 监控：内存占用（向量占比）、KNN P95、缓存命中率、索引同步状态（FT.INFO）。
- 增长预案：内存 >70% 触发评估——量化不可用，换 Qdrant 或拆分向量存储，触发条件写进 ADR。

## 5. 面试高频题与答题范式

**Q1：Redis Stack 和 Redis 8 什么关系？**
答：Redis Stack 已于 2025-05 并入 Redis 8.0（Redis Open Source 统一发行版）——搜索/JSON/时序/Bloom 内置核心，Stack 维护版 2025-12 停更。2026 年"Redis Stack"= Redis 8 能力集合；迁移三查：ACL、FT.* 弃用命令、loadmodule。

**Q2：Redis 8 的向量检索怎么做？**
答：FT.CREATE 声明 VECTOR 字段（HNSW/FLAT/SVS-VAMANA + DIM + COSINE/L2/IP）→ 数据写入 Hash/JSON（索引自动同步）→ FT.SEARCH `*=>[KNN k @field $vec]` + PARAMS + SORTBY 距离字段。距离越小越相似。HNSW 三参数：M/EF_CONSTRUCTION/EF_RUNTIME。

**Q3：混合查询怎么实现？比 post-filter 好在哪？**
答：主查询（TAG/NUMERIC 过滤）作为 KNN 子句前缀——`@category:{jvm}=>[KNN 10 @embedding $vec]`。Redis 自动二选一：batches 模式（近似路径）或 ad-hoc 暴力模式（过滤集小，即使 HNSW 也精确）——过滤进查询路径不吞召回。8.4 还有 FT.HYBRID 做词法 + 向量双腿 RRF 融合。

**Q4：语义缓存是什么？为什么 Redis 独有？**
答：缓存键是问题向量而非精确字符串——相似问题（相似度 > 阈值）命中缓存答案，跳过 LLM 调用，成本直降 30%+。Redis 独有因为三合一：向量检索 + 缓存 TTL + 内存高速命中；阈值要高（0.9+），误命中比 miss 更糟。

**Q5：Redis 8 和 Qdrant 怎么选？**
答：Redis 8 甜区 = 已有 Redis + 百万级内 + 语义缓存刚需 + 混合查询；Qdrant 甜区 = 向量核心资产 + 规模增长 + 量化 + 分布式。分界线：内存账（Redis 无量化 + 缓存同池）与专业度（Qdrant 过滤感知/量化/集群）。

**Q6：Java 项目怎么接入 Redis 8 向量？**
答：四条路径——Spring AI `spring-ai-starter-vector-store-redis`（统一 VectorStore 抽象，builder 配 HNSW/度量/前缀）、Spring Data Redis（RedisTemplate 直连）、Redis OM Spring（注解即索引 + 自动向量化）、Redisson 4.2（已有 Redisson 的轻量接入）。

**Q7：向量检索结果召回率下降怎么排查？**
答：四层排查——数据层（embedding 模型是否一致、DIM 是否匹配、PREFIX 是否覆盖新数据）、索引层（FT.INFO 看同步状态、字段类型是否正确声明）、参数层（EF_RUNTIME 是否被调小、DIALECT 是否漂移）、查询层（过滤字段是否建索引、距离方向是否理解反）。先 `FT.EXPLAIN` 看执行树，再验证数据。

**答题范式**：先定位（缓存型多模型 vs 独立向量库）→ 再给原理（索引/混合查询/缓存机制）→ 最后给边界与替代方案。"定位 → 原理 → 边界"三段式，与 Chroma/Qdrant/PgVector 体系共用。

> 🎯 **核心要点**：迁移三查（ACL/FT.* 弃用/loadmodule）是 Stack 存量用户的第一课；十二坑清单覆盖 90% 事故；面试记住"并入 Redis 8"与"语义缓存独有"两个硬考点；答题三段式与向量库体系通用。
