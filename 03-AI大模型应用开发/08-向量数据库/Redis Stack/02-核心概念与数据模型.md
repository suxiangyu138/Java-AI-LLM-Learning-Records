# 核心概念与数据模型

> 四类数据结构 + FT 索引模型 + Vector Set——Redis 8 的多模型数据组织，理解后 FT.* 命令行为可推导

## 1. 四类数据结构

Redis 8 内置四类"高级"数据结构，各有主场：

| 结构 | 数据形态 | 主场场景 | 对应命令族 |
|------|---------|---------|-----------|
| **Hash** | 字段值映射 | 业务对象、向量载体（二进制） | `HSET`/`HGET` |
| **RedisJSON** | 原生 JSON 文档 | 复杂嵌套对象、JSONPath 查询 | `JSON.SET`/`JSON.GET` |
| **RedisTimeSeries** | 时序数据（采样+聚合） | 监控、IoT、金融 | `TS.ADD`/`TS.RANGE` |
| **RedisBloom** | 概率结构 | 去重、基数估计、热榜 | `BF.ADD`/`CMS.INCRBY` |

选型判断：**简单键值对象用 Hash、嵌套文档用 JSON**；向量可存 Hash（二进制）或 JSON（浮点数组）；时序与概率结构按场景按需用。四者共享 Redis 的**单线程命令模型与内存存储**——数据都常驻内存（可选持久化），这是"多模型"与"多数据库"的本质区别：同实例、同内存、同复制。

共享命令模型的三个工程推论：**原子性**（单线程模型下复合命令天然原子——`JSON.SET` + 索引同步无中间态，对比多数据库的事务协调成本为零）；**性能可预测**（无跨库网络开销，检索链路是单实例内的命令执行）；**瓶颈同源**（所有模型的性能瓶颈都是内存与 CPU——向量检索与缓存淘汰争抢同一资源池，容量规划必须一起算）。

## 2. FT 索引模型：索引 → 文档 → 字段

RediSearch（Redis 8 内置）的索引模型：`FT.CREATE` 创建**索引**，索引指向一类**文档**（Hash 或 JSON），文档的**字段**按类型声明进 SCHEMA。索引与数据的关系是"旁路索引"——数据用原生命令写入（`HSET`/`JSON.SET`），索引自动同步更新。

```text
FT.CREATE idx:docs ON JSON PREFIX 1 doc:
  SCHEMA
    $.title AS title TEXT          ← 全文检索字段
    $.category AS category TAG     ← 精确匹配字段（枚举）
    $.price AS price NUMERIC       ← 数值范围字段
    $.embedding AS embedding VECTOR HNSW 6 TYPE FLOAT32 DIM 768 DISTANCE_METRIC COSINE
```

字段类型五族：**TEXT**（全文分词）、**TAG**（精确枚举匹配）、**NUMERIC**（数值范围）、**GEO**（地理位置）、**VECTOR**（向量）。要点：**JSON 字段用 JSONPath 引用**（`$.embedding AS embedding`），Hash 字段直接字段名；**一个索引的字段类型决定查询能力**——全文查询只走 TEXT、过滤走 TAG/NUMERIC、相似度走 VECTOR。

## 3. Vector Set（beta）：一等公民的向量类型

Vector Set 是 Redis 8 引入的**原生向量数据结构**（Redis 创始人 Salvatore Sanfilippo 设计），定位是 Query Engine 向量索引的轻量替代：

```text
VADD key DIM 768 DISTANCE_METRIC COSINE "vector_bytes" [MEMBER "id1"]
VSIM key "query_bytes" COUNT 10
VCARD key / VDIM key / VINFO key
```

与 FT 向量索引的对比：**VSET 是数据即索引**（向量集本身就是检索入口，无需 FT.CREATE 建索引）；FT 向量索引**依附业务文档**（向量与业务字段共存，支持混合查询）。适用判断：**纯向量检索 + 极简语义 → VSET；向量与业务数据关联 + 混合查询 → FT 索引**。注意 VSET 仍是 beta——生产主路径是 Query Engine，VSET 用于原型与轻量场景（07 篇细讲）。

## 4. 文档 ID 与数据一致性

文档 ID 决定索引同步：`PREFIX` 匹配的 key 自动进索引（`doc:1`、`doc:2`），新写入自动索引、删除自动出索引。三个要点：**ID 是业务主键**（幂等覆盖，与 Chroma/PgVector 的"业务主键做 ID"纪律同源）；**PREFIX 要精准**（过宽前缀会把无关 key 拉进索引）；**同步是异步的**（写入返回后索引可能短暂滞后，强一致场景用 `FT.SYNUPDATE` 类命令或接受最终一致）。

## 5. 与关系型/向量库的概念映射

| 概念 | Redis 8 | 类比 |
|------|---------|------|
| 表 | FT 索引 + PREFIX | 表 |
| 行 | Hash/JSON 文档 | 行 |
| 列 | SCHEMA 字段 | 列 |
| 主键 | 文档 key（PREFIX 后段） | 主键 |
| 二级索引 | FT 索引的字段索引 | 索引 |
| 向量列 | VECTOR 字段 | 向量列 |
| 查询 | FT.SEARCH（过滤+全文+KNN） | SQL |

与独立向量库的核心差异：**Redis 没有独立的"集合"概念**——向量是文档的一个字段，检索是"文档级查询"的一部分；**数据常驻内存**（对比 Chroma 的磁盘持久化、PgVector 的 WAL）；**混合查询是原生**（一条命令完成过滤+全文+向量，见 06 篇）。

## 6. 数据生命周期与命名规范

**命名规范**：业务隔离用 key 前缀（`cache:`/`doc:`/`vec:`），索引名用 `idx:` 前缀；一个索引的 PREFIX 不重叠（同一 key 只属于一个索引，避免重复索引与同步混乱）。

**TTL 与淘汰**：向量数据与缓存同池——`maxmemory` 淘汰策略会影响向量索引（被淘汰的文档自动出索引，但索引结构本身常驻），**向量场景优先 noeviction 或按业务设置**，避免 LRU 悄悄清掉"重要但低频"的向量数据。

**删除与过期**：`DEL`/`JSON.DEL` 自动触发索引同步，无需手动维护索引；带 TTL 的文档过期同样自动出索引——"过期即失效"对缓存类数据是特性，对向量资产是风险（向量 TTL 要按业务明确设置，不要依赖默认不过期）。索引本身不占 TTL（索引结构常驻，直到 DROPINDEX）。索引删除与数据删除的边界要清楚：`FT.DROPINDEX` 默认只删索引保留数据（`DD` 参数连数据删）——**误删索引可重建，误删数据不可恢复**，运维脚本里删除操作先确认参数。

**内存账的工程化**：向量 + 索引 + 缓存数据三部分同池，`INFO memory` 的 `used_memory` 是总量，`FT.INFO` 显示索引占用——**定期对账"向量占了多少内存"**（总内存 - 业务数据 - 缓存），超预算先量化评估再扩容，与 Qdrant 体系的内存账纪律一致（Redis 无量化，只能控制规模）。对账节奏：**每周一次脚本化统计**（`INFO memory` + 各 `FT.INFO` 的 `indexing` 与内存字段 + key 前缀计数），变化趋势进监控面板——内存账"悄悄地涨"是 Redis 向量场景最常见的容量事故形态。

> 🎯 **核心要点**：Redis 8 的多模型 = 四结构（Hash/JSON/时序/Bloom）+ FT 索引模型（字段五族）+ Vector Set；JSON 字段走 JSONPath、向量字段走 VECTOR 类型；VSET 是轻量替代、Query Engine 是生产主路径；数据常驻内存是它与独立向量库的本质差异。
