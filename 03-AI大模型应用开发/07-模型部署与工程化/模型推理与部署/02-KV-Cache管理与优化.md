# 02 - KV Cache 管理与优化

> 🎯 KV Cache 是 LLM 推理显存的头号杀手 — 长序列+高并发时，KV Cache 占用远超模型权重。PagedAttention 把利用率从 30% 拉到 90%

## KV Cache 原理

```text
自回归生成时，每个新 token 需要与所有历史 token 做 Attention

第1步：算 "Hello" → 存 K₁,V₁
第2步：算 "Hello world" → 复用 K₁,V₁ + 算 K₂,V₂
第3步：算 "Hello world !" → 复用 K₁₂,V₁₂ + 算 K₃,V₃

不缓存：每次 O(n²) 从头算 → 1000 个 token → 50万次计算
有缓存：O(n) 新 token → 1000 个 token → 1000 次计算

KV Cache 的大小：
  size = 2 × num_layers × hidden_dim × seq_len × bytes × batch_size
  2 × 32 × 4096 × 8192 × 2 × 1 = 4 GB（单个请求 8K 上下文）
```

## 传统 KV Cache 的问题

```text
问题：预分配连续显存 → 碎片化

  请求A 预分配 max_len=8192 → 实际只用 500 tokens → 浪费 93%
  请求B 预分配 max_len=4096 → 实际只用 2000 tokens → 浪费 50%

实际利用率 ~30% → 80GB 显存只用了 24GB → 浪费 56GB
```

## PagedAttention 解决方案

```text
将 KV Cache 分成固定大小的 Page（类似 OS 虚拟内存分页）

  Page Pool: [page₀][page₁][page₂]...[pageₙ]
  
  请求A：分配 page₀, page₃, page₇ ← 只分配需要的
  请求B：分配 page₁, page₄, page₅, page₈
  请求C：分配 page₂, page₆

  所有请求共享 Page Pool → 按需分配 → 零碎片 → 利用率 ~90%
```

## KV Cache 量化

```python
# INT8 量化 KV Cache → 显存减半
from vllm import LLM
llm = LLM(model="Qwen/Qwen2-7B",
          kv_cache_dtype="fp8",  # FP8 量化 KV Cache
          max_model_len=8192)
```

| 精度 | KV Cache 大小(8K/请求) | 精度损失 |
|------|:---:|:---:|
| FP16 | 4 GB | 基准 |
| FP8 | 2 GB | 几乎无损 |
| INT8 | 2 GB | 几乎无损 |
| INT4 | 1 GB | 轻微 |

| 优化 | 7B模型+8K上下文+8并发 |
|------|:---:|
| 原始分配 | ~48 GB（30%利用率） |
| +PagedAttention | ~18 GB（90%利用率） |

## 5. KV Cache 显存估算速查

**显存估算公式**（面试必答 + 生产规划）：

```text
KV Cache 显存 = 2（K和V） × 层数 × 头数 × 头维度 × 上下文长度 × 2 字节（FP16） × 批大小

示例（7B 模型典型参数）：
  层数 32 × 头数 32 × 头维度 128 = 每层每 token 128K 值
  → 单 token KV = 32 × 32 × 128 × 2 × 2B = 512KB... 实际按模型参数量级：
  7B 模型 ≈ 每 token ~0.5MB（FP16）
  → 8K 上下文 × 单请求 ≈ 4GB；32 并发 × 8K ≈ 128GB（远超权重！）

权重 vs KV 的对比（7B 模型）：
  权重（FP16）：~14GB
  KV（8K × 32 并发）：~128GB ← 显存大头是 KV！
```

**KV Cache 优化的完整手段**（从易到难）：

| 手段 | 效果 | 成本 |
|------|------|------|
| 限制 max-model-len | 控制上限 | 零 |
| PagedAttention | 显存利用率 95%+ | 引擎内置 |
| 前缀缓存 | 共享前缀免重复计算 | 引擎内置 |
| 量化 KV（FP8） | 省 50% | 精度验证 |
| 滑动窗口 | 只保留近窗口 | 长文档损失 |

**KV Cache 的 2026 状态**：

```text
引擎已内置：PagedAttention + 前缀缓存（vLLM 标配）
新方向：KV 量化（FP8，长上下文关键）、缓存淘汰策略
长上下文（1M）的 KV 是硬约束——"长上下文贵在 KV 而非权重"
```

> 🎯 **核心要点**：KV 显存 = "**长上下文场景的显存大头**"（8K×32 并发 > 7B 权重）——**优化手段七件套（限长/PagedAttention/前缀/量化 KV/滑动窗口）**从易到难；"长上下文贵在 KV"是 2026 关键认知。

## 6. KV Cache 问题速查

| 问题 | 原因 | 解法 |
|------|------|------|
| OOM（长上下文） | KV 显存暴涨 | 限长/KV 量化/前缀缓存 |
| 前缀重复计算 | 系统提示共享 | **前缀缓存**（RAG 场景收益最大） |
| 显存碎片 | 变长请求 | PagedAttention（引擎内置） |
| 多轮对话显存累积 | 历史 KV 保留 | 滑动窗口/历史摘要化 |
| 批处理显存不足 | 批×上下文乘积 | 降批大小/量化 KV |

**KV Cache 的面试标准话术**：

```text
"KV Cache 是什么？"
① 定义：注意力计算中 K/V 的缓存（避免重复计算历史 token）
② 显存：长上下文场景的大头（8K×32 并发 > 7B 权重）
③ 优化：PagedAttention（碎片）+ 前缀缓存（重复）+ 量化（容量）+ 限长（上限）
④ 趋势：长上下文模型（1M）让 KV 优化成为核心课题
```

> 🎯 **核心要点**：KV 面试话术 = "**定义 → 显存大头 → 四优化 → 长上下文趋势**"四段式——**"长上下文贵在 KV"是最重要的认知**；五问题速查覆盖生产排障。
