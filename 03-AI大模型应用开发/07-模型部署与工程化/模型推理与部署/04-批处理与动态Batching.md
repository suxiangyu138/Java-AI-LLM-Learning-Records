# 04 - 批处理与动态 Batching

> 🎯 批处理是推理吞吐的倍增器 — 静态Batching吞吐×3、动态Batching×5、连续Batching×10

## 三种批处理对比

| 类型 | 做法 | 利用率 | 延迟 |
|------|------|:---:|:---:|
| **静态 Batching** | 固定 batch_size，等满再算 | 50% | 高 |
| **动态 Batching** | 不等满，到齐就处理 | 70% | 中 |
| **连续 Batching** | 来一个加一个，完一个丢一个 | 90%+ | **低** |

## 连续批处理 Continuous Batching

```text
传统批处理：
  Batch = [reqA(50t), reqB(200t), reqC(30t)]
  → 必须等 reqB 生成完 200 tokens 才结束整个 batch
  → reqA 和 reqC 早就完了 → 槽位空等 → GPU 浪费

连续批处理 (vLLM / TensorRT-LLM)：
  t=0:   Batch = [reqA, reqB, reqC]
  t=1:   reqC 生成结束 → 踢出
  t=1.1: reqD 到达 → 立即加入
  t=2:   Batch = [reqA(继续), reqB(继续), reqD(新)]
  
  → 槽位永不空等 → GPU 利用率 90%+
  → 原理：每个 KV Cache 独立管理，随时增删请求
```

## vLLM 并发配置

```python
llm = LLM(
    model="Qwen/Qwen2-7B",
    max_num_seqs=256,        # 最大并发请求数
    max_num_batched_tokens=8192,  # 单 batch 最大 token 数
    # Prefill 和 Decode 会自动混排 → 连续批处理
)
```

## Flight Batching (TensorRT-LLM)

```text
TensorRT-LLM 的更激进方案：

  将请求拆分为独立 Token → 按 Token 而非按请求调度
  → 比连续批处理更细粒度

效果：极端并发场景下仍有高吞吐
代价：实现复杂度极高
```

## 5. 批处理策略速查

**批处理参数速查**（vLLM 等引擎）：

| 参数 | 作用 | 调优方向 |
|------|------|---------|
| max-num-seqs | 最大并发批大小 | 大=吞吐↑延迟↑（按显存） |
| max-model-len | 上下文上限 | 与 KV 显存联动 |
| 前缀缓存 | 共享前缀复用 | RAG/系统提示场景开启 |

**批大小选择的权衡**（2026 实践）：

```text
交互式（聊天/搜索）：小批（4-16）→ 延迟优先
批处理式（离线生成/批量总结）：大批（32-128）→ 吞吐优先
混合：连续批处理自动平衡（引擎默认方案）

调优验证：
  压测不同 max-num-seqs → 画"吞吐 vs P95 延迟"曲线
  找拐点（吞吐不再线性增长处）→ 最优批大小
```

**连续批处理 vs 静态批处理对比**：

| 维度 | 静态批处理 | 连续批处理 |
|------|:----------:|:----------:|
| 请求进出 | 整批等齐才处理 | 动态进出（完成即出） |
| 吞吐 | 基准 | **2-4x** |
| 延迟 | 高（等批） | 低（即到即处理） |
| 实现 | 简单 | 引擎内置（vLLM 标配） |
| 2026 状态 | 已淘汰 | **生产标准** |

> 🎯 **核心要点**：批处理 = "**连续批处理（2026 标配）+ 批大小权衡（交互小批/批量大批）+ 拐点压测**"——**"完成即出"是连续批处理的核心**（不等整批）；批大小用"吞吐 vs P95 曲线"找拐点。

## 6. 批处理实践速查

**vLLM 批处理配置**：

```bash
# 关键参数
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --max-num-seqs 32 \          # 最大并发批大小（默认 256）
  --max-model-len 8192 \       # 上下文上限（与 KV 联动）
  --enable-prefix-caching      # 前缀缓存（RAG 场景必开）
```

**批大小调优方法**：

```text
① 交互式：max-num-seqs 4-16（延迟优先）
② 批处理式：32-128（吞吐优先）
③ 找拐点：压测不同值 → 吞吐 vs P95 曲线
   → 拐点后吞吐不再线性增长 = 最优批大小
④ 显存约束：批 × 平均上下文 × KV/请求 ≤ 可用显存

场景验证：
  聊天机器人：小批 + 流式（首 token 快）
  离线批量总结：大批（吞吐最大）
  RAG 问答：前缀缓存（共享系统提示）
```

**常见问题速查**：

| 问题 | 原因 | 解法 |
|------|------|------|
| 吞吐不升 | 批太小/前缀未缓存 | 调大批/开前缀缓存 |
| 延迟暴涨 | 批太大 | 降 max-num-seqs |
| OOM | 批×上下文超显存 | 降批/量化/限长 |
| 首 token 慢 | 队列等待 | 小批 + 前缀缓存 |

> 🎯 **核心要点**：批处理实践 = "**三参数（max-num-seqs/max-len/前缀缓存）+ 拐点调优 + 场景配置**"——**"吞吐 vs P95 找拐点"是批大小调优的标准方法**；RAG 场景前缀缓存是必开项。

## 8. 批处理面试题补充

| # | 追问 | 速答 |
|:-:|------|------|
| 1 | 静态批处理为什么慢？ | 等整批齐 + 等整批完成（最慢者拖累） |
| 2 | 连续批处理的实现？ | 引擎调度（请求级抢占/插入）——vLLM 内置 |
| 3 | 批大小和延迟的关系？ | 批越大吞吐越高但单请求延迟越高（权衡） |
| 4 | 前缀缓存和批处理关系？ | 批内共享前缀的 KV 可复用（叠加收益） |
| 5 | 长上下文请求的批问题？ | 长请求占批时间长——需限制 max-model-len |
| 6 | 怎么测最优批大小？ | 吞吐 vs P95 曲线找拐点 |

> 🎯 **核心要点**：批处理追问六题 = "**为什么慢（静态）/ 怎么实现（调度）/ 怎么权衡（批-延迟）/ 怎么叠加（前缀）**"——**"最慢者拖累整批"是静态批处理的本质缺陷**（连续批处理的动机）。
