# 10 - 容灾监控与告警体系

> 🎯 没有监控的容灾 = 盲人开车 — 监控是容灾的眼睛，告警是容灾的耳朵。RED+USE+黄金信号三件套

---

## 1. 监控框架

### RED 方法（面向服务）

```text
RED = Rate + Errors + Duration

  Rate (请求速率)：每秒多少请求？
  Errors (错误率)：多少请求失败？
  Duration (延迟)：P50/P90/P99 延迟变化？

  → 适合 API 服务、LLM 推理服务
```

### USE 方法（面向资源）

```text
USE = Utilization + Saturation + Errors

  Utilization (利用率)：GPU/CPU/内存利用率
  Saturation (饱和度)：排队请求数、线程池队列长度
  Errors (资源错误)：GPU ECC Error、OOM Kill

  → 适合 GPU 资源、网络、存储
```

## 2. LLM 核心告警规则

```yaml
groups:
  - name: llm_critical
    rules:
      # 🔴 严重 — 需立即响应
      - alert: LLMServiceDown
        expr: up{job="llm-service"} == 0
        for: 1m
        annotations:
          summary: "LLM 服务挂掉！"
          severity: critical

      - alert: HighErrorRate
        expr: rate(llm_errors_total[5m]) / rate(llm_requests_total[5m]) > 0.05
        for: 2m
        annotations:
          summary: "LLM 错误率超过 5%"
          runbook: "https://wiki.example.com/runbooks/llm-high-error"

      # 🟡 警告 — 需关注
      - alert: GPUMemoryHigh
        expr: gpu_memory_used / gpu_memory_total > 0.95
        for: 5m
        annotations:
          summary: "GPU 显存使用 > 95%，即将 OOM"

      - alert: ModelSwitchDetected
        expr: rate(llm_model_switch_total[10m]) > 3
        for: 5m
        annotations:
          summary: "模型频繁切换 → 主模型可能不稳定"
```

## 3. 告警分级与 On-Call

```text
告警分级：

  🔴 P0 — 立即响应（5分钟内）
     → 服务完全不可用、错误率 > 10%
     → 通知：电话 + 短信 + 企微/钉钉

  🟠 P1 — 30分钟内响应
     → 降级运行、P99 延迟翻倍
     → 通知：企微/钉钉 + 邮件

  🟡 P2 — 2小时内响应
     → GPU 利用率异常、模型频繁切换
     → 通知：企微/钉钉

  🔵 P3 — 下一个工作日
     → 非紧急优化项

降噪策略：
  → 相同告警 5 分钟内聚合（避免告警风暴）
  → 自动恢复的告警不发（熔断后自动恢复了 → 只记录不告警）
```
