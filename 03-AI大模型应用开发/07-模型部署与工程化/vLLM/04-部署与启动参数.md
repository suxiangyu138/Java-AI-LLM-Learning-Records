## 1. 安装与快速启动

```bash
pip install vllm
vllm serve Qwen/Qwen3-32B-AWQ \
  --gpu-memory-utilization 0.9 \
  --max-model-len 32768 \
  --host 0.0.0.0 --port 8000
```

启动后即 OpenAI 兼容服务：`http://localhost:8000/v1`。环境要求：Linux + NVIDIA GPU（CUDA 13.0 起为 v0.20+ 默认）、Python 3.12+（v0.21 起支持 3.14）、PyTorch 2.11。CPU/Mac/Windows 不在支持范围——这是 vLLM 与 Ollama 最硬的分界线。

## 2. 参数四组全景

### 模型与精度组

| 参数 | 说明 |
|---|---|
| `--quantization awq/gptq/fp8` | 量化方式，与模型文件匹配 |
| `--dtype auto/float16/bfloat16` | 推理精度，一般 auto 跟随权重 |
| `--trust-remote-code` | 允许远端代码，**生产需人工审查**再开 |
| `--served-model-name` | API 中暴露的模型名（路由/鉴权/灰度都依赖它） |

### 显存与上下文组

| 参数 | 说明 |
|---|---|
| `--gpu-memory-utilization 0.9` | 显存使用上限，权重+KV 共用这 90% |
| `--max-model-len 32768` | 最大上下文，每翻倍 KV 显存翻倍 |
| `--kv-cache-memory-bytes` | 显式指定 KV 缓存容量（精细控制） |
| `--cpu-offload-gb` | 权重卸载到 CPU 的容量（显存不足兜底） |

### 并发与批处理组

| 参数 | 说明 |
|---|---|
| `--max-num-seqs 128` | 并发序列上限 |
| `--max-num-batched-tokens 8192` | 单批 token 上限（chunk 控制） |
| `--enable-prefix-caching` | 前缀缓存开关 |
| `--enable-chunked-prefill` | Chunked Prefill 开关 |

### 服务与安全组

| 参数 | 说明 |
|---|---|
| `--host/--port` | 监听地址，生产绑 0.0.0.0 + 防火墙 |
| `--api-key` | 简单鉴权（补充层，不能替代网关） |
| `--log-requests` | 请求日志（注意脱敏） |
| `--served-model-name` | 见上（重复列出因其重要） |

> ⚠️ 参数配置的三条铁律：① `--max-model-len` 决定 KV 上限，先定它再定并发；② `--gpu-memory-utilization` 不是越高越好——留 5-10% 给 CUDA Graphs 与运行时；③ `--trust-remote-code` 默认关，非必要不开。

## 3. OpenAI 兼容 API

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
resp = client.chat.completions.create(
    model="Qwen/Qwen3-32B-AWQ",           # 或 --served-model-name 的别名
    messages=[{"role": "user", "content": "你好"}],
    stream=True)                           # 流式与 OpenAI 完全一致
```

vLLM 的 API 面包含 chat/completions、completions、embeddings（v0.25 起实时 embeddings）三类端点，与 OpenAI SDK 直接兼容。`--served-model-name` 的规范命名很重要：多模型路由、网关按模型名鉴权、灰度按模型名分流都依赖它——建议带版本号（如 `qwen3-32b-v1`），上线后改名会破坏所有下游配置。

## 4. Docker 与 K8s 部署

```bash
# Docker：官方镜像
docker run --gpus all -p 8000:8000 \
  -v /models:/models \
  vllm/vllm-openai:latest \
  --model /models/qwen3-32b-awq --served-model-name qwen3-32b-v1

# K8s：GPU 资源声明 + 探针 + 滚动更新
resources:
  limits:
    nvidia.com/gpu: 1        # 精确声明，多给浪费少给 OOM
```

K8s 部署三个要点：GPU 调度（节点亲和 + `nvidia.com/gpu` 精确声明）；探针区分存活与就绪——**就绪探针要等模型加载完成**（冷启动数分钟），否则滚动更新时流量打到未就绪实例全是 503；多副本做负载均衡（vLLM 实例无状态，天然支持）。

## 5. 冷启动与预热

vLLM 冷启动的三个阶段：加载权重（分钟级）→ CUDA kernel 编译（首次数分钟，缓存后秒级）→ CUDA Graphs 捕获（秒级）。生产实践：

1. **容器内预热**：就绪探针调 `/health` 端点，返回 200 才放流量。
2. **首次启动预热**：部署后发一个空请求触发 kernel 编译与图捕获，避免第一个用户承受 5 分钟冷启动。
3. **扩容预期**：自动扩缩容的副本启动有 30-60s 延迟——扩缩容按队列深度触发（见 08 篇），提前量要覆盖冷启动时间。

### 5.1 参数之间的因果链

四组参数不是孤立的，它们被一条因果链串起来：**`--max-model-len`（上下文）→ 决定 KV 缓存需求 → 决定 `--gpu-memory-utilization` 的分配 → 决定 `--max-num-seqs`（并发）能开多大**。这条链是生产配置的心智模型：先定上下文（业务需求），再算 KV（用 02 篇公式），再分显存（权重+KV+余量），最后定并发。违反这条链的典型错误：把 `--max-num-seqs` 调到 256 想堆并发，但没算 KV——上下文一长就 OOM，然后降上下文，用户又投诉"回答不全"。每一步的调整都要沿链重算，不能只动一头。

链条上还有一个常被忽略的环节：CUDA Graphs 与运行时也会占显存（约 5-10%），`--gpu-memory-utilization 0.9` 的 0.9 不是"权重+KV 可用 90%"，而是"引擎全部占用上限 90%"——把上限调满到 0.98 会挤压 CUDA Graphs 与 kernel 编译空间，反而在低并发时变慢。留余量不是浪费，是给引擎的运行时呼吸空间。

### 5.2 参数配置的排障映射

参数配置错误的表现与根因对照，是生产排障的第一张表：

| 现象 | 根因参数 | 修正 |
|---|---|---|
| 并发一高就 OOM | max-model-len 过长 / gpu-memory-utilization 过满 | 沿因果链重算 |
| 短请求也慢 | CUDA Graphs 空间被挤压（utilization 0.98） | 降到 0.9 留余量 |
| 长上下文报错 | max-model-len 小于请求长度 | 按业务上限调大（同时重算 KV） |
| 模型名对不上 | served-model-name 与客户端 model 不一致 | 统一命名规范 |
| 流式卡顿 | 反代缓冲了 SSE | 关 proxy_buffering |

排障纪律与 08 篇一致：一次只改一个参数，改完压测验证再改下一个。参数配置的 80% 错误都能在"上下文 → KV → 显存 → 并发"这条因果链上找到答案，先把链上的数字算对，再谈调优。

### 5.3 常见误区速排

| 误区 | 事实 |
|---|---|
| "参数越多越专业" | 默认参数是工程团队调过的，先理解再动 |
| "gpu-memory-utilization 调满" | 留 5-10% 给 CUDA Graphs，调满反而低并发变慢 |
| "trust-remote-code 方便就开" | 远端代码 = 远端执行，生产默认关 |
| "冷启动慢是故障" | 分钟级冷启动是正常，用预热与就绪探针解决 |
| "api-key 够安全" | 简单鉴权是补充层，公网必须网关 |

## 6. 版本升级与参数迁移

vLLM 版本迭代快（2026 年半年四个大版本），参数迁移有三个纪律：升级前读 release notes 的 breaking changes（v0.20 换 CUDA 13.0、v0.23 调度器默认变更等），确认自己用到的参数是否有改名/删改；升级后在测试环境重跑一遍参数矩阵（四组参数逐一验证生效），不要直接在生产升级；参数文件（启动脚本/Helm values）入 git 并记录版本对应关系——"这套参数针对 vLLM x.y.z 验证过"是配置文档的必备元信息。参数没有版本意识的团队，升级一次崩一次，且每次都查不出原因。

## 7. 本模块小结

> 🎯 **核心要点**：部署 = 安装一条命令 + 参数四组（模型精度/显存上下文/并发批处理/服务安全）+ OpenAI 兼容 API + 容器化。三条铁律：先定 `--max-model-len` 再定并发；显存利用率留 5-10% 余量；`--trust-remote-code` 非必要不开。`--served-model-name` 是生产架构的隐性关键（路由/鉴权/灰度都靠它）。冷启动 5 分钟级，预热与就绪探针是生产必配。
