# 08 性能调优与监控

> 调优的第一原则是"先判瓶颈再动手"：内存瓶颈和计算瓶颈的解法完全不同，方向错了越调越差。第二原则是"按顺序叠加"，每步验证收益。

## 1. 瓶颈判定：ops:byte 比率

调优前先回答一个问题：当前服务是算不动（计算瓶颈）还是喂不饱（内存瓶颈）？判据是 ops:byte 比率（每字节访存对应的计算量）：

```text
ops:byte < 50    → 内存瓶颈：GPU 在等数据（KV 缓存/权重带宽不足）
ops:byte > 200   → 计算瓶颈：GPU 算力打满（kernel 效率/并行度不足）
```

| 瓶颈 | 典型特征 | 解法方向 |
|---|---|---|
| 内存瓶颈 | 显存带宽打满、利用率高但算力低 | 量化 KV/权重、加大 batch（摊薄访存） |
| 计算瓶颈 | 算力利用率 90%+、吞吐上不去 | kernel fusion、张量并行、FP8 |

判据的意义：**同样是"吞吐低"，内存瓶颈靠压缩数据、计算瓶颈靠并行与精度**——方向反了，优化全白费。实测用 `nvidia-smi` 看显存带宽利用率与算力利用率，或 vLLM metrics 的数值对比。

## 2. 调优顺序

按"收益确定性 × 副作用"排序，前两项无脑开，后面的按场景：

| 顺序 | 优化 | 开启条件 |
|---|---|---|
| 1 | PagedAttention（KV 分页） | 始终开启（内建，无需配置） |
| 2 | 连续批处理 | 始终开启（vLLM 默认） |
| 3 | 前缀缓存 | 有共享前缀（Agent/RAG）就开 |
| 4 | KV 缓存量化（INT8/FP8） | KV 是显存瓶颈时 |
| 5 | 推测解码 | 延迟敏感且接受率稳定时 |
| 6 | 张量并行 | 模型单卡放不下时 |
| 7 | FP8 权重量化 | 新硬件且质量回归通过 |

纪律：**每次只开一项、验证一项**——多优化叠加后无法归因，调优变玄学。前两项白送（内建默认），第三四项是高性价比，五六七按场景。

## 3. 监控指标体系

| 指标 | 定义 | 健康基线 |
|---|---|---|
| TTFT | 首 token 延迟 | < 500ms（交互场景） |
| ITL | token 间延迟 | < 50ms |
| KV 缓存利用率 | KV 页使用比例 | 高 = 显存利用好；接近 100% 注意驱逐 |
| 批利用率 | 批次实际 token/最大 token | 高 = 批处理健康 |
| 队列深度 | 等待中的请求数 | 持续 > 0 说明容量不足 |

监控要点：TTFT 与 ITL 是用户体验的直读指标（10 秒 TTFT 的高吞吐无意义）；队列深度是容量信号——**扩缩容按队列深度触发，不按 GPU 利用率**（见下节）。vLLM 原生 `/metrics` 端点输出 Prometheus 格式，Grafana 直接接。

## 4. 扩缩容策略

一个反直觉但重要的原则：**不要按 GPU 利用率扩缩容**。原因是 GPU 利用率是滞后指标——利用率飙升时队列已经堆积，而且新副本冷启动要 30-60 秒，等利用率告警再扩容，用户已经在等。

```text
正确信号：队列深度（排队请求数）
阈值设计：队列深度 > N 持续 30s → 扩容；队列空 > M 持续 → 缩容
提前量：扩容触发要覆盖冷启动时间（30-60s）
```

副本策略：无状态多副本 + 负载均衡；滚动更新时就绪探针等模型加载完成再放流量（04 篇）。

## 5. 常见误区

| 误区 | 事实 |
|---|---|
| "只测吞吐不测延迟" | 10 秒 TTFT 的高吞吐对交互无意义——两个都要测 |
| "为权重预留显存，KV 空间不足" | 权重 + KV 共享显存池，比例失衡是头号配置错误 |
| "单 batch 解码够用" | 单 batch 是内存瓶颈（GPU 计算闲置 95%），必须并发/批处理 |
| "忽略前缀缓存" | 80% 请求共享 system prompt 时不开 = 白丢成本 |
| "高温下用推测解码" | 接受率跌破 50% 时推测解码反而变慢，需动态关闭 |

### 5.1 调优与监控的闭环

调优不是一次性动作，而是"基线 → 变更 → 验证 → 回归"的闭环，这要求监控体系在调优之前就位。推荐的流程：第一步采集基线——服务上线后先跑 24 小时，记录 TTFT/ITL 的 P50/P95、KV 利用率、批利用率、队列深度的正常区间，这是后续一切判断的参照系；第二步按 08 篇顺序逐项变更——每项变更后观察 30-60 分钟，对比基线判断收益是否成立；第三步记录决策——每项参数的最终值、调整原因、验证结果写入配置文档，否则半年后没人知道"为什么 max-num-seqs 是 96 而不是 128"。这个闭环的价值在长期：vLLM 版本升级、模型替换、流量形态变化后，用基线对比能快速发现"什么变了"。

监控的另一个务实建议是"告警要可执行"：每条告警配一个排查路径（TTFT 劣化 → 看队列深度 → 队列深看扩容/限流，队列浅看显存/KV 驱逐），把告警从"通知"变成"指令"。没有排查路径的告警只会被值班同学忽略，最终沦为噪音——而噪音告警比没有告警更危险，因为它会掩盖真正的问题。

### 5.2 压测方法论

调优验证依赖可靠的压测，三个要点：一是**流量形态必须复现生产**——长短混合、并发曲线、前缀复用比例都要贴近真实，纯短或纯长请求的压测结果不能外推到生产（连续批处理对混合形态最敏感）；二是**指标要采集分布而非均值**——TTFT/ITL 记录 P50/P95/P99，均值会掩盖尾延迟劣化，而尾延迟正是用户投诉的来源；三是**压测工具要能持续加压**——用 k6/Locust 类工具跑持续压测（15 分钟以上）而非瞬时打满，才能暴露 KV 驱逐、缓存填满等"时间相关"问题。压测通过的标准：P95 达标且持续稳定 10 分钟以上，队列深度不持续堆积。

### 5.3 常见误区速排

| 误区 | 事实 |
|---|---|
| "调优靠经验直觉" | 先判瓶颈（ops:byte）再动手，方向错全白费 |
| "GPU 利用率高 = 健康" | 利用率是滞后指标，队列深度才是扩容信号 |
| "均值达标就上线" | 看 P95/P99，均值掩盖尾延迟 |
| "压测打满就行" | 流量形态要复现生产（长短混合/前缀复用） |
| "多优化一起上更快" | 一次一项，无法归因的调优是玄学 |

## 6. 本模块小结

> 🎯 **核心要点**：调优 = 先判瓶颈（ops:byte：<50 内存 / >200 计算）→ 按序叠加（前两项白送、KV 量化高性价比、推测解码/TP 按场景）→ 每步验证。监控看五指标（TTFT<500ms/ITL<50ms/KV 利用率/批利用率/队列深度），扩缩容按队列深度触发而非 GPU 利用率。五个误区里最贵的一个：只测吞吐不测延迟——生产调优的一切努力最终要落在用户体验的两个数字上。
