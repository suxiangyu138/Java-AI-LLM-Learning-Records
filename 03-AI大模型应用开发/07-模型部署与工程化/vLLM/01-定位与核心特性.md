## 1. vLLM 是什么

vLLM 是 UC Berkeley 团队开源的高吞吐大模型推理引擎（Apache 2.0），2026 年已是生产环境的事实标准：单卡支撑 50-100 并发，高并发下吞吐是 llama.cpp 系引擎的 2-4 倍。它只做一件事——把模型跑得又快又省显存——并且围绕这一件事做到了极致：不提供 GUI、不提供模型管理，只有一个 OpenAI 兼容的 HTTP 服务端点和 Python 库。

它的出现解决了 2023-2024 年推理服务的三大痛点：KV 缓存碎片浪费显存（60-80% 被浪费）、静态批处理让 GPU 空转（利用率约 60%）、长输入 prefill 阻塞整个队列。三个痛点对应它的三大核心特性。

## 2. 三大核心特性

| 特性 | 解决的问题 | 量化收益 |
|---|---|---|
| PagedAttention | KV 缓存碎片化浪费显存 | 碎片 60-80% → 4% 以下；Qwen3-8B 32K 上下文 KV 从 49.6GB 降至 5.2GB |
| 连续批处理 | 静态批处理 GPU 空转 | 利用率 60% → 85-95%；吞吐提升 3-23 倍 |
| 前缀缓存 | 共享前缀重复计算 | Agent 循环场景命中率 70-95%，成本降 70%+ |

三个特性相互独立又协同：PagedAttention 决定"显存能装多少并发"，连续批处理决定"并发如何被调度"，前缀缓存决定"重复计算如何被跳过"。理解 vLLM，就是理解这三者的分工。

## 3. 与同类引擎的对比

| 维度 | vLLM | Ollama | TGI | SGLang |
|---|---|---|---|---|
| 定位 | 生产高吞吐 | 开发极简 | 生产（维护模式） | 生产 + 结构化输出 |
| 批处理 | 连续批处理 | 有限 | 连续批处理 | 连续批处理 |
| KV 优化 | PagedAttention（MRv2 内核） | llama.cpp 分页 | PagedAttention | RadixAttention |
| 前缀缓存 | ✅ | ❌ | ✅ | ✅（更强） |
| 平台 | Linux+NVIDIA | 全平台 | Linux+NVIDIA | Linux+NVIDIA |
| 生态状态 | 事实标准，活跃 | 开发工具 | 2026 已进入维护模式 | 高并发 Agent 场景追赶者 |

对比要点：Ollama 与 vLLM 不是竞争关系而是阶段关系（开发→生产，OpenAI 兼容 API 无缝切换）；TGI（HuggingFace）2026 年已进入维护模式，vLLM 成为事实标准；SGLang 的 RadixAttention 在复杂前缀树场景（多轮 Agent 对话）比 vLLM 的前缀缓存更激进，但生态与模型支持仍落后。

## 4. 2026 版本线

| 版本 | 时间 | 关键变化 |
|---|---|---|
| v0.20.0 | 2026-04 | FlashAttention 4 默认 MLA prefill、CUDA 13.0、PyTorch 2.11、DeepSeek V4 支持 |
| v0.21.0 | 2026-05 | 推测解码支持 thinking budget（DeepSeek-R1 类）、KV Offload + Hybrid Memory Allocator、Python 3.14 |
| v0.23.0 | 2026-06 | Rust 前端生产级（流式/LoRA/工具解析）、MRv2 调度器默认、多层 KV 卸载、新模型支持 |
| **v0.25.0** | 2026 下半年 | **MRv2 成为全部 dense 模型默认执行路径，legacy PagedAttention 代码移除**、视频采样 EVS、动态推测解码兼容完整 CUDA Graphs |

> 💡 v0.25.0 的象征意义：PagedAttention 作为"独立代码"退出历史舞台，其分页思想已内化为新一代内核（MRv2）的执行底座——"技术被吸收进架构"而非被废弃。升级注意：MRv2 默认后，依赖旧内部接口的自定义集成需要适配。

## 5. 适用边界

vLLM 不是万能的，用错场景就是"过度配置"：

| 场景 | 用 vLLM 吗 | 理由 |
|---|---|---|
| 生产高并发 API（10+ 并发） | ✅ | 连续批处理优势充分释放 |
| 单用户/个人工具 | ❌ | 优势不体现，配置复杂度与显存开销白扛 |
| 开发原型 | ❌ | Ollama 秒级拉起更合适 |
| CPU/Windows/Apple Silicon | ❌ | 仅 Linux+NVIDIA，这些平台无解 |
| RAG/Agent（前缀复用多） | ✅ | 前缀缓存直接转化为成本优势 |

判断标准一句话：**并发是 vLLM 的氧气**。没有并发负载，vLLM 的三大特性全部空转。

### 5.1 为什么 2026 年 vLLM 成为事实标准

vLLM 的胜出不是单一技术的胜利，而是三个结构性因素叠加的结果：一是性能叙事完整——三大机制每一项都有可量化的公开基准（显存省 89%、吞吐 3-23 倍、命中率 70-95%），技术社区对"为什么快"有共识，选型不需要赌；二是生态先发——模型厂商（Qwen/DeepSeek/Llama 官方）直接发布 vLLM 兼容的量化版与配置文件，新模型出来第一天 vLLM 就能跑，这种"官方支持"的雪球效应让后来者难以追赶；三是工程化成熟——Docker 镜像、Prometheus 指标、OpenAI 兼容 API、K8s 部署文档齐备，企业落地的路径清晰，而 TGI 在 2026 年进入维护模式，SGLang 虽在结构化输出与 RadixAttention 上更强，但生态宽度仍落后。

选型时的现实判断：如果团队已经在用 vLLM，没有必要因为 SGLang 的某些基准优势而迁移——除非结构化输出或复杂前缀树场景成为明确瓶颈。引擎迁移的成本虽然被 OpenAI 兼容 API 压得很低，但运维知识、监控体系、调优经验都是沉淀成本。

### 5.2 与"模型推理与部署"体系的分工

本体系与仓库内的「模型推理与部署」体系（11 篇）在 KV Cache 与量化主题上有内容交叠，但视角不同：该体系讲通用原理——KV Cache 是什么、投机采样怎么做、量化为什么有效，是"理论课"；本体系讲 vLLM 工程实现——这些原理在 vLLM 里如何落地、参数如何配置、瓶颈如何定位，是"实战课"。阅读建议：原理卡壳时回该体系补理论，参数调不通时回本体系查实践。两个体系配合使用，才是完整的推理优化知识栈——理论给方向，实践给细节，缺一不可。

### 5.3 常见误区速排

| 误区 | 事实 |
|---|---|
| "vLLM 比 Ollama 快，所以全面更好" | 单用户场景优势不体现，是阶段关系不是竞争 |
| "TGI 还值得新项目选" | 2026 已进入维护模式，新项目选 vLLM |
| "SGLang 更快就迁移" | 除非结构化输出成瓶颈，否则生态成本大于基准收益 |
| "开源引擎都差不多" | 三大机制差异决定吞吐量级差，vLLM 是事实标准 |

## 6. 本模块小结

> 🎯 **核心要点**：vLLM = 生产吞吐引擎（不是通用部署工具），三大特性（PagedAttention/连续批处理/前缀缓存）分别解决显存、吞吐、成本三个问题。2026 格局：TGI 进入维护模式、vLLM 成事实标准、SGLang 在高并发 Agent 场景追赶；v0.25.0 标志 MRv2 内核时代（legacy PagedAttention 代码移除）。适用边界：有并发才用，单用户场景选 Ollama。与 Ollama 是阶段关系不是竞争关系——OpenAI 兼容 API 让两者无缝衔接。
