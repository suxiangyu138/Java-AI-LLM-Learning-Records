## 1. 三种多卡形态

| 形态 | 解决什么问题 | 适用 |
|---|---|---|
| 张量并行（TP） | 单卡显存放不下模型 | 70B+ 大模型 |
| 多实例 | 单实例吞吐不够 | 高并发、故障隔离 |
| 多模型分实例 | 多个模型并存互不干扰 | 通用 + 专用模型混布 |

三者的区别要刻清楚：张量并行是"一个模型拆到多卡"（内部通信频繁，依赖 NVLink）；多实例是"同一模型跑多份"（彼此独立，负载均衡）；多模型分实例是"不同模型各占各的"（资源隔离）。很多部署混乱源于把三者混为一谈——比如用张量并行去解决并发不够，结果吞吐没涨、通信开销还拖慢了单请求。

## 2. 张量并行详解

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 vllm serve Qwen/Qwen3-72B-AWQ \
  --tensor-parallel-size 4 --max-model-len 8192
```

关键规则与注意：

1. **必须显式指定 `--tensor-parallel-size`**：vLLM 能看到所有 GPU 但不会自动分配，不指定就只用一张。
2. **NVLink 优先**：TP 的每层前向都要跨卡通信（all-reduce），卡间带宽直接决定效率——PCIe 卡做 TP 会变成通信瓶颈，2 卡 PCIe 跑 TP 往往不如单卡大显存。
3. **显存按并行度分摊**：TP=4 时模型权重分到 4 卡，单卡权重显存 = 总量/4，但通信开销与复杂度上升——**显存够用就不要 TP**，它是"放不下"的解决方案而非"更快"的方案。
4. **量化先行**：70B 模型先 AWQ 量化（约 40GB），单张 48GB 卡就能跑，比 2×24GB 做 TP 更简单高效——"先量化、再 TP"是铁律。

## 3. MoE 的弹性专家并行

MoE 模型（DeepSeek 系、Qwen3-MoE 等）的注意力层与专家层分离，vLLM 支持弹性专家并行（v0.7.3 起优化）：

```text
原理：MoE 的专家层按专家分布到多卡，激活专家动态调度
收益：MoE 大模型（如 671B）用远小于全量权重的显存部署
优化：v0.7.3 弹性专家并行 + 多卡间通信减负
```

MoE 部署的注意：激活参数远小于总参数（671B 激活约 37B），显存账按"全部专家权重"算（还是要全量装下），但算力账按激活量算——MoE 的性价比来自"算得少"，不是"装得下"。

## 4. 多实例与多模型

```text
┌─ vLLM-A（Qwen3-32B：通用助手）        ┐
│─ vLLM-B（Qwen3-8B：代码补全，高并发）  ├─ 网关按 model 路由
└─ vLLM-C（Embedding：RAG 向量化）       ┘
```

多实例部署的三个纪律：

1. **故障隔离**：一个实例 OOM/崩溃不影响其他模型——比单实例多模型（vLLM 支持但不推荐混跑）稳定得多。
2. **embedding 单独部署**：RAG 向量化与推理解耦，embedding 挂了不影响对话主链路。
3. **资源按场景配**：高并发场景（代码补全）多副本 + 负载均衡，低并发场景（通用对话）单副本即可——别一刀切。

## 5. 多卡排障

| 现象 | 原因 | 排查 |
|---|---|---|
| TP 后速度反而慢 | PCIe 通信瓶颈 | 确认 NVLink；TP 与卡间带宽匹配 |
| 显存 OOM | TP 分摊后单卡仍超 | 降上下文/量化/换更大卡 |
| 某卡利用率 0 | 并行度与卡数不匹配 | 确认 `--tensor-parallel-size` 与 `CUDA_VISIBLE_DEVICES` 一致 |
| 多实例一个崩全挂 | 共享了同卡资源 | 每实例独立卡（`CUDA_VISIBLE_DEVICES` 隔离） |
| 跨卡同步报错 | NCCL 版本/拓扑问题 | 查 NCCL 日志；升级驱动与 NCCL |

排障原则：多卡问题先问"哪种形态"（TP/多实例/多模型），再查对应层——形态混淆是排障绕圈的头号原因。

### 5.1 多卡架构的容量规划

多卡架构的规划要同时算清三笔账，缺一笔都会在扩容时踩坑。第一笔是显存账：TP 分摊后单卡权重显存（总权重/TP 数）+ KV 余量是否放得下——70B AWQ 约 40GB 权重，TP=2 时单卡 20GB 权重 + KV，24GB 卡勉强、48GB 卡从容。第二笔是吞吐账：单实例吞吐上限 × 副本数是否覆盖峰值 QPS——压测得到单实例真实吞吐（不要用官方基准），再反推副本数。第三笔是通信账：TP 依赖 NVLink 带宽，多实例靠网络延迟，两种形态的扩展曲线不同——TP 到 8 卡后通信开销增长快于算力增长，继续加卡不如拆实例。

扩容决策的一个常见错误是"并发不够就加 TP"：并发瓶颈在调度与批处理，加 TP 只解决显存不解决并发——正确做法是加副本（多实例 + 负载均衡）。反过来"模型放不下就多实例"也是错的：多实例每个都要完整加载权重，显存开销翻倍，放不下只能 TP 或量化。三笔账与三种形态的对应关系想清楚，扩容就是按公式算数，而不是拍脑袋。

### 5.2 多卡场景的压测方法

多卡部署上线前必须压测，方法与单卡有两个关键差异：一是**通信占比测试**——TP 场景单独测"跨卡通信开销"（对比 1 卡与 2 卡跑同一请求的延迟差，通信开销过大说明 NVLink 未生效或拓扑不对）；二是**多实例的隔离测试**——确认每个实例独占的 GPU 编号与显存边界（`CUDA_VISIBLE_DEVICES` 隔离），防止实例间互相抢显存导致偶发 OOM。压测数据要按"单实例吞吐 × 实例数"外推峰值容量，并留 20% 余量——多卡环境的故障面更大（NCCL 通信、GPU 拓扑、驱动版本），余量要比单卡更足。

### 5.3 常见误区速排

| 误区 | 事实 |
|---|---|
| "多卡自动分配" | 必须显式 --tensor-parallel-size 与 CUDA_VISIBLE_DEVICES |
| "PCIe 也能高效 TP" | 通信瓶颈，NVLink 优先，2 卡 PCIe 不如单卡大显存 |
| "并发不够加 TP" | 并发不够加副本；TP 只解决放不下 |
| "多模型塞一个实例" | 故障隔离优先，每模型独立实例 |

## 6. 本模块小结

> 🎯 **核心要点**：多卡三形态各管一事——TP 管"放不下"（NVLink 优先、显存够就不 TP）、多实例管"扛不住"（负载均衡、故障隔离）、多模型分实例管"并存"（按场景配资源）。两条铁律：先量化再 TP（70B AWQ 单卡 48GB 能跑就别拆卡）；TP 必须显式指定并行度。MoE 部署按"激活参数算算力、全部专家算显存"。多卡排障先分形态再查层。
