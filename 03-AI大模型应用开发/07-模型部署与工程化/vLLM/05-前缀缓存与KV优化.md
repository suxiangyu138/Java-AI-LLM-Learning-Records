# 05 前缀缓存与 KV 优化

> 前缀缓存是 vLLM 三大特性里"最赚"的一个：不加速任何单个请求，却能在 Agent/RAG 场景把整体成本降 70%+——因为它消灭的是重复计算本身。

## 1. 前缀缓存的原理

多轮对话、Agent 循环、RAG 场景有一个共同特征：**每次请求的前缀高度重复**——system prompt、工具定义、对话历史、检索到的文档，每次都要重新 prefill 一遍。前缀缓存把已计算的前缀 KV 页缓存起来（PagedAttention 的页共享能力是地基），后续请求命中相同前缀时直接复用，跳过重复计算。

```text
请求 1：system prompt(500 token) + 文档A + 问题1 → 全量计算，缓存 system+文档A
请求 2：system prompt(500 token) + 文档A + 问题2 → 命中缓存，只算"问题2"部分
```

收益有两层：TTFT 大幅下降（前缀越长越明显，Agent 场景输入输出比可达 131:1）；GPU 算力从"重复劳动"中解放，等效吞吐提升。

## 2. 命中率场景表

| 场景 | 命中率 | 说明 |
|---|---|---|
| Agent 循环（固定 system+tools） | 70-95% | 最高收益场景，多轮工具调用前缀几乎全同 |
| 多租户共享 system prompt | 30-60% | 各租户前缀部分重叠 |
| RAG 按需检索 | 0-15% | 每次检索不同 chunk，前缀命中少（可按文档分块缓存） |
| 通用聊天 | 0-10% | 前缀太短/太随机，收益有限 |

> 💡 反直觉点：RAG 场景命中率低，不是因为缓存没用，而是"检索结果每次不同"——改进方向是把高频文档块与对话前缀分离缓存。判断你的场景值不值得开：**固定前缀越长、复用越频繁，收益越大**。

## 3. 启用与调优

```bash
vllm serve Qwen/Qwen3-32B-AWQ --enable-prefix-caching
```

调优三件事：

1. **缓存空间**：前缀缓存与推理共用同一显存池，缓存填满时新请求可能延迟——通过 `--gpu-memory-utilization` 或 `--kv-cache-memory-bytes` 控制分配，缓存与并发之间找平衡。
2. **驱逐策略**：默认 LRU（最近最少使用），不可改——常用前缀常驻，冷前缀自然淘汰。
3. **隔离**：`cache_salt` 参数隔离不同用户/会话间的缓存，防止跨租户缓存共享（隐私场景必开）。

前缀缓存开启是零风险的（不命中就退化为普通计算），所以判断标准很简单：**有共享前缀就开，没有也不亏**。

## 4. KV Offload：显存超卖

KV Offload（v0.21.0 起与 Hybrid Memory Allocator 整合）允许 KV 缓存溢出时卸载到 CPU 内存甚至 SSD：

```text
显存 KV 满 → 冷页卸载到 CPU RAM → 更冷页卸载到 SSD
需要时按优先级回载（RAM 快、SSD 慢）
收益：上下文长度突破显存上限（如 8GB 卡跑 128K 上下文）
代价：卸载/回载引入延迟，命中冷页的请求明显变慢
```

适用场景：长上下文为主、但对"偶尔慢"不敏感的服务（离线批处理、长文档分析）；对延迟敏感的生产服务慎用——TTFT 抖动可能让人以为服务故障。判断标准：**显存真的不够且能接受 P99 劣化，才开 KV offload**。

## 5. Mooncake：分布式缓存池

针对 Agent 工作负载（长上下文多轮、输入输出比 131:1、缓存命中 94.2%），vLLM 与 Mooncake Store 集成（2026-05 官方博客）实现分布式 KV 缓存池：多实例通过 RDMA 共享缓存，一个实例算过的前缀，其他实例直接复用。

实测收益：吞吐 3.8 倍、TTFT 降 46 倍、端到端延迟降 8.6 倍，支持多达 60 张 GB200 GPU 的近线性扩展。

```text
适用：多实例部署 + Agent 类高重复负载
不适用：单实例/低重复流量（分布式缓存的开销大于收益）
```

> ⚠️ Mooncake 是重度方案：需要 RDMA 网络（InfiniBand 或 RoCE）与额外的存储组件，适合"多实例 + 高重复负载"的规模化场景，小规模部署不需要。

### 5.1 前缀缓存与并发显存的平衡

前缀缓存与并发共享同一个显存池，这个共享关系决定了它的调优本质是"缓存空间 vs 并发容量"的权衡：缓存分得多，命中率升、但并发装得少；并发开得多，缓存被驱逐、命中率降。两个实操策略：一是通过 `--kv-cache-memory-bytes` 显式划分缓存空间——对 Agent 类高重复负载（命中率 70-95%）给缓存留足空间，对通用聊天（命中率 0-10%）则完全不需要留，把显存让给并发；二是监控"缓存命中率 + KV 利用率"两个指标的组合——命中率高且 KV 利用率高是理想状态，命中率低但 KV 利用率高说明缓存挤占了并发，命中率高但利用率低说明缓存空间过度预留。

一个值得注意的细节：前缀缓存对 TTFT 的改善在"前缀很长"时才显著（Agent 循环动辄数千 token 前缀），短前缀场景（几百 token）命中的收益可能被缓存查询开销抵消。所以评估缓存收益不要看命中率一个数，要看"命中节省的 prefill 时间 vs 缓存管理开销"的净收益——这也是为什么社区基准里 Agent 场景收益巨大、聊天场景无人问津。

### 5.2 前缀缓存与成本模型

前缀缓存的价值最终要落到成本上，给一个简化的账：假设 Agent 循环每次请求 2000 token 前缀 + 500 token 新内容，命中率 80%，无缓存时每次全量计算 2500 token，有缓存时只算 500 token——算力消耗降 80%，等效吞吐提升 5 倍，TTFT 从秒级降到毫秒级。这个账解释了为什么 Agent 场景（输入输出比 131:1）是前缀缓存的主场：前缀占比越高，缓存收益越大。反过来说，通用聊天场景前缀占比低（几十到几百 token），缓存收益几乎可以忽略——**评估任何缓存类优化，先算"重复占比"，重复占比低于 20% 的项目不值得做缓存**。这条规律同样适用于 KV 卸载的取舍：卸载只对"冷页占比高"的负载有意义。

### 5.3 常见误区速排

| 误区 | 事实 |
|---|---|
| "前缀缓存自动最优" | 缓存与并发共用显存池，要显式平衡 |
| "RAG 场景开缓存没用" | 命中率低但非零，高频文档块仍有收益 |
| "cache_salt 可有可无" | 多租户场景不开 = 跨租户缓存共享，隐私事故 |
| "KV 卸载免费" | 冷页回载引入延迟，P99 会劣化，非长上下文不开 |
| "Mooncake 小规模也上" | 需要 RDMA，单实例场景开销大于收益 |

## 6. 本模块小结

> 🎯 **核心要点**：前缀缓存 = 复用共享前缀的 KV 页，消灭重复 prefill——Agent 场景命中 70-95%、成本降 70%+，是三大特性里性价比最高的一项。三个控制点：缓存空间与并发共用显存池（找平衡）、LRU 驱逐（不可改）、cache_salt 隔离（隐私必开）。开启零风险（不命中退化普通计算），有共享前缀就开。KV Offload 是显存超卖工具（长上下文优先，接受 P99 劣化）；Mooncake 是规模化利器（多实例 + RDMA，吞吐 3.8 倍），小规模别碰。
