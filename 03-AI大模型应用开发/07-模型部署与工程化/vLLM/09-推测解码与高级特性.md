## 1. 推测解码的原理

推测解码（Speculative Decoding）的核心思想是"让小模型打草稿，大模型做验收"：

```text
① 小模型（draft model）快速生成 N 个候选 token（草稿）
② 大模型一次前向同时验证 N 个 token（并行，单次前向成本）
③ 全部接受 → 一次前向产出 N 个 token（吞吐 N 倍）
④ 部分接受 → 接受前缀，从第一个拒绝处重新草拟
```

收益与代价：

| 维度 | 说明 |
|---|---|
| 收益 | 延迟敏感场景吞吐提升 1.5-2.5 倍（单请求体验为主） |
| 代价 | 小模型额外占显存；草稿与主模型分布不一致时接受率暴跌 |
| 高并发下 | 可能损害吞吐（批处理已饱和，推测的并行度无处释放） |

关键理解：推测解码优化的是"延迟"（单请求的 token 生成速度），不是"吞吐"（并发总量）——与连续批处理的优化目标正交。v0.25.0 起动态推测解码兼容完整 CUDA Graphs。

## 2. 适用条件与配置

```bash
vllm serve Qwen/Qwen3-32B-AWQ \
  --speculative-config '{"model": "Qwen/Qwen3-1.5B", "num_speculative_tokens": 5}'
```

| 适用条件 | 说明 |
|---|---|
| 草稿模型选择 | 与主模型同系（同 tokenizer 家族），小 10-20 倍 |
| 接受率 | > 50% 才有正收益；< 50% 建议关闭 |
| 温度 | 高温（采样随机性大）接受率暴跌——低温/贪婪解码最佳 |
| 场景 | 延迟敏感的单请求体验（客服/交互），非高吞吐批处理 |
| 监控 | 关注接受率指标，劣化自动关闭（或人工关闭） |

判断流程：先测接受率（vLLM metrics 有专门指标），接受率 > 50% 就开、跌破就关——**推测解码不是"永远开着好"的优化，是条件优化**。

## 3. thinking budget：推理模型的思考控制

DeepSeek-R1 类推理模型（先输出思考再输出答案）带来一个新问题：思考过程不可控——短问题也可能想几千 token，又慢又贵。vLLM v0.21.0 起推测解码支持 thinking budget：

```text
能力：限制/控制模型的思考预算（思考 token 上限、思考开关）
价值：简单问题不思考（省时省钱）、复杂问题给足思考（质量保障）
配合：推测解码现在能"尊重"思考预算，草拟/验证覆盖思考阶段
```

实践建议：按问题复杂度动态设置思考预算——检索型问题关思考，推理型问题开思考；监控"思考 token 占比"，占比过高说明预算设置过宽。

## 4. 工具调用与结构化输出

vLLM 对 Agent 场景的支撑（2026 年已成熟）：

| 能力 | 说明 |
|---|---|
| 工具调用 | 完整支持 OpenAI function calling 格式，流式工具调用稳定 |
| 结构化输出 | 约束解码（JSON Schema 强制），输出格式 100% 合规 |
| 前缀缓存协同 | 工具 schema 是固定前缀，Agent 场景命中率 70-95% 的来源 |

v0.23.0 起工具解析管线统一（Rust 前端实现），多模型工具调用行为一致——Agent 框架（LangChain/Claude Code 类）接入 vLLM 的体验与 OpenAI 无差别。

## 5. 工程化新特性

| 特性 | 版本 | 说明 |
|---|---|---|
| Rust 前端 | v0.23.0 | 生产级：流式、LoRA、工具解析；性能与稳定性提升 |
| 实时 embeddings | v0.25.0 | embeddings 端点低延迟化，RAG 场景友好 |
| 视频采样（EVS） | v0.25.0 | 视频 token 剪枝，长视频上下文（注意：禁用视频 CUDA Graphs） |
| 多层 KV 卸载 | v0.23.0 | CPU/SSD 分级卸载（05 篇） |
| Python 3.14 | v0.21.0 | 新运行时支持 |

工程化特性的选择原则：**Rust 前端/工具解析是默认收益（升级即得），视频 EVS 是 niche（视频模型才用），KV 卸载是权衡（按 05 篇判断）**——不要因为"新"就全开，特性越多，可排查面越广。

### 5.1 高级特性的选型哲学

vLLM 高级特性有一个共同的选型哲学：**先测量，再启用；劣化即关**。推测解码测接受率（>50% 开）、thinking budget 测思考占比（按复杂度设）、KV 卸载测 P99（可接受才开）、视频 EVS 只在视频场景开。原因在于这些特性全部有明确的代价面：推测解码多占一份小模型显存且高并发下反噬吞吐、KV 卸载牺牲 P99、EVS 禁用视频 CUDA Graphs。与三大核心机制（默认开启无副作用）不同，高级特性是"条件收益"，启用条件必须实测确认——这也是生产环境"特性最小化"原则的体现：默认只开核心机制，特性按需逐个验证，不在生产里做实验。

另一个容易被忽略的点是特性之间的组合约束：v0.25.0 之前动态推测解码与 CUDA Graphs 互斥、EVS 禁用视频 CUDA Graphs、KV 卸载与某些 attention backend 不兼容——升级 vLLM 后组合行为可能变化。生产实践是把"特性组合"作为升级回归测试的一部分：升级后跑一轮特性开关矩阵（推测解码开/关 × KV 卸载开/关），确认组合行为符合预期，再放流量。

### 5.2 高级特性的监控配套

每个高级特性启用后都要配对应的监控指标，否则"劣化即关"无从谈起：推测解码监控接受率（dropped tokens 比率）与草稿命中分布；thinking budget 监控思考 token 占比与超预算率；KV 卸载监控卸载命中率与 P99 劣化幅度；Mooncake 监控跨实例命中率与 RDMA 网络质量。每个特性配一个"关闭阈值"，达到阈值自动告警并触发关闭预案——高级特性是条件优化，条件恶化时快速退出与快速启用同等重要。这套"特性 + 指标 + 阈值 + 退出预案"的配套是生产级使用高级特性的完整形态，缺一环特性就会从优化变成事故源。

### 5.3 常见误区速排

| 误区 | 事实 |
|---|---|
| "推测解码永远开" | 接受率 <50% 或高并发下反而变慢 |
| "思考预算越大越好" | 简单问题想太多 = 又慢又贵，按复杂度设 |
| "新特性全上" | 特性越多排查面越大，条件优化按需开 |
| "升级后行为不变" | 特性组合（推测解码 × KV 卸载 × CUDA Graphs）升级后要重测 |

## 6. 本模块小结

> 🎯 **核心要点**：高级特性四件套各有各的门——推测解码管延迟（小模型草拟 + 大模型验收，接受率 >50% 才开，高并发下反而有损）、thinking budget 管推理模型的思考成本（按复杂度动态设预算）、工具调用/结构化输出是 Agent 标配（v0.23 起 Rust 前端统一）、工程化特性按需取用。选择哲学：**vLLM 的每个优化都有适用边界，"默认开启"的只有三大核心机制**——高级特性全是条件优化，先测再开、劣化就关。
