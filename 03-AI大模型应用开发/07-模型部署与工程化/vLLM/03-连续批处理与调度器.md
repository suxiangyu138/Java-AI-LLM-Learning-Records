# 03 连续批处理与调度器

> PagedAttention 解决了"显存装得下多少并发"，连续批处理解决"并发如何被高效调度"——它是 vLLM 吞吐优势的第二根支柱，本质是把 GPU 从"等批"中解放出来。

## 1. 批处理的演进

推理服务的批处理经历了三代演进，每一代都在解决上一代的空转问题：

```text
静态批处理：攒够一批才开工 → 等待期 GPU 空转；一个慢请求拖住全批
动态批处理：请求到达即加入 → 批内进度不同步，仍要等最慢的
连续批处理：完成的请求立即出批、新请求随时进批 → GPU 永不空转
```

传统静态批处理的 GPU 利用率约 60%，连续批处理提升到 85-95%，吞吐提升 10-30%（混合长度流量下最高 40-60%）。这也是实测对比里 vLLM 在 8 并发时约 187 tok/s、Ollama 约 82 tok/s 差距的来源——差距不在模型执行，而在调度。

## 2. 连续批处理的调度模型

核心机制是"每次解码迭代重新调度"：引擎在每一轮前向计算前，检查当前批次——谁完成了（踢出）、谁还在（继续）、谁在排队（加入）——动态组装本轮批次。

```text
t=0  批次 [A(生成中), B(生成中)]          新请求 C 到达
t=1  批次 [A(生成中), B(完成→出批), C(进批)]   A 也快完成了
t=2  批次 [A(完成→出批), C, D(新进)]         GPU 始终满负荷
```

三个工程要点：

1. **准入控制**：不是来多少接多少——批次大小受显存（KV 页）与 `--max-num-seqs` 约束，超额请求排队。
2. **公平性**：默认 FCFS，长请求不会饿死短请求；并发上限内长短混合。
3. **尾部延迟**：单请求延迟可能被并发摊薄（吞吐优先的代价）——延迟敏感场景靠 09 篇的推测解码或独立实例。

## 3. Chunked Prefill：长输入不阻塞

prefill（输入解析）与 decode（逐 token 生成）是两种截然不同的计算形态：prefill 是密集矩阵乘、decode 是访存密集。传统实现里，一个长输入的 prefill 会独占 GPU 数秒，期间所有 decode 请求全部等待——这就是"一个 10 万字文档让整个服务卡死"的根源。

Chunked Prefill 把长 prefill 切成小块，与 decode 请求交错执行：

```text
传统：prefill(100K token) 独占 GPU 30s → 期间 decode 全部阻塞
Chunked：prefill(2K/块) × 50 块，与 decode 交错 → 无长阻塞
```

代价是单请求的 prefill 总时间略增（交错引入切换开销），换来的是整体服务延迟的稳定。生产配置 `--max-num-batched-tokens` 控制单批 token 上限，间接决定 chunk 大小——调小保延迟稳定，调大保吞吐。

## 4. 调度器与优先级

调度器（Scheduler）是连续批处理的决策核心，vLLM 的调度策略分两层：

| 层 | 决策 | 策略 |
|---|---|---|
| 批内调度 | 本轮批次装哪些请求 | 按到达顺序 + 优先级；长 prefill 自动 chunk |
| 显存调度 | KV 页如何分配/驱逐 | 按需分配；前缀缓存 LRU 驱逐；溢出走 KV offload |

v0.23.0 起 MRv2 调度器成为默认，与旧调度器的差异在细粒度批内重排与更好的长上下文处理。对使用者而言，调度器的可配置面很小（`--max-num-seqs`、`--max-num-batched-tokens`），大部分策略是内建最优——**别乱调，先理解，再按压测结果微调**。

## 5. CUDA Graphs 加速

CUDA Graphs 把一串 GPU kernel 启动"录制"成一张图，执行时一次启动整图——消除 kernel 启动开销（每 kernel 数微秒到数十微秒）。

```text
传统：每 token 触发 50 个 kernel × 每次启动开销 → 短请求被启动开销淹没
CUDA Graphs：图捕获后整图执行 → 短请求/低并发场景提速显著
```

vLLM 默认启用 CUDA Graphs；2026 年 v0.25.0 让动态推测解码与完整 CUDA Graphs 兼容（此前二者互斥）。注意：图捕获会预占一部分显存（`--cpu-offload-gb` 与图大小相关），显存极紧时可用 `--enforce-eager` 关闭换稳定性——但生产默认开着。

### 5.1 吞吐与延迟的权衡认知

连续批处理的核心代价常被忽略：它以单请求延迟为代价换取整体吞吐。在连续批处理下，一个请求的完成时间取决于"它被调度进批次的时机"——高并发时新请求要排队等批次空位，这让尾延迟（P99）明显抬升。生产调优的本质是在两端找平衡：`--max-num-seqs` 调大提升吞吐但抬高 P99，调小保延迟但浪费 GPU。两个务实的处理方式：一是延迟敏感场景（客服、交互）与吞吐优先场景（批处理、离线）分开部署实例，各配各的参数；二是用监控区分"队列等待"与"计算耗时"——TTFT 劣化时先看队列深度（调度问题）再看 GPU 利用率（计算问题），两个信号指向完全不同的解法。

另一个认知是"连续批处理对请求混合形态敏感"：全是短请求时批次切换频繁、收益有限；长短混合时收益最大（短请求插空、长请求填满）；全是超长请求时退化为近串行。所以压测要用业务真实的长短混合流量，纯短或纯长的压测数据都不能代表生产表现——这也是"压测要复现生产流量分布"这句老话在 vLLM 场景的具体含义。

### 5.2 与 PagedAttention 的协同

连续批处理与 PagedAttention 的协同关系值得单独讲清：连续批处理决定了"每轮批次装哪些请求"，PagedAttention 决定了"这些请求的 KV 页从哪里分配"——前者管调度、后者管资源，两者在调度器里汇合。每轮迭代，调度器先决定批次（连续批处理逻辑），再为批内请求分配/回收 KV 页（分页逻辑），一次决策同时完成调度与显存管理。这个协同是 vLLM 高性能的结构性原因：传统方案里调度与显存分离（调度只看队列、显存只按预留），而 vLLM 把两者合并进同一决策循环，让"显存余量"直接参与调度决策——显存够才放请求进批，放进去就一定有页可用，从根上避免了"调度进去了却 OOM"这类传统框架的经典故障。

### 5.3 常见误区速排

| 误区 | 事实 |
|---|---|
| "连续批处理是默认的批处理" | 它是 vLLM 的招牌，不是所有引擎都有 |
| "并发越高延迟越低" | 吞吐与 P99 延迟是权衡，高并发必然抬尾延迟 |
| "Chunked Prefill 关掉更快" | 长输入场景关掉 = 一个文档卡死全服务 |
| "调度策略可以随便调" | 大部分策略内建最优，可调面只有两个参数 |

## 6. 本模块小结

> 🎯 **核心要点**：连续批处理 = 每轮迭代动态组装批次（完成出批、新请求进批），GPU 利用率 60% → 85-95%，这是 vLLM 吞吐领先的调度层原因。三个配套机制各管一摊：Chunked Prefill 防长输入阻塞、调度器做准入与显存分配、CUDA Graphs 消 kernel 启动开销。生产参数记住两个：`--max-num-seqs`（并发上限）与 `--max-num-batched-tokens`（批大小/chunk 控制）——其他调度策略信任内建默认。
