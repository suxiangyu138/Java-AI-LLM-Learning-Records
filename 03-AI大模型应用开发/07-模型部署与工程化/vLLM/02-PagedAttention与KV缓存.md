# 02 PagedAttention 与 KV 缓存

> PagedAttention 是 vLLM 的成名之作：把 KV 缓存从"连续大块内存"变成"按页分配的小块内存"，显存碎片问题从根上消失——这是 vLLM 一切性能优势的地基。

## 1. KV 缓存为什么会浪费显存

推理时，模型每生成一个 token 都要把之前的 Key/Value 向量保存下来供注意力计算使用——这就是 KV 缓存。问题出在传统实现的分配方式：**为最长可能上下文一次性分配连续内存**。

```text
传统方案：为 32K 上下文预留一整块连续显存
实际请求：只用了 2K → 93% 显存闲置但被"预留占用"
并发 20 个请求 → 20 块预留内存，碎片与浪费叠加
```

后果是残酷的：KV 缓存碎片化导致 60-80% 的显存被浪费——不是不够用，是"用不起来"。这正是"显存看着够，一并发就 OOM"的根源。

## 2. PagedAttention 的分页思想

PagedAttention 把操作系统虚拟内存的分页思想搬进 GPU：KV 缓存按固定大小（16 token 一页）分成块，按需分配、不连续也没关系——用一张"页表"记录逻辑页到物理页的映射。

```text
逻辑视角：请求 A 的 KV 是连续的 1-100 页
物理视角：页散落在显存各处，页表记录真实地址
收益 1：只分配实际需要的页（不用预留 32K）
收益 2：碎片消失（小块页可以拼进任何空隙）
收益 3：同一页可被多个请求共享（前缀缓存的地基）
```

三个收益对应三个能力：显存按需分配（省）、碎片消除（装更多并发）、页共享（前缀缓存）。PagedAttention 不是优化技巧，而是把 KV 缓存管理从"一次性大块"升级为"按页精细管理"的架构级改变。

## 3. 显存节约的量化对比

| 场景 | 传统方案 | PagedAttention | 收益 |
|---|---|---|---|
| Qwen3-8B @ 32K 上下文 | 49.6GB | 5.2GB | 省 89% |
| 内部碎片（并发场景） | 60-80% | <4% | 碎片消失 |
| 单卡并发请求数 | 2-4 个 | 50-100 个 | 数量级提升 |

> 💡 关键理解：PagedAttention 省的不是"模型权重"显存，而是"KV 缓存"显存——权重显存是固定的，KV 才是并发场景的变量。这也是为什么"显存公式 ×1.5-2"里那 0.5-1 的余量，在 vLLM 里可以被压得很低。

## 4. KV 缓存容量估算

生产规划前先算 KV 账，公式与示例：

```text
每 token KV 显存 = 2 × 层数 × KV heads × head_dim × 字节数

示例 Llama 3 70B（BF16）：约 320KB/token
100 用户 × 4K 上下文 = 100 × 4096 × 320KB ≈ 125GB
→ 单卡 80GB 装不下，需要量化 KV 或换更大卡
```

估算的意义：先算 KV 账，再定 `--max-model-len` 与 `--gpu-memory-utilization` 的分配比例。权重 + KV 都在同一批显存里，比例失衡（权重占满、KV 没空间）是生产最常踩的配置错误。

## 5. 2026 演进：MRv2 与 Blackwell

| 演进 | 内容 |
|---|---|
| v0.25.0 MRv2 | Model Runner V2 成为 dense 模型默认执行路径，legacy PagedAttention 代码移除——分页概念内化为新内核底座 |
| 动态页大小 | Blackwell B200 优化：固定 16-token 页改为 4/8/16 多尺寸页，短请求内存浪费降 75% |
| FP8/FP4 混合精度 | 新内核支持混合精度张量核，Llama-3-70B FP8 吞吐 2.2 倍、TTFT 降 40% |
| 通信优化 | 三级通信（本地/共享内存分页）多卡同步开销降 60%，可扩展至 64 卡 |

> ⚠️ 版本注意：Blackwell 相关优化（动态页/FP4）部分来源单一，落地前以官方 release notes 为准；v0.25.0 升级需关注自定义集成对旧 PagedAttention 接口的依赖。

### 5.1 从原理到工程的两个推论

PagedAttention 的原理带来两个容易忽略的工程推论。第一个推论是"KV 缓存是可管理的资源，不是不可控的开销"：传统方案里 KV 是"预留多少就占多少"，分页之后 KV 变成"用多少占多少"——这直接催生了前缀缓存（页共享）、KV 量化（页内容压缩）、KV offload（冷页换出）三项能力，它们全是建立在"页"这个可操作单元之上的。理解这一点，就能理解为什么 vLLM 的优化选项总是围绕 KV 展开：不是 KV 特别重要，而是它第一次变得可控。

第二个推论是"显存规划要先算 KV 账再算权重账"：很多人部署时只关注模型权重占多少显存（毕竟那是模型卡上写的数字），但并发场景下 KV 才是变量——权重是固定开销，KV 随上下文与并发线性增长。生产上"权重 60% + KV 30% + 余量 10%"的分配比例，是在 KV 账算清楚之后才能定下来的。算不清楚的后果很典型：压测时单请求正常、并发一到就 OOM，然后归咎于"卡不够大"——其实只是 KV 分配没规划。

### 5.2 分页思想在其他环节的延伸

PagedAttention 的分页思想不止于 KV 缓存，它已经扩散到 vLLM 的多个环节：前缀缓存的页共享（05 篇）、KV 量化后的页压缩（06 篇）、KV 卸载的页换出（05 篇）、分布式缓存的页迁移（Mooncake）。这套"以页为操作单元"的设计贯穿始终，是 vLLM 架构一致性的体现——理解"页"这个抽象，就能快速理解 vLLM 的大多数新特性，因为新特性大多是对"页"的某种新操作。这也是面试时可以展开的深度：PagedAttention 的意义不止于显存优化，它把 KV 缓存变成了"可编程的资源"，后续所有 KV 相关的优化都是在这个资源模型上做文章。

### 5.3 常见误区速排

| 误区 | 事实 |
|---|---|
| "PagedAttention 被移除了" | v0.25 移除的是 legacy 实现，概念已并入 MRv2 内核 |
| "KV 缓存占显存不大" | 长上下文并发场景 KV 与权重同级，100 用户 × 4K 可达 125GB |
| "显存不够就加卡" | 先算 KV 账，可能量化 KV 就够，加卡是最后手段 |
| "权重显存 = 部署所需" | 权重 + KV + 余量三部分，KV 是变量 |

## 6. 本模块小结

> 🎯 **核心要点**：PagedAttention = KV 缓存的分页管理（按需分配/碎片消失/页共享），显存浪费从 60-80% 降到 4% 以下，单卡并发从个位数到 50-100。它是前缀缓存（05 篇）的地基，也是 vLLM 高并发的根因。2026 年 v0.25.0 将其概念并入 MRv2 内核，Blackwell 动态页与 FP8 混合精度带来新一轮提升。生产纪律：先算 KV 账（320KB/token 级），再分配权重与 KV 的显存比例。
