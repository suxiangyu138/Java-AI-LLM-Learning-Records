# 08 运维监控与成本管理

> 私有化部署上线只是开始，运维决定生死：三个指标盯健康、一套监控栈看全貌、TCO 算清经济账——不会运维的私有化，硬件就是最贵的摆设。

## 1. 三大核心指标

| 指标 | 定义 | 健康基线 |
|---|---|---|
| TTFT | 首 token 延迟（交互体验关键） | < 2s（短上下文）；劣化先查模型是否被换出显存 |
| 吞吐 | token/s（并发能力） | 稳定即可；持续下降查批处理与显存 |
| 显存占用 | GPU 利用率与显存水位 | 90% 封顶，超了先降并发再升硬件 |

三个指标盯不住的运维不是运维。**TTFT 是私有化最常翻车的指标**：模型被换出显存（Ollama KEEP_ALIVE 到期）、上下文过长、并发打满，都会让首 token 从 0.5s 飙到 5s+——体验从"本地部署很快"变成"比云端还慢"。

## 2. 监控栈搭建

```text
Prometheus（采集）→ Grafana（看板） + Alertmanager（告警）

vLLM：/metrics 端点原生 Prometheus 格式（吞吐/时延/显存/KV 缓存）
Ollama：ollama ps 脚本采集 + node_exporter 补系统指标
GPU：DCGM Exporter（NVIDIA 官方，显存/温度/利用率）
```

| 组件 | 作用 | 注意 |
|---|---|---|
| Prometheus | 指标采集与存储 | 保留策略按成本定（15 天默认） |
| Grafana | 可视化看板 | 三指标 + GPU 温度/功耗一屏 |
| Alertmanager | 告警路由 | 按严重级分通道（钉钉/邮件） |
| node_exporter/DCGM | 系统与 GPU 指标 | 阈值：显存 90%、GPU 温度 85°C |

监控原则：**先盯三个业务指标，再扩展系统指标**——不要一上来堆 30 张看板，运维的核心是"5 分钟内定位：模型问题还是硬件问题还是网络问题"。

## 3. 日志与告警

| 日志 | 内容 | 注意 |
|---|---|---|
| 访问日志 | 调用者/模型/参数摘要/耗时/结果类型 | 脱敏（见 07 篇），不落完整输入输出 |
| 引擎日志 | 加载/错误/显存事件 | Ollama 看 journalctl，vLLM 看容器日志 |
| 错误日志 | 4xx/5xx/超时 | 与访问日志关联 request_id |

告警四件套（按严重度）：P0 服务不可用 → 立刻；P1 显存 90%+ → 5 分钟；P2 吞吐下降 50% → 15 分钟；P3 延迟翻倍 → 小时级。**告警要可执行**：每条告警配"先看哪条命令"（如显存告警 → `ollama ps` 看模型驻留），不然告警就是噪音。

## 4. 模型更新与灰度

模型更新是私有化特有的高频运维动作（新模型、新量化档位），流程：

```text
① 评测：新模型跑离线评测（业务用例 + 安全回归）对比旧模型
② 预下载：内网先拉好权重（或离线导入），校验哈希
③ 灰度：网关路由 10% 流量到新模型实例，观察三指标与用户反馈
④ 全量：灰度通过后切全量，旧实例保留 1-2 周可回滚
⑤ 回收：确认稳定后释放旧模型显存
```

要点：**量化档位变更视为一次完整发布**（质量可能变化）；灰度期间监控"回答质量"只能靠用户反馈与抽检（自动指标看不到质量）；回滚预案要提前写好（网关一条配置切回去）。

## 5. 备份与容灾

| 对象 | 备份策略 | 恢复目标 |
|---|---|---|
| 模型权重 | 可重新下载（内网源） | 不备份，但保存来源与版本清单 |
| 配置 | Modelfile/vLLM 启动参数/网关配置入 git | 分钟级恢复 |
| 会话/知识库数据 | 每日增量 + 每周全量，加密存储 | RPO ≤ 24h |
| 系统镜像 | 关键节点镜像快照 | 硬件故障快速重建 |

容灾现实：单机私有化没有高可用（GPU 挂了就停）；生产级至少 2 副本（vLLM 多实例 + LB）。**先保配置与数据，再谈双机**——配置入 git 是成本最低、收益最大的容灾动作。

## 6. TCO 成本测算

```text
TCO = 硬件投入/折旧年限 + 年度电费 + 运维人力 + 模型更新成本

示例（中小企业生产，2×A10 48GB，约 15,000 美元）：
  硬件折旧 3 年：5,000 美元/年
  电费（2×300W×24h×365）：约 1,500 美元/年
  运维人力（0.5 人）：约 25,000 美元/年
  合计：约 31,500 美元/年 → 对比同量云端 API 是否更优
```

| 成本项 | 优化手段 |
|---|---|
| 硬件 | 翻新卡（第二/三层预算场景）、租赁代替自购 |
| 电费 | 空闲时段缩容/休眠、温度管理 |
| 人力 | 轻量场景用 Ollama 免运维；容器化 + 一键脚本 |
| 模型 | 小模型够用就不上大模型（算力利用率是关键） |

关键判断：**TCO 对比要与 01 篇的用量预测联动**——用量预测错了，TCO 全是空算。私有化的经济性结论：高频高用量才划算，低频场景 TCO 大概率劣于云端 API。

## 7. 运维检查单

```text
□ 三指标（TTFT/吞吐/显存）已监控并有告警
□ 告警可执行（每条配排查命令）
□ 配置全部入 git（Modelfile/vLLM 参数/网关）
□ 数据每日备份且加密，做过一次恢复演练
□ 模型更新流程（评测→预下载→灰度→回滚）文档化
□ TCO 测算与用量预测联动，季度复盘
```

### 7.1 运维排障三板斧

私有化运维的日常排障建议固定成三板斧，顺序不要乱。第一斧看显存：`ollama ps` 或 DCGM 看板确认模型是否驻留、显存水位——超过一半的"变慢"问题根源是模型被换出显存或并发超限，一眼可见；第二斧看指标趋势：Grafana 拉出 TTFT/吞吐最近 24 小时曲线，对比故障时刻与正常时段，确定是突发还是渐进——突发查网络/网关，渐进查显存/上下文；第三斧看日志：网关访问日志与引擎日志按 request_id 关联，定位具体请求的失败原因。三板斧覆盖 90% 的运维问题，剩下的再上抓包与复现实验。

### 7.2 值班与交接

私有化模型服务建议纳入值班体系：告警分级明确 P0（服务不可用）必须 15 分钟内响应；交接文档记录当前模型版本、已知问题、常用排障命令与回滚方法——运维知识不沉淀在个人脑里，而是沉淀在文档里。模型变更（升级/灰度/回滚）后第一时间更新交接文档，这是小团队最容易忽略、也最容易出事的环节。

## 8. 本模块小结

> 🎯 **核心要点**：运维 = 三指标（TTFT/吞吐/显存）+ 一套栈（Prometheus+Grafana+DCGM）+ 可执行告警 + 模型灰度流程 + 配置入 git 的备份。TCO = 硬件+电费+人力+更新，与用量预测联动才有意义。私有化运维的三个高频坑：TTFT 劣化（模型被换出显存）、告警不可执行（成了噪音）、备份只备权重不备配置（恢复不了）。
