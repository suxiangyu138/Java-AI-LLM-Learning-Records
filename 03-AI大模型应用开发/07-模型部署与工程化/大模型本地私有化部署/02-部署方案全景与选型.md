## 1. 五引擎定位

| 引擎 | 一句话定位 | 最佳场景 | 上手难度 | 平台 |
|---|---|---|---|---|
| Ollama | "LLM 版 Docker"，一条命令部署 | 开发原型、个人、小团队 | ⭐ 极低 | Mac/Win/Linux，Apple Silicon 深度优化 |
| vLLM | 生产级推理引擎（UC Berkeley） | 高并发 API 服务、企业生产 | ⭐⭐⭐ | 仅 Linux + NVIDIA GPU |
| llama.cpp | 极致轻量的底层引擎 | CPU/低配/嵌入式 | ⭐⭐ | 全平台，无 GPU 也能跑 |
| LM Studio | 开箱即用桌面 GUI | 模型探索、评测、非技术用户 | ⭐ 极低 | Win/macOS/Linux |
| SGLang | 高性能 + 结构化输出 | 高并发 Agent/复杂推理 | ⭐⭐⭐ | Linux + GPU |

五个引擎全部提供 OpenAI 兼容 API（Ollama 默认 `localhost:11434/v1`、LM Studio 默认 `localhost:1234/v1`、vLLM 默认 8000）——应用代码只需改 base_url 即可切换后端，这是"开发用 Ollama、生产用 vLLM"能无缝衔接的结构性原因。

## 2. 两两对比的关键差异

Ollama vs vLLM（最常被比较的一对）：

| 维度 | Ollama | vLLM |
|---|---|---|
| 吞吐 | 基准约慢 20-30% | PagedAttention 减 KV 缓存浪费 60-80%，高并发吞吐 2-4 倍 |
| 批处理 | 有限 | 连续批处理，GPU 利用率 90%+ |
| 并发 | 单用户/轻量 | 单卡 50-100 并发 |
| 平台 | 跨平台 | 仅 Linux+CUDA |
| 运维 | 单个二进制 + systemd | Python+CUDA 依赖、冷启动数分钟、10GB+ 磁盘 |
| 多卡 | 基础 | 张量并行/流水线并行 |
| 成本 | 低配小机器 | 显存占用高 20-30% |

关键认知：**vLLM 的优势只在负载下才体现**。单用户聊天场景两者吞吐差距不明显，vLLM 反而"过度配置"；10+ 并发场景 vLLM 的连续批处理才真正拉开差距。选型错误的典型形态：小团队用了 vLLM，配置复杂度与资源占用全扛了，吞吐优势一点没吃到。

llama.cpp 是 Ollama 和 LM Studio 的底层引擎（Ollama v0.30.0 起直接对齐 llama.cpp 上游）。需要它"亲自上阵"的场景：纯 CPU 服务器、嵌入式设备、极致内存占用控制。

## 3. 选型决策树

```text
你的场景是？
├─ 个人/开发原型/小团队内网工具 → Ollama（运维面最小）
├─ 非技术用户/模型评测对比 → LM Studio
├─ 生产高并发 API（10-100+ 并发）→ vLLM（NVIDIA GPU）或 SGLang
├─ 纯 CPU/低配/嵌入式 → llama.cpp
├─ Apple Silicon Mac 团队 → Ollama（MLX 引擎加速）
└─ Windows 服务器 → Ollama（vLLM 无 Windows 支持）
```

配套决策：Web 界面统一用 Open WebUI（团队/私有化场景标配）；多租户隔离先于引擎选择考虑——多租户是比引擎更大的成本与治理杠杆。

## 4. 成本决策框架

| 流量形态 | 最优选择 | 理由 |
|---|---|---|
| 高并发稳定流量 | vLLM 连续批处理 | GPU 利用率高，单位 token 成本最低 |
| 突发/单用户 | Ollama + 小机器 | vLLM 批处理大半为空，纯浪费 |
| RAG/多轮 Agent（前缀复用多） | 开前缀缓存（vLLM prefix caching/SGLang RadixAttention） | 复用 KV 缓存大幅降本 |
| 多团队多租户 | 先做租户隔离 | 治理杠杆大于引擎差异 |

## 5. 2026 版本基线

| 引擎 | 2026-08 基线 | 关键变化 |
|---|---|---|
| Ollama | v0.31.2 | v0.30.0（2026-06）重大重构：底层切 llama.cpp、原生支持 HF GGUF、Vulkan 默认启用（AMD/Intel）、NVIDIA 性能 +20%、MLX 引擎 Apple 芯片提速（prefill +57%/decode +93%） |
| vLLM | 0.9.x 系 | 生产标配，前缀缓存/推测解码成熟 |
| LM Studio | 0.4.x | 新增 llmster 无头守护进程（无 GUI 服务器）、LM Link 远程共享（3-10 人小团队） |
| llama.cpp | 持续滚动 | Ollama v0.30 后与其深度对齐 |

> 💡 版本纪律：Ollama v0.30.0 是破坏性变更（底层引擎切换），升级前先读 changelog；LM Studio 适合评测不适合生产（性能比 Ollama 慢 10-15%、内存占用高 40-50%、无 Docker 镜像）。

### 5.1 组合架构与引擎迁移

推荐的企业组合不是"选一个引擎"，而是"开发/生产双轨"：开发环境用 Ollama（秒级拉起、迭代快），生产环境用 vLLM（扛并发），中间靠 OpenAI 兼容 API 与网关路由无缝衔接——模型卡在开发期验证过的代码，切到生产只改 base_url。这种双轨结构同时降低了试错成本与生产风险：新模型先在日常工具里跑一周再上生产，比直接在生产环境赌一把稳妥得多。

引擎迁移的另一个常见路径是"Ollama 起步 → 负载起来后加 vLLM"：小团队先用 Ollama 把产品跑通，用户量上来后在网关后追加 vLLM 实例，两个引擎共存于同一网关（按 model 前缀路由），零停机完成升级。这种渐进式演进比一开始就上重型架构更符合实际节奏。

### 5.2 常见选型误区

这些误区的共同根源是把"引擎"当成了目的而不是手段——引擎只是把模型跑起来的载体，真正决定业务成败的是模型选择、数据质量与安全治理，引擎选型在其中的权重其实不高。想通这一点，选型焦虑就消除大半：**任何一个主流引擎都能把 32B 模型跑好，差别只在并发天花板与运维成本**，而不是"能不能用"。

除上述四条外，还有一个更隐蔽的误区：**"先选引擎再定场景"**。正确的顺序永远是先明确场景（多少用户、多少并发、什么延迟要求、什么平台），再让引擎适配场景——反过来先爱上某个引擎再找理由，选型必然偏差。另一个实践建议：选型前用同一模型在两个候选引擎上各跑一轮基准（单并发 TTFT、10 并发吞吐、显存占用），10 分钟的实测胜过两小时的资料对比——2026 年的引擎差异已经收敛，实测数据比印象分可靠。

| 误区 | 事实 |
|---|---|
| "vLLM 全面比 Ollama 好" | 单用户场景优势不体现，配置复杂度全扛 |
| "LM Studio 能当生产服务" | 无 Docker、并发不成熟，定位是评测 |
| "llama.cpp 过时了" | 它是 Ollama 的底层引擎，CPU 部署唯一答案 |
| "引擎定了就不能换" | OpenAI 兼容 API 让迁移成本趋近于零 |
| "开源模型一定落后很多" | 2026 开源与闭源差距已显著收窄，32B 级覆盖多数业务 |

## 6. 本模块小结

> 🎯 **核心要点**：2026 选型公式 = 场景决定引擎：开发用 Ollama、生产用 vLLM、评测用 LM Studio、穷尽用 llama.cpp、极致高并发用 SGLang。所有引擎 OpenAI 兼容 API 打通，切换零代码改动。两个常见错误：小团队上了 vLLM（过度配置）、生产环境用了 LM Studio（无 Docker 无并发）。Ollama v0.30 重构（llama.cpp 底层 + GGUF 原生）使它与 llama.cpp 生态深度对齐，选择它不再有"格式锁定"顾虑。
