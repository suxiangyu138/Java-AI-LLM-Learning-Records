## 1. 提示词与上下文的关系

回顾核心公式：

```
AI 生成效果 = LLM（Task 任务 + Context 语境 + Prompt 提示词）
```

| 要素 | 类比 | 特点 |
|------|------|------|
| **Prompt（提示词）** | 喊话的内容 | 单次、可复制、边际收益递减 |
| **Context（上下文）** | 对话的环境 | 持续性、决定性、需要长期经营 |

> ⚠️ **核心认知**：新手拼命优化提示词，高手系统构建上下文。提示词决定"这一轮好不好"，上下文决定"整个项目成不成"。

### 1.1 提示词工程在 Vibe Coding 中的定位

传统 Prompt 工程（面向 API 单次调用）关注：指令清晰、示例引导、格式约束。

Vibe Coding 的 Prompt 工程（面向长流程开发）额外关注：

```
Vibe Coding Prompt 三要素
├── ① 一致性：与项目既有代码风格/架构保持一致（最重要）
├── ② 可验证性：输出能被自动/人工快速验证（测试用例、规范检查）
└── ③ 可追溯性：改动点清晰、决策有据（注释、ADR）
```

## 2. 结构化 Prompt 四段式

**角色-任务-约束-输出格式**，是 Vibe Coding 场景下最稳定的 Prompt 骨架：

```text
【角色】你是一名资深后端工程师，精通 Java 17 + Spring Boot 3，
        熟悉本项目的分层架构（controller/service/mapper）与代码规范。

【任务】实现「订单超时自动关闭」功能：
        1. 新增 Scheduled 任务，每分钟扫描超时 30 分钟的待支付订单
        2. 状态流转：PAYING → CLOSED，更新 close_time 字段
        3. 并发安全：使用乐观锁（version 字段）防止重复关闭

【约束】
        - 使用 @Scheduled(cron = "0 * * * * ?")，禁止引入 Quartz
        - Mapper 使用 MyBatis-Plus 的 LambdaQueryWrapper
        - 数据库操作必须走事务，方法名以 Tx 结尾
        - 参考现有代码风格：service 层必须接口 + 实现分离
        - 日志使用 slf4j，关键节点输出 info 级日志
        - 不要修改 Order 实体类，只新增相关代码

【输出】
        - OrderCloseTask.java（定时任务）
        - OrderCloseService.java + OrderCloseServiceImpl.java
        - 3 个单元测试：正常关闭/已关闭不重复/并发冲突场景
```

### 2.1 四段式设计要点

| 段落 | 要点 | 反面案例 |
|------|------|---------|
| **角色** | 给 AI 明确身份与经验画像 | 「帮我写个功能」（无角色） |
| **任务** | 原子化：一次只做一个功能，编号列出子步骤 | 「做整个系统」（任务过大） |
| **约束** | 技术栈/风格/规范/禁止项，引用项目内参考文件 | 只写需求不写约束 |
| **输出** | 明确交付文件清单与测试要求 | 「实现一下」（交付物模糊） |

> 💡 **引用参考文件**是四段式的进阶技巧：`【参考】代码风格请严格对齐 src/main/java/com/xx/config/CorsConfig.java 的注释与命名风格`——把已有代码当 few-shot 示例用，一致性立竿见影。

## 3. 上下文五层模型

按对项目的影响范围分层管理上下文：

```
第 5 层 项目级规则  CLAUDE.md / AGENTS.md / 架构文档 / 目录结构
第 4 层 代码级风格  现有代码、命名规范、设计模式示例
第 3 层 约束级标准  技术栈、依赖版本、安全基线、合规要求
第 2 层 流程级规范  Git 规范、测试要求、CI/CD、Code Review 清单
第 1 层 决策级历史  已解决过的重复问题、ADR 决策记录、踩坑日志
```

### 3.1 各层落地方式

| 层级 | 落地载体 | 优先级 |
|------|---------|:---:|
| 项目级规则 | 仓库根目录 `CLAUDE.md`（或 AGENTS.md） | ⭐⭐⭐⭐⭐ |
| 代码级风格 | 会话开始时引用 2-3 个代表文件 | ⭐⭐⭐⭐ |
| 约束级标准 | 技术选型文档、依赖清单（lock 文件） | ⭐⭐⭐⭐ |
| 流程级规范 | CI 配置文件、PR 模板、测试目录结构 | ⭐⭐⭐ |
| 决策级历史 | ADR 目录、SOLVED.md 踩坑记录 | ⭐⭐⭐ |

> 🎯 **CLAUDE.md 是最重要的上下文资产**：把项目目标、技术栈、目录结构、代码规范、已知约束写进根目录规则文件，每个会话自动加载，一劳永逸。

## 4. 上下文管理三原则

### 4.1 原则一：上下文宁精勿滥

> ⚠️ **上下文腐烂（Context Rot）**：上下文信息过多时，模型反而无法判断优先级，生成质量断崖式下降。

```text
❌ 错误：把整个项目代码全部塞进上下文（5 万行）
✅ 正确：只带相关模块（3-5 个文件）+ 规则文件（CLAUDE.md）
```

| 上下文量 | 效果 |
|---------|------|
| 不足 | 答非所问、风格混乱 |
| 适中（**最优**） | 精准、一致、快速 |
| 过量 | 上下文腐烂、成本爆炸、响应变慢 |

### 4.2 原则二：上下文可裁剪

- 每轮对话结束，主动清理无关内容
- 大文件只带关键段落（`#region` 或按行号截取）
- 用 `/clear` 分段开会话，避免长会话积累噪音

### 4.3 原则三：上下文可沉淀

把「一次性有效」的上下文沉淀为「可复用资产」：

```
一次性上下文 ──沉淀──→ 可复用资产
├── 解决了某个重复问题 → 写入 CLAUDE.md / SOLVED.md
├── 有效的任务描述模板  → 项目模板库（prompts/ 目录）
├── 踩过的坑           → ADR / 踩坑日志
└── 反复使用的指令      → Agent Skills / 自定义命令
```

## 5. 意图工程：分层需求模板

面向大型功能（跨多文件、多模块）时，用「意图工程」替代零散 Prompt：

### 5.1 三层约束模板

```yaml
# intent-spec.yaml 意图规格（示例：用户中心）
业务意图:
  用户: 注册用户、管理员
  场景: 注册、登录、资料修改、权限管理
  交互逻辑: 未登录跳转登录页；管理员可见用户管理入口
技术约束:
  语言/框架: Java 17 + Spring Boot 3 + Vue 3
  数据库: MySQL 8 + Redis 7
  安全: Spring Security + JWT，密码 BCrypt 加密
  规范: 分层架构，禁止 controller 写业务逻辑
验收标准:
  性能: 登录接口 P95 < 300ms
  测试: 核心接口单元测试覆盖率 > 80%
  效果: 通过所有验收用例，无红屏、无控制台报错
```

### 5.2 意图拆解为任务流

```text
意图（用户中心）→ 拆解为 6 个原子任务
├── 01-数据库表设计（user/role/permission）→ 独立 Prompt
├── 02-JWT 认证过滤器                     → 独立 Prompt
├── 03-注册/登录 API                       → 独立 Prompt
├── 04-用户 CRUD + 分页查询                → 独立 Prompt
├── 05-权限注解 @PreAuthorize 接入          → 独立 Prompt
└── 06-Vue 登录页 + 用户管理页             → 独立 Prompt
每个任务：独立会话 + 完整四段式 + 引用第 01 步的产出
```

> 💡 意图工程的核心价值：**把大而模糊拆成小而清晰**，每个原子任务上下文完整、可验证、可回滚。

## 6. 反馈与迭代话术

反馈质量直接决定迭代轮次。对照表：

| ❌ 低效反馈 | ✅ 高效反馈 | 原因 |
|-----------|-----------|------|
| 「不对，重写」 | 「分页接口第 3 行 `page` 参数没校验，加 size ≤ 100 限制」 | 精准定位 |
| 「有点问题」 | 「JSON 返回的 date 字段是 `2026-08-03T00:00:00`，应改为 `2026-08-03`」 | 给出期望值 |
| 「UI 不好看」 | 「列表页卡片间距过大（32px→16px），按钮主色换成 #1677FF」 | 可执行 |
| 「这个 bug 帮我修下」 | 「登录接口报 500：`NullPointerException at LoginServiceImpl:47`，第 47 行 `user.getPhone()` 可能为 null」 | 附上错误上下文 |
| 「再优化一下」 | 「查询接口 QPS 只有 200，用 Redis 缓存用户角色，目标 2000」 | 量化目标 |

### 6.1 高效反馈公式

```text
高效反馈 = 位置定位（文件:行号） + 当前表现（报错/截图/日志） + 期望结果（具体值）
```

## 7. 常见失效模式与修复

| # | 失效模式 | 表现 | 修复方案 |
|---|---------|------|---------|
| 1 | **上下文饥饿** | AI 频繁问基础问题、风格跑偏 | 预加载 CLAUDE.md + 参考文件 |
| 2 | **上下文腐烂** | 越改越乱、前后矛盾 | /clear 开新会话，只带必要上下文 |
| 3 | **任务过大** | 生成一半中断、逻辑残缺 | 拆分为原子任务（2-4 小时粒度） |
| 4 | **约束遗漏** | 用了禁止的依赖/写法 | 约束段逐条清单化，禁止项显式列出 |
| 5 | **幻觉依赖** | 引入不存在的包（slopsquatting 温床） | 约束段锁定版本，依赖变更必须人工确认 |
| 6 | **反馈模糊** | 反复迭代不收敛 | 用反馈公式：位置+表现+期望 |
| 7 | **全量重写** | 修改一处结果重写了整个文件 | 明确指令：只改 xxx 方法，其他不动 |
| 8 | **越权修改** | 改了一堆无关文件 | 约束段声明：禁止修改的文件清单 |

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 提示词定"这一轮"，上下文定"整个项目"——高手构建上下文，新手堆提示词
> 2. 四段式骨架（角色/任务/约束/输出）+ 引用参考文件，是 Vibe Coding 提示词的黄金组合
> 3. 上下文管理三原则：**宁精勿滥、可裁剪、可沉淀**，警惕上下文腐烂
> 4. 大功能用意图工程拆原子任务，反馈用「位置+表现+期望」公式，迭代必收敛
