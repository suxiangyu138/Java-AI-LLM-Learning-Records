## 1. 为什么工程规范是效率核心

### 1.1 数据说话

| 数据 | 来源 | 含义 |
|------|------|------|
| 非标准化 Vibe Coding 返工 **+72%** | McKinsey 2026 | 无规范 = 隐性成本爆炸 |
| **43%** AI 代码生产环境需要调试 | 2026 行业统计 | 默认不信任 AI 输出 |
| 规范化团队成功率 **90%** vs 无规范 30% | 8 项目实战验证 | 规范是成败分水岭 |

### 1.2 规范的本质

```
工程规范的本质 = 给 AI 注入高质量上下文 + 给输出设置质量闸门
├── 规则文件（CLAUDE.md）→ AI 每次生成都遵守
├── 审查流程（Review）   → 人把关每一行合并
├── 质量门禁（CI/CD）    → 机器拦截低质量输出
└── 测试要求（Tests）    → 用可执行标准验收
```

> 🎯 **公式**：代码质量 = 规则前置 × 审查把关 × 门禁拦截 × 测试验收。四者缺一，AI Slop 必然出现。

## 2. 规则文件体系

### 2.1 三层规则文件

| 层级 | 文件 | 内容 | 作用对象 |
|------|------|------|---------|
| 项目根 | `CLAUDE.md` | 项目目标、技术栈、目录结构、规范速查 | 所有 AI 会话 |
| 模块级 | `模块/AGENTS.md` | 模块职责、边界、接口约定 | 该模块相关任务 |
| 功能级 | 任务描述内嵌 | 本次任务的约束与禁止项 | 单次生成 |

### 2.2 CLAUDE.md 标准模板

```markdown
# CLAUDE.md

## 项目概述
用户中心微服务：Spring Boot 3 + Vue 3，支撑 CRM 系统的认证与权限。

## 技术栈
- Java 17 / Spring Boot 3.2 / MyBatis-Plus / MySQL 8 / Redis 7
- 前端：Vue 3 + Element Plus + Vite
- 禁止引入：Quartz、Lombok 之外的代码生成器

## 目录结构
src/main/java/com/xx/
  ├── controller/  # 仅参数接收与校验，禁止业务逻辑
  ├── service/     # 接口 + Impl，业务逻辑所在地
  ├── mapper/      # 数据访问，禁止原生 SQL 拼接
  └── config/      # 配置类

## 代码规范
- 分层：controller → service → mapper，禁止跨层调用
- 命名：类名 PascalCase、方法 camelCase、常量 UPPER_SNAKE
- 异常：统一 BusinessException + 全局异常处理器
- 日志：slf4j，info 记录关键节点，error 记录异常
- 注释：类头注释 + 复杂逻辑行内注释（中文）

## 测试要求
- 新功能必须附带单元测试（JUnit 5 + Mockito）
- 核心接口覆盖率目标 > 80%

## 安全基线
- 密码 BCrypt，禁止明文存储
- 外部输入必须参数化查询，禁止拼接
```

> 💡 规则文件要**精炼可执行**：AI 每次会话都会读取，过长会稀释重点。目标：一屏内读完。

### 2.3 依赖版本锁定

```yaml
# 防幻觉依赖的关键：锁死版本，变更必须人工确认
# pom.xml 片段示例
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.baomidou</groupId>
      <artifactId>mybatis-plus-boot-starter</artifactId>
      <version>3.5.5</version>  <!-- 锁定，禁止 AI 擅自升级 -->
    </dependency>
  </dependencies>
</dependencyManagement>
```

## 3. 代码审查流程

### 3.1 AI 生成 → 人工审查的三道闸

| 闸口 | 时机 | 检查项 |
|------|------|--------|
| **第一道：生成时** | AI 输出后立即 | 是否越权改文件、是否引入新依赖、是否合规 |
| **第二道：PR 时** | 合并前 | 逐行 diff、逻辑正确性、边界条件 |
| **第三道：发布前** | 上线前 | 安全扫描、性能评估、回滚预案 |

### 3.2 审查重点清单（针对 AI 代码）

```text
AI 代码审查重点（与人类代码不同的关注点）
├── ① 幻觉检查：方法/类/依赖是否真实存在
├── ② 边界检查：空值、超长、并发、超时是否处理
├── ③ 风格检查：是否与既有代码一致（AI 倾向自创风格）
├── ④ 安全检查：SQL 注入/XSS/敏感信息硬编码
├── ⑤ 过度设计：是否生成无用抽象（YAGNI）
└── ⑥ 回归检查：是否影响现有功能（AI 常误改相关代码）
```

### 3.3 高风险变更人工强制

```text
需要强制人工逐行审查的变更类型：
├── 🔴 认证/授权相关（JWT、权限注解、密码逻辑）
├── 🔴 支付/资金相关
├── 🔴 用户隐私数据（PII）处理
├── 🟡 数据库结构变更（迁移脚本）
└── 🟡 依赖升级（版本变更）
```

## 4. 测试策略

### 4.1 三级测试金字塔（AI 时代版）

| 层级 | 覆盖 | AI 协作方式 |
|------|------|------------|
| **单元测试** | 单个方法/类 | 让 AI 生成测试，人补充边界用例 |
| **集成测试** | 模块间协作 | 让 AI 编写跨层用例，人工审核数据准备 |
| **端到端测试** | 完整用户流程 | 人工编写核心流程，AI 补充场景 |

### 4.2 测试提示词要点

```text
【任务】为 OrderService.createOrder 编写单元测试
【约束】
- 使用 JUnit 5 + Mockito，禁止引入新测试框架
- 覆盖：正常下单/库存不足/余额不足/并发重复下单
- 断言使用 assertThat（Hamcrest 风格），禁止 System.out
- 命名遵循 given_when_then 风格
【输出】OrderServiceTest.java + 每个用例一句话说明测试意图
```

> 💡 **测试即验收标准**：把测试用例当作「可执行的验收标准」——AI 生成代码 + AI 生成测试 + 测试通过 = 该任务完成，无需人工猜测。

## 5. CI/CD 质量门禁

### 5.1 流水线设计（AI 时代必须增加的阶段）

```yaml
# GitHub Actions 质量门禁流水线（示意）
name: quality-gate
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 编译
        run: mvn -q compile
      - name: 单元测试        # 门禁 1：新代码必须有测试
        run: mvn test
      - name: 覆盖率检查       # 门禁 2：核心模块覆盖率 > 80%
        run: mvn jacoco:check
      - name: 静态分析         # 门禁 3：SonarQube 代码质量
        run: mvn sonar:sonar
      - name: 依赖漏洞扫描     # 门禁 4：SCA 供应链安全
        run: mvn org.owasp:dependency-check:check
      - name: 构建镜像并推送
        run: docker build -t registry/order-service:${{ github.sha }} .
```

### 5.2 四道质量门禁

| 门禁 | 工具 | 拦截内容 |
|------|------|---------|
| 测试门禁 | JUnit + JaCoCo | 测试失败 / 覆盖率不足 |
| 静态门禁 | SonarQube / Checkstyle | 坏味道、规范违规 |
| 安全门禁 | SAST（Semgrep/CodeQL）+ SCA（Dependency-check） | 漏洞、风险依赖 |
| 部署门禁 | 灰度 + 监控告警 | 线上异常自动回滚 |

> ⚠️ **每个 PR 必过门禁**——静态分析（SAST/SCA）不是可选项，是拦截 AI 代码幻觉与漏洞依赖的最后防线。

## 6. 安全扫描与依赖审计

### 6.1 三类扫描

| 扫描类型 | 工具示例 | 针对问题 |
|---------|---------|---------|
| **SAST 静态应用安全测试** | Semgrep、CodeQL、SonarQube | 注入、硬编码密钥、不安全函数 |
| **SCA 软件成分分析** | OWASP Dependency-Check、Snyk | 已知漏洞依赖、许可合规 |
| **Secrets 检测** | gitleaks、TruffleHog | 误提交的密钥/令牌 |

### 6.2 AI 代码特有安全要点

```text
AI 生成代码高危点排查清单
├── ① 硬编码密钥：AI 倾向把 API Key/数据库密码写死在代码里
├── ② 不安全 SQL：AI 可能拼字符串（若项目未锁 MyBatis-Plus）
├── ③ 反序列化漏洞：AI 生成的反序列化代码未做类型白名单
├── ④ 认证绕过：AI 写的权限判断可能有逻辑漏洞
├── ⑤ 依赖幻觉：引入不存在的包（slopsquatting 攻击面）
└── ⑥ 日志泄露：把敏感信息（手机号/身份证）打进日志
```

## 7. 结构化重构规划

### 7.1 为什么必须规划重构

AI 迭代速度越快，技术债累积越快。**没有重构规划 = 3 个月后无人能改**（包括 AI 自己）。

### 7.2 重构节奏建议

| 周期 | 动作 | 产出 |
|------|------|------|
| 每个功能完成后 | 顺手清理重复代码、无用 import | 保持整洁 |
| 每 2-3 个迭代周期 | 模块级重构：抽公共组件、统一命名 | 结构收敛 |
| 每个里程碑（季度） | 架构评审：分层是否被打破、依赖是否上移 | 架构健康报告 |

### 7.3 重构提示词

```text
【任务】重构 UserServiceImpl，消除 3 处重复的校验逻辑
【约束】
- 抽取 validateUserInput 私有方法，参数为 UserDTO
- 禁止改变对外方法签名（public 方法不动）
- 重构后必须跑全部单元测试验证行为不变
【输出】重构后的文件 diff + 重构说明 + 测试结果
```

> 🎯 **重构铁律**：行为不变性优先——重构前后测试全绿才算成功；AI 重构时明确「禁止改 public 签名、禁止改行为」，否则容易夹带私货。

## 8. 规范落地检查清单

```text
项目启动前（一次性）：
[ ] 创建 CLAUDE.md（技术栈/结构/规范/安全基线）
[ ] 锁定依赖版本（pom.xml / package-lock.json）
[ ] 配置 CI/CD 质量门禁（测试+覆盖率+SAST+SCA）
[ ] 约定代码审查清单与高风险变更范围

每次任务（循环）：
[ ] 四段式 Prompt（角色/任务/约束/输出）
[ ] 约束段声明禁止修改的文件
[ ] 生成后过第一道闸（越权/新依赖/合规）
[ ] 测试用例随代码一起交付
[ ] PR 过第二道闸（逐行 diff 审查）
[ ] 有效上下文沉淀（CLAUDE.md / SOLVED.md）

定期（循环）：
[ ] 依赖漏洞扫描（SCA）结果清零
[ ] 结构化重构按节奏执行
[ ] 技术债清单评审与消化
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 工程规范是 Vibe Coding 的效率核心：返工率 -72% 的差距（McKinsey）就来自规范有无
> 2. 质量 = 规则前置（CLAUDE.md）× 审查把关（三道闸）× 门禁拦截（CI/CD）× 测试验收
> 3. AI 代码审查重点不同于人类代码：幻觉检查、边界检查、风格一致性、安全硬编码
> 4. 重构是强制项不是可选项：行为不变性铁律 + 每 2-3 个迭代周期结构化重构
