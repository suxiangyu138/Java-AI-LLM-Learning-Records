## 1. 为什么需要多 Agent

### 1.1 单 Agent 的瓶颈

| 瓶颈 | 表现 |
|------|------|
| **上下文容量** | 一个会话无法承载整个大型项目 |
| **角色冲突** | 写代码的 Agent 不擅长审视自己的代码 |
| **串行瓶颈** | 前端/后端/测试串行做，周期拉长 |
| **分工缺失** | 没有专职测试/安全视角，漏洞靠运气 |

### 1.2 多 Agent 的价值

```
单 Agent（串行）          多 Agent（并行）
需求 → 编码 → 测试 → 部署    需求
│                          ├→ 前端 Agent
├→ 总耗时 = 各阶段之和      ├→ 后端 Agent
│                          ├→ 测试 Agent
└→ 质量 = 一个视角          └→ 安全 Agent
                           并行执行，总耗时 ≈ 最慢阶段
                           质量 = 多视角交叉验证
```

> 📊 实测：多 Agent 工作流让「一周做出 MVP、一个月上线」成为现实——某 8 人团队用多 Agent 编排，把金融产品 MVP 周期压缩到 7 天。

## 2. 多 Agent 编排架构

### 2.1 主从式编排（最常用）

```
┌─────────────┐     分配任务       ┌─────────────────┐
│  主 Agent    │ ────────────────→ │ 前端 Agent       │
│ （规划/决策） │ ←──────────────── │ Vue 组件/页面    │
│             │      回传结果      ├─────────────────┤
│ 维护全局上下文│                   │ 后端 Agent       │
│ 拆分任务/审查 │                   │ API/业务逻辑     │
│ 仲裁冲突     │                   ├─────────────────┤
│             │                   │ 测试 Agent       │
│             │                   │ 用例/回归        │
└─────────────┘                   └─────────────────┘
```

| 角色 | 职责 | 关键能力 |
|------|------|---------|
| **主 Agent** | 全局规划、任务拆分、质量仲裁 | 架构视野、依赖管理 |
| **执行 Agent** | 垂直领域实现（前端/后端/测试） | 领域技能 |
| **审查 Agent** | 代码审查、漏洞扫描 | 批判性视角 |

### 2.2 编排工具（2026）

| 工具 | 编排方式 | 特点 |
|------|---------|------|
| Claude Code 子 Agent | `Agent` 工具内嵌 | 任务委派 + 结果回传 |
| Cursor 并行子 Agent | IDE 内 worktree 隔离 | 可视化管理 |
| Codex 多 Agent 并行 | 云端并行 | 1M 上下文共享 |
| GitHub 生态 | Actions + Copilot | 异步编排 |

> 💡 **Worktree 隔离**：让每个执行 Agent 在独立 git worktree 中工作，避免并行修改冲突——这是多 Agent 并行落地的工程前提。

## 3. 上下文打通：最高指令软链接法

### 3.1 问题：上下文孤岛

多 Agent 协作的最大难点：**上下文在不同工具之间不流动**——Claude Code 改过的决策，Cursor 不知道；Aider 调整的架构，Copilot 看不到。

### 3.2 解决方案：软链接统一入口

```text
项目根目录
├── CLAUDE.md          ← 规则主文件（唯一事实源 Single Source of Truth）
├── COLLABORATION.md   ← 协作章程（多 Agent 协作专用）
├── ARCHITECTURE.md    ← 架构决策（ADR 聚合）
├── SOLVED.md          ← 踩坑记录
└── prompts/           ← 任务模板库
```

**最高指令软链接法**：在所有 Agent 的配置中，将 `CLAUDE.md` / `COLLABORATION.md` 软链接（或引用）为各自上下文的最高优先级指令：

```bash
# 示例：Cursor 配置引用项目规则
cursor_rules: ["CLAUDE.md", "COLLABORATION.md"]

# 示例：Aider 启动即读规则
aider --message-file COLLABORATION.md

# 示例：Claude Code 原生读取 CLAUDE.md（自动）
# 项目根目录放置 CLAUDE.md 即自动加载
```

### 3.3 COLLABORATION.md 模板

```markdown
# COLLABORATION.md — 多 Agent 协作章程

## 目标
本文件统一所有 Agent 的工作上下文。任何 Agent 开工前必读。

## 角色分工
- 主 Agent：架构决策、任务拆分、质量仲裁
- 前端 Agent：仅修改 frontend/ 目录
- 后端 Agent：仅修改 backend/ 目录
- 测试 Agent：仅修改 src/test/ 目录

## 沟通协议
1. 决策必须回写 ARCHITECTURE.md
2. 踩坑必须追加 SOLVED.md
3. 任务完成必须附测试结果
4. 禁止修改其他 Agent 的工作目录

## 当前状态
- 进行中任务：任务 ID + 负责人
- 阻塞项：阻塞原因 + 需要的协助
```

> 🎯 **核心原则**：所有 Agent 读同一套规则、写同一套记录——上下文不流动的问题，靠「共享文件」解决，而不是靠「多聊天窗口」。

## 4. 上下文腐烂治理

### 4.1 什么是上下文腐烂

> ⚠️ 上下文腐烂（Context Rot）：上下文过多时模型反而无法判断优先级——AI 开发环境不仅要**增加**上下文，还要能**管理、裁剪、调试**上下文。

### 4.2 腐烂信号

| 信号 | 表现 |
|------|------|
| 指令衰减 | Agent 开始忽略 COLLABORATION.md 中的规则 |
| 重点模糊 | 次要需求被当主需求做 |
| 前后矛盾 | 不同 Agent 的实现互相冲突 |
| 成本上升 | token 消耗暴增但产出下降 |

### 4.3 治理手段

```text
治理三板斧
├── ① 裁剪：每会话只带「当前任务 + 规则文件」两级上下文
├── ② 归档：完成的任务从活动上下文移入 ARCHITECTURE.md 归档
├── ③ 刷新：出现腐烂信号立即 /clear + 重新加载规则
```

### 4.4 上下文配额（团队经验值）

| 内容 | 建议占比 |
|------|:---:|
| 规则文件（CLAUDE.md + COLLABORATION.md） | 10% |
| 当前任务相关代码 | 40% |
| 任务描述与验收标准 | 20% |
| 历史决策与踩坑记录 | 20% |
| 其他 | 10% |

## 5. 知识沉淀：Skill 化

### 5.1 从踩坑到 Skill

把「已解决的重复问题处理过程」沉淀为 Skill（技能包）：

```text
踩坑过程 ──沉淀──→ Skill
├── 问题：前端每次报跨域 CORS 错误
├── 解决：后端加 CorsFilter + 前端代理配置
└── 沉淀：cors-fix skill（触发词：跨域/CORS）
```

### 5.2 Skill 结构示例

```yaml
# .claude/skills/cors-fix/SKILL.md
---
name: cors-fix
description: 处理前后端跨域问题，含后端 CORS 配置与前端代理修正
---

# CORS 修复流程
1. 确认报错：浏览器控制台 CORS 错误信息
2. 后端方案：添加 CorsConfigurationSource Bean（代码片段见下）
3. 前端方案：Vite 配置 proxy（代码片段见下）
4. 验证：curl -X OPTIONS 预检请求通过
```

> 🎯 Skill 化的价值：**团队的知识不随人走，而随库走**——新成员（人或 AI）接手项目时，Skill 库就是「领域专家速成手册」。

## 6. 团队落地五步法

| 步骤 | 动作 | 产出 |
|------|------|------|
| **① 选型统一** | 全团队统一主工具 + 规则文件机制 | 工具基线 |
| **② 规则建设** | 产出 CLAUDE.md + COLLABORATION.md | 上下文基建 |
| **③ 试点项目** | 选 1 个低风险项目全流程 Vibe Coding | 经验 + 数据 |
| **④ 复盘沉淀** | 提炼模板、Skill、避坑清单 | 团队资产 |
| **⑤ 推广制度化** | 写入开发流程规范，新项目默认执行 | 制度落地 |

### 6.1 团队落地关键成功因素

```text
✅ 成功因素
├── 规则文件是团队共识产物（全员评审后定稿）
├── 试点项目失败被允许（先验证再推广）
├── 人机审查流程固定（谁审查、审什么、何时审）
└── 数据说话（效率/返工/缺陷率对比基线）

❌ 失败因素
├── 个人乱用 + 团队无规范（AI Slop 温床）
├── 规则文件一人独写、无人遵守
├── 跳过试点直接全员铺开
└── 只引入工具，不调整流程
```

## 7. 人机团队的角色再分工

### 7.1 团队角色演化（2026）

| 角色 | 传统职责 | AI 时代职责 |
|------|---------|-------------|
| 产品经理 | 写 PRD | 意图定义 + 验收标准量化 |
| 架构师 | 技术方案 | **上下文体系设计**（规则/目录/决策记录） |
| 开发者 | 写代码 | 意图转译 + 代码审查 + 质量把控 |
| 测试工程师 | 写测试用例 | 测试策略 + AI 用例审核 |
| 运维 | 部署监控 | 流水线设计 + 门禁策略 |
| **新增：AI 管控者** | — | 上下文管理、Agent 编排、质量仲裁 |

### 7.2 资深工程师的新定位

```
资深工程师 = 架构设计师 + 业务战略师 + AI 管控者
├── 设计 AI 无法设计的：系统边界、演进路径
├── 决策 AI 无法决策的：技术选型、取舍权衡
├── 审查 AI 无法审查的：业务正确性、合规性
└── 沉淀 AI 无法沉淀的：团队知识、工程文化
```

> 💡 2026 共识：**AI 接管的是"写"，人接管的是"想"**——谁的意图定义、上下文管理、质量判断能力强，谁就是新范式下的高价值工程师。

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 多 Agent 的价值 = 并行提速 + 多视角质量；主从式编排 + Worktree 隔离是落地基础
> 2. 上下文流动靠「最高指令软链接法」：CLAUDE.md + COLLABORATION.md 统一所有 Agent 的语境
> 3. 上下文腐烂必须主动治理：裁剪、归档、刷新三板斧
> 4. 团队落地五步法（选型→规则→试点→复盘→制度化），知识 Skill 化沉淀，人机角色再分工
