## 1. 分析师视角的数据库

**数据库是公司数据的"水龙头"**——业务系统把数据存进 MySQL/PostgreSQL/SQLite，分析师用 SQL 拧开龙头取水。本课与数据库主体系（`../../../02-后端核心技术%20微服务%20分布式%20云原生/01-关系型数据库/`）的分工很清晰：**他们管库（建表/索引/运维/性能），我们取数（SELECT 出 DataFrame）**——**"分析师不是 DBA——我们只问三个问题：连上哪、取什么、怎么取快"**。

**三类常见库**：**SQLite**（单文件、零配置——本地小项目/爬虫存储的标配，`../../12-Python爬虫/阶段%203：数据存储/` 爬虫阶段 3 用它存数据）、**MySQL**（公司业务库最常见）、**PostgreSQL**（功能更强、数据分析生态好）——**"先搞清楚你面对的是哪个，连接串不同但取数代码几乎一样"**。

## 2. 连接：SQLAlchemy 统一入口

**SQLAlchemy 是 Python 访问数据库的统一接口**——不管 SQLite/MySQL/PostgreSQL，都通过 `create_engine` 一个入口：

```python
from sqlalchemy import create_engine

# 三类库的连接串（格式：方言+驱动://用户:密码@主机/库名）
sqlite_engine = create_engine("sqlite:///data.db")              # 本地单文件
mysql_engine  = create_engine("mysql+pymysql://root:密码@localhost:3306/sales")
pg_engine     = create_engine("postgresql+psycopg2://user:pw@localhost:5432/sales")
```

**连接心智**：**"engine 只建一次，反复复用"**——`create_engine` 自带连接池，多次调用是浪费；**密码不要硬编码在代码里**（用环境变量——`../../阶段%201：前置基础/01-Python环境与数据分析工具箱.md` 的环境纪律）；**MySQL 连接串注意 `charset=utf8mb4`**（中文乱码的老朋友——爬虫阶段 3 的同款坑）；**连不上先查三件事：服务在跑吗、密码对吗、网络通吗**（`../../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/网络问题排查/` 的排查思路）。

## 3. read_sql 三件套

**pandas 把 SQL 查询结果直接变 DataFrame**：

```python
import pandas as pd

# 1. read_sql_query：自己写 SQL（最常用——分析师的自由）
df = pd.read_sql_query(
    "SELECT order_id, amount, date FROM orders WHERE date >= '2026-01-01'",
    sqlite_engine,
)

# 2. read_sql：与 read_sql_query 等价（别名）
df = pd.read_sql("SELECT * FROM orders LIMIT 100", sqlite_engine)

# 3. read_sql_table：整表读（不写 SQL——适合小表）
df = pd.read_sql_table("orders", sqlite_engine)

# 4. 分块读（大结果集）
for chunk in pd.read_sql_query("SELECT * FROM orders", sqlite_engine, chunksize=100_000):
    process(chunk)
```

**三件套心智**：**"90% 的场景用 read_sql_query 写 SQL"**——因为取数逻辑都在 SQL 里完成（过滤/聚合/排序），DataFrame 拿到手就是接近可分析的状态；`read_sql_table` 适合小表偷懒；**大结果集加 `chunksize`**（和 CSV 分块同一思路——03 篇）——**"SQL 能过滤的别让 pandas 过滤"**——数据库有索引、有优化器，`WHERE` 在库里执行比拉全表到内存再筛快几个数量级。

## 4. SQL 取数纪律

**分析师写 SQL 取数的五条纪律**（DBA 看了会点赞的姿势）：

1. **只取需要的列**——`SELECT order_id, amount` 而不是 `SELECT *`——**"列少取一列，内存少一块"**（3GB 表只读 3 列可能是 30MB）
2. **用 WHERE 过滤**——`WHERE date >= ...` 把行数降下来——**"过滤在库里做，不在 pandas 里做"**
3. **先 LIMIT 探路**——`LIMIT 1000` 先看结构再全量——**"和 CSV 的 nrows 同一思路"**
4. **参数化防注入**——**永远不要用字符串拼接 SQL**：`f"SELECT ... WHERE id = {user_input}"` 是注入漏洞（`../../../02-后端核心技术%20微服务%20分布式%20云原生/09-Web开发全流程/Web%20高阶知识/` 的 SQL 注入章节）——用占位符：

```python
# 正确姿势：占位符（? 是 SQLite，%s 是 MySQL/PostgreSQL）
safe = pd.read_sql_query(
    "SELECT * FROM orders WHERE city = ? AND date >= ?",
    engine, params=("北京", "2026-01-01"),
)
```

5. **不连生产库跑重查询**——大查询会拖垮业务——**"先问 DBA：这个库是生产还是分析库？"**——分析库/只读副本才是分析师的地盘。

**纪律心智**：**"SQL 取数 = 把过滤和瘦身做在源头"**——从库到 DataFrame 的数据量是第一条内存线——**"SELECT * 拉全表是分析师的三大罪之一"**（另两大罪：不看 schema 直接跑、乱连生产库）。

**与 DBA 协作的心智**：分析师和 DBA 是"取数与管库"的搭档——**问 DBA 三件事**：**① 有没有分析库/只读副本**（别在生产库跑重查询）；**② 大表有没有索引**（没索引的 `WHERE` 是慢查询——`EXPLAIN` 看执行计划是 DBA 的活，但分析师要会看"有没有走索引"）；**③ 数据口径谁说了算**（`amount` 含不含税、`date` 是下单还是支付时间——**"口径问题不问 DBA，分析结论就是空中楼阁"**——09 篇数据契约在库场景的落地：把口径写进契约文档）。**"会问 DBA 的分析师，比会写复杂 SQL 的分析师更受欢迎"**——因为问对问题 = 少走弯路。

## 5. 增量读取

**数据每天在涨，全量重读越来越慢——增量读取只读"新增部分"**：

```python
# 断点续读：记住上次读到哪，这次只读新的
last_id = get_last_processed_id()          # 从本地记录上次处理到哪
df_new = pd.read_sql_query(
    "SELECT * FROM orders WHERE id > ? ORDER BY id", engine, params=(last_id,),
)
process(df_new)
save_last_processed_id(df_new["id"].max())  # 更新断点
```

**增量心智**：**"增量的核心是断点（watermark）"**——用自增 id 或时间戳当断点，每次只取 `id > 上次的 max(id)`；**断点要持久化**（存本地文件/小表，别放内存——进程一重启就丢）；**增量取数要配合幂等处理**（重复取到同一批数据不产生错误——爬虫阶段 3 的去重策略同款思路：`UNIQUE` 约束兜底）；**时间断点要注意时区和"迟到数据"**（凌晨 1 点补录昨天的单，`date > 上次时间` 会漏——**"用 id 断点最稳，时间断点要留余量"**）。

**SQLite 与 MySQL 的取数差异**（都是 SELECT，但细节不同）：**连接串不同**（`sqlite:///` vs `mysql+pymysql://`——04 篇第 2 节）；**参数占位符不同**（SQLite 用 `?`，MySQL/PostgreSQL 用 `%s`——**"换个库第一个踩的坑就是占位符"**）；**SQLite 单写多读**（并发写入会锁库——不适合高并发业务，适合本地分析）；**MySQL 有 `LIMIT` 也别忘了 `ORDER BY`**（不排序的 LIMIT 拿哪 100 行是随机的——**"LIMIT 之前先 ORDER BY，否则结果不可复现"**）。
