## 1. 业务背景与事件数据

**背景**：某电商 App 想提升"下单转化率"——运营直觉认为"用户到支付就流失了"，但数据怎么证明？**漏斗分析回答"用户走到哪一步流失、哪一步流失最严重"**。

**数据形态（事件流——和报表完全不同的数据模型）**：

```python
import pandas as pd

# 事件流：每行 = 一个用户行为（埋点数据——2026 年电商标配）
events = pd.read_csv("data/raw/user_events.csv", encoding="utf-8-sig")
# 列：user_id, event（view_item/click_buy/add_cart/order/pay）, page, ts, channel
print(events.head(), events["event"].value_counts())
```

**事件数据心智**：**"报表数据是'结果表'（一行一笔订单），事件数据是'过程表'（一行一个动作）"**——漏斗分析必须用事件数据；**事件列是固定的"动词集合"**（`value_counts` 一眼看全——"事件字典先背下来"）；真实数据可用淘宝天池用户行为数据集（1 亿条行为记录——`../阶段%203：数据来源（数据从哪里来）/02-公开数据集与数据平台.md` 的天池中文业务场景），练习用模拟事件流（`../阶段%203：数据来源（数据从哪里来）/08-数据模拟与合成.md` 业务模拟）。

## 2. 漏斗定义：先设计再计算

**漏斗不是"算出来的"，是"设计出来的"**——第一步：定义关键路径：

```python
# 漏斗路径定义（业务方 + 分析师共同确认——契约思维）
FUNNEL = [
    ("view_item", "浏览商品"),
    ("click_buy",  "点击购买"),
    ("add_cart",   "加入购物车"),
    ("order",      "提交订单"),
    ("pay",        "支付成功"),
]

# 时间窗：一次购买旅程最多 7 天（用户可能隔几天才下单）
WINDOW = "7D"
```

**定义心智**：**"漏斗设计三要素：路径、顺序、时间窗"**——路径（哪几步）、顺序（必须按序吗——浏览→点击→加购→下单→支付是典型线性漏斗）、时间窗（7 天内算一次旅程——**"不设时间窗的漏斗会把两个月的动作算成一次"**）；**漏斗的粒度要问业务**——"加购物车"算不算"购买意图"？（口径问题——`../阶段%203：数据来源（数据从哪里来）/09-数据质量与来源管理.md` 的契约精神）——**"漏斗设计错了，计算再对也是错的"**。

## 3. 漏斗计算

```python
# 每个用户按时间排序，找出每个事件的"首次发生"
events["ts"] = pd.to_datetime(events["ts"])
events = events.sort_values(["user_id", "ts"])

# 计算每个漏斗步骤的独立用户数（去重！）
funnel_counts = []
for event, name in FUNNEL:
    users = events[events["event"] == event]["user_id"].nunique()
    funnel_counts.append({"step": name, "users": users})

funnel_df = pd.DataFrame(funnel_counts)
funnel_df["conv"] = funnel_df["users"] / funnel_df["users"].iloc[0]   # 总转化率
funnel_df["step_conv"] = funnel_df["users"].shift(1)                  # 上一步到本步
funnel_df["step_conv"] = funnel_df["users"] / funnel_df["users"].shift(1)  # 步间转化率
print(funnel_df)
```

**计算心智**：**"漏斗每一步都算'独立用户数'（`nunique`）"**——不是事件次数（一个用户点 10 次购买算 1 人）——**"漏斗是'人'的漏斗，不是'动作'的漏斗"**；**两个转化率口径**：**总转化率**（相对第一步——"浏览 100 人中 3 人支付"）与**步间转化率**（相对上一步——"加购的人里 60% 提交了订单"）——**"总转化率看全局，步间转化率看瓶颈"**；总转化率 = 步间转化率连乘（3% ≈ 30% × 50% × 20% × ...）——**"漏斗像水管：总流量 = 每段通过率的乘积"**。

## 4. 流失点诊断

**漏斗算完，看"最大的流失裂缝"在哪**：

```python
# 流失 = 1 - 步间转化率
funnel_df["drop"] = 1 - funnel_df["step_conv"]
print(funnel_df[["step", "step_conv", "drop"]])

# 流失量（绝对人数）——流失最严重的环节
funnel_df["drop_users"] = funnel_df["users"].shift(1) - funnel_df["users"]
worst = funnel_df.dropna().sort_values("drop_users", ascending=False).iloc[0]
print(f"最大流失环节：{worst['step']}，流失 {worst['drop_users']:.0f} 人")
```

**诊断心智**：**"流失看两个口径：流失率（相对）和流失量（绝对）"**——"支付页流失率 50%"如果只有 10 人走到那，绝对流失只有 5 人；"加购页流失 30%"但 1000 人走到那——**"改支付页救 5 人，改加购页救 300 人——改最大流失量，不是最高流失率"**——这是漏斗分析最有价值的结论形态；**"瓶颈在哪就修哪"**的落地动作要配合业务排查（支付页加载慢？价格不透明？——**"漏斗指出伤口，业务找病因"**）。

## 5. 分群漏斗

**总漏斗会掩盖人群差异——按渠道/设备/新老用户拆分**：

```python
# 按渠道分群算漏斗
results = {}
for channel, g in events.groupby("channel"):
    funnel = []
    for event, name in FUNNEL:
        n = g[g["event"] == event]["user_id"].nunique()
        funnel.append(n)
    results[channel] = funnel

by_channel = pd.DataFrame(results, index=[n for _, n in FUNNEL])
# 对比：哪个渠道总转化率高？哪个渠道在"支付步"特别差？
print(by_channel)
```

**分群心智**：**"分群漏斗回答'哪群人转化差'"**——渠道 A 总转化 5%、渠道 B 2%——A 是优质渠道要加大投放？**先看成本**（A 的获客成本可能高 3 倍——"转化率 × 获客成本 = 真实价值"）；**分群维度按业务假设选**（渠道/设备/新老用户/城市——分群 = 假设，`../阶段%202：核心三大库（必学）/Pandas%20—%20数据分析主力库/04-分组聚合groupby.md` 的"分组维度 = 业务假设"）；**分群后依然要回到"最大流失量"**——"新用户在支付页流失 500 人，老用户只流失 50 人——修复方向是'新用户支付引导'"——**"分群让诊断更精准"**。

## 6. 结论与建议

**报告结论（三段式）**：

```markdown
# 电商转化漏斗分析报告

## 结论
1. 现象：整体转化 3.1%（浏览→支付）；最大流失环节是"点击购买→加购"，
   流失率 58%、绝对流失 8,200 人/周；支付步流失率 15% 但绝对流失仅 300 人。
2. 原因（待业务确认）：加购流失 58% 异常高——可能加购入口不显眼
   或商品页信息不完整（价格/库存）；支付步流失 15% 正常（支付方式受限等）。
3. 建议：① 优先优化商品页到加购路径（目标：步间转化率提升 10pp）；
② 分群发现"新用户支付引导缺失"——新用户支付流失是老用户的 10 倍；
③ 渠道对比：渠道 A 转化最高但成本高，建议按 ROI 而非转化率分配预算。

## 局限
无对照组，无法验证"改版是否有效"（实验见 08 篇 A/B 测试）；
事件埋点可能漏报（覆盖率未验证）；时间窗 7 天假设待业务确认。
```

**建议心智**：**"漏斗报告的价值 = 指出'改哪里收益最大'"**——"改支付页救 5 人，改加购页救 300 人"是可量化的优先级；**"埋点覆盖率"是事件数据的质量前提**（漏报 20% 的事件，漏斗比例仍成立但绝对量失真——`../阶段%203：数据来源（数据从哪里来）/09-数据质量与来源管理.md` 的体检清单）；**"无对照组"要写进局限**——漏斗是"观察"，验证改版效果要实验（08 篇的伏笔）。
