**毕业验收标准（模拟"上线评审"）**：

```markdown
# 毕业评审自检
- [ ] 问题与指标：业务目标 → 指标选型（代价矩阵讲清）
```

**毕业项目心智**：**"毕业项目 = 你面试时'能讲 10 分钟'的代表作品"**——**"面试官不问'分数多高'，问'泄漏怎么查的、阈值怎么定的、漂移怎么监控的'"**——本项目的每个环节都要经得起追问；**用真实数据加分**（真实公开数据集——阶段 3 02 篇——"真实数据的问题（缺失/噪声）才是练习价值"）；**控制规模**——"全链路跑通 > 单环节炫技"（"模型 0.85 但没部署 = 半成品；模型 0.8 但全链路完整 = 成品"）。

## 3. 报错速查 10 条

| 报错/现象 | 原因 | 解法 |
|---------|------|------|
| `ValueError: Input contains NaN` | 特征还有缺失 | 建模前 `X.isna().sum()`（模型不吃 NaN） |
| 训练分数 0.99 测试 0.6 | 泄漏/过拟合 | 先查泄漏三问（02 篇）再查过拟合 |
| `ConvergenceWarning` | 线性模型没收敛 | 加 `max_iter` / 特征标准化 |
| LightGBM 报 `bin_construct_sample_cnt` | 数据问题 | 检查类别/缺失异常值（先体检） |
| `KMeans` 结果每次不同 | 没设 random_state/n_init | `n_init=10, random_state=42` |
| 时序预测"未来泄露" | 特征用了未来 | 时序特征只用"截至 t 的信息"（02/07 篇） |
| SHAP 序列化报错 | 版本不兼容 | 锁 `shap==0.46.0` + 与模型同版本部署（09 篇） |
| MLflow 加载模型失败 | 依赖版本不一致 | requirements.txt 锁全版本（09 篇第一纪律） |
| API 预测延迟高 | 模型大/无缓存 | 模型预热 + 批量/缓存（09 篇） |
| PSI 一直 >0.25 | 阈值/参考分布不对 | 参考分布用训练集（不是测试集）——先对齐基线 |

**报错心智**：**"ML 报错的排查顺序：数据 → 泄漏 → 版本"**——"60% 的 ML 报错是数据问题、25% 是泄漏、10% 是版本——**'报错先看数据，别急着改模型'"**——把新踩的坑加进自己的速查表。

## 5. 面试演练

**ML 工程师面试问答（本方向特有）**：

**Q1：讲讲你的 ML 项目（完整链路）？**——答：**"我做了信用风险预测——业务目标是降低坏账（代价矩阵：漏坏人损失 > 误伤好人）；数据是 XX 数据集（2 万样本 30 特征）；特征工程做了编码选型和 3 个业务交互特征，泄漏检查发现并修掉一个'全局统计'泄漏；模型从逻辑回归基线（0.72）到 LightGBM（0.83 AUC），Optuna 调参提升到 0.85；评估用了 PR-AUC + 阈值调到 0.3（业务要召回）；SHAP 解释发现'逾期次数'权重最高；部署用 MLflow 注册 + FastAPI 服务，PSI 监控漂移——局限是样本量小、公平性审计发现性别群体差异待缓解"**——结构：**业务 → 数据 → 特征 → 模型 → 评估 → 解释 → 部署 → 局限**——"全链路 + 每环节有数字 + 局限不回避 = 高级 ML 工程师的回答"。

**Q2：你的模型上线后效果变差了，怎么排查？**——答：**"三步：① 先看监控（PSI/SHAP 漂移——输入分布还是解释分布变了）；② 定位根因（业务变了吗——规则/产品；数据源变了吗——口径/采集；用户变了吗——人群结构）；③ 决策（根因明确 → 针对性重训/修正特征；根因不明 → 抽样人工复核 + 灰度对比）——同时检查'是不是部署事故'（版本回滚了没、依赖变了没）"**——结构：**监控 → 根因 → 决策**——"答出'先看监控再猜原因'显示工程素养"。

**Q3：为什么用 LightGBM 不用深度学习？**——答：**"表格数据上深度学习很少赢 GBDT：① 表格特征是'异构稀疏'（类别+数值混合），树模型天然处理；② GBDT 训练快、调参成本低（Optuna 几十次就够）；③ 可解释性配合 SHAP 成熟；④ 我做了对比实验验证——LightGBM 0.85 vs MLP 0.83——差距不大选简单的。深度学习的适用是图像/文本/序列数据——表格数据用它是'杀鸡用牛刀且杀不好'"**——结构：**结论 → 四个理由 → 实验证据 → 边界**——"答出'我做过对比实验'比答'深度学习过拟合'强十倍"。
