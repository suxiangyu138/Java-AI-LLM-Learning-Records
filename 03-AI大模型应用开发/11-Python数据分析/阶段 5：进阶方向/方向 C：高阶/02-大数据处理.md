## 1. 大数据处理的选型逻辑

**"大数据"在 2026 年的 Python 语境 = 超过内存的数据（几十 GB 到几 TB）**——三个工具的分工（01 篇混合栈的实战版）：

```text
工具选型逻辑（数据规模 × 任务）
├── < 内存：pandas（生态最全——阶段 1-4 的熟悉世界）
├── 超内存探索/查询：DuckDB（SQL 直查文件——自动落盘，内存只占 1-2 GB）
├── 超内存转换管道：Polars（惰性执行 + 流式——生产级）
└── 集群级（TB+）：Spark（多机分布式——超出本方向范围，知道存在即可）
    ——"先问'数据多大'再选工具——70% 的'大数据问题'其实 DuckDB 单机就能解决"
```

**选型心智**：**"2026 年单机处理能力的边界远比你想象的大"**——"16GB 内存的笔记本能处理 50GB 数据（DuckDB 自动落盘）——**'大数据'的第一反应不是上集群，是上 DuckDB'"**；**性能基准（2026）**：2TB Parquet 扫描 DuckDB 约 45 秒 vs Polars 约 60 秒（默认模式）、100M 行 CSV——Polars 加载 5GB CSV 不到 10 秒（pandas 8 分钟+）——**"从 pandas 到 Polars/DuckDB 是 10-100 倍的差距"**；**内存是真正的分水岭**——140GB 文件 DuckDB 峰值内存 1.3GB vs Polars 17GB（mmap 默认）——**"DuckDB 是'省内存冠军'（自动落盘），Polars 是'快且可控'（流式需开启）"**。

## 2. DuckDB：SQL 直接查文件

**DuckDB（1.5.x——2026 生产线，"SQL 界的 SQLite"）——不加载就能查**：

```python
import duckdb

# 直接 SQL 查 Parquet/CSV 文件（不加载进内存！）
df_result = duckdb.sql("""
    SELECT category, SUM(amount) AS gmv, COUNT(*) AS orders
    FROM 'data/sales_2026.parquet'          -- 直接查文件
    WHERE date >= '2026-01-01'
    GROUP BY category ORDER BY gmv DESC
""").df()                                   # 结果转 pandas（收尾层）

# 查多个文件（glob 模式——分区数据直接聚合）
duckdb.sql("SELECT * FROM 'data/*.parquet'").df()

# 和 pandas 零拷贝互通
df = duckdb.from_df(pandas_df).sql("SELECT * FROM df WHERE amount > 100").df()
```

**DuckDB 心智**：**"DuckDB 的杀手锏：不加载、直接查——谓词下推 + 列存 + 自动落盘"**——**"pandas 是'先全搬进内存再算'，DuckDB 是'直接在文件上算，只把结果搬回来'"**（阶段 3 03 篇 Parquet 谓词下推的终极形态）；**DuckDB 是 2026 年探索层的默认首选**——"拿到一个大 Parquet，第一件事不是 `pd.read_parquet`，是 `duckdb.sql('SELECT * FROM ... LIMIT 100')`"（阶段 3 03 篇 nrows 探路的 DuckDB 版——**"探路用 DuckDB，收尾用 pandas"**）；**DuckDB 的功能边界**——单机（多机集群不支持——"TB 级 + 多机才上 Spark"）、内存大户查询仍需小心（返回结果集要 `.df()` 前先聚合——"查完别把全表 `.df()` 拉回内存——只拉结果"）。

## 3. Polars：生产级管道

**Polars（1.0+——2026 流式引擎稳定）——生产管道的数据转换主力**：

```python
import polars as pl

# 惰性执行（lazy）：先描述"要做什么"，最后 collect 一次执行
q = (pl.scan_csv("data/big.csv")                    # 惰性扫描（不加载）
     .filter(pl.col("amount") > 100)                 # 过滤下推
     .with_columns((pl.col("amount") / pl.col("qty")).alias("unit_price"))
     .group_by("category").agg(pl.col("amount").sum().alias("gmv"))
     .sort("gmv", descending=True))
df = q.collect()                                     # 此刻才真正执行

# 流式模式（超内存：collect(streaming=True)——2026 稳定）
# df = q.collect(streaming=True)
```

**Polars 心智**：**"Polars 的核心思想：惰性执行 + 查询优化器"**——"pandas 是'一步步执行'（每步都算），Polars 是'先描述整条流水线，再一次性优化执行'（合并过滤/下推/并行）"——**"惰性 = 给优化器看全图的机会——所以快 5-10 倍"**；**Polars 的类型安全**（严格类型——错误在写代码时暴露而非运行时才炸——"pandas 的 object 列到 Polars 是编译期错误"）；**迁移的代价**（01 篇提到的）：API 命名不同（`with_columns` vs 赋值）、类型契约差异——**"从 pandas 迁移 Polars 的决策：数据 >10GB / 管道要生产化 → 迁；小数据 → 不迁"**；**Polars 与 DuckDB 的互补**（2026 官方集成）：`duckdb.from_df(polars_lf)` 让 DuckDB 对 Polars 惰性帧做谓词下推——"**管道里 DuckDB 查、Polars 转——两者配合是 2026 的标准姿势**"。

## 4. 超内存数据的处理策略

**数据 > 内存时的三条路（按任务类型选）**：

```text
超内存处理策略
├── 只查询/聚合 → DuckDB 直查（零加载——首选）
├── 要转换后全量分析 → 分块管道（阶段 3 03 篇 chunksize 的思路 + Polars 流式）
└── 建模用 → 采样 + 特征工程（模型不需要全量——方向 B 02 篇特征选择思维）
    ——"超内存的第一反应：'我真的需要全量吗？'——多数分析只需要聚合结果"
```

```python
# 策略三：建模数据的正确姿势（不需要全量）
# ① 聚合特征在 DuckDB 算（全量在库里聚合——零内存）
features = duckdb.sql("""
    SELECT user_id, COUNT(*) AS order_cnt, SUM(amount) AS total_gmv
    FROM 'data/orders.parquet' GROUP BY user_id
""").df()
# ② 明细级建模：分层采样（每类按比例抽——保留分布）
sample = duckdb.sql("SELECT * FROM 'data/orders.parquet' USING SAMPLE 10%").df()
```

**策略心智**：**"超内存的第一问：'要不要全量'"**——**"90% 的分析只需要聚合结果——在库里聚合（DuckDB），别把明细拉进内存"**（阶段 3 04 篇"SQL 能过滤的别让 pandas 过滤"的规模版）；**分区是性能之王**——"按日期分区的 Parquet，查询只碰需要的分区——**'分区比换引擎影响大 8 倍'**（2026 基准：分区让 DuckDB 内存降 8 倍）"（阶段 3 03 篇 row_group 调优的延伸）；**采样的纪律**——"采样要保留分布（分层采样）+ 记录采样方式（来源卡——阶段 3 09 篇——'采样过的数据要标注'）"；**落盘 vs 流式**——"DuckDB 自动落盘（省心）、Polars 流式需显式开启（可控）——**'省心选 DuckDB，精细控制选 Polars'"**。

## 5. 混合栈实战

**一个超内存分析的完整流程（三件套协作示范）**：

```python
import duckdb, polars as pl, pandas as pd

# ① 探索层（DuckDB）：快速看数据规模与结构
duckdb.sql("SELECT COUNT(*), MIN(date), MAX(date) FROM 'data/sales.parquet'").df()

# ② 查询层（DuckDB）：在库里做重量级聚合（零加载）
monthly = duckdb.sql("""
    SELECT date_trunc('month', date) AS month,
           SUM(amount) AS gmv, COUNT(*) AS orders
    FROM 'data/sales.parquet' WHERE date >= '2025-01-01'
    GROUP BY 1 ORDER BY 1
""").df()

# ③ 转换层（Polars）：结果集处理（样本量适中时）
pl_df = pl.from_pandas(monthly)
pl_df = pl_df.with_columns((pl_df["gmv"] / pl_df["orders"]).alias("aov"))

# ④ 收尾层（pandas）：喂可视化/建模（生态最全）
final = pl_df.to_pandas()
final.plot(x="month", y="aov")          # 可视化在 pandas 生态
```

**混合栈心智**：**"混合栈的黄金分工：重的（聚合/过滤）在 DuckDB、转的（清洗/派生）在 Polars、尾的（可视化/建模）在 pandas"**——**"每个工具干它最擅长的活——组合起来是 2026 年单机数据分析的最优解"**；**互操作的成本**（Arrow 零拷贝——转来转去几乎免费——"三个工具共享 Arrow 内存格式——互转不是序列化，是'借指针'"）；**混合栈的调试**——"管道出错先定位在哪层（DuckDB SQL 错/Polars 类型错/pandas 兼容错）——**'报错定位到层，是混合栈的排障第一课'"**；**什么时候不用混合栈**——"数据 <1GB、一次性分析——pandas 单挑够了——**'工具复杂度跟着数据规模走'"**。
