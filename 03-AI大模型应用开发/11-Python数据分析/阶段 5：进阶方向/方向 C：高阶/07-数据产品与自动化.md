## 1. 数据产品的定位

**数据产品 = 把"分析能力"打包成"可反复使用的系统"**——2026 年数据团队的产出形态：

```text
分析交付的三种形态（递进）
├── 分析报告：一次性交付——"这个月怎么样"（阶段 4 的方向）
├── 自动化报表：周期性自动产出——"每周自动出报告"（阶段 4 06 篇管道）
└── 数据产品：系统化平台——"业务自己查数/看板/自助分析"（本课）
    ——"报告是'打鱼'，产品是'渔场'——产品让数据能力规模化复用"
```

**定位心智**：**"数据产品的核心价值：把分析师从'重复劳动'中解放"**——**"业务问 10 次'上个月转化率'——回答 10 次是打鱼，建一个'指标自助查询'是渔场"**（方向 A 01 篇"BI 是分析师的'分身'"的产品化）；**数据产品的三类形态**（2026 主流）：**指标平台**（指标统一治理——本课第 2 节）、**报表/看板平台**（自助分析——第 3 节）、**数据 API/服务**（数据能力开放给业务系统——"推荐接口/风控接口——数据产品的'服务化'"）；**产品化思维**（方向 A 09 篇影响力建设的工程版）——"分析方法论沉淀成产品 = 个人能力 → 团队资产 → 组织标准"。

## 2. 指标平台

**指标平台 = 指标的"统一治理系统"——方向 A 02 篇指标字典的工程化落地**：

```text
指标平台四件套
├── 指标定义层：指标字典数字化（定义/口径/公式——02 篇五要素）
├── 指标语义层：口径统一（"GMV"全公司一个定义——跨部门不打架）
├── 指标血缘层：指标 → 数仓表 → 上游来源（02 篇血缘图的工程实现）
└── 指标服务层：统一查询 API（业务/看板/AI 都调它——"一个口径出口"）
    ——"指标平台 = 指标的'宪法法院'——所有查询/看板/报告的指标都从这里出"
```

**平台心智**：**"指标平台的灵魂：口径的'单一事实来源'（Single Source of Truth）"**——**"没有指标平台的公司：运营看板的 GMV 和财务报表的 GMV 永远差一点——两个口径在打架"**（方向 A 04 篇"看板与报告口径打架是信任危机"的系统解法）；**2026 年指标平台的 AI 意义**——"NL2Metrics（自然语言查指标）依赖指标语义层——**'指标平台是 AI 问数的地基——指标都没统一，AI 答什么都会错'"**（09 篇 Data Agent 的前置条件——2026 Data Agent 最佳实践报告的共识："可信数据基础（指标/血缘/权限）是 Agent 规模化应用的前提"）；**指标平台的落地**——"先治理 20 个核心指标（不贪多），再扩"——"**指标平台的建设 = 治理的循序渐进——先核心后长尾**"。

## 3. 报表自动化平台

**报表平台 = 让"要报表的人"自助——分析师从取数机器解放**：

```text
报表平台三层（2026 年形态）
├── 自助查询层：业务拖拽取数（BI 工具——方向 A 08 篇）
├── 定时报表层：周期报表自动生成 + 推送（邮件/企微——管道 + 调度）
└── 订阅与预警层：业务订阅指标 + 异常自动预警（"转化率跌破阈值自动提醒"）
    ——"报表平台的进化：查数自助化 → 报表自动化 → 异常主动化"
```

```python
# 定时报表 + 异常预警（分析师写的'一次部署'）
import schedule, time

def daily_check():
    df = read_kpi()                                   # 读指标（指标平台 API）
    conv = df["conversion"].iloc[-1]
    baseline = df["conversion"].iloc[-10:].mean()
    if conv < baseline * 0.9:                          # 跌破 90% 基线
        send_alert(f"转化率异常：今日 {conv:.2%} vs 10 日均 {baseline:.2%}")  # 推企微
    else:
        send_report(df)                                # 正常则发日报

schedule.every().day.at("09:00").do(daily_check)
```

**平台心智**：**"报表自动化的三层价值：省人力（分析师不再发周报）、快响应（异常 30 秒内有人知道）、规模复用（100 个业务方自助查数）"**——**"自动化的终点：分析师只做'机器做不了的事'——异常解读、归因分析、建议"**（方向 A 04 篇"数由机器出，判断由人出"的落地）；**预警的设计**——"阈值要定（跌破 90% 报警）+ 防打扰（同一异常 24 小时只报一次——'**预警的敌人是狼来了**'——报太多没人看）；**自动化的边界**——"自动化不是'一次写完永远不管'——数据源变了/口径变了要更新——**'自动化系统也要运维——它是产品不是一次性脚本'"**。

## 4. 数据产品设计思维

**数据产品设计 = 产品思维（用户/场景/价值）× 数据能力**：

```text
数据产品设计五问（做产品前的设计文档）
├── ① 用户是谁：业务方/管理层/外部客户？（每个用户一种设计）
├── ② 场景是什么：日常监控/周度复盘/决策支持？（场景决定功能）
├── ③ 核心价值：省时间/提决策/降风险？（价值决定优先级）
├── ④ 指标与口径：哪些指标、什么口径？（指标平台对接——02 篇）
├── ⑤ 成功标准：怎么衡量产品"有用"？（使用率/决策采纳率/时间节省）
    ——"数据产品失败的第一原因：做了一堆功能，没人用——从'用户场景'出发而非'技术炫技'"
```

**设计心智**：**"数据产品的'最小可用版'（MVP）思维"**——"先做 3 个指标 + 1 个看板上线（1 周），用户用了再迭代——**'数据产品也是互联网产品：小步快跑，别憋大招'"**；**数据产品的用户分层**——"高管看结论页（一句话）、业务看明细页（能下钻）、分析师看原始层（能验证）——**'一个产品三层读者，三层视图'"**（阶段 4 07 篇三层看板的系统化）；**产品 vs 项目的区别**——"项目有截止日期、产品有生命周期（上线 → 使用 → 迭代 → 下线）——**'做产品的心态：交付只是开始，运营才是主体'"**（09 篇模型部署"上线是开始"的产品版）；**产品文档**——"PRD（产品需求文档——五问写全）+ 使用手册 + 迭代日志——**'产品的交付物 = 系统 + 文档 + 运营'"**。

## 5. 自动化体系

**完整自动化体系 = 数据管道 + 报表 + 预警 + 监控的闭环**（阶段 4 06 篇的团队版）：

```text
自动化体系全景
├── 采集管道（阶段 4 06 篇）：数据自动更新（断点续采——团队版由数仓管道负责）
├── 数仓加工（01 篇）：ODS → DWD → DWS（定时调度——DAG 任务编排）
├── 报表生成（本课 3 节）：周期报表自动产出 + 推送
├── 异常预警（本课 3 节）：指标跌破阈值自动提醒
└── 数据质量监控（阶段 3 09 篇）：行数对账/缺失监控——管道健康度
    ——"自动化体系的验收：连续 30 天无人值守运行——稳定是自动化的生命线"
```

**自动化心智**：**"自动化的分层：采集自动 → 加工自动 → 报表自动 → 决策辅助"**——**"越往上自动化越难（采集加工是工程问题、预警是规则问题、决策辅助是智能问题）——逐步推进"**（"先自动化'重复的'，再自动化'判断的'——09 篇 AI 融合是决策辅助自动化的方向）；**任务编排**（多任务依赖调度）——"报表要等数仓加工完再跑——**'任务依赖 = 调度的核心——Airflow/Dagster（2026 主流）'**（阶段 4 06 篇 cron 的团队版——"单机 cron 管单任务，DAG 编排管多任务依赖"）；**自动化与人的边界**——"自动化处理'规则明确'的（报表/预警），人处理'需要判断'的（异常归因/建议）——**'人机分工：机器保证'不漏'，人保证'不错'"**（2026 Data Agent 三原则的工程版——"规则明确的场景用确定性自动化，认知推理场景用 AI/人"）。
