## 3. 报错速查 10 条

| 报错/现象 | 原因 | 解法 |
|---------|------|------|
| SQL `Unknown column` | 列名错 | 先 `DESCRIBE 表` / `SHOW COLUMNS` 看真实列名 |
| SQL `Window function not allowed` | 窗口函数位置错 | 窗口函数只能在 SELECT/ORDER BY（不能进 GROUP BY/WHERE） |
| `pandas` 数据量和 SQL 对不上 | 拉数时漏了过滤/去重 | 回 SQL 检查 WHERE 与 DISTINCT（对账——04 篇纪律） |
| 同比数据"离谱" | 口径变了（去年含运费） | 查指标字典变更史（02 篇——变更史不记，同比全是坑） |
| BI 里指标和报表对不上 | BI 口径和字典不一致 | 统一用指标字典口径（08 篇 BI 落地三件事） |
| 活动复盘"增量"算得巨大 | 把活动期全部 GMV 当增量 | 建基线再算增量（07 篇——没有基线的活动分析是看烟花） |
| LTV 算出来高得离谱 | 留存月数假设太乐观 | LTV 是估算——写清假设（Cohort 数据支撑） |
| 老板追问答不上来 | 汇报前没预演追问 | 预演清单（09 篇）——答不上来的先补分析 |
| 业务方说"数据不对" | 口径没对齐就开跑 | 需求五问 + 口径确认单（01 篇——先对齐再动手） |
| AI 生成的 SQL 结果错 | AI 漏了维度/过滤 | AI 代码必须过三关：跑通/验证/读懂（08 篇） |

**报错心智**：**"业务分析的报错一半在技术、一半在口径"**——"报错速查表里 5 条是口径问题——**'数据不对'先查口径，再查代码"**——"口径是业务分析的万恶之源，也是第一排查项"。

## 5. 面试演练

**业务分析师面试问答（本方向特有）**：

**Q1：你怎么搭指标体系？**——答：**"先定北极星（反映核心价值、业务导向、可量化），再用 OSM 把目标拆成策略和度量（每个指标有'策略爸爸'，不允许孤儿指标），用 KPI 树 MECE 拆解到'有人管'的粒度，最后建指标字典统一口径（定义/口径/来源/负责人/变更史）——例如我们 GMV 体系拆成流量×转化×客单，各环节对应运营/产品/商品部门"**——结构：**北极星 → OSM → KPI 树 → 字典**——"答出'变更史'显示做过真指标治理"。

**Q2：GMV 环比下降了，你怎么分析？**——答：**"先对比确认（同比/环比/对标——看是不是趋势性还是偶发），再量价拆解（量降还是价降还是结构变了，连环替代法归因到因素），然后落渠道/品类/用户三个维度定位（哪个渠道少了、哪个品类拖累、是不是新客少了），最后给建议（有对象有动作有预期）——所有结论带数据支撑，验证不了的原因明确写'待验证'"**——结构：**对比 → 拆解 → 下钻 → 建议**——"答出'待验证'显示分析严谨性"。

**Q3：业务方不认可你的分析结论，怎么办？**——答：**"① 先听业务方的'一线观察'——他们的质疑可能是我没看到的数据（比如线下渠道没统计）；② 对齐口径（两边算的'新客'是不是一个定义）；③ 回到数据验证（把质疑变成可验证的假设，跑数据说话）；④ 结论如果被推翻，认——复盘为什么错（数据缺了/口径错了），这比维护结论更有价值"**——结构：**倾听 → 对齐 → 验证 → 复盘**——"答出'结论被推翻敢认'是业务分析师的成熟标志"。
