## 1. 为什么需要科学的评测体系

```text
2023 → 2026 代码模型评测进化史

2023 时代：
  "HumanEval 82%！" → 就能发 PR 文章
  问题是：HumanEval 164 道题被刷烂，模型可能"背答案"

2024 时代：
  SWE-bench 成为新标准 → 测真实 GitHub Issue 修复
  但 SWE-bench Verified 也只有 500 道题

2025 时代：
  多基准交叉验证 → SWE-bench + LiveCodeBench + BigCodeBench
  从"会不会写代码"到"能不能修工程"

2026 时代：
  Agent 基准爆发 → Frontier-Bench, DeepSWE, A-CODE-LLM, SlopCodeBench
  从"修一个 Bug"到"自主完成整个开发任务"
```

## 2. 八大核心基准详解

### 2.1 SWE-bench Verified（真实 Bug 修复）

```text
测什么：从 GitHub 真实 Issue 中提取的 500 个 Python 项目 Bug
怎么测：给模型 Issue 描述 + 代码库 → 生成 Patch → 跑项目原有测试
为什么重要：最接近"真实世界修 Bug"场景

2026.07 Top 5：
| 模型 | 得分 | 成本/任务 |
| DeepSeek V4 Pro | 80.6% | ~$0.20 |
| Qwen3.7-Max | 80.4% | ~$0.80 |
| Claude 4.5 Opus (高推理) | 76.8% | $0.75 |
| Gemini 3 Flash (高推理) | 75.8% | $0.36 |
| MiniMax M2.5 (高推理) | 75.8% | $0.07 |

局限性：只有 Python 项目，只有 500 道题，不能完全代表真实开发
```

### 2.2 SWE-bench Pro（多文件工程修复）

```text
测什么：SWE-bench 的"专业版"，测试跨文件、多步骤工程修复
怎么测：更复杂的 Issue + 多文件修改 + 更严格的验证
为什么重要：区分"片段编程"和"工程编程"能力

2026.07 Top 5：
| GLM-5.2 | 62.1% | MIT 协议开源 |
| MiniMax M3 | 59.0% | 开源权重第一 |
| Mythos 5 | 80.3% | 闭源最高分 |
| Claude Fable 5 | 80.0% | Anthropic 旗舰 |
| Claude Opus 5 | 79.2% | 半价 Fable 5 |

关键发现：SWE-bench Pro 排名与 SWE-bench Verified 排名差异巨大！
GLM-5.2 在 Pro 上第一（62.1%），但在 Verified 上只有 72.8%
→ 说明"修简单 Bug"和"改复杂工程"是两种不同的能力
```

### 2.3 LiveCodeBench（竞赛级代码生成）

```text
测什么：从 LeetCode/Codeforces 等竞赛平台收集的新题目（防止数据污染）
怎么测：给题目描述 → 生成代码 → 在线评测（通过所有测试用例）
为什么重要：防止"背答案"，测试真正的算法推理能力

2026.07 Top 5：
| DeepSeek V4 Pro | 93.5% | 开源第一 |
| Gemini 3 Pro Preview (high) | 92.0% | Google 旗舰 |
| GPT-5.2 (xhigh) | 89.0% | OpenAI |
| Grok 4.5 | ~88% | xAI |
| Qwen3.7-Max | ~85% | 阿里云 |

与 SWE-bench 的区别：
LiveCodeBench = 算法竞赛（从零写新代码）
SWE-bench = 工程修复（理解现有代码 + 最小改动）
```

### 2.4 Code Arena（盲测编程偏好）

```text
测什么：LMArena 的编程专项盲测——用户不知道是哪个模型，纯粹投"谁写得好"
怎么测：两个模型生成代码 → 用户盲选投票 → ELO 排名
为什么重要：用户实际偏好的最直接反映，不被"品牌光环"影响

2026.07 Top 5：
| Kimi K3 | 1679 | 登顶！超越所有闭源模型 |
| Claude Fable 5 | 1631 | 前第一 |
| GPT-5.6 Sol | 1618 | OpenAI 最强 |
| Qwen3.7-Max | 1541 | 国产第二 |
| DeepSeek V4 Pro | ~1520 | 开源高性价比 |

Kimi K3 的胜利意义：开源模型首次在人类盲测中超越所有闭源旗舰
```

### 2.5 DeepSWE（深度工程理解）

```text
测什么：比 SWE-bench 更难的工程理解测试——需要理解项目架构、设计意图
怎么测：复杂工程任务 → 需要深层架构理解的修复方案

2026.07 Top 5：
| Claude Fable 5 | pass@1 69.9% | 一次通过率最高 |
| Kimi K3 | pass@1 68.5% | 紧追 Fable |
| | pass@2 82.0% | 二次采样反超 |
| | pass@4 89.4% | 四次采样大幅领先 |

关键发现：Kimi K3 pass@4 (89.4%) > Claude Fable 5 pass@1 (69.9%)
→ 多采样策略下，开源模型可以超越闭源旗舰
→ 成本：Kimi K3 $4.65/轮 vs Fable 5 $13.41/轮
```

### 2.6 Frontier-Bench（Agent 编程新标准）

```text
测什么：2026 年 Anthropic 发布的新基准——测试模型作为 Agent 自主编程的能力
怎么测：多步骤工程任务 → Agent 规划/执行/验证 → 端到端成功率

2026.07 Top 5：
| Claude Opus 5 | 43.3% | 碾压第二名 9 个点！ |
| GPT-5.6 Sol | 34.4% | 差距明显 |
| Claude Fable 5 | 33.7% | 不如 Opus 5 |
| Claude Opus 4.8 | 21.1% | 代际飞跃 |

关键发现：Frontier-Bench 是 Opus 5 最亮眼的胜利——
Opus 5 的 Agent 编程能力比 Opus 4.8 翻倍，甚至超越 Fable 5
```

### 2.7 A-CODE-LLM Bench（Agent 编程性价比）

```text
测什么：Agent 编程能力 + 成本效率的综合评测
怎么测：完成编程任务的得分 ÷ 消耗的成本

2026.07 Top 5：
| Grok 4.5 | 0.732 | $0.46/任务 — 性价比之王 |
| Claude Sonnet 5 | 0.707 | $2.23/任务 — 贵但能力强 |
| Grok 4.3 | 0.702 | $0.51/任务 |
| Claude Opus 4.8 | 0.702 | $1.67/任务 |

有趣发现：Sonnet 5 的代码评分超过 Opus 4.8！
→ Anthropic 内部也承认 Sonnet 5 是"最能干的 Sonnet"
```

### 2.8 SlopCodeBench（代码可维护性）

```text
测什么：2026 年 7 月新基准——不是测"能不能写"，而是测"写的代码能不能维护"
怎么测：模型增量修改代码 → 检查是否引入混乱/重复/死代码

2026.07 结果：
| Claude Opus 5 | 24% | 最高分，但也没及格！ |
| Claude Opus 4.8 | 6% | |
| Claude Sonnet 5 | 6% | |

惨烈结论：没有一个模型及格！Opus 5 虽然最高，但也写出了 5× 不必要的代码
→ 2026 年 AI 代码的"可维护性"仍是巨大挑战
```

## 4. 基准的局限性与正确读法

### 4.1 基准不是万能的

```text
常见误读：
❌ "SWE-bench Pro 第一 = 最厉害的代码模型"
✅ "SWE-bench Pro 第一 = 在这个特定类型的任务上表现最好"

基准的七大局限：
1. 数据污染：训练数据可能"见过"测试题
2. 语言局限：大部分基准只测 Python
3. 场景偏差：开源项目 Bug ≠ 企业业务代码
4. 评测方差：不同 Agent/Scaffolding 影响巨大
5. 过拟合：模型厂商可能针对特定基准优化
6. 时效性：LiveCodeBench 这类基准题目在变，单次排名不稳定
7. 可维护性：几乎所有基准只测"能不能做对"，不测"代码好不好维护"
```

### 4.2 正确读法：交叉验证

```text
✅ 正确思路：看一个模型在多个基准上的表现模式

案例：DeepSeek V4 Pro
  SWE-bench Verified: 80.6% 🥇
  LiveCodeBench:      93.5% 🥇
  SWE-bench Pro:      55.4% (第 N 名)
  → 结论：擅长"算法编程"和"单文件 Bug 修复"，但"多文件工程重构"较弱

案例：GLM-5.2
  SWE-bench Pro:      62.1% 🥇
  SWE-bench Verified: 72.8% (第 N 名)
  → 结论：擅长"复杂工程修改"，但基础场景不如 DeepSeek V4 Pro
```

## 5. 如何综合评估一个代码模型

### 5.1 五维度评估框架

```text
┌─────────────────────────────────────┐
│  维度 1：代码生成力 (LiveCodeBench)  │
│  → 从零写代码的能力                  │
├─────────────────────────────────────┤
│  维度 2：代码修复力 (SWE-bench)      │
│  → 读懂代码 + 精准修改的能力          │
├─────────────────────────────────────┤
│  维度 3：工程理解力 (DeepSWE/Pro)    │
│  → 理解架构 + 多文件协同的能力        │
├─────────────────────────────────────┤
│  维度 4：Agent 执行力 (Frontier/A-CODE)│
│  → 自主规划 + 执行 + 验证的能力       │
├─────────────────────────────────────┤
│  维度 5：用户体验 (Code Arena)       │
│  → 实际使用中开发者的偏好            │
└─────────────────────────────────────┘
```

### 5.2 权重建议

| 你的角色 | 代码生成 | 代码修复 | 工程理解 | Agent | 体验 |
|------|:---:|:---:|:---:|:---:|:---:|
| 日常开发 | 40% | 30% | 10% | 10% | 10% |
| Bug 修复为主 | 10% | 50% | 20% | 10% | 10% |
| 架构重构 | 10% | 10% | 50% | 10% | 20% |
| Agent 自动化 | 10% | 10% | 10% | 60% | 10% |

> 🎯 **核心要点**：2026 年没有单一的"代码模型之王"——不同基准测出不同的冠军。选模型应该看你的实际任务匹配哪个基准，组合使用多个模型是最大化效率的关键。
