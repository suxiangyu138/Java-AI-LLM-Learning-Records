# 10 - 实操验证：从 Demo 到故障复现

> 🎯 不动手永远是纸上谈兵。最小 Demo、控制变量实验、刻意制造故障——三层验证让理解落地

---

## 1. 最小 Demo（Java 后端 CRUD）

### 输入需求

```text
用 Spring Boot 3.2 + MyBatis Plus 3.5 写一个用户 CRUD 接口：
- User 实体（id, name, email, createTime）
- 包含分页查询 + 按邮箱模糊搜索
- 参数校验（@Valid + @NotBlank/@Email）
- Swagger/OpenAPI 文档注解
- 完整的单元测试（JUnit5 + Mockito）
- 参考项目中已有的 OrderController 代码风格
```

### 验证步骤

```text
① Codex 生成代码
   → 观察：它是否读懂了 OrderController 的风格？
   → 观察：生成的注解格式是否一致？

② 编译运行
   → 直接复制到 IDE 编译
   → 运行 mvn test → 测试是否通过？

③ 检查测试质量
   → 是否有正常 Case + 边界 Case + 异常 Case？
   → Mock 是否正确？

④ 检查代码规范
   → 命名是否符合项目风格？
   → 异常处理是否完整？
```

## 2. 控制变量实验

### 实验 1：需求详细程度对代码质量的影响

```text
变量 A（模糊）：
  "写一个用户管理的 CRUD"

变量 B（详细）：
  "用 Spring Boot 3.2 + MyBatis Plus 3.5 + JDK 17 写用户 CRUD：
   - Entity/DTO/Controller/Service/Mapper
   - 分页 + 条件查询
   - @Valid 校验 + 全局异常处理
   - Swagger 文档 + 单元测试"

对比结果：
  → A 组：代码可用但缺少校验、测试、文档
  → B 组：功能完整、风格统一、可直接使用
  → 结论：需求越具体，代码越可用的可能性越高
```

### 实验 2：上下文长度对代码风格一致性的影响

```text
变量 A：不给参考文件 → Codex 用"通用风格"
变量 B：给 1-2 个参考 Controller → Codex 模仿参考风格
变量 C：给完整项目代码 → Codex 精确匹配项目风格

对比结果：
  → 提供的上下文越多，输出越贴合项目规范
```

### 实验 3：联网搜索对 API 准确率的影响

```text
需求："用 Spring Boot 3.3 最新版本的虚拟线程配置"

变量 A：关闭联网 → 可能使用旧版 API（训练数据截止前的版本）
变量 B：开启联网 → 查阅最新文档 → 使用正确的新 API

结论：使用最新版本框架时，务必开启联网搜索
```

## 3. 故障复现（刻意验证局限性）

### 故障 1：私有 SDK 幻觉

```text
输入：
"用公司内部的 DataEncryptor 工具类加密用户密码"

预期：Codex 无法找到这个类，会生成不存在的调用
验证：
  生成的代码中调用了一个不存在的 encrypt() 方法
  → 证明了私有框架是 Codex 的盲区
  → 解决方案：提供 SDK 文档 + 示例代码作为上下文
```

### 故障 2：超大架构重构的局限

```text
输入：
"将整个微服务项目从 Spring Boot 2.x 升级到 3.x，
涉及 50+ 个服务、200+ 个文件"

预期：Codex 能处理局部模块，但无法输出全局架构方案
验证：
  → 对单个服务的升级完成得很好
  → 但跨服务的依赖关系和接口变更没处理好
  → 结论：大型架构重构需按服务拆分，逐个处理
```
