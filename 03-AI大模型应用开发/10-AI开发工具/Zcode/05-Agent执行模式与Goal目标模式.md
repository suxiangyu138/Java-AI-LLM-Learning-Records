## 1. ZCode Agent 执行闭环

ZCode Agent（主 Agent）围绕长程任务设计，标准执行闭环：

```
理解需求 → 拆解计划 → 写代码 → 测试验证 → 代码审查 → 收尾汇报
```

各阶段特点：

| 阶段 | Agent 行为 | 用户干预点 |
|---|---|---|
| 理解需求 | 读取工作区、引用文件、AGENTS.md 项目约定 | 需求描述清晰度决定上限 |
| 拆解计划 | 输出执行计划（改哪个文件、写什么、放哪） | 计划模式下在此审批 |
| 写代码 | 逐文件修改，遵守项目规范 | 变更前确认模式逐一审批 |
| 测试验证 | 运行测试、构建命令、修 Bug 重试 | 失败时查看日志继续驱动 |
| 代码审查 | 自查改动、检查边界 | 要求 review 或换模型再审 |
| 收尾汇报 | 输出变更摘要、文件路径 | 验收 + Git 提交 |

长程任务能力依赖 GLM-5.2 的 1M 上下文：同一上下文里完成全流程，连续编码数小时不掉链子。

## 2. 四种执行模式（权限控制）

| 模式 | 文件修改 | 命令执行 | 适用场景 |
|---|---|---|---|
| 变更前确认（Default） | 每次询问 | 每次询问 | 关键代码、生产配置 |
| 自动编辑 | 自动执行 | 仍需确认 | 常规迭代开发 |
| 计划模式 | 先给计划，确认后动手 | 随计划执行 | 复杂任务、陌生项目 |
| 完全访问 | 尽量少确认 | 尽量少确认 | 目标明确、风险低的小任务 |

切换方式：输入框聚焦时按 `Shift+Tab` 循环切换。

### 模式选型决策

| 场景 | 推荐模式 |
|---|---|
| 第一天用 ZCode / 陌生项目 | 变更前确认 或 计划模式 |
| 日常功能开发 | 自动编辑 |
| 大型重构、涉及多文件联动 | 计划模式 |
| 改个配置文件、补个注释 | 完全访问 |
| Goal 模式 + 自动化批量任务 | 自动编辑 / 完全访问 |

> ⚠️ 高危操作（删文件、改配置、执行破坏性命令）无论什么模式都建议回退到"变更前确认"；完全访问只用于自己完全理解风险的任务。

## 3. 安全确认弹窗

弹窗提供四个选项：

| 选项 | 行为 |
|---|---|
| 允许 | 本次放行 |
| 始终允许 | 本会话/本任务内同类操作不再询问 |
| 拒绝 | 本次拦截 |
| 始终拒绝 | 本任务内同类操作永久拦截 |

使用策略：

- 初期一律"允许"观察行为模式，摸清 Agent 习惯后按操作类型批量放行
- 对"始终允许"保持警惕：命令执行类操作建议逐条确认
- 拒绝后 Agent 会调整方案，不会死循环

## 4. Goal 目标模式

Goal 是 ZCode 3.0 的核心特色：用自然语言设定目标，Agent 每轮迭代自动校验是否完成，**没完成继续跑，完成才收尾**。

### 命令族

| 命令 | 功能 |
|---|---|
| `/goal <目标描述>` | 设置目标 |
| `/goal replace <新目标>` | 替换目标 |
| `/goal pause` | 暂停（Agent 停止迭代） |
| `/goal resume` | 恢复 |
| `/goal clear` | 清除 |

### 工作方式

1. 输入框设置目标：`/goal 给订单模块补充单元测试，覆盖率到 80%`
2. 右侧摘要面板实时显示：目标状态、累计时间、累计 Token、迭代轮次
3. Agent 每轮迭代结束自动校验目标完成度，未完成自动继续
4. 完成后收尾汇报

### 使用建议

- 复杂任务用 Goal 模式比连续多轮对话稳得多——不用一直盯着喊"继续"
- 搭配"完全访问"或"自动编辑"模式，设好目标后放手
- 目标描述要含验收标准（如"覆盖率 80%""跑通全部测试"），否则 Agent 自己定义完成标准可能放水
- 长目标注意上下文占用提醒，必要时 `/compact`

## 5. 推理强度控制

输入框右下角思考图标控制推理强度：

| 档位 | 行为 | 适用 |
|---|---|---|
| Off | 直接回答，最快 | 简单修改、明确指令 |
| On | 最深思考深度 | 复杂架构设计、疑难 Bug 排查 |

要点：

- 深度思考耗 token、耗时间，简单任务不要开
- 复杂任务先开深度思考拿到方案，再关掉执行细节，省额度

## 6. 会话级版本回滚

每条消息作为检查点，支持一键回退：

- 回退到任意一次对话变更前的快照
- 场景：Agent 改坏了 → 找到出错前的那条消息 → 一键回退
- 相当于 Agent 时代的 Git：对话本身就是版本历史

使用场景：

| 场景 | 回滚策略 |
|---|---|
| Agent 改坏了代码 | 回退到改动前消息 |
| 方向跑偏（需求理解错） | 回退到分歧点重新描述需求 |
| 实验性改动想对比 | 回退 + 另开任务对比 |

> 🎯 核心要点：回滚的是**文件变更快照**，不是简单撤销消息——所以放心让 Agent 放手改，改坏了有检查点兜底。
