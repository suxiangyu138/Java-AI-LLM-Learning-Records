## 1. 官方 Java SDK：为什么必须用它

**豆包 API 要求签名头（X-Content-Sha256 / X-Signature，HMAC-SHA256），手写 RestTemplate 极易 401/400**——这是 Java 接入的第一课。官方 SDK 已内置：请求签名、OAuth2.0 自动刷新、429 指数退避重试、SSE 流式解析、空值/嵌套结构处理。

```xml
<dependency>
  <groupId>com.volcengine</groupId>
  <artifactId>volcengine-java-sdk-ark-runtime</artifactId>
  <version>1.3.1</version>   <!-- 2026-08 最新 -->
</dependency>
```

```java
ArkService service = ArkService.builder()
        .apiKey(System.getenv("ARK_API_KEY"))      // 或 AK/SK 签名
        // .accessKeyId(...).secretAccessKey(...)  // 企业场景
        .region("cn-beijing")                       // ★ 必须与开通地域一致
        .readTimeout(90, TimeUnit.SECONDS)          // ★ 长上下文响应可达 20-45 秒
        .build();
```

三个必配参数：apiKey（或 AK/SK）、region、model。region 填错直接 403；超时默认偏小，长上下文场景必须显式加大。

## 2. Spring AI 集成：OpenAI 兼容路径

火山方舟兼容 OpenAI 协议，Spring AI 直接复用 OpenAI 模块，改三处配置即可：

```properties
spring.ai.openai.api-key=${ARK_API_KEY}
spring.ai.openai.base-url=https://ark.cn-beijing.volces.com/api/v3
spring.ai.openai.chat.options.model=doubao-seed-2-1-pro-260623
```

```java
@RestController
public class ChatController {
    private final ChatClient chatClient;

    public ChatController(ChatClient.Builder builder) {
        this.chatClient = builder.build();   // 依赖注入，不要 new
    }

    @PostMapping("/chat")
    public String chat(@RequestBody String question) {
        return chatClient.prompt(question).call().content();
    }
}
```

Spring AI 的收益是**一套代码多模型切换**：换 DeepSeek/GLM 只改 base-url 与 model 属性，适合需要多供应商降级的项目。轻量对话场景够用；需要 thinking 控制、签名鉴权等深度能力时切官方 SDK。

Python 生态同理：LangChain 的 `ChatOpenAI` 直接指向方舟端点即可复用全部链式能力（RAG、Agent、记忆），配合豆包 embedding 模型可搭完整检索链路。选型建议按"深度"分层：**最浅**——OpenAI SDK/LangChain/Spring AI 改 base_url（原型与轻量场景，成本最低）；**中等**——官方 Ark SDK（生产 Java 场景，签名/重试/流式内置）；**最深**——火山方舟 Bot 应用 API（扣子编排的复杂 Agent，平台托管记忆与工具）。三层的选择标准：是否用到平台独有能力（思考控制、Bot 编排、TPM 保障包），用不到就留在最浅层，减少供应商绑定。

## 3. Spring Boot 实战：对话 + 流式

```java
// 官方 SDK 流式（打字机效果）
@PostMapping("/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter streamChat(@RequestBody String question) {
    SseEmitter emitter = new SseEmitter(120_000L);

    service.streamChatCompletion(            // ★ 默认即流式
        ChatCompletionRequest.builder()
            .model("doubao-seed-2-1-pro-260623")
            .messages(List.of(ChatMessage.user(question)))
            .build()
    ).toObservable().subscribe(
        resp -> {
            String text = resp.getChoices().get(0).getMessage().getContent();
            if (text != null) {
                emitter.send(SseEmitter.event().data(text));   // 逐 token 推送
            }
        },
        emitter::completeWithError,
        emitter::complete
    );
    return emitter;
}
```

官方 SDK 与 Spring AI 的关键差异：**SDK 默认 stream=true**，不显式 `.stream(false)` 时返回 SSE 流，Spring Web 默认处理会卡住——这是集成第一坑。messages 列表至少含一条 user 角色消息，不能只传 system。

官方 SDK 的非流式对话示例：

```java
ChatCompletionRequest req = ChatCompletionRequest.builder()
        .model("doubao-seed-2-1-pro-260623")
        .messages(List.of(ChatMessage.user("你好")))
        .stream(false)                                  // ★ 非流式必显式设置
        .build();

ChatCompletionResult resp = service.chatCompletion(req);
String answer = resp.getChoices().get(0).getMessage().getContent();
```

SDK 的 AkService 是线程安全的重量级对象：连接池、签名器、OAuth2 刷新、重试策略都在实例内维护，**必须声明为 @Bean 单例**，方法内 new 会让所有机制失效并造成连接泄漏。企业环境还可用 AK/SK 构造器（accessKeyId + secretAccessKey）走签名鉴权，请求头自动带 X-Content-Sha256 与 X-Signature——这也是手写 HTTP 无法替代 SDK 的原因。

## 4. 应用生态：扣子 / TRAE / Coding Plan

| 生态 | 是什么 | 对开发者的价值 |
|------|--------|------|
| 扣子 Coze | 低代码 Agent 开发平台 | 不写代码搭 Bot，模型/插件/知识库编排，可发 Bot API |
| TRAE | 字节 AI IDE | 豆包 Code 模型深度集成，Coding Plan 的主阵地 |
| Coding Plan | AI 编程订阅套餐 | Lite ¥40/月、Pro ¥200/月，双协议端点接入 Claude Code/Cursor 等 |
| 即梦 | 视频创作应用 | Seedance 的 C 端入口 |

接入姿势：**复杂业务直接在扣子编排 Bot，通过 Bot 应用 API 调用**（平台托管记忆、插件、知识库）；需要精细控制的场景直接调模型 API。扣子适合"业务人员也能改"的应用——提示词、知识库、插件在界面调整即时生效，技术团队只维护 Bot API 的调用封装。Coding Plan 的额度在兼容工具间共享，模型名用逻辑名（如 `doubao-seed-2.0-code`、`ark-code-latest`），控制台切换 3-5 分钟生效；注意 Coding Plan 鉴权仅限官方兼容的 AI 编程工具，禁止在非编程工具中调用，违规会被判定停用或封禁——这是套餐型产品的红线，别拿套餐 Key 去接业务 API。

## 5. 生产架构与可观测性

豆包服务在生产环境的完整形态建议如下：

```text
前端 → 网关 → 业务后端（Spring Boot）
                ├── ArkService @Bean 单例（签名/重试/连接池）
                ├── 工具执行层（allowlist 分发 + 二次校验）
                ├── usage 打点（token 按业务线/Key 汇总）
                └── 降级链：Pro → Turbo → Mini → 第三方模型
```

可观测性三件套：**日志**（记录 model、耗时、finish_reason、错误码）、**指标**（每模型调用量/TPS、429 率、平均 token 成本）、**告警**（429 率突增、成本日环比超阈值、错误率超 1%）。成本是豆包体系的独特监控对象——低价模型被滥用时消耗依然可观，把"每千次调用成本"纳入看板比只看 QPS 更能暴露异常调用。

## 6. 多模型切换与降级

火山方舟同时托管 DeepSeek/GLM/Kimi 等第三方模型，多模型降级成本极低：

```text
主模型：Seed 2.1 Pro（质量优先）
降级链：Seed 2.1 Turbo → Seed 2.0 Mini → DeepSeek（第三方托管）
切换成本：只改 model 参数，base_url 与鉴权不变
```

生产降级触发条件：429 限流、5xx 服务异常、超时。注意火山方舟被社区反馈存在高峰超售导致的 400/429 波动，关键业务必须配降级链——这是"平台型供应商"与"单模型供应商"在运维上的核心差异。降级要可观测：每次降级打点（原模型→目标模型→原因），每周复盘降级率，持续触发说明 TPM 配额或模型选型需要调整，而不是让降级成为常态。

## 7. 生产避坑清单

| # | 坑 | 解法 |
|---|-----|------|
| 1 | 手写 HTTP 调用缺签名头 401 | 必须官方 SDK |
| 2 | SDK 默认流式，Spring 卡住 | 显式 `.stream(false)` |
| 3 | region 不填/填错 403 | 与控制台开通地域一致 |
| 4 | 只传 system 消息 | 至少一条 user 消息 |
| 5 | 超时默认偏小 | readTimeout 90 秒+ |
| 6 | API Key 硬编码 | 环境变量/K8s Secret |
| 7 | ArkService 方法内 new | 声明为 @Bean 单例（连接池/签名/重试才生效） |
| 8 | thinking 写顶层 400 | extra_body 传参 |
| 9 | 模型 ID 硬编码 | 控制台实时列表为准，Evolving 版本自动更新 |
| 10 | 无降级链 | 429/5xx 时切 Turbo/Mini/第三方模型 |
