## 1. thinking 三模式：怎么选

| 模式 | 行为 | 适用场景 |
|------|------|----------|
| `enabled` | 强制开启思考，先想后答 | 数学、代码、多步骤规划等复杂任务 |
| `disabled` | 强制关闭，直接回答 | 高频对话、翻译、摘要等简单任务 |
| `auto` | 模型按问题难度自动决定 | 混合任务流，推荐默认 |

参数位置与模型差异是高频坑：

```python
response = client.chat.completions.create(
    model="doubao-seed-1-6-251015",          # 标准版支持三模式
    messages=[{"role": "user", "content": "..."}],
    extra_body={"thinking": {"type": "auto"}}  # 必须 extra_body，顶层报错
)
```

- `doubao-seed-1-6-thinking`：**默认开启且不支持关闭**，选它就要接受思考成本
- `doubao-seed-1-6`：支持 enabled/disabled/auto 三模式
- `doubao-seed-1-6-flash`：不支持 auto，只有 enabled/disabled
- Seed 2.x 系列：Pro/Turbo 均为深度思考模型，用 thinking 参数控制

开启思考时，`temperature` / `top_p` 等采样参数对推理阶段无效——思考阶段的输出由推理策略决定，采样参数只影响最终回答。这对"想要稳定输出"的开发者是个隐藏陷阱：你调了 temperature=0 期望结果确定，但思考阶段仍可能走不同推理路径，同一问题两次思考的中间过程与最终答案都可能不同。需要严格可复现的场景（评测、回归测试）要么关闭思考，要么接受思考路径差异并把断言放在结果语义层面而非字面层面。

思考模式还改变响应时延分布：非思考模式首 token 通常 1-2 秒内返回；开启思考后，复杂任务可能要先等 10-30 秒思考完成才开始输出回答（流式场景思考增量会提前返回，但很多前端只渲染 content 区域，感知上仍是"长时间无响应"）。产品设计上建议把思考状态渲染出来，或用 auto 模式让模型只对真正复杂的问题付思考成本。

## 2. reasoning_content：思考与回答分离

响应结构上，思考内容与最终回答分两个字段：

```
message.reasoning_content   # 思考过程（按输出 token 计费！）
message.content             # 最终回答
usage.reasoning_tokens      # 思考 token 数
```

三条解析纪律：

- **只把 content 喂给下游**：结构化解析、存储、展示都只读 content；reasoning_content 用于展示"思考中"状态或调试，不参与业务逻辑
- **思考也算钱**：reasoning_content 按输出 token 计费，思考 token 可能占输出的 70%+，成本敏感场景显式 `disabled`
- **max_completion_tokens 包含思考**：该上限覆盖 reasoning_content + content 两部分，思考过长会截断回答，返回 `finish_reason=length`——长任务要调大上限

## 3. 流式思考：增量渲染与前后端方案

流式模式下 reasoning_content 与 content 都以 delta 增量返回：

```python
stream = client.chat.completions.create(
    model="doubao-seed-2-1-pro-260623",
    messages=[{"role": "user", "content": "解这道题"}],
    stream=True,
    extra_body={"thinking": {"type": "enabled"}}
)
for chunk in stream:
    delta = chunk.choices[0].delta
    if delta.reasoning_content:          # 思考增量
        print(f"[思考] {delta.reasoning_content}", end="")
    if delta.content:                    # 回答增量
        print(f"[回答] {delta.content}", end="")
```

前端实现要点：原生 EventSource 仅支持 GET，SSE 流式对话需自定义支持 POST 的客户端（或走 SSE 包装）；思考与回答分两个区域渲染，回答区等思考结束后再展示，或思考区折叠显示。

## 4. 多轮对话的思考回传纪律

工具调用或长链路多轮场景，**上一轮的 reasoning_content 必须回传**，这是火山方舟 API 的硬性要求（与 Kimi 系一致）：

```python
# 错误：只回传 content，思考被丢弃 → 后续质量不稳定
messages.append({"role": "assistant", "content": prev_content})

# 正确：完整回传 content + reasoning_content
messages.append({
    "role": "assistant",
    "content": prev_content,
    "reasoning_content": prev_reasoning
})
```

若模型未产生思考（disabled 模式），reasoning_content 为空字符串，同样原样回传即可。这条纪律在多轮 Agent 循环中尤其重要——丢思考会导致模型"忘记自己推理到哪"。

## 5. 思考的成本与时间账

| 因素 | 影响 |
|------|------|
| 输出单价 | 2.1 Pro 输出 30 元/百万 tokens，思考含在内 |
| 思考占比 | 复杂任务思考可能占输出 token 的 50-70% |
| 延迟 | 思考使首 token 延迟显著增加（秒级到数十秒） |
| 超时 | 客户端超时按分钟级设置（长上下文可达 20-45 秒+） |

成本控制三板斧：简单任务显式 `disabled`；混合任务用 `auto` 让模型自己判断；复杂任务接受思考成本但用流式渲染降低用户等待感知。

## 6. 思考与工具调用的交互

开启思考的 Agent 循环里，思考内容会随工具调用轮次反复产生：每一轮"思考 + 调工具"都生成新的 reasoning_content，且**每轮回传时都要带着当轮的思考**——这与普通多轮对话的纪律一致，但成本影响更大：思考 token 每轮都按输出计费，8 轮工具循环可能产生 8 份思考。两条优化：简单工具调用场景显式 `disabled`（工具参数提取不需要深度推理）；必须在思考模式下跑长链路时，把轮次上限从 8 收紧到 4-5，用"更准的思考"换"更少的轮次"。

## 7. Deep Think：工具验证循环

Seed 2.1 的 Deep Think 是比 thinking 更进一步的推理扩展：执行"推理→验证→修正→选择"自动循环，验证阶段**显式调用网络搜索与代码沙盒**。与 thinking 的区别：

- thinking：纯内部思考，不调外部工具，思考内容也通过 reasoning_content 返回
- Deep Think：思考 + 外部验证闭环，假设会被真实执行/检索验证，再修正迭代

适合数学证明、复杂代码调试、长链路规划等"想出来可能错"的任务；耗时长，适合离线批处理或允许等待的场景。注意它不是独立模型，而是推理时配置，与 Function Calling 是两回事——Deep Think 是模型自验，Function Calling 是模型调你的工具。
