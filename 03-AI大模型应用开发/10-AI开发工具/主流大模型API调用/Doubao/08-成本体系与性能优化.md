## 1. 价格体系全景

价格口径：元/百万 tokens（输入 / 输出），2026-08 官方价：

| 模型 | 输入 | 输出 | 缓存命中 | 定位 |
|------|:---:|:---:|:---:|------|
| Seed 2.1 Pro | 6 | 30 | 1.2 | 深度思考旗舰 |
| Seed 2.1 Turbo | 3 | 15 | — | 高频生产（Pro 半价） |
| Seed 2.0 Mini | 0.2 | 2 | — | 速度成本优先 |
| Seed 1.6 Vision | 0.8 | 8 | — | 视觉深度思考 |
| Seed 1.6（2025） | 0.8 | 2 | — | 存量低价主力 |

三个读法：

- **输出比输入贵 5 倍**是行业惯例，但豆包的输出价（30 元）是 Claude Opus 4.7 的近 1/5——官方称综合成本较 Claude Opus 4.6 降低近 80%
- **缓存命中 1.2 元**：比正常输入价（6 元）便宜 80%，长上下文场景成本大头在输入，缓存是最大杠杆
- **思考 token 按输出计费**：开启 thinking 后实际单次调用成本可能翻倍，预算要按"输出 2-3 倍"估算

## 2. 模型分级：按成本档位逐级下探

豆包的模型梯度设计就是给你做成本下探用的。选型决策树：

```
任务质量要求高（复杂代码/推理/长链路 Agent）→ Seed 2.1 Pro（6/30）
高频业务但可接受稍弱 → Seed 2.1 Turbo（3/15，半价）
低延迟大规模并发 → Seed 2.0 Mini（0.2/2，1/10 价格）
视觉理解 → Seed 1.6 Vision（0.8/8）
```

生产实践：**先 Pro 验证效果，再逐级下探找性价比甜点**。同一业务用 Pro 调通、用 Turbo/Mini 跑量，是豆包生态特有的降本姿势——因为切换成本只有一个 model 参数。注意不同档位的上下文窗口与 max output 不同（如 1.6 系列最大输出 32K-64K），下探前确认能力边界。

## 3. 缓存命中：1.2 元的省钱杠杆

豆包缓存命中价 1.2 元/百万 tokens（命中输入部分），比未命中价省 80%。机制与优化：

```text
缓存命中条件：请求前缀（字节级完全一致）命中缓存
├── 命中 → 输入按 1.2 元计，显著降本
├── 未命中 → 按正常输入价计费
└── 命中量查看：usage.prompt_tokens_details.cached_tokens
```

最大化命中率的三个姿势：

1. **稳定长前缀**：system prompt、工具定义、知识库固定内容放最前且保持稳定，动态内容（用户问题）放最后——前缀一致性是命中率的核心
2. **系统提示集中管理**：不要每次请求拼接不同的指令，公共提示模板化
3. **注意缓存异步写入**：缓存建立是异步的，紧接的重复请求可能未命中，首轮冷启动成本无法避免

RAG 场景收益最大：知识库前缀几千到几万 token，命中后每次提问的输入成本从 6 元/百万降到 1.2 元，降幅 80%。对日均百万级调用的业务，这是数量级的成本差。

一个完整算例把成本结构算清楚（Seed 2.1 Pro，单次 RAG 问答）：

```text
输入：system(500) + 知识库(5000) + 用户问题(200) = 5700 tokens
  缓存命中 → 5700 × 1.2元/百万 = 0.0068 元
  未命中   → 5700 × 6元/百万   = 0.0342 元
输出：回答 300 tokens × 30元/百万 = 0.009 元（思考关闭）
总计：命中 ≈ 0.016 元/次，未命中 ≈ 0.043 元/次 → 缓存省 63%

同样的任务若开启思考（输出翻倍 600 tokens）→ 0.025 元/次，思考成本 ≈ 回答成本
```

结论：**单次调用看似"几厘钱"，日均百万级调用差一个数量级**。三个成本杠杆按优先级排序：缓存命中（输入降 80%）> 思考控制（输出降 50%）> 模型分级（单价降 50-90%）。

## 4. TPM 限流与保障包

- 火山方舟按 TPM（每分钟 token）/RPM（每分钟请求）限流，超限返回 429
- 免费/基础档限额较低，高并发业务需购买 **TPM 保障包**（按量锁定吞吐额度）
- 平台路线是"低价高并发 + 上下文缓存 + TPM 保障包"三件套：低价模型 + 缓存降本 + 保障包保吞吐

客户端应对：指数退避重试（429 后按 1s/2s/4s 退避）、限流降级（切 Turbo/Mini 或第三方模型）、请求合并（减少 RPM 消耗）。注意第三方反馈火山方舟存在高峰超售导致的限流波动，关键业务要设计降级路径（09 篇）。

## 6. 成本治理实战

| 治理手段 | 做法 | 收益 |
|----------|------|------|
| 模型分级 | Pro 验证 → Turbo/Mini 跑量 | 成本降 50-90% |
| 缓存优化 | 稳定前缀 + 公共模板 | 输入成本降 80% |
| 思考控制 | 简单任务 disabled，混合任务 auto | 省 50-70% 输出 token |
| 轮次上限 | Agent 循环硬性 8-12 轮 | 防死循环烧钱 |
| usage 打点 | 每调用记录 usage，按业务线汇总 | 成本可观测，定位异常 |
| 限流降级 | 429 退避 + 多模型降级 | 吞吐稳定不超预算 |

成本治理闭环：**记录（usage 打点）→ 分析（哪条业务线贵）→ 优化（分级/缓存/思考控制）→ 验证（成本回归）**。豆包的模型梯度与缓存机制是国产里最利于成本治理的，前提是把 usage 数据收集起来。
