## 1. MoE 稀疏架构：激活效率 7 倍

混合专家（Mixture of Experts, MoE）是当前千亿级大模型的主流架构，核心思想：**总参数量很大，但每次推理只激活一部分参数**。豆包 Seed 2.1 采用完整 MoE 稀疏架构，官方称激活参数效率达到稠密模型的 7 倍。

这一数字的含义需要拆开理解：

- **稀疏激活**：总参数按专家（expert）分组，输入 token 经路由器（router）分发给 Top-K 个专家计算，未激活的参数不参与前向计算
- **效率来源**：相比同规模稠密模型（所有参数每次全激活），MoE 在相同算力下可以承载大得多的总参数量，知识容量更高、单 token 推理成本更低
- **7 倍的含义**：即同样"干活"的激活参数下，模型承载的知识/能力约为稠密模型的 7 倍——这是豆包"低价高性能"路线的架构根基

MoE 的路由机制决定了它的两个工程特征：**负载不均衡**——热门专家可能被过度调用，需要额外的负载均衡损失（auxiliary loss）约束路由分布；**专家冗余**——不同 token 可能路由到高度相似的专家组合，需要反复剪枝与合并优化。这些是训练侧的代价，对 API 调用者透明，但解释了为什么"MoE 模型便宜"的承诺依赖平台侧的调度质量——火山方舟的 TPM 限流与超售管理，本质就是在有限的专家算力上做配额分配。

字节强调不追求参数规模堆砌，而是让模型高效完成实际任务。这与部分竞品（如 Kimi K3 公开 2.8T 总参数）形成对比：豆包选择不公开参数规模，以评测结果和价格说话。

## 2. UltraMem：访存成本降 83%

MoE 的瓶颈不在计算而在**访存**：专家参数放不进单卡显存，需要跨卡搬运。字节自研的 UltraMem 是针对 MoE 的访存优化技术：

- 优化方向：将专家权重按访问频率分层放置，热专家驻留高带宽内存，冷专家下沉廉价存储
- 效果：MoE 访存成本降低 83%，直接转化为更低的推理延迟与更低的单位成本
- 工程意义：83% 的访存降幅解释了豆包为何能把输出价格打到 30 元/百万 tokens（Seed 2.1 Pro）——同价位 Claude Opus 4.7 的成本是它的近 5 倍

除 UltraMem 外，字节还自研了 MoE 架构的计算资源调度方案，使调度效率提升 37%。这些优化共同支撑火山方舟"低价高并发 + 上下文缓存 + TPM 保障包"的基础设施路线。

## 3. 256K 上下文与推理时资源分配

Seed 2.1 系列支持 **256K tokens 上下文窗口**，与国产第一梯队持平（Kimi K3 为 1M，DeepSeek 为 128K）。

256K 上下文（约 20-30 万字中文）覆盖了绝大多数工程场景：整仓代码分析（Seed 2.1 可理解整个代码仓库）、长文档问答、多轮 Agent 会话。上下文长度在服务端还直接影响显存占用——KV cache 随序列长度线性增长，256K 的显存成本是 32K 的 8 倍，平台因此对长上下文请求的定价（或限流）更严格，这也是长任务优先考虑缓存命中价的原因之一。需要注意三点：

- **上下文不是越长越好**：256K 下长文检索精度会下降，RAG 场景仍建议分块检索而非全量塞入
- **成本非线性**：输入 token 按量计费，长上下文直接推高单次成本，缓存命中（1.2 元/百万）是长上下文场景的省钱关键
- **输出窗口单独限制**：Seed 1.6 系列最大输出 32K-64K，长回答/长代码生成要确认所选模型的 max output

## 4. Deep Think：推理-验证-修正-选择

Deep Think 是 Seed 2.1 引入的推理时配置（inference-time scaling），执行"推理→验证→修正→选择"的自动化循环：

- 模型先生成假设方案
- 调用外部工具（网络搜索、代码沙盒）验证假设
- 根据验证结果修正方案
- 多轮迭代后选择最优答案输出

这与 OpenAI o3 系的"隐藏思考"不同：Deep Think 的验证步骤**显式调用工具**，把"想"和"验"分开，适合数学证明、复杂编程、长链路推理任务。开发者视角的要点：

- Deep Think 通过请求参数开启（类似 thinking 配置），不是独立模型
- 循环耗时长，适合离线任务或允许等待的场景
- 与 Function Calling 是两回事：Function Calling 是模型调用你的工具，Deep Think 是模型自调沙盒/搜索验证自己

## 5. 与其他模型架构的对比

| 维度 | Seed 2.1 | DeepSeek V4 | Kimi K3 | Claude Opus 4.7 |
|------|----------|-------------|---------|-----------------|
| 架构 | MoE 稀疏（7 倍激活效率） | MoE + MLA 多头潜注意力 | MoE（2.8T 总参/1M 上下文） | 混合（未完全公开） |
| 上下文 | 256K | 128K | 1M | 200K |
| 推理扩展 | Deep Think（工具验证循环） | 深度思考（思考预算） | 思考默认开启 | Extended Thinking |
| 参数公开 | 否（强调效率） | 是 | 是（2.8T） | 否 |
| 性能基准 | SciCode 59.8 超 GPT-5.5 | 代码约为 Claude 90% | SWE-Bench Pro 58.6 | 综合标杆 |

豆包的架构策略一句话总结：**不拼参数数字，拼效率与工程**——MoE 提容量、UltraMem 降访存、Deep Think 拉长推理时间换质量，三者叠加支撑"对标 GPT-5.5 + 价格只有其 1/5"的定位。
