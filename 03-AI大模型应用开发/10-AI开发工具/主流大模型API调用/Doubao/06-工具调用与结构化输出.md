## 1. Function Calling 完整循环

模型不执行工具——这是理解 Function Calling 的第一原则。完整循环五步：

```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的实时天气",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名"}
            },
            "required": ["city"]
        }
    }
}]

messages = [{"role": "user", "content": "北京今天天气怎么样？"}]

for turn in range(8):                        # ① 硬性轮次上限，防死循环
    response = client.chat.completions.create(
        model="doubao-seed-2-1-pro-260623",
        messages=messages,
        tools=tools,
        tool_choice="auto"                   # auto / none / required
    )
    msg = response.choices[0].message

    if msg.tool_calls:                       # ② 模型要调工具
        messages.append(msg)                 # ③ 完整 assistant 消息回传（含 tool_calls）
        for tc in msg.tool_calls:
            result = execute_tool(tc.function.name, tc.function.arguments)  # ④ 服务端执行
            messages.append({                # ⑤ tool 结果回传
                "role": "tool",
                "tool_call_id": tc.id,       # ★ tool_call_id 必须匹配
                "content": result
            })
    else:                                    # 模型停止调工具
        print(msg.content)
        break
```

三个铁律：assistant 消息必须完整回传（含 tool_calls 与 reasoning_content）、tool_call_id 必须一一匹配、轮次上限硬性设置。工具定义中 description 是模型的"说明书"，写清做什么、何时用、参数含义，直接决定调用准确率。

工具定义的设计规范直接影响调用质量，四条经验：

1. **描述三要素**：做什么（功能）、何时用（触发条件）、边界（不做什么）。"查询指定城市的实时天气，当用户询问天气时使用；不处理历史天气"比"天气查询"命中率高得多
2. **参数即决策负担**：参数越少越准。可选参数尽量拆成独立工具或用默认值，模型在 10 个参数里挑错字段的概率远高于 3 个参数
3. **一工具一职责**：不要写"全能工具"（一个函数既查订单又退款），模型难以决策该不该调、参数怎么填
4. **tool_choice 四值**：`auto`（默认，模型自选）、`none`（禁止调用）、`required`（强制调用一次，用于路由/提取场景）、指定工具名（强制调该工具）——路由分发、信息提取类任务用 required/指定名，能显著提升准确率

## 2. 并行工具调用

豆包支持 Parallel Tool Calls：模型一次返回多个 tool_calls，你的代码并行执行再批量回传：

```python
if msg.tool_calls:
    messages.append(msg)
    results = await asyncio.gather(*[
        execute_tool(tc.function.name, tc.function.arguments)
        for tc in msg.tool_calls
    ])
    for tc, result in zip(msg.tool_calls, results):
        messages.append({
            "role": "tool",
            "tool_call_id": tc.id,
            "content": result
        })
```

使用前提：多个工具调用之间**无依赖**。有依赖（第二个工具的入参来自第一个的输出）时，协议层无法表达，只能串行多轮。并行工具是 Agent 吞吐的关键杠杆，但要注意每个工具结果都有 token 成本，无脑并行会推高上下文占用。

## 3. 流式 + 工具的增量累积

流式模式下 tool_calls 参数按 index 分片返回，必须累积完整再解析：

```python
stream = client.chat.completions.create(
    model="doubao-seed-2-1-pro-260623",
    messages=messages, tools=tools, stream=True
)
tool_calls = {}
for chunk in stream:
    delta = chunk.choices[0].delta
    if delta.tool_calls:
        for tc in delta.tool_calls:
            idx = tc.index                      # 分片按 index 组织
            tool_calls.setdefault(idx, {"id": tc.id, "name": "", "args": ""})
            if tc.function.name:
                tool_calls[idx]["name"] += tc.function.name
            if tc.function.arguments:
                tool_calls[idx]["args"] += tc.function.arguments   # 增量拼接

# 流结束后才解析 JSON 并执行
for idx, tc in tool_calls.items():
    args = json.loads(tc["args"])               # ★ 等完整再解析
    ...
```

不能从第一个分片就开始执行工具——arguments 是跨分片增量拼接的，中途解析必然 JSON 解析失败。

## 4. 结构化输出：JSON Object 与 JSON Schema

豆包支持两种结构化输出（beta），与思考、工具调用可组合：

```python
# 方式一：JSON Object（宽松，提示词中需包含 "json" 关键词）
response = client.chat.completions.create(
    model="doubao-seed-2-1-pro-260623",
    messages=[{"role": "user", "content": "提取订单信息，输出 json"}],
    response_format={"type": "json_object"}
)

# 方式二：JSON Schema（严格，字段完整校验）
response = client.chat.completions.create(
    model="doubao-seed-2-1-pro-260623",
    messages=[{"role": "user", "content": "提取订单信息"}],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "order_extraction",
            "schema": {
                "type": "object",
                "properties": {
                    "date": {"type": "string"},
                    "product": {"type": "string"},
                    "quantity": {"type": "integer"}
                },
                "required": ["date", "product", "quantity"]
            }
        }
    }
)
```

选择逻辑：数据要进数据库/下游强类型系统 → JSON Schema 严格模式；只是便于解析 → JSON Object。严格模式仍建议在服务端做二次校验——结构化输出降低但不会消除格式错误。

一个常见误解是"JSON Object 模式不需要提示词约束"——实际上它仍是自由文本生成 + 格式约束，模型可能输出不完整 JSON 或把字段名改写，提示词里必须明确要求输出字段与格式（官方建议包含 "json" 关键词）。JSON Schema 模式则把约束写死在 schema 里，模型按 schema 逐字段生成，字段名与类型稳定，但 schema 设计要克制：`required` 只放业务必须字段、枚举值要写全、避免深层嵌套（模型生成深层嵌套 JSON 的失败率显著更高）。

## 5. 工具调用与思考的叠加

Seed 2.x 支持 thinking + tools 组合：模型先思考"该调哪个工具、参数怎么给"，再输出 tool_calls。工程要点：

- 多轮循环中 assistant 消息需同时回传 reasoning_content 与 tool_calls（05 篇纪律的延伸）
- 流式场景思考增量与 tool_calls 增量交错到达，按字段分别累积
- 思考开启会显著增加每轮耗时，Agent 长链路任务要在轮次上限与超时上留足余量

## 6. 工具执行失败的处理

工具调用循环最常见的崩溃点是"工具执行失败后循环卡死"。三条处理纪律：

1. **错误转 JSON 回传，不抛异常**：把异常捕获后转为结构化错误内容回传给模型（`{"error": "订单号不存在"}`），模型能据此修正参数或换工具重试——这是消除 80% 卡死的经验做法
2. **工具结果限大小**：大结果截断（如 4KB）或摘要后回传，防上下文爆炸推高后续轮次成本
3. **失败计数兜底**：同一工具连续失败 N 次（如 3 次）直接终止循环返回兜底话术，避免模型反复重试同一个必失败的工具

## 7. 安全清单

| 安全项 | 做法 |
|--------|------|
| Allowlist 分发 | 只执行白名单内工具，禁止 eval/动态导入 |
| Schema 二次校验 | 模型输出的工具参数服务端再验证 |
| 轮次上限 | 硬性 8-12 轮，防死循环烧钱 |
| 敏感操作审批 | 删除/支付类人工确认 + 幂等键 |
| 工具结果限大小 | 截断大结果，防上下文爆炸 |
| 日志脱敏 | 工具参数中的密钥/个人信息脱敏 |
| 思考内容不落业务库 | reasoning_content 仅调试/展示用 |
