## 1. 工作流核心概念

### 1.1 什么是工作流

```text
工作流 = 预定义的多步骤 AI 任务流水线

聊天模式：用户输入 → LLM → 输出 (不可控过程)
工作流：  用户输入 → 步骤1 → 步骤2 → ... → 输出 (精确控制每一步)

对比：
┌──────────────────────────────────────────────────┐
│ 聊天模式 (Chat)           工作流 (Workflow)       │
├──────────────────────────────────────────────────┤
│ 自由度大、不可预测        精确控制、可复现        │
│ AI 决定做什么             你决定做什么            │
│ 适合开放式对话            适合业务流程自动化      │
└──────────────────────────────────────────────────┘
```

### 1.2 工作流在 Bot 中的使用

```text
方式一：作为 Bot 技能
  Bot → 技能 → 添加工作流 → 选择已创建的工作流
  → Bot 对话中，当用户意图匹配时自动触发

方式二：独立运行
  工作流编辑页 → 运行 → 输入参数 → 执行 → 查看结果
  → 不依赖 Bot，可通过 API 直接调用

方式三：API 调用
  POST /v1/workflow/run
  → 外部系统（Java/Python/脚本）调用工作流
```

## 2. 节点体系详解

### 2.1 节点全景

```text
Coze 工作流节点类型：

┌─────────────────────────────────────────────────────┐
│ 节点类型            功能              使用频率       │
├─────────────────────────────────────────────────────┤
│ 开始节点            定义输入参数          ✅ 必须     │
│ 结束节点            定义输出结果          ✅ 必须     │
│ LLM 节点            调用大模型             ⭐⭐⭐⭐⭐  │
│ 知识库检索          语义搜索知识库         ⭐⭐⭐⭐   │
│ 代码节点            Python/JS 脚本         ⭐⭐⭐⭐   │
│ 插件节点            调用插件能力           ⭐⭐⭐⭐   │
│ 条件判断 (IF-ELSE)  分支逻辑               ⭐⭐⭐⭐   │
│ 循环节点            遍历数组               ⭐⭐⭐     │
│ 变量赋值            创建/修改变量          ⭐⭐⭐     │
│ HTTP 请求            调用外部 API           ⭐⭐⭐     │
│ 文本处理            模板拼接/格式化        ⭐⭐⭐     │
│ 数据库操作          查询结构化数据         ⭐⭐       │
│ 子工作流            调用另一个工作流       ⭐⭐       │
│ 定时器              延时/定时执行          ⭐         │
└─────────────────────────────────────────────────────┘
```

### 2.2 开始/结束节点

```text
开始节点 (Start) — 定义工作流的输入

输入字段类型：
├── 文本 (String)：单行文字
├── 多行文本：长文、多段落
├── 数字 (Number)：整数或小数
├── 布尔 (Boolean)：是/否
├── 文件：图片、文档
└── 数组 (Array)：列表数据

每个字段都有：
├── 变量名 (key)：在后续节点中以 {{input.key}} 引用
├── 是否必填
└── 默认值

结束节点 (End) — 定义工作流的输出

输出内容：
├── 变量选择：{{llm_node.output}}
├── 文本拼接："处理完成，结果为：" + {{result}}
└── JSON 对象：结构化输出
```

### 2.3 LLM 节点

```text
LLM 节点 = 工作流中调用大模型

配置项：
├── 模型选择：豆包 1.5 Pro / Lite / Kimi / DeepSeek
├── 系统提示词 (System Prompt)：角色 + 规则
├── 用户提示词 (User Prompt)：当前任务 + 数据
├── 上下文 (Context)：引用的变量（知识库结果、前置节点输出）
├── 输出格式：
│   ├── 文本 (Text)：自由文本输出
│   ├── JSON：结构化 JSON 输出
│   └── Markdown：格式化文本
├── 温度 (Temperature)：0.0-1.0
└── 记忆窗口：是否带入对话历史

提示词中使用变量：
系统提示词：
"你是专业的数据分析师，分析以下数据并给出洞察。"
用户提示词：
"请分析以下订单数据：
{{start.order_data}}

分析维度：
1. 总金额统计
2. 热销商品 TOP3
3. 异常订单标注"
```

### 2.4 代码节点

```python
# Coze 代码节点 — Python 3 运行环境

# 输入：通过变量引用 {{variable_name}}
# 输出：return 字典

def main(input_text: str, threshold: float = 0.8) -> dict:
    """
    输入：上行节点的输出文本和阈值
    输出：处理后的结构化结果
    """
    import json
    import re

    # 解析文本
    data = json.loads(input_text) if isinstance(input_text, str) else input_text

    # 业务逻辑
    total = sum(item.get('amount', 0) for item in data.get('orders', []))
    high_value = [o for o in data.get('orders', []) if o.get('amount', 0) > threshold]

    return {
        "total_amount": total,
        "order_count": len(data.get('orders', [])),
        "high_value_count": len(high_value),
        "avg_amount": total / len(data.get('orders', [])) if data.get('orders') else 0
    }
```

```javascript
// Coze 代码节点同样支持 JavaScript
function main(inputText, threshold = 0.8) {
    const data = typeof inputText === 'string' ? JSON.parse(inputText) : inputText;

    const orders = data.orders || [];
    const total = orders.reduce((sum, o) => sum + (o.amount || 0), 0);
    const highValue = orders.filter(o => o.amount > threshold);

    return {
        total_amount: total,
        order_count: orders.length,
        high_value_count: highValue.length,
        avg_amount: orders.length ? total / orders.length : 0
    };
}
```

### 2.5 条件判断节点

```text
条件判断 (IF-ELSE) — 根据条件走向不同分支

条件类型：
├── 变量比较：{{code.score}} > 0.8
├── 文本包含：{{llm.output}} contains "紧急"
├── 文本为空：{{input.query}} is empty
├── 数组长度：len({{knowledge.result}}) > 0
├── 布尔判断：{{input.is_vip}} == true
└── 多条件组合：A AND (B OR C)

分支结构：
         ┌──→ 分支 A (条件满足时)
  IF → ──┤
         └──→ 分支 B (条件不满足时) — ELSE

  复杂分支 (多个 IF 级联)：
  IF 条件1 ──→ 分支A
  ELSE IF 条件2 ──→ 分支B
  ELSE ──→ 分支C
```

### 2.6 循环节点

```text
循环节点 — 对数组中的每个元素重复执行

配置：
├── 输入数组：{{source.array_data}}
├── 循环变量：{{loop.item}} — 当前迭代元素
├── 循环索引：{{loop.index}} — 从 0 开始
├── 最大循环次数：防止无限循环
└── 输出：所有迭代结果的数组

场景：
├── 批量分析：逐篇分析文档摘要
├── 批量翻译：列表中的每条文本
├── 批量 API 调用：逐条查询商品详情
└── 批量数据清洗：逐行处理 CSV 数据
```

### 2.7 插件节点

```text
插件节点 — 在工作流中直接调用插件

已安装的插件直接作为节点拖入工作流：

示例 1：必应搜索插件
输入：{{input.search_query}}
输出：搜索结果列表 {title, url, snippet}

示例 2：图片理解插件
输入：{{input.image_url}}
输出：图片的文字描述

示例 3：链接读取 (WebPilot)
输入：{{http_response.url}}
输出：网页正文内容

插件节点的输入/输出变量可以直接连接其他节点
→ 形成：LLM 分析意图 → 搜索 → LLM 总结 → 输出
```

## 3. 变量系统与类型

### 3.1 变量来源

```text
工作流中变量的三级来源：

1. 输入变量 (Start 节点定义)
   引用：{{start.variable_name}}

2. 节点输出变量 (每个节点产出)
   LLM 节点：{{llm_node.output}}
   代码节点：{{code_node.result}}
   知识库：{{knowledge_node.items}}
   插件节点：{{plugin_node.result}}
   HTTP 节点：{{http_node.body}}

3. 变量赋值节点 (主动创建的中间变量)
   引用：{{my_var}}
```

### 3.2 变量类型

| 类型 | 示例 | 适用操作 |
|------|------|---------|
| **String** | `"Hello"` | 拼接、搜索、截取、正则 |
| **Number** | `42`, `3.14` | 加减乘除、比较 |
| **Boolean** | `true`, `false` | 条件判断 |
| **Object (JSON)** | `{"name":"张三"}` | `.属性名` 取值 |
| **Array** | `[1, 2, 3]` | 遍历、索引访问 `[0]` |
| **File** | 图片/文档 | 传给 LLM/插件 |

### 3.3 变量作用域

```text
变量可见性规则：

├── 节点输出 → 后续所有节点可见
├── 上游节点输出 → 下游节点可见
├── 下游节点输出 → 上游不可见 ❌
├── 循环内部变量 → 仅循环体内可见
├── 条件分支内变量 → 分支结束 不可见（需用变量聚合）
└── 全局变量 → 整个工作流可见
```

## 4. 工作流实战案例

### 4.1 案例一：订单智能处理

```text
场景：电商订单自动处理——分类 → 风险评估 → 生成回复

开始 (订单数据)
    │
    ▼
LLM (订单分类)
  Prompt: "分析以下订单，输出 JSON: {category, priority, risk}"
    │
    ▼
条件判断 priority
    │
    ├── priority == "urgent"
    │   └──→ LLM (紧急处理话术 + 升级到人工)
    │
    ├── priority == "normal"
    │   └──→ 知识库检索 (订单政策)
    │        └──→ LLM (根据政策生成回复)
    │
    └── priority == "low"
        └──→ LLM (自动确认 + 营销推荐)
              │
              ▼
         结束 (回复结果)
```

### 4.2 案例二：内容审核与改写

```text
场景：UGC 内容发布前审核

开始 (用户提交内容)
    │
    ▼
LLM (内容分析)
  Prompt: "分析以下内容，输出: {is_safe, issues[], risk_level}"
    │
    ▼
条件判断 is_safe
    │
    ├── true → 结束 (通过，直接发布)
    │
    └── false →
        条件判断 risk_level
            │
            ├── "high" → LLM (生成拒绝理由) → 结束 (拒绝)
            │
            └── "low" / "medium" →
                LLM (改写违规内容)
                → 结束 (返回修改建议)
```

### 4.3 案例三：日报自动生成

```text
场景：根据工作日志自动生成日报

开始 (日期 + 项目名)
    │
    ▼
HTTP 请求 (查询工作日志系统 API)
    │
    ▼
代码节点 (数据清洗: 按项目/类型分组)
    │
    ▼
LLM (生成日报)
  Prompt: "根据以下工作记录生成日报：

  # 今日完成
  {{code.today_done}}

  # 进行中
  {{code.in_progress}}

  # 遇到的问题
  {{code.blockers}}

  日报格式：标题 → 摘要 → 分项详情 → 明日计划"
    │
    ▼
结束 (日报 Markdown)
```

## 5. 工作流调试与优化

### 5.1 调试方法

```text
工作流编辑页 → 右上角"运行"

1. 输入测试数据
2. 查看节点执行顺序（高亮当前执行节点）
3. 查看每个节点的输入/输出
4. 查看错误信息

逐节点调试：
├── 绿色勾 → 节点执行成功
├── 红色叉 → 节点执行失败（查看错误详情）
├── 灰色 → 节点未执行（条件分支跳过）
└── 耗时显示 → 每个节点执行时间

日志：
├── 查看 LLM 节点的完整 Prompt（发给模型的原文）
├── 查看 LLM 节点的完整返回
└── 查看知识库检索的具体片段
```

### 5.2 常见问题排错

```text
问题 1：LLM 节点返回的 JSON 格式不正确
解决：
  ├── 在 Prompt 中给出精确的 JSON Schema 示例
  ├── 使用 JSON 输出模式（部分模型支持）
  └── 用代码节点做 JSON 校验和纠错

问题 2：条件判断永远走不到某个分支
解决：
  ├── 检查条件中引用的变量是否正确
  ├── 打印变量值 → 对比预期值
  └── 检查变量类型（字符串 "42" ≠ 数字 42）

问题 3：循环节点输出为空
解决：
  ├── 检查输入数组是否真的非空
  ├── 检查循环体内是否有报错被静默吞掉
  └── 减小最大循环次数做测试

问题 4：工作流执行超时
解决：
  ├── 减少 LLM 调用的 max_tokens
  ├── 减少循环迭代次数
  ├── 合并不必要的顺序节点（2个 LLM 节点合并为1个）
  └── 检查 HTTP 请求的超时设置
```

### 5.3 优化建议

```text
成本优化：
├── 简单任务用豆包 Lite（成本是 Pro 的 1/10）
├── 减少不必要的 LLM 调用（能代码处理的不要用 LLM）
├── 降低最大 Token 数（不要设比实际需要大很多的值）
└── 缓存重复的知识库检索

性能优化：
├── 并行节点 → 不互相依赖的节点可并行执行
├── 提前退出 → 条件不满足时尽早结束
└── 数据筛选 → 先过滤再处理，减少后续节点负担
```
