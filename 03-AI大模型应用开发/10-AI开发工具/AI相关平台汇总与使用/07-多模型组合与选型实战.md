## 1. 选型三维矩阵

```text
选模型三问：

① 场景 → 主打什么？（编程/聊天/长文档/多模态/Agent）
② 成本 → 预算多少？调用频率？
③ 中文 → 是否面向中文用户？合规要求？是否需要国内直连？

三个答案交圈，就是最适模型。
```

├── 需要 API 集成 → DeepSeek（兼容 OpenAI SDK 直接替换）

## 5. 实战方案模板

### 5.1 Java 后端全栈 AI 应用方案

```text
模型层     → DeepSeek V4（高频调用，低成本）+ Claude Sonnet（复杂推理/代码）
向量库     → pgvector（起步）→ Milvus（规模化）
AI 框架    → Spring AI 2.x（Boot 4 + Java 21）
自动化平台 → Dify（知识库 RAG 编排）
编程工具   → Cursor（日常）+ Claude Code（复杂重构）
部署       → Railway（应用层）+ DeepSeek API（模型层，无需自托管）
监控       → OpenTelemetry + Micrometer（Spring Boot 4 内置）
```

## 7. 选型避坑清单

| 坑 | 说明 | 对策 |
|----|------|------|
| 只看基准跑分不看实测 | 基准与实际使用场景差异大 | 拿自己的典型 prompt 实测 3 个候选模型 |
| 忽略 API 定价陷阱 | 输入便宜但输出贵（如 o3-pro 输出 $60/百万Token） | 看**输入+输出**总价，而非只看输入价格 |
| 锁死单一模型 | 技术栈切换成本高 | 用兼容 OpenAI SDK 的模型（DeepSeek/通义/Kimi/GLM），换模型只改 base_url |
| 免费版过度依赖 | 免费版随时可能降额或取消 | 至少有一个付费的 fallback 方案 |
| 忽略合规与数据安全 | 企业数据不能上传第三方 | DeepSeek/通义开源版 + 私有化部署 |
| 向量库过早过度设计 | 百万级以下向量 pgvector 足够 | 量没上千万前不要引入独立向量数据库 |

> 🎯 **核心要点**：2026 的 AI 使用哲学 = **多模型组合（日常免费国产 + 深度付费海外）+ API 层做兼容（OpenAI SDK 兼容的国产模型任意切换）+ 向量库按量演进（pgvector→Milvus）**。一个 Java 后端团队的标准配置：DeepSeek API（主力）+ Claude Sonnet（深度推理）+ Spring AI（框架）+ Dify（RAG）+ pgvector（起步向量库）。
