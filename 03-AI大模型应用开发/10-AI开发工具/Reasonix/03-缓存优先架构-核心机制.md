## 1. DeepSeek 前缀缓存原理

DeepSeek API 的上下文缓存（prefix caching）机制：

- **默认开启**，无需额外配置
- 匹配规则：**当前请求的精确字节前缀必须与先前请求完全一致**——差一个字节缓存即失效
- 实现方式：前缀哈希/字节指纹匹配
- 价格差：缓存命中的输入 token 计费仅为未命中的 **1/50（V4 Flash）甚至 1/120（V4 Pro）**

```text
请求 A：  [system][tools][history-1][query-1]     → 全价
请求 B：  [system][tools][history-1][query-2]     → 前缀命中（system+tools+history-1 按缓存价）
请求 C：  [system][tools][history-1'][query-3]    → 全价（history-1 被改写，前缀失效）
```

关键推论：**长会话中每轮请求都重复发送的历史上下文，如果字节稳定，就是持续的"折扣区"**——会话越长，缓存收益越大。

## 2. 通用 Agent 为什么命中率低

| 通用 Agent 的常见操作 | 对前缀缓存的破坏 |
|---|---|
| 动态压缩历史 | 重写已有内容，前缀字节变化 |
| 消息重排 | 顺序变化，前缀变化 |
| 注入时间戳/随机 ID | 前缀插入新字节 |
| 轮次摘要改写 | 旧内容被替换 |
| 工具结果排序不稳定 | 工具输出顺序变化 |

结果：通用 Agent 在 DeepSeek 上的缓存命中率通常只有 **20-60%**。

Reasonix 的核心批判：**"为了省 100 个 token 损失 10000 个 token 的缓存"**——压缩省下的是全价小 token，丢掉的是折扣大 token，亏本买卖。

## 3. 三区上下文划分

Reasonix 把上下文划分为三个区域，作为架构级不变量强制执行：

```
┌─────────────────────────────────────────────────────┐
│ ① 不可变前缀（IMMUTABLE PREFIX）                     │
│    system prompt + 工具定义 + 持久记忆 + few-shots   │
│    会话内固定不变，只计算一次，哈希锁定                │
├─────────────────────────────────────────────────────┤
│ ② 只追加日志（APPEND-ONLY LOG）                      │
│    对话历史：assistant → tool → assistant → tool     │
│    只追加、不重写、不重排                             │
├─────────────────────────────────────────────────────┤
│ ③ 临时草稿区（VOLATILE SCRATCH）                     │
│    每轮重置的临时信息，不重复上传                     │
│    归入日志前需经 Tool-Call Repair 提炼               │
└─────────────────────────────────────────────────────┘
```

| 区域 | 内容 | 稳定性策略 |
|---|---|---|
| 不可变前缀 | system、工具定义、持久记忆、few-shots | 会话内固定，计算一次哈希锁定 |
| 只追加日志 | assistant/tool 消息对 | 只追加，永不改写 |
| 临时草稿区 | 每轮临时信息 | 每轮重置，不重复上传 |

三区各自承担什么：

- **前缀区**承担"所有确定性内容"——变化最少的字节放在最前面，是缓存命中率的最大贡献区
- **日志区**承担"对话推进"——天然追加型结构，与缓存机制同构
- **草稿区**承担"易变内容"——把它隔离出来，防止污染前缀

## 4. 只追加循环（Append-Only Loop）

执行循环的核心规则：

1. 消息和工具结果一律**尾部追加**
2. 工具调用顺序与时间戳**完全确定性**（相同输入 → 相同顺序）
3. 即使多次 dispatch 工具，前缀仍能命中缓存

```text
轮次 1:  [前缀][user][assistant][tool]         → 命中前缀，全价只有本轮新增
轮次 2:  [前缀][user][assistant][tool][assistant][tool]  → 命中更多前缀
轮次 N:  前缀不断变长，命中率趋于 90%+
```

确定性设计举例：工具调用按固定规则排序而非按结果到达顺序，保证重放时字节一致。

## 5. 接近上限时的优雅压缩

上下文接近窗口上限时，Reasonix **不重写已有内容**，而是：

```
[前缀][摘要(追加的新消息)][日志尾部...]
```

- 旧轮次被摘要成**一条新消息追加**到前缀之后
- 前缀本身保持不变 → 缓存照常命中
- 对比通用 Agent：直接重写历史 → 前缀全碎

压缩决策还支持弹窗确认（v1.20 优化了压缩决策卡片布局，有本地记录回执），用户能看到压缩发生在何时、省了多少。

## 6. 跨会话缓存持久化

DeepSeek 缓存有 TTL（约 5-15 分钟），Reasonix 利用这一点实现跨会话复用：

| 场景 | 机制 |
|---|---|
| 短时间内重开会话 | 重建相同前缀，首次 API 调用仍能命中缓存 |
| 会话中断后续接 | 相同前缀 + 追加日志，缓存延续 |

前提：前缀内容（system/工具定义/持久记忆）必须字节级可复现——这也是记忆文件、技能文件放在固定位置加载的原因（见 06 篇）。

## 7. 成本实测数据

| 指标 | 数据 |
|---|---|
| 长会话缓存命中率 | 90%+，数小时会话保持 94%+ |
| 极端案例（GitHub Projects） | **99.82%**：单日 4.35 亿输入 token，命中 435,033,856，未命中仅 767,616 |
| 成本对比（同会话） | 无缓存约 $61 → Reasonix 约 $12（**2 折，省 80%**） |
| 第三方实测（无矩 AI，2026-05） | 当日实际花费 $1.38（v4-flash），有消费记录佐证 |
| 单任务成本 | Reasonix 约 $0.08 vs Claude Code 约 $0.34（1/4） |
| 日常会话 | Flash 会话 $0.03-0.08；Pro 会话 $0.14-0.35 |

成本公式：

```
会话成本 ≈ 每轮新增全价token × 轮数
           + 前缀token × (1 - 命中率) × 全价比例
```

命中率 99%+ 时，前缀部分成本趋近于零——长会话成本只随"新增内容"线性增长。

> 🎯 核心要点：Reasonix 的架构本质是**把 DeepSeek 的计费规则翻译成工程约束**——"命中缓存 = 1/50 价"→ 上下文必须只追加；"字节精确匹配"→ 一切内容必须确定性生成。缓存不是优化项，是架构本身。
