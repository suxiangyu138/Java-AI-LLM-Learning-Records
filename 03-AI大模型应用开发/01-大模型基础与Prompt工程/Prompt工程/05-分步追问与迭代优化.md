## 1. 追问三层法

### 1.1 三层追问模型

```text
追问三层法 — 从表面到本质的递进：

  第一层：What（是什么）
    → "解释 XX 是什么"
    → 建立基本认知

  第二层：Why（为什么这样设计）
    → "为什么要用 XX 而不是 YY？"
    → "这个设计的权衡是什么？"
    → 理解设计意图

  第三层：How / What If（怎么实现 / 边界在哪）
    → "如果我改成 XX 会怎样？"
    → "极端情况下会出什么问题？"
    → 触及知识边界
```

### 1.2 追问实战

```text
用户："Spring @Transactional 的原理是什么？"
LLM：详细解释 AOP 代理机制...

追问 1（Why 层）：
  "为什么要用 AOP 代理而不是直接在方法前后插代码？
   这种设计有什么代价？"

追问 2（How 层）：
  "如果方法内部调用另一个 @Transactional 方法，
   事务传播行为会怎样？为什么经常有人踩这个坑？"

追问 3（What If 层）：
  "如果我在 @Transactional 方法里开新线程操作数据库，
   事务会传播到新线程吗？Spring 6 的虚拟线程会改变这个行为吗？"

效果：
  一层回答 → 表面知识
  三层追问 → 深度理解 + 边界认知 + 版本差异
```

## 2. Prompt 迭代优化流程

### 2.1 四步迭代法

```text
Prompt 迭代优化流程：

  ① 写初版 Prompt → 跑一遍 → 记录问题
  ② 分析问题：是角色不对？约束不够？还是缺少示例？
  ③ 针对性修改 → 再跑一遍 → 对比
  ④ 稳定后 → 保存为模板

迭代中问自己的问题：
  → 输出格式符合预期吗？
  → 有没有遗漏关键信息？
  → 有没有不该出现的冗余？
  → 对边界情况的处理是否正确？
  → Token 消耗是否合理？
```

### 2.2 迭代记录模板

```text
Prompt 迭代日志：

  v1 (2026-01-01)：
  Prompt: "解释 Java GC"
  问题：回答太长（500字），没有代码示例，过于学术
  Token: 850

  v2 (2026-01-01)：
  改动：+角色设定（"你是 Java 性能调优专家"）
        +格式约束（"300字以内，附一个示例"）
  效果：长度符合，但示例太简单

  v3 (2026-01-02)：
  改动：+具体示例要求（"用实际线上OOM场景"）
  效果：完美
  Token: 420
```

## 3. Chain-of-Density 摘要

### 3.1 原理

```text
Chain-of-Density (CoD) = 迭代式摘要生成

  第 1 轮：生成初始摘要（稀疏，只含核心信息）
  第 2 轮：在上一轮基础上，增加 2-3 个新信息点
  第 3 轮：继续增加，但移除最不重要的信息点
  ...直到摘要长度上限

效果：
  逐步"压缩"信息 → 相同长度下信息密度更高
```

### 3.2 Prompt 模板

```text
CoD 摘要 Prompt：

  "文章：{原文}

   第 1 轮：
   生成一段 50 字以内的摘要，只包含最核心的 2-3 个信息点。

   第 2 轮：
   在上一轮摘要的基础上，增加 2-3 个新信息点，
   摘要总长度不超过 70 字。
   如果信息点冲突，保留更重要的。

   第 3 轮：
   继续增加 2-3 个信息点，移除 1-2 个最不重要的信息点，
   总长度不超过 80 字。"
```

## 4. 错误分析与 Prompt 修正

### 4.1 常见 LLM 输出错误类型

| 错误类型 | 表现 | Prompt 修正 |
|----------|------|------------|
| **格式错误** | JSON 多了 `\`\`\`json` 标记 | 加 "不要包含 markdown 标记" |
| **信息遗漏** | 要求 5 点只给了 3 点 | 加 "必须包含全部 X 项" |
| **幻觉编造** | 编造不存在的 API | 加 "不确定就说不知道" |
| **风格跑偏** | 要求幽默结果很严肃 | 给具体风格示例 |
| **长度失控** | 要求 100 字给了 500 字 | 加 "超过长度截断重来" |
| **提前终止** | 代码只写了一部分 | 加 "如果截断，回复'继续'" |

### 4.2 系统性 Prompt 调试

```python
def prompt_debug(prompt_template, test_cases, llm):
    """系统性测试 Prompt 在不同输入上的表现"""
    results = []
    for case in test_cases:
        prompt = prompt_template.format(**case)
        output = llm(prompt)
        results.append({
            'input': case,
            'output': output,
            'issues': check_issues(output)  # 检查格式/长度/内容
        })
    
    # 统计问题分布
    from collections import Counter
    issue_counts = Counter()
    for r in results:
        for issue in r['issues']:
            issue_counts[issue] += 1
    
    return results, issue_counts
```

## 5. 迭代实战案例

### 从一个 Prompt 的进化看迭代过程

```text
需求：让 LLM 为 Java 方法生成单元测试

v1（初版）：
  "为以下方法生成单元测试" → 输出格式混乱、缺少边界 case

v2：
  +角色："你是 Java 测试专家，熟悉 JUnit 5 和 Mockito"
  +约束："使用 Given-When-Then 结构"
  → 格式改善，但测试覆盖不全

v3：
  +模板：
  "为以下方法生成单元测试，要求：
   1. 正常情况测试（1个）
   2. 边界值测试（1个）
   3. 异常情况测试（1个）
   4. Mock 外部依赖
   
   使用 JUnit 5 + Mockito，不要写注释"

v4（最终版）：
  +示例：给一个完整的测试类作为格式参照
  → 输出完美
```

## 核心要点回顾

- 追问三层法：What → Why → What If，从认知到边界
- Prompt 迭代 = 写 → 跑 → 分析问题 → 修改 → 再跑 → 稳定 → 保存
- 记录迭代日志，积累可复用的 Prompt 模板
- Chain-of-Density：迭代式增加信息密度
- 系统性测试 Prompt 在不同输入上的表现 → 发现隐藏问题
