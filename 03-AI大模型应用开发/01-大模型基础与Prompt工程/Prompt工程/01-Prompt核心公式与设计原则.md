## 1. Prompt 的本质

```text
Prompt = 给 LLM 的"指令"或"上下文"

本质：用自然语言编程 → Prompt 就是代码

传统编程：
  input → 代码(规则) → output
  确定性逻辑

LLM Prompt：
  prompt → LLM(概率模型) → output
  概率性生成

关键区别：LLM 不会"严格执行"你的指令，而是"概率性地遵循"
  → Prompt 工程 = 让模型"更可能"输出你想要的
```

## 2. 四要素核心公式

```text
Prompt 输出质量 = 角色设定 × 任务清晰度 × 约束条件 × 示例质量

  四个因子是"乘法"关系 — 任一项为 0，整体归零

  ① 角色设定：  告诉模型"你是谁"→ 决定回答风格和专业度
  ② 任务清晰度： 告诉模型"做什么"→ 决定是否跑偏
  ③ 约束条件：  告诉模型"怎么做"→ 控制输出格式和范围
  ④ 示例质量：  给模型"参照物"→ 精确控制输出样式
```

### 对比示例

```text
❌ 差 Prompt：
  "解释 Java 多态"

✅ 好 Prompt：
  "你是一个有 10 年经验的 Java 架构师（角色）。
   请用以下结构解释 Java 多态（任务+约束）：
   1. 一句话定义（20字以内）
   2. 三种实现方式的代码示例（接口/继承/泛型）
   3. 常见面试陷阱（3个）
   4. 与 Go 语言的 interface 对比

   参考格式（示例）：
   # 一句话定义
   [定义内容]
   
   # 代码示例
   [代码]
   
   # 面试陷阱
   - 陷阱1: ...

   # 对比
   [表格]"
```

## 3. 角色设定

### 3.1 为什么角色很重要

```text
同一问题，不同角色 → 完全不同的回答：

"你是 Python 初学者"    → 通俗解释，大量基础概念
"你是资深 Java 架构师"  → 直接深入原理，用设计模式术语
"你是 Spring 框架维护者" → 从框架作者视角解释设计意图
"你是面试官"           → 以提问方式引导你思考

角色 = 决定回答的深度、角度、术语、风格
```

### 3.2 角色设定技巧

```text
好的角色设定 = 专业身份 + 经验年限 + 具体场景

模板：你是一个 [专业身份]，拥有 [N] 年经验，擅长 [具体领域]

示例：
  ✅ "你是一个 Java 后端架构师，有 10 年经验，擅长高并发系统设计"
  ✅ "你是一个数据分析师，擅长用通俗语言解释统计概念"
  ❌ "你是一个专家"（太模糊）
  ❌ "你是 GPT-4"（无意义）
```

## 4. 任务分解

### 4.1 任务越具体，输出越精准

```text
模糊任务 vs 具体任务：

  ❌ "优化这段代码"
  ✅ "优化这段代码的性能，重点关注：
       1. 数据库查询次数
       2. 不必要的对象创建
       3. 改用 Stream API 简化循环
      输出修改前后的对比 diff"

  ❌ "写一篇关于 AI 的文章"
  ✅ "写一篇面向 Java 后端开发者的 AI 入门文章，1000 字以内，
       重点介绍 RAG 和 Agent 两种落地方式，各附一个 Java 代码示例"
```

### 4.2 复杂任务的结构化分解

```text
复杂任务 → 分解为子任务 → 逐步执行

技巧：
  ① 用编号列出步骤
  ② 每步说明预期产出
  ③ 让模型先确认理解再执行

示例：
  "请按以下步骤完成：
   第一步：分析需求文档，提取核心功能点（用列表）
   第二步：为每个功能点设计 REST API 端点（用表格）
   第三步：选择合适的数据存储方案并说明理由
   
   请先回复'已理解'再开始第一步。"
```

## 5. 约束条件

### 5.1 常用约束类型

| 约束类型 | 示例 | 效果 |
|----------|------|------|
| **长度** | "100 字以内"、"恰好 3 句话" | 控制输出篇幅 |
| **格式** | "用 JSON 格式返回"、"用 Markdown 表格" | 结构化输出 |
| **风格** | "用小学生能理解的语言" | 调整难度 |
| **范围** | "只使用 Java 8 语法"、"不要用框架" | 限制方案空间 |
| **否定** | "不要使用 XX 模式"、"不要写注释" | 排除不需要的 |
| **温度** | "确定的答案不要猜测" | 控制随机性 |

### 5.2 约束的组合使用

```text
强约束 Prompt 示例：

  "用 JSON 格式返回以下内容（约束1）：
   {
     'summary': '50字以内的事故总结'（约束2）,
     'root_cause': '用术语解释'（约束3）,
     'fix': '修复代码，不写注释'（约束4）
   }
   如果无法确定根因，在 root_cause 中写 'UNKNOWN'（约束5）"
```

## 6. 示例驱动

### 6.1 Why Examples

```text
Few-Shot 示例 = 给模型"照葫芦画瓢"的参照

示例告诉模型：
  ✅ 输出的精确格式（比描述更有效）
  ✅ 风格和语气（"用这种口吻回答"）
  ✅ 边界情况处理（"这种情况返回 X"）

原则：示例 > 描述
  → "输出成表格" vs 给出一个表格示例 → 后者效果明显更好
```

### 6.2 示例设计原则

```text
① 格式一致性：示例的格式 = 期望输出的格式
② 覆盖边界：至少包含一个正常 case + 一个异常 case
③ 简洁但有代表性：示例不需要完整，展示模式即可
④ 排序：最相关的示例放在最后（nearer to query）

示例：
  "将以下文本分类为 {正面, 负面, 中性}：
  
   文本：这个产品太垃圾了
   分类：负面
   
   文本：还行吧，凑合用
   分类：中性
   
   文本：[待分类的文本]
   分类："
```

## 7. 常见 Prompt 反模式

| 反模式 | 问题 | 改正 |
|--------|------|------|
| **模糊指令** | "写点什么" | 明确任务+约束+格式 |
| **信息过载** | 给 5 页上下文+复杂要求 | 逐步分解，分轮对话 |
| **自相矛盾** | "简洁但要详细" | 选一个，或分层输出 |
| **假示例** | 示例和实际要求不一致 | 确保示例精确对应 |
| **忘掉角色** | 角色设定后中途失效 | 每个新 Prompt 重申角色 |
| **过度微妙** | "用稍微正式一点的语气" | 给具体示例而非模糊描述 |

---

## 核心要点回顾

- Prompt 输出质量 = 角色 × 任务 × 约束 × 示例（乘法关系）
- 角色 = 专业身份 + 经验年限 + 具体场景 → 决定回答视角
- 示例 > 描述：给一个格式示例比长篇描述格式要求有效得多
- 复杂任务 → 编号分解步骤 → 让模型先确认理解
- 避免模糊指令、自相矛盾、信息过载三大反模式
