## 1. 四方对比总表

| 维度 | LlamaIndex | LangChain | Haystack | LangGraph |
|---|---|---|---|---|
| 第一抽象 | **检索/数据** | 编排 | 管道 | 图/状态 |
| 数据连接 | **300+ 连接器** | 最大生态 | 中 | 依赖 LangChain |
| 文档解析 | **LlamaParse（商业级）** | 基础 | 基础 | 依赖 LangChain |
| 索引 | **四种内置** | 外部 | 存储抽象 | 依赖 LangChain |
| 编排 | Workflows（事件） | LCEL | 管道 DAG | 状态机 |
| 生产导向 | 中 | 低 | **高** | 中 |
| Agent | LlamaAgents | 深（LangGraph） | 保守 | **最强** |
| 可观测 | OTel/LlamaTrace | LangSmith | OTel 原生 | LangSmith |
| 代码量（基础 RAG） | **少 30-40%** | 基准 | 中 | 中 |
| 许可 | MIT | MIT | Apache 2.0 | MIT |

### 定位一句话

```
LlamaIndex：数据/检索最专（解析是竞争资产）
LangChain：编排/生态最广（抽象厚）
Haystack：生产管道最稳（强类型）
LangGraph：复杂 Agent 最深（状态机）
```

## 2. 基准数据

### 框架开销基准（2026）

| 框架 | 每次查询框架开销 | Token 开销 |
|---|---|---|
| **LlamaIndex** | **约 6ms** | **约 1.6K tokens** |
| LangGraph | 约 14ms | 约 2.4K tokens |

### 代码量基准

```
基础 RAG 流水线：
LlamaIndex 比 LangChain 少 30-40% 代码
（建索引/查询引擎的封装深度）
```

### 解析成本基准

```
复杂文档解析（2026 实测）：
LlamaParse Agentic 以 18 倍更低成本胜出 GPT-5.2 高推理模式
（解析不是越强模型越好——专用管线更优）
```

### 基准的解读

```
① 编排开销：LlamaIndex 更轻（高并发友好）
② 代码量：封装深 = 上手快、定制要深入
③ 解析：专用管线 > 通用强模型（数据层专业化的证据）
```


## 4. 混用模式

### 2026 实践（行业共识）

```
LlamaIndex 管数据/检索层（连接/解析/索引/QueryEngine）
LangGraph 管编排层（多步 Agent 状态机）
边界：LlamaIndex 查询引擎 → 包装为工具 → LangGraph 节点调用
```

### 实现思路

```python
# 1. LlamaIndex 构建检索（QueryEngine）
query_engine = index.as_query_engine()

# 2. 包装为工具（供 LangGraph Agent 调用）
def search_knowledge(query: str) -> str:
    response = query_engine.query(query)
    return response.response

# 3. LangGraph 节点使用该工具
# node: agent 调用 search_knowledge → 继续编排
```

### 混用原则

```
① 各管一段：数据层 LlamaIndex、编排层 LangGraph（别重叠）
② 接口简单：工具调用（字符串进出）
③ 可观测统一：两边都接同一 OTel/LangSmith
```

### 类似组合（本仓库框架体系）

```
AutoGen 对话编排 + LlamaIndex 检索
Haystack 管道 + LangGraph Agent
核心模式：检索框架 + 编排框架 = 数据与流程解耦
```

## 5. 面试速记

### 核心结论（背诵版）

```
1. LlamaIndex = 检索第一抽象的数据框架（连接/解析/索引/检索/编排）
2. 核心主张："RAG 瓶颈不是模型而是数据管道"（2026 共识）
3. 竞争资产：LlamaParse（v2 四级）+ 300 连接器 + 四种索引
4. Workflows 1.0：事件驱动异步编排（6ms 开销优于 LangGraph 14ms）
5. 基础 RAG 代码比 LangChain 少 30-40%
6. 选型：数据复杂 → LlamaIndex；管道生产 → Haystack；Agent → LangGraph
7. 混用：LlamaIndex 检索 + LangGraph 编排（2026 常见实践）
8. LlamaCloud 正以 LlamaParse 为核心重塑（2026-02 更名）
```

### 面试高频问题

| 问题 | 回答要点 |
|---|---|
| LlamaIndex 与 LangChain 区别？ | 检索优先 vs 编排优先 |
| 为什么选 LlamaIndex？ | 数据接入/解析/检索最专（LlamaParse） |
| Workflows 与 LangGraph？ | 事件驱动 vs 状态机；更轻但深度浅 |
| 生产怎么用？ | 检索层 LlamaIndex + 编排层 LangGraph |
| 数据瓶颈论？ | 模型趋同，解析/检索质量拉开差距 |
| 学它前置？ | RAG 阶段 1-4（原理）是前置 |

### 项目故事模板

> "我负责的知识库系统用 LlamaIndex 做数据层：SimpleDirectoryReader 接入多源文档、层级分块 + 混合检索（RRF）保证召回、QueryEngine 带溯源返回；复杂扫描件走 LlamaParse Agentic 级解析。编排层用 LangGraph 处理多步问题——两框架各管一段，边界清晰。"

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "四个框架必须选一个" | 混用是常态（检索+编排解耦） |
| "数据框架做不了 Agent" | Workflows/LlamaAgents 成熟 |
| "LlamaParse 是智商税" | 复杂文档 18 倍成本优势（vs 强模型高推理） |
| "基准 6ms 全面碾压" | 编排开销优势，状态机深度不如 LangGraph |
| "学框架不学原理" | 框架是封装——质量判断力来自原理（RAG 体系） |

### 选型最终建议

```
复杂文档/多源数据 → LlamaIndex（数据层最专）
受监管生产管道 → Haystack
复杂多步 Agent → LangGraph（检索交给 LlamaIndex）
快速多源原型 → LangChain
企业级数据+Agent → LlamaIndex 检索 + LangGraph 编排
```

> 🎯 收官总结：LlamaIndex 是"数据层专业化"的代表——检索第一抽象 + LlamaParse 竞争资产；选型看"数据复杂度"（数据复杂选它）；2026 混用模式（LlamaIndex 检索 + LangGraph 编排）是复杂系统的务实答案；基准数据要辩证看（编排开销优势 vs 状态机深度差距）；学它之前先把 RAG 原理打牢——框架是原理的封装，原理是框架的钥匙。
