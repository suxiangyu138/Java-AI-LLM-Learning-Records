## 1. 工具调用的机制

### 工具在对话中的角色

```
Agent 生成工具调用请求（不是执行！）
→ 框架执行工具
→ 结果作为消息回传 Agent
→ Agent 基于结果继续

LLM 负责"决定调什么工具 + 参数"
框架负责"实际执行 + 结果回传"
```

### 工具调用循环

```text
assistant: "我需要查一下数据库" (+ tool_call: query_db)
tool 结果: "库存：100 件"
assistant: "库存充足，可以下单" (+ tool_call: create_order)
...
```

### 关键概念：模型不执行，框架执行

| 角色 | 做什么 |
|---|---|
| LLM | 生成工具调用（函数名 + JSON 参数） |
| 框架 | 校验参数 → 执行函数 → 回传结果 |

## 2. FunctionTool 使用

### 定义工具函数

```python
from autogen_core.tools import FunctionTool

def query_inventory(product_id: str) -> str:
    """查询商品库存（模拟）"""
    inventory = {"A001": 100, "A002": 50}
    return f"商品 {product_id} 库存：{inventory.get(product_id, 0)} 件"

# 包装成 Agent 工具
inventory_tool = FunctionTool(
    query_inventory,
    description="查询商品库存，参数 product_id 为商品编号",
)
```

### 注册到 Agent

```python
agent = AssistantAgent(
    name="SalesAgent",
    model_client=model,
    tools=[inventory_tool],        # 工具列表
    system_message="你是销售助手，需要库存信息时调用查询工具。",
)
```

### FunctionTool 关键点

| 要点 | 说明 |
|---|---|
| 自动生成 JSON schema | 从函数签名推断（参数/类型/文档字符串） |
| description 必写 | LLM 靠它决定"何时用这个工具" |
| 类型提示 | 参数要有类型（str/int）——schema 依赖它 |
| 返回字符串 | 结果作为消息回传（要可读） |

## 3. 代码执行器

### 为什么需要代码执行

```
代码生成任务的两条路：
① 生成代码文本给用户（不验证）
② 生成代码 → 执行 → 看结果 → 修正（闭环）
AutoGen 支持②——代码生成闭环是它的招牌能力
```

### 配置代码执行器

```python
from autogen_ext.code_executors.docker import DockerCommandLineCodeExecutor

# 需要 Docker：隔离执行环境
code_executor = DockerCommandLineCodeExecutor(work_dir="workspace")

# 本地执行器（开发用）
# from autogen_ext.code_executors.local import LocalCommandLineCodeExecutor
```

### 执行流程

```
Agent 生成代码（Python 块）
→ 执行器在沙箱运行
→ 输出（stdout/stderr）回传 Agent
→ Agent 分析结果 → 修正或完成
```

### 代码执行器的选择

| 执行器 | 隔离 | 适用 |
|---|---|---|
| LocalCommandLineCodeExecutor | 无（本机） | 开发调试 |
| DockerCommandLineCodeExecutor | 容器隔离 | 生产推荐 |
| JupyterCodeExecutor | notebook 环境 | 数据分析 |

> ⚠️ 安全铁律：**生产环境必须用 Docker 沙箱执行 Agent 代码**——Agent 生成的代码是"不可信代码"，本地执行有任意代码执行风险（06 节展开）。

## 4. 工具注册与多工具管理

### 多工具注册

```python
agent = AssistantAgent(
    name="Assistant",
    model_client=model,
    tools=[
        FunctionTool(query_inventory, description="查询库存"),
        FunctionTool(check_price, description="查询价格"),
        FunctionTool(create_order, description="创建订单"),
    ],
)
```

### 工具设计原则（与 Function Calling 体系一致）

| 原则 | 说明 |
|---|---|
| 一工具一职责 | 别把多个操作塞一个函数 |
| description 写清三件事 | 做什么/何时用/参数边界 |
| 参数越少越好 | 参数多 = 决策负担大 |
| 返回结构化 | JSON/可读字符串，别返回对象 |
| 幂等性 | 可重试不产生副作用（重要操作） |

### 工具数量与上下文

```
工具定义进系统提示 → 工具越多上下文越大、决策越难
经验：单 Agent 工具 10 个以内；超过考虑拆分 Agent
```

## 5. 错误处理与重试

### 工具执行失败的处理

| 失败类型 | 处理 |
|---|---|
| 参数校验失败 | 框架报错 → LLM 修正参数重试 |
| 执行异常 | 异常消息回传 → LLM 决定改参数/换工具 |
| 超时 | 超时返回 → 触发重试策略 |

### 把错误转成消息（关键实践）

```python
def safe_tool(product_id: str) -> str:
    """工具内部兜底：错误转成可读消息（别抛异常）"""
    try:
        result = query_inventory(product_id)
        return result
    except Exception as e:
        # 错误作为消息返回，LLM 能理解并调整
        return f"查询失败：{e}。请检查参数是否正确。"

# 再包一层：框架级重试
inventory_tool = FunctionTool(
    safe_tool,
    description="查询商品库存",
    max_attempts=2,        # 框架自动重试
)
```

### 错误处理三原则

```
① 错误转消息（LLM 可读）——不是抛异常（LLM 看不到）
② 参数错误给提示（"product_id 应为 A001 格式"）
③ 关键操作加幂等（重试不重复执行）
```

## 6. 安全边界

### 工具调用的安全风险

| 风险 | 场景 | 防护 |
|---|---|---|
| 任意代码执行 | Agent 生成的代码本地跑 | Docker 沙箱 |
| 越权操作 | Agent 调用删除/写库工具 | 工具白名单 + 审批 |
| 提示注入 | 工具结果/文档含恶意指令 | 结果隔离 + 输入过滤 |
| 资源滥用 | 无限循环调用工具 | 轮次上限 + 成本预算 |
| 数据泄露 | 工具返回敏感数据 | 脱敏 + 最小权限 |

### 安全基线

```
① 代码执行：Docker 沙箱（生产铁律）
② 危险工具：Human-in-the-loop（审批）
③ 工具白名单：Agent 只能调注册的工具
④ 终止兜底：max_turns + 成本上限
⑤ 审计日志：记录每个工具调用
```

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 模型执行工具还是框架？ | 模型决定"调什么"，框架执行并回传结果 |
| FunctionTool 怎么用？ | 包装函数 + description；自动生成 JSON schema |
| 代码执行器为什么用 Docker？ | Agent 代码不可信，沙箱隔离是安全铁律 |
| 工具报错怎么处理？ | 错误转消息回传（LLM 可读）+ 框架重试 |
| 工具设计原则？ | 一工具一职责/description 三件事/幂等 |
| 工具多了怎么办？ | 拆 Agent（工具数量别超过 10） |

### 面试加分表达

> "工具闭环是 Agent 干活的根本：LLM 只负责'决定调什么工具和参数'，框架负责执行与回传。两个工程要点：错误必须转成可读消息回传（抛异常 LLM 看不见）；生产环境代码执行必须 Docker 沙箱——Agent 生成的代码是不可信代码。"

## 8. 与 MCP 的集成

### 为什么集成 MCP

```
MCP（Model Context Protocol）：工具生态的标准协议
AutoGen 原生支持 → 一行接入海量 MCP 服务器（文件/GitHub/数据库...）
```

### 集成方式

```python
from autogen_ext.tools.mcp import mcp_server_tools
# 或 autogen_ext[mcp] 扩展

# 把 MCP 服务器的工具暴露为 Agent 工具
tools = await mcp_server_tools("npx", ["-y", "some-mcp-server"])
agent = AssistantAgent(
    name="Assistant",
    model_client=model,
    tools=tools,          # MCP 工具直接注册
)
```

### 集成价值

| 价值 | 说明 |
|---|---|
| 生态复用 | 不用自写工具，直接用 MCP 生态 |
| 标准协议 | 工具定义/调用跨框架一致 |
| 快速扩展 | 加能力 = 挂 MCP 服务器 |

> 💡 与本仓库 `MCP 协议` 体系交叉：AutoGen 是"MCP 的消费方"——把 MCP 服务器变成 Agent 的工具库。

## 9. 代码执行实战示例

```python
"""代码生成闭环：Agent 写代码 → 沙箱执行 → 看结果 → 修正"""
from autogen_ext.code_executors.docker import DockerCommandLineCodeExecutor

async def code_task():
    executor = DockerCommandLineCodeExecutor(work_dir="workspace")

    coder = AssistantAgent(
        name="Coder",
        model_client=model,
        code_executor=executor,        # 挂代码执行器
        system_message=(
            "你是编码专家：输出 Python 代码完成任务；"
            "执行失败时根据错误修正再试；完成后输出最终答案。"
        ),
    )

    team = RoundRobinGroupChat([coder], max_turns=5)
    await Console(team.run_stream(
        task="写代码计算 1 到 100 的质数之和，并运行验证结果"
    ))
    await executor.close()
```

### 执行流程观察

```text
user: 计算 1-100 质数之和
Coder: （生成代码块）def is_prime(n): ...
[沙箱执行] 输出: 1060
Coder: 验证通过，答案是 1060
[终止]（结果正确）
```

> 🎯 核心要点：工具调用 = LLM 决策 + 框架执行；FunctionTool 包装（description 必写、类型提示必写）；代码执行器让 Agent 形成"写→跑→看→改"闭环（生产必沙箱）；错误转消息 + 框架重试；工具设计遵循一工具一职责/幂等原则；MCP 集成让 Agent 复用标准工具生态；安全五条基线（沙箱/审批/白名单/兜底/审计）。
