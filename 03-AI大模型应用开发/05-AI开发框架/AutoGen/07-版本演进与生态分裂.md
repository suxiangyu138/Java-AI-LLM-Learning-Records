## 1. 版本演进时间线

| 时间 | 版本/事件 | 意义 |

## 2. v0.2 时代：爆火与心智模型

### v0.2 的成就

```
① 心智模型出圈："智能体即对话参与者"（群聊式）
② 生态繁荣：教程/案例/社区大量涌现
③ 生产验证：许多团队用它搭建了首批多 Agent 应用
```

### v0.2 的 API 特征

| 特征 | 说明 |
|---|---|
| ConversableAgent | 统一基类（助手/代理都是它） |
| initiate_chat | 同步式对话入口 |
| GroupChatManager | 群聊编排（LLM 选择发言者） |
| 阻塞式 | 同步执行，简单直观 |

### v0.2 的架构局限（v0.4 的动机）

| 局限 | 表现 |
|---|---|
| 同步阻塞 | 无法并发/流式 |
| 消息线性 | 不支持复杂通信模式（广播/订阅） |
| 可观测性弱 | 调试困难 |
| 扩展困难 | 自定义组件侵入性强 |

## 3. v0.4 重构：事件驱动三层架构

### 三层架构

| 层 | 包 | 核心抽象 |
|---|---|---|
| autogen-core | 事件驱动原语 | RoutedAgent、消息主题、订阅/发布 |
| autogen-agentchat | 高层 API | AssistantAgent、团队（Team）、run_stream |
| autogen-ext | 扩展 | OpenAI/MCP/gRPC/代码执行器 |

### 核心改进

| 改进 | 说明 |
|---|---|
| 完全异步 | 并发与流式支持（run_stream） |
| 模块化 | 内存/模型/编排可替换 |
| 错误恢复 | 检查点机制 |
| 跨语言 | Python/.NET |
| 可观测性 | 事件流可视化（Studio 配合） |

### 代价：破坏性变更

```
v0.2 → v0.4 不是升级，是重写：
- 包名变化：pyautogen → autogen-agentchat
- API 变化：ConversableAgent → AssistantAgent
- 范式变化：同步 → 异步（事件驱动）
- 迁移成本：存量代码全部重写
```

## 4. 社区分裂：AG2 分叉

### AG2 是什么

```
原核心创建者 Chi Wang 与吴清云离开微软后主导的分叉
基于 v0.2 API 延续（不走 v0.4 的破坏性重构）
主打：稳定性、兼容存量 v0.2 代码
```

### AutoGen vs AG2

| 维度 | AutoGen（官方） | AG2（分叉） |
|---|---|---|
| 基础 | v0.4（事件驱动） | v0.2 API 延续 |
| 路线 | 重构（新架构） | 稳定（兼容存量） |
| 维护者 | 微软 | 社区（核心作者） |
| 适用 | 新架构需求/微软生态 | 存量 v0.2 代码/稳定性优先 |

### 社区分裂的影响

```
① 用户困惑：升级还是分叉？
② 生态稀释：教程/插件双轨发展
③ 信任裂痕：破坏性重构的教训
④ 微软转向：分裂加速了 MAF 战略（整合止血）
```

## 5. 分裂的深层原因

### 结构性矛盾

| 矛盾 | 说明 |
|---|---|
| 重构 vs 兼容 | 技术演进需要重写，存量用户要兼容 |
| 开源 vs 公司战略 | 社区要自主，微软要统一平台 |
| 作者 vs 公司 | 核心作者理念与公司路线分歧（离职） |

### v0.2 与 v0.4 代码对照（迁移者必看）

| 场景 | v0.2 写法 | v0.4 写法 |
|---|---|---|
| 创建助手 | ConversableAgent(name, llm_config=...) | AssistantAgent(name, model_client=...) |
| 发起对话 | agent.initiate_chat(other, message=...) | team.run_stream(task=...) |
| 群聊 | GroupChat + GroupChatManager | RoundRobinGroupChat/SelectorGroupChat |
| 工具 | register_function | FunctionTool 列表 |
| 同步/异步 | 同步 | 异步（await） |

```
对照结论：v0.4 是"思想延续 + 工程重写"——
概念还在（Agent/群聊/工具），API 与范式全变
这也是为什么存量 v0.2 用户更愿意去 AG2 而非升级
```

### 行业教训（面试深度题）

```
"第一次 AI 框架 Succession"的启示：
① 破坏性重构要谨慎——v0.4 伤了社区信任
② 框架命运与公司战略绑定——合并/退休是常态
③ 分叉是开源社区的自我修复——AG2 保住存量
④ 学框架要学思想——思想可迁移，代码会过时
```

## 6. 2026 选型建议

### 三个选项

| 场景 | 选择 |
|---|---|
| 新项目（微软生态/Azure） | **MAF**（官方推荐，08 篇） |
| 存量 v0.2 代码维护 | **AG2**（API 兼容延续） |
| 新项目（非微软生态） | LangGraph / OpenAI Agents SDK 等 |
| 学习对话编排思想 | 本体系（AutoGen 档案） |

### 选型决策树

```
新项目？
├─ 微软/Azure 技术栈 → MAF
├─ 需要图式可控编排 → LangGraph
├─ 需要 OpenAI 生态 → OpenAI Agents SDK
└─ 存量 v0.2 代码 → AG2（维护）
```

### 务实提醒

```
框架选型的三个维度（2026）：
① 活跃度：维护/社区/路线（MAF/LangGraph 活跃）
② 兼容性：存量代码与迁移成本
③ 思想迁移：选择框架 = 选择编排思想
```

## 8. 存量代码维护指南

### 三种存量的处理

| 存量 | 建议 |
|---|---|
| v0.2 代码在跑 | AG2 延续（API 兼容）或计划迁移 |
| v0.4 代码在跑 | 可继续（维护模式仍有 bug 修复）；评估 MAF 时机 |
| 纯学习代码 | 直接按 08 篇学 MAF |

### 维护期注意事项

```
① 锁定版本：维护模式不新增功能，锁版本防漂移
② 安全补丁：关注安全更新（维护模式仍发布补丁）
③ 依赖收敛：减少外围依赖（生态增长放缓）
④ 文档留存：保存配置与运行手册（社区教程会逐渐过时）
⑤ 迁移窗口：规划"什么时候必须迁"（业务新需求触发）
```

### 迁移触发信号

```
遇到以下需求 → 是迁移时机：
✓ 需要检查点/恢复（MAF 一等公民）
✓ 需要企业集成（Azure/365/数据源）
✓ 需要负责任 AI（守卫/PII）
✓ 项目大重构（反正要改）
✓ 团队要新框架技能
```

> 🎯 核心要点：AutoGen 分裂 = v0.4 重构（技术）+ 作者出走（人事）+ 公司战略（MAF）三重因素；v0.4 三层架构（事件驱动/异步/模块化）是技术遗产；AG2 保住 v0.2 存量生态；选型按"存量 AG2 / 新项目 MAF 或 LangGraph"；存量维护五件事（锁版本/安全补丁/依赖收敛/文档留存/规划迁移窗口）；行业教训——学思想不学代码，框架命运与公司战略绑定。
