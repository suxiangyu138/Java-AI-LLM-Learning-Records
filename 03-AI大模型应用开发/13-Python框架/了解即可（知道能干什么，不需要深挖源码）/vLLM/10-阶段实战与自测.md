## 1. 实战项目：部署 LLM API 服务

**实战项目 = 把本体系九课串成"亲手部署"的完整流程**：

```text
实战项目三步（从启动到生产）
├── 第一步：启动服务（02/04 篇）
│    vllm serve 启动一个量化小模型（AWQ——7B 或更小）
│    验证：/v1/models + OpenAI SDK 对话
├── 第二步：接入验证（05/07 篇）
│    OpenAI SDK 完整调用（对话 + 流式）
│    压测找拐点（吞吐/延迟数字）
└── 第三步：生产部署（06 篇）
    Docker/systemd 管进程 + /health 验证
    部署文档（模型/量化/参数/压测数据）
```

```bash
# 实战核心命令（生产姿势汇总）
# ① 启动（量化模型——生产标配）
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ \
  --quantization awq \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.9 \
  --host 0.0.0.0

# ② 验证
curl http://localhost:8000/v1/models          # 模型列表（服务活了）
# OpenAI SDK 对话 + 流式（05 篇）

# ③ 生产（Docker 管进程——06 篇）
docker run --gpus all -p 8000:8000 vllm/vllm-openai:latest \
  vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --host 0.0.0.0
```

**实战心智**：**"实战的验收标准：'三问'——服务能答吗（SDK 调用）、并发能扛吗（压测数字）、挂了能起吗（进程管理）"**——"**验收三看：对话跑通（API 可用）、压测有数字（性能可知）、kill 后自动重启（生产姿势）——'三个验收 = LLM 服务的三件套证明'"**（"了解即可的实战观：跑通流程 + 记录数字——不深挖 CUDA 内核——**'你验证的是'怎么部署'，不是'内核怎么写的'"**）；**实战的环境**——"NVIDIA GPU 8GB 起步（量化小模型）——**'没 GPU：本地上手用 Ollama（08 篇）——vLLM 的舞台是 GPU'"**（"模型的选择：小模型起步（1.5B/7B——下载快显存低）——**'先小模型跑通流程，再上大模型（与 bitsandbytes/trl 同款）'"**）；**实战的常见卡点**——"显存不足（09 篇速查第一坑——减长度/量化）、模型加载失败（指定 quantization）、启动慢（正常等待）——**'卡住先查速查表——别卡在同一个坑两次'"**；**实战的进阶方向**——"**① 大模型**（7B → 70B——TP 多卡——04 篇）；**② 场景优化**（RAG 用前缀缓存——03 篇）；**③ 监控接入**（Prometheus 指标——06 篇）；**④ 多实例**（负载均衡——水平扩展——06 篇）——**'部署跑通后的四步进阶 = 从'能跑'到'生产级'"**；**实战的完整闭环**——"部署 → 压测（数字）→ 监控（健康）→ 文档（交接）——**'闭环四步 = 模型服务的完整交付'"**。

## 3. 报错速查

**高频报错速查（09 篇完整版的精要——十选六）**：

| 报错/现象 | 原因 | 解法 |
|---------|------|------|
| `CUDA out of memory` | 显存不足 | 量化 → 减长度 → 减 gpu-memory |
| 模型加载失败 | 格式不匹配 | 指定 --quantization |
| `model not found`（404） | 模型名错 | /v1/models 查实际名 |
| V0 标志报错 | v0.25.0 移除 legacy | 删 V0 参数 |
| 输出截断 | max-model-len 太短 | 加长 |
| 速度慢 | 没量化 | 用量化模型（AWQ） |

**速查心智**：**"六条的规律：'显存两条 + 模型两条 + 版本/性能各一条'"**——"**背下六条的'原因列'——报错时先对原因再对解法——'排障的本质是原因归类'"**（"新坑必记（09 篇纪律延续）——**'速查表是你的，不是我的——我的十条是起点，你的实战坑要补充'"**）。

## 4. 面试演练

**面试问答（LLM 推理部署相关——本体系特有）**：

**Q1：怎么把开源大模型部署成 API 服务？**——答：**"三步：① 模型准备——生产用量化（AWQ 4bit——省 3/4 显存 + Marlin 内核提速 61%）；② 启动服务——vllm serve 模型名（一条命令出 OpenAI 兼容 API——加载+引擎+API 三合一）；③ 生产部署——Docker 管进程 + /health 健康检查 + 压测定并发上限（安全并发 = 拐点 × 0.8）——接入方只改 base_url 一行（OpenAI SDK 直接用）——我实际部署过 7B AWQ 模型：8GB 卡跑通、OpenAI SDK 对话 + 流式正常"**——结构：**三步 → 数字 → 接入 → 实战验证**——"答出'量化 + OpenAI 兼容 + 压测'是生产经验的证明"。

**Q2：vLLM 为什么比 Transformers 快？**——答：**"两个核心技术：① PagedAttention——KV 缓存分页管理（像操作系统虚拟内存）——显存碎片从 60-80% 降到 4% 以下——同样显存装 4-5 倍请求；② 连续批处理——请求动态进出（不等整批）——GPU 利用率 85-92%——两者合起来吞吐比 Transformers 高 24 倍——再加前缀缓存（RAG 场景公共前缀拼车——翻倍）"**——结构：**两个核心 → 数字 → 场景补充**——"答出'碎片数字 + 利用率数字'显示理解深度"。

**Q3：选型：Ollama 还是 vLLM？**——答：**"场景决定：本地开发/快速原型用 Ollama（一条命令上手——但无连续批处理——50 并发就掉到 155 tok/s——不适合生产）；生产 GPU 服务用 vLLM（吞吐 5100 tok/s batch=256——连续批处理 + PagedAttention——生产事实标准）——TGI 已进入维护模式（2025-12 官方宣布）——新项目迁移 vLLM/SGLang——无 GPU/边缘用 llama.cpp（GGUF——全平台）——我自己的规则：体验用 Ollama、上线用 vLLM"**——结构：**对比 → 数字 → 生态状态 → 个人规则**——"答出'TGI 维护模式'是 2026 年的新认知"。
