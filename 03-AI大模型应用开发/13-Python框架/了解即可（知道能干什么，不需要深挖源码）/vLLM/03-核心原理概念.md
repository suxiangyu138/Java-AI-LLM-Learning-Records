## 1. KV 缓存问题

**LLM 推理的显存大头 = KV 缓存（不是模型权重）**：

```text
KV 缓存问题
├── 什么是 KV 缓存：生成每个 token 时保存的"注意力中间结果"
│    —— 生成第 100 个 token 要用前 99 个的信息——缓存避免重复计算
├── 显存占用：KV 缓存随"并发 × 上下文长度"线性增长
│    —— 长上下文 + 多并发 = 显存大头（常常超过模型权重）
└── 传统实现的问题：预分配固定显存（按最大长度预留）——
    "10 个请求各留 4K 长度 → 实际只用 1K → 显存碎片浪费 60-80%"
    ——"KV 缓存是推理的'内存黑洞'——谁管好它，谁吞吐高"
```

**KV 心智**：**"KV 缓存的记忆：'生成 token 的便签本——占显存的大头'"**——"**为什么是瓶颈：模型权重是固定的（一次加载）、KV 缓存是动态的（随请求涨）——'并发上来 → KV 缓存爆炸 → 显存不够 → 吞吐受限'"**（"长上下文（8K/32K）的代价：KV 缓存线性涨——**'max-model-len 的权衡（02 篇）的底层原因'"**）；**KV 缓存的优化思路**——"① 分页管理（PagedAttention——本课 2 节）；② 量化（KV 缓存量化——省一半）；③ 卸载（CPU/SSD——v0.23.0 多级卸载）——**'三个优化 = vLLM 的显存管理三件套'"**（"了解即可：知道'KV 是显存大头 + vLLM 在管它'——细节是论文的事"）。

## 2. PagedAttention：显存分页

**PagedAttention = 把 KV 缓存按"页"管理（借鉴操作系统虚拟内存）**：

```text
PagedAttention 一句话原理
├── 传统：每个请求预分配连续显存（按最大长度——浪费）
├── vLLM：KV 缓存切成固定大小的"页"（块——如 16 token/页）
│    —— 逻辑页表 → 物理显存（不连续也行——像操作系统的虚拟内存）
└── 效果：碎片从 60-80% → 4% 以下——同样显存装更多请求
    ——"一句话：KV 缓存的'分页管理'——要多少页给多少页，不预分配"
```

**PagedAttention 心智**：**"PagedAttention 的记忆：'KV 缓存的虚拟内存'——像操作系统管内存一样管显存"**——"**为什么效果惊人：传统按'最坏情况'预留（每请求 4K 长度）——实际平均只用 1K——浪费 60-80%；分页后'按需分配'（用到多少页给多少页）——碎片降到 4% 以下——'同样显存 = 4-5 倍的请求容量'"**（"这是 vLLM 吞吐革命的技术根基（01 篇 24× 的底层）——**'知道'分页'两个字 + 效果数字就够'"**）；**2026 的演进**——"v0.7.3 动态分页（4/8/16-token 多尺寸页——适配不同场景）+ v0.25.0 删除 legacy 实现（概念并入新后端 MRv2）——**'概念不变，实现演进——PagedAttention 的精神还在（01 篇版本演进）'"**（"了解即可：知道'分页管理'是 vLLM 的灵魂——**'具体页大小/调度是版本细节'"**）。

## 3. 连续批处理：请求动态进出

**连续批处理（Continuous Batching）= 请求随时进、随时出（不等整批）**：

```text
连续批处理
├── 传统批处理（静态）：攒一批请求 → 一起处理 → 一起结束
│    —— 慢请求拖累整批（一个没完全批等）——批间空闲
├── vLLM 连续批处理：每个请求"独立推进"
│    —— 新请求随时插入（有空位就进）
│    —— 完成的请求随时退出（不等别人）
│    —— 每个 token 生成都是"动态调度"
└── 效果：GPU 永远在干活（利用率 85-92%）——吞吐翻倍级提升
    ——"传统是'整列火车一起走'，连续批处理是'每节车厢独立跑'"
```

**批处理心智**：**"连续批处理的记忆：'动态调度——GPU 不闲着'"**——"**为什么吞吐高：传统批处理的'批间空闲'（一批结束下一批开始之间的空档）没了——新请求随时补位——'GPU 利用率 85-92%（对比 TGI 的 68-74%——08 篇）的机制来源'"**（"连续批处理 + PagedAttention 是 vLLM 的两大支柱——**'一个是调度（时间维度）、一个是内存（空间维度）——合起来 = 吞吐革命'"**）；**批处理的代价**——"单请求延迟略升（为了整体吞吐）——**'吞吐与延迟的权衡（07 篇）——服务型场景吞吐优先'"**（"延迟敏感场景（单用户交互）vLLM 不是最优（08 篇选型）——**'知道权衡 = 知道何时用'"**）。

## 4. 前缀缓存与其他优化

**前缀缓存（Prefix Caching）= 相同开头的请求共享计算（RAG/系统提示词场景）**：

```text
前缀缓存
├── 场景：多个请求有相同前缀（系统提示词/RAG 的检索文档）
├── 原理：前缀的 KV 缓存被缓存——相同前缀直接复用（不重算）
└── 效果：RAG/Agent 场景吞吐大幅提升（公共前缀 = 白赚）
    ——"前缀缓存 = 相同开头的请求'拼车'——前面那段路一起走"

其他优化（知道存在即可）
├── 投机解码（Speculative Decoding）：小模型猜、大模型验——加速单请求
├── KV 缓存量化：KV 缓存省一半显存
└── 多级卸载（v0.23.0）：KV 缓存溢出到 CPU/SSD——长上下文省钱
    ——"vLLM 的优化全家桶：分页 + 连续批处理 + 前缀缓存是三大支柱"
```

**前缀缓存心智**：**"前缀缓存的记忆：'公共前缀拼车——RAG/Agent 的提速器'"**——"**为什么场景重要：RAG（检索增强）请求带长文档前缀、Agent 带系统提示词——前缀重复率高——'前缀缓存让这些场景吞吐翻倍'"**（"了解即可：知道'前缀缓存适合什么场景'——**'RAG/Agent 服务用 vLLM 的理由之一'"**）；**优化全家桶的认知**——"三大支柱（分页/连续批处理/前缀缓存）+ 辅助优化（投机解码/量化/卸载）——**'知道三支柱 + 辅助优化存在——细节按需查'"**（"优化的选择：场景决定用哪个（RAG 用前缀缓存、长上下文用卸载）——**'优化的选型 = 场景的匹配（07 篇）'"**）。
