## 1. 性能指标：吞吐 vs 延迟

**LLM 服务的两个性能维度——先分清再优化**：

```text
吞吐 vs 延迟
├── 吞吐（Throughput）：每秒生成多少 token（tok/s）
│    —— 服务多人场景（并发）的核心指标——"单位时间能干多少活"
├── 延迟（Latency）：单请求多快返回
│    —— 首 token 延迟（TTFT——用户等第一个字多久）
│    —— 生成延迟（每个 token 的速度）
└── 权衡：吞吐优先 → 延迟略升（连续批处理——03 篇）；延迟优先 → 吞吐降
    ——"服务型场景吞吐优先（vLLM 的设计取向）；交互型场景延迟敏感"
```

**指标心智**：**"指标的记忆：'吞吐 = 干多少活、延迟 = 等多久'"**——"**两个指标的读法：吞吐看'并发能力'（服务多少人）、延迟看'体验'（用户等多久）——'服务型产品（API/批量）吞吐优先；聊天产品（交互）延迟重要'"**（"vLLM 的设计取向：吞吐优先（连续批处理——03 篇）——**'要极低延迟选别的引擎（08 篇选型）'"**）；**指标的数字**——"参考（2026 实测）：Llama-3-70B 单卡 H100——batch=1 约 58 tok/s、batch=256 约 5100 tok/s——**'并发上来吞吐暴涨（连续批处理的威力——03 篇）'"**（"自己的服务要实测（压测——本课 4 节）——**'别人的数字是参考，自己的数字是答案'"**）。

## 2. 量化内核：Marlin

**Marlin 内核 = 量化模型推理的加速内核（AWQ/GPTQ 的速度来源）**：

```text
Marlin 内核
├── 本质：专为量化模型（4bit）优化的 GPU 内核（比通用内核快）
├── 效果（2026 实测——H100 + Llama-3.1-8B）：
│    Marlin-AWQ：741 tok/s（比 FP16 基线 +61%）
│    Marlin-GPTQ：712 tok/s（+54%）
│    FP16 基线：461 tok/s
├── 前提：模型用 AWQ/GPTQ 量化（04 篇）——vLLM 自动用 Marlin
└── 结论：量化 + Marlin = 显存省 + 吞吐涨（双赢）
    ——"Marlin 让'量化'从'省显存'变'省显存 + 提速'——量化的性价比之王"
```

**内核心智**：**"Marlin 的记忆：'量化模型的速度引擎——+61% 吞吐'"**——"**为什么量化反而快：4bit 数据量小（内存带宽瓶颈——数据搬得快）+ Marlin 内核优化（计算高效）——'量化 = 省显存 + 提速（打破'省了就要慢'的直觉）'"**（"与 bitsandbytes 的对比：bitsandbytes 运行时量化推理慢（无专用内核——bitsandbytes 07 篇）——**'vLLM 吃预量化文件（AWQ/GPTQ）→ Marlin 加速——推理侧的量化选型（bitsandbytes 09 篇）'"**）；**内核的自动性**——"vLLM 对 AWQ/GPTQ 自动用 Marlin（不用配置）——**'量化格式选对 = 内核自动加速（04 篇）'"**（"FP8 的新趋势：新卡（H100/Blackwell）原生支持——**'FP8 是 2026 新卡的选择（04 篇）'"**）。

## 3. 调优清单

**性能调优清单（按收益排序——从大到小）**：

```text
调优清单（ROI 排序）
├── ① 量化（AWQ/FP8）：省 3/4 显存 + Marlin 提速（04 篇——最大收益）
├── ② 连续批处理（引擎自带）：并发吞吐（03 篇——vLLM 的天赋）
├── ③ 前缀缓存：RAG/Agent 场景（公共前缀拼车——03 篇）
├── ④ max-model-len 权衡：显存 ↔ 长度（02 篇——显存不够先减）
├── ⑤ gpu-memory-utilization：0.9 甜点（02 篇）
├── ⑥ TP 多卡：大模型装下（04 篇）
└── ⑦ 投机解码：单请求加速（03 篇——可选）
    ——"调优的顺序：先量化（最大）、再场景（前缀缓存）、后配置（长度/显存）"
```

**调优心智**：**"调优的记忆：'量化最大、场景次之、配置兜底'"**——"**vLLM 本身已优化到天花板（PagedAttention + 连续批处理——03 篇）——你的调优是'逼近天花板'：量化（最大头）+ 场景配置（前缀缓存）+ 显存权衡（长度）——'调优不是改引擎，是配好场景'"**（"90% 的调优收益来自量化 + 场景匹配——**'先量化再谈其他（04 篇的深化）'"**）；**调优的验证**——"每次调优前后压测对比（记录数字）——**'调优报告 = 参数 + 数字（与 uvicorn/bitsandbytes 同款纪律）'"**（"调优的边界：单机有极限 → 水平扩展（多实例 + 负载均衡——06 篇架构）——**'先调优后扩展'"**）。

## 4. 压测方法论

**压测 = 知道自己的服务"能扛多少"（性能的尺子）**：

```text
压测四步（与 uvicorn 06 篇同款）
├── ① 基线：低并发（1/5）跑——记录吞吐/延迟（基线）
├── ② 爬坡：并发逐级加（10/50/100）——找拐点（延迟陡增处）
├── ③ 判拐点：延迟 P99 超标/吞吐不再涨 = 到了上限
└── ④ 定档：安全并发 = 拐点 × 0.8（留余量）
    ——"压测的目的：知道'能扛多少'——定生产并发上限"
```

```python
# 压测工具（了解即可——OpenAI 兼容压测）
# ① openai-python 写脚本（并发请求——简单）
# ② vLLM 生态压测工具（benchmark_serving.py——官方脚本）
# ③ 通用压测（locust/wrk——uvicorn 06 篇方法论）
# 核心指标：吞吐（tok/s）+ 延迟（TTFT/P99）
```

**压测心智**：**"压测的记忆：'爬坡找拐点——安全并发 = 拐点 × 0.8'"**——"**压测的价值：生产前的'体检'（并发上限/延迟分布）——'不压测的部署 = 上线赌运气（拐点可能在用户手里）'"**（"压测的注意：压测也是请求（别压爆自己的服务——留余量——和爬虫压测的'礼貌'同款——爬虫 06 篇）——**'压测是试探不是攻击'"**）；**压测的产物**——"压测报告（并发/吞吐/延迟表格 + 安全线）——**'压测报告 = 生产配置的依据（限流/扩容决策）'"**（"压测与监控的联动：压测的安全线 → 监控的告警阈值（06 篇架构）——**'压测数据是监控的基线'"**）；**压测的常见误区**——"① 只测单并发（看不到连续批处理的威力——要爬坡）；② 压测数据当生产承诺（环境不同——要留余量）；③ 不测流式（流式是主要调用方式——要单独测）——**'三个误区 = 压测的常见坑（了解即可：知道'要爬坡 + 留余量 + 测流式'）'"**（"压测的重复：模型/配置变了要重测（07 篇的持续验证）——**'压测不是一次性的，是配置变更的配套'"**）。
