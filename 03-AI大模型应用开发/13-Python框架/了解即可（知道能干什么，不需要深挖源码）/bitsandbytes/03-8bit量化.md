## 1. 8bit 量化的定位

**8bit（INT8）= 每个权重用 8 位存——显存省一半**：

```text
8bit 的定位
├── 历史：bitsandbytes 的第一个爆款功能（2022 年 LLM.int8() 论文）
├── 效果：FP16（2 字节）→ INT8（1 字节）——加载显存省一半
├── 精度：比 4bit 损失更小（8bit 档位多——256 档）
└── 现状：4bit 出现后 8bit 变成"过渡选择"——但仍有其场景
    ——"8bit 是量化的'第一站'——4bit 的'大哥'（位数多精度好）"
```

**定位心智**：**"8bit 的记忆锚点：'省一半'"**——"7B 模型 FP16 14GB → 8bit 7GB——**'8GB 显卡的 7B 模型刚好装下'"**（账本公式 02 篇的实例）；**8bit 与 4bit 的关系**——"4bit 是 8bit 的升级（省 3/4 vs 省 1/2）——**'能上 4bit 就上 4bit——8bit 是'4bit 不够精确或版本不支持'时的选择'"**（"实际使用 2026 年 8bit 出场率下降——但知道它存在、知道它省一半，是完整认知"）；**8bit 的隐藏价值**——"8bit 的精度损失比 4bit 更小（09 篇 PPL 对比）——**'显存差一点点就够（差一半以内）——8bit 是'最不伤精度'的省显存方案'"**（"精度敏感任务：先试 8bit（损失小），不够再 4bit"）。

## 2. LLM.int8()：一句话原理

**LLM.int8() = 8bit 量化的实现方案——知道一句话原理即可**：

```text
LLM.int8() 一句话原理
├── 普通权重：直接量化到 8bit（256 个档位）
├── 关键例外：少数"异常值"（outlier——激活特别大的维度）保持高精度
│    —— 论文发现：大模型的激活有少数极端值——量化它们损失巨大
├── 处理：异常值维度用 16bit 计算，正常维度 8bit——混合精度
└── 效果：精度接近全精度（"无害量化"）——同时省一半显存
    ——"一句话：'大部分 8bit + 少数 16bit'——专治大模型激活的异常值"
```

**原理心智**：**"了解即可的原理观：知道'为什么 8bit 精度不崩'就够"**——"8bit 只有 256 档——按理说损失不小——但 LLM.int8() 把'异常值'拎出来用 16bit 算——**'异常值少但关键——保护它们 = 保住精度'"**（"原理的价值：解释'为什么 8bit 不崩'——面试/理解都够用，不用读论文"）；**原理的边界**——"异常值保护是 LLM.int8() 的设计——其他 8bit 方案（如 GPTQ 的 8bit）机制不同——**'方案不同，原理不同——知道名字别混'"**（"了解即可：LLM.int8() 是 bitsandbytes 的 8bit——记住这一个就够"）；**为什么 4bit 更流行**——"4bit 用 NF4 码本（按分布分档）解决了'档位少精度差'的问题——**'NF4 是 LLM.int8() 异常值保护思路的'分布版'——更省 + 更聪明'"**（04 篇衔接）。

## 3. 怎么用：一行加载

**8bit 加载 = 一行代码（通过 Transformers——不直接碰 bitsandbytes API）**：

```python
# 方式一：旧式参数（bitsandbytes < 0.43.0 可用——老教程常见）
from transformers import AutoModelForCausalLM

# model = AutoModelForCausalLM.from_pretrained(
#     "Qwen/Qwen2.5-7B", load_in_8bit=True, device_map="auto")

# 方式二：新式配置（≥0.43.0 唯一入口——2026 标准姿势）
from transformers import BitsAndBytesConfig, AutoModelForCausalLM

config = BitsAndBytesConfig(
    load_in_8bit=True,                    # 开启 8bit
)
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B",
    quantization_config=config,           # 新 API：quantization_config
    device_map="auto",
)
print(model.get_memory_footprint() / 1024**3)   # 打印加载后的显存占用（约 7GB）
```

**使用心智**：**"使用的记忆点：`BitsAndBytesConfig`（新 API）+ `quantization_config` 参数——≥0.43.0 后旧参数报错"**——**"版本姿势：2026 年一律用 BitsAndBytesConfig——老教程的 `load_in_8bit=True` 参数写法在新版直接报错（01 篇版本纪律）"**（08 篇排障第一条的源头）；**device_map="auto"**——"让 Transformers 自动分配设备（GPU 放得下就全 GPU）——**'加载量化模型的标准配菜'"**（"4bit 的坑：device_map='auto' 可能静默拆到 CPU（07/08 篇）——8bit 相对安全"）；**验证加载效果**——"`model.get_memory_footprint()` 打印实际显存——**'加载完打印显存 = 量化有没有生效的唯一证据'"**（"显存对不上预期 = 配置没生效（常见：忘了传 quantization_config）"）。

**8bit 加载的预期数字**（验证时的对照表）："7B 模型：FP16 约 14GB → 8bit 约 7GB（账本公式 02 篇）；1.5B 模型：FP16 约 3GB → 8bit 约 1.5GB——**'加载后显存 ≈ 账本的一半，配置就对了'**——如果显存接近 FP16 数值（没省）——查三件事：**① quantization_config 传了吗（最常忘）；② 版本够新吗（老版本静默失效）；③ 模型本身小吗（小模型省得绝对值小——看比例不看绝对值）**"（"验证的对照：'预期数字 vs 实际数字'——对不上就走排查（08 篇）——**'显存数字是量化的'验收单'"**）。

## 4. 什么时候用 8bit

**8bit 的适用场景——四个判断**：

```text
什么时候用 8bit
├── ① 显存差一半以内：4bit 用不上（4bit 显存也超？不——4bit 更省）
│    —— 更正：8bit 的场景是"精度敏感 + 省一半够用"
├── ② 精度敏感任务：8bit 损失比 4bit 小——能 8bit 就不 4bit
├── ③ 老版本环境：bitsandbytes 版本老（<0.39）只支持 8bit
└── ④ 不想上 QLoRA：纯推理 + 精度优先——8bit 是"最不伤精度"的省显存
    ——"核心判断：'省一半够不够' + '精度多重要'——两个都满足 → 8bit"
```

**选型心智**：**"8bit vs 4bit 的选型一句话：'精度优先选 8bit，显存优先选 4bit'"**——"**推理演示（要快要不崩）→ 4bit；精度敏感分析（代码/数学任务）→ 8bit 或全精度"**（09 篇实测：任务越难量化损失越大——"复杂任务 8bit 比 4bit 稳"）；**8bit vs 不量化**——"显存够 → 不量化（全精度最优）；差一半 → 8bit；差更多 → 4bit——**'量化的档位跟着'缺口'走——省到刚好够用为止'"**（"量化不是越狠越好——够用是标准"）；**8bit 的未来**——"2026 年 8bit 出场率下降（4bit NF4 太强）——但**认知价值不降：理解 8bit = 理解'量化的精度阶梯'**（"从 8bit 学起，理解 4bit 更容易"）。

**8bit 的实战判断流**（一个决策示例）："8GB 显卡 + 7B 模型——**① 算账**：7B FP16 14GB（装不下）、8bit 7GB（刚好——但运行要缓存余量）、4bit 3.5GB（舒适）；**② 定需求**：任务是中文聊天（精度要求中等）——4bit 即可；任务是代码生成（精度敏感）——8bit 或换小模型；**③ 决策**：聊天 → 4bit（最省心）；代码 → 8bit + 关长上下文（省缓存）；**④ 验证**：加载后 `get_memory_footprint` + 跑一句测试——"**四步判断流（算账→定需求→决策→验证）是量化选型的标准动作——8bit 在'精度敏感且省一半够用'时出场"**。
