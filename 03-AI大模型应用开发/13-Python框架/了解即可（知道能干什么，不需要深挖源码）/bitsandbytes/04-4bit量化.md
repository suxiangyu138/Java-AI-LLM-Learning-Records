## 1. 4bit 的定位

**4bit = 每个权重 4 位——显存省 3/4——2026 年 bitsandbytes 的绝对主角**：

```text
4bit 的定位
├── 效果：FP16（2 字节）→ 4bit（0.5 字节）——显存省 3/4
├── 实战：7B 模型 14GB → 3.5GB（8GB 显卡轻松跑）
│        13B 模型 26GB → 6.5GB（12GB 显卡装下）
│        70B 模型 140GB → 35GB（80GB 显卡装下——"单卡 70B 甜点"）
├── 地位：QLoRA 微调的地基（05 篇）——唯一能训练的 4bit
└── 现状：90% 的 bitsandbytes 使用场景是 4bit
    ——"4bit = 量化的'性价比之王'——省最多 + 损失可接受"
```

**定位心智**：**"4bit 的记忆锚点：'省 3/4 + 能吃下 4 倍大的模型'"**——"**同样的显卡，4bit 能跑的模型是 FP16 的 4 倍大——'显存不够？4bit 翻 4 倍'**"（账本公式 02 篇的 4bit 版——"12GB 显卡：FP16 只能 5B 以下，4bit 能 13B"）；**4bit 为什么能"烂大街"**——"8bit 省一半（256 档）——4bit 只有 16 档——按理说精度崩——但 **NF4 码本（按分布分档）让 16 档用出了"聪明"**——精度损失仅 1.7%（09 篇实测）——**'NF4 是 4bit 能流行的技术原因'"**（03 篇末尾的衔接——"8bit 靠异常值保护，4bit 靠分布分档"）；**4bit 的两种格式**——"NF4（NormalFloat——正态分布分档——QLoRA 标配）与 FP4（均匀浮点）——**'首选 NF4——FP4 是备选（特定场景）'"**（"配置里 `bnb_4bit_quant_type="nf4"` 就是它"）。

## 2. NF4：聪明分档的码本

**NF4（NormalFloat4）= 按权重分布设计档位的 4bit 码本**：

```text
NF4 一句话原理
├── 普通 INT4：16 个档位均匀分布（-1, -0.87, -0.73...）
├── 权重的现实：大模型权重的值集中在 0 附近（正态分布！）
├── NF4 的设计：档位按正态分布的分位数放（0 附近密、两边疏）
│    —— 权重最常出现的区域（0 附近）有最精细的档位
└── 效果：同样的 16 档，NF4 的"有效精度"比 INT4 高得多
    ——"一句话：档位放在'权重多的地方'——把精度花在刀刃上"
```

**NF4 心智**：**"NF4 的直觉：'把 16 个档位放在最常用到的地方'——像地图上把标注放在城市密集区"**——**"为什么比 FP4/INT4 准：权重正态分布 → 0 附近档位密 → 常见值的误差小"**（09 篇实测 NF4 精度损失 1.7%——"16 档用出了接近 8bit 的精度——**'NF4 = 4bit 的身材、接近 8bit 的精度'"**）；**NF4 的实现细节（了解即可）**——"码本按标准正态分布的分位数构造——加载时把权重映射到最近档位、计算时反量化回 bf16——**'知道'按分布分档'四个字就够——实现细节是库作者的事'"**；**双重量化（double quant）**——"量化过程中的'缩放因子'也量化一次（再省一点）——**'配置里 bnb_4bit_use_double_quant=True——默认开——白赚的省显存'"**（06 篇配置四件套之一）。

## 3. 怎么用：配置四件套

**4bit 加载 = BitsAndBytesConfig 四件套（2026 标准姿势）**：

```python
from transformers import BitsAndBytesConfig, AutoModelForCausalLM
import torch

# 配置四件套（QLoRA 官方推荐——HuggingFace 对齐手册标配）
config = BitsAndBytesConfig(
    load_in_4bit=True,                      # ① 开启 4bit
    bnb_4bit_quant_type="nf4",              # ② 量化类型：NF4（默认也是 nf4）
    bnb_4bit_compute_dtype=torch.bfloat16,  # ③ 计算精度：bf16（反量化后运算用）
    bnb_4bit_use_double_quant=True,         # ④ 双重量化（缩放因子也量化——默认开）
)

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B",
    quantization_config=config,
    device_map="auto",
)
print(f"4bit 显存: {model.get_memory_footprint() / 1024**3:.1f} GB")   # 约 3.5GB
```

**配置心智**：**"四件套的记忆：'开 4bit + NF4 + bf16 + 双重量化'"**——**"为什么四件套缺一不可：① 开关（不开不量化）；② 格式（NF4 精度最优）；③ 计算精度（bf16 抗 NaN——float16 会 NaN 崩溃——07/08 篇）；④ 双重量化（白赚的省显存）"**（"四件套是'抄作业'级别的标准配置——**'QLoRA 微调不写四件套 = 不是标准姿势'"**）；**计算精度 bf16 vs float16**——"反量化后要算（前向传播）——**bf16 指数范围大（不会 NaN）——float16 在训练场景会 NaN 损失（官方文档警告）——一律 bf16"**（"推理场景 float16 凑合——训练/QLoRA 必须 bf16——**'配置抄标准答案，别自己发明'"**）；**验证**——"打印显存（3.5GB 左右）+ 推理一句测试——**'四件套配置 + 显存验证 = 4bit 加载的完整闭环'"**。

**4bit 的配置变体**（四件套之外的按需调节）："**① 8bit 与 4bit 二选一**——`load_in_8bit=True` 与 `load_in_4bit=True` 互斥（只开一个——两个都开报错）；**② 存储格式 `bnb_4bit_quant_storage`**——默认按计算精度存，FSDP 多卡训练要 `torch.uint8`（08 篇）；**③ 双重量化开关**——默认 True（白赚省显存），极端场景（要极致精度）可关——**'四件套是默认，变体是按需——80% 场景四件套原样抄'"**（06 篇 Config 六参数的完整版——"本课记住四件套，06 篇给全参数表"）。

## 4. 4bit 的边界

**4bit 的边界——什么情况不适合**：

```text
4bit 边界（三不适合）
├── ① 高精度任务：代码生成/数学推理——量化损失放大（09 篇 HumanEval -7.7%）
│    —— 任务越难，4bit 损失越明显——复杂任务用 8bit/全精度
├── ② 高吞吐服务：bitsandbytes 推理速度慢（无专用内核）
│    —— 生产高并发用 GPTQ/AWQ（Marlin 内核——09 篇）
└── ③ 需要推理引擎兼容：vLLM/Ollama 不直接吃 bitsandbytes 的运行时量化
    —— 部署栈用 vLLM → 预量化格式（GPTQ/AWQ/GGUF）
    ——"4bit 的边界 = 部署栈与任务难度的边界——选型见 09 篇"
```

**边界心智**：**"4bit 的主场与客场：'学习/原型/QLoRA 微调'是主场；'生产高吞吐/高精度任务'是客场"**——**"为什么有边界：bitsandbytes 是'运行时量化'（加载时动态做——权重文件不变）——专为 Transformers/PEFT 生态设计——'出了这个生态，性能就吃亏'"**（"部署栈是 vLLM → 换 GPTQ（预量化格式——Marlin 内核快 61%）——**'工具链决定量化方案，不是量化方案决定工具链'"**）；**边界的心智意义**——"知道边界 = 知道'什么时候别用'——**'选型的能力 = 知道每个方案的'主场'在哪——4bit 的主场：微调与学习'"**（09 篇决策树的预告——"本课记边界，下课给地图"）。

**4bit 与其他格式的快速对照**（边界问题的即时答案）："**① bnb 4bit vs GPTQ/AWQ 4bit**——同为 4bit 但机制不同：bnb 运行时（文件不变、能训练、精度好）；GPTQ/AWQ 预量化（文件变小、推理快、不能训练）——**'同为 4bit，训练与推理两个世界'**；**② bnb 4bit vs GGUF Q4_K_M**——GGUF 是 llama.cpp 生态的容器（CPU/苹果专用）——**'有 GPU 用 bnb，没 GPU 用 GGUF'**——两个数字锚点：bnb NF4 精度损失 1.7%（四家里最优）、Marlin-AWQ 吞吐 +61%（生产最快）——**'数字锚点背下来，选型时脱口而出'"**（09 篇对比表的预告版）。
