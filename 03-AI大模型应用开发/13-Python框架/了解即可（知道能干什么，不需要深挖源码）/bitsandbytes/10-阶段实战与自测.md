## 1. 实战项目：量化全流程动手

**实战项目 = 把本体系九课串成"亲手跑通"的完整流程**：

```text
实战项目三步（从加载到微调）
├── 第一步：4bit 加载（04/06 篇）
│    四件套配置加载一个小模型（Qwen2.5-1.5B 或 7B——看显卡）
│    验证：显存数字 + 推理一句
├── 第二步：8bit vs 4bit 对比（03/07 篇）
│    同模型两种精度加载——记录显存差（约一半）
│    结论：账本公式的实测验证
└── 第三步：QLoRA 微调小模型（05 篇）
    小数据集（几百条）+ 三步微调（四件套 + LoRA + Trainer）
    验证：loss 下降 + 保存适配器 + 微调前后输出对比
```

```python
# 实战核心代码（第一步——四件套加载）
from transformers import BitsAndBytesConfig, AutoModelForCausalLM, AutoTokenizer
import torch

config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,
)
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-1.5B", quantization_config=config, device_map="auto")
print(f"4bit 显存: {model.get_memory_footprint()/1024**3:.2f} GB")
# 1.5B 模型：FP16 约 3GB → 4bit 约 0.8GB——账本公式的实证
```

**实战心智**：**"实战的验收标准：'三个数字 + 一个对比'——显存数字（省了多少）、loss 数字（微调生效）、输出对比（效果变化）"**——**"了解即可的实战观：'跑通流程 + 记录数字'——不需要理解内核（那是库作者的事）——'你验证的是'怎么用'，不是'为什么这么实现'"**（本体系的深度定位——"动手到'会用'为止，源码留给专业人士"）；**实战的显卡要求**——"1.5B 4bit 加载：4GB 显存即可；QLoRA 微调 1.5B：8GB 起步——**'没显卡：加载可跑 CPU（慢）——微调要 GPU'"**（"CPU 场景的替代：GGUF/llama.cpp（09 篇）——'bnb 的实战舞台是 GPU'"）；**实战的常见卡点**——"配置报错（08 篇速查）、显存不够（减 batch/换小模型）——**'卡住先查速查表，再查 Issues——别卡在同一个坑两次'"**。

**实战的进阶路径**（跑通后的三个方向）："**① 换大模型**——1.5B 跑通 → 7B（12GB 卡）——配置不变只换模型名；**② 换真数据**——几百条测试数据 → 真实业务数据（格式照旧）；**③ 换部署**——微调产物 merge 后重新量化（09 篇训练侧→推理侧流程）——**'三步进阶 = 从'跑通'到'能用'——本体系毕业后的自然延伸"**（"延伸的方向：`../HuggingFace%20生态（只做推理，不训练）/` 的 transformers/peft 体系——**'bitsandbytes 是量化这一站，HuggingFace 是全景'"**）。

## 3. 报错速查

**高频报错速查（08 篇完整版的精要——十选六）**：

| 报错/现象 | 原因 | 解法 |
|---------|------|------|
| `CUDA error: no kernel image` | CUDA 版本不匹配 | 对齐 torch/CUDA/bnb 三件套 |
| `load_in_4bit` 参数报错 | 版本 ≥0.43 旧 API | 包进 `BitsAndBytesConfig` |
| 显存没省 | 配置静默失效（老版本） | 升级 + `get_memory_footprint` 验证 |
| 训练 loss NaN | float16 计算精度 | 换 `torch.bfloat16` |
| 训练中突然 OOM | 反量化缓冲尖峰 | 前向热身 + 减 batch |
| 训练速度断崖 | device_map auto 拆 CPU | 手动 `device_map={"": 0}` |

**速查心智**：**"六条的规律：'版本两类（旧 API/版本不匹配）+ 配置两类（精度/显存）+ 设备两类（拆分/缓冲）'"**——"**背下六条的'原因列'——报错时先对原因再对解法——'排障的本质是原因归类'"**（"新坑必记（08 篇纪律延续）——**'速查表是你的，不是我的——我的十条是起点，你的实战坑要补充'"**）。

## 4. 面试演练

**面试问答（量化相关——本体系特有）**：

**Q1：怎么让大模型跑在消费级显卡上？**——答：**"两条路：① 量化——用 bitsandbytes 4bit（NF4）加载，显存省 3/4（7B 从 14GB 到 3.5GB）——精度损失约 1.7%（PPL），感知上接近全精度；② 选对模型大小——按显存账本（参数 × 字节/参）选 7B/1.5B——生产环境推理换 GPTQ/AWQ + vLLM（Marlin 内核吞吐 +61%）；CPU 场景用 GGUF。我实际用 4bit 在 8GB 卡上跑过 7B 模型，显存 3.5GB，推理速度单用户可接受"**——结构：**方案 → 数字 → 场景区分 → 实战验证**——"答出'训练侧 vs 推理侧'的区分是加分项"。

**Q2：QLoRA 微调的原理？和全量微调的区别？**——答：**"QLoRA = 4bit 量化底座 + LoRA 适配器——底座 NF4 冻结（省显存），适配器全精度训练（保质量），前向时底座反量化回 bf16 计算（存算分离）——区别：全量微调 7B 要 56GB+ 显存，QLoRA 只要 8-12GB（24GB 卡舒适）——效果差距约 1-2%（指令跟随任务）——配置四件套（load_in_4bit/nf4/bf16 计算精度/double_quant）+ PEFT 三件套（LoraConfig/get_peft_model/Trainer）——可训练参数约 1%（r=16）"**——结构：**原理三句 → 数字对比 → 标准配置**——"答出'存算分离'显示理解深度"。

**Q3：怎么选量化方案？**——答：**"先定场景：① 微调 → bitsandbytes NF4（唯一能训练的）；② 生产高吞吐（NVIDIA+vLLM）→ GPTQ/AWQ + Marlin 内核（吞吐 +54-61%）；③ CPU/苹果 → GGUF Q4_K_M（llama.cpp）；④ 学习/原型 → bnb 4bit（最方便）——关键是分清'训练侧（内存问题）与推理侧（文件/速度问题）'——微调产物要 merge 后重新量化再上线——选型还看生态活跃度（AutoGPTQ 停维护的教训——选活跃库）——最后实测验证（精度/速度/显存三数字）"**——结构：**决策树 → 关键区分 → 生态 → 实测**——"答出'生态风险'是 2026 年的新加分项"。
