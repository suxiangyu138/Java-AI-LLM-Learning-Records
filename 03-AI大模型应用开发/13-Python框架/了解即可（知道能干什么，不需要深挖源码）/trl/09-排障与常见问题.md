## 1. 排障方法论

**对齐排障的第一原则：'问题分三类，按顺序查'**：

```text
排障三分类（按顺序）
├── ① 版本类：装不上/API 报错（0.x → 1.0 迁移/参数改名）
├── ② 数据类：训练不学/学歪（偏好对格式/质量——07 篇）
└── ③ 参数类：训练崩/效果差（学习率/beta/组大小）
    ——"排障顺序：先版本（能跑吗）→ 再数据（学得对吗）→ 后参数（调得好吗）"
```

**方法论心智**：**"排障的第一动作：看版本与报错全文"**——"**`pip show trl` + 报错第一行（版本要求都在里面）+ 官方 MIGRATION.md（0.x→1.0 迁移指南）——'对齐库的版本演进快（0.12 到 1.0 几个月）——老教程大概率过期'"**（"报错信息是'第一线索'——**'读报错第一行 + 最后一行（原因往往在末尾）'"**）；**排障的第二动作：最小复现**——"缩小到最小代码（一个模型 + 最小数据）——**'问题范围越小越好查——大项目报错先缩小'"**（"最小复现 = 排障的黄金工具（与 bitsandbytes 体系同款方法论）"）；**排障的记录**——"报错 → 解决 → 记进速查表（本课 5 节）——**'排障经验是对齐使用的护城河'"**（"trl 的坑有'时代性'（版本演进）——**'速查表要跟着版本更新'"**）。

## 2. 版本迁移坑

**版本迁移三坑——0.x → 1.0 的适配**：

```text
版本迁移三坑
├── ① 参数改名：tokenizer → processing_class（0.12 起）
│    —— 老代码 trainer = Trainer(..., tokenizer=...) → 报错
├── ② 大版本跳变：0.29.x → 1.0.0（跳过 0.30-0.99）
│    —— 老教程基于 0.x——代码大概率不兼容
└── ③ API 重构：Trainer 接口统一（_BaseTrainer 重构）
    —— 老代码的定制 Trainer 子类要适配
    ——"迁移三坑的解法：看官方 MIGRATION.md + 升级到最新稳定版"
```

**迁移心智**：**"迁移坑的核心：'trl 的演进太快'——几个月一个大变化——老教程过期是常态"**——"**2026-03 前是 0.x（研究库）、之后是 1.0（生产库）——'你的学习资源如果是 2025 年的，代码大概率要适配'"**（"适配的姿势：报错 → 搜官方 MIGRATION.md → 改参数名——**'官方迁移指南是最权威的适配手册'"**）；**版本选择的姿势**——"新项目直接用最新稳定版（1.5.x）——**'别用老版本（缺新能力 + 文档对不上）'"**（"生产项目锁版本（requirements.txt——`trl==1.5.1`）——**'锁版本是对齐项目的复现保障（与 bitsandbytes 同款纪律）'"**）；**升级的注意**——"升级看 release notes（1.4.0 的 chunked_nll 省 50% 显存、1.5.0 的 chat templates）——**'升级 = 白赚的新能力——季度性评估升级'"**。

## 3. 训练不稳定坑

**训练不稳定三坑——"loss 不降/乱跳/学歪"**：

```text
训练不稳定三坑
├── ① loss 不降（不学习）：
│    —— 学习率太小（默认值对不上你的数据）/ 数据格式错（trainer 没吃到）
├── ② loss 乱跳/发散（NaN）：
│    —— 学习率太大（DPO/RL 的 lr 要小——5e-6 级）/ 计算精度 float16（要 bf16）
├── ③ 学歪（loss 降但输出怪）：
│    —— 数据问题（偏好对质量差——chosen 比 rejected 差）/ 过拟合 chosen
└── 解决顺序：lr → 数据 → beta——"先调参数，再查数据，最后怀疑模型"
```

**不稳定心智**：**"不稳定排查的记忆：'lr 先行'——学习率是对齐训练的第一旋钮"**——"**对齐训练的学习率要小：SFT 2e-5、DPO 5e-6、GRPO 1e-6（越往后的方法越小）——'对齐是'微调偏好'——大学习率会把模型'打回原形'"**（"对比 SFT：对齐的 lr 比普通微调还小——**'记住三个数：2e-5 / 5e-6 / 1e-6'"**）；**数据问题的识别**——"loss 降但输出怪（学歪）= 数据问题（chosen/rejected 标反了/质量差）——**'学歪先查数据，别调参数（参数救不了坏数据）'"**（"抽检数据（07 篇）——**'数据抽检是学歪的第一解药'"**）；**过拟合 chosen**（04 篇局限）——"模型输出僵化（复读好答案）——**'对策：数据多样性 + 早停（eval 监控 loss 与输出）'"**（"早停策略：保存 eval 最好的 checkpoint——**'别让训练跑满全程——eval 说了算'"**）。

## 4. 数据与显存坑

**数据与显存四坑——"跑得动但不对 / 跑不动"**：

```text
数据与显存四坑
├── ① KeyError: prompt/chosen/rejected——字段名不对（07 篇三字段）
├── ② 训练"没学到"（loss 不降）——数据没配对/差距模糊（07 篇）
├── ③ OOM——显存不够：
│    减 batch → 梯度累积 → QLoRA（08 篇组合）→ 换小模型
├── ④ 显存尖峰（GRPO）——生成 N 个回答 = N 倍激活显存
│    减 num_generations / 减 batch
└── 共同规律：数据问题看格式，显存问题减配置
    ——"数据坑：格式与质量；显存坑：batch 与组大小"
```

**数据坑心智**：**"数据坑的记忆：'KeyError 查字段、不学习查配对'"**——"**KeyError = 字段名错（三字段背下来）；loss 不降 = 数据没配对（chosen/rejected 不是同一问题）——'数据坑的两个第一检查'"**（"数据的深度问题（质量差）→ 抽检（07 篇）——**'数据排障的层次：格式（报错）→ 配对（不学）→ 质量（学歪）'"**）；**显存坑的调节顺序**——"**batch 减半 → 梯度累积加倍 → QLoRA → 换小模型——'显存调节旋钮的顺序 = 损失最小优先（与 bitsandbytes 08 篇同款）'"**（"GRPO 的显存特殊性：生成 N 个回答的激活是 N 倍——**'GRPO 显存不够先减 num_generations（N=8 → 4）'"**）；**显存的预防**——"开跑前算账（02 篇账本 + 训练 ×3）+ 留余量——**'OOM 的预防 = 账本先行（和 bitsandbytes 同款纪律）'"**。

## 5. 报错速查表

**报错速查表（十大高频——本体系的"排障字典"）**：

| 报错/现象 | 原因 | 解法 |
|---------|------|------|
| `tokenizer` 参数报错 | 0.12+ 改名 | 用 `processing_class`（MIGRATION.md） |
| 老代码整体报错 | 0.x → 1.0 大迁移 | 看官方 MIGRATION.md 适配 |
| `KeyError: 'chosen'` | 数据集字段名错 | 检查 prompt/chosen/rejected 三字段 |
| loss 不降（不学习） | 数据没配对/lr 太小 | 抽检配对 + lr 升一档 |
| loss 变 NaN | lr 太大/float16 | lr 降一档 + 计算精度 bf16 |
| 学歪（loss 降输出怪） | 偏好对质量差 | 抽检数据（chosen 是否真的好） |
| 输出僵化（复读） | 过拟合 chosen | 数据多样性 + 早停 |
| OOM | 显存不够 | batch 减半 → 累积 → QLoRA |
| GRPO 显存尖峰 | 生成 N 回答 | 减 num_generations |
| DPO 无参考模型报错 | 漏传 ref_model | `DPOTrainer(..., ref_model=...)` |

**速查心智**：**"速查表的读法：'先对现象 → 找原因 → 按解法改'——十条覆盖 90% 的对齐问题"**——"**十条的规律：版本两条（迁移）、数据三条（格式/配对/质量）、训练三条（lr/NaN/过拟合）、显存两条（OOM/GRPO）——'报错先归类：版本/数据/参数/显存——四类记忆"**（"新坑必记（个人版速查表）——**'速查表 = 排障经验的沉淀库'"**）；**查不到的姿势**——"查官方 GitHub Issues（huggingface/trl——2026 活跃）+ 社区（HuggingFace 论坛）——**'先搜再问——报错信息 + trl 是搜索姿势'"**。

## 7. 本节验收
