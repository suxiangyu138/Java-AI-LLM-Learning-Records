## 1. 性能的来源

**uvicorn 的性能来源 = 异步模型 × 加速组件 × 合理配置**：

```text
性能三来源
├── 异步模型（03 篇）：单进程事件循环——IO 等待不占资源（架构级优势）
├── 加速组件（本课）：uvloop（事件循环加速）/httptools（HTTP 解析加速）
├── 合理配置（本课）：worker 数/超时/限流（配置级调优）
└── 测量先行：压测（wrk/locust——Python 异步 + FastAPI 体系的压测方法论）
    ——"性能的认知：架构（异步）决定上限，组件/配置逼近上限"
```

**性能心智**：**"性能的记忆：'异步是地基，standard 是装修，配置是家具'"**——"**异步模型（架构）决定了 uvicorn 的天花板（数千并发）；uvloop/httptools（组件）让天花板更接近；worker/超时（配置）让运行更稳——'调优的顺序：先架构（写 async def）、再组件（standard）、后配置'"**（"最大的性能坑在应用侧（慢查询/同步阻塞）——**'uvicorn 本身很快——瓶颈 90% 在应用代码'"**）；**性能的衡量**——"指标：QPS（每秒请求）、延迟（P50/P99）、并发数——**'性能不说数字 = 玄学（压测报告是标配）'"**（"压测工具（wrk/locust——`../../../01-Python语言/Python%20异步%20+%20FastAPI/` 有方法论）——**'压测是调优的'尺子'"**）。

## 2. standard 扩展三件宝

**standard 扩展（01/02 篇提过）——三件加速组件**：

```text
standard 三件宝
├── uvloop：事件循环的"涡轮增压"（C 实现的事件循环——比 asyncio 快）
├── httptools：HTTP 解析加速（C 实现的解析器——请求头/体解析快）
└── websockets：WebSocket 支持（标准库之外的高性能实现）
    ——"三件宝 = uvicorn 的'性能包'——一次安装，处处加速"
```

```bash
# 安装（02 篇重申——一次装到位）
pip install "uvicorn[standard]"
# 效果：吞吐提升 20-50%（官方基准——IO 密集场景更明显）
# 验证：uvicorn --version 输出带 [standard] 字样
```

**standard 心智**：**"standard 的记忆：'三件宝 = 白捡的性能——20-50% 的提升，一行安装'"**——"**为什么白捡：uvloop 用 C 实现事件循环（Python 的 asyncio 是纯 Python——C 更快）；httptools 同理（C 解析 HTTP）——'加速组件的本质：把热点用 C 重写'"**（"对比：裸装 uvicorn（纯 Python 事件循环）vs standard（C 加速）——**'生产必装 standard——性能差 20-50% 没理由不装'"**）；**三件宝的适用**——"uvloop：Linux/macOS 支持（Windows 不支持 uvloop——用标准 asyncio）——**'Windows 开发的坑：uvloop 装不上（不报错就行——Windows 自动回退）'"**（"Windows 生产很少（Linux 是服务器主场）——**'了解即可：Windows 用标准 asyncio，性能略差'"**）；**验证安装**——"`uvicorn --version` 输出 `[standard]` 标记——**'装没装对，版本命令说话（02 篇姿势）'"**。

## 3. 超时与限流

**超时与限流 = 保护的配置（防慢请求拖垮服务器）**：

```bash
# 常用保护参数（生产配置）
uvicorn app:app --workers 4 \
  --timeout-keep-alive 5 \          # 长连接空闲超时（秒）——防连接占着不放
  --limit-concurrency 1000 \        # 并发上限（同时处理的请求数）——防过载
  --limit-max-requests 10000 \      # 每个 worker 处理多少请求后重启——防内存泄漏累积

# Gunicorn 组合场景（04/05 篇）
gunicorn -k uvicorn.workers.UvicornWorker app:app \
  --timeout 60 \                    # 请求处理超时（秒）——防慢请求卡死
  --graceful-timeout 30             # 优雅停机超时
```

**超时心智**：**"超时的记忆：'防慢请求拖垮——每个超时管一类问题'"**——"**三个超时：keep-alive（连接空闲——防占资源）、timeout（请求处理——防卡死）、graceful（停机——防无限等）——'超时 = 服务器的'安全阀'"**（"不设超时：慢请求/坏连接无限占资源 → 服务器被拖垮——**'超时是生产标配（不是可选项）'"**）；**限流的记忆**——"**limit-concurrency（并发上限）**：保护服务器不被突发流量打崩（503 兜底）；**limit-max-requests（请求数重启）**：防内存泄漏累积（worker 处理 N 请求后重启）——'限流 = 服务器的'刹车'"（"限流与压测的关系：上限按压测结果定（压测 1500 并发 → 限 1000 留余量）——**'限流阈值来自压测，不是拍脑袋'"**）；**超时与业务的权衡**——"超时太短 → 慢业务被误杀（大文件/长任务）；太长 → 资源被占——**'超时按业务特性调（文件上传类放宽 timeout）'"**（"长任务的正解：异步任务队列（不占请求）——**'超时是兜底，任务队列是正解'"**）。

## 4. 性能调优清单

**性能调优清单（按收益排序——从大到小）**：

```text
性能调优清单（ROI 排序）
├── ① 应用侧（最大收益——占瓶颈的 90%）：
│    写 async def（IO 场景）/ 避免同步阻塞（time.sleep/同步 DB 调用）
│    DB 查询优化/缓存（Redis——02 后端体系）
├── ② standard 扩展（一行安装——20-50%）
├── ③ worker 数（≈ 核数——04 篇）
├── ④ 超时限流（保护——稳）
└── ⑤ 静态文件给 Nginx（不动 uvicorn——05 篇）
    ——"调优的顺序：先应用（async/缓存）、再组件（standard）、后配置（worker/超时）"
```

**清单心智**：**"清单的记忆：'应用 > 组件 > 配置——90% 的瓶颈在应用'"**——"**uvicorn 本身很快（异步 + C 加速）——你的应用慢才是瓶颈（同步阻塞/慢查询/无缓存）——'先看应用再调服务器——服务器背了太多应用的锅'"**（"典型慢应用：`time.sleep` 在 async 端点（阻塞整个事件循环——**'async 里的同步阻塞 = 性能杀手'"**（"同步阻塞的排查：压测时延迟陡增 + CPU 低——**'async 端点里绝不能 time.sleep（要 asyncio.sleep）'"**）；**调优的验证**——"每次调优前后压测对比（记录数字）——**'调优报告 = 参数 + 数字（性能不说数字 = 玄学）'"**（"压测方法论（wrk/locust——Python 异步 + FastAPI 体系）——**'压测是调优的尺子'"**）；**性能的边界**——"单机有极限（CPU/带宽）——**'单机调优到顶后：水平扩展（多实例 + 负载均衡——05 篇 Nginx 的负载能力）'"**（"性能的路线：调优（榨干单机）→ 扩展（加机器）——**'先调优后扩展'"**）。
