## 1. 生产与开发的差异

**生产环境的要求：稳定 × 性能 × 安全 × 可运维**：

```text
开发 vs 生产（差异对照）
├── 开发：单进程 + reload + 127.0.0.1（怎么方便怎么来）
├── 生产：多 worker + 无 reload + 0.0.0.0 + Nginx 反代 + 日志监控
└── 生产四要求：
    稳定（7×24 不崩）  性能（多核利用）  安全（不裸奔）  可运维（日志/监控/重启）
    ——"开发是'跑起来'，生产是'扛得住'——部署是'扛得住'的工程"
```

**生产心智**：**"生产部署的记忆锚点：'多 worker + 反代 + 进程管理 + 优雅'"**——"**四件套：多 worker（利用多核——04 篇）、Nginx 反代（门户——本课 3 节）、进程管理（systemd/Docker——本课 2 节）、优雅停机（不中断请求——本课 4 节）——'四件套齐 = 生产姿势'"**（"少一件都有风险：裸跑（无反代）→ 性能与安全问题；无进程管理 → 挂了不重启——**'生产部署是'组合拳'"**）；**部署的目标形态**——"用户请求 → Nginx（静态/HTTPS/负载）→ uvicorn（多 worker 跑应用）→ 业务逻辑——**'链路清晰 = 故障好定位（08 篇监控）'"**（"部署的文档化：部署文档（架构图/命令/检查清单）是团队的标配——**'部署姿势要写下来，别只在脑子里'"**）。

## 2. 多 worker 与进程管理

**多 worker（04 篇深化）+ 进程管理（谁保证它活着）**：

```bash
# 方案一：Gunicorn 管进程（经典组合——04 篇）
gunicorn -k uvicorn.workers.UvicornWorker app:app --workers 4 \
  --bind 127.0.0.1:8000 --timeout 60 --graceful-timeout 30

# 方案二：systemd 管进程（Linux 服务——挂了自动重启）
# /etc/systemd/system/myapp.service
[Service]
ExecStart=/path/venv/bin/uvicorn app:app --workers 4 --host 127.0.0.1 --port 8000
Restart=always          # 挂了自动重启
User=myapp

# 方案三：Docker 管进程（容器——01 后端 Docker 体系）
# CMD ["uvicorn", "app:app", "--workers", "4", "--host", "0.0.0.0", "--port", "8000"]
```

**进程管理心智**：**"进程管理的记忆：'谁保证 uvicorn 活着'——Gunicorn/systemd/Docker 三选一"**——"**裸跑 uvicorn 的风险：进程崩了没人拉起（服务挂了没人知道）——'进程管理器 = uvicorn 的'看护人'"**（"三选一的场景：单机 Linux 用 systemd、容器用 Docker、要 worker 管理用 Gunicorn——**'进程管理是生产的底线（挂了能自动重启）'"**）；**Gunicorn 组合的细节**——"`-k uvicorn.workers.UvicornWorker` 是关键（让 Gunicorn 用 uvicorn 的协议处理）——**'Gunicorn 管 worker 生命周期（超时/优雅重启），uvicorn 管请求处理——各管一段'"**（"Gunicorn 的 worker 数 = uvicorn 的 worker 数——**'核数原则一样（04 篇）'"**）；**绑定的选择**——"生产绑定 127.0.0.1（只让 Nginx 访问——安全）vs 0.0.0.0（直接暴露——不推荐）——**'uvicorn 绑定内网，Nginx 面向公网——分层'"**（"容器里绑定 0.0.0.0（容器网络隔离）——**'绑定地址跟着部署形态走'"**）。

## 3. Nginx 反向代理

**Nginx 反代 = uvicorn 前面的"门户"（生产架构的关键一环）**：

```text
为什么加 Nginx
├── 静态文件：Nginx 直接返回（不占 uvicorn——性能）
├── HTTPS：证书终止（uvicorn 不用管 SSL）
├── 负载均衡：多 uvicorn 实例分发（水平扩展）
├── 安全：隐藏内部结构/限流/防护
└── HTTP/2：Nginx 支持（补 uvicorn 的短板——03 篇协议边界）
    ——"uvicorn 管应用，Nginx 管门户——分工明确"
```

```nginx
# nginx.conf（核心片段）
server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://127.0.0.1:8000;      # 转发给 uvicorn
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    # WebSocket 支持（长连接）
    location /ws/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;   # WebSocket 三件套
        proxy_set_header Connection "upgrade";
    }
}
```

**Nginx 心智**：**"Nginx 的记忆：'门户'——uvicorn 是'办公室'，Nginx 是'前台'"**——"**请求先进前台（Nginx——静态/HTTPS/安全），需要业务才进办公室（uvicorn）——'动静分离 + 安全分层 = 生产架构的标准'"**（"Nginx 的完整知识在 `../../02-后端核心技术%20微服务%20分布式%20云原生/07-工程运维基础/运维/Nginx%20基础/` 体系——**'本课知道'为什么加'，Nginx 体系教'怎么配'"**）；**代理的注意**——"**X-Forwarded 头**：Nginx 转发时要带（uvicorn 才知道真实 IP/协议——否则日志里全是 127.0.0.1）——'不配 X-Forwarded = 日志失真'"（"WebSocket 的 Upgrade 头：普通 proxy_pass 不够（长连接要升级头）——**'WebSocket 三件套（Upgrade/Connection/HTTP1.1）是常见坑'"**）；**Nginx 的替代**——"Caddy（自动 HTTPS）/云负载均衡（云厂商 LB）——**'Nginx 是通用解，云 LB 是托管解——按部署环境选'"**。

## 4. 优雅停机与安全

**优雅停机 = 处理完存量请求再退出（部署不中断服务）**：

```text
优雅停机原理
├── 收到停止信号（SIGTERM）→ 停止接收新请求
├── 处理完正在进行的请求（存量——不中断）
└── 全部完成 → 退出（部署/升级时用户无感）
    ——"对比粗暴退出：直接 kill → 正在处理的请求全断（用户报错）——优雅停机 = 用户无感的部署"
```

```bash
# 触发优雅停机（生产姿势）
kill -TERM <uvicorn_pid>        # SIGTERM = 优雅停机（uvicorn 支持）
# systemd: systemctl restart myapp（自带优雅）
# Docker: docker stop（默认 SIGTERM——优雅）

# 超时控制（Gunicorn 场景——04 篇）
# --graceful-timeout 30（30 秒内没处理完的强制结束）
```

**优雅停机心智**：**"优雅停机的记忆：'先停新、再等旧、后退出'"**——"**部署/升级的瞬间用户在请求（正在处理）——粗暴退出 = 请求中断（用户看到 500/连接断）——'优雅停机 = 部署无感（用户体验的底线）'"**（"配合多 worker：逐个优雅重启（滚动更新——一个停完另一个再停）——**'滚动更新 = 部署全程有服务（零停机）'"**）；**生产安全要点**（部署的底线）——"**① 不裸跑**（Nginx 前面挡着）；**② 权限最小**（非 root 用户跑 uvicorn）；**③ 密钥管理**（环境变量/密钥库——别写代码里）；**④ 依赖锁版本**（requirements 锁——复现保障）——**'安全的部署 = 默认不信任外部'"**（"详细安全在 Python 异步 + FastAPI 体系的部署篇——**'本课知道'安全四要点'即可'"**）。
