## 1. 排障方法论

**服务器排障的第一原则：'日志先行'——先看日志再猜原因**：

```text
排障三分类（按顺序）
├── ① 启动类：起不来（模块名错/端口占用/版本不兼容）
├── ② 运行时：请求出错（应用 bug/超时/连接断）
└── ③ 部署类：外部访问不到（host/防火墙/Nginx 配置）
    ——"排障顺序：先看日志（报什么错）→ 再查配置（参数对吗）→ 后查网络（通不通）"
```

**方法论心智**：**"排障的第一动作：看启动日志与错误日志"**——"**uvicorn 的报错信息很明确（模块找不到/端口占用/异常堆栈）——'报错第一行 + 最后一行（原因往往在末尾）'"**（"日志分级排查：ERROR 先看、WARNING 参考、INFO 看请求流——**'错误日志 = 排障的第一现场（08 篇）'"**）；**排障的第二动作：最小复现**——"缩小到最小应用（一个路由）复现——**'问题范围越小越好查（与 trl/bitsandbytes 同款方法论）'"**（"最小复现 = 排障的黄金工具——**'能最小复现 = 一半已定位'"**）；**排障的记录**——"报错 → 解决 → 记进速查表（本课 5 节）——**'排障经验是服务器运维的护城河'"**。

## 2. 启动类问题

**启动三坑——"起不来"的常见原因**：

```text
启动三坑
├── ① ModuleNotFoundError / 模块:应用写错：
│    uvicorn app:app 报 "module 'app' has no attribute 'app'"
│    —— 冒号前后写反/对象名错（02 篇——文件:对象）
├── ② 端口占用：
│    "address already in use" —— 8000 被别的进程占了
│    —— 换端口（--port 8001）或杀占用进程
└── ③ 版本/环境不兼容：
│    应用用了新特性但 uvicorn/Python 太老——启动报错
│    —— 升级 uvicorn（0.38+ 支持 Python 3.14——01 篇）
    ——"启动三坑的共同解法：看报错信息——它直接告诉你哪错了"
```

**启动心智**：**"启动坑的记忆：'模块名/端口/版本——报错信息直接说'**——"**ModuleNotFoundError 三查：① 文件在吗（路径）；② 名字对吗（app:app——文件:对象）；③ 目录对了吗（--app-dir——04 篇的坑）——'起不来先对这三个'"**（"端口占用的处理：`netstat -ano | findstr 8000`（Windows）/ `lsof -i:8000`（Linux）看谁占着——**'端口排查 = 先查占用再换端口'"**）；**版本不兼容的识别**——"报错里带 'requires' / 'not supported' → 版本问题——**'版本问题的解法：升级 uvicorn/Python（01 篇版本基线）'"**（"环境的隔离（venv——`../01-Python语言/pip/`）——**'版本冲突多在全局环境——venv 隔离是第一防线'"**）。

## 3. 运行时问题

**运行三坑——"跑起来了但不对"**：

```text
运行三坑
├── ① 请求 500（应用异常）：
│    —— 错误日志有堆栈——应用 bug（不是 uvicorn 的错）
├── ② 请求卡住/超时（慢请求）：
│    —— async 端点里的同步阻塞（time.sleep——06 篇性能杀手）
│    —— 慢数据库/外部调用（没超时——挂起）
├── ③ 连接断/WebSocket 断：
│    —— keep-alive 超时/代理没配 Upgrade 头（05 篇 WebSocket 三件套）
└── 共同规律：多数"运行问题"是应用问题——先查应用再怀疑 uvicorn
    ——"uvicorn 很稳定——运行问题 90% 是应用代码的问题"
```

**运行心智**：**"运行坑的核心认知：'uvicorn 背了应用的锅'——多数运行问题在应用"**——"**500 的错误日志有完整堆栈（哪行代码出错）——'查 500 = 看错误日志的堆栈（08 篇）'"**（"500 vs 502 的区别：500 应用内部错（uvicorn 正常转发）；502 网关错（uvicorn 没响应——反代视角——04 篇）——**'状态码定位故障侧'"**）；**卡住的排查**——"慢请求的排查：看访问日志的响应时间（慢在哪）、压测复现——**'卡住先查'同步阻塞'（time.sleep/同步 DB）'"**（"asyncio 里的 `time.sleep` 阻塞整个事件循环（所有请求一起卡）——**'async 端点必须 asyncio.sleep（06 篇性能杀手的实战版）'"**）。

## 4. 部署类问题

**部署三坑——"本地好好的，部署就挂"**：

```text
部署三坑
├── ① 外部访问不到：
│    —— host 没配 0.0.0.0（默认 127.0.0.1——只能本机——02 篇部署第一坑）
│    —— 防火墙/安全组没放行端口（云服务器——02 后端网络排查体系）
├── ② Nginx 502 Bad Gateway：
│    —— uvicorn 没启动/端口不对/绑定地址不对（05 篇）
│    —— Nginx 的 proxy_pass 指向的 127.0.0.1:8000 没服务
├── ③ 代理后 IP 全是 127.0.0.1：
│    —— Nginx 没配 X-Forwarded-For（05 篇——日志失真）
└── 共同规律：部署问题 = 配置问题（host/端口/代理头）
    ——"本地好部署挂：三查——host/防火墙/代理配置"
```

**部署心智**：**"部署坑的记忆：'host/防火墙/代理头——三查'**——"**外部访问不到的第一查：host（127.0.0.1 vs 0.0.0.0）——'部署第一坑就是 host（02 篇）'"**（"云服务器还要查防火墙/安全组（云厂商控制台放行端口）——**'本地防火墙 + 云安全组双查'"**）；**502 的排查顺序**——"① uvicorn 起了吗（进程）；② 端口对吗（uvicorn 端口 vs proxy_pass）；③ 绑定对吗（uvicorn 绑定 127.0.0.1——Nginx 同机访问没问题；跨机要 0.0.0.0）——'502 = Nginx 找不到 uvicorn——按三查定位'"（"502 vs 504：502 连不上（服务没起/端口错）；504 连上了没响应（超时——慢请求）——**'502 找连接、504 找超时'"**）；**日志失真的坑**——"Nginx 没转发 X-Forwarded-For → uvicorn 日志全是 127.0.0.1（无法分析真实访问）——**'配 Nginx 必带转发头（05 篇）'"**。

## 5. 报错速查表

**报错速查表（十大高频——本体系的"排障字典"）**：

| 报错/现象 | 原因 | 解法 |
|---------|------|------|
| `ModuleNotFoundError` | 模块/对象名错 | 查 app:app 写法 + --app-dir |
| `address already in use` | 端口占用 | 换端口或杀占用进程 |
| `[WinError 10013]` | Windows 端口被权限拦 | 换高端口（8000 可能被占/拦） |
| 外部访问不到 | host 是 127.0.0.1 | `--host 0.0.0.0` + 防火墙放行 |
| 请求 500 | 应用异常 | 看错误日志堆栈（应用 bug） |
| 全部请求卡住 | async 里同步阻塞 | `time.sleep` → `asyncio.sleep` |
| Nginx 502 | uvicorn 没起/端口错 | 502 三查（进程/端口/绑定） |
| Nginx 504 | uvicorn 响应超时 | 查慢请求 + 调 timeout |
| 日志全 127.0.0.1 | Nginx 没转发头 | 配 X-Forwarded-For |
| WebSocket 连不上 | 代理没 Upgrade 头 | Nginx 配 WebSocket 三件套 |

**速查心智**：**"速查表的读法：'先对现象 → 找原因 → 按解法改'——十条覆盖 90% 的 uvicorn 问题"**——"**十条的规律：启动三条（名/端口/权限）、运行三条（500/卡/断）、部署四条（host/502/504/头）——'报错先归类：启动/运行/部署——三类记忆'"**（"新坑必记（个人版速查表）——**'速查表 = 排障经验的沉淀库'"**）；**查不到的姿势**——"查官方 GitHub Issues（encode/uvicorn——活跃）+ Stack Overflow——**'先搜再问——报错信息 + uvicorn 是搜索姿势'"**。

## 7. 本节验收

**验收动作**：① 模拟启动三坑（写错模块名/占端口）并解决；② 制造 500 并看错误日志定位；③ 模拟 502（停 uvicorn 访问 Nginx）并排查；④ 背下速查表前 5 条——**"方法论 + 三类问题 + 速查表 = 排障能力"**——**练习纪律**：新坑必记——"排障经验是服务器运维的护城河"。
