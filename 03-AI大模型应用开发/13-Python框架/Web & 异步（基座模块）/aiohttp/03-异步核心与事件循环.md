## 1. 原生 asyncio，不是适配层

这是 aiohttp 与 httpx 的本质区别。httpx 的异步 API 是在同步实现外层包了异步壳——它内部维护独立的异步传输层，但与 asyncio 生态的协作停留在「能 await」层面。aiohttp 的每一层都是为 asyncio 设计的：`ClientSession` 的每个操作返回协程、`StreamReader` 直接对接事件循环的读回调、服务端每个连接就是一个 Task、背压通过 `asyncio.wait` 原语实现。这意味着它可以使用 asyncio 的全部能力：`asyncio.gather` 并发、`Semaphore` 限流、`TaskGroup` 结构化并发、`timeout` 上下文超时——全部原生契合，没有适配损耗。

## 2. await 语义与事件循环

理解 aiohttp 代码，只需要理解一句话：**`await` 是「让出 CPU，等 I/O 完成」的声明**。执行 `await session.get(url)` 时，协程把请求交给操作系统，事件循环立刻去执行其他就绪的协程；网络响应到达时，事件循环唤醒这个协程继续往下走。

```python
async def fetch(session, url):
    async with session.get(url) as resp:   # await 网络 I/O：让出控制权
        return await resp.text()           # 继续 await：等待响应体读完
```

三次 await（建立连接、读响应头、读响应体）之间，事件循环都在服务其他请求。所以「并发」不是同时执行，而是**轮转推进**：单线程内无数协程排队等待各自的 I/O 事件，谁的事件到了谁跑。这也解释了为什么协程里写阻塞代码是致命的——`time.sleep(1)` 不产生 I/O 事件，事件循环只能干等，全程序停摆 1 秒。

## 3. 并发模型：单线程轮转

**先分清三个概念**：协程对象（`async def` 调用产生的对象，还没开始执行）、Task（`asyncio.create_task`/`asyncio.run` 把协程包装成调度单元，开始排队执行）、Future（Task 的底层承诺——「结果将来给你」）。aiohttp 代码里你直接接触的是协程对象与 Task：`await` 一个协程是「内联等待」，`create_task` 是「后台排队执行」。`asyncio.gather(*(fetch(u) for u in urls))` 的实质是：为每个 `fetch(u)` 协程创建一个 Task，全部丢进事件循环，然后当前协程挂起等所有 Task 完成——这就是一行代码实现并发的全部秘密。理解这三层概念后，读任何异步代码都不会再晕。

| 维度 | requests 线程池 | aiohttp 事件循环 |
|------|----------------|------------------|
| 并发载体 | 线程（OS 资源） | 协程（内存对象） |
| 1000 并发内存 | 线程栈 8MB×1000 | 协程栈 几十 KB 总量 |
| 切换成本 | 内核调度、GIL 竞争 | 协程 yield，纳秒级 |
| 阻塞行为 | 阻塞线程，其他继续 | 阻塞循环，全部暂停 |

1000 个并发请求，requests 方案需要 1000 个线程；aiohttp 方案就是 1000 个协程对象 + 一个事件循环。这也是为什么异步爬虫能「一个进程打满千级并发」——瓶颈从线程资源转移到对端服务器的承受能力。

## 4. 与异步编程体系的配合

**并发入口用 `asyncio.run`**。3.14 起 asyncio 的 policy 系统整体弃用，任何 `set_event_loop_policy`、手动 `new_event_loop` 的写法都是过时姿势。`asyncio.run(main())` 一个入口管建、跑、关。

**结构化并发用 `asyncio.TaskGroup`**。Python 3.11+ 的标准姿势：组内任一任务异常，组内所有任务自动取消并向外抛出——比裸 `gather` 更安全，不会出现「一个挂了其他还在傻等」的僵尸任务。

```python
async with asyncio.TaskGroup() as tg:
    for url in urls:
        tg.create_task(fetch(session, url))   # 全部并发，异常自动聚集
```

**限流用 `asyncio.Semaphore`**。并发请求的阀门：`sem = asyncio.Semaphore(50)`，每个请求 `async with sem:`——同时进行的最多 50 个，其余排队。这是爬虫与批量调用的第一纪律，见 08 篇详解。

**超时用 `asyncio.timeout`**（3.11+）。对协程块整体限时：超时抛 `TimeoutError`，配合 `asyncio.CancelledError` 正确处理取消。aiohttp 自身还有更细的四段 `ClientTimeout`，两者层次不同：前者管一段业务逻辑，后者管单次 HTTP 交互。

**更快的事件循环用 uvloop**。uvloop 是 Cython 实现的 asyncio 事件循环替代品，普遍快 2-4 倍，与 aiohttp 零代码配合：

```python
import uvloop, asyncio
uvloop.install()          # 全局替换事件循环，之后照常写
asyncio.run(main())
```

注意 `uvloop.install()` 必须在 `asyncio.run` 之前调用，且不兼容 Windows——Windows 生产环境仍用默认循环，性能差距在 HTTP 场景通常可接受。

## 5. 阻塞操作的正确姿势

协程里遇到真正的阻塞操作（同步 requests、文件读、CPU 密集、数据库同步驱动），有三种解法按优先级排列：

**换异步库**。优先用 asyncpg、aiofiles、`redis.asyncio` 等原生异步替代品，不产生线程切换。

**`asyncio.to_thread` 兜底**（3.9+）。把阻塞函数丢进默认线程池，协程 await 结果，事件循环不阻塞：

```python
data = await asyncio.to_thread(requests.get, url)   # 同步库放进线程池跑
```

**进程池处理 CPU 密集**。`loop.run_in_executor(ProcessPoolExecutor(), fn, arg)`——注意 asyncio 不解决 CPU 密集问题，这是它的边界，要上多进程。

## 6. 五大反模式

**反模式一：协程里 `time.sleep` / 同步 requests**。整个事件循环冻结，所有并发请求一起等。诊断信号：并发一高程序反而更慢。

**反模式二：忘写 await**。`session.get(url)` 不 await 拿到的是一堆协程对象，请求根本没发出——常见于列表推导里没加括号。`asyncio.run` 直接报 `RuntimeError: no running event loop` 或静默什么都不做。

**反模式三：fire-and-forget 任务**。`asyncio.create_task(fn())` 后不保存引用、不 await——任务随时可能被 GC 回收，异常无人接住静默吞掉。要么 TaskGroup 管理，要么至少保存引用并 await。

**反模式四：无上限并发**。`asyncio.gather(*(fetch(u) for u in urls))` 一万个 URL 就一万个并发——打爆对端、耗尽本机连接、触发限流。并发必须有 Semaphore 或 `limit` 约束。

**反模式五：循环里反复建 session**。`for url in urls: async with ClientSession() as s:`——每个请求新建连接池，复用机制完全失效，性能退化到同步水平。session 建一次，全程序复用（见 04 篇）。

**反模式六：在回调/钩子里启动新事件循环**。比如在线程回调里 `asyncio.run(...)` 跑请求——多线程各自跑循环是常见架构（如结合 Celery 消费任务），但每个循环各管各的会话，连接池无法共享，跨循环对象共享更是并发雷区。正确姿势：线程只做分发，把请求塞进统一的事件循环（`loop.call_soon_threadsafe`），或干脆用 asyncio 原生调度（TaskGroup）替代线程。判断标准：**一个进程只该有一个事件循环在跑请求**。
