## 1. pytest-aiohttp 与插件生态

aiohttp 历史上有两个测试插件：内置的 `aiohttp.pytest_plugin` 与独立的 pytest-aiohttp。**3.14 起内置插件已弃用**，官方指定 pytest-aiohttp 为唯一测试方案——新项目直接装它，看到老教程里的 `aiohttp.pytest_plugin` 代码一律换成 pytest-aiohttp。

```bash
pip install pytest-aiohttp
```

pytest-aiohttp 提供两个核心能力：`asyncio` fixture（pytest 直接测协程，无需 `asyncio.run` 包装）与 `TestClient`/`TestServer`（进程内起测试服务，无需真实端口与网络）。配合 pytest 的 `pytest.mark.asyncio` 标记，测试即写即跑：

```python
import pytest
from aiohttp import web

async def index(request):
    return web.json_response({"ok": True})

@pytest.mark.asyncio
async def test_index(aiohttp_client):
    app = web.Application()
    app.router.add_get("/", index)
    client = await aiohttp_client(app)          # 进程内测试客户端
    resp = await client.get("/")
    assert resp.status == 200
    assert await resp.json() == {"ok": True}
```

`aiohttp_client` 是插件注入的 fixture：启动应用、返回 TestClient、测试结束自动清理。TestClient 是 aiohttp 客户端与服务端之间的桥梁——**请求真正走完整个 HTTP 栈（含解析器）**，但发生在进程内，不占端口、不碰网络，速度与可靠性远超起真实服务。

**异步测试的分层思想**：测试要快、要稳、要隔离，代价最小的是「mock 最外层」。你的代码调用外部 HTTP——aioresponses 拦掉（层一）；你的服务端依赖数据库——测试起内存库或 mock 掉（层二）；只有端到端验收才起真服务连真库（层三，慢且脆，单独标记）。aiohttp 项目里这个金字塔的具体形态：**单元测试**直接测纯函数（URL 构造、响应解析——不碰网络不碰 session）；**组件测试**用 TestClient 测服务端路由与中间件、用 aioresponses 测客户端封装；**集成测试**起真实 TestServer + 真数据库（或容器化依赖）验证全链路。金字塔越高用例越少越慢——90% 的用例应该落在前两层。

## 2. 服务端测试：TestClient

TestClient 不止测「能返回 200」，还能测框架行为：

**测试路径参数与状态码**：

```python
@pytest.mark.asyncio
async def test_not_found(aiohttp_client):
    resp = await client.get("/no-such-path")
    assert resp.status == 404

@pytest.mark.asyncio
async def test_match_info(aiohttp_client):
    resp = await client.get("/items/42")
    assert await resp.json() == {"id": 42}     # match_info 正确解析
```

**测试中间件**（异常兜底、统一头）：断言错误响应体与 header。

**测试 WebSocket**：TestClient 提供 `client.ws_connect("/ws")` 协程——测试环境里完成完整握手与收发，断线重连逻辑也能测（服务端关连接后断言客户端行为）。

**测试生命周期钩子**：`on_startup`/`on_cleanup` 由 TestClient 触发，初始化 DB 的钩子天然被测到。fixture 复用：把 app 构建与 client 获取写进 `@pytest.fixture`，用例间共享，避免每个用例重建应用。

一个注意点：TestClient 是「整栈但隔离」的测试——验证协议行为足够；集成测试（真实数据库、外部 API）另起一组慢速用例，两组分开跑（`-m "not integration"` 日常快速回归）。

## 3. 客户端测试：aioresponses mock

测客户端代码（爬虫、API 封装、Agent 工具）时不能真打外部服务——aioresponses 用 mock 拦截 `ClientSession` 的请求，返回脚本化响应：

```python
import aioresponses

@pytest.mark.asyncio
async def test_fetch_user(aioresponses):
    with aioresponses.aioresponses() as mocked:
        mocked.get("https://api.example.com/users/1",
                   payload={"id": 1, "name": "alice"}, status=200)

        async with aiohttp.ClientSession() as session:
            async with session.get("https://api.example.com/users/1") as resp:
                assert await resp.json() == {"id": 1, "name": "alice"}
```

关键能力：按 URL 精确 mock（`payload=` 自动序列化 JSON）、按正则 `re.compile(r"https://api\.example\.com/users/\d+")` 批量 mock、断言调用次数（`mocked.assert_called_once()`）、模拟异常（`exception=TimeoutError()`）测重试逻辑、`repeat` 参数模拟「第一次 500、第二次 200」的退避场景。这是重试、超时、错误处理测试的核心工具——**先写 mock 再写代码，行为可预期**。

注意 `aioresponses` 是第三方包（非 aiohttp 官方），拦的是 aiohttp 的 `ClientSession` 内部传输层——对测试中的 aiohttp 请求有效，对 httpx/requests 无效。

## 4. TraceConfig 请求追踪

TraceConfig 是 aiohttp 内置的观测钩子：把回调挂在 `ClientSession(trace_configs=[...])` 上，请求生命周期每个节点触发。四个核心回调：

```python
async def on_start(session, ctx, params):  log.info(f"开始: {params.url}")
async def on_end(session, ctx, params):    log.info(f"完成: {params.url} {params.response.status} 耗时={params.time}")
async def on_exception(session, ctx, params):  log.error(f"异常: {params.url} {params.exception!r}")
async def on_redirect(session, ctx, params):   log.warning(f"重定向: {params.url} → {params.redirected}")

trace_config = aiohttp.TraceConfig()
trace_config.on_request_start.append(on_start)
trace_config.on_request_end.append(on_end)
trace_config.on_request_exception.append(on_exception)
trace_config.on_request_redirect.append(on_redirect)

session = aiohttp.ClientSession(trace_configs=[trace_config])
```

用途分三层：**调试层**——看每个请求的 URL、状态、耗时，定位「哪个请求慢」；**监控层**——生产环境统计耗时分布、错误率（配合 [[../../强烈推荐（做项目必用，简历加分）/loguru/00-loguru总览|loguru]] 结构化日志）；**业务层**——在回调里做限流计数、缓存决策。回调是协程，可以直接 await——注意回调本身别阻塞，它跑在请求协程内。

## 5. 日志调试三板斧

**第一板斧：开启 aiohttp 内部日志**。aiohttp 的各个子系统（客户端、服务端、连接池、DNS）都有 logger，默认 INFO 级别，看不到细节：

```python
import logging
logging.basicConfig(level=logging.DEBUG)
logging.getLogger("aiohttp").setLevel(logging.DEBUG)
```

DEBUG 级别会输出每次请求的完整过程：DNS 解析、连接建立、请求头、响应状态——「连上了没」「谁慢」一目了然。生产只开 aiohttp.client，避免噪音。

**第二板斧：服务端访问日志**。`web.run_app(app, access_log=logger)` 或 Gunicorn 默认打 access log——每条请求的方法、路径、状态、耗时全记录。用 loguru 的 handler 接管后，按状态码统计 5xx、按耗时统计 P99，就是最简单的监控。

**第三板斧：TraceConfig 补业务上下文**。内部日志管协议层，TraceConfig 管业务视图——把 URL、耗时、异常挂上业务字段（爬虫任务 ID、批次号），日志才能回答「这批任务的失败分布」。三板斧配合：内部日志看「怎么了」，access log 看「多不多」，Trace 看「是谁干的」。

## 6. 常见坑

**坑一：测试里直接 `asyncio.run`**。pytest-aiohttp 的 asyncio fixture 已管理事件循环，再 `asyncio.run` 会报循环冲突——用 `@pytest.mark.asyncio` 写协程即可。

**坑二：测试打真实网络**。用例连外部 API——CI 断网即红、外部抖动即假失败。外部依赖一律 aioresponses mock，真实联调用单独标记的集成用例。

**坑三：TestClient 当生产客户端**。TestClient 是测试专用（进程内、无真实端口），生产代码用普通 `ClientSession`——别为了「快」在生产引 TestClient。

**坑四：TraceConfig 回调里做重活**。回调跑在请求协程内，同步重活阻塞请求本身——只做记录，不做计算。

**坑五：mock 的 URL 与代码不一致**。mock 了 `https://api.example.com` 但代码实际请求 `https://api.example.com/`——尾斜杠不同即不匹配，请求直通真网络。用 `aioresponses` 的 `passthrough` 参数显式控制，或先断言调用再放行。

**坑六：日志级别在生产忘了降回**。DEBUG 全开的生产环境每秒打爆磁盘——日志配置走环境变量，CI/生产默认 INFO。

**坑七：mock 全部请求后漏了断言**。aioresponses 拦掉的请求默认放行真实网络（`passthrough` 默认开启的语义）；测试结束用 `mocked.assert_not_called()`/断言调用次数验证「代码确实发了预期的请求」——只 mock 不断言，测试等于没写。
