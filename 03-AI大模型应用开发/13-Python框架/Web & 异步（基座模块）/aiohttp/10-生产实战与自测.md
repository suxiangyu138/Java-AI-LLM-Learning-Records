## 1. 实战：并发下载器

把全体系知识点压进一个项目：滑动窗口并发、信号量限流、指数退避重试、断点续传、结构化日志。目标是下载一批文件，优雅应对网络抖动与对端限流。

```python
import asyncio, random, time
import aiohttp
from aiohttp import ClientTimeout, encode_basic_auth
from loguru import logger

class ConcurrentDownloader:
    def __init__(self, urls, dest_dir="downloads/", max_conn=20, max_retry=3):
        self.urls, self.dest_dir = urls, dest_dir
        self.sem = asyncio.Semaphore(max_conn)      # 限流：并发上限
        self.max_retry = max_retry
        timeout = ClientTimeout(total=60, connect=10, sock_read=30)
        connector = aiohttp.TCPConnector(limit=max_conn, limit_per_host=4)
        self.session = aiohttp.ClientSession(
            timeout=timeout, connector=connector,
            headers={"Accept-Encoding": "gzip, deflate"},
            trace_configs=[self._trace()])

    def _trace(self):
        tc = aiohttp.TraceConfig()
        tc.on_request_exception.append(
            lambda s, ctx, p: logger.error(f"请求异常 {p.url}: {p.exception!r}"))
        return tc

    async def _download_one(self, url):
        name = url.rsplit("/", 1)[-1]
        done = 0
        for attempt in range(self.max_retry):
            try:
                async with self.sem:                 # 令牌：限制并发
                    headers = {"Range": f"bytes={done}-"} if done else {}
                    async with self.session.get(url, headers=headers) as resp:
                        resp.raise_for_status()      # 4xx 直接失败不重试
                        mode = "ab" if done else "wb"
                        with open(self.dest_dir + name, mode) as f:
                            async for chunk in resp.content.iter_chunked(64 * 1024):
                                f.write(chunk); done += len(chunk)
                logger.info(f"完成 {name} ({done} bytes)")
                return name, done
            except aiohttp.ClientResponseError:
                logger.error(f"{name} HTTP {resp.status}，不重试"); return name, -1
            except (aiohttp.ClientError, asyncio.TimeoutError):
                backoff = min(2 ** attempt, 10) + random.uniform(0, 0.5)  # 退避+抖动
                logger.warning(f"{name} 第{attempt+1}次失败，{backoff:.1f}s 后重试")
                await asyncio.sleep(backoff)
        return name, -1

    async def run(self):
        results = await asyncio.gather(*(self._download_one(u) for u in self.urls))
        ok = sum(1 for _, n in results if n > 0)
        logger.info(f"成功 {ok}/{len(results)}")
        await self.session.close()                   # 收尾：关连接池

if __name__ == "__main__":
    urls = [f"https://mirror.example.com/files/{i}.bin" for i in range(50)]
    asyncio.run(ConcurrentDownloader(urls).run())
```

验收三问：**并发受限吗**——Semaphore + limit_per_host 双限流，不会打死对端；**断点续传吗**——Range 头 + 追加写，失败重试从断处继续；**失败可观测吗**——loguru 每条完成/失败/重试留痕，异常钩子兜底。这就是「生产级」与「脚本」的分界线。

## 2. 生产配置模板与纪律清单

**超时**：`ClientTimeout(total=60, connect=10, sock_read=30)` 起步，按对端 SLA 调 total。**并发**：Semaphore 与 `limit_per_host` 取压测拐点的一半。**重试**：连接/超时/5xx 才重试，指数退避 + 抖动，3-5 次封顶，全局限流包住重试。**安全**：版本 ≥3.14.0（两个 CVE），敏感 Cookie 走 headers，`CookieJar.load()` 只吃自己写的文件。**日志**：loguru 结构化，TraceConfig 挂请求耗时，access log 统计 5xx/P99。**资源**：session 全局复用、`on_cleanup` 关闭、下载流式落盘、WS 心跳 30s。

**从脚本到生产的演进路径**，不要一步到位：第一版能跑（脚本 + 打印）→ 第二版加限流与超时（Semaphore + ClientTimeout）→ 第三版加重试与断点（退避 + Range）→ 第四版加观测（loguru + TraceConfig）→ 第五版进服务（测试 + 部署 + 监控）。每一版都有明确验收点，避免「一开始就想完美」导致永远写不完——生产能力是在一次次的「能跑」之上叠出来的。

**生产事故复盘清单**：每次线上出问题，按「现象 → 根因 → 修法 → 防止再犯」四步复盘，四个问题里最容易漏的是最后一步——加一条测试或检查项，把「这次踩的坑」固化成「下次自动挡住」。复盘结论写进项目文档，而不是只存在于聊天记录；三个月后你会得到一份属于自己的故障地图，比任何教程都有价值。这套方法论与 [[../../强烈推荐（做项目必用，简历加分）/loguru/00-loguru总览|loguru]] 体系的日志治理是配套的：日志留痕是复盘的材料，复盘是日志的产出。

## 3. 报错速查十条

| 报错 | 含义 | 处理 |
|------|------|------|
| `ClientConnectorError` | 连不上（DNS/拒绝/超时） | 查目标可达性，可重试 |
| `ClientConnectionResetError` | 连接被重置 | keep-alive 失效常见，自动重试 |
| `ClientResponseError: 429` | 对端限流 | 读 Retry-After，退避后重试 |
| `ClientResponseError: 404/400` | 对端明确拒绝 | 不重试，查 URL/参数 |
| `TimeoutError` | 四段超时之一命中 | 看是 connect 还是 sock_read，调对应段 |
| `ClientPayloadError` | 响应体不完整 | 传输中断，可重试 |
| `ValueError: Unsupported URL` | URL 协议不支持 | 检查 `http(s)://` 前缀 |
| `WSServerHandshakeError` | WS 握手失败 | 查路径/协议，服务端返回了非 101 |
| `RuntimeError: Event loop is closed` | 循环重复使用 | 统一 `asyncio.run` 入口 |
| `DeprecationWarning: BasicAuth` | 用了弃用 API | 换 `encode_basic_auth` |

## 4. 面试三范式

**价值式**：「我在爬虫项目中用 aiohttp 把 10 万 URL 的抓取从 2 小时压到 8 分钟——信号量限流 50 并发，指数退避应对 429，断点续传扛住中断，成功率从 92% 提到 99.7%。」——先讲收益数据，再讲手段。

**技术式**：「aiohttp 是 asyncio 原生实现，`await` 让出控制权给事件循环；连接池复用 TCP 连接；Semaphore 限流、TaskGroup 管理生命周期；服务端处理函数是协程，万级连接不爆线程。」——原理要讲到「让出控制权」这一层，别停在「它很快」。

**生产式**：「超时四段独立设，sock_read 防吊死；重试只对连接/超时/5xx，退避加抖动防风暴；版本锁 3.14.0+ 因为两个 CVE；Cookie 敏感信息走 headers。」——安全与运维意识是区分度所在。

**追问四连**：为什么不用 httpx？（双件套、WebSocket、与 asyncio 深度绑定）｜并发 1000 时连接池怎么配？（limit=100 排队背压 + limit_per_host）｜服务端怎么扛住推送峰值？（全异步 + 中间件限流 + 心跳管理）｜怎么保证测试不碰真网络？（aioresponses mock + TestClient 整栈测试）。

## 5. 简历呈现

项目经历写法：「基于 aiohttp 的异步数据采集管道——10 万级 URL 并发抓取，信号量限流 + 指数退避重试 + Range 断点续传，成功率 99.7%；服务端用 aiohttp 自建推送网关，WebSocket 心跳保活，单机支撑 2 万长连接；pytest-aiohttp + aioresponses 全覆盖测试。」技能栏：「Python 异步编程（asyncio/aiohttp/uvloop），异步 HTTP 客户端与服务端。」——量化 + 技术名 + 工具链，三要素齐。
