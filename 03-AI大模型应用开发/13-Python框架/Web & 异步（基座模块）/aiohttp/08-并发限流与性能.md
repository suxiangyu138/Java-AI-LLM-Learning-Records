## 1. 并发编排三原语

**批量并发**：`asyncio.gather` 一把梭。注意失败语义——默认一个异常整体炸掉；`return_exceptions=True` 时各结果保留异常，方便逐条统计成功失败。

**结构化并发**：`asyncio.TaskGroup`（3.11+）是 2026 年的标准答案。组内任一任务抛异常，组内所有任务被取消，异常在 `async with` 退出时统一抛出——不会出现「一个挂了，其余还在傻跑」的泄漏。

**并发限制**：`asyncio.Semaphore` 是唯一的限流原语。组合姿势：

```python
sem = asyncio.Semaphore(50)          # 同时最多 50 个请求

async def bounded_fetch(session, url):
    async with sem:                  # 排队等令牌
        async with session.get(url, timeout=...) as resp:
            return await resp.json()

results = await asyncio.gather(*(bounded_fetch(session, u) for u in urls))
```

Semaphore 是**令牌发放**而非队列——拿不到令牌的协程原地挂起等待，不会丢弃请求。这正是爬虫与批量 API 调用的标准骨架：一万个 URL、并发 50、一个循环跑完。

## 2. 限流三件套

**应用层限流用 Semaphore**——控制「同时发起的请求数」，是业务视角的并发上限。**连接层限流用 TCPConnector 的 limit**——控制「实际建立的连接数」，是 TCP 视角的硬上限。两者配合：Semaphore 管逻辑并发，limit 管物理连接，任意一层先到先截。

**对端限流（服务端 429）用退避**——第三件套。爬虫/批量调用被 429 后必须尊重 `Retry-After` 头（见 [[../../../12-Python爬虫/阶段%204：反爬基础（高频遇到）/00-阶段4总览|爬虫反爬体系]] 的 429 应对）。三件套缺一不可：只有 Semaphore 没有 limit，连接还是会被打爆；只有 limit 没有 Semaphore，业务层排队状态不可见。

**动态限流的进阶**：对端限流阈值未知时，用「梯度探测」——从并发 10 起步，观测成功率和 P99，逐步加压直到成功率下降，取拐点作为上限。这是限流参数唯一靠谱的确定方式，比抄教程数字强一个量级。

## 3. 背压：异步的自我保护

背压（backpressure）指「下游处理不动时，上游放慢供给」的机制。aiohttp 里有两层自然背压：连接池满时新请求**排队等待**（sock_connect 超时兜底）；流式下载时 `iter_chunked` 的消费速度决定读盘速度，不消费就不读。

但背压不是自动的：`gather` 一万个任务时，一万个协程对象同时创建，全部挂着等令牌——内存与调度压力先于连接压力到来。所以**生产者端也要限流**：不要一次性创建全部任务，用「滑动窗口」——维护一个 `set` 存运行中的任务，满了就等最快的那个完成再补（`asyncio.wait(..., return_when=FIRST_COMPLETED)`）。这是百万级 URL 批量任务的正确姿势，也是 AI 批量推理调度的通用骨架。

## 4. 重试策略

**什么值得重试**：连接失败（`ClientConnectionError`）、超时（`TimeoutError`）、5xx（对端临时故障）。**什么不值得**：4xx（客户端错误，重试也是同一结果）、DNS 永久失败、TLS 校验失败（修配置而不是重试）。

**指数退避 + 抖动**：`sleep = min(base * 2**attempt, cap) + random.uniform(0, 0.5)`——退避防「同步风暴」（所有失败请求同一时刻重试，再打爆对端），抖动防「固定周期撞车」。base=1s、cap=30s、最多 3-5 次是常见基线。

**重试风暴的血案**：100 个请求同时失败同时重试 3 次，对端压力瞬时 300——雪崩的经典起点。生产铁律：**全局限流器必须在重试之上**（Semaphore 包住整个重试循环），重试退避加抖动，重试次数封顶。批量场景再做「错峰」：把请求均匀撒在时间轴上而非集中在启动瞬间。

**幂等性检查**：重试前确认请求幂等——GET 天然安全；POST 重试可能重复创建资源，要么带 `Idempotency-Key` 头（服务端支持时），要么「先查询再创建」的补偿逻辑。

## 5. 性能加速清单

按收益从大到小排列：

**装 `aiohttp[speedups]`**。llhttp C 解析器 + aiodns 异步 DNS + Brotli/zstd 解码 + cchardet 编码检测，整体吞吐提升 2-5 倍，DNS 并发场景提升更明显。装完 `aiohttp.__http_impl__` 确认是 `c_impl`。

**uvloop**（非 Windows）。事件循环替换，请求收发本身快 2-4 倍，`uvloop.install()` 一行。

**orjson 替代 json**。响应解析：`resp.json(loads=orjson.loads)`（`json_serialize`/`loads` 参数）；WS 消息用 `decode_text=False` + orjson（06 篇）。大 JSON 场景收益数倍。

**复用一切**。session 全局复用（04 篇）、连接池命中、DNS 缓存 `ttl_dns_cache` 调大——重复建拆的开销远大于单次请求本身。

**压缩**。`headers={"Accept-Encoding": "gzip, deflate, br, zstd"}` 让对端发压缩体，网络传输减半——但注意压缩解压是 CPU 活，本机 CPU 吃紧时反而更慢，压测后取舍。

**降并发看拐点**。并发 50 与并发 500 吞吐可能相同，但延迟与失败率翻倍——不是并发越高越好，压测找拐点（见下节）。

## 6. 压测方法论

压测的结论要能指导决策，四个步骤：

**第一步，定目标**。本机与对端分开测：测 aiohttp 自身性能打本机/局域网服务；测对端承受力才打真服务（且有负载顾虑）。

**第二步，变并发梯度**。10 → 50 → 100 → 200 → 500，记录每档的：吞吐（完成数/秒）、P50/P95/P99 延迟、失败率。

**第三步，找拐点**。吞吐停止上升或延迟开始陡增的并发值，就是生产上限的参考值；留 50% 余量作生产配置（压测 200 拐点 → 生产限 100）。

**第四步，注意干扰**。同一进程里 `time.sleep`、日志同步写、`print` 都会污染数据；压测用 `asyncio.run` + `time.monotonic()` 计时，日志走异步或收集后统一打。

一个可复用的压测骨架：URL 列表 × N 并发梯度，Semaphore 限流 + gather 收集，输出每档的三指标。结论用「本机 100 并发 500 请求 3.2s，P99 120ms」这样的量化描述，而不是「很快」。

## 7. 常见坑

**坑一：Semaphore 放循环里重建**。每轮 `asyncio.Semaphore(50)` 新建——令牌池每轮重置，等于没限流。

**坑二：重试不带退避**。失败立即重试，对端还没缓过来，连环失败。

**坑三：`gather` 无上限**。十万 URL 一次性 gather——协程对象全建、内存涨、事件循环调度压垮，必须滑动窗口。

**坑四：压测打生产服务**。真流量负载叠加压测流量，线上 P99 飙升——压测前确认目标环境。

**坑五：并发拉满以为更快**。500 并发比 50 并发慢的常见原因：DNS 排队、连接池争抢、对端限流——拐点压测说话。

**坑六：`print` 进请求循环**。同步 print 是 GIL 锁 + 终端 IO，高频请求下每秒几万次 print 直接把事件循环拖垮——日志走 loguru 异步（[[../../强烈推荐（做项目必用，简历加分）/loguru/00-loguru总览|loguru 篇]]）或收集后批打。
