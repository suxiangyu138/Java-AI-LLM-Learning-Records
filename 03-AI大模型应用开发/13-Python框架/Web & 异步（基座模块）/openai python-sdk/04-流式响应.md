## 1. 流式的价值：首 token 延迟

对话应用**必须流式**，理由不是"炫技"而是产品指标：

**其一，首 token 延迟（TTFT）**——LLM 生成一段 500 token 的回答可能要 10-20 秒，**不流式用户要干等全部生成完**；流式下**第一个 token 几百毫秒就出来**，用户感知"模型在思考/在回答"——"**TTFT 是对话产品的第一体验指标，流式是它的实现方式**"。

**其二，长输出体验**——代码生成/长文写作场景，逐 token 显示让用户能**边看边打断**（停止按钮才有意义）——"**流式是把'等待'变成'对话'**"。

**其三，服务端节省**——不用缓存整个响应，内存与超时压力小——"**生产级对话应用，流式是默认值**"。

**选型判断**：**对话/问答类一律流式**（交互体验）；**后台任务（批量总结/离线处理）不必流式**（没人看中间过程，直接等完整结果）——"**流式是给'人看'的，不是给'机器跑'的**"；流式的额外成本：解析逻辑 + 前端配套（SSE 消费），值得为体验付。

## 2. chat 流式：delta 增量

```python
stream = client.chat.completions.create(
    model="gpt-5.2",
    messages=[{"role": "user", "content": "写一首关于春天的诗"}],
    stream=True,          # 关键开关
)
for chunk in stream:
    if chunk.choices[0].delta.content:     # 空判断！choices/delta 都可能为空
        print(chunk.choices[0].delta.content, end="", flush=True)
```

**流式返回的真相**：`stream=True` 时返回的是**生成器**，每个 chunk 是一个增量——**chunk 与 chunk 之间内容不重叠，拼接起来就是完整回答**。**空判断是第一课**：**`chunk.choices` 可能是空列表**（流结束的 chunk、usage 携带 chunk），`delta.content` 也可能是 `None`（只带 role 的 chunk）——**"直接取 .delta.content 不判断，流式必崩"**。

**stream_options 与 usage**：`stream_options={"include_usage": True}` 让最后的 chunk 带 usage 统计——"**要账单就把这个打开，不然流式调用的 token 统计要自己拼**"。

## 3. 增量组装：完整姿势

```python
def chat_stream(messages):
    full = ""
    stream = client.chat.completions.create(
        model="gpt-5.2", messages=messages, stream=True,
        stream_options={"include_usage": True},
    )
    for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            piece = chunk.choices[0].delta.content
            full += piece
            yield piece                       # 逐段吐给前端
    # 循环结束后 full 就是完整回答（存库/记日志用）
    return full   # 生成器里不这么用——实际用外部变量收集
```

**三条纪律**：其一，**边 yield 边收集**——`full` 在循环外累积，流式输出与完整文本同时到手（前端显示 + 落库用）；其二，**yield 是生成器**——配合 FastAPI 的 StreamingResponse 直接转发（第 5 节）；其三，**结束信号**——`chunk.choices[0].finish_reason`（在某个 chunk 上非 None）是"流结束"的判定——"**拼接完整性靠 finish_reason 确认，不是靠'循环跑完'**"。

## 4. responses 流式：类型化事件

responses 的流式是**类型化事件**（不是裸 delta）：

```python
stream = client.responses.create(
    model="gpt-5.2",
    input="讲个笑话",
    stream=True,
)
for event in stream:
    if event.type == "response.output_text.delta":
        print(event.delta, end="", flush=True)
    elif event.type == "response.completed":
        print("\n[完成]", event.response.output_text)   # 结束事件自带完整文本
```

**事件三件套**：`response.output_text.delta`（文本增量）、`response.reasoning_text.delta`（推理过程增量，推理模型可见）、`response.completed`（完成事件，**自带完整 output_text**——不需要自己拼！）——"**responses 的类型化事件比 chat 的裸 delta 友好：事件类型就是语义，completed 直接给全文**"；工具调用场景监听 `response.output_item.done`（05 篇）。

## 5. 与 FastAPI 配合：SSE 转发

生产标配：**FastAPI 接请求 → SDK 流式 → SSE 转发给前端**：

```python
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.post("/chat")
async def chat(payload: dict):
    def gen():
        stream = client.chat.completions.create(
            model="gpt-5.2",
            messages=payload["messages"],
            stream=True,
        )
        for chunk in stream:
            if chunk.choices and chunk.choices[0].delta.content:
                yield f"data: {chunk.choices[0].delta.content}\n\n"   # SSE 格式
    return StreamingResponse(gen(), media_type="text/event-stream")
```

**SSE 三要素**：`data: 内容\n\n` 格式、`text/event-stream` 媒体类型、前端 `EventSource`/`fetch` 流式消费——"**后端一个生成器，前端一个事件流，对话体验就通了**"（FastAPI 体系 04 篇流式响应同源，`../FastAPI/04-流式响应与实时通信.md`）。

**流式的中断与取消**：前端用户点击"停止"——后端**生成器被中断**时，FastAPI 会向客户端发送取消信号；SDK 侧流式生成器支持手动关闭（`stream.close()`），停止后**不再向 API 拉取剩余 token**——"**用户中断 = 停止拉取 = 停止计费**"（LLM 按生成 token 计费，中断能省钱）；服务端还要处理"客户端断开后生成器继续跑"的泄漏——"**流式资源管理：用户走了，生成器要停，token 要省**"。

## 6. 异步流式

```python
from openai import AsyncOpenAI
aclient = AsyncOpenAI()

async def chat_async(messages):
    stream = await aclient.chat.completions.create(
        model="gpt-5.2", messages=messages, stream=True)
    async for chunk in stream:          # 异步迭代
        if chunk.choices and chunk.choices[0].delta.content:
            yield chunk.choices[0].delta.content
```

**要点**：AsyncOpenAI 与 OpenAI **同参构造、同 API**，只是 `await` + `async for`——"**同步版本跑通，异步版本是机械改写**"；**FastAPI 的 async 端点里必须用异步客户端**（否则阻塞事件循环，07 篇详讲）——"**Web 场景：AsyncOpenAI + async for 是标准姿势**"。

**流式与其他能力叠加**：流式 + 工具（05 篇：工具段缓冲、文本段流式）、流式 + 结构化（parse 不支持流式，先收全文再解析）、流式 + 多模态（图片输入同样流式）——"**叠加场景记一条主线：文本增量流式走，工具/结构等完整**"。

## 7. 常见坑

1. **不判断空 choices**——流结束 chunk 的 choices 为空列表，直接取下标崩。
2. **delta.content 为 None**——role chunk 不带内容；`if ... .content:` 判断。
3. **不用 finish_reason 确认结束**——靠"循环跑完"判断，最后一段可能没收到。
4. **流式不开 include_usage**——token 账单缺失，成本监控断档。
5. **responses 流式当 chat 写**——监听 `output_text.delta`/`completed` 事件，不是 choices。
6. **同步客户端跑在 async 端点**——阻塞事件循环；Web 场景用 AsyncOpenAI。
7. **SSE 格式写错**——漏 `data:` 前缀或 `\n\n` 分隔，前端解析失败。
8. **流式里做重试**——流中途失败要重连策略（09 篇）；简单场景先不做。
9. **前端不是事件流消费**——普通 fetch 拿不到增量；用 EventSource 或 fetch 的 ReadableStream 消费 SSE。
10. **流式拼全文只在内存**——长会话内存累积；需要持久化的场景边拼边落（存数据库/日志）。
