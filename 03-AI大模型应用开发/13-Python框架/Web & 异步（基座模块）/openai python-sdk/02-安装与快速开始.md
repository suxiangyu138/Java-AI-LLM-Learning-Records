## 1. 安装与验证

```bash
pip install openai==2.53.0    # 2026-08 基线，锁版本
```

```python
import openai
print(openai.__version__)     # 2.53.0
from openai import OpenAI
client = OpenAI(api_key="sk-...")   # 能建客户端即安装成功
```

**锁版本的理由**：2.x 约两周一个版本，且存在破坏性变更（Assistants 弃用、参数调整）——"教程 API 是 2.16 的，锁住版本才锁住行为"。**依赖说明**：SDK 底层用 httpx，自动安装；Pydantic 用于结构化输出（05 篇）。

## 2. API key 三姿势

**姿势一：环境变量（推荐）**——SDK 自动读 `OPENAI_API_KEY`，代码零配置：

```bash
# Windows PowerShell
$env:OPENAI_API_KEY = "sk-..."
# Linux/macOS
export OPENAI_API_KEY="sk-..."
```

```python
client = OpenAI()   # 自动读环境变量
```

**姿势二：构造参数（测试/多 key 场景）**——`OpenAI(api_key="sk-...")`；多供应商场景可配 `base_url`（DeepSeek/vLLM 等 OpenAI 兼容服务）：`OpenAI(api_key=..., base_url="https://api.deepseek.com")`——"**换 base_url 就是换供应商，语法零改动**"。

**姿势三：配置文件（生产）**——`from openai import OpenAI; client = OpenAI()` 配合部署环境的密钥管理（K8s Secret/云 KMS），**代码里永不出现 key 字符串**。

**安全红线**：**key 永不硬编码、永不进 git**（`.env` 进 `.gitignore`）；key 泄露 = 别人花你的钱——"**key 的保管纪律是 LLM 应用的第一安全课**"（09 篇详讲）。

## 3. Client 对象：进程内的单例

```python
client = OpenAI(
    timeout=60.0,           # 请求超时（默认 10 分钟较长，按场景收）
    max_retries=2,          # 重试次数（默认 2，指数退避）
)
```

**三条纪律**：其一，**Client 是重量级对象**——内部含连接池与重试器，**进程内创建一次、全局复用**（循环里新建 = 每次重建连接池）；其二，**timeout/max_retries 在构造时配好**——这是你的全局请求策略；其三，**多 key 场景建多个 Client**（每个 key 一个实例）——"**一个进程一个 Client，特殊情况（多 key/多供应商）按需多建**"。

## 4. 第一个对话

```python
client = OpenAI()
resp = client.chat.completions.create(
    model="gpt-5.2",                    # 模型名（gpt-5.x 系列，03 篇详讲）
    messages=[                          # 对话历史（角色 + 内容）
        {"role": "developer", "content": "你是严谨的技术助手。"},  # 系统指令
        {"role": "user", "content": "Python 的 GIL 是什么？"},
    ],
    temperature=0.7,                    # 采样温度（0-2，默认 1）
    max_completion_tokens=1024,         # 输出上限（o 系模型用这个，03 篇）
)
print(resp.choices[0].message.content)  # 回答文本
print(resp.usage)                       # CompletionUsage(tokens 统计)
```

**对话模型的心智**：**`messages` 是完整对话历史**——每次调用把全部上下文发给模型（无服务端状态，Responses API 例外，03 篇）；**角色三件套**：`developer`（系统指令，2026 新推荐）/`user`（用户）/`assistant`（模型回复，多轮对话要回填）——"**多轮对话 = 历史完整回放，不是增量**"。

**多轮对话示例**——把上一轮的 `assistant` 回复回填进历史，模型才有上下文：

```python
messages = [{"role": "developer", "content": "你是技术助手。"}]
messages.append({"role": "user", "content": "什么是 GIL？"})
resp = client.chat.completions.create(model="gpt-5.2", messages=messages)
messages.append({"role": "assistant", "content": resp.choices[0].message.content})  # 回填
messages.append({"role": "user", "content": "那它是怎么释放的？"})                  # 追问
resp2 = client.chat.completions.create(model="gpt-5.2", messages=messages)
```

**"不回填 assistant 消息，模型就'失忆'"**——追问/多轮场景的经典 bug；历史越长 token 越多，超长要截断/摘要（09 篇上下文治理）。

## 5. 响应结构解读

`resp` 是类型化对象，关键路径：

- **`resp.choices[0].message.content`**——回答文本（`choices` 是候选列表，默认 1 个）；
- **`resp.choices[0].finish_reason`**——结束原因：`"stop"`（正常）/`"length"`（截断）/`"tool_calls"`（要调工具，05 篇）/`"content_filter"`（被过滤）；
- **`resp.usage`**——token 账单：`prompt_tokens` / `completion_tokens` / `total_tokens`——**"每次调用都带回账单，成本监控从这开始"**（09 篇）；
- **`resp.model`**——实际使用的模型（路由场景确认用）。

**调试第一直觉**：**"结果不对先看 finish_reason 与 usage"**——`length` 说明输出被截断（调大 max_completion_tokens），token 异常说明历史回放有问题。

**usage 的四个字段**：`prompt_tokens`（输入）、`completion_tokens`（输出）、`total_tokens`（合计）、`cached_tokens`（缓存命中部分，09 篇 prompt caching 详讲）——"**每次调用自带账单，四字段全打点，成本监控从第一次调用开始**"；`resp.model` 字段在路由/代理场景用于确认实际命中模型——"**响应对象里带着全部事实，调试时先打印再下结论**"。

## 6. 快速调试三步

**第一步：冒烟对话**——一个 `user` 消息的极简调用，确认 key/网络/模型三件事通——"跑不通先查这三点"。

**第二步：看原始响应**——打印 `resp` 全文（类型化对象支持 repr），确认字段路径——"**响应结构以 SDK 实际输出为准，别凭记忆剥嵌套**"。

**第三步：边界验证**——空消息/超长消息/多轮回放各一次——"**正常跑通只证明 happy path，边界验证才证明生产可用**"；`finish_reason` 与 `usage` 一起看（第 5 节）。

**"跑通 + 会排查"两步一起到手才算上手**——报错先分三层：key/网络（401/连接错误）、请求（400 参数非法）、模型（404/不支持）——"**报错分层定位，五分钟内找到根因，是 SDK 上手的隐性标准**"。

## 7. 常见坑

1. **key 硬编码/进 git**——泄露即被盗刷；环境变量 + .gitignore。
2. **循环里新建 Client**——连接池反复重建；进程内建一次。
3. **模型名写错**——`model not found` 报错；查账号可用模型列表。
4. **messages 结构拼错**——角色非法/缺 content 报 400；角色限 developer/system/user/assistant/tool。
5. **max_tokens 用在 o 系模型**——用 `max_completion_tokens`（含推理 token）。
6. **超时设置太短**——LLM 首 token 延迟可能 10s+，timeout 按场景放宽。
7. **不设 max_completion_tokens**——默认输出可能很长，成本失控；显式设上限。
8. **developer 与 system 混用不清**——2026 推荐 developer；存量 system 仍兼容，但新代码统一 developer。
9. **多轮不回填 assistant**——追问场景模型"失忆"；历史完整回放（第 4 节示例）。
