## 1. API key 安全

**key = 钱**——泄露的 key 会被盗刷（别人替你调用，账单归你）。生产纪律：

1. **永不入代码/仓库**——环境变量（`OPENAI_API_KEY`）或密钥管理（K8s Secret/云 KMS），`.env` 进 `.gitignore`——"**git 历史里的 key 比代码泄露更持久，已泄露的要吊销轮换**"；
2. **最小权限**——用项目级/组织级 key 而不是全局 key，必要时 Admin API keys 按端点限制（2.34.0 能力）——"**一个项目一个 key，一个 key 一种权限**"；
3. **轮换与审计**——定期轮换、监控用量异常（账单突增 = 泄露信号）、`usage` 打点进监控——"**key 管理是 LLM 应用的第一安全课，不是运维细节**"。

## 2. 错误处理体系

SDK 的**类型化异常**是生产代码的分支依据：

```python
from openai import (
    APIConnectionError,    # 网络层：连不上/超时
    RateLimitError,        # 429：限流
    APIStatusError,        # 4xx/5xx 基类
    AuthenticationError,   # 401：key 错误
    NotFoundError,         # 404：模型/端点不存在
)
try:
    resp = client.chat.completions.create(...)
except RateLimitError:
    # 限流：退避重试或降级（03 节）
    raise
except AuthenticationError:
    # key 问题：告警（人处理）
    raise
except APIConnectionError:
    # 网络：退避重试（SDK 已自动做 2 次）
    pass
```

**错误处理三原则**：其一，**按类型分支，不按消息文本匹配**——异常类就是语义；其二，**可重试的（连接/429）交给 SDK 自动重试或业务重试，不可重试的（401/400/404）直接告警**——"重试是给暂时性问题的"；其三，**5xx 是服务端问题**——退避重试或降级供应商（06 节）。

## 3. 限流治理

**限流维度**：RPM（每分钟请求数）与 TPM（每分钟 token 数）——**账号级别共享**，多进程/多服务并发时都要算进额度。429 的处理链：

1. **预防**：信号量限流（07 篇）——**并发贴着额度跑，别撞墙**；
2. **退避**：SDK 默认自动重试 2 次（指数退避），**高并发下手动控制重试**（`max_retries` 调小，避免重试风暴放大）；
3. **降级**：429 持续时切备用模型（大模型 → min 版）或备用供应商（06 节）——"**限流治理 = 预防（信号量）+ 退避（指数）+ 降级（备胎）三层防线**"。

**监控指标**：429 率（应趋近 0）、重试次数、额度使用率（TPM 剩余）——"**429 率是限流治理的唯一裁判**"。

## 4. 成本治理

LLM 成本 = **token 数 × 单价**，治理四板斧：

**其一，prompt caching（缓存命中）**——对话前缀（system prompt + 工具定义）稳定时**自动命中缓存**，缓存 token 价格约为输入价 1/10：`cached_tokens` 出现在 usage 里就是命中——"**前缀稳定 = 缓存命中 = 输入成本降 90%**"；Responses API 的缓存命中率比 chat 提升 40-80%（03 篇）。

**其二，模型选型**——"重任务上大模型，高频任务上 min 版"；`responses` 的 `fast tier`（2.51.0 起）低延迟场景付费通道——"**按任务分级配模型，是成本治理的第一板斧**"。

**其三，批量与上下文**——批量请求（Batching API）离线任务降 50%；历史只回放必要窗口（超长对话截断/摘要）——"**每个 token 都是钱：不带无关历史**"。

**其四，监控与预算**——`resp.usage` 全量打点（prompt/completion/cached 分开记）、按用户/项目/功能记账、预算告警——"**成本治理的前提是可见：usage 打点是第一步**"。

## 5. 可观测性

生产 LLM 服务要看到**三层**：

1. **调用日志**——模型/延迟（TTFT 与总时长）/token（usage）/费用（换算）/错误类型——"**每次调用一条日志，字段固定**"（loguru 体系结构化日志同源）；
2. **指标**——QPS、延迟 p95、429 率、错误率、成本/天——"**指标进监控面板，告警在阈值**"；
3. **追踪**——trace_id 贯穿"用户请求 → 多轮工具调用 → 每次 LLM 调用"，出问题能回放完整链路——"**LLM 应用排查 = 找到那条 trace，重放那几轮调用**"（与 Python 异步 + FastAPI 体系的追踪中间件同源）。

**最少闭环**：日志（结构化）+ 指标（429/延迟/成本）+ trace（trace_id）——"**三样没有一样，生产 LLM 服务等于盲飞**"。

## 6. 多供应商降级

**OpenAI 故障/限流时要有备胎**——SDK 的 `base_url` 让切换成本极低：

```python
# 备用：兼容服务（DeepSeek/vLLM/Ollama 等 OpenAI 兼容端点）
fallback = OpenAI(
    api_key=os.environ["FALLBACK_KEY"],
    base_url=os.environ["FALLBACK_URL"],   # 如 https://api.deepseek.com
)
```

**降级三原则**：其一，**只降级不混用**——正常走主供应商，429/5xx 连续触发才切备胎；其二，**模型能力对齐**——备胎模型的参数（temperature/max_completion_tokens）与主模型兼容；其三，**降级留痕**——每次降级记日志，统计降级率——"**降级是生产 LLM 服务的保险丝：主路断了，备胎顶上，日志记录一切**"。**规模化场景换 LiteLLM**（多供应商统一网关，02 篇分工）——"**单项目 base_url 切换够用，多供应商治理上 LiteLLM**"。

## 7. 常见坑

1. **key 进 git**——永久泄露；吊销轮换 + .gitignore。
2. **按错误消息文本匹配**——API 文案会变；用类型化异常。
3. **重试 400/401**——无意义重试浪费额度；只重试连接/429/5xx。
4. **高并发不设信号量**——429 风暴 + 重试放大。
5. **不看 cached_tokens**——缓存命中不自知；usage 里三个字段分开记。
6. **历史全量回放**——超长对话 token 爆炸；截断/摘要窗口。
7. **无降级方案**——OpenAI 抖动 = 服务全挂；base_url 备胎。
8. **无 usage 打点**——成本不可见，账单来了才慌。
