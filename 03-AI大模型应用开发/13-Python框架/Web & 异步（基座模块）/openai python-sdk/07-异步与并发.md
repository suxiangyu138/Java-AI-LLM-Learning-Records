## 1. AsyncOpenAI：同参构造的异步双胞胎

```python
from openai import AsyncOpenAI
aclient = AsyncOpenAI()          # 构造参数与 OpenAI() 完全一致

resp = await aclient.chat.completions.create(
    model="gpt-5.2",
    messages=[{"role": "user", "content": "你好"}],
)
```

**"AsyncOpenAI 与 OpenAI 是同一套 API 的异步版本"**——构造参数（api_key/timeout/max_retries）一致、方法一致、响应结构一致，只是调用加 `await`、流式改 `async for`（04 篇）——"**同步版本跑通，异步版本是机械改写**"。**两个客户端可以并存**：同一进程 `OpenAI()` 与 `AsyncOpenAI()` 各建一个，同步任务与异步任务各用各的。

## 2. 并发收益：IO 密集的吞吐钥匙

**LLM 调用是 IO 密集任务**——请求发出后 90% 时间在等网络与模型生成，CPU 闲置。异步并发让**多个请求在等待期并行推进**：

```python
import asyncio

async def ask_one(q):
    resp = await aclient.chat.completions.create(
        model="gpt-5.2", messages=[{"role": "user", "content": q}])
    return resp.choices[0].message.content

async def main():
    questions = ["问题1", "问题2", ...] * 10     # 几十个任务
    results = await asyncio.gather(*(ask_one(q) for q in questions))
    return results
```

**收益的量化**：单个请求 5 秒，串行 10 个 = 50 秒；**并发 10 个 ≈ 5-8 秒**（视限流）——"**并发不是'加速单个请求'，是'摊薄等待时间'——IO 密集场景的吞吐钥匙**"。

**注意**：并发收益有上限——**API 速率限制（RPM/TPM）是天花板**（09 篇限流治理）——"**并发要贴着限流跑，不是无脑拉满**"。

**同步场景的并发替代**：没有 async 环境的脚本/批处理，可用**线程池**跑同步客户端（`concurrent.futures.ThreadPoolExecutor`）——SDK 的同步调用会释放 GIL（底层 httpx 是 IO 等待），线程池同样能吃满吞吐；但**Web 服务里禁用线程池跑 LLM**（线程数爆炸）——"**脚本用线程池，Web 用 AsyncOpenAI，场景决定姿势**"。

## 3. 批量并发与限流

**无脑 gather 会撞限流**——429 风暴。正确姿势：**信号量限流 + 分批**：

```python
sem = asyncio.Semaphore(10)          # 同时最多 10 个在飞请求

async def ask_limited(q):
    async with sem:                   # 超出的等待
        resp = await aclient.chat.completions.create(...)
        return resp.choices[0].message.content

async def main():
    results = await asyncio.gather(*(ask_limited(q) for q in all_questions))
```

**限流纪律**：其一，**信号量上限 ≈ API 限流值 × 0.8**（留缓冲）；其二，**大批量分批**——1000 个任务分 10 批 × 100，每批 gather 后落库（配合 06 篇嵌入批量）；其三，**429 要退避**——SDK 自动重试（默认 2 次指数退避），但**高并发下重试会放大风暴**，信号量是最有效的防线——"**并发与限流是跷跷板：信号量把它压在你想要的高度**"。

**批量处理场景**（离线评估/批量问答/批量嵌入）：`asyncio.gather` 批量 + 信号量 + 分批落库——"**离线批量是异步并发的主场：吞吐上量级，成本也上量级——先小批验证**"。

## 4. 超时与重试

异步场景的超时/重试在**构造时配置**（全局）或**调用时覆盖**：

```python
aclient = AsyncOpenAI(
    timeout=30.0,        # 全局超时
    max_retries=2,       # 全局重试（连接错误/429 自动）
)
# 单次覆盖
resp = await aclient.chat.completions.create(
    model="gpt-5.2", messages=..., timeout=60.0)
```

**三层超时心智**：其一，**连接超时**（默认较短）——服务不可达快速失败；其二，**请求超时**（`timeout` 参数）——**LLM 场景要放宽**（首 token 可能 10s+，长生成可能 60s+）；其三，**整体上限**——业务层兜底（如 120s 掐断）。**重试纪律**：连接错误与 429 可重试（SDK 自动），**业务错误（400/404）不重试**——"**重试是给'暂时性问题'的，不是给'请求写错'的**"。

**并发任务的错误隔离**：`asyncio.gather` 一个任务异常会**整体抛错**（其他任务的返回丢失）——正确姿势是 `gather(..., return_exceptions=True)` 逐个检查结果，失败任务单独重试/记录：

```python
results = await asyncio.gather(*(ask_limited(q) for q in questions), return_exceptions=True)
for q, r in zip(questions, results):
    if isinstance(r, Exception):
        failed.append(q)        # 失败清单，稍后重试
    else:
        ok_results.append(r)
```

**"批量并发任务 = 结果逐个检视，失败进清单重试——一锅端抛错是批处理的天敌"**。

**asyncio 基础三件套**（FastAPI 体系 03 篇同源）：`async def` 定义协程、`await` 等待结果、`asyncio.gather` 并行编排——SDK 的异步用法不引入新概念，**就是这三个语法的 LLM 落地**——"**会 asyncio 就会 AsyncOpenAI，SDK 只是把 IO 换成了模型调用**"；**掌握路径建议**：先在同步客户端把业务逻辑写对（调试友好），再机械改写成异步（await/async for），最后叠加并发与限流——"**同步跑对、异步提速、并发限流收尾，三步走不跳步**"。

## 5. 与 FastAPI 配合

**FastAPI 的 async 端点必须用异步客户端**——同步调用会**阻塞事件循环**，整个服务卡住：

```python
from fastapi import FastAPI
from openai import AsyncOpenAI

app = FastAPI()
aclient = AsyncOpenAI()            # 模块级单例

@app.post("/chat")
async def chat(payload: dict):
    resp = await aclient.chat.completions.create(
        model="gpt-5.2", messages=payload["messages"])
    return {"answer": resp.choices[0].message.content}
```

**"async 端点 + await 调用 = 请求期间事件循环继续服务其他请求"**——同步客户端在 async 端点里是并发事故（一个慢请求拖住全部）；流式场景用 `async for` + StreamingResponse（04 篇）——"**Web 服务的心智：async def 端点 + AsyncOpenAI + await——三步缺一不可**"（FastAPI 体系 03 篇异步编程同源）。

## 6. 常见坑

1. **同步客户端跑在 async 端点**——阻塞事件循环，全员等待；用 AsyncOpenAI。
2. **忘 await**——返回协程对象而非结果；`resp = await ...`。
3. **无信号量 gather 大批量**——429 风暴 + 重试放大；信号量限流。
4. **超时设置太短**——长生成被掐断；timeout 放宽 + 业务层兜底。
5. **重试业务错误**——400/404 重试无意义；只重试连接/429。
6. **同步异步混用同任务**——同一逻辑别 sync/async 两套写法；选一条路。
7. **并发任务不落库**——结果只存在内存，进程重启全丢；分批 gather 后落库。
8. **gather 全量构造协程**——1 万个任务一次性 gather 内存爆炸；分批（如 100 一批）逐批 gather。
9. **信号量设成限流值**——没有缓冲余量；0.8 系数留抖动空间（第 3 节）。
