## 1. 类型即 schema

pydantic 的核心机制：**每个类型注解都被编译成一份"核心 schema"**——Rust 核心按 schema 校验。所以**"类型注解的质量 = 校验质量"**：`str` 是"任意字符串"、`str = Field(min_length=1, max_length=100)` 是"1-100 字符"、`Literal["pending", "done"]` 是"三个词之一"。**写类型注解时要想的不是"类型对了没有"，而是"这份数据契约声明完整了吗"**——契约声明得越细，错误拦截越早，下游代码越不用防御。pydantic 的编译器还会自动生成 JSON Schema（`model_json_schema()`）——**一份注解，三种用途（校验/序列化/接口声明）**。

## 2. 内置类型与常用组合

**基础类型**：`str`/`int`/`float`/`bool`/`bytes`/`Decimal`——注意 pydantic 对基础类型做**智能转换**（"18"→18、"true"→True、float→int 截断）；**容器类型**：`list[T]`/`set[T]`/`dict[K, V]`/`tuple[T, ...]`——元素类型也校验（`list[int]` 里的 "3" 会被转成 3）；**结构类型**：`str | None`（可空）、`list[dict]`（裸 dict 容器）、`dict[str, Any]`（任意内容，只要求键是字符串）。

**类型选择的三条主线**：其一，**能用具体类型不用 Any**——`Any` 是"不校验"，用一次就漏一次；其二，**数字用 Decimal 还是 float**——金额/精度敏感场景用 `Decimal`（浮点误差），一般统计用 float；其三，**大文本/二进制场景用 bytes**——文件上传、消息体场景省去字符串编码往返。

**时间类型**（datetime/date/time）：pydantic 自动解析 ISO 8601 字符串——`"2026-08-10T12:00:00"` → datetime 对象——**外部时间字符串进模型即变对象**，业务层直接比较运算，不用手动 strptime（07 篇还有 PastDatetime/FutureDatetime 语义类型）。

## 3. Field：字段级约束

```python
from pydantic import BaseModel, Field

class Product(BaseModel):
    sku: str = Field(min_length=3, max_length=32, pattern=r"^[A-Z]{2}-\d+$")
    price: float = Field(gt=0, le=100000)        # 范围约束
    qty: int = Field(default=0, ge=0)            # 默认值 + 下界
    tags: list[str] = Field(default_factory=list, max_length=10)  # 可变默认
    note: str | None = Field(default=None, description="备注")    # 文档字段
```

**Field 参数分组**：**约束类**——`min_length/max_length`（字符串与容器）、`pattern`（正则）、`gt/ge/lt/le`（数值）、`multiple_of`；**默认值类**——`default`、`default_factory`（可变默认必用）；**元数据类**——`alias`（字段别名）、`description`（进 JSON Schema，AI 工具描述的场景尤其重要，09 篇）、`title`、`examples`。**约束的组合逻辑**：同一字段可叠多条，**全部满足才通过**（与或逻辑用 Annotated 与联合类型表达）。

## 4. Annotated：现代约束写法

```python
from typing import Annotated
from pydantic import BaseModel, Field, StringConstraints

# 写法一：Field 嵌入（字段定义处约束）
class A(BaseModel):
    name: str = Field(min_length=1)

# 写法二：Annotated 组合（推荐：类型与约束一起复用）
Name = Annotated[str, Field(min_length=1, max_length=50)]
class B(BaseModel):
    name: Name          # 直接复用
    display_name: Name  # 同约束复用第二处

# 写法三：StringConstraints（字符串专用约束）
Code = Annotated[str, StringConstraints(min_length=4, pattern=r"^\d{4}$")]
```

**Annotated 是 v2 的现代姿势**：把"类型 + 约束"打包成一个可复用的类型别名——**约束跟着类型走，而不是跟着字段走**——多处字段共享同一套规则时，改一处全生效。**组合顺序**：`Annotated[T, 约束1, 约束2]` 按顺序应用，多个 Annotated 可以叠加（如先正则再长度）。**推荐规则：单个字段用 Field，跨字段复用的规则用 Annotated 别名**（FastAPI 的 Query/Path 也是 Annotated 风格——一脉相承）。

## 5. 嵌套模型与容器

```python
class Address(BaseModel):
    city: str
    zip: str = Field(pattern=r"^\d{6}$")

class User(BaseModel):
    name: str
    addr: Address                    # 嵌套模型：dict 自动转 Address
    friends: list[Address] = []      # 容器里的模型元素
    meta: dict[str, str] = {}        # 键值都是 str

u = User(name="x", addr={"city": "BJ", "zip": "100000"},
         friends=[{"city": "SH", "zip": "200000"}])
```

**嵌套是 pydantic 组织复杂数据的核心能力**：**外部进来的裸 dict 自动转成嵌套模型**（递归校验），错误路径是元组（`('friends', 0, 'zip')`——"friends 第 0 个的 zip 出错"），**定位精确到路径**。组织原则：**"三层以内用嵌套模型，超过三层拆成独立模型 + 引用"**——嵌套太深时校验错误路径难读，且 JSON Schema 膨胀。递归模型（树形结构）用 `model_rebuild()` 后向引用。

**Any 的边界**：`dict[str, Any]` 的 Any 只校验键不校验值——"**结构化外壳 + 自由内容**"的平衡写法（元数据/扩展字段场景常用）——注意"用了 Any 就断了该层校验"是它的代价，能用具体类型就不用。

## 6. 枚举与 Literal：取值白名单

```python
from enum import Enum
from typing import Literal

class Status(Enum):
    PENDING = "pending"
    DONE = "done"

class Task(BaseModel):
    status: Status              # 枚举：值必须是枚举成员
    level: Literal["low", "mid", "high"]   # 字面量：三个字符串之一
```

**两者都是"取值白名单"**，差别在形态：**枚举**给状态加名字（`Task.Status.DONE` 可读、可遍历），**Literal** 轻量直接（值就是字符串）。**选型主线**：状态机/多状态用枚举（序列化输出 `.value`），单一字段的固定取值用 Literal。**注意**：校验时传 `"pending"` 会**自动转成枚举成员**（`Task(status="pending").status is Status.PENDING`）——"校验即转换"在枚举上同样生效；Literal 配合 Union 可以做"按字段分派"（07 篇判别联合的基础）。

## 7. Union 的陷阱

`Union[A, B]`（写作 `A | B`）表示"任一类型"，但有两个经典陷阱：

**陷阱一：顺序即优先级**——pydantic **按声明顺序尝试**：`str | int` 时传 123 会被转成 "123"（str 先匹配），`int | str` 传 "123" 会被转成 123——**"宽松类型（str/Any）放后面，具体类型放前面"**是铁律。

**陷阱二：同构 Union 的歧义**——`list[int] | list[str]` 传 `["a", "b"]` 会匹配前者失败再匹配后者（慢且绕）；**v2 的 smart union（默认）会合并校验器先试**，但复杂 Union 仍建议显式判别（07 篇 Discriminated Union——按 tag 字段直接分派，快且错误信息好）。

**实用规则**：两三个简单类型用 `A | B | None` 没问题；**"按内容分派"的复杂联合（事件类型/消息类型）一律用判别联合**。

**None 的另一种写法**：`str | None` 里的 None 是"允许缺失"，与默认值 `= None` 配合时注意——**声明可空 ≠ 给了默认值**：可空字段缺失仍报错（除非显式 `= None`），两者语义不同。

## 8. 五个常见坑

- **坑一**：`list` 不写元素类型——校验等于没有；**容器必须带元素类型**；
- **坑二**：`Optional[str]` 与 `str | None` 混用老写法——功能相同，**2026 用 `| None` 风格**（3.10+ 语法）；
- **坑三**：`pattern` 写 Python 正则但不了解 Rust 正则差异——**pydantic 的正则在 Rust 里执行，look-around（后顾断言）不支持**（00 篇误区七）；
- **坑四**：可变默认值 `tags: list = []`——v2 直接报错，**用 `Field(default_factory=list)`**；
- **坑五**：Literal 传了枚举想做的事——两者不能互换使用场景；**白名单用哪个先想清楚再写**。
