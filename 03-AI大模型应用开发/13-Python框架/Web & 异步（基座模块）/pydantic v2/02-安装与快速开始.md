## 1. 安装与版本锁定

```bash
pip install "pydantic==2.13.3"
# 配置管理场景（07 篇）单独装
pip install "pydantic-settings==2.x"
# 可选：email/URL 等特殊类型支持
pip install "pydantic[email]"
```

**版本纪律**：pydantic 2.x 是稳定主线，**新项目锁 2.13.x**；Python 3.9 用户在 2.14 起被弃（2.14.0a1 已确认）——**开发环境至少 Python 3.10**。**注意 pydantic-core 已并入主仓库**：2026 年只需装 pydantic 一个包，不再有"core 版本与 python 版本不匹配"的经典问题。装完验证：

```bash
python -c "import pydantic; print(pydantic.__version__)"   # 2.13.3
```

装完顺手 `pip list | findstr pydantic`（Windows）/`grep pydantic`（Linux）确认**没有多个 pydantic 版本共存**——混装是疑难 bug 的常见来源。

## 2. 第一个模型：三行核心

```python
from pydantic import BaseModel

class User(BaseModel):
    name: str
    age: int = 18          # 默认值
    email: str | None = None  # 可空字段
```

**一个模型的三个事实**：其一，**类型注解即声明**——每个注解同时是"字段定义"与"校验规则"，`str` 要求字符串、`int` 要求整数并自动转换、`str | None` 允许缺失；其二，**构造即校验**——`User(name="x", age="20")` 把 "20" 转成 20，`User(name="x", age="abc")` 抛 ValidationError；其三，**模型是普通对象**——`user.name` 取属性、`user.age = 21` 可改值（默认允许，frozen 可锁，06 篇）、可嵌套（`class Team(BaseModel): users: list[User]`）。**记住：pydantic 模型 ≈ "类型注解写成的数据类 + 自动校验器"**。

**模型的类级别 API 也值得第一眼认识**：`User.model_fields`（字段元数据字典——调试、动态生成表单用）、`User.model_json_schema()`（生成 JSON Schema——FastAPI 文档与 LLM 工具声明的数据源，09 篇）、`User.model_rebuild()`（**前向引用/递归模型定义后重建**——`class Node(BaseModel): children: list["Node"]` 必须在定义后调一次 rebuild，否则运行时 NameError）。

## 3. 校验的三种入口

```python
# 入口一：构造（最常用）
u = User(name="x", age="20")              # dict 风格关键字参数

# 入口二：model_validate（从 dict/对象/JSON 加载）
u = User.model_validate({"name": "x", "age": 20})
u = User.model_validate_json('{"name": "x", "age": 20}')

# 入口三：TypeAdapter（任意类型的校验，07 篇）
from pydantic import TypeAdapter
ta = TypeAdapter(list[User])
users = ta.validate_python([{"name": "a"}, {"name": "b"}])
```

**选型主线**：**代码内构造用入口一、从外部数据（请求体/JSON/LLM 输出）加载用入口二、批量校验无模型容器用入口三**——`model_validate_json` 比 `model_validate(json.loads(...))` **快一个量级**（JSON 直接在 Rust 层解析，08 篇性能细节）。

**model_validate 的扩展来源**：除了 dict 和 JSON 字符串，还可以从**任意对象**（配 from_attributes，06 篇）和**另一个模型实例**校验构造——"数据源多样，校验逻辑不变"；**入口二还有细节**：`strict=` 参数可单次调用强制严格模式（06 篇）。

## 4. 错误处理：ValidationError 结构

```python
try:
    User.model_validate({"name": "x", "age": "abc"})
except pydantic.ValidationError as e:
    print(e.errors())   # [{'type': 'int_parsing', 'loc': ('age',), 'msg': 'Input should be a valid integer', 'input': 'abc'}]
    print(str(e))       # 人类可读的多行错误报告
```

**ValidationError 的三个设计**：其一，**聚合所有错误**——一次校验返回所有字段的所有错误，不是第一个错就停（FastAPI 的 422 响应就是它）；其二，**errors() 是结构化数据**——`type`（错误码）、`loc`（字段路径，嵌套模型是元组路径）、`msg`、`input`——**机器可解析，loguru 结构化日志直接吃**；其三，**错误码体系**——`int_parsing`/`string_type`/`missing`/`extra_forbidden`/`greater_than` 等，**按错误码分支处理比按 msg 字符串匹配可靠得多**。生产姿势：入口统一 try/except → 记日志（含 loc+type）→ 转业务错误码返回（10 篇）。

**错误的嵌套路径**：嵌套模型里 loc 是元组路径（`('items', 0, 'qty')`）——**定位精确到"哪个列表第几个的哪个字段"**，排查时按路径拆解，不用翻整段错误文本。

**调试第四步（进阶）**：怀疑"值对了但被校验拦了"时，先临时简化模型跑一次——"**校验规则是最后一个怀疑对象，因为它最显眼、也最容易被甩锅**"（04 篇排查）。

## 5. 序列化三件套

```python
# dict：进数据库/缓存/下游
data = u.model_dump()                 # {'name': 'x', 'age': 20}
data = u.model_dump(exclude_none=True)  # 排除空值字段

# JSON：出接口/落日志
json_str = u.model_dump_json()        # '{"name":"x","age":20}'

# 复制：改副本不动原对象
u2 = u.model_copy(update={"age": 30})  # 只改 age 的新对象
```

**三个细节**：其一，`model_dump` 返回 dict、`model_dump_json` 返回字符串——**v1 的 .dict()/.json() 已死，别混用**；其二，`model_copy(update=...)` 是"复制并修改"惯用法——**2026 的 2.14 起它只深拷贝被更新的字段，其余字段浅拷贝共享**（性能优化，行为对大多数场景无感）；其三，序列化方向还有 computed_field（计算字段，05 篇）与别名（by_alias，06 篇）。

**序列化的方向性**：model_dump 是"模型 → 数据"，model_validate 是"数据 → 模型"——**两者参数不对称**（dump 有 exclude/round_trip，validate 有 strict/context）——"**序列化与校验是两个独立规则面，别以为对称**"。

## 6. 完整闭环示例

```python
from pydantic import BaseModel, ValidationError
import json

class Order(BaseModel):
    order_id: str
    items: list[dict]
    total: float
    note: str | None = None

# 模拟外部输入（第三方 API / LLM 输出 / 前端请求）
raw = '{"order_id": "A1024", "items": [{"sku": "P1", "qty": 2}], "total": "99.9"}'

try:
    order = Order.model_validate_json(raw)     # 校验 + 转换（"99.9" → 99.9）
    print(order.total * 2)                     # 业务层拿到的是 float，直接算
    out = order.model_dump(exclude_none=True)  # 干净 dict 出库
    print(json.dumps(out, ensure_ascii=False))
except ValidationError as e:
    print(f"字段 {[err['loc'] for err in e.errors()]} 校验失败")  # 记录错误路径
```

**这个闭环就是 pydantic 的日常**：**外部字符串 → 强类型对象（业务直接用）→ 干净 dict（对外输出）→ 校验失败结构化上报**。配合 FastAPI 时，`model_validate_json` 这步由框架自动完成（请求体注解即校验），业务代码只看到模型（10 篇实战）。

**真实项目的最小骨架**（FastAPI 场景）——请求体注解 `def api(body: OrderInput)`：框架自动 model_validate_json → 校验失败自动 422 → 业务代码拿强类型对象——**业务函数里不用写任何 try/except**（10 篇实战）。

## 7. 八个常见坑

- **坑一**：`from pydantic import BaseSettings`——v2 起在 pydantic-settings 包（07 篇），直接 ImportError；
- **坑二**：字段名与 Python 关键字冲突（`class`/`type` 等）——用别名：`type_: str = Field(alias="type")`；
- **坑三**：可变默认值——`def f(): return []` 的写法在 pydantic 里不适用，**用 `Field(default_factory=list)`**（v2 对可变默认直接报错）；
- **坑四**：`model_validate` 传了 JSON 字符串——它是"dict 入口"，字符串请用 `model_validate_json`；
- **坑五**：捕获异常写成 `except Exception`——校验错误会被吞掉；**先捕 ValidationError 再捕 Exception**；
- **坑六**：Union 顺序——`str | int` 会把 123 变 "123"（03 篇）——**宽松类型放后面**；
- **坑七**：`model_dump()` 忘了 `exclude_none=True`——下游收到一堆 null 字段；
- **坑八**：Python 3.9 跑新代码——2.14 起直接不支持，**开发环境 3.10+**。
- **坑九**：嵌套字段给了裸 dict 类型（`addr: dict` 而非 `addr: Address`）——内部裸 dict 无人校验；**嵌套字段必须给模型类型**（03 篇）。
- **坑十**：前向引用写了但没调 model_rebuild()——运行时 NameError；**定义后调一次 rebuild**。
- **坑十一**：异常里捕到的是 pydantic_core 的 PydanticCustomError——**统一用 `e.errors()` 读取**，别依赖 msg 字符串（msg 随版本可能变化）。
- **坑十二**：`model_dump()` 后再 json.dumps 中文变 \uXXXX——**用 model_dump_json() 一步到位**（默认 ensure_ascii=False 输出 UTF-8）。
- **坑十三**：把类级 API 当实例方法用（`user.model_validate(...)`）——**类级 API（model_*）只在类上调用**，实例上只有属性与方法。
