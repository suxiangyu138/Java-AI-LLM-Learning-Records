## 1. 为什么需要校验器

类型注解能拦"形状错误"（类型不对、长度越界、取值越界），但**拦不了"语义错误"**：金额为负、结束时间早于开始时间、两个字段必须一致、字符串需要按业务规则清洗（去空格/去前缀）——**这些规则需要代码表达，校验器就是给字段/模型挂上自定义代码的钩子**。pydantic 的执行顺序值得先记住：**默认值填充 → 字段类型校验 → field_validator（after）→ model_validator（after）**——顺序决定"你在哪个阶段能拿到什么"（嵌套模型先内后外：先校验子模型再校验父模型）。

## 2. field_validator：字段级校验

```python
from pydantic import BaseModel, field_validator

class Order(BaseModel):
    amount: float
    coupon: str | None = None

    @field_validator("amount")
    @classmethod
    def amount_must_be_positive(cls, v: float) -> float:
        if v <= 0:
            raise ValueError("金额必须大于 0")
        return v

    @field_validator("coupon", mode="before")
    @classmethod
    def clean_coupon(cls, v: object) -> object:
        if isinstance(v, str):
            return v.strip().upper()      # 清洗：去空格 + 大写
        return v
```

**三个铁律**：其一，**必须 @classmethod**——v2 的校验器是类方法（v1 的实例方法时代结束），漏写直接报错；其二，**必须返回校验后的值**——返回 None 等于把字段清空了，return 的值才是最终值（before 模式返回值还会继续走类型校验）；其三，**抛 ValueError/AssertionError 表示校验失败**——pydantic 捕获后转成 ValidationError 的条目。**多字段可以共用一个校验器**：`@field_validator("a", "b")`。

## 3. 三种 mode：before / after / wrap

**mode="before"**——在类型校验**之前**运行：拿到的可能是任何类型（str/int/dict…），适合**清洗与转换**（去空格、解析原始格式、把字符串转对象）——"进来的东西先收拾干净再走类型检查"。

**mode="after"**（默认）——在类型校验**之后**运行：拿到的一定是正确类型，适合**语义校验**（金额正负、长度业务规则）与**派生逻辑**（校验后算个缓存值存私有属性）——"类型对了再谈业务"。

**mode="wrap"**——**包裹模式**：自己控制"要不要继续校验"，签名 `(v, handler, info)`——调 `handler(v)` 继续原流程，也可以绕过。**场景**：需要"先看上下文再决定走哪条校验路"的复杂逻辑，90% 的日常用不到，**知道存在即可**。

**选型主线**：**清洗用 before、语义校验用 after、需要截断/改写默认流程用 wrap**——90% 的代码只需要 before + after。

**before 与 after 的取值对比**：同一个字段 `" 18 "`——before 校验器先收到原始字符串（可以 strip 清洗），after 校验器收到 int 18（类型已转换）——"**想要原始输入去 before，想要可靠类型去 after**"；wrap 里 `handler(v)` 返回的也是"过完后续流程"的值。

## 4. model_validator：模型级校验

```python
from pydantic import BaseModel, model_validator

class Booking(BaseModel):
    start: int
    end: int

    @model_validator(mode="after")
    @classmethod
    def check_order(cls, m: "Booking") -> "Booking":
        if m.end <= m.start:
            raise ValueError("结束时间必须晚于开始时间")
        return m
```

**model_validator 解决"跨字段"问题**：两个字段单独都合法、合起来不合法（起止时间、总价 vs 明细、密码与确认密码）。**mode="after"**（默认）拿到**完整的模型实例**——直接读字段、比对、抛错，**必须返回模型本身**；**mode="before"** 拿到的是**原始 dict**——适合"多个原始字段合成一个新字段"（如把 `first_name`/`last_name` 合成 `full_name` 后喂给模型）。**v1 的 @root_validator 对应关系**：`@root_validator(pre=True)` → `@model_validator(mode="before")`、`@root_validator` → `@model_validator(mode="after")`——**换名字，换 mode 必须显式写**。

## 5. ValidationInfo：上下文

```python
from pydantic import BaseModel, field_validator, ValidationInfo

class Invoice(BaseModel):
    base: int
    tax_rate: float = 0.1
    total: int = 0

    @field_validator("total", mode="after")
    @classmethod
    def calc_total(cls, v: int, info: ValidationInfo) -> int:
        if v == 0:                      # 没传 total 时自动算
            return round(info.data["base"] * (1 + info.data["tax_rate"]))
        return v
```

**ValidationInfo 提供两个信息**：`info.data`（**已校验完成的字段值 dict**——before 模式里是原始值、after 模式里是类型校验后的值）与 `info.field_name`（当前字段名，可用于通用校验器）。**注意 2.13.2 修复过 field_name 在 model_validate_json 里缺失的问题**——用到就锁 2.13.3+。**用途**：跨字段计算、把"其他字段"的值纳入当前字段校验（如"amount 不能超过账户余额 balance"）。

## 6. Annotated 与校验器组合

```python
from typing import Annotated
from pydantic import BaseModel, field_validator, Field

def check_even(v: int) -> int:
    if v % 2:
        raise ValueError("必须是偶数")
    return v

EvenInt = Annotated[int, Field(gt=0), check_even]   # 约束 + 校验器打包

class Data(BaseModel):
    a: EvenInt
    b: EvenInt       # 复用同一套规则
```

**Annotated 里可以直接放校验函数**（不只是 Field）——**"规则打包成类型别名，处处复用"**是 v2 最优雅的组合模式：约束（Field）、校验器（函数）、元数据（description）全进一个类型别名。**工厂函数模式**：`def even() -> Annotated[int, ...]` 生成带参数的校验器（如"最大 N 的偶数"）——跨模型共享复杂规则的标准姿势。

## 7. v1 迁移对照

| v1（已退场） | v2（2026 写法） |
|------|------|
| `@validator("f")`（实例方法） | `@field_validator("f")` + `@classmethod` |
| `@validator("f", pre=True)` | `@field_validator("f", mode="before")` |
| `@root_validator` | `@model_validator(mode="after")` |
| `@root_validator(pre=True)` | `@model_validator(mode="before")` |
| `values` 参数（dict） | `ValidationInfo.data`（info.data） |
| `always=True` | 不需要（v2 校验器对默认值也运行） |
| 校验器改字段值（return 后字段更新） | **默认不可改**：after 模式字段已固定，改值用 wrap 或 model_validator |

**迁移最痛的三个差异**：其一，**classmethod 必须写**（不写直接报错）；其二，**after 模式不能改其他字段**（v1 可以，v2 里字段不可变语义——跨字段改写用 model_validator 或 info.data 只在计算时参考）；其三，**默认值也过校验器**（v1 的 always=True 是显式开关，v2 默认行为）——**老代码里"默认值绕过校验"的写法要重查**。

## 8. 实战模式与五个坑

**实战模式一：清洗 + 语义分两步**——before 清洗原始输入（strip/parse），after 做业务语义校验（范围/关系）——"**先收拾再评判**"。**实战模式二：派生字段用 computed_field 而不是校验器**——只读的展示字段（05 篇）别在 after 校验器里硬塞。**实战模式三：校验器尽量小**——一个校验器只做一件事，出错信息具体（"金额必须大于 0"好过"值不合法"）。

**五个坑**：其一，漏 @classmethod——直接 TypeError；其二，忘了 return——after 校验器返回 None 时字段被清空（对 after 模式，pydantic 要求返回原类型）；其三，在 after 校验器里试图改别的字段——报错或无效，**跨字段用 model_validator**；其四，抛的不是 ValueError 而是自定义异常——不被捕获，**统一抛 ValueError/AssertionError**；其五，before 模式假设输入是 dict——**输入的可能是任意类型（str/None），先 isinstance 再取键**；其六，校验器里抛 RuntimeError 等内置异常——pydantic 不捕获（只捕 ValueError/AssertionError），**错误会穿透成 500；统一抛 ValueError**。
