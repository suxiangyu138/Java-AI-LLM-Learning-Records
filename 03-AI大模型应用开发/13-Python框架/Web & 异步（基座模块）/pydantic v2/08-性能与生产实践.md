## 1. 性能真相：快在哪里

**v2 的性能革命来自核心重写**：校验引擎从 Python 换成 Rust（pydantic-core），**单个字段校验从微秒级降到亚微秒级（约 5-50 倍）**；Python 层只做"模型定义 → 核心 schema"的翻译（有缓存），运行时绝大部分工作在 Rust 里完成。**快在哪、慢在哪要分清楚**：**校验与 JSON 解析快**（Rust 直接处理）；**Python 层的模型构造/属性访问仍有开销**（对象创建、Python 调用）；**校验器/序列化器只要是你写的 Python 函数，那部分就是 Python 速度**——"**Rust 管框架，Python 管插件**"：越少写 Python 校验器、越用内置类型，整体越快。2.13 的正则编译缓存等优化都在 Rust 侧——**要提速，先看 Python 侧有没有可删的往返**。

## 2. 三个性能杠杆

**杠杆一：JSON 直验（model_validate_json）**——**JSON 字符串直接在 Rust 层解析 + 校验，不走 json.loads + validate_python 的两次 Python 往返**——"外部拿 JSON 就 validate_json，别先 dumps 再 validate"。**杠杆二：TypeAdapter 预热编译**——模型/TypeAdapter 首次使用会编译核心 schema（约毫秒级），**模块级构造、请求循环外复用**——"别在热路径里反复构造 TypeAdapter/定义模型"；批量场景 `TypeAdapter(list[T])` 一次编译、逐批 validate_json，比循环构造模型快一个量级。**杠杆三：少写 Python 校验器**——能用内置类型（Field 约束/Strict 类型/EmailStr）表达就不用自定义函数——"**每个 Python 校验器都是一次 Python 层往返**"；**杠杆四：避免无谓的模型重建**——`model_copy(update=...)` 比"新建模型"便宜（少一次完整校验）——"**热路径复用对象、批量路径用 TypeAdapter**"。

## 3. 性能实测方法论

```python
import time
from pydantic import TypeAdapter

ta = TypeAdapter(list[dict])          # 预热（首次编译核心 schema）
data = [{"a": i, "b": str(i)} for i in range(10_000)]

t0 = time.perf_counter()
for _ in range(10):
    ta.validate_python(data)
print(f"TypeAdapter: {(time.perf_counter()-t0)/10*1000:.1f} ms/批")
```

**实测三原则**：其一，**先预热再计时**——首次调用含 schema 编译，不计入性能；其二，**多轮取平均**——单轮受 GC/调度噪声影响大；其三，**对比才有意义**——同一数据对比 `model_validate_json` vs `json.loads + model_validate`、`TypeAdapter` vs 循环构造——**"性能结论必须来自你自己的数据与压测，不抄博客数字"**（00 篇误区六的精神）。**关注点**：P95 延迟而不是平均值（服务场景），批量吞吐（管道场景）；**内存同样要测**——`tracemalloc` 对比大列表校验的内存峰值，批量场景内存与速度并重。

## 4. 生产错误处理模式

```python
from pydantic import ValidationError

def parse_orders(raw: str) -> list[dict]:
    """统一入口：校验失败 → 结构化错误日志 → 业务错误码"""
    try:
        return OrdersAdapter.validate_json(raw)
    except ValidationError as e:
        for err in e.errors():
            log.error("校验失败", loc=err["loc"], type=err["type"], input=err["input"])
        raise BizError("INVALID_INPUT", e.errors())   # 业务层统一错误码
    except Exception:
        log.exception("非校验类异常")
        raise
```

**生产模式四条**：其一，**入口统一**——外部数据只从"校验函数"进来，业务代码见不到裸 dict；其二，**结构化日志**——errors() 的 loc/type/input 直接进 loguru 结构化字段（loguru 体系交叉）；其三，**转业务错误码**——ValidationError 不直接冒泡到用户，按错误码映射响应（FastAPI 场景由框架转 422）；其四，**分类捕获**——先捕 ValidationError 再捕 Exception，**非校验异常别伪装成校验错误**。

**错误码映射表**：missing → 400 REQUIRED_FIELD、类型错误 → 422 INVALID_TYPE、业务约束 → 422 OUT_OF_RANGE——"**错误码是出口契约，errors() 是内部证据**"——映射表放一处集中维护（10 篇报错速查）。

## 5. v1 迁移清单

**迁移现状（2026）**：FastAPI 0.128 起 pydantic.v1 完全移除——**v1 写法在任何现代依赖栈里都是存量债**。迁移步骤：

1. **扫描**：grep 老 API——`\.dict\(`/`\.json\(`/`parse_obj`/`@validator`/`@root_validator`/`class Config`/`BaseSettings`——**看到 @validator 与 @field_validator 并存 = 迁移未完成**；
2. **机械替换**：`uv run bump-pydantic ./src/`——自动改大部分（dict→model_dump、parse_obj→model_validate、validator→field_validator+classmethod）；
3. **人工排查三类**：校验器行为差异（after 模式不能改其他字段、默认值也过校验器）、自定义类型重写（pydantic.v1 的 custom type 迁移到 pydantic-core 协议）、Config 选项映射（orm_mode→from_attributes 等）；
4. **验证**：`pydantic.__version__` 确认 2.13.x、全量测试、OpenAPI 对比（schema 变化要评审）；
5. **渐进策略**：**一个模块一个模块迁**，每次合并一个小 PR——"**大爆炸迁移必翻车，增量迁移虽然慢但每次都有退路**"。

## 6. 与 FastAPI 的配合

**FastAPI 的校验链路完全构建在 pydantic 上**：请求体注解 → 框架自动 `model_validate_json`（JSON 直验）；响应模型 → 自动 `model_dump`；OpenAPI 文档 → `model_json_schema`。**2026 状态**：FastAPI 纯 v2（0.128 起无 v1 支持），**FastAPI 场景校验提速约 20-30%**（相对混用 v1 的时代）。**配合要点**：其一，**响应模型必写**（response_model 生成文档 + 过滤多余字段）；其二，**PATCH 语义用 exclude_unset**（只序列化客户端传过的字段，避免默认值覆盖存量，06 篇）；其三，**类型标注用 Annotated 风格**（与 FastAPI 的 Query/Path 一致，03 篇）——"**FastAPI 里写 pydantic = 写请求契约，慢不了，反而省了手写校验**"（实战见 10 篇）。

- [ ] 版本锁定 `pydantic==2.13.x`，无任何 v1 API 残留（grep 五连）

- [ ] FastAPI 场景 response_model 必写、PATCH 用 exclude_unset

## 8. 五个常见坑

- **坑一**：热路径里定义模型/构造 TypeAdapter——**首次编译开销每次白付；模块级构造**；
- **坑二**：`json.loads(x)` 后再 validate_python——**两次解析；validate_json 一步完成**；
- **坑三**：迁移只跑了 bump-pydantic 就上线——**校验器行为差异人工排查必做**（04 篇）；
- **坑四**：ValidationError 裸抛给用户——**错误信息暴露内部字段名；转业务错误码**；
- **坑五**：性能优化不看数据——**"validate_json 快"是结论不是信仰，压测自己的数据**。
