## 1. 为什么 AI 应用尤其需要 pydantic

**AI 应用的输入输出都是"高不确定数据"**：LLM 输出是概率采样的文本（**同一 prompt 两次结果可能不同，格式随时翻车**）、工具调用是模型生成的 JSON（**字段名靠"模型记得"**）、配置是 yaml（**手写易错**）。pydantic 在这条链路上承担同一职责——**把"模型说了算"变成"契约说了算"**：**结构化输出**让 LLM 直接产出符合 schema 的 JSON（校验在 SDK/框架层自动完成）；**工具 Schema** 让模型"知道"参数长什么样（tools 声明本质是 pydantic 生成的 JSON Schema）；**配置校验**让 llm.yaml 在加载时快速失败。**一句话**："**LLM 是生成器，pydantic 是质检员——AI 应用的质量边界，一半在 prompt，一半在 pydantic**"。

## 2. LLM 结构化输出：response_format

```python
from openai import OpenAI
from pydantic import BaseModel

class Weather(BaseModel):
    city: str
    temp: float
    condition: Literal["sunny", "rain", "cloudy"]

client = OpenAI()
resp = client.chat.completions.create(
    model="gpt-5.x",
    messages=[...],
    response_format=Weather,        # 直接传 pydantic 模型
)
w = Weather.model_validate_json(resp.choices[0].message.content)
```

**OpenAI SDK 的 response_format 直接收 pydantic 模型**（SDK 内部生成 JSON Schema 并校验响应，openai python-sdk 体系待建）；**Anthropic/DeepSeek 等各家也以 OpenAI 兼容方式支持**。**三层保障的价值**：**模型层**（strict JSON 约束采样）、**SDK 层**（返回前校验）、**业务层**（type 转换）——**"三层的任何一层漏了，pydantic 兜底"**。**失败处理**：校验失败重试（携带错误信息回传模型，Function Calling 体系 03 篇的"错误回传"姿势）——**"结构化输出不是 100% 成功，重试循环是生产标配"**。

**strict 结构化输出的额外约束**：OpenAI strict 模式要求 `additionalProperties: false`——pydantic 默认 schema 已满足；Optional 字段会变成 nullable——**模型可能输出 null，字段设计时想清楚"允许为空的字段才用 | None"**。

## 3. 工具调用：tools 声明即 JSON Schema

```python
from pydantic import BaseModel, Field

class SearchTool(BaseModel):
    query: str = Field(description="搜索关键词")
    top_k: int = Field(default=5, ge=1, le=20, description="返回条数")

tools = [{"type": "function",
          "function": {"name": "search", "parameters": SearchTool.model_json_schema()}}]
```

**Function Calling 的 tools 声明 = pydantic 的 model_json_schema()**（Function Calling 体系 `../../../02-大模型基础与Prompt工程/Function Calling 函数调用【Agent 基石】/00-FunctionCalling知识体系总览.md` 02 篇对照）。**description 是关键**——**它直接进 JSON Schema 成为模型的"参数说明书"**（03 篇 Field 元数据类参数的 AI 场景落地）。**工具参数的设计纪律**（与 Function Calling 体系一致）：**参数少而明确、description 写清"做什么/何时用/边界"、可选参数独立成工具**——**pydantic 的约束（ge/le/枚举）同时是"给模型的提示"**：约束越具体，模型越不容易乱填。**2026 生态**：LangChain/LlamaIndex/MCP 的工具定义层全部以 JSON Schema 为标准——**"会 pydantic = 会定义全生态的工具"**。

## 4. 解析 LLM 自由输出

```python
class Review(BaseModel):
    rating: int = Field(ge=1, le=5)
    sentiment: Literal["pos", "neg", "neutral"]
    keywords: list[str]

# 姿势一：response_format 结构化输出（最稳，第 2 节）
# 姿势二：自由文本解析（模型没保证格式时）
text = "这篇评论不错，给 4 星，关键词：性价比、物流"
try:
    r = Review.model_validate_json(extract_json(text))   # 先用正则/LLM 提取 JSON 片段
except ValidationError:
    r = fallback_parse(text)                              # 兜底解析
```

**自由输出解析的两种姿势**：**提示词要求 JSON + 提取片段 + pydantic 校验**（快但脆弱）、**让模型二次生成结构化 JSON**（稳但多一次调用）。**pydantic 在其中的角色**：**校验是最后防线**——模型给的内容不对，ValidationError 告诉你"错在哪"，而不是业务代码在运行时踩炸。**生产姿势**：**能 structured output 就 structured output，不能就"提取 + 校验 + 兜底"三件套**——"LLM 输出按'不可信外部输入'对待"（02 篇入口哲学在 AI 场景的延伸）。

## 5. 配置校验：llm.yaml 与 Settings

```python
# llm.yaml
model: deepseek-v4
temperature: 0.7
max_tokens: 2048
retrieval:
  top_k: 10
  threshold: 0.75

# config.py
from pydantic import BaseModel, Field
import yaml

class RetrievalCfg(BaseModel):
    top_k: int = Field(ge=1, le=50)
    threshold: float = Field(ge=0, le=1)

class LLMCfg(BaseModel):
    model: str
    temperature: float = Field(ge=0, le=2)
    max_tokens: int = Field(ge=1)
    retrieval: RetrievalCfg

cfg = LLMCfg.model_validate(yaml.safe_load(open("llm.yaml")))   # yaml 读取 + pydantic 校验
```

**"pyyaml 管读取、pydantic 管校验"在 AI 应用的标准落地**（pyyaml 体系 07 篇交叉）：**yaml 进来是裸 dict，model_validate 把它变成带约束的强类型配置**——temperature 超界、top_k 为负都在加载时快速失败。**部署差异配置走 pydantic-settings**（07 篇）：**模型名/密钥走环境变量**（API_KEY 永不进 yaml），**业务参数走 yaml**——"**yaml 管业务、env 管部署、pydantic 管两者**"。**2026 标准组合**：`yaml.safe_load + LLMCfg.model_validate + Settings`——**配置加载即校验，缺失即失败**。

## 6. RAG/向量检索的数据契约

**RAG 管道的每一段都有 pydantic 的位置**：**文档元数据**（解析后的 chunk 结构：`Chunk(BaseModel): text: str; page: int; source: str`——unstructured Elements 与向量库记录的强类型化）；**检索结果**（milvus 返回的裸 dict → `Hit` 模型，业务层拿到强类型）；**重排输出**（rerank 分数与文档的配对校验）。**价值**：**管道数据流强类型化后，每一段的 bug 在"入口校验"暴露而不是"下游空指针"暴露**——"**RAG 管道质量 = 每一段入口的 pydantic 闸口**"（RAG 体系交叉：`../../../04-RAG检索增强生成/` 检索链路实践）。**注意**：向量库返回的 dict 字段名可能与模型不一致——**用 Field(alias) 对齐外部字段名**（06 篇别名体系）。

## 7. 已知限制与规避

**限制一：JSON Schema 不能 round-trip**——Rust 正则库不支持 look-around，`Decimal` 字段生成的 schema（含负向前瞻）**无法被 pydantic 自己重新校验**（issue #13017）——**影响 FastMCP 等"从 schema 重建模型"的工具**——规避：**schema 只做对外声明；需要回读的场景避免 Decimal，用 float/字符串**。

**限制二：Union 与复杂类型在 strict JSON 模式下的行为**——structured output 的 strict 模式要求 `additionalProperties: false` 与全 required——**pydantic 默认 schema 已满足，但 Optional 字段会变成 nullable**——模型输出 null 的字段要接受（`str | None`）。

**限制三：模型输出的 JSON 可能不是合法 JSON**（截断/重复键）——**pydantic 只校验"合法 JSON"，解析失败在 JSON 层**——配合重试与兜底（第 4 节）。

## 8. 五个常见坑

- **坑一**：response_format 传模型但没做失败重试——**结构化输出成功率 95-99%，1-5% 的失败没有重试 = 线上偶发炸**；
- **坑二**：工具 description 不写——**模型瞎填参数；description 是给模型的说明书**（第 3 节）；
- **坑三**：llm.yaml 的字段与模型定义不同步——**yaml 改了模型没改，静默用默认值；加载后打印校验结果留痕**；
- **坑四**：把 LLM 输出当可信输入——**不校验直接用，业务层到处防御；入口 pydantic 一道闸口全解决**；
- **坑五**：SecretStr 的密钥进了 yaml——**密钥只进环境变量；yaml 里的默认值一提交 git 就泄露**（第 5 节纪律）。
