## 1. 选型决策树：六类场景六种结论

按"项目画像"对号入座，先看结论再看理由：

| 场景 | 画像 | 结论 |
|------|------|------|
| 运营/管理平台 | 后台 + CRUD + 报表 | **Django**（Admin 王牌） |
| 内容站/CMS/电商 | 页面 + 模板 + SEO | **Django**（服务端渲染） |
| 纯 API/微服务 | 接口 + 契约 + 并发 | **FastAPI**（类型驱动） |
| AI 模型服务 | 推理 + 流式 + 兼容 API | **FastAPI**（生态默认） |
| MVP/原型/教学 | 快 + 简单 + 可演示 | **Flask**（极简） |
| 内部工具/脚本服务 | 轻 + 无负担 | **Flask** 或 FastAPI 均可 |

决策口诀：**"要后台选 Django，要接口选 FastAPI，要快选 Flask"**——三个"要"通常只有一个成立，成立的那个就是答案；两个成立（如"要后台也要接口"）用 Django + Ninja 或 sidecar；三个都要的贪心项目，用「08 章」的三层地图拆分，而不是选一个"万能框架"。

再补一条**团队信号判据**，它与项目画像同等重要：**团队里谁是主力决定框架的上手成本**——全员 Django 熟手而项目偏 API，选 FastAPI 意味着短期效率损失（异步心智 + 数据层重组），此时"Django + Ninja"是更优过渡；反之全员 FastAPI 熟手而项目需要后台，直接用 FastAPI + 低代码后台可能比引入 Django 更快。**"理想选型"与"现实选型"的差距，由团队技能与学习成本决定**——选型文档写理想答案，执行时叠加"团队当前最顺的路"折中，这也是 09 章迁移路径存在的意义：选型不是一次性的，是沿着团队成长逐步优化的。

## 2. 场景案例一：运营管理平台

**画像**：内部运营后台——订单管理、用户管理、报表导出、权限分级；3-5 人团队、两周上线。

- **选 Django**：Admin 注册模型即后台（搜索/过滤/编辑/权限集成），Django 6.0 内置任务框架承接报表导出，认证权限开箱——**全部需求都有内置答案**，团队把时间花在业务逻辑而非框架组装
- **对照**：FastAPI 实现同等后台要自建前端（或低代码平台）加认证加权限，两周工期翻倍
- **结论**：这类项目的成本公式是"后台开发成本"——Django 在这一项上有量级优势，选型没有悬念

## 3. 场景案例二：AI 对话产品

**画像**：RAG 知识库问答 + Agent 工具调用 + 流式输出 + 管理后台（知识库管理）。

- **选 FastAPI 为主体 + Django（或自建后台）**：对话与流式（SSE/WebSocket）是 FastAPI 原生姿势；知识库/会话管理若想快速出后台，用 Django sidecar 或直接 Ninja
- **关键决策点**：流式对话（体验刚需）——FastAPI 一条 `StreamingResponse` 解决，Django 要 Channels 绕路；**"流式"需求一出，主体框架就定了**
- **结论**：FastAPI 管对话/检索/工具调用，后台按团队能力选（Django Admin 或低代码）；这正是 08 章三层地图的实战版

## 4. 场景案例三：高并发 API 网关

**画像**：日请求百万级、纯 JSON API、无后台需求、多团队对接。

- **选 FastAPI**：ASGI 事件循环承载高并发连接，Pydantic 契约自动（多团队对接最怕文档漂移），OpenAPI 客户端生成（多语言团队直接拿 spec 生成 SDK）
- **对照**：Flask 的 WSGI 线程模型在并发拐点后需要更多 worker 与机器；Django 的重量对纯 API 是负担
- **结论**：**"纯 API + 高并发 + 契约自动"三要素全中 = FastAPI 的唯一主场**——这是 2026 年 FastAPI 市占率登顶的核心场景

## 5. Flask→FastAPI 平滑迁移

三大迁移中最平滑的路径（2026 年被反复验证）：

```text
第 1 步：路由对照迁移（装饰器结构几乎 1:1）
第 2 步：请求/响应改 Pydantic 模型（校验与文档随迁）
第 3 步：同步函数改 async（IO 调用逐步 async 化）
第 4 步：SQLAlchemy 数据层不动（两者通用）
第 5 步：删 Flask 扩展（Flask-Login→fastapi.security 等）
```

为什么平滑：**路由模型同构（装饰器 + 函数）、数据层共享（SQLAlchemy）、无状态服务**——Flask 的"乐高积木"恰好让迁移像"换积木盘"。基准收益：同场景吞吐约 6 倍提升（并发模型差异，06 章）；**迁移后保留哪些**：Jinja2 模板可换 Jinja2 独立使用，或页面部分留给前端。

迁移的**坑位清单**（都是真实翻车点）：① `request.form`/`request.args` 换成 FastAPI 的 `Form()`/`Query()` 参数，别在视图里再手动读；② 全局 `g` 对象没有等价物——用 `Depends` 传递请求上下文；③ Flask 的 `before_request` 钩子换成中间件或依赖（`yield` 模式）；④ 测试从 Flask test client 换 `TestClient`（httpx 基座），断言库可共用 pytest。**迁移不是"改语法"，而是"换上下文传递机制"**——把第 ② 条想透，迁移就成功了一半。

## 6. Django→API 化：DRF / Ninja / 渐进拆分

Django 项目的 API 化有三条路，成本递增：

| 路径 | 做法 | 成本 | 适用 |
|------|------|:---:|------|
| DRF | 原框架加 API 层 | 低 | 已有 DRF 存量、传统 API |
| Django Ninja | 原框架加现代 API 层 | 低-中 | 要 Pydantic 契约/自动文档 |
| 渐进拆分 | 业务服务化（FastAPI sidecar 接管接口） | 中-高 | 接口量大、要独立扩缩容 |

关键认知：**Django→FastAPI 的"重写"路线（弃 ORM/Admin 重写）成本最高、收益最不确定**——除非接口规模与并发需求大到 Django 体系扛不住（罕见），否则 Ninja 或 sidecar 是更优解。**"Django 打底 + 渐进 API 化"是 2026 年 Django 存量项目的主流演进方向**，不是二选一的豪赌。

## 7. 迁移的成本思维：什么时候不该迁

迁移不是"升级"，是"重写一部分"——三问不过不迁：

1. **性能缺口真实吗？** 先压测——P99 延迟拐点出现前，框架差异不是瓶颈（06 章）；把成本投在索引/缓存/连接池上通常收益更大
2. **生态锁定深吗？** Django 的 ORM/Admin/认证深度绑定——迁移 ≈ 数据层重写 + 后台重做；Flask→FastAPI 轻（数据层共享），Django→FastAPI 重（全部重写）
3. **业务还在变吗？** 需求频繁变更期迁移 = 双倍变更量；**"流量到了再迁"（业务稳定后）的成本远低于"业务动荡期迁移"**——这是迁移决策最重要的时机判断

给三个案例补上"迁与不迁"的实感：**案例 A**——Flask 报表服务日请求 20 万、P99 正常，业务稳定：不迁（三问全否，迁移无收益）；**案例 B**——Flask 接口日请求 500 万、峰值 P99 开始陡增、压测确认拐点：迁（三问全中，6 倍吞吐直接换机器数）；**案例 C**——Django 电商后台想"全部重写成 FastAPI"：否决（生态锁定深 + 后台需求仍在，正确路径是 Ninja 或 sidecar）。**"迁"与"不迁"的答案藏在三个问题的交叉里**——多数项目止步于问题一（压测没过），多数灾难源于跳过了问题三（动荡期硬迁）。

> 🎯 **核心要点**：六类场景口诀"要后台 Django、要接口 FastAPI、要快 Flask"；Flask→FastAPI 平滑（数据层共享、5 步迁移、6 倍吞吐）；Django API 化走 Ninja/sidecar 而非重写；迁移三问（性能真实？锁定深？业务稳？）不过不迁。

## 8. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. 决策树：后台→Django、接口/模型服务→FastAPI、MVP→Flask；两个"要"成立用 Ninja/sidecar；
> 2. 迁移：Flask→FastAPI 平滑（6 倍吞吐），Django→API 用 Ninja/渐进拆分，避免重写豪赌；
> 3. 迁移三问：性能缺口真实？生态锁定深浅？业务是否稳定？——"流量到了再迁"优于"焦虑提前迁"。
