## 1. ASGI vs WSGI：协议层的本质差异

性能差距的第一性来源不在框架，在**网关协议**：

- **WSGI**（Django/Flask 传统模型）：同步请求-响应——一个请求占用一个线程，从进入到返回线程一直持有；并发 = 线程数（每 worker 线程池，如 gunicorn 默认 4 线程 × N worker）
- **ASGI**（FastAPI/Starlette）：异步事件循环——请求是"协程任务"，IO 等待时让出事件循环给其他请求；单进程可承载数千并发连接

```text
WSGI 模型（每请求一线程）          ASGI 模型（事件循环并发）
请求1 ── 线程1 ── IO等待……阻塞    请求1 ─┐
请求2 ── 线程2 ── IO等待……阻塞    请求2 ──┤ 事件循环 ── IO 等待时切换
请求3 ── 线程3 ── IO等待……阻塞    请求3 ─┘ 一个线程跑 N 个协程
```

差距的量化：**"并发连接数"上 ASGI 天然高一个量级**（千级 vs 万级）；"单请求 CPU 处理"上两者相当（都是 Python，都受 GIL 约束）。所以"FastAPI 快 6 倍"的真实含义是"**IO 密集场景的并发承载高**"，纯计算场景优势会缩小。

## 2. 2026 基准数据解读

被广泛引用的基准（DZone/社区，需注意测试条件差异）：

| 框架 | 基准 RPS（同机 IO 型测试） | 模型 |
|------|:---:|------|
| FastAPI | ~10,000-20,000 | ASGI 事件循环 |
| Flask | ~1,500-4,000 | WSGI 线程 |
| Django（传统视图） | ~1,000-3,000 | WSGI 线程 |

正确解读三原则：

1. **测试条件决定一切**：纯内存路由测试 vs 带 ORM/模板的完整栈，数字差 10 倍——上述数字是"轻量路由 + JSON 响应"条件，真实业务里 ORM 查询会淹没框架差异
2. **GIL 是公共天花板**：任何 Python 框架的单进程 CPU 并行都受限，多 worker（多进程）才是扩展手段——"Python 框架性能"的上限由 GIL + worker 数决定，框架本身只决定"单 worker 的并发形态"
3. **IO 场景的真实瓶颈在下游**：数据库、下游 API、网络——框架差异在延迟曲线尾部（高并发时）显现，日常负载下无感

## 3. 服务器矩阵：uvicorn / gunicorn / hypercorn

框架本身不跑 HTTP——需要一个 ASGI/WSGI 服务器，2026 年选型：

| 服务器 | 协议 | 定位 | 2026 状态 |
|--------|------|------|-----------|
| uvicorn | ASGI | FastAPI 官方默认（0.51.0，2026-07） | 首选，uvloop 加速 |
| gunicorn | WSGI + ASGI | 传统同步框架首选；26.0 起 ASGI worker 转正 | Django/Flask 标准搭配 |
| hypercorn | ASGI | 支持 HTTP/2、HTTP/3 的实验性选手 | 有 HTTP/3 需求时考虑 |
| 组合姿势 | 混合 | gunicorn 管进程 + uvicorn worker（`gunicorn -k uvicorn.workers.UvicornWorker`） | 生产标准：进程管理 + 异步 worker |

生产实践要点：**gunicorn + uvicorn worker 是 FastAPI 的经典生产组合**——gunicorn 负责进程管理与信号（优雅退出/重启），uvicorn worker 提供事件循环；Django/Flask 则 gunicorn 原生 WSGI worker 即可。容器里直接 uvicorn 多 worker 也行（K8s 接管进程管理后，两者趋同）。

## 4. Gunicorn 26：ASGI 兼容套件与时代信号

Gunicorn 26.0.0（2026-05）发布是框架生态的标志性事件：

- **ASGI worker 从 beta 转正**——Gunicorn 官方正式支持异步框架，同步时代的代表服务器完成"跨时代"
- **ASGI 兼容测试套件上线**：Docker 化测试网格覆盖 HTTP/WebSocket/流式/生命周期/HTTP2/并发，**438/444 通过（98%）**——涵盖 Starlette、FastAPI、Litestar、Quart、Sanic、BlackSheep
- **移除 Eventlet worker**——同步服务器生态收缩，迁移路径指向 gevent/gthread/tornado

信号解读：**ASGI 已从"新锐"变成"标准"**——服务器层、框架层、兼容层全部就位，2026 年的"Python Web 性能基础设施"之争已基本尘埃落定：**新项目默认 ASGI（FastAPI/Starlette 系），WSGI 只服务存量（Django/Flask 传统部署）**。

## 5. 什么时候性能差距不重要

反直觉但关键的结论：**多数业务选框架时，性能差距不该是首要变量**：

- **IO 密集是常态**：真实服务的延迟构成——数据库 60% + 下游 20% + 网络 10% + 框架 10%。框架的 10% 里，ASGI vs WSGI 的差距只在并发拐点后显现；日均请求低于"并发拐点"（通常数千 QPS 以上）时，三框架无感差异
- **架构先行**：缓存命中率、索引质量、连接池大小、限流策略——这些对吞吐的影响是框架差异的 10 倍以上；"先调架构再谈换框架"是性能优化的铁律
- **可观测是前提**：没有 P99 延迟与错误率的基线，就无法判断"框架是不是瓶颈"——先上 OTel/APM 再谈性能对比，否则一切结论都是猜测；把"性能讨论"建立在数据上，比建立在框架信仰上可靠得多
- **性能是增长问题**：**"流量到了再换"的成本，低于"性能焦虑提前选错"的成本**——先用 Flask/Django 快速验证业务，流量与资金到位后再 FastAPI 化（06/09 章的迁移路径），比一开始就为"可能到来的高并发"选重方案更划算

给"性能不重要的日常负载"一个可感知的标尺：假设单机日均 100 万请求（约 12 QPS 均值、峰值 50-100 QPS），Flask 的 WSGI 模型完全游刃有余——**这个量级下三框架的 P99 差异通常在 10ms 以内，用户无感**。差距真正显现的拐点通常在"峰值数千 QPS 且延迟敏感"之后：此时 ASGI 的并发承载开始拉开（同样的 8 核机器，事件循环可以少开 worker、省内存），但即便如此，"升 worker 数"仍是 Flask/Django 的第一轮解药。**把"性能差距"翻译成"机器数与延迟拐点"，比抽象地"快 6 倍"更能指导决策**——多数团队在拐点之前就把业务验证完了。

## 6. 并发场景实测指南

判断"我的场景是否需要 ASGI"的实测三步：

1. **量级自查**：预估峰值 QPS 与连接数——低于数千 QPS 且无长连接需求 → WSGI 完全够用
2. **压测验证**：`locust`/`wrk` 打 3-5 倍预估峰值，观察延迟拐点（P99 陡增处）——拐点前的日常负载下，Flask 与 FastAPI 差距通常 <20%
3. **场景画像**：有 WebSocket/SSE/流式需求 → 无条件 ASGI（WSGI 做不到，非性能问题而是能力问题）；纯 CRUD API → 两者皆可，按生态选

压测的一个**常见误区**要提醒：很多人压测时用"本机单 worker + 无真实数据层"的玩具配置，结论是"三框架差不多"或"Flask 比 FastAPI 快"（同步框架在低并发下反而省了事件循环开销）——**这个结论对真实生产没有参考价值**。正确姿势是"生产配置 + 真实数据层 + 分级并发"（100/1000/5000 并发三档），重点看三档下的 P99 曲线形态而不是单点峰值；**曲线形状比峰值数字重要**：同步框架的 P99 从某档开始陡增（线程耗尽），异步框架的 P99 平缓（事件循环排队）——这个"拐点位置"才是决策依据。

> 🎯 **核心要点**：性能差距的本质是并发模型（ASGI 事件循环 vs WSGI 线程），量级在"并发承载"而非"单请求速度"；Gunicorn 26 的 ASGI 转正标志异步时代落定；多数业务"架构先于框架"——性能是增长问题，不是选型焦虑问题。

## 7. 核心要点与思考题

> 🎯 **本章三句话总结**：
> 1. ASGI vs WSGI：事件循环并发 vs 每请求一线程，差距在并发承载量级（千级 vs 万级）；
> 2. 基准读数三原则：条件决定数字、GIL 是公共天花板、真实瓶颈在下游；
> 3. Gunicorn 26 ASGI 转正 + 438/444 兼容套件 = 异步时代落定；多数业务性能不构成选型首要变量。
