## 1. 配置读取的标准模式

```python
import os
import yaml

def load_config(path: str) -> dict:
    """读取 YAML 配置：安全加载 + 空文件兜底 + 错误带行号"""
    try:
        with open(path, encoding="utf-8") as f:
            return yaml.safe_load(f) or {}
    except FileNotFoundError:
        return {}
    except yaml.YAMLError as e:
        raise RuntimeError(f"配置文件 {path} 解析失败: {e}") from e
```

**四个设计点**：**safe_load 唯一**（04 篇红线）；**`or {}` 兜底空文件**（03 篇）；**YAMLError 包装成 RuntimeError 带文件名**（定位哪个文件坏了）；**FileNotFoundError 返回空 dict**（让"默认值兜底"流程接管——第 2 节）。**启动期调用**：应用入口最先加载配置（FastAPI 的 lifespan 里、脚本的 main 开头），**配置错 = 快速失败**（03 篇：带错运行比没配置更危险）。

## 2. 默认值合并

**配置文件通常只写"要覆盖的"**，其余用代码默认值——合并姿势：

```python
DEFAULTS = {
    "server": {"host": "0.0.0.0", "port": 8080},
    "logging": {"level": "INFO"},
    "retry": {"max_attempts": 3},
}

def merge(defaults: dict, override: dict) -> dict:
    """递归合并：override 覆盖 defaults，未覆盖的保持默认"""
    result = dict(defaults)
    for k, v in override.items():
        if isinstance(v, dict) and isinstance(result.get(k), dict):
            result[k] = merge(result[k], v)      # 递归合并嵌套
        else:
            result[k] = v
    return result

config = merge(DEFAULTS, load_config("config.yaml"))
```

**"代码默认值 + 配置覆盖"是配置管理的核心模式**：配置里没写的字段自动有默认值、写了就覆盖、嵌套字典递归合并——**配置文件的体积被压到最小（只写差异），缺文件也能跑（纯默认值）**。注意浅合并的坑：`{**a, **b}` 只合并第一层，**嵌套字典必须递归**（上面的 merge 就是）。

## 3. 多环境配置

**开发/测试/生产三套配置的标准姿势**——"基础配置 + 环境覆盖"双层：

```yaml
# config/base.yaml —— 公共配置
server:
  port: 8080
database:
  host: localhost
  pool_size: 10

# config/prod.yaml —— 生产覆盖（只写差异）
database:
  host: prod-db.internal
  pool_size: 50
logging:
  level: WARNING
```

```python
import os

ENV = os.getenv("APP_ENV", "dev")
config = merge(
    load_config("config/base.yaml"),
    load_config(f"config/{ENV}.yaml"),
)
```

**三层心智**：**公共层**（base，所有环境共享）→ **环境层**（dev/prod 覆盖差异）→ **运行时层**（环境变量 `os.getenv` 覆盖敏感项——端口、token，**凭证永远走环境变量不进 YAML**，与 02-后端配置安全、milvus 体系的 token 纪律一致）。**"环境选择用 APP_ENV 环境变量，不在 YAML 里选环境"**——YAML 是配置不是逻辑。

## 4. 校验闭环：加载成功 ≠ 值合法

**safe_load 只保证类型结构正确，不保证值合法**——`port: 70000`、`max_attempts: -3` 全部加载成功。**校验是配置管理不能省的最后一环**，两种姿势：

**姿势一：pydantic 模型校验**（生产推荐——声明式、类型 + 约束）：

```python
from pydantic import BaseModel, Field

class ServerConfig(BaseModel):
    host: str = "0.0.0.0"
    port: int = Field(default=8080, ge=1, le=65535)
    pool_size: int = Field(default=10, ge=1)

class AppConfig(BaseModel):
    server: ServerConfig
    retry: dict = {}

config = AppConfig(**merge(DEFAULTS, load_config("config.yaml")))
# 非法值直接抛 ValidationError（端口 70000、负数重试都会挂）
```

**姿势二：手动断言**（配置项少时够用）：`assert 1 <= config["port"] <= 65535`。**选型**：**配置层级多、团队大用 pydantic**（类型错误、越界、缺字段全部编译期可见）；配置简单用手动断言。**"校验失败 = 启动失败"**（快速失败原则）——校验的报错信息要写清"哪个字段、期望什么"（07 篇排障友好）。

## 5. AI 应用中的 YAML 配置

YAML 在 AI 应用栈的三类典型配置（本体系的框架配合，00 篇分工）：

**框架配置**——LangChain/LlamaIndex 的模型、检索参数、流水线定义（`../LangChain/00-LangChain总览.md`、`../llama‑index/00-LlamaIndex总览.md` 里那些 yaml 配置的读取层就是 PyYAML）；**工具/Agent 描述**——工具参数 schema、Agent 流程步骤定义常以 YAML 组织（可读 + 版本可控）；**RAG 管道元数据**——文档分片规则、索引参数、检索策略的声明式配置。**AI 项目的"配置即代码"**：YAML 存参数、代码存逻辑——**换模型/换参数只改 YAML 不碰代码**是 2026 年 AI 工程化的普遍约定。

**一个具体的 AI 配置形态**（LLM 调用参数 + 检索策略 + 工具清单）：

```yaml
# config/llm.yaml —— LLM 应用配置
llm:
  default: {provider: openai, model: gpt-4o, temperature: 0.7}
  cheap:   {provider: openai, model: gpt-4o-mini, temperature: 0.3}
retrieval:
  top_k: 5
  threshold: 0.6
  rerank: true
tools: [web_search, calculator]     # Agent 工具白名单
```

**读这个配置 → pydantic 校验 → 注入应用**就是 07 篇闭环在 AI 场景的完整落地——**"YAML 描述做什么，代码决定怎么做"**是配置即代码的精确表述。

## 6. 配置管理规范

**规范一：配置进版本库**——YAML 配置是代码的一部分（评审、回溯、环境一致性全靠它），**敏感值除外**（走环境变量/密钥管理）。

**规范二：校验与 lint 进 CI**——yamllint 查语法与风格（02 篇坑五的自动化）、配置校验脚本跑一遍（第 4 节）——**"配置错在 CI 挂，而不是上线挂"**。

**规范三：启动快速失败**——加载 + 校验在入口完成，**错就退出**（带清晰报错：文件、行号、字段）。

**规范四：读写分离纪律**——程序运行中**不该改配置文件**（改配置 = 重启流程）；运行期动态配置走配置中心/数据库。

**规范五：文档化配置项**——每个配置项写注释（`# 含义/取值范围/默认值`）——**"配置是可读的文档"**是 YAML 优于 JSON 的隐性价值（02 篇）。

## 7. 常见坑

**坑一：浅合并**——`{**a, **b}` 只盖第一层，嵌套配置丢失默认值；**递归 merge**（第 2 节）。

**坑二：校验缺位**——端口 70000 上线的配置事故；**pydantic/断言必配**（第 4 节）。

**坑三：凭证写进 YAML**——仓库泄露事故；**凭证永远环境变量**（第 3 节）。

**坑四：配置文件运行时被改**——读到一半数据不一致；**配置一次性加载进内存**（启动读一次）。

**坑五：多环境文件复制粘贴**——base 改了 prod 忘同步；**"base + 覆盖"模式 + 注释标明差异**（第 3 节）。

**坑六：配置校验只验类型不验业务**——pydantic 的 ge/le 验了"端口范围"，但"这个服务该不该有 8 个副本"是业务校验；**分层校验：语法（lint）→ 结构（safe_load）→ 类型（pydantic）→ 业务（代码断言）**四层缺一不可（07 篇第 4 节是类型层，业务层在应用代码里）。

**坑七：配置中心与本地 YAML 双写**——两处配置漂移，改了一处另一处静默旧值；**"本地 YAML 是启动基线，配置中心是运行时覆盖"职责要写清**（07 篇规范四）。

**坑八：把"环境判断"写进配置**——`if config["env"] == "prod"` 在代码里四处出现；**环境差异应该收敛在"配置加载层"**（第 3 节：base + 环境覆盖一次完成），**业务代码只读合并后的配置，不感知环境**——"**环境是加载期概念，不是运行期概念**"。
