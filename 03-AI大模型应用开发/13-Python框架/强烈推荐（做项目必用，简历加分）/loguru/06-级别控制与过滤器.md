## 1. 级别语义与 per-sink 配置

loguru 的级别是**数字大小比较**：记录某条日志时，如果它低于 sink 配置的 level，该 sink 直接丢弃。七个内置级别：TRACE(5) / DEBUG(10) / INFO(20) / SUCCESS(25) / WARNING(30) / ERROR(40) / CRITICAL(50)。

与标准库的关键差异：**级别是 per-sink 的，不是 logger 全局的**。同一个 logger，可以让 stderr sink 收 DEBUG 以上、文件 sink 收 INFO 以上、告警函数 sink 只收 ERROR——**一个 logger 多档输出**：

```python
logger.add(sys.stderr, level="DEBUG")    # 开发控制台：全量
logger.add("logs/app.log", level="INFO") # 生产文件：INFO 起
logger.add(alert_sink, level="ERROR")    # 告警通道：只有错误
```

打日志时方法名即级别（`logger.debug(...)`），不用传 level 参数——级别语义被压缩进方法名，这是 loguru"简单"的又一体现。

## 2. filter：三种过滤写法

`level` 是"按级别收"，`filter` 是"按规则收"——三种写法覆盖从粗到细：

**字符串（模块名前缀）**——只收指定模块（或其子模块）的日志：

```python
logger.add("app.log", filter="my_app.biz")   # 只收 my_app.biz 及其子模块
```

**字典（模块名 → 级别）**——给不同模块不同级别，治理"噪音模块"：

```python
logger.add("app.log", filter={"": "INFO", "my_app.biz": "DEBUG",
                              "urllib3": "WARNING"})
```

空字符串 `""` 是兜底级别，其余模块名单独覆盖——**这是生产最常用的过滤形态**。

**函数（返回 True 才收）**——最强自由度，基于 record 任意判断：

```python
def only_biz(record):
    return record["extra"].get("component") == "biz"

logger.add("biz.log", filter=only_biz)
```

**选择心法**：只想安静调某模块用字符串；多模块混合治理用字典；按业务字段/自定义规则筛用函数。

## 3. disable/enable：库开发模式

这是 loguru 给**库开发者**的设计（也是它与标准库 logging 哲学的又一差异）。标准库里库打印日志默认全量输出，使用者得自己过滤；loguru 反过来——**库默认静默，应用显式启用**：

```python
# 在库内部（比如你的 Python SDK 包）：
logger.disable("my_sdk")       # 库的日志默认 no-op

# 在使用方的应用里：
logger.enable("my_sdk")        # 应用显式打开，级别/格式由应用决定
```

**价值**：你的库被打进别人的项目时，不会把调试日志灌进别人的日志系统；对方想开也只是一行 `enable`。对应到第三方库治理：requests、urllib3、httpx 这类标准库日志库，用第 8 篇的 InterceptHandler 接管后再用 `filter` 字典统一调级——**先接管、再分级**。

## 4. 环境变量化配置

loguru 支持用环境变量覆盖配置，不改代码换环境行为——对 Docker/K8s 部署尤其重要：

| 环境变量 | 作用 |
|---------|------|
| `LOGURU_LEVEL` | 覆盖默认级别（如 `LOGURU_LEVEL=WARNING`） |
| `LOGURU_FORMAT` | 覆盖默认格式模板 |
| `LOGURU_COLORIZE` | 覆盖颜色开关（`true/false`） |
| `LOGURU_AUTOINIT` | 控制是否自动创建默认 stderr sink |
| `NO_COLOR` / `FORCE_COLOR` | 终端配色通用协议 |

生产部署姿势：**代码里写死开发友好的默认值，部署层用环境变量调整**——Docker Compose 的 `environment:` 段、K8s 的 env 配置都能改日志级别，不用重新构建镜像。例如：压测环境 `LOGURU_LEVEL=WARNING` 降噪，故障排查时临时 `LOGURU_LEVEL=DEBUG` 重启即升级日志。

```yaml
# docker-compose.yml：部署层调日志，不碰镜像
services:
  app:
    environment:
      LOGURU_LEVEL: WARNING          # 压测降噪
      LOGURU_FORMAT: "{time} {level} {message}"
```

`LOGURU_AUTOINIT` 值得单独记一笔：设 `false` 可**禁止 loguru 自动创建默认 stderr sink**——库开发者或"完全由应用决定输出"的场景用它，配合 `logger.add()` 由最终应用全权接管输出形态。

## 5. 生产级别策略

不同环境的日志级别选择直接影响"看得见什么"：

| 环境 | 推荐级别 | 理由 |
|------|---------|------|
| 本地开发 | DEBUG | 细节全开，快速定位 |
| CI/测试 | INFO | 保留关键流程，避免刷爆 CI 输出 |
| 压测 | WARNING | DEBUG 日志会拖慢压测且淹没真实错误 |
| 生产 | INFO | 业务留痕 + 错误全量；DEBUG 需要时临时开 |

**两条铁律**：其一，**生产 INFO 是底线**——只留 WARNING 会丢失"请求进来了"这类排障关键信息；其二，**DEBUG 永不常驻生产**——性能与噪音双输。生产疑难排障的标准流程：`LOGURU_LEVEL=DEBUG` 重启 → 复现 → 收集 → 恢复 INFO（配合 04 篇的轮转，DEBUG 短时开不会炸磁盘）。

**级别语义的团队约定**（比配置更重要的软规范）：**INFO 记业务留痕**（请求完成、任务开始结束——可回答"系统在做什么"）；**WARNING 记可恢复的异常**（重试成功、限流生效、配置降级——不需要立刻处理但要知道）；**ERROR 记不可恢复的失败**（本次操作失败但服务存活——当天必须有人处理）；**CRITICAL 记停机级事件**（启动失败、核心依赖全挂——要接告警）。**判别口诀：这条日志出现时，值班的人要不要醒？要醒是 CRITICAL，明天处理是 ERROR，不用管但要留痕是 WARNING**——级别定义模糊是日志治理最常见的失败模式。

## 6. 多 sink 级别分工实例

一个完整的"三级分流"配置——开发控制台、生产文件、审计文件各司其职：

```python
from loguru import logger
import sys, os

logger.remove()
logger.add(sys.stderr, level="DEBUG")                      # 1. 开发台：全量
logger.add("logs/app.log", rotation="500 MB",
           retention="30 days", compression="zip",
           level="INFO", enqueue=True)                     # 2. 生产文件：INFO+
logger.add("logs/audit.log", filter=lambda r: r["level"].name == "AUDIT",
           rotation="1 week", retention="90 days")         # 3. 审计文件：仅 AUDIT
```

三个 sink 同源但收的东西完全不同——**控制台全量、文件业务级、审计文件合规级**。审计日志单独保留 90 天、AUDIT 级别专属（02 篇自定义 level 的实战落地），这是金融/合规项目的标配结构。

## 7. 常见坑

**坑一：级别大小写写错**——`level="info"` 报 `ValueError: Level 'info' does not exist`；级别名必须大写（`"INFO"`）。

**坑二：filter 字符串误伤**——`filter="app"` 会匹配 `app`、`app.biz`，但**不会**匹配 `myapp`（按点分隔的前缀匹配）——想按前缀模糊筛要用函数或字典。

**坑三：disable 后忘 enable**——自己开发的库 `logger.disable("my_sdk")` 后在自己项目里测，日志全没了排查半天——测试代码里先 `enable` 再断言。

**坑四：环境变量与代码冲突**——部署设了 `LOGURU_LEVEL=WARNING`，代码里 add 的 `level="INFO"` 会互相覆盖（环境变量覆盖的是"默认值"，显式参数优先）——**线上改级别改不动的第一排查点：代码里有没有写死的 level**。
