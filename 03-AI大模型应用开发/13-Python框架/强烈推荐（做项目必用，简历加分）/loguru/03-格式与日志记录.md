## 1. 消息即模板：惰性拼接

loguru 的消息用大括号占位符 `{}`，参数在真正写日志时才拼接：

```python
logger.info("订单 {} 已支付，金额 {}", order_id, amount)
```

这带来两个好处。**其一，类型天然安全**：`str.format` 风格的 `{}` 自动调用参数的 `__str__`，不用像 `%` 风格那样操心 `%s`/`%d` 配错。**其二，惰性求值**：如果这条消息被 level 过滤掉了，参数表达式根本不会执行——对比 f-string 是"先算完再决定要不要打"，在热路径上这是白拿的性能：

```python
# f-string：即使 DEBUG 被过滤，repr(huge_obj) 照样执行
logger.debug(f"对象内容: {repr(huge_obj)}")

# loguru：被过滤时参数不计算
logger.debug("对象内容: {}", repr(huge_obj))

# 更彻底的惰性：opt(lazy=True) 连函数调用都推迟
logger.opt(lazy=True).debug("对象内容: {}", lambda: repr(huge_obj))
```

`opt(lazy=True)` 把参数换成无参函数，**只有真正要写日志时才调用**——适合"参数计算很贵"的场景（序列化大对象、渲染复杂结构）。

## 2. format 与 record 字段

`format` 是模板字符串，花括号里填 **record 字段**——每次日志事件都携带的结构化元数据：

```python
logger.add(
    sys.stderr,
    format="{time:YYYY-MM-DD HH:mm:ss} | {level: <8} | {name}:{function}:{line} | {message}",
)
```

常用字段：`{time}` 时间、`{level}` 级别名、`{message}` 消息正文、`{name}` 模块名、`{function}` 函数名、`{line}` 行号、`{file}` 文件名、`{module}` 模块短名、`{process}` 进程 ID、`{thread}` 线程 ID、`{exception}` 异常信息（仅在异常日志非空）、`{extra}` 自定义字段集合。字段支持对齐与宽度控制（`{level: <8}` 左对齐 8 格），格式统一后日志列整齐、grep 好筛。

带业务字段的完整格式示例（配合 bind，见第 6 节）：

```python
logger.add(sys.stderr,
    format="{time:HH:mm:ss} | <level>{level: <8}</level> | "
           "trace={extra[trace_id]} | {message}")
logger.bind(trace_id="abc123").info("下单成功")  # trace=abc123 | 下单成功
```

**设计建议：format 尽量短**——format 是每行日志的固定开销，字段越多每行越长、写盘越慢；**把可检索字段放 extra（JSON 化后仍可查询，见 09 篇），format 只保留"人眼扫读必需"的字段**（时间/级别/消息 + 一两个关键 extra）——"format 给人看，extra 给机器查"。

> 💡 **提示**：format 里字段写错不会崩——loguru 在记录时替换失败会给出警告并输出原模板，便于调试而不是半夜炸掉。

## 3. 时间格式化

loguru 用自带的时间格式指令（不是 strftime 的 `%Y`），默认精确到微秒：

```python
"{time:YYYY-MM-DD HH:mm:ss.SSS}"   # 毫秒
"{time:YYYY-MM-DD at HH:mm:ss}"    # 带 at 分隔
"{time:HH:mm}"                     # 只取时分
"{time:YYYY-MM-DD HH:mm:ss Z}"     # 带时区
```

文件名里也能用 `{time}`（04 篇的文件分片就靠它）。跨时区部署注意：默认本地时区，容器环境建议统一 UTC（`TZ=UTC` 环境变量即可）。0.7.3 专门优化了 datetime 格式化性能——它是日志热路径上最高频的开销之一，官方已把这块提速做了。

## 4. 颜色 markup 与终端控制

日志颜色用 markup 标签包裹，`<level>` 是个特殊标签——**自动采用当前级别的默认颜色**（INFO 绿、WARNING 黄、ERROR 红）：

```python
logger.add(sys.stderr,
    format="<green>{time:HH:mm:ss}</green> | <cyan>{name}</cyan> | <level>{message}</level>")
```

颜色标签支持嵌套与修饰：`<red>`、`<green>`、`<yellow>`、`<blue>`、`<magenta>`、`<cyan>`、`<bold>`、`<underline>`，可以 `<bold><red>` 叠加。**终端控制三件事**：环境变量 `NO_COLOR` 存在时自动禁用颜色（CI 友好）、`FORCE_COLOR` 强制启用、`LOGURU_COLORIZE` 可覆盖默认行为。向文件写日志时颜色会按颜色标签**自动去除**——日志文件里不会出现转义序列垃圾，只有终端里上色，这个细节常被忽略但非常实用。

## 5. opt()：逐条日志微调

`opt()` 返回一个临时配置的 logger 副本，**只影响这一条**：

```python
logger.opt(record=True).info("函数 {} 在 {} 被调用", caller_name, func_name)
logger.opt(colors=True).info("<red>金额异常: {}</red>", amount)   # 本条强制上色
logger.opt(raw=True).info("<bold>原始输出，不加前缀</bold>")        # 绕过全局格式
logger.opt(depth=1).info("记录调用者的行号而非本行")               # 栈深度调整
logger.opt(exception=e).info("手动附加异常信息")                    # 当前无异常也可带
```

四类用途记住即可：**record** 往模板里塞 record 字段、**colors/raw** 控制本条输出形态、**depth** 修正行号归属（在封装函数里打日志时指回调用者）、**exception** 手动附加异常。`opt(exception=True)` 还能配合 `except` 上下文把异常完整格式化进普通消息。

## 6. bind/contextualize：给日志加上下文

日志检索的核心需求是"这条日志属于哪个请求/哪次任务"。`bind()` 给日志加 extra 字段：

```python
logger.add("app.log", format="{time} | {extra[user_id]} | {message}")
logger.bind(user_id=123).info("用户下单")   # extra 字段出现在 {extra[...]} 里
```

`bind()` 是"临时绑定"，**而 `contextualize()` 是上下文管理器**——块内所有日志自动携带上下文，配合 `enqueue=True` 还能跨线程传递（异步场景下每个 Task 携带自己的 context）：

```python
with logger.contextualize(request_id=trace_id, user_id=uid):
    logger.info("处理请求开始")
    logger.info("处理完成")     # 自动带 request_id / user_id
```

`patch()` 则更底层——动态修改每条日志的 record（比如统一注入服务名、版本号），适合在入口处全局加字段。**生产链路追踪的最小闭环**：中间件生成 `trace_id` → `contextualize` 注入 → 全链路日志自动带 ID → 查询时一个 ID 捞出整条调用链（10 篇实战）。

## 7. 常见坑

**坑一：拿 `%` 风格拼接**——`logger.info("数量 %d", n)` 在 loguru 里是错误用法（`%d` 当普通文本输出），统一用 `{}` 占位。

**坑二：f-string 提前求值**——`logger.debug(f"...{expensive}")` 白花性能，用 `{}` 占位或 `opt(lazy=True)`（本文第 1 节已对比）。

**坑三：extra 字段没写进 format**——`bind(user_id=123)` 了但 format 里没有 `{extra[user_id]}`，字段就静默丢弃；排查"日志里怎么没有我绑的字段"先查 format。

**坑四：颜色标签里带反斜杠**——`\<level>` 等特殊转义（0.7.3 修复了反斜杠紧邻 markup 显示异常的问题），需要转义时用 `\\<level>`。

**坑五：业务字段拼进 message 而不是 extra**——`logger.info(f"用户 {uid} 下单")` 里 uid 只存在于文本，JSON 化之后无法按字段检索；**规范是"人话进 message，数据进 extra"**——`logger.bind(user_id=uid).info("用户下单")`，检索靠 `extra[user_id]`（09 篇的 schema 治理根植于此）。

**日志模板规范建议**（团队公约）：message 里写"发生了什么"的自然语言 + 关键名词；参数化变量只放必要展示项；所有可检索字段放 extra；统一使用 `{}` 占位禁止 f-string 拼接。**模板规范的收益**：日志可读、可检索、可聚合，三份日志拼起来能还原完整事件——这是"日志即证据"的工程实践。
