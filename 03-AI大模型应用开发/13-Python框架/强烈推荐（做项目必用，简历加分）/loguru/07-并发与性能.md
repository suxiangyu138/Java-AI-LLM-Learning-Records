## 1. 线程安全与文件写入

**单进程内多线程写同一 sink，loguru 默认线程安全**——每条日志通过内部锁串行化落盘，不会出现行交错、半行污染。这是默认保证，不需要任何参数。但要认清它的代价：锁意味着**写入是串行的**，高并发下日志线程会成为瓶颈之一——这正是 `enqueue=True` 存在的理由。

**单进程多线程场景的判断**：Web 服务（FastAPI 单进程多 worker 之前）、脚本、爬虫的线程池——直接写没问题，日志量级（每秒几百条）远到不了锁的瓶颈。

## 2. enqueue=True：队列化写入

`enqueue=True` 把日志改为**异步队列模型**：打日志 → 消息进内存队列 → 专门的队列线程统一消费落盘。三个收益：

**其一，主线程零阻塞**——日志写入从"同步 IO"变成"入队 O(1)"，打日志不再拖慢业务线程。**其二，多进程安全**——进程 A/B/C 共享同一个队列消费者，只有消费者线程真正写文件，多进程写同一文件不再互踩。**其三，异步支持**——队列模型天然兼容协程 sink。

代价同样要看清：**日志延迟落盘**（毫秒级，可接受）；**进程崩溃丢尾部日志**——队列里未消费的消息随进程一起没了。对"尽力而为"的普通日志没问题；**审计类日志（必须不丢）不应走内存队列**，或配合 `blocking=False` 权衡。`enqueue=True` 还额外提供 `blocking` 参数：默认 `False`（入队不等待，极端背压时丢消息），审计场景可设 `True`（队列满时业务线程阻塞等待，保证不丢）。

## 3. 多进程部署的轮转竞态

这是生产最隐蔽的坑：**多进程同时写一个文件 + 轮转**时，两个进程可能同时判断"该轮转了"、同时尝试改文件名——结果文件错乱或轮转丢失。`enqueue=True` 通过"唯一消费者"根治了它（04 篇已预告）。**gunicorn/FastAPI 多 worker、K8s 多副本共享挂载卷**——这类部署形态的文件日志必须 `enqueue=True`，否则轮转竞态迟早出现。

> 💡 **提示**：多副本场景还有一种更简单的选择——**每个副本写自己的文件**（文件名带 PID 或实例 ID，如 `app_{time}_{process}.log`），采集端（Loki/ELK）按实例聚合。`{process}` 字段可以直接用在文件名里。两种方案对比：enqueue 统一文件简单；按实例分文件天然无竞态但文件数随副本数增长。

## 4. 异步 sink 与 complete()

loguru 支持**协程函数作为 sink**——异步应用（FastAPI、async 爬虫）可以把日志直接交到事件循环里处理：

```python
async def async_sink(message):
    await http_sender.post(message)     # 异步发送到远程日志服务

logger.add(async_sink, enqueue=True)    # 异步 sink 必须配 enqueue=True

# 应用退出前等待异步日志全部发送完
logger.complete()
```

关键点：**异步 sink 必须配合 `enqueue=True`**（否则协程不会被执行）；`complete()` 在关闭前调用，阻塞直到所有排队的异步日志处理完——**漏掉 complete() 的后果：退出瞬间排队的日志静默丢失**。异步 sink 的典型场景：日志推到远程（HTTP/数据库/云日志服务），不阻塞业务协程，又比同步 HTTP 推送快得多。

## 5. 性能优化点全景

loguru 官方宣称"比标准库快 10 倍"（部分场景），路线图是 C 实现（0.7.3 尚未包含，属未来计划）。当前纯 Python 实现的性能优化点按收益排序：

**第一档：惰性求值**——`opt(lazy=True)` 和 `{}` 占位（不满足级别时参数不计算，03 篇）——**热路径上最值得做的优化**，一个 f-string 改占位符可能省掉昂贵 repr。

**第二档：减格式化开销**——`serialize=True`（JSON 序列化）比文本格式化贵；`enqueue=True` 把格式化挪到消费线程（业务线程只入队）；0.7.3 已提速 datetime 格式化（日志热路径最大单项开销之一）。

**第三档：减少日志量**——级别治理（06 篇：生产 INFO）、DEBUG 不常驻——**日志量减 90% 比任何微优化都有效**；loguru 对"被过滤的日志"开销极小（跳过硬格式化）。

**第四档：并行写入**——多个 sink 是串行消费的（同一日志事件过所有 sink）；日志量大时拆 sink 数（每个 sink 独立文件）能分散写压力——但一般到不了这一步，先做前三档。

## 6. 性能取舍决策

| 场景 | 推荐配置 | 理由 |
|------|---------|------|
| 脚本/CLI | 默认 stderr | 零配置，性能无压力 |
| 爬虫（线程池） | 文件 sink + `enqueue=True` | 多线程写文件安全 + 不阻塞抓取 |
| FastAPI 单进程 | 文件 + enqueue | 队列缓冲突发日志 |
| 多 worker 部署 | 文件 + enqueue（或按实例分文件） | 根治轮转竞态 |
| 异步高吞吐 | 异步 sink + complete() | 事件循环内不阻塞 |
| 审计（不丢） | 文件 + enqueue + blocking=True | 保证不丢，接受阻塞 |

**核心决策问题只有一个：日志会不会丢/乱/卡业务**——普通日志选"快"（enqueue 默认），审计日志选"稳"（blocking=True），远程推送选"异步 sink + complete()"。

## 7. 常见坑

**坑一：异步 sink 忘配 enqueue=True**——协程 sink 不执行，日志静默消失（排查第一问：你的 sink 是 async 函数吗）。

**坑二：退出前漏 complete()**——FastAPI shutdown 钩子里没调 `logger.complete()`，最后几秒的日志（往往正好是错误）丢了。

**坑三：多进程裸写文件 + 轮转**——没 enqueue，轮转竞态导致文件错乱（第 3 节）。

**坑四：以为 enqueue=True 就不丢日志**——它防的是"并发写坏"，不防"崩溃丢尾部"；审计日志要 blocking=True 或专用通道。

> 🎯 **核心要点**：并发日志的正确姿势 = **多线程直接写（默认安全）+ 多进程上 enqueue（唯一消费者根治轮转竞态）+ 异步场景 async sink + complete()**；性能优化的第一原则是"**减量优于加速**"——级别治理 > 惰性求值 > 格式化优化 > 并行写入。
