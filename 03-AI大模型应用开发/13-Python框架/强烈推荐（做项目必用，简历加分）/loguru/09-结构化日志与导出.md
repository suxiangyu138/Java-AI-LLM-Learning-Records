## 1. 为什么需要结构化日志

纯文本日志的问题：**靠正则和肉眼筛**——`grep "error"` 筛出噪音、时间字段各家格式不统一、业务字段（订单号、trace_id）无法被查询引擎索引。结构化日志（每行一个 JSON 对象）把日志变成**可查询的数据**：Loki 的 LogQL、ELK 的 Kibana 可以直接按 `order_id`、`trace_id`、`level` 字段过滤聚合，比 grep 文本快一个数量级。

什么时候必须结构化：**部署了 Loki/ELK/云日志服务**（采集端吃 JSON 行，schema 即检索字段）；**业务需要按字段查询**（按订单号捞全部日志、按 trace_id 串链路）；**多服务聚合**（字段统一才能跨服务关联）。纯单机脚本、只看终端输出则不必——**结构化是给采集与检索准备的，不是给终端准备的**。

## 2. serialize=True：JSON 行输出

一行配置，sink 输出变成 JSON 行（每行一个完整 JSON 对象）：

```python
logger.add("logs/app.jsonl", serialize=True, rotation="500 MB", enqueue=True)
```

输出示例（每行一个 JSON）：

```json
{"text": "订单 1001 已支付", "record": {"elapsed": {"repr": "0:00:00.123456", "seconds": 0.12}, "exception": null, "extra": {"user_id": 7}, "file": {"name": "app.py", "path": "app.py"}, "function": "pay_order", "level": {"icon": "ℹ️", "name": "INFO", "no": 20}, "line": 42, "message": "订单 1001 已支付", "module": "app", "name": "__main__", "process": {"id": 1234, "name": "MainProcess"}, "thread": {"id": 4321, "name": "MainThread"}, "time": {"repr": "2026-08-10 10:00:00.123456", "timestamp": 1754805600.12}}
```

结构特点：`text` 是渲染好的完整文本（含颜色标记外的全部内容），`record` 是结构化字段全集（时间戳是 epoch 秒、级别有 name/no/icon、extra 是业务字段）。**采集端直接吃 `record.extra` 和 `record.level.name`** 做索引。注意：`serialize=True` 时 format 参数仍生效于 `text` 字段，但采集端应该读 record 而不是解析 text——**text 是给人看的冗余，record 是给机器吃的数据**。

## 3. record 字段与业务字段注入

JSON 里真正值钱的字段是 `extra`——业务注入的字段，靠 03 篇的 bind/contextualize/patch 填充：

```python
# 入口中间件生成 trace_id，整条请求链自动携带
with logger.contextualize(trace_id=uuid4().hex, user_id=user.id, path=req.path):
    logger.info("请求开始")
    ...
    logger.error("数据库超时")   # 自动带 trace_id/user_id/path
```

**trace_id 是结构化的第一优先级字段**——没有它，多服务日志无法串成链路。生产模板的最小集：`trace_id`（链路追踪）、`service`（服务名，patch 全局注入）、`env`（环境）、`user_id`（业务归属）。字段名固定用 snake_case 小写，**schema 从第一天定好**——事后改名 = 查询脚本全改 + 历史数据作废（00 篇误区五）。

## 4. parse()：日志反解析

`parse()` 是从**已有日志文件**里用正则提取结构——反向操作，适合历史日志分析（正则命名组 + 类型转换器）：

```python
import re

pattern = r"(?P<time>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}) \| (?P<level>\w+) \| (?P<message>.*)"
for entry in logger.parse("logs/app.log", pattern, cast={"time": lambda s: ...}):
    print(entry["level"], entry["message"])
```

典型场景：**老项目没有结构化日志，但要用 Loki 查询历史日志**——先 `parse()` 批量转成 JSON 行再导入；或者采集端没配好时，离线把文本日志规整成结构化数据。`cast` 参数支持自定义转换（时间字符串 → datetime、数字字符串 → int）。

## 5. 对接观测平台

loguru 到观测平台的链路通常**不需要任何 loguru 插件**——JSON 行文件就是通用的交接协议：

**Loki**：Promtail/Alloy 采集 `app.jsonl`，JSON 解析成标签，`{service="pay"} |= "error"` 直接查。**ELK**：Filebeat 采集 JSON 行 → Logstash/ES 索引 → Kibana 按字段筛。**云日志（阿里云 SLS/腾讯 CLS）**：采集器原生支持 JSON 行。**OTel**：loguru 没有官方 OTel 集成，常见姿势是 JSON 行 → OTel Collector 的 filelog receiver 收进 pipeline——**日志进 OTel 的字段映射靠 JSON 结构保证**（与 Java 侧的 OTel Agent 采集方式不同，但产出格式一致，见总览分工）。

对接检查清单：文件命名/轮转格式（04 篇）要匹配采集器配置；时间字段用 ISO 格式（`time` 字段是 epoch 秒 + repr 双份，采集端选其一）；**脱敏在写入前做**——JSON 字段过采集端后再脱敏等于没脱（第 6 节）。

## 6. 成本与治理

结构化日志的成本与对策：

**磁盘膨胀**——JSON 行比文本大 2-4 倍（字段冗余）：对策是轮转 + retention + compression（04 篇组合拳），或只对"要检索的字段"保留。**序列化开销**——`serialize=True` 比文本格式慢（JSON 组装 + 转义）：高吞吐路径配合 `enqueue=True` 把序列化挪到消费线程。**敏感字段泄露**——`extra` 里塞了 `password`、`token` 会进 JSON 字段且被索引——**写入前脱敏**：

```python
def mask_sensitive(record):
    for k in ("password", "token", "api_key"):
        record["extra"].pop(k, None)

logger.add("app.jsonl", serialize=True, filter=lambda r: (mask_sensitive(r), True)[1])
```

**schema 治理**：字段名固定、类型固定（`user_id` 别一会 int 一会 str）、版本化（改字段加前缀或新字段名）；日志量治理优先于一切（06 篇级别策略）。

**时间字段规范是 schema 的隐藏地雷**：`record.time` 同时给出 `repr`（本地时区字符串）和 `timestamp`（UTC epoch 秒）——**采集端必须统一取 `timestamp`（转 UTC ISO）**，否则"早上 8 点的日志"在容器时区不同的环境里排序错乱。生产模板：时间在写入端统一 UTC、展示端再转本地，日志时间只认一个口径。

**日志量预算思维**：每行 JSON 平均 300-500 字节，INFO 全量每天每进程约 50-200 MB——**上线前先算日志预算**（日量 × 保留天数 ≤ 磁盘配额 × 压缩系数），算完再定级别与保留天数；日志成本失控的根因从来不是"库不好"，而是"没人算过账"（参考 04 篇容量规划）。

## 7. 与 structlog 对比

| 维度 | loguru | structlog |
|------|--------|-----------|
| 定位 | 通用日志库（简单优先） | 专注结构化日志（架构化） |
| 上手 | 零配置秒上手 | 需理解处理器/链式上下文 |
| JSON | `serialize=True` 一键 | 原生就是键值对，JSON 是默认输出 |
| 上下文 | bind/contextualize/patch | 绑定器链式更细粒度 |
| 性能 | 好（C 化路线图） | 好（同样强调惰性） |
| 生态 | 通用项目通吃 | 结构化重度场景 |

**选型判断**：**绝大多数项目用 loguru + serialize=True 就够了**——JSON 能力完整（extra 字段 + 上下文 + 序列化）；只有"日志即数据产品"的重度结构化场景（事件流分析、大量键值字段需要链式组装）才考虑 structlog。**用 loguru 的团队未来想换 structlog 也不难——JSON 输出格式是业界共同语言**。
