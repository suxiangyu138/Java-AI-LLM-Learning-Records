## 1. 一句话定位

**切分把 Document 切成 Node，索引把 Node 组织成可检索结构——"切分质量 = 检索上限，索引选择 = 查询模式"**：

```text
构建链路
├── 切分：NodeParser（定长/语义）→ List[Node]
├── 嵌入：embed_model（Settings 全局）→ 每个 Node 一个向量
├── 入库：Index（VectorStoreIndex 默认——组织 + 存储）
└── 持久化：storage_context（存了才能复用——否则每次重建）
    ——"切分器 + embedding + 存储 = 索引三要素"
```

**定位心智**：**"切分是'一次定生死'的环节——后面所有检索都在这批 Node 上发生"**——"**切太粗：一个 Node 装多个主题，检索召回带噪声；切太细：上下文割裂，答案缺上下文——'没有万能 chunk_size，按文档类型调'"**。

## 2. 切分策略

**两种主流切分器——定长与语义**：

```python
from llama_index.core.node_parser import SentenceSplitter, SemanticSplitterNodeParser
from llama_index.embeddings.openai import OpenAIEmbedding

# 定长切分：按句子边界凑 chunk（主流默认）
splitter = SentenceSplitter(chunk_size=512, chunk_overlap=20)

# 语义切分：embedding 算句间相似度，语义断裂处切（长文档质量更高）
splitter = SemanticSplitterNodeParser(
    embed_model=OpenAIEmbedding(model="text-embedding-3-small"),
    breakpoint_percentile_threshold=95,   # 相似度掉到 95 分位以下处切断
)
```

**选型**：普通文档（说明书/文章）用 SentenceSplitter 就够；**技术手册/长文档用语义切分**——"**定长 512/20 起步，检索质量不够再换语义切分**"；其他：`TokenTextSplitter`（按 token 数——多语言混合）、`MarkdownNodeParser`（按标题层级切——结构化文档保留大纲）。

**chunk_size 的权衡**（论述，不背参数）：chunk 越小检索越精准（一个节点一个主题），但答案需要的上下文可能被切散——chunk 越大上下文越完整，但一个节点塞进多个主题，相似度检索容易带噪声。经验区间 250-1000——**"先按文档的'段落粒度'定：说明书写 512、法律条款写 250、技术手册长段落写 768——'chunk 对齐文档的语义粒度，不是对齐数字'**"。`chunk_overlap`（20-50）用于缝合被切断的语义——"上一段结尾的信息在下一段开头，overlap 给检索兜底"。

## 3. IngestionPipeline：标准流水线

**把"切分 → 嵌入 → 入库"固化成可复现的流水线**：

```python
from llama_index.core.ingestion import IngestionPipeline
from llama_index.core.node_parser import SentenceSplitter
from llama_index.embeddings.openai import OpenAIEmbedding
from llama_index.vector_stores.qdrant import QdrantVectorStore

pipeline = IngestionPipeline(
    transformations=[
        SentenceSplitter(chunk_size=512, chunk_overlap=20),
        OpenAIEmbedding(model="text-embedding-3-small"),
    ],
    vector_store=QdrantVectorStore(...),   # 向量库（默认内存）
)
nodes = pipeline.run(documents=docs)       # 返回带 embedding 的 Node

pipeline.vector_store.add(nodes)           # 显式入库（转换 ≠ 存储）
```

**要点**：① `transformations` 是标准件列表——增删环节改列表即可，流水线可 `persist/load` 复用；② **转换与存储分离**——`pipeline.run()` 只产出带向量的 Node，入库要显式 `add`；③ 向量库可插拔——Chroma/Qdrant/Milvus 换一个实现（08 向量数据库体系）。

## 4. 索引类型

| 索引 | 结构 | 适合场景 | 记忆 |
|------|------|---------|------|
| VectorStoreIndex | 向量 + 相似度 | 默认选择——"找关于 X 的信息" | 约 95% 场景 |
| SummaryIndex | 全量顺序汇总 | 全文总结 | 小语料 |
| TreeIndex | 树状摘要聚合 | 摘要优先的问答 | 少用 |
| PropertyGraphIndex | 属性图 | 多跳关系查询 | 07 篇 |

**选型心智**：**"默认 VectorStoreIndex——95% 的 RAG 都够；要'总结全文'用 SummaryIndex；要'跨文档关系推理'用 PropertyGraphIndex"**——"**索引类型跟着'查询模式'走——先想清楚用户问什么"**；多个索引可并存——**"一个语料建多种索引（向量 + 摘要 + 图），Router 按问题路由（06 篇）——'索引不是二选一，是组合'"**。

## 5. 持久化与增量

```python
from llama_index.core import VectorStoreIndex, load_index_from_storage
from llama_index.core.storage import StorageContext

# 首次构建：from_documents（切分 + 嵌入 + 入库一步到位）
index = VectorStoreIndex.from_documents(docs)

# 持久化（存向量 + 文档 + 索引结构）
index.storage_context.persist(persist_dir="./storage")

# 后续加载：from_vector_store（绝不重复嵌入）
storage = StorageContext.from_defaults(persist_dir="./storage")
index = load_index_from_storage(storage)
```

**铁律**：**`from_documents` 只用于首次构建**——"生产加文档用 `InsertionBatch`/`pipeline.run` 增量插，别再 from_documents 全量重建（重新嵌入烧钱）"；持久化三件套（docstore/index_store/vector_store）一个目录搞定——**"能持久化 = 能复用 = 能上生产"**。

**向量库选择与持久化**：默认索引存内存——**"原型随便玩；生产接外部向量库（Chroma/Qdrant/Milvus——见 08-向量数据库 体系选型），索引数据随库持久化"**；换库只改 `vector_store` 构造——**"Index 与存储解耦 = 换库不换业务代码"**；生产用外部向量库后，`persist` 只管 docstore/index_store，向量在库里——**"备份要两头都备份（库 + persist 目录）"**。

## 6. 生产三坑

**坑一：重复文档重复嵌入**——`pipeline.run()` 不做去重——**解法：文档内容 hash 存 metadata，跑前过滤已处理 ID**。

**坑二：大语料 OOM**——>1 万文档一次 run 内存炸——**解法：分批 `docs[i:i+500]` 跑，嵌入并行化**。

**坑三：元数据不继承**——Node 的 metadata 只有 `Document(text=..., metadata={...})` 显式传才带——**解法：加载后打印 `nodes[0].metadata` 验证，别假设有**。

**流水线复用**：IngestionPipeline 可 `pipeline.persist("./pipeline")` / `IngestionPipeline.load`——**"切分/嵌入配置固化成文件，团队共用同一套参数，改参数走 review 不靠口口相传"**；`cache` 参数（`cache=IngestionCache`）缓存嵌入结果——**"同一文档二次跑直接命中缓存，增量更新的成本杀手锏"**。

## 7. 嵌入模型与增量更新

**嵌入模型选择（决定检索上限的第二杠杆）**：

| 模型 | 特点 | 场景 |
|------|------|------|
| text-embedding-3-small | 便宜、够用 | 起步/原型 |
| text-embedding-3-large | 质量高、贵 | 生产质量优先 |
| bge-m3 | 开源、多语言强 | 中文语料/本地部署 |

**铁律**：**建索引和查询必须同一个 embedding 模型——"换模型 = 全量重嵌入（dimension 不匹配直接报错，匹配了检索质量也废）"**；embedding 模型决定"语义边界"——**"检索上限由 embedding 定，其余都是逼近它"**。

**增量更新（生产常态——文档不断来）**：

```python
from llama_index.core import InsertionBatch

# 新文档插入（只切分嵌入新文档，不重建旧的）
batch = InsertionBatch(
    transformations=[SentenceSplitter(...), OpenAIEmbedding(...)],
    vector_store=index.vector_store,
    docstore=index.docstore,
)
batch.run(documents=new_docs)

# 删除文档（按 doc_id 精确删）
index.delete_ref_doc("doc-001", delete_from_docstore=True)
```

**要点**：① 增量插入前先做去重——文档 hash 存 metadata 过滤已处理 ID（生产三坑之一）；② 删除按 `doc_id`——**"所以 doc_id 要稳定可预测（文件名/业务 ID），不然删不了"**；③ 删改后要重建索引文件（图/树索引）——**"向量索引删改友好，复合索引删改要重建"**。
