## 1. 一句话定位

**混合检索补召回（关键词 + 语义两路），重排提精度（精排模型二轮筛选）——"召回宽、重排精，是 2026 年 RAG 生产的最小配置"**：

```text
高级检索三板斧
├── 多路召回：向量 + BM25 → 融合（QueryFusionRetriever）
├── 重排精化：交叉编码器/LLM 对 top-k 重新打分（Reranker）
└── 查询路由：按问题类型分派到不同引擎（Router/SubQuestion）
    ——"召回保证'不漏'，重排保证'不杂'，路由保证'问对人'"
```

**定位心智**：**"单路检索 = 起步；生产质量 = 混合 + 重排"**——"**先跑通单路（05 篇），质量不够再叠加——'加一路检索、挂一个重排，常常比换 embedding 模型见效快'"**。

## 2. 为什么单路向量检索不够

**向量相似度对三类查询天然弱势**：

```text
单路短板
├── 专有名词/ID：API 名、型号（"GBK-542"）——语义向量难区分
├── 精确匹配：代码、公式、合同条款——关键词才是硬信号
└── 缩写变体：BM25 命中字面、向量命中语义——两路互补
    ——"向量懂'意思'，BM25 懂'字面'——结合才全"
```

**心智**：**"向量检索回答'语义相关'，BM25 回答'字面相关'——多数查询是两者的混合——混合检索是默认生产配置，不是加分项"**。

## 3. 混合检索：QueryFusionRetriever

**0.13.0+ 的正确姿势（旧 HybridQueryEngine 已移除）**：

```python
from llama_index.core.retrievers import QueryFusionRetriever, VectorIndexRetriever
from llama_index.core.retrievers import BM25Retriever
from llama_index.core.query_engine import RetrieverQueryEngine

# 两路检索器
vector_retriever = VectorIndexRetriever(index=index, similarity_top_k=10)
bm25_retriever = BM25Retriever.from_defaults(
    docstore=index.docstore, similarity_top_k=10
)

# 融合检索器（0.13.0+ 必须显式指定 mode）
fusion_retriever = QueryFusionRetriever(
    retrievers=[vector_retriever, bm25_retriever],
    similarity_top_k=5,
    mode="relative_score",        # relative_score/reciprocal_rerank 等
)

query_engine = RetrieverQueryEngine(retriever=fusion_retriever, llm=Settings.llm)
```

**要点**：① `QueryFusionRetriever` 默认还会做"查询改写"（LLM 把原问题改写成多个变体再检索）——可传 `num_queries=4` 控制；② mode 必填（0.13+ 行为）——`relative_score` 常用；③ 融合思路通用：向量 + 图谱检索也能融（07 篇）——**"融合 = 把多路 top-k 合并重新排序"**。

## 4. 重排：Reranker

**重排器挂在 `node_postprocessors`——召回宽、重排精**：

```python
from llama_index.postprocessor.cohere_rerank import CohereRerank

query_engine = index.as_query_engine(
    similarity_top_k=20,          # 召回宽：先拿 20
    node_postprocessors=[
        CohereRerank(top_n=5, model="rerank-english-v3.0"),  # 重排精：留 5
    ],
    response_mode="compact",
)
```

**重排器家族**：

| 类型 | 原理 | 场景 | 记忆 |
|------|------|------|------|
| CohereRerank | 交叉编码器（付费 API） | 生产主流 | 质量/成本平衡 |
| LLMRerank | LLM 打分排序 | 无外部依赖 | 慢但全本地 |
| ColBERT/ColPali | 向量级精排 | 多模态/长文档 | 高阶 |

**心智**：**"重排的本质：用更强的模型（但更慢）对召回的候选重新打分——top_k 越大重排收益越高——'召回 20 重排留 5，质量通常碾压直接 top5'"**。

## 5. 生产配方

```text
生产检索配方（照抄起步）
├── 召回：VectorRetriever(top_k=20) + BM25Retriever(top_k=20) 融合
├── 重排：CohereRerank(top_n=5)
├── 过滤：metadata filter（库内）+ similarity cutoff（召回后）
└── 合成：compact + 带引用输出
    ——"召回宽 → 融合 → 重排精 → 过滤 → 合成：五步一条链"
```

**调优顺序（按 ROI）**：先挂重排（收益最大）→ 加 BM25 混合（补精确匹配）→ 调 chunk/embedding（动切分重嵌入，成本高放最后）——**"别一上来就换 embedding 模型——重排与融合便宜见效快"**。

**中文语料的特别注意**：BM25 是字面词频统计——**"中文不做分词时，'模型'与'模型训练'按子串匹配尚可，但'LLM'与'大语言模型'完全失联——中文语料混合检索的收益尤其大（向量补语义、BM25 补精确词）"**；中文 embedding 选 bge-m3 等中文强化模型（04 篇）——"**中文 RAG 的检索上限，一半在 embedding 选型，一半在混合与重排**"。

## 6. 查询路由与子问题

**不同问题走不同引擎——路由与拆解**：

```python
from llama_index.core.query_engine import RouterQueryEngine
from llama_index.core.tools import QueryEngineTool

tool1 = QueryEngineTool.from_defaults(engine=summary_engine, description="适合总结类问题")
tool2 = QueryEngineTool.from_defaults(engine=vector_engine, description="适合事实查询")

router = RouterQueryEngine.from_defaults(
    selector=LLMSingleSelector.from_defaults(),  # LLM 选路
    query_engine_tools=[tool1, tool2],
)
```

**心智**：**"Router 按'问题类型'分派（总结 → 总结引擎，事实 → 向量引擎）；SubQuestionQueryEngine 把'复杂问题'拆成子问题分别检索再合成（多跳查询）"**——"**路由解决'问对人'，拆解解决'问题太大'——都是 05 篇引擎的编排升级"**。

**路由的适用边界（论述）**：路由不是万能——**"引擎之间差异大才值得路由（总结 vs 事实），差异小路由反而是负担（多一次 LLM 选择 + 选错风险）"**；子问题拆解同理——"**问题能一次检索答好就别拆——拆解的成本 = 多次检索 + 多次 LLM 调用 + 合成时的信息损耗**"。"**判断标准：问题是否天然可分（多实体/多条件）——是才拆**"。两个工具都要配好 `description`（路由选择的依据）——"描述写清'擅长什么、什么时候用'，选错率立刻降"。

## 7. 融合模式与成本评估

**融合模式怎么选（论述，不背参数）**：

```text
两种主流融合
├── reciprocal_rerank：按排名倒数的倒数计分——只认"位次"不认"分数"
│    ——不同检索器分数不可比时用（向量 0.8 vs BM25 15 没有可比性）
└── relative_score：先归一化各路的分数再相加——保留"分数强度"信息
    ——各路分数分布相近时用（如两个向量检索器）
    ——"位次法稳、分数法精——混合异构检索器（向量+BM25+图）默认位次法"
```

**成本三笔账**：① 查询改写（`num_queries=4` 即 4 次 LLM 调用——省成本改 1）；② BM25 无成本（本地关键词）；③ 重排 API 按调用量计费——**"生产配方成本排序：重排 > 查询改写 > 融合本身——'先用单查询 + BM25 + 重排起步，效果不够再加改写'"**；**与 LangChain 的检索对比**：LlamaIndex 的检索组件开箱即用、无需自己拼（框架开销约 6ms vs LCEL 10ms/LangGraph 14ms）——"**纯 RAG 场景 LlamaIndex 更快更省——'编排复杂度低时别用重框架'"**（01 篇选型）。

**评估驱动调优**（配尺子再动手）：**改造前先跑 `RetrieverEvaluator`（HitRate/MRR）拿基线 → 加一路检索 → 重跑对比 → 只保留"有数字提升"的改动**——"**凭感觉调参 = 玄学；评估数字说话 = 工程（09 篇评估方法）"**。
