## 1. search 基础：五个参数

```python
client.search(
    collection_name="demo_docs",
    data=[query_vector],            # 1. 查询向量（可多个，批量检索）
    limit=10,                       # 2. 返回条数（top_k）
    output_fields=["title", "source"],  # 3. 返回哪些标量字段
    filter='category == "news"',    # 4. 过滤表达式
    search_params={"metric_type": "COSINE", "params": {"ef": 100}},  # 5. 检索参数
)
```

五个参数各管一件事：**data** 是查询向量列表（一条查询或多条批量查询）；**limit** 是返回条数（RAG 上下文一般 3-10 条）；**output_fields** 决定结果里带哪些标量字段（**不带 = 只返回 id 和 distance**——忘了加它是最常见的"结果没内容"事故）；**filter** 是标量过滤表达式（第 3 节）；**search_params** 是当次检索的精度旋钮（第 2 节）。**RAG 完整姿势**：search 拿到 id + 字段 → 拼 prompt → 送 LLM——**search 是检索链路的第一环，output_fields 决定后续能拼出什么上下文**。

## 2. search_params：当次检索精度

search_params 里两个关键位：**metric_type**（必须与索引度量一致）与 **params**（索引特定的查询参数）：

```python
# HNSW：ef 越大召回越高、越慢
search_params={"metric_type": "COSINE", "params": {"ef": 100}}

# IVF：nprobe 越大召回越高、越慢
search_params={"metric_type": "L2", "params": {"nprobe": 16}}

# 范围过滤：只返回距离在范围内的结果
search_params={"metric_type": "COSINE", "params": {"ef": 100,
               "radius": 0.7, "range_filter": 0.5}}
```

**"构建参数定索引质量、查询参数定当次精度"**（06 篇）：ef/nprobe 就是查询时的召回旋钮——**线上调试"召回不够"先加大 ef/nprobe 验证，再考虑重建索引**。范围过滤（radius/range_filter）做"相似度阈值"：**检索结果必须超过相似度阈值才返回**——RAG 里防止"硬凑的无关上下文"进 prompt（答案质量的关键防线，10 篇实战会用到）。

## 3. filter：先过滤再召回

**filter 是 search 的标量过滤条件**——"只在我关心的数据里找相似向量"。三种典型写法：

```python
# 等值/范围（结构化列）
filter='category == "news" and publish_year >= 2024'

# JSON 字段
filter='meta["lang"] == "zh" and $meta["source"] == "pdf"'

# 数组包含（ARRAY 字段）
filter='tags contains "ai"'
```

**表达式全家桶**：比较（`==`、`!=`、`>`,`<`,`>=`,`<=`）、逻辑（`and`、`or`、`not`）、包含（`in`、`contains`、`array_contains`、`json_contains`）、存在（`exists`——动态字段 `$meta` 判空用）。**"先过滤再召回"**意味着：过滤在向量相似度计算**之前/之中**执行，缩小检索范围——**过滤写得好，检索又快又准**（过滤字段要建好（03 篇列化），否则 filter 走全表扫描。

**生产心法**：**能过滤就过滤**——RAG 里"只搜最近 30 天的文档"（时间过滤）、"只搜某租户数据"（分区/过滤）都是标配；**filter 字段的选择在建 schema 时就该想好**（03 篇"可查询字段"四问）。

## 4. 返回结构解析

search 返回结构是"列表套列表"（外层每一条查询、内层该查询的命中）：

```python
results = client.search(...)
# results[0] = 第一条查询的命中列表
for hit in results[0]:
    print(hit["id"])                    # 主键
    print(hit["distance"])              # 相似度（COSINE 越大越相似）
    print(hit["entity"])                # output_fields 的字段字典
    print(hit["entity"]["title"])       # 具体字段
```

**三个易错点**：**distance 语义随度量变**（COSINE/IP 越大越好、L2 越小越好——06 篇）；**entity 只在 output_fields 指定时才有内容**；**空结果返回空列表**（不是 None——2026 年修复了空结果误判 None 的 bug，但代码仍要兼容空列表）。**RAG 调试**：打印第一条命中的 distance——**低于阈值说明检索召回质量有问题**（换参数/换索引/换 embedding 模型）。

## 5. 限定分区与集合

```python
client.search(
    collection_name="demo_docs",
    data=[q],
    limit=5,
    partition_names=["news"],          # 只在 news 分区内检索
    anns_field="embedding",            # 指定用哪个向量字段检索
)
```

**partition_names**：限定分区检索——多租户/按业务分区的场景性能关键（04 篇分区）。**anns_field**：多向量字段集合（标题向量 + 内容向量）时指定本次用哪个字段检索——**"一个集合多向量 = 每次检索选路"**。还有 `output_fields`、`group_by_field`（3.0 分组去重——同组只留一条，避免同一文档多个 chunk 全占 top_k，**RAG 去重的高级姿势**）等参数。

## 6. hybrid_search：多路召回融合

**hybrid_search 是 2.6+ 的核心检索姿势**：多个检索请求（不同向量字段、不同度量、稠密 + 稀疏混合）并行执行，再把结果融合排序：

```python
client.hybrid_search(
    collection_name="demo_docs",
    reqs=[
        {"query": dense_vec, "anns_field": "dense_vec",
         "limit": 10, "search_params": {"metric_type": "COSINE"}},
        {"query": sparse_vec, "anns_field": "sparse_vec",
         "limit": 10, "search_params": {"metric_type": "IP"}},
    ],
    ranker=RRFRanker(k=60),      # 融合排序器
    limit=10,
    output_fields=["title"],
)
```

**为什么需要它**：单路稠密检索的短板——**专有名词/精确匹配/短词检索**（"RAG 体系的混合检索共识"）：稠密向量管语义相似（"如何部署"≈"怎么安装"），稀疏向量管关键词精确（"LlamaIndex"一字不差）。**"稠密管语义 + 稀疏管关键词"双路召回，融合排序取长补短**——这是 2026 年 RAG 检索的事实标准组合（与 04-RAG 体系、LlamaIndex 的 QueryFusionRetriever 同思想，本体系给裸 SDK 姿势）。

## 7. Ranker：融合排序器

融合排序器决定多路结果怎么合并成最终 top-K，两种内置：

```python
from pymilvus import RRFRanker, WeightedRanker

RRFRanker(k=60)                    # 倒数排名融合：按排名位置融合，鲁棒
WeightedRanker(0.7, 0.3)           # 加权分数融合：按分数加权，权重自己定
```

**RRF（Reciprocal Rank Fusion）**：每条结果按"1/(排名+k)"计分融合——**对分数尺度不敏感**（稠密 COSINE 分数与稀疏 IP 分数量级不同，直接加权不公平），鲁棒性好——**默认推荐**。**WeightedRanker**：给各路分数加权相加——**适合知道哪路更重要**（如"稠密 7 成、稀疏 3 成"）。**融合调优心法**：先 RRF 跑通，再看"哪些结果被挤掉了"判断权重——**"RRF 保底，权重调优"**是混合检索的标准节奏。注意：稀疏向量做关键词检索前要先把文本转稀疏向量（BM25 算法或 SPLADE 模型，主体系/04-RAG 有工具）。

## 8. 常见坑

**坑一：output_fields 忘加**——结果只有 id/distance，RAG 拼不出上下文（第 1 节）。

**坑二：filter 用错字段**——过滤字段没在 schema 列化（走了动态字段）但表达式写法按列化写，报字段不存在；**JSON/动态字段过滤要用 `$meta[...]` 或 JSON 路径**。

**坑三：distance 语义搞反**——L2 结果里"最大的 distance"其实是"最不相似"；**按度量语义读 distance**。

**坑四：hybrid_search 的分数不匹配**——直接用 WeightedRanker 但稠密/稀疏分数量级悬殊，融合结果被单一维度主导；**先 RRF**。

**坑五：检索结果不过相似度阈值**——低质量上下文进 prompt；**radius/range_filter 或业务侧 threshold 过滤**。

> 🎯 **核心要点**：检索姿势 = **search 五参数（向量/top_k/字段/过滤/精度）+ filter 先过滤再召回 + radius 阈值防硬凑 + hybrid_search 双路召回 + RRF 融合**——"稠密管语义、稀疏管关键词、过滤管范围、阈值管质量"是生产 RAG 检索的完整配方。
