## 1. AsyncMilvusClient：原生异步

v2.5.3 起提供 `AsyncMilvusClient`——**与同步版完全同参**，方法全部返回协程：

```python
from pymilvus import AsyncMilvusClient

async_client = AsyncMilvusClient(uri="http://localhost:19530")

async def main():
    await async_client.create_collection("docs", dimension=1024)
    await async_client.insert("docs", data=[...])
    results = await async_client.search("docs", data=[q], limit=5)
```

**设计要点**：同参数 = 同步代码改 `await` 即成异步（迁移成本极低）；`AsyncMilvusClient` 与同步 `MilvusClient` 是两个独立类，**不混用连接**（一个连接对象要么同步要么异步）。SDK v2 的设计口号"原生 async/await，取代 v1 的 Future/回调"（01 篇）——**异步不是"能跑的补充"，是官方一等公民 API**。

## 2. 同步 vs 异步：选型边界

| 场景 | 选择 | 理由 |
|------|------|------|
| 脚本/批处理/爬虫 | 同步 | 简单直接，无事件循环 |
| FastAPI/异步服务 | **AsyncMilvusClient** | 同步调用会阻塞事件循环 |
| 高并发 Web | AsyncMilvusClient + gather | 吞吐最大 |
| 库内部（给他人调用） | 同步为主 | 兼容性最广 |

**核心纪律：异步服务（FastAPI、异步爬虫）里禁用同步客户端**——一次 search 阻塞事件循环 = 全服务卡顿（与 Python 异步体系"async def 里禁同步 IO"是同一纪律，那个体系讲过：**事件循环阻塞 = 全员等待**）。**反方向同样成立**：脚本/线程池场景用异步客户端没有收益（还要维护事件循环生命周期）——"**跟着应用形态走，不跟潮流走**"。

## 3. asyncio.gather 并发姿势

**异步的价值在并发**：同时发起多个独立操作，总耗时 ≈ 最慢单个而非总和：

```python
import asyncio

async def ingest_batch(batch):
    await async_client.insert("docs", data=batch)

async def main():
    # 并发插入 10 批（每批 5000 条）
    await asyncio.gather(*[ingest_batch(batch) for batch in batches])

    # 并发检索：一条 query 配 3 种召回
    q1, q2, q3 = await asyncio.gather(
        async_client.search("docs", data=[dense_q], limit=10, filter='category == "news"'),
        async_client.search("docs", data=[dense_q], limit=10, filter='category == "blog"'),
        async_client.hybrid_search("docs", reqs=[...], ranker=RRFRanker(), limit=10),
    )
```

**并发模型心智**：gRPC 请求是 IO 密集——**等待网络响应期间让出事件循环，其他任务并行推进**——这是异步的全部收益来源。**并发度不是越高越好**：gRPC 连接池有上限，过度并发触发排队反而变慢——**从 8-16 路起步，压测找拐点**（10 篇压测方法）。

## 4. 批量写入吞吐调优

入库吞吐（RAG 灌库阶段）的可调旋钮按收益排序：

**第一：并发批次**——把大数据分成 N 批 + `asyncio.gather` 并发（或线程池）——**吞吐提升最明显，先做这个**。**第二：批次大小**——单批 1 千-2 万条区间压测找最优（05 篇：几百条浪费往返、几十万条单请求超时）。**第三：列式组织**——大批次用列式字典组织数据（字段为键）省序列化。**第四：分区并行**——多分区集合按分区并发写（分区间无锁）。**第五：服务器侧**——`num_shards` 分片数、flush 节奏（数据进内存即可继续，不用等落盘）——**服务器调优看主体系**。

**验收指标**：记录"条/秒"与"单批耗时"——**入库吞吐目标：单进程万条/秒级（小向量）可达到；达不到先看并发批次，再看批次大小，最后看网络**。

## 5. 连接管理与 schema cache

**连接管理**：MilvusClient 内部管理 gRPC 连接池（默认自动维护），**长驻服务只建一次客户端、全进程复用**——"每次请求新建客户端"是性能事故（握手 + 连接建立成本巨大）。多环境（开发/测试/生产）各建一个客户端对象，互不干扰（02 篇）。**关闭纪律**：进程退出时 `close()`；FastAPI shutdown 钩子里关闭（与 loguru 的 complete() 同习惯——"**退出前收尾**"）。

**schema cache**：SDK v2 的关键优化——**首次获取集合 schema 后本地缓存**，后续 insert/query/search 免去重复校验请求。影响与注意：**集合结构变更（add/drop 字段）后，客户端缓存可能过期**——变更后如遇"明明改了字段还报错"，重建客户端或等待缓存刷新（重连是最简单的兜底）。**收益量化**：高频读写场景减少网络往返与服务端 CPU，**延迟与开销明显下降**（01 篇）——**这是 SDK v2 比 v1 快的底层原因之一**。

## 6. 超时与重试

**超时**：所有操作支持 `timeout` 参数——**生产必配**（默认可能长时间挂住）：

```python
await async_client.search("docs", data=[q], limit=5, timeout=10)
```

**超时设计**：检索超时 5-10 秒（向量检索毫秒级响应，超时说明索引没加载/服务器过载）；插入超时 30-60 秒（大批次需要更长）；**超时值 = 正常耗时的 3-5 倍**（给抖动留余量，又不会挂死）。

**重试策略**：**只对可重试错误重试**——连接类（`ConnectionConfigException`/`ServerNotAvailableException`）可重试；**业务类（主键冲突、schema 校验失败）重试无意义**。**指数退避 + 抖动**：1s → 2s → 4s 退避，加随机抖动防"重试风暴"；**重试 3 次封顶**。**幂等性**：insert 失败重试要防重复主键——**大批量重试前先 query 校验已插入范围**（05 篇断点续灌思想）。

## 7. 性能监控

生产性能监控四件事：**指标**——单次操作耗时 P95/P99、吞吐（条/秒）、错误率；**位置**——客户端耗时 vs 服务器耗时（客户端慢查网络/序列化，服务器慢查索引/负载）；**工具**——服务器侧有 metrics 端点（Prometheus，主体系讲）、`get_collection_stats` 查行数、客户端计时装饰器（简单打点：`time.perf_counter` 包 search）；**告警**——P99 超时率、错误率、连接失败数上告警（日志告警体系配套）。**性能是迭代的**：先测基线（第 3 节并发度拐点、第 4 节批次拐点）→ 调优 → 复测——**"每个旋钮都要有压测依据"**（10 篇压测三问）。

## 8. 常见坑

**坑一：异步服务里用同步客户端**——事件循环阻塞，全服务卡顿（第 2 节纪律——最严重且最隐蔽的坑）。

**坑二：每次操作新建客户端**——连接成本爆炸；**长驻服务一个客户端全进程复用**。

**坑三：并发度拉满**——连接池排队，吞吐不升反降；**从 8-16 路起步压测找拐点**。

**坑四：集合结构变更后缓存过期**——"改了 schema 还报旧错误"；**重建客户端兜底**。

**坑五：无 timeout 裸奔**——网络抖动时请求挂住，服务线程被耗尽；**所有操作显式 timeout**。
