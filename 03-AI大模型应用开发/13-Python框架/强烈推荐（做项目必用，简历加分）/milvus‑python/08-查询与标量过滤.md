## 1. query 与 search 的分工

**search 管"相似"（向量召回），query 管"精确"（条件取数）**——两者是 Milvus 的两大读取通道，分工清晰：

| 维度 | search | query |
|------|--------|-------|
| 依据 | 向量相似度 | 标量表达式 |
| 输出 | 按相似度排序的 top_k | 满足条件的全部（可排序分页） |
| 典型场景 | RAG 召回 | 按 ID/条件取数、数据校验、管理 |
| 性能 | 索引加速 | 标量索引/全表扫描 |

**协同姿势**：RAG 里"search 召回 top_k → query 按 id 补齐字段"（search 的 output_fields 已能带字段，但需要"补拉"时 query 更直接）；数据流水线里"query 验证写入是否成功 → 按条件清理"。**边界判断**：要"最相似的 K 条"用 search；要"满足某条件的所有记录"（无论相似度）用 query——**"相似度思维 vs 条件思维"是选错接口的第一原因**。

## 2. query 基础参数

```python
client.query(
    collection_name="demo_docs",
    filter='category == "news"',     # 过滤表达式
    output_fields=["id", "title", "source"],   # 返回字段
    limit=100,                       # 返回条数
    offset=100,                      # 跳过条数（分页）
    partition_names=["news"],        # 限定分区
)
```

**要点**：**filter 是核心参数**（不传 = 全表取数，慎用！）；**limit 必传习惯**——不传 limit 可能返回全部匹配（大集合直接爆内存）；`offset + limit` 做传统分页（第 5 节讲迭代器为何更优）。**output_fields 同上**（不带 = 只回主键）。query 返回结构是普通字典列表：

```python
rows = client.query(...)     # [{"id": 1, "title": "...", "source": "pdf"}, ...]
for row in rows: print(row["title"])
```

**query 的常见用途**：按条件批量取数（"取所有 category=draft 的文档"）、写入验证（"insert 后 query 看数据在不在"）、管理操作前置检查（delete 前 query 确认目标——05 篇纪律）。

**query 与 search 的协同实战**（RAG 里的"检索 + 补拉"组合）：search 只带 `output_fields=["id"]` 快速召回（省流量），拿到 id 列表后 `get`/`query` 补齐大字段（content 全文）——**"search 先筛出候选，query 再取细节"**在 context 大的场景省一半网络传输；批量场景（多查询合并去重）用 `query(ids 过滤)` 一次取全。**协同的判断标准**：output_fields 能覆盖就不查第二次——**一次 search 拿全 vs 两段式取数，按 payload 大小与字段数量权衡**。

## 3. 表达式语法全解

filter 表达式是 Milvus 的查询语言，家族完整：

```python
# 比较：== != > < >= <=（数值/字符串/日期）
'publish_year >= 2024 and category != "archive"'

# 逻辑组合：and or not（括号改变优先级）
'(category == "news" or category == "blog") and not status == "deleted"'

# 包含：in / like / contains
'id in [1, 2, 3]'
'title like "Milvus%"'                  # 前缀匹配（like 是前缀语义）
'tags contains "ai"'                    # ARRAY 字段包含

# JSON 字段路径
'meta["lang"] == "zh"'
'$meta["source"] == "pdf"'              # 动态字段用 $meta

# 数组/JSON 深度
'array_contains(tags, "ai")'            # 等价 contains
'json_contains(meta, "key")'            # JSON 键存在
'exists($meta["chunk_no"])'             # 动态字段判存在
```

**三个易错点**：**字符串要引号**（`category == "news"`，单双引号都行，但值必须带引号）；**like 是前缀匹配不是 SQL 的 % 模糊**（`like "Milvus%"` 匹配以 Milvus 开头）；**JSON/动态字段要用 `[]` 路径**（`.` 点号在早期版本不统一，`[]` 写法最稳）。表达式在 search 的 filter 参数里同语法（07 篇）——**一套表达式语言，search/query/delete 通用**。

## 4. get：按主键快取

```python
client.get(
    collection_name="demo_docs",
    ids=[1, 2, 3],
    output_fields=["title", "embedding"],
)
```

**get = 按主键直接取**（不需要 filter 表达式），语义精确、性能快（主键是聚簇的）。**典型场景**：search 拿到 id 后按 id 补全数据（第 1 节协同姿势的最简形态）；数据存在性检查。**细节**：不存在的 id 静默跳过（不报错）——"**get 结果数量 < 请求数量，先怀疑 id 不存在而不是出错**"；get 在集合未加载时也可用（query/search 需要加载，get 走标量路径）。

## 5. 分页与迭代器

**大结果集的两种取法**：

```python
# 方式一：offset/limit 分页（小结果集）
page1 = client.query(..., limit=100, offset=0)
page2 = client.query(..., limit=100, offset=100)

# 方式二：迭代器（大结果集，官方推荐）
iterator = client.query_iterator(
    collection_name="demo_docs",
    filter='category == "news"',
    batch_size=1000,
)
for batch in iterator:
    for row in batch:
        process(row)
```

**offset/limit 的代价**：offset 越大越慢（跳过 N 条 = 扫描 N 条）——**10 万条里取第 9 万页，性能灾难**。**迭代器（query_iterator）**按主键分段取数，服务端游标推进，**适合百万级全量导出/清洗**——"**分页查界面，迭代器查全量**"是选型口诀。迭代器在 2.6.x 继续可用（gRPC 形态）；超大导出考虑"按主键范围分段 query"做并发（09 篇并发姿势）。

**超大导出的并发分段姿势**（主键是 INT64 时）：

```python
async def export_range(lo, hi):
    rows = await async_client.query("docs", filter=f"id >= {lo} and id < {hi}",
                                    limit=100_000, output_fields=[...])
    save_batch(rows)

# 按主键均分 N 段，并发导出（09 篇 gather 姿势）
await asyncio.gather(*[export_range(i * step, (i + 1) * step) for i in range(N)])
```

**适用判断**：主键连续分布（自增 id/时间戳 id）才适合分段——**均匀分段的前提是主键均匀**；主键稀疏/字符串主键用迭代器更稳。**"迭代器最稳、分段最快、分页最慢"**是导出性能的排序。

## 6. 3.0 聚合查询

3.0 给 query 增加了聚合能力（查询端聚合，不把全量拉到客户端）：

```python
client.query(
    collection_name="demo_docs",
    filter='category == "news"',
    aggr="count",              # 计数：有多少条匹配
    group_by_field="category", # 分组字段
)
```

**能力**：`count`（匹配条数）、`group_by`（分组计数）、`aggregation`（max/min/sum/avg 等标量聚合）、**faceted search**（search 结果同时返回 facet 分布——"搜索结果里按类目/年份计数"）。**适用**：管理面板统计（"news 类目有多少文档"）、检索结果分面（电商搜索结果侧栏的类目分布）、数据质量检查（某字段空值比例）。**注意**：聚合是 3.0 服务器专属（2.6 报 unknown-field）；统计类需求先考虑"用 get_collection_stats 还是聚合"——**stats 是集合级快照，聚合是查询级实时**，需求粒度决定接口。**faceted search 的落地形态**：search 请求带 `group_by_field`/facets 参数，返回里除命中列表外附带各分组的计数——**"检索 + 分面统计一次往返"是搜索产品的标配能力**（电商类目筛选栏、知识库按来源过滤），3.0 前要两次查询拼装，现在一次完成。

## 7. 常见坑

**坑一：query 不传 filter**——全表取数 + 不传 limit = 内存爆炸；**query 必带 filter + limit**（除非明确要全量且用迭代器）。

**坑二：字符串值忘引号**——`filter='category == news'` 直接报语法错；**值一律加引号**。

**坑三：like 当 SQL 用**——`like "%xxx%"` 中间模糊匹配在 Milvus 是前缀语义，写错查不到；**需要中间匹配用字符串字段 + 提前设计（或走向量/关键词检索）**。

**坑四：offset 深分页**——10 万条后翻页越来越慢；**全量用迭代器，界面分页限制在千级以内**。

**坑五：get 结果变少以为出错**——不存在的 id 静默跳过；**先确认 id 在不在（query 校验）**。
