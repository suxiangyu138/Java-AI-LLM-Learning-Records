## 1. 索引是什么：速度与精度的交易

向量检索的本质是"找最相似的 K 个向量"——**朴素做法是暴力扫描（FLAT）**：每个查询向量与库中全部向量算相似度，准确但慢。**索引是用空间/构建时间换检索速度的数据结构**：它牺牲"保证找到最相似"（近似，ANN）换取毫秒级响应。**核心心智：向量索引是"速度与精度"的交易**，交易参数决定你在天平上的位置：

- **召回率**（找到真正最相似的比例）——用户感知的质量
- **查询延迟**（单次 search 耗时）——用户体验
- **构建时间/内存**（建索引与驻留内存的成本）

没有免费的午餐：召回率要 100% 就退化为暴力扫描（FLAT）；要高召回 + 低延迟就要更多内存和更长构建时间。**工程上 95-99% 召回率是常见目标**——肉眼不可见的召回损失换 10-100 倍查询加速。

## 2. 度量类型三选一

度量（metric）定义"相似"的算法，建索引时必须选定：

| 度量 | 含义 | 适用 |
|------|------|------|
| `COSINE` | 余弦相似度（向量夹角） | **RAG 默认**（embedding 模型普遍用它训练） |
| `IP` | 内积（含大小与方向） | 向量已归一化时与余弦等价 |
| `L2` | 欧氏距离（越小越相似） | 距离语义明确的场景 |

**选型要点**：embedding 模型（OpenAI/国产 BGE 等）官方推荐通常写明了——**按模型文档选**，多数 RAG 用 COSINE；换度量要重建索引（索引按度量构建）——**度量与维度一样，建库定死**（03 篇）。搜索结果按度量语义排序：COSINE/IP 越大越相似（`distance` 值越大越好），L2 越小越相似。

## 3. 索引类型全家族

| 索引 | 类型 | 特点 | 适用 |
|------|------|------|------|
| `FLAT` | 暴力扫描 | 100% 召回，最慢 | 小数据（<10 万）验证 |
| `IVF_FLAT` | 聚类 + 倒排 | 快，召回略降 | 中等数据（百万级） |
| `IVF_PQ` | 聚类 + 乘积量化 | 省内存，精度降 | 超大库内存受限 |
| `HNSW` | 多层图 | 快 + 召回高 | **生产默认推荐** |
| `DISKANN` | 磁盘图 | 数据驻磁盘 | 十亿级超大库 |
| `GPU_CAGRA`/`GPU_IVF` | GPU 索引 | 极快（需 GPU 节点） | 高吞吐 GPU 集群 |
| `SPARSE_INVERTED_INDEX` | 稀疏倒排 | 稀疏向量专用 | 词袋/BM25 检索 |

**HNSW 是生产主力**：图结构让它在"延迟、召回、内存"三角上综合最优，10 万-千万级数据量都合适；IVF 系适合"数据大 + 内存有限"的工程权衡；DISKANN 是 HNSW 的"数据太大放不下内存"时的续集；GPU 系是 2026 年 HNSW 之上的吞吐王（需服务器有 GPU，`部署工具`/主体系的 GPU 部署配合）；FLAT 只用于小数据验证——**"能上 HNSW 就上 HNSW"是 RAG 项目的默认答案**。

## 4. HNSW 与 IVF 参数详解

**HNSW 两个参数**（构建时定，查询时还有 ef）：

```python
index_params.add_index(
    field_name="embedding", index_type="HNSW",
    metric_type="COSINE",
    params={"M": 16, "efConstruction": 200},
)
```

- **M**：每个节点的最大连接数（8-64）。越大图越稠密 → 召回越高、内存越大、构建越慢。**经验值 16-32**。
- **efConstruction**：构建时候选队列大小（100-500）。越大构建质量越高（召回提升），构建越慢。**经验值 200**。

查询时 HNSW 还有 `ef`（search_params 里）：候选队列越大召回越高、查询越慢——**"构建用 M/efConstruction 定质量，查询用 ef 定当次精度"**是 HNSW 调优的完整闭环（07 篇）。

**IVF 两个参数**：`nlist`（聚类中心数，构建时；越大越精细，构建越慢）、`nprobe`（查询时扫描的聚类数，越大召回越高越慢）。**IVF 的调优心法**：nlist 按数据量取（10 万级取 1024 左右），nprobe 从 8 开始往上试——**"nlist 管构建、nprobe 管查询"**与 HNSW 同构。

## 5. 稀疏向量索引与 3.0 新索引

**稀疏向量**（`SPARSE_FLOAT_VECTOR`）是 2.5+ 的重要能力：向量绝大多数维度为 0（词袋、BM25 特征、SPLADE），只存非零坐标。索引用 `SPARSE_INVERTED_INDEX`（稀疏倒排）：

```python
index_params.add_index(
    field_name="sparse_vec", index_type="SPARSE_INVERTED_INDEX",
    metric_type="IP",   # 稀疏向量用 IP 度量
)
```

稀疏检索的典型场景：**BM25 关键词检索**——把文档/查询转成稀疏向量，与稠密向量检索互补（**"稠密管语义、稀疏管关键词精确匹配"**，07 篇 hybrid_search 双路融合）。**3.0 新索引**：`dataCoord.targetVecIndexVersion=10` 启用新版向量索引后，**SINDI** 成为稀疏 IP 检索默认、**MaxScore** 成为 BM25 默认（更快的稀疏检索算法）——3.0 服务器的稀疏检索性能是 2026 重点演进（01 篇 3.0 线 opt-in 注意：开新版索引格式不能回滚 2.6）。

## 6. 选型决策链路

生产选索引按"数据量 → 查询要求 → 硬件"三步：

**第一步：数据量**——小于 10 万：FLAT 或 HNSW（体验召回 100% 的代价）；10 万-千万：**HNSW 默认**（内存足够时）；千万-亿级内存放不下：IVF_PQ（省内存）/ DISKANN（数据驻磁盘）；十亿级 + GPU：GPU_CAGRA。

**第二步：查询要求**——低延迟（毫秒级）选 HNSW/GPU；高召回优先 HNSW + 大 ef；吞吐优先 GPU/IVF 系。

**第三步：硬件约束**——内存紧张用 IVF_PQ/DISKANN；有 GPU 节点考虑 GPU 索引。

**验证闭环**：**索引参数最终靠"召回率测试"验收**——抽样查询算 recall@K（10 篇实战有方法），95%+ 合格；**"网上抄的参数大概率不差，但你的数据要自己验证"**是索引调优的唯一真理。

## 7. 索引生命周期

```python
client.create_index(collection_name="demo_docs", index_params=index_params)  # 建索引
client.drop_index(collection_name="demo_docs", index_name="...")             # 删索引
client.describe_index(collection_name="demo_docs", index_name="...")         # 索引详情
client.list_indexes(collection_name="demo_docs")                             # 全部索引
```

**要点**：集合建索引后才能加载检索（04 篇"索引 + 加载"组合）；建索引是**异步任务**（大集合要时间），`describe_index` 可查状态；**删索引后集合不可检索**（需要重建 + 重新加载）；一个集合可建多个字段的索引（稠密 + 稀疏共存，07 篇混合检索的前提）。**生产节奏**：数据灌完 → 建索引 → 等索引 Ready → 加载 → 检索。

## 8. 常见坑

**坑一：小数据上重型索引**——一万条数据建 HNSW + 大 efConstruction，构建时间比暴力扫描还长；**小数据 FLAT 验证，大数据 HNSW**。

**坑二：参数照抄不验证**——M/efConstruction/ef 的值与数据分布强相关；**每换一个数据源都要重测召回率**（第 6 节闭环）。

**坑三：稀疏向量用错索引**——稀疏字段用稠密索引（FLAT/HNSW）会报错或行为异常；**稀疏向量必须 SPARSE_INVERTED_INDEX**。

**坑四：索引没 Ready 就检索**——插入后立即 search 可能走旧索引或等待；**describe_index 确认 Ready + load 确认 Loaded 再服务**。
