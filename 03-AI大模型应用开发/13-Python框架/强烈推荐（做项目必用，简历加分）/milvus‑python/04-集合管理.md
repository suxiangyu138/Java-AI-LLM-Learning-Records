## 1. 集合：Milvus 的数据表

集合（Collection）是 Milvus 的数据组织单位，类比关系数据库的表：**一个集合 = 一套 schema（字段定义）+ 一批数据（实体行）+ 一个或多个向量索引**。集合有几种状态：**已创建未加载**（数据在但不可检索）、**已加载**（索引在内存，可检索）、**已释放**（内存归还）。这个"创建 ≠ 可检索"的两段式模型是 Milvus 与普通数据库的最大差异——**检索必须过内存索引，而索引加载是显式动作**。

集合命名规范：字母开头、可含数字与下划线、最长 255 字符。一个客户端可管理多个集合（`client.list_collections()` 列出全部），多租户可以"一租户一集合"或"一集合 + 分区键"（03 篇分区键）。

## 2. 创建：一步式与完整式

SDK v2 提供两种建集合姿势。

**一步式（最简）**——只给维度，自动生成 schema（单主键 + 单向量字段 + 默认索引 + 自动加载）：

```python
client.create_collection(
    collection_name="demo_docs",
    dimension=1024,
    metric_type="COSINE",
)
```

一行完成"建表 + 建索引 + 加载"——**原型开发首选**，但字段只有主键 + 向量，无法按标题过滤。

**完整式（生产）**——03 篇的 schema 图纸 + index_params + 显式加载：

```python
from pymilvus import MilvusClient, DataType
import pymilvus

schema = MilvusClient.create_schema(auto_id=False, enable_dynamic_field=True)
schema.add_field(field_name="id", datatype=DataType.INT64, is_primary=True)
schema.add_field(field_name="title", datatype=DataType.VARCHAR, max_length=512)
schema.add_field(field_name="embedding", datatype=DataType.FLOAT_VECTOR, dim=1024)

index_params = client.prepare_index_params()
index_params.add_index(field_name="embedding", index_type="HNSW",
                       metric_type="COSINE", params={"M": 16, "efConstruction": 200})

client.create_collection(
    collection_name="demo_docs",
    schema=schema,
    index_params=index_params,
)
```

**心智**：一步式是"快捷入口"，完整式是"标准姿势"——**生产集合必须完整式**（schema 决定未来查询能力，索引参数决定检索质量，见 06 篇）。`create_collection` 还可带 `partition_key`、`num_shards`（分片数，数据量大调）等参数。**重复创建同名校会报错**——先 `has_collection` 判断或 `drop_collection` 清理（测试脚本常犯）。

**三个进阶参数**：`num_shards`——分片数（数据写入的并行度，大数据量默认值不够时调大，如 10 万级调 8）；`partition_key_field`——03 篇分区键字段的声明位置（在 create_collection 指定"哪个字段是分区键"，配合 schema 的 `is_partition_key`）；`enable_dynamic_field` 已随 schema 走。**多向量字段集合**（标题向量 + 内容向量）：schema 里声明两个向量字段，index_params 里为每个字段 `add_index`——检索时用 `anns_field` 选路（07 篇）。

## 3. index_params 与加载

**索引参数独立于 schema 单独准备**——`prepare_index_params()` 返回索引参数对象，`add_index` 声明"哪个字段、什么索引、什么度量、什么参数"：

```python
index_params = client.prepare_index_params()
index_params.add_index(
    field_name="embedding",
    index_type="HNSW",            # 索引类型（06 篇全家族）
    metric_type="COSINE",         # 度量：COSINE/IP/L2
    params={"M": 16, "efConstruction": 200},  # HNSW 参数
)
```

**加载是检索的前提**：

```python
client.load_collection(collection_name="demo_docs")      # 加载进内存
client.release_collection(collection_name="demo_docs")   # 释放内存
```

**"索引 + 加载"两件事的关系**：索引是磁盘上的数据结构（建一次即可），加载是把索引装进内存（可反复加载/释放）。数据插入后索引**异步构建**，构建完成前检索可能慢或等待——**大批量插入后立刻搜索，先确认加载状态**。`get_load_state()` 查加载状态（Loaded/Loading/NotLoaded），批量导入流水线里这是必经检查点。

## 4. 状态管理全家桶

集合的生命周期操作全部是 client 方法：

```python
client.has_collection("demo_docs")        # 是否存在
client.list_collections()                 # 全部集合名
client.describe_collection("demo_docs")   # schema/分片/索引详情
client.get_collection_stats("demo_docs")  # 实体行数等统计
client.drop_collection("demo_docs")       # 删除集合（含数据，谨慎！）
client.rename_collection("demo_docs", "docs_v2")   # 重命名
client.get_load_state("demo_docs")        # 加载状态
```

**描述与统计是排障第一工具**：`describe_collection` 输出完整 schema（验证字段对不对）、`get_collection_stats` 给出行数（验证数据到底写进去没有）——"**数据插了却搜不到，先查 stats 行数，再查 load 状态**"是检索排查的标准顺序（10 篇报错速查）。drop 是**不可恢复操作**（数据全删），生产环境加保护习惯：drop 前 `describe` 确认名字没写错。

## 5. 分区操作

分区（Partition）是集合内部的物理分组，两类用途：**性能**（查询限定分区避免全量扫描）与**隔离**（按业务维度分区管理）：

```python
client.create_partition("demo_docs", partition_name="news")
client.insert("demo_docs", data=[...], partition_name="news")   # 写入指定分区
client.search("demo_docs", ..., partition_names=["news"])       # 只在分区内搜
client.list_partitions("demo_docs")
client.drop_partition("demo_docs", partition_name="news")
```

**分区与分区键的关系**：分区键（03 篇 `is_partition_key`）是"自动分区"——插入时按字段值自动落到对应分区，查询时按分区键过滤自动只扫相关分区；手动分区是自己指定 partition_name。**用法建议**：多租户隔离用分区键（省心 + 查询自动收敛），业务性分批管理（按天/按来源归档）用手动分区。3.0 里分区能力保留，快照与外部集合是新的扩展（第 6 节）。

## 6. 3.0 新能力：外部集合与快照

**外部集合（External Collection）**——3.0 数据面与对象存储解耦的产物：集合的 schema/元数据在 Milvus，**数据实体留在对象存储（S3/MinIO）**，Milvus 按需读取——适合"数据在数据湖、想直接向量化检索"的场景，插入走外部写入通道。**集合快照（Snapshot，MVCC）**——给集合打快照后可以查询任意时间点的数据视图，**时间旅行查询**能力（审计、历史回溯场景），快照管理接口 `create_snapshot`/`list_snapshots` 等。

这两项是 3.0 专属（2.6 服务器不支持，报 unknown-field），**生产 RAG 一般用不上，知道存在即可**——面试提"Milvus 3.0 的新方向是湖仓一体化与快照"是加分认知（01 篇 3.0 线）。

## 7. 常见坑

**坑一：创建后没加载就 search**——报 `collection not loaded` 或检索失败；**流程铁律：创建/插入后 → load_collection → 确认 Loaded → search**。

**坑二：重复 create 同名集合**——`CollectionAlreadyExists` 报错；脚本里先 `has_collection` 再决定创建/复用。

**坑三：drop 前不看名字**——`drop_collection("demo_doc")`（少个 s）会静默删掉别的集合……不会，名字不匹配就不存在，**但拼错名 drop 掉同名旧集合是真实事故**——生产 drop 前 describe 确认。

**坑四：插入后立即检索结果不全**——索引异步构建 + 数据可见性延迟；批量导入后 `get_collection_stats` 等行数达标、`get_load_state` 等 Loaded 再对外服务。
