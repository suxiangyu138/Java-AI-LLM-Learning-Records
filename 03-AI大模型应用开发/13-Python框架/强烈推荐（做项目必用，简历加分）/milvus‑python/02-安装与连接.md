## 1. 安装与版本锁定

```bash
pip install "pymilvus==2.6.17"    # 2.6 维护线（配 Milvus 2.6.x）
pip install "pymilvus>=3.0.1,<3.1"  # 3.0 主线（配 Milvus 3.0.x）
```

**版本锁定的两个理由**：其一，**客户端与服务器必须配对**——3.0 协议只有 3.0 SDK 能讲，2.6 服务器遇 3.0 SDK 会报 unknown-field 或不兼容错误；其二，**3.0 有破坏性变更**——真实项目已经发生过"锁文件从 2.6.12 静默升到 3.0.0，CI 直接打爆"的案例（01 篇）——**requirements 里写死版本号是 pymilvus 的第一工程纪律**。Python 版本要求与安装方式：普通 `pip install` 即可（wheel 包含 gRPC/ORM 依赖），`uv`、conda 同价；验证安装：`python -c "import pymilvus; print(pymilvus.__version__)"`。

## 2. 连接三形态

pymilvus 用同一个 `MilvusClient` 覆盖三种运行形态，**只差 uri/token 的传法**：

**形态一：Milvus Lite（本地文件库）**——不装服务器，一个本地文件就是库：

```python
from pymilvus import MilvusClient

client = MilvusClient("milvus_demo.db")   # 本地文件，第一次创建
```

**形态二：自部署 Milvus 服务器**——Docker 起服务后连 URI：

```python
client = MilvusClient(uri="http://localhost:19530")
```

**形态三：Zilliz Cloud（云托管）**——云端地址 + API key/token：

```python
client = MilvusClient(
    uri="https://in03-xxxx.region.zillizcloud.com:19530",
    token="<api_key>",
)
```

**心智模型**：**"uri 决定连谁，token 决定身份，其余代码完全一致"**——三种形态下建集合、插入、检索的代码一模一样，切换部署形态零改动。这就是 SDK v2 统一连接模型的价值：**原型用 Lite 写代码，上线改一行 uri 连生产**。

## 3. MilvusClient：统一连接入口

`MilvusClient` 同时是"连接对象"和"全部操作的入口"——实例化即连接（默认自动建立 gRPC 通道），后续所有方法都在它身上：

```python
client.create_collection(...)   # 建集合
client.insert(...)              # 写入
client.search(...)              # 检索
client.query(...)               # 查询
client.list_collections()       # 列集合
```

**与旧 ORM 的连接对比**：v1 是 `connections.connect("default", ...)` 注册全局连接 + `Collection("name")` 隐式使用；v2 是**连接即对象、对象即一切**——没有全局状态，一个进程可同时持有多个 MilvusClient（连不同环境），互不干扰。**关闭连接**：`client.close()`（进程退出前调用，释放 gRPC 通道与资源；长驻服务里一般不主动关）。`client.get_server_version()` 可确认连到的服务器版本——**排查"为什么 3.0 新特性报错"的第一动作就是看服务器版本**。

**连接自检的标准三段**（新环境部署后必跑）：

```python
client = MilvusClient(uri=os.getenv("MILVUS_URI"), token=os.getenv("MILVUS_TOKEN"))
assert client.get_server_version(), "连接失败"
assert "default" in client.list_databases(), "默认库不可访问"
print("Milvus 连接正常，服务器版本：", client.get_server_version())
```

**"连上了"≠"能用"**——服务器版本对、默认库可访问，才证明权限与协议都正常（10 篇报错速查第一层）。

## 4. 连接参数详解

| 参数 | 作用 | 示例 |
|------|------|------|
| `uri` | 连接地址（文件路径 / http(s):// 地址） | `"http://localhost:19530"` |
| `token` | 认证凭证（云 API key / user:password） | `"db_admin:pass"` 或 API key |
| `db_name` | 默认数据库名（多租户库） | `"default"` |
| `user`/`password` | 传统账号密码认证 | 自部署开启认证时用 |
| `timeout` | 操作超时（秒），默认无/继承 | `timeout=30` |
| `secure` | TLS 加密（云必开） | `secure=True`（云默认） |

**认证两种方式**：云托管用 `token`（API key）；自部署开启用户认证后用 `user` + `password` 或 `token="user:password"` 二选一。**连接池与超时**：SDK 内部维护 gRPC 连接池，一般无需手动管理；生产经验——**所有操作显式传 `timeout`**，否则网络抖动时请求可能挂住（09 篇重试策略）。

**连接对象生命周期与多环境**：MilvusClient 是**重量级对象**（内部建 gRPC 通道与连接池）——**长驻服务只创建一次，全进程复用**（每次请求 new 一个客户端是连接成本爆炸的典型事故，09 篇坑二）。一个进程可同时持有多个客户端：开发连 Lite、测试连测试库、生产连生产库——**互不干扰、按环境切换**；多租户场景还可通过 `db_name` 区分逻辑库。**安全红线**：token/密码走环境变量（`os.getenv`），**绝不写进代码仓库**——`MilvusClient(uri=..., token=os.getenv("MILVUS_TOKEN"))` 是生产标配写法（与 02-后端 配置安全同纪律）。

## 5. Milvus Lite 的边界

Milvus Lite（本地嵌入式版）让"零安装体验 Milvus"成为可能，是**原型开发的黄金工具**（学习本体系的推荐起点）：数据落在一个 `.db` 文件里，API 与服务器版完全一致。但**四个边界必须清楚**：

其一，**它是单机嵌入式**，无集群、无分布式能力——生产高可用场景不可用；其二，**索引与查询能力是子集**——GPU 索引、部分 3.0 新特性（外部集合等）不支持；其三，**数据量上限**——适合百万级以下数据（服务器版处理十亿级），本质是"本地模拟器"；其四，**它代替不了服务器版的性能语义**——本地秒回不代表生产同样快，**Lite 只验"代码正确性"，不验"生产性能"**。定位总结：**学习、原型、单机 Demo 用 Lite；任何要上线的东西直接上服务器版**（Docker 起一个 2.6/3.0 即可，一行命令）。

**Lite 的快速体验闭环**：装好 pymilvus 即自带 Lite（随包自动安装，无需额外步骤），`MilvusClient("demo.db")` 建库 → 插入 → 检索三步跑通，全程无服务器进程——本体系全部动手练习都可在 Lite 上完成；练习代码上线时把 uri 从 `"demo.db"` 换成 `"http://prod:19530"` 即为生产连接——**"零成本起步、零差异迁移"是 Lite 的最大价值**。

## 6. 连接排查

**排查方法论**（按顺序）：**一，先验服务器**——`docker ps` 看容器活着、`curl http://localhost:19530/healthz` 看健康（服务器版自带健康端点）；**二，再验客户端版本**——`pymilvus.__version__` 与服务器版本配对（01 篇表格）；**三，看错误类型**——`ConnectionConfigException`（连不上：uri 错/端口错/防火墙）、`AuthenticationException`（token/账号错）、`ProtocolException`（版本不配）、`ServerNotAvailableException`（服务器没起来或过载）。常见三连：**连不上查 uri 与健康端点；认证失败查 token 与用户；版本错配查配对表**——十分钟内定位 90% 连接问题（10 篇有完整报错速查）。

**Docker 起服务器的标准姿势**（本地开发/自测）：

```bash
docker run -d --name milvus -p 19530:19530 -p 9091:9091 \
  milvusdb/milvus:v2.6.18          # 或 v3.0.0（与 SDK 配对）
curl http://localhost:19530/healthz     # 期望 {"status":"OK"}
python -c "from pymilvus import MilvusClient; \
  c = MilvusClient('http://localhost:19530'); print(c.get_server_version())"
```

**三个端口的默认分工**：19530 是 gRPC（SDK 走这个）、9091 是 metrics（Prometheus 监控，主体系讲）、健康检查走 HTTP——**排查时"SDK 通了但监控没数据"这类问题先想端口**，三件事分开验证。
