## 1. insert：基本写入

插入数据是"行列表"结构——每个字段一个值列表（列式组织）：

```python
client.insert(
    collection_name="demo_docs",
    data=[
        {"id": 1, "title": "Milvus 入门", "embedding": [0.1, 0.2, ...]},
        {"id": 2, "title": "RAG 实战",   "embedding": [0.3, 0.4, ...]},
    ],
)
```

data 参数接受**字典列表**（推荐，字段名直观）或**按字段名的列式字典**（`{"id": [1,2], "title": [...], "embedding": [...]}`——大批次时列式更高效）。插入返回结果含插入数量与主键列表；失败时返回错误码与失败行——**批量插入必须检查返回值**，`insert_count == 0` 说明数据全被拒（schema 校验失败），只检查"没抛异常"会漏掉静默失败。

**插入校验**：字段必须匹配 schema（或动态字段已开）、主键不能重复（重复主键的 insert 行为是报错——重复插入用 upsert）、向量维度必须匹配——**维度不匹配是插入失败第一高频原因**（embedding 模型输出与 schema 的 dim 不一致）。

## 2. upsert：按主键覆盖

**upsert = 主键存在则更新，不存在则插入**——RAG 增量更新的主力：

```python
client.upsert(
    collection_name="demo_docs",
    data=[{"id": 1, "title": "Milvus 入门（修订版）", "embedding": [0.15, 0.25, ...]}],
)
```

**与 insert 的本质差异**：insert 遇重复主键报错；upsert 直接覆盖旧记录（旧向量与新向量同时被替换）。**使用纪律**：upsert 比 insert 重（内部是先删后插的语义），**纯新增场景用 insert，混合新增/更新场景统一用 upsert**（不用"先查再决定 insert 还是 update"——**Milvus 没有独立 update 方法，更新 = upsert**）。upsert 要求集合已加载；upsert 与 delete 一样按主键定位——**主键不稳定（业务 ID 会变）的项目要规划主键迁移策略**（03 篇四问）。

## 3. delete：按主键与表达式

```python
client.delete(collection_name="demo_docs", ids=[3, 4])           # 按主键删
client.delete(collection_name="demo_docs",
              filter="category == 'draft' and created_at < 2025")  # 按表达式删
```

**两种删除姿势**：`ids`（精确主键，快）与 `filter`（表达式，灵活——批量清数据用表达式最省事）。删除是**异步生效**的（删除标记先写入，数据物理清理在后），**删除后立即查询可能仍可见**——一致性模型决定（第 6 节）。**生产建议**：按 filter 删除前先 query 验证"要删的是什么"（同 drop 前 describe 的习惯），误删在向量库里同样不可逆。

## 4. 批量写入与性能姿势

写入性能是 RAG 入库阶段的最大瓶颈，四个关键数字与姿势：

**批次大小**——单次 insert 的数据量推荐 **几千到几万条**（几百条太小浪费往返，几十万条太大单请求超时）；用 `timeout` 参数保护大批次。

**并发姿势**——同步客户端用 `ThreadPoolExecutor` 并行 insert，异步客户端用 `asyncio.gather`（09 篇）——**多路并发比单路大批次吞吐高得多**。

**列式组织**——大批次用列式字典组织数据（字段为键）比逐行字典省内存和序列化时间。

**分批 + 断点**——超大库（百万级）按"分批插入 + 记录已插入主键范围"做断点续灌——**一次任务挂掉不用从头再来**（爬虫/文档入库流水线的标准做法，与爬虫体系的断点续爬同思想）。

写入一致性（`consistency_level`）：默认 **Bounded**（读到的数据最多延迟秒级），强一致用 **Strong**（写完立即可读，性能更慢）——**RAG 场景 Bounded 够用**，强一致留给金融级场景。

## 5. auto_id 与自定义主键

03 篇讲过主键设计的取舍，写入侧的配合姿势：

```python
schema = MilvusClient.create_schema(auto_id=True)   # 服务器生成主键
client.insert("demo_docs", data=[{"title": "...", "embedding": [...]}])  # 不用传 id
```

`auto_id=True` 时插入数据**不带主键字段**，返回结果里的主键列表就是生成的 id（写回自己的业务表做关联——**"Milvus 生成 id 要回存，否则删/更找不到"**是 auto_id 场景第一坑）。**2.6.3 起 auto_id 可配自定义主键值**：`auto_id=True` 时仍传自己的 id——适合"业务 ID 由自己生成但希望服务器兜底"的过渡场景。**推荐**：业务有稳定唯一 ID（文档 ID、订单号）就自定义主键（可控、可关联）；纯向量无业务 ID 用 auto_id。

## 6. 动态字段与一致性

**动态字段（dynamic field）**：schema 开了 `enable_dynamic_field` 后，插入数据里未声明的字段自动进 `$meta`（JSON 结构），查询时可用 `$meta` 过滤：

```python
client.insert("demo_docs", data=[
    {"id": 5, "title": "新文档", "embedding": [...],
     "source": "pdf", "chunk_no": 12},      # source/chunk_no 不在 schema 里
])
client.search("demo_docs", ..., filter='$meta["source"] == "pdf"')
```

**动态字段 = 免预声明的灵活性**，代价是查询走 JSON 解析（比结构化列慢）——**高频过滤字段列化，低频附加信息走动态字段**（03 篇黄金法则的落地）。

**一致性级别**（`consistency_level` 参数）：`Strong`（写完即可读，最慢）、`Bounded`（默认，秒级延迟）、`Eventually`（最终一致，最快）、`Session`（会话内强一致）。**选型**：搜索场景 Bounded；"写入即验证"的测试场景 Strong；高吞吐导入 Eventually + 定期校验。

## 7. FieldOp 数组部分更新

**FieldOp（2.6.14+）**解决数组字段的"部分更新"——不整体覆盖数组，只操作指定元素：

```python
from pymilvus import FieldOp

client.upsert("demo_docs", data=[
    {"id": 1, "title": "更新标题", "embedding": [...]}   # 常规字段整体覆盖
])
client.update_collection_field(  # 或 upsert 内嵌 FieldOp 操作符
    collection_name="demo_docs", field_name="tags",
    values=[FieldOp.add(["新标签"])],  # 数组追加/删除/按索引改
)
```

FieldOp 支持 `add`、`remove`、`add_all` 等数组操作符——**"标签/评论列表这类数组字段的增量维护"不再需要整行重写**，写放大与数据竞争明显改善。3.0 扩展了 **partial array upsert**（数组级部分更新，同族能力）——**"数组字段当一等公民维护"是 2.6.14→3.0 的持续演进方向**。

## 8. 常见坑

**坑一：insert 不检查返回值**——插入被静默拒绝（维度不匹配/schema 校验失败）还以为成功了；**批量插入必查 `insert_count`**。

**坑二：维度不匹配**——embedding 模型输出维度与 schema 的 dim 不一致，报 `dimension mismatch`；换模型后必须同步检查（03 篇"先定模型再建库"）。

**坑三：auto_id 的 id 不回存**——生成的 id 没写回业务表，后续 delete/update 找不到数据。

**坑四：update 不存在**——**Milvus 没有独立 update 方法**，"更新"就是 upsert；面试/文档里看到"update"要自动翻译成 upsert。

**坑五：删除后立即查询仍可见**——异步生效 + 一致性级别；测试脚本里删除后验证用 Strong 一致性或 sleep 一下。
