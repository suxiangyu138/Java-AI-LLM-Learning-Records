## 1. 生产形态选型

unstructured 的三种部署形态（00 篇误区五的解法）：

| 形态 | 场景 | 优点 | 代价 |
|------|------|------|------|
| 本地库 | 原型/开发/测试 | 零成本、调试方便 | 性能受限、依赖重 |
| Docker | 生产自部署 | 资源隔离、可扩缩、GPU | 运维成本 |
| 托管 API | 生产规模化 | 免运维、GPU 内置、弹性 | 数据出网、按量付费 |

**选型心法**：**"原型用本地库，上线用 Docker，规模化用 API"**——本地库的 hi_res 性能（3-5 页/分 CPU）决定了**生产解析必须是隔离资源**（解析任务不该和 Web 服务抢内存——4-6GB/200 页的账单，00 篇）；**数据合规决定 API 可行性**（企业文档出网要过评估——与 12-Python 爬虫/数据合规同纪律）。

## 2. 大文件与内存治理

**大文件（200 页+ PDF）的四个治理姿势**：

**分页处理**（内存第一防线）：

```python
from unstructured.partition.pdf import partition_pdf
import pypdf

reader = pypdf.PdfReader("huge.pdf")
for start in range(0, len(reader.pages), 50):     # 每 50 页一批
    batch = partition_pdf(filename="huge.pdf",
                          strategy="hi_res",
                          starting_page_number=start + 1,   # 页码偏移
                          ending_page_number=min(start + 50, len(reader.pages)))
    process_and_store(batch)     # 每批处理完即释放
```

**要点**：`starting_page_number`/`ending_page_number` 分段解析（页码正确）+ **批处理完即入库/落盘（内存不累积）**；**文档拆分**——超大门户文档先在文件层拆（按章节 PDF）；**内存监控**——hi_res 200 页 4-6GB（04 篇账单），容器内存限额要按此规划——**"分页 + 批处理 + 限额"是内存治理三件套**。

## 3. GPU 加速

**hi_res 的布局模型与 VLM 策略都支持 GPU**（推理加速数倍——04 篇性能账单）：

```python
# hi_res 模型（detectron2/yolox/chipper）自动利用可用 GPU
elements = partition_pdf(filename="complex.pdf", strategy="hi_res",
                         model_name="chipperv2")

# VLM 策略走托管 API（本地调多模态大模型不现实）
# from unstructured.partition.api import partition_via_api  # 托管姿势
```

**GPU 部署要点**：**本地库 + GPU** 需要 CUDA 环境（模型推理框架的驱动）；**Docker 里 GPU 用 `--gpus all`**（第 4 节）；**吞吐对比**：hi_res CPU 3-5 页/分 → GPU 数倍提升（20+ 页/分）——**"批量解析的吞吐瓶颈在 GPU 是否可用"**；**VLM 策略（GPT-4o 等）本质是调外部模型——生产走托管 API/自带密钥**（04 篇模型家族）。

## 4. Docker 部署

```bash
# 官方镜像（含常用解析依赖）
docker pull downloads.unstructured.io/unstructured-io/unstructured:latest
docker run -d --name unstructured -p 8000:8000 \
  --gpus all \                                    # GPU 加速（可选）
  -v /data/documents:/data/documents \            # 文档挂载
  downloads.unstructured.io/unstructured-io/unstructured:latest

# 调用（官方 API 端点）
curl -X POST http://localhost:8000/general/v0/general \
  -H "accept: application/json" \
  -F "files=@/data/documents/report.pdf" \
  -F "strategy=hi_res"
```

**部署要点**：**官方镜像自带解析依赖**（免去 extras 安装地狱）；**资源限额**（内存按 hi_res 账单设 limit——4-6GB/200 页）；**GPU 参数**（`--gpus all` + 镜像内置 CUDA 支持）；**数据卷分离**（文档与产出分离）；**健康检查与监控**（解析队列长度/内存水位——loguru 留痕 + Prometheus 指标，00 篇分工）。**"Docker 是生产解析的标准运行单元"**——资源隔离解决"解析吃内存拖垮 Web 服务"。

**镜像与版本管理**（生产的隐性细节）：**镜像 tag 与库版本对应**（镜像内置的 unstructured 版本要锁定记录——升级镜像 = 升级解析行为）；**依赖膨胀治理**——官方镜像包含全部 extras（方便），自建镜像按需裁剪（`pip install "unstructured[pdf]"` 精简版，体积小部署快）——**"镜像要么跟官方 tag 锁版本，要么自建裁剪"二选一，别用 latest 裸跑**（与 Docker 体系 02 篇镜像版本管理同纪律）。

## 5. 并发与批处理

**批量解析的并发姿势**（解析是 CPU/GPU 密集 + IO 密集混合）：

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def parse_one(path: str):
    elements = partition_pdf(filename=path, strategy="fast")   # 按文档选策略
    return clean_and_store(path, elements)                     # 清洗 + 入库

with ThreadPoolExecutor(max_workers=8) as pool:    # 并发度按 CPU/内存预算定
    futures = {pool.submit(parse_one, p): p for p in pdf_paths}
    for fut in as_completed(futures):
        fut.result()     # 失败要记录（断点续跑）
```

**并发三纪律**：**并发度 = f(内存预算)**（hi_res 4-6GB/任务——8 并发 = 32-48GB，先算账）；**失败留痕 + 断点续跑**（记录已成功清单，重跑只跑失败的——与爬虫断点续爬同思想）；**fast/hi_res 混跑**（简单文档 fast 并行、复杂文档 hi_res 单独队列——**"按文档复杂度分队列"是批量管道的标准设计**）。

## 6. 托管 API 与生产链路

**托管 API（unstructured.io）的 2026 形态**（00 篇）：**统一 push 式接口**——一次调用完成"分区 → 富化 → 分块 → 向量化"全流程（on-demand jobs）：

```python
# 托管 API 姿势（unstructured-client SDK）
from unstructured_client import UnstructuredClient

client = UnstructuredClient(api_key=os.getenv("UNSTRUCTURED_API_KEY"))
# 分区 + 分块 + 向量化一次完成（预置工作流模板）
result = client.general.partition(
    request={"files": {...}, "strategy": "hi_res",
             "chunking_strategy": "by_title", ...})
```

**生产链路取舍**：**本地管道**（数据不出网、全控制——合规优先）；**托管 API**（免 GPU 运维、VLM 策略可用——速度优先）；**混合**（敏感文档本地、公开文档 API）。**"本地库负责深度定制，API 负责规模化"是 2026 年的官方推荐分工**（01 篇）。**成本**：API 按解析量计费——**"先本地验证质量，再 API 规模化"避免白花钱**。

**生产监控与告警**（管道是可观测的，09 篇收尾）：**指标三件套**——解析队列长度（积压 = 瓶颈信号）、内存水位（hi_res 账单对照）、失败率（解析失败/清洗异常）；**日志留痕**——每文档解析结果打 loguru 日志（成功/失败/元素数——02 篇质量报告进日志）；**告警规则**——失败率超阈值、队列积压超时——**"解析管道是可观测的工程，不是跑完就忘的脚本"**（与日志监控指标体系同思想，00 篇分工）。

## 8. 常见坑

**坑一：生产裸跑本地库 hi_res**——与 Web 服务抢内存崩机；**Docker 隔离 + 限额**（第 1/4 节）。

**坑二：200 页 PDF 一把梭**——内存爆掉；**分页 + 批处理**（第 2 节）。

**坑三：并发拉满**——hi_res 的 4-6GB/任务 × 16 并发 = 内存灾难；**并发度先算账**（第 5 节）。

**坑四：失败不记录**——批量解析中断无从续跑；**失败清单 + 断点**（第 5 节）。

**坑五：托管 API 凭证进代码**——泄露即烧钱；**环境变量 + 密钥管理**（第 6 节）。
