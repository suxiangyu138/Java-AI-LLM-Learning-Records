## 1. 为什么框架都封装它

LangChain 与 LlamaIndex 都把 unstructured 做成**官方集成件**（Loader/Reader）——原因正是 01 篇的定位：**"加载与解析"是 RAG 链路的第一环，而 unstructured 是这一环的事实标准**——框架的哲学是"数据源接入用官方封装"，于是：

- **LangChain**：`UnstructuredLoader`（`langchain-community`）——文档加载器家族的一员；
- **LlamaIndex**：`UnstructuredReader`（`llama_index.readers.file`）——文件读取器家族的一员。

**"框架封装 = 把 partition 调用 + Elements 转换包成框架的数据结构"**——底层还是 unstructured 的 partition 家族——**"看懂裸库（本体系 02-07 篇），框架封装就是一层窗户纸"**（00 篇分工）。

## 2. LangChain 集成：UnstructuredLoader

```python
from langchain_community.document_loaders import UnstructuredLoader

loader = UnstructuredLoader(
    "docs/report.pdf",
    strategy="hi_res",            # 直接透传 unstructured 参数
    infer_table_structure=True,
)
docs = loader.load()              # List[Document]——LangChain 标准结构

# 目录加载（批量）
loader = UnstructuredLoader("docs/")   # 目录下全部文档
```

**封装做了什么**：内部调 `partition_pdf/partition_docx/...`（按文件类型自动选分区器），**Elements 转成 LangChain 的 Document**——**text → `page_content`、metadata → `metadata`**（页码/来源保留）。**能透传什么**：`strategy`/`model_name`/`languages` 等 partition 参数直接透传（**"框架封装不牺牲底层控制力"**——04/05 篇的参数在框架里照样能用）。**注意**：`langchain_community` 里的 loader 依赖 `unstructured` 包——**版本匹配**（LangChain 封装的 unstructured 版本与你的锁版本可能不同，08 篇避坑）。

## 3. LlamaIndex 集成：UnstructuredReader

```python
from llama_index.readers.file import UnstructuredReader

reader = UnstructuredReader()
documents = reader.load_data(file="./docs/report.pdf")
# → List[Document]（LlamaIndex 结构：text + metadata）

# 可选：直接指定分区器与参数
reader = UnstructuredReader(
    partitioner="unstructured.partition.pdf.partition_pdf",
    strategy="hi_res",
)
```

**封装做了什么**：同样底层调 partition 家族，Elements → LlamaIndex Document；**LlamaIndex 版的差异**：`load_data` 返回结构（含 `doc_id`）、支持 `split_documents` 等 LlamaIndex 生态衔接（与 Index 构建流程配合）。**生态对照**：LlamaIndex 自己的 `LlamaParse` 是"云托管解析"选项（01 篇替代品表）——**"本地解析用 UnstructuredReader，云解析用 LlamaParse"是 LlamaIndex 生态内的分工**。

## 4. Connectors：40+ 数据源连接器

**Connectors 是 unstructured 的企业数据源接入层**——不只在框架里，库自身也带：

| 类别 | 连接器示例 |
|------|-----------|
| 云存储 | S3、Azure Blob、GCS、Dropbox |
| 文档协作 | Google Drive、SharePoint、Confluence |
| 通讯 | Outlook、Gmail、Slack |
| 项目/工单 | Jira、Notion、Reddit |
| 数据库 | Postgres、MongoDB（数据管道） |

**Connectors 的价值**：**"企业知识库 = 散落在 20 个系统的文档"**——RAG 落地第一步是"把数据聚齐"，Connectors 提供**源系统 → 解析 → Elements**的一体化接入（`unstructured.connectors` 模块）。**2026 演进**：托管 API 的 connectors 保持向后兼容（00 篇），本地库的 connectors 同样可用——**"数据源接入用 Connector，格式解析用 partition，两件事分清楚"**。

**Connector 的接入姿势与权限治理**：

```python
from unstructured.connectors.s3 import S3Connector   # 以 S3 为例

connector = S3Connector(
    aws_access_key_id=os.getenv("AWS_ACCESS_KEY_ID"),    # 凭证走环境变量
    aws_secret_access_key=os.getenv("AWS_SECRET_ACCESS_KEY"),
    url="s3://my-bucket/docs/",
)
elements = connector.get_elements()      # 拉取并解析成 Elements
```

**三个要点**：**凭证纪律**——Connector 的凭证（云 key/账号密码）一律环境变量（与 pyyaml 07 篇、09 篇坑五同纪律——**"Connector 是凭证最集中的地方，也是最容易泄露的地方"**）；**权限最小化**——只给 Connector 对应桶/邮箱的只读权限（IAM 最小权限，与 02-后端安全体系同思想）；**批量与增量**——Connector 的元数据（时间戳）支撑"只拉新增"的增量管道（06 篇 element_hash 的源端配套）。

## 5. 框架集成 vs 裸库

| 维度 | 框架集成（Loader/Reader） | 裸库（partition 家族） |
|------|--------------------------|------------------------|
| 上手 | 一行加载 | 手动调 partition + 转换 |
| 控制力 | 参数透传但结构框架化 | 全量控制（清洗/过滤/排序） |
| 生态 | 直接接框架的链/索引/检索 | 自己拼装 |
| 学习价值 | 依赖懂裸库原理 | 理解一切集成层 |
| 场景 | 快速搭建/框架为主的项目 | 深度控制/管道定制 |

**选型判断**：**"项目以框架为主 → 集成件起步；要深度控制解析细节（清洗管线/定制分区）→ 裸库"**；**两者不互斥**——管道里可以"裸库解析 + 清洗 → 转成框架 Document 进索引"（10 篇实战的混合姿势）。**"学习期先裸库（本体系 02-07 篇），项目期按需求选"**是 00 篇路线的延续。

**混合姿势的完整代码**（裸库深度控制 + 框架生态，两全其美）：

```python
# 裸库解析 + 清洗（深度控制）
from unstructured.partition.pdf import partition_pdf
from unstructured.cleaners.core import clean_extra_whitespace

elements = partition_pdf(filename="report.pdf", strategy="hi_res")
keep = [el for el in elements if el.category not in ("Header", "Footer")]
for el in keep:
    el.text = clean_extra_whitespace(el.text)

# 转成 LangChain Document 进框架生态
from langchain_core.documents import Document
docs = [Document(page_content=el.text,
                 metadata={"source": "report.pdf",
                           "page": el.metadata.get("page_number"),
                           "category": el.category})
        for el in keep]
# docs 直接进 LangChain 的向量存储/索引流程（milvus 封装类）
```

**"裸库管解析质量，框架管生态衔接"**——**混合姿势是生产管道的最优解**：清洗质检在裸库层做全，交接点在 Document 结构（metadata 完整带过）——**"掌握两边的交接点（Elements ↔ Document）就是架构师的视野"**（与 milvus‑python 08 篇的裸 SDK 哲学同构）。

**三种姿势的最终选型表**（面试/项目决策一张图）：

| 姿势 | 解析控制 | 生态衔接 | 适用 |
|------|---------|---------|------|
| 纯框架集成 | 参数透传 | 最好（原生） | 快速原型/框架为主 |
| 纯裸库 | 全量控制 | 自己拼装 | 深度定制管道 |
| **混合**（推荐） | 全量控制 | 好（Document 交接） | **生产管道标准答案** |

**"混合是生产标准答案，集成是快速起点，裸库是学习地基"**——三种姿势对应三条路线（00 篇路线一/二/三）。

## 6. 集成避坑

**坑一：版本漂移**——框架封装的 unstructured 版本与项目锁版本不一致，行为差异；**锁版本对齐 + 读框架 changelog**（第 2 节注意）。

**坑二：参数透传无效**——框架 loader 的 kwargs 没透传到 partition（老版本限制）；**验证：看 Document metadata 里有没有预期字段**（第 2 节）。

**坑三：Elements 的清洗被跳过**——框架封装直接转 Document，**清洗管线（06 篇）要自己补**（框架不替你做质检）；**"框架负责接，清洗负责你"**。

**坑四：目录加载递归行为**——UnstructuredLoader("docs/") 的递归深度/支持格式有默认值；**显式指定或自己 glob 文件列表**。

**坑五：Connector 凭证硬编码**——S3/Gmail 的凭证写进代码；**凭证走环境变量/密钥管理**（与 pyyaml 07 篇同纪律）。

**LangChain loader 家族里 unstructured 的位置**（面试常问"loader 怎么选"）：

| Loader | 能力 | 场景 |
|--------|------|------|
| TextLoader | 纯文本读取 | TXT/Markdown 简单文件 |
| PyPDFLoader | PDF 基础文本 | 干净数字 PDF（无结构需求） |
| UnstructuredLoader | **全格式 + 结构解析** | **RAG 数据管道（推荐）** |
| DirectoryLoader | 目录批量（可配 loader） | 批量文档 |

**选型判断**：**"Loader 选型的本质是'要不要结构化解析'"**——只需要文本流（简单文档/原型）用 PyPDFLoader 类轻量件；**要 Element 级结构（标题/表格/OCR）用 UnstructuredLoader**——**"RAG 想做好，loader 选 unstructured"**是 LangChain 生态内的共识（01 篇"为什么框架都封装它"的延续）。
