## 1. 文档解析 ETL：RAG 的第一公里

unstructured 的定位一句话：**"ETL 库——把任意格式的文档变成 LLM 可消费的结构化数据"**。RAG 链路的第一公里是"加载与解析"：企业知识库里躺着 PDF、Word、PPT、扫描件、邮件——**LLM 不能直接吃这些格式，向量库也不能**。unstructured 做的正是这一跳：

**输入**：25+ 格式（PDF/DOCX/PPTX/XLSX/HTML/Markdown/EPUB/图片/邮件/RTF/TXT/XML……）；**输出**：**带类型与元数据的 Elements 列表**——`Title`、`NarrativeText`（正文）、`Table`、`ListItem`、`Header`、`Footer`、`Image`、`Formula` 等 20+ 类型，每个元素携带 `metadata`（页码、坐标、语言、哈希、来源）。

**为什么它比"PDF 转文本"高一维**：转换只给文本流，**分区（partition）给"结构化文档"**——RAG 需要知道"这段是标题还是正文、这张表有几行几列、这个元素在第几页"——**类型与元数据就是 RAG 切分与检索质量的底层依据**（03 篇详讲 Element 模型）。

## 2. 解决什么问题

**问题一：PDF 是 RAG 最大的坑**——PDF 没有统一的"内容流"概念：多列排版、表格、图片、扫描件、嵌入字体——**pdfminer 之类工具裸解析的结果经常是"列混排、表格碎裂、扫描件全空"**。unstructured 的分区策略体系（fast 启发式 / hi_res 布局模型 / OCR）分层解决：**"普通 PDF 快速解析，复杂版面上模型，扫描件上 OCR"**（04 篇策略选型）。

**问题二：表格结构化**——表格是 RAG 召回率的重灾区：表格转纯文本后语义全丢。unstructured 用 Table Transformer 等模型提取表格结构，**输出 HTML 表格表示（行/列结构保留）**——"表格进 RAG 的正确姿势是结构化表示而不是文本流"（05 篇）。

**问题三：多格式统一**——Word/PPT/Excel/邮件/网页各有各的解析器，**团队不想为每种格式维护一套代码**。unstructured 的 partition 家族（partition_pdf/partition_docx/partition_pptx/…）**一个 API 风格覆盖全部格式**——"换格式只换函数名，输出结构一致"（05 篇）。

**问题四：数据管道最后一公里**——解析出来的 Elements 还要清洗、分块、入库——unstructured 自带 **clean 清洗家族 + 4 种分块策略 + JSON/CSV/DataFrame/Markdown 转换**，**"解析 → 清洗 → 分块"一站式**（06/07 篇）。

## 3. 2026 现状与版本基线

**2026-08 基线：0.24.1（2026-07-11 发布）**，发布节奏非常活跃：0.24.0（2026-07-06）、0.23.x（2026-06）、0.22.x 维护线持续到 2026-05——**"周更级迭代，锁版本是必须"**（0.22 到 0.24 三个月跨三个大版本）。

项目基本面：**Apache-2.0、15K stars、PyPI 累计 93M+ 下载**（RAG 时代的现象级数据预处理库）、25+ 格式、20+ 元素类型、40+ 连接器。**2026-01 托管 API 大升级**：从分段端点演进为**统一 push 式接口**——一次调用完成"分区 → 富化 → 分块 → 向量化"（on-demand jobs），支持预置工作流模板、UI 与 API 对等（可视化工作流直接导出为 API）——**"本地库管原型，托管 API 管生产全流程"是 2026 年的官方推荐分工**。**MCP 服务器集成开发中**——AI Agent 通过 MCP 协议操作解析管道（与 06-MCP 协议体系呼应）。

**对学习者的含义**：库本身 API 稳定（partition 家族 + Element 模型多年不变），**迭代集中在性能、新格式与新策略**——"**核心 API 学一遍用几年，版本跟着锁**"。

## 4. 与替代品对比

| 工具 | 定位 | 强项 | 短板 |
|------|------|------|------|
| unstructured | 全格式解析 ETL | 格式全、元素类型、策略体系、分块集成 | 依赖重（all-docs 2GB） |
| PyPDF2/pypdf | PDF 基础操作 | 轻量、页面/文本提取 | 无结构、无表格、无 OCR |
| pdfplumber | PDF 精细提取 | 坐标/表格定位准 | 仅 PDF、无 ML 版面 |
| docling | IBM 文档解析 | 版面分析强 | 生态小、格式少 |
| LlamaParse | 托管解析服务 | 云托管、模型强 | 闭源、依赖 LlamaCloud |

**选型判断**：**PDF 基础读取用 pypdf/pdfplumber，RAG 数据管道用 unstructured**——**"unstructured 是唯一把'解析 + 清洗 + 分块 + 集成'做成一条链的库"**；docling 是学术/版面研究向，LlamaParse 是 LlamaIndex 生态的托管选项（数据要过 LlamaCloud）——**"多数项目默认 unstructured，特殊场景（纯坐标提取/云托管）再换"**。

**为什么排"强烈推荐"**：RAG 是 2026 年 AI 应用的核心形态，而**文档解析是每个 RAG 项目绕不开的第一公里**——不做文档解析的 RAG 只适用于"文本已经规整"的理想世界；企业知识库（PDF/扫描件/表格）的现实让 unstructured 成为**做项目必用**的工具；简历上"RAG 数据管道"项目的含金量，很大程度体现在"**能处理真实世界的复杂文档**"——这正是 unstructured 的能力边界（多列/表格/扫描件/多语言）。**"LangChain 系解决怎么检索，unstructured 系解决喂什么进去"**——它是"强烈推荐"目录里**唯一的数据预处理件**，与其他五套（编排/日志/检索/配置）互补构成 RAG 全链路。

## 5. 生态位置与边界

**生态位置**：unstructured 是 **RAG 数据预处理层的事实标准**——LangChain 的 UnstructuredLoader、LlamaIndex 的 UnstructuredReader 都是它的封装（08 篇），40+ 连接器（S3/Gmail/Jira/SharePoint/Confluence）覆盖企业数据源，**"加载企业数据 → 解析 → 进 RAG"的链路里它是默认选择**。93M+ 下载说明它不只是"一个库"——**是 RAG 时代数据预处理的基础设施**。

**边界要划清楚**：其一，**它提取内容与结构，不做格式转换**（"PDF 转 PDF/Word 转换"不是它的活）；其二，**本地库到 Elements 为止**——向量化/富化是托管 API 的增值服务，本地要自己做 embedding；其三，**解析质量有上限**——复杂版面（手写、极度混乱扫描件）任何工具都有极限，**"hi_res 是当前最优，不是完美"**；其四，**它不解决检索**——Elements 之后要接 milvus 等向量库（00 篇分工）；其五，**解析质量依赖输入质量**——模糊扫描件、被裁剪的页面、加密 PDF 都会显著降低结果——**"垃圾进垃圾出"在文档解析上同样成立**（02 篇三步调试法就是为"质量不可见"设计的检查手段）。
