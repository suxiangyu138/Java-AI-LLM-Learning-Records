## 1. 一句话定位

**记忆让多轮对话/多 Agent 共享上下文，观测让每一步可追踪可排障——"记忆解决'忘了前面说的'，观测解决'不知道哪一步错了'"**：

```text
两个横切能力
├── 记忆：ChatMemoryBuffer（多轮历史）→ 摘要记忆（超长压缩）
└── 观测：OTel 追踪（检索/LLM/工作流全链路）→ 平台（LlamaTrace/Phoenix/Langfuse）
    ——"记忆在前端体验，观测在后端保障——两者都该默认开启"
```

**定位心智**：**"记忆不是'存对话'，是'控制上下文成本'——历史全塞会爆 token，记忆策略 = 保留什么、压缩什么"**——"**观测不是'日志'，是'链路'——一个问题从提问到回答经历了哪些检索/调用/工具，一条 trace 全看清"**。

## 2. 记忆机制

```python
from llama_index.core.memory import ChatMemoryBuffer, ChatSummaryMemoryBuffer

# 默认：环形缓冲区——超 token_limit 丢最早的消息
buffer = ChatMemoryBuffer.from_defaults(token_limit=6000)

# 摘要记忆：超限后把旧消息压缩成摘要（长会话保信息）
summary_memory = ChatSummaryMemoryBuffer.from_defaults(
    llm=Settings.llm, token_limit=6000,
)

# 聊天引擎/AgentWorkflow 共用同一个记忆对象
chat_engine = index.as_chat_engine(chat_mode="condense_plus_context", memory=buffer)
```

**要点**：① `token_limit` 是唯一关键旋钮——"**记住多少 = 预算**"；② 会话隔离：**每个用户/会话一个 memory 实例（别全局共享——串号事故）**；③ 持久化：`memory.get_all()` 序列化入库，重启恢复——**"生产聊天必须落盘（Redis/DB），内存记忆重启即失"**；④ 多 Agent 场景：AgentWorkflow 内部共享一个记忆（08 篇）——**"记忆粒度 = 会话粒度"**。

**记忆与上下文成本**：历史全量塞提示词是 token 大户——**"token_limit 不是随便设的：6000 意味着约 4000 词的上下文，长会话必须靠摘要记忆压缩——'记忆策略 = 质量与成本的折中'（成本账见 Function Calling 体系的上下文管理篇）"**；**角色消息要保结构**——history 里的 system 指令别被当普通消息截掉——"**截断时保留 system + 最近对话，中间用摘要代替**"。

## 3. 向量记忆与集成

**跨会话长期记忆——历史向量化按需召回**：

```python
# 集成 mem0（长期个性化记忆库）
from llama_index.memory.mem0 import Mem0Memory

memory = Mem0Memory.from_client(  # mem0 2.x（2026 集成包基线）
    client=Mem0Memory._create_client(),
    token_limit=6000,
)
```

**心智**：**"短期记忆（对话内）用 ChatMemoryBuffer；长期记忆（跨会话用户画像/偏好）上向量记忆（mem0 等）——'短期管流畅，长期管个性化'"**——"**记忆选型跟场景走：客服要长期记忆（记得上次诉求），文档问答只要短期（每问独立检索）"**；**记忆的评估**——"加记忆后做前后对比（同一问题、有记忆 vs 无记忆），'记住'不是目的、'答得对'才是（06 篇评估纪律）"。

## 4. 可观测性：OTel

**OpenTelemetry 是 LlamaIndex 的观测底座——一条配置全链路追踪**：

```python
from llama_index.core import set_global_handler

# 接入 OTel（一次配置，检索/LLM/工作流全追踪）
set_global_handler("otlp", endpoint="http://localhost:4317")

# 本地开发：控制台看 trace
set_global_handler("simple")
```

**追踪内容**：① 检索：query → 每路 retriever 的 top-k 与分数；② LLM：每次调用的 prompt/响应/token/耗时；③ 工作流：每个 step 的事件进出（08 篇）；④ 工具：Agent 的每次工具调用参数与结果——**"一条 trace = 一次问答的完整切片"**。

## 5. 观测平台

| 平台 | 定位 | 场景 |
|------|------|------|
| LlamaTrace | LlamaIndex 官方（LlamaCloud 集成） | 官方全家桶 |
| Arize Phoenix | 开源本地（免费） | 自建首选 |
| Langfuse | 开源/云（产品成熟） | 生产主流 |

**选型心智**：**"本地开发用 Phoenix（docker 一条命令）；生产正式产品按团队习惯选——'观测平台的收益 = 排障速度'"**——"**面板看三件事：检索质量（召回了什么）、成本（token 消耗）、失败（哪步报错）——'先有基线，再谈优化'"**。

**本地接入 Phoenix 最小步骤**：

```bash
# 1. 起 Phoenix（docker 一条命令）
docker run -p 6006:6006 -p 4317:4317 arizephoenix/phoenix:latest
```

```python
# 2. LlamaIndex 一行接入（OTel 协议直通）
set_global_handler("arize_phoenix", endpoint="http://localhost:6006")
# 3. 面板看：http://localhost:6006 —— 每条问答的检索节点与 LLM 调用
```

**要点**：Phoenix 本地免费 + 数据不出内网——**"国产/合规场景的观测首选（数据不出域）"**；OTel 是行业标准——**"换平台只换 handler 名，业务代码零改动（与 02-后端 的日志监控指标体系同协议）"**。

**追踪粒度控制**：默认追踪可能过细（每次 embedding 调用都记）——**"生产开采样率（OTel sampler）——'追踪有成本（存储/流量），只保 10%-100% 关键流量'"**；敏感内容（用户问题原文）入 trace 要脱敏——**"观测数据的合规与业务数据同等对待"**。

## 6. 评估

**生产质量闭环——检索质量与回答质量分开评**：

```python
from llama_index.core.evaluation import (
    RetrieverEvaluator, BatchEvalRunner, CorrectnessEvaluator,
)

# 检索质量：HitRate / MRR（换检索方案先跑这组数）
retriever_eval = RetrieverEvaluator.from_metric_names(
    ["hit_rate", "mrr"], retriever=retriever)
result = await retriever_eval.aevaluate(query="…", expected_ids=[…])

# 回答质量：正确性/相关性/忠实度（对照参考答案）
runner = BatchEvalRunner(evaluators={"correctness": CorrectnessEvaluator()}, workers=4)
results = await runner.aevaluate_queries(query_engine, queries=[…])
```

**心智**：**"改任何环节（切分/模型/重排）先跑评估对比——HitRate 看召回、Correctness 看回答——'评估是检索调优的尺子（06 篇调优顺序要配尺子）'"**。

## 7. 生产落地清单

**记忆持久化（会话重启不丢）**：

```python
import json

# 存：memory 导出 → Redis/DB（按 session_id 存 key）
data = {"chat_history": [m.dict() for m in memory.get_all()]}
redis.set(f"memory:{session_id}", json.dumps(data, ensure_ascii=False))

# 取：启动会话时恢复
raw = redis.get(f"memory:{session_id}")
if raw:
    memory.set([ChatMessage(**m) for m in json.loads(raw)["chat_history"]])
```

**落地三件事**：① 记忆按 session_id 隔离 + 过期（TTL 7-30 天——防隐私与膨胀）；② 观测面板固定盯三件事——检索质量（召回了什么节点）、token 成本（每问题多少钱）、失败率（哪步报错）；③ 评估数据集要"人工标注金标准"——**"评估质量 = 数据质量——先人工标 50 条问题 + 参考答案，再谈自动化"**。

**评估对比纪律**：任何检索改动（chunk/模型/重排）先跑基线再改——**"同一数据集、同一指标、同一随机种子——数字对比才有意义（06 篇调优配尺子）"**；改完发现 HitRate 持平但回答变好？——**"分别跑两维：检索指标看召回、人工抽查看回答——别混为一谈"**。

**成本治理**：观测里加 `response_cost` 维度（模型输出 token × 单价）——**"检索成本大头在 embedding 与重排调用——'先看成本再看质量，双指标定方案'"**。

## 9. 本节验收

**验收动作**：① 给聊天引擎挂上摘要记忆并验证长会话不爆 token；② set_global_handler 接入 Phoenix 跑 5 个问题看完整 trace；③ 跑一轮 retriever 评估记录 HitRate 基线——**"记忆 + 观测 + 评估 = 生产三角"**。
