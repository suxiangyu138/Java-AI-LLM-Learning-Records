## 1. 显存公式：先算账

推理显存 = **权重 + KV cache + 激活值**，前两项是大头：

**权重 = 参数量 × 每参字节数**。7B 模型：fp32 28GB → bf16 14GB → int8 7GB → 4bit 3.5GB。

**KV cache ≈ 2 × 层数 × 注意力头数 × 头维度 × 序列长度 × 字节数**（每 token 每层存 K、V 两组）。7B 模型（28 层、32 头、128 维、bf16、2048 序列）约 2×28×32×128×2048×2 ≈ 0.9GB，但 128K 长上下文场景暴涨到 56GB+——**长上下文才是显存杀手**，模型尺寸只是入门费。

**经验法则**：单卡能跑的模型 ≈ 显存 ÷ 5（bf16 权重 + 典型序列的 KV 与激活余量）。24GB 卡 → 7B bf16 勉强、7B 4bit 舒服；48GB 卡 → 70B 4bit；8GB 卡 → 3B 4bit。先算账再选模型，避免「下载 70B 才发现要 8 张卡」。

**一个完整算例**（把公式走一遍）：选 Qwen2.5-7B（28 层、32 头、128 头维）跑 bf16、序列 4096。权重 = 7e9 × 2B ≈ 14GB。KV cache = 2 × 28 × 32 × 128 × 4096 × 2 ≈ 1.9GB（单请求；批量 8 请求则 ×8 ≈ 15GB）。激活 ≈ 1-2GB。总计：单请求 ≈ 18GB（24GB 卡勉强），批量 8 ≈ 31GB（超 24GB——要么降批量、要么量化）。**同一个模型，批量与序列长度决定它在哪张卡上能跑**——这就是「先算账」的完整含义：不是查一个「7B 需要多少显存」的答案，而是按自己的序列长度与批量自己算。

## 2. 精度阶梯

| 精度 | 字节/参数 | 7B 权重 | 质量 | 适用 |
|------|----------|--------|------|------|
| fp32 | 4 | 28GB | 100% | 训练/调试，推理不用 |
| bf16/fp16 | 2 | 14GB | ~100% | **默认推荐**，GPU 原生支持 |
| int8 | 1 | 7GB | 轻微损失 | 显存紧时过渡 |
| 4bit | 0.5 | 3.5GB | 损失可控 | **单卡大模型标准** |

bf16 是推理默认档：现代 GPU（Ampere+）原生支持，速度无损质量无损。**fp16 与 bf16 的区别**：fp16 尾数精度高但范围窄（大数值溢出风险），bf16 范围大尾数少——大模型训练与推理官方模型卡多数推荐 bf16，听模型卡的。8GB 以下的卡才考虑 int8/4bit 起步。

## 3. bitsandbytes 量化

bitsandbytes 是运行时量化库：模型加载时把权重压到 8bit/4bit，推理时按需反量化计算。transformers 5.x 中量化是一等公民——`quantization_config` 参数直接传给 from_pretrained：

```python
from transformers import BitsAndBytesConfig

quant_config = BitsAndBytesConfig(
    load_in_4bit=True,                # 4bit 量化（8bit 用 load_in_8bit=True）
    bnb_4bit_compute_dtype=torch.bfloat16,   # 计算精度：反量化后按 bf16 算
    bnb_4bit_quant_type="nf4",        # NF4 数据格式（默认，比 fp4 质量好）
    bnb_4bit_use_double_quant=True,   # 双重量化：再省 0.4 字节/参
)
model = AutoModelForCausalLM.from_pretrained(
    model_id, quantization_config=quant_config, device_map="auto")
```

**4bit NF4 单卡 70B 的甜点组合**就是上面这份配置：70B 权重压到约 40GB（70×0.5+ 双重量化余量），48GB 卡直接跑。三条要点：**计算精度用 bf16 而不是 fp16**（NF4 反量化后计算，bf16 范围稳）；**量化必须配合 `device_map="auto"`**（量化与分发由 accelerate 协同完成，手动 .to() 会破坏量化状态）；**首次加载需联网装 bitsandbytes**（`pip install bitsandbytes`，与 CUDA 版本匹配）。

## 4. 预量化格式 GPTQ/AWQ

bitsandbytes 是**运行时量化**（加载时才压），GPTQ/AWQ 是**权重预量化**（社区离线压好，仓库直接提供量化版权重，如 `TheBloke/Qwen-...-GPTQ` 风格仓库，2026 年主流模型官方直接出量化版）。

```python
# GPTQ 仓库加载（仓库内已有量化权重与量化配置）
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-7B-Instruct-GPTQ-Int4", device_map="auto")
```

两者对比：bitsandbytes 灵活（任何模型即时量化）但加载慢、反量化开销大；GPTQ/AWQ 质量略好、加载快（权重已是量化态）但依赖社区预量化版本。**生产服务化首选预量化版本**（09 篇 serve 支持 `--quantization bnb-4bit` 也可选），实验随意。GPTQ 加载需要 `auto-gptq`/`optimum` 库——报 `GPTQConfig` 缺失时先补依赖。

## 5. 量化与 device_map 组合

量化解决「权重占显存」，device_map 解决「放不下时的分层」。两者组合的顺序感：**先量化到 4bit（把权重压缩到极限）→ 再 device_map=auto（剩余的放不下才 offload CPU）**。别反着来——先 offload 后量化，模型既慢又没省到位。

显存预算不足时的完整优先级：4bit 量化（-87% 权重显存）→ 降低序列长度（KV cache 线性缩）→ `max_memory` 手动限定（让部分层去 CPU）→ 换小模型。前两步是甜的（无损或微损），第三步开始变慢，换模型是最后手段。**低显存卡（8GB）跑 7B 4bit**：权重 3.5GB + KV/激活，勉强可行但序列要短；这类场景实测以 3B 模型 4bit 体验最佳。

## 6. 量化决策

**什么时候必须量化**：显存不够、要部署到小卡/低成本卡、多模型共存单卡。**什么时候不量化**：显存充足且追求极致质量（量化有可测的质量损失，长文本与推理密集型任务放大损失）；小模型（<1B）量化收益小损失相对大。**质量损失量化衡量**：同 prompt 对比量化前后输出的困惑度/任务分数，而不是「看起来差不多」——评测驱动的量化决策是工程做法。4bit 对 7B+ 模型的损失通常可控（任务分数掉 1-3%），70B 4bit 常优于 7B fp16——**模型越大，量化越划算**，这是「单卡跑大模型」策略的理论依据。

**量化与低显存之外的显存治理**：量化不是唯一手段，按「先免费后付费」排序还有四招——**降批量**（KV cache 按并发线性缩，最直接）；**降序列长度**（截断到实际需要，128K 预算 vs 8K 实际是 16 倍 KV 差异）；**梯度不涉及推理但激活要管**（长输入单次前向的激活峰值，`chunked_prefill`/分块处理）；**显存碎片治理**（`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 缓解反复加载/长会话的碎片化）。生产观察：显存水位用 `nvidia-smi` 监控，OOM 前 24 小时的趋势比瞬时快照更说明问题——治理是持续行为不是一次性动作。

## 7. 五个坑

**坑一：quantization_config 与 torch_dtype 混设冲突**。量化时计算精度由 `bnb_4bit_compute_dtype` 管，别再传 `torch_dtype` 打架。

**坑二：量化后手动 .to("cuda")**。破坏量化状态或报设备错误——quantization + device_map=auto 绑定。

**坑三：bitsandbytes 与 CUDA 版本不匹配**。装最新 bitsandbytes（≥0.46.1，5.x 要求）；报 `CUDA Setup failed` 先查它。

**坑四：8GB 卡硬上 7B 4bit 长上下文**。权重装下了，KV cache 爆——显存公式全量算，别只算权重。

**坑五：量化质量不评测**。「感觉差不多」不成立——任务分数对比是唯一依据。

**坑六：4bit 模型直接 torch.compile 报错**。部分量化权重与编译图不兼容——先 compile 后量化或反之按模型实测，报错时降级用非编译路径。
