## 1. 推理引擎的定位

transformers 是 HuggingFace 生态的中枢库：模型仓库（Hub）里的 150 万+ 模型，绝大多数用它加载和运行。对推理场景，它承担的角色一句话概括——**从 `AutoModelForCausalLM.from_pretrained("仓库ID")` 到 `model.generate()` 之间的全部工程**：下载与缓存、权重复合、设备与精度分发、分词与消息构造、生成参数与停止条件、量化与注意力加速、以及 v5 起的一条命令服务化。

它不只是一家公司的库，而是整个开源模型生态的「加载器事实标准」：你在 GitHub、论文、课程里看到的所有 `from_pretrained` 用法，都是它。学推理，它是第一站也是必站。

生态规模是选它的底气：Hub 上 150 万+ 模型、每周数万次新上传，从千亿参数旗舰到 0.5B 玩具模型都用同一套 API；主流开源模型（Llama、Qwen、DeepSeek、Gemma、Mistral、GLM）官方仓库全部提供 transformers 版本，模型卡的第一行示例代码永远是 `from transformers import ...`。这意味着学一次、用全部：换模型只换仓库 ID，API 骨架十年未变。对比之下，专用推理引擎（vLLM 等）虽然吞吐更强，但「任意模型都能跑、每步都能调试」的能力仍然是 transformers 独有——这也是本体系把它定为推理第一站的原因。

## 2. 解决什么问题

**模型分发的复杂性**。一个模型不是一个文件：config.json 描述架构、模型权重（safetensors 分片）、分词器文件、chat template 模板——散落在仓库不同位置。transformers 的 `from_pretrained` 一次拉齐全部组件，版本与格式由 `trust_remote_code`、`revision` 参数控制。

**架构的千差万别**。DeepSeek、Qwen、Llama、Gemini 开源版——每个模型架构不同（MoE、Mamba、混合注意力），手写加载器要重写 N 遍。Auto 类按 config 自动路由到对应实现，换模型只换仓库 ID。

**推理的完整链路**。加载只是第一步：输入要分词、对话要套模板、生成要控制长度与随机性、输出要解码、大模型要管显存。五个环节（加载→输入→生成→量化→服务）缺一环推理就跑不通或跑不快，本体系十篇就按这五环节展开。

## 3. 2026 基线：5.13.1

**当前最新稳定版 5.13.1（2026-07-11）**，5.13.0（2026-07-03）为本代功能里程碑。版本节奏是月级迭代：v5.0.0（2026-01-27）起半年内 5.0→5.13 连发十三个 minor——**必须锁版本**，跟着最新版写代码，一周后就可能被新版本行为差异坑到。

**5.x 的架构性变化**（继承自 5.0，本体系全程按 v5 写法）：模块化乐高架构、WeightConverter 动态权重复合（加载即融合 QKV/MoE）、统一 Rust 分词器（tokenizer.json 为唯一分词文件）、量化一等公民（bitsandbytes ≥0.46.1）、`HF_HOME` 统一缓存目录、`apply_chat_template` 返回 BatchEncoding。

**5.13.0 三件大事**：一是 7 个新模型接入（KimiK 2.5-2.7、MiMo-V2-Flash、Nemotron 3.5 ASR、Qwen3 ASR、HunYuan VL 等）；二是统一导出系统 HfExporter 上线（`DynamoExporter` 走 PyTorch AOT 编译、`OnnxExporter` 支持 ORT/TensorRT/OpenVINO、`ExecutorchExporter` 走移动端），自动把生成模型拆成 prefill + decode 两段导出；三是 Kernels 大升级（`use_kernels=True` 回归修复、默认内核映射改懒加载、GB10/SM121 Hub 内核支持）。**5.13.1** 专门修 vLLM 兼容性——与最新 vLLM 服务栈对齐，服务化组合时注意版本配对。

**环境要求**：Python 3.10+（5.0 起不再支持 3.9）；PyTorch 2.x；CUDA 推理需要对应 GPU 驱动。依赖关系是「transformers 依赖 torch，torch 依赖 CUDA 工具链」——环境事故九成出在这条链上，02 篇细讲。

**与 [[../../../07-模型部署与工程化/模型推理与部署/00-模型推理与部署体系总览|模型推理与部署体系]]**：那边讲推理原理（KV Cache、投机采样、批处理、成本）——概念层；本体系讲 transformers 这个具体工具怎么用——工具层。原理课 + 工具课搭配：先懂原理再看 API，参数才不是死记硬背。

**与 [[../../../07-模型部署与工程化/vLLM/00-vLLM知识体系总览|vLLM 体系]]**：vLLM 是生产级推理服务引擎，transformers 是研究与单机工具——生产吞吐靠 vLLM（PagedAttention + 连续批处理），单机实验与灵活控制靠 transformers。09 篇给完整分工决策。

## 5. 替代品对比

| 维度 | transformers | llama.cpp | vLLM/SGLang | Ollama |
|------|-------------|-----------|-------------|--------|
| 定位 | 加载+推理+工具全家桶 | 纯 C++ 推理（GGUF） | 生产级服务引擎 | 桌面化封装层 |
| 模型格式 | safetensors 原生 | GGUF 需转换 | safetensors 原生 | 包 llama.cpp |
| 灵活度 | 最高（源码级控制） | 低（参数有限） | 中（服务参数） | 最低 |
| 吞吐优化 | 弱（无调度器） | 中 | 最强（连续批处理） | 中 |
| 适用 | 实验/学习/单机 | 无 GPU/嵌入式 | 生产服务 | 本地尝鲜 |

选择逻辑：**要理解与调试模型、跑通任意架构、做实验——transformers 无可替代**；纯推理吞吐是目标且规模上来了——vLLM；没 GPU 或要极简分发——llama.cpp/Ollama。四者不是竞争而是层次：Ollama 内部就是 llama.cpp，vLLM 兼容 transformers 的模型生态。

## 6. 五条边界

**不负责训练**——训练请用 Trainer/PEFT（[[../peft（了解%20API%20即可）/00-PEFT总览|peft 体系]]）；本体系所有参数面向推理。

**不负责吞吐调度**——连续批处理在 v5 只是 serve 的 opt-in 实验特性，生产级批处理是 vLLM 的战场。

**不主导量化格式**——GPTQ/AWQ 权重格式由社区工具产出，transformers 负责加载；4bit 运行时量化靠 bitsandbytes。

**不做服务治理**——serve 提供 HTTP 端点，但没有负载均衡、优雅扩缩、监控告警；生产栈需要自己拼。

**不是所有模型的家**——超大模型（如万亿参数）与特殊后端仍需专用引擎；transformers 覆盖的是「社区主流开源模型」这个范畴。
