## 1. 速度的三要素

生成速度（每秒 token 数）由三个瓶颈决定，排查时按序诊断：**注意力计算**（序列越长占比越大，O(n²) 复杂度）、**KV cache 访存带宽**（每步都要读全部历史 KV，权重访存主导——为什么量化能提速：权重小了带宽压力小）、**批处理吞吐**（单请求推理利用率极低，批量是数量级的提升）。三要素对应三个工具族：flash attention、cache 治理与量化、批处理（服务化）。

**首 token 延迟（TTFT）与生成速度（TPS）要分开看**：TTFT 由 prefill（处理整个 prompt）决定，TPS 由 decode（逐 token 生成）决定——优化动作对不同指标效果不同：flash attention 对长 prompt 的 TTFT 提升明显，量化主要提升 TPS（访存减半）。

## 2. flash attention 与注意力后端

`attn_implementation` 三个选项决定注意力怎么算：

```python
model = AutoModelForCausalLM.from_pretrained(
    model_id, torch_dtype=torch.bfloat16,
    attn_implementation="flash_attention_2",   # 或 "sdpa"（默认）
)
```

**`sdpa`**（PyTorch 2.x 原生 scaled dot-product attention）：5.x 默认推荐，Fused kernel 已足够快，零依赖零风险——**先上它**。**`flash_attention_2`**：IO 优化的分块注意力（不物化完整注意力矩阵），长序列（4K+）吞吐数倍提升、显存占用大幅下降。**`eager`**：纯 PyTorch 实现，最慢，仅调试用。

选型决策：序列 ≤2K 且追求零依赖——sdpa 够用；**序列 4K+ 或显存紧张——flash_attention_2**。硬性要求：Ampere 架构以上 GPU（A100/RTX 30 系+）、bf16/fp16 精度（不支持 fp32）。条件不满足时 flash 静默回退或报错——`attn_implementation="flash_attention_2"` 不可用时先用 sdpa。

## 3. torch.compile

torch.compile 把模型编译成优化图（算子融合、内核自动生成），推理场景普遍提速 10-30%，长序列更明显：

```python
model = torch.compile(model, mode="reduce-overhead")   # 或 "max-autotune"（更慢的编译，更快运行）
out = model.generate(...)   # 编译后正常使用
```

三个要点：**编译发生在首次调用**（首次运行慢 1-2 分钟，之后走缓存）；**与 generate 天然兼容**（5.x 深度集成）；**与量化/分布式组合**——先量化再 compile 收益叠加，device_map 多卡时 compile 每卡生效。**DynamoExporter（5.13 的 HfExporter 之一）**把这一步固化：AOT 编译成独立产物，部署时免去首次编译等待。编译失败回退：报错时 `torch._dynamo.config.suppress_errors = True` 可降级运行（性能退回但功能可用）。

## 4. KV cache 治理

KV cache 由 generate 自动管理，但 5.x 提供了显式控制（长会话与内存敏感场景必需）：

```python
# 多轮对话续接：把上一轮 cache 传回，避免重复 prefill
cache = model.get_cache()          # 本轮结束取出
out = model.generate(inputs, past_key_values=cache)   # 下轮带 cache 续接
# 显式 cache 类型（5.x）：StaticCache 预分配（快）、OffloadedCache（显存换 CPU）
model.generation_config.cache_implementation = "static"   # 或 "offloaded"
```

**多轮对话的续接优化**：服务端每轮重发全部历史（无状态协议，见 09 篇），模型每轮重复 prefill 历史——把上轮 cache 传回可省掉重复计算。**OffloadedCache**：KV 放 CPU，显存不够长会话时的折中。**cache 与量化/compile 的兼容**是 5.13 重点修复区（FlashAttention + StaticCache、offload 钩子）——升级到 5.13.1 避坑。

## 5. 长上下文优化

长上下文（32K-256K）是推理的显存与速度双重挑战：**显存**——KV cache 线性膨胀（06 篇公式，128K 时 56GB+）；**速度**——注意力 O(n²) 与 cache 访存放大。治理三板斧：**attention 用 flash**（长序列收益最大）；**cache 用 Offloaded/压缩变体**（5.13 修复了 sliding window mask、cache 长度追踪）；**位置编码扩展**——模型声称的上下文长度由 RoPE 缩放配置决定（`rope_scaling` 在 config 里，推理时按模型卡说明处理，超长输入注意质量衰减）。**实测纪律**：模型宣称 128K 不等于 128K 好用——分档测（8K/32K/64K）看质量拐点再定生产上限。

## 6. 投机采样

投机采样（speculative decoding）：小模型（草稿）先快速生成 K 个候选 token，大模型一次验证——候选正确则 K 步并一步，错误则回退，加速 1.5-3 倍且输出分布不变：

```python
out = model.generate(inputs, max_new_tokens=200,
                     assistant_model=small_model)   # 草稿模型参数
```

transformers 原生支持 `assistant_model` 参数，5.13 修复了混合架构（Mamba2/Zamba2 等）的投机采样问题。前提：**草稿模型词表与主模型一致**（同族小模型），且显存有富余（两个模型共存）。加速收益在「大模型生成慢」的场景显著，小模型场景收益有限。原理细节见 [[../../../07-模型部署与工程化/模型推理与部署/00-模型推理与部署体系总览|模型推理与部署体系]] 03 篇。

## 7. 吞吐：批处理的本质

单请求推理时 GPU 利用率可能只有 20-30%——**吞吐提升的最大杠杆是批量**：多个请求同时进入模型，权重只读一次、计算复用。transformers 侧的批量：pipeline `batch_size` 参数（07 篇）。真正的生产级批处理是**连续批处理**（Continuous Batching：请求动态进出，完成即出、新请求即入）——v5 的 `transformers serve --continuous-batching` 已支持（opt-in，实验级），生产大规模仍是 [[../../../07-模型部署与工程化/vLLM/00-vLLM知识体系总览|vLLM]] 的领域（PagedAttention + 调度器）。**理解边界**：transformers 的批量是「固定批次」，vLLM 的批量是「动态流水」——吞吐需求上量时，优化动作从 transformers 内部移到引擎切换。

## 8. 优化顺序

**先正确，再量化，后加速，终批量**：第一步保证推理正确（版本、dtype、attn 配置对）；第二步量化解决显存（06 篇）；第三步注意力与 compile 提速（本篇 2-3 节）；第四步服务化批量与引擎选型（09 篇）。每一步有明确的收益与验收（测 TPS/TTFT 前后对比），**不做无基准的优化**——「感觉快了」不算数，`time` 计时与 TPS 计算才是依据。

## 9. 五个坑

**坑一：fp32 下用 flash_attention_2**。不支持 fp32——bf16 是前置条件。

**坑二：老 GPU 上 flash 报错**。Ampere 以下架构不支持——sdpa 兜底。

**坑三：torch.compile 首调超时当成卡死**。编译耗时 1-2 分钟正常——耐心等或改 max-autotune 为 reduce-overhead。

**坑四：长序列直接干到模型宣称上限**。质量拐点提前到来——分档实测。

**坑五：优化不做基准**。改完不测 TPS/TTFT——无法判断收益与回退，优化动作全部白做。

**坑六：KV cache 与量化后模型混用报错**。部分旧 cache 实现与量化权重不兼容——5.13 已修，锁版本 + 升级即解。
