## 1. 实战：本地 LLM 推理 API 服务

把全体系知识点压进一个项目：离线加载、量化、服务化、客户端接入、压测验收。目标：在单卡上跑一个私有对话服务，任何 OpenAI 客户端可接入。

**第一步，离线准备**（有网机器）：

```bash
pip install "transformers[serving]==5.13.1" torch accelerate bitsandbytes
python -c "
from huggingface_hub import snapshot_download
snapshot_download('Qwen/Qwen2.5-7B-Instruct')   # 全量拉取（约 15GB）
"
```

**第二步，服务化**（GPU 机器，模型缓存拷入）：

```bash
export HF_HUB_OFFLINE=1
transformers serve \
  --force-model Qwen/Qwen2.5-7B-Instruct \
  --quantization bnb-4bit --dtype bfloat16 \
  --continuous-batching --model-timeout 600 \
  --port 8000
```

**第三步，客户端接入与验收**：

```python
from openai import OpenAI
import time

client = OpenAI(base_url="http://localhost:8000/v1", api_key="local")

# 验收一：对话正确性（响应非空 + 内容合理）
resp = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[{"role": "user", "content": "用三句话介绍 RAG"}],
    max_tokens=200)
assert resp.choices[0].message.content

# 验收二：流式可用（SSE 逐块）
stream = client.chat.completions.create(..., stream=True)

# 验收三：吞吐压测（并发请求，统计 TPS）
from concurrent.futures import ThreadPoolExecutor
def one(i):
    t0 = time.monotonic()
    client.chat.completions.create(model=..., messages=[{"role": "user", "content": "hi"}], max_tokens=50)
    return time.monotonic() - t0
with ThreadPoolExecutor(8) as ex:
    times = list(ex.map(one, range(32)))
print(f"P50={sorted(times)[16]:.2f}s  TPS≈{sum(50 for _ in times)/sum(times):.1f}")
```

**验收三问**：**能服务吗**——对话/流式/并发三场景通过；**资源可控吗**——`nvidia-smi` 看显存占用符合 4bit 预期；**可观测吗**——日志记录请求、延迟、错误率。加试：多轮对话（拼接历史）、工具调用（Qwen 支持）、卸载重启（`--model-timeout` 生效）。

**常见失败模式与排查顺序**：服务起不来——先查环境（CUDA 可用性、bitsandbytes 版本、锁版本一致性），再查模型（离线完整性 `HF_HUB_OFFLINE=1` 后 local_files_only 试加载），最后查端口与权限；请求报 4xx/5xx——先 curl `/v1/models` 确认模型名匹配，再看服务日志的异常栈（90% 是输入问题：缺模板、超长、格式错）；请求慢——先看是 TTFT 慢（prefill 长/加载了模型）还是 TPS 慢（量化没生效/CPU 推理），再按 08 篇三要素定位；显存 OOM——`nvidia-smi` 看占用曲线，量化 → 短序列 → 降批量的顺序治理。**排查的第一原则是「先环境后代码」**：transformers 的报错信息里环境类错误占比超过一半，别一上来就改业务逻辑。

## 2. 生产配置模板与纪律清单

**加载**：`torch_dtype=bf16` + `device_map="auto"` 绑定；离线 `HF_HUB_OFFLINE=1` + `local_files_only=True`。**量化**：4bit NF4 起步（`bnb_4bit_compute_dtype=bf16`），服务化用预量化仓库优先。**生成**：`max_new_tokens` + `stop_strings` 双停止，`do_sample=True` + temperature/top_p。**优化**：先 sdpa 后 flash（长序列），torch.compile 免费提速。**服务**：serve 锁版本、force-model、预下载、连续批处理配 flash。**监控**：TPS/TTFT/P99 三指标 + 显存水位 + 日志（[[../../强烈推荐（做项目必用，简历加分）/loguru/00-loguru总览|loguru]]）。**版本**：transformers==5.13.1 锁死，升级先跑回归（生成质量 + 兼容性）。

## 3. 报错速查十条

| 报错 | 含义 | 处理 |
|------|------|------|
| `CUDA out of memory` | 显存不足 | 显存公式算账：量化 → 短序列 → 换模型 |
| `torch.cuda.is_available()=False` | torch 装成 CPU 版 | 重装 cu128 索引版 |
| `Tokenizer does not have a padding token` | 缺 pad_token | `tok.pad_token = tok.eos_token` |
| `GPTQConfig` 缺失 | 预量化加载缺依赖 | `pip install optimum auto-gptq` |
| `CUDA Setup failed`（bitsandbytes） | 版本不匹配 | 升 bitsandbytes ≥0.46.1 |
| `device_map` 与 `.to()` 冲突 | 手动移动破坏分发 | 只用 device_map=auto |
| `max_length` 警告 | 新旧参数混用 | 统一 max_new_tokens |
| `trust_remote_code` 报错 | 远程代码未授权 | 只对可信仓开 |
| `ConnectionError` 下载失败 | 网络问题 | HF_ENDPOINT 镜像 |
| flash 不可用回退 | GPU 架构不支持 | sdpa 兜底 |

**生产环境的版本与升级纪律**：transformers 月级迭代意味着「锁版本」不只是安装动作，更是**升级流程**——升级前先看 changelog（破坏性变更集中在 5.0/5.13 这类代际版本）、升级后跑回归（生成质量对比 + 兼容性冒烟：加载→生成→serve 三连）、灰度观察（先一台再全量）。2026 年的教训是 5.13.0 的 Kernels 接口变更（不再接受 model-type 仓库）影响了一批存量调用——**升级 = 计划内项目，不是顺手行为**。生产环境的另一个纪律是「环境即代码」：依赖清单（requirements.txt 锁版本）、环境变量（HF_ENDPOINT/HF_HOME）、启动参数全部进仓库，换机器一键复现——这也是面试常问的「你如何保证生产环境可复现」。

## 4. 面试三范式

**价值式**：「我在单卡 24GB 上跑通了 70B 模型推理——4bit NF4 量化把权重压到 40GB 以内，配合 device_map 分层，服务化用 transformers serve 起 OpenAI 兼容端点，压测 P50 延迟 X 秒。」——先讲结果与数据，再讲手段。

**技术式**：「推理显存 = 权重 + KV cache，KV 随序列线性膨胀所以长上下文才是瓶颈；bf16 默认档、4bit 是单卡大模型标准；flash attention 是 IO 优化不物化注意力矩阵；生成是自回归循环，流式用线程 + streamer。」——原理讲透，别停在「transformers 很流行」。

**生产式**：「锁版本（5.13.1）因为月级迭代；离线三件套（snapshot + HF_HUB_OFFLINE + local_files_only）；质量评测驱动量化决策；吞吐量级需求换 vLLM。」——版本意识、离线部署、评测纪律、引擎选型，四点是区分度。

**追问四连**：为什么 chat 必须 template？（模型标记各异，模板在仓库里自动适配）｜70B 怎么上单卡？（4bit + 必要时 offload，质量评测）｜KV cache 多轮对话怎么省？（cache 传回避免重复 prefill）｜serve 与 vLLM 怎么选？（中低负载 serve，吞吐上量换 vLLM）。

## 5. 简历呈现

项目经历写法：「基于 transformers 的私有 LLM 推理服务——4bit 量化在单卡部署 70B 模型，transformers serve 提供 OpenAI 兼容 API，支持流式输出与工具调用；离线部署三件套保障内网可用；压测 TPS X、P99 Y，量化质量评测损失 1-3%。」技能栏：「HuggingFace Transformers（模型加载/生成/量化/服务化），LLM 推理优化（flash attention/KV cache/量化）」。——量化 + 数据 + 工具链三要素。
