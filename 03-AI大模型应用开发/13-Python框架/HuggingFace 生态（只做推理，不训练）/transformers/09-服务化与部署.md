## 1. transformers serve 是什么

v5 内置的推理服务 CLI：一条命令启动本地 HTTP 服务，**兼容 OpenAI API 协议**——这是 2026 年的事实标准协议，意味着任何 OpenAI 客户端（LangChain、OpenAI SDK、各类工具）改个 base_url 就能接入你的本地模型。

```bash
pip install "transformers[serving]"
transformers serve --port 8000
```

支持的端点：`/v1/chat/completions`（对话，支持文本/图像/音频/视频多模态输入）、`/v1/completions`（补全）、`/v1/responses`（OpenAI Responses API，实验级）、`/v1/audio/transcriptions`（语音转写）、`/v1/models`（扫描本地缓存列出可加载模型）、`/load_model`（预加载模型，SSE 流式返回加载进度）。还支持 OpenAI 风格工具调用（Qwen/Gemma 4 开箱即用）与 MCP 客户端能力（当前限 Qwen 家族）——本地模型直接给 Agent 当工具使。

## 2. 启动与关键参数

```bash
transformers serve \
  --port 8000 \
  --force-model Qwen/Qwen2.5-7B-Instruct \   # 固定模型，避免每请求加载决策
  --continuous-batching \                    # 连续批处理（吞吐关键，配 sdpa/flash）
  --quantization bnb-4bit \                  # 加载即量化（或 bnb-8bit，或预量化仓库）
  --dtype bfloat16 \                         # 精度（fp32 默认太费显存）
  --model-timeout 300                        # 空闲 300s 自动卸载（-1 禁用）
```

参数组合是性能的关键：**`--continuous-batching` + `--attn_implementation flash_attention_2`** 是中负载吞吐标准组合（5.13 修了 vLLM 兼容，同理注意 serve 与版本）；**`--quantization bnb-4bit` + `--dtype bfloat16`** 是单卡大模型组合；**`--force-model`** 固定模型避免请求间模型切换抖动。启动后 `--model-timeout` 控制空闲卸载——多模型按需加载时省显存，但首请求要等加载（`/load_model` 预热接口解决）。

## 3. 客户端接入

任何 OpenAI 兼容客户端，改 base_url 即用：

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="local")

resp = client.chat.completions.create(
    model="Qwen/Qwen2.5-7B-Instruct",        # 名称要匹配 /v1/models 里的
    messages=[{"role": "user", "content": "你好"}],
    stream=True,                             # 流式：SSE 逐块返回
)
for chunk in resp:
    print(chunk.choices[0].delta.content or "", end="")
```

**无状态协议纪律**：OpenAI 兼容服务是无状态的——每次请求必须携带完整对话历史（`messages` 全量），服务端不做会话记忆。多轮对话由调用方拼接历史（04 篇 messages 结构）。`stream=True` 流式响应是标准姿势——SSE 逐块推送，前端实时显示。CLI 验证：`transformers chat` 起一个命令行聊天界面，快速验证服务可用性。

## 4. 模型生命周期管理

**预下载**：服务启动时模型按需下载会拖慢首个请求——生产先下载再启动：

```bash
transformers download Qwen/Qwen2.5-7B-Instruct   # 提前下载，/v1/models 立即可见
```

**多模型共置**：缓存里有多个模型时，serve 按请求的 model 参数加载对应模型（`--force-model` 则固定一个）；加载/卸载由 `--model-timeout` 自动管理。**加载可视化**：`/load_model` 端点 SSE 推送进度（processor→config→下载→权重 四阶段），前端可显示加载进度条——本地部署 UI 的好用接口。

## 5. 与 vLLM 的选型分工

| 维度 | transformers serve | vLLM |
|------|--------------------|------|
| 定位 | 单机/实验/中低负载 | 生产大规模服务 |
| 吞吐 | 连续批处理（opt-in 实验） | PagedAttention + 调度器，最强 |
| 兼容性 | OpenAI 协议 | OpenAI 协议 |
| 部署复杂度 | 一条命令 | 参数多但成熟 |
| 适用 | 开发调试/本地私有化/内网工具 | 线上服务/高并发/多模型 |

**选型决策**：开发期、内网私有化、中低负载（并发 <几十）、模型快速切换场景——serve 足够且零成本；**高并发生产、吞吐要求量级提升、长时稳定服务——vLLM**。升级路径平滑：serve 里验证过的模型与参数，vLLM 直接复用（同仓库同量化格式）。官方定位明确：serve「experimental/评估/中低负载」，大规模生产推荐 vLLM 或 SGLang——别把实验特性当生产承诺。

## 6. 导出：HfExporter

5.13 的统一导出系统把模型导出成独立产物，部署时脱离 transformers 运行时：

| 导出器 | 目标 | 用途 |
|--------|------|------|
| `DynamoExporter` | PyTorch AOT 编译 | 编译产物免首调等待，torch 运行时 |
| `OnnxExporter` | ONNX（ORT/TensorRT/OpenVINO） | 跨运行时部署，CPU/边缘加速 |
| `ExecutorchExporter` | ExecuTorch | 移动端/边缘设备 |

```bash
# 生成模型自动拆成 prefill + decode 两段导出（5.13 特性）
transformers export onnx --model Qwen/Qwen2.5-0.5B-Instruct --output onnx_dir
```

导出场景：**CPU 生产部署**（ONNX Runtime 推理比 torch 快且轻）、**边缘设备**（ExecuTorch）、**免首次编译**（Dynamo 产物）。导出产物配合 ONNX Runtime/OpenVINO 运行时使用——性能与灵活性是 trade-off：导出后换架构就难了，锁定部署形态才值得导出。

## 7. 容器化与生产加固

**Docker 部署标准形态**（配合 [[../../../07-模型部署与工程化/部署工具/00-部署工具知识体系总览|部署工具体系]]）：

```dockerfile
FROM nvidia/cuda:12.x-runtime  # 或 pytorch 官方镜像
RUN pip install "transformers[serving]==5.13.1" torch bitsandbytes
ENV HF_HUB_OFFLINE=1 HF_HOME=/models   # 离线模式 + 模型挂载卷
# 模型提前 snapshot_download 到 /models
CMD ["transformers", "serve", "--port", "8000", "--quantization", "bnb-4bit"]
```

```bash
docker run -p 8000:8000 -v /data/models:/models my-tf-server  # 模型数据卷，镜像不含模型
```

**生产加固五件事**：模型卷与镜像分离（模型 10-40GB 不进镜像层）；`HF_HUB_OFFLINE=1` 防启动联网卡死；启动健康检查（`/v1/models` 就绪探测）；请求限流与超时（网关层，见 [[../../../01-Python语言/Python%20异步%20+%20FastAPI/00-Python异步与FastAPI总览|FastAPI 网关]]）；GPU 监控（`nvidia-smi` 显存/利用率，配合 [[../../强烈推荐（做项目必用，简历加分）/loguru/00-loguru总览|loguru]] 日志——请求延迟、token 数、错误率三指标）。单 GPU 容器标准：`--gpus all` + `shm-size` 调大（共享内存不足是高频坑）。

**安全与暴露面**：serve 默认监听 0.0.0.0，OpenAI 协议无内置鉴权（api_key 只是占位）——**内网部署也建议加一层网关鉴权**（简单 token 校验或 [[../../../01-Python语言/Python%20异步%20+%20FastAPI/00-Python异步与FastAPI总览|FastAPI 反代]]），绝不直接暴露公网。数据面考虑：请求与响应会进日志，敏感 prompt（客户数据、内部文档）需要脱敏或关闭请求日志。多租户/多人使用还要做**并发与速率限制**（防单用户打满 GPU 影响他人）与**模型白名单**（serve 的 /v1/models 会列出缓存全部模型，按需用网关过滤）。

## 8. 五个坑

**坑一：服务启动时模型现下**。首个请求慢到超时——`transformers download` 预下载。

**坑二：OpenAI 客户端 model 名写错**。与 `/v1/models` 不一致报 404/400——先 curl 端点看模型列表。

**坑三：连续批处理不生效**。`--continuous-batching` 需配合 sdpa/flash 注意力——参数组合缺一不可。

**坑四：容器 shm 太小**。PyTorch DataLoader 与多进程共享内存 OOM——`--shm-size` 调大。

**坑五：把 serve 当生产承诺**。高并发场景 serve 掉链子——量级需求直接上 vLLM，别等线上再换。
