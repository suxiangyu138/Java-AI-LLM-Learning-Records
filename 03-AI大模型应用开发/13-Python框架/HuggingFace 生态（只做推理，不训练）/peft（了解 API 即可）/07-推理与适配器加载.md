## 1. 为什么推理侧离不开 PEFT

**2026 年模型分发的主流形态是 adapter 而不是全量 checkpoint**：社区里"微调过的模型"仓库，十有八九只有 `adapter_config.json + adapter_model.safetensors`（几十 MB）——底座还是社区基座模型。原因很现实：**全量 checkpoint 140GB 的存储与下载成本，与几十 MB 的 adapter 相比没有竞争力**；底座更新时，adapter 社区还会跟随发布新版本。**所以"用微调模型"这件事的默认姿势是：`AutoModel.from_pretrained(底座)` + `PeftModel.from_pretrained(adapter)`——PEFT 是推理链路的固定一环**，这正是本目录"只做推理，不训练"定位下 PEFT 依然存在的原因。

## 2. 加载 adapter：两条路径

```python
# 路径一：显式 PEFT（控制力最强）
from peft import PeftModel
base = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B")
model = PeftModel.from_pretrained(base, "user/qwen2.5-7b-legal-lora")

# 路径二：transformers 原生（目录自带 adapter 时自动识别）
model = AutoModelForCausalLM.from_pretrained("user/qwen2.5-7b-legal-lora")
```

**路径二之所以可行**：transformers v5 的 `PeftAdapterMixin` 集成层——加载时检测到目录里有 `adapter_config.json`，自动把加载工作转交给 PEFT（v5 要求 peft ≥ 0.19.1）。**两条路径等价**，路径一显式（自己控底座，适合"底座已加载、临时挂 adapter"），路径二省心（一个 API 一条龙，适合"仓库自包含"场景）。

**加载的配套设置**：`device_map`（多卡/CPU 场景分配层）、`torch_dtype`（**与底座训练时一致，QLoRA 产物按 bf16 加载**）、`trust_remote_code=True`（自定义架构仓库需要，**只对可信仓库开**）——**"底座怎么加载，adapter 就怎么加载"**：两者走同一条 from_pretrained 链，PEFT 的活只是"挂"。

## 3. 三种推理姿势

**姿势一：不合并直接推理**——`PeftModel.from_pretrained(base, adapter)` 后直接 `generate()`。**PEFT 前向时把 α/r·BA 叠加进权重计算**（推理开销约 1-2%，adapter 保持"可切换"状态）。适合：多 adapter 切换、临时体验、底座还要继续挂别的任务。

**姿势二：merge_and_unload 合并**——A、B 写回 W、拆掉 PEFT 外壳，得到**普通 transformers 模型**。合并后推理零额外开销，且**任何推理框架都能加载**（不依赖 peft 环境）。适合：部署（最常用，09 篇）、对比实验。

**姿势三：unload 还原**——卸下 adapter 恢复纯净底座。适合：调试"adapter 贡献了什么"（同一 prompt 对比合并前后输出）。

**选型主线**：**本地玩/切换用姿势一，生产部署用姿势二**——"合并是部署的最短路径：一个普通模型文件，处处可跑"。

**姿势一的代码要点**：生成前 `model.eval()` + `torch.no_grad()`；**merge 前先确认不需要继续切换**（合并不可逆）；**对比实验的黄金做法**：同一 prompt 依次跑 纯底座 / 姿势一 / 姿势二 三种输出——**三份输出对比就是"adapter 贡献"的最直观证据**，面试讲适配器效果时这是最扎实的论据。

## 4. 一致性铁律

**adapter 与底座必须严格匹配，这是推理侧最大的坑**。匹配的四个维度：

- **底座型号**：`adapter_config.json` 里记录 base_model_name_or_path——**Llama-3-8B 的 adapter 挂到 Llama-4-8B 上报尺寸不匹配**；
- **底座版本**：同一型号不同版本（如 Qwen2.5-7B 与 Qwen2.5-7B-Instruct）层结构可能不同——**KeyError/形状错误是最常见信号**；
- **量化方式**：4bit 底座上训练的 adapter 加载到 fp16 底座——报错或精度劣化（QLoRA 训练的 adapter 最好在同样量化配置下加载）；
- **依赖版本**：adapter 的 config 里若记录了新参数（如 finetuning_type="dora"），**peft < 0.18 加载直接失败**。

**实操规则**：**模型卡会写明"Base Model: Qwen/Qwen2.5-7B"——照抄，不猜**；加载报 KeyError 先核对底座与 adapter 是否同一型号，而不是改 target_modules。

**一致性验证的快速法**（不用等报错）：加载后跑一个冒烟 prompt，**输出与模型卡示例不符（或输出乱码/空）说明底座不匹配**；再进一步：`model.active_adapter` 确认 adapter 确实生效——**"能加载 ≠ 加载对了"**，输出验证是最后一道保险。

## 5. 多 adapter 切换与停用

```python
model = PeftModel.from_pretrained(base, "user/legal-lora", adapter_name="legal")
model.load_adapter("user/code-lora", adapter_name="code")   # 挂第二个
model.set_adapter("code")          # 切换生效
model.active_adapter                # 'code'
model.disable_adapter()             # 全停：用纯净底座推理（对比基线用）
```

**多 adapter 场景的真实价值**：同一底座上"法律版/代码版/聊天版"按请求切换——**显存只占一份底座**；生产侧 vLLM 把这套能力变成"请求级动态加载"（第 7 节）。**注意 set_adapter 是 O(1) 切换，但多 adapter 都驻留显存**（每个 adapter 的 A/B 都要占一份），adapter 数量太多时反而要取舍。

## 6. transformers v5 的原生支持

transformers v5 的 PEFT 集成（`src/transformers/integrations/peft.py` 的 `PeftAdapterMixin`）做了三件事：**自动识别 adapter 目录并转发给 PEFT 加载**；**合并权重逻辑**（v5 早期在 transformers 内重复实现，PR #46442 后收敛回 PEFT 0.19.1，去重）；**提供 adapter 卸载/管理的标准接口**。**给使用者的结论**：v5 起"加载微调模型"的体验完全统一——**`from_pretrained` 一个 API 通吃纯模型与带 adapter 模型，不必关心内部是 PEFT 还是普通权重**；代价是版本约束（peft ≥ 0.19.1）成为硬性依赖。

## 7. 服务化：vLLM 与动态加载

生产服务化的两个方向：

**方向一：合并后部署**——`merge_and_unload` 产出普通模型，vLLM/Ollama/TGI 按普通模型加载，**无 peft 依赖、兼容性最好**；代价：每个 adapter 一份完整底座存储，多任务要多个服务或重启切换。

**方向二：vLLM LoRA 动态加载**——vLLM 支持 `--enable-lora` 与请求级 `lora_request`：**一个底座服务，请求时按名字动态挂 adapter**（几十 MB 即时加载，`/v1/lora_adapters` 接口管理）——"**多任务一份底座，切换零重启**"，与 PEFT 的 adapter 格式直接兼容。**选型主线**：单任务合并部署最简单；多任务/频繁切换上 vLLM 动态加载（vLLM 部署细节看 `../../../../07-模型部署与工程化/vLLM/00-vLLM知识体系总览.md`）。

## 8. 五个常见坑

- **坑一**：底座型号不匹配（最常见）——**先查 adapter 的模型卡 Base Model 字段**；
- **坑二**：QLoRA 训练的 adapter 加载到 fp16 底座——**保持训练时的量化配置加载**（08 篇）；
- **坑三**：merge_and_unload 后想再 load_adapter——合并不可逆，**先备份 adapter 目录**；
- **坑四**：推理忘了 eval()——dropout 仍在工作，**结果不稳定；`model.eval()` 是推理第一行**；
- **坑五**：多 adapter 全部 load 后显存暴涨——**只挂常用的几个，其余按需 load_adapter**。
- **坑六**：加载时 torch_dtype 与训练时不一致（训练 bf16 加载 fp32）——显存翻倍或精度漂移；**显式传 torch_dtype="auto"**。
