## 1. 适配器即产品

**把 adapter 当成产品而不是"训练副产品"**——这是本体系生产观的起点。事实支持：**adapter 只有几十 MB、格式自包含（config + 权重 + 底座声明）、可以像软件一样版本化**。全量 checkpoint 做不到的事，adapter 全做得到：**多版本并存（同一底座不同 r 的 adapter 按需加载）、组合叠加（多个 adapter 加权融合）、即时切换（服务内热加载）**。生产思维转换：**"底座是操作系统，adapter 是应用——应用可以单独发布、升级、回滚，不用重装系统"**。

## 2. 多适配器的组织与命名

```python
model = PeftModel.from_pretrained(base, "user/legal-v1", adapter_name="legal-v1")
model.load_adapter("user/legal-v2", adapter_name="legal-v2")   # 升级版并存
model.load_adapter("user/code-v1", adapter_name="code-v1")
model.set_adapter("legal-v2")          # 切换
model.get_peft_config()                # 查看各 adapter 配置
```

**命名规范是生产纪律**：adapter_name 建议 `任务-版本`（legal-v1/code-v2）——**切换/回滚/审计都靠名字**；目录层面建议 `adapter-<任务>-<版本>/` 统一前缀，与底座目录分离存储（adapter 目录独立可拷贝）。**多 adapter 驻留显存的账要算**：每个 adapter 的 A/B 常驻（r=16 时一个 adapter 约几 MB 级权重，但**反向时各自独立计算图**），**生产上同时激活的 adapter 控制在 3-5 个内，其余按需 load_adapter**。

**目录组织参考**（小团队够用的结构）：

```text
adapters/
├── legal-v1/  legal-v2/     # 同一任务多版本（v2 是升级版）
├── code-v1/                 # 另一任务
└── merged/                  # 合并产物（部署目录，普通模型）
```

**版本管理纪律**：**adapter 目录内放一个 config.yaml 记录 r/alpha/数据摘要/底座版本**——三个月后回看，只有目录名的 adapter 等于没留档（第 7 节审计）。

## 3. 合并部署：最短生产路径

```python
model = PeftModel.from_pretrained(base, "./legal-v1")
merged = model.merge_and_unload()
merged.save_pretrained("./deploy/legal-v1")   # 普通 transformers 模型
tokenizer.save_pretrained("./deploy/legal-v1")

# 部署端：零 PEFT 依赖
import vllm  # 或任何推理服务
vllm.LLM(model="./deploy/legal-v1")            # 就是普通模型路径
```

**合并部署的三个优势**：其一，**推理零额外开销**（没有叠加计算）；其二，**任意推理框架无感加载**（不依赖 peft 环境、不要求版本匹配）；其三，**回滚简单**（重新合并旧 adapter 即可）。**代价**：每个 adapter 一份完整底座存储（7B fp16 约 14GB）——**单任务部署的最优解，多任务的账要算**。

## 4. 加权融合：add_weighted_adapter

```python
model = PeftModel.from_pretrained(base, "user/legal-v1", adapter_name="legal")
model.load_adapter("user/code-v1", adapter_name="code")
weights = [0.6, 0.4]                       # 两个 adapter 的融合权重
model.add_weighted_adapter(
    adapters=["legal", "code"], weights=weights,
    combination_type="linear",             # linear/svd/cat 三种组合方式
    adapter_name="legal-code-v1",
)
model.set_adapter("legal-code-v1")
```

**融合的用途**：**多能力叠加**（法律 + 代码的"全能 adapter"）、**能力微调**（调权重比例消融贡献）。**v0.19 行为变更**：`add_weighted_adapter` 支持**负权重**——**减法式组合**：通用 adapter 减去任务 adapter 得到"排除某能力"的 adapter（GenKnowSub 思路的 API 化）。**注意**：组合方式 `linear`（按权重线性加，速度快）/ `svd`（SVD 低秩近似，质量高但慢）/ `cat`（拼接，参数量翻倍）——**小模型用 linear 起步，质量不足换 svd**；融合产物也是一个普通 adapter，可继续 merge 部署。

**融合 vs 切换的选型**：融合（add_weighted_adapter）得到"**一个** adapter"——能力是两者的加权混合，适合"固定组合"的部署；切换（set_adapter）保留"**多个** adapter"——能力随请求变，适合"按需分流"的服务——**"融合是打包，切换是分拣"**；融合不可逆（原 adapter 仍保留），先小权重比例验证再上线。

## 5. 发布 Hub：adapter 的分发规范

```bash
huggingface-cli login    # 或环境变量 HF_TOKEN
```

```python
peft_model.push_to_hub("your-name/your-lora", token=os.environ["HF_TOKEN"])
```

**发布目录规范**（模型卡 README 必写三项）：**Base Model**（底座型号 + 版本，用户加载的第一依据）；**使用方式**（`PeftModel.from_pretrained` 三行代码）；**训练配置摘要**（r/alpha/数据量/任务——**adapter 的"说明书"，缺了别人不敢用**）。Hub 上的 adapter 与本地目录同构：`PeftModel.from_pretrained("your-name/your-lora")` 全球可加载——**发布即分发，一条命令完成**。

## 6. 服务化部署两种形态

**形态一：合并静态部署**（第 3 节）——单任务、稳定版本：合并 → 普通模型 → 任意框架。**形态二：动态加载**（07 篇第 7 节）——多任务、高频切换：vLLM `--enable-lora`，请求级指定 adapter，**切换零重启**。**选型主线**：**任务数 × 切换频率决定**——"任务少合并最省心，任务多动态加载最省资源"；动态加载的 adapter 目录直接从 Hub 拉取（vLLM 支持 `lora_adapters` 配置源），**发布与部署闭环**。

## 7. 审计与版本管理

adapter 是资产，就要有资产管理纪律：

- **底座版本锁定**：adapter 记录底座型号，**底座升级必须重新验证 adapter**（7B 底座升版本，旧 adapter 可能 KeyError——一致性铁律的生产版）；
- **版本号语义**：adapter 目录名/仓库 tag 用 `v1/v2`，**训练配置变更（r/alpha/数据）必须升版本**；
- **效果基线留档**：每个版本留下"评估样本 + 输出对比"快照——**回滚决策靠数据，不靠记忆**；
- **量化与精度**：QLoRA 产物标注量化配置（nf4/fp16），**加载方按配置复现**；
- **合规**：adapter 继承底座许可（如 Llama 系 license），**发布页写明底座许可与再分发条件**；
- **卡片完整**：README 含 Base Model（底座 + 版本）、任务描述、训练数据摘要、超参（r/alpha/epochs/lr）、评估结果、已知限制——**字段齐 = 别人敢用 = 生产资产**。

## 8. 生产检查清单

- [ ] adapter 与底座型号/版本匹配（模型卡照抄）
- [ ] 推理前 `model.eval()`；合并前备份 adapter 目录
- [ ] 部署产物 = 合并模型（单任务）或 vLLM 动态加载（多任务）
- [ ] 发布目录含 Base Model/使用方式/训练配置三项说明
- [ ] tokenizer 随 adapter 一起保存/发布
- [ ] 版本号语义清晰，旧版本可回滚
- [ ] 效果基线（评估样本 + 输出对比）留档
- [ ] 量化配置（nf4/fp16/计算精度）随产物标注
- [ ] 底座许可与再分发条款确认
- [ ] 生产监控：加载成功率/切换延迟/推理耗时（含 merge 前后对比）

## 9. 五个常见坑

- **坑一**：多 adapter 全量 load 常驻显存——**只激活常用的 3-5 个**；
- **坑二**：add_weighted_adapter 的 adapter 必须是同底座同结构——**混底座融合直接报错**；
- **坑三**：融合后不 merge 就部署——**融合产物是 PEFT 模型，直接部署仍需 peft 环境；先 merge 再部署**；
- **坑四**：发布时忘了 tokenizer——**加载方 from_pretrained 底座后没有分词器，API 直接断**；
- **坑五**：底座升级后旧 adapter 直接上生产——**先做一致性验证（加载 + 冒烟推理）再切流**。
