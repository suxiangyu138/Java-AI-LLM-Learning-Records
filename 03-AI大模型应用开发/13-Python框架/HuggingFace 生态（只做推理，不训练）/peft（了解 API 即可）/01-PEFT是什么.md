## 1. PEFT：一个概念与一个库

**PEFT**（Parameter-Efficient Fine-Tuning）是一类训练策略的总称：**不更新全部模型参数，只训练一小部分新增参数（或子集），就能达到接近全量微调的效果**。**HuggingFace PEFT** 是这套策略的 Python 事实标准库：`pip install peft`，API 围绕"配置 → 包装 → 训练 → 保存/加载"四个动作展开。2026 年的生态现实是：**社区发布"微调过的模型"时，绝大多数只发布 adapter（几十 MB 的增量权重），而不是全量 checkpoint（几十 GB）**——所以"会加载 adapter"是每个用模型的人的日常，而加载器就是 PEFT。本体系定位"了解 API 即可"：**把 PEFT 的 API 层（配置/训练/加载/合并）吃透，不深挖源码**——这正是本目录"只做推理，不训练"定位下的真实分工：99% 的日子你在加载别人训好的 adapter，1% 的日子自己训一把。

**名词辨析先厘清三对关系**：**PEFT 是类**（Parameter-Efficient Fine-Tuning 一族训练策略的总称），**LoRA 是 PEFT 最著名的实例**（低秩注入式），**QLoRA 是 LoRA 的量化变体**（4bit 底座 + LoRA，08 篇）——三者的关系是"策略 → 方法 → 变体"的递进，面试时把这三层说清楚，比背十个方法名有用得多。PEFT 库则是这套策略的 Python 实现容器：LoRA/DoRA/QLoRA 等全部方法都通过它统一暴露（04 篇的 finetuning_type 就是方法目录）。

## 2. 解决什么问题

**问题一：显存**——全量微调 70B 模型需要 42GB+ 显存（每参数约 6 字节：梯度 + 优化器状态）；LoRA 只训增量矩阵，**70B 也能在 24GB 卡上微调，QLoRA 更是把门槛压到 10GB 级别**（08 篇账本）。

**问题二：存储与分发**——全量微调产出一个 70B 的 checkpoint 是 140GB+；LoRA 的 adapter 只有 **r×d×2 个参数**（r=16 时约 0.1% 总量），**几十 MB**——"训练在云端，下载是瞬间"。

**问题三：训练成本与灾难性遗忘**——只训练少量参数，收敛快、过拟合小；更关键的是**一个底座可以挂多个 adapter**：同一个 Llama-4-8B 底座上挂"法律 adapter""代码 adapter""聊天 adapter"，切换只换几十 MB 文件，**不用为每个任务存一份完整模型**（03/09 篇多 adapter 管理）。

**问题四：训练速度与迭代节奏**——全量微调一次 70B 要几天（多卡并行 + 大量通信），LoRA 只训练 1% 参数，**单卡数小时到一天内出结果**——"试错成本低"是 PEFT 的另一层隐性价值：数据与超参迭代可以一天多轮，全量微调只能周级迭代。2026 年团队做模型适配（领域化、风格化）的默认节奏就是"晚上挂训练、早上看结果"——**只有 PEFT 撑得起这个迭代速度**。

## 3. 一个画面：冻结与注入

把模型想象成一张大网：**全量微调 = 整张网重新编织；PEFT = 网保持原样，只在关键节点上缝几根细线**。LoRA 的细线是低秩矩阵 A、B（形状 r×d 与 d×r），注入后每层权重变成 `W' = W + (α/r)·BA`——**W 冻结不动，训练只更新 A、B**。PEFT 库把这套动作封装成一行：`model = get_peft_model(base_model, LoraConfig(...))`——包装后模型"看起来一样"（前向完全兼容），训练时自动跳过冻结参数、自动组装优化器状态。**训练结束保存的是 A、B 而非 W**——这就是"adapter 即产品"的来历。

## 4. 2026 现状与版本基线

**2026-08 基线：v0.19.1（2026-04-16 发布，Python ≥ 3.10）**。版本演进关键节点：

| 版本 | 时间 | 关键变化 |
|------|------|---------|
| 0.19.1 | 2026-04-16 | 当前稳定版（锁这个版本） |
| 0.19.0 | 2026-04-14 | BD-LoRA/LoRA-GA/PVeRA/PSOFT；非 LoRA→LoRA 转换；cartridges；LoRA 支持 Transformer Engine |
| 0.18.1 | 2026-01-09 | transformers v5 兼容修复、ROCm 修复 |
| 0.18.0 | 2025-11-13 | **弃 Python 3.9；方法大爆发 + `finetuning_type` 统一 API** |
| 0.17.0 | 2025-08 | SHiRA 方法；target_parameters（MoE 层）；state_dict 注入 |

**两条 2026 关键认知**：其一，**transformers v5（2026-01-27）与 PEFT < 0.18.0 不兼容**，v5.12.1 把下限提到 0.19.0，后续 PR #46442 提到 0.19.1 并移除 transformers 里重复的转换代码——**装 transformers v5 必配 peft ≥ 0.19.1**；其二，**方法演进进入"周更"节奏**——0.17 到 0.19 一年内新增十余种方法，但 **LoRA 始终是事实标准，新方法围绕 LoRA 家族打补丁**（DoRA 解耦幅度、rsLoRA 稳定高秩、S-LoRA 稀疏化），API 只新增了 `finetuning_type` 一个统一开关——**"学会 LoRA 一个，全家族贯通"**。

## 5. 方法家族全景

PEFT 方法按"训什么"分四族：**注入式**（LoRA 系：在层旁加低秩分支，2026 年绝对主流，QLoRA/DoRA/rsLoRA/LoRA-XS/S-LoRA/SHiRA 都是它的变体）；**重参数化**（在原始权重上直接做低秩更新，如 Galore-Plus，把梯度也当低秩矩阵，70B 单卡 48GB 可训）；**前缀式**（Prompt Tuning/Prefix Tuning：冻结全部权重、只训输入侧的虚拟 token，NLG 场景效果弱于 LoRA）；**门控式**（IA3：按维度缩放激活值，参数量最少但效果不稳定）。**选型主线一句话：默认 LoRA；显存紧张上 QLoRA；追求与全量持平的精度上 DoRA；高秩（r>64）上 rsLoRA；极稀疏场景看 S-LoRA/SHiRA**——完整对比在 05 篇。

方法家族的**演进逻辑**值得一句话点透：2025-2026 年的新方法（DoRA/rsLoRA/S-LoRA/DeLoRA…）几乎都在回答同一个问题——**"LoRA 的增量 W = BA 还能怎么优化"**：DoRA 说拆成幅度与方向更好学，rsLoRA 说高秩时缩放公式要改，S-LoRA 说多数参数更新没用不如稀疏化，LoRA-XS 说初始化时就能更省——**"LoRA 是主干，其余是枝杈"**，学会主干后按需摘枝。

## 6. 与 transformers 的关系

**分工**：transformers 管"模型本体"（架构、分词、`from_pretrained` 加载），PEFT 管"适配器"（训练、保存、加载、合并）。**集成层**：transformers v5 内置 `PeftAdapterMixin`（`src/transformers/integrations/peft.py`），所以 `AutoModelForCausalLM.from_pretrained` 加载带 adapter 的目录时**能自动识别 adapter_config.json 并接管加载/合并**——"加载 adapter"这件事，transformers 是入口、PEFT 是引擎（07 篇）。

## 7. 生态位置与五条边界

**生态位置**：PEFT 是 HuggingFace 训练侧的"地基件"——**与 transformers（模型）、datasets（数据）、Trainer（训练循环）组成微调四件套**；它同时是推理侧 adapter 加载的事实标准（vLLM 的 LoRA 动态加载底层也复用它）。**一句话定位**："**全量微调是重工业，PEFT 是精益制造——底座共享、增量分发**"。

**五条边界**：其一，**PEFT 管训练方法，不管训练循环**——优化器调度、梯度累积、日志归 Trainer；其二，**PEFT 不保证效果**——方法只是手段，数据质量决定上限（微调体系讲数据）；其三，**PEFT ≠ 量化**——QLoRA 的 4bit 底座由 bitsandbytes 负责，PEFT 只负责在其上挂 LoRA（08 篇）；其四，**adapter 不是独立模型**——没有底座 W，adapter 一文不值（一致性铁律，07 篇）；其五，**了解 API 即可 ≠ 了解 API 足够**——LoRA 原理（低秩假设）是面试必问，原理看微调体系 02 篇；其六，**PEFT 不负责部署**——合并后的模型交给 vLLM/Ollama，动态加载由 vLLM 的 LoRA 功能承接（07/09 篇）；PEFT 只管"训出来 + 挂上去"，服务化是推理框架的活。
