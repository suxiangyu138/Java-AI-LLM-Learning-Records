## 1. 四操作语义：写入家族全解

| 操作 | 语义 | 已存在的 id | 新 id | 典型场景 |
|------|------|:---:|:---:|---------|
| `add` | 纯新增 | 报错 | 写入 | 首次全量入库 |
| `upsert` | 有则覆盖，无则新增 | 覆盖 | 写入 | 幂等重放/增量刷新 |
| `update` | 只覆盖已存在 | 覆盖 | **静默忽略** | 局部字段修正 |
| `delete` | 删除 | 删除 | 无操作 | 下架/纠错移除 |

**`add` 与 `upsert` 的抉择是写入设计的第一决策**：全量初始化用 `add`（重复 id 报错 = 免费校验，帮你发现脏数据）；任何"可能重跑"的流程用 `upsert`——**"爬虫重跑、管道重放、断点续传，一律 upsert——幂等是写入的铁律"**。`update` 与 `upsert` 的区别要记牢：`update` 对**不存在的 id 不报错也不写入**（静默忽略），容易造成"以为写了其实没写"的事故——**"不确定 id 是否存在，用 upsert 不用 update"**。

**参数形态**：四个操作都接受 `ids` 必填 + `documents/metadatas/embeddings` 可选——**字段按列表按位置对齐**（`ids[0]` 对应 `documents[0]`），列表长度不一致直接报错。只传部分字段的更新（如只改 metadata）没问题，但要小心：**传了 documents 而未传 embeddings 会重新嵌入**（新向量覆盖旧向量），只改 metadata 则向量原样保留——"改文档 = 改向量，改标签 = 不动向量"。

`delete` 两种姿势：`delete(ids=[...])` 精确删；`delete(where={...})` 按条件删（1.5.3 起可配 `limit` 控制删除条数）。**删除不可恢复**，生产上先 `get(where=...)` 验证条件命中集再删（03 篇调试三步同款思路）。

## 2. 批量写入：千条级起步

Chroma 的设计假设是**批量写入**——`add` 一次传入几千条是正常姿势，一次一条才是反模式：

```python
chunk_batch = [
    {"id": f"doc{i}:chunk{j}", "document": text, "metadata": meta}
    for i, doc in enumerate(docs) for j, text in enumerate(chunks(doc))
]
collection.upsert(ids=[c["id"] for c in chunk_batch],
                  documents=[c["document"] for c in chunk_batch],
                  metadatas=[c["metadata"] for c in chunk_batch])
```

**批量三原则**：其一，**几千到几万条一批**是甜点区间（库内部批量向量化 + 批量建索引）；其二，**批量要带嵌入函数的吞吐来配**——API 型嵌入（OpenAI）几千条要分批 + 限速，本地 ONNX 模型则快得多；其三，**大批量分片 + 断点**——"1 万条拆 5 批 × 2000，每批完成记录偏移，重跑用 upsert 兜底"。

**服务器模式并发写入**：1.x Rust 核心支持并发写入（原生异步 SDK），但**并发度不是越大越好**——写入瓶颈在嵌入计算与磁盘，压测找拐点；单进程嵌入式模式下并发写入由进程内锁串行化，**"嵌入式模式别开多线程写，服务器模式再谈并发"**。

## 3. 读取：get 家族

`get` 是"精确读取"通道，与 `query`（相似度检索）分工（06 篇对比）：

```python
data = collection.get(
    ids=["doc1:chunk0"],                 # 按 id 取（可与 where 组合）
    where={"doc_id": "doc1"},            # 按元数据条件取
    where_document={"$contains": "MySQL"},  # 按文档内容取
    include=["documents", "metadatas"],  # 控制返回字段
    limit=100, offset=0,                 # 分页
)
```

**`include` 是性能开关**：默认返回全部字段，只取所需能显著减小响应体（尤其远程服务器模式）——**"调试过滤时 `include=[]` 只看 id 命中集，再决定要不要取全文"**。`count()` 返回集合总数，是健康检查的第一指标。

## 4. 增量更新模式

RAG 数据的现实是**文档会变**：新文档入库、旧文档更新、过期文档删除。三种模式：

**模式一：全量重建**（数据量小/变化频繁）——`delete_collection` 重建 + 全量 upsert。简单粗暴，但**索引重建有成本**，"小库适用，大库别天天全量"。

**模式二：文档级增量**（推荐）——**以文档为单位管理**：metadata 里存 `doc_id`，新文档直接 upsert 新 chunk；文档更新 = 先 `delete(where={"doc_id": "doc_1"})` 再 upsert 新 chunk 集；删除 = 条件删除。**"chunk 是检索单位，文档是管理单位"**——增删改都以 doc_id 为锚。

**模式三：变化检测增量**——外部系统（爬虫/CDC）只推送变化的文档，配合模式二执行——**"谁变了谁进来，没变的别动"**。Chroma 本身不做变更追踪，**幂等 upsert + doc_id 锚定**就是增量体系的核心。

## 5. 备份与迁移

Chroma 的数据 = 本地目录（PersistentClient）/ 服务器数据卷（09 篇）。**备份的通用姿势**（不依赖内部文件格式）：

```python
# 导出：全量 get（分批取）→ 落盘
# 恢复：重建集合（同嵌入函数同配置）→ upsert 回写
```

**迁移与备份三纪律**：其一，**备份带集合配置**（名称/嵌入函数/距离度量）——"光有数据没有配置，恢复出来的集合不是原来的集合"；其二，**大集合分批 get**（limit/offset 分页），避免一次拉爆内存；其三，**恢复后验证**——`count()` 对数量 + 抽样 query 对检索结果——"备份的价值在恢复，恢复的价值在验证"。

## 6. 常见坑

1. **add 重复 id 报错**——初始化之外一律 upsert。
2. **update 以为写了其实没写**——id 不存在时静默忽略；不确定用 upsert。
3. **列表长度不对齐**——ids/documents/metadatas 必须等长，错位报错是保护，别 try 掉。
4. **只改 document 不重新嵌入**——传了 documents 会自动重嵌入，但**手传 embeddings 时必须自己保证新旧一致**。
5. **循环里单条 add**——几千条跑出几分钟；批量一条调用。
6. **批量太大一把梭**——内存与超时风险，分片 + 断点 + upsert 兜底。
7. **删除前不验证 where**——`delete(where=...)` 先 `get(where=...)` 看命中集。
8. **嵌入式模式多线程写**——进程内锁串行化，无收益有风险；并发交给服务器模式。
