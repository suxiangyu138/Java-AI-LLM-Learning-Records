## 1. 实战：端到端 RAG 五段

**场景**：企业知识库问答——把一批 PDF/Word 文档变成可问答的 RAG 服务。五段管道：

```python
# 第一段：文档解析 + 分块（unstructured，08 篇配合）
from unstructured.partition.pdf import partition_pdf
from unstructured.chunking.title import chunk_by_title
elements = partition_pdf("manual.pdf", strategy="hi_res")
chunks = chunk_by_title(elements, max_characters=800, overlap=50)

# 第二段：向量库准备（本体系核心）
import chromadb
client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_or_create_collection(
    name="kb",
    metadata={"hnsw:space": "cosine", "hnsw:construction_ef": 200},
)

# 第三段：批量入库（05 篇批量三原则）
collection.upsert(
    ids=[f"manual:{i}" for i in range(len(chunks))],
    documents=[c.text for c in chunks],
    metadatas=[{"source": "manual.pdf", "page": c.metadata.page_number,
                "doc_id": "manual"} for c in chunks],
)

# 第四段：过滤检索（06 篇）
res = collection.query(
    query_texts=["部署步骤是什么？"],
    n_results=5,
    where={"source": "manual.pdf"},
    where_document={"$not_contains": "勘误"},
)

# 第五段：问答（LLM 消费检索结果）
context = "\n".join(res["documents"][0])
answer = llm.chat(f"基于以下资料回答：\n{context}\n问题：部署步骤是什么？")
```

**验收三问**：其一，**数量对得上**——`count()` 等于 chunks 总数；其二，**检索有区分度**——top-5 里人工判断"相关文档排前面、无关的不混入"；其三，**问答可溯源**——每个回答都能指出基于哪几段（`documents` 回显 + metadata 来源），**"不可溯源的 RAG 是幻觉放大器"**。

**加试：LangChain 对比**——用 `LangChainChroma`（08 篇）替换第四、五段：`as_retriever(filter=...)` + `create_retrieval_chain`——"裸库版与框架版输出一致，证明你既懂底层又懂集成"。

## 2. 生产管道模板与纪律清单

**管道骨架**（可直接套用）：`解析 → 分块 → 批量 upsert（分批 + 断点）→ 检索验证 → 框架集成`。**纪律清单六条**：

1. **嵌入函数建集合时绑定**，换模型 = 克隆重建（04 篇）；
2. **度量第一天定好**——文本场景 cosine（07 篇）；
3. **metadata 字段类型一致**，doc_id 做管理锚点（03/05 篇）；
4. **幂等重放**——全流程 upsert，断点续跑不重复（05 篇）；
5. **检索质量采样验证**——top-50 距离分布定阈值（07 篇）；
6. **生产走服务器模式 + 数据卷 + 内网**（09 篇）。

**管道可观测性三件事**（与 loguru 体系呼应）：入库日志（每批条数/耗时/失败数）、查询日志（QPS/延迟/空结果率）、质量巡检（每周抽样 50 个问题人工标注 top-5 命中率）——**"空结果率突增 = 数据没入进来或过滤写错，先看日志再看代码"**——管道可观测是生产 RAG 与 Demo RAG 的分水岭。

## 3. 报错速查

| 报错 | 根因 | 处理 |
|------|------|------|
| unique constraint violation | add 重复 id | 改 upsert |
| InvalidDimensionException | 向量维度 ≠ 集合维度 | 嵌入函数/模型不一致，重建集合 |
| Metadata type mismatch | 同字段类型混用 | 字段类型全集合一致 |
| "Chroma is not running" | HttpClient 连不上服务器 | 检查容器/端口/heartbeat |
| Collection 不存在 | 集合名写错 | get_or_create_collection 幂等 |
| 数据重启后消失 | 卷没挂/用了 Ephemeral | 挂数据卷（09 篇） |
| 查询结果为空 | where 过严/where_document 大小写 | 先 get 隔离验证过滤 |
| 距离值"不对劲" | 默认 l2/归一化/跨模型比较 | 显式 cosine + 采样看分布 |
| 首次嵌入慢/失败 | 模型文件下载 | 预下载模型或换 API 嵌入 |

## 4. 面试三范式

**范式一：价值式**——"Chroma 是 Python RAG 生态的嵌入式向量数据库，184.8M 下载、1.x Rust 核心重写后 40K+ vectors/s——我用它把检索存储端从零到生产两周落地，原型零部署，1-2M 向量内不需要引入分布式"。

**范式二：技术式**——"它的核心模型是 Collection 五要素（id/embedding/document/metadata/distance），嵌入函数绑定集合保证入库查询一致；查询是'先过滤后排序'——where/where_document 缩小候选，HNSW 相似度排序；度量不可变所以建集合前定 cosine；1.x 元数据 schema 强制"。

**范式三：生产式**——"生产走服务器模式 + Docker 数据卷 + 内网隔离（1.0 无内置鉴权），批量 upsert + doc_id 增量锚定，ef_search 随数据量调，采样定阈值，备份双层（卷快照 + get 导出）；规模超 1-2M 向量按'导出→重建→回灌'迁 Milvus，业务只动 vector store 一层"。

**追问四连**：换嵌入模型怎么办？（克隆集合搬原文）→ 多进程访问？（服务器模式）→ 距离值怎么定阈值？（采样分布）→ 怎么保证不重灌？（幂等 upsert + doc_id）。

**简历呈现写法**：项目段写"基于 Chroma + unstructured 构建企业知识库 RAG 管道：文档解析分块 → 余弦距离 Collection 批量入库 → where/where_document 过滤检索 → LangChain 检索链问答；生产走服务器模式 + Docker 数据卷，1-2M 向量量级检索 p95 约 10ms"——**"技术词 + 数据量 + 架构决策三要素齐全，一段话立住向量库能力"**（与 milvus‑python/unstructured 体系简历写法呼应，按项目规模二选一：中小规模写 Chroma，大规模写 Milvus）。
