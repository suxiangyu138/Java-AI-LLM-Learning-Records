## 1. 嵌入式向量数据库：RAG 的检索存储端

Chroma 的定位一句话：**"嵌入式向量数据库（embedded vector database）——向量 + 元数据 + 文档一起存、一起检索"**。RAG 链路的"向量化 → 检索"环节需要三样东西：**向量索引**（找相似）、**元数据过滤**（按条件缩小范围）、**原文回取**（检索到的是可读文本）——Chroma 把这三样做成一个库，`pip install chromadb` 就能用：

**它和"搜索引擎/数据库"的区别在于形态**：传统数据库你要部署一个服务器进程再连；Chroma 最常用的形态是**嵌入式**——直接 `import chromadb` 在你的 Python 进程里跑，数据落本地磁盘（SQLite + HNSW 索引），**"零部署、零配置、零账号"**。这也决定了它的定位：**做项目必用的 RAG 检索存储端，原型与中小规模生产的一站式选择**。

**核心抽象**：`Collection`（集合）像一张表，每行五要素——`id`（唯一标识）、`embedding`（向量）、`document`（原文）、`metadata`（可过滤的属性字典）、`distance`（相似度度量）——**"写入时五要素一起进库，查询时按向量排序、按元数据过滤、按原文返回"**（03 篇详讲数据模型）。

## 2. 解决什么问题

**问题一：RAG 原型落地太慢**——自己搭 FAISS 要写索引、写持久化、写元数据关联；部署 Milvus 要起分布式集群。Chroma **三行代码**建库入库：

```python
import chromadb
client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_or_create_collection(name="docs", metadata={"hnsw:space": "cosine"})
collection.add(ids=["1"], documents=["这是第一段文档"], metadatas=[{"tag": "产品"}])
```

**"从零到能检索：五分钟，不用装任何服务"**——这是它 184.8M 下载量的根本原因。

**问题二：向量检索和条件过滤要一起做**——真实业务不会只做相似度：要"只在某个分类里找相似"、"排除已删除的"、"按时间范围筛选"。Chroma 的 `where`（元数据过滤）+ `where_document`（文档内容过滤）**一套语法与向量检索天然组合**，`query` 一次调用完成"相似度排序 + 条件过滤 + 原文返回"（06 篇全语法）。

**问题三：嵌入模型选择被锁死**——向量库最怕"嵌入函数换来换去、新旧向量不可比"。Chroma 把嵌入函数做成**集合的持久化配置**（v1.1.13+ 服务端持久化，重新连接自动恢复）：默认内置 all-MiniLM 本地模型免配置，也支持 OpenAI/HuggingFace/自定义——**"集合创建时绑定嵌入函数，之后所有读写自动一致"**（04 篇）。

## 3. 2026 现状与版本基线

**2026-08 基线：1.5.9（2026-05-05 发布）**。2026 年迭代节奏极快：1.5.0（2026-02-09）→ 1.5.1（02-19）→ 1.5.2（02-27）→ 1.5.3（03-07，删除带 limit、移除 Pydantic v1 兼容层支持 Python 3.14）→ 1.5.6（04-07）→ 1.5.9（05-05），**约两周一个小版本，锁版本是必须**。

**1.x 的分水岭是 Rust 核心重写**：v1.0.0（2025-03-01）把索引/存储核心用 Rust 重写——**写入吞吐从约 10K 提升到 40K+ vectors/s（服务器模式），标准查询 p95 延迟约 10ms，整体 4 倍级提升**；同时 Python/TypeScript SDK 原生支持异步，消除了旧的线程限制。伴随的**破坏性变更**（内置鉴权移除、服务端配置改 config.yaml、Docker 数据路径从 /chroma/chroma 移到 /data）让"老教程照搬"成为最大的坑（09 篇专讲）。

**2026 新能力**：GroupBy 聚合（2026-01，结果去重/多样化——"每个 document_id 只留一个 chunk"）、混合检索（稠密 + BM25/SPLADE 稀疏 + RRF 融合）、数组元数据 `$contains` 过滤（1.5.0）、多模态检索（OpenCLIP 图文互检）、Chroma Sync（从 S3/GitHub 自动灌数据）——**"单机库在往'检索能力完整'的方向狂奔"**。

**对学习者的含义**：核心 API（Collection 五要素、add/query）多年稳定，**学一遍用几年**；1.x 的变化集中在性能、检索能力与部署形态——"**版本跟着锁，心智模型不变**"。

## 4. 与替代品对比

| 工具 | 形态 | 强项 | 短板 |
|------|------|------|------|
| Chroma | 嵌入式/单节点 | 零配置、Python 原生、过滤检索一体 | 无分布式、单机内存上限 |
| FAISS | 检索库（非数据库） | 纯检索性能最快、GPU | 持久化/过滤/备份全要自己写 |
| Milvus | 分布式集群 | 亿级规模、GPU 加速、多租户 | 运维复杂（K8s） |
| Qdrant | 独立服务/Rust | 过滤性能最佳、量化压缩 | 需要部署、生态略小 |
| pgvector | PG 扩展 | SQL/ACID/事务一体 | 检索专项能力弱于专用库 |

**选型判断**：**<10 万向量用 Chroma 或 pgvector（简单取胜），10 万-100 万用 Qdrant 或 pgvector，>100 万用 Milvus/Qdrant 集群**——Chroma 官方定位与社区共识是**"1-2M 向量以内的生产 RAG 首选"**，它的短板不是性能而是**分布式能力**：单节点、内存索引、无多租户——**"数据量大了换 Milvus，代码要改的是客户端，心智模型一致"**（09 篇互迁路径）。**vs FAISS 的关键差异**：FAISS 是算法库，检索之外的一切（持久化、过滤、去重、备份）要自己搭——**"Chroma 是数据库，FAISS 是计算内核"**。

## 5. 生态位置与边界

**生态位置**：Chroma 是 **Python RAG 生态的默认检索存储端**——LangChain 的 LangChainChroma、LlamaIndex 的 ChromaVectorStore 都是官方集成件（08 篇）；与 unstructured（文档解析）互补构成"**预处理 → 存储检索**"管道两段；184.8M 下载量说明它早已越过"库"的门槛——**是 RAG 时代的基础设施**。

**边界要划清楚**：其一，**它是单机数据库，不是分布式系统**——多进程/多副本/多租户要服务器模式配合外部治理；其二，**检索质量取决于嵌入质量**——默认模型对中文/领域文本效果有限，"垃圾向量进，相似度出"；其三，**1.x 检索能力全量（Search API/GroupBy）目前在 Chroma Cloud**，本地单节点版本在规划中——本地先吃透 query/where 这套（06 篇）；其四，**它不管数据从哪来**——分块（unstructured）、向量化（04 篇）都是前置环节；其五，**元数据 schema 有约束**——1.x 强制字段类型一致，宽松设计的代价是写入报错（03 篇）。
