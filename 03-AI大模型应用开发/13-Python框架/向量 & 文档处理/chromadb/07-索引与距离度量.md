## 1. 距离度量三选：相似的定义

Chroma 建集合时通过 `metadata={"hnsw:space": ...}` 指定距离度量（**默认 l2**），三选一：

| 度量 | 公式 | 直觉 | 典型场景 |
|------|------|------|---------|
| `l2`（默认） | ∑(Ai−Bi)² | 空间几何距离 | 图像特征/非归一化向量 |
| `cosine` | 1 − cos(θ) | 只比方向不比长短 | **文本嵌入（推荐）** |
| `ip` | 1 − ∑(Ai×Bi) | 方向 + 模长都算 | 推荐系统/评分向量 |

**关键认知：Chroma 返回的是"距离"不是"相似度"**——cosine 度量下返回的是**余弦距离**（= 1 − 余弦相似度），**0 表示最相似**，范围约 [0, 2]；l2 是平方欧氏距离。**"越小越相似"对 l2/cosine 成立**，别把距离值当相似度百分数解读（06 节专讲）。

**选型判断**：文本嵌入模型（OpenAI/bge/miniLM）输出的向量**模长携带长度信息但语义主要靠方向**——所以文本检索的标准答案是 cosine；l2 适合"模长有意义"的场景（图像特征、聚类向量）；ip 适合"方向和大小都重要"的评分/偏好向量。**"不知道选什么：文本 RAG 闭眼 cosine"**。

## 2. 度量选型：文本检索为什么默认 cosine

默认是 l2 是历史包袱：**l2 对"向量长短"敏感**——两个语义相同的文本，如果嵌入函数让"长文本向量模长更大"，l2 会把它们判为不相似，而 cosine 只看方向角、忽略模长。文本嵌入的语义表达主要编码在方向里，所以：

```python
client.get_or_create_collection(
    name="kb",
    metadata={"hnsw:space": "cosine"},   # 文本检索显式配 cosine
)
```

**"建集合时配度量，就像建表时定主键——第一天定死，之后改要付出克隆的代价"**。配了 cosine 后可以放心用余弦距离的语义：`distance < 0.3` 视为高相似、`> 0.8` 视为不相关（阈值随嵌入模型浮动，先采样看分布再定，06 节）。

## 3. HNSW 索引参数全解

Chroma 的向量索引是 **HNSW**（分层可导航小世界图），建集合时可配置的 `hnsw:*` 参数：

| 参数 | 默认 | 作用 | 可后改 |
|------|:---:|------|:---:|
| `hnsw:space` | l2 | 距离度量 | ❌ |
| `hnsw:M`（max_neighbors） | 16 | 节点最大连接数（越大图越密、越准越慢） | ❌ |
| `hnsw:construction_ef` | 100 | 建索引时的候选队列大小（越大质量越好、建库越慢） | ❌ |
| `hnsw:ef_search` | 10 | **查询时**的候选队列大小（越大越准越慢） | ✅（modify） |

**两个 ef 的分工是理解 HNSW 的钥匙**：`construction_ef` 管"建索引的精细度"——一次性成本，建库时大一点（如 200）让图质量更好，**"建库慢一点、检索受益终身"**；`ef_search` 管"每次查询的精细度"——**运行时可调**（`collection.modify(metadata={"hnsw:ef_search": 100})`），"结果不够准就调大 ef_search，这是检索调优的第一个旋钮"。`M` 管图的稠密度，一般默认 16 够用，数据量大且内存宽裕再加大。

**参数与规模的直觉**：候选队列从 10 调到 100，查询延迟增加但召回显著提升——**"ef_search 是准确率与延迟的买卖，用数据验证不用感觉调"**；`sync_threshold`（默认 1000）控制索引刷盘频次，批量写入场景与写吞吐相关。

## 4. 参数不可变与克隆集合

**空间与结构参数（space/M/construction_ef）创建后不可修改**——HNSW 图结构建好后，换度量意味着全图重算。官方文档把"改距离函数"列为**克隆集合**的正当理由：

```python
old = client.get_collection("kb")
data = old.get(include=["documents", "metadatas"])   # 只搬原文与元数据
new = client.create_collection("kb_v2", metadata={"hnsw:space": "cosine", "hnsw:construction_ef": 200})
new.upsert(ids=data["ids"], documents=data["documents"], metadatas=data["metadatas"])
client.delete_collection("kb")
```

**"度量不可变"的设计意图**：保证集合内所有向量在同一度量空间可比——**"报错拒绝你变，好过静默给你不可比的结果"**。所以建集合前的度量决策（02 篇"跑通前想清楚三个配置"）是成本最低的调优——**"克隆能救，但几百 GB 的克隆不便宜——第一天配对最省钱"**。

## 5. 量化与索引生命周期

1.5.0 起集合 schema 支持**启用量化**（quantization）——压缩向量存储（PQ 式），**牺牲少量精度换取内存与磁盘大幅下降**：千万级向量、内存吃紧的场景值得；小集合（十万级）收益不明显，**"先跑通再量化，别开局就压"**。

索引生命周期与写入同频：**写入即建索引**（HNSW 增量插入），`sync_threshold` 控制落盘节奏——"写多读少与读多写少可以有不同的 sync 配置"；删除记录后索引自动维护，**无需手动 rebuild**（对比 FAISS 的"重建索引"心智——"Chroma 把索引维护藏起来了，这是嵌入式库的甜点"）。

## 6. 距离值的正确解读

**第一课：距离 ≠ 相似度百分数**。cosine 距离 0.2 不是"80% 相似"——距离值跨模型不可比（同模型可比）：**阈值判断必须"先采样、看分布、再定界"**：

```python
res = collection.query(query_texts=["典型问题"], n_results=50)
dists = sorted(res["distances"][0])   # 看 50 条的距离分布
# 观察：前 5 条 <0.35，6-20 条 0.35-0.6，其余 >0.6 —— 阈值 0.35 起步，人工验证
```

**第二课：1.x 默认归一化向量**——Chroma 默认对向量做归一化处理（与距离计算配合），个别版本/配置下距离值区间与教科书公式有偏移——**"以实际采样为准，别背公式"**。

**第三课：验证闭环**——"阈值定完必须回测：top-k 里人工标注'准不准'，调 ef_search 与阈值直到达标"——**"检索质量不是配置出来的，是采样验证出来的"**。

## 7. 常见坑

1. **默认 l2 直接跑文本 RAG**——结果"差得没道理"；文本场景显式 cosine。
2. **把距离当相似度**——`distance 0.5` 不是"50% 相似"，跨模型更不可比。
3. **建库后想改 space**——报错；克隆集合是唯一正道。
4. **ef_search 忘了调**——默认 10 偏小，结果不准先调它（可改，成本最低）。
5. **construction_ef 贪大**——建库时间线性涨，10 万向量级 100-200 足够。
6. **不采样就定阈值**——"感觉 0.3 合理"没有依据；先看 50 条距离分布。
7. **小集合就上量化**——收益小、风险早，先跑通。
