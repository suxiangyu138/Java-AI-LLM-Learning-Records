## 1. 部署形态选型

| 形态 | 数据位置 | 适用 | 上线注意 |
|------|---------|------|---------|
| EphemeralClient | 内存 | 测试/Notebook | 绝不用于生产 |
| PersistentClient | 本地目录（SQLite） | 单进程应用/脚本 | **独占锁，多进程事故** |
| HttpClient + Docker 服务器 | 服务器数据卷 | **多进程/Web 服务/生产** | 持久化 + 鉴权 + 内网 |
| CloudClient | Chroma Cloud | 免运维/多区域 | 数据出网合规 |

**选型口诀升级版**：**"脚本用内存，单进程用本地，Web 服务/多进程/生产一律服务器模式"**——FastAPI 默认多 worker 是多进程，每个 worker 各开 PersistentClient 指向同一路径就是事故（02 篇已警示）——**"生产部署的第一步不是写代码，是决定'数据住在哪、谁来连'**"。

## 2. 服务器模式：Docker 部署

```bash
docker run -d \
  -p 8000:8000 \
  -v /data/chroma:/data \          # 数据卷（1.0+ 默认路径 /data）
  --name chroma \
  chromadb/chroma:1.5.9            # 锁镜像 tag

# 健康检查
curl http://localhost:8000/api/v1/heartbeat   # 返回 {} 即存活
```

客户端连接：

```python
client = chromadb.HttpClient(host="localhost", port=8000)
# 或带 SSL：HttpClient(host=..., port=443, ssl=True, settings=...)
```

**生产三件事**：其一，**与应用同网络**（Docker 内网互联），**不要对公网暴露 8000**；其二，**1.0+ 服务器配置走 config.yaml**（`chroma run --config ./config.yaml`），老环境变量（CORS/OTel 等）改由配置文件注入；其三，**资源限额**——容器内存上限按数据量估（1-2M 向量级 2-8GB 量级），别让 Chroma 吃满宿主机。

## 3. 持久化：生产第一纪律

**1.0 重写后"内存模式"被移除**——Rust 服务器**始终写盘**（默认 `/data`），这本来是好事，但带来一个反向陷阱：**不挂数据卷时，重启容器 = 数据清空**（容器文件系统不持久）。

**持久化清单**：其一，**数据卷必须挂载**（`-v` 或 compose volume），**卷与镜像版本一起治理**；其二，**`IS_PERSISTENT` 这类老环境变量在 1.0+ 不再是开关**（始终持久化），照着老教程设反而混淆；其三，**备份靠两层**——服务器数据卷快照（文件级）+ 应用层导出（05 篇 get 全量导出），**"文件快照救急，应用层导出保底"**；其四，**恢复演练**——"备份的价值在恢复，每季度真实演练一次恢复流程"。

## 4. 鉴权与安全

**1.0 重写移除了内置鉴权实现**——这是最大的安全认知更新：老教程里的 `CHROMA_SERVER_AUTHN_PROVIDER` / token 认证环境变量在 1.0+ **可能被静默忽略**，照抄配置等于裸奔。

**2026 生产安全姿势（网络层优先）**：

1. **内网隔离**——Chroma 只监听内网/本机，公网访问一律不允许；
2. **网关鉴权**——应用与 Chroma 之间放 API 网关/反向代理做鉴权（应用的 token/权限在网关层校验）；
3. **网络策略**——K8s 用 NetworkPolicy、Docker 用内部网络，最小互通；
4. **mTLS/加密**——跨主机流量加密（服务网格或应用层 TLS）；
5. **验证不是假设**——部署后从"无鉴权网络位置"实测 curl 是否可达，**"假设有鉴权 vs 验证有鉴权，生产只认后者"**。

Chroma Cloud（CloudClient）侧则用 `X_CHROMA_TOKEN` 等云凭证体系，与自托管两套心智。

## 5. 1.0 Rust 重写：破坏性变更清单

| 变更 | 0.x 心智 | 1.x 现实 |
|------|---------|---------|
| 核心实现 | Python | Rust（4 倍性能） |
| 内置鉴权 | 环境变量启用 | **已移除，走网络层** |
| 服务端配置 | 环境变量 | **config.yaml**（chroma run --config） |
| Docker 数据路径 | /chroma/chroma | **/data** |
| 内存模式 | IS_PERSISTENT=false | **始终写盘** |
| 元数据 | 宽松 | **schema 类型强制** |
| list_collections | 返回名字列表 | 返回 Collection 对象 |

**迁移动作**：锁版本（1.5.x）→ 读官方迁移指南 → 本地/测试环境先跑通 → 再上生产——**"老教程的坑集中在三处：鉴权、配置路径、数据路径"**。

## 6. 性能基线

**官方与社区实测（2026）**：服务器模式写入 **40K+ vectors/s**（0.x 约 10K，Rust 重写 4 倍级提升）、标准查询 **p95 约 10ms**；单机内存占用 **<200MB 起步**（数据量增加后指数增长，约 50 万条后要关注内存水位）；嵌入式单进程模式写入/查询与服务器模式同量级（无网络开销）。

**性能调优顺序（收益递减）**：其一，**批量写入**（05 篇三原则）——单条写入是最慢姿势；其二，**ef_search 匹配数据量**（07 篇）——数据涨了 ef_search 也涨，别默认 10 打天下；其三，**嵌入瓶颈外包**——API 嵌入的吞吐上限远低于库本身，**"嵌入计算才是管道瓶颈，向量库不是"**；其四，**监控三件套**——`count()` 数据量、查询延迟、内存水位，进日志与告警。

## 7. 规模边界与升级路径

**Chroma 的规模边界：单机 1-2M 向量**（社区 2026 对比文章共识）——再大时内存压力与单点风险上升。**升级路径**（保留心智模型的迁移）：

1. **数据导出**：`get()` 分页全量导出（含 documents/metadatas）；
2. **目标库建集合**：同嵌入函数、同度量（Milvus/Qdrant 的集合配置对齐）；
3. **批量回灌**：目标库 SDK 批量 upsert；
4. **检索层切换**：框架集成件换一个（LangChain 的 Milvus/Qdrant vector store 类）——**"业务代码里只有 vector store 这一个抽象，换库换一行"**。

**"Chroma 教你学会了向量库该有的心智（集合/嵌入/过滤/距离），升级时带着这套心智走，库只是实现"**——这正是本体系与 milvus‑python（`../../强烈推荐%EF%BC%88做项目必用%EF%BC%8C简历加分%EF%BC%89/milvus‑python/00-milvus‑python总览.md`）衔接的接口。

## 8. 常见坑

1. **不挂卷跑 Docker**——重启即清空，"数据哪去了"是生产第一事故。
2. **照抄 0.x 鉴权配置**——1.0+ 可能静默忽略，生产裸奔。
3. **公网暴露 8000**——无鉴权向量库对全互联网可写，**任何人不挂卷 + 任何人可写 = 双重灾难**。
4. **多 worker 共用一个本地目录**——独占锁，索引损坏。
5. **老环境变量当开关用**——配置迁移看迁移指南，别信旧博客。
6. **单条循环写入上生产**——吞吐差一个数量级。
7. **数据量涨了 ef_search 不变**——召回率悄悄下降，监控 + 采样验证（07 篇）。
8. **不演练恢复**——"有备份"不等于"能恢复"。
