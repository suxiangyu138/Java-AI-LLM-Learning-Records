## 1. Collection 五要素

Collection 是 Chroma 唯一的数据结构，**一行记录 = 五个字段**，理解这五字段就是理解 Chroma 的模型：

| 字段 | 类型 | 必填 | 作用 |
|------|------|:---:|------|
| `id` | str | ✅ | 唯一标识，写入去重/更新/删除的锚点 |
| `embedding` | List[float] | ✅* | 向量，相似度计算的载体（*与 document 二选一） |
| `document` | str | ❌ | 原文，检索直接返回、可被 where_document 过滤 |
| `metadata` | dict | ❌ | 可过滤的属性字典（where 的过滤对象） |
| `distance` | float | 计算 | 查询结果携带的相似度距离（越小越相似） |

**为什么五要素一起存**：传统向量库（如 FAISS）只管"向量 → id"映射，拿到 id 后还要回业务库查原文——两步走且过滤能力薄弱。Chroma 的模型是**"文档检索的一站式记录"**：写入时 embedding 由嵌入函数从 document 自动算出，metadata 随行存储；查询时一次返回"最相似的原文 + 它的属性 + 距离"——**"RAG 问答链的输入（原文）与过滤条件（metadata）都在同一行里"**，这是它数据模型的灵魂。

**嵌入与原文的关系**：`documents` 与 `embeddings` 传入时二选一即可——给 documents，嵌入函数自动算；给 embeddings，跳过嵌入函数直接用（自定义向量/图像向量场景）。但**两者不同时给会少一边**：只给 embeddings 的记录没有 document，检索回来只有向量没有原文；只给 documents 则自动补全向量——**"RAG 场景永远给 documents，让嵌入一致性由库保证"**。

## 2. 元数据：可过滤的标签层

metadata 是一个 dict，**key 是字符串，value 支持 str/int/float/bool 四类标量（1.5.0+ 支持数组）**。它是 Chroma 过滤能力的来源：`where` 条件直接作用于 metadata 字段（06 篇语法全解）。

**1.x 的 schema 强制（重要）**：同一个 metadata key 在**所有记录里必须类型一致**——`{"tag": "a"}` 和 `{"tag": 1}` 混在同一集合会写入报错。这是 1.0 Rust 重写引入的严格化：**"元数据像数据库的列，第一行写入就定了类型"**。设计含义：字段要么全字符串、要么全数字，**枚举类字段（标签/分类）固定用字符串**，数值类（价格/时间戳）固定用数字。

**过滤是元数据存在的唯一意义**：检索时 `where={"tag": "键盘"}` 先按条件过滤、再在剩余记录中做相似度排序——**"元数据是检索的闸门，不是备注栏"**。所以设计时问自己："这个字段未来会不会出现在 where 条件里？"——会，就放 metadata；不会，就塞进 document 或干脆不放。

## 3. ID：写入去重与更新锚点

ID 是字符串，**集合内唯一**，承担三个职责：

- **去重锚点**：`add` 重复 ID 报错，`upsert` 重复 ID 覆盖——"ID 决定写入语义"（05 篇）。
- **更新锚点**：`update(ids=[...], documents=[...])` 只更新文档不更新嵌入是危险姿势——**改了 document 必须连带改 embedding**，否则旧向量配新文本（05 篇专门讲）。
- **删除锚点**：`delete(ids=[...])` 精确删除；`delete(where=...)` 按条件删。

**ID 设计三规范**：其一，**用业务稳定标识**（如 `doc_123`、`chunk_456`）——增量更新时"同一 chunk 更新不新增"靠它保证；其二，**命名带前缀**（`kb:chunk:123` 风格）避免跨集合/跨库冲突；其三，**不要用自增数字**——向量库没有 auto_increment，且自增 ID 无法表达业务含义。

## 4. 数据模型设计四问

建集合前问四个问题，答案就是数据模型：

1. **主键是什么？**——"一条记录对应一个 chunk 还是一个文档？"RAG 常见做法：一个文档切成多个 chunk，ID 用 `doc_id + chunk_index`，metadata 里同时存 `doc_id`（GroupBy 去重按它做，01 篇提到的新能力）。
2. **向量怎么来？**——用默认 ONNX 还是 OpenAI/领域模型？**模型一旦定下，集合内所有向量必须同一模型同一维度**（换模型 = 重建集合，04 篇）。
3. **哪些字段要过滤？**——分类、时间、来源、权限……这些进 metadata 并保持类型一致；**"过滤字段越多，检索越精准，但写入约束越多"**。
4. **要不要原文？**——RAG 必存 document；只做相似度匹配（如推荐系统）可以只存 embedding + metadata。

**示例：知识库集合设计**：

```python
collection = client.create_collection(
    name="kb_chunks",
    metadata={"hnsw:space": "cosine"},
)
# 每行：id="doc_1:chunk_3" document="原文片段"
# metadata={"doc_id": "doc_1", "source": "pdf", "lang": "zh", "seq": 3}
```

## 5. 与关系型数据库思维对比

**相同处**：Collection 像表、id 像主键、metadata 像列、where 像 WHERE——**"写 SQL 的人上手很快"**。

**关键差异**：其一，**没有 join**——Chroma 是文档型，需要关联的数据（如文档与其作者详情）要在写入前摊平进 metadata；其二，**查询模式是"排序 + 过滤"不是"过滤 + 投影"**——`query` 永远做相似度排序，`where` 只是先缩小候选集；其三，**没有事务/外键**——批量写入要么全成功要么部分成功，靠 upsert 幂等重放兜底；其四，**schema 是隐式的**——不像建表语句显式声明，而是由第一批写入的记录决定（1.x 的类型强制是其补丁）——**"隐式 schema 更需要纪律：第一行写入前想好全部字段与类型"**。

## 6. 常见坑

1. **metadata 类型混用**——"第一行 tag 是字符串，后面写数字"→ 写入报错；字段类型全集合一致。
2. **只给 embeddings 不给 documents**——检索结果没有原文，RAG 问答无米下锅。
3. **update 只改 document 不改 embedding**——文本与向量失配，检索结果诡异（05 篇正确姿势）。
4. **ID 用自增/随机**——增量更新无法定位旧记录，重复入库越积越多。
5. **把大文本塞进 metadata**——metadata 是过滤层不是内容层，长文本进 document。
6. **忽略 distance 语义**——l2/cosine/ip 的距离方向不同（07 篇），"越小越相似"只对 l2/cosine 成立。
7. **一个集合混多个嵌入模型**——维度不一致直接报 InvalidDimensionException，换模型必须重建集合。
