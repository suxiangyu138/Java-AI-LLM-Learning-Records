## 1. 裸索引的 ID：行号不是业务 ID

IndexFlatL2 这类顺序索引的"ID"是**添加顺序的行号**——第一条 add 的是 0，第二条是 1……`search` 返回的 `I` 就是这个行号。三个现实问题：

**其一，无法对应业务**——行号 4312 是"哪篇文档的哪段"？不知道——**"FAISS 只管'行号'，'行号是什么'要你自己维护"**；**其二，删除会移位**——顺序索引 remove 一条后，**它后面的所有行号集体前移**，你记录的 ID 全部失效；**其三，无法按业务查询**——"查 id=doc_5 的所有向量"在裸索引上不存在。

**结论**：**"把 FAISS 当数据库用的第一件事，就是给它装业务 ID——IDMap 就是这件外套"**。

## 2. IndexIDMap：业务 ID 的第一件外套

```python
base = faiss.IndexFlatL2(d)                       # 任何底层索引
index = faiss.IndexIDMap(base)                    # 包一层 ID 映射
ids = np.array([1001, 1002, 1003], dtype='int64') # 业务 ID（必须 int64！）
index.add_with_ids(vectors, ids)                  # 铁律：IDMap 上必须 add_with_ids
D, I = index.search(queries, k)                   # I 现在返回业务 ID
```

**三条铁律**：其一，**包了 IDMap 后只能 `add_with_ids`**——普通 `add` 直接报错（保护）；其二，**ID 必须是 int64 数组**（`dtype='int64'`），字符串 ID 要先映射成 int64；其三，**ID 唯一**——重复 ID 的 add 是污染（先 remove 再 add，见下节）。

**IndexIDMap2 是升级版**：带**反向索引**（ID → 向量位置），支持 `reconstruct(key)` 按业务 ID 还原向量——"**需要按 ID 还原/删除的场景用 IDMap2 不用 IDMap**"。**注意**：IVF 系索引**原生支持 add_with_ids**，不必再包 IDMap（05 篇已述）——"**Flat/HNSW 系包 IDMap，IVF 系自带**"。

## 3. 删除与更新：remove_ids 的正确姿势

**删除**——`remove_ids` 是 FAISS 的唯一删除入口：

```python
import numpy as np
index.remove_ids(np.array([1002], dtype='int64'))        # 按业务 ID 删
# 或选择器对象：
index.remove_ids(faiss.IDSelectorBatch(np.array([1001], dtype='int64')))
print(index.ntotal)                                       # 删完查总量确认
```

**删除语义因索引而异（关键差异）**：**顺序索引（Flat/PQ/LSH）删除后行号集体移位**——"删一条，后面全变号"；**IVF 与 IDMap2 显式存 ID，删除不影响其他 ID**——"**要频繁删除，选 IDMap2/IVF，否则你的 ID 会悄悄漂移**"。

**更新 = 先删后加**——FAISS 没有 update 方法，**直接 add 同 ID 新向量 = 重复记录污染结果**：

```python
index.remove_ids(np.array([1002], dtype='int64'))   # ① 删旧
index.add_with_ids(new_vector_1002, np.array([1002], dtype='int64'))  # ② 加新
```

**"FAISS 的 update 语义是你自己写的：remove + add_with_ids，顺序不能反"**——这是 FAISS"算法库"属性最典型的体现（Chroma 一条 upsert 搞定，FAISS 两条 API 自理）。

## 4. reconstruct：还原向量

`reconstruct(i)` 按**行号**还原向量；IDMap2 上按**业务 ID**还原：

```python
vec = index.reconstruct(0)          # 行号 0 的原始向量（float32, (d,)）
# IDMap2：按业务 ID
vec2 = index.reconstruct(1002)      # ID=1002 的向量
```

**三个用途**：其一，**调试**——"库里存的到底是不是预期的向量"（02 篇冒烟三步）；其二，**导出迁移**——全量 reconstruct 导出向量做备份/迁移（配合 09 篇）；其三，**内容回取**——FAISS 不存原文，reconstruct 拿到向量后你要用**自己的 ID→原文映射**回查文本——"**FAISS 只还原向量，向量背后的业务数据在你自己手里**"。

**批量还原**：循环单条 reconstruct 是慢姿势——按块取 `index.reconstruct_n(i0, n)` 一次还原连续 n 条（IDMap2 上配合 ID 列表对位）；导出 100 万条用块式还原 + 分批落盘，"**能块取就别单取，与批量检索同一条性能纪律**"。

## 5. 持久化：write/read 与数据库外围

**索引本身落盘**（一行命令）：

```python
faiss.write_index(index, "kb.index")     # 序列化整个索引（含训练结构）
loaded = faiss.read_index("kb.index")    # 加载即用（含 IDMap/IVF 簇结构）
```

**但"索引文件"不是"数据库"**——FAISS 的持久化边界到此为止，**数据库外围（元数据/原文/增量状态）要自己搭**。生产最小方案：

```python
# 三件套：索引文件 + 元数据表 + ID 映射
faiss.write_index(index, "kb.index")          # ① 向量检索结构
np.save("kb_ids.npy", ids)                    # ② ID 数组（int64）
# ③ 业务元数据（原文/标签）——JSON/DB/parquet 任选，键 = 业务 ID
# 恢复流程：read_index + 读 ID 数组 + 读元数据 → 三件对上即恢复
```

**持久化四纪律**：其一，**备份三件套一起备份**——只备份索引文件 = 备份了一串无意义行号；其二，**写前考虑版本**——索引文件格式与 FAISS 版本相关，升级前先导出数据再重建；其三，**增量靠 ID 幂等**——重跑管道用 remove+add 保证不重复（与 Chroma upsert 心智同源）；其四，**恢复后验证**——`ntotal` 对数量 + 抽样 search 对结果——"**备份的价值在恢复，恢复的价值在验证**"（chromadb 05 篇同款纪律）。

**增量更新姿势**：新文档入库 = 新 ID 直接 `add_with_ids`（HNSW 图增量友好，无需重建）；文档更新 = 先 remove 旧 ID 再 add 新向量；**重跑管道 = 全量 remove_ids（用 ID 选择器按批删）再重灌**——"**增量与重跑全靠 ID 纪律：ID 稳定、先删后加、幂等可重放**"——这与 chromadb 的 doc_id 锚定心智完全同源，换库不换思想。

## 6. 常见坑

1. **IDMap 上用 add**——报错；IDMap 必须 add_with_ids。
2. **ID 用 int32/字符串**——必须 int64；字符串 ID 先建映射表。
3. **重复 ID 直接 add**——不报错！两条同 ID 向量共存，污染检索结果。
4. **顺序索引上删一条**——行号集体移位，你记的 ID 全废；删除频繁用 IDMap2/IVF。
5. **update 直接 add 同 ID**——重复记录；先 remove 再 add。
6. **只备份索引文件**——没有 ID 与元数据 = 不可恢复；三件套。
7. **跨版本读索引**——大版本升级读旧索引可能失败；升级前导出数据。
