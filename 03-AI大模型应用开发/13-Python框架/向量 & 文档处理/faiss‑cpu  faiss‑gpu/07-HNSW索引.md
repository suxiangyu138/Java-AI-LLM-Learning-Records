## 1. 图索引思想：从粗到细的导航

HNSW（Hierarchical Navigable Small World，分层可导航小世界）的思想一句话：**"把向量组织成多层图，从'最粗的一层'开始导航，逐层细化逼近最近邻"**——

- **底层**：每个向量连到附近 M 个邻居（精细的"小世界"图，所有点都在）；
- **上层**：随机抽取部分向量组成的稀疏图（粗略导航层）；
- **查询**：从最高层（最稀疏）进入，沿边走向"更像查询"的节点，**逐层下钻**，每层贪心前进——"**先在大地图上找到城市，再在城市里找街道，最后在街道里找人**"。

**为什么又快又准**：导航路径长度是**对数级**（与图高度相关），而每一跳都朝着查询方向走——"**不像 IVF 那样先粗筛再全扫桶内，HNSW 是边走边修正方向，天然少走弯路**"；召回率典型 **~99%**，是近似索引里质量最高的一族。

## 2. IndexHNSWFlat：零训练直接 add

```python
M = 32                        # 每个节点最大连接数
index = faiss.IndexHNSWFlat(d, M)
index.add(vectors)            # 零训练！直接入库（边在建库时动态生成）
index.hnsw.ef_search = 64     # 查询候选队列（可随时改）
D, I = index.search(queries, k)
```

**与 IVF 的关键差异**：**无需 train**——图结构是增量构建的（每 add 一条向量动态连边），不像 IVF 要先学簇中心——"**建库 = 一个 add 循环，这是 HNSW 上手快的原因**"；也因此**增量添加天然友好**（不断 add 新向量图自动生长），而 IVF 的簇是固定的（新数据分布变了要重训）。

**M 的语义**：每个节点连多少条边——**M 越大图越密、导航路径越短、检索越准，但构建与内存开销越大**；**"M=32 是默认好配方，16 更省、64 更准"**。

## 3. 两个旋钮：efConstruction 与 efSearch

| 参数 | 作用 | 默认 | 阶段 |
|------|------|:---:|------|
| `efConstruction` | 建图时每节点的候选队列大小 | 40 | 构建（一次性） |
| `efSearch` | 查询时候选队列大小 | 16 | 查询（随时改） |

```python
index.hnsw.ef_construction = 200   # 建图前设：越大图质量越高、建库越慢
index.add(vectors)                 # 设了再 add
index.hnsw.ef_search = 64          # 查询前设：越大召回越高、查询越慢
D, I = index.search(queries, k)
```

**两个 ef 的分工是 HNSW 的钥匙**：**efConstruction 管"建图质量"**——一次性成本，建库时加大（200 起）让边连得更优，"建库慢一点、检索受益终身"；**efSearch 管"当次查询精度"**——运行时可改，**"结果不够准先加 efSearch，这是 HNSW 的第一个旋钮"**。两者都大 → 逼近精确检索。

**与 IVF 的对应**：efConstruction ≈ nlist（建库粒度），efSearch ≈ nprobe（查询旋钮）——**"每个近似索引都有'建库旋钮'与'查询旋钮'，理解一组就能理解全部"**（03 篇两轴心智）。

## 4. 构建慢、检索快：时间账本

**HNSW 的代价在构建**：建图是**单线程串行**的（每 add 一条要查候选队列、更新边）——**100M+ 向量建库可能数小时**；而检索是**图导航**，延迟最低——"**构建慢、检索快**"是 HNSW 的固有特征。

**内存账单**：图结构本身吃内存——**每条向量约 M × 2 × 4 字节的边开销**（M=32 时约 256 B/条，加上向量本身 1536 B/条 ≈ 1.8KB/条）——"**HNSW 的内存 = 向量 + 图边，是索引家族里最重的；内存不够时的答案是 PQ（06 篇）**"。

**对策**：建库慢 → 分块并行建索引再合并（`index.merge_from`）或分片部署（09 篇）；内存重 → 换 HNSWPQ（图 + 量化组合）或直接 IVFPQ——"**HNSW 是质量之王，但它是'贵'的索引：时间贵在建库，空间贵在图边**"。

**量化数字**：100 万条 384 维向量，HNSW(M=32) 的内存 ≈ 1.5GB（向量）+ 0.25GB（图边）≈ 1.8GB，建库约几分钟；对比 Flat 的 1.5GB——"**图边让 HNSW 比 Flat 多约 1/6 内存，换来的是 100 万条上检索从全扫变为图导航**"。


**决策节奏**：efConstruction 定 200（建库质量上限）→ efSearch 扫描 16/64/256 → **取"召回 ≥ 目标（如 98%）的最小 efSearch"**——"**efSearch 不是越大越好，是'达标最小'——多出来的候选队列全是延迟**"。

**调参记录进生产配置**：`M/efConstruction/efSearch` 三个数字与数据量、召回率、p95 一起写进部署文档——"**参数是决策结果不是魔法数字，配着验证数据记录才有复现价值**"（09 篇压测方法同源）。

## 6. 常见坑

1. **efSearch 默认 16 忘调**——召回不达标；先加 efSearch（成本最低）。
2. **efConstruction 调在 add 之后**——无效！它只影响建图，必须 add 前设置。
3. **M 贪大**——M=64 更准但内存与建库时间双涨；默认 32 起步测了再说。
4. **拿 HNSW 当"构建也快"的索引**——构建单线程串行，100M 级数小时；建库预算先算。
5. **内存预算漏算图边**——每条约 M×8 字节额外开销，账单先算（09 篇）。
6. **批量增量 add 不合并**——大批量 add 前先 efConstruction，add 完再调 efSearch 查询。
7. **与 IVF 参数混记**——nlist/nprobe 是 IVF 的，efConstruction/efSearch 是 HNSW 的；两套旋钮别串。
