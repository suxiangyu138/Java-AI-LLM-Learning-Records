## 1. 性能优化阶梯：收益递减的顺序

FAISS 调优有明确的**优先级顺序**，别跳过前面的去折腾后面的：

1. **批量检索**——单查变批量，吞吐差一个数量级（04 篇）；
2. **索引选型**——Flat 换 HNSW/IVF，召回-延迟换空间（03-07 篇）；
3. **查询旋钮**——nprobe/efSearch 达标最小化（05/07 篇）；
4. **线程与内存布局**——本片主题；
5. **降维**——PCA 减维，延迟与内存同降；
6. **GPU**——最后一张牌（本片后半）。

**"调优顺序 = 先改姿势（批量/索引），再拧旋钮（nprobe/ef），最后加资源（线程/GPU）"**——每步都要压测验证（05 篇闭环方法），**"感觉变快了不算数，p95 数字说话"**。

## 2. 批量检索与线程

**批量是第一收益**：`search((Q, d))` 一次调用，底层 SIMD 与多线程按批量摊薄——100 个查询一次算 vs 100 次单查，**差一个数量级**——"能批量就批量，这排在调优榜第一位"。

**线程数**：FAISS 的 CPU 实现（BLAS）默认用满所有核；单次查询延迟敏感场景反而**限制线程**（`faiss.cpu.omp_set_num_threads(4)`）避免多线程调度开销——"**吞吐场景多线程，延迟敏感场景少线程，压测找拐点**"。**Python 侧注意**：`search` 调用会**释放 GIL**（底层 C++ 计算），多线程 Python 程序里 FAISS 检索本身不吃 GIL——"**FAISS 的并发瓶颈在内存带宽，不在 GIL**"。

## 3. 内存治理

**第一步：确认 float32**——`astype('float32')` 一遍（02 篇铁律），float64 内存直接翻倍。

**第二步：算账**——`条数 × 每向量字节数`（Flat 384 维 = 1536B/条；HNSW 再加 M×8B 图边；PQ 后每条约 d/m × nbits/8 B）——"**先算账后开工**"（06 篇账本）。

**第三步：降维**——PCA 从 384 维降到 128/64 维：`faiss.index_factory(d, "PCA128,IVF100,PQ8")`——"**降维是延迟与内存的双降，代价是信息损失**"；先测降维后召回再决定。

**第四步：实测**——`resource.getrusage(resource.RUSAGE_SELF).ru_maxrss` 打点，与账本对照——"**账本估算，实测校准**"。

## 4. GPU 渠道现状：PyPI 停更的真相

**PyPI 的 `faiss-gpu` 包已停更**——卡在 1.7.x（2023 年），仅支持 Python ≤3.10，官方明确"PyPI faiss-gpu 不受支持"（GitHub Issue #3617）。**2026 的正确安装姿势**：

| 渠道 | 命令 | 适用 |
|------|------|------|
| conda（官方推荐） | `conda install faiss-gpu -c pytorch` 或 `-c conda-forge` | 有 conda 的环境 |
| 社区轮子 | `pip install faiss-gpu-cu12`（CUDA 12.x）或 `faiss-gpu-cu11` | 纯 pip 环境 |
| 官方 faiss-cpu | `pip install faiss-cpu` | 只需 CPU（大多数场景） |

**社区轮子注意**：基于 kyamagu/faiss-wheels，支持 CUDA 12.1/11.8、Python 3.8+、Linux x86_64、GPU 架构 Volta-Ada（7.0-8.9，**不含 Hopper/Blackwell**）；仍需 NVIDIA 驱动——"**pip 用户先试 cu12 轮子，踩坑再转 conda**"。

**选渠道的决策**：**有 conda（数据科学环境常态）→ 官方 conda-forge/pytorch 通道**（版本最新、CUDA 依赖自动解析）；**纯 pip 环境（微服务/容器）→ faiss-gpu-cu12**（对应你的 CUDA 驱动版本）；**无 GPU/小数据 → faiss-cpu 即可**（绝大多数项目用不到 GPU 版）——"**渠道选择 = 环境形态 × 数据规模，先问自己要不要 GPU，再谈怎么装**"。

**"2026 年第一大 FAISS 坑：照老教程 `pip install faiss-gpu` 装上 1.7.x 旧版，或者干脆装不上——渠道与版本一起锁"**。

## 5. GPU 桥接代码

安装对的前提下，代码桥接非常简单——**索引在 CPU/GPU 间零成本转换**：

```python
res = faiss.StandardGpuResources()              # GPU 资源池（创建一次复用）
index_gpu = faiss.index_cpu_to_gpu(res, 0, index_cpu)   # CPU 索引 → GPU（单卡）
index_gpu2 = faiss.index_cpu_to_all_gpus(index_cpu)     # 多卡分片（自动切分）
index_back = faiss.index_gpu_to_cpu(index_gpu)          # 转回 CPU（落盘前）
```

**三条纪律**：其一，**建库在 GPU 上做**（train/add 的耗时大头在 GPU 上秒级完成），**落盘前转回 CPU**（write_index 写 CPU 索引）；其二，**GPU 资源对象复用**——`StandardGpuResources` 创建开销大，进程内建一次；其三，**IVF/PQ 在 GPU 上另有实现**（GpuIndexIVFFlat 等），桥接函数自动选择——"**接口不变，硬件换引擎**"。

## 6. 何时上 GPU

**GPU 不是默认答案**，是**数据量压出 CPU 上限后**的选择：

**上 GPU 的信号**：其一，**百万级向量 + 延迟要求 <5ms**；其二，**批量检索吞吐瓶颈**（CPU 核用满、p95 仍超标）；其三，**建库太慢**（HNSW 建库数小时 → GPU 分钟级）。

**不上 GPU 的信号**：其一，**10 万条以内**——CPU 毫秒级，GPU 传输开销反而亏；其二，**延迟敏感单查**——GPU 的 PCIe 传输 + 启动开销可能比 CPU 直接算还慢；其三，**没有 CUDA 运维能力**——驱动/显存/多卡管理是新的运维面——"**先压测 CPU 上限，压不破别上卡；压破了，GPU 桥接只要三行**"。

**混合部署的常见姿势**：**建库（train/add）上 GPU、查询留在 CPU**——建库是算力密集的离线任务（GPU 分钟级 vs CPU 小时级），查询是延迟敏感的在线任务（CPU 图导航已够快）——"**GPU 干重活（建索引），CPU 干快活（查索引），各得其所**"；批量查询/离线评估再切 GPU——"**先想清负载形态，再分配硬件**"。

## 7. 常见坑

1. **pip install faiss-gpu**——停更包，装上也是 1.7.x；conda/cu12 轮子才是正道。
2. **单条循环查询**——性能第一杀手；批量检索一次算。
3. **线程默认拉满**——延迟敏感场景反而慢；`omp_set_num_threads` 限核压测。
4. **内存不算账**——float64/漏算 HNSW 图边；账本 + 实测。
5. **GPU 索引直接 write_index**——先 `index_gpu_to_cpu` 再落盘。
6. **显存不够硬上 GPU**——IVFPQ 在 GPU 上同样适用（显存 = 新内存账本）。
7. **不压测就调优**——"感觉快"不算数；p95/召回率两个数字。
