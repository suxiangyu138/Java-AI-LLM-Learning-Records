## 1. 实战：RAG 检索端 FAISS 方案

**场景**：文档问答系统，检索端用 FAISS（对比 chromadb 方案的"内核派"）。六段管道：

```python
import faiss, numpy as np

# 第一段：向量化（嵌入模型输出，如 384 维）
vectors = np.array([embed(t) for t in chunk_texts]).astype('float32')
faiss.normalize_L2(vectors)                        # 归一化（cosine 前置）

# 第二段：建索引（HNSW 质量优先 + IDMap 装业务 ID）
base = faiss.IndexHNSWFlat(d, 32)
base.hnsw.ef_construction = 200                    # 建图质量旋钮
index = faiss.IndexIDMap2(base)                    # IDMap2：可还原可删除
ids = np.arange(len(chunk_texts), dtype='int64')   # 业务 ID
index.add_with_ids(vectors, ids)

# 第三段：持久化三件套
faiss.write_index(index, "kb.index")
np.save("kb_ids.npy", ids)
# 元数据表：{id: {"doc_id":..., "page":..., "text":...}} —— 自己维护（08 篇）

# 第四段：检索
faiss.normalize_L2(queries)                        # 查询同样归一化
index.hnsw.ef_search = 64                          # 查询旋钮
D, I = index.search(queries, k=5)                  # I 是业务 ID

# 第五段：元数据回查（FAISS 不存原文，自己查）
results = [[meta_db[i] for i in row if i != -1] for row in I]
context = "\n".join(r["text"] for r in results[0])

# 第六段：问答（LLM 消费 context）
answer = llm.chat(f"基于以下资料回答：\n{context}\n问题：{question}")
```

**验收三问**：其一，**数量对得上**——`ntotal` 等于分块总数；其二，**检索有区分度**——自查冒烟（查询在库中应命中自身）+ top-5 人工抽检；其三，**结果可溯源**——`I` 是业务 ID，能回查到原文与来源（metadata 表）——"**不可溯源的检索端是幻觉放大器**"。

**加试：与 Chroma 对比**——同数据用 chromadb（`../chromadb/00-chromadb总览.md`）方案实现一遍——"FAISS 版多写了 IDMap/元数据/持久化三件外围，换来的是索引内核的完全控制——**两种方案，一种心智：检索质量取决于嵌入与索引选型，不取决于壳**"。

## 2. 生产模板与纪律清单

**骨架**：`向量化（float32+归一化）→ 索引选型（HNSW/IVF/PQ）→ IDMap 装 ID → write_index 落盘 → 查询归一化 → 元数据回查`。**纪律清单六条**：

1. **float32 + 归一化双前置**——进库前 astype、cosine 场景入库查询各归一化一次（02/04 篇）；
2. **索引选型先定架构**——10 万内 Flat、以上 HNSW/IVF、内存受限 PQ，选型表先跑（03 篇）；
3. **train 纪律**——IVF/PQ 先 train 后 add，训练集同分布、子集即可（05/06 篇）；
4. **ID 与元数据三件套**——IDMap int64 + 索引文件 + 元数据表一起备份（08 篇）；
5. **更新先删后加**——remove + add_with_ids，重跑幂等（08 篇）；
6. **压测验证**——Flat 基准测召回、p95 测延迟，参数"达标最小"（05/07/09 篇）。

## 3. 报错速查

| 报错 | 根因 | 处理 |
|------|------|------|
| dtype 不匹配 | float64 传入 | astype('float32') |
| dimension 不匹配 | 向量维度 ≠ 索引维度 | 对齐嵌入模型输出维度 |
| "add not supported" | IDMap 上用了 add | 改 add_with_ids |
| 检索结果全 -1 | k > ntotal | min(k, ntotal) |
| IVF 结果垃圾 | 忘 train/先 add 后 train | 重训重建（05 篇） |
| 归一化后结果不对 | 只归一化入库没归一化查询 | 两次都做（04 篇） |
| 行号漂移 | 顺序索引删除导致 | IDMap2/IVF（08 篇） |
| 索引文件读不了 | 跨版本/文件损坏 | 数据导出重建（08 篇） |
| pip 装 faiss-gpu 失败 | PyPI 包停更 | conda / faiss-gpu-cu12（09 篇） |
| GPU 桥接报错 | 驱动/显存/架构不支持 | 查驱动、换轮子、回 CPU（09 篇） |

## 4. 面试三范式

**范式一：价值式**——"FAISS 是 Meta 开源的相似度检索算法库，PyPI 周下载 350 万——我用它做 RAG 检索端：HNSW+IDMap 索引 10 万级文档、检索 p95 毫秒级，比数据库方案内存省一半、延迟低一个量级——代价是自己搭持久化与元数据"。

**范式二：技术式**——"它的核心是索引家族：Flat 精确全扫、IVF 倒排分簇（nlist/nprobe）、PQ 乘积量化压缩（1536B→96B/条）、HNSW 分层图（efConstruction/efSearch）；余弦没有专属类，标准姿势是 L2 归一化 + IP；IDMap 装业务 ID、remove+add 实现更新——我理解每个索引的时间-精度-内存三角"。

**范式三：生产式**——"生产方案：float32 铁律 + 归一化双前置 + HNSW 质量优先 + IDMap2 支持删除还原 + 三件套备份（索引/ID/元数据）+ Flat 基准测召回、p95 测延迟调 nprobe/efSearch；GPU 是最后一张牌，数据量压破 CPU 上限才上，conda 渠道装（PyPI faiss-gpu 已停更）"。

**追问四连**：十万条用什么索引？（Flat，别过度设计）→ 百万条精度优先？（HNSW，efSearch 达标最小）→ 内存不够？（PQ，先算账本再定 m）→ 怎么验证？（Flat 基准召回率 + p95）。

**简历呈现写法**：项目段写"基于 FAISS + HuggingFace 嵌入构建检索服务：HNSW+IDMap 索引百万级向量、PQ 量化压缩内存 60%、Flat 基准验证召回 98%、检索 p95 8ms；自建持久化与元数据回查体系"——"**内核级词汇（HNSW/PQ/召回率）+ 量化数据 + 外围搭建能力三要素，一段话立住向量检索深度**"。
