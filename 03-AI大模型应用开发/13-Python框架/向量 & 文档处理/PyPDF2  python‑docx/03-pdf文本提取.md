## 1. 提取的原理与质量真相

理解 `extract_text()` 能干什么，先理解 PDF 里文本长什么样：PDF 页面内容是**字形绘制指令**——「在坐标 (x,y) 用字体 F 绘制字符串 'Hello'」。提取就是反向过程：扫描页面指令流，按绘制顺序把字符串拼出来。

这个原理决定了三个质量真相：**顺序**——按绘制顺序拼接，多栏版式的阅读顺序（先左栏后右栏）往往不对；**空白**——坐标间距丢失，字与字之间的空格可能消失或爆炸；**字体**——字体不含 Unicode 映射时（自定义编码字体），提取出来是乱码或空。**「提取质量由 PDF 本身决定」**是必须建立的认知：工具负责把字挖出来，但「挖出来的排布是否正确」取决于 PDF 制作方的良心——从 Word/WPS 正常导出的 PDF 提取质量高，从专业排版工具（InDesign 等）导出的复杂版式提取质量参差，扫描件根本没有文本层。

## 2. 分页遍历与整本提取

`extract_text()` 是逐页方法，整本提取是循环拼接。三个姿势按场景选：

```python
from pypdf import PdfReader

reader = PdfReader("book.pdf")

# 姿势一：全量提取（小文件、整本入库）
full = "\n".join(page.extract_text() or "" for page in reader.pages)

# 姿势二：按页索引（章节定位、增量处理）
page5 = reader.pages[4].extract_text()

# 姿势三：分批流式（大文件防内存爆——生成器惰性读页）
def iter_pages(reader):
    for page in reader.pages:
        yield page.extract_text() or ""

for i, text in enumerate(iter_pages(reader)):
    process(text, page_no=i)
```

要点：**`extract_text()` 返回 `None` 时用 `or ""` 兜底**（空页、无文本层页会返回 None，不兜底则 `join` 报错）；**大文件用生成器惰性遍历**，`reader.pages` 是懒加载的（页码索引才真正解析），全量 `join` 会一次性占满内存；**逐页保留页码**是 RAG 溯源的基础（回答要能定位到第几页，08 篇）。

## 3. 提取参数

`extract_text()` 有几个常用参数，按场景启用：

```python
text = page.extract_text(
    extraction_mode="layout",      # "layout" 按版面布局提取（保留换行与间距）
    visitor_text=my_callback,      # 逐文本片段回调（精细控制）
)
```

**`extraction_mode="layout"`**：默认 "plain" 模式是「文本流」拼接，layout 模式尝试还原版面（多栏、缩进、换行更接近视觉排布）——复杂版式提取质量提升明显，但输出可能带大量空白字符，清洗成本上升。**`visitor_text` 回调**：每个文本片段调用一次，可以拿到片段的坐标与字体信息——需要「哪个区域是页眉页脚」这类位置判断时用它（配合 08 篇的清洗规则）。日常提取用默认即可，质量不满再逐级上 layout、回调、pdfplumber。

## 4. 乱码治理

提取出乱码（`锟斤拷`、`□`、空串）的排查路径，按概率排序：

**第一问：是扫描件吗**。打开 PDF 用眼睛看——如果内容是图片（放大失真、无法选中文字），没有文本层，提取必然失败，走第 5 节 OCR。

**第二问：加密了吗**。`reader.is_encrypted` 为 True 时提取报错或返回空——先 `reader.decrypt("密码")` 或 `PdfReader(path, password="...")` 打开（04 篇）。

**第三问：字体编码特殊**。老 PDF（扫描时代的矢量版）用自定义字体编码，无 Unicode 映射——pypdf 尽力还原仍乱码，换 PyMuPDF 或 pdfminer.six 试试（不同提取引擎对字体编码的处理不同，交叉验证是最后一招）。

**第四问：文本本身是乱码**。PDF 制作时就编码错误（源头脏），工具无解——换源文件。

**第五问：提取是空但 PDF 有字**。同上按序排查；还有一类是「文本是矢量轮廓」（文字被转成图形），与扫描件同性质。

## 5. 扫描件处理

无文本层的扫描件，提取前必须 OCR——pypdf 自己不做 OCR，工作流是「渲染 → OCR → 文本」：

```python
# 方案一：OCR 引擎直接吃 PDF（配合 pdf2image 渲染）
from pdf2image import convert_from_path
import pytesseract

images = convert_from_path("scan.pdf", dpi=300)      # PDF → 图片
for img in images:
    text = pytesseract.image_to_string(img, lang="chi_sim+eng")  # 中文+英文
```

要点：**DPI 决定 OCR 质量**——300dpi 是底线，低于 200 识别率显著下降；**中文要 `lang="chi_sim"`**（tesseract 需装对应语言包）；**多语言用 `+` 连接**。生产级扫描件处理建议直接用 [[../../强烈推荐（做项目必用，简历加分）/unstructured/00-unstructured总览|unstructured]] 的 OCR 策略（`strategy="ocr_only"`）或云 OCR（识别率更高）——pytesseract 本地免费但中文长文质量一般。判断「是不是扫描件」的脚本化方式：提取文本长度 / 页数 < 阈值（如每页 < 50 字符）即判定无文本层。

## 6. 提取质量评估

「提取的质量」不能靠肉眼扫一眼就下结论——RAG 场景的文本质量直接决定检索效果，量化评估三步：

**第一步，抽样对比**：随机抽 3-5 页，人工对照 PDF 原文，检查三类错误——丢字（数字、英文、公式最易丢）、错序（多栏、表格列错位）、噪音（页眉页脚页码混入正文）。**第二步，量化指标**：提取字数 vs 预期字数（粗略完整性）、中文标点比例（乱码的标点会是 `□`）、换行密度（异常换行 = 版面结构问题）。**第三步，决策**：质量不合格时按 08 篇升级路径处理——layout 模式 → pdfplumber → OCR → unstructured 分层。

**评估是「一次建立，反复使用」的资产**：写一个 `quality_report(text)` 函数（字数/标点/换行/重复率），进批处理管道（09 篇），每批文档自动出质量报告——「这条管道跑出来的文本靠不靠谱」永远有数字答案。

## 7. 常见坑

**坑一：`or ""` 忘写**。None 页让 `"\n".join()` 直接炸——提取循环统一兜底。

**坑二：多栏 PDF 顺序错乱**。默认 plain 模式跨栏拼接——layout 模式或按坐标回调。

**坑三：中文提取出来是英文符号**。字体映射问题——尝试 layout 模式或换引擎。

**坑四：大 PDF 全量 join 内存爆**。生成器逐页处理——RAG 预处理常见事故。

**坑五：扫描件直接提取**。返回空或乱码——先判类型再走 OCR。

**坑六：评估靠肉眼**。扫一眼「还行」就入库——写 quality_report 函数量化。
