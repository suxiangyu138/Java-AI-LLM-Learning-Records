## 1. 批量管道骨架

批量处理的核心不是「循环」，是「可重跑」——同一次运行中断后能续跑、重跑结果一致、失败有据可查。骨架：

```python
import os, json
from pypdf import PdfReader

def process_one(path: str, out_dir: str) -> dict:
    """单文件处理：提取 → 清洗 → 输出 JSON（纯函数，可重跑）"""
    reader = PdfReader(path)
    text = "\n".join(p.extract_text() or "" for p in reader.pages)
    result = {"source": os.path.basename(path), "pages": len(reader.pages),
              "chars": len(text), "text": text}
    out = os.path.join(out_dir, os.path.splitext(os.path.basename(path))[0] + ".json")
    with open(out, "w", encoding="utf-8") as f:
        json.dump(result, f, ensure_ascii=False)
    return result

def batch_process(src_dir: str, out_dir: str):
    os.makedirs(out_dir, exist_ok=True)
    for name in sorted(os.listdir(src_dir)):
        if not name.lower().endswith(".pdf"):
            continue
        out = os.path.join(out_dir, name.replace(".pdf", ".json"))
        if os.path.exists(out):            # 断点续跑：已产出跳过
            continue
        try:
            process_one(os.path.join(src_dir, name), out_dir)
        except Exception as e:
            log_failure(name, e)           # 单文件失败不中断整体

batch_process("pdfs/", "output/")
```

三条纪律：**纯函数单文件处理**（输入路径 + 输出路径，无全局状态——可并行、可重跑）；**产出检查续跑**（输出文件存在即跳过——中断后重跑只补缺失）；**失败隔离**（单文件异常捕获留痕，不炸整体）。

## 2. 异常隔离与断点续跑

文档处理的异常面比代码处理广得多——损坏文件、加密 PDF、超长文件名、权限错误，每种都要隔离：

```python
from dataclasses import dataclass

@dataclass
class Failure:
    name: str
    error: str
    stage: str          # extract / clean / write

failures: list[Failure] = []

def process_one(path: str) -> dict | None:
    try:
        reader = PdfReader(path)
    except Exception as e:
        failures.append(Failure(path, repr(e), "open")); return None
    try:
        text = "\n".join(p.extract_text() or "" for p in reader.pages)
    except Exception as e:
        failures.append(Failure(path, repr(e), "extract")); return None
    if len(text) < 100:                      # 空提取 = 扫描件/加密，单独归类
        failures.append(Failure(path, "text too short", "quality")); return None
    return {"source": path, "text": text}

# 结束统一输出失败清单（按阶段归类 → 批量修复依据）
json.dump([f.__dict__ for f in failures], open("failures.json", "w"), ensure_ascii=False)
```

**失败分类的价值**：`open` 失败 = 文件损坏清单（换源）；`extract` 失败 = 加密清单（解密后重跑）；`quality` 失败 = 扫描件清单（走 OCR 管道）——一次运行产出三类修复任务，下一轮针对性处理。这就是「批量处理的可演进性」：每轮运行让下轮更聪明。

## 3. 性能纪律

文档处理的性能瓶颈在「解析成本」而非 CPU——PDF 逐页解析、docx 解压 XML 都是慢操作。五条纪律：

**第一，别重复打开**。循环里 `PdfReader(path)` 打开一次读完全部页，别每页重新打开（PdfReader 是懒加载，`pages` 遍历一次解析一次）。

**第二，大文件流式**。几百 MB 的 PDF 全量 `join` 内存爆炸——逐页处理、页用完即弃（03 篇生成器）。

**第三，合理并行**。文档处理是 I/O + 解析混合，`concurrent.futures.ProcessPoolExecutor` 多进程并行（CPU 解析密集，GIL 下线程收益有限）；**并行时注意输出文件冲突**——每个 worker 写独立输出文件，或统一收集结果最后写。

**第四，批量小文件合并处理**。几百个小 PDF 逐文件打开开销大——pypdf 的 `PdfWriter.append` 支持文件对象列表流式合并。

**第五，预筛减少无效处理**。按扩展名、文件大小、修改时间预筛，跳过明显无效的输入。

**第六，输出格式的工程选择**。批量提取的输出格式按下游定：**纯文本 txt**（最简、人读）、**JSON**（结构化，带 source/page/metadata——RAG 入库首选）、**CSV**（表格类数据）、**Parquet**（大数据量分析）。JSON 是文档处理管道的推荐中间格式：`{"source": ..., "page": ..., "text": ..., "metadata": {...}}` 每文件一条记录——下游无论是入库（chromadb）、分析（pandas）、还是再处理（清洗增强），JSON 都能无损对接；且 JSON 文件天然支持断点续跑（存在即完成，09 篇第 1 节）。

**第七，管道的可观测输入**。批量处理的输入质量决定输出质量——跑之前先统计输入分布（文件数、大小分布、扩展名分布、疑似扫描件数量），跑之后对比输出统计（成功数、失败数、平均字数、空提取数）。「输入统计」与「输出统计」的对比就是管道健康度报告：输入 1000 份、成功 950、失败 50（加密 30 + 扫描 15 + 损坏 5）——每项都有下一步动作。

## 4. 日志与监控

批量管道必须有「跑完能复盘」的日志——用 [[../../强烈推荐（做项目必用，简历加分）/loguru/00-loguru总览|loguru]] 三行接入：

```python
from loguru import logger
logger.add("pipeline.log", rotation="10 MB", retention="7 days", enqueue=True)

logger.info("开始批处理：{n} 个文件", n=len(files))
ok, fail = 0, 0
for name in files:
    try:
        process_one(name)
        ok += 1
    except Exception as e:
        fail += 1
        logger.error("失败 {name}: {error}", name=name, error=e)
logger.info("完成：成功 {ok}，失败 {fail}，耗时 {t:.1f}s", ok=ok, fail=fail, t=elapsed)
```

监控三件事：**进度**（处理到哪了——每 N 个文件打一行）；**失败率**（失败清单 + 归类统计——扫描件 vs 加密 vs 损坏）；**耗时**（总量与单文件平均——性能回归的报警器）。**日志是管道的「可审计性」**——出问题能回答「哪个文件、哪一步、什么错」。

## 5. 与 unstructured 的选型

| 维度 | pypdf/python-docx 手搓 | unstructured |
|------|----------------------|--------------|
| 格式覆盖 | PDF + docx | 25+ 格式（含 PPT、HTML、图片） |
| 版面分析 | 无（文本流） | 有（标题/表格/列表识别） |
| 表格 | pdfplumber 补充 | 原生 text_as_html |
| 控制粒度 | 全控制 | 参数化控制 |
| 依赖重量 | 轻（纯 Python） | 重（extras 体系） |
| 适用 | 单库精细操作/轻量管道 | 生产级文档 ETL |

选型决策：**单格式、单文档精细操作、轻量脚本 → 双件套**；**多格式批量入库、要版面结构、生产级 ETL → unstructured**。混合姿势也常见：unstructured 管解析入库，python-docx 管报告生成——一个是「读进来」，一个是「写出去」，互补不冲突。RAG 生产管道的完整形态：unstructured 解析 → 清洗 → 切块 → 向量库 → 检索；双件套是这条管道的「单点工具」与「学习路径」。

## 6. 报告生成实战模式

python-docx 的报告生成是生产高频场景，一个可复用模式——**数据进表格、结论进段落、图表进图片**：

```python
def build_report(doc, data: dict):
    doc.add_heading(data["title"], level=0)
    doc.add_paragraph(f"统计周期：{data['period']}")
    # 核心数据进表格
    table = doc.add_table(rows=len(data["rows"]) + 1, cols=3)
    table.style = "Table Grid"
    headers = ["指标", "数值", "同比"]
    for j, h in enumerate(headers):
        table.cell(0, j).text = h
    for i, row in enumerate(data["rows"], start=1):
        for j, v in enumerate(row):
            table.cell(i, j).text = str(v)
    # 结论进段落（自然语言表述）
    doc.add_paragraph(f"结论：{data['conclusion']}")
    # 图表进图片（matplotlib 先行生成）
    doc.add_picture(data["chart_path"], width=Inches(5))

# 调用：数据一变，报告即变
doc = Document()
build_report(doc, {"title": "8 月销售报告", "rows": [...], "chart_path": "aug.png"})
doc.save("sales_aug.docx")
```

模式要点：**数据与文档生成分离**（build_report 吃 dict 不碰数据库）；**同一个模板函数服务多期**（月度报告换数据即可）；**「表格 + 段落 + 图片」三件套覆盖报告 90% 形态**。

## 7. 常见坑

**坑一：循环里重复打开大文件**。每页 new PdfReader——打开一次，遍历 pages。

**坑二：单文件失败炸整体**。一个坏 PDF 中断整批——异常隔离 + 失败清单。

**坑三：并行写同一输出**。多进程写同名文件互相覆盖——输出按文件名隔离。

**坑四：无日志盲跑**。跑完不知道成败——loguru 三件套（进度/失败/耗时）。

**坑五：手搓一切**。25 格式 + 版面需求还在手搓——上 unstructured，别重复造轮子。

**坑六：报告函数耦合数据库**。build_report 直接查库——传 dict，数据与生成分离。
