## 1. 为什么需要所有权

### 无主的问题

```
技能没人负责：
① 坏技能没人修（用户受苦）
② 依赖变化没人更新（漂移）
③ 问题没人响应（issue 堆积）
——"技能即产品"需要有人负责
```

### 所有权的价值

```
① 责任明确（谁管什么）
② 响应及时（owner 负责）
③ 质量稳定（长期维护）
④ 交接顺畅（owner 是接口人）
——从"大家的事"到"明确分工"
```

### Google 实践（技能即产品）

```
repo maintainers：负责仓库健康/CI 管道/架构标准
skill owners：长期维护技能（API 变化时更新）
——双层所有权（库级 + 技能级）
```

## 2. 角色分工

### 双层角色

| 角色 | 职责 |
|---|---|
| Repo Maintainer | 仓库健康/CI 管道/架构标准/质量门禁 |
| Skill Owner | 单个技能的长期维护（更新/修复/响应） |
| 贡献者 | 提交技能/改进（非长期负责） |
| 审核者 | 合并前审查（质量/安全） |

### 分工原则

```
库级问题 → maintainer（全局）
技能问题 → owner（局部）
——职责不重叠（谁的问题谁负责）
```

### Owner 的职责清单

```
① 技能质量（持续达标）
② 依赖更新（API 变化时）
③ 问题响应（issue）
④ 版本管理（SemVer）
⑤ 废弃决策（替代/清理）
——owner 是技能的第一责任人
```

## 3. 技能注册表

### 是什么

```
集中式 Skill Registry（技能注册表）：
所有技能的登记处（发现/状态/元数据）
——内部"市场"（阶段 4 的 Marketplace 企业版）
```

### 注册表内容

```
每个技能：
名称/版本/描述/owner
状态（active/deprecated）
评估数据（评分/门禁结果）
依赖/兼容性
——一站式信息（发现 + 治理）
```

### 注册表的价值

```
① 发现：团队知道有什么技能
② 治理：状态/评分集中可见
③ 复用：避免重复开发（先查再用）
④ 审计：全库清单（谁有什么）
——"技能复用率低"痛点的解法
```

### 实现

```
skill-guard catalog（注册表命令）
或自建（内部 wiki/平台）
——注册表 = 治理的"目录"
```

## 4. 审批工作流

### 审批流程

```
技能提交 → 质量门禁（自动）
→ 安全扫描（自动）
→ 人工审查（审核者）
→ Owner 确认（负责）
→ 入库（注册表登记）
```

### 审批层级

| 层级 | 把关 |
|---|---|
| 自动门禁 | 格式/安全/冲突（skill-guard） |
| 人工审查 | 质量/设计（审核者） |
| Owner 确认 | 责任接收（负责后续） |

### 审批效率

```
① 自动门禁先跑（过滤低级问题）
② 人工只看"过门禁的"（聚焦）
③ changed-only（只审变更）
——审批不卡流程（自动化前置）
```

## 5. 审计轨迹

### 为什么审计

```
企业合规需求：
谁提交了什么/谁审批的/版本变更历史
——可追溯（出了事查得到）
```

### 审计内容

```
① 技能变更历史（git）
② 审批记录（谁批准）
③ 扫描结果（安全记录）
④ 评估数据（质量轨迹）
——全链路留痕
```

### 审计实现

```
① git 历史（变更天然留痕）
② CI 日志（门禁/扫描记录）
③ 评估报告（质量轨迹）
——治理的"账本"（03 篇呼应）
```

## 6. 协作模式

### 贡献指南

```
技能贡献者的文档（团队 onboarding）：
① 从模板生成（规范内建）
② 写元数据（skill.yaml）
③ 本地跑门禁（validate/secure）
④ 提交 PR（自动门禁 + 人工审查）
⑤ owner 确认后入库
——贡献流程文档化（新成员照做）
```

### 团队协作方式

```
① 贡献者提交 PR → 门禁 → 审查 → 入库
② Owner 维护技能（更新/修复）
③ Maintainer 管库（规范/CI/架构）
④ 用户反馈（issue → owner 响应）
——标准开源协作模式（技能也是软件）
```

### 多团队场景

```
多团队共享技能库：
① 按领域分目录（团队各自 owner）
② 公共技能（共享 owner/轮值）
③ 跨团队 review（质量保障）
——大型组织的扩展方式
```

### 治理成熟度

```
单团队：owner + 注册表（起步）
多团队：分域 owner + 跨团队审查（发展）
企业级：完整治理闭环（07 篇）
——按规模选治理深度
```

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "技能不用 owner" | 无主即无维护（漂移） |
| "注册表是文档" | 是发现 + 治理的目录 |
| "审批全人工" | 自动门禁前置（人工聚焦） |
| "审计可省" | 合规要求（可追溯） |
| "一个人全包" | 双层分工（maintainer/owner） |

## 8. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 为什么所有权？ | 无主即无维护（技能是产品） |
| 双层角色？ | maintainer 管库/owner 管技能 |
| 技能注册表？ | 发现 + 治理的目录（内部市场） |
| 审批流程？ | 自动门禁 → 人工审查 → owner 确认 |
| 审计轨迹？ | git + CI 日志 + 评估报告 |
| 多团队扩展？ | 分域 owner + 跨团队审查 |

### 面试加分表达

> "所有权治理的核心是'技能即产品，有人负责'：repo maintainer 管仓库健康/CI/架构标准，skill owner 管单个技能的长期维护（依赖更新/问题响应/废弃决策）。集中式技能注册表解决'复用率低'痛点（先查再用、状态可见）。审批工作流是自动门禁前置（skill-guard 先跑）+ 人工聚焦审查 + owner 确认。git + CI 日志 + 评估报告形成审计轨迹。"

> 🎯 核心要点：所有权 = 技能即产品（有人负责）；双层角色（maintainer 库级/owner 技能级）；注册表（发现 + 治理目录，解决复用率低）；审批流程（自动门禁前置 + 人工聚焦 + owner 确认）；审计轨迹（git/CI/评估全留痕）；多团队扩展（分域 owner + 跨团队审查）。
