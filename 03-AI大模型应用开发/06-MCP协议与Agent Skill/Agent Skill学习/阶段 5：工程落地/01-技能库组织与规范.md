## 1. 为什么需要标准化

### 没有规范的问题

```
① 发现难：技能散落（目录/命名各异）
② 审查难：每个技能结构不同（无法批量检查）
③ 维护难：改规范要适配 N 种写法
④ 交接难：新成员学不会（无统一模式）
```

### 标准化的价值

| 价值 | 说明 |
|---|---|
| 可发现 | 统一布局 → 快速定位 |
| 可审查 | 统一结构 → 批量校验 |
| 可维护 | 统一模式 → 升级容易 |
| 可交接 | 统一规范 → onboarding 快 |

### Google 实践（标杆）

```
所有技能遵循统一仓库布局
提交时自动检查（lint 校验元数据/行数/目录/命名）
——标准化是治理的地基
```

## 2. 仓库布局规范

### 技能仓库结构（参考）

```
skills-repo/
├── skills/
│   ├── code-review/
│   │   ├── SKILL.md
│   │   ├── scripts/
│   │   └── references/
│   ├── doc-generator/
│   └── ...
├── templates/              # 新技能模板
├── validate_skills.py      # 校验脚本
├── VALIDATION_REPORT.md    # 验证报告
└── README.md               # 技能索引
```

### 布局原则

```
① 技能目录集中（skills/ 下）
② 每技能一个目录（标准结构）
③ 模板与校验工具配套
④ 索引文档（README 列出全部）
```

### 跨 agent 注意

```
仓库内技能可放 .agents/skills/（通用总线）：
技能既在库中（治理）又在各 agent 可用（分发）
——"构建一次，处处使用"
```

## 3. 命名规范

### 技能命名

```
kebab-case（小写连字符）：
✅ code-review / doc-generator / env-setup
❌ CodeReview / code_review / My Skill
```

### 目录命名 = 技能名

```
强制一致（发现机制依赖）：
skills/code-review/SKILL.md
（name: code-review 与目录名一致）
```

### 命名语义

```
动词-对象（做了什么）：
生成 → generate-*
审查 → review-*
校验 → validate-*
——命名即功能（可发现性）
```

## 4. 元数据定义（skill.yaml）

### 是什么

```
技能库级元数据（区别于 SKILL.md frontmatter）：
仓库统一的技能登记信息（便于索引/管理）
```

### 元数据字段

```yaml
# skill.yaml（示例）
name: code-review
version: 1.2.0
description: 代码审查技能
inputs:          # 输入输出定义（标准化接口）
  - 代码路径
outputs:
  - 问题清单
dependencies:    # 依赖声明
  - git
compatibility:   # 平台兼容
  - claude-code
  - codex
owner: review-team    # 所有权（06 篇）
```

### 元数据的价值

```
① 标准化接口（输入/输出定义——复用基础）
② 依赖声明（知道技能要什么）
③ 所有权登记（谁负责）
④ 兼容性声明（跨平台）
——从"文件夹"到"登记在册的资产"
```

## 5. 模板目录

### 新技能模板

```
templates/
└── skill-template/
    ├── SKILL.md          # 标准骨架（frontmatter + 七部分）
    ├── skill.yaml        # 元数据模板
    └── README.md         # 使用说明模板
```

### 模板的价值

```
① 规范内建：新技能从模板生成 = 天然合规
② 快速起步：不用从零写（脚手架）
③ 质量基线：模板含最佳实践
——规范通过模板"自动执行"
```

### 模板 vs 技能

```
模板 = 未填写的技能（骨架）
技能 = 填充后的模板（成品）
——模板是"规范的具体化"
```

## 6. 规范落地

### 落地步骤

```
① 定义规范（布局/命名/元数据/模板）
② 建模板目录（新技能走模板）
③ 配校验脚本（validate_skills.py）
④ 进 CI（提交时检查）
⑤ 文档化（规范写入 README/AGENTS.md）
```

### 规范文档

```
规范写入仓库级文档（AGENTS.md）：
Agent 开发技能时自动遵守（不靠人记）
——规范"可执行化"（Agent 读得到）
```

### 落地检查清单

| 项 | 检查 |
|---|---|
| 布局统一 | skills/ 下每技能一目录 |
| 命名一致 | kebab-case = 目录名 = name |
| 元数据齐全 | skill.yaml（接口/依赖/owner） |
| 模板存在 | 新技能从模板生成 |
| 校验脚本 | 可批量检查 |
| CI 接入 | 提交时自动跑 |

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "规范是文档" | 规范要可执行（模板 + 校验 + CI） |
| "命名随意" | 发现机制依赖（目录=name） |
| "skill.yaml 可省" | 接口/依赖/owner 登记（治理基础） |
| "模板多余" | 模板让规范自动执行 |
| "规范一次定死" | 持续演进（Google 也在迭代） |

## 8. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 为什么标准化？ | 可发现/审查/维护/交接 |
| 仓库布局？ | skills/ 集中 + 模板 + 校验工具 |
| 命名规范？ | kebab-case = 目录 = name |
| skill.yaml？ | 接口/依赖/owner 登记（治理基础） |
| 模板价值？ | 规范自动执行 |
| 规范怎么落地？ | 模板 + 校验脚本 + CI + 文档 |

### 面试加分表达

> "技能库治理的第一步是标准化：统一仓库布局（skills/ 集中 + 模板 + 校验脚本）、命名规范（kebab-case 且目录名=name，这是发现机制依赖的）、元数据登记（skill.yaml 定义接口/依赖/owner——从'文件夹'到'登记在册的资产'）。关键认知：规范不能只是文档，要通过模板（自动合规）+ 校验脚本（批量检查）+ CI（提交时强制）让它可执行。"

> 🎯 核心要点：标准化 = 可发现/审查/维护/交接；仓库布局（skills/ + 模板 + 校验工具 + 索引）；命名（kebab-case = 目录 = name）；skill.yaml 元数据（接口/依赖/owner）；模板让规范自动执行；落地五步（定义→模板→脚本→CI→文档）；规范可执行化（AGENTS.md）。
