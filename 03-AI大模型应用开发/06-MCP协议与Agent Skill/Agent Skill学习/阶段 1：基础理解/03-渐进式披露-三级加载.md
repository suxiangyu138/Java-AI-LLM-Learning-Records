# 03 渐进式披露：三级加载

> Skill 控制上下文成本的核心机制：启动只加载元数据（L1）、任务触发才读正文（L2）、执行按需取配套（L3）——"用到才看，不浪费注意力"。

## 1. 为什么需要渐进式披露

### 上下文是稀缺资源

```
Agent 的上下文窗口有限（几万到百万 token）
技能多了：每个技能全量加载 = 上下文爆炸
```

### 朴素方案的缺陷

| 方案 | 缺陷 |
|---|---|
| 全部加载 | 上下文爆炸、互相干扰 |
| 不加载 | Agent 不知道有这技能 |
| 关键词过滤 | 匹配不准 |

### 渐进式披露的答案

```
按需加载：启动只读元数据（占极小），用到才加载正文与配套
→ 同时维护大量技能而不爆上下文
```

## 2. 三级加载模型

### Level 1：元数据（启动时）

```
加载内容：所有技能的 name + description（frontmatter）
用途：技能发现与任务匹配
上下文占用：极小（每技能几十 token）
```

### Level 2：SKILL.md 正文（触发时）

```
加载条件：任务与 description 匹配
加载内容：完整 SKILL.md 正文
用途：执行指令（步骤/规范）
```

### Level 3：配套文件（执行中）

```
加载条件：正文执行到需要时
加载内容：scripts/ references/ assets/ 中的具体文件
用途：脚本/资料/模板
```

```
┌─────────────────────────────────────┐
│ L1 元数据（启动）：name+description │  ← 所有技能
├─────────────────────────────────────┤
│ L2 正文（触发）：SKILL.md 全文      │  ← 匹配的技能
├─────────────────────────────────────┤
│ L3 配套（执行）：scripts 等按需     │  ← 用到的文件
└─────────────────────────────────────┘
```

## 3. 省钱原理与实测

### 实测案例（Strapi 的 skill）

```
4 个模板文件共约 94KB 数据：
用户选择具体模板前 → 完全不加载
只有 blog.json 被选中 → 才进入上下文
节省约 70KB tokens
```

### 省钱公式

```
省下的上下文 = 未触发技能正文 + 未使用配套文件
技能越多、配套越大 → 渐进式披露越值
```

### 为什么"多技能共存"成为可能

```
100 个技能：
朴素方案：100 × 正文（爆）
渐进式：100 × description（几十 KB）+ 触发的 1-2 个正文
→ 技能库可以很大，上下文保持小
```

## 4. 与上下文窗口的关系

### 对比"全塞进 prompt"

| 维度 | 全塞 prompt | 渐进式披露 |
|---|---|---|
| 技能数 | 几个就爆 | 大量共存 |
| 上下文 | 常满 | 按需占用 |
| 匹配精度 | 全部可见 | description 匹配 |
| 干扰 | 互相干扰 | 互不影响 |

### 与 1M 上下文的关系

```
"窗口大了还需要省吗？"——需要：
① token 成本：上下文越大越贵（每次调用都算）
② 注意力：内容越多，关键指令越被稀释
③ 技能库规模：1M 窗口也装不下全部技能
渐进式披露在窗口时代同样必要（甚至更必要）
```

## 5. 实现视角

### 平台的实现逻辑（理解即可）

```
① 启动扫描技能目录 → 解析 frontmatter → 构建技能索引（L1）
② 每次任务：用 description 匹配（LLM 或规则）→ 命中加载正文（L2）
③ 执行中：正文提到文件 → 按需读取（L3）
```

### 对技能作者的要求

```
渐进式披露倒逼技能结构：
description 必须能独立承担"匹配"（否则触发不了）
正文必须自包含执行指令（加载后不用外部解释）
大文件必须拆配套（否则 L2 就爆）
```

## 6. 设计启示

### 三个设计原则（技能作者视角）

| 原则 | 说明 |
|---|---|
| description 是门户 | 匹配全靠它——写触发场景 |
| 正文要自包含 | 加载后能独立执行 |
| 大文件往下拆 | 配套文件按需加载 |

### 类比

```
渐进式披露 = 图书馆的"目录-书架-翻页"：
目录（L1）：扫一眼知道有什么
书架定位（L2）：找到那本书
翻页（L3）：看具体章节
不把整座图书馆搬进脑子
```

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 渐进式披露是什么？ | 三级按需加载（元数据→正文→配套） |
| L1 加载什么？ | 所有技能的 name+description（启动时） |
| L2 何时加载？ | 任务与 description 匹配时 |
| L3 加载什么？ | scripts/references/assets 按需 |
| 省多少？ | 实测案例省约 70KB tokens |
| 窗口大了还需要吗？ | 需要——成本/注意力/技能库规模 |

### 面试加分表达

> "渐进式披露是 Skill 控制上下文的杀手锏：启动只加载全部技能的 description（L1），任务匹配才读正文（L2），执行按需取配套（L3）——实测案例省约 70KB tokens。这让技能库可以很大而上下文保持小。它倒逼技能作者：description 必须写好（门户）、正文必须自包含、大文件必须拆配套。"

## 8. 常见误区

| 误区 | 真相 |
|---|---|
| "description 只加载一次" | 每任务都要匹配（常驻小开销） |
| "L2 加载后一直占着" | 任务结束可释放（按任务生命周期） |
| "配套文件随便放" | 放错目录 → L3 找不到 |
| "窗口大不用省" | 成本/注意力/库规模三个理由仍在 |
| "渐进式是平台的事" | 技能作者的结构决定披露效率 |

## 9. 与缓存/上下文的工程结合

### 与 prompt caching 的关系

```
加载后的技能正文可被缓存（同一技能多次触发）：
首次加载（L2）→ 缓存 → 后续命中（省重复加载）
技能正文稳定 = 缓存友好（不要频繁改技能）
```

### 上下文预算视角

```
技能上下文预算：
L1：技能数 × description（常驻，控制总量）
L2：触发的 1-2 个正文（按任务）
L3：执行中的配套（按需）
预算设计：技能库规模 ↔ description 精简度
```

### 工程启示

```
① description 写短：L1 总量 = 技能数 × description
② 正文稳定：利于缓存与可预测加载
③ 配套按需：大文件绝不放正文
④ 技能分级：常用技能正文精简（高频命中省 token）
```

> 🎯 核心要点：渐进式披露 = L1 元数据（启动发现）→ L2 正文（触发加载）→ L3 配套（按需读取）；省钱原理 = 未触发技能不占上下文（实测省 70KB）；窗口时代仍必要（成本/注意力/库规模）；与缓存结合（正文稳定 = 缓存友好）；倒逼技能三设计（description 门户/正文自包含/大文件下拆）；类比"目录-书架-翻页"。
