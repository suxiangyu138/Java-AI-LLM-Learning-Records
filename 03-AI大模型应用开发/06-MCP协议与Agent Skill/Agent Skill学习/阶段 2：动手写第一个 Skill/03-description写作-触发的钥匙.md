# 03 description 写作：触发的钥匙

> description 是技能最重要的那一行——Agent 靠它决定是否触发；写作公式"[做什么] + [什么时候用] + [触发词]"，且要应对模型的 undertrigger（触发不足）倾向。

## 1. 为什么 description 决定成败

### description 的角色

```
description 是唯一常驻的"广告位"：
L1 加载（启动时）：所有技能的 name + description
L2 加载（触发时）：匹配的技能正文

匹配靠什么？——description（正文还没加载，无法参与匹配）
```

### 失败的后果

```
description 差 = 永不触发 = 技能白写
（写得好不好，直接决定技能用不用得上）
```

### 触发机制

```
用户说话 → Agent 拿 description 匹配 → 命中 → 加载正文
description 不匹配 → 技能永远沉默
```

## 2. 写作公式

### 核心公式

```
description = [做什么] + [什么时候用] + [关键能力/触发词]
```

### 结构拆解

| 要素 | 内容 | 例子 |
|---|---|---|
| 做什么 | 动词开头 | 生成部署检查清单 |
| 什么时候用 | Use when... | 用户提到部署/上线/发布 |
| 触发词 | 用户会说的短语 | "deploy" "going to production" |

### 完整示例

```markdown
description: 生成部署检查清单。当用户提到部署、上线、发布、
  或询问上线就绪度时使用——即使他们没有明确要求清单。
```

## 3. 好与坏对比

| 写法 | 例子 | 效果 |
|---|---|---|
| ❌ 太笼统 | "Helps with automation tasks." | 永不触发（谁都沾边） |
| ❌ 缺触发词 | "Commit helper" | 永远不触发（没有"何时用"） |
| ❌ 写自己 | "I can help with..." | 不是"触发场景"视角 |
| ✅ 公式完整 | 做什么+何时用+触发词 | 触发可靠 |

### 关键区别

```
坏 description 回答"这个技能是什么"
好 description 回答"什么时候该用这个技能"
——触发匹配需要的是后者
```

## 4. Undertrigger 与"催促感"

### 什么是 undertrigger

```
官方明确：Claude 有 undertrigger（触发不足）倾向
——即使任务匹配，模型也可能不触发技能
```

### 应对：写得"带点催促感"

```
官方建议：description 要稍微 pushy：
即使没明确要求，只要用户提到相关场景就该触发
例："...使用——即使他们没有明确要求清单。"
```

### 催促感的度

```
过度：什么都触发（误触发）
不足：该触发不触发（undertrigger）
平衡：覆盖相关场景 + 明确边界（"除非明确拒绝"）
```

## 5. 触发词设计

### 触发词来源

```
① 用户会怎么问？（口语/专业说法）
② 相关同义词？（部署/上线/发布/投产）
③ 间接说法？（"快上线了""准备发布吗"）
```

### 触发词清单示例

```markdown
description: 生成部署检查清单。用于用户提到以下场景时：
  部署、上线、发布、投产、go live、production、
  或询问上线就绪度/发布准备情况——即使没明确要求清单。
```

### 每词要有价值

```
"你是在竞争上下文预算"：
每个字要么说明功能、要么说明触发时机
没价值的词删掉（description 越精越有效）
```

## 6. 实战改写练习

### 练习一：通用描述改写

```
原（坏）：
"Helps with code review."

改（好）：
"审查代码改动，输出问题清单。用于提交代码、发起 PR、
  或用户要求'审查/检查/看下代码'时——即使只是让'看看'。
  包含正确性、边界、安全隐患检查项。"
```

### 练习二：你的技能描述

```
按公式写你的技能：
① 做什么：______（动词开头）
② 何时用：______（Use when...）
③ 触发词：______（用户会说的 3-5 个说法）
```

### 自检清单

| 项 | 检查 |
|---|---|
| 有"做什么" | 动词开头，具体不笼统 |
| 有"何时用" | Use when 结构 |
| 有触发词 | 用户会说的短语（含同义/间接） |
| 第三人称 | 不是"I can..." |
| ≤1024 字符 | 别超限 |
| 每词有价值 | 删掉不影响就删 |

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| description 为什么关键？ | 触发匹配的唯一依据（L1 常驻） |
| 写作公式？ | 做什么 + 何时用 + 触发词 |
| undertrigger？ | 模型触发不足倾向——写得带催促感 |
| 触发词从哪来？ | 用户会怎么说（口语/同义/间接） |
| description 写自己？ | 不——写"何时该用" |
| 字数限制？ | ≤1024 字符，每词有价值 |

### 面试加分表达

> "description 是技能唯一常驻的广告位——L1 只加载它，匹配靠它，正文根本没机会参与匹配。写作公式三要素：做什么、何时用（Use when）、触发词（用户会说的说法）。还要应对 undertrigger：官方说模型有触发不足倾向，所以 description 要稍微 pushy——'即使没明确要求也该触发'。"

## 8. 常见误区

| 误区 | 真相 |
|---|---|
| "description 写能力清单" | 写"何时该用"（触发场景） |
| "触发词越多越好" | 每词要挣位置（竞争预算） |
| "描述自己很厉害" | 模型看的是匹配，不是宣传 |
| "写完 description 就不动" | 触发率是 KPI——不触发就改 |
| "催促感 = 到处触发" | 催促 + 边界（别误触发） |

## 9. 本仓库技能 description 拆解

### 真实案例（.claude/skills/）

```
以 markdown-doc-generator 为例拆解：
"生成学习向高密度 Markdown 技术文档——结构精简、表格优先、
无废话套话、适合直接归档 GitHub。用户要求'生成学习笔记/技术文档'、
'按高密度风格写文档'时使用。"

拆解：
✅ 做什么：生成学习向高密度 Markdown 文档
✅ 何时用：用户要求生成笔记/文档时
✅ 触发词："学习笔记""技术文档""高密度风格"
✅ 风格关键词：表格优先/无废话（匹配用户期望）
```

### 拆解练习

```
拆你自己的技能 description（对照公式）：
① 做什么：______
② 何时用：______
③ 触发词：______
④ 风格词：______（可选）
```

> 🎯 核心要点：description = 触发钥匙（L1 唯一常驻）；公式三要素（做什么/何时用/触发词）；坏例三种（笼统/缺触发词/写自己）；undertrigger 应对（催促感但要平衡）；触发词（口语/同义/间接三来源）；每词有价值（竞争上下文预算）；本仓库技能 description 可拆解学习（四要素拆法）。
