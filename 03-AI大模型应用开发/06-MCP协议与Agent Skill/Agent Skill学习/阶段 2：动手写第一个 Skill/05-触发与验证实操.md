## 1. 触发流程

### 四阶段

```
INSTALL（放置到 skills 目录）
  → STARTUP（Claude 读 frontmatter，L1）
  → ACTIVATE（用户说中触发短语，匹配 description）
  → EXECUTE（加载正文执行，L2/L3）
```

### 各阶段的关键

| 阶段 | 关键 | 失败点 |
|---|---|---|
| INSTALL | 路径正确 | 放错目录 |
| STARTUP | frontmatter 有效 | 语法错/预算溢出 |
| ACTIVATE | description 匹配 | 触发词不对 |
| EXECUTE | 正文可执行 | 正文不完整 |

### 两种调用方式

```
自然语言自动触发：用户说触发词 → 自动匹配
斜杠显式调用：/skill-name → 明确指令
```

## 2. 验证的三个维度

| 维度 | 测什么 | 方法 |
|---|---|---|
| 触发测试 | 技能能被激活 | 说触发词观察 |
| 功能测试 | 执行结果正确 | 真实任务验收 |
| 性能测试 | 加载/执行开销合理 | 观察上下文占用 |

```
写完必须三维验证：
触发测试（叫不叫得动）→ 功能测试（干不干得好）→ 性能测试（费不费）
```

## 3. 触发测试实操

### 测试方法

```
① 新会话（确保技能加载）
② 说触发词（用户会说的自然说法）
③ 观察：技能是否激活（正文是否加载）
```

### 测试用例设计

| 用例 | 说法 | 期望 |
|---|---|---|
| 直接触发 | "帮我生成文档" | 技能激活 |
| 间接触发 | "写个学习笔记" | 技能激活（同义） |
| 边界 | 无关任务 | 不激活（不误触发） |
| 斜杠 | /doc-generator | 显式激活 |

### 观察方式

```
怎么知道激活了？
① 对话回复体现技能内容（步骤/格式）
② 直接问"你加载了什么技能？"
③ 正文引用的文件被读取（L3 痕迹）
```

## 4. 功能测试实操

### 测试流程

```
① 构造真实任务（技能的目标场景）
② 执行技能（触发后让它干活）
③ 验收输出（对照"输出格式"）
④ 边界测试（异常输入）
```

### 功能测试清单

| 项 | 检查 |
|---|---|
| 输出格式 | 符合正文的"输出"定义 |
| 步骤执行 | 按顺序完成（无跳步） |
| 错误处理 | 异常输入有兜底 |
| 自包含 | 不需要外部解释 |
| 质量 | 结果达到人工验收标准 |

### 回归测试（改后必跑）

```
改 description/正文后：
① 重跑触发测试（还能触发吗）
② 重跑功能测试（还干得好吗）
——"改坏了"要靠回归发现
```

## 5. 不触发的三步排查

### 排查表

```
技能喊不动？
① 说法太含糊？（触发词没覆盖用户说法）
   → 用技能自己的触发词测试（排除说法问题）
② description 不匹配？（触发词/场景不对）
   → 对照 03 篇公式改写
③ 压根没启用？（路径/加载/预算问题）
   → 01 篇环境四查（路径/重启/预算/同名）
```

### 排查顺序

```
先排除"说法"（用技能触发词直接说）
再检查"匹配"（description 对照公式）
最后查"环境"（/skills 菜单确认加载）
```

### 常见根因

| 根因 | 表现 | 修复 |
|---|---|---|
| description 缺触发词 | 怎么说都不触发 | 03 篇公式 |
| 技能没加载 | /skills 看不到 | 路径/重启 |
| 预算溢出 | /doctor 警告 | 精简技能/description |
| 同名覆盖 | 加载的是另一个 | 检查优先级 |

## 6. 迭代与回归

### 迭代循环

```
写 → 测（触发/功能）→ 改 → 回归（重测）→ 定稿
```

### 迭代重点

```
不触发 → 调 description（触发率是它的 KPI）
执行差 → 调正文（步骤/规则/输出）
加载重 → 拆 references（渐进式披露）
```

### 迭代纪律

```
① 一次只改一个变量（description 或正文）
② 每次改动跑回归（触发 + 功能）
③ 记录版本（version 递增）
④ 测试用例保留（回归资产）
```

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 触发流程四阶段？ | INSTALL→STARTUP→ACTIVATE→EXECUTE |
| 验证三维？ | 触发/功能/性能 |
| 怎么知道激活了？ | 回复体现技能内容/直接问/文件读取痕迹 |
| 三步排查？ | 说法→匹配→环境 |
| 改坏了怎么发现？ | 回归测试（触发+功能重跑） |
| 不触发调什么？ | description（触发率是它的 KPI） |

### 面试加分表达

> "写技能的纪律是'写完必须验证，不靠玄学'：三维测试——触发测试（说触发词看激活）、功能测试（真实任务验收输出）、性能测试（上下文开销）。不触发走三步排查：先排除说法（用技能触发词直接说）、再查匹配（description 对照公式）、最后查环境（/skills 菜单）。每次改动跑回归，触发和功能都要重测。"

> 🎯 核心要点：触发四阶段（INSTALL→STARTUP→ACTIVATE→EXECUTE）；验证三维（触发/功能/性能）；触发测试四用例（直接/间接/边界/斜杠）；三步排查（说法→匹配→环境）；回归纪律（一次一变量 + 重跑触发功能）；测试用例是回归资产。

## 8. 常见误区

| 误区 | 真相 |
|---|---|
| "触发一次就算成功" | 要全用例测试（直接/间接/边界） |
| "功能对就完事" | 触发/功能/性能三维都要 |
| "改完不用回归" | 一次一变量 + 重跑是纪律 |
| "不触发就改正文" | 先查 description（触发靠它） |
| "验证是可选" | 写完必须验证（不靠玄学） |
