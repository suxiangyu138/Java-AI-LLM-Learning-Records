# 04 正文编写：结构与指令

> 正文是技能的"执行手册"：七部分结构（概述/前置/步骤/输出/错误/示例/资源）、声明式优先的指令风格、自包含原则——正文写得好，执行才可靠。

## 1. 正文的七个部分

### 七部分结构（Your First Skill 教程）

| 部分 | 内容 | 必写？ |
|---|---|---|
| Overview（概述） | 技能做什么、何时用 | ✅ |
| Prerequisites（前置条件） | 需要什么环境/文件 | 视情况 |
| Instructions（执行步骤） | 编号步骤 | ✅ |
| Output（输出格式） | 结果长什么样 | ✅ |
| Error Handling（错误处理） | 出错怎么办 | 视情况 |
| Examples（示例） | 输入输出示例 | 推荐 |
| Resources（资源） | 配套文件指引 | 有配套时 |

### 最小必写

```
最小正文 = 概述 + 执行步骤 + 输出格式
（其他部分按需补充）
```

## 2. 指令风格：声明式 vs 程序式

### 两种风格

| 风格 | 形式 | 适用 |
|---|---|---|
| 声明式 | bullet 规则（行为边界/约束） | **默认首选** |
| 程序式 | 编号步骤（严格顺序） | 严格顺序任务 |

### 为什么声明式优先

```
bullet 规则 = 行为边界（比步骤更可靠）
编号步骤 = 严格顺序（顺序错了会乱）
经验：能声明就不编号；编号只用于真正有顺序的任务
```

### 示例对比

```markdown
# 声明式（默认）
## 规则
- 文档标题用 # 一级标题
- 代码块必须标注语言
- 表格优先于大段文字

# 程序式（严格顺序）
## 执行步骤
1. 确认文档类型
2. 读取模板
3. 填充内容
```

## 3. 步骤编写规范

### 编号步骤的规则

```
① 只用于严格顺序任务
② 限制在 10-15 步内（超出拆子流程）
③ 每步具体可执行（不是抽象描述）
④ 步骤间有明确产出传递
```

### 每步的写法

| 好 | 坏 |
|---|---|
| 读取 assets/templates/ 中的 blog 模板 | 读一下模板 |
| 运行 `npm test` 验证改动 | 验证一下 |
| 输出包含问题列表和严重级别 | 输出结果 |

### 正面指令优先

```
错误规则写成正面指令：
✅ "Use pipeline() for stream composition"
❌ "Don't use .pipe()"（反模式表）
——正面指令比"不要做"更可靠
```

## 4. 自包含原则

### 含义

```
正文加载后（L2）应能独立执行：
不依赖正文外的解释（description 不参与执行）
```

### 自包含检查

```
① 步骤提到的文件/工具有路径或获取方式
② 术语有定义（或指向 references）
③ 不假设"读者知道"（Agent 第一次执行）
```

### 与渐进式披露的配合

```
正文保持精简（≤500 行）：
细节放 references/（L3 按需加载）
正文里给出"路由列表"（什么时候读哪个参考）
```

## 5. 错误处理与输出规范

### 错误处理表

```markdown
## 错误处理
| 情况 | 处理 |
|---|---|
| 模板文件不存在 | 提示并创建最小模板 |
| 命令执行失败 | 报告错误并给出修复建议 |
| 输入不完整 | 询问缺失信息 |
```

### 输出规范

```markdown
## 输出
- 问题清单（按严重级别排序）
- 每个问题附：位置 + 原因 + 建议
- 无问题时明确说"未发现问题"
```

### 输出设计要点

```
① 明确"最终输出长什么样"（Agent 知道交什么）
② 结构化（清单/表格）优于散文
③ 包含"无问题"分支（防空输出）
```

## 6. 正文检查清单

| 项 | 检查 |
|---|---|
| 概述 | 有（做什么/何时用） |
| 步骤/规则 | 有（声明式优先） |
| 输出格式 | 有（明确交付物） |
| 自包含 | 步骤可独立执行 |
| 正面指令 | 无"不要做"式反模式 |
| 行数 | ≤500（细节拆 references） |
| 错误处理 | 有（视复杂度） |
| 示例 | 有（推荐） |

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 正文七部分？ | 概述/前置/步骤/输出/错误/示例/资源 |
| 声明式 vs 程序式？ | bullet 规则默认，编号只用于严格顺序 |
| 步骤上限？ | 10-15 步（超出拆子流程） |
| 自包含？ | 正文加载后可独立执行 |
| 错误怎么写？ | 错误处理表（情况→处理） |
| 正面指令？ | 规则写"该怎么做"而非"不要做" |

### 面试加分表达

> "正文编写我遵循三个原则：声明式优先（bullet 规则比编号步骤可靠，编号只给严格顺序任务且限 10-15 步）、自包含（正文加载后能独立执行）、正面指令（写'该怎么做'而不是'不要做'）。错误处理写成表（情况→处理），输出必须明确格式和'无问题'分支——正文是执行手册，可靠比华丽重要。"

> 🎯 核心要点：七部分结构（最小=概述+步骤+输出）；声明式优先（bullet > 编号，编号限 10-15 步）；自包含（L2 后可独立执行）；错误处理表 + 输出规范（含无问题分支）；正面指令；≤500 行拆 references（路由列表）；检查清单八项。

## 8. 常见误区

| 误区 | 真相 |
|---|---|
| "正文越长越专业" | 500 行上限——长是负担 |
| "所有步骤都编号" | 声明式优先（编号给严格顺序） |
| "错误处理可省" | 异常输入无兜底 = 执行失败 |
| "示例是装饰" | 示例是"输入→输出"的最快理解 |
| "正文写给人类看" | 写给 Agent 执行——具体可执行 |

## 9. 正文质量自检法

### 三读自检

```
第一读：站在 Agent 角度（能执行吗？）
  → 步骤具体？文件路径明确？输出格式清楚？
第二读：站在用户角度（结果对吗？）
  → 输出符合需求？错误有兜底？
第三读：站在维护角度（好改吗？）
  → 规则集中？无重复矛盾？版本可追溯？
```

### 与 description 的分工

```
description：说"什么时候该用"（匹配）
正文：说"怎么执行"（执行手册）
两者分工明确：
- description 写触发场景（03 篇）
- 正文写执行细节（本篇）
别在 description 里写步骤、也别在正文里重复触发场景
```

| 是否声明式优先 | ______ |
