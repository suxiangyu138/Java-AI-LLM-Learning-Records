## 1. 三个可选目录的分工

| 目录 | 装什么 | 定位 |
|---|---|---|
| scripts/ | 可执行代码（Python/Shell 等） | **确定性**（交给代码） |
| references/ | 详细文档/参考资料 | **知识**（按需加载） |
| assets/ | 模板/资源/schema | **素材**（复用填充） |

```
SKILL.md：判断力（流程、规则、决策）
scripts/：确定性（重复、脆弱、易错的操作）
references/：深度（细节、边界情况、背景）
assets/：模板（可填充的骨架）
```

### 一句话分工

```
会变化的 → scripts（代码）
要细读的 → references（资料）
要复用的 → assets（模板）
要判断的 → SKILL.md（正文）
```

## 2. 何时用哪个目录

### scripts 的触发条件（官方实践）

```
任何脆弱、重复、变化即 bug 的操作 → 写成脚本：
① 字段抽取（解析比逐字段生成稳定）
② 数据转换（固定规则）
③ 验证检查（重复执行）
④ 脚手架生成（固定结构）
```

### references 的触发条件

```
① 边界情况细节（正文放不下）
② 深度背景（不需要每次读）
③ 大表格/长列表（正文太占）
④ 具体操作手册（--help 模式）
```

### assets 的触发条件

```
① 文档模板（生成时填充）
② schema（结构化输出）
③ 示例资源（参考结构）
④ 图标/图片（展示用）
```

## 3. 扁平布局与目录深度

### 扁平布局（官方允许）

```
规范允许完全扁平布局：
my-skill/
├── SKILL.md
├── script.py        # 可以直接放根目录？规范允许
├── reference.md
└── template.md
——验证器不应惩罚扁平结构
```

### 目录深度建议

```
references/ 保持一层深度：
✅ SKILL.md → references/edge-cases.md
❌ SKILL.md → advanced.md → details.md（链式嵌套）

为什么：Agent 可能只部分预览嵌套文件（深层文件易被跳过）
```

### 选择：扁平 vs 目录

| 布局 | 适用 |
|---|---|
| 扁平 | 文件少（3-5 个） |
| scripts/references/assets | 文件多（组织清晰） |

## 4. 拆分决策树

```
这段内容放哪？
├─ 是"执行逻辑"（重复/脆弱/易错）？
│   ├─ 是 → scripts/（写脚本）
│   └─ 否 ↓
├─ 是"细节知识"（边界/背景/长文档）？
│   ├─ 是 → references/（按需加载）
│   └─ 否 ↓
├─ 是"可复用模板"（骨架/格式）？
│   ├─ 是 → assets/
│   └─ 否 ↓
└─ 留在 SKILL.md（判断力/流程/规则）
```

### 拆分红线

```
SKILL.md 保持 ≤500 行：
接近上限 → 拆（scripts/references/assets）
正文只留"必须每次读"的内容
```

## 5. 多文件技能示例

```
doc-generator/
├── SKILL.md                    # 流程、规则、决策
├── scripts/
│   ├── check_links.py          # 校验内部链接（确定性）
│   └── validate_anchors.py     # 校验锚点（确定性）
├── references/
│   ├── 写作风格指南.md          # 深度规范（需要时读）
│   └── 常见错误.md              # 边界情况（输出差时读）
└── assets/
    ├── templates/
    │   ├── 知识体系模板.md       # 生成时填充
    │   └── 单篇笔记模板.md
    └── schema/
        └── doc_meta.json        # 元数据 schema
```

### 示例解读

```
SKILL.md：说"生成文档 + 校验"（判断）
scripts/：校验是确定性操作（重复易错 → 代码）
references/：风格细节（不需要每次读）
assets/：模板（每次生成填充）
```

### 拆分顺序建议

```
① 先列出所有内容（逐条清单）
② 确定性操作 → scripts（写脚本）
③ 长文档/边界 → references（按主题拆）
④ 骨架/格式 → assets（参数化）
⑤ 判断力留 SKILL.md
⑥ 每拆一步跑回归（功能不退化）
——一次拆一个，别一次大动
```

## 6. 常见误区

| 误区 | 真相 |
|---|---|
| "目录越多越专业" | 文件少用扁平（规范允许） |
| "所有逻辑写脚本" | 判断力留 SKILL.md（脚本只做确定性） |
| "references 随便嵌套" | 一层深度（防跳过） |
| "assets 可省" | 模板是复用核心（参数化） |
| "SKILL.md 越长越好" | 500 行红线——拆！ |

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 三个目录分工？ | scripts 确定性/references 知识/assets 素材 |
| 何时写脚本？ | 脆弱/重复/易错操作 |
| 扁平布局可以吗？ | 可以（规范允许，验证器不惩罚） |
| references 深度？ | 一层（链式嵌套易被跳过） |
| 拆分红线？ | SKILL.md ≤500 行 |
| 一句话分工？ | 变化进 scripts/细读进 references/复用进 assets/判断留正文 |

### 面试加分表达

> "多文件结构的核心是'SKILL.md 留判断力，其他交给文件'：确定性操作（解析/转换/校验）写进 scripts——比逐字段生成稳定；细节知识进 references 按需加载（JIT 指针）；模板进 assets 参数化复用。references 保持一层深度，链式嵌套 Agent 会跳过。红线是 SKILL.md ≤500 行，接近上限就拆。"

> 🎯 核心要点：三目录分工（scripts 确定性/references 知识/assets 素材）；触发条件各三；扁平布局允许（文件少时）；references 一层深度（防跳过）；拆分决策树 + 500 行红线；示例结构（校验进 scripts/风格进 references/模板进 assets）；一句话分工（变化进 scripts/细读进 references/复用进 assets/判断留正文）。
