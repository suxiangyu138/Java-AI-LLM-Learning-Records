## 1. 为什么需要可重复评估

### 问题

```
技能改没改好？——"感觉"不可靠：
改 description 触发率升了吗？
改正文质量真的变了吗？
——没有对比数据，迭代是盲改
```

### 可重复评估的价值

```
① 对比：with-skill vs baseline（有没有用）
② 回归：新版本 vs 旧版本（改没改坏）
③ 量化：pass rate/耗时/token（数据说话）
——从"玄学迭代"到"数据驱动"
```

### 2026 转折

```
skill-creator 重做（2026-03，"Claude Skills 2.0"）：
核心解决：Skill 缺少可重复评估的问题
```

## 2. 对比评估方法（skill-creator 2.0）

### 核心机制

```
① 准备 2-5 条真实测试 prompt
② 每条分别运行：with-skill vs baseline
③ 聚合指标：pass rate/耗时/token（均值 + 标准差）
④ 浏览器 eval viewer 并排展示
```

### baseline 的两种形态

| 场景 | baseline |
|---|---|
| 新建技能 | 不加载任何技能的裸 Claude |
| 迭代技能 | 旧版本快照（skill-snapshot/） |

```
快照的意义：每轮可见"比上一版进步多少"
（回归测试的量化版）
```

### 断言策略

| 任务类型 | 评估方式 |
|---|---|
| 确定性任务（转换/抽取/代码） | 写断言（自动判 pass） |
| 主观任务（写作风格） | 人工审阅 |

```
可确定性验证的 → 写成脚本（跨 iteration 复用）
```

## 3. 技能评分体系（skill-test-skill）

### 六维 100 分

| 维度 | 分值 | 检查 |
|---|---|---|
| 目录结构 | 10 | 布局合规 |
| frontmatter 合规性 | 30 | 字段/语法/约束 |
| 正文内容质量 | 25 | 结构/自包含/指令 |
| 渐进式披露设计 | 15 | 拆分/加载控制 |
| 可选目录质量 | 10 | scripts/references/assets |
| 描述触发优化 | 10 | description 有效性 |

### 等级划分

| 分数 | 等级 |
|---|---|
| 90-100 | 生产就绪 |
| 75-89 | 良好 |
| 60-74 | 可接受 |
| 40-59 | 需重大返工 |
| 0-39 | 需重写 |

```
评分工具价值：客观基线（对着规范逐项查）
支持中英文输出
```

## 4. skilltest CLI 工具

### 三个命令

| 命令 | 功能 |
|---|---|
| eval | 运行评估（工具响应 mock，不真实执行） |
| check | lint + trigger + eval（质量门） |
| improve | 重写 SKILL.md 后在冻结测试集验证 |

### eval 的特点

```
工具响应全部 mock（不执行真实工具/脚本/shell/MCP）
支持 grader：tool_called / tool_not_called / tool_argument_match
——安全评估（不产生副作用）
```

### check 的质量门

```
默认阈值：
--min-f1 0.8（触发 F1）
--min-assert-pass-rate 0.9（断言通过率）
——低于阈值 = 不通过
```

### improve 的纪律

```
重写后 → 冻结测试集验证 → 有可衡量改进才写入
（默认 dry-run——不直接覆盖）
——改坏了不落盘（安全迭代）
```

## 5. 验证循环

### 核心循环

```
verify → fix → re-verify
（验证 → 修复 → 再验证）
```

### 各类型技能的验证

| 技能类型 | 交付前验证 |
|---|---|
| 文档类 | 视觉 QA（渲染检查） |
| 代码类 | 测试通过 + 零类型错误 |
| 数据类 | schema 验证（输出前） |

### 发布前流程

```
① 质量检查清单（评分 ≥ 门槛）
② 冒烟测试（安装后跑通）
③ 评估与迭代（对比数据）
④ 版本化（version 递增）
```

## 6. 质量维度与阈值

### 核心质量维度

| 维度 | 指标 | 阈值参考 |
|---|---|---|
| 触发 | F1（触发准确率） | ≥0.8 |
| 执行 | 断言通过率 | ≥0.9 |
| 效率 | token/耗时 | 对比 baseline |
| 合规 | 规范评分 | ≥75（良好） |

### 质量门的组合

```
skilltest check = lint（规范） + trigger（触发）+ eval（执行）
——三维一体，一票否决
```

### 阈值设定

```
① 从 baseline 起步（先测再定）
② 按任务脆弱性调整（越关键越严）
③ 持续迭代（每版收紧）
```

## 7. 常见误区

| 误区 | 真相 |
|---|---|
| "评估可省" | 没有数据 = 盲改（玄学迭代） |
| "一次评估够" | 要对比（with/baseline）+ 回归（新旧） |
| "主观任务不评估" | 人工审阅也是评估（记录） |
| "评分高 = 好用" | 规范分 + 功能分都要（trigger/eval） |
| "improve 直接覆盖" | dry-run + 有改进才写 |

## 8. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 为什么可重复评估？ | 对比/回归/量化（数据说话） |
| 对比评估怎么做？ | 2-5 测试 prompt × with/baseline |
| baseline 是什么？ | 裸 Claude 或旧版本快照 |
| 评分体系？ | 六维 100 分（frontmatter 30 最大） |
| skilltest？ | eval/check/improve（mock + 质量门） |
| 验证循环？ | verify → fix → re-verify |

### 面试加分表达

> "2026 年技能质量评估的工具链成熟了：skill-creator 2.0 做可重复对比评估（2-5 条真实 prompt × with-skill vs baseline，聚合 pass rate/耗时/token，迭代时旧版快照作 baseline 看每轮进步）；skill-test-skill 给规范分（六维 100 分）；skilltest CLI 的 check 是质量门（F1≥0.8 + 断言通过率≥0.9，工具响应 mock 无副作用）。验证循环 verify→fix→re-verify 是最大质量提升手段。"

> 🎯 核心要点：可重复评估（对比/回归/量化）；skill-creator 2.0（with vs baseline、快照、断言策略）；skill-test-skill 六维 100 分（90+ 生产就绪）；skilltest（eval mock/check 质量门/improve dry-run）；验证循环 verify→fix→re-verify；质量门（F1≥0.8/断言≥0.9）。
