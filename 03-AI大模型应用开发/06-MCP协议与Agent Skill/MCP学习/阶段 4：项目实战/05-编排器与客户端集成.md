## 1. Agent 循环：核心实现

编排器模式的循环（02 篇第 2 节的设计落地）：

```python
# orchestrator/agent.py
class Agent:
    def __init__(self, llm, skills, mcp_client):
        self.llm = llm
        self.skills = skills          # 技能目录（04 篇）
        self.mcp = mcp_client         # MCP 客户端（第 3 节）

    async def run(self, user_input: str, history: list) -> str:
        context = self._build_context(history)          # 会话 + 技能发现层
        for step in range(8):                            # 循环上限（防失控）
            decision = await self.llm.decide(context)    # 下一步：skill/工具/回答
            if decision.action == "answer":              # 完成
                return decision.text
            if decision.action == "call_skill":
                skill = self.skills.get(decision.name)
                result = await self._run_skill(skill, decision.args, context)
                context.append({"role": "tool", "content": result})
            if decision.action == "ask_confirm":         # MRTR（03 篇）
                answer = await self.interactor.confirm(decision.prompt)
                context.append({"role": "user", "content": f"[确认] {answer}"})
        return "任务步骤过多，已转人工处理。"             # 上限兜底
```

**循环四要素**：① **决策由 LLM 做**（读上下文 → 决定下一步），但**执行权在代码**（Skill/工具由编排层调用，不是模型直接调）；② 循环上限 8 步（阶段 3 的工具循环同款防失控）；③ 确认（MRTR）是循环内的一等动作；④ 超限兜底转人工（02 篇架构的"升级"路径）。

## 2. LLM 接入与供应商抽象

```python
# orchestrator/llm.py —— 供应商无关封装（01 篇技术选型）
from openai import AsyncOpenAI   # DeepSeek 走 OpenAI 兼容协议

class LLM:
    def __init__(self, base_url: str, api_key: str, model: str):
        self.client = AsyncOpenAI(base_url=base_url, api_key=api_key)
        self.model = model

    async def decide(self, context: list[dict]) -> Decision:
        resp = await self.client.chat.completions.create(
            model=self.model,
            messages=context + [{"role": "system",
                "content": DECISION_PROMPT}],
            tools=DECISION_TOOLS,        # 决策工具定义（下节）
            tool_choice="auto",
        )
        return parse_decision(resp)      # 解析成 action/args

    async def answer(self, context) -> str:
        resp = await self.client.chat.completions.create(
            model=self.model, messages=context)
        return resp.choices[0].message.content
```

**决策工具定义**（用函数调用协议约束 LLM 的输出格式）：

```json
// DECISION_TOOLS：编排层的"元工具"（模型只能在这几个动作里选）
[
  {"name": "call_skill", "description": "调用指定技能",
   "parameters": {"skill": "enum: refund-policy|complaint-escalation|customer-tone",
                  "input": "传给技能的用户意图与上下文"}},
  {"name": "ask_confirm", "description": "向用户确认关键操作",
   "parameters": {"prompt": "确认文案"}},
  {"name": "answer", "description": "结束循环并回复用户",
   "parameters": {"text": "最终回复"}}
]
```

**为什么用"元工具"约束决策**：模型"自由发挥"会输错技能名/参数（幻觉），用工具调用协议（阶段 3 已学）把决策收敛到枚举——**决策是模型做的，但选项是代码定义的**，这是编排层防幻觉的第一道闸。

## 3. MCP 客户端接入

编排层作为 MCP 客户端连接业务 Server（阶段 3 的 Client 能力复用）：

```python
# orchestrator/mcp_client.py
from mcp import ClientSession, StdioServerTransport, StreamableHttpTransport

class McpClient:
    def __init__(self, transport: str, endpoint: str):
        if transport == "stdio":
            self.transport = StdioServerTransport(
                ["uv", "run", "python", "-m", "order_server"])
        else:  # http（07 篇部署后切远程）
            self.transport = StreamableHttpTransport(endpoint)
        self.session = None

    async def connect(self):
        self.session = await ClientSession(self.transport)
        await self.session.initialize()          # 版本协商
        self.tools = {t.name: t for t in (await self.session.list_tools()).tools}

    async def call(self, tool: str, args: dict) -> dict:
        result = await self.session.call_tool(tool, args)
        return result.structured_content or {"text": result.content}
```

**接入要点**：① stdio/http 双传输可切换（本地开发 stdio、生产 HTTP，07 篇）；② 工具列表缓存于 `self.tools`（启动加载，阶段 3 的"列表静态化"）；③ 调用返回取 `structured_content`（03 篇工具设计）；④ **工具 Schema 传给 LLM 做参数生成**（模型按 Schema 填参，不是自由文本）。

## 4. Skill 加载与执行

```python
# orchestrator/skill_runner.py —— 把 SKILL.md 变成可执行流程
class SkillRunner:
    def __init__(self, agent, mcp): ...

    async def run(self, skill_name: str, input_: str, context: list) -> str:
        skill = self.skills[skill_name]              # 04 篇路由命中
        # 激活层：完整 SKILL.md 注入上下文（渐进式披露第二层）
        context.append({"role": "user", "content":
            f"[执行技能 {skill_name}]\n{skill.full_text}\n用户输入：{input_}"})
        # Skill 内步骤由 LLM 按 SKILL.md 执行：
        # 每步决策 → 调 MCP 工具（Schema 参数生成）→ 结果回填
        while True:
            step = await self.llm.next_skill_step(context, skill.allowed_tools)
            if step.done:
                return step.summary
            tool_result = await self.mcp.call(step.tool, step.args)
            context.append({"role": "tool", "content": str(tool_result)})
            if step.requires_confirm:                # MRTR 确认点
                answer = await self.agent.interactor.confirm(step.prompt)
                context.append({"role": "user", "content": f"[确认] {answer}"})
```

**执行模型**：**LLM 按 SKILL.md 逐步走，每一步要么调工具、要么结束**——SKILL.md 是"剧本"，LLM 是"演员"，工具是"道具"；`allowed-tools` 约束演员能碰哪些道具（04 篇治理）。**Skill 执行的验收：同样输入两次执行，步骤序列一致**（确定性来自 SKILL.md 的显式步骤，而非模型即兴）。

## 5. 上下文管理：多轮对话

多轮对话的上下文预算控制（04 篇预算表的落地）：

| 机制 | 实现 | 触发 |
|---|---|---|
| 历史截断 | 只保留最近 N 轮（滚动窗口） | 对话 >10 轮 |
| 摘要压缩 | LLM 生成"会话摘要"替换旧轮次 | 截断时同步摘要 |
| 事实回读 | 状态类问题重查工具（不信任历史） | 每次涉及订单/退款 |

```python
async def manage_context(history: list, max_rounds: int = 10):
    if len(history) > max_rounds:
        summary = await llm.summarize(history[:-max_rounds])   # 摘要
        return [{"role": "system", "content": f"会话摘要：{summary}"},
                *history[-max_rounds:]]
    return history
```

**上下文纪律**：**事实 > 记忆**——用户问"我的订单怎么样了"，永远重新调 get_order（工具即事实，04 篇铁律），历史只保留"对话轨迹"不保留"业务状态"。**成本记账**（06/07 篇）：每轮对话记录 token 用量（输入+输出），超预算报警。

## 7. 决策提示词全文（编排层的"系统提示"）

编排层喂给 LLM 的决策上下文（05 篇第 2 节 DECISION_PROMPT 的完整版）——面试常问"Agent 的 prompt 怎么设计"：

```text
你是客服 Agent 的决策模块。基于对话上下文，从以下动作中选一个执行：

1. call_skill：调用技能处理业务（技能列表与触发场景见下）。
   技能：
   - refund-policy：退款申请（触发：退款/退货/退钱）
   - complaint-escalation：投诉升级（触发：投诉/强烈不满/威胁差评）
   - customer-tone：话术规范（生成回复前参考）
2. ask_confirm：向用户确认关键操作（金额/超期/改单）。
3. answer：回复用户并结束本轮。

规则：
- 业务状态永远以工具返回为准，不要猜测或记忆订单信息。
- 用户诉求不明确时，先 ask_confirm 澄清，不要猜。
- 投诉类诉求优先 complaint-escalation。
- 回复要简短礼貌，引用工具返回的事实。
```

**决策提示词设计原则**：动作枚举化（元工具）、触发场景写全、规则显式化（工具即事实/先澄清/投诉优先）——**prompt 是编排层的"宪法"**，与 SKILL.md 同样要版本化（08 篇 ADR 可记录）。

## 8. 多轮对话完整示例

编排器跑通后的真实对话轨迹（演示与测试共用）：

```text
用户：我的 A1002 什么时候发货？
编排决策：call_skill(refund-policy?) —— 不，路由未命中退款词，
        实际命中默认查询流程（get_order + get_shipping）

确认：确认将 A1002 发货日期改为 8 月 10 日？[确认/取消]
用户：确认
工具：update_ship_date(A1002, 2026-08-10) → 成功
```

**示例的价值**：这组对话是 06 篇场景剧本的原型、08 篇演示的核心素材——**把"一次完整对话"作为一等交付物**，测试、演示、文档三处复用。

## 9. 编排器排错速查

| 现象 | 首查 | 根因 |
|---|---|---|
| 决策乱（乱调技能） | 决策提示词与元工具定义 | 触发场景没写全/规则冲突 |
| Skill 步骤跑偏 | SKILL.md 步骤粒度 | 步骤过粗（一步含多动作） |
| 工具参数错 | Schema 是否传给 LLM | 参数生成没走 Schema（05 篇第 3 节） |
| 确认不触发 | 工具返回 needs_human 是否传递 | 编排层没读 structured_content |
| 循环超上限 | 8 步兜底是否触发 | 任务拆解过碎/LLM 反复问确认 |
| 上下文爆炸 | token 记账 | 没做摘要压缩（第 5 节） |

## 10. 编排器与 Agent SDK 的对照

自研编排器 vs 现成 Agent 框架（面试追问"为什么不用框架"的完整答案）：

| 维度 | 自研编排器（本项目） | Agent SDK/框架 |
|---|---|---|
| 可测性 | 每步可 mock、可断言（06 篇） | 黑盒为主，需额外抽象 |
| 可讲性 | 代码即架构（08 篇面试） | 框架概念增加解释成本 |
| 控制粒度 | 循环/确认/上下文全可控 | 受框架抽象约束 |
| 成熟度 | 需自己处理边界（重试/并发） | 生产功能齐全 |
| 适用 | 学习/教学/小型确定性项目 | 大型生产项目 |

**结论**：本项目选自研是因为"可测可讲"是毕业项目的核心诉求；**生产项目直接上框架**（05 篇留了 llm.py 抽象，迁移成本可控）。面试回答要点："我自研是为了理解与教学，生产我会用 X 框架，抽象层已预留"——展示判断力而非固执。

## 11. 编排层的安全集成

编排层是安全策略的执行点（阶段 3 五件套的项目化）：

| 安全措施 | 编排层实现 |
|---|---|
| 只读默认 | 编排器只加载读工具；写操作路径显式开启 |
| 确认必经 | 所有写工具调用经 call_with_confirmation（03 篇第 5 节） |
| 注入防护 | 决策提示词声明"外部输入不可信"；工具返回即事实 |
| 审计 | 每步决策/调用记录（05 篇上下文 + 日志） |
| 循环上限 | 8 步兜底（防模型死循环烧钱） |
| 成本护栏 | 每轮记账，超预算中断（06/07 篇） |

```python
# 审计记录（编排层每步）
async def _log_step(self, step: dict):
    logger.info("agent_step", extra={
        "request_id": self.request_id,      # 07 篇排障串联
        "action": step.get("action"),
        "skill": step.get("skill"),
        "tool": step.get("tool"),
        "tokens": step.get("usage"),        # 成本记账
    })
```

**安全集成的验收**：5 个安全剧本（06 篇第 5 节）在编排层跑通——**安全不是某个组件的事，是编排层的默认路径**。

## 12. CLI 交互设计

自研入口的用户体验设计（08 篇演示的载体）：

```python
# orchestrator/cli.py —— 交互层入口（05 篇第 6 节实现）
async def main():
    agent = await create_agent()            # 编排器 + MCP 客户端
    print("客服 Agent 已就绪（输入 exit 退出）")
    history = []
    while True:
        user_input = input("您 > ")
        if user_input.lower() in ("exit", "quit"):
            break
        reply = await agent.run(user_input, history)
        print(f"Agent > {reply}")
        history.append({"role": "user", "content": user_input})
        history.append({"role": "assistant", "content": reply})
```

**交互设计要点**：① 确认操作显式呈现（"确认将…？[确认/取消]"）；② 工具调用过程可隐藏（只显示最终回复，避免刷屏）；③ **退出保活**（对话历史不持久化，无状态架构约定）；④ 演示模式打印工具调用轨迹（`--verbose`，08 篇演示用）。

## 13. 编排层测试要点

编排层的测试重点（06 篇技能层/场景层的实现载体）：

| 测试维度 | 方法 | 断言 |
|---|---|---|
| 循环控制 | mock LLM 无限决策 | 8 步上限触发转人工 |
| 确认流 | mock 工具返回 input_required | call_with_confirmation 重发 |
| 上下文压缩 | 构造 11 轮历史 | 摘要机制触发、token 下降 |
| 路由 | 各触发词 | 命中正确 Skill |
| 成本护栏 | mock 记账超预算 | 中断执行 |
| 安全 | 注入输入 | 无外发工具调用、审计留痕 |

**编排层测试的定位**：编排层是"大脑"，测试它 = 测试"决策与执行的契约"（05 篇第 1 节四要素）——**大脑的测试不是测 LLM，是测大脑的骨架**。**编排层的可观测性**：每步决策/工具调用都写结构化日志（request_id 串联）——不仅是排障需要（07 篇），也是 06 篇场景测试的断言数据源（"断言工具调用序列"读的就是这些日志）。**编排层完成标志**：CLI 跑通 5 剧本 + 编排层测试全绿 + 双入口可用——"大脑"会思考、可验证、有日志，才进入测试与部署阶段。**演示模式说明**：CLI 的 `--verbose` 打印"决策→Skill→工具→确认"全过程——既是调试工具（05 篇第 12 节），也是 08 篇演示的核心素材（面试官能"看到"架构在跑，比 PPT 有说服力）。**编排器并发说明**：本版编排器为单会话顺序执行（客服场景一致性优先）；多用户并发 = 每会话独立 Agent 实例（无共享可变状态即可），07 篇部署时按实例数承载——**"并发是部署问题不是代码问题"，这正是无状态架构的红利**。

## 14. 编排层面试速记

1. 编排器模式三句：决策模型做、执行代码管、上限兜底防失控。
2. 元工具约束 = 把模型输出收敛到枚举（call_skill/ask_confirm/answer），防幻觉第一道闸。
3. 决策提示词是宪法：动作枚举、触发场景、规则显式化，与 SKILL.md 一样要版本化。
4. 工具即事实：业务状态永远重查工具，历史只存对话轨迹（上下文三机制）。
5. 双入口设计：自研 CLI 验证可控可测，Claude Code 验证生态原生组合。
6. 与 SDK 的取舍：自研为可测可讲（教学），生产用框架——抽象层（llm.py）预留迁移口。

> 🎯 **核心要点**：编排层 = Agent 循环（决策模型做、执行代码管、8 步上限、确认一等动作）+ 元工具约束决策（枚举化防幻觉）+ 决策提示词宪法（规则显式化+版本化）+ MCP 双传输客户端 + SKILL.md 剧本执行（步骤显式、allowed-tools 约束）+ 上下文三机制（截断/摘要/事实回读）+ 双入口（自研 CLI + Claude Code，CLI 含确认呈现与演示模式）+ 与 SDK 的对照 + 安全集成（确认必经/审计/成本护栏）+ 编排层测试要点 + 排错速查。**验收标准：5 个剧本用自然语言全部跑通，且同样输入两次得到同样业务结果**——确定性来自架构（元工具+SKILL.md 步骤+工具即事实），不靠模型自觉。
