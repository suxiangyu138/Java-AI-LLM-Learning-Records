## 1. Skill 设计：流程与知识的拆分

**Skill = 流程（怎么做）+ 知识（什么是什么）**，与 MCP 工具的分工（阶段 3 第 8 节、01 篇映射矩阵）：

| 能力 | 放 Skill | 放 MCP 工具 |
|---|---|---|
| 多步协调 | 退款判断流程（查单→对政策→决定→执行） | — |
| 领域知识 | 7 天政策、超期规则、金额门槛 | — |
| 原子操作 | — | get_order / refund_order |
| 状态变更 | — | 写工具（带确认） |

**拆分原则**：**可复用的原子操作进工具，业务特有的协调进 Skill**——同一个退款工具可以被"用户自助退款"和"客服代退款"两个 Skill 共用；同一个政策知识可以被多个场景引用。**工具是库（可组合），Skill 是程序（可编排）**——这是 2026 双体系协作的核心心智。

**本项目的三个 Skill 设计**：

| Skill | 职责 | 调用的工具 | 输入 | 输出 |
|---|---|---|---|---|
| refund-policy | 退款判断与执行 | get_order → refund_order → notify | 订单号+原因 | 回执/人工审核标记 |
| complaint-escalation | 投诉升级判定 | get_order → create_ticket → notify | 会话记录 | 工单号 |
| customer-tone | 客服话术规范 | （无工具，纯知识） | 场景+语气 | 回复文案 |

## 2. SKILL.md 规范落地

2026 年 Agent Skill 开放标准（与 `Agent Skill学习/阶段 1-2` 完全一致）：

```markdown
---
name: refund-policy
description: 处理用户退款申请：校验订单状态与退款政策（7 天无理由、金额门槛），
  调用退款工具并生成回执。当用户提到"退款/退货/退钱/不想要了"时使用。
allowed-tools: [get_order, refund_order, notify]
user-invocable: false
---

# 退款处理流程

## 第一步：查询订单（必须）
1. 调用 `get_order(order_id=<用户提供的订单号>)`。
2. 若返回 NOT_FOUND：直接回复"未查询到该订单"，流程结束（不要编造订单）。
3. 若返回 CONFLICT（未支付/已退款）：按返回信息回复，流程结束。

## 第二步：政策校验（依据本技能知识，不依赖模型记忆）
- 已支付且 ≤7 天：无条件受理。
- 已支付且 >7 天：按"超期审核"处理（需人工确认）。
- 金额 >500 元：无论天数，需人工确认。

## 第三步：执行退款
1. 调用 `refund_order(order_id=<订单号>, reason=<用户原因>)`。
2. 返回中 `needs_human=true` → 向用户确认后继续；false → 直接继续。
3. 调用 `notify(user_id=<订单用户>, message=<回执文案>)`。

## 第四步：回执
按"退款受理，单号 X，预计 Y"格式回复；需人工时回复"已提交人工审核"。
```

**SKILL.md 四要素**（对照标准）：frontmatter（name 与目录同名、description 是激活开关、allowed-tools 治理）、步骤显式化（每步写"调用什么工具、失败怎么办"）、**知识写进文件**（政策规则在 Skill 里，不在模型记忆里）、**工具即事实**（"不要编造订单"是铁律）。

## 3. 技能一：退款政策 refund-policy

**设计要点**（对应 01 篇映射矩阵 F4 与场景 C）：

1. **政策知识外置**：7 天/500 元规则写在 SKILL.md，改政策只改文件不改代码——这是"Skill 是程序"的治理红利（合规部门可以直接审 SKILL.md）；
2. **失败路径全覆盖**：每个工具调用都写了"返回什么错误码 → 怎么回复"（NOT_FOUND/CONFLICT/超期），**Skill 的健壮性 = 每个分支都有答复**；
3. **确认点按工具返回驱动**：`needs_human` 来自工具（03 篇设计），Skill 只决定"怎么问"；
4. **回执模板在 Skill**：文案与业务规则绑定（"预计 3-5 个工作日到账"），工具 notify 不碰内容（03 篇职责分离）。

**验收剧本**（06 篇直接消费）：A1001（已发货不可退款）、A1003（超期+大额需人工）、A1004（正常退款）、不存在的单、重复退款（CONFLICT）。

## 4. 技能二：投诉升级 complaint-escalation

```markdown
---
name: complaint-escalation
description: 处理用户投诉与不满：按严重程度判定是否升级人工工单。
  当用户表达强烈不满、威胁差评、多次重复同一诉求、涉及人身攻击时使用。
allowed-tools: [get_order, create_ticket, notify]
---

# 投诉升级流程

## 第一步：情绪判定（本技能知识）
- 程度 1（一般不满）：重复诉求 ≥2 次 或 语气强烈
- 程度 2（严重）：威胁差评/投诉平台/媒体 或 涉及安全与人身
- 程度 3（高危）：涉及资金安全、人身安全、法律诉求

## 第二步：按程度分流
- 程度 1：安抚话术（引用 customer-tone）+ 复述解决方案，流程结束。
- 程度 2/3：创建工单 `create_ticket(order_id, level, 摘要)` → 返回工单号。
  → 通知 `notify(user_id, "已升级人工客服，工单号 X")`。

## 第三步：升级后行为
- 升级后不再承诺结果（"工单已转人工，由专员处理"）。
- 全程记录：会话摘要写进工单（编排层从上下文提取）。
```

**设计要点**：① 情绪判定标准显式化（"≥2 次/威胁差评"是可执行的规则，不是感觉）；② **升级即止语**（升级后不再承诺，防模型越权承诺赔偿）；③ 依赖 `customer-tone` 技能（技能间协作——Skill 链的雏形，05 篇编排层实现）。

## 5. 技能三：客服话术 customer-tone

**纯知识型技能**（不调工具），为回复文案提供规范：

```markdown
---
name: customer-tone
description: 客服回复话术规范：礼貌语气、结构模板、禁忌用语。
  生成任何用户可见回复文案时参考本技能。
allowed-tools: []
---

# 客服话术规范

## 语气三原则
1. 先共情后解决（"理解您的情况"先于"您可以这样做"）。
2. 具体承诺用事实（引用工具返回），模糊承诺禁止（"大概""应该"）。
3. 错误归己（"我们的系统未查到"不写"您提供的信息不对"）。

## 回复结构
1. 确认理解（复述用户诉求）
2. 行动说明（做了什么/正在做什么）
3. 结果与后续（回执/预计时间/工单号）

## 禁忌用语
- 禁止："这不归我们管""您自己看订单详情""按规定就是这样"
- 禁止承诺：赔偿金额、到货时间、处理时限（除非工具返回确认）
```

**设计要点**：① `allowed-tools: []` 声明纯知识（治理透明）；② 与退款/升级 Skill 链式使用（"安抚话术引用 customer-tone"）；③ **禁忌用语即安全规则**——"禁止承诺"是防模型乱承诺赔偿的护栏（客服场景的核心风险）。

## 6. 渐进式披露与 token 预算

2026 标准的三层加载（`Agent Skill学习/阶段 1` 详述），本项目落实：

| 层 | 加载时机 | 内容 | token 成本 |
|---|---|---|---|
| 发现 | 编排层启动 | 全部 Skill 的 name+description | ~100/Skill |
| 激活 | 任务命中描述 | 完整 SKILL.md | <5000/Skill |
| 按需 | 步骤执行 | references/scripts（本项目暂不需要） | 按需 |

**token 预算表**（本项目实测目标）：

| 场景 | 预算 | 说明 |
|---|---|---|
| 5 个 Skill 描述常驻 | ~500 token | 启动即加载（发现层） |
| 单任务激活 Skill | ~3000-5000 token | 完整 SKILL.md |
| MCP 工具列表 | ~2000 token/Server | 6 个工具（阶段 3 的 5-7 原则） |
| 对话上下文 | 按轮增长 | 05 篇做摘要压缩 |

**预算纪律**：① Skill 文件 ≤500 行（超出拆 references）；② 描述写触发场景不写内容摘要（激活开关语义）；③ 工具数保持 6 个（不膨胀）；④ **对话超 10 轮做上下文摘要**（05 篇）——与阶段 3 的"工具列表 token 降 99.9%"（code mode）同理，上下文预算决定项目能跑多长。

## 7. 技能路由：从关键词到语义

**路由两档**（01 篇技术选型：先关键词，规模大了再嵌入）：

| 档位 | 机制 | 准确率 | 成本 | 本项目 |
|---|---|---|---|---|
| 关键词 | description 与用户输入的关键词/子串匹配 | 够用（5 个技能） | 零 | ★ 采用 |
| 语义嵌入 | 描述与输入向量化 → top-1 相似度 | 93.8%（2026 实测）vs 关键词 77.1% | 嵌入 API 调用 | 技能 >10 个时升级 |

```python
# orchestrator/skill_router.py —— 关键词路由（5 个技能够用）
TRIGGERS = {
    "refund-policy": ["退款", "退货", "退钱", "不想要"],
    "complaint-escalation": ["投诉", "差评", "举报", "强烈不满"],
    "customer-tone": ["怎么说", "话术", "回复"],
}

def route(user_input: str) -> str | None:
    for skill, triggers in TRIGGERS.items():
        if any(t in user_input for t in triggers):
            return skill
    return None   # 未命中 → 编排层默认查询流程（05 篇）
```

**路由边界**：路由只做"初步筛选"，**SKILL.md 里的第一步才做"确认"**（退款 Skill 第一步查单，非订单诉求自然走不通）——路由错了可以纠正，Skill 内校验兜底（两段式信任，与阶段 3 的"Schema 层+业务层"双层校验同构）。

## 8. SKILL.md 格式校验清单

技能层测试的静态检查（06 篇技能层测试的前置步骤，可做成 pytest）：

| 检查项 | 规则 | 失败示例 |
|---|---|---|
| name 与目录同名 | skills/refund-policy/ 的 name 必须是 refund-policy | name: refund（少 -policy） |
| description 可触发 | 含触发词与使用场景（激活开关语义） | "退款技能"（无场景） |
| allowed-tools 合法 | 引用的工具都存在于 MCP Server | 引用了 get_price（不存在） |
| 文件行数 | ≤500 行（渐进式披露约束） | 800 行超限 |
| 步骤引用工具 | 每个工具调用都写了错误分支 | "调用 refund_order"（无失败处理） |
| 政策知识外置 | 业务规则在文件内（可审） | "按常规退款政策"（依赖模型记忆） |

```python
# tests/skills/test_skill_format.py
def test_all_skills_valid():
    for skill in load_skills():
        assert skill.name == skill.dirname          # 同名规则
        assert len(skill.lines) <= 500
        for tool in skill.allowed_tools:
            assert tool in ALL_TOOLS                # 工具存在性
        assert "错误" in skill.full_text or "失败" in skill.full_text  # 错误分支
```

**校验的价值**：格式校验是"最便宜的质量门禁"——坏格式的 Skill 在运行时才炸（路由命中但步骤乱），静态校验把这类问题挡在 CI。

## 9. 技能层测试要点

技能层的可测性设计（06 篇第二层）：

| 测试维度 | 方法 | 断言 |
|---|---|---|
| 步骤序列 | mock LLM 按 SKILL.md 逐步执行 | 工具调用顺序正确（查单→判断→执行→通知） |
| 工具参数 | 断言传给工具的参数值 | 订单号来自用户输入而非模型编造 |
| 错误分支 | 工具返回各错误码 | 每个错误码都有对应话术 |
| 确认触发 | needs_human=true 时 | 编排层弹出确认（MRTR） |
| 政策边界 | 7 天/500 元边界样本 | 超期判定正确 |

**技能层测试的定位**：它测的是"剧本好不好"——**SKILL.md 是代码（业务程序），技能测试是单测**；改政策行、加错误分支，跑技能测试就知道剧本没被改坏。

## 10. 面试速记（Skill 篇）

1. Skill 是程序（流程+知识），MCP 是库（工具），LLM 是语言。
2. 决策框架：确定性流程→Skill；实时数据/外部动作→MCP。
3. SKILL.md 四要素：name 同名、description 激活开关、allowed-tools、步骤显式化。
4. 渐进式披露三层：发现 ~100 token / 激活 <5000 / 按需加载。
5. 政策知识进 Skill 的价值：可读可审可改（合规部门审文件）。
6. 路由升级路径：关键词（77.1%）→ 语义嵌入（93.8% top-1）。

## 11. 工具引用规范详表

SKILL.md 中"调用工具"的标准写法（04 篇第 2 节规范的细化）：

| 规范项 | 标准写法 | 反例 |
|---|---|---|
| 参数来源 | `order_id=<用户提供的订单号>` | `order_id=<订单>`（来源不明） |
| 失败分支 | "若返回 NOT_FOUND：直接回复…" | "调用 get_order"（无失败处理） |
| 状态判断 | "以工具返回为准，不假设" | "订单应该已支付" |
| 确认触发 | "needs_human=true → 询问用户" | "大额订单要确认"（条件写死在模型记忆） |
| 下一步 | "流程结束" / "继续第三步" | "视情况而定"（模型自由发挥） |

**规范的工程意义**：工具引用规范决定了 Skill 的确定性——**每步"参数怎么来、失败怎么办、下一步去哪"都写死，LLM 只是执行器**；规范越细，技能层测试越好写（06 篇断言序列）。

## 12. Skill 与工具的边界案例

分不清"进 Skill 还是进工具"时，用三个案例定边界：

| 案例 | 归类 | 理由 |
|---|---|---|
| "订单金额不能超过用户余额" | 工具（refund_order 内校验） | 数据完整性约束（业务规则+数据） |
| "退款后要发回执短信" | Skill（流程步骤） | 跨工具协调（退款+通知） |
| "退款原因可选下拉" | 工具（Schema 枚举） | 参数结构约束 |
| "超 7 天需人工审核" | Skill（政策知识） | 政策可改（文件级变更） |
| "同一订单不能重复退款" | 工具（幂等校验） | 数据一致性（工具兜底） |

**边界判定口诀**：**数据完整性进工具、流程协调进 Skill、政策规则进 Skill、参数结构进 Schema**——拿不准时问一句"改它需要改代码吗？"：需要→考虑放 Skill（文件级变更），不需要→进工具。

> 🎯 **核心要点**：Skill 层 = 三个 SKILL.md（退款政策/投诉升级/客服话术）+ 标准四要素（frontmatter 激活开关/allowed-tools/步骤显式化/知识外置）+ 工具引用规范（参数来源/失败分支/状态判断/确认触发/下一步全显式）+ 渐进式披露（发现~100 token/激活<5000）+ 关键词路由（>10 技能再升语义）+ 格式校验门禁 + 技能层测试 + 边界判定口诀（数据完整性进工具/政策进 Skill）。**验收标准：政策改一行文件就能生效、投诉升级不越权承诺、每个工具错误码都有对应话术**——Skill 是"可读、可审、可改"的业务程序。
