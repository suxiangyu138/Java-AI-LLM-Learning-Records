## 1. 三层架构总览

```
┌─────────────────────────────────────────────────────┐
│ 交互层（用户入口）                                    │
│   CLI / Web 聊天 / Claude Code（多入口共用编排层）      │
└──────────────────────┬──────────────────────────────┘
┌──────────────────────▼──────────────────────────────┐
│ 编排层（Agent 大脑）                                  │
│   orchestrator：意图识别 → Skill 路由 → 循环执行       │
│   LLM（DeepSeek/Claude）→ 自然语言 ↔ 结构化决策        │
└──────────────────────┬──────────────────────────────┘
┌──────────────────────▼──────────────────────────────┐
│ 执行层（能力底座）                                    │
│   Agent Skill（流程/知识）：退款流程 / 投诉升级 / 话术   │
│        ↓ 调用                                        │
│   MCP Server（原子工具）：订单 / 物流 / 退款 / 通知     │
│        ↓ 读写                                        │
│   业务数据（sqlite）+ 桩服务（外部 API 模拟）           │
└─────────────────────────────────────────────────────┘
```

**三层职责与边界**：

| 层 | 职责 | 不做什么 |
|---|---|---|
| 交互层 | 接收输入、展示输出、人工确认入口 | 不做业务判断 |
| 编排层 | 意图识别、Skill 路由、循环控制、LLM 接入 | 不直接碰数据库 |
| 执行层 | Skill 流程执行 + MCP 工具调用 | 不做意图理解 |

**分层纪律**：编排层通过 Skill 与工具接口访问执行层，**不直接写数据库**——这样换数据源、换 LLM、加入口都不动其他层。这个纪律在 06 篇测试时尤其值钱（每层可独立 mock）。

## 2. 编排模式选型

2026 年三种主流模式（检索结论），按项目规模选：

| 模式 | 机制 | 适用 | 本项目 |
|---|---|---|---|
| 编排器模式 | orchestrator + LLM + Skills + MCP 单进程循环 | 单 Agent、中小任务 | ★ 采用 |
| 指挥官+专家 | 主 Agent 用 Skills 规划，子 Agent 并行执行 | 多任务并行、研究类 | 备用扩展 |
| 三层多智能体 | 交互/协作总线（A2A）/执行三层分离 | 企业级多 Agent 协同 | 07 篇展望 |

**为什么本项目选编排器模式**：客服场景是"单任务串行 + 少量分支"，不需要多 Agent 并行；编排器模式代码最少、可测性最好（单进程、显式循环），**把复杂度留给 Skill 与工具本身**。指挥官模式留作扩展方向（01 篇风险表里已砍掉的装饰需求用不上）。

**编排器核心循环**（05 篇详实现）：

```text
while 任务未完成:
    1. LLM 读当前状态（用户意图 + 已收集信息）
    2. 匹配 Skill（语义路由）→ 加载 SKILL.md
    3. Skill 步骤 → 调 MCP 工具（参数由 LLM 按 Schema 生成）
    4. 工具结果回填上下文
    5. 判断：完成 → 输出；需确认 → MRTR；循环 → 继续
```

## 3. 项目目录结构

```text
customer-service-agent/
├── README.md                    # 08 篇交付物
├── docs/
│   ├── architecture.md          # 架构图与设计决策（本文件）
│   └── requirements.md          # 01 篇需求文档
├── orchestrator/                # 编排层
│   ├── main.py                  # CLI/Web 入口（交互层）
│   ├── agent.py                 # Agent 循环（05 篇）
│   ├── skill_router.py          # Skill 语义路由（04/05 篇）
│   └── llm.py                   # LLM 客户端封装（可替换供应商）
├── mcp_servers/                 # 执行层：MCP Server（03 篇）
│   ├── order_server/            # 订单/物流/退款/通知工具
│   │   ├── __init__.py          # FastMCP 应用（阶段 3 标准）
│   │   ├── tools/               # 工具实现
│   │   └── tests/               # 06 篇测试
│   └── pyproject.toml
├── skills/                      # 执行层：Agent Skill（04 篇）
│   ├── refund-policy/           # 退款政策 SKILL.md
│   ├── complaint-escalation/    # 投诉升级 SKILL.md
│   └── customer-tone/           # 客服话术 SKILL.md
├── data/                        # 业务数据（sqlite + 桩）
│   └── seed.py                  # 造数据脚本
└── tests/                       # 端到端场景测试（06 篇）
    └── scenarios/               # 5 个剧本
```

**目录设计三原则**：① 按层分目录（交互/编排/执行）——职责即路径；② Skill 独立目录（可单独分发，07 篇）——技能与代码解耦；③ `docs/` 前置——**先有文档再有代码**（阶段 4 的纪律）。

## 4. 数据流：一次对话的旅程

以场景 C（退款）为例走完整数据流：

```text
用户：申请退款 A1003
  │
  ▼ 交互层：CLI 收到输入 → 交给编排层
编排层：
  1. LLM 意图识别 → "退款申请"（命中 refund Skill 描述）
  2. skill_router 加载 SKILL.md（退款政策 + 流程步骤）
  3. Skill 步骤 1：get_order(A1003) ──MCP──▶ order_server ──▶ sqlite
  4. 工具返回 {status:"shipped", 超期:false} → 回填上下文
  5. Skill 步骤 2：判断符合 7 天政策 → 继续
  6. Skill 步骤 3：refund_order(A1003) ──MCP──▶ 写操作 → 需确认
  7. MRTR：编排层向用户确认"确认退款 199 元？"
  8. 用户确认 → 重发 → refund_order 执行 → 状态更新
  9. Skill 步骤 4：notify(A1003, "退款成功") → 回执
  ▼ 交互层：输出"退款成功，预计 3-5 个工作日到账"
```

**数据流设计要点**：① **工具返回即事实**——模型不"记得"订单状态，每次判断都查工具（防幻觉）；② **Skill 步骤显式化**——流程步骤在 SKILL.md 里，可读可审可改；③ **确认点唯一**——写操作统一走 MRTR，不在多个地方各写一套确认逻辑；④ **全程留痕**——每步日志带 request_id（阶段 3 标准），07 篇监控靠它。

## 5. 状态与句柄设计

沿用阶段 3 无状态规范（2026-07-28）的结论：

| 状态 | 放哪 | 形态 |
|---|---|---|
| 对话上下文 | 编排层进程内（单会话短期） | 消息列表（LLM 上下文） |
| 业务状态（订单/退款） | sqlite（业务库） | 数据库行 |
| 跨请求业务句柄 | 工具参数（订单号/退款单号） | 显式 ID |
| 人工确认状态 | MRTR requestState | 协议级（阶段 3 已实现） |

**无状态红利在项目层的体现**：MCP Server 无状态（轮询可扩）；编排层会话状态外置后也可多实例（07 篇）；**"哪个实例在处理哪个对话"不再是约束**——这是阶段 3 学到的架构资产在项目层的兑现。

## 6. 技术选型

| 组件 | 选型 | 理由 |
|---|---|---|
| MCP Server | FastMCP 3.x（Python） | 阶段 3 已学、OAuth/中间件/任务内建 |
| LLM | DeepSeek API（OpenAI 兼容）或 Claude | 便宜、兼容层统一（llm.py 封装） |
| 编排器 | Python asyncio + 自研循环 | 显式可控、可测（06 篇） |
| Skill 格式 | SKILL.md（YAML frontmatter + Markdown） | Agent Skill 开放标准（04 篇） |
| Skill 路由 | 关键词 → 语义嵌入（可选升级） | 5 个 Skill 关键词够用；大了再嵌入 |
| 数据 | sqlite + 桩 HTTP 服务 | 本地可复现（01 篇风险表） |
| 客户端 | 自研 CLI + Claude Code 双入口 | 自研验证编排，Claude Code 验证生态（05 篇） |
| 部署 | Docker Compose（07 篇） | 阶段 3 已配 |

**选型铁律**：**全部组件都是"阶段 3 已验证过的技术"**——毕业项目用已知技术组合，不用新技术冒险（新技术留到项目后探索）。

## 7. 技术选型对比与决策

选型背后的对比思考（08 篇 ADR 的原料）：

| 决策点 | 选项 A | 选项 B | 选择与理由 |
|---|---|---|---|
| 编排器 | 自研循环 | Agent SDK/框架 | 自研：可测性最好、能讲清每步；SDK 是扩展方向 |
| Skill 路由 | 关键词 | 语义嵌入 | 关键词：5 个技能够用零成本；嵌入是 >10 技能的升级路径 |
| LLM | DeepSeek（OpenAI 兼容） | Claude 直连 | DeepSeek：便宜 + 兼容层统一；llm.py 抽象可换 |
| 传输 | stdio（一体） | HTTP（分离） | stdio：本地演示安全面小；HTTP 是 07 篇扩展 |
| 数据 | sqlite + 桩 | 真实 API | sqlite：可复现可测试；桩是真实 API 的替身 |
| 确认 | MRTR（协议级） | 代码内确认 | MRTR：阶段 3 资产复用，协议标准语义 |

**选型原则回顾**：全部组件都是前三个阶段验证过的技术——**毕业项目用已知技术组合，未知技术留到扩展**（02 篇第 6 节铁律）。

## 8. 指挥官模式设计（扩展预览）

02 篇第 2 节提到"指挥官模式"是升级方向，给出设计草图（面试加分项）：

```text
主 Agent（规划）                   子 Agent（执行）
   │ 用 Skills 拆任务                  │
   ├─▶ 客服 Agent（退款/升级）── 调 MCP 订单工具
   ├─▶ 报表 Agent（汇总）────── 调 MCP 统计工具
   └─▶ 质检 Agent（抽查话术）── 调 customer-tone
   │ 汇总结果
   ▼
交付：结果经 MCP 写入外部系统（Notion/工单）
```

**触发条件**（什么信号说明该升级了）：任务可并行拆解（客服+报表+质检互不依赖）、单 Agent 上下文放不下、响应时间要求高（并行换时间）。

## 11. 架构决策的自问清单

写架构文档前自问（答案即 ADR 素材）：

1. 为什么用三层而不是两层？（测试与替换的解耦）
2. 为什么编排器自研而不是框架？（可测性 + 可讲性，08 篇面试点）
3. 为什么状态外置？（阶段 3 无状态红利：轮询扩容）
4. 为什么确认用 MRTR？（协议级标准，阶段 3 资产复用）
5. 为什么数据用 sqlite + 桩？（可复现测试，01 篇风险表）
6. 为什么 Skill 独立目录？（可单独分发、可版本化）
7. 为什么决策用元工具约束？（防幻觉，05 篇第一道闸）

**自问的价值**：每个"为什么"都有答案的架构才是设计过的架构——**没有自问过的架构是"代码拼图"，自问过的架构是"设计文档"**。**架构篇的完成标准**：架构文档（含图与 ADR）能独立回答上述七问 + 面试速记六条——文档是面试的"剧本"，代码只是舞台布景。

## 12. 接口契约表

三层之间的接口契约（02 篇架构的"粘合剂"，排障先对齐它）：

| 接口 | 契约 | 违约症状 |
|---|---|---|
| 交互层→编排层 | 输入：文本；输出：文本 + 可选确认请求 | 输出格式混乱 |
| 编排层→LLM | 输入：决策提示词+上下文；输出：决策动作（元工具） | 决策乱（枚举外值） |
| 编排层→Skill | 输入：技能名+用户输入；输出：步骤序列（调工具/结束） | 步骤跑偏 |
| Skill→MCP 工具 | 输入：按 Schema 的参数；输出：structured_content | 参数错/结果解析失败 |
| 编排层→用户确认 | MRTR：提示文案→确认/取消 | 确认不触发/循环 |

**契约设计原则**：每个接口都有"显式结构"（Schema/枚举/格式）——**显式契约是"可测性"的物理基础**（06 篇三层测试全建立在契约上）；接口松散的架构，测试无从写起。

## 13. 面试速记（架构篇）

1. 三层架构：交互/编排/执行，编排不碰库（分层纪律）。
2. 编排器模式：决策模型做、执行代码管、8 步上限。
3. 状态外置：业务状态在库、句柄在参数、确认在协议（无状态红利）。
4. 工具即事实：模型不记忆业务状态，判断永远查工具。
5. 目录按层分 + docs 前置：文档是宪法，代码从文档长出来。
6. 扩展路径：指挥官模式 / Skills Over MCP / 分离部署（触发条件驱动）。

## 14. 架构演进：从演示到生产

架构不是一次画完的，演进路径（08 篇"扩展愿景"的完整版）：

```text
v1（本项目）：一体容器 + stdio + 单实例
  ↓ 触发条件：团队 >5 人共享
v2：Server 分离部署（HTTP + OAuth，阶段 3 全套）
  ↓ 触发条件：任务可并行
v3：指挥官模式（主 Agent 规划 + 子 Agent 并行 + Skills Over MCP）
```

**演进原则**：**每级演进由触发条件驱动，且不破坏前级契约**（接口契约表是"不破坏"的保证）——**架构的价值不在于"一开始就画全"，而在于"每一版都能讲清、能测试、能演进"**。**架构文档的时效性**：每次演进同步更新 architecture.md 与 ADR（新增决策必须记录）——文档与架构脱节之日，就是架构开始腐化之时。

> 🎯 **核心要点**：架构 = 三层（交互/编排/执行，分层纪律：编排不碰库）+ 编排器模式（单 Agent 串行循环，复杂度留给 Skill 与工具）+ 目录按层分（docs 前置）+ 数据流四要点（工具即事实/Skill 步骤显式/确认点唯一/全程留痕）+ 状态外置（无状态红利兑现）+ 已知技术栈 + 接口契约表（显式结构=可测性）+ 演进路径（触发条件驱动、契约不破坏）+ 扩展预览（指挥官模式）+ 架构图规范 + 设计自问清单。**架构图的验收标准：拿着图能讲清"一次对话从输入到输出的每一步发生在哪层、用什么组件"**——讲不清就回炉。
