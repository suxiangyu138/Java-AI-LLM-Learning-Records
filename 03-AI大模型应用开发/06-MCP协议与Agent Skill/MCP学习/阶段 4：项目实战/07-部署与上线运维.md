## 1. 部署架构总览

```
                    ┌────────────────────────────┐
用户/客户端 ───────▶ │ 编排器（Agent 容器）          │
(CLI/Web/Claude Code)│  Agent 循环 + Skill 路由      │
                    │  LLM 密钥（Secret）            │
                    └────────────┬───────────────┘
                                 │ MCP（stdio 容器内 / HTTP 远程）
                    ┌────────────▼───────────────┐
                    │ MCP Server（业务工具容器）    │
                    │  order_server（FastMCP）    │
                    └────────────┬───────────────┘
                                 │ 读写
                    ┌────────────▼───────────────┐
                    │ 业务数据 sqlite/桩服务        │
                    └────────────────────────────┘
```

**两种部署形态**：

| 形态 | 组合方式 | 适用 |
|---|---|---|
| 一体容器 | 编排器 + Server 同容器（stdio 连接） | 单机演示、小团队（本项目 ★） |
| 分离部署 | Server 走 HTTP 远程（阶段 3 全套） | 多客户端共享、水平扩展 |

**本项目选一体容器的理由**：客户量小、stdio 连接零网络层（安全面小）；**07 篇演示从一体起步，分离部署是 08 篇展示的升级方向**（阶段 3 已具备全部能力，切换只是配置）。

## 2. 容器化：Server 与编排器

```dockerfile
# Dockerfile（一体容器：编排器 + MCP Server）
FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml ./
RUN pip install --no-cache-dir .
COPY orchestrator/ ./orchestrator/
COPY mcp_servers/ ./mcp_servers/
COPY skills/ ./skills/
COPY data/ ./data/
RUN useradd -m agent && chown -R agent:agent /app
USER agent
# 编排器启动时拉起 MCP Server（stdio 子进程，阶段 2/3 模式）
CMD ["python", "-m", "orchestrator.main"]
```

**编排器与 Server 的进程关系**（一体容器内）：编排器启动时以子进程拉起 order_server（stdio 传输），退出时优雅关闭——**阶段 3 的"进程即生命周期"模式**；分离部署时改为编排器连 HTTP 端点（05 篇 McpClient 双传输切换）。

**K8s/Compose 清单**（阶段 3 全部复用）：非 root、健康检查（编排器 `/healthz` 探活 + MCP Server `/readyz` 探依赖）、内存限制、优雅退出（SIGTERM → 结束对话 → 关子进程）、日志 stdout。

## 3. Skill 分发：随项目还是独立仓库

Skill 是"可移植、可版本化"的目录（04 篇），分发策略三选：

| 策略 | 机制 | 适用 |
|---|---|---|
| 随项目分发 | skills/ 打进镜像，随应用部署 | 本项目（技能与业务强绑定）★ |
| 独立技能库仓库 | skills 独立 git 仓库，多项目引用 | 通用技能（话术规范可复用） |
| 注册表/路由服务 | Skills Over MCP（SEP-2640）分发 | 技能库 >10 个、多客户端（08 篇展望） |

```text
# 独立仓库形态（升级方向）
agent-skills/
├── refund-policy/SKILL.md
├── complaint-escalation/SKILL.md
└── customer-tone/SKILL.md
# 消费方（编排器）通过子模块/依赖拉取，随版本锁定
```

**Skill 版本化纪律**（`Agent Skill学习/阶段 5` 同源）：SKILL.md 变更 = 版本变更（业务规则变化必须可回溯）；CI 校验 SKILL.md 格式（frontmatter 必填项/描述长度/文件行数上限）。

## 4. 密钥与配置管理

| 密钥/配置 | 管理方式 | 泄露后果 |
|---|---|---|
| LLM API Key | Secret Manager / 环境变量注入 | 烧钱 + 滥用 |
| 数据库访问 | 容器内环境变量（只读账号） | 数据泄露 |
| 通知网关凭据 | 环境变量（桩→真实切换点） | 短信轰炸 |
| read_only 开关 | 配置（默认 true） | 写工具意外开放 |

**配置清单**（上线核对）：

```bash
export LLM_BASE_URL="https://api.deepseek.com"   # 供应商切换点
export LLM_API_KEY="sk-..."                      # Secret 注入
export LLM_MODEL="deepseek-chat"
export ORDER_DB="/data/orders.db"
export MCP_READ_ONLY="true"                      # 阶段 3 安全基线
export LOG_LEVEL="info"                          # 防 debug 泄密
```

**安全基线**：LLM Key 只进编排器（Server 不碰）；read_only 默认 true（写工具需要显式开启 + 确认，阶段 3 五件套项目级兑现）；日志脱敏（阶段 3 中间件审计"记键不记值"）。

## 5. 监控三支柱与成本告警

**项目级监控**（阶段 3 第 8 节的项目化）：

| 支柱 | 监控项 | 告警 |
|---|---|---|
| 指标 | 对话数、工具调用数、错误率、P99 端到端延迟 | 错误率 >1%、P99 >10s |
| 日志 | 结构化日志（request_id 串联：输入→Skill→工具→输出） | 错误日志量突增 |
| **成本** | **token 消耗/次、LLM 费用/日、工具调用分布** | **日费用超预算、单次 >10K token** |

**成本告警是项目特色**（LLM 应用独有）：编排层每轮记录 token（05 篇记账），监控面板展示"成本/对话"趋势；**工具调用分布异常是信号**——某工具占比 >90% 说明模型陷入循环（阶段 3 值班手册同款）。

**排障流程**（阶段 3 值班手册项目化）：trace 定位（输入→决策→工具→输出）→ 日志看决策与参数 → 指标看影响面 → 修复后补场景剧本（06 篇闭环）。

## 7. 扩展方向：多智能体与 Skills Over MCP

**毕业后的三个扩展方向**（02 篇架构模式的升级路径）：

| 方向 | 形态 | 触发条件 |
|---|---|---|
| 多客户端共享 | Server 分离部署（HTTP + OAuth） | 团队 >5 人共用 |
| 指挥官模式 | 主 Agent 规划，子 Agent 并行（客服/报表/质检） | 任务并行化需求 |
| Skills Over MCP | 技能库经 MCP 分发（SEP-2640，skill-router-mcp） | 技能 >10 个、多项目复用 |

**Skills Over MCP 简介**（2026 检索的新趋势）：把技能库做成 MCP Server，客户端按任务语义路由到技能（嵌入匹配 93.8% vs 关键词 77.1%）——**技能与工具用同一协议分发**，双体系的融合方向。本项目的关键词路由（04 篇）升级为语义路由即此路线，08 篇面试可讲。

## 8. 完整 Compose 配置

```yaml
# docker-compose.yml —— 一体容器 + 数据卷 + 监控
services:
  agent:
    build: .
    ports: ["8000:8000"]               # CLI/Web 入口
    environment:
      LLM_BASE_URL: ${LLM_BASE_URL}
      LLM_API_KEY: ${LLM_API_KEY}      # Secret 注入（宿主环境）
      LLM_MODEL: deepseek-chat
      MCP_READ_ONLY: "true"
      LOG_LEVEL: info
    volumes:
      - order-data:/data               # sqlite 持久化（重启不丢）
    healthcheck:
      test: ["CMD", "python", "-m", "orchestrator.healthcheck"]
      interval: 30s
      timeout: 5s
      retries: 3
    deploy:
      resources: { limits: { memory: 1g, cpus: "1.0" } }
    restart: unless-stopped

  prometheus:                          # 指标（07 篇第 5 节）
    image: prom/prometheus
    volumes: ["./prometheus.yml:/etc/prometheus/prometheus.yml"]

  grafana:                             # 可视化（成本面板）
    image: grafana/grafana
    ports: ["3000:3000"]
    environment:
      GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_PASSWORD}
```

**Compose 要点**：数据卷（sqlite 挂卷是"重启不丢"的关键）、Secret 从宿主注入（镜像内无明文）、健康检查真实探活（编排器 + 子进程 Server）、资源限制（LLM 应用内存峰值可控）。

## 9. 监控指标与值班手册

**监控指标清单**（07 篇第 5 节的落地表）：

| 类别 | 指标 | 告警阈值 |
|---|---|---|
| 业务 | 对话数/日、工具调用分布 | 单工具占比 >90% |
| 质量 | 错误率、P99 端到端延迟 | >1%、>10s |
| 成本 | token/次、LLM 费用/日 | >10K/次、超日预算 |
| 安全 | 401 率、确认拒绝率 | 突增 >10% |

**值班手册**（告警→动作）：

| 告警 | 首查 | 动作 |
|---|---|---|
| 成本超预算 | token 记账（05 篇） | 查循环（工具调用分布）、降模型档 |
| 错误率突增 | 日志（request_id 串联） | 查最近发布（Skill 变更/工具变更） |
| 工具分布异常 | 调用矩阵（06 篇） | 模型陷入循环 → 查决策提示词 |
| 确认拒绝率高 | 会话日志 | 确认文案误导 → 改 Skill 话术 |

**值班铁律**（阶段 3 延续）：先止血（降成本/回滚）后根治（改代码/改 Skill），复盘补剧本（06 篇闭环）。

## 11. Skill 版本化与回滚

Skill 是"业务程序"（04 篇），上线后改政策是常态，版本化纪律：

| 机制 | 实现 |
|---|---|
| 版本标记 | SKILL.md frontmatter 加 `version: "1.2"` |
| 变更记录 | skills/CHANGELOG.md（政策变更必须记录） |
| 镜像锁定 | 技能随镜像发布（07 篇检查单第 9 项） |
| 回滚 | 回滚 = 回滚镜像（技能回到旧版） |
| 灰度 | 策略变更先内部环境验证（06 篇剧本回归） |

```markdown
# skills/refund-policy/SKILL.md（frontmatter）
---
name: refund-policy
version: "1.3"
description: 退款处理流程（v1.3：7 天→30 天政策调整，2026-08-10）
allowed-tools: [get_order, refund_order, notify]
---
```

**Skill 变更流程**（生产标准）：改 SKILL.md → 更新 changelog → 技能层测试（06 篇）→ 场景回归 → 发版 → 监控确认。**"改一行政策"的完整链路 = 文件 → 测试 → 发布 → 观测**——这就是"Skill 是程序"在生产中的含义。

## 13. 备份与恢复演练

数据与配置的备份策略（07 篇上线检查单第 9 项的展开）：

| 备份对象 | 方式 | 频率 | 恢复验证 |
|---|---|---|---|
| sqlite 业务数据 | 文件快照（挂卷目录） | 每日 | 季度恢复演练 |
| SKILL.md 技能 | Git 版本库（changelog） | 每次变更 | git checkout 即恢复 |
| 编排器配置 | 环境变量清单（文档化） | 每次变更 | 从零重建演练 |
| 监控配置 | Compose/面板导入文件 | 每次变更 | 一键重建 |

**恢复演练三步**：① 杀容器 + 删数据卷 → ② 从备份恢复数据 + 重建容器 → ③ 5 剧本重跑全绿。**演练的意义：备份的有效性只有"恢复成功"能证明**——"有备份"与"能恢复"之间差一次演练。

## 14. 上线发布节奏

项目级发布节奏（小步快跑）：

| 阶段 | 动作 | 验证 |
|---|---|---|
| 开发 | 本地全绿 | pytest + 5 剧本 |
| 预发布 | 部署环境重跑 | 真实 LLM 剧本 + 成本报告 |
| 上线 | 容器发布 | 健康检查 + 冒烟 |
| 观测 | 监控 24h | 错误率/成本/延迟 |
| 迭代 | 按需发版 | 06 篇门禁三件套 |

**发布纪律**：**每次发布都有记录（版本+变更+验证结果）**；无记录 = 无法回滚 = 无法复盘——07 篇第 11 节的版本化纪律贯穿始终。**发布的最终检验**：上线 24 小时内不出现"部署环境才有的问题"（数据路径、环境差异、权限）——**预发布环境与生产环境的一致性，是"上线不翻车"的最大保障**（配置基线表逐项对齐）。**部署篇完成标志**：上线检查单 10 项全过 + 恢复演练一次成功 + 监控面板（指标/日志/成本）就绪——"能上线、能恢复、能观测"三件事落地，运维闭环完成。**部署的面试表达**：突出"无状态架构让部署退化为普通 Web 服务"（阶段 3 资产的兑现）+ "成本告警是 LLM 应用独有的运维维度"——两个点都讲，运维深度立现。**运维与交付的衔接**：监控面板（成本/错误率）的截图放进作品集（08 篇）——"项目真的跑过、真的被观测"的证据，比代码仓库更有说服力；**上线后的 5 剧本重跑记录（07 篇检查单第 2 项）同样是交付素材**。**运维的最小闭环**：即使不部署到云（本地 Docker 也算），也要完成"健康检查→日志查看→成本对账→恢复演练"四件事——**运维能力不是"上云"才需要，本地跑通的最小闭环就是简历里的"运维经验"**。**关于"上线"的界定**：本项目的"上线"指"在可复现的部署环境中持续运行并被观测"（本地 Docker + 监控面板即达标）——**毕业项目展示的是运维方法与工程习惯，不是商业级 SLA**；把"已上线（本地 Docker，含监控与恢复演练）"写进简历是诚实且加分的表述。

## 15. 部署篇面试速记

1. 一体容器起步（编排器+Server 同进程 stdio），分离部署是触发条件驱动的扩展。
2. 数据卷 = 重启不丢；健康检查真实探活（编排器+子进程）；优雅退出保对话。
3. 密钥分离：LLM Key 只在编排器，Server 不碰；read_only 默认；日志脱敏。
4. Skill 版本化：frontmatter 版本 + changelog + 镜像锁定——回滚 = 镜像回滚。
5. 成本告警是 LLM 应用特色：token 是直接成本，工具调用分布异常是循环信号。
6. 备份有效性 = 恢复演练成功（"有备份"与"能恢复"之间差一次演练）。

> 🎯 **核心要点**：部署 = 一体容器起步（编排器+Server 同进程 stdio）+ Compose 全家桶（数据卷/Secret/健康检查/资源限制）+ 阶段 3 全套清单复用 + Skill 随项目分发（版本化+changelog+回滚=镜像回滚）+ 密钥分离 + 监控三支柱含**成本告警** + 值班手册 + 上线检查单 10 项 + 备份恢复演练（能恢复才算备份）+ 发布节奏（小步快跑+全记录）+ 扩展演进由触发条件驱动。**验收标准：杀容器重启后对话数据不丢、成本每天可对账、5 个剧本在部署环境重跑全绿**——"演示能用"与"上线能用"的分界就在这三点。
