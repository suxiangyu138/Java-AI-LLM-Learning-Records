## 1. 选题：什么样的项目适合毕业实战

阶段 4 的项目要同时验证 MCP（工具）与 Skill（流程），选题四原则：

| 原则 | 说明 | 反例 |
|---|---|---|
| 有真实外部动作 | 至少一个工具要"改变状态"（写数据库/调 API） | 纯查询的只读工具集 |
| 有流程性知识 | 至少一个任务需要多步协调（非单个工具能完成） | 单工具能答的问题 |
| 数据可模拟 | 业务数据可造（本地库/桩 API），不依赖真实第三方 | 必须真实支付网关 |
| 规模可控 | 3-5 个工具 + 2-4 个 Skill 足够闭环 | 试图做一个企业 ERP |

**候选项目对比**：

| 候选 | 外部动作 | 流程知识 | 规模 | 评分 |
|---|---|---|---|---|
| 智能客服 Agent | 改单/通知 | 投诉升级/退款流程 | 3-5 工具 + 3 Skill | ★★★★★ |
| 代码评审助手 | 提 PR/发消息 | 评审规范流程 | 依赖 GitHub | ★★★☆ |
| 个人知识库问答 | 无（只读） | 检索流程 | 缺外部动作 | ★★☆ |
| 电商运营看板 | 查询+报表 | 报表生成流程 | 中 | ★★★★ |

**结论**：智能客服 Agent 是"动作 + 流程 + 规模"均衡的毕业项目——后续各篇都以它为例，你也可以替换业务域（订单→工单、商品→库存），方法不变。

## 2. 本项目：智能客服 Agent

**一句话定位**：一个能查订单、查物流、处理退款申请、按流程升级投诉的智能客服——用户用自然语言对话，Agent 用 Skill 路由流程、用 MCP 调用业务工具。

**业务场景剧本**（贯穿全项目的主线）：

```text
场景 A（查询）：用户问"我的订单 A1001 到哪了？" → 查物流 → 回答
场景 B（改单）：用户要求"把订单 A1002 改成明天发货" → 校验权限 → 改单 → 确认
场景 C（退款）：用户申请"A1003 退款" → 校验条件 → 发起退款（人工确认）→ 回执
场景 D（投诉升级）：用户不满 → 客服流程判定升级 → 转人工工单 → 通知
场景 E（报表）：运营问"本周退款率？" → 汇总 → 生成报表
```

**为什么选客服**：查询/改单/退款/升级/报表五个场景覆盖了工具（读/写/外部动作）、流程（多步协调）、确认（MRTR 人工确认）、数据（可造）全部要素——**一个项目测遍 MCP 与 Skill 的所有关键能力**。

## 3. 需求拆解：从业务到功能

**拆解三步法**：业务场景 → 功能点 → 能力需求（工具/技能/人工）。

以场景 C（退款）为例：

```text
用户：申请退款 A1003
  ↓ 拆解
1. 识别意图（是退款不是查询）          → LLM 意图识别（编排层）
2. 查询订单状态与退款条件              → 工具 get_order（校验资格）
3. 按退款政策判断（7 天无理由？）       → Skill 退款流程（流程知识）
4. 执行退款（改状态 + 金额回滚）        → 工具 refund_order（写操作）
5. 人工确认（大额/超期需人工）          → MRTR 确认（阶段 3 模式）
6. 生成回执并通知                      → 工具 notify + 回复组装
```

**功能点清单**（全项目）：

| 编号 | 功能 | 场景 | 类型 |
|---|---|---|---|
| F1 | 订单查询 | A | 读工具 |
| F2 | 物流轨迹查询 | A | 读工具 |
| F3 | 发货时间修改 | B | 写工具（权限） |
| F4 | 退款申请处理 | C | 写工具（MRTR 确认） |
| F5 | 投诉升级转人工 | D | 写工具 + 流程 |
| F6 | 退款率报表 | E | 读工具 + 流程 |
| F7 | 订单状态解释 | A/B/C | Skill 知识 |
| F8 | 退款政策咨询 | C | Skill 知识 |
| F9 | 客服话术规范 | 全部 | Skill 流程 |

## 4. 工具/技能映射矩阵

**核心交付物**：需求与能力的一一映射——这张表就是项目设计的"宪法"：

| 需求/功能 | MCP 工具（原子能力） | Agent Skill（流程知识） | 人工（确认点） |
|---|---|---|---|
| 订单查询 | get_order | 订单解释话术 | — |
| 物流查询 | get_shipping | 物流状态术语表 | — |
| 修改发货时间 | update_ship_date | 改单校验流程 | 写操作确认 |
| 退款申请 | refund_order | 退款政策（7 天/超期规则） | 大额/超期人工 |
| 投诉升级 | create_ticket | 升级判定流程 | 升级后转人工 |
| 报表 | get_refund_stats | 报表生成规范 | — |
| 通知 | notify（发送回执） | 通知模板 | — |

**映射规则**：
- **原子操作**（一次函数调用完成）→ MCP 工具：查询、改状态、发通知；
- **多步协调 + 领域知识** → Agent Skill：退款判断（查单→对政策→决定→执行）；
- **有安全后果的步骤** → 人工确认点（MRTR，阶段 3 已实现）；
- **一个 Skill 可调多个工具，一个工具可被多个 Skill 用**——工具原子、知识可组合（阶段 3 第 8 节原则的落地）。

## 5. 验收标准设计

**验收 = 场景剧本 + 质量指标 + 边界用例**三件套：

| 维度 | 验收项 | 通过标准 |
|---|---|---|
| 场景 | 5 个剧本全跑通 | 自然语言输入 → 正确业务结果 |
| 工具 | 单元/协议测试全绿 | 阶段 3 标准（覆盖率 ≥80%） |
| Skill | 路由准确率 | 5 个剧本意图命中率 ≥80% |
| 安全 | 未授权改单被拒 | 权限/MRTR 生效 |
| 成本 | token 消耗记录 | 单次对话 <10K token（Tool Search 开启） |
| 性能 | 端到端延迟 | P95 <10s（含 LLM 调用） |

**边界用例**（必须测的"刁钻输入"）：不存在的订单号、未授权用户改单、超过 7 天退款、投诉升级后无人接单、同时问两个订单（多意图）、语气恶劣的投诉（情绪识别）。

## 6. 风险与边界

| 风险 | 应对 |
|---|---|
| LLM 幻觉（编订单号/编政策） | 工具返回即事实：查无此单必须返回 NOT_FOUND，Skill 里写"以工具返回为准" |
| 提示注入（用户引导 Agent 干坏事） | 阶段 3 五件套：只读默认、写工具确认、输入净化、最小权限、审计 |
| 退款条件判断错误 | 政策规则写进 Skill（可读可审），不依赖模型记忆 |
| 项目范围膨胀 | 砍掉"优惠券计算"等装饰功能；**5 个剧本是范围护栏** |
| 依赖外部 API 不稳定 | 数据全部本地模拟（sqlite + 桩服务），生产形态留到 07 篇 |

## 7. 需求评审清单

立项文档写完，用评审清单过一遍（既是自查也是团队评审提纲）：

| 评审项 | 通过标准 |
|---|---|
| 场景完整性 | 5 个剧本覆盖读/写/流程/报表四类能力 |
| 边界用例 | 不存在订单/超期退款/未授权/多意图/恶劣语气全覆盖 |
| 映射矩阵 | 每个需求都有工具或 Skill 承接；无孤儿需求 |
| 确认点 | 所有写操作都标了确认触发条件（03 篇落地） |
| 数据可造 | 种子数据覆盖全部边界（03 篇数据层） |
| 范围可控 | 无"顺手加的功能"；范围变化必须改文档再改代码 |
| 验收可测 | 每项验收有明确通过标准（非"感觉可以"） |

**评审的意义**：立项文档是项目宪法——**评审通过后，改需求 = 改文档 + 改矩阵 + 改代码三联动**；跳过评审直接写代码的项目，一半的返工发生在"需求没想清楚"上。

## 8. 面试速记（立项篇）

1. 选题四原则：真实外部动作、流程性知识、数据可模拟、规模可控。
2. 拆解三步：业务场景 → 功能点 → 能力需求（工具/技能/人工）。
3. 映射矩阵四列：需求 → MCP 工具 → Agent Skill → 人工确认点。
4. 分工规则：原子操作进工具、多步协调进 Skill、安全后果进人工。
5. 验收三件套：场景剧本 + 质量指标 + 边界用例。
6. 工具即事实：模型不记忆业务状态，判断永远查工具（防幻觉第一原则）。

## 9. 需求文档模板

立项阶段的产出物模板（docs/requirements.md 直接套用）：

```markdown
# 需求文档：智能客服 Agent
## 1. 项目定位
一句话：基于 MCP（工具）+ Agent Skill（流程）的智能客服…
## 2. 场景剧本（5 个，含边界）
| 编号 | 场景 | 输入 | 期望输出 |
## 3. 功能清单（F1-F9，见 01 篇第 3 节）
## 4. 工具/技能映射矩阵（四列：需求→工具→Skill→人工）
## 5. 验收标准（剧本/指标/边界三件套）
## 6. 风险与边界（依赖/范围/安全）
```

**文档的验收**：这份文档是"项目宪法"——**代码与文档冲突时，以文档为准（先改文档再改代码）**；团队评审只审文档不审代码（先立项后开发）。

## 10. 边界用例设计详解

边界用例是验收的灵魂（01 篇第 5 节展开）：

| 边界类型 | 样本 | 为什么重要 | 防什么 |
|---|---|---|---|
| 不存在订单 | "退 X999" | 防幻觉（编造订单） | 模型编订单号调工具 |
| 状态不符 | "退已发货的 A1001" | 业务校验（CONFLICT） | 错误退款 |
| 未授权 | 无令牌改单 | 权限校验 | 越权操作 |
| 超期/大额 | "退 A1003"（9 天 600 元） | MRTR 确认触发 | 无确认退款 |
| 多意图 | "查 A1001 顺便退 A1004" | 路由与顺序 | 一次只处理一个诉求 |
| 恶劣语气 | "你们什么破公司！" | 情绪识别 | 与用户对喷 |
| 边界数字 | 恰好 7 天/恰好 500 元 | 政策判定 | 边界判定错误 |

**设计方法**：每个场景剧本配 1-2 个边界变体——**测试矩阵的"坏输入"全部来自这张表**（06 篇直接消费）。

## 11. 需求变更管理

项目进行中需求必变（这是常态），变更纪律：

| 变更类型 | 流程 | 示例 |
|---|---|---|
| 小改（文案/参数） | 改矩阵 → 改文档 → 改代码 | 退款窗口 7 天→30 天 |
| 中改（新功能） | 评审 → 加矩阵行 → 加剧本 → 开发 | 新增"改地址"功能 |
| 大改（换业务域） | 回到立项重新评审 | 客服→库存管理 |

**变更铁律**：**变更必须先落文档（映射矩阵）再动代码**；改代码不改文档 = 项目宪法失效，后续所有决策都会错乱。**"顺手加个小功能"是范围膨胀的开始**——01 篇风险表第 4 项的日常考验。**评审的分寸**：立项评审不是"找茬大会"而是"风险对齐会"——评审通过 ≠ 需求完美，而是"风险已知、边界明确、验收可测"；**过度评审（纠结文案细节）与不评审（直接写代码）同样有害**，评审的产出物是"风险清单"，不是"完美文档"。

**变更的连锁反应表**（改一处波及哪里，排障与评审的对照表）：

| 改了什么 | 必须同步 |
|---|---|
| 工具 Schema | Skill 引用（04 篇）、剧本断言（06 篇）、README |
| 政策规则 | SKILL.md（04 篇）、种子数据（03 篇）、剧本期望（06 篇） |
| 确认条件 | 工具返回（03 篇）、剧本断言（06 篇） |
| LLM 供应商 | llm.py 抽象层（05 篇）、成本基线（06/07 篇） |

## 12. 面试速记（立项篇二）

1. 需求变更三纪律：先文档后代码、改一处联动四表（工具/Skill/种子/剧本）、砍范围是常态。
2. 边界用例设计：每个场景配 1-2 个"坏输入"变体（防幻觉/状态不符/越权/边界数字）。
3. 需求文档 = 项目宪法：评审通过后，改需求 = 改文档 + 改矩阵 + 改代码三联动。
4. 验收可测性：每项验收有明确通过标准（剧本/指标/边界），拒绝"感觉可以"。
5. 映射矩阵是面试必答：能现场画"退款需求 → 工具/Skill/人工"的映射，即证明理解。

> 🎯 **核心要点**：立项 = 选题四原则（动作/流程/数据/规模）+ 需求拆解三步（场景→功能→能力）+ **工具/技能映射矩阵**（原子操作进工具、多步流程进 Skill、安全后果进人工）+ 验收三件套（剧本/指标/边界）+ 评审清单 + 需求文档模板 + 边界用例表 + 变更管理（先文档后代码，改一处联动四表）。映射矩阵是项目设计的宪法——后续所有代码都从这张表长出来；改需求先改矩阵，再改代码。**立项篇的验收**：能向非技术人员讲清"这个项目给谁解决什么问题、怎么验收"——立项文档不是给代码写的，是给人写的；**映射矩阵能现场画出来**（选一个需求即兴映射工具/Skill/人工），即证明立项方法论内化。
