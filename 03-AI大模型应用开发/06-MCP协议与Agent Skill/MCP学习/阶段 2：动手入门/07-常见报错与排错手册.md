## 1. 排错方法论：四层定位

```text
应用层   工具调用结果不对 / 报错信息不可读
协议层   JSON-RPC 解析失败 / 版本不匹配 / 方法未找到
传输层   stdio 起不来 / HTTP 401 / 超时 / 连不上
进程层   依赖缺失 / 路径错误 / 端口占用 / 代码 bug
```

**定位铁律：从底层往上查**——先确认进程能跑，再确认传输通，再确认协议对，最后才怀疑应用逻辑。

```text
排查顺序（固定）：
1. 终端手动跑 Server —— 有没有报错？依赖全不全？
2. 最小客户端/curl 手测 —— 传输通不通？
3. Inspector 连接 —— 协议对不对？工具在不在？
4. 真实客户端调用 —— 应用逻辑好不好？
```

## 2. 第一层：进程启动问题

| 现象 | 根因 | 解法 |
|---|---|---|
| `FileNotFoundError: [Errno 2]` | command 路径错/不存在 | 绝对路径；确认 `uv`/`python` 在 PATH |
| `ModuleNotFoundError: fastmcp` | 依赖没装/装错环境 | `uv add fastmcp`；确认用的是同一解释器 |
| Server 启动即退出 | 代码顶层报错 | 终端先跑 `uv run python server.py` 看堆栈 |
| 端口占用 | `Address already in use` | 换端口或 `lsof -i :8080` 找占用进程 |
| Uvicorn 启动但无日志 | 启动静默失败 | 加 `--log-level debug`；查 stdout/stderr |

**验证命令**：

```bash
# 手动跑 Server（任何 MCP 排错的第一步）
uv run python server.py

# 检查端口
lsof -i :8080        # macOS/Linux
netstat -ano | findstr :8080   # Windows
```

## 3. 第二层：传输连接问题

| 现象 | 根因 | 解法 |
|---|---|---|
| stdio 连接即断开 | Server 进程崩溃 | 看 stderr 日志（客户端不会显示） |
| HTTP 404 | 端点路径错 | 确认 `/mcp`（不是 `/` 或旧版 `/sse`） |
| HTTP 401/403 | 无 Token/Token 过期 | 检查 `Authorization` 头与 Server 校验 |
| 连接超时 | 地址/端口/防火墙 | curl 手测（04 篇）；检查绑定地址与容器映射 |
| SSE 连不上 | 用了废弃的 SSE 端点 | 2026-07 规范统一走 Streamable HTTP |
| 偶发断连 | 网络抖动/Server 重启 | 客户端重试；无状态协议天然可重连 |

**关键验证**（stdio 与 HTTP 各一条）：

```bash
# stdio：手发 tools/list，应返回 JSON
printf '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}' | uv run python server.py

# HTTP：curl 调用，应返回 JSON 或 SSE
curl -s -X POST http://127.0.0.1:8080/mcp -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

## 4. 第三层：工具调用问题

| 现象 | 根因 | 解法 |
|---|---|---|
| tools/list 为空 | 注册代码未执行 | 检查装饰器是否在导入时执行；入口是否正确 |
| 工具名找不到 | 拼写/命名空间 | `list_tools()` 先看准确名字 |
| 参数校验报错 | 类型/必填不符 | 检查 Schema；给默认值减少必填项 |
| 返回内容不可读 | 返回了非文本对象 | 转成字符串；`content[0].text` |
| 工具执行抛异常 | 业务代码 bug | Server stderr 看堆栈；try/except 转友好错误 |
| 调用超时 | 长任务/死锁 | 用 async、加进度通知、调大超时 |
| 模型不调用工具 | 描述不清 | docstring 写"做什么+何时用"；先手动验证工具本身 |

**错误返回的规范姿势**（生产要这么做，动手阶段先学会）：

```python
@mcp.tool
def divide(a: float, b: float) -> str:
    """除法。"""
    if b == 0:
        return "错误：除数不能为 0"   # 返回友好错误文本，而非抛异常
    return str(a / b)
```

## 5. 第四层：协议与版本问题

| 现象 | 根因 | 解法 |
|---|---|---|
| `UnsupportedProtocolVersionError` | 版本协商失败 | 每请求 `_meta` 带协议版本；SDK 版本对齐 |
| `Method not found` | 调了未实现方法 | 2026-07 规范：`server/discover` 先发现；确认实现 |
| JSON-RPC 解析失败 | stdout 被 print 污染 | 日志写 stderr！`print(..., file=sys.stderr)` |
| `-32600` 等错误码 | 请求格式错 | 检查 jsonrpc/id/method/params 结构 |
| 初始化失败 | v1 与 v2 混用 | 客户端与服务端 SDK 同代（01 篇 v2 迁移表） |
| 响应为空 | 进程提前退出 | 先看进程层；再查响应是否进了 stderr |

**协议排错神器**：Inspector 的每个调用都展示完整 JSON-RPC 请求/响应——协议层问题一律先挂 Inspector 复现。

## 6. Windows 专项坑

| 坑 | 现象 | 解法 |
|---|---|---|
| Inspector Proxy 起不来 | `-32001 Request timed out`（v0.21+ 已知问题） | 换 HTTP/SSE 传输；升级 Node |
| `uv` 找不到 | 子进程启动失败 | 用 `uv.exe` 绝对路径或 `python -m` |
| 中文路径乱码 | 工具名/文件乱 | 项目放纯英文路径；终端 `chcp 65001` |
| curl 不存在 | 手测命令失败 | 用 `curl.exe`（Win10+ 自带）或 PowerShell `Invoke-RestMethod` |
| 端口占用不释放 | 重启后端口被 TIME_WAIT 占用 | 换端口；`netstat -ano` + `taskkill /PID` |

## 7. 排错速查表

| 症状 | 第一排查动作 | 常见根因 |
|---|---|---|
| 什么都连不上 | 终端手动跑 Server | 依赖/路径 |
| stdio 静默断开 | 看 stderr | 进程崩溃 |
| HTTP 404/401 | curl 手测 | 端点/Token |
| 工具列表空 | Inspector 连一次 | 注册未执行 |
| 调用报错不可读 | 看 Server 堆栈 | 业务异常未捕获 |
| 版本相关报错 | 查 SDK 版本 | v1/v2 混用 |
| 偶发超时 | 重试+日志 | 长任务/资源竞争 |

**排错纪律**：一次只改一个变量；每步先复现再修；修完必跑回归（最小客户端调用）。**能复现的 bug 都是好 bug——最怕"偶尔出现"**，那种先补日志。

> 🎯 **核心要点**：MCP 排错 80% 集中在三件事——**进程没跑起来（依赖/路径）、传输没通（端点/Token/端口）、stdout 被污染（print 日志）**。记住四层定位法（进程→传输→协议→应用）与"终端手跑 + curl/printf 手测 + Inspector 复现"三步排查，本阶段的坑基本都能半小时内定位。
