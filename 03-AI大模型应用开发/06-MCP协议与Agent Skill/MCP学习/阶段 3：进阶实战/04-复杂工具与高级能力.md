## 1. 工具 Schema 设计规范

工具的"接口"是 JSON Schema——模型只看 Schema 决定是否调用、传什么参数。设计三原则：

| 原则 | 做法 | 反例 |
|---|---|---|
| 描述写"做什么+何时用+边界" | `"""查询订单（订单号必填；物流信息在另一个工具）。"""` | `"""订单查询。"""` |
| 类型收窄 | `Literal["pending","paid"]`、枚举、正则 | 裸 `str` 让模型乱传 |
| 参数即决策负担 | 可选参数拆独立工具；必填参数用默认值填充 | 一个工具 8 个可选参数 |

```python
from typing import Literal
from fastmcp import FastMCP

mcp = FastMCP("order")

@mcp.tool
def get_order(
    order_id: str,                       # 必填：业务主键
    include_items: bool = False,         # 可选：默认关闭（少传少错）
) -> dict:
    """按订单号查询订单。

    何时用：用户问订单状态/金额时。
    何时不用：查物流走 get_shipping；查商品走 get_product。
    边界：order_id 为平台内部单号，不接受第三方单号。
    """
    return order_service.fetch(order_id, include_items)
```

**Schema 大小控制**：工具描述 100-200 token 最优（多了模型注意力分散）；10 个以内工具最优（见下节）；参数描述只在**模型可能传错**时写（业务含义、单位、格式）。

## 2. 工具爆炸治理

工具数量是 MCP Server 最现实的质量指标：

| 工具数 | 模型表现 | 结论 |
|---|---|---|
| 5-7 | 最佳——高意图工具直接命中 | 目标区间 |
| 10-25 | 可用，选择开始犹豫 | 可接受上限 |
| 50+ | 选择失误明显上升 | 需要治理 |
| 128+ | OpenAI 系模型硬 API 上限 | 必须治理 |

**四个治理手段**：

| 手段 | 机制 | 适用 |
|---|---|---|
| 合并 | 相关工具合成"灵活单工具"（`action` 参数） | REST 端点 1:1 映射（工具爆炸重灾区） |
| 动态加载 | 按用户/上下文只暴露子集（FastMCP tags + disable） | 多租户：写工具对只读用户隐藏 |
| code mode | FastMCP 3.1：沙箱 Python 执行代替逐个工具；**工具列表 token 降 99.9%**（Cloudflare 实测） | 数据探索类 Server |
| 分层 Server | 按域拆 Server（订单/库存/用户），客户端按需挂载 | 大型组织 |

```python
@mcp.tool(tags={"write"})
def update_order(order_id: str, status: str) -> str:
    """更新订单状态（写操作，需授权）。"""
    ...

# 只读模式下隐藏全部写工具
if read_only_mode:
    mcp.disable(tags={"write"})
```

> 💡 OpenAPI 集成（FastMCP 支持从 REST 规格自动生成工具）是工具爆炸的典型来源——**1:1 端点→工具映射必然爆炸**，必须配合过滤/动态加载/合并使用。

## 3. 流式输出

需要边生成边返回（长文本、日志流、推理过程）时用异步生成器：

```python
import asyncio

@mcp.tool
async def stream_logs(n: int = 100) -> str:
    """流式返回最近 n 条日志。"""
    async def gen():
        for line in await log_service.tail(n):
            yield line + "\n"
            await asyncio.sleep(0.05)   # 模拟生产节奏
    return "".join([l async for l in gen()])  # 或框架原生流式返回
```

**流式的适用边界**：模型消费端对"流"的感知有限——**优先返回结构化摘要**，流式留给"必须全量呈现"的场景（日志、代码、翻译长文）。别为炫技把列表型结果流式化——一个 JSON 数组分页更省事（第 6 节）。

## 4. 长任务：Tasks 扩展

超过正常超时（数十秒-分钟级）的操作用任务系统（2026 规范：`io.modelcontextprotocol/tasks` 扩展，SEP-2133）：

```text
客户端 ── 调用(长任务工具) ────────────▶ 服务器
◀─ 立即返回 {task_id: "task-456", status: "running"}
客户端 ── tasks/get {task_id:"task-456"} ─▶ 服务器
◀─ {status:"running", progress:0.4, message:"处理第 40/100 个文件"}
... 轮询直到 ...
◀─ {status:"completed", result:{...}}
```

| 要点 | 说明 |
|---|---|
| 工具先返句柄 | `task_id` 即无状态句柄（03 篇模式）：状态在任务存储，客户端持句柄轮询 |
| 轮询而非推送 | 无状态规范下客户端主动 `tasks/get`（无会话可推） |
| 进度 | `progress` 字段（0-1）+ `message`，客户端可展示 |
| FastMCP 实现 | `pip install "fastmcp[tasks]"`，框架自动管理任务生命周期 |

**适用判断**：任务 >30 秒 或 客户端超时内无法完成 → Tasks；否则直接返回。**别把短任务做成任务**——轮询开销 > 收益。

## 5. 进度与取消

**进度**：长操作（非 Tasks 的普通工具也可）通过进度通知表达（legacy 有 `notifications/progress`；无状态规范下并入 `_meta`/MRTR 体系）：

| 机制 | 客户端可见效果 |
|---|---|
| 进度回调（ctx 提供） | 界面进度条/百分比 |
| 阶段消息 | "连接数据库… / 拉取数据… / 生成报告…" |

**取消**：无状态规范下"取消"= 客户端不再轮询（Tasks 场景）；**工具内要实现幂等与中断点**——长循环里检查取消标志，正在写的外部副作用（数据库/文件）在取消时回滚或标记失败。**"取消不清理"是长任务最常见的缺陷**。

## 6. 分页：大量结果怎么办

返回大量数据时，三种模式：

| 模式 | 机制 | 适用 | 注意 |
|---|---|---|---|
| 服务端分页 | `page/page_size` 参数 + 返回 `next_token` | 查询列表 | 句柄式游标（无状态友好） |
| 客户端提取 | 返回文档/文本，模型自取 | 小数据量 | 别滥用（token 成本） |
| 摘要优先 | 默认返回摘要+总数，详情二次调用 | 分析报告 | 交互最友好 |

```python
@mcp.tool
def list_orders(page: int = 1, page_size: int = 20) -> dict:
    """分页查询订单列表。

    返回 next_token 表示还有下一页；无 next_token 即末页。
    """
    items, total = order_service.list(page, page_size)
    return {
        "items": items,
        "total": total,
        "next_token": str(page + 1) if page * page_size < total else None,
    }
```

**为什么用游标不用页码**：无状态规范下页码依赖"服务器记得总页数"（易变）；游标（`next_token`）是无状态句柄的自然延伸——即使数据中途变化，游标仍稳定。

## 7. 资源模板与提示词参数化

**Resources（资源）**：只读数据面，`@mcp.resource("uri")` 暴露文件/文档/配置：

```python
@mcp.resource("vault://docs/{doc_id}", mime_type="text/markdown")
def get_doc(doc_id: str) -> str:
    """按 ID 返回文档内容（资源模板：参数化 URI）。"""
    return vault.read(doc_id)
```

| 能力 | 说明 |
|---|---|
| 资源模板 | `{param}` 参数化 URI：客户端按模板列出并取值 |
| mime_type | `text/markdown`、`application/json`——客户端决定如何渲染 |
| 静态资源 | 固定 URI：服务说明、FAQ、配置 |

**Prompts（提示词）**：可复用模板 + 参数：

```python
@mcp.prompt
def code_review(language: str, focus: str = "security") -> str:
    """生成代码评审提示词。"""
    return f"请以{language}工程师视角评审：{focus}。"
```

**三原语的正确分工**：**Tools = 执行动作；Resources = 读数据；Prompts = 复用提示**。常见错误：把只读数据做成工具（模型会反复调用浪费 token）、把提示词做进系统提示（无法参数化复用）。

## 8. 输入校验：可信与不可信边界

模型传参**不可信**（可能幻觉、可能被提示注入污染）——工具侧三层校验：

| 层 | 校验内容 | 手段 |
|---|---|---|
| Schema 层 | 类型/枚举/必填 | pydantic/Zod 自动（FastMCP 先于中间件执行，01 篇提过） |
| 业务层 | 存在性/状态/权限 | 查询前校验：订单存在吗？归属当前用户吗？ |
| 危险操作层 | 金额上限、路径白名单、URL 黑名单 | 转账限 5000、文件只读目录、URL 只允许内网白名单 |

```python
@mcp.tool
def fetch_url(url: str) -> str:
    """抓取网页内容（仅允许 https 外部站点）。"""
    if not url.startswith("https://"):
        return ToolResult(is_error=True, content="仅支持 https 链接")
    if is_private_ip(url):            # 防 SSRF 核心（05 篇）
        return ToolResult(is_error=True, content="不允许内网地址")
    ...
```

## 9. TypeScript 对照：Zod 定义工具

TS 生态（官方 SDK）用 Zod 定义 Schema，与 Python 的"类型注解+docstring"是同一套工程原则：

```typescript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { z } from "zod";

const server = new McpServer({ name: "order-server", version: "1.0.0" });

server.registerTool(
  "get_order",
  {
    description: "按订单号查询订单。何时用：用户问订单状态/金额时。边界：平台内部单号。",
    inputSchema: {
      order_id: z.string().describe("平台内部订单号"),
      include_items: z.boolean().optional().describe("是否包含商品明细"),
    },
    outputSchema: z.object({
      order_id: z.string(),
      status: z.enum(["paid", "shipped", "completed", "cancelled"]),
      total: z.number(),
    }),
  },
  async (args) => ({ order_id: args.order_id, status: "...", total: 0 })
);
```

**Python vs TS 对照表**：

| 能力 | Python（FastMCP） | TypeScript（官方 SDK） |
|---|---|---|
| Schema 生成 | 类型注解+docstring 自动 | Zod 显式声明 |
| 输出 Schema | 返回类型注解（3.4+ 支持） | `outputSchema` 显式 |
| 工具版本 | `@mcp.tool(version="1.0")` | 注册时 version 字段 |
| 依赖注入 | Depends/lifespan | 闭包/上下文对象 |
| 流式 | async 生成器 | `ReadableStream`/异步迭代 |

**工具版本化**（Schema 稳定信号）：版本号随**接口形态**变（参数/描述/返回结构），不随实现细节变；客户端可以按版本缓存与适配（配合 03 篇 `ttlMs` 缓存）。

## 10. 动态加载与多租户

"不同用户看到不同工具"是大型 Server 的常见需求，实现三层：

| 层 | 机制 | 粒度 |
|---|---|---|
| 工具级标签 | `tags={"write"}` + `mcp.disable(tags=...)` | 按能力分组整体开关 |
| 租户过滤 | 中间件按 `ctx.auth.user` 过滤工具列表 | 按用户个性化 |
| Server 级组合 | 按域拆 Server，客户端按需挂载 | 按业务域 |

```python
# 租户过滤中间件（01 篇中间件 + 04 篇动态加载）
class TenantFilter(Middleware):
    async def before(self, context):
        user = context.auth.user if context.auth else None
        if user and user.plan == "free":
            # 免费用户隐藏高级工具（也可在工具层用 tags 实现）
            ...
```

**为什么动态加载重要**：工具列表是每请求上下文的一部分——**列表越长，模型决策质量越差、token 越贵**。免费/专业分层、只读/读写分层、部门数据隔离，都能用"按用户裁剪工具"表达——**裁剪比"工具内做权限判断"更省 token 也更安全**（看不见的工具不会被调用）。

## 11. 错误码设计规范

结构化错误（01 篇 ToolResult）落地为错误码体系：

| 错误域 | 码 | 含义 | 客户端动作 |
|---|---|---|---|
| 输入 | INVALID_ARGUMENT | 参数不合法 | 让模型改参数重试 |
| 业务 | NOT_FOUND | 对象不存在 | 停止尝试，向用户说明 |
| 业务 | CONFLICT | 状态冲突（重复操作） | 提示用户确认现状 |
| 权限 | PERMISSION_DENIED | 无权限 | 引导授权（02 篇） |
| 外部 | UPSTREAM_TIMEOUT | 下游超时 | 稍后重试（幂等工具才可自动重试） |
| 基础设施 | INTERNAL | 内部错误 | 报障，不重试 |

```python
@mcp.tool
def cancel_order(order_id: str) -> ToolResult:
    """取消订单（幂等：已取消返回成功）。"""
    result = order_service.cancel(order_id)
    if result == "already_cancelled":
        return ToolResult(content="订单已取消", structured_content={"code": "CONFLICT", "idempotent": True})
    if result == "not_found":
        return ToolResult(is_error=True, content="订单不存在", structured_content={"code": "NOT_FOUND"})
    return ToolResult(content="已取消", structured_content={"code": "OK"})
```

**错误码的设计价值**：模型（和排障工程师）能按码决策——"CONFLICT 且幂等 → 告诉用户即可；UPSTREAM_TIMEOUT → 重试；PERMISSION_DENIED → 换授权路径"。**错误码是工具与调用方之间的另一份契约**，与 Schema 同等重要。

## 12. 工具设计反模式清单

| 反模式 | 症状 | 修正 |
|---|---|---|
| 描述只写功能名 | 模型在"该不该用"上犹豫/误用 | 写"何时用/何时不用/边界" |
| 参数全用裸 str | 模型传"订单状态"字符串时瞎猜 | 枚举/Literal 收窄 |
| 一个工具十参数 | 模型漏参/传错 | 拆工具或默认值兜底 |
| 只读数据做成工具 | 反复调用浪费 token | 改 Resources（04 篇第 7 节） |
| 工具名含糊 | get_info/set_data 无辨识度 | 动词+对象（get_order/update_status） |
| 结果不结构化 | 文本拼凑，模型无法解析 | ToolResult + structured_content |
| 无边界说明 | 用户问"查物流"时调了"查订单" | 描述边界，让模型分流 |

**快速自查**：拿自己的工具列表给一个没读过代码的同事看——他能否凭描述+Schema 正确使用每个工具？不能，就按上表修正。

## 13. 面试速记

1. 工具质量 = Schema（描述/类型/默认值）× 数量（5-7 个）× 机制（任务/分页/流式按需）× 错误（错误码契约）。
2. 工具爆炸三解：合并、动态加载、code mode（token 降 99.9%）。
3. 长任务 = 句柄 + 轮询（tasks 扩展），不是推送。
4. 分页用游标不用页码——无状态规范的自然选择。
5. 三层校验：Schema 层、业务层、危险操作层（白名单）。

## 14. 工具生命周期管理

工具不是写完就完事，它与 API 一样有生命周期：

| 阶段 | 动作 | 注意 |
|---|---|---|
| 设计 | Schema 评审（描述/类型/数量） | 先过反模式清单（04 篇第 12 节） |
| 注册 | 打标签（write/租户）、定版本 | 版本随接口变（04 篇第 9 节） |
| 发布 | 进测试矩阵（06 篇用例矩阵） | 高危工具优先安全用例 |
| 运维 | 监控调用分布（07 篇） | 单工具占比异常=模型循环信号 |
| 变更 | 加参/改描述=新版本 | 已发布工具 Schema 变更需版本化 |
| 弃用 | 明确废弃+替代指引 | 模型可能仍在用旧工具，弃用要留过渡期 |

**变更纪律**：工具的 Schema 是给模型看的契约——**改参数语义必须发新版本**，旧版本保留一段时间（客户端/模型会缓存工具列表）；弃用工具在描述里写"已废弃，请用 get_order_v2"，比直接删除对存量用户更友好。

> 🎯 **核心要点**：复杂工具的工程主线 = **Schema 控输入（描述/类型/默认值，Python 注解与 TS Zod 同原则）→ 数量控选择（5-7 个工具，爆炸即治理）→ 动态加载控可见性（按租户/分层裁剪）→ 机制控形态（流式/任务/进度/分页各归其位）→ 错误码控契约（结构化错误可决策）→ 校验控边界（三层校验，危险操作白名单）→ 生命周期控变更（版本化与弃用纪律）**。模型是聪明的调用者，但也是会犯错、会被污染的调用者——Schema、错误码与校验是"聪明且安全"的底座，反模式清单是日常自查的尺子。
