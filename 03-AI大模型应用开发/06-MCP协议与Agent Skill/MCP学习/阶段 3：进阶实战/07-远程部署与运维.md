## 1. 部署形态总览

| 形态 | 传输 | 适用 | 关键点 |
|---|---|---|---|
| 本机 stdio | stdio | 个人开发 | 无网络面，最简单 |
| 云 VM/容器 | Streamable HTTP | 生产主力 | TLS + LB + 监控 |
| 容器编排（K8s） | Streamable HTTP | 多实例/弹性 | 无状态后水平扩容无痛 |
| Serverless/Edge | Streamable HTTP | 低频/突发 | 冷启动可接受；状态必须外置 |
| 网关代理 | HTTP（经网关） | 企业合规 | 认证/审计/扫描集中在网关（08 篇） |

**2026 部署前提**：Streamable HTTP 是唯一远程传输（HTTP+SSE 已弃用）；无状态规范让"云 VM/容器/K8s/Serverless"全部可行——**会话时代的粘性约束已不存在**（03 篇）。

## 2. 容器化：Docker 生产镜像

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml ./
RUN pip install --no-cache-dir .
COPY src/ ./src/
# 非 root 用户（安全基线）
RUN useradd -m mcp && chown -R mcp:mcp /app
USER mcp
# 健康检查：MCP 端点探活（见第 6 节）
HEALTHCHECK CMD python -m healthcheck || exit 1
EXPOSE 8080
CMD ["uvicorn", "server:app", "--host", "0.0.0.0", "--port", "8080"]
```

**容器化清单**：非 root 运行、只装运行依赖（镜像瘦身）、`--no-cache-dir` 锁依赖、健康检查、日志走 stdout（容器日志驱动）、内存限制（`--memory`）、**敏感配置只从环境注入**（01 篇）。

**启动方式**：

```bash
docker build -t my-mcp-server .
docker run -d --name mcp -p 8080:8080 \
  -e DATABASE_URL=... -e API_KEY=... \
  --memory=512m --restart=unless-stopped \
  my-mcp-server
```

## 3. TLS 与反向代理

MCP HTTP 端点必须 TLS（Bearer 令牌裸跑明文=白送攻击者）：

```nginx
# Nginx 反代：TLS 终结 + 方法级路由（SEP-2243 头）
server {
    listen 443 ssl;
    server_name mcp.example.com;
    ssl_certificate     /etc/letsencrypt/live/mcp.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/mcp.example.com/privkey.pem;

    location /mcp {
        proxy_pass http://mcp-backend:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        # 透传 MCP 强制头：Mcp-Method / Mcp-Name
        proxy_set_header Mcp-Method $http_mcp_method;
        proxy_set_header Mcp-Name $http_mcp_name;
    }
    # OAuth 元数据端点
    location /.well-known/ { proxy_pass http://mcp-backend:8080; }
}
```

**要点**：TLS 1.2+（默认 1.3）、证书自动续期（certbot）、**透传 `Mcp-Method`/`Mcp-Name` 头**（代理层别吞掉）、`.well-known` 路径必须可达（客户端发现依赖它，02 篇）。

## 4. 无状态负载均衡

无状态规范的最大部署红利（03 篇）：**普通轮询 LB 即可，无需粘性会话**：

```text
客户端 ──▶ LB（round-robin）──▶ 实例 1 / 实例 2 / 实例 3
               │                    （全部无状态，任意实例处理任意请求）
               ▼
         健康检查：/healthz 失败实例自动摘除
```

**扩容即部署**：K8s HPA 按 CPU/请求数扩；无状态让"缩容零风险"（不像会话时代掉线）。**唯一要求**：跨请求状态必须外置（数据库/Redis/对象存储）——03 篇句柄模式的收益在此兑现。

**LB 层注意事项**：透传 MCP 强制头；响应缓存按 `cacheScope`/`ttlMs` 头（SEP-2549）配置（`tools/list` 可缓存）；超时设置要覆盖长任务轮询周期。

## 5. Serverless 与边缘部署

无状态 + 请求级计费 = Serverless 天然适配：

| 优势 | 注意 |
|---|---|
| 零空闲成本（低频 Server 神器） | 冷启动延迟（函数平台 2026 已压到亚秒级） |
| 自动扩缩到零 | 任务存储必须外置（Tasks 扩展依赖 Redis/DB） |
| 边缘就近（Cloudflare Workers 类） | 认证元数据端点要一起部署 |
| 安全隔离强（每请求新容器） | 长连接/流式场景受限 |

**Serverless 适用判断**：低频个人工具、内部自动化、突发负载（AI 事件驱动）→ 合适；高频低延迟（每请求 <10ms 要求）→ 传统 VM。**fastmcp-remote 让 stdio-only 客户端也能接 Serverless 端点**（第 9 节）。

## 6. 健康检查与启动就绪

| 探针 | 端点 | 语义 |
|---|---|---|
| 存活 | `/healthz` | 进程活着（返回 200） |
| 就绪 | `/readyz` | 依赖就绪（DB 连通、任务存储可写） |

**就绪检查要真实**：`/readyz` 里实际 ping 数据库/下游——否则"进程活着但请求全 500"的假健康（01 篇 lifespan 启动校验的运维版）。K8s 用 `startupProbe`+`readinessProbe` 分离"冷启动等待"与"运行中就绪"。

**优雅退出**：收到 SIGTERM → 停止接收新请求 → 等 in-flight 请求完成（超时兜底）→ 关依赖（lifespan 清理）→ 退出。**"立即 kill"会让正在执行的工具中途死掉**（长任务尤其致命）。

## 7. 速率限制与配额

模型调用比人快得多——限流是防"一个循环烧光预算"的最后防线：

| 层 | 限流对象 | 手段 |
|---|---|---|
| 认证层 | 每用户/每令牌 | 令牌速率限制（Redis 计数） |
| 工具层 | 高危工具（外发/写） | 每用户每日配额 |
| 后端层 | 下游 API | 透传限流（上游配额） |
| 传输层 | 每 IP | 反代 `limit_req` |

```nginx
# Nginx 层基础限流：每 IP 20 req/s 突发 40
limit_req_zone $binary_remote_addr zone=mcp:10m rate=20r/s;
location /mcp {
    limit_req zone=mcp burst=40 nodelay;
    proxy_pass http://mcp-backend:8080;
}
```

**超时三件套**（配合 04 篇）：调用超时（普通工具 30s）、任务超时（Tasks 长轮询）、连接空闲超时（防挂死连接吃资源）。

## 8. 可观测性：OTel 三支柱

FastMCP 3.0 起内建 OpenTelemetry 支持，配合 W3C Trace Context（03 篇 SEP-414）全链路串起：

| 支柱 | 内容 | MCP 特有要点 |
|---|---|---|
| 指标 | 请求数、延迟直方图、错误率、令牌消耗 | 按工具名分维度（哪个工具慢） |
| 日志 | 结构化 JSON（含 trace_id） | 中间件"记键不记值" |
| 追踪 | 请求→工具→下游 API 全链路 | **MCP 头自带 trace 传播**，链路自动连通 |

**生产监控四告警**：错误率突增（>1%）、P99 延迟超阈值、认证失败率（被攻击信号）、限流触发率。**排障三步**：trace 找到慢调用 → 日志看工具参数与结果码 → 指标确认影响面——先止血、后根治。

## 9. fastmcp-remote：桥接本机客户端

**痛点**：Claude Code/部分宿主只支持 stdio 传输；你的 Server 在云端（HTTP）。

**解法**：`fastmcp-remote`（FastMCP 3.4.0）——一个本地 stdio 代理，把本机宿主连到远程 HTTP Server：

```bash
# 本机起一个 stdio 代理，内部桥接远程端点
fastmcp-remote https://mcp.example.com/mcp
# Claude Code 配置指向这个代理（像配置本地 Server 一样）
```

**特性**：HTTPS Server 自动启用 OAuth（代理完成认证流程）；支持显式 Bearer/自定义头；**fail-loud**——后端不可达/认证失败时初始化失败大声报错（而不是静默返回空工具列表）；令牌空闲期存活（`fastmcp_access_token_expiry_seconds` 控制，自动透明续期）。

**桥接的运维含义**：客户端配置零改动（还是 stdio 本地路径）；认证与刷新在代理层完成；**代理是安全边界**——本机代理进程权限即云 Server 访问权限，别在共享机器上跑。

## 10. Docker Compose 全家桶

单机生产的最小全家桶（Server + 限流存储 + 监控）：

```yaml
# docker-compose.yml
services:
  mcp-server:
    build: .
    ports: ["8080:8080"]
    environment:
      MCP_DATABASE_URL: postgres://mcp:pass@db/mcp
      MCP_API_KEY: ${MCP_API_KEY}          # 从宿主环境注入
      MCP_READ_ONLY: "true"
    depends_on:
      db: { condition: service_healthy }
      redis: { condition: service_healthy }
    deploy:
      resources:
        limits: { memory: 512m, cpus: "1.0" }
    restart: unless-stopped

  db:
    image: postgres:16
    healthcheck: { test: ["CMD", "pg_isready"], interval: 10s }
    volumes: ["pgdata:/var/lib/postgresql/data"]

  redis:
    image: redis:7
    healthcheck: { test: ["CMD", "redis-cli", "ping"], interval: 10s }

  prometheus:
    image: prom/prometheus
    volumes: ["./prometheus.yml:/etc/prometheus/prometheus.yml"]
```

**K8s 最小部署**（无状态让 HPA 直白）：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: mcp-order }
spec:
  replicas: 3                    # 无状态：随便扩缩
  selector: { matchLabels: { app: mcp-order } }
  template:
    metadata: { labels: { app: mcp-order } }
    spec:
      containers:
        - name: mcp
          image: myorg/order-mcp:1.2.0
          ports: [{ containerPort: 8080 }]
          envFrom: [{ secretRef: { name: mcp-secrets } }]
          readinessProbe:
            httpGet: { path: /readyz, port: 8080 }
          resources:
            requests: { memory: 256Mi }
            limits: { memory: 512Mi }
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: mcp-order }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: mcp-order }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
```

## 11. OTel 接入与监控清单

**FastMCP 3.x OTel 接入**（三支柱一键）：

```python
from fastmcp.observability import configure_otel

configure_otel(
    service_name="order-mcp",
    otlp_endpoint="http://otel-collector:4317",   # 或直接厂商端点
)
```

**监控指标清单**（按重要性排序）：

| 指标 | 告警阈值 | 含义 |
|---|---|---|
| 错误率（工具维度） | >1% 持续 5 分钟 | 工具故障/被滥用 |
| P99 延迟 | >2s | 下游慢/拥塞 |
| 401 率 | 突增 >10% | 被扫描/令牌问题 |
| 限流触发率 | >5% | 用户行为异常/配额太小 |
| 工具调用分布 | 单工具占比 >90% | 模型陷入循环调用（提示注入信号） |
| 令牌消耗（可选） | 预算超支 | 成本失控 |

**排障三步**（结合 05 篇事件响应）：trace 定位慢请求 → 日志看参数与错误码 → 指标量化影响面。**"先止血（限流/禁用工具）、后根治（修代码）、最后复盘（补测试）"**——生产事故的通用节奏。

## 12. 故障演练清单

上线前至少演练一次：

| 场景 | 演练 | 预期 |
|---|---|---|
| 实例崩溃 | kill 一个 pod | LB 摘除，请求由其他实例完成（无状态红利） |
| 数据库故障 | 停 db | /readyz 变红，实例不再接流量（不 500 风暴） |
| 令牌泄露 | 撤销令牌 | 旧令牌立即 401（OAuth 可撤销性） |
| 流量突增 | 压测到 2 倍容量 | HPA 扩容、限流兜底、P99 可控 |
| 写工具被滥用 | 模拟循环调用 | 配额拦截 + 审计日志可溯 |

| 告警 | 动作 | 升级条件 |
|---|---|---|
| 错误率 >1% | 查最近发布；trace 定位错误码分布 | 持续 15 分钟→回滚 |

## 15. 部署形态决策与回滚流程

**部署形态决策表**：

| 场景 | 推荐 | 理由 |
|---|---|---|
| 内部团队工具、低延迟要求 | 云 VM/容器 | 可控、便宜、延迟稳定 |
| 对外产品、弹性需求 | K8s + HPA | 无状态扩容无痛（03/07 篇） |
| 低频个人工具、成本敏感 | Serverless/Edge | 零空闲成本，冷启动可接受 |
| 受监管/内网 | 企业网关 + 自托管 | 合规：扫描/审计/隔离（08 篇） |
| 混合（本地客户端+云 Server） | fastmcp-remote 桥接 | 客户端配置零改动 |

**版本回滚流程**（无状态让回滚近乎无痛）：

1. 回滚 = 部署旧镜像 + 切流（LB/发布系统一键）；
2. 令牌与数据兼容检查：旧版本是否兼容新令牌的 aud/scope？（02 篇）
3. 任务存储兼容：进行中的长任务句柄新老版本都能读？（03/04 篇）
4. 回滚后验证：健康检查 + 冒烟 + 指标对比。

**回滚纪律**：**"新版本 Schema 变更"是回滚的地雷**——客户端已缓存新工具列表，回滚后按旧 Schema 调用会报错；策略：Schema 变更用新工具名（v2），保持回滚空间。

**SLO 与错误预算**（运维的量化管理）：为 Server 定义服务等级目标，如"月度可用性 99.9%、P99 延迟 <2s、错误率 <1%"；错误预算 = (1 - SLO) × 月度请求量——**预算花完就冻结发布**，强制先修稳定性。MCP Server 的 SLO 特别要包含"认证失败率"（被攻击/配置错误的信号）与"限流触发率"（配额设计是否合理）。**没有 SLO 的运维是"随缘"，有 SLO 的运维是"工程"**——SLO 让"多稳定才算稳定"变成可讨论、可度量、可问责的数字。

**部署配置基线表**（上线前环境变量核对）：

| 变量 | 生产值示例 | 缺失后果 |
|---|---|---|
| MCP_DATABASE_URL | postgres://…（只读账号） | 启动拒绝（01 篇） |
| MCP_READ_ONLY | true（默认） | 写工具意外开放 |
| MCP_JWKS_URL | https://auth…/jwks.json | 认证不生效（裸奔） |
| MCP_LOG_LEVEL | info（不含 debug 密钥） | debug 日志可能泄密 |
| MCP_TOKEN_EXPIRY_SECONDS | 3600 | 令牌生命周期失控 |
| 反代 TLS 证书 | 自动续期配置 | 证书过期=服务中断 |

**配置核对的意义**：**环境变量即安全策略**——read_only 决定写工具生死、jwks_url 决定认证生死、日志级别决定泄密面。上线清单里加"配置核对"一行，比任何代码审查都便宜。

**运维排障的 MCP 特色**：普通服务的"网络问题"在 MCP 场景多了三层——传输（stdio/HTTP 连接是否通）、协议（版本协商/resultType/强制头是否合规）、工具语义（参数/错误码/句柄）。排障顺序：先看 trace（请求到没到服务器）→ 再看日志（工具参数与错误码）→ 最后看指标（影响面）——**"客户端列表为空"先查 discover 与版本协商，而不是查网络**，这是 MCP 排障与普通 Web 排障最大的不同。**运维工具三件套**：日志查询（按 request_id/trace_id）、指标面板（工具维度 P99/错误率）、配置快照（环境变量与版本可回溯）——三者齐备，"换个环境就报错"类问题五分钟定位。**部署即文档**：部署手册要写"如何从零重建"（镜像构建、配置清单、数据迁移）而非只有"如何升级"——灾难恢复演练时，从零重建手册才是救命文档。

> 🎯 **核心要点**：远程部署 = Streamable HTTP + Docker（非 root/健康检查/优雅退出）+ TLS 反代（透传 MCP 头 + .well-known 可达）+ 无状态轮询 LB/Serverless + 限流超时 + OTel 三支柱 + 故障演练 + 值班手册 + 回滚流程。**无状态是 2026 部署范式的核心资产**：粘性会话时代的所有拓扑限制消失，运维退化为"普通 Web 服务"的成熟套路——而 fastmcp-remote 把"只能本机的客户端"也解放了。上线前确认两件事：写工具禁用开关可用、令牌撤销可用。
