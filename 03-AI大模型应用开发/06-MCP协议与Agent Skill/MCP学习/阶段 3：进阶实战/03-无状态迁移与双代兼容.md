## 1. 无状态革命：移除了什么

2026-07-28 规范（2026-07-28 定稿）移除了两个"连接级状态"机制：

| 移除项 | SEP | 旧行为 | 新行为 |
|---|---|---|---|
| `initialize`/`initialized` 握手 | SEP-2575 | 连接先握手协商版本与能力 | **无握手**：每请求 `_meta` 自带版本/客户端信息/能力 |
| `Mcp-Session-Id` 头 | SEP-2567 | 服务器发会话 ID，客户端后续携带 | **无会话**：请求互不关联 |

**连带变化**：
- 版本不匹配 → `UnsupportedProtocolVersionError`（每请求检测）；
- 服务器通过每个结果 `_meta.serverInfo` 自报身份；
- `tools/list`、`resources/list`、`prompts/list` **不得再因连接而异**（无会话可关联）；
- 旧 HTTP GET 事件流移除；HTTP+SSE 正式弃用，统一 Streamable HTTP；
- 持续通知并入 `subscriptions/listen`。

> 🎯 一句话：**连接从"有状态的会话"变成"独立请求的序列"**。服务器不能再假设"客户端上次问过我什么"。

## 2. 新增了什么：discover/_meta/头/缓存/trace

| 新机制 | SEP | 作用 |
|---|---|---|
| `server/discover` RPC | — | 服务器必须实现：广播协议版本、能力、身份；客户端可先调用于版本选择；stdio 下可作为向后兼容探测 |
| `_meta` 每请求携带 | — | 协议版本、客户端信息、能力全部随请求走 |
| `Mcp-Method`/`Mcp-Name` HTTP 头 | SEP-2243 | **强制**：负载均衡器不用解析 body 就能路由（方法级路由/限流/调度成为可能） |
| `ttlMs`/`cacheScope` 缓存元数据 | SEP-2549 | 响应可缓存性声明：`tools/list` 等静态结果可缓存（配合无状态 = 缓存友好） |
| W3C Trace Context | SEP-414 | 请求带 trace 头：跨客户端-服务器-下游 API 的完整链路追踪 |
| MRTR（见下节） | SEP-2322 | 替代服务器主动发起的请求（roots/sampling/elicitation） |

**对开发者最直接的三件事**：
1. **静态列表可缓存**：`tools/list` 结果如果标了 `cacheScope`+`ttlMs`，网关/客户端可以缓存——工具列表不再每请求拉取；
2. **方法级路由**：网关按 `Mcp-Method` 头把 `tools/call` 与 `tools/list` 分流到不同后端（读扩散/写收敛架构成为可能）；
3. **全链路 trace**：配 OTel 时，MCP 请求与下游 API 在同一 trace 内——排障不再"断链"。

## 3. MRTR：服务器要输入的协议级答案

服务器（工具执行中）需要用户/客户端额外输入时怎么办？旧规范用"服务器主动发请求"（roots、sampling、elicitation 三件套，各有各的机制）；新规范统一为 **MRTR（Multi Round-Trip Requests，SEP-2322）**：

```text
客户端 ── tools/call {job="提交订单"} ──▶ 服务器
                                        │ 执行中需要用户确认
◀─ InputRequiredResult {resultType:"input_required",
     inputRequests:[{id:"confirm", prompt:"确认下单 100 元？"}],
     requestState:"state-123"} ────────┘
客户端 处理输入（问用户/应用层决策）
客户端 ── tools/call {job="提交订单"} + inputResponses 重发 ──▶ 服务器
◀─ resultType:"complete" 最终结果
```

**关键点**：
- 每个结果必带 `resultType`（`complete` 或 `input_required`）——客户端据此决定是否重发；
- 重发时带 `inputResponses` 与 `requestState`（服务器识别是"同一调用的续集"）；
- **"同一调用"的身份由 requestState 表达**——这正是无状态下的状态：状态随请求走，不留在服务器；
- roots/sampling/elicitation 被 MRTR 吸收，进入 12 个月注解式弃用窗口（见第 7 节）。

**开发影响**：需要人工确认的工具（转账、删除、发布）在新规范下是"返回 input_required → 客户端决定 → 重发"的两段式；FastMCP 3.x 的 ToolResult 与任务系统围绕此设计。

## 4. 状态去哪了：显式句柄模式

无状态后跨调用状态放哪？规范给出的答案是**服务器铸造的显式句柄**：

```python
@mcp.tool
def create_basket(items: list[str]) -> ToolResult:
    """创建购物篮，返回 basket_id。"""
    basket_id = store.create_basket(items)
    return ToolResult(content=str(basket_id),
                      structured_content={"basket_id": basket_id})

@mcp.tool
def checkout(basket_id: str, db=Depends(get_db)) -> ToolResult:
    """结算指定购物篮（basket_id 为 create_basket 返回值）。"""
    total = db.checkout(basket_id)
    return ToolResult(content=f"已结算 {total} 元")
```

| 旧模式（会话） | 新模式（句柄） |
|---|---|
| 服务器记得"上次创建了篮子"，checkout 不用参数 | 客户端把 `basket_id` 显式传回 |
| 状态与连接绑定（LB/故障后丢失） | 状态在句柄里（数据库/对象存储） |
| 模型无法组合（只能线性对话） | **模型可组合**：拿着句柄可并行、可重试、可跨会话 |

**为什么说句柄模式"更强"**：模型可以推理句柄——"订单 123 失败？用 123 重试"；可以并行管理多个句柄；可以持久化句柄跨会话复用。**会话状态本来就是模型的负担，句柄把它变成模型的资产**。

## 5. 双代兼容：modern/legacy/dual-era

规范刻意做成**增量、版本门控的平行路径**：

| 代际 | 版本 | 握手/会话 | 状态 |
|---|---|---|---|
| modern | 2026-07-28 | 无（discover + _meta） | 无状态 |
| legacy | ≤2025-11-25（含 2025-06-18） | initialize/initialized + Session-Id | 有会话 |
| dual-era | 两者都支持 | 现代优先，legacy 兜底 | 按协商 |

**SDK 的现实策略**（Tier 1 SDK：TS/Python/Go/C#）：
- **显式请求无状态模式**（不默认）——保证旧客户端能协商降级；
- 客户端：现代路径（discover + _meta）优先，legacy 服务器拒绝现代发现时**回退 initialize 握手**；会话只在 legacy 路径存在；
- 服务器：同时通告两个版本（如 Respira 的做法），现代客户端走新路径，旧客户端走旧路径；
- **注意**：新版本故意**不**进 `supportedVersions`，直到无状态请求路径完全落地——避免"半吊子协商"。

**双代兼容的实操含义**：你 2026 年的 Server 最好 `dual-era`——`server/discover` 支持 + 旧握手兜底；SDK 升级时看 release notes 确认"stateless mode"开关。

## 6. 迁移检查单：现有 Server 怎么办

| 检查项 | 行动 |
|---|---|
| 依赖会话状态？ | 改为显式句柄（第 4 节）：状态入库/对象存储，句柄作参数 |
| tools/list 随连接变化？ | 改为静态列表（能力差异用参数表达或拆 Server） |
| 用服务器主动请求（roots/sampling）？ | 迁移到 MRTR：`input_required` + `inputResponses` |
| 依赖 SSE/旧 GET 流？ | 迁移 Streamable HTTP + `subscriptions/listen` |
| 结果缺 resultType？ | 补上：`complete` / `input_required` |
| 依赖 Session-Id？ | 删——用 `requestState`/句柄替代 |
| 启动时读 initialize 参数？ | 改从 `_meta` 读（每请求） |
| HTTP 服务？ | 加 `Mcp-Method`/`Mcp-Name` 头（SEP-2243） |
| 对外文档？ | 补 `server/discover` 说明 + 版本表 |
| SDK 版本？ | TS 拆包 server/client；Python FastMCP→MCPServer 路径（阶段 2 已预告的 v2 迁移） |

**迁移优先级**：先删 Session-Id 依赖（多数 Server 只用它做身份）；再改 tools/list 静态化（影响缓存与 LB）；最后上 MRTR（只在有人工确认场景需要）。

**迁移时机判断**：新项目一律按 2026-07-28 写（无历史包袱）；存量项目按"影响面"排序迁移——**先迁移"要上云的"**（无状态红利最大），再迁移"要进网关的"（缓存与路由收益），纯本机个人工具可滞后（legacy 兼容窗口内不迁移也能跑）。**"等所有 SDK 都默认无状态再迁"是常见拖延**——dual-era 的意义就是让你按自己的节奏迁，而不是等生态。

## 7. Extensions 框架与废弃

| 变更 | 详情 |
|---|---|
| Extensions 框架（SEP-2133） | 实验功能移出核心，成为 `io.modelcontextprotocol/tasks` 扩展：`tasks/get` 轮询、`tasks/update` 新增、`tasks/list` 移除 |
| Roots 弃用 | 12 个月"注解式弃用"窗口（SEP-2577）：仍工作但新代码不该用 |
| Sampling 弃用 | 同上——被 MRTR 的 `input_requests` 替代 |
| Logging 弃用 | 同上——被 W3C Trace Context（SEP-414）替代 |

**任务系统的新形态**：长任务（分钟级+）不再"服务器推"，而是：调用返回任务句柄（`tasks/start` 类调用）→ 客户端按需 `tasks/get` 轮询 → `tasks/update` 服务器可更新状态。**这是"无状态 + 句柄模式"在长任务上的体现**——任务状态在任务服务里，客户端持句柄轮询（04 篇详述）。

## 8. 无状态的部署红利

移除会话的直接收益是**部署自由**：

| 能力 | 有会话时代 | 无状态时代 |
|---|---|---|
| 负载均衡 | 需粘性会话/共享会话存储 | **普通轮询（round-robin）即可** |
| 水平扩展 | 会话漂移是头号故障 | 加实例即扩容 |
| Serverless/Edge | 会话状态无处安放 | **天然适配**（每请求冷启动也行） |
| 故障转移 | 会话丢失=用户重来 | 请求级重试即可 |
| 缓存 | 列表结果无法缓存 | `cacheScope`+`ttlMs` 声明后可缓存 |

## 9. 改造对照：一个 Server 的迁移实录

以"购物篮 + 结算"为例，展示迁移前后（旧规范 → 2026-07-28）：

**迁移前（依赖会话状态，错误示范）**：

```python
# 旧：服务器记住"上次的篮子"
_baskets: dict[str, list] = {}          # 会话状态（全局变量 = 反模式）

@mcp.tool
def add_item(item: str) -> str:
    """加入购物篮（隐含当前会话）。"""
    _baskets.setdefault(session_id(), []).append(item)   # 依赖 Session-Id
    return f"已加入 {item}，共 {len(_baskets[session_id()])} 件"

@mcp.tool
def checkout() -> str:
    """结算当前购物篮。"""
    items = _baskets.pop(session_id(), [])               # 隐含状态
    return f"已结算 {len(items)} 件"
```

**迁移后（显式句柄模式）**：

```python
# 新：状态在存储，句柄是显式参数
@mcp.tool
def create_basket() -> str:
    """创建购物篮，返回 basket_id。"""
    basket_id = basket_store.create()                    # 状态入库
    return basket_id

@mcp.tool
def add_item(basket_id: str, item: str) -> str:
    """向指定购物篮加入商品。"""
    count = basket_store.add(basket_id, item)
    return f"已加入 {item}，共 {count} 件"

@mcp.tool
def checkout(basket_id: str) -> str:
    """结算指定购物篮。"""
    total = basket_store.checkout(basket_id)
    return f"已结算 {total} 元"
```

**改造收益对照**：重启不丢篮子（状态在库）；负载均衡任意实例可处理（无会话）；模型可同时管理多个篮子（可组合）；调用可重试（句柄幂等）。**同一个业务，会话是"服务器的记忆"，句柄是"协议的参数"——后者把状态从实现细节变成接口契约**。

## 10. 请求与缓存示例（协议视图）

**请求 _meta 视图**（无状态请求长什么样）：

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "checkout",
    "arguments": {"basket_id": "b-123"},
    "_meta": {
      "protocolVersion": "2026-07-28",
      "clientInfo": {"name": "my-agent", "version": "1.0"},
      "capabilities": {"tools": {"listChanged": false}}
    }
  }
}
```

**缓存声明视图**（SEP-2549，`tools/list` 场景）：

```json
{
  "jsonrpc": "2.0",
  "result": {
    "tools": [...],
    "cacheScope": "server",
    "ttlMs": 300000,
    "resultType": "complete"
  }
}
```

**缓存粒度选择**：`cacheScope: "server"`（全服务器共享，适合静态列表）+ `ttlMs` 决定刷新频率；**写操作类结果绝不标缓存**。网关按此头直接缓存列表响应——这是"无状态 + 缓存头"的组合红利（07 篇）。

## 11. 迁移常见坑

| 坑 | 症状 | 解法 |
|---|---|---|
| 把 requestState 当会话用 | 内存泄漏、状态混乱 | requestState 只标识"同一次 MRTR 的续集"，业务状态用句柄 |
| tools/list 仍按用户返回 | 缓存命中用户 A 的列表给用户 B | 列表静态化；个性化需求拆工具参数 |
| 结果漏 resultType | 新客户端报协议错误 | 全路径补 `complete`/`input_required` |
| 依赖 SSE 订阅 | 事件收不到 | 改 `subscriptions/listen`（轮询/拉取） |
| 版本协商硬编码 | 客户端升级后 UnsupportedProtocolVersionError | 读请求 `_meta` 的版本动态响应 |
| 只支持 modern | 旧客户端全挂 | dual-era：discover + initialize 兜底 |

## 12. 迁移收益量化与面试八问

**迁移收益对照表**（同一个业务，两种实现的运维差异）：

| 运维场景 | 会话时代 | 无状态时代 |
|---|---|---|
| 扩容 | 粘性会话配置 + 会话存储扩容 | 加实例，完毕 |
| 故障转移 | 会话丢失=用户重来 | 请求级重试，无感 |
| 新客户端接入 | 握手协议耦合版本 | discover 自描述 |
| 列表缓存 | 无法缓存（会话相关） | cacheScope+ttlMs 直接缓存 |
| 日志排障 | 会话内事件难串 | W3C trace 全链路 |
| 人工确认 | 服务器主动请求（机制各异） | MRTR 统一 |

**面试八问**：
1. 无状态移除了什么？——initialize/initialized 握手与 Mcp-Session-Id。
2. 状态放哪？——显式句柄（basket_id/job_id），模型可组合可重试。
3. 服务器要输入怎么办？——MRTR：input_required + requestState + inputResponses。
4. 强制 HTTP 头是啥？——Mcp-Method/Mcp-Name，LB 免看 body 路由。
5. 列表为什么能缓存？——无会话 + cacheScope/ttlMs 声明。
6. 旧客户端怎么办？——dual-era：modern 优先、legacy 握手兜底。
7. Roots/Sampling 怎么了？——12 个月注解式弃用，被 MRTR 与 trace 吸收。
8. 部署最大红利？——轮询 LB + Serverless + 水平扩容零负担。

## 13. SEP 术语速查表

| SEP | 名称 | 作用 |
|---|---|---|
| SEP-2575 | initialize 移除 | 握手废除，版本/能力走每请求 _meta |
| SEP-2567 | Mcp-Session-Id 移除 | 会话废除，连接变请求序列 |
| SEP-2243 | 强制 HTTP 头 | Mcp-Method/Mcp-Name：LB 免看 body 路由 |
| SEP-2549 | 缓存元数据 | ttlMs/cacheScope：静态结果可缓存 |
| SEP-414 | W3C Trace Context | 全链路追踪标准 |
| SEP-2322 | MRTR | 服务器要输入统一为 input_required 两段式 |
| SEP-2133 | Extensions 框架 | 任务等实验功能移出核心成扩展 |
| SEP-2577 | 废弃窗口 | Roots/Sampling/Logging 12 个月注解式弃用 |

**记忆锚**：三移除（握手/会话/SSE）、三补位（discover/MRTR/头+缓存+trace）、一框架（Extensions）、一窗口（12 个月废弃）。

**无状态对模型的影响**（为什么规范这么改）：会话时代，状态是"服务器对用户的记忆"——模型根本看不见，也无法管理；句柄时代，状态变成"模型手中的参数"——**模型可以读、可以传、可以组合、可以持久化**。这不仅是工程简化，更是能力升级：一个携带订单句柄的模型可以跨会话恢复业务、并行管理多个业务、失败后用同一句柄重试。**无状态不是"去掉了记忆"，而是"把记忆交给了最聪明的调用者"**——这是 2026 规范设计哲学的核心。

> 🎯 **核心要点**：无状态 = 握手/会话移除（SEP-2575/2567）+ discover/_meta/强制头/缓存/trace 补位 + MRTR 统一服务器要输入 + 显式句柄承载状态 + dual-era 渐进迁移。对开发者：**状态改为句柄、列表改为静态、确认改为 MRTR、日志改为 trace**——四件事做完，你的 Server 就站在 2026 规范上，并白拿轮询 LB 与 Serverless 的部署红利。
