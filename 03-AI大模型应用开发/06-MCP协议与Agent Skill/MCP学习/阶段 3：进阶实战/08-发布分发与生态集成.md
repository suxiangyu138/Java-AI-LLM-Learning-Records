## 1. 官方注册表：MCP 的 npm

**Official MCP Registry**（registry.modelcontextprotocol.io）是 MCP 生态的规范命名空间，2026 年状态：

| 维度 | 现状 |
|---|---|
| 性质 | **元数据注册表**——只存 server manifest，不放代码（代码仍在 npm/PyPI/Docker/GitHub） |
| 接口 | 机器优先的 JSON API，API freeze v0.1 |
| 治理 | Anthropic + GitHub + PulseMCP + Microsoft 联合 |
| 定位 | 官方规范、无排名、无编辑判断——"事实来源"，不是应用商店 |
| 命名验证 | OAuth / DNS / OIDC 三种方式验证命名空间归属 |
| 多格式 | 支持 npm、PyPI、Docker 包与远端 Server 地址 |

**与 npm 的类比**：npm 存包 + 跑脚本；MCP Registry 只存"去哪装 + 装什么版本"的清单——**发布者负责把包托管在包仓库，注册表负责让客户端找到并信任它**。

> ⚠️ 注意：Claude Code 的 `/mcp` 不浏览官方注册表——Anthropic 的 Connectors 目录与插件市场是平行入口。注册表发布是"生态可见性"，不等于"Claude Code 内可见"。

## 2. 发布流程：server.json 与命名空间

**server.json 清单文件**（官方注册表的核心元数据）：

```json
{
  "name": "io.github.myorg/order-server",
  "description": "订单查询与物流跟踪（只读，无写操作）",
  "version": "1.2.0",
  "packages": [
    { "type": "pypi", "package": "myorg-mcp-order", "pypi_version": "1.2.0" }
  ],
  "remote": { "url": "https://mcp.myorg.com/mcp", "transport": "http" },
  "env": [
    { "name": "API_KEY", "description": "下游订单 API 密钥", "isRequired": true, "isSecret": true }
  ],
  "deployment": ["local", "remote"],
  "security": {
    "readOnly": true,
    "promptInjection": "工具返回下游数据，调用方需处理 untrusted data 风险",
    "permissions": "仅查询，无修改能力"
  }
}
```

**命名空间（身份验证）**：

| 命名空间格式 | 验证方式 | 适用 |
|---|---|---|
| `io.github.<org>/<server>` | GitHub OIDC（自动） | 开源项目（无需额外配置） |
| `com.<你的域名>/<server>` | DNS TXT 或 HTTP challenge | 组织/商业 |

**版本化铁律**：**已发布版本不可变**——发布后想改只能发新版本；严格语义化版本（SemVer）；环境变量用 `isRequired`/`isSecret` 显式声明。

**发布命令**：

```bash
mcp-publisher login github          # OIDC 登录（无密码）
mcp-publisher publish              # 读取 server.json 并发布
mcp-publisher publish --version 1.3.0   # 发新版本
```

## 3. 发布自动化：GitHub Actions + OIDC

发布自动化 = 零凭据 + 每次发版自动同步：

```yaml
# .github/workflows/publish.yml
on:
  push:
    tags: ["v*"]                     # 打 tag 即发布

jobs:
  publish:
    permissions: { id-token: write, contents: write }
    steps:
      - uses: actions/checkout@v4
      - run: pip install mcp-publisher
      - name: Publish to official registry
        run: mcp-publisher publish    # OIDC 自动验证 io.github 命名空间
```

**自动化价值**：① 无凭据（OIDC 联邦，密钥不进 CI）；② 与版本 tag 绑定（`v1.2.0` → registry 1.2.0）；③ 可接 06 篇的测试门禁（测试过才允许发 tag）。**发布流水线与测试流水线串成一条"提交→测试→发布"链**，人工发布从流程里消失。

## 4. 注册表与市场生态对比

| 平台 | 规模 | 定位 | 安全措施 | 适用 |
|---|---|---|---|---|
| 官方注册表 | 官方规范集 | 事实来源（元数据） | 命名空间验证 | 所有发布者的"必发" |
| Smithery | 7000+ | 开发者默认市场 | 托管执行、审计、限流、每 Server 令牌 | 个人开发者首选体验 |
| mcp.so | 19700+ | 生态枢纽（浏览为主） | 无安装自动化、无安全信号 | 发现与检索 |
| PulseMCP | 3000+ | 厂商发布追踪 | 链接官方文档 | 关注厂商动态 |
| mcpmarket | ~38000 页 | 体量最大 | 按 GitHub star 排名（可刷） | 参考不决策 |
| Glama / mcpservers.org | 4000-6000+ | 聚合目录 | 指标可被刷 | 检索补充 |
| JFrog Universal | 企业 | **企业单一事实源** | Xray 静态分析、CVE 扫描、阻断未审查 | 企业合规 |
| Kong MCP Registry | 企业 | 网关一体化 | 身份与策略层治理 | 已有 Kong 的企业 |
| 自建网关注册表 | 内部 | 内网唯一入口 | Keycloak/Entra + 审计 | 受监管行业 |

**发布策略**：官方注册表必发（事实来源）；Smithery 选发（开发者发现）；企业内走自建网关（受控）。**注册表多 ≠ 质量高**——05 篇数据显示注册表条目恰恰是攻击面。

## 5. 多客户端分发

一个 Server 的安装说明要覆盖主流客户端（发布者义务：提供 8-12 个客户端的即贴即用片段）：

| 客户端 | 配置位置 | 示例 |
|---|---|---|
| Claude Code | `claude mcp add` | `claude mcp add order https://mcp.myorg.com/mcp` |
| Claude Desktop | `claude_desktop_config.json` | Connectors UI 或 JSON（远程经 OAuth） |
| Cursor | `.cursor/mcp.json` | 项目级配置 + 建议目录 |
| VS Code | `@mcp` gallery（2026 初原生支持） | 按 `servers` 键（非 `mcpServers`） |
| 自定义客户端 | SDK | `McpClient(transport="http")` |

**分发要点**：README 顶部放"安装矩阵"（每客户端一行命令）；远程 Server 给出 OAuth 流程说明（02 篇元数据端点）；本地包给出 `uvx`/`npx` 一键运行；**每个分发点都要写安全说明**（05/08 篇义务）。

## 6. 企业网关与受控注册表

企业（尤其受监管行业）的标准架构：**所有 MCP Server 进网关**：

```text
员工客户端 ──▶ 企业 MCP 网关（认证/审计/策略/扫描）
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
  内部 Server    官方注册表(筛选后同步)  第三方(经扫描)
```

| 能力 | 实现 |
|---|---|
| 目录同步 | 官方注册表同步 + 内部分支过滤 + 私有 Server 合并（subregistry 架构） |
| 依赖扫描 | JFrog Xray 类静态分析、CVE 阻断 |
| 身份 | 统一 IdP（Keycloak/Azure Entra）OAuth |
| 策略 | 只读默认、高危工具白名单、审计日志 |
| 平台 | VMware Tanzu（CF Marketplace 化）、Kong、自建（mcp-gateway-registry 开源） |

**企业决策点**：MCP 网关不是"网络防火墙"而是"**策略与信任边界**"——决定"谁能用哪个 Server 的哪个工具"，并把所有调用留痕。**合规行业的审计问题从"你连了什么"变成"你的网关允许了什么"**。

## 7. Server 发现：.well-known/mcp.json

不通过注册表，域名直接宣告 MCP Server：

```json
// https://myorg.com/.well-known/mcp.json
{
  "servers": [
    { "name": "order-server", "url": "https://mcp.myorg.com/mcp", "transport": "http" }
  ]
}
```

**机制**：Agent/客户端访问域名时自动探测 `/.well-known/mcp.json`——**域名即发现入口**。适用：组织自有服务、不想进公开注册表的内部/半公开服务。与 OAuth 的 `/.well-known/oauth-protected-resource`（02 篇）是配套的"域名上的一组标准端点"。

## 8. 与 Agent Skill 的组合

MCP 与 Agent Skill 是双标准（阶段 1 已学）：**MCP = 工具（functions），Skill = 知识（know-how）**。生产级组合姿势：

| 组合模式 | 分工 | 示例 |
|---|---|---|
| 工具在 MCP，流程在 Skill | Server 暴露原子能力；Skill 编排调用顺序与决策 | 订单服务（MCP 查单工具）+ 售后流程（Skill：先验证→再查单→再登记） |
| 数据在 MCP，指令在 Skill | Server 提供资源/数据；Skill 提供专业指令模板 | 代码库资源（MCP）+ 评审规范（Skill） |
| 认证在 MCP，人在 Skill | 服务器鉴权；Skill 定义人工确认点 | 转账工具（OAuth）+ 财务审批 Skill（MRTR 确认） |

**架构原则**：**工具保持原子与可复用，知识保持可组合与可更新**——工具绑定知识则复用性死，知识绑定工具则演进性死。发布 Server 时同步发布配套 Skill 模板，是"生态完整度"的标志（本知识库 `Agent Skill` 体系对应）。

## 9. server.json 字段与发布命令族

**server.json 全字段表**：

| 字段 | 必填 | 说明 |
|---|---|---|
| name | ✓ | 命名空间限定名（io.github.myorg/order-server） |
| description | ✓ | 一句话描述（客户端展示） |
| version | ✓ | 语义化版本；**已发布版本不可变** |
| packages | ✓（或 remote） | 包清单：type（pypi/npm/docker）+ 包名 + 版本 |
| remote | ✓（或 packages） | 远端端点：url + transport（http） |
| env | | 环境变量声明：name/description/isRequired/isSecret |
| deployment | | 支持的部署模型：local/remote |
| security | | 安全声明：readOnly、promptInjection、permissions |
| authors | | 维护者信息（信任信号） |
| license | | 许可证（开源 Server 必填） |

**mcp-publisher 命令族**：

| 命令 | 用途 |
|---|---|
| `mcp-publisher login github` | OIDC 登录（无密码/无令牌文件） |
| `mcp-publisher publish` | 按 server.json 发布/更新 |
| `mcp-publisher publish --version X` | 显式发新版本 |
| `mcp-publisher validate` | 本地校验 server.json 合法性 |
| `mcp-publisher status` | 查看已发布版本与命名空间状态 |

**发布检查单**：server.json 校验通过 → 包已推到包仓库 → 命名空间验证完成（OIDC/DNS）→ 版本号与包版本一致 → 安全声明完整 → 冒烟测试在远端端点跑通 → 发布 → 更新 README 安装矩阵。

## 10. 消费者检查单（用别人的 Server 之前）

| 检查项 | 动作 |
|---|---|
| 命名空间 | 确认 `io.github.anthropic/` 与仿冒的 `io.github.anthropic-tools/` 之别 |
| 版本锁定 | 生产锁版本（不可变版本是信任基础） |
| 工具清单 | 先 `tools/list` 看全：`fetch(url)`/`exec(command)` 是高危信号 |
| 安全声明 | README/registry 的 security 段：有无 readOnly/权限边界说明 |
| 来源 | 已验证所有者 + 多维护者 > 单作者无名项目 |
| 认证 | 检查 OAuth 元数据端点存在（02 篇） |
| 试用 | **先在 Inspector/测试环境跑通再连敏感系统**（05 篇） |
| 凭据 | 最小权限令牌（只读角色），不用生产主账号 |

## 12. 发布策略决策与面试速记

**发布到哪里：一张决策表**：

| 你的身份 | 必发 | 选发 | 不发 |
|---|---|---|---|
| 开源作者 | 官方注册表（事实来源+命名空间信任） | Smithery（开发者发现） | 企业网关（内网专用） |
| 企业内团队 | 内部网关/私有注册表 | — | 公开注册表（除非产品化） |
| SaaS 厂商 | 官方注册表（产品曝光） | PulseMCP（厂商动态） | — |
| 个人临时工具 | — | — | 全部（README 够了） |

**面试速记**：
1. 官方注册表 = 元数据注册表（不放代码），API freeze v0.1。
2. 命名空间两种：io.github.<org>（OIDC 自动）/ com.<domain>（DNS 验证）。
3. 已发布版本不可变——改 bug 只能发新版本。
4. 发布自动化 = GitHub Actions + OIDC（零凭据）。
5. 企业网关解决三件事：目录同步、依赖扫描、统一认证审计。
6. `.well-known/mcp.json` = 域名即发现入口（免注册表）。
7. MCP 与 Skill：工具原子可复用、知识可组合可更新。
8. 消费端铁律：注册 ≠ 安全，先过检查单再连敏感系统。

## 13. 版本策略与发布常见坑

**SemVer 在 MCP 场景的映射**：

| 版本位 | 变更 | 示例 |
|---|---|---|
| major | Schema 破坏性变更（参数改名/删除工具） | 1.x→2.0 |
| minor | 新增工具/新增可选参数（向后兼容） | 1.1→1.2 |
| patch | 修复/文档/内部实现（接口不变） | 1.2.0→1.2.1 |

**已发布版本不可变的含义**：修 bug 必须发新版本（不能覆盖 1.2.0）；客户端可以放心锁版本。**发布常见坑**：① 版本号与包版本不一致（注册表对不上）；② 忘记声明 `isSecret`（密钥出现在客户端安装界面）；③ 只发远端端点没发包（断网用户装不了）；④ 命名空间拼错（仿冒风险，05 篇）；⑤ 发布前不冒烟（用户第一个请求就 500）。

**发布仪式感**：正式发布 = 测试全绿 → tag → 自动发布 → 冒烟验证 → 更新 README 安装矩阵 → 通知用户（changelog）。**发布是"承诺"，不是"上传"**——承诺了这个版本可用、兼容、可回滚。

**生态趋势展望**（2026 视角）：官方注册表 API freeze v0.1 意味着"元数据规范已稳定，治理刚起步"；企业自建网关（JFrog/Kong/自托管）正在把 MCP 从"开发者玩具"推向"企业基础设施"——**2026 年的 MCP 分发格局：官方注册表定标准、市场平台做发现、企业网关管消费**。对发布者的启示：server.json 的 security 段与 isSecret 声明会越来越成为"能不能进企业白名单"的硬门槛——**现在就把安全声明写全，是给未来的自己省事**。

**分发矩阵设计原则**（08 篇第 5 节展开）：安装说明不是"一份文档"，是"一个矩阵"——按客户端×部署模式（本地包/远程端点）交叉覆盖；每条安装命令都要"无上下文可执行"（用户复制即用）；远程端点必须给认证说明（OAuth 流程链接）；**矩阵旁边放一行风险提示**（"本工具可写数据库，请用只读账号"）。发布者的口碑 = 安装体验 + 安全透明度——这两样都不在代码里，在 README 里。

**"发布完成"的定义**（避免"发了就忘"）：注册表可查到 + 至少一个客户端装通 + 冒烟通过 + 文档更新 + 监控可达（07 篇）。**"上传成功"不等于"发布完成"**——上传只是开始，验证与文档才是承诺的兑现。每次发布留 changelog 的习惯，三个月后用户报问题时你还能记得"这个版本改了什么"。**多版本并存策略**：为兼容"锁版本"的保守用户，保留前一个 minor 版本在线（bug 修复只发当前版）；**"最新版"永远指向已冒烟的版本**——发布节奏比发布数量重要。**命名空间是长期资产**：改名/迁组织会丢失已验证的命名空间信任（消费者检查单第一项）——**起名想清楚再注册**，发布后改名成本远高于起名成本。

> 🎯 **核心要点**：发布分发 = 官方注册表（server.json + 命名空间 + 不可变版本 + OIDC 自动发布）为事实来源，Smithery 等市场补发现力，企业网关做受控消费；域名 `.well-known/mcp.json` 是免注册表发现；消费端有独立检查单；与 Agent Skill 组合时**工具原子、知识可组合**；版本策略按 SemVer 映射接口变更。安全提醒常挂嘴边：**"在官方注册表" ≠ "安全"——41% 零认证、33% 高危，消费端检查单永远先于信任**。
