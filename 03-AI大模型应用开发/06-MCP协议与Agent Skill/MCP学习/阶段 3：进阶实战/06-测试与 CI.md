## 1. 测试金字塔：MCP Server 的四层

| 层 | 测什么 | 工具 | 速度 | 数量 |
|---|---|---|---|---|
| L1 工具函数 | 纯逻辑：输入→输出、错误码 | pytest 直接调函数 | 毫秒 | 多 |
| L2 进程内协议 | 装饰器→Schema、Context、依赖注入 | `Client(mcp)` 进程内 | 毫秒-秒 | 中 |
| L3 集成 | 真实传输：stdio/HTTP、认证、下游 API | Inspector、curl、真实 Client | 秒-分 | 少 |
| L4 端到端 | 客户端视角：模型调用链、授权流 | Claude Code、自定义 Client | 分 | 极少 |

> 🎯 比例原则：**L1/L2 覆盖 80% 逻辑，L3 守传输与边界，L4 做发布前冒烟**——别把全部希望压在端到端（慢且脆）。

## 2. 进程内测试：不启动传输

FastMCP 支持 `Client(mcp)` 进程内连接——不启动子进程、不走网络，直接以协议语义调工具：

```python
import pytest
from fastmcp import Client

@pytest.mark.asyncio
async def test_get_order_success():
    async with Client(mcp) as client:          # mcp 为被测 Server 实例
        tools = await client.list_tools()
        assert any(t.name == "get_order" for t in tools)

        result = await client.call_tool("get_order", {"order_id": "A1001"})
        assert not result.is_error
        assert "A1001" in result.content
```

**进程内测试的三大红利**：
1. **快**——毫秒级，适合 CI 高频回归；
2. **覆盖协议语义**——`list_tools`/`call_tool` 走的是真实协议处理路径（装饰器→Schema→Context→结果），不是裸函数调用；
3. **可注入**——配合 lifespan/Depends override 换掉外部依赖（见第 4 节）。

**必测清单（L2）**：
- 每个工具：正常路径 + 错误参数 + 边界值（空串/负数/超长）；
- Schema 生成正确：`list_tools` 返回的 inputSchema 与函数签名一致（类型/默认值/描述）；
- 错误处理：`is_error` 工具返回错误码而非异常；
- 中间件：审计/限流逻辑生效（可断言日志/计数）。

## 3. 集成测试：Inspector 与 curl

**Inspector 三连**（阶段 2 已会，这里做自动化版）：

| 步骤 | 命令/动作 | 断言 |
|---|---|---|
| 启动 Server | `uv run python server.py`（或 http 模式） | 进程存活、无启动错误 |
| tools/list | Inspector UI 或 CLI 冒烟 | 工具列表完整、Schema 正确 |
| tools/call | 正常参数 + 错误参数各一次 | 结果正确、错误形态正确 |

**HTTP 模式 curl 冒烟**（Streamable HTTP）：

```bash
# 冒烟：list（无认证时预期 401；有认证则带令牌）
curl -s http://localhost:8080/mcp \
  -H "Content-Type: application/json" \
  -H "Mcp-Method: tools/list" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'

# 认证流程冒烟（OAuth 元数据可达）
curl -s http://localhost:8080/.well-known/oauth-protected-resource
```

**集成测试陷阱**：端口冲突（CI 并行时用随机端口）、依赖未启动（下游 API 用 mock 或 testcontainers）、令牌过期（测试专用长有效期令牌或 mock 授权服务器）。

## 4. Mock 策略：依赖替身

MCP Server 的依赖通常是"数据库/外部 API/文件系统"——测试里全部替身化：

| 依赖 | 替身 | 说明 |
|---|---|---|
| 数据库 | 内存库（sqlite:memory）或 mock 仓库 | 真实 SQL 用 sqlite；纯逻辑用 mock |
| 外部 HTTP API | `respx`/`responses` 拦截 | 断言请求参数 + 返回预设响应 |
| 文件系统 | tmp_path fixture | pytest 内置 |
| 认证 | 测试 JWT 或 mock 验证器 | 用私钥签测试令牌，公钥校验路径真实执行 |
| 时钟/随机 | monkeypatch | 时间敏感逻辑（过期判断） |

**依赖注入的测试红利**（01 篇）：工具依赖通过 `Depends` 注入，测试里 override：

```python
def test_order_with_mock_db(monkeypatch):
    fake_db = FakeOrderRepo(data={"A1": {...}})
    monkeypatch.setattr("server.get_db", lambda: fake_db)
    # 或 override lifespan 上下文
    ...
```

**Mock 的红线**：**mock 的是"外部世界"，不是"自己的逻辑"**——别 mock 掉被测工具本身的函数，否则测试无意义。

## 5. 协议合规测试

无状态规范（03 篇）后新增的合规点，测试里显式验证：

| 合规项 | 测试 |
|---|---|
| server/discover 存在且返回版本/能力 | 调用 discover 断言字段齐全 |
| 每结果带 resultType | 遍历全部调用断言 `complete` |
| 请求带版本（_meta） | 断言服务器接受带 `_meta` 的请求 |
| Mcp-Method/Mcp-Name 头 | HTTP 集成测试断言头存在 |
| 列表不随连接变化 | 两次不同连接 list_tools 结果一致 |
| 版本不匹配报错 | 带旧版本调用，断言 UnsupportedProtocolVersionError |
| 双代兼容 | legacy 握手路径仍通（dual-era 时） |

**为什么值得做**：协议不合规的 Server 在不同客户端表现不一（Claude Code 通、其他客户端挂）——**合规测试是"多客户端兼容"的廉价保证**。

## 6. 压力与安全测试

**压力测试**（发布前至少跑一次）：

| 场景 | 方法 | 关注指标 |
|---|---|---|
| 工具调用吞吐 | locust/wrk 打 `/mcp` 端点 | P99 延迟、错误率 |
| 并发连接 | 模拟多客户端同时挂载 | 连接数上限、内存 |
| 长任务并发 | 并发起多个 Tasks | 任务存储压力、轮询命中率 |
| 认证风暴 | 令牌校验路径高频 | 验签 CPU（JWKS 缓存是否生效） |

**安全测试**（配合 05 篇检查单）：

| 测试 | 断言 |
|---|---|
| 注入参数 | 超大参数、非法类型、负数、路径穿越 `../` 全部被拒 |
| 未认证调用 | 无令牌 → 401，不泄露任何数据 |
| 越权令牌 | 低 scope 令牌调高权限工具 → 拒绝 |
| URL 工具 | 内网 IP、file://、重定向跳内网 → 全部拦截 |
| 令牌日志泄露 | 抓日志 grep 令牌值 → 无 |

## 7. CI 流水线

GitHub Actions 标准流水线（发布即自动化，08 篇发布流程复用）：

```yaml
name: test-and-publish
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -e ".[test]"
      - run: pytest --cov=server --cov-fail-under=80
      - run: python -m server.checks.compliance   # 协议合规测试
      - run: uvx mcp-inspector --smoke            # Inspector 冒烟
      - name: Dependency scan
        run: uvx pip-audit                        # 依赖漏洞扫描

  publish:
    needs: test
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    permissions: { id-token: write }              # OIDC：无需密钥
    steps:
      - uses: actions/checkout@v4
      - run: mcp-publisher publish                # 见 08 篇
```

**门禁设计**：单测+合规+冒烟+依赖扫描全绿才允许发 tag；**覆盖率红线 80%**（新代码分支覆盖优先）；发布走 OIDC（无凭据泄露面）。**CI 的价值 = 把"发布时才发现的问题"提前到"提交时"**。

## 8. 测试文化：发布前守门

**发布前五问**：

1. 新工具有没有 L1/L2 测试？（没有 → 不放行）
2. 协议合规测试过没过？（discover/resultType/头）
3. 安全清单全绿？（05 篇检查单）
4. 认证流程冒烟过没过？（401→元数据→令牌→调用）
5. 依赖扫描有没有新增高危？

**测试债管理**：工具数少时（<10）全量覆盖成本低；工具爆炸后（04 篇）优先测**高危工具**（写/外发/URL 类）——风险导向的测试优先级。

## 9. 完整测试文件参考

一个生产级测试文件的骨架（覆盖 L1-L3 全部要点）：

```python
# tests/test_order_server.py
import pytest
from fastmcp import Client
from order_server import mcp

# ---------- L1：工具纯逻辑（直接调函数） ----------
def test_get_order_not_found():
    from order_server.tools import get_order
    r = get_order(order_id="NOPE")
    assert r.is_error and r.content == "订单不存在"

# ---------- L2：进程内协议 ----------
@pytest.mark.asyncio
async def test_schema_generation():
    tools = await mcp.list_tools()          # 或 mcp.get_tools()
    schema = tools["get_order"].inputSchema
    assert schema["properties"]["order_id"]["type"] == "string"
    assert "何时用" in tools["get_order"].description

@pytest.mark.asyncio
async def test_call_tool_full_flow():
    async with Client(mcp) as client:
        result = await client.call_tool("get_order", {"order_id": "A1"})
        assert not result.is_error

@pytest.mark.asyncio
async def test_write_tool_blocked_by_default():
    async with Client(mcp) as client:
        r = await client.call_tool("update_order_status", {...})
        assert r.is_error                    # 只读默认（05 篇）

# ---------- L3：HTTP 传输 + 认证 ----------
def test_http_401_without_token():
    resp = httpx.post("http://localhost:8080/mcp",
                      json={"jsonrpc": "2.0", "id": 1, "method": "tools/list"})
    assert resp.status_code == 401
    assert "WWW-Authenticate" in resp.headers   # 质询头（02 篇）

def test_oauth_metadata_reachable():
    resp = httpx.get("http://localhost:8080/.well-known/oauth-protected-resource")
    assert resp.status_code == 200 and "authorization_servers" in resp.json()
```

**pytest 配置**（覆盖率红线 + 测试隔离）：

```toml
# pyproject.toml
[tool.pytest.ini_options]
asyncio_mode = "auto"                    # asyncio 自动模式
testpaths = ["tests"]

[tool.coverage.run]
source = ["order_server"]
fail_under = 80                          # 覆盖率门禁（06 篇）

[tool.coverage.report]
show_missing = true
```

## 10. 常见测试陷阱

| 陷阱 | 症状 | 解法 |
|---|---|---|
| 测试间状态泄漏 | 用例顺序影响结果 | 每测试独立 lifespan/内存库（fixture 隔离） |
| 只测 happy path | 错误处理形同虚设 | 每工具至少一个错误用例（错误码/边界值） |
| mock 掉被测函数 | 测试全绿但功能坏 | mock 只替外部世界（DB/API），不替自己逻辑 |
| 集成测试依赖真服务 | CI 不稳定/慢 | testcontainers 或 mock 服务；真服务留 L4 冒烟 |
| 异步测试裸奔 | asyncio 警告/挂起 | asyncio_mode=auto；所有 async 测试加 await |
| 覆盖率虚高 | 只测工具不测中间件 | 中间件/认证路径单独用例（02/05 篇） |

## 11. 发布门禁组合拳

把 06 篇所有门禁组装成"发布前一刻"清单（CI 全绿 + 人工确认两不误）：

```text
提交（push/PR）
  → L1+L2 单测（覆盖率 ≥80%）
  → 协议合规测试（discover/resultType/头/版本协商）
  → 安全测试（注入/越权/SSRF/令牌泄露 grep）
  → 依赖扫描（pip-audit，高危阻断）
  → Inspector 冒烟（tools/list → call → 错参）
  → 打 tag vX.Y.Z
      → 发布流水线（OIDC）→ 官方注册表（08 篇）
```

**门禁哲学**：**能自动化的全自动化，不能自动化的显式化**——模型幻觉/提示注入这类"语义风险"无法全自动验证，发布清单里保留"人工安全复核"一格，但把它做成"必须逐项打钩"的显式步骤，而不是默认通过的过场。

## 12. 用例矩阵模板

按工具维度组织测试用例（新增工具时照此填充）：

| 工具 | 正常路径 | 边界/错误 | 安全用例 | 幂等/并发 |
|---|---|---|---|---|
| get_order | 存在订单返回 | 不存在→NOT_FOUND；空 ID→校验拒绝 | 无令牌→401；低 scope→拒绝 | 并发查询一致 |
| update_order_status | 合法状态更新 | 非法状态→枚举拒绝；不存在→NOT_FOUND | 只读模式→拒绝；写操作确认流程 | 同单重复更新收敛 |
| fetch_url | https 正常抓取 | 超时→降级返回 | **内网 IP→拦截**；file://→拦截；重定向→拦截 | 重复抓取结果一致 |

**模板的价值**：把"测什么"变成填表题——每个工具四列必填，**安全列是硬性要求**（URL 工具必测 SSRF，写工具必测权限）。用例矩阵是测试计划的骨架，测试代码只是它的执行。

## 13. 覆盖率策略与测试债

| 覆盖率决策 | 建议 |
|---|---|
| 红线设多少 | 80%（新代码）；高危工具要求 100% 关键路径 |
| 哪些必须覆盖 | 认证分支、权限分支、错误码分支、幂等分支 |
| 哪些可豁免 | 纯样板（main 入口）、第三方集成（冒烟即可） |
| 测试债处理 | 新增工具必须带测试；存量工具按"高危优先"补齐 |
| 覆盖率虚高防坑 | 中间件/认证单独统计（常被工具测试稀释） |

**测试债的度量**：不是"覆盖率数字"而是"**发布前焦虑程度**"——每次发布都要靠人工验证的工具列表就是测试债清单，逐项补测试，焦虑逐项消失。

**测试即文档**：一组好的测试就是 Server 的活文档——每个工具的正常/边界/安全行为全部可执行、可回归。**新人接手 Server 第一件事是跑测试**：全绿=理解现状的起点；失败=立即进入排障场景（比读文档更真实）。写测试时把"这段代码在防什么坑"写进用例名（如 `test_url_tool_blocks_private_ips`），三个月后回来看，测试在替你记住设计意图。

## 14. 测试金字塔详解与分层策略

```
        ▲  数量少、速度慢、真实度高
   L4 端到端（Claude Code/真实客户端）── 发布前冒烟
  L3 集成（HTTP/stdio/认证/下游）────── CI 关键路径
 L2 进程内协议（Client(mcp)）─────────── 开发高频回归
L1 工具纯逻辑（直接调函数）───────────── 数量最多、毫秒级
        ▼  数量多、速度快、覆盖细
```

| 层 | 运行频率 | 失败成本 | 维护成本 | 策略 |
|---|---|---|---|---|
| L1 | 每次保存 | 低（定位准） | 低 | 全量覆盖，含边界 |
| L2 | 每次提交 | 中 | 中 | 全量覆盖，协议语义 |
| L3 | CI 每次 | 高（依赖环境） | 中高 | 关键路径+认证 |
| L4 | 发布前 | 最高（环境复杂） | 高 | 冒烟即可，别全量 |

**分层铁律**：**L1/L2 能抓的问题绝不上浮到 L3/L4**——"等端到端才发现"意味着测试反馈周期长、定位成本高。反过来，L4 只做"链路通不通"的冒烟（认证→列表→调用），不做细粒度断言（那是 L1/L2 的活）。

**测试面试速记**：
1. 进程内 `Client(mcp)` = 协议语义毫秒级可测的核心。
2. 金字塔四层各司其职：L1 逻辑、L2 协议、L3 传输、L4 冒烟。
3. mock 只替外部世界（DB/API），不替自己的逻辑。
4. 协议合规测试（discover/resultType/头/版本协商）= 多客户端兼容保证。
5. CI 门禁五件套：单测+覆盖率+合规+依赖扫描+冒烟。
6. 用例矩阵四列：正常/边界/安全/幂等——高危工具安全列必填。

**测试与发布的闭环**：测试不是"发布前的检查"，而是"发布的一部分"——门禁全绿是发布的前提条件，发布失败（线上问题）要回流成新测试用例（回归测试），让"同类事故不再发生"成为可验证的承诺。**每修一个线上 bug，先补一个测试再修代码**（红→绿），是防止"修了又坏"的唯一可靠办法——这条纪律对 MCP Server 与其他服务完全一致。**测试覆盖率数字的诚实解读**：80% 红线是底线不是目标——高危工具的关键路径（认证、权限、错误码、幂等）要求 100%，其余可以靠用例矩阵的边界列兜底；覆盖率报告里"被豁免"的代码要写明理由，而不是默认忽略。**测试的最终验收**：把 Server 交给一个没参与开发的人，让他只靠测试输出判断"能否发布"——他能做出正确判断，测试体系才算完整。

> 🎯 **核心要点**：MCP Server 测试 = 金字塔分层（L1 纯逻辑 / L2 进程内协议 / L3 真实传输 / L4 端到端）+ 依赖替身 + 协议合规 + 压力/安全专项 + CI 守门 + 用例矩阵。**进程内 `Client(mcp)` 是效率核心**——它让协议语义在毫秒级可测；**合规测试是兼容性保证**——它让 Server 在多客户端下表现一致；**用例矩阵让"测什么"可管理**；**分层策略让"测多少"有谱**。发布不再靠"我本地跑过"，而靠"CI 全绿 + 清单逐项打钩"。
