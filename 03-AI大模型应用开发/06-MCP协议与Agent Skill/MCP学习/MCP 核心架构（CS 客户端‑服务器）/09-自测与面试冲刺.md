## 2. 自测答案速查

| # | 答案要点 |
|---|---|
| 1 | Host（容器与协调者）/ Client（1:1 连接器）/ Server（能力提供者）；Client 一对一连接 Server，Host 管理多个 Client |
| 2 | 1:1 保证协议纯净：方法名/状态/订阅天然隔离；多服务器组合由 Host 层上下文聚合解决 |
| 3 | 不能；服务器互不可见，只能看到当前请求；完整历史永远留在 Host |
| 4 | Tools（我能做什么→操作）/ Resources（你能给我什么→数据）/ Prompts（按模板生成→复用） |
| 5 | 从"有状态会话"重构为"无状态核心"：握手移除、会话移除、请求自包含 |
| 6 | 每个请求的 `params._meta`：protocolVersion / clientCapabilities / clientInfo |
| 7 | stdout 只属于协议（日志走 stderr）；进程退出即连接结束 |
| 8 | 三步：initialize 请求 → InitializeResult → notifications/initialized；新版：可选 server/discover + 每请求 _meta |
| 9 | 服务器 MUST 实现的能力/版本探测；对旧服务器探测失败（MethodNotFound）即回退 initialize，官方认可的 STDIO 兼容探测 |
| 10 | 新客户端+旧服务器：discover 失败→回退握手→会话模式；旧客户端+新服务器：服务器双代应答，继续会话模式 |
| 11 | Multi Round-Trip Requests：服务器处理中返回 input_required + inputRequests + requestState，客户端带 inputResponses 重试；旧版是连接生命周期内随时发起的全双工请求 |
| 12 | complete / input_required；收集答案 → 重发原请求（带 inputResponses + requestState）；旧服务器缺字段按 complete 处理 |
| 13 | -32022 版本不支持（原 -32004）；-32020 头不匹配（原 -32001）；-32602 资源未找到归并 JSON-RPC Invalid Params（原 -32002） |
| 14 | 不续传（Last-Event-ID 移除）：重新 listen + 主动重拉目录 + ttlMs 缓存兜底；续传复杂度不值得 |
| 15 | 显式句柄（如 basket_id 参数回传）；模型能看见并推理句柄，隐式会话状态模型看不见 |
| 16 | 保持 initialize 应答路径（双代）；按请求版本分发：无 _meta → 会话模式处理 |
| 17 | 去掉 sticky；round-robin；删服务端会话存储；重试靠业务幂等 |
| 18 | subscriptions/listen 订阅 toolsListChanged → 收到通知重拉 tools/list；缓存按 ttlMs 过期 + 通知即时失效 |
| 19 | Mcp-Method / Mcp-Name 路由头（SEP-2243）；不匹配返回 -32020 HeaderMismatchError |
| 20 | Host 生成 traceparent 进 _meta → Client 透传 → Server 透传到业务调用；日志记：工具名 + traceId + 参数摘要（脱敏）+ 耗时 + resultType |

## 3. 面试 10 题与答题范式

### Q1：讲讲 MCP 的整体架构

**范式**：三方角色 + 通信模型 + 设计原则 → 落到"为什么这么设计"。
**要点**：Host 容器与协调者（权限/授权/LLM 集成/上下文聚合）；Client 与 Server 1:1，协议消息双向路由；Server 独立暴露原语。原则：服务器不知全貌、状态留 Host、能力协商制。

### Q2：2026-07-28 规范对架构最大的改变是什么？

**范式**：先给结论（有状态→无状态）→ 三个具体删除（initialize 握手/Mcp-Session-Id/ping）→ 三个新增（_meta 协商/server/discover/MRTR）→ 影响（LB、Serverless、运维简化）。
**金句**：复杂度从协议层转移到业务层，换来部署自由。

### Q3：新旧两代协议如何兼容共存？

**范式**：四象限矩阵（新新/新旧/旧新/旧旧）+ 双栈机制（客户端 discover 回退 initialize；服务器双代应答）+ 12 个月弃用窗口。
**要点**：版本是"集合取交集、逐请求协商"；唯一不兼容例外是 Tasks 扩展重设计。

### Q4：客户端请求为什么必须带 _meta？都带什么？

**范式**：无状态化的载体 → 三键逐一说明（版本/能力/身份）→ 可选键（traceparent/logLevel）→ 服务器回 serverInfo。
**要点**：没有 _meta，服务器不知道"用哪代逻辑处理这个请求"。

### Q5：MRTR 解决了什么问题？与旧版有什么区别？

**范式**：旧版痛点（服务器生命周期内随时发起请求 → 依赖全双工长连接 → 阻碍无状态化）→ 新版方案（input_required + requestState + 重试原请求）→ 取舍（服务器失去事后主动询问，换来无状态）。
**要点**：requestState 是不透明令牌；多轮可叠加。

### Q6：MCP 服务器怎么部署才可靠？

**范式**：传输选型（stdio 本机/HTTP 远程）→ 无状态红利（round-robin、去 sticky、Serverless）→ 网关模式（路由/鉴权/限流/审计）→ 订阅长流的部署注意（断流重订阅）。
**要点**：写工具幂等性是重试安全的前提。

### Q7：MCP 怎么保证安全？

**范式**：四层——传输层（HTTPS）、认证层（OAuth 2.1 + iss 校验 + CIMD）、授权层（最小权限/工具白名单）、数据层（输入输出净化防提示注入、private 缓存不可共享）。
**要点**：iss 校验（RFC 9207）与凭证按 issuer 绑定是 2026-07-28 的关键词。

### Q8：工具目录变化了，客户端怎么感知？

**范式**：推送（subscriptions/listen 订阅 toolsListChanged）+ 拉取兜底（ttlMs 过期重拉）双机制 → 断流语义（不续传、重订阅）。
**要点**：ttlMs/cacheScope 是 2026-07-28 正式化的缓存契约。

### Q9：怎么观测 MCP 调用链路？

**范式**：W3C Trace Context 进 _meta（traceparent/tracestate/baggage）→ 全链路透传 → 日志字段规范（工具名/traceId/参数摘要/耗时/resultType）→ 网关按 Mcp-Method 统计三指标。
**要点**：无状态让追踪更简单——traceId 随请求自包含。

### Q10：你自己实现一个 MCP 服务器，怎么设计？

**范式**：分层（原语注册层/协议层/传输层/运行层）→ 原语注册表三表 → 双代服务（discover + initialize 应答）→ 状态句柄化 → 缓存字段 + 幂等设计。
**要点**：先协议合规（MUST 项：discover、resultType、缓存字段），再谈 API 优雅。

### 3.1 面试高频追问与应答

| 追问 | 应答要点 |
|---|---|
| "为什么无状态比会话好？" | 三笔账：部署（LB/Serverless）、可靠（请求级失败）、演进（协议变简单）——再补一句代价：客户端复杂、业务要幂等 |
| "会话状态去哪了？" | 两处：显式句柄参数（业务态）+ 客户端协商缓存（协议态）；没有第三个地方 |
| "服务器怎么知道客户端会什么？" | 每请求 _meta.clientCapabilities；不 discover 也能工作，discover 只是优化 |
| "你服务器支持哪些版本？" | 版本集合概念：支持集 ∩ 客户端集 → 最高共同版本；逐请求可不同 |
| "MRTR 里 requestState 是什么？" | 不透明令牌：关联服务器中间状态；客户端原样回传、永不解析 |
| "订阅和轮询怎么选？" | 通知（即时）+ ttlMs 缓存（兜底）+ 周期重拉（最后手段）三层；断流不续传是设计决定 |

### 3.2 常见误区（面试雷区）

| 误区说法 | 纠正 |
|---|---|
| "2026-07-28 把 initialize 删了" | 从新协议路径删除；服务器仍需双代应答旧客户端 |
| "无状态后没有状态了" | 协议无状态，业务状态用句柄显式建模 |
| "server/discover 可选" | 服务器 MUST 实现；客户端 MAY 调用 |
| "sampling 被删了" | 弃用（12 个月窗口），MRTR 是替代路径 |
| "订阅流断了会续传" | 不续传：重订阅 + 重拉兜底 |

### 4.3 面试官可能追问的"反向题"

| 反向题 | 你的反问/澄清 |
|---|---|
| "你说无状态好，那有没有不适合无状态的场景？" | 服务器需要长连接推送（订阅流）、工具需要跨请求上下文的强依赖场景（但句柄化可解） |
| "MRTR 和旧 sampling 哪个好？" | 无优劣，是架构约束下的取舍：MRTR 可均衡可审计，代价是失去全双工 |
| "你推荐新项目直接用 2026-07-28 吗？" | 新项目直接上（双代默认），存量按三步走迁移 |
| "协议版本为什么用日期？" | 语义化 + 天然排序 + 发布节奏透明（与 RFC 惯例一致） |

### 4.6 常见失分点与规避

| 失分点 | 规避 |
|---|---|
| 只说变化不说取舍 | 每个机制都配一句"代价是什么" |
| 版本号说错 | 记牢：2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28 |
| 混淆 SDK 版本与协议版本 | 主动澄清：SDK 版本 ≠ 协议版本 |
| 说"删了握手" | 说"新路径移除、双代保留" |
| 说不出迁移步骤 | 背三步走：先客户端 → 再服务器 → 后拆会话 |

## 5. 延伸学习路线

| 方向 | 路径 |
|---|---|
| 动手写代码 | `阶段 2：动手入门`（stdio/HTTP 实操）→ `阶段 3：进阶实战`（无状态迁移/双代兼容） |
| 框架选型 | `主流 MCP 开发框架`（Python/TS/Java/Go/C# 对照） |
| 协议速查 | `MCP` 体系（09 篇：原语/传输/认证） |
| 认证深潜 | `阶段 3：进阶实战/02-认证与授权：OAuth 2.1 落地` |

> 🎯 **核心要点**：架构面试的底层逻辑是"机制与取舍"——每个机制（握手/_meta/MRTR/头路由）都对应一个取舍（部署自由/客户端复杂度/服务器能力收缩/基础设施可观测）。把"机制 → 取舍 → 适用场景"三段式答全，就是满分范式。考前过一遍速记卡（无状态三删三增、四个新字段、三个错误码、弃用三件套），20 自测至少答对 16 题、面试 10 题脱稿 8 题，即可视为本体系毕业。本体系学到的能力是"读懂规范变更 → 讲清取舍 → 落地迁移"的通用方法论，不止于 MCP 本身。

### 5.1 结业寄语

本体系的价值不在背诵，而在建立三种能力：**读规范**（看懂 changelog 的 Key Changes 并追溯机制）、**讲取舍**（每个机制都能说出代价与场景）、**做迁移**（把协议变更变成可执行的三步走）。带着这三种能力去读任何新一代协议（A2A、MCP 扩展、未来的 v6），你都能在一天内建立正确的架构图景。祝学习愉快，架构长青。
