## 1. 服务器内部组件分层

与客户端对称，服务器内部也是四层：

```text
┌─────────────────────────────────────────────┐
│ ① 原语注册层   @tool/@resource/@prompt 注册表 │  ← 业务代码挂载点
├─────────────────────────────────────────────┤
│ ② 协议层       方法分发、能力声明、MRTR 组装   │
├─────────────────────────────────────────────┤
│ ③ 传输层       stdio / Streamable HTTP        │
├─────────────────────────────────────────────┤
│ ④ 运行层       进程/HTTP 服务器、生命周期       │
└─────────────────────────────────────────────┘
```

| 层 | 职责 | 双代迁移影响 |
|---|---|---|
| 原语注册层 | 收集工具/资源/提示定义与实现 | 装饰器不变（FastMCP 改名 MCPServer 后 API 不变） |
| 协议层 | 把注册表序列化为 tools/list 响应、分发 tools/call | 结果补 resultType、列表补 ttlMs/cacheScope |
| 传输层 | 消息解析、响应流、请求头校验（Mcp-Method） | 需兼容两种请求形态 |
| 运行层 | 进程生命周期、优雅停机、并发上限 | 基本不变 |

## 2. 原语注册表设计

```python
# Python mcp v2（原 FastMCP 改名 MCPServer）——注册表心智
from mcp import MCPServer

server = MCPServer("order-service")

@server.tool()                          # → 注册进 tools 注册表
def calculate_discount(amount: float, vip_level: int) -> str:
    """计算订单折扣（金额、会员等级）"""
    return f"折扣价：{amount * (1 - vip_level * 0.05):.2f}"
```

注册表内部 = 三张映射表 + 能力自省：

| 注册表 | 键 | 值 | 协议出口 |
|---|---|---|---|
| tools | 工具名 | schema + 实现函数 | tools/list → tools/call |
| resources | URI（含模板） | 读取函数 + 内容类型 | resources/list → resources/read |
| prompts | 模板名 | 参数 schema + 展开函数 | prompts/list → prompts/get |

服务器端"双代迁移零成本"的关键：装饰器层（@server.tool）在两代协议下完全一致，v2 只在协议层自动补 `resultType: "complete"` 与 `ttlMs`，业务代码一行不改。TS v2 唯一破坏性改动是 `.tool()` 改名 `registerTool()`。

## 3. server/discover：新协议的招牌方法

| 属性 | 说明 |
|---|---|
| 方向 | 客户端 → 服务器 |
| 必实现 | **服务器 MUST 实现**（与旧版 initialize 同级的强制性） |
| 何时调用 | 客户端"可以在任何其他请求之前"调用，用于前置能力发现与版本选择 |
| 兼容探测 | 允许作为 STDIO 上的向后兼容探测（旧客户端连新服务器仍走 initialize） |
| 结果 | 支持的协议版本集合、capabilities、identity（serverInfo），带 ttlMs/cacheScope |

```json
// 请求：server/discover
{ "jsonrpc": "2.0", "id": 1, "method": "server/discover" }

// 响应：返回支持的版本集合 + 能力 + 身份（缓存元数据）
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "protocolVersions": ["2026-07-28", "2025-11-25", "2025-06-18"],
    "capabilities": {
      "tools": { "listChanged": true },
      "extensions": { "io.modelcontextprotocol/tasks": { "polling": true } }
    },
    "serverInfo": { "name": "order-service", "version": "1.4.0" },
    "ttlMs": 60000,
    "cacheScope": "public"
  }
}
```

设计意图（官方"按需复杂度"）：核心协议保持精简——没有强制性握手，客户端不 discover 也能直接发请求（版本放在每个请求的 _meta 里）；需要发现时再花一次 RTT。对网关/LB 而言 discover 结果可缓存（ttlMs），不必每连接都问。

## 4. 请求处理管线

服务器处理一次请求的完整管线（无状态版）：

```text
① 传输层收帧 → 校验 Mcp-Method/Mcp-Name 头（HTTP）→ 解析 JSON-RPC
② 协议层：读 _meta.protocolVersion → 选定处理逻辑（新/旧两套分发）
③ 方法分发：tools/list → 读注册表；tools/call → 找工具实现
④ 参数校验：inputSchema（JSON Schema 2020-12，支持 oneOf/anyOf/allOf）
⑤ 执行：调用业务函数；需要更多输入 → 返回 InputRequiredResult
⑥ 响应组装：result + resultType + serverInfo（_meta）+ 缓存字段（列表类）
⑦ 发送：普通结果直接回；input_required 结果等客户端带答案重试
```

| 阶段 | 双代差异点 |
|---|---|
| 头校验 | 仅新协议：Mcp-Method 与方法名不一致 → -32020 |
| 版本读取 | 新：_meta.protocolVersion；旧：握手时确定的会话版本 |
| 列表结果 | 新：必带 ttlMs/cacheScope；旧：无 |
| 结果结构 | 新：必带 resultType；旧：无（客户端按 complete 处理） |
| 索要输入 | 新：MRTR input_required；旧：服务器发起 sampling/elicitation/roots 请求 |

### 4.1 服务器对请求的校验清单

| 校验项 | 说明 | 失败处理 |
|---|---|---|
| 协议版本 | 读 _meta.protocolVersion，是否在支持集合 | -32022 |
| 方法头 | Mcp-Method 与 body.method 一致（HTTP） | -32020 |
| 能力声明 | 方法所需能力客户端是否已声明 | -32021 |
| 参数 schema | inputSchema（JSON Schema 2020-12）校验 | -32602（参数错误） |
| 权限 | 该客户端/用户是否有权调用此工具 | 403 或自定义错误 |
| 限流 | 按 Mcp-Name / IP 的配额检查 | 429 |
| 幂等 | 写操作检查幂等键是否已处理 | 返回缓存结果或冲突 |

> ⚠️ 参数校验是安全底线：模型输出的参数不可信，strict 校验（additionalProperties: false + 全 required）能拦截绝大多数注入与误用。

## 5. MRTR：处理中的内联索要输入

MRTR（Multi Round-Trip Requests，SEP-2322）取代旧版"服务器发起的请求"（sampling/createMessage、elicitation/create、roots/list）。旧版服务器可以在连接生命周期内随时向客户端发起请求（依赖长连接/会话）；新版只在"处理某个客户端请求的过程中"允许索要输入：

```json
// ① 服务器处理 tools/call 时发现缺用户确认 → 返回 input_required
{
  "jsonrpc": "2.0", "id": 3,
  "result": {
    "resultType": "input_required",
    "inputRequests": [
      {
        "id": "confirm-payment",
        "type": "user_input",
        "question": "确认支付 ¥128.00？",
        "options": ["确认", "取消"]
      }
    ],
    "requestState": "opaque-token-9f2a"
  }
}

// ② 客户端收集答案后，携带答案重试原请求（同 id 或新 id + inputResponses）
{
  "jsonrpc": "2.0", "id": 4, "method": "tools/call",
  "params": {
    "name": "place_order",
    "arguments": { "order_id": "A1024" },
    "inputResponses": [
      { "id": "confirm-payment", "response": "确认" }
    ],
    "requestState": "opaque-token-9f2a"
  }
}
```

| 对比维度 | 旧版（服务器发起请求） | 新版（MRTR） |
|---|---|---|
| 触发时机 | 生命周期任意时刻 | 仅处理某请求过程中 |
| 依赖 | 长连接/会话存在 | 无状态：token 回传即可 |
| 语义 | 隐藏的双向通道 | 显式多轮往返 |
| 与负载均衡 | 冲突（必须粘滞） | 兼容（无状态） |

> 💡 服务器不再能"事后"找客户端要东西——这既是架构简化的代价（服务器失去主动询问能力），也是无状态化的必然（每个请求必须能独立完成或明确中断）。

## 6. 双代服务：一个端点两代协议

2026-07-28 发布的 SDK 全部采用"双栈并行"而非"flag-day 切换"：

| SDK | 双代实现方式 |
|---|---|
| Python mcp v2.0.0 | 同一 `MCPServer` 自动服务 2026-07-28 与全部 2025 版修订，零配置 |
| TypeScript v2 | `createMcpHandler` 每请求自动回退：新协议直通，旧协议走 2025-11-25 路径 |
| Go SDK v1.7.0-pre.1 | 每端点保留旧版兼容，连接时协商最高共同版本 |
| Dart mcp_server | 2026-07-28 作为版本门控并行路径，握手路径保留给 ≤2025-11-25 对端 |

服务器的选择逻辑：

```text
收到请求
 ├─ _meta.protocolVersion 存在 → 新协议路径（无状态处理）
 ├─ 是 initialize 方法 → 旧协议路径（握手 + 会话）
 └─ 版本集合协商 → 响应中声明 supportedVersions（旧版在握手结果中带 protocolVersion）
```

## 7. 并发与资源控制

无状态服务器的并发模型比旧版简单得多：

| 维度 | 旧版（会话式） | 新版（无状态） |
|---|---|---|
| 并发单位 | 会话（每会话状态独占） | 请求（无共享状态，天然并发安全） |
| 限流 | 按会话配额 | 按请求/按客户端（IP、ClientInfo） |
| 扩容 | 会话亲和的节点必须复制会话 | 任意节点处理任意请求 |
| 长耗时工具 | 单会话内串行受限 | 请求级并发，超时由客户端控制 |
| 内存 | 会话状态随连接驻留 | 请求处理完即可回收 |

服务器仍要防的坑：单个工具调用超长（建议流式响应或 Tasks 扩展异步化）、恶意高频 discover/list（缓存 ttlMs 兜底）、参数过大（JSON Body 大小限制）。

### 7.1 服务器并发与流式输出

| 并发策略 | 适用 | 实现 |
|---|---|---|
| 同步单线程 | 教学/低并发 | 简单但慢工具会阻塞其他请求 |
| 异步并发（asyncio/事件循环） | Python/Node 标准做法 | 工具函数协程化，事件循环天然并发 |
| 线程池 | Java/Go 传统做法 | 每请求一任务，限制池大小防打满 |
| 队列 + 工作进程 | CPU 密集工具 | 外部队列，服务器只做调度 |

流式输出（大结果/长生成）：新版下进度与中间结果挂在"发起请求的响应流"上（SSE），请求结束流即结束——与旧版"服务器随时推"完全不同，长任务应优先考虑 Tasks 扩展（任务 ID + 轮询）而不是硬塞进一次 tools/call。

## 8. 无状态下的状态建模

服务器需要跨请求状态时的官方建议——**显式句柄**：

```text
❌ 会话隐式状态：客户端"连上购物服务"就有购物车（旧版幻想）
✅ 显式句柄建模：
   ① create_basket() → 返回 basket_id      （工具创建句柄）
   ② add_item(basket_id, sku, qty)         （句柄作参数回传）
   ③ get_basket(basket_id) / checkout(basket_id)
```

句柄模式的好处（官方原话大意）：**模型能推理句柄**——模型在计划阶段就能看到 `basket_id` 变量并显式讨论它，而隐式会话状态模型看不见、只能猜。这是"把状态从协议挪到业务层"的架构红利。

## 9. SDK 服务器源码结构

| SDK | 服务器类/入口 | 要点 |
|---|---|---|
| Python mcp v2 | `MCPServer`（原 FastMCP） | `mcp.run()` 自动选传输；`@server.tool()` API 不变 |
| Python mcp v1.28 | `FastMCP` | 旧名旧 API，v2 前不要升级 |
| TypeScript v2 | `@modelcontextprotocol/server` | `createMcpHandler` 双代；`registerTool()`；ESM-only |
| TypeScript v1.29 | `@modelcontextprotocol/sdk` | `McpServer` + `server.tool()` |
| Java SDK 1.1.0 | `McpServer` + `McpSyncServerExchange` | Spring AI 2.0.0-M3 的 `@McpTool` 注解挂载 |

```python
# 双代服务器最小骨架（Python mcp v2）
from mcp import MCPServer

server = MCPServer("weather")

@server.tool()
def get_weather(city: str) -> str:
    """查询城市天气"""
    return "晴，32°C"

if __name__ == "__main__":
    server.run()          # stdio 或 HTTP，自动双代服务
```

### 9.1 服务器测试与验收要点

| 测试 | 内容 | 工具/方法 |
|---|---|---|
| 协议合规 | discover/列表/调用全方法覆盖、resultType、缓存字段 | MCP Inspector |
| 双代兼容 | v1 客户端握手路径 + v2 客户端 discover 路径 | 两代 SDK 各写一个测试客户端 |
| 并发 | 并发调用无串扰、注册表线程安全 | 压测（如 50 并发） |
| 错误路径 | 参数错误/权限拒绝/版本不支持/头不匹配 | 错误码断言 |
| 长任务 | 慢工具不阻塞其他请求（异步化） | 注入延迟 |
| 迁移回归 | 会话代码移除后行为一致 | 对照测试 |

### 9.2 服务器常见踩坑清单

| 坑 | 后果 | 解法 |
|---|---|---|
| stdout 打印日志 | stdio 帧错乱 | 日志走 stderr |
| 忘记 discover 实现 | 新客户端探测失败被当旧服务器 | MUST 实现（协议强制） |
| 结果缺 resultType | 新版客户端按 complete 处理，MRTR 失效 | SDK 自动补，手写注意 |
| 列表缺 ttlMs | 客户端无法缓存，每连接重拉 | SDK 自动补 |
| 工具函数线程不安全 | 并发调用数据错乱 | 注册表/实现无共享可变状态 |
| 参数 schema 宽松 | 注入/误用 | strict 校验 |
| 长任务同步阻塞 | 单请求拖死全部 | 异步化 + Tasks 扩展 |

### 9.3 服务器的资源与安全基线

| 项目 | 基线建议 |
|---|---|
| 请求体上限 | 1-10 MB（防超大参数） |
| 单工具超时 | 60s 内返回；更长走 Tasks 扩展 |
| 并发上限 | 显式限制（连接数/请求数），防单客户端打满 |
| 敏感信息 | 参数/结果脱敏（日志、错误信息、追踪 span 均需） |
| 认证 | OAuth 2.1 + iss 校验；内部服务可用服务凭证 |
| 速率 | 按 Mcp-Name/IP 限流（网关或应用层） |

### 9.4 服务器能力暴露的艺术

| 原则 | 反面教训 |
|---|---|
| 一工具一职责，参数精炼 | 万能工具（几十个参数）→ 模型不会用、参数易错 |
| 描述写"做什么/何时用/边界" | "处理订单"这种描述 → 模型误触发 |
| 写操作独立工具 | 读写混在一个工具 → 权限无法细分 |
| 稳定命名（版本化） | 改名 → 客户端缓存失效 + 模型困惑 |
| 敏感工具加确认流程 | 直接执行 → 误操作不可逆 |

> 💡 服务器的"能力面"就是模型的"决策面"：工具怎么暴露，直接决定 Agent 的成功率。这条与 8 节"状态建模"合起来，就是服务器设计的全部哲学——把状态和决策都交给模型可见的东西。

### 9.5 服务器架构自检清单

```text
□ 实现 server/discover（MUST）且返回版本集合 + 能力 + 身份
□ 双代应答：initialize 旧握手路径仍可用
□ 结果带 resultType；列表类带 ttlMs/cacheScope
□ 参数 strict 校验（additionalProperties: false）
□ 工具注册表线程安全、无共享可变状态
□ 长任务异步化（或 Tasks 扩展）
□ 状态全部句柄化（无跨请求隐式状态）
□ stdout 干净（stdio）；Mcp-Method/Mcp-Name 头正确（HTTP）
□ 限流 + 超时 + 脱敏日志齐备
```

## 10. 本模块小结

> 🎯 **核心要点**：服务器 = 注册表（原语三表）+ 招牌方法（server/discover，MUST）+ 管线（头校验→版本选择→分发→校验→执行→组装）+ 双代能力（一个端点服务两代客户端）+ 句柄式状态建模。无状态化的最大收益在运维侧：任意节点处理任意请求、round-robin 均衡、Serverless 部署；最大代价在能力侧：失去"事后主动询问"，统一收编为 MRTR 内联模式。写服务器先过协议合规（discover/resultType/缓存字段三件套），再谈业务优雅——这是与 9.4"能力暴露的艺术"合起来的总纲。服务器架构的最终形态：业务代码零协议感知，全部协议复杂度收敛在 SDK 四层中。
