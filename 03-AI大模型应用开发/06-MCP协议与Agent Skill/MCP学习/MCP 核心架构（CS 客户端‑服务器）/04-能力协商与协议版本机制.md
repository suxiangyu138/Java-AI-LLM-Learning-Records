# 04 能力协商与协议版本机制

## 1. 协议版本时间线

| 版本 | 发布日期 | 里程碑 |
|---|---|---|
| 2024-11-05 | 2024-11-05 | 协议诞生（Anthropic 开源） |
| 2025-03-26 | 2025-03-26 | 引入 HTTP+SSE 传输、OAuth 2.0 |
| 2025-06-18 | 2025-06-18 | 引入 Streamable HTTP（当前主流旧传输） |
| 2025-11-25 | 2025-11-25 | 版本修订（elicitation、审计等） |
| **2026-07-28** | 2026-07-28 | **第 5 版：无状态核心（问世以来最大修订）** |

版本号即日期字符串，客户端/服务器用它做集合运算。官方对旧版的承诺：**12 个月最低弃用窗口**（弃用特性仍完全可用，2026-07-28 发布的功能 2027-07-28 前不会移除）。

## 2. 旧版协商：initialize 握手全流程

旧版（2024-11-05 ~ 2025-11-25）协商是**连接时的一次性仪式**：

```text
客户端                             服务器
   │── initialize（协议版本/能力/身份）──→│
   │←── InitializeResult（版本/能力/身份）──│
   │── notifications/initialized ─────→│    ← 告知"我准备好了"
   │════════ 会话建立（带 Session ID）════╪════
   │── 业务请求（依赖会话状态） ────────→│
```

握手三要素（都在 initialize 参数里）：

| 字段 | 含义 | 例子 |
|---|---|---|
| protocolVersion | 客户端支持的协议版本 | `"2025-11-25"` |
| capabilities | 客户端能力（roots/sampling/elicitation） | `{"sampling": {}}` |
| clientInfo | 客户端身份 | `{"name": "claude-code", "version": "2.x"}` |

服务器侧裁决：版本匹配 → 返回自己的 capabilities + serverInfo；不匹配 → `-32004 UnsupportedProtocolVersionError`（客户端可降级重试）。握手后所有请求都隐式携带会话，能力不再逐请求声明。

## 3. 新版协商：_meta 携带 + server/discover

新版把协商从"仪式"拆成两半：

```text
① 可选探测：server/discover（能力/版本集合/身份 + 缓存元数据）
② 常态声明：每个请求 _meta 携带 protocolVersion + clientCapabilities + clientInfo
③ 服务器回：结果 _meta 带 serverInfo，行为按请求内能力声明决定
```

| 对比维度 | 旧版 initialize | 新版 _meta + discover |
|---|---|---|
| 时机 | 连接时一次 | 探测可选一次 + 每请求恒携带 |
| 载体 | initialize 请求/结果 | 每个请求的 params._meta |
| 版本 | 单一常量协商 | 版本集合，逐请求可不同 |
| 会话依赖 | 强依赖（sessionId 之后才有意义） | 无（请求自包含） |
| 失败成本 | 连接失败 | 单请求失败 |
| 网关友好性 | 需解析握手状态 | 请求头即可路由 |

新版的取舍：用"每个请求多带几十字节元数据"换"无状态、可均衡、可 Serverless"——字节换架构自由度，官方认为划算。

## 4. 版本集合与逐请求协商

2026-07-28 起，协议版本不再是单一常量，而是**带支持版本集合的逐请求协商值**：

```json
// 服务器 discover 结果中的版本集合
"protocolVersions": ["2026-07-28", "2025-11-25", "2025-06-18"]
```

协商规则：

1. 客户端取"自身支持集合 ∩ 服务器支持集合"中的**最高版本**。
2. 该版本写入本次请求的 `_meta.protocolVersion`。
3. 同一连接的不同请求可使用不同版本（实践中客户端会统一，但协议允许逐请求）。
4. 服务器按请求内版本走对应的处理路径（新逻辑/旧逻辑）。
5. 交集为空 → `-32022 UnsupportedProtocolVersionError`。

> 💡 逐请求协商的意义：网关可以按请求粒度混合新旧客户端流量，服务器无需"全有或全无"地选择协议代次——这是双栈能够无痛并存的结构性原因。

### 2.1 握手细节与安全含义

旧版握手的三个容易被忽略的细节：

1. **版本降级循环**：客户端 initialize 带最高版本 → 服务器拒绝（-32004/-32022）→ 客户端用更低版本重试——协商是"试探—回落"循环，不是一次成功。
2. **握手窗口是安全薄弱点**：握手完成前服务器不应处理业务请求；未握手的请求按协议错误拒绝。
3. **会话 ID 的生命周期归属**：服务端生成、客户端回传，后续每个请求都要带——一旦丢失（LB 变化/序列化丢失）整个会话作废。

旧版握手在跨代时的角色：新服务器收到旧客户端的 initialize 时，按"双代应答"处理——返回的 protocolVersion 用客户端支持的版本，能力声明合并新旧能力集（旧客户端看不到 extensions 等新字段，忽略即可）。

## 5. 四象限兼容矩阵

| | 新服务器（2026-07-28） | 旧服务器（≤2025-11-25） |
|---|---|---|
| **新客户端** | server/discover → 无状态请求，全功能 | discover 探测失败 → 回退 initialize 握手 → 会话模式（功能受限：无 MRTR/缓存字段） |
| **旧客户端** | 直接 initialize 握手 → 服务器双代应答，会话模式 | initialize 握手 → 会话模式，完整旧功能 |

落地要点：

- **新客户端对旧服务器**：`server/discover` 返回 MethodNotFound（-32601）即触发回退；STDIO 下这是官方认可的探测手段。
- **旧客户端对新服务器**：服务器必须仍接受 initialize 握手（双代服务器 MUST 保持）；无状态路径对旧客户端不可见。
- **迁移路线**：先升客户端（回退路径保证不断），再升服务器（双代应答保证不崩），最后拆掉会话相关代码。

## 6. 协商失败与错误码

2026-07-28 错误码重编号：`-32000 ~ -32019` 留给实现自定义，`-32020 ~ -32099` 预留给 MCP 规范。

| 错误码 | 名称 | 场景 | 旧值 |
|---|---|---|---|
| -32020 | HeaderMismatchError | Mcp-Method/Mcp-Name 头与方法不匹配 | -32001 |
| -32021 | MissingRequiredClientCapability | 请求所需能力客户端未声明 | -32003 |
| -32022 | UnsupportedProtocolVersionError | 版本交集为空 | -32004 |
| -32602 | Invalid Params | 资源未找到（原 -32002 归并） | -32002 |
| -32601 | MethodNotFound | 方法不存在（discover 回退触发条件） | -32601 |

传输层错误剥离：传输失败返回真实 HTTP 状态码（如未知方法 → HTTP 404），不再用 JSON-RPC 错误包装传输问题——"传输层与应用层干净分离"。

## 7. 能力矩阵速查

| 能力 | 声明方 | 旧版 | 新版 | 说明 |
|---|---|---|---|---|
| tools | 服务器 | ✅ | ✅ | listChanged 订阅能力 |
| resources | 服务器 | ✅ | ✅ | 模板/订阅（订阅改 subscriptions/listen） |
| prompts | 服务器 | ✅ | ✅ | 提示模板 |
| logging | 服务器 | ✅ | ⚠️ 弃用 | 改 per-request logLevel |
| completions | 服务器 | ✅ | ✅ | 参数自动补全 |
| roots | 客户端 | ✅ | ⚠️ 弃用 | 建议资源 URI/工具参数替代 |
| sampling | 客户端 | ✅ | ⚠️ 弃用 | 建议直接调 LLM API |
| elicitation | 客户端 | ✅ | ⚠️ 弃用 | MRTR input_required 替代 |
| extensions | 双方 | — | ✅ | 扩展映射（Tasks/Apps） |

### 7.1 能力协商的最佳实践

| 实践 | 理由 |
|---|---|
| 客户端：能力声明最小化 | 只声明真实支持的能力，声明了就要兑现（"双方必须尊重声明"） |
| 服务器：能力声明精确化 | 过度声明（如声明 listChanged 却不发通知）是兼容性隐患 |
| 双向：先 discover 再使用 | 一次探测避免多轮失败重试（ttlMs 内缓存） |
| 服务器：版本集合宁缺毋滥 | 只列真支持的版本，避免被选择后行为错乱 |
| 客户端：降级显式记录 | discover 回退 initialize 时打日志，方便排障 |
| 双方：能力变化通知 | 目录/能力变化通过 listChanged 通知，别让客户端长期缓存过期能力 |

### 7.2 协商相关的错误处理演练

| 场景 | 正确行为 | 错误行为 |
|---|---|---|
| 客户端带 2026-07-28 请求旧服务器 | discover 失败 → initialize 回退 | 直接报"协议不支持" |
| 服务器只支持 2025-11-25，客户端只发新版本 | 返回 -32022 + 支持版本列表 | 静默按旧版处理（数据错位风险） |
| 客户端声明了 extensions.tasks 但服务器没声明 | 服务器拒绝 tasks 方法（-32021 或 404） | 服务器假装支持（行为未定义） |
| 网关透传版本不匹配 | 网关按头路由返回 400/404 | 网关改 body 里的版本（篡改协议） |

### 7.3 版本演进的管理纪律

| 纪律 | 说明 |
|---|---|
| 语义化版本选择 | 客户端应优先支持"较新但已稳定"的版本，而非盲目追最新 |
| 12 个月窗口倒计时 | 弃用功能在新版发布后 12 个月内移除；升级计划以窗口为准 |
| 版本集合声明测试 | 每个新版本上线前用两代客户端各测一遍（兼容矩阵回归） |
| changelog 追踪 | 每次规范发布读 changelog 的"Key Changes"——本体系各表均源自官方 changelog |
| SDK 升版纪律 | SDK 版本 ≠ 协议版本；确认 SDK 声明支持的协议版本后再升 |

> 💡 面试加分点：能说出"协议版本是日期字符串、逐请求协商、版本集合取交集"这三件事的人，说明真的读过规范而不是背的八股。

## 8. 协商决策树

```text
收到客户端请求
│
├─ 请求带 _meta.protocolVersion？
│   ├─ 是 → 版本 ∈ 服务器支持集合？
│   │     ├─ 是 → 无状态路径处理 ✅
│   │     └─ 否 → -32022 拒绝（建议降级重试）
│   └─ 否（旧客户端）
│        ├─ 是 initialize 方法？
│        │   ├─ 是 → 旧握手路径（回 protocolVersion 协商结果）
│        │   └─ 否 → 按会话模式处理（需已握手）
│        └─ 会话不存在 → -32001/-32000 类错误
```

### 8.1 协商过程的时序总结

```text
新客户端 ↔ 新服务器：
  ① （可选）server/discover → 版本集合 + 能力 + 身份（可缓存 ttlMs）
  ② 每个请求 _meta 带 protocolVersion + clientCapabilities
  ③ 服务器按版本走新路径，返回 resultType + 缓存字段 + serverInfo

新客户端 ↔ 旧服务器：
  ① discover → MethodNotFound（-32601）→ 判为旧服务器
  ② initialize 握手 → 会话模式（能力降级：无 MRTR/缓存字段）
  ③ 每个请求带会话标识（SDK 内部处理）

旧客户端 ↔ 新服务器：
  ① initialize 握手 → 服务器双代应答（回旧版 protocolVersion）
  ② 后续按会话模式处理，一切如旧
```

### 8.2 协商与安全的关系

协商结果直接决定安全边界，三处要点：

| 安全点 | 说明 |
|---|---|
| 能力声明即授权边界 | 客户端声明了什么，服务器才按什么对待——未声明的能力不允许调用（-32021） |
| 版本协商与漏洞面 | 旧版本可能有已知缺陷；服务器可选择拒绝过旧版本（业务策略） |
| discover 的缓存风险 | discover 结果带 cacheScope，private 场景不得共享缓存（防能力信息泄漏） |
| MRTR 令牌安全 | requestState 不透明令牌不得泄露在日志/错误信息中 |

> ⚠️ 安全金句：**协商是"承诺"，不是"宣传"**——声明能力的一方必须兑现，使用能力的一方必须验证。

### 8.3 协商相关名词辨析

| 名词 | 含义 | 易混淆点 |
|---|---|---|
| protocolVersion | 协议版本（日期字符串） | 不是 SDK 版本！SDK 版本 ≠ 协议版本 |
| capabilities | 能力声明（双方各自） | 不是权限！声明能力 ≠ 授予权限 |
| extensions | 扩展映射（reverse-DNS） | 不是插件！是能力协商的扩展命名空间 |
| server/discover | 能力探测方法 | 不是握手！探测可选、握手（旧版）强制 |
| _meta | 请求元数据容器 | 不是业务参数！业务参数在 arguments |
| resultType | 结果类型标记 | 不是 MIME 类型！是 complete/input_required 二值 |

> 💡 面试时把"protocolVersion ≠ SDK 版本"说清楚，能立刻区分读过规范和背过八股的人。

### 8.4 协商全过程的时序复盘

一次完整的新旧混合环境接入流程：

```text
① 新客户端启动，配置了 5 个服务器（3 新 2 旧）
② 并行 discover：3 新成功（缓存能力与版本集），2 旧返回 -32601
③ 2 旧服务器改走 initialize 握手（会话模式）
④ 每请求 _meta 装配：新服务器走无状态，旧服务器走会话（SDK 内部）
⑤ 工具目录合并：5 个 Client 的 list 结果聚合进 Host 目录（命名空间化）
⑥ 运行期：新服务器目录变化走 subscriptions/listen，旧服务器靠轮询
⑦ 迁移完成：旧服务器升双代后，客户端自动切换到 discover 路径
```

这条流程把本模块所有知识点串成了实际操作——能复述它，就说明协商机制已经真正内化。

### 8.5 协商机制的底层动机

| 设计选择 | 动机 |
|---|---|
| 版本=日期字符串 | 语义自明、天然排序、发布节奏透明 |
| 集合取交集 | 不要求全序比较，新老实现各让一步 |
| 逐请求协商 | 网关按请求混流，无需按连接锁版本 |
| 声明必尊重 | 能力边界 = 行为契约，防止幻觉式调用 |
| 12 个月弃用窗口 | 生态有可预期的迁移期，避免 flag-day 破坏 |

> 💡 这五条合起来回答一个面试深问："MCP 是怎么做到两年 5 个大版本还不破坏生态的？"——答案是"协商制 + 双栈 + 窗口政策"三位一体。

## 9. 本模块小结

> 🎯 **核心要点**：协商机制三代演进——一次性握手（旧）→ 每请求自包含（新）。不变的是"集合取交集、声明必尊重"两条铁律。版本从常量变集合、错误码从 MCP 专属编号归并 JSON-RPC 标准、传输错误回 HTTP 状态码，三处改动共同把 MCP 从"专有会话协议"推向"标准无状态 RPC"。**双栈回退（discover 失败 → initialize）是 2026 下半年所有 SDK 的标配逻辑**。版本演进的管理纪律（12 个月窗口、四象限回归）是把协议变化变成工程可控的关键。
