# 01 架构全景：Host-Client-Server 三方模型

> 整个 MCP 架构只有三张牌：Host 是容器与协调者、Client 是与服务器一一对应的连接器、Server 是独立的能力提供者——先看懂"谁管什么、边界在哪"，再看任何源码与规范都不会迷路。

## 1. 三方角色总览

官方对架构的定性一句话："一种客户端—主机—服务器架构，其中每个主机可以运行多个客户端实例"（client-host-server architecture where each host can run multiple client instances）。三方各司其职：

| 角色 | 一句话职责 | 与谁通信 | 类比 |
|---|---|---|---|
| Host | 容器与协调者：创建/管理 Client、管权限与授权、协调 LLM、聚合上下文 | 直接对话用户与模型 | 应用本体 |
| Client | 与**恰好一个** Server 建立 1:1 连接，协议消息双向路由 | 只对一个 Server | 设备驱动 |
| Server | 通过原语暴露能力，独立运行、互不知晓 | 只面对自己的 Client | 外设 |

三个关键约束塑造了全部架构：

1. **1:1 关系**：一个 Client 只连一个 Server，跨服务器的能力组合必须由 Host 层协调——这保证服务器彼此隔离。
2. **单向发现**：Client 发现 Server 的能力（list/read/call），Server 不知道 Host 里还有哪些其他服务器。
3. **状态归属 Host**：完整对话历史永远留在 Host，服务器"既读不到整段对话，也看不到别的服务器"。

## 2. Host：容器与协调者

### 2.1 职责清单（官方架构页逐条展开）

| 职责 | 具体内容 | 落点 |
|---|---|---|
| 容器 | 创建、持有、销毁多个 Client 实例，每个 Client 绑一个 Server | 生命周期管理 |
| 连接策略 | 决定允许/拒绝哪些服务器（用户配置 + 审批） | 权限前置 |
| 安全策略 | 强制执行安全边界，隔离服务器之间的数据访问 | 信任边界 |
| 用户授权 | 处理用户的同意/拒绝决策（工具调用前确认） | 人机界面 |
| LLM 集成 | 协调模型与工具结果的循环（调用模型 → 发请求 → 回传结果） | Agent 循环 |
| 上下文聚合 | 把多个 Client 获取的结果聚合成模型的上下文窗口 | 记忆编排 |
| 权限控制 | 按服务器/工具粒度下发权限（如只读工具白名单） | 最小权限 |

> 💡 Host 不直接参与协议：协议通信发生在 Client↔Server，Host 只负责"上层决策"与"下层资源"。这也是 MCP 与传统 RPC 中间件的核心区别——中间件是服务间通信，MCP 是**应用内嵌连接器**到外部能力的通信。

### 2.2 典型 Host 全景

| Host 类型 | 代表 | 形态 |
|---|---|---|
| CLI Agent | Claude Code | 终端内多 Client 并行 |
| 桌面 IDE | Cursor / VS Code Copilot | 编辑器内嵌 |
| 桌面应用 | Claude Desktop | 双 Client（filesystem/git） |
| 自建应用 | 企业智能客服系统 | 服务端 Host，Client 走 Streamable HTTP |
| 网关型 Host | AgentCore Gateway 等 | 把 MCP 能力再封装成 API 面 |

## 3. Client：1:1 连接器

Client 是架构里"最容易低估、实际最重"的角色——所有协议机制都发生在它身上。官方列出的职责：

| 职责 | 说明 |
|---|---|
| 1:1 连接 | 与一个 Server 建立并维护唯一连接 |
| 请求装配 | 给**每个请求**附加协议版本、客户端能力与身份（_meta） |
| 双向路由 | 请求 → Server；响应/通知 ← Server |
| 订阅管理 | 打开/关闭订阅（subscriptions/listen），处理 notifications/* |
| 安全边界 | 维护服务器之间的隔离，不透传状态 |

### 3.1 为什么是 1:1 而不是 1:N

```
Host（Claude Code）
 ├── Client A ──→ Server A（文件系统）
 ├── Client B ──→ Server B（数据库）
 └── Client C ──→ Server C（内部 API）
```

- 若一个 Client 连多 Server，协议上必须引入"路由维度"，方法名冲突（两个 Server 都有 `read`）、通知归属都无从谈起。
- 1:1 让每个 Client 成为"纯净的协议对端"：状态、能力、订阅都天然隔离。
- 代价由 Host 承担：模型要用的工具来自多个 Server 时，Host 把多 Client 的结果聚合进上下文——这正是"Host 是协调者"的意义。

### 3.2 双栈 Client（2026-07-28 新要求）

无状态规范要求新 Client 同时会说两代协议：

```text
连接 Server 时：
  1. 尝试 server/discover（无状态探测）
  2. 若对方是旧 Server（2025-11-25 及更早）→ 回退 initialize 握手
  3. 之后每个请求按协商出的版本装配 _meta
```

> 💡 官方明确允许 `server/discover` 作为 STDIO 上的向后兼容探测：探测失败即视为旧服务器，无缝降级。这就是"新客户端 + 旧服务器"象限能正常工作的原因。

## 4. Server：独立能力提供者

### 4.1 职责清单

| 职责 | 说明 |
|---|---|
| 原语暴露 | 通过 tools/resources/prompts 三种原语提供能力 |
| 独立运行 | 本地子进程（stdio）或远程服务（Streamable HTTP），互不依赖 |
| 能力声明 | 响应 server/discover（新版）或 initialize（旧版）时通告 capabilities |
| 请求处理 | 处理 client 发来的 list/read/call 请求，返回 resultType 标记的结果 |
| 内联索要输入 | 处理中返回 `InputRequiredResult`（MRTR），向客户端索要用户输入或模型补全 |
| 遵守安全约束 | 遵循 Host 下发的权限与 OAuth 授权边界 |

### 4.2 服务器的"无状态"心智

2026-07-28 之后，Server 被明确要求**不依赖协议层会话状态**：

```text
❌ 旧心智：客户端连上 → 我记住它的能力与偏好 → 后续请求都按这个会话处理
✅ 新心智：每个请求自包含（版本+能力+身份）→ 我无脑处理 → 请求结束即忘
```

需要跨请求状态的业务（如购物车），把状态显式建模为参数：`basket_id` 由工具创建并回传给客户端，模型能"看见并推理"这个句柄——官方认为这比隐藏的会话状态更优，因为模型可以显式讨论它。

## 5. 架构设计原则

官方架构页明确的设计原则，是理解一切取舍的钥匙：

| 原则 | 含义 | 影响 |
|---|---|---|
| 服务器不知道整段对话 | Server 只能看到当前请求上下文 | 隐私隔离，Host 不把全部历史发给工具 |
| 服务器之间不可见 | 每个 Server 独立，互不知晓存在 | 无共享状态，天然可横向扩展 |
| 完整历史留在 Host | 对话、记忆、聚合都由 Host 管理 | Host 是唯一有全局视角的组件 |
| 能力协商制 | 双方必须尊重已声明的能力 | 渐进式扩展，向后兼容 |
| 按需复杂度 | 核心保持精简，复杂特性（扩展）按需挂载 | 扩展框架的价值 |
| 请求自包含 | 每个请求携带版本与能力（无状态核心） | 负载均衡、Serverless 成为可能 |

### 5.1 设计原则在生产中的三种体现

| 原则 | 生产体现 | 反面教材 |
|---|---|---|
| 服务器不知道整段对话 | 工具调用只传必要参数，不把对话历史塞进 arguments | 把用户聊天记录全量传给工具 → 隐私泄漏 + token 浪费 |
| 服务器之间不可见 | 每个能力独立部署、独立鉴权、独立扩容 | 服务器间共享数据库/共享配置 → 耦合 + 安全隐患 |
| 完整历史留在 Host | Host 维护会话记忆与上下文窗口 | 服务器侧缓存对话 → 状态泄漏到无状态边界外 |
| 能力协商制 | 先 discover 再调用，客户端尊重服务器能力边界 | 假设服务器有未声明的工具 → 运行时失败 |
| 按需复杂度 | 默认只挂三原语，需要 UI 再协商 MCP Apps 扩展 | 一口气实现全部官方扩展 → 维护灾难 |
| 请求自包含 | 网关无脑转发、LB 无脑均衡 | 依赖请求间状态 → 均衡后行为错乱 |

### 5.2 通信模型：谁对谁说话

```text
用户 → Host（自然语言交互）
Host → Client（意图驱动的调用指令）
Client ⇄ Server（JSON-RPC：请求/响应/通知）
Server ⇄ 外部系统（业务调用：DB/API/文件）
```

注意一个不对称：**模型不直接跟 Server 说话**。模型的所有工具调用都经过 Host 的编排器 → Client → Server，模型看到的只是"工具列表 + 调用结果"。这个间接层正是安全控制（授权确认、参数净化、结果审计）的落点，也是 MCP 与"直接函数调用"的本质区别。

## 6. 部署拓扑与类比

### 6.1 三种拓扑

```text
① 本地单机（开发期）：Host 内嵌 Client，Server 为本地子进程（stdio）
② 远程直连（生产）：Host 内嵌 Client，Server 为远端 HTTP 服务（Streamable HTTP）
③ 网关托管（企业）：Host → MCP 网关 → 多个远端 Server（网关做路由/鉴权/限流）
```

### 6.2 类比记忆法

| MCP 角色 | 计算机体系 | 现实世界 |
|---|---|---|
| Host | 操作系统 | 老板（全局决策） |
| Client | 设备驱动 | 项目经理（对接单一外包商） |
| Server | 外设（打印机/硬盘） | 外包商（只做自己的活） |

打印机不会知道电脑里还插了键盘——对应"服务器之间不可见"；老板决定要不要把打印结果纳入决策——对应"上下文聚合在 Host"。

### 6.3 选择拓扑的三个判断

| 判断依据 | 选择 |
|---|---|
| 服务器跑在用户机器上？ | 本地 stdio（无网络暴露，权限即本机权限） |
| 服务器是团队共享服务？ | 远程 Streamable HTTP + OAuth |
| 需要跨团队/跨部门治理？ | 网关托管（路由/鉴权/计量/审计集中化） |

## 7. 双代架构对比（2025-11-25 vs 2026-07-28）

| 维度 | 旧架构（2025-11-25 及更早） | 新架构（2026-07-28） |
|---|---|---|
| 连接模型 | 有状态会话（Mcp-Session-Id） | 无状态，请求自包含 |
| 能力协商 | 连接时 initialize 握手一次性交换 | 每次请求 _meta 携带 + server/discover 按需探测 |
| 状态归属 | 会话状态在连接双方 | 状态显式建模为参数/句柄 |
| 服务器发起请求 | 支持（roots/sampling/elicitation 长流） | 仅限处理中内联（MRTR input_required） |
| 心跳 | ping 请求 | 移除（HTTP 层健康检查替代） |
| 扩展能力 | 无统一机制 | extensions 映射 + 官方扩展（Apps/Tasks） |
| 部署形态 | 会话亲和的负载均衡 | round-robin 均衡 + Serverless |
| 兼容关系 | — | 新实现双栈兼容旧实现，12 个月弃用窗口 |
| 缓存 | 无正式缓存契约 | ttlMs/cacheScope 正式化（SEP-2549） |
| 追踪 | 私有扩展各搞各的 | W3C traceparent/tracestate 进 _meta（SEP-414） |

### 7.1 双代共存的现实形态

2026-07-28 发布后，生态处于"新旧并行"的过渡期，现实中的系统往往是这样的：

```text
旧客户端（2025 SDK）───→ 新服务器（双代）──→ 旧服务器
新客户端（v2 SDK）───→ 新服务器（双代）──→ （走 discover）
```

- **同一条流水线里新旧混跑**：网关按请求逐版本分发，无需区分实例。
- **升级顺序建议**：先升客户端（回退路径保底）→ 再升服务器（双代应答）→ 最后移除会话代码。
- **12 个月窗口的用途**：旧实现有充足时间发布兼容版本，无需 7 月 28 日当天停机。

## 8. 架构 FAQ 快问快答

| 问题 | 一句话答案 |
|---|---|
| Host 能同时连几个 Server？ | 无限（受资源限制），每 Server 一个 Client |
| 一个 Client 能连两个 Server 吗？ | 不能，协议层强制 1:1；要连多个就开多个 Client |
| 服务器能主动找客户端要数据吗？ | 旧版能（采样/追问），新版只能在处理请求中（MRTR） |
| 谁负责把工具结果拼进上下文？ | Host；它聚合所有 Client 的结果再交给模型 |
| 服务器崩溃了客户端怎么办？ | 新版：重试请求（业务幂等）；旧版：会话重建 |
| 无状态后会话丢了怎么办？ | 会话本来就不该存在——状态建模为句柄参数 |

### 8.1 自检三问

1. 我能否画出 Host 含三个 Client、每个连不同 Server 的拓扑，并说出谁负责把三个服务器的结果合并给模型？（答案：Host）
2. 我能否说出三条以上"为什么 1:1 是必然"的理由？（方法名隔离/状态隔离/订阅归属/安全边界）
3. 我能否把"服务器不可见原则"翻译成一个具体的权限设计？（每个 Server 独立的凭证与数据范围）

答不出第 2 问回到 3.1 节，答不出第 3 问回到 5 节——本模块自洽闭环。

## 9. 本模块小结

> 🎯 **核心要点**：MCP 架构的三方 = Host（容器与协调者，管全局）、Client（1:1 连接器，管协议）、Server（独立能力提供者，管原语）。六条设计原则中，"服务器不知全貌、状态留 Host、能力协商制"是永恒骨架；2026-07-28 把"会话式"重构为"无状态"是机制层变革——骨架没变，机制换了，部署形态因此从"会话亲和"走向"无状态水平扩展"。
