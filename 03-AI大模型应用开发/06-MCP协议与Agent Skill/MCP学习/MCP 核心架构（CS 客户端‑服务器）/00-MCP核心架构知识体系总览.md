### 3.1 架构演进主线（为什么是现在这样）

MCP 架构两年多走了一条清晰的收敛线，看懂这条线就能理解"为什么 2026-07-28 要无状态化"：

| 阶段 | 架构特征 | 暴露的问题 |
|---|---|---|
| 2024-11-05 诞生 | 仅 stdio、会话式握手、三原语 | 只能本机玩 |
| 2025-03-26 | 引入 HTTP+SSE 远程传输 + OAuth 2.0 | 远程化打开企业场景 |
| 2025-06-18 | 引入 Streamable HTTP | 双传输并存，会话仍是核心 |
| 2025-11-25 | 版本稳定期，生态爆发（百万级服务器） | 会话式架构阻碍规模化：LB 粘滞、Serverless 不可用、双向通道难治理 |
| **2026-07-28** | **无状态核心：删握手、删会话、协商入 _meta、MRTR 收编双向通道** | 把协议变成可均衡、可缓存、可观测的标准 HTTP 服务 |

演进主线一句话：**从"专有会话协议"走向"标准无状态 RPC"**——每次修订都在把复杂度从协议层移向业务层与基础设施层，让 MCP 越来越像普通 HTTP 服务，从而能吃下任意规模的部署。这也是本体系每个机制都要回答"它对部署形态意味着什么"的原因。

演进动因拆解（为什么 2025 年底非改不可）：

| 痛点 | 数据/事实 | 无状态化后的解法 |
|---|---|---|
| 负载均衡必须粘滞 | 会话 ID 在服务端存储，请求必须回原实例 | 请求自包含 → round-robin |
| Serverless 不可用 | Lambda/Workers 无持久连接概念 | 纯请求处理 → 天然适配 |
| 双向通道难治理 | sampling/elicitation 长流在网关/审计下是黑盒 | MRTR 内联化 → 每步可审计 |
| 缓存零基础 | 工具目录每次重拉 | ttlMs/cacheScope 正式化 |
| 可观测性割裂 | 追踪靠私有扩展 | traceparent 进 _meta（SEP-414） |

这张表也是面试回答"为什么 2026-07-28 要大改"的最佳素材：每个痛点都能对上具体的规范变更。

## 4. 核心概念速查

下表覆盖本体系全部核心术语（22 项），是速查与面试前 5 分钟的复习卡。状态列：✅ 现行 / ❌ 移除 / ⚠️ 弃用 / 🔄 重编号 / 新增。

| 概念 | 一句话定义 | 2026-07-28 状态 |
|---|---|---|
| Host | 宿主应用，容器与协调者：创建/管理多个 Client，管权限、授权、LLM 集成 | 角色不变 |
| Client | 与一个 Server 一一对应的协议连接器，给每个请求附加版本与能力 | 核心不变 |
| Server | 能力提供者，暴露 tools/resources/prompts 原语 | 核心不变 |
| initialize 握手 | 连接时的强制初始化协商（版本 + 能力 + 会话 ID） | ❌ 移除 |
| server/discover | 可选的服务器能力/版本/身份探测 RPC | ✅ 新增（Server MUST） |
| Mcp-Session-Id | HTTP 传输的会话标识头 | ❌ 移除 |
| _meta 协商 | 每次请求自包含协议版本、客户端能力、身份 | ✅ 新增（强制） |
| MRTR | 服务器在处理请求中返回 input_required 索要输入，客户端带答案重试 | ✅ 新增 |
| resultType | 每个结果的必填字段：`complete` / `input_required` | ✅ 新增 |
| Mcp-Method/Mcp-Name 头 | Streamable HTTP POST 必带的协议路由头，供网关按方法名路由 | ✅ 新增 |
| ttlMs/cacheScope | 列表类结果必带缓存元数据（public/private） | ✅ 新增 |
| subscriptions/listen | 服务器主动通知的订阅机制（取代 GET 流与 resources/subscribe） | ✅ 新增 |
| Roots/Sampling/Logging | 服务器侧向客户端索要上下文/模型补全/日志控制 | ⚠️ 弃用（12 个月窗口） |
| HTTP+SSE 传输 | 旧远程传输（GET /mcp + SSE 流） | ⚠️ 弃用 |
| ping | 心跳保活方法 | ❌ 移除 |
| 错误码 -32022 | 协议版本不支持（原 -32004） | 🔄 重编号 |
| 错误码 -32602 | 资源未找到改归 JSON-RPC Invalid Params | 🔄 重编号 |
| 扩展框架 | reverse-DNS ID + capabilities.extensions 协商 + 独立发布节奏 | ✅ 新增 |
| MCP Apps / Tasks | 官方扩展：沙箱 HTML 交互界面 / 异步长任务 | ✅ 新增 |
| 双栈兼容 | 新实现同时服务 2026-07-28 与旧版客户端，12 个月弃用窗口 | ✅ 政策 |

### 4.1 常见误区速排

| 误区 | 事实 |
|---|---|
| "MCP 是 RPC 中间件" | 是应用内嵌连接器到外部能力的协议；跨服务通信不是它的职责 |
| "2026-07-28 删了握手，旧客户端就断了" | 双代兼容：新服务器继续应答 initialize，12 个月弃用窗口 |
| "无状态 = 不能保存任何状态" | 协议层无状态；业务状态用显式句柄（basket_id）建模，协议鼓励 |
| "subscriptions/listen 断了会续传" | 不续传！断流 → 重新 listen + 重拉目录 + ttlMs 兜底 |
| "MRTR 只是改名" | 机制变了：旧版服务器生命周期内随时可发起请求，新版只能在处理请求中内联索要 |
| "错误码 -32002 还是资源未找到" | 重编号 -32602（归并 JSON-RPC Invalid Params） |
| "采样/roots 已经删了" | 弃用不是移除：12 个月内完全可用，只是建议迁移 |
| "server/discover 是可选实现" | 服务器 MUST 实现（与旧版 initialize 同级强制） |

### 4.2 版本基线说明

本体系以 **2026-07-28 规范（第 5 版）** 为主基线、2025-11-25 及更早为对比基线。SDK 版本参照 2026-08 生态现状：Python `mcp` 稳定线 v1.28.x / 新线 v2.0.0（FastMCP 改名 MCPServer）、TypeScript `@modelcontextprotocol/sdk` v1.29 / v2 拆包为 `@modelcontextprotocol/client`+`@modelcontextprotocol/server`（2.0.0-beta）、Java SDK 1.1.0、Go SDK v1.7.0-pre.1、C# SDK v2.0.0。文中标注"旧版"均指 2025-11-25 及更早规范。

### 4.3 阅读约定

- **"旧版"**：指 2025-11-25 及更早的会话式规范；**"新版"**：指 2026-07-28 无状态规范。
- **"双代"**：同一个实现同时服务新旧两代协议（服务器双代应答、客户端双栈回退）。
- **弃用 ≠ 移除**：标注 ⚠️ 的功能在 12 个月窗口内仍完全可用。
- 代码示例为教学性简化，生产请以官方 SDK 与规范原文为准；每条结论均可在文末参考来源溯源。

### 5.4 一句话总结

> 🎯 **核心要点**：MCP 架构 = 三方角色（Host 协调、Client 一一对应、Server 独立能力）+ 两大机制（能力协商、消息流）+ 两类部署（本地 stdio、远程 HTTP）。2026-07-28 规范把架构从"会话式"重构为"无状态"：握手移除、协商入 _meta、状态出协议——但三方角色骨架与 1:1 连接模型从未改变。学架构先学"骨架恒、机制变"。
