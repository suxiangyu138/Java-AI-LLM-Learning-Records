# 06 会话与生命周期

> 旧版 MCP 的生命周期是一部"会话状态机"，新版把它删成一页纸：连接 → 请求 → 断开。理解两代生命周期的差异，就理解了"无状态化"到底删掉了什么。

## 1. 旧版：会话状态机

旧版（≤2025-11-25）连接双方各持一张状态机：

```text
客户端：                       服务器：
┌─────────┐                   ┌─────────┐
│ connecting │→ initialize     │ created  │← 进程启动/HTTP 端点就绪
└─────────┘                   └─────────┘
     │ ← InitializeResult          │ ← 收到 initialize
     ▼                            ▼
┌─────────┐  initialized 通知  ┌─────────┐
│ initializing │──────────────→│ initializing │
└─────────┘                   └─────────┘
     │                            │
     ▼                            ▼
┌─────────┐                   ┌─────────┐
│ running  │═════════════════│ running  │← 业务请求、ping、订阅、服务器发起请求
└─────────┘                   └─────────┘
     │ 断开/出错                    │ 断开/出错
     ▼                            ▼
┌─────────┐                   ┌─────────┐
│ closed   │                  │ closed   │
└─────────┘                   └─────────┘
```

| 状态 | 允许的操作 |
|---|---|
| connecting / created | 仅 initialize |
| initializing | 等待握手完成 |
| running | 全部业务请求 + 订阅 + 服务器发起请求（sampling/elicitation/roots） |
| closed | 无操作；HTTP 场景可选 DELETE 会话 |

状态机派生出的工程约束：会话 ID 必须存储（服务器端）、请求必须粘滞（负载均衡）、服务器可随时发起请求（需要全双工长连接）、心跳必须定期发送（ping）。

## 2. 新版：无状态生命周期

2026-07-28 的生命周期退化为一句话：**连接建好即可发请求，请求处理完即结束**。

```text
客户端 → 服务器连接建立（stdio 进程启动 / HTTP 端点可达）
   │
   ├─（可选）server/discover → 能力与版本探测
   ├─ tools/list（可缓存）→ tools/call → ...
   ├─ subscriptions/listen（如需推送）
   └─ 连接关闭（无会话清理、无状态保存）
```

| 生命周期事件 | 旧版动作 | 新版动作 |
|---|---|---|
| 连接建立 | initialize 握手 + 会话创建 | 无（或可选 discover） |
| 请求发送 | 依赖会话隐式状态 | 每请求自包含 |
| 健康检查 | ping（协议内） | HTTP 健康端点 / 传输层超时 |
| 服务器重启 | 客户端重握手、会话重建 | 客户端重试请求即可（幂等性由业务保证） |
| 连接关闭 | 可选会话删除 | 无 |
| 优雅停机 | 通知客户端 + 清理会话 | 传输层停机（HTTP 返回 503） |

## 3. ping 移除与健康检查替代

旧版 `ping`（请求 + 空结果）用于保持连接活跃与检测对端存活，2026-07-28 移除。替代方案：

| 场景 | 替代手段 |
|---|---|
| stdio | 子进程存活探测（进程存在 + 管道可写） |
| Streamable HTTP | HTTP 层：健康检查端点、请求超时（TCP keep-alive） |
| 长订阅流 | subscriptions/listen 流的存活即健康（断流即重连） |
| 网关 | 上游健康检查（如 LB 的 /healthz），按 MCP 方法头路由 |

> 💡 ping 的移除是无状态化的必然：ping 是"会话协议"的体检工具，无状态协议没有会话可体检，健康责任整体上移给传输层与基础设施。

### 3.1 健康检查与超时设计

无状态下的健康检查全部下放传输层与业务层，客户端只需一套统一超时策略：

| 场景 | 超时 | 说明 |
|---|---|---|
| 发现类（list/discover/read） | 5-10s | 目录操作应快 |
| 调用类（tools/call） | 30-120s | 工具可能慢 |
| 订阅流 | 无限（流式） | 靠断流检测替代超时 |
| 连接建立（HTTP） | 10s | 含 TLS 握手 |
| 重试间隔 | 指数退避（1s→2s→4s→上限） | 防雪崩 |

与旧版对比：旧版还多一层"ping 超时"（协议级保活），新版把这一层整个删掉——少一层超时，就少一类故障。

## 4. 订阅生命周期

订阅在 2026-07-28 有专门的生命周期（SEP-2549 相关）：

```text
① 打开：subscriptions/listen { type: "toolsListChanged", ... }
② 确认：服务器 → notifications/subscriptions/acknowledged（带 subscriptionId）
③ 推送：服务器 → notifications/toolsListChanged（带 subscriptionId）
④ 消费：客户端按 subscriptionId 路由 → 刷新对应目录缓存
⑤ 失效：流中断 → 客户端重新 listen（新 subscriptionId）
```

| 属性 | 旧版（GET 流 + resources/subscribe） | 新版（subscriptions/listen） |
|---|---|---|
| 载体 | 独立 HTTP GET 流 / subscribe 方法 | 单一 POST 响应流（长流） |
| 标识 | 无统一 ID | subscriptionId 统一标识 |
| 可恢复性 | SSE 事件 ID 可续传（Last-Event-ID） | **无续传**：断流重发请求 + 新 ID |
| 订阅对象 | 仅资源 | 工具/提示/资源目录 + 资源内容 |

**断流语义是重点**：新版明确移除了 SSE 可恢复性与重投递（Last-Event-ID、事件 ID 全部删除）——订阅流断了就重新订阅，期间错过的变更靠客户端"周期性重拉 + ttlMs 缓存"兜底。

## 5. 中断、恢复与重连

| 故障 | 旧版恢复 | 新版恢复 |
|---|---|---|
| 请求超时 | 依赖会话重试（小心粘滞） | 客户端重试，无会话概念 |
| 传输断流 | 重连 → 重握手 → 会话重建（旧会话状态丢失） | 重连 → 重发请求（业务幂等性负责去重） |
| 服务器崩溃 | 会话表失效，客户端需感知重连 | 负载均衡器摘除实例，请求被其他实例接管 |
| 订阅流断 | 按事件 ID 续传 | 重新 listen + 主动重拉目录 |

无状态下"重连成本"归零，取而代之的新义务：**业务请求的幂等性**（重试可能重复执行工具）——这是运维从"协议层"转移到"业务层"的成本。

## 6. 会话 vs 无状态：取舍对照

| 维度 | 会话式（旧） | 无状态（新） |
|---|---|---|
| 部署 | 会话亲和（sticky session）、会话存储 | round-robin、无状态实例、Serverless |
| 服务器复杂度 | 会话表、状态同步、优雅清理 | 无会话管理（实现成本下降） |
| 客户端复杂度 | 简单（状态在服务器） | 上升（每请求装配 _meta、句柄建模） |
| 可靠性 | 会话丢失 = 连接报废 | 请求级失败，可无限重试 |
| 双向通信 | 服务器随时可主动发起 | 仅请求处理中（MRTR） |
| 业务状态 | 隐式（会话内全局） | 显式（参数/句柄，模型可推理） |

一句话：**旧版把复杂度埋在协议里，新版把它推给业务层——换来的是部署自由**。

## 7. 迁移检查单

```text
□ 服务器：实现 server/discover（MUST）；保留 initialize 应答（双代）
□ 服务器：列表类结果补 ttlMs/cacheScope；结果补 resultType
□ 服务器：移除对 Mcp-Session-Id 的依赖；会话状态改显式句柄
□ 服务器：资源未找到错误改为 -32602；检查 -3200x 系列错误码引用
□ 客户端：新增 discover 探测 + initialize 回退；每请求装配 _meta
□ 客户端：订阅迁移到 subscriptions/listen；删除 Last-Event-ID 续传逻辑
□ 基础设施：删除负载均衡器的会话亲和配置；删除服务端会话存储
□ 工具层：为可重复工具补幂等（幂等键）；把 elicitation/sampling 改为 MRTR 或直连 LLM API
```

### 7.1 迁移后的运维差异对照

| 运维动作 | 会话式（旧） | 无状态（新） |
|---|---|---|
| 扩容 | 新建实例 + 会话迁移/复制 | 直接加实例（无状态） |
| 发布回滚 | 会话不兼容则全量重建 | 新旧实例并存（双代） |
| 故障演练 | 会话丢失告警 | 请求失败率监控 |
| 容量规划 | 按会话数 × 每会话内存 | 按请求 QPS × 单请求耗时 |
| 缓存管理 | 无协议契约 | ttlMs/cacheScope 协议化 |

> 💡 迁移后最值得做的第一个运维改动：把监控从"会话数/会话错误"改成"方法级错误率（按 Mcp-Method 统计）+ 重试率 + 幂等冲突率"——前者是旧世界指标，后者才是无状态世界的健康信号。

### 7.2 关闭流程与优雅停机

| 场景 | 旧版 | 新版 |
|---|---|---|
| 客户端主动关闭 | 可选发送会话删除请求 | 直接关传输（无会话可清理） |
| 服务器进程退出 | 客户端感知断开 → 会话丢失告警 | 客户端感知断开 → 请求重试 |
| 服务器优雅停机 | 拒绝新请求 → 处理在途 → 清理会话 | 摘出 LB → 在途请求处理完 → 退出 |
| 停机期间新请求 | 会话不可用错误 | 503/连接拒绝 → 客户端重试其他实例 |

优雅停机在无状态下是纯基础设施动作：**先摘流量、再排空在途、最后退出**——三步与普通 HTTP 服务完全一致，这也是"无状态化 = 运维标准化"最直观的体现。

### 7.3 状态机的调试排障

| 现象 | 旧版根因 | 新版根因 |
|---|---|---|
| 连接后请求全失败 | 握手未完成/会话过期 | 版本协商错位/_meta 缺失 |
| 请求时好时坏 | 会话在 LB 间漂移 | 无（无会话漂移）；多为限流/重试冲突 |
| 服务器重启后全断 | 会话表丢失 | 无需重建，请求自动恢复 |
| 长连接莫名断开 | ping 超时判定 | 代理空闲超时/流回收 |

> 💡 面试点：旧版排障第一问是"会话还在吗"，新版排障第一问是"重试幂等吗"——问题域迁移是架构演进的缩影。

### 7.4 会话与无状态的本质问答

| 问题 | 答案 |
|---|---|
| "会话"到底是什么？ | 协议双方共同持有的隐式状态：版本、能力、订阅、业务上下文 |
| 为什么 2026-07-28 要删？ | 隐式状态不可均衡、不可缓存、不可 Serverless，成为规模化的天花板 |
| 删了之后状态去哪？ | 业务态 → 显式句柄参数；协议态 → 每请求 _meta；配置态 → 环境/注册中心 |
| 会不会有功能回退？ | 有：服务器失去"事后主动询问"；MRTR 内联化是补偿方案 |
| 迁移的最大成本是什么？ | 不是代码，是心智——从"连接有状态"到"请求无状态"的思维切换 |

> 💡 面试升华句：MCP 无状态化的本质是把"隐式连接状态"显式化为"请求参数"——这是一次教科书级的协议演进，值得在任何分布式系统面试中当作案例讲。

### 7.5 生命周期相关配置速查

| 配置项 | 旧版 | 新版 |
|---|---|---|
| 连接超时 | 握手超时（如 10s） | 连接建立超时（如 10s） |
| 保活 | ping 间隔（如 30s） | 传输层 keep-alive / 订阅流心跳 |
| 重连退避 | 会话重建退避 | 请求重试退避（1s→2s→4s→上限） |
| 订阅重连 | 事件 ID 续传 | 重新 listen + 重拉 |
| 版本缓存 | 握手时确定，连接内固定 | 客户端缓存协商结果（ttlMs 刷新） |

### 7.6 生命周期迁移的代码级检查

| 检查点 | 旧代码特征（要改） | 新代码特征（目标） |
|---|---|---|
| 连接建立 | `initialize()` 后才有 session | 建连即可用（discover 可选） |
| 每请求 | 依赖 session 对象隐式状态 | _meta 显式携带 |
| 会话清理 | `deleteSession()` | 无此概念 |
| 重连 | 重建 session | 重试请求 |
| 订阅 | subscribe/unsubscribe 方法 | subscriptions/listen + 重订阅 |
| 心跳 | ping 定时器 | 传输层 keep-alive |

> 💡 迁移代码量通常很小（SDK 双代自动处理大部分），真正的工作在测试矩阵：新客户端 × 新旧服务器、旧客户端 × 新旧服务器，四个象限各跑一遍回归。

### 7.7 生命周期速记口诀

```
旧版：连上先握手，会话随身走，断了全重建
新版：请求自包含，连接即通行，断了就重试
```

| 记忆点 | 口诀 |
|---|---|
| 三删 | 握手、会话、ping |
| 三增 | _meta、discover、MRTR |
| 一改 | 订阅断流不续传（重订阅 + 重拉） |
| 一移 | 状态从协议移业务（句柄参数） |

### 7.8 双代生命周期对照速览

| 事件 | 旧客户端×旧服务器 | 新客户端×新服务器 | 混搭 |
|---|---|---|---|
| 建连 | initialize 握手 | 直接发请求（可选 discover） | discover 失败回退握手 |
| 请求 | 会话模式 | 无状态 _meta 模式 | 按协商结果 |
| 保活 | ping | 无 | 无（传输层） |
| 订阅 | GET 流/subscribe | subscriptions/listen | 按服务器能力 |
| 断连 | 会话重建 | 请求重试 | 双路径各自动 |

## 8. 本模块小结

> 🎯 **核心要点**：旧版生命周期是双端状态机（五态 + 握手 + 会话），新版是"请求即生命周期"。ping 没了（传输层替代）、订阅断流不续传（重拉兜底）、会话状态没了（句柄显式建模）。迁移的三个动作：服务器双代应答、客户端双栈回退、基础设施拆会话亲和——做完这三步，2026-07-28 的核心迁移即告完成。运维心智同步切换：从"会话健康"到"重试率 + 幂等冲突率"，监控指标先行换血。生命周期问题域迁移是架构演进最直观的镜子：旧版排障先问"会话还在吗"，新版先问"重试幂等吗"。

---

### 7.9 本模块一句话

旧版生命周期是"连接的两端共同持有的一张状态机"，新版是"每个请求自己带齐身份出门"——会话从协议里消失，但状态从未消失：它去了参数、去了 _meta、去了 Host。记住这句话，就抓住了 2026-07-28 全部生命周期改动的灵魂。
