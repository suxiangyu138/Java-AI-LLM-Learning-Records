## 1. JSON-RPC 2.0 三类消息

MCP 全协议构建在 JSON-RPC 2.0 之上，只使用三类消息：

| 类型 | 结构 | 有响应？ | 使用场景 |
|---|---|---|---|
| 请求（Request） | `{id, method, params}` | ✅ 必须响应 | 客户端→服务器：tools/call 等 |
| 响应（Response） | `{id, result}` 或 `{id, error}` | — | 服务器→客户端：请求的结果 |
| 通知（Notification） | `{method, params}`（无 id） | ❌ 无响应 | 服务器→客户端：progress、listChanged |

```json
// 请求（新版：_meta 必带版本与能力）
{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "city": "北京" },
    "_meta": { "io.modelcontextprotocol/protocolVersion": "2026-07-28",
               "io.modelcontextprotocol/clientCapabilities": {} } } }

// 响应（新版：resultType 必带）
{ "jsonrpc": "2.0", "id": 7,
  "result": { "resultType": "complete",
    "content": [ { "type": "text", "text": "晴，32°C" } ] } }

// 通知（无 id，发后即忘）
{ "jsonrpc": "2.0", "method": "notifications/progress",
  "params": { "progressToken": "tk-1", "progress": 50, "total": 100 } }
```

铁律：

1. **请求必须有响应**（通知除外），响应按 `id` 与请求配对。
2. **通知无响应**，失败只能靠日志/监控兜底。
3. **新版响应必带 `resultType`**；旧服务器缺字段时，客户端按 `"complete"` 处理（向后兼容的显式条款）。

## 2. 原语总览

| 原语 | 回答的问题 | 关键方法 | 适合场景 |
|---|---|---|---|
| Tools | "你能帮我做什么？" | tools/list、tools/call | 操作型能力：写库、发命令、调 API |
| Resources | "你能给我什么数据？" | resources/list、resources/read | 数据型能力：文件、数据库记录、文档 |
| Prompts | "你能按什么模板生成？" | prompts/list、prompts/get | 模板型能力：代码审查、邮件撰写 |

选择铁律：**会改变状态 → Tool；只读取数据 → Resource；复用模板 → Prompt**。工具是"动词"，资源是"名词"，提示是"预制句"。

### 2.1 三原语的使用边界判断

| 问题 | 该用 |
|---|---|
| "帮我下单/发消息/改配置"（有副作用） | Tool |
| "给我这个月的报表/某个文件"（纯读取） | Resource |
| "按模板帮我写周报/审查代码"（生成文本） | Prompt |
| "既要读又要写" | 组合：读用 Resource，写用 Tool |
| "数据会变化" | Resource + subscriptions/listen 订阅 |
| "参数需要自动补全" | Tool/Prompt schema + completions/complete |

> 💡 边界判断失误的代价：把写操作做成 Resource → 客户端无法表达副作用意图；把读操作做成 Tool → 失去 URI 寻址与订阅能力。选型错误通常到"接入第二个客户端"时才暴露——因为各客户端对三原语的呈现方式差异很大。

## 3. 工具（tools）完整消息序列

```text
① 发现：客户端 tools/list
        ← 工具列表 + schema（JSON Schema 2020-12）+ ttlMs/cacheScope
② 缓存：客户端按 ttlMs 缓存目录（避免每次重拉）
③ 调用：客户端 tools/call { name, arguments }
④ 执行：服务器校验参数 → 执行业务 → 返回文本/结构化内容
⑤ 刷新：收到 toolsListChanged 通知 → 重新 list（缓存失效）
```

```json
// tools/list 响应（新版必带缓存元数据）
{ "jsonrpc": "2.0", "id": 2, "result": {
    "resultType": "complete",
    "tools": [
      { "name": "get_weather",
        "description": "查询城市实时天气",
        "inputSchema": { "type": "object",
          "properties": { "city": { "type": "string" } },
          "required": ["city"] } }
    ],
    "ttlMs": 60000, "cacheScope": "public" } }
```

工具结果可以是纯文本、结构化内容（structuredContent，2026-07-28 起接受任意 JSON 值）、图片/资源（嵌入内容）。工具支持进度通知（notifications/progress）与流式结果（部分 SDK）。

## 4. 资源（resources）完整消息序列

```text
① 列举：resources/list → URI 目录（模板：resources/templates/list）
② 读取：resources/read { uri } → 文本/二进制内容 + mimeType
③ 订阅：subscriptions/listen（新版）→ 内容变化推送通知
④ 刷新：收到资源更新通知 → 重读
```

```json
{ "jsonrpc": "2.0", "id": 5, "method": "resources/read",
  "params": { "uri": "file:///reports/Q2-2026.md" } }
```

资源特点：URI 是寻址键（支持模板 `reports/{quarter}.md`）、内容带 mimeType、可订阅变化。2026-07-28 起 `resources/subscribe/unsubscribe` 移除，订阅统一走 `subscriptions/listen`。

## 5. 提示（prompts）完整消息序列

```text
① 列举：prompts/list → 模板目录
② 获取：prompts/get { name, arguments } → 展开后的消息序列
③ 使用：Host 把展开结果注入模型上下文
```

```json
// prompts/get 响应：展开为可直接给模型的消息
{ "jsonrpc": "2.0", "id": 6, "result": {
    "resultType": "complete",
    "description": "代码审查提示词",
    "messages": [
      { "role": "user",
        "content": { "type": "text", "text": "请审查以下代码，关注安全与性能：..." } }
    ] } }
```

Prompts 与 Tool 的区别：Prompt 不执行任何操作，只是"模板展开"；结果直接进模型上下文。

## 6. resultType 与 MRTR 消息流

每个结果必带 `resultType`：

| 值 | 含义 | 客户端动作 |
|---|---|---|
| `complete` | 结果完整 | 正常消费 |
| `input_required` | 服务器需要更多输入 | 收集 inputRequests 答案 → 带 inputResponses 重试 |

MRTR 完整往返（旧版"服务器主动发请求"的替代）：

```text
客户端                                服务器
  │── tools/call { place_order } ──────→│
  │←── input_required + inputRequests ──│  ← 服务器处理中索要输入
  │      + requestState（opaque token）  │
  │── tools/call + inputResponses ─────→│  ← 客户端带答案重试
  │      + requestState                  │
  │←── complete + 订单结果 ────────────│
```

设计要点：

- `requestState` 是**不透明令牌**：服务器用它关联"第一次请求的中间状态"，客户端只负责原样回传。
- 可叠加多轮：input_required 结果可再次含 inputRequests（多步确认流程）。
- inputRequests 类型：`user_input`（问用户）、`llm_completion`（请求模型补全——替代 sampling）。

## 7. 通知体系

| 通知 | 方向 | 触发 | 2026-07-28 状态 |
|---|---|---|---|
| notifications/progress | 服务器→客户端 | 长任务进度（附在发起请求的响应流） | ✅ 保留（请求域内） |
| notifications/toolsListChanged | 服务器→客户端 | 工具目录变化（经 subscriptions/listen 订阅） | ✅ 保留（订阅域内） |
| notifications/promptsListChanged | 服务器→客户端 | 提示目录变化 | ✅ 保留 |
| notifications/resourcesListChanged | 服务器→客户端 | 资源目录变化 | ✅ 保留 |
| notifications/message | 服务器→客户端 | 日志消息（需请求内 logLevel） | ⚠️ 半弃用（配合弃用的 logging） |
| notifications/elicitation/complete | 服务器→客户端 | 旧版追问完成 | ❌ 移除（MRTR 替代） |
| notifications/roots/list_changed | 客户端→服务器 | 根目录变化 | ❌ 移除（roots 弃用） |

订阅域通知必须带 `subscriptionId`（来自 subscriptions/listen 的确认），客户端按订阅 ID 路由处理。

## 8. 扩展框架：原语之外的世界

2026-07-28 新增的正式扩展机制（SEP-2133）：

| 要素 | 规则 |
|---|---|
| ID | reverse-DNS（如 `io.modelcontextprotocol/tasks`） |
| 协商 | 双方 capabilities.extensions 映射中声明，未声明即不支持 |
| 发布 | 独立于核心协议的发布节奏 |
| 状态 | 随扩展自身演进，不进核心版本 |

```json
// 客户端声明支持 Tasks 扩展
"extensions": { "io.modelcontextprotocol/tasks": { "polling": true } }
```

| 官方扩展 | 用途 | 核心方法 |
|---|---|---|
| MCP Apps（SEP-1865） | 服务器定义沙箱 HTML 交互界面，渲染在聊天宿主内 | apps 相关方法 |
| Tasks（io.modelcontextprotocol/tasks） | 持久化异步长任务，任务 ID + 轮询 | tasks/create、tasks/get、tasks/update |

Tasks 扩展注意：重设计版（SEP-2663）与 2025-11-25 实验版**不线缆兼容**——这是双代兼容的唯一例外。

### 8.1 扩展与核心的关系（再讲清楚一层）

| 维度 | 核心原语（tools/resources/prompts） | 扩展（extensions） |
|---|---|---|
| 定义权 | 核心规范 | 各扩展自身规范 |
| 发布节奏 | 随协议版本 | 独立（不阻塞核心版本） |
| 协商 | 能力字段内置 | extensions 映射显式协商 |
| 生命周期 | 与协议同进退 | 独立弃用窗口（如 Tasks 实验版不兼容） |
| 例子 | 三原语、completions、MRTR | MCP Apps、Tasks |

判断一个能力"该进核心还是该做扩展"：**所有 Host 都应该有的 → 核心；部分 Host/Server 才需要的 → 扩展**。Tasks 是后者的典型——异步长任务只有企业级场景需要，做成扩展让本地小工具不必实现。

### 8.2 消息流的性能与体积预算

| 消息 | 典型体积 | 优化手段 |
|---|---|---|
| tools/list | 数十 KB（工具多时上百 KB） | ttlMs 缓存 + 通知失效 |
| tools/call 请求 | 1-10 KB | 参数精简、避免塞大文档 |
| tools/call 结果 | 1 KB - 数十 MB | 截断/摘要；大结果用 Tasks 异步 |
| 订阅流 | 常驻连接，单通知 <1 KB | 按需订阅，只订需要的类型 |

> 💡 体积预算遵循"模型上下文友好"原则：工具结果最终要进模型上下文（几万到几十万 token 的窗口），服务器输出越胖，Agent 的推理空间越小。

### 8.3 JSON Schema 2020-12 参数校验要点

2026-07-28 起工具 schema 支持完整 JSON Schema 2020-12（此前受限子集），实战要点：

| 能力 | 示例 | 用途 |
|---|---|---|
| oneOf/anyOf/allOf | `"oneOf": [{...日期格式...}, {...文本...}]` | 多形态参数 |
| $ref 解析 | 跨定义引用（SDK 需实现引用解析） | 复用复杂结构 |
| 默认值类型修正 | minimum/maximum 为 number（不再强制 integer） | 数值范围校验 |
| 严格模式 | `additionalProperties: false` + 全 required | 防注入与误传 |
| 嵌套校验 | 深层对象逐层校验 | 复杂业务对象 |

> ⚠️ 模型输出的参数不可信：协议校验 + 业务校验双层必须都过。协议层挡格式错误，业务层挡语义错误（如金额为负、库存不足）。

### 8.4 通知消息负载示例

```json
// 进度通知（挂在发起请求的响应流上）
{ "jsonrpc": "2.0", "method": "notifications/progress",
  "params": { "progressToken": "tk-1", "progress": 60, "total": 100 } }

// 目录变化通知（订阅流上，带 subscriptionId）
{ "jsonrpc": "2.0", "method": "notifications/toolsListChanged",
  "params": { "subscriptionId": "sub-9f2a" } }
```

客户端路由规则：**progress 类 → 请求域**（按发起请求 id 关联）；**listChanged 类 → 订阅域**（按 subscriptionId 关联）；两类通知绝不混流。

## 9. 端到端消息流示例

Agent 一次"查天气并提醒带伞"的完整消息流（新协议）：

```text
Host/Agent        Client             Server
   │                │── server/discover ──→│     发现能力（可选）
   │                │←── versions/caps ───│
   │                │── tools/list ──────→│     发现工具（可缓存 60s）
   │                │←── [get_weather] ───│
   │ 模型决定调用 ──→│
   │                │── tools/call ──────→│     执行工具
   │                │←── complete+结果 ───│
   │ 聚合进上下文 ──→│
   │ 模型生成回复 ──→│
```

### 9.1 消息流排障速查

| 现象 | 可能原因 | 排查点 |
|---|---|---|
| 响应迟迟不回 | 服务器处理慢/流式挂起 | 超时分级、进度通知、Tasks 化 |
| 通知收到但没反应 | 订阅域与请求域混淆 | 检查 subscriptionId 路由 |
| MRTR 死循环 | inputRequests 无终止条件 | 服务端限制轮数 |
| 工具结果超大 | 塞进上下文爆 token | 截断/摘要/Tasks |
| 缓存不生效 | ttlMs 缺失或 cacheScope=private 被共享 | 检查缓存字段与消费端 |
| 参数反复被拒 | schema 过严/描述不清 | 严格模式与模型可理解性平衡 |

### 9.2 三原语与 Agent 工作流的映射

| Agent 工作流环节 | 用到的原语/消息 | 说明 |
|---|---|---|
| 计划（规划工具调用） | tools/list（目录注入上下文） | 模型"看见"能力面 |
| 取数 | resources/read（按需注入细节） | 避免全量塞上下文 |
| 执行 | tools/call（副作用操作） | 权限确认 + 审计 |
| 追问/确认 | MRTR input_required（user_input） | 人机协作点 |
| 模板化输出 | prompts/get（标准流程生成） | 一致性保证 |
| 长任务 | Tasks 扩展（tasks/create + poll） | 异步化 |

> 💡 一个成熟的 Agent Host 必然是"三原语 + MRTR + Tasks"的组合用户——只会调工具的是玩具，能按需取数、能确认、能异步的才是产品。这个映射表就是面试"MCP 怎么支撑 Agent"的满分回答骨架。

### 9.3 原语设计规范速查

| 规范 | 内容 |
|---|---|
| 工具命名 | 动词开头（get_/create_/send_），一工具一职责 |
| 工具描述 | 三段式：做什么 + 何时用 + 边界/注意 |
| 参数设计 | 最少必要参数；可选参数独立成工具（降低决策负担） |
| 资源 URI | 稳定语义命名（file:///reports/{quarter}.md 模板化） |
| 提示模板 | 参数化 + 版本化（模板变更影响所有下游） |
| schema | JSON Schema 2020-12 + strict 模式 |

> 💡 设计规范的本质是"降低模型的决策负担"：模型选择工具、填参数、理解结果都是概率行为，规范越清晰，成功率越高——这是 2026 年 Agent 工程的核心共识，也是本模块与 09 篇面试题的连接点。

### 9.4 消息 ID 与请求关联的工程要点

| 要点 | 说明 |
|---|---|
| id 唯一性 | 客户端生成（自增/雪花），服务器按 id 回包 |
| 流式聚合 | SSE 流中多帧同 id → 客户端装配成完整响应 |
| 并发请求 | 同连接多请求并发，靠 id 不靠顺序 |
| 通知无 id | 通知不参与配对，按方法名+上下文路由 |
| MRTR 关联 | 首次请求与重试请求的关联靠 requestState（非 id） |

> 💡 id 是"请求级寻址"，requestState 是"跨请求会话级关联"——两者职责不同，别混淆。这个区分在实现 MRTR 客户端时是第一个坑。

### 9.5 原语安全注意

| 原语 | 安全注意 |
|---|---|
| Tools | 参数 strict 校验；敏感工具二次确认；写操作审计 |
| Resources | URI 白名单（防路径穿越）；内容脱敏；private 缓存不共享 |
| Prompts | 模板内容不拼接不可信输入；参数校验防注入 |
| MRTR | requestState 令牌不落日志；确认类问题明确边界 |

> ⚠️ 原语是攻击面：工具是 RCE 入口、资源是数据泄漏出口、提示是注入载体——三层都要按"模型输出不可信"前提加固。

## 10. 本模块小结

> 🎯 **核心要点**：消息层三件事——三类消息（请求/响应/通知）、三个原语（工具动词/资源名词/提示模板）、两种新结果（complete/input_required）。2026-07-28 的消息流变化集中两点：**列表类结果可缓存（ttlMs/cacheScope）**、**服务器索要输入内联化（MRTR）**。扩展框架是原语之外的第三空间，正式化了"核心协议 + 按需扩展"的演进模型。参数校验（JSON Schema 2020-12 + strict）与通知域路由（请求域 vs 订阅域）是两个最容易出错、面试最爱考的实现细节。完整消息流心智：发现（可缓存）→ 调用（含 MRTR 多轮）→ 通知（域内路由）三步，覆盖全部业务路径。

---

### 9.6 本模块一句话

消息流架构 = 三类消息 × 三个原语 × 两种结果，2026-07-28 在"结果形态"上加了一档（input_required），在"目录消费"上加了一层（缓存元数据）——其余骨架未动。这印证了本体系的主题：**骨架恒、机制变**。
