## 1. 模式一：单 Host 多 Client 多 Server

最基础的生产形态：Host 聚合多个工具服务器，模型一次决策可跨多个服务器取数。

```text
┌─────────────── Host（Agent 服务端）───────────────┐
│  LLM ←→ 编排器（工具选择）                          │
│     ├── Client A ──→ 订单服务 MCP（Streamable HTTP） │
│     ├── Client B ──→ 库存服务 MCP（Streamable HTTP） │
│     └── Client C ──→ 本地工具 MCP（stdio 子进程）     │
└───────────────────────────────────────────────────┘
```

| 设计决策 | 推荐 |
|---|---|
| Client 数量 | 与服务器 1:1，必要时客户端级连接池（同服务器多并发连接） |
| 上下文聚合 | Host 层统一：工具结果按服务器标记来源，聚合进模型上下文 |
| 工具名冲突 | Host 在路由层加前缀命名空间（如 `orders.get`、`stock.get`） |
| 权限 | 按 Client 粒度授权：只读工具 vs 写工具分开服务器/分开 Client |
| 优雅降级 | 单服务器故障不影响其他 Client，Host 告诉模型"库存服务不可用" |

## 2. 模式二：MCP 网关/代理

企业多租户/多团队场景，由网关统一收口：路由、鉴权、限流、计量、缓存、审计。

```text
Agent 客户端 ──→ MCP 网关 ──→ 订单服务 MCP
                    │  ├──→ 财务服务 MCP
                    │  └──→ 文档服务 MCP
              （路由/鉴权/限流/计量）
```

| 网关能力 | 实现载体 | 2026-07-28 增强 |
|---|---|---|
| 按方法路由 | 解析 Mcp-Method 头（不再需要解析 JSON） | ✅ 头路由 |
| 按客户端限流 | Mcp-Name 头 + 租户配额 | ✅ 头路由 |
| 能力聚合 | 多服务器工具目录合并（命名空间化） | 无状态后更简单 |
| 版本透传 | 网关可新旧客户端共存（逐请求协商） | ✅ 双栈 |
| 缓存 | discover/list 结果缓存（ttlMs/cacheScope） | ✅ 缓存字段 |
| 鉴权 | OAuth 2.1 + OIDC（Entra/Okta） | ✅ iss 校验 |
| 审计 | 全量请求/响应留痕 + traceparent 关联 | ✅ 追踪元数据 |

代表实现：AWS AgentCore Gateway、Solo.io Agent Gateway、开源 mcp_gateway（Dart）等。网关本质是"无状态协议代理"，因为 MCP 请求自包含，网关转发无需粘滞。

## 3. 模式三：无状态水平扩展

2026-07-28 最大部署红利：**去掉会话亲和**。

```text
                  ┌── MCP Server 实例 1（无状态）
LB（round-robin） ─┼── MCP Server 实例 2（无状态）
（无 sticky）      └── MCP Server 实例 3（无状态）
      ↑
客户端任意请求 → 任意实例处理（每请求自包含）
```

| 运维项 | 会话式时代 | 无状态时代 |
|---|---|---|
| 负载均衡 | 必须 sticky session | round-robin / 最少连接 |
| 会话存储 | Redis/DB 存会话 | 不需要 |
| 缩容 | 会话迁移 | 直接摘实例 |
| 滚动发布 | 会话兼容 | 蓝绿/滚动无差别 |
| 故障恢复 | 会话重建 | 请求重试（业务幂等） |

## 4. 模式四：Serverless 部署

无状态 + 纯 HTTP = AWS Lambda / Cloudflare Workers 天然适配：

| Serverless 平台 | 适配点 | 注意 |
|---|---|---|
| AWS Lambda | 函数即 MCP 端点，API Gateway 前置 | 冷启动、超时上限、无长流（订阅需自托管网关） |
| Cloudflare Workers | Workers 上直接跑 MCP 端点 | CPU/时长限制，长流受限 |
| 自托管容器 | K8s Deployment + HPA | 最通用，推荐默认 |

限制边界：**subscriptions/listen 长流与 Serverless 冲突**（Lambda 请求超时上限）——长流场景需常驻实例或网关代理订阅。无订阅需求的服务（纯工具调用）在 Serverless 上体验最佳。

### 4.1 Serverless 的限制清单

| 限制 | 影响 | 缓解 |
|---|---|---|
| 请求时长上限 | 长工具调用超时 | 异步化 + Tasks 扩展轮询 |
| 无长连接 | subscriptions/listen 不可用 | 常驻实例/网关代理订阅；纯工具服务器无影响 |
| 冷启动 | 首次调用延迟 | 预热 + 常驻并发；容忍 P99 抖动 |
| 本地文件系统 | 无持久化 | 对象存储替代；状态走显式句柄 |
| 环境变量大小 | 配置限制 | 配置中心注入 |

## 5. 安全边界架构

2026-07-28 授权强化（与生产 OAuth 2.0/OIDC 对齐）：

| 安全项 | 要求 |
|---|---|
| OAuth 授权码 | 标准 OAuth 2.1 流程，授权服务器颁发访问令牌 |
| iss 校验（RFC 9207） | **客户端 MUST 校验 iss 后再换 code**（防授权码注入） |
| 客户端注册 | CIMD（Client ID Metadata Documents）取代 DCR（RFC 7591，弃用但仍兼容） |
| 凭证绑定 | 客户端凭证绑定签发授权服务器：按 issuer 区分，不跨服务器复用 |
| 企业身份 | 直连 Entra/Okta（OIDC），无需 workaround |
| 传输安全 | HTTPS 强制；stdio 本地信任（同机） |
| 输入净化 | 工具参数校验（JSON Schema）+ 输出过滤（防提示注入） |
| 最小权限 | 按服务器/工具粒度授权；写工具单独审批流 |

客户端身份流：Mcp-Name 头 + ClientInfo（_meta）双通道上报，网关按身份做配额与审计——"认证在 OAuth 层、身份在协议层"。

## 6. 可观测性：追踪、日志、指标

| 维度 | 机制 | 说明 |
|---|---|---|
| 追踪 | `_meta.traceparent/tracestate/baggage`（SEP-414） | W3C Trace Context 直接进协议元数据；Host 生成 span，服务器透传到业务调用，全链路一条 traceId |
| 日志 | per-request `io.modelcontextprotocol/logLevel` | 取代 logging/setLevel；服务器按请求粒度决定日志详略；stdio 走 stderr |
| 指标 | 网关/服务器自行采集 | 按 Mcp-Method 统计调用量、延迟、错误率 |
| 订阅监控 | subscriptions/listen 流健康 | 断流告警 + 重订阅计数 |

```text
Agent 请求（traceparent: 4bf92f35…）
 └─ MCP Client → MCP Server（透传 traceparent）
     └─ 业务调用（DB/API，span 挂在同一 traceId 下）
```

无状态下追踪反而更简单：**没有会话维度的 traceId 映射，traceId 随请求自包含**，网关聚合即得全链路。日志建议：工具名 + traceId + 参数摘要（脱敏）+ 耗时 + 结果类型（complete/input_required）。

## 7. 缓存策略：ttlMs 与 cacheScope

| 字段 | 含义 | 使用 |
|---|---|---|
| ttlMs | 缓存有效期（毫秒） | 目录类结果（tools/list）客户端/网关可缓存 |
| cacheScope: public | 可共享缓存 | 网关/CDN 可缓存（无敏感信息） |
| cacheScope: private | 仅消费方可缓存 | 含用户上下文，禁止共享缓存服务 |

```json
{ "ttlMs": 60000, "cacheScope": "public" }   // 可进 CDN/网关共享缓存
{ "ttlMs": 5000,  "cacheScope": "private" }  // 仅当前客户端缓存
```

规则：**private 结果不得从共享缓存服务**（官方明令）；工具目录变化时用 toolsListChanged 通知强制失效。

## 8. 生产部署清单

```text
□ 协议：服务器实现 discover + 双代应答；列表结果带 ttlMs/cacheScope
□ 传输：Streamable HTTP + Mcp-Method/Mcp-Name 头；反代放行长流（订阅）
□ 网关：按方法头路由限流；目录结果缓存；请求审计留痕
□ 均衡：LB 去掉 sticky；实例无状态；健康检查按方法头探测
□ 安全：OAuth 2.1 + iss 校验；HTTPS；工具最小权限；输入输出净化
□ 可观测：traceparent 透传全链路；logLevel 请求粒度；按方法统计三指标
□ 幂等：写工具幂等键；重试策略与退避；MRTR 令牌不落日志
□ 发布：蓝绿/滚动；订阅流断流重订阅验证；旧客户端回归测试
```

### 8.1 监控指标与告警清单

| 指标 | 来源 | 告警阈值建议 |
|---|---|---|
| 方法级调用量（按 Mcp-Method） | 网关/服务器 | 工具调用量突降 = 编排异常 |
| P95/P99 延迟（tools/call） | 服务器 | 延迟翻倍告警 |
| 错误率（按错误码） | 服务器 | -32022/-32020 出现即告警（版本/头配置问题） |
| 重试率 | 客户端 | >5% 提示网络/实例问题 |
| 幂等冲突率 | 服务器 | 突增 = 重试风暴或重复提交 |
| 订阅断流次数 | 网关 | 频繁断流 = 网络或代理问题 |
| input_required 比例 | 服务器 | 突增 = 工具参数设计问题（模型频繁缺信息） |

> 💡 无状态世界最值得盯的三个信号：**重试率**（重试是新的"会话重建"）、**幂等冲突率**（业务层兜底能力）、**input_required 比例**（工具设计健康度）。

### 8.2 容量规划速算

| 参数 | 估算公式/建议 |
|---|---|
| 单实例 QPS | 100-1000（语言/复杂度决定），压测实测为准 |
| 实例数 | 峰值 QPS ÷ 单实例 QPS × 1.5（冗余） |
| 内存 | 单请求处理内存 × 并发数 × 2（GC 余量） |
| 目录缓存 | 工具目录 ≤ 几百 KB，网关缓存 ttlMs 即可 |
| 日志量 | 按方法 × 1KB/条估算，留 30 天 |
| 订阅流 | 每流常驻连接，实例连接数上限要评估 |

> 💡 无状态让容量规划变成普通 HTTP 服务的算术题——这正是它替代会话式的最实际理由之一。

### 8.3 多服务器聚合的上下文管理

Host 聚合多服务器结果时的上下文预算策略：

| 策略 | 做法 |
|---|---|
| 按需注入 | 只把"模型即将调用的工具"注入上下文，不一次性全塞 |
| 结果摘要 | 大结果先摘要再给模型，细节按需二次读取（Resource） |
| 淘汰策略 | 上下文超限时先淘汰历史工具结果（保留系统提示与工具定义） |
| 结果标记 | 标注来源服务器，模型可区分并追问 |
| 权限联动 | 无权限的服务器不注入其工具（模型不知道就不乱调） |

> 💡 上下文管理是 Host 层唯一"有状态"的地方——它天然由 Host 持有，与无状态化不冲突；这也解释了为什么"历史留 Host"是六原则中不可动摇的一条。

### 8.4 生产案例：双代迁移三步走

```text
第 1 步（先稳）：客户端升 v2 SDK（回退路径保底，旧服务器无感）
第 2 步（再进）：服务器升双代（discover + initialize 双应答，新旧客户端共存）
第 3 步（后拆）：移除会话代码 → 拆 sticky → 删会话存储 → 加幂等
```

每步的验证指标：

| 步骤 | 验证 |
|---|---|
| 客户端升级 | 新旧服务器调用全绿；降级日志可见 |
| 服务器双代 | 新旧客户端并发压测通过；discover 响应正常 |
| 拆会话 | 会话相关告警清零；重试率 < 1%；幂等冲突可控 |

> 💡 迁移最大的失败模式是"一步到位"：客户端和服务器同天切换、sticky 同天拆除——任何一个环节出问题都无法回退。三步走 + 每步可回退，是双代政策（12 个月窗口）设计者的本意。

### 8.5 生产架构决策速查

| 决策问题 | 快速答案 |
|---|---|
| 服务器部署形态？ | 内部工具 → K8s Deployment；对外公开 → 网关托管；纯请求型 → 可 Serverless |
| 网关要不要？ | 多团队/多服务器/审计需求 → 要；单一内部服务 → 可省 |
| 缓存开不开？ | 目录类结果必开（ttlMs）；private 场景仅消费端缓存 |
| 追踪接什么？ | OTel（traceparent 已进协议，直接对齐） |
| 幂等怎么做？ | 写工具幂等键（idempotency-key 参数） |
| 多服务器命名冲突？ | Host/网关层命名空间化 |

### 8.6 生产架构自测 8 问

```text
□ 我的 LB 还有 sticky session 配置吗？（应无）
□ 我的服务器有没有会话存储？（应无）
□ 我的写工具幂等键齐了吗？（重试安全的前提）
□ 我的网关按 Mcp-Method 限流了吗？
□ 我的订阅流反代超时调大了吗？缓冲关了吗？
□ 我的日志带 traceId 且参数脱敏了吗？
□ 我的目录缓存尊重 ttlMs/cacheScope 了吗？
□ 我的 OAuth 校验 iss 了吗？（RFC 9207）
```

8 问全过 = 本模块毕业；任一为否，回到对应小节修。

### 8.8 生产指标基线参考

| 指标 | 健康基线 |
|---|---|
| 工具调用 P95 延迟 | < 2s（内部服务）；< 5s（含外部依赖） |
| 目录缓存命中率 | > 90%（ttlMs 生效） |
| 请求重试率 | < 1% |
| 幂等冲突率 | < 0.1%（正常）；突增即告警 |
| 订阅流断流次数 | < 1 次/小时/连接 |
| input_required 占比 | < 20%（过高说明工具参数设计有问题） |

### 8.9 本模块一句话

生产架构 = 四种模式按需组合 + 三件新武器（头路由/追踪/缓存）+ 安全基线（iss/CIMD/最小权限）。无状态化让 MCP 的运维从"专有协议运维"退化为"普通 HTTP 运维"——这是它给企业带来的最大隐性价值：团队不需要新技能栈。

## 9. 本模块小结

> 🎯 **核心要点**：生产架构四模式——多服务器聚合（Host 层）、网关收口（路由/鉴权/计量）、无状态水平扩展（去 sticky）、Serverless（纯请求型）。2026-07-28 的三件新武器：头路由（Mcp-Method 让基础设施看懂协议）、追踪元数据（traceparent 进 _meta）、缓存字段（ttlMs/cacheScope 让目录缓存成为正式能力）。安全上 iss 校验与 CIMD 是本次强化的两个关键词。运维监控换血三指标：方法级错误率、重试率、幂等冲突率——三个信号共同定义无状态世界的健康度。落地节奏建议：先网关后 Serverless、先幂等后重试、先双代后拆会话。
