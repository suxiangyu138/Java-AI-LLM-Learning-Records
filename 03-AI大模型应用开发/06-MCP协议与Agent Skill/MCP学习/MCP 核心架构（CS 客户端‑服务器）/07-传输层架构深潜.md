## 1. 传输层定位与总览

传输层 = 消息的"管道"：它不关心 JSON-RPC 内容，只负责"字节进、字节出"。协议层与传输层严格解耦（SDK 里 Transport 是独立接口），因此同一服务器代码可以换传输运行。

| 传输 | 方向 | 状态 | 适用 |
|---|---|---|---|
| stdio | 本地（子进程） | ✅ 现行 | 开发、本机工具、CLI/IDE 集成 |
| Streamable HTTP | 远程（HTTP 1.1/2） | ✅ 现行（推荐） | 生产远程服务器、Serverless、网关 |
| HTTP+SSE | 远程（GET 流 + POST） | ⚠️ 弃用（2027-07-28 前可继续用） | 存量部署，尽快迁移 |

## 2. stdio：本地进程传输

Host/Client 以子进程方式拉起服务器，消息走标准输入/输出：

```text
┌──────────────┐   stdin（请求）   ┌──────────────┐
│  Host/Client  │ ────────────────→ │ MCP Server   │
│   （父进程）   │ ←──────────────── │   （子进程）   │
└──────────────┘  stdout（响应）    └──────────────┘
```

| 属性 | 说明 |
|---|---|
| 帧格式 | 每行一条 JSON（换行分隔），UTF-8 编码 |
| 日志 | **不能污染 stdout**（输出走 stderr 或文件）——最常见事故源 |
| 启动 | 客户端负责 spawn 子进程、注入环境变量（如 MCP 配置） |
| 生命周期 | 客户端杀进程 = 服务器死亡，无需优雅协议 |
| 双向 | 请求/响应/通知全走同一管道（通知不阻塞，靠 id 区分） |
| 调试 | `mcp dev` / Inspector 可本地调试 stdio 服务器 |
| 2026-07-28 角色 | 无状态请求在 stdio 同样适用；discover 是 stdio 上的官方兼容探测方式 |

stdio 的两条铁律：

1. **stdout 只属于协议**：任何 `print()` 调试输出都会破坏 JSON 帧（客户端解析失败）。
2. **一次性生命**：进程退出 = 连接结束，无重连概念（重连 = 重启进程）。

## 3. Streamable HTTP：无状态远程传输

2025-06-18 引入、2026-07-28 成为唯一推荐的远程传输。核心模型：

```text
POST /mcp
  Headers: Content-Type: application/json
           Mcp-Method: tools/call          ← 协议方法路由头（2026-07-28 必带）
           Mcp-Name: my-agent              ← 客户端身份路由头
  Body: JSON-RPC 请求（含 _meta 版本与能力）
```

| 属性 | 说明 |
|---|---|
| 请求方式 | POST 单条 JSON-RPC；结果可走流式（SSE 响应）或单次 JSON |
| 会话 | **无会话头**（Mcp-Session-Id 移除），请求自包含 |
| 服务器状态 | 无状态：任意实例可处理任意请求，LB 可 round-robin |
| 长流 | POST 响应可保持打开：progress/通知（请求域内）；subscriptions/listen 专用长流 |
| 认证 | OAuth 2.1 授权码（iss 校验 RFC 9207）或自定义 Authorization 头 |
| 可缓存 | 列表类结果带 ttlMs，网关/CDN 可缓存（注意 cacheScope: private 不可共享缓存） |
| 部署 | 普通 HTTP 服务：Nginx 反代、K8s Service、Lambda/Workers 均可 |

### 3.1 两种响应形态

```text
① 单次响应：处理快 → 直接返回 application/json（一条 JSON-RPC 响应）
② 流式响应：处理慢/带通知 → 返回 text/event-stream，逐步发 JSON-RPC 消息
```

客户端行为："先发 POST，若响应头是 SSE 则按流解析，否则按单条 JSON 解析"。

### 2.1 stdio 调试与生产要点

| 要点 | 说明 |
|---|---|
| 调试工具 | `mcp dev`（本地跑 server 并自动连 Inspector）、MCP Inspector 网页端 |
| 日志通道 | stderr（CLI 可见）；文件（持久化）；OTel（结构化） |
| 环境隔离 | 服务器环境变量由客户端注入（如 API key），避免写死在代码里 |
| 启动失败 | 客户端应捕获启动错误（非 JSON 输出/退出码）并给出可读报错 |
| Windows 注意 | spawn 用 `python -m` 而非裸 `python`；路径用绝对路径；中文路径编码 |

> 💡 stdio 调试的黄金工具组合：Inspector（协议层）+ stderr 日志（业务层）+ `--inspect`/断点（代码层）——三层配合，stdio 服务器的问题没有查不出来的。

## 4. 消息帧格式

| 传输 | 帧格式 | 说明 |
|---|---|---|
| stdio | newline-delimited JSON（NDJSON） | 一行一条，无分隔符歧义 |
| HTTP 单次 | `application/json` body | 一条 JSON-RPC |
| HTTP 流式 | SSE（`data:` 行） | 每条 `data:` 一帧 JSON-RPC，可含 progress/通知 |

SSE 流与 JSON-RPC 的映射：流里的每条 `data:` 可以是——请求的最终响应（按 id 匹配）、请求域通知（progress）、订阅通知（带 subscriptionId）。客户端必须有"按 id 聚合流式响应"的装配器。

## 5. Mcp-Method/Mcp-Name 路由头

2026-07-28 新增（SEP-2243），把"协议信息"上提到 HTTP 头，让基础设施无需解析 JSON 即可路由：

| 头 | 取值 | 用途 |
|---|---|---|
| `Mcp-Method` | `tools/list`、`tools/call` 等 | 网关/LB/限流器按方法名路由与计量（如只放行 tools/call、对 discover 限流） |
| `Mcp-Name` | 客户端/服务器名 | 按客户端身份做配额、灰度、审计 |
| `x-mcp-header` | 自定义扩展头 | 传递自定义元数据（透传） |

校验规则：`Mcp-Method` 与 body 中 method 不一致 → `-32020 HeaderMismatchError`（WAF 可直接 400 拦截）。

```nginx
# 网关按方法头限流的示例语义
location /mcp {
    if ($http_mcp_method = "tools/call") { limit_req zone=call burst=20; }
    if ($http_mcp_method = "server/discover") { limit_req zone=discover burst=5; }
}
```

## 6. subscriptions/listen 长流

订阅长流是 2026-07-28 传输层的新形态：**单条 POST 响应保持打开**，服务器往里推通知。

```text
① 客户端 POST subscriptions/listen（订阅工具/提示/资源目录）
② 服务器返回 SSE 长流（text/event-stream，保持连接）
③ 服务器在流中推送 notifications/toolsListChanged 等（带 subscriptionId）
④ 断流 → 客户端重新 listen（新请求 ID），目录变化靠重拉兜底
```

| 特性 | 说明 |
|---|---|
| 与旧 GET 流区别 | 旧版用独立 GET 端点开流；新版统一为 POST 长流 |
| 通知归属 | 订阅通知只属于"订阅流"；progress/message 只属于"发起请求的流" |
| 恢复 | 无续传；断流重订阅 + ttlMs 缓存兜底 |
| 网关 | 长流适配（反代超时需调大，或升级 SSE 代理） |

## 7. HTTP+SSE：弃用的旧远程传输

| 属性 | 说明 |
|---|---|
| 形态 | `GET /mcp/sse`（服务器→客户端事件流）+ `POST /mcp`（客户端→服务器消息） |
| 状态 | 2025-03-26 引入，2026-07-28 正式标记弃用，12 个月窗口后移除 |
| 弃用原因 | 双端点复杂、SSE 可恢复性开销大、与无状态模型冲突 |
| 迁移目标 | Streamable HTTP（单 POST 端点 + 可选长流） |
| 兼容 | 弃用期间仍可用；新服务器不应再实现 |

迁移提示：客户端先发 POST 探测新端点，失败回退旧 SSE 端点——与版本回退同构。

## 8. 并发模型与限流

| 维度 | stdio | Streamable HTTP |
|---|---|---|
| 并发 | 单子进程，进程内并发（SDK 内部调度） | HTTP 天然并发（连接池/多实例） |
| 吞吐瓶颈 | 进程内 CPU/IO | 实例数 × 单实例吞吐 |
| 扩展 | 无（1 客户端 1 进程） | 水平扩展（无状态 = 随意加实例） |
| 限流点 | 客户端节奏控制 | 网关（Mcp-Method 头）+ 服务器（请求级） |
| 超时 | 客户端控制（子进程挂起检测） | HTTP 超时 + 网关超时链 |

2026-07-28 的运维建议：远程服务器背后接标准 LB + 网关，按 `Mcp-Method` 分流（discover/list 可缓存少放行、call 限量流）、按 `Mcp-Name` 做租户配额。

## 9. 传输选型决策树

```text
服务器部署在哪？
├─ 本机/开发/CLI 集成 → stdio（进程模型最简单）
└─ 远程/生产/多租户
    ├─ 标准 HTTP 服务栈可用 → Streamable HTTP ✅（唯一推荐）
    └─ 存量旧部署 → HTTP+SSE（过渡，尽快迁移）
```

### 9.1 传输层错误映射与排障速查

| 现象 | 可能原因 | 排查方向 |
|---|---|---|
| 405 Method Not Allowed | 用了旧 GET 端点 / 方法头不匹配 | 确认 POST 端点与 Mcp-Method |
| 400 + -32020 | Mcp-Method 与 body 方法不一致 | 头/体一致性（网关层） |
| 404 | 路径错误 / 未知方法（传输层剥离后 HTTP 语义） | 端点路径 + 方法名 |
| 503 | 实例摘除/部署中 | LB 健康检查 |
| 429 | 限流（Mcp-Name 配额） | 网关限流配置 |
| 订阅流静默断开 | 代理超时/空闲回收 | 调大反代超时 / 服务器发心跳帧 |
| stdio 解析错乱 | stdout 被日志污染 | 检查所有 print 是否走 stderr |

### 9.2 传输选型与网关的配合

| 传输 | 网关适配点 |
|---|---|
| stdio | 不适合网关（进程级），由 Host 直接管理 |
| Streamable HTTP | 头路由（Mcp-Method/Mcp-Name）、长流适配、缓存（ttlMs） |
| HTTP+SSE（弃用） | 网关需要维护双端点映射，尽快迁移 |

### 9.3 传输层安全配置

| 传输 | 安全项 | 配置要点 |
|---|---|---|
| stdio | 本机信任 | 仅限可信用户启动；敏感凭据经环境变量注入 |
| HTTP | HTTPS 强制 | TLS 1.2+；证书由受信 CA 签发 |
| HTTP | 认证 | OAuth 2.1（远程服务器）或共享密钥（内部） |
| HTTP | 限流 | 按 Mcp-Name/IP 配额，防止工具滥用 |
| HTTP | CORS | 浏览器端 Host 需正确 CORS 白名单（同源代理更简单） |
| HTTP | 日志脱敏 | 参数、令牌、请求头均需脱敏后记录 |

> ⚠️ 2026-07-28 安全基线：客户端 MUST 校验 OAuth 授权响应的 `iss`（RFC 9207）后再换 code；客户端凭证按授权服务器（issuer）隔离，禁止跨服务器复用。

### 9.4 传输层演进对照（2025 → 2026）

| 维度 | 2025-06-18（Streamable HTTP 诞生） | 2026-07-28（无状态化） |
|---|---|---|
| 会话头 | Mcp-Session-Id 必要 | 移除 |
| 初始化 | 必须先 initialize | 无（可选 discover） |
| 路由头 | 无 | Mcp-Method / Mcp-Name 必带 |
| 长流 | GET 端点 + subscribe | subscriptions/listen POST 长流 |
| 续传 | SSE Last-Event-ID | 移除 |
| 缓存 | 无 | ttlMs / cacheScope |
| 追踪 | 私有 | W3C traceparent 进 _meta |

> 💡 一句话：2025 年传输层"长得像 HTTP 的会话协议"，2026 年变成"彻底的 HTTP 服务"——每一行变化都能对应上一条运维痛点。

### 9.5 传输层常见问题三问

| 问题 | 答案 |
|---|---|
| stdio 服务器能接 HTTP 客户端吗？ | 不能直接；需要包装层（stdio→HTTP 桥），或用双传输服务器 |
| 一个 HTTP 服务器能同时服务 stdio 和 HTTP 客户端吗？ | 能：同一协议层，两套 transport 适配（SDK 支持多传输） |
| 无状态后还要长连接吗？ | 只有订阅流需要；纯请求型服务器可完全无连接管理 |

> 💡 传输层设计的终点形态：**协议层一套代码 + transport 可插拔**——stdio（本地）、Streamable HTTP（远程）、自定义（企业内网）自由切换，业务代码零改动。这是 SDK 与自研服务器都应该遵循的结构。判断一个传输实现是否合格的三问：能否承载请求/响应/通知三类消息？能否区分请求域与订阅域的通知？断流后客户端能否自愈（重试/重订阅/重拉）？三问全过才算生产可用。对自研传输的最后提醒：宁可少做特性，不可破坏"请求自包含 + 帧格式严格"两条底线，否则协议层一切假设都会失效。

### 9.6 传输层配置模板（Nginx 反代示例）

```nginx
# Streamable HTTP MCP 服务器反代要点
location /mcp {
    proxy_pass http://mcp-backend;
    proxy_http_version 1.1;
    # 长流（subscriptions/listen）必须放行
    proxy_read_timeout 3600s;
    proxy_buffering off;              # SSE 流需关闭缓冲
    proxy_set_header Mcp-Method $http_mcp_method;   # 透传路由头
    proxy_set_header Mcp-Name $http_mcp_name;
    # 限流按方法头
    if ($http_mcp_method = "tools/call") { limit_req zone=call burst=20 nodelay; }
}
```

> ⚠️ 反代三个必配项：长流超时、关闭缓冲（否则 SSE 不即时）、透传自定义头。漏掉任意一个，订阅流或 MRTR 流式响应就会出现"客户端等不到数据"的疑难故障。

### 9.7 传输层记忆卡片

| 卡片 | 内容 |
|---|---|
| stdio | NDJSON 一行一帧；stdout 神圣；stderr 日志；进程即连接 |
| Streamable HTTP | POST 单端点；Mcp-Method/Name 头；单次 JSON 或 SSE 流；无会话 |
| subscriptions/listen | POST 长流；subscriptionId；断流重订阅 |
| 弃用 | HTTP+SSE（2027-07-28 前迁移）；SSE 续传已删 |
| 部署三必配 | 长流超时 / 关闭缓冲 / 透传头 |

### 9.8 传输层与协议层职责边界

| 职责 | 传输层 | 协议层 |
|---|---|---|
| 字节编解码 | ✅ 帧格式/流解析 | — |
| 请求头 | ✅ Mcp-Method/Name（路由用） | — |
| 方法语义 | — | ✅ list/call/read |
| 能力协商 | — | ✅ discover/_meta |
| 错误处理 | ✅ HTTP 状态码 | ✅ JSON-RPC 错误码 |
| 超时重试 | ✅ 连接级 | ✅ 请求级 |
| 会话 | ❌ 无（2026） | ❌ 无（2026） |

> 💡 边界清晰的好处：传输层换实现（stdio→HTTP）时协议层零改动；协议层升级版本时传输层零改动——这是 SDK 架构与自研服务器都应该遵守的纪律。

## 10. 本模块小结

> 🎯 **核心要点**：传输层就记三组数字——stdio 是"一行一帧、stdout 神圣不可污染"；Streamable HTTP 是"单 POST 端点 + Mcp-Method 路由头 + 可选 SSE 长流"，无状态化让它能进 LB 与 Serverless；HTTP+SSE 已弃用（12 个月）。传输与协议解耦是 SDK 的通用设计，同一服务器代码换传输只改一行配置。生产部署必查三项：反代长流超时、关闭缓冲、透传自定义头——漏一项，订阅流和流式响应就会"莫名超时"。传输层与协议层边界清晰（帧/头归传输，方法/协商归协议），是双代共存与多传输插拔的结构前提。

### 9.8 传输层速查补遗

| 问题 | 答案 |
|---|---|
| 一个 POST 能并发几个请求？ | 协议允许并发；实现上按 id 配对，响应可乱序 |
| 流式响应的终止怎么判断？ | 流结束（EOF）/ 收到最终响应帧 |
| 通知能跨流吗？ | 不能：progress/message 只在发起请求的流上；订阅通知只在订阅流上 |
| 网关要解析 body 吗？ | 路由/限流不需要（Mcp-Method 头）；审计需要 |
| HTTP/2 有特殊要求吗？ | 无；HTTP/1.1 即可，长流建议 HTTP/2（多路复用） |
| 断流后客户端怎么办？ | 请求重试（幂等兜底）、订阅重新 listen、目录重新拉取 |
| 帧大小有限制吗？ | 传输层无硬限制；应用层建议 1-10MB 上限防滥用 |

### 9.9 本模块一句话

传输层选型 = 部署形态 × 长流需求 × 基础设施能力：本机选 stdio、远程选 Streamable HTTP、旧系统过渡期保留 HTTP+SSE（12 个月内迁走）。传输层的每次演进都向"标准 HTTP 服务"靠近一步——这是 MCP 吃下企业规模的根本路径。
