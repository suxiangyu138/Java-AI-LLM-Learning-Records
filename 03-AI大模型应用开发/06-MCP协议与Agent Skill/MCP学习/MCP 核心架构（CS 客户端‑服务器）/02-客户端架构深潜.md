## 1. 客户端内部组件分层

一个生产级 Client 内部应分为四层（与 SDK 实际结构一致）：

```text
┌─────────────────────────────────────────────┐
│ ① 原语 API 层   tools.list / tools.call / …  │  ← 业务/Agent 调用入口
├─────────────────────────────────────────────┤
│ ② 协议层       请求装配、能力管理、消息路由    │  ← 本模块重点
├─────────────────────────────────────────────┤
│ ③ 传输层       stdio / Streamable HTTP       │
├─────────────────────────────────────────────┤
│ ④ 连接层       进程启动、HTTP 客户端、重连     │
└─────────────────────────────────────────────┘
```

| 层 | 职责 | 失败时的表现 |
|---|---|---|
| 原语 API | 把协议方法封装成业务友好的调用（如 `listTools()` 返回对象而非原始 JSON） | 业务层抛异常 |
| 协议层 | 方法名、参数校验、id 配对、_meta 装配、版本协商 | 返回协议错误码 |
| 传输层 | 消息编解码、流式响应（SSE/流式 POST）、请求头 | 传输错误（HTTP 状态码） |
| 连接层 | 拉起子进程/建立 HTTP 连接、健康检查 | 连接不可用 |

> 💡 四层分离的意义：2026-07-28 版本迁移时，改动集中在"协议层"（_meta 装配、discover 探测），原语 API 层对上层几乎透明——这正是 SDK 双栈设计的底气。

## 2. 请求装配：_meta 三键

2026-07-28 无状态核心要求**每个请求**在 `_meta` 中携带协议元数据：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "extensions": {
          "io.modelcontextprotocol/tasks": { "polling": true }
        }
      },
      "io.modelcontextprotocol/clientInfo": {
        "name": "my-agent",
        "version": "1.4.0"
      },
      "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
    }
  }
}
```

| _meta 键 | 必填 | 含义 |
|---|---|---|
| `io.modelcontextprotocol/protocolVersion` | ✅ 客户端 | 本次请求使用的协议版本 |
| `io.modelcontextprotocol/clientCapabilities` | ✅ 客户端 | 客户端支持的能力（含 extensions 映射） |
| `io.modelcontextprotocol/clientInfo` | 建议 | 客户端身份（name/version），便于服务器端排障 |
| `io.modelcontextprotocol/serverInfo` | 服务器回 | 服务器身份，放在**结果**的 `_meta` 中 |
| `traceparent` / `tracestate` / `baggage` | 可选 | W3C 追踪上下文，透传到服务器日志 |
| `io.modelcontextprotocol/logLevel` | 可选 | 本次请求的日志级别（替代 logging/setLevel） |

装配规则：

1. **客户端 SHOULD 但未要求**：规范要求 `clientInfo` 尽量携带（SHOULD），服务器对应返回 `serverInfo`。
2. **版本是"按请求协商"的值**：不是全局常量，客户端用协商出的最高共同版本装配每个请求。
3. **透传即溯源**：traceparent 由 Host 生成，贯穿 Client→Server→内部调用，网关可据此把一次 Agent 交互的所有 MCP 调用串成一条追踪链。

## 3. 能力声明与协商

客户端能力在旧版（initialize 握手）与新版（_meta）中声明结构一致，只是载体不同：

```json
{
  "roots": { "listChanged": true },
  "sampling": {},
  "elicitation": {},
  "extensions": {
    "io.modelcontextprotocol/tasks": { "polling": true }
  }
}
```

| 能力键 | 含义 | 2026-07-28 状态 |
|---|---|---|
| roots | 客户端可提供根目录列表给服务器 | ⚠️ 弃用（建议改资源 URI/工具参数） |
| sampling | 客户端可为服务器调用 LLM 补全 | ⚠️ 弃用（建议直接调 LLM API） |
| elicitation | 客户端可回应用户提问 | ⚠️ 弃用（被 MRTR 取代） |
| extensions | 扩展能力映射（reverse-DNS ID → 参数） | ✅ 新增 |

协商三步（新版）：

```text
① 客户端（可选）调用 server/discover → 拿到服务器版本集合、能力、身份
② 客户端从服务器支持集合 ∩ 自身集合中取最高版本，作为本次请求的协议版本
③ 之后每个请求在 _meta 中声明 clientCapabilities，服务器按声明决定行为
```

> ⚠️ "双方必须尊重已声明的能力"：客户端声明了 `extensions.tasks`，服务器才会返回任务相关方法；客户端没声明，服务器不得假设其存在。

## 4. 1:1 连接生命周期

Client 对 Server 的连接管理（无状态版）：

| 阶段 | 客户端动作 | 失败处理 |
|---|---|---|
| 探测 | 调 `server/discover`（可跳过） | 视为旧服务器，转握手路径 |
| 协商 | 确定协议版本（最高共同版本） | 版本不匹配 → -32022 |
| 运行 | 逐请求发送（每个请求自包含） | HTTP 层错误按状态码处理 |
| 订阅 | `subscriptions/listen` 打开长流 | 断流需重发请求 + 新请求 ID |
| 关闭 | 关闭传输连接 | 幂等：无会话可清理 |

旧版（2025-11-25）对应：initialize → 收 InitializeResult（含 sessionId）→ notifications/initialized → 运行（所有请求带会话）→ 关闭时可选删除会话。新版把"运行期"的会话状态全部删掉了，Client 端唯一残留的状态是"协商出的协议版本"。

### 4.1 连接管理的工程细节

| 场景 | stdio | Streamable HTTP |
|---|---|---|
| 连接建立 | spawn 子进程（注入环境变量/工作目录） | HTTP 客户端连接池（复用 TCP） |
| 进程/连接守护 | 子进程退出检测 + 自动重启（指数退避） | 连接池健康检查（失败摘除） |
| 环境注入 | MCP 相关配置经环境变量传给服务器 | 请求头（Mcp-Name）+ Authorization 头 |
| 并发上限 | 单进程串行/低并发 | 连接池大小 + 每连接请求队列 |
| 优雅关闭 | 发退出信号 → 等待回收 → 杀进程 | 关闭连接池 → 等待在途请求 |
| 故障转移 | 重启进程（状态丢失，句柄重建） | LB 摘实例 + 重试（业务幂等） |

工程铁律三条：

1. **stdout 污染检测**：客户端必须对服务器 stdout 做解析容错（非 JSON 行打日志告警，不直接崩溃）——这是生产中最常见的"莫名其妙"故障源。
2. **超时分级**：发现类方法（list/discover）短超时（5-10s），调用类方法（call）长超时（30-120s），订阅流永不超时（靠断流检测）。
3. **版本缓存**：协商出的版本与能力在客户端内存缓存，避免每请求重复 discover（ttlMs 控制刷新）。

## 5. 双栈回退逻辑

新 Client 必须能对旧服务器说话，回退是规范认可的正式路径：

```python
# 双栈客户端核心逻辑（伪代码）
async def connect(transport):
    try:
        info = await call("server/discover")          # ① 新协议探测
        version = negotiate(info.protocolVersions)     # ② 选最高共同版本
        mode = "stateless"
    except MethodNotFoundError:                        # ③ 旧服务器不认识
        init = await call("initialize", ...)           # ④ 回退握手
        version = init.protocolVersion
        mode = "session"
    return ClientSession(transport, version, mode)
```

| 组合 | 客户端行为 | 服务器行为 |
|---|---|---|
| 新客户端 + 新服务器 | server/discover → 无状态请求 | 响应 discover + 无状态处理 |
| 新客户端 + 旧服务器 | discover 失败 → initialize 握手 → 会话模式 | 旧服务器无感知 |
| 旧客户端 + 新服务器 | 直接 initialize 握手 | 服务器按请求版本应答（双代服务） |

## 6. 原语 API 封装

协议方法 → 业务 API 的映射（客户端视角）：

| 协议方法 | 业务 API | 返回（新版必带 resultType） |
|---|---|---|
| tools/list | `listTools()` | 工具列表 + ttlMs/cacheScope |
| tools/call | `callTool(name, args)` | 文本/结构化内容 + resultType |
| resources/list + resources/read | `readResource(uri)` | 资源内容 |
| prompts/get | `getPrompt(name, args)` | 消息模板展开结果 |
| completions/complete | `completeCompletion(...)` | 参数补全候选 |
| server/discover | `discover()` | 版本集合 + 能力 |

工具调用是唯一"双向"路径（旧版）：工具执行中服务器可发起 progress 通知。新版下 progress 通知仍允许，但必须附着在"发起请求的响应流"上——请求结束流即结束。

## 7. 订阅与通知处理

新版订阅机制（取代旧 GET 流与 resources/subscribe）：

```text
① 客户端 subscriptions/listen { subscriptions: [{type: "toolsListChanged"}] }
② 服务器确认（notifications/subscriptions/acknowledged）
③ 服务器推送 notifications/toolsListChanged（带 subscriptionId）
④ 客户端收到后刷新缓存（工具列表可能已变化）
```

| 订阅类型 | 触发时机 | 客户端响应 |
|---|---|---|
| toolsListChanged | 服务器工具集变化 | 重拉 tools/list |
| promptsListChanged | 提示模板变化 | 重拉 prompts/list |
| resourcesListChanged | 资源列表变化 | 重拉 resources/list |
| resourceSubscriptions | 已订阅资源内容变化 | 重读 resources/read |

### 6.1 客户端工具发现与路由

客户端承载"模型 → 工具"的路由职责，这是它除了协议之外最重的业务面：

```text
① 聚合：多 Client 各拉一次 tools/list → Host 汇总成统一工具目录
② 命名：跨服务器冲突 → 加前缀命名空间（orders.get / stock.get）
③ 呈现：把目录注入模型上下文（schema 描述 → 模型可理解）
④ 路由：模型请求 tools/call "orders.get" → Host 找到对应 Client → 转发
⑤ 回传：结果按工具来源标记后聚合进模型上下文
```

| 路由细节 | 处理 |
|---|---|
| 工具名冲突 | Host 层命名空间化（协议层不做，因为 Client 是 1:1 无冲突） |
| 目录刷新 | ttlMs 缓存 + toolsListChanged 通知即时失效 |
| 权限过滤 | 按用户角色过滤工具（未授权的工具不注入上下文） |
| 结果大小 | 大结果截断/摘要（模型上下文预算） |

这个"目录聚合 + 命名空间 + 权限过滤"模式，正是 MCP 网关产品（AgentCore Gateway 等）在 Host 层的复制品——理解 Client 的路由职责，就理解了网关的全部价值。

### 7.1 订阅健康与重连策略

订阅长流是客户端唯一"常驻连接"，健康管理有三板斧：

| 手段 | 做法 | 兜底 |
|---|---|---|
| 断流检测 | 流空闲超时（如 60s 无数据）→ 判定断流 | 心跳数据可由服务器周期性发送 |
| 自动重订阅 | 断流后指数退避重新 listen | 重订阅失败 → 降级为周期重拉 |
| 目录对账 | 每次重连后拉一次 list 与本地缓存比对 | 防"断流期间错过的变更" |

优先级排序：**订阅通知（即时）> ttlMs 过期（兜底）> 周期重拉（最后手段）**。三者配合，目录变化的最长感知延迟 ≈ max(ttlMs, 重拉周期)。

## 8. 错误、超时与重试

| 场景 | 处理 |
|---|---|
| 方法不存在 | JSON-RPC MethodNotFound（-32601），旧服务器表现为 discover 失败 → 回退 |
| 版本不支持 | -32022 UnsupportedProtocolVersionError |
| 头不匹配 | -32020 HeaderMismatchError（网关层先拦） |
| 资源未找到 | -32602 Invalid Params（2026-07-28 起） |
| 传输断流 | 重发请求（新请求 ID），订阅需重新 listen |
| 超时 | 客户端自行控制：工具调用通常 30-120s，发现类 5-10s |

> 💡 客户端 = 装配器（_meta 三键每请求自包含）+ 协商器（discover/握手双栈回退）+ 路由器（请求/响应/通知三类消息）+ 订阅器（subscriptions/listen）。它不拥有业务状态，但拥有"协议元状态"：版本选择、能力声明、订阅集合。记住"请求自包含"四个字，客户端架构就通了一半。四个角色的职责边界正是 SDK Client 源码分层（transport/protocol/session/API）的依据。

## 9. SDK 客户端源码结构

| SDK | 客户端类 | 结构要点 |
|---|---|---|
| Python mcp v2 | `Client(target)` | 构造即自动协商版本（双代）；`MCPServer` 改名后的配套；`Resolve(fn)` 参数兼容两代工具体 |
| Python mcp v1.28 | `ClientSession(transport)` | 先 `initialize()` 再使用，会话对象持有协议状态 |
| TypeScript v2 | `@modelcontextprotocol/client` 包 | ESM-only、Node 20+；`Client` 类 + 独立 transport 对象 |
| TypeScript v1.29 | `@modelcontextprotocol/sdk` | `Client` + `StdioClientTransport`/`StreamableHTTPClientTransport` |
| Java SDK 1.1.0 | `McpClient` / `McpClient.async` | 同步 + 异步双 API，`McpClientSession` |

```python
# Python mcp v2：一行构造，版本自动协商（无状态 + 旧版双栈）
from mcp import Client, StdioServerParameters

async with Client(StdioServerParameters(command="python", args=["server.py"])) as client:
    tools = await client.list_tools()      # 自动完成 discover/握手与版本选择
    result = await client.call_tool("sum", {"a": 1, "b": 2})
    print(result.content)                  # 文本/结构化内容
```

### 9.1 客户端测试要点

| 测试类型 | 测什么 | 方法 |
|---|---|---|
| 协议合规 | _meta 装配正确、id 配对、resultType 处理 | 用 MCP Inspector / 录制回放 |
| 双栈回退 | 对旧服务器自动降级 initialize | 起一个 v1 SDK 写的模拟服务器 |
| 断流恢复 | 订阅流中断后重订阅、请求重试 | 掐断连接 → 断言重连行为 |
| 超时 | 慢服务器不挂死客户端 | 注入延迟，验证超时分级 |
| 并发 | 多 Client 并行不串扰 | 并发调用 + 断言目录隔离 |

### 9.2 客户端常见踩坑清单

| 坑 | 后果 | 解法 |
|---|---|---|
| stdout 日志污染 | JSON 解析错乱、请求错位 | 日志走 stderr；客户端对非 JSON 行告警 |
| 忘记装配 _meta | 服务器按旧逻辑处理、能力不生效 | SDK 自动装配，手写协议才需自查 |
| discover 失败直接报错 | 旧服务器全部连不上 | 回退 initialize（规范认可的路径） |
| 订阅断流后干等 | 目录变化永远不知道 | 断流即重订阅 + 周期重拉兜底 |
| 用会话思维写重试 | 重试后状态错乱 | 业务幂等 + 句柄参数化 |
| 缓存无视 ttlMs | 工具目录过期、调用 404 | 按 ttlMs 过期 + 通知失效 |
| 超时一刀切 | 慢工具误杀 / 快方法挂起 | 方法级超时分级（list 短、call 长） |

### 9.3 客户端对旧服务器的能力降级矩阵

| 服务器能力 | 旧版（客户端能力声明） | 新版（客户端如何处理） |
|---|---|---|
| 服务器发起 sampling | 客户端实现 `sampling/createMessage` 响应 | 不再支持 → 工具层改为直连 LLM API |
| 服务器发起 elicitation | 客户端实现追问流程 | MRTR 的 inputRequests（user_input） |
| roots | 客户端声明 roots + listChanged | 弃用 → 资源 URI / 工具参数 |
| logging | 客户端响应 setLevel | 请求内 logLevel + stderr/OTel |
| 资源订阅 | resources/subscribe | subscriptions/listen |

这张矩阵是"新客户端连旧服务器"时功能降级的完整地图：协议不崩，但能力面缩水——降级决策应显式记录在客户端日志中（如 `[mcp] fallback: session-mode, sampling disabled`）。

## 10. 本模块小结

> 🎯 **核心要点**：客户端四层结构（原语 API/协议/传输/连接）中，协议层是 2026-07-28 迁移的主战场：_meta 三键装配、server/discover 探测、双栈回退、subscriptions/listen——原语 API 层保持稳定，这是 SDK 能"一行升级"的原因。客户端不存业务状态，只存"协议元状态"（版本、能力、订阅），其余全部自包含进请求。
