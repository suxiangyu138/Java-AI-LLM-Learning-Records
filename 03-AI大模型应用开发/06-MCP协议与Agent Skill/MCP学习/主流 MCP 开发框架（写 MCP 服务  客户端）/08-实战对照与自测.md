## 1. 同一 Server，四语言对照

**需求**：天气查询 Server（一个工具：get_weather，参数 city，返回文本）。四个生态各写一遍，对比"同一个协议概念在不同框架的形态"。

| 维度 | Python | TypeScript | Java | Go |
|---|---|---|---|---|
| 框架 | FastMCP 3.x | 官方 SDK v1.29 | Spring AI starter | mark3labs |
| 注册 | 装饰器 | registerTool | @Tool 注解 | AddTool 链式 |
| Schema | 类型注解+docstring | Zod | 注解参数 | 链式 WithString |
| 启动 | mcp.run() | connect(transport) | Spring Boot 启动 | ServeStdio |
| 行数 | ~15 | ~25 | ~30 | ~30 |

## 2. Python 实现（FastMCP）

```python
from fastmcp import FastMCP

mcp = FastMCP("weather")

@mcp.tool
def get_weather(city: str) -> str:
    """查询城市天气。何时用：用户问天气时。"""
    return f"{city}: 晴，25°C"

if __name__ == "__main__":
    mcp.run()          # stdio；HTTP: mcp.run(transport="http", port=8080)
```

## 3. TypeScript 实现（官方 SDK）

```typescript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "weather", version: "1.0.0" });
server.registerTool("get_weather", {
  description: "查询城市天气。何时用：用户问天气时。",
  inputSchema: { city: z.string().describe("城市名") },
}, async ({ city }) => `${city}: 晴，25°C`);

await server.connect(new StdioServerTransport());
```

## 4. Java 实现（Spring AI）

```java
@Service
public class WeatherTool {
    @Tool(description = "查询城市天气。何时用：用户问天气时。")
    public String getWeather(@ToolParam(description = "城市名") String city) {
        return city + ": 晴，25°C";
    }
}
// application.yml: spring.ai.mcp.server.protocol=STREAMABLE
// 启动类 @SpringBootApplication 即 Server
```

## 5. Go 实现（mark3labs）

```go
s := server.NewMCPServer("weather", "1.0.0")
s.AddTool(mcp.NewTool("get_weather",
    mcp.WithDescription("查询城市天气"),
    mcp.WithString("city", mcp.Required(), mcp.Description("城市名")),
), func(req mcp.CallToolRequest) (*mcp.CallToolResult, error) {
    city, _ := req.Params.Arguments["city"].(string)
    return mcp.NewToolResultText(city + ": 晴，25°C"), nil
})
server.ServeStdio(s)
```

## 6. 对照结论：框架的共性

四份实现揭示 MCP 框架的"五要素共性"：

| 共性要素 | 各语言形态 |
|---|---|
| 服务器实例 | FastMCP("weather") / McpServer / @SpringBootApplication / NewMCPServer |
| 工具注册 | 装饰器 / registerTool / @Tool / AddTool |
| Schema 来源 | 类型注解 / Zod / 注解参数 / 链式 DSL |
| Handler | 函数体（同业务逻辑） |
| 传输启动 | run() / connect() / Spring 启动 / ServeStdio |

**结论**：**MCP 框架 API 高度同构**——会一种语言，其他语言半天上手；差异集中在"Schema 声明方式"（注解/Zod/DSL）与"启动方式"（显式/框架接管）。**这条结论就是 07 篇"协议是稳定层"的代码级证据**。

**五要素共性的实操含义**：这份共性不是巧合，而是**协议本身的结构决定的**——MCP 的协议原语（list/call/资源/提示词）在规范层面固定，各框架只是用本语言习惯重新表达；理解这一点后，"学新框架"就变成"找到五要素的对应物"：新框架文档先找"服务器实例怎么建、工具怎么注册、Schema 怎么声明、Handler 怎么写、传输怎么启动"五个问题，答完就能写代码——**这套"五问法"比逐章读文档快一个数量级**，也是面试官考察"框架迁移能力"时的真实考题。

## 9. 自测参考答案

1. TypeScript/Python/Go(官方)/C#；Tier 1 = 官方保证 100% 协议合规与 day-one 支持。
2. 2026-07-28 无状态规范发布当天即支持新协议；四个 Tier 1 SDK 全部做到。
3. 语言（团队栈）→ 官方/社区（协议保证 vs 效率）→ 高层/底层（业务 vs 基础设施）。
4. FastMCP 是建在官方 mcp SDK 之上的社区高层框架（PrefectHQ）；选效率选 FastMCP，选协议层选官方。
5. FastMCP → MCPServer；mcp-migration 扫描工具。
6. stdio 客户端桥接远程 HTTP Server（OAuth 自动、fail-loud）。
7. 协议行为定义以 TS SDK 为基准，其他语言对照实现。
8. 类型定义即工具 Schema（z.string().describe() 同时产生 TS 类型与 JSON Schema）。
9. @modelcontextprotocol/server + client + spec；codemod v1-to-v2。
10. Client/Server 层 → Session 层 → Transport 层（响应式内核 + 同步门面）。
11. 方法标注即工具（自动注册），Java 写 MCP 降为"写一个 Service 方法"。
12. spring.ai.mcp.server.protocol=STATELESS。
13. mark3labs（社区，业务应用）vs 官方 go-sdk（Tier 1，基础设施/合规）。
14. ModelContextProtocol；Tier 1 稳定。
15. 官方 rmcp（生态/贡献者）vs rust-mcp-stack（API 体验）；beta 慎上核心生产。
16. 团队技术栈（第一问永远先问团队会什么）。
17. Tier（合规）× 风格（效率）× v2 支持（新规范可用性）。
18. 状态改造（会话状态→显式句柄）——改名/拆包是机械步骤，无状态改造才是正活。
19. 生产稳定 + 无远程部署需求（12 个月弃用窗口内不迁合法）。
20. 服务器实例/工具注册/Schema 来源/Handler/传输启动。

## 7.1 客户端对照（补充）

服务端之外，客户端在各框架的形态对照（阶段 4 编排器的跨语言视角）：

| 语言 | 客户端 API | 用法 |
|---|---|---|
| Python | 官方 Client / FastMCP 无独立客户端 | 阶段 4 编排器（McpClient 封装） |
| TS | Client + StreamableHTTPClientTransport | 自定义 Agent 应用 |
| Java | spring-ai-starter-mcp-client（配置化） | Spring 应用注入工具 |
| Go | 官方/社区 SDK 的 Client 部分 | CLI 工具内嵌 |

**客户端对照结论**：**客户端比服务端更"配置化"**（Spring AI 配置即连、TS 显式传输）——但核心能力一致（list/call + 传输 + 认证）；阶段 4 学过的"编排器=客户端"心智跨语言通用。

## 7.2 认证对照（补充）

框架的认证能力差异（选型时的高权重维度）：

| 框架 | 认证能力 | 形态 |
|---|---|---|
| FastMCP 3.x | OAuth 四策略（JWT/远程/Proxy/完整） | 内建 |
| TS SDK | mcpAuthRouter（OAuth 2.1 + PKCE） | 内建 |
| Spring AI | Spring Security 生态复用 | 集成 |
| Java SDK | 无内建（配合 Spring Security） | 集成 |
| 官方 Python 1.x | 无（v2 规划） | 缺失 |

**认证选型启示**：**需要开箱即用认证 → FastMCP 或 TS SDK**；Java 生态靠 Spring Security（企业已有）；官方 Python 1.x 裸奔（生产需自行封装）——**"认证能力"是 02-05 篇之外最容易被忽略的框架差异点**。

## 7.3 传输对照（补充）

| 框架 | 传输 API 形态 | 切换成本 |
|---|---|---|
| FastMCP | run(transport="http") 参数切换 | 零（一行） |
| TS SDK | 不同 transport 类 + connect() | 低（换类） |
| Spring AI | 配置项 protocol=STREAMABLE/STATELESS | 零（改配置） |
| mark3labs | 不同 Serve 函数 | 低（换函数） |

**传输对照结论**：**"传输可切换"是所有框架的共性设计**（stdio 本地开发、HTTP 远程部署）——阶段 3 的"传输即配置"心智跨框架成立；Spring AI 的配置化（改一行）最彻底。

**实战演练建议**（把 08 篇变成动手能力）：① 用你的主力语言写天气 Server（对照第 2-5 节任一实现）并接 Inspector 验证（tools/list → call → 错参）；② 再选一门语言写同一个 Server（建议选与你主力差异最大的：Java 开发者试 Python、Python 开发者试 Go）——**第二次写的速度就是"五要素迁移能力"的实测**（目标：1 小时内）；③ 把两次实现对比写进个人笔记（Schema 声明方式/启动方式的差异就是框架知识的第一手素材）；④ 用 07 篇决策树给自己的主力语言做一次"为什么选它"的 ADR 练习——**演练产出比阅读产出更值钱**：四步做完，框架知识体系从"读过"变成"做过"。

**对照实现的"深度变体"**（进阶演练）：天气 Server 太简单，进阶版给它加三个真实约束——① 写操作（update_ship_date 类）：比较四语言"写工具 + 确认"的写法（阶段 3 MRTR 的跨框架形态）；② 认证（Bearer 校验）：比较四语言的认证实现成本（TS 的 mcpAuthRouter vs Python 的 JWTVerifier vs Java 的 Security vs Go 手写）——**这一步直接验证 08 篇"认证是框架差异点"的结论**；③ 资源+提示词（再加一个 Resource 与 Prompt）：验证各框架对三原语的支持完整性。**进阶变体的价值**：天气版证明"共性"，进阶版暴露"差异"——共性是迁移能力的底子，差异是选型决策的依据，两者都亲自验证过，框架知识才算闭环。
