## 1. 选型决策树

```text
开始：要写 MCP 什么？
│
├─ 写 Server（业务工具）
│   │
│   ├─ 团队技术栈是？
│   │   ├─ Python → FastMCP 3.x（官方 v2 MCPServer 为备选）
│   │   ├─ Java/Spring → Spring AI starter（STATELESS 模式）
│   │   ├─ TypeScript/前端 → 官方 SDK（v1.29 稳定，v2 等稳定）
│   │   ├─ Go → mark3labs/mcp-go（要 day-one 合规选官方 go-sdk）
│   │   ├─ C# → csharp-sdk（唯一答案）
│   │   ├─ Rust → 官方 rmcp（beta 慎上生产）
│   │   └─ 其他 → 回 Tier 1 或接受 Tier 3 代价
│   │
│   └─ 团队栈未定 → 默认 TS 或 Python（生态最大、参考实现）
│
├─ 写 Client（编排器/网关）
│   ├─ 编排器已用某语言 → 同语言 SDK 的 Client（阶段 4 模式）
│   ├─ 网关基础设施 → 官方 SDK（TS/Go 的 Tier 1 保证）
│   └─ Spring 应用 → spring-ai-starter-mcp-client
│
├─ 写基础设施/平台（协议级）
│   └─ 官方 SDK（Tier 1：TS/Python/Go/C#）——合规与长期支持优先
│
└─ 学习/教学
    └─ 官方低层 API 写一遍（Python 1.x / TS v1 / Java SDK 低层）再切高层
```

**决策树的三条主线**：团队栈（第一问）→ 端（Server/Client/基础设施）→ 官方 vs 社区（业务选社区高层、基础设施选官方低层）——**01 篇三层心智的落地形态**。

## 2. 全框架对比矩阵

| 框架 | 语言 | Tier | 风格 | 传输 | v2/新规范 | 适用 |
|---|---|---|---|---|---|---|
| FastMCP 3.x | Python | 社区 | 高层 | stdio/HTTP | 官方 v2 后跟进 | 业务 Server |
| 官方 mcp 1.x/2.x | Python | 1 | 中/高层 | 全 | **原生** | 协议/通用 |
| TS SDK v1.29 | TS | 1 | 高/中 | 全+Express | 拆包 alpha | 全端/前端 |
| Java SDK | Java | 2 | 中 | 全 | 跟进中 | Java 协议层 |
| Spring AI starter | Java | 2 | 高层 | 全+STATELESS | **STATELESS 模式** | Spring 业务 |
| mark3labs | Go | 社区 | 高层 | 全 | 未知 | Go 业务 |
| 官方 go-sdk | Go | 1 | 低层 | 全 | **day-one** | Go 基础设施 |
| csharp-sdk | C# | 1 | 高层 | 全 | day-one | .NET 企业 |
| rmcp | Rust | 2 | 高层 | stdio 等 | beta | 高性能/边缘 |

**矩阵的读法**：① Tier 列决定合规承诺；② 风格列决定开发效率；③ v2 列决定"2026-07-28 规范什么时候可用"——**三列合起来就是选型答案**。

## 3. v2 迁移总清单

2026-07-28 无状态规范的迁移，跨语言通用清单：

| 步骤 | 内容 | 工具 |
|---|---|---|
| 1. 盘点 | 列出所有 Server 的会话依赖（Session-Id/状态变量） | 代码扫描 |
| 2. 状态改造 | 会话状态 → 显式句柄（basket_id/job_id） | 手改（阶段 3 方法论） |
| 3. 列表静态化 | tools/list 等不再随连接变化 | 手改 |
| 4. 确认改造 | 服务器主动请求 → MRTR（input_required） | 手改 |
| 5. SDK 升级 | 按各语言 v2 路径 | Python: pip mcp==2.0.0b1 + mcp-migration；TS: codemod v1-to-v2 |
| 6. 合规补全 | resultType/discover/_meta/强制头 | 手改 + 协议合规测试（阶段 3 第 6 篇） |
| 7. 回归 | 全量测试 + 客户端兼容验证 | 既有测试体系 |

**各语言 v2 路径速查**：

| 语言 | v2 包/类 | 迁移工具 |
|---|---|---|
| Python | mcp 2.x（FastMCP→MCPServer） | mcp-migration |
| TypeScript | @modelcontextprotocol/server + client | codemod v1-to-v2 |
| Go | 官方 go-sdk v1.2+（2026-07 起新规范） | 官方文档 |
| C# | ModelContextProtocol 新版 | 官方文档 |
| Java | Java SDK / Spring AI STATELESS | Spring 配置切换 |

## 4. 迁移触发条件

**什么时候该迁 v2**（不迁移的"合法理由"）：

| 状态 | 建议 | 理由 |
|---|---|---|
| 新项目 | 直接 v2 起步 | 无历史包袱 |
| 生产稳定 + 无远程部署 | 暂缓（12 个月弃用窗） | 稳定性优先 |
| 生产 + 要上云/Serverless | 优先迁 | 无状态红利（轮询 LB/Serverless） |
| 生产 + 多客户端 | 评估迁 | 客户端生态在向 v2 走 |
| 纯本机个人工具 | 不迁 | legacy 兼容期内照常跑 |

**迁移不是"必须立刻做"**：规范给了 12 个月弃用窗口（Roots/Sampling/Logging 等旧特性）与双代兼容（legacy 握手兜底）——**迁移节奏由部署需求驱动，不由版本焦虑驱动**（与阶段 3 的迁移时机判断一致）。

## 5. 迁移的通用方法论

**换框架/升版本的通用五步**（GitLab CLI 迁移案例的方法论化）：

```text
1. 盘现状：清单化（工具/传输/认证/状态依赖）
2. 定边界：新框架的对应物映射（旧 API → 新 API 对照表）
3. 试点：一个 Server 全量迁移，其余冻结
4. 验证：协议合规测试 + 客户端全量回归（阶段 3/4 的测试体系复用）
5. 分批：按 Server 逐批切换，每批独立验证与回滚点
```

**迁移纪律**：① **协议不换，框架可换**——MCP 是稳定层，换框架不换协议（GitLab CLI 案例的启示）；② 迁移期间新旧并存（双代兼容）；③ 每批迁移有回滚点（镜像回滚）；④ **迁移的验收 = 测试全绿 + 客户端行为不变**——"看起来一样"比"用起来顺手"优先。

**选型与迁移的团队协作**：选型和迁移都不是单人决策——**选型要写 ADR**（架构决策记录，阶段 4 已学）：记录"考虑了哪些选项、为什么选这个、什么条件下换"，三个月后团队问"为什么不用 X"时 ADR 就是答案；**迁移要立"变更窗口"**（发布节奏：选低峰期、每批独立验证、失败即回滚）。企业环境里，框架选型的失败很少是技术问题，多半是"决策没记录、变更没窗口、回滚没预案"的流程问题——**把 07 篇的方法论写成团队的 ADR 模板与发布清单，比任何人记住决策树都可靠**。这也是本体系从"个人知识"走向"团队规范"的最后一步：框架知识最终要变成团队的工程制度。

**决策树与矩阵的使用边界**：决策树和对比矩阵是"起步工具"，不是"终点答案"——真实项目还有三个矩阵没覆盖的变量：**既有代码资产**（已有 200 个 Python 工具函数时，框架选型向 Python 倾斜）、**团队学习成本**（上线时间紧时，选团队最熟的不是最好的）、**组织约束**（集团标准/合规要求指定语言）。**正确的用法**：先跑决策树得到"理论答案"，再用三个现实变量修正，最后把修正过程写进 ADR——**"理论与现实的差距"正是 ADR 最值钱的部分**（面试官问"为什么没选理论最优"时，你的 ADR 就是完整答案）。记住：方法论的价值不在"给出唯一答案"，而在"让答案可解释、可复核、可更新"。

**本体系的最终总结**（读完本体系应该带走的三句话）：第一句——**"协议是稳定层，框架是可换层"**：学框架不必有"选错焦虑"，换框架的成本由测试与契约决定，不由框架决定；第二句——**"Tier 定合规，锚点定场景，效率定日常"**：Tier 回答"协议会不会掉队"，锚点回答"为什么选它"，效率回答"每天写代码顺不顺"——三者齐备，选型无死角；第三句——**"版本会过时，心智不会"**：Tier 心智、五要素共性、选型方法论三样不变资产，配上一套"复核方法"（季度看 Tier 表、发版看 changelog、迁移跑七步清单），框架知识体系就永远新鲜——**这不是一套读完即弃的教程，而是一套可持续维护的决策系统**。

**与阶段体系的最终衔接**：阶段 2 用 FastMCP 跑通最小链路（"会用一个框架"）、阶段 3 用生产级清单打磨（"用好一个框架"）、阶段 4 用项目组合（"在项目里用框架"）、本体系给的是第四层——**"在任何框架面前都有方法论"**。四层叠加，你的 MCP 能力从"会写"到"会选"到"会教"（能向团队解释选型并写成 ADR）——**"会教"是框架知识体系的最高形态**：能教会别人选型的人，必然同时掌握了事实、因果与判断，这正是本体系 00-08 篇层层递进想要达到的终点。祝选型顺利，祝代码长青。

## 6. 选型案例三则

**案例 A：本库主线（Java 后端团队）**。写订单助手 MCP Server：团队 Java + Spring → Spring AI starter（@Tool + STATELESS）；需要协议级定制时用 Java SDK 低层。**决策路径**：技术栈（Java）→ 官方（Spring 官方化）→ 高层（starter）。

**案例 B：AI 初创（Python + 快速迭代）**。写数据处理工具 Server：FastMCP 3.x（OAuth 内建 + 中间件 + code mode）——比官方 SDK 省一半代码；协议层风险由"建在官方 SDK 上"兜底。**决策路径**：技术栈（Python）→ 社区（效率优先）→ 高层（FastMCP）。

**案例 C：云平台基础设施（Go）**。写 MCP 网关/认证基础设施：官方 go-sdk（Tier 1 day-one 合规 + 长期支持）——社区框架的时间线未知不可接受。**决策路径**：技术栈（Go）→ 官方（合规优先）→ 低层（协议级控制）。

**三案例的共性**：**同样的三层心智走出三条不同路径**——选型没有"最好"，只有"匹配"。

## 7. 迁移实战案例：无状态改造

一个 v1 Server 迁移 v2 的实战演练（阶段 3 无状态方法论的框架落地）：

```text
迁移前（v1，会话依赖）：
  server 保存 session_id → 工具隐含"当前购物篮"
迁移步骤：
  1. 盘点：发现 2 处 Session-Id 依赖
  2. 状态改造：basket_id 改为显式参数（工具接口变化）
  3. 列表静态化：tools/list 不再按用户过滤（参数化表达）
  4. 确认改造：无（本项目无服务器主动请求）
  5. SDK 升级：pip mcp==2.0.0b1 + mcp-migration 扫描
  6. 合规补全：resultType 检查（每个工具返回补 complete）
  7. 回归：阶段 3 测试体系全量跑 + 客户端兼容验证
结果：协议合规（无状态）+ 部署红利（轮询 LB 可用）
```

**案例启示**：**迁移的 80% 工作量是"状态改造与合规补全"（语义工作），20% 是 SDK 升级（机械工作）**——工具只能代劳 20%，这就是"迁移是方法论的活不是工具的活"。

## 8. 面试速记与常见坑

**面试速记**：
1. 选型三问：团队栈 → 端（Server/Client/基础设施）→ 官方/社区。
2. 对比矩阵三列：Tier（合规）× 风格（效率）× v2（新规范可用性）。
3. 迁移七步：盘点→状态→列表→MRTR→SDK→合规→回归。
4. 迁移节奏：新项目直接 v2；生产按部署需求；12 个月窗口不焦虑。
5. 迁移五步法：盘现状→定边界→试点→验证→分批（每批回滚点）。
6. 金句：协议是稳定层，框架是可换层。

**常见坑**：
- 选型跳过"团队栈"直接比框架（第一问答错全错）；
- 迁移只升 SDK 不做状态改造（正活跳过，行为没变");
- 全量迁移一次完成（没有回滚点）；
- 把弃用窗口当"永久可用"（12 个月后旧特性移除）；
- 迁移验证只看"能跑"不看"行为一致"（客户端体验回归）。

## 9. 迁移成本评估表

决定"迁不迁、何时迁"的成本模型（给决策者算账用）：

| 成本项 | 量级 | 可控性 |
|---|---|---|
| 机械迁移（SDK 升级/改名） | 小时级（工具代劳） | 高（codemod/mcp-migration） |
| 状态改造（会话→句柄） | 天级（核心工作） | 中（依赖状态复杂度） |
| 合规补全（resultType/discover） | 小时-天级 | 高（清单化） |
| 回归验证（测试+客户端） | 天级 | 中（测试体系复用） |
| 运维切换（部署/回滚点） | 小时级 | 高（镜像回滚） |

**成本结论**：**典型 Server 的 v2 迁移总成本 2-5 人日**；其中"状态改造+回归"占 70%——**迁移预算应该花在盘点状态与补测试上，不是花在"学新 API"上**（API 形态高度同构，08 篇已证）。

**选型的"反模式"清单**（避免常见选型错误）：① 从框架出发选语言（"FastMCP 好用所以学 Python"——顺序反了，先团队栈后框架）；② 为"潮流"选框架（"官方 SDK 新出的必须用"——先看场景再看版本）；③ 忽视合规需求（做基础设施却选社区框架，2026-07-28 时间线未知是硬伤）；④ 忽视部署形态（选 Go 却要跑在 JVM 环境，选 Java 却要单二进制）；⑤ 把"教程多"当"适合我"（mark3labs 教程最多，但你的场景可能更需要官方保证）；⑥ 迁移一刀切（全量切换无回滚点）。**对照清单自查：你的选型决策如果命中两条以上反模式，回到 01 篇三层心智重新走一遍**——选型错误在项目早期几乎无感，在"要上 v2/要合规/要换端"时集中爆发。

## 10. 面试速记补充（选型篇）

1. 三案例三路径：Java 官方高层 / Python 社区高层 / Go 官方低层——选型是匹配不是最好。
2. 迁移成本模型：总 2-5 人日，70% 在状态改造与回归。
3. 迁移 80/20：语义工作（状态/合规）80%，机械工作（SDK）20%——工具只代劳 20%。
4. 决策树第一问永远是团队技术栈（先决变量）。
5. 弃用窗口是"计划期"不是"免死金牌"（12 个月后旧特性移除）。

> 🎯 **核心要点**：选型 = 决策树（团队栈→端→官方/社区三问）+ 对比矩阵（Tier/风格/v2 三列）+ 迁移总清单（状态→句柄、列表静态化、MRTR、SDK 升级、合规补全、回归七步）+ 迁移成本模型（2-5 人日，70% 在状态改造与回归）+ 迁移节奏（新项目直接 v2、生产按部署需求评估、12 个月窗口不焦虑）+ 通用方法论（盘现状→试点→分批→每批回滚点）+ 三案例（Java 官方高层/ Python 社区高层/ Go 官方低层）。**选框架靠矩阵，换框架靠清单，两者都记住一句：协议是稳定层，框架是可换层**。
