# 07 适用场景与边界

> 不是所有"接外部能力"都需要 MCP：需要模型自主发现调用、多应用复用、跨模型标准 → 用 MCP；单应用写死调用、无需标准化 → 传统 API 更合适——判断口诀："模型要用 + 多处复用 + 标准价值"。

## 1. 适合 MCP 的特征

### 三个特征（缺一不可）

| 特征 | 说明 |
|---|---|
| 模型要用 | 能力给模型动态调用（非写死） |
| 多处复用 | 多个应用/工具要用同一能力 |
| 标准价值 | 标准化带来收益（生态/互通） |

### 特征详解

```
模型要用：模型自主发现/调用（MCP 的价值所在）
多处复用：写一次处处用（N+M 的收益）
标准价值：有生态/跨工具需求（否则自研更简）
```

## 2. 典型适用场景

| 场景 | 为什么适合 |
|---|---|
| 文件系统工具 | 多应用都要（Claude Code/Cursor 等） |
| 数据库访问 | 模型查询 + 多工具复用 |
| 搜索/网页 | 通用能力（生态标准） |
| GitHub/Git 工具 | 开发工具链标准化 |
| 企业数据服务 | 统一接入（认证/治理） |

### 场景共同点

```
全是"通用能力 + 多消费方"：
一个能力多方用 → MCP 标准化收益最大
```

## 3. 不适合的场景

| 场景 | 为什么不适合 |
|---|---|
| 单应用专用 | 无复用（自研更简） |
| 高频低延迟 | MCP 协议开销 > 直调 |
| 无需模型调用 | 应用代码写死即可 |
| 一次性集成 | 标准化成本 > 收益 |
| 敏感但无需共享 | 保持私有（最小暴露） |

### 不适合的共同点

```
无复用 / 非模型调用 / 无标准需求
——MCP 是"生态工具"不是"万能胶"
```

## 4. 与 API / 插件 / Agent Skill 的边界

| 方案 | 给谁用 | 标准化 | 适用 |
|---|---|---|---|
| 传统 API | 应用代码 | 各自定义 | 业务接口 |
| MCP | 模型 | 统一协议 | 模型调用 + 复用 |
| 插件 | 特定应用 | 应用私有 | 单应用扩展 |
| Agent Skill | 模型 | 开放标准 | 任务知识 |

### 边界判断

### 与阶段 2 的衔接

```
阶段 1 的边界认知 → 阶段 2 的选题：
选 Server 主题时用三问判断：
① 模型要自主调用吗？
② 多应用复用吗？
③ 有标准价值吗？
——三问通过再动手（避免做了没用）
```

### 边界判断

```
模型自主调用 + 跨应用 → MCP
应用写死调用 → 传统 API
单应用扩展 → 插件
任务知识 → Agent Skill（双标准）
——各管一段（不是替代关系）
```

### 关键区别（回顾 01 篇）

```
传统 API = 给程序用（写死）
MCP = 给模型用（自主发现调用）
——服务对象决定方案
```

## 5. 判断决策树

### 一句话定位总结

```
MCP 不是万能胶，是"生态工具"：
模型自主调用 + 多应用复用 + 标准价值 → 用
单应用写死 / 非模型调用 / 无复用 → 别用
——先判断再动手（避免为用而用）
```

```
这个能力要接给谁？
├─ 应用代码写死调用？
│   ├─ 是 → 传统 API（不用 MCP）
│   └─ 否 ↓
├─ 模型需要自主调用？
│   ├─ 否 → 应用内处理
│   └─ 是 ↓
├─ 多个应用都要用？
│   ├─ 否 → 可直连（评估成本）
│   └─ 是 ↓
├─ 需要标准生态/互通？
│   ├─ 否 → 可自研（简单场景）
│   └─ 是 ↓
└─ ✅ 适合 MCP
```

### 口诀

```
"模型要用 + 多处复用 + 标准价值"——三问全是通过
写死调用 → API；单应用 → 插件；任务知识 → Skill
```

## 6. 边界案例

### 常见误区

| 误区 | 真相 |
|---|---|
| "MCP 万能胶" | 有明确边界（三问判断） |
| "有工具就用 MCP" | 单应用/写死调用不需要 |
| "MCP 与 API 对立" | 服务对象不同（可共存） |
| "插件会被 MCP 取代" | 单应用扩展仍用插件 |
| "越标准越好" | 标准化有成本（评估收益） |

### 案例 A：文件系统工具

```
用 MCP？✅
理由：多应用都要（Claude Code/Cursor/自建）+ 模型调用
```

### 案例 B：内部报表接口

```
用 MCP？⚠️
理由：模型调用（可）但单应用专用（无复用）
→ 评估：直连更简（无标准化收益）
```

### 案例 C：搜索能力

```
用 MCP？✅
理由：通用能力 + 多消费方 + 生态标准
```

### 案例 D：配置读取

```
用 MCP？❌
理由：应用启动时读一次（非模型调用）
→ 配置文件即可
```

### 案例 E：团队共享工具

```
用 MCP？✅
理由：多个 AI 工具（Claude Code/Cursor）都要用
+ 团队标准化（一套 Server 全工具可用）
→ MCP 的"写一次处处用"场景
```

```
用 MCP？❌
理由：应用启动时读一次（非模型调用）
→ 配置文件即可
```

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 什么适合 MCP？ | 模型要用 + 多处复用 + 标准价值 |
| 什么不适合？ | 单应用/非模型调用/无标准需求 |
| 与 API 边界？ | 给模型（自主）vs 给程序（写死） |
| 与插件边界？ | 开放标准 vs 应用私有 |
| 与 Agent Skill？ | 工具 vs 知识（互补） |
| 判断口诀？ | 三问 + 服务对象 |

### 面试加分表达

> "MCP 的判断三问：模型需要自主调用吗？多个应用都要用吗？标准化有生态收益吗？三问全是通过才适合。边界清晰：传统 API 给程序写死调用、MCP 给模型自主发现调用、插件是单应用私有扩展、Agent Skills 管任务知识——各管一段，不是替代关系。单应用专用、高频直调、非模型调用的场景，别为用 MCP 而用 MCP。"

> 🎯 核心要点：适合三特征（模型要用/多处复用/标准价值）；不适合四类（单应用/非模型/一次性/私有）；边界（API 程序/MCP 模型/插件单应用/Skill 知识）；判断决策树 + 口诀；边界案例四则；别为用而用。
