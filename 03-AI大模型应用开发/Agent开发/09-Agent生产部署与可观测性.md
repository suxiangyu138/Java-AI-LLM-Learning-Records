## 1. 原型到生产的鸿沟

> ⚠️ **最常见的失败模式**：把复杂 Agent 工作流强塞进同步 REST API——用户等 5 分钟拿不到响应，请求超时、任务丢失、系统不可用。

```text
原型 vs 生产
├── 原型：同步调用、单线程、无状态、无监控
│   └── 能用就行（演示场景可接受）
├── 生产：异步处理、可扩展、可恢复、可观测
│   └── 10x 并发 + 故障恢复 + 成本可控
└── 鸿沟点：同步 → 异步 是第一步
```

| 维度 | 原型 | 生产 |
|------|------|------|
| 调用方式 | 同步 REST | **异步事件驱动** |
| 任务时长 | 秒级 | 分钟级（长任务） |
| 扩展 | 单实例 | 水平扩展 |
| 失败处理 | 报错结束 | **重试 + 恢复 + 告警** |
| 观测 | 无 | 全链路追踪 |

## 2. 服务架构：事件驱动微服务

### 2.1 为什么事件驱动

> 📊 **数据**：从单体架构转向事件驱动微服务，可将 AI 处理延迟降低最多 **60%**——允许 CPU 预处理、GPU 推理、CPU 后处理**独立扩缩容**。

```text
Agent 服务的三段式
┌──────────┐   ┌──────────┐   ┌──────────┐
│ 预处理     │   │ AI 推理   │   │ 后处理     │
│ (CPU)     │ → │ (GPU)    │ → │ (CPU)     │
│ 上下文组装  │   │ 模型调用  │   │ 工具执行   │
└──────────┘   └──────────┘   └──────────┘
     ↓ 独立扩缩容：推理高峰只扩 GPU 段
```

### 2.2 架构设计

```text
事件驱动微服务架构
用户请求 → API 网关 → 消息队列（事件）→ Worker 集群
                                        │
                                  执行 Agent 循环
                                        │
                                  结果 → 存储/回调通知
                                        │
                                    监控/追踪/告警
```

| 组件 | 职责 | 选型 |
|------|------|------|
| **API 网关** | 认证/限流/路由 | Kong/APISIX |
| **消息队列** | 异步任务分发 | Kafka/RabbitMQ |
| **Worker 集群** | Agent 循环执行 | K8s 部署 |
| **状态存储** | 任务状态/检查点 | Redis/PostgreSQL |
| **结果存储** | 任务结果/审计 | 对象存储/数据库 |

### 2.3 任务状态机

```text
Agent 任务状态机
PENDING → RUNNING → SUCCEEDED
   │         │           │
   │         ├─→ FAILED ─┴─→ RETRYING → RUNNING（重试）
   │         │
   └─→ CANCELLED（超时/人工取消）

要点：
├── 状态外部化（Redis/DB），Worker 崩溃可恢复
├── 幂等处理（同任务重复投递不重复执行）
└── 超时机制（任务级 + 步骤级）
```

## 3. 三大开发挑战与对策

### 3.1 循环死路（Looping）

| 表现 | 对策 |
|------|------|
| Agent 卡在循环反复执行 | ① 最大尝试次数（step 上限） |
| 同一失败动作重复 | ② 失败模式记忆（同错误不再犯） |
| 工具调用环 | ③ 工具调用去重 + 上限 |

```python
# 循环防护
def guard_loop(history):
    """循环检测：识别重复模式"""
    recent = history[-5:]
    if len(recent) >= 3 and all(x.tool == recent[0].tool for x in recent):
        return "LOOP_DETECTED"      # 检测到重复 → 干预
    if len(history) > MAX_STEPS:
        return "STEP_LIMIT"         # 步骤上限 → 终止
    return "OK"
```

└── Guardrails + HITL 审批

## 4. 成本控制

### 4.1 成本构成

```text
Agent 成本三支柱
├── ① Token 成本（最大头）：模型调用
├── ② 基础设施：GPU/实例/存储
├── ③ 工具成本：第三方 API 调用
→ 优化重点：Token 成本（占 70%+）
```

### 4.2 小模型路由策略

> 🎯 **核心优化**：引入小模型路由器——简单规划用小模型（如 Llama-8B），复杂决策才调用大模型：

```text
模型路由
┌─────────┐  简单任务  ┌──────────┐
│ 路由判断  │ ────────→ │ 小模型    │（成本 1x）
│ (分类器) │            └──────────┘
└─────────┘
    │ 复杂任务
    ▼
┌─────────┐
│ 大模型   │（成本 10-50x）
└─────────┘
→ 收益：70% 简单步骤走小模型，总成本降 50%+
```

### 4.3 成本控制清单

```text
成本控制六招
├── ① 模型路由：简单任务小模型（最大收益）
├── ② 上下文压缩：只带必要上下文（token = 成本）
├── ③ 缓存：相同请求结果缓存（KV Cache/语义缓存）
├── ④ 预算上限：任务级 token 预算 + 硬中断
├── ⑤ 批量处理：非实时任务批量调用
└── ⑥ 每任务成本指标：监控 + 告警（异常飙升即查）
```

### 4.4 预算示例

| 任务类型 | 预算参考 |
|---------|---------|
| 简单查询任务 | 5-20K token |
| 中等分析任务 | 20-80K token |
| 复杂多 Agent 任务 | 100-500K token（15 倍注意） |
| 月成本估算 | = 日均任务量 × 单任务 token × 单价 |

## 5. 可观测性三支柱

### 5.1 日志（Logs）

```text
Agent 日志体系
├── 业务日志：任务/步骤/结果
├── 模型日志：请求/响应摘要（脱敏）
├── 工具日志：调用/参数/耗时
└── 安全日志：注入尝试/越权/审批记录
→ 关键：敏感信息脱敏（PII/密钥不进日志）
```

### 5.2 追踪（Traces）——因果链

```text
Agent 追踪 = 因果链追踪（见 07 篇）
├── trace_id：任务唯一标识
├── span：每次模型/工具调用
├── parent_span_id：因果链
└── 聚合查询：任务 × 模型 × 工具维度
→ 排障核心：一条 trace 看全链路决策
```

### 5.3 指标（Metrics）

| 指标 | 内容 | 告警阈值参考 |
|------|------|:---:|
| **任务成功率** | 完成任务/总任务 | <85% 告警 |
| **平均轮次** | 每任务 Agent 循环次数 | >15 告警 |
| **Token 消耗** | 每任务/每小时 | 预算超 80% 告警 |
| **端到端延迟** | P95/P99 | P95 >60s 告警 |
| **工具失败率** | 工具调用失败占比 | >10% 告警 |
| **注入尝试** | 安全事件计数 | >0 告警 |

## 6. 部署策略

### 6.1 灰度发布

```text
Agent 灰度发布流程
├── ① 影子模式：新版本与旧版本并行（只观测不接管）
├── ② 金丝雀：5% 流量试运行（对比评估分数）
├── ③ 渐进：25% → 50% → 100%
└── ④ 回滚预案：一键回滚（状态兼容性检查）
```

### 6.2 版本管理

```text
Agent 版本管理（提示词即代码）
├── 提示词/技能入库版本管理（Git）
├── 模型版本 + Harness 配置锁定
├── 评估分数随版本记录（回归基线）
└── 回滚 = 版本回退 + 状态兼容
```

### 6.3 环境划分

| 环境 | 用途 | 数据 |
|------|------|------|
| dev | 开发调试 | 模拟数据 |
| staging | 集成验证 | 脱敏数据 |
| prod | 生产运行 | 真实数据 |
| shadow | 新版本对比 | 真实流量副本 |

## 7. 生产运营体系

### 7.1 日常运营

```text
生产运营日历
├── 每日：错误率/延迟/token 监控巡检
├── 每周：评估分数对比（模型/提示词变更回归）
├── 每月：红队测试 + 成本复盘 + 评估集扩充
└── 每季：架构评审（瓶颈/扩展性/新能力）
```

### 7.2 事故响应

```text
Agent 事故响应流程
├── ① 发现：监控告警/用户反馈
├── ② 定位：trace 因果链 → 失败环节
├── ③ 处置：回滚/停用 Agent/修复配置
├── ④ 复盘：根因分类（模型/工具/上下文/配置）
└── ⑤ 改进：根因转评估用例（防复发）
→ 金句：每次事故都是一次免费的评估集扩充
```

### 7.3 持续优化循环

```text
生产优化飞轮
遥测数据 → 发现瓶颈 → 改进（提示词/路由/缓存）
    ↑                                    ↓
    ←──── 评估验证（分数对比） ←─────────┘
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 原型到生产第一道坎：同步 → 异步（事件驱动微服务，延迟可降 60%）
> 2. 三大挑战：循环死路（上限+检测）、安全越权（隔离+守卫）、成本失控（小模型路由）
> 3. 成本控制六招：路由/压缩/缓存/预算/批量/监控——小模型路由收益最大
> 4. 可观测三支柱（日志/追踪/指标）+ 灰度发布 + 事故飞轮（事故转评估用例）= 生产运营体系
