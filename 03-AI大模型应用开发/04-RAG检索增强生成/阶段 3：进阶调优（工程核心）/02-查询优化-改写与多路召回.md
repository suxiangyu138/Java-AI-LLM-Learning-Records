## 1. 查询优化的目标与边界

### 目标

让"进检索的问题"与"知识库文档的表达"尽量对齐：

| 问题形态 | 检索痛点 |
|---|---|
| 口语化（"咋退钱啊"） | 与正式文档用词差异大 |
| 带指代（"它什么时候到？"） | 缺少上下文，检索器无法理解 |
| 模糊（"说说那事"） | 检索意图不明确 |
| 术语多义（"苹果"指公司还是水果） | 语义空间歧义 |

### 边界（重要）

```
查询优化解决"检索前的问题质量问题"
不能解决：知识库没内容、切片切坏了、Embedding 不行
```

2026 年行业共识：查询改写等**不是无脑叠加**——SemEval-2026 参赛系统的实测发现，"领域感知提示、多查询扩展等更复杂策略反而降低性能"；HyDE 也呈现"有时更好"的特性。**一切以评估为准**（01 篇的累积提升表）。

## 2. 查询改写（Query Rewriting）

### 解决什么

把用户问题改写为**检索友好**的查询——补全上下文、统一术语、结构化表达。

### 核心场景：多轮对话指代消解

```text
用户："退款多久到账？"
助手：（回答）
用户："那退货呢？"        ← "那...呢"指代"退款流程"
改写后："退货的流程和到账时间是怎样的？"  ← 可独立检索
```

### 实现方式

| 方式 | 做法 | 适用 |
|---|---|---|
| Prompt 改写 | LLM 按提示词改写 | 快速验证、通用场景 |
| 微调专用模型 | LoRA 微调小模型（如 Qwen-7B） | 高频、延迟敏感、固定领域 |
| 规则改写 | 正则/模板（指代词替换） | 简单场景、零成本 |

### Prompt 改写示例

```python
REWRITE_PROMPT = """把用户问题改写为适合检索的独立查询：
- 补全对话历史中的指代（它/这个/那）
- 用正式、准确的术语表达
- 保持原意，不要添加新信息
- 直接输出改写结果

【对话历史】
{history}

【当前问题】
{query}"""

def rewrite_query(query: str, history: list[str]) -> str:
    prompt = REWRITE_PROMPT.format(history="\n".join(history[-3:]), query=query)
    return generate(prompt, temperature=0)  # 改写要确定性
```

### 改写纪律

| 纪律 | 原因 |
|---|---|
| 只补不增 | 不添加用户没说的信息 |
| 确定性输出 | temperature=0，避免改写本身引入噪音 |
| 按领域调温 | SemEval-2026 实测：技术领域用确定性解码更稳 |
| 先测再上 | 改写可能把好查询改坏——评估验证 |

## 3. Multi-Query 多路查询

### 解决什么

查询模糊、术语多义时，**一个视角检索可能漏**——从多个视角分别检索，合并去重。

### 流程

```
用户问题
  → LLM 生成 3-5 个不同视角的子查询
  → 每个子查询分别检索
  → 合并去重 → 进入重排
```

### 示例

```text
原问题："苹果公司的发展"
子查询 1："Apple Inc. 的发展历史"
子查询 2："苹果公司的市值变化"
子查询 3："苹果的产品线演进"
```

### 实现要点

```python
def multi_query(query: str, n: int = 3) -> list[str]:
    prompt = f"""把问题改写成 {n} 个不同视角的检索查询，覆盖不同表述方式：
原问题：{query}
每个查询一行，直接输出："""
    lines = generate(prompt, temperature=0.7).strip().split("\n")
    return [l.strip() for l in lines if l.strip()][:n]

def retrieve_multi(store, model, query, n=3, k=10):
    queries = [query] + multi_query(query, n)
    results = {}
    for q in queries:
        for r in retrieve(store, model, q, k):
            results[id(r["chunk"])] = r   # 按 chunk id 去重
    return sorted(results.values(), key=lambda r: -r["score"])
```

### 代价与适用

| 维度 | 说明 |
|---|---|
| 成本 | 检索次数 ×(n+1)，LLM 调用 +1 |
| 延迟 | 多路检索可并行（asyncio），LLM 生成为新增延迟 |
| 适用 | 查询模糊、术语多义、覆盖面要求高 |
| 不适用 | 查询精准的简单场景（多路纯属浪费） |

## 4. HyDE 假设文档嵌入

### 解决什么

**查询-文档分布差异**：短查询（几十 token）与长文档（几百 token）在语义空间分布不同，直接检索可能偏差。

### 原理

```
用户问题 → LLM 生成一段"假设答案文档"（Hypothetical Document）
         → 用假设文档的向量检索真实文档
为什么有效：假设文档与真实文档在语义空间更接近（都是"回答型文本"）
```

### 实现

```python
HYDE_PROMPT = """根据问题写一段假设答案（500 字以内），风格像一篇百科条目：
问题：{query}"""

def hyde_retrieve(store, model, query, k=5):
    hypo_doc = generate(HYDE_PROMPT.format(query=query), temperature=0.3)
    # 关键：用假设文档向量检索，不用原查询向量
    qv = model.encode([hypo_doc], normalize_embeddings=True)
    qv = np.array(qv, dtype=np.float32)
    D, ids = store.index.search(qv, k)
    return [store.chunks[i] for i in ids[0] if i != -1]
```

### 实测数据（必须记住的双面性）

| 案例 | 效果 |
|---|---|
| 案例 A：context precision | 0 → 0.80（显著提升） |
| 案例 B：Recall | 0.80 → 0.17（显著恶化） |

结论：

- 研究引用：零样本下 HyDE 比 BM25 提升 +21% nDCG@10（平均意义上）
- **但不是无差别叠加**：只有"词汇不匹配是主要瓶颈"时才值得用
- 判定方法：跑评估，看 HyDE 层在累积提升表上是正是负

### HyDE 使用决策

```
问：词汇不匹配是否是主要瓶颈？
├─ 是（口语化提问 vs 正式文档）→ 值得试 HyDE
├─ 否（查询与文档用词已接近）→ 别用，白花一次 LLM 调用
└─ 不确定 → 评估验证（累积提升表加一层 HyDE 看指标）
```

## 5. 意图路由（Routing）

### 解决什么

不同类型的问题走不同路径——简单问题直答、复杂问题检索、特定问题查特定库：

```text
问题 → 分类器 → 简单问题 → 直接 LLM（省检索）
              → 复杂问题 → RAG 检索
              → 数学问题 → 计算工具
              → 领域问题 → 对应知识库
```

### 路由实现

| 方式 | 做法 | 适用 |
|---|---|---|
| LLM 路由 | 让模型判断问题类型 | 灵活、通用 |
| 分类模型 | 微调小分类器 | 高频、低延迟 |
| 规则路由 | 关键词/正则匹配 | 简单明确 |

### 路由的价值

- **成本优化**：简单问题省掉检索与长上下文（Adaptive RAG 思想）
- **质量提升**：复杂问题走更深的检索流程
- **多库管理**：企业多知识库时按领域分发

## 7. 代价与选型总结

| 技术 | 解决 | 代价 | 何时值得 |
|---|---|---|---|
| 查询改写 | 指代/口语/不完整 | +1 LLM 调用 | 多轮对话场景（几乎必用） |
| Multi-Query | 模糊/多义 | 检索次数×(n+1) | 查询模糊、覆盖要求高 |
| HyDE | 查询-文档分布差异 | +1 LLM 调用 | 词汇不匹配是瓶颈时 |
| 意图路由 | 路径不分 | +分类成本 | 简单问题占比高/多知识库 |

### 2026 年实践共识

```
必用：查询改写（多轮场景）
按需：Multi-Query / HyDE / 路由
原则：先评估后上——查询层技术最容易"看起来有道理但实测负收益"
```

## 8. 改写质量的验证方法

### 为什么要验证改写

改写是"新生成的文本"——它可能引入噪音：

| 风险 | 例子 |
|---|---|
| 改写出错 | 把"苹果（水果）"改写成"苹果（公司）" |
| 添加信息 | 改写时补了用户没说的限定 |
| 丢失信息 | 把关键数字/型号删掉了 |

### 三层验证

| 层 | 方法 | 检查什么 |
|---|---|---|
| 语义保持 | 改写前后 embedding 相似度 | 相似度应 >0.9（语义没变） |
| 检索效果 | 改写前后检索 Top-K 对比 | 改写后应召回更多正确块 |
| 端到端 | 测试集指标对比（01 篇） | 四指标不降 |

```python
def verify_rewrite(original: str, rewritten: str, model) -> bool:
    """语义保持验证：相似度低于阈值视为改写失败，回退原查询"""
    v1 = model.encode([original], normalize_embeddings=True)
    v2 = model.encode([rewritten], normalize_embeddings=True)
    sim = float(v1[0] @ v2[0])
    return sim > 0.9, sim
```

### 回退机制（必须设计）

```
改写失败（相似度低）→ 用原查询检索（不信任改写）
```

这是查询层工程化的安全底线：**改写的价值是概率性的，必须留原查询兜底**。

## 9. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 多轮对话的 RAG 怎么处理？ | 指代消解改写：历史 + 当前问题 → 独立查询 |
| 改写会不会引入错误？ | 会——所以验证相似度 + 原查询兜底 |
| HyDE 原理？ | 生成假设答案文档，用其向量检索（缩小查询-文档分布差） |
| HyDE 有没有坑？ | 有——实测 context precision 0→0.80 和 recall 0.80→0.17 并存，按瓶颈启用 |
| 什么时候用 Multi-Query？ | 查询模糊/多义、覆盖要求高；代价是检索次数×(n+1) |
| 改写模型怎么选？ | 起步 Prompt 改写；高频低延迟场景微调小模型（SemEval-2026 用 LoRA 微调 Qwen-7B） |
| 查询层优化能解决所有检索问题吗？ | 不能——知识库缺失/切片问题/Embedding 问题都解决不了 |

### 面试加分表达

> "查询层我遵循'验证 + 兜底'：改写后做语义保持验证（相似度>0.9），失败回退原查询——因为 2026 年多个评测系统的结论是复杂改写策略可能负收益，安全第一。"

> 🎯 核心要点：查询层优化的本质是"让问题与文档在语义空间更接近"——改写补上下文、多路扩视角、HyDE 换载体、路由定路径。每项都有明确代价，2026 年实测反复证明"更复杂≠更好"；工程上必须配"验证 + 回退"双保险，用评估定取舍。
