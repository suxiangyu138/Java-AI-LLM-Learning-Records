## 1. 数据层调优的三个目标

阶段 2 的切片是"能跑"，阶段 3 的切片要解决三个硬矛盾：

| 矛盾 | 表现 | 数据层解法 |
|---|---|---|
| 定位精度 vs 上下文完整 | 小块定位准但信息碎；大块完整但噪音多 | **父子文档索引** |
| 语义边界 vs 固定长度 | 固定窗口切断语义 | **语义切块** |
| 相关 vs 精确 | 语义相似但部门/时间不匹配 | **元数据过滤** |

数据层调优收益最大的原因：**上游修正一个切片问题，下游检索与生成全部受益**——切片是"一劳永逸"的优化。

## 2. 语义切块的工程化

### 回顾：语义切块原理（阶段 2 的 03 篇）

按段落单元计算相邻语义相似度，相似度低处即主题断点。阶段 3 把它工程化：

```python
def semantic_chunk_engine(text: str, model, threshold: float = 0.55,
                          min_chunk: int = 200, max_chunk: int = 800) -> list[str]:
    """工程化语义切块：主题断点 + 尺寸约束（防止过短/过长）"""
    paragraphs = [p.strip() for p in text.split("\n\n") if p.strip()]
    if len(paragraphs) <= 1:
        return paragraphs or [text]

    vecs = model.encode(paragraphs, normalize_embeddings=True)
    sims = np.array([np.dot(vecs[i], vecs[i + 1]) for i in range(len(vecs) - 1)])

    chunks, current = [], []
    for i, para in enumerate(paragraphs):
        current.append(para)
        cur_len = sum(len(p) for p in current)
        # 断点条件：主题切换 且 已超过最小尺寸；或超过最大尺寸强制断
        if (i < len(sims) and sims[i] < threshold and cur_len >= min_chunk) or cur_len >= max_chunk:
            chunks.append("\n\n".join(current))
            current = []
    if current:
        chunks.append("\n\n".join(current))
    return chunks
```

### 工程化要点

| 要点 | 说明 |
|---|---|
| min_chunk | 防碎片：主题切换但块太短就继续拼 |
| max_chunk | 防巨块：超过上限强制断 |
| threshold 调优 | 低→块大；高→块小（按文档实测） |
| 缓存段落向量 | 同一文档多次切块复用（成本优化） |

### 语义切块的适用边界

| 适合 | 不适合 |
|---|---|
| 结构清晰的长文档（报告/论文） | 短文档（FAQ）——没必要 |
| 主题段落分明的 Markdown | 表格密集内容 |
| 需要按主题聚合检索的场景 | 超大规模（计算成本线性增加） |

## 3. 父子文档索引

### 解决的核心矛盾

```
小块定位准（检索命中精确片段）
大块上下文全（生成有完整语境）
父子索引：检索用小块，生成用大块——两者兼得
```

### 结构

```
父文档（大块 800-1500 字）──┬── 子块 1（200-400 字）
                           ├── 子块 2
                           └── 子块 3
检索命中子块 → 返回父块（或子块+父块）→ 进 Prompt
```

### 实现

```python
class ParentChildStore:
    """父子索引：子块入库检索，命中后取父块"""

    def __init__(self, parent_chunk_size=1000, child_chunk_size=300):
        self.parents: list[dict] = []          # 父块（供生成）
        self.children: list[dict] = []         # 子块（供检索，含 parent_id）
        self.parent_chunk_size = parent_chunk_size
        self.child_chunk_size = child_chunk_size

    def build(self, text: str, title: str):
        """父块切分 → 每个父块再切子块 → 双向建立索引"""
        parents = semantic_chunk_engine(text, model, min_chunk=600, max_chunk=self.parent_chunk_size)
        for pi, parent in enumerate(parents):
            pid = len(self.parents)
            self.parents.append({"text": parent, "meta": {"title": title, "parent_id": pid}})
            # 父块内切子块（递归切分）
            for child in fixed_chunk(parent, self.child_chunk_size, overlap=50):
                self.children.append({"text": child, "parent_id": pid})

    def retrieve(self, query_vec, k=5):
        """检索子块 → 按 parent_id 去重 → 返回父块"""
        _, ids = child_index.search(query_vec, k * 3)      # 多召回子块
        parent_ids = list(dict.fromkeys(self.children[i]["parent_id"] for i in ids[0] if i != -1))
        return [self.parents[pid] for pid in parent_ids[:k]]
```

### 效果与取舍

| 维度 | 普通切片 | 父子索引 |
|---|---|---|
| 检索精度 | 中 | **高**（小块精确命中） |
| 上下文完整 | 中 | **高**（大块提供语境） |
| 存储 | 1 份 | 2 份（父+子） |
| 索引成本 | 1 次向量化 | 约 1.3-1.5 次 |
| 适用 | 通用 | 长文档、知识密集场景 |

> 2026 实践：父子分块被多个生产系统采用（RAG-Chinese-QA 等），是"精度+完整"兼得的主流方案。

## 4. 句子级分块与段落感知

### 句子级分块

- 以句子为最小单元聚合，保证块内句子完整
- 2026 研究结论：**句子级分块 + overlap 几乎无收益**（overlap 主要对固定窗口有意义）
- 适用：FAQ、短问答、实体密集内容

```python
def sentence_chunk(text: str, max_sentences: int = 5) -> list[str]:
    """按句号/感叹号/问号切句，聚合为块"""
    import re
    sentences = re.split(r"(?<=[。！？])", text)
    return ["".join(sentences[i:i + max_sentences])
            for i in range(0, len(sentences), max_sentences)]
```

### 段落感知（保留文档结构）

- Markdown 文档：保留标题层级 → 标题进元数据（section）
- 表格：整表一块，不切断行
- 代码块：整体保留
- 列表：按列表项聚合

### 切片元数据升级

```python
{"text": "...", "meta": {
    "title": "产品手册", "section": "退款政策",
    "parent_id": 12, "page": 3, "updated_at": "2026-08-09"
}}
```

元数据是过滤检索的基础（下节）。

## 5. 元数据过滤

### 解决什么

```
用户问："2025 年的营收是多少？"（只要 2025 年报）
向量检索返回：2024、2023、2026 的报告混杂 → 噪音
元数据过滤：只查 year='2025' 的文档 → 精确
```

### 实现方式

| 方案 | 做法 |
|---|---|
| FAISS（本阶段） | 不支持过滤——按元数据分组建多个索引，或检索后代码过滤 |
| pgvector（生产） | SQL WHERE 过滤（`metadata->>'year' = '2025'`） |
| Milvus | 原生过滤表达式（`year == "2025"`） |

### 代码过滤（FAISS 场景）

```python
def retrieve_filtered(store, model, query, filters: dict, k=5):
    """检索后按元数据过滤（FAISS 无原生过滤时的方案）"""
    results = retrieve(store, model, query, k=50)      # 扩大召回
    filtered = [r for r in results
                if all(r["meta"].get(f_key) == f_val for f_key, f_val in filters.items())]
    return filtered[:k] if filtered else results[:k]   # 过滤为空则回退
```

### 过滤设计原则

| 原则 | 说明 |
|---|---|
| 过滤字段必须进元数据 | 建库时就要规划（阶段 2 的 02 篇） |
| 过滤为空要回退 | 别让过滤把答案全滤掉 |
| 过滤优先于相似度 | 业务约束（时间/部门）先满足，相似度其次 |
| 别过度过滤 | 过滤条件越多，召回越少——只过滤硬约束 |

## 6. 切片参数的系统调优

### 系统调优流程（取代阶段 2 的"拍脑袋"）

```
① 固定测试集（01 篇）
② 扫描 chunk_size：300/500/800/1000
③ 对每个尺寸：重建索引 → 跑评估 → 记录指标
④ 扫描 overlap：0/10%/20%（固定最优 size）
⑤ 选"指标最优 + 成本可接受"的组合
```

### 扫描脚本

```python
def scan_chunk_size(texts, sizes=[300, 500, 800, 1000]):
    for size in sizes:
        # 重建切片 → 重建索引 → 跑评估（01 篇 evaluate）
        metrics = evaluate_with_size(texts, size)
        print(f"size={size}: precision={metrics['context_precision']:.3f} "
              f"recall={metrics['context_recall']:.3f}")
```

### 参数选择的代价约束

| 参数 | 增大的代价 |
|---|---|
| chunk_size | 上下文占用、噪音、索引 token 成本 |
| overlap | 重复 token（2026 研究：句子级切块下几乎无收益） |
| 索引粒度（父子） | 索引成本 1.3-1.5 倍 |

## 8. 切块策略对评估指标的影响

### 不同切块与指标的关系

| 切块策略 | 主要影响指标 | 机理 |
|---|---|---|
| 块太大 | Context Precision 降 | 单块混多个主题，无关部分稀释 |
| 块太小 | Context Recall 降 + Faithfulness 降 | 信息被切断，检索不到完整答案 |
| 父子索引 | 两者都升 | 小块的精度 + 大块的完整 |
| 语义切块 | Precision 升 | 主题内聚，单块噪音少 |
| 句子级 | 实体类问题 Recall 升 | 细粒度定位 |

### 用指标反推切块问题

| 指标异常 | 可能的切块根因 |
|---|---|
| Precision 低 | 块太大 / 主题混杂 |
| Recall 低 | 块太小 / 信息被切断 |
| 答案不完整（Faithfulness 看着高但漏信息） | 关键信息跨块断裂 |
| 特定数字/实体找不到 | 数字/实体被切断（表格/长数字） |

### 切块与评估的闭环流程

```
测试集固定 → 换切块策略 → 重索引 → 跑评估 → 指标对比 → 定方案
```

这正是 01 篇"一次一层"纪律在数据层的应用：**切块实验与检索实验分开做**，指标变化才能归因。

## 9. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 父子文档索引是什么？ | 小块检索（精度）+ 父块生成（完整），命中子块返回父块 |
| 父子索引的代价？ | 索引成本约 1.3-1.5 倍（两份向量化） |
| 什么时候用语义切块？ | 结构清晰长文档、主题段落分明；短文档没必要 |
| 元数据过滤与相似度检索谁优先？ | 业务硬约束（时间/部门）先过滤，相似度其次 |
| 过滤为空怎么办？ | 回退到不过滤（别让过滤滤掉所有答案） |
| 切块参数怎么定？ | 测试集扫描（300/500/800/1000），不是拍脑袋 |
| 句子级切块还要 overlap 吗？ | 2026 研究：几乎无收益 |

### 面试加分表达

> "数据层我做过一次'用指标反推问题'的调优：context precision 一直低，排查发现是块太大主题混杂——换父子索引后 precision 和 recall 同时提升。这类优化是一次性的，收益持续，性价比最高。"

> 🎯 核心要点：数据层调优是"一劳永逸"的——父子索引同时解掉"精度 vs 完整"矛盾，语义切块解"语义边界"，元数据过滤解"相关 vs 精确"。用指标反推切块问题（Precision 低查块大小、Recall 低查信息断裂），按文档类型选方案，用测试集扫描参数。
