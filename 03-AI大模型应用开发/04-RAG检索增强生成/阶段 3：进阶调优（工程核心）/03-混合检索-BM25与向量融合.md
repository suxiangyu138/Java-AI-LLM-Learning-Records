## 1. 为什么纯向量检索不够

### 两类检索的互补性

| 维度 | 向量检索（Dense） | BM25（关键词） |
|---|---|---|
| 匹配方式 | 语义相似 | 词频/词法 |
| 擅长 | 同义改写、语义相关 | 精确词、型号、人名、缩写 |
| 弱点 | 对精确标识符不敏感 | 语义鸿沟（同义不同词） |
| 典型失败 | "RTX5090 参数"匹配到"显卡介绍" | "怎么退款"匹配不到"退费流程" |

### 必须混合的场景（几乎全部）

```
问："这个月销售额怎么算？"（"销售额"精确词 → BM25 强）
问："咱家咋退货？"（口语 → 向量强）
```

**混合检索的意义**：两路互补覆盖"关键词盲区 + 语义鸿沟"，2026 年生产环境**应始终使用混合检索**——因为查询时它几乎零额外成本（BM25 检索极快）。

## 2. BM25 关键词检索

### BM25 是什么

经典词频加权检索算法（BM = Best Matching），是 TF-IDF 的现代替代：

```text
score(q, d) = Σ IDF(t) × [tf(t,d) × (k1+1)] / [tf(t,d) + k1×(1-b+b×|d|/avgdl)]

tf：词频（该词在文档中出现次数）
IDF：逆文档频率（词越罕见越重要）
k1、b：饱和参数（默认 k1=1.5, b=0.75）
```

### 特点

| 特点 | 说明 |
|---|---|
| 零训练 | 无需模型，词频统计即可 |
| 极快 | 倒排索引，毫秒级 |
| 精确 | 对型号/人名/缩写等精确词命中率高 |
| 缺点 | 语义鸿沟——同义不同词匹配不到 |

### Python 实现（rank_bm25）

```python
from rank_bm25 import BM25Okapi
import jieba

# 1. 中文分词（BM25 需要分词）
tokenized = [list(jieba.cut(c["text"])) for c in chunks]
bm25 = BM25Okapi(tokenized)

# 2. 检索
query_tokens = list(jieba.cut(query))
scores = bm25.get_scores(query_tokens)        # 每个 chunk 一个分数
top_ids = sorted(range(len(scores)), key=lambda i: -scores[i])[:k]
```

> 💡 中文 BM25 必须分词（jieba）；英文按空格即可。分词的词表质量直接影响 BM25 效果。

## 3. 混合检索架构

### 标准架构（2026 事实标准）

```
query ──→ 向量检索 top-50 ──┐
     └──→ BM25 检索 top-50 ─┴─→ RRF 融合 → Rerank top-5 → 生成
```

### 关键参数

| 参数 | 建议 | 原因 |
|---|---|---|
| 初召回 K | **50**（不是 10） | 候选池太小会限制重排效果 |
| 融合方式 | RRF（默认 k=60） | 对分数尺度不敏感，无需归一化 |
| 两路输入 | **必须同一分块集合** | 常见错误：两路用不同 chunk |

> ⚠️ 最常见错误：BM25 与向量检索使用**不同的分块集合**——比如向量用了新切片、BM25 用了旧文本。两路必须基于同一份 chunks，否则融合结果错位。

## 4. RRF 融合算法

### RRF（Reciprocal Rank Fusion）公式

```
score(d) = Σ 1 / (k + rank_i(d))

rank_i(d)：文档 d 在第 i 路检索中的排名（1 开始）
k：平滑常数（通常 60）
```

### 为什么用 RRF 不用分数加权

| 方式 | 问题 |
|---|---|
| 分数直接加权（0.5×向量分 + 0.5×BM25分） | 两路分数尺度不同（向量 0-1，BM25 无界），不可直接加 |
| 归一化后加权 | 多一步归一化，分布假设易错 |
| **RRF** | **只看排名不看分数，天然免尺度问题** |

### 实现

```python
def rrf_fusion(dense_ids: list[int], bm25_ids: list[int], k: int = 60) -> list[int]:
    """两路结果按 RRF 融合，返回融合后排序的 id 列表"""
    scores = {}
    for rank, ids in enumerate([dense_ids, bm25_ids]):
        for pos, doc_id in enumerate(ids):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + pos + 1)
    return sorted(scores, key=lambda i: -scores[i])
```

### RRF 的已知问题

> ⚠️ RRF 并非免费：**若两路检索器投票不平衡，融合可能"平均掉"唯一正确的信号**——有实践者发现 naive RRF（各 0.5 权重）反而降级了 BM25 命中的精确匹配结果。解决：权重调优（下节）。

## 5. 权重调优

### 加权 RRF

```python
def rrf_fusion_weighted(dense_ids, bm25_ids, w_dense=0.6, w_bm25=0.4, k=60):
    scores = {}
    for pos, doc_id in enumerate(dense_ids):
        scores[doc_id] = scores.get(doc_id, 0) + w_dense / (k + pos + 1)
    for pos, doc_id in enumerate(bm25_ids):
        scores[doc_id] = scores.get(doc_id, 0) + w_bm25 / (k + pos + 1)
    return sorted(scores, key=lambda i: -scores[i])
```

### 权重选择方法

| 场景 | 建议权重（BM25:Dense） | 理由 |
|---|---|---|
| 通用问答 | 40:60 | 语义为主，关键词兜底 |
| 产品型号/编号密集 | 60:40 | 精确词是主信号 |
| 口语化咨询 | 30:70 | 语义为主 |
| 不确定 | 50:50 起步，评估微调 | 用测试集扫权重 |

### 权重扫描实验

```python
for w_bm25 in [0.3, 0.4, 0.5, 0.6, 0.7]:
    w_dense = 1 - w_bm25
    fused = rrf_fusion_weighted(...)
    metric = evaluate_retrieval(fused, testset)   # 01 篇评估
    print(f"w_bm25={w_bm25}: context precision={metric:.3f}")
# 取指标最高的权重组合
```

## 6. 工程实现

### 方案一：rank_bm25 + FAISS（纯 Python）

```python
class HybridRetriever:
    def __init__(self, store, bm25, w_dense=0.6, w_bm25=0.4, top_k=50):
        self.store = store
        self.bm25 = bm25
        self.w_dense, self.w_bm25 = w_dense, w_bm25
        self.top_k = top_k

    def retrieve(self, query, final_k=5):
        # 向量路
        qv = model.encode([query], normalize_embeddings=True)
        _, ids = self.store.index.search(np.array(qv, dtype=np.float32), self.top_k)
        dense_ids = ids[0].tolist()
        # BM25 路
        scores = self.bm25.get_scores(list(jieba.cut(query)))
        bm25_ids = sorted(range(len(scores)), key=lambda i: -scores[i])[:self.top_k]
        # RRF 融合
        fused = rrf_fusion_weighted(dense_ids, bm25_ids, self.w_dense, self.w_bm25)
        return [self.store.chunks[i] for i in fused[:final_k]]
```

### 方案二：pgvector + 全文检索（生产）

```sql
-- PostgreSQL：向量 + 全文检索 一体（pg_trgm 支持中文模糊）
SELECT content,
       ts_rank(to_tsvector('simple', content), plainto_tsquery('simple', ?)) AS bm25_score,
       1 - (embedding <=> ?::vector) AS vec_score
FROM document_chunks
WHERE content ILIKE '%' || ? || '%'          -- 精确词兜底（可选）
ORDER BY (1 - (embedding <=> ?::vector)) * 0.6
       + ts_rank(...) * 0.4 DESC              -- 或应用层 RRF
LIMIT 50;
```

### 方案三：Elasticsearch（混合检索一体）

- ES 8.x 原生支持 BM25 + dense_vector + RRF（`rank: { rrf: {...} }`）
- 已有 ES 业务的优先方案

## 8. 中文 BM25 的细节与坑

### 中文分词是前提

BM25 基于"词"统计，中文必须分词：

| 分词器 | 特点 | 适用 |
|---|---|---|
| jieba | 通用中文分词，默认词典 | 通用场景（起步） |
| jieba + 自定义词典 | 加入业务词（产品名/术语） | 业务关键词场景 |
| 专业分词（LTP/THULAC） | 更准确但更重 | 领域精度要求高 |
| 字符级 n-gram | 不分词直接按 n-gram | 专有名词保护 |

### 常见坑

| 坑 | 现象 | 对策 |
|---|---|---|
| 不分词直接用 BM25 | 中文检索效果差 | 必须分词 |
| 业务词被切碎 | "深度学习"被切成"深度/学习" | 自定义词典 |
| 查询与文档分词器不一致 | 词不一致匹配不到 | 两端必须同分词器 |
| 停用词未处理 | "的/了/是"占据词频 | 加停用词表 |
| 词典版本漂移 | 新业务词未加 | 词典随业务更新 |

### 自定义词典示例

```python
import jieba
jieba.load_userdict("domain_words.txt")   # 每行一个词：深度学习 等

# domain_words.txt 内容示例
BGE-M3
火山引擎
混合检索
```

### BM25 参数（k1、b）

| 参数 | 默认 | 调大 | 调小 |
|---|---|---|---|
| k1（词频饱和） | 1.5 | 词频影响更大 | 词频影响更小 |
| b（长度归一化） | 0.75 | 长文档惩罚更重 | 长度影响更小 |

实际经验：默认参数 80% 场景够用，用测试集扫描确认即可（b 调小对中文长文档有时有正收益）。

## 9. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 为什么纯向量检索不够？ | 语义好但精确标识符弱（型号/人名/缩写）；BM25 互补 |
| BM25 原理？ | 词频 + 逆文档频率加权，关键词匹配 |
| RRF 为什么不用归一化？ | 只看排名不看分数，免尺度问题 |
| 权重怎么定？ | 场景分析起步（型号密集 60:40）+ 测试集权重扫描 |
| 混合检索的常见错误？ | 两路不同分块集合；初召回太小；不看评估直接上线 |
| 中文 BM25 注意什么？ | 分词 + 自定义词典 + 两端同分词器 |
| 混合检索性能？ | BM25 毫秒级，总增量可忽略——生产必配 |

### 面试加分表达

> "混合检索是我们性价比最高的一层：查询时几乎零额外成本，但把精确词召回问题解决了——测试集上 recall 从 0.55 到 0.75。关键是两路必须用同一份分块集合，否则融合会错位。"

## 10. 混合检索的边界与演进

### 混合检索解决不了什么

| 边界 | 说明 |
|---|---|
| 知识库本身没内容 | 检索再混合也召不回不存在的知识 |
| 切片切坏了 | 信息被切断，两路都命中不了 |
| 查询语义完全错位 | 改写层的事（02 篇），不是混合能救的 |
| 排序质量 | 混合只负责"召回有"，"排得准"交给 Rerank |

### 与检索技术演进的衔接

| 方向 | 与混合检索的关系 |
|---|---|
| 稀疏向量（SPLADE 等） | 学习式稀疏表示，替代纯 BM25（阶段 4 可探索） |
| 多路召回扩展 | 元数据过滤 + 父子索引都算"更多路"（05 篇） |
| 图检索（GraphRAG） | 实体关系召回，与向量/关键词正交（阶段 4） |
| 向量库原生混合 | Milvus/ES 已内置 BM25+向量融合（生产简化） |

### 实验结论沉淀（累积提升表的一行）

```
混合检索层：
  收益：recall 0.55 → 0.75（精确词场景显著）
  代价：检索延迟 +20ms
  保留：是（零额外成本的召回保障）
```

> 🎯 核心要点：混合检索是 2026 年**生产必配**（零额外成本 + 互补收益）；RRF 免尺度融合 + 权重按场景调；两路必须同一分块集合；初召回 50 起步给 Rerank 留空间；中文场景别忘了分词与自定义词典。它补的是检索层的"召回盲区"，下一步用 Rerank 把"有"变"准"。
