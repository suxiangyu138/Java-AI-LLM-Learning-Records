## 1. 为什么评估必须先于调优

### 没有测量的调优 = 玄学

| 没有评估 | 有评估 |
|---|---|
| "感觉检索变好了" | "context precision 从 0.60 → 0.78" |
| 调了 5 个参数，不知道哪个有效 | 一次一层，指标归因清晰 |
| 上线后用户反馈差才返工 | 上线前 CI 门禁拦截 |
| 技术堆了一大堆，成本爆炸 | 累积提升表只留有收益的层 |

### 一个真实案例（评估的价值）

```
现象：RAG 系统回答总被吐槽"不对"
直觉："模型不行，换个更强的 LLM"
评估后：faithfulness 0.96（生成层没问题），
        context precision 0.60（检索层才是瓶颈）
结论：换 LLM 是浪费钱——瓶颈在检索，该调检索
```

这个案例说明了评估的第一价值：**把"模糊的不满"变成"精确的定位"**。RAG 的失败发生在两个独立环节（检索与生成），不拆开测量，永远不知道钱该花在哪。

### 评估的四个层次

| 层次 | 测什么 | 工具 |
|---|---|---|
| 检索层 | 召回的块准不准 | context precision / recall |
| 生成层 | 答案是否忠于资料 | faithfulness |
| 端到端 | 答案是否切题正确 | answer relevancy / correctness |
| 工程层 | 延迟与成本 | p50/p95、token 消耗 |

## 2. RAGAS 四大核心指标

RAGAS 是开源 RAG 评估框架，2026 年仍是被引用最多的框架。核心是"四指标模式"，全部用 LLM-as-judge 打分：

| 指标 | 衡量 | 计算方式 | 需要真值？ |
|---|---|---|---|
| Faithfulness 忠实度 | 答案是否只反映检索上下文（防幻觉） | 提取答案中的原子声明 → 逐条 judge 判断是否被上下文支持 → 支持数/总数 | 否 |
| Answer Relevancy 答案相关性 | 回答是否切题 | 让 judge 根据答案反写问题 → 与原问题算 embedding 相似度 | 否 |
| Context Precision 上下文精度 | 检索回的 Top-K 中相关块是否排前面 | 按位置逐块评判相关性 | 否 |
| Context Recall 上下文召回 | 标准答案的知识点是否被检索上下文覆盖 | 知识点逐条检查 | **是**（唯一需要 ground truth） |

### 指标含义的直觉理解

| 指标 | 一句话 | 类比 |
|---|---|---|
| Faithfulness | "有没有照着资料说" | 学生有没有抄对书 |
| Answer Relevancy | "答的是不是我问的" | 学生有没有跑题 |
| Context Precision | "有用的资料排前面没有" | 书里有用的页好不好找 |
| Context Recall | "该找的资料找全了没有" | 该带的书带齐没有 |

### 补充指标（按需使用）

| 指标 | 用途 | 特点 |
|---|---|---|
| Answer Correctness | 端到端综合质量（事实准确 + 语义相似加权） | faithfulness 高但 correctness 低 → 检索缺口 |
| Answer Similarity | 纯 embedding 相似度 | 便宜，可作预过滤 |
| Context Entity Recall | 实体级召回（人名/产品/日期） | 实体密集领域（客服/财报） |
| Aspect Critique | 自定义维度（语气/安全/风格） | 按业务自定义 |

## 3. 指标如何定位瓶颈

### 瓶颈定位矩阵

| 指标组合 | 含义 | 调优方向 |
|---|---|---|
| Faithfulness 高 + Precision 高 | 检索准、生成忠 | 可能只是 Recall 不足 → 扩召回 |
| Faithfulness 高 + Precision 低 | **瓶颈在检索** | 混合检索/改写/重排 |
| Faithfulness 低 | **瓶颈在生成** | Prompt 约束/换模型/temperature |
| Relevancy 低 | 答非所问 | 查询理解/问题类型路由 |
| Recall 低 + Precision 高 | 召回不足 | Top-K 扩容/多路召回/父子索引 |
| Recall 高 + Precision 低 | 噪音多 | Rerank/阈值过滤/压缩 |

### 一句话定位法

```
先看 Faithfulness：生成层守不守得住
再看 Precision/Recall：检索层哪一端差
最后看 Relevancy：整体方向对不对
```

## 4. 测试集构建

### 测试集的三要素

| 要素 | 说明 | 数量建议 |
|---|---|---|
| 问题集 | 覆盖真实使用场景的问题 | 起步 30-50 个，扩展 100+ |
| 参考答案 | ground truth（Context Recall 需要） | 每个问题一条 |
| 期望来源 | 答案应出自哪篇文档/哪个片段 | 每个问题标注 |

### 三种构建方式

| 方式 | 做法 | 适用 |
|---|---|---|
| 人工整理 | 从真实咨询/工单中挑选问题 + 人工写答案 | 最可靠，起步必做 |
| 合成生成 | 用 TestsetGenerator 按文档自动生成问答对 | 量大、快，需人工策展 |
| 混合 | 人工种子 + 合成扩充 + 人工审核 | 推荐 |

### 合成生成的比例建议

```
TestsetGenerator 按比例生成：
简单题（直接抽取）50%
推理题（需要综合多句）25%
多文档关联题 25%
```

**合成后必须人工策展**：删掉劣质问题、修正参考答案——合成集直接上评估会污染结论。

### 测试集维护

- 每次知识库更新后复查：旧问题是否仍适用
- 新业务场景出现 → 扩充测试集
- 测试集是资产：与代码同库管理（git 管理）

## 5. 基线评估流程

### 标准流程（六步）

```
① 构建测试集（30-50 问 + 参考答案）
② 跑当前系统（阶段 2 的 rag.py 即基线）
③ 记录四指标 + 延迟 + 成本
④ 保存为基线（baseline.json）
⑤ 每次调优后重跑对比
⑥ 只接受"指标变好 + 归因清晰"的改动
```

### 最小评估脚本（自实现四指标思路）

```python
def evaluate(system, testset, judge_model="deepseek-chat"):
    """对测试集跑评估，输出四指标均值"""
    results = []
    for case in testset:
        retrieval = system.retrieve(case["question"])   # 检索结果
        answer = system.ask(case["question"])            # 生成答案
        results.append({
            "question": case["question"],
            "retrieved": [r["text"] for r in retrieval],
            "answer": answer,
            "golden": case.get("reference"),             # 参考答案（可选）
        })
    # 四指标计算：faithfulness/relevancy 用 LLM judge，
    # precision/recall 基于检索结果与 golden 比对
    return compute_metrics(results, judge_model)
```

> 💡 生产直接用 RAGAS 库（`pip install ragas`）；理解其计算原理后，自实现也能得到同样有效的结论——关键是"先测再调"的流程，不是工具本身。

## 6. 评估的已知陷阱

| 陷阱 | 说明 | 对策 |
|---|---|---|
| 同族模型互评虚高 | GPT-4 评 GPT-4 得分虚高 5-12 分 | 跨模型家族评判 |
| judge 版本漂移 | 不同版本评分不一致 | 固定版本 + temperature=0 |
| 衡量内部一致性而非正确性 | 忠实于"错误资料"也能得高分 | 配合 Context Recall（有真值） |
| RAGAS 不测延迟 | 只测质量 | 单独加 p50/p95 监控 |
| 评估成本 | 每 case 0.01-0.05 美元 | 用便宜模型 judge + 控制测试集规模 |
| 测试集过小 | 30 问以下波动大 | 起步 30-50，目标 100+ |
| 只跑一次 | 单次波动 | 每轮调优跑 2-3 次取均值 |

### 评估可信度的三个保证

1. **测试集稳定**：同一份测试集贯穿所有实验
2. **judge 固定**：同版本、temperature=0
3. **多次取均值**：关键结论跑 2-3 次

## 7. CI 门禁与持续评估

### 2026 年实践：RAGAS 进 CI

```
每次 PR → 跑测试集评估 → 指标低于阈值 → CI 失败 → 阻止合并
```

| 指标 | 建议初始阈值（示例） |
|---|---|
| Faithfulness | 0.85 |
| Answer Relevancy | 0.80 |
| Context Precision | 0.80 |
| Context Recall | 0.75 |

> ⚠️ 阈值从当前基线设定，不要凭空拍——先跑基线，再在基线上定目标值。

### 生产环境的持续监控

| 层次 | 监控内容 | 频率 |
|---|---|---|
| 推理层 | 四指标漂移（ARES 校准 judge） | 每周 |
| 检索层 | precision_k / recall_k / mrr_k / ndcg_k | 每次发布 |
| 索引层 | 内容审核时间、所有权覆盖、血缘完整性、schema 时效 | 持续 |
| 工程层 | p50/p95 延迟、token 成本 | 实时 |

## 8. 评估工具生态

### 主流框架对比（2026）

| 框架 | 特点 | 适用 |
|---|---|---|
| RAGAS | 四指标开源标准，LLM-as-judge | CI 门禁（每次 PR） |
| ARES | 带置信度的校准 judge | 生产环境每周漂移检测 |
| TruLens | 可视化评估 + 反馈回路 | 调试与演示 |
| DeepEval | 集成 RAGAS 指标 + 测试框架 | 工程化测试 |
| Phoenix | 可观测性平台内置评估 | 全链路观测 |

### 2026 年推荐组合

```
开发期：RAGAS（本地模型 judge，零成本迭代）
CI 门禁：RAGAS（跨家族 judge，temperature=0）
生产监控：ARES（校准置信度，每周漂移检测）
```

### 本地模型 judge（隐私与成本）

```
RAGAS 可搭配 Ollama 本地模型运行评估：
- 数据不出内网（合规）
- 零成本迭代（调优期每天跑）
- 注意：本地模型 judge 精度略低于旗舰 API
```

### 评估成本控制

| 手段 | 效果 |
|---|---|
| 测试集控制在 50-100 问 | 成本与波动平衡 |
| 用便宜模型 judge（gpt-4o-mini 档） | 每 case 0.01-0.05 美元 |
| 分层评估 | 检索指标（免费）先跑，生成指标（LLM judge）后跑 |
| 失败抽样 | 只对失败 case 深挖，不全量重复 |

## 9. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 怎么评估 RAG 系统？ | 四指标拆检索/生成两层 + 测试集 + LLM-as-judge |
| 为什么 RAG 评估难？ | 无单一标准答案；衡量"内部一致性"而非"外部正确性" |
| 没有参考答案怎么评估？ | 三个指标 reference-free；Context Recall 需要真值，可用合成生成 |
| LLM 自己评自己靠谱吗？ | 有陷阱——同族互评虚高 5-12 分，要跨家族 + 固定版本 + 温度 0 |
| 调优怎么证明有效？ | 基线 → 逐层 → 累积提升表，指标对比为证 |
| 上线后怎么防退化？ | CI 门禁 + 每周漂移检测 + 索引层治理监控 |
| 评估成本高怎么办？ | 分层评估 + 便宜 judge + 控制测试集规模 |

### 面试答题模板

> "我评估 RAG 用 RAGAS 四指标：faithfulness 和 relevancy 管生成层（LLM judge，不需要真值），context precision 和 recall 管检索层（recall 需要参考答案，我用合成生成+人工策展）。每轮调优都在固定测试集上跑基线对比，用累积提升表逐层决策——比如我们实测 HyDE 负收益就直接撤掉了。"

> 🎯 核心要点：**没有测量就没有调优**——RAGAS 四指标把质量拆到检索层与生成层，先量基线再动手，一次只改一层，只留有收益的改动。评估不是"上线的负担"，是"调优的指南针"：工具选型按 2026 组合（RAGAS 进 CI + ARES 做生产漂移），陷阱（同族互评/版本漂移）先记住再上路。
