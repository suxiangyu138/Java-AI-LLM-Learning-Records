## 1. 为什么需要重排序

### 问题的本质

向量检索 + 混合检索是"**粗召回**"——它们用近似方法快速找出候选，排序质量有限：

| 现象 | 原因 |
|---|---|
| Top-5 里混入不相关 | 向量相似≠相关（字面像但语义无关） |
| 正确答案排在第 8 位 | 粗召回排序粗糙 |
| Top-K 太小漏掉答案 | K 太小；K 太大上下文放不下 |

### 重排序解决什么

```
粗召回：Top-50（保证召回，排序粗糙）
精排：  对 50 个候选逐一精细打分 → Top-5（保证精度）
```

一句话：**召回负责"有"，重排负责"准"**——把"能召回"变成"排前面"。

### 关键判断标准（什么时候需要 Rerank）

| 指标形态 | 结论 |
|---|---|
| Recall@50 好，但 Recall@5 差 | **需要 Rerank**（召回够、排序差） |
| Recall@5 已经很好 | 不需要，Rerank 是浪费延迟 |
| Precision@5 差 | 需要 Rerank 或阈值过滤 |

## 2. Bi-Encoder 与 Cross-Encoder 的区别

| 维度 | Bi-Encoder（Embedding 用） | Cross-Encoder（Rerank 用） |
|---|---|---|
| 编码方式 | 查询、文档分别编码 | 查询+文档**拼接后整体编码** |
| 向量化 | 有（存入向量库） | 无（不存向量） |
| 交互 | 无交互，只比向量 | **深度交互**（注意力看到对方全文） |
| 精度 | 中（预排序） | 高（精排） |
| 速度 | 快（可预计算） | 慢（每对都要算） |
| 用途 | 向量库检索 | 对候选对打分排序 |

### 为什么 Cross-Encoder 更准

```
Bi-Encoder：   [查询向量] vs [文档向量] → 余弦相似度（丢失细粒度交互）
Cross-Encoder：[查询 + 文档] 拼接 → 注意力机制整体建模 → 精细相关分
```

Cross-Encoder 能看到"查询的每个词与文档每个词的交互"，精度上限远高于 Bi-Encoder——代价是无法预计算，只能对少量候选实时打分。

## 3. 粗召回 + 精排流水线

### 标准流水线

```
query → 混合检索 Top-50（粗召回）
      → Rerank 逐一打分（50 对）
      → 取 Top-5（精排）→ 进 Prompt
```

### 实现

```python
from sentence_transformers import CrossEncoder

# 加载 Rerank 模型（一次）
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

def rerank(query: str, candidates: list[dict], top_n: int = 5) -> list[dict]:
    """对粗召回候选精排，返回 Top-N"""
    pairs = [[query, c["text"]] for c in candidates]
    scores = reranker.predict(pairs)          # 每个 (query, doc) 对打分
    ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
    return [{"**c": c, "rerank_score": float(s)} for c, s in ranked[:top_n]]
```

### 流水线参数

| 参数 | 建议 | 原因 |
|---|---|---|
| 粗召回 K | 50 | 候选池足够，Rerank 才有意义 |
| 精排 Top-N | 5（或 3-10） | 匹配 LLM 上下文窗口与成本 |
| Rerank 输入 | 两路混合结果 | 先融合再精排（03 篇） |

> ⚠️ 常见错误：粗召回只取 10 个就精排——候选池太小，正确答案可能压根不在池子里，Rerank 再准也排不出来。

## 4. Rerank 模型选型

| 模型 | 参数规模 | 特点 | 适用 |
|---|---|---|---|
| BAAI/bge-reranker-v2-m3 | 568M | 多语言、效果好 | 通用首选（中文友好） |
| BGE-reranker-large | 560M | 英文为主 | 英文场景 |
| BGE-reranker-base | 280M | 轻量 | 资源受限 |
| Cohere Rerank | API | 托管、免部署 | 已用 Cohere 生态 |

### 选型要点

- 中文场景首选 **bge-reranker-v2-m3**（多语言，实测优秀）
- CPU 可跑（50 对约 50-200ms，看硬件）
- Rerank 模型与 Embedding 模型**可以不同**（它们职责不同，不违反一致性铁律）

### 一致性澄清（面试易混点）

| 铁律 | 适用范围 |
|---|---|
| 建库/查询必须同一 Embedding 模型 | Embedding 层 |
| Rerank 模型可独立选 | Rerank 层（与 Embedding 无关） |

## 5. 上下文精炼与压缩

### 为什么需要

即使 Rerank 后取 Top-5，片段也可能冗长、重复、含噪音：

| 问题 | 影响 |
|---|---|
| 片段太长 | 挤占上下文窗口，Token 成本上升 |
| 片段重复 | 同一信息多份拷贝 |
| 含无关句 | 干扰模型聚焦 |

### 三级精炼策略

| 级别 | 做法 | 效果 |
|---|---|---|
| 过滤 | Rerank 分数阈值，砍掉低分片段 | 减少噪音 |
| 截断 | 长片段只保留关键段 | 省 token |
| 压缩 | LLM 将多片段浓缩为要点摘要 | 最省，但多一次调用 |

### 截断实现（最常用）

```python
def refine_context(results: list[dict], max_len: int = 2000) -> str:
    """把 Rerank 后的片段精炼为上下文：超长截断 + 去重"""
    seen, parts = set(), []
    for r in results:
        text = r["text"]
        key = text[:50]                      # 指纹去重
        if key in seen:
            continue
        seen.add(key)
        if len(text) > max_len:
            # 截断：保留首尾（很多关键信息在开头），中间省略
            text = text[:int(max_len * 0.7)] + "……" + text[-int(max_len * 0.2):]
        parts.append(f"[来源:{r['meta'].get('title', '?')}] {text}")
    return "\n\n".join(parts)
```

### 压缩 vs 截断的取舍

| 方式 | 保真度 | 成本 | 适用 |
|---|---|---|---|
| 过滤 | 高 | 零 | 必做 |
| 截断 | 中高 | 零 | 通用默认 |
| LLM 压缩 | 中 | +1 调用 | 片段多、上下文紧张 |

## 6. 延迟与成本控制

### Rerank 的延迟账单

| 环节 | 耗时（CPU 参考） |
|---|---|
| 粗召回（混合） | 10-50ms |
| Rerank 50 对 | 50-200ms（模型与硬件而定） |
| 合计增量 | 50-200ms |

### 延迟优化选项

| 优化 | 效果 |
|---|---|
| 用 base 模型 | 减半延迟，精度略降 |
| GPU 推理 | 10 倍提速 |
| 减少候选（30 而不是 50） | 快 40%，召回略降 |
| 仅对"不确定"查询 Rerank | 折中方案 |

### 成本控制

```
Rerank 是本地模型：无 API 成本（只有算力）
Token 成本：精炼后上下文更小 → 生成成本下降
净效果：Rerank 通常"质量升、成本降"（上下文瘦身）
```

## 8. Rerank 与阈值、压缩的配合

### 完整排序层流水线

```
粗召回 50（混合检索）
  → Rerank 打分
  → 阈值过滤（低于阈值的候选丢弃）
  → 上下文精炼（截断/去重）
  → Top-5 进 Prompt
```

### 阈值与 Rerank 的配合

| 组合 | 效果 |
|---|---|
| Rerank + 阈值 | 分数低于 0.3 的片段直接丢弃（明显无关） |
| Rerank 无阈值 | 前 5 名全进（哪怕都是低分） |
| 阈值无 Rerank | 粗召回分数不靠谱，阈值不可信 |

**经验**：Rerank 分数比粗召回分数更可信，所以阈值要基于 Rerank 分数设定：

```python
def rerank_with_threshold(query, candidates, top_n=5, min_score=0.3):
    """精排 + 阈值：低分候选丢弃，为空则降级返回 top1（避免空上下文）"""
    ranked = rerank(query, candidates, top_n=len(candidates))
    passed = [r for r in ranked if r["rerank_score"] >= min_score]
    return passed[:top_n] or ranked[:1]   # 全被过滤时降级保留一个
```

### 降级策略（防止空上下文）

| 情况 | 降级 |
|---|---|
| 全部低于阈值 | 返回最高分 1 条（别让 Prompt 没资料） |
| 测试集上阈值过严 | 调低阈值，让 Precision/Recall 平衡 |
| 业务要求严格拒答 | 返回空 → Prompt 走"知识库没有"分支 |

## 9. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 为什么 Rerank 更准？ | Cross-Encoder 拼接查询与文档深度交互，Bi-Encoder 只看向量 |
| Rerank 的延迟代价？ | 50 对约 50-200ms（CPU），GPU 10 倍提速 |
| 什么情况不需要 Rerank？ | Recall@5 已达标时（别为高级而叠加） |
| 粗召回 K 为什么取 50？ | 候选池太小正确答案可能不在池内 |
| Rerank 模型与 Embedding 模型要一致吗？ | 不需要——职责不同，可独立选 |
| 上下文太长怎么办？ | 三级精炼：过滤 → 截断 → LLM 压缩 |
| Rerank 实测收益？ | +6% 精度 +10% 召回（2026 实测参考） |

### 面试加分表达

> "我们判断 Rerank 必要性的标准是看 Recall@50 与 Recall@5 的差距——召回够但排序差时才上。上了之后延迟 +100ms，但精度 +10 个点，测试集验证后保留。"

## 10. Rerank 的替代方案与演进

### 什么时候可以不上 Rerank

| 场景 | 替代方案 |
|---|---|
| 查询模式固定 | 规则排序（按元数据优先级） |
| 预算极紧 | 粗召回 + 阈值过滤（牺牲精度） |
| 检索已足够准 | Recall@5 达标——Rerank 纯属浪费延迟 |
| 低延迟强约束（<300ms） | 用小模型或减候选 |

### 排序技术演进路径

| 技术 | 特点 | 位置 |
|---|---|---|
| Bi-Encoder 排序 | 快但粗 | 向量检索（阶段 2） |
| 混合 + RRF | 零成本互补 | 阶段 3（本模块） |
| Cross-Encoder Rerank | 准但慢 | 阶段 3（本模块） |
| 排序模型微调 | 领域定制 | 阶段 4 可探索 |
| LLM 排序（RankGPT） | 最强但最贵 | 高价值场景可选 |

### Rerank 层的决策沉淀

```
判断依据：Recall@50 vs Recall@5 差距
实现：bge-reranker-v2-m3，50 候选精排取 5
代价：+50-200ms（本地模型，无 API 成本）
收益：精度 +6-10%、召回 +10%、上下文瘦身降生成成本
```

> 🎯 核心要点：Rerank 把"召回有"变成"排得准"——Cross-Encoder 精排 50 取 5，+6-10% 精度 +10% 召回；配阈值与降级防"空上下文"；上下文精炼顺带降 token 成本。先看 Recall@50 vs Recall@5 判断是否需要，用评估验证收益，别为"看起来高级"而叠加。
