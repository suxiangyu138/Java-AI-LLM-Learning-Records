## 2. 向量存储生产化

### FAISS → pgvector 的迁移理由

| 需求 | FAISS | pgvector |
|---|---|---|
| 多实例共享 | ❌ | ✅ |
| SQL 过滤 | ❌ | ✅ |
| 事务/备份 | ❌ | ✅ |
| 增量删除 | 麻烦 | ✅（SQL DELETE） |
| 运维成本 | 低 | 低（复用 PG） |

### pgvector 生产配置

```sql
-- 建表（生产 schema）
CREATE TABLE document_chunks (
    id BIGSERIAL PRIMARY KEY,
    content TEXT NOT NULL,
    embedding vector(1024) NOT NULL,
    metadata JSONB NOT NULL DEFAULT '{}',
    doc_id TEXT NOT NULL,
    is_deleted BOOLEAN DEFAULT FALSE,
    updated_at TIMESTAMPTZ DEFAULT now()
);

-- HNSW 索引
CREATE INDEX idx_chunks_embedding
    ON document_chunks USING hnsw (embedding vector_cosine_ops);

-- 增量删除（配合 06 篇）
DELETE FROM document_chunks WHERE doc_id = 'xxx';
```

### 检索 + 过滤 SQL

```sql
SELECT content, 1 - (embedding <=> :query_vec) AS similarity
FROM document_chunks
WHERE metadata->>'year' = '2025'        -- 元数据过滤
  AND is_deleted = FALSE                -- 软删过滤
ORDER BY embedding <=> :query_vec
LIMIT 50;                                -- 粗召回给 Rerank
```

### pgvector 关键配置

| 配置 | 建议 | 说明 |
|---|---|---|
| 索引类型 | HNSW | 召回/速度平衡 |
| 距离函数 | cosine | 文本语义标准 |
| dimensions | 与 Embedding 一致 | 建表时定死，改模型需迁移 |
| 检索并行 | 可加 pgvector 并行扫描 | 大库优化 |

## 3. 三级缓存体系

### 缓存全景

| 级别 | 缓存什么 | 命中收益 | 失效条件 |
|---|---|---|---|
| L1 答案缓存 | 完整问答结果 | 省全部生成成本 | 知识库更新 |
| L2 检索缓存 | Top-K 检索结果 | 省检索+重排 | 知识库更新 |
| L3 Embedding 缓存 | 文本→向量 | 省编码 | 换模型 |

### L1 答案缓存（收益最大）

```python
class AnswerCache:
    """相似问题复用答案——高频问题成本趋近于零"""

    def __init__(self, redis_client, ttl=3600):
        self.redis = redis_client
        self.ttl = ttl

    def get(self, query: str) -> str | None:
        key = self._key(query)
        return self.redis.get(key)

    def set(self, query: str, answer: str):
        self.redis.set(self._key(query), answer, ex=self.ttl)

    def _key(self, query: str) -> str:
        # 归一化后取哈希：大小写/空白归一，相似问题共享缓存
        import hashlib
        normalized = " ".join(query.strip().split()).lower()
        return f"rag:answer:{hashlib.md5(normalized.encode()).hexdigest()}"
```

### 缓存的失效设计（关键）

| 失效策略 | 做法 | 适用 |
|---|---|---|
| TTL 过期 | 定时失效 | 简单、通用 |
| 主动失效 | 知识库更新时清相关缓存 | 政策类（更新即失效） |
| 版本化 key | key 带知识库版本号 | 发布时整体失效 |

### 缓存命中率目标

| 指标 | 目标 |
|---|---|
| 答案缓存命中率 | 30-60%（重复问题多的场景更高） |
| Embedding 缓存命中率 | 90%+（同一批文档重复编码） |

## 4. 成本构成与优化

### RAG 成本构成拆解

| 成本项 | 占比（典型） | 优化手段 |
|---|---|---|
| LLM 生成 | 60-80% | 答案缓存、压缩上下文、便宜模型 |
| Embedding 编码 | 10-20% | 缓存、批量 |
| Rerank 算力 | 5-10% | 本地模型、减少候选 |
| 基础设施 | 5-10% | 按量扩缩 |

### 生成成本优化（大头）

| 手段 | 效果 |
|---|---|
| 答案缓存（L1） | 高频问题成本归零 |
| 上下文精炼（04 篇） | token 减 30-50% |
| 模型分层 | 简单问题走便宜模型 |
| 路由直答（02 篇） | 简单问题免检索免长上下文 |

### 成本核算模板

```python
def estimate_cost(tokens_in, tokens_out, price_in, price_out):
    """单次请求成本估算"""
    return tokens_in * price_in + tokens_out * price_out

# 典型请求：改写 200 + 检索上下文 2000 + 答案 500
# 成本 = 2700 × 输入单价 + 500 × 输出单价
```

| 监控 | 内容 |

| 每请求成本 | 均值 + P95 |
| 总成本趋势 | 日/周环比 |

## 5. 延迟预算与性能目标

### 延迟预算分配（P95 目标示例）

| 环节 | 预算（示例） |
|---|---|
| 查询改写 | 100ms（LLM 调用） |
| 混合检索 | 50ms |
| Rerank | 150ms |
| LLM 生成（TTFT） | 1000ms（首字） |
| **总 P95** | **约 1.5-2s** |

### 超预算的优化顺序

```
1. 答案缓存（命中即零延迟）
2. 检索优化（HNSW 参数/索引）
3. Rerank 减候选/换小模型
4. 生成流式输出（首字更快）
5. 改写模型换小（或规则改写）
```

## 9. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| RAG 成本大头在哪？怎么降？ | LLM 生成占 60-80%——答案缓存、上下文精炼、模型分层 |
| 三级缓存是什么？ | L1 答案 / L2 检索 / L3 Embedding；L1 收益最大 |
| 缓存失效怎么设计？ | TTL + 主动失效（知识库更新）+ 版本化 key |
| pgvector 为什么优于 FAISS？ | 多实例共享/SQL 过滤/事务/增量删除 |

| 上线前检查什么？ | 质量/性能/成本/数据/可靠性/安全/监控/回归八项 |

### 面试加分表达

> "我们上线前的成本核算：生成占大头，所以先上答案缓存（高频问题成本归零）+ 上下文精炼（token 减 40%）——质量不降的情况下单请求成本降了三分之一。监控上四指标漂移（RAGAS 进 CI + ARES 周检）和 P95 延迟并行盯。"

## 10. 成本优化案例复盘

### 案例：客服知识库的成本瘦身

```
背景：每日 5000 次问答，月成本约 1.5 万元（生成占 80%）

第一轮：答案缓存（Redis，TTL 24h）
  命中率 45% → 生成调用减半 → 月成本约 0.9 万元

第二轮：上下文精炼（截断+去重，token 减 40%）
  未命中请求的输入 token 减 40% → 月成本约 0.6 万元

第三轮：模型分层（简单问题走便宜模型）
  20% 请求降档 → 月成本约 0.5 万元

结果：月成本 1.5 万 → 0.5 万（-67%），质量指标不降
```

### 案例启示

| 手段 | 成本降幅 | 质量影响 |
|---|---|---|
| 答案缓存 | 直接减半生成 | 无（高频重复问题） |
| 上下文精炼 | 输入 token -40% | 略升（噪音减少） |
| 模型分层 | 视降档比例 | 需测试集验证 |
| 检索缓存 | 省检索算力 | 无 |
| 换便宜 Embedding | 省编码费 | 需验证中文效果 |

### 成本优化顺序建议

```
① 答案缓存（收益最大、风险最低）→ 先做
② 上下文精炼（质量还升）→ 必做
③ 模型分层（需验证）→ 谨慎
④ 换模型（效果风险最高）→ 最后
```

> 🎯 核心要点：工程化的本质是"把质量优势转化为成本优势"——缓存让高频问题成本归零、精炼让 token 减半、监控让问题在用户感知前暴露。成本优化按"缓存→精炼→分层→换模型"顺序走，每步用测试集确认质量不降。Java 生产用 Spring Cache + PgVectorStore 落地同一套架构，上线检查清单八项全过，才算真正"可用"。
