## 1. 为什么增量更新是刚需

### 全量重建的痛点

| 场景 | 全量重建的问题 |
|---|---|
| 每天新增 100 篇文档 | 每天重向量化整个库（浪费 99% 算力） |
| 单篇文档更新 | 全部重切重向量化 |
| 万亿级大规模 | 重建耗时不可接受 |

### 增量更新的核心

```
只处理变化的文档：
新增 → 只向量化新增部分
修改 → 删旧块 + 建新块
删除 → 只删对应块
```

### 增量更新收益（量化）

| 维度 | 全量重建 | 增量更新 |
|---|---|---|
| 1 万块库 + 100 块新增 | 1 万块全重算 | 只算 100 块 |
| 更新延迟 | 小时级 | **分钟级** |
| 算力消耗 | 100% | 约 1% |

## 2. 增量索引实现

### 文档变更检测

| 方式 | 做法 | 适用 |
|---|---|---|
| 文件时间戳 | 比较 mtime 与上次索引时间 | 简单、本地场景 |
| 内容哈希 | 计算文档哈希，变化则重建 | 更可靠（mtime 可能被改） |
| 数据库 CDC | 监听变更日志（Debezium 等） | 生产、实时流式 RAG |
| 手动触发 | API 主动上报变更 | 可控流程 |

### 实现（哈希 + 元数据）

```python
import hashlib, json

def doc_fingerprint(text: str) -> str:
    """文档内容指纹：内容变化则指纹变化"""
    return hashlib.md5(text.encode("utf-8")).hexdigest()

class IncrementalIndexer:
    def __init__(self, store, state_path: str = "index_state.json"):
        self.store = store
        self.state_path = state_path
        # 状态：doc_id → (fingerprint, 向量 id 范围)
        self.state = self._load_state()

    def sync(self, docs: list[dict]):
        """同步文档：新增/修改/删除"""
        current_ids = set()
        for doc in docs:
            fp = doc_fingerprint(doc["text"])
            current_ids.add(doc["doc_id"])
            if self.state.get(doc["doc_id"], {}).get("fp") == fp:
                continue                              # 未变化，跳过
            self._remove_old(doc["doc_id"])            # 删旧块
            new_ids = self._index_new(doc)             # 建新块
            self.state[doc["doc_id"]] = {"fp": fp, "ids": new_ids}
        # 删除已不存在的文档
        for doc_id in set(self.state) - current_ids:
            self._remove_old(doc_id)
            del self.state[doc_id]
        self._save_state()

    def _remove_old(self, doc_id):
        """删除旧块：FAISS 需要重建索引或用 IDMap（生产用 IDMap）"""
        # 简化版：记录待删 id，定期重建；生产用 faiss.IndexIDMap 支持删除
        pass

    def _index_new(self, doc):
        """对新文档切片、向量化、入库，返回新向量 id 列表"""
```

### FAISS 的删除问题（重要）

| 方案 | 做法 | 适用 |
|---|---|---|
| 定期重建 | 累积待删 id，批量时重建索引 | 简单、小库 |
| IndexIDMap | 显式 id 管理，支持 remove_ids | 生产推荐 |
| 标记过滤 | 元数据标记 deleted，检索时过滤 | 最简单但库膨胀 |

## 3. 去重与文档指纹

### 为什么必须去重

| 重复来源 | 危害 |
|---|---|
| 同一文档多版本导入 | 旧版误导检索 |
| 多源重复（官网+内部库） | 上下文冗余、来源混淆 |
| 相似文档（版本迭代） | 召回多个近似块，浪费 Top-K |

### 两级去重

```python
def dedup_pipeline(docs: list[dict]) -> list[dict]:
    """两级去重：精确指纹 + 相似度近邻"""
    # 第一级：内容指纹精确去重
    seen, result = set(), []
    for doc in docs:
        fp = doc_fingerprint(doc["text"])
        if fp not in seen:
            seen.add(fp)
            result.append(doc)
    # 第二级：向量相似度近邻去重（可选，代价高）
    # 对入库文本两两算相似度，>0.95 视为重复，保留更新的
    return result
```

### 去重策略

| 策略 | 级别 | 代价 |
|---|---|---|
| 精确指纹 | 必做 | 零 |
| 相似度近邻 | 可选 | O(N²) 向量比较，大库要抽样 |

## 4. 版本管理与过期清理

### 版本管理的目标

```
同一文档多版本并存时：
检索应该命中"当前有效版本"，而不是最旧的或最新的
```

### 方案对比

| 方案 | 做法 | 适用 |
|---|---|---|
| 只保留最新 | 更新时删除旧版本块 | 政策类（旧版无价值） |
| 版本元数据 + 过滤 | 全版本入库，过滤 current=true | 需追溯历史 |
| 版本号排序 | 检索时优先高版本 | 需排序逻辑 |

### 过期清理规则

| 规则 | 说明 |
|---|---|
| 生命周期策略 | 过期文档自动删除（如政策 1 年后失效） |
| 定期审计 | 每月检查"无访问 + 超期"文档 |
| 版本上限 | 每文档最多保留 N 个版本 |
| 清理备份 | 删除前归档到冷存储 |

### 清理与索引层监控（2026 实践）

索引层持续追踪四个信号，任一退化触发审查：

| 信号 | 含义 |
|---|---|
| 内容最后审核时间 | 多久没审过（stale 风险） |
| 所有权覆盖率 | 多少文档无人负责 |
| 血缘完整性 | 来源链是否完整 |
| schema 版本时效 | 元数据格式是否过时 |

> 2026 行业结论："检索到的内容结构正确但值已过期（stale）"是 RAG 系统与业务现实不一致的三大根因之一。

## 5. 知识库治理指标体系

### 治理四维度

| 维度 | 指标 | 目标 |
|---|---|---|
| 新鲜度 | 内容平均审核年龄 | 低于业务可接受值 |
| 完整性 | 覆盖率（应入库/已入库） | 100% |
| 质量 | 重复率、失效率 | 重复 <1% |
| 时效 | 更新延迟（变更→生效） | 分钟级 |

### 治理报告模板

```
知识库治理周报
├── 新增文档：N 篇，增量索引耗时 X 分钟
├── 更新文档：M 篇（含版本变更）
├── 删除/过期：K 篇
├── 重复率：0.8%（目标 <1%）
└── 平均审核年龄：45 天（需关注：>60 天的 X 篇）
```

## 6. 数据管线的自动化

### 标准数据管线

```
文档源（CMS/网盘/数据库）
  → 变更检测（定时轮询 / 事件触发）
  → 加载清洗（阶段 2 的 02 篇）
  → 去重指纹（本节）
  → 切片（05 篇方案）
  → 向量化入库（增量）
  → 状态持久化（index_state.json）
  → 治理报告
```

### 触发方式

| 方式 | 延迟 | 适用 |
|---|---|---|
| 定时轮询（每小时/每日） | 小时级 | 简单、多数场景够用 |
| 事件驱动（webhook/CDC） | 秒-分钟级 | 实时流式 RAG |
| 手动触发 | 按需 | 发布流程内 |

### 调度工具

| 工具 | 场景 |
|---|---|
| cron / 计划任务 | 简单定时 |
| Airflow / Dagster | 复杂管线、依赖编排 |
| 消息队列 + worker | 高吞吐事件流 |
| CI/CD 钩子 | 文档发布即触发 |

### 落地清单

| 项 | 检查 |
|---|---|
| 变更检测 | 哈希指纹（不是 mtime） | ☐ |
| 增量索引 | 只处理变化文档 | ☐ |
| 删除支持 | IndexIDMap 或定期重建 | ☐ |
| 两级去重 | 指纹必做 + 近邻可选 | ☐ |
| 版本策略 | 明确"只留最新"或"过滤" | ☐ |
| 过期清理 | 生命周期规则 + 定期审计 | ☐ |
| 状态持久化 | index_state.json 可恢复 | ☐ |
| 治理报告 | 四维度指标定期输出 | ☐ |

### 验证实验

```
① 新增 10 篇文档 → 检查只索引了 10 篇（日志）
② 修改 1 篇 → 检查旧块删除、新块建立
③ 删除 2 篇 → 检查检索不再返回
④ 重复导入同一篇 → 检查指纹去重
⑤ 更新延迟计时 → 目标分钟级
```

## 8. 数据治理失效案例复盘

### 案例 A：过期政策污染

```
现象：用户问"当前报销标准"，系统回答半年前的旧标准
根因：政策更新后直接替换文档文件，但索引未重建；旧版本块仍在库中
教训：文档变更必须走"变更检测 → 删旧建新"管线，不能只改文件
对策：内容指纹检测 + 增量索引（本节实现）+ 版本元数据 current 标记
```

### 案例 B：重复文档稀释检索

```
现象：同一合同被导入 3 份（不同命名），检索结果重复且来源混乱
根因：无去重机制，导入流程只看文件名不看内容
教训：精确指纹去重是入库必做项（成本为零）
对策：doc_fingerprint 指纹 + 入库前检查
```

### 案例 C：stale 数据无人发现

```
现象：知识库 60% 文档超过 90 天未审核，检索频繁命中过时内容
根因：无治理指标监控，内容失效无人感知
教训：索引层四信号（审核时间/所有权/血缘/schema）必须持续监控
对策：治理周报 + 生命周期清理规则（本节 5/6 节）
```

### 案例复盘方法论

```
每个案例问三句：
① 哪个环节缺了？（变更检测/去重/监控）
② 修复手段是什么？（增量/指纹/治理指标）
③ 如何提前发现？（治理周报/告警）
```

## 9. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 增量更新怎么做？ | 内容指纹检测变化 → 只处理变化文档 → 删旧建新 |
| FAISS 怎么删除向量？ | IndexIDMap 支持 remove_ids；或定期重建 |
| 全量 vs 增量怎么选？ | 万级以下全量可接受；万级以上/高频更新必须增量 |
| 文档重复怎么处理？ | 精确指纹必做；相似度近邻可选（O(N²) 代价） |
| 旧版本文档怎么办？ | 策略三选：只留最新 / 版本元数据过滤 / 版本号排序 |
| 数据治理怎么量化？ | 四维度：新鲜度/完整性/质量（重复率）/时效（更新延迟） |
| "知识实时"为什么是相对的？ | RAG 的实时 = 入库才实时，索引更新延迟决定时效 |

### 面试加分表达

> "我做过一次数据治理复盘：某政策类查询频繁命中旧版本，根因是文档变更没走增量管线。修复后做了两件事——内容指纹驱动的增量索引 + 治理周报（重复率/审核年龄/更新延迟），这类看不见的工程恰恰决定了 RAG 的长期质量。"

> 🎯 核心要点：增量更新把"知识实时"从口号变成现实（分钟级生效），去重与版本管理防止脏数据长期污染。数据治理是"看不见的护城河"——检索质量差时先查治理指标，往往是 stale 数据在捣乱；三个失效案例（过期/重复/无人发现）对应三件必做：增量管线、指纹去重、治理监控。
