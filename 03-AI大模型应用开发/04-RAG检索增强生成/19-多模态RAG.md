## 1. 为什么需要多模态 RAG

**企业文档的现实**（多模态 RAG 的动机）：

```text
企业知识库中的文档形态：
  PDF（含图表/表格/扫描件）
  PPT（版式即信息：标题层级/图示关系）
  扫描件/图片（合同、发票、手写批注）
  电子表格（行列结构）

传统文本 RAG 的问题：
  ① PDF 文本抽取（PyMuPDF 等）→ 表格结构丢失、图表完全丢失
  ② 图表信息（趋势图/流程图/架构图）在文本层不存在
  ③ 版式语义（"第 3 列第 2 行"）被平铺成文本后无法回答

结论：只用文本层 = 丢弃了文档的 30-50% 信息
```

**多模态 RAG 的目标**：让检索系统**直接理解"图像/版式"本身**——问图表、问表格、问扫描件。

> 🎯 **核心要点**：多模态 RAG 的动机 = "**企业文档的模态是混合的**"——只做文本层等于主动丢弃图表/表格/版式信息。2026 年文档智能（DocAI）类应用的核心就是多模态检索。

## 2. 多模态 RAG 的两条路线

| 路线 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 解析转文本**（传统） | OCR/表格解析 → 转文本 → 文本 RAG | 生态成熟、便宜 | 结构/图表信息仍丢失 |
| **B. 视觉检索**（2024+） | 直接对页面图像编码检索 | **保留版式语义**、简单 | 依赖视觉模型、成本略高 |

```text
路线 A 的典型流程：
  PDF → PyMuPDF/OCR（PaddleOCR）→ 表格提取（Camelot）→ 文本块 → 向量库
  局限：图表仍不可检索（"这张图的趋势是什么"答不了）

路线 B 的典型流程：
  PDF 页面 → 渲染为图像 → 视觉编码器（ColPali 等）→ 图像向量 → 向量库
  查询："第二季度哪个产品线增长最快？" → 直接检索到相关页面图像
  → VLM（视觉语言模型）阅读图像回答
```

**2026 年趋势**：路线 B（视觉检索）成熟（ColPali 系列），与路线 A 混合使用——**文本层用文本 RAG（快、便宜）、图表/版式用视觉检索（准、完整）**。

> 🎯 **核心要点**：两条路线的取舍 = "**文本信息占比**"——纯文本文档用 A（省钱）、图表/版式密集用 B（保真）、企业混合文档用 A+B 双索引（路由分发，见 14 模块 Router）。

## 3. ColPali：视觉文档检索

**ColPali（2024，法国 HUR 团队）**——视觉检索的代表作：

```text
核心思想：用视觉语言模型（VLM）直接把"文档页面图像"编码为向量，
  检索时用"查询文本"与"页面图像"匹配 —— 跳过文本抽取！

技术机制：late-interaction（晚期交互）
  查询编码：查询 → token 级向量序列
  文档编码：页面图像 → patch 级向量序列（与 ColBERT 同族）
  匹配：查询每个 token 与文档每个 patch 的最大相似度求和
  → 保留"精确匹配"能力（比整体向量更细粒度）

命名由来：Col = ColBERT 式 late-interaction；Pali = 视觉语言模型（PaliGemma）

家族演进：ColPali → ColQwen2（更强 VLM 底座）→ 多语言/表格增强版本
```

**ColPali 的优势**（为什么跳过文本抽取）：

| 维度 | 文本抽取 RAG | ColPali 视觉检索 |
|------|:------------:|:----------------:|
| 版式/图表 | 丢失 | **保留** |
| 扫描件/低质量 PDF | OCR 错误累积 | 直接视觉理解 |
| 流程复杂度 | 抽取+清洗+切块（易碎） | **页面即块（简单）** |
| 检索粒度 | 文本块 | 页面级（粗，配合重排） |
| 成本 | 低 | 略高（VLM 编码） |

> 🎯 **核心要点**：ColPali 的本质 = "**把'页面图像'当作检索单元**"——跳过 OCR/解析这些"易碎的中间层"，用 VLM 的视觉理解直接匹配。**它对"图表/版式密集文档"是范式级改进**（面试谈多模态检索必提 ColPali）。

## 4. 表格与图表检索

**表格检索的特殊性**（多模态 RAG 的高频难题）：

```text
表格的问题：
  ① 平铺转文本后"行列关系"丢失（"第 3 行第 2 列"无法回答）
  ② 表头/合并单元格/多级表头：解析器经常出错
  ③ 大表格：切块会切断行列结构

三种方案（按投入排序）：
  ① 表格转 Markdown/HTML 后入库（保留结构，文本 RAG 可用）
  ② 表格专用解析（Camelot/Tabula）→ 结构化 JSON 入库
  ③ 视觉检索（ColPali 直接对表格页面检索）+ VLM 读表
  → 生产常见组合：②结构化入库（可查询）+ ③视觉兜底（复杂表）
```

**图表检索的现状**：

```text
图表（趋势图/柱状图/架构图）：
  文本层不存在 → 只能视觉检索（路线 B）
  查询方式："XX 产品线的增长趋势" → 检索图表页面 → VLM 解读
  评估难点：图表的"相关性"人工标注成本高
  → 2026 年：图表检索以"页面级视觉检索 + VLM 解读"为主流
```

> 🎯 **核心要点**：表格/图表的检索 = "**结构化转写（表格可查）+ 视觉兜底（图表必查）**"——表格能用结构化方案（便宜可查询），图表只能走视觉路线（保真）。**"问图表"是检验多模态 RAG 能力的试金石**。

## 5. 多模态 RAG 架构与评估

**2026 多模态 RAG 参考架构**：

```text
文档 → 双通道索引：
  ├── 文本通道：文本抽取 → 文本块 → 文本向量库（dense + BM25）
  └── 视觉通道：页面渲染 → 页面图像 → 视觉向量库（ColPali 系）

查询 → 路由（14 模块）：
  ├── 文本型问题 → 文本通道（快、便宜）
  ├── 图表/版式问题 → 视觉通道（保真）
  └── 混合 → 双通道结果融合

生成：VLM（视觉语言模型）阅读检索到的图像 + 文本回答
  → 支持"看图说话"（多模态 LLM，如 GPT-4o / Qwen-VL / Claude）
```

**多模态 RAG 的评估注意**：

| 维度 | 说明 |
|------|------|
| 检索指标 | 与文本 RAG 相同（Hit Rate/MRR）——但相关性标注要考虑"图像相关性" |
| 生成评估 | faithfulness/answer relevance 同样适用（RAGAS 可复用，见 20 模块） |
| **特有难点** | 图表的"相关性"人工标注主观性高；VLM 读图错误难自动检测 |
| 工程目标 | 检索失败率 <5%（同文本 RAG 的 2026 标准） |

**选型建议**（2026）：

```text
纯文本知识库 → 文本 RAG（别为多模态付费）
图表/扫描件多 → ColPali 视觉通道（路线 B）
混合企业文档 → 双通道 + 路由（A + B）
生成模型要求 → 多模态 LLM（VLM）而非纯文本 LLM
```

> 🎯 **核心要点**：多模态 RAG 的架构 = "**双通道索引（文本 + 视觉）+ 路由分发 + VLM 生成**"——评估与文本 RAG 同框架（RAGAS 复用），特有难点在"图表相关性标注"。2026 年它是**成熟可落地**的方向，不是概念验证。

**多模态 RAG 实战清单**（落地检查表）：

```text
① 文档分析：扫描你知识库的模态分布（纯文本 % / 表格 % / 图表 % / 扫描件 %）
   → 图表+扫描件 > 30% 才值得建视觉通道（否则文本通道够用）
② 文本通道：解析（PyMuPDF/Camelot）→ 结构化块（表格转 Markdown/JSON）
③ 视觉通道：页面渲染 → ColPali/ColQwen2 编码 → 视觉向量库
   （页面级索引：粗但完整——配合 VLM 阅读）
④ 路由：问题含"图表/表格/版面"信号 → 视觉通道（或双通道融合）
⑤ 生成：多模态 LLM（GPT-4o / Qwen-VL / Claude）读图回答
⑥ 评估：文本指标（RAGAS 复用）+ 图表相关性人工抽样标注
⑦ 成本：视觉编码与 VLM 生成比文本贵——路由要"按需走视觉"
```

**常见坑**（多模态 RAG 特有）：

| 坑 | 表现 | 解法 |
|----|------|------|
| 扫描件直接文本抽取 | 乱码/错字 | 先 OCR（PaddleOCR）或走视觉通道 |
| 表格切块切坏 | 行列结构断裂 | 表格转结构化（JSON）再入库，别当文本切 |
| 图表问题走了文本通道 | 答"查不到" | 路由层加"图表信号"判断 |
| 页面级检索过粗 | 一个页面多主题 | 页面内二次定位（VLM 或区域标注） |

**多模态 RAG 的选型决策**（2026 一句话版）：

```text
纯文本文档为主 → 文本 RAG 足够（多模态是浪费）
表格多 → 结构化解析（Camelot → JSON）入库即可
图表/扫描件多（>30%）→ 上视觉通道（ColPali 系）
混合企业文档 → 双通道 + 路由（文本通道为主力，视觉通道按需）
生成必须"看图说话" → 多模态 LLM（VLM）而非纯文本 LLM
```

> 💡 记忆锚：**"问图表"是试金石**——你的系统能回答"这张图的趋势是什么"，才算真正多模态；否则只是"加了 OCR 的文本 RAG"。
