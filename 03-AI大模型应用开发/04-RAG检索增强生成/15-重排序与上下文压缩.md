## 1. Bi-Encoder vs Cross-Encoder

**两种编码架构是检索精度的分水岭**：

```text
Bi-Encoder（检索用）：
  查询编码一次 + 文档预先编码 → 点积/余弦算相似度
  → 快（文档可预计算）、但查询与文档"各自独立编码"→ 精度有限

Cross-Encoder（重排用）：
  查询 + 文档【拼接后一起编码】→ 输出相关度分数
  → 慢（每对都要编码）、但"联合注意力"看到交互 → 精度显著更高
```

| 维度 | Bi-Encoder | Cross-Encoder |
|------|:----------:|:-------------:|
| 编码方式 | 查询/文档独立 | **拼接联合编码** |
| 精度 | 中（语义近似） | **高（精确交互）** |
| 速度 | 快（文档预计算） | 慢（每对实时编码） |
| 用途 | **检索（召回）** | **重排（精排）** |
| 经典 | BGE-M3、OpenAI Embedding | Cohere Rerank、BGE-Reranker |

**为什么 Cross-Encoder 更准**：联合编码让模型能看到"查询中的词"与"文档中的词"的**精确交互**（attention 对齐）——Bi-Encoder 只能比较"两个压缩向量的整体相似度"。

> 🎯 **核心要点**：**检索用 Bi（快）、重排用 Cross（准）**——两级架构是生产 RAG 的标配：先 Bi-Encoder 粗召回（几百毫秒），再 Cross-Encoder 精排（Top-20 → Top-5）。

## 2. 生产级 Reranker 选型

**2026 生产级 Reranker 家族**：

| Reranker | 出品 | 特点 | 部署 |
|---------|------|------|------|
| **Cohere Rerank v3** | Cohere | 商业 API、多语言、行业标准 | API |
| **BGE-Reranker-v2** | BAAI | 开源、中文强、可本地 | 本地/API |
| Voyage Rerank-2 | Voyage AI | 高质量、长文本 | API |
| Jina Reranker v2 | Jina | 开源、效率优化 | 本地/API |
| 自有 Cross-Encoder | 自训 | 领域定制 | 本地 |

**选型决策**：

```text
数据合规/离线 → 开源本地（BGE-Reranker-v2 / Jina v2）
质量优先 + 预算充足 → Cohere Rerank v3（行业标准）
领域特殊（法律/医疗）→ 自训 Cross-Encoder（需要标注数据）
中文为主 → BGE-Reranker-v2（中文基准最优之一）
```

**收益量级**（2025-2026 社区基准）：Cross-Encoder 重排带来 **MRR +5~15 点**（困难集），代价是 **50-150ms 延迟**（Top-20 规模）。

> 🎯 **核心要点**：Reranker 选型 = "**合规决定开源/API，语言决定模型，质量决定品牌**"——BGE 系开源本地是 Java/Python 后端最常见的默认选择（LangChain4j/Spring AI 均有集成）。

## 3. 标准重排模式：召回 20 → 重排 → Top-5

**2026 生产 RAG 的标准检索流水线**：

```text
问题
  → 查询改写（HyDE/Multi-Query，可选）
  → 混合检索（BM25 + Dense，各 Top-10~20）
  → RRF 融合 → 候选 20 条
  → Cross-Encoder 重排 → Top-5  ← 本模块核心
  → 上下文压缩（可选）
  → LLM 生成
```

```python
# 标准实现（伪代码）
def retrieve_and_rerank(question: str) -> list[Document]:
    # ① 混合召回 20 条
    candidates = rrf_fuse(
        bm25_search(question, k=10),
        dense_search(question, k=10)
    )
    # ② Cross-Encoder 重排（打分排序）
    reranked = reranker.rerank(question, candidates, top_k=5)
    # ③ 阈值过滤（可选）
    return [d for d in reranked if d.score >= 0.3]
```

**重排解决的核心问题——Lost in the Middle**：

```text
问题：相关文档在上下文"中间"时，LLM 容易忽视（准确率 75% → 50%）
重排的解法：把最相关的块排到第 1 位 → 消除"中间位置劣势"
+ 附带收益：Token 成本下降（只喂 Top-5 而非 Top-20）
```

**阈值与数量的权衡**：

| 参数 | 参考 | 说明 |
|------|------|------|
| 召回量 | 20-50 | 重排的候选池（太少漏、太多贵） |
| 重排后 TopK | 5-10 | 给 LLM 的上下文量（5 是默认） |
| 阈值 | 0.3-0.4 | 过滤低分（宁可少给，不可乱给） |

> 🎯 **核心要点**：重排的完整收益 = "**精度（+5-15 MRR）+ 位置（缓解 Lost in the Middle）+ 成本（只喂 Top-5）**"——三个收益一次拿到，是 2026 生产 RAG 性价比最高的单点优化。

## 4. 上下文压缩 Contextual Compression

**问题**：检索到的块可能"部分相关"——含大量与问题无关的内容，喂给 LLM 浪费 token 且引入噪声：

```text
块内容："本产品包含 A 功能（详细说明...500字）和 B 功能（...）"
用户问的是 A 功能 → 整个块喂进去，B 功能的 500 字是噪声
```

**Contextual Compression（上下文压缩）**：检索后、生成前，**压缩/裁剪块内容**：

```python
# LangChain 的 ContextualCompressionRetriever 模式
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor

compressor = LLMChainExtractor.from_llm(llm)      # LLM 提取相关片段
compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=retriever                       # 先召回再压缩
)
docs = compression_retriever.invoke(question)      # 返回压缩后的块
```

**压缩的三种策略**：

| 策略 | 做法 | 适用 |
|------|------|------|
| **LLM 提取** | LLM 从块中抽取与问题相关的片段 | 块大噪声多（默认） |
| 片段过滤 | 按句/段切分后过滤低相关片段 | 速度快 |
| **LongLLMLingua** | 专门的长文本压缩模型 | 长上下文场景 |

**压缩的权衡**：

```text
收益：token 减少 50-70%、噪声降低 → 回答质量↑、成本↓
代价：多一次 LLM 调用（延迟 +30-100ms）
决策：块小（<300 token）不压；块大（>500 token）值得压
```

> 🎯 **核心要点**：上下文压缩 = "**喂给 LLM 之前再筛一遍**"——与重排互补：**重排管"哪些块进"（文档级）、压缩管"块里哪些内容进"（片段级）**。2026 年长上下文模型普及后，压缩反而更关键（上下文越贵越要精）。

## 5. 重排的评估：Uplift 视角

**重排的效果必须用"提升量（Uplift）"评估**——对比有无重排：

| 指标 | 定义 | 重排的关注点 |
|------|------|-------------|
| Precision@1 | Top-1 是否相关 | **重排的核心目标（把最优块顶到第 1）** |
| nDCG | 排序质量（位置加权） | 重排是否"重排"了（不只是过滤） |
| **Reranker Uplift** | 有重排 - 无重排 | **重排的真实价值** |
| 延迟增量 | 重排耗时 | 50-150ms 是否可接受 |

```text
Uplift 评估方法：
① 基线：混合检索直接取 Top-5 → 测 Precision@1
② 实验：混合检索 Top-20 → 重排 → Top-5 → 同样指标
③ 差值 = Reranker Uplift（MRR +5~15 的由来）
④ 若 Uplift 接近 0 → 检查：候选池太小？Reranker 与领域不匹配？阈值过高？
```

**重排选型的评估实践**：

```text
多模型对比：同一黄金集上跑 Cohere vs BGE vs Voyage → 选 Uplift 最大的
注意：Reranker 的领域适配差异大（通用基准分高 ≠ 你的领域好）
定期复评：知识库内容变化后重跑评估
```

> 🎯 **核心要点**：重排评估的铁律 = "**只信 Uplift，不信单项分**"——Reranker 的基准分是参考，**你的黄金集上的提升量才是决策依据**（黄金集构建见 20 模块）。

**重排 + 压缩的集成模式**（生产检索管线的完整形态）：

```text
查询
  → 混合检索（BM25 + Dense，各 Top-10~20）
  → RRF 融合 → 候选 20 条
  → Cross-Encoder 重排 → Top-5~10（文档级精选）
  → 上下文压缩（LLM 提取/片段过滤）→ 精简后的片段（片段级精选）
  → 组装上下文 → LLM 生成

注意点：
  ① 重排后阈值过滤（0.3-0.4）——宁可少给不可乱给
  ② 压缩对"块大噪声多"有效；小块（<300 token）可跳过压缩省延迟
  ③ 两者都是"LLM 前处理"——效果用黄金集端到端验证
```
