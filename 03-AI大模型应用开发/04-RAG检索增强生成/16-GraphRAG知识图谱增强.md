## 1. 为什么需要 GraphRAG

**向量 RAG 的"看不见"**：

```text
向量检索的本质：找"语义相似的文本块"——只有"局部视野"

三类问题向量 RAG 搞不定：
① 全局问题："总结一下我们所有客户反馈中提到的共性问题"
   → 需要看全部文档的"整体"，不是某几个块
② 关系问题："哪些供应商同时参与过 A 和 B 两个项目？"
   → 关系分散在多个文档，向量检索拼不出"关系网络"
③ 跨文档聚合："公司三年战略的演变路径"
   → 需要跨文档的实体/事件关联

GraphRAG 的思路：把文档转成"实体-关系图"，用图的全局结构回答
```

**核心差异**：

| 维度 | 向量 RAG | GraphRAG |
|------|:--------:|:--------:|
| 数据结构 | 文本块（向量） | **实体-关系图谱** |
| 查询方式 | 语义相似检索 | 图遍历 + 社区摘要 |
| 视野 | 局部（Top-K 块） | **全局（图谱结构）** |
| 适合 | 单点事实/局部细节 | 全局总结/关系推理 |
| 构建成本 | 低（Embedding） | **高（LLM 实体抽取）** |

> 🎯 **核心要点**：GraphRAG 解决的是"**向量检索的结构盲区**"——语义相似找得到"像的块"，找不到"连起来的关系"。**全局问题用图、局部问题用向量**是选型第一原则。

## 2. GraphRAG 核心架构（微软方案）

**微软 GraphRAG（2024 开源，8 万+ Star）的完整流水线**：

```text
文档
  → ① LLM 实体/关系抽取
       （"张三负责项目A" → 实体：张三、项目A；关系：负责）
  → ② 知识图谱构建（实体-关系图）
  → ③ Leiden 社区检测（图算法：把图分成社区）
  → ④ 社区摘要生成（LLM 为每个社区写摘要）
  → ⑤ 索引完成（两级：实体图 + 社区摘要）
```

```python
# 使用（官方 pipeline 伪代码）
from graphrag.query import GlobalSearch, LocalSearch

# 全局搜索：基于社区摘要（Map-Reduce 聚合）
global_engine = GlobalSearch(llm, community_summaries)
answer = global_engine.search("总结公司三年战略演变")

# 局部搜索：基于实体子图
local_engine = LocalSearch(llm, entity_graph)
answer = local_engine.search("张三负责哪些项目")
```

**关键设计：两级索引**：

```text
第一级：实体-关系图（细粒度）→ Local Search（具体事实/关系）
第二级：社区摘要（粗粒度）→ Global Search（全局总结）

Global Search 的执行：
  社区摘要按相关度排序 → 取 Top 社区 → Map（各社区回答）→ Reduce（综合答案）
  本质：把"全局问题"分解为"多个社区的局部回答"再聚合
```

> 🎯 **核心要点**：GraphRAG 的架构记忆 = "**抽取（实体/关系）→ 图谱 → 社区发现 → 社区摘要**"四步索引 + "**Local（图）/Global（摘要）**"两种查询——两级索引是它能同时处理"具体事实"和"全局总结"的关键。

## 3. Local Search vs Global Search

| 维度 | Local Search | Global Search |
|------|:------------:|:-------------:|
| 数据 | 实体子图（局部） | 社区摘要（全局） |
| 查询类型 | 具体事实/关系 | **全局性/总结性** |
| 例子 | "张三负责什么" | "客户反馈的共性问题" |
| 机制 | 实体链接 → 图遍历 | 社区摘要 Map-Reduce |
| 成本 | 中 | **高（多次 LLM 调用）** |
| 精度 | 高（精确实体） | 中（摘要综合） |

```text
选型判断：
  "XX 的具体信息/关系" → Local Search（便宜、精确）
  "总结/概述/共性/演变" → Global Search（贵、全局）
  ⚠️ 全局问题硬用向量 RAG = 查不到；局部问题硬用 Global = 浪费
```

**与向量 RAG 的协同**（生产常见组合）：

```text
查询 → 路由：
  局部事实 → 向量 RAG（快、便宜）
  全局总结 → GraphRAG Global（贵、全局）
  关系推理 → GraphRAG Local（图遍历）
  混合 → 向量 + 图谱结果融合（RRF/加权）
```

> 🎯 **核心要点**：Local/Global 的区分是 GraphRAG 使用的最关键决策——**"问题问的是'一个点'还是'一整片'"**：点走 Local、片走 Global。路由层（见 14 模块）按此分发。

## 4. 收益数据与适用场景

**实测收益（2024-2025 社区/论文基准，量级参考）**：

| 任务类型 | 相对向量 RAG 的提升 |
|---------|:------------------:|
| Exact-match QA（精确事实） | +23% |
| Multi-hop QA（多跳推理） | +46% |
| 跨文档推理 | +47% |

**GraphRAG 的甜点场景**：

| 场景 | 为什么适合 |
|------|-----------|
| 企业知识库全局问答 | "合规风险共性"类问题需要全局视野 |
| 关系密集型领域（供应链/组织架构） | 实体关系天然是图 |
| 多文档综合（研究报告/尽调） | 跨文档实体关联 |
| 审计与合规 | 实体-事件-责任人链条可追溯 |

**不适用的场景**（成本与收益失衡）：

```text
① 纯单点事实问答（客服 FAQ）→ 向量 RAG 足够
② 文档量小（<100 篇）→ 图谱构建成本 > 收益
③ 知识频繁更新 → 图谱重建成本高（增量索引是痛点）
④ 实时性要求高 → 索引是离线批处理
```

> 🎯 **核心要点**：GraphRAG 的选型判据 = "**问题需要'全局/关系'视野吗 + 文档量够大吗 + 更新不频繁吗**"——三个"是"才值得上 GraphRAG（成本见下节）。

## 5. 成本分析与必要性之争

**成本黑洞**（生产决策必须算的账）：

| 成本项 | 说明 | 量级参考 |
|--------|------|---------|
| **索引构建** | LLM 实体抽取：每块都要 LLM 调用 | **100 万字文档可消耗数十美元 API 费用** |
| 社区摘要 | 每个社区一次 LLM 生成 | 与社区数线性 |
| Global 查询 | Map-Reduce 多次 LLM | 单次查询 $0.1-1 量级 |
| 更新成本 | 文档变化 → 相关图与摘要重建 | 增量索引是痛点 |

**必要性之争（2026 核心争论）**——ACL GEM 2026 论文《Is GraphRAG Needed?》：

```text
关键结论：
① "检索-生成鸿沟"（retrieval-generation gap）：
   扩大检索范围 ≠ 成比例提升生成质量
   → 检索指标会高估高级检索（GraphRAG）的收益
② 全局问题：GraphRAG 显著优于纯向量 RAG ✅
③ 局部问题：混合检索 + 重排通常就够 —— 不必为它付图谱成本 ❌
④ 上下文工程可降低 19%-53% 的 token 消耗（替代部分图谱需求）

工程结论（2026 共识）：
  按场景决策，不盲目上 GraphRAG —— 先评估"问题类型分布"：
  全局问题占比高 → 值得
  以局部问答为主 → 混合检索+重排是更划算的答案
```

> 🎯 **核心要点**：GraphRAG 的决策公式 = "**全局问题占比 × 文档规模 − 构建成本 × 更新频率**"——正数再上。面试答"要不要用 GraphRAG"的标准框架 = 收益数据（+23/46/47%）+ 成本账（数十美元/百万字）+ 必要性研究（局部问题不需要）。

## 6. 轻量替代：LightRAG 等

**GraphRAG 家族的开源演进**：

| 方案 | 特点 | 适用 |
|------|------|------|
| 微软 GraphRAG | 完整（社区摘要 + 双模式） | 全局问题为主的企业场景 |
| **LightRAG** | 轻量图谱 + 增量更新 | 中等规模、更新较频繁 |
| FastGraphRAG | 简化抽取流程（省 token） | 成本敏感 |
| 自建轻量图谱 | 只抽实体-关系，不做社区摘要 | 关系查询为主 |

```text
LightRAG 的取舍：
  不做社区摘要（省 Global 的索引成本）
  支持增量索引（解决"静态图谱跟不上更新"痛点）
  只保留 Local 风格查询（实体/关系检索）
  适用：以"关系查询"为主、成本敏感的中等场景
```

**架构决策建议**（2026）：

```text
场景 A：全局总结为主 → 微软 GraphRAG（完整版）
场景 B：关系查询为主 + 更新频繁 → LightRAG / 自建轻量图谱
场景 C：局部问答为主 → 别上图谱，混合检索 + 重排（15 模块）
场景 D：混合 → 路由层按问题类型分发（向量 + 图谱并存）
```

> 🎯 **核心要点**：GraphRAG 不是"全有或全无"——**LightRAG 等轻量方案用"砍社区摘要、换增量更新"换取成本可控**。选型 = 问题类型 × 成本预算 × 更新频率三个维度打分。
