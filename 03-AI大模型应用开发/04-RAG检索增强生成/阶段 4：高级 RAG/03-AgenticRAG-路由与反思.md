## 1. 从固定流程到自主决策

### 传统 RAG 的结构性局限

| 局限 | 表现 |
|---|---|
| 固定流水线 | 简单问题也走全套检索 |
| 一次检索定终身 | 检索失败无补救 |
| 无路径选择 | 多知识库/多工具不知选哪个 |
| 无自我评估 | 答错了不知道 |

### Agentic RAG 的转变

```
传统：问题 → 固定检索 → 生成
Agentic：问题 → Agent 判断 → 选路径 → 检索/工具 → 生成 → 自评 →（不足）再查
```

### 2026 定位

Agentic RAG 不是"花哨版 RAG"，而是**复杂问题场景的结构性升级**——当问题需要多步、多源、多工具时，固定流水线天然达不到质量上限。

## 2. 核心组件架构

```
┌─────────────────────────────────────┐
│  Agent（决策中枢）                    │
│  ├─ Router：选路径/知识库/工具        │
│  ├─ Planner：拆解多步任务            │
│  ├─ Executor：执行检索/工具调用       │
│  └─ Reflector：自评答案质量          │
├─────────────────────────────────────┤
│  工具层                               │
│  向量检索 / 图检索 / SQL / API / 计算 │
└─────────────────────────────────────┘
```

| 组件 | 职责 | 类比 |
|---|---|---|
| Agent | 整体决策 | 项目经理 |
| Router | 选路径 | 接线员 |
| Planner | 拆解任务 | 排计划 |
| Executor | 执行动作 | 干活的人 |
| Reflector | 检查结果 | QA |

### 五种核心能力（阶段 1 回顾 + 深化）

| 能力 | 说明 |
|---|---|
| 路由决策 | 判断问题类型选知识库/工具 |
| 工具调用 | 检索之外调 API/数据库/计算 |
| 多 Agent 协作 | 专业 Agent 分工再整合 |
| 反思验证 | Self-RAG：评估检索与答案 |
| 迭代优化 | 多轮检索-生成-验证循环 |

## 3. Router 路由决策

### Router 解决什么

| 问题 | 传统做法 | Router 做法 |
|---|---|---|
| 简单 vs 复杂 | 一律全流程 | 简单直答、复杂深查 |
| 多知识库 | 全库检索（噪音） | 按领域分发 |
| 多工具 | 只检索 | 检索/数据库/计算按需 |

### 路由实现

```python
ROUTER_PROMPT = """判断问题类型，输出路由决策（JSON）：
- type: simple | complex | database | math | graph
- target: 直接回答 | 向量检索 | SQL查询 | 计算工具 | 图检索
问题：{query}"""

def route(query: str) -> dict:
    resp = generate(ROUTER_PROMPT.format(query=query), temperature=0)
    return json.loads(resp)   # {"type": "complex", "target": "向量检索"}
```

### 路由的价值量化（Adaptive RAG 思想）

```
复杂问题准确率提升 40%（深度路径）
简单问题成本下降（不走全流程）
```

| 路径 | 触发 | 成本 |
|---|---|---|
| 直接回答 | 简单/模型已有知识 | 最低 |
| 单轮检索 | 常规知识库问题 | 中 |
| 多轮检索 | 复杂/多源 | 高 |
| 工具+检索 | 需要计算/数据配合 | 高 |

## 4. Self-Reflection 反思闭环

### Self-RAG 原理

```
生成答案 → LLM 自评（是否充分？是否有依据？）
  → 充分 → 输出
  → 不充分 → 重写查询 → 再检索 → 再生成
```

### 反思的评估维度

| 维度 | 检查 | 触发再检索 |
|---|---|---|
| 检索充分性 | 上下文是否覆盖问题 | 不足则扩检 |
| 答案依据性 | 答案是否来自上下文 | 无依据则重答 |
| 完整性 | 是否漏了子问题 | 拆分再查 |

### 实现示例

```python
def agentic_retrieve(query, max_rounds=3):
    for round in range(max_rounds):
        results = retrieve(query)
        answer = generate(query, results)
        verdict = reflect(query, answer, results)   # 反思评估
        if verdict["sufficient"]:
            return answer
        query = verdict["rewritten_query"]           # 重写再查
    return answer  # 兜底返回最后一轮
```

### 反思的代价

| 代价 | 说明 |
|---|---|
| LLM 调用数 | 每轮 +2（自评 + 重写） |
| 延迟 | 多轮线性上升 |
| 不确定 | 可能收敛也可能循环（要轮数上限） |

> 关键设计：**必须有轮数上限**（如 3 轮）和超时保护，防止"反思死循环"烧钱。

## 5. 多 Agent 协作模式

### 三种协作模式

| 模式 | 结构 | 适用 |
|---|---|---|
| 主管-下属 | 主 Agent 派子 Agent | 子任务并行 |
| 分工专家 | 领域 Agent 各自检索 | 多领域知识库 |
| 评审制 | 生成 Agent + 评审 Agent | 质量敏感场景 |

### 主管-下属示例

```
主 Agent（拆解）→ 派 3 个子 Agent
  ├─ Agent A：检索财务文档
  ├─ Agent B：检索人事文档
  └─ Agent C：检索产品文档
→ 汇总整合 → 主 Agent 回答
```

### 多 Agent 的代价与适用

| 维度 | 说明 |
|---|---|
| 成本 | 每 Agent 独立上下文，token 翻倍级 |
| 延迟 | 可并行（asyncio）但编排有开销 |
| 适用 | 强多领域问题（跨财务/人事/产品） |
| 不适用 | 单库简单问题（杀鸡用牛刀） |

### 子 Agent 的模型分层（成本优化）

```
检索型子 Agent → 便宜模型（DeepSeek flash 档）
整合/决策主 Agent → 强模型
```

## 6. 成本与不确定性控制

### 成本控制三板斧

| 手段 | 效果 |
|---|---|
| 路由分流 | 简单问题不走 Agent（大头） |
| 轮数上限 | 反思最多 3 轮 |
| 模型分层 | 子任务用便宜模型 |

### 不确定性管理

| 风险 | 对策 |
|---|---|
| 循环不收敛 | 轮数上限 + 超时 |
| 决策错误（路由错） | 路由置信度 + 默认路径兜底 |
| 子 Agent 失败 | 降级（跳过该路，不阻塞整体） |
| 成本不可预测 | 每轮预算检查 + 告警 |

### 适用判断（什么时候上 Agentic）

| 适用 | 不适用 |
|---|---|
| 问题需多步推理 | 简单 FAQ |
| 多知识库/多工具 | 单库精确检索 |
| 用户问题千变万化 | 问题模式固定 |
| 质量优先于成本 | 成本敏感、延迟敏感 |

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| Agentic RAG 与传统区别？ | 固定流水线 → 自主决策：路由/反思/多 Agent |
| Self-RAG 是什么？ | 生成后自评，不足则重写查询再检索 |
| 成本怎么控制？ | 路由分流 + 轮数上限 + 模型分层 |
| 什么时候不该用？ | 简单 FAQ——多轮调用纯浪费 |
| Router 怎么做？ | LLM 分类 + JSON 决策，temperature=0 |
| 反思循环会不会死循环？ | 必须轮数上限与超时保护 |

### 面试加分表达

> "Agentic RAG 我把它当'最后一公里'用：80% 的简单问题走路由直答，只有复杂多源问题才进多轮反思路径——这样既拿到复杂问题的质量上限，又控制整体成本。关键是轮数上限和模型分层。"

## 8. Agentic RAG 的评估与调试

### 评估的特殊性

```
传统 RAG：评估固定流水线（四指标直接适用）
Agentic RAG：路径不固定 → 评估要加两层：
  ① 过程评估：路由对不对？步骤合理吗？
  ② 结果评估：最终答案质量（四指标照用）
```

### 过程指标

| 指标 | 衡量 | 方法 |
|---|---|---|
| 路由准确率 | 问题类型判断对不对 | 路由决策 vs 人工标注 |
| 步骤有效率 | 检索动作是否必要 | 日志分析 |
| 反思收敛率 | 是否在轮数上限内收敛 | 日志统计 |
| 工具成功率 | 工具调用成功比例 | 日志统计 |

### 调试方法

| 问题 | 调试 |
|---|---|
| 路由总错 | 看路由 Prompt 与决策日志，加 few-shot 示例 |
| 反思不收敛 | 轮数上限 + 反思 Prompt 收紧（更明确的标准） |
| 子任务遗漏 | Planner 输出结构化（子任务清单 JSON） |
| 成本超预算 | 日志按轮计费，找最贵的轮次优化 |

### 日志设计（Agentic 必备）

```json
{"query": "...", "route": "complex",
 "steps": [{"action": "retrieve", "target": "db", "cost": 0.001}, ...],
 "rounds": 2, "final_verdict": "sufficient", "total_cost": 0.012}
```

## 9. 失败模式与降级设计

| 失败模式 | 表现 | 降级 |
|---|---|---|
| 路由决策错 | 复杂问题走简单路径 | 路由置信度阈值，低于则走默认深路径 |
| 反思死循环 | 反复重写查询 | 轮数上限（硬）+ 超时（软） |
| 子 Agent 失败 | 某路检索挂掉 | 跳过该路，不阻塞整体 |
| 工具调用错误 | API 返回异常 | 重试一次 → 跳过 → 记录 |
| 成本失控 | 多轮调用超预算 | 每轮预算检查 + 超限走单轮路径 |

### 降级总原则

```
Agentic 的复杂性必须配套"回退阶梯"：
最强路径（多轮 Agent）→ 标准路径（单轮 RAG）→ 缓存/直答
任何一层失败都能安全回退到下一层
```

## 10. 与 GraphRAG 的组合应用

### Agentic GraphRAG（2026 演进方向）

```
Agent（决策层）决定走哪条检索路径：
  ├─ 局部多跳 → 图检索（实体路径）
  ├─ 全局总结 → 社区摘要（Global Search）
  └─ 单事实 → 向量检索
生成 → 反思（不足则重写再查）
```

### 组合的价值

| 能力 | 单独范式 | Agentic GraphRAG |
|---|---|---|
| 路径选择 | 固定 | 按意图自主 |
| 多跳 | 图支持 | 图 + Agent 规划 |
| 全局 | 社区摘要 | 摘要 + 反思修正 |
| 自纠错 | 无 | 反思闭环 |

### 实现架构（LangGraph 参考）

```
状态图节点：
  router（路由）→ planner（规划）
  → graph_retrieve / vector_retrieve（并行检索）
  → generate（生成）→ reflect（反思）
  → 不足：回到 planner（重写查询）
  → 完成：输出
```

### 适用判断

| 适用 | 不适用 |
|---|---|
| 问题兼有多跳+全局+自纠错需求 | 单跳事实（经典 RAG 足够） |
| 有图谱基础设施 | 无图需求 |
| 成本可接受（多轮+图双开销） | 成本敏感 |

> 🎯 核心要点：Agentic RAG = 路由 + 反思 + 多 Agent——用多轮调用换复杂问题质量；与 GraphRAG 组合成 Agentic GraphRAG（2026 演进方向）时，Agent 管"走哪条路"、图管"多跳与全局"、反思管"纠错"；评估加过程指标、设计回退阶梯、成本三板斧是生产前提。
