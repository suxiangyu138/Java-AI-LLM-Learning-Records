## 1. 纯向量检索的天花板

### 为什么复杂问题答不好

| 问题类型 | 纯向量 RAG 的表现 |
|---|---|
| 单事实查询（"X 公司的 CEO 是谁"） | ✅ 好 |
| 跨文档综合（"近三年营收趋势"） | ⚠️ 片段拼凑，缺全局 |
| 多跳推理（"CEO 的母校在哪里"） | ❌ 两跳以上基本失败 |
| 全局总结（"报告的核心论点是什么"） | ❌ 无全局视图 |

2026 年 4 月微软研究院与 LangChain 联合报告《Beyond Vector Search》的量化结论：

```
纯向量 RAG 复杂问答准确率：<45%
引入知识图谱的 GraphRAG：89%+
```

### 失败根因

```
向量检索 = 找"相似的片段"
复杂问题 = 需要"关联的知识"
相似 ≠ 关联：两段文本不相似，但通过实体关系相连
```

例："公司 CEO 的母校"——CEO 与母校的信息散落不同文档、表述不相似，向量检索找不到这条"关系链"。

## 2. GraphRAG 核心原理

### 一句话

把非结构化文档抽成**显式的关系网络**（实体-关系-实体三元组），让检索沿关系路径走，而不是只找相似片段。

### 与向量 RAG 的本质区别

| 维度 | 向量 RAG | GraphRAG |
|---|---|---|
| 知识表示 | 向量（语义空间） | 图（实体 + 关系） |
| 检索方式 | 相似度搜索 | 关系遍历 + 社区检索 |
| 多跳能力 | 弱 | **强（沿关系走）** |
| 全局视野 | 无 | **有（社区摘要）** |
| 构建成本 | 低（向量化） | 高（LLM 抽取） |
| 2026 成本 | 基线 | 已塌缩至接近基线 |

### 核心组件

| 组件 | 作用 |
|---|---|
| 实体提取 | LLM 从文本抽（人名/组织/产品…） |
| 关系提取 | LLM 抽（实体A）-关系->（实体B）三元组 |
| 知识图谱 | 存储三元组网络（Neo4j/NetworkX 等） |
| 社区发现 | Leiden 算法把图划分为社区 |
| 社区摘要 | LLM 为每个社区生成多层级全局摘要 |

## 3. Local Search 与 Global Search

微软 GraphRAG 的两种查询模式：

### Local Search（局部检索）

```
查询 → 匹配实体 → 取实体子图 + 关联文本块 → LLM 回答
适用：具体事实类（"X 公司的政策是什么"）
特点：类似向量检索的"精确查找"，但带上了实体关联上下文
```

### Global Search（全局检索）

```
查询 → 社区摘要 Map-Reduce：
  ① Map：每个社区摘要独立评估相关性
  ② Reduce：汇总相关摘要 → LLM 全局回答
适用：宏观总结类（"报告的核心主题是什么""整体趋势"）
特点：不依赖向量相似度，基于社区摘要的全局视角
```

### 两种模式对比

| 维度 | Local Search | Global Search |
|---|---|---|
| 目标 | 具体事实 | 全局总结 |
| 上下文 | 实体子图 + 文本块 | 社区摘要（多层级） |
| 依赖向量 | 部分 | 不依赖 |
| 成本 | 低 | 高（Map-Reduce 多轮） |
| 解决 | "查一个事" | "看全局" |

> 核心能力：Global Search 首次让 AI 具备回答"整体趋势、跨文档关联"类问题的能力——这是纯向量 RAG 的结构性缺失。

## 4. 构建流程详解

```
文档切片
  → LLM 实体/关系提取（三元组）
  → 构建知识图谱（NetworkX/Neo4j）
  → Leiden 社区发现（模块化聚类）
  → LLM 社区摘要（多层级：社区 → 超社区 → 全局）
  → 查询服务（Local + Global）
```

### 各步骤成本占比（2024 版）

| 步骤 | 成本占比 | 说明 |
|---|---|---|
| 实体/关系提取 | 60-70% | 每片都要 LLM 调用 |
| 社区摘要 | 20-30% | 每社区摘要 |
| 其余 | 10% | 图构建等 |

### 增量更新问题（2024 版痛点）

```
图结构变更（新增文档）→ 社区划分可能大变 → 摘要需要重算
这是早期 GraphRAG 维护困难的原因之一
→ LightRAG 的双层索引解决（下节）
```

## 5. 成本塌缩：LazyGraphRAG 与 LightRAG

### 成本演进（关键数据，面试必背）

| 版本 | 时间 | 索引成本（大语料） | 核心创新 |
|---|---|---|---|
| 微软完整 GraphRAG | 2024 | **约 $33,000** | 社区摘要全量预计算 |
| LazyGraphRAG | 2024 末 | 与纯向量一致 | **摘要延迟到查询时** |
| LightRAG | 2025 | 约 1/6000 | 双层索引 + 免社区摘要 |

1M tokens 语料的 2026 实测：

| 方案 | 索引成本 |
|---|---|
| 微软完整 GraphRAG | $20-40 |
| LightRAG | 约 $0.50 |

### LazyGraphRAG 原理

```
完整版：索引时预计算所有社区摘要（贵）
Lazy 版：索引只建图，查询时按需生成摘要（省）
效果：查询成本比完整版低 700 倍以上，全局搜索质量相当或更优
```

### LightRAG 原理

```
双层索引：图（实体关系）+ 向量（原始文本）并行
跳过社区摘要（最贵的步骤）
查询：关键词 + 实体 + 图遍历 + 向量 多路组合
支持增量更新（不重建全图）
索引 token 成本降低约 6000 倍
```

> 🎯 2026 结论：GraphRAG 从"企业级奢侈品"变成"可负担标配"——新项目用 LazyGraphRAG/LightRAG 起步，完整 GraphRAG 只在需要社区级大规模推理时用。

## 6. 适用场景与边界

### 适用（"图"的价值场景）

| 场景 | 为什么用图 |
|---|---|
| 多跳推理 | "CEO 的母校"类关系链 |
| 跨文档综合 | 多文档实体关联 |
| 全局总结 | 报告核心论点、趋势 |
| 实体密集语料 | 研报、法规、病历 |

### 不适用（"图"是负担）

| 场景 | 为什么不用 |
|---|---|
| 扁平 FAQ | 无实体关系可挖 |
| 单文档问答 | 长上下文就够 |
| 高频低延迟 | 图检索链路更重 |
| 语料快速变化 | 图增量更新复杂（LightRAG 缓解） |

### 2026 决策框架（三问）

```
① 查询形态：查找型（向量）vs 综合型（图）？
② 语料结构：实体关系密集（图）vs 扁平（向量）？
③ 变更频率：静态（图可接受）vs 高频（向量/LightRAG）？
```

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| GraphRAG 解决什么？ | 纯向量答不好的：多跳推理、跨文档综合、全局总结 |
| Local vs Global Search？ | 局部查事实（实体子图）；全局做总结（社区摘要 Map-Reduce） |
| GraphRAG 不是特别贵吗？ | 2024 年 $33,000 → 2026 年塌缩三个数量级：LazyGraphRAG 查询省 700 倍、LightRAG 索引省 6000 倍 |
| 什么时候用 GraphRAG？ | 三问：查询形态/语料结构/变更频率 |
| GraphRAG 的增量更新？ | 完整版难；LightRAG 双层索引支持 |
| 与向量 RAG 是替代关系吗？ | 不是——2026 生产常态是"向量 + 图"混合路由按查询分流 |

### 面试加分表达

> "GraphRAG 的价值在 Global Search——纯向量 RAG 永远答不了'整体趋势'类问题，因为它的知识表示里没有全局视图。2026 年成本塌缩后（LightRAG 索引 $0.50/1M token），多跳场景已经可以无负担地用了。"

## 8. 向量与图混合实践

### 为什么混合

```
2026 生产共识：多数生产栈采用"向量 + 图"混合路由，按查询类型分流
原因：单事实用向量又快又省；多跳/全局才需要图
```

### 混合架构

```
query → Router
  ├─ 单跳事实 → 向量检索（快、省）
  └─ 多跳/全局 → 图检索（准、全）
```

### 混合实现要点

| 要点 | 说明 |
|---|---|
| 路由判定 | LLM 或规则（含多跳关键词/实体关系信号） |
| 双索引 | 向量索引 + 图索引并行维护 |
| 结果融合 | 两路结果 RRF 融合或分流 |
| 评估 | 两路分别建测试集（单跳集/多跳集） |

### 混合的收益

```
成本：单事实不付图的开销
质量：多跳拿到图的准确率
工程：一次维护两套索引（增量管线扩展）
```

## 9. 社区摘要的生成细节

### 为什么需要社区摘要

```
图检索只能拿到"相邻实体"——要回答全局问题，需要"一群实体的主题"视图
Leiden 社区发现：把图划分为模块化社区（内聚的实体群）
社区摘要：LLM 为每个社区生成多层级摘要（社区 → 超社区 → 全局）
```

### 生成方式对比

| 方式 | 做法 | 代价 |
|---|---|---|
| 预计算（完整版） | 索引时全量生成摘要 | 索引贵（$33,000 时代的主因） |
| 延迟生成（Lazy） | 查询时按需生成 | 查询略贵，索引平价 |
| 跳过（LightRAG） | 双层检索替代摘要 | 全局能力略降 |

### 摘要质量影响因素

| 因素 | 说明 |
|---|---|
| 社区粒度 | Leiden 分辨率参数决定社区大小 |
| 摘要模型 | 强模型摘要质量更高 |
| 层级深度 | 多层级支持从粗到细的全局视角 |
| 增量更新 | 社区结构变化 → 摘要失效（LightRAG 缓解） |

## 10. GraphRAG 常见误区

| 误区 | 真相 |
|---|---|
| "GraphRAG 一定更准" | 单事实查询向量更快更省；图的价值在多跳与全局 |
| "必须上完整版" | LightRAG/Lazy 在多数场景更优（成本与增量） |
| "图替代向量" | 生产常态是"向量+图"混合路由 |
| "建图一次搞定" | 增量更新是常态（LightRAG 支持，完整版难） |
| "社区摘要越多越好" | 摘要层级过多 → 成本与噪音上升 |
| "图谱没有安全风险" | AGEA 可黑盒恢复 90% 实体关系 |

### 误区背后的原则

```
每个误区都源于"把一个范式绝对化"：
GraphRAG 是"多跳/全局问题的工具"，不是"所有问题的答案"
评估 + 三问选型，是破除一切误区的唯一方法
```

> 🎯 核心要点：GraphRAG = 显式关系网络 + 社区摘要——Local 查事实、Global 看全局；2026 年成本塌缩三个数量级（LightRAG/LazyGraphRAG）让它从奢侈品变标配；生产常态是"向量+图"混合路由按查询分流；适用判断用"查询形态/语料结构/变更频率"三问；记住六个误区，别把范式绝对化。
