## 1. 多跳推理的量化评测

### IEEE 2026 评测（100 个多跳问题）

| 架构 | 综合得分 | LLM-Judge 评分 |
|---|---|---|
| **LightRAG（混合架构）** | **0.653** | **4.24/5** |
| 微软完整 GraphRAG | 0.551 | 2.89/5 |
| 纯向量 RAG | 0.542 | 2.92/5 |

### 评测结论（颠覆直觉的两点）

| 结论 | 说明 |
|---|---|
| 混合架构 > 纯图架构 | LightRAG（图+向量双层）胜过微软完整 GraphRAG |
| 纯图不是必然赢 | 微软 GraphRAG 在 100 问上仅略超纯向量 |

### 结论的工程含义

```
① "上 GraphRAG"不等于"上微软完整版"——选对变体比选对范式更重要
② 混合（图+向量）是当前多跳问题的最优结构
③ 任何范式都要在自己的测试集上验证（阶段 3 方法论不变）
```

## 2. 实体整合与双层检索：评测揭示的关键

### 支撑多跳推理的两个关键因素

| 关键因素 | 说明 | 为什么重要 |
|---|---|---|
| 实体整合（Entity Consolidation） | 同一实体多种表述合并（"苹果公司"/"Apple Inc."/"AAPL"） | 关系链依赖实体对齐，不合并则链条断裂 |
| 双层级检索 | 关键词/实体层 + 向量层并行 | 精确实体用图，模糊语义用向量，互补 |

### 实体整合的实现

```python
def consolidate_entities(entities: list[str]) -> dict[str, str]:
    """实体归一：别名映射到标准实体（可用 LLM 或规则）"""
    alias_map = {
        "苹果公司": "Apple Inc.",
        "苹果": "Apple Inc.",
        "AAPL": "Apple Inc.",
        "苹果电脑": "Apple Inc.",
    }
    return {e: alias_map.get(e, e) for e in entities}
```

### 落地清单（构建图时）

| 项 | 检查 |
|---|---|
| 实体别名表 | 同实体多表述是否归一 |
| 实体类型标注 | 人/组织/产品/地点（关系抽取需要） |
| 关系类型约束 | 只抽定义好的关系类型（避免噪音） |
| 置信度过滤 | 低置信三元组丢弃或降权 |
| 增量合并 | 新文档的实体是否与旧图合并（LightRAG） |

## 3. Agentic GraphRAG

### 2026 WAIC 共识：下一代范式

2026 年 WAIC 闭门论坛（微软、蚂蚁、LangChain 架构师）共识：**基于 LangGraph 的 Agentic GraphRAG** 成为替代传统 RAG 的下一代标准范式。

### 核心组件

| 组件 | 职责 |
|---|---|
| 知识图谱 | 三元组网络（保留网状拓扑） |
| 社区摘要 | Leiden 模块化 + 摘要（全局视野） |
| **Agentic Router** | Agent 自主决定走局部多跳检索 or 全局社区摘要 |
| **Self-Reflection Loop** | 生成后自评，不充分则重写查询再检索 |

### 与传统 RAG 的能力对比

| 能力 | 传统 RAG | Agentic GraphRAG |
|---|---|---|
| 检索次数 | 一次定终身 | 多步自主规划 |
| 路径选择 | 固定流水线 | 动态路由 |
| 多源组合 | 弱 | 强（先查结构化数据库拿人名，再拿人名去文档检索） |
| 自我纠错 | 无 | 反思闭环 |

### 示例：跨源多跳

```
问题："李总的审批额度是多少？"
Agent 步骤：
① 查结构化数据库 → 拿到"李总 = 财务 VP 李明"
② 拿"李明 + 审批额度"去非结构化文档语义检索
③ 汇总回答 → 反思：额度来源是否权威 → 补检
```

## 4. 图数据库选型

| 方案 | 定位 | 适用 |
|---|---|---|
| NetworkX（内存） | 原型/学习 | 小图、快速验证 |
| Neo4j | 企业图数据库 | 生产主力（LLM 集成层完善） |
| NebulaGraph | 分布式高性能 | 超大图 |
| Memgraph | 内存实时 | 低延迟 |
| PostgreSQL + Apache AGE | PG 扩展 | 已有 PG 生态 |

### 选型决策

```
原型 → NetworkX（零部署）
生产小图 → Postgres + AGE（复用 PG）
生产主力 → Neo4j（生态最成熟）
超大图/高并发 → NebulaGraph
```

### 图存储 vs 关系存储的心智

```
图数据库：为"关系遍历"优化（多跳查询天然高效）
关系数据库：为"条件查询"优化（图遍历要多次 JOIN）
多跳推理是图的甜区——这是选图库的根本理由
```

## 5. 安全风险：图谱提取攻击

### ACL 2026 新威胁（必须知道）

```
攻击：AGEA 框架（新颖性引导探索-利用 + 外部图记忆 + 两阶段提取）
效果：黑盒查询可恢复 GraphRAG 系统高达 90% 的实体与关系
对象：微软 GraphRAG 和 LightRAG 均受影响
```

### 风险等级

| 风险 | 说明 |
|---|---|
| 数据泄露 | 图谱是"浓缩的知识"——窃图 ≈ 窃知识库 |
| 越权访问 | 查询 API 即攻击入口 |
| 预算受限仍可攻击 | 查询预算限制不构成有效防御 |

### 防御方向

| 防御 | 说明 |
|---|---|
| 查询鉴权与限流 | 防批量提取 |
| 图访问白名单 | 只暴露必要实体 |
| 敏感实体标记 | 图谱中标记机密节点，查询过滤 |
| 审计日志 | 检测异常查询模式（大量低重叠查询） |

> ⚠️ 落地提醒：GraphRAG 上线前必须做安全评估——图谱把"文档级知识"浓缩为"实体级知识"，泄露面更大。

## 6. 落地决策框架与步骤

### 三问选型（01 篇回顾）

```
① 查询形态：查找型（向量）vs 综合型（图）
② 语料结构：实体密集（图）vs 扁平（向量）
③ 变更频率：静态（完整版可）vs 高频（LightRAG）
```

### 落地六步

```
① 语料评估：实体密度？多跳需求？→ 决定要不要图
② 变体选择：LightRAG 起步，完整版仅在需要社区级推理
③ 实体整合：别名表 + 类型标注（评测揭示的关键）
④ 混合架构：图 + 向量双层，按查询路由
⑤ 测试集验证：多跳问题集，与纯向量基线对比
⑥ 安全评估：图谱提取攻击防御（5 节）
```

### 成本预算模板

| 项 | 估算 |
|---|---|
| 1M token 索引（LightRAG） | 约 $0.50 |
| 1M token 索引（完整 GraphRAG） | $20-40 |
| 查询成本（Lazy 模式） | 接近向量基线 |
| 存储 | 图 + 向量双层 |

## 8. 落地案例复盘

### 案例：研报知识库的多跳问答

```
背景：券商研报 2 万篇，分析师要"某公司 CEO 背景 + 竞对关系"类多跳问答
基线：纯向量 RAG——单事实 80% 准确，多跳 <40%

第一轮：上 LightRAG（双索引）
  多跳准确率 → 62%（实体未整合，关系链常断）

第二轮：实体整合（别名表 + 类型标注）
  多跳准确率 → 75%（关键提升）

第三轮：混合路由（单跳走向量，多跳走图）
  整体准确率 → 78%，成本比纯图低 40%

结论：实体整合是最大杠杆；混合路由控成本
```

### 案例启示

| 阶段 | 杠杆 |
|---|---|
| 第一步 | 选对变体（LightRAG 而非完整版） |
| 第二步 | 实体整合（评测揭示的关键） |
| 第三步 | 路由分流（成本优化） |

## 10. 图与向量双索引的工程细节

### 双索引的数据流

```
文档 → 实体/关系提取 → 图索引（图谱存储）
     → 向量化 → 向量索引（LightRAG 双层）
两条索引共享同一份文档（一致性约定，类比阶段 3 的"同一分块集合"）
```

### 一致性风险

| 风险 | 表现 | 对策 |
|---|---|---|
| 双索引不同步 | 文档更新只改了向量没改图 | 增量管线统一驱动双索引 |
| 实体与文本错位 | 图里有实体但文本被删 | 删除联动（图节点+向量一起删） |
| 元数据不一致 | 两索引的元数据字段不同 | 共享元数据 schema |

### 同步实现

```python
def sync_document(doc, graph_store, vector_store):
    """一份文档同步进两个索引（增量管线统一入口）"""
    # 1. 更新向量索引（阶段 3 的 06 篇增量逻辑）
    vector_store.upsert_doc(doc)
    # 2. 更新图索引（实体提取 + 节点/边写入）
    triples = extract_triples(doc)
    graph_store.upsert_doc(doc["doc_id"], triples)
    # 3. 删除联动：两边按 doc_id 删除
```

### 运维要点

| 项 | 说明 |
|---|---|
| 状态文件 | 双索引各一份状态（doc_id → 指纹） |
| 重建策略 | 单边损坏可独立重建（从共享文档源） |
| 监控 | 两边 ntotal/节点数对应关系 |

> 🎯 核心要点：多跳场景的最优解是"图+向量混合"（LightRAG 0.653 vs 纯向量 0.542），纯图并不必然赢；实体整合是成败关键（案例中准确率 62%→75%）；双索引必须"统一入口同步、共享元数据 schema、删除联动"，否则一致性风险爆发；Agentic GraphRAG 是 2026 演进方向；上线前必须做安全评估与构建质量检查。
