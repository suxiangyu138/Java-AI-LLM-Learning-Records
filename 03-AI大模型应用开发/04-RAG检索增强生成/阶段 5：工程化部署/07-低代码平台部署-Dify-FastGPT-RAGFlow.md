## 1. 为什么要考虑低代码平台

### 自建的代价

```
自建 RAG 全栈 = 开发 + 部署 + 运维 + 评估 + 迭代
小团队/知识库场景：80% 的工作与业务无关（纯工程）
```

### 平台的收益

| 维度 | 自建 | 平台 |
|---|---|---|
| 上线速度 | 周-月 | 天 |
| 运维成本 | 全自担 | 平台处理 |
| 可视化 | 无 | 拖拽编排 |
| 迭代 | 改代码 | 改配置 |
| 掌控力 | 全掌控 | 受平台限制 |

### 平台的边界（诚实清单）

```
适合：知识库问答、简单 Agent、快速验证业务价值
不适合：深度定制、复杂多步编排、特殊性能要求
选型错误 = 88% 工业 AI 项目困在试点的原因之一
```

## 2. 三平台定位对比

| 平台 | 定位 | 一句话总结 | 开源 | star 量级 |
|---|---|---|---|---|
| Dify | 最成熟的全栈 LLMOps 应用平台 | 做"广度"：应用编排最强 | Apache-2.0 | 45k+ |
| FastGPT | 最轻量的 RAG+Agent 平台 | 做"深度"：知识库主线最稳 | Apache-2.0 | 25k+ |
| RAGFlow | 最强的 RAG 文档处理 | 做"精度"：复杂文档无敌 | Apache-2.0 | 18k+ |

### 定位解读

```
Dify = 应用工厂（工作流/Agent/LLMOps 一体化）
FastGPT = 知识库问答专家（开箱即用、最稳最快）
RAGFlow = 文档解析专家（复杂 PDF/表格/扫描件）
```

## 3. 核心能力对比

### 能力矩阵

| 能力 | Dify | FastGPT | RAGFlow |
|---|---|---|---|
| RAG 能力 | 中 | 中 | **极强**（OCR/表格还原/混合检索/语义路由） |
| Agent 能力 | **极强** | 中 | 基础 |
| 工作流引擎 | **完整**（拖拽/条件/循环） | 基础 | 无 |
| 文档解析 | 弱（复杂表格被切碎） | 中 | **行业领先** |
| 部署难度 | 中（8+ 容器） | **最简单**（2 核 4G） | 较难（依赖多） |
| 二次开发 | Python | Node.js | 无官方 Java SDK |
| 可观测性 | **标杆**（节点级日志/Trace 导出） | 中 | 中 |

### 关键差异解读

```
文档越复杂，RAGFlow 优势越明显：
合同/扫描件/嵌套表格 → RAGFlow
规整 Word/Markdown → 三平台差异可忽略

FastGPT 的 RAG 链路可调参深度最高：
问题预处理/检索策略/重排序/上下文组装/答案生成
五步均为可视化节点，可单独测试与开关
```

## 4. 选型决策树

```
我的场景？
├─ 要做复杂 AI 应用（不止问答）/企业级工程化 → Dify
├─ 知识库问答为主 + 要快要稳
│   ├─ 文档规整 → FastGPT（国内企业首选）
│   └─ 文档复杂（合同/扫描件）→ RAGFlow
├─ 文档解析是核心痛点 → RAGFlow
└─ 中小企业最保险路径：
    先用 RAGFlow 把问答做好
    → 效果达标且需要 Agent 时再引入 Dify
```

### 选型注意

| 注意 | 说明 |
|---|---|
| 先验证再私有化 | 优先试用云服务验证业务价值 |
| 用最烂的文档测试 | 拿 3-5 份最难处理的文档试（非标准文档） |
| 供应商锁定 | 关注开源协议与可迁移性 |
| 双重计费 | 平台费 + 模型 API 费都要算 |
| 信创适配 | 鲲鹏/飞腾等国产化要求 |

## 5. 部署要点与资源需求

### 资源需求对比

| 平台 | 最低配置 | 生产建议 | 说明 |
|---|---|---|---|
| FastGPT | 2 核 4G | 4 核 8G+ | 一键 Compose |
| Dify | 4 核 8G | 8 核 16G+ | 完整部署 8+ 容器 |
| RAGFlow | 较高 | 高（GPU 可选） | 深度解析消耗大 |

> ⚠️ 官方标注的"最低配置"只是勉强启动的下限——并发或大规模向量化时内存指数级增长，**生产按 3 倍以上规划**（04 篇容量逻辑）。

### 各平台部署要点

| 平台 | 要点 |
|---|---|
| FastGPT | docker-compose 一键；需会 Nginx 反代与 PG/Milvus 连接 |
| Dify | 微服务集群（API/Web/Worker/PG/Redis/向量库）；分块上限需改 .env（INDEXING_MAX_SEGMENTATION_TOKENS_LENGTH） |
| RAGFlow | 依赖多、资源高；深度解析管线配置 |

### 公共排障

```
① 容器健康检查三级验证（02 篇）
② 向量库连接问题（PG/Milvus 地址与端口）
③ 模型 API Key 与配额
④ 分块配置（超长文档硬截断）
⑤ 网络（Nginx 反代/跨容器）
```

### Dify 分块硬截断陷阱（必须知道）

```
Dify 默认分块：4000 字符块 + 200 重叠
超长文档超上限 → 硬截断 → 超出部分语义永久丢失且无法召回
对法律合同/技术手册致命！
解决：改 .env 的 INDEXING_MAX_SEGMENTATION_TOKENS_LENGTH
或放弃自动分块，用自定义分隔符/清洗策略
```

## 6. 平台化落地路径

### 中小企业落地三步

```
① 验证：云服务试用（拿最难文档测）
② 私有化：Docker 部署（FastGPT 起步最稳）
③ 扩展：问答达标 → 加 Agent/工作流 → Dify
```

### 省钱自建方案

```
本地服务器 + Docker（Dify/RAGFlow）
+ 本地 Ollama 跑 Embedding
+ DeepSeek/Qwen API（或全本地）
= 数据不出内网 + 成本压到硬件+电费
适合：医疗/金融/政务合规敏感场景
```

### 平台与自建的组合

```
混合路线（务实）：
平台（FastGPT/RAGFlow）处理 80% 标准知识库场景
自建（阶段 2-4 能力）处理 20% 深度定制场景
平台做不了的下钻自建，自建太慢的上平台
```

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| Dify/FastGPT/RAGFlow 怎么选？ | Dify 应用编排 / FastGPT 知识库 / RAGFlow 文档解析 |
| 平台与自建怎么权衡？ | 速度 vs 掌控；小团队平台、深度定制自建 |
| RAGFlow 强在哪？ | 深度文档解析（OCR/表格/扫描件行业领先） |
| Dify 的坑？ | 分块硬截断（超长文档语义丢失）、最低配置是下限 |
| 数据合规场景怎么做？ | 私有化 + 本地模型（Ollama + DeepSeek/Qwen） |
| 平台能替代自建吗？ | 不能全替代——深度定制与性能要求仍需自建 |

### 面试加分表达

> "低代码平台是中小企业 RAG 落地的捷径，但要选对：FastGPT 做知识库问答最稳、RAGFlow 文档解析最强、Dify 应用编排最全。我的建议是先拿公司最难的 3-5 份文档试，验证价值再私有化——平台选型错误是项目困在试点的头号原因。"

## 8. 平台落地实战要点

### 三平台验证矩阵（动手前）

| 验证项 | 方法 |
|---|---|
| 文档解析 | 拿 3-5 份最难文档（合同/扫描件）试 |
| 检索质量 | 20 问测试集，看命中率 |
| 并发能力 | 简单压测（10 并发） |
| 二次开发 | 确认 SDK/API 是否满足 |
| 合规 | 数据是否可不出内网 |
| 成本 | 平台费 + 模型费预算 |

### FastGPT 调优案例（真实参考）

```
场景：300 页产品手册，默认切片 QA 精度 60%
调整：按章节切分 + overlap 100 + BGE reranker
结果：精度提升到 85%
启示：平台也要调优——默认配置不是最优配置
```

### 平台排障常见问题

| 问题 | 排查 |
|---|---|
| 检索不到新文档 | 检查摄取任务是否完成（平台日志） |
| 向量库连接失败 | PG/Milvus 地址端口（跨容器用服务名） |
| 模型调用失败 | API Key/配额/网络 |
| 长文档丢内容 | 分块上限（Dify 硬截断） |
| 中文乱码 | 编码/分词配置 |

### 平台落地的团队分工

| 角色 | 在平台上的工作 |
|---|---|
| 业务人员 | 上传文档、调知识库、看效果 |
| AI 工程师 | 配置 RAG 链路、调参数、评估 |
| 运维 | 平台部署、监控、升级 |
| 管理者 | 验收效果与成本 |

```
平台降低了"开发门槛"，但没降低"设计门槛"：
切片参数、检索策略、评估——阶段 3 的方法论在平台上同样适用
（FastGPT 调优案例已证明：默认配置 ≠ 最优配置）
```

### 平台化的边界判断

```
用平台，如果：
✓ 标准知识库问答为主
✓ 团队无专职 AI 工程
✓ 需要快速验证业务价值
✓ 需求变化频繁（拖拽改比改代码快）

自建，如果：
✓ 深度定制（特殊检索/流程）
✓ 性能要求严苛
✓ 已有工程团队
✓ 平台满足不了的需求占比高
```

> 🎯 核心要点：三平台分工明确（Dify 编排 / FastGPT 知识库 / RAGFlow 解析）；选型先拿最难文档验证（6 项验证矩阵）；部署注意"最低配置是下限 + Dify 分块硬截断"两个坑；平台也要调优（FastGPT 案例：默认 60% → 调优后 85%）；数据合规走私有化 + 本地模型；平台与自建是组合关系，不是替代关系。
