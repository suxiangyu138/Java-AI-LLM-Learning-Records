## 1. 容量规划的方法论

### 核心思路

```
从目标 QPS 出发，逐层反推：
目标 QPS → 每层容量 → 副本数 = 目标 ÷ 单副本容量 × 余量系数
```

### 规划四步

```
① 定目标：稳态 QPS、峰值 QPS（通常为稳态的 3 倍）
② 定基准：每层单副本容量（下表）
③ 算副本：副本数 = 峰值 ÷ 单副本容量
④ 加余量：预留 30%（HPA 响应延迟）
```

### 峰值计算

```
峰值 QPS ≈ 稳态 QPS × 3（行业经验值）
例：稳态 100 QPS → 峰值按 300 QPS 规划
```

## 2. 各层容量基准（2026 实测参考）

| 层 | 容量基准 | 备注 |
|---|---|---|
| 编排服务 | 约 50 QPS / 2-vCPU 副本 | 预留 30% 余量给 HPA |
| 向量库（Qdrant） | 3 节点（ef=128，r6i.xlarge）支撑 10M 向量约 300 QPS | 与向量量/ef 参数相关 |
| Embedding 服务 | 约 1000 QPS / 块 L4 GPU（768 维） | 与维度/批大小相关 |
| LLM 网关 | 约 500 RPS / 1-vCPU Pod | 网关通常不是瓶颈，供应商才是 |

### 基准的使用注意

```
基准是"参考值"不是"保证值"：
- 与模型维度、批大小、硬件型号强相关
- 生产前必须压测校准（06 节）
- 保留 30% 余量的根本原因：基准有偏差
```

## 3. 容量计算实战

### 场景设定

```
目标：稳态 100 QPS 的知识库问答
峰值：100 × 3 = 300 QPS
每请求链路：编排 → Embedding → 向量检索 → LLM 生成
```

### 逐层计算

| 层 | 计算 | 结果 |
|---|---|---|
| 编排服务 | 300 ÷ 50 = 6 副本 × 1.3 | **8 副本**（2-vCPU 各） |
| 向量库 | 300 QPS 需 ≥3 节点 | **3-4 节点** |
| Embedding | 300 ÷ 1000 = 0.3 → 至少 1 | **1 GPU**（余量充足） |
| LLM 网关 | 300 ÷ 500 = 0.6 → 至少 1 | **2 副本**（冗余） |
| LLM 供应商 | 300 QPS 生成并发 | 确认配额（外部瓶颈） |

### 容量规划的产物

```
容量表（交付物）：
┌─────────┬───────┬────────┬──────┬───────┐
│ 层       │ 目标QPS│ 单副本  │ 副本数│ 余量  │
├─────────┼───────┼────────┼──────┼───────┤
│ 编排     │ 300   │ 50     │ 8    │ 30%   │
│ Embedding│ 300   │ 1000   │ 1    │ —     │
│ 向量库   │ 300   │ 100/节点│ 3-4  │ —     │
│ LLM 网关 │ 300   │ 500    │ 2    │ 冗余  │
└─────────┴───────┴────────┴──────┴───────┘
```

## 4. 高可用设计

### 高可用的三个层次

| 层次 | 手段 | 目标 |
|---|---|---|
| 单组件 | 多副本 + 探针 | 单 Pod 挂不影响 |
| 集群 | 多节点 + 亲和/反亲和 | 单节点挂不影响 |
| 区域 | 跨区域故障切换 | 区域级故障可恢复 |

### 反亲和设计（RAG 场景）

```
编排服务副本分散到不同节点：
podAntiAffinity：required 反亲和
（避免同一节点故障全挂）
```

### 有状态服务的高可用

| 服务 | 方案 |
|---|---|
| 向量库 | 分片 + 副本（Qdrant 集群） |
| 数据库 | 主从复制 + 自动故障转移 |
| Redis | 主从 + Sentinel |
| 模型 | 多副本 + 多供应商 |

### 依赖降级（高可用的另一半）

```
LLM 供应商挂了 → 备用供应商 → 缓存答案 → 明确降级响应
向量库挂了 → 只读缓存 → 明确降级响应
设计原则：任何依赖故障都不应导致"无响应"（要降级而非崩溃）
```

## 5. 零停机实践

### 零停机四件事

| 事项 | 做法 | 防什么 |
|---|---|---|
| 数据库持久化 | PostgreSQL 替代 SQLite | SQLite 并发锁 |
| 文件持久化 | S3/MinIO 替代本地盘 | 容器重启丢文件 |
| 滚动发布 | 分批更新副本 | 发布期间请求中断 |
| 迁移先行 | DB 迁移脚本先于代码发布 | 新旧版本 schema 不匹配 |

### 发布时序

```
① 数据库迁移（向后兼容）
② 新版本滚动发布（先 1 个副本验证）
③ 观察指标（错误率/延迟）
④ 全量发布
⑤ 回滚预案就绪（Helm rollback）
```

### 摄取链路的健壮性

```
异步摄取 worker（Celery）+ tenacity 指数退避：
网络中断 → 重试退避（1s→2s→4s...）
失败任务 → 重试队列 → 死信告警
```

## 6. 压测验证

### 压测方法

| 工具 | 场景 |
|---|---|
| wrk/ghz | 接口 QPS/延迟 |
| Locust | 复杂场景/混合流量 |
| 自定义脚本 | 真实链路（含 LLM 调用） |

### 压测指标

| 指标 | 目标 |
|---|---|
| QPS | 达到规划目标 |
| P95 延迟 | 达标（如 <2s） |
| 错误率 | <0.1% |
| 资源 | CPU/内存/GPU 利用率正常 |

### 压测流程

```
① 基线压测（当前配置）
② 逐层压测（定位瓶颈层）
③ 扩容再压（验证容量计算）
④ 峰值压测（3 倍 QPS，观察降级）
⑤ 记录校准（容量表更新为实测值）
```

### 压测的注意

```
LLM 供应商配额是外部瓶颈——压测前确认配额上限
压测环境与生产隔离（防污染线上指标）
压测数据脱敏（合规）
```

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 容量怎么规划？ | 目标 QPS → 每层基准 → 副本数 → 30% 余量 |
| 峰值怎么定？ | 稳态 × 3（行业经验） |
| 各层容量基准？ | 编排 50 QPS/副本、向量库 300 QPS/3 节点、Embedding 1000 QPS/GPU |
| 高可用几层？ | 单组件/集群/区域三层 |
| 降级设计？ | 供应商→备用→缓存→明确降级 |
| 零停机怎么做？ | 持久化/滚动发布/迁移先行 |
| 压测怎么验证？ | 基线→逐层→扩容→峰值，校准容量表 |

### 面试加分表达

> "容量规划我的方法是从目标 QPS 反推：峰值按稳态 3 倍，编排层 50 QPS 一个副本算下来 8 个副本加 30% 余量，Embedding 一个 GPU 就够。上线前用压测校准容量表——规划是预算，压测是决算。"

## 8. 容量规划的常见错误

| 错误 | 后果 | 正解 |
|---|---|---|
| 按稳态不按峰值 | 高峰打爆 | 峰值 = 稳态 × 3 |
| 不留余量 | HPA 来不及响应 | 30% 余量 |
| 只算一层 | 检索扩了生成堵 | 全链路逐层算 |
| 忽略外部瓶颈 | LLM 供应商配额不足 | 确认配额（外部不可扩） |
| 基准当保证 | 实测差距大 | 压测校准容量表 |
| 不监控验证 | 容量表是摆设 | 上线后指标对账 |

### 容量对账（上线后持续做）

```
每周对账：
① 实际峰值 QPS vs 规划值
② 每层实际利用率 vs 预估
③ 扩容延迟（HPA 响应时间）
④ 更新容量表（实测值替换参考值）
```

### 容量规划的输出物

```
一份完整的容量规划交付三件套：
① 容量表（层 × 目标 QPS × 副本数 × 余量）
② 压测报告（实测校准值与差距说明）
③ 扩容预案（自动扩/预扩/故障切换）

用途：上会评审的依据、运维的基线、预算的凭据
```

### 成本与容量的联动

```
容量规划的另一面是成本预算：
每层副本数 × 单价 = 月成本
例：8 副本编排（2vCPU）+ 1 GPU Embedding + 3 节点向量库
≈ 算力成本 + 模型 API 成本（LLM 供应商按 token）

成本优化与容量的关系：
缓存命中率 ↑ → 生成调用 ↓ → LLM 容量需求 ↓
模型分层 → 简单问题走便宜模型 → 配额压力 ↓
容量规划要同时回答："要多少资源" + "花多少钱"
```

### 扩容预案

| 场景 | 预案 |
|---|---|
| QPS 超预期 2 倍 | HPA 自动扩 + 告警 |
| 大促/发布高峰 | 预扩容（提前扩好） |
| 单节点故障 | 反亲和保证多节点 |
| 区域故障 | 跨区域切换（03 篇） |

> 🎯 核心要点：容量规划 = 目标 QPS → 每层基准 → 副本数 × 1.3 余量；高可用分单组件/集群/区域三层，任何依赖故障都要降级而非崩溃；零停机靠持久化 + 滚动发布 + 迁移先行；上线前压测校准容量表（规划是预算，压测是决算），上线后每周对账持续校准。
