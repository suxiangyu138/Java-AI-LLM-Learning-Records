## 1. 监控体系总览

### 五层监控

| 层 | 工具 | 回答什么问题 |
|---|---|---|
| 基础设施 | Prometheus + Grafana | CPU/内存/GPU 够吗？ |
| 应用指标 | Prometheus 自定义指标 | QPS/延迟/错误率？ |
| LLM 调用 | Langfuse | 每次 LLM 调用花了多少 token/钱？ |
| 链路追踪 | OpenTelemetry | 慢在哪一层？ |
| 质量评估 | Ragas CronJob | 回答质量退化了吗？ |

### 监控的四个目标

```
① 可用性：服务活着吗（探针）
② 性能：快吗（延迟）
③ 质量：对吗（评估）
④ 成本：贵吗（token 计量）
```

## 2. Prometheus + Grafana 指标监控

### RAG 核心指标

| 指标 | 类型 | 说明 |
|---|---|---|
| rag_requests_total | Counter | 请求总量 |
| rag_request_duration_seconds | Histogram | 延迟分布（p50/p95） |
| rag_error_total | Counter | 错误数（按类型） |
| rag_retrieval_latency | Histogram | 检索层延迟 |
| rag_llm_latency | Histogram | 生成层延迟 |
| rag_cache_hit_ratio | Gauge | 缓存命中率 |
| rag_tokens_total | Counter | token 消耗（成本） |

### 指标暴露示例（FastAPI）

```python
from prometheus_client import Counter, Histogram, generate_latest

REQUESTS = Counter("rag_requests_total", "Total requests")
LATENCY = Histogram("rag_request_duration_seconds", "Request latency")

@app.get("/ask")
def ask(query: str):
    with LATENCY.time():
        answer = pipeline(query)
    REQUESTS.inc()
    return {"answer": answer}
```

### Grafana 看板设计

| 面板 | 展示 |
|---|---|
| 总览 | QPS、错误率、P95 延迟 |
| 分层 | 检索延迟 vs 生成延迟 |
| 成本 | token 消耗趋势 |
| 质量 | 评估分数趋势（与 Ragas 联动） |

## 3. Langfuse LLM 可观测性

### 解决什么

```
传统日志看不到 LLM 调用细节：
- 每次调用用了什么模型/多少 token/多少钱
- Prompt 是什么、输出是什么
- 多步 Agent 的调用链
```

### 核心能力

| 能力 | 说明 |
|---|---|
| Trace | 一次请求的完整调用链 |
| Span | 每次 LLM/检索调用 |
| 成本 | token 用量与费用 |
| 回放 | 精确复现某次请求 |
| 对比 | 模型 A vs B 的效果对比 |

### 接入方式

```python
from langfuse import Langfuse

langfuse = Langfuse()

@app.get("/ask")
def ask(query: str):
    trace = langfuse.trace(name="rag_ask", input=query)
    with trace.span(name="retrieve") as span:
        results = retrieve(query)
        span.output = {"top_k": len(results)}
    with trace.span(name="generate", model="deepseek-chat") as span:
        answer = generate(query, results)
        span.output = answer
    trace.update(output=answer)
    return {"answer": answer}
```

### Langfuse 部署容量

```
事件摄取：约 1 worker / 万事件/秒，预留 50% 余量
（事件量 = 请求量 × 每请求 span 数）
```

## 4. OpenTelemetry 链路追踪

### 为什么需要链路追踪

```
指标看"整体慢"——不知道慢在哪层
链路追踪看"具体慢在哪"：检索 200ms + 生成 1.8s → 生成是瓶颈
```

### 接入方式

```
OTel SDK 自动埋点（HTTP/gRPC 库自动插桩）
+ 手动 Span（RAG 各层边界）
+ 导出到 Jaeger/Tempo
```

### 采样策略

| 场景 | 采样率 |
|---|---|
| 开发 | 100% |
| 生产（高流量） | 10-20% |
| 错误请求 | 100%（错误全采） |
| 慢请求 | 100%（慢全采） |

```
采样原则：错误与慢请求全采（排障用），正常请求抽样（成本控制）
```

### 与 Langfuse 的分工

```
OTel：基础设施/应用链路追踪（标准协议）
Langfuse：LLM 专项可观测（Prompt/token/成本）
可导出互通：Langfuse 支持 OTel 导出
```

## 5. Ragas 定时评估闭环

### 定时评估（2026 实践）

```
K8s CronJob 每日运行 Ragas 评估：
① 拉取最新测试集
② LLM-as-judge 评估（忠实度 + 相关性等）
③ 结果推送 Prometheus（Pushgateway）
④ Grafana 展示趋势 + 告警
```

### CronJob 示例

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: ragas-eval
  namespace: rag-platform
spec:
  schedule: "0 3 * * *"          # 每日凌晨 3 点
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: ragas
              image: registry/ragas-eval:1.2
              envFrom:
                - secretRef: { name: rag-secrets }
          restartPolicy: OnFailure
```

### 评估闭环设计

```
每日评估 → 指标趋势 → 阈值告警 → 人工介入
退化检测：连续 2 天低于阈值 → 告警
回归防线：发布前手动跑评估（阶段 3 CI 门禁）
```

### 评估与发布联动

```
发布流程：
① CI：测试集评估（阶段 3 门禁）
② 上线：金丝雀 + 实时监控
③ 每日：CronJob 持续评估（防退化）
```

## 6. 告警设计

### 告警分层

| 级别 | 示例 | 响应 |
|---|---|---|
| P0 致命 | 错误率 >5%、服务不可用 | 立即处理 |
| P1 严重 | P95 延迟 >2s | 当天处理 |
| P2 关注 | 缓存命中率下降 | 观察 |
| P3 信息 | token 成本上升 | 记录 |

### 告警规则示例（PromQL）

```yaml
# 错误率告警
- alert: RagErrorRateHigh
  expr: rate(rag_error_total[5m]) / rate(rag_requests_total[5m]) > 0.05
  for: 5m
  labels: { severity: P0 }

# 质量退化告警（Ragas 指标）
- alert: RagQualityDrop
  expr: rag_faithfulness < 0.85
  for: 2d           # 连续 2 天低于阈值
  labels: { severity: P1 }
```

### 告警设计原则

```
① 少而准：每告警必须有可执行动作
② 分级响应：P0 立即/P1 当天/P2 观察
③ 防抖：for 时长避免瞬时抖动误报
④ 告警疲劳：连续误报的告警要删
```

| 问题 | 回答要点 |
|---|---|
| RAG 监控哪些指标？ | QPS/延迟/错误率/缓存命中/token 成本 |
| Langfuse 解决什么？ | LLM 调用细节：模型/token/成本/回放 |

| 质量怎么持续监控？ | Ragas CronJob 每日评估 + 阈值告警 |

### 面试加分表达

> "上线后我配了五层可观测：Prometheus 盯 QPS/延迟、Langfuse 看每次 LLM 调用的 token 和成本、OTel 追踪链路定位瓶颈、Ragas CronJob 每日评估质量、Grafana 汇总告警。质量退化连续两天低于阈值会告警——上线不是终点，监控评估闭环才是。"

## 8. 监控指标设计实践

### 指标设计的 RED 方法论

```
R（Rate）：请求速率（QPS）
E（Errors）：错误率
D（Duration）：延迟（p50/p95/p99）
RAG 扩展：+ 质量指标（评估）+ 成本指标（token）
```

### 指标命名与标签

```text
规范：rag_<层>_<指标>
rag_retrieval_latency_seconds{model="bge", index="prod"}
rag_llm_tokens_total{provider="deepseek", model="deepseek-chat"}

标签设计原则：
- 分层标签（retrieval/llm/cache）
- 供应商标签（成本归因）
- 版本标签（发布对比）
- 避免高基数标签（如 query 全文——用归一化哈希）
```

### 监控最佳实践清单

| 实践 | 说明 |
|---|---|
| 延迟分位数 | p50/p95/p99 都看（均值骗人） |
| 错误分类 | 按类型（超时/限流/依赖） |
| 基线对比 | 发布前后指标对比 |
| 成本看板 | token 趋势 + 供应商分摊 |
| 质量联动 | 评估分数与发布记录关联 |
| 告警去重 | 聚合相似告警（防风暴） |

> 🎯 核心要点：监控五件套各有分工——Prometheus 指标、Grafana 看板、Langfuse LLM 可观测、OTel 链路追踪、Ragas 定时评估；指标设计用 RED 方法论（速率/错误/延迟）+ RAG 扩展（质量/成本）；标签分层 + 避免高基数；告警分层（P0-P3）+ 少而准 + 防抖；"监控看活着，评估看健康"，上线后评估闭环才是质量防线。
