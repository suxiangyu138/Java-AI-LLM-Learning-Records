# 01 生产架构设计：三层分层

> 生产级 RAG 的第一性原理：分层——模型服务层管 GPU、检索服务层管低延迟、应用集成层管业务；层间解耦、独立扩展、默认拒绝的安全边界。

## 1. 为什么要分层

### 单体的痛点

| 痛点 | 表现 |
|---|---|
| 扩展粒度粗 | 检索瓶颈被迫连生成一起扩 |
| 故障放大 | 一个组件挂掉全系统挂 |
| GPU 资源错配 | 检索（CPU）与生成（GPU）抢资源 |
| 发布耦合 | 改检索必须重启全部 |

### 分层的好处

```
① 独立扩展：GPU 层扩 GPU、检索层扩副本（各自成本最优）
② 故障隔离：检索服务挂了，生成服务不受影响（可降级）
③ 独立发布：每层独立版本迭代
④ 资源匹配：CPU 任务与 GPU 任务分池
```

## 2. 三层架构详解

### 三层总览

| 层 | 职责 | 典型组件 | 资源 |
|---|---|---|---|
| 应用集成层 | API 网关、业务逻辑、路由、缓存 | RAG 服务、Redis | CPU |
| 检索服务层 | Embedding + 向量检索（低延迟） | TEI、Qdrant/Milvus | CPU/小 GPU |
| 模型服务层 | LLM 生成、Rerank | LiteLLM、vLLM | GPU 池 |

### 层间调用关系

```
用户 → 应用层（路由/鉴权/缓存）
  → 检索层（Embedding + 向量库）→ Top-K
  → 模型层（LLM 生成）
  → 应用层（组装答案/溯源/日志）→ 用户
```

### 每层的扩展逻辑

| 层 | 扩展方式 | 瓶颈信号 |
|---|---|---|
| 应用层 | 水平扩副本 | QPS 高、CPU 高 |
| 检索层 | 扩 Embedding Pod/向量库分片 | 检索延迟高 |
| 模型层 | 扩 GPU Pod | GPU 利用率高、排队 |

## 3. 生产参考架构（K8s 视角）

2026 年 K8s 参考架构（多命名空间隔离）：

```
┌── 命名空间：rag-platform ──┐
│  编排服务 / 摄取 worker     │
├── embeddings ─────────────┤
│  TEI GPU Pod（仅内部访问）  │
├── vectordb ───────────────┤
│  Qdrant 集群               │
├── llm-gateway ────────────┤
│  LiteLLM + Postgres/Redis  │
├── observability ──────────┤
│  Langfuse/Prometheus/Grafana│
├── data ───────────────────┤
│  Postgres/Redis/Kafka      │
└── ingress-nginx（共享）────┘
```

### 每个命名空间的特点

| 命名空间 | 内容 | 网络策略 |
|---|---|---|
| rag-platform | 编排 + 摄取 | 对外暴露 |
| embeddings | TEI | 仅内部（default-deny） |
| vectordb | 向量库 | 仅内部 |
| llm-gateway | LiteLLM | 仅内部 |
| observability | 监控 | 内部 + 管理 |
| data | 数据存储 | 仅内部 |

> 核心安全实践：**每个命名空间采用 default-deny 的 NetworkPolicy**，仅允许显式规则——这是审计认可的安全基线（不是可选项）。

## 4. 服务拆分与职责边界

### 最小服务清单

| 服务 | 职责 | 独立部署理由 |
|---|---|---|
| RAG 编排服务 | 路由/组装/缓存 | 业务核心，频繁迭代 |
| Embedding 服务 | 文本→向量 | 可热切换模型 |
| 向量库 | 存储+检索 | 独立扩展 |
| LLM 网关 | 模型路由/配额 | 统一管理密钥与限流 |
| 摄取 worker | 文档→索引 | 异步不阻塞查询 |
| 评估服务 | 定时跑测试集 | 独立于在线链路 |

### 同步与异步拆分

```
在线（同步）：RAG 编排 → Embedding → 检索 → LLM → 返回
离线（异步）：文档 → 摄取 worker（Celery）→ 索引
```

| 链路 | 特征 |
|---|---|
| 在线 | 低延迟、高可用、失败要降级 |
| 离线 | 可重试、可排队、失败可补跑 |

### 服务间通信

| 方式 | 适用 |
|---|---|
| REST/gRPC 同步 | 在线链路（编排→检索→生成） |
| 消息队列（Kafka） | 离线摄取、评估结果 |
| 事件驱动 | 文档变更通知 |

## 5. 安全网络设计

### 网络隔离

| 层级 | 设计 |
|---|---|
| 命名空间 | 按职责分（5 个 + ingress） |
| NetworkPolicy | default-deny + 显式允许 |
| 服务暴露 | 仅 ingress 对外，其余内部 |
| 敏感服务 | Embedding/向量库/数据完全内网 |

### 安全基线（审计认可）

```
① 无公网集群 API（内部服务不暴露公网）
② 工作负载身份联邦（Pod 身份而非长期密钥）
③ 客户托管 KMS 密钥（数据加密）
④ 全路由限流（Redis 支持的 slowapi）
⑤ 审计日志（谁调了什么模型）
```

### 合规提示

```
数据主权场景（医疗/金融/政务）：
遵守 NESA/CBUAE/ADGM 等本地合规要求
数据不出内网 → 本地模型 + 私有化向量库
```

## 6. 架构决策记录

### 决策模板（每层一个）

```markdown
## 架构决策：检索服务层
- 决策：Qdrant 3 节点集群 + TEI Embedding 服务
- 理由：10M 向量规模、需要 HNSW ef=128 精度
- 替代：Milvus（更大规模）、pgvector（复用 PG）
- 代价：多一个运维组件
- 验证：压测检索延迟 p99 < 50ms
```

### 决策驱动因素

```
规模 → 向量量级决定向量库选型
延迟 → 在线链路预算决定服务拆分
成本 → GPU 与 CPU 分池决定资源规划
合规 → 数据主权决定本地化程度
团队 → 运维能力决定 K8s vs 平台化
```

## 7. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| 生产 RAG 分几层？ | 三层：应用/检索/模型，各层独立扩展 |
| 为什么 Embedding 要独立服务？ | 单独扩容 + 热切换模型 |
| 命名空间隔离怎么设计？ | 按职责分 + default-deny NetworkPolicy |
| 在线与离线链路怎么分？ | 同步走 REST，异步走消息队列 |
| 安全基线有哪些？ | 内网隔离/身份联邦/KMS/限流/审计 |
| 单体能跑吗？ | 小规模可以，但扩展/故障/资源都会出问题 |

### 面试加分表达

> "生产架构我按三层设计：应用层管路由和缓存，检索层用 TEI 服务化 Embedding 加 Qdrant，模型层走 LiteLLM 网关。每层独立扩缩——GPU 瓶颈扩模型层，检索瓶颈扩检索层。网络用命名空间隔离加 default-deny，审计认可。"

## 8. 分层设计的反模式

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 全部塞一个服务 | 无法独立扩展 | 按职责拆分 |
| GPU 与 CPU 混跑 | 资源互相抢 | 分池 |
| 在线离线混在一起 | 摄取拖慢查询 | 异步 worker 分离 |
| 服务间直连无网关 | 密钥散落/无法限流 | LiteLLM 统一入口 |
| 无网络策略 | 内部服务暴露 | default-deny |

### 与阶段 4 范式的部署关系

```
阶段 4 的范式选择在生产架构中的落点：
GraphRAG（LightRAG）→ 检索服务层新增图索引服务
Agentic Router → 应用集成层的路由组件
ColPali 多模态 → 检索服务层新增视觉检索服务
融合模式（长上下文）→ 应用层上下文组装逻辑

原则：范式是"检索层与应用层的功能扩展"，三层骨架不变
——这也是分层架构的收益：加范式不改骨架，只加服务
```

### 架构评审清单（上线前评审用）

| 评审项 | 问题 |
|---|---|
| 分层 | 每层能否独立扩展/发布？ |
| 网络 | 内部服务是否 default-deny？ |
| 在线/离线 | 摄取是否异步隔离？ |
| 依赖 | 每个外部依赖有无降级方案？ |
| 资源 | GPU 与 CPU 是否分池？ |
| 密钥 | 密钥是否走 Secret（非明文）？ |
| 可观测 | 每层是否有指标与日志？ |

评审结论模板："架构评审通过/不通过——阻塞项：___"

### 反模式自查

```
问自己的系统：
① 检索瓶颈时能只扩检索吗？
② Embedding 换模型要重启整个服务吗？
③ 摄取任务会阻塞查询吗？
④ 内部服务能被外部访问吗？
任何"不能"都对应一个分层缺口
```

> 🎯 核心要点：生产级 RAG = 三层分层（应用/检索/模型）——各层独立扩展、故障隔离、资源匹配；K8s 部署按职责分命名空间 + default-deny 网络策略是安全基线；同步在线链路与异步离线链路分开设计；架构决策用"决策-理由-替代-代价-验证"模板记录；用四个反模式自查题检验自己的系统。
