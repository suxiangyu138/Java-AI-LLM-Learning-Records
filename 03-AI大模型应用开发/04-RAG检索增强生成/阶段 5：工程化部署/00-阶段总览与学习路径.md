## 2. 工程化部署全景图

```
┌────────────────────────────────────────────────┐
│ 应用集成层（API 网关 + 业务逻辑）                │
│   RAG 服务 / 路由 / 缓存 / 鉴权 / 限流          │
├────────────────────────────────────────────────┤
│ 检索服务层（低延迟相似度计算）                   │
│   Embedding 服务（TEI）+ 向量库（Qdrant/Milvus）│
├────────────────────────────────────────────────┤
│ 模型服务层（GPU 资源池，动态扩展）               │
│   LLM 网关（LiteLLM）+ 生成模型 / Rerank 模型   │
├────────────────────────────────────────────────┤
│ 数据与运维层                                    │
│   Postgres / Redis / Kafka / 监控（Prometheus）│
│   评估（Ragas CronJob）/ 可观测（Langfuse/OTel）│
└────────────────────────────────────────────────┘
```

### 三层设计的核心原则

```
① 分层解耦：每层独立扩展（GPU 层扩 GPU、检索层扩副本）
② 服务化：Embedding/检索/生成都是独立服务
③ 可观测：每层都有指标与日志
④ 安全隔离：命名空间 + NetworkPolicy default-deny
```

## 6. 2026 部署格局一句话总结

| 形态 | 一句话 |
|---|---|
| 自建容器化 | Docker Compose 起步 → K8s 生产（控制力最强） |
| Embedding 服务化 | TEI 独立 GPU Pod + LiteLLM 网关 |
| 低代码平台 | Dify（应用编排）/ FastGPT（知识库）/ RAGFlow（文档解析） |
| 托管云服务 | 向量库/LLM 全托管（成本高、省运维） |

### 贯穿全阶段的核心认知

```
1. 分层是根本：三层各扩各的，互不拖累
2. 可观测是底线：没有指标就不知道系统死活
3. 容量是预算：先算 QPS 再定副本，别拍脑袋
4. 平台化是捷径：小团队用 Dify/FastGPT 省 80% 工作
5. 评估不停止：上线后 Ragas 持续跑，防退化
```

## 7. 常见疑问快答

| 疑问 | 回答 |
|---|---|
| 必须上 K8s 吗？ | 不必须——单机/Compose 够用时别过度设计；K8s 是多副本/弹性扩缩的需要 |
| Embedding 也要服务化？ | 生产要——独立服务可单独扩容与热切换模型 |
| 监控要全吗？ | 至少 Prometheus + 日志；Langfuse 级可观测按需 |
| 低代码平台能用吗？ | 能——小团队/知识库场景 Dify/FastGPT 是主流选择 |
| 部署要会 K8s 吗？ | 面试要会讲架构与关键概念；实操可从 Docker Compose 起步 |
| 与阶段 3 的关系？ | 阶段 3 的缓存/评估/成本优化全部要在部署中落地 |

## 8. 常见失败画像与工具速查

### 失败画像

| 失败画像 | 现象 | 预防 |
|---|---|---|
| 过度设计型 | 小规模上 K8s 全家桶 | 规模决定形态（04 篇判断） |
| 容量盲算型 | 上线即被打爆 | QPS 反推 + 压测校准 |
| 无监控上线型 | 出问题不知道 | 五件套先配再上线 |
| 平台万能型 | 平台解决一切 | 平台与自建组合 |
| 无评估型 | 质量悄悄退化 | Ragas CronJob 每日 |
| 安全裸奔型 | 内部服务暴露 | default-deny 基线 |
