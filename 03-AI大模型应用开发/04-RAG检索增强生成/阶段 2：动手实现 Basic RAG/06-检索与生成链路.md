## 1. 链路总览

```
用户问题 → ① 查询向量化（同一 Embedding 模型）
        → ② 向量库检索 Top-K
        → ③ 组装 Prompt（检索片段 + 问题）
        → ④ LLM 生成带依据答案
```

与阶段 1 的映射：① 属于检索（Retrieval）前的查询处理，③④ 属于生成（Generation）——索引部分在 02-05 篇已完成。

### 四个环节的延迟预算

| 环节 | 耗时 | 优化空间 |
|---|---|---|
| ① 查询向量化 | 10-100ms | 换小模型 |
| ② Top-K 检索 | 1-50ms | 索引类型 |
| ③ Prompt 组装 | <1ms | 可忽略 |
| ④ LLM 生成 | 1-10s | 模型/缓存 |

## 2. 查询向量化与检索

```python
def retrieve(store: VectorStore, model, query: str, k: int = 5) -> list[dict]:
    """查询全流程：向量化 → 检索 → 组装结果"""
    q_vec = model.encode([query], normalize_embeddings=True)
    q_vec = np.array(q_vec, dtype=np.float32)

    distances, ids = store.index.search(q_vec, k)
    results = []
    for dist, idx in zip(distances[0], ids[0]):
        if idx == -1:
            continue
        results.append({
            "text": store.chunks[idx]["text"],
            "score": float(dist),
            "meta": store.chunks[idx].get("meta", {}),
        })
    return results
```

| 参数 | 本阶段默认 | 说明 |
|---|---|---|
| k | 5 | Top-K 召回数（阶段 3 会讲粗召回 20-50 + 精排 3-5 的组合） |
| 阈值过滤 | 可选 | score < 0.5 视为不相关（阈值需按实际分布调） |
| 排序 | 按 score 降序 | 归一化后内积越大越相关 |

### 查询与索引的对称性

```
索引：文档 → 同一模型 → 向量 → 库
查询：问题 → 同一模型 → 向量 → 搜库
```

**两个方向的编码必须用同一个模型**——这是 RAG 检索正确的第一前提（04 篇一致性铁律的落地）。

> ⚠️ 检索后先人工看一眼 Top-K 结果：**如果 Top-5 本身就不相关，生成环节再怎么调都白搭**——这是定位问题层的第一原则。

### 检索调试打印

```python
def debug_retrieve(store, model, query, k=5):
    """带调试输出的检索：先看检索对不对，再谈生成"""
    results = retrieve(store, model, query, k)
    for i, r in enumerate(results, 1):
        print(f"[{i}] 分数={r['score']:.3f} 来源={r['meta'].get('title','?')}")
        print(f"    {r['text'][:60]}...")
    return results
```

## 3. Prompt 组装设计

Prompt 结构（检索增强的核心）：

```python
SYSTEM_PROMPT = """你是一个基于知识库回答问题的助手。
请严格依据下方【参考资料】回答问题：
1. 答案只能来自参考资料，不要编造
2. 如果参考资料中没有答案，明确回答"知识库中没有相关内容"
3. 回答时注明信息出处（文档标题/章节）
4. 用中文回答"""

def build_prompt(query: str, results: list[dict]) -> str:
    context = "\n\n".join(
        f"[资料{i + 1}]（来源：{r['meta'].get('title', '未知')}）\n{r['text']}"
        for i, r in enumerate(results)
    )
    return f"""{SYSTEM_PROMPT}

【参考资料】
{context}

【用户问题】
{query}
"""
```

设计要点：

| 设计项 | 为什么 |
|---|---|
| "只能来自参考资料" | 压幻觉：约束模型引用检索内容 |
| "没有就明说" | 拒答机制：避免硬编 |
| 标注来源 | 可溯源 + 审计 |
| 编号资料 | 模型可引用"据资料2" |

### Prompt 模板迭代法（本阶段就要养成的习惯）

```
版本 1：只给资料和问题 → 模型自由发挥 → 发现会编
版本 2：加"只能依据资料" → 编造减少 → 发现不标注来源
版本 3：加"注明出处" → 有来源了 → 发现检索不到时硬答
版本 4：加"没有就明说" → 拒答生效 → 达标
```

每次改动只加一条约束，**记录改动前后效果**——这就是 Prompt 工程的最小迭代闭环。

## 4. LLM 生成（DeepSeek API）

DeepSeek 兼容 OpenAI 协议，直接用 openai SDK：

```python
from openai import OpenAI

client = OpenAI(
    api_key="sk-xxx",                 # 或从环境变量读 DEEPSEEK_API_KEY
    base_url="https://api.deepseek.com",
)

def generate(prompt: str) -> str:
    resp = client.chat.completions.create(
        model="deepseek-chat",        # 或 deepseek-reasoner（深度推理）
        messages=[{"role": "user", "content": prompt}],
        temperature=0.3,              # RAG 问答低温：忠实引用
        max_tokens=1024,
    )
    return resp.choices[0].message.content

# 完整问答
def ask(query: str) -> str:
    results = retrieve(store, model, query, k=5)
    return generate(build_prompt(query, results))
```

| 参数 | 推荐 | 理由 |
|---|---|---|
| model | deepseek-chat | 日常问答性价比高 |
| temperature | 0.3 左右 | 低温度忠实引用，减少发散 |
| max_tokens | 512-1024 | 够回答问题，控成本 |

### 生成参数对 RAG 的影响

| 参数 | 调高 | 调低 |
|---|---|---|
| temperature | 更有创意但易跑偏 | 更忠实但可能呆板 |
| top_p | 类似 temperature | 类似 temperature |
| max_tokens | 能答长问题 | 省成本、防超时 |
| presence_penalty | 避免重复 | — |

> RAG 问答的默认纪律：**temperature=0.3 以下**。需要创造性时再上调（但那时就不该用 RAG）。

## 5. 无 Key 的本地替代方案

没有 DeepSeek Key 也能跑通全链路（检索部分完全免费）：

| 方案 | 说明 | 限制 |
|---|---|---|
| 纯检索版 | 只跑 retrieve()，人工看 Top-K | 无生成，但验证链路有效 |
| Ollama 本地模型 | `ollama run qwen2.5:7b`，OpenAI 兼容本地端点 | 需下载模型（数 GB） |
| 其他免费 API | 各平台新用户额度 | 协议兼容即可 |

Ollama 接入（接口兼容，仅换 base_url）：

```python
client = OpenAI(
    api_key="ollama",                       # 任意占位
    base_url="http://localhost:11434/v1",   # Ollama OpenAI 兼容端点
)
# model 参数改为 "qwen2.5:7b"
```

### 本地 vs API 的取舍

| 维度 | DeepSeek API | Ollama 本地 |
|---|---|---|
| 成本 | 按 token | 免费（硬件成本） |
| 速度 | 网络延迟 | 本地快（硬件限制） |
| 质量 | 旗舰级 | 7B-14B 级别 |
| 隐私 | 数据出网 | 完全本地 |
| 部署 | 零部署 | 需装 Ollama + 拉模型 |

## 6. 检索与生成的职责边界

```
检索负责：拿到对的料（相关性）
生成负责：用对的方式说（忠实性）

检索失败 → 神仙 Prompt 也救不回
生成失败 → 料是对的，但说错了
```

### 问题定位二分法

| 现象 | 问题层 | 查什么 |
|---|---|---|
| Top-K 不相关 | 检索层 | 切片/Embedding/查询改写 |
| Top-K 相关但答案错 | 生成层 | Prompt 约束/temperature/模型 |
| 相关且遵循但信息不全 | 数据层 | 文档缺失/切片切断 |
| 一切正常但偶尔错 | 评估层 | 建测试集统计失败率（阶段 3） |

## 7. 多轮对话支持（扩展）

本阶段先跑通单轮问答；多轮支持是客服场景的刚需，原理先掌握：

### 两种多轮方案

| 方案 | 做法 | 问题 |
|---|---|---|
| 简单拼接 | 历史 + 当前问题一起送 | 历史太长超窗口；token 浪费 |
| 检索式多轮 | 每轮检索 + 只带上一轮答案 | 需要维护会话状态 |

### 最小多轮实现（思路）

```python
history = []  # 会话级历史（每轮只存问答摘要）

def ask_with_history(query: str) -> str:
    # 1. 上下文补充：把"它"等指代还原（可选，阶段 3 查询改写）
    # 2. 检索：只对当前问题检索（历史不参与检索）
    results = retrieve(store, model, query, k=TOP_K)
    # 3. Prompt 带最近 2 轮历史 + 检索片段
    prompt = build_prompt(query, results, history=history[-2:])
    answer = generate(prompt)
    history.append({"q": query, "a": answer[:200]})  # 只存摘要
    return answer
```

### 多轮设计的三个坑

| 坑 | 对策 |
|---|---|
| 历史无限增长 | 只带最近 N 轮 + 摘要化 |
| 指代混乱（"它"指什么） | 查询改写（阶段 3） |
| 历史参与检索还是生成 | 经验：历史进生成，不进检索 |

> 本阶段掌握思路即可；阶段 3 的查询改写与上下文管理会系统解决多轮问题。

> 🎯 核心要点：检索与生成的职责边界——**检索负责"拿到对的料"，生成负责"用对的方式说"**。检索结果质量是上限，Prompt 设计决定下限，temperature 低是 RAG 问答的基本纪律。多轮对话记住三个坑：历史限量、指代改写、历史进生成不进检索。
