## 1. 评估的层次：检索层 / 生成层 / 端到端

**核心原则：分三层评估**（只测端到端会掩盖问题出在哪一层）：

```text
问题定位链：
  回答错 → 是检索漏了（检索层）？还是检索到了但没用对（生成层）？
  → 只测端到端无法区分 → 必须分三层

三层评估：
① 检索层（Retrieval）
   指标：Context Precision、Recall@K、MRR、nDCG、Hit Rate
   回答："检索系统找到相关文档了吗"
② 生成层（Generation）
   指标：Faithfulness（忠实度）、Answer Relevance、Context Utilization
   回答："生成是否基于检索上下文、是否答非所问"
③ 端到端（End-to-End）
   指标：Answer Correctness（对答案/正确性）、Task Success
   回答："最终答案对不对"
```

| 故障 | 检索层表现 | 生成层表现 | 定位 |
|------|:----------:|:----------:|------|
| 检索漏了 | ❌ 差 | ✅ 好（用的都是相关上下文） | 检索层 |
| 检索到了但没用 | ✅ 好 | ❌ Faithfulness 差 | 生成层 |
| 检索和生成都差 | ❌ | ❌ | 双层问题 |

> 🎯 **核心要点**：评估的第一原则 = "**分层定位**"——三层指标分开测，才能知道"优化检索"还是"优化提示词"。**只测端到端 = 出了问题不知道改哪**。

## 2. RAGAS 四指标详解

**RAGAS**（开源评估框架，2026 事实标准，集成进 DeepEval/Phoenix 等）——LLM-as-Judge 的四指标：

| 指标 | 衡量 | 问题 | 关注点 |
|------|------|------|--------|
| **Faithfulness**（忠实度） | 回答是否**完全基于**检索上下文 | 回答中的每个主张都能在上下文中找到支持吗？ | **幻觉的哨兵（最高优先级）** |
| **Answer Relevance**（答案相关） | 回答是否切题 | 回答对问题的相关性打分 | 答非所问检测 |
| **Context Precision**（上下文精度） | 检索结果中相关块的比例与排序 | 相关块是否排在前面 | 检索质量 |
| **Context Recall**（上下文召回） | 检索结果是否覆盖了需要的全部信息 | 黄金答案中的信息都被检索到了吗 | 检索覆盖 |

```python
# RAGAS 使用（伪代码）
from ragas import evaluate
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall

result = evaluate(
    dataset=golden_set,          # 问题 + 黄金答案 + 检索上下文
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall]
)
# 输出各指标分数 → 定位短板：
# Context Recall 低 → 检索问题（改查询/混合检索）
# Faithfulness 低 → 生成问题（改提示词/压缩上下文）
```

**第五指标**：有黄金答案时加 **Answer Correctness**（与标准答案对比，非 LLM 判断而是字符串/语义匹配）。

> 🎯 **核心要点**：RAGAS 四指标的记忆 = "**两个管检索（Precision/Recall）、两个管生成（Faithful/Relevant）**"——与三层评估一一对应。**Faithfulness 是可告警的首要指标**（幻觉检测）。

## 3. 黄金集构建：评估的基石

**黄金集（Golden Set）**：人工标注的评估数据集——评估体系的"测试集"：

```text
黄金集结构（每条样本）：
  问题（真实用户查询）
  黄金答案（人工撰写/人工认可的标准答案）
  相关文档 ID / 相关块 ID（检索的 ground truth）

规模建议（2026 实践）：
  检索相关性标注：200-500 对（校准 LLM-judge 的检索评分）
  端到端问答对：50-200 条起步，最多 ~500 条
  → 规模不在大，在"覆盖问题类型分布"（单点/多跳/全局/表格...）
```

**黄金集构建流程**：

```text
① 采集真实问题：线上日志抽样 + 业务方提供（比编造更真实）
② 问题聚类：按类型分组（确保覆盖各策略场景）
③ 标注答案与相关块：人工（或先 LLM 生成 + 人工审核）
④ 一致性校验：多人标注的交叉一致性（标注冲突要讨论）
⑤ 版本管理：黄金集入库版本化（评估结果可回溯）
```

**黄金集的使用原则**：

| 原则 | 说明 |
|------|------|
| 隔离 | 评估集与开发集分开（防"背题"） |
| 定期刷新 | 知识库变化后更新相关块标注 |
| 覆盖新场景 | 新问题类型出现 → 补样本 |

> 🎯 **核心要点**：黄金集 = "**RAG 的测试集**"——没有它，所有优化都是"感觉"。**规模 50-500 条、覆盖问题类型分布、人工标注相关块**三条做到，评估体系就立住了。

## 4. CI 门禁与在线评估

**离线评估（CI 门禁）**：每次改动跑评估，不达标不放行：

```text
触发点（2026 最佳实践）：
  每次 prompt 修改 / 检索器修改 / 模型升级 / 切分策略修改
门禁指标：
  Faithfulness / Context Relevance / Answer Correctness（核心三项）
  与基线对比：下降超过阈值（如 2-3%）→ 阻断合并
工具：DeepEval（pytest 原生，CI 友好）或 RAGAS 脚本

价值：让"改坏了"在合并前暴露，而不是上线后事故
```

**在线评估（生产监控）**：持续监测线上质量：

```text
① 抽样评估：5-10% 的线上流量跑同样的评估器
② 漂移监控：指标趋势下滑 → 告警（知识库更新/模型变化/查询分布变化）
③ 人工抽检：分层抽样 + 高风险领域（金融/医疗）人工复核
④ 反馈闭环：用户反馈（点赞/踩）回流到评估集
```

**2026 评估架构（两层）**：

```text
第一层：离线批量评估（RAGAS/DeepEval）—— 发布门禁
第二层：在线可观测性（LangSmith/Braintrust/Phoenix）—— 线上监控
→ 共识：两层各司其职，缺一不可
```

> 🎯 **核心要点**：评估体系 = "**离线 CI 门禁（防回归）+ 在线抽样监控（防漂移）**"两层——**"改了不评估"是 RAG 迭代的头号坏习惯**；"评估只离线不监控"会让线上悄悄变差。

## 5. LLM-as-Judge 的成本控制

**LLM-as-Judge 的悖论**：评估要准 → 用强模型 → 贵；评估要频繁 → 贵不可持续：

| 方案 | 成本 | 精度 | 适用 |
|------|:----:|:----:|------|
| 旗舰 LLM 判官（GPT-5/Claude 级） | 高 | 最高 | 边缘案例/终审 |
| 中小模型判官（开源 7B-14B） | 低 | 中高 | **日常批量评估（主流）** |
| **蒸馏判官**（2026 趋势） | 极低 | 接近旗舰 | **在线高频评分** |
| 规则/启发式 | 零 | 低 | 检索层指标（MRR 等无需 LLM） |

**成本控制三原则**：

```text
① 检索层指标不用 LLM：Recall@K/MRR/nDCG 是确定性计算（零成本）
② 生成层指标分级：日常用小模型判官，边缘案例用旗舰
③ 蒸馏判官（2026 方向）：用旗舰判官标注数据，蒸馏出专用小判官
   → 在线 5-10% 抽样高频评分的主要承载
```

**判官偏差的注意事项**（LLM-as-Judge 的已知问题）：

| 偏差 | 表现 | 缓解 |
|------|------|------|
| 位置偏差 | 偏好先出现的答案 | 交换顺序双评 |
| 自我偏好 | 偏好"与自己风格相似"的回答 | 匿名化/多判官投票 |
| 长度偏差 | 长答案分数偏高 | 提示词明确标准 |

> 🎯 **核心要点**：评估成本 = "**检索层零成本（确定性指标）+ 生成层分级（小模型日常 + 旗舰终审）+ 蒸馏判官（2026 在线标准）**"——评估体系要可持续，成本设计必须前置。

**评估体系落地清单**（从 0 到 1）：

```text
第一阶段（第一天）：
  □ 采集 50-100 条真实问题（线上日志抽样）
  □ 人工标注黄金答案 + 相关文档/块
  □ 跑通 RAGAS 四指标 → 得到基线分

第二阶段（一周内）：
  □ 问题分类标注（单点/多跳/全局/术语）→ 分类型指标
  □ 检索层指标自动化（Hit Rate/MRR 确定性计算，零成本）
  □ 建立 CI 门禁（改动跑评估，关键指标对比基线）

第三阶段（持续）：
  □ 在线抽样（5-10% 流量）+ 漂移告警
  □ 蒸馏判官（旗舰标注 → 小判官）降本
  □ 黄金集季度刷新（知识库变化后更新）
  □ 反馈闭环（用户反馈回流评估集）
```

> 💡 关键认知：**评估体系是"越早建越省"的投资**——第一阶段的 50 条黄金集就能拦住"拍脑袋优化"；三个阶段的投入产出比远超任何单个检索优化。
