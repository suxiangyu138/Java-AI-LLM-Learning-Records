# 03 RAG vs 微调 vs 长上下文

## 1. 三方案本质对比

| 方案 | 本质 | 一句话 |
|---|---|---|
| RAG | 知识放外部库，检索后注入提示词 | 先翻书再回答 |
| 微调 | 把知识/风格压进模型参数 | 把知识背进脑子里 |
| 长上下文 | 把整篇文档直接塞进上下文窗口 | 开卷考试（全带进考场） |

### 各自优势与硬伤

| 方案 | 优势 | 硬伤 |
|---|---|---|
| RAG | 低成本、实时更新、可溯源、无泄露风险 | 受检索质量限制、多一跳延迟 |
| 微调 | 风格稳定、响应快、领域能力内化 | 成本高、更新慢、有数据泄露风险 |
| 长上下文 | 保留完整上下文、无需切片、理解全局 | Token 成本极高、长文注意力下降、无法溯源 |

## 2. 细节对比表

| 维度 | RAG | 微调 | 长上下文 |
|---|---|---|---|
| 知识更新 | 秒级（换文档即可） | 月级（重新训练） | 即时（换 Prompt 即可） |
| 成本 | 向量化 + 检索基建 | 训练算力 + 数据工程 | 每次请求按 token 计费 |
| 可解释性 | ✅ 可引用来源 | ❌ 黑盒 | ✅ 内容可见但无定位 |
| 适用知识量 | 大（百万级文档） | 小（聚焦领域） | 受窗口限制（可达百万 token） |
| 数据安全 | 私有数据不出系统 | 数据进入模型参数（泄露风险） | 数据进请求（需加密通道） |
| 典型场景 | 知识库问答、客服、搜索 | 风格/格式/领域适配、代码 | 单文档深读（合同、论文） |
| 质量瓶颈 | 检索召回质量 | 训练数据质量 | 窗口内信息利用效率 |
| 启动周期 | 天级（建库） | 周-月级（数据+训练） | 小时级（写 Prompt） |
| 失败模式 | 检索不到就答错 | 过拟合训练集 | 长文中间信息被忽略 |

## 3. 三种方案的工作原理差异

理解"为什么差异这么大"，要看知识进入模型的路径：

```text
RAG：   知识在外部库 → 检索 → 以 Prompt 形式进入上下文窗口
微调：  知识在训练数据 → 梯度更新 → 固化进参数
长上下文：知识在请求里 → 整个塞进上下文窗口
```

### 3.1 RAG 的知识路径：检索门控

- 知识必须**通过检索才能进入**生成——检索不到，知识等于不存在
- 好处：可控（可过滤、可溯源）、可更新
- 代价：检索是瓶颈（召回率决定上限）

### 3.2 微调的知识路径：参数固化

- 知识经梯度更新写入参数——**模型"记住了"但不能告诉你记在哪**
- 好处：响应时不依赖外部检索，风格/能力内化
- 代价：更新要重新训练；"记错"无法单条修正；隐私数据进入模型有泄露风险（可被对抗性提取）

### 3.3 长上下文的知识路径：窗口直塞

- 知识随请求一起送入——模型"看得到"但注意力是有限的
- 研究事实：窗口越长，**中间部分的信息被利用得越差**（lost in the middle 现象）
- 代价：每次请求都按全部 token 计费；百万 token 请求成本是检索方案的几十倍

### 三者失败的典型画面

| 方案 | 典型失败 |
|---|---|
| RAG | 检索 Top-K 里没有正确答案 → 模型依据错误上下文作答 |
| 微调 | 领域数据质量差 → 模型"学会了错误答案"且无法单条修正 |
| 长上下文 | 600 页文档塞进去 → 答案遗漏中间章节的关键条款 |

## 4. 选型决策树

```
需要给 LLM 注入知识？
├─ 知识需频繁更新 / 数据敏感 / 必须可溯源 → RAG ✅
├─ 需要特定风格/格式/领域能力内化
│   ├─ 知识量大且更新少 → 微调（或 RAG+微调组合）
│   └─ 数据敏感不允许训练 → RAG
├─ 单文档深度分析（合同/论文/长报告）
│   ├─ 文档长但一次能装下 → 长上下文（成本允许时）
│   └─ 文档超长或需跨文档 → RAG（切片 + 检索）
└─ 高频问答 + 知识变化快 → RAG ✅（事实类）或 RAG+微调（风格+事实）
```

### 决策四维法（面试答题框架）

无论什么问题，先按四个维度分析再给结论：

| 维度 | 问题 | 决定方向 |
|---|---|---|
| 更新频率 | 知识多久变一次？ | 高→RAG；低→微调可选 |
| 安全要求 | 数据能进模型/进训练吗？ | 不能→RAG |
| 溯源需求 | 答案需要引用来源吗？ | 需要→RAG |
| 成本预算 | 训练 vs 每次请求哪个贵？ | 高频→微调分摊；低频→RAG |

### 场景对照速查

| 场景 | 推荐 | 理由 |
|---|---|---|
| 企业知识库问答 | RAG | 更新频繁、需溯源 |
| 客服机器人话术风格 | RAG + 微调 | 事实走 RAG，风格走微调 |
| 法律合同审查 | 长上下文 + RAG | 全文理解 + 条款检索 |
| 代码风格迁移 | 微调 | 风格内化、响应快 |
| 实时新闻问答 | RAG | 知识秒级更新 |
| 论文精读 | 长上下文 | 全局理解优先 |
| 垂直领域模型（医疗问答） | 微调 + RAG | 领域能力 + 指南事实 |

## 5. 组合使用策略

2026 年行业实践已不再是"三选一"，而是**组合**：

| 组合 | 结构 | 场景 |
|---|---|---|
| RAG + 微调 | 微调管风格/格式，RAG 管事实 | 客服（风格统一 + 事实实时） |
| RAG + 长上下文 | 长上下文管整体理解，RAG 管精准定位 | 合同审查（先全文再定位条款） |
| 微调 + 长上下文 | 微调管领域语言，长上下文塞资料 | 专业写作 |

### 组合设计三原则

1. **事实与风格分离**：事实类问题永远走 RAG（可溯源），风格类能力走微调（参数内化）
2. **成本分层**：高频简单问答走便宜路径，低频复杂任务走高成本路径
3. **安全优先**：私有数据一律不进入训练（微调禁用），只走 RAG 本地检索

### 组合示例：智能客服（最典型）

```
用户问题
  ├─ 事实类（政策/价格/进度）→ RAG 检索 → 生成（带引用）
  └─ 情绪/话术（安抚/道歉）→ 微调后的风格模型 → 生成（语气统一）
```

## 6. 面试高频问法

| 问题 | 回答要点 |
|---|---|
| RAG 和微调的区别？ | 知识存储位置：外挂检索 vs 参数内化；更新成本：秒级 vs 月级 |
| 为什么 RAG 治幻觉微调治不了？ | 微调改变参数分布仍可能编造；RAG 给模型真实文本依据、可引用 |
| 长上下文会取代 RAG 吗？ | 不会——成本差异悬殊；窗口再大也是每次全价输入，RAG 只付检索命中部分（详见根目录 18 篇） |
| 什么场景必须用微调？ | 特定输出格式、领域语言风格、低延迟高频调用、无法接受检索延迟 |
| 三者的最佳组合？ | 事实走 RAG、风格走微调、长文档走长上下文，按成本与场景分层 |
| RAG 的缺点？ | 检索质量是上限；多一跳延迟；知识库治理负担（脏数据进库） |
| 微调后还能用 RAG 吗？ | 能且推荐——微调改"表达能力"，RAG 改"知识内容"，互不冲突 |

### 标准答题模板（3 分钟版）

1. **下定义**：三者都是"给 LLM 注入知识"，路径不同——外挂、内化、直塞
2. **给对比**：RAG 赢在更新与溯源，微调赢在风格与速度，长上下文赢在全局
3. **做决策**：按"更新频率/安全/溯源/成本"四维判断
4. **给组合**：事实走 RAG、风格走微调、长文档走长上下文

## 7. 成本计算示例

把"成本差异"量化，选型才不是空谈。以下为量级估算（非精确报价）：

### 场景假设

- 知识库 100 万 token（约 200 篇文档）
- 每日 1000 次问答，每次需要 5000 token 上下文

### 三方案成本对比

| 方案 | 一次性成本 | 每日成本 | 更新成本 |
|---|---|---|---|
| RAG | 向量化费用（一次性，百元级） | 检索（免费）+ 生成 1000 × 1 万 token | 更新文档重新向量化（分钟级） |
| 微调 | 训练算力（万元级 + 数据准备） | 生成 1000 × 1 万 token（同生成成本） | 每次更新重新训练（周级） |
| 长上下文 | 无 | 1000 × 105 万 token（全量塞入） | 改 Prompt 即可 |

### 关键结论

| 结论 | 数字依据 |
|---|---|
| RAG 比长上下文省 100 倍+ 输入成本 | 5 千 token 检索 vs 100 万 token 全塞 |
| 微调的固定成本是 RAG 的几十倍 | 训练算力 vs 向量化 |
| RAG 的更新成本几乎为零 | 秒级 vs 月级 |
| 高频调用时微调可摊薄固定成本 | 10 万+ 次调用后持平 |

### 面试中的成本话术

> "同样的知识库问答场景，RAG 每次只支付检索命中的上下文成本，长上下文方案每次都要全量输入——RAG 的输入 token 成本大约只有后者的几十分之一；微调则把成本从每次转移到了训练的一次性投入，高频场景才划算。"

> 🎯 核心要点：**RAG 是"事实基础设施"，微调是"能力内化"，长上下文是"上下文宽松"**——三者不是竞争关系，是分工关系。面试答"选型"时先说决策维度（更新频率/安全/溯源/成本），再给结论；讲成本时用"每次 vs 一次性"的视角量化。
