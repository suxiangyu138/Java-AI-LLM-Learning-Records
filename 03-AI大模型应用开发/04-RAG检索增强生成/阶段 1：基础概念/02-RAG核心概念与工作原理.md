## 1. RAG 的标准定义

> RAG（Retrieval-Augmented Generation，检索增强生成）：在 LLM 生成前，先从外部知识库检索与问题最相关的文本片段，作为上下文注入提示词，让模型基于检索到的真实内容生成答案。

一句话公式：

```
RAG = 文本 → Embedding → 向量检索 → Prompt 增强 → LLM 生成
```

### 与普通 Prompt 工程的区别

| 维度 | 普通提示词 | RAG |
|---|---|---|
| 上下文来源 | 人工写死 | 检索动态获取 |
| 知识规模 | 提示词长度限制（几千 token） | 知识库规模（百万级文档） |
| 更新方式 | 改提示词 | 更新知识库 |
| 可扩展性 | 一次一个场景 | 一个库服务所有问题 |

RAG 的"检索"环节是它与"把所有知识硬塞进提示词"的本质区别：**提示词负责策略，检索负责知识**。

## 2. 三步核心流程

| 步骤 | 英文 | 做什么 | 类比 |
|---|---|---|---|
| 索引 | Indexing | 把外部知识（PDF/数据库/网页）切小块、转向量、存入向量库 | 图书馆编目上架 |
| 检索 | Retrieval | 用户提问 → 问题转向量 → 向量库搜最相关片段 | 按主题查图书 |
| 生成 | Generation | 检索片段 + 问题拼成 Prompt → LLM 生成基于事实的答案 | 带着资料写回答 |

### 2.1 索引（Indexing）

```
原始文档 → 解析 → 切片（Chunk）→ Embedding 向量化 → 向量库
```

- 输入：PDF、Word、HTML、Markdown、数据库记录等一切知识载体
- 关键步骤：**切片**——把长文档切成适合检索的小块（几百 token），切法直接影响检索质量
- 向量化：每个切片经 Embedding 模型转为高维向量（如 1024 维）
- 存储：向量库（FAISS/Milvus/pgvector 等）同时保存向量与原文

索引阶段的两个关键认知：

| 认知 | 说明 |
|---|---|
| 索引是一次性的吗？ | 不是——文档增删改都要重索引对应部分（增量更新，阶段 3） |
| 索引是"文本层"还是"向量层"？ | 两层都要：原文（给 LLM 看）+ 向量（给检索用） |

### 2.2 检索（Retrieval）

```
用户问题 → Embedding 向量化 → 向量库相似度搜索 → Top-K 片段
```

- 查询同样转向量，在向量库里做**相似度检索**（余弦相似度/内积等）
- 返回 Top-K（如 Top-5）最相似片段——**检索质量直接决定答案上限**
- 进阶：混合检索（关键词 + 向量）、重排序（Rerank），详见阶段 3

检索的本质是"语义匹配"：

```text
问题：怎么退款？        → 向量 A
文档：退费流程如下...    → 向量 B
相似度：0.93（高）→ 命中
```

这解决的是关键词检索解决不了的**同义不同词**问题——"退款"与"退费"字面不重合，但语义相同。

### 2.3 生成（Generation）

```
[系统提示] + [检索片段 1..K] + [用户问题] → LLM → 带依据的答案
```

- 把检索结果与原始问题拼进 Prompt（上下文增强）
- LLM 基于检索内容生成答案，可要求"只依据给定内容回答并标注来源"
- 生成策略可调：严格引用 / 总结融合 / 拒绝回答（检索不足时）

生成阶段的设计自由度（阶段 2/3 逐步展开）：

| 设计点 | 选项 | 场景 |
|---|---|---|
| 引用方式 | 严格逐条引用 | 合规、审计 |
| 拒答策略 | 检索不足时明说"没有" | 医疗/法律 |
| 上下文窗口管理 | 动态选择 Top-K 数量 | 长文档 |
| 多轮对话 | 携带历史 + 检索 | 客服 |

## 3. 完整链路拆解

```
┌────────────────── 离线（索引） ──────────────────┐
│  文档源 → 解析 → 切片 → Embedding → 向量库(入库)  │
└─────────────────────────────────────────────────┘
                    │
┌────────────────── 在线（查询） ──────────────────┐
│  用户问题 → 向量化 → 检索 Top-K → Prompt 组装     │
│      → LLM 生成 → 引用标注 → 返回答案             │
└─────────────────────────────────────────────────┘
```

| 阶段 | 发生时机 | 成本特征 |
|---|---|---|
| 索引 | 离线（文档新增/变更时） | 一次性，可批量、可缓存 |
| 查询 | 在线（每次提问） | 每次请求：检索 + 生成 |

这个"离线建索引、在线查询"的结构是理解 RAG 工程化的钥匙——索引可以慢慢建、建得好；查询必须快、必须稳。

### 链路延迟分布（经验值）

| 环节 | 耗时量级 | 优化方向 |
|---|---|---|
| 查询向量化 | 10-100ms | Embedding 模型大小 |
| 向量检索 | 1-50ms | 索引类型（HNSW/IVF） |
| Prompt 组装 | <1ms | 忽略 |
| LLM 生成 | 1-10s（TTFT 之后流式） | 模型选择、缓存 |

## 4. 核心组件职责

| 组件 | 职责 | 类比 |
|---|---|---|
| Embedding 模型 | 文本 ↔ 向量互转 | 翻译官（把人类语言译成机器可比的坐标） |
| 向量数据库 | 存向量 + 相似度检索 | 图书馆 + 检索员 |
| LLM | 基于检索上下文生成答案 | 拿到资料写报告的人 |
| RAG 框架 | 编排索引与查询流程 | 图书馆管理系统 |

### 组件间的依赖关系

```
Embedding 模型 ←→ 向量数据库（维度必须一致）
向量数据库 ←→ LLM（中间隔着一个 Prompt 组装器）
框架 → 组装器（把检索结果变成 Prompt）
```

**维度一致性**是组件间的第一约束：Embedding 输出维度（如 1024）必须等于向量库索引维度，否则检索失败或结果错误（阶段 2 的 05 篇有完整实验）。

## 5. 设计决策背后的权衡

RAG 不是"套上就完事"的模板，每个设计点都有权衡：

| 设计决策 | 选项 A | 选项 B | 权衡点 |
|---|---|---|---|
| 切片大小 | 大块（语义完整） | 小块（定位精准） | 粒度 vs 完整性 |
| Top-K | 大（信息全） | 小（噪音少） | 召回 vs 干扰 |
| 相似度阈值 | 有（拒答） | 无（总有结果） | 覆盖率 vs 准确率 |
| 检索方式 | 纯向量 | 混合（向量+关键词） | 语义 vs 字面 |
| 单轮/多轮 | 单轮（快） | 迭代（准） | 成本 vs 质量 |

> 💡 记住这个"权衡思维"：RAG 的所有参数都是**双刃剑**，没有绝对最优——这也是阶段 3 调优的核心方法论。

## 6. RAG 的两种查询路径

| 路径 | 流程 | 特点 |
|---|---|---|
| 基础路径 | 问题 → 检索 → 生成（一次性） | 简单，一次检索定成败 |
| 迭代路径 | 问题 → 检索 → 生成 → 评估 →（不足）再检索 | Agentic RAG，质量高、成本高 |

阶段 1 先掌握基础路径；迭代路径（Self-RAG、多轮反思）在阶段 4 展开。

### 什么时候必须用迭代路径

| 信号 | 说明 |
|---|---|
| 一次检索覆盖率不足 | 复杂问题需要多源信息 |
| 问题有歧义 | 需要澄清/拆解子问题 |
| 答案需要验证 | 生成后自查"依据是否充分" |
| 跨知识库聚合 | 多库路由 + 结果融合 |

## 7. 术语表

| 术语 | 含义 |
|---|---|
| Chunk / 切片 | 文档切成的检索单元（通常 200-1000 token） |
| Chunk Size | 切片大小，直接影响检索粒度与上下文占用 |
| Overlap | 相邻切片的重叠 token，防止语义被切断 |
| Embedding | 文本到向量的映射；语义相近的文本向量距离近 |
| 向量库 | 支持向量存储与 ANN（近似最近邻）检索的存储 |
| Top-K | 检索返回的相似片段数量 |
| 相似度检索 | 按向量距离/相似度找最近片段 |
| 语义鸿沟 | 关键词与语义的错位（如问"怎么退款"vs 文档写"退费流程"） |
| Prompt 增强 | 把检索结果注入提示词，构成带上下文的生成输入 |
| 上下文窗口 | LLM 一次能处理的最大 token 数，决定能塞多少检索内容 |
| 幻觉残留 | 检索质量差时模型仍可能编造，RAG 降低但不消除幻觉 |
| Rerank | 对 Top-K 召回结果二次精排（阶段 3 详解） |
| RAG 框架 | LangChain/LlamaIndex 等编排工具（阶段 1 的 04 篇） |
| ANN | Approximate Nearest Neighbor 近似最近邻（向量库核心技术） |
| HNSW | Hierarchical Navigable Small World 分层图索引（FAISS 常用） |
| 向量维度 | Embedding 输出的坐标数（BGE-large-zh 为 1024） |

### 术语记忆法

把术语按链路分组记忆：

```
数据层：Chunk / Chunk Size / Overlap / 元数据
向量层：Embedding / 维度 / 相似度 / ANN
检索层：Top-K / 阈值 / Rerank / 混合检索
生成层：Prompt 增强 / 上下文窗口 / 引用 / 拒答
架构层：Naive / Advanced / Agentic / 向量库选型
```

## 8. 易错概念辨析

| 易混淆 | 辨析 | 一句话区分 |
|---|---|---|
| 向量数据库 vs 关系数据库 | 向量库管相似度，关系库管精确条件 | 向量库问"像不像"，SQL 问"是不是" |
| Embedding vs 向量数据库 | Embedding 是模型（生成向量的），向量库是存储（存向量的） | 模型产出向量，库存储向量 |
| 检索 vs 搜索 | 检索是 RAG 内部环节，搜索是产品形态 | 检索是手段，搜索是产品 |
| Top-K vs 阈值 | Top-K 定数量，阈值定质量 | 先取 K 个，再过滤差的 |
| 相似度 vs 相关度 | 相似度是向量几何量，相关度是语义评价 | 相似≠相关（字面像但语义无关） |
| RAG vs RAG 框架 | RAG 是范式，框架是工具 | 框架帮你实现 RAG |
| 切片 vs 分块 | 同义（chunking） | 无区别，译法不同 |
| 索引 vs 缓存 | 索引是数据结构，缓存是重复利用 | 索引加速检索，缓存省成本 |

### 辨析记忆法

```
三个"库"别混：
知识库（原文）→ 向量库（向量）→ 缓存（结果）
```

> 🎯 核心要点：三步流程中，**索引决定"库里有什么"，检索决定"能拿回什么"，生成决定"能用出什么"**——链路越长，上游误差放大越明显。所以 RAG 优化的第一优先永远是检索质量。概念辨析记住三个"库"（知识库/向量库/缓存）就不混。
