## 1. 四件套总览

| 组件 | 职责 | 决策关键 |
|---|---|---|
| Embedding 模型 | 文本↔向量互转 | 语言能力、维度、成本、是否本地 |
| 向量数据库 | 存储 + ANN 检索 | 规模、部署方式、已有基础设施 |
| LLM | 基于上下文生成 | 推理质量、成本、上下文窗口 |
| 编排框架 | 串起索引与查询流程 | 生态、团队语言、复杂需求 |

选型核心逻辑：**先定规模与部署约束，再选组件**——数据量、是否上云、是否信创，决定了 90% 的选择。

### 四件套的依赖关系（谁先定）

```
先定：部署约束（云/本地/信创）
  ↓
Embedding 与向量库（维度必须配对）
  ↓
LLM（能力与预算）
  ↓
框架（团队语言）
```

## 2. Embedding 模型选型

| 模型 | 特点 | 适用 |
|---|---|---|
| BGE-M3 | 多语言、多粒度、多功能（稠密+稀疏） | 中文场景首选之一 |
| BGE-large-zh | 中文专精，效果好 | 纯中文知识库 |
| text-embedding-3 | OpenAI 生态，API 方便 | 已用 OpenAI 体系 |
| voyage/Cohere embed | 长文本/多语言商业方案 | 海外生产 |
| 本地部署 BGE 系列 | 数据不出内网 | 保密要求高 |

### 选型五问

| 问题 | 影响 |
|---|---|
| 语种是什么？ | 中文→BGE 系列；混合→BGE-M3 或商业多语言 |
| 数据能出网吗？ | 不能→本地部署（BGE 等开源） |
| 维度多少合适？ | 1024 维平衡存储与精度；1536+ 更准更贵 |
| 预算多少？ | 开源免费 vs API 按量 |
| 效果怎么验证？ | 用业务样本实测相似度排序（不要只看榜单） |

### 关键数据（中文场景）

| 指标 | 通用多语言模型 | BGE 中文模型 |
|---|---|---|
| 近义词相似度（"退款申请"/"申请退款"） | 约 0.72 | 0.95+ |
| 维度 | 1536 | 1024 |
| 存储（万块） | 约 12MB | 约 8MB（-44%） |
| 检索速度 | 基准 | +35% |

## 3. 向量数据库选型

| 方案 | 定位 | 适用规模 |
|---|---|---|
| Chroma / FAISS | 本地/快速验证 | 原型、个人项目、小规模 |
| pgvector | PostgreSQL 扩展 | 已有 PG 业务、中小规模 |
| Qdrant / Milvus Lite | 中小规模生产 | 起步生产的平衡点 |
| Milvus | 大规模企业级 | 百万级向量、高并发 |
| Pinecone | 托管 SaaS | 不想运维、预算充足 |
| Elasticsearch | 全文 + 向量一体 | 已有 ES 业务（混合检索天然支持） |

### 选型决策

```
验证原型 → Chroma/FAISS
已有 PG → pgvector（零新增组件）
中小规模 → Qdrant / Milvus Lite
大规模/企业 → Milvus
不运维 → Pinecone
已有 ES → ES 8.x（关键词+向量一体）
```

### 向量库核心能力对照

| 能力 | FAISS | pgvector | Milvus | ES |
|---|---|---|---|---|
| 部署形态 | 库（进程内） | PG 扩展 | 独立服务 | 独立服务 |
| 过滤检索（元数据条件） | ❌ | ✅ SQL | ✅ | ✅ |
| 混合检索（关键词+向量） | 需自组 | ✅（pg_trgm） | ✅ | ✅ 原生 |
| 分布式/高可用 | ❌ | ✅ | ✅ | ✅ |
| 事务 | ❌ | ✅ | 部分 | ❌ |
| 典型定位 | 原型/理解 | 中小生产 | 大规模生产 | 已有 ES 升级 |

> 💡 国内生产环境常见组合：Milvus（独立向量库）或 pgvector（复用 PG），配合 ES 做混合检索——阶段 3 详解。

## 4. LLM 选型

| 模型 | 特点 | 适用 |
|---|---|---|
| Claude 系列 | 推理质量顶尖、长上下文 | 高质量问答 |
| GPT 系列 | 生态成熟、工具调用好 | 通用生产 |
| DeepSeek | 中文强、价格低、开源 | 成本敏感 + 中文 |
| Qwen 系列 | 中文强、开源、部署灵活 | 国产化/私有化 |
| Gemini 系列 | 超长上下文 | 长文档场景 |

### RAG 场景对 LLM 的核心要求

| 要求 | 为什么 |
|---|---|
| 遵循指令强 | 严格"只依据检索内容"，不自由发挥 |
| 上下文窗口够 | 容纳 Top-K 检索片段 + 问题 |
| 中文表达好 | 中文场景的基本盘 |
| 成本可控 | 每轮都带检索上下文，token 消耗大 |

### 接入方式

| 方式 | 说明 | 场景 |
|---|---|---|
| API（云服务） | DeepSeek/OpenAI 等 | 快速上线 |
| 本地推理（vLLM/Ollama） | 开源模型私有部署 | 数据敏感、降本 |
| 混合 | 常规 API + 敏感走本地 | 折中 |

## 5. RAG 编排框架选型

| 框架 | 特点 | 适用 |
|---|---|---|
| LangChain | 生态最全、组件多 | 通用、快速集成 |
| LlamaIndex | 专注 RAG、组件粒度细 | RAG 深度定制 |
| Haystack | 企业级、生产友好 | 企业项目 |
| Spring AI | Java 官方生态 | Java 后端团队 |
| Dify / FastGPT / Coze | 低代码平台 | 非工程团队、快速交付 |

### 框架 vs 零框架

| 维度 | 用框架 | 零框架（手写） |
|---|---|---|
| 开发速度 | 快（现成组件） | 慢（全自建） |
| 可控性 | 中（框架抽象） | 高（每行代码可见） |
| 学习价值 | 低（黑盒） | 高（原理通） |
| 生产稳定性 | 高（社区验证） | 取决于自己 |
| 2026 趋势 | 框架变薄 | 向量库原生能力 + LLM 直调 |

> 💡 学习路径建议：**先用零框架跑通原理（阶段 2），再用框架提效（阶段 3+）**——直接上框架容易"会调用但不懂原理"。

| 场景 | Embedding | 向量库 | LLM | 框架 |

## 7. 选型决策方法论

### 三问定基调

| 问题 | 回答方向 |
|---|---|
| 数据量多大？ | <1 万块：Chroma/FAISS；<100 万：pgvector/Qdrant；更大：Milvus |
| 能上云吗？ | 能：Pinecone/云托管的灵活；不能：全本地化 |
| 团队什么语言？ | Python：LangChain/LlamaIndex；Java：Spring AI |

### 技术栈演进路线（推荐）

```
阶段 2（本系）：FAISS + BGE + DeepSeek API（零框架理解原理）
阶段 3：pgvector/Milvus + 混合检索 + Rerank（工程化）
阶段 4：Agentic 编排 + 评估闭环（生产级）
```

## 8. 选型常见误区与决策陷阱

| 误区 | 真实情况 | 正确做法 |
|---|---|---|
| 只看榜单选 Embedding | 榜单测试集≠你的业务 | 用业务样本实测排序质量 |
| 上来就上 Milvus | 万级数据用 FAISS 就够 | 按数据量分层，别过度设计 |
| 框架选最流行的 | LangChain 生态全但不一定适合 | 按团队语言与复杂度选 |
| 忽略维度一致性 | 换 Embedding 忘改向量库维度 | 配置集中管理 + 启动断言 |
| 以为向量库能解决一切 | 混合检索要关键词配合 | 向量 + BM25 互补（阶段 3） |
| 云端万能 | 数据合规场景必须本地 | 先问"数据能出网吗" |
| 全用商业 API | 高频调用成本失控 | 开源本地模型 + API 混合 |

### 选型后的验证清单（换栈必做）

| 验证项 | 方法 |
|---|---|
| Embedding 效果 | 10 组业务近义词相似度实测（04 篇实验） |
| 向量库性能 | 千级向量检索耗时 <50ms |
| LLM 遵循度 | 5 个测试问题"只依据资料"是否生效 |
| 端到端质量 | 20 问测试集通过率 ≥80% |

> 🎯 核心要点：技术栈没有"最好"，只有"匹配"——先回答三个问题：数据量多大？能不能上云/必须内网？团队用什么语言？答案出来，四件套基本定型。选型之后记得跑验证清单，别让选型成为"拍脑袋"。
