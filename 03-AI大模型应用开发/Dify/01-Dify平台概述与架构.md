## 1. Dify 是什么

### 1.1 一句话定位

```text
Dify = 开源 LLM 应用开发平台

让你在几分钟内：
├── 搭建基于 LLM 的聊天助手
├── 构建 RAG 知识库问答系统
├── 编排多步骤 AI 工作流
├── 创建具备工具调用能力的 Agent
└── 一键发布为 API / Webhook / 嵌入网页
```

### 1.2 核心价值

| 价值 | 说明 | 传统方式对比 |
|------|------|------------|
| **可视化编排** | 拖拽节点构建 AI 工作流 | 手写 LangChain/LlamaIndex 代码 |
| **模型无关** | 一套代码对接 OpenAI/DeepSeek/Ollama/通义千问... | 每个模型写不同的客户端代码 |
| **RAG 开箱即用** | 上传文档→自动分段→向量化→搜索→问答 | 手动搭建 Embedding + 向量 DB + 检索逻辑 |
| **API 即服务** | 构建完成直接生成 REST API | 另写 FastAPI/Spring Boot 包装 |
| **日志与标注** | 内置 LLM 调用日志、用户反馈、标注系统 | 需要自己搭建监控 |
| **多租户** | 团队协作、应用权限管理 | 自建 |
| **开源** | Apache 2.0 协议，可私有化部署 | Coze 等竞品闭源 |

### 1.3 发展里程碑

| 时间 | 里程碑 |
|------|--------|
| 2023.03 | Dify 开源，首个版本发布 |
| 2023.08 | GitHub Stars 突破 10K |
| 2024.01 | 工作流功能上线（Workflow DSL） |
| 2024.05 | Agent 功能上线（ReAct + Function Call） |

| 2025.02 | GitHub Stars 突破 60K |
| 2026.06 | 插件生态 + MCP 协议支持 |

```text
│       └──────────────┴────────────┴──────────────┘          │
│                          │                                   │
├──────────────────────────┼───────────────────────────────────┤
│                    Dify API (Python Flask)                    │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐   │
│  │ App      │ │ Dataset  │ │ Workflow │ │ Plugin       │   │

│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐   │
│  │ 文档处理  │ │ Embedding│ │ LLM 调用  │ │ 定时任务      │   │

```

### 2.2 核心组件说明

| 组件 | 技术栈 | 职责 | 部署方式 |
|------|--------|------|---------|
| **API Server** | Python Flask + Gunicorn | 处理 HTTP 请求、业务逻辑 | `docker compose up api` |
| **Web Frontend** | Next.js (React) | 可视化操作界面 | `docker compose up web` |
| **Worker** | Celery + Python | 异步任务（文档处理、Embedding） | `docker compose up worker` |
| **PostgreSQL** | PostgreSQL 15+ | 元数据存储（应用配置、用户、日志） | Docker 容器 |
| **Redis** | Redis 7+ | 消息队列（Celery Broker）+ 缓存 | Docker 容器 |
| **向量数据库** | Weaviate / Qdrant / Milvus / pgvector | 存储文档向量，语义搜索 | 可选，Weaviate 内置 |
| **Nginx** | Nginx | 反向代理、SSL 终结 | Docker 容器 |

### 2.3 数据流

```text
用户上传文档到知识库：

  Web UI → API Server → Celery Queue
                           │
                    ┌──────▼──────┐
                    │   Worker     │
                    │  1. 解析文档  │ (PDF/Word/HTML/Markdown...)
                    │  2. 分段清洗  │ (按段落/自定义分隔符)
                    │  3. 调用      │
                    │     Embedding │ (OpenAI text-embedding-3)
                    │  4. 写入      │
                    │     向量数据库 │ (Weaviate/Qdrant)
                    └──────────────┘

用户发起聊天提问：

  Web UI → API Server → 工作流引擎
                           │
            ┌──────────────┼──────────────┐
            │              │              │
    ┌───────▼───────┐ ┌───▼────┐ ┌─────▼──────┐
    │ 知识库检索     │ │ LLM 调用│ │ 工具调用    │
    │ (语义搜索)     │ │ (生成)  │ │ (API/代码) │
    └───────┬───────┘ └───┬────┘ └─────┬──────┘
            │              │              │
            └──────────────┼──────────────┘
                           │
                    ┌──────▼──────┐
                    │ 返回答案     │
                    │ + 引用来源   │
                    └─────────────┘
```

## 3. 核心概念体系

### 3.1 应用类型

| 类型 | 说明 | 适用场景 | 复杂度 |
|------|------|---------|:---:|
| **聊天助手** | 对话式 AI，支持知识库 + 变量 | 客服机器人、知识问答 | ⭐⭐ |
| **文本生成** | 单次输入→输出，无对话历史 | 翻译、摘要、文案生成 | ⭐ |
| **Agent** | 具备工具调用能力 | 数据分析、自动化任务 | ⭐⭐⭐ |
| **工作流** | 可视化多步骤编排 | 复杂业务流程 | ⭐⭐⭐⭐ |

### 3.2 知识库（Dataset）

```text
知识库 = 文档集合 + 向量索引

支持的数据源：
├── 上传文件：PDF、Word、Excel、PPT、TXT、Markdown、HTML、CSV
├── 在线网页：URL 抓取、递归爬取
├── Notion：直接同步 Notion 页面
├── API：通过 API 增删文档
└── 手动输入：直接粘贴文本

处理流程：
文档上传 → ETL 管道 → 分段清洗 → Embedding 向量化 → 写入向量数据库
```

### 3.3 模型供应商

| 类别 | 代表模型 | Dify 中的供应商名称 |
|------|---------|-------------------|
| **LLM (对话生成)** | GPT-4o, Claude, DeepSeek-V4, Qwen | OpenAI / Anthropic / DeepSeek / 通义千问 |
| **Embedding (向量化)** | text-embedding-3, bge-large, jina-embeddings | OpenAI / HuggingFace / Jina |
| **Rerank (重排序)** | bge-reranker, Cohere Rerank | HuggingFace / Cohere |
| **TTS (语音)** | OpenAI TTS, Azure Speech | OpenAI / Azure |
| **STT (语音识别)** | Whisper, SenseVoice | OpenAI / 本地模型 |

## 5. 适用场景与局限

### 5.1 适合场景

```text
✅ 企业内部知识库问答系统
✅ 客服机器人（接入企业文档、FAQ）
✅ AI 辅助内容生成平台（营销文案、产品描述）
✅ 数据分析 Agent（SQL 生成 + 自然语言查询）
✅ API 聚合工作流（LLM + HTTP 请求 + 代码节点）
✅ 教育/培训领域的智能助教
✅ 代码审查助手（结合 Git 知识库）
```

### 5.2 当前局限

```text
⚠️ 不适合：
├── 实时性要求极高（<100ms）的场景 → Dify 每次调用经过多节点
├── 需要复杂前端交互的 AI 应用 → 不适合直接嵌入，需自建前端
├── 大规模并发（10K+ QPS）→ 需要深度定制 + K8s 集群
├── 完全离线场景 → 依赖外部 API（除非全部换成本地模型 + Ollama）
└── 替代传统后端业务逻辑 → 适合编排 AI 相关任务，不是通用后端框架
```

> 🎯 **核心要点**：Dify 定位是"AI 应用编排平台"，不是"通用后端框架"。把 Dify 当作 AI 能力层，Spring Boot 等传统后端负责业务逻辑和 API 编排，是最佳搭配。
