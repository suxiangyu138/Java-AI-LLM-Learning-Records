## 1. 知识库创建与文档管理

### 1.1 创建知识库

```text
首页 → 知识库 → 创建知识库

步骤：
1. 命名：如"产品帮助文档 v2.3"
2. 选择文档来源：
   ├── 导入已有文本
   ├── 上传本地文件（批量支持）
   ├── 从网页获取（URL 批量导入）
   └── 从 Notion 同步
3. 选择分段策略（详见第 2 节）
4. 选择 Embedding 模型（详见第 3 节）
5. 选择检索设置（详见第 4 节）
```

### 1.2 支持的文件格式

| 格式 | 支持程度 | 说明 |
|------|:---:|------|
| **Markdown (.md)** | ✅ 完美 | 最佳格式，天然结构化 |
| **TXT** | ✅ 完美 | 纯文本，无格式 |
| **PDF** | ✅ 好 | 含 OCR 识别（图片中的文字） |
| **DOCX / DOC** | ✅ 好 | Word 文档 |
| **HTML** | ✅ 好 | 网页格式 |
| **CSV** | ⚠️ 中等 | 表格数据，行式分段 |
| **Excel (.xlsx)** | ⚠️ 中等 | 多工作表需注意 |
| **PPT / PPTX** | ⚠️ 中等 | 幻灯片格式 |
| **EPUB** | ⚠️ 有限 | 电子书 |
| **图片 (PNG/JPG)** | ⚠️ 有限 | 依赖 OCR（中文 OCR 精度有限） |

### 1.3 文档管理

```text
知识库 → 文档列表 → 操作：

├── 添加文档：拖拽上传 / URL 导入 / Notion 同步
├── 重新处理：修改分段策略后重新向量化
├── 启用/禁用：暂不使用的文档可禁用（不参与检索）
├── 删除：彻底从向量数据库中删除
├── 查看详情：文档元数据、分段列表、字符统计
└── 同步状态：监控文档处理进度（排队 → 处理中 → 完成）
```

### 1.4 知识库维护

```text
维护策略：

1. 增量更新：
   └── 添加新文档 → 自动分段 → 自动向量化 → 立即可检索

2. 全量重处理：
   └── 修改分段策略/Embedding 模型 → 批量重新向量化（耗时）

3. 版本管理：
   └── 导出知识库配置 → 复用到其他环境

4. 质量监控：
   └── 定期检查：哪些文档从未被检索到 → 可能需要补充/删除
```

## 2. 文档处理：分段与清洗

### 2.1 分段策略

```text
分段 (Chunking) = RAG 质量的第一决定因素

Dify 提供的分段模式：

┌─────────────────────────────────────────────────────────────┐
│ 模式           │ 原理                │ 适合场景              │
├─────────────────────────────────────────────────────────────┤
│ 自动分段       │ 智能检测段落边界     │ 通用文档（默认）      │
│ 自定义分隔符   │ 按指定分隔符切分     │ 结构化文档            │
│ 按段落         │ 按自然段（换行符）   │ 排版规范的文档        │
│ 按字数         │ 固定长度窗口+重叠    │ 长文/论文/书籍        │
│ QA 模式        │ 问题-答案成对切分   │ FAQ 文档              │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 分段参数调优

| 参数 | 说明 | 推荐值 | 影响 |
|------|------|:---:|------|
| **分段最大长度** | 单段包含的最大字符数 | 500-800 | 太短切断语义，太长稀释相关性 |
| **分段重叠长度** | 相邻段重复的字符数 | 10-20% | 避免在句子边界截断关键信息 |
| **分段分隔符** | 优先级切割符号 | `\n\n` > `\n` > `。` > `.` > ` ` | 保持语义完整性 |

```text
分段过短 vs 过长的影响：

❌ 太短（200 字符）：
   分段："Dify 是一个开源的"
   → 语义不完整，检索效果差

❌ 太长（3000 字符）：
   分段：包含 5 个不相关主题的段落
   → 检索精度低，噪声大

✅ 恰当（500-800 字符）：
   分段：一个完整的概念/步骤/功能描述
   → 检索精准，LLM 能正确理解
```

### 2.3 清洗模式

```text
Dify 文档处理中的清洗选项：

├── 移除空白行 → 减少无效分段
├── 移除 URL → 去除纯网址内容
├── 移除 Email → 去除邮箱地址
├── 移除特殊字符 → 清理不可见字符
├── 智能清洗 → AI 判断内容质量
└── 保留元数据 → 文件名、来源、页数等
```

### 2.4 QA 分段模式（FAQ 优化）

```text
适合 FAQ / 帮助文档：

原始文档格式：
Q: 如何重置密码？
A: 在登录页点击"忘记密码"，输入注册邮箱...

Q: 退款需要多久？
A: 退款审核通过后 3-5 个工作日到账...

QA 分段后，每对 QA 是一个独立分段。
检索时直接匹配问题，返回完整答案。
→ RAG 准确率提升 30-50%（对比通用分段）
```

## 3. Embedding 模型与向量数据库

### 3.1 Embedding 模型选型

| 模型 | 维度 | 语言 | 成本 | 评分 |
|------|:--:|------|:---:|:---:|
| **OpenAI text-embedding-3-small** | 512 | 多语言 | $0.02/1M tokens | ⭐⭐⭐⭐⭐ |
| **OpenAI text-embedding-3-large** | 3072 | 多语言 | $0.13/1M tokens | ⭐⭐⭐⭐⭐ |
| **bge-large-zh-v1.5** (BAAI) | 1024 | 中文 | 免费 (本地) | ⭐⭐⭐⭐⭐ |
| **bge-m3** (BAAI) | 1024 | 多语言 | 免费 (本地) | ⭐⭐⭐⭐⭐ |
| **jina-embeddings-v3** | 1024 | 多语言 | 免费额度 | ⭐⭐⭐⭐ |
| **通义千问 text-embedding-v4** | 2048 | 多语言 | ¥ | ⭐⭐⭐⭐ |
| **Cohere Embed v3** | 1024 | 英语 | 免费额度 | ⭐⭐⭐⭐ |

> 🎯 **推荐**：中文场景 → `bge-large-zh-v1.5` 免费且效果极好；中英混合 → `bge-m3`；追求省心 → `text-embedding-3-small`

### 3.2 向量数据库选型

| 数据库 | 类型 | 部署难度 | 性能 | 过滤 | Dify 集成 |
|------|------|:---:|:---:|:---:|:---:|
| **Weaviate** | 专用向量 DB | ⭐⭐ (内置) | ⭐⭐⭐⭐ | ✅ 强大 | ✅ 默认内置 |
| **Qdrant** | 专用向量 DB | ⭐⭐ | ⭐⭐⭐⭐⭐ | ✅ 强大 | ✅ |
| **Milvus** | 专用向量 DB | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ✅ 强大 | ✅ |
| **pgvector** | PostgreSQL 扩展 | ⭐ (已有 PG) | ⭐⭐⭐ | ⚠️ 基础 | ✅ |
| **Chroma** | 轻量向量 DB | ⭐ | ⭐⭐⭐ | ⚠️ 有限 | ✅ |
| **Elasticsearch** | 全文搜索引擎 | ⭐⭐⭐ | ⭐⭐⭐⭐ | ✅ 强大 | ✅ |

```bash
# Dify .env 中切换向量数据库
# 默认 Weaviate（内置在 docker-compose 中）
VECTOR_STORE=weaviate

# 切换到 Qdrant
VECTOR_STORE=qdrant
QDRANT_URL=http://your-qdrant-host:6333
QDRANT_API_KEY=your_api_key

# 切换到 pgvector（最轻量，无需额外容器）
VECTOR_STORE=pgvector
PGVECTOR_HOST=db
PGVECTOR_PORT=5432
PGVECTOR_USER=postgres
PGVECTOR_PASSWORD=your_password
PGVECTOR_DATABASE=dify
```

### 3.3 向量数据库的 Dify 视角

```text
Dify 自动完成：
✅ 文档 → 分段 → 调 Embedding API → 写入向量 DB
✅ 用户提问 → 调 Embedding API → 向量相似度搜索 → 返回 Top-K
✅ 元数据过滤（按文档来源/日期/标签等）
✅ 向量重建（修改 Embedding 模型后重新处理）

你不需要写：
❌ 向量索引创建
❌ 向量查询代码
❌ 相似度计算
❌ 数据库维护
```

## 4. 检索策略对比与调优

### 4.1 三种检索模式

```text
Dify 知识库检索设置：

┌─────────────────────────────────────────────────────────────┐
│ 检索模式        │ 原理                │ 优势              │
├─────────────────────────────────────────────────────────────┤
│ 1. 向量检索     │ Embedding 相似度匹配 │ 语义理解好        │
│ 2. 全文检索     │ BM25 关键词匹配     │ 精确匹配好        │
│ 3. 混合检索     │ 向量 + 全文融合      │ ✅ 兼得二者优势   │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 检索参数调优

| 参数 | 说明 | 推荐值 | 影响 |
|------|------|:---:|------|
| **Top-K** | 返回的最相关片段数 | 3-5 | 太少信息不足，太多噪声干扰 |
| **分数阈值** | 低于此分数的片段被丢弃 | 0.5-0.7 | 过滤低质量结果 |
| **Rerank** | 二次精排序 | ✅ 开启 | 大幅提升 Top-3 准确率 |
| **Rerank Top-N** | Rerank 前取多少个候选 | 10-20 | 召回池大小 |
| **权重 (混合检索)** | 向量：全文的权重比 | 0.7:0.3 | 偏语义理解 |
| **元数据过滤** | 按标签/日期/来源筛选 | 按需 | 缩小检索范围 |

### 4.3 Rerank 重排序

```text
为什么要 Rerank？

向量检索 (粗排)：
  用户问："如何退款？"
  向量召回 Top-10：
  1. "退款流程说明" ← 相关性 0.82
  2. "支付方式介绍" ← 相关性 0.78 (语义相近但无关！)
  3. "订单取消政策" ← 相关性 0.76
  ...

Rerank 精排后：
  1. "退款流程说明" ← 高相关 ✅
  2. "退款到账时间" ← 高相关 ✅
  3. "订单取消政策" ← 中相关
  → "支付方式介绍" 被踢出 Top-3 ✅

推荐 Rerank 模型：
├── bge-reranker-v2-m3 (BAAI) ← 免费、中文好、本地部署
├── Cohere Rerank v3 ← API 调用，英文最好
└── jina-reranker-v2 ← 多语言
```

### 4.4 检索配置最佳实践

```text
场景 → 推荐配置：

1. 产品帮助文档问答
   混合检索、TopK=4、Rerank=ON、权重=0.7:0.3

2. 法律/合规文档
   混合检索、TopK=5、Rerank=ON、权重=0.5:0.5
   （关键词精确匹配很重要）

3. FAQ 简短问答
   向量检索、TopK=3、Rerank=OFF
   （QA 分段已足够精准）

4. 长文档摘要/研究
   向量检索、TopK=6、Rerank=ON、分段长度=1000
   （需要更大上下文）

5. 多语言文档
   混合检索、TopK=3、Rerank=ON、bge-m3 Embedding
   （跨语言语义理解）
```

## 5. RAG 质量评估与优化

### 5.1 质量检查清单

```text
RAG 质量差 = 用户觉得 AI 不准确

常见问题诊断：

□ 回答"我不知道"/"知识库中没有" 太多
  → Top-K 太小？分数阈值太高？知识库真的缺内容？

□ 回答中有编造的信息（幻觉）
  → 提示词未强调"仅基于提供的上下文"
  → 上下文片段相关性不够

□ 引用了知识库片段但答非所问
  → 检索策略有问题（全文检索权重太高等致关键词污染）
  → 需要 Rerank

□ 回答太泛，没有具体细节
  → 分段太短（信息被截断）
  → Top-K 不够

□ 列出的引用来源不对
  → LLM 幻觉了引用序号
  → 在提示词中要求引用具体原文
```

### 5.2 调优迭代流程

```text
循环优化 RAG：

1. 准备 20-30 个测试问题（覆盖各类场景）
2. 逐题查看回答 + 引用片段
3. 记录问题（偏题/遗漏/幻觉/引用错误）
4. 调整参数（分段长度/TopK/Rerank/检索模式）
5. 如果检索没问题但回答差 → 调提示词
6. 如果检索本身差 → 调分段策略/Embedding模型
7. 如果内容本身缺 → 补充文档
8. 重新测试 → 对比改进差异
```

### 5.3 提示词中引导正确引用

```jinja2
{# 强制引用知识库内容 #}

{% if context %}
参考以下知识库片段回答问题：

{% for doc in context %}
---
来源: {{doc.metadata.source}}
片段 {{loop.index}}:
{{doc.content}}
---
{% endfor %}

回答要求：
1. 必须基于以上片段，不要编造信息
2. 如果某片段包含答案，请在回答后引用片段编号
3. 如果以上片段都不包含答案，请明确说"知识库中暂无相关信息"
4. 回答格式：先给出答案，然后列出引用的片段编号

{% else %}
知识库中没有找到相关信息。请告知用户暂时无法回答此问题，
并建议联系人工客服获取帮助。
{% endif %}

用户问题：{{query}}
```
