## 1. Collection 与 Schema

**Collection（集合）**：Milvus 的数据容器——类比关系型的"表"。

**Schema（模式）**：Collection 的结构定义——类比"建表语句"，**创建后不可修改**（3.0 前；3.0 起支持在线演进，见 01 模块）：

```python
from pymilvus import CollectionSchema, FieldSchema, DataType, Collection

# Schema 定义（类比 CREATE TABLE）
fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True, auto_id=False),
    FieldSchema(name="document_id", dtype=DataType.VARCHAR, max_length=64),
    FieldSchema(name="title", dtype=DataType.VARCHAR, max_length=512),
    FieldSchema(name="content", dtype=DataType.VARCHAR, max_length=65535),
    FieldSchema(name="metadata", dtype=DataType.JSON),                    # 灵活元数据
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=1536) # 向量字段
]
schema = CollectionSchema(fields=fields, description="文档知识库")
collection = Collection(name="document_kb", schema=schema)
```

**Schema 设计铁律**：

1. **向量字段必声明维度**（dim=1536——与 Embedding 模型输出对齐，如 OpenAI text-embedding-3 / BGE）；
2. **主键必选**（INT64 自增或 VARCHAR）；`auto_id=True` 时插入不用带主键；
3. **检索不返回的字段要想好**：embedding 维度大，查询默认带出会浪费带宽（用 `output_fields` 控制）；
4. **先设计后建集**：Collection 创建后字段不可改（2.x）——**Schema 即合同**。

> 🎯 **核心要点**：Schema 是 Milvus 的"表结构"——**一次创建，长期使用**（2.x 不可改；3.0 起支持在线演进）。设计时想清楚"检索要返回哪些字段"（output_fields）与"过滤要用哪些字段"（标量索引）。

## 2. 字段类型全景（含 3.0 新类型）

| 分类 | 类型 | 说明 |
|------|------|------|
| 数值 | INT8/16/32/64、FLOAT、DOUBLE | 常规标量 |
| 字符串 | **VARCHAR** | 短文本/ID（需 max_length） |
| 文本 | **TEXT（3.0 一等类型）** | 长文本原文（支持 BM25 全文检索，无需 max_length） |
| 布尔 | BOOL | |
| 时间 | DATE、TIMESTAMP、**TIMESTAMPTZ（3.0，实体级 TTL）** | |
| JSON | JSON | 灵活元数据（可过滤） |
| 数组 | ARRAY（2.4+） | 标量数组 |
| 二进制 | **BLOB（3.0）** | 文件/图片/视频二进制 |
| 向量 | FLOAT_VECTOR 等六种（下节） | 检索主体 |

**TEXT 类型的价值（3.0）**：

```text
2.x 的做法：content 存 VARCHAR + 外挂 ES 做全文检索（两套系统）
3.0 的做法：TEXT 字段直接存原文 → Milvus 内置 BM25 索引
→ 向量检索 + 全文检索 + 原文存储，一个库全搞定
```

> 💡 VARCHAR vs TEXT：短 ID/标题用 VARCHAR（可排序/索引），长正文用 TEXT（3.0 起；2.5 起 VARCHAR 超长内容也能走 BM25 但 TEXT 更规范）。

## 3. 向量字段：六种向量类型

| 向量类型 | 说明 | 典型来源 | 版本 |
|---------|------|---------|:----:|
| FLOAT_VECTOR | 标准稠密向量（float32） | OpenAI/BGE 等 Embedding | 一直 |
| FLOAT16_VECTOR | 半精度（省内存，精度略降） | 移动端/大模型 | 2.4+ |
| BFLOAT16_VECTOR | 脑浮点（训练友好） | 大模型内部 | 2.4+ |
| BINARY_VECTOR | 二值向量（哈希式） | 图像相似（感知哈希） | 一直 |
| INT8_VECTOR / INT4_VECTOR | 量化向量 | 量化模型输出 | 2.4+ |
| **SPARSE_FLOAT_VECTOR** | **稀疏向量**（大部分为 0） | **BM25/Splade 等** | **2.4+（混合检索关键）** |

```python
# 稀疏向量字段（混合检索的基石）
FieldSchema(name="sparse_embedding", dtype=DataType.SPARSE_FLOAT_VECTOR)
# 稀疏向量的存储形态：{token_id: weight} 字典，大部分位置为 0
# 用途：BM25BuiltInFunction 自动从 TEXT 字段生成，或 Splade 等学习型稀疏模型输出
```

**稠密 vs 稀疏（面试必答）**：

| 维度 | 稠密向量 | 稀疏向量 |
|------|---------|---------|
| 形态 | 固定维数（1536 等）密集数值 | 高维（词表大小）但大部分为 0 |
| 语义 | 整体语义相似度 | **词汇精确匹配**（BM25/词权重） |
| 擅长 | 描述性/语义查询（"少年在瓜田刺猹"） | 精确术语/专名（"藤野先生"） |
| 来源 | Embedding 模型 | BM25 内置生成 / Splade |
| 检索 | ANN（HNSW 等） | 倒排索引（SINDI） |

> 🎯 **核心要点**：**"稠密管语义、稀疏管关键词"**——两者互补（精确术语语义检索可能漏），**混合检索 = 两者同时查 + 融合排序**（见 06 模块）。SPARSE_FLOAT_VECTOR 是 2.4+ 混合检索的数据基础。

## 4. 主键与唯一性

| 主键类型 | 说明 | 场景 |
|---------|------|------|
| INT64 + auto_id=False | 业务自定义长整型主键 | 业务 ID 直接作主键 |
| INT64 + auto_id=True | Milvus 自动生成 | 无自然主键 |
| VARCHAR | 字符串主键（如 UUID/文档 ID） | 与外部系统对齐 |
| **3.0 全局主键去重** | 跨分片全局唯一（2.x 按分片） | 数据管道幂等写入 |

**主键的工程作用**（不只是唯一性）：

```python
# upsert：主键存在则更新，不存在则插入（2.4+ 原子操作）
collection.upsert([{"id": 1, "title": "新标题", "embedding": [...]}])

# delete by 主键
collection.delete(expr="id in [1, 2, 3]")

# 幂等写入的关键：数据管道重跑不产生重复
# → 用外部系统 ID（文档 ID）作主键，重跑 upsert 即可
```

> 🎯 **核心要点**：主键 = "**数据管道的幂等锚点**"——RAG 知识库增量更新（新增/修改/删除文档）全部靠主键操作（upsert/delete by PK）。**用文档 ID（如 `${source_path}:${chunk_index}`）作主键**是标准实践。

## 5. 分区与分片：数据组织

```text
Collection
├── Shard 0（主键哈希分布）     ← 分片：水平切分（写入并行度）
├── Shard 1
├── Shard 2
└── Partition（可选分组）       ← 分区：按业务维度分组（检索可指定）
    ├── 分区 1（如 2026-01）
    └── 分区 2（如 2026-02）
```

| 机制 | 作用 | 使用方式 |
|------|------|---------|
| **分片（Shard）** | 写入水平扩展（自动，按主键哈希） | 无需干预，2 个起（可调） |
| **分区（Partition）** | 检索裁剪 + 物理隔离（如按月分区） | 建集时 `add_partition`，检索指定 `partition_names` |
| **分区键（Partition Key，2.4+）** | 按字段值自动路由分区（**多租户标准姿势**） | Schema 字段 `is_partition_key=True` |

```python
# 多租户：partition_key 实现（推荐，见 08 模块）
FieldSchema(name="tenant_id", dtype=DataType.INT64, is_partition_key=True)
# 写入时自动按 tenant_id 路由分区；检索时指定 tenant 过滤
# 收益：租户数据物理隔离 + 检索只扫本租户分区（性能与安全双赢）
```

> 🎯 **核心要点**：**分片管"写入并行"、分区管"检索裁剪"**——分区键（2.4+）把"多租户"变成 Schema 声明（物理隔离 + 检索加速），比"全局加 tenant 过滤条件"更快更安全。

## 6. Collection 操作常用 API 速查

```python
from pymilvus import Collection, utility

# 创建与查询
collection = Collection(name="document_kb", schema=schema)   # 创建
utility.list_collections()          # 列出所有集合
collection.describe()               # 查看 Schema/分区/索引信息
collection.num_entities             # 实体数量（写入后刷新）

# 分区操作
collection.create_partition("p2026-08")     # 建分区（检索可裁剪）
collection.drop_partition("p2025-01")       # 删分区（快速清理）

# 索引与加载
collection.create_index("embedding", index_params)   # 建索引（异步）
collection.load()                   # 加载到 QueryNode（检索前必做）
collection.release()                # 释放内存

# 数据操作（见 04 模块详述）
collection.insert(data) / upsert(data) / delete(expr=...)
collection.flush()                  # 强制落盘
```

**Collection 生命周期的完整链条**：

```text
建集（Schema）→ 建索引 → load（可检索）→ 写入/检索/更新
  → release（省内存）→ drop（删集）→ drop_index（删索引）
注意：drop 集合会级联删除数据与索引 —— 生产需先备份（3.0 快照/2.x Backup）
```

> 💡 **load/release 是资源管理**：多集合场景只 load 热集合（冷集合 release）——内存是 QueryNode 的稀缺资源（见 08 模块）。

## 7. 动态字段与一致性级别

**动态字段（Dynamic Field）**：Schema 外的额外字段自动存储——灵活但**无法建标量索引**：

```python
schema = CollectionSchema(fields=fields, enable_dynamic_field=True)
# 插入时带了 Schema 外的字段（如 source）→ 自动存入 $meta（JSON）
# 权衡：灵活（无需预定义）vs 不可索引（$meta 内字段不能建标量索引/过滤慢）
# 规范：频繁过滤的字段进 Schema（可索引），偶发元数据走动态字段
```

**一致性级别（Consistency Level）**：

| 级别 | 语义 | 场景 |
|------|------|------|
| Strong | 读写强一致（最慢） | 金融等强一致 |
| **Bounded（默认）** | 有界陈旧（默认 5s 内可见） | **绝大多数业务（推荐）** |
| Session | 会话内一致 | 用户会话场景 |
| Eventually | 最终一致（最快） | 日志/非关键检索 |

> 🎯 **核心要点**：**一致性 = 可见性延迟的权衡**——RAG 检索场景"写入后 5 秒内可见"完全可接受（Bounded 默认即可）；"刚写入立即能搜到"的强一致场景（如收藏后立即检索）用 Strong 或 Session，代价是延迟。
