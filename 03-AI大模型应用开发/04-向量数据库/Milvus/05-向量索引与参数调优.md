## 1. 索引类型全景

**索引 = 加速 ANN（近似最近邻）检索的数据结构**——用"近似"换速度（召回率 <100% 可接受）：

| 索引 | 原理 | 适用规模 | 召回 | 内存 | 场景 |
|------|------|:-------:|:----:|:----:|------|
| **FLAT** | 暴力扫描全部向量 | <10 万 | **100%** | 高 | 精确检索/小数据/验证 |
| **IVF_FLAT** | 聚类分桶 + 桶内扫描 | 百万级 | 高 | 中 | 通用入门 |
| **IVF_SQ8** | IVF + 8bit 量化 | 百万级 | 中高 | **低（省 70-75%）** | 内存受限 |
| **HNSW** | 分层可导航小世界图 | **千万级** | **高** | 较高 | **生产首选** |
| **DiskANN** | 图 + 磁盘存储 | **亿级** | 高 | 低（磁盘） | 超大规模 |
| BINARY | 二值向量专用 | 百万级 | 中 | 极低 | 感知哈希类 |

```python
# 建索引（pymilvus）
from pymilvus import IndexType, MetricType

index = {
    "index_type": IndexType.HNSW,          # 索引类型
    "metric_type": MetricType.COSINE,       # 度量（见 06 模块）
    "params": {"M": 16, "efConstruction": 200}   # 索引构建参数
}
collection.create_index("embedding", index)
```

> 🎯 **核心要点**：索引本质 = "**用空间/构建时间换查询速度的近似结构**"——FLAT 是"全扫"（精确但慢）、IVF 是"分桶扫"、HNSW 是"图导航"、DiskANN 是"图+磁盘"（索引原理详见 `04-向量数据库/02-向量索引原理-HNSW与IVF.md`）。

## 2. HNSW：生产首选与三参数调优

**HNSW（Hierarchical Navigable Small World）**：分层图索引——**生产默认首选**（召回/速度/内存均衡）。

**三个关键参数**（面试必考）：

| 参数 | 含义 | 推荐值 | 调大 | 调小 |
|------|------|:------:|------|------|
| **M** | 每层每个节点最大连接数 | 16-64（默认 16） | 召回↑、内存↑、构建慢 | 内存↓、召回↓ |
| **efConstruction** | 构建时动态列表大小 | 200-500（默认 200） | 构建质量↑、构建慢 | 构建快、质量↓ |
| **ef** | **查询时**动态列表大小 | **TopK ~ TopK×10**（128 是召回/性能平衡点，约 92% 召回） | **召回↑、查询慢** | 查询快、召回↓ |

```python
# 构建参数（建索引时）
index = {"index_type": "HNSW", "metric_type": "COSINE",
         "params": {"M": 32, "efConstruction": 300}}

# 查询参数（search 时）—— ef 是查询期参数，可动态调整
result = collection.search(data=[query_vec], anns_field="embedding",
        param={"metric_type": "COSINE", "params": {"ef": 128}},   # 查询期调 ef
        limit=10)
```

**调优心法**：

```text
召回率不够 → 优先调大 ef（查询期，零成本重建）→ 还不够再调 M/efConstruction（需重建索引）
查询慢 → 调小 ef 或换更低内存索引（IVF_SQ8）
内存超 → M 调小 / IVF_SQ8 / DiskANN
经验基线：M=16~32、efConstruction=200~300、ef=128 起步，按"召回 vs 延迟"实测微调
```

> 🎯 **核心要点**：HNSW 三参数记忆 = "**M 管图密度（内存）、efConstruction 管构建质量、ef 管查询召回**"——**查询期先调 ef**（不用重建索引，最快见效）是调优第一步。

## 3. 稀疏索引：SINDI 与倒排

**稀疏向量的索引 = 倒排索引**（类似全文检索的词表结构）：

```text
稀疏向量 {token_id: weight} 的词表结构：
token_1 → [doc_5(0.8), doc_12(0.3), ...]
token_2 → [doc_1(0.9), ...]
查询时：取查询词对应倒排列表 → 累加权重 → TopK
```

**SINDI（3.0 默认稀疏索引，2026 新）**：

| 维度 | 旧稀疏索引 | **SINDI（3.0）** |
|------|:---------:|:---------------:|
| 体积 | 基准 | **小 ~3 倍**（同召回率） |
| QPS | 基准 | 学习型稀疏向量上**高 ~10 倍** |
| 版本 | 2.4+ | **3.0 默认** |

```python
# 稀疏索引创建（2.5+）
sparse_index = {"index_type": "SPARSE_INVERTED_INDEX", "metric_type": "IP"}
collection.create_index("sparse", sparse_index)   # 或 3.0 的 SINDI
```

**稀疏检索的注意**：

1. **度量必须 IP**（内积）——稀疏向量用 IP 计算相关性（BM25 天然是权重累加）；
2. **BM25 内置函数**（2.5+）：`BM25BuiltInFunction` 从 TEXT/VARCHAR 字段自动生成稀疏向量——**无需外部计算稀疏向量**；
3. 学习型稀疏（Splade 等）：模型直接输出稀疏向量，质量高于 BM25（代价是模型推理）。

> 🎯 **核心要点**：稀疏索引 = "**向量化的全文检索**"——BM25 生成的稀疏向量走倒排索引，与稠密向量走图索引**并存于同一 Collection**（这就是混合检索的存储基础，见 06 模块）。

## 4. 索引选择决策树

```text
数据规模多少？
├── < 10 万 → FLAT（精确，开发/验证期）
├── 百万级
│     ├── 内存充足 → HNSW（召回/性能最佳）
│     ├── 内存受限 → IVF_SQ8（省 70-75% 内存）
│     └── 入门简单 → IVF_FLAT
├── 千万级 → HNSW（M 调大 + ef 调优）✅ 生产主流
├── 亿级+ → DiskANN（磁盘索引）或分片集群
└── 需要全文/混合 → 稠密（HNSW）+ 稀疏（SINDI）双索引

其他维度：
- 召回率要求极高 → FLAT（100%）或 HNSW 高 ef
- 查询延迟敏感 → HNSW 低 ef / IVF 小 nprobe
- 内存红线 → IVF_SQ8 / DiskANN
```

**三个场景的标准答案**（面试/生产）：

> 💡 决策树速记：**"十万 FLAT、百万 IVF、千万 HNSW、亿级 DiskANN"**——规模是第一判据；同规模下优先 HNSW（召回/速度均衡），内存受限下移一级（IVF_SQ8）。

| 场景 | 推荐 | 理由 |
|------|------|------|
| RAG 知识库（百万-千万级） | **HNSW（M=32, ef=128）** | 召回/速度均衡，生产验证充分 |
| 原型验证（<10 万） | FLAT | 100% 召回，排除索引因素 |
| 亿级日志/图片库 | DiskANN | 磁盘索引，内存可控 |

> 🎯 **核心要点**：索引选型 = "**规模定类型、内存定量化、延迟定 ef**"——千万级以内的生产默认 HNSW，没有第二个需要犹豫的答案。

## 5. 索引构建与加载机制

**理解"索引何时生效"**（新手最常见的困惑）：

```text
写入 → 段（Segment）落盘 → 未索引段（检索用暴力扫描，慢）
     → IndexNode 构建索引 → 索引段（检索走索引，快）
关键点：
① 数据写入后"先可查（暴力）后走索引"——大数据量下刚写入时查询慢是正常的
② 索引构建是异步任务（IndexNode）——小数据秒级、大数据分钟级
③ 查询侧：QueryNode 需加载索引/段到内存 → 内存规划决定并发
```

```python
# 强制等待索引就绪（数据量小时常用）
collection.create_index(...)
collection.load()        # 加载到 QueryNode 内存（检索前必须！）
# 未 load 的集合 search 会报错：collection not loaded
```

**索引运维要点**：

| 动作 | 说明 |
|------|------|
| `load()` | 集合加载到内存（**search 前必做**，与索引无关） |
| `release()` | 释放内存（不用的集合可释放） |
| 索引构建监控 | 大集合索引构建耗时的观察点：IndexNode 日志/指标 |
| 内存规划 | QueryNode 内存 ≈ 加载集合的数据量 + 索引结构开销 |

> 🎯 **核心要点**：**"load 才能查、索引异步建"**是两个独立机制——报 "collection not loaded" 先 `load()`；"查询慢"检查数据是否已走索引（未索引段是暴力扫描）。面试答"写入后检索慢"的标准链 = 未索引段 → 索引构建异步 → 等待/优化索引。

## 6. 3.0 新索引与扩展

**3.0 的索引相关新增**（衔接 01 模块）：

| 新增 | 说明 |
|------|------|
| **SINDI** | 新的默认稀疏倒排索引（体积小 3 倍、学习型稀疏 QPS 高 10 倍） |
| Faiss 兼容索引扩展 | **SVS、Panorama、PQ、IVFPQ、ScaNN**——更多硬件/场景适配 |
| StructList + DISKANN | 多向量（ColBERT/ColPali）的首个变体组合 |
| 服务端 MinHash（DIDO） | 近似重复检测（索引/聚类场景） |
| 外部集合索引 | 对数据湖上的开放格式数据建索引（Lance/Iceberg）——**索引与数据分离** |

> 🎯 **核心要点**：3.0 索引方向 = "**稀疏更快（SINDI）+ 兼容更广（ScaNN 等）+ 多向量（StructList）+ 湖上索引（外部集合）**"——2.x 的选型框架（规模/内存/延迟）依然成立，新增的是稀疏与湖仓两个维度。
