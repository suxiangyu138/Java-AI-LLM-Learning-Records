## 1. 为什么需要向量数据库

```text
传统数据库：
  SELECT * FROM docs WHERE content LIKE '%Transformer%'
  → 只能精确/模糊匹配关键词 → 找不到语义相关的内容

向量数据库：
  查询 "Attention 机制" → 找向量最相似的文档
  → 能返回 "自注意力机制"、"Transformer 核心架构" → 语义匹配
```

---

## 2. 核心概念

| 概念 | 说明 |
|------|------|
| **向量 Embedding** | 文本/图片转成的浮点数数组（如 1024 维） |
| **ANN 近似最近邻** | Approximate Nearest Neighbor — 牺牲少量精度换速度 |
| **索引 Index** | 加速向量检索的数据结构（Flat/HNSW/IVF） |
| **Collection** | 向量 + 元数据的集合（类似数据库的 Table） |
| **相似度度量** | 余弦相似度 / 内积 / 欧氏距离 |

```text
ANN 的核心 trade-off：
  精度 Recall vs 速度 QPS vs 内存
  → 三选二，无法三者兼得
```

---

## 3. 核心性能指标

| 指标 | 说明 | 目标 |
|------|------|:---:|
| **QPS** | 每秒查询数 | >100 |
| **Recall@K** | 前 K 个结果中包含正确答案的比例 | >95% |
| **延迟 P99** | 99% 请求的响应时间 | <50ms |
| **内存** | 向量索引占用的内存 | — |
| **插入速度** | 每秒可插入的向量数 | >1000/s |

## 4. 向量数据库 vs 传统数据库

| 维度 | MySQL/PostgreSQL | Elasticsearch | 向量数据库 (Milvus) |
|------|:---:|:---:|:---:|
| **查询方式** | SQL 精确匹配 | 全文检索 | 向量相似度 |
| **语义理解** | ❌ | ❌ | ✅ |
| **扩展性** | 垂直 | 水平 | 水平 |
| **典型 QPS** | 10K+ | 1K+ | 100-10K |
| **数据规模** | TB 级 | TB 级 | 10 亿向量 |

## 7. 2026 市场格局：双轨并行

**2026 向量数据库已从"新兴技术"变为"商品化基础设施"**——市场五条赛道：

| 赛道 | 代表 | 定位 |
|------|------|------|
| 纯向量数据库 | Pinecone/Weaviate/Qdrant/Milvus/Chroma | 专用能力（规模/性能/混合检索） |
| 关系型向量扩展 | **pgvector** | SQL 统一 + 零新增基础设施 |
| 搜索引擎扩展 | Elasticsearch/OpenSearch | 全文检索 + 向量一体 |
| NoSQL 扩展 | MongoDB/Redis | 既有数据栈内嵌向量 |
| 嵌入式/算法库 | FAISS/DiskANN | 索引组件（非数据库） |

**双轨并行的选型含义**：

```text
核心判断标准（2026 共识）：
  向量数据与关系数据的关联程度：
  → 频繁关联订单/用户/权限等结构化数据 → 融合型（pgvector/SQL+AI）
  → 纯向量检索 + 上亿数据 → 独立向量库（Milvus/Qdrant）
  → 已有 Postgres 且 <5000 万向量 → pgvector 默认起点（零新增基础设施）
```

> 🎯 **核心要点**：2026 的选型不是"哪个向量库最强"而是"**我的数据架构需要什么**"——**"最好的新基础设施往往就是不加新基础设施"**（pgvector 成为默认起点的原因）。

## 8. 核心概念速查表

**向量检索的完整术语表**（面试/文档速查）：

| 术语 | 定义 |
|------|------|
| ANN | 近似最近邻（Approximate Nearest Neighbor）——牺牲少量精度换速度 |
| Recall@K | Top-K 结果中相关文档占比 |
| 向量维度 | Embedding 输出长度（如 1536/768/1024） |
| 度量（Metric） | L2/IP/COSINE（距离/内积/余弦） |
| 索引 | 加速检索的数据结构（HNSW/IVF/DiskANN） |
| 过滤 | 检索时叠加标量条件（元数据/租户） |
| 混合检索 | 稀疏（BM25）+ 稠密双路 + 融合（RRF） |

**RAG 场景的向量库使用流程**：

```text
文档 → 切块 → Embedding（稠密向量）→ 入库（含元数据）
查询 → Embedding → 向量检索（+标量过滤）
→ 混合检索（+BM25 稀疏路，RRF 融合）→ 重排 → 生成
```

**与传统数据库的关键差异**（面试必答）：

| 维度 | 传统 DB（MySQL） | 向量 DB |
|------|:---------------:|:-------:|
| 查询方式 | SQL 精确匹配 | **相似度检索（ANN）** |
| 结果 | 精确集合 | **近似 Top-K**（召回率 <100%） |
| 索引 | B+树 | HNSW/IVF/DiskANN |
| 排序 | ORDER BY 字段 | 相似度分数 |
| 一致性 | 强一致 | 一致性级别可调 |

> 🎯 **核心要点**：向量检索的本质 = "**用近似换速度**"——所有概念（召回率/索引/度量）都围绕这个核心；与传统 DB 的差异也在"精确 vs 近似"这一根本点上。

## 11. 一句话总结

```text
向量数据库 = "用近似检索换速度"的专用存储
  → 存储向量 + 元数据，按相似度返回 Top-K
  → 与传统 DB 的根本差异：精确匹配 vs 近似相似

2026 三大认知：
  ① 混合检索是刚需（BM25 + 稠密 + RRF）
  ② 选型看"数据架构"而非"库的性能"（pgvector 默认起点）
  ③ 亿级用 DiskANN（磁盘索引），召回 0.95 是生产甜点
```
