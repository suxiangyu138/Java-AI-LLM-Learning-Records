## 1. 索引参数调优

### HNSW 参数

| 参数 | 含义 | 调大效果 | 推荐 |
|------|------|----------|:---:|
| **M** | 每节点连接数 | 精度↑ 内存↑ 构建↓ | 16-32 |
| **efConstruction** | 构建搜索宽度 | 精度↑ 构建↓ | 100-200 |
| **ef** | 查询搜索宽度 | 精度↑ 速度↓ | 64-128 |

```python
# Milvus HNSW 配置
index_params = {
    "index_type": "HNSW",
    "metric_type": "COSINE",
    "params": {
        "M": 16,                # 生产推荐 16-32
        "efConstruction": 200   # 构建时高一点无妨
    }
}

search_params = {"ef": 64}  # 查询时：低延迟用 32，高精度用 128
```

### IVF 参数

```python
# nlist = 聚类中心数（约为 sqrt(N) × 4）
# nprobe = 查询时搜索簇数（越大精度越高越慢）

index = faiss.index_factory(dim, "IVF1024,Flat")
index.nprobe = 32  # 生产常用 8-64
```

## 2. 量化与压缩

| 方法 | 压缩比 | 精度损失 | 适用 |
|------|:---:|:---:|------|
| **FP32→FP16** | 2× | 几乎无损 | 所有 |
| **FP32→INT8** | 4× | <0.5% | 生产推荐 |
| **PQ (64×8)** | 8-32× | 2-5% | 亿级向量 |
| **Scalar Quantization** | 4× | <1% | 平衡 |

```python
# FAISS PQ 索引
index = faiss.index_factory(dim, "IVF1000,PQ64x8")
#                          1000簇  64段×8bit = 64字节/向量

# 原始 FP32: 1024维 × 4字节 = 4096字节/向量
# PQ 64×8:   64字节/向量 → 压缩 64×
```

## 3. 批量操作优化

```python
# ❌ 逐条插入（慢）
for vec in vectors:
    index.add(np.array([vec]))

# ✅ 批量插入（快 10-100×）
index.add(np.array(vectors))  # 一次性全部
# 或分批：每批 1000-10000

# Milvus 批量插入
client.insert("collection", data, batch_size=1000)
```

## 4. 缓存策略

```text
① 查询结果缓存（Redis）
   → 相同查询 → 直接返回缓存结果
   → 命中率取决于查询重复度

② Embedding 缓存（SQLite/Redis）
   → 文档向量不变 → 只算一次 → 永久缓存

③ 热数据内存常驻
   → 高频访问的向量 → 保持在内存
   → 冷数据 → 磁盘

④ 预加载索引
   → 服务启动时 → 加载索引到内存 → 避免冷启动
```

## 8. 2026 性能优化新维度

**性能优化的场景化扩展（2026）**：

| 新维度 | 说明 |
|--------|------|
| **混合检索性能** | BM25 + 向量双路检索的开销——并行执行 + RRF 融合（别串行） |
| **过滤性能** | 高度选择性过滤（过滤后只剩 1%）——Qdrant 原生过滤索引 vs pgvector 先搜后滤 |
| **磁盘索引** | DiskANN 的延迟预算管理（亿级场景：内存 HNSW 5-15ms vs 磁盘 30-80ms） |
| **量化权衡** | IVF-PQ/标量量化：内存省 8-32 倍 vs 召回下降（按场景定） |
| **GPU 索引** | Milvus GPU 索引吞吐提升 10-100 倍（大吞吐场景） |

**2026 性能调优优先级**：

```text
① 索引形态：HNSW（默认）→ 亿级换 DiskANN/量化
② 检索形态：混合检索（并行 + RRF）已是标配
③ 过滤：过滤占比高 → 选"过滤原生"的库（Qdrant）或优化 Schema
④ 召回目标：recall@10 = 0.95（别追求 0.99，代价 2-5 倍延迟）
⑤ 实测验证：用真实数据 + 真实过滤条件做 POC（别信基准测试）
```

> 🎯 **核心要点**：2026 性能优化 = "**索引（HNSW/DiskANN）+ 混合（并行 RRF）+ 过滤（原生 vs 后滤）+ 量化权衡**"四维——**"真实数据 POC 验证"取代"基准测试崇拜"**是 2026 的工程共识。

## 9. 性能优化速查清单

**优化动作速查（按投入产出排序）**：

```text
① 索引形态（最高杠杆）：HNSW 默认 → 亿级 DiskANN/量化
② 混合检索：BM25 + 稠密并行 + RRF（召回提升最大）
③ 过滤设计：过滤占比高 → 原生过滤索引（Qdrant）或 Schema 优化
④ 召回目标：recall@10 = 0.95（别追求 0.99）
⑤ 批量写入：大批量 insert（勿逐条）+ 索引构建错峰
⑥ 缓存：热门查询缓存（语义缓存见 RAG 深化 21 号）
⑦ 内存：量化（IVF-PQ 省 8-32 倍）/ 只加载必要字段
⑧ 硬件：GPU 索引（Milvus 10-100 倍吞吐，大吞吐场景）
```

**常见性能问题速查**：

| 症状 | 原因 | 解法 |
|------|------|------|
| 查询慢（刚写入） | 未索引段暴力扫描 | 等索引构建/优化索引 |
| 写入慢 | 逐条 insert | 批量写入 |
| 过滤慢 | 无标量索引 | 建过滤字段索引 |
| 内存高 | 加载全部字段 | 只加载必要字段/量化 |
| 召回低 | ef/nprobe 太小 | 查询期参数调大 |
| 分页深翻 | OFFSET 深分页 | Keyset/游标分页 |

> 🎯 **核心要点**：性能优化 = "**索引形态 → 混合检索 → 过滤设计 → 批量写入 → 缓存**"五板斧——**先查"症状-原因"表定位，再选对应动作**；2026 关键认知：真实数据 POC 验证取代基准测试崇拜。

## 10. 容量规划速查

**容量估算公式**（生产规划必算）：

```text
存储估算：
  向量数据 ≈ 向量数 × 维度 × 4 字节（float32）
  HNSW 索引膨胀 ≈ 数据量 × 1.3-1.5 倍（图结构开销）
  量化索引（IVF-PQ）≈ 数据量 × 0.3-0.5 倍（压缩后）

示例（1000 万条 × 768 维）：
  原始向量 = 10⁷ × 768 × 4B ≈ 30GB
  HNSW 索引 ≈ 40-45GB 内存
  IVF-PQ（8x）≈ 4-5GB 内存
  → 内存规划：HNSW 约 40GB / 量化约 5GB（差 8 倍）

亿级参考：1 亿 × 768 维 ≈ 300GB+（HNSW）→ 必须 DiskANN/量化
```

**写入吞吐规划**：

```text
批量写入吞吐参考：单节点数千-数万条/秒（取决于维度与硬件）
索引构建：数据量 × 索引类型决定耗时（HNSW 构建慢于 IVF）
建议：批量入库 + 索引构建错峰（写入高峰不建索引）

节点规划：按"内存（索引）+ 吞吐（QPS）"双维度水平扩展
```

> 🎯 **核心要点**：容量规划 = "**向量大小 × 索引膨胀系数**"——**HNSW 内存是数据的 1.3-1.5 倍、量化可省 8 倍**；亿级数据在规划阶段就要决定"内存型还是磁盘型"（DiskANN）。
