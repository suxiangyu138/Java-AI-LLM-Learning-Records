## 1. 什么是 Harness Engineering

**Harness Engineering（驾驭工程）**：为主动执行任务的 AI Agent 搭建**全流程约束、监控、校验体系**的工程实践。Harness 是独立于大模型之外、由代码、配置与执行规则组成的**运行管控体系**——它不参与实际作业，但全权把控作业的稳定性与合规性。

> 💡 类比：天赋极高的厨师仍需标准化的后厨管理体系——菜谱（模型）决定菜品上限，但厨房动线、卫生规范、火警预案（Harness）决定能否稳定出餐。

### 1.1 Harness 与模型的区分

| 维度 | Model（模型） | Harness（管控体系） |
|------|--------------|-------------------|
| 本质 | 概率推理引擎 | 代码 + 配置 + 执行规则 |
| 决定 | 能力上限（能做多难的事） | **稳定下限（能不能可靠完成）** |
| 迭代 | 训练/微调 | 工程开发 |
| 故障表现 | 输出质量下降 | 执行失控/越权/不可审计 |
| 供应商 | 模型厂商 | **你自己的工程团队** |

> 🎯 **核心认知**：裸模型不等于智能体——把 Claude/GPT 接上 API 不等于部署了 Agent。模型 + 运行管控体系（Harness）才是 Agent。这也是"强模型缺乏好 Harness 表现反而不如弱模型+好 Harness"的原因。

## 2. 核心公式：Agent = Model + Harness

```
Agent = Model + Harness
        │       │
        │       └── Harness（你掌控的部分）
        │            ├── 指令层：任务目标、执行边界、优先级
        │            ├── 工具层：工具白名单、调用权限、参数校验
        │            ├── 状态层：任务进度、操作日志、历史决策
        │            ├── 观测层：行为留痕、回放、溯源
        │            ├── 评估层：客观验收标准
        │            ├── 约束层：高危操作拦截、人工审核、自动回滚
        │            └── 反馈层：错误汇总、规则迭代
        │
        └── Model（供应商提供的部分）
             ├── 推理能力、语言能力、知识
             └── 你只能"选"不能"改"
```

### 2.1 公式的三层含义

| 含义 | 说明 |
|------|------|
| **能力分离** | 模型负责"想"，Harness 负责"做+控+查" |
| **责任归属** | Agent 出事故，先查 Harness 而非怪模型 |
| **投资方向** | 2026 年企业应把工程预算投向 Harness，而非反复换模型 |

> ⚠️ 常见误区：团队遇到 Agent 问题就换更强模型——而实际失败往往出在 Harness：无状态丢失、工具权限过宽、无评估门禁、不可审计。换模型是改上限，问题是下限。

## 3. 控制论治理器：Martin Fowler 的定义

Martin Fowler 将 Harness 定义为**「控制论治理器」（Cybernetic Governor）**：

```
控制论治理器模型
         ┌────────── 前馈（Feed-forward）──────────┐
         │                                        ↓
   需求/目标 ──→ 规则与策略 ──→ Agent 执行 ──→ 输出 ──→ 验收
                              │                   ↑
                              └── 反馈（Feedback）─┘
                                （错误/偏差回传）
```

| 控制机制 | 作用 | Harness 中的实现 |
|---------|------|-----------------|
| **前馈（Feed-forward）** | 执行前设定约束 | 指令层、工具白名单、权限策略、审批规则 |
| **反馈（Feedback）** | 执行后修正行为 | 评估层、错误回传、规则迭代、自动回滚 |

> 🎯 控制论视角的价值：Harness 不是"安全带"（被动防护），而是**闭环控制器**（主动调控）——通过前馈设定边界、反馈修正偏差，让 Agent 行为收敛在期望范围内。

## 4. 三大基础属性

arXiv 2605.18747 提出 Harness 的三大基础属性，是评估一个 Harness 好坏的标准：

| 属性 | 定义 | 反面案例 |
|------|------|---------|
| **可执行性（Executable）** | 能验证 Agent **实际做了什么**，而非仅记录其声称 | 只有对话日志，无法确认是否真执行了命令 |
| **可检查性（Inspectable）** | 失败时产生**可操作的诊断输出** | 报错"任务失败"但无任何上下文 |
| **有状态性（Stateful）** | 会话状态**外部化**，跨会话保持连续性 | 崩溃后从零开始，上下文全丢 |

### 4.1 三大属性落地检查

```text
Harness 体检三问
├── 可执行性：能回答「Agent 刚才到底执行了哪几条命令？改动了哪些文件？」吗
├── 可检查性：Agent 卡住时，能输出「哪一步、哪条工具调用、哪个参数」的诊断吗
└── 有状态性：进程重启/会话切换后，任务进度和决策历史还在吗
```

> 💡 这三个属性是"Agent 可生产化"的最低门槛——满足不了，Agent 只能停留在 Demo 阶段。

## 5. 三代范式演进

### 5.1 演进全景

```
2022-2024          2025                 2026
Prompt Engineering → Context Engineering → Harness Engineering
│                    │                    │
│ 雕琢语言            │ 管理信息             │ 管控行为
│ 单次生成质量         │ 上下文注入与组织      │ 主动执行任务的 Agent 运行管控
│                     │                    │
│ 问题：输出不对       │ 问题：输出好但        │ 问题：Agent 乱执行/
│                     │ 语境漂移、无状态     │ 被攻陷/不可审计
```

| 阶段 | 核心问题 | 关键工具 | 范式代表性失败 |
|------|---------|---------|--------------|
| Prompt 工程 | 如何把指令说清楚 | 提示词模板、few-shot | 输出质量不稳定 |
| 上下文工程 | 如何把信息喂合适 | CLAUDE.md、RAG、上下文裁剪 | 语境漂移、上下文腐烂 |
| **Harness 工程** | **如何确保执行稳定可控** | **运行时、权限、观测、评估、治理** | **Agent 越权/失控/被注入** |

### 5.2 演进驱动力

为什么三代范式依次出现？因为 AI 的自主性逐级提升：

```text
AI 自主性进化
├── 第一阶段：文本生成（被动，Prompt 够用）
├── 第二阶段：对话 + 上下文（半主动，Context 成为瓶颈）
└── 第三阶段：Agent 主动执行（主动 + 有副作用，必须 Harness）
     └── Agent 有工具、能操作文件/发消息/执行命令 → 副作用出现
         → 必须约束、监控、校验 → Harness Engineering
```

> ⚠️ **本质逻辑**：AI 从"只会说"到"能动手"，风险从"说错话"升级为"做错事"——管控的复杂度因此量级跃升。

## 6. Harness 与相关概念的边界

| 概念 | 与 Harness 的关系 |
|------|------------------|
| **提示词工程** | 解决单次输出质量，是 Harness 指令层的子集 |
| **上下文工程** | 解决信息供给，是 Harness 上下文管理的子集 |
| **RAG** | 检索增强生成，是 Agent 记忆/知识的来源之一 |
| **Guardrails（护栏）** | 输出安全过滤，是 Harness 约束层的一部分 |
| **Agent 框架**（LangGraph 等） | 提供 Harness 的编程底座，框架 ≠ Harness |
| **可观测性** | 观测层，是 Harness 三大属性之一的具体实现 |

> 💡 关系总结：**框架给你骨架，Harness 给你治理**——用 LangGraph 写出的循环代码只是骨架，加上权限、评估、观测、治理才是完整的 Harness。

## 7. 为什么 2026 年才需要 Harness

### 7.1 行业转折点

| 信号 | 数据 |
|------|------|
| Agent 从 Demo 走向生产 | 64% 企业已在生产环境发现未授权智能体运行（IDC） |
| 供应链事件爆发 | OpenClaw 事件中约 12% 技能被检出含恶意代码（CVE-2026-25253） |
| 权限审查失效 | 93% 的 Agent 权限请求未经充分审查即被批准（Anthropic 内部数据） |
| 评估缺位 | 多数团队无 Agent 级质量门禁，直接把对话模型当 Agent 用 |

### 7.2 从「调教模型」到「构建管控体系」

```
2024 年的思路：换更好的模型 → 期待更好的 Agent
2026 年的思路：构建 Harness（约束+观测+评估+治理）→ 让 Agent 稳定交付
```

> 🎯 **结论**：2026 年胜出的团队不是提示词最好的团队，而是**遥测最好、评估最硬、约束最严**的团队——这就是 Harness Engineering 的全部意义。

---

## 8. 核心要点

> 🎯 **核心要点**：
> 1. Agent = Model + Harness：模型定能力上限，Harness 定稳定下限，后者才是企业工程的主战场
> 2. Harness 是控制论治理器：前馈定边界（工具白名单/权限/审批）+ 反馈纠偏差（评估/回滚/迭代）
> 3. 三大基础属性：可执行性、可检查性、有状态性——Agent 可生产化的最低门槛
> 4. 三代演进：Prompt（说清楚）→ Context（喂合适）→ Harness（管得住）——自主性升级驱动范式升级
