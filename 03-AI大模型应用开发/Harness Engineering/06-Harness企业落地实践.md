## 1. 十二条最佳实践

### 1.1 起步与设计（实践 1-3）

| # | 实践 | 要点 |
|---|------|------|
| **1** | **从有界工作流开始** | 选边界清晰、失败模式明确的单一业务流程，而非六个月宏大项目；成功标准模糊的多 Agent 系统必失败 |
| **2** | **先埋点再优化** | 调模型/加工具之前先构建可查询追踪：每次模型调用、工具调用、状态转换都捕获 |
| **3** | **先建评估再建 Agent** | 50 个代表用例定义"成功运行"，每天对构建结果运行（详见 05 篇） |

> 💡 **实践 2 金句**：2026 年胜出的团队不是提示词最好的团队，而是**遥测最好的团队**。

### 1.2 工程质量（实践 4-6）

| # | 实践 | 要点 |
|---|------|------|
| **4** | **验证器独立进程** | 生成器与评估器不得同一上下文窗口；验证器全新上下文 + 只读权限 |
| **5** | **工具即产品** | 每个工具获得公共 API 级待遇：清晰名称/描述、输入验证、结构化错误、契约 |
| **6** | **确定性基础 + 概率性上层** | 内核/OS/网络隔离（确定性承重）→ 身份授权（策略）→ 行为控制（概率性，可安全失败） |

### 1.3 多 Agent 治理（实践 7）

详见第 3 节。核心：任务所有者 + 交接预算、错误防火墙、上下文膨胀控制、共享资源协调、token 预算。

### 1.4 组织与评估（实践 8-12）

| # | 实践 | 要点 |
|---|------|------|
| **8** | **模式化运行时设计** | 有界迭代、只读并行、受控写入、两阶段上下文压缩、大工具输出持久化、可恢复会话、轨迹保留、作用域工具权限、生命周期钩子、提供商抽象 |
| **9** | **内部智能体平台团队** | Harness 工程置于平台/共享服务组，拥有 harness 原语，产品团队组合智能体 |
| **10** | **评估「模型-Harness 对」** | 强模型缺好 Harness 可能更差；弱模型 + 好 Harness 更可靠 |
| **11** | **企业落地五大议题** | 见第 4 节 |
| **12** | **理性认知** | Harness 管控只能大幅降低风险，无法零失误；价值是缩小模型能力与业务落地的差距 |

## 2. 内部智能体平台团队

### 2.1 组织模式：内部开发者平台（IDP）再现

```
┌─────────────────────────────────────────────┐
│ 智能体平台团队（Harness 原语拥有者）            │
│  ├── 编排运行时（循环引擎/会话管理）            │
│  ├── 评估框架（Evals 基建/门禁）               │
│  ├── 可观测性（追踪/审计/告警）                │
│  ├── 策略执行（OPA/审批门/权限模型）            │
│  └── MCP 网关（工具接入/身份/审计）             │
└─────────────────────────────────────────────┘
           │ 提供原语（harness primitives）
           ▼
┌─────────────────────────────────────────────┐
│ 产品团队（组合智能体）                         │
│  ├── 客服智能体（用平台原语组装）               │
│  ├── 数据分析智能体（用平台原语组装）           │
│  └── 流程自动化智能体（用平台原语组装）         │
└─────────────────────────────────────────────┘
```

### 2.2 平台团队 vs 产品团队分工

| 职责 | 平台团队 | 产品团队 |
|------|:---:|:---:|
| 运行时/编排引擎 | ✅ | |
| 评估与门禁基建 | ✅ | |
| 可观测性与审计 | ✅ | |
| 权限/策略原语 | ✅ | |
| 业务智能体定义 | | ✅ |
| 业务工具接入 | | ✅（经网关） |
| 业务效果优化 | | ✅ |

> 🎯 **分工原则**：平台团队拥有「harness 原语」，产品团队在其上「组合智能体」——这正是内部开发者平台模式在 AI 时代的再现。

## 3. 多 Agent 系统的治理

> ⚠️ 多 Agent 系统的失败模式与单 Agent 本质不同，必须结构性治理：

### 3.1 五大结构性失败模式与对策

| # | 失败模式 | 后果 | 治理对策 |
|---|---------|------|---------|
| 1 | **握手循环** | Agent 间互相交接任务，永远不完成 | 每个任务设置明确所有者 + 交接预算（最大交接次数） |
| 2 | **级联错误** | 单一虚假信息感染全部 Agent | 安装"防火墙"：每个 Agent 输出经验证器校验再传播 |
| 3 | **上下文膨胀** | 编排器上下文无限增长 | 控制编排器上下文：子 Agent 结果只回传摘要 |
| 4 | **共享资源冲突** | 多 Agent 并发写同一资源 | 锁、队列、事务门、结构化协议 |
| 5 | **成本失控** | token 消耗爆炸 | token 预算 + 每任务成本指标 |

> 📊 **成本参考**：多 Agent 系统同任务 token 消耗约为单 Agent 对话的 **15 倍**——预算管控是刚需。

### 3.2 级联错误场景

```text
hub-and-spoke 拓扑感染链
┌─ Agent A（被投毒/错误）
│     │ 输出（含错误信息）
│     ▼
┌─ 编排器（转发错误信息）
│     │
│     ├──→ Agent B（基于错误信息决策 → 错误）
│     ├──→ Agent C（基于错误信息决策 → 错误）
│     └──→ Agent D（基于错误信息决策 → 错误）
→ 单一错误可感染 100% 的 Agent（实测）
→ 对策：编排器对每个子 Agent 输出先过验证器
```

## 4. 企业落地五大关键议题

### 4.1 议题一览

| # | 议题 | 核心内容 |
|---|------|---------|
| 1 | **行为可信治理** | 让 Agent 行为可预期、可验证、可追溯 |
| 2 | **遗留系统渐进适配** | 老系统（如 MES）用 AI 适配器对接——以新建平台 **18% 的成本**接入 |
| 3 | **人机协同编排** | 共控模式：阈值以下自主，阈值以上批准 |
| 4 | **最小权限原则** | 「角色-权限-资源」三位一体管控模型 |
| 5 | **全链路数据防泄漏** | DLP + 提示词脱敏 + 私有化部署 |

### 4.2 遗留系统适配（重点）

```text
遗留系统适配 vs 平台重建
├── 平台重建：投入高、周期长、风险大
├── AI 适配器方案：以新建平台 18% 的成本部署适配器
│   ├── 对接传统 MES/ERP/CRM 的既有接口
│   ├── Agent 通过适配器访问遗留能力
│   └── 渐进演进，无需推倒重来
└── 适用场景：遗留系统资产仍在使用价值的场景
```

### 4.3 最小权限模型

```text
「角色-权限-资源」三位一体
├── 角色：Agent 能做什么（读/写/审批）
├── 权限：到什么范围（自己/部门/全公司）
└── 资源：能碰什么（库表/API/文件/外部系统）

示例：客服 Agent = 读取角色 × 本部门范围 × 客户库/工单系统
```

## 5. 预算与投资参考

### 5.1 投入结构（2026 市场参考）

| 类别 | 说明 | 占比参考 |
|------|------|:---:|
| **模型推理成本** | API 调用费用 | 20-30% |
| **Harness 平台建设** | 运行时/评估/观测/治理开发 | 40-50% |
| **业务集成** | 工具接入/数据打通 | 20-30% |
| **运营与迭代** | 评估集维护/红队/优化 | 10% |

> 💡 2026 年的关键认知：**Harness 平台建设是最大投入项**——把预算主要花在模型 API 上而 Harness 薄弱，是典型的错误投资结构。

### 5.2 项目规模预算参考

| 项目类型 | 预算参考 |
|---------|---------|
| 轻量 POC（低代码平台） | 5-10 万人民币 |
| 行业专用级（深度集成 + 长期记忆） | 30-80 万 |
| 多智能体群落（几十个 Agent 分工） | 150 万以上 |

## 6. 落地路线图

### 6.1 三阶段路线

```
阶段一：验证（0-2 个月）
├── 选 1 个有界业务流（客服工单/数据查询）
├── 建立评估集 + 埋点（先埋点再优化）
├── 最小 Harness：白名单工具 + 日志 + 循环上限
└── 产出：可信度数据 + 经验

阶段二：深化（3-6 个月）
├── 完善 Harness：评估门禁 + 审批门 + 审计追踪
├── 平台团队就位，沉淀原语
├── 扩展 2-3 个业务智能体
└── 产出：可复用的 harness 原语

阶段三：规模化（7-12 个月）
├── 全生命周期治理（Agent DLC）+ 资产目录
├── 红队常态化 + AIBOM 落地
├── 遗留系统适配器对接
└── 产出：平台化运营，新 Agent 按模板快速上线
```

### 6.2 成功与失败信号

```text
✅ 成功信号
├── 评估分数稳定在门禁线以上
├── 新 Agent 上线周期从月级降到周级
├── 事故可回放、可追溯、可复盘
└── 平台原语被多个业务团队复用

❌ 失败信号
├── 只买模型/工具，无 Harness 投入
├── 没有评估集，"看着能跑"就上线
├── 每个 Agent 各搞一套权限/日志
└── 影子 Agent 越扫越多
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. 十二条最佳实践的核心顺序：**有界起步 → 先埋点 → 先评估 → 验证器独立 → 工具即产品 → 确定性承重**
> 2. 平台团队拥有 harness 原语、产品团队组合智能体——内部开发者平台模式的 AI 化
> 3. 多 Agent 五大结构性失败：握手循环/级联错误/上下文膨胀/资源冲突/成本失控，逐个治理
> 4. 预算重心在 Harness 平台建设（40-50%）；三阶段路线：验证→深化→规模化
