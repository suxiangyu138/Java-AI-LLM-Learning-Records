## 1. 多 Agent 协作概述

### 1.1 为什么需要多 Agent

```text
单 Agent 的局限：
┌─────────────────────────────────────────┐
│ 用户：帮我分析市场 → 写 PRD → 做技术方案   │
│         → 开发实现 → 写测试 → 部署上线    │
│                                          │
│ 单 Agent：上下文越来越长                  │
│           → 注意力分散                    │
│           → 不同阶段需要不同思维模式        │
│           → 长任务质量衰减                 │
└─────────────────────────────────────────┘

多 Agent 的优势：
┌─────────────────────────────────────────┐
│ 同一个任务，分配给不同的专家 Agent：       │
│                                          │
│ 市场分析 Agent → 竞品报告                  │
│ 产品 Agent     → PRD 文档                 │
│ 架构 Agent     → 技术方案                  │
│ 开发 Agent     → 代码实现                  │
│ 测试 Agent     → 测试用例                  │
│ 运维 Agent     → 部署配置                  │
│                                          │
│ 每个 Agent：专注、高质量、上下文不膨胀      │
└─────────────────────────────────────────┘
```

### 1.2 WorkBuddy 多 Agent 的核心能力

| 能力 | 说明 |
|------|------|
| **角色分工** | 每个 Agent 有明确的角色定义、知识范围和工具权限 |
| **并行执行** | 独立的子任务可以并发进行 |
| **上下文隔离** | 每个 Agent 有自己的上下文，互不干扰 |
| **结果聚合** | 汇总 Agent 将多方结果整合为统一输出 |
| **流转交接** | Agent 之间可以传递任务状态和中间产物 |

## 2. 专家团模式

### 2.1 专家团的工作流程

WorkBuddy 的"专家团"是典型的多 Agent 协作模式：

```text
┌─────────────────────────────────────────────────────┐
│                    专家团工作流程                       │
│                                                       │
│  用户提出复杂任务                                      │
│      ↓                                                │
│  ┌─────────────────────────┐                         │
│  │ 调度 Agent（Dispatcher） │ ← 分析任务，拆解子任务      │
│  └────┬──────┬──────┬──────┘                         │
│       │      │      │                                │
│       ▼      ▼      ▼        ← 并行执行              │
│  ┌────────┐┌────────┐┌────────┐                      │
│  │专家 A   ││专家 B   ││专家 C   │  ← 各自独立研究       │
│  │维度 1   ││维度 2   ││维度 3   │                      │
│  └───┬────┘└───┬────┘└───┬────┘                      │
│      │         │         │                           │
│      └─────────┼─────────┘                           │
│                ▼          ← 结果汇聚                  │
│  ┌─────────────────────────┐                         │
│  │ 整合 Agent（Integrator） │ ← 合并、去重、总结        │
│  └────────────┬────────────┘                         │
│               ▼                                      │
│          最终输出给用户                                │
└─────────────────────────────────────────────────────┘
```

### 2.2 典型场景示例

#### 场景一：内容创作

```text
任务：写一篇关于"AI Agent 发展趋势"的深度文章

专家团配置：
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ 行业产品研究员 │  │ 平台内容研究员 │  │ 人文思考研究员 │
│              │  │              │  │              │
│ 研究：        │  │ 研究：        │  │ 研究：        │
│ • 主流产品动向 │  │ • 技术社区热点 │  │ • 社会影响     │
│ • 融资与并购   │  │ • 论文突破     │  │ • 就业变革     │
│ • 竞争格局     │  │ • 开源项目     │  │ • 伦理考量     │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
       └─────────────────┼─────────────────┘
                         ▼
              ┌──────────────────┐
              │   写作 Agent      │
              │                  │
              │ 基于三方研究结果   │
              │ 撰写完整文章       │
              └──────────────────┘
```

#### 场景二：软件开发

```text
任务：实现一个用户反馈收集系统

专家团配置：
PM Agent        → 需求分析 → 用户故事
架构师 Agent     → 技术方案 → 系统设计文档
开发 Agent       → 代码实现 → Spring Boot 项目
测试 Agent       → 测试用例 → 单元测试 + 集成测试
审查 Agent       → 代码审查 → 发现问题 → 通知开发修复
                                        ↓
                                   开发修复 → 测试再验证
                                        ↓
                                   ✅ 通过 → 输出最终代码
```

## 3. 协作架构模式

### 3.1 四种协作拓扑

```text
1. 顺序流水线（Sequential Pipeline）
   A → B → C → D
   适用：阶段分明、有依赖的任务（需求→设计→开发→测试）

2. 并行汇总（Parallel Aggregation）
   A1 ─┐
   A2 ─┼─→ 汇总 Agent → 输出
   A3 ─┘
   适用：多维度独立研究（市场/技术/竞品分析）

3. 辩论仲裁（Debate & Arbitrate）
   A 方案 ─┐
   B 方案 ─┼─→ 仲裁 Agent → 最优方案
   C 方案 ─┘
   适用：方案选型、架构决策、风险评估

4. 层级委托（Hierarchical Delegation）
   主管 Agent
   ├── 子 Agent 1
   │   ├── 孙 Agent 1a
   │   └── 孙 Agent 1b
   └── 子 Agent 2
   适用：大型项目的多层次任务拆解
```

### 3.2 模式对比

| 模式 | 并行度 | 延迟 | 适用任务类型 | 复杂度 |
|------|:---:|:---:|------|:---:|
| 顺序流水线 | 低（串行） | 高（累加） | 强依赖任务 | 低 |
| 并行汇总 | 高 | 低（取决于最慢的） | 独立研究 | 中 |
| 辩论仲裁 | 高 | 低 | 方案决策 | 中 |
| 层级委托 | 中 | 中 | 大型复杂项目 | 高 |

## 4. Agent 角色设计

### 4.1 角色定义模板

```yaml
# agent-role: 代码审查专家
agent:
  name: "CodeReviewer"
  role: "资深代码审查专家"
  expertise:
    - "Java/Spring Boot 代码审查"
    - "安全漏洞检测（OWASP Top 10）"
    - "性能瓶颈分析"
    - "代码可维护性评估"
  personality: "严谨、挑剔、建设性"
  constraints:
    - "不修改代码，只提供审查意见"
    - "每个问题必须附修复建议"
    - "按严重程度排序：Critical > High > Medium > Low"
  tools:
    - "read_file"
    - "grep_search"
    - "git_diff"
    # 注意：没有 write_file 权限！
  output_format: "markdown_table"
```

### 4.2 角色设计原则

| 原则 | 说明 | 好设计 | 坏设计 |
|------|------|-------|-------|
| **职责单一** | 一个 Agent 只负责一个领域 | "安全审查 Agent" | "代码质量全流程 Agent" |
| **权限最小** | 只给完成任务必需的工具 | 审查 Agent 不能写文件 | 所有 Agent 都有全部权限 |
| **输出标准化** | 每个 Agent 输出统一格式 | 都输出 Markdown 表格 | 有的 JSON、有的纯文本 |
| **可独立验证** | 每个 Agent 的结果可单独检查 | 附来源和推理过程 | 结论黑盒 |
| **幂等性** | 相同输入得相同输出 | 不受历史会话影响 | 依赖前面 Agent 的副作用 |

### 4.3 角色冲突处理

```text
常见冲突场景：
┌────────────────────────────────────────┐
│ 开发 Agent：用 Redis 缓存，高性能！      │
│ 安全 Agent：Redis 没设密码，高风险！     │
│                                        │
│ 处理策略：                              │
│ 1. 仲裁 Agent 识别冲突                  │
│ 2. 评估冲突级别（性能 vs 安全＝安全优先） │
│ 3. 给出折中方案："加密码后使用 Redis"     │
│ 4. 记录决策理由到项目记忆                │
└────────────────────────────────────────┘
```

## 5. 跨机协作：双 Agent 架构

### 5.1 实战案例：WorkBuddy + Hermes

基于真实实践总结的双 Agent 跨机协作模式：

```text
┌──────────────────────────────────────────────────────┐
│              双 Agent 跨机协作架构                       │
│                                                        │
│  ┌──────────────────┐       ┌──────────────────┐      │
│  │  Windows 机器      │       │  Ubuntu 机器       │      │
│  │                    │       │                    │      │
│  │  WorkBuddy Agent   │       │  Hermes Agent     │      │
│  │  (交互主控)         │       │  (终端执行者)       │      │
│  │  • 任务拆解         │       │  • 命令执行         │      │
│  │  • 代码生成         │       │  • 环境管理         │      │
│  │  • 文档编写         │       │  • 服务部署         │      │
│  └────────┬───────────┘       └────────┬──────────┘      │
│           │                            │                 │
│           │    ┌──────────────────┐    │                 │
│           └────│  共享"信箱"       │────┘                 │
│                │  (IMA 知识库)     │                      │
│                │  • 任务交接文件    │                      │
│                │  • 中间产物同步    │                      │
│                │  • 状态通知       │                      │
│                └──────────────────┘                      │
└──────────────────────────────────────────────────────┘
```

### 5.2 三权分立文件夹结构

```text
项目根目录/
├── shared/                    # 共享交接区（两个 Agent 都可读写）
│   ├── INBOX/                 # 接收到的任务文件
│   ├── OUTBOX/                # 发送出去的结果文件
│   └── ARCHIVE/               # 已完成任务的归档
│
├── workbuddy-workspace/       # WorkBuddy 私域（Hermes 不可见）
│   ├── drafts/                # 中间草稿
│   ├── research/              # 研究笔记
│   └── output/                # 最终产出
│
└── hermes-workspace/          # Hermes 私域（WorkBuddy 不可见）
    ├── scripts/               # 执行脚本
    ├── logs/                  # 运行日志
    └── build/                 # 构建产物
```

### 5.3 交接文件规范

```text
文件命名：{任务ID}-{轮次}-{发送方}-{状态}.md

示例：ORG-042-R3-WorkBuddy-INPROGRESS.md

文件内容规范（单文件 < 2KB）：
┌─────────────────────────────────────┐
│ # 任务 ORG-042：用户模块重构          │
│                                     │
│ ## 状态：INPROGRESS（第 3 轮）        │
│                                     │
│ ## 本轮输入                          │
│ 已完成 UserController 重构            │
│ 文件：user-service/.../UserController│
│                                     │
│ ## 需要 Hermes 执行                  │
│ 1. 运行单元测试：mvn test            │
│ 2. 检查代码风格：mvn checkstyle:check│
│                                     │
│ ## 本轮输出（由 Hermes 填写）          │
│ （待填写）                            │
└─────────────────────────────────────┘
```

## 6. 通信协议与规范

### 6.1 Token 铁律

> WorkBuddy 官方文档中总结的双 Agent 通信"铁律"

| 铁律 | 内容 | 目的 |
|------|------|------|
| **不寒暄** | 去掉"你好"、"收到"、"辛苦了" | 节省 Token |
| **不复述** | 不重复对方说的话、不回顾历史 | 避免信息冗余 |
| **不解释常识** | 不解释业内通用概念 | 聚焦增量信息 |
| **引用而非转述** | `见 file://xxx.md L42` 而非大段复制 | 减少上下文膨胀 |
| **单次预算** | 每次任务 ≤ 3000 Token | 控制成本 |

### 6.2 交接文件模板

```markdown
## 任务标识
- ID: TASK-{YYYYMMDD}-{序号}
- 优先级: P0 / P1 / P2

## 当前状态
- 进度: {百分比}%
- 阻塞项: {无 / 等待XXX}

## 传递内容
### 本次输入（发送方填写）
- 已完成的工作
- 产生的中间文件（路径 + 简要说明）
- 发现的问题

### 本次输出（接收方填写）
- 执行的操作
- 产生的结果
- 下一步建议

## 附件清单
- [ ] 文件1: {路径} ({大小})
- [ ] 文件2: {路径} ({大小})
```

## 7. 编排引擎设计

### 7.1 编排引擎的核心能力

```text
编排引擎（Orchestration Engine）
├── 任务分析（Task Analysis）
│   ├── 识别任务类型
│   ├── 评估复杂度
│   └── 确定拆解策略
│
├── 角色分配（Role Assignment）
│   ├── 选择合适的 Agent 角色
│   ├── 分配权限和工具
│   └── 确定并行/串行执行顺序
│
├── 执行监控（Execution Monitor）
│   ├── 跟踪各 Agent 进度
│   ├── 超时检测与重试
│   └── 异常处理与降级
│
├── 结果聚合（Result Aggregation）
│   ├── 合并多方输出
│   ├── 冲突检测与仲裁
│   └── 格式统一
│
└── 质量把关（Quality Gate）
    ├── 验收标准检查
    ├── 不通过 → 重新分配或人工介入
    └── 通过 → 输出最终结果
```

### 7.2 编排配置示例

```yaml
# orchestration: content-creation
name: "深度内容创作流水线"
trigger: "用户请求撰写研究报告/深度文章"

pipeline:
  - stage: "research"
    mode: parallel
    agents:
      - role: "行业研究员"
        prompt: "研究{主题}的市场现状和竞争格局"
        timeout: 300s
      - role: "技术研究员"
        prompt: "研究{主题}的技术原理和实现方案"
        timeout: 300s
      - role: "趋势研究员"
        prompt: "研究{主题}的未来趋势和潜在影响"
        timeout: 300s

  - stage: "synthesis"
    mode: sequential
    depends_on: ["research"]
    agents:
      - role: "主编"
        prompt: |
          基于三位研究员的结果：
          1. 识别核心观点和关键数据
          2. 去除重复信息
          3. 标注信息来源
          4. 输出结构化大纲
        timeout: 180s

  - stage: "writing"
    mode: sequential
    depends_on: ["synthesis"]
    agents:
      - role: "撰稿人"
        prompt: "根据大纲撰写完整文章，2000-3000 字"
        timeout: 300s

  - stage: "review"
    mode: sequential
    depends_on: ["writing"]
    agents:
      - role: "审稿人"
        prompt: "检查文章的事实准确性、逻辑连贯性和可读性"
        timeout: 180s

quality_gates:
  - "文章字数在 2000-3000 之间"
  - "每个观点有至少一个数据/引用支撑"
  - "没有明显的逻辑跳跃"
```

---

> 🎯 **核心要点**：多 Agent 协作的核心不是"更多 Agent"，而是"更清晰的职责边界 + 标准化的通信协议"。专家团模式解决的是复杂任务的"质量衰减"问题——让每个 Agent 只做自己擅长的事，而不是让一个 Agent 从头干到尾。
