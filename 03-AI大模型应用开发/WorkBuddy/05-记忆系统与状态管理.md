## 1. 记忆系统概述

### 1.1 为什么需要记忆

```text
如果没有记忆系统：
┌─────────────────────────────────────────┐
│ 对话 1：用户说"我喜欢简洁的代码风格"       │
│ 对话 2：Agent 又生成了一大堆冗余注释       │
│                                          │
│ 用户：😤 我不是说过喜欢简洁风格吗？         │
│ Agent：😅 抱歉，我不记得上一轮对话了       │
└─────────────────────────────────────────┘

有了记忆系统：
┌─────────────────────────────────────────┐
│ 对话 1：用户偏好 → 写入记忆               │
│         "代码风格偏好：简洁，不要冗余注释"  │
│ 对话 2：读取记忆 → System Prompt 注入     │
│         "注意：用户偏好简洁代码风格"        │
│ 对话 2：Agent 生成简洁代码 → 用户满意 ✅   │
└─────────────────────────────────────────┘
```

### 1.2 记忆系统的核心设计

```text
WorkBuddy 记忆系统的核心原则：
┌────────────────────────────────────────────┐
│                                            │
│  原则 1：模型内部不存状态                    │
│  → 所有状态由外部记忆系统维护                 │
│                                            │
│  原则 2：记忆按作用域分层                    │
│  → 作用域越大，写入门槛越高                   │
│                                            │
│  原则 3：区分"事实"与"方法"                  │
│  → 用户事实 → 记忆；工作方法 → Skill          │
│                                            │
│  原则 4：记忆可衰减和清理                    │
│  → 长期不用 → 降低优先级 → 归档 → 删除        │
│                                            │
└────────────────────────────────────────────┘
```

## 2. 五类长期记忆

WorkBuddy 将需要持久化的信息分为五大类别：

### 2.1 分类总览

| 类别 | 英文 | 存储内容 | 示例 | 更新频率 |
|------|------|---------|------|:---:|
| **稳定事实** | Stable Facts | 不常变的客观信息 | 用户名、项目名、技术栈 | 低 |
| **知识背景** | Knowledge Context | 用户的专业领域和水平 | "熟悉 Spring Boot，新手于 K8s" | 中 |
| **行为信号** | Behavioral Signals | 从交互中提取的模式 | "经常在下午提交代码" | 高 |
| **表达偏好** | Expression Preferences | 交流风格和格式偏好 | "用表格对比，不要长段落" | 中 |
| **会话延续** | Session Continuity | 跨会话的任务进度 | "正在重构 User 模块，已完成 60%" | 高 |

### 2.2 各类记忆详解

#### 稳定事实（Stable Facts）

```yaml
# memory/stable-facts/user-profile.yaml
name: "张三"
role: "高级 Java 开发工程师"
team: "后端基础架构组"
projects:
  - name: "电商平台"
    role: "技术负责人"
    stack: ["Spring Boot", "MySQL", "Redis", "Kafka"]
  - name: "内部工具平台"
    role: "核心开发"
    stack: ["Python", "FastAPI", "PostgreSQL"]
work_os: "macOS"
editor: "IntelliJ IDEA"
```

#### 知识背景（Knowledge Context）

```yaml
# memory/knowledge/user-expertise.yaml
expertise:
  Java: expert
  Spring_Boot: expert
  MySQL: advanced
  Redis: advanced
  Docker: intermediate
  Kubernetes: beginner      # ← 影响系统推荐的方案复杂度
  Python: intermediate
  AI_LLM: intermediate
learning_goals:
  - "深入学习 Kubernetes 运维"
  - "掌握 MCP 协议开发"
```

#### 行为信号（Behavioral Signals）

```yaml
# memory/behavioral/work-patterns.yaml
active_hours:
  weekday: "09:00-12:00, 14:00-18:00"
  weekend: "rarely"
commit_pattern:
  frequency: "每天 3-5 次"
  peak_time: "16:00-17:00"
  message_style: "conventional commits"
code_review:
  response_time: "< 2 hours"
  focus_areas: ["安全性", "性能", "代码简洁性"]
```

#### 表达偏好（Expression Preferences）

```yaml
# memory/preferences/communication.yaml
language: "中文为主，技术术语用英文"
format:
  comparison: "表格"
  steps: "有序列表"
  summary: "要点列表"
code_style:
  comments: "简洁，关键逻辑才注释"
  naming: "完整单词，不用缩写"
  test_format: "Given-When-Then"
dislikes:
  - "过长的段落文字"
  - "过多的 emoji"
  - "没有代码示例的抽象解释"
```

#### 会话延续（Session Continuity）

```yaml
# memory/session/task-progress.yaml
active_tasks:
  - id: "TASK-042"
    description: "重构 User 模块认证逻辑"
    progress: 60%
    last_session: "2026-07-29"
    context_file: "session-20260729-summary.md"
    next_steps:
      - "完成 JWT 刷新逻辑"
      - "补充单元测试"
      - "更新 API 文档"
  - id: "TASK-043"
    description: "集成 Elasticsearch 搜索"
    progress: 20%
    blocked_by: "等待运维开通 ES 集群"
```

## 3. 记忆作用域层级

### 3.1 五层作用域

```text
作用域越大 → 影响越广 → 写入/晋升门槛越高

┌─────────────────────────────────────────────┐
│ L5: 组织记忆（Organization）                  │
│ 团队规范、公司技术标准、安全策略                │
│ 例："所有 API 必须经过 API Gateway"            │
│ 写入门槛：🔴 极高（需要管理员审批）              │
├─────────────────────────────────────────────┤
│ L4: 团队记忆（Team）                          │
│ 团队约定、项目架构决策、共享知识                 │
│ 例："团队统一使用 MyBatis-Plus"                │
│ 写入门槛：🟡 高（需要 Tech Lead 确认）           │
├─────────────────────────────────────────────┤
│ L3: 项目记忆（Project）                       │
│ 项目上下文、技术决策记录、里程碑                 │
│ 例："user-service 使用 JWT 认证"               │
│ 写入门槛：🟢 中（需要 PR Review 确认）           │
├─────────────────────────────────────────────┤
│ L2: 用户记忆（User）                          │
│ 个人偏好、技能水平、行为模式                     │
│ 例："用户偏好表格对比格式"                      │
│ 写入门槛：🟢 中（自动采集 + 用户可修正）          │
├─────────────────────────────────────────────┤
│ L1: 会话记忆（Session）                       │
│ 当前会话的临时上下文、中间结果                   │
│ 例："刚才搜索的结果是 42 条记录"                │
│ 写入门槛：✅ 低（自动、临时、会话结束即清理）     │
└─────────────────────────────────────────────┘
```

### 3.2 记忆晋升机制

```text
记忆如何从低作用域晋升到高作用域：

会话记忆（L1）→ 用户记忆（L2）：
  触发条件：同一信息在 3+ 个会话中被使用
  晋升前：验证是否为用户稳定特征（非临时偏好）
  例：3 次会话都用了表格 → 晋升为"偏好表格"的用户记忆

用户记忆（L2）→ 项目记忆（L3）：
  触发条件：多个团队成员有相同或相似的记忆
  晋升前：需要经过团队 Review
  例：3 个人都标注了同一个坑 → 晋升为项目经验

项目记忆（L3）→ 团队记忆（L4）：
  触发条件：跨项目通用、被验证为最佳实践
  晋升前：需要 Tech Lead 审批
  例：某个项目的 CI/CD 配置被 3 个项目采用 → 晋升为团队规范
```

## 4. 记忆的生命周期

### 4.1 生命周期阶段

```text
┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
│  采集   │→│  存储   │→│  检索   │→│  更新   │→│  衰减   │→│  清理   │
│Collect │  │ Store  │  │Retrieve│  │Update  │  │ Decay  │  │Purge   │
└────────┘   └────────┘   └────────┘   └────────┘   └────────┘   └────────┘
```

| 阶段 | 说明 | 关键机制 |
|------|------|---------|
| **采集** | 从对话中自动提取 + 用户显式告知 | NLP 提取、模式识别、用户指令 |
| **存储** | 结构化写入记忆库 | 向量化（用于语义检索）+ 结构化字段（用于精确匹配） |
| **检索** | 相关记忆注入 System Prompt | 语义检索 + 关键词匹配 + 时效性权重 |
| **更新** | 修正、补充、覆盖旧记忆 | 冲突检测（新旧信息不一致时触发确认） |
| **衰减** | 长期未使用 → 降低权重 | 时间衰减函数：上次访问越久，权重越低 |
| **清理** | 过时或不准确的信息归档/删除 | 用户审核 + 自动过期（如会话记忆） |

### 4.2 检索策略

```text
每次对话开始时，记忆系统按以下优先级检索：

1. 会话延续（最高优先级）
   → 是否有未完成的任务？上次做到哪了？

2. 当前项目上下文
   → 用户在操作哪个项目？相关技术栈是什么？

3. 用户偏好
   → 回答格式偏好、代码风格偏好

4. 知识背景
   → 用户水平 → 调整回答深度

5. 行为信号（辅助）
   → 不直接注入 Prompt，用于优化交互体验
```

## 5. 程序性记忆的边界

### 5.1 核心原则

> ⚠️ **WorkBuddy 不将程序性记忆（Procedural Memory）纳入长期记忆**

```text
什么是程序性记忆？
  "用户让我做安全审查时，我总是先检查 SQL 注入，再检查 XSS..."

为什么不纳入长期记忆？
  ❌ 局部经验可能只是巧合或特定上下文下的临时策略
  ❌ 一旦晋升为通用策略，可能在其他场景下不适用
  ❌ 难以评估程序性记忆的质量和普适性

正确的做法：
  验证过的方法 → 编码为 Skill（而非记忆）
  未经验证的经验 → 留在会话范围内，不写入长期存储
```

### 5.2 记忆 vs Skill 的职责边界

| 类型 | 存储什么 | 不存储什么 |
|------|---------|-----------|
| **记忆（Memory）** | 用户是 X 的专家 / 项目使用 Y 技术栈 | 应该用 Y 方案而不是 Z 方案 |
| **Skill（技能）** | — | 如何一步步完成代码审查 / 如何部署应用 |

## 6. 状态管理架构

### 6.1 状态类型

```text
WorkBuddy 中的状态分类：

┌────────────────────────────────────────────┐
│  会话状态（Session State）                   │
│  ├── 对话历史（messages[]）                   │
│  ├── 工具调用栈（当前正在执行哪些工具）         │
│  ├── 临时变量（用户刚说的项目名、文件路径）      │
│  └── 上下文窗口快照                           │
│  生命周期：单次会话                            │
├────────────────────────────────────────────┤
│  任务状态（Task State）                       │
│  ├── 任务 ID 和描述                          │
│  ├── 当前进度百分比                           │
│  ├── 子任务列表及完成状态                     │
│  └── 下一步操作建议                           │
│  生命周期：任务开始 → 任务完成                  │
├────────────────────────────────────────────┤
│  持久状态（Persistent State）                 │
│  ├── 用户记忆（五类）                         │
│  ├── 项目配置                                │
│  ├── 已安装的 Plugin/Skill 清单               │
│  └── 权限设置                                │
│  生命周期：长期持久                            │
└────────────────────────────────────────────┘
```

### 6.2 状态注入模型

```text
每次模型调用前的状态注入流程：

┌──────────────────────────────────────────┐
│ 1. 加载 System Prompt（固定模板）           │
│ 2. 检索相关记忆 → 注入偏好和上下文          │
│ 3. 检查活跃任务 → 注入进度信息              │
│ 4. 加载工具定义                             │
│ 5. 追加当前会话历史                         │
│ 6. 追加用户最新消息                         │
│                                            │
│ 结果 → 发送给模型                            │
└──────────────────────────────────────────┘
```

## 7. 与 RAG 知识库的协同

### 7.1 记忆 vs 知识库

| 维度 | 记忆系统 | RAG 知识库 |
|------|---------|-----------|
| **内容** | 用户画像、偏好、会话状态 | 领域知识、文档、FAQ |
| **来源** | 对话交互中自动提取 | 外部文档导入 |
| **检索方式** | 语义 + 关键词，带时效性权重 | 向量相似度 |
| **更新** | 持续自动更新 | 手动或定时导入 |
| **隐私** | 私密，仅对当前用户 | 可共享，团队级 |
| **典型数据** | "用户喜欢表格" | "Spring Security 配置文档" |

### 7.2 协同模式

```text
用户问题："帮我优化 UserService 的认证逻辑"
         │
         ├──→ 记忆系统检索：
         │      - 用户是 Spring Security 专家
         │      - 当前项目使用 JWT
         │      - 偏好：先给方案概述，再给代码
         │
         ├──→ 知识库检索：
         │      - Spring Security 6.x 最佳实践
         │      - JWT token 刷新策略文档
         │      - UserService 现有代码
         │
         └──→ 组合注入上下文 → 模型生成个性化回答
```

> 🎯 **核心要点**：记忆系统是 WorkBuddy "越来越懂你"的关键。区分五类记忆、管理作用域层级、严守程序性记忆的边界——三者缺一不可。好的记忆系统让 AI 从"工具"变成"搭子"。
