## 1. Harness 工程概述

### 1.1 为什么叫 Harness

"Harness"原意指套在马身上的整套装备（缰绳、马鞍、马镫等），WorkBuddy 借用这个比喻：

```text
模型 = 马（有力量，但没有方向和控制）
Harness = 马具（让人能驾驭、约束和整合马的力量）

好的 Harness → 马的力量被精准引导
差的 Harness → 马乱跑，甚至伤人
没有 Harness → 无法骑乘
```

### 1.2 Harness 的三个维度

```text
                    ┌──────────┐
                    │  Harness │
                    └────┬─────┘
         ┌───────────────┼───────────────┐
         ▼               ▼               ▼
   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │  驾驭     │   │  约束     │   │  整合     │
   │  Steer   │   │Constrain │   │Integrate │
   └──────────┘   └──────────┘   └──────────┘
   控制方向和策略   防止越界操作     能力协同工作
```

| 维度 | 核心问题 | 实现手段 |
|------|---------|---------|
| **驾驭（Steer）** | 模型"往哪走"、"怎么走" | System Prompt、Rules、Skills、任务拆解 |
| **约束（Constrain）** | 模型"不能做什么" | Sandbox、Approval Gate、Allowlist/Denylist、预算上限 |
| **整合（Integrate）** | 模型"能用什么" | Tools、MCP、Memory、Sub-agents、Hooks |

## 2. 驾驭（Steer）：控制方向与策略

### 2.1 System Prompt 设计

System Prompt 是驾驭的第一道缰绳，决定了 Agent 的"人格"和行为模式：

```text
┌─────────────────────────────────────────────┐
│              System Prompt 结构               │
├─────────────────────────────────────────────┤
│ 1. 角色定义     "你是一个专业的代码审查助手"      │
│ 2. 能力边界     "你可以审查代码，但不能修改代码"   │
│ 3. 行为准则     "优先检查安全问题，再检查性能"     │
│ 4. 输出格式     "使用 Markdown 格式，分级列出"    │
│ 5. 约束条件     "每次审查不超过 5 个主要问题"      │
│ 6. 工具使用指南  "优先使用 read_file，再使用 grep" │
└─────────────────────────────────────────────┘
```

### 2.2 驾驭策略对比

| 策略 | 适用场景 | 风险 |
|------|---------|------|
| **强约束 Prompt** | 安全敏感任务（金融、权限操作） | 可能过度限制创造力 |
| **宽松引导** | 创意任务（写作、头脑风暴） | 可能偏离预期方向 |
| **分阶段拆解** | 复杂长任务（Day 级项目） | 需要设计阶段衔接机制 |
| **示例驱动** | 格式敏感任务（代码生成、数据转换） | 示例可能被过拟合 |

### 2.3 Rules 文件——持久化的驾驭指令

Rules 是将 System Prompt 中的规则**外部化、持久化**：

```markdown
## code-review-rules.md

1. 禁止在审查中直接修改代码
2. 安全问题标记为 Critical
3. 性能问题标记为 Warning
4. 样式问题标记为 Suggestion
5. 每个问题必须附带行号和修复建议
```

> 💡 **为什么外部化**：规则独立于 Prompt，可以版本管理、复用、团队共享。修改规则不需要改 Prompt 代码。

## 3. 约束（Constrain）：防止越界操作

### 3.1 约束的三个维度

```text
约束体系
├── 权限边界（Authorization Boundary）
│   ├── 文件系统：哪些目录可读写
│   ├── 网络：允许连接哪些域名/端口
│   ├── 系统调用：允许执行哪些命令
│   └── 数据访问：允许查询哪些数据库/表
│
├── 审批机制（Approval Gate）
│   ├── 高危操作必须人工确认（删文件、发邮件、Git Push）
│   ├── 分级审批：低风险自动通过，高风险弹窗确认
│   └── 审批记录：所有高风险操作留痕
│
└── 资源限制（Resource Limits）
    ├── Token 预算：单次任务上限
    ├── 时间限制：单次任务最长执行时间
    ├── 并发限制：同时运行的 Sub-agent 数量
    └── 调用频率：API 调用速率限制
```

### 3.2 Allowlist vs Denylist

| 机制 | 默认行为 | 安全性 | 易用性 | 适用场景 |
|------|---------|:---:|:---:|------|
| **Allowlist（白名单）** | 全部拒绝，只放行列表内的 | 高 | 低 | 生产环境、安全敏感场景 |
| **Denylist（黑名单）** | 全部允许，只拦截列表内的 | 低 | 高 | 开发环境、内部工具 |

### 3.3 Sandbox 沙箱机制

```text
┌─────────────────────────────────────────┐
│              Sandbox 沙箱                  │
│                                           │
│  ┌─────────┐   ┌─────────┐               │
│  │ Agent A │   │ Agent B │  ← 隔离执行    │
│  └────┬────┘   └────┬────┘               │
│       │             │                     │
│  ┌────┴─────────────┴────┐               │
│  │    受控文件系统          │ ← 只读/只写指定目录│
│  │    受控网络访问          │ ← 只连接白名单域名 │
│  │    受控进程执行          │ ← 只允许安全命令   │
│  └────────────────────────┘               │
│                                           │
│  所有操作 → 日志记录 → 异常检测 → 告警      │
└─────────────────────────────────────────┘
```

## 4. 整合（Integrate）：能力协同工作

### 4.1 整合的能力矩阵

```text
整合层
├── Tools        ↔ 文件读写、API 调用、命令执行
├── MCP Server   ↔ 外部数据源、第三方服务
├── Memory       ↔ 长期记忆、用户偏好、项目上下文
├── Sub-agents   ↔ 任务拆解、并行执行、角色分工
├── Hooks        ↔ 事件驱动：PreToolUse / PostToolUse / SessionStart
├── Skills       ↔ 可复用的任务执行模板
└── Plugins      ↔ 第三方能力包
```

### 4.2 整合的设计原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **最小权限** | 每个 Agent 只获得完成任务所需的最少工具 | 给所有 Agent 开放全部文件系统 |
| **显式依赖** | 工具之间的依赖关系要显式声明 | 隐式依赖特定文件存在 |
| **失败隔离** | 一个工具的失败不影响其他工具 | 一个 API 超时导致整个任务崩溃 |
| **可观测性** | 每次工具调用记录输入/输出/耗时/状态 | 工具调用黑盒，无法排查问题 |

## 5. 上下文工程五大操作

Context Engineering 定义：**在一次模型决策前，设计哪些信息进入上下文、以什么形式进入、放在什么位置、何时更新或移出**。

```text
┌──────────────────────────────────────────────────────┐
│                  Context Engineering                    │
│                                                        │
│  ┌────────┐  ┌────────┐  ┌────────┐  ┌──────┐  ┌────┐│
│  │  写入   │  │  选择   │  │  检索   │  │ 压缩  │  │隔离 ││
│  │ Write  │  │ Select │  │Retrieve│  │Compr. │  │Iso. ││
│  └───┬────┘  └───┬────┘  └───┬────┘  └──┬───┘  └──┬─┘│
│      │           │           │          │         │    │
│      ▼           ▼           ▼          ▼         ▼    │
│  主动注入      按需放入     从外部     长内容     独立   │
│  目标/规则     当前需要     捞取信息    外置      会话   │
│  环境信息      的信息      (RAG等)   留结论     SubAgent│
└──────────────────────────────────────────────────────┘
```

### 5.1 写入（Write）

> 主动把目标、规则、环境写进上下文

```text
写入的内容类型：
├── 固定内容（每轮都带）
│   ├── System Prompt（角色 + 规则）
│   ├── 工具定义
│   └── 基础约束
│
├── 任务级内容（任务开始时写入）
│   ├── 任务目标与验收标准
│   ├── 相关项目文档
│   └── 任务拆解计划
│
└── 动态内容（根据执行情况写入）
    ├── 上一步执行结果摘要
    ├── 当前进度状态
    └── 下一步建议
```

### 5.2 选择（Select）

> 从候选信息中只挑当前需要的放入窗口

```text
选择策略：
├── 基于相关性：当前任务需要什么信息？
├── 基于优先级：Token 有限，哪些信息最重要？
├── 基于新鲜度：最近的信息 > 历史信息
└── 基于来源：用户明确指定的 > 模型自动获取的
```

| 上下文窗口大小 | 选择策略 |
|:---:|------|
| **小窗口（< 8K）** | 极度精简：只放当前步骤必需的信息 |
| **中窗口（8K-128K）** | 平衡：任务目标 + 最近 3 轮对话 + 关键文档 |
| **大窗口（> 128K）** | 丰富：完整对话历史 + 多份参考文档 + 上下文示例 |

### 5.3 检索（Retrieve）

> 从历史会话、资料库按需捞取信息

```text
检索触发时机：
├── 用户引用历史对话："上次那个方案..."
├── 任务需要领域知识："帮我用 Spring Security 实现..."
├── 对话中出现新术语："什么是 MCP？"
└── 主动预检索：模型判断接下来可能需要的信息
```

### 5.4 压缩（Compress）

> 长内容外置，只留结论与证据位置

```text
压缩前（占大量 Token）：
"我读取了 config/application.yml，内容如下：
server:
  port: 8080
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/mydb
    username: root
    ...（200 行配置）"

压缩后（节省 Token）：
"已读取 config/application.yml：
- 服务端口：8080
- 数据库：MySQL @ localhost:3306/mydb
- （完整内容引用：file://config/application.yml）"
```

### 5.5 隔离（Isolate）

> 用独立会话/Sub-agent 处理旁支任务

```text
主 Agent 会话                       Sub-agent 会话
┌──────────────────┐         ┌──────────────────┐
│ 用户：帮我重构   │         │ 任务：分析依赖关系  │
│ 整个用户模块     │         │                    │
│                  │         │ 读取 15 个文件      │
│ Agent：          │         │ 生成依赖图          │
│ 1. 先分析依赖 →  │────────→│ 返回：A→B→C→D      │
│                  │  结果    │                    │
│ 2. 基于依赖图    │←────────│                    │
│    逐步重构      │         └──────────────────┘
└──────────────────┘
```

> 💡 **隔离的好处**：Sub-agent 的上下文不会污染主会话，主会话只拿到"结论"而不是"过程"。这避免了上下文窗口被大量中间信息填满。

## 6. Prompt Cache 优化

### 6.1 缓存原理

```text
缓存命中策略：
┌─────────────────────────────────────────────┐
│  前缀匹配：模型的 Prompt Cache 从前缀开始匹配  │
│                                             │
│  ✅ 可缓存（稳定前缀）                         │
│  System Prompt | 工具定义 | 长期规则          │
│                                             │
│  ❌ 不可缓存（每次变化）                        │
│  用户最新消息 | 动态检索结果 | 本次执行摘要      │
└─────────────────────────────────────────────┘
```

### 6.2 最佳实践

```text
上下文组织顺序（从上到下）：

1. System Prompt       ← 固定，可缓存
2. 工具定义             ← 固定，可缓存
3. 长期规则             ← 尽量固定
4. 当前任务描述         ← 任务级变化
5. 相关文档（检索结果）  ← 动态
6. 会话历史摘要         ← 变化
7. 最近 3 轮对话        ← 最新，变化
8. 用户当前消息         ← 每次不同
```

| 优化策略 | 缓存命中率提升 | 实施难度 |
|---------|:---:|:---:|
| System Prompt 固定不变 | +30% | 低 |
| 工具定义按字母序排列（防抖动） | +10% | 低 |
| 动态内容追加到末尾 | +20% | 低 |
| 减少不必要的 System Prompt 修改 | +15% | 中 |
| 使用相同的前缀模板 | +10% | 低 |

## 7. 业界实践参考

### 7.1 Claude Code 的 Harness 设计

```text
驾驭（Steer）：
├── CLAUDE.md 作为项目级 System Prompt
├── 6 层金字塔知识体系组织
└── 模块化文件导航

约束（Constrain）：
├── 权限模式（Default / AcceptEdits / Bypass / Plan）
├── Sandbox 命令执行
└── 用户确认高危操作

整合（Integrate）：
├── MCP 多服务器
├── Sub-agent 子任务拆解
└── Hooks 事件驱动
```

### 7.2 OpenAI Codex 的使用数据

> 3 人小组 5 个月产出 100 万行代码

关键实践：
- **Linter 自动检查**：每次生成后自动运行静态分析
- **周期性代码漂移扫描**：检测模型生成代码的质量变化趋势
- **初始化 Agent + Coding Agent**：双角色跨会话交接

### 7.3 LangChain 的编排支持

LangChain 提供框架级的 Agent 编排：
- `AgentExecutor`：ReAct 循环的标准实现
- `Tool` 抽象：统一的工具接口
- `Memory` 抽象：多种记忆后端
- `Callback`：事件驱动的可观测性

---

> 🎯 **核心要点**：Harness 工程是 WorkBuddy 区别于简单 Chat 应用的关键。驾驭、约束、整合三个维度缺一不可——光有驾驭没有约束，Agent 会越界；光有约束没有整合，Agent 什么都做不了。上下文工程不是简单的"塞更多信息"，而是精心设计每一轮模型看到什么、以什么顺序、什么粒度。
