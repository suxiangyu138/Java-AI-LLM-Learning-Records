## 1. 成本控制的本质

### 1.1 成本公式

```text
LLM 应用总成本 = 有效调用成本 + 浪费调用成本 + 工程基础设施成本

                    ┌─────────────────────────────┐
                    │   总成本                     │
                    │                             │
                    │  有效调用 ~40%               │
                    │  ├── 最终给用户的有效回复      │
                    │  └── 必要的工具调用和检索      │
                    │                             │

                    │  ├── JSON 截断导致的重试      │

## 2. Credit 消耗的四大陷阱

### 2.1 陷阱一：JSON 截断导致重试

```text
问题场景：
┌─────────────────────────────────────────┐
│ 模型输出 JSON（工具调用参数）：            │
│                                          │
│ {                                        │
│   "query": "SELECT * FROM users WHERE    │
│                                          │
│ → 达到 max_tokens 限制，JSON 被截断        │
│ → 解析失败                                │
│ → 重试一次完整调用 = 浪费 2 倍 Token       │
└─────────────────────────────────────────┘

修复方案：
├── 预留 buffer：max_tokens 预留 20% 给 JSON 闭合
├── 流式检测：实时检测 JSON 是否完整，不完整继续生成
├── 截断恢复：对不完整 JSON 做启发式修复
└── 效果：重试率从 ~35% 降至 <5%
```

```python
# JSON 截断检测与修复示例
import json

def safe_json_parse(model_output: str) -> dict:
    """安全解析模型输出的 JSON，自动修复常见截断问题"""
    try:
        return json.loads(model_output)
    except json.JSONDecodeError:
        # 尝试修复：补全缺失的引号、括号
        fixed = model_output.rstrip(",\n\r\t ")
        # 计算未闭合的大括号和方括号
        open_braces = fixed.count("{") - fixed.count("}")
        open_brackets = fixed.count("[") - fixed.count("]")
        fixed += "}" * open_braces + "]" * open_brackets
        try:
            return json.loads(fixed)
        except json.JSONDecodeError:
            raise ValueError(f"无法修复截断的 JSON: {model_output[-100:]}")
```

### 2.2 陷阱二：慢模型超时白烧

```text
问题场景：
┌─────────────────────────────────────────┐
│ 使用 GLM-5.1 模型处理复杂任务             │
│                                          │
│ 超时设置：120s                           │
│ → 120s 到，没返回 → 重试                  │
│ → 再等 240s → 又超时                     │
│ → 再等 300s → 还是超时                   │
│                                          │
│ 结果：3 次超时，Credit 全浪费，结果为空    │
└─────────────────────────────────────────┘

修复方案：
├── 渐进式超时：120s → 降级模型 → 30s（快模型兜底）
├── 超时即降级：不要用同一慢模型反复重试
├── 超时监控：同一模型超时 3 次 → 标记为"不可用"
└── 效果：Credit 节省 25%
```

```text
渐进式超时策略：
┌────────────────────────────────────────────┐
│ 第 1 次尝试：主模型，超时 120s               │
│   ├─ 成功 → 返回结果                        │
│   └─ 超时 → 降级                            │
│                                            │
│ 第 2 次尝试：备用模型（更快），超时 60s       │
│   ├─ 成功 → 返回结果（标注"降级回答"）        │
│   └─ 超时 → 再次降级                        │
│                                            │
│ 第 3 次尝试：规则引擎兜底，超时 10s           │
│   └─ 返回规则匹配结果（不依赖 LLM）           │
└────────────────────────────────────────────┘
```

### 2.3 陷阱三：响应格式不兼容

```text
问题场景：
┌─────────────────────────────────────────┐
│ 不同模型返回不同格式的 Markdown 代码块：    │
│                                          │
│ DeepSeek V4：```java\ncode\n```          │
│ GLM-5.1：   ```\ncode\n```（无语种标注）  │
│ GPT-4o：    有时用四个反引号 ````          │
│                                          │
│ 解析器假设统一格式 → 部分模型结果丢失       │
└─────────────────────────────────────────┘

修复方案：统一做 Markdown 代码块剥离
```

```python
import re

def extract_code_blocks(text: str) -> list[dict]:
    """统一剥离各模型的 Markdown 代码块"""
    # 处理三反引号和四反引号
    pattern = r'`{3,4}(\w*)\n(.*?)`{3,4}'
    matches = re.findall(pattern, text, re.DOTALL)

    results = []
    for lang, code in matches:
        results.append({
            "language": lang.strip() or "text",
            "code": code.strip()
        })
    return results
```

问题场景：

└─────────────────────────────────────────┘

```

## 3. 三层降级架构

### 3.1 架构设计

```text
┌─────────────────────────────────────────────────┐
│                三层降级架构                        │
│                                                   │
│  ┌─────────────────────────────────────┐         │
│  │ L1: LLM 意图映射                      │         │
│  │ 模型：DeepSeek V4 / Claude           │         │
│  │ 覆盖率：78.9%                         │         │
│  │ 延迟：2-5s                            │         │
│  │ 成本：中                              │         │
│  └──────────────┬──────────────────────┘         │
│                 │ 失败 / 超时 / 低置信度            │
│                 ▼                                 │
│  ┌─────────────────────────────────────┐         │
│  │ L2: 关键词规则引擎 + 语义匹配          │         │
│  │ 方式：正则 + BM25 + 向量相似度        │         │
│  │ 累计覆盖率：89.5%                     │         │
│  │ 延迟：< 100ms                         │         │
│  │ 成本：极低                            │         │
│  └──────────────┬──────────────────────┘         │
│                 │ 未匹配                           │
│                 ▼                                 │
│  ┌─────────────────────────────────────┐         │
│  │ L3: UNCATEGORIZED（人工兜底）         │         │
│  │ 方式：记录到待标注队列               │         │
│  │ 累计覆盖率：100%                      │         │
│  │ 延迟：人工处理（异步）                │         │
│  │ 成本：人工成本                        │         │
│  └─────────────────────────────────────┘         │
└─────────────────────────────────────────────────┘
```

### 3.2 降级触发条件

| 触发条件 | 动作 | 适用层 |
|---------|------|:---:|
| API 返回 5xx 错误 | 重试 1 次 → 降级到 L2 | L1 → L2 |
| 请求超时（>120s） | 立即降级到 L2 | L1 → L2 |
| 返回格式无法解析 | 尝试修复 → 失败则降级 | L1 → L2 |
| 置信度低于阈值（<0.7） | 降级到 L2 规则匹配 | L1 → L2 |
| L2 规则也未匹配 | 进入 L3 待标注 | L2 → L3 |
| API 配额耗尽 | 全部走 L2 规则引擎 | L1 → L2 |
| 检测到成本异常飙升 | 限制 L1 调用频率 | L1 → L2 |

### 3.3 L2 规则引擎设计

```python
# 关键词规则引擎示例
class KeywordRuleEngine:
    """L2 降级：不依赖 LLM 的意图分类"""

    def __init__(self):
        self.rules = {
            "代码审查": {
                "keywords": ["review", "审查", "检查代码", "code review"],
                "exclude": ["写", "生成", "创建"],  # 排除条件
                "action": "trigger_skill:code-review"
            },
            "天气查询": {
                "keywords": ["天气", "温度", "下雨", "weather"],
                "exclude": ["天气API", "天气接口"],
                "action": "call_api:weather_service"
            },
            "文档生成": {
                "keywords": ["生成文档", "文档化", "javadoc", "api doc"],
                "action": "trigger_skill:doc-generator"
            }
        }

    def classify(self, user_input: str) -> dict:
        """对用户输入进行规则匹配分类"""
        results = []
        for intent, config in self.rules.items():
            score = self._calculate_score(user_input, config)
            if score > 0.5:  # 阈值
                results.append({
                    "intent": intent,
                    "score": score,
                    "action": config["action"],
                    "source": "keyword_rules"
                })

        if results:
            # 返回得分最高的匹配
            return max(results, key=lambda r: r["score"])
        else:
            return {
                "intent": "UNCATEGORIZED",
                "score": 0,
                "source": "fallback"
            }

    def _calculate_score(self, text: str, config: dict) -> float:
        keyword_score = sum(
            1 for kw in config["keywords"] if kw.lower() in text.lower()
        ) / len(config["keywords"])

        exclude_hit = any(
            ex.lower() in text.lower() for ex in config.get("exclude", [])
        )

        return 0 if exclude_hit else keyword_score
```

## 4. 模型选择与成本对比

### 4.1 方案对比

| 维度 | 高效果方案 | 高性价比方案 | 节省 |
|------|-----------|-------------|:---:|
| **LLM 架构** | 4 模型并联（每次都调 4 个） | 1 主 + 1 备 + 降级 | 75% |
| **主模型** | Claude Opus + DeepSeek V4 | DeepSeek V4 | 60% |
| **超时策略** | 固定 30s | 渐进式 120s→60s→10s | — |
| **重试次数** | 3 次 | 1 次 + 降级 | 67% |
| **测试策略** | 每次调用真实 LLM | Mock 优先，仅 4/331 测试调真实 LLM | 99% |
| **上下文管理** | 全量携带 | 摘要 + 按需检索 | 40% |
| **月 Credit** | ~3.7M | ~0.8M | **78%** |

### 4.2 模型选择决策树

```text
任务类型？
│
├── 简单分类/提取 → 用小模型 or 规则引擎
│   例：判断用户情绪、提取关键词
│   推荐：DeepSeek V4-Lite / GLM-4-Flash
│   成本：极低
│
├── 中等复杂度生成 → 用中模型
│   例：写周报、生成 SQL、总结文档
│   推荐：DeepSeek V4 / GPT-4o-mini
│   成本：中
│
├── 复杂推理/代码生成 → 用大模型
│   例：架构设计、复杂 Bug 修复、多步骤推理
│   推荐：DeepSeek V4 Pro / Claude Opus
│   成本：高
│
└── 需要多模型投票 → 只在关键决策时并联
    例：安全审查（3 模型投票）
    成本：高，但只在必要时使用
```

### 5.2 Mock 策略

```python
# 测试中的 Mock 策略示例
import pytest
from unittest.mock import Mock, patch

class TestIntentClassifier:
    """意图分类器测试——完全不调 LLM"""

    def test_classify_code_review_intent(self):
        """测试：识别代码审查意图 → 不调 LLM"""
        # Mock LLM 调用的返回结果
        mock_llm_response = {
            "intent": "code_review",
            "confidence": 0.95,
            "entities": {"language": "Java", "files": ["UserService.java"]}
        }

        with patch("services.llm.call") as mock_call:
            mock_call.return_value = mock_llm_response

            classifier = IntentClassifier()
            result = classifier.classify("帮我审查一下 UserService 的代码")

            assert result.intent == "code_review"
            assert result.entities["language"] == "Java"
            # 验证确实调用了 LLM（但用的是 Mock）
            mock_call.assert_called_once()

    def test_classify_with_l2_fallback(self):
        """测试：LLM 失败时降级到 L2 规则引擎"""
        with patch("services.llm.call") as mock_call:
            mock_call.side_effect = TimeoutError("LLM 超时")

            classifier = IntentClassifier()
            result = classifier.classify("审查代码")

            # 应该降级到 L2 规则引擎
            assert result.source == "keyword_rules"
            assert result.intent == "代码审查"

    def test_rule_engine_no_llm_call(self):
        """测试：规则引擎完全不调 LLM"""
        engine = KeywordRuleEngine()
        result = engine.classify("帮我检查一下这段代码")

        assert result["source"] == "keyword_rules"
        # 0 Credit 消耗！
```

## 6. 上下文窗口优化

### 6.1 窗口分配策略

```text
上下文窗口（以 128K 为例）的 Token 分配：

┌─────────────────────────────────────────────┐
│ System Prompt（固定）          5K  (4%)      │
│ 工具定义                       10K  (8%)     │
│ 长期规则 + 项目上下文           15K (12%)     │
│ ─────────────────────────────────────       │
│ 相关知识库文档（动态）          30K (23%)     │
│ 会话历史摘要                   10K  (8%)     │
│ 最近 N 轮完整对话               30K (23%)     │
│ ─────────────────────────────────────       │
│ 用户当前输入                    2K  (2%)     │
│ 模型输出预留                    26K (20%)     │  ← 给模型回复留空间
└─────────────────────────────────────────────┘
```

### 6.2 压缩策略

| 策略 | 节省比例 | 信息损失 | 适用场景 |
|------|:---:|:---:|------|
| **对话摘要** | 60-80% | 低 | 超过 10 轮的长对话 |
| **只保留结论** | 80-90% | 中 | 大文件读取后的上下文 |
| **外置引用** | 90-95% | 低 | 文件绝对路径 + 行号引用 |
| **结构化压缩** | 50-70% | 低 | JSON/API 响应精简 |
| **增量更新** | 40-60% | 极低 | 只发送变更部分 |

## 7. 监控与告警体系

### 7.1 关键指标

```text
成本相关指标：
├── Credit 消耗速率（/小时、/天、/月）
├── 有效调用 vs 浪费调用比例
├── 各模型/各 Agent 的 Credit 分布
├── 降级触发频率（L1→L2, L2→L3）
└── 单次任务平均 Credit 消耗

性能相关指标：
├── 端到端响应延迟（P50, P95, P99）
├── 首 Token 延迟（TTFT）
├── Token 生成速率（tokens/s）
├── 模型超时率
└── 工具调用成功率
```

### 7.2 告警规则

```yaml
alerts:
  - name: "Credit 消耗异常"

  - name: "降级率过高"
    condition: "L1→L2 降级率 > 20%"

  - name: "超时率飙升"
    condition: "模型超时率 > 10%"
    action: "切换备用模型"

  - name: "接近配额上限"
    condition: "当月消耗 > 配额的 80%"

  - name: "JSON 解析失败率"

```

> 🎯 **核心要点**：成本控制不是"不用好模型"，而是"不在没必要的地方用好模型"。三层降级架构保证系统在任何情况下都可用，测试 Mock 策略消除最大的浪费源头，渐进式超时避免慢模型的白烧。
