# 08 - 多活架构与异地容灾

> 🎯 同城双活防单机、异地多活防城市级灾难、多云多活防供应商绑定 — 容灾的终极防线

---

## 1. 容灾架构演进

```text
单机 (开发) → 主备 (MVP) → 同城双活 (生产) → 异地多活 (企业) → 多云多活 (金融)

  单机：       一台 GPU 服务器 → 挂了全挂
  主备：       主机 + 备机（冷备/热备）→ 故障手动切换
  同城双活：   两个机房同时服务 → 自动切换
  异地多活：   不同城市同时服务 → GPS 就近路由
  多云多活：   不同云供应商 → 防单一供应商故障
```

## 3. 异地多活

```text
跨城市部署的挑战：

① 延迟问题：
   北京↔上海 RTT ~30ms → 同步复制不可行
   方案：异步复制 + 最终一致性
   RAG 的向量数据：允许秒级不一致

② 数据同步：
   Milvus CDC (Change Data Capture) → 跨集群同步
   文档上传 → 主集群写入 → 异步复制到从集群

③ 用户路由：
   GSLB 就近接入：华北用户 → 北京集群，华东用户 → 上海集群
   故障时：全部切到健康集群
```

## 5. 脑裂防御

```text
脑裂 (Split-Brain) = 网络分区导致两个节点都认为自己是 Master

LLM 场景的脑裂：
  主集群和备集群同时处理请求 → 用户看到不一致的回复
  → "我刚才问的问题，怎么两次回答不一样？"

防御：
  ① 分布式锁 (etcd/ZK) → 只有拿到锁的节点才能服务
  ② Fencing Token (递增版本号) → 旧 Master 的写操作被拒绝
  ③ K8s Lease → Pod 自动续约 → 失联自动释放
```
