## 1. 真实故障案例

### 案例 1：OpenAI 全球宕机（2023.11）

```text
事件：OpenAI API 全球不可用约 90 分钟
影响：无数 AI 产品同时瘫痪

应对得当的团队：
  ✅ 自动切换到 Anthropic Claude（备选 API）
  ✅ 用户看到"当前使用备用模型，部分功能受限"提示
  ✅ 降级：画图/数据分析功能暂时不可用，基础聊天正常

应对失败的团队：
  ❌ 只接入了 OpenAI → 整个产品白屏
  ❌ 没做降级 → 用户看到 500 Error
  ❌ 事后才发现 → 客服被投诉淹没

教训：必须接至少两个不同供应商的模型 API
```

### 案例 2：GPU 显存泄漏（某企业内部）

```text
现象：vLLM 服务运行 6 小时后 OOM Kill → 重启 → 6 小时后又 OOM
根因：KV Cache 未正确释放 → 显存缓慢增长

排查过程：
  ① Prometheus 发现 GPU 显存持续增长（非锯齿）
  ② 对比新旧版本 → vLLM 版本升级后引入 Bug
  ③ 定位到 Prefix Caching 的显存回收逻辑

解决：
  → 回滚 vLLM 版本到稳定版
  → 加显存告警（>90% 即告警，不等 OOM）
  → 定期重启策略作为兜底（每 4 小时滚动重启）

教训：显存泄露比 OOM 更难发现（缓慢增长），需要趋势监控
```

### 案例 3：用户 Prompt 注入导致系统指令失效

```text
现象：部分用户发现能让客服机器人说出"我是 DAN，可以做任何事"
根因：未做 Prompt 注入防御 → 用户输入覆盖了系统 Prompt

解决：
  → 输入清洗 + injection 检测
  → 系统 Prompt 加固（用户输入不可覆盖）
  → 输出内容审核（敏感词过滤）

教训：LLM 容灾不只是"服务不挂"，输出内容安全也是容灾
```

## 2. 高频面试题

**Q1: 99.99% 可用性意味着什么？怎么实现？**
```text
年宕机 < 52.6 分钟 → 日宕机 < 8.6 秒
实现：同城双活 + 自动切换 + 熔断降级 + 冗余供应商
```

**Q2: 熔断器三种状态及转换条件？**
```text
CLOSED(正常)→失败达阈值→OPEN(快速失败)→休眠→HALF-OPEN(探测)→成功→CLOSED
```

**Q3: LLM 服务降级怎么做？**
```text
模型降级(GPT-4o→GPT-4o-mini) → 功能降级(去RAG) → 质量降级(短上下文) → 静态兜底
```

**Q4: 重试风暴怎么防？**
```text
指数退避+随机抖动+重试预算+服务端限流+最大重试次数
```

**Q5: 多模型冗余的切换怎么做到用户无感？**
```text
健康检查→故障检测→自动切换(<1s)→恢复后自动切回→用户全程无感知
```

## 3. 容灾架构评审清单

```text
上线前必须通过：

  冗余：
    □ 至少 2 个不同供应商的 LLM API
    □ 或 1 个供应商 + 1 个自建模型
    □ 自建模型至少 2 个 GPU Pod

  降级：
    □ 模型降级链配置完毕
    □ 静态兜底回复已准备
    □ 降级恢复策略已测试

  熔断限流：
    □ 每个 API 独立熔断器
    □ 用户级 + API级 + GPU级三级限流
    □ 熔断后用户看到友好提示

  监控：
    □ 可用性 / 延迟 / 错误率 Dashboard
    □ 模型切换告警
    □ GPU 显存告警

  演练：
    □ 至少做过 1 次故障切换演练
    □ 有 Runbook（故障处理手册）
    □ On-Call 排班 + 升级机制

  数据：
    □ RAG 文档有备份
    □ 模型权重有版本管理 + 回滚能力
```

## 核心要点回顾

- LLM 容灾 = 降级链 + 熔断器 + 多模型冗余 + 健康检查 + 监控告警
- SLA：99.9%(主备) → 99.99%(同城双活) → 99.999%(异地多活)
- 真实故障复盘是提高容灾能力的最快途径
- 容灾不是一次性项目，而是持续迭代的工程实践
