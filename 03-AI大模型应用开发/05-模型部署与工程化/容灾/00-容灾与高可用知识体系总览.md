## 4. LLM 容灾的特殊性

```text
LLM 服务与传统微服务容灾的差异：

① 依赖链更长：
   传统：App → DB → Cache
   LLM：App → Gateway → LLM Service → GPU → Model Weights
   每一层都可能挂！

② 故障模式更复杂：
   传统：超时、连接拒绝、返回null
   LLM：幻觉、违规输出、Token超限、GPU OOM、模型加载超时

③ 降级手段不同：
   传统：返回缓存数据
   LLM：切到备选模型、返回模板回复、降级为关键词搜索

④ 成本敏感性：
   传统：多部署几台机器即可
   LLM：每台 GPU 机器月费数万 → 冗余成本极高
   不能简单"加机器"→需要智能路由和模型分层
```

## 5. LLM 容灾成熟度模型

```text
Level 1 — 单点无容灾（开发环境）
  一台 GPU 服务器 → 挂了全挂

Level 2 — 基础降级（MVP）
  主模型 + 静态兜底回复 → 挂了至少不报错

Level 3 — 模型冗余（生产就绪）
  GPT-4o(主) + GPT-4o-mini(备) → 自动切换

Level 4 — 多云多活（企业级）
  OpenAI + Azure + 自建 → 跨供应商容灾

Level 5 — 混沌验证（金融级）
  定期故障演练 + 自动化恢复 + 99.99% SLA
```
