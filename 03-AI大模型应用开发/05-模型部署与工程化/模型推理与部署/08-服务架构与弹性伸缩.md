## 请求队列与背压

```python
import asyncio
from collections import deque

class RequestQueue:
    def __init__(self, max_size=1000, timeout=30):
        self.queue = asyncio.Queue(maxsize=max_size)
        self.timeout = timeout
    
    async def enqueue(self, request):
        try:
            await asyncio.wait_for(
                self.queue.put(request), timeout=self.timeout
            )
        except asyncio.TimeoutError:
            raise HTTPException(503, "服务繁忙，请稍后重试")
    
    async def dequeue(self):
        return await self.queue.get()
```

## 弹性伸缩策略

```text
基于 GPU 利用率的 HPA：
  → GPU 利用率 > 70% 持续 2 分钟 → 扩容 +1
  → GPU 利用率 < 30% 持续 5 分钟 → 缩容 -1

基于请求队列：
  → queue_size > 100 → 扩容
  → queue_size < 10 → 缩容

冷启动优化：
  → 预加载模型到 GPU（常驻）
  → 预热请求（启动后自动发几个请求）
  → 模型缓存到本地 SSD（避免每次从 HF 下载）
```

## 5. 弹性伸缩速查（2026）

**LLM 弹性伸缩的特殊性**：

```text
与普通服务的关键差异：
  ① 模型加载耗时（分钟级）→ 扩容滞后
  ② 显存是硬约束（不可超卖）→ 扩容 = 加节点/卡
  ③ GPU 成本高 → 弹性 = 成本控制关键

伸缩策略选择：
  ① 预留（基线）：常驻最小副本（覆盖基础负载）
  ② 弹性（峰值）：HPA/KEDA 按 QPS/队列扩（模型加载耗时需预热）
  ③ 突发（预案）：预留 GPU 池 + 快速加载（模型预加载/多副本）

注意：K8s HPA 对 GPU 场景需自定义指标（vLLM 排队长度/QPS）
     而非 CPU/内存（模型加载慢导致滞后）
```

**服务架构速查**：

```text
标准架构（2026）：
  客户端 → 网关（鉴权/限流/路由）
  → 推理服务（vLLM 实例，按模型分服务）
  → GPU 池（按模型规格分池：7B/70B 不同池）

多模型管理：
  每模型独立服务（隔离/独立扩缩容）→ 推荐
  单服务多模型（显存共享）→ 成本优但隔离差
  网关路由：/v1/chat/completions?model=xxx
```

**弹性伸缩的关键指标**：

```text
扩容触发：vLLM 排队长度（等待中的请求数）> 阈值
缩容保护：避免频繁抖动（冷却期 + 最小副本）
成本指标：GPU 利用率目标（如 >60% 才值得保留弹性副本）
```

> 🎯 **核心要点**：LLM 弹性 = "**预留基线 + 按队列扩容 + 模型预热**"三件套——**GPU 场景 HPA 用 vLLM 排队指标而非 CPU**（模型加载慢）；多模型独立服务 + 网关路由是标准架构。

## 6. 服务架构速查（2026）

**标准服务架构分层**：

```text
客户端
  → 网关（鉴权/限流/路由/缓存）
  → 推理服务池（按模型分：7B 池 / 70B 池）
  → GPU 节点（nvidia-device-plugin 调度）
  → 模型存储（PV/NFS/对象存储）

关键设计：
  ① 模型路由：网关按 model 参数路由（多模型统一入口）
  ② 队列管理：vLLM 排队（背压返回 429）
  ③ 缓存层：语义缓存（重复查询秒回，见 RAG 深化 21 号）
  ④ 降级：模型不可用 → 小模型兜底/明确报错
```

**多模型管理的三种模式**：

| 模式 | 隔离 | 成本 | 适用 |
|------|:----:|:----:|------|
| 每模型独立服务 | ✅ 好 | 高 | 生产标准 |
| 单服务多模型 | ❌ 差 | 低 | 原型/小规模 |
| 混合（热模型独立 + 冷模型共享） | 中 | 中 | 负载不均场景 |

**弹性伸缩配置示例**（KEDA 按 vLLM 队列）：

```yaml
# KEDA ScaledObject（vLLM 排队长度触发扩容）
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: vllm-scaler}
spec:
  scaleTargetRef: {name: vllm-deployment}
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus:9090
        query: vllm_num_requests_waiting
        threshold: "10"     # 排队 >10 触发扩容
```

> 🎯 **核心要点**：服务架构 = "**网关路由 + 模型分池 + 排队背压 + KEDA 队列扩容**"四件套——**GPU 场景弹性触发用"排队长度"而非 CPU**（模型加载慢）；多模型独立服务是生产标准。

## 7. 总结速查

```text
服务架构核心记忆：
  分层：网关（鉴权/限流/路由）→ 推理池（按模型分）→ GPU
  多模型：独立服务（标准）/ 单服务多模型（原型）
  弹性：KEDA 按排队长度触发（非 CPU）+ 模型预热
  降级：小模型兜底 / 明确报错（不允许静默失败）

面试话术：
  "LLM 服务架构的关键是 GPU 弹性与普通服务不同——
   模型加载分钟级导致 HPA 滞后，所以按 vLLM 排队长度
   触发扩容（KEDA）；显存是硬约束不可超卖；
   多模型用独立服务 + 网关路由"
```

> 🎯 **核心要点**：服务架构总结 = "**网关分层 + 模型分池 + 排队弹性 + 降级兜底**"——**"GPU 弹性按排队指标而非 CPU"是最高频考点**；与部署工具 02-K8s 的 GPU 调度联动。
