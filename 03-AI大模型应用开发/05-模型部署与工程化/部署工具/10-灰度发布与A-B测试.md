## 6. LLM 灰度发布的特有要点（2026）

**LLM 灰度与普通服务的关键差异**：

| 维度 | 普通服务 | LLM 服务 |
|------|---------|---------|
| 评估 | 错误率/延迟 | **质量（黄金集）+ 安全 + 延迟** |
| 显存 | 无 | **双版本 = 双份显存**（资源规划） |
| 回滚 | 快速 | 模型切换（加载耗时）+ 缓存清理 |
| 漂移 | 无 | 新模型可能"答得不同"（行为漂移） |

**LLM 金丝雀的完整流程**：

```text
① 双版本部署：旧（v1）+ 新（v2），各占 GPU（资源翻倍规划）
② 流量分割：5% → v2（金丝雀）
③ 评估：
   - 客观：TTFT/吞吐/错误率
   - 质量：抽样黄金集评估（v2 是否达标）
   - 安全：输出审核（偏见/有害）
④ 逐步放量：5% → 25% → 50% → 100%（每步评估）
⑤ 回滚：任何指标异常 → 切回 v1（版本切换）

A/B 测试：v1/v2 并行长期对比（质量 + 用户反馈）
  → 适合"新模型效果验证"（不立即全量）
```

**模型版本切换的工程**：

```text
方式 1：双服务 + 网关路由（流量分割）—— 标准
方式 2：vLLM 单服务换模型 —— 需重载（停机窗口）
推荐方式 1：网关（Envoy/Nginx）按权重路由 /v1/chat/completions
```

> 🎯 **核心要点**：LLM 灰度 = "**双服务 + 网关分流 + 质量评估 + 逐步放量**"——**与普通灰度的差异在评估维度（质量/安全/漂移）与显存规划（双份）**；模型行为漂移是 LLM 特有的回滚触发条件。

## 7. 灰度发布速查（命令与配置）

**K8s 金丝雀的两种实现**：

```yaml
# 方式 1：多 Deployment + 网关权重路由（推荐，模型场景）
apiVersion: networking.k8s.io/v1
kind: Service
metadata:
  name: llm-gateway
spec:
  selector:
    app: llm  # 匹配 v1/v2 两个 Deployment 的公共标签
# 网关层（Istio/Envoy）按权重路由：v1 95% / v2 5%

# 方式 2：单 Deployment 滚动（简单但无流量分割粒度）
kubectl set image deployment/llm llm=new-image:v2
```

**灰度发布决策清单**：

```text
① 资源规划：双版本 = 双份 GPU（确认显存够）
② 流量分割：5% → 25% → 50% → 100%（每步至少观察 1 天）
③ 评估维度：
   - 客观指标（TTFT/吞吐/错误率）
   - 质量指标（黄金集抽样评估）
   - 安全审核（输出检查）
④ 回滚条件：任何指标异常 / 行为漂移 → 切回 v1
⑤ 沟通：灰度期间标注"新模型"（用户反馈渠道）

A/B 测试的区别：长期并行（50/50），用统计显著性决策
  → 适合"新模型是否更好"的研究型问题
```

> 🎯 **核心要点**：灰度速查 = "**双 Deployment + 网关权重 + 逐步放量 + 评估门槛**"——**模型场景务必用网关路由方式**（滚动更新无流量分割粒度）；回滚条件包含"行为漂移"（LLM 特有）。

## 8. 发布策略选择速查

**三种发布方式对比**（LLM 场景）：

| 方式 | 机制 | LLM 适用性 | 场景 |
|------|------|:----------:|------|
| 金丝雀 | 小流量验证后全量 | ✅ 标准 | 模型更新 |
| 蓝绿 | 双环境切换（瞬时） | ✅ 回滚最快 | 大版本/紧急修复 |
| 滚动 | 逐个替换 | ⚠️ 模型加载慢 | 小改动 |
| A/B | 长期并行对比 | ✅ 研究型 | 新模型效果验证 |

**选择速查**：

```text
模型小更新（bug 修复）→ 金丝雀（5% 验证 → 全量）
大版本/风险高 → 蓝绿（瞬时切换 + 快速回滚）
"新模型是否更好" → A/B（长期对比 + 统计显著性）
GPU 资源紧张 → 金丝雀（双版本占双份显存，注意预算）

蓝绿在 LLM 场景的注意：
  v1/v2 同时驻留 = 双份显存（大模型可能放不下）
  → 蓝绿适合中小模型；大模型用金丝雀（网关分流）
```

> 🎯 **核心要点**：发布选择 = "**金丝雀（标准）+ 蓝绿（回滚快）+ A/B（对比研究）**"——**大模型显存约束让蓝绿受限**（双份驻留），金丝雀 + 网关分流是 2026 LLM 场景的标准答案。

## 9. 发布流程速查（完整命令链）

**金丝雀发布完整操作**（K8s + Istio 示例）：

```bash
# ① 部署 v2（金丝雀）
kubectl apply -f deployment-v2.yaml        # v2 Deployment（少量副本）

# ② 网关路由（5% 流量到 v2）
kubectl apply -f virtualservice.yaml
# spec: weight: v1: 95, v2: 5

# ③ 验证（黄金集抽样 + 指标）
python evaluate_sample.py --url v2-endpoint --gate 0.9

# ④ 逐步放量
kubectl patch virtualservice llm -p '{"spec":{"http":[{"route":[
  {"destination":{"host":"v1"},"weight":75},
  {"destination":{"host":"v2"},"weight":25}]}]}}'
# 25% → 50% → 100%（每步观察 + 评估）

# ⑤ 回滚（任何异常）
kubectl patch virtualservice llm -p '...v1:100...'   # 切回 v1
```

**灰度完成后的清理**：

```text
① 确认 v2 稳定（观察期 ≥ 1 天）
② 删除 v1（释放 GPU 显存）
③ 更新默认路由（v2 = 100%）
④ 归档评估结果（模型版本记录）
```

> 🎯 **核心要点**：灰度命令链 = "**双部署 + 网关权重（5%→100%）+ 每步评估 + 回滚预案**"——**v1 保留到观察期结束**（回滚通道），确认稳定后再释放显存。
