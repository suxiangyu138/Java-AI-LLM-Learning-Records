# 09 - 监控告警与日志

> 🎯 部署只是开始，持续监控才是运维 — GPU 利用率、推理延迟 P99、Token 消耗、模型漂移四大核心指标

### 核心监控指标

```text
GPU 指标：
  → GPU 利用率 > 80% → 需扩容
  → 显存使用 > 90% → 需要更大显存/量化
  
推理指标：
  → QPS (每秒请求数)
  → P50/P95/P99 延迟
  → 首 Token 延迟 (TTFT)
  → Token 生成速度 (tokens/s)

业务指标：
  → 请求成功率
  → 平均 Token 消耗/请求
  → 用户满意度 (👍/👎)
  → 模型输出分布变化 (漂移检测)
```

def detect_drift(recent_outputs, baseline_outputs, threshold=0.1):
    recent_mean = np.mean(recent_outputs, axis=0)
    baseline_mean = np.mean(baseline_outputs, axis=0)
    drift = cosine_similarity(recent_mean, baseline_mean)
    if drift < (1 - threshold):
        alert("检测到模型输出分布漂移！")

## 6. LLM 特有监控指标（2026）

**LLM 服务必须监控的指标（远超 CPU/内存）**：

| 指标 | 含义 | 告警参考 |
|------|------|---------|
| **TTFT（首 token 延迟）** | 用户感知延迟 | P95 > 1s 告警 |
| **TPOT（每 token 生成时间）** | 生成速度 | 高于基线 2 倍告警 |
| 吞吐量（tok/s） | 引擎总吞吐 | 下降告警 |
| KV Cache 显存 | 显存利用率 | > 90% 告警（OOM 风险） |
| 排队长度 | 批处理队列 | 增长告警（容量不足） |
| 生成 token 数 | 成本指标 | 异常增长告警 |

**监控架构速查**：

```text
指标：Prometheus（vLLM 原生 /metrics 端点）+ Grafana
日志：结构化（请求 ID 贯穿）
追踪：OpenTelemetry（LLM span：模型/引擎/服务三层）
漂移：Embedding 分布对比 + 输出质量抽样评估

vLLM 内置指标（/metrics）：
  llm_request_success_total / llm_request_ttft / llm_generation_tokens_total
```

**模型漂移检测（LLM 特有）**：

```text
① 输入漂移：用户查询的 Embedding 分布变化
   → 定期聚类对比（TVD/MMD 距离）
② 输出漂移：回答质量的抽样评估（黄金集指标趋势）
   → 与 RAG/Agent 的评估体系联动（见 RAG 深化 20 号）
③ 上下文漂移：知识库更新后的检索质量变化
```

> 🎯 **核心要点**：LLM 监控 = "**TTFT/TPOT/吞吐/KV 显存四指标 + 漂移检测**"——**"只看 CPU/内存"是 LLM 运维的经典误区**；vLLM 原生 /metrics 开箱即用。

## 7. 监控搭建速查（Prometheus + Grafana）

**vLLM 监控搭建三步**：

```yaml
# ① Prometheus 抓取配置
scrape_configs:
  - job_name: vllm
    metrics_path: /metrics
    static_configs:
      - targets: ["vllm-service:8000"]

# ② Grafana 面板核心指标（LLM 专属）
#    - llm_request_ttft（首 token 延迟）
#    - llm_request_success_total（成功率）
#    - llm_generation_tokens_total（吞吐）
#    - GPU 显存利用率（nvidia_exporter）
```

**告警规则速查**：

```text
① TTFT P95 > 1s（持续 5 分钟）→ 容量告警
② 吞吐下降 50% → 引擎异常告警
③ KV 显存 > 90% → OOM 风险告警
④ 错误率 > 1% → 服务异常告警
⑤ 漂移检测触发 → 质量告警（需要人工评估）
```

**日志与追踪**：

```text
日志：结构化 JSON（request_id 贯穿）
追踪：OpenTelemetry → 三 span：
  网关 span（鉴权/限流）
  服务 span（业务逻辑）
  引擎 span（模型/Token/延迟）
→ LLM 排障：从 request_id 拿到全链路
```

> 🎯 **核心要点**：监控搭建 = "**Prometheus 抓 vLLM /metrics + Grafana LLM 面板 + 五条告警规则**"——**TTFT/吞吐/KV 显存是 LLM 三核心**，加漂移检测构成完整监控体系。

## 8. 监控实践总结与速查

**监控体系全景图**（LLM 服务三层）：

```text
基础设施层：CPU/内存/网络/磁盘（标准监控）
GPU 层：显存利用率/温度/算力（nvidia_exporter）
LLM 层：TTFT/TPOT/吞吐/KV 显存/排队/漂移（vLLM metrics + 自研）

三层缺一不可：只看基础设施 = 看不到模型问题
```

**监控指标速查卡**（一张表记住）：

| 层 | 指标 | 告警阈值参考 |
|----|------|-------------|
| LLM | TTFT P95 | > 1s |
| LLM | 吞吐（tok/s） | 下降 > 50% |
| LLM | KV 显存 | > 90% |
| LLM | 错误率 | > 1% |
| GPU | 显存利用率 | > 95%（OOM 风险） |
| GPU | 温度 | > 85°C |
| 基础 | CPU/内存 | 常规 |
| 质量 | 漂移检测 | 触发即告警 |

**排障流程速查**（LLM 服务变慢）：

```text
① 看 TTFT：升高 → 排队/显存不足（引擎侧）
② 看吞吐：下降 → 批处理问题/模型异常
③ 看 GPU 显存：满 → KV Cache 挤占（降并发/扩显存）
④ 看漂移：质量下降 → 模型/知识库变化
⑤ request_id 全链路追踪定位具体环节
```

> 🎯 **核心要点**：监控实践 = "**三层指标 + 八条告警 + 五步排障**"——**LLM 层指标（TTFT/吞吐/KV）是核心**，漂移检测是质量兜底；排障按"引擎 → GPU → 质量"顺序排查。

## 9. 监控工具速查

**监控栈组件清单**（LLM 服务标准）：

| 组件 | 作用 | 部署方式 |
|------|------|---------|
| Prometheus | 指标采集 | K8s 内（Operator） |
| Grafana | 可视化 | 面板模板（vLLM 官方有） |
| nvidia-exporter | GPU 指标 | DaemonSet |
| Loki/ELK | 日志 | 结构化日志 |
| OpenTelemetry | 追踪 | SDK 埋点 |
| Alertmanager | 告警 | 规则 + 通知 |

**关键告警规则示例**（PromQL）：

```yaml
# vLLM TTFT 告警（P95 > 1s 持续 5 分钟）
- alert: LLMTTFTTooHigh
  expr: histogram_quantile(0.95, sum(rate(llm_request_ttft_bucket[5m])) by (le)) > 1
  for: 5m
  labels: {severity: warning}

# 吞吐骤降告警
- alert: LLMThroughputDrop
  expr: sum(rate(llm_generation_tokens_total[5m])) < 
        sum(rate(llm_generation_tokens_total[1h])) * 0.5
  for: 5m
```

> 🎯 **核心要点**：监控工具栈 = "**Prometheus + Grafana + nvidia-exporter + OTel**"四件套——**TTFT 与吞吐两条 PromQL 告警规则是 LLM 监控的入门标配**（模板可直接套用）。
