Java 高并发核心知识点
一、 高并发基础概念
1. 高并发的定义
高并发指系统在单位时间内接收大量请求（如每秒数万甚至数十万次请求），并能保持稳定、高效的处理能力。其核心目标是提高系统吞吐量、降低响应延迟、保证数据一致性。
2. 高并发的关键指标
- 吞吐量：单位时间内系统处理的请求数，常用单位 QPS（每秒查询数）、TPS（每秒事务数）。
- 响应时间：从请求发出到接收响应的总时间，包括网络传输、服务器处理、数据存储等耗时。
- 并发用户数：系统同时处理的用户请求数，需区分“绝对并发用户数”和“在线用户数”。
- 错误率：单位时间内失败请求数占总请求数的比例，高并发下需严格控制错误率。
3. 高并发面临的核心问题
- 线程安全：多线程并发访问共享资源导致的数据不一致、脏读、幻读等问题。
- 资源竞争：CPU、内存、磁盘、网络等资源的竞争，可能引发线程阻塞、系统过载。
- 死锁：多个线程相互等待对方释放资源，导致系统卡死。
- 性能瓶颈：如数据库锁竞争、网络带宽不足、GC 频繁停顿等，限制系统并发能力。
二、 线程安全与同步机制
（一） 线程安全的实现级别
1. 不可变对象：对象状态创建后不可修改，天然线程安全，如  String 、 Integer 、 Long  等。实现方式包括：使用  final  修饰成员变量、不提供 setter 方法、返回对象副本而非本身。
2. 线程封闭：将对象限制在单个线程内，仅该线程可访问，避免多线程竞争。常见方式：
- 栈封闭：局部变量存储在线程栈中，属于线程私有。
- ThreadLocal：为每个线程提供独立的变量副本，线程间互不干扰，适用于存储用户会话、连接信息等。
3. 无状态设计：对象不包含任何成员变量，仅通过参数传递处理数据，无共享状态，天然线程安全，如 Servlet 无状态化改造。
4. 同步控制：通过加锁或原子类保证多线程对共享资源的有序访问，是最常用的线程安全实现方式。
（二） 同步机制详解
1. synchronized 关键字
- 属于可重入的隐式锁，底层通过 JVM 的  monitorenter / monitorexit  指令实现，锁对象为  this 、类对象或自定义对象。
- 优化：JDK 1.6 后引入偏向锁、轻量级锁、重量级锁的升级机制，减少锁竞争开销。
- 适用场景：锁竞争不激烈的场景，使用简单，无需手动释放锁。
2. Lock 接口及其实现类
- ReentrantLock：可重入的显式锁，支持公平锁/非公平锁，需手动通过  lock() / unlock()  加解锁（ unlock()  必须在  finally  中执行）。
- ReentrantReadWriteLock：读写分离锁，读锁共享、写锁排他，适用于读多写少的场景（如缓存），大幅提高并发读效率。
- StampedLock：JDK 1.8 新增，支持乐观读、悲观读、写锁，性能优于读写锁，适用于读极多写极少的场景。
3. 原子类（java.util.concurrent.atomic）
- 基于 CAS（Compare-And-Swap，比较并交换） 机制实现原子操作，无需加锁，性能高于同步锁。
- 核心类：
- 基本类型： AtomicInteger 、 AtomicLong 、 AtomicBoolean 。
- 引用类型： AtomicReference 、 AtomicStampedReference （解决 CAS 的 ABA 问题）。
- 数组类型： AtomicIntegerArray 、 AtomicLongArray 。
- CAS 原理：包含 3 个参数（内存值 V、预期值 A、更新值 B），仅当 V=A 时，才将 V 改为 B，否则不操作，属于乐观锁。
- 缺点：存在 ABA 问题、自旋开销大（高并发下 CAS 失败会循环重试）。
三、 并发容器
（一） 并发容器与同步容器的区别
- 同步容器：如  Vector 、 Hashtable 、 Collections.synchronizedList ，通过  synchronized  修饰方法实现同步，锁粒度大，并发效率低。
- 并发容器：JDK 1.5 后引入，位于  java.util.concurrent  包下，采用分段锁、CAS 等机制，锁粒度更小，并发性能更高。
（二） 核心并发容器
1. ConcurrentHashMap
- JDK 1.7：采用分段锁（Segment），将数据分为多个 Segment，每个 Segment 独立加锁，不同 Segment 的线程可并发访问。
- JDK 1.8：取消分段锁，采用 CAS + synchronized + 红黑树 实现，对单个 Node 加锁，进一步降低锁粒度，支持更高并发。
- 核心方法： putIfAbsent(K key, V value) （不存在则插入）、 computeIfAbsent(K key, Function<? super K, ? extends V> mappingFunction) （按需计算）。
2. CopyOnWriteArrayList/CopyOnWriteArraySet
- 写时复制机制：写入数据时，复制一份新的数组进行修改，修改完成后替换原数组，读操作无锁，适用于读多写少的场景（如配置列表）。
- 缺点：写操作开销大（需复制数组），数据一致性为最终一致性（读操作可能读取到旧数据）。
3. ConcurrentLinkedQueue/ConcurrentLinkedDeque
- 基于无锁 CAS 实现的并发队列，适用于高并发的队列操作，不支持阻塞操作。
4. BlockingQueue 接口（阻塞队列）
- 支持阻塞的入队/出队操作，是生产者-消费者模型的核心组件，适用于任务解耦、流量削峰。
- 核心实现类：
-  ArrayBlockingQueue ：有界队列，基于数组实现，公平/非公平锁可选。
-  LinkedBlockingQueue ：无界/有界队列，基于链表实现，吞吐量高于  ArrayBlockingQueue 。
-  SynchronousQueue ：同步队列，无存储容量，生产一个数据必须消费一个数据，适用于线程池直接提交任务。
-  PriorityBlockingQueue ：优先级阻塞队列，按优先级排序，适用于任务优先级调度。
四、 线程池与任务调度
（一） 线程池的核心作用
- 降低线程创建/销毁的开销，提高线程复用率。
- 控制并发线程数，避免线程过多导致 CPU 上下文切换频繁、内存溢出。
- 提供任务队列、拒绝策略，便于任务管理和流量控制。
（二） ThreadPoolExecutor 核心参数
java  
public ThreadPoolExecutor(int corePoolSize,
                          int maximumPoolSize,
                          long keepAliveTime,
                          TimeUnit unit,
                          BlockingQueue<Runnable> workQueue,
                          ThreadFactory threadFactory,
                          RejectedExecutionHandler handler)
 
1. corePoolSize：核心线程数，线程池长期保持的线程数量，空闲时不回收（除非设置  allowCoreThreadTimeOut(true) ）。
2. maximumPoolSize：最大线程数，线程池允许创建的最大线程数，限制并发上限。
3. keepAliveTime + unit：非核心线程的空闲存活时间，超时后回收，减少资源占用。
4. workQueue：任务队列，存放等待执行的任务，决定线程池的排队策略。
5. threadFactory：线程工厂，自定义线程名称、优先级、是否为守护线程，便于问题排查。
6. handler：拒绝策略，当线程池和任务队列满时，处理新任务的策略：
-  AbortPolicy ：默认策略，抛出  RejectedExecutionException 。
-  CallerRunsPolicy ：由提交任务的线程执行，降低流量峰值。
-  DiscardPolicy ：直接丢弃新任务，不抛异常。
-  DiscardOldestPolicy ：丢弃队列最旧的任务，尝试提交新任务。
（三） 线程池的工作流程
1. 提交任务 → 核心线程未满 → 创建核心线程执行任务。
2. 核心线程已满 → 任务队列未满 → 任务加入队列等待。
3. 任务队列已满 → 线程数未达最大线程数 → 创建非核心线程执行任务。
4. 线程数达最大线程数 → 执行拒绝策略。
（四） 常用线程池类型（Executors 工具类）
-  newFixedThreadPool(n) ：固定核心线程数的线程池，无界队列，适用于任务量稳定的场景。
-  newCachedThreadPool() ：可缓存线程池，核心线程数 0，最大线程数无限，空闲线程 60 秒回收，适用于短期、突发任务。
-  newSingleThreadExecutor() ：单线程池，任务按顺序执行，适用于需要串行处理的场景。
-  newScheduledThreadPool(n) ：定时任务线程池，支持延迟执行、周期性执行，替代  Timer 。
（五） 线程池的合理配置
- CPU 密集型任务（如计算）：核心线程数 = CPU 核心数 + 1，减少上下文切换。
- IO 密集型任务（如网络请求、文件读写）：核心线程数 = CPU 核心数 × 2 或 CPU 核心数 / (1 - 阻塞系数)，提高 CPU 利用率。
- 任务队列：优先使用有界队列（如  ArrayBlockingQueue ），避免无界队列导致内存溢出。
- 拒绝策略：生产环境避免使用  AbortPolicy ，推荐  CallerRunsPolicy  或自定义拒绝策略（如记录日志、任务持久化）。
五、 并发工具类
（一） CountDownLatch
- 倒计时门闩，让一个或多个线程等待其他线程完成操作后再执行。
- 核心方法： countDown() （计数器减 1）、 await() （等待计数器归零，支持超时）。
- 适用场景：任务拆分（如并行计算多个子任务，主线程等待所有子任务完成后汇总结果）。
（二） CyclicBarrier
- 循环栅栏，让多个线程到达屏障点时阻塞，直到所有线程到达后，所有线程继续执行，计数器可重置，支持循环使用。
- 核心方法： await() （等待其他线程，支持超时）。
- 适用场景：多线程协同工作（如多个线程准备好数据后，同时执行下一步操作）。
（三） Semaphore
- 信号量，控制同时访问特定资源的线程数量，实现限流、资源池管理。
- 核心方法： acquire() （获取许可，无许可则阻塞）、 release() （释放许可）。
- 适用场景：接口限流、连接池管理（如限制同时访问数据库的连接数）。
（四） Exchanger
- 交换器，让两个线程在指定点交换数据，线程会阻塞直到另一个线程到达交换点。
- 核心方法： exchange(V x) （交换数据）。
- 适用场景：数据交换（如生产者线程和消费者线程交换数据缓冲区）。
（五） Phaser
- 阶段器，支持动态调整参与线程数，分阶段执行任务，每个阶段完成后进入下一个阶段，功能比  CountDownLatch  和  CyclicBarrier  更灵活。
- 适用场景：多阶段任务（如分布式任务的多个阶段执行）。
六、 JVM 与高并发优化
（一） 垃圾回收（GC）优化
- 高并发下的 GC 问题：Full GC 停顿时间过长，导致系统响应延迟增加，甚至引发超时。
- 优化策略：
1. 选择合适的 GC 收集器：
- JDK 8：优先使用 ParallelGC（吞吐量优先）或 CMS（低延迟优先）。
- JDK 11+：优先使用 G1GC（平衡吞吐量和延迟），超大堆场景使用 ZGC/ShenandoahGC（停顿时间毫秒级）。
2. 调整堆内存大小：避免堆过大（GC 时间长）或过小（频繁 GC），建议新生代占堆的 1/3~1/2。
3. 减少大对象创建：大对象直接进入老年代，易引发 Full GC，尽量复用对象（如对象池）。
（二） 线程上下文切换优化
- 上下文切换是指 CPU 从一个线程切换到另一个线程，保存/恢复线程状态，频繁切换会消耗大量 CPU 资源。
- 优化策略：
1. 合理设置线程池大小，避免线程过多。
2. 使用无锁编程（如 CAS、原子类）替代同步锁，减少线程阻塞。
3. 避免线程频繁阻塞（如减少 IO 操作、使用非阻塞 IO）。
七、 高并发系统设计原则
1. 无状态化：服务端不存储用户会话信息，会话数据存储在 Redis 等缓存中，便于水平扩展。
2. 数据分片：将数据按一定规则（如哈希、范围）拆分到多个节点，降低单节点数据量和访问压力，如数据库分库分表、Redis 集群分片。
3. 缓存优化：
- 多级缓存：本地缓存（Caffeine） + 分布式缓存（Redis），减少分布式缓存访问压力。
- 缓存穿透：布隆过滤器过滤不存在的 key，避免请求直达数据库。
- 缓存击穿：热点 key 设置互斥锁或永不过期，避免缓存失效时大量请求击穿数据库。
- 缓存雪崩：缓存过期时间随机化，避免大量 key 同时过期；使用多级缓存、熔断降级。
4. 异步化处理：将非核心流程（如日志记录、短信发送）异步化，通过消息队列（如 RocketMQ、Kafka）解耦，提高主流程响应速度。
5. 限流与熔断降级：
- 限流：限制单位时间内的请求数，避免系统过载，常用算法：令牌桶、漏桶、计数器。
- 熔断降级：当依赖服务故障时，触发熔断机制，降级返回默认结果，避免雪崩效应，常用框架：Sentinel、Hystrix。
6. 分布式锁：多节点并发访问共享资源时，通过分布式锁保证数据一致性，常用实现：Redis Redlock、ZooKeeper 分布式锁。
八、 高并发问题排查工具
1. JDK 自带工具：
-  jps ：查看 Java 进程 ID。
-  jstack ：查看线程堆栈信息，排查死锁、线程阻塞。
-  jstat ：监控 JVM 内存、GC 情况。
-  jmap ：生成堆转储快照，分析内存泄漏。
2. 第三方工具：
- Arthas：阿里巴巴开源的 Java 诊断工具，支持实时监控、线程排查、方法追踪。
- VisualVM：可视化 JVM 监控工具，集成多种 JDK 工具功能。
