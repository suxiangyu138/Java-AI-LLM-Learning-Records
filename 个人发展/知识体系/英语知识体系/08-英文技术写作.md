# 英文技术写作

## 一、技术写作的本质与原则

### 1.1 技术写作 ≠ 学术写作
技术写作的目的不是展示你的词汇量或语法复杂度，而是**让读者用最少的认知成本，准确完成一个技术任务**。

学术写作和技术写作的差异：
| 维度 | 学术写作 | 技术写作 |
|------|---------|---------|
| 读者 | 同行研究者 | 需要完成任务的开发者 |
| 目的 | 说服、论证 | 指导、告知 |
| 阅读方式 | 线性阅读 | 跳读、搜索 |
| 句式偏好 | 长句、被动语态 | 短句、主动语态 |
| 判断标准 | 论证是否有力 | 能不能完成任务 |

### 1.2 技术写作四大铁律

**铁律 1：Plain English（简明英语）**
最理想的技术句子长度 = 15-20 词。超过 25 词的句子考虑拆成两句。
- 不说：utilize, facilitate, implement, subsequent to
- 而说：use, help, carry out, after

**铁律 2：一句一事**
每个句子只承载一个技术操作或一个概念。如果一个句子包含 "and" 连接的两个独立操作，拆开它。

Bad:
```
After you have cloned the repository and installed the dependencies,
you can run the development server by executing the start script.
```

Good:
```
Clone the repository. Then install the dependencies. Start the
development server by running the start script.
```

**铁律 3：主动语态优先**
主动语态更短、更清晰、更有力。被动语态只在"动作发出者不重要/不知道"时才使用。

| 被动（Avoid） | 主动（Prefer） |
|-------------|-------------|
| The button should be clicked. | Click the button. |
| The configuration file is created by the CLI. | The CLI creates the configuration file. |
| Errors are displayed when they occur. | The app displays errors when they occur. |

**铁律 4：结论先行（Bottom Line Up Front）**
文档的每个层级（全文 → 章节 → 段落 → 句子）都把最重要的信息放在最前面。

## 二、文档类型与写作模板

### 2.1 README.md —— 项目的门面

**标准结构**：
```markdown
# Project Name
[一句话描述这个项目做什么]

[CI badge] [npm version] [license]  ← 徽章区

## Installation
[复制粘贴就能装的命令]

## Quick Start
[最小可运行示例，让用户在 30 秒内看到效果]

## Documentation
[指向完整文档的链接]

## API
[核心 API 的简要说明和示例]

## Contributing
[如何提交 Issue/PR]

## License
[MIT/Apache 2.0/etc.]
```

**README 写作要点**：
- 第一段必须是"这个项目解决什么问题"——不是"这个项目是什么"，而是"你什么时候需要它"
- Quick Start 必须是完整可运行的——读者复制粘贴后直接能用
- 如果是 CLI 工具，录一个 10 秒的终端 GIF 比写 200 字效果好得多

### 2.2 API 文档

**REST API 端点文档模板**：
```markdown
## GET /api/users/:id

Returns a user by ID.

### Parameters

| Name | Type   | In   | Required | Description          |
|------|--------|------|----------|----------------------|
| id   | string | path | Yes      | The user's unique ID |

### Response

**200 OK**
```json
{
  "id": "usr_123",
  "name": "Jane Doe",
  "email": "jane@example.com"
}
```

**404 Not Found**
```json
{
  "error": "User not found",
  "code": "USER_NOT_FOUND"
}
```

### Example

```bash
curl https://api.example.com/users/usr_123 \
  -H "Authorization: Bearer $TOKEN"
```
```

**API 文档写作要点**：
- 每个字段必须标注：类型、是否必填、默认值、（如果是枚举）所有可选值、(如果是数字）有效范围
- 必须展示真实可用的 curl 示例——不要用占位符
- 错误响应和正常响应同等重要——开发者查文档有一半是为了处理错误情况
- 不要在文档里只说"returns the user object"——展示出来

### 2.3 技术博客/教程

**技术教程的三段式**：
```
1. 开头（Why + What）
   - 一句话：读者读完后能做什么
   - 前置条件：需要什么环境、什么知识
   - 最终效果：最好放一张最终效果的截图

2. 正文（How —— 逐步操作）
   - 每一步 = 一段说明 + 一个代码块
   - 每一步都可以独立验证（做完这步能看到什么结果）
   - 解释 WHY（为什么这么做）而非仅仅 WHAT（做什么）

3. 结尾（Where next）
   - 完整代码在哪里（GitHub 链接）
   - 进一步阅读的建议
   - 常见坑点/排错指南
```

### 2.4 Troubleshooting / FAQ 文档

**每个条目结构**：
```markdown
### [错误信息原文]
**Cause**: [用一句话说出原因]
**Fix**: [给出具体的修复步骤]
**Why this happens**: [可选，解释底层原理]
```

示例：
```markdown
### `npm install` fails with "EACCES: permission denied"
**Cause**: npm does not have write permission to the global node_modules directory.
**Fix**: Either use a Node version manager (nvm) or fix permissions:
```bash
sudo chown -R $(whoami) /usr/local/lib/node_modules
```
```

## 三、句子与段落层面的技巧

### 3.1 精简句子（Sentence Reduction）

**去掉空洞的开头**：
| 空洞 | 直接 |
|------|------|
| It is important to note that ... | [直接说重要的内容] |
| Please be aware that ... | [直接说要注意的内容] |
| There are several things to consider ... | Consider ... |
| In order to achieve X, you must ... | To do X, ... |

**去掉冗余的修饰词**：
| 冗余 | 精简 |
|------|------|
| completely eliminate | eliminate |
| absolutely essential | essential |
| very unique | unique |
| basic fundamentals | fundamentals |
| advance planning | planning |
| past experience | experience |
| end result | result |

**把名词化动词改回动词**：
| 名词化（弱） | 动词化（强） |
|------------|------------|
| make a decision | decide |
| perform an analysis of | analyze |
| conduct an investigation | investigate |
| take into consideration | consider |
| give a demonstration of | demonstrate |

### 3.2 确定性与模糊性

技术写作中，精确比"好听"重要的多：

| 模糊 | 精确 |
|------|------|
| This method returns a value. | This method returns a Promise<string>. |
| It may take some time. | It typically takes 2-5 seconds. |
| You should use this with caution. | Do NOT use this with more than 1000 items. |
| The function is fast. | The function runs in O(n log n). |

### 3.3 列表使用规范

**何时用无序列表**：项目之间无特定顺序
**何时用有序列表**：必须按照顺序执行（如安装步骤）
**列表引导句格式**：引导句以冒号结尾，每个列表项小写开头

```
To install the package, you need:
- Node.js version 18 or higher
- npm or yarn
- A Unix-like environment
```

**平行结构**：列表中每一项的语法形式必须一致——要么都是名词短语、要么都是祈使句、要么都是完整句子。

### 3.4 代码与文字的关系
- 不要在正文中描述代码的每一行（"第一行导入了 React，第二行定义了一个函数..."）——代码本身应该足够清晰
- 注释解释 WHY，正文解释上下文（什么场景下用这段代码）
- 代码块前后各空一行
- 代码块必须标注语言（```javascript, ```bash, ```python）

## 四、常见技术写作场景的英文表达

### 4.1 Git Commit Message
```
<type>(<scope>): <50-char summary>

<Extended body, wrapped at 72 chars, explaining WHY>
```

**类型规范**：
- `feat`: A new feature
- `fix`: A bug fix
- `docs`: Documentation only changes
- `style`: Formatting, missing semi-colons, etc; no code change
- `refactor`: Neither fix nor feature; code restructuring
- `perf`: Performance improvement
- `test`: Adding or fixing tests
- `chore`: Build process, tooling, CI changes

### 4.2 Code Review 评论
| 场景 | 英文表达 |
|------|---------|
| 指出问题 | "This could cause a race condition if ..." |
| 温和的建议 | "What do you think about using X instead? It handles Y edge case better." |
| 追问理解 | "I'm not sure I follow — could you elaborate on why ...?" |
| 指出更好的做法 | "Nitpick: we could simplify this by ..." |
| 赞同某个做法 | "Nice catch! / Good call on using X here. / +1" |
| 要求改动 | "Let's add a test for the edge case where ..." |
| 解释你的设计选择 | "I went with X because Y, even though Z is also an option. The tradeoff is ..." |

### 4.3 Issues / Bug Reports
```markdown
## Expected Behavior
[What you expected to happen]

## Actual Behavior
[What actually happened]

## Steps to Reproduce
1.
2.
3.

## Environment
- OS: [e.g., macOS 14.2]
- Version: [e.g., v2.1.0]
- Node: [e.g., v20.5.0]

## Additional Context
[Error logs, screenshots, anything else relevant]
```

### 4.4 技术演讲 / Presentation 英文表达
| 场景 | 表达 |
|------|------|
| 开场 | "Today I'm going to talk about ..." |
| 介绍结构 | "I've divided this talk into three parts: ..." |
| 过渡 | "That covers X. Now let's move on to Y." |
| 展示代码 | "Let me walk you through this code." |
| 强调重点 | "The key takeaway here is ..." |
| 回答问题 | "That's a great question. ..." |
| 收尾 | "To wrap up, ... / In summary, ..." |

## 五、工具与自检清单

### 5.1 写作辅助工具
- **Hemingway App**：检测可读性等级、被动语态、难句子。目标 Grade 8-10
- **Grammarly**：语法和拼写检查，但注意它不理解技术语境
- **Vale**：命令行风格的 prose linter，可以集成到 CI 中
- **write-good**：npm 包，检测 weasel words、被动语态等

### 5.2 文章自检清单

**结构层面**：
- [ ] 读者看到标题知道这篇文章会解决什么问题吗？
- [ ] 最重要的信息在第一节吗？
- [ ] 如果我只读标题和每个小节的标题，能知道文章的大致内容吗？

**段落层面**：
- [ ] 一个段落只讲一个概念吗？
- [ ] 段首句能概括全段吗？

**句子层面**：
- [ ] 有超过 25 词的句子吗？→ 拆短
- [ ] 有被动语态可以改为主动语态吗？
- [ ] 有 "It is important to note that" 之类的空洞开头吗？→ 删除
- [ ] 有可以在代码块中展示而不用文字描述的内容吗？→ 用代码

**精确性**：
- [ ] "may", "should", "could" 都用对了吗？
- [ ] 每个"快"、"大"、"多"都有具体数字支撑吗？
- [ ] 每个步骤读者都能独立验证吗？

**读者视角**：
- [ ] 一个完全不了解这个项目的开发者，能照着文档跑起来吗？
- [ ] 常见错误有说明吗？（文档的价值一半在于告诉用户哪里会出错）

## 六、进阶：从非母语者到被当成母语者的写作提升

### 6.1 英语非母语者最常见的 10 个写作问题

| 问题 | 示例 | 修正 |
|------|------|------|
| 冠词缺失/错误 | We implemented **solution**. | We implemented **a/the solution**. |
| 可数/不可数混淆 | There are many **informations**. | There is a lot of **information**. |
| 介词搭配错误 | **depends from** the input | **depends on** the input |
| 中式语序迁移 | **I very much like** this. | **I like this very much**. |
| 时态不一致 | We **test** the API and **found** a bug. | We **tested** the API and **found** a bug. |
| 副词位置 | We **handle carefully** the error. | We **carefully handle** the error. |
| 主语缺失 | **Is necessary to** install Node. | **It is necessary to** install Node. |
| that 从句误用 | It is recommended **to use** Node 18. | It is recommended **that you use** Node 18. |
| and 连接不等价成分 | You need Node and **to install** npm. | You need **Node and npm**. |
| 词性用错 | We need to **analysis** the data. | We need to **analyze** the data. |

### 6.2 长期提升路径
1. **阅读优秀的技术文档**：Stripe、Vercel、React 的文档是技术写作的标杆
2. **模仿写作**：选一段优秀文档，用自己的项目内容仿写其结构和句式
3. **获取反馈**：把你的文档给一个非中文母语的同事看，问他哪里读起来不自然
4. **持续积累**：维护一个"写作灵感本"，收藏好的句子和表达方式
