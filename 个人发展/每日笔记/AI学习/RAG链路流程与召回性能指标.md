# 1. 说说你这个RAG链路的具体流程，有用指标衡量召回性能吗？
回答：
我实现的RAG链路主要分为以下几个阶段：
1. 数据预处理：将非结构化文档进行清洗、分段，按业务逻辑设置重叠窗口，避免上下文断裂。
2. 向量化与存储：调用Embedding模型将文本片段转为向量，存入向量数据库（如Milvus/Chroma），建立索引。
3. 用户Query处理：对用户输入进行意图识别、关键词提取和Query改写，解决歧义。
4. 向量召回：根据用户Query向量，在向量库中进行Top-K相似性检索，得到相关片段。
5. 重排序（Rerank）：使用交叉编码器模型对召回结果进行相关性排序，过滤低质量结果。
6. Prompt组装与生成：将重排序后的上下文与用户问题一起注入Prompt模板，调用LLM生成最终答案。
    性能指标：
    - 核心指标：召回率(Recall@k)、准确率(Precision@k)、MRR（平均倒数排名）
    - 业务指标：答案相关性、幻觉率
    - 调优方式：通过调整Chunk大小、重叠窗口、Embedding模型、Rerank模型等方式优化，将Recall@5提升到了90%以上。
 
2. Skill技能封装和MCP协议交互的区别，以及在项目中怎么使用？
    回答：
    这两者的核心区别在于抽象层级和交互方式：
    - Skill技能封装：是面向开发者的本地/服务端函数封装。它把一个具体的能力（如调用API、执行数据库查询）包装成一个可被大模型调用的函数，定义输入输出参数、参数校验和异常处理。它是一个“可执行单元”，运行在你的应用服务中。
    - MCP协议交互（Model Control Protocol/Model Communication Protocol，不同厂商定义略有差异）：是标准化的远程交互协议。它定义了大模型与外部工具/服务之间的通信格式，包括请求头、请求体、错误码、流式响应格式等。它解决的是跨服务、跨语言的标准化通信问题。
    项目中的使用方式：
    - 我先将业务逻辑封装成了一个个独立的Skill（如订单查询、天气查询），每个Skill都有明确的Schema定义。
    - 然后基于MCP协议规范，开发了一个通用的工具调用客户端。当大模型通过Function Call返回工具调用请求时，客户端会解析请求、路由到对应的Skill，执行后再按MCP协议的格式将结果返回给大模型。
    - 这样设计的好处是，Skill的业务逻辑和协议交互解耦，新增Skill时无需修改协议层代码，提升了扩展性。
 
3. 多轮对话管理和上下文优化，怎么实现会话记忆，上下文管理怎么做的？
    回答：
    我实现会话记忆和上下文管理，主要分三层：
    1. 会话存储层：
    - 使用Redis作为会话缓存，以 sessionId 为Key，存储对话历史，设置过期时间。
    - 数据库（MySQL）持久化会话记录，用于后续的审计和模型微调。
    2. 上下文优化层：
    - 滑动窗口（Sliding Window）：保留最近N轮对话，防止上下文过长。
    - 摘要压缩：当对话超过一定轮数时，调用LLM对历史对话进行摘要，用摘要替代原始对话历史，压缩Token消耗。
    - 关键信息提取：从对话中提取实体（如订单号、用户ID）和意图，作为结构化信息单独存储，减少后续轮次的重复提问。
    3. Prompt组装层：
    - 将优化后的对话历史、当前用户问题和系统提示词按固定格式组装成最终Prompt。
    - 实现了Token计数逻辑，确保组装后的Prompt长度不超过模型的最大上下文窗口限制。
 
4. 借助Cursor优化prompt工程，说说你对prompt工程的理解？
    回答：
    我理解的Prompt工程，核心是通过设计清晰、明确、可被大模型理解的输入指令，引导模型输出符合预期的结果。它不是玄学，而是一套有方法论的工程实践。
    在项目中，我借助Cursor（AI代码编辑器）主要做了几件事：
    1. 快速迭代Prompt模板：用Cursor的AI对话功能，快速生成和修改不同场景下的Prompt模板，比如RAG场景、多轮对话场景、工具调用场景，大大提升了开发效率。
    2. 调试和优化Few-shot示例：通过和Cursor对话，设计和验证Few-shot示例，确保示例覆盖了主要的业务场景和边界情况。
    3. Prompt性能分析：利用Cursor辅助分析不同Prompt的输出结果，对比不同模板的效果，找出模型容易产生幻觉或答非所问的点，针对性地优化指令。
    Prompt工程的核心原则是：
    - 指令明确：清晰地告诉模型任务、角色、格式和约束。
    - 提供上下文：给模型足够的背景信息，减少歧义。
    - 设置边界：定义模型不能做什么，减少幻觉。
    - 结构化输出：指定输出格式（如JSON），方便下游解析。
 
5. 两个项目都用了RabbitMQ，为什么选择它？对比过其他消息队列吗？
    回答：
    我在项目中选择RabbitMQ，主要基于以下几点考虑：
    1. 高可靠性：RabbitMQ支持消息持久化、生产者确认、消费者确认机制，能保证消息不丢失，这对业务的最终一致性很重要。
    2. 灵活的路由：支持Direct、Topic、Fanout、Headers等多种Exchange类型，可以灵活地实现消息的路由和广播，满足了我项目中不同业务场景的解耦需求。
    3. 成熟的社区与生态：对Java生态支持良好，Spring AMQP集成方便，文档和问题解决方案丰富。
    对比过的其他消息队列：
    - Kafka：Kafka吞吐量极高，适合日志、大数据流处理，但它的设计初衷不是为了强一致性，消息可能丢失或重复，且不支持复杂路由，对于我的业务场景来说有些重了。
    - RocketMQ：阿里开源，性能也很强，支持事务消息，但社区活跃度在国内不如Kafka，且我当时的团队对RabbitMQ更熟悉，维护成本更低。
    所以，结合我的业务场景（对可靠性要求高、需要灵活路由、开发维护成本可控），最终选择了RabbitMQ。
