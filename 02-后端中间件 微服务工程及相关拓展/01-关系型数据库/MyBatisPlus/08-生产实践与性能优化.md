## 1. 逻辑删除 × 唯一索引冲突（头号坑）

**问题**：逻辑删除只做"滤镜"（查询加 `deleted=0`），**不释放数据库唯一索引槽位**：

```text
场景：user.phone 有唯一索引，用户注销（逻辑删除 deleted=1）
→ 新用户用同一手机号注册 → INSERT 报 Duplicate entry（唯一约束冲突）！
原因：逻辑删除的记录还在表里（deleted=1），phone='138...' 仍占着唯一索引槽位
```

**三种解法**（按推荐度）：

| 解法 | 做法 | 权衡 |
|------|------|------|
| **① 释放唯一字段**（推荐） | 注销时把唯一字段改成 `phone + "_del_" + id` | 字段被改写，展示需还原；最通用 |
| ② 应用层校验 | 不建唯一索引，Service 层查重（`exists(phone)`） | 有并发窗口期——需分布式锁/事务兜底 |
| ③ 条件唯一索引 | PostgreSQL `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL` | MySQL 8.x **不支持**（部分版本不支持条件索引） |

```java
// 解法 1 的落地：注销时改写唯一字段
@Transactional(rollbackFor = Exception.class)
public void deactivateUser(Long userId) {
    User user = getById(userId);
    // 先释放唯一字段（改写成不可注册的形态）
    lambdaUpdate().eq(User::getId, userId)
            .set(User::getPhone, user.getPhone() + "_del_" + userId)
            .set(User::getDeleted, 1)
            .update();
}
```

> ⚠️ **深层提醒**：**复合唯一索引 `(phone, deleted)` 不可行**——第一个注销的人永久占据 `(phone, 1)` 槽位，后续同号注销必冲突，只是把坑从"注册时"推迟到"注销时"。**规范答案是解法 1（释放字段）或解法 2（应用层校验）**。

## 2. 批量操作性能对比与最佳参数

**实测数据**（1 万条，2025 社区基准，量级参考）：

| 方式 | 耗时 | 提升 |
|------|:----:|:----:|
| 循环单条 insert | ~8200ms | 1× |
| **MP saveBatch（默认 1000/批）** | ~1500ms | ~5.5× |
| 手动拼接批量 SQL | ~900ms | ~9× |
| JDBC 批处理 | ~750ms | ~11× |

**最佳参数与实践**：

```java
// ① 显式指定批次大小（默认 1000）
orderService.saveBatch(list, 500);        // 考虑 max_allowed_packet 与连接池

// ② 批量更新同样用 batch（复用 SqlSession）
orderService.updateBatchById(list);

// ③ 百万级 + 需要主键回填/精确控制 → 分批循环（每批 500-1000）
for (List<Order> batch : partition(orders, 1000)) {
    orderService.saveBatch(batch);
    // 每批之间业务处理（回调/统计）
}

// ④ 终极场景（千万级导入）→ JDBC 批处理 / 多线程分片 + 每线程一批
```

**批量操作的三个注意**：

| 注意 | 说明 |
|------|------|
| 大包限制 | 单批过大触发 MySQL `max_allowed_packet` 报错——批次别贪大 |
| 主键回填 | saveBatch 不回填主键——需要 id 的业务逐条 save |
| 循环红线 | **循环里调 MP 单条方法 = 性能灾难**（N 次提交） |

> 🎯 **核心要点**：批量性能口诀 = "**saveBatch 起步（5 倍）、拼 SQL 进阶（9 倍）、JDBC 终极（11 倍）**"——99% 场景 saveBatch 足够，超大数据量再升级。

## 3. 千万级数据的 CRUD 优化

**千万级单表的 MP 优化清单**（结合 `MySQL/` 系统）：

| 层面 | 手段 | 说明 |
|------|------|------|
| 查询 | 索引匹配 Wrapper 条件 | WHERE + ORDER BY 建复合索引（见 06 模块） |
| 查询 | 只查必要列 | `wrapper.select(...)` 减少回表 |
| 查询 | 深分页 Keyset | OFFSET 大页 → 游标式（06 模块第 3 节） |
| 查询 | 大列表流式 | `selectCursor` 游标（导出/批处理） |
| 写入 | 分批 saveBatch | 单批 500-1000，分批提交 |
| 写入 | 合理索引数量 | 索引多 → 写放大（每 INSERT 维护多个索引） |
| 写入 | 归档策略 | 热冷分离（历史表/分区表）——**千万级表的终局方案** |
| 架构 | 读写分离 | 查询走从库（配合 `@DS` 多数据源） |

```java
// 千万级查询的 MP 写法示范
Page<Order> page = orderMapper.selectPage(new Page<>(1, 20),
        new LambdaQueryWrapper<Order>()
                .select(Order::getId, Order::getOrderNo, Order::getAmount)   // 只查必要列
                .eq(Order::getStatus, 1)
                .between(Order::getCreateTime, start, end)
                .orderByDesc(Order::getId));           // 索引：idx_status_ctime
```

> 🎯 **核心要点**：千万级的真相 = **"索引 + 少取列 + 不分页深翻"**——MP 只是执行者，性能决策在索引与查询形态。**表超过千万行先做数据治理（归档/分区），再谈 SQL 优化**。

## 4. 监控：性能插件与慢 SQL

**三个监控手段**：

```java
// ① 性能分析插件（开发/测试期用，生产慎用——有开销）
interceptor.addInnerInterceptor(new PerformanceInterceptor());   // 或 PerfSqlInterceptor
// 输出：每条 SQL 的执行耗时 —— 发现慢 SQL 的快捷方式

// ② SQL 日志（开发期）
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.stdout.StdOutImpl   // 打印完整 SQL（排查用）
    # 生产用 logback 的 mybatis.mapper 包级别控制

// ③ 生产监控：慢 SQL 接入数据库侧（MySQL slow_query_log）+ APM
```

**性能分析插件的使用注意**：

| 注意 | 说明 |
|------|------|
| 生产谨慎 | 每条 SQL 计时有开销——压测确认影响可接受再开 |
| 阈值配置 | `PerformanceInterceptor` 的 maxTime 超时告警 |
| 与分页共存 | 性能插件放最内层（先分页后计时）——顺序参考官方文档 |

**慢 SQL 排查三步**：

```text
① 定位：慢查询日志/APM 找到慢 SQL（含 MP 生成的完整语句）
② 分析：EXPLAIN 看 type（ALL=全表扫描）、key（用了哪个索引）、rows（扫描行数）
③ 修复：补索引 / 改 Wrapper（like 前缀 / 少取列）/ 改查询形态（Keyset/游标）
```

> 🎯 **核心要点**：**MP 生成 SQL 的排查黄金法 = 开日志看 SQL + EXPLAIN 看执行计划**——框架帮忙生成了 SQL，但索引决策永远在 DBA 思维（见 `02-.../SQL调优/` 系统）。

## 5. 生产坑清单（20 条）

| # | 坑 | 现象 | 解法 |
|:-:|-----|------|------|
| 1 | 3.5.9+ 没引 jsqlparser | 分页静默失效 | 引入 `mybatis-plus-jsqlparser` |
| 2 | Boot 4 用错 starter | 启动失败 | `mybatis-plus-spring-boot4-starter`（3.5.13+） |
| 3 | 同时引入 mybatis/mybatis-spring | 版本冲突/异常 | 只留 MP 的 starter |
| 4 | 逻辑删除 × 唯一索引 | 重复注册冲突 | 释放唯一字段（08 模块第 1 节） |
| 5 | 手写 SQL 无逻辑删除条件 | 已删数据被查出来 | XML 手动加 `deleted=0` |
| 6 | updateById 想置 null | 字段没更新（静默） | `UpdateWrapper.set(col, null)` |
| 7 | `.eq(col, null)` | 查询结果为空 | 条件重载 `.eq(cond, col, val)` |
| 8 | 分页页码传 0 | 查不到数据 | 页码从 1 起 / `Math.max(current,1)` |
| 9 | 多数据源分页失效 | 无 LIMIT | 每数据源注册拦截器（06 模块第 7 节） |
| 10 | 乐观锁没注册插件 | version 不生效（静默） | 注册 OptimisticLockerInnerInterceptor |
| 11 | 乐观锁冲突不检查返回值 | 覆盖更新 | `rows == 0` 处理冲突 |
| 12 | 更新无 WHERE | 全表更新事故 | BlockAttack 插件 + 代码规范 |
| 13 | 循环里调 MP 方法 | 性能灾难 | saveBatch/updateBatchById |
| 14 | 雪花 ID 传前端 | JS 精度丢失 | Long → String 序列化 |
| 15 | 实体加非表字段忘 `exist=false` | 列不存在报错 | `@TableField(exist = false)` |
| 16 | 自定义 SQL 里 `${}` `#{}` 混用 | 注入风险/参数错误 | 值用 `#{}`，片段用 `${ew.customSqlSegment}` |
| 17 | 实体无 getter 用 Lambda Wrapper | 编译失败 | Lombok @Data 或手写 getter |
| 18 | saveBatch 无主键回填 | 后续要用 id 拿不到 | 逐条 save 或分批后单独查询 |
| 19 | 多租户手写 SQL 无 tenant 条件 | 跨租户数据泄露（最高危） | XML 手动加租户条件 |
| 20 | 逻辑删除字段与实体字段名不一致 | 逻辑删除不生效 | 确认驼峰映射开启/注解指定 |

> 🎯 **核心要点**：20 条坑的**总根源 = 三个"静默"**——**依赖缺失静默（jsqlparser）、插件未注册静默（分页/乐观锁）、MP 自动能力不覆盖手写 SQL（逻辑删除/租户/填充）**。记住三个静默，坑清单记住一半。

## 6. 80/20 原则：MP 与原生 SQL 的边界

**行业共识**：**80% 单表操作交给 MP，20% 复杂查询用原生 MyBatis/XML**：

```text
用 MP（80%）：
- 单表 CRUD、单表条件查询/分页
- 逻辑删除/乐观锁/多租户/自动填充等规范能力
- 批量操作（saveBatch）

用原生 SQL/XML（20%）：
- 多表联查（JOIN）、复杂聚合（GROUP BY 多级）
- 性能敏感 SQL（需要手控执行计划）
- 特殊语法（窗口函数、JSON 函数等）
```

```java
// 边界决策示例：订单报表查询（多表聚合）→ 原生 XML
@Select("""
    SELECT u.user_name, COUNT(o.id) AS order_count, SUM(o.amount) AS total_amount
    FROM `order` o
    JOIN user u ON u.id = o.user_id
    WHERE o.create_time BETWEEN #{start} AND #{end}
    GROUP BY u.id
    ORDER BY total_amount DESC
    """)
List<ReportRow> reportOrderStats(@Param("start") LocalDateTime start,
                                 @Param("end") LocalDateTime end);
```

**判断标准**：**"单表 + 简单条件"用 MP；"多表 + 聚合 + 性能敏感"写 SQL**——Wrapper 硬拼 JOIN 是可读性灾难（见 04 模块第 6 节）。

> 🎯 **最终核心要点**：MP 的生产定位 = "**效率引擎 + 规范框架**"——单表开发快 5 倍、规范（逻辑删除/乐观锁/租户）由框架强制、批量操作开箱即用；同时**清醒地守住边界**：复杂 SQL 回归原生、三个"静默"场景有预案、性能决策交给索引与执行计划。用得好，MP 是后端效率的倍增器。
