## 1. 批量 vs 循环：性能差距

**为什么循环单条慢**（批量优化的动机）：

```text
循环单条（N 次 executeUpdate）：
  每次：SQL 发送 + 数据库解析执行 + 提交（autoCommit）
  → N 次网络往返 + N 次解析 + N 次提交

批量（1 次 executeBatch）：
  1 次发送 N 条 + 数据库批量执行 + 1 次提交
  → 网络往返 1 次 + 解析 1 次

实测量级（社区基准，参考）：
  10 万条插入：
    循环单条      ~8000ms
    JDBC 批处理   ~750ms（约 10 倍提升）
    + rewriteBatchedStatements → 更快（MySQL 多值插入）
```

**批处理快在三个地方**：

| 环节 | 循环 | 批量 |
|------|:----:|:----:|
| 网络往返 | N 次 | **1 次** |
| SQL 解析 | N 次 | **1 次** |
| 事务提交 | N 次 | 1 次 |

> 🎯 **核心要点**：批量 = "**一次发送 N 条（省往返/解析/提交）**"——**约 10 倍提升**是基准；与 `MyBatisPlus/08` 的 saveBatch 数据（循环 8200ms vs 批处理 750ms）同源。

## 2. addBatch / executeBatch 基础

```java
// 批量插入的标准姿势
String sql = "INSERT INTO user (name, age) VALUES (?, ?)";
try (Connection conn = ds.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql)) {

    conn.setAutoCommit(false);              // ① 关闭自动提交（批处理必须）

    for (User u : users) {
        ps.setString(1, u.getName());
        ps.setInt(2, u.getAge());
        ps.addBatch();                      // ② 加入批次（不执行）
        // 分批控制：每 1000 条执行一次（防内存/超时）
        if (batchCount++ % 1000 == 0) {
            ps.executeBatch();              // ③ 执行批次
            ps.clearBatch();                // 清空批次
        }
    }
    ps.executeBatch();                      // ④ 执行剩余
    conn.commit();                          // ⑤ 统一提交

} catch (SQLException e) {
    conn.rollback();                        // ⑥ 失败回滚
    throw e;
}
```

**executeBatch 的关键**：

```text
① 返回 int[]：每条的执行结果（EXECUTE_FAILED = -3 表示失败）
② 必须配合 setAutoCommit(false)：批处理 + 自动提交 = 每批独立提交
③ 分批执行：大数据量分批（每批 500-1000）防内存与超时
④ 失败处理：批量失败 → 判断哪些成功（int[] 逐条）
⑤ 预编译复用：addBatch 前 setXxx（同一条 SQL 复用执行计划）
```

> 🎯 **核心要点**：批量 = "**addBatch 攒批 + executeBatch 执行 + 关自动提交 + 分批控制**"——**"setAutoCommit(false) 是批处理前提"**（否则每批自动提交）；int[] 返回值可逐条判断成败。

## 3. MySQL rewriteBatchedStatements

**MySQL 批处理的隐藏问题与优化**：

```text
问题：MySQL 驱动默认的批处理 = "逐条发送"（只是省了提交）
  → executeBatch 收益打折（网络往返没省！）

解法：rewriteBatchedStatements=true
  → 驱动把 N 条 INSERT 改写成"多值 INSERT"
  INSERT INTO user (name, age) VALUES (?,?),(?,?),(?,?)...
  → 真正的 1 次发送（网络往返省掉）
```

```java
// URL 参数（必配，见 01 模块）：
String url = "jdbc:mysql://localhost:3306/db"
        + "?rewriteBatchedStatements=true"
        + "&serverTimezone=Asia/Shanghai";
```

**rewriteBatchedStatements 的效果**：

| 配置 | 机制 | 收益 |
|------|------|------|
| 默认（false） | 逐条发送 + 批量提交 | 省提交 |
| **true** | **多值 INSERT（1 次发送）** | **省网络往返（再提升数倍）** |

**注意边界**：

```text
① 仅对 INSERT 有效（UPDATE/DELETE 不重写）
② 多值 INSERT 有大小限制（max_allowed_packet）——分批控制
③ 与 MyBatis 的 batch 执行器配合（MyBatisPlus saveBatch 底层）
   → MyBatisPlus/08 的实测数据（750ms vs 1500ms）即此参数差异
```

> 🎯 **核心要点**：MySQL 批量优化 = "**rewriteBatchedStatements=true（多值 INSERT）**"——**"默认批处理在 MySQL 只是省提交、此参数才省网络往返"是深度考点**；与 MyBatisPlus saveBatch 联动理解。

## 4. 批量与事务组合

**批量操作的事务边界**（正确姿势）：

```java
// 方案 1：整批一个事务（推荐——要么全成要么全回滚）
conn.setAutoCommit(false);
try {
    for (batch : chunks(users, 1000)) {   // 分批
        addBatchAll(batch);
        ps.executeBatch();
    }
    conn.commit();                        // 全部提交
} catch (SQLException e) {
    conn.rollback();                      // 全部回滚
}

// 方案 2：每批一个事务（单批失败不影响其他批）
conn.setAutoCommit(false);
for (batch : chunks(users, 1000)) {
    try {
        executeBatch(batch);
        conn.commit();                    // 每批提交
    } catch (SQLException e) {
        conn.rollback();                  // 只回滚本批
        log.error("批次失败，跳过: {}", batch.size(), e);
    }
}
```

**两种方案的选型**：

| 场景 | 方案 | 理由 |
|------|------|------|
| 导入必须全成（对账） | 整批一个事务 | 原子性 |
| 导入允许部分成功（容错） | 每批一个事务 | 单批失败不影响其他 |
| 超大导入（百万级） | 每批一个事务 | 大事务回滚成本高 |

**注意**：大事务（几十万条）的回滚成本高——**分批提交是超大导入的标准**（与 `MyBatisPlus/08` 的批量实践一致）。

> 🎯 **核心要点**：批量事务 = "**整批一事务（原子）vs 每批一事务（容错）**"——**"百万级导入必须分批提交"**（防大事务回滚灾难）；与 MyBatisPlus saveBatch 的事务配合（@Transactional）联动。

## 5. 批量操作最佳实践

**批量操作完整清单**（2026 实践）：

```text
① 预编译：PreparedStatement（批处理前提）
② 关自动提交：setAutoCommit(false)
③ URL 优化：rewriteBatchedStatements=true（MySQL）
④ 分批控制：每批 500-1000 条（防内存/超时/max_allowed_packet）
⑤ 事务策略：原子（整批）vs 容错（每批）
⑥ 失败处理：executeBatch 的 int[] 逐条判断
⑦ 监控：批处理耗时/吞吐（批量导入任务指标）
⑧ 与框架：MyBatis BatchExecutor / MyBatisPlus saveBatch
```

**性能对比总表**（参考量级，与 MyBatisPlus/08 一致）：

| 方式 | 10 万条耗时 | 关键 |
|------|:-----------:|------|
| 循环单条 | ~8000ms | 反模式 |
| JDBC 批处理 | ~750ms | addBatch + 关提交 |
| + rewriteBatched | ~400-600ms | 多值 INSERT |
| MyBatisPlus saveBatch | ~1500ms | 内部批处理（未开 rewrite 时） |

**一句话总结**：

```text
批量操作四件套：
  PreparedStatement（预编译）+ setAutoCommit(false)（关提交）
  + executeBatch（批量执行）+ 分批（500-1000）
MySQL 再加：rewriteBatchedStatements=true（多值 INSERT）
事务二选一：整批原子 or 每批容错（超大导入分批提交）
```

> 🎯 **核心要点**：最佳实践 = "**预编译 + 关提交 + 分批 + rewrite**"四件套——**"循环单条是性能红线"与"百万级分批提交"**两条规范；与 MyBatisPlus/08 的 saveBatch 数据完全同源（底层就是 JDBC 批处理）。
