> 🎯 Oracle 索引和 MySQL 有显著差异——B-Tree 默认不存 NULL、函数索引直接支持 `UPPER(name)`、聚簇因子决定全表扫描还是索引扫描。读懂执行计划是性能调优的第一步

## 1. 索引类型速查

| 索引类型 | 说明 | 适用场景 |
|---------|------|---------|
| **B-Tree** | 默认索引（最常用） | 等值/范围查询 |
| **Bitmap** | 位图索引（DW 环境） | 低基数列（性别/状态） |
| **Function-Based** | 函数索引 | `WHERE UPPER(name) = ?` |
| **Reverse Key** | 反转键索引 | 自增主键高并发 |
| **IOT** | 索引组织表 | 主键查询（数据+索引在一起） |
| **Partitioned** | 分区索引 | 大表分区 |

```sql
-- 创建索引
CREATE INDEX idx_name ON users(name);
CREATE UNIQUE INDEX idx_email ON users(email);
CREATE BITMAP INDEX idx_status ON orders(status);       -- 位图索引
CREATE INDEX idx_upper_name ON users(UPPER(name));      -- 函数索引（Oracle 特性！）
```

### Oracle 索引特殊规则

```text
Oracle B-Tree 索引不存 NULL！
  → WHERE name IS NULL → 不会走索引
  → 解决：CREATE INDEX idx ON users(name, 1) 复合索引+常量

每条索引都有聚簇因子 (Clustering Factor)：
  → 低 = 数据物理顺序接近索引顺序 → 全表扫描少
  → 高 = 数据分散 → 优化器倾向于全表扫描
```

## 2. 执行计划阅读

```sql
-- 生成执行计划
EXPLAIN PLAN FOR SELECT * FROM users WHERE name = 'Alice';
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

-- 典型执行计划输出：
-- | Id | Operation         | Name      | Rows | Cost |
-- |  0 | SELECT STATEMENT  |           |   10 |    3 |
-- |  1 |  TABLE ACCESS FULL| USERS     |   10 |    3 |  ← 全表扫描

-- 加索引后：
-- | Id | Operation                   | Name      | Rows | Cost |
-- |  0 | SELECT STATEMENT            |           |    1 |    2 |
-- |  1 |  TABLE ACCESS BY INDEX ROWID| USERS     |    1 |    2 |
-- |* 2 |   INDEX RANGE SCAN          | IDX_NAME  |    1 |    1 |
```

### 常见操作

| 操作 | 含义 | 好坏 |
|------|------|:---:|
| `TABLE ACCESS FULL` | 全表扫描 | 🔴 大表很慢 |
| `INDEX RANGE SCAN` | 索引范围扫描 | 🟢 好 |
| `INDEX UNIQUE SCAN` | 索引唯一扫描 | 🟢 最好 |
| `INDEX FULL SCAN` | 索引全扫描 | 🟡 比全表快 |
| `HASH JOIN` | 哈希连接 | 🟡 看情况 |
| `NESTED LOOPS` | 嵌套循环连接 | 🟢 小表驱动大表 |

## 3. 索引优化实战

```sql
-- 1. 查看慢查询的执行计划
SELECT sql_id, executions, elapsed_time/1e6 AS sec, sql_text
FROM v$sql WHERE elapsed_time > 1e7 ORDER BY elapsed_time DESC;

-- 2. 查看表索引使用情况
SELECT index_name, num_rows, distinct_keys, clustering_factor
FROM user_indexes WHERE table_name = 'ORDERS';
-- 聚簇因子接近表行数 → 全表扫描优于索引 → 考虑重建表

-- 3. 索引监控（某个索引是否被使用）
ALTER INDEX idx_name MONITORING USAGE;
-- 跑一段时间业务后...
SELECT * FROM v$object_usage WHERE index_name = 'IDX_NAME';
-- USED = YES/NO

-- 4. 收集统计信息（让优化器做出正确决策）
EXEC DBMS_STATS.GATHER_TABLE_STATS('SCHEMA', 'ORDERS');
```

## 核心要点回顾

- Oracle B-Tree 索引不存 NULL（设计复合索引时注意）
- 函数索引 = Oracle 独有（`CREATE INDEX ON UPPER(name)`）
- 聚簇因子决定优化器选索引还是全表扫描
- 执行计划看 Cost（越低越好）+ Cardinality（估算行数，越准越好）
- 定期 `GATHER_TABLE_STATS`（统计信息是优化器的眼睛）
