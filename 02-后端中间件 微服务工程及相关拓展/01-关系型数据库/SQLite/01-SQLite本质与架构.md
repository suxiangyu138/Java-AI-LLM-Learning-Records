## 1. 嵌入式定位

### 1.1 什么是嵌入式数据库

```text
嵌入式数据库：作为库嵌入应用程序进程内，而非独立服务

SQLite 的定位：
  无服务器（无守护进程）
  零配置（无需安装/配置）
  单文件（整个数据库 = 一个 .db 文件）
  可移植（拷贝文件即迁移数据库）

对照服务型数据库（MySQL/PostgreSQL）：
  独立进程 + 网络协议 + 账号体系 + 配置管理
```

### 1.2 适用边界

| 适用场景 | 不适用场景 |
|---------|-----------|
| 本地/移动应用（手机、桌面） | 高并发写（>1000 写/秒） |
| 工具/原型/嵌入式设备 | 多机共享写入 |
| 数据缓存/离线存储 | 大规模数据分析（用专用库） |
| AI Agent 本地状态 | 需要细粒度权限/网络访问 |

```text
官方口径（SQLite 适用场景说明）：
  适合：设备端、应用内嵌、中小规模（GB 级）
  不适合：高并发写、客户端-服务器场景
  —— "SQLite 通常不是 C/S 应用的正确选择"

规模参考：单机读 10 万+/秒、写数百-数千/秒
  页缓存命中时读极快（内存数据库级别）
```

> 🎯 核心认知：**SQLite 是"库"不是"服务"**——它用进程内调用替代网络 IO，用文件锁替代服务端锁管理。这个定位决定了它的一切特性（快、简单、单写者）与边界（无并发写、无网络）。

## 2. 单文件格式

### 2.1 数据库文件的内部结构

```text
一个 .db 文件包含：
  ① 文件头（100 字节）：magic、页大小、版本号、编码
  ② 页序列：表/索引的 B-tree 页
  ③ 页类型：表页（叶子/内部）、索引页、溢出页
  ④ 空闲页链表：删除后回收的页

关键特性：
  单文件原子性：写入要么全部成功要么不变（回滚日志/WAL）
  跨平台：文件格式在所有平台一致（大小端自动处理）
  版本兼容：新版本可读旧文件（向后兼容承诺）
```

### 2.2 页大小与文件布局

```text
页大小：默认 4096 字节（512-65536 可配置）
  影响：B-tree 扇出、IO 粒度、缓存效率

文件头关键字段：
  offset 16：页大小（1 表示 65536）
  offset 18：文件格式版本（读写版本）
  offset 23：编码（UTF-8/16）

页的分配：
  表/索引使用独立 B-tree（每表一棵树）
  大字段（BLOB/TEXT）→ 溢出页链
```

## 3. B-tree 存储架构

### 3.1 两种 B-tree

| 类型 | 用途 | 结构 |
|------|------|------|
| 表 B-tree | 存储表数据 | 叶子页存完整行（rowid 排序） |
| 索引 B-tree | 存储索引 | 叶子页存键 + rowid 引用 |

```text
表 B-tree 的特点：
  按 rowid 有序存储（非 rowid 表按主键）
  叶子页 = 数据页（无需二次跳转）
  内部页 = 索引页（键 + 子页指针）

对比 MySQL InnoDB：
  InnoDB 聚簇索引 = 表即索引（主键 B+tree 存数据行）
  SQLite 表 B-tree ≈ 同样的聚簇结构（rowid 即主键）
```

### 3.2 B-tree 的操作

```text
查找：从根页二分到叶子（页内二分 + 页间指针）
插入：定位叶子 → 插入 → 满则分裂（页分裂）
删除：定位叶子 → 删除 → 稀疏则合并/留空闲页

复杂度：O(log n)（n 为行数）
  10 亿行 ≈ 3-4 层（4096 页大小下）

缓存友好：页大小与 OS 页对齐 → 顺序扫描高效
```

### 3.3 索引与覆盖

```text
普通索引：CREATE INDEX → 索引 B-tree
  查询：先查索引树 → 拿 rowid → 回表（查表树）

覆盖索引：索引包含查询所需全部列
  → 无需回表（索引树直接出结果）

组合索引：最左前缀原则（同 MySQL）
  (a, b, c) 索引 → 支持 a、a+b、a+b+c 查询

（索引设计详见 03 模块）
```

## 4. 页缓存与读路径

### 4.1 页缓存（Page Cache）

```text
页缓存：内存中的页池（默认 2000 页 ≈ 8MB@4KB 页）
  作用：减少磁盘 IO（热数据驻留内存）
  管理：LRU 淘汰

读路径：
  查询 → 页缓存命中？→ 直接返回
              → 未命中 → 磁盘读入缓存 → 返回

写路径（WAL 模式）：
  写 → WAL 文件追加（顺序写，快）
  → checkpoint 时才合并回主库文件
```

### 4.2 缓存配置

```text
PRAGMA cache_size：缓存页数（默认 -2000 = 2MB 绝对值）
  负值 = 以 KB 为单位的绝对值
  正值 = 页数（受 SQLITE_DEFAULT_CACHE_SIZE 限制）

PRAGMA mmap_size：内存映射读（默认 0）
  开启后读路径走 mmap（省一次拷贝）

PRAGMA page_size：页大小（建库时确定，之后不可改）

性能影响（经验）：
  热数据集 < 缓存 → 读性能 = 内存数据库
  冷数据 → 磁盘 IO 主导（随机读 ~100 微秒/页）
```

## 5. 与 MySQL/PostgreSQL 对比

| 维度 | SQLite | MySQL | PostgreSQL |
|------|:---:|:---:|:---:|
| 部署 | 嵌入式（库） | 服务（进程） | 服务（进程） |
| 配置 | 零配置 | 需要 | 需要 |
| 并发写 | 单写者 | 多写并发 | 多写并发（MVCC） |
| 读并发 | 多读（WAL） | 多读（MVCC） | 多读（MVCC） |
| 类型 | 动态（存储类） | 静态 + 宽松 | 静态（严格） |
| 网络访问 | 无（文件） | TCP | TCP |
| 运维 | 无（拷文件） | 备份/主从 | 备份/主从 |
| 扩展 | 单机 | 集群/分片 | 集群/分片 |
| 适用 | 嵌入式/本地/AI Agent | 在线业务 | 复杂查询/分析 |

```text
本质差异：
  MySQL/PG：并发模型 + 网络协议 + 服务治理（面向"多用户共享"）
  SQLite：单文件 + 进程内（面向"单应用本地存储"）

迁移视角：SQLite → MySQL 不是"换驱动"，是"换架构"
  （类型系统、并发模型、运维方式全部不同）
```

## 6. 部署形态

### 6.1 经典部署

| 形态 | 场景 |
|------|------|
| 移动端内嵌 | Android/iOS（系统自带） |
| 桌面应用内嵌 | 浏览器（WASM）、Electron |
| 服务端本地库 | 边缘节点、单实例服务 |
| 工具链 | 数据分析、测试夹具 |
| 边缘云 | Cloudflare D1（SQLite 边缘分发） |

### 6.2 2025-2026 的新形态（详见 07/08 模块）

```text
AI 时代的新部署形态：
  ① AI Agent 本地状态库（记忆、会话、任务）
  ② RAG 的向量+元数据一体存储（sqlite-vec）
  ③ MCP 服务器的数据层（db-mcp 等）
  ④ 浏览器内数据库（WASM + OPFS 持久化）
  ⑤ 分布式化（Turso/libSQL 多区域复制、Litestream 流式备份）

趋势：SQLite 从"移动端标配"走向"AI 基础设施"
```

> 🎯 **核心要点**：SQLite = "文件即数据库"的极致工程——B-tree 单文件存储、页缓存加速、零配置部署。理解它的架构（单文件、B-tree、页缓存、WAL），就理解了它"为什么快"（进程内 + 页缓存）与"为什么单写者"（文件锁模型）。2025-2026 年它正借助向量搜索与 WASM 成为 AI 应用的默认本地存储。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 嵌入式意味着什么？ | 进程内库、零配置、单文件、无网络 |
| 文件里有什么？ | 头 100 字节 + B-tree 页 + 空闲页 |
| 表怎么存？ | 每表一棵 B-tree（rowid 有序，叶子存数据） |
| 页缓存？ | 默认 2MB，LRU，命中即内存速度 |
| vs MySQL？ | 单写者/动态类型/无网络 vs 并发/静态/服务 |
| 新形态？ | AI Agent 存储、WASM、向量搜索、分布式 fork |
