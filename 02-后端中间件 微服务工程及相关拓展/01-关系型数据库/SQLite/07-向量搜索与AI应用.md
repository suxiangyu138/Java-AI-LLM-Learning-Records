## 1. 为什么 SQLite 需要向量搜索

### 1.1 AI 时代的存储需求

```text
AI 应用（RAG/Agent）的数据模式：
  ① 文档 + 向量（embedding）—— 语义检索
  ② 结构化元数据 —— 过滤
  ③ 关键词索引 —— 精确召回
  ④ 会话/任务状态 —— 记忆

传统方案：向量库（Milvus/Chroma）+ 数据库（SQLite）分离
  → 两套系统、数据同步、部署复杂

SQLite 方案：一个文件装下全部（向量 + 元数据 + 全文）
  → 单文件、零运维、进程内
```

### 1.2 定位：本地/单机的向量方案

| 维度 | SQLite + vec | 专用向量库 |
|------|:---:|:---:|
| 部署 | 库内嵌 | 独立服务 |
| 规模 | 百万级向量 | 十亿级 |
| 索引 | 暴力扫描（目前） | HNSW/IVF |
| 适用 | 本地/边缘/Agent | 在线大规模检索 |
| 运维 | 零 | 集群 |

```text
2026 现状：sqlite-vec 索引为暴力扫描（Brute-force）
  → 百万级向量内可用（毫秒-十毫秒）
  → 更大规模/高并发 → 专用向量库

定位总结：SQLite 向量 = "本地优先的 RAG 存储"
  服务器大规模检索仍用 Milvus 等（见 03-AI 层向量数据库目录）
```

## 2. sqlite-vec 扩展

### 2.1 简介

```text
sqlite-vec：SQLite 的向量搜索扩展（Alex Garcia）
  特点：
    ① 纯 C、无依赖、标准扩展加载
    ② 全平台（含 WASM/移动端）
    ③ 虚拟表实现（vec0）
    ④ 支持批量插入、增量更新

安装：
  下载 .so/.dll/.dylib → 加载：
  SELECT load_extension('vec0');  -- 或应用层加载
```

### 2.2 创建与插入

```sql
-- 创建向量表（维度固定）
CREATE VIRTUAL TABLE embeddings USING vec0(
  id INTEGER PRIMARY KEY,
  embedding FLOAT[384]        -- 维度匹配嵌入模型
);

-- 插入（向量 + 元数据外键）
INSERT INTO embeddings (id, embedding)
VALUES (1, '[0.12, -0.34, ...]');   -- 384 维数组

-- 常用维度参考：
--   all-MiniLM-L6-v2: 384 维
--   OpenAI ada-002: 1536 维
--   bge-large-zh: 1024 维
```

### 2.3 距离度量

| 度量 | 语法 | 适用 |
|------|------|------|
| 余弦 | distance_metric=cosine（默认） | 语义相似度（推荐） |
| 欧氏（L2） | distance_metric=L2 | 数值距离 |
| 曼哈顿 | distance_metric=manhattan | 稀疏向量 |
| 汉明 | distance_metric=hamming | 二值向量 |

```sql
CREATE VIRTUAL TABLE embeddings USING vec0(
  embedding FLOAT[384] distance_metric=cosine
);
-- 注意：cosine 模式内部对向量归一化
```

## 3. KNN 查询与过滤

### 3.1 KNN 基本查询

```sql
-- 最近邻（k 个）
SELECT id, distance
FROM embeddings
WHERE embedding MATCH '[0.1, -0.2, ...]'    -- 查询向量
  AND k = 10;                                -- 取前 10

-- 带距离阈值
SELECT id, distance
FROM embeddings
WHERE embedding MATCH '[...]'
  AND k = 100
  AND distance < 0.5;                        -- 阈值过滤
```

### 3.2 与元数据结合

```sql
-- 向量表 + 元数据表 JOIN（标准模式）
SELECT d.id, d.distance, m.title, m.category
FROM embeddings e
JOIN documents m ON m.id = e.id          -- 向量 id → 文档
WHERE e.embedding MATCH '[...]'
  AND k = 50
  AND m.category = 'tech'                -- 元数据过滤（先过滤后 KNN）
ORDER BY e.distance
LIMIT 10;

-- 过滤位置：KNN 前过滤（缩小候选） vs KNN 后过滤
-- 当前版本：过滤在 KNN 内部/外层（注意性能差异）
```

### 3.3 混合过滤模式

```text
三种过滤模式（sqlite-vec 用法）：
  ① KNN 后过滤（简单）：先取 k 个再过滤 → 可能不足 k
  ② KNN 内过滤（支持）：id 范围/排除条件内嵌
  ③ 预过滤（应用层）：先查元数据再向量（推荐）

工程建议：元数据过滤优先"预过滤"
  → 减少向量扫描量（暴力扫描的优化方向）
```

## 4. 混合检索：FTS5 + 向量 + RRF

### 4.1 为什么混合

```text
单一检索的缺陷：
  纯向量：语义好，但精确关键词（人名/ID/专有名词）召回差
  纯 FTS5：关键词精确，但同义词/语义变体召回差

混合检索：两路召回 + 融合排序
  → 语义 + 关键词互补（2025-2026 RAG 标配）

案例（检索共识）：
  "sqlite 的 WAL 模式" → 向量召回（语义）
  "SQLite 3.53 发布" → FTS5 召回（关键词精确）
```

### 4.2 RRF 融合（Reciprocal Rank Fusion）

```text
RRF 原理：基于排名（而非分数）融合
  score(d) = Σ 1/(k + rank_i(d))
  k 通常取 60

为什么用 RRF：
  两路分数不可比（BM25 负值 vs 余弦相似度）
  排名融合规避尺度问题（鲁棒）

流程：
  ① FTS5 查询 → 前 N 条（排名）
  ② 向量查询 → 前 N 条（排名）
  ③ RRF 合并 → 取 Top-K
```

### 4.3 SQL 实现（应用层融合）

```java
// 混合检索流程（Java 示例）
// ① FTS5 召回（关键词）
List<Long> ftsIds = query(
    "SELECT rowid FROM articles_fts WHERE articles_fts MATCH ?", query);
// ② 向量召回（语义）
List<Long> vecIds = query(
    "SELECT id FROM embeddings WHERE embedding MATCH ? AND k = 50", vec);
// ③ RRF 融合
Map<Long, Double> rrf = new HashMap<>();
for (int i = 0; i < ftsIds.size(); i++)
    rrf.merge(ftsIds.get(i), 1.0 / (60 + i + 1), Double::sum);
for (int i = 0; i < vecIds.size(); i++)
    rrf.merge(vecIds.get(i), 1.0 / (60 + i + 1), Double::sum);
// ④ 排序取 Top-K → 回表取详情
List<Long> top = rrf.entrySet().stream()
    .sorted(Map.Entry.<Long, Double>comparingByValue().reversed())
    .limit(10).map(Map.Entry::getKey).toList();
```

```text
工程要点：
  ① 两路召回各取 50-100（融合窗口）
  ② RRF 在应用层实现（简单且可控）
  ③ 可加权重（如向量 0.7 + FTS 0.3）
  ④ 2025-2026 工具链：sqlite-vec-mcp 等已内置混合检索
```

## 5. RAG 的 SQLite 方案

### 5.1 单文件 RAG 架构

```text
一个 .db 文件装下 RAG 全部数据：
  documents 表：文档内容/元数据
  embeddings 表：向量（sqlite-vec）
  articles_fts：全文索引（FTS5）
  chunks 表：切片与关联

查询链路：
  用户问题 → Embedding → 向量召回 + FTS5 召回 → RRF 融合
  → 回表取切片 → 拼上下文 → LLM

优势：
  部署简单（拷文件即迁移）
  本地离线可用（隐私场景）
  无网络依赖（边缘/设备）
```

### 5.2 与专用 RAG 存储对比

| 维度 | SQLite 单文件 | Chroma/FAISS + DB |
|------|:---:|:---:|
| 部署 | 零（库） | 服务/进程 |
| 数据一致 | 天然（同库事务） | 两库同步 |
| 规模 | 百万级 | 亿级 |
| 混合检索 | FTS5+vec 同库 | 需组合两套 |
| 适用 | 本地/小规模/原型 | 大规模生产 |

```text
选型判断：
  <100 万片段 + 本地/边缘 → SQLite 方案（简洁）
  大规模在线 → Milvus/专用（见 03-AI 层）
  混合：生产先用 SQLite 验证 → 规模大再迁移
```

### 5.3 离线/边缘场景

```text
边缘 RAG（2025-2026 场景）：
  设备端知识库（文档 + 向量同文件）
  离线问答（无网络：本地模型 + 本地向量）
  数据隐私（不出设备）

WASM 场景：
  浏览器内 RAG（sqlite-vec 支持 WASM）
  OPFS 持久化 → 完全客户端应用
```

## 6. AI Agent 与 MCP 集成

### 6.1 Agent 的默认状态库

```text
AI Agent 的本地存储需求：
  记忆（长期/短期）
  会话/任务状态
  工具调用记录
  知识缓存（RAG 结果）

为什么 SQLite：
  单文件易备份/迁移
  结构化查询（过滤/聚合）
  事务性（状态一致）
  2025-2026 事实标准：多数 Agent 框架默认 SQLite
```

### 6.2 MCP 服务器

```text
MCP（Model Context Protocol）与 SQLite：
  db-mcp 等服务器：把 SQLite 暴露为 MCP 工具
    （JSON/JSONB、FTS5、向量搜索、统计、SpatiaLite）
  混合检索工作流：FTS5 + 向量（RRF）
  Code 模式沙箱执行：token 开销降 90%

应用模式：
  LLM 直接查询本地库（结构化数据）
  记忆检索（向量 + 关键词）
  工具结果持久化

（MCP 协议详见 03-AI 层 Multi-Agent 与 MCP 目录）
```

### 6.3 Agent 记忆的实现

```text
Agent 记忆的 SQLite 模式：
  短期记忆：messages 表（会话）
  长期记忆：facts 表 + 向量（语义检索）
  混合记忆：FTS5 关键词 + 向量语义（RRF）

写模式（单写者适配）：
  记忆写入频繁 → 批量提交 + 队列
  会话独立库/表 → 分片避免竞争

示例表：
  CREATE TABLE memory (
    id INTEGER PRIMARY KEY,
    content TEXT,
    embedding BLOB,          -- JSONB 向量
    created_at TEXT
  );
```

## 7. 限制与选型

### 7.1 当前限制（2026）

| 限制 | 说明 | 对策 |
|------|------|------|
| 暴力扫描 | sqlite-vec 无 HNSW/IVF | 百万级内可用；预过滤 |
| 无并发写 | 单写者（04 模块） | 写队列/分库 |
| 无分布式 | 单文件 | Turso/libSQL（08 模块） |
| 维度上限 | 每向量最大 512 维（vec0 当前） | 降维/分块 |
| 混合检索手写 | RRF 需应用层 | 工具链/自实现 |

```text
注意：sqlite-vec 与官方 sqlite-vss 的差异
  sqlite-vss（旧，依赖 FAISS，已不维护）
  sqlite-vec（新，纯 C，活跃维护）
  → 新项目用 sqlite-vec
```

### 7.2 选型建议

```text
场景判断：
  本地/边缘/Agent/原型 → SQLite + sqlite-vec（一个文件搞定）
  生产在线 RAG（万 QPS）→ Milvus/Chroma（03-AI 层目录）
  混合：本地验证 → 规模后迁移（数据模型对齐）

趋势（2025-2026）：
  向量搜索进 SQLite 主线（社区讨论中）
  WASM + 向量 = 浏览器端 AI 应用
  MCP 生态把 SQLite 变成 AI 的"通用数据库"
```

> 🎯 **核心要点**：SQLite 在 AI 时代的新身份 = "单文件 RAG/Agent 存储"——向量（sqlite-vec）+ 全文（FTS5）+ 结构化（关系表）三合一，配合 RRF 混合检索，一个 .db 文件即可支撑本地 RAG 与 Agent 记忆。定位是"本地优先"：百万级向量、零运维、可离线；大规模在线检索仍属专用向量库。2025-2026 的生态信号：MCP 服务器、WASM、Turso 分布式化正把它推向 AI 基础设施。
