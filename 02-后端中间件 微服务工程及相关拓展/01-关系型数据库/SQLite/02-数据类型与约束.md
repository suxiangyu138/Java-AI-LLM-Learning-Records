## 1. 存储类：SQLite 的类型系统

### 1.1 五个存储类

| 存储类 | 说明 | 例子 |
|--------|------|------|
| NULL | 空值 | NULL |
| INTEGER | 有符号整数（1-8 字节变长） | 42 |
| REAL | 8 字节浮点 | 3.14 |
| TEXT | 文本（UTF-8/16） | 'hello' |
| BLOB | 二进制数据 | x'FF00' |

```text
核心特性：动态类型（manifest typing）
  列没有固定类型——每行的每个值自带类型
  同一列可存不同存储类的值（默认模式）

与静态类型数据库（MySQL/PostgreSQL）的本质差异：
  静态：列类型约束所有值（INT 列只能存整数）
  动态：列声明只是"建议"（INT 列可存文本！）

示例（默认模式）：
  CREATE TABLE t (a INT);
  INSERT INTO t VALUES (1), ('text'), (3.14), (NULL), (x'AB');
  -- 全部合法！列 a 混合了四种存储类
```

### 1.2 整数存储

```text
INTEGER 的变长存储（1-8 字节）：
  值越小占用越少（存储优化）
  范围：-2⁶³ ~ 2⁶³-1（8 字节）

溢出行为：超出 INTEGER 范围的值 → 存为 REAL
  例：2⁶³ → 存为 REAL（精度可能损失）
  → 大整数场景注意（用 TEXT 存或接受转换）
```

> 🎯 核心认知：**SQLite 的类型是"值的属性"而非"列的属性"**——这是它最独特的特性，也是"SQLite 没有类型"误区的真相（有类型，只是动态）。

## 2. 类型亲和性

### 2.1 五类亲和性

```text
列声明的类型 → 决定"亲和性"（倾向存储的类）：
  INT/INTEGER/BIGINT 等 → INTEGER 亲和
  CHAR/CLOB/TEXT/VARCHAR 等 → TEXT 亲和
  BLOB/无类型 → BLOB 亲和（无倾向）
  REAL/FLOA/DOUBLE 等 → REAL 亲和
  NUMERIC/DECIMAL/BOOLEAN/DATE 等 → NUMERIC 亲和

亲和性的作用：插入时"尽量转换"（但不是强制）
```

### 2.2 转换规则

| 存储类 | INTEGER 亲和 | TEXT 亲和 | NUMERIC 亲和 |
|--------|:---:|:---:|:---:|
| INTEGER → TEXT 列 | 保持 INTEGER | 转 TEXT | 保持 INTEGER |
| REAL → INTEGER 列 | 无损则转 INTEGER | 转 TEXT | 保持 REAL |
| TEXT → INTEGER 列 | 可无损解析则转 | 保持 TEXT | 可解析则转 |
| TEXT → REAL 列 | 可无损解析则转 | 保持 TEXT | 可解析则转 |

```text
关键规则（记忆版）：
  TEXT 亲和：数字转文本（除非是整数且无法转）
  INTEGER/REAL 亲和：文本"看起来像数字"就转数字
  NUMERIC 亲和：宽松转换（布尔/日期声明常用）

示例：
  CREATE TABLE t (a TEXT, b INT);
  INSERT INTO t VALUES (42, '42');
  -- a: 42 存为 TEXT '42'（TEXT 亲和）
  -- b: '42' 存为 INTEGER 42（INTEGER 亲和）
```

## 3. STRICT 表

### 3.1 什么是 STRICT 表（3.37+）

```text
STRICT 表：列类型严格化（接近静态类型）
  CREATE TABLE t (a INT, b TEXT) STRICT;

STRICT 表的规则：
  ① 列必须声明类型（INT/INTEGER/REAL/TEXT/BLOB/ANY）
  ② 值必须匹配声明类型（违反 → 约束错误）
  ③ 无类型亲和性转换（严格匹配）
  ④ 不支持部分类型（无 NUMERIC/DATE 等）

INT 在 STRICT 中特指 64 位整数（区别于 INTEGER 的变长）
```

### 3.2 STRICT vs 默认

| 维度 | 默认模式 | STRICT 表 |
|------|:---:|:---:|
| 类型检查 | 动态（宽松） | 严格 |
| 存储优化 | 变长 | INT 固定 8 字节 |
| 兼容性 | 广泛 | 更严格（像 PG） |
| 适用 | 历史/宽松场景 | 新项目、数据严谨 |

```text
工程建议（2025-2026）：
  新项目默认 STRICT → 减少类型 bug（'42' vs 42）
  迁移场景：ALTER 不能直接改 STRICT（需重建表）
  与 ORM（sqlite-jdbc/JPA）配合良好（类型映射清晰）

注意：STRICT 不支持检查转换（仍无 BOOLEAN/DATE 原生类型）
  → 布尔用 INTEGER 0/1、日期用 TEXT（ISO8601）或 INTEGER（epoch）
```

## 4. 约束体系

### 4.1 约束类型

| 约束 | 作用 | 示例 |
|------|------|------|
| PRIMARY KEY | 主键（rowid 别名/非 rowid） | id INTEGER PRIMARY KEY |
| NOT NULL | 非空 | name TEXT NOT NULL |
| UNIQUE | 唯一 | email TEXT UNIQUE |
| CHECK | 条件检查 | age INT CHECK (age >= 0) |
| FOREIGN KEY | 外键（需 PRAGMA foreign_keys=ON） | user_id INT REFERENCES users |
| DEFAULT | 默认值 | created TEXT DEFAULT (datetime('now')) |

### 4.2 主键的特殊性

```text
INTEGER PRIMARY KEY = rowid 别名：
  ① 自动生成（不提供则自增）
  ② 插入 NULL → 自动分配最大 rowid+1
  ③ 快（B-tree 直接定位）

非 INTEGER 主键（TEXT 主键等）：
  ① 表成为 WITHOUT ROWID？不——默认仍是 rowid 表 + 唯一索引
  ② WITHOUT ROWID 表：主键即聚簇索引（3.8+）
     适用：大表按主键查询（省一次间接）

AUTOINCREMENT 的误区：
  AUTOINCREMENT 保证"rowid 不重用"（删除后不回收）
  默认 INTEGER PRIMARY KEY 可能重用最大 rowid+1
  → 一般场景无需 AUTOINCREMENT（除非要求不重用）
```

### 4.3 外键与级联

```text
外键默认关闭！必须：
  PRAGMA foreign_keys = ON;（每个连接设置）

级联动作：
  ON DELETE CASCADE / SET NULL / RESTRICT
  ON UPDATE CASCADE

注意：外键不影响性能（无索引自动创建要求）
  → 外键列建议显式建索引（否则 JOIN 慢）
```

## 5. 默认值与生成列

### 5.1 默认值

```text
默认值的两种形式：
  常量：DEFAULT 0、DEFAULT 'unknown'
  表达式：DEFAULT (datetime('now'))、DEFAULT (randomblob(16))

表达式默认值（括号包裹）：
  CURRENT_TIMESTAMP（固定格式）
  (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))（ISO8601）
  注意：表达式默认值在插入时求值

3.53 新特性（2026-04）：
  ALTER TABLE 可增删 NOT NULL/CHECK 约束
  （此前需重建表——sqlite-utils transform 等工具的历史工作）
```

### 5.2 生成列（Generated Columns）

```text
生成列：由其他列计算得出（不存储或存储）

VIRTUAL（默认）：每次读取时计算
  → 可建索引（3.31+）
STORED：写入时计算并存储（占空间）

示例：
  CREATE TABLE orders (
    price REAL,
    qty INT,
    total REAL GENERATED ALWAYS AS (price * qty) STORED
  );
  -- 可对 total 建索引加速查询

适用：冗余计算列（加速聚合/过滤）、规范化衍生字段
```

## 6. 类型转换与陷阱

### 6.1 比较与排序规则

```text
值的比较顺序（跨存储类）：
  NULL < INTEGER/REAL < TEXT < BLOB

排序规则（Collation）：
  BINARY（默认，逐字节）
  NOCASE（忽略大小写，仅 ASCII）
  RTRIM（忽略尾部空格）
  自定义（应用层注册）

中文注意：
  默认 BINARY 排序按 UTF-8 字节序
  → 中文"排序"不是拼音/笔画序（需自定义 collation）
```

### 6.2 常见类型陷阱

| 陷阱 | 示例 | 建议 |
|------|------|------|
| '42' vs 42 比较 | WHERE a = 42 匹配不到 TEXT '42'（亲和规则） | STRICT 表或类型一致 |
| 布尔是整数 | TRUE = 1（无原生布尔） | 用 0/1，别用字符串 'true' |
| 日期是文本 | 无原生 DATE 类型 | ISO8601 TEXT 或 epoch |
| 大整数溢出 | 2⁶³ → REAL 精度损失 | TEXT 存储或限制范围 |
| 浮点精度 | 0.1+0.2 ≠ 0.3 | 金额用整数分或 TEXT |

```text
工程铁律（SQLite 特有的）：
  ① 新表用 STRICT（类型可控）
  ② 布尔/日期明确约定（0/1、ISO8601）
  ③ 跨语言传值注意类型（JDBC setString vs setLong）
  ④ 金额用"分"（整数）避免浮点
```

> 🎯 **核心要点**：SQLite 的类型系统 = 动态存储类 + 类型亲和 + STRICT 可选——理解"值的类型"与"列的倾向"的分离，就能解释 90% 的 SQLite 类型怪象。STRICT 表（3.37+）为严谨场景提供了静态类型选项；布尔/日期/大整数三大陷阱是工程中最常见的坑。
