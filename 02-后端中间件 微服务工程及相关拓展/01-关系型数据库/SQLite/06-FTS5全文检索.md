## 1. FTS5 概览

### 1.1 什么是 FTS5

```text
FTS5（Full-Text Search 5）：
  SQLite 内置的全文检索扩展（3.9+，替代 FTS3/4）
  倒排索引：词 → 文档列表（快速定位）

能力：
  关键词查询（BM25 排序）
  短语查询、布尔查询、前缀查询
  近邻查询（NEAR）、列过滤
  高亮/摘要（snippet、highlight）

与 LIKE '%x%' 的本质差异：
  LIKE：全表扫描（无索引，慢）
  FTS5：倒排索引（词定位，快 100-1000 倍）
```

### 1.2 与关系表的配合

```text
FTS5 表 = 虚拟表（特殊存储）：
  CREATE VIRTUAL TABLE articles_fts
    USING fts5(title, body, content='articles', content_rowid='id');

内容表（content=）：
  数据仍存普通表（articles）
  FTS5 只存索引 → 避免双份存储
  查询时 join 回内容表取全文

三种模式：
  ① 独立表（无 content=）：FTS5 自己存数据（简单）
  ② 外部内容表（content=普通表）：省存储（推荐）
  ③ contentless（content=''）：索引 only（无全文存储）
```

## 2. 创建与基本查询

### 2.1 创建 FTS5 表

```sql
-- 简单独立表
CREATE VIRTUAL TABLE docs USING fts5(title, body, content);

-- 外部内容表（推荐：数据在普通表，索引在 FTS5）
CREATE TABLE articles (id INTEGER PRIMARY KEY, title TEXT, body TEXT);
CREATE VIRTUAL TABLE articles_fts USING fts5(
    title, body,
    content='articles', content_rowid='id'
);

-- 同步触发器（增删改时维护索引）
CREATE TRIGGER articles_ai AFTER INSERT ON articles BEGIN
  INSERT INTO articles_fts(rowid, title, body)
  VALUES (new.id, new.title, new.body);
END;
-- （DELETE/UPDATE 同理，略）
```

### 2.2 查询语法

```sql
-- 基本关键词（隐式 AND）
SELECT * FROM articles_fts WHERE articles_fts MATCH 'database sqlite';

-- 布尔操作
... MATCH 'sqlite AND database'     -- 与
... MATCH 'sqlite OR database'      -- 或
... MATCH 'sqlite NOT database'     -- 非
-- 优先级：NOT > AND > OR

-- 短语（双引号）
... MATCH '"high performance"'

-- 前缀
... MATCH 'sql*'

-- 近邻（NEAR，默认 10 词内）
... MATCH 'sqlite NEAR database'

-- 列过滤
... MATCH 'title:sqlite'

-- 联合行号获取详情（外部内容表）
SELECT a.id, a.title, b.snippet(articles_fts, 1, '[', ']', '...', 20)
FROM articles a JOIN articles_fts b ON a.id = b.rowid
WHERE articles_fts MATCH 'sqlite';
```

### 2.3 高亮与摘要

```text
snippet(table, column, prefix, suffix, ellipsis, tokens)：
  提取匹配片段（带高亮标记）

highlight(table, column, prefix, suffix)：
  全文高亮匹配词

示例：
  SELECT snippet(articles_fts, 1, '<b>', '</b>', '…', 12)
  FROM articles_fts WHERE articles_fts MATCH 'sqlite';
  -- 输出：…<b>sqlite</b> 是嵌入式数据库…
```

## 3. BM25 相关性排序

### 3.1 BM25 算法

```text
BM25（Best Matching 25）：现代搜索引擎的标准相关性算法
  评分考虑：
    ① 词频（TF）：词出现次数（饱和处理）
    ② 逆文档频率（IDF）：词越稀有越重要
    ③ 文档长度归一化（长文档惩罚）

SQLite 的 bm25()：
  SELECT ..., bm25(articles_fts) AS rank
  FROM articles_fts WHERE articles_fts MATCH 'sqlite'
  ORDER BY rank;         -- 升序：值越小越相关！

注意：SQLite 的 bm25 返回负值（排序用升序）
  值越小（越负）→ 越相关
  0 = 完全不匹配（理论上）
```

### 3.2 权重调整

```sql
-- bm25(表, 列权重...)：调整各列重要性
-- 例：title 权重 5，body 权重 1（标题命中更值钱）
SELECT ..., bm25(articles_fts, 5.0, 1.0) AS rank
FROM articles_fts WHERE articles_fts MATCH 'sqlite'
ORDER BY rank;
-- 参数顺序对应列定义顺序（title, body）

-- 与混合检索结合（07 模块：RRF 融合）
```

### 3.3 排序实践

```text
排序策略：
  纯相关性：ORDER BY bm25()
  时间衰减：相关性 + 时间因子（应用层计算）
  混合排序：BM25 与向量相似度融合（07 模块 RRF）

限制：
  不支持"相关性与时间"直接混合（需应用层/自定义）
  评分不可跨查询比较（只用于同一查询内排序）
```

## 4. 分词器（Tokenizer）

### 4.1 内置分词器

| 分词器 | 规则 | 适用 |
|--------|------|------|
| unicode61 | Unicode 字母数字（默认） | 英文/拉丁 |
| porter | unicode61 + 波特词干 | 英文（复数/时态归一） |
| trigram | 3 字符滑动窗口 | 子串搜索、模糊匹配 |
| ascii | ASCII 简化 | 快速英文 |

```text
选择要点：
  英文文档 → porter（词干归一提升召回）
  代码/ID → unicode61（保留符号语义？不——unicode61 分词）
  子串/模糊 → trigram（LIKE '%x%' 的替代）
  中文 → 无原生中文分词（见下节）
```

### 4.2 trigram 的妙用

```sql
-- trigram：支持子串匹配（模糊搜索/容错）
CREATE VIRTUAL TABLE names USING fts5(name, tokenize='trigram');

-- 子串查询（LIKE '%xxx%' 的索引版）
SELECT * FROM names WHERE names MATCH '"abc"';   -- 包含 abc 的行
-- 模糊匹配：'ab'、'bc' 都命中（3 字符窗口）

适用：名称模糊搜索、日志检索、URL 匹配
代价：索引更大（3 字符组合多）、只支持 3+ 字符查询
```

### 4.3 自定义分词器

```text
fts5_tokenizer_v2 API（3.47+）：
  注册应用层分词器（C 接口）
  支持 locale 参数（语言环境感知）

应用场景：
  中文分词（jieba 等词库对接）
  领域词典（专有名词）
  多语言混合

Java 侧：
  sqlite-jdbc 支持加载扩展
  自定义分词器需 JNI/C（成本高）
  → Java 工程中文方案见下节
```

## 5. 中文全文检索方案

### 5.1 问题：SQLite 无原生中文分词

```text
默认分词器的问题（unicode61/porter）：
  按字符边界切分——中文"连续文本"被切成单字/整句？
  unicode61 对 CJK：每个汉字是独立 token？
  → 查"数据库"匹配不到"数据 库"（切分不一致）

实际行为：unicode61 把连续中文按"字符序列"处理
  → 查询"数据库"要求精确序列（无分词概念）
  → 召回差（"数据库管理" 与 "数据库" 不匹配）
```

### 5.2 中文方案对比

| 方案 | 原理 | 优劣 |
|------|------|------|
| trigram | 3 字窗口 | 召回好、索引大、无需分词 |
| 应用层分词 | 先分词再入库（jieba 等） | 精准、需预处理 |
| 扩展分词器 | C 自定义 | 最优、成本高 |
| 字符 n-gram 化 | 预处理拆分 | 简单通用 |

```text
推荐（工程实践）：
  方案 A：trigram（快速部署）
    查询 "数据库" → MATCH '"数据库"' 精确 3 字
    模糊容错好（"数据"、"据库" 都能命中）
    局限：2 字词查询不生效（<3 字符）

  方案 B：应用层分词（精准）
    Java 侧 jieba/HanLP 分词 → 空格连接入库
    FTS5 按空格分词 → 词级检索
    查询同样分词 → MATCH 词序列

  方案 C：混合（生产推荐）
    分词索引（精准）+ trigram（容错）双表
    或分词索引 + LIKE 兜底
```

### 5.3 中文分词入库示例

```java
// 应用层分词方案（Java 侧预处理）
// ① 分词（jieba 等库）
String text = "SQLite 是嵌入式数据库";
String tokens = segment(text);   // "sqlite 是 嵌入式 数据库"

// ② 入库（分词结果进 FTS5）
INSERT INTO articles_fts (rowid, title, body)
VALUES (id, segment(title), segment(body));

// ③ 查询同样分词
String query = segment("嵌入式数据库");  // "嵌入式 数据库"
SELECT * FROM articles_fts WHERE articles_fts MATCH ?;
```

## 6. 内容表与维护

### 6.1 FTS5 的维护命令

```sql
-- 合并索引段（提升查询性能，降碎片）
INSERT INTO articles_fts(articles_fts) VALUES('merge=100');

-- 优化（完全合并——写入前做，代价大）
INSERT INTO articles_fts(articles_fts) VALUES('optimize');

-- 重建索引（分词器/配置变更后）
INSERT INTO articles_fts(articles_fts) VALUES('rebuild');

-- 删除（3.43+：contentless_delete）
INSERT INTO articles_fts(articles_fts, rowid, title, body)
VALUES('delete', 123, '', '');
```

```text
维护节奏（经验）：
  频繁写入 → 定期 merge（如每小时 merge=100）
  批量导入完成 → optimize（查询性能最大化）
  配置/分词器变更 → rebuild
  rebuild 前备份（重建耗时按数据量）
```

### 6.2 FTS5 的版本演进（2025-2026）

```text
3.43+：contentless_delete（contentless 表支持删除）
3.45.2+：tokendata 选项（分词器附加数据）
3.47+：fts5_tokenizer_v2（locale 参数）、contentless_unindexed
   （未索引列）、缺失分词器的表可 drop
3.49/3.48：查询计划器改进、iif 增强
3.51+：改进 FTS5 错误消息

2026 状态：FTS5 是稳定成熟的检索组件
  （与 sqlite-vec 组合 = 混合检索，见 07 模块）
```

### 6.3 与普通查询的配合

```sql
-- FTS5 过滤 + 普通条件（两阶段）
SELECT a.*
FROM articles a JOIN articles_fts f ON a.id = f.rowid
WHERE articles_fts MATCH 'sqlite'
  AND a.status = 'published'        -- 普通条件（内容表）
  AND a.created_at > '2026-01-01'
ORDER BY bm25(articles_fts), a.created_at DESC
LIMIT 20;
```

> 🎯 **核心要点**：FTS5 是 SQLite 的"搜索引擎"——倒排索引 + BM25 排序 + 布尔/短语/近邻查询。工程三要点：**外部内容表（省存储）、bm25 加权排序、分词器选型**；中文是最大挑战（无原生分词），trigram 与"应用层分词"是两条主流路线。维护纪律：定期 merge、批量后 optimize、变更后 rebuild。
