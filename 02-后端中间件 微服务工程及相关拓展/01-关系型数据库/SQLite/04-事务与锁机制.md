## 1. 事务的基本性质

### 1.1 ACID 与实现

| 性质 | SQLite 的实现 |
|------|--------------|
| 原子性 | 回滚日志/WAL（事务失败回滚） |
| 一致性 | 约束检查（含外键、CHECK） |
| 隔离性 | 单写者 + 快照读（可串行化） |
| 持久性 | 刷盘策略（synchronous 配置） |

```text
SQLite 事务的特点：
  默认可串行化（最高隔离级别）——单写者模型的天然红利
  原子提交：要么全部写入要么不变（崩溃恢复）
  崩溃恢复：下次打开时自动回滚未完成事务
```

### 1.2 事务类型

```text
自动事务：每条语句隐式包裹（默认）
显式事务：BEGIN ... COMMIT/ROLLBACK

BEGIN 的三种变体：
  BEGIN DEFERRED（默认）：拿到第一个读/写时才锁
  BEGIN IMMEDIATE：立即拿写锁（避免升级死锁）
  BEGIN EXCLUSIVE：立即拿独占锁（最严格）

工程建议：多语句写事务用 BEGIN IMMEDIATE
  → 避免"读锁升级写锁"时的 SQLITE_BUSY
```

## 2. 两种日志模式

### 2.1 回滚日志（Rollback Journal，默认）

```text
写事务流程：
  ① 修改前：原页复制到回滚日志（journal）
  ② 修改数据库页
  ③ 提交：删除 journal（提交点）
  ④ 崩溃恢复：journal 存在 → 用原页回滚

特点：
  读-写互斥（读阻塞写、写阻塞读）
  写事务期间其他进程不能读
  单文件（无额外文件）——简单

劣势：并发读性能差（读写互斥）
```

### 2.2 WAL（Write-Ahead Logging）

```text
WAL 模式（PRAGMA journal_mode=WAL）：
  写事务：追加到 -wal 文件（顺序写，快）
  读事务：读主库 + wal 中未合并部分（快照）
  checkpoint：定期把 wal 合并回主库

特点（关键优势）：
  读不阻塞写、写不阻塞读（读写并行）
  写性能更好（顺序追加 vs 随机覆盖）
  崩溃恢复更快（wal 重放）

代价：
  额外文件（-wal、-shm）
  单写者限制仍在（写之间互斥）
  网络文件系统不支持（NFS/SMB 问题）
```

| 维度 | 回滚日志 | WAL |
|------|:---:|:---:|
| 读写并发 | 互斥 | 并行 |
| 写性能 | 随机写 | 顺序追加 |
| 读性能 | 好 | 更好（免 journal 回滚） |
| 崩溃恢复 | 回滚 journal | 重放 wal |
| 额外文件 | 无 | -wal/-shm |
| 适用 | 读多写少/简单 | **现代默认（生产推荐）** |

> 🎯 核心认知：**WAL 是 SQLite 并发模型的关键升级**——从"读写互斥"到"读写并行"，让嵌入式数据库在服务端场景可用。生产环境默认 WAL + busy_timeout 是最佳组合。

## 3. WAL 模式的细节

### 3.1 WAL 文件结构

```text
-wal 文件：按帧（frame）追加的日志
  -shm 文件：共享内存索引（读事务定位 wal 帧）

WAL 生命周期：
  写入 → wal 增长 → checkpoint 触发 → wal 截断

checkpoint 触发条件：
  自动（wal 达 wal_autocheckpoint 默认 1000 页）
  手动（PRAGMA wal_checkpoint / wal_checkpoint(FULL)）
```

### 3.2 WAL 模式的关键 PRAGMA

```sql
-- 开启 WAL（持久设置）
PRAGMA journal_mode=WAL;

-- 自动 checkpoint 阈值（页数，默认 1000）
PRAGMA wal_autocheckpoint=1000;

-- 手动 checkpoint（TRUNCATE 截断 wal）
PRAGMA wal_checkpoint(TRUNCATE);

-- 同步级别（见下）
PRAGMA synchronous=NORMAL;
```

```text
WAL 的工程要点：
  ① 每次连接都要设 journal_mode（或放连接池初始化）
  ② 只读场景不需要 WAL
  ③ wal 文件可能很大（checkpoint 前）——监控
  ④ 备份注意：拷贝主库文件不包含 wal（需 checkpoint 或备份 API）
  ⑤ 3.51.3 修复了 WAL-reset 数据库损坏 bug（升级提示）
```

### 3.3 synchronous 三档

| 级别 | 行为 | 风险 |
|------|------|------|
| FULL（默认） | 每个 checkpoint 前 fsync | 最安全 |
| NORMAL | WAL 模式下的推荐（checkpoint 时 fsync） | 极低（OS 崩溃可能丢 wal） |
| OFF | 不 fsync（交给 OS） | 掉电可能损坏/丢失 |

```text
工程建议：
  WAL + synchronous=NORMAL（生产标配——性能与安全的平衡）
  synchronous=FULL：wal_autocheckpoint 大的场景
  OFF：仅缓存/临时数据（可容忍丢失）
```

## 4. 锁状态机

### 4.1 五级锁（回滚日志模式）

```text
锁的升级路径（读 → 写）：
  UNLOCKED → SHARED（读）→ RESERVED（写意向）
  → EXCLUSIVE（写）→ 提交/释放

各锁的兼容性：
  SHARED：多个读共存
  RESERVED：可写但允许读（准备阶段）
  EXCLUSIVE：独占（提交时短暂持有）

WAL 模式下的锁：
  读：共享（WAL 读不阻塞）
  写：独占（写之间互斥）——单写者的核心
```

### 4.2 锁等待与 SQLITE_BUSY

```text
锁冲突时（写被占用）：
  默认立即返回 SQLITE_BUSY（不等待！）
  → 应用需处理 busy 或设置超时

busy_timeout 设置（推荐）：
  PRAGMA busy_timeout=5000;  -- 最多等 5 秒
  → 等待期间重试（内部轮询）

SQLITE_BUSY vs SQLITE_LOCKED：
  BUSY：其他连接持锁（跨连接）
  LOCKED：同一连接内冲突（少见）

工程处理：
  ① 设 busy_timeout（常规等待）
  ② 失败重试（应用层指数退避）
  ③ BEGIN IMMEDIATE（避免升级死锁）
```

## 5. 单写者与并发模型

### 5.1 单写者的含义

```text
SQLite 的写并发模型：
  同一时刻只有一个写事务（写之间完全串行）
  多进程/多线程写 → 排队（busy 等待）

为什么单写者：
  文件级锁（无行级锁/页级锁）
  设计目标：简单可靠（无死锁检测/锁管理器）

写吞吐的现实：
  单写者 + WAL → 数百-数千写/秒（取决于磁盘）
  对比 MySQL：多写并发（行锁）→ 数万写/秒
```

### 5.2 提升写并发的方案

| 方案 | 思路 | 适用 |
|------|------|------|
| 写合并（批量） | 攒批写（事务包裹） | 高吞吐场景标配 |
| 分库 | 多文件分片 | 可水平拆分的数据 |
| 队列写 | 单写线程 + 队列 | 服务端封装 |
| BEGIN CONCURRENT | 实验性（未入主线） | Turso/libSQL fork |
| 读写分离 | 读副本（WAL 多读） | 读多写少 |

```text
2026 现状：
  BEGIN CONCURRENT（允许并发写）仍在实验分支
  Turso/libSQL 已实现（多写者，写冲突检测）
  → 单写者是主线 SQLite 的现实约束
  → 写合并 + 队列是工程主流解法
```

### 5.3 连接与线程模型

```text
连接使用规则：
  单连接单线程（同一连接不同线程 → 需串行化）
  多线程 → 每线程独立连接（或连接池）

SQLITE_THREADSAFE 编译选项：
  0：单线程模式（最快）
  1：串行化（默认，连接内串行）
  2：多线程模式（连接不可跨线程）

Java/JDBC 实践（09 模块）：
  sqlite-jdbc 每连接独立
  线程池场景：连接池管理（每线程借还）
  写集中：单连接 + 队列（避免锁竞争）
```

## 6. 隔离级别与忙碌处理

### 6.1 隔离级别

```text
SQLite 的隔离（WAL 模式）：
  读事务：快照隔离（读时点的一致性视图）
  写事务：串行化（单写者）

支持的隔离级别：
  READ UNCOMMITTED：可选（PRAGMA read_uncommitted=ON，仅回滚日志模式）
  其余级别：SQLite 实际上只有可串行化（写）+ 快照（读）

对比：
  MySQL 默认 REPEATABLE READ（MVCC）
  PG 默认 READ COMMITTED（MVCC）
  SQLite：简单——单写者天然避免大部分隔离问题

注意：WAL 读事务持续打开 → wal 无法 checkpoint（写放大）
  → 长读事务监控（读事务结束时 checkpoint）
```

### 6.2 死锁与忙处理

```text
SQLite 死锁场景（少但存在）：
  连接 A：BEGIN IMMEDIATE（持写锁）→ 等 B
  连接 B：BEGIN DEFERRED → 升级写锁 → 等 A
  → 双方 busy 超时 → 失败（非死锁，是忙等待）

预防：
  ① 全部用 BEGIN IMMEDIATE（一步到位拿写锁）
  ② busy_timeout 足够大
  ③ 应用层重试

工程处理模板：
  PRAGMA busy_timeout=5000;
  BEGIN IMMEDIATE;
  ... 写操作 ...
  COMMIT;
  -- 失败（SQLITE_BUSY）→ 退避重试（最多 N 次）
```

### 6.3 只读与并发读

```text
只读打开：
  file:xxx?mode=ro（URI）或 SQLITE_OPEN_READONLY
  → 无锁竞争（只拿 SHARED）

并发读扩展：
  WAL 模式：多读 + 一写并行
  读副本：打开同一文件的多个只读连接
  内存库（:memory:）：进程内（多线程共享需串行）

热备份（在线备份）：
  backup API（sqlite3_backup）→ 不打断读写
  VACUUM INTO 'backup.db'（3.27+，简单备份）
```

> 🎯 **核心要点**：SQLite 的并发 = **WAL（读写并行）+ 单写者（写串行）+ busy_timeout（等待机制）**。理解锁状态机与 busy 语义，就能正确设计服务端集成（连接池、写队列、BEGIN IMMEDIATE）；理解快照隔离，就能避免长读事务拖住 checkpoint。单写者是物理约束——工程解法是"合并写、排队写、分库写"。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 两种日志模式？ | 回滚日志（读写互斥）/ WAL（读写并行） |
| WAL 的优势？ | 读写并行、顺序写、崩溃恢复快 |
| 锁状态机？ | SHARED（读）→ RESERVED → EXCLUSIVE（写） |
| SQLITE_BUSY？ | 锁冲突默认立即失败 → busy_timeout 等待 |
| 单写者怎么办？ | 写合并、写队列、分库（BEGIN CONCURRENT 未入主线） |
| 隔离级别？ | 可串行化（写）+ 快照（读）——单写者红利 |
