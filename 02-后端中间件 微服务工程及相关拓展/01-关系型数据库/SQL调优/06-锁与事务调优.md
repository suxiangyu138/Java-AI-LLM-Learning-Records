# 06 - 锁与事务调优

> **核心摘要**：**锁等待是「查不到」的慢查询**——SQL 本身很快，但排队等锁。调优核心：行锁/间隙锁/意向锁的行为、**死锁**的产生与排查、**锁等待监控**、以及**事务长短与隔离级别**对性能的影响。锁问题调优 80% 靠「短事务 + 一致顺序 + 正确索引」。

## 1. 锁等待：看不见的慢查询

> **背景**：业务反馈「某更新特别慢」，EXPLAIN 一切正常——问题在锁。
> **目的**：学会区分「查询慢」与「等锁慢」。
> **适用范围**：更新/删除/并发写入场景的性能排查。

```text
两种「慢」的区分
├── 查询慢（执行慢）：扫描行数多/排序/回表
│   ├── 特征：EXPLAIN 分析有明确问题
│   └── 解法：索引/SQL 改写（前几篇）
├── 等锁慢（排队慢）：SQL 本身快，等别人释放锁
│   ├── 特征：慢日志 Lock_time 高（Query_time 的绝大部分）
│   ├── 特征：performance_schema 看到锁等待
│   └── 解法：短事务/锁顺序/索引（本篇）
└── 金句：看到 Lock_time 占比高 → 这是锁问题，不是查询问题

等锁的典型场景
├── 同一行被长事务占着（先查事务再谈锁）
├── 间隙锁范围扩大（RR 隔离级别）
├── 更新顺序不一致 → 死锁（见第 4 节）
└── 大事务批量更新（锁太多行太久）
```

## 2. InnoDB 锁类型全景

> 🎯 **InnoDB 锁体系**——先认识锁，才能分析锁：

```text
按粒度分
├── 表级锁（整表）：
│   ├── 意向锁（IS/IX）：行锁前的「预告」（快）
│   ├── 元数据锁 MDL：DDL 时（ALTER 阻塞读写）
│   └── 自增锁 AUTO-INC：INSERT 自增
├── 行级锁（InnoDB 特色）：
│   ├── 记录锁 Record Lock：锁单行索引记录
│   ├── 间隙锁 Gap Lock：锁索引间隙（防插入）
│   └── 临键锁 Next-Key Lock：记录 + 间隙（RR 默认）
└── 按模式分
    ├── 共享锁 S（读锁）：可共享，阻塞写
    ├── 排他锁 X（写锁）：互斥
    └── 意向锁辅助：IS/IX

行锁 vs 表锁的真相
├── InnoDB 行锁是「索引记录锁」——走索引才锁行！
├── 没走索引的 UPDATE → 锁全表（间隙锁全覆盖）
│   └── 表现：一条更新锁住整表读写（严重事故！）
└── 金句：UPDATE/DELETE 的 WHERE 必须走索引——不只是性能，是锁安全
```

## 3. 间隙锁与幻读

> 🎯 **间隙锁（Gap Lock）是 RR 隔离级别的「防幻读机制」**——也是锁冲突和死锁的重要来源：

```text
幻读与间隙锁
├── 幻读：同一事务两次查询，第二次多出行（其他事务插入了）
├── 间隙锁：锁定「行之间的空隙」→ 禁止插入
│   ├── 例：SELECT ... WHERE id BETWEEN 10 AND 20 FOR UPDATE
│   ├── 锁住 10-20 的行 + 行间所有间隙
│   └── 其他事务插入 id=15 → 阻塞（防幻读）
├── 临键锁（Next-Key）= 记录锁 + 前间隙（RR 默认组合）
└── 代价：锁范围大 → 并发插入互相阻塞 → 性能下降

间隙锁的性能影响
├── 高频插入场景：范围条件更新 → 间隙锁扩大 → 插入排队
├── 典型事故：按状态批量更新 + 高并发插入 → 全表插入等待
└── 对策：
    ├── 条件走索引 + 精确条件（缩小锁范围）
    ├── 必要场景降隔离级别（RC——无间隙锁）
    └── 拆分大范围更新为小批量

RC vs RR 的锁差异（性能关键）
├── RC（读已提交）：只锁记录（无间隙锁）——并发高
├── RR（可重复读）：记录 + 间隙（防幻读）——并发受限
└── 金句：无幻读硬需求的场景用 RC——锁开销立减（见第 7 节）
```

## 4. 死锁：原理与排查

> 🎯 **死锁 = 两个事务互相等对方的锁**——InnoDB 自动检测并回滚一个（牺牲品）：

```text
死锁产生（经典案例）
├── 事务 A：UPDATE t SET ... WHERE id=1 → 锁 id=1 → UPDATE ... WHERE id=2（等 B）
├── 事务 B：UPDATE t SET ... WHERE id=2 → 锁 id=2 → UPDATE ... WHERE id=1（等 A）
├── A 等 B、B 等 A → 循环等待 → 死锁
└── InnoDB 处理：检测到 → 回滚其中一个（报错：Deadlock found）

排查死锁
├── SHOW ENGINE INNODB STATUS;（LATEST DETECTED DEADLOCK 段）
│   ├── 死锁时间/涉及事务的 SQL/持有与等待的锁
│   └── 分析：两个事务的加锁顺序
├── performance_schema 死锁记录
└── 应用日志：捕获 1213 错误码（Deadlock found when trying to get lock）

死锁根治（四个方向）
├── ① 统一加锁顺序：所有事务按相同顺序操作资源
│   ├── 先 id 小再 id 大（或按业务顺序）
│   └── 例：转账 A→B 与 B→A 都按「小 id 先锁」
├── ② 缩短事务：锁持有时间越短，交叉概率越低
├── ③ 减少锁范围：精确条件 + 索引（避免间隙锁扩大）
└── ④ 重试机制：死锁发生时捕获重试（最终一致性兜底）

死锁 vs 锁等待（别混淆）
├── 死锁：循环等待 → 数据库强制回滚（秒级解决）
├── 锁等待：单方向等待 → 等到超时（innodb_lock_wait_timeout 默认 50s）
└── 金句：死锁是「报错可重试」，锁等待是「静默超时」——后者更要警惕
```

## 5. 锁监控与诊断

> 🎯 **锁问题诊断工具链**——从现象到根因：

```sql
-- ① 查看当前锁等待
SELECT * FROM performance_schema.data_lock_waits\G
SELECT * FROM performance_schema.data_locks\G

-- ② 查看正在运行的事务（谁占着锁）
SELECT trx_id, trx_state, trx_started, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;              -- 找「长事务」= 锁的老大难

-- ③ 慢日志里锁等待高的 SQL
-- ④ SHOW ENGINE INNODB STATUS 看死锁/锁信息
```

```text
诊断流程（谁在等锁、谁占锁）
├── ① innodb_trx：找事务状态（RUNNING/LOCK WAIT）+ 启动时间
│   └── 长事务（小时级）→ 锁的来源（排查应用侧）
├── ② data_lock_waits：等待关系（谁等谁）
├── ③ 定位后：应用侧查长事务代码（事务忘了提交？循环事务？）
└── 常用处理
    ├── 杀掉占用事务：KILL <trx_id 对应连接>
    ├── 应用修复：事务及时提交/超时配置
    └── 金句：锁问题的根因永远是「事务」——锁只是事务的影
```

## 6. 事务调优原则

> 🎯 **锁问题的 80% 是事务问题**——六个原则：

```text
原则一：短事务（最重要的原则）
├── 锁持有时间 = 事务持续时间
├── 事务里别做：网络调用/远程服务/慢查询/等待
├── 规范：只把「必要的写操作」包进事务
└── 金句：事务越短，锁冲突概率越小

原则二：一致的加锁顺序
├── 所有代码路径按相同顺序访问资源（防死锁）
└── 统一约定：小 id → 大 id / 业务顺序

原则三：条件必须走索引
├── UPDATE/DELETE 的 WHERE 走索引 → 只锁目标行
├── 不走索引 → 间隙锁全表（灾难）
└── 金句：锁安全依赖索引——调优与安全一体

原则四：避免大事务
├── 一次性更新 10 万行 → 锁 10 万行 10 分钟
├── 拆批：每批 1000 行 + 间隔提交
└── 批处理脚本：分批 + 每批小事务

原则五：避免长事务（读写混合）
├── 读事务也应尽快提交（快照版本堆积）
├── undo log 膨胀 → 磁盘/回滚慢
└── 只读操作也「用完即提交」

原则六：监控与兜底
├── innodb_lock_wait_timeout：等锁超时（默认 50s 太长，可调 5-10s）
├── 死锁捕获重试（应用层）
└── 金句：事务六大原则 = 「短、序、索引、批、快、兜」
```

## 7. 隔离级别与性能权衡

> 🎯 **隔离级别 = 一致性强度与并发性能的交易**——2026 生产实践：

```text
四个隔离级别（由弱到强）
├── READ UNCOMMITTED：读未提交（脏读）——生产禁用
├── READ COMMITTED（RC）：读已提交
│   ├── 无间隙锁（只锁记录）
│   ├── 无幻读防护（业务自查）
│   └── 并发性能最好——互联网主流（Oracle 默认）
├── REPEATABLE READ（RR）：可重复读（MySQL 默认）
│   ├── MVCC 快照读 + 间隙锁防幻读
│   ├── 一致性好，锁开销大
│   └── MySQL 默认（历史原因——主从复制对 RR 依赖）
└── SERIALIZABLE：串行化（全锁）——性能极差，仅特殊场景

版本与隔离级别的建议（2026）
├── MySQL 8.0 主从复制：RC 也支持（binlog=ROW 时）
│   ├── 老限制：5.7 前 RR 是复制安全的默认选择
│   ├── 8.0 ROW 格式 → RC 复制安全
│   └── 所以：新项目可放心用 RC（性能 + 复制双优）
├── 生产建议：
│   ├── 默认保持 RR（无风险，MySQL 官方默认）
│   ├── 高并发写 + 无幻读需求 → RC（锁开销立减）
│   └── 金句：改隔离级别是「全局决策」——评估业务一致性需求

修改方式
SET GLOBAL transaction_isolation = 'READ-COMMITTED';   -- 8.0
SET SESSION transaction_isolation = 'READ-COMMITTED';  -- 会话级
-- 持久化：my.cnf [mysqld] transaction-isolation = READ-COMMITTED
```

> 💡 **RC vs RR 的选择逻辑**：先问业务「有幻读容忍度吗」——订单/支付类求稳用 RR；日志/计数类高并发写用 RC；拿不准就保持 RR（默认）。

## 8. 核心要点

> 🎯 **核心要点**：
> 1. **Lock_time 高 = 锁问题不是查询问题**——先分「执行慢」还是「排队慢」
> 2. **InnoDB 锁全景**：行锁（记录/间隙/临键）+ 表锁（意向/MDL）——UPDATE 不走索引 = 锁全表
> 3. **间隙锁防幻读**（RR）：锁范围大是并发杀手——精确条件 + 索引缩小锁
> 4. **死锁**：循环等待 → 自动回滚一个 → **统一加锁顺序根治** + 捕获重试
> 5. **监控**：innodb_trx 找长事务 → data_lock_waits 看等待关系 → KILL 止损
> 6. **事务六原则**：短、序、索引、批、快、兜——锁问题 80% 是事务问题
> 7. **隔离级别**：RC 无间隙锁（并发好）/RR 防幻读（默认）——8.0 ROW 复制下 RC 安全可用
