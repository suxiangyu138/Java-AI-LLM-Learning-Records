## 1. Spring Cloud 核心（15 题）

**Q1: Spring Cloud 和 Dubbo 的区别？**
> Spring Cloud 是 HTTP RESTful 微服务全家桶（完整生态），Dubbo 是高性能 RPC 框架（专注通信）。Spring Cloud 集成 Gateway/Nacos/Sentinel 等组件，Dubbo 需要额外整合。两者可混用：Gateway + Feign 对外、Dubbo 内部高性能 RPC。

**Q2: Nacos 和 Eureka 的区别？**
> Nacos：AP/CP 可切换、注册+配置一体、主动健康检查、控制台完善。Eureka：AP 仅保证最终一致、仅注册中心、被动心跳、已停维。Nacos 全面替代 Eureka。

**Q3: @RefreshScope 的原理？**
> 配置变更 → Nacos 推送 RefreshEvent → ContextRefresher.refresh() → 销毁并重建 @RefreshScope Bean → 新 @Value 生效。本质是 Bean 懒加载代理 + 刷新时销毁重建。

**Q4: Feign 和 RestTemplate 的区别？**
> Feign 是声明式 HTTP 客户端（接口+注解自动生成代理），RestTemplate 是命令式（需手动构建 URL/Header/Body）。Feign 更简洁、自动负载均衡、支持拦截器/日志/重试。

**Q5: 服务 A 调用服务 B 的完整流程？**
> A 的 Feign 代理 → LoadBalancer 从 Nacos 获取 B 的实例列表 → 选择实例 → 发送 HTTP 请求 → B 的 Gateway(如有) → B 的 Controller → 返回。拦截器传递 Token/TraceId。

**Q6-Q15**: 涵盖 Sentinel 流控熔断原理、Gateway 路由匹配规则、Seata AT 模式回滚机制、SkyWalking APM 原理、服务雪崩与应对、CAP 在 Spring Cloud 中的体现等。

## 2. 分布式理论（10 题）

**Q16: CAP 定理是什么？为什么只能三选二？**
> 网络分区（P）发生时，如果要保证一致性（C）必须拒绝写入，牺牲可用性（A）；如果要保证可用性必须允许写入，可能产生不一致。P 在网络中不可避免，所以实际是 CP vs AP。ZooKeeper 选 CP，Eureka 选 AP。

**Q17: BASE 理论和 ACID 的区别？**
> ACID 是单机数据库的强事务模型；BASE 是分布式系统的务实妥协。BA（基本可用）+ S（软状态）+ E（最终一致性）。银行交易用 ACID，社交动态用 BASE。

**Q18: Raft 的 Leader 选举过程？**
> Follower 超时未收到心跳 → 转为 Candidate，term++ → 投票给自己，向其他节点请求投票 → 获得多数票当选 Leader → 立即发心跳确立权威。随机超时（150-300ms）防止平票。

**Q19-Q25**: 两阶段提交 vs TCC、一致性哈希原理、分布式 ID 生成方案对比、Paxos vs Raft、分布式锁 Redlock 争议。

## 3. 服务治理（10 题）

**Q26: 如何设计一个注册中心？**
> 核心功能：服务注册（临时节点）、服务发现（获取列表+Watch）、健康检查（心跳/主动探测）、CAP 选型（AP 优先）、高可用（集群）。进阶：namespace 隔离、分组、权重、元数据。

**Q27: 熔断和降级的区别？**
> 熔断是服务调用方的自我保护（下游挂了我不调了），降级是业务兜底（下游挂了返回默认值）。熔断触发降级，但降级不一定由熔断触发（如主动降级）。

**Q28-Q35**: Sentinel 三种熔断策略区别、限流算法（计数器/滑动窗口/令牌桶/漏桶）、雪花算法原理、网关和 Service Mesh 的区别、全链路追踪 TraceId 传递方案。

## 4. 分布式事务（8 题）

**Q36: 2PC 的缺点是什么？**
> 同步阻塞（Phase 1 到 Phase 2 之间锁资源不释放）、协调者单点故障（参与者无限等待）、Phase 2 部分 Commit 成功部分失败导致数据不一致。

**Q37: TCC 和 Saga 的区别？**
> TCC（Try-Confirm-Cancel）：业务层补偿，强隔离性，代码侵入大。Saga：长事务拆分为多个本地事务+补偿，松耦合，隔离性弱。TCC 适合支付等核心链路，Saga 适合跨部门长流程。

**Q38-Q43**: Seata AT 模式原理（前后镜像+Undo Log）、可靠消息最终一致性（本地消息表/RocketMQ 事务消息）、最大努力通知的实现。

## 5. 消息队列（7 题）

**Q44: Kafka 为什么快？**
> 顺序写磁盘（比随机写快 1000 倍）、零拷贝（sendfile）、批量压缩、分区并行消费、Page Cache 热数据读取。

**Q45: 如何保证消息不丢失？**
> 生产端：ack=all + retries。Broker 端：replication.factor≥3 + min.insync.replicas≥2。消费端：手动提交 offset（处理完再 commit）。

**Q46-Q50**: 消息重复消费如何解决（幂等：DB 唯一键/Redis Set/业务状态机）、Kafka vs RocketMQ 选型、死信队列的作用、消息积压的紧急处理方案。
