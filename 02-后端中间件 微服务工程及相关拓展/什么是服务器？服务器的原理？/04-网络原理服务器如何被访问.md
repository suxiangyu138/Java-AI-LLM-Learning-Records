## 1. 一次请求的完整旅程

> **背景**：后端调试网络问题（连不上/慢/断连），先要有「全链路地图」。
> **目的**：建立一次请求端到端的全景心智。
> **适用范围**：网络排障/性能分析/安全（DDoS 防护）的思考框架。

```text
用户点击「下单」→ 完整旅程
├── ① DNS 解析：www.example.com → 203.0.113.10
│   ├── 浏览器缓存 → 系统缓存 → 本地 DNS → 根/权威 DNS
│   └── 拿到 IP（可能多个——轮询）
├── ② TCP 连接：三次握手（客户端 ↔ 服务器）
├── ③ TLS 握手（HTTPS）：证书校验 + 密钥协商（1-2 次往返）
├── ④ 发送请求：HTTP 报文（方法/路径/头/体）
├── ⑤ 网络传输：客户端 → 运营商 → 机房交换机 → 服务器网卡
├── ⑥ 内核处理：网卡收包 → 协议栈解包 → socket 队列
├── ⑦ 应用处理：Nginx → 业务服务 → 数据库……
├── ⑧ 响应返回：原路反向（同 TCP 连接）
└── ⑨ 连接管理：长连接复用 / 关闭

排障启示
├── 「连不上」→ DNS/TCP/防火墙（①②③）
├── 「连上但慢」→ 网络/后端处理（⑤⑥⑦）
├── 「超时无响应」→ 应用卡死/队列堆积（⑦）
└── 金句：网络排障 = 定位请求「死在哪一步」
```

## 2. TCP/IP 四层模型

> 🎯 **分层是网络设计的灵魂**——每一层只关心自己的职责，上下层通过接口协作：

```text
四层模型（从下到上）
├── ① 链路层（网卡/交换机）
│   ├── 单位：帧（Frame）
│   ├── 地址：MAC 地址（物理地址）
│   └── 协议：以太网
├── ② 网络层（路由器）
│   ├── 单位：包（Packet）
│   ├── 地址：IP 地址（逻辑地址）
│   ├── 协议：IP（寻址 + 路由）
│   └── 工具：ping（ICMP）
├── ③ 传输层（操作系统内核）
│   ├── 单位：段（Segment）
│   ├── 协议：TCP（可靠）/ UDP（快）
│   ├── 端口：16bit（0-65535）——区分同一 IP 上的不同服务
│   └── 工具：ss/netstat
└── ④ 应用层（应用程序）
    ├── 协议：HTTP/HTTPS/DNS/SSH/MySQL……
    └── 例子：curl -v（应用层视角调试）

封装与解封装（数据的旅行形态）
├── 发送：应用数据 → +TCP头 → +IP头 → +以太网头（层层打包）
├── 接收：反向层层剥壳（每层只处理自己的头）
└── 金句：数据像俄罗斯套娃——每层包一层，每层剥一层
```

## 3. TCP 三次握手与四次挥手

> 🎯 **TCP 是「可靠传输」的协议**——握手建立连接、确认保证不丢、窗口控制流量：

```text
三次握手（建立连接）
├── ① 客户端 → SYN（我想连接）
├── ② 服务器 → SYN+ACK（收到，我也可以）
├── ③ 客户端 → ACK（连接建立）
└── 为什么三次不是两次？
    ├── 双方都要确认「自己发的能到、对方发的能回」
    └── 两次握手 → 服务器无法确认客户端收到了自己的 SYN+ACK

四次挥手（关闭连接）
├── ① 主动方 → FIN（我说完了）
├── ② 被动方 → ACK（收到）
├── ③ 被动方 → FIN（我也说完了）
├── ④ 主动方 → ACK（关闭）
└── 为什么四次？→ 半关闭：TCP 允许单向关闭（还有数据要发）

连接状态机（后端排障必看）
├── 大量 TIME_WAIT：主动关闭方等待 2MSL（60s）——连接复用不足
│   └── 调优：keep-alive 长连接 / 调整 MSL
├── 大量 CLOSE_WAIT：被动方没关（应用 bug——连接泄漏！）
│   └── 排查：应用层连接没释放（数据库/HTTP 客户端）
├── SYN_RECV 堆积：半连接洪水（DDoS 特征）
└── 查看：ss -ant | awk 统计状态
```

> 💡 **Java 后端常见坑**：CLOSE_WAIT 堆积 = 应用忘记关闭响应/连接（try-with-resources 漏写）；TIME_WAIT 多 = 短连接风暴（改用连接池/长连接）。

## 4. 端口与连接的本质

> 🎯 **端口是「同一 IP 上区分服务的门牌号」**——连接是「四元组」：

```text
连接 = 四元组（唯一标识一条连接）
├── 源 IP + 源端口（客户端）
├── 目标 IP + 目标端口（服务器）
└── 例：10.0.0.5:34567 → 203.0.113.10:8080（一条连接）

端口与服务的对应（服务器常见端口）
├── 22 SSH（运维入口）
├── 80/443 HTTP/HTTPS
├── 3306 MySQL / 6379 Redis / 5432 PostgreSQL
├── 8080/9090 应用服务（Java 常用）
├── 5672 RabbitMQ / 9092 Kafka / 9200 ES
└── 20000-65535 临时端口（客户端出站用）

容量认知（高并发的基础）
├── 一个端口能承受多少连接？→ 无数（只要内存够）
├── 服务端连接数 ≈ 客户端数 × 每客户端连接数
├── 10 万连接 = 常见（连接是「资源」不是「瓶颈」）
├── 真正的瓶颈：每连接的数据量（吞吐）/每连接的 CPU（处理）
└── 金句：万级连接是常态，百万级连接靠 epoll（见 [[05]]）
```

## 5. 内核收包路径：从网卡到应用

> 🎯 **数据包进入服务器的完整路径**——理解它 = 理解「为什么网络性能受内核影响」：

```text
收包路径（简化版）
├── ① 网卡收到数据 → 放入网卡接收队列（DMA 直写内存，不占 CPU）
├── ② 网卡触发中断 → 通知 CPU 有新包
│   ├── 传统：每个包一个中断（高流量下 CPU 被打爆）
│   └── NAPI 合并：中断 + 轮询（批量处理）
├── ③ 内核协议栈处理：
│   ├── 以太网层：剥 MAC 头
│   ├── IP 层：校验/路由（本机则收下）
│   ├── TCP 层：重组/确认/流控（滑动窗口）
│   └── socket 层：放入对应连接的接收缓冲区
├── ④ 应用唤醒：阻塞的 read() 返回 → 应用拿到数据
└── ⑤ 发送路径：反向（应用 → socket 缓冲 → 协议栈 → 网卡）

性能优化方向（2026）
├── 减少拷贝：零拷贝 sendfile（见 [[05]]）
├── 多队列：网卡多队列 + CPU 亲和（RSS——各核各收各的）
├── 卸载：TSO/GSO/LRO（大包合并交给网卡）
└── 绕过内核：DPDK/XDP（用户态网卡处理——极致性能，复杂）
```

## 6. DNS 与域名解析

> 🎯 **DNS 是「互联网的电话簿」**——域名 → IP 的分布式映射系统：

```text
DNS 解析流程（递归 + 迭代）
├── ① 浏览器缓存 → ② 操作系统缓存（/etc/hosts + 解析缓存）
├── ③ 本地 DNS（运营商/公司 DNS）
├── ④ 根 DNS（.）→ 顶级域 DNS（.com）→ 权威 DNS
└── ⑤ 权威 DNS 返回记录（A 记录：域名→IP）

DNS 记录类型
├── A：IPv4 地址
├── AAAA：IPv6 地址
├── CNAME：别名（CDN 的核心机制）
├── MX：邮件服务器
└── TXT：验证/SPF（防垃圾邮件）

服务器部署相关（后端必知）
├── 域名解析到服务器 → A 记录
├── CDN：CNAME 指向 CDN 厂商 → 就近节点
├── 云负载均衡：域名 → SLB VIP → 后端服务器
├── 内部服务：内网 DNS（服务名解析，K8s 内置 CoreDNS）
└── 排障：dig/nslookup 查解析（nslookup www.xxx.com）
```

> ⚠️ **DNS 的坑**：TTL 缓存（改解析要等缓存过期）；DNS 故障 = 全站不可访问（大厂自建 DNS + 多副本）；DDoS 攻击 DNS（DNS 放大攻击）。

## 7. 服务器的网络架构

> 🎯 **单台服务器的网络 = 业务接入 + 集群互连 + 带外管理**三张网：

```text
服务器网络三平面（数据中心标准）
├── ① 业务平面（访问流量）
│   ├── 入站：客户端 → SLB → 服务器（对外）
│   ├── 出站：服务器 → 外部 API/数据库（需要 NAT 出网）
│   └── 规格：10G/25G（按流量）
├── ② 集群互连平面（内部流量）
│   ├── 微服务调用/数据同步/训练集群
│   └── 规格：25G/100G/RDMA（AI 集群）
└── ③ 带外管理平面（IPMI/BMC）
    ├── 不依赖 OS 的管理通道（远程开关机/看硬件状态）
    └── 独立网口 + 独立网段（安全隔离）

服务器对外暴露方式（2026 云原生）
├── 公网 IP 直连：简单（单机时代）
├── 负载均衡（SLB/Nginx）：多机分发 + 健康检查
├── 网关 + 服务网格：微服务统一入口（见 [[微服务架构]]）
└── 金句：服务器「裸奔」在公网 = 安全灾难——永远挂在负载均衡后面
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. **一次请求九步**：DNS→TCP→TLS→请求→传输→内核→应用→响应→连接管理
> 2. **四层模型**：链路/网络/传输/应用——层层封装剥壳，每层只管自己的头
> 3. **三次握手建连接、四次挥手关连接**：TIME_WAIT（主动方）/CLOSE_WAIT（应用 bug）是排查重点
> 4. **连接 = 四元组**：万级连接常态，百万级靠 epoll（[[05]]）
> 5. **收包路径**：DMA → 中断 → 协议栈 → socket——优化方向是「少拷贝、多队列、硬卸载」
> 6. **DNS 是电话簿**：A 记录/CDN CNAME/内网 CoreDNS——TTL 缓存是排障点
> 7. **三平面**：业务 + 集群 + 带外管理——服务器永远挂在负载均衡后面
