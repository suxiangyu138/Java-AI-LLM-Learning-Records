## 1. Linux 为什么统治服务器

> **背景**：开发者天天 ssh 到 Linux，但很少想「为什么是 Linux」。
> **目的**：理解 OS 层对服务器的重要性 + Linux 的生态地位。
> **适用范围**：全栈后端（云服务器默认 Linux）。

```text
Linux 统治服务器的原因
├── ① 开源免费：无授权费（Windows Server 按核收费）
├── ② 稳定可靠：内核级稳定性（服务器 7×24 运行）
├── ③ 生态完整：开发/运维工具全家桶（docker/k8s/nginx……）
├── ④ 资源占用低：无桌面，最小系统仅几百 MB
├── ⑤ 可裁剪：按需构建（容器镜像小到几 MB）
├── ⑥ 服务器生态事实标准：云主机/容器/超算/AI 全 Linux
└── 发行版格局（2026）
    ├── Ubuntu：开发/云主机最流行（友好 + 新）
    ├── CentOS Stream / Rocky / Alma：企业稳定（RHEL 兼容）
    ├── Debian：稳定纯粹（容器基础镜像）
    └── openEuler / 麒麟：国产化（政企需求）
```

> 💡 **CentOS 命运（2024 停止维护）**：CentOS 7 停止更新 → 企业迁移 Rocky/Alma（免费 RHEL 兼容）或 Ubuntu LTS——2026 新项目直接 Ubuntu LTS 或 Rocky 起步。

## 2. 内核与用户态：操作系统的心智模型

> 🎯 **操作系统的核心分工：内核管资源，用户态跑程序**——所有「原理」都建立在这个分界上：

```text
用户态 vs 内核态
├── 用户态（User Space）：应用程序运行
│   ├── 你的 Java 进程/nginx/脚本
│   ├── 不能直接碰硬件（受保护）
│   └── 想用硬件 → 系统调用（syscall）
├── 内核态（Kernel Space）：操作系统核心
│   ├── 进程调度/内存管理/文件系统/网络栈/驱动
│   ├── 特权指令（碰硬件）
│   └── 系统调用入口（open/read/write/socket……）
└── 金句：内核是「资源的管家」，应用是「房客」——房客不能直接接水管

系统调用的代价（性能认知）
├── 每次系统调用：用户态→内核态→用户态（上下文切换）
├── 高频系统调用是性能杀手（read/write 每字节都调用？→ 用缓冲）
├── 高并发框架的优化方向：减少系统调用（见 [[05]] 零拷贝）
└── 排查工具：strace 看系统调用（性能诊断神器）
```

**内核四大核心子系统**：

| 子系统 | 职责 | 后端关联 |
|--------|------|---------|
| 进程调度 | 决定哪个进程用 CPU | CPU 使用率/多核负载 |
| 内存管理 | 虚拟内存/分页/交换 | JVM 堆外内存/内存溢出 |
| 文件系统 | 磁盘数据组织 | 日志落盘/数据库刷盘 |
| 网络栈 | TCP/IP 处理 | 连接/吞吐/延迟 |

## 3. 进程与线程

> 🎯 **进程 = 资源的容器，线程 = 执行的单位**——Linux 的进程模型：

```text
进程（Process）
├── 定义：运行中的程序（代码 + 数据 + 资源）
├── 每个进程独立：内存空间/文件描述符/环境（互不干扰）
├── 树形结构：init/systemd(1 号进程) → 各服务
├── 状态机：运行/就绪/睡眠（阻塞）/僵尸
└── 查看：ps -ef / top（PID 是进程的身份证）

线程（Thread）
├── 定义：进程内的执行流（共享进程的内存）
├── 轻量：创建/切换开销小于进程
├── Java 视角：1 Java 线程 = 1 原生线程（Loom 虚拟线程 2023+ 例外）
└── 查看：ps -eLf / top -H

进程 vs 线程（服务器场景）
├── 多进程：Nginx worker（隔离强，内存独立）
├── 多线程：Java 应用（共享内存，通信方便）
├── 线程池：创建线程有开销 → 复用（Java 线程池/连接池同理）
└── 排查关联：CPU 高 → 找进程内哪个线程（jstack）
```

```text
进程调度与 CPU 负载
├── 调度器：把 CPU 时间片分给进程（CFS 完全公平调度）
├── 负载（load average）：1/5/15 分钟运行队列长度
│   ├── 单核 load=1 表示满载
│   └── 多核 load = 核数 × 利用率（8 核 load 8 ≈ 满载）
└── 金句：load 超过核数 → 排队了（CPU 瓶颈）
```

## 4. 虚拟内存机制

> 🎯 **虚拟内存是操作系统最优雅的设计**——每个进程以为自己独占整个内存：

```text
虚拟内存（Virtual Memory）
├── 进程视角：自己拥有完整连续地址空间（4G/128T）
├── 实际：页表映射 虚拟地址 → 物理页框
├── 好处：
│   ├── 隔离：进程 A 看不到进程 B（安全）
│   ├── 独立：各进程地址空间不冲突
│   ├── 超卖：物理 64G 可跑 200G 虚拟（按需换页）
│   └── 惰性加载：用多少映射多少
└── 金句：虚拟内存 = 「每个进程都以为自己独占机器」

关键机制
├── 页（Page）：内存管理单位（4KB）
├── 缺页（Page Fault）：访问未映射页 → 内核加载 → 慢！
├── swap：物理内存不足 → 换页到磁盘（性能灾难）
└── OOM Killer：内存耗尽 → 内核选进程杀掉（日志 dmesg 可查）

JVM 与虚拟内存（Java 后端关联）
├── 堆：JVM 申请的大块虚拟内存
├── 堆外：直接内存（Netty 用）——绕过 JVM 堆管理
├── 监控：看 RSS（常驻物理内存）而非 VIRT（虚拟）
└── 内存溢出排查：堆 OOM（Java 层面）vs 系统 OOM（杀进程）
```

## 5. 文件系统

> 🎯 **文件系统 = 磁盘上的「数据组织结构」**——日志、数据库、镜像都靠它：

```text
Linux 文件系统体系
├── 虚拟文件系统（VFS）：统一接口（一切皆文件）
│   ├── 普通文件：/data/app.log
│   ├── 设备文件：/dev/sda（磁盘）
│   ├── 目录：/（根）/home（用户）/var（日志）/tmp（临时）
│   └── 特殊：/proc（内核信息）、/sys、/dev/null
├── 底层文件系统：ext4（老牌）/ XFS（大文件）/ Btrfs（快照）
│   ├── 2026 容器默认：OverlayFS（分层镜像）
│   └── 数据库推荐：XFS/ext4（按厂商指引）
└── 金句：「一切皆文件」= 统一抽象的威力——网络/设备/进程都能读写

写盘机制（性能关键）
├── 页面缓存（Page Cache）：写先到内存缓存，内核异步刷盘
│   ├── 快：应用感知不到磁盘慢
│   └── 风险：断电丢数据（数据库用 fsync 强制落盘）
├── fsync：强制刷盘（数据库提交的关键——性能与可靠性权衡）
├── 目录结构规范（FHS）
│   ├── /var/log（日志）、/etc（配置）、/opt（第三方软件）
│   └── 容器镜像只读层 + 可写层（OverlayFS）
└── 排查：df -h（容量）/ iostat（I/O 性能）
```

## 6. Linux 启动流程

> 🎯 **服务器开机后发生了什么**——从按下电源到服务就绪：

```text
Linux 启动五阶段
├── ① BIOS/UEFI（固件）：自检硬件 → 找引导设备
│   └── UEFI（现代）替代 BIOS（支持大磁盘/安全启动）
├── ② Bootloader（GRUB）：加载内核
│   ├── GRUB 菜单（多内核/恢复模式）
│   └── 传递内核参数（root 分区等）
├── ③ 内核初始化：
│   ├── 解压内核 → 初始化子系统（内存/驱动/文件系统）
│   └── 挂载根文件系统 → 启动 1 号进程（init/systemd）
├── ④ systemd（1 号进程）：初始化用户态
│   ├── 并行启动系统服务（网络/sshd/containerd……）
│   ├── 单元管理：systemctl start/status nginx
│   └── 日志：journalctl（systemd 统一日志）
└── ⑤ 应用就绪：业务服务启动（部署的服务由 systemd/容器管理）

启动排查（服务器起不来？）
├── 无显示：看 IPMI/串口日志（带外管理）
├── 内核阶段：GRUB 菜单进单用户模式（紧急修复）
├── systemd 阶段：journalctl -b 查本次启动日志
└── 服务阶段：systemctl status <svc>（看依赖/启动顺序）
```

## 7. 容器与内核：共享的秘密

> 🎯 **容器「共享内核」的本质**——理解这点就理解容器的隔离边界：

```text
容器 vs 虚拟机（内核视角）
├── 虚拟机：每个 VM 一个完整内核（虚拟化硬件 → 装完整 OS）
│   ├── 隔离强（内核级隔离）
│   └── 开销大（多套内核/驱动）
├── 容器：共享宿主机内核
│   ├── 用 Namespace（命名空间）隔离视图
│   │   ├── PID 命名空间：容器内只能看到自己的进程
│   │   ├── 网络命名空间：容器有自己的 IP/端口
│   │   └── Mount：容器有自己的根文件系统视图
│   ├── 用 Cgroup 限制资源（CPU/内存配额）
│   └── 优点：秒级启动/镜像可移植/密度高
└── 代价：隔离边界 = 内核边界
    ├── 内核漏洞 → 容器逃逸（安全风险）
    ├── 特殊应用（需要独立内核）→ 必须 VM
    └── 金句：容器不是「轻量虚拟机」，是「受约束的进程」

容器在服务器上的落地（2026）
├── containerd：运行时（Docker 的容器部分）
├── K8s：容器编排（多台服务器的容器调度）
└── 见 [[06-虚拟化与云服务器]] 深化
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. **Linux 统治服务器**：开源/稳定/生态——CentOS 停维护后选 Ubuntu LTS/Rocky
> 2. **内核 vs 用户态**：应用不能碰硬件，系统调用是唯一通道——性能优化围绕「减少系统调用」
> 3. **进程容器化资源、线程执行计算**：Java 线程=原生线程；load 超核数=排队
> 4. **虚拟内存**：隔离 + 超卖 + 惰性加载；swap 是性能灾难；看 RSS 别看 VIRT
> 5. **文件系统**：Page Cache 提速、fsync 保可靠——数据库刷盘的本质
> 6. **启动五阶段**：UEFI→GRUB→内核→systemd→服务——起不来按阶段排查
> 7. **容器共享内核**：Namespace 隔离视图 + Cgroup 限资源——隔离边界=内核边界
> 8. **与后续联动**：I/O 模型（[[05]]）、容器化（[[06]]）都是本讲的延伸
