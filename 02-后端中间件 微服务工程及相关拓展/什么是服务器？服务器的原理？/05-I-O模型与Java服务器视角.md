## 1. 为什么 I/O 是服务器性能的核心

> **背景**：服务器 90% 的时间在「等 I/O」——等网络数据、等磁盘读写，而不是算。
> **目的**：理解「等」是常态，I/O 模型决定「等待的效率」。
> **适用范围**：高并发设计/性能优化/JVM 调优的底层依据。

```text
服务器的时间都去哪了
├── 网络 I/O：等待客户端请求（连接大部分时间空闲！）
├── 磁盘 I/O：数据库读写/日志/文件
├── 计算：CPU 干活（占比小——业务大多是 I/O 密集型）
└── 金句：后端应用是「I/O 密集型」——优化 I/O = 优化性能

传统阻塞模型的致命问题
├── 每个连接 = 一个线程（连接数 = 线程数）
├── 10 万连接 = 10 万线程：
│   ├── 线程栈内存：默认 1MB × 10万 = 100GB（内存爆炸）
│   ├── 上下文切换：10 万线程争抢 CPU（疯狂切换）
│   └── 结果：C10K 问题（万级连接就崩）
└── 解法：让「一个线程管 N 个连接」→ 多路复用（第 3 节）
```

## 2. 四个 I/O 模型

> 🎯 **I/O 模型 = 「等待 I/O 完成的方式」**——四模型按「等待是否阻塞、谁通知」分类：

```text
① 阻塞 I/O（Blocking，最朴素）
├── 流程：read() → 数据没来 → 线程睡眠 → 数据来了返回
├── 特点：简单直观；线程被占死（等一个连接）
└── 应用：Java BIO（老 Tomcat 模式）

② 非阻塞 I/O（Non-blocking）
├── 流程：read() → 没数据 → 立即返回 EAGAIN（不等待）
├── 特点：线程可干别的；但要「轮询」（反复问，CPU 浪费）
└── 应用：轮询模式（少用）

③ I/O 多路复用（Multiplexing，服务器主流）
├── 流程：一个线程同时监听 N 个 socket → 内核通知「哪个可读了」
├── 特点：1 线程管 10 万连接（事件驱动）
└── 应用：epoll（Linux）/ Nginx / Netty / Redis 单线程

④ 异步 I/O（AIO）
├── 流程：发起读 → 内核读完主动回调（应用全程不等）
├── 特点：最省线程；Linux AIO 支持不成熟（io_uring 2020+ 改善中）
└── 应用：Windows IOCP（成熟）/ Linux io_uring（2026 逐步采用）
```

**模型对比表**：

| 模型 | 线程占用 | 并发能力 | 实现复杂度 | 适用 |
|------|:---:|:---:|:---:|------|
| 阻塞 BIO | 1 连接 1 线程 | 低（C10K 崩） | 低 | 教学/低并发 |
| 非阻塞 | 轮询占 CPU | 中 | 中 | 少用 |
| 多路复用 epoll | 1 线程 N 连接 | **高（百万级）** | 中 | Nginx/Netty/Redis |
| 异步 AIO | 几乎不占 | 高 | 高 | 极致场景（io_uring） |

> 💡 **面试金句**：**Redis 单线程为什么快？**——不是单线程快，是「epoll 多路复用 + 内存操作」——单线程避免了锁竞争，事件驱动一个循环处理所有连接。

## 3. I/O 多路复用：select / poll / epoll

> 🎯 **多路复用三兄弟的演进**——epoll 是 Linux 上高并发的基石：

```text
select（老）
├── 把「要监听的 fd 列表」全量传给内核 → 内核全量扫描
├── 缺点：fd 上限 1024；每次调用全量拷贝；O(N) 扫描
└── 状态：教科书存在

poll（改进）
├── 取消 1024 上限（链表）
└── 仍全量拷贝 + 全量扫描 → 连接多了依旧慢

epoll（Linux 2.6+，服务器标准）
├── 三个关键改进：
│   ├── ① 红黑树注册：fd 注册一次，不用每次全量传
│   ├── ② 就绪链表：内核只通知「有事件的 fd」（不再全扫描）
│   └── ③ 回调机制：事件发生 → 回调挂入就绪链表
├── 复杂度：O(1) 处理就绪事件（select 是 O(N) 全扫）
└── 水平触发（LT）vs 边缘触发（ET）：
    ├── LT：还有数据就一直通知（简单，默认）
    └── ET：只通知一次（要一次读完，高效但易错——Netty 用 LT）

epoll 为什么快（面试必答）
├── 有事件才通知（事件驱动）——空闲连接零开销
├── 注册一次（红黑树）——不用反复拷贝
└── 就绪队列 O(1) 取——百万连接也能毫秒响应
```

## 4. Java 视角：BIO → NIO → Netty

> 🎯 **Java 服务器的 I/O 演进**——BIO 线程爆炸 → NIO 事件驱动 → Netty 封装：

```text
BIO（阻塞 I/O，老 Tomcat 默认）
├── 1 连接 1 线程（accept 后每连接起线程）
├── 限制：默认 maxThreads=200 → 200 并发（连接再多排队）
├── 调优空间小（加大线程数 = 内存/切换爆炸）
└── 2026 现状：新项目不再用（除非 Tomcat 虚拟线程模式）

NIO（非阻塞 + 多路复用，Java 1.4+）
├── 核心组件：
│   ├── Channel（通道：SocketChannel）
│   ├── Buffer（缓冲区）
│   ├── Selector（选择器：epoll 的 Java 封装）
│   └── 模式：一个 Selector 线程注册 N 个 Channel
├── 问题：API 复杂（Buffer flip/事件处理/粘包半包）
└── 结论：直接写 NIO 容易出 bug → 用 Netty

Netty（NIO 的工业封装，2026 Java 网络事实标准）
├── 基于 NIO 的事件驱动框架
│   ├── Reactor 模型：Boss 线程（accept）+ Worker 线程（read/write）
│   ├── 零拷贝（CompositeByteBuf/FileRegion）
│   ├── 编解码器（粘包半包处理器）
│   └── 线程模型优化（IO 线程不阻塞）
├── 使用场景：网关/IM/推送/RPC（Dubbo 底层/Spring WebFlux）
└── 金句：Netty = 「Java 里用 epoll 的正确姿势」

Java 高并发体系对照
├── 老：Tomcat BIO（200 并发封顶）
├── 中：Tomcat NIO + 线程池（几千并发）
├── 高：Netty 事件驱动（十万级）
└── 新：虚拟线程（见第 6 节）
```

## 5. 零拷贝：绕开用户态

> 🎯 **零拷贝 = 「数据不经过应用内存直达目标」**——文件传输/网络转发的性能神器：

```text
传统文件发送（4 次拷贝 + 4 次切换）
├── 磁盘 → 内核缓冲区 → 用户缓冲区（read，2 次拷贝）
├── 用户缓冲区 → 内核 socket 缓冲区（write）
├── socket 缓冲区 → 网卡（1 次拷贝）
└── 每次拷贝伴随用户态/内核态切换——浪费 CPU

零拷贝（sendfile，2 次拷贝）
├── 磁盘 → 内核缓冲区 → 网卡（DMA 直传，不经用户态）
└── 系统调用一次完成：sendfile(fd_in, fd_out)
    └── 节省：用户态拷贝 + 上下文切换

mmap（内存映射）
├── 文件映射到进程地址空间（读文件像读内存）
├── 应用：Netty 的 FileRegion / Kafka 的日志读写
└── 注意：mmap 后文件变更需同步（msync）

零拷贝在 Java 的落地
├── Netty：FileRegion（sendfile）/ CompositeByteBuf（缓冲合并）
├── Kafka：mmap 写日志（顺序写 + mmap = 高性能存储）
└── Nginx：sendfile on（静态文件服务标配）
```

## 6. 虚拟线程（Loom）：2023+ 高并发革命

> 🎯 **Java 21（2023.9）虚拟线程**——「1 线程 1 连接」的阻塞模型回来了，但没有线程开销：

```text
虚拟线程（Virtual Thread，JDK 21 正式版）
├── 本质：JVM 管理的轻量线程（数百万级）
│   ├── 映射：虚拟线程 → 平台线程（载波线程）池（通常 1:1 核数）
│   ├── 阻塞自动让出：遇到 I/O 阻塞 → 让出载波线程 → 恢复时挂回
│   └── 无线程栈 1MB 限制（栈可增长/挂起）
├── 使用：几乎零改动（Thread.ofVirtual().start / Executors.newVirtualThreadPerTaskExecutor）
└── 效果：
    ├── 10 万连接 = 10 万虚拟线程（内存 ~KB 级/线程）
    ├── 代码回到「阻塞式」写法（可读性↑）
    └── Tomcat 21+：虚拟线程模式（新项目标配）

虚拟线程 vs Netty（2026 选型）
├── 虚拟线程：同步阻塞代码 + 高并发（简单）
│   ├── 适合：业务服务（RPC/DB 调用多）
│   └── 注意：synchronized 持锁阻塞会卡载波线程（JDK 21+ 已改进）
├── Netty：事件驱动 + 精细控制（复杂）
│   ├── 适合：网关/框架层/极致性能
│   └── 注意：回调地狱/线程模型心智
└── 金句：虚拟线程「吃掉了 90% 用 Netty 的理由」——业务层用虚拟线程，框架层用 Netty
```

> 💡 **2026 趋势**：Spring Boot 3.4+ 原生支持虚拟线程（`spring.threads.virtual.enabled=true`）；高并发业务服务的默认姿势 = **虚拟线程 + 阻塞式代码**。

## 7. 服务器 I/O 性能实践

> 🎯 **I/O 性能 = 模型（软件）× 硬件（网卡/磁盘）× 系统配置（内核参数）**：

```text
I/O 性能排查三板斧
├── ① 看瓶颈在谁：
│   ├── 网络 I/O：ss -s（连接）/ 网卡 ethtool -S（丢包）
│   ├── 磁盘 I/O：iostat（util% > 80% = 瓶颈）
│   └── CPU 系统态高：协议栈开销大（考虑卸载/零拷贝）
├── ② 选对模型：
│   ├── 业务服务：虚拟线程（阻塞式）
│   ├── 网关/框架：Netty/epoll
│   └── 文件/日志：零拷贝（sendfile/mmap）
└── ③ 内核参数调优（服务器级）：
    ├── /proc/sys/net/ipv4/tcp_tw_reuse（TIME_WAIT 复用）
    ├── somaxconn（连接队列长度——防 SYN 堆积）
    ├── file-max（文件描述符上限——ulimit -n）
    └── vm.swappiness（内存交换倾向——服务器调低）

典型调优案例
├── 高并发短连接：tcp_tw_reuse + 连接池
├── 大量文件传输：sendfile + 调大 socket 缓冲
├── 百万连接：epoll + 多队列网卡 + ulimit 放开
└── 金句：先看模型对不对，再调内核参数——别倒过来
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. **I/O 是服务器命脉**：后端是 I/O 密集型——等网络/等磁盘占 90% 时间
> 2. **四模型**：阻塞（1 线程 1 连接）→ 非阻塞（轮询）→ **多路复用（1 线程 N 连接）**→ 异步
> 3. **epoll 三改进**：红黑树注册、就绪链表、回调通知——O(1) 处理就绪事件
> 4. **Redis 单线程快的真相**：epoll + 内存操作，无锁竞争
> 5. **Java 演进**：BIO（线程爆炸）→ NIO（Selector）→ Netty（工业级封装）
> 6. **零拷贝**：sendfile 2 次拷贝替代 4 次——Kafka mmap、Nginx sendfile
> 7. **虚拟线程（JDK 21）**：阻塞代码 + 百万级线程——业务层替代 Netty 的理由
> 8. **排查顺序**：先看瓶颈在谁 → 再选模型 → 最后调内核参数
