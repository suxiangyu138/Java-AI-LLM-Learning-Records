## 1. Git 工作流

### 1.1 推荐的 Git Flow

```text
主分支：
  main / master    → 生产环境代码（只接受 PR 合并）
  develop          → 开发主线

功能分支：
  feature/xxx      → 从 develop 切出 → 开发 → PR → 合并回 develop

发布分支：
  release/x.x.x    → 从 develop 切出 → 修复 bug → 合并到 main + develop

热修复分支：
  hotfix/xxx       → 从 main 切出 → 修复 → 合并到 main + develop

简化版（小团队推荐）：
  main ← feature/*（PR 合并进 main，main 自动部署）
```

### 1.2 Commit 规范

```text
Commit Message 格式（Conventional Commits）：
  <type>(<scope>): <subject>

type:
  feat     → 新功能
  fix      → 修 Bug
  refactor → 重构（不改变功能）
  docs     → 文档
  test     → 测试
  chore    → 构建/工具变更
  style    → 格式（不影响逻辑）
  perf     → 性能优化

示例：
  feat(user): 添加手机号注册功能
  fix(order): 修复并发下单库存超卖问题
  refactor(auth): 提取 Token 验证公共逻辑
  chore(deps): 升级 Spring Boot 到 3.3

每条 Commit 一个原子变更，不要"修了几个bug顺便改了样式"
```

### 1.3 常用 Git 操作

```bash
# 分支操作
git checkout -b feature/user-register develop   # 从 develop 切新分支
git checkout develop && git pull && git merge feature/user-register  # 合并

# 提交前整理（变基替代合并提交）
git fetch origin && git rebase origin/develop    # 变基到最新 develop
# 解决冲突后：
git rebase --continue

# 合并多个 commit 为一个
git rebase -i HEAD~3    # 交互式合并最近 3 个 commit

# 暂存当前工作
git stash push -m "临时保存"
git stash pop

# 撤销
git reset --soft HEAD~1   # 撤销 commit 保留修改
git checkout -- file.txt  # 撤销文件修改
```

## 2. 分支策略

### 2.1 三种策略对比

| 策略 | 适合 | 合并方式 | 特点 |
|------|:--:|:------:|------|
| **Git Flow** | 有固定发布周期的项目 | merge | 分支多，流程重 |
| **GitHub Flow** | SaaS/持续部署 | squash/merge | 极简，main 即发布 |
| **Trunk-Based** | 成熟 DevOps 团队 | rebase | 主分支极短，频繁集成 |

### 2.2 分支命名规范

```text
feature/<模块>-<简述>      → feature/user-login
feature/<JIRA编号>-<简述>  → feature/DEV-1234-add-avatar
bugfix/<简述>              → bugfix/fix-null-pointer
hotfix/<简述>              → hotfix/fix-payment-crash
release/<版本号>           → release/1.5.0
```

## 3. 代码规范

### 3.1 Java 编码规范速查

```java
// ==== 命名 ====
// 类名：UpperCamelCase
public class UserService {}
// 方法/变量：lowerCamelCase
public UserDTO getUserById(Long id) {}
// 常量：UPPER_SNAKE_CASE
public static final int MAX_RETRY_COUNT = 3;
// 包名：全小写
package com.example.user.service;

// ==== 注释 ====
/**
 * 根据用户ID获取用户信息。
 * @param id 用户ID
 * @return 用户DTO，不存在时返回 null
 * @throws IllegalArgumentException 当 id 为 null 或小于等于 0
 */
public UserDTO getUserById(Long id) {
    // 不要写废话注释：i++ // i 自增  ← 这种不需要！
    // 写为什么这样做，而不是做了什么
}

// ==== 空值防御 ====
// ✅ 返回空集合而非 null
public List<User> getUsers() {
    return users != null ? users : Collections.emptyList();
}

// ✅ Optional 处理可能为 null 的返回值
public Optional<User> findByEmail(String email) {
    return Optional.ofNullable(userMapper.selectByEmail(email));
}
```

## 4. Code Review

### 4.1 Review 关注点

```text
Code Review 检查清单：

  功能性：
    □ 逻辑是否正确？边界条件是否处理？
    □ 空值/NPE 防御是否到位？
    □ 并发安全问题（线程安全、事务边界）
    □ SQL 是否有性能隐患？索引是否合理？

  可维护性：
    □ 命名是否清晰、符合团队规范？
    □ 方法是否过长（> 50 行）？
    □ 是否有过深的嵌套（> 3 层）？
    □ 硬编码是否提取为常量/配置？

  安全性：
    □ 是否有 SQL 注入风险？
    □ 敏感信息是否脱敏/加密？
    □ 权限校验是否正确？
```

### 4.2 Review 礼仪

```text
作为 Reviewer：
  ✅ "这里可以考虑用 Map 替代 switch，扩展性更好"（建议式）
  ❌ "你这写得什么垃圾"（攻击式）
  ✅ 超过 400 行的 PR 要求拆分

作为 Author：
  ✅ PR 描述写清楚：做了什么、为什么这样做、如何测试
  ✅ 超过 400 行主动拆分为多个 PR
  ✅ 及时响应 Review 意见，有异议友好讨论
```

## 5. 日志规范

### 5.1 日志级别使用

| 级别 | 使用场景 |
|:----:|------|
| **ERROR** | 影响功能的错误（异常、数据库连接失败） |
| **WARN** | 潜在问题（降级、重试、配置缺失使用默认值） |
| **INFO** | 关键业务流程（请求开始/结束、订单状态变更） |
| **DEBUG** | 调试信息（方法入参出参、SQL 参数） |
| **TRACE** | 极细节（循环内变量值，生产环境永远不开） |

### 5.2 日志打印规范

```java
// ✅ 占位符（SLF4J）
log.info("用户{}登录成功，IP: {}", userId, ip);

// ❌ 字符串拼接（即使日志级别关闭也会执行拼接！）
log.info("用户" + userId + "登录成功，IP: " + ip);

// ✅ 异常日志必须包含堆栈
log.error("订单创建失败，orderId={}", orderId, exception);

// ❌ 只打 message 丢失堆栈
log.error("订单创建失败: " + e.getMessage());

// ✅ 关键入口出口
@PostMapping("/orders")
public Result createOrder(@RequestBody CreateOrderRequest req) {
    log.info("创建订单请求: {}", req);  // 注意敏感信息脱敏！
    try {
        Result result = orderService.create(req);
        log.info("创建订单成功: orderId={}", result.getData().getId());
        return result;
    } catch (Exception e) {
        log.error("创建订单失败", e);
        throw e;
    }
}
```
