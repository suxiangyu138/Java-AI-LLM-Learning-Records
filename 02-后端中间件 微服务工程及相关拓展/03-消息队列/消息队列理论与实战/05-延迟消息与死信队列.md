## 1. 延迟消息：为什么需要

### 1.1 典型场景

| 场景 | 需求 | 延迟量级 |
|------|------|---------|
| 订单超时未支付取消 | 下单 30 分钟后检查 | 分钟级 |
| 延迟通知（支付提醒） | 指定时间发送 | 秒-小时级 |
| 定时任务（报表生成） | 每天固定时间 | 天级 |
| 库存预留释放 | 预留 10 分钟后释放 | 分钟级 |
| 分布式任务调度 | 指定时刻执行 | 秒级 |

```text
不用 MQ 延迟消息的替代方案：
  ① 定时轮询数据库（每秒扫超时订单）→ 数据库压力大
  ② 定时任务框架（Quartz/XXL-Job）→ 分钟级精度，无 MQ 语义
  ③ 延迟消息 = 精度更高 + 负载更轻（扫描量小）

MQ 延迟消息的本质：消息"到期"后才对消费者可见
```

## 2. 延迟消息的实现原理

### 2.1 时间轮（Time Wheel）

```text
时间轮：环形数组 + 槽位链表
  tick：每 tick 推进一格（如 1 秒）
  槽位：每个槽放"该时刻到期"的任务链表
  轮数：任务可跨多圈（记录圈数）

延迟消息的时间轮实现（RocketMQ 5.x）：
  消息带延迟时间 → 入时间轮对应槽
  时间到达 → 消息转入普通队列 → 消费者可见

复杂度：插入/删除 O(1)，推进 O(1)（每 tick）
  对比数据库轮询：扫描量从"全部待执行"降到"当前槽"
```

### 2.2 分级延迟（Level-based）

```text
RocketMQ 4.x 的延迟分级：
  预定义 18 个等级：1s/5s/10s/30s/1m/2m/.../2h 等
  消息指定等级 → 放入对应延迟队列（DELAY_TOPIC）
  定时线程按等级到期 → 转发到真实 Topic

局限：
  只能选预设等级（不能任意秒数）
  高等级延迟占用独立队列

5.x 改进：任意精度延迟（时间轮 + 秒级粒度）
```

### 2.3 实现方案对比

| 方案 | 精度 | 复杂度 | 代表 |
|------|:---:|:---:|------|
| 数据库轮询 | 秒-分 | 低 | 自研（不推荐） |
| 延迟队列（分级） | 等级粒度 | 中 | RocketMQ 4.x |
| 时间轮 | 秒级任意 | 中 | RocketMQ 5.x、Kafka 自定义 |
| 专门延迟服务 | 毫秒级 | 高 | 自研/云服务 |

```text
Kafka 无原生延迟消息（社区有 KIP 讨论未落地）
  实现方式：消息带"到期时间"字段，消费者判断
  或：用时间轮自研/对接延迟服务

云上（2025-2026）：云厂商 MQ 提供秒级延迟
  （阿里云 RocketMQ 延迟到秒、华为 DMS 支持毫秒级调度）
```

## 3. 各中间件的延迟能力

| 中间件 | 原生支持 | 精度 | 实现 |
|--------|:---:|------|------|
| RocketMQ 4.x | ✅ | 18 个等级 | 分级延迟队列 |
| RocketMQ 5.x | ✅ | 任意秒级 | 时间轮 |
| Kafka | ❌ | 需自研 | 字段标记/时间轮 |
| RabbitMQ | ✅ | 秒级 | TTL + 死信路由（见下） |
| Pulsar | ✅ | 秒级 | Delayed delivery |

```text
RabbitMQ 延迟的巧妙实现：
  TTL（消息存活时间）+ 死信路由（DLX）
  消息 → 延迟队列（TTL=N 秒）→ 到期 → 死信路由 → 真实队列
  → 用"死信"机制实现延迟（TTL 到期 = 延迟结束）

Pulsar：delayed delivery（BookKeeper 延迟索引）
  延迟消息在 Broker 侧管理，到期后投递
```

> 💡 设计洞察：**延迟消息与死信在 RabbitMQ 中共享同一机制**（TTL + DLX）——延迟 = "到期的死信被路由到正确队列"。理解机制比记忆 API 更重要。

## 4. 死信队列：失败消息的收容所

### 4.1 什么是死信

```text
死信（Dead Letter）：反复消费失败、无法正常处理的消息

进入死信的常见条件：
  ① 消费重试次数超限
  ② 消息 TTL 过期未被消费
  ③ 队列达到最大长度被拒收
  ④ 消费端显式拒绝（reject/nack）

死信队列（DLQ）：专门存放死信的队列
  → 隔离失败消息（不阻塞正常消费）
  → 提供人工介入/重放入口
```

### 4.2 各中间件的死信机制

| 中间件 | 死信机制 | 触发 |
|--------|---------|------|
| RocketMQ | 重试 16 次后进死信 Topic | 消费失败重试超限 |
| RabbitMQ | DLX（死信交换机）路由 | TTL/拒绝/队列满 |
| Kafka | 无原生（自定义重试 Topic） | 消费失败写 DLQ Topic |
| Pulsar | 死信 Topic（DLA） | 重试超限 |

```text
RocketMQ 的死信流程：
  消费失败 → 重试队列（16 级：1s 起指数增长）
  → 重试超限 → 死信 Topic（%DLQ%业务名）
  → 死信消息 3 天后自动删除（需及时处理）

RabbitMQ 的死信流程：
  消费者 nack/reject（requeue=false）
  → 消息路由到 DLX → 死信队列
```

### 4.3 死信的处理

| 处理方式 | 做法 | 适用 |
|---------|------|------|
| 人工排查 | 查看死信内容，修复后重放 | 代码 bug 类 |
| 自动重放 | 定时扫描死信 → 重新发送 | 可恢复的临时失败 |
| 数据修正 | 死信内容不合法 → 修正后重放 | 脏数据 |
| 监控告警 | 死信产生即告警（SLA 指标） | 所有场景 |

```text
死信处理的铁律：
  ① 死信必须监控（死信 = 业务失败的显性信号）
  ② 死信不能"躺着"（自动重放/人工定期处理）
  ③ 死信要带上下文（原始消息 + 失败原因）

云厂商实践（2025）：死信队列的自动重放与告警集成
  （阿里云 RocketMQ 死信可配置自动重放策略）
```

## 5. 消费重试策略

### 5.1 重试的层级

```text
重试发生在三个层级：
  ① 客户端本地重试（代码级：捕获异常立即重试）
  ② Broker 重试队列（RocketMQ：消息重新投递）
  ③ 业务补偿（延迟重试：如退避后重新触发）

设计要点：区分"可重试失败"与"不可重试失败"
  可重试：下游超时、网络抖动、锁竞争
  不可重试：消息格式错误、业务状态非法（直接死信）
```

### 5.2 退避策略

| 策略 | 机制 | 适用 |
|------|------|------|
| 固定间隔 | 每次等 N 秒 | 简单场景 |
| 指数退避 | 1s/2s/4s/8s... | 下游抖动 |
| 指数 + 抖动 | 退避 × 随机因子 | 避免惊群 |
| 分级（RocketMQ） | 16 级递增 | 内置默认 |

```text
RocketMQ 16 级重试间隔（默认）：
  1s → 5s → 10s → 30s → 1m → 2m → ... → 2h
  第 16 次失败后进死信

Kafka 自定义重试的设计：
  消费失败 → 写"重试 Topic"（带下次执行时间）
  重试消费者轮询到期消息 → 重新投递
  → 本质是"用 Topic 实现延迟队列"
```

### 5.3 重试与顺序的冲突（呼应 03 模块）

```text
严格顺序场景（订单）：
  失败重试不能跳（阻塞重试）
  但阻塞可能拖垮分区（坏消息阻塞后续）

折中方案：
  ① 顺序敏感消息：本地阻塞重试（有上限）
  ② 顺序不敏感消息：直接重试队列/死信
  ③ 按业务键分区重试（重试队列也用业务键路由）

工程原则：重试策略与顺序需求匹配，勿一刀切
```

## 6. 工程实践与监控

### 6.1 延迟消息工程清单

```text
① 延迟精度需求？（秒级 → 5.x/云服务；分钟级 → 分级即可）
② 延迟量大？（时间轮方案吞吐远高于轮询）
③ 延迟与顺序冲突？（延迟消息天然乱序——按需重排）
④ 补偿机制？（延迟到期后失败 → 重试/死信链路）
⑤ 监控？（延迟队列积压、到期执行成功率）

注意：延迟消息到期后仍可能消费失败
  → 延迟 + 重试 + 死信要串成完整链路
```

### 6.2 死信治理闭环

```text
死信治理的完整闭环：
  产生（重试超限）→ 隔离（DLQ）→ 监控（告警）
  → 分析（失败原因）→ 处理（修复重放/修正数据）
  → 复盘（防复发：改代码/改配置）

量化指标：
  死信率 = 死信数 / 总消息数（目标 < 0.01%）
  死信处理时延（目标：告警后 X 小时内处理）
```

### 6.3 常见错误

| 错误 | 后果 |
|------|------|
| 死信无监控 | 失败静默（业务损失不可见） |
| 重试无上限 | 消息无限重试（下游被打爆） |
| 死信自动删除 | 无人工介入窗口（RocketMQ 3 天） |
| 延迟消息无限膨胀 | 时间轮内存占用（需容量监控） |
| 重试与顺序混用 | 顺序场景乱序 |

> 🎯 **核心要点**：延迟消息与死信队列是"时间"与"失败"两大非功能需求的工程化——延迟靠时间轮/分级/TTL 实现（精度与复杂度权衡），死信靠重试超限 + DLQ 隔离（失败可见 + 可干预）。工程铁律：**死信必须监控、重试必须有上限、延迟精度按需选择**——三者是消息系统 SLA 的隐形支柱。
