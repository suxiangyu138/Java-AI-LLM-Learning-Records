## 1. 问题：跨系统事务

### 1.1 分布式事务的困境

```text
单体事务：本地数据库事务（ACID）——一条 SQL 或一个事务块

分布式事务：跨库/跨服务的一致性
  例：下单 = 订单库写订单 + 库存服务扣库存 + 账户服务扣款
  每个操作在不同数据库/服务 → 无法用本地事务保证原子

困境：无法跨系统"提交或回滚"
  → 引入消息队列，把"原子性"转化为"最终一致性"
```

### 1.2 强一致 vs 最终一致

| 方案 | 一致性 | 特点 |
|------|:---:|------|
| 两阶段提交（2PC/XA） | 强一致 | 阻塞、性能差、少用 |
| TCC（Try-Confirm-Cancel） | 强一致 | 侵入业务、实现复杂 |
| **本地消息表** | 最终一致 | 简单可靠 |
| **事务消息** | 最终一致 | 中间件原生支持 |
| **普通消息 + 补偿** | 最终一致 | 最通用 |

```text
消息队列的定位：解决"最终一致性"（非强一致）
  适用：订单、支付通知、积分、短信等允许短暂不一致的业务
  不适用：扣款（需强一致 → 用 TCC/2PC 或单库事务）

核心思想：把"跨系统原子操作"拆成
  "本地原子操作 + 消息驱动后续操作"
```

> 🎯 核心认知：**分布式事务的工程答案是"分解"而非"原子"**——本地事务保证"第一步+发消息"的原子性，消息驱动后续步骤，失败靠重试/补偿收敛。最终一致性不是"弱"，而是"用时间换正确性"。

## 2. 方案一：本地消息表

### 2.1 原理

```text
核心：业务表与消息表在同一数据库事务中写入

流程（经典）：
  ① 业务操作 + 写消息表（status=待发送）——同一本地事务
  ② 定时任务扫描消息表 → 发送消息到 MQ
  ③ 发送成功 → 更新消息表 status=已发送
  ④ 发送失败/未确认 → 定时重试

关键保证：
  业务与消息同库事务 → "业务成功必有消息"（原子性）
  消息发送可重试 → "消息最终必达"（可靠性）
```

```sql
-- ① 业务 + 消息同事务（原子性保证）
BEGIN;
INSERT INTO orders (...) VALUES (...);       -- 业务
INSERT INTO outbox (msg_id, payload, status)
  VALUES (uuid(), '{"orderId":123}', 'PENDING');  -- 消息表
COMMIT;

-- ② 定时任务（发送 + 状态更新）
SELECT * FROM outbox WHERE status = 'PENDING' LIMIT 100;
-- → 逐条发送 MQ → 成功则 UPDATE status='SENT'
```

### 2.2 优缺点

| 优点 | 缺点 |
|------|------|
| 实现简单（纯应用层） | 消息表与业务耦合（侵入业务表结构） |
| 不依赖中间件特性 | 定时扫描有延迟（分钟级） |
| 通用（任何 MQ 都行） | 消息表膨胀需清理 |
| 可靠（本地事务保证） | 状态管理需自研 |

```text
适用：已有系统改造、不想依赖特定中间件特性
变形：Outbox 模式（事件溯源中的发件箱）
  → 2025 年微服务事件驱动的事实标准模式
```

## 3. 方案二：事务消息

### 3.1 原理：两阶段提交（RocketMQ 5.x）

```text
事务消息（RocketMQ 原生，两阶段）：
  第一阶段（Half 消息）：
    发送"半消息"（消费者不可见）→ Broker 存储
  第二阶段（提交/回滚）：
    本地业务执行
    成功 → 提交半消息（消费者可见）
    失败 → 回滚半消息（丢弃）

回查机制（可靠性兜底）：
  Broker 发现半消息长时间未确认 → 回查业务
  → 业务返回"提交/回滚"（根据本地事务状态）
  → 最多回查 15 次（超时则消息作废/告警）

关键：半消息的提交与本地事务的原子性
  靠"回查"而非分布式锁（无阻塞）
```

```java
// RocketMQ 事务消息（事务监听器）
public class OrderTransactionListener implements TransactionListener {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderService.createOrder(arg);   // ① 本地业务
            return LocalTransactionState.COMMIT_MESSAGE;  // 提交半消息
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // ② 回查：根据本地事务状态决定
        return orderService.isCreated(msg.getKeys())
            ? LocalTransactionState.COMMIT_MESSAGE
            : LocalTransactionState.ROLLBACK_MESSAGE;
    }
}
```

### 3.2 事务消息 vs 本地消息表

| 维度 | 本地消息表 | 事务消息 |
|------|:---:|:---:|
| 侵入性 | 业务表加消息表 | 无表侵入（半消息在 Broker） |
| 实时性 | 定时扫描（分钟级） | 提交即投递（秒级） |
| 依赖 | 任何 MQ | RocketMQ 等原生支持 |
| 复杂度 | 自研状态机 | 回查逻辑 |
| 可靠性 | 高（本地事务） | 高（回查兜底） |

```text
选型建议：
  新系统 + RocketMQ → 事务消息（优雅）
  存量系统/其他 MQ → 本地消息表（通用）
  Kafka → 无原生事务消息（用本地消息表或 KIP 讨论方案）
```

## 4. 方案三：基于消息的最终一致性

### 4.1 简化模型

```text
不需要"事务消息"的最小方案：
  ① 业务执行（本地事务）
  ② 发送普通消息（失败 → 重试）
  ③ 消费端处理 + 幂等

缺陷：②失败 → 消息丢失（业务与发送不原子）
  弥补：消息失败落库 + 定时补发（回到本地消息表）
  → 方案三本质是方案一的简化版

适用场景：
  可容忍少量丢失（日志、通知）
  或有幂等兜底（即使丢，业务状态可恢复）
```

### 4.2 与补偿事务的结合

```text
消息驱动的最终一致性 + 补偿：
  正向链路：订单创建 → 发消息 → 扣库存 → 扣款
  反向补偿：任一步失败 → 消息驱动回滚

补偿设计（工程重点）：
  ① 每个操作有"补偿操作"（订单取消、库存回滚）
  ② 补偿也是消息驱动（保证最终执行）
  ③ 幂等（补偿可能重复执行）
  ④ 状态机（订单状态：创建→已扣款→已发货→完成/取消）

Saga 模式：消息队列是 Saga 编排的天然载体
```

## 5. 方案对比与选型

### 5.1 三方案总对比

| 维度 | 本地消息表 | 事务消息 | 普通消息+补偿 |
|------|:---:|:---:|:---:|
| 原子性 | 本地事务 | 两阶段+回查 | 无（靠幂等/补偿） |
| 实时性 | 分钟级 | 秒级 | 秒级 |
| 实现成本 | 中 | 低（用特性） | 低 |
| 可靠性 | 高 | 高 | 中 |
| 侵入性 | 高（表） | 低 | 低 |
| 适用 | 存量改造 | 新系统（RocketMQ） | 低要求场景 |

### 5.2 选型决策树

```text
需要"业务与消息原子"？
  是 + RocketMQ → 事务消息
  是 + 其他 MQ → 本地消息表（Outbox）
  否 + 可容忍丢失 → 普通消息 + 幂等
  否 + 需强一致 → 不要用 MQ（TCC/2PC/单库）

业务一致性要求：
  强一致（扣款）→ TCC/本地事务
  最终一致（通知/积分/状态同步）→ 消息方案
```

> ⚠️ 重要边界：**MQ 方案解决的是"最终一致"，不是"强一致"**——下单扣库存可以最终一致（先下单后扣减），但"余额必须即时准确"的账务场景要慎用消息队列。

## 6. 工程实践与补偿

### 6.1 完整工程清单

```text
① 消息与业务原子？（事务消息/本地消息表）
② 消费幂等？（唯一键/状态机——必配）
③ 重试策略？（分级退避 + 死信）
④ 补偿操作？（失败回滚的消息驱动）
⑤ 监控？（消息成功率、事务回查率、死信率）
⑥ 对账？（定时对账发现"消息丢失"）

对账是最终一致性的"最后防线"：
  每日对账任务：数据库状态 vs 消息消费结果
  → 发现不一致 → 补偿/重放
```

### 6.2 幂等与顺序的配合（综合 02/03）

```text
最终一致性的三件套：
  ① 事务/原子（业务与消息同生共死）
  ② 幂等（重复无害）
  ③ 顺序（状态机正确）——按业务键路由

三者缺一：
  无原子 → 消息可能丢（业务成功但无消息）
  无幂等 → 重复消费（扣两次款）
  无顺序 → 状态错乱（支付先于创建）
```

### 6.3 常见错误

| 错误 | 后果 |
|------|------|
| 事务消息回查逻辑与业务不一致 | 半消息永远挂起/误提交 |
| 补偿操作不幂等 | 补偿重复执行出双份 |
| 无对账机制 | 丢失静默（最终一致性变成"永远不一致"） |
| 消费失败无死信 | 消息丢失 |
| 回查超时无告警 | 事务卡死不可见 |

> 🎯 **核心要点**：用消息队列做分布式事务 = "本地原子 + 消息驱动 + 幂等补偿"的组合。事务消息（half message + 回查）是最优雅的实现（RocketMQ 5.x 成熟特性），本地消息表（Outbox）是最通用的兜底，普通消息+补偿适合低要求场景。**最终一致性的工程闭环：事务保证"必达"、幂等保证"不乱"、对账保证"可发现"**。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 分布式事务困境？ | 跨库/跨服务无法原子提交回滚 |
| 本地消息表？ | 业务与消息同事务 + 定时发送（通用） |
| 事务消息？ | Half 消息 + 本地事务 + 回查（RocketMQ 原生） |
| 回查机制？ | Broker 超时回查业务状态（最多 15 次） |
| 最终一致性三件套？ | 原子（必达）+ 幂等（不乱）+ 对账（可发现） |
| 强一致场景？ | 不要用 MQ（TCC/2PC/单库） |
