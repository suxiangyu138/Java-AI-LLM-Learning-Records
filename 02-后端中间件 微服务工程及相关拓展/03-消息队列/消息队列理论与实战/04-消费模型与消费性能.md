## 1. 拉模型 vs 推模型

### 1.1 两种模型

| 模型 | 机制 | 代表 | 特点 |
|------|------|------|------|
| 拉（Pull） | 消费者主动拉取 | **Kafka、RocketMQ** | 消费速率可控、可批量 |
| 推（Push） | Broker 主动推送 | RabbitMQ（AMQP）、ActiveMQ | 实时性好、速率不可控 |

```text
推模型的本质（RabbitMQ）：
  Broker 推送 → 消费者处理
  消费者处理不过来 → 消息积压在消费者侧（QoS 限制）

拉模型的本质（Kafka/RocketMQ）：
  消费者按需拉取（fetch）→ 处理 → 再拉
  消费速率完全由消费者掌控（天然削峰）

长轮询（Long Polling）：拉模型的"伪推送"
  拉取时若无消息，Broker 挂起请求直到新消息或超时
  → 兼顾实时性与速率控制（现代 MQ 标配）
```

### 1.2 模型选择的工程影响

| 维度 | 拉模型 | 推模型 |
|------|:---:|:---:|
| 消费速率控制 | ✅ 消费者决定 | ❌ 需 QoS 限制 |
| 批量消费 | ✅ 天然支持 | 需攒批 |
| 实时性 | 长轮询下接近推 | ✅ 原生 |
| 消费失败处理 | 可控（下轮重拉） | 依赖确认/重投 |
| 适用 | 大数据/高吞吐 | 低延迟/路由复杂 |

> 🎯 核心认知：**拉模型把"消费节奏"的控制权交给消费者**——这是 Kafka/RocketMQ 能支撑百万级吞吐的关键设计；RabbitMQ 的推送模型则更适合低延迟、小消息量的企业集成场景。

## 2. 消费组与分区分配

### 2.1 消费组模型

```text
消费组（Consumer Group）：
  组内：每个分区只被一个消费者处理（负载均衡）
  组间：每个组独立消费全部消息（广播语义）

核心约束（Kafka）：
  组内消费者数 ≤ 分区数
  → 消费者多于分区时，多余消费者闲置（无分区可消费）

RocketMQ 5.x 新特性（KIP-932 对应物）：
  Pop 消费模式：分区可被多消费者并发处理
  → 打破"消费者 ≤ 分区"的硬约束
```

### 2.2 分区分配策略

| 策略 | 机制 | 特点 |
|------|------|------|
| Range（范围） | 按分区序号分段 | 分配不均（多主题时） |
| RoundRobin（轮询） | 分区轮流分配 | 均匀 |
| Sticky（粘性） | 尽量保持原有分配 | 重平衡影响最小 |
| 协作式（Cooperative） | 增量重平衡 | **现代默认**（减少停顿） |

```text
重平衡（Rebalance）的代价：
  旧：stop-the-world 全量重平衡（所有消费者暂停，分钟级）
  新：KIP-848（Kafka 4.0）服务端协调重平衡
    → 增量式、秒级完成（详见 08 模块）

工程影响：重平衡期间消费暂停
  → 消费者数变动/分区变动会引发短暂消费中断
```

## 3. 消费并行度设计

### 3.1 并行度的决定因素

```text
消费并行度 = min(分区数, 消费者实例数 × 每实例线程数)

提升路径：
  ① 加分区（生产者侧规划，扩容代价大）
  ② 加消费者实例（水平扩展，受分区数上限约束）
  ③ 消费者内多线程（同分区内不可并行！）

关键约束：
  同分区同一时刻只有一个消费者线程处理（顺序保证的前提）
  → 单分区吞吐 = 单消费者线程吞吐
  → 总吞吐 = 分区数 × 单分区吞吐
```

### 3.2 消费者内多线程的三种模式

| 模式 | 做法 | 顺序 | 适用 |
|------|------|:---:|------|
| 单线程逐条 | 一条处理完再下一条 | ✅ | 顺序要求 |
| 单线程批量 | 拉一批逐条处理 | ✅ | 顺序 + 减少拉取开销 |
| 多线程分发 | 拉到后按业务键分发线程池 | 部分 | 无严格顺序 |

```java
// 多线程消费（无顺序要求的高吞吐模式）
// ① 拉取一批消息
List<Message> batch = consumer.poll(1000);
// ② 提交到业务线程池（并行处理）
for (Message msg : batch) {
    executor.submit(() -> process(msg));   // 并行处理
}
// ③ 全部完成后提交位点
// 注意：位点提交必须在处理完成后（否则崩溃丢消息）
```

### 3.3 消费吞吐的计算

```text
理论吞吐估算：
  单条处理耗时 t（含 IO）
  单消费者线程吞吐 = 1/t
  总吞吐 = 分区数 / t

例：单条处理 50ms → 单线程 20/s
  100 个分区 → 2000/s（瓶颈在业务处理速度）
  处理加速（批量化/并行化）比加分区更有效

批量消费的收益：
  拉取开销分摊（网络/解析）
  Kafka 批量处理可提升 5-10 倍吞吐（同分区内）
```

## 4. 消息积压：监控与治理

### 4.1 积压的本质

```text
积压 = 生产速率 > 消费速率（持续一段时间）

积压的来源：
  ① 瞬时洪峰（削峰填谷的设计预期）
  ② 消费者故障/变慢（需要治理）
  ③ 消费者数不足/分区不足（容量规划问题）

区分"良性积压"与"恶性积压"：
  良性：削峰场景，可恢复（消费追平）
  恶性：持续增长（消费能力不足/故障）
```

### 4.2 积压监控

| 指标 | 含义 | 告警阈值 |
|------|------|---------|
| 消费位点落后（Lag） | 生产位点 − 消费位点 | 持续增长即告警 |
| 积压消息数 | 队列中未消费数量 | 按业务容忍度 |
| 消费速率 | 每秒处理数 | 与生产速率对比 |
| 积压时间 | 最老消息等待时长 | 超过 SLA 告警 |

```text
Kafka：消费组 Lag 监控（kafka-consumer-groups 命令/工具）
RocketMQ：消息堆积量（控制台/API）
RabbitMQ：队列消息数（管理界面）

告警设计：Lag 持续上升（而非 Lag 大）才是问题信号
```

### 4.3 积压治理三板斧

| 手段 | 做法 | 适用 |
|------|------|------|
| 扩容消费者 | 增加消费者实例（需分区余量） | 分区充足 |
| 扩分区 | 增加分区（顺序场景慎用） | 分区不足 |
| 临时改逻辑 | 降级处理（丢弃非关键/简化处理） | 峰值应急 |
| 重放 | 失败消息重放（死信处理后） | 死信积压 |

```text
极端积压的处理（如 24h 积压）：
  ① 评估：哪些消息可丢弃（非关键）
  ② 扩容：临时消费集群（并行追平）
  ③ 分流：新消息走新 Topic（避免继续堆积）
  ④ 复盘：为什么积压（容量规划/故障根因）

经验法则：积压治理的三步 = 止血（停新）→ 清淤（追平）→ 防复发（监控）
```

## 5. 消费性能优化

### 5.1 消费端优化清单

| 优化 | 效果 | 注意 |
|------|------|------|
| 批量消费 | 吞吐 5-10× | 顺序保持（同分区内） |
| 业务并行化 | 吞吐 ×线程数 | 无顺序要求时 |
| 减少单条耗时 | 吞吐线性提升 | 优化 IO/序列化 |
| 预取/缓存 | 减少下游调用 | 数据一致性 |
| 异步化下游 | 主链路提速 | 可靠性转移 |

### 5.2 Broker 侧优化

```text
服务端瓶颈与调优：
  Kafka：页缓存命中率、磁盘顺序写、网络线程
  RocketMQ：CommitLog 顺序写、ConsumeQueue 索引
  RabbitMQ：内存/磁盘配额

通用调优方向：
  ① 消息大小（小消息吞吐更高）
  ② 压缩（gzip/zstd——吞吐与 CPU 的权衡）
  ③ 刷盘策略（可靠性与性能权衡）
  ④ 消费者拉取大小（fetch size/批量）
```

### 5.3 消费变慢的定位方法

```text
定位流程：
  ① 看监控：消费速率下降？Lag 上升？
  ② 看消费者：CPU/GC/线程阻塞？（JFR/jstack）
  ③ 看下游：数据库慢查询？下游服务变慢？
  ④ 看 Broker：分区热点？（个别分区 Lag 高 = 数据倾斜）

数据倾斜问题：
  某业务键消息量巨大 → 单分区积压 → 其他分区空闲
  解决：键拆细（子键）、二级分区、RocketMQ Pop 消费
```

## 6. 消费侧工程实践

### 6.1 消费代码标准模板

```java
// Kafka 手动提交（防丢 + 可控）的标准结构
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(1000);
    if (records.isEmpty()) continue;
    try {
        for (ConsumerRecord<String, String> r : records) {
            process(r);                       // ① 处理业务
        }
        consumer.commitSync();                // ② 成功后再提交
    } catch (Exception e) {
        // ③ 失败：记录/告警；不提交（下轮重拉）
        // ④ 超限：进重试 Topic / 死信（05 模块）
    }
}
```

### 6.2 消费组设计清单

```text
① 分区数：按峰值吞吐 × 处理耗时估算（提前规划）
② 消费者数：≤ 分区数（每实例单线程时）
③ 位点管理：手动提交（处理成功后）
④ 监控：Lag 持续上升告警
⑤ 幂等：重复消费兜底（02 模块）
⑥ 顺序：有顺序需求 → 业务键路由（03 模块）
⑦ 应急：积压预案（扩容/降级/分流）
```

> 🎯 **核心要点**：消费性能 = 分区数（容量）× 消费者并行度（扩展）× 单条处理速度（优化）的乘积——三者任一瓶颈都会造成积压。拉模型把节奏交给消费者，手动 ACK 把可靠性交给代码；积压治理的关键是"区分良性/恶性 + Lag 趋势告警 + 止血/清淤/防复发"三步。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 拉 vs 推？ | 拉可控可批量（Kafka/RocketMQ）；推实时（RabbitMQ） |
| 消费并行度？ | min(分区数, 消费者数)（Kafka；Pop 消费打破） |
| 重平衡代价？ | 旧式全量停顿；KIP-848 服务端协调秒级 |
| 积压怎么判断？ | Lag 持续上升（趋势信号，不是 Lag 大） |
| 治理三板斧？ | 止血（停新）→ 清淤（扩容追平）→ 防复发（监控） |
| 消费代码要点？ | 手动提交 + 处理成功后提交 + 幂等 |
