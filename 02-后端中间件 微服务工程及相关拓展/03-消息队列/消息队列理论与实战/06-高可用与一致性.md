## 1. 高可用的目标

### 1.1 可用性 vs 可靠性

| 概念 | 含义 | 冲突 |
|------|------|------|
| 可用性 | 系统持续对外服务（不宕机） | 一致性牺牲换可用 |
| 可靠性 | 数据不丢失（消息不丢） | 一致性要求换可靠 |
| 一致性 | 各副本数据一致 | — |

```text
CAP 的视角（消息中间件）：
  分区容忍（P）不可避免（节点会挂/网络会断）
  一致性（C）与可用性（A）二选一

MQ 的设计选择：
  绝大多数选 CP（一致性优先）——消息不能丢
  牺牲的是"少数派副本不可用时的可用性"
  （如 ISR 多数派写入：少数派故障不影响，多数派故障则不可写）

最终目标：节点故障时——不丢消息 + 服务不中断（尽量）
```

### 1.2 故障类型与应对

| 故障 | 应对 | 可用性影响 |
|------|------|-----------|
| 单节点宕机 | 副本切换（ISR 选新首领） | 秒级中断 |
| 网络分区 | 多数派原则（防脑裂） | 少数派不可用 |
| 磁盘故障 | 副本重建 | 无（副本兜底） |
| 机房故障 | 跨机房复制 | 依赖容灾设计 |

> 🎯 核心认知：**高可用的本质是"冗余 + 共识"**——冗余（副本）提供不丢的底牌，共识（选主/ISR）决定"哪个副本说了算"。冗余让数据活着，共识让系统不乱。

## 2. 副本机制

### 2.1 副本的基本模型

```text
每个分区/队列有多个副本：
  首领副本（Leader）：处理读写（唯一写入口）
  跟随副本（Follower）：同步复制、故障时接任

数据流向：生产者 → Leader → Follower（复制）
  读路径：只读 Leader（Kafka 传统模型）

副本数的权衡：
  3 副本：标准（容忍 1 节点故障）
  5 副本：高可靠（容忍 2 节点）
  2 副本：不推荐（单点故障窗口）
```

### 2.2 各中间件的副本实现

| 中间件 | 复制机制 | 可靠性基础 |
|--------|---------|-----------|
| Kafka | Leader/Follower + ISR | 分区级复制 |
| RocketMQ | 主从（同步/异步复制） | 主从切换（Dledger 可选） |
| RabbitMQ | Quorum 队列（Raft） | 队列级复制（4.0 唯一选项） |
| Pulsar | BookKeeper（Ensemble） | 条带化副本（WAL + 多副本） |

```text
同步复制 vs 异步复制：
  同步：Leader 等 Follower 确认后才 ACK 生产者
    → 不丢（Follower 确认即安全）
    → 延迟上升（等最慢副本）
  异步：Leader 落盘即 ACK
    → 吞吐高
    → 极端故障（Leader 挂 + 数据未复制）会丢

工程默认：核心业务同步复制（acks=all）
           日志类可异步（丢可接受）
```

## 3. ISR 与消息确认（acks）

### 3.1 ISR 的定义

```text
ISR（In-Sync Replicas，同步副本集合）：
  与 Leader 保持"足够同步"的副本集合

判定标准（Kafka）：
  落后 Leader 超过 replica.lag.time.max.ms（默认 30s）
  → 被踢出 ISR
  追平后重新加入

ISR 的作用：
  ① 写确认范围（acks=all → 写入全部 ISR）
  ② 选主范围（新 Leader 只能从 ISR 选）
  ③ 可靠性度量（ISR 大小 = 当前安全副本数）
```

### 3.2 acks 三档与可靠性

| acks | 含义 | 可靠性 | 场景 |
|:---:|------|:---:|------|
| 0 | 不等确认 | 最低 | 日志可丢 |
| 1 | Leader 落盘确认 | 中（Leader 挂丢） | 一般业务 |
| all | 全部 ISR 确认 | 最高 | 核心业务 |

```text
acks=all 的边界：
  ISR 只剩 Leader（其他副本全挂）→ acks=all 退化为单点
  → min.insync.replicas（最小同步副本数）兜底：
    写请求要求 ISR ≥ min.insync.replicas，否则拒绝（宁可不可用，不可丢）
  → 这是"CP 倾向"的显式配置：数据安全 > 写入可用
```

### 3.3 可靠性的完整链路（呼应 02 模块）

```text
消息"真正安全"的判定：
  生产者收到 ACK（acks=all 时 = ISR 全确认）
  → 之后 Leader 故障 → ISR 中选新 Leader（数据在）→ 不丢

可能丢的最后窗口：
  生产者 ACK 前 Leader 故障（未入 ISR 的数据）
  → 生产者重试（幂等生产者去重）

结论：acks=all + ISR 选主 + 生产重试 = 存储层不丢
  消费端再配幂等 = 端到端可靠
```

## 4. 选主与脑裂

### 4.1 为什么需要选主

```text
Leader 故障 → 需要从 ISR 中选出新 Leader：
  谁当 Leader？→ 必须"唯一"（否则脑裂）

选主要求：
  ① 新 Leader 必须包含已确认的数据（从 ISR 选）
  ② 全局唯一（同一时刻只有一个 Leader）
  ③ 快速（秒级完成，减少不可用窗口）
```

### 4.2 脑裂（Split Brain）

```text
脑裂：网络分区 → 两个节点都认为自己是 Leader
  → 两个写入口 → 数据分叉 → 不一致

经典场景：
  网络断开 → 旧 Leader 与多数派失去联系
  多数派选出新 Leader → 旧 Leader 恢复连接后还在写
  → 两份"真相"冲突

防脑裂的机制：
  ① 多数派（Quorum）原则：只有获得多数票才能当 Leader
  ② 纪元（Epoch）机制：新 Leader 纪元更高，旧 Leader 被否决
  ③ 隔离（Fencing）：旧 Leader 被标记失效（fencing token）
```

### 4.3 各中间件的防脑裂

| 中间件 | 机制 |
|--------|------|
| Kafka（KRaft） | Raft 共识（多数派 + 任期） |
| Kafka（旧 ZooKeeper） | ZK 的 ZAB + 临时节点（已随 4.0 移除） |
| RocketMQ 主从 | 手动/自动切换（Dledger 用 Raft） |
| RabbitMQ Quorum | Raft 共识 |
| Pulsar BookKeeper | Quorum 写入（E/A/W 配置） |

```text
结论：现代 MQ 的选主全部收敛到 Raft 家族
  （Kafka KRaft、RabbitMQ Quorum、Pulsar BK）
  → 脑裂问题从"工程技巧"变成"协议保证"
```

## 5. Raft 与 KRaft

### 5.1 Raft 共识要点

```text
Raft 的核心机制：
  ① 任期（Term）：每次选主递增
  ② 选主：多数派投票（随机超时避免选主竞争）
  ③ 日志复制：Leader 复制 → 多数派确认 → 提交
  ④ 脑裂防护：只有当前任期 Leader 可提交

Raft 与消息队列的适配：
  副本 = Raft 日志（顺序追加）
  消息确认 = 多数派提交
  选主 = Raft 选举
  → 消息系统的"不丢"与"唯一 Leader"由 Raft 一次性保证
```

### 5.2 KRaft：Kafka 的 Raft 化（4.0）

```text
KRaft（KIP-500 的落地，Kafka 4.0 唯一模式）：
  元数据（Topic/分区/配置）由 Raft 协议管理
  存储在内部主题 __cluster_metadata
  → 彻底移除 ZooKeeper（运维简化里程碑）

KRaft 的优势：
  ① 少一个组件（ZK 是 Kafka 运维的最大痛点）
  ② 控制器动态扩展（KIP-853，无需停机）
  ③ 元数据一致性与分区数据同一套协议
  ④ 更快的故障恢复（控制器选举秒级）

2025-2026 现实：Kafka 4.0（2025-03 发布）全面 KRaft
  → 存量 3.x 集群迁移是 2025-2026 的重要运维任务
```

### 5.3 控制器角色

```text
KRaft 中的控制器（Controller Quorum）：
  作用：管理元数据（分区分配、Leader 选举）
  构成：奇数节点（3/5 个控制器，多数派运行）

控制器故障 → 从其余节点选举（秒级）
  → 期间：分区管理暂停，数据读写不受影响

对比旧架构：
  ZooKeeper：外部集群（元数据 + 分布式协调）
  KRaft：内部集成（同进程/独立控制器节点）
```

## 6. 容灾与多活

### 6.1 容灾级别

| 级别 | 方案 | RPO（可丢数据） | RTO（恢复时间） |
|------|------|:---:|:---:|
| 单机房 | 副本冗余 | 0（多数派内） | 秒级 |
| 同城双活 | 跨机房同步复制 | 0-秒级 | 分钟级 |
| 异地容灾 | 跨地域异步复制 | 秒-分钟级 | 分钟-小时级 |

```text
RPO/RTO 权衡：
  同步复制（RPO=0）→ 跨地域延迟高（不可行跨洲）
  异步复制（RPO>0）→ 灾难时可能丢消息

工程实践（2025）：
  Kafka MirrorMaker 2（跨集群异步复制）
  云厂商 MQ 的跨地域同步（阿里云/腾讯云）
  多数业务：同城双活（RPO≈0）+ 异地异步备份
```

### 6.2 容灾演练

```text
高可用不是"配置出来的"，是"演练出来的"：
  ① 定期杀节点（混沌测试：随机杀 Broker）
  ② 验证选主时长与数据完整性
  ③ 验证消费者重连（重平衡）
  ④ 记录演练结果（RTO 实测）

2025-2026 趋势：混沌工程工具普及
  （Kafka 生态的故障注入、云厂商的容灾演练服务）
```

> 🎯 **核心要点**：高可用 = 副本冗余（不丢的底牌）+ Raft 共识（不乱的前提）+ 多数派（防脑裂）。Kafka 4.0 的 KRaft 标志着消息中间件全面 Raft 化——选主、防脑裂、元数据一致性由协议保证而非工程技巧。可靠性配置的最优组合：**acks=all + min.insync.replicas≥2 + ISR 选主 + 生产重试 + 消费幂等**。
