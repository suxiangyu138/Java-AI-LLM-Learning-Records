## 1. 顺序问题的本质

### 1.1 为什么业务需要顺序

```text
经典顺序场景：
  ① 订单状态流转：创建 → 支付 → 发货 → 完成
     乱序 → 支付在创建前？发货在支付前？业务错乱
  ② 账户流水：转账 A→B、B→A 的顺序决定余额结果
  ③ 库存变更：+10 与 -5 的顺序影响中间态

结论：有状态且状态依赖顺序的业务，必须保证有序消费
```

### 1.2 乱序的来源

| 来源 | 说明 |
|------|------|
| 多分区并行 | 消息分布到不同分区 → 消费并行 → 顺序丢失 |
| 多消费者并行 | 同一分区被多消费者处理（需避免） |
| 消费失败重试 | 失败消息延迟处理 → 后续消息先完成 |
| 异步处理线程 | 消费回调内的异步逻辑顺序不定 |

```text
核心矛盾：并行（吞吐）与顺序（正确性）互斥
  → 顺序保证必然牺牲并行度
  → 工程答案：把"顺序"限制在必要的粒度（分区级）
```

## 2. 全局顺序 vs 分区顺序

### 2.1 两种顺序

| 类型 | 含义 | 吞吐 | 可行性 |
|------|------|:---:|:---:|
| 全局顺序 | 整个 Topic 所有消息严格有序 | 1（单分区） | 理论可行，实践罕见 |
| 分区顺序 | 同一分区/队列内有序 | 分区数 | **工程主流** |

### 2.2 为什么不做全局顺序

```text
全局顺序 = 单一分区 = 单一消费者线程
  → 吞吐上限 = 单分区吞吐（通常 1-10 万/秒）
  → 无法水平扩展（违背 MQ 的初衷）

而且绝大多数业务不需要全局顺序：
  "所有消息"有序 是伪需求
  "同一实体的消息"有序 才是真需求（订单、用户、账户）

结论：把顺序粒度从"全部"降到"同一业务键" → 并行度回来了
```

### 2.3 分区顺序的正确理解

```text
分区顺序的保证边界：
  ✅ 同一分区内的消息按生产顺序存储
  ✅ 同一分区由单个消费者线程处理（正常情况）
  ❌ 不同分区之间无顺序（本就无需求）
  ❌ 消息键相同 → 同一分区（靠路由保证）

关键：分区顺序 ≠ 全局顺序
  但"同一业务实体的消息进同一分区" → 该实体的顺序有保证
```

## 3. 如何实现分区顺序

### 3.1 消息路由：业务键 → 分区

```text
核心机制：用业务键（订单 ID、用户 ID）做分区路由
  同一业务键的消息 → 永远进入同一分区

Kafka：key 哈希取模 → 分区
  producer.send(new ProducerRecord(topic, orderId, message))
  → orderId 相同 → 分区相同 → 顺序保证 ✓

RocketMQ：MessageQueueSelector 自定义选择
  → 按业务键哈希选择队列

RabbitMQ：无原生分区——单队列单消费者才能有序
  （或一致性哈希交换器）
```

```java
// Kafka 按业务键路由（顺序消息的标准姿势）
ProducerRecord<String, String> record =
    new ProducerRecord<>(ORDER_TOPIC, orderId, payload);
// key = orderId → 哈希路由 → 同一订单永远同一分区
producer.send(record);
```

### 3.2 分区数量与顺序的关系

```text
分区数固定后：
  业务键哈希 → 分区映射确定
  不同业务键可能映射同一分区（冲突，无碍——顺序按分区不按键）

注意：分区数扩容会导致键重分布！
  → 扩容时旧分区的顺序被打破（新键映射到新分区）
  → 顺序场景的分区数应提前规划，避免扩容

RocketMQ 5.x 对比：队列与消息的绑定可保持
  → 通过 MessageQueueSelector + 固定队列数
```

## 4. 顺序消费的实现

### 4.1 消费端的顺序要求

```text
即使消息按序入分区，消费端也要配合：
  ① 单线程处理（同一分区不并发）
  ② 失败重试不破坏顺序（先阻塞重试，不乱投）
  ③ 重平衡期间的顺序（暂停消费，完成后再继续）

各中间件的支持：
  Kafka：分区与消费者一一对应（一个分区同一时刻一个消费者）
    → 单消费者内顺序天然保证
  RocketMQ：MessageListenerOrderly（顺序消费接口）
    → 队列与线程一一绑定（加锁）
  RabbitMQ：单队列单消费者（否则无法保证）
```

### 4.2 顺序消费与失败重试的矛盾

```text
乱序的最大来源：消费失败重试

错误做法：失败消息跳过，先处理后续（顺序断裂）
正确做法：失败消息阻塞重试（处理成功才继续）

RocketMQ 的 MessageListenerOrderly 语义：
  失败 → 本地重试（默认最多 16 次）→ 仍失败 → 挂起队列
  （不能跳到死信，否则顺序破坏——需要人工介入）

Kafka 的实践：
  失败 → 暂停该分区消费（pause）→ 重试 → 成功恢复
  或：单线程串行处理 + 失败进重试 Topic（同键路由）
```

### 4.3 顺序消费的异常场景

| 场景 | 处理 |
|------|------|
| 消费者宕机 | 重平衡 → 新消费者从头/断点消费（分区继续） |
| 消费失败 | 阻塞重试（不跳过） |
| 重平衡中 | 暂停消费 → 完成分配 → 继续（RocketMQ 加锁） |
| 消息积压 | 顺序消费吞吐受限 → 增大分区数（需提前规划） |

> ⚠️ 顺序消费的"暂停-重试"可能阻塞整个分区——**一个坏消息拖住后续全部消息**。设计上要区分"可跳过"与"不可跳过"的业务，仅对不可跳过的用严格顺序。

## 5. 顺序的代价与权衡

### 5.1 顺序消费的成本

| 代价 | 说明 |
|------|------|
| 吞吐下降 | 单分区单线程（并行度 = 分区数） |
| 分区数规划 | 提前定死（扩容打破顺序） |
| 失败阻塞 | 坏消息拖住分区 |
| 复杂度 | 路由键设计 + 顺序消费配置 |

### 5.2 顺序 vs 吞吐的平衡

```text
优化手段（在不破坏顺序的前提下提升吞吐）：
  ① 提高分区数：更多业务键并行（键级并行）
  ② 消费端批量处理：同一分区内批量（顺序仍保）
  ③ 异步化非关键路径：只保关键状态有序
  ④ 状态机校验：即使乱序，状态校验兜底（幂等思想）

工程判断：
  严格顺序需求（订单支付）→ 分区顺序 + 阻塞重试
  弱顺序需求（日志）→ 普通消费（乱序可接受）
  可校验顺序（幂等/状态机）→ 普通消费 + 校验兜底
```

## 6. 顺序场景工程实践

### 6.1 典型顺序场景方案

| 场景 | 方案 | 说明 |
|------|------|------|
| 订单状态机 | 订单 ID 路由 + 顺序消费 | 状态流转严格有序 |
| 用户操作流水 | 用户 ID 路由 | 同用户串行 |
| 账户余额 | 账户 ID 路由 + 幂等 | 顺序 + 幂等双保险 |
| 数据库 binlog 同步 | 主键路由 | 行级顺序 |

### 6.2 顺序 + 幂等的组合

```text
顺序保证 + 幂等消费的组合逻辑：
  顺序：保证"正常路径"按序（业务状态机正确）
  幂等：兜底"重试/重复"（可靠性兜底）

两者互补：
  顺序解决"乱序的正确性"
  幂等解决"重复的正确性"
  缺一不可（只顺序不幂等 → 重投乱序；只幂等不顺序 → 状态机错乱）
```

### 6.3 设计检查清单

```text
① 业务键是什么？（订单 ID/用户 ID——维度要准）
② 顺序粒度？（同键有序即可，勿贪全局）
③ 分区数规划？（考虑峰值与未来，提前定）
④ 失败策略？（阻塞重试 vs 跳过——顺序敏感性）
⑤ 幂等是否配套？（重投兜底）
⑥ 扩容预案？（顺序场景分区数扩容 = 破坏顺序）
```

> 🎯 **核心要点**：顺序消息的正确姿势 = **业务键路由到分区（生产端）+ 单线程顺序消费（消费端）+ 阻塞重试（失败不跳）+ 幂等兜底（重复无害）**。全局顺序是伪需求，分区顺序是工程答案；顺序的代价（吞吐/阻塞）要用"键级并行 + 状态机校验"来对冲。

## 7. 小结

| 问题 | 答案 |
|------|------|
| 乱序来源？ | 多分区并行、多消费者、失败重试 |
| 全局 vs 分区顺序？ | 全局单分区不可扩展；分区顺序是主流 |
| 怎么保证同键同分区？ | 业务键作为消息 key 哈希路由 |
| 消费端怎么做？ | 单线程 + 阻塞重试（MessageListenerOrderly） |
| 顺序的代价？ | 吞吐受限、分区不可随意扩容、坏消息阻塞 |
| 与幂等的关系？ | 顺序管"乱序"、幂等管"重复"，互补 |
