## 1. 正排 vs 倒排

### 1.1 MySQL 正排索引（B+Tree）

传统关系型数据库使用正排索引：文档 ID 映射到文档内容。

```text
文档 ID → 内容
  doc1 → "计算机专业学生"
  doc2 → "计算机科学与技术"
  doc3 → "软件工程专业"

查询"计算机"：
  → 全表扫描 / LIKE "%计算机%"
  → 逐行比对，时间复杂度 O(n)
  → 无法利用 B+Tree 索引加速
```

B+Tree 索引适合等值查询和范围查询（`WHERE id = 1`、`WHERE age > 18`），但对全文搜索无能为力。其叶子节点按主键排序存储，无法对文本内容建立有效索引。

### 1.2 ES 倒排索引

倒排索引将数据模型彻底反转：词项（Term）映射到包含该词项的文档 ID 列表。

```text
词项(Term) → 文档 ID 列表
  "计算机"   → [doc1, doc2]
  "专业"     → [doc1, doc3]
  "学生"     → [doc1]
  "科学"     → [doc2]
  "技术"     → [doc2]
  "软件"     → [doc3]
  "工程"     → [doc3]

查询"计算机"：
  → 查 Term Dictionary
  → 直接命中，O(1) 找到文档列表
  → 无需扫描任何文档
```

### 1.3 对比总结

| 维度 | MySQL B+Tree | ES 倒排索引 |
|------|-------------|-------------|
| 数据结构 | 平衡多路搜索树 | FST + Skip List + Posting List |
| 模糊搜索 | `LIKE %keyword%` 全表扫描 | Term 直接命中，O(1) |
| 最左前缀 | 强依赖索引顺序 | 不依赖，独立匹配 |
| 排序 | 叶子链表天然有序 | 需 Doc Values |
| 更新 | 原地更新 | 标记删除 + 新增 |
| 适用场景 | 事务、精确查询 | 全文搜索、分词、海量文本 |
| 压缩率 | 低（整行存储） | 高（Delta + Bitmap 编码）|

### 1.4 为什么倒排索引更适合搜索

搜索本质：从大量文档中找到包含某个词的文档。正排思路遍历所有文档（`O(n)`），倒排思路直接查词（`O(1)`）。数据量越大差距越悬殊——1万文档正排10ms倒排1ms，1亿文档正排不可接受倒排仅5ms。

## 2. 倒排索引三大核心结构

```text
┌──────────────────────────────────────┐
│          Term Dictionary             │ ← 内存常驻（FST 压缩）
│  "计算" ───→ 指向 Posting List 的指针 │
│  "计算机" ─→ offset                  │
└──────────────┬───────────────────────┘
               │
               ▼
┌──────────────────────────────────────┐
│           Posting List               │ ← 磁盘存储（FOR/Roaring Bitmap）
│  "计算机": [doc1, doc2, doc4, doc8]   │
└──────────────┬───────────────────────┘
               │
               ▼
┌──────────────────────────────────────┐
│     Payload（位置/偏移/词频）          │ ← 用于高亮、短语匹配
│  "计算机" in doc1: pos: [0], TF: 1   │
└──────────────────────────────────────┘
```

### 2.1 Term Dictionary（词项词典）

存储所有不重复的词项，使用 **FST（Finite State Transducer）** 压缩存储。**这是 ES 快的核心原因之一。**

| FST 特性 | 说明 |
|---------|------|
| 共享前缀 | "计算机"和"计算"共享前缀"计算" |
| 内存占用小 | 比 HashMap 节省 90%+ 空间 |
| 查询速度快 | O(len(term))，与词典大小无关 |
| 有序性 | 输出有序，方便合并和范围查询 |

```text
FST 示例："cat"→12, "deep"→10, "do"→15, "dog"→8

            c         d
            |        / \
           a       e   o
           |       |   | \
           t:12   ep  g   p:15
                 (:10) | \
                       og:8
```

### 2.2 Posting List（倒排列表）

每个 Term 对应的文档 ID 列表，使用高效压缩算法存储。

```text
原始： "计算机" → [1, 3, 5, 7, 9, 11, 13, 15]
Delta 编码后： [1, 2, 2, 2, 2, 2, 2, 2]
原始 8 个 int = 32 字节，压缩后 8 个 byte = 8 字节（75% 压缩率）
```

### 2.3 Skip List（跳表）

加速多词查询的合并操作。例如 "计算机 AND 专业"：

```text
"计算机": [1, 3, 5, 7, 9, 11, 13]
"专业":   [1, 4, 7, 10, 13]
交集: [1, 7, 13] ← Skip List 跳跃合并，O(log n)
```

## 3. 压缩算法详解

### 3.1 FOR（Frame Of Reference）

对有序递增的文档 ID 进行差值编码：

```text
原始 ID:     [73, 300, 302, 332, 343, 372]
差值(Delta): [73, 227, 2, 30, 11, 29]
最大值 227 → 只需 8 bit 存储
每个 ID 用 8 bit 而非 32 bit → 75% 压缩率
```

### 3.2 Roaring Bitmap

当 Posting List 非常长时（如词"的"出现在 100 万文档中），用 Bitmap 压缩：

```text
FOR 方案：100 万 × 4 bytes = 4MB
Bitmap 方案：每个 bit 代表一个文档 → 125KB

ES 自动选择：文档少 → FOR；文档多 → Roaring Bitmap
```

### 3.3 压缩效果对比

| 算法 | 原理 | 适用场景 | 压缩比 |
|------|------|---------|:------:|
| FOR | Delta 编码 + 按帧打包 | 有序小数值 | 3:1 ~ 10:1 |
| Roaring Bitmap | Bit 位标记 | 大量文档的词 | 10:1 ~ 100:1 |
| FST | 前缀共享 + 有限状态机 | Term Dictionary | 5:1 ~ 20:1 |

## 4. 段 Segment 机制

### 4.1 什么是 Segment

ES 中的一个 Shard 由多个 **Segment** 组成，每个 Segment 是一个完整的倒排索引（类似 LSM Tree 的 SSTable）。

```text
Index: goods (1 Primary Shard)
  ┌─────────────────────────────────────┐
  │  Segment 1 (500 docs, 3MB)          │
  │  Segment 2 (300 docs, 2MB)          │
  │  Segment 3 (200 docs, 1MB)          │
  │  Segment 4 (1000 docs, 6MB)         │
  └─────────────────────────────────────┘
```

**Segment 核心特性：**
- **不可变性**：一旦写入，永不修改
- **独立性**：每个 Segment 有自己的 Term Dictionary + Posting List
- **查询范围**：查询需遍历所有 Segment 后合并结果

### 4.2 写入、删除与更新

```text
写入新文档 → Memory Buffer → Refresh(1s) → 新 Segment（可搜索）

删除文档 → 不在原 Segment 删除，而是追加 .del 标记文件
           查询时过滤掉标记删除的文档

更新文档 → 标记旧文档删除 + 写入新文档
```

### 4.3 Segment 合并（Merge）

```text
合并前：Seg1(100条) + Seg2(100条) + Seg3(100条) = 3 个 Segment
合并后：Seg4(297条) = 300 - 3(已删除) = 297 条 = 1 个 Segment

合并带来的好处：
  - 查询需扫描的 Segment 数减少
  - 被标记删除的文档空间真正释放
```

| 合并策略 | 说明 |
|---------|------|
| Tiered（默认）| 按大小分层合并，大 Segment 不参与 |
| `index.merge.policy.max_merged_segment` | 最大合并段大小（默认 5GB）|

> 💡 合并耗 I/O，建议在业务低峰期执行 `POST /my_index/_forcemerge?max_num_segments=1`。

### 4.4 为什么 Segment 不可变？

| 优点 | 说明 |
|------|------|
| 无锁读 | 不涉及并发写，无需锁和同步 |
| 高吞吐 | 写入新 Segment 即可，不需修改旧数据 |
| 缓存友好 | 数据不变，OS Page Cache 命中率高 |
| 崩溃安全 | 旧数据不变，恢复只需重做 Translog |

### 4.5 Refresh 与 Flush

```text
写流程：
Write → Translog(持久化,防丢失) → Memory Buffer → Refresh(1s) → Segment(可搜索)
                                                                       ↓
                                                               Flush(30min/512MB) → 磁盘
```

| 操作 | 触发条件 | 效果 |
|------|---------|------|
| Refresh | 默认 1s | Memory Buffer → Segment（数据变为可搜索）|
| Flush | 默认 30min / 512MB translog | Segment 刷磁盘，清空 translog |

## 5. 列式存储 Doc Values

### 5.1 为什么需要 Doc Values

倒排索引擅长搜索但不擅长排序和聚合。

```json
// 需求：查找包含"计算机"的文档，按 age 排序
{ "query": { "match": { "desc": "计算机" } }, "sort": [{ "age": "asc" }] }

// 倒排索引：Term → DocIDs（查"计算机" → [doc1, doc2]）
// 但倒排索引没有存储 age 字段的值！
// 需要另一种结构：DocID → Field Values
```

### 5.2 Doc Values 原理

```text
倒排索引（搜索用）：Term → [DocID]
  "计算机" → [1, 2, 5, 8]

Doc Values（排序/聚合用）：DocID → Field Value（列式存储）
  doc1 → age: 25, price: 100
  doc2 → age: 30, price: 200
```

| 特点 | 说明 |
|------|------|
| 列式存储 | 同一字段的所有值连续存储，而非按行 |
| 磁盘存储 | 使用 OS Page Cache 加速 |
| 构建时机 | 索引文档时同步构建，Segment 不可变则 DV 也不可变 |

### 5.3 三种数据结构对比

| 结构 | 方向 | 用途 | 存储位置 | 默认启用 |
|------|------|------|---------|:-------:|
| 倒排索引 | Term → [DocID] | 全文搜索 | 磁盘 | 是（text）|
| Doc Values | DocID → Value | 排序、聚合、过滤 | 磁盘（列式）| 是（keyword/数值）|
| fielddata | DocID → Value | text 字段排序/聚合 | 内存 | 否（谨慎）|

> ⚠️ 对 text 字段排序/聚合，优先使用 Multi-field 的 keyword 子字段，而非 fielddata。fielddata 加载到内存容易 OOM。

## 6. 分词器原理

### 6.1 分词器是什么

将文本拆分为独立词条（Term），是倒排索引的入口。

```text
输入: "计算机专业学生" → ["计算机", "专业", "学生"] ← 写入倒排索引
查询: "计算机"         → ["计算机"]                ← 与索引使用相同分词器
```

**关键规则：文档分词和查询分词必须使用相同的分词器，否则查不到。**

### 6.2 三大组件

```text
┌──────────────────────────────────────────────┐
│                  Analyzer                     │
│  ┌──────────────┐   ┌──────────┐   ┌────────┐│
│  │Character     │ → │Tokenizer │ → │ Token  ││
│  │Filter(s)     │   │          │   │Filter(s)││
│  └──────────────┘   └──────────┘   └────────┘│
│  0~n 个           1 个           0~n 个      │
└──────────────────────────────────────────────┘
```

| 组件 | 作用 | 示例 |
|------|------|------|
| Character Filter | 原始文本预处理 | 去除 HTML 标签、替换特殊字符 |
| Tokenizer | 切分为词条 | 按空格/标点/字典切分 |
| Token Filter | 词条再加工 | 转小写、去停用词、同义词替换 |

### 6.3 内置分词器

| 分词器 | 能力 | 适用场景 |
|--------|------|---------|
| `standard` | Unicode 标准分词 + 小写 | 英文通用（默认）|
| `simple` | 非字母字符分割 + 小写 | 简单英文文本 |
| `whitespace` | 按空格分割 | 精确控制分词结果 |
| `stop` | standard + 去停用词 | 去除 a/the/is |
| `keyword` | 不分词，原样输出 | ID、邮箱、精确匹配字段 |
| `pattern` | 正则分割 | 自定义分割规则 |

## 7. IK 中文分词器

### 7.1 为什么需要 IK

```text
standard: "计算机专业" → ["计", "算", "机", "专", "业"] ← 不可用！
IK:       "计算机专业" → ["计算机", "专业"]              ← 分词正确
```

### 7.2 安装

```bash
docker exec -it es bash
./bin/elasticsearch-plugin install \
  https://github.com/medcl/elasticsearch-analysis-ik/releases/download/v7.17.0/elasticsearch-analysis-ik-7.17.0.zip
docker restart es
```

### 7.3 ik_smart vs ik_max_word

| 模式 | 策略 | 示例："中华人民共和国国歌" |
|------|------|-------------------------|
| `ik_smart` | 粗粒度（最少切分，精准） | ["中华人民共和国", "国歌"] |
| `ik_max_word` | 细粒度（最多切分，召回高）| ["中华人民共和国", "中华", "华人", "人民", "共和国", "国歌"] |

测试分词效果：

```json
POST /_analyze
{ "analyzer": "ik_smart", "text": "计算机专业学生学习Java" }
// ["计算机", "专业", "学生", "学习", "Java"]
```

**最佳实践：索引用 `ik_max_word`（高召回），搜索用 `ik_smart`（高精准）。**

```json
PUT /my_index
{
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "ik_max_word",      // 索引用最大分词
        "search_analyzer": "ik_smart"   // 搜索用智能分词
      }
    }
  }
}
```

### 7.4 自定义词典

```bash
cd {ES_HOME}/config/analysis-ik/
mkdir custom
vi custom/mydict.dic
```

```text
# mydict.dic
张三丰
高并发
微服务
计算机专业
```

```xml
<!-- IKAnalyzer.cfg.xml -->
<properties>
    <entry key="ext_dict">custom/mydict.dic</entry>
    <!-- 远程词典支持热更新，IK 每分钟检查变化，无需重启 ES -->
    <entry key="remote_ext_dict">http://your-server/config/ik_dict.dic</entry>
</properties>
```

### 7.5 字段类型分词建议

| 字段 | 分词器 | 原因 |
|------|--------|------|
| 商品标题 | `ik_max_word` | 最大限度匹配搜索词 |
| 分类/标签 | `keyword` | 精确匹配 |
| 文章正文 | `ik_max_word` | 全文检索 |
| 品牌名 | `keyword` | 精确匹配 |
| ID/邮箱 | `keyword` | 不分词，精确查询 |

### 7.6 同义词配置

```json
PUT /goods
{
  "settings": {
    "analysis": {
      "filter": {
        "my_synonym": {
          "type": "synonym",
          "synonyms": [
            "计算机, 电脑, 电子计算机",
            "手机, 移动电话"
          ]
        }
      },
      "analyzer": {
        "ik_synonym": {
          "tokenizer": "ik_max_word",
          "filter": ["lowercase", "my_synonym"]
        }
      }
    }
  }
}
```

## 8. 拼音与自定义分词器

### 8.1 安装拼音分词器

```bash
docker exec -it es bash
./bin/elasticsearch-plugin install \
  https://github.com/medcl/elasticsearch-analysis-pinyin/releases/download/v7.17.0/elasticsearch-analysis-pinyin-7.17.0.zip
docker restart es
```

### 8.2 拼音分词测试

```json
POST /_analyze
{ "analyzer": "pinyin", "text": "你好世界" }
// ["ni", "hao", "shi", "jie", "nhsj"]
```

### 8.3 中文 + 拼音混合配置

```json
PUT /user_index
{
  "settings": {
    "analysis": {
      "analyzer": {
        "ik_pinyin_analyzer": {
          "tokenizer": "ik_max_word",
          "filter": ["my_pinyin", "lowercase"]
        }
      },
      "filter": {
        "my_pinyin": {
          "type": "pinyin",
          "keep_full_pinyin": true,
          "keep_original": true,
          "remove_duplicated_term": true
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "name": {
        "type": "text",
        "analyzer": "ik_pinyin_analyzer",
        "search_analyzer": "ik_smart"
      }
    }
  }
}
```

### 8.4 自定义分词器完整实战

```json
PUT /ecommerce
{
  "settings": {
    "analysis": {
      "char_filter": {
        "my_html": { "type": "html_strip" }
      },
      "filter": {
        "my_synonym": {
          "type": "synonym",
          "synonyms": ["计算机, 电脑", "手机, 移动电话"]
        }
      },
      "analyzer": {
        "my_custom_analyzer": {
          "type": "custom",
          "char_filter": ["my_html"],
          "tokenizer": "ik_max_word",
          "filter": ["lowercase", "my_synonym"]
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "title": {
        "type": "text",
        "analyzer": "my_custom_analyzer",
        "search_analyzer": "ik_smart"
      },
      "price": { "type": "double" },
      "category": { "type": "keyword" }
    }
  }
}
```

## 9. 面试核心要点

| 问题 | 答案 |
|------|------|
| **倒排索引是什么？** | Term → [DocID] 的映射，FST（Term Dictionary）+ Posting List 实现 |
| **FST 和 HashMap 的区别？** | FST 共享前缀节省空间、天然有序；HashMap 空间大且无序 |
| **ES 为什么不能替代 MySQL？** | 不支持事务、不支持 JOIN、写入非立即可见 |
| **Segment 为什么不可变？** | 不可变 = 无锁读 = 高并发 = OS Cache 友好 |
| **删除文档空间何时释放？** | Segment 合并时 |
| **standard vs IK 区别？** | standard 按单字拆分，IK 按中文词汇拆分 |
| **ik_smart vs ik_max_word？** | smart 最少切分（精准），max_word 最多切分（召回高）|
| **Doc Values vs fielddata？** | DV 磁盘列式（推荐），fielddata 内存（谨慎）|
| **Analyzer 三大组件？** | Character Filter → Tokenizer → Token Filter |
| **同义词在哪配置？** | Token Filter 中的 synonym filter |

> 🎯 **极简总结**：倒排 = 把"文档→词"反过来存成"词→文档"。查词直接命中，不用扫全表。分词决定了哪些词被索引，不同的分词结果直接影响搜索体验。
