# 02 - 分布式 ID 生成方案深度剖析

## 1. 分布式 ID 的需求与评价维度

> **背景**：单机自增 ID（AUTO_INCREMENT）在分库分表/多服务下会冲突——需要全局唯一的发号方案。
> **目的**：建立「按场景选 ID 方案」的评价框架。
> **适用范围**：所有分布式业务（订单号/用户ID/消息ID/日志ID）。

```text
分布式 ID 的五大需求
├── ① 全局唯一：跨节点不重复（底线）
├── ② 趋势递增：索引友好（B+Tree 顺序写）
├── ③ 高性能：高并发下发（10w+/s）
├── ④ 高可用：发号服务挂了不阻塞业务
└── ⑤ 安全：不可预测（防爬/防猜测订单号）

评价维度（选型看这些）
├── 有序性：趋势递增 vs 完全随机
├── 依赖：纯本地 vs 依赖 DB/Redis/ZK
├── 吞吐：单机 vs 集群可扩展
├── 时延：本地生成（ns）vs 网络获取（ms）
└── 长度/格式：64bit long vs 32bit vs 字符串
```

## 2. 方案全景对比

| 方案 | 原理 | 有序 | 依赖 | 吞吐 | 缺点 |
|------|------|:---:|------|:---:|------|
| DB 自增 | 单库 AUTO_INCREMENT | ✅ | DB | 低（单点） | 单点瓶颈/性能差 |
| DB 多级自增 | 多库步长错位（1、3、5…） | ✅ | 多库 | 中 | 扩容要重配步长 |
| Redis INCR | 原子自增 | ✅ | Redis | 高 | 依赖 Redis 可用性 |
| **雪花算法** | 时间戳+机器+序列 | ✅ 趋势 | **纯本地** | **极高** | 时钟回拨风险 |
| **号段模式** | DB 批量发号+内存发放 | ✅ | DB（低频） | 高 | 号段耗尽要等 |
| UUID v4 | 随机 128bit | ❌ 无序 | 无 | 极高 | 无序伤索引/长 |
| UUID v7 | 时间有序 128bit | ✅ 趋势 | 无 | 极高 | 兼容性（DB 需支持） |
| 混合 | 随机+时间截断 | 部分 | 无 | 高 | 实现复杂度 |

> 🎯 **一句话结论（2026 工程共识）**：**高并发场景 → 雪花/号段**；**无状态场景 → UUIDv7**；**低并发简单场景 → DB 自增也够**。

## 3. 雪花算法：源码级拆解

> 🎯 **雪花算法（Twitter Snowflake，2010）**——64 位 long 分三段：**时间戳(41) + 机器ID(10) + 序列号(12)**，趋势递增 + 本地生成 + 高吞吐：

```text
64 位布局（1 + 41 + 10 + 12）
┌────┬─────────────────────────┬──────────────┬──────────────┐
│ 0  │  41 位毫秒时间戳         │  10 位机器ID  │  12 位序列号  │
│ 符号│ (69 年有效期)            │ (1024 台机器) │ (4096/毫秒)   │
└────┴─────────────────────────┴──────────────┴──────────────┘
├── 时间戳：当前毫秒 - 自定义纪元（如 2020-01-01，延长可用年限）
├── 机器 ID：10 bit = 1024 台（5bit 机房 + 5bit 机器 或 独立 workerId）
└── 序列号：同一毫秒内自增，溢出则等下一毫秒

核心公式：id = (timestamp - epoch) << 22 | workerId << 12 | sequence
```

```java
// 雪花算法核心实现（手写精简版，面试能默写）
public class SnowflakeIdGenerator {
    // 纪元起点（自定义，延长可用年限）
    private final long epoch = 1577808000000L;      // 2020-01-01
    // 位分配
    private final long workerIdBits = 10L;           // 机器 ID 位
    private final long sequenceBits = 12L;           // 序列号位
    private final long maxWorkerId = ~(-1L << workerIdBits);  // 1023
    private final long sequenceMask = ~(-1L << sequenceBits); // 4095

    private long workerId;                           // 机器 ID
    private long sequence = 0L;                      // 序列号
    private long lastTimestamp = -1L;                // 上次生成时间

    public SnowflakeIdGenerator(long workerId) {
        if (workerId < 0 || workerId > maxWorkerId) {
            throw new IllegalArgumentException("workerId 超范围");
        }
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();
        // 时钟回拨：直接抛异常（最严格）
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨，拒绝生成");
        }
        // 同一毫秒：序列号 +1，溢出等下一毫秒
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & sequenceMask;
            if (sequence == 0) {                     // 4096 用完
                timestamp = tilNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;                           // 新毫秒重置
        }
        lastTimestamp = timestamp;
        // 组装 64 位
        return ((timestamp - epoch) << 22)        // 时间戳部分
             | (workerId << 12)                    // 机器部分
             | sequence;                           // 序列号部分
    }

    private long tilNextMillis(long last) {
        long ts = System.currentTimeMillis();
        while (ts <= last) { ts = System.currentTimeMillis(); }
        return ts;
    }
}
```

**三个关键设计点（面试考点）**：

```text
① 为什么 41 位时间戳够用？
   → 2^41 ms ≈ 69.7 年；从纪元起算，自定义纪元可「后移」有效期
② 序列号为什么要 & sequenceMask？
   → 位与实现模 4096 循环（溢出回绕，配合等下一毫秒）
③ 为什么 synchronized？
   → 序列号自增必须单线程内原子（多线程并发会重复）
```

## 4. 时钟回拨与容错

> 🎯 **雪花算法的阿克琉斯之踵**——时间回拨（NTP 校时/人工改时间）会让「新 ID 小于旧 ID」甚至重复。容错策略四级：

```text
回拨处理四级策略（按严格度排序）
├── L0 直接抛异常：最严格（上面代码）
│   ├── 适用：强一致场景
│   └── 问题：回拨期间服务不可用
├── L1 等待追平：回拨量小（<5ms）时 sleep 等到追平
│   ├── 实现：算出回拨毫秒数，Thread.sleep 补回来
│   └── 适用：回拨罕见且量小的场景
├── L2 备用序列号：回拨期间用「备用时钟」生成
│   ├── 如美团 Leaf 的「回拨拨正 + 序列号补偿」
│   └── 复杂度高，少用
└── L3 时钟信号源（NTP 守护）：主动监控时钟漂移
    ├── 超过阈值 → 告警 + 服务降级
    └── 最佳实践：运维层防回拨（chrony 配置 maxslew）

工程补充
├── 进程启动时校验时钟（启动时钟晚于运行中 → 拒绝启动）
├── 多进程分配 workerId：ZK 自动注册/分布式锁分配
└── 金句：回拨不可怕，可怕的是「没预案」
```

## 5. 号段模式（Leaf-segment）

> 🎯 **号段模式 = DB 批量发号 + 服务内存发放**——「一次取一段，内存慢慢用」，把 DB 压力降到极低：

```text
工作原理
├── DB 表：leaf_alloc(id, biz_tag, max_id, step)
│   ├── biz_tag：业务标识（订单/用户/消息各自独立号段）
│   ├── max_id：已分配的最大值
│   └── step：号段步长（如 1000）
├── 流程：
│   ① 服务启动/号段用完 → UPDATE max_id = max_id + step RETURNING
│   ② 拿到 [max_id-step+1, max_id] 号段 → 内存原子自增发放
│   ③ 号段剩余 < 阈值（如 20%）→ 异步预取下一段（双缓冲）
└── DB 压力：一次 UPDATE 换 1000 个 ID（QPS 只需业务量/1000）

双缓冲优化（Leaf 官方实现）
├── 两个号段：一个在用、一个在备
├── 当前段用到 10% → 立即异步加载下一段
└── 效果：DB 故障也不中断发号（备用段顶上）

优缺点
├── ✅ 有序递增、无时钟依赖、DB 压力小
├── ❌ 依赖 DB（DB 挂了号段用完即停）；号段丢失浪费
└── 适用：订单号/流水号（强有序要求）
```

```sql
-- 号段表结构（Leaf-segment 标准）
CREATE TABLE leaf_alloc (
  biz_tag   VARCHAR(128) NOT NULL COMMENT '业务标识',
  max_id    BIGINT NOT NULL COMMENT '当前最大ID',
  step      INT NOT NULL COMMENT '步长',
  version   INT NOT NULL COMMENT '乐观锁版本',
  PRIMARY KEY (biz_tag)
);
-- 取号段（原子 UPDATE + 乐观锁）
UPDATE leaf_alloc SET max_id = max_id + ?, version = version + 1
WHERE biz_tag = ? AND version = ?;
```

## 6. 大厂方案：美团 Leaf 与百度 UidGenerator

| 方案 | 类型 | 核心设计 | 开源 |
|------|------|---------|:---:|
| 美团 Leaf-segment | 号段 | 双缓冲 + 多业务 tag | ✅ leaf |
| 美团 Leaf-snowflake | 雪花 | ZK 分配 workerId + 回拨兜底 | ✅ |
| 百度 UidGenerator | 雪花变体 | **序列号用 RingBuffer（无锁）** | ✅ |
| 滴滴 Tinyid | 号段 | 双号段 + 异步预取 | ✅ |
| 腾讯 Seqsvr | 自研 | 内存段 + 持久化 WAL | ❌ 未开源 |

```text
美团 Leaf-snowflake（雪花 + ZK 的结合）
├── workerId 由 ZK 自动分配（持久顺序节点）——免手工配置
├── 回拨处理：小回拨 sleep、大回拨启动校验拒绝
└── 落地方案：解决「1024 台机器上限 + 手工配置」痛点

百度 UidGenerator（雪花 + RingBuffer）
├── 经典雪花三段式，但序列号改用 RingBuffer
│   ├── 预生成 2^13 个 ID 缓存进环形队列
│   └── 生成时从 RingBuffer 取（CAS 无锁）→ 吞吐更高
├── workerId 支持 DB 自动分配
└── 适用：极致吞吐场景（RingBuffer 预生成抵消并发争用）
```

> 💡 **工程启示**：大厂方案不是新算法，而是「雪花 + 基础设施（ZK/DB）」的组合——**workerId 自动分配**和**回拨容错**是两个真正的工程化增量。

## 7. 2026 新趋势：UUIDv7 与国产方案

> 🎯 **UUIDv7（RFC 9562，2024 发布）正在成为「无状态 + 有序」的新宠**——不需要任何基础设施就能生成趋势递增 ID：

```text
UUIDv7 的结构（128 bit）
┌─────────────────────┬───────────┬──────────────┬─────────────┐
│ 48 位毫秒时间戳      │ 4 位版本  │ 12 位随机     │ 62 位随机    │
│ （可排序，趋势递增） │ (0111)    │ 变体          │ 熵源         │
└─────────────────────┴───────────┴──────────────┴─────────────┘
├── 时间前缀 → 全局趋势递增（索引友好）
├── 无协调者 → 任意节点本地生成（无依赖）
└── 碰撞概率：2^74 随机位 → 实际不可能

2026 生态支持现状
├── Java：java.util.UUID 尚无 v7 原生 → 三方库（uuid-creator/Java-UUID-Generator）
├── 数据库：PostgreSQL 14+ / MySQL 8.x 直接存储（BINARY(16)）
│   → UUID 排序可用：MySQL 8 的 UUID_TO_BIN(..., 1) 时间可排序
├── 应用：日志 ID/分布式 trace ID/无状态服务 ID（首选）
└── 局限：不是「严格递增」（毫秒内随机），分库分表场景仍推荐雪花/号段

对比选型（2026 更新）
├── 需要严格有序 + 高并发 → 雪花/号段（DB 排序友好）
├── 无状态 + 趋势有序 + 零运维 → UUIDv7
├── 完全无状态 + 无顺序要求 → UUIDv4
└── 金句：UUIDv7 是「雪花的无状态平替」——没有回拨问题，代价是毫秒内无序
```

## 8. 选型建议

```text
按场景选型（2026 工程共识）
├── 分库分表主键（订单/用户）
│   ├── 规模大 → 雪花（美团 Leaf-snowflake 模式：ZK 分配 workerId）
│   └── 规模中 → 号段（Leaf-segment 双缓冲）
├── 消息/日志/链路追踪 ID → UUIDv7（无状态零成本）
├── 低并发小系统 → DB 自增足够（别过度设计）
├── 对外订单号（防猜测）→ 雪花/号段 + 加密混淆（截断打乱）
└── 跨语言/无状态微服务 → UUIDv7 统一（语言无关）

配套要求
├── workerId 分配：ZK/Redis/配置文件（三选一，别手工）
├── 时钟监控：回拨告警必须上
└── 测试：并发重复校验（压测对比序列号位）
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. **四大流派**：雪花（本地高吞吐）/号段（DB 批量+内存）/UUID（无状态）/DB 自增（简单）
> 2. **雪花 64 位布局**：41 时间戳 + 10 机器 + 12 序列——公式 `(ts-epoch)<<22 | wid<<12 | seq`
> 3. **三个设计点**：自定义纪元延长有效期、& mask 循环序列、synchronized 保原子
> 4. **回拨四级容错**：抛异常 < 等待追平 < 备用时钟 < NTP 防护
> 5. **号段双缓冲**：DB 一次 UPDATE 换一批 ID，异步预取防断档
> 6. **大厂组合拳**：雪花 + ZK 自动 workerId（Leaf）、雪花 + RingBuffer 无锁（UidGenerator）
> 7. **UUIDv7（RFC 9562）**：无状态趋势有序新宠——分库分表仍用雪花/号段
> 8. **选型口诀**：有序高并发→雪花/号段；无状态→UUIDv7；低并发→自增
