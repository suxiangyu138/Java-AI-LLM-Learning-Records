# 07 - 分布式幂等与调度

## 1. 为什么幂等是分布式第一准则

> **背景**：分布式环境里「重试」无处不在——超时重试、MQ 重投、网络重发、用户双击。**每次重试都是一次「重复执行」**，不幂等就出事故。
> **目的**：建立「默认所有接口都要考虑幂等」的工程意识。
> **适用范围**：所有写接口、消息消费、定时任务。

```text
重试的必然性
├── 网络不可靠（[[01]] 基本事实二）→ 超时了你怎么知道服务端成没成？
├── 客户端超时重试：第一次其实成功了 → 第二次再执行 = 重复
├── MQ 重投：消费方处理失败 → 消息重投 → 再消费一遍
├── 用户操作：双击提交/刷新重发
└── 金句：重试是分布式系统的常态，幂等是重试的保险

不幂等的后果（真实事故）
├── 支付回调重放 → 用户余额加两次
├── 下单接口重试 → 生成两笔订单
├── 扣库存重放 → 库存多扣
└── 消息重复消费 → 数据重复写入
```

## 2. 幂等的本质与判定

> 🎯 **幂等（Idempotent）定义**：**同一操作执行一次与执行 N 次，结果一致**：

```text
数学定义
├── f(f(x)) = f(x)：幂等函数
└── 工程定义：同一请求（同业务号）多次执行，最终状态相同

幂等判定标准（设计时自问）
├── ① 重复执行会改变结果吗？（扣款会，查余额不会）
├── ② 有天然幂等标识吗？（订单号/流水号/回调 ID）
└── ③ 结果能被「约束」兜住吗？（唯一索引/状态校验）

哪些天然幂等（不用额外设计）
├── 纯读操作：SELECT
├── 状态覆盖式更新：SET status = 'PAID'（同值重复设置无影响）
├── DELETE by id
├── UPDATE 依赖条件：WHERE id=? AND status='UNPAID'（影响行数判重）
└── 哪些必须设计：INSERT 类、累加类（+1）、非条件更新

接口幂等的三种实现层面
├── 令牌层：前端生成请求号（防重复提交）
├── 业务层：唯一键/状态机（见下节）
└── 数据层：唯一索引/约束（最后防线）
```

## 3. 幂等四件套：唯一键 / 状态机 / 去重表 / 幂等表

### 3.1 唯一键（数据库唯一索引）

> 🎯 **最硬核的幂等**——数据库层面保证，重复插入直接报错：

```sql
-- 下单幂等：订单号唯一
CREATE TABLE t_order (
  order_no VARCHAR(64) NOT NULL,
  ...
  UNIQUE KEY uk_order_no (order_no)
);
-- 重复插入：Duplicate entry 报错 → 捕获后按「已存在」处理
```

```java
// 捕获重复（Spring 写法）
try {
    orderMapper.insert(order);
} catch (DuplicateKeyException e) {
    // 已存在 → 幂等返回成功（或返回已处理状态）
}
```

### 3.2 状态机（业务状态流转约束）

> 🎯 **用状态机挡重复**——非法状态转移直接拒绝：

```text
订单状态机
├── 状态：CREATED → PAID → SHIPPED → COMPLETED
├── 幂等规则：UPDATE ... WHERE status = 上一状态
│   ├── 支付回调：UPDATE t_order SET status='PAID' WHERE id=? AND status='CREATED'
│   ├── 第一次：影响行数 1（成功）
│   ├── 重复回调：影响行数 0（已 PAID，不重复处理）
│   └── 结果：状态机天然防重复 + 防状态回退
└── 金句：状态机 = 把「允许的转移」写进 WHERE——非法即拒绝

注意：状态机要防「回退」
├── PAID 不能回 CREATED
└── 用版本号/状态校验双重保护
```

### 3.3 去重表（防重流水表）

> 🎯 **专门建一张「已处理记录」表**——处理前先查/先占位：

```sql
-- 消息/回调去重表
CREATE TABLE t_msg_dedup (
  msg_id     VARCHAR(64) PRIMARY KEY,   -- 业务唯一标识
  status     TINYINT,                   -- 0处理中 1已完成
  create_time DATETIME
);
-- 消费流程
-- ① INSERT IGNORE INTO t_msg_dedup (msg_id, status) VALUES (?, 0)
--    → 影响行数 0 = 已存在（已处理过）→ 直接 ACK 跳过
--    → 影响行数 1 = 抢到处理权 → 处理业务 → UPDATE status=1
```

### 3.4 幂等表（全链路幂等方案）

> 🎯 **大厂通用「幂等框架」**——请求 ID + 幂等表，覆盖所有写接口：

```text
幂等框架设计
├── 请求头带幂等键（幂等 ID：UUID/业务号）
├── 幂等表（或 Redis）：
│   ├── 请求前：SET key=幂等ID 状态=PROCESSING（NX 成功才继续）
│   ├── 处理成功：状态=DONE（存响应结果，重放直接返回旧结果）
│   ├── 处理失败：删除/置 FAILED（允许重试）
│   └── 处理中超时：可重入（带锁 + 状态校验）
├── 实现载体
│   ├── Redis：高性能（SETNX + TTL）——参考 [[03]] 的锁思路
│   └── DB 幂等表：可靠（对账友好）
└── 金句：幂等表 = 「请求级去重 + 结果缓存」——重试拿旧结果

四件套选型速查
├── 数据写入唯一 → 唯一索引（最硬）
├── 状态流转业务 → 状态机（自带防回退）
├── 消息/回调消费 → 去重表（轻量）
└── 通用写接口 → 幂等框架（Redis/DB 幂等表）
```

## 4. 消息消费幂等

> 🎯 **MQ 场景必须默认「消息会重投」**——至少一次投递语义（at-least-once）下，消费方幂等是唯一防线：

```text
MQ 投递语义
├── at-most-once：最多一次（可能丢）
├── at-least-once：至少一次（可能重复）——RocketMQ/Kafka 默认
├── exactly-once：恰好一次（理论上完美，工程上≈幂等消费）
└── 结论：Kafka/RocketMQ 都是至少一次 → 消费必须幂等

消费幂等三板斧
├── ① 业务唯一键去重（去重表/唯一索引）：消息里的业务 ID 就是幂等键
├── ② 状态机校验：处理过的状态直接跳过
├── ③ 消费组 offset 管理：确认后再提交（防丢）——但重复投递交给幂等

经典案例：支付回调消息
├── 消息体：orderNo + payResult
├── 消费逻辑：UPDATE t_order SET status='PAID' WHERE order_no=? AND status='CREATED'
│   └── 重投 N 次也只会成功一次（状态机 + WHERE 约束）
├── 配合去重表：msg_id 记录已消费消息
└── 金句：MQ 幂等的核心 = 「业务级去重」，不是依赖 MQ 配置
```

> ⚠️ **RocketMQ 事务消息的消费端幂等**：半消息 commit 后可能重复投递——事务消息只保证「投递不丢」，**消费幂等必须自己实现**（[[05]] 联动）。

## 5. 幂等与分布式锁的关系

> 🎯 **锁是「防并发」，幂等是「防重复」**——两者配合才完整：

```text
锁 vs 幂等
├── 分布式锁：同一时刻只有一个执行（并发互斥）
├── 幂等：同一请求执行 N 次结果一致（时序去重）
├── 关系：
│   ├── 锁不防重复（锁释放后重试又执行一遍）
│   ├── 幂等不防并发（两个并发请求可能同时通过校验）
│   └── 正确组合：高并发互斥用锁 + 长期重复防护用幂等
└── 金句：锁保「同时刻」，幂等保「长期」——两个维度都要

「锁可能失效，幂等永不失效」（[[03]] 的终极结论）
├── Redisson 锁在异常场景可能失效（GC 停顿/主从丢失）
├── 但业务幂等（唯一键/状态机）在数据库层面保证
└── 架构原则：锁是优化，幂等是兜底——兜底必须存在
```

## 6. 分布式调度：XXL-Job 深度

> 🎯 **分布式调度解决「定时任务多实例只跑一份」**——XXL-Job（2026 国内主流）核心机制：

```text
XXL-Job 架构
├── 调度中心（admin）：任务注册/触发/监控（独立部署）
├── 执行器（executor）：业务服务内嵌，接收任务执行
├── 任务分片：一台任务拆成多片分给多个执行器并行跑
└── 通信：调度中心 HTTP 触发执行器

核心特性
├── 任务注册：执行器启动自动注册到调度中心
├── 调度方式：cron 表达式 + 手动触发 + 依赖触发
├── 分片广播：shardingIndex/shardingTotal 参数
├── 失败重试：执行失败自动重试（重试要幂等！）
├── 路由策略：轮询/故障转移/一致性哈希/分片广播
└── 阻塞策略：单机串行/丢弃后续/覆盖之前

执行器开发（Spring Boot）
@Component
public class OrderJobHandler {
    @XxlJob("orderStatisticsJob")
    public void execute() {
        // 任务逻辑
    }
}
```

```text
XXL-Job 的可靠性设计
├── 调度记录：每次触发落库（可审计/可补跑）
├── 日志：执行日志收集到调度中心（排查方便）
├── 过期任务：错过调度时间的任务丢弃（防堆积）
└── 金句：调度中心是「触发器」不是「执行器」——业务在服务里
```

## 7. ElasticJob 与分片策略

> 🎯 **ElasticJob（Apache ShardingSphere 团队）**——与 XXL-Job 的选型对比与分片机制：

```text
XXL-Job vs ElasticJob（2026 对比）
├── XXL-Job：调度中心架构、功能全（报警/路由/分片）、运维友好
│   └── 适用：中小团队默认选择
├── ElasticJob：嵌入应用（无中心）、依赖 ZK 协调、分片更细
│   ├── 分片总数配置 + ZK 节点协调
│   ├── 与 ShardingSphere 同源（集成方便）
│   └── 适用：分片复杂/已有 ZK 的团队
└── 结论：国内默认 XXL-Job；数据分片任务（订单分片处理）ElasticJob 更细

分片策略设计（以「处理 100 万订单」为例）
├── 分片数：等于执行器实例数（或数据分片数）
├── 分片参数：shardingIndex=0, shardingTotal=4 → 处理 user_id%4==0 的数据
├── 数据路由：SELECT * FROM t_order WHERE user_id % 4 = {index}
├── 弹性伸缩：执行器增减 → 重新分片（ZK 协调）
└── 金句：分片 = 「把大任务切成小份并行」——切分维度要贴合数据
```

```java
// XXL-Job 分片任务（大任务并行处理）
@XxlJob("shardOrderJob")
public void shardOrder() {
    int index = XxlJobHelper.getShardIndex();      // 本实例 0
    int total = XxlJobHelper.getShardTotal();      // 总 4
    // 处理 user_id % total == index 的订单（天然不重复、可并行）
    List<Order> orders = orderMapper.selectByShard(index, total);
    for (Order order : orders) { process(order); }
}
```

## 8. 调度与幂等的结合：任务幂等

> 🎯 **定时任务也是「写操作」——重跑/补跑/并发触发都要幂等**：

```text
任务幂等的三种场景
├── ① 重复触发：手动触发 + cron 触发撞车
│   ├── 方案：分布式锁（任务执行期间加锁，见 [[03]]）
│   └── 方案：执行记录表（task_exec_log 唯一键）
├── ② 失败重试：XXL-Job 自动重试 = 重复执行
│   ├── 方案：业务逻辑本身幂等（按状态/唯一键处理）
│   └── 方案：重试前检查执行结果标记
├── ③ 分片重叠：分片算法设计不当数据重复
│   └── 方案：分片键严格不重叠（user_id % total）
└── 金句：任务的「每一条处理」都要幂等——任务只是调用了接口

任务幂等设计清单
├── 处理明细幂等：唯一键（订单处理记录 order_id 唯一）
├── 汇总结果幂等：汇总表按日期/维度 upsert
├── 外部调用幂等：调第三方前先查本地状态
└── 补偿任务幂等：对账补偿也要能重复跑（对账本身就是幂等校验）
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. **重试必来，幂等必须**——分布式第一准则
> 2. **幂等判定**：重复执行结果一致；INSERT/累加必设计，读/覆盖式更新天然幂等
> 3. **四件套**：唯一索引（最硬）/状态机（自带防回退）/去重表（消息消费）/幂等表（通用框架）
> 4. **消息 at-least-once**：消费幂等是唯一防线——业务唯一键 + 状态机
> 5. **锁防并发，幂等防重复**——锁可能失效，幂等永不失效
> 6. **XXL-Job**：调度中心 + 执行器 + 分片参数（shardingIndex/Total）
> 7. **分片切分要贴合数据**（user_id % total）——严格不重叠
> 8. **任务幂等三场景**：重复触发/失败重试/分片重叠——执行记录 + 业务幂等
