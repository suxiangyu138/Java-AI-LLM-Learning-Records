## 1. 核心数据结构的四个 Map

```java
// ★ 所有缓存定义在 DefaultSingletonBeanRegistry 中

// ① 一级缓存：成品库 — 完全初始化完成的单例 Bean（对外承诺的"单例"就在这里）
private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);

// ② 二级缓存：半成品库 — 已实例化但未完成属性填充/初始化的 Bean
//    供循环依赖时注入另一方使用
private final Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>(16);

// ③ 三级缓存：工厂库 — 存放 ObjectFactory（延迟创建代理的关键）
//    getObject() 内部调用 getEarlyBeanReference（可能创建 AOP 代理）
private final Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>(16);

// ④ 正在创建中的 BeanName 集合 — 循环依赖判定的核心
//    isSingletonCurrentlyInCreation(beanName) = 此 Set 中是否包含 beanName
private final Set<String> singletonsCurrentlyInCreation =
    Collections.newSetFromMap(new ConcurrentHashMap<>(16));
```

**一条重要规则：** 同一个 beanName 的实例不会同时存在于多个缓存中 → **三级 → 二级（调用 getObject 后迁移）→ 一级（初始化完成后迁移并清空二、三级）**。

## 2. getSingleton 源码全链路

```java
// ★ DefaultSingletonBeanRegistry#getSingleton(beanName, allowEarlyReference)
//    这是 Spring 解决循环依赖的核心逻辑 — 三次查找 + 缓存迁移

protected Object getSingleton(String beanName, boolean allowEarlyReference) {
    // ===== 第 1 次查找：一级缓存（成品）=====
    Object singletonObject = this.singletonObjects.get(beanName);

    // 一级缓存没有 且 当前 Bean 正在创建中 → 说明可能发生了循环依赖
    if (singletonObject == null && isSingletonCurrentlyInCreation(beanName)) {

        // ===== 第 2 次查找：二级缓存（半成品）=====
        singletonObject = this.earlySingletonObjects.get(beanName);

        // 二级也没有 且 允许提前引用
        if (singletonObject == null && allowEarlyReference) {
            synchronized (this.singletonObjects) {   // 加锁保证并发安全
                // 双重检查（并发场景下其他线程可能已放入）
                singletonObject = this.singletonObjects.get(beanName);
                if (singletonObject == null) {
                    singletonObject = this.earlySingletonObjects.get(beanName);
                    if (singletonObject == null) {

                        // ===== 第 3 次查找：三级缓存（工厂）=====
                        ObjectFactory<?> singletonFactory = this.singletonFactories.get(beanName);
                        if (singletonFactory != null) {
                            // ⚠️ getObject() 内部调 getEarlyBeanReference →
                            //    调用 SmartInstantiationAwareBPP → 可能生成 AOP 代理
                            singletonObject = singletonFactory.getObject();

                            // ★ 关键迁移：三级 → 二级（同时移除三级）
                            //    之后再次获取直接从二级拿，不再经过工厂
                            this.earlySingletonObjects.put(beanName, singletonObject);
                            this.singletonFactories.remove(beanName);
                        }
                    }
                }
            }
        }
    }
    return singletonObject;
}
```

**三个关键判断节点（面试画出这三步即满分）：**

| 查找步骤 | 缓存 | 存放内容 | 说明 |
|----------|------|----------|------|
| ① | singletonObjects | 完全初始化完成的成品 | 正常获取路径 |
| ② | earlySingletonObjects | 半成品（已实例化、未初始化） | 循环依赖时的提前引用 |
| ③ | singletonFactories | ObjectFactory（包装 getEarlyBeanReference） | **仅调用一次** |

### 配套方法：addSingletonFactory / addSingleton

```java
// ★ doCreateBean() 中调用：实例化后、属性填充前 → 放入三级缓存（提前暴露）
//   只有在 earlySingletonExposure=true 时才执行
addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean));
//                            ↑ 注意：存的是 lambda，不是 bean 本身（延迟策略）

// ★ 初始化完成后调用：成品入一级、清理二三级
addSingleton(beanName, singletonObject);
// 内部：singletonObjects.put + earlySingletonObjects.remove + singletonFactories.remove
//       + registeredSingletons.add + singletonsCurrentlyInCreation.remove
```

## 3. 循环依赖解决的完整推演（A → B → A）

```text
场景：A 的字段 b 是 B；B 的字段 a 是 A（都通过 @Autowired Setter 注入）

步骤①：getBean(A)
  ├── doCreateBean(A)
  ├── createBeanInstance(A)   → A 空实例（字段 b = null）
  ├── addSingletonFactory(A)  → ★ A 的 ObjectFactory 放入三级缓存
  │   标记：singletonsCurrentlyInCreation 包含 A
  ├── populateBean(A)         → 需要注入 b → 触发 getBean(B)
  │
  └──→ 步骤②：getBean(B)
         ├── doCreateBean(B)
         ├── createBeanInstance(B)   → B 空实例（字段 a = null）
         ├── addSingletonFactory(B)  → ★ B 的 ObjectFactory 放入三级缓存
         │   标记：singletonsCurrentlyInCreation 包含 A、B
         ├── populateBean(B)         → 需要注入 a → 触发 getBean(A)
         │
         └──→ 步骤③：getBean(A)
                ├── singletonObjects 无（A 只实例化未初始化）
                ├── isSingletonCurrentlyInCreation(A)? ★ YES！
                ├── earlySingletonObjects 无
                ├── singletonFactories 有 ★ → getObject() → getEarlyBeanReference(A)
                │   → 三级缓存中的 A 被取出（可能已被 AOP 代理包装）→ 放入二级缓存
                └── ★ 将 A（可能代理后的半成品）返回给 B
         ←── B 拿到半成品 A，完成属性 a 填充
         B 执行初始化 → addSingleton(B) 放入一级、清理二三
  ←── B 成品返回给 A
  A 完成属性 b 填充（拿到的是成品 B）
  A 执行初始化 → addSingleton(A) 放入一级、清理缓存

关键验证：B 注入的 "半成品 A" 和一级缓存的 "成品 A"
          是否为同一个对象/代理？ → 是的（三级缓存保证一致性，见下节）
```

## 4. 为什么是三级而不是二级

**这是面试的金扣题，答出 AOP 代理唯一点就过关。**

### 4.1 二级缓存能解决什么

```text
如果只有 singletonObjects + earlySingletonObjects（两级）：
A 实例化 → 放入二级缓存 → B 创建时注入 A → A 初始化 → 移入一级
只要 A 不需要 AOP 代理，二级足够解决（半成品 A 被引用后，最终成品 A 是同一个对象）
```

### 4.2 二级缓存的致命缺陷

```text
如果 A 需要 AOP 代理（@Transactional/@Async/@Aspect）：
A 实例化 → 原始 A 放入二级缓存
B 创建时拿到"原始 A"并注入（此时还没创建代理！）
A 继续初始化 → afterInitialization 调用 → AOP 代理创建 → 代理 A 放入一级
                                         ↑
    结果：B 持有的原始 A ≠ 一级缓存中的代理 A
    后果：B 调用 a.doSomething() 时：事务不会生效！切面不会执行！
```

### 4.3 三级缓存的解决方案

```java
// 三级缓存中存放的不是"原始对象"，而是 ObjectFactory：
addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean));

// getEarlyBeanReference 内部：
//   → 遍历所有 SmartInstantiationAwareBeanPostProcessor
//   → AnnotationAwareAspectJAutoProxyCreator（继承 AbstractAutoProxyCreator）:
//       如果需要代理 → 在此处提前创建代理对象并返回
//       同时标记 earlyProxyReferences → 确保之后 afterInitialization 不重复创建
//       从而全局只存在一个代理实例

// ★ 关键逻辑：
//   1. 有循环依赖 → getObject() 被调用 → 提前创建代理（从三级升到二级）
//   2. 无循环依赖 → getObject() 从未被调用 → 代理按常规在 afterInitialization 创建
//   3. 代理对象全局唯一：提前创建过一次，afterInitialization 不会再创建
```

**最终答案：** 三级缓存通过 `ObjectFactory` + `getEarlyBeanReference` 实现**代理的延迟按需创建** — 只有发生循环依赖时才提前生成代理，保证"B 注入的半成品 A"和"一级缓存的成品 A"**是同一个代理对象**。

**追问：** 那为什么不用 `getEarlyBeanReference` 提前给所有 Bean 都创建代理，省去 afterInitialization 步骤？→ 这违背了"初始化阶段再创建代理"的设计原则 — 大部分 Bean 无循环依赖，提前代理增加不必要的开销。

## 5. 无法解决的场景

| 场景 | 原因 | 对策 |
|------|------|------|
| **构造器注入** | 实例化前就需要完整依赖对象，无法提前暴露 | 改用 Setter/@Lazy/重构设计 |
| **Prototype 作用域** | Spring 不缓存原型 Bean | 直接重构，Prototype 循环是设计问题 |
| **@Async 代理** | 代理在 afterInitialization 创建，无法提前 | 重构依赖（避免 @Async Bean 互相依赖） |
| **FactoryBean 的场景** | FactoryBean 创建的 Bean 时序复杂 | 使用 `&` 前缀获取 FactoryBean 本身 |

**核心记忆：** 能解决的 = **单例 + Setter/字段注入**；不能解决的 = 构造器注入、Prototype、@Async 代理场景。

## 6. 源码断点调试指引

```text
调试调用链（断点按此顺序下）：
getBean() → doGetBean() → createBean() → doCreateBean()
  ├── createBeanInstance()        → 实例化（断点 1）
  ├── addSingletonFactory()       → 放入三级缓存（断点 2：看 earlySingletonExposure）
  ├── populateBean()              → 属性填充（断点 3：循环依赖触发点）
  └── initializeBean()            → 初始化 + AOP 代理（断点 4）

关键变量追踪：
  - singletonsCurrentlyInCreation  → 包含哪些 BeanName？
  - singletonFactories             → 工厂是否已注册？
  - earlySingletonObjects          → 工厂是否被调用过（三级已迁至二级）？
  - singletonObjects               → 成品何时入一级？

验证 AOP 代理一致性：
  在 B 的字段 a 上打断点 → 取 a.getClass()：
    $Proxy...（如果是 CGLIB/AOP 代理）= 说明注入的是代理对象
```
