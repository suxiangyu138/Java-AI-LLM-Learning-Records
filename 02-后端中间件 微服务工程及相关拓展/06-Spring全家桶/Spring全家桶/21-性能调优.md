## 2. JVM参数调优

>  JVM调优是性能调优的基石 -- 不合理的JVM参数会直接导致GC频繁、内存溢出、应用卡顿，合理配置可提升30%以上吞吐量

### 2.1 JVM内存结构回顾

```
JVM内存结构
├── 堆（Heap）-- 所有线程共享
│   ├── 年轻代（Young Generation）
│   │   ├── Eden（伊甸园，对象首次分配）
│   │   └── Survivor（S0 / S1，存活对象交换区）
│   ├── 老年代（Old Generation）-- 长期存活对象
│   └── 元空间（Metaspace，JDK 8+）-- 类元数据
├── 栈（Stack）-- 线程私有
├── 程序计数器（PC Register）
└── 直接内存（Direct Memory）-- NIO、堆外缓存
```

### 2.2 堆内存参数详解

#### 2.2.1 核心堆参数

| 参数 | 说明 | 默认值 | 建议范围 |
|------|------|--------|----------|
| `-Xms` | 初始堆大小 | 物理内存的1/64 | 4g ~ 16g |
| `-Xmx` | 最大堆大小 | 物理内存的1/4 | 4g ~ 16g |
| `-Xmn` | 年轻代大小 | 堆的1/3 | 堆的1/4 ~ 1/3 |
| `-XX:MetaspaceSize` | 元空间初始大小 | 约21MB | 256m ~ 512m |
| `-XX:MaxMetaspaceSize` | 元空间最大大小 | 无上限 | 512m ~ 1g |
| `-XX:SurvivorRatio` | Eden:Survivor比例 | 8 | 6 ~ 8 |
| `-XX:NewRatio` | 老年代:年轻代比例 | 2 | 2 ~ 4 |

> ⚠️ **重要原则**：`-Xms`和`-Xmx`必须设置为相同值，避免运行时动态调整堆大小导致的性能抖动。

```bash
# 典型4C8G配置
-Xms4g -Xmx4g
-Xmn1536m
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m

# 典型8C16G配置
-Xms8g -Xmx8g
-Xmn3g
-XX:MetaspaceSize=512m
-XX:MaxMetaspaceSize=1g
```

#### 2.2.2 为什么Xms和Xmx要相等

>  JVM在运行时如果发现当前堆使用量接近Xmx，会尝试扩大堆（直到Xmx）；如果使用量降低，可能又收缩（直到Xms）。这种动态调整会触发Full GC，造成性能抖动。设置-Xms = -Xmx后，JVM启动即分配全部内存，避免此问题。

```bash
# 错误做法 -- 会导致性能抖动
-Xms512m -Xmx4g

# 正确做法 -- 固定堆大小
-Xms4g -Xmx4g
```

#### 2.2.3 年轻代大小设置原则

| 场景 | 年轻代比例 | 原因 |
|------|-----------|------|
| 高吞吐（批量处理） | 堆的1/3 | 大年轻代减少对象晋升频率 |
| 低延迟（Web应用） | 堆的1/4 ~ 1/3 | 控制Minor GC暂停时间 |
| 大量临时对象 | 堆的1/3 ~ 1/2 | 减少对象进入老年代 |
| 大内存（32G+） | 堆的1/4 | 避免GC暂停过长 |

### 2.3 GC收集器选择

#### 2.3.1 各GC收集器对比

| 特性 | ParallelGC | G1GC | ZGC | Shenandoah |
|------|-----------|------|-----|------------|
| JDK版本 | JDK 8+ | JDK 9+（JDK 11+默认） | JDK 15+（JDK 21+生产就绪） | JDK 12+ |
| 工作方式 | 吞吐量优先 | 区域化分代收集 | 并发标记-整理，无停顿 | 并发evacuation |
| 暂停时间 | 数百ms~数秒 | 10~200ms | < 1ms | < 10ms |
| 吞吐量 | 最高 | 高 | 中 | 中 |
| 内存开销 | 低 | 中等 | 高 | 高 |
| 最大堆推荐 | < 8G | < 32G | 8G~16T | < 32G |
| 适用场景 | 批处理、离线计算 | Web应用、微服务 | 低延迟金融、实时系统 | 低延迟、大堆场景 |

#### 2.3.2 GC选择决策树

```
应用需要多低的延迟？
├── 无特殊要求（< 200ms）
│   ├── < 4G堆  -> ParallelGC
│   ├── 4G~8G   -> G1GC
│   └── > 8G    -> G1GC
├── 低延迟（< 50ms）
│   └── G1GC调优暂停时间
└── 极低延迟（< 10ms）
    ├── JDK 17+ -> ZGC
    └── JDK 11  -> G1GC精细调优
```

### 2.4 G1GC深度调优

#### 2.4.1 G1GC关键参数

| 参数 | 说明 | 默认值 | 建议值 |
|------|------|--------|--------|
| `-XX:MaxGCPauseMillis` | 目标最大GC暂停时间(ms) | 200 | 50~200 |
| `-XX:InitiatingHeapOccupancyPercent` | 触发混合GC的堆占用百分比 | 45 | 35~60 |
| `-XX:G1HeapRegionSize` | Region大小(1M~32M) | 自动计算 | 1M~8M |
| `-XX:ConcGCThreads` | 并发GC线程数 | CPU的1/4 | 2~4 |
| `-XX:ParallelGCThreads` | 并行GC线程数 | CPU数 | CPU数量 |
| `-XX:G1ReservePercent` | 预留空间百分比 | 10% | 10~20 |
| `-XX:G1MixedGCLiveThresholdPercent` | 混合GC存活对象阈值 | 85% | 65~85 |
| `-XX:G1MixedGCCountTarget` | 混合GC轮次 | 8 | 8~16 |

#### 2.4.2 G1GC调优步骤

>  G1GC调优核心目标：在满足MaxGCPauseMillis目标的前提下，最大化吞吐量。

**步骤1：设置合理的暂停时间目标**

```bash
# 不要设置过小，否则G1会过于激进，频繁GC降低吞吐量
-XX:MaxGCPauseMillis=150
```

**步骤2：调整IHOP阈值**

```bash
# IHOP控制何时启动并发标记，默认45%
# 老年代增长慢（存活率高），适当提高
-XX:InitiatingHeapOccupancyPercent=55

# 老年代增长快（短生命周期对象多），应该降低
-XX:InitiatingHeapOccupancyPercent=35
```

**步骤3：调整Region大小**

```bash
# Region大小 = 堆大小 / 2048，取2的幂
# 4G堆 -> Region约2MB
# 8G堆 -> Region约4MB
# 16G堆 -> Region约8MB
-XX:G1HeapRegionSize=4M
```

#### 2.4.3 G1GC完整示例

```bash

-Xms8g -Xmx8g
-Xmn3g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=150
-XX:InitiatingHeapOccupancyPercent=45
-XX:ConcGCThreads=4
-XX:ParallelGCThreads=8
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m
-XX:G1HeapRegionSize=4M
-XX:G1ReservePercent=15
```

```bash
# 4C4G微服务 - G1GC推荐配置
-Xms4g -Xmx4g
-Xmn1536m
-XX:+UseG1GC
-XX:MaxGCPauseMillis=100
-XX:InitiatingHeapOccupancyPercent=35
-XX:ConcGCThreads=2
-XX:ParallelGCThreads=4
-XX:MetaspaceSize=128m
-XX:MaxMetaspaceSize=256m
-XX:G1HeapRegionSize=2M
```

### 2.5 ZGC深度调优

#### 2.5.1 ZGC核心原理

ZGC是JDK 11引入的超低延迟GC（< 1ms暂停），使用染色指针（Colored Pointers）和读屏障（Load Barrier）实现并发。

```
ZGC工作流程（全部并发）
1. 并发标记（Concurrent Mark）
2. 并发预备重分配（Concurrent Prepare for Relocation）
3. 并发重分配（Concurrent Relocate）
4. 并发重映射（Concurrent Remap）
```

#### 2.5.2 ZGC关键参数

| 参数 | 说明 | 默认值 | 建议值 |
|------|------|--------|--------|
| `-XX:+UseZGC` | 启用ZGC | 不启用 | JDK 17+生产可用 |
| `-XX:ZCollectionInterval` | ZGC收集间隔(秒) | 0（自适应） | 30~120 |
| `-XX:ZFragmentationLimit` | 碎片率限制 | 25% | 5~25 |
| `-XX:ConcGCThreads` | 并发GC线程数 | CPU的1/8 | CPU的1/8~1/4 |
| `-XX:+ZGenerational` | 分代ZGC(JDK 21+) | 启用 | 推荐 |

>  **JDK 21+分代ZGC**是重大改进：年轻代GC更频繁但暂停依然< 1ms，老年代GC频率降低，总体吞吐量提升20%~40%。

```bash
# 8C16G低延迟服务 - ZGC配置
-Xms8g -Xmx8g
-XX:+UseZGC
-XX:ZCollectionInterval=60
-XX:ZFragmentationLimit=10
-XX:ConcGCThreads=4
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m
```

```bash
# JDK 21+分代ZGC配置
-Xms8g -Xmx8g
-XX:+UseZGC
-XX:+ZGenerational
-XX:ZCollectionInterval=60
-XX:MetaspaceSize=256m
-XX:MaxMetaspaceSize=512m
```

## 3. Tomcat线程池调优

>  Tomcat是Spring Boot默认的Web容器，其线程池配置直接影响请求处理能力和响应速度

### 3.1 Tomcat线程池架构

```
HTTP请求处理流程
客户端 -> accept队列(acceptCount) -> 连接器(maxConnections) -> 工作线程池(maxThreads) -> 业务处理

三个阶段：
1. accept队列：请求到达后，如果工作线程池满了，进入acceptCount等待队列
2. 连接器维护：maxConnections限制最大TCP连接数，超过则拒绝
3. 线程池处理：minSpareThreads维持的最小空闲线程数，maxThreads最大工作线程数
```

### 3.2 核心参数详解

#### 3.2.1 参数一览

| 参数 | 说明 | 默认值 | 建议范围 |
|------|------|--------|----------|
| `server.tomcat.threads.max` | 最大工作线程数 | 200 | 100~500 |
| `server.tomcat.threads.min-spare` | 最小空闲线程数 | 10 | 10~50 |
| `server.tomcat.accept-count` | 等待队列长度 | 100 | 100~1000 |
| `server.tomcat.max-connections` | 最大连接数 | 8192 | 1000~10000 |
| `server.tomcat.connection-timeout` | 连接超时(ms) | 20000 | 5000~30000 |

#### 3.2.2 参数交互流程

```
请求到达
    |
    v
accept-count队列未满？ --否--> 拒绝连接（返回503）
    | 是
    v
max-connections未达到？ --否--> 进入accept-count等待
    | 是
    v
创建连接，进入线程池
    |
    v
有空闲线程？ --是--> 立即处理
    | 否
    v
等待线程释放（排队）
    |
    v
处理完成 -> 返回响应
```

>  核心原则：**acceptCount >= maxThreads**，确保线程池满时请求能排队而不是直接拒绝。

#### 3.2.3 连接流程详解

Tomcat处理连接的完整流程：

1. **连接建立阶段**：客户端发起TCP连接，Tomcat的Acceptor线程接收连接
2. **连接队列阶段**：如果当前连接数超过`maxConnections`，新连接进入`acceptCount`队列
3. **连接处理阶段**：Poller线程轮询已建立的连接，检测到数据可读后提交给工作线程池
4. **业务处理阶段**：工作线程执行Servlet容器请求处理，执行业务逻辑
5. **响应阶段**：处理完成后，通过Poller线程将响应写回客户端

### 3.3 线程池大小计算公式

#### 3.3.1 Little's Law公式

```
N_threads = N_cpu * (1 + W / S)

其中：
  N_cpu = CPU核心数
  W = 等待时间（IO等待、网络IO、DB查询等阻塞时间）
  S = 服务时间（CPU计算时间）

推导：
  - CPU密集型任务（W=0）：N_threads = N_cpu
  - IO密集型任务（W=3S）：N_threads = 4 * N_cpu
  - 网络IO密集型（W=10S）：N_threads = 11 * N_cpu
```

#### 3.3.2 不同类型应用推荐

| 应用类型 | W/S比例 | 推荐线程数 | 示例 |
|----------|---------|-----------|------|
| CPU密集型（加密、计算） | 0~1 | N_cpu ~ 2*N_cpu | 图片处理、加解密服务 |
| 普通Web（少量DB） | 2~5 | 3*N_cpu ~ 6*N_cpu | CRUD接口 |
| IO密集型（大量DB/缓存） | 5~10 | 6*N_cpu ~ 11*N_cpu | 数据聚合服务 |
| 微服务编排（Feign调用） | 10~50 | 11*N_cpu ~ 51*N_cpu | BFF网关、编排服务 |

### 3.8 Tomcat线程池调优误区

>  线程数不是越大越好。过多的线程会导致：
>  1. **CPU上下文切换开销**：线程数超过CPU核心数后，切换开销急剧上升
>  2. **内存消耗**：每个线程默认栈大小1MB（-Xss），200线程=200MB
>  3. **锁竞争加剧**：太多线程竞争共享资源，反而降低吞吐量

正确的做法是压测找到拐点：

```
QPS
  ^
  |    /
  |   /  ---- 拐点：再增加线程QPS不再提升甚至下降
  |  /        |
  | /            |/              +-----------------> 线程数
     最佳线程数
```

## 4. 连接池调优-HikariCP

>  HikariCP是Spring Boot 2.x+的默认数据库连接池，以"零开销"为设计目标，性能远超传统连接池

### 4.1 HikariCP为什么是默认选择

#### 4.1.1 各连接池基准对比

| 特性 | HikariCP | Druid | DBCP2 | Tomcat CP |
|------|----------|-------|-------|-----------|
| 性能（吞吐量） | 最高 | 中 | 低 | 中 |
| 连接获取延迟 | < 1ms | 2~5ms | 5~10ms | 2~3ms |
| CPU开销 | 最低 | 中 | 高 | 中 |
| 稳定性 | 优 | 优 | 一般 | 优 |
| 监控功能 | 基础（Metrics） | 强大（Druid Monitor） | 弱 | 基础 |
| SQL防火墙 | 无 | 有 | 无 | 无 |
| PSCache | 无（不需要） | 有 | 有 | 有 |
| 自动重连 | 支持 | 支持 | 有限 | 支持 |
| 配置复杂度 | 低（极少参数） | 中 | 高 | 中 |
| Spring Boot默认 | 是（2.x+） | 否（需引入） | 否（已弃用） | 否（1.x默认） |

#### 4.1.2 HikariCP优势来源

>  为什么HikariCP能如此之快？

1. **代码极致精简**：HikariCP字节码仅约200KB，相比Druid的MB级别，体积小意味着执行路径短
2. **无锁集合**：使用ConcurrentBag实现（类似ThreadLocal + CAS），比传统的BlockingQueue更高效
3. **代理模式优化**：使用javassist生成动态代理，而不是JDK Proxy，减少反射调用开销
4. **友元优化**：JIT编译器可以将小方法内联，HikariCP精心设计了方法大小以触发内联优化
5. **零开销度量**：默认不采集metrics，只在开启时才启用，不产生额外开销

### 4.2 核心参数详解

#### 4.2.1 参数一览

| 参数 | 说明 | 默认值 | 建议范围 |
|------|------|--------|----------|
| `maximumPoolSize` | 最大连接数 | 10 | 10~50 |
| `minimumIdle` | 最小空闲连接数 | 10（等于maximumPoolSize） | 10~30 |
| `connectionTimeout` | 连接超时(ms) | 30000 | 5000~30000 |
| `idleTimeout` | 空闲超时(ms) | 600000（10分钟） | 300000~600000 |
| `maxLifetime` | 连接最大存活时间(ms) | 1800000（30分钟） | 900000~1800000 |
| `keepaliveTime` | 心跳检测间隔(ms) | 0（不启用） | 60000~300000 |
| `validationTimeout` | 连接检测超时(ms) | 5000 | 2000~5000 |
| `leakDetectionThreshold` | 连接泄漏检测阈值(ms) | 0（不启用） | 60000~300000 |

#### 4.2.2 参数详细说明

**maximumPoolSize（最大连接数）**

>  这是最重要的参数，但也是最容易被误解的参数。**更大的连接池并不一定带来更好的性能**。

```yaml
spring:
  datasource:
    hikari:
      maximumPoolSize: 20  # 大多数应用20~30足矣
```

**minimumIdle（最小空闲连接数）**

```yaml
spring:
  datasource:
    hikari:
      minimumIdle: 10       # 保持10个空闲连接
      # HikariCP推荐：不设置minimumIdle，默认等于maximumPoolSize
      # 这样可以避免频繁创建/销毁连接
```

**connectionTimeout（连接超时）**

```yaml
spring:
  datasource:
    hikari:
      connectionTimeout: 10000  # 10秒拿不到连接就超时
      # 设置太短->频繁超时错误；太长->请求堆积
      # 建议：根据DB查询的TP99决定，一般5000~15000ms
```

**maxLifetime（连接最大存活时间）**

```yaml
spring:
  datasource:
    hikari:
      maxLifetime: 1200000  # 20分钟
      # 必须小于数据库的wait_timeout（MySQL默认28800秒=8小时）
      # 建议：1200000~1800000ms（20~30分钟）
      # 定期回收连接可以避免连接泄漏和TCP层面的问题
```

**leakDetectionThreshold（连接泄漏检测）**

```yaml
spring:
  datasource:
    hikari:
      leakDetectionThreshold: 60000  # 60秒
      # 当连接获取后超过60秒未归还，HikariCP会在日志中输出警告
      # 包含获取连接的堆栈信息，便于排查
      # 仅建议在开发/测试环境开启，生产环境根据情况开启
```

### 4.3 连接池大小计算公式

#### 4.3.1 经典公式

```text
connections = (core_count * 2) + effective_spindle_count

其中：
  - core_count = CPU核心数
  - effective_spindle_count = 磁盘有效主轴数（通常忽略）

简化版：connections = core_count * 2
```

>  为什么公式如此之小？因为数据库连接池的核心不是"连接数"，而是"并发事务数"。大多数数据库的并发能力有限（PostgreSQL的活跃连接数超过50后性能下降，MySQL超过100后也会下降）。

#### 4.3.2 按场景推荐

| 场景 | CPU核心数 | 推荐连接数 | 说明 |
|------|-----------|-----------|------|
| 轻量CRUD | 2C | 10~15 | 查询快，连接周转快 |
| 普通Web | 4C | 15~25 | 混合读写，中等复杂度 |
| 重度Web | 8C | 25~40 | 复杂查询，大量IO |
| 数据/报表 | 16C | 40~60 | 长时间查询 |
| 高并发写入 | 8C | 20~30 | 写操作有锁，不宜过多 |

#### 4.3.3 误区："Bigger Pool = Better Performance"

这是一个常见的错误认识。实际上：

```
QPS vs 连接池大小
QPS
  ^
  | *   *   *
  | *   *   *   *    *      <- QPS曲线
  | *   *   *   *    *
  | *   *   *   *    *    *
  | *   *   *   *    *    *    *
  +---------------------------------> 连接数
    5   10  15  20   30   50   100
```

>  当连接数超过某个阈值后，QPS不再增长，反而可能下降。原因：
>  1. 数据库端连接管理开销增加
>  2. 上下文切换加剧（应用端）
>  3. 数据库锁竞争加剧
>  4. TCP连接数过高导致网络层瓶颈

### 4.5 连接泄漏检测

连接泄漏是最常见的数据库问题之一，通常由以下原因导致：
- 获取连接后未在finally块中关闭
- 异步处理中传递了连接但没有正确管理生命周期
- 某些ORM框架的会话管理不当

```yaml
spring:
  datasource:
    hikari:
      leakDetectionThreshold: 60000
      # 当连接获取后超过60秒未归还，HikariCP输出如下警告：
      # "Connection leak detection triggered..."
      # 并打印获取连接的堆栈信息
```

```java
// 典型连接泄漏代码（不要这样写）
@GetMapping("/leak")
public String leak() throws SQLException {
    Connection conn = dataSource.getConnection();
    Statement stmt = conn.createStatement();
    ResultSet rs = stmt.executeQuery("SELECT 1");
    // 忘记关闭 conn / stmt / rs！连接泄漏！
    return "ok";
}

// 正确写法（try-with-resources）
@GetMapping("/no-leak")
public String noLeak() throws SQLException {
    try (Connection conn = dataSource.getConnection();
         Statement stmt = conn.createStatement();
         ResultSet rs = stmt.executeQuery("SELECT 1")) {
        return "ok";
    }
}
```

## 5. Feign连接池优化

### 5.3 Feign核心调优参数

```java
@Configuration
public class OkHttpConfig {

    @Bean
    public OkHttpClient okHttpClient() {
        return new OkHttpClient.Builder()
            .connectTimeout(5, TimeUnit.SECONDS)      // 连接超时
            .readTimeout(10, TimeUnit.SECONDS)         // 读取超时
            .writeTimeout(10, TimeUnit.SECONDS)        // 写入超时
            .connectionPool(new ConnectionPool(
                50,                  // maxIdleConnections
                5, TimeUnit.MINUTES  // keepAliveDuration

            .retryOnConnectionFailure(true)            // 连接失败重试
            .build();
    }
}
```

#### 5.3.3 参数详解

**maxConnectionsPerRoute（每个路由最大连接数）**

每个目标服务（路由）的最大连接数。如果A服务调用B服务、C服务，则每个服务独立计算。

```yaml

```

**connectionTtl（连接TTL）**


## 6. Redis连接池调优

>  Redis作为缓存中间件，连接池的合理配置直接影响缓存访问延迟和系统吞吐量

### 6.1 Lettuce vs Jedis

#### 6.1.1 对比

| 特性 | Lettuce（Spring Boot 2.x+默认） | Jedis |
|------|--------------------------------|-------|
| 线程安全 | 是（基于Netty，共享连接实例） | 否（需配合连接池） |
| 连接池 | 可选（非必须） | 必须（非线程安全） |
| 异步/响应式 | 支持（原生异步API） | 不支持 |
| Redis 6+支持 | 支持（SSL、集群、Sentinel） | 支持 |
| 性能 | 高（Netty NIO） | 中（BIO） |
| 连接模型 | 多路复用（单连接） | 阻塞IO（每线程一连接） |
| 断线重连 | 自动重连 | 需手动处理 |
| API风格 | 响应式+同步 | 同步 |
| 依赖大小 | ~2MB | ~1MB |
| Spring Boot默认 | 是（2.x+） | 否 |

#### 6.1.2 核心差异说明

```text
Jedis模型（每线程一个连接）：
Thread-1 -> Jedis-1 -> Redis
Thread-2 -> Jedis-2 -> Redis
Thread-3 -> Jedis-3 -> Redis

Lettuce模型（多线程共享连接）：
Thread-1 -Thread-2 -+-> Lettuce -> RedisConnection -> Redis
Thread-3 -/
```

>  Lettuce基于Netty的异步事件驱动模型，一个连接可以处理多个并发请求，天生线程安全。Jedis是BIO模型，每个操作独占一个连接，非线程安全。

### 6.2 Lettuce连接池配置

#### 6.2.1 是否使用连接池？

```text
Lettuce连接池选型：
├── 高并发场景（QPS > 5000） -> 建议使用连接池
├── 普通场景（QPS < 5000）  -> 共享连接即可（默认）
└── Redis Cluster模式       -> 建议使用连接池
```

#### 6.2.2 启用Lettuce连接池

```xml
<!-- pom.xml - 需要添加commons-pool2依赖 -->
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-pool2</artifactId>
</dependency>
```

```yaml
spring:
  redis:
    host: localhost
    port: 6379
    password: ${REDIS_PWD}
    timeout: 3000               # 连接超时(ms)
    connect-timeout: 2000       # TCP连接超时(ms)

    lettuce:
      pool:
        max-active: 16           # 最大活跃连接数（默认8）
        max-idle: 8             # 最大空闲连接数（默认8）
        min-idle: 4             # 最小空闲连接数（默认0）
        max-wait: 5000          # 获取连接最大等待时间(ms)，默认-1（永远等待）
        time-between-eviction-runs: 30000  # 空闲连接回收间隔(ms)
      shutdown-timeout: 100     # 关闭超时(ms)
```

#### 6.2.3 参数详解

**max-active（最大活跃连接数）**

```yaml
spring:
  redis:
    lettuce:
      pool:
        max-active: 32   # 最大连接数
        # 根据并发数计算：max-active = TP99耗时(ms) * QPS / 1000
        # 例如：TP99=5ms，QPS=5000 -> max-active = 5 * 5000 / 1000 = 25
        # 建议范围：16~64，过大浪费资源
```

**max-wait（获取连接等待超时）**

```yaml
spring:
  redis:
    lettuce:
      pool:
        max-wait: 3000   # 3秒拿不到连接就抛异常
        # 设置太短 -> 高峰时频繁超时
        # 设置太长 -> 请求堆积，线程阻塞
        # 建议：3000~5000ms
```

**time-between-eviction-runs（回收间隔）**

```yaml
spring:
  redis:
    lettuce:
      pool:
        time-between-eviction-runs: 30000  # 30秒回收一次
        # 设置太短 -> 频繁扫描浪费CPU
        # 设置太长 -> 空闲连接占用资源
        # 建议：30000~60000ms
```

### 6.3 Redis连接池大小估算

#### 6.3.1 计算公式

```text
PoolSize = (TP99_Latency_ms * QPS) / 1000

示例：
- QPS = 10000，TP99延迟 = 2ms
- PoolSize = (2 * 10000) / 1000 = 20

- QPS = 5000，TP99延迟 = 10ms（大Value场景）
- PoolSize = (10 * 5000) / 1000 = 50
```

#### 6.3.2 不同场景推荐

| 场景 | QPS | TP99延迟 | 推荐max-active | 是否使用连接池 |
|------|-----|----------|---------------|--------------|
| 轻量缓存（短Key小Value） | 5000 | < 1ms | 8~16 | 可选 |
| 中等流量（会话缓存） | 10000 | 2~3ms | 16~32 | 推荐 |
| 高并发（热点数据） | 50000 | 1~2ms | 32~64 | 必须 |
| 大Value（JSON/序列化） | 2000 | 10~20ms | 32~50 | 必须 |
| Redis Cluster | 10000 | 2~5ms | 32~64 | 必须 |

### 6.4 Redis客户端超时设置

## 7. Gateway线程池优化

>  Spring Cloud Gateway基于Spring WebFlux（Reactor Netty），使用事件循环模型，线程模型与传统的Servlet容器完全不同

### 7.1 Gateway线程模型

```
Gateway线程模型（Reactor Netty）
        ┌─────────────────────────────────┐
        │         Boss EventLoop          │
        │    （1~2个线程，接受连接）       │
        └──────────┬──────────────────────┘
                   │
        ┌──────────▼──────────────────────┐
        │      Worker EventLoop           │
        │   （默认CPU核心数*2个线程）      │
        │  处理请求/响应、路由转发、过滤   │
        └─────────────────────────────────┘
                   │
        ┌──────────▼──────────────────────┐
        │       业务线程池（可选）         │
        │  执行阻塞操作（DB查询、Feign调用）│
        └─────────────────────────────────┘
```

>  **关键区别**：Gateway的EventLoop线程不能执行阻塞操作！如果需要调用后端服务或DB，请使用异步调用或将阻塞操作放到自定义线程池。

### 7.2 Netty EventLoop配置

```yaml
spring:
  cloud:
    gateway:
      httpclient:                    # 下游HTTP客户端
        connect-timeout: 5000        # 连接超时(ms)
        response-timeout: 10s        # 响应超时
        pool:
          type: elastic              # 连接池类型：elastic/fixed
          max-idle-time: 60000       # 空闲超时(ms)
          max-life-time: 1800000     # 最大存活(ms)
          acquire-timeout: 45000     # 获取连接超时(ms)
          max-connections: 1000      # 最大连接数

      httpserver:                    # 上游HTTP服务器
        connect-timeout: 5000
        max-initial-line-length: 4096
```

#### 7.2.1 自定义EventLoop线程数

```yaml
# 通过reactor.netty配置
reactor:
  netty:
    io:
      worker-count: 8          # Worker线程数（默认CPU*2）
```

```java
// 编程式自定义
@Bean
public NettyReactiveWebServerFactory nettyReactiveWebServerFactory() {
    NettyReactiveWebServerFactory factory = new NettyReactiveWebServerFactory();
    factory.addServerCustomizers(server -> server
        .runOn(LoopResources.create(
            "gateway-worker",     // 线程名前缀
            2,                    // boss线程数
            8,                    // worker线程数
            true                  // daemon
        ))
    );
    return factory;
}
```

### 7.3 Gateway连接池类型

| 类型 | 说明 | 适用场景 |
|------|------|----------|
| `elastic`（默认） | 连接数无上限，空闲连接自动回收 | 大多数场景 |
| `fixed` | 固定最大连接数 | 需要控制连接数的场景 |

```yaml

      httpclient:
        pool:
          type: fixed

          acquire-timeout: 45000     # 获取连接超时
```

### 7.6 Gateway线程阻塞排查

>  **Gateway常见的性能问题就是EventLoop线程被阻塞**，导致网关吞吐量急剧下降。

#### 7.6.1 阻塞操作示例（禁止！）

```java
@Component
public class BlockingFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        // 错误：在EventLoop线程中执行阻塞操作！
        String result = restTemplate.getForObject("http://service/api", String.class);

        // 正确：使用异步调用
        return WebClient.create()
            .get()
            .uri("http://service/api")
            .retrieve()
            .bodyToMono(String.class)
            .flatMap(data -> {
                exchange.getAttributes().put("data", data);
                return chain.filter(exchange);
            });
    }
}
```

## 8. 高频踩坑与误区

>  性能调优中常见的误区和陷阱，熟练掌握可以避免线上故障

### 8.1 常见问题汇总

| 序号 | 问题 | 现象 | 原因 | 解决方案 |
|------|------|------|------|----------|
| 1 | JVM参数不生效 | jinfo检查显示默认值 | 参数位置错误或优先级被覆盖 | 使用jinfo -flag验证，确保参数在java命令最前面 |
| 2 | 连接池爆满 | 应用卡死，大量连接超时 | 连接泄漏或连接数过小 | 开启leakDetectionThreshold，检查代码中的连接管理 |
| 3 | Feign超时与连接池混用 | 调用超时不稳定，有时快有时慢 | Feign超时、Hystrix超时、Ribbon超时三层混用 | 理解三层超时关系，统一配置 |
| 4 | Redis连接耗尽 | Redis操作超时，获取连接失败 | 连接池过小或慢查询阻塞 | 增大连接池，优化慢查询，使用Pipeline |
| 5 | Gateway线程阻塞 | 网关响应变慢，TP99急剧上升 | EventLoop线程执行了阻塞操作 | 使用WebClient代替RestTemplate，阻塞操作放到独立线程池 |
| 6 | 元空间溢出 | Metaspace OOM | 类加载过多（动态代理、CGlib） | 增大-XX:MaxMetaspaceSize |
| 7 | 直接内存泄漏 | OOM但堆使用率低 | NIO/DirectBuffer未释放 | 使用-XX:MaxDirectMemorySize限制，排查Netty/Buffer使用 |

### 8.2 踩坑详解

#### 8.2.1 坑1：JVM参数不生效

```bash
# 错误示例
java -jar myapp.jar -Xms4g -Xmx4g    # 参数在-jar后面，不生效！

# 正确写法
java -Xms4g -Xmx4g -jar myapp.jar   # 参数在-jar前面

# 验证
jps -lv | grep myapp                  # 查看实际生效参数
jinfo -flag MaxHeapSize <pid>         # 查看MaxHeapSize
```

>  **规则**：JVM参数必须在`-jar`之前，`-jar`之后的参数会传递给Spring Boot（作为program arguments），JVM不会读取。

#### 8.2.2 坑2：连接池爆满

```text
现象：
- 应用日志大量出现"Cannot acquire connection from POOL"或"Connection is not available"
- 请求响应变慢，最终超时
- 数据库负载不高，但应用端连接池满了

原因（前3个占80%案例）：
1. 代码中获取连接后忘记释放（最常⻅）
2. 事务中处理时间过长，连接被长期占用
3. 慢SQL导致连接长时间不释放
4. 连接池maxActive设置过小
5. 数据库端连接被防火墙/NGFW主动断开，客户端未感知
```

```yaml
# 预防方案
spring:
  datasource:
    hikari:
      leakDetectionThreshold: 60000   # 开启泄漏检测
      maxLifetime: 1200000            # 小于数据库wait_timeout
      keepaliveTime: 60000            # 心跳检测
      validationTimeout: 3000
```

#### 8.2.3 坑3：Feign超时三层混用

Feign调用涉及三层超时，容易混淆：

```
Feign调用链路
应用层 -> Feign客户端 -> Ribbon负载均衡 -> HTTP客户端 -> 目标服务

三层超时：
1. Feign超时：feign.client.config.default.readTimeout
2. Ribbon超时：ribbon.ReadTimeout
3. Hystrix超时：hystrix.command.default.execution.isolation.thread.timeoutInMilliseconds

关系：Hystrix超时 > Ribbon超时 + 重试时间 > Feign超时
```

```yaml
# 正确配置示例
feign:
  client:
    config:
      default:
        connectTimeout: 3000    # 连接超时
        readTimeout: 5000       # 读取超时

ribbon:
  ConnectTimeout: 3000          # 必须和Feign一致
  ReadTimeout: 5000             # 必须和Feign一致
  MaxAutoRetries: 1             # 最大重试次数
  MaxAutoRetriesNextServer: 1   # 切换实例重试

hystrix:
  command:
    default:
      execution:
        isolation:
          thread:
            timeoutInMilliseconds: 10000  # 必须 > Feign超时*(1+重试次数)
```

#### 8.2.4 坑4：Redis连接耗尽

```text
现象：
- redis.clients.jedis.exceptions.JedisConnectionException: Could not get a resource from the pool
- Lettuce: Unable to acquire connection from pool
- 应用Redis操作响应变慢

原因：
1. 连接池max-active太小，无法应对流量高峰
2. Redis慢命令（KEYS *、SMEMBERS大集合、ZRANGE大区间）
3. 大Value操作导致网络传输延迟
4. 未使用Pipeline批量操作
5. Redis服务器maxclients限制

排查：
1. 监控连接池active/idle曲线
2. 开启Redis slowlog
3. 记录Redis命令执行时间
```

```bash
# Redis慢日志查看
redis-cli SLOWLOG GET 10
redis-cli SLOWLOG LEN
redis-cli CONFIG SET slowlog-log-slower-than 10000  # 设置慢查询阈值(微秒)
```

#### 8.2.5 坑5：Gateway线程阻塞

```text
现象：
- Gateway响应越来越慢，最终大量超时
- CPU使用率不高但TPS很低
- 其他服务正常，只有Gateway异常

排查：
1. jstack查看reactor-http线程状态
2. 如果大量reactor-http线程在BLOCKED/WAITING状态
3. 检查代码中是否使用了RestTemplate/DB查询等阻塞操作

预防：
1. Gateway中始终使用WebClient而非RestTemplate
2. 阻塞操作放到@Async线程池
3. 使用Hystrix/Sentinel做线程隔离
```

```java
// 错误：阻塞EventLoop线程
@Bean
public GlobalFilter badGatewayFilter() {
    return (exchange, chain) -> {
        String result = restTemplate.getForObject("http://service/api", String.class);
        return chain.filter(exchange);
    };
}

// 正确：使用WebClient异步调用
@Bean
public GlobalFilter goodGatewayFilter(WebClient webClient) {
    return (exchange, chain) ->
        webClient.get()
            .uri("http://service/api")
            .retrieve()
            .bodyToMono(String.class)
            .flatMap(result -> chain.filter(exchange));
}
```

### 8.3 误区总结

| 误区 | 正解 |
|------|------|
| 线程池越大越好 | 超过最佳值后吞吐量下降（上下文切换） |
| 连接池越大越好 | 小连接池有时比大连接池更快（数据库并发有限） |
| GC暂停时间设得越小越好 | 过小导致GC频繁，降低吞吐量 |
| Xms和Xmx可以不等 | 必须相等，避免Full GC调整堆大小 |
| 默认GC参数够用 | 需要根据硬件和场景调整 |
| Gateway可以像WebMVC那样写 | Gateway是响应式模型，不能使用阻塞操作 |
| 调优一次永久有效 | 业务变化后需要重新评估和调优 |

### 13.2 JDK 21+ Generational ZGC

JDK 21的**分代ZGC**是ZGC的重大升级：

| 特性 | ZGC | Generational ZGC |
|------|-----|-----------------|
| 分代 | 不分代 | 年轻代+老年代 |

### 13.3 Virtual Threads对线程池调优的影响

JDK 21的Virtual Threads（虚拟线程）彻底改变了Java并发模型，对传统线程池调优产生了深远影响：

#### 13.3.1 传统模型 vs 虚拟线程

```text
传统线程模型（Platform Thread）：
- 线程 = OS线程（1:1映射），数量受限（~1000~5000）
- 线程池大小需要精确调优
- 上下文切换开销大

虚拟线程模型（Virtual Thread）：
- 线程 = JVM管理，数量巨大（百万级）
- 无需线程池，每个请求一个虚拟线程
- 挂起几乎无开销
```

#### 13.3.2 对Tomcat调优的影响

```yaml
# Tomcat + 虚拟线程（Spring Boot 3.2+）
server:
  tomcat:
    threads:
      max: 0                    # 设置为0表示使用虚拟线程
      # 或者不设置，启用虚拟线程后Tomcat会自动使用
```

```java
@Configuration
public class TomcatConfig {

    @Bean
    public TomcatProtocolHandlerCustomizer<?> protocolHandlerCustomizer() {
        return handler -> {
            handler.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
        };
    }
}
```

```yaml

```

#### 13.3.3 对HikariCP调优的影响

虚拟线程环境下，连接池调优策略变化不大，因为数据库连接是真实资源。


#### 2.13.2 使用MAT分析堆Dump的步骤

```text
1. 生成堆Dump
   jcmd <pid> GC.heap_dump /tmp/dump.hprof

2. 用MAT打开
   - File -> Open Heap Dump -> 选择dump.hprof

4. 分析技巧

   - Top Consumers: 按包/类加载器汇总内存使用
   - OQL: 使用类似SQL的语法查询对象

   - Thread Overview: 查看线程栈中的局部变量
```

#### 2.13.3 常见内存泄漏模式

| 泄漏模式 | 现象 | 诊断方法 | 修复方案 |
|----------|------|----------|----------|
| ThreadLocal未清理 | 线程池中的线程持有大对象 | 查看线程栈中的ThreadLocalMap | 用完后调用remove() |
| 静态集合无限增长 | 堆中某个HashMap/ArrayList持续增长 | Dominator Tree查看最大对象 | 改用缓存（Caffeine）或限制大小 |
| 类加载器泄漏 | 元空间持续增长（Tomcat热部署） | 查看类加载器创建数量 | 避免重复创建ClassLoader |
| 回调/监听器未注销 | 观察者模式中的被观察者持有大量监听器 | 查看集合中的Listener数量 | 在destroy时注销 |
| 连接/流未关闭 | IO/DB连接未关闭 | 查看socket/connection对象 | try-with-resources |
| 内部类持有外部引用 | 非静态内部类持有外部类引用 | 查看内部类实例 | 改为静态内部类 |

### 2.14 JIT编译器调优

>  JIT（Just-In-Time）编译器对Java应用性能有重要影响，理解JIT可以帮助我们写出更容易被优化的代码。

#### 2.14.1 JIT编译层次

```text
Java代码执行过程：
.java -> .class (字节码) -> 解释执行 -> 热点代码 -> C1编译（客户端）-> C2编译（服务端）

- 解释执行：启动快，但性能低
- C1编译：快速优化，适合启动阶段
- C2编译：深度优化，适合长时间运行
- 分层编译（JDK 8+默认）：先C1后C2，兼顾启动和峰值性能
```

#### 2.14.2 JIT相关参数

| 参数 | 说明 | 默认值 | 建议 |
|------|------|--------|------|
| `-XX:+PrintCompilation` | 打印编译信息 | 关闭 | 开启（诊断用） |
| `-XX:CompileThreshold` | C2编译阈值 | 10000 | 默认即可 |
| `-XX:TieredCompilation` | 分层编译 | 开启 | 开启（默认） |
| `-XX:ReservedCodeCacheSize` | 代码缓存 | 240M | 256M~512M |
| `-XX:+UseCounterDecay` | 方法调用计数衰减 | 开启 | 关闭（-XX:-UseCounterDecay，长时间运行服务） |

```bash
# 查看JIT编译情况
-XX:+PrintCompilation                       # 打印编译的方法
-XX:+UnlockDiagnosticVMOptions              # 解锁诊断参数
-XX:+PrintInlining                          # 打印内联信息

# 输出示例
java.lang.String::hashCode (55 bytes)   made not entrant
java.lang.String::equals (79 bytes)     made not entrant
java.lang.String::hashCode (55 bytes)   made not entrant
java.util.HashMap::get (368 bytes)
java.util.HashMap::put (378 bytes)
```

#### 2.14.3 编写对JIT友好的代码

```java
// 1. 方法不要太大（< 325字节码），便于内联
// 2. 热点方法要小，频繁调用的方法内联后性能提升明显
// 3. 避免过于复杂的继承层次（虚方法分派影响内联）
// 4. 使用接口编程，但避免在热点路径上频繁做instanceof
// 5. final方法更容易被内联

// 好的示例：小方法，频繁调用，容易内联
public int add(int a, int b) {
    return a + b;  // 小方法，JIT容易内联
}

// 不好的示例：大方法，难以优化
public void processOrder(Order order) {
    // 300行代码...
    // JIT难以内联，编译开销大
}
```

>  💡 **不要过度优化**：大部分情况下，编写清晰的代码，让JIT决定如何优化。只有在对性能敏感的核心路径上才需要考虑JIT友好的代码风格。

### 11.3 精选题型解析

以下为高频面试/笔试题目解析：

#### 题目1：JVM调优

**题目**：一个4C8G的Spring Boot应用，使用ParallelGC，Full GC频繁（每30分钟一次），每次暂停2~5秒。分析原因并给出解决方案。

**解析**：
```text
原因分析：
1. ParallelGC适合高吞吐量，但暂停时间长
2. Full GC频繁通常意味着老年代空间不足
3. 可能存在内存泄漏或堆设置过小

解决方案：
1. 首先检查堆大小：-Xms4g -Xmx4g（固定堆）
2. 考虑切换到G1GC：-XX:+UseG1GC -XX:MaxGCPauseMillis=150
3. 生成堆Dump分析泄漏
4. 检查是否有关键对象持续增长
5. 增大年轻代：-Xmn1536m减少对象晋升
```

#### 题目2：连接池调优

**题目**：一个8C16G的微服务，HikariCP设置maximumPoolSize=50，高峰期出现连接获取超时。dstat显示CPU使用率仅30%，数据库负载正常。如何排查和解决？

**解析**：
```text
排查步骤：
1. 检查连接池监控：active/pending/timeout指标
2. 检查代码中是否有连接泄漏（开启leakDetectionThreshold）
3. 检查慢SQL（数据库slow_log）
4. 检查数据库wait_timeout是否小于maxLifetime

解决方案：
1. 如果存在慢SQL -> 优化SQL，加索引
2. 如果连接泄漏 -> 修复代码，试用try-with-resources
3. 如果连接池过小 -> 适度增大maximumPoolSize
4. 如果数据库连接被服务端断开 -> 调整maxLifetime < wait_timeout
5. 注意：50连接已经较大，检查是否真的是连接数不足
   通常此时应检查SQL性能而不是增大连接池
```

#### 题目3：Tomcat调优

**题目**：一个4C8G的Web应用，设置maxThreads=500，压测发现QPS在200线程时达到峰值（5000 QPS），之后增加线程QPS反而下降。分析原因。

**解析**：
```text
原因：
1. CPU上下文切换：500线程 > 4核*2超线程=8逻辑核，切换开销巨大
2. 锁竞争：线程数过多导致共享资源争用
3. 内存压力：500线程 * 1MB栈 = 500MB，加上堆内存，接近内存上限

解决方案：
1. 设置合理的maxThreads：根据Little's Law计算
   N = N_cpu * (1 + W/S)
   假设W/S=3（普通Web应用），N = 4 * (1+3) = 16
   考虑峰值余量，推荐maxThreads=200
2. 配合accept-count=400，maxConnections=5000
3. 如果仍要处理高并发，考虑：
   a. 增加机器规格
   b. 引入消息队列削峰
   c. 服务拆分为更细粒度
```
