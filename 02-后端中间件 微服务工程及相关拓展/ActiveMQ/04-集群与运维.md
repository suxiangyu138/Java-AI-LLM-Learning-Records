## 1. 主从架构深度对比

### 1.1 Classic 三种主从

| 模式 | 共享方式 | 切换 | 优点 | 缺点 |
|------|---------|:---:|------|------|
| 共享存储 | SAN/NFS | ✅ 自动 | 高可用 | 存储单点 |
| JDBC Master-Slave | 数据库锁 | ✅ 自动 | 已有 DB 复用 | DB 有并发瓶颈 |
| ZooKeeper + LevelDB | ZK 选举 | ✅ 自动 | **生产推荐** | 需 ZK 集群 |

### 1.2 JDBC 主从实现

```xml
<!-- Broker A 与 Broker B 配置完全相同 -->
<broker brokerName="shared-master" ...>
    <persistenceAdapter>
        <jdbcPersistenceAdapter dataSource="#mysql-ds"
                createTablesOnStartup="false" />
    </persistenceAdapter>
</broker>
<!-- 谁先拿到 DB 锁 → Master；锁释放 → 另一个抢到 → 新 Master -->
```

```
⚠️ JDBC 主从的故障切换流程：
  ① Master 宕机 → DB 连接超时 → 锁自动释放
  ② Slave 周期性检查锁 → 发现锁释放 → 获取锁 → 成为新 Master
  ③ 客户端 failover URL → 自动重连新 Master
  切换时间：约 30 秒（等待超时 10s + 锁检测间隔 20s）
```

### 1.3 Artemis HA 配置（推荐）

```yaml
# Artemis broker.xml 中的 HA 配置
<ha-policy>
    <replication>
        <master>
            <check-for-live-server>true</check-for-live-server>
        </master>
    </replication>
</ha-policy>

<!-- 或共享存储 -->
<ha-policy>
    <shared-store>
        <master/>
        <slave>
            <failover-on-shutdown>true</failover-on-shutdown>
        </slave>
    </shared-store>
</ha-policy>
```

### 1.4 主从 vs 集群的选型

| 维度 | 主从 | 集群（Network of Brokers） |
|------|:---:|:---:|
| 目的 | 高可用（容灾） | 负载分担/扩展 |
| 数据 | 共享存储（消息不丢） | 不共享 Queue |
| 适用 | 生产必备 | 跨地域/大数据量 |

## 2. Network of Brokers 网络

### 2.1 静态发现配置

```xml
<!-- Broker A：连接到 B -->
<networkConnectors>
    <networkConnector
        name="brokerA-to-B"
        uri="static:(tcp://broker-b:61616)"
        duplex="false"
        conduitSubscriptions="true"
        networkTTL="3"
        decreaseNetworkConsumerPriority="true"  />
</networkConnectors>
```

```
关键参数：
  duplex=false：单向连接（A 发消息到 B，B 不返回发到 A）
  networkTTL=3：消息转发跳数上限（防无限路由）
  conduitSubscriptions=true：多消费者共享一个 Broker 间连接（减 TCP 开销）
  decreaseNetworkConsumerPriority=true：优先本地消费者（降网络消费者优先级）

⚠️ 核心认知：Network of Brokers 不复制 Queue！
  Queue 消息只在创建它的 Broker 上存在——转发的是"订阅关系"而非数据
```

### 2.2 拓扑模式

```
① Hub-and-Spoke（星型）：
   中心 Broker 连接所有边缘 Broker
   适用：总部分部消息汇总

② Mesh（全网状）：
   每对 Broker 直接连接
   适用：小规模（≤5 节点）

③ 链式：
   A → B → C 线形连接
   适用：地域性链式转发
```

## 3. 安全：认证与授权

### 3.1 JAAS 认证

```java
// login.config：JAAS 配置文件
activemq {
    org.apache.activemq.jaas.PropertiesLoginModule required
        org.apache.activemq.jaas.properties.user="users.properties"
        org.apache.activemq.jaas.properties.group="groups.properties";
};

// users.properties
admin=admin123
producer=pwd123
consumer=pwd456

// groups.properties
admins=admin
producers=producer
consumers=consumer
```

### 3.2 授权（Authorization）

```xml
<!-- broker 中的授权插件配置 -->
<plugins>
    <authorizationPlugin>
        <map>
            <authorizationMap>
                <authorizationEntries>
                    <!-- 管理员：全部权限 -->
                    <authorizationEntry queue=">"
                        read="admins" write="admins" admin="admins" />
                    <!-- 生产者：只能写 -->
                    <authorizationEntry queue="orders.>"
                        write="producers" read="admins,consumers" />
                    <!-- 消费者：只能读 -->
                    <authorizationEntry queue="orders.>"
                        read="consumers" />
                </authorizationEntries>
            </authorizationMap>
        </map>
    </authorizationPlugin>
</plugins>
<!-- ⚠️ 通配符 > 匹配所有（queue.> 匹配 queue.abc、queue.a.b） -->
```

### 3.3 SSL/TLS 传输加密

```xml
<broker>
    <sslContext>
        <sslContext keyStore="file:${activemq.conf}/broker.ks"
                    keyStorePassword="password" />
    </sslContext>
    <transportConnectors>
        <transportConnector name="ssl" uri="ssl://0.0.0.0:61617" />
    </transportConnectors>
</broker>
```

```
⚠️ 安全三件套（面试必答）：
  ① JAAS 认证（用户+角色）
  ② 授权（队列/主题级别的读写管理）
  ③ SSL 加密传输（内网也建议开启）
```

## 4. 监控指标体系

### 4.1 JMX 关键指标

```java
// JMX Bean 指标（可通过 JConsole / Actuator 访问）
// ① 队列深度（最重要的告警指标）
org.apache.activemq:type=Broker,brokerName=*,destinationType=Queue,
    destinationName=orders.queue
  → QueueSize（当前积压消息数）
  → ConsumerCount（消费者数）
  → DequeueCount / EnqueueCount（消费/入队累计）

// ② 内存使用率
org.apache.activemq:type=Broker,brokerName=*
  → MemoryPercentUsage
    ⚠️ 达到 100% = 触发 Producer Flow Control（阻塞生产者）

// ③ 存储使用率
  → StorePercentUsage（磁盘存储）
```

### 4.2 Spring Boot Actuator 集成

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,metrics,jmx
  metrics:
    export:
      jmx:
        enabled: true

  health:
    jms:
      enabled: true          # ⚠️ JMS 连接健康检查
```

```java
// 自定义健康检查
@Component
public class ActiveMQHealthIndicator implements HealthIndicator {

    private final JmsTemplate jms;

    @Override
    public Health health() {
        try {
            jms.execute(session -> null, true);
            return Health.up().build();
        } catch (Exception e) {
            return Health.down().withDetail("error", e.getMessage()).build();
        }
    }
}
```

### 4.3 Prometheus + Grafana 接入

```java
// Micrometer 集成（Boot 3+ 自动）
// 引入 micrometer-jmx 或 micrometer-registry-prometheus
// ActiveMQ JMX 指标 → Micrometer → Prometheus 采集

// 关键告警规则：
// ① QueueSize > 10000 持续 5 分钟 → P1 告警
// ② ConsumerCount = 0 → P0 紧急（消费者全部离线）
// ③ MemoryPercentUsage > 90% → P2 告警
```

## 5. 消息堆积完整排查树

```
消息堆积排查树（按概率排序）：
  ① 消费者数量不够？
     → 增加 concurrency 或扩容实例
  ② 消费者处理慢？
     → JMX 看 DequeueCount 增长速率是否低于 EnqueueCount
     → 优化消费逻辑（慢 SQL/外部调用/无索引）
  ③ 消费者全部停止？
     → ConsumerCount = 0？→ 重启消费者 → 告警！
  ④ 生产者 Flow Control（阻塞）？
     → MemoryPercentUsage = 100%？
     → 扩容 Broker / 限制生产者 / 流控
  ⑤ 消息无人消费？
     → DLQ 持续增长？
     → 原队列无活跃消费者 → 配置检查

⚠️ 面试必答：
"堆积排查 = 消费者数 → 消费速率 → 消费者存活
 → Broker 内存 → 无人消费/DLQ；
 先看 ConsumerCount 是否为 0（是否有活着的消费者）
 再看 QueueSize 增长速率匹配度（处理能力 vs 入队速率）。"
```

## 6. 性能调优参数

```xml
<!-- Classic Broker 性能调优 -->
<broker>
    <!-- ① 内存限制（防止被打爆） -->
    <systemUsage>
        <systemUsage>
            <memoryUsage>
                <memoryUsage percentOfJvmHeap="70" />  <!-- 最大 70% 堆 -->
            </memoryUsage>
            <storeUsage>
                <storeUsage limit="20 gb"/>            <!-- 磁盘上限 -->
            </storeUsage>
            <tempUsage>
                <tempUsage limit="10 gb"/>             <!-- 临时存储 -->
            </tempUsage>
        </systemUsage>
    </systemUsage>

    <!-- ② 异步发送优化（生产者） -->
    <transportConnectors>
        <transportConnector name="openwire"
            uri="tcp://0.0.0.0:61616?maximumConnections=1000" />
    </transportConnectors>

    <!-- ③ 消费者预取（prefetch）：减少网络往返 -->
    <destinationPolicy>
          <!-- Queue：prefetch=1000（一次取 1000 条到消费者内存） -->
          <!-- Topic：prefetch=32766（较大，广播场景一次取多） -->
    </destinationPolicy>
</broker>
```

| 参数 | 作用 | 调优建议 |
|------|------|--------|
| memoryUsage limit | 限制消息内存 | 70% 堆，触发 Flow Control |
| maximumConnections | 连接上限 | 500-1000（过大 → 线程切换多） |
| prefetch | 消费者预取批量 | Queue 100-1000（均衡）、Topic 保持默认 |
| asyncSend | 生产者异步 | 非关键消息开启 |
| optimizeAcknowledge | 批量 ACK | 高吞吐开启（略微损失可靠性） |

```
⚠️ 调优口诀：
  "内存别超 70%、连接 500-1000、
   预取 Queue 要适当（防单消费者霸占）、
   异步发送省时间（关键消息不敢用）。"
```

> 🎯 **核心要点**：运维体系 = **主从三种**（JDBC/ZK/共享存储）+ **Network of Brokers**（不复制 Queue，转发订阅）+ **安全三件套**（JAAS认证/授权/SSL）+ **监控四指标**（QueueSize/ConsumerCount/Memory%/Store%）+ **堆积六步排查树**（消费者数→消费速率→存活→内存→无人消费→DLQ）+ **调优五参数**（内存/连接/预取/异步/批量ACK）。"先看 ConsumerCount 是否为 0"是堆积排查第一直觉。
