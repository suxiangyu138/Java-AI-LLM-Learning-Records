## 2. 消费组模型

### 2.1 核心概念

```text
消费组 = 一组协同消费的消费者实例

消费组内分区分配原则：
  ┌─────────────────────────────────────────────────────┐
  │ 一个 Partition 只能被组内 1 个 Consumer 消费           │
  │ 一个 Consumer 可以消费多个 Partition                   │
  │ 组内 Consumer 数 ≤ Partition 数（多了闲置）             │
  └─────────────────────────────────────────────────────┘

示例：
  Topic: 3 Partitions, Group: 2 Consumers
  ┌───────┐     ┌───────────┐     ┌───────────┐
  │  P0   │────→│ Consumer1 │  →  │           │
  │  P1   │     └───────────┘     │   Group   │
  │  P2   │────→┌───────────┐     │           │
  └───────┘  └─→│ Consumer2 │     └───────────┘
               └───────────┘
```

### 2.2 点对点 vs 发布订阅

```text
【点对点模式】所有消费者在同一个消费组
  → 消息被组内分摊，每条消息只被消费一次
  → 场景：订单处理（一个订单只被一个服务处理）

【发布订阅模式】每个消费者在独立消费组
  → 每条消息广播到所有消费组
  → 场景：用户行为采集（多个系统都需要行为数据）

Group-1: [Consumer A]     ──→ 独立消费所有消息
Group-2: [Consumer B]     ──→ 独立消费所有消息
Group-3: [Consumer C, D]  ──→ 组内分摊消费
```

### 2.3 GroupCoordinator

```text
每个消费组有一个 GroupCoordinator（位于某个 Broker）

GroupCoordinator 职责：
  ✅ 管理消费组成员（加入/离开/心跳）
  ✅ 触发和管理 Rebalance
  ✅ 提交消费位移到 __consumer_offsets
  ✅ 分配分区给组内 Consumer

定位 GroupCoordinator：
  hash(groupId) % __consumer_offsets 分区数 → 该分区 Leader 所在 Broker
```

## 3. Rebalance 详解

### 3.1 触发时机

```text
Rebalance 触发条件：
  1. 组内 Consumer 数量变化（加入/离开/宕机）
  2. 订阅的 Topic 分区数变化
  3. 订阅的 Topic 被创建/删除
  4. 订阅方式变更（subscribe → assign）
```

### 3.2 Rebalance 流程（Eager 协议）

```text
经典 Rebalance 流程 — "先全部停止，再重新分配"

Phase 1: FIND_COORDINATOR
  Consumer → Broker → 找到 GroupCoordinator

Phase 2: JOIN_GROUP
  所有 Consumer → GroupCoordinator → 选举 Leader Consumer
                                      (第一个加入组的)

Phase 3: SYNC_GROUP
  Leader Consumer → 制定分配方案 → 发送给GroupCoordinator
  GroupCoordinator → 将分配结果广播给所有 Consumer
  
Phase 4: 开始消费
  每个 Consumer → 根据分配结果 → 开始消费

问题：STW（Stop-The-World）
  所有 Consumer 暂停消费 → 重新分配 → 恢复
```

### 3.3 渐进式 Rebalance（Cooperative / Incremental）

```text
Kafka 2.4+ 引入（推荐使用）

与 Eager 的区别：
  ┌──────────────┬──────────────────┬────────────────────┐
  │  特性         │  Eager            │  Cooperative       │
  ├──────────────┼──────────────────┼────────────────────┤
  │  暂停范围     │  全部 Consumer    │  仅受影响的 Consumer │
  │  暂停时间     │  长（全部重分配）  │  短（增量调整）     │
  │  STW          │  严重             │  轻微              │
  │  分配效率     │  低               │  高                │
  └──────────────┴──────────────────┴────────────────────┘

配置：
  partition.assignment.strategy=
    org.apache.kafka.clients.consumer.CooperativeStickyAssignor
```

### 3.4 分区分配策略

| 策略 | 规则 | 适用场景 |
|------|------|----------|
| **Range**（默认） | 按 Topic 逐个分配，Partition 数 / Consumer 数 | 通用 |
| **RoundRobin** | 所有 Partition 轮询分配 | 尽量平均 |
| **Sticky** | 保持上次分配 + 最小变动 | 避免大规模 Rebalance |
| **CooperativeSticky** | Sticky + 渐进式 Rebalance | **生产推荐** |

```text
Range 分配示例（Topic: t1[P0,P1,P2], t2[P0,P1]; 2 Consumers）：
  Consumer 1: t1-P0, t1-P1, t2-P0 → 不均！(3个)
  Consumer 2: t1-P2, t2-P1        → (2个)

Sticky 分配示例：
  Consumer 1 宕机前: t1-P0, t1-P1
  Consumer 2 宕机前: t1-P2, t2-P0
  Consumer 3 宕机前: t2-P1
  → Consumer 3 宕机 → 仅 t2-P1 移给 Consumer 1，其余不变
```

## 4. 位移（Offset）管理

### 4.1 Offset 存储位置

```text
位移存储位置：
  ┌────────────────────────────────────────────────┐
  │  Old (≤0.9): ZooKeeper                         │
  │  New (≥0.10): __consumer_offsets（内部 Topic）   │
  └────────────────────────────────────────────────┘

__consumer_offsets 特点：
  ✅ Kafka 自带，无需外部依赖
  ✅ compact 策略（只保留每个 Key 的最新 Value）
  ✅ 默认 50 个分区
```

### 4.2 三种提交方式

```java
// 1. 自动提交（最简单，可能丢/重消息）
props.put("enable.auto.commit", "true");
props.put("auto.commit.interval.ms", "5000"); // 每5秒自动提交

// 2. 同步提交（可靠，但阻塞）
consumer.commitSync();                    // 提交当前位移
consumer.commitSync(offsetMap);           // 指定偏移量

// 3. 异步提交（高吞吐，不阻塞）
consumer.commitAsync((offsets, exception) -> {
    if (exception != null) {
        log.error("提交失败: {}", offsets, exception);
    }
});
```

### 4.3 提交策略对比

| 方式 | 吞吐 | 可靠性 | 重复消费风险 | 适用场景 |
|------|:---:|:---:|:---:|------|
| **自动提交** | 高 | 低 | 高 | 非关键数据 |
| **同步提交** | 低 | 高 | 低 | 关键业务 |
| **异步提交** | 高 | 中 | 中 | 高吞吐 |
| **混合提交** | 中 | 高 | 低 | **生产推荐** |

```java
// 混合提交（生产推荐）
try {
    while (true) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
        for (ConsumerRecord<String, String> record : records) {
            // 处理消息
            process(record);
        }
        // 先异步提交
        consumer.commitAsync();
    }
} catch (Exception e) {
    log.error("消费异常", e);
} finally {
    try {
        // close 前同步提交，确保不丢位移
        consumer.commitSync();
    } finally {
        consumer.close();
    }
}
```

### 4.4 位移重置

```bash
# 消费组位移重置（三种重置策略）

# earliest — 从最早开始
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group my-group --topic my-topic \
  --reset-offsets --to-earliest --execute

# latest — 从最新开始（跳过历史）
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group my-group --topic my-topic \
  --reset-offsets --to-latest --execute

# datetime — 按时间重置
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group my-group --topic my-topic \
  --reset-offsets --to-datetime 2026-07-01T00:00:00.000 --execute

# shift-by — 前后移动
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group my-group --topic my-topic \
  --reset-offsets --shift-by -100 --execute  # 回退 100 条
```

**重置触发条件（auto.offset.reset）：**

| 值 | 行为 | 场景 |
|------|------|------|
| `latest`（默认） | 从最新开始，忽略历史 | 新消费组不关心旧数据 |
| `earliest` | 从最早开始，全量消费 | 首次启动需要全量数据 |
| `none` | 没找到位移 → 抛异常 | 不希望自动重置 |

## 5. 消费模式与语义

### 5.1 三种交付语义

```text
最多一次（At-Most-Once）：
  先提交位移 → 再处理消息
  风险：处理失败但位移已提交 → 消息丢失

至少一次（At-Least-Once）：
  先处理消息 → 再提交位移
  风险：处理成功后提交失败 → 消息重复
  ✅ Kafka 默认保证（推荐）

精确一次（Exactly-Once）：
  消息处理 + 位移提交 = 原子操作
  实现方式：
    ① Kafka → Kafka：事务 Producer + 事务 Consumer
       isolation.level=read_committed
    ② Kafka → DB：两阶段提交 / 出去表模式
```

### 5.2 At-Least-Once 实现要点

```java
// 标准 At-Least-Once 模式
records.forEach(record -> {
    processMessage(record);      // ① 处理消息（要幂等）
});
consumer.commitSync();          // ② 提交位移（可能失败 → 重复消费）

// 关键：业务处理必须是幂等的！
// 例如：数据库 INSERT → INSERT ... ON DUPLICATE KEY UPDATE
//       Redis SET → 天然幂等
//       发送 RPC → 需要业务层防重
```

### 5.3 Exactly-Once（Kafka → Kafka）

```java
// 消费 → 处理 → 生产（事务保证原子性）
props.put("isolation.level", "read_committed"); // 只读已提交的事务消息

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(consumerProps);
KafkaProducer<String, String> producer = new KafkaProducer<>(producerProps);
producer.initTransactions();

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));
    
    // 开启事务
    producer.beginTransaction();
    try {
        for (ConsumerRecord<String, String> record : records) {
            producer.send(new ProducerRecord<>("output-topic", record.value()));
        }
        // 位移提交也用事务
        Map<TopicPartition, OffsetAndMetadata> offsets = buildOffsets(records);
        producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());
        
        producer.commitTransaction(); // 原子提交：消息 + 位移
    } catch (Exception e) {
        producer.abortTransaction();
    }
}
```

## 6. Java 消费者实战

```java
import org.apache.kafka.clients.consumer.*;
import java.time.Duration;
import java.util.*;

public class ReliableConsumer {
    public static void main(String[] args) {
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "my-group");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
                "org.apache.kafka.common.serialization.StringDeserializer");
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
                "org.apache.kafka.common.serialization.StringDeserializer");
        
        // 位移管理
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);  // 手动提交
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        
        // Rebalance
        props.put(ConsumerConfig.PARTITION_ASSIGNMENT_STRATEGY_CONFIG,
                "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");
        
        // 性能
        props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 500);       // 单次拉取条数
        props.put(ConsumerConfig.FETCH_MAX_BYTES_CONFIG, 52428800);   // 50MB
        props.put(ConsumerConfig.MAX_PARTITION_FETCH_BYTES_CONFIG, 1048576); // 1MB

        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
            consumer.subscribe(Collections.singletonList("my-topic"),
                    new ConsumerRebalanceListener() {
                @Override
                public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
                    // 再均衡前：提交位移
                    consumer.commitSync();
                }
                @Override
                public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
                    // 再均衡后：可做初始化
                    System.out.println("Assigned: " + partitions);
                }
            });

            while (true) {
                ConsumerRecords<String, String> records =
                        consumer.poll(Duration.ofMillis(1000));
                for (ConsumerRecord<String, String> record : records) {
                    System.out.printf("topic=%s, partition=%d, offset=%d, key=%s, value=%s%n",
                            record.topic(), record.partition(),
                            record.offset(), record.key(), record.value());
                    processBusiness(record);
                }
                // 批量处理完后异步提交
                consumer.commitAsync();
            }
        } catch (Exception e) {
            // 重平衡/网络异常...
            e.printStackTrace();
        }
    }
    
    private static void processBusiness(ConsumerRecord<String, String> record) {
        // 幂等的业务处理逻辑
    }
}
```

## 7. 最佳实践与常见问题

### 7.1 consumer.poll() 陷阱

```text
🚨 max.poll.interval.ms（默认 5 分钟）
  poll() 间隔 > 5 分钟 → 被认为宕机 → Rebalance

✅ 如果单条消息处理慢：
  → 减小 max.poll.records（默认 500）
  → 或增大 max.poll.interval.ms

✅ 如果周期性慢（批量操作）：
  → 暂停分区：consumer.pause(partitions)
  → 处理完后：consumer.resume(partitions)
```

### 7.2 消费积压（Lag）处理

```bash
# 查看消费积压
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group my-group

# 输出：
# GROUP    TOPIC     PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# my-group my-topic  0          105             9500            9395  ← 积压！
```

**积压处理方案：**

| 方案 | 操作 | 时效 |
|------|------|:---:|
| **增加 Consumer** | 最多加到 `Partition 数` | 分钟级 |
| **增加 Partition** | `kafka-topics.sh --alter --partitions N` | 分钟级 |
| **优化消费逻辑** | 减少 DB 操作、加缓存、异步化 | 取决于改造 |
| **临时跳过** | 重置 Offset 到 latest | 秒级（丢数据） |

### 7.3 消费者关键配置速查

| 参数 | 默认值 | 推荐值 | 说明 |
|------|--------|--------|------|
| `group.id` | — | 语义化命名 | 消费组 ID |
| `enable.auto.commit` | true | **false** | 手动提交位移 |
| `auto.offset.reset` | latest | earliest/latest | 无位移时的行为 |
| `max.poll.records` | 500 | 100~500 | 单次拉取最大条数 |
| `max.poll.interval.ms` | 300000 (5min) | 300000 | 两次 poll 最大间隔 |
| `session.timeout.ms` | 45000 (45s) | 30000 | 会话超时 |
| `heartbeat.interval.ms` | 3000 | 3000 | 心跳间隔 |
| `partition.assignment.strategy` | Range | **CooperativeSticky** | 分配策略 |

### 7.4 常见故障排查

| 问题 | 原因 | 解决 |
|------|------|------|
| 频繁 Rebalance | poll 处理慢、GC 暂停 | 调大 `max.poll.interval.ms`、减少 `max.poll.records` |
| 消费停止 | Consumer 太慢被踢出组 | 同上，注意心跳配置 |
| 积压增加 | 生产 > 消费 | 增加消费者或优化逻辑 |
| 消息重复 | 消费后提交前宕机 | 业务逻辑做幂等 |
| 消息丢失 | 自动提交 + 处理失败 | 改为手动提交 |
| Consumer 加入不生效 | 消费者数 > 分区数 | 增加分区数 |
