## 1. 生产者架构

```text
KafkaProducer 内部结构

┌─────────────────────────────────────────────────────────────┐
│  KafkaProducer.send(record)                                 │
│  ┌─────────────────────────────────────────────────────────┐│
│  │  Serializer (Key + Value) → 序列化为 byte[]              ││
│  └────────────────────┬────────────────────────────────────┘│
│  ┌────────────────────▼────────────────────────────────────┐│
│  │  Partitioner → 根据 Key/策略选择目标 Partition             ││
│  └────────────────────┬────────────────────────────────────┘│
│  ┌────────────────────▼────────────────────────────────────┐│
│  │  RecordAccumulator（记录累加器）                           ││
│  │  ┌──────────┬──────────┬──────────┐                     ││
│  │  │ Batch 0  │ Batch 1  │ Batch 2  │  ← 每个 Partition     ││
│  │  │ (P0)     │ (P1)     │ (P2)     │     一个 Deque<Batch> ││
│  │  └──────────┴──────────┴──────────┘                     ││
│  └────────────────────┬────────────────────────────────────┘│
│  ┌────────────────────▼────────────────────────────────────┐│
│  │  Sender 线程（独立线程，异步发送）                           ││
│  │  → 按 Broker 聚合 Batch → 发送 → 处理响应 → 重试           ││
│  └─────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
```

| 组件 | 职责 |
|------|------|
| **Serializer** | 将 Key/Value 对象序列化为字节数组 |
| **Partitioner** | 决定消息发往哪个 Partition |
| **RecordAccumulator** | 批量缓冲区，每个 Partition 一个 Deque 存放 Batch |
| **Sender** | 独立 I/O 线程，从 Accumulator 捞出 Batch 发送到 Broker |
| **Interceptor** | 拦截器链，可以在序列化前后处理消息 |

## 2. 分区策略

### 2.1 默认分区策略

```java
// Kafka 3.x 默认：Sticky Partition（粘性分区）

场景一：指定了 Key
  → hash(key) % numPartitions → 相同 Key 到同一分区

场景二：未指定 Key
  // Kafka 2.4 之前：Round-Robin（轮询）
  // Kafka 2.4 之后：Sticky（粘性）
  → 一个 Batch 填满后再切到下一个 Partition
  → 优点：减少网络请求，提升吞吐
```

### 2.2 分区策略对比

| 策略 | 规则 | 优点 | 缺点 |
|------|------|------|------|
| **Hash（默认）** | `hash(key) % N` | 消息保序 | Hash 不均可倾斜 |
| **Round-Robin** | 逐条轮询 | 绝对均衡 | 不保序、频繁切换 |
| **Sticky** | 粘住 Batch，满了再换 | 吞吐高、一定均衡 | 微延迟 |
| **自定义** | 实现 `Partitioner` | 灵活 | 需维护 |

### 2.3 自定义分区器

```java
public class MyPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        // 获取 topic 的分区数
        List<PartitionInfo> partitions = cluster.partitionsForTopic(topic);
        int numPartitions = partitions.size();

        if (keyBytes == null) {
            // 无 Key：随机
            return ThreadLocalRandom.current().nextInt(numPartitions);
        }
        // 有 Key：Hash
        return Math.abs(Utils.murmur2(keyBytes)) % numPartitions;
    }
}
```

## 3. 发送流程与批量机制

### 3.1 两种发送方式

```java
// 1. 异步发送（推荐）
producer.send(record, new Callback() {
    @Override
    public void onCompletion(RecordMetadata metadata, Exception e) {
        if (e != null) {
            log.error("发送失败", e);
        } else {
            log.info("发送成功: topic={}, partition={}, offset={}",
                metadata.topic(), metadata.partition(), metadata.offset());
        }
    }
});

// 2. 同步发送（低吞吐，一般不用）
RecordMetadata meta = producer.send(record).get(); // 阻塞等待
```

### 3.2 批量参数详解

```text
┌─────────────────────────────────────────────────────────┐
│ RecordAccumulator（默认 32MB）                            │
│                                                         │
│  每个 Partition 一个 Deque<ProducerBatch>：              │
│  ┌─────────────────────────────────────────────────┐    │
│  │ Batch (16KB) │ Batch (16KB) │ Batch (16KB) │... │    │
│  └─────────────────────────────────────────────────┘    │
│               ↑                                         │
│         当前活跃 Batch（未满，等待更多消息）               │
└─────────────────────────────────────────────────────────┘

发送时机（满足任一即发送）：
  ✅ batch.size=16384（默认 16KB）Bath 填满
  ✅ linger.ms=0（等待时间），有消息立即发
  ✅ buffer.memory 满了 → block.on.buffer.full 控制阻塞/抛异常
  ✅ max.block.ms=60000 超时 → 抛 TimeoutException
```

| 参数 | 默认值 | 建议值 | 说明 |
|------|--------|--------|------|
| `batch.size` | 16384 (16KB) | 16KB~64KB | 批次大小，过小吞吐低 |
| `linger.ms` | 0 | 1~10 | 等待时间，增加可提升批量率 |
| `buffer.memory` | 32MB | 64~128MB | 缓冲区总内存 |
| `max.block.ms` | 60000 | 60000 | send 阻塞的最大时间 |
| `compression.type` | none | lz4 / zstd | 压缩算法（snappy/lz4/zstd/gzip） |

> 💡 权衡公式：**linger.ms ↑ → 延迟 ↑、吞吐 ↑**。低延迟场景设 0，高吞吐场景设 5~10ms。

## 4. ACK 与可靠性保障

### 4.1 ACK 三种模式

```text
acks = 0（最多一次 — 不管成功与否）
  Producer ──发──→ Broker（不等待确认，不重试）
  风险：消息可能丢失
  场景：日志采集等可容忍少量丢失

acks = 1（至少一次 — Leader 确认就行）
  Producer ──发──→ Leader ──响应──→ Producer
  风险：Leader 确认后宕机、Follower 未同步 → 消息丢失
  场景：默认值、平衡可靠性与延迟

acks = all / -1（精确一次 — 所有 ISR 确认）
  Producer ──发──→ Leader ──→ 等待所有 ISR 副本同步
           ←────────── 全部确认后响应 ←────────
  风险：延迟高、min.insync.replicas 影响可用性
  场景：金融/支付等不允许丢消息的业务
```

### 4.2 配合参数：min.insync.replicas

```text
acks=all 需要至少 min.insync.replicas 个副本确认才算成功

配置示例：
  replication.factor = 3
  min.insync.replicas = 2
  acks = all

情况：
  ✅ 正常：Leader + 至少 1 个 Follower 确认 → 写入成功
  ❌ 仅 Leader 活着：ISR=1 < min.insync.replicas=2 → NotEnoughReplicasException

推荐配置：
  replication.factor = 3
  min.insync.replicas = 2  ← 允许宕 1 台不影响写入
  acks = all
```

### 4.3 可靠性矩阵

| | acks=0 | acks=1 | acks=all |
|---|---|---|---|
| **吞吐** | 最高 | 中等 | 最低 |
| **延迟** | 最低 | 中等 | 最高 |
| **持久性** | ❌ 不保证 | ⚠️ Leader 确认 | ✅ ISR 都确认 |
| **丢失风险** | 高 | 中 | 低（配合 min.insync.replicas） |
| **适用场景** | 日志/监控 | 一般业务 | 金融/交易 |

## 5. 幂等性与事务

### 5.1 幂等生产者（Idempotent Producer）

```text
问题：acks=1 + retries>0 → 网络抖动导致重试 → 消息重复

解决：enable.idempotence=true
  │
  ├── Producer 维护 Producer ID (PID) + Sequence Number
  ├── 每条消息带 <PID, Partition, SeqNumber>
  └── Broker 端去重：相同 PID + Partition + 连续 Seq → 只写一次

限制：
  ❌ 只能保证单分区内幂等（单连接内）
  ❌ 跨 Session（重启）不保证（新 PID）
```

```java
Properties props = new Properties();
props.put("enable.idempotence", "true");  // 开启幂等
// 幂等模式下必须设置：
//   max.in.flight.requests.per.connection ≤ 5
//   retries > 0
//   acks = all
```

### 5.2 事务（Transactions）

```text
场景：跨分区、跨 Topic 的原子写入

"要么全成功，要么全失败" — 类似数据库事务

实现原理：
  ┌──────────────────────────────┐
  │  Transaction Coordinator     │ ← 特殊的内部 Topic
  │  (全局事务管理器)              │
  └──────┬───────────────────────┘
         │ 管理 Transaction Log
    ┌────┴────┐
    │  Producer │ ← transactional.id 标识
    └──────────┘
```

```java
// 事务生产者
Properties props = new Properties();
props.put("transactional.id", "my-transactional-id"); // 全局唯一
props.put("enable.idempotence", "true");

KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();  // 初始化事务

try {
    producer.beginTransaction();
    producer.send(new ProducerRecord<>("topic-A", "key1", "v1"));
    producer.send(new ProducerRecord<>("topic-B", "key2", "v2"));
    producer.commitTransaction();  // 原子提交
} catch (Exception e) {
    producer.abortTransaction();   // 原子回滚
}
```

### 5.3 幂等 vs 事务

| 维度 | 幂等 Producer | 事务 Producer |
|------|:---:|:---:|
| **粒度** | 单分区 | 跨分区/跨 Topic |
| **语义** | 不重复 | 原子写入 |
| **性能开销** | 很小 | 中等 |
| **跨 Session** | ❌（重启后新 PID） | ❌（重启后新 transactional.id） |
| **依赖** | 无 | 需要幂等 + transactional.id |

## 6. 生产者关键配置

```properties
# ========== 必配项 ==========
bootstrap.servers=broker1:9092,broker2:9092,broker3:9092
key.serializer=org.apache.kafka.common.serialization.StringSerializer
value.serializer=org.apache.kafka.common.serialization.StringSerializer

# ========== 可靠性 ==========
acks=all                                          # all / 1 / 0
enable.idempotence=true                            # 幂等
retries=2147483647                                 # 最大重试次数（MAX_INT）
max.in.flight.requests.per.connection=5            # 幂等模式 ≤ 5

# ========== 吞吐 ==========
batch.size=32768                                   # 32KB
linger.ms=5                                        # 等 5ms 积攒
buffer.memory=67108864                             # 64MB
compression.type=lz4                               # 压缩

# ========== 超时 ==========
request.timeout.ms=30000                           # 请求超时
delivery.timeout.ms=120000                         # 发送总超时（含重试）
max.block.ms=60000                                 # send 阻塞超时
```

## 7. Java 生产者实战

```java
import org.apache.kafka.clients.producer.*;
import java.util.Properties;

public class ReliableProducer {
    public static void main(String[] args) {
        Properties props = new Properties();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
                "org.apache.kafka.common.serialization.StringSerializer");
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
                "org.apache.kafka.common.serialization.StringSerializer");
        
        // 可靠性配置
        props.put(ProducerConfig.ACKS_CONFIG, "all");
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
        
        // 吞吐配置
        props.put(ProducerConfig.BATCH_SIZE_CONFIG, 32768);
        props.put(ProducerConfig.LINGER_MS_CONFIG, 5);
        props.put(ProducerConfig.COMPRESSION_TYPE_CONFIG, "lz4");

        try (KafkaProducer<String, String> producer = new KafkaProducer<>(props)) {
            for (int i = 0; i < 100; i++) {
                ProducerRecord<String, String> record = new ProducerRecord<>(
                        "my-topic",
                        "key-" + i,     // Key
                        "value-" + i     // Value
                );
                
                producer.send(record, (metadata, exception) -> {
                    if (exception != null) {
                        System.err.printf("发送失败: %s%n", exception.getMessage());
                    } else {
                        System.out.printf("发送成功: topic=%s, partition=%d, offset=%d%n",
                                metadata.topic(), metadata.partition(), metadata.offset());
                    }
                });
            }
            // close 会 flush 剩余消息
        }
    }
}
```

## 8. 常见问题与最佳实践

### 8.1 消息顺序性保证

```text
✅ 相同 Key → 相同 Partition → 单 Partition 内有序
✅ max.in.flight.requests.per.connection = 1（禁用幂等时）
✅ enable.idempotence = true（推荐，允许并发发送，Kafka 保证有序）

❌ 不同 Key → 可能不同 Partition → 全局无序
❌ retries > 0 + 多 in-flight 请求 → 消息乱序（无幂等时）
```

### 8.2 生产避坑清单

| 问题 | 原因 | 解决 |
|------|------|------|
| 消息丢失 | acks=0/1、clean shutdown 丢数据 | acks=all + min.insync.replicas≥2 |
| 消息重复 | 网络重试 | enable.idempotence=true |
| 消息乱序 | 重试+多in-flight | 幂等模式 或 max.in.flight=1 |
| 发送阻塞 | buffer.memory 满 | 增大 buffer 或加快消费 |
| 分区倾斜 | 少数 Key 热数据 | 自定义分区器 |
| 磁盘满 | 生产太快/消费慢 | 限流+告警+清理策略 |

### 8.3 监控指标（生产者端）

| 指标 | 含义 | 告警阈值 |
|------|------|:---:|
| `record-send-rate` | 发送速率 | 接近目标 |
| `record-error-rate` | 错误率 | >0.1% |
| `record-retry-rate` | 重试率 | >1% |
| `request-latency-avg` | 平均请求延迟 | >100ms |
| `buffer-available-bytes` | 缓冲区可用 | <10% |
| `waiting-threads` | 等待线程数 | >0 持续 |
