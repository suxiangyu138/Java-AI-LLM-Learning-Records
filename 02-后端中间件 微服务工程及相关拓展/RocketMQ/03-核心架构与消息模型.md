## 2. CommitLog — 消息存储核心

### 2.1 设计理念

```text
CommitLog 核心思想 — "所有消息顺序追加到一个文件"

传统方式（每个 Topic 独立存储）：
  Topic-A: [file-a1] [file-a2] [file-a3]
  Topic-B: [file-b1] [file-b2]
  Topic-C: [file-c1] [file-c2] [file-c3] [file-c4]
  → 碎片化写入，磁盘随机 I/O

RocketMQ 方式（混合写入一个 CommitLog）：
  CommitLog: [A1][B1][A2][C1][B2][A3][C2][C3][A4][C4]
  → 所有消息顺序追加，磁盘 100% 顺序写 ✅
```

### 2.2 文件布局

```text
/data/rocketmq/store/commitlog/
├── 00000000000000000000          ← 文件名为起始偏移量（20位）
├── 00000000001073741824          ← 每个文件默认 1GB
├── 00000000002147483648
└── ...

单条消息存储格式：
┌────────────────────────────────────────────────────┐
│ totalSize (4B)                                    │
├────────────────────────────────────────────────────┤
│ magicCode (4B)  │ 消息唯一标识 (8B)                 │
├────────────────────────────────────────────────────┤
│ bodyCRC (4B)    │ queueId (4B) │ flag (4B)         │
├────────────────────────────────────────────────────┤
│ queueOffset (8B)│ physicalOffset (8B)              │
├────────────────────────────────────────────────────┤
│ sysFlag (4B)    │ bornTimestamp (8B)               │
├────────────────────────────────────────────────────┤
│ bornHost (8B)   │ storeTimestamp (8B)              │
├────────────────────────────────────────────────────┤
│ storeHost (8B)  │ reconsumeTimes (4B)              │
├────────────────────────────────────────────────────┤
│ preparedTransactionOffset (8B)                    │
├────────────────────────────────────────────────────┤
│ bodyLength (4B) │ body内容                         │
├────────────────────────────────────────────────────┤
│ topicLength (1B)│ topic内容 (变长)                  │
├────────────────────────────────────────────────────┤
│ propertiesLength (2B) │ properties内容 (变长)       │
└────────────────────────────────────────────────────┘
```

### 2.3 MappedByteBuffer

```text
RocketMQ 使用 MappedByteBuffer（内存映射文件）读写 CommitLog

┌──────────────────────────────────────────────┐
│              物理内存                           │
│  ┌────────────────────────────────────────┐   │
│  │   Mapped Memory (CommitLog 映射区)      │   │
│  │   ── 直接操作内存，OS 负责刷盘 ──        │   │
│  └────────────────────────────────────────┘   │
│              ↕ 页缓存映射                       │
│  ┌────────────────────────────────────────┐   │
│  │   磁盘文件 (CommitLog)                   │   │
│  └────────────────────────────────────────┘   │
└──────────────────────────────────────────────┘

优势：
  ✅ 零拷贝（数据不经过 JVM 堆）
  ✅ 减少数据拷贝次数
  ✅ 页缓存利用效率高

vs Kafka sendfile：
  Kafka    → sendfile（消费端零拷贝）
  RocketMQ → MappedByteBuffer（生产端零拷贝）
```

## 3. ConsumeQueue — 消费索引

### 3.1 为什么需要 ConsumeQueue

```text
问题：CommitLog 包含了所有 Topic 的消息混合写入。
消费者只想消费 Topic-A 的消息 — 怎么办？

❌ 方案 A：全量扫描 CommitLog → 太慢
✅ 方案 B：按 Topic+Queue 建立索引 → ConsumeQueue

ConsumeQueue 文件结构：
  每条 20 字节：
  ┌──────────────────┬─────────────────┬──────────┐
  │ CommitLog Offset │ Message Size    │ Tag Hash │
  │  (8 字节)        │   (4 字节)       │ (8 字节) │
  └──────────────────┴─────────────────┴──────────┘

  通过这个索引可以快速定位到 CommitLog 中的消息位置！
```

### 3.2 文件布局

```text
/data/rocketmq/store/consumequeue/
├── Topic-A/
│   ├── 0/                          ← Queue ID = 0
│   │   ├── 00000000000000000000
│   │   └── 00000000000006000000
│   ├── 1/                          ← Queue ID = 1
│   │   └── ...
│   └── 2/                          ← Queue ID = 2
│       └── ...
└── Topic-B/
    └── ...
```

### 3.3 ConsumeQueue 构建流程

```text
构建是异步的（不由生产线程阻塞）：

① 消息写入 CommitLog → 返回成功给 Producer
② ReputMessageService（后台线程）→ 解析 CommitLog
③ 分发到对应 Topic/Queue 的 ConsumeQueue
④ 更新 IndexFile

⚠️ 这意味着：消息写入后，消费者可能需要等几毫秒
   才能消费到（ConsumeQueue 构建完成的延迟）
```

## 4. IndexFile — 消息检索

### 4.1 索引文件结构

```text
IndexFile 用于按 Key 或时间范围查询消息

文件结构：
┌───────────────────────────────────────────┐
│  Header (40 字节)                          │
│  ├── beginTimestamp / endTimestamp         │
│  ├── beginPhyOffset / endPhyOffset         │
│  ├── hashSlotCount / indexCount            │
├───────────────────────────────────────────┤
│  Hash Slot Table (500万槽位)               │
│  ├── slot[0] = indexCount                  │
│  ├── slot[1] = indexCount                  │
│  └── ...                                   │
├───────────────────────────────────────────┤
│  Index Items (最多 2000 万条)              │
│  每条 20 字节：                             │
│  ├── keyHash (4B)                          │
│  ├── commitLogOffset (8B)                  │
│  ├── timestampDiff (4B)                    │
│  └── nextIndexPre (4B) ← 冲突解决链        │
└───────────────────────────────────────────┘
```

### 4.2 按 Key 查询过程

```text
查询 Key = "ORDER-12345"

① 对 Key 做 Hash → hashValue
② hashValue % 5000000 → slot 位置
③ 从 slot 拿到链表头 indexCount
④ 遍历链表 → 比对完整 Key Hash + 消息 Key
⑤ 找到后从 CommitLog 读取完整消息
```

## 5. 消息写入流程

```text
一条消息的完整写入路径：

Producer
  │ ① 发送消息 (Topic=A, Queue=0, Body="...")
  ▼
Broker
  │ ② 获取 CommitLog 写锁（串行化！）
  │ ③ 写入 CommitLog（顺序追加）
  │    ├── 同步刷盘？→ 等待 flush 完成
  │    └── 异步刷盘？→ 立即返回
  │ ④ 释放写锁
  │
  ├── ⑤ 返回 ACK 给 Producer（异步刷盘时已返回）
  │
  └── ⑥ 后台线程 ReputMessageService
       ├── 解析 CommitLog 新消息
       ├── 构建 ConsumeQueue 条目
       └── 更新 IndexFile

关键：
  ✅ CommitLog 写锁保证写入顺序
  ✅ 写 CommitLog 是唯一的磁盘 IO（异步刷盘）
  ✅ ConsumeQueue + Index 异步构建，不阻塞生产
```

## 6. 消息消费流程

```text
Consumer 拉取消息：

Consumer
  │ ① PullRequest (Topic=A, Queue=0, Offset=100)
  ▼
Broker
  │ ② 读取 ConsumeQueue 条目
  │    定位到 Queue=0 的 Offset=100
  │    → 获取 CommitLog Offset + Size + Tag Hash
  │
  │ ③ Tag 过滤（Broker 端）
  │    对比 ConsumeQueue 中的 Tag Hash
  │    不匹配 → 跳过，读取下一条
  │
  │ ④ 根据 CommitLog Offset → 随机读 CommitLog
  │    读取完整消息内容
  │
  │ ⑤ 属性过滤（SQL92 表达式，Consumer 订阅时指定）
  │    Broker 端解析消息属性 → 只返回匹配的
  │
  ▼ ⑥ 返回消息给 Consumer

注意：
  ⚠️ ConsumeQueue 读是顺序的（很快）
  ⚠️ CommitLog 读是随机的（可能较慢）→ 依赖页缓存
  ⚠️ Tag 过滤在 Broker 端 → 减少网络传输
```

## 7. 与 Kafka 存储模型对比

| 维度 | RocketMQ | Kafka |
|------|----------|-------|
| **写入模型** | CommitLog 混合追加（1 个物理写） | Partition 独立写（N 个物理写） |
| **索引模型** | ConsumeQueue（按队列索引） | .index（按偏移量索引） |
| **消息定位** | ConsumeQueue → CommitLog（两级跳） | Segment → .index（直接找） |
| **顺序写** | 100% 顺序写（所有 Topic 共享） | 按 Partition 顺序写 |
| **随机读** | CommitLog 读是随机的 | Segment 内顺序读 |
| **零拷贝** | MappedByteBuffer（读写都零拷贝） | sendfile（消费零拷贝） |
| **存储文件数** | CommitLog 1 个文件 + N 个 ConsumeQueue | N 个 Partition 各自文件 |
| **文件描述符** | 少量（1 + N queues） | 大量（N partitions × 2） |
| **tag 过滤** | ✅ Broker 端过滤 | ❌ 需客户端过滤 |
| **消息回放** | 按时间/Offset | 按时间/Offset |

### 设计哲学

```text
RocketMQ：写优化
  → 所有消息写入一个 CommitLog（100% 顺序写）
  → 通过 ConsumeQueue 解决"读什么"的问题
  → 适合：Topic 多、Queue 多、业务消息（读写比均衡）

Kafka：读写都优化
  → 每个 Partition 一个 Segment（读就是顺序的）
  → 文件描述符开销大（Partition × Replication × 3 个文件）
  → 适合：Topic 少、Partition 合理、数据管道（高吞吐消费）
```

## 存储核心要点

| 要点 | 一句话 |
|------|--------|
| **CommitLog** | 所有 Topic 消息混合顺序写入一个文件 |
| **ConsumeQueue** | 按 Topic+Queue 索引 CommitLog 位置（20B/条） |
| **异步构建** | ConsumeQueue/Index 后台异步构建，不阻塞生产 |
| **MappedByteBuffer** | 内存映射文件，零拷贝写入 |
| **两段查找** | ConsumeQueue（找到位置）→ CommitLog（读取内容） |
| **Tag 过滤** | Broker 端通过 ConsumeQueue 中的 Tag Hash 过滤 |
| **顺序写保证** | CommitLog 全局写锁 → 单线程写入保证顺序 |
