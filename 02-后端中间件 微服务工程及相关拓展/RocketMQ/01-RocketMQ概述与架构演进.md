```text
MetaQ (2011)
  → 阿里内部消息中间件，替代 ActiveMQ
  → 支撑淘宝交易核心链路

RocketMQ 3.x (2012-2016)
  → 完全重写，优化存储模型
  → 扛住历年双十一峰值

Apache RocketMQ (2016)
  → 捐献 Apache 基金会
  → 2017 年成为顶级项目（TLP）

  → 企业级特性完善（ACL、DLedger、事务消息增强）
  → 云原生适配

RocketMQ 5.x (2022+)
  → Controller 模式（去 ZK/DLedger 化）
  → gRPC Proxy、分级存储、轻量级流处理
```

## 2. 核心架构与四大组件

### 2.1 架构总览

```text
┌────────────────────────────────────────────────────────────┐
│                      NameServer 集群                        │
│                 (无状态、最终一致性路由)                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                 │
│  │ NS Node 1 │  │ NS Node 2 │  │ NS Node 3 │  ← 彼此不通信！  │
│  └─────┬─────┘  └─────┬─────┘  └─────┬─────┘                │
└────────┼──────────────┼──────────────┼──────────────────────┘
         │  注册/心跳    │              │  定时拉取路由
    ┌────▼──────────────▼──────────────▼────┐
    │              Broker 集群               │
    │  ┌──────────────┐  ┌──────────────┐   │
    │  │  Master-A    │  │  Master-B    │   │
    │  │  (可读写)     │  │  (可读写)     │   │
    │  │  Slave-A     │  │  Slave-B     │   │
    │  └──────────────┘  └──────────────┘   │
    └─────────────────┬─────────────────────┘
                      │
         ┌────────────┼────────────┐
         │            │            │
    ┌────▼────┐  ┌────▼────┐  ┌────▼────┐
    │Producer │  │Consumer │  │Consumer │
    └─────────┘  └─────────┘  └─────────┘
```

### 2.2 四大组件职责

| 组件 | 职责 | 关键特性 |
|------|------|----------|
| **NameServer** | 路由注册与发现 | 无状态、彼此不通信、最终一致 |
| **Broker** | 消息存储与投递 | 主从同步、CommitLog 存储 |
| **Producer** | 消息生产者 | 与 NameServer 交互获取路由 |
| **Consumer** | 消息消费者 | 推/拉模式、负载均衡、重试 |

### 2.3 NameServer 为什么如此设计

```text
NameServer 设计哲学 — "简单即是美"

vs ZooKeeper:
  ┌─────────────────┬──────────────┬──────────────┐
  │                  │  NameServer  │  ZooKeeper   │
  ├─────────────────┼──────────────┼──────────────┤
  │  一致性协议       │  无（最终一致）│  ZAB 协议     │
  │  节点间通信       │  不通信       │  选举+同步    │
  │  CAP 偏向        │  AP          │  CP          │
  │  运维复杂度       │  极低         │  中等         │
  │  分区容忍         │  高           │  中          │
  └─────────────────┴──────────────┴──────────────┘

为什么不选择强一致？
  ✅ 路由数据变更不频繁（Broker 上下线）
  ✅ 短暂不一致不致命（生产者有重试+容错机制）
  ✅ 极大简化了部署和运维
```

## 3. 消息领域模型

```text
RocketMQ 消息模型：

Topic（逻辑分类）
  └── MessageQueue（物理队列，类似 Kafka Partition）
        ├── Queue-0 (Broker-a)
        ├── Queue-1 (Broker-a)
        ├── Queue-2 (Broker-b)
        └── Queue-3 (Broker-b)

消息投递：
  Producer ──→ MessageQueue（多 Queue 并行写）
  Consumer ←── MessageQueue（多 Consumer 并行消费）

关键差异（vs Kafka）：
  ✅ RocketMQ Queue 数可 < Consumer 数（支持动态负载均衡）
  ✅ 全局顺序消息（指定一个 Queue）
  ✅ 消费失败自动重试（内置重试队列）
  ✅ Tag 过滤（Broker 端过滤，减少网络传输）
```

### 消息生命周期

```text
一条消息的一生：

1. Producer → 选择 Queue → 发送
2. Broker → 写入 CommitLog（顺序追加）
3. Broker → 异步构建 ConsumeQueue + Index
4. Consumer → 从 Broker 拉取消息 → 消费
5. 消费成功 → 返回 CONSUME_SUCCESS → 进度更新
6. 消费失败 → 返回 RECONSUME_LATER → 进入重试队列
     ├── 重试 16 次 → 进入死信队列
     └── 死信队列 → 人工处理或丢弃
```

## 4. RocketMQ vs Kafka 深度对比

### 4.1 架构层面

| 维度 | RocketMQ | Kafka |
|------|----------|-------|
| **注册中心** | NameServer（自研，简单） | ZK / KRaft |
| **存储模型** | CommitLog + ConsumeQueue | Partition + Segment |
| **队列模型** | Topic → MessageQueue（轻量） | Topic → Partition（重量）|
| **副本模型** | Master-Slave（异步/同步） | ISR Leader-Follower |
| **高可用** | DLedger / Controller 模式 | KRaft 共识 |

### 4.2 功能层面

| 功能 | RocketMQ | Kafka |
|------|:---:|:---:|
| **事务消息** | ✅ 半消息（业界领先） | ⚠️ 事务 Producer（有限） |
| **顺序消息** | ✅ 全局+分区 | ⚠️ 仅分区内 |
| **延迟消息** | ✅ 18 个级别 | ❌ |
| **消息过滤** | ✅ Tag + SQL92 | ❌ |
| **消息重试** | ✅ 内置重试队列 | ❌ |
| **死信队列** | ✅ 内置 | ❌ |
| **批量消息** | ✅ 同 Topic 批量 | ✅ 自动批量 |
| **定时消息** | ✅ 任意时间（5.x） | ❌ |

### 4.3 选型建议

```text
选 RocketMQ：
  ✅ 业务解耦（订单、支付、库存）
  ✅ 需要事务消息、延迟消息
  ✅ 需要 Tag/SQL 过滤
  ✅ 国内企业（阿里生态、中文社区）
  ✅ 金融级可靠性要求

选 Kafka：
  ✅ 大数据管道（日志、埋点、CDC）
  ✅ 流处理（Flink/Spark/Kafka Streams）
  ✅ 超高吞吐（百万 TPS+）
  ✅ 国际化场景
  ✅ 成熟生态（Connect、ksqlDB）
```

## 5. 典型应用场景

| 场景 | 说明 | 用到特性 |
|------|------|----------|
| **订单处理** | 下单 → 减库存 → 支付 → 物流 | 事务消息 |
| **异步解耦** | 服务间异步通信 | 普通消息 |
| **削峰填谷** | 秒杀场景 | 普通 + 延迟消息 |
| **顺序消费** | 订单状态流转 | 顺序消息 |
| **定时通知** | 30 分钟未支付取消 | 延迟消息 |
| **数据分发** | MySQL binlog 分发 | Tag 过滤 |
| **分布式事务** | 下单+扣库存一致性 | 事务消息（半消息） |

## 6. 核心术语速查

| 术语 | 说明 | 类比 |
|------|------|------|
| **NameServer** | 路由注册中心（无状态） | 电话黄页 |
| **Broker** | 消息存储服务器 | 邮局 |
| **Topic** | 消息主题/逻辑分类 | 收件地址 |
| **MessageQueue** | 消息队列（物理分区） | 分拣格口 |
| **Producer Group** | 生产者组（事务回查使用） | 寄件人组织 |
| **Consumer Group** | 消费者组（集群模式负载均衡） | 收件组 |
| **CommitLog** | 所有 Topic 消息顺序写入的日志 | 总流水账 |
| **ConsumeQueue** | 按 Topic+Queue 索引消息位置 | 分类目录 |
| **Tag** | 消息标签（二级分类） | 邮件标签 |
| **Offset** | 消费位移/进度 | 已读到第几行 |
| **重试队列** | 消费失败自动重试 | 疑难件处理 |
| **死信队列** | 重试耗尽的消息 | 废弃信箱 |
