## 1. 消费者类型

```java
// 1. DefaultMQPushConsumer — 推模式（最常用）
//    → 内部也是 Pull，但封装了长轮询
DefaultMQPushConsumer consumer = new DefaultMQPushConsumer("group");
consumer.setConsumeFromWhere(ConsumeFromWhere.CONSUME_FROM_LAST_OFFSET);
consumer.subscribe("Topic", "*");
consumer.registerMessageListener((MessageListenerConcurrently) (msgs, context) -> {
    process(msgs);
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});

// 2. DefaultLitePullConsumer — 拉模式（手动控制）
DefaultLitePullConsumer consumer = new DefaultLitePullConsumer("group");
consumer.subscribe("Topic", "*");
consumer.start();
List<MessageExt> msgs = consumer.poll(1000);  // 手动拉取

// 3. DefaultMQPullConsumer — 原始拉模式（过于底层，已不推荐）
```

### 消费者类型对比

| 类型 | 使用方式 | 推荐度 | 适用场景 |
|------|:---:|:---:|------|
| **Push** | 注册监听器，自动回调 | ⭐⭐⭐⭐⭐ | 99% 的场景 |
| **LitePull** | 手动 poll | ⭐⭐⭐⭐ | 需要精细控制拉取速率 |
| **Pull** (原始) | 手动管理 Offset/Queue | ⭐⭐ | 特殊定制场景 |

## 2. 消费模式

### 2.1 集群模式（默认）

```java
// 集群模式 — 同组内负载均衡
consumer.setMessageModel(MessageModel.CLUSTERING);
// Group 内 N 个 Consumer → 每个消费部分 Queue
// 消费进度存储在 Broker → 所有 Consumer 共享
```

### 2.2 广播模式

```java
// 广播模式 — 每个 Consumer 消费全部消息
consumer.setMessageModel(MessageModel.BROADCASTING);
// Group 内每个 Consumer → 都消费所有 Queue
// 消费进度存储在本地 → 各自独立
```

### 2.3 模式对比

| 维度 | 集群模式 | 广播模式 |
|------|----------|----------|
| **消息投递** | 同组 Consumer 分摊 | 每个 Consumer 全量 |
| **消费进度** | Broker 存储 | Consumer 本地存储 |
| **水平扩展** | ✅ 增加 Consumer 即可 | ❌ 每个 Consumer 都独立 |
| **重试** | ✅ 支持 | ❌ 无重试（本地进度） |
| **适用** | 业务处理 | 配置刷新、缓存更新 |

## 3. 消费者启动与负载均衡

### 3.1 启动流程

```text
consumer.start() 内部流程：

① 创建 MQClientInstance
② RebalanceImpl 启动 — 向所有 Broker 心跳
③ 拉取 Topic 路由
④ 执行负载均衡（分配 Queue 给 Consumer）
⑤ 创建 PullRequest — pullMessageService 开始拉消息
⑥ 消息到达 → 回调 MessageListener
```

### 3.2 负载均衡策略

```text
默认：AllocateMessageQueueAveragely（平均分配）

6 个 Queue，3 个 Consumer：
  C1 → Q0, Q1
  C2 → Q2, Q3
  C3 → Q4, Q5

其他策略：
┌────────────────────────────────┬──────────────────────────┐
│  策略                           │  说明                     │
├────────────────────────────────┼──────────────────────────┤
│  AllocateMessageQueueAveragely │  平均分配（默认）          │
│  AllocateMessageQueueByCircle  │  轮询分配                   │
│  AllocateMessageQueueByConfig  │  固定分配（需配置）         │
│  AllocateMessageQueueByMachineRoom │ 按机房分配              │
│  AllocateMessageQueueConsistentHash │ 一致性 Hash 分配      │
└────────────────────────────────┴──────────────────────────┘

// 设置负载均衡策略
consumer.setAllocateMessageQueueStrategy(
    new AllocateMessageQueueAveragely()
);
```

### 3.3 Rebalance 触发时机

```text
Rebalance 触发条件：
  ① Consumer 数量变化（加入/离开）
  ② Broker 数量变化（宕机/恢复）
  ③ Topic Queue 数量变化

Rebalance 过程（默认 20s 间隔）：
  ① 从所有 Broker 获取 Consumer 列表
  ② 从 NameServer 获取 Topic Queue 分布
  ③ 执行负载均衡算法 → 分配 Queue
  ④ 释放不再属于自己的 Queue
  ⑤ 添加新分配的 Queue
```

## 4. 消费进度管理

### 4.1 Offset 存储

```text
Offset 存储位置：
  集群模式 → Broker 内存 + 定时持久化到磁盘
  广播模式 → Consumer 本地文件

持久化路径：
  ~/store/config/consumerOffset.json （Broker 端）

持久化频率：
  默认 5s 持久化一次（可能丢最多 5s 的进度）
  手动指定 CONSUME_SUCCESS 后立即持久化
```

### 4.2 消费起点

```java
// 消费起点策略
consumer.setConsumeFromWhere(ConsumeFromWhere.CONSUME_FROM_LAST_OFFSET);
// CONSUME_FROM_LAST_OFFSET    — 从上次停止的位置（默认）
// CONSUME_FROM_FIRST_OFFSET   — 从最早开始（首次/过期）
// CONSUME_FROM_TIMESTAMP      — 从指定时间戳开始
```

### 4.3 流控机制

```java
// 消费者流控参数
consumer.setPullBatchSize(32);               // 每次拉取最大条数
consumer.setConsumeMessageBatchMaxSize(1);   // 每次消费最大条数（并发消费时）

// 背压原理：消费慢 → 本地缓存满 → 停止拉取 → 自然流控
DefaultMQPushConsumer.setPullThresholdForQueue(1000);      // 队列级别缓存上限
DefaultMQPushConsumer.setPullThresholdSizeForQueue(100);   // 队列级别缓存大小上限(MB)
```

## 5. 消息重试机制

### 5.1 消费失败处理

```java
// 并发消费监听器
consumer.registerMessageListener(new MessageListenerConcurrently() {
    @Override
    public ConsumeConcurrentlyStatus consumeMessage(
            List<MessageExt> msgs, ConsumeConcurrentlyContext context) {
        try {
            process(msgs);
            return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;  // 成功
        } catch (Exception e) {
            // 方式 1：直接返回失败（默认延迟重试）
            return ConsumeConcurrentlyStatus.RECONSUME_LATER;
            
            // 方式 2：设置延迟级别后重试
            // context.setDelayLevelWhenNextConsume(3); // 10 秒后重试
            // return ConsumeConcurrentlyStatus.RECONSUME_LATER;
        }
    }
});

// 顺序消费监听器
consumer.registerMessageListener(new MessageListenerOrderly() {
    @Override
    public ConsumeOrderlyStatus consumeMessage(
            List<MessageExt> msgs, ConsumeOrderlyContext context) {
        try {
            process(msgs);
            return ConsumeOrderlyStatus.SUCCESS;
        } catch (Exception e) {
            // 顺序消费：失败会暂停当前 Queue，无限重试
            // 可设置暂停时间
            context.setSuspendCurrentQueueTimeMillis(3000);
            return ConsumeOrderlyStatus.SUSPEND_CURRENT_QUEUE_A_MOMENT;
        }
    }
});
```

### 5.2 重试流程

```text
消费失败 → RECONSUME_LATER → 消息投递到重试队列

重试流程：
① Consumer 返回 RECONSUME_LATER
② Broker 收到，将消息投递到 %RETRY%ConsumerGroupName
③ 消息属性 reconsumeTimes + 1
④ 延迟时间 = 根据 reconsumeTimes 查表（10s/30s/1m/2m/...）
⑤ 到期后 → Broker 将消息投递回原 Topic
⑥ Consumer 重新消费

注意：
  ⚠️ 重试队列中的消息是原消息的副本
  ⚠️ 消费者会同时收到新消息和重试消息
  ⚠️ 重试消息的 reconsumeTimes 记录了重试次数
```

### 5.3 重试延迟级别

```text
并发消费重试延迟：基于 Broker 配置的 messageDelayLevel

默认延迟（对应 delayLevel）：
  重试次数    delayLevel    延迟时间
    1          3             10s
    2          4             30s
    3          5             1m
    4          6             2m
    5          7             3m
    ...
    16         18            2h

最大重试次数 = 16 → 失败后进入死信队列
```

### 5.4 重试注意事项

| 要点 | 说明 |
|------|------|
| **不适用重试的场景** | 消息格式错误/反序列化失败（重试无意义） |
| **重试消息特点** | reconsumeTimes > 0，delayLevel > 0 |
| **业务幂等** | 重试可能重复，业务逻辑必须幂等 |
| **重试次数** | 可配置 `consumer.setMaxReconsumeTimes(10)` |
| **特定异常不重试** | 在 listener 中捕获特定异常，返回 SUCCESS 并记录 |

## 6. 死信队列

### 6.1 死信队列机制

```text
消息重试 maxReconsumeTimes 次后仍然失败 → 进入死信队列

死信队列 Topic: %DLQ%ConsumerGroupName

特点：
  ✅ 不会再投递给消费者（除非手动操作）
  ✅ 需要人工介入处理
  ✅ 默认不会自动删除

查看死信：
  在控制台 → Topic → %DLQ%your-group → 查看消息
```

### 6.2 死信处理方案

```java
// 方案 1：监控死信队列（独立消费者）
consumer.subscribe("%DLQ%order-consumer-group", "*");
consumer.registerMessageListener((MessageListenerConcurrently) (msgs, context) -> {
    for (MessageExt msg : msgs) {
        log.error("死信消息: topic={}, keys={}, body={}, retryTimes={}",
            msg.getTopic(), msg.getKeys(), new String(msg.getBody()),
            msg.getReconsumeTimes());
        
        // ① 写入数据库供人工处理
        saveToDeadLetterTable(msg);
        
        // ② 发送告警通知
        sendAlert(msg);
    }
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});

// 方案 2：死信重投（控制台操作或 API）
DefaultMQProducer producer = new DefaultMQProducer("dead-letter-resend");
producer.setNamesrvAddr("localhost:9876");
producer.start();

// 从死信读取消息，重新发送到原 Topic
Message msg = deadMsg; // 从死信队列取出
msg.setTopic(originalTopic); // 改回原 Topic
producer.send(msg);
```

## 7. 消费模式：推 vs 拉

### 7.1 Push 模式（长轮询封装）

```java
// Push 模式内部实际上也是 Pull
// Broker 端使用长轮询（Long Polling）优化

// 长轮询参数：
DefaultMQPushConsumer consumer = new DefaultMQPushConsumer("group");
consumer.setPullTimeDelayMillsWhenException(1000);   // 长轮询等待时间
consumer.setPollNameServerInterval(30000);           // NameServer 拉取间隔

// 长轮询原理：
// Consumer → Broker: PullRequest（我来了，有消息叫我）
// Broker → 有消息 → 立即返回
// Broker → 无消息 → 挂起 15s（长轮询）→ 有新消息再返回
// 优点：避免空轮询，降低网络开销
```

### 7.2 LitePull 模式

```java
// LitePullConsumer — 更灵活的拉模式
DefaultLitePullConsumer consumer = new DefaultLitePullConsumer("group");
consumer.setNamesrvAddr("localhost:9876");
consumer.subscribe("Topic", "*");

// 按需拉取
consumer.setPullBatchSize(50);    // 单次拉取条数
consumer.setPollTimeoutMillis(5000); // poll 超时

consumer.start();

while (true) {
    List<MessageExt> msgs = consumer.poll();  // 手动 poll
    for (MessageExt msg : msgs) {
        process(msg);
    }
    // 手动提交 Offset
    consumer.commitSync();
}
```

### 7.3 两种模式对比

| 维度 | Push (Default) | LitePull |
|------|:---:|:---:|
| **编码复杂度** | 低（回调即可） | 中（手动 poll） |
| **流控能力** | 自动（阈值触发） | 手动控制 |
| **批量控制** | 自动 | 手动指定 |
| **Offset 管理** | 自动提交 | 手动 commit |
| **适用场景** | 99% 业务场景 | 精细控制场景 |
| **性能** | 高（长轮询优化） | 可控 |

## 8. Java 消费者实战

```java
public class OrderConsumer {
    
    public static void main(String[] args) throws MQClientException {
        DefaultMQPushConsumer consumer = new DefaultMQPushConsumer("order-group");
        consumer.setNamesrvAddr("localhost:9876");
        
        // 基本配置
        consumer.setConsumeFromWhere(ConsumeFromWhere.CONSUME_FROM_LAST_OFFSET);
        consumer.setMessageModel(MessageModel.CLUSTERING);
        
        // 并发配置
        consumer.setConsumeThreadMin(10);             // 最小消费线程
        consumer.setConsumeThreadMax(20);             // 最大消费线程
        consumer.setConsumeMessageBatchMaxSize(1);    // 单次消费最大条数
        
        // 流控
        consumer.setPullBatchSize(32);
        consumer.setPullThresholdForQueue(1000);
        
        // 重试
        consumer.setMaxReconsumeTimes(16);
        
        // 订阅
        consumer.subscribe("OrderTopic", "PAID || CREATED");
        
        // 注册监听器
        consumer.registerMessageListener(new MessageListenerConcurrently() {
            @Override
            public ConsumeConcurrentlyStatus consumeMessage(
                    List<MessageExt> msgs, ConsumeConcurrentlyContext context) {
                for (MessageExt msg : msgs) {
                    try {
                        // 幂等检查
                        if (isDuplicate(msg)) {
                            log.warn("重复消息跳过: msgId={}", msg.getMsgId());
                            continue;
                        }
                        
                        // 业务处理
                        String body = new String(msg.getBody(), StandardCharsets.UTF_8);
                        processOrder(body);
                        
                        // 标记已处理（幂等）
                        markProcessed(msg.getMsgId());
                        
                    } catch (BusinessException e) {
                        // 业务异常 → 可重试
                        log.warn("业务处理失败，进入重试: keys={}, retryTimes={}",
                            msg.getKeys(), msg.getReconsumeTimes());
                        return ConsumeConcurrentlyStatus.RECONSUME_LATER;
                    } catch (FormatException e) {
                        // 格式错误 → 重试无意义，直接确认
                        log.error("消息格式错误，跳过: keys={}", msg.getKeys());
                    }
                }
                return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
            }
        });
        
        consumer.start();
        log.info("消费者启动成功");
    }
}
```

## 9. 最佳实践与常见问题

### 9.1 消费幂等性

```text
RocketMQ 保证 At-Least-Once → 必须做幂等！

幂等方案：
  ① 业务唯一 ID 去重：Message Key → Redis/DB 查重
  ② DB 唯一索引：INSERT ... ON DUPLICATE KEY UPDATE
  ③ Redis SET NX：原子性保证
  ④ 版本号：乐观锁更新

示例：
  String orderId = msg.getKeys();  // 使用消息 Key
  // Redis: SET order:lock:{orderId} 1 NX EX 3600
  if (!redis.setIfAbsent("order:lock:" + orderId, "1", 1, TimeUnit.HOURS)) {
      return;  // 已处理，跳过
  }
```

### 9.2 消费线程数配置

```java
// 消费线程数 = Queue 数 × 每个 Queue 期望并发数
// 设 Queue=8，期望每个 Queue 2 个并发线程
consumer.setConsumeThreadMin(16);
consumer.setConsumeThreadMax(16);

// ⚠️ 线程数不是越大越好：
//  → 过多线程导致上下文切换开销
//  → 数据库连接池可能不够
//  → 建议：Queue 数 × (1~3)
```

### 9.3 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| 消费堆积 | 消费速度 < 生产速度 | 增加 Consumer/Queue、优化逻辑 |
| 重复消费 | At-Least-Once | 幂等设计 |
| 消息丢失 | BROADCASTING 模式无重试 | 用集群模式 或 自建补偿 |
| 部分 Queue 不消费 | Consumer 数 > Queue 数 | Consumer ≤ Queue |
| 消费慢 | 单线程处理 | 增加消费线程、异步化 DB |
| 重试风暴 | 大量消息同时失败 | 熔断降级、限流 |
