## 1. 调优黄金流程

> **背景**：调优失败的常见原因——不量化就动手、一次改太多、改完不验证。
> **目的**：建立可复制的调优 SOP。
> **适用范围**：任何线上 SQL 性能问题的处理。

```text
黄金五步（每一步都有产出物）
├── ① 量化问题
│   ├── 指标：耗时（P50/P95/P99）、QPS、扫描行数、锁等待
│   ├── 产出：现状基线（优化前快照）
│   └── 金句：没有数字，就没有「优化了」——只有「感觉快了」
├── ② 定位根因
│   ├── EXPLAIN/EXPLAIN ANALYZE → 执行计划
│   ├── 慢日志 Lock_time → 锁问题？
│   ├── 性能监控 → 资源瓶颈？
│   └── 产出：根因结论（索引/写法/锁/资源之一）
├── ③ 设计优化方案
│   ├── 从轻到重：SQL 改写 → 索引 → 架构（[[04]] 四层）
│   ├── 一次只改一处（变量隔离）
│   └── 产出：方案 + 预期效果
├── ④ 执行与验证
│   ├── 测试环境复现（数据量接近生产）
│   ├── EXPLAIN 前后对比（type/rows/Extra）
│   ├── 实测耗时对比（EXPLAIN ANALYZE）
│   └── 产出：前后对照数据
└── ⑤ 上线与回归
    ├── 灰度发布 + 监控观察
    ├── 对比上线前后基线
    └── 产出：长期验证结论

纪律三不要
├── 不量化不优化（没基线不动手）
├── 不一次改多（变量隔离——改坏了知道谁干的）
├── 不跳过验证（优化后必须对比）
└── 金句：调优是工程不是玄学——数据驱动每一步
```

## 2. 性能基线：拿数据说话

> 🎯 **基线 = 优化的「刻度尺」**——没有基线无法评估优化效果：

```text
基线三件套
├── ① 耗时基线：接口 P50/P95/P99（调用链监控）
├── ② SQL 基线：慢 SQL 数量/耗时/扫描行数（慢日志统计）
└── ③ 资源基线：CPU/内存/磁盘 IO/连接数（监控平台）

如何建立基线
├── 抓取：监控平台（Prometheus + Grafana / 云 RDS 监控）
├── 周期：按周汇总（流量有周期性——避开大促）
├── 阈值：P99 突破历史 2 倍 = 告警
└── 金句：基线是「历史自己」——比任何行业标准都贴切

优化效果的表述（面试/汇报规范）
├── 优化前：P99 = 850ms（慢日志：日均 120 条 > 1s）
├── 优化后：P99 = 45ms（慢日志：日均 2 条）
├── 提升：扫描行数 500 万 → 50（99.99%↓），耗时 18.9 倍
└── 金句：用「前后对照数字」汇报——不吹牛不邀功
```

## 3. 跨体系调优全景

> 🎯 **SQL 调优不是孤岛**——2026 全栈视角的调优阶梯（与仓库其他体系联动）：

```text
调优阶梯（从应用层到存储层）
├── ① 应用层
│   ├── 连接池大小（HikariCP 配置——池小排队/池大浪费）
│   ├── 批处理/异步化（减少数据库往返）
│   └── N+1 查询治理（循环查库 → JOIN/批量）
├── ② 缓存层（[[分布式深度剖析学习]] 04 篇）
│   ├── Redis 缓存热点查询（读多写少）
│   ├── 缓存穿透/击穿/雪崩防护
│   └── 金句：SQL 优化的尽头是「不查 SQL」——缓存挡掉 80% 读
├── ③ SQL 层（本系列）
│   ├── 索引/EXPLAIN/慢查询治理
│   └── 本系列的战场
├── ④ 架构层（[[分布式深度剖析学习]] 06 篇）
│   ├── 读写分离（读压力大）
│   ├── 分库分表（数据量大）
│   └── 归档（历史数据膨胀）
└── ⑤ 硬件层（[[什么是服务器]] 02 篇）
    ├── 内存：buffer pool（SSD 之前先加内存）
    └── 磁盘：HDD → SSD → NVMe

调优顺序金句
├── 「缓存挡读、索引挡查、分片挡量、硬件挡底」
├── 先 SQL 后架构：90% 的查询问题在 SQL 层解决
└── 架构手段为「量级问题」准备——别为 1 万行数据分库分表
```

## 4. 经典案例复盘

> 🎯 **一个「慢 SQL 拖垮全库」的完整复盘**（综合应用前 6 篇）：

```text
事故背景
├── 现象：某接口 P99 从 80ms 飙到 3s，数据库 CPU 100%
├── 影响：全站接口变慢（数据库是公共资源）
└── 定位过程（黄金流程走一遍）

① 量化
├── 数据库 CPU 100%、连接数打满
├── 慢日志：日均 5000 条 > 1s（平时 50 条）
└── 基线对比：异常 100 倍

② 定位（pt-query-digest Top1）
├── SELECT * FROM t_order WHERE create_time > '2026-01-01'
│   ORDER BY create_time DESC LIMIT 100
├── EXPLAIN：type=ALL（全表），rows=500 万，Extra=filesort
├── 锁等待：Lock_time 正常（不是锁问题）
└── 根因：大促后 create_time 无索引 → 全表 + 文件排序

③ 方案设计
├── L1 索引：idx_create_time (create_time)（排序也走索引）
├── L2 限制：业务侧 LIMIT 更合理 + 时间范围收窄
└── 只做索引（一次一处）

④ 验证
├── EXPLAIN 复查：type=range，rows=1.2 万，无 filesort
├── 实测：EXPLAIN ANALYZE 850ms → 20ms
└── 测试环境 + 压测通过

⑤ 上线回归
├── 灰度 → 监控 P99 回落 80ms
├── 慢日志：5000 条/天 → 60 条
└── 复盘沉淀：大表加索引必须评估「已有查询是否会触发全表」

经验教训
├── 「查询没走到索引」比「没有索引」更隐蔽——大促后新查询上线
├── 预防：新 SQL 上线前 EXPLAIN 预检（治理体系，[[04]] 07 节）
└── 金句：调优 = 黄金流程 × 预防体系——救火不如防火
```

## 5. 面试高频题

**Q1：SQL 调优的完整流程？**

```text
答：黄金五步——① 量化（耗时/QPS/扫描行数基线）；② 定位
（EXPLAIN/慢日志/锁等待）；③ 方案（SQL→索引→架构从轻到重，
一次一处）；④ 验证（前后 EXPLAIN + 实测对比）；⑤ 上线回归
（灰度 + 基线对比）。核心：拿数据说话，不跳步。
```

**Q2：为什么用了索引还是慢？**

```text
答：六种可能——① 索引失效（函数包裹/类型转换/前导%）；② 选择性
差（低基数索引，优化器估计回表贵）；③ 回表多（非覆盖索引，命中
行数大）；④ 排序没走索引（filesort）；⑤ 统计信息失真（先
ANALYZE TABLE）；⑥ 锁等待（Lock_time 高，不是查询问题）。
```

**Q3：联合索引 (a,b,c) 哪些查询能用到？**

```text
答：最左前缀原则——WHERE a；WHERE a,b；WHERE a,b,c 能用；
WHERE b 或 b,c 用不到。等值条件可乱序（优化器调整）；范围条件
（b>10）后 c 无法接力；WHERE a ORDER BY b 排序也能走索引。
```

**Q4：IN 和 EXISTS 怎么选？**

```text
答：MySQL 8.0+ 优化器会把子查询改写成半连接/物化，IN 与 EXISTS
性能趋于一致——写可读性好的即可。注意子查询结果集别太大
（物化临时表大），复杂场景显式 JOIN 更可控。
```

**Q5：深分页怎么优化？**

```text
答：OFFSET 大 = 扫描丢弃大量行。方案：① 游标分页（WHERE id >
last_id ORDER BY id LIMIT 10——App 场景主流）；② 延迟关联
（先查 ID 再回表——必须跳页的后台场景）；③ 业务限制页数。
```

**Q6：死锁怎么排查和避免？**

```text
答：排查——SHOW ENGINE INNODB STATUS 看 LATEST DETECTED
DEADLOCK（涉及 SQL 与加锁顺序）；避免——① 统一加锁顺序
（小 id 先锁）；② 短事务（缩锁持有时间）；③ 条件走索引
（缩小锁范围）；④ 应用捕获死锁重试。
```

**Q7：RR 和 RC 隔离级别怎么选？**

```text
答：RR 有间隙锁防幻读（默认，一致性最强，锁开销大）；RC 无
间隙锁（并发高，无幻读防护）。8.0 + ROW 格式 binlog 下 RC 复制
安全——高并发写场景可用 RC；拿不准保持 RR 默认。
```

**Q8：一条 SQL 从发起到返回经历了什么？（综合题）**

```text
答：解析（词法/语法/语义）→ 优化（成本模型 + 统计信息选执行
计划）→ 执行（按计划访问：索引/全表/JOIN 算法）→ 返回。
EXPLAIN 看到的就是优化结果；EXPLAIN ANALYZE 是真实执行。
```

**Q9：怎么看一个执行计划好不好？**

```text
答：四要素——type（目标 range 及以上，ALL 警告）；key（NULL
= 没索引）；rows（对比实际，失真先 ANALYZE）；Extra（filesort/
temporary 红灯，Using index 绿灯覆盖索引）。
```
