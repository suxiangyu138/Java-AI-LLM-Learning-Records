# 05 - JOIN 与分页排序优化

> **核心摘要**：JOIN 优化的本质是**「小表驱动大表 + 让被驱动表走索引」**；MySQL 8.0.18+ 引入 **Hash Join** 后大表等值 JOIN 性能飞跃（5.7 时代的很多 JOIN 经验已过时）。分页优化的核心是**深分页**——OFFSET 越大越慢，用**游标分页/延迟关联**根治。排序优化的核心是**让 ORDER BY 走索引**。

## 1. JOIN 的三种执行算法

> **背景**：JOIN 慢是调优高频问题——先懂算法再谈优化。
> **目的**：掌握 NLJ/BNL/Hash Join 三种算法与适用场景。
> **适用范围**：所有联表查询。

```text
① NLJ（Nested Loop Join，嵌套循环）
├── 流程：驱动表每行 → 去被驱动表找匹配（逐行查）
├── 前提：被驱动表连接列有索引（否则退化为逐行全表——灾难）
├── 特点：最通用；被驱动表走索引时性能可接受
└── 适用：等值 + 被驱动表有索引

② BNL（Block Nested Loop，块嵌套循环，5.7 默认）
├── 流程：驱动表一批（join buffer）→ 批量去被驱动表匹配
├── 特点：被驱动表无索引时的「缓存优化」（读一次驱动表块）
└── 5.7 里被驱动表无索引的 JOIN 全靠它——但还是很慢

③ Hash Join（哈希连接，8.0.18+）
├── 流程：小表建哈希表 → 大表逐行探测（一次构建一次探测）
├── 特点：**无需索引也能高效 JOIN**！
│   ├── 无索引等值 JOIN：5.7 灾难 → 8.0+ 秒级
│   └── 大数据量等值 JOIN 性能飞跃
└── 适用：等值 JOIN（=），尤其大表无索引场景

算法选型（优化器自动选）
├── 被驱动表有索引 → NLJ（索引查找最快）
├── 被驱动表无索引 + 等值 → Hash Join（8.0+）
├── 被驱动表无索引 + 非等值 → BNL（退化场景，尽量别出现）
└── 金句：8.0+ 升级最大的红利之一 = Hash Join——老经验要更新
```

> 💡 **EXPLAIN 识别算法**：Extra 列显示 `Using join buffer (hash join)` = Hash Join；`Nested loop` = NLJ；`Using join buffer (block nested loop)` = BNL（8.0 下通常是 hash join 显示）。

## 2. 驱动表：小表驱动大表

> 🎯 **驱动表 = 外层循环的表**——小表驱动大表是 JOIN 优化的第一原则：

```text
为什么小表驱动大表
├── NLJ 场景：驱动表每行都要去被驱动表查找
│   ├── 大表驱动小表：大表 100 万行 × 小表每次查 = 100 万次查找
│   ├── 小表驱动大表：小表 1 万行 × 大表索引查 = 1 万次查找
│   └── 差 100 倍——驱动表越小，循环次数越少
├── Hash Join 场景：构建哈希表的表越小越好（内存占用）
└── 金句：外层循环少一次，总开销少一大截

优化器怎么选驱动表
├── 默认：按成本估算自动选（通常已正确）
├── 估算失准：统计信息过时 → ANALYZE TABLE
├── 手动干预：STRAIGHT_JOIN（强制左边为驱动表）
│   └── SELECT STRAIGHT_JOIN ... FROM t_small s JOIN t_big b ON ...
└── 判断当前驱动：EXPLAIN 第一行（id 最小的）就是驱动表

判断「小」的标准（不只是行数）
├── 行数少（明显标准）
├── WHERE 过滤后更小（带条件的表更优）
├── 索引覆盖（不需要回表的表更轻）
└── 金句：实际参与连接的数据量小 = 好驱动表
```

## 3. 被驱动表必须走索引

> 🎯 **JOIN 性能的生死线**——被驱动表连接列必须有索引：

```text
没有索引的后果
├── 5.7：被驱动表无索引 → 每次匹配全表扫描 → O(N×M) 灾难
├── 8.0+：退化到 BNL/Hash Join（好很多，但仍有成本）
└── 金句：先看被驱动表连接列有没有索引——没有就建

索引怎么建（JOIN 场景）
├── 等值连接列：普通索引即可（B-tree）
├── 多列连接：联合索引（顺序按连接条件）
├── 字符串连接：前缀索引可能够用（长度取舍）
└── 验证：EXPLAIN 看被驱动表 type=ref/eq_ref（不是 ALL）

实战检查
├── 小表驱动大表（第 2 节）
├── 大表（被驱动）连接列建索引
├── JOIN 条件列类型一致（隐式转换破坏索引！）
└── 金句：JOIN 优化 = 驱动表选小 + 被驱动表走索引
```

## 4. 子查询与 EXISTS / IN 的选择

> 🎯 **8.0+ 子查询优化已成熟**——旧经验「IN 比 EXISTS 慢」大多已过时：

```text
8.0+ 优化器对子查询的改写
├── IN 子查询 → 半连接（Semi-join）：
│   ├── 物化（Materialization）：先算子查询结果 → 主查询匹配
│   ├── 或改 JOIN：优化器自动展开
│   └── 结果：IN 与 EXISTS 性能趋于一致（别再迷信旧结论）
├── EXISTS → 半连接/物化（按成本选）
├── 派生表：合并（merge）或延迟物化（lazy materialization）
└── 金句：8.0+ 的 IN/EXISTS 由成本模型决定——写可读性好的即可

真正的注意点（2026 视角）
├── ① 子查询返回大结果集 → 物化临时表大 → 慢
│   └── 对策：加 WHERE 限制/改 JOIN
├── ② 相关子查询（每行执行一次）→ 注意被驱动方向
│   └── 相关子查询 = 隐式 NLJ（小表驱动大表原则同样适用）
├── ③ NOT IN 子查询 → 反连接（anti-join）8.0 已优化
└── ④ 深嵌套子查询 → 拆开中间结果（可读性 + 可调优）

写法建议（2026 主流）
├── 简单 IN/EXISTS：直接写（优化器会处理）
├── 复杂场景：显式 JOIN 更可控（可看执行计划）
├── 大子查询：先物化到临时表/缓存
└── 金句：别再纠结 IN vs EXISTS——8.0+ 交给优化器，你管可读性
```

## 5. 深分页：OFFSET 之痛

> 🎯 **OFFSET 越大越慢**——LIMIT 999990, 10 要扫描 100 万行再丢弃：

```text
OFFSET 深分页的真相
├── LIMIT 1000000, 10：
│   ├── 数据库扫描前 1,000,010 行
│   ├── 丢弃前 1,000,000 行（全部白干）
│   └── 第 100 万行后每翻一页都扫 100 万+ 行
├── 时间曲线：页数越大耗时线性增长（第 1 页 5ms，第 10 万页 5s）
└── 金句：OFFSET 分页的复杂度 = O(页码 × 每页行数)

方案一：游标分页（推荐，互联网主流）
├── 原理：WHERE id > 上次最后一条的 id ORDER BY id LIMIT 10
├── 优点：每次只扫 10 行（恒定 O(1) 级别）
├── 缺点：无法跳页（只能「下一页」——App 场景完美适配）
└── 实现：前端传 lastId（或后端从上次结果取）

方案二：延迟关联（必须跳页时）
├── 原理：先查 ID（走索引快）→ 再回表取全字段
│   SELECT * FROM t_order o
│   JOIN (SELECT id FROM t_order ORDER BY create_time DESC LIMIT 1000000, 10) t
│   ON o.id = t.id
├── 效果：内层只扫索引（快）→ 外层按主键回表（10 行）
└── 适用：后台管理系统（必须跳页）

方案三：其他
├── 业务限制：最多翻 100 页（大部分场景合理）
├── 时间分页：按日期维度（历史数据用日期范围）
└── ES 搜索分页（深度分页有 search_after）
```

> ⚠️ **深分页排查**：慢日志里 `LIMIT 大OFFSET` 形态的 SQL——统一改游标分页。

## 6. 排序优化：让 ORDER BY 走索引

> 🎯 **排序两种实现**：索引有序（免费）vs filesort（文件排序，贵）——目标是前者：

```text
filesort 的代价
├── 数据量小：内存排序（sort buffer）
├── 数据量大：临时文件多路归并（磁盘 IO！）
├── 表现：Extra: Using filesort
└── 金句：filesort = 排序是「额外工作」——索引排序是「免费午餐」

让 ORDER BY 走索引的条件（联合索引设计）
├── ① ORDER BY 列顺序与索引列顺序一致（最左前缀）
│   └── 索引 (a, b)：ORDER BY a, b ✅ / ORDER BY b, a ❌
├── ② 排序方向一致（全升或全降）
│   └── ORDER BY a ASC, b DESC ⚠️（8.0 前不支持混排索引——8.0+ 支持）
├── ③ WHERE 等值条件与 ORDER BY 组成前缀
│   └── WHERE a = 1 ORDER BY b → 索引 (a, b) ✅
├── ④ 排序列不能被表达式包裹
│   └── ORDER BY DATE(create_time) ❌（函数破坏有序性）
└── ⑤ LIMIT 也有帮助（索引有序 → 取前 N 行即停）

GROUP BY 同理
├── GROUP BY 列与索引前缀一致 → 走索引（Extra: Using index for group-by）
├── 否则 → Using temporary + filesort（双重惩罚）
└── 金句：排序/分组优化 = 与索引设计「联合设计」（[[03]] 一石二鸟）
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. **三种算法**：NLJ（被驱动走索引）/ BNL（无索引兜底）/ **Hash Join（8.0.18+ 无索引等值飞跃）**
> 2. **小表驱动大表**：外层循环少一次，总开销少一大截（STRAIGHT_JOIN 强制）
> 3. **被驱动表必须走索引**：JOIN 性能生死线——连接列类型一致防隐式转换
> 4. **IN vs EXISTS 已过时**：8.0+ 半连接/物化优化——可读性优先，注意子查询结果集大小
> 5. **深分页**：OFFSET 是 O(页码) 灾难——游标分页（App）/延迟关联（后台跳页）
> 6. **排序走索引五条件**：列序一致/方向一致/等值前缀/无函数包裹/LIMIT 加持
> 7. **GROUP BY 同理**：不匹配索引 = temporary + filesort 双重惩罚
