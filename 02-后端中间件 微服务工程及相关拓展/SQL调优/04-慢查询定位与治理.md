## 1. 慢查询治理闭环

> **背景**：慢 SQL 是数据库性能的最大杀手——一条慢 SQL 可能拖垮整个库（占连接/锁）。
> **目的**：建立「发现→分析→优化→验证→预防」的治理体系思维。
> **适用范围**：所有线上数据库的日常运维。

```text
治理闭环（PDCA 在 SQL 治理上的应用）
┌─────────────────────────────────────────────┐
│ ① 发现（Detect）                             │
│    慢日志/监控平台/告警 → 抓到慢 SQL 列表      │
├─────────────────────────────────────────────┤
│ ② 分析（Analyze）                            │
│    pt-query-digest 归类 → 找 TopN → 看执行计划 │
├─────────────────────────────────────────────┤
│ ③ 优化（Optimize）                           │
│    索引/改写/拆表 → 小步验证（灰度）            │
├─────────────────────────────────────────────┤
│ ④ 验证（Verify）                             │
│    对比基线：耗时/QPS/扫描行 → 回归确认         │
└─────────────────────────────────────────────┘
金句：治理不是「救火一次」，是「闭环重复 + 预防」
```

## 2. 慢查询日志配置

> 🎯 **慢日志 = 调优的「雷达」**——记录超过阈值的 SQL：

```sql
-- 查看当前配置
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';

-- 开启慢日志（8.0 动态配置）
SET GLOBAL slow_query_log = ON;         -- 开启
SET GLOBAL long_query_time = 1;         -- 阈值 1 秒（生产推荐 1-2s）
SET GLOBAL log_queries_not_using_indexes = ON;  -- 记录没用索引的查询
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';
-- 持久化：my.cnf 配置（重启生效）
-- [mysqld]
-- slow_query_log = 1
-- long_query_time = 1
-- log_queries_not_using_indexes = 1
```

```text
阈值怎么定
├── 生产标准：1 秒（核心表 500ms 更严）
├── 阈值过低：日志爆炸（大量正常查询）
├── 阈值过高：漏掉真问题
└── 金句：先 2s 跑一周看基线 → 再压到 1s（治理渐进）

慢日志内容解读（关键字段）
├── Query_time：查询耗时（核心指标）
├── Lock_time：锁等待时间（高 = 锁问题，见 [[06]]）
├── Rows_sent / Rows_examined：发送/扫描行数
│   └── Rows_examined >> Rows_sent → 扫描浪费（索引问题）
├── 实际 SQL + 执行环境
└── 金句：Rows_examined 是「优化空间」的量化指标
```

## 3. 分析工具：pt-query-digest

> 🎯 **pt-query-digest（Percona Toolkit）**——慢日志的「统计大师」：把海量慢 SQL 归类聚合：

```bash
# 安装（Percona Toolkit）
apt install percona-toolkit

# 分析慢日志（最常用）
pt-query-digest /var/log/mysql/slow.log

# 输出三大板块
# ① 总览：慢 SQL 条数/总耗时/最大耗时
# ② Profile：Top 慢 SQL 排名（耗时/占比/次数）
# ③ 每条明细：指纹（归一化 SQL）+ 执行计划统计

# 实战参数
pt-query-digest slow.log --limit 10         # Top10
pt-query-digest slow.log --since '24h ago'  # 只看最近 24h
pt-query-digest slow.log --filter '$event->{Rows_examined} > 100000'  # 过滤大扫描
```

```text
输出解读（Profile 板块）
├── # Rank Query ID Response time Calls Rows examined
├── 第 1 名：某 SQL 占总慢查询 40% 耗时 ← 治理优先级最高
├── 指纹（Fingerprint）：SQL 归一化
│   ├── SELECT * FROM t WHERE id = ?（参数被 ? 替换）
│   └── 同指纹聚合 → 统计「同一类」SQL 的整体影响
└── 金句：治理顺序 = 按「耗时占比」从大到小（二八法则）

替代工具（2026 生态）
├── 云监控自带慢查询分析（阿里云 RDS 等——开箱即用）
├── SkyWalking/PMM（Percona Monitoring）可视化
└── 自研：sys.schema 表查询（MySQL 自带诊断库）
```

## 4. 定位：从 SQL 到根因

> 🎯 **拿到慢 SQL 后「六步定位法」**——避免瞎优化：

```text
六步定位
├── ① 复现确认：EXPLAIN ANALYZE 实测（真实执行路径）
├── ② 看访问方式：type 是 ALL？→ 索引缺失（[[02]]）
├── ③ 看扫描行数：rows 对比实际（统计信息失真？先 ANALYZE）
├── ④ 看 Extra：filesort/temporary → 排序/分组问题
├── ⑤ 看锁等待：Lock_time 高 → 锁问题（[[06]]）
└── ⑥ 看资源：数据库 CPU/IO 高？→ 系统瓶颈（[[服务器运维深度剖析]]）

根因分类（80% 慢 SQL 的归属）
├── ① 索引问题（60%）：缺索引/失效/设计不当
├── ② 写法问题（15%）：深分页/隐式转换/子查询低效
├── ③ 锁与并发（10%）：长事务/行锁等待/死锁
├── ④ 数据问题（10%）：数据倾斜/大字段/历史数据膨胀
└── ⑤ 系统资源（5%）：CPU 打满/磁盘慢（优化 SQL 前先确认）

定位纪律
├── 先确认「是不是慢 SQL 本身的问题」——锁等待不是索引能解决的
├── 用 EXPLAIN ANALYZE 实测（估算会骗人）
└── 金句：定位错方向 = 优化白做——先分类再动手
```

## 5. 优化手段全景

> 🎯 **优化手段分层**——从「最廉价」到「最重」逐级尝试：

```text
L1 SQL 写法优化（零成本）
├── 改写：隐式转换修正/函数去包裹/IN 改 JOIN
├── 减少返回：只查需要的列（SELECT 指定列，别 SELECT *）
├── 减少扫描：LIMIT 提前/谓词下推
└── 深分页改写（[[05]]）

L2 索引优化（低成本）
├── 加索引/联合索引设计（[[03]]）
├── 覆盖索引（高频查询）
└── 生成列索引（表达式场景）

L3 架构优化（中成本）
├── 读写分离（读压力大）
├── 缓存（Redis 挡读——[[分布式深度剖析学习]] 04 篇）
├── 冷热分离（历史数据归档）
└── 分库分表（数据量大——[[分布式深度剖析学习]] 06 篇）

L4 参数与硬件（高成本，最后）
├── buffer pool 调大（内存换 IO）
├── 磁盘升级（SSD → NVMe）
└── 加从库/升级实例

优化优先级金句
├── 「先 SQL 再索引，先索引再架构」
├── 80% 的慢 SQL 在 L1+L2 解决
└── 架构级手段是为「量级问题」准备的——别杀鸡用牛刀
```

## 6. 典型治理案例库

> 🎯 **四个高频案例**（覆盖 60% 慢查询场景）：

### 案例一：全表扫描（缺索引）——最常见

```text
现象：接口偶发超时，慢日志出现 SELECT ... WHERE user_id=?
定位：EXPLAIN → type=ALL, rows=500 万
根因：t_order 只有主键索引，user_id 查询全表
优化：ALTER TABLE t_order ADD INDEX idx_user_id (user_id)
验证：rows 500 万 → 3，耗时 2s → 10ms
```

### 案例二：深分页（OFFSET 大）

```text
现象：列表第 100 页接口慢
定位：EXPLAIN → type=range，但实际扫描 100 万行
根因：LIMIT 999990, 10 → 扫描 100 万行后丢弃 99.9 万
优化：游标分页（WHERE id > 上次最后 ID ORDER BY id LIMIT 10）
验证：扫描 100 万 → 10 行（详见 [[05]]）
```

### 案例三：隐式类型转换

```text
现象：订单号查询慢，但确认有索引
定位：EXPLAIN → key=NULL
根因：order_no 是 VARCHAR，条件传了数字（类型转换）
优化：改代码传字符串 / 或改字段类型
验证：key 恢复使用，耗时正常
```

### 案例四：JOIN 大表驱动顺序问题

```text
现象：联表查询秒级
定位：EXPLAIN → 大表先访问（驱动顺序反了）
根因：优化器估算偏差（统计信息过时）
优化：ANALYZE TABLE + 必要时 STRAIGHT_JOIN
验证：耗时秒级 → 毫秒级（详见 [[05]]）
```

## 7. 治理体系建设

> 🎯 **把「救火」变成「体系」**——2026 生产环境的慢 SQL 治理标准：

```text
体系五件套
├── ① 阈值与告警
│   ├── 慢日志：1s 阈值 + 持续采集
│   ├── 告警：慢 SQL 突增（对比基线倍数）→ 告警
│   └── 工具：云 RDS 慢查询监控 / PMM / 自研采集
├── ② 定期治理周报
│   ├── 每周 TopN 慢 SQL 评审
│   ├── 新慢 SQL 必须「立单治理」
│   └── 治理闭环追踪（发现→修复→回归）
├── ③ 上线前置检查（预防 > 救火）
│   ├── 新功能 SQL 评审：EXPLAIN 预检
│   ├── 测试环境压测（数据量接近生产）
│   └── SQL 规范（禁 SELECT * / 禁隐式转换……）
├── ④ 基线管理
│   ├── 核心接口耗时基线（P99）
│   ├── 版本发布前后对比（回归）
│   └── 金句：没基线 = 没法说「变好还是变坏」
└── ⑤ 容量与趋势
    ├── 慢 SQL 数量/耗时趋势（周/月）
    └── 数据量增长预警（提前规划索引/归档）
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. **闭环**：发现（慢日志）→ 分析（pt-query-digest）→ 定位（EXPLAIN ANALYZE）→ 优化 → 验证回归
> 2. **慢日志配置**：1s 阈值 + 记录未用索引查询；Rows_examined 是优化空间量化指标
> 3. **pt-query-digest**：指纹归一化聚合——按「耗时占比」定治理优先级（二八法则）
> 4. **六步定位**：实测复现 → 访问方式 → 扫描行 → Extra → 锁等待 → 资源
> 5. **优化四层**：SQL 写法 → 索引 → 架构 → 硬件——80% 在前两层解决
> 6. **四大案例**：缺索引/深分页/类型转换/驱动顺序
> 7. **体系五件套**：阈值告警 + 周报治理 + 上线预检 + 基线 + 趋势
