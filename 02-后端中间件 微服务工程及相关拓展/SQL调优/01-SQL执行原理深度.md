# 01 - SQL 执行原理深度

> **核心摘要**：调优的前提是「知道优化器在想什么」——一条 SQL 的执行旅程：**解析 → 预处理 → 优化（成本估算）→ 执行**。核心是**成本优化器（Cost-based Optimizer）**：它根据统计信息估算各方案的代价，选「最便宜」的执行计划。理解它，才能解释「为什么没用索引」「为什么选错了索引」「怎么干预」。

## 1. SQL 执行的完整旅程

> **背景**：发一条 SELECT 到数据库，中间发生了什么？
> **目的**：建立「SQL 是被执行引擎一步步处理」的心智。
> **适用范围**：所有调优/排查的底层框架。

```text
SQL 执行四阶段
├── ① 解析（Parser）
│   ├── 词法分析：SQL 拆成 token（SELECT/WHERE/列名……）
│   ├── 语法分析：生成语法树（语法错误在此报错）
│   └── 校验：表/列是否存在、权限检查
├── ② 预处理（Preprocessor）
│   ├── 语义检查：类型匹配、视图展开
│   └── 生成逻辑执行计划（JOIN 顺序/谓词）
├── ③ 优化（Optimizer，核心！）
│   ├── 等价重写：子查询改写/谓词下推/常量折叠
│   ├── 生成候选方案：不同索引/不同 JOIN 顺序/不同访问方式
│   ├── 成本估算：每个方案算代价（IO + CPU + 内存）
│   └── 选最低成本方案 → 物理执行计划
└── ④ 执行（Executor）
    ├── 按计划访问数据：索引扫描/全表扫描/JOIN 算法
    └── 返回结果（或缓存结果）

金句
├── 「优化」发生在执行前——优化器选完就定了
├── EXPLAIN 看到的就是「优化器选中的方案」
└── 调优 = 「让优化器的成本估算偏向你想要的方案」
```

## 2. 成本优化器：调优的核心心智

> 🎯 **MySQL 用「成本模型」选执行计划**——不是「用没用索引」，是「哪个更便宜」：

```text
成本模型（Cost Model）
├── 评估维度：
│   ├── IO 成本：读数据页次数（顺序读 vs 随机读系数不同）
│   ├── CPU 成本：行过滤/比较的运算量
│   └── 内存成本：排序/临时表（8.0 起计入）
├── 示例：100 万行表
│   ├── 方案 A（索引扫描）：IO ≈ 索引页 + 回表页（可能 2000 页）
│   ├── 方案 B（全表扫描）：IO ≈ 全表数据页（5 万页，顺序读）
│   └── 优化器选 A 或 B——取决于选择性（命中行数占比）
└── 金句：全表扫描不总是坏事——查 99% 数据时全表反而便宜

核心指标：选择性（Selectivity）
├── 选择性 = 命中行数 / 总行数
├── 选择性高（<5% 命中）→ 索引划算（回表少）
├── 选择性低（>30% 命中）→ 全表扫描可能更便宜
└── 优化器按「估算命中行数」决定——估算来自统计信息

代价（Cost）单位
├── EXPLAIN 中不直接显示成本（MySQL）——看 rows 估算行数
├── 8.0 用 optimizer_trace 看详细成本（OPTIMIZER_TRACE=ON）
└── 调优启示：让 rows 估算准确 = 让优化器决策正确
```

## 3. 统计信息：优化器的决策依据

> 🎯 **优化器靠「统计信息」猜数据分布**——统计信息过时 = 决策错误 = 选错索引：

```text
统计信息内容（InnoDB 维护）
├── 表行数（n_rows）
├── 索引基数（cardinality）：索引中不同值的个数
│   ├── cardinality / 行数 = 选择性
│   └── 基数过小（如 status 只有 3 种值）→ 优化器倾向不用该索引
└── 数据分布（8.0 直方图 histogram——范围查询更准）

统计信息的收集方式
├── 采样收集：InnoDB 随机采样 8 个页估算（默认）
│   ├── 数据量变小时估算可能不准
│   └── 表变大/分布变化 → 统计信息过时
├── ANALYZE TABLE：手动重新收集（调优标准动作！）
│   └── 表结构/数据大变化后必做
└── 自动更新：超过 10% 行变化自动重算（默认阈值）

优化器选错索引 → 先做三件事（官方推荐顺序）
├── ① ANALYZE TABLE 更新统计信息（最可能解决）
├── ② 索引提示干预：USE INDEX / FORCE INDEX / IGNORE INDEX
│   └── FORCE INDEX：告知「用该索引成本更低」（比 USE 更强硬）
├── ③ 系统变量：max_seeks_for_key（告诉优化器键查找上限）
└── ④ 改写 SQL（最差手段——先试统计信息与提示）
```

```sql
-- 调优标准动作
ANALYZE TABLE t_order;                    -- 重新收集统计信息
SHOW INDEX FROM t_order;                  -- 查看基数（Cardinality 列）
SELECT * FROM t_order FORCE INDEX (idx_user_id) WHERE user_id = 10086;
SELECT STRAIGHT_JOIN ... FROM t_big t1, t_small t2 ...   -- 强制连接顺序
```

## 4. 优化器的常见重写

> 🎯 **优化器会自动改写 SQL**——有些「你以为的低效写法」实际被优化了；有些则没有：

```text
① 常量折叠与表达式化简
├── WHERE id = 1 + 2 → WHERE id = 3（常量提前算好）
└── WHERE id = 10086 OR id = 10087 → IN (10086, 10087) 语义等价

② 谓词下推（Predicate Pushdown）
├── 外层条件推进内层（JOIN/视图场景）
└── 效果：先过滤再 JOIN（减少中间结果）

③ 子查询改写
├── IN 子查询 → 半连接（Semi-join）
├── EXISTS → 半连接/物化（按成本选择）
└── 8.0 起：派生表合并/延迟物化（Derived table merge）

④ 行构造器优化（MySQL 9 手册明确）
├── WHERE (c1,c2) = (1,1) 与 c1=1 AND c2=1 语义等价
├── 但：行构造器 + AND/OR 混用时可能只用到部分索引！
│   └── (c1,c2) > (1,1) 混合 c1=1 → 可能只用 c1（key_len 变小）
└── 建议：避免行构造器与 AND/OR 混用——改写为展开表达式

⑤ 生成列索引（MySQL 9 亮点）
├── 表达式无法直接建索引 → 建生成列 + 索引
│   └── gc INT AS (f1 + 1) STORED → 索引 gc
├── 查询 WHERE f1 + 1 > 9 自动匹配该索引（表达式完全一致时）
└── 注意：表达式必须逐字匹配（1 + f1 不匹配 f1 + 1）
```

> 💡 **判断优化器是否重写了**：`EXPLAIN ... SHOW WARNINGS` 查看优化后的 SQL；或 OPTIMIZER_TRACE 看完整决策过程。

## 5. 为什么选错索引：原因与干预

> 🎯 **优化器选错索引 = 统计信息失真或估算偏差**——2026 官方调优手册的完整干预体系：

```text
选错索引的典型原因
├── ① 统计信息过时：表变化大但没 ANALYZE
├── ② 估算偏差：采样不准（8 页采样在小表/数据分布不均时失真）
├── ③ 低基数索引：status 类字段选择性差——优化器直接放弃
├── ④ 多列条件复杂：优化器算错「联合索引 vs 单列索引」的组合成本
└── ⑤ 参数/环境：内存小 → 排序成本高 → 优化器绕开索引排序

干预手段（从轻到重）
├── L1 ANALYZE TABLE：更新统计信息（90% 场景够用）
├── L2 索引提示：
│   ├── USE INDEX (idx)   ——建议
│   ├── FORCE INDEX (idx) ——强制（比 USE 更强硬）
│   └── IGNORE INDEX (idx) ——禁用（测试对比）
├── L3 不可见索引（Invisible Index，低风险调优神器！）
│   ├── ALTER TABLE ... ALTER INDEX idx INVISIBLE
│   ├── 索引对优化器「不可见」但仍在维护
│   ├── 用途：A/B 对比（不可见 → 看执行计划变化 → 验证后再删）
│   └── 金句：调优测试的「回滚开关」——比直接 DROP 安全
├── L4 STRAIGHT_JOIN：强制连接顺序（对 JOIN 场景）
├── L5 max_seeks_for_key：告诉优化器键查找的假设上限
└── L6 SQL 改写：拆查询/改写谓词（最后手段）
```

## 6. MySQL 8.0+ / 9.x 优化器演进

> 🎯 **优化器在持续进化**——2026 新项目直接用 8.0+/9.x 才能吃到红利：

```text
8.0（2018，长期支持）的优化器大版本
├── 成本模型升级：加入内存成本
├── 直方图：范围查询估算更准
├── 反连接/半连接改进：NOT IN 性能
├── 哈希连接（Hash Join）：8.0.18+ 等值 JOIN 飞跃（见 [[05]]）
├── 窗口函数/CTE：写法更高效
└── EXPLAIN ANALYZE（8.0.18+）：真实执行 + 实际耗时（不是估算！）

9.x（2025+，持续迭代）的新特性
├── 生成列索引优化：表达式自动匹配索引（见第 4 节）
├── 行构造器优化：避免部分索引退化
├── 优化器问题修复持续（9.7 手册 optimizer-issues）
└── 更多能力：向量/JSON 查询优化（AI 场景）

版本选择建议（2026）
├── 生产：8.0 LTS（稳妥）或 8.4 LTS / 9.x（新特性）
├── 新项目：8.4+（8.0 系列优化器完整成熟）
└── 金句：优化器特性是「版本红利」——老 5.7 没有 Hash Join/直方图
```

> ⚠️ **5.7 时代的老经验要更新**：5.7 里「IN 子查询慢」「JOIN 大表慢」的很多坑在 8.0+（Hash Join/物化优化）已不存在——**调优文档要看 8.0+/9.x，别背 5.7 的旧结论**。

## 7. 核心要点

> 🎯 **核心要点**：
> 1. **四阶段旅程**：解析 → 预处理 → 成本优化 → 执行——EXPLAIN 看的是「优化结果」
> 2. **成本优化器**：选「最便宜」不是「用没用索引」——选择性决定一切
> 3. **统计信息是决策依据**：ANALYZE TABLE 是调优第一动作
> 4. **优化器自动重写**：谓词下推/半连接/生成列索引——SHOW WARNINGS 看真实 SQL
> 5. **选错索引六层干预**：ANALYZE → USE/FORCE → **不可见索引（低风险 A/B）** → STRAIGHT_JOIN → 参数 → 改写
> 6. **版本红利**：8.0+ 才有 Hash Join/直方图/EXPLAIN ANALYZE——调优文档认准新版
