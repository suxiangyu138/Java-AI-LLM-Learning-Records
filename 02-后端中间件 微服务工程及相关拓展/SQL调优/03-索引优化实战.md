## 1. 索引设计方法论

> **背景**：慢查询 80% 是索引问题——要么没索引，要么索引设计不对。
> **目的**：掌握「先分析查询，再设计索引」的工程顺序。
> **适用范围**：所有 WHERE/ORDER BY/GROUP BY/JOIN 场景。

```text
索引设计三步（先分析再动手）
├── ① 收集高频查询（业务视角）
│   ├── 慢日志 TopN + 高频接口 SQL
│   └── 合并同类查询（同一个表/同一组条件）
├── ② 分析每条的访问模式
│   ├── 等值条件：= / IN → 放索引前面
│   ├── 范围条件：> / BETWEEN / LIKE 前缀 → 放后面
│   ├── 排序：ORDER BY → 尽力并入索引
│   └── 分组：GROUP BY → 覆盖分组列
└── ③ 设计联合索引（一石多鸟）
    ├── 一个联合索引服务多类查询（等值 + 范围 + 排序）
    └── 宁少勿多：每多一个索引 = 写放大（插入/更新变慢）

金句
├── 「索引是给查询建的，不是给表建的」
├── 一个表 5-8 个索引是上限（写放大权衡）
└── 读多写少表可以多建，写密集表要克制
```

## 2. 最左前缀：联合索引的灵魂

> 🎯 **联合索引 (a, b, c) 的匹配规则**——查询条件必须从最左列开始「接力」：

```text
索引 (a, b, c) 能服务的查询
├── WHERE a = 1                      ✅ 用 a
├── WHERE a = 1 AND b = 2            ✅ 用 a, b
├── WHERE a = 1 AND b = 2 AND c = 3  ✅ 用 a, b, c（完全匹配）
├── WHERE b = 2                      ❌ 跳过 a —— 索引失效！
├── WHERE c = 3 AND b = 2            ❌ 没从 a 开始
└── WHERE a = 1 AND c = 3            ⚠️ 只用 a（b 断档，c 用不上）

关键边界
├── 等值条件可以乱序：WHERE b=2 AND a=1 → 优化器自动调整 ✅
├── 范围条件断档：WHERE a=1 AND b>10 AND c=3
│   └── b 用范围 → c 无法接力（b 范围后索引中断）
├── ORDER BY 也能走最左前缀
│   └── WHERE a=1 ORDER BY b → 索引内已有序（无 filesort）
└── 金句：联合索引是「接力棒」——从 a 开始，断一处全断

设计口诀
├── 等值条件放最前（可乱序，优化器调整）
├── 范围条件放中间偏后（断档止损）
├── 排序字段紧跟其后（一石二鸟）
└── 覆盖查询列收尾（覆盖索引，见第 4 节）
```

## 3. 索引失效场景全清单

> 🎯 **索引明明存在却不用——失效场景清单**（面试必背 + 实战自查）：

```text
① 函数/表达式包裹列（索引列裸奔失效）
├── WHERE DATE(create_time) = '2026-01-01'   ❌
│   └── 改：WHERE create_time >= '2026-01-01' AND create_time < '2026-01-02' ✅
├── WHERE id + 1 = 100                       ❌
│   └── 改：WHERE id = 99                    ✅
├── WHERE LEFT(name, 3) = 'abc'              ❌
└── 生成列解法：表达式无法改 → 建生成列 + 索引（见第 6 节）

② 隐式类型转换
├── 索引列是 varchar，条件传数字
│   └── WHERE phone = 13800000000  （phone 是 VARCHAR）❌
│   └── 改：WHERE phone = '13800000000'      ✅
└── 判断：EXPLAIN 的 key 为 NULL 时检查类型

③ 前导模糊查询
├── WHERE name LIKE '%abc%'    ❌（前导 % 无法走索引）
├── WHERE name LIKE 'abc%'     ✅（前缀匹配可走索引）
└── 全文场景：用 FULLTEXT 索引 / ES（[[04-Elasticsearch]]）

④ OR 连接非索引条件
├── WHERE a = 1 OR b = 2（b 无索引）❌
│   └── 改：UNION 拆两条 / 给 b 建索引
└── 注意：OR 两边都有索引 → 优化器可能用 index_merge 合并

⑤ NOT IN / NOT EXISTS（不等判断）
├── WHERE status NOT IN (1, 2)   ⚠️ 大概率全表
└── 改：业务上尽量用正向条件

⑥ 优化器「觉得」不用更好（不是失效！）
├── 小表全表扫描比索引快（表 < 千行）
├── 低选择性：status 只有 3 个值 → 全表更便宜
└── 金句：别只怪「失效」——先看选择性（[[01]] 成本模型）
```

> ⚠️ **失效自查顺序**：函数包裹 → 类型转换 → 前导 % → OR → 优化器选择（EXPLAIN 确认，别猜）。

## 4. 覆盖索引：免回表

> 🎯 **覆盖索引 = 查询所需列全在索引里**——索引直接返回数据，零回表：

```text
回表是什么
├── 普通索引只存「索引列 + 主键」
├── 查到索引 → 拿主键 → 回聚簇索引取整行 → 回表
└── 回表次数 = 命中行数（大范围查询回表多 → 慢）

覆盖索引（Extra: Using index）
├── 查询列 ⊆ 索引列 → 数据全在索引里 → 不回表
├── 示例：
│   ├── 索引 (user_id, status)
│   └── SELECT status FROM t WHERE user_id = 1 → 覆盖 ✅
│   └── SELECT amount FROM t WHERE user_id = 1 → 需回表 ❌

设计权衡（覆盖索引的取舍）
├── 好处：省回表 IO（大范围查询收益显著）
├── 代价：索引变大（更多列 = 更大 B+Tree）
│   ├── 索引列太长 → 页能放的条目少 → 树变深
│   └── 写放大（更新覆盖列要维护索引）
└── 适用：高频查询的「常用列组合」——不是所有列都塞索引

实践案例
├── 订单列表页（高频）：索引 (user_id, create_time) + 查询列
│   SELECT id, order_no FROM t WHERE user_id=? ORDER BY create_time DESC
├── 列多时取舍：选「高频 + 短」列进索引
└── 金句：覆盖索引 = 「用空间换回表 IO」——高频场景值得
```

## 5. ICP 索引下推

> 🎯 **ICP（Index Condition Pushdown，8.0 默认开启）**——**索引层先过滤，再回表**：

```text
没有 ICP（5.6 前）
├── 联合索引 (name, age)
├── WHERE name LIKE '张%' AND age > 30
├── 索引取回所有「张%」行 → 回表 → 再过滤 age
└── 回表浪费（大量不满足 age 的行也回表了）

有 ICP（Extra: Using index condition）
├── 索引遍历时直接判断 age > 30 → 只回表满足条件的行
└── 回表行数大幅减少（索引层过滤）

ICP 的意义
├── 范围/模糊场景收益大（过滤发生在回表前）
├── 无需改 SQL/索引——版本红利（8.0 默认开）
└── 看到 Extra: Using index condition = 正常的好状态

对比（三档状态）
├── Using index（覆盖索引）——最好，零回表
├── Using index condition（ICP）——好，少回表
└── 无 Extra/Using where——普通回表（可考虑覆盖/调整）
```

## 6. 生成列索引与表达式优化

> 🎯 **表达式查不了索引的「官方解法」**——生成列（MySQL 9 优化器自动匹配）：

```sql
-- 场景：WHERE price * quantity > 1000 无法用 price 索引
-- ① 建生成列（STORED 存储值）
ALTER TABLE t_order
  ADD COLUMN amount DECIMAL(10,2)
  GENERATED ALWAYS AS (price * quantity) STORED;
-- ② 生成列上建索引
ALTER TABLE t_order ADD INDEX idx_amount (amount);
-- ③ 查询改为匹配生成列（或直接写原表达式——9.x 优化器自动匹配）
SELECT * FROM t_order WHERE amount > 1000;
-- 9.x 甚至支持：WHERE price * quantity > 1000 自动匹配生成列索引
```

```text
生成列索引的要点（MySQL 9.7 手册）
├── 表达式必须「完全一致」才能自动匹配（1 + f1 ≠ f1 + 1）
├── 适用运算符：= / < / <= / > / >= / BETWEEN / IN
├── 生成列必须包含函数或运算符（纯列引用不行）
├── JSON 表达式可能需要 JSON_UNQUOTE() 匹配
└── 验证：EXPLAIN 看 key + SHOW WARNINGS 看重写 SQL

适用场景清单
├── 日期函数：DATE(create_time) 类查询
├── 计算字段：price * quantity 类
├── JSON 字段提取：JSON_EXTRACT(data, '$.name')
└── 字符串处理：LOWER(email) 类
```

> 💡 **另一个官方技巧**：`WHERE LEFT(name, 3) = 'abc'` 改写成 `WHERE name LIKE 'abc%'` 也能走索引——能改写的优先改写，改不了的用生成列。

## 7. 索引设计规范

> 🎯 **大厂索引设计规范**（建表/评审时对照）：

```text
① 命名与元数据
├── 索引名：idx_字段名（唯一：uk_，全文：ft_）
├── 每表索引数：≤ 8 个（写放大权衡）
├── 复合索引列数：≤ 4-5 列（再多收益递减）
└── 大字段（TEXT/BLOB）不建普通索引（用前缀索引）

② 字段选择
├── 选择性高的列优先（user_id > status）
├── 短列优先（索引大小 = 页条数）
├── 字符串长列：前缀索引（INDEX(name(10))）——取舍
└── 低基数列（性别/状态）单独建索引收益低（组合使用）

③ 维护规范
├── 加索引评估：EXPLAIN 验证 + 上线窗口（表锁风险）
├── 大表加索引：pt-online-schema-change / gh-ost（在线变更）
├── 删除废弃索引：冗余索引检测（(a,b) 含 (a)——后者冗余）
└── 定期检查：information_schema.statistics 审计

④ 常见冗余索引检测
├── 索引 (a, b) 与索引 (a) 冗余（(a) 可删）
├── 索引 (a, b) 与索引 (b) 不冗余（顺序不同）
└── 工具：pt-duplicate-key-checker 检测
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. **设计三步**：收集高频查询 → 分析访问模式 → 设计联合索引（宁少勿多）
> 2. **最左前缀**：接力棒从 a 开始——等值可乱序、范围断档、ORDER BY 可并入
> 3. **失效六场景**：函数包裹/类型转换/前导 %/OR/NOT IN/优化器选择——EXPLAIN 确认
> 4. **覆盖索引**：查询列 ⊆ 索引列 → 零回表（Extra: Using index）——高频场景值得
> 5. **ICP**：索引层先过滤再回表（8.0 默认）——Extra: Using index condition 是好状态
> 6. **生成列索引**：表达式场景官方解法（9.x 自动匹配，表达式必须逐字一致）
> 7. **规范**：≤8 索引、选择性优先、在线 DDL、冗余检测
> 8. **金句**：索引是给查询建的；写放大与查询加速的平衡
