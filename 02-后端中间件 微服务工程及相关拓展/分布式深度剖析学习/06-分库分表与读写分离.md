# 06 - 分库分表与读写分离

> **核心摘要**：数据库水平扩展的两板斧：**读写分离**（一主多从扛读流量）与**分库分表**（数据切分扛数据量）。核心技术点：分片键设计（选错 = 查询全路由）、ShardingSphere 集成、**扩容难题**（分片数不可轻易变）、主从复制原理（binlog 三种格式）。2026 共识：**分库分表是「最后的弹药」**——先用缓存/归档/冷热分离，数据量真到了再分。

## 1. 分层的演进：从单库到分片

> **背景**：数据量/流量增长，单库单表有天花板（单表 500w-2000w 行性能拐点、单库连接/磁盘上限）。
> **目的**：按「先易后难」的顺序理解演进路径——别一上来就分库分表。
> **适用范围**：数据治理路线图（2026 架构师必修）。

```text
演进阶梯（每一步都在上一级不够时再走）
├── ① 优化 SQL/索引：先排查慢查询（90% 的「数据量大」是索引问题）
├── ② 缓存：读多写少 → 缓存挡流量（见 [[04]]）
├── ③ 归档：历史数据冷热分离（3 年前数据移归档表/库）
├── ④ 读写分离：读流量大 → 一主多从（数据量未超）
├── ⑤ 垂直拆分：业务模块拆库（订单库/用户库/商品库——微服务自带）
├── ⑥ 水平分表：单表数据量超拐点 → 按分片键拆表
├── ⑦ 水平分库：单库容量/连接超限 → 拆到多库（分片分布式）
└── ⑧ 混合：分库 + 分表 + 读写分离（大厂最终形态）

金句
├── 「先优化，再缓存，再归档，最后才分片」
├── 分库分表是「不可逆的高成本手术」——做了就很难回来
└── 2026 大厂口径：80% 系统到不了分片那一步（缓存+归档已够）
```

## 2. 读写分离：一主多从

> 🎯 **读写分离 = 主库写、从库读**——读流量翻几倍都扛得住（一台主 + N 台从）：

```text
架构
├── 主库（Master）：只处理写（INSERT/UPDATE/DELETE）
├── 从库（Replica × N）：只处理读（SELECT）
├── 复制：主库 binlog → 从库应用（异步复制，毫秒~秒级延迟）
└── 路由：应用层/中间件层决定读走从、写走主

路由方式
├── 应用层：Spring 读写分离（AbstractRoutingDataSource，手写）
├── 中间件层：ShardingSphere（规则配置，推荐）
└── 代理层：MyCat/ProxySQL（SQL 级代理，运维友好但多一跳）

延迟问题的解决
├── 问题：写主后立刻读从 → 读到旧值（复制延迟）
├── ① 关键读走主：支付结果/登录态（强制主库读）
├── ② 半同步复制：主等一个从 ack 才提交（收窄窗口）
├── ③ 会话粘滞：同一用户写后秒内读 → 路由回主库
└── ④ 缓存兜底：读从库前先查缓存
```

> ⚠️ **读写分离 ≠ 数据量大，是「读流量大」**——数据量小但读 QPS 高（如活动页）同样适用；数据量大但读少（如日志库）则相反。

## 3. 主从复制原理：binlog 深度

> 🎯 **主从复制 = 基于 binlog 的日志回放**——理解 binlog 格式与复制链路，才能解决延迟/丢失：

```text
复制链路三线程
├── ① 主库 dump 线程：推送 binlog 给从库
├── ② 从库 IO 线程：接收 binlog → 写入 relay log（中继日志）
├── ③ 从库 SQL 线程：回放 relay log → 应用数据变更
└── 延迟点：IO 线程落后（网络/大事务）/ SQL 线程落后（单线程回放）

binlog 三种格式（面试必考）
├── STATEMENT（语句级）：记录 SQL 原文
│   ├── 体积小；但非确定性函数（NOW()/UUID()）主从不一致
├── ROW（行级，5.7+ 默认）：记录每行变更前后值
│   ├── 最精确（任意函数安全）；体积大（批量更新爆炸）
├── MIXED：语句级为主，不确定时自动切行级
└── 工程结论：生产用 ROW（Canal 等 binlog 消费也依赖 ROW）

复制模式
├── 异步复制：主不等待 → 延迟小，故障丢数据
├── 半同步复制（Semisync）：主等至少一个从 ack
│   ├── 丢数据窗口收窄为「主+从同时挂」
│   └── 性能代价：每次写多一次往返
└── 组复制（MGR，MySQL 8）：多数派共识——强一致但复杂

延迟排查（从库 Seconds_Behind_Master）
├── 大事务：一次 UPDATE 全表 → 回放耗时
├── 从库硬件差：CPU/IO 跟不上
├── 主库写入并发高：SQL 线程单线程回放（MTS 多线程可缓解）
└── 网络：IO 线程拉取慢
```

## 4. 分库 vs 分表 vs 垂直 vs 水平

> 🎯 **四个概念先理清**——两对维度交叉：

```text
两对维度
├── 按拆法：垂直（按业务列/表拆）vs 水平（按行数据拆）
├── 按粒度：分库（拆到多库）vs 分表（拆成多表）
└── 组合出四种：
    ├── 垂直分库：订单库/用户库/商品库（微服务天然形态）
    ├── 垂直分表：大字段表拆（detail 拆出去——现代 SSOT）
    ├── 水平分表：order_0/order_1/...（同库多表）
    └── 水平分库：db_0/db_1（多库多表，大厂最终态）

垂直拆分（先做，成本低）
├── 依据：业务域/字段访问频率
├── 案例：user 表拆 user_base + user_detail（热点字段 vs 冷字段）
├── 收益：单表变窄、热点行变小、缓存命中提高
└── 注意：垂直拆分后跨表 JOIN 变难 → 先评估查询形态

水平拆分（后做，成本高）
├── 依据：数据量/单表行数超拐点（500w-2000w 视硬件）
├── 案例：order 按 user_id 拆 16 张表
├── 收益：单表行数降 1/N，写压力分散
└── 注意：分片键外的查询全表路由（见第 5 节）
```

## 5. 分片键：最重要的决策

> 🎯 **分片键选错了，系统就废了**——90% 的查询都要带上它：

```text
分片键选择标准
├── ① 查询频率最高：绝大多数查询用它定位（用户查询自己的订单）
├── ② 分布均匀：值域分布均匀（user_id 好；订单状态差）
├── ③ 不可变：主键类（用户 id/订单 id）——变了 = 数据搬家
└── ④ 支持范围查询的退化：范围查询会变广播（所有分片查一遍）

路由算法
├── 哈希取模：user_id % 16 → 0-15 号表
│   ├── 分布均匀 ✅；扩容必须翻倍（见第 7 节）
├── 范围分片：按时间/ID 区间（2025 表/2026 表）
│   ├── 扩容友好 ✅；热点集中（新数据全写最新表）
├── 一致性哈希：减少迁移量（环上映射）
│   └── 复杂度高，少用
└── 雪花 ID 分片：ID 本身带时间+机器 → 直接取模（[[02]] 联动）

选错分片键的后果（经典反面教材）
├── 按 status 分片：99% 数据都在「已完成」片 → 热点片
├── 按日期分片 + 写热点：全部写今天 → 单表爆炸
└── 补救成本：全量数据迁移（≈重新做一遍系统）
```

## 6. ShardingSphere 实战

> 🎯 **ShardingSphere（Apache 顶级项目，2026 主流）**——分库分表 + 读写分离 + 数据脱敏一体化中间件：

```yaml
# ShardingSphere-JDBC 配置（应用内嵌，推荐；5.x 语法）
rules:
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_${0..1}.t_order_${0..15}   # 2库×16表
        tableStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: order_inline
        keyGenerateStrategy:
          column: id
          keyGeneratorName: snowflake            # 内置雪花 ID
    bindingTables: t_order, t_order_item         # 绑定表（避免笛卡尔）
    broadcastTables: t_config                    # 广播表（全库同结构）
  - !READWRITE_SPLITTING
    dataSources:
      ds_0:
        writeDataSourceName: ds_0_master
        readDataSourceNames: [ds_0_slave_0, ds_0_slave_1]
        loadBalancerName: round_robin

shardingAlgorithms:
  order_inline:
    type: INLINE
    props:
      algorithm-expression: t_order_${user_id % 16}   # 分片表达式

keyGenerators:
  snowflake:
    type: SNOWFLAKE
```

```java
// 使用（应用无感知：SQL 自动改写）
@Mapper
public interface OrderMapper {
    // 自动路由：user_id=10086 → t_order_10 表
    @Select("SELECT * FROM t_order WHERE user_id = #{userId}")
    List<Order> listByUser(Long userId);

    // 无分片键的查询 → 广播到 32 张表再合并（慢！要避免）
    @Select("SELECT * FROM t_order WHERE status = 1")
    List<Order> listByStatus(Integer status);
}
```

**ShardingSphere 两种形态**：

| 形态 | 模式 | 优点 | 缺点 |
|------|------|------|------|
| ShardingSphere-JDBC | 应用内嵌（增强 JDBC） | 性能好/无额外组件 | 每应用一套配置 |
| ShardingSphere-Proxy | 独立代理（SQL 网关） | 多语言/运维友好 | 多一跳延迟 |

> ⚠️ **绑定表（bindingTables）必配**：order 与 order_item 同分片键时，JOIN 只关联同片表（否则笛卡尔积扫描 16×16=256 组）。

## 7. 扩容难题与方案

> 🎯 **扩容是分库分表的「渡劫」**——取模分片下，加一张表 = 所有数据的路由结果全变（2 张表 → 4 张表，旧数据 hash 结果全不对）：

```text
扩容困境（取模分片）
├── 原：user_id % 2 → 2 张表
├── 扩容：user_id % 4 → 4 张表
├── 问题：user_id=5 原来在表1（5%2=1），现在在表1（5%4=1）？
│   └── 不对！5%2=1, 5%4=1 巧合而已——大量数据路由变化
├── 全量重哈希：所有历史数据重新分片（停机迁移/双写迁移）
└── 金句：取模分片「扩容=重分片」，提前想好

扩容方案
├── ① 翻倍扩容 + 全量迁移（最简单也最重）
│   ├── 停机：备份 → 新集群 → 回放 binlog → 切流量
│   ├── 不停机（双写）：双写新旧 → 追平 → 切读
│   └── 工具：canal/数据同步工具（数据迁移 = binlog 回放）
├── ② 一致性哈希：扩容只迁部分数据
│   └── 但路由计算复杂，实际采用少
├── ③ 范围分片：天然免迁移（新表直接建）
│   └── 热点问题用「分片键前置设计」缓解
├── ④ 中间层表（映射表）：id → 位置 动态路由
│   └── 灵活但多一次查询
└── ⑤ 预分片：一步到位分 1024 片（多数表空闲）
    ├── 初期浪费（空表多）
    └── 但 10 年内不用动分片——大厂常用「预分片 + 归档」
```

> 💡 **2026 主流实践**：**预分片（一次分够）+ 冷热归档**——分片数按 3-5 年峰值设计（如 1024 表），日常只写热表，历史归档冷库；永远不触发「扩容重分片」这个大手术。

## 8. 分片后的痛：全局ID/事务/查询

> 🎯 **分片解决「容量」，带来「四痛」**——都需要配套方案：

```text
① 全局主键（分片表不能自增了）
├── 方案：雪花/号段（[[02]]）——ShardingSphere 内置雪花生成器
└── 注意：ID 即分片依据时，生成器与分片算法配套设计

② 分布式事务（跨分片写）
├── 方案：Seata（[[05]]）——AT/TCC 按业务选
└── 注意：ShardingSphere + Seata 整合（数据源代理叠加）

③ 聚合查询（GROUP BY/ORDER BY/COUNT）
├── 中间件做「分片并行执行 + 结果合并」
├── 深分页问题：LIMIT 100000,10 → 每片都取 100010 条再合并
│   ├── 方案：游标分页（WHERE id > ? LIMIT 10）——别用 OFFSET
│   └── 方案：两次查询（先取 ID，再回表）
└── 关联查询（JOIN）
    ├── 绑定表同片 JOIN ✅
    ├── 不同片 JOIN → 代码层聚合/宽表/ES 冗余（[[04-Elasticsearch]]）
    └── 金句：分片后「能省的 JOIN 全省掉」——宽表 + 冗余 + 最终一致

④ 分布式查询与统计
├── 运营报表：独立数仓（ETL 汇聚分片数据）
├── 搜索：ES 冗余索引（分片数据同步）
└── 实时统计：不对分片跑，对缓存/ES 跑
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. **演进阶梯**：索引 → 缓存 → 归档 → 读写分离 → 垂直 → 水平（最后才分片）
> 2. **读写分离解读流量**：主写从读 + 半同步收窄窗口 + 关键读走主
> 3. **binlog 三格式**：STATEMENT/ROW/MIXED——生产 ROW（Canal 消费依赖）
> 4. **四种拆分**：垂直分库（业务域）/垂直分表（字段）/水平分表/水平分库
> 5. **分片键四标准**：高频查询、分布均匀、不可变、支持退化查询
> 6. **ShardingSphere**：INLINE 表达式 + 绑定表必配 + 内置雪花主键
> 7. **扩容 = 重分片**：取模扩容全量迁移——预分片 + 归档是 2026 主流
> 8. **四痛配套**：雪花全局 ID + Seata 事务 + 游标分页 + 宽表去 JOIN
> 9. **金句**：分库分表是最后弹药——先优化，再缓存，再归档
