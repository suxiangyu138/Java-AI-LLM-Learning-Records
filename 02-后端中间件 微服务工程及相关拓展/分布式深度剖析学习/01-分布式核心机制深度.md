## 1. 分布式为什么难：两个基本事实

> **背景**：单机系统一切确定（共享内存/单时钟/单故障域）；分布式把这三个前提全部打破。
> **目的**：建立「困难来自何处」的心智模型。
> **适用范围**：后续所有专题的思考起点。

```text
两个基本事实（一切分布式难题的根源）
├── 事实一：没有全局时钟
│   ├── 每台机器时钟独立（NTP 同步也只是尽力而为）
│   ├── 「A 在 B 之前发生」无法用墙上时钟可靠判断
│   └── → 需要逻辑时钟/顺序协议（见第 3 节）
├── 事实二：网络不可靠
│   ├── 消息可能丢失/延迟/乱序/重复
│   ├── 无法区分「节点挂了」和「网络分区」（50% 假死）
│   └── → 需要超时/重试/幂等/仲裁（见第 4 节及 [[07-分布式幂等与调度]]）

派生难题清单
├── 数据不一致（复制延迟/冲突）
├── 分布式事务（多库原子性）
├── 分布式锁（互斥 vs 可用）
├── 故障转移（假死导致双活）
├── 时钟依赖（ID/过期时间/排序）
└── 金句：先承认「没全局时钟、网络不可靠」，再谈方案
```

## 2. 时间与顺序：时钟深度

> 🎯 **墙上时钟在分布式里「不可信」**——但工程上仍广泛使用，理解它的失效模式才能正确使用：

```text
时钟的三种角色
├── ① 绝对时间（墙上时钟）：NTP 同步，精度毫秒~秒级
│   ├── 用途：过期时间（锁/缓存 TTL）、审计日志
│   └── 失效模式：时钟漂移/回拨（NTP 调整可让时间倒退！）
├── ② 单调时钟（monotonic）：只增不减
│   ├── 用途：测量耗时、Raft 选举超时
│   └── 安全：不随 NTP 回退（跨进程不共享）
└── ③ 逻辑时钟：事件顺序的数学抽象（见第 3 节）

NTP 与回拨问题（工程坑）
├── NTP 校时可能把本地时钟往前调 → 时间回拨
├── 雪花算法依赖时间戳 → 回拨导致 ID 重复（见 [[02]] 的解法）
├── Redis 过期依赖服务器时钟 → 时钟回拨让 TTL 失效时间错乱
└── 对策：监控时钟偏移、ID 生成器容忍回拨（毫秒级等待）

面试必答：什么场景必须单调时钟？
├── 分布式锁续期判断（Redisson 用 System.currentTimeMillis？
│   → 实际是 nanoTime/绝对值混合，见 [[03]]）
└── 高精度排序：用递增版本号/序号替代时间戳
```

## 3. 逻辑时钟：Lamport 与向量时钟

> 🎯 **逻辑时钟用「计数器」定义事件的先后**——不依赖物理时间，只依赖因果关系（happens-before）：

```text
Lamport 时钟（单值逻辑时钟）
├── 规则：本地事件 +1；发消息携带自己的时间戳；
│   收消息时取 max(本地, 对方+1)
├── 能力：保证因果序（cause → effect 必然 t(cause) < t(effect)）
├── 局限：t(A) < t(B) 不能推出 A 在 B 前（无因果的两个事件）
└── 应用：Raft 任期号、版本号比较

向量时钟（每个节点一个分量）
├── 规则：每个节点维护整个集群的计数器向量
├── 能力：可以判断「无因果关系」（并发冲突检测）
├── 代价：存储 O(N)（节点数），大集群不可行
└── 应用：Dynamo/Riak 的冲突检测（版本合并）

工程对比
├── 日志排序/分布式 ID → Lamport 足够
├── 多主写入的冲突检测 → 需要向量时钟（或 LWW 时间戳胜负）
└── 金句：Lamport 定因果序，向量时钟辨并发——按需选用
```

## 4. 脑裂与仲裁

> 🎯 **脑裂（Split Brain）= 网络分区后集群分裂成两个「活」的组**——各自主导读写，数据分裂。所有分布式系统都要回答「如何检测并解决脑裂」：

```text
脑裂的典型场景
├── ZooKeeper：3 节点分裂成 1+2，旧 Leader 与 2 节点组各自为政
├── Redis 哨兵：Master 假死，旧主恢复后与新主并存
├── MySQL 主从：双主互写（配置错误/人为）
└── 后果：数据双写、ID 冲突、缓存互踩——全线雪崩

解决机制：仲裁（Quorum）与法定人数
├── 多数派原则：任何决策需要 N/2+1 节点同意
│   ├── ZK 3 节点可容忍 1 个故障（2 存活即可选主）
│   ├── ZK 5 节点可容忍 2 个故障
│   └── 奇数节点设计（4 vs 5 都容错 1，但 5 更稳）
├── 选主（Leader Election）：分区后只有多数派组能选出新 Leader
│   ├── Raft：任期 + 选票多数
│   └── ZK：ZAB + epoch 递增
├── Fencing Token（防护令牌）：旧主操作被令牌拒绝
│   ├── 每次选主递增 token
│   └── 旧 Leader 的写请求携带旧 token → 存储拒绝
└── 金句：用「多数派」换「安全」——少数派只能等分区恢复

工程要点
├── 集群节点数：3/5/7 奇数（容忍 1/2/3 故障）
├── 读写 quorum：W+R > N 才保证读最新（见 [[04-缓存]]）
└── 故障恢复：旧主回归 → 降级为从（绝不自动双主）
```

## 5. 最终一致性模型

> 🎯 **BASE 不是「放弃一致性」而是「换了一致性的时间窗口」**——工程上最常见的模型，理解其收敛条件：

```text
最终一致性（Eventual Consistency）
├── 定义：停止写入后，经过足够时间所有副本收敛到同一值
├── 特性：读可能读到旧值（stale read）——但有界收敛时间
├── 变体（按强度排列）
│   ├── 因果一致性：有因果关系的读必新（最强实用级）
│   ├── 读己之写：自己写的自己立刻读到（会话内）
│   ├── 单调读：不读到比之前更旧的值
│   └── 单调写：写顺序一致（最简单）
└── 收敛保障三要素
    ├── ① 冲突解决：LWW（最后写胜）/版本合并/业务规则
    ├── ② 反熵机制：读修复/后台对账/CDC 补偿
    └── ③ 单调性：写操作全部落到同一主（单主架构天然收敛）

工程形态（常见组合）
├── MySQL 主从（异步复制）：读可能滞后毫秒~秒级
│   └── 修正：半同步复制（主等从 ack）收窄窗口
├── Redis 主从（异步）：同上
├── 消息队列 + 事件补偿：异步解耦 + 对账任务兜底
└── 金句：最终一致性 = 一致性 + 收敛时间预算——业务能接受多长的窗口？
```

## 6. CAP 的工程权衡

> 🎯 **CAP 常被误读为「三选二」**——真实表述是：**网络分区必然发生（P 不是选项），你要在分区期间选择 A 还是 C**：

```text
CAP 正确理解
├── 分区（P）：网络分区必然发生（无法避免，不是选择）
├── 分区期间的二选一：
│   ├── 选一致性（CP）：拒绝服务部分请求（ZK/etcd/Raft）
│   └── 选可用性（AP）：容忍读到旧值（Redis 主从/ES/Dynamo）
├── 分区恢复后：系统可以「同时」满足 A 和 C（收敛）
└── 金句：不是「三选二」，是「分区时二选一，恢复后尽力兼得」

工程实践（按业务分级）
├── 强一致需求：账户余额/库存扣减/支付 → CP 或事务
│   ├── 单库事务（本地 ACID）
│   ├── 分布式事务（见 [[05]]）
│   └── 共识系统（Raft 选主/配置）
├── 最终一致可接受：订单状态/文章阅读量/缓存 → AP + 收敛
│   ├── Redis 缓存（TTL 收敛）
│   ├── 消息异步（重试+对账）
│   └── 读多写少 + 宽松 SLA
└── 统一原则：按「数据重要性」分级定策略——不是一刀切

一致性级别的工程选型表
├── 强一致 → 单库/分布式锁/同步复制/CP 中间件
├── 读己之写 → 会话粘滞 + 主读从写
├── 有界陈旧 → 半同步复制 + 缓存 TTL
└── 弱一致 → 读多写少场景（指标/日志/非关键数据）
```

## 7. 核心要点

> 🎯 **核心要点**：
> 1. **两个基本事实**：无全局时钟 + 网络不可靠——一切难题的根源
> 2. **时钟分三种**：墙上时钟（会回拨）/单调时钟（测量）/逻辑时钟（定序）
> 3. **Lamport 定因果序**、向量时钟辨并发——按场景选用
> 4. **脑裂靠仲裁**：多数派 quorum + Fencing Token，奇数节点
> 5. **最终一致性** = 一致性 + 收敛预算——用「对账 + 读修复」保收敛
> 6. **CAP 是分区时二选一**，不是三选二；按数据重要性分级
> 7. **地基铺垫**：本章的时钟→[[02-分布式ID]]、仲裁→[[03-分布式锁]]、一致性→[[04-缓存]]、事务→[[05-事务]]
