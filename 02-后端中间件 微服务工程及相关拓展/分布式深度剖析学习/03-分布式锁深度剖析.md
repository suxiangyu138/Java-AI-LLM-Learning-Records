## 1. 分布式锁的需求与评价维度

> **背景**：多实例部署后，单机 `synchronized`/`ReentrantLock` 失效——需要跨进程互斥。
> **目的**：明确「好锁」的标准，才能评价各种方案。
> **适用范围**：秒杀、防重复提交、定时任务互斥、分布式事务前置等。

```text
分布式锁的核心需求
├── ① 互斥性（Safety）：任何时刻只有一个客户端持有
├── ② 安全性（Safety）：锁必须有超时（防死锁）
├── ③ 可用性（Liveness）：锁服务挂了业务不阻塞
├── ④ 容错性：Redis 集群故障时锁不失效
└── ⑤ 附加能力：可重入/阻塞等待/公平性（Redisson 全家桶）

Safety vs Liveness 的本质冲突（贯穿全文）
├── 固定过期时间：业务超时 → 锁提前释放 → 脏写（牺牲 Safety）
├── 看门狗续期：锁永续 → 服务停摆（牺牲 Liveness）
├── 金融/交易核心 → 保 Safety（数据不能错）
└── 秒杀/活动 → 保 Liveness（可用性优先）
```

## 2. 演进路线：SETNX → Lua → Redisson

> 🎯 **四代实现，每一代补一个致命漏洞**：

```java
// ① 初代：SETNX + 手动 DEL（2010 时代）
Boolean ok = jedis.setnx("lock:order", "1");
if (ok) {
    try { doBusiness(); } finally { jedis.del("lock:order"); }
}
// 漏洞 1：业务崩溃 → 锁永不释放（死锁）
// 漏洞 2：误删别人的锁（A 超时后 B 加锁，A 的 finally 删了 B 的锁）

// ② 二代：SETNX + EXPIRE（补超时）
jedis.setnx("lock:order", "1");
jedis.expire("lock:order", 30);   // 分开两步 → 非原子！
// 漏洞 3：setnx 成功但 expire 前崩溃 → 死锁（两步间无原子性）

// ③ 三代：SET 原子指令（补原子性，2026 仍是最小可行方案）
String token = UUID.randomUUID().toString();
String ok = jedis.set("lock:order", token, "NX", "EX", 30);
if ("OK".equals(ok)) {
    try { doBusiness(); }
    finally {
        // 校验 token 再删（防误删）——但「校验+删除」又非原子！
        if (token.equals(jedis.get("lock:order"))) jedis.del("lock:order");
    }
}
// 漏洞 4：判断 token 与 DEL 之间锁被换人 → 删错（需 Lua 原子）

// ④ 四代：Lua 脚本原子化（校验+删除一体，2019 标准答案）
String lua = "if redis.call('get', KEYS[1]) == ARGV[1] then "
           + "return redis.call('del', KEYS[1]) else return 0 end";
jedis.eval(lua, Arrays.asList("lock:order"), Arrays.asList(token));
```

**演进总结表**：

| 代际 | 技术 | 解决的坑 | 遗留问题 |
|:---:|------|---------|---------|
| ① | SETNX + DEL | 无 | 死锁/误删 |
| ② | SETNX + EXPIRE | 死锁 | 非原子两步 |
| ③ | SET NX EX + token | 误删 | 校验+删除非原子 |
| ④ | **Lua 脚本** | 校验删除原子 | 续期问题（业务超 30s） |
| ⑤ | **Redisson** | 看门狗续期 | 主从锁丢失/Redlock 争议 |

> 💡 **面试考点**：手写四代演进是分布式锁的必考题——能讲清每一代补了什么漏洞，说明真懂。

## 3. Redisson 核心机制：源码级

> 🎯 **Redisson（Redis 官方 Java 客户端）**——把上面所有坑封装好，开箱即用：

```java
// 使用（2026 标准姿势）
RLock lock = redissonClient.getLock("lock:order");
boolean locked = lock.tryLock(3, 30, TimeUnit.SECONDS);  // 等3s，租约30s
// 或最常用：不传 leaseTime → 走看门狗自动续期
boolean locked = lock.tryLock(3, TimeUnit.SECONDS);

if (locked) {
    try { doBusiness(); }
    finally { lock.unlock(); }
}
```

**底层数据结构（可重入的 Hash）**：

```text
Key = lock:order
Hash 结构
├── field = 客户端唯一标识（UUID + 线程ID）
└── value = 重入次数（加锁+1，释放-1，归零才真正删 key）

加锁 Lua（RedisTemplate 或 eval 提交）
if redis.call('exists', KEYS[1]) == 0
    or redis.call('hexists', KEYS[1], ARGV[1]) == 1 then
    redis.call('hincrby', KEYS[1], ARGV[1], 1)     -- 重入+1
    redis.call('pexpire', KEYS[1], ARGV[2])        -- 刷新过期
    return 1
else return 0

释放锁 Lua
if redis.call('hexists', KEYS[1], ARGV[1]) == 0 then return nil
local c = redis.call('hincrby', KEYS[1], ARGV[1], -1)  -- 重入-1
if c > 0 then
    redis.call('pexpire', KEYS[1], ARGV[2])            -- 还有重入，刷新
    return 0
else
    redis.call('del', KEYS[1])                          -- 归零才删
    return 1
end
```

**Redisson 锁类型全家桶**：

| 锁 | 机制 | 场景 |
|----|------|------|
| `RLock`（可重入） | Hash 计数 | 默认，90% 场景 |
| `tryLock(wait, lease)` | 阻塞等待 + 租约 | 有等待预算 |
| 公平锁 `FairLock` | List 队列 + ZSet 超时 | 防饥饿/惊群 |
| 读写锁 `RReadWriteLock` | 读读共享/写互斥 | 读多写少 |
| 联锁 `MultiLock` | 同时锁多个 key | 转账多账户 |
| 红锁 `RedissonRedLock` | 多节点过半数 | 强一致（谨慎） |

## 4. 看门狗：续期机制深度

> 🎯 **看门狗（Watchdog）解决「业务跑得比租约久」**——业务执行多久，锁就活多久：

```text
看门狗机制（2026 权威细节）
├── 默认租约时间：30 秒（lockWatchdogTimeout）
├── 续期节奏：每 10 秒续一次（租约的 1/3）
│   └── 续期动作：重置 key 的过期时间为 30s（pexpire）
├── 触发条件：tryLock 不传 leaseTime 时自动启用
├── 线程模型：Redisson 启动一条 Netty 定时任务线程
│   ├── 每 10s 检查持有中的锁 → 执行续期 Lua
│   └── 锁释放 → 取消续期任务
└── 崩溃安全：客户端宕机 → 定时任务停止 → 锁 30s 内自动过期

看门狗的取舍
├── ✅ 业务超时不用手动续期（消灭「业务跑完前锁过期」）
├── ✅ 崩溃自动释放（30s 上限，不永久死锁）
├── ❌ 业务无限循环 → 锁无限续期 → 其他实例永远拿不到
│   └── 对策：代码层设置业务超时兜底
└── 面试点：watchdog 是「Liveness 与 Safety 的平衡点」——默认 30s 可配
```

> ⚠️ **传 leaseTime 与不传的区别（高频面试坑）**：`tryLock(3, 30, SECONDS)` 传了租约 → **看门狗不启用**，30s 后锁强制过期（即使业务没跑完）；`tryLock(3, SECONDS)` 不传 → 看门狗启用，自动续期。**生产建议：核心业务用看门狗 + 业务超时兜底**。

## 5. Redlock 算法与世纪争议

> 🎯 **Redlock（Redis 作者 Antirez 2016 提出）**——多节点过半数加锁，应对单点/主从锁丢失；随之而来的「世纪论战」（Martin Kleppmann《How to do distributed locking》vs Antirez 反驳）：

```text
Redlock 算法流程（5 个独立 Master）
├── ① 依次向 5 个 Redis 实例加锁（带 client_id + 短过期时间）
├── ② 成功数 ≥ 3（过半）且总耗时 < 锁有效期 → 加锁成功
├── ③ 锁的有效期 = 初始有效期 - 获取耗时
├── ④ 失败 → 向所有实例释放（防残留）
└── 设计动机：任一 Redis 挂掉，过半数机制保证仍有锁可用

Kleppmann 的三点致命质疑
├── ① GC 停顿：持有者 GC 停 60s → 锁过期 → 别人加锁成功
│   └── 前者醒来，以为锁还在 → 两个客户端同时操作！
├── ② 时钟漂移：Redlock 用本地时间判断有效性
│   └── gettimeofday 非原子、可回拨 → 判断失真
├── ③ 没有 Fencing Token：无法让旧持有者的操作被拒绝
└── 结论：任何「基于过期时间」的锁都无法根治并发问题

Antirez 的反驳
├── ① 理论正确但工程可规避：合理配置 + 幂等业务兜底
├── ② 时钟漂移可监控（NTP 阈值告警）
└── ③ 真有「一锁定生死」的场景 → 用 CP 系统（ZK/etcd），别用 Redis

2026 定论（社区共识）
├── Redlock 比单节点安全，但非绝对安全（分布式锁没有银弹）
├── 金融强一致 → 直接 ZK/etcd（CP）或放弃锁走 DB 唯一键
└── 金句：Redlock 的争议本质 = 「过期时间锁」的天花板
```

## 6. 主从架构的锁丢失问题

> 🎯 **即使不用 Redlock，主从复制也有锁丢失**——这是 Redlock 诞生的真实背景：

```text
锁丢失场景（异步复制）
├── ① 客户端 A 向 Master 加锁成功（锁数据只在 Master）
├── ② Master 宕机（锁未复制到 Slave）
├── ③ 哨兵提升 Slave 为新 Master
├── ④ 新 Master 无锁数据 → 客户端 B 加锁成功！
└── 结果：A、B 同时持锁 → 互斥性被破坏

解决思路（按成本排序）
├── ① 接受风险：锁丢失概率低 + 业务幂等兜底（90% 场景够用）
├── ② 主从同步：Redis 7 的 WAIT 命令（同步复制保障）
│   └── 性能代价大，少用
├── ③ Redlock：多 Master 过半（前面已讲，不根治但改善）
└── ④ 换 CP 系统：ZK/etcd 选主本身就是共识 → 无此问题
```

> 💡 **工程启示**：分布式锁「一定会有失效窗口」——**设计业务时默认「锁会失效」**，用幂等（[[07-分布式幂等与调度]]）做最后防线。

## 7. CP 方案：ZooKeeper / etcd

> 🎯 **强一致场景的正确选择**——ZK/etcd 是 CP 系统（Raft/ZAB 共识），锁的正确性由「多数派写入」保证，无时钟问题、无主从丢失：

```text
ZooKeeper 锁实现（临时顺序节点）
├── ① 创建临时顺序节点 /locks/lock_0001
├── ② 检查自己是否是最小序号 → 是 → 获锁
├── ③ 不是 → 监听前一个节点（Watch 链式唤醒，防惊群）
├── ④ 释放：删除节点 / 客户端会话超时自动删除（临时节点）
└── 特点：会话机制（Session）替代过期时间——会话有效则锁有效

etcd 锁实现（lease + revision 版本号）
├── ① 创建 lease（租约）→ 以租约创建 key
├── ② key 的 revision 最小者获锁
├── ③ 续期：lease keepalive 心跳
└── 特点：Fencing Token 天然支持（revision 即单调递增令牌）

CP vs AP 锁对比
├── 优点：无时钟依赖、无锁丢失、天然 Fencing
├── 缺点：吞吐低（共识写）、故障时不可用（分区期间拒绝服务）
└── 适用：配置中心/选举/金融锁（强一致 > 吞吐）
```

| 维度 | Redis（AP） | ZK/etcd（CP） |
|------|:---:|:---:|
| 一致性 | 最终一致（锁可能丢） | 强一致（共识保证） |
| 吞吐 | 10w+/s | 千~万级 |
| 时钟依赖 | 有（过期时间） | 无（会话/租约） |
| 可用性 | 分区仍可用 | 分区拒绝写 |
| 适用 | 秒杀/缓存级 | 金融/选举/配置 |

## 8. DB 方案与终极兜底

> 🎯 **「不用锁」才是终极方案**——DB 唯一索引 + 乐观锁 + 幂等设计，从架构上消灭锁：

```sql
-- ① DB 唯一索引：天然互斥（防重复提交/幂等最稳）
CREATE TABLE t_order (order_no VARCHAR(64) UNIQUE, ...);
INSERT INTO t_order (order_no) VALUES (?) -- 重复插入报 DuplicateKey

-- ② 乐观锁：版本号 CAS（不加锁的并发控制）
UPDATE t_inventory SET stock = stock - 1, version = version + 1
WHERE id = ? AND stock > 0 AND version = ?;   -- 影响行数=0 则并发失败

-- ③ 悲观锁：SELECT ... FOR UPDATE（DB 行锁当分布式锁用）
SELECT * FROM t_account WHERE id = ? FOR UPDATE;
```

```text
方案对比（终极兜底三件套）
├── 唯一索引：防重复（下单/支付回调/消息消费）
├── 乐观锁：防超卖（库存扣减，影响行数判成功）
├── 状态机：防重入（订单状态流转校验，无效状态直接拒绝）
└── 金句：能不用分布式锁就不用——业务层约束 > 基础设施锁
```

## 9. 选型决策框架

```text
分布式锁选型（2026 决策流程）
│
├─ 业务真需要跨进程互斥吗？
│   ├─ 单实例 → synchronized/JVM 锁（别过度设计）
│   └─ 多实例 → 继续
│
├─ 数据重要性级别？
│   ├─ 强一致（金融/扣款/选举）
│   │   ├─ ZK/etcd（CP，首选）
│   │   └─ 或不用锁：DB 唯一键 + 幂等
│   └─ 最终一致（秒杀/任务/缓存）→ Redis
│       ├─ 单节点/主从 + 看门狗 → Redisson RLock（90-95% 场景）
│       ├─ 多实例强容错 → Redlock（谨慎，需理解局限）
│       └─ 主从可用性差 → 哨兵/集群架构保障
│
└─ 最后一道防线（永远要有）
    └─ 业务幂等：锁失效了，幂等兜住（见 [[07]]）

性能与成本基线（参考）
├── Redis 锁：微秒级（业务可接受的最快）
├── ZK/etcd：毫秒级（共识往返）
└── DB 唯一键：毫秒级 + 天然审计（对账友好）
```

## 10. 核心要点

> 🎯 **核心要点**：
> 1. **四代演进**：SETNX → EXPIRE → SET NX EX + token → Lua 原子——每代补一个漏洞
> 2. **Redisson 看门狗**：30s 租约 + 10s 续期，业务跑多久锁活多久；传 leaseTime 则看门狗不启用
> 3. **可重入 = Hash 计数**：hincrby +1/-1，归零才删
> 4. **Redlock 争议**：Kleppmann 三点质疑（GC/时钟/Fencing）——过期时间锁的天花板
> 5. **主从锁丢失**：异步复制 + 故障转移 = 互斥破坏；接受风险 + 幂等兜底
> 6. **CP 方案 ZK/etcd**：会话/租约替代过期时间，无时钟问题——强一致首选
> 7. **终极方案是「不用锁」**：唯一索引 + 乐观锁 + 状态机
> 8. **2026 共识**：90-95% 场景 Redisson 足够；「锁会失效，幂等永不失效」
