# 04 - 分布式缓存与一致性

> **核心摘要**：缓存是分布式系统的「双刃剑」——加一层缓存解千愁，也埋三类雷：**穿透**（查不存在的数据）、**击穿**（热点 key 过期）、**雪崩**（批量 key 同时过期）。再加双写一致性的老大难（Cache Aside/延迟双删/订阅 binlog）。2026 工程共识：**缓存是「读多写少」的加速器，不是数据正确性的兜底**——一致性交给数据库，缓存只负责快。

## 1. 缓存的价值与边界

> **背景**：数据库磁盘 IO 是瓶颈（千级 QPS），Redis 内存是高速路（10w+ QPS）。
> **目的**：明确缓存解决的问题和不该承担的责任。
> **适用范围**：读多写少、数据变更不频繁、允许轻微延迟的场景。

```text
缓存的收益
├── 吞吐：DB 千级 → 缓存 10w+ QPS（两个数量级）
├── 延迟：磁盘毫秒级 → 内存微秒级
├── 保护：缓存是 DB 的「盾牌」（防打满）
└── 成本：内存贵 → 只缓存热点数据（20% 数据承载 80% 流量）

缓存的边界（不该用它解决的）
├── 强一致数据（账户余额）→ 数据库为准，缓存只是加速
├── 高频写数据（库存扣减）→ 写直达 DB + 消息异步更新
├── 变化极快（实时行情）→ 缓存反而增加复杂度
└── 金句：缓存加速「读」，一致性责任永远在「写」侧
```

## 2. 三大故障：穿透 / 击穿 / 雪崩

> 🎯 **面试三兄弟**——穿透、击穿、雪崩，一字之差，机制和治理完全不同：

### 2.1 缓存穿透（Cache Penetration）

```text
定义：查询「缓存和 DB 都不存在」的数据
├── 请求 key = 99999999（无此订单）→ 缓存 miss → 打 DB → DB 也查无
├── 恶意攻击：构造大量不存在的 key → DB 被白打（防不胜防）
└── 与击穿的区别：击穿是「存在的热点」过期；穿透是「根本不存在的 key」

治理方案
├── ① 缓存空值：key 不存在 → 缓存 null + 短 TTL（3-5 分钟）
│   ├── 防攻击 ✅ 简单 ✅
│   └── 缺点：大量空 key 占用内存（null 值 key 数量控制）
├── ② 布隆过滤器（Bloom Filter）：请求前先过滤
│   ├── 原理：位数组 + 多次哈希——不存在必判不存在（误判存在无碍）
│   ├── 适用：id 集可控（订单号/用户号）
│   └── 缺点：数据删除要重建过滤器（bitmap 不能删单元素）
└── ③ 参数校验：非法参数直接拒绝（负数/超长/格式错）
```

### 2.2 缓存击穿（Hotspot Invalidation）

```text
定义：热点 key 过期瞬间，大量请求同时打到 DB
├── 场景：秒杀商品详情、微博热搜——单个 key 扛 90% 流量
├── 与雪崩的区别：雪崩是一批 key；击穿是「一个超热 key」
└── 危害：DB 连接打满 → 级联故障（DB 挂了全站挂）

治理方案
├── ① 互斥重建（业界主流）：重建加锁
│   ├── 流程：miss → 抢分布式锁 → 抢到者查 DB 写缓存
│   │   → 抢不到者短暂自旋重试（防所有请求打 DB）
│   └── 锁即 [[03-分布式锁深度剖析]] 的 Redisson
├── ② 逻辑过期：缓存永不过期，过期时间放 value 里
│   ├── 读到「逻辑过期」→ 后台异步重建（不阻塞请求）
│   └── 适用：允许短暂旧值
└── ③ 热点预热：活动前主动加载（秒杀开场前 10 分钟预写）
```

### 2.3 缓存雪崩（Cache Avalanche）

```text
定义：大批 key 同时过期 / Redis 整体宕机 → 请求全量打 DB
├── ① 批量过期：缓存 key 设了相同 TTL（如全部 30 分钟）
├── ② Redis 宕机：无降级策略 → 全站雪崩
└── 危害：DB 打满 → 核心服务不可用（最严重）

治理方案
├── ① TTL 随机化：基础 TTL + 随机抖动（±5 分钟）
├── ② 多级缓存：本地缓存（Caffeine）挡第一波（见第 7 节）
├── ③ 熔断降级：Redis 挂了 → 直接降级到「限流 + 读 DB 限额」
│   └── 相关：[[微服务架构]] 05-熔断限流
└── ④ 双 Redis 集群（成本高，备选）
```

**三兄弟对比表（面试速记）**：

| 维度 | 穿透 | 击穿 | 雪崩 |
|------|------|------|------|
| 对象 | 不存在的 key | 一个热点 key | 一批 key/整个集群 |
| 本质 | 缓存无意义 | 缓存瞬间失效 | 缓存批量失效 |
| 防护 | 空值/布隆过滤 | 互斥锁重建 | TTL 随机化 |
| 共性 | 都是「缓存失效 → DB 承压」→ 需要兜底限流 | | |

## 3. 缓存更新策略：Cache Aside 详解

> 🎯 **Cache Aside（旁路缓存）是读多写少的标准姿势**——先操作数据库，再操作缓存：

```text
Cache Aside 流程
├── 读：先查缓存 → miss → 查 DB → 写缓存
├── 写：更新 DB → 删除缓存（不是更新缓存！）
└── 金句：写操作用「删除」不用「更新」——延迟加载省计算

为什么写后删缓存而非写后更新缓存？
├── ① 更新缓存有并发窗口：
│   ├── 请求 A 更新缓存为 v2 → 请求 B 更新缓存为 v1（旧值覆盖）
│   └── 两个写并发 → 缓存可能停在新旧之间
├── ② 删除缓存天然简单：
│   ├── 下次读 miss → 从 DB 拉最新 → 保证最终一致
│   └── 删除是幂等的（不存在删了也无妨）
└── ③ 冷数据不写缓存（更新缓存 = 把不读的数据也写了）
```

**Cache Aside 的并发问题**（写后删仍有窗口）：

```text
经典竞态：读 miss + 并发写
├── ① 读 A：缓存 miss → 查 DB 得 v1
├── ② 写 B：更新 DB 为 v2 → 删除缓存
├── ③ 读 A：把 v1 写回缓存（覆盖！）
└── 结果：缓存 v1（旧）直到下次删除/TTL → 不一致窗口

对策（工程折中）
├── ① 延迟双删：删除 → sleep 100ms → 再删一次
│   ├── 补掉「读回写」的覆盖
│   └── 代价：多一次删除 + 延时（见下节）
├── ② 版本号：缓存带 version，写回前校验
├── ③ 过期兜底：TTL 强制收敛（最终一致）
└── 金句：缓存一致性「没有银弹」，只有窗口大小
```

## 4. 双写一致性：从延迟双删到 binlog 订阅

> 🎯 **双写一致性（缓存与 DB）的演进路线**——窗口从秒级收敛到毫秒级，复杂度递增：

```text
方案一：Cache Aside + TTL（最简单，窗口秒级~分钟级）
├── 窗口：删除失败/覆盖 → 等 TTL 收敛
└── 适用：容忍分钟级不一致（大部分业务够用）

方案二：延迟双删（窗口毫秒级，工程主流）
流程：
├── ① 更新 DB
├── ② 删除缓存
├── ③ sleep 100-500ms（等「读回写」的线程完成写回）
└── ④ 再次删除缓存（清掉读回写的旧值）
坑：
├── 延迟时间怎么定？→ 大于「读+写回」的平均耗时（压测估）
├── 删缓存失败？→ 重试队列（失败补偿）
└── sleep 是硬等待 → 高并发下用异步延迟队列（MQ 延迟消息）更好

方案三：订阅 binlog 异步删除（最强，窗口毫秒级+可靠）
流程：
├── ① 更新 DB（应用不管缓存！）
├── ② Canal 订阅 MySQL binlog
├── ③ 解析出变更事件 → 投递 MQ
└── ④ 消费端删除对应缓存 key
优点：
├── 应用与缓存解耦（写路径零额外代码）
├── 删除可靠（MQ 重试）
└── 缺点：引入 Canal + MQ 基础设施
```

**方案选型（2026 工程共识）**：

| 方案 | 不一致窗口 | 复杂度 | 适用 |
|------|:---:|:---:|------|
| TTL 兜底 | 秒~分钟 | ⭐ | 所有缓存必备（最后防线） |
| Cache Aside + 删除 | 秒级 | ⭐⭐ | 多数业务 |
| 延迟双删 | 毫秒~秒 | ⭐⭐⭐ | 一致性要求中高 |
| binlog 订阅（Canal） | 毫秒级 | ⭐⭐⭐⭐⭐ | 核心链路/无法容忍旧值 |
| 写直达 + 事务（强一致） | 无窗口 | 极高 | 几乎不用（缓存失去意义） |

> ⚠️ **现实结论**：100% 消除不一致窗口的成本是「缓存变数据库」——**绝大多数系统接受「短暂旧值 + TTL 收敛」**，把一致性预算花在数据库事务上。

## 5. 缓存集群与高可用

> 🎯 **Redis 集群三形态**（2026 现状）：主从+哨兵（小规模）、Cluster（大规模）、自研代理（超大）：

```text
① 主从 + 哨兵（Sentinel）
├── 读可走从库（读写分离）——注意：从库有复制延迟
├── 故障转移：哨兵选主（毫秒~秒级）
└── 适用：几十 G 数据、单机写够用

② Redis Cluster（官方集群）
├── 16384 个 slot 分片（CRC16(key) % 16384）
├── 数据分布：slot 划分到节点（0-5460/5461-10922/10923-16383）
├── 多主多从：主写从备，故障自动迁移
└── 适用：数据量/GDPS 超单机

③ 代理方案（Codis/自研）
├── 应用连代理，代理路由
└── 适用：跨机房/定制路由（已边缘化，Cluster 为主）

客户端路由细节（Cluster 直连）
├── 客户端算 slot → 直连对应节点
├── MOVED 重定向：slot 迁移后客户端重新路由
├── ASK 重定向：迁移中临时指向
└── 坑：multi-key 操作必须同 slot（用 hash tag {} 强制同槽）
```

**hash tag 与批量操作的坑**：

```redis
# 批量操作要求 key 在同一 slot
MSET {user:1}:name tom {user:1}:age 25   # {} 内 hash 同槽
# 反之：不同 slot 的 key 无法事务/批量（Cluster 下）
```

## 6. 热点 key 治理

> 🎯 **单个 key 撑起海量流量时**——加本地缓存、拆分 key、复制 key：

```text
热点 key 三类问题
├── ① 读写集中于单 key → 单节点 CPU/网卡打满
│   └── 案例：明星微博、秒杀商品、节假日订票
├── ② 热 key 过期 → 击穿（见 2.2）
└── ③ 热 key 被攻击（恶意刷）

治理方案
├── ① 本地缓存（Caffeine）：JVM 内再挡一层
│   ├── 热点 key 直接进程内命中（零网络）
│   └── 注意：本地缓存一致性（短 TTL，秒级过期）
├── ② key 复制（Read Replicas）：热点 key 复制 N 份
│   ├── 热点 key 变 hot1/hot2/hot3… 分摊到多节点
│   ├── 读取随机选一份；写入全删（一致性代价）
│   └── 适用：极高热点（10w+ 读/s）
├── ③ 多级缓存兜底（见下节）
└── ④ 监控 + 自动发现（热点 key 识别，自动预热）
```

## 7. 多级缓存架构

> 🎯 **生产架构的最终形态：三级缓存**——本地（最快）→ Redis（次快）→ DB（保底）：

```text
三级缓存架构（2026 主流电商/高并发标准）
┌─ 第一级：JVM 本地缓存（Caffeine）
│   ├── 命中：纳秒级（无网络）
│   ├── 适用：热点 key / 配置 / 基础数据
│   └── 代价：多实例各自一份（一致性弱，TTL 极短 3-60s）
├─ 第二级：Redis（分布式共享）
│   ├── 命中：微秒级（一次网络）
│   ├── 适用：全量热点 + 跨实例共享数据
│   └── 代价：网络 + 一致性由删除策略保证
└─ 第三级：DB（最终权威）
    └── miss 兜底 + 限流保护

一致性模型（逐级放宽）
├── DB → Redis：延迟双删/binlog 订阅（毫秒~秒级）
├── Redis → 本地：短 TTL 主动过期（秒级）
└── 金句：每往上一级，「更快」换「更旧」——各安其位

架构要点
├── 本地缓存必须设上限（Caffeine maximumSize + expireAfterWrite）
├── 缓存预热：启动/活动前批量加载热点
├── 缓存监控：命中率看板（<70% 检查策略）
└── 降级预案：Redis 挂 → 本地缓存 + DB 限流直读
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. **缓存定位**：读多写少的加速器——一致性责任永远在写侧
> 2. **三兄弟**：穿透（不存在的 key→空值/布隆）、击穿（热 key 过期→互斥重建）、雪崩（批量失效→TTL 随机化+多级）
> 3. **Cache Aside**：写后删缓存（非更新）——删除幂等、冷数据不写
> 4. **延迟双删**：删→sleep→再删，收敛「读回写」窗口；binlog 订阅是终极解
> 5. **一致性没有银弹**：接受「短暂旧值 + TTL 收敛」，预算花在 DB 事务
> 6. **Cluster 分片**：16384 slot + CRC16；multi-key 用 hash tag 同槽
> 7. **热点治理**：本地缓存 + key 复制 + 自动预热
> 8. **三级缓存**：本地（最快）→ Redis（共享）→ DB（权威）——每级快换旧
