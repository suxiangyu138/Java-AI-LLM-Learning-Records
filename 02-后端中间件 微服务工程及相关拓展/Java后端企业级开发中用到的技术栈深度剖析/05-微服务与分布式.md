## 1. 微服务架构核心

```
微服务 vs 单体：
  单体：一个应用（部署简单、扩展受限）
  微服务：按业务拆分（独立部署、复杂度高）

微服务核心问题：
  服务发现、配置管理、网关路由、
  分布式事务、链路追踪、限流熔断

⚠️ 面试必答：
"微服务是'业务边界的分布式化'——
 独立部署 + 独立扩展；
 收益是弹性，代价是分布式复杂度。"
```

## 2. 注册与配置中心

### 2.1 注册中心（Nacos）

```
注册中心职责：
  服务注册（启动上报）
  服务发现（调用方获取实例列表）
  健康检查（剔除故障实例）

Nacos 特性：
  注册 + 配置一体
  支持临时/持久实例
  健康检查 + 负载均衡配合

⚠️ 面试必答：
"注册中心 = 服务的'通讯录'——
 注册/发现/健康检查；
 Nacos 国产主流（注册配置一体）。"
```

### 2.2 配置中心

```
配置中心价值：
  动态刷新（免重启）
  环境隔离（dev/prod）
  配置审计

Nacos 配置：
  Data ID（配置文件）+ 分组 + 命名空间
  @RefreshScope 动态刷新

⚠️ 面试必答：
"配置中心 = 配置外置 + 动态刷新——
 Nacos/Spring Cloud Config/Apollo 三选；
 敏感配置加密存储。"
```

## 3. API 网关

### 3.1 网关职责

```
网关六大职责：
  ① 路由转发（入口统一）
  ② 鉴权认证（统一入口校验）
  ③ 限流熔断（保护后端）
  ④ 日志审计（统一记录）
  ⑤ 跨域处理
  ⑥ 协议转换

⚠️ 面试必答：
"网关 = 微服务唯一入口——
 鉴权/路由/限流/审计集中处理；
 核心价值：统一管控 + 减轻服务端重复。"
```

### 3.2 Spring Cloud Gateway

```
Gateway 特性：
  WebFlux（非阻塞，性能高）
  路由（Route）+ 断言（Predicate）+ 过滤器（Filter）
  全局过滤器（鉴权/限流）

⚠️ 面试必答：
"Gateway = WebFlux 非阻塞 + 路由断言过滤器；
 对比 Zuul（阻塞、已过时）。
 鉴权全局过滤器是网关标配。"
```

## 4. 分布式锁

### 4.1 为什么需要

```
单机锁（synchronized/Lock）只能锁本进程
多实例（微服务）需要跨进程锁

场景：库存扣减、订单防重、定时任务防重复

⚠️ 面试必答：
"分布式锁 = 跨进程互斥——
 多实例下的'临界区保护'；
 场景：库存/防重/定时任务。"
```

### 4.2 Redis 分布式锁

```java
// Redis 锁标准实现（setnx + 过期 + Lua 释放）
public boolean tryLock(String key, String value, long expireSeconds) {
    // ⚠️ setIfAbsent + 过期：原子（防死锁）
    return redis.opsForValue()
        .setIfAbsent(key, value, expireSeconds, TimeUnit.SECONDS);
}

public void unlock(String key, String value) {
    // ⚠️ Lua 脚本：先校验持有者再删除（防误删他人锁）
    String script = "if redis.call('get', KEYS[1]) == ARGV[1] " +
                    "then return redis.call('del', KEYS[1]) " +
                    "else return 0 end";
    redis.execute(new DefaultRedisScript<>(script, Long.class),
                  List.of(key), value);
}
```

```
⚠️ 分布式锁演进：
  setnx + 过期（基础）→ 看门狗续期（Redisson）
  → RedLock（多节点，强一致）

⚠️ 面试必答：
"Redis 锁三要点——原子加锁（setnx+过期）、
 原子释放（Lua 校验持有者）、
 续期（Redisson 看门狗）；
 高一致场景用 ZooKeeper 锁。"
```

## 5. 分布式事务

### 5.1 为什么难

```
本地事务：单库 ACID（简单）
分布式事务：跨库/跨服务 → 无法单库事务

场景：下单扣库存（订单库 + 库存库）、
     支付（账户 + 订单）

⚠️ 面试必答：
"分布式事务难在'跨资源原子性'——
 单库事务失效、网络不可靠、
 需要协调者保证一致性。"
```

### 5.2 方案对比

| 方案 | 原理 | 一致性 | 适用 |
|------|------|:---:|------|
| 2PC/XA | 准备 + 提交 | 强 | 极少（性能差） |
| TCC | 预留/确认/取消 | 强 | 资金类 |
| 可靠消息 | 消息最终一致 | 最终 | 异步场景 |
| 本地消息表 | 表 + 定时任务 | 最终 | 简单可靠 |
| Seata AT | 自动补偿 | 最终 | 主流（透明） |

```
⚠️ 面试必答：
"事务方案五选——强一致 TCC/2PC、
 最终一致 消息/本地表/Seata；
 大多数业务最终一致足够
 （Seata AT 模式透明接入）。"
```

## 6. 分布式 ID

### 6.1 方案对比

| 方案 | 特点 | 场景 |
|------|------|------|
| 数据库自增 | 简单、单点 | 小系统 |
| Redis INCR | 快、依赖 Redis | 中 |
| **雪花算法** | 趋势递增、无依赖 | ✅ 主流 |
| UUID | 无序、长 | 非排序场景 |

```
雪花算法组成（64 位）：
  1 符号位 + 41 时间戳 + 10 机器 ID + 12 序列号
  特点：趋势递增、无中心、可排序

⚠️ 面试必答：
"雪花 = 时间戳 + 机器 + 序列——
 趋势递增、无中心依赖；
 是分布式 ID 主流方案
 （MyBatis-Plus 内置/自实现）。"
```

> 🎯 **核心要点**：分布式体系 = **微服务**（业务边界 + 独立部署）+ **注册配置**（Nacos 一体）+ **网关**（统一入口六大职责）+ **分布式锁**（Redis 三要点 + Redisson）+ **分布式事务**（强一致 TCC vs 最终一致 Seata/消息）+ **分布式 ID**（雪花算法）。"注册/配置/网关是骨架、锁/事务/ID 是难题"。
