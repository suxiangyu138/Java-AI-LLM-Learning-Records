## 1. 为什么需要会话管理

```
HTTP 无状态：每次请求独立，服务器"不记得"你

会话管理解决：
  登录后记住你是谁
  购物车/偏好/权限保持

三种主流方案：
  Cookie + Session（服务端状态）
  JWT（无状态令牌）
  Token + Redis（服务端存储的令牌）

⚠️ 面试必答：
"HTTP 无状态是协议设计——
 会话管理补上'记住用户'的能力；
 方案选择是认证设计的核心决策。"
```

## 2. Session 机制

### 2.1 工作流程

```
Session 流程：
  ① 首次请求 → 服务器创建 Session → 生成 ID
  ② 响应 Set-Cookie: JSESSIONID=abc
  ③ 后续请求带 Cookie → 服务器匹配 Session

存储位置：服务端内存（默认）或 Redis/DB

⚠️ 面试必答：
"Session = 服务端存储 + Cookie 传 ID——
 数据在服务器（可存用户信息）、
 客户端只有会话 ID。"
```

### 2.2 Session 生命周期

```
创建：首次 getSession()
失效三时机：
  ① 超时（默认 30 分钟）
  ② invalidate()（登出必调）
  ③ 应用重启（内存丢失）

⚠️ 面试必答：
"Session 失效三时机——超时、invalidate、
 重启丢失；登出必须 invalidate
 （防会话固定攻击）。"
```

## 3. JWT 方案

### 3.1 JWT 结构

```
JWT = Header.Payload.Signature（三段）

  Header：{"alg":"RS256","typ":"JWT"}
  Payload：{"sub":"1001","roles":["ADMIN"],"exp":...}
  Signature：签名（防篡改）

特点：
  自包含（服务端无需存储）
  可验证（签名保证未被篡改）
  无状态（水平扩展友好）

⚠️ 面试必答：
"JWT 三段——头（算法）、负载（声明）、
 签名（防篡改）；自包含无状态，
 服务器不用存会话。"
```

### 3.2 JWT 使用规范

```java
// ① 登录签发
String token = Jwts.builder()
    .subject(userId)
    .claim("roles", roles)
    .expiration(new Date(System.currentTimeMillis() + 30 * 60 * 1000))  // ⚠️ 短时效
    .signWith(privateKey)                    // RS256 非对称
    .compact();

// ② 请求校验（过滤器）
// Authorization: Bearer <token>
String token = request.getHeader("Authorization").substring(7);
Claims claims = Jwts.parserBuilder()
    .setSigningKey(publicKey)
    .build()
    .parseClaimsJws(token)
    .getBody();
```

```
⚠️ JWT 安全五要点：
  RS256 签名（非对称，密钥安全）
  短过期（15-30 分钟 + refresh token）
  HTTPS 传输
  敏感信息不进 Payload（base64 可解码！）
  服务端仍做授权校验（JWT 只认证）

⚠️ 面试必答：
"JWT 安全——RS256、短时效、HTTPS、
 不放敏感信息、服务端授权；
 'JWT 解决认证，授权仍需 RBAC'是经典表述。"
```

## 4. Session vs JWT 对比

| 维度 | Session | JWT |
|------|:---:|:---:|
| 状态存储 | 服务端 | 客户端 |
| 水平扩展 | 需共享存储 | ✅ 天然支持 |
| 主动失效 | ✅ 立即 | ❌ 等过期 |
| 安全 | 需防固定 | 需防泄露 |
| 适用 | 传统 Web、强管控 | 微服务、移动端 |

```
选型决策：
  需要立即踢人（封号/改密） → Session/Redis Token
  微服务无状态 + 移动端 → JWT
  安全性要求高 → Redis Token（可注销）

⚠️ 面试必答：
"'能不能立即失效'是核心分界——
 能（服务端存）选 Session/Redis Token、
 不能（客户端存）选 JWT；
 金融等高安全场景 Redis Token 更可控。"
```

## 5. 分布式会话

### 5.1 多节点问题

```
集群部署问题：
  登录到 Node A → Session 在 A
  下次请求到 Node B → 找不到 → 未登录！

三种方案：
  ① Session 黏性（LB 固定节点）
  ② Session 复制（节点同步）
  ③ 集中存储（Redis）✅ 现代标准

⚠️ 面试必答：
"分布式会话三方案——黏性（单点风险）、
 复制（同步开销）、Redis 集中存储（标准）。
 Spring Session + Redis 是现代答案。"
```

### 5.2 Spring Session Redis

```java
// 引入依赖：spring-session-data-redis
// 配置后 Session 自动存 Redis（代码零改动）

@Configuration
public class SessionConfig {
    @Bean
    public CookieSerializer cookieSerializer() {
        DefaultCookieSerializer serializer = new DefaultCookieSerializer();
        serializer.setCookieName("SESSION");        // 自定义 Cookie 名
        serializer.setUseHttpOnlyCookie(true);      // 防 XSS
        serializer.setUseSecureCookie(true);        // 仅 HTTPS
        serializer.setSameSite("Lax");              // 防 CSRF
        return serializer;
    }
}
```

> 🎯 **要点**：Spring Session + Redis = 透明分布式会话——代码不变、Session 存 Redis、任意节点可服务。**Cookie 安全属性**（HttpOnly/Secure/SameSite）一并配置。

## 6. 会话安全

### 6.1 会话攻击与防御

| 攻击 | 原理 | 防御 |
|------|------|------|
| 会话固定 | 预置 ID 骗登录 | 登录后 invalidate + 重建 |
| 会话劫持 | 窃取 Cookie | HttpOnly + Secure + 短时效 |
| XSS 窃取 | JS 读 Cookie | HttpOnly（JS 不可读） |
| CSRF | 伪造请求带 Cookie | SameSite + Token 校验 |

### 6.2 会话安全清单

```
✅ HttpOnly（防 XSS 窃取）
✅ Secure（仅 HTTPS）
✅ SameSite（防 CSRF）
✅ 登录后 invalidate（防固定）
✅ 超时自动失效
✅ 敏感操作二次验证（改密/支付）
✅ 分布式会话 Redis（可统一失效）

⚠️ 面试必答：
"会话安全四件套——HttpOnly + Secure +
 SameSite + 登录重建；
 敏感操作二次验证是最后防线。"
```

---

> 🎯 **核心要点**：会话体系 = **Session**（服务端存储 + Cookie 传 ID + 三失效时机）+ **JWT**（三段自包含 + RS256/短时效）+ **对比选型**（能否立即失效是分界）+ **分布式**（Spring Session Redis 透明化）+ **安全**（HttpOnly/Secure/SameSite 四件套）。"无状态 HTTP → 会话方案"是 Web 认证的第一课。
