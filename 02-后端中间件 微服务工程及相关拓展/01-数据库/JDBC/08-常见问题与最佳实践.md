## 1. 连接泄漏：最高频事故

**连接泄漏 = 借了没还**（close 未执行）：

```java
// ❌ 泄漏写法（异常路径不关闭）
Connection conn = null;
try {
    conn = ds.getConnection();
    // ... 业务（抛异常 → 直接跳 catch → 没有 finally close）
} catch (SQLException e) {
    throw e;          // 连接没还！
} // conn 没有 close —— 池中连接被"借走"不回

// ✅ 正确：TWR（自动关闭 = 自动归还）
try (Connection conn = ds.getConnection()) {
    // ... 业务
} catch (SQLException e) {
    throw e;
}
```

**泄漏的症状与排查**：

```text
症状：连接池活跃数持续上升 → 获取连接超时 → 服务不可用
排查：
  ① HikariCP leak-detection-threshold（借用超时打堆栈）
  ② 活跃连接监控趋势（只增不减 = 泄漏）
  ③ 代码审查：所有 getConnection 是否 TWR
  ④ 常见漏点：异常路径、嵌套资源、静态/字段持有连接

预防：
  ① 一律 TWR（Connection/Statement/ResultSet）
  ② 连接不得存字段/静态（生命周期 = 方法内）
  ③ 监控活跃连接数（告警阈值）
```

> 🎯 **核心要点**：泄漏 = "**借了没还（close 未执行）**"——**"TWR 是一劳永逸的根治"**（与 `Java异常体系/04` 联动）；leakDetectionThreshold + 活跃连接监控是排查双保险。

## 2. 时区问题：serverTimezone

**时区问题的表现与根因**：

```text
症状：
  ① 连接报错：The server time zone value 'CST' is unrecognized
  ② 时间错乱：存进去 8 点，读出来 0 点（差 8 小时）

根因：
  ① MySQL 与 JVM 时区不一致（默认差异）
  ② 驱动需要明确时区（新驱动强制要求）

解法：URL 必配 serverTimezone（见 01 模块）
  jdbc:mysql://...?serverTimezone=Asia/Shanghai
  # 或 GMT%2B8（+ 号需编码）
```

**时区最佳实践**（2026 规范）：

```text
① URL 必配：serverTimezone=Asia/Shanghai（或容器时区）
② 存储规范：数据库存 UTC/时间戳，展示时转本地（见 06 模块时间）
③ 连接池时区一致性：所有连接同参数（防"这条对那条错"）
④ Docker 部署：容器 TZ 环境变量（与 serverTimezone 一致）
   - 例：-e TZ=Asia/Shanghai

排查"时间差 8 小时"三步：
  ① 数据库时区：SELECT @@global.time_zone, @@session.time_zone
  ② JVM 时区：TimeZone.getDefault()
  ③ URL 参数：serverTimezone 是否设置
```

> 🎯 **核心要点**：时区 = "**URL 必配 serverTimezone（新驱动强制）**"——**"时间差 8 小时 = 时区不一致"是最高频时间事故**；存储 UTC + 展示本地是治本规范（与 `Java常用的库函数剖析/06` 联动）。

## 3. 编码问题：characterEncoding

**中文乱码的表现与根因**：

```text
症状：插入中文变 ?? / 读出乱码
根因：
  ① 客户端连接编码 ≠ 数据库编码
  ② URL 未指定 characterEncoding（用默认）

解法：URL 必配（见 01 模块）
  jdbc:mysql://...?characterEncoding=utf8&useUnicode=true
  # 注意：utf8（MySQL 的 utf8mb3）vs utf8mb4（完整 Unicode，含 emoji）

2026 规范：utf8mb4 是 MySQL 8 默认（emoji/生僻字需要）
```

**编码排查链**：

```text
三层编码必须一致：
  ① 数据库：CHARACTER SET utf8mb4
  ② 连接：characterEncoding=utf8mb4（URL）
  ③ 应用：源码/文件 UTF-8
→ 任何一层不一致 → 乱码

验证：SHOW VARIABLES LIKE 'character_set%'；
```

> 🎯 **核心要点**：编码 = "**URL 必配 characterEncoding（utf8mb4）**"——**"utf8mb4（含 emoji）而非 utf8"是 2026 规范**；三层一致性（库/连接/应用）是排查框架。

## 4. 性能问题：预编译/批处理/查询

**JDBC 层性能优化清单**（与各模块联动）：

| 优化 | 手段 | 模块 |
|------|------|------|
| 预编译 | PreparedStatement（复用执行计划） | 02 |
| 批量 | executeBatch + rewriteBatchedStatements | 06 |
| 连接池 | HikariCP 参数（池大小） | 05 |
| 流式 | setFetchSize（大结果集） | 03 |
| 查询 | SQL 优化（索引/减少列） | MySQL/ 系统 |
| 缓存 | 框架层缓存（MyBatis 二级缓存） | MyBatis/04 |

```java
// 预编译的性能细节：
// MySQL useServerPrepStmts=true → 服务端预编译（执行计划缓存）
String url = "...?useServerPrepStmts=true&cachePrepStmts=true";
// 收益：同结构 SQL 复用执行计划（高频查询场景）
// 注意：MySQL 8 驱动默认行为有变化（按场景验证）
```

**查询性能的三个检查**：

```text
① 列裁剪：SELECT 需要的列（别 SELECT *）
② 索引：WHERE/ORDER BY 字段有索引（EXPLAIN）
③ 结果量：大结果集流式（setFetchSize）或分页
→ JDBC 层只管"怎么取"，SQL 质量看 MySQL/ 系统
```

> 🎯 **核心要点**：性能 = "**预编译 + 批处理 + 池化 + 流式**"四板斧——**"列裁剪/索引/流式"是查询性能三查**；JDBC 层优化的终点是"让 SQL 本身更好"（`SQL调优/` 联动）。

## 5. SQLException 的处理

**SQLException 的层次与处理规范**：

```java
// SQLException 支持链式（cause 链）与状态码
catch (SQLException e) {
    int code = e.getErrorCode();       // 数据库错误码（如 1062 重复键）
    String state = e.getSQLState();    // SQL 状态（SQLState 5 位码）
    Throwable next = e.getNextException();  // 链式下一个异常

    // 常见处理：
    if (code == 1062) {                // MySQL 重复键
        throw new DuplicateException("数据已存在");
    }
    // 统一：包装为业务异常（保留 cause）
    throw new DataAccessException("数据库操作失败", e);
}
```

**SQLException 处理规范**：

```text
① 不要吞：catch 后必须处理或包装上抛
② 包装保留 cause：new DataAccessException(msg, e)（异常链）
③ 框架统一：MyBatis 转 PersistenceException / Spring 转 DataAccessException
   → 业务层面向框架异常（非 JDBC 细节）
④ 状态码速查（MySQL 常见）：
   1062 重复键 / 1451 外键约束 / 1045 权限 / 1049 库不存在
```

> 🎯 **核心要点**：SQLException = "**错误码（getErrorCode）+ 包装保留 cause**"——**"1062 重复键"等常见码速查是排障加速器**；框架层已包装（MyBatis/Spring），业务层不直接碰 SQLException（与 `Java异常体系/05` 联动）。

## 6. 最佳实践清单

**JDBC 生产最佳实践全集**（2026）：

```text
连接管理：
  □ 生产一律 DataSource（连接池，不用 DriverManager）
  □ 资源一律 TWR（Connection/Statement/ResultSet）
  □ 连接不存字段/静态（生命周期 = 方法内）

SQL 执行：
  □ 一律 PreparedStatement（99%）
  □ MySQL URL：serverTimezone + characterEncoding=utf8mb4
  □ 批处理：rewriteBatchedStatements=true + 分批

事务：
  □ setAutoCommit(false) + commit/rollback + finally 复位
  □ 事务边界最小化（长事务 = 锁持有久）

性能：
  □ 列裁剪（不 SELECT *）
  □ 大结果集流式（setFetchSize）
  □ 批量导入分批提交（防大事务）

异常：
  □ 不吞 SQLException（包装保留 cause）
  □ 常见错误码速查（1062/1451）
```

**一句话总结**：

```text
JDBC 最佳实践 = 
  TWR 管连接、PreparedStatement 管 SQL、
  serverTimezone/utf8mb4 管正确性、
  批处理管性能、包装异常管可排查
```

> 🎯 **核心要点**：最佳实践 = "**五管（连接/SQL/正确性/性能/异常）**"——**每条都是"一次配置、长期收益"**（URL 参数配一次、TWR 写一次）；与各模块的规范一致（本体系是 JDBC 全景的收口）。
