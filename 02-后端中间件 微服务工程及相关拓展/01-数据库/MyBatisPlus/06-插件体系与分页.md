## 1. MybatisPlusInterceptor 机制

**MybatisPlusInterceptor**：MP 的插件总管——基于 MyBatis 拦截器（Interceptor）机制，在 SQL 执行前**解析并改写 SQL**：

```text
机制原理：
Mapper 方法调用 → MyBatis 执行 SQL 前 → MybatisPlusInterceptor 拦截
  → 内部按注册顺序执行各 InnerInterceptor（分页/乐观锁/防全表/多租户）
  → 每个插件用 jsqlparser 解析 SQL AST → 改写（加 LIMIT/WHERE/版本校验）
  → 执行改写后的 SQL
```

**注册方式**（配置类，顺序有讲究）：

```java
@Configuration
public class MybatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));  // ① 分页
        interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());        // ② 乐观锁
        interceptor.addInnerInterceptor(new BlockAttackInnerInterceptor());             // ③ 防全表
        interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(handler));       // ④ 多租户
        return interceptor;
    }
}
```

> 🎯 **核心要点**：**所有"自动改写 SQL"的能力都在这一个 Bean 里**——没注册 = 能力不生效（且**不报错**！）。排查"分页不生效/乐观锁不生效"第一步：检查拦截器是否注册、顺序是否合理。

## 2. 分页插件：配置与 3.5.9+ 依赖变化

**分页是 MP 使用率最高的插件**——`selectPage` 自动拼 LIMIT：

```java
// ① 依赖（3.5.9+ 必须！否则分页静默失效——不报错但没有 LIMIT）
// mybatis-plus-jsqlparser（JDK8 用 -4.9 版）

// ② 注册（显式指定 DbType）
PaginationInnerInterceptor pagination = new PaginationInnerInterceptor(DbType.MYSQL);
pagination.setMaxLimit(500L);          // 单页上限：防恶意全量查询
interceptor.addInnerInterceptor(pagination);

// ③ 使用
Page<User> page = new Page<>(1, 10);                    // 页码从 1 开始！
Page<User> result = userMapper.selectPage(page,
        new LambdaQueryWrapper<User>().eq(User::getStatus, 1));
// result.getRecords() 列表 / getTotal() 总数 / getCurrent() getSize()
```

**分页执行的 SQL 语义**：

```text
selectPage(page, wrapper) → 两条 SQL：
① SELECT COUNT(*) FROM user WHERE status = 1            ← 总数（大表性能点！）
② SELECT ... FROM user WHERE status = 1 LIMIT 0, 10     ← 当前页
```

**分页高频坑**（生产）：

| 坑 | 表现 | 解法 |
|----|------|------|
| 页码传 0 | **查不到数据**（总数为 0 的常见原因！） | 前端传 1 起；后端 `Math.max(current, 1)` |
| 3.5.9+ 没引 jsqlparser | 分页静默失效（无 LIMIT） | 引入依赖 |
| 没注册拦截器 | 同上 | 检查配置类 |
| 大表 COUNT 慢 | selectPage 的 COUNT 全表扫 | 索引 + 优化 COUNT（见下节） |
| 深分页 OFFSET 大 | 第 10000 页 = 扫描 10 万行再丢弃 | Keyset 分页（下节） |

> 🎯 **核心要点**：分页 = **依赖（3.5.9+ 的 jsqlparser）+ 注册（DbType 显式）+ 使用（页码 1 起）**——三段式记住，分页不再"静默失效"。

## 3. 分页优化：索引 / Keyset / 游标

**三层优化**（数据量大时按需升级）：

### 第一层：索引（必做）

```sql
-- 分页查询的 WHERE 与 ORDER BY 字段建复合索引
-- 例：WHERE status = 1 ORDER BY create_time DESC
ALTER TABLE user ADD INDEX idx_status_ctime (status, create_time);
-- 收益：避免文件排序 + 全表扫描；COUNT 也走索引
```

### 第二层：Keyset 分页（深分页，替代 OFFSET）

```java
// 原理：不用 OFFSET 跳过，而是"记住上一页最后一条的位置"继续
// 第一页
List<User> page1 = userMapper.selectList(new LambdaQueryWrapper<User>()
        .orderByDesc(User::getId)
        .last("limit 100"));                    // 白名单常量，安全
// 下一页：id < 上一页最后一条的 id（游标）
List<User> page2 = userMapper.selectList(new LambdaQueryWrapper<User>()
        .lt(User::getId, page1.get(page1.size() - 1).getId())
        .orderByDesc(User::getId)
        .last("limit 100"));
// 性能：每次都从索引定位，O(log n) —— OFFSET 100000 则是扫描 10 万行
```

### 第三层：游标查询（超大数据量流式）

```java
// selectCursor：流式读取，不一次性加载全部（适合批量导出）
try (Cursor<User> cursor = userMapper.selectCursor(
        new LambdaQueryWrapper<User>().eq(User::getStatus, 1))) {
    cursor.forEach(u -> exportOne(u));          // 逐条处理，内存恒定
}
// 注意：游标查询期间连接被占用 —— 处理完再关闭（try-with-resources）
```

> 🎯 **核心要点**：分页优化三阶梯 = **索引（必做）→ Keyset（深分页）→ 游标（海量流式）**——OFFSET 深分页是千万级系统的性能杀手，Keyset 是标准解法（10 万+ 条时启动第二层）。

## 4. 乐观锁插件

**OptimisticLockerInnerInterceptor**：让 `@Version` 字段生效（见 02 模块第 5 节）：

```java
// 注册
interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());

// 生效条件（缺一不可！）：
// ① 实体字段有 @Version
// ② 拦截器已注册
// ③ 更新走 updateById / update(entity, wrapper)（拦截器改写 WHERE version=?）

// 更新时的 SQL 改写：
// UPDATE product SET stock=?, version=version+1 WHERE id=? AND version=0
// 影响行数 0 = 版本冲突（不抛异常！必须检查返回值）
```

**三个容易"不生效"的场景**：

| 场景 | 原因 |
|------|------|
| 忘了注册拦截器 | 更新变普通 UPDATE（无 version 条件）——**静默失效** |
| update 用 UpdateWrapper.set(version,...) | 手动 set version 会绕过拦截器逻辑 |
| 修改了 version 字段本身 | 拦截器认为"你主动管版本"，不再自动 +1 |

> 🎯 **核心要点**：乐观锁 = **@Version 注解 + 插件注册 + 检查返回值**三件套——注册缺失是静默失效的头号原因；冲突处理（0 行）见 02 模块第 5 节。

## 5. 防全表更新插件

**BlockAttackInnerInterceptor**：拦截**无 WHERE 条件的 UPDATE/DELETE**——生产安全红线：

```java
// 注册
interceptor.addInnerInterceptor(new BlockAttackInnerInterceptor());

// 效果：
userMapper.update(entity, new QueryWrapper<>());   // ❌ 空条件 → 抛 MybatisPlusException
userMapper.delete(null);                            // ❌ 全表删除 → 拦截
// SQL 里没有 WHERE 子句的 update/delete 直接拒绝执行！
```

**为什么必须有**（生产事故统计的高频原因）：

```text
开发手误：update(entity, wrapper) 忘传 wrapper → 全表数据被改
线上操作：删表字段（不是删除条件）→ 全表删除
→ 一个字符的疏忽 = 生产数据事故
→ 拦截器兜底：无 WHERE 一律拒绝
```

**注意边界**：拦截的是"无 WHERE"——**有 WHERE 但不精准**（如 `WHERE 1=1`）拦不住；配合"UPDATE 永远先写定位条件"的代码规范双保险。

> 🎯 **核心要点**：**防全表插件 = 生产必装**——它把"手误删全表"从"事故"变成"异常"（抛错而不是执行）。注册成本一行，收益是数据安全底线。

## 6. 多租户插件

**TenantLineInnerInterceptor**：SaaS 多租户自动拼 `tenant_id` 条件——**SQL 层面强制隔离**：

```java
// ① 实现 TenantLineHandler
@Component
public class TenantHandler implements TenantLineHandler {

    @Override
    public Expression getTenantId() {
        // 从上下文取当前租户（登录用户/请求头/Token）
        return new LongValue(TenantContext.getTenantId());
    }

    @Override
    public String getTenantIdColumn() {
        return "tenant_id";          // 租户列名
    }

    @Override
    public boolean ignoreTable(String tableName) {
        return !isTenantTable(tableName);   // 非租户表忽略（字典表等）
    }
}

// ② 注册
interceptor.addInnerInterceptor(new TenantLineInnerInterceptor(tenantHandler));

// ③ 效果：所有 SQL 自动改写
// SELECT * FROM user WHERE status = 1
// → SELECT * FROM user WHERE status = 1 AND tenant_id = 1001
// UPDATE user SET name = ? WHERE id = 1
// → UPDATE user SET name = ? WHERE id = 1 AND tenant_id = 1001
```

**多租户的三个要点**：

| 要点 | 说明 |
|------|------|
| 表级豁免 | `ignoreTable` 返回 true 的表不加条件（字典/全局配置表） |
| **手写 SQL 不生效** | XML 自定义 SQL 需手动加 `tenant_id`（同逻辑删除的边界） |
| 租户上下文 | `TenantContext` 需在请求入口设置（过滤器/拦截器），线程池传参注意（ThreadLocal 传播） |

> 🎯 **核心要点**：多租户插件 = **"数据隔离的 SQL 层强制"**——业务代码完全无感（不用手动 where tenant_id），杜绝"忘了加条件导致跨租户数据泄露"（SaaS 最高危事故）。边界：手写 SQL 要自己补（与逻辑删除同规则）。

## 7. 多数据源的分页失效坑

**经典生产坑**：使用 `dynamic-datasource` 多数据源后，**分页静默失效**（不报错，SQL 无 LIMIT）：

```text
原因：PaginationInnerInterceptor 在注册时绑定"默认 SqlSessionFactory"
      —— 每个数据源有自己的 SqlSessionFactory
      —— 第二个数据源执行的 SQL 没有被拦截器处理！

解法：每个数据源注册独立的 MybatisPlusInterceptor
（dynamic-datasource 的 @DS 切换数据源时，拦截器集合也要对应）
```

```java
// dynamic-datasource 的推荐配置：为每个数据源组配置拦截器
@Configuration
public class MybatisPlusConfig {

    @Bean
    @DS("master")
    public MybatisPlusInterceptor masterInterceptor() {
        return buildInterceptor(DbType.MYSQL);
    }

    @Bean
    @DS("slave")
    public MybatisPlusInterceptor slaveInterceptor() {
        return buildInterceptor(DbType.MYSQL);
    }

    private MybatisPlusInterceptor buildInterceptor(DbType dbType) {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(dbType));
        return interceptor;
    }
}
```

**排查方法**：分页结果异常（返回全量/第一页重复）时——**开启 SQL 日志看有没有 LIMIT**；没有 LIMIT = 拦截器没作用到该数据源。

> 🎯 **核心要点**：多数据源 + 分页 = "**每个数据源一套拦截器**"——这是 MP 多数据源场景最高频的坑。排查口诀：**分页失效先看 SQL 有没有 LIMIT，没有就查拦截器绑定**。
