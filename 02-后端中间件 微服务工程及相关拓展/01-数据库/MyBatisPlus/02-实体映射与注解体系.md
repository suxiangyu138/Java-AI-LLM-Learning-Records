## 1. 三大映射注解：@TableName / @TableId / @TableField

```java
@Data
@TableName("sys_user")                    // ① 实体 → 表名（默认驼峰转下划线）
public class User {
    @TableId(type = IdType.ASSIGN_ID)     // ② 主键：策略 + 列名
    private Long id;

    @TableField("user_name")              // ③ 字段映射（默认驼峰自动转）
    private String userName;

    @TableField(exist = false)            // 非表字段：实体有但表没有（计算/展示字段）
    private String ageGroup;

    @TableField(fill = FieldFill.INSERT)  // 自动填充：插入时填充
    private LocalDateTime createTime;

    @TableField(updateStrategy = FieldStrategy.IGNORED)  // 更新策略：允许置 null
    private String remark;
}
```

| 注解 | 属性 | 说明 |
|------|------|------|
| `@TableName` | `value` | 表名（实体名驼峰转下划线时可不写） |
| `@TableId` | `value`/`type` | 主键列名与策略（不写 value 时按驼峰映射 id） |
| `@TableField` | `value`/`exist`/`fill`/`updateStrategy` | 列名、是否存在、填充策略、更新策略 |

> 🎯 **核心要点**：三大注解解决"实体 ↔ 表"的全部映射差异——**命名规范（驼峰↔下划线）时几乎不用写**；差异场景（非表字段、填充、置 null）才用注解声明。规范越好，注解越少。

## 2. 主键策略：雪花 ID 与自增

| IdType | 策略 | 适用 |
|--------|------|------|
| `ASSIGN_ID`（默认） | **雪花算法**生成 19 位 Long 分布式 ID | 分布式环境默认 |
| `AUTO` | 数据库自增 | 单库场景、整型主键 |
| `INPUT` | 应用自行赋值 | 业务自定义主键（如订单号） |
| `ASSIGN_UUID` | UUID 字符串 | 字符串主键（性能劣于雪花） |
| `NONE` | 不处理 | 框架不管 |

```java
@TableId(type = IdType.ASSIGN_ID)   // 默认：雪花 ID（MP 全局默认，可省略）
private Long id;

@TableId(type = IdType.AUTO)        // 自增：insert 后 id 被回填
private Long id;
// AUTO 前提：数据库列 AUTO_INCREMENT

@TableId(type = IdType.INPUT)       // 业务主键：insert 前自己赋值
private String orderNo;
```

**雪花 ID 要点**：

```text
雪花算法：时间戳(41位) + 机器ID(10位) + 序列号(12位) → 64 位 Long，趋势递增
优点：全局唯一、趋势递增（对索引友好）、无中心依赖
注意：前端接收 19 位 Long 会丢精度（JS Number 安全上限 2^53）→ 序列化为 String！
```

> ⚠️ **雪花 ID 的经典坑（面试高频）**：19 位 Long 传给前端 JS 会**精度丢失**（最后几位变 0）——解决：Jackson 配置 Long → String 序列化（`@JsonSerialize(using = ToStringSerializer.class)` 或全局配置）。查询再按 String 反查。

## 3. 驼峰映射与命名规范

**默认行为**：`map-underscore-to-camel-case` 默认开启——Java 驼峰字段自动映射下划线列：

```java
// Java: userName / createTime / orderNo
// SQL:  user_name / create_time / order_no
// 命名规范一致时，@TableField 可以完全不写
```

**规范约定**（MP 官方推荐 + 阿里规约）：

| 位置 | 规范 | 例子 |
|------|------|------|
| 表名 | 小写 + 下划线 | `sys_user`、`order_detail` |
| 列名 | 小写 + 下划线 | `user_name`、`create_time` |
| 实体 | 大驼峰类名 + 小驼峰字段 | `User`、`userName` |
| 主键 | 统一 `id`（Long 雪花） | `id` |
| 通用字段 | create_time/update_time/deleted/version | 自动填充（第 6 节） |

```yaml
mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true   # 默认开启，勿关
```

> 🎯 **核心要点**：**命名规范 = 零注解映射**——全团队统一"下划线表/列 + 驼峰实体"后，实体类干净到只有字段声明。规范是 MP 高效的第一前提。

## 4. 逻辑删除 @TableLogic

**逻辑删除**：不物理删除数据，用标记字段（`deleted`）软删——**可恢复、可审计**：

```java
@Data
@TableName("user")
public class User {
    private Long id;
    private String name;
    @TableLogic                          // 逻辑删除标记字段
    private Integer deleted;             // 0=未删 1=已删
}

// 效果（自动改写 SQL！）：
mapper.deleteById(1L);
// 实际执行：UPDATE user SET deleted=1 WHERE id=1 AND deleted=0
mapper.selectById(1L);
// 实际执行：SELECT ... FROM user WHERE id=1 AND deleted=0   ← 已删的查不到
mapper.selectList(wrapper);
// 实际执行：... WHERE deleted=0 [AND wrapper条件]
```

**配置方式**（注解或全局）：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted    # 全局指定逻辑删除字段（字段上可免注解）
      logic-delete-value: 1          # 已删除值
      logic-not-delete-value: 0      # 未删除值
```

**三条重要边界**（高频坑，见 08 模块详述）：

1. **自定义 SQL 不生效**：XML/`@Select` 手写 SQL 不会自动拼 `deleted=0`——需手动加；
2. **唯一索引冲突**：逻辑删除的记录仍占唯一索引槽位（如 phone 唯一）——新用户注册会冲突（解法见 08 模块）；
3. **查询条件叠加**：MP 自动拼的 `deleted=0` 与 Wrapper 条件用 AND 连接。

> 🎯 **核心要点**：逻辑删除 = **"DELETE 变 UPDATE + 查询自动过滤"**——这是 MP 最常用的数据规范能力。但它是"滤镜"不是"魔法"：手写 SQL 与唯一索引需要自己处理边界。

## 5. 乐观锁 @Version

**乐观锁**：并发更新时的版本校验——**读取带 version，更新校验 version**：

```java
@Data
public class Product {
    private Long id;
    private Integer stock;
    @Version                        // 乐观锁版本字段
    private Integer version;        // 初始 0
}

// 效果（配合 OptimisticLockerInnerInterceptor 插件，见 06 模块）：
// UPDATE product SET stock=?, version=version+1 WHERE id=? AND version=旧值
// 影响行数 = 0 → 说明 version 已被别人改过 → 冲突！

// 使用：
Product p = productMapper.selectById(1L);    // version=0
p.setStock(p.getStock() - 1);
int rows = productMapper.updateById(p);       // WHERE id=1 AND version=0
if (rows == 0) {
    throw new ConflictException("库存已被修改，请刷新重试");   // ⚠️ 必须检查返回值！
}
```

**三个关键认知**：

1. **插件必须注册**：`OptimisticLockerInnerInterceptor` 不注册，`@Version` 不生效（update 会变成普通更新）；
2. **冲突不抛异常**（与 JPA 不同！）：MP 返回 **0 行**——业务代码必须检查返回值并处理（提示/重试）；
3. **重试须重新读**：冲突后重试不能复用旧 entity（version 已过期），要重新 `selectById`。

> ⚠️ **面试必答差异**：JPA 的 `@Version` 冲突**抛 OptimisticLockException**；MP **返回 0 行不抛异常**——两种框架行为不同，用 MP 必须显式检查返回值（`updateById` 的 int 结果）。

## 6. 自动填充：MetaObjectHandler

**自动填充**：插入/更新时自动填字段（创建时间、更新时间、操作人）——**规范字段零手写**：

```java
// ① 实体标注填充策略
@Data
public class Order {
    @TableField(fill = FieldFill.INSERT)              // 插入时填充
    private LocalDateTime createTime;

    @TableField(fill = FieldFill.INSERT_UPDATE)       // 插入+更新时填充
    private LocalDateTime updateTime;

    @TableField(fill = FieldFill.INSERT)              // 操作人（如当前登录用户）
    private Long createBy;
}

// ② 实现 MetaObjectHandler
@Component
public class MyMetaObjectHandler implements MetaObjectHandler {

    @Override
    public void insertFill(MetaObject metaObject) {
        this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now());
        this.strictInsertFill(metaObject, "createBy", Long.class, currentUserId());
        // strict 系列：仅当字段为 null 时填充 —— 不覆盖手动设置的值
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        this.strictUpdateFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
    }
}
```

> 🎯 **核心要点**：自动填充的规范价值 = **"创建/更新时间、操作人"零手写且全库一致**——`strictInsertFill/strictUpdateFill`（仅 null 填充）是推荐用法，避免覆盖业务显式赋的值。

## 7. 枚举处理与类型转换

**枚举 ↔ 数据库值自动转换**（避免魔法数字）：

```java
// ① 枚举实现 IEnum（或标注 @EnumValue）
@Getter
public enum OrderStatus implements IEnum<Integer> {
    PENDING(0, "待支付"),
    PAID(1, "已支付"),
    SHIPPED(2, "已发货");

    private final int value;
    private final String desc;
    OrderStatus(int value, String desc) { this.value = value; this.desc = desc; }

    @Override
    public Integer getValue() { return value; }
}

// ② 实体直接使用枚举类型
@Data
public class Order {
    private Long id;
    private OrderStatus status;    // 数据库存 0/1/2，实体用枚举 —— 自动转换
}

// ③ 配置：扫描枚举包（默认开启）
mybatis-plus:
  configuration:
    default-enum-type-handler: com.baomidou.mybatisplus.extension.handlers.MybatisEnumTypeHandler
```

**3.5.17 增强**：枚举类型处理器增加缓存机制——高并发下枚举转换性能优化。

> 🎯 **核心要点**：枚举处理消灭"魔法数字"——数据库存数值、实体用枚举、自动转换。状态字段（订单状态/用户状态）是最大受益者；复杂映射（JSON 字段）用 `JacksonTypeHandler` 配合 `@TableField(typeHandler = ...)`。
