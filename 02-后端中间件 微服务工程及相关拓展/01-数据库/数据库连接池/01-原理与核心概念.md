## 1. 为什么创建连接贵

**一次连接创建的完整成本**（连接池存在的根本原因）：

```text
getConnection() 的全过程：
  ① TCP 网络握手（网络往返）
  ② 数据库认证（用户名/密码验证，可能含 SSL 握手）
  ③ 会话初始化（权限检查/变量/时区/字符集设置）
  ④ 驱动对象初始化
  → 耗时：毫秒 ~ 几十毫秒（与网络/认证方式相关）

无连接池的放大效应：
  100 并发 × 每次新连接 = 100 次握手认证
  → 数据库连接数暴涨（耗尽 max_connections）
  → 每个请求都付创建成本（延迟飙升）

连接池的核心价值：创建一次，复用 N 次
  → 创建成本摊薄到每次借用
```

**三个价值维度**（面试必答）：

| 价值 | 机制 |
|------|------|
| 性能 | 复用连接（免握手/认证/会话初始化） |
| 控制 | 最大连接数限制（防压垮数据库） |
| 管理 | 空闲回收/泄漏检测/健康校验 |

> 🎯 **核心要点**：连接池存在的原因 = "**创建连接贵（握手+认证+会话）→ 预先建池复用**"——**"创建一次、复用 N 次"是全部价值的根源**；无池时高并发 = 连接数爆炸 + 延迟飙升。

## 2. 借/还模型

**连接池的本质 = 连接的对象池（借/还）**：

```java
// 借（池空则等待，超时抛异常）
Connection conn = dataSource.getConnection();
// 使用...
// 还（close 语义 = 归还！）
conn.close();

// 正确姿势：TWR（自动归还）
try (Connection conn = dataSource.getConnection()) {
    // 使用
}   // close 自动执行 = 归还池中
```

**借/还模型的四个关键认知**：

```text
① close ≠ 断开：归还池中（可复用）—— 池实现包装了 close
② 池空的行为：等待（connection-timeout 内）→ 超时抛 SQLTransientConnectionException
③ 归还的复位：autoCommit=true + 隔离级别默认（防"上次事务污染"）
④ 借用记录：池可追踪"谁借了没还"（leakDetectionThreshold）

对比 DriverManager：
  DriverManager 的 close = 真断开
  连接池的 close = 归还（代理包装）
→ "close 语义因来源而异"是最重要的认知差
```

> 🎯 **核心要点**：借/还 = "**getConnection 借、close 还**"——**"连接池的 close 是归还不是断开"是理解一切连接池行为的第一认知**；TWR 是自动归还的标准姿势（`Java异常体系/04` 联动）。

## 3. 连接生命周期

**一个连接的完整生命周期**：

```text
创建阶段：
  初始化建池（initial-size）或按需创建（懒加载）
  达到 maximum-pool-size 后不再创建（新请求等待）

使用阶段：
  借出 → 业务使用 → 归还
  归还时：复位（autoCommit/隔离级别）+ 有效性校验

回收阶段：
  idle-timeout：空闲超过 → 回收（降到 minimum-idle）
  max-lifetime：存活超过 → 销毁重建（防数据库侧断连）
  有效性校验：归还/借用时测试（validationQuery / 心跳）

销毁阶段：
  池关闭（应用退出）→ 全部连接关闭
```

**生命周期的三个关键参数**（决定连接"何时死何时生"）：

| 参数 | 作用 | 配置要点 |
|------|------|---------|
| max-lifetime | 连接最大存活 | **必须 < 数据库 wait_timeout**（防死连接） |
| idle-timeout | 空闲回收 | 波动负载调小（省资源） |
| minimum-idle | 最小空闲数 | 保底（防突发不够用） |

> 🎯 **核心要点**：生命周期 = "**创建 → 借还 → 回收 → 销毁**"四阶段——**"max-lifetime < wait_timeout"是最重要的配置约束**（防死连接，见 06 模块）；归还复位与有效性校验是池的"卫生机制"。

## 4. DataSource 标准接口

**DataSource（javax.sql）**：连接池的统一标准接口——**换连接池零代码改动**：

```java
// 标准接口（核心方法）
public interface DataSource {
    Connection getConnection() throws SQLException;
    Connection getConnection(String user, String password) throws SQLException;
}

// 用法（面向接口）
DataSource ds = new HikariDataSource(config);   // 或 DruidDataSource
try (Connection conn = ds.getConnection()) { ... }

// Spring Boot：自动注入 DataSource（配置驱动实现）
@Autowired
private DataSource dataSource;    // 实际是 HikariDataSource（默认）
```

**DataSource 的扩展接口**：

```java
// 连接池的额外能力（非标准，各池实现）
// HikariCP：HikariDataSource（getHikariPoolMXBean 监控）
// Druid：DruidDataSource（getStatManager 统计）

// 标准关联：
// ConnectionPoolDataSource（连接池专用，框架内部）
// XADataSource（分布式事务，JTA）
```

**为什么框架都注入 DataSource**：

```text
① 面向接口：HikariCP → Druid 切换零代码（只改配置）
② 池化统一：MyBatis/Spring 不关心池实现，只调 getConnection
③ 事务协作：DataSourceUtils 从池取"线程绑定连接"（Spring 事务）
④ 监控扩展：池实现的统计接口（JMX/Metrics）
```

> 🎯 **核心要点**：DataSource = "**连接池的标准接口（getConnection）**"——**"面向接口注入，换池零改动"是框架的依赖倒置实践**；Spring/MyBatis 的 dataSource 配置都建立在它之上。

## 5. 连接池 vs 线程池

**两个"池"的关系**（调优必须联动）：

```text
连接池大小 ≤ 线程池大小
  → 每个数据库操作占用一个连接（方法执行期间）
  → 线程池 100、连接池 10 → 最多 10 个线程同时访问 DB
  → 90 个线程在"等连接"（排队）—— 资源错配

调优联动：
  ① 先定线程池（并发模型）
  ② 再定连接池（≤ 线程池，按数据库能力）
  ③ 观察排队（连接等待时间）—— 池太小信号

对比：
  线程池：CPU 资源管理（复用线程）
  连接池：数据库连接资源管理（复用连接）
  共同点：创建贵 → 池化复用 + 上限控制
```

```text
容量规划示例：
  线程池 50（IO 密集）→ 连接池 20-30
  → 连接池公式：核数×2+磁盘 起步（HikariCP 建议）
  → 观察指标：等待获取连接时间（0 = 池够大；>0 = 偏小）
```

> 🎯 **核心要点**：两个池 = "**连接池 ≤ 线程池（每个 DB 操作占一连接）**"——**"先定线程池再定连接池 + 观察排队"**是容量规划的联动方法；两者都是"创建贵 → 池化 + 上限"的同一模式。

## 6. 参数全景速查

**连接池核心参数全景**（HikariCP 视角，其他池类似）：

| 参数 | 默认 | 语义 | 调优方向 |
|------|:----:|------|---------|
| maximum-pool-size | 10 | 最大连接 | 按并发与 DB 能力（04 模块） |
| minimum-idle | =max | 最小空闲 | 波动负载调小 |
| connection-timeout | 30s | 获取超时 | 业务容忍（池耗尽信号） |
| idle-timeout | 10min | 空闲回收 | 波动场景调小 |
| max-lifetime | 30min | 最大存活 | **< DB wait_timeout** |
| validation-timeout | 5s | 校验超时 | 默认即可 |
| connection-test-query | 无 | 有效性测试 SQL | 用 pool 自带校验 |

**配置检查清单**（生产上线前）：

```text
□ max-lifetime < 数据库 wait_timeout
□ connection-timeout 按业务容忍设置（别默认 30s 无感知）
□ minimum-idle 按波动负载设置（稳定负载 = max）
□ 泄漏检测开启（leakDetectionThreshold）
□ 监控接入（活跃/空闲/等待指标）
□ 与线程池联动评估（连接池 ≤ 线程池）
```

> 🎯 **核心要点**：参数全景 = "**五参数 + 六检查**"——**"max-lifetime < wait_timeout"是唯一硬约束**；其余按"波动/容忍/监控"三视角配置；上线前过一遍检查清单 = 防 80% 连接池事故。
