## 1. 必背考点：十二问

### 1.1 为什么需要连接池？

**答题链**：**创建连接贵（TCP 握手 + 认证 + 会话初始化，毫秒级）** → 无池高并发 = 连接数爆炸 + 延迟飙升 → **池化复用（创建一次用 N 次）** → 三大价值（性能/控制/管理）。

### 1.2 连接池的 close 是什么语义？

**答题链**：**归还池中（不是断开）**——池用代理包装 close → 归还 + 复位（autoCommit/隔离级别）→ 与 DriverManager 的 close（真断开）对比 → **TWR 是自动归还的标准姿势**。

### 1.3 连接池的核心参数？

**答题链**：**maximum-pool-size（最大，池满等待）+ minimum-idle（最小空闲）+ connection-timeout（获取超时）+ idle-timeout（空闲回收）+ max-lifetime（最大存活）** → **"max-lifetime < 数据库 wait_timeout"是硬约束**。

### 1.4 池大小怎么定？

**答题链**：**公式起步（核数×2+磁盘）→ 压测验证（等待=0 为佳）** → 数据库能力是上限（非应用并发）→ **池满 = 排队（不是创建更多）** → 与线程池联动（连接池 ≤ 线程池）。

### 1.5 HikariCP 为什么快？

**答题链**：**FastList（数组 removeLast O(1)）+ ConcurrentBag（无锁集合 + ThreadLocal 优先）+ 字节码代理（Javassist 无反射）** → 每个高频路径都优化 → 微基准比其他池快一个数量级。

### 1.6 HikariCP 的 ConcurrentBag 怎么工作？

**答题链**：**ThreadLocal 缓存（本线程优先复用，无锁）+ 主集合（CopyOnWriteArrayList 弱一致遍历）+ CAS 状态标记（借出）+ handoff 队列（等待唤醒）** → 核心 = 减少锁竞争。

### 1.7 Druid 和 HikariCP 怎么选？

**答题链**：**默认 HikariCP（性能 + Spring Boot 生态）** → 需要监控页面/慢 SQL/防火墙 → Druid → **监控可外置（Micrometer+Prometheus）则 HikariCP 足够** → 阿里系联动（Nacos/Seata）Druid 更顺。

### 1.8 连接池耗尽怎么排查？

**答题链**：**获取超时（Connection is not available）** → 三类根因：**慢 SQL 占用（最常见）> 池太小 > 泄漏** → 黄金三步：**SHOW PROCESSLIST（谁占着）→ 池指标（active/pending）→ 泄漏趋势** → 先查慢 SQL 再调池。

### 1.9 连接泄漏怎么检测？

**答题链**：**借了没还（close 未执行）→ 活跃只增不减** → 根治：TWR → 检测：**leakDetectionThreshold（借出超时打堆栈，直接定位代码）** → 监控 active 趋势告警。

### 1.10 死连接怎么防？

**答题链**：**wait_timeout 断连/网络中断 → 池中连接"看似可用实际已断"** → **max-lifetime < wait_timeout（池主动更换）** → 归还/借用校验（validation）→ "重启恢复"是死连接特征。

### 1.11 多数据源的事务边界？

**答题链**：**单事务管理器管单库** → 跨库 = 分布式事务（Seata）→ 推荐：**按库拆事务边界（避免跨库）** → @DS 切从库只读 → 强一致强制 @DS("master")。

### 1.12 虚拟线程与连接池？

**答题链**：**虚拟线程（JDK 21+）不稀缺 → 连接池成为唯一瓶颈** → 大量虚拟线程等连接 → **Semaphore 应用层限流数据库并发** → pending 指标更关键。

## 2. 高频陷阱题 12 连问

1. **对错**：连接池的 close 会断开数据库连接。（❌ 归还池中）
2. **结果**：池满时新请求？（等待（connection-timeout）而非创建更多）
3. **对错**：池越大越好。（❌ 数据库能力是上限——超过反而排队）
4. **结果**：max-lifetime 应该？（< 数据库 wait_timeout——防死连接）
5. **对错**：HikariCP 用锁队列管理连接。（❌ ConcurrentBag 无锁 + ThreadLocal）
6. **结果**：活跃连接持续上升？（泄漏信号——借了没还）
7. **对错**：获取超时的第一反应是调大池。（❌ 先查慢 SQL 占用）
8. **结果**：SHOW PROCESSLIST 看什么？（谁占着连接、执行多久）
9. **对错**：多数据源可以用一个事务管理器。（❌ 每源一个——跨库要分布式）
10. **结果**：@DS("slave") 方法内能写吗？（不建议——只读语义）
11. **对错**：连接池必须大于线程池。（❌ 连接池 ≤ 线程池）
12. **结果**：虚拟线程时代连接池的定位？（唯一瓶颈——Semaphore 限流）

## 3. 高频追问速答

| 追问 | 速答 |
|------|------|
| initial-size 和 minimum-idle？ | 初始化建池数 vs 最小空闲（保持） |
| 连接校验怎么做的？ | 归还/借用测试（validation）/ 驱动自带校验 |
| pending 指标含义？ | 等待获取连接的线程数（池压力） |
| 泄漏检测原理？ | 借出记堆栈 → 超时打印（定位不还者） |
| 主从延迟怎么办？ | 强一致 @DS("master") 强制主库读 |
| HikariCP 的字节码代理干嘛？ | 拦截 close（归还）+ 零反射调用 |
| 池大小和数据库关系？ | 池 × 单连接负载 < 数据库吞吐 |
| 连接被 kill 的特征？ | 批量失败 + 时间集中（外部操作） |
| 从库连接池要多大？ | 按读负载（通常 > 主库池） |
| 连接池监控接什么？ | Micrometer → Prometheus（active/pending/timeout） |

## 4. 场景题：连接池调优方案

**题目**：线上服务出现"获取连接超时"（Connection is not available），请给出排查与调优方案。

**答题框架**（按评分点展开）：

```text
① 先确认根因（黄金三步）：
   - SHOW PROCESSLIST：有没有慢 SQL 占着连接（最常见！）
     → Time 大的连接 + 慢查询日志
   - 池指标：active 是否长期 = maximum（容量）vs 波动
   - 泄漏趋势：active 只增不减 = 泄漏
② 分方向修复：
   - 慢 SQL → 优化 SQL/索引（治本）
   - 池太小 → 压测确认后调大（公式起步 + 等待=0 验证）
   - 泄漏 → TWR + leakDetectionThreshold
③ 配置核对：
   - max-lifetime < wait_timeout（防死连接）
   - connection-timeout 按业务容忍
   - 与线程池联动（连接池 ≤ 线程池）
④ 监控与预防：
   - active/pending/timeout 接入 Prometheus 告警
   - 泄漏检测常开
   - 数据库侧 max_connections 核对
⑤ 加分点：
   - 谈"先查慢 SQL 再调池"（假池小的根因）
   - 谈"一次只改一个参数"（调优纪律）
   - 谈虚拟线程时代连接池是唯一瓶颈（Semaphore）
```
