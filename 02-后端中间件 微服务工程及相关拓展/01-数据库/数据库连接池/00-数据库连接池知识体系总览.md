## 3. 为什么必须学透连接池

1. **数据库访问的第一性能瓶颈**：连接创建耗时（握手+认证）是毫秒级——**没有连接池，高并发直接崩溃**；连接池参数错 = 生产事故。
2. **面试必考的"底层基础设施"**："连接池为什么快""HikariCP 源码级机制""池大小怎么定"——区分"会用"与"懂原理"的标准题。
3. **排障的高频现场**：连接泄漏、池耗尽、死连接、连接被 kill——**线上数据库事故 50% 与连接池有关**。
4. **多数据源时代的复杂度**：读写分离、多库、动态数据源——连接池配置与事务边界是微服务架构的必修。
5. **框架配置的第一站**：Spring Boot 的 `spring.datasource.hikari.*`、MyBatis 的 `dataSource`——**理解连接池才能理解框架的数据访问配置**。

## 4. 核心概念速查

### 4.1 借/还模型

```text
getConnection() = 从池中"借"（池空则等待/超时）
close() = 归还池中（不是断开！）

池生命周期：创建（初始化/按需）→ 借出 → 使用 → 归还
            → 空闲回收（idle-timeout）→ 最大存活（max-lifetime）
            → 校验（连接有效性）
```

### 4.2 核心参数速查

| 参数 | 默认 | 语义 |
|------|:----:|------|
| maximum-pool-size | 10 | 最大连接数 |
| minimum-idle | =max | 最小空闲 |
| connection-timeout | 30s | 获取超时 |
| idle-timeout | 10min | 空闲回收 |
| max-lifetime | 30min | 连接最大存活 |

### 4.3 主流连接池

| 连接池 | 特点 | 定位 |
|--------|------|------|
| HikariCP | 最快（字节码代理+无锁） | Spring Boot 默认 |
| Druid | 监控+防火墙最全 | 阿里系 |
| dbcp2/c3p0 | 老牌 | 遗留项目 |

## 7. 常见误区

| 误区 | 真相 |
|------|------|
| "close 会断开连接" | 池的 close = **归还**（可复用） |
| "池越大越快" | 数据库能力是上限——超过反而排队 |
| "池满就创建更多" | 池满 = **等待**（connection-timeout 内） |
| "获取超时先调池" | **先查慢 SQL**（占用连接才是根因） |
| "连接池要大于线程池" | **连接池 ≤ 线程池**（每 DB 操作占一连接） |
| "max-lifetime 随便设" | **必须 < 数据库 wait_timeout**（防死连接） |
| "HikariCP 用锁队列" | ConcurrentBag 无锁 + ThreadLocal 优先 |
| "多源可以一个事务管理器" | 每源一个——跨库要分布式（拆事务更优） |
