## 1. 池大小公式与误区

**池大小的经验公式**（2026 实践）：

```text
HikariCP 作者建议（起步）：
  池大小 = 核数 × 2 + 磁盘数
  → 4 核机器：4×2+1 = 9（约 10）
  → 8 核机器：8×2+1 = 17（约 15-20）

为什么不是"越大越好"：
  ① 连接是数据库资源（max_connections 上限）
  ② 连接数 × 单连接负载 > 数据库处理能力 → 排队/超时
  ③ 过多空闲连接 = 资源浪费（内存/数据库开销）

核心约束：
  池大小 × 每连接的工作负载 < 数据库吞吐能力
  → 池大小由"数据库能力"而非"应用并发"决定
```

**两个常见误区**：

```text
误区 1："并发 1000 → 池 1000"
  真相：池满 = 排队等待（不是创建更多）
  正确：池由数据库能力定（10-30 常见），排队由应用层缓冲

误区 2："池越大越快"
  真相：超过数据库处理能力 → 更多等待而非更快
  正确：观察"获取连接等待时间"——0 等待即为池够用
```

> 🎯 **核心要点**：池大小 = "**公式起步（核数×2+磁盘）+ 数据库能力约束**"——**"池满 = 排队（不是无限创建）"是最重要的认知**；多数业务 10-30 够用（数据库 100+ 连接是压力信号）。

## 2. 排队分析：池太小的信号

**获取连接等待（pending）是池压力的核心指标**：

```text
信号链：
  pending > 0（有线程在等连接）→ 池压力
  → 等待时间长 → connection-timeout 抛异常（池耗尽）
  → 应用异常率上升

指标解读：
  pending = 0 持续 → 池够用（甚至偏大）
  pending > 0 偶发 → 池略小（峰值场景）
  pending 持续 > 0 → 池太小 或 慢 SQL 占连接
  timeout 递增 → 池耗尽（紧急！）

关键区分：
  池太小 vs 慢 SQL 占用：
  慢 SQL 长 → 连接被长时间占用 → 池"看起来"小
  先查慢 SQL（Druid/数据库慢日志）再调池
```

```bash
# 观察方式（HikariCP Metrics）：
# hikaricp_connections_pending（等待线程数）
# hikaricp_connections_timeout（超时次数）
# 或用 JFR/线程栈：大量线程卡在 getConnection → 池压力
```

> 🎯 **核心要点**：排队分析 = "**pending > 0 = 池压力、timeout = 耗尽**"——**"先查慢 SQL 再调池"是黄金顺序**（慢 SQL 占用连接是"假池小"的根因）；指标三看（pending/timeout/active）。

## 3. 压测方法：连接池专项

**连接池压测的目标与指标**：

```text
目标：确定"池大小 + 并发模型"的最佳组合
指标：
  ① 获取连接等待时间（P95/P99）—— 池压力的直接度量
  ② 事务成功率/失败率 —— 超时影响
  ③ 吞吐（TPS）—— 容量
  ④ 数据库侧：连接数、CPU、慢查询

压测场景设计：
  ① 基线：固定池（10）→ 阶梯并发（20/50/100/200）
  ② 变池：并发固定（100）→ 池（10/20/30/50）
  ③ 峰值：突发负载（模拟高峰）
  ④ 慢 SQL 模拟：插入慢查询（观察池被占用的影响）
```

```text
压测判读：
  池 10 → 并发 100：等待时间显著 > 0 → 池偏小（或并发模型问题）
  池 30 → 并发 100：等待 ≈ 0、TPS 达标 → 池合适
  池 50 → 与 30 无差别 → 池 30 已够（避免浪费）

注意：
  压测环境与生产同规格（连接数/网络延迟）
  观察数据库侧（不能只压不测库）
```

> 🎯 **核心要点**：压测 = "**双变量（并发×池大小）矩阵 + 三指标（等待/失败/吞吐）**"——**"找到'等待=0 的池大小'是目标"**（再大无收益）；数据库侧同步观察（压测是双向的）。

## 4. 与线程池联动调优

**连接池与线程池的联动**（两者必须一起评估）：

```text
关系：连接池大小 ≤ 线程池大小
  → 每个 DB 操作占用一个连接（方法执行期间）
  → 线程池 100 而连接池 10 → 90 线程等连接

调优流程：
  ① 定并发模型（线程池）：IO 密集可大、虚拟线程另说
  ② 定连接池：≤ 线程池 + 数据库能力
  ③ 观察排队：连接等待（pending）与线程等待（队列）分开看
  ④ 平衡点：两个池的"等待"都趋近 0 为佳

示例（典型配置）：
  线程池 50（IO 密集）
  连接池 20-30（数据库可承受）
  → 等待分布：线程等任务 vs 线程等连接（分别定位）
```

**虚拟线程的联动**（JDK 21+）：

```text
虚拟线程：每任务一个（线程数不再稀缺）
  → 连接池成为唯一瓶颈（大量虚拟线程等连接）
  → 连接池需要更精确的容量规划（Semaphore 限流连接）
  → 观察：pending 指标更关键（虚拟线程不限制数量）

最佳实践（2026）：
  虚拟线程 + 连接池（池大小按数据库能力）
  → 用信号量（Semaphore）在应用层限流数据库并发
```

> 🎯 **核心要点**：联动调优 = "**连接池 ≤ 线程池 + 双等待分开看**"——**"虚拟线程时代连接池是唯一瓶颈"是 2026 新认知**（线程不稀缺了，连接稀缺）；Semaphore 限流连接（`Java多线程/07` 联动）。

## 5. 参数配置检查清单

**连接池调优的完整检查清单**（2026 实践）：

```text
□ 池大小：公式起步 + 压测验证（等待=0 为佳）
□ max-lifetime < 数据库 wait_timeout（硬约束）
□ connection-timeout：按业务容忍（30s 默认可能过长）
□ minimum-idle：稳定负载 = max；波动负载调小
□ 泄漏检测：leakDetectionThreshold 开启
□ 监控：active/pending/timeout 指标接入告警
□ 与线程池联动：连接池 ≤ 线程池
□ 慢 SQL 排查：先查慢 SQL 再调池
□ 数据库侧：max_connections 核对
□ 多环境一致：staging 与生产同参数压测

调优红线：
  ① 一次只改一个参数（与 JVM 调优同纪律）
  ② 有基线再调（先记录当前指标）
  ③ 数据库能力是上限（不是应用并发）
```

**一句话总结**：

```text
连接池调优 = 
  公式起步（核数×2+磁盘）
  + 排队分析（pending/timeout）
  + 压测验证（等待=0 为佳）
  + 线程池联动（连接池 ≤ 线程池）
  + 慢 SQL 优先（假池小的根因）
```

> 🎯 **核心要点**：检查清单 = "**十项 + 三条红线**"——**"一次只改一个参数 + 有基线再调"与 JVM 调优纪律一致**（`JVM调优/01` 联动）；慢 SQL 优先是"假池小"的根治顺序。

## 6. 调优速查卡

**连接池调优决策速查**：

```text
症状 → 动作：
  获取超时 → 先查慢 SQL（PROCESSLIST）→ 再调池
  pending > 0 持续 → 池压力（慢 SQL 或容量）
  active 只增不减 → 泄漏（TWR + 检测）
  偶发失败（重启恢复）→ 死连接（lifetime vs wait_timeout）
  批量失败（时间集中）→ 被 kill（数据库侧）

参数 → 建议：
  maximum-pool-size → 核数×2+磁盘起步，压测等待=0 为佳
  connection-timeout → 按业务容忍（别 30s 干等）
  max-lifetime → < wait_timeout（硬约束）
  minimum-idle → 稳定负载 = max；波动调小

红线三条：
  一次只改一个参数
  有基线再调（先记录当前指标）
  数据库能力是上限（非应用并发）
```

**"面试一句话调优"**：

```text
"连接池调优我按数据驱动：
 先看指标定位（pending/timeout/active），
 先查慢 SQL 再调池（占用才是根因），
 池大小公式起步 + 压测验证（等待=0 为佳），
 硬约束 max-lifetime < wait_timeout，
 与线程池联动（连接池 ≤ 线程池）。"
```

> 🎯 **核心要点**：调优速查 = "**症状→动作表 + 参数建议 + 三红线**"——**"先查慢 SQL 再调池"是最重要的顺序认知**；一句话话术覆盖面试调优题（与 `JVM调优/01` 的数据驱动纪律一致）。
