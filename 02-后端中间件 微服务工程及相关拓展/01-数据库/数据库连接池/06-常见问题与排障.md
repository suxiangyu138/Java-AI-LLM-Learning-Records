## 1. 问题全景：四大高频事故

**连接池四大高频事故**（线上 80% 的数据库连接问题）：

| 事故 | 症状 | 根因 |
|------|------|------|
| 连接泄漏 | 活跃数只增不减 → 耗尽 | close 未执行（借了没还） |
| 池耗尽 | 获取连接超时异常 | 慢 SQL 占用 / 池太小 / 泄漏 |
| 死连接 | 偶发 SQL 失败（连接已断） | wait_timeout / 网络中断 |
| 被 kill | 连接突然消失 | 数据库 kill / 重启 / 防火墙 |

```text
排查的总原则（与 JVM 调优一致）：
  ① 先看监控（活跃/等待/超时指标）
  ② 分方向（泄漏/容量/连接质量）
  ③ 有数据再动手（一次一个假设）
```

> 🎯 **核心要点**：四大事故 = "**泄漏（代码）+ 耗尽（容量/慢 SQL）+ 死连接（配置/网络）+ 被 kill（数据库侧）**"——**"先看指标分方向"是排障第一步**（数据驱动，与 `JVM调优/01` 同纪律）。

## 2. 连接泄漏：借了没还

**泄漏 = 借出后 close 未执行**（异常路径/长生命周期持有）：

```java
// ❌ 泄漏写法（异常路径不归还）
Connection conn = dataSource.getConnection();
try {
    // 业务（抛异常 → 直接跳出不执行 close）
} catch (SQLException e) {
    throw e;
} // conn 未 close → 泄漏

// ✅ TWR（自动归还）
try (Connection conn = dataSource.getConnection()) {
    // 业务
} catch (SQLException e) {
    throw e;
}
```

**症状与排查**：

```text
症状链：
  活跃连接持续上升（不回落）→ 池满 → 新请求等待 → 超时 → 服务不可用

排查：
  ① 监控：active 趋势（只增不减 = 泄漏）
  ② leakDetectionThreshold：超时借出打堆栈（直接定位代码）
  ③ 代码审查：所有 getConnection 是否 TWR
  ④ 常见漏点：异常路径、嵌套资源、连接存字段/静态

根治：
  ① 一律 TWR（Connection/Statement/ResultSet 三层）
  ② 连接生命周期 = 方法内（不存字段/静态）
  ③ 泄漏检测开启（防患于未然）
```

> 🎯 **核心要点**：泄漏 = "**借了没还（close 未执行）**"——**"TWR 根治 + leakDetection 定位"是双保险**；"活跃只增不减"是泄漏的监控特征（`Java异常体系/04` 联动）。

## 3. 连接池耗尽：获取超时

**池耗尽 = 连接不够用**（获取超时异常）：

```text
症状：SQLTransientConnectionException（HikariCP）
      "Connection is not available, request timed out"

三类根因（按频率）：
  ① 慢 SQL 占用：长事务/慢查询占着连接不放（最常见！）
  ② 池太小：并发超过池容量（容量规划问题）
  ③ 泄漏：借了没还（与第 2 节联动）

排查顺序（黄金三步）：
  ① 慢 SQL：Druid/数据库慢日志 → 先排除"占用"问题
  ② 池指标：active 是否长期 = maximum（容量）vs 波动
  ③ 泄漏：active 趋势（只增不减 = 泄漏）
```

```bash
# 排查命令：
# ① 线程栈：找大量卡在 getConnection 的线程
jstack <pid> | grep -B2 "getConnection" | head -20
# ② 数据库侧：当前连接与执行中的 SQL
SHOW PROCESSLIST;    # 看连接状态与耗时（Time 大的 = 占用）
# ③ 池指标：active/pending/timeout（Prometheus）
```

**根治策略**：

```text
慢 SQL → 优化 SQL/索引（治本）
池太小 → 压测确认后调大（04 模块）
泄漏 → TWR + 检测
外加：connection-timeout 合理设置（别 30s 干等）
```

> 🎯 **核心要点**：耗尽 = "**慢 SQL > 池小 > 泄漏**"三类根因——**"先查 SHOW PROCESSLIST（谁占着连接）再调池"是黄金顺序**；慢 SQL 是"假池小"的最常见根因（与 `SQL调优/` 联动）。

## 4. 死连接：wait_timeout 与网络中断

**死连接 = 连接"看起来在池里但实际已断"**：

```text
成因：
  ① wait_timeout：数据库空闲超时断连（MySQL 默认 8 小时）
     → 池中空闲连接被数据库关闭 → 借出后执行失败
  ② 网络中断：防火墙/网络抖动断开长连接
  ③ 数据库重启：所有旧连接失效

症状：
  偶发 SQL 失败（"Connection closed" / "Communications link failure"）
  重启应用后恢复（新连接）

根治（配置 + 校验双管）：
  ① max-lifetime < wait_timeout（关键！）
     → 池在数据库断连前主动更换连接
  ② 有效性校验：归还/借用时测试（validation）
  ③ 数据库侧：wait_timeout 调大或关闭（按业务）

配置示例：
  HikariCP：max-lifetime=1800000（30min）< MySQL wait_timeout=28800
  Druid：test-while-idle=true + validation-query=SELECT 1
```

> 🎯 **核心要点**：死连接 = "**池不知道连接已断（数据库超时/网络）**"——**"max-lifetime < wait_timeout"是根治的核心配置**（01 模块的硬约束）；"重启恢复"是死连接的典型特征（排查信号）。

## 5. 连接被 kill：数据库侧

**连接被 kill = 数据库主动断开**（应用侧无法自愈的配置）：

```text
数据库侧 kill 连接的原因：
  ① 管理操作：kill <thread_id>（运维/脚本误操作）
  ② max_connections 达到：数据库拒绝新连接（已有的可能被挤）
  ③ 防火墙/安全策略：长连接被中间层断开
  ④ 数据库重启/故障切换

症状：
  批量连接失败（不只是单个）—— 时间集中
  应用恢复后连接池重建（重启或自动重连）

排查：
  ① 数据库日志：kill 记录 / 错误日志
  ② 时间关联：批量失败时间 vs 运维操作时间
  ③ 网络层：防火墙/网关策略（连接空闲/时长限制）

应对：
  ① 连接池重连机制：自动重建（HikariCP 默认会重试）
  ② 监控：连接失败率告警
  ③ 沟通：数据库变更/运维操作的通知流程
```

> 🎯 **核心要点**：被 kill = "**数据库侧主动断开（批量时间集中）**"——**"批量失败 + 时间集中 = 外部操作"是排查特征**；应用侧能做的只有重连与告警（根因在数据库/运维侧）。

## 6. 排障工具与方法链

**连接池排障的工具与方法链**（完整流程）：

```text
① 监控先行（指标定位方向）：
   - active（活跃）/ pending（等待）/ timeout（超时）
   - 失败率（获取失败/执行失败）
② 线程栈（定位等待者）：
   - jstack 找卡在 getConnection 的线程（谁在等）
③ 数据库侧（定位占用者）：
   - SHOW PROCESSLIST（谁占着连接、执行多久）
   - 慢查询日志（占用连接的时间来源）
④ 泄漏检测（定位不还者）：
   - leakDetectionThreshold（借出超时打堆栈）
⑤ 配置核对（定位配置问题）：
   - max-lifetime vs wait_timeout
   - 池大小 vs 并发/数据库能力
⑥ 修复与验证：
   - 一次改一个 → 观察指标变化 → 确认
```

**排障决策树**：

```text
获取连接超时？
├── active = max 且 pending > 0 → 池耗尽
│     ├── 慢 SQL？（SHOW PROCESSLIST）→ 优化 SQL
│     ├── 泄漏？（active 趋势）→ TWR + 检测
│     └── 池太小？（压测）→ 调大
├── active 波动正常但偶发失败 → 死连接
│     └── max-lifetime vs wait_timeout 核对
└── 批量失败 + 时间集中 → 被 kill
      └── 数据库/运维侧排查
```

> 🎯 **核心要点**：排障方法链 = "**监控 → 线程栈 → PROCESSLIST → 泄漏检测 → 配置核对 → 验证**"六步——**"决策树三分（耗尽/死连接/被 kill）"让排障有路径**；与 `JVM调优/05` 的排查总图同构（数据驱动）。
