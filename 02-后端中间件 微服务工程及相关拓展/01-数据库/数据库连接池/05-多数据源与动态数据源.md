## 1. 多数据源的三种架构

**多数据源的三种典型场景**：

```text
① 读写分离：主库（写）+ 从库（读）
   → 写走主、读走从（负载分担）
   → 连接池：主池 + 从池（各配置）

② 多业务库：订单库 + 用户库 + 库存库
   → 不同业务不同库（领域隔离）
   → 连接池：每库一个

③ 混合：读写分离 + 多业务库
   → 最复杂（N 个库 × 主从）
```

**读写分离的典型配置**：

```text
主库池（写）：连接池 A（master）
从库池（读）：连接池 B（slave，可多个）

使用：@DS("master") / @DS("slave") 切换（dynamic-datasource）
或：MyBatis 插件按 SQL 类型路由（读走从、写走主）

注意：
  从库延迟（主从复制延迟 → 读写一致性）
  强一致场景必须走主库（@DS("master") 强制）
```

> 🎯 **核心要点**：多数据源 = "**读写分离 + 多业务库 + 混合**"三种架构——**"每库一个连接池"是基础**；读写分离的从库延迟是必须考虑的语义（强一致走主）。

## 2. 多数据源的配置映射

**多数据源的连接池配置**（Spring Boot 手动方案）：

```yaml
# 主库
spring:
  datasource:
    primary:
      url: jdbc:mysql://master:3306/order_db
      username: root
      password: root
      hikari:
        maximum-pool-size: 20
# 从库
    secondary:
      url: jdbc:mysql://slave:3306/order_db
      username: read
      password: read
      hikari:
        maximum-pool-size: 30
```

```java
// 手动配置两个数据源（+ 各自连接池）
@Configuration
public class DataSourceConfig {

    @Bean
    @Primary
    @ConfigurationProperties("spring.datasource.primary")
    public DataSource primaryDataSource() {
        return DataSourceBuilder.create().build();    // Hikari
    }

    @Bean
    @ConfigurationProperties("spring.datasource.secondary")
    public DataSource secondaryDataSource() {
        return DataSourceBuilder.create().build();
    }
}
```

**配置映射的要点**：

```text
① 每个数据源独立连接池参数（容量按负载分）
② @Primary 标记主数据源（框架默认注入）
③ 切换：@DS 注解 / AbstractRoutingDataSource
④ 事务管理器：每数据源一个（DataSourceTransactionManager）
```

> 🎯 **核心要点**：多源配置 = "**每源一个 DataSource Bean + 独立连接池 + @Primary 主源**"——**"每库独立池参数（容量按负载）"是规范**；`@ConfigurationProperties` 绑定（`Spring框架核心/08` 联动）。

## 3. dynamic-datasource 方案

**dynamic-datasource（苞米豆开源）**：多数据源的注解化切换（主流方案）：

```yaml
# 依赖
# com.baomidou:dynamic-datasource-spring-boot-starter

spring:
  datasource:
    dynamic:
      primary: master                # 默认数据源
      strict: false                  # 未匹配是否报错
      datasource:
        master:
          url: jdbc:mysql://master:3306/order_db
          username: root
          password: root
          driver-class-name: com.mysql.cj.jdbc.Driver
        slave:
          url: jdbc:mysql://slave:3306/order_db
          username: read
          password: read
          driver-class-name: com.mysql.cj.jdbc.Driver
```

```java
// 注解切换（Service/Mapper 方法级）
@Service
@DS("master")                        // 类级默认
public class OrderService {

    @DS("slave")                     // 方法级覆盖：读走从库
    public List<Order> listOrders() { ... }

    @DS("master")                    // 写走主库
    public void createOrder(Order o) { ... }
}

// 编程式切换
DynamicDataSourceContextHolder.push("slave");
try { ... } finally {
    DynamicDataSourceContextHolder.poll();
}
```

**dynamic-datasource 的优势**：

```text
① 注解切换（@DS）—— 声明式，侵入小
② 内置连接池管理（每个数据源独立池）
③ 与 MyBatis/MyBatisPlus 无缝集成
④ 支持主从（read/write 自动路由的简化版）

注意（衔接 MyBatisPlus/06）：
  多数据源下分页/拦截器需要每源注册（分页失效坑）
```

> 🎯 **核心要点**：dynamic-datasource = "**@DS 注解切换多数据源（主流方案）**"——**"类级默认 + 方法级覆盖"是声明式用法**；多源下分页拦截器要每源注册（`MyBatisPlus/06` 的经典坑）。

## 4. 多数据源的事务边界

**多数据源的事务是难点**（单事务管理器管不了跨库）：

```text
问题：一个事务跨越两个库（写主库 + 写订单库）
  → DataSourceTransactionManager 只管理一个数据源
  → 跨库事务 = 分布式事务（两阶段/最终一致）

方案（按需求选）：
  ① 避免跨库事务：按库拆分事务边界（推荐）
     - 一个业务一个库内完成
     - 跨库操作解耦（事件/MQ 异步）
  ② 分布式事务：Seata（AT/TCC）—— 02 层有专题
  ③ 本地消息表：最终一致

@DS 与 @Transactional 的关系：
  @Transactional 由"默认/主数据源"的事务管理器管理
  切 @DS 到从库时：只读操作无事务问题
  跨源写操作：不是同一事务（需要分布式方案）
```

**多源事务的注意清单**：

```text
① 读走从、写走主：@DS("slave") 方法内不做写
② 强一致：强制 @DS("master")（主库读）
③ 跨库事务：评估必要性（能用单库就不跨）
④ 事务管理器：多源时明确 @Transactional(transactionManager=...)
⑤ 从库延迟：读写分离的语义边界（最终一致 vs 强一致）
```

> 🎯 **核心要点**：多源事务 = "**单事务管单库、跨库要分布式**"——**"尽量按库拆事务（推荐）"是 2026 实践**（避免为跨库引入分布式复杂度）；@DS 与 @Transactional 的组合边界要清楚（`Spring框架核心/06` 与 `02-.../Seata` 联动）。

## 5. 多数据源的常见坑

**多数据源的高频坑清单**（生产实践）：

| # | 坑 | 表现 | 解法 |
|:-:|-----|------|------|
| 1 | **分页失效** | 从库 SQL 无 LIMIT | 每源注册拦截器（MyBatisPlus/06） |
| 2 | **事务走错源** | @DS 切从库但事务在主库 | 明确 transactionManager |
| 3 | **主从延迟** | 写完立即读不到 | 强一致 @DS("master") |
| 4 | **连接池混淆** | 从库池太小被写占满 | 独立池参数按负载 |
| 5 | **@DS 不生效** | 注解在自调用内 | 走代理（拆类） |
| 6 | **默认源配置错** | primary 未配 | dynamic.primary 指定 |
| 7 | **从库只读误写** | 写操作走从库 | 路由规则校验/告警 |
| 8 | **池耗尽连锁** | 主库慢 → 从库也被拖 | 独立监控 + 熔断 |

**排障方法链**：

```text
多源问题先确认"请求走了哪个源"：
  ① 日志：数据源路由信息（dynamic-datasource 打印）
  ② 监控：各源连接池指标分开看
  ③ 事务：@Transactional 的 transactionManager 归属
→ 定位"源"再排查（配置/参数/事务）
```

> 🎯 **核心要点**：多源坑 = "**分页失效 + 事务错源 + 延迟 + 池混淆**"四大类——**"先确认走了哪个源再排查"是方法论**；八坑清单与 `MyBatisPlus/06` 的分页失效联动（每源注册拦截器）。
