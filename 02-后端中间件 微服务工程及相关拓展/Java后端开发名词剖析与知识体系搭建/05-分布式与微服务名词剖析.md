## 1. 分布式理论基础

### 1.1 CAP 定理

```text
CAP Theorem（2000年 Brewer 提出）：

  C = Consistency（一致性）
    → 所有节点同一时刻看到相同数据

  A = Availability（可用性）
    → 每个请求都能收到非错误的响应

  P = Partition Tolerance（分区容错性）
    → 网络分区时系统仍能继续运作

  核心结论：三者不可兼得，最多同时满足两个！

  ┌──────────────────────────────────┐
  │  CP 系统（一致性 + 分区容错）     │
  │  → ZooKeeper, Etcd, Consul       │
  │  → 发生分区时可能不可用           │
  ├──────────────────────────────────┤
  │  AP 系统（可用性 + 分区容错）     │
  │  → Eureka, Cassandra, CouchDB    │
  │  → 发生分区时可能数据不一致       │
  ├──────────────────────────────────┤
  │  CA 系统（一致性 + 可用性）       │
  │  → 单机数据库（MySQL, PostgreSQL）│
  │  → 网络分区不存在于单机系统       │
  └──────────────────────────────────┘

实际选择：由于 P（分区）在分布式系统中不可避免，
实际是在 C 和 A 之间做权衡。
```

### 1.2 BASE 理论

```text
BASE = Basically Available + Soft state + Eventually consistent

  Basically Available（基本可用）
    → 故障时允许损失部分可用性（如降级、限流）

  Soft State（软状态）
    → 允许系统存在中间状态，不需要时刻一致

  Eventually Consistent（最终一致性）
    → 不保证立刻一致，但保证最终会一致

BASE 是 AP 系统的实践指导，是 CAP 中 C 的妥协。
```

## 2. 一致性协议

### 2.1 Paxos vs Raft

| 维度 | Paxos | Raft |
|------|-------|------|
| **提出者** | Leslie Lamport (1990) | Stanford (2013) |
| **可理解性** | 极其困难 😵 | 易理解 ✅ |
| **角色** | Proposer/Acceptor/Learner | Leader/Follower/Candidate |
| **选举** | 无明确 Leader 选举 | Leader 选举（Term 机制） |
| **日志同步** | 多轮两阶段 | Leader → Follower 单向复制 |
| **实际使用** | Chubby (Google) | Etcd, Consul, TiKV, Kafka |

```text
Raft 协议核心流程：

  1. Leader 选举（Leader Election）
     → 随机 Election Timeout（150-300ms）
     → 先到期的 Follower → Candidate → 发起投票
     → 收到多数票 → 成为 Leader
     → Term（任期号）递增，保证单调

  2. 日志复制（Log Replication）
     → Leader 接收客户端请求
     → 追加到本地日志（uncommitted）
     → 并行发送 AppendEntries 给所有 Follower
     → 收到多数确认 → commit → 返回客户端

  3. 安全性保证
     → 选举限制：Candidate 的日志必须至少和多数节点一样新
     → 提交限制：Leader 只能提交当前 Term 的日志
```

### 2.2 共识算法对比

| 算法 | 类型 | 拜占庭容错 | 使用场景 |
|------|:--:|:--------:|---------|
| **Paxos** | CFT | ❌ | 分布式协调基础 |
| **Raft** | CFT | ❌ | 服务发现、配置中心 |
| **ZAB** | CFT | ❌ | ZooKeeper 专用 |
| **PBFT** | BFT | ✅ | 联盟链（Fabric） |
| **PoW/PoS** | BFT | ✅ | 公链（Bitcoin/Ethereum） |

> CFT = Crash Fault Tolerance（节点崩溃）；BFT = Byzantine Fault Tolerance（节点作恶）

## 3. 服务治理

### 3.1 核心组件

| 组件 | 功能 | 代表 |
|------|------|------|
| **注册中心** | 服务注册 + 服务发现 + 健康检查 | Nacos, Eureka, Consul, ZooKeeper |
| **配置中心** | 配置集中管理 + 动态刷新 | Nacos, Apollo, Spring Cloud Config |
| **API 网关** | 路由、限流、鉴权、日志、跨域 | Gateway, Kong, APISIX |
| **负载均衡** | 将请求分发到多个实例 | Ribbon/LoadBalancer, Nginx |

### 3.2 注册中心对比

| 维度 | Nacos | Eureka | Consul | ZooKeeper |
|------|:-----:|:------:|:------:|:---------:|
| **CAP** | CP + AP 可切换 | AP | CP | CP |
| **一致性** | Raft (CP) | 最终一致 | Raft | ZAB |
| **健康检查** | TCP/HTTP/MySQL | Client 心跳 | Script/TCP/HTTP | KeepAlive |
| **配置中心** | ✅ 内置 | ❌ | ✅ KV | ❌ |
| **多数据中心** | ✅ | ✅ | ✅ | ❌ |
| **保护阈值** | ✅ | ✅ | ❌ | ❌ |
| **控制台** | ✅ 丰富 | ✅ 简单 | ✅ | ❌ 无(需第三方) |

### 3.3 网关核心概念

```text
Gateway 三大核心：

  1. 路由 Route：
     → Predicate（断言）：匹配请求路径/参数/Header
     → URI：目标服务地址
     → Filter：处理链

  2. 断言 Predicate（Java 8 Function）：
     Path=/api/user/**         → 路径匹配
     Header=X-Request-Id,\d+   → 请求头匹配
     Method=GET,POST           → 请求方法匹配
     Host=**.example.com       → 主机名匹配

  3. 过滤器 Filter：
     GatewayFilter（局部）：
       AddRequestHeader       → 添加请求头
       RequestRateLimiter     → 令牌桶限流
       CircuitBreaker         → 熔断
       Retry                  → 重试
     GlobalFilter（全局）：
       LoadBalancerClientFilter → 负载均衡
       NettyRoutingFilter      → 转发请求
```

## 4. 远程调用 RPC

### 4.1 HTTP vs RPC

| 维度 | HTTP/REST | RPC (gRPC/Dubbo) |
|------|:---------:|:--------------:|
| **协议** | HTTP/1.1 or 2.0 | TCP (自定义) / HTTP/2 |
| **序列化** | JSON (文本) | Protobuf/Hessian (二进制) |
| **性能** | 较低（JSON 序列化开销大） | 高（二进制序列化） |
| **跨语言** | ✅ 天然支持 | gRPC ✅ / Dubbo ❌ |
| **服务定义** | 无严格契约 | .proto (gRPC) / Java Interface (Dubbo) |
| **适用** | 对外 API / BFF | 内部微服务间调用 |

### 4.2 Feign / OpenFeign

```java
// 声明式 HTTP 客户端
@FeignClient(name = "user-service", path = "/users")
public interface UserClient {

    @GetMapping("/{id}")
    UserDTO getUser(@PathVariable Long id);

    @PostMapping
    Result<Long> createUser(@RequestBody CreateUserRequest request);
}

// 调用就像本地方法一样！
UserDTO user = userClient.getUser(1L);

// 内置集成：Ribbon 负载均衡 + Hystrix/Sentinel 熔断
```

### 4.3 序列化协议对比

| 协议 | 类型 | 大小 | 速度 | 可读性 | 跨语言 |
|------|:---:|:---:|:---:|:----:|:----:|
| **JSON** | 文本 | 大 | 慢 | ✅ 好 | ✅ |
| **Protobuf** | 二进制 | 小 | 快 | ❌ | ✅ |
| **Hessian** | 二进制 | 中 | 中 | ❌ | 部分 |
| **Kryo** | 二进制 | 小 | 很快 | ❌ | ❌ |
| **MsgPack** | 二进制 | 中 | 快 | ❌ | ✅ |
| **Java Serializable** | 二进制 | 大 | 慢 | ❌ | ❌ |

> 💡 gRPC 默认 Protobuf；Dubbo 默认 Hessian，可选 Kryo/Protobuf。

## 6. 分布式事务

### 6.1 解决方案对比

| 方案 | 原理 | 一致性 | 性能 | 复杂度 | 代表 |
|------|------|:----:|:---:|:---:|------|
| **2PC** | 两阶段提交 | 强一致 | 低 | 中 | XA 事务 |
| **TCC** | Try-Confirm-Cancel | 最终一致 | 高 | 高 | Seata TCC |
| **Saga** | 正向+补偿操作链 | 最终一致 | 高 | 中 | Seata Saga |
| **本地消息表** | 本地事务 + 消息表 + 定时重试 | 最终一致 | 高 | 低 | RocketMQ 事务消息 |
| **AT 模式** | 自动回滚 Undo Log | 最终一致 | 高 | 低 | Seata AT |
| **可靠消息** | 消息可靠投递 + 消费确认 | 最终一致 | 高 | 中 | RocketMQ |

### 6.2 Seata 三种模式

```text
AT 模式（推荐）：
  → 一阶段：执行 SQL + 记录 Undo Log
  → 二阶段-提交：删除 Undo Log
  → 二阶段-回滚：根据 Undo Log 反向补偿
  → 优点：无业务侵入，自动回滚
  → 缺点：依赖数据库的 ACID

TCC 模式：
  → Try：资源预留
  → Confirm：确认执行
  → Cancel：释放资源
  → 优点：不依赖数据库
  → 缺点：需手动实现每个方法，侵入性强

Saga 模式：
  → 正向链：A → B → C（每个步骤有对应补偿操作）
  → 失败回滚：C补偿 → B补偿 → A补偿
  → 优点：长事务场景
  → 缺点：补偿设计复杂
```

## 7. 分布式协调

### 7.1 分布式锁

```java
// Redis 分布式锁（Redisson）
RLock lock = redisson.getLock("order:lock:123");
try {
    if (lock.tryLock(10, 30, TimeUnit.SECONDS)) {
        // 执行业务
        doSomething();
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}

// ZooKeeper 分布式锁（Curator）
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order");
lock.acquire();
try {
    doSomething();
} finally {
    lock.release();
}
```

### 7.2 Redis 锁 vs ZK 锁

| 维度 | Redis (Redisson) | ZooKeeper (Curator) |
|------|:--------------:|:-----------------:|
| **实现** | Lua 脚本 + 看门狗续期 | 临时顺序节点 + Watch |
| **性能** | 高 | 中等 |
| **可靠性** | RedLock 提升，非绝对可靠 | CP 保证，更可靠 |
| **阻塞** | 自旋重试 | Watch 监听，不耗 CPU |
| **适合** | 高性能、可接受极小概率失效 | 强一致性要求 |

### 7.3 分布式 ID

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **UUID** | 随机生成 128bit | 简单，无依赖 | 无序，B+Tree 不友好 |
| **雪花算法（Snowflake）** | 时间戳+机器ID+序列号 | 有序递增，本地生成 | 时钟回拨问题 |
| **数据库自增** | AUTO_INCREMENT | 严格递增 | 单点瓶颈 |
| **号段模式（Leaf）** | 批量预分配号段 | 高性能 | 需额外服务 |
| **Redis 自增** | INCR 命令 | 简单 | 需持久化 |
| **美团 Leaf** | 号段 + 雪花双模式 | 企业级 | 需部署服务 |

```text
雪花算法 64bit 组成：
  [1bit 不用][41bit 毫秒时间戳][10bit 机器ID][12bit 序列号]

  → 41bit 时间戳可用 69 年
  → 每毫秒每台机器可生成 4096 个 ID
  → 整体趋势递增（非严格递增，有时钟回拨风险）
```
