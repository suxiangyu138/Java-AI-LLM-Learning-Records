## 1. 性能指标体系

### 1.1 核心指标

| 指标 | 英文 | 说明 | 好/坏标准 |
|------|------|------|---------|
| **吞吐量** | Throughput / QPS / TPS | 单位时间处理请求数 | 越高越好 |
| **响应时间** | Response Time / Latency | 请求返回的时间 | 越低越好 |
| **P50/P90/P95/P99** | Percentile | 百分位延迟 | P99 < 目标值 |
| **并发数** | Concurrency | 同时处理的请求数 | - |
| **错误率** | Error Rate | 错误响应占比 | < 0.1% |
| **资源利用率** | CPU/Memory/Disk/Network | 系统资源使用率 | 70-80% 是合理区间 |

### 1.2 P99 为什么比平均值重要

```text
假设 100 个请求的响应时间（ms）：
  [10, 10, 10, ..., 10, 5000]  ← 99个10ms + 1个5s

  平均值 = (99×10 + 5000)/100 = 59.9ms ← 看起来还行？
  P99 = 5000ms                       ← 但 1% 的用户等了 5秒！

  → 平均值掩盖了长尾延迟
  → P99/P999 才能真正反映用户体验
  → 互联网服务通常要求 P99 < 200ms
```

## 2. 压测工具与方法论

### 2.1 常用压测工具

| 工具 | 优势 | 语言 | 适用场景 |
|------|------|:--:|---------|
| **JMeter** | GUI + 插件丰富、分布式压测 | Java | 全链路压测、复杂场景 |
| **wrk / wrk2** | 极高并发、Lua 脚本扩展 | C | API 简单压测 |
| **ab** (ApacheBench) | 极简、随 Apache 自带 | C | 快速验证 |
| **Locust** | Python 脚本定义场景、Web UI | Python | 复杂业务流程 |
| **K6** (Grafana) | 云原生、JavaScript、CI 集成 | Go | 开发者友好 |
| **阿里云 PTS** | 云端压测、地理分布 | SaaS | 大流量模拟 |

### 2.2 压测方法论

```text
压测流程：

  1. 明确目标
     → 验证新接口的 QPS 上限？
     → 验证系统在高并发下的稳定性？
     → 找出瓶颈点？

  2. 设计场景
     → 基准测试：单个接口，确定基线
     → 负载测试：逐步增加并发，找拐点
     → 压力测试：超过预期负载，找极限
     → 稳定性测试：恒定负载长时间运行，看内存泄漏、GC 频率
     → 混合场景：模拟真实流量比例

  3. 环境准备
     → 压测环境与生产隔离
     → 数据量级与生产一致
     → 预热 JIT、缓存

  4. 执行 + 监控
     → CPU、内存、GC、线程 → JVM 层面
     → QPS、延迟、错误率 → 应用层面
     → 连接池、慢查询 → 中间件层面

  5. 分析 + 优化 → 再验证
```

## 3. JVM 调优实战

### 3.1 调优流程

```text
JVM 调优黄金流程：

  dump 分析 → 参数调整 → 压测验证 → 监控对比

调优目标优先级：
  1. 稳定性（不 OOM、不频繁 Full GC）
  2. 响应时间（P99 延迟）
  3. 吞吐量（QPS）
```

### 3.2 常见问题与方案

| 问题 | 现象 | 排查 | 解决 |
|------|------|------|------|
| **OOM: Heap** | 应用崩溃，heap dump | MAT 分析 dominator tree | 查内存泄漏 / 增大 -Xmx |
| **频繁 Full GC** | GC 日志 Full GC 间隔短 | jstat -gc PID | 调大老年代 / 调优晋升 |
| **YGC 时间长** | 单次 Young GC > 50ms | GC 日志分析 | 减小新生代 / 减少存活对象 |
| **线程数暴涨** | 线程数持续上升 | jstack | 检查线程池配置 / 资源泄漏 |
| **CPU 100%** | 持续满载 | top -Hp + jstack | 死循环 / 大量 GC / 序列化 |
| **接口响应慢** | P99 > 500ms | Arthas trace | SQL 慢查询 / 远程调用慢 / 锁竞争 |

### 3.3 内存泄漏排查

```bash
# 1. dump 堆内存
jmap -dump:live,file=heap.hprof PID

# 2. MAT / JProfiler 分析
# → 查看 Dominator Tree（支配树）
# → 查找占用最高的对象
# → 查看 Path to GC Roots：谁在持有它

# 3. 常见内存泄漏场景
# → ThreadLocal 未 remove（线程池复用）
# → 静态集合不断 add
# → 连接未关闭（数据库、HTTP、Redis）
# → 监听器未注销
# → 内部类持有外部引用（匿名类、Lambda）
```

### 3.4 推荐 JVM 参数（微服务 2C4G）

```bash
java -jar app.jar \
  -Xms2g -Xmx2g \              # 堆 2G（Xms=Xmx 避免动态调整）
  -Xmn1g \                     # 新生代 1G
  -XX:MetaspaceSize=256m \     # 元空间
  -XX:MaxMetaspaceSize=512m \
  -XX:+UseG1GC \               # G1 收集器
  -XX:MaxGCPauseMillis=200 \   # 目标暂停时间 200ms
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/logs/heap.hprof \
  -XX:+PrintGCDetails \
  -Xlog:gc*:file=/logs/gc.log:time,level,tags
```

## 4. SQL 性能优化

### 4.1 慢查询排查流程

```text
慢查询排查六步法：

  1. 开启慢查询日志
     SET GLOBAL slow_query_log = ON;
     SET GLOBAL long_query_time = 1;  -- 超过1秒记录

  2. 定位慢 SQL
     → mysqldumpslow 分析慢日志
     → 或通过监控（Prometheus MySQL Exporter）

  3. EXPLAIN 分析执行计划
     → type 是否 ALL/INDEX？（需要优化到 range 以上）
     → rows 扫描行数是否过大？
     → Extra 是否有 Using filesort/Using temporary？

  4. 检查索引
     → WHERE 条件列是否有索引？
     → 联合索引是否符合最左前缀？
     → 是否可以用覆盖索引避免回表？

  5. 优化 SQL
     → 避免 SELECT *
     → 避免大分页 LIMIT 浅
     → 避免 OR 条件（改用 UNION ALL）
     → 避免函数操作索引列

  6. 优化表结构
     → 垂直拆分（冷热分离）
     → 历史数据归档
```

### 4.2 索引优化速查

```sql
-- 如何看一个 SQL 是否用了索引？
EXPLAIN SELECT ...;

-- type 字段从好到坏排序：
-- system > const > eq_ref > ref > range > index > ALL
--                                        ↑ 至少要到这！

-- 覆盖索引：不需要回表
-- Extra 出现 Using index → 好！
CREATE INDEX idx_cover ON orders(user_id, status, create_time);
SELECT user_id, status, create_time FROM orders WHERE user_id = 123;
-- → 查询列全部在索引中，无需回表

-- 索引下推（MySQL 5.6+）：在索引遍历时就过滤
-- Extra 出现 Using index condition
SELECT * FROM users WHERE name LIKE '张%' AND age = 25;
```

## 5. 缓存优化策略

### 5.1 多级缓存架构

```text
┌──────────────────────────────────────────┐
│  请求 → CDN（边缘缓存，静态资源）        │
│         ↓ miss                           │
│        Nginx 本地缓存（热点页面/API）     │
│         ↓ miss                           │
│        Redis 分布式缓存（核心缓存层）     │
│         ↓ miss                           │
│        本地缓存 Caffeine（极致热点）      │
│         ↓ miss                           │
│        MySQL（数据库层）                  │
└──────────────────────────────────────────┘
```

### 5.2 缓存更新策略

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **Cache Aside** | 读：先缓存，miss 再 DB；写：先 DB，再删缓存 | 简单 | 可能短暂不一致 |
| **Read/Write Through** | 缓存层负责同步 DB | 业务代码简单 | 需额外组件 |
| **Write Behind** | 异步批量写 DB | 高吞吐 | 数据丢失风险 |

```java
// Cache Aside 模式（最常用）
public User getById(Long id) {
    // 1. 查缓存
    User user = redisTemplate.opsForValue().get("user:" + id);
    if (user != null) return user;

    // 2. 缓存 miss → 查数据库 + 加互斥锁（防击穿）
    String lockKey = "lock:user:" + id;
    try {
        if (redisTemplate.opsForValue().setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS)) {
            user = userMapper.selectById(id);
            // 3. 存缓存 + 随机过期时间（防雪崩）
            int ttl = 3600 + ThreadLocalRandom.current().nextInt(600);
            redisTemplate.opsForValue().set("user:" + id, user, ttl, TimeUnit.SECONDS);
        } else {
            Thread.sleep(50);  // 等待锁持有者加载完成
            return getById(id); // 重试
        }
    } finally {
        redisTemplate.delete(lockKey);
    }
    return user;
}
```

### 5.3 缓存一致性

```text
确保 Redis 与 DB 一致性的常用方案：

  1. Cache Aside + 延迟双删
     先删缓存 → 更新 DB → 延迟 N ms → 再删缓存
     （适用于读多写少）

  2. Canal + MQ 异步更新
     MySQL Binlog → Canal → MQ → 消费者更新 Redis
     （准实时，解耦）

  3. 设置合理过期时间
     TTL 作为最终兜底，保证最终一致性
```

## 6. 全链路性能排查思路

### 6.1 四层排查法

```text
┌──────────────────────────────────────────────────┐
│ 第一层：资源层                                    │
│ → CPU / Memory / Disk / Network / FD (文件描述符) │
│ → top, vmstat, iostat, netstat, lsof              │
├──────────────────────────────────────────────────┤
│ 第二层：JVM 层                                    │
│ → 堆/非堆内存、GC、线程、类加载                    │
│ → jstat, jstack, jmap, Arthas                     │
├──────────────────────────────────────────────────┤
│ 第三层：中间件层                                   │
│ → 连接池、慢查询、MQ 积压、Redis 慢命令            │
│ → 各自的管理后台/命令行                            │
├──────────────────────────────────────────────────┤
│ 第四层：应用层                                     │
│ → 业务日志、链路追踪、代码逻辑、锁竞争              │
│ → SkyWalking, Arthas trace/watch                  │
└──────────────────────────────────────────────────┘
```

### 6.2 性能排查速查表

| 症状 | 先看什么 | 工具 |
|------|---------|------|
| 接口整体慢 | 链路追踪 → 找最慢的 Span | SkyWalking / Zipkin |
| CPU 高 | 哪个线程 → 在做什么 | top -Hp + jstack + Arthas |
| 内存高 | 哪个对象 → GC Roots | jmap + MAT |
| 频繁 GC | GC 日志 → 各区域大小 + 晋升速率 | GCViewer / GC Easy |
| 线程数多 | 线程状态分布 → 死锁/等待/阻塞 | jstack / Arthas thread -b |
| SQL 慢 | 慢查询日志 → EXPLAIN | SkyWalking / 数据库监控 |
| Redis 慢 | 慢命令日志 | `SLOWLOG GET 10` |
| 网络延迟 | DNS 解析、网络往返 | `dig`, `traceroute`, `ping` |

### 6.3 一句话总结

> 🎯 性能调优的本质是 **测量、定位、优化、验证** 的循环。永远先用数据说话（压测 + 监控），定位瓶颈所在层（资源/JVM/中间件/应用），再做针对性优化。**不要凭直觉优化，迷信调参而忽视架构设计。**
