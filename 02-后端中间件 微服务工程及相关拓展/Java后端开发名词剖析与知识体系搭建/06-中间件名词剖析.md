## 1. Redis 缓存中间件

### 1.1 五种基础数据结构

| 类型 | 底层实现 | 常用命令 | 典型场景 |
|------|---------|---------|---------|
| **String** | SDS (简单动态字符串) | GET/SET/INCR | 缓存对象(JSON)、计数器、分布式锁 |
| **Hash** | HashTable / ZipList | HSET/HGET/HGETALL | 对象属性缓存、购物车 |
| **List** | QuickList (LinkedList+ZipList) | LPUSH/RPUSH/LRANGE | 消息队列、时间线 |
| **Set** | HashTable / IntSet | SADD/SMEMBERS/SINTER | 标签、共同好友、去重 |
| **ZSet** | SkipList + HashTable | ZADD/ZRANGE/ZREVRANK | 排行榜、延迟队列 |

### 1.2 高级数据结构

| 结构 | 说明 | 场景 |
|------|------|------|
| **HyperLogLog** | 基数统计(误差 0.81%) | UV 统计 |
| **Bloom Filter** | 判断元素是否存在(可能误判) | 缓存穿透防护 |
| **BitMap** | 位图操作 | 签到统计 |
| **Geo** | 地理坐标 | 附近的人 |
| **Stream** | 消息流(5.0+) | 轻量 MQ |

### 1.3 缓存三大问题

```text
缓存穿透：
  请求数据既不在缓存也不在数据库（如 id=-1）
  → 解决：
    1. 布隆过滤器拦截不存在的 key
    2. 缓存空值（null），设置短过期时间

缓存击穿：
  热点 key 过期瞬间，大量请求打到数据库
  → 解决：
    1. 互斥锁：一个线程去 DB 加载，其余等待
    2. 热点 key 永不过期 + 逻辑过期（value 中存过期时间）

缓存雪崩：
  大量 key 同时过期，或 Redis 宕机
  → 解决：
    1. TTL 加随机值（避免同时过期）
    2. Redis 集群/哨兵（高可用）
    3. 多级缓存（本地缓存 Caffeine + Redis）
```

### 1.4 过期策略与淘汰策略

```text
过期删除策略：
  → 惰性删除：访问 key 时检查是否过期
  → 定期删除：每隔 100ms 随机抽取一批 key 检查
  → Redis 采用两者结合！

内存淘汰策略（maxmemory-policy）：
  noeviction：      不淘汰，写请求报错（默认）
  allkeys-lru：     所有 key 中 LRU 淘汰
  allkeys-lfu：     所有 key 中 LFU 淘汰
  volatile-lru：    设了过期时间的 key 中 LRU 淘汰
  volatile-lfu：    设了过期时间的 key 中 LFU 淘汰
  allkeys-random：  随机淘汰
  volatile-random： 设了过期时间的随机淘汰
  volatile-ttl：    即将过期的优先淘汰

推荐：allkeys-lru（最常用）
```

### 1.5 持久化

| 方式 | RDB (快照) | AOF (追加日志) |
|------|-----------|---------------|
| **原理** | 定时全量快照 → dump.rdb | 每个写操作追加 → appendonly.aof |
| **恢复速度** | 快 | 慢（重放所有命令） |
| **数据安全** | 可能丢失最后一次快照后的数据 | 最多丢 1 秒（everysec） |
| **文件大小** | 小（压缩） | 大（需 rewrite） |
| **推荐** | 主从复制用 RDB | 数据安全优先用 AOF |

> 💡 生产环境推荐 **RDB + AOF 混合持久化**（Redis 4.0+）

### 1.6 高可用架构

```text
主从复制（Replication）：
  1 主 N 从，主写从读
  → 问题：主宕机需手动切换

哨兵模式（Sentinel）：
  → 监控主节点 + 自动故障转移
  → 至少 3 个 Sentinal 节点（避免脑裂）
  → Quorum：判定主观下线的票数

集群模式（Cluster）：
  → 数据分片（16384 个槽位，CRC16(key) % 16384）
  → 每个分片 = 主 + 从
  → 去中心化，Gossip 协议通信
  → 不支持跨 slot 的事务/mget
```

## 2. 消息队列 MQ

### 2.1 三大 MQ 对比

| 维度 | Kafka | RocketMQ | RabbitMQ |
|------|:-----:|:--------:|:--------:|
| **语言** | Java/Scala | Java | Erlang |
| **吞吐量** | 极高（百万 TPS） | 高（十万 TPS） | 中等（万 TPS） |
| **延迟** | 毫秒级 | 毫秒级 | 微秒级 |
| **消息可靠性** | 高（分区副本） | 高（同步刷盘） | 高 |
| **事务消息** | ✅ | ✅ 原生支持 | ❌ 需补偿 |
| **顺序消费** | 分区内有序 | 队列内有序 | 队列内有序 |
| **延时消息** | ❌ | ✅ 18个级别 | ✅ 插件 |
| **适用场景** | 大数据、日志、流计算 | 业务解耦、分布式事务 | 低延迟、复杂路由 |

### 2.2 Kafka 核心概念

```text
┌────────────────────────────────────────┐
│              Kafka 架构                 │
├────────────────────────────────────────┤
│                                        │
│  Producer → Topic → Partition → Broker │
│                ↓                       │
│         Consumer Group                 │
│                                        │
│  核心概念：                             │
│  Broker：     Kafka 服务节点            │
│  Topic：      逻辑消息分类              │
│  Partition：  Topic 的物理分片          │
│  Replica：    分区副本（Leader+Follower）│
│  Offset：     消息在分区中的唯一序号     │
│  Consumer Group：消费者组，组内协作消费  │
│  ISR：        In-Sync Replicas（同步副本集）│
│  HW：         High Watermark（已提交位置）│
│  LEO：        Log End Offset（日志末端） │
│                                        │
└────────────────────────────────────────┘
```

### 2.3 消息可靠投递

```text
生产端可靠性：
  → acks=all：Leader + 所有 ISR 副本写入成功才返回
  → retries=MAX：失败无限重试
  → max.in.flight.requests.per.connection=1：严格有序

Broker 端可靠性：
  → replication.factor=3：至少 3 副本
  → min.insync.replicas=2：最少同步副本数
  → unclean.leader.election.enable=false：不允许落后太多的副本当 Leader

消费端可靠性：
  → enable.auto.commit=false：关闭自动提交
  → 业务处理完成后手动 commitSync()
  → 幂等处理（数据库唯一键 / Redis 去重）
```

### 2.4 重复消费与顺序消费

```text
重复消费原因：
  → 生产端：网络超时重试 → 同一条消息发了两次
  → 消费端：消息处理完但 offset 提交失败 → 重启后重复消费

幂等方案：
  1. 数据库唯一键（INSERT IGNORE）
  2. Redis 记录消费过的消息 ID（SETNX）
  3. 前置状态判断（如订单已支付 → 跳过）

顺序消费：
  Kafka：同一 partition 内保证有序
    → 相同 key 的消息进同一分区
    → partition 内有多个消费者 → 失去有序性！
  RocketMQ：同一 MessageQueue 内有序
  RabbitMQ：同一 Queue 内有序（单消费者）
```

## 3. Elasticsearch 搜索引擎

### 3.1 核心概念

| 概念 | 对应关系 | 说明 |
|------|---------|------|
| **Index (索引)** | ≈ MySQL Database | 文档的集合 |
| **Type** | - | ES 7.x 移除，8.x 完全废弃 |
| **Document** | ≈ MySQL Row | JSON 文档，最小数据单元 |
| **Field** | ≈ MySQL Column | 文档中的字段 |
| **Mapping** | ≈ Schema | 定义字段类型和索引规则 |
| **Shard** | - | 索引分片（水平扩展） |
| **Replica** | - | 分片副本（高可用） |
| **Node** | - | ES 实例 |

### 3.2 倒排索引

```text
倒排索引 = 搜索引擎的核心！

传统正向索引：
  文档 → 包含哪些词语
  Doc1: "Java is great"
  Doc2: "Python is great"

倒排索引：
  词语 → 在哪些文档中出现
  "Java"   → [Doc1]
  "Python" → [Doc2]
  "is"     → [Doc1, Doc2]
  "great"  → [Doc1, Doc2]

为什么快？
  → 用户搜索 "Java" → 直接定位到词条 → 返回 Doc1
  → O(1) 查找，不需要扫描所有文档！
```

### 3.3 ES 查询类型

```json
// 全文搜索
{ "match": { "title": "Java Spring Boot" } }

// 精确匹配（不分词）
{ "term": { "status": "published" } }

// 多字段搜索
{ "multi_match": {
    "query": "分布式事务",
    "fields": ["title^3", "content"]
}}

// 范围查询
{ "range": { "price": { "gte": 100, "lte": 500 } } }

// Bool 组合查询
{ "bool": {
    "must":     [{ "match": { "title": "Java" } }],
    "must_not": [{ "term": { "status": "deleted" } }],
    "should":   [{ "match": { "tags": "spring" } }],
    "filter":   [{ "range": { "price": { "gte": 100 } } }]
}}
```

## 4. Nginx 反向代理

### 4.1 核心概念

| 概念 | 说明 |
|------|------|
| **正向代理** | 代理客户端，客户端知道目标服务器（VPN） |
| **反向代理** | 代理服务端，客户端不知道真正的服务器 |
| **负载均衡** | 将请求分发到多个后端服务器 |
| **动静分离** | 静态资源由 Nginx 返回，动态请求转发 Tomcat |
| **虚拟主机** | 一台服务器运行多个网站（不同域名） |

### 4.2 负载均衡算法

| 算法 | 指令 | 说明 |
|------|------|------|
| **轮询** | 默认 | 逐个分配 |
| **加权轮询** | `weight=N` | 按权重分配 |
| **IP Hash** | `ip_hash` | 同 IP 固定到同一服务器（Session 保持） |
| **最少连接** | `least_conn` | 分到连接最少的服务器 |
| **URL Hash** | `hash $request_uri` | 相同 URL 到同一服务器（缓存命中） |
| **Fair** | `fair` (第三方) | 按响应时间分配 |

```nginx
upstream backend {
    # 加权轮询
    server 192.168.1.10:8080 weight=3;
    server 192.168.1.11:8080 weight=1;
    server 192.168.1.12:8080 backup;  # 备份服务器
}

server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

## 5. ZooKeeper 协调服务

### 5.1 核心概念

```text
ZooKeeper 数据模型：类似文件系统的树形结构
  /
  ├── /config
  │   └── /config/app1  (data=...)
  ├── /services
  │   ├── /services/user-service  (临时节点)
  │   └── /services/order-service (临时节点)
  └── /locks
      └── /locks/order-123

节点类型：
  PERSISTENT           → 持久节点（显式删除才消失）
  PERSISTENT_SEQUENTIAL → 持久顺序节点（自动递增后缀）
  EPHEMERAL            → 临时节点（客户端断开自动删除）
  EPHEMERAL_SEQUENTIAL → 临时顺序节点

监听机制 Watcher：
  → 客户端对节点注册 Watcher → 节点变更触发通知
  → 一次性触发（触发后需重新注册）
```

### 5.2 ZK 典型应用

| 应用 | 实现方式 |
|------|---------|
| **配置管理** | PERSISTENT 节点存储配置 + Watcher 监听变更 |
| **服务发现** | EPHEMERAL 注册服务 + 父节点 Watcher 感知上下线 |
| **分布式锁** | EPHEMERAL_SEQUENTIAL 节点，序号最小获取锁 |
| **Master 选举** | EPHEMERAL_SEQUENTIAL 节点，序号最小当选 Master |
| **分布式队列** | PERSISTENT_SEQUENTIAL 节点，按序消费 |
