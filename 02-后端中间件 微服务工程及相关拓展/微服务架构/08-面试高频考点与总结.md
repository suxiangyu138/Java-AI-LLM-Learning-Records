## 1. 面试高频题与答题框架

### 1.1 概念与拆分类

**Q1：什么是微服务？什么场景才适合用？**

```text
① 定义：按业务能力拆分的独立服务（独立部署/扩展/库）
② 特征：业务域拆分/独立部署/独立库/故障隔离
③ 适用三大痛点：大团队并行/高流量弹性/独立演进
④ 不适用：<10 人团队/简单系统（单体更高效）
⑤ 金句：为解决问题而拆，不为架构而拆
⑥ 加分：模块化单体起步，痛点驱动拆分
```

**Q2：微服务怎么拆分？依据是什么？**

```text
① 依据：DDD 限界上下文（业务域）——不是技术层
② 顺序：先核心域（订单/支付）→ 非核心逐步
③ 粒度：宁粗勿细（5-8 个）；调用链 >3 跳 = 太细
④ 通信：核心同步、非核心异步
⑤ 数据：独立库（先逻辑拆后物理拆）
⑥ 金句：边界 = 模型的归属——每个领域有自己的语言
```

**Q3：单体 vs 微服务的取舍？**

```text
① 单体优势：简单/高效/易调试/低成本
② 微服务优势：并行开发/独立部署/按需扩展
③ 微服务代价：分布式难题/运维复杂/团队要求
④ 演进：模块化单体 → 痛点出现 → 逐步拆
⑤ 金句：微服务的价值在边界清晰——不在服务多
```

### 1.2 通信与注册类

**Q4：服务间通信方式？**

```text
① 同步：OpenFeign（HTTP——Spring 标准）/Dubbo（RPC 高性能）
② 异步：RocketMQ/Kafka（解耦削峰）
③ 决策：核心链路同步、非核心异步
④ 铁律：写操作幂等（重试前提）
⑤ 金句：Feign 同步 + MQ 异步 = Java 微服务通信标配
```

**Q5：超时链路怎么设计？**

```text
① 网关 > 下游所有服务超时最大值（防提前截断）
② A→B→C：A 超时 > B 超时 + B→C 耗时
③ 每跳留余量：调用方 = 被调方 + 传输余量
④ 三层：连接超时/读取超时/总超时
⑤ 金句：超时 = 防线程无限等待的保险丝
```

**Q6：Nacos 的 AP/CP 怎么选？**

```text
① AP：可用性优先（分区仍可用）——微服务默认
② CP：一致性优先（分区拒绝写）——强一致场景
③ 微服务场景：临时实例 + AP（可用性优先）
④ 心跳铁律：timeout ≥ 3 × interval（防假死）
⑤ 金句：微服务注册默认 AP——可用性 > 一致性
```

**Q7：Nacos 三级隔离是什么？**

```text
① Namespace：环境隔离（dev/prod 物理隔离）
② Group：业务域隔离（支付/订单独立）
③ DataId：具体配置（服务名+环境+扩展名）
④ 价值：防环境混乱 + 权限控制 + 业务隔离
⑤ 金句：环境 × 业务 × 配置的三维管控
```

### 1.3 网关类

**Q8：网关的职责是什么？**

```text
① 四职责：路由/鉴权/限流/日志
② 不做：业务逻辑/权限细节/数据存储
③ 鉴权边界：网关认证（你是谁）、服务授权（能做什么）
④ 超时铁律：网关 > 下游最大
⑤ 金句：网关管入口治理——业务语义留给服务
```

**Q9：Gateway 和 Zuul 的区别？**

```text
① Gateway：WebFlux 响应式非阻塞（吞吐 1.5 倍）
② Zuul：Servlet 阻塞（过时）
③ Gateway 特性：Sentinel 集成/WebSocket/长连接
④ 2026：Spring Cloud 官方标准
⑤ 注意：Gateway 是 WebFlux（无 Tomcat）
```

### 1.4 治理类

**Q10：什么是雪崩？三道防线是什么？**

```text
① 雪崩：超时等待 → 线程耗尽 → 级联放大
② 限流：入口保护（防打垮）——QPS/热点
③ 熔断：依赖保护（防拖垮）——慢调用/异常比例
④ 降级：业务兜底（保可用）——默认值/缓存
⑤ 金句：限流防进来太多、熔断防等太久、降级保还能用
```

**Q11：Sentinel 的熔断策略有哪些？**

```text
① 慢调用比例：RT 超阈值比例 > 阈值熔断
② 异常比例：异常数/总数 > 阈值
③ 异常数：固定时间内异常数超限
④ 半开恢复：熔断窗口后试探
⑤ 规则持久化：Nacos（内存规则重启丢失！）
⑥ 金句：熔断 = 快速失败——不让请求等必挂的服务
```

**Q12：降级有什么讲究？**

```text
① 查询类：返回保守默认值（缓存兜底）
② 写操作：不能降级（扣库存降级 = 超卖）
③ 非核心：直接跳过/进 MQ
④ 实现：Feign fallbackFactory
⑤ 金句：读可降级、写不降级——数据正确性是底线
```

### 1.5 分布式事务类

**Q13：分布式事务有哪些方案？**

```text
① Seata AT：自动回滚 SQL（侵入最小——首选）
② 事务消息：本地事务 + 消息原子化（异步）
③ TCC：Try/Confirm/Cancel（强一致——侵入大）
④ Saga：正向 + 反向补偿（长流程）
⑤ 选择：常规 AT、异步事务消息、金融 TCC
⑥ 金句：先选最终一致——强一致只在必须时
```

**Q14：Seata AT 模式原理？**

```text
① 角色：TC（协调者）/TM（管理器）/RM（资源管理器）
② 流程：业务前记 before 镜像 → 执行 → 记 after 镜像
③ 回滚：失败生成反向 SQL（UNDO_LOG）
④ 使用：@GlobalTransactional 注解
⑤ 注意：全局锁（写冲突等待）
⑥ 金句：AT = 注解开启 + 自动回滚
```

**Q15：事务消息怎么保证一致性？**

```text
① 半消息：Broker 暂存（不可见）
② 本地事务：执行后提交/回滚半消息
③ 回查：超时未确认 → Broker 询问本地事务状态
④ 保证：本地事务成功 = 消息必达（原子性）
⑤ 消费幂等：重复投递处理
⑥ 金句：事务消息 = 本地事务与消息发送的原子化
```

### 1.6 可观测与演进类

**Q16：可观测性三支柱是什么？**

```text
① 指标：系统怎么样（Prometheus + Grafana）
② 日志：发生了什么（ELK/Loki）
③ 链路：请求经历了什么（Zipkin/Jaeger）
④ 串联：traceId 关联日志与链路
⑤ 金句：指标告警、日志细节、链路路径
```

**Q17：Spring Cloud 和 K8s 怎么协同？**

```text
① K8s 管基础设施：服务发现/部署/ConfigMap/探针
② Spring Cloud 管业务语义：网关/动态配置/熔断
③ 黄金法则：不重复造轮子
④ 双层网关：Ingress（TLS）+ Gateway（业务路由）
⑤ 金句：K8s 擅长的事别重复做
```

**Q18：服务网格是什么？怎么演进？**

```text
① 定义：sidecar（Envoy）接管治理——无侵入
② 能力：路由/熔断/mTLS/故障注入
③ 渐进迁移：保留注册中心 → K8s DNS → 路由 → 熔断
④ 对比 Spring Cloud：代码内治理 vs 基础设施治理
⑤ 金句：治理下沉 + 无侵入 = 云原生演进方向
```

## 2. 速查表

```text
技术栈（2026）：
├── 注册/配置：Nacos 2.x（AP 默认/三级隔离）
├── 网关：Spring Cloud Gateway（WebFlux）
├── 调用：OpenFeign + LoadBalancer
├── 治理：Sentinel（流控/熔断/持久化 Nacos）
├── 事务：Seata AT / 事务消息（RocketMQ）
├── 观测：Micrometer + Prometheus + Zipkin
└── 演进：K8s 协同 → 服务网格（ASM/Istio）

铁律：
├── 超时：网关 > 下游最大；A > B + B→C
├── 幂等：写操作必幂等（重试前提）
├── 降级：读默认值、写抛异常
├── 规则持久化：Sentinel → Nacos（重启不丢）
├── 心跳：timeout ≥ 3 × interval
└── 一致性：先最终一致，强一致只在必须

拆分：
├── DDD 限界上下文（业务域）
├── 粒度宁粗勿细（5-8 服务）
└── 痛点驱动（不是银弹）
```

## 3. 五大常见误区

| # | 误区 | 真相 |
|---|------|------|
| 1 | 「微服务一定比单体好」 | <10 人团队单体更高效——痛点驱动 |
| 2 | 「服务拆得越细越好」 | 粒度宁粗勿细——调用链 >3 跳 = 灾难 |
| 3 | 「Sentinel 规则配好就行」 | 内存规则重启丢失——必须持久化 Nacos |
| 4 | 「降级就是返回 null」 | 写操作不能降级（超卖）——按业务定制 |
| 5 | 「K8s 有了 Spring Cloud 可以丢」 | 分工：K8s 基础设施、Spring Cloud 业务语义 |

## 4. 一句话总结全系列

```text
01 拆分：DDD 边界 + 粒度宁粗勿细 + 微服务不是银弹
02 通信：Feign 同步 + MQ 异步 + 超时/幂等/降级
03 注册：Nacos AP 默认 + 三级隔离 + 心跳铁律
04 网关：Gateway（WebFlux）+ 四职责 + 超时铁律
05 治理：三道防线（限流/熔断/降级）+ 规则持久化
06 事务：AT 首选 + 事务消息 + 最终一致优先
07 观测：三支柱 + K8s 协同 + 服务网格演进
08 面试：18 题框架 + 速查 + 避坑
```

> 🎯 **系列总结**：微服务能力 = **边界（DDD 拆分）× 治理（注册/网关/熔断/事务）× 可观测（三支柱）× 演进（K8s/网格）** 四维体系。2026 年核心共识：**微服务不是更多组件，而是边界划分 + 职责协同**——Spring Cloud 管业务语义、Kubernetes 管基础设施，可观测与弹性（熔断/限流/超时/降级）是分布式系统稳定性的四根支柱。
