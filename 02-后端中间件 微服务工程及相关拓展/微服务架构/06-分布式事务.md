## 1. 为什么需要分布式事务

> **背景**：微服务「独立数据库」——一个业务跨多个服务/库时，本地事务无法保证跨库一致性。
> **目的**：理解分布式事务的困境与场景。
> **适用范围**：跨服务的数据一致性场景。

```text
单体 vs 微服务的事务
├── 单体：一个库 → 本地事务（ACID 完整）
├── 微服务：每个服务独立库 →
│   ├── 下单（订单库）→ 扣库存（库存库）→ 扣余额（账户库）
│   └── 中间失败 → 部分成功部分失败（不一致！）
└── 金句：拆库是微服务的必然——分布式一致性是拆库的代价

经典场景（下单链路）
├── ① 订单服务：创建订单（订单库）
├── ② 库存服务：扣减库存（库存库）
├── ③ 账户服务：扣减余额（账户库）
└── 任一步失败 → 需回滚其他（分布式事务）
```

## 2. 一致性模型选择

> 🎯 **2026 共识：优先最终一致性而非强一致**——按业务场景选模型：

```text
一致性模型
├── ① 强一致（即时一致）：
│   ├── 所有节点立即一致
│   ├── 代价：性能 + 可用性（阻塞）
│   └── 场景：支付/资金（金融核心）
├── ② 最终一致（收敛一致）：
│   ├── 短暂不一致 → 最终一致
│   ├── 代价：需要补偿/对账
│   └── 场景：订单-库存（电商常规）
└── ③ 弱一致：
    ├── 不保证何时一致
    └── 场景：通知/日志

选型原则
├── 支付/资金 → 强一致（必须）
├── 订单-库存 → 最终一致（可接受）
├── 通知/积分 → 最终一致/弱一致
└── 金句：一致性强度 = 业务风险决定（不是技术偏好）
```

## 3. 分布式事务方案全景

| 方案 | 一致性 | 业务侵入 | 性能 | 适用 |
|------|:---:|:---:|:---:|------|
| **Seata AT** | 最终一致 | **低（注解）** | 中 | 常规（首选） |
| **事务消息** | 最终一致 | 低 | 高 | 异步链路 |
| **TCC** | 强一致 | 高（三方法） | 高 | 金融强一致 |
| **Saga** | 最终一致 | 中（补偿） | 高 | 长流程 |
| **2PC** | 强一致 | 中 | 低 | 少用（阻塞） |

```text
方案本质
├── ① Seata AT：自动生成回滚 SQL（对业务透明）
├── ② 事务消息：本地事务 + 消息发送原子化
├── ③ TCC：Try-Confirm-Cancel（业务三方法）
├── ④ Saga：正向流程 + 反向补偿
└── ⑤ 2PC：两阶段提交（协调者阻塞——性能差）
→ 金句：AT 最常用（侵入小）、TCC 最强一致（侵入大）
```

## 4. Seata AT 模式

### 4.1 原理

> **背景**：Seata（阿里开源）AT 模式是 2026 国内分布式事务首选——自动生成回滚 SQL，业务侵入最小。

```text
AT 模式角色
├── ① TC（事务协调者）：全局事务管理
├── ② TM（事务管理器）：开启/提交/回滚全局事务
├── ③ RM（资源管理器）：本地事务 + 分支注册
└── ④ 原理：
    ├── ① 业务 SQL 前：记录快照（before image）
    ├── ② 执行业务 SQL
    ├── ③ 记录快照（after image）
    ├── ④ 提交全局事务
    └── ⑤ 失败 → 根据镜像生成回滚 SQL（UNDO_LOG）
```

### 4.2 使用

```java
// ① 开启全局事务（业务方法加注解）
@Service
public class OrderService {
    @GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
    public OrderResult createOrder(CreateOrderCommand command) {
        // ① 创建订单（本地事务）
        orderDao.insert(order);

        // ② 扣库存（远程调用——参与全局事务）
        stockClient.deductStock(command.getSkuId(), command.getQuantity());

        // ③ 扣余额（远程调用）
        accountClient.deductBalance(command.getUserId(), order.getAmount());

        return OrderResult.success(order.getId());
    }
}
```

### 4.3 AT 模式要点

```text
AT 模式要点
├── ① 侵入小：只加 @GlobalTransactional 注解
├── ② 回滚自动：UNDO_LOG 生成回滚 SQL
├── ③ 依赖：Seata Server（TC）+ 数据库 UNDO_LOG 表
├── ④ 隔离：全局锁（写冲突时等待）
├── ⑤ ⚠️ 注意：
│   ├── 不适合大并发写（全局锁）
│   ├── 业务 SQL 需可回滚（镜像还原）
│   └── 表需加 UNDO_LOG 支持
└── ⑥ 金句：AT = 「注解开启 + 自动回滚」——首选方案
```

## 5. 事务消息

### 5.1 原理（RocketMQ）

> **背景**：事务消息保证「本地事务执行」与「消息发送」的原子性——异步链路的最终一致性。

```text
事务消息流程
├── ① 发送半消息（Broker 暂存——不可见）
├── ② 执行本地事务
├── ③ 提交/回滚半消息
│   ├── 提交 → 消息可见（消费者处理）
│   └── 回滚 → 消息删除
├── ④ 事务回查：Broker 超时未确认 → 询问本地事务状态
└── ⑤ 保证：本地事务成功 = 消息必达（原子性）

场景
├── 下单成功 → 发「扣积分」消息
├── 订单创建 + 消息发送 原子化
└── 消费失败 → 重试/死信（最终一致）
```

### 5.2 实现

```java
// ① 发送事务消息（Spring + RocketMQ）
@Autowired
private RocketMQTemplate rocketMQTemplate;

public void createOrder(Order order) {
    // 事务消息：本地事务 + 消息发送 原子化
    rocketMQTemplate.sendMessageInTransaction(
        "order-topic",                          // topic
        MessageBuilder.withPayload(order).build(),
        order                                   // 参数（回调用）
    );
}

// ② 事务回调（本地事务执行）
@RocketMQTransactionListener
public class OrderTransactionListener
        implements RocketMQLocalTransactionListener {
    @Override
    public RocketMQLocalTransactionState executeLocalTransaction(
            Message msg, Object arg) {
        try {
            orderDao.insert((Order) arg);       // 本地事务
            return RocketMQLocalTransactionState.COMMIT;
        } catch (Exception e) {
            return RocketMQLocalTransactionState.ROLLBACK;
        }
    }

    @Override
    public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
        // 事务回查（Broker 超时询问）
        Order order = (Order) msg.getPayload();
        return orderDao.exists(order.getId())
            ? RocketMQLocalTransactionState.COMMIT
            : RocketMQLocalTransactionState.ROLLBACK;
    }
}
```

## 6. Saga 与 TCC

### 6.1 Saga（长流程补偿）

```text
Saga 模式
├── ① 正向：S1 → S2 → S3（本地事务链）
├── ② 失败：执行反向补偿（C3 → C2 → C1）
├── ③ 编排：中心协调（Choreography/Orchestration）
├── ④ 适用：长流程/无锁（比 AT 并发好）
└── ⑤ 代价：补偿逻辑手写 + 中间状态可见

示例（下单 Saga）
├── S1 创建订单 → S2 扣库存 → S3 扣余额
├── S3 失败 → C2 回补库存 → C1 取消订单
└── 金句：Saga = 「正向业务 + 反向补偿」——适合长流程
```

### 6.2 TCC（强一致）

```text
TCC 模式（Try-Confirm-Cancel）
├── ① Try：预留资源（冻结库存/预扣）
├── ② Confirm：确认（真正扣减）
├── ③ Cancel：取消（释放预留）
├── ④ 适用：金融强一致（转账/支付）
├── ⑤ 代价：业务三方法手写（侵入最大）
└── ⑥ 金句：TCC = 「预留 + 确认/取消」——强一致但复杂
```

## 7. 方案选型

```text
分布式事务选型（2026）
├── ① 常规跨库事务（下单链路）→ Seata AT
├── ② 异步解耦链路（通知/积分）→ 事务消息
├── ③ 金融强一致（资金/支付）→ TCC
├── ④ 长流程（多步骤/审批）→ Saga
├── ⑤ 支付-订单跨系统 → 事务消息/对账
└── ⑥ 金句：先选「最终一致」（简单可靠）——强一致只在必须时

选型决策树
 ├─ 资金/强一致？→ TCC
 ├─ 长流程（5+ 步）？→ Saga
 ├─ 异步链路？→ 事务消息
 ├─ 常规同步跨库？→ Seata AT
 └─ 能接受对账？→ 事务消息 + 对账兜底
```

## 8. 生产实践清单

```text
分布式事务生产清单
[ ] 一致性模型明确？（强/最终——按业务）
[ ] Seata：Server 高可用？UNDO_LOG 表就绪？
[ ] 事务消息：回查实现？消费幂等？
[ ] 幂等设计：所有写操作幂等（重试前提）
[ ] 超时链路：参与全局事务的调用超时合理？
[ ] 全局锁冲突评估？（AT 写冲突等待）
[ ] 补偿/对账：最终一致需对账脚本
[ ] 监控：事务失败率/回滚数告警
[ ] 演练：故障演练（中间服务挂 → 回滚验证）
[ ] 金句：分布式事务 = 「模型选择 + 幂等 + 对账 + 演练」
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 拆库的代价 = 分布式一致性——跨服务事务需要专门方案
> 2. **优先最终一致**：支付强一致、订单-库存最终一致（按风险选）
> 3. Seata AT：@GlobalTransactional + 自动回滚 SQL——侵入最小首选
> 4. 事务消息：本地事务 + 消息原子化（RocketMQ 半消息 + 回查）
> 5. Saga 长流程补偿 / TCC 金融强一致（Try/Confirm/Cancel）
> 6. 生产铁律：幂等设计 + 对账兜底 + 故障演练——一致性不是靠运气
