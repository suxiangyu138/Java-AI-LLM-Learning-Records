## 1. 可观测性三支柱

> **背景**：微服务链路长（5-6 跳）——没有可观测性 = 排障靠猜。
> **目的**：理解三支柱的分工与配合。
> **适用范围**：所有微服务生产系统。

```text
可观测性三支柱
├── ① 指标（Metrics）：
│   ├── 系统怎么样（趋势）
│   ├── 工具：Prometheus + Grafana
│   └── 内容：QPS/错误率/P95 耗时
├── ② 日志（Logs）：
│   ├── 发生了什么（细节）
│   ├── 工具：ELK/Loki
│   └── 内容：traceId/业务上下文/异常
├── ③ 链路（Traces）：
│   ├── 请求经历了什么（路径）
│   ├── 工具：Zipkin/Jaeger/ARMS
│   └── 内容：服务间调用/耗时/错误点
└── ④ 配合：traceId 串联日志与链路
    ├── 指标告警 → 日志看细节 → 链路找路径
    └── 金句：指标告诉你「有问题」、日志告诉你「什么问题」、链路告诉你「在哪」

2026 工具链
├── Micrometer（统一埋点）
├── Prometheus + Grafana（指标）
├── Zipkin/Jaeger（链路）
├── ELK/Loki（日志）
└── 云厂商：ARMS（阿里）/ APM
```

## 2. Micrometer 统一可观测

> **背景**：Spring Cloud 3.x 官方方案——Sleuth 合并入 Micrometer Tracing。
> **目的**：统一指标/链路埋点（一个 API 多后端）。

```text
Micrometer 的价值
├── ① 统一 API：一个接口对接多后端
│   ├── Prometheus（指标）
│   ├── Zipkin/Jaeger（链路）
│   └── 云 ARMS（阿里）
├── ② 自动埋点：Web/数据库/消息自动采集
├── ③ 标准传播：W3C traceparent（兼容 SkyWalking）
└── ④ 2026：Spring Boot 3.x 标准（Sleuth 已合并）

依赖
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

```yaml
# 配置（指标 + 链路）
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  tracing:
    sampling:
      probability: 0.1        # 采样率 10%（见第 4 节）
  zipkin:
    tracing:
      endpoint: http://zipkin:9411/api/v2/spans
```

## 3. 链路追踪

### 3.1 核心概念

```text
链路追踪核心概念
├── ① Trace（链路）：一次请求的完整路径
├── ② Span（跨度）：一次调用（服务间一跳）
│   ├── spanId：当前调用 ID
│   └── parentSpanId：父调用（构建树）
├── ③ 传播：traceId/spanId 随请求头传递
│   ├── W3C：traceparent（标准）
│   └── 自定义：X-Trace-Id
└── ④ 串联：按 traceId 查全链路（见日志系列 MDC）

链路图（下单请求）
用户 → Gateway(span1) → Order(span2) → Stock(span3)
                                    └→ Account(span4)
└── 定位：哪一跳慢/失败 → 看 span 耗时/状态
```

### 3.2 使用要点

```text
链路追踪实践
├── ① 自动埋点：Spring Cloud 自动采集（HTTP/DB/MQ）
├── ② 手动埋点：自定义 Span（@SpanTag/Annotation）
├── ③ 日志关联：MDC 注入 traceId（见日志系列）
├── ④ 错误定位：span 的错误状态 + 日志
├── ⑤ 金句：traceId = 微服务排障的「导航键」
```

## 4. 采样策略

> 🎯 **采样率是成本与覆盖的平衡**（2026 推荐）：

```text
采样策略
├── ① 正常流量：0.01-0.1（1%-10%）
│   ├── 足够趋势分析（P95/错误率）
│   └── 成本可控（链路数据量控制）
├── ② 错误请求：100% 采样
│   ├── 错误必须全量（排障必需）
│   └── 配置：错误采样策略
├── ③ 慢请求：100%（可选）
└── ④ 金句：正常采样省成本、错误全量保排障

配置
spring:
  tracing:
    sampling:
      probability: 0.1        # 正常 10%
# 错误 100%：自定义 Sampler（按状态码）
```

## 5. 探针与健康检查

> 🎯 **Actuator 探针供 K8s 使用**（2026 标准）：

```yaml
# 探针端点
management:
  endpoint:
    health:
      probes:
        enabled: true
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
```

```text
探针两维度
├── ① liveness（存活）：进程活着吗
│   ├── 失败 → K8s 重启 Pod
│   └── 检查：/actuator/health/liveness
├── ② readiness（就绪）：能接流量吗
│   ├── 失败 → K8s 摘流量（不重启）
│   └── 检查：/actuator/health/readiness
└── ③ 实践：
    ├── 启动慢：readiness 延迟就绪
    ├── 依赖挂：readiness 失败（不接流量）
    └── 金句：liveness 管重启、readiness 管流量

指标告警（Prometheus）
├── CPU 连续 10 分钟 > 85%
├── 错误率 > 阈值（按服务）
├── P95 耗时 > 阈值
└── 熔断/限流事件（Sentinel 指标）
```

## 6. Spring Cloud 与 K8s 协同

> 🎯 **2026 黄金法则**：「不要在 Kubernetes 已经做得很好的事情上重复造轮子」：

```text
职责划分
├── K8s 擅长（基础设施）：
│   ├── 服务发现：Kubernetes Service + CoreDNS
│   ├── 部署/伸缩：Deployment + HPA
│   ├── 配置：ConfigMap/Secret
│   └── 探针：liveness/readiness
├── Spring Cloud 擅长（业务语义）：
│   ├── 业务路由：网关（lb://）
│   ├── 动态配置：Nacos（功能开关）
│   ├── 熔断限流：Sentinel
│   └── 业务语义治理
└── 决策：
    ├── 纯 K8s 环境：优先 K8s 服务发现（不重复）
    ├── 跨集群/混合 VM：才引入注册中心
    └── 配置分层：
        ├── 基础设施（DB/MQ 地址）→ ConfigMap
        └── 业务逻辑（开关/阈值）→ Nacos

双层网关（见 04 篇）
├── 外层：K8s Ingress（TLS/域名/全局限流）
└── 内层：Spring Cloud Gateway（鉴权/路由/业务限流）
```

## 7. 服务网格演进

> **背景**：服务网格（Istio/ASM）把治理能力下沉到 sidecar——无需改代码。
> **目的**：理解 Spring Cloud → 服务网格的渐进迁移。
> **适用范围**：云原生成熟团队（治理能力升级）。

```text
服务网格核心
├── ① Sidecar：每个 Pod 旁挂代理（Envoy）
├── ② 能力下沉：
│   ├── 服务发现 → K8s DNS
│   ├── 路由规则 → VirtualService/DestinationRule
│   ├── 熔断限流 → sidecar 接管
│   ├── mTLS：自动双向加密
│   └── 故障注入：混沌测试支持
├── ③ 无侵入：不改源代码（基础设施层治理）
└── ④ 对比 Spring Cloud：
    ├── Spring Cloud：业务代码内治理（注解/配置）
    └── 服务网格：基础设施层治理（sidecar）

渐进迁移（阿里 ASM 实践）
├── ① 初期：保留注册中心（互通）
├── ② 逐步：服务发现收敛到 K8s DNS
├── ③ 路由：VirtualService 接管
├── ④ 熔断：sidecar 接管（Sentinel 移除）
└── ⑤ 完成：mTLS + 故障注入（全网格能力）
→ 金句：服务网格 = 「治理下沉 + 无侵入」——云原生演进方向
```

## 8. 演进路线图

```text
微服务云原生演进（2026）
┌─────────────────────────────────────────────┐
│ 阶段 1：Spring Cloud 微服务（治理在代码）      │
│ ├── Nacos 注册 + 配置                        │

│ └── 可观测：Micrometer + Prometheus          │

│ 阶段 2：容器化 + K8s（治理分工）               │
│ ├── 镜像化 + Deployment + HPA                │
│ ├── ConfigMap/Secret（基础设施配置）          │
│ ├── 探针（liveness/readiness）               │
│ └── Ingress 双层网关                         │
├─────────────────────────────────────────────┤
│ 阶段 3：服务网格（治理下沉）                   │
│ ├── Sidecar 接管路由/熔断/mTLS                │
│ ├── 注册收敛 K8s DNS                         │
│ └── 故障注入（混沌工程）                      │
└─────────────────────────────────────────────┘
→ 金句：演进 = 业务语义治理（Spring Cloud）→ 基础设施治理（K8s）→ 全下沉（网格）
```

## 9. 核心要点

> 🎯 **核心要点**：
> 1. 三支柱：指标（趋势）+ 日志（细节）+ 链路（路径）——traceId 串联
> 2. Micrometer：统一埋点（Sleuth 合并入）——指标 + 链路一个 API
> 3. 采样策略：正常 1-10%、错误 100%——成本与排障平衡
> 4. 探针：liveness（重启）+ readiness（流量）——K8s 使用
> 5. **K8s 协同黄金法则**：不重复造轮子——K8s 管基础设施、Spring Cloud 管业务语义
> 6. 服务网格：sidecar 治理下沉（无侵入）——渐进迁移（注册→路由→熔断→mTLS）
> 7. 演进三阶段：Spring Cloud → K8s → 服务网格
