## 1. 注册与发现机制

> **背景**：微服务实例动态变化（扩缩容/故障）——调用方不能写死 IP，需要「通讯录」动态维护。
> **目的**：理解注册中心的三个角色与机制。
> **适用范围**：所有微服务架构。

```text
注册中心三角色
├── ① Provider（服务提供方）：
│   ├── 启动 → 向注册中心注册（服务名/IP/端口/元数据）
│   ├── 运行 → 心跳续约
│   └── 下线 → 注销
├── ② Consumer（服务消费方）：
│   ├── 启动 → 拉取服务列表（缓存）
│   ├── 订阅变更（服务列表变化推送）
│   └── 按负载均衡策略选择实例
└── ③ Registry（注册中心）：
    ├── 存储服务实例信息
    ├── 健康检查（剔除故障实例）
    └── 通知变更（推送给消费者）

调用流程
Consumer → 注册中心（查服务列表）→ 选实例 → 直连调用
└── 金句：注册中心 = 「微服务的通讯录」——动态维护谁在哪
```

## 2. Nacos 核心能力

> **背景**：Nacos（阿里开源）是 2026 国内微服务注册/配置的事实标准。
> **目的**：掌握 Nacos 的核心能力与配置要点。
> **适用范围**：Spring Cloud Alibaba 生态。

```text
Nacos 2.x 核心能力
├── ① 注册中心：服务注册/发现/健康检查
├── ② 配置中心：配置管理/动态刷新（见配置文件系列）
├── ③ 双模式：AP（可用性优先）/CP（一致性优先）
├── ④ 2.x 性能：gRPC 通信（推送性能提升 10 倍）
├── ⑤ 临时/持久实例：临时（心跳管理）vs 持久（主动注销）
└── ⑥ 命名空间/分组/DataId：三级隔离

Spring Cloud Alibaba 集成
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
```

## 3. AP vs CP 模式

> 🎯 **AP/CP 选择（面试必考）**——微服务场景默认 AP：

```text
CAP 理论（注册中心视角）
├── ① AP（可用性优先）：分区时仍可注册/发现
│   ├── 缺点：可能读到「旧的服务列表」
│   └── 适用：微服务场景（临时实例）
├── ② CP（一致性优先）：分区时拒绝写（保证一致）
│   ├── 缺点：分区时不可用（无法注册）
│   └── 适用：持久实例/强一致要求
└── ③ 选择：
    ├── 微服务调用 → AP（可用性优先）
    ├── 配置/强一致 → CP
    └── 金句：微服务场景一律临时实例 + AP 模式

Nacos 配置
# 临时实例（默认——AP 风格）
spring.cloud.nacos.discovery.ephemeral=true
# 持久实例（CP 风格）
spring.cloud.nacos.discovery.ephemeral=false
```

## 4. 心跳与健康检查

### 4.1 心跳机制

```text
心跳（临时实例）
├── ① 客户端周期发送心跳（heart-beat-interval）
├── ② 超时未收到 → 标记不健康（heart-beat-timeout）
├── ③ 超过剔除时间 → 移除（ip-delete-timeout）
└── ④ 配置铁律：
    ├── heart-beat-timeout ≥ 3 × heart-beat-interval
    └── 否则网络波动 → 服务频繁「假死」剔除
```

```yaml
# 心跳配置（Nacos 客户端）
spring:
  cloud:
    nacos:
      discovery:
        heart-beat-interval: 5000       # 心跳间隔 5s
        heart-beat-timeout: 15000       # 超时 15s（≥3 倍！）
        ip-delete-timeout: 30000        # 剔除 30s
```

### 4.2 健康检查

```text
健康检查两层面
├── ① Nacos 层：心跳（服务进程活着）
├── ② 业务层：/actuator/health（业务可用性）
│   ├── liveness（存活）：进程活着
│   └── readiness（就绪）：可以接流量
├── ③ 2026 实践：
│   ├── 服务注册前就绪（先 readiness 再注册）
│   └── K8s 探针 + 注册中心联动
└── ④ 金句：心跳 = 进程级；health = 业务级——两者配合
```

## 5. Nacos 三级隔离

> 🎯 **三级隔离（Namespace → Group → DataId）**——多环境/多业务的配置与注册隔离：

```text
三级隔离
├── ① Namespace（命名空间）：环境隔离（物理级）
│   ├── dev / test / staging / prod
│   └── 生产独立命名空间（权限隔离）
├── ② Group（分组）：业务域隔离
│   ├── DEFAULT_GROUP（默认）
│   └── PAYMENT_GROUP（支付域独立）
├── ③ DataId（配置 ID）：具体配置
│   ├── order-service.yaml
│   └── 服务名 + 环境 + 扩展名

配置（Spring）
spring:
  cloud:
    nacos:
      discovery:
        namespace: prod       # 环境（Namespace ID）
        group: DEFAULT_GROUP
      config:
        namespace: prod
        group: DEFAULT_GROUP
        file-extension: yaml

价值
├── ① 防环境混乱（dev 配置不会影响 prod）
├── ② 权限控制（Namespace 级权限）
├── ③ 业务隔离（支付域与订单域独立）
└── ④ 金句：三级隔离 = 「环境 × 业务 × 配置」的三维管控
```

## 6. 灰度发布

> **背景**：Nacos 原生不支持灰度路由——需通过元数据 + 负载均衡权重实现流量染色：

```text
灰度发布方案（2026）
├── ① 元数据标记：实例带 version 标签
│   ├── v1 实例：metadata.version=v1
│   └── v2 实例：metadata.version=v2
├── ② 负载均衡权重：
│   ├── 初始：v2 权重 10%（少量流量）
│   ├── 观察：无问题逐步提高
│   └── 全量：v2 权重 100%
├── ③ 流量染色：
│   ├── 请求头带灰度标记（X-Canary: v2）
│   └── 网关/负载均衡按标记路由
└── ④ 2026 更优：服务网格（Istio 原生灰度）
    ├── VirtualService 权重路由
    └── 无需改代码（见 07 篇）

实现（LoadBalancer 自定义）
├── ① 读取实例元数据（version）
├── ② 按权重选择实例
└── ③ 支持请求头染色
→ 金句：灰度 = 「少量验证 → 逐步放量」——元数据 + 权重实现
```

## 7. 高可用部署

```text
Nacos 高可用（生产必备）
├── ① 集群：≥3 节点（Raft 选举）
├── ② 存储：MySQL（配置持久化——非内嵌 Derby）
├── ③ 负载：VIP/云负载均衡（客户端连 VIP）
├── ④ 故障切换：节点故障自动选举
└── ⑤ 客户端容错：本地快照（服务端不可达用缓存）

⚠️ 生产红线
├── ① 绝不用内嵌 Derby（数据易丢）
├── ② 集群 ≥3（Raft 多数派）
├── ③ 配置即资产（备份策略）
└── ④ 金句：注册中心是「单点中的单点」——必须高可用
```

## 8. 核心要点

> 🎯 **核心要点**：
> 1. 注册中心三角色：Provider 注册/Consumer 发现/Registry 维护——微服务的通讯录
> 2. Nacos 2.x：注册 + 配置一体、AP/CP 双模式、gRPC 推送（快 10 倍）
> 3. **AP vs CP**：微服务场景默认临时实例 + AP（可用性优先）
> 4. 心跳铁律：heart-beat-timeout ≥ 3 × interval（防假死）
> 5. 三级隔离：Namespace（环境）× Group（业务）× DataId（配置）
> 6. 灰度：元数据 version + LoadBalancer 权重（服务网格原生更优）
> 7. 高可用：≥3 节点集群 + MySQL 持久化（绝不用 Derby）
