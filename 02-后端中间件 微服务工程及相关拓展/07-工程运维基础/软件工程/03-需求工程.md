## 1. 需求工程概述

### 1.1 为什么需求是软件工程的第一道关口

> Requirements = 需求。软件工程的铁律：**前期需求的错误修复成本是后期修复成本的1/100甚至1/1000**。

```text
修复一个需求缺陷的成本：
  需求阶段:     $1
  设计阶段:     $5-10
  编码阶段:     $20-50
  测试阶段:     $100-200
  生产运行:     $1000+
  
每个阶段修复成本约×10倍增长！
```

### 1.2 需求层次

| 层次 | 英文 | 关注者 | 形式 |
|------|------|--------|------|
| **业务需求** | Business Requirement | 高层/投资人 | "我们要提升用户留存率" |
| **用户需求** | User Requirement | 产品经理/用户 | "用户可以一键分享内容" |
| **系统需求** | System Requirement | 开发/测试 | "POST /api/share { contentId }" |
| **功能需求** | Functional Requirement | 开发 | 系统具体要做什么 |
| **非功能需求** | Non-Functional Requirement | 架构师 | 性能/安全/可用性约束 |

```
业务需求 → 用户需求 → 系统需求
  (Why)      (What)     (How)
```

## 2. 需求获取

### 2.1 需求获取技术对比

| 技术 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| **访谈** | 与关键干系人一对一 | 深入理解、可追问 | 耗时、受被访者偏见影响 |
| **问卷调查** | 大量用户、统计需求 | 覆盖面广、可量化 | 无法追问、设计偏差 |
| **观察法** | 了解实际工作流程 | 发现用户说不出来的需求 | 霍桑效应(被观察时行为改变) |
| **头脑风暴** | 创新需求、发散思维 | 产生新想法 | 需引导、可能跑偏 |
| **原型法** | 不确定的需求、UI探索 | 可视化、快速反馈 | 用户可能"喜欢原型 ≠ 需要功能" |
| **文档分析** | 已有系统/制度/法规 | 客观、可追溯 | 文档可能过时 |
| **竞品分析** | 了解市场和对手 | 获取行业标准 | 直接照搬可能不适用 |

### 2.2 有效访谈的技巧

```text
✅ 提前准备访谈提纲，发给受访者
✅ 以"开放性问题"开头："你的一天怎么开始？"
✅ 追问"为什么"5次 → 发现真实需求，而非表面需求
✅ 结束时做总结："我理解的你的需求是...对吗？"
✅ 48小时内整理访谈纪要并确认

❌ 提引导性问题："你是不是想要一个搜索按钮？"
  → 用户会说"是"，但这不是真实需求
❌ 技术人员主导谈话 → 陷入"怎么实现"而忽略"做什么"
```

### 2.3 用户故事（User Story）标准格式

```text
作为 <角色>
我想要 <功能>
以便 <价值>

示例：
作为 普通用户，
我想要 按价格区间筛选商品，
以便 快速找到预算内的商品。

验收标准 (Acceptance Criteria)：
- [ ] 输入价格区间后，商品列表实时刷新
- [ ] 支持只输入最低价或只输入最高价
- [ ] 输入非法价格时给出提示
- [ ] 筛选结果支持排序
```

## 3. 需求分析

### 3.1 需求分析的核心任务

| 任务 | 说明 | 技术 |
|------|------|------|
| **需求分类** | 将需求按功能域/优先级/风险分类 | MoSCoW分类法 |
| **冲突消解** | 解决需求之间的不一致 | 协商、优先级排序 |
| **优先级排序** | 决定哪些先做哪些后做 | MoSCoW、Kano模型 |
| **可行性分析** | 技术上、时间上、成本上是否可行 | 技术预研、原型验证 |
| **建模** | 用图形化方式表示需求 | 用例图、流程图、数据流图 |

### 3.2 MoSCoW优先级分类

| 类别 | 含义 | 策略 |
|:---:|------|------|
| **M** (Must have) | 必须有，没有则不可发布 | 本期100%完成 |
| **S** (Should have) | 应该有，重要但可临时缺失 | 尽量完成 |
| **C** (Could have) | 可以有，锦上添花 | 有余力则做 |
| **W** (Won't have) | 明确不做（至少本期） | 放入后续Backlog |

### 3.3 Kano模型

```text
Kano模型将需求分为三类：

满意度  ↑
        │     ╱ 兴奋型需求（Excitement）
        │   ╱   "居然有这个！太棒了"
        │ ╱    例：下单后的惊喜优惠券
        │╱
        └──────────→ 功能实现度
         ╲
          ╲  期望型需求（Performance）
           ╲ "越多越好" 例：加载速度越快越好
            ╲
             ‾‾‾‾‾  基本型需求（Basic/Threshold）
              "理所当然" 例：能登录、能支付
              没有它 → 极度不满。有了 → 不会特别满意。

启示：基本需求必须满足（先做），期望需求越多越好，兴奋需求创造口碑。
```

## 4. 需求规格说明

### 4.1 SRS文档结构

> SRS (Software Requirements Specification) = 软件需求规格说明书。

```text
SRS标准结构（IEEE 830-1998）：
1. 引言
   1.1 目的
   1.2 范围（做什么、不做什么）
   1.3 定义和缩略词
   1.4 参考文献
   
2. 总体描述
   2.1 产品视角（系统上下文图）
   2.2 产品功能（功能总览）
   2.3 用户特征
   2.4 约束条件
   2.5 假设和依赖
   
3. 具体需求（核心！）
   3.1 功能需求（每个功能的一句话描述+输入输出+前置条件）
   3.2 非功能需求（性能/安全/可用性/可维护性）
   3.3 接口需求（API/UI/硬件接口）
   
附录: 用例图、数据字典、术语表
```

### 4.2 需求的SMART原则

| 字母 | 含义 | 反面示例 |
|:---:|------|----------|
| **S** | Specific 具体 | ~~"系统要快"~~ → "搜索响应P99<200ms" |
| **M** | Measurable 可度量 | ~~"用户体验好"~~ → "SUS问卷评分>80" |
| **A** | Achievable 可实现 | 技术上可能、时间上可行 |
| **R** | Relevant 相关 | 与业务目标关联 |
| **T** | Traceable 可追溯 | 每个需求可追溯到来源和实现 |

## 5. 需求验证与管理

### 5.1 需求评审检查清单

```checkbox
□ 完整性：是否覆盖了所有用户场景？
□ 一致性：不同需求之间有无矛盾？
  （如：需求A要求"7×24可用"，需求B要求"每天凌晨3点维护"）
□ 可测试性：每个需求是否可验证？
□ 无歧义性：是否所有人理解一致？
  （"支持大文件上传" — 多大算大？10MB？1GB？）
□ 可追溯性：能否追溯到业务目标？
□ 可行性：技术和时间上是否可行？
```

### 5.2 需求变更管理

```text
需求变更流程：
  提出变更 → 影响分析（成本/时间/风险） → CCB审核 → 批准/拒绝

影响分析模板：
  - 变更描述：增加了导出Excel功能
  - 影响范围：订单服务、前端订单页面
  - 工作量：开发2天、测试1天
  - 风险：对现有导出CSV功能的影响
  - 优先级：P1（客户合同要求）
```

## 6. 需求工程的敏捷实践

| 传统需求工程 | 敏捷需求工程 |
|-------------|-------------|
| 一次性写完所有SRS | 每个Sprint逐步细化 |
| 200页需求文档 | User Story卡片 + Acceptance Criteria |
| 需求冻结（需求变更=变更请求） | 欢迎变化（下个Sprint再调整） |
| 用户签字确认 | 每个Sprint Review持续确认 |
| 需求分析师独立完成 | PO+开发+测试共同参与 |

> 🎯 **需求工程的终极目标**：回答"我们到底要做什么"并让所有干系人对答案达成一致。不是写出完美的文档，而是建立对目标的共识。
