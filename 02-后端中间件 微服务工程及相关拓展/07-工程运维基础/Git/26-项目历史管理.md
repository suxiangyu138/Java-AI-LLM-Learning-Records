## 1. Git历史的数据模型

### 1.1 历史的核心：DAG有向无环图

```text
项目的完整历史 = 所有commit组成的DAG (Directed Acyclic Graph)

    A ← B ← C ← D  (main)
         ↖ 
           E ← F    (feature)
         
每个commit指向其父commit(s)，形成不可篡改的链：
  - 修改任何commit → SHA-1改变 → 所有后代commit的SHA-1级联改变
  - 这是Git历史不可篡改性的数学基础
```

### 1.2 Commit的完整元信息

```bash
# 查看一个commit的完整信息
git cat-file -p a1b2c3d

# 输出：
# tree 8f3a2c9b...          ← 文件目录快照
# parent d4e5f6g...          ← 父commit
# author Zhang San <zhangsan@example.com> 1704067200 +0800
# committer Zhang San <zhangsan@example.com> 1704067200 +0800
#                            ← author=谁写的, committer=谁提交的
# feat(user): 添加用户登录功能
# 
# 实现了用户名密码登录和JWT Token签发

# 一个commit包含：
#   tree: 本次提交的文件快照
#   parent: 父提交（首次提交无parent，merge提交有2个parent）
#   author/committer: 作者和提交者（cherry-pick/rebase时两者可能不同）
#   message: 提交说明
```

## 2. git log 高级用法

### 2.1 格式化输出

```bash
# 一行日志（最常用）
git log --oneline -20

# 图形化分支拓扑
git log --graph --oneline --decorate --all -30

# 自定义格式
git log --pretty=format:"%C(yellow)%h%Creset %C(cyan)%ad%Creset | %s %C(green)%d%Creset %C(blue)[%an]%Creset" --date=short
```

| 占位符 | 含义 | 示例输出 |
|--------|------|----------|
| `%h` | 简短hash | `a1b2c3d` |
| `%H` | 完整hash | `a1b2c3d4e5f...` |
| `%ad` | 作者日期(--date=short) | `2024-01-15` |
| `%s` | 提交标题 | `feat: 添加登录` |
| `%an` | 作者名 | `Zhang San` |
| `%d` | 分支/标签引用 | `(HEAD -> main)` |
| `%b` | 提交正文 | 详细描述... |

### 2.2 按条件过滤

```bash
# === 按时间 ===
git log --since="2024-01-01" --until="2024-01-31"
git log --since="1 week ago"
git log --after="yesterday"

# === 按作者 ===
git log --author="Zhang San"

# === 按文件 ===
git log -- src/main/java/.../UserService.java      # 某个文件的变更历史
git log -p -- src/main/java/.../UserService.java   # 含详细diff
git log --follow -- src/main/java/.../UserService.java  # 跟踪重命名

# === 按提交信息 ===
git log --grep="fix"                 # 搜索commit message含"fix"
git log --grep="JIRA-1234"           # 关联Issue的提交

# === 按代码内容（pickaxe搜索）===
git log -S"findByEmail"              # 搜索代码中出现/删除"findByEmail"的所有commit
git log -G"password.*encrypt"        # 正则搜索代码变更

# === 组合过滤 ===
git log --author="Zhang" --since="2024-01-01" -- src/main/java/.../service/ --oneline
```

### 2.3 统计与对比

```bash
# 提交统计（每人提交数）
git shortlog -sn --all --no-merges

# 文件变更统计
git log --stat                           # 每个commit变更了哪些文件
git log --numstat                        # 机器可读的文件变更统计

# 两个版本之间的差异
git log main..feature                    # feature有但main没有的commit
git log main...feature                   # 两者各自独有的commit(= 对称差)
git log --left-right main...feature     # 标注每个commit属于哪边
```

## 3. 标签管理：版本的里程碑

### 3.1 轻量标签 vs 附注标签

| 维度 | 轻量标签 (Lightweight) | 附注标签 (Annotated) |
|------|----------------------|---------------------|
| 本质 | 指向commit的指针（和分支一样） | 独立的Git对象（含作者/日期/说明/GPG签名） |
| 元信息 | ❌ 无 | ✅ 标签人、日期、说明 |
| 适用 | 临时标记、个人使用 | **生产发布唯一推荐** |
| 命令 | `git tag v1.0.0` | `git tag -a v1.0.0 -m "Release v1.0.0"` |

```bash
# 创建附注标签（推荐）
git tag -a v2.3.1 -m "Release v2.3.1: 新增订单导出、修复支付超时Bug"

# GPG签名标签（企业级安全）
git tag -s v2.3.1 -m "Release v2.3.1"

# 查看标签详情
git show v2.3.1              # 标签信息 + 对应commit的diff

# 为历史commit补打标签
git tag -a v1.0.0 a1b2c3d -m "首次正式发布"

# 列出标签
git tag                       # 所有标签
git tag -l "v2.*"             # 通配符过滤

# 推送标签
git push origin v2.3.1        # 单个标签
git push origin --tags        # 所有标签

# 删除标签
git tag -d v2.3.1             # 本地删除
git push origin --delete v2.3.1  # 远程删除
```

### 3.2 语义化版本与标签联动

```text
版本规则: MAJOR.MINOR.PATCH (semver.org)

MAJOR: 不兼容的API变更（v1.x → v2.0.0）
MINOR: 向后兼容的新功能（v1.1 → v1.2.0）
PATCH: 向后兼容的Bug修复（v1.1.0 → v1.1.1）

Java后端发布流程：
  1. develop → release/v2.3.0
  2. 在release分支测试 → 修复Bug → 提交
  3. release分支 → 合并到main
  4. 在main上打tag: git tag -a v2.3.0 -m "Release v2.3.0"
  5. git push origin main --tags
  6. CI/CD检测到 v* 标签 → 触发生产部署
```

## 4. 历史搜索与追溯

### 4.1 追溯代码来源

```bash
# 查看文件每一行的最后修改者和commit
git blame UserService.java

# 指定行范围
git blame -L 10,50 UserService.java

# 忽略空白变更（代码格式化后有用）
git blame -w UserService.java

# 显示完整hash而非缩写
git blame -l UserService.java

# 查看某行在某个commit之前是谁写的
git blame a1b2c3d^ -- UserService.java
```

### 4.2 追溯文件变动

```bash
# 文件被谁在什么时候删除的
git log --diff-filter=D --summary -- src/main/java/.../OldService.java

# 查看某次commit改了哪些文件
git show --stat a1b2c3d
git diff-tree --no-commit-id --name-only -r a1b2c3d

# 两个Tag之间的变更文件列表
git diff --name-only v1.0.0 v2.0.0

# 生成Release Notes
git log v1.0.0..v2.0.0 --oneline --no-merges
```

### 4.3 reflog：终极恢复工具

```bash
# reflog记录HEAD的所有移动（包括被删除的分支、reset、rebase）
git reflog

# 输出：
# a1b2c3d HEAD@{0}: commit: feat: 添加用户登录
# d4e5f6g HEAD@{1}: reset: moving to HEAD~1     ← reset也能找回！
# g7h8i9j HEAD@{2}: checkout: moving from main to feature/user
# ...

# 恢复"丢失"的commit
git checkout -b recovered-branch HEAD@{3}   # 恢复到3步前的状态

# 恢复误删的分支
git checkout -b recovered-branch a1b2c3d    # 如果记得SHA-1
# 或用reflog找到分支最后指向的commit
```

> 💡 `git reflog` 是Git的"后悔药"——只要commit过，即使`reset --hard`或删除了分支，也能通过reflog找回（默认保留90天）。

## 5. git bisect：二分法定位Bug

### 5.1 工作原理

```text
场景：v1.0.0正常，v2.0.0出现Bug，但中间有200个commit
    
传统方式：逐个commit回退测试 → 最坏200次
bisect方式：二分查找 → 最多log₂(200) ≈ 8次！

原理：
  确定good commit（没Bug）和bad commit（有Bug）
  → Git自动跳到中间commit
  → 你测试并告诉Git这是good还是bad
  → Git继续二分...直到定位到引入Bug的第一个commit
```

### 5.2 手动bisect

```bash
# 1. 开始bisect
git bisect start

# 2. 标记当前版本有Bug
git bisect bad HEAD

# 3. 标记已知正常的版本
git bisect good v1.0.0

# Git会自动checkout中间版本
# 4. 测试 → 告诉Git结果
git bisect good     # 如果这个版本正常
# 或
git bisect bad      # 如果这个版本有Bug

# 重复第4步直到Git告诉你：
# a1b2c3d is the first bad commit

# 5. 结束bisect
git bisect reset    # 回到原始状态
```

### 5.3 自动bisect

```bash
# 如果Bug可以自动化检测（测试用例/脚本），让Git自动执行
git bisect start HEAD v1.0.0
git bisect run mvn test -Dtest=PaymentBugTest    # 测试失败=bad，成功=good
# Git自动二分查找，无需人工干预！
```

## 6. 历史重写：什么时候可以、什么时候禁止

### 6.1 安全边界

```text
✅ 可以重写的历史（绝对安全）：
  - 还未push的本地commit
  - 个人feature分支（确认无人基于此工作）

❌ 绝对禁止重写的历史：
  - 已push到公共仓库的commit（main/develop/release）
  - 别人可能基于你的commit继续开发的任何分支
```

| 操作 | 安全条件 | 命令 |
|------|----------|------|
| 修改最近commit | 未push | `git commit --amend` |
| 撤销最近commit | 未push | `git reset HEAD~1` |
| 交互式整理commit | 未push的个人分支 | `git rebase -i HEAD~5` |
| 强制推送 | 仅个人分支 + `--force-with-lease` | `git push --force-with-lease` |

### 6.2 安全重写操作

```bash
# 修改最近的commit message
git commit --amend -m "feat(user): 正确的commit message"

# 追加忘记的文件到上一个commit
git add forgotten-file.java
git commit --amend --no-edit          # 不修改message，只追加文件

# 把最近3个commit压成1个
git rebase -i HEAD~3
# pick a1b2c3d feat: 用户登录
# squash d4e5f6g fix: typo
# squash g7h8i9j fix: another typo
# → 1个干净的commit

# 修改历史commit的author（团队要求统一邮箱时）
git rebase -i HEAD~3
# 将 pick 改为 edit → git commit --amend --author="Name <email>" --no-edit
# → git rebase --continue
```

## 7. 历史审计与合规

### 7.1 审计场景

```bash
# 谁改了这个配置？
git log -p -- application-prod.yml

# 某个文件的历史中出现了"password"？
git log -S"password" -p -- src/

# 查看某段时间范围内的所有变更
git log --since="2024-01-01" --until="2024-01-31" --all --oneline

# 检查是否有commit绕过了代码审查（直接在main上提交）
git log main --author="developer" --oneline
# ← 这些commit没有伴随merge commit，说明可能跳过了PR
```

### 7.2 GPG签名提交

```bash
# 配置GPG签名（确保commit不可伪造）
gpg --gen-key                                    # 生成GPG密钥
gpg --list-secret-keys --keyid-format=long       # 查看密钥ID

git config --global user.signingkey <KEY-ID>
git config --global commit.gpgsign true           # 所有commit自动签名
git config --global tag.gpgsign true              # 所有tag自动签名

# GitHub显示：Verified ✓  — 即使用户名被伪造，GPG签名无法伪造
```

> 🎯 **项目历史管理的本质**：让每一次变更都可追溯、可审计、可回滚。好的历史是项目的"黑匣子" — 出问题时不仅告诉你"现在是什么状态"，还告诉你"怎么变成这样的"。
