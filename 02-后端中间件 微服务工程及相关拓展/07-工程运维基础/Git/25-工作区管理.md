## 1. Git三大区域与文件状态

### 1.1 三态流转图

```text
┌──────────────┐    git add     ┌──────────────┐    git commit   ┌──────────────┐
│  工作区       │──────────────→│  暂存区        │───────────────→│  版本库        │
│  Working      │               │  Staging      │                │  Repository   │
│  Directory   │←──────────────│  Area         │               │  (.git/)      │
│              │  git restore   │              │                │              │
│              │               │              │               │              │
│  实际文件      │               │  .git/index   │                │  .git/objects │
│  可编辑        │               │  待提交清单     │                │  所有历史版本   │
└──────────────┘               └──────────────┘                └──────────────┘
        │                             │                               │
        │     git diff                │     git diff --staged         │
        │     (工作区 vs 暂存区)        │     (暂存区 vs HEAD)            │
        └─────────────────────────────┘                               │
                                                                      │
                        git diff HEAD (工作区 vs HEAD)                  │
```

### 1.2 文件四种状态

| 状态 | 英文 | 含义 | `git status` 显示 |
|------|------|------|------------------|
| **未跟踪** | Untracked | 新文件，Git尚未管理 | `?? filename` |
| **已修改** | Modified | 已跟踪文件被修改，未暂存 | `M filename` (红色) |
| **已暂存** | Staged | 修改已add到暂存区 | `M filename` (绿色) |
| **未修改** | Unmodified | 与HEAD一致，无变更 | 不显示 |

```bash
git status --short
# 输出解读：
#  ?? new-file.java        ← 未跟踪
#  M modified-file.java    ← 右侧M = 工作区有修改（未暂存）
# M  staged-file.java      ← 左侧M = 已暂存
# MM both-staged.java      ← 两侧M = 暂存后又修改了
```

## 2. 工作区日常操作

### 2.1 状态查看

```bash
git status                    # 详细状态（最常用）
git status --short            # 精简状态
git status --branch           # 同时显示分支信息

# Java项目中的典型输出：
# On branch feature/order
# Changes not staged for commit:
#   modified:   OrderService.java        ← 修改了但未add
# Changes to be committed:
#   new file:   OrderController.java     ← 已add待commit
# Untracked files:
#   OrderServiceTest.java                ← 新建的测试类
```

### 2.2 差异对比

```bash
git diff                              # 工作区 vs 暂存区（未暂存的修改）
git diff --staged                     # 暂存区 vs HEAD（已暂存的修改）
git diff HEAD                         # 工作区 vs HEAD（所有修改）

git diff --stat                       # 只显示文件变更统计
git diff --name-only                  # 只显示变更的文件名

# 对比特定文件
git diff src/main/java/.../OrderService.java

# 忽略空白差异（代码格式化后验证）
git diff -w
```

## 3. git add 精准暂存

### 3.1 分层暂存策略

```bash
# 按文件/目录
git add OrderController.java          # 单个文件
git add src/main/java/.../service/    # 整个目录
git add *.java                        # 通配符

# 按变更类型
git add -u                            # 仅已跟踪文件的修改+删除（不含新增）
git add -A                            # 所有变更（新增+修改+删除）

# 交互式暂存（按hunk选择）⭐
git add -p                            # 逐块确认是否暂存
```

### 3.2 git add -p 交互式暂存

```text
git add -p 后交互选项：
  y - 暂存此块 (yes)
  n - 不暂存此块 (no)
  s - 将此块拆分成更小的块 (split)  
  e - 手动编辑此块 (edit)
  q - 退出，已选的不变

场景：UserService.java里改了3个方法，只想先提交其中1个
  → git add -p → 对每个hunk选y/n → 只暂存目标方法
```

```text
git add -p 输出示例：
@@ -15,6 +15,10 @@ public class UserService {
     }
 
+    public User findByEmail(String email) {    ← hunk 1
+        return userRepository.findByEmail(email);
+    }
+
+    public void updatePassword(Long id, String pwd) { ← hunk 2
+        // 修改密码逻辑
+    }
Stage this hunk [y,n,s,e,q]? n     ← 暂不提交hunk 1
Stage this hunk [y,n,s,e,q]? y     ← 提交hunk 2
```

## 4. git stash 工作区暂存

### 4.1 核心命令

```bash
git stash                           # 暂存所有修改（= git stash push）
git stash push -m "开发中-用户模块"   # 带说明的暂存
git stash push -p                   # 交互式选择暂存哪些

git stash list                      # 查看暂存列表
# stash@{0}: On feature/order: 开发中-用户模块
# stash@{1}: On main: 临时修复

git stash pop                       # 恢复最近一次暂存并删除记录
git stash pop stash@{1}            # 恢复指定暂存

git stash apply                     # 恢复但不删除记录（可多次apply）
git stash drop stash@{0}            # 删除指定暂存
git stash clear                     # 清空所有暂存
```

### 4.2 Stash进阶用法

```bash
# 只暂存已跟踪文件的修改（不含untracked文件）
git stash

# 包含未跟踪文件
git stash -u                        # --include-untracked

# 包含所有（含.gitignore忽略的文件）
git stash -a                        # --all

# 只暂存特定文件
git stash push -m "暂存配置文件" -- application.yml

# 从stash创建分支（当pop有冲突时很安全）
git stash branch recovery-branch stash@{0}
```

### 4.3 Stash使用场景

| 场景 | 操作 |
|------|------|
| 开发到一半需要切分支修Bug | `git stash` → `git switch hotfix/xxx` → 修完 → `git switch -` → `git stash pop` |
| 拉取远程更新前暂存本地修改 | `git stash` → `git pull` → `git stash pop` |
| 试验性修改不想commit | `git stash` → 如果后来需要 → `git stash pop`，不要就 → `git stash drop` |
| 把当前修改移到另一个分支 | `git stash` → `git switch target-branch` → `git stash pop` |

## 5. 工作区撤销与恢复

### 5.1 撤销决策矩阵

| 你做了什么 | 想撤回 | 命令 |
|-----------|--------|------|
| 修改了文件，没add | 恢复到暂存区/HEAD的样子 | `git restore <file>` |
| 修改了文件，没add | 恢复到某个commit的样子 | `git restore -s <commit> <file>` |
| add了文件，没commit | 取消暂存（回到modified） | `git restore --staged <file>` |
| 删除了文件 | 从Git恢复文件 | `git restore <file>` |
| 想清空所有工作区修改 | 全部恢复 | `git restore .` |

### 5.2 git restore vs git reset vs git checkout

| 命令 | 推荐度 | 用途 |
|------|:---:|------|
| `git restore <file>` | ⭐⭐⭐⭐⭐ | 撤销工作区修改（Git 2.23+新命令） |
| `git restore --staged <file>` | ⭐⭐⭐⭐⭐ | 取消暂存 |
| `git reset HEAD <file>` | ⭐⭐⭐⭐ | 取消暂存（老方法，仍可用） |
| `git checkout -- <file>` | ⭐⭐⭐ | 撤销工作区修改（老方法） |

> 💡 Git 2.23+ 推荐用 `git restore` 和 `git switch`，职责分离更清晰：`restore` 管文件恢复，`switch` 管分支切换，`checkout` 职能太多容易混淆。

## 6. 工作区清理与维护

```bash
# 查看会被清理的文件（先预览！）
git clean -n                        # --dry-run，只显示不删除

# 删除未跟踪文件
git clean -f                        # 删除文件
git clean -fd                       # 删除文件+目录
git clean -fx                       # 删除文件+被.gitignore忽略的文件

# 交互式清理
git clean -i

# 同时清理已跟踪但未暂存的修改（危险！）
git reset --hard HEAD && git clean -fd
```

> ⚠️ `git clean -fd` 会**永久删除**未跟踪的文件！执行前务必`git clean -n`预览。Java项目常见需要清理：编译产物、IDE生成的临时文件。

## 7. .gitignore 深入配置

### 7.1 Java项目标准模板

```gitignore
# === 编译产物 ===
target/
build/
out/
*.class
*.jar
*.war

# === IDE ===
.idea/
*.iml
*.iws
.vscode/
.settings/
.project
.classpath

# === 依赖 ===
.m2/
gradle/
node_modules/

# === 本地配置 ===
application-local.yml
application-*.local.yml
.env
.env.local

# === 日志与临时文件 ===
logs/
*.log
*.tmp
*.swp
*.bak

# === OS文件 ===
.DS_Store
Thumbs.db
```

### 7.2 忽略规则语法

| 规则 | 含义 | 示例 |
|------|------|------|
| `*.log` | 匹配所有.log文件 | 所有目录 |
| `logs/` | 匹配logs目录 | 所有层级 |
| `/logs/` | 只匹配根目录下的logs | 仅根目录 |
| `!important.log` | 排除规则（不忽略） | 例外 |

### 7.3 已跟踪文件的忽略

```bash
# .gitignore只对新文件生效。如果文件已被Git跟踪，需要先移除跟踪：
git rm --cached application-local.yml     # 移除跟踪但保留本地文件
git commit -m "chore: 移除本地配置文件跟踪"

# 批量移除已跟踪的无用文件
git rm --cached -r target/ .idea/
git commit -m "chore: 清理版本库中的编译产物和IDE配置"
```

### 7.4 全局.gitignore

```bash
# 避免每个项目重复配置
git config --global core.excludesfile ~/.gitignore_global
# 将上述模板写入 ~/.gitignore_global
```

## 9. 实战场景演练

### 场景1：多需求并行，暂存切换

```bash
# 正在开发用户模块，突然要紧急修复订单Bug

# 1. 保存当前进度
git stash push -m "用户模块-登录功能开发中"

# 2. 切换到hotfix
git switch main
git pull
git switch -c hotfix/order-bug

# 3. 修复Bug + 提交 + 推送 + 合并
# ... 修复操作 ...

# 4. 回到原开发
git switch feature/user-login
git stash pop
# 继续开发
```

### 场景2：精准筛选提交

```bash
# OrderService.java 里改了3个独立的功能，需要分3次commit

# 1. 交互式暂存第一个功能
git add -p OrderService.java     # 选y只暂存查询相关的hunk

# 2. 提交第一部分
git commit -m "feat: 新增订单多条件查询"

# 3. 重复add -p，逐个提交后续功能
git add -p OrderService.java     # 暂存导出逻辑
git commit -m "feat: 新增订单Excel导出"

git add -p OrderService.java     # 暂存批量操作
git commit -m "feat: 新增订单批量取消"
```

### 场景3：误删文件恢复

```bash
# 不小心删了UserService.java

# 恢复文件（从暂存区或HEAD）
git restore src/main/java/.../UserService.java

# 如果已经add了删除
git restore --staged src/main/java/.../UserService.java
git restore src/main/java/.../UserService.java

# 如果已经commit了删除
git revert <commit-that-deleted-the-file>
```

### 场景4：工作区彻底重置

```bash
# 放弃所有本地修改，回到干净状态
git reset --hard HEAD         # 放弃已跟踪文件的修改
git clean -fd                 # 删除所有未跟踪的文件和目录
# 现在工作区 = HEAD 完全一致
```
