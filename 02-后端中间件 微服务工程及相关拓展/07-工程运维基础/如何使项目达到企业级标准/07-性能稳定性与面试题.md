## 1. 性能压测体系

### 1.1 压测类型

| 类型 | 目的 | 工具 |
|------|------|------|
| 基准测试 | 单接口性能基线 | JMeter / wrk |
| 负载测试 | 预期流量下表现 | JMeter |
| 压力测试 | 找出崩溃点 | JMeter |
| 稳定性测试 | 长时间运行（7×24） | JMeter |
| 峰值测试 | 极限流量（秒杀） | Locust |

```
⚠️ 面试必答：
"压测五类——基准、负载、压力、稳定、峰值；
 上线前必须知道：性能基线、瓶颈位置、
 崩溃阈值（红线）。"
```

### 1.2 压测方法论

```
压测流程：
  ① 明确目标（预期 QPS/延迟 P99）
  ② 单接口压测 → 全链路压测
  ③ 逐步加压找拐点（吞吐不再线性增长 = 瓶颈）
  ④ 瓶颈定位（CPU/内存/IO/锁/DB）
  ⑤ 优化 → 回归压测

⚠️ 面试必答：
"压测核心 = 找拐点——
 吞吐不再随并发增长时即瓶颈；
 分层定位（应用/DB/网络/GC）。"
```

## 2. 容量规划

### 2.1 容量估算

```
容量估算公式：
  所需实例数 = 峰值 QPS × 单请求耗时 / 单实例并发能力

例：峰值 10000 QPS，单实例 500 QPS
  → 需要 20 台（含 20-30% 冗余）

⚠️ 面试必答：
"容量 = 峰值 QPS / 单实例能力 × 冗余系数——
 预留 20-30% 冗余应对流量波动；
 大促场景按历史峰值 × 增长系数。"
```

### 2.2 扩容策略

```
扩容两种：
  垂直扩容（升配置）：简单但有上限
  水平扩容（加实例）：⚠️ 需无状态（12-Factor）

弹性伸缩：
  K8s HPA（CPU/自定义指标自动扩缩）
  提前扩容（大促预案：提前 2 小时）

⚠️ 面试必答：
"水平扩容前提 = 无状态服务 +
 会话外置（Redis）；
 弹性伸缩用 HPA + 大促预案提前扩容。"
```

## 3. 容灾与高可用

### 3.1 高可用层级

```
高可用四层：
  ① 应用层：多实例（负载均衡）
  ② 数据层：主从复制 + 读写分离
  ③ 机房层：多可用区（同城双活）
  ④ 地域层：异地多活（容灾）

⚠️ 面试必答：
"高可用四层——应用多实例、
 数据主从、同城双活、异地容灾；
 每层解决不同故障域。"
```

### 3.2 数据容灾

```
数据容灾手段：
  备份：全量（每日）+ 增量（binlog）
  RPO（恢复点）：允许丢多少数据
  RTO（恢复时间）：多久恢复

级别：
  RPO=0：同步复制（同城双活）
  RPO≈0：半同步
  RPO>0：异步 + 备份

⚠️ 面试必答：
"容灾两指标——RPO（丢多少）、RTO（多快恢复）；
 备份是最后防线（全量 + binlog 增量）；
 同城双活 RPO≈0、异地容灾 RPO 分钟级。"
```

## 4. 稳定性保障

### 4.1 稳定性三板斧

```
稳定性核心手段：
  ① 限流：保护系统（令牌桶/漏桶/滑动窗口）
  ② 熔断：故障快速失败（Sentinel/Resilience4j）
  ③ 降级：非核心功能让路（核心可用）

⚠️ 面试必答：
"稳定性三板斧——限流（防超载）、
 熔断（防雪崩）、降级（保核心）；
 三者配合形成'自我保护'机制。"
```

### 4.2 雪崩与防护

```
雪崩链路：
  A 慢 → 线程池满 → 请求堆积 → 下游全挂 → 系统崩溃

防护：
  ① 超时控制（连接/读超时必设）
  ② 线程池隔离（Bulkhead）
  ③ 熔断器（错误率阈值打开）
  ④ 队列削峰（MQ 缓冲）

⚠️ 面试必答：
"防雪崩四件套——超时、隔离、
 熔断、削峰；
 雪崩本质是'慢请求占用资源'的
 级联放大。"
```

### 4.3 预案与演练

```
稳定性运营：
  ① 故障预案（常见故障处置文档）
  ② 混沌工程（主动注入故障验证韧性）
  ③ 演练常态化（定期故障演练）
  ④ 复盘改进（事后分析 → 改进项）

⚠️ 面试必答：
"稳定性是运营出来的——
 预案、混沌演练、复盘改进循环；
 '故障不可怕，可怕的是没预案没演练'。"
```

## 5. 企业级面试题精选

**Q1: 项目怎么达到企业级标准？**
```
八维自查——代码质量（规范/审查/门禁）、
工程化（模块/依赖/版本）、测试（金字塔/覆盖率）、
CI/CD（流水线/发布策略）、可观测（三支柱）、
安全（左移/密钥/漏洞）、性能（压测/容量）、
稳定性（限流熔断降级）。度量用 DORA + SLO。
```

**Q2: 上线前要做什么？**
```
压测（性能基线/瓶颈/红线）→ 容量规划 →
安全扫描（依赖/密钥）→ 监控就绪（指标/日志/告警）→
发布预案（回滚方案）→ 灰度发布（金丝雀）→
SLO 确认（错误预算）。
```

**Q3: 线上出故障怎么排查？**
```
① 指标看全局（错误率/延迟/资源）
② 链路定位（Trace 找到慢的环节）
③ 日志确认（traceId 查详情）
④ 三板斧（限流/熔断/降级）控制影响
⑤ 回滚（自动/手动）→ 复盘
```

**Q4: 怎么保证代码质量？**
```
规范（工具强制风格）+ Code Review（小 PR 必审）+
三层门禁（静态/测试覆盖率/部署检查）+
测试金字塔（单元 70%）+ 技术债务管理。
```

**Q5: CI/CD 流水线怎么设计？**
```
每次提交触发 → 分层反馈（<5 分钟编译静态、
15 分钟单元、60 分钟集成/E2E）→ 质量门禁 →
安全扫描 → 制品（签名 + SBOM）→ 发布
（蓝绿/金丝雀 + 自动回滚）。
```

**Q6: 可观测性怎么做？**
```
三支柱：Metrics（Prometheus + 黄金指标）、
Logs（JSON 结构化 + traceId）、
Traces（OTel + Jaeger）；
SLO 错误预算联动自动处置。
```

**Q7: 限流怎么做？**
```
令牌桶（Guava RateLimiter/Redis+Lua）、
漏桶（恒定速率）、滑动窗口（计数）；
分布式限流用 Redis + Lua（原子性）；
Sentinel 提供限流/熔断/降级一体。
```

**Q8: 怎么防雪崩？**
```
超时控制 + 线程池隔离 + 熔断器 +
MQ 削峰 + 限流保护；
核心链路降级、非核心让路。
```

**Q9: 数据库层面怎么保障？**
```
主从复制 + 读写分离（读多写少）、
连接池（HikariCP 调优）、
慢 SQL 治理（EXPLAIN + 索引）、
分库分表（数据量大时）、
备份（全量 + binlog，验证恢复）。
```

**Q10: 项目怎么度量好坏？**
```
DORA 四指标（部署频率/前置时间/失败率/恢复时长）+
SLO（可用性 99.9%）+ 错误预算 +
压测数据（QPS/P99）+ 监控告警覆盖度。
```

---

> 🎯 **核心要点**：性能稳定性 = **压测**（找拐点）+ **容量**（峰值/单实例能力 × 冗余）+ **容灾**（RPO/RTO + 备份）+ **三板斧**（限流/熔断/降级）+ **运营**（预案/演练/复盘）。企业级 = 八维体系 + 度量驱动 + 持续改进——本体系 00-07 即是完整自查清单。
