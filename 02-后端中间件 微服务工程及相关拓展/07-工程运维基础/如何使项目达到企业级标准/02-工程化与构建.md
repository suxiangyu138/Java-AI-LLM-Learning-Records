## 1. 多模块工程结构

### 1.1 标准多模块划分

```
企业级 Java 多模块（Maven/Gradle）：

parent-pom（父工程：依赖版本统一管理）
├─ common/          # 通用工具（无业务）
├─ domain/          # 领域模型/实体
├─ service-api/     # 服务接口（Dubbo 场景）
├─ service-impl/    # 服务实现
├─ web/             # 控制层/启动入口
└─ dao/             # 数据访问（可选聚合）

⚠️ 面试必答：
"多模块价值——依赖边界清晰（编译期约束）、
 复用（common 共享）、独立演进
 （api 模块可单独发布）。"
```

### 1.2 模块划分原则

```
划分依据（不是按层拆！）：
  ① 按领域/业务边界（用户模块/订单模块）
  ② 按复用性（common/api）
  ③ 按部署单元（可独立部署的拆出）

⚠️ 面试必答：
"模块划分按'业务边界 + 复用性'，
 不是机械按 controller/service 分层——
 分层是包内结构、模块是业务边界。"
```

## 2. 依赖管理

### 2.1 Maven 依赖管理

```xml
<!-- 父 POM：版本统一管理（dependencyManagement） -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-dependencies</artifactId>
            <version>3.3.5</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<!-- ⚠️ 子模块只声明 groupId/artifactId（版本继承父级） -->
```

### 2.2 依赖规范

```
依赖管理黄金规则：
  ① 版本集中在父 POM（dependencyManagement）
  ② 禁止传递依赖（显式声明自己用的）
  ③ 依赖锁文件（Maven 无原生锁 → enforcer 插件）
  ④ 漏洞扫描（OWASP DC / Trivy，CI 门禁）
  ⑤ 减少依赖数量（每个依赖都是攻击面）

⚠️ 面试必答：
"依赖管理四规则——版本集中、
 显式声明、漏洞扫描、最小化；
 依赖是供应链攻击入口（安全左移）。"
```

## 3. 版本控制规范

### 3.1 分支策略（2026 主流）

```
Trunk-Based（主干开发，2026 主流）：
  短生命周期特性分支（≤ 2 天）
  频繁合并主干
  Feature Flag 解耦"代码集成"与"功能发布"

对比 Git Flow：
  Trunk-Based：快节奏 CI/CD 配套
  Git Flow：版本节奏慢的遗留选择

⚠️ 面试必答：
"2026 主流是 Trunk-Based——小分支快速合
 主干，Feature Flag 控制功能上线；
 适合高频部署。Git Flow 适合低频发版。"
```

### 3.2 提交规范

```
Conventional Commits（语义化提交）：
  feat: 新功能
  fix: 修复
  refactor: 重构
  docs: 文档
  test: 测试
  chore: 杂项

feat(user): 添加用户登录接口
fix(order): 修复订单金额精度问题

⚠️ 面试必答：
"语义化提交的价值——自动生成 changelog、
 语义化版本（feat 升 minor/fix 升 patch）、
 代码审查可读性。"
```

### 3.3 语义化版本（SemVer）

```
版本格式：主版本.次版本.修订号
  主版本：不兼容变更
  次版本：向后兼容的新功能
  修订号：向后兼容的修复

⚠️ 面试必答：
"SemVer 三规则——主版本破坏性、
 次版本加功能、修订号修 bug；
 API 兼容性是版本递增的依据。"
```

## 4. 构建优化

### 4.1 构建时间优化

```
构建优化手段：
  ① 增量构建（只编译变更模块）
  ② 构建缓存（Maven 3.9+/Gradle 天然）
  ③ 并行构建（-T 1C 多线程）
  ④ 依赖缓存（CI 缓存 ~/.m2）
  ⑤ 跳过无关测试（增量检查）

⚠️ 面试必答：
"构建优化的核心是'缓存 + 增量'——
 CI 缓存依赖仓库、只构建变更模块、
 并行任务；目标 5 分钟内完成流水线。"
```

### 4.2 构建产物可信

```
制品可信三件套（2026 安全趋势）：
  ① 签名：cosign 签名镜像（防篡改）
  ② SBOM：syft 生成物料清单（依赖可追溯）
  ③ 扫描：Trivy 构建时漏洞扫描（零 CVE）

⚠️ 面试必答：
"构建产物可信 = 签名（谁构建的）+
 SBOM（依赖什么）+ 扫描（有无漏洞）——
 供应链安全的基础设施。"
```

## 5. 环境与配置管理

### 5.1 环境分层

```
环境四层：
  dev（开发）→ test（测试）→ staging（预发）→ prod（生产）

每环境独立配置（12-Factor 配置外置）：
  application-dev.yml / application-prod.yml

⚠️ 面试必答：
"环境四层（dev/test/staging/prod）
 + 配置外置（环境变量/配置中心）——
 代码一份、配置随环境注入。"
```

### 5.2 配置中心方案

| 方案 | 适用 |
|------|------|
| Spring Cloud Config | 微服务（Spring 生态） |
| Nacos | 国产主流（动态刷新） |
| Apollo | 携程开源（企业级） |
| 环境变量 + Docker | 简单场景 |

```
⚠️ 敏感配置（密码/密钥）：
  ❌ 配置文件硬编码
  ✅ 环境变量 / Vault / KMS
  ✅ 密文存储 + 解密运行时

⚠️ 面试必答：
"配置管理三原则——外置（环境变量）、
 分层（环境隔离）、加密（敏感信息）；
 生产密钥绝不出现在代码仓库。"
```
