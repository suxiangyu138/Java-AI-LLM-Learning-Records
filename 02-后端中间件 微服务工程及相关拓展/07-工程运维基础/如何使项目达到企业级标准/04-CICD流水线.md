## 1. CI/CD 是什么

```
CI（持续集成）：频繁合并代码 + 自动构建测试
CD（持续交付/部署）：自动部署到环境

价值流：
  提交 → CI（构建/测试/扫描）→ 制品 → CD（部署）→ 上线

⚠️ 面试必答：
"CI = 自动构建测试（每次提交）、
 CD = 自动部署（到环境/生产）；
 目标是'提交到上线的自动化闭环'。"
```

## 2. 流水线设计原则

### 2.1 分层反馈（2026）

```
流水线反馈分层：
  即时反馈（<5 分钟）：编译、基础静态检查
  快速反馈（5-15 分钟）：完整单元测试
  完整反馈（15-60 分钟）：集成/E2E/安全扫描

⚠️ 面试必答：
"流水线按反馈速度分层——
 快层（编译/静态）几分钟内给结果，
 慢层（E2E/扫描）后台跑；
 开发者等快层、慢层自动完成。"
```

### 2.2 设计五原则

```
① 每次提交触发（主干开发配套）
② 5 分钟内完成（快反馈）
③ 可靠（不因环境偶发失败）
④ 可并行（任务依赖分析）
⑤ 可缓存（依赖锁文件哈希作缓存键）

⚠️ 面试必答：
"流水线五原则——每次触发、快速、
 可靠、并行、缓存。
 性能目标：5 分钟内主流程完成。"
```

## 3. GitHub Actions 实践

### 3.1 标准流水线

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]        # ⚠️ 主干触发
  pull_request:             # PR 也触发

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # ① JDK 环境
      - name: Setup JDK
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '17'

      # ② 依赖缓存（关键优化）
      - name: Cache Maven
        uses: actions/cache@v3
        with:
          path: ~/.m2
          key: ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }}

      # ③ 质量门禁（静态检查 + 测试 + 覆盖率）
      - name: Verify
        run: mvn verify   # ⚠️ checkstyle/spotbugs/jacoco 绑定

      # ④ 漏洞扫描（安全左移）
      - name: Scan Dependencies
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: 'fs'

      # ⑤ 构建镜像
      - name: Build & Push Docker
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ${{ secrets.REGISTRY }}/app:${{ github.sha }}
```

### 3.2 流水线关键点

```
✅ 质量门禁失败即阻断（fail fast）
✅ 缓存依赖（构建时间减半）
✅ 安全扫描进流水线（左移）
✅ 制品带 commit sha 标签（可追溯）
✅ 多阶段 Docker 构建（镜像瘦身）
```

> 🎯 **要点**：CI 流水线 = 检出 → 缓存 → 门禁（静态+测试+覆盖率）→ 安全扫描 → 构建制品。每一步失败即阻断是"质量内建"的落地。

## 4. 发布策略

### 4.1 三种策略对比

| 策略 | 原理 | 回滚 | 适用 |
|------|------|:---:|------|
| 滚动发布 | 逐台替换 | 慢 | 无状态服务 |
| 蓝绿部署 | 两套环境切换 | ✅ 秒级 | 核心服务 |
| 金丝雀发布 | 小流量试运行（5%→100%） | ✅ | 高风险变更 |

```
蓝绿：旧（蓝）+ 新（绿）→ 切换流量 → 回滚 = 切回
金丝雀：5% → 20% → 50% → 100% 渐进放量（Argo Rollouts）

⚠️ 面试必答：
"三种发布——滚动（逐台）、蓝绿（整切）、
 金丝雀（渐进放量）；
 回滚速度：蓝绿 > 金丝雀 > 滚动。"
```

### 4.2 自动回滚

```
自动回滚触发条件：
  错误率超阈值（5xx 比例）
  延迟超 SLO（P99 恶化）
  健康检查失败

⚠️ 面试必答：
"自动回滚 = 指标驱动——
 错误率/延迟超阈值自动回滚到上一版本；
 与 SLO 错误预算联动（烧毁率触发）。"
```

## 5. 安全左移

### 5.1 左移思想

```
安全左移 = 安全检测从"上线前"移到"开发中"
  ① 开发期：IDE 插件 + 提交扫描
  ② CI 期：依赖漏洞 + 静态安全扫描
  ③ 构建期：镜像扫描（Trivy）+ 签名
  ④ 部署期：配置校验 + 密钥检查

⚠️ 面试必答：
"安全左移 = 漏洞发现越早修复越便宜——
 依赖扫描（Trivy）、密钥扫描（gitleaks）、
 静态安全（CodeQL）全部进流水线。"
```

### 5.2 左移工具链

| 阶段 | 工具 | 检查项 |
|------|------|--------|
| 提交 | gitleaks | 硬编码密钥 |
| CI | OWASP DC / Trivy | 依赖漏洞 |
| CI | CodeQL | 代码漏洞（注入/越权） |
| 构建 | cosign + syft | 签名 + SBOM |
| 部署 | Vault 校验 | 密钥管理 |

## 6. 流水线度量

### 6.1 DORA 指标落地

```
DORA 四指标（见 00 篇）在流水线中的度量：
  部署频率：流水线成功次数
  前置时间：提交 → 上线耗时
  失败率：流水线失败占比
  恢复时长：失败 → 恢复耗时

⚠️ 面试必答：
"DORA 指标从流水线数据自动采集——
 部署频率/前置时间/失败率/恢复时长
 四看板衡量交付效能。"
```

### 6.2 流水线健康度

```
流水线本身要监控：
  失败率趋势（上升 = 环境/测试问题）
  运行时长（变慢 = 缓存失效/测试膨胀）
  假失败（偶发失败破坏信任）

⚠️ 面试必答：
"'流水线的可靠性'本身要度量——
 假失败会摧毁团队对 CI 的信任，
 偶发失败必须根治。"
```

---

> 🎯 **核心要点**：CI/CD 体系 = **分层反馈**（快/慢反馈分层）+ **GitHub Actions**（缓存 + 门禁 + 扫描）+ **发布策略**（滚动/蓝绿/金丝雀 + 自动回滚）+ **安全左移**（依赖/密钥/镜像全流程扫描）+ **DORA 度量**（四指标看板）。"自动化一切可重复的事"是 CI/CD 的灵魂。
