## 1. 三种注入方式对比

| 方式 | 写法 | 优点 | 缺点 |
|------|------|------|------|
| **构造器注入** | `public OrderService(OrderDao dao)` | 不可变、必填依赖强制、无循环依赖隐患、易测试 | 依赖多时构造器参数膨胀 |
| Setter 注入 | `@Autowired public void setDao(OrderDao dao)` | 可选依赖、可重新配置 | 依赖可变、可被部分注入 |
| 字段注入 | `@Autowired private OrderDao dao` | 代码最少 | **不可测试、隐藏依赖、违反封装** |

```java
// ✅ 推荐：构造器注入（Spring 官方文档与 IDEA 均推荐）
@Service
public class OrderService {
    private final OrderDao dao;                    // final：不可变，必填
    private final PaymentService paymentService;

    public OrderService(OrderDao dao, PaymentService paymentService) {   // 依赖一目了然
        this.dao = dao;
        this.paymentService = paymentService;
    }
}

// ⚠️ 字段注入：能跑，但难以单测（无法 new 出半成品），依赖关系藏在注解里
@Service
public class OrderService {
    @Autowired
    private OrderDao dao;                          // 测试时只能靠反射注入
}
```

> 🎯 **核心要点**：**构造器注入 = 不可变 + 必填 + 可测**；字段注入把"依赖关系"藏进了私有字段，测试要反射、语义要猜。工程规范（阿里规约）也推荐构造器或 setter，字段注入是妥协写法。

## 2. 为什么构造器注入是首选

| 维度 | 构造器注入 | 字段注入 |
|------|:----------:|:--------:|
| 不可变性 | ✅ final 字段 | ❌ 可变 |
| 依赖可见性 | ✅ 签名即契约 | ❌ 注解藏匿 |
| 单元测试 | ✅ `new OrderService(mockDao)` | ❌ 反射/容器 |
| 必填校验 | ✅ 编译期/构造期 | ❌ 运行时才炸 |
| 循环依赖 | 构造器循环 → **立即报错**（好） | 字段循环 → 三级缓存绕开（隐藏问题） |
| 与 Spring 解耦 | ✅ 纯 Java 可测 | ❌ 依赖注解 |

**一个例外**：依赖**确实可选**时用 setter 注入（如可选的通知器），构造器注入可选依赖会逼着调用方传 null。

> 💡 构造器参数过多（>5 个）是设计信号——考虑拆分类或引入参数对象（见 `Java面向对象/06` Builder 讨论）。

## 3. @Autowired 装配规则与冲突解决

**@Autowired 的装配顺序**（`DefaultListableBeanFactory.resolveDependency`）：

```text
① 按类型找候选 Bean
② 多个候选 → 看 @Primary 标注（最高优先）
③ 无 @Primary → 看 @Priority（jakarta.annotation.Priority）
④ 仍多 → 按字段名/参数名匹配 Bean 名
⑤ 仍无法唯一 → NoUniqueBeanDefinitionException
```

```java
@Service
public class PayService {
    private final PayChannel channel;

    // 场景：两个实现 WeChatPay、Alipay 都 implements PayChannel
    public PayService(@Qualifier("alipay") PayChannel channel) {   // 方案 1：点名
        this.channel = channel;
    }
}

// 方案 2：@Primary 默认实现（如微信为主渠道）
@Component
@Primary
public class WeChatPay implements PayChannel { ... }

// 方案 3：@Qualifier 自定义限定符
@Qualifier("quick")
@Component
public class QuickPay implements PayChannel { ... }

// 方案 4（Spring 6.1+ 简化）：构造器参数直接用 @Qualifier 同义
public PayService(@Qualifier("alipay") PayChannel channel) { ... }  // 无需 @Autowired
```

**@Primary vs @Qualifier 的选择**：`@Primary` 定"默认候选"（注入点少时最省事）；`@Qualifier` 是"注入点显式点名"（精确、可读）。**两者可以并存**：默认走 Primary，特殊点用 Qualifier 覆盖。

> 🎯 **核心要点**：多实现注入的解决链 = **Primary → Priority → 名字 → 报错**。工程上推荐"一个 @Primary 默认 + 注入点 @Qualifier 点名"，避免靠字段名巧合匹配。

## 4. 泛型注入、集合注入与名字匹配

**泛型注入**：Spring 支持按泛型参数匹配——`Repository<User>` 注入时自动找 `UserRepository`：

```java
public interface BaseRepo<T> { }
@Component public class UserRepo implements BaseRepo<User> { }
@Component public class OrderRepo implements BaseRepo<Order> { }

@Service
public class QueryService {
    private final BaseRepo<User> userRepo;      // 按泛型 User 精确匹配 UserRepo

    public QueryService(BaseRepo<User> userRepo) {
        this.userRepo = userRepo;
    }
}
```

**集合注入**：注入同一类型的所有 Bean——策略模式的最佳搭档：

```java
@Service
public class PayRouter {
    private final Map<String, PayChannel> channels;    // 按 Bean 名注入所有实现
    private final List<PayChannel> allChannels;        // 按定义顺序注入列表

    public PayRouter(Map<String, PayChannel> channels) {
        this.channels = channels;
    }

    public PayChannel route(String name) {
        return channels.get(name);                     // wechat / alipay ...
    }
}
```

> 💡 `Map<String, X>` 的 key 是 Bean 名——这是"策略注册表"的官方标准姿势，替代手写 Map 注册。

## 5. @Resource vs @Autowired

| 维度 | @Autowired（Spring） | @Resource（Jakarta 规范） |
|------|:--------------------:|:------------------------:|
| 来源 | Spring 扩展 | JSR-250，`jakarta.annotation` |
| 匹配顺序 | **先按类型** → 再名字 | **先按名字** → 再类型 |
| 必填 | `required=true` 默认必填 | 默认必填 |
| 多实现 | 需 @Qualifier/@Primary | `@Resource(name="alipay")` 直接点名 |
| 通用性 | 仅 Spring | **可移植到其他容器**（CDI） |

```java
// @Resource：按名字优先 —— 多实现时直接点名
@Resource(name = "alipay")
private PayChannel channel;

// @Autowired：按类型优先 —— 需要辅助注解
@Autowired
@Qualifier("alipay")
private PayChannel channel;
```

**选择建议**：Spring 生态内两者皆可——**代码希望可移植（如规范敏感）用 @Resource，希望与 Spring 深度特性（泛型注入、集合注入）协同用 @Autowired**。现代 Spring 项目 @Autowired（构造器注入时不写注解）是主流。

> ⚠️ 迁移提示（Spring 7.0）：`javax.inject` 已被移除——`@Inject`/`@Named` 必须换 `jakarta.inject` 版本；`@Resource` 同理用 `jakarta.annotation.Resource`。

## 6. 循环依赖：成因、处理与规避

**循环依赖**：A 依赖 B，B 又依赖 A。Spring 通过**三级缓存**（源码机制，此处只讲工程结论，源码见 `Spring生态深度剖析/03`）能解决**大部分**场景：

| 场景 | 能否解决 | 原因 |
|------|:--------:|------|
| 字段/setter 注入的 singleton 循环 | ✅ | 三级缓存提前暴露半成品引用 |
| **构造器注入**循环 | ❌ | 构造器必须完整参数，无法暴露半成品 → `BeanCurrentlyInCreationException` |
| prototype 循环 | ❌ | 原型每次新建，无缓存可用 |
| @Async/@AOP 代理 Bean 的循环 | 部分 | 代理创建时机冲突，可能报错 |

```java
// ❌ 构造器循环依赖：启动即报错
@Service
public class A {
    public A(B b) { }                       // A 需要 B 的完整实例
}
@Service
public class B {
    public B(A a) { }                       // B 需要 A 的完整实例 —— 死锁
}

// ✅ 规避方案 1：改成字段注入（不推荐，掩盖设计问题）
// ✅ 规避方案 2：重构依赖方向 —— 把双向依赖拆成单向 + 事件/回调
// ✅ 规避方案 3：@Lazy 注入 —— 延迟到真正使用时才解析
@Service
public class A {
    private final B b;
    public A(@Lazy B b) { this.b = b; }     // 构造器注入 + 惰性代理
}
```

**工程判断**：循环依赖是**设计信号**——两个类互相依赖说明职责边界不清。**正确做法是重构**（提取公共依赖、事件解耦），而不是依赖三级缓存"恰好能跑"。

> 🎯 **核心要点**：面试答循环依赖的完整链条 = **成因（双向依赖）→ 三级缓存解决原理（提前暴露引用，见深度剖析系统）→ 不能解决的三类场景（构造器/prototype/代理）→ 工程态度（能避则避，重构优先）**。

## 7. 注入失败排查手册

| 报错 | 原因 | 排查步骤 |
|------|------|---------|
| `NoSuchBeanDefinitionException` | 没注册 | ① 包在扫描范围？② @Component 加了？③ @Bean 方法被执行？（@Conditional 是否满足） |
| `NoUniqueBeanDefinitionException` | 多候选 | ① 找同接口的实现类列表 ② 加 @Primary/@Qualifier |
| `BeanCurrentlyInCreationException` | 循环依赖 | ① 看 cause 里的链条 ② 改构造器注入为 @Lazy ③ 重构 |
| `UnsatisfiedDependencyException` | 依赖注入失败 | 看 cause（可能是被注入 Bean 的创建失败） |
| `NullPointerException`（注入为 null） | 注入没发生 | ① 自己 new 了对象（绕过容器）② static 上下文 ③ 类没被扫描 |
| 泛型注入不匹配 | 泛型擦除 | 检查基类泛型参数是否一致 |

**排查心法**：注入失败的**根因链条**——"A 注入失败"往往因为"B 创建失败"，B 失败因为"C 的初始化方法抛异常"——**永远看最底层的 cause**，不要停在第一层报错。
