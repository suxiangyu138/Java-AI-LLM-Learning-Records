## 1. 编程式 vs 声明式事务

| 维度 | 编程式（TransactionTemplate） | 声明式（@Transactional） |
|------|:----------------------------:|:------------------------:|
| 侵入 | 业务代码包裹事务逻辑 | 注解声明，零侵入 |
| 粒度 | 可精确控制每条语句 | 方法级（最小单位是方法） |
| 可读性 | 模板代码多 | 一行注解 |
| 灵活性 | 动态条件开启事务 | 固定属性 |
| 适用 | 事务边界需要动态控制 | **绝大多数业务** |

```java
// 声明式：一行注解
@Transactional
public void transfer(String from, String to, BigDecimal amount) {
    accountDao.debit(from, amount);
    accountDao.credit(to, amount);
    // 任一异常 → 全部回滚
}

// 编程式：适合"动态决定是否开启事务"的少数场景
@Service
public class BatchService {
    private final TransactionTemplate txTemplate;

    public void process(List<Order> orders) {
        for (Order o : orders) {
            txTemplate.execute(status -> {      // 每条记录一个事务，单条失败不影响其他
                saveOne(o);
                return null;
            });
        }
    }
}
```

> 🎯 **核心要点**：**@Transactional 的实现本质 = AOP 环绕通知**——进入方法开启事务、正常返回提交、异常回滚（见 05 模块代理模型）。所以**所有 AOP 的失效场景（自调用、final 方法）同样会让事务失效**。

## 2. @Transactional 属性全景

| 属性 | 默认值 | 说明 |
|------|--------|------|
| `propagation` | `REQUIRED` | 传播行为（见第 4 节） |
| `isolation` | `DEFAULT`（用数据库默认） | 隔离级别（见第 5 节） |
| `timeout` | -1（用数据库默认） | 事务超时秒数，超时抛异常并回滚 |
| `readOnly` | false | 只读优化（ORM 层跳过脏检查；**不能防止写**） |
| `rollbackFor` | RuntimeException/Error | **指定哪些异常回滚**（关键！） |
| `noRollbackFor` | 空 | 指定哪些异常不回滚 |
| `transactionManager` | 按类型找 | 多数据源时指定管理器 |

**rollbackFor 是最高频的配置**——默认只回滚 RuntimeException 和 Error，**受检异常默认不回滚**：

```java
// ❌ 受检异常不触发回滚（默认行为）
@Transactional
public void create(Order o) throws IOException {
    dao.insert(o);
    fileService.write(o);          // IOException —— 默认不回滚！数据已提交
}

// ✅ 显式声明回滚
@Transactional(rollbackFor = Exception.class)      // 所有异常都回滚
public void create(Order o) throws IOException { ... }

// ✅ 精确指定
@Transactional(rollbackFor = {IOException.class, OrderException.class})
```

> ⚠️ 面试必答：**为什么默认只回滚 RuntimeException？** 与"受检异常 = 可恢复"的设计哲学一致（见 `Java异常体系/02`）——Spring 认为受检异常（如文件不存在）可能"业务上可接受部分成功"，所以不自动回滚，由开发者用 rollbackFor 显式声明。**实际工程中绝大多数业务希望"任何异常都回滚"→ 写 `rollbackFor = Exception.class`**。

## 3. 七种事务失效场景

| # | 场景 | 根因 | 解法 |
|:-:|------|------|------|
| 1 | **同类内部调用**（`this.method()`） | 绕过代理（见 05 模块第 6 节） | 拆分 Bean / 注入代理 / TransactionTemplate |
| 2 | **方法不是 public** | 代理只拦截 public 方法 | 改 public |
| 3 | **final 类 / final 方法** | CGLIB 无法子类化 | 去掉 final（Spring 7.0 前尤其注意） |
| 4 | **异常被吞掉**（try-catch 后不抛） | 事务看不到异常，以为成功 | 不吞异常 / 手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` |
| 5 | **受检异常**未声明 rollbackFor | 默认不回滚受检异常 | `rollbackFor = Exception.class` |
| 6 | **自研注解失效**：@Transactional 加在自定义注解上，或类被多次代理（顺序问题） | 代理链路被破坏 | 检查代理顺序、@Order |
| 7 | **多数据源/分布式事务** | 单事务管理器只管一个数据源 | 分布式事务方案（Seata 等，见 Spring全家桶/14） |

```java
// 场景 4 演示：吞异常 = 事务假装成功
@Transactional
public void update(Order o) {
    try {
        dao.update(o);
    } catch (Exception e) {
        log.error("更新失败", e);          // ❌ 不抛出 → 事务提交，数据不一致
    }
}

// 场景 1 演示：自调用（最高频）
@Transactional
public void pay(String id) { ... }

public void checkout(String id) {
    this.pay(id);        // ❌ 绕过代理，事务失效
}
```

> 🎯 **核心要点**：失效场景的**总根因只有两个**——**① 调用没走代理（自调用/非 public/final）② 异常没让事务看到（吞掉/受检异常）**。记住这个总纲，七种场景不用死背。

## 4. 传播行为七种语义

| 传播行为 | 语义 | 场景 |
|---------|------|------|
| `REQUIRED`（默认） | 有事务加入，无则新建 | 绝大多数业务 |
| `REQUIRES_NEW` | **总是新开事务**，挂起外层 | 日志记录（失败不影响主事务）、独立任务 |
| `SUPPORTS` | 有则加入，无则不建 | 只读查询 |
| `NOT_SUPPORTED` | 挂起事务，非事务执行 | 事务中调用非事务资源 |
| `MANDATORY` | 必须已有事务，否则抛异常 | 强事务上下文（内部方法校验） |
| `NEVER` | 必须无事务，否则抛异常 | 禁止事务的场景 |
| `NESTED` | 嵌套事务（**保存点**，JDBC 支持时） | 大事务内部分段可独立回滚 |

**REQUIRED vs REQUIRES_NEW vs NESTED**（面试最常问的三兄弟）：

```java
// REQUIRED：A 和 B 同一个事务 —— B 回滚则 A 也回滚（同生共死）
@Transactional public void a() { dao.a(); b(); }
@Transactional(propagation = Propagation.REQUIRED) public void b() { throw new RuntimeException(); }
// 结果：a、b 全部回滚

// REQUIRES_NEW：B 独立事务 —— B 回滚不影响 A 已做的部分
@Transactional public void a() { dao.a(); b(); }
@Transactional(propagation = Propagation.REQUIRES_NEW) public void b() { throw new RuntimeException(); }
// 结果：B 回滚，A 的 a() 操作已提交（B 挂起 A 事务后独立提交/回滚）

// NESTED：B 是 A 的保存点 —— B 回滚只回滚到保存点
@Transactional public void a() { dao.a(); b(); }
@Transactional(propagation = Propagation.NESTED) public void b() { throw new RuntimeException(); }
// 结果：B 回滚到保存点；若外层随后也回滚则整体回滚；外层提交但 B 已回滚
```

**注意事项**：

1. **REQUIRES_NEW 的自调用同样失效**——必须走代理（拆分 Bean）；
2. `NOT_SUPPORTED` 挂起事务后，外层事务的锁（行锁）**不会释放**——只是代码不参与事务；
3. 传播行为失效的排查：先确认调用链走了代理。

> 🎯 **核心要点**：三兄弟的记忆锚点——**REQUIRED 同生共死、REQUIRES_NEW 各自独立、NESTED 保存点局部回滚**。日志/审计记录独立提交用 REQUIRES_NEW，批量分段处理用 NESTED。

## 5. 隔离级别与并发问题

**四个隔离级别**（对应 SQL 标准，与数据库实现相关）：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---------|:----:|:---------:|:----:|------|
| READ_UNCOMMITTED | ❌ 可能 | 可能 | 可能 | 几乎不用 |
| READ_COMMITTED | ✅ 防 | 可能 | 可能 | **多数数据库默认**（Oracle/PG/MySQL） |
| REPEATABLE_READ | ✅ | ✅ 防 | MySQL 可防（MVCC） | **MySQL 默认** |
| SERIALIZABLE | ✅ | ✅ | ✅ | 全串行，性能最差 |

**三个并发问题**：

```java
// 脏读：读到未提交的数据（事务 A 改了未提交，事务 B 读到了）
// 不可重复读：同一查询两次结果不同（期间被别的事务提交修改）
// 幻读：范围查询两次行数不同（期间被别的事务插入新行）

@Transactional(isolation = Isolation.REPEATABLE_READ)
public Order getForUpdate(String id) {
    return orderDao.findById(id);
    // 高并发扣库存等场景：配合 SELECT ... FOR UPDATE 行锁
}
```

**配置建议**：隔离级别**默认用数据库默认**（`isolation = DEFAULT`）——除非明确需要（如读已提交 + 悲观锁），不要随意提升到 SERIALIZABLE（性能代价大）。**分布式系统下，隔离级别的"绝对保证"不存在**——最终一致性靠业务设计（幂等、乐观锁、对账）。

> 💡 **乐观锁 vs 悲观锁**（事务配合）：悲观锁 `SELECT ... FOR UPDATE`（行锁，冲突多时好）；乐观锁 version 字段 + `UPDATE ... WHERE version = ?`（冲突少时好）。二者都是"事务 + 锁"的组合，面试常与隔离级别一起问。

## 6. 事务管理器的选择

```java
// 事务管理器 = 具体数据访问技术的适配器（统一接口，切换实现不影响业务代码）
public interface PlatformTransactionManager {
    TransactionStatus getTransaction(TransactionDefinition definition);
    void commit(TransactionStatus status);
    void rollback(TransactionStatus status);
}

// 常用实现
DataSourceTransactionManager      // JDBC / MyBatis / JdbcTemplate
JpaTransactionManager             // JPA / Hibernate
JtaTransactionManager             // 分布式（JTA，已过时，用 Seata 等）
// Spring Boot 自动装配：单一数据源时自动选择对应事务管理器
```

**多数据源场景**：`@Transactional(transactionManager = "orderTxManager")` 指定管理器；跨数据源事务属于**分布式事务**——用 Seata（AT/TCC）、本地消息表等方案（详见 `Spring全家桶/14-分布式事务-Seata.md`），**单库事务管理管不了分布式**。

> 🎯 **核心要点**：事务的完整机制链 = **@Transactional（声明）→ AOP 环绕通知（代理拦截）→ PlatformTransactionManager（适配器）→ 具体数据源（连接/锁）**——面试答事务题时按这条链展开，既有广度又有深度。
