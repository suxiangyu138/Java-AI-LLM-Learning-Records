## 1. 基础与索引

**Q1: B+Tree 相比 B 树和红黑树的优势是什么？**

| 对比 | 结论 |
|------|------|
| vs 红黑树 | 红黑树是二叉树，1000 万行树高约 24 层；B+Tree 只需 3-4 层（每层一次磁盘 IO） |
| vs B 树 | B+Tree 非叶子节点只存 key（不存数据），一页存更多 key → 树更矮；叶子有双向链表 → 范围查询高效 |

```
⚠️ 核心表述："树高 = IO 次数。B+Tree 用'非叶子只存 key'
 把 1000 万行的树高压到 3-4 层——这是它胜出的全部原因。"
```

**Q2: 聚簇索引和二级索引的区别？回表是什么？**

```
聚簇索引（主键）：叶子存整行数据，表按主键组织
二级索引：叶子存主键值
回表：二级索引查到主键 → 再走聚簇索引取整行

⚠️ 面试必答："回表 = 两次 B+Tree 查找；
 覆盖索引（查询列全在二级索引中）可免回表。"
```

**Q3: 最左前缀原则？联合索引 (a,b,c) 哪些条件能用？**

| 查询条件 | 索引使用 |
|---------|---------|
| WHERE a=1 | ✅ |
| WHERE a=1 AND b=2 | ✅ |
| WHERE a=1 AND b=2 AND c=3 | ✅ 完全匹配 |
| WHERE b=2 | ❌ 跳过了 a |
| WHERE a=1 AND c=3 | ⚠️ 只用 a（c 用不上） |
| WHERE a=1 AND b>2 AND c=3 | ⚠️ a、b 用（范围阻断 c） |

**Q4: 覆盖索引为什么快？Using index 和 Using index condition 区别？**

```
覆盖索引：查询列全在索引中 → 免回表（Extra: Using index）
ICP（索引下推）：索引中其他条件在存储引擎层先过滤
  → 减少回表次数（Extra: Using index condition）

⚠️ 面试必答："覆盖索引是'查都不用查表'；
 ICP 是'少回表'——级别不同，覆盖更高。"
```

**Q5: 为什么建议自增主键而不是 UUID？**

```
自增：新数据追加到 B+Tree 右侧 → 页分裂最少
UUID：随机插入已有页 → 频繁页分裂 + 碎片

⚠️ 面试必答："页分裂是插入性能杀手——
 自增主键顺序插入几乎不分裂；
 分布式场景的 UUID 权衡见 08 全局 ID 生成。"
```

## 2. 事务与锁

**Q6: MVCC 如何实现可重复读？ReadView 的生成时机和判断规则？**

```
快照读（普通 SELECT）：
  RR：事务第一次 SELECT 生成 ReadView，之后复用
  RC：每次 SELECT 都生成新 ReadView

ReadView 判断（沿 undo 版本链回溯）：
  ① DB_TRX_ID < up_limit_id → 已提交，可见
  ② DB_TRX_ID >= low_limit_id → 未开始，不可见
  ③ 中间区间 → 查 trx_ids：在列表（未提交）不可见，否则可见

⚠️ 面试必答："RR 的'可重复读'来自 ReadView 只生成一次；
 RC 每次新 ReadView 所以不可重复读。"
```

**Q7: MySQL 默认隔离级别？为什么 RR 而不是 RC？**

```
默认 REPEATABLE READ（SQL 标准默认是 RC）
历史原因：早期 binlog 基于 STATEMENT 格式，
  RR 下当前读+Next-Key 更安全（避免主从不一致）
现状：8.0 默认 ROW binlog 后 RC 也安全，
 很多大厂业务用 RC（更少锁冲突）

⚠️ 面试必答："RR 是历史选择（binlog 一致性），
 现在 ROW 格式下 RC 足够——默认 RR 但可改 RC。"
```

**Q8: Next-Key Lock 如何解决幻读？快照读/当前读差异？**

```
Next-Key Lock = Record Lock + Gap Lock（左开右闭）
  锁住 (10, 20] 区间 → 阻止插入 10-20 之间的行 → 防幻读

差异：
  快照读（普通 SELECT）：MVCC 解决幻读（看到旧快照）
  当前读（FOR UPDATE/UPDATE/DELETE）：Next-Key Lock 防幻读

⚠️ 面试必答："幻读只在当前读场景需要锁解决——
 快照读靠 MVCC、当前读靠 Next-Key。"
```

**Q9: 死锁怎么产生？MySQL 如何处理？**

```
产生：两个事务互相持有对方需要的锁（循环等待）
处理：
  ① 等待图检测（默认）：检测到环 → 回滚代价小的事务
  ② 锁等待超时：innodb_lock_wait_timeout（默认 50s）

预防：
  ① 事务按相同顺序访问表/行
  ② 缩短事务长度（不做外部调用）
  ③ 合理索引减少锁范围

⚠️ 面试必答："死锁四条件（互斥/持有等待/不可剥夺/循环）
 在 MySQL 中通过'等待图 + 回滚'打破循环等待。"
```

**Q10: Gap Lock 只在什么隔离级别下存在？为什么？**

```
只在 REPEATABLE READ（RR）下存在
原因：RC 不需要防幻读（每次新 ReadView），
 间隙锁只服务于 RR 的当前读防幻读

⚠️ 面试必答："Gap Lock 是 RR 的专属——
 RC 不防幻读所以无间隙锁，锁冲突也更少。"
```

## 3. SQL 优化

**Q11: 一条 SQL 很慢，排查思路？**

```
① 先分"偶尔慢 vs 一直慢"
   偶尔慢：刷脏页、等待 MDL 锁、InnoDB 锁等待
   一直慢：进入 ②
② EXPLAIN 分析：type/key/rows/Extra
   type 低于 range → 索引问题
   rows 大 → 选择性差/数据量大
   Using filesort/temporary → 排序/分组问题
③ 数据量过大 → 分库分表/归档

⚠️ 面试必答："先定性（偶尔/持续）再定量（EXPLAIN）——
 偶尔慢查锁与刷盘、持续慢查执行计划。"
```

**Q12: EXPLAIN 的 type 值？至少达到什么级别？**

```
system > const > eq_ref > ref > range > index > ALL

⚠️ 面试必答："优化目标至少 range，力争 ref/const；
 ALL 全表扫描是红线。"
```

**Q13: count(*) / count(1) / count(列) 的区别？**

```
count(*)：统计行数，MySQL 选最短二级索引扫描（最快）
count(1)：等价 count(*)
count(列)：忽略 NULL，且不能走最短索引优化（较慢）

⚠️ 面试必答："count(*) = count(1) > count(列)；
 别用 count(列) 数行数（NULL 会被忽略）。"
```

**Q14: 如何优化大分页？**

```
① 延迟关联：子查询先取主键（覆盖索引）再回表
② 游标分页：WHERE id > 上一页最大 id（推荐）

⚠️ 面试必答："LIMIT 100000, 20 要读 100020 行——
 游标分页（id 比较）与延迟关联是标准解法。"
```

**Q15: 用了索引还是慢？可能原因？**

```
① 回表太多（索引筛选不够 → 大量回表）
② 查询列多（非覆盖索引 → 全列回表）
③ 索引区分度低（如性别列）
④ 数据量太大（索引也扛不住 → 分库分表）
⑤ 隐式类型转换/函数包裹（实际没走索引）

⚠️ 面试必答："'用了索引还慢'先查 Extra——
 Using index（覆盖）还是大量回表；
 再查 rows 与区分度。"
```

## 4. 架构

**Q16: 主从复制原理？延迟原因与解决？**

```
原理（三线程）：
  主库 Dump 线程读 binlog → 从库 IO 线程写 relay log
  → 从库 SQL 线程回放

延迟原因：
  ① 从库 SQL 单线程回放（旧版）→ 5.7+ 并行复制
  ② 从库硬件差
  ③ 大事务回放慢 → 拆分大事务
  ④ 从库慢查询占资源

⚠️ 面试必答："延迟核心 = 主库并发写 vs 从库串行回放；
 并行复制（slave_parallel_workers）是主解。"
```

**Q17: binlog 三种格式？**

| 格式 | 说明 | 优缺点 |
|------|------|--------|
| STATEMENT | 记录 SQL | 日志小；非确定函数（NOW()）主从不一致 |
| ROW（8.0 默认） | 记录行变化 | 安全确定；日志大 |
| MIXED | 自动判断 | 折中 |

```
⚠️ 面试必答："8.0 默认 ROW——确定性优先；
 STATEMENT 的 NOW()/UUID() 问题是经典坑。"
```

**Q18: 分库分表的难点？**

```
① 跨分片查询：JOIN/聚合需应用层合并（尽量按分片键查询）
② 全局 ID：雪花算法/号段模式（不能用单库自增）
③ 分布式事务：两阶段提交/XA/最终一致性（TCC/消息）
④ 扩容：一致性哈希/二次分片（取模扩容全量重排）

⚠️ 面试必答："分片键选择决定一切——
 查询不按分片键 → 广播全分片；
 全局 ID 用雪花（趋势递增 + 无单点）。"
```

**Q19: 半同步复制解决了什么问题？**

```
异步复制：主库提交即返回 → 主库崩溃可能丢数据
半同步：至少一个从库写入 relay log 才返回
  → 主库崩溃不丢已确认事务（牺牲一点延迟）

⚠️ 面试必答："半同步 = 性能换安全——
 解决'异步复制主库崩溃丢数据'；
 需要插件 rpl_semi_sync_master。"
```
