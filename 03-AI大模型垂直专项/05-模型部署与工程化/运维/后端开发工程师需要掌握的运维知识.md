## 一、Linux 基础与常用命令

### 1.1 为什么后端必须懂 Linux

| 场景 | 说明 |
|---|---|
| 服务部署 | 99% 的后端服务运行在 Linux 服务器上 |
| 问题排查 | 线上故障需要上服务器查日志、看进程、调 JVM |
| 环境搭建 | 中间件（MySQL、Redis、Nginx、ES）全部跑在 Linux |
| 性能分析 | top/free/iostat/netstat 是性能分析的标配工具 |

### 1.2 必备命令清单

| 类别 | 命令 | 用途 |
|---|---|---|
| **文件操作** | `ls` `cd` `cp` `mv` `rm` `find` `tar` `scp` | 日常文件管理、远程传输 |
| **文本处理** | `cat` `head` `tail` `grep` `awk` `sed` `wc` `sort` `uniq` | 日志分析、配置查看 |
| **进程管理** | `ps` `top` `htop` `kill` `nohup` `&` `jobs` `fg` `bg` | 查看/管理 Java 进程 |
| **网络排查** | `curl` `ping` `telnet` `nc` `ss` `netstat` `tcpdump` `lsof` | 端口连通性、抓包分析 |
| **系统信息** | `df` `du` `free` `uptime` `uname` `dmesg` `iostat` `vmstat` | 磁盘、内存、CPU 状态 |
| **权限管理** | `chmod` `chown` `useradd` `sudo` `visudo` | 文件权限、用户管理 |

### 1.3 高频实用命令示例

```bash
# 查看 Java 进程及 JVM 参数
ps aux | grep java

# 实时查看日志文件尾部
tail -f /var/log/app.log

# 过滤日志中的 ERROR 并统计数量
grep "ERROR" app.log | wc -l

# 按时间段过滤日志
sed -n '/2026-07-13 10:00/,/2026-07-13 11:00/p' app.log

# 查看某个端口被哪个进程占用
lsof -i :8080

# 查看磁盘使用情况
df -h

# 查看目录大小
du -sh /var/log/*

# 查找大于 100MB 的文件
find / -type f -size +100M 2>/dev/null

# 统计 Nginx 访问日志 Top 10 IP
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10

# 查看 TCP 连接状态分布
ss -tan | awk '{print $1}' | sort | uniq -c
```

### 1.4 文本处理三剑客：grep、awk、sed

| 工具 | 核心能力 | 典型场景 |
|---|---|---|
| **grep** | 正则匹配过滤 | 从海量日志中筛选关键行 |
| **awk** | 按列提取与计算 | 提取日志第 N 列、统计聚合 |
| **sed** | 流编辑替换 | 批量替换配置、提取时间范围 |

```bash
# grep：过滤包含 "OutOfMemoryError" 的日志
grep -n -A 5 -B 5 "OutOfMemoryError" app.log

# awk：统计每个接口的平均响应时间（假设第5列是耗时）
awk '{sum[$4]+=$5; count[$4]++} END {for(k in sum) print k, sum[k]/count[k]}' access.log

# sed：批量替换配置文件中的端口
sed -i 's/port=8080/port=8081/g' application.properties
```

## 二、Shell 脚本编写

### 2.1 为什么后端要会写 Shell

服务启停脚本、定时清理日志、批量部署、健康检查——这些日常运维任务靠 Shell 脚本自动化，效率提升 10 倍。

### 2.2 常用脚本模板

#### 服务启动脚本

```bash
#!/bin/bash
# 启动 Java 服务

APP_NAME="my-app"
JAR_FILE="/opt/app/${APP_NAME}.jar"
LOG_FILE="/opt/app/logs/${APP_NAME}.log"
JVM_OPTS="-Xms2g -Xmx2g -XX:+UseG1GC -XX:+HeapDumpOnOutOfMemoryError"

# 检查是否已运行
pid=$(ps aux | grep "${JAR_FILE}" | grep -v grep | awk '{print $2}')
if [ -n "$pid" ]; then
    echo "[WARN] ${APP_NAME} 已在运行，PID: ${pid}"
    exit 1
fi

# 启动服务
nohup java ${JVM_OPTS} -jar ${JAR_FILE} --spring.profiles.active=prod \
    > ${LOG_FILE} 2>&1 &

echo "[INFO] ${APP_NAME} 启动中，PID: $!"

# 等待启动完成（轮询健康检查接口）
for i in {1..60}; do
    sleep 1
    if curl -s http://localhost:8080/actuator/health | grep -q "UP"; then
        echo "[INFO] ${APP_NAME} 启动成功"
        exit 0
    fi
done

echo "[ERROR] ${APP_NAME} 启动超时，请检查日志: ${LOG_FILE}"
exit 1
```

#### 日志清理脚本

```bash
#!/bin/bash
# 清理 N 天前的日志文件

LOG_DIR="/opt/app/logs"
RETENTION_DAYS=7

find ${LOG_DIR} -name "*.log.*" -type f -mtime +${RETENTION_DAYS} -exec rm -f {} \;
find ${LOG_DIR} -name "*.gz" -type f -mtime +${RETENTION_DAYS} -exec rm -f {} \;

echo "[INFO] 已清理 ${RETENTION_DAYS} 天前的日志"
```

#### 批量部署脚本

```bash
#!/bin/bash
# 批量部署到多台服务器

SERVERS=("10.0.1.101" "10.0.1.102" "10.0.1.103")
APP_NAME="my-app"
JAR_FILE="target/${APP_NAME}.jar"
REMOTE_PATH="/opt/app/"

for server in "${SERVERS[@]}"; do
    echo "[INFO] 正在部署到 ${server}..."

    # 上传 JAR 包
    scp ${JAR_FILE} root@${server}:${REMOTE_PATH}

    # 重启服务
    ssh root@${server} "cd ${REMOTE_PATH} && sh restart.sh"

    # 等待服务启动（避免并发重启）
    sleep 10

    # 健康检查
    if curl -s --max-time 5 "http://${server}:8080/actuator/health" | grep -q "UP"; then
        echo "[OK] ${server} 部署成功"
    else
        echo "[FAIL] ${server} 部署失败，请立即排查！"
    fi
done
```

### 2.3 Shell 脚本最佳实践

| 实践 | 说明 |
|---|---|
| `set -euo pipefail` | 遇到错误/未定义变量/管道失败立即退出 |
| 日志带时间戳 | `echo "[$(date '+%Y-%m-%d %H:%M:%S')] message"` |
| 幂等设计 | 重复执行不会产生副作用 |
| 参数校验 | 检查必需参数是否传入 |
| 返回码规范 | 成功 `exit 0`，失败 `exit 1` |

## 三、Docker 容器化

### 3.1 核心概念

| 概念 | 说明 | 类比 |
|---|---|---|
| **镜像（Image）** | 应用的只读模板 | 类（Class） |
| **容器（Container）** | 镜像的运行实例 | 对象（Instance） |
| **Dockerfile** | 构建镜像的蓝图 | 构建脚本 |
| **Docker Compose** | 多容器编排 | 一键启停全套环境 |
| **Registry** | 镜像仓库 | Maven 仓库 / NPM Registry |

### 3.2 Dockerfile 最佳实践（Java 项目）

```dockerfile
# 多阶段构建，减小最终镜像体积
FROM maven:3.8-openjdk-17 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

FROM eclipse-temurin:17-jre-alpine
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
WORKDIR /app
COPY --from=builder /app/target/*.jar app.jar
USER appuser
EXPOSE 8080

# 优雅关闭
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
    CMD wget -q -O - http://localhost:8080/actuator/health || exit 1

ENTRYPOINT ["java", "-XX:+UseContainerSupport", "-XX:MaxRAMPercentage=75.0", \
            "-jar", "app.jar"]
```

> **多阶段构建**可将最终镜像体积从 600MB+ 压缩到 200MB 以内，显著加快拉取和部署速度。

### 3.3 Docker Compose 编排全套开发环境

```yaml
version: '3.8'
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root123
      MYSQL_DATABASE: my_app
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      retries: 5

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    command: redis-server --appendonly yes

  app:
    build: .
    ports:
      - "8080:8080"
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_started
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://mysql:3306/my_app
      SPRING_REDIS_HOST: redis

volumes:
  mysql_data:
  redis_data:
```

| 命令 | 用途 |

## 四、CI/CD 流水线

### 4.1 核心概念

| 概念 | 说明 |
|---|---|
| **持续集成（CI）** | 代码提交后自动构建、测试，快速发现问题 |
| **持续交付（CD）** | 通过测试的代码自动部署到 staging 环境 |
| **持续部署（CD）** | 通过测试的代码自动部署到生产环境 |

### 4.2 GitLab CI 流水线示例（Java 项目）

```yaml
stages:
  - build
  - test
  - docker-build
  - deploy-staging
  - deploy-prod

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"
  DOCKER_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

# 缓存 Maven 依赖，加速构建
cache:
  key: ${CI_COMMIT_REF_SLUG}
  paths:
    - .m2/repository/

# 阶段1：编译
build:
  stage: build
  image: maven:3.8-openjdk-17
  script:
    - mvn compile
  only:
    - main
    - merge_requests

# 阶段2：单元测试 + 覆盖率
unit-test:
  stage: test
  image: maven:3.8-openjdk-17
  script:
    - mvn test
    - mvn jacoco:report
  coverage: '/Total.*?([0-9]{1,3})%/'   # 从日志提取覆盖率
  artifacts:
    reports:
      junit: target/surefire-reports/*.xml
      coverage_report:
        coverage_format: cobertura
        path: target/site/jacoco/jacoco.xml

# 阶段3：构建 Docker 镜像
docker-build:
  stage: docker-build
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker build -t $DOCKER_IMAGE .
    - docker push $DOCKER_IMAGE
  only:
    - main

# 阶段4：部署到 staging
deploy-staging:
  stage: deploy-staging
  script:
    - ssh staging-server "docker pull $DOCKER_IMAGE && docker-compose up -d"
    - echo "验证 staging 环境..."
    - curl -f http://staging.example.com/actuator/health || exit 1
  only:
    - main

# 阶段5：生产部署（手动触发）
deploy-prod:
  stage: deploy-prod
  script:
    - ssh prod-server "docker pull $DOCKER_IMAGE && docker-compose up -d"
  when: manual                # 手动触发
  only:
    - main
```

### 4.3 GitHub Actions 流水线示例

```yaml
name: Java CI/CD

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
          cache: maven
      - run: mvn test
      - run: mvn jacoco:report

  docker-build-and-push:
    needs: build-and-test
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
```

### 4.4 CI/CD 最佳实践

| 实践 | 说明 |
|---|---|
| **构建缓存** | 缓存 Maven/Gradle 依赖，避免每次全量下载 |
| **多阶段构建** | 编译 → 测试 → 镜像构建 → 部署，阶段失败不进入下一阶段 |
| **蓝绿部署 / 滚动发布** | 零停机部署，出问题可秒级回滚 |
| **生产部署手动触发** | 避免自动部署到生产，加一道人工确认 |
| **健康检查 + 自动回滚** | 部署后自动验证健康状态，异常自动回滚 |

## 五、Nginx 反向代理与负载均衡

### 5.1 Nginx 在后端体系中的角色

```
客户端 → Nginx（入口网关）→ 后端服务集群（多实例）
                  ├── 静态资源（直接返回）
                  ├── API 路由（反向代理）
                  ├── WebSocket 代理
                  └── SSL 卸载
```

### 5.2 核心配置示例

```nginx
# 基础反向代理 + 负载均衡
upstream backend_cluster {
    # 负载均衡策略：默认轮询，可选 least_conn / ip_hash
    least_conn;
    server 10.0.1.101:8080 weight=3 max_fails=3 fail_timeout=30s;
    server 10.0.1.102:8080 weight=2 max_fails=3 fail_timeout=30s;
    server 10.0.1.103:8080 weight=1 backup;   # 备用节点
}

server {
    listen 80;
    server_name api.example.com;

    # 限流：每秒最多 100 个请求
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=100r/s;
    limit_req zone=api_limit burst=50 nodelay;

    # 客户端请求体大小限制
    client_max_body_size 10m;

    # 反向代理到后端集群
    location /api/ {
        proxy_pass http://backend_cluster;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        # 超时设置
        proxy_connect_timeout 5s;
        proxy_read_timeout 30s;
        proxy_send_timeout 30s;
    }

    # 静态资源直接返回
    location /static/ {
        root /var/www;
        expires 30d;
        add_header Cache-Control "public, immutable";
    }

    # 健康检查端点（K8s / 负载均衡器探测用）
    location /health {
        return 200 "OK";
        add_header Content-Type text/plain;
    }
}

# HTTPS 配置
server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    location / {
        proxy_pass http://backend_cluster;
    }
}
```

### 5.3 负载均衡策略对比

| 策略 | 指令 | 适用场景 |
|---|---|---|
| **轮询**（默认） | 无需配置 | 服务器性能一致 |
| **加权轮询** | `weight=N` | 服务器性能不均 |
| **最少连接** | `least_conn` | 长连接服务（WebSocket） |
| **IP Hash** | `ip_hash` | 需要 session 粘性 |
| **随机** | `random` | 简单场景 |

### 5.4 常见问题排查

| 问题 | 排查命令/方法 |
|---|---|
| 502 Bad Gateway | 检查后端服务是否启动、端口是否监听 |
| 504 Gateway Timeout | 增大 `proxy_read_timeout`，排查后端慢接口 |
| 499 Client Closed | 客户端主动断开，检查前端超时设置 |
| 静态资源不更新 | 检查 `expires` 配置，加版本号参数 |

```bash
# 排查命令
nginx -t                          # 检查配置文件语法
nginx -s reload                   # 热重载配置
tail -f /var/log/nginx/error.log  # 查看错误日志
tail -f /var/log/nginx/access.log # 查看访问日志
```

## 六、日志管理与分析

### 6.1 日志体系架构

```
应用日志 → Filebeat/Logback Appender → Kafka（缓冲）→ Logstash（解析）→ Elasticsearch（存储）→ Kibana（可视化）
```

### 6.2 Java 日志最佳实践

```xml
<!-- logback-spring.xml：生产环境日志配置 -->
<configuration>
    <!-- 控制台输出（JSON 格式，便于日志平台解析） -->
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder class="net.logstash.logback.encoder.LogstashEncoder"/>
    </appender>

    <!-- 文件输出：按日期 + 大小滚动 -->
    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>/var/log/app/app.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
            <fileNamePattern>/var/log/app/app.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
            <maxFileSize>200MB</maxFileSize>
            <maxHistory>30</maxHistory>
            <totalSizeCap>10GB</totalSizeCap>
        </rollingPolicy>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} [%X{traceId}] - %msg%n</pattern>
        </encoder>
    </appender>

    <!-- 错误日志单独输出 -->
    <appender name="ERROR_FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>/var/log/app/error.log</file>
        <filter class="ch.qos.logback.classic.filter.ThresholdFilter">
            <level>ERROR</level>
        </filter>
        <!-- rollingPolicy 同上 -->
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
        <appender-ref ref="FILE"/>
        <appender-ref ref="ERROR_FILE"/>
    </root>
</configuration>
```

### 6.3 日志规范

| 规范 | 说明 |
|---|---|
| **必须包含 traceId** | 全链路追踪，快速串联一次请求的所有日志 |
| **关键节点打日志** | 接口入参/出参、外部调用、异常捕获、定时任务 |
| **敏感信息脱敏** | 手机号/身份证/密码/Token 必须脱敏或禁止输出 |
| **日志分级合理** | DEBUG（开发调试）、INFO（关键流程）、WARN（可恢复异常）、ERROR（需人工介入） |
| **结构化输出** | 生产环境输出 JSON 格式，便于 ELK/云平台解析和检索 |

### 6.4 常用日志排查技巧

```bash
# 按 traceId 追踪全链路日志
grep "traceId=abc123" app.log | sort -k1

# 按时间范围筛选
awk '/2026-07-13 10:00/,/2026-07-13 11:00/' app.log

# 统计 Top 10 异常类型
grep "ERROR" app.log | awk -F' - ' '{print $NF}' | sort | uniq -c | sort -rn | head -10

# 查看某个接口的慢请求（假设日志中记录了耗时）
grep "costTime" app.log | awk -F'costTime=' '{if($2>1000) print $0}' | head -20
```

## 七、监控与告警

### 7.1 后端必须监控的指标

| 维度 | 指标 | 工具 |
|---|---|---|
| **JVM** | 堆内存、GC 频率与耗时、线程数 | Micrometer + Prometheus |
| **接口** | QPS、P95/P99 延迟、错误率 | Prometheus + Grafana |
| **中间件** | DB 连接池、Redis 命中率、MQ 积压 | 中间件自带的 Exporter |
| **系统** | CPU、内存、磁盘、网络 IO | Node Exporter |
| **业务** | 订单量、支付成功率、注册转化率 | 自定义 Metrics |

### 7.2 Spring Boot 集成 Prometheus

```xml
<!-- pom.xml -->
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

```yaml
# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics
  metrics:
    tags:
      application: ${spring.application.name}
      environment: ${spring.profiles.active}
    export:
      prometheus:
        enabled: true
  endpoint:
    health:
      show-details: always
      probes:
        enabled: true    # K8s liveness / readiness 探针
```

### 7.3 Grafana 告警规则示例

```yaml
# Prometheus 告警规则
groups:
  - name: backend-alerts
    rules:
      # QPS 突增
      - alert: HighQPS
        expr: rate(http_server_requests_seconds_count[1m]) > 1000
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.application }} QPS 过高"
          description: "当前 QPS: {{ $value }}，过去1分钟均值超过 1000"

      # 错误率飙升
      - alert: HighErrorRate
        expr: rate(http_server_requests_seconds_count{status=~"5.."}[5m]) /
              rate(http_server_requests_seconds_count[5m]) > 0.05
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.application }} 错误率超过 5%"

      # JVM 堆内存使用率过高
      - alert: HighHeapUsage
        expr: jvm_memory_used_bytes{area="heap"} /
              jvm_memory_max_bytes{area="heap"} > 0.85
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "{{ $labels.application }} JVM 堆内存使用率 > 85%"

      # 服务宕机
      - alert: ServiceDown
        expr: up{job="spring-boot"} == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.instance }} 服务已宕机"
```

### 7.4 告警分级与通知

| 级别 | 说明 | 通知方式 | 响应时间 |
|---|---|---|---|
| **P0 - 紧急** | 服务宕机、核心功能不可用 | 电话 + 企微/钉钉 + 短信 | 5 分钟内 |
| **P1 - 严重** | 功能降级、错误率飙升 | 企微/钉钉群 + 短信 | 15 分钟内 |
| **P2 - 警告** | 资源使用率过高、慢接口增多 | 企微/钉钉群 | 1 小时内 |
| **P3 - 通知** | 非紧急信息、日常报表 | 邮件 / 群消息 | 工作时间处理 |

## 八、数据库运维基础

### 8.1 MySQL 运维必知

#### 慢查询分析与优化

```sql
-- 查看慢查询配置
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';

-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;   -- 超过 1 秒记为慢查询

-- 查看最近慢查询
-- 使用 mysqldumpslow 工具
-- mysqldumpslow -s t -t 10 /var/log/mysql/slow.log   # Top 10 耗时最长
```

```sql
-- 查看当前连接数与最大连接数
SHOW STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';

-- 查看正在执行的事务（排查锁等待）
SELECT * FROM information_schema.INNODB_TRX\G

-- 查看锁等待
SELECT * FROM information_schema.INNODB_LOCK_WAITS\G

-- 杀掉长时间未提交的连接
SELECT CONCAT('KILL ', id, ';') 
FROM information_schema.processlist 
WHERE TIME > 300 AND Command != 'Sleep';
```

#### 备份与恢复

```bash
# 全量备份
mysqldump -h 127.0.0.1 -u root -p --single-transaction \
    --routines --triggers --events my_database > backup_$(date +%Y%m%d).sql

# 恢复
mysql -h 127.0.0.1 -u root -p my_database < backup_20260713.sql

# 定时备份脚本（crontab）
# 0 2 * * * /opt/scripts/mysql_backup.sh >> /var/log/backup.log 2>&1
```

### 8.2 Redis 运维必知

```bash
# 连接 Redis
redis-cli -h 127.0.0.1 -p 6379 -a password

# 查看内存使用
redis-cli INFO memory | grep used_memory_human

# 查看慢查询
redis-cli SLOWLOG GET 10

# 查看大 Key（内存占用 Top 10）
redis-cli --bigkeys

# 查看连接数
redis-cli INFO clients | grep connected_clients
```

| 常见问题 | 排查方向 | 解决方案 |
|---|---|---|
| 内存不足 | `INFO memory` 查看 `used_memory` 占比 | 设置过期时间、淘汰策略、扩容 |
| 慢查询 | `SLOWLOG GET` 分析 | 避免 KEYS *、改用 SCAN、优化大 Key |
| 缓存穿透 | 大量请求查询不存在的 Key | 布隆过滤器、缓存空值 |
| 缓存雪崩 | 大量 Key 同时过期 | 过期时间加随机值、多级缓存 |
| 缓存击穿 | 热点 Key 过期瞬间高并发 | 互斥锁、永不过期 + 异步更新 |

### 8.3 数据库连接池配置（HikariCP）

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20          # 最大连接数（根据 CPU 核数调整）
      minimum-idle: 5                # 最小空闲连接
      idle-timeout: 600000           # 空闲连接超时 10min
      max-lifetime: 1800000          # 连接最大存活 30min
      connection-timeout: 30000      # 获取连接超时 30s
      leak-detection-threshold: 10000 # 连接泄漏检测 10s
```

## 九、云服务基础与故障排查

### 9.1 云服务核心概念

| 概念 | 说明 | 对应产品 |
|---|---|---|
| **计算** | 虚拟机/容器/Serverless | ECS/CVM、ACK/TKE、函数计算 |
| **存储** | 对象存储/块存储/文件存储 | OSS/COS、云盘、NAS |
| **网络** | VPC/负载均衡/CDN/NAT | 专有网络、SLB/CLB、CDN |
| **数据库** | 关系型/缓存/搜索 | RDS、Redis、Elasticsearch |
| **安全** | WAF/安全组/SSL 证书 | Web 应用防火墙、安全组 |

### 9.2 故障排查思路

```
故障发生 → 确认范围（单节点 / 集群 / 全站）→ 查看监控面板
→ 检查最近变更（发布 / 配置 / 数据库变更）→ 查看日志
→ 定位根因 → 制定修复方案 → 执行修复 → 复盘总结
```

### 9.3 常见线上故障

| 故障 | 典型表现 | 排查步骤 |
|---|---|---|
| **CPU 飙升** | 响应变慢、超时 | `top` 定位进程 → `top -Hp pid` 定位线程 → `jstack` 分析线程 → 转十六进制查找代码 |
| **内存泄漏** | 频繁 Full GC、最终 OOM | `jmap -heap pid` 查看堆 → `jmap -dump:format=b,file=heap.hprof pid` → MAT/JProfiler 分析 |
| **死锁** | 线程阻塞、请求卡住 | `jstack pid \| grep "deadlock"` 或 `jstack pid > thread.txt` 全文搜索 |
| **数据库连接池耗尽** | 获取连接超时 | 检查慢 SQL → 检查事务未提交 → 确认连接池配置 |
| **磁盘满** | 写入失败、服务异常 | `df -h` 定位 → `du -sh /*` 逐层排查 → 清理大文件/日志 |
| **网络问题** | 连接超时、间歇性不可用 | `ping`/`telnet`/`curl` 测连通 → `tcpdump` 抓包 → 检查安全组/防火墙 |

### 9.4 JVM 线上诊断工具速查

| 命令 | 用途 |
|---|---|
| `jps -l` | 列出所有 Java 进程 |
| `jstack <pid>` | 打印线程堆栈（排查死锁、CPU 高） |
| `jmap -heap <pid>` | 查看堆内存配置和使用 |
| `jmap -histo <pid> \| head -20` | 查看内存中对象 Top 20 |
| `jmap -dump:format=b,file=heap.hprof <pid>` | 导出堆 Dump（线上慎用，会 STW） |
| `jstat -gc <pid> 1000 10` | 每秒查看 GC 情况，共 10 次 |
| `jcmd <pid> VM.flags` | 查看 JVM 启动参数 |
| `arthas` | 阿里开源 Java 诊断神器（无需重启，动态排查） |

### 9.5 Arthas 快速上手

```bash
# 下载并启动 Arthas
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar           # 选择目标 Java 进程

# 常用命令
dashboard                           # 实时面板（线程、内存、GC）
thread -n 5                         # 查看 CPU 最高的 5 个线程
thread -b                           # 查看死锁
watch com.example.MyService process '{params, returnObj, throwExp}' -x 3
                                    # 监控方法入参/返回值/异常
trace com.example.MyService process # 追踪方法调用链路及耗时
jad com.example.MyService           # 反编译 class 文件
logger --name com.example --level debug  # 动态修改日志级别（无需重启）
```

### 知识体系总览


| 阶段 | 内容 | 目标 |
