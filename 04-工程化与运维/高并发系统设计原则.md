# 高并发系统设计原则

## 核心指标

| 指标 | 含义 | 举例 |
|------|------|------|
| QPS | 每秒请求数 | 10000 QPS |
| RT | 响应时间 | P99 < 100ms |
| 并发数 | 同时处理的请求数 | 1000 并发 |
| 可用性 | 正常运行时间比例 | 99.99%（全年 52 分钟不可用） |

## 设计原则

### 1. 缓存先行

离用户越近的缓存，性能越好：
```
浏览器缓存 → CDN → Nginx 缓存 → Redis → 本地缓存
```
- 静态资源走 CDN
- 热点数据放 Redis
- 极热点数据放本地缓存（Caffeine）

### 2. 池化复用

- **连接池**：数据库、Redis、HTTP 客户端都要用连接池
- **线程池**：异步任务、批量处理用线程池，不要 `new Thread()`
- **对象池**：大开销的对象复用（如 Protobuf Builder）

### 3. 异步解耦

- 非核心逻辑异步化：注册后发欢迎短信 → 消息队列异步处理
- 响应式编程：IO 密集型接口用 WebFlux 提升吞吐
- 批量合并：多条 SQL 合并为一条，多次 Redis 调用合并为一次 Pipeline

### 4. 削峰填谷

- **消息队列**：突发请求不直接打 DB，先进队列消峰
- **限流**：Sentinel / RateLimiter 控制接口并发
- **降级**：高峰期关闭非核心功能
- **熔断**：下游不可用时快速失败，不耗死自己

### 5. 读写分离 + 分库分表

- **一主多从**：写走主库，读走从库
- **ShardingSphere**：分库分表中间件
- **冷热分离**：热数据放 Redis/SSD，历史数据归档

## 常见方案速查

| 问题 | 方案 | 工具 |
|------|------|------|
| 热点数据 | 多级缓存 | Caffeine + Redis |
| 大量请求 | 限流 | Sentinel / Guava RateLimiter |
| 秒杀超卖 | 分布式锁 + lua 脚本 | Redisson + Redis |
| 接口响应慢 | 异步 + 缓存预热 | RocketMQ + 定时任务 |
| DB 扛不住 | 读写分离 / 分表 | ShardingSphere |
| 服务雪崩 | 熔断 + 降级 | Sentinel / Resilience4j |
| 重复下单 | 幂等设计（唯一索引 + Redis） | MySQL + Redis |
| 数据一致性 | 最终一致 + 补偿 + 对账 | MQ + 定时任务 |

## 实践分层

**初级阶段（校招必备）：**
- 会用 Redis 做缓存
- 会用消息队列异步处理
- 知道布隆过滤器的原理和使用场景
- 会写基础的分布式锁
- 理解幂等和如何实现

**进阶阶段：**
- 设计秒杀系统（限流 + Redis 库存预扣 + MQ 异步下单）
- 缓存一致性方案选型（先删缓存再更新 DB、先更新 DB 再删缓存、双删）
- 多级缓存架构设计
- 分库分表方案落地（ShardingSphere）

## 面试常见高并发题

**Q: 如何设计一个秒杀系统？**
A: 9 层保护：
1. 前端：按钮置灰 + 防重复点击
2. CDN：静态资源走 CDN
3. 网关：IP 限流
4. Nginx：并发连接数限制
5. 服务层：Sentinel 接口限流
6. Redis：预减库存（lua 原子操作）
7. MQ：下单请求入队消峰
8. DB：扣减最终库存
9. 对账：发现超卖回补

**Q: 缓存和数据库一致性怎么保证？**
A: 经典方案 — 更新数据库后删除缓存（Cache Aside）。复杂场景用 Canal 监听 binlog 异步更新缓存。

**Q: 亿级流量下怎么扩容？**
A: 横向扩展（加机器）→ 无状态服务随意扩 → 数据库读写分离 → 分库分表 → 多级缓存 → CDN
