# Redis 实战核心知识点
---

## 一、Redis 核心架构与选型
### 1. 核心特性与适用边界
| 特性 | 实战解读 |
|------|----------|
| 单线程模型 | 核心命令串行执行，无锁竞争，性能瓶颈不在CPU，而在内存和网络IO |
| 内存存储 | 数据默认在内存，读写纳秒级，是缓存场景的核心优势 |
| 多数据结构 | 不止K-V，Hash/Set/ZSet等是业务组件化的关键 |
| 原子命令 | 单条命令/Lua脚本天然原子，轻松实现锁、限流、计数 |

✅ **适用场景**：缓存、分布式锁、限流、计数器、社交关系链、时间线、热搜、消息队列
❌ **不适用场景**：大数据持久存储、复杂事务、海量长文本、多表关联查询

## 二、数据结构实战应用（项目全覆盖）
### 1. String（字符串）
**核心用途**：缓存、计数器、验证码、分布式锁、配置
**实战示例**：
```java
// 缓存用户信息，1小时过期
redisTemplate.opsForValue().set("user:1001", user, 3600, TimeUnit.SECONDS);
// 自增计数器（点赞/访问量）
redisTemplate.opsForValue().increment("article:1001:like", 1);
```
**优化点**：数字类型用`incr`/`incrby`，Redis会自动用`int`编码，内存极小。

### 2. Hash（哈希）
**核心用途**：存储结构化数据（用户资料、商品信息）
**实战示例**：
```java
// 存用户信息，比多个String更省key和内存
redisTemplate.opsForHash().put("user:1001", "name", "张三");
redisTemplate.opsForHash().put("user:1001", "age", 20);
```
**优化点**：小Hash用`ziplist`编码，内存远低于多个独立String。

### 3. List（列表）
**核心用途**：轻量消息队列、操作日志、浏览历史
**实战示例**：
```java
// 消息队列（FIFO）
redisTemplate.opsForList().rightPush("order:queue", orderId);
String task = redisTemplate.opsForList().leftPop("order:queue");
```
**注意**：不支持消费确认，适合简单场景，生产级队列建议用RabbitMQ/Kafka。

### 4. Set（集合）
**核心用途**：去重、关注/粉丝关系、黑名单、UV统计
**实战示例**：
```java
// 关注关系
redisTemplate.opsForSet().add("follow:1001", "1002");
// 黑名单
redisTemplate.opsForSet().add("blacklist:ip", "192.168.1.1");
```
**优化点**：纯数字Set会用`intset`编码，内存极低。

### 5. ZSet（有序集合）
**核心用途**：排行榜、时间线、限流、前缀搜索
**实战示例**：
```java
// 动态时间线（按时间倒序）
redisTemplate.opsForZSet().add("timeline:1001", feedId, System.currentTimeMillis());
// 热搜榜（按搜索次数排序）
redisTemplate.opsForZSet().incrementScore("hot:search", "redis教程", 1);
```
**关键特性**：支持字典序匹配（`rangeByLex`），可实现搜索联想。

### 6. 高级结构（项目拓展必备）
- **Bitmap**：亿级签到、日活统计，1亿用户仅需12.5MB内存
- **HyperLogLog**：超低内存UV统计，误差率0.81%，亿级UV仅需12KB
- **Geo**：地理位置、附近的人（社交网络拓展功能）

## 三、缓存三大问题与解决方案（面试高频）
### 1. 缓存穿透
**问题**：恶意请求不存在的key，直接打到数据库，压垮DB
**解决方案**：
- 布隆过滤器拦截非法请求
- 对不存在的key设置空值缓存（短TTL）

### 2. 缓存击穿
**问题**：热点key过期瞬间，大量并发请求直接打DB
**解决方案**：
- 互斥锁（分布式锁）：同一时间只允许一个请求查DB
- 热点key永不过期（后台异步更新）
- 提前预热热点数据

### 3. 缓存雪崩
**问题**：大批量key同时过期，或Redis宕机，导致所有请求打DB
**解决方案**：
- 过期时间加随机偏移，避免同时过期
- 缓存集群+哨兵，避免单点故障
- 多级缓存（本地Caffeine + Redis）

## 四、分布式锁实战（生产级）
### 核心要求
- 互斥性：同一时间只有一个客户端持有锁
- 防死锁：自动过期释放锁
- 防误删：只能由持有锁的客户端释放
- 高性能：低延迟、高并发

### 标准实现（Lua脚本+原子命令）
```lua
-- 加锁（原子命令）
SET lock:order:123 uuid NX EX 10

-- 解锁（Lua脚本防误删）
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```
### 进阶优化
- 看门狗续期：守护线程定期延长锁过期时间，避免业务未完成锁提前释放
- Redlock：多节点部署，避免单节点故障导致锁失效

## 五、限流实战（高并发防护）
### 1. 计数器限流（简单高效）
```java
// 1分钟最多访问100次
Long count = redisTemplate.opsForValue().increment("limit:ip:127.0.0.1");
if (count == 1) {
    redisTemplate.expire("limit:ip:127.0.0.1", 60, TimeUnit.SECONDS);
}
if (count > 100) {
    throw new RuntimeException("访问频繁");
}
```

### 2. 滑动窗口限流（更精准）
结合ZSet实现，避免计数器的“边界突刺问题”。

## 六、Lua脚本实战（Redis高级特性）
### 核心优势
- 原子执行：多条命令打包执行，避免竞态条件
- 减少网络开销：一次请求完成复杂逻辑
- 逻辑封装：服务端实现复杂业务，避免客户端多次交互

### 经典场景
1. 安全释放分布式锁（防误删）
2. 原子限流（滑动窗口）
3. 批量数据操作（如社交关系链同步）
4. 条件执行（库存扣减前校验）

### 关键注意事项
- 脚本执行时间过长会阻塞Redis，禁止编写耗时脚本
- key必须通过`KEYS`数组传递，不能硬编码（Cluster模式路由需要）
- 脚本必须是纯函数，禁止使用`RANDOM`/`TIME`等不确定函数

## 七、Redis 持久化与高可用
### 1. 持久化方案
| 方案 | 原理 | 适用场景 |
|------|------|----------|
| RDB 快照 | 定时全量二进制快照 | 冷备份、快速恢复 |
| AOF 日志 | 记录每一条写命令 | 数据安全要求高的场景 |
| 混合持久化 | AOF+RDB结合 | 生产环境推荐 |

### 2. 高可用架构
- **主从复制**：读写分离，提升查询性能
- **Sentinel哨兵**：自动监控、故障自动切换，解决单点故障
- **Cluster集群**：16384个哈希槽分片，突破单机内存和并发上限

## 八、性能优化与内存管理
### 1. 性能优化
- 短key设计：减少key长度，降低内存和网络开销
- 批量操作：使用Pipeline批量执行命令，减少网络往返
- 避免大key：超大集合、超长字符串会阻塞Redis，拆分或裁剪
- 热点key优化：本地缓存+分片，避免单点打爆

### 2. 内存管理
- 设置`maxmemory`限制，结合`allkeys-lru`淘汰策略
- 业务数据强制加TTL，避免数据永久占用内存
- 利用底层编码优化：优先存储数字ID、短字符串，触发`intset`/`ziplist`压缩编码

## 十、高频面试题核心解答
1. **为什么Redis单线程还这么快？**
   - 纯内存操作，无磁盘IO开销
   - IO多路复用，单线程处理万级并发连接
   - 单线程无锁竞争，上下文切换开销低

2. **Redis和MySQL的一致性如何保证？**
   - 先更新DB，再删缓存（或先删缓存再更新DB）
   - 定时任务/消息队列异步更新缓存
   - 缓存加短TTL，自动过期重建

3. **如何解决Redis大key问题？**
   - 拆分大key为多个小key
   - 限制集合大小，定期裁剪
   - 改用其他存储方式（如MySQL存长文本）
