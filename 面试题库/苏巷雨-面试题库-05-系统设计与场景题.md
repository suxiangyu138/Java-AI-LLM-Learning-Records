## 一、高频系统设计题

### 1. 设计一个秒杀系统

**需求**：100W 人抢 1W 件商品，不能超卖，响应快，数据库不能挂。

**全链路架构**（SuGuangMall实战：QPS 2000+、JMeter压测、Redis Lua原子库存预占→确认扣减→超时回滚、RabbitMQ死信延迟队列15min关单、Seata AT分布式事务、ShardingSphere订单按user_id分16表、Caffeine+Redis多级缓存）：

```
┌────────────────────────────────────────────────────┐
│ 第一层：前端                                          │
│  - 按钮防重复点击（点击后灰掉 + 倒计时）              │
│  - 动态验证码（拉长用户请求时间）                     │
│  - CDN 静态资源                                      │
│  - 秒杀开始前才露出链接（防脚本）                     │
├────────────────────────────────────────────────────┤
│ 第二层：Nginx 反向代理                                │
│  - limit_req_zone：单 IP 每秒最多 10 次              │
│  - 拒绝大部分流量（假设 100W 人 → 过滤到 10W）        │
│  - 动静分离：静态页面走 CDN                           │
├────────────────────────────────────────────────────┤
│ 第三层：Gateway 网关（SuGuangMall实测）                │
│  - JWT 鉴权：未登录/无效 token 直接拒绝               │
│  - Sentinel 网关流控：QPS 超阈值(2000+)→ 快速失败     │
│  - Nacos服务发现 → 请求路由到 Seckill Service          │
├────────────────────────────────────────────────────┤
│ 第四层：Seckill Service                              │
│                                                      │
│  ① 用户维度限流（Sentinel 热点参数，SuGuangMall实测） │
│    同一用户 1 秒内最多 1 次请求，QPS压测2000+零超卖    │
│                                                      │
│  ② Redis 预减库存（Lua 原子脚本，SuGuangMall实测）    │
│    -- 三步原子操作：预占库存→确认扣减→超时回滚         │
│    if redis.call('get', 'stock:123') > 0 then        │
│        redis.call('decr', 'stock:123')               │
│        return 1  -- 抢购成功（预占库存成功）           │
│    else                                              │
│        return 0  -- 已售罄                            │
│    end                                               │
│    -- 支付超时 → 死信队列触发Lua回滚 incr 恢复库存     │
│                                                      │
│  ③ 抢购成功 → 异步处理                                │
│    返回"抢购成功，请尽快支付"（不等订单创建完成）      │
│    发 MQ 消息：{userId, productId, seckillId}        │
├────────────────────────────────────────────────────┤
│ 第五层：MQ 异步削峰                                    │
│                                                      │
│  OrderQueue Consumer：                                │
│    - 创建订单（MySQL 写入）                           │
│    - 扣减实际库存（SET stock = stock - 1）            │
│                                                      │
│  DelayQueue（死信延迟队列，SuGuangMall实测）：          │
│    - 15 分钟超时未支付 → 关单 + 库存回滚              │
│    - Lua 脚本 incr + 标记订单取消                     │
│    - Seata AT分布式事务保证订单/库存/MQ最终一致性      │
├────────────────────────────────────────────────────┤
│ 第六层：数据层（SuGuangMall实测）                      │
│  - Redis Cluster：库存缓存 + 用户抢购标记             │
│  - Caffeine本地L1缓存 + Redis L2缓存（多级缓存架构）   │
│  - MySQL + ShardingSphere 分库分表（订单按user_id分16表）│
│  - 读写分离（查询走从库）                             │
├────────────────────────────────────────────────────┤
│ 第七层：监控                                          │
│  - Prometheus + Grafana 秒杀大盘                      │
│  - 订单创建速率、库存消耗、MQ 积压                    │
└────────────────────────────────────────────────────┘
```

**SuGuangMall实战验证数据**：
- **QPS**: 秒杀接口峰值 2000+（JMeter 5并发线程压测验证）
- **库存准确率**: 100%（零超卖，Redis Lua原子脚本+Seata AT分布式事务双保险）
- **关单时效**: 15分钟超时未支付订单100%自动关闭+库存回滚（RabbitMQ死信延迟队列）
- **订单分表**: ShardingSphere按user_id分16张物理表，单表数据量从千万降至百万级
- **缓存层级**: Caffeine本地一级缓存（毫秒级响应）+ Redis分布式二级缓存
- **技术栈验证**: Spring Cloud Alibaba (Nacos+Gateway+Sentinel+Seata) + Dubbo + ShardingSphere 全链路实测通过

**关键设计决策**：

| 决策 | 为什么不这样 | 为什么这样 |
|------|-----------|-----------|
| Redis 预减库存而不是 DB（SuGuangMall实测） | DB 行锁 → 串行化 → QPS 极低 | Redis 单线程 + Lua 原子操作 → QPS 10W+，实测2000+无超卖 |
| 异步下单而不是同步（SuGuangMall实测） | 同步等 DB 写入 → 响应慢 → 超时 | 抢到立即返回，订单异步创建，MQ削峰填谷 |
| 延迟队列关单（SuGuangMall实测） | 定时任务扫表 → 性能差且延迟 | MQ 延迟消息准时触发，15min精准关单 |
| 前端验证码 | 无验证码 → 脚本直接发请求 | 增加请求间隔（通用最佳实践） |

**扩展性思考**：
- 如果 Redis 也扛不住 → 多级库存（本地库存分段 + Redis + DB）
- 如果 MQ 积压 → 动态扩容 Consumer 实例
- 如果需要更公平 → 引入排队机制（预排队 → 获得资格 → 下单）

### 2. 设计一个短链接系统（如 t.cn）

**需求**：长 URL → 短 URL，访问短链跳转，QPS 10W+。

```
┌─────────────────────────────────────────────────┐
│ 1. 短链生成                                      │
│                                                  │
│ 方案：分布式 ID（雪花算法，趋势递增）               │
│       → Base62 编码（0-9a-zA-Z = 62 个字符）      │
│       → 如 ID=12345 → Base62 = "3d7"             │
│                                                  │
│ 为什么不用 Hash？                                 │
│   - MD5 → 太长了                                 │
│   - Hash 冲突需要处理（加随机盐重试）              │
│   - 分布式 ID 趋势递增、无冲突                    │
│                                                  │
│ 唯一性保证：                                      │
│   - 长 URL 先查是否已生成过（Redis + MySQL）       │
│   - 已存在 → 直接返回已有的短链                    │
│   - 不存在 → 分配新 ID → 生成短链 → 存储           │
├─────────────────────────────────────────────────┤
│ 2. 存储设计                                      │
│                                                  │
│ MySQL：                                          │
│   id BIGINT PRIMARY KEY                          │
│   short_code VARCHAR(8) UNIQUE INDEX             │
│   long_url TEXT                                  │
│   created_at TIMESTAMP                           │
│   expired_at TIMESTAMP                           │
│                                                  │
│ Redis：                                          │
│   key: short_code → value: long_url              │
│   热点短链缓存（如热门活动链接）                    │
│   TTL = expired_at - now                         │
├─────────────────────────────────────────────────┤
│ 3. 跳转流程                                      │
│                                                  │
│ 用户访问 t.cn/3d7                                 │
│    ↓                                             │
│ ① CDN / Nginx 层 → 直接到短链服务                  │
│    ↓                                             │
│ ② 查 Redis 缓存 "url:3d7"                        │
│    hit → 302 跳转（返回 Location 头）              │
│    miss ↓                                        │
│ ③ 查 MySQL WHERE short_code = '3d7'              │
│    hit → 写回 Redis → 302 跳转                   │
│    miss → 404                                    │
│    ↓                                             │
│ ④ 异步 +1 访问计数（发 MQ，不阻塞跳转）            │
├─────────────────────────────────────────────────┤
│ 4. 高并发优化                                    │
│                                                  │
│  - CDN 302 缓存（减少回源）                       │
│  - Redis 预加载热点短链                            │
│  - 布隆过滤器：快速判断短链是否存在                 │
│  - 短码预生成池：提前生成一批短码放内存中           │
│                                                  │
│ 5. 扩展                                          │
│  - 自定义后缀（VIP 功能）                         │
│  - 多域名支持（防微信封域名）                      │
│  - 统计报表（来源、地域、设备）                    │
└─────────────────────────────────────────────────┘
```

> **项目锚点**：SuGuangMall商品分享短链场景 —— 用户生成商品推广链接时，将含参长URL压缩为短链，存储映射关系到Redis + MySQL，布隆过滤器防恶意短链攻击。

### 3. 设计一个实时排行榜系统

**需求**：千万用户，实时更新积分排名，支持查看 Top-100 和个人排名。

> **项目锚点**：Flavor Dash外卖平台 —— 首页展示当日餐厅销量排行榜。Redis ZSet key=`restaurant:daily:rank:{date}`，score=当日订单量，ZREVRANGE取Top-10展示首页，定时任务每小时将排行持久化到MySQL，避免Redis宕机丢失数据。

```
方案选择：Redis Sorted Set（ZSet）

┌─ 数据结构 ───────────────────────────────────────┐
│ ZADD ranking {score} {userId}                     │
│                                                  │
│ 积分 = score，支持实时更新                        │
│ 底层：跳表 + 哈希表，O(log n) 更新，O(log n) 查询 │
│                                                  │
│ Top 100：ZREVRANGE ranking 0 99 WITHSCORES        │
│ 个人排名：ZREVRANK ranking {userId} (0-based)      │
│ 个人积分：ZSCORE ranking {userId}                  │
│ 附近排名：ZREVRANGEBYSCORE + LIMIT                │
└──────────────────────────────────────────────────┘

┌─ 大规模优化 ─────────────────────────────────────┐
│                                                  │
│ 问题：千万级 ZSet 内存大 + 更新频繁                │
│                                                  │
│ 方案 1：分段排行榜                                │
│   [0~1000分] [1001~5000分] [5001~∞]              │
│   先看分数段 → 查该段内的 ZSet → 小数据量排序     │
│                                                  │
│ 方案 2：定时计算 + 缓存                           │
│   - 用户行为 → 积分变动 → Redis ZSet 实时更新      │
│   - 定时任务（每分钟）→ 计算前 100 → 缓存          │
│   - 前端展示用缓存结果（非实时 OK）                │
│   - 个人排名实时查 ZSet                           │
│                                                  │
│ 方案 3：多级排行榜                                │
│   - 小时榜 → 用小 ZSet（只存当小时数据）           │
│   - 天榜 → Redis + 定时归档 MySQL                 │
│   - 总榜 → MySQL + 定时计算                       │
└──────────────────────────────────────────────────┘
```

### 4. 设计一个消息推送系统

**需求**：向百万用户推送消息（App Push/短信/邮件），不丢消息，不重复。

> **项目锚点**：Flavor Dash外卖平台 —— WebSocket + RabbitMQ 实现订单状态实时推送（已接单→配送中→已送达），延迟<500ms。生产者confirm模式 + 消费者手动ack保证不丢消息，失败重试走死信队列。

```
┌─ 架构设计（Flavor Dash实测） ──────────────────────┐
│                                                  │
│ 1. 消息创建                                      │
│   运营后台创建推送任务 → 入库（消息表 + 目标用户表）│
│                                                  │
│ 2. 用户筛选                                      │
│   - 按标签/行为筛选目标用户                       │
│   - 分批取出用户 ID 列表                          │
│   - 推送目标写入 Redis Queue                      │
│                                                  │
│ 3. 推送执行（WebSocket实时推送，Flavor Dash实现）   │
│   - 订单状态变更 → RabbitMQ消息 → WebSocket推送用户  │
│   - 生产者confirm模式确保消息到达MQ                  │
│   - 手动ACK + 死信队列处理消费失败（重试3次）         │
│                                                  │
│ 4. 可靠性保证（Flavor Dash实测）                   │
│   - 消息不丢：MQ（RabbitMQ confirm + 手动ack）      │
│   - 延迟<500ms：WebSocket全双工通信                 │
│   - 失败重试：死信队列 + 指数退避 ×3                │
│   - 限流：控制调用频次（防第三方 API 限流）        │
│                                                  │
│ 5. 跟踪与统计                                    │
│   - 下发量 → 到达量 → 点击量 → 转化量             │
│   - 实时大盘 + 离线报表                           │
└──────────────────────────────────────────────────┘
```

│  核心表设计（5表 + 1数据规则表）：                   │

│  ├── sys_permission (id, name, code, url, method)   │
│  ├── sys_user_role (user_id, role_id)              │
│  ├── sys_role_permission (role_id, perm_id)        │
│  └── sys_data_rule (role_id, table_name, condition) │
│      例：(ROLE_DOCTOR, medical_record, "doctor_id={userId}")│
│                                                    │
│  鉴权流程（Gateway + Spring Security）：              │
│  Gateway Filter                                     │
│    ↓                                                │
│  ① 解析 JWT → 获取 userId + role                   │
│  ② 查 Redis 「user:perm:{userId}」 → 功能权限匹配    │
│  ③ 查 Redis 「user:data_rule:{roleId}」 → 数据权限   │
│  ④ 请求到业务层 → MyBatis-Plus自动拼接数据权限SQL    │
│                                                    │
│  权限变更 → Canal binlog → MQ → 刷新Redis缓存       │
└──────────────────────────────────────────────────────┘
```

## 二、场景题

### 7. 线上接口突然变慢，怎么排查？

> **项目锚点**：Flavor Dash真实排障经历 —— LLM API调用超时导致Tomcat线程池打满，所有接口响应变慢。完整排查链路：Grafana发现RT飙升 → 看Tomcat线程池（200个线程全部WAITING）→ Arthas trace找出LLM Client调用耗时30s+ → 原因是某厂商模型API响应超时 → 修复：降级熔断（Sentinel）+ 超时缩短至5s + 线程池隔离（LLM调用单独线程池）。

**完整排查链路**：

```
1. 确认问题范围
   ✏ "是所有接口慢还是某个？什么时间开始的？"
   → 看 Grafana 大盘：QPS/RT/Error Rate 曲线

2. 排查数据库
   ✏ SHOW FULL PROCESSLIST
   → 是否有锁等待（Waiting for table lock）？
   → 是否有慢查询堆积？
   
   ✏ 慢查询日志
   → EXPLAIN 关键 SQL → 是否走了索引？type=ALL？
   → 是否出现 filesort/temporary？
   
   ✏ 连接池
   → Druid/HikariCP 监控 → 活跃连接数是否打满？

3. 排查缓存
   ✏ Redis 命中率是否暴跌？
   → 是否热 key 过期（缓存击穿）？
   → 是否 Redis 内存满被淘汰？

4. 排查 JVM
   ✏ jstat -gc PID 1000 → 是否频繁 Full GC？
   ✏ jmap -histo:live PID → 是否有大对象？
   ✏ 是否发生 STW 停顿？

5. 排查下游服务
   ✏ OpenFeign/Dubbo 调用链追踪
   → 哪个下游服务响应变慢？
   → 是否有线程池阻塞？

6. 排查代码层面
   ✏ Arthas trace 方法耗时
   ✏ 日志中是否有异常/重试

7. 排查外部依赖
   ✏ 第三方 API 是否超时？（LLM 模型 API？支付 API？）
   ✏ DNS 解析是否变慢？

8. 临时止血 + 最终修复

### 8. 大量数据（1000W 条）如何高效导入 MySQL？

### 12. 缓存和数据库不一致怎么办？如何保证最终一致性？

> **项目锚点**：SuGuangMall电商（多级缓存一致性更复杂）—— Cache Aside + 延迟双删（更新DB后休眠500ms再删缓存，清理脏数据）+ TTL 10分钟兜底 + Canal监听Binlog异步MQ删缓存。Caffeine一级缓存（本地）+ Redis二级缓存，更新时需同时失效两级缓存，通过MQ广播通知各实例清除本地Caffeine缓存。

```
问题根源：Cache Aside 模式下，更新 DB + 删除缓存的非原子性

┌─ 方案 1：延迟双删（SuGuangMall应用） ────────────┐
│ ① 删除缓存（Caffeine + Redis 两级同时删除）        │
│ ② 更新 DB                                        │
│ ③ 休眠 500ms                                     │
│ ④ 再次删除缓存（清理"②期间读到旧数据回填的脏缓存"）│
│ → 简单但不够可靠（500ms 是经验值）                 │
└──────────────────────────────────────────────────┘

┌─ 方案 2：订阅 Binlog（SuGuangMall实测） ──────────┐
│ ① 更新 DB                                        │
│ ② Canal 监听 MySQL binlog                        │
│ ③ 解析到数据变更 → 发 MQ                          │
│ ④ 消费者 → 删除/更新 Redis（广播通知清除Caffeine） │
│ → 可靠，异步，最终一致性                          │
└──────────────────────────────────────────────────┘

┌─ 方案 3：MQ 异步重试 ───────────────────────────┐
│ ① 更新 DB                                        │
│ ② 发 MQ 消息「删除缓存 task:xxx」                 │
│ ③ 消费者删除缓存（Redis+Caffeine两级）            │
│ ④ 删除失败 → 重试队列 → N 次重试 → 死信 → 人工处理 │
│ → 可靠，但增加了 MQ 依赖                          │
└──────────────────────────────────────────────────┘

┌─ 读者问题：极端情况下读到脏数据怎么办？ ────────┐
│                                                  │
│ 关键：Cache Aside 模式下，脏数据的生命周期很短      │
│                                                      │
│ 时间线（脏数据产生）：                              │
│ T1：缓存过期（删除）                                │
│ T2：读请求 A → miss → 查 DB（旧数据）→ 准备写缓存   │
│ T3：写请求 B → 更新 DB（新数据）→ 删除缓存           │
│ T4：读请求 A → 把旧数据写回缓存 ❌ 脏缓存！          │
│                                                      │
│ 脏数据持续到：下一次缓存过期 / 下一次更新                │
│                                                      │
│ 缓解：                                              │
│   - TTL 不要太长（5~10 分钟）                         │
│   - 关键数据用延迟双删                               │
│   - 业务层面容忍短暂不一致                           │
└──────────────────────────────────────────────────┘
```

### 14. 如何设计一个限流系统？

> **项目锚点**：SuGuangMall电商全链路限流 —— Gateway层全局QPS限流3000、秒杀接口独立2000 QPS阈值（Sentinel）、热点参数限流（同一用户1s最多1次）、线程池隔离（秒杀/订单/支付各用独立线程池防级联）。所有阈值经JMeter压测验证。

```
┌─ 限流算法 ───────────────────────────────────────┐
│                                                  │
│ 1. 固定窗口（Fixed Window）                       │
│   窗口内计数，超过阈值拒绝                        │
│   问题：边界突发（窗口切换瞬间打满）               │
│                                                  │
│ 2. 滑动窗口（Sliding Window）                     │
│   过去 N 秒内的请求计数                           │
│   Redis ZSet 实现：key=timestamp, score=timestamp │
│   每次请求：ZREMRANGEBYSCORE 清理过期 + ZADD + COUNT│
│   → 平滑，精准，稍重                              │
│                                                  │
│ 3. 漏桶（Leaky Bucket）                          │
│   请求放入桶 → 固定速率流出                        │
│   桶满则拒绝                                      │
│   → 绝对平滑，但无法应对突发                       │
│                                                  │
│ 4. 令牌桶（Token Bucket）★ Sentinel 默认          │
│   固定速率生成令牌 → 请求拿令牌 → 没有则拒绝        │
│   桶满可积攒令牌 → 允许一定突发                     │
│   → 最常用，平衡平滑和突发                         │
│                                                  │
│ 5. 滑动日志（Sliding Log）                        │
│   记录每次请求的时间戳                             │
│   新请求时统计过去 N 秒内的时间戳数量               │
│   → 最精准，但内存开销大                           │
└──────────────────────────────────────────────────┘

┌─ 限流架构层次（SuGuangMall实测阈值）───────────────┐
│                                                    │
│  ① Nginx limit_req_zone：单IP 10次/秒（防爬虫）    │
│  ② Gateway Sentinel：全局 QPS 3000（全服务共享）    │
│  ③ 服务 Sentinel：秒杀接口 QPS 2000（独立阈值）     │
│  ④ 热点参数限流：同一用户 1s/1次（防脚本刷单）      │
│  ⑤ 线程池隔离：秒杀/订单/支付独立线程池（防级联）    │
│  （所有阈值经JMeter压测验证，超过则快速失败降级）    │
└──────────────────────────────────────────────────────┘
```

## 三、数据量与并发预估

### 15. 给定业务场景，估算 QPS 和存储

> **项目锚点**：SuGuangMall电商数据 —— 以秒杀接口实测QPS 2000+作为基准，反推业务量级。秒杀场景 100W人抢1W件商品，峰值QPS可达2000+（JMeter实测），日常接口均值约116 QPS（按100W DAU估算）。

**经典面试题**："我们每天有 100W 活跃用户，每人平均 10 次请求，请估算 QPS 和存储"

```
日活跃用户：100W
每人日均请求：10 次
日均总请求：100W × 10 = 1000W

平均 QPS = 1000W / 86400 ≈ 116 QPS

峰值 QPS（按 3 倍均值~10 倍均值）：
  一般峰值 = 116 × 3 = 348 QPS
  极端峰值 = 116 × 10 = 1160 QPS

存储估算（假设有日活相关数据）：
  每条请求日志 ≈ 500 字节
  每天日志量 = 1000W × 500B = 5GB/天
  保留 30 天 = 150GB
  保留 1 年 = 1.8TB
```

**MySQL 单表容量估算**：
```
1000W 行 × 每行 1KB ≈ 10GB + 索引 3GB ≈ 13GB
→ 单表 OK，但接近瓶颈
→ 考虑分表或冷热分离
```

**Redis 内存估算**：
```
缓存 10W 个热点用户信息，每个 1KB
→ 10W × 1KB ≈ 100MB（纯数据）
→ 加上 Redis 内部开销（指针、过期字典等）×1.5
→ 实际 ≈ 150MB
→ 单实例 OK
```
